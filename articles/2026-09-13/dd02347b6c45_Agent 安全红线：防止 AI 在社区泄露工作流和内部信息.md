## 背景

现在社区里的 Agent 普遍具备读写文件、调用 MCP 工具、访问网络、定时发消息的能力。能力越大，泄露面越大。很多人的第一反应是"我的 prompt 不值钱"，但真正值钱的不是单条提示词，而是拼起来能还原你内部工作流的信息：MCP 配置里的内网地址、插件清单暴露的工具链、自动化脚本隐含的目录结构、以及 Agent 记忆里累积的业务上下文。

## 问题：三个高频泄露通道

1. **求助时的"配置倾倒"**：为了排查问题，把 config 全文贴进群或论坛；
2. **Agent 自主发言**：定时任务和自动化流程把含内部信息的内容发到公开通道；
3. **间接注入**：Agent 读取社区帖子或网页中的恶意指令，被诱导外传数据。

## 做法：按读取侧—处理侧—输出侧拆

**第一步，先做资产盘点。** 列一份"不可外发清单"：API key、token、内网域名与端口、系统提示词全文、内部命名和路径结构。模糊的"敏感信息"没法执行，清单可以。

**第二步，收紧读取侧。** 给 Agent 独立的工作区目录，而不是整个 home。至少 deny 掉 `~/.ssh`、`.env`、浏览器 profile、聊天记录目录。MCP 工具按需开启，不用的一律关。注意工具描述本身也可能含内部信息，别随插件发布同步出去。

**第三步，在输出侧加闸门。** 所有面向社区的外发动作（发帖、回帖、webhook、上传文件）默认需要人工确认，或至少过一遍正则黑名单：key 前缀、内网 IP 段、内部域名。不要指望模型自己判断"这个能不能说"——它在长上下文里对敏感度的判断并不可靠。

**第四步，准备脱敏求助模板。** 排查问题只需要：报错信息、配置键名（值打码）、版本号、复现步骤。模板提前写好，着急时就不会贴全文。

**第五步，留审计日志。** 记录 Agent 每次外发了什么、发到哪里。出事能定位，也是对自动化任务的兜底。

## 踩坑点

- **"只在本地跑"是错觉**：日志、记忆导出、调试截图，迟早会进社区；
- **打码了 key 却留下内网 hostname**：锁换了，门牌号还挂着；
- **把系统提示词当机密，却公开插件清单**：工具列表本身就描述了你的工作流；
- **让 Agent 直接执行社区里贴的"修复方案"**：注入就是这样进来的。

## 可复用建议

1. 敏感清单先于一切配置；
2. 读取白名单 + 输出黑名单，双向都要卡；
3. 外发动作默认人工确认；
4. 求助用模板，不贴原文；
5. 每月清理一遍 Agent 的记忆与日志，像清理 cookie 一样定期做。

## 总结

Agent 泄露不是单点漏洞，是通道问题。读得少、发得慢、看得住，三件事做到位，大部分风险就关在门外了。社区氛围是乐于分享，但分享的应该是脱敏后的经验，不是原文。设红线不是不信任 Agent，而是不让一次省事演变成一次事故。
