## 背景

社区日常运营里有不少固定动作：每周精华帖汇总、GitHub issue 周报、新成员答疑合集。这些活儿格式固定、重复度高，靠人做每周要耗掉两三个小时。于是我用 OpenClaw 搭了一个发帖机器人，目标很明确：不是全自动，而是机器出草稿、人审一遍、定时发布。

## 问题

一开始我偷懒，写了个大 prompt 丢给模型，让它"收集本周 issue → 生成帖子 → 调用发布 API"。跑了一周就暴露三个问题：

1. 同一内容重复发帖两次（任务重试导致）；
2. 模型编造了不存在的 issue 链接；
3. 深夜三点发帖，被群友截图调侃。

本质原因是：把"取数、生成、发布"三个职责塞进了一个不可控的黑盒里，出了问题既难定位，也难兜底。

## 架构与做法

重构后拆成五层，各司其职：

1. **调度层**：cron 触发，显式指定 `Asia/Shanghai` 时区，任务配置持久化到 SQLite。
2. **内容层**：Agent 通过 MCP 工具拉取数据源（issue 列表、精华帖元数据），只接收结构化 JSON，不让模型"凭记忆"写素材。
3. **校验层**：所有链接必须来自工具返回值，并逐一做 HTTP 可达性检查；正文过一遍长度与敏感词校验。
4. **状态层**：以 `(source_id, publish_date)` 作为幂等键，数据库唯一索引兜底。
5. **发布层**：默认写入草稿箱，人工确认后才真正发布；遇到 429 用指数退避加随机抖动重试。

改完之后，重复发帖和幻觉链接基本消失，人工审核耗时从半小时降到五分钟以内。

## 踩坑点

- **幂等没第一天做**：第一版重试逻辑是"失败就重跑"，没有状态记录，一次网络抖动发了三遍。教训：幂等键和唯一索引应该是最先写的代码。
- **模型不能当事实来源**：让模型"引用链接"，它就敢编。正确姿势是工具返回候选集，模型只做筛选和组织。
- **凭证差点进仓库**：平台 token 硬编码在配置文件里，commit 前才发现。现在统一走环境变量，且只授予发帖所需的最小权限 scope，不给删除权限。
- **限流处理太天真**：固定 3 秒重试，遇到连续 429 直接崩。改成指数退避 + 抖动，连续失败 N 次后降级为"通知人来处理"。
- **长文截断**：平台有字数上限，超长帖直接报错。发布前预校验长度，超长自动降级为摘要版。

## 可复用建议

1. 发帖类机器人永远先做半自动：草稿箱 + 人工确认是安全底线。
2. 状态必须落库，别依赖进程内存——机器人随时可能被重启。
3. 每个环节可单独重跑，失败日志带上 task_id，方便定位。
4. 把模型定位成"编辑"，而不是"记者"：素材由工具提供，模型只负责组织语言。

## 总结

这个机器人上线一个月，稳定产出了四期周报，返工率从接近一半降到个位数。最大的心得是：自动化省下的是重复劳动，判断权要留在人手里。架构上多做一层校验、多留一个确认点，看似流程变慢，实际省掉了大量事后救火的时间。欢迎在评论区交流你们的发帖自动化实践。
