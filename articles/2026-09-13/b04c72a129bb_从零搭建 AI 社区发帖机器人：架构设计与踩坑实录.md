## 背景

社区每天都会产生值得沉淀的内容：高质量问答、issue 里的关键结论、分享纪要。之前靠人工整理"每日精选"，坚持三周就断了——整理半小时，发帖五分钟，多数人卡在前者。

于是有了这个项目：用 OpenClaw 的 Agent 能力搭一个发帖机器人，定时抓取社区内容，生成摘要帖并自动发布。跑了两个多月、发帖 60+，中途翻过几次车，把架构决策和坑记下来。

## 核心架构决策

最重要的一个决定：**Agent 只负责"写"，确定性代码负责"拿、去重、发"。** 最初想让 Agent 全权编排，实测问题很大（见坑 1），最终收敛为五层流水线：

1. **抓取**：Python 脚本定时拉论坛 API 和 RSS，写入 SQLite；
2. **过滤**：URL 哈希 + 标题相似度去重，只留当日新增候选；
3. **生成**：Agent 通过两个 MCP 工具工作——`query_digest` 读候选，`submit_post` 提交草稿；
4. **审核**：dry-run 默认开启，草稿先落库，前两周人工放行；
5. **发布**：限速、重试、幂等键控制。

## 踩坑实录

**坑 1：让 Agent 编排一切。** 早期版本把抓取也交给 Agent 调工具完成，某次论坛 API 超时后它陷入重试循环，一晚上烧掉的 token 够平时跑一周。教训：循环、重试、状态管理这类需要确定性的环节交给代码，LLM 只放在生成环节。

**坑 2：幻觉链接。** 摘要帖的引用链接，模型偶尔会"编"一个格式正确但不存在的 URL。对策：URL 全部来自结构化数据，prompt 里明确要求只准原样引用上下文中的链接，禁止拼接生成。

**坑 3：重复发帖。** cron 意外重跑，同一天发了两帖。对策：发帖记录建唯一索引，以本地日期为幂等键，发布前先查库。

**坑 4：MCP 工具给太多。** 最初一口气挂了七个工具，Agent 经常选错，该读摘要时去调发布。精简到两个、把前置条件写进工具描述后，选错率基本归零。工具描述本身就是 prompt 的一部分，值得认真写。

**坑 5：时区。** 调度按 UTC 跑，晚上十点生成的摘要是"昨天"的内容。幂等键改用 Asia/Shanghai 日期后解决。这类问题不炸则已，一炸就是数据错乱。

**坑 6：语气漂移。** 跑了几天后帖子风格开始跑偏。对策：把两三篇人工认可的历史帖固定进 system prompt 作风格样例，生成后加一步自检。

## 可复用建议

- **先 dry-run 两周**：人工放行，质量稳定后再放开全自动；
- **幂等设计提前做**：日期唯一键 + 发帖前查库，成本极低，收益极大；
- **工具数量克制**：两三个足够，描述写清前置条件与返回格式；
- **状态落盘**：SQLite 够用，别依赖 Agent 的上下文记忆；
- **失败可观测**：失败时往群里推一条通知，别让机器人静默挂掉。

## 总结

两个多月下来维护成本很低，真正的经验只有一条：把不确定性和确定性分开。LLM 擅长写，不擅长可靠地编排和记状态；抓取、去重、限速、幂等交给代码，Agent 反而更稳。想搞自动化发帖的同学，建议从这个最小架构起步，先跑通 dry-run，再谈智能化。
