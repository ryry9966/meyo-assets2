## 背景

社区运营里有两类内容高度重复：每周的更新速递、对高频问题的标准化回复。手写两周之后就会发现，时间全花在复制粘贴和排版上。于是我用 OpenClaw 加 MCP 工具搭了一个发帖机器人，目标很克制：给它信息源，它产出草稿，人审完一键发布。不求全自动，先求稳定。

## 问题

最初的版本很直接：一个 cron 触发，prompt 里塞上“写一篇社区周报”，直接调发帖 API。跑了一周就暴露三个问题：

1. 模型会编造不存在的链接和版本号；
2. 同一批源内容反复被写成雷同的帖子；
3. 重试逻辑和发帖接口没有幂等保障，一次网络抖动发了两遍。

## 做法：Draft-First 流水线

重构后的架构分四层：

- **触发层**：cron 加手动触发双通道，任务配置全部进版本库；
- **采集层**：MCP 工具负责抓取——仓库 release、社区未读帖、RSS。只有工具返回的 URL 才允许进入上下文；
- **生成层**：Agent 两段式工作，先用小模型把源内容压成结构化摘要，再由主模型基于摘要写稿，prompt 中明确“禁止输出工具结果之外的链接”；
- **发布层**：草稿先落库（SQLite），进审核队列，人工通过后才调发帖接口。

关键设计是幂等键：`hash(源条目 ID + 发布周期)`。同一条源内容无论重试多少次，发布层都会先查这个键，查到即跳过。

## 踩坑实录

- **去重做错了对象。** 一开始对生成文本做相似度去重，成本高且不稳定；改成对源条目做哈希，问题直接消失。去重的粒度应该是“事实”，不是“表达”。
- **时区。** cron 按容器默认 UTC 跑，周报提前八小时发出。所有调度时间显式写死时区，别依赖默认值。
- **两段式摘要是必须的。** 把一周的 release note 全量塞进上下文，token 开销翻了几倍，主模型还会漏重点。先压缩再生成，质量和成本同时改善。
- **Markdown 转义。** 正文里的下划线和代码片段被论坛渲染吃掉，后来加了一步格式化校验：生成后按目标平台的渲染规则先过一遍再入库。
- **审核疲劳。** 前两周每篇都人工审，之后发现生成层几乎不出错，就改成“低风险内容自动发，含外链或新话题的必须审”。审核规则要随信任度演进，不要一步到位。

## 可复用建议

1. 进入正文的外部事实必须来自工具返回，prompt 层面禁止模型凭记忆补链接；
2. 一切写操作上幂等键，重试才有安全感；
3. 草稿落库而不是直接发布，给自己留回滚和改写空间；
4. prompt 与调度配置进版本库，出问题能 diff 出是哪次改动引入的；
5. 日志记全链路：触发时间、采集条目数、草稿 ID、审核人、发布结果。

## 总结

上线一个月，周报从手写 40 分钟降到审稿 5 分钟。回头看，最关键的不是模型能力，而是把“生成”和“发布”拆开、给写操作上幂等锁这两件事。自动化项目里，工程上的克制比 prompt 技巧更能决定成败。欢迎在评论区交流你们的工作流设计。
