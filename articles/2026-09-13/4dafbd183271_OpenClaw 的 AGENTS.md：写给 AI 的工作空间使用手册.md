## 背景

OpenClaw 的 agent 每次进入一个工作空间，面对的都是同样的冷启动问题：这是个什么项目、目录怎么组织、测试怎么跑、哪些路径不能碰。这些答案固定，却往往不写在任何地方，只能靠 system prompt 里反复口述，或者让 agent 自己猜。

AGENTS.md 是社区逐渐形成的开放约定：在仓库里放一份 Markdown，专门写给 AI agent 看，就像 README 写给人看一样。OpenClaw 原生支持这个约定，会话启动时自动把工作空间内的 AGENTS.md 注入上下文。

## 没有手册时会发生什么

- agent 猜错包管理器，用 npm 去跑 pnpm 项目；
- 不知道单测入口，自己造一条会污染本地状态的命令；
- 改了生成目录里的文件，下次构建被覆盖；
- 每个新会话、每个新同事都要重新教一遍，同样的坑反复踩。

这些不是模型能力问题，是信息缺失问题。解法很朴素：把事实写下来，并让它随代码一起维护。

## 怎么写一份能用的 AGENTS.md

1. **分层放置**。全局偏好放用户级（比如 commit message 风格），项目级放仓库根，子模块特例放子目录。OpenClaw 按就近原则合并，近处覆盖远处。
2. **只写事实和可执行动作**。推荐分区：一句话项目概述、目录结构及"哪些目录不要动"、构建/测试/lint 的确切命令、代码风格约定、明确禁止的事项。
3. **让 agent 起草初稿**。让它先扫描仓库生成一版，人工删掉废话、补上它不知道的坑，比从零写快得多。
4. **进版本控制，走 PR review**。它影响 agent 的每一次行为，值得和代码同等对待。

## 踩坑点

- **写太长**。几百行"重要事项"等于没有重要事项，上下文被稀释后 agent 开始各凭心情。一到两屏为宜，细则下沉到子目录。
- **写愿望不写动作**。"请写出高质量代码"没有信息量；"提交前跑 `make check`，失败不要 commit"才可执行。
- **过期即毒药**。重构改了命令但没更新文件，agent 会忠实执行那条必然报错的旧命令。把"改命令必须同步改 AGENTS.md"加进 review 清单。
- **层级冲突**。根目录和子目录说法不一致时，agent 行为不可预测，合并前先自查一遍。
- **别放敏感信息**。它会被注入每次会话上下文，密钥、内网地址一律不写。

## 可复用的建议

把它当成 agent 的回归测试集来运营：agent 每犯一次错，就补一条针对性规则，和给代码补测试是同一件事。同时控制总量，新增规则时问一句"能不能删掉某条旧的"。如果接了 MCP 工具或插件，工具的使用约定也应该写进去——工具能力描述归服务端，工作空间的使用偏好归 AGENTS.md，两边职责分开，避免同一件事写两处。

## 总结

AGENTS.md 的价值不在文件本身，而在于它把"教 agent"从一次性口述，变成了可版本化、可 review、可持续积累的工程资产。写得克制、写得具体、随代码一起维护，agent 输出的稳定性会有肉眼可见的提升。建议从今天的工作空间开始：先让 agent 起草，你只负责删。
