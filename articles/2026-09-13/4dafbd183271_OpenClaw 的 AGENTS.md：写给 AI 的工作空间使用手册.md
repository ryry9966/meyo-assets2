## 背景

OpenClaw 的 agent 每次会话启动时，会把工作区里的一组固定文件注入上下文，`AGENTS.md` 是其中最核心的一个。可以把它理解成 README 的镜像：README 写给人看，AGENTS.md 写给模型看。它不是普通文档，而是运行时会被逐字读取的配置，你写什么，agent 的行为边界就在哪。

## 问题

没有 AGENTS.md 时，agent 的行为完全依赖模型默认习惯加对话内临时纠偏。实际跑下来有几个典型症状：

- **文件乱放**：长期记忆写进临时目录，产物直接覆盖源码；
- **工具乱用**：明明该走 MCP 查询，偏偏自己编数据；
- **重复踩坑**：同一个错误每个会话犯一遍，你要反复口头纠正。

口头纠正是会话级的，会话结束就清零；AGENTS.md 是持久化的。这就是它的价值——把你纠偏过一次的东西固化下来。

## 做法

以 OpenClaw 默认模板为骨架，按这个顺序填：

1. **先写硬约束**。开头三五行只放“绝不允许”的事：不删除工作区既有文件、密钥不写入任何记忆文件、对外消息需确认。这类指令模型遵循率最高，必须放最前面。
2. **画工作区地图**。每个文件、目录一句话说明用途，明确“什么写到哪”：长期事实进 `MEMORY.md`，会话草稿进 `tmp/`，互不越界。
3. **写工具规则**。列出工具优先级与禁用场景，例如“查询一律走 MCP 工具，不可用时明确说明，不要编造”。
4. **定义记忆协议**。什么值得记、何时写、什么格式，否则 `MEMORY.md` 很快变成垃圾场。
5. **控制篇幅**。全文建议 100 行以内——它每轮都占上下文，越长，单条规则的权重越被稀释。

一个可抄的极简骨架：

```markdown
# 硬约束
- 不删除/覆盖工作区既有文件，产物写进 outputs/
- 密钥、内网地址不写入任何记忆文件

# 工作区地图
- MEMORY.md：长期事实，一条一行，带日期
- tmp/：会话草稿，可随时清理

# 工具规则
- 查询一律走 MCP 工具，不可用时明确说明，不要猜
```

## 踩坑点

- **写成宣传文案**。agent 需要祈使句规则，不需要自我介绍。“你是热情的助手”归 `SOUL.md` 管，别占 AGENTS.md 的预算。
- **文件之间职责重叠**。AGENTS.md、`SOUL.md`、`MEMORY.md` 内容互相冲突时，模型行为不可预测。分层原则：性格归 SOUL，规则归 AGENTS，事实归 MEMORY。
- **改完不重开会话**。会话中途修改 AGENTS.md 不会热加载，新会话才生效。别误以为是写法问题。
- **把它当保险箱**。AGENTS.md 全文进上下文，且通常被 git 追踪，密钥、内网地址、客户信息一律不写。

## 可复用建议

把维护 AGENTS.md 当作日常操作，而不是一次性配置：

- agent 每犯一个错，就沉淀一条对应的禁令，这比换模型、写插件便宜得多；
- 每两周回头清理一次失效规则，防止膨胀；
- 用 git 管理，改动走 commit，出问题可回滚、可 diff；
- 经验上，一条精确的负面规则（“不要 X”）比十条正面描述更能改变行为。

## 总结

调 agent 的手段很多——换模型、写插件、接 MCP——但性价比最高的，往往是把 AGENTS.md 写扎实。它是你和 agent 之间唯一稳定、可版本化、可复现的接口，值得像对待代码一样对待它。
