# 让 Agent 替你写 E2E 测试：一套可落地的协作流程

## 背景

E2E 测试是典型的"人人都说重要，没人愿意维护"的活儿。写一条 Playwright 用例不难，难的是覆盖几十条用户流程、跟着 UI 迭代持续修复。LLM 出现后，"AI 生成测试"听起来很美，但直接甩一个 URL 让模型写测试，产出的用例往往一跑就挂。问题不在模型不会写代码，而在它看不见你的页面。下面是我们跑通的一套 Agent 协作流程。

## 问题

直接生成的测试通常有四类毛病：

- **选择器靠猜**：生成 `div.container > button.primary` 这类脆弱选择器，改一版样式就崩；
- **不懂工程约定**：不知道你的 fixture、登录态、测试数据怎么准备；
- **断言流于形式**：断言了 class 名，却没断言业务结果，绿了也不说明任何事；
- **批量生成失控**：一次产出二十条用例，半数失败，评审成本反而比手写更高。

## 做法

核心思路：把 Agent 接到真实浏览器上，而不是让它凭空想象。分四步：

1. **给 Agent 装上眼睛。** 通过 Playwright MCP（或同类 browser MCP）让 Agent 能导航、点击、读取页面的 accessibility snapshot。所有选择器必须来自真实快照，优先 `getByRole` / `getByTestId`。
2. **喂工程约定。** 在仓库放一份 `testing-conventions.md`：选择器策略、等待策略（禁止硬 sleep）、fixture 用法、断言风格，作为上下文注入每次生成。
3. **单流程迭代生成。** 一次只处理一条用户流程（如"登录后创建订单"）。循环是：探索页面 → 生成 spec → 运行 → 失败信息回喂 → 修复，一般 2~3 轮收敛。
4. **人审断言 + CI 验稳定性。** Agent 产出后，人只审一件事——断言是否表达了业务意图。合入前在 CI 连续跑 3 次全过才算稳定。

## 踩坑点

- **别让 Agent 看截图写测试。** 视觉猜测的选择器极脆弱，一律以 accessibility tree 为准。
- **一次生成太多。** 超过一条流程，修复回路就会失控，小批量快迭代。
- **硬等待污染。** 模型爱写 `waitForTimeout(3000)`，在约定文件里明确禁止，强制条件等待。
- **测试数据硬编码。** 给测试工具链包一层薄 MCP server，暴露登录、造数、清理接口让 Agent 调用，别让它自己编数据。
- **全绿就合入。** 没有有效断言的测试照样全绿，绿不等于对。

## 可复用建议

- 把 `testing-conventions.md` 当作 Agent 的"系统提示词"沉淀进仓库，团队共用一套上下文。
- 单流程生成 + 失败回喂的循环 prompt 存成团队模板，换人也能跑出同样质量。
- 维护阶段同样受益：UI 改版后把失败用例 + 新快照喂回去，Agent 修选择器的成功率相当高，这往往比生成新测试更省时间。
- 把 Agent 产出当实习生的 PR 看待：重点 review 断言逻辑，而不是它能不能跑绿。

## 总结

Agent 协作改变的不是"能不能写出 E2E"，而是成本结构：写的成本大幅下降，评审与约定维护成为新的核心工作。把 Agent 锚定在真实页面状态上，用约定约束生成，用人审把关断言——这套流程跑顺之后，补齐历史欠账的测试覆盖率，是一件可以正常排期推进的事。
