## 背景

大多数 Agent 的工作模式是被动应答：你不发消息，它就安静待着。问答场景没问题，但如果你把它当作长期运行的自动化助手，很快会发现一个尴尬的事实——它不知道"现在该干嘛"。磁盘快满了、某个同步任务三天没跑、你昨晚让它盯的结果早出来了，但没人问，它就不说。

OpenClaw 的 HEARTBEAT.md 就是针对这个问题的轻量机制：让 Agent 按固定间隔醒来，读一次这份文件，自己判断有没有该主动做的事。

## 问题

主动化的难点不在"定时执行"，而在"定时判断"。Cron 能跑脚本，但脚本不理解上下文。你真正想要的是：Agent 每个周期醒来后，结合当前状态（文件内容、最近对话、工具返回）自行决定——这事值得打扰用户吗？值得的话做到什么程度？

## 做法

1. 在 Agent 工作区根目录创建 HEARTBEAT.md，用 checklist 形式写清任务：

```markdown
# HEARTBEAT

- [ ] 检查 ~/reports 下是否有超过 24h 未处理的文件，有则汇总发我
- [ ] 如果本地 git 仓库有未推送提交，提醒我（不要自动 push）
- [ ] 每天早 8 点后第一次心跳，摘要当日日历
```

2. 配置心跳间隔。可通过 `HEARTBEAT_INTERVAL` 环境变量设置，默认值偏保守（30 分钟量级）。监控类任务可调到 10–15 分钟，日常巡检 1 小时足够。

3. 每次心跳，Agent 读取该文件并自查：条件满足才执行动作，否则静默返回。这个"静默"很关键——不是每次心跳都必须产出消息。

## 踩坑点

- **任务写得太模糊**。"帮我盯着服务器"这种描述会让 Agent 每次心跳都纠结要不要报告，最后要么刷屏要么装死。每个任务必须有明确的触发条件和明确的动作。
- **心跳太频繁烧 token**。每次心跳都是一次完整的模型调用。只需每 6 小时查一次同步，就别设 5 分钟。
- **把危险操作写成无条件任务**。我早期写过一条"发现依赖更新就自动升级"，结果某个晚上它真升了，搞挂了一个 API 版本。主动任务务必区分"只报告"和"可执行"，执行类动作加白名单。
- **心跳输出污染主对话**。低价值信息建议让它走日志或独立通道，别和正常聊天混在一起。

## 可复用建议

- 任务模板固定三段：**条件（什么时候）+ 判断（查什么）+ 动作（做什么 / 或只报告）**。
- 用注释区分任务级别，比如"每次心跳必查"和"每日一次"，Agent 对频率的理解比你预期的可靠。
- HEARTBEAT.md 本身也是文件，可以进 git。改任务就是改文件，下次心跳自动生效，不用重启。
- 要求心跳输出结构化摘要（一句话结论 + 是否需要你介入），长期下来会积累一份很有价值的"Agent 值班日志"。

## 总结

HEARTBEAT.md 的价值不在技术复杂度——它就是一份被周期性读取的 markdown——而在于它把"主动性"变成了可版本化、可审查的文本配置。建议从一个低频、只读的任务起步（比如每日摘要），观察一周心跳日志，再逐步加入需要执行动作的任务。主动的边界，应该由你通过这份文件显式划定，而不是靠模型自己猜。
