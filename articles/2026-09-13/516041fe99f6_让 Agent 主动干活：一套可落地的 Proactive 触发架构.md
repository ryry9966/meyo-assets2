## 背景

大多数 AI 助手的交互模型是"拉"式的：你提问，它回答。而真正省时间的场景往往是"推"式的——CI 挂了它先告诉你、会议前它把相关材料整理好、磁盘快满它提前报警。随着 MCP 让事件源接入 Agent 变得标准化，proactive 能力第一次具备了工程上可落地的条件。

但社区里大量 proactive demo 的实际归宿是：跑三天，被误报轰炸，然后关掉。问题不在模型，在系统设计。

## 问题

把"主动"拆开，其实是三个工程问题：

1. **什么时候触发**（时机与信号源）
2. **该不该动手**（权限与风险）
3. **会不会打扰**（信任与噪音）

多数实现只粗糙地解决了第一条（挂个 cron），后两条完全没管，于是翻车。

## 做法

社区里几个跑得比较稳的实践，结构都收敛到三层：

**感知层：确定性触发。** 用 MCP server 或简单脚本暴露事件：git push、文件变更、CI 状态、日历、阈值指标。关键原则是触发条件必须确定性——磁盘超过 90%、CI 连续两次失败——而不是让 LLM 判断"这件事重不重要"。

**决策层：模型只做加工。** Agent 收到事件 payload 后做三件事：去重、相关性过滤、生成人话摘要。输出被约束为四个动作之一：记日志 / 发通知 / 给建议待确认 / 自动执行。策略写在 YAML 配置里，可 review、可回滚。

**执行层：动作门控。** 写操作默认要确认；每个触发任务带幂等键，防止重启后重复执行；所有主动行为落审计日志，记录触发原因。

然后按阶梯放权：先只读（只汇报）→ 汇总通知 → 建议待确认 → 最后才考虑低风险写操作自动执行。这个爬坡过程建议以周为单位，不要一天放开。

## 踩坑点

- **让 LLM 判断紧迫性。** 实测不可靠，模型倾向于把一切都标记为重要。触发用阈值，LLM 只负责把触发结果说清楚。
- **重复触发。** cron 型 Agent 重启后补跑，同一事件通知两遍。幂等键 + 触发状态持久化，缺一不可。
- **通知疲劳。** 一次误报消耗的信任，比十次有用提醒建立的还多。加冷却窗口和 digest 模式（低优先级事件攒着定时汇总）。
- **一上来就给写权限。** 先只读跑两周，看误报率和触发分布，再谈动手。
- **轮询烧 token。** 高频轮询成本很快超过事件驱动方案。能接 webhook 就别轮询，必须轮询就把间隔拉到可容忍的上限。

## 可复用建议

一句话原则：**触发确定性、内容模型化、动作门控化。**

- proactive 策略放配置文件，像代码一样走 review；
- 每条主动行为记录 trigger reason，事后能回答"它为什么当时动手"；
- 上线前用历史事件回放测一轮，先看误报率，再敢开通知；
- 设静默时段，尊重人的作息。

## 总结

Proactive 不是模型能力的胜利，而是系统工程的结果。模型在其中只负责"怎么说清楚"，而触发、限流、权限这些不起眼的部分，才决定"该不该做"。把这三件事做扎实，Agent 才能真正做到——不等你开口，就把事情办了，而且办得让你放心。
