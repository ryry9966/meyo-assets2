## 背景

Agent 的价值在于闭环：读到结果、做出判断、落到外部系统。OpenClaw 的工具层——无论是 plugin 还是 MCP server——承担的就是"最后一公里"。但社区里不少对接方式还停留在脚本思维：写个函数包一层 HTTP 调用，扔给模型，出问题再打补丁。短期能跑，长期会在认证、上下文膨胀、错误处理上持续还债。

## 问题

把外部 API 直接包装成 tool，反复出现三类故障：

1. **上下文爆炸**：API 原始响应直接透传，一次调用吃掉几千 token，后续对话质量骤降。
2. **模型盲试**：错误信息只有一句 "request failed"，模型不知道错在哪，开始反复猜测重试。
3. **副作用失控**：非幂等操作（下单、发消息）被超时触发的重试放大，产生重复数据。

## 做法

按下面的顺序接入一个外部服务，基本能避开上述问题：

**1. 先定契约，再写代码。** 用 JSON Schema 定义参数，命名对模型友好（用 `date_range` 而不是 `dr`），description 里写清单位、时区、取值范围。这份 schema 是模型理解工具的唯一入口，值得花时间打磨。

**2. 认证收敛到配置层。** 密钥从环境变量或密钥管理服务读取，由 OpenClaw 配置注入，工具代码里只拿引用。禁止硬编码，也禁止把 key 拼进返回值。

**3. 加一层薄 adapter 做响应裁剪。** 筛掉无关字段、截断超长列表、把深层嵌套压成扁平摘要。原则：返回给模型的内容，以"能否支撑下一步决策"为标准，而不是"接口给了什么"。

**4. 把错误设计成可行动的。** 4xx 返回结构化信息：哪个参数、什么原因、建议动作。模型拿到这种错误能自我修正；拿到笼统错误只会盲试。

**5. 超时与重试区别对待。** 所有调用设明确 timeout；只对幂等的读操作做指数退避重试；写操作不自动重试，必要时业务侧加幂等键。

**6. 灰度上线。** 在 MCP/plugin 注册后，先以只读或 dry-run 模式跑通主流程，确认日志脱敏、响应体积正常，再放开写权限。

## 踩坑点

- **大响应直接进上下文**：一个列表接口返回 200 条记录，一轮对话就膨胀。adapter 里必须限流截断。
- **日志泄漏密钥**：debug 时顺手打印完整 headers，key 落盘。日志层要统一脱敏。
- **Schema 静默漂移**：外部 API 改了字段名，工具不报错但返回空。对关键字段做最小校验，缺字段立即快速失败。
- **工具粒度过大**：一个 `do_everything` 工具的描述永远写不清楚，模型选错参数的概率随参数数量上升。

## 可复用建议

- 工具是写给模型的界面，不是写给人的 SDK。描述、错误、返回值，都问一句：模型能据此决策吗？
- 小工具自由组合，优于一个大而全。
- 破坏性操作加 `dry_run` 参数，默认关闭，写操作另要求显式确认。
- adapter 保持薄，外部 API 变更只改一层。
- 每个工具配一个最小冒烟用例，纳入 CI。

## 总结

对接外部服务的关键不是"调通"，而是让每次握手对模型可理解、对系统可控。契约先行、响应裁剪、错误可行动、写操作谨慎——这四件事做到位，OpenClaw 的工具层才经得起长期跑。
