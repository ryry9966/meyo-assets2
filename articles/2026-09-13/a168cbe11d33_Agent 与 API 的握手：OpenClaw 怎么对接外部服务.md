## 背景

Agent 的价值不在对话本身，而在能不能动手。一个只会规划、不会执行的 agent，最后还是把活儿交回给人。OpenClaw 这类 agent 运行时的核心能力之一，就是把外部服务变成模型可以安全调用的工具——通过 MCP server、插件，或直接封装的 HTTP 工具。

## 问题

实际对接中，难点从来不是“发一个请求”，而是：

- 各服务鉴权方式不统一：API Key、OAuth、请求签名各一套；
- 模型生成的参数不可信，格式、单位、枚举值都可能出错；
- 上游报错如何反馈给模型，让它自我修正而不是越修越歪；
- 超时、重试、幂等这些老工程问题，在 agent 自动化场景下被成倍放大。

## 做法

以对接一个内部 REST 服务为例：

1. **选路径。** 服务稳定且需要复用，写一个 MCP server；一次性的脚本场景，直接用 OpenClaw 的 HTTP 工具配置即可，别过度工程化。
2. **定义工具 schema。** 描述是写给模型看的，不是写给文档看的。把参数含义、单位、取值约束写清楚，最好附一组输入输出示例，模型传参准确率提升明显。
3. **封装鉴权与凭据。** 密钥一律走环境变量或凭据管理，不落配置文件、不进提示词。OAuth 类服务在工具层内部做 token 刷新，对模型透明。
4. **错误映射。** 把上游报错翻译成结构化信息：状态、原因、建议动作三段式。避免把 HTML 错误页或堆栈直接透传进上下文。
5. **注册并灰度。** 先只挂只读接口，观察参数命中率和失败模式，再逐步放开写操作。

## 踩坑点

- **没设超时。** 上游 hang 住，agent 跟着卡死，整轮任务作废。所有工具调用必须有显式超时，没有例外。
- **重试放大了写操作。** POST 下单失败自动重试，结果下了两单。非幂等接口要么上游支持幂等键，要么工具层直接禁止自动重试。
- **原始错误污染上下文。** 一大段 stack trace 会把模型带偏，之后的决策全程跑偏。务必二次包装成模型可读的“发生了什么 + 能做什么”。
- **入口不做校验。** 模型偶尔会把数字拼进字符串、日期格式写错。工具入口必须再做一层 schema 校验，永远不要信任上游模型输出。
- **工具越挂越多。** 十几个近义工具同时挂载，模型选错的概率明显上升。宁可用一个带 action 参数的工具收敛，也别堆一堆重复工具。

## 可复用建议

- 工具描述按“模型读者”来写，附两个示例，这是性价比最高的一件事。
- 错误响应固定三段式：状态、原因、建议动作。
- 上线顺序：只读 → 幂等写 → 非幂等写，每一步在真实流量下观察再推进。
- 记录每次工具调用的参数、耗时、结果摘要。出问题时，这是唯一靠谱的证据链。

## 总结

对接外部服务在工程上没有新问题，都是老问题的变体：鉴权、超时、重试、校验、日志。OpenClaw 的 MCP 与插件机制只是把这些边界收拢到一个可控的层里。记住一个朴素的结论：工具层的质量决定 agent 的上限——模型再强，工具不可靠，整体就不可靠。先把手上的 API 包扎实，再谈更复杂的编排。
