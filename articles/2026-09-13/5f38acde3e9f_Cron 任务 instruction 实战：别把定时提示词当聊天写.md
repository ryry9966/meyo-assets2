## 背景

我在 OpenClaw 里长期跑着七八个 cron 任务：每日开发动态摘要、仓库巡检、周报汇总、服务器健康检查。最早几条 instruction 写得像聊天消息——“每天早上整理一下昨天的动态发给我”——结果三种死法轮番上演：**空跑**（执行了但没产出）、**编数据**（工具失败后一本正经地胡说）、**发错地方**（该发频道的发去了私聊）。后来把 instruction 当运维脚本写，才算稳定。

## 问题：cron 是冷启动执行

交互对话里，agent 可以追问、可以参考上文。cron 任务没有这些：它在**没有对话历史的上下文里冷启动**，旁边没有活人帮你澄清。所有你在聊天里靠默契解决的事——现在几点、数据从哪来、发给谁、失败了怎么办——都必须写死在 instruction 里。

## 做法：五段式模板

我现在每条 cron instruction 都按这个结构写：

1. **目标**：一句话说清产出什么。
2. **时间与数据源**：明确“先用工具获取当前时间（时区 Asia/Shanghai）”，数据来自哪个 MCP 工具或命令。不写“最新的”“昨天的”这类悬空词，而是“以工具返回的当前时间为基准，取过去 24 小时”。
3. **步骤**：编号、原子化，抓取 → 过滤 → 汇总，一步一件事。
4. **输出契约**：发到哪个渠道、什么格式、长度上限。例如“Markdown，≤300 字，无内容则不发送”。
5. **失败行为**：工具调用失败怎么办。我固定写“重试一次，仍失败则发一行失败说明，禁止用旧数据或编造内容凑数”。

对比一下：

```text
❌ 每天早上整理一下昨天的 GitHub 动态发给我

✅ 目标：生成过去24小时仓库动态摘要。
   时间：调用 date 工具取当前时间（Asia/Shanghai），据此计算时间窗。
   步骤：1) 用 github 工具列出 org/repo 过去24h 的 issue/PR；
         2) 过滤 bot 与 renamed/closed 事件；
         3) 按"新issue/新PR/已合并"三类汇总。
   输出：发到 #dev-daily，Markdown，≤300字，每条一行；无动态不发送。
   失败：重试1次，仍失败发一行失败说明；禁止编造。
```

## 踩坑点

1. **时区分裂**：cron 表达式按容器时区（常见 UTC）触发，instruction 里却写“每天早上九点”。先确认服务端时区，表达式和 instruction 用同一基准。
2. **“昨天”的边界**：午夜附近跑的任务，相对时间容易算错窗口。让 agent 基于工具返回的时间算区间，别靠模型估。
3. **引用不存在的上下文**：instruction 里出现“上次提到的那个项目”，冷启动时只能靠猜。每条 cron 必须自包含。
4. **静默失败最危险**：不写失败路径时，模型倾向于“装作成功”。失败行为是必选项，不是可选项。
5. **高频任务叠重 instruction**：5 分钟一次的任务带上千 token 的说明纯属烧钱。拆成“轻量检查 + 条件触发重活”。
6. **改完不实测**：instruction 就是代码，改完立即手动触发跑通一次再上线。

## 可复用建议

- 五段式模板直接抄：目标 / 时间与数据源 / 步骤 / 输出契约 / 失败行为。
- instruction 变更纳入 review，在任务备注里留一行改动记录。
- 每条 cron 配一条手动触发命令，当冒烟测试用。
- 输出契约写“上限 ≤N 字”，比写“尽量简洁”有效得多。

## 总结

Cron 的 instruction 不是聊天 prompt，而是写给“未来某个没有上下文的执行者”的运行手册。**自包含、时间显式、输出有契约、失败有出路**——这四条做到，定时任务才能从偶尔抽风变成可以托付。
