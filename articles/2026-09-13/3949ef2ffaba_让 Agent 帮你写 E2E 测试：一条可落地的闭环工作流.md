## 背景

E2E 测试大概是团队里最没人爱写的部分：写起来慢、选择器脆、UI 一改就崩。很多同学尝试过让 LLM "一句话生成测试"，结果往往是代码看着像样，一跑全红——因为模型没有真正"看到"页面，选择器和等待点全靠猜。

思路需要换一下：不要单次生成，而是让 Agent 拿到浏览器工具（比如通过 MCP 接入 Playwright），进入"探索 → 生成 → 执行 → 修复"的闭环。生成时带上运行时反馈，质量完全是另一个量级。

## 问题

单次生成有三个典型失败模式：

1. **选择器靠猜**：生成的 `nth-child(3)` 或动态 class 一跑就失效；
2. **断言同义反复**：测试只验证了它自己 mock 的数据，等于什么都没测；
3. **没有等待策略**：本地能过，CI 上时灵时不灵。

本质原因都一样：生成时缺运行时反馈。

## 做法

环境：OpenClaw 接入浏览器操作类 MCP 工具，测试框架用 Playwright Test。

**Step 1：先立契约。** 和 Agent 约定测试规范——只用 `data-testid`、禁止硬 sleep、每个用例必须有显式业务断言。写成一份 `TESTING.md` 放仓库里，Agent 每轮生成前先读。

**Step 2：让 Agent 先"逛"应用。** 给它一段用户流程描述（例如"登录后创建项目并邀请成员"），让它用浏览器工具实际走一遍，记录真实路由、可用选择器、常见等待点。这一步的产出比直接生成的代码更值钱，后面会讲怎么复用。

**Step 3：生成 + 自跑 + 自修。** 基于探索结果生成测试文件，然后自己执行测试命令，把失败输出原样喂回上下文让它修。**迭代次数必须设上限**（我一般给 3 轮），防止死循环烧 token。

**Step 4：人工审断言。** 跑绿不等于测对了。重点看断言是否覆盖业务结果——数据库状态、接口返回、关键 UI 内容——而不是只断言"元素存在"。

## 踩坑点

- **Agent 会"应试"**：修不动时它会尝试放宽甚至删掉断言。指令里必须写死：只允许修选择器和等待逻辑，削弱断言需要人工确认。
- **探索结果的时效性**：Agent 看到的 DOM 有快照性质。给关键交互元素提前补 `data-testid`，是整个流程里性价比最高的一次投入。
- **用例间污染**：Agent 生成的用例经常共享登录态但不清理。要求每个用例独立 seed 数据，teardown 里删除。
- **MCP 权限要收敛**：给浏览器工具的同时，别顺手把 shell 全量权限也给了，防止它在"修测试"时顺手改了业务代码。

## 可复用建议

- 把 Step 2 的探索结果沉淀成**选择器清单文件**，后续人写测试也直接复用，一份投入两次收益。
- Agent 产出的测试**单独提 PR 并标注来源**，review 粒度和回滚都更干净。
- **修 bug 是最佳切入点**：让 Agent 先写一个复现 bug 的失败测试，再修代码，转绿即完成。这条流程的价值密度最高。
- 定期让 Agent 跑全量 E2E，把 flaky 用例清单拉出来人工裁决，别让它自己静默 retry 掩盖问题。

## 总结

Agent 写 E2E 的核心不是"生成代码"，而是**把运行时反馈接进生成回路**。OpenClaw + MCP 工具链让这个闭环的搭建成本已经很低：一份测试规范、一套浏览器工具、一个迭代上限。剩下最关键的仍是人对断言质量的把关——Agent 能把覆盖率和周转速度拉上来，但"测什么"的判断权，要留在自己手里。
