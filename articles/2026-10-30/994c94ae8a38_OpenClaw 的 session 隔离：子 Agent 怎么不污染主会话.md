## 背景

用 OpenClaw 跑了一段时间后，最直观的痛点是主会话越来越"重"：让它调研一批网页、批量读仓库文件、跑浏览器抓取，中间过程全是工具调用和长输出，几轮下来主会话上下文被塞满，触发 compaction 后细节丢失，接着它开始忘事、重复干活。这类"脏活"不适合在主会话里做。

## 问题

本质是上下文污染：中间产物（工具原始输出、网页正文、逐文件的读取结果）对最终决策价值很低，却占用大量 token，还改变了主会话的记忆结构。主会话应该只承载**状态与决策**，而不是**过程**。

## 做法

以我手上的版本为例，核心是 `sessions_spawn` + 工具分层：

1. **重 IO 任务走子 agent。**"读 30 个文件找配置不一致"这种任务下发给子 agent，它有独立的 session 和上下文窗口，过程记录落在子会话里。
2. **任务提示词里写死返回格式。**比如"只返回 JSON：文件路径 + 问题 + 证据行号，不超过 20 行"。主会话最终只收到这一条结构化结果，子 agent 的中间 transcript 不会回流。
3. **工具分层。**主会话保留调度、消息、决策类工具；browser、批量读文件、搜索这类高噪音工具主要在子 agent 里用。
4. **大批量任务并行拆分。**多个子 agent 各自隔离跑，主会话只做汇总和裁决。

## 踩坑点

- **子 agent 默认继承主 agent 的工具集。**我第一次跑的时候，它在子任务里调了消息工具，又往群里回了一条消息。外呼类工具一定要在子任务里显式收掉。
- **主会话看不到子 agent 的中间过程。**这既是特性也是坑。调试别在主会话里问"你刚才读了什么"，直接去翻子会话的 transcript。
- **子 agent 里再 spawn 子 agent，成本是平方级的**，也容易失控，浅层调用就够。
- **隔离不等于消失。**子会话文件仍然落盘，跑多了记得清理，否则磁盘和会话列表都会变乱。
- **并行 spawn 的结果顺序不保证。**聚合逻辑按任务 ID 对齐，别依赖返回顺序。

## 可复用建议

- 把"主会话是调度器，子 agent 是工人"当默认架构原则。
- 沉淀几套子任务提示词模板（调研、读码、抓取），返回格式固定，主会话解析就不容易翻车。
- 让子 agent 只做幂等、可重跑的事：失败就重发一次任务，不污染任何状态。
- 粗略估算上下文预算：单任务预期产出超过主会话剩余上下文的两三成，就该 spawn 了。

## 总结

session 隔离不算高深机制，核心就一句话：**过程留在子会话，结论回到主会话**。把主会话的上下文当稀缺资源管理，OpenClaw 跑长任务的稳定性会有肉眼可见的提升。有更好的聚合姿势（比如结构化回传 + 自动校验）欢迎在楼下补充。
