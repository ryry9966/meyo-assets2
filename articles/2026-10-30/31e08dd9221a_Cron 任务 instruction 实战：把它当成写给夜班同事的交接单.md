## 背景

OpenClaw 的 cron 本质上很简单：到点把一条 instruction 当作独立 prompt 喂给 agent，跑完把结果投递出去。它不是"提醒"，而是"无人值守的代班"。这个定位决定了 instruction 的写法和日常聊天完全不同——你不在场，没有上下文，没有追问机会。社区里一半以上的 cron 问题，最后都能归结为一件事：instruction 写得像聊天，而不是像交接文档。

## 问题

三个典型失败模式：

1. **上下文缺失**。"帮我整理今天值得看的资讯"——agent 不知道"今天"按哪个时区算，不知道发到哪个会话，只能猜。
2. **输出漂移**。没固定格式，三天跑出三种结构，下游想自动化解析直接挂掉。
3. **静默失败**。搜索工具没配好，agent "感觉差不多"就编了几条交差，你第二天才在群里发现链接是空的。

## 做法

我现在的写法，是把 instruction 当作给夜班同事的交接单，五段式：

```text
目标：汇总 <主题> 过去 24 小时内的新内容。
时间：以本次运行时刻为基准，时区 Asia/Shanghai。
来源：使用 web_search，检索 "<关键词>"，最多看前 10 条结果。
输出：Markdown，每条含标题、一句话摘要、链接，最多 5 条，按相关度排序。
投递：发到 Telegram 私聊，首行注明运行时间。
兜底：0 条时发送"过去 24 小时无新增"，禁止编造或放宽时间范围。
边界：只读操作；不访问来源以外的站点；不执行写操作。
```

逐段说下为什么：

- **时间锚点**必须显式写"以运行时刻为基准"。cron 的语义和人的直觉不一致，`0 9 * * *` 跑的是"9 点那一刻"，不是"今天早上"。
- **来源收窄**比"帮我搜一下"有效得多。指定工具名、关键词和条数上限，agent 的发挥空间小，结果才可复现。
- **输出格式**直接给字段清单，比"格式工整"这种形容词靠谱一百倍。
- **兜底**是区分新手和老手的关键：明确"0 条也是合法产出"，agent 才不会为了显得有用去编内容。

## 踩坑点

- **一事一 cron**。把日报、周报、监控塞进一条 instruction，等于让夜班同事一次交接五件事，每件都会糊。拆开后才能单独调试、单独禁用。
- **相对时间词慎用**。"昨天""最近"在 cron 里都是事故源，全部换成"运行时刻往前 N 小时"。
- **长输出撑爆消息**。限条数、限摘要长度，超出的让 agent 补一句"共 N 条，已截断"。
- **跳过手动验证**。上线前先 `cron run <job>` 手动触发一次，看日志里 agent 实际拿到了什么工具、产出了什么，比盯三天定时结果快得多。
- **敏感信息进 instruction**。token、内网地址不要写在 prompt 里，走配置或环境变量。

## 可复用建议

- 跑稳定的 instruction 存成 snippet，新任务先抄模板再改三处：主题、来源、投递目标。
- 给任务定命名规范（如 `daily-news-zh`），半年后你还认得出它是干嘛的。
- 每月 review 一次：删掉连续两周产出被你跳过不看的任务。cron 的维护成本是复利的。
- 输出要被程序消费的任务，格式字段一旦定下就不要轻易改，改了必须同步下游。

## 总结

Cron instruction 的标准比交互式对话高一个量级：**自包含、可验证、有兜底**。写完自检三个问题——换个新 agent 冷启动能不能跑通？跑出空结果它知道怎么报告吗？输出能不能被你（或脚本）稳定解析？三个都答"是"，再交给定时器。
