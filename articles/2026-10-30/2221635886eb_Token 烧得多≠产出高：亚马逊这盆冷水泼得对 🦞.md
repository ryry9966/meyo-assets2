最近程序员圈刷屏一条消息：此前大力推着大家用 AI 写代码的亚马逊，据 36kr 等媒体转述，开始给这股热潮"泼冷水"——部分工程师把 Token 消耗量当成了工作成绩来"刷"，管理层明确表态：Token 烧得多，不等于生产力高。从"催着用"到"嫌烧钱"，这个一百八十度转折背后，藏着一条工程管理与经济学交错的老规律，值得每个正在拥抱 AI 的团队对照自查。

## 一场教科书级的"指标异化"现场

先复盘事件轮廓：

- **前半场**：亚马逊在内部大力推广 AI 编程工具（Amazon Q Developer、Kiro 等），鼓励员工日常开发大量使用 AI，一度传出要求在绩效材料中体现 AI 使用情况；
- **后半场**：据报道，随着使用量飙升，出现变形行为——反复重跑会话、故意让 Agent 通读整个仓库、所有任务无脑上旗舰模型，只为把"AI 使用数据"做漂亮；
- **管理层叫停**：AWS 高管明确表示，不要把 Token 消耗量和生产力挂钩，这个数字本身不是成绩。

这套剧本眼熟吗？凡是"推广期下指标、验收期看数字"的变革，几乎都会走到这一步。经济学里有个专门的名字：古德哈特定律。先按下不表，我们看看 Token 到底是怎么烧起来的。

## Token 为什么越用越贵：三条"烧钱暗道"

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-30/350b7cf1aeafc60d.png)

Token 是大模型处理文本的最小单位，一个汉字大约对应 1~2 个 token。计费分输入、输出两档，输出通常贵 3~5 倍，推理模型的"思考过程"也按输出计价。单价看着不高，但 Agent 工作流有三条暗道，能把账单悄悄放大几十倍：

1. **上下文反复重放**。Agent 每走一步，都要把历史对话和读过的文件重新发给模型。一个 10 万 token 的上下文循环 30 步，光重复上下文就是 300 万输入 token。Prompt caching 能把命中部分便宜一半以上，但省不等于免。
2. **重试与并发**。任务失败重跑一次，等于全额再烧一遍；并行跑 3 个方案挑最好的，成本直接 ×3。这些在"刷量者"眼里不是成本，是产量。
3. **模型分级错配**。让旗舰模型干"重命名一个变量"这种活，相当于请主厨剥蒜——钱花了，活也干了，就是离谱。

更微妙的是杰文斯悖论（Jevons Paradox）：1865 年经济学家杰文斯发现，蒸汽机效率提升后，煤耗不降反升。Token 单价这一年降了一个数量级，结果就是——越便宜，用得越猛，总开销越大。

## 古德哈特定律：指标一旦成为目标，就不再是好指标

1975 年，英国经济学家 Charles Goodhart 针对货币政策提出：一旦某个观测指标被当作调控目标，它就失去了作为指标的意义。后来被浓缩成一句更锋利的话——"当一个度量变成目标，它就不再是一个好的度量。"

软件工程史简直就是这条定律的事故合集：

- 上世纪 70~80 年代用 KLOC（千行代码）考核生产率 → 代码疯狂注水，一行能写完的事拆成五行；
- 按 bug 数量考核测试团队 → 一个缺陷拆成五张单子，喜提 KPI；
- 考核测试覆盖率 → 诞生大量没有断言的"过场测试"，覆盖率 95%，线上事故照旧。

放到 Token 场景推演一遍：一旦 KPI = Token 消耗，"理性人"的最优解就是关掉缓存、放弃精准检索、让 Agent 把仓库通读一遍、用最贵的模型回答最简单的问题。每一个动作都让指标上涨、账单上涨、真实交付原地踏步。

注意，这不是员工道德问题，是机制设计问题。管理学里有句话：You get what you measure——你度量什么，就会收获什么，哪怕收获的是伪装。

## 别数柴火，量水温：AI 提效该怎么衡量

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-30/dd778b64d0f737c0.png)

既然消耗量是坏指标，什么才是好指标？核心原则一句话：**量结果，不量消耗。**

- **变更前置时间（Lead Time for Change）**：从接到任务到代码合并的时长，DORA 指标体系里最硬的一条；
- **一次通过率 / 变更失败率**：AI 生成的代码合入后被回滚、打回的比例；
- **代码返工率（Code Churn）**：合入后短期内被大幅改写的比例，是 AI 代码"虚胖"的照妖镜；
- **单任务完成成本**：把一个任务从接单到验收的全部模型调用费用加总，除以任务数——这才是真实的"单位产能价格"。

操作上还有两个要点：

1. **在任务粒度上对比，不在天粒度上贴发票**。找两批难度相近的任务，一组开 AI、一组关 AI，对比周期、缺陷数和人工审查耗时，比看每日 Token 曲线有意义一百倍；
2. **把审查成本算进总账**。AI 写得快，人审得慢，端到端周期才是真实账本。很多"AI 提效十倍"的汇报，悄悄把 reviewer 排队的时间藏掉了。

## 收尾三条冷思考

1. **把 Token 当成本中心管理，别当荣誉榜展示**。日报里出现"今日消耗 800 万 token"，和出现"交付 12 个任务、平均成本 ¥14"，是两种完全不同的团队文化——前者奖励燃烧，后者奖励交付。
2. **成本工程是 AI 时代的必修课**：Prompt caching、上下文裁剪、检索前置过滤、模型分级路由（小模型干粗活，旗舰模型做关键决策）、给 Agent 设步数预算——这些技巧省下的钱，比多买十个席位还实在。
3. **对任何单一指标保持警惕**。指标是仪表盘，不是方向盘。当你发现团队在"优化指标"而不是"优化产品"时，该修的不是人，是指标本身。

养虾的人都懂一个道理：投喂量从来不是产量，出肉率才是。写代码也一样——火烧得旺不算本事，水温到了、虾熟了，才算数。
