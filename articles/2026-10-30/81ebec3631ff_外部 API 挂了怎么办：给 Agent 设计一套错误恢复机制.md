## 背景

跑过稍复杂一点的 Agent 任务都知道：一条链路里模型只占一环，剩下全是外部依赖——搜索、数据库、第三方 SaaS、MCP tool 背后的真实服务。本地代码挂了能看堆栈，但外部 API 挂掉时，Agent 的表现往往更糟：它会把错误响应原文当作“工具返回结果”继续推理，一本正经地总结一段 500 页面的内容；或者陷入“再试一次”的循环，把 token 烧完才停。

问题不在模型不够聪明，而在我们没有把“外部世界不可靠”当成一等公民来设计。

## 问题拆开看

实际故障通常分三类：

1. **瞬时错误**：超时、502/503、网络抖动，重试有用；
2. **限流（429）**：重试有用，但要按对方的节奏来；
3. **致命错误**：401/403、参数错误、服务下线，重试只浪费资源。

Agent 场景还有两个特有难题：重试可能触发**重复副作用**（消息发两次、工单建两个），以及长任务中断后没有断点，只能从头再来。

## 我们的做法

核心思路：**把重试决策从模型手里拿走，放到代码层；模型只负责在拿到结构化错误后选择路径。**

**第一步**，给所有工具调用包一层统一 wrapper（MCP tool 和插件入口都适用）：

```python
result = with_recovery(
    call=lambda: tool.invoke(args),
    classify=classify_error,          # 瞬时/限流/致命
    max_retries=3,
    backoff=ExponentialJitter(base=1, cap=30),
    idempotency_key=make_key(args),   # 非幂等操作必备
)
```

**第二步**，错误分类后结构化回传。不要把原始堆栈塞进上下文，而是给模型一段明确描述：

```
status: rate_limited
retryable: false
hint: 该搜索服务暂不可用，可改用 fallback_search 或直接告知用户
```

**第三步**，准备降级路径，优先级从高到低：备用 API → 缓存的上次结果 → 明确的部分完成。哪怕降级，也要在最终回复里告诉用户“该子任务未完成/数据来自缓存”，别让模型拿降级数据冒充完整结果。

**第四步**，长任务落盘。每次工具调用成功后写 checkpoint（任务状态 + 已完成副作用清单），中断后从断点恢复，而不是重跑整条链。

## 踩坑点

- **让模型自己决定重试**。实测它要么死循环，要么一次失败就放弃。重试策略必须是代码里的确定性行为。
- **429 和 5xx 用同一套退避**。429 要读 Retry-After，5xx 才用指数退避加抖动。
- **对非幂等操作裸重试**。要么带 idempotency key，要么把“创建”类操作改成“先查再建”。
- **超时设太长**。单个工具 30 秒无响应就该走恢复流程，别让整条任务挂住。
- **错误上下文污染**。失败的原始响应留在上下文里，模型后面还会引用它。恢复成功后要把脏上下文清掉或显式标记失效。

## 可复用的建议

- 错误分类常量表（瞬时/限流/致命）团队统一一份，所有插件共用，别各写各的。
- system prompt 里写“遇到不可用工具时的行为准则”（告知用户、选择备选路径），但重试次数、退避参数只存在于代码。
- 任何写操作默认按非幂等处理。
- 给恢复流程本身加监控：**降级触发次数、重试成功率**。这两个指标比任务成功率更能提前暴露依赖劣化。

## 总结

外部 API 挂掉不是异常，是日常。好的错误恢复不指望模型随机应变，而是用工程手段把不可靠的部分圈起来：代码层管重试和退避，结构化错误喂给模型做路径选择，幂等和断点保证重来的代价可控。Agent 的可靠性上限，大头上不取决于模型，取决于这些不起眼的 wrapper。
