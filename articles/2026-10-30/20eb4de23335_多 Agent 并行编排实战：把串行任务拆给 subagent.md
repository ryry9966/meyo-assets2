## 背景

单个 agent 串行干活的问题，在任务量上来之后暴露得很快。比如让主 agent 对 15 个仓库做依赖升级评估，或者对一批文档做统一抽取，串行跑一次半小时起步；而且所有中间过程都堆在同一个会话上下文里——跑到一半，模型开始“忘事”，工具调用结果互相干扰，最后还要花一轮功夫从泥潭里捞结论。

OpenClaw 的 subagent 机制给了另一条路：主 agent 负责拆任务、收结果，subagent 各自在独立会话和工作区里并行执行。这篇记录我们团队跑了一段时间的编排方式，以及踩过的坑。

## 做法

流程固定成五步：

1. **角色与资源配置**。在配置里声明若干 subagent，每个绑定独立 workspace 和工具白名单。原则是子 agent 只拿完成该类任务所需的最小权限，能用只读工具就不给写权限。
2. **主 agent 先落盘任务清单**。拆解结果写成一个 manifest 文件（JSON），每条包含任务 ID、输入路径、预期输出路径、超时时间。这一步很关键——任务定义先固化再分发，避免口头指令带来的理解漂移。
3. **受限并发分发**。并发数控制在 3~4。每个 subagent 启动时只接收任务描述、输入路径和输出约定，不带主会话历史。
4. **结果一律落盘**。subagent 把结论写到自己的目录下（如 `results/<task_id>.md`），返回值只带状态：成功 / 失败 / 超时。不靠对话回传大段内容。
5. **聚合与重试**。主 agent 读目录汇总，失败的进重试队列，重试仍失败的标记为人工处理。

## 踩坑点

- **并发开太猛必翻车**。一开始开到 8 并发，模型限流、token 消耗翻倍，效果反而差。3~4 是我们在成本和墙钟时间之间的平衡点。
- **共享工作区会互相覆盖**。两个 subagent 同时写 `output.md`，后写的把先写的冲掉。每个 subagent 必须有独立子目录，输出路径写进任务定义里。
- **任务描述模糊等于灾难**。“帮我看看这个仓库”这种指令，subagent 会自由发挥，结果没法聚合。每条任务必须有明确的输入、输出和“完成”判据。
- **没有超时就有僵尸会话**。有个 subagent 卡在一个交互式命令上，会话挂了一小时才发现。所有任务强制超时，超时即终止并重派。
- **别让 subagent 碰对外动作**。发消息、调外部付费接口这类操作只留给主 agent，子 agent 的爆炸半径必须可控。

## 可复用建议

- 任务清单先落盘再分发，可审计、可重放；
- 结果文件化，而不是对话化；
- 每类任务固定一个 subagent 模板（工具白名单 + 提示词模板），像管理代码一样管理它们；
- 上线前用一个低风险任务（比如批量生成摘要）做冒烟测试，重点观察并发、超时和聚合逻辑。

## 总结

subagent 编排的本质不是“更多 AI”，而是把任务定义、执行隔离、结果回收拆开，让主 agent 回到调度者的位置。跑通之后，原来半小时的批量任务缩到六七分钟，主会话上下文也干净了很多。它不解决所有问题——任务间有强依赖的场景还是得串行或分批——但在“大量同构小任务”这个场景下，是我们目前性价比最高的模式。欢迎在社区里交换各自的并发上限和超时参数，这块大家都还在摸索。
