## 背景

OpenClaw 的 Agent 默认是"呼叫—应答"模式：你发消息，它才干活。但它内置了一个常被忽略的机制——心跳。Agent 每隔一段时间（默认 30 分钟）醒来一次，读取工作区里的 `HEARTBEAT.md`：文件为空就继续睡，几乎没有开销；有内容就当作任务清单执行一遍。这是把 Agent 从"问答机器人"变成"值守进程"的最小改动。

## 问题

很多自动化需求并不需要精确 cron：不是"每天 9 点发日报"，而是"有异常再告诉我"。这类条件触发型任务用外部脚本写，要处理鉴权、通知渠道、上下文拼接，绕一圈最后还是把结果喂回 Agent。HEARTBEAT.md 把这件事收敛成了一个 Markdown 文件。

## 做法

1. 在工作区根目录建 `HEARTBEAT.md`（通常在 `~/.openclaw/workspace/` 下）。
2. 用清单写任务，每条固定三段：**触发条件、检查动作、汇报策略**。例如：
   - 监控 `~/repos/api` 的 git 状态：发现未推送提交时汇总 diff 摘要发到 Telegram；否则静默。
3. 汇报策略必须写明"无异常时怎么办"。让模型在无事发生时输出 `NO_REPLY`，心跳就不会打扰你的聊天窗口。
4. 调试期把心跳间隔临时调到 1 分钟（gateway 配置），盯日志确认每一步，跑通后再调回去。
5. 复杂任务的细节不要堆在 HEARTBEAT.md 里，写进同目录的 playbook 文件，清单只留一行索引，让 Agent 按需去读。

## 踩坑点

- **成本**：文件非空，每次心跳都是一次完整模型调用。清单越长越贵，做完的任务及时删，把它当 crontab 维护。
- **重复触发**：Agent 默认没有跨心跳记忆，"今天发过没有"它不知道。让它把状态写到 `state.json` 或日志文件，每次先读再判断，保证幂等。
- **精度错觉**：心跳不是定时器。"每小时检查一次"尚可，"9:00 整执行"不可靠。精确调度交给系统 cron 触发，心跳只做状态巡检。
- **任务堆积**：单次任务耗时超过间隔会排队堆积。心跳任务保持轻量，重活让它落一个任务文件转异步处理。
- **权限**：心跳在 gateway 侧无人值守执行，沙箱和工具权限要提前放开，否则总在你睡觉时失败。

## 可复用建议

- 三段式模板（条件/动作/汇报）适用于所有值守类任务，建议做成 snippet 复用。
- 分工要清楚：秒级反应用 webhook，精确时刻用 cron，"有情况再说"用心跳。三者互补，别用心跳硬扛所有调度。
- 工作区放进 git，HEARTBEAT.md 每次改动都可 review，出问题能回滚。
- 打开心跳日志统计调用次数，成本心里有数再扩任务。

## 总结

HEARTBEAT.md 的价值不在功能多强，而在它把"主动性"压到了一个纯文本文件的复杂度。建议先写一条真实任务（比如仓库巡检）跑一周，观察成本和噪音，再逐步加。让 Agent 主动做事的门槛，其实就是写清楚一句话：**什么情况下才来找我**。
