## 背景

用 OpenClaw 一段时间后，大多数人的第一个瓶颈不是功能，而是模型账单和隐私边界。OpenClaw 本身是模型无关的：配置里每个 agent 都可以指定自己的 model，还支持 fallback 链。这意味着"多模型路由"不需要装额外插件，而是要回答一个工程问题——哪类请求值得花云端前沿模型的钱，哪类请求本地小模型就能接住。

## 问题

社区里常见的两个极端：一是全部走云端旗舰模型，一个月下来 token 费用比服务器还贵；二是为了省钱全部切本地，结果 agent 在多步任务里频繁调错工具，返工成本反而更高。路由的价值在于把"贵而强"和"便宜稳定"各用在刀刃上，同时不让路由本身变成新的排障负担。

## 我的做法

按 agent 粒度拆，而不是按消息粒度拆。

1. **主对话 agent 用云端强模型。** 涉及代码修改、多步规划、复杂 MCP 工具编排的任务，对推理和 function calling 稳定性要求高，这部分钱不该省。
2. **旁路 agent 用本地模型。** 我单开了几个 workspace，跑摘要、频道消息过滤、定时整理笔记这类高频低难度任务，走本地小参数模型，延迟低、零成本、数据不出机器。
3. **配 fallback 链兜底。** 主模型限流或超时时自动降级，但我在 fallback 里放的是同级或略弱的云端模型，而不是直接跳到本地——避免质量断崖。
4. **隐私敏感的任务强制本地。** 凡是会读到私钥、聊天记录原文的 skill，直接在对应 agent 配置里锁死本地模型，不依赖运行时判断。

## 踩坑点

- **本地模型的工具调用是最大的坑。** MCP 工具参数 schema 一复杂，小模型就开始瞎填参数或漏调用，表面看任务"跑了"，实际结果不可用。我的判断标准：一个任务需要串联 3 个以上工具，别交给本地模型。
- **上下文长度差异会静默截断。** 云端长上下文的会话习惯带到本地小窗口模型上，中间内容直接丢，而且不报错。切换前先看会话 token 量。
- **fallback 切换是静默的**，质量下滑很难第一时间发现。我加了个日志 hook，每次降级都记录原因，定期回看。
- **延迟要实测。** 本地模型省了网络往返，但生成速度可能更慢；对定时任务无所谓，对交互式对话体感差异明显。

## 可复用建议

- 路由粒度选 agent/workspace，别做逐条消息的动态路由——后者的调试成本远超节省的费用。
- 先跑一周"全云端"，记录各 agent 的实际 token 消耗，再决定谁降级，让数据说话。
- 每个 skill 写清自己的模型假设（需要强推理，还是只需格式化输出），接手的人不用猜。
- 保留统一的调用日志，按 agent 维度统计成功率，本地模型上线后每周对比一次。

## 总结

多模型路由的本质，是给不同风险等级的任务匹配不同成本的执行器。OpenClaw 的 agent 隔离机制让这件事可以做得非常干净：每个 agent 独立配模型、独立配 fallback，互不干扰。我的默认原则是——面向人的输出和不可逆操作走云端强模型，高频、可丢弃、隐私敏感的中间任务走本地。先把边界画清楚，再去抠成本，顺序不能反。
