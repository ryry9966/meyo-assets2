## 背景

LLM 本身无状态。你在 OpenClaw 里搭的助手，每次会话都是从零开始：装包偏好、部署习惯、代码风格，说一遍忘一遍。上下文窗口再大也不解决根本问题——上下文是"这一轮的输入"，记忆是"跨会话的状态"，两件事不能混着做。

## 问题

常见的三种错误做法：

1. **全塞 system prompt**。跑半年后 prompt 膨胀到几万 token，注意力被稀释，成本也崩。
2. **原始聊天记录做 RAG**。召回一堆"上次我说过……"的噪音，新旧偏好打架时没有仲裁机制。
3. **只靠模型自觉**。不给写入口，模型想记也记不了；给太大权限，又会把一次性的话固化成永久偏好。

核心矛盾其实是三个：记什么、记多久、谁说了算。

## 做法

我目前的方案是三层，够简单也够用：

**第一层：结构化偏好表（必带）**。一张 JSON 或 SQLite 表，字段至少有 key、value、source、confidence、updated_at。比如 `{key: "包管理器", value: "pnpm"}`。每轮会话固定注入，控制在 300 token 以内。这一层贡献 80% 的价值，别急着上向量库。

**第二层：情景记忆（按需召回）**。会话摘要 + embedding 存进 sqlite-vec 之类的本地库，任务相关时才检索。存的是"事件"，不是"事实"。

**第三层：写入管线（关键）**。通过 MCP 暴露 `memory_write` / `memory_forget` 工具，让 agent 自己决定何时记录；同时跑一个夜间蒸馏任务，从当日会话日志提取候选记忆。写入前过三道闸：去重（同 key 合并）、冲突仲裁（新值覆盖旧值，旧值留版本历史）、置信度（只有用户明确陈述才标 high）。

## 踩坑点

- **记太早**。用户说一次"这次先用 npm"，就被永久记成偏好。加了两条规则：低置信度记忆注入时带"仅供参考"标记；同一 key 出现 2 次以上才升级为稳定偏好。
- **记忆自我污染**。模型自己的回答被写回成"事实"，越滚越歪。现在只允许 user 来源的陈述进入偏好表，写入时打 source 标签。
- **过期不处理**。换掉工具链后，旧记忆天天出来捣乱。给 value 加 ttl，仲裁时比较 updated_at。
- **全量注入**。曾把整张记忆表塞进 prompt，效果反而下降。改成只注入第一层，第二层严格按任务检索。

## 可复用建议

1. 先做结构化偏好表，不要从向量库起步。
2. source 和 confidence 从第一天就要进 schema，后补很痛苦。
3. 把读写工具显式给到 agent，而不是只藏在管线里——模型知道自己"记过什么"很重要。
4. 每次写入留日志。记忆系统出问题时，这是唯一的排查手段。
5. 必须给用户留 `memory_forget`。删除权过不了关，整个系统就上不了线。

## 总结

记忆系统的目标不是"存得多"，而是"记得准、删得掉、改得动"。结构化偏好层解决确定性，情景记忆层解决上下文，写入闸门解决正确性。先小后大、先结构化后语义化，两周能跑出一版能用的。有更好玩的仲裁策略欢迎回帖讨论。
