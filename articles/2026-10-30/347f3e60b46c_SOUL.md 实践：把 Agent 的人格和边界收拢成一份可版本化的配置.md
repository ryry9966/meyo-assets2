## 背景

OpenClaw 的 workspace 里有一组约定文件：`AGENT.md` 管操作规程，`TOOLS.md` 管工具备注，而 `SOUL.md` 承担的是另一件事——定义这个 Agent "是谁"。它会在每次会话启动时随上下文注入，是少数能稳定影响模型行为、又不依赖某个具体插件的机制。

很多人的第一反应是：人格这种东西，写在提示词里不就行了？实践下来你会发现问题。

## 问题

人格散落各处时：

- 各插件/技能自带的 system 片段互相覆盖，最后加载的赢
- 每次调整语气要翻好几个文件，改完不敢确定生效的是哪份
- "不做的事"和"不能做的事"混在一起，出了事故说不清是提示词的锅还是权限的锅

典型症状是 Agent 的"性格"随会话漂移：今天话多，明天冷漠，对某个工具的热情完全取决于上一次加载了哪个 skill。

## 做法

**1. 先写边界，再写人格。** 边界是硬约束，人格是软倾向。`SOUL.md` 里优先放"绝不做什么"：不主动私聊第三方、不执行删除类命令、不代替用户做支付确认。

**2. 结构化分段，不写成作文。** 我目前的模板：

- 定位：一句话，这是谁、服务谁
- 语气：3–5 条可判定的规则
- 硬边界：枚举，能和工具权限对上的
- 不确定时的行为：问还是停
- 升级路径：什么情况必须停下来找人

**3. 与权限分层。** SOUL.md 写"不做"，MCP allowlist 和插件权限管"不能"。两层都要有：前者挡上下文里被注入的绕过指令，后者才是真正的执行层兜底。

**4. 进 git，改动走 review。** 人格是配置，不是心情。

一个精简示例：

```markdown
# Soul
定位：个人工作台 Agent，只服务主人一个用户。
语气：简短直接，结论先行，不使用感叹号。
硬边界：
- 不执行 rm/sudo 类命令
- 不在群聊里主动 @ 任何人
- 涉及金钱和凭据的操作，只准备命令，不执行
不确定时：先说明缺什么信息，再问一个问题，不多问。
```

## 踩坑点

1. **写太长。** 超过一两屏，模型对中段的遵循度明显下降。我的经验是 60 行以内，超出的挪去 AGENT.md 或技能说明。
2. **写不可验收的形容词。** "幽默一点""有温度"没法执行。改成可判定的："自嘲最多一句""不用 emoji"。
3. **和 AGENT.md 打架。** 两份文件对同一行为给出相反指令时，行为会不稳定。职责划清：SOUL.md 管身份与边界，AGENT.md 管流程与规程。
4. **指望 SOUL.md 兜安全。** 它是软约束，提示词注入可以绕过。真正的红线必须落在工具权限和沙箱上。
5. **多 Agent 共用一份。** 不同实例职责不同，值班 Agent 复制了主 Agent 的人格，就会出现学着主人语气闲聊这类怪事。

## 可复用建议

- 把 SOUL.md 当配置文件：短、枚举、可验收
- 每次改版后跑一组固定测试消息，对比前后行为差异
- 边界条目和 MCP 工具列表放同一次 review，保证"说了不做"和"权限真没有"一致
- 拿不准某句话归不归 SOUL.md 时问自己：这是身份问题还是流程问题？前者留下，后者去 AGENT.md

## 总结

SOUL.md 的价值不在于"让 Agent 更有人味"，而在于把人格和边界从散落的提示词碎片里收拢成一份可版本化、可 review、可回滚的配置。人格是软的，边界要靠权限硬化，两层一起才立得住。
