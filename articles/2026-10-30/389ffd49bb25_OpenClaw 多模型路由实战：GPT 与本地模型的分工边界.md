## 背景

OpenClaw 的 agent 循环里，任务复杂度差异极大：一次多步工具编排可能要啃 30k token 的上下文，而一条"把这段总结成三行"的消息，7B 本地模型就够了。默认配置往往一个模型打天下——全走云端，账单和延迟难看；全走本地，复杂任务翻车。多模型路由的价值，就是把任务显式分层。

## 问题

路由本质上要同时权衡三个变量：

- **能力**：能否稳定完成 tool calling、长上下文推理；
- **成本与延迟**：云端按 token 计费、受网络波动；本地吃显存、长输出慢；
- **隐私**：聊天记录、本地文件路径、凭据是否允许出网。

三者互相牵制，不存在全局最优，只有按任务类型的局部最优。

## 做法

我目前在用的一套分层方案，可以直接复现：

1. **定义三个 tier**：
   - Tier A：多步 agent 编排、长上下文、复杂工具链 → 云端 GPT 级模型做 primary；
   - Tier B：摘要、改写、分类、格式化 → 本地 7B~14B（Ollama 起一个就够）；
   - Tier C：涉及本地文件、聊天记录、密钥内容的任务 → 强制本地，或先脱敏再上云。
2. **按 agent 指定模型，不用全局单模型**：编排类 agent 绑云模型，轻量工具型 agent 绑本地。
3. **路由判断规则先行**：token 数阈值、是否命中敏感目录、是否多工具调用。规则不够用，再加一个便宜的分类步骤，别一上来就堆 LLM router。
4. **配 fallback 链加重试上限**：云模型超时或限流时降级到本地，并明确提示"结果可能降质"，避免静默失败。
5. **hook 里做脱敏**：命中敏感模式（绝对路径、key 格式）的内容替换成占位符后再放行到云端。

## 踩坑点

- **本地模型 function calling 不稳定**：JSON 输出偶尔多个逗号就解析崩。换模型前先拿固定的工具调用测试集跑一轮，别直接上生产。
- **上下文窗口静默截断**：本地 8k 模型接到长会话，前面的工具结果被悄悄丢掉，表现为"模型失忆"。路由规则里要把 token 估算算进去。
- **降级循环**：云失败 → 本地失败 → 又重试云，形成风暴。重试必须封顶，两级之间加退避。
- **延迟直觉会骗人**：本地模型首 token 快，但长输出的总耗时经常输给云模型。按总耗时优化，别只看首包。
- **embedding 别走云端**：调用量最大、价值密度最低，本地跑又快又不出网。

## 可复用建议

- 先只用**两个模型**（一云一本地），跑稳了再考虑第三层。多数个人部署，两层够用。
- 路由表写成**配置**而不是硬编码，调阈值不用重新部署。
- 记一周路由日志：任务类型、token 数、模型、延迟、是否降级。用数据调阈值，比拍脑袋准得多。
- 隐私边界一条就够：**碰本地文件和凭据的，默认不出网，白名单放行。**

## 总结

多模型路由不是炫技，而是把能力、成本、隐私三个约束显式化的工程手段。规则先行、两层起步、日志驱动调参——做到这三点，这套方案就能长期稳定跑下去。
