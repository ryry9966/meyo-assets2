## 背景

OpenClaw 跑起来之后你会发现，模型调用的负载高度不均匀：大量请求其实是"读日志、总结、归类、改格式"，真正需要强推理的只有规划、多步工具调用和代码修改。全部走 GPT 级云端模型，账单和延迟都难看；全部压给本地模型，agent 又经常在 function calling 上翻车。多模型路由解决的就是这个分配问题。

## 问题

我的实例一天几百次调用，统计下来七成以上是轻任务。早期一刀切用云端模型，成本大半花在"总结邮件"这类事上；换成全本地后，又接连出现工具调用 JSON 格式错、长上下文被截断的情况。结论很明确：需要一个按任务分层的路由策略，而不是二选一。

## 做法

1. **先分类，再路由。** 我把任务分三档：重型（多步规划、代码修改、复杂 MCP 工具链）走云端主力；轻型（摘要、分类、格式化、记忆检索）走本地 7B–14B 级模型；中间态本地优先、失败升级。
2. **配主备链路，不留单点。** 主模型设本地，fallback 链挂云端；同时给重型 skill 单独 override 成云端直连。路由粒度到 skill/tool 级，比会话级更省。
3. **用工具调用次数做升级信号。** 入口层预判这次要串 3 个以上 MCP 工具，就直接走高配模型；纯文本任务走本地。判断只做一次，比中途反复切换稳定得多。
4. **记录路由日志。** 每次调用记录模型、token 数、延迟、是否触发 fallback。跑满一周再调阈值，别拍脑袋。

## 踩坑点

- 本地模型的 function calling 兼容性差异很大：有的输出 JSON 会多字段或漏字段，工具一多就崩。选本地模型先验证工具调用质量，再看跑分。
- 上下文长度错配是隐性坑：本地 8k 窗口遇到长会话会静默截断，agent 表现"变笨"但不报错。路由层必须做长度检查。
- fallback 触发后如果没打状态标记，同一轮可能重复计费甚至重复执行工具。升级路径上要带标记。
- 别用关键词规则做路由，中英混合请求下误判率远比预想高。

## 可复用建议

- 起步配置：云端做主力，本地只接"确定轻"的任务，比反过来稳得多。
- 维护一份 20 条左右的自有评测集（从真实历史任务里挑），换模型、调阈值之前先跑一遍。
- 给云端调用设预算上限和告警，路由写错时止损靠它。

## 总结

多模型路由的核心不是省钱，而是让每一档任务拿到刚好够用的模型。分层标准、升级信号、路由日志这三件事做扎实，本地和云端就能各干各的活，成本和稳定性同时拿住。顺序记住：先跑日志，再动配置。
