## 背景

我们日常跑 agent 自动化，最常见的模式是单 agent 串行：读代码、改代码、跑测试、写文档，一条线走到底。任务小的时候没问题，但碰到"给 20 个模块补单测""批量迁移配置文件""同时调研几个技术方案"这类批量活，串行的两个问题就暴露了：

1. **慢**。所有步骤排队，等待时间线性叠加。
2. **上下文膨胀**。文件内容、日志、搜索结果这些中间产物全堆在主 agent 上下文里，越往后越"失焦"，开始忘事、乱改。

## 做法

我们现在的分工是：主 agent 只做三件事——拆解、派发、验收。具体执行下沉到 subagent。

**第 1 步：划任务边界。** 只把"相互独立、结果可校验"的任务拆出去并行，按文件或目录切，比如每个 subagent 负责一个模块的单测，互不碰对方的文件。有依赖的环节（先迁移配置、再跑验证）坚决串行。

**第 2 步：给每个 subagent 明确的输入和权限。** 派发 prompt 里写清楚：负责哪些文件、达成什么标准（测试全绿）、输出什么格式、禁止做什么（不许改公共代码、不许 push）。工具权限最小化，用不到的能力直接不配。

**第 3 步：控制回传体积。** 子 agent 完成后只回传结构化摘要：成功与否、改动文件列表、关键结论。原始日志留在子 agent 自己的上下文里。这一条是主 agent 上下文不爆炸的关键。

**第 4 步：控制并发度。** 我们实测 3~5 个并行比较稳。再高会撞 API 限流、本地资源争抢，重试风暴反而拉长总耗时。

**第 5 步：验收。** 主 agent 汇总后做一轮校验——跑整体测试、抽查改动。不合格的任务重派一次，仍失败就降级为串行自己处理。

## 踩坑点

- **子 agent 改同一个文件**：并行写入直接冲突。任务必须按物理边界（文件/目录）切，不能按逻辑功能切。
- **静默失败**：子 agent 偶尔返回空结果，甚至"编造成功"。必须约定结构化返回格式，主 agent 做存在性校验，别信自然语言里的"已完成"。
- **上下文给太少**：子 agent 缺关键背景就会自由发挥，产出跑偏。要给"最小充分上下文"——相关路径、约定、示例，而不是一句"去补个测试"。
- **限流打满**：并发一上去就撞 rate limit。加队列和指数退避，宁可慢一点也别雪崩。
- **权限过大**：子 agent 能执行 push、删除类操作时，一个跑偏的 prompt 就是事故。高危工具一律不进子 agent 的工具表。

## 可复用建议

- 把高频子任务（跑测试、代码审查、写文档）固化成 subagent 模板，prompt 沉淀到配置里，用时只填变量。
- 输出格式统一（JSON 或固定字段），主 agent 才能程序化汇总，不靠猜。
- 子任务尽量幂等：重跑无副作用，失败重试才没心理负担。
- 每次派发把输入输出落盘记录。复盘时你会发现，80% 的失败来自同两类 prompt 写法。
- 先用 2~3 个并行验证流程，跑顺再扩并发，别一上来开满。

## 总结

Subagent 编排的提速是真实的，但它的本质是**任务分解 + 上下文隔离 + 结果验收**的工程问题，不是"多开几个 agent 就自动变快"。拆分粒度、回传协议、并发上限、权限边界——这几处设计比模型本身更决定成败。建议从一个小而独立的批量任务开始试，把流程固化下来，再逐步扩大使用面。
