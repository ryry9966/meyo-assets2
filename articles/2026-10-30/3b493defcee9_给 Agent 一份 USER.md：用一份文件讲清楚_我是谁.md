## 背景

OpenClaw 的会话天然是短命的，重启、换设备、清理会话之后，agent 对你的认知就会归零。社区目前通用的解法是用 workspace 里的几份 Markdown 作为常驻上下文：`AGENTS.md` 约束行为，`SOUL.md` 定义人格，`USER.md` 负责回答"你是谁"。三份文件各司其职，但实践里大多数人的精力都花在前两者，`USER.md` 往往留着模板原文没动过。

## 问题

没有一份像样的 USER.md，典型症状有三个：

- 每次新会话都要重新交代时区、常用语言、技术栈；
- agent 靠默认假设回答，比如给你 Python 示例，而你的主力语言是 Go；
- 项目代号、团队术语它听不懂，你每次都得现场解释一遍。

这些摩擦单次不大，但按会话频次累积起来，是自动化体验里最容易被忽视的损耗。

## 做法

`USER.md` 放在 workspace 根目录（默认 `~/.openclaw/workspace/USER.md`），随会话启动注入上下文。建议结构如下：

```markdown
# User Profile

## 基本信息
- 称呼：老张
- 时区：Asia/Shanghai，上午处理复杂任务
- 语言：中文交流，代码注释与提交信息用英文

## 技术栈
- 主力：Go / TypeScript，编排用 k8s
- 明确不用：PHP、jQuery

## 在进行的事
- openclaw 消息插件：当前在做路由重构
- 团队术语：内部把预发环境叫"预演"

## 协作偏好
- 先给结论，再给依据
- 代码示例直接给完整可运行版本
```

写法上三条原则：只写稳定事实；名词优先于形容词；宁可少，不要多。

## 踩坑点

1. **写成小作文**。USER.md 是每轮都消耗的固定 token，三百行的自我介绍会持续吃掉上下文预算。控制在几十行以内。
2. **放敏感信息**。密钥、内网地址、真实手机号都不要写。这份文件可能随 workspace 同步，也可能在你截屏分享时被带出去。
3. **放易变状态**。"这周在赶 v2 上线"两周后就过期了。易变内容交给 memory 或日志，USER.md 只留长期事实。
4. **和 AGENTS.md 抢职责**。"回答要简洁"是行为规则，归 AGENTS.md 管；USER.md 写"偏好先结论后依据"这类事实描述。两边重复会导致后续维护漂移。
5. **放任 agent 整篇重写**。默认行为里 agent 会被鼓励更新 USER.md，但它可能整文件覆盖，把你手工打磨的内容冲掉。建议明确约束：只做条目级追加或修改，重大改动先在对话里提出，人工确认。

## 可复用建议

- **让 agent 参与维护，人做守门员**：定期让它对比近期对话与 USER.md，输出"建议新增/删除的条目"，确认后写回。人负责准确，agent 负责发现。
- **一套模板多处复用**：同一份 USER.md 可以按 agent 裁剪，团队内部的 agent 加一节"组织背景"即可，不必从零写。
- **用 git 管 workspace**：USER.md 的提交历史，就是你为 agent 认知投入的账本，回滚和审计都方便。

## 总结

USER.md 的价值不在于让 agent"记住你"这种拟人化叙事，而在于把你的个人上下文从口头重复，变成一份可版本化、可审查、可复用的配置。花二十分钟写一版，之后每个会话都省掉一轮自我介绍——在自动化实践里，这是投入产出比最高的几分钟之一。
