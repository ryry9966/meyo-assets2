## 背景

OpenClaw 里最容易被低估的能力是 cron 任务：给 agent 一条 instruction，让它在指定时间自动醒来干活。很多人第一次配置时，把 instruction 写成一句日常对话，比如"每天早上帮我总结一下待办"，结果跑起来要么输出不稳定，要么半夜在错误的频道发了一堆消息。

原因很简单：cron 任务和交互式对话，是两种完全不同的运行环境。

## 问题出在哪

交互时你人在场，agent 犹豫了可以问你，跑偏了你可以拉回来。而 cron 触发时你大概率不在——instruction 就是 agent 拿到的全部信息。这带来三个硬约束：

1. **不能有歧义**。agent 无法追问，遇到含糊指令只能猜，猜错就是一次浪费的运行。
2. **上下文不保证**。定时任务往往跑在较干净的会话里，上次对话的结论、你口头交代过的偏好，它都不记得。
3. **输出有去处**。不说清发到哪、发多少，默认行为可能不是你想要的。

## 做法：把 instruction 当任务简报写

我的做法是按五段式写，每条 cron 都套这个结构：

```text
任务：每天 08:00 汇总 ~/notes/todo.md 中未完成事项
数据源：只读 ~/notes/todo.md，不读取其他文件
输出：发送到当前会话，格式「待办 N 条」，超过 5 条只列前 5 条并注明总数
边界：不修改任何文件，不调用额外工具，不要向我提问
异常：文件缺失或为空时，输出「数据源不可用：<原因>」后结束
```

几个关键点：

- **自包含**：数据源写绝对路径，别写"昨天那个文件"。
- **输出定格式和上限**：格式固定，后续才能做自动化校验或人肉巡检。
- **边界显式声明**："不要提问、不要改文件"这类否定句，在无人值守场景下非常值钱。
- **异常路径必须有**：数据源不可用时要求如实报告，而不是基于记忆编一份——这是防幻觉最有效的一条。
- **加完成信号**：末尾加一句"完成后单独输出一行 DONE"，方便 grep 运行日志确认跑没跑成。

## 踩坑点

- **对话式语气**。"帮我看看今天的日程"——哪个日历？什么算"看看"？cron 场景下这类问题没有答案。
- **假设它记得上次**。所有上下文写进 instruction，宁多勿缺。
- **时区**。确认 cron 调度器的时区和 agent 侧理解一致，"早上八点"差八小时的案例我见过不止一次。
- **一条任务塞多件事**。instruction 里出现"然后……接着……"就该拆成两条 cron，链式任务的失败率会陡增。
- **上线前不手动触发**。先手动跑一次看输出，别让第一次 scheduled run 兼职当测试。

## 可复用建议

- 把五段式模板存成自己的 snippet，新任务只填空。
- instruction 也是配置，进版本库管理，改了什么有据可查。
- 每周花五分钟翻一遍运行记录，输出格式漂移了就回去收紧 instruction——迭代 prompt 和迭代代码是一回事。

## 总结

Cron instruction 的本质，是写给一个无人值守、无法追问的执行者的任务简报：目标、数据源、输出、边界、异常，一段都不能省。写得越像"交代给同事的正式工单"，跑得越稳。
