## 背景

在 OpenClaw 里，cron 任务的本质是一次**无人值守的单轮 agent 会话**：到点唤醒、把 instruction 喂给一个全新会话、执行、投递结果，然后彻底忘记。它没有你平时的聊天上下文，也没有上一次运行的记忆。

这意味着 instruction 不是"提示词"，而是这个任务的**全部世界观**——工具、路径、时间、投递目标，缺一样它就只能猜。

## 问题

社区里常见的翻车姿势大致三类：

1. **写成对话腔**："帮我看下仓库有没有新 issue"——哪个仓库？发给谁？什么都不说。
2. **依赖上下文**："接着上次的事继续"——cron 冷启动，根本没有"上次"。
3. **无输出约束**：模型热情汇报，每天一条"今天一切正常"，两周后你开始无视所有通知，真出事反而看不见。

根因都一样：把 cron instruction 当成了和 agent 聊天，而它实际是给一个**失忆值班员写的交接备忘录**。

## 做法

我在用的一条结构化模板，五个固定段落，直接给例子（每天早上巡检 GitHub issue）：

```markdown
角色：你是我的仓库值班助手。当前时间由系统注入，时区 Asia/Shanghai。

任务：
1. 用 github 工具列出 <org>/<repo> 过去 24 小时内新增的 issue。
2. 按 bug / feature / question 分类，每类最多 3 条，
   附编号和一句话摘要。

投递规则：
- 有新增：把汇总发送到 Telegram 的「dev-alert」会话。
- 无新增：不要发送任何消息。

失败处理：
- 工具调用失败最多重试 1 次；仍失败则发一条含原因的一句话通知。
```

要点拆开说：

- **时间锚点**：要么显式注入当前时间，要么把逻辑写成"过去 24 小时"这种相对窗口，别让模型猜"今天几号"。
- **工具与对象写全**：MCP 工具名、仓库/文件/URL 路径、会话名，全部落字。cron 里不存在"你知道我说的是哪个"。
- **静默条款**：明确"无事不发"。对话里汇报是礼貌，cron 里**沉默才是**——这是两者最大的差异。
- **失败策略**：限重试次数，失败也要一句话通知。否则任务静默挂掉，你两周都不会发现。

## 踩坑点

- **要求确认**：任何会触发"请问需要我执行吗？"的写法，在无人值守下都是死锁。全部改成语义明确的祈使句。
- **跨次运行的状态**：想做到"只报新东西"，就得让 agent 每次把已处理的 ID 落盘到状态文件，下次先读再比对。别指望它记得。
- **输出无上限**：给格式模板和条数上限，汇报长度稳定，才有人看。
- **一条 cron 塞多件事**：抓取＋分析＋汇总＋多渠道分发，任何一环失败整条作废。拆开，每条只做一件事。

## 可复用建议

1. **先手动跑再挂表**：把 instruction 原样贴进对话执行一遍，确认工具可达、输出对路，再上调度，能省掉 80% 的"为什么没跑"。
2. **每次运行落一条日志**：让 agent 把时间戳和结果摘要 append 到文件，排查"到底跑没跑"全靠它。
3. **instruction 当代码管**：进版本库、改动走 review。三个月后你会感谢自己。
4. **加自检项**：在 instruction 末尾补一句"若发现现有工具无法完成本任务，发一条配置告警"，能兜住 MCP 改名、权限回收这类静默失效。

## 总结

一句话心法：cron instruction 是给一个**每次上班都失忆的值班员**写的交接备忘录——自包含、有锚点、有出口（投递到哪）、有静默条款（什么时候闭嘴）、有失败预案。满足这五条，定时任务才从"玄学"变成"运维"。
