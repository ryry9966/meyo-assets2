## 背景

OpenClaw-CN 社区的高质量讨论散落在论坛、GitHub issue 和群聊里，人工整理发帖效率低，还经常漏掉好内容。我花了两周业余时间做了个发帖机器人：定时抓取社区动态，由 Agent 生成候选帖，人工确认后自动发布。本文记录架构选型和踩过的坑。

## 问题

三个核心诉求：

1. **内容可信**——不能编造不存在的帖子、链接和数据
2. **发布可控**——不刷屏、不重复、失败可追溯
3. **单人可维护**——业余时间维护，链路必须短

## 架构设计

拆成四层（见配图）：

- **触发层**：cron 定时任务 + 手动触发入口
- **采集层**：通过 MCP 工具拉取数据源，统一输出结构化 JSON
- **生成层**：Agent 基于 JSON 素材生成 Markdown 草稿
- **发布层**：调用论坛 API 发帖，带幂等键

关键决策是**生成与发布分离**，中间插入审核队列。机器人只产出"草稿 + 引用来源"，不直接上线。

## 实施步骤

1. 定义两个 MCP 工具：`fetch_community_digest`（返回结构化素材）和 `post_topic`（封装论坛 API），每个工具只做一件事
2. Agent 的 system prompt 限定：只能基于素材写作，每个论点必须映射到素材 ID
3. 审核队列落 SQLite，状态机：`draft → approved → published / rejected`
4. 发布携带幂等键（素材 ID 的 hash），API 侧去重
5. 重试上限 3 次，超限告警到群

## 踩坑实录

**坑 1：幻觉链接。** 早期允许模型自由发挥，它编出了不存在的帖子标题。改法：映射不上的字段直接置空，发布前校验链接可达性，校验不过退回草稿。

**坑 2：重复发帖。** cron 重叠触发加重试逻辑，同一内容发了两次。改法：幂等键 + 发布前查库，把所有写入路径收口到状态机的单一路径上。

**坑 3：时区漂移。** 服务器是 UTC，crontab 按 UTC 跑，帖子总在国内凌晨发出。改法：时区换算写进代码，不依赖 cron 表达式本身。

**坑 4：Markdown 双重转义。** 正文里的代码块被采集层和发布层各转义一次，出现反斜杠堆积。教训：**sanitize 只做一次，且只在一层做**。

**坑 5：AI 味太重。** 生成帖一眼就是模型写的。改法：在 prompt 里放 3~5 条社区真实帖作为风格样例，并明确要求"宁可短，不要套话"。效果立竿见影。

## 可复用建议

1. MCP 工具粒度宁细勿粗，方便单测和单独替换
2. 一切外部写入必须有幂等键，别信"任务不会重复触发"
3. 状态落库，不依赖进程内存——机器人重启是常态
4. 人工审核不是妥协，是早期最便宜的质检手段，准确率稳定后再逐步放权
5. 归档每次发布的素材快照，事后能回答"当时为什么发这条"

## 总结

这个项目代码量不大，真正的工作量在边界处理：去重、重试、校验、时区。经验一句话：**AI 负责内容，工程负责确定性**——两者的分界线画清楚，自动化才能长期跑下去。欢迎在评论区交流你们的 Agent 自动化实践。
