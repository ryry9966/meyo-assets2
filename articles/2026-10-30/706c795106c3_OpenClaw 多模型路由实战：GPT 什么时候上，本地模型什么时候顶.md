## 背景

OpenClaw 的 agent 一旦接上定时任务和消息通道，调用量会远超"一天问几句"的预期：心跳巡检、会话摘要、工具编排、记忆压缩，全都是 LLM 调用。全走 GPT 这类云端模型，月底账单很难看；全换本地模型（Ollama / LM Studio），复杂任务又明显拉胯。多模型路由要解决的就是这个分配问题。

## 问题

我们一个跑了两周的 OpenClaw 实例，统计下来 80% 的调用是低价值任务（格式化、摘要、意图分类），只贡献了 15% 的实际效果；剩下 20% 的规划和代码生成才是质量敏感的。一开始全用旗舰云端模型，成本顶不住；一刀切全换本地小模型后，工具调用失败率从 2% 涨到 27%，直接不可用。

## 做法与步骤

**1. 先给任务分层，再谈配置。** 我们内部约定一张路由表：

- 意图分类、消息去重、记忆摘要、格式转换 → 本地小模型（qwen2.5:7b 级别）
- 常规对话、单工具调用 → 性价比云端模型（gpt-4.1-mini 一档）
- 多步规划、代码生成、复杂 MCP 编排 → 旗舰云端模型
- 纯心跳/巡检轮询 → 本地，或者干脆用脚本绕过 LLM

**2. 在 openclaw.json 里配主备和按 agent 覆盖**（节选示意）：

```jsonc
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4.1-mini",
        "fallbacks": ["ollama/qwen2.5:14b"]
      }
    },
    "list": [
      { "id": "digest",  "model": { "primary": "ollama/qwen2.5:7b" } },
      { "id": "planner", "model": { "primary": "openai/gpt-4.1" } }
    ]
  }
}
```

摘要、分类这类任务拆成独立 agent 绑定本地模型；planner 这种质量敏感的 agent 单独指定旗舰模型；默认值里配 fallback，云端限流时兜底。

**3. 观察一周再调。** 打开调用日志，看每个 agent 实际命中的模型、失败率和延迟分布，路由表按数据修订，不靠感觉。

## 踩坑点

- **本地模型的工具调用格式不稳。** 7b 以下参数量的模型 function calling 经常漏参数、编造 schema。工具多的 agent 别绑小模型，这是硬边界。
- **上下文窗口不对齐。** 本地 8k/32k vs 云端 128k，长会话 fallback 到本地会静默截断历史，表现为"agent 突然失忆"。会话长的 agent 别配本地 fallback。
- **fallback 风暴。** 云端限流时流量瞬间全砸本地，显存打满后两边一起挂。fallback 之间要留冷却时间，本地只做降级兜底，不做平级备胎。
- **"本地快"是错觉。** 短输出时确实快，长生成（尤其 planner）反而比云端慢。路由前先看清楚各任务的输出长度分布。

## 可复用建议

1. 路由表先写成文档、评审后再落配置，避免每个人随手加 agent 各自为政。
2. 每条调用日志记上命中的模型 ID，一周后拉个分布图，路由是否合理一目了然。
3. 用"降级可用"而不是"质量对齐"的标准验收本地模型。
4. 能用确定性脚本解决的轮询任务，别过 LLM——最便宜的路由是不路由。

## 总结

多模型路由的本质是按任务价值分配算力：低价值高频任务交给本地小模型，质量敏感的低频任务交给云端旗舰，本地模型承担兜底而非平替。先把任务分层、再配路由、最后用数据收敛，这套流程在任何 agent 框架里都成立。
