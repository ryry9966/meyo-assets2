## 背景

这段时间做 Agent 自动化的直观感受：模型本身很少出问题，出问题的往往是它调用的外部世界——搜索 API 限流、上游 503、MCP server 进程崩溃、内部接口超时。

Agent 的故障模式比传统服务更隐蔽：模型收到一个模糊的错误后，可能脑补一个结果继续往下走，也可能陷入无意义的重试循环把 token 烧光。所以错误恢复不是加个 try/catch，而是设计工具层与模型之间的契约。

## 问题：四种典型翻车现场

1. **异常直接抛出**：整条任务链中断，前面几步的成果作废；
2. **错误信息太模糊**（比如只返回"请求失败"）：模型反复重试同一调用，一晚上烧掉几十万 token；
3. **部分成功**：写了 3 个文件，第 4 步的 API 失败，状态不一致；
4. **降级不标注**：模型把三天前的缓存数据当最新结果汇报给用户。

## 做法：五层防线

**1. 错误分类。** 先区分可重试（429 / 503 / 超时 / 网络抖动）和不可重试（400 / 401 / 404）。分类错了，后面全白搭。

**2. 重试收在工具层。** 在工具包装器里做指数退避 + 抖动，最多 2~3 次。不要靠模型重试——模型的每次重试都是一个完整 LLM 回合，又慢又贵，而且它经常等不及就换思路。

```python
@tool_wrapper(timeout=10, retries=2, backoff=1.5)
def search_web(query: str) -> dict: ...
```

**3. 结构化错误返回给模型。** 重试耗尽后不要抛异常，返回结构化结果：

```json
{
  "ok": false,
  "error_code": "UPSTREAM_503",
  "retryable": false,
  "hint": "源站过载，建议稍后重试或改用 cache_read",
  "fallback": "cache_read"
}
```

模型看到 `retryable` 和 `hint`，才能做出合理决策：换工具、降级，或如实告诉用户失败。

**4. 熔断。** 单个工具连续失败 5 次就短路 60 秒，期间直接返回"该工具暂不可用"，避免模型在必死的调用上循环。

**5. 检查点。** 长任务每完成一步就持久化中间状态，恢复时从断点继续而不是从头再来。对跑了半小时的自动化任务，这一条最值钱。

## 踩坑点

- **幂等性**：重试 GET 没问题，重试 POST 可能重复下单。非幂等调用要么带幂等键，要么重试前先查询是否已成功。
- **吞错误**：失败时返回空字符串或空列表，模型会理解成"查到了，结果为空"。失败必须显式失败。
- **超时不匹配**：工具超时 30 秒，编排层 20 秒就杀进程，重试永远没机会跑。
- **MCP 断连**：stdio 方式启动的 MCP server 崩了不会自动重连，插件里要有显式的拉起与握手逻辑。
- **降级不标注**：fallback 数据必须在返回结构里带 `degraded: true`，否则模型照样当新数据用。

## 可复用建议

- 所有工具统一错误信封：`ok / error_code / retryable / hint / fallback`；
- 工具包装器标准化成统一装饰器：超时 10s、重试 2 次、熔断 5 次失败冷却 60s；
- 做故障注入：写一个永远返回 503 的 mock 工具，验证 Agent 的降级路径真的走得通；
- 结构化记录每次工具失败：哪个上游、什么错误码、重试几次后放弃，事后能复盘。

## 总结

外部 API 一定会挂，这是常态不是异常。Agent 的可靠性不取决于上游有多稳，而取决于你给模型的错误信息有多清晰、兜底路径有多明确。把错误当成一种结构化的返回值来设计，而不是当成异常来处理，Agent 才能在混乱中稳住。
