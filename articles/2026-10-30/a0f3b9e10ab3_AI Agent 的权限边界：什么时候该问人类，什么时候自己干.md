## 背景

Agent 接上工具之后，问题就从"它能不能做"变成了"它该不该自己做"。OpenClaw 这类网关型 Agent，日常动作包括读文件、调 MCP 工具、跑 shell、往渠道发消息。动作一旦能产生副作用，权限边界就不是可选项，而是设计的一部分。

## 问题

实践里常见两种极端：一种是什么都问，每步都要人确认，人很快疲劳，开始闭眼点"允许"，审批形同虚设；另一种是全放开，Agent 自信满满地把递归删除当成清理临时目录的合理手段。两种极端的根因相同：没有把"动作的风险"和"决策的方式"对应起来。

## 做法

我目前用的是三个维度打标签：

1. **可逆性**：做错了能不能撤销。只读操作（list、get、search）天然可逆；写本地文件可逆；发消息、调外部 API、删数据基本不可逆。
2. **爆炸半径**：影响一个文件，还是整个仓库、外部用户、生产环境。
3. **模糊度**：指令有没有多解释空间。"整理一下目录"比"把这 3 个文件移到 archive"模糊得多。

对应到策略：

- 只读 + 低模糊 → 自动执行，记日志即可
- 可逆写 + 明确范围 → 自动执行，但先 dry-run 或输出 diff
- 不可逆 / 出范围 / 高模糊 → 必须停下问人

落地时按工具类别配权限档位，而不是逐个动作配置。审批环节注意两点：展示将要执行的原始命令或请求体，而不是 Agent 的转述；审批默认带过期时间，超时视为拒绝。

## 踩坑点

- **审批疲劳**：问得太频繁，人就开始无脑放行。宁可收紧自动执行的范围，也要把"问"的次数压到真正值得问的水平。
- **把置信度当风险**：模型很确定 ≠ 动作很安全。置信度只该影响"问问题时附带的上下文"，不该影响"要不要问"。
- **一次审批被当成永久授权**："可以删这批临时文件"不等于"以后删什么都行"。审批要绑定到具体动作实例，不做隐式续期。
- **问得太模糊**："我可以继续吗"是坏问题。正确姿势是贴出 diff、命令、目标地址，让人 10 秒内能做出判断。
- **没有留痕**：自动执行和人工审批的动作要分开记录，事后排查全靠这个。

## 可复用建议

- 权限策略写成版本化文件，跟项目一起演进，别散落在 prompt 里
- 默认拒绝 + 白名单放行，反过来做一定会漏
- 破坏性操作强制二次确认 + 幂等键，防止重试导致重复执行
- 审批超时即拒绝，别让任务挂着等人半夜回来点确认
- 定期翻审批日志：放行率长期接近 100%，说明边界划得太保守；拒绝频繁，说明自动执行的范围放得太宽

## 总结

权限边界的本质不是"信任模型"，而是承认模型会错，且错了要有兜底。用可逆性、爆炸半径、模糊度三个维度划分动作等级，让低风险的事自动跑起来，高风险的事以具体、可快速判断的方式交还给人。边界划得好，人和 Agent 各自做擅长的事；划不好，要么人变成审批机器，要么 Agent 变成事故来源。
