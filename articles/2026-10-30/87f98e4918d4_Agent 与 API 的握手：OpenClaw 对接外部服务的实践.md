# 背景

Agent 的价值上限往往不在模型本身，而在它能触达多少真实服务。查订单、发消息、拉监控数据——这些都要和外部 API 打交道。OpenClaw 这类可本地运行的 Agent 框架，天然面对一个问题：怎么让模型稳定、安全地“握住”外部 API 的手。

# 问题：裸调 API 为什么不靠谱

早期我们试过最直接的路：把 API 文档片段塞进 system prompt，让模型自己拼 HTTP 请求。能跑，但问题很多：

- 模型拼 URL 和鉴权头时偶发出错，重试成本高；
- 密钥进了上下文，有泄漏风险；
- 返回的大段 JSON 直接灌进对话，token 烧得飞快；
- 模型“以为”调成功了，实际是 429 或超时，后续推理建立在幻觉结果上。

结论：让 LLM 直接面对 HTTP 协议，是把协议层的工作错交给了一层概率系统。握手这件事，应该由确定性代码完成。

# 做法：三步握手

1. **包一层 MCP Server。** 把目标服务封装成 MCP 工具，而不是让模型裸调 REST。一个领域一个 server：搜索归搜索，数据库归数据库，别塞成大杂烩。

2. **按“意图”设计工具，而不是按“端点”。** 不要把 `GET /users` 和 `GET /users/:id` 原样映射成两个工具，合并成 `search_users(query)` 和 `get_user(id)`，工具总数压到两位数以内。工具的 description 是写给模型看的：参数格式、返回结构、什么时候该用——这部分投入产出比最高。

3. **收窄返回面。** MCP 工具内部做完过滤、分页、字段裁剪，只返回模型需要的最小结构。错误别透传原始堆栈，转成一句人话加错误码，模型才知道下一步该重试、换路径，还是直接告诉用户失败。

鉴权走环境变量，server 启动时读取，不进上下文。写操作（建工单、发消息）单独加确认门：先 dry-run 打印意图，用户点头再真发。

# 踩坑点

- **工具多了选不对。** 15 个以上相似工具时，模型选择准确率明显下降，要么合并，要么按场景开关。
- **写操作没有幂等。** Agent 超时重试，结果建了三条重复工单。给写接口带上客户端生成的 idempotency key。
- **长请求阻塞主循环。** 超过 10 秒的调用改成异步任务加轮询工具，别让整个会话卡死。
- **日志里打印了完整请求。** 密钥和用户数据进了日志，事后清理成本极高。脱敏逻辑写进 server 代码，不能靠自觉。

# 可复用建议

- 新服务先只开只读工具，跑一周看调用日志，再决定开放哪些写操作；
- 用固定脚本做回归：准备 10 个典型问题，断言工具选择和参数拼装是否正确，每次改 prompt 后跑一遍；
- description 里明确“不要用这个工具做什么”，负向约束往往比正向描述更管用。

# 总结

Agent 对接外部服务，本质是把“概率式的语言理解”和“确定性的协议执行”接在一起。正确的握手姿势是：协议和鉴权交给 MCP/适配层，模型只负责决定调什么、传什么、拿到结果后怎么办。OpenClaw 的插件体系足够支撑这套分层，剩下的功夫在于工具粒度的克制和边界的收紧——这是 Agent 工程里最不像 AI、却最决定成败的部分。
