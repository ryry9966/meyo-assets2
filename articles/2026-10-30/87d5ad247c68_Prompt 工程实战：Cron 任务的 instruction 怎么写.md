## 背景

OpenClaw 的 cron 任务本质上是「无人值守的单轮对话」：到点唤醒一个 agent，塞一段 instruction，跑完工具就把结果发出去。它不像聊天窗口那样有上下文、有追问机会。社区里不少定时任务（每日摘要、监控播报、数据巡检）刚上线表现不错，跑一两周后开始跑偏——要么输出越来越长，要么重复播报，要么静默失败好几天没人发现。

复盘下来，问题大多不在调度配置，而在 instruction 的写法：很多人把它当成一句对话式请求来写，这在无人值守场景下是不够的。

## 定时任务和对话差在哪

三个关键差异决定了写法：

1. **没有现场用户**。agent 无法追问，遇到模糊指令只能猜或自由发挥。
2. **冷启动**。每次运行没有上次记忆，「今天」「最近」这类相对时间不定义，就靠模型猜。
3. **成本乘以频率**。每小时跑一次的任务，instruction 里塞的大段背景会被重复计费，输出刷屏也会被重复放大。

## 做法：五段式模板

迭代几轮后，我们把 cron instruction 固定成五段：**目标、步骤、输出、禁止、异常**。

```text
任务：每日 08:00 汇总上一轮运行以来的仓库告警。
步骤：
1. 读取 workspace/alerts.md 中记录的游标时间。
2. 通过 monitoring MCP 拉取（游标, 现在] 区间的告警。
3. 成功后把游标更新为本次运行时间。
输出：
- 无新告警：只回复"今日无新增告警"，一行。
- 有新告警：按 时间/服务/级别/摘要 列表输出，最多 20 条，其余汇总数量。
禁止：不执行重启等写操作；不调用列表之外的接口；不追问；不补充建议。
异常：任一步骤失败，回复"任务失败：<原因>"，不要编造或省略。
```

几个设计点：

- **状态放文件，指令放指针**。游标、去重用的 ID 列表都写在 workspace 文件里，instruction 只说「读这个文件、跑完更新它」。指令保持很短，状态还能跨次持久。
- **空结果也是结果**。必须规定没数据时回复什么，否则模型倾向于编一点内容交差。
- **输出格式收紧到可解析**。下游是脚本或另一个 agent 就给固定字段；发给人看也要限条数，防止刷屏。

## 踩坑记录

- 「帮我看看有没有什么值得关注的」这类开放式指令，第三天开始 agent 会把范围越扩越大，从看告警变成「顺便总结代码提交」。
- 相对时间没定义，服务器时区和用户时区不一致时拉取窗口会错位，出现漏报或重复。
- 没写异常分支，MCP 接口超时后 agent 回了一句「今日无异常」——静默错误最隐蔽，我们是靠输出里突然消失的游标更新才发现的。
- instruction 里贴了完整的项目背景文档，按小时跑一个月，token 花费是模板版的七倍多，对结果几乎没有影响。

## 可复用建议

1. 上线前手动触发跑三次，重点看空数据、接口失败两个分支。
2. 上线第一周每天人工 review 输出，之后放宽到每周抽查。
3. 频率和指令长度一起评估成本：10 分钟级的任务，每多 200 字都是乘出来的。
4. 涉及写操作的，在「禁止」段显式列出，比指望模型自己判断安全边界可靠。
5. instruction 改版时在 workspace 留一版 changelog，方便回溯某次异常对应哪个版本。

## 总结

Cron 任务的 instruction 不是一段提示词，而是一份给无人值守进程的运行说明。核心原则三条：上下文自足、边界显式、异常有出口。把状态外置到文件、输出格式定死、失败路径写清楚，定时任务才能从「演示」变成「基建」。模板不复杂，价值在于每次新任务都照着填，而不是即兴发挥。
