## 背景

关注的技术源一多（博客、GitHub Release、周刊、论文），手动刷新就变成负担。RSS 到今天仍是最稳的结构化订阅协议，但"订阅"本身不解决问题——你还是得读。LLM 摘要的价值在于把"读"压缩成"扫"，前提是有一条稳定的管线，而不是每次手动把内容丢给模型。

## 问题

我最初的做法很朴素：cron 拉几个 feed，拼一起丢给模型，输出推到群里。跑两周就暴露问题：

- 同一篇内容反复摘要，token 白烧；
- feed 里只有摘要没正文，模型总结得模棱两可；
- 偶发失败后没有状态记录，重跑会重复推送；
- 模型偶尔"补充"原文里没有的细节。

本质是把管线当成了无状态脚本。信息流管线的核心不是"调一次模型"，而是**状态管理 + 漏斗设计**。

## 做法

管线拆成四层，每层独立可替换：

1. **采集层**：RSSHub + 原生 RSS 混用，cron 定时拉取。只保留正文抓得全的源，抓不全的宁可不订。
2. **状态层**：SQLite 一张表，`url_hash` 做唯一键，记录条目状态（待处理 / 已摘要 / 已推送）。去重和断点续跑都靠它。
3. **加工层**：先规则粗筛（关键词、来源权重）把量压下来；再用便宜模型做单条摘要，约束输出结构化 JSON——一句话总结 + 标签 + 相关度评分 1–5。评分 ≥4 的才进精读队列，换强模型深读。摘要按 content hash 缓存，内容没变不重算。
4. **分发层**：攒成每日 digest 推到 Telegram / 飞书 webhook，附原文链接。链接只从原始条目取，绝不经过模型。

在 OpenClaw 里，加工层可以直接挂成 agent 任务：MCP 提供 fetch 和 sqlite 工具，agent 负责编排。但状态判断必须落库，不依赖 agent 的会话记忆。

## 踩坑点

- **guid 不可靠**：有些源 guid 和 link 都会变，去重要用"规范化 URL + 标题相似度"双保险。
- **正文抓取**：近一半的 feed 只给摘要。上 readability 类正文提取，提取失败就标记跳过，别硬塞给模型。
- **时间字段混乱**：Atom 和 RSS 时间格式不一，统一转 UTC 存储，按入库时间而非发布时间做增量，避免时区漏单。
- **输出格式漂移**：不约束格式，评分会飘。用 schema 校验，不合格重试一次，再失败进人工队列。
- **别让 agent 自由发挥**：定时任务里的 agent 只做编排和工具调用，阈值、去重这类决策写成显式规则，否则每次跑法都不一样。

## 可复用建议

- 四层结构（采集 / 状态 / 加工 / 分发）可平移到 changelog 监控、issue 摘要等场景。
- 状态用 SQLite 足够，别一上来上消息队列，量大了再拆。
- 成本控制靠漏斗：规则筛 → 便宜模型粗摘要 → 强模型精读，三层下来通常只剩 10% 的量。
- 原始条目永远保留，摘要只是缓存，模型和 prompt 随时可重跑。

## 总结

这套管线跑了快两个月，每日 digest 从最初 80+ 条压到 10 条左右，真正需要点开原文的约 2–3 条。体会是：AI 摘要本身不难，难的是去重、状态、漏斗这些"无聊"的工程。把 boring 的部分做扎实，AI 才有发挥空间。
