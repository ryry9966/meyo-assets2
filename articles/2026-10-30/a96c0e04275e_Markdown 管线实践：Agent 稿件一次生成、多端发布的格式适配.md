## 背景

OpenClaw Agent 的常见产出是 Markdown：教程、周报、发布说明、社区帖。写完只是第一步，摩擦都在发布端——公众号、知乎、掘金、GitHub Pages、RSS 各自吃不同的 Markdown 方言和 HTML 白名单。让模型针对每个平台各生成一份，很快失控：内容漂移，格式各自腐化。

## 问题

实际跑下来，适配层的坑集中在四类：

1. **方言差异**：脚注、任务列表、表格对齐，各平台支持参差；
2. **HTML 消毒**：公众号基本只认内联样式，外部 CSS 全部失效；
3. **资源外链**：图床防盗链，公众号会直接把外链图片清掉；
4. **模型输出不稳定**：同一份 prompt，今天输出标准脚注，明天给你一个 `[1]` 硬编码。

## 做法

思路是"单一事实源 + AST 变换 + 平台适配器"，用 unified/remark 全家桶：

1. **收敛方言**。给 Agent 的系统提示明确语法白名单：GFM 基础集 + 受控扩展，禁止裸 HTML。发布前跑 markdownlint 加自定义规则做门禁，不合规打回重写，而不是静默修正。
2. **规范化中间产物**。remark-parse 解析成 mdast 后先 normalize：图片引用统一为本地相对路径、剥掉模型偶尔夹带的 HTML、区分 front matter 与正文里的 `---` 分隔符（高频翻车点）。中间产物落盘一份严格 GFM 或 JSON，作为所有下游的输入。
3. **每个目标一个渲染器**。mdast → rehype 后按平台分流：公众号走样式内联渲染器，代码高亮转成 span 加行内色值；静态站和仓库保留原 Markdown，仅补 front matter；知乎、掘金按各自 API 能接受的子集渲染，超出的语法降级为纯文本。
4. **资源管道单独处理**。发布前把图片下载、压缩、按平台重传到对应存储，记录 URL 映射表保证幂等——重跑管线不会重复传图。
5. **接入自动化**。管线暴露成 MCP 工具（`render.preview` / `publish.post`），Agent 只负责把稿件写进 drafts 目录并调用预览；真正的发布动作保留人工确认。

## 踩坑点

- 别用正则做格式转换，嵌套结构（列表里的代码块、引用里的表格）必炸，坚持走 AST；
- 公众号编辑器会吞连续空行和部分嵌套列表，渲染器输出后要用 API 回读校验一遍；
- 代码高亮必须内联成行内样式，主题色值提前定死，别指望发布端帮你套主题；
- 模型幻觉出的"脚注引用"在 lint 层直接拒绝，降级处理比静默删除安全；
- 用金样测试锁定每个渲染器的输出快照，升级 remark 依赖前先跑 diff。

## 可复用建议

- 约束输入端（prompt 白名单 + lint 门禁）比在输出端打补丁便宜一个数量级；
- 一份 mdast，N 个渲染器，新增平台只写适配器，不碰上游；
- 预览优先：任何平台先出本地 HTML 预览，人确认后再触发发布工具；
- 图片映射表和稿件一起进 git，回滚时有据可查。

## 总结

这条管线本质上是把"格式适配"从每次手动的苦力活，变成一层可测试、可回滚的构建产物。Agent 负责内容，管线负责确定性，发布确认留给人——边界清楚之后，多平台发布就从玄学变成了 CI 任务。
