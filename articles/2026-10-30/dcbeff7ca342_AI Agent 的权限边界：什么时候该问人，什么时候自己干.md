## 背景

Agent 接上 MCP 和插件之后，能力从"聊天"变成了"干活"：读写文件、执行命令、调外部 API、往群里发消息。能力越大，一个问题越绕不过去：哪些事它自己拍板，哪些事必须停下来问人？

## 问题

实际用下来，失败模式就两种，而且经常来回横跳：

- **事事都问**。每写一个文件都来确认，三天之后你就开始无脑回"yes"——确认环节形同虚设，还平白消耗注意力。
- **自作主张**。它"好心"帮你清理临时目录，顺手把没备份的数据删了；或者把你让它起草的"回复"直接发进了客户群。

这两种都不是模型不够聪明，而是没划边界。边界不是靠一句"请谨慎操作"的 system prompt 划出来的。

## 做法

我们按两个维度给动作分级：**可逆性**（能不能撤销）和**爆炸半径**（影响多少人、多少系统、多少钱）。

1. **盘点工具**。把所有已接入的 MCP 工具和插件列一张清单，写清每个工具真实能触达什么：本地还是远程、只读还是可写、有没有外部副作用。
2. **分级**：
   - L0 读操作：查文件、搜索、看日志 → 直接放行；
   - L1 工作区内的可逆写：改草稿、生成代码 → 放行 + 留痕；
   - L2 不可逆或外发：删数据、部署到生产、给真人发消息、花钱调付费 API → 必须人确认；
   - 硬禁区：凭据操作、超过阈值的花费 → 配置层直接禁用，问了也不许做。
3. **闸门做在工具层**。分级规则写进 MCP 工具封装或插件 hook，高风险调用先走"预览 → 确认 → 执行"三步。不要只写在 prompt 里。
4. **默认 dry-run**。写操作先输出 diff 或将要执行的命令，人点头后才真跑。
5. **留审计日志**。自动执行的动作全部记录，每周翻一遍，边界划松了就收紧。

## 踩坑点

- **规则只写在 system prompt**：长对话后会被稀释，也挡不住注入。prompt 是软约束，工具层才是硬约束。
- **确认疲劳**：问得太频，人就变成橡皮图章。如果一周下来你 100% 都回"确认"，这个闸门等于没有，该往 L1 挪就挪。
- **靠关键词判风险**：盯"删除"两个字不可靠——文件名带"删除"的读操作不危险，不带"删"的 `DROP TABLE` 才致命。风险要看工具语义和参数，不看字面。
- **预览和执行不一致**：LLM 预览了一条命令，执行时又重新生成一条。正确做法是预览内容即最终执行内容，确认的是同一份快照。
- **授权粒度太粗**：整个插件一把梭放行，插件更新加了新工具，权限就悄悄扩大了。授权到工具级，最好到参数模式级。

## 可复用建议

一句话方针：**读放行、写留痕、外发必审、删改加锁**。另外三条：

- 先设计撤销，再设计确认；
- 一次确认只覆盖一次操作，不接受"以后都自动"；
- 把确认率当健康指标定期看，过高说明边界太紧，过低说明你在裸奔。

## 总结

权限边界不是一次砌好的墙，而是随信任度调整的闸门：Agent 表现越稳，L1 的范围可以逐步放宽；出过一次事故，就往回收一级。核心判断永远是两个问题——**这事撤销得了吗？搞砸了疼不疼？**想清楚这两个，剩下的交给分层闸门去执行。
