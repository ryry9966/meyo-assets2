## 背景

大多数助手默认是"被动应答机"：你发消息，它回消息。但真正省时间的场景往往是反过来的——每天早上它自己汇总昨天的 CI 失败，监控指标到了阈值主动提醒，发现日历冲突提前预警。OpenClaw 这类常驻 agent 框架天然具备做 proactive 的条件：进程常驻、有持久会话、能挂 cron 和 webhook。剩下的问题是，怎么让它"主动得恰到好处"。

## 问题

主动不等于勤快。做得糙的 proactive 助手，结局通常是被静音：心跳十来分钟一次，每次挤出一两条"一切正常"的废话；或者 webhook 一抖动连发五条消息。核心矛盾是：**触发很便宜，判断"值不值得打扰用户"很贵。**

## 做法：三层触发，按顺序上

**第一层：定时（cron）。** 确定性任务。比如每天 8:30 拉取昨日 GitHub 通知和日历，生成晨报发到固定会话。这层不涉及判断，最稳，先跑通它建立信任。

**第二层：心跳（heartbeat）。** OpenClaw 的 heartbeat 会周期性唤醒 agent。关键是在它的 system prompt 里写清判定标准："只在出现需要用户决策的事项时发言，否则保持沉默。"把沉默设为默认行为，而不是把"汇报"设为默认。

**第三层：事件（webhook / MCP 事件）。** 外部系统推事件进来，先过一道规则预筛——按事件 ID 去重、时间窗内聚合、阈值判断——再决定是否唤起 agent。比如监控告警，5 分钟内同一服务只聚合为一次。

另外，每层用独立会话、独立 prompt、独立 token 预算，不要混用主对话上下文。

## 踩坑点

- 心跳间隔设了 5 分钟，一天 288 次唤醒，token 消耗肉眼可见。改成 30 分钟加上业务时段限制后，成本降了一个量级。
- 早期晨报只是"汇报"，没有可执行结论，用户看了也不知道干嘛。改成三段式：发生了什么 / 我的判断 / 建议动作（附确认命令），反馈立刻变好。
- webhook 重试导致同一事件触发三次 agent。解法是在入口按事件 ID 做幂等。
- 让 agent 无人值守直接执行写操作（删分支、给客户发消息）风险极高。现在凡是非只读动作，一律降级为"提议 + 等确认"。
- 心跳醒来时上下文是空的，它不记得之前干过什么。每次触发必须注入一份状态摘要，不能指望它自己记得。

## 可复用建议

1. **用"打扰成本"倒推设计。** 一条 proactive 消息值不值得发，标准是"用户看到后能做什么 action"。没有 action 的通知，一律合并或丢弃。
2. **加静默窗口。** 夜间、会议时段不推，积压事件在窗口结束后聚合成一条发。
3. **渐进上线。** 先 cron 跑两周，稳定了再加 heartbeat，最后才接事件流。跳步直接上事件层的，基本都会被噪音教育。
4. **留审计尾巴。** 每次主动触发的决策（触发源、判定理由）落日志，出问题能回溯，也方便调 prompt。

## 总结

Proactive 的工程本质不是"让模型多想一点"，而是把**触发、判定、执行**三个环节拆开，各自设闸门。先让它在固定时间可靠地干活，再教它判断什么时候值得开口。宁可沉默，不要废话——用户对助手主动性的信任，是靠克制一点点攒出来的。
