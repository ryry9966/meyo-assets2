## 背景

OpenClaw 的 Agent 默认行为基本靠模型本身，但"它是谁、怎么说话、什么不做"这些特征，不写下来就是漂的。多轮对话、换模型、加插件之后，语气和边界经常不一致。SOUL.md 是 OpenClaw 工作区里的一个约定：一份纯 Markdown 文件，随会话加载进系统上下文，充当 Agent 的"人格层"。它和 AGENTS.md 分工不同——AGENTS.md 管做事流程，SOUL.md 管身份和边界；在定时任务、主动消息这类没有用户实时在环的自动化场景里，后者的作用反而更大。

## 问题

实际用下来有三个痛点：

1. **语气漂移**——今天正式明天卖萌，用户感知割裂；
2. **边界模糊**——Agent 对不该做的事（主动推送、处理敏感数据、越权操作）缺乏一致判断依据；
3. **配置散落**——人格相关指令散在 system prompt、插件描述、用户提示里，改一处漏三处。

## 做法

1. 工作区根目录建 `SOUL.md`；全局人格放 `~/.openclaw/` 下，项目里局部覆盖。
2. 按五个区块写：**身份**（我是谁、服务对象）、**语气**（正式度、回复长度、称呼习惯）、**边界**（不做什么、什么情况先停下来问）、**升级规则**（何时转人工/拒绝执行）、**禁忌清单**（明确红线）。
3. 篇幅控制在 30–60 行，每条写成可判定的规则，拒绝形容词堆砌。
4. 写完跑一轮对抗测试：故意诱导越界、逼它输出超长回答、丢敏感话题，看是否按规则行动。
5. 进 git，每次行为调整提交一个版本，回滚有据。

## 踩坑点

- **写成愿景文档**："你是一个乐于助人的伙伴"读了等于没读。要写"回复不超过 5 句，不确定就直说"。
- **当成硬约束**：SOUL.md 是软引导。真正的硬边界靠工具权限兜底——不装某插件、MCP 只开只读。两者互补，不能互相替代。
- **与全局 system prompt 冲突**：两边说法不一致时行为不可预测，改人格前先核对。
- **一次写太长**：超过一屏，靠后的规则注意力基本覆盖不到。
- **忽略覆盖关系**：项目目录的 SOUL.md 会盖掉全局版，换项目后人格"突变"多半是这个原因。

## 可复用建议

- 团队内定一个骨架模板，各项目只换身份段和边界段。
- 每接入一个新 MCP/插件，就把权限配置和红线清单放一起 review。
- 文件头部写一行版本号，日志里的行为变化能对到具体版本。
- 每月用同一组测试 prompt 打历史版本，diff 行为差异，防止规则腐化。

## 总结

SOUL.md 的价值不在"让 Agent 更像人"，而在把行为决策从隐式变显式：可版本化、可 review、可回滚。人格是软层，权限是硬层，两层都写清楚，Agent 才能在自动化场景里稳定服役。建议从 20 行的最小版本起步，用真实对话反馈迭代，别指望一次写完美。
