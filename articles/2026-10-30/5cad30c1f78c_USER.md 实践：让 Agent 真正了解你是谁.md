## 背景

用 Agent 干活一段时间后，会发现一个明显的错位：项目侧的记忆已经很成熟——`AGENTS.md` 把仓库约定、构建命令、代码风格都交代清楚了，但"你这个人"对 Agent 来说仍然是零。每次新会话，它不知道你偏好简体中文、不知道主力机是 Linux、不知道你讨厌长篇铺垫。这些信息要么每次重说，要么靠它猜。

OpenClaw 的工作区模板里有一份 `USER.md`，定位正是补上这块：`AGENTS.md` 告诉 Agent"怎么干活"，`USER.md` 告诉它"为谁干活"。

## 问题

没有 USER.md 的日常大概是这样：

- **沟通风格不稳定**：今天想要一句话结论，明天又收到长篇铺垫；
- **环境信息靠口头传递**："我的 shell 是 zsh，路径是……"，说完这次，下次归零；
- **偏好漂移**：你在某次会话里纠正过它的命名习惯，换个会话又退回默认。

本质上，是把"用户上下文"错当成了"会话上下文"。会话结束该丢弃的东西，不该包括你是谁。

## 做法

我现在的 USER.md 约 40 行，分五段：

1. **基本盘**：时区、常用语言、沟通偏好（结论优先，细节放后面）；
2. **环境**：操作系统、shell、常用工具链、网络环境特点，Agent 生成命令时直接对齐；
3. **技术画像**：熟悉/不熟悉的领域，决定它可以省略哪些解释、哪里要多给一步；
4. **当前焦点**：正在推进的 2-3 个方向，用于新会话冷启动时的优先级判断；
5. **红线**：明确不做的事，比如"不主动重构我没提的代码""替我发消息前必须先确认"。

写法上有两条原则：

- **稳定事实与易变状态分层**。身份、环境、长期偏好进 USER.md；进行中的任务、临时上下文放 memory 或项目文件。USER.md 里出现"本周要做 X"这类内容，一个月后就是污染源。
- **一条信息只写在一处**。项目级 AGENTS.md 已经写了"用 pnpm"，USER.md 就别再写，否则冲突时 Agent 无所适从。

**冷启动技巧**：不用硬憋。让 Agent 反过来采访你——"问我 10 个问题，帮我生成 USER.md 初稿"，再人工删改。它比你更清楚它需要什么。

## 踩坑点

- **写成简历**。我最初写了 100 多行，后来发现 Agent 根本用不上职业经历，它只关心"我能不能读懂这段代码"。砍到 40 行后命中率明显更高。
- **塞敏感信息**。USER.md 会注入每一次会话，别放密钥、真实住址。用"常用某云托管的 K8s 集群"这类抽象表述就够了。
- **只写禁令**。满屏"不要 XX"会挤压正向信息，且 Agent 对反向指令的执行本就不稳。能改写的尽量改写："回复先给结论"好于"别啰嗦"。
- **从不维护**。它和代码一样会腐化，我的习惯是每周顺手扫一遍，删掉失效条目。

## 可复用建议

- 把 USER.md 纳入 dotfiles 仓库，多机同步，版本可回溯；
- 各段用固定小标题，Agent 检索更稳；
- 会话结束时让 Agent 提议更新（"这轮对话有没有值得沉淀进 USER.md 的事实？"），你做最终裁决，避免它自作主张越写越长；
- 定期验证是否真的生效：新开会话问一个依赖环境信息的问题，看回答是否对齐。没生效就去查文件路径和注入逻辑。

## 总结

USER.md 的价值不在"存了什么"，而在把散落在无数次纠正和口头说明里的用户上下文，收敛成一份可版本化、可审查、可演进的事实清单。Agent 的能力边界近期不会突变，但你对它的"供给质量"可以——一个真正了解你的 Agent 和一个每次从零认识你的 Agent，产出差距是实打实的。40 行的成本，值得。
