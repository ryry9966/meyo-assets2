## 背景

用 OpenClaw 做自动化久了，总会撞上同一类任务：给 15 个模块各补一组单测、扫十几个数据源汇总成日报、把一批仓库逐个做依赖审查。这类活的共性是——单步不难，但量大、耗时，且彼此独立。

最初我让主 Agent 串行干，问题很明显：一是主会话上下文被中间过程塞满，跑到一半就开始"失忆"；二是慢，一个环节卡住，后面全部排队。

OpenClaw 的 subagent 机制正好对症：主 Agent 通过 `sessions_spawn` 派生独立子会话，子 Agent 干完把结果回传。听起来简单，但要稳定跑起来，编排层有不少工程细节。

## 做法

我目前的做法可概括为 fan-out / fan-in 三段式：

**1. 拆任务，先判独立性。** 并行的前提是子任务之间不共享可变状态。判断标准很朴素：各干各的文件、各查各的源，互不写对方的输出。

**2. 定契约，写死输出格式。** 给 subagent 的 prompt 用固定模板：目标、范围（显式写"不要碰 X 之外的任何文件"）、产出方式。关键一条是"结果落盘，回复只给摘要"——详细产出写到指定路径，回传不超过三句话。

**3. 并行派发，降配执行。** 子任务不需要旗舰模型，指定更快更便宜的模型跑，主 Agent 保留强模型做编排和验收。并发控制在 3~5 个。

**4. 收口合并。** 主 Agent 等待完成回调，逐份读取落盘结果做校验（格式对不对、有没有越界），再合并成最终产出。失败的任务重派一次，仍失败就降级为串行补跑。

## 踩坑点

- **并行写同一批文件必冲突。** 早期让子 Agent 直接改源文件，两个 agent 抢同一处改动，互相覆盖。现在每个子任务分配独立工作目录，合并由主 Agent 统一做。
- **回传太长，撑爆主会话。** 不约束输出长度的话，subagent 会把推理过程全贴回来。契约里必须写死"落盘 + 短摘要"。
- **子 Agent 会自由发挥。** 没禁止的事它都干。范围约束要显式、具体，"只处理 A 目录"比"注意范围"有用得多。
- **并发拉满触发限流。** 一次性 spawn 十几个，API 报错连锁失败。小步放量，先 3 个验证再往上加。
- **成本是倍数关系。** 并行很爽，token 消耗也是并行的。跑大批量前先拿 2~3 个任务估一下单价。

## 可复用建议

- 把子任务 prompt 沉淀成模板或脚本参数，换批数据就能复跑；
- 结果交接一律走文件，不走对话——文件是确定性的，对话是易丢的；
- 主 Agent 只做拆解、派发、验收，重活全下放；
- 每个子任务设超时和重试上限，编排层永远要有兜底。

## 总结

subagent 并行不是"多开几个窗口"，核心就两件事：任务拆分的独立性、结果交接的确定性。契约写清楚、兜底做扎实，批量类任务的耗时会从小时级降到分钟级，主会话也始终保持干净。这套 fan-out/fan-in 模式在社区的各种自动化场景里几乎通用，值得照着搭一遍。
