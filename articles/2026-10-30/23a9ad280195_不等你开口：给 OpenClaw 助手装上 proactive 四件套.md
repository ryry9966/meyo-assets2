## 背景

大多数人用 Agent 还停留在"一问一答"：发消息、等回复、会话结束。而 OpenClaw 这类常驻助手的真正差异点在于 heartbeat——它可以按间隔自己醒来，检查环境，再决定要不要说话。但不少人开了心跳后，得到的是每 30 分钟一条"今天一切正常"，一周后默默关掉。这篇记录我把自家助手从"定时废话机"调成"值得信任的值班员"的过程。

## 问题：proactive 的三个失败模式

1. **噪音**：心跳触发 ≠ 有事可报。没有判断标准时，模型倾向于"汇报点什么"，产出大量低价值消息。
2. **重复**：每次心跳是独立会话，Agent 不记得上次报过什么，同一个失败任务能连报三天。
3. **越权**：为了让它"直接把事办了"，有人一上来就给写权限——删文件、发消息、调接口，误操作只是时间问题。

## 做法

**第一步：触发器分层。** 低频心跳（30–60 分钟）跑常规巡检；固定周期的任务（晨报、周盘点）走 cron；外部事件（CI 失败、新邮件）走 webhook，别用轮询硬扛。

**第二步：把判断标准写进心跳清单。** 为每项职责写三行：检查什么、什么算异常、异常时做什么。关键是显式钉死**默认沉默**："无异常时回复 HEARTBEAT_OK，不给用户发消息"，否则模型每一轮都想表演工作。

**第三步：接 MCP 工具，只读先行。** 巡检所需的取数能力（查仓库状态、读日志、调监控 API）全走 MCP 或本地脚本。前两周只挂只读工具，先观察它上报的质量。

**第四步：降噪与状态记忆。** 用一个状态文件记录已上报的事件 ID 和时间戳，心跳时先读它做去重；同类事件加冷却时间；夜间静默时段只放行严重级别高于阈值的报警。

**第五步：权限分级放行。** 上报质量稳定后，逐个放开低风险写操作（打标签、建草稿）；高危操作（发消息、删除、支付类调用）保持"先通知、人确认、再执行"。

## 踩坑点

- **心跳间隔贪快**：15 分钟一次，token 账单先教你做人。巡检 30–60 分钟足够，事件类交给 webhook。
- **没写沉默默认**：模型天性是"有输出好过没输出"，提示词里不钉死，它每轮都找话说。
- **去重靠会话记忆**：跨会话记忆不可靠，状态文件 + 事件 ID 才是确定性的。
- **心跳里跑长任务**：一次心跳分析全部日志，超时后干了一半。心跳只做检查和分诊，重活拆给单独触发的任务。
- **没有审计日志**：它半夜到底干了什么？把每次心跳的输入、决策、动作落盘成 JSONL，出事能回放。

## 可复用建议

- 心跳清单当配置管理，进 git，改规则走 commit，别在聊天里口头改。
- 所有主动行为收敛成三档：**静默 / 通知 / 行动**，每档写清进入条件。
- 观察期制度：任何新权限先 read-only 跑两周再放行。
- 单次心跳设 token 和时间 budget，防止巡检失控。

## 总结

Proactive 的核心不是让模型更聪明，而是工程四件套：**可靠的触发器、显式的判断标准、确定性的去重、分级的权限**。默认沉默、异常发声、行动需授权——做到这三条，它才从"定时打扰"变成你愿意留在白名单里的值班员。
