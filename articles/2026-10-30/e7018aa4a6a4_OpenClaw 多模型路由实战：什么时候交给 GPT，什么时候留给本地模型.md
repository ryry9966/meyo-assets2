## 背景

OpenClaw 的模型层本来就不绑定单一供应商：gateway 里可以同时挂云端模型和本地推理（Ollama、LM Studio、vLLM 都行），每个 agent、每个 skill 还能单独指定模型。但很多人的用法仍然是“全局一个旗舰模型跑所有任务”，结果要么账单难看、隐私数据出域，要么反过来全走本地，agent 频繁抽风。

## 问题

把路由问题拆开，其实是三个权衡：

- **能力**：重推理、代码生成、复杂工具编排，旗舰模型明显更稳；轻量摘要、格式转换、分类打标，本地小模型够用。
- **成本与延迟**：云端按 token 计费，首 token 延迟受网络影响；本地小模型几乎免费，交互场景体感反而更快。
- **隐私**：聊天记录、日志、内网文档这类内容，出域前要过一道心。

单一模型不可能同时在这三条线上最优，所以路由的本质不是“选哪个模型”，而是“按任务分桶”。

## 做法

我的分层方案，供参考：

1. **任务分桶**。把 agent 的工作流过一遍，粗分四类：复杂推理/代码、长上下文处理、结构化输出、轻量预处理。
2. **配三档模型**。重任务给云端旗舰；中间档给云端小杯或本地 30B 级别；轻任务（清洗、摘要、字段抽取）全走本地 7B~14B。
3. **落到配置而不是写死**。按 agent/skill 指定模型，别在代码里硬编码，切档只改配置。
4. **隐私规则前置**。涉及内网地址、凭据上下文的工作流，直接绑死本地模型，不给路由选择权。
5. **建一条 fallback 链**。云端限流或超时降级到本地，保证自动化任务半夜不挂——但降级必须写日志，必须可见。
6. **每周看一次指标**。token 消耗和工具调用成功率超过阈值就回头调分桶。

## 踩坑点

- **工具调用是分水岭**。小本地模型 tool calling 掉链子的概率远高于旗舰，表现为死循环、参数幻觉。凡是多步工具编排的 agent，别贪便宜。
- **长上下文别硬塞**。本地模型上下文窗口小，长文档 RAG 一上就截断或爆显存，该走云端就走云端。
- **结构化输出要加校验**。本地模型的 JSON 格式漂移明显，schema 校验加重试一次，仍失败再升档到云端。
- **静默降级最危险**。fallback 触发了但没记录，你会以为质量一直这么差，其实是模型悄悄换了。
- **只算单价会算错账**。云端重试、超长上下文、agent 多轮膨胀，都是隐性 token，按会话算成本才真实。

## 可复用建议

- 三档起步即可，别上来做五档，分桶过细维护不动。
- 把“哪些数据不许出域”写成清单，绑定到具体 skill，而不是靠人肉判断。
- 固定一个小评测集（20~50 个典型任务），换模型、改路由前跑一遍，避免凭感觉切。
- 本地模型优先选 function calling 成熟度高的（Qwen 系列实测较稳），能省大量调参时间。

## 总结

多模型路由的核心不是省 token，而是让每个环节拿到“刚好够用”的模型：重活给旗舰，杂活给本地，敏感数据不出门，降级必须留痕。先把任务分桶做扎实，再谈模型选择——顺序反了，就是一个持续调参的无底洞。
