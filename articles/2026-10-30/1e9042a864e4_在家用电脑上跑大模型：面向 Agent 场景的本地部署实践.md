## 背景

用 OpenClaw 这类常驻型 Agent 网关做自动化的人，迟早会面对同一个问题：任务 7×24 在跑，云端 API 账单和隐私边界都在变大。本地跑模型不是要替代云端，而是做分层——高频、低难度的任务（总结、格式化、简单的 MCP 工具调用）交给本地模型，复杂推理留给云端。这篇帖记录我在这台 32GB 内存 + 12GB 显存的家用机上折腾两个月的结论。

## 问题

家用硬件的核心矛盾有三个：

1. 显存有限，装不下心心念念的大模型；
2. 本地小模型的**工具调用质量参差**，直接决定 Agent 和插件链路能不能用；
3. 运行时默认的上下文配置偏小，Agent 多轮循环很容易撑爆。

## 做法

1. **盘点硬件**。经验值：Q4 量化下 7-8B 模型约需 6GB 显存，14B 约 10-12GB，32B 要 20GB 以上。纯 CPU 能跑，但 Agent 场景首 token 延迟很伤体验。
2. **选运行时**。Ollama 上手最快，llama.cpp 可控性强，两者都提供 OpenAI 兼容接口，接 OpenClaw 没有障碍。LM Studio 适合桌面端快速试模型。
3. **选模型**。中文 + 工具调用场景，Qwen 系列是稳妥选择。8B 级别（Q4_K_M）是本地 Agent 的甜点位；Qwen3-30B-A3B 这类 MoE 模型激活参数少，中端机器也能有不错的吞吐。
4. **接入网关**。把 provider 指向本地端点（如 `http://127.0.0.1:11434`），设好模型名和上下文长度，务必跑一个包含工具调用的测试任务再上真活。
5. **分层路由**。在 Agent 配置里区分任务等级：本地吃轻任务，重任务回落云端，成本立刻可控。

## 踩坑点

- Ollama 默认 `num_ctx` 只有 2048，Agent 场景必改。但上下文拉高会线性增加 KV cache 显存，8B 模型开 16k 上下文，实际占用远超模型本体，别只看参数量算账。
- 工具调用在 4B 以下模型上基本不可靠，参数幻觉、JSON 崩坏是常态，这点显存省不得。
- Q2 量化会破坏结构化输出，而 Agent 依赖 JSON 解析，Q4_K_M 是底线。
- MoE 模型显存占用看着低，但全部参数都要进内存，统一内存架构的笔记本要按总账算。
- Windows 下驱动和 CUDA 版本问题比 Linux 多，建议先在 WSL2 里验证，再固化到生产。

## 可复用建议

- **建评测集**：收集 10-20 条你真实的 Agent 任务，换模型时跑一遍，比看任何跑分都管用。
- 给本地模型定位是"省钱的工具调用工人"，别期待它做深度推理。
- 用 docker compose 固化 Ollama + OpenClaw 的本地栈，配置进版本管理，重装系统十分钟恢复。
- 监控首 token 延迟和每轮 token 消耗，Agent 循环失控时能第一时间发现。

## 总结

本地部署的价值不在"完全离线"，而在分工：让八成的轻任务零成本、零隐私顾虑地跑在自己机器上。路径很简单——从 8B Q4 + Ollama 起步，用真实任务验证工具调用质量，再决定往上加规模还是往下压成本。家用电脑跑大模型早已不是能不能的问题，而是怎么分工的问题。
