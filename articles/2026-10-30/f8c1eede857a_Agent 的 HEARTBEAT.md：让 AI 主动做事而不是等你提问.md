## 背景：被动应答的局限

绝大多数 Agent 的工作模式是被动的：你发消息，它响应，然后沉寂。问答场景没问题，但一旦想让它承担日常值守——盯仓库、巡检磁盘、定时汇总 CI——被动模式就失效了。脚本加 crontab 能做，但逻辑游离在 Agent 的上下文和工具链之外，改一处要同步两处。

OpenClaw 里有一个很轻的机制解决这个问题：**heartbeat**。Agent 每隔一段时间被唤醒一次，读取工作区里的 `HEARTBEAT.md`，按里面的清单决定这一轮要不要干活、要不要说话。

## 做法：一个文件 + 一行配置

**1. 新建心跳清单**

```markdown
# HEARTBEAT

<!-- 每轮执行，仅异常时说话 -->
- 检查 ~/repos/api 的 git remote，有新 commit 才汇报
- 磁盘使用率 > 85% 时提醒我

<!-- 定时任务 -->
- 每天早上 8 点：汇总昨晚 CI 失败记录，没有则跳过
```

**2. 配置唤醒间隔**（默认 30 分钟）：

```json
// ~/.openclaw/openclaw.json
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "30m" }
    }
  }
}
```

**3. 理解静默约定**：文件只有默认的 `# HEARTBEAT` 一行时，Agent 会跳过本轮、不做输出。这是省 token 的总开关——暂时不想要主动行为，把清单注释掉恢复默认即可，不用动配置。

## 踩坑点

1. **Token 成本线性于频率。** 每次唤醒都会把清单和上下文送进模型。清单控制在几行内，低价值任务合并或降频。
2. **噪音是第一个坑。** 我第一版写了"汇报巡检结果"，结果一晚上收到十几条"一切正常"。改成"仅异常时输出"后世界安静了。措辞里一定要写清*什么情况才值得说话*。
3. **别让它改自己的心跳文件。** 有次我在任务里写了"根据负载调整检查频率"，它真的重写了 `HEARTBEAT.md`。清单是给 Agent 的输入，不是它的可变状态，不要在任务里授权编辑这个文件。
4. **长任务会打乱节奏。** 心跳是串行唤醒的，某轮塞一个跑十分钟的构建检查，后续全乱。心跳任务保持幂等、快速，重活交给系统 cron 或让它自己排期。
5. **敏感信息别进清单。** 文件内容每轮都会进入上下文，当成明文对待。

## 可复用建议

- 用注释把清单分成三区：**每轮执行的 / 定时的 / 仅异常出声的**，"默认沉默、异常出声"可以直接当模板。
- 实际检查交给 MCP 工具（探活、查库、读日志），`HEARTBEAT.md` 只描述"何时检查、何时报告"，职责分离。
- 跨天的定时任务别完全依赖 Agent 的时间感，汇报里让它带上上次执行时间，或者用系统 cron 打桩兜底。
- 频率先低后高：从 1 小时起步，观察一两周的 token 账单再收紧到 30m/15m。

## 总结

HEARTBEAT.md 的价值不在功能多强，而在于它把"主动性"收敛成一个纯文本文件：可版本化、可 review、可回滚。你不需要写调度代码，只需要回答一个问题——**每隔一段时间，什么情况值得我被打扰**。把这个问题写清楚，Agent 就从应答机变成了值守者。建议从一两个低频巡检任务起步，跑两周再扩。
