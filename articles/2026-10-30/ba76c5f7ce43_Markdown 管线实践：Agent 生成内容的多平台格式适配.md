## 背景

在 OpenClaw 这类 agent 环境里，内容生产的终点往往是一篇 Markdown：agent 写完稿，真正的麻烦才开始——同一篇稿子要发公众号、知乎、掘金和自己的静态站，各平台对格式的容忍度差异极大。我们跑了一条从 AI 生成到多平台发布的管线，稳定用了几个月，把设计和踩坑整理如下。

## 问题

- 公众号编辑器只接受内联样式的 HTML，Markdown 原文贴进去排版基本报废；外链图片有防盗链，大概率裂开。
- 知乎、掘金接受 Markdown，但对表格、脚注、代码高亮的支持各不相同。
- 静态站最宽松，GFM 全支持。
- AI 产出本身也不干净：标题层级乱跳、混入内联 HTML、代码块缺语言标签、全角半角标点混用。

如果每加一个平台就重写一遍后处理脚本，维护成本很快失控。

## 做法

核心思路：**一次生成，中间标准化，末端自适配**。

1. **生成侧立契约**。在 agent 的 skill 提示里硬约束：只用标准 Markdown，禁内联 HTML，标题最多三级且不跳级，代码块必须带语言标签，图片统一 `![alt](local-path)` 占位。
2. **中间层统一转 AST**。用 remark 把文档解析成 mdast，写一组小插件做规范化：标题降级、图片上传图床并回写 URL、剥离 frontmatter、统一标点；脚注、任务列表等节点按目标平台能力决定保留或降级。关键是一切变换都在 AST 上做，不要正则改字符串。
3. **平台适配器**。每平台一个渲染器：公众号走“Markdown → 内联样式 HTML”的主题渲染，图片改传平台素材库；知乎、掘金直接吃规范化后的 Markdown；静态站保留完整 GFM。适配器只处理差异，共享同一份规范化输出。
4. **发布前校验 + 人工闸门**。lint 检查图片可达性、标题层级、死链，渲染一份预览；发布动作保留人工确认，agent 负责备稿，不直接发。

## 踩坑点

- 正则处理 Markdown 必挂：代码块里的示例文本、转义字符都能把脚本搞崩，尽早换 AST。
- 公众号图片必须传到自己的素材库，外链必裂；上传接口有频率限制，要做重试和本地缓存。
- AI 爱用加粗当标题、随手画 `---` 分割线，契约里要显式禁止。
- 缺语言标签的代码块会让各平台高亮不一致，规范化时兜底一个默认语言。
- 不要让 agent 直接生成 HTML：class 名每次都不一样，主题渲染根本没法复用。

## 可复用建议

- 维护一张“平台能力矩阵”（脚注/表格/任务列表是否支持），规范化插件读它做决策，新增平台只加一行。
- 准备一份特性全覆盖的 golden Markdown，进 CI 做渲染快照对比，改主题或插件时所有平台的输出 diff 一目了然。
- 管线设计成幂等：同样的输入重跑输出一致，排查问题省心。
- 把适配器拆成独立插件或 MCP tool，agent 按目标平台调用，别堆成一个大而全的脚本。

## 总结

多平台发布的复杂度不在“写”，在“适配”。把格式差异收敛到 AST 规范化层，用能力矩阵驱动降级策略，发布前保留人工闸门，这条管线就能随平台数量线性扩展而不是指数恶化。它不性感，但很稳。
