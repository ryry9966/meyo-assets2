## 背景

大多数 Agent 的用法还是“你问一句、它答一句”。这没问题，但真实工作里有大量事情是周期性、可预期的：早上的日程汇总、CI 挂了要第一时间知道、订阅源里筛出值得看的内容。这些事不该等人想起来。proactive 的本质不是让模型更聪明，而是把“触发”从用户转移到系统：定时器、事件源、策略规则先行，Agent 只负责在被触发后聚合上下文、给出结论。

## 问题

把 proactive 做成“每 5 分钟唤醒一次模型”很快就会翻车：通知轰炸、token 成本失控、用户开始忽略一切推送。核心矛盾是信号率——主动推送的价值必须显著高于打扰成本，否则这个能力反而降级了体验。我们在 OpenClaw 里折腾了几轮，最后收敛成一个三层结构。

## 做法：三层结构

**1. 定时心跳层。** 一个独立调度入口（cron 或常驻进程）按策略唤醒 Agent，注入两样东西：上次运行的时间戳 + 预定义任务模板。Agent 通过 MCP 拉取日历、监控、Git 等数据源，做增量对比而非全量重述，产出一份摘要。要点：状态外置，每次只处理 delta。

**2. 事件订阅层。** Webhook / MCP 事件推送进统一的 inbox 队列，Agent 消费前先过策略：是否命中订阅规则、是否在静默时段、是否与近期已推送内容重复。所有插件不直接触达用户，必须走 inbox——这是去重和频控的唯一收口。

**3. 提案层（draft-only）。** 带副作用的动作（发消息、合并 PR、改配置）默认只产出草稿和 diff，等用户一键确认。主动性体现在“它已经把事准备好了”，而不是“它替你做了”。

## 踩坑点

- **触发器没做幂等**：重试导致同一事件推了三次。给每条事件加 ID，在 inbox 层去重。
- **上下文膨胀**：每次心跳都全量拉所有 MCP 工具结果，token 直接失控。只拉任务模板声明的数据源，并缓存上次结果做 diff。
- **权限一开始放太开**：某次自动重试把草稿直接发出去了。副作用必须分级，写操作一律要确认。
- **没有退出机制**：用户嫌吵却找不到怎么关某个触发器。策略要暴露成可编辑的配置文件，不能散在代码里。

## 可复用建议

- 把主动性做成**声明式策略**：trigger、数据源、静默时段、是否需确认，一个 JSON 说清楚，Agent 只执行策略，不夹带私货。
- 每次主动触发都留**审计日志**（时间、触发源、是否推送、是否被采纳），每周看一次采纳率，低于阈值的触发器直接删。
- 频控做在 inbox 而不是各插件里：全局每小时上限 + 优先级排序，低优先级事件攒成每日摘要。

## 总结

proactive 不是让模型猜你想什么，而是一个工程问题：触发从哪来、信号怎么过滤、副作用怎么兜住。把心跳、事件、提案三层拆开，把策略声明式地配置出去，主动的 Agent 才能长期有用而不讨人嫌。欢迎在社区帖下交流你们的事件源接法和频控参数。
