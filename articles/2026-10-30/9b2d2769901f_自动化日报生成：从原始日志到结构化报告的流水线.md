## 背景

我们团队维护几个线上服务，日报需求很朴素：每天早上十点前，群里要有一份昨日摘要——错误总量、Top 错误、发布记录、值得关注的异常。之前一直靠人肉：早上打开几个日志平台，切时间窗，grep 一遍，把数字填进模板。全程约二十分钟，且经常漏项。

于是花了两个周末，把它做成了一条自动化流水线，跑在 OpenClaw 的定时任务上，配合 MCP 工具调用。目前稳定运行两个多月，本文记录做法和踩坑。

## 问题：为什么不是"把日志丢给 Agent"

最初的直觉是把原始日志直接喂给 Agent 让它总结。试过一次就放弃了：

1. 单日日志量轻松上百万行，远超上下文，靠截断必然丢信息；
2. LLM 数数不可靠，错误次数这类关键字段必须精确，幻觉一个数字，日报就废了；
3. 输出格式每天不一样，历史数据没法纵向比对。

结论：**统计交给脚本，叙述交给 Agent**。日志归日志，报告归报告。

## 做法：四段流水线

**第一段：采集与归一化。** cron 触发脚本，从 nginx、应用日志、发布系统各拉一份昨日数据，统一转成 JSONL 中间格式，字段固定：timestamp、level、service、error_code、message。这一步纯脚本，不涉及模型。

**第二段：本地聚合。** 用 Python（早期是 jq + awk）做统计：按 error_code 计数、取 Top 10、按 service 分组、解析发布记录。产出一个几百字节以内的结构化摘要 JSON。所有关键数字都在这里产生。

**第三段：Agent 叙述。** 把摘要 JSON 通过 MCP 工具传给 OpenClaw Agent，同时给一份固定模板，要求逐槽位填充：数字原样引用，不新增不推算；每个异常项附一句解释。模型在这一步只做两件事——组织语言、标记需要人工关注的点。

**第四段：投递与存档。** 拼好的 Markdown 推到群 webhook，同时在仓库存档一份，文件名带日期。失败时发告警消息，而不是默默吞掉。

## 踩坑点

- **时区边界。** 第一版用 UTC 算"昨天"，和本地日期差八小时，日报里混进了前天晚上和今天早上的日志。改成显式指定本地时区再取日界。
- **日志格式漂移。** 某服务升级后 error_code 字段改名，解析器静默产出空值，日报连续三天显示"错误数：0"。教训：聚合脚本必须校验 schema，解析失败率超过阈值直接告警。
- **模板不定，风格漂移。** 早期让 Agent 自由发挥，输出有时表格有时段落。后来把模板锁死成固定槽位，模型只填空，日报才有可比性。
- **静默失败最致命。** 流水线挂掉比报告难看更糟。加了两层：cron 退出码监控 + 报告文件心跳检查，当天十点前无产出就告警进群。

## 可复用建议

1. **"脚本计算、Agent 叙述"是一个通用分层。** 凡是需要精确数字的报告场景都适用，Agent 永远不要接触原始明细。
2. **JSONL 中间产物值得保留。** 后来的周报、月报直接复用这份聚合数据，只改叙述模板，几乎零额外成本。
3. **幂等性很重要。** 任意日期重跑结果一致，历史日报可随时重生成，也方便回溯排查。
4. **失败路径和成功路径同等设计。** 告警、心跳、schema 校验三件套，比流水线本身更能决定它能活多久。

## 总结

这条流水线的核心不是"用 AI 写日报"，而是任务切分：确定性的事交给脚本，语言层面的事交给 Agent，中间用一份小的结构化摘要衔接。总代码量不到三百行，模型调用每天一次，成本可忽略。对有类似日报、周报需求的团队，建议先从"归一化 + 本地聚合"做起，Agent 层最后接入——顺序反了，很容易停在"Demo 惊艳、上线不可靠"的状态。
