## 背景

单个 agent 跑长任务链的痛点大家都遇到过：上下文越滚越长，工具调用只能串行，中途一步跑偏，后面全部作废。subagent 编排是目前比较务实的解法：主 agent 只负责拆任务和收结果，把“脏活”——大量读文件、批量检索、多方案调研——交给若干上下文隔离的 subagent 并行处理。

我们在文档补全和仓库批量重构两类任务上跑了一段时间，这里记录一下做法和踩过的坑。

## 问题

落到工程里，单 agent 模式有三个硬伤：

- **上下文污染**：几十个文件的读取记录堆在一个窗口里，后半段推理质量明显下降；
- **串行延迟**：40 个模块逐个处理，纯等待时间占了大头；
- **职责混杂**：搜索、判断、写入混在一个循环里，出错后很难定位是哪一环。

## 做法

以“给仓库 40 个模块补文档”为例，我们的编排分五步：

1. **拆任务**。主 agent 先扫描目录，产出任务清单。每个子任务声明：目标模块、产出物、禁止触碰的路径。拆分原则是按资源边界切，保证子任务之间不写同一个文件。
2. **定契约**。每个 subagent 只拿到最小上下文（该模块的代码 + 一个模板），工具白名单只开文件读写和一个检索用的 MCP server，输出强制为固定结构：`{module, summary, diff_path, warnings}`。
3. **并行派发**。一批一次性发出，并发上限 3–5。再高基本只会换来 API 限流和成本曲线失控。
4. **落盘回收**。subagent 的完整输出写入 `run/<task_id>/` 目录，主 agent 只读 summary 字段做汇总；需要细节时按 task_id 定向翻原始文件，而不是让 subagent 把全文塞回来。
5. **失败降级**。超时或输出不合契约的子任务标记为 partial，由主 agent 决定重试还是降级为串行处理。

一个可以直接抄的结构示意：

```json
{
  "task_id": "docs-auth-07",
  "scope": ["src/auth/**"],
  "tools": ["fs", "search"],
  "output_schema": ["module", "summary", "diff_path", "warnings"],
  "max_turns": 8
}
```

## 踩坑点

- **子任务不独立**。最初按“功能”拆，两个 subagent 同时改 `config.py`，互相覆盖。改成按目录/文件分片后才稳定。
- **输出不守契约**。subagent 偶尔会“热心”多写分析段落，汇总时上下文又爆了。解法是严格校验 output_schema，不合格直接判失败重试，不要宽容。
- **递归派发**。有次 subagent 自己又开了 subagent，深度失控。现在硬性规定：编排深度为 1，subagent 内部禁止再派发。
- **上下文大礼包**。把主 agent 的完整历史传给 subagent，又贵又带偏方向。只传最小必要上下文，效果反而更好。
- **摘要丢细节**。只读 summary，后续追问时信息已经不在了。原始输出落盘 + 按 ID 检索是必须的。

## 可复用建议

- 把“拆分–派发–回收–降级”固化成一个可复用的工作流或 MCP tool，参数化并发数、输出 schema 和 run 目录，不要每次手写。
- 子任务用稳定 ID 命名，实现幂等：重跑时跳过已有产出的任务，断点续跑几乎免费。
- 调试期把并发设为 1，先串行跑通契约，再放开并行。并行只会放大契约设计的问题，不会修复它。
- 给每批任务设 token/成本预算，超了就熔断——这是成本失控唯一有效的闸门。

## 总结

subagent 编排的核心不是“多个 AI 很酷”，而是上下文管理和契约设计：主 agent 保持轻，子任务保持独立，输出保持结构化。它适合可拆分、子任务间弱依赖的批量型工作；如果任务本身强串行依赖，硬拆只会扩大失败面。建议从一个真实的小规模批量任务起步，把契约和落盘机制跑顺，再逐步放大并发。
