## 背景

我的 OpenClaw 常驻跑着几个自动化任务：定时摘要、搜索查询，还有几个走 MCP 接家庭设备的插件，链路全部依赖外部 API。某天上游搜索接口开始间歇性 503，暴露出 agent 层最脆弱的部分：它不会"恢复"，只会循环重试，或者硬编一个答案。

问题不在于 API 会挂——一定会挂——而在于挂掉之后 agent 的行为是否可控。

## 问题：三种典型失控

1. **重试风暴**：插件内部重试 3 次，agent 看到 error 又自己重试，乘法效应一次任务打出十几个请求，触发 429 恶性循环。
2. **幻觉成功**：工具抛异常被外层 try/except 吞掉，返回空数据，模型把"空"当"结果"，编出一条像模像样的回复。
3. **整体阻塞**：一个 hanging 的 HTTP 请求没设超时，整个 session 卡住，后面排队的任务全部延迟。

还有隐蔽的一条：对写操作盲目重试，消息发两遍、设备状态翻转两次。错误恢复必须是系统设计，不是 prompt 里一句"失败了重试"。

## 做法

插件层四件事，agent 层两件事：

**1. 错误分级，结构化返回。** MCP 工具永远不抛裸异常，统一返回：

```json
{ "ok": false, "code": "UPSTREAM_TIMEOUT", "retryable": true }
```

模型能读懂结构，才会选"换源"而不是瞎猜。

**2. 有界重试，且只放一层。** 只对 retryable 类（429/5xx/网络错误）重试，最多 2 次，指数退避加抖动，尊重 `Retry-After`；4xx 一律不重试。agent 侧规则只有一条：失败可以直接再调一次，失败两次必须如实告知用户。

**3. 熔断。** 插件内维护计数：连续 5 次失败后熔断 60 秒，期间快速失败并返回 `CIRCUIT_OPEN`。熔断按 endpoint 维度而非 provider——一个慢接口不该连累同一家其它工具。

**4. 降级链。** 主源 → 备源 → 本地缓存（允许陈旧，但必须标注"数据为 N 分钟前"）→ 明确告诉用户"现在拿不到"。缓存只在成功响应上写入，TTL 5 分钟，错误响应绝不入缓存。

**5. 超时与预算。** 每个工具调用 10s 超时，每次运行有总时长预算。宁可快速失败，也不要在工具里 sleep 30 秒——那在 agent 看来就是 hang。

**6. 幂等约束。** 自动重试只允许读操作；写操作要么带幂等键，要么降级为"报告失败，等确认"。

## 踩坑点

- **两层都写重试**（插件一层、agent 一层），实际次数相乘，这是最常见的事故源。重试所有权只给一层。
- **catch-all 吞异常后返回空数据**，模型视为成功。宁可让错误"难看"地透传。
- **退避没加抖动**，几个定时任务整点对齐，上游恢复瞬间打出同步洪峰。
- **熔断状态藏起来**。我加了一个只读的 status 工具，agent 和我都能查"哪些源当前不健康"，排障快很多。
- **把错误响应缓存成数据**，导致恢复后几分钟内还在吐旧错误。

## 可复用建议

任何接外部 API 的工具包装器，过一遍这个清单：有没有超时？错误有没有分类和结构化？重试是否有界且单层？有没有熔断和降级路径？写操作是否幂等？失败时模型拿到的信息，够不够它做"如实告知"这个最简单的决定？

## 总结

API 挂掉不是异常路径，是常态路径。Agent 的可靠性不来自更聪明的 prompt，而来自工具层把失败"说得清楚"：分类、有界、可降级、可观测。做完这套之后，那次 503 再出现时，agent 的行为从"疯掉"变成了"换源，或者告诉你拿不到"——这就够了。
