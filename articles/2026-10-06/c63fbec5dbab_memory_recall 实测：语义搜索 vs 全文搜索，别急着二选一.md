## 背景

OpenClaw 里 `memory_recall` 是 agent 长期记忆的入口，召回质量直接决定它“记不记得住事”。社区里常见两种路线：**全文检索**（SQLite FTS5 / BM25）和**语义检索**（embedding 向量召回）。前者被嫌“土”，后者被认为“高级”，争论很久，我们干脆拿真实记忆库跑了一轮对比。

## 问题

memory 条目大多不是文档，而是短句笔记：项目代号、配置片段、客户需求、报错记录。真实查询也偏短，比如“上次那个 Redis 配置”、“XX 项目的部署账号”。这类 query 下，语义搜索真的更优吗？带着这个疑问做了个小实验。

## 做法

1. **数据准备**：从 memory 目录导出约 200 条真实条目，去重、按时间排序、保留来源标签。
2. **全文侧**：SQLite FTS5 建索引，BM25 排序，top 8。
3. **语义侧**：中文 embedding 模型（bge-small-zh 级别即可），条目级存储，余弦相似度 top 8。
4. **评测**：40 条真实 query 人工标注相关条目，计算 Recall@5 和 MRR。
5. **混合**：两路结果用 RRF（倒数排名融合）合并。

结果（样本有限，仅供参考）：

- 精确关键词类 query（报错码、文件名、专有名词）：**全文明显更稳**；
- 口语化改写类 query（“那个跑批失败的事”）：**语义召回更好**；
- **RRF 混合平均表现最均衡**，没有明显短板。

## 踩坑点

- **FTS5 默认 unicode61 分词对中文几乎无效**——整句被当成一个 token，中文匹配基本失效。要么用 trigram tokenizer，要么检索前先 jieba 分词。
- **embedding 对短查询漂移严重**。人名、代号这类 query，向量召回经常给出“语义相近但完全无关”的条目，别迷信向量库。
- **切块太碎会丢上下文**。记忆条目建议整条存储，检索命中后附带前后邻居条目，agent 的利用率明显更高。
- **记忆会过期**。排序时必须让时间戳参与权重，否则半年前的旧事实会盖过昨天的更新。
- **top_k 别贪多**。融合后取 5 条左右比较平衡，塞太多反而污染上下文窗口。

## 可复用建议

1. **别二选一**。简单做法是查询路由：含引号、代码、数字、英文标识符的 query 走全文优先；自然语言长句走语义优先。省事做法是直接 RRF 混合。
2. **先建评测集再动手**。哪怕只有 30 条人工标注 query，也比凭感觉调参强——没有评测，换模型就是来回震荡。
3. **检索日志落盘**，统计命中率。这是判断“换 embedding 模型有没有用”的唯一客观依据。
4. **中文 embedding 选型务必在自己语料上实测**，公开榜单分数高不等于你的记忆条目上好用。

## 总结

语义 vs 全文不是替代关系，是互补关系。OpenClaw 实践里最省心的组合是：**FTS5 保底**（快、零外部依赖、结果可解释），**embedding 补语义召回**，RRF 融合加时间衰减排序。先有评测集，再谈优化——memory_recall 的上限不在检索算法多新，而在你对自家记忆数据有多了解。
