## 背景

OpenClaw 的 Agent 是长期运行的常驻进程，不是一次性的对话。每次会话启动时，workspace 里的一组 Markdown 文件会被注入上下文：`AGENTS.md` 管工作约定，`USER.md` 记用户信息，`SOUL.md` 定行为基调，而 `IDENTITY.md` 决定"它是谁"——名字、语气、性格边界。

很多人的用法走两个极端：要么装完就用默认身份，要么把它当成第二个系统提示词，塞几十行规则进去。两种做法跑一段时间后都会撞上同一个问题：Agent 表现不稳定，今天简洁明天啰嗦，你不断在聊天里重复纠正同样的事。

## 问题：身份放哪、怎么改

先厘清边界，这是我踩坑之后稳定下来的分工：

- `IDENTITY.md`：它是谁。名字、人设、语气、硬边界。只写"是什么"，不写"怎么做"。
- `SOUL.md`：它信什么。价值观与行为优先级。
- `AGENTS.md`：它怎么干活。任务流程、工具使用惯例。
- `USER.md` / `MEMORY.md`：它面对谁、记住了什么。

混着写会导致优先级不可预测——两份文件对同一行为给出矛盾指令时，结果基本看运气。

## 做法

1. **保持精简。** 我的 IDENTITY.md 常年控制在 15 行以内：名字、整体气质（creature/emoji）、语气基准线、三到五条硬边界。身份不是提示词仓库，每次会话都要付 token 成本。

2. **用 git 管它。** workspace 本身就是目录，init 一个仓库，身份变更和代码变更一样走 commit，message 写清"为什么改"。回滚和跨设备同步都有了。

3. **建立进化闭环。** 当你在对话里第三次纠正同一件事（比如"别道歉那么多次"），就把它蒸馏成一行写进 IDENTITY.md，而不是继续口头纠正。这个文件的价值就在这：一次性成本，之后每个会话生效。

4. **让 Agent 参与提案，人来拍板。** 重度使用一整天后，我会让它对 IDENTITY.md 出一份 diff 建议，逐条审。它比你自己更能注意到哪些指令它总做不到、哪些是冗余的。审核权必须留在人手上，否则身份会朝"讨好当前会话"的方向漂移。

5. **定期修剪。** 每季度过一遍，删掉已被 SOUL.md 覆盖或证明无效的条目。身份应该一屏读完。

示例片段：

```markdown
# IDENTITY.md
- Name: Claw
- Creature: 一只务实的工程橘猫，低功耗待机
- Emoji: 🐾
- 语气: 直接、简短，先给结论再给理由，不堆客套
- 硬边界: 不确定时明说"我不确定"，不编造；不替用户做不可逆操作
```

## 踩坑点

- **改了不立即生效。** IDENTITY.md 在新会话加载，正在跑的会话不会热更新，改完记得开新会话验证。
- **别写能力声明。** "你可以访问 GitHub"这种句子没用也有害——能力来自 MCP/工具配置，写进身份文件只会制造幻觉空间。
- **多设备同步易冲突。** 建议固定一台主力机编辑，其他端只读，避免 workspace 的 git merge 地狱。

## 可复用的建议

- 一条规则一行；写不进一行的，说明它属于 AGENTS.md。
- 新增条目带日期前缀，三个月没再触发就删。
- 把 IDENTITY.md 的 commit history 当作 Agent 的"成长记录"来回顾，比翻聊天记录高效得多。

## 总结

IDENTITY.md 是 OpenClaw 里成本最低、杠杆最高的文件之一：十几行 Markdown，加上 git 和一个"纠正即蒸馏"的习惯，就能让 Agent 的性格从默认模板变成随你的使用方式收敛的东西。它不神秘——本质上是把对人的反馈周期，工程化地搬到了对 Agent 的配置上。
