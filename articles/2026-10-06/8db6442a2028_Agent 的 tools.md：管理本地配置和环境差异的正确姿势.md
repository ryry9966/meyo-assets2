## 背景

跑 Agent 做自动化时，最贵的不是 token，是 Agent 的"猜"。同一份任务描述，在我的机器上顺利跑完，换一台机器就卡在 ffmpeg 缺失、代理没配、路径不对。Agent 每次会话都在重新认识你的环境，认识方式要么靠试探（慢、浪费、可能装错东西），要么靠你写进提示词——写多了污染上下文，写少了就靠猜。

tools.md 就是给 Agent 的一份"环境事实清单"：本机有什么工具、版本多少、路径在哪、有什么怪癖。思路和 AGENTS.md 这类约定同源，但聚焦在工具与环境本身。

## 问题

实际用下来有三个痛点：

1. **环境漂移**。手写的 tools.md 很快过时：文件里写着 python 3.10，机器早已升到 3.12；文档说有 GPU，其实驱动挂了。Agent 信任过期信息，排障比没有文档更难。
2. **共享与本地混杂**。项目要求什么工具是团队共识，本机装在哪、用哪个包管理器是个人事实。混在一个文件里，要么提交了私人路径，要么漏掉公共约定。
3. **规模失控**。有人把整段 `--help` 输出贴进去，上下文瞬间被吃掉，Agent 反而抓不住重点。

## 做法

我的方案是"分层 + 生成 + 校验"：

**第一步：分层。** 仓库里放 `tools.md`（提交），只写项目级契约：最低版本、必需命令、已知限制。本机事实放 `tools.local.md`（gitignore），写 OS、包管理器、实际路径、代理、GPU 状态。优先级约定：local 覆盖 repo。

**第二步：生成而非手写。** 写一个 `probe.py`（约百行），探测关键工具后输出本机文件。每行保持原子格式：

```
python: /usr/bin/python3 (3.12.1)
node: /opt/homebrew/bin/node (20.11.0)
proxy: http://127.0.0.1:7890 (env HTTP_PROXY)
quirk: ffmpeg 需 brew 完整版，系统自带的不带 libx264
```

时间戳写进文件头，Agent 一眼能判断新鲜度。

**第三步：接入会话流程。** 在启动钩子里先跑 probe 再加载文件。同时约定：Agent 发现现实与文档不符时，停下来说明差异、重新生成文件，而不是自己绕过去。

**第四步：控制体量。** 上限 50 行左右，只写 Agent 会据此行动的事实，背景解释一律不放。

## 踩坑点

- **别放密钥**。只写环境变量的名字（如 `API_KEY 从 env 读取`），绝不写值。这个文件很容易被读进上下文，泄漏面比 .env 大得多。
- **路径写探测规则而非死值**。跨平台路径差异大，与其写死 `C:\...`，不如由 probe 生成，彻底避免手滑。
- **确认加载机制真的生效**。不同框架对工作区根目录文件的读取时机不同。上线前用一个"复述 tools.md 第三行"之类的探针任务验证一次，别默认写了就等于读到。
- **行尾与编码**。跨平台协同时统一输出 LF，避免某些解析器对 CRLF 敏感。

## 可复用建议

- probe 脚本和仓库级 tools.md 一起版本管理，本机文件当作构建产物——"文档即缓存"。
- 单独维护 `quirks` 小节，专收"每次都咬你一口"的坑，这是整个文件里 ROI 最高的部分。
- 团队多人使用时，把 probe 放进 CI，跑在不同 OS 镜像上，输出样例文件供参考。

## 总结

tools.md 本质是机器与 Agent 之间的一层显式契约：仓库级管共识，本机级管事实，脚本管新鲜度。让 Agent 少猜一次，自动化链路就少一个随机故障点。这套做法不绑定特定框架，三十分钟就能在现有项目里落地。
