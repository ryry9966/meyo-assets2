## 背景

Agent 做自动化久了，你会反复回答同一类问题：Python 在哪、浏览器 profile 用哪个、这台机器上某个 MCP 服务的端口是多少。这些本质上是"环境事实"，常见做法是塞进 system prompt 或让 Agent 自己探索——结果换台机器、换个容器，工具调用就开始翻车。

tools.md 的定位很直接：给 Agent 的本机说明书，声明这台机器上有哪些工具、怎么调用、前置条件是什么。它不是给人看的文档，是运行时依赖。在 OpenClaw 这类带 workspace 的框架里，它可以直接放进工作区，随会话自动加载。

## 问题

把环境信息硬编码进 prompt 或脚本，通常撞上三种故障：

1. **漂移**：环境升级后路径变了，旧信息还躺在 prompt 里，Agent 按错误前提调用，错误越滚越大。
2. **不可移植**：同一份配置在 macOS、Linux 服务器、Docker 容器之间复制粘贴，home 目录、包管理器、shell 全不一样。
3. **泄密**：为省事把 token、内网地址写进共享配置，仓库一推就出去了。

## 做法：公共层 + 本地层

核心思路是拆两层，Agent 同时读，冲突时本地层覆盖公共层。

**公共层 `tools.md`**（进仓库）：只描述契约，不放本机事实。每个条目固定四项——用途、调用模板、验证命令、注意事项：

```markdown
## browser-automation
- 用途：网页抓取与表单操作
- 调用：走 playwright MCP 工具集
- 验证：test -n "$BROWSER_PROFILE_DIR"
- 注意：容器内无头模式需加 --no-sandbox
```

**本地层 `tools.local.md`**（gitignore）：只放本机事实——绝对路径、端口、版本号、启停开关、环境变量名（是名字，不是值）。仓库放一份 example 模板，新机器复制一份即可。

**加载与验证**：启动时公共层打底，叠加本地层；没有本地条目的工具按"未验证"处理，首次调用前先跑验证命令。每个验证命令就是一行 shell，建议把检查脚本挂进启动流程，几秒钟标出所有失效项——这是整套机制里性价比最高的一步。

**边界要清楚**：MCP 连接配置归 MCP 配置文件管，tools.md 只引用、不复制内容。单一事实源，别搞出两个。

## 踩坑点

- **密钥写进本地文件**：即使 gitignore 了，备份、截图、贴日志都可能带出去。只写变量名，值放环境变量或系统密钥管理器。
- **条目只增不减**：失效工具不清掉，Agent 会在无关选项上浪费推理甚至选错。删的比加的多才是健康状态。
- **忽略平台差异**：Windows 的路径分隔符、PowerShell 与 bash 的命令差异，验证命令要分开写，别想一套通吃。
- **抄进 prompt 图省事**：内容一旦复述进 system prompt，两处必然漂移。原则是 prompt 里只说"先读 tools.md"。

## 可复用建议

1. 新机器初始化三步走：clone 仓库、从 example 生成本地文件、跑验证脚本。
2. 公共层改动走 PR 评审，本地层永不进版本库。
3. 定期 diff 本地文件，半年没被调用的条目直接删。
4. 把"验证通过"当作 Agent 启动的前置条件，而不是事后排查的依据。

## 总结

tools.md 的价值不在文件本身，而在于把环境事实从 prompt 和脚本里剥离出来，变成可分层、可验证、可移植的显式声明：公共层管契约，本地层管事实，验证脚本管真相。做到这三件事，Agent 跨环境迁移的翻车率会明显下降，排查时也只需要看一个文件。
