## 背景

OpenClaw 的典型形态是一个常驻 Agent 挂着若干 MCP 工具和技能，处理从"帮我改个格式"到"跨三个数据源排查问题"的各种请求。请求难度方差极大，但很多部署默认所有流量走同一个旗舰模型——账单线性上涨，敏感数据也全部出网。

## 问题

我们踩过的真实痛点有三个：

1. **成本**：80% 的请求其实是短摘要、格式转换、字段抽取，用旗舰模型纯属浪费；
2. **延迟与可用性**：简单任务也要吃云端排队和限流，而本地模型明明空闲且毫秒级响应；
3. **隐私**：日志、客户数据类内容不希望离开本机，但又不想为这类任务单开一套流程。

核心问题是：路由边界画在哪里，怎么画得可维护。

## 做法：三级分级 + 回退链

我们按"任务复杂度 × 数据敏感度"两个维度分级：

- **L0 机器级任务**：格式转换、正则式抽取、简单重写 → 本地小模型（7B~14B，走 Ollama / LM Studio 接入 OpenClaw）；
- **L1 常规任务**：单文档摘要、常规问答、简单工具编排 → 中档云模型；
- **L2 疑难任务**：多步推理、代码重构、跨源排障 → 旗舰模型，开更高的思考预算。

落地上分三步：

1. **按 agent 显式指定模型**，不依赖全局默认。比如消息分拣 agent 固定本地模型，深度分析 agent 用旗舰模型。都在 `openclaw.json` 里落到 agent 级配置，一目了然。
2. **加一个"复杂度闸门"**。主 agent 前置一个轻量分类步骤（本地模型跑一个分类 prompt 即可），输出 L0/L1/L2 标签再分发。注意别用 token 数做唯一判据——很多短请求其实是难题。
3. **配置回退链**：云端超时或限流时降级到本地模型，并明确告知用户"本轮结果来自降级模型"。宁可明说，不要静默降级让输出质量抖动。

## 踩坑点

- **工具调用可靠性差异最大**：本地模型对 function calling / MCP 参数 schema 的遵循度明显弱于旗舰模型，长工具链别路由到本地；
- **上下文窗口**：本地模型常见 8k~32k，MCP 返回的大块结果会被静默截断，路由层要前置做长度检查；
- **隐性重试**：降级链路里如果两层各自重试，成本和延迟会翻倍，重试上限要在全局收敛；
- **中文 token 成本与英文不同构**，费用估算别照搬英文基准；
- **分类器漂移**：流量分布变化后闸门准确率会掉，留一个每周抽样人工核对的入口。

## 可复用建议

- 先全量打标跑一周，统计每类请求的真实分布，再定路由规则，不要拍脑袋定比例；
- 给每个模型记录调用次数、平均时延、失败率，路由调优靠数据不靠感觉；
- 敏感任务宁可牺牲一点质量也固定走本地，这类决策不要做成动态的。

## 总结

多模型路由的本质不是省钱技巧，而是把"任务难度异质性"显式建模。先用分级和回退链兜住下限，再用数据慢慢收窄边界。多数场景走到"L0 全本地、L2 全云端"这个稳态就够用了，不必追求完美路由。
