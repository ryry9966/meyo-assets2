## 背景

Agent 接上 MCP 和插件之后，能力从"回答问题"变成了"改文件、调接口、发消息、花钱"。每个做自动化的人迟早会撞上同一个问题：哪些动作让 Agent 自己执行，哪些必须停下来等人确认？这个边界不划清楚，要么自动化没价值，要么一次事故赔掉所有信任。

## 问题：两种失败模式

实践里常见的两个极端：

- **全都问**：写个文件也要弹确认，人沦为点击机器，自动化价值归零。
- **全都干**：一次误删分支、一封发错对象的邮件，代价远超省下的确认时间。

这不是"多问少问"的调参问题，而是需要显式设计的工程问题。

## 做法：按可逆性和影响面分四级

给每个工具调用按两个维度打标：**可逆性**（能不能撤回）、**影响面**（出事后波及多大）。分四档：

| 档位 | 特征 | 典型动作 | 策略 |
|---|---|---|---|
| L0 | 只读、本地 | 读文件、搜索、只读 API | 直接执行 |
| L1 | 可逆写、影响面小 | 写工作区草稿、建 draft PR | 自动执行 + 审计日志 |
| L2 | 不可逆或对外 | 发邮件、删数据、部署生产、支付 | 必须人工确认 |
| L3 | 禁区 | 改自身权限配置、触碰凭据 | 直接拒绝，写死在系统提示 |

落地步骤：

1. **盘点归档**：列出 Agent 可调用的全部工具，逐个归入 L0–L3，形成权限矩阵文档。
2. **最小授权**：MCP server 只挂需要的工具；目录白名单、域名白名单这类参数级限制，比工具级开关更有效。
3. **确认必须带 diff**：L2 动作的确认内容要展示"将把什么改成什么、发给谁、花多少钱"，而不是一句"可以执行吗？"——后者人根本没法判断。
4. **新工具先 dry-run**：跑一轮看日志，再决定它是升档还是降档。

## 踩坑点

- **确认疲劳**：L2 动作太多，人会机械点"同意"，闸门形同虚设。解法不是加提醒，而是把动作本身做成可逆（草稿代替直接发送、回收站代替删除），让它降级到 L1。
- **提示词过紧泄漏**：系统提示里笼统写"谨慎操作"，Agent 连读文件都开始请示。要显式说明哪些动作"不需要问"。
- **授权永久化**：任务级授权用完应回收，别让一次确认变成永久通行证。
- **异步确认没有超时策略**：人不在，Agent 要么卡死要么自行其是。应定义超时后挂起，而不是降级自答。

## 可复用建议

- **默认拒绝，增量放行**：信任用日志换，每次事故后回溯一次分级。
- **L1 必须留痕**：自动执行的动作全部进审计日志，出事能回放。
- **权限矩阵当代码评审**：改一档要写明理由，而不是顺手一改。

## 总结

权限边界不是一次性配置，而是随事故历史持续调整的旋钮。起点从严，用日志和复盘换取放松的依据。本质上，让更多动作变得可逆，Agent 的自主空间就自然变大——这比反复调提示词管用得多。
