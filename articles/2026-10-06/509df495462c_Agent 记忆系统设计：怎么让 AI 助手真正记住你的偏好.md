## 背景

模型本身是无状态的。你昨天告诉 Agent"构建用 pnpm，别用 npm"，今天它照样生成 `npm install`。上下文窗口不是记忆，只是工作区——会话一关，什么都不剩。对长期运行的自动化 Agent 来说，偏好评判标准很朴素：记得住事的 Agent，废话少一半。

## 问题：三种常见方案为什么不够用

1. **全量塞 system prompt**：几轮后 prompt 膨胀，费用上升，无关记忆还会稀释关键指令。
2. **重放聊天历史**：token 成本线性增长，超窗截断时，被截掉的往往恰是偏好。
3. **会话摘要**：摘要丢细节，"不吃香菜"这种硬约束通常在第三次摘要里就消失了。

核心矛盾是：记忆要足够结构化才能精准注入，又要足够轻量才能长期维护。

## 做法：一个最小可行记忆系统

我在自己的 OpenClaw 插件里跑了一版，五步：

**1. 分层。** 会话内工作记忆（对话本身）、偏好记忆（结构化事实）、情景记忆（按需摘要）分开存，重点做偏好记忆。

**2. 抽取。** 会话结束后跑一个独立的抽取 pass，用小模型从对话中提取候选偏好，强制输出 JSON：`key`（如 `build_tool`）、`value`、`confidence`（0~1）、`evidence`（原对话中的支撑引用）、`created_at`。evidence 是硬性约束：抽取模型编造时无引用可填，直接丢弃。

**3. 存储。** 别急着上向量库。SQLite 一张表就够：id、category、content、confidence、hit_count、last_hit、updated_at。几百条以内的量级，category + 关键词匹配完全够用。

**4. 注入。** 每次会话启动时检索：按相关性 × confidence × 近期命中加权排序，取 top-K（我限在 400 token 内）注入 system prompt。稳定偏好（口味、代码风格）放最前，易变项（当前在赶的项目）靠后。

**5. 更新。** 新信息与旧记忆冲突时不直接覆盖——标记 conflict，下次命中时向用户确认："你之前说构建用 pnpm，现在要改吗？"重要偏好变更必须留版本记录。

## 踩坑点

- **记忆只增不减。** 前两周没做清理，注入成本翻倍。后来加 confidence 衰减：未命中的记忆每月降权，低于阈值移入冷存档而非删除。
- **一次提及 ≠ 长期偏好。** 用户随口说在学 Rust，Agent 之后每次都推 Rust 资料，很烦。对策：confidence 起始值压低，需多次独立提及或用户显式确认才升级为稳定偏好。
- **抽取幻觉。** 不校验 evidence 时出现过"用户喜欢深度学习风格回复"这种凭空记忆，加引用校验后基本消失。
- **注入顺序影响遵守率。** 同一批记忆，代码风格类放尾部时遵守率明显下降。LLM 对 prompt 首尾的注意力不是玄学。

## 可复用建议

- 用 MCP 把 `memory_read` / `memory_write` 暴露成工具，让模型自行决定何时查询；但写入路径必须过 evidence 校验，模型不能自由写。
- 记忆保持人类可读可编辑（SQLite + 导出 JSON）。用户能手动删记忆，比任何"遗忘算法"都实在。
- 写一组评测用例：会话 1 埋偏好，会话 2 验证遵守情况。没有这组用例，调注入策略全靠感觉。

## 总结

记忆系统本质是数据工程问题，不是模型问题：结构化 schema、生命周期管理、冲突确认、可评测，四件事做扎实，比换更强的模型有效得多。先从一张 SQLite 表加一个抽取 pass 开始，跑两周收集坏案例，再决定要不要上向量检索。
