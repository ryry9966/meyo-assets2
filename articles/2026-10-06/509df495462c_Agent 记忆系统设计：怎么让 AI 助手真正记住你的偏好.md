## 背景

LLM 本身无状态，每次会话都从零开始。对 OpenClaw 这类常驻 Agent 来说，这尤其难受：你上周刚说过"项目统一用 pnpm"、"回复尽量短"，这周它又问一遍。记忆系统是 Agent 从"工具"变成"助手"的分水岭，但大多数实现停在"往一个 markdown 文件里追加内容"，用两天就废了。

## 问题

两种典型的失败做法：

1. **全量塞上下文**：把历史对话一股脑注入，token 成本爆炸，关键偏好被噪声淹没。
2. **单文件 append-only 记忆**：越写越长，旧偏好和新偏好打架，读取靠模型"通读全文"，召回全凭运气。

核心矛盾其实很清楚：**写入太随意导致记忆膨胀，读取太粗放导致无效注入**。记忆系统本质是三个工程问题——写入策略、检索策略、生命周期管理。

## 做法

推荐分层设计，四层各司其职：

- **会话记忆**：当前 context，不落盘，交给框架。
- **偏好档案（Profile）**：结构化 KV，例如 `{ "package_manager": "pnpm", "reply_style": "concise" }`，每条带 `updated_at` 和来源。每轮注入 system prompt，量小且稳定。
- **情景记忆（Episodic）**：向量化存历史决策和事件，按需检索 top-k，只在相关时注入。
- **工作记忆**：跨会话的进行中任务状态，会话结束后归档或清除。

写入路径建议：

1. 显式信号优先。用户说"以后都用 xx"，直接写 Profile，不走抽取。
2. 会话结束前用小模型跑一次抽取，产出候选记忆，带置信度，低置信度丢弃或标记待确认。
3. 去重合并：新记忆与现有条目做相似度比对，相似就覆盖而不是追加。

工程上用 MCP 暴露三个工具：`memory_write`、`memory_search`、`memory_forget`——别忘了给 Agent 遗忘的能力，这比记忆本身更重要。

## 踩坑点

- **什么都记**：抽取模型会把临时状态、一次性事实都写成"偏好"。在抽取 prompt 里限定只抽稳定偏好，并设字段白名单。
- **旧偏好不失效**：用户三个月前喜欢详细解释，现在嫌啰嗦。覆盖时保留旧版本（版本号 + changelog），别直接删，否则出问题没法回溯。
- **注入过多**：每轮塞 20 条记忆反而稀释主指令。Profile 控制在一屏内，情景记忆只取 top 3 且过相关性阈值。
- **抽取幻觉**：模型会"总结"出用户根本没说过的偏好。前几百条抽样人工 review，调稳抽取 prompt 再放开。
- **隐私泄漏**：密钥、密码、手机号必须在写入前用正则/规则拦截，这一层不要指望模型自觉。

## 可复用建议

1. **先做结构化 Profile，别急着上向量库。** 90% 的"记住偏好"需求，几十个字段就能覆盖。向量检索留给长尾的情景回忆。
2. **读写分开评估**：写入看抽取准确率，读取看命中率（该想起时想没想起）。没有指标就没有优化方向。
3. 给记忆加 `last_used` 和 TTL，定期归档冷数据，防止档案无限膨胀。
4. 所有记忆操作走工具调用并留审计日志，出问题能回放是排障的底线。

## 总结

记忆系统不是"存得越多越好"，而是**克制地写入、精准地读取、体面地遗忘**。先用结构化档案解决 80% 的问题，向量检索补充长尾，版本化和遗忘机制决定它能不能长期用。把记忆当成一个带生命周期的小型数据系统来设计，而不是一个越写越长的文本文件——这是这半年我踩完坑后最确定的一条结论。
