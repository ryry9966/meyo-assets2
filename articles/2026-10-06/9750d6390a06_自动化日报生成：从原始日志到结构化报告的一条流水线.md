## 背景

团队每天要发日报：昨天上线了什么、CI 挂了几次、有哪些报错、待办推进到哪。以前的做法是有人打开若干个面板，复制粘贴，再凭记忆补两句话。问题不在于写，而在于"凑材料"——材料散在 git、CI、日志系统和工单里，人肉汇总既慢又不稳定。

这篇帖子记录我用 OpenClaw 把这件事自动化的完整流水线：定时触发一个 Agent 任务，从原始日志出发，产出一封结构化日报。思路不复杂，但有几个坑值得提前说。

## 问题拆解

直接把"帮我写日报"丢给模型行不通，核心矛盾有三个：

1. 原始日志又多又噪，上下文装不下，装下了也容易被噪声带偏；
2. 模型擅长归纳但不擅长算数，关键数字（错误次数、提交数）不能靠它现场数；
3. 流水线一旦定时跑，失败往往是静默的——没人发现"今天没日报"，直到第三天。

## 做法：五步流水线

**1. 采集层：shell 脚本先行。** 几个独立脚本分别拉数据：`git log --since` 拿提交记录、CI API 拿昨日构建结果、日志系统按 error 级别导出近 24h 聚合片段。每个脚本输出一份 JSON，落到固定目录。

**2. 预处理：先过滤再进模型。** 这一步纯脚本、不经过模型：按错误指纹去重、丢 DEBUG 级别、把高频重复报错折叠成"出现 N 次"的计数条目。原则是：模型只看摘要，不看原始流。

**3. 数字由脚本算好。** 错误总数、构建成功率、新增提交数等硬指标，全部由脚本统计后以字段形式塞进输入 JSON。模型的任务是解读，不是计算。

**4. Agent 生成与校验。** OpenClaw 定时触发，读取预处理后的 JSON，按提示词输出固定 schema 的结构（分节 + 关键条目 + 一句话总结）。schema 校验失败就重试一次，仍失败走兜底模板。最后由渲染器（模板引擎或一个简单的 MCP 工具）把 JSON 渲染成 Markdown，推送群 webhook。

**5. 调度与心跳。** cron 触发整条流水线；另设一个心跳检查：当天 09:30 还没看到产物文件，就给个人发告警，而不是等群里有人问。

## 踩坑点

- **时区与数据窗口**：第一版用 UTC 的"昨天"切数据，早上生成的日报少了晚间一段。改成显式传起止时间戳，采集和 Agent 输入共用同一份时间参数。
- **模型改写数字**：早期提示词让模型"整理数据"，它偶尔把 147 条报错写成"约 150 条"。解决：提示词明确"数字字段原样引用，禁止四舍五入"，并加校验比对输入输出中的数值字段。
- **重试导致格式漂移**：重试时模型换了一种 JSON 结构。把 schema 和 few-shot 例子放进版本库、每次重试带同一份后，问题基本消失。
- **静默失败**：某天日志系统 token 过期，采集脚本输出空 JSON，Agent 老老实实生成了一份"今日无事发生"。教训：每个采集脚本要输出采集状态，空数据 ≠ 无事故。

## 可复用建议

- 采集、计算、生成三层解耦，任何一层坏了都能单独重跑；
- schema 和提示词进版本库，改模板走 review；
- 保留当日输入快照，出问题时能回放"模型当时看到了什么"；
- 日报每节标注数据来源和统计窗口，方便读者自查。

## 总结

这套东西每天省下的时间有限（十几分钟），真正的收益是稳定：格式不漂、数字可信、没人需要记得"今天该发日报了"。自动化日报的价值不在文笔，而在把"凑材料"变成确定性的工程问题。建议先跑通最小闭环——一个数据源、一个模板、一个心跳告警——再逐步加数据源。
