## 背景

OpenClaw agent 跑久了会积累大量记忆条目：用户偏好、项目约定、踩过的坑、临时拍板的决定。`memory_recall` 的职责是在每次对话前，把这些"该想起来的"捞出来注入上下文。捞得准，agent 表现稳定；捞不准，轻则答非所问，重则用三个月前的旧配置覆盖你昨天的决定。

社区里最常见的争论就是：召回该用语义搜索还是全文搜索？我把自己那条链路改了三版，跑了组对比，结论如下。

## 问题：两类查询，两种命门

先看失败案例，比讲理论更直接：

**全文搜索输的地方**：用户问"部署老是挂怎么办"，记忆里存的是"服务不稳定，频繁 OOM 重启"。字面零重叠，关键词检索一条都召不回。

**语义搜索输的地方**：用户问"ECONNREFUSED 那个问题后来怎么解决的"，记忆里明明有这条，但 embedding 模型对错误码和日常句子的相似度排序并不可靠——它排第七，top-5 里全是"差不多的排障经历"。

结论前置：identifier 类查询（错误码、路径、版本号、人名）全文稳赢；意图改写类查询语义稳赢。这不是取舍题，是组合题。

## 做法：双路召回 + RRF 融合

我的最终结构，全部 SQLite 就够：

1. **存储层**：memories 表存原文、时间戳、来源标签；FTS5 虚拟表做全文索引；embedding 列存 512 维向量（本地 bge-small-zh，不走 API）。
2. **双路召回**：查询同时走 FTS5（LIMIT 20）和向量余弦（LIMIT 20）。
3. **RRF 融合**：score = Σ 1/(60 + rank)，两路排名直接融合，免去调权重的玄学，取 top-8。
4. **后处理**：按时间衰减（半衰期 30 天）微调，同主题去重，按 token 预算截断注入。

核心逻辑三十来行，向量检索用 sqlite-vec 一个扩展即可。一万条以内的记忆量级，上独立向量库纯属杀鸡用牛刀。

## 踩坑点

- **FTS5 默认 unicode61 分词器对中文基本无效**，整句会变成一个 token。要么换 trigram，要么接 jieba 分词后入库。这是中文场景最容易翻车的地方。
- **换 embedding 模型等于全量重建索引**。查询和入库必须用同版本模型，我把模型名写进了表元数据。
- **语义召回的假阳性很隐蔽**：相似度 0.85 的"相关"记忆可能只是主题相近，注入了也是浪费上下文 token。要设相似度下限，别盲目 top-k。
- **记忆条目要原子化**。一条记忆塞五个事实，embedding 就是一锅粥，召回精度直接崩。

## 可复用建议

- 冷启动别急着上向量：FTS5 + 时间衰减 + 手写同义词表，能覆盖七成场景，先跑通闭环。
- 用真实会话攒一个 50 条的评测集（query → 期望命中的记忆 id），每次改召回逻辑都回归一遍。凭感觉调参必翻车。
- 记录每次召回的命中/未命中日志，跑一周你就知道瓶颈在哪一路。
- 旧记忆要有失效机制，避免陈年配置覆盖新决定。

## 总结

"语义 vs 全文"是个伪命题。真实答案是：**全文保底**（精确匹配零失误），**语义补盲**（改写与意图），RRF 融合 + 时间衰减兜底。先建评测集再动手，否则你只是把一种玄学换成了另一种玄学。
