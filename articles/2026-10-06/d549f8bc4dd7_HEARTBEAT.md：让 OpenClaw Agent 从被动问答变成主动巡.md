## 背景

大多数人对 Agent 的用法是问答式：你提需求，它执行，然后沉默地等你下一次开口。OpenClaw 的心跳机制改变了这个模型：网关进程按固定间隔（默认 30 分钟）给 agent 注入一条内部提示，agent 醒来后读取工作区里的 `HEARTBEAT.md`，判断有没有要做的事——有，就执行并把结果发到你的聊天渠道；没有，就输出约定的静默标记 `HEARTBEAT_OK`，你什么都收不到。

换句话说，HEARTBEAT.md 就是你写给 agent 的一份值班巡检清单。

## 问题

把定时类需求全推给 cron 插件，会撞上两类它做不了的事：

1. **条件触发**。"如果应用日志有新报错就摘给我"——cron 只能定时执行，"要不要打断我"这个判断需要 LLM 结合上下文来下。
2. **综合多个数据源**。"看完今天的日历和昨天的笔记，有冲突就提醒我"。先读状态、再决定要不要开口，这正是 heartbeat 擅长的形态。

而人肉驱动的问题更直接：你想不起来问，agent 也不会自己想起来说。

## 做法

**1. 写清单。** 在工作区（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`，每行一个任务，尽量写成"条件 + 动作 + 频率"：

```markdown
# Heartbeat Checklist

- 若 ~/logs/app.err 在上次心跳后有新增：摘录最后 10 行发我，并在下方登记已处理位置
- 每天 9 点后的第一次心跳：读日历，30 分钟内开始的会议提醒我
- 周五 15 点后：汇总 memory/ 里的待办发我
- 其余情况：一律 HEARTBEAT_OK，不要汇报"无事发生"
```

**2. 调频率。** 在 `~/.openclaw/openclaw.json` 里改默认间隔；夜间不想被打扰，设置活跃时段或直接在清单里写免打扰窗口：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "45m" }
    }
  }
}
```

**3. 控成本。** 心跳的判断环节用不到最强模型，指向一个便宜快速的即可，额度留给正经对话。投递渠道用 target 指定，别让它向所有渠道广播。

**4. 跑一周。** 跟着网关日志看每次心跳的实际输出，统计多少次是 HEARTBEAT_OK、多少次真的打扰了你，再回头修清单。

## 踩坑点

- **清单写太长**。每次心跳都会读一遍，行数多既费 token 又提高模型跑偏的概率。控制在 5 条以内，复杂逻辑写成脚本让 agent 去调用。
- **条件不可判定**。"帮我盯着服务器"会换来每 45 分钟一次的"我看了一下，没问题"。要写成明确的判定条件和触发动作。
- **忘了写沉默规则**。不显式写"无事不报"，部分模型会每次都礼貌汇报，频道直接被刷屏。清单第一行就应该是静默规则。
- **重复报警**。日志没清理，同一件事心跳每次都会报。给任务设计"确认动作"：处理完让 agent 在 memory 里记一笔，或在清单上打钩——清单不是只读的，让 agent 自己维护是最省事的防重复手段。
- **把它当监控系统**。心跳本质是轮询，网关没跑、机器睡眠就漏拍，且不会补发。秒级告警请走真正的监控加 webhook，心跳只做低频巡检。

## 可复用建议

- 分层：固定时间的用 cron 插件，条件判断的用 HEARTBEAT.md，高时效的用事件/webhook。三者各管一段，别混用。
- 按 SRE 巡检手册的写法来写清单：条件、动作、频率、豁免规则，四要素齐全。
- 从两三个任务起步，观察一周再决定是否扩。心跳的价值密度取决于你砍掉了多少伪需求。

## 总结

HEARTBEAT.md 的价值不是"自动化一切"，而是给 agent 一个固定节拍的自查机制：到点醒一次，扫一眼清单，有事说事，没事闭嘴。写好这份清单，本质上是在给一个 LLM 员工写 on-call 手册——条件写得越明确，它越像同事；写得越模糊，它就越像个频繁转发垃圾消息的群友。
