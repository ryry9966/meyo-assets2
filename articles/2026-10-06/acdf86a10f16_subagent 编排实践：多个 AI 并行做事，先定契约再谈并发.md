## 背景

用 OpenClaw 跑了一段时间单 Agent 之后，很自然会遇到天花板：让主 Agent 一次性完成“调研三个技术方案 + 各写一份对比笔记 + 跑一轮验证”这类任务，通常表现为三种症状——中间产物把上下文撑爆、任务串行排队导致整体耗时不可接受、一次工具调用失败就把整条链路卡死。这时候就该考虑 subagent 编排了。

## 问题

拆开看是三个独立的工程问题：

1. **上下文污染**。调研类任务的中间输出（网页摘要、日志、临时结论）大量挤占上下文，关键约束反而被截断，后续步骤质量明显下降。
2. **串行瓶颈**。三个方案的调研彼此独立，但单 Agent 只能顺序执行，延迟直接叠加。
3. **无隔离**。试验性改动直接落在主工作区，失败一次就要手工回滚。

## 做法

我的编排思路是：**主 Agent 只做拆解、派发、验收，不做具体活**。落地分五步：

1. **任务拆解**。只拆“彼此独立、结果可验证”的子任务。判断标准很简单：如果子任务 A 的输入依赖 B 的输出，就别硬拆成并行，老老实实串行。
2. **收窄上下文**。每个 subagent 只拿到三样东西：任务描述、相关文件路径、输出格式要求。不传主 Agent 的历史对话，上下文越窄越稳。
3. **工作区隔离**。涉及改代码的子任务，用独立 worktree 或子目录跑，验收通过后再合并；调研类子任务只读不写。
4. **并发控制**。同时最多 3 个 subagent，其余进队列。并发数不是越大越好，原因见下面的坑。
5. **统一结果契约**。subagent 返回固定结构的 JSON：`status`、结论摘要、变更文件列表。主 Agent 验收后再决定合并或重试。

## 踩坑点

- **多 subagent 改同一个文件**。最常见的事故。解法是派发前明确文件归属，一个文件只允许一个 subagent 碰。
- **subagent 静默失败**。跑完了，返回“已完成”，实际上什么都没做成。结果契约里的 `status` 字段缺失即视为失败，不做善意解读。
- **成本乘数**。并发 4 路等于 token 消耗 ×4，失败的子任务重试还要再烧一遍。给每个 subagent 设最大轮次上限，超限即终止。
- **拆得过细**。有次把一个任务拆成 8 个子任务，编排开销超过了实际工作量。经验值：单个 subagent 的工作量至少要覆盖十几轮工具调用，才值得拆出去。
- **工具权限没有收口**。subagent 默认继承全部工具，一次试验性调用动了共享目录。现在派发时显式声明工具白名单，白名单外一律拒绝。

## 可复用建议

- 拆解三问：能否独立完成？是否幂等？结果能否独立验证？三个都是“是”才并行。
- 编排者不干活。主 Agent 一旦开始亲自执行子任务，编排逻辑就散了。
- 结果契约先行。先定返回结构，再写任务描述，顺序不能反。
- 限流、超时、轮次上限，三件套缺一不可。
- 重试在 subagent 层做，不要整链重跑——整链重跑等于为一次局部失败支付全局成本。

## 总结

subagent 编排不是“多开几个 AI 就更快”，本质是用隔离换质量、用并行换延迟、用结构化契约换可靠性。先把拆解标准和结果契约定好，再谈并发——这条顺序反过来，基本都会翻车。欢迎大家分享自己的并发数上限和契约字段设计，这部分目前还没有公认的最优解。
