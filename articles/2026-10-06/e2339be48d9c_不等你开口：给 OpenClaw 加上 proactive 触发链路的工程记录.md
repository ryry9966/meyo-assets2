## 背景

大多数 AI 助手的工作模式是被动应答：用户发消息 → 模型回复 → 结束。这种模式下，助手的价值上限取决于你提问的频率。而真正省事的场景往往相反——CI 挂了、仓库有新 release、证书快过期，这些事你不想主动去查，希望助手"值班"时自己发现、自己汇报，甚至自己处理。

OpenClaw 常驻运行、自带 cron 和多通道消息能力，做 proactive 有天然条件。最近我把家里的实例从"问答机"改成了"值班员"，记录一下过程。

## 问题

把被动改成主动，核心难点不是"定时跑个任务"，而是三个工程问题：

1. **触发源从哪来**：cron 只是其中一种，更有价值的事件往往来自外部系统（webhook、监控告警、git push）。
2. **要不要打扰用户**：不是所有事件都值得推送，判断错了就是通知轰炸。
3. **别做重复功**：同一个告警连续触发十次，不能推送十遍。

## 做法

我的链路分三层：

**第一层：触发源。** 低频巡检用 OpenClaw 自带 cron（每 30 分钟查一次 GitHub releases 和证书有效期）；高频事件走 webhook，比如 CI 失败回调直接打到本地一个轻量 HTTP 入口，转成消息交给 agent 处理。

**第二层：决策闸门。** 这是关键。agent 收到事件后不直接推送，而是先过明确的规则：事件是否满足"用户定义的值得知道"的条件？我把它落成一份白名单配置（哪些 repo、哪些指标、什么阈值）。规则外的默认静默，只记日志。

**第三层：状态去重。** 维护一个小 JSON 状态文件，记录"上次已经报告过什么"。推送前 diff 一下，内容没变化就不发。这个文件同时充当短期记忆，避免每次触发都重新拉全量上下文。

需要执行动作的场景（比如自动重启某个服务）单独走"确认制"：agent 只产出建议和命令，发消息等用户回复一个关键词才真正执行。

## 踩坑点

- **循环触发**：早期让 agent 处理事件后写文件，结果文件变更又触发了监控事件，进入自激循环。解法是给事件源打标，agent 自己产生的变更不进触发队列。
- **规则被模型"自由发挥"**：把推送标准写在系统提示里，模型偶尔会同情心泛滥（"这个看起来也挺重要的"）。后来把阈值判断改成代码层硬编码，模型只负责描述发生了什么，不负责判断要不要发。
- **cron 时区**：默认 UTC，静默时段全错位。显式指定时区，并在安静时段把非紧急事件攒起来合并成一条日报。
- **上下文污染**：proactive 拉回的信息如果全写进长期记忆，几次之后记忆里全是噪音。现在巡检结果默认不落记忆，只有用户交互过的才写入。

## 可复用建议

1. 先做只读 proactive（监控 + 汇报），跑稳两周再放开任何写操作。
2. "要不要打扰"的判断放代码/配置，不要放模型——模型擅长描述，不擅长克制。
3. 所有 proactive 触发留日志，出问题能回放。
4. 状态文件 + diff 推送，是成本最低的通知降噪手段。
5. 静默时段 + 合并日报，能把推送量砍掉八成而不丢关键信息。

## 总结

Proactive 的本质不是让模型更聪明，而是给它加一套值班制度：明确的触发源、代码层做闸门、状态做去重、写操作要确认。做到这四点，助手才算从"你问它答"变成"它守着你不用问"。目前我的实例日均主动推送 2–3 条，误报率可控，这套结构可以直接复用到类似的常驻 agent 场景。
