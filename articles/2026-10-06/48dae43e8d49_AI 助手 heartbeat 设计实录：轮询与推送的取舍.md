## 背景

OpenClaw 这类跑在自己设备上的常驻 agent，绕不开一个问题：它怎么“自己醒来”？内置答案是 heartbeat——按固定间隔唤醒，读 workspace 里的 HEARTBEAT.md，判断有没有值得说的事；没事就回一个约定标记，静默收场。用了一段时间后自然有人问：很多系统都能发 webhook，为什么不干脆全改成推送？

## 问题：两条路各差在哪

核心差异在延迟、成本、可达性三个维度：

- **轮询（heartbeat）**：实现极简，不需要公网入口，NAT 后的家庭机器照跑；间隔可控、成本可预算。代价是延迟下限就是间隔本身，且每次唤醒有固定 token 开销——哪怕最后只是确认无事发生。
- **推送（webhook/事件）**：事件驱动，没事件零开销，延迟毫秒级。代价是入站可达（公网端点或隧道）、签名校验、重试幂等，一样都不能少；事件密集时还可能反过来把模型轰醒。

单独看哪条都不完整：纯轮询在“重要事件需秒级响应”的场景失效；纯推送则把所有鸡蛋放进一个必须暴露在公网的篮子里。

## 做法：heartbeat 做主干，推送做放大器

1. **调间隔**。openclaw.json 里 agents.defaults.heartbeat.every 从默认 30m 出发按使用密度调，非活跃时段可不跑。
2. **收紧 HEARTBEAT.md**。它是每个 tick 都要读的清单，控制在 5–8 行，只放“现在能检查、现在能行动”的条目。
3. **定义静默路径**。无话可说时输出约定的 OK 标记、不投递通知；只有真正需要人处理的事项才走主动消息通道。
4. **外部事件走推送**。对能提供 webhook 的系统（代码仓库、监控、表单），起一个几十行的接收脚本：验签 → 写入 workspace 的事件队列文件或直接投递。
5. **推不了的全交给巡检**。本地文件变化、日历导出、磁盘水位这类没有推送源的东西，放进 HEARTBEAT.md，靠轮询兜底。
6. **留观测**。每个 beat 记录耗时和 token 消耗，跑一周再回头定间隔，比拍脑袋准。

## 踩坑记录

- **间隔压太短**：token 按天烧，更糟的是模型容易“为了响应而响应”，制造噪音通知。从 30 分钟起步，往长了调。
- **清单膨胀**：HEARTBEAT.md 从 5 行长到 50 行，单次 tick 成本线性上涨，过期条目当垃圾清。
- **接收脚本不验签**：任何人 POST 一段话就等于向 agent 注入指令，HMAC 校验和来源白名单是底线。
- **推送风暴**：事件触发 agent 动作，动作又触发新事件。队列里加去重键和冷却窗口。
- **设备休眠**：笔记本合盖后定时器不保证触发，唤醒后应主动补一次检查。
- **队列并发写**：多来源写同一文件，追加式 + 单消费者最省心，别急着上锁。

## 可复用建议

- **默认选轮询**。除非有明确低延迟需求，或事件源天然只能推——尤其 agent 跑在 NAT 后面时，轮询是更安全的选择。
- **用预算反推间隔**。先定“heartbeat 每天最多花多少 token”，除以单次成本，就是 interval 上限。
- **每个 beat 幂等且有界**。限制单次 tick 的工具调用次数，防止一次巡检变成算力事故。
- **检测与通知分离**。先落盘、再判断要不要打断人；通知的克制程度决定用户会不会关掉你。
- **推送入口按不可信输入处理**，防护等级对齐 MCP 工具。

## 总结

heartbeat 是调度骨架，推送是事件放大器，二者不冲突：轮询给你确定性、安全边界和可预算的成本，推送给你低延迟和零空转。在 OpenClaw 上，把 HEARTBEAT.md 压到最小，把能推的来源接到验签后的 webhook，剩下的交给时间——跑一周看数据再调参，比任何预设都可靠。
