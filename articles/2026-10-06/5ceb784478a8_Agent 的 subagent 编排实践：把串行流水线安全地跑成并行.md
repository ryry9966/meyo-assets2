## 背景

过去几个月我们在 OpenClaw 上跑的自动化任务，大多是单 agent 串行链路：读需求 → 查代码 → 改文件 → 跑测试 → 写报告。一条链跑下来四十多分钟，中途上下文一旦被中间结果撑满，后半段质量明显滑坡。后来我们把链路改造成 subagent 编排：主 agent 只负责拆解、派发和汇总，实际执行交给多个独立上下文的子 agent 并行跑。同样的流水线，稳定在 12 分钟左右。

## 问题：什么时候值得拆

实践中判断标准很简单，满足两条以上才拆：

- 子任务之间没有共享的可变状态（比如各自审查不同模块）；
- 单个子任务 5~15 分钟能做完，输入输出都能序列化成 JSON；
- 主会话上下文已被中间产物占满，开始遗忘早期约束。

反例也常见：任务强依赖前序结果（改完 A 才知道 B 怎么改），硬拆并行只会返工。

## 做法：五步

1. **拆任务**。主 agent 先产出任务清单，每项包含独立工作目录、明确输入和期望输出。
2. **配子 agent**。每个 subagent 一个角色 prompt + MCP 工具白名单，只挂它需要的工具，权限收窄。
3. **约定返回格式**。统一 schema，例如：

```json
{ "status": "ok | failed", "summary": "...", "artifacts": ["path"], "errors": [] }
```

4. **控并发**。上限设 3~5，配单任务超时（10 分钟）和一次重试，超出走降级队列。
5. **汇总**。主 agent 只做合并、冲突标记和抽查，不重做子任务。发现 `status` 非 ok 的，单独补跑而不是整批重来。

## 踩坑点

- **并发一高就撞限流**。四个子 agent 同时调同一模型，token 消耗翻四倍，还触发 429。加令牌桶限流后才稳定。
- **子 agent 失败但不报错**。早期它会把失败包装成一段"看起来合理"的总结，主 agent 照单全收。强制 schema 校验 + 显式 status 字段后才堵住。
- **工作区冲突**。两个子 agent 同时改同一文件，后写覆盖先写。现在每个子 agent 独立工作目录，合并阶段统一处理冲突。
- **上下文传递不足**。子 agent 缺背景就跑偏。解法是派发时带"最小必要上下文"——相关文件路径、约束清单，而不是整个会话历史。
- **主 agent 手痒**。它经常想自己下场改两行代码，破坏并行结构。角色 prompt 里明确写"你只编排，不执行"。

## 可复用建议

- 把高频子 agent（代码审查、测试、文档）沉淀成模板插件：角色 prompt、工具白名单、输出 schema 三件套，新流水线直接复用。
- 放量前先跑一个 pilot 子 agent，验证 prompt 和 schema 后再并行铺开。
- 子任务设计成幂等可重跑，重试和补跑才安全。
- 记录编排 trace：每个子 agent 的耗时、token、失败率。并发数不该拍脑袋定，应该看数据调。

## 总结

Subagent 并行不是加个循环就完事，拆分粒度、结构化返回和失败处理才是成败关键。我们的经验是：先串行验证流程正确，再并行提效；主 agent 严守编排者角色，把执行和判断下沉到子 agent。跑稳之后，这套模式基本可以套到大部分多阶段自动化任务上。
