## 背景

用 OpenClaw 做内容自动化后，常见形态变成"Agent 产出 Markdown，人只负责审校"。但写完只是开始：公众号、知乎、掘金、GitHub 各自的渲染器对 Markdown 的支持差异很大，同一份稿子在不同平台需要不同处理。与其每次手工调，不如把它做成管线。

## 问题

几个典型的坑源：

- **Markdown 有方言**：脚注、任务列表、数学公式、表格对齐，很多平台的渲染器要么不支持，要么行为不一致。
- **平台限制**：公众号编辑器会剥掉大部分 HTML 和外部样式；掘金/知乎对代码块语言标记的处理各不相同。
- **图片**：外链防盗链、临时链接失效、粘贴时被转成 base64 导致体积爆炸。
- **Agent 输出不稳定**：同样的任务可能产出嵌套列表混着 HTML 的"脏"结构，直接投递必碎。

## 做法

核心思路是**单一事实源 + 分层转换**，管线分四层：

1. **归一化层**。AI 输出先过规范器：统一换行、剥离幻觉出来的 HTML 标签、按配置决定任务列表是降级还是保留。改写建议走 AST（比如 mdast）而不是正则——正则在嵌套结构上必翻车。这层产出"规范 Markdown"，作为唯一上游。
2. **适配层**。每个目标平台一个 adapter，只做一件事：把规范 Markdown 转成该平台可接受的形态。公众号走 HTML 中转加内联样式；掘金/知乎主要处理代码块标记和图片下载转存。adapter 之间不共享状态。
3. **渲染校验层**。发布前用接近平台真实行为的渲染器本地渲染一遍，产出预览和差异报告。OpenClaw 的优势在这里：让 Agent 拿渲染结果自检一轮（代码块是否被吞、表格是否断行），再决定放行。
4. **发布层**。接 MCP 工具或平台 API 投递，并把规范版与各平台成品版归档。发布必须幂等，重复执行不产生重复文章。

## 踩坑点

- 别在 prompt 里让模型直接输出"平台特化格式"，那是适配层的事。模型只写标准 Markdown，职责分离后出错率明显下降。
- 图片务必落地到自己的存储，外链在公众号里十有八九裂。
- 表格是重灾区：列宽、对齐、内嵌代码三个平台三种表现，复杂表格能转图片就转图片。
- 转换要做幂等性验证：同一份规范 Markdown 跑两遍 adapter，产物应逐字节一致。
- 保留原始 AI 输出，别覆盖。溯源和回滚都靠它。

## 可复用建议

- 把 adapter 做成 OpenClaw 插件或 skill，配置里声明支持的平台和特性矩阵，新平台加一个文件即可。
- 校验规则沉淀成 checklist 文件，Agent 每次发布前跑同一套检查，不靠人记。
- 预览优先：先出预览让人确认，再自动发布，不要一步到位。

## 总结

这套管线本质上是把"格式适配"从每次手工劳动变成声明式的工程问题：AI 负责内容，管线负责形态，人只做最终审校。跑通一次之后，新增平台的边际成本就只剩一个 adapter 文件。
