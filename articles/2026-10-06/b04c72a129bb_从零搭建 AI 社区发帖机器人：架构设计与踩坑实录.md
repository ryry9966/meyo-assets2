## 背景

社区运营里最耗时间的不是写内容，而是"搬运与格式化"：每周精选、新帖摘要、活动预告，都要人工复制粘贴。我们尝试用 OpenClaw 搭一个发帖机器人，目标很克制：不追求全自动，只做"自动起草 + 人工确认 + 定时发布"，把每周约 3 小时的机械操作压到 20 分钟。

## 问题

第一版很天真：cron 触发 → LLM 生成 → 直接调发帖 API。跑了三天就暴露三个问题：重复发帖（cron 重叠触发）、内容撞车（同一话题两天内发了两次）、以及一次 JSON 格式漂移导致把原始 prompt 当正文发了出去。这让我们意识到，发帖机器人的难点不在"生成"，而在"工程化地可靠发布"。

## 做法

最终架构拆成五层，每层独立可测：

1. **采集层**：插件定时拉取社区 RSS 和站内 API，落地 SQLite，用 content hash 去重。
2. **策划层**：一个 Agent 通过 MCP 调用"查重""打分"两个工具，选出本周值得写的 3 条，输出结构化 JSON。
3. **生成层**：模板约束 + JSON Schema 校验，不通过重试一次，仍不通过则丢弃并记日志。
4. **审核层**：草稿写入队列，IM 推送卡片，人工点确认才进入发布队列。这一步是红线，前两个月从未放开。
5. **发布层**：单飞锁保证同一时刻只有一个发布任务，指数退避重试，失败落盘待人工补发。

状态全部落在 SQLite，核心是 intent log：发布前先写一条 `intended` 记录，成功后置为 `done`，重启后据此恢复，避免"生成了没发出去"或"发了但没人知道"。

## 踩坑点

- **cron 重叠**：长任务撞上短周期触发，两个实例并发执行。解法很简单——文件锁 + 任务表状态机，但第一版就是没做。
- **LLM 格式漂移**：temperature 调到 0 也不能保证 JSON 合法。Schema 校验、有限重试、丢弃告警，三件套缺一不可。
- **MCP 工具超时**：查重工具依赖外部服务，一次网络抖动卡死整条流水线。每个 MCP 调用要单独设超时和熔断，别复用全局配置。
- **幂等陷阱**：重试导致同一篇发了两次。发布动作带上 idempotency key（content hash + 目标版块），服务端拒绝重复。
- **频控风险**：起初固定整点发帖，连续几天后触发站方风控。改成随机化发布窗口 + 每日上限。

## 可复用建议

- 先跑"草稿箱模式"至少两周，观察误报率，再谈自动化。
- 假设所有对外动作会失败两次：设计 intent log 和幂等键，而不是祈祷不重试。
- 把"选什么发"和"怎么发"拆成两个模块，前者可频繁换策略，后者追求稳定。
- 每次发帖留 trace：输入摘要、模型版本、工具调用耗时，出问题能回放。

## 总结

整个项目代码不到 800 行，但 70% 的精力花在状态管理、幂等和失败路径上。经验浓缩成一句话：Agent 负责聪明，工程负责可靠，两者别混在同一层。代码结构正在整理成模板放进社区仓库，欢迎按自己的板块改造后反馈踩坑。
