## 背景

社区每周的「本周动态」（精选新帖、Release 摘要、热门讨论）一直靠手工整理，费时且容易漏。于是我用 OpenClaw 搭了一个发帖机器人：定时抓取信息源 → Agent 起草 → 规则校验 → 调社区 API 发布。跑了两个月，发布几十篇，踩了不少坑，记录如下。

## 目标与约束

- 全自动但有底线：默认只产草稿，通过校验才允许自动发布；
- 可回溯：每篇帖子能查到引用了哪些信息源；
- 不打扰社区：严格限频，失败不能重试到刷屏。

## 架构与实现步骤

整体分四层，Agent 只负责「写」，其余全是确定性代码：

1. **采集层**：cron 触发 OpenClaw 定时任务，抓取 GitHub Release、RSS、社区热帖，原始内容落 SQLite。
2. **工具层**：把社区 API 封装成 MCP server，暴露 `draft.save`、`post.publish`、`state.query` 等小粒度工具；token 只存在于 MCP server 的环境变量里，不进 prompt。
3. **Agent 层**：OpenClaw Agent 读取采集摘要，产出结构化草稿（标题、正文、引用来源 ID），写入待审队列。
4. **发布层**：独立脚本消费草稿队列，做硬校验（链接可达、长度、黑名单词、来源 ID 真实存在），通过后带幂等键调用发布工具。

关键决策：**状态全部在数据库，Agent 无状态**。每次运行只是「读上下文 → 产出 → 落库」，重跑不产生副作用。

## 踩坑实录

**坑一：Agent 编造版本号和链接。** 第一周就发出了一个不存在的 Release 链接。解法：prompt 里禁止输出任何上下文中没有的 URL 和版本号，发布层再校验来源 ID 与 URL 的对应关系，对不上直接打回。

**坑二：重试导致重复发帖。** 网络超时后脚本重试，同一篇内容发了两遍。解法：以正文 hash 为幂等键，发布前查库命中即跳过；工具侧再加「同标题 24 小时内不重复」一道保险。

**坑三：上下文膨胀。** 最初把抓到的全文塞给 Agent，token 开销翻倍，质量反而下降。改为采集层先做规则筛选和摘要，每个源只给 200 字以内的素材。

**坑四：定时任务重叠。** 上一次没跑完，下一次 cron 又触发，两条流水线同时写库。加了个文件锁解决。

**坑五：MCP 工具设计太粗。** 最初只有一个 `publish` 大工具，参数一堆，Agent 经常填错。拆成多个单一职责的小工具后错误率明显下降——工具越小，模型越不容易幻觉参数。

## 可复用建议

1. 先用 draft-only 模式跑两周，草稿质量稳定后再放开自动发布；
2. 能用确定性代码做的事（校验、限频、状态），不要交给模型；
3. MCP 工具按「动词 + 单一资源」拆分，宁可多几个小工具；
4. 所有外部写操作都带幂等键；
5. 留一个 kill switch：一个配置项能让机器人立刻退回纯草稿模式。

## 总结

这个项目里，Agent 的真正价值只在「把素材组织成可读文章」这一步，其余可靠性全部来自外围工程。OpenClaw + MCP 的组合让工具封装和调度都比较省事，但发帖机器人这类「对外写」的场景，防线必须建在模型之外。一句话总结：**让模型只做生成，让代码守住边界。**
