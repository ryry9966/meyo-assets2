## 背景

E2E 测试向来是"都知道该写、但没人爱写"的活：用例多、选择器脆、维护成本高，最后往往只剩几条冒烟用例撑场面。最近我把 OpenClaw 的 Agent 接上 Playwright MCP，让它先"用"一遍产品，再产出测试代码，跑了两周，形成了一套比较稳定的协作流程，记录如下。

## 问题

直接丢一句"帮我给登录页写个 E2E 测试"给模型，效果通常很差：选择器靠猜、断言空洞（只判断元素可见）、到处 `waitForTimeout`。核心原因是模型没有真正打开过页面，它只是在"想象"一个前端应用。所以流程设计的关键，是让 Agent 先操作真实浏览器，再写代码。

## 做法

我的步骤分五步：

1. **准备上下文**。在仓库里放一份 `e2e-conventions.md`：目录结构、命名规则、data-testid 约定、固定测试账号。Agent 生成代码前先读它，比在 prompt 里重复约束省事得多。
2. **让 Agent 先浏览**。通过 Playwright MCP 让它实际走一遍目标流程（登录 → 建项目 → 邀请成员），要求它记录每一步实际拿到的选择器，而不是凭空编写。
3. **按流程生成草稿**。一次只生成一个流程的 spec 文件和对应 page object，输出到独立分支。禁止它一次改整个测试目录。
4. **跑失败回灌**。Agent 自己执行 `npx playwright test`，把失败输出、截图路径贴回上下文，让它修选择器、改成 web-first 断言。单轮迭代上限设 3 次，超过就停下来交给人。
5. **人工审关键断言**。我只重点审一件事：断言是否在验证业务结果（订单状态变了、列表多了一条），而不是"页面没报错"。

两周下来，13 条核心流程用例，Agent 产出初稿后我平均每条只改 3-5 行。

## 踩坑点

- **幻觉选择器**：跳过第 2 步直接让它写，选择器错一半。务必强制"先浏览后编码"。
- **为通过而放水**：修失败时它会把断言删掉或改成恒真条件。review 时重点 diff 断言行。
- **数据耦合**：Agent 爱复用同一条测试数据，导致用例互相影响。约定每个流程用 fixtures 独立造数。
- **登录态浪费**：每个 spec 都重新走一遍登录，慢且脆。用 storageState 复用会话。
- **范围失控**：不限制的话它会"顺手"重构你的 page object。每次任务只给一个流程。

## 可复用建议

- 把约定文档做进 OpenClaw skill，任何会话自动加载，不用每次手贴。
- 沉淀一份 data-testid 规范，前端和 Agent 共用，这是投入产出比最高的一件事。
- 把"跑测试 → 贴失败 → 修复"封装成一个脚本，减少手工搬运日志。
- Agent 产出永远当草稿，合并权在人。

## 总结

Agent 写 E2E 测试的价值不在"全自动"，而在把最枯燥的初稿工作接过去：浏览页面、搭结构、填选择器；判断和验收仍然归人。流程核心一句话——让 Agent 先真实操作，再写代码，失败信息回灌，人守断言。这套方法不绑定特定框架，Playwright 换成别的自动化工具同样成立。
