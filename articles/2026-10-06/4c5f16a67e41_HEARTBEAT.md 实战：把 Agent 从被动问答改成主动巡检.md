## 背景

用 OpenClaw 这类常驻 agent 一段时间后，你会发现交互模式基本是"你问它答"。模型再强，你不发消息它就不动。但很多事本来不需要人发起：每天早上的日程汇总、盯着 error.log、到点提醒、定期检查磁盘和备份。传统解法是 cron + 一堆 shell 脚本，但上下文就散了，脚本是脚本，agent 是 agent，两边不认识。

heartbeat 机制就是为这个准备的：agent 每隔一段时间（默认 30 分钟，可在配置里调 `heartbeat` 的 `every` 字段）被唤醒一次。如果 workspace 根目录存在 `HEARTBEAT.md`，其内容会作为任务清单注入这次唤醒，agent 读完自行决定：要么干活，要么保持安静。

## 问题

没有这个文件，heartbeat 只是空转；有了它，agent 才从"聊天机器人"变成"值班员"。但这份文件怎么写，直接决定它是巡检系统，还是每小时骚扰你一次的噪音源。

## 做法

在 workspace 根目录创建 `HEARTBEAT.md`，把任务写成**可判定的条件句**：

```markdown
# 巡检任务

## 早报
- 若当前时间在 08:00–09:00 且 daily-log.md 里今天还没有记录：
  汇总日历今日日程和未读邮件数，发到我的私聊，并追加一行到 daily-log.md

## 错误日志
- 检查 ~/logs/app.log 是否有新增 ERROR；若有，摘要不超过 3 条发我
- 无异常则回复 NO_REPLY（保持安静）
```

三个要点：

1. **触发条件要可判定**："有没有 ERROR"、"时间是否在窗口内"、"今天是否已做过"，让 agent 每次都有明确的 yes/no 可走。
2. **静默默认**：明确写出"无任务命中时回复 NO_REPLY"。heartbeat 的设计里 agent 可以用 NO_REPLY 结束本次唤醒且不打扰你，这是控制噪音的核心约定。
3. **挂接已有能力**：任务里可以直接引用 agent 的工具和 MCP 服务——查邮箱、调 API、跑 shell 都行，心跳只是一个触发入口，不限制执行方式。

## 踩坑点

- **频率即成本**。每次心跳都是一次完整的模型调用。非关键任务从 1 小时起步，别一上来就 5 分钟。
- **模糊指令必翻车**。"帮我盯着服务器"这种写法，agent 会每隔半小时汇报一次"一切正常"。必须写成"有 X 才做 Y，否则 NO_REPLY"。
- **文件膨胀**。HEARTBEAT.md 每次心跳都会注入，别把大段背景资料堆进去。背景放 SKILL 或 memory，这里只放触发条件和动作。
- **别让模型猜时间**。时区和"今天"的判断让它先跑一下 `date` 再决策，否则早报可能下午三点发。
- **高风险动作要设门槛**。给"发消息给其他人"、"git push"这类动作写上确认条件，或限定为"先报告，等回复再执行"。

## 可复用建议

- 像维护 crontab 一样定期 review 这份文件：删掉不再需要的任务，合并重复的检查项。
- 复杂任务遵循"心跳只做检测与触发，重活进正式会话"的分层，避免心跳被长时间执行阻塞。
- 让每次执行都留痕（追加日志文件），出问题时能回溯它到底在心跳里干了什么。
- 把常用巡检段落做成模板，新项目复制改路径即可，几分钟就能上线一套轻量监控。

## 总结

HEARTBEAT.md 的价值不在花哨，而在于它把 agent 的触发权从"人来问"改成"条件满足就动"。写清触发条件、默认静默、控制频率和体量，它就是一个不需要额外基础设施的常驻巡检系统。先从一件小事跑起来，比如每天一封早报，再逐步加任务，比一次写十个检查项靠谱得多。
