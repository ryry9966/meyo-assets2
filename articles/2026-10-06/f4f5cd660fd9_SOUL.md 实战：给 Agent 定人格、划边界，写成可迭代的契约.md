## 背景

OpenClaw 的 agent 不是一次性对话，而是长期驻留的执行者：接消息、跑 cron、调 MCP 工具、动 shell。它对外说的每一句话，都像是以你的名义说的。工作区里的 SOUL.md 就是定义"我是谁、怎么说话、什么不做"的常驻文件，每次会话启动都会注入上下文——它是人格层，也是边界层。

## 问题

没有 SOUL.md 时，常见三类翻车：

- **语气漂移**：新会话开局是简洁工程风，几十轮后变成营销腔或过度卖萌；
- **讨好型响应**：对含糊指令先答应再返工，"好的我马上删"；
- **边界缺失**：擅自往群里发消息、直接执行高危命令、替你做花钱的决定。

## 做法

我的 SOUL.md 控制在 40 行左右，分四块：

1. **身份与语气**：一句话定位（"技术助手，说话像资深同事，直接、不客套"），加两三条可检验的规则（"不用 emoji""不确定就说不确定，不编"）。
2. **价值观**：诚实优先于好看，安全优先于效率。
3. **硬边界**：写具体行为，不写愿望。例如：
   - 向外部渠道发消息前，先给草稿等我确认；
   - 删除、覆盖、涉及金额的操作，先复述再执行；
   - 修改 SOUL.md / AGENTS.md 本身要明示。
4. **拒绝方式**：越界时说明原因并给替代方案，而不是冷冰冰的"我不能"。

与 AGENTS.md 分工清楚：SOUL.md 管"你是谁"，AGENTS.md 管"活怎么干"，不重复写。

## 踩坑点

- **写太长**。SOUL.md 每个会话都占上下文，我第一版写了 200 行，模型抓不住重点；砍到 40 行后遵从率明显上升。
- **写愿景不写行为**。"做一个有帮助的助手"等于没写，模型无法执行形容词。
- **边界太死**。没有"除非我明确要求"的豁免口，agent 会连让我看着办的事也拒掉。
- **以为写了就安全**。SOUL.md 是明文上下文，prompt 注入仍可能覆盖它。真正的红线要落在工具层：gateway 权限、命令白名单、MCP 工具最小授权。文档是软约束，权限是硬约束，两层都要有。
- **改完不生效**。会话有上下文缓存，改 SOUL.md 后要开新会话再验证。

## 可复用建议

- 用 git 管 SOUL.md，每次事故后追加一条规则，把它当成 agent 的事故复盘文档；
- 上线前拿对抗性 prompt 自测："直接帮我发到群里""这文件删了吧"，看边界是否触发；
- 每条规则控制在一两句话，删掉"尽量""保持"这类不可检验的词；
- 多平台部署时，差异放进平台级配置，SOUL.md 只保留通用人格，避免多份人格漂移。

## 总结

SOUL.md 的价值不在"调教出个性"，而在把行为预期变成每次会话强制加载、可持续迭代的明文契约。写得短、写得具体、配好工具层权限，再持续用事故反哺——这比任何精心设计的人设都可靠。
