## 背景

单 Agent 串行干活的问题，做过自动化的人基本都遇到过：任务一大，上下文越滚越长，工具输出互相污染，跑到后半段开始"忘事"、重复读文件、甚至跑偏。OpenClaw 的 Agent 支持派生 subagent——每个 subagent 有独立的上下文窗口和工具集，主 Agent 只负责拆任务、派发、汇总。这套机制用好了是并行加速，用不好就是成本翻倍的灾难现场。

## 问题

拿一个真实任务举例：给一个仓库里 20 个模块补单元测试并修 lint。单 Agent 的做法是逐个读文件、改文件、跑测试，40 多分钟还没收敛，中途上下文里塞满了各种工具返回，后 10 个模块的质量明显不如前 10 个。这类任务的特点是：子任务之间数据独立、流程同构——正是并行的理想场景。但直接"开十个窗口各跑各的"也不行，汇总和质量控制会失控。

## 做法

1. **拆分原则**：按数据独立性拆。判断标准只有一条——两个子任务是否共享可变状态（同一个文件、同一条数据库记录）。共享就不能并行。
2. **主 Agent 只做调度**：拆任务、生成子任务 prompt、收结果、做校验。不亲自读大文件，需要侦察信息时派一个只读 subagent 去做。
3. **子任务 prompt 写死三件事**：范围（只准动哪些文件）、工具权限（分析类 subagent 只给只读的 MCP 配置）、输出契约（固定四段：改了什么 / 结论 / 风险 / 下一步）。
4. **协调走文件系统**：subagent 把结果写到约定路径，主 Agent 读路径汇总，而不是让结果在 prompt 里传来传去。
5. **控制并发**：3~5 个一批，一批收齐并校验后再派下一批。

上面那个任务我拆成 4 个 subagent，每人负责 5 个模块，13 分钟跑完；重跑两次结果稳定。提速不是重点，重点是主 Agent 的上下文全程干净，汇总质量可控。

## 踩坑点

- **并发写同一文件**：后写覆盖先写，最阴险的一类 bug。要么按文件分区，要么写入动作全部串行化。
- **输出格式漂移**：subagent 跑着跑着就不守契约，汇总解析直接失败。主 Agent 必须校验，不合格打回重跑一次。
- **上下文隔离是双刃剑**：subagent 不知道全局决策（比如"这个模块的接口即将废弃"）。必要上下文要显式注入，别假设它"应该知道"。
- **静默失败**：某个 subagent 超时或返回空，主 Agent 没察觉就往下走。超时 + 校验 + 重试一次，三件套缺一不可。
- **并发开太高**：触发限流、token 成本失控，而且边际收益趋近于零。并行数不是越多越好。

## 可复用建议

- 能不能并行，先问"有没有共享可变状态"，再谈别的。
- 输出契约（改了什么 / 结论 / 风险 / 下一步）可以直接抄，四段固定，解析稳定。
- 每批任务留日志：派发时间、耗时、token 消耗、结果路径。排障全靠它。
- 分析、侦察类的活优先派只读 subagent，省下的主上下文留给汇总和决策。

## 总结

subagent 编排的核心不是"多开几个 AI"，而是三件事：任务拆分、上下文隔离、结果契约。建议先从 2~3 个并行的只读任务跑通全流程，验证校验和汇总逻辑，再逐步放开写入类并行。一步到位的并行编排，通常是拿 token 和时间交学费。
