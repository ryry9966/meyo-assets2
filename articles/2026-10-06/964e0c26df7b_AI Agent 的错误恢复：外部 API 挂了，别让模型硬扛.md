# 背景

跑过 Agent 自动化的人大都遇到过：流程前半段顺利，到某个 MCP 工具或外部 API 时突然 503，整条工作流要么中断，要么更糟——模型开始自由发挥。错误恢复不是加分项，是 Agent 上生产的门槛。

# 问题

API 故障在 Agent 场景下比传统服务更麻烦，因为中间多了 LLM 这个不确定层。典型表现有三种：

- **无限重试**：模型收到报错后反复调同一个工具，token 烧完，API 也被打击得更狠；
- **幻觉兜底**：重试失败后模型不甘心交白卷，编一个"看起来合理"的结果塞进流程，下游全被污染；
- **崩溃扩散**：一个非关键 API 挂掉，把本可以降级完成的整条流程带崩。

# 做法

核心思路一句话：**重试逻辑放在代码层，不放提示词里；给模型的是结构化结论，不是原始报错。**

**1. 先分类，再动作。** 错误分两类：瞬时错误（429 / 502 / 503 / 超时 / 连接重置）值得重试；确定性错误（401 密钥错、400 参数错、404）重试只是浪费预算。在插件层把两类标记出来。

**2. 代码层做指数退避 + 抖动。** 比如 1s → 2s → 4s，加 0~1s 随机抖动，硬上限 3~5 次。429 场景优先读 `Retry-After` 头。

**3. 给模型结构化错误信封。** 工具失败不要抛裸异常，返回类似：

```json
{
  "ok": false,
  "error": "upstream_unavailable",
  "retryable": false,
  "hint": "use cached data or skip this step"
}
```

模型拿到 `retryable: false` 和 `hint`，才会走降级路径而不是硬刚。

**4. 预设降级路径。** 每接一个外部依赖就问一句：它挂了，流程还能不能完成？常见选项：读缓存（带时间戳，明确标注"数据截至 X 时点"）、备用 provider、跳过该步骤并显式标记、转人工。

**5. 长流程做检查点。** 多步工作流每完成一步落盘状态，故障恢复后从断点续跑而不是从头再来——对配额型 API 这一点尤其省成本。

# 踩坑点

- **在提示词里写"失败了就重试几次"**。模型对次数和间隔没有可靠概念，实测经常变成 10+ 次连发。
- **对 4xx 重试**。见过 401 被退避重试 5 次的，纯属浪费。
- **退避不加抖动**。多个 Agent 实例同时重试，服务恢复瞬间形成惊群，把刚缓过来的 API 再打挂一次。
- **吞掉错误返回空结果**。模型会把空结果当真实数据继续推理，这比直接失败危险得多。
- **超时设太长**。单工具 120s 超时会卡死整个 Agent 循环，外部 API 建议 10~30s，靠重试补可靠性。

# 可复用建议

- 所有外部工具调用统一走一个封装层：错误信封、重试、熔断、日志都在这一层做，不要每个插件各写一套。
- 按失败分类做统计：某个上游一周内 retryable 失败 40 次，就该考虑换供应商或加本地缓存了。
- 定期演练：手动把依赖 API 断掉，看 Agent 是优雅降级还是当场开始编数据。演练比事后排查便宜得多。

# 总结

外部 API 挂掉不可怕，可怕的是 Agent 从未被设计过"挂掉之后怎么办"。把重试、降级、检查点做在代码层，把结构化的结论交给模型，Agent 才能在不稳定的依赖之上，跑出稳定的输出。
