## 背景

在 OpenClaw 这类自动化环境里，任务重复执行几乎是必然事件：调度器超时重试、Agent 判断失误后重跑、用户手动补触发、MCP 工具调用网络抖动后重发。我们习惯把「任务只跑一次」当作默认，但工程上更接近现实的假设是：**任何任务都可能被执行两次，甚至 N 次**。幂等性就是让这件事变得无害的设计。

## 问题

非幂等操作的典型翻车现场：

- 通知类插件重复发送，同一个提醒推了三遍
- 定时任务重复写入，表里堆出一堆同内容记录
- Agent 调用创建类工具，超时后重试，服务端其实已经成功，结果生成了两份资源

共同点是：**副作用和执行次数相关**，执行两次就产生两份后果。这不是偶发 bug，是设计缺陷。

## 做法

**1. 优先选择天然幂等的操作形态**
写配置用整文件覆盖（upsert）而不是 append；更新操作带目标状态而不是增量：`set status=done` 天然幂等，`count += 1` 不是。

**2. 给关键写操作加幂等键**
客户端生成一个稳定的 key（如 `task_id + step + 目标资源`），在工具 handler 层统一拦截：重复请求带相同 key，直接返回上次的结果，不再执行。MCP 工具封装里这一层尤其值得做。

**3. 执行前查状态，执行后落标记**
任务入口先检查目标是否已完成（文件存在？记录已写入？远端资源已创建？），完成后写明确的完成标记。注意必须和幂等键配合，单独的「先查再做」有竞态（见下）。

**4. 拆分查询与变更**
让 Agent 的只读探查和写操作走不同工具。查询随便重试，写操作必须过幂等层，同时降低了 LLM 误触发写操作的代价。

## 踩坑点

- **check-then-act 竞态**：查和写之间可能已有另一个实例完成。标记写入要尽量和业务操作原子化，做不到就退回幂等键去重。
- **用时间戳或随机数当幂等键**：每次重跑 key 都不同，等于没做。key 必须从任务的确定性输入派生。
- **超时不等于失败**：最阴险的场景。请求已到达、服务端已执行，你这边却报超时然后重试。所以幂等键要客户端生成、随请求带上，而不是事后补查。
- **LLM 参数不稳定**：Agent 重试时可能产出略有差异的参数（改个标题、换个路径），拿参数内容做去重指纹会失效。去重要锚定在任务 ID 上。
- **文件写入非原子**：写一半崩溃，「文件存在」的检查会误判为已完成。用临时文件 + rename 的原子写。

## 可复用建议

1. 写一个通用幂等层（记录表 + key 拦截），自定义插件和 MCP 工具默认接入，别各写一套
2. 副作用收敛到少数几个入口函数，便于统一加去重和日志
3. 日志里记下幂等 key 和命中去重的请求，排查「为什么没执行」时能救命
4. 幂等记录设合理的过期时间，避免长期运行后积累死记录

## 总结

幂等性不是加分项，是自动化系统能「放心重试」的前提。调度器、Agent、网络都在制造重复，你的任务是让重复变得无害。核心三件事：**写操作带稳定幂等键、完成状态可查询、副作用入口收敛**。做到这些，重跑一个任务和跑一次一样安全，自动化才真正敢放手。
