## 背景

写自动化任务时，大家默认"一个触发只跑一次"。但在 Agent 系统里，重复执行几乎是常态：cron 任务重叠、webhook 被上游重推、网络超时后重试（请求其实已经成功）、Agent 重规划时把同一个工具再调一遍，还有人工补跑。底层调度最多给你 at-least-once，"恰好一次"从来不是免费的——它要靠你在业务层做幂等来兜住。

## 问题

非幂等操作遇到重复执行，翻车方式很固定：消息发两遍、文件创建两份、计数被累加、收费 API 被调用两次、状态机被多推一格。这类 bug 平时看不见，一旦触发就是线上事故，而且很难复盘——因为日志里"每次执行都是对的"。

## 做法

我的做法分四步：

1. **先分类。** 把工具和任务操作分成两类：设值型（写目标状态，天然幂等，比如覆盖写配置）和追加型（发消息、建资源、累加计数，天然不幂等）。分类本身就是一半的答案。
2. **追加型加幂等键。** key 必须来自稳定的业务标识：触发事件 ID、任务 ID + 时间窗，而不是 `now()`。执行前查账本，命中就跳过；执行后记账。
3. **账本要原子。** 用 SQLite 唯一约束或 Redis SETNX 做占位，别写"先查一下再执行"的裸逻辑——并发下两个执行都能通过检查。
4. **能改设值型就改。** upsert 代替 insert、按内容 hash 命名文件、把"执行步骤"改写成"声明期望状态再收敛"。状态收敛式的任务，重复跑一遍结果也是收敛的，这是最省心的幂等。

另外注意分层：触发层做单飞锁（防 cron 重叠），工具层在 MCP server 里做去重中间件，副作用层优先用上游支持的幂等参数。只在一层防，总有漏网的。

## 踩坑点

- **用时间戳当 key。** 每次运行 key 都不同，去重形同虚设。key 要跟着触发事件走，不跟着运行时刻走。
- **记账和副作用不原子。** 副作用成功了、记账失败了，重试照样重复。兜底方案是让副作用可查询：按内容 hash 反查"这条是不是已经发过、这个文件是否已存在"。
- **重试叠加。** Agent 重试、HTTP 客户端重试、插件内部重试，三层叠起来，只在触发层去重根本不够。
- **key 粒度失衡。** 太粗会把合法的第二次执行也吞掉（比如同一天两条不同的告警），太细等于没去重。粒度要对齐业务语义。
- **LLM 的不确定性。** 模型可能两次调用同一工具且参数略有出入，参数 hash 做 key 会失效。在工具参数里显式要求传业务 ID，比事后算 hash 靠谱。

## 可复用建议

- 写 MCP 工具时默认提供 upsert 语义；创建类操作要求调用方带 idempotency key。
- 账本表结构固化下来：`key` 唯一索引 + 状态 + 结果引用，跨任务复用，别每个脚本自己造一套。
- CI 里加一条"连跑两次"的幂等性测试：跑两遍，断言副作用数量不变。
- 提供 dry-run 模式：先打印将要产生的副作用清单，确认后再真跑。
- 心法一句话：拿不准的操作，按"它一定会被执行两次"来设计。

## 总结

幂等不是洁癖，而是自动化系统的默认假设。调度的 at-least-once 你改不了，能改的是自己的操作：能设值就别追加，必须追加就上幂等键和账本，账本要原子，副作用要可查。把"重复执行"当成设计输入而不是异常，自动化任务才敢真的放手让它跑。
