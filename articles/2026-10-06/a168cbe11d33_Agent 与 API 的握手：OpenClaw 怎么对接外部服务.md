## 背景

Agent 跑通本地任务之后，下一个问题永远是：它能不能碰到真实系统？查库存、发工单、调内部 RPC——这些能力都不在模型里，而在接口后面。OpenClaw 的思路是让 Agent 通过统一的工具层（MCP server / 插件 / function tool）去碰这些服务。但"能调通"和"能稳定跑在生产里"之间，差着不少工程细节。

## 问题

实际对接时常见三类麻烦：

1. **鉴权碎片化**：有的服务是 API Key，有的要走 OAuth2 刷新，还有内网 mTLS。密钥放哪、怎么换新，直接决定能不能上生产。
2. **工具面失控**：工具声明一多，模型选错工具、传错参数的概率明显上升；描述写得像 API 文档，模型反而读不懂"什么时候该用我"。
3. **错误不可读**：接口抛 500 或返回一大坨原始 JSON，Agent 拿到后要么死循环重试，要么把上下文撑爆。

## 做法

我们的落地流程分五步：

**1. 先收敛工具面。** 按业务域划分，一个领域一个 MCP server，而不是一个 API 一个工具。比如订单域只暴露 `query_order`、`create_ticket` 两个工具，参数用 JSON Schema 卡死枚举和必填项。

**2. 描述写给模型看。** 工具 description 里写清"何时用 / 何时不用 / 参数从哪来"，比罗列字段有用得多。实测一句"仅当用户明确给出订单号时调用"，能把误调用率降一大截。

**3. 密钥只进配置，不进对话。** API Key、Token 全部走环境变量或插件的 secret 注入，工具参数里永远不出现明文凭据，日志层再做一次脱敏。

**4. 错误做归一化。** 工具层把上游错误统一翻译成 Agent 可读的结构：`{code, message, retryable}`。只有可重试的才重试，并配指数退避；写操作必须带幂等键，避免重试造成重复下单。

**5. 超时和熔断放插件层。** 每个工具调用设硬超时，上游挂了就返回明确错误，而不是让 Agent 干等。

## 踩坑点

- "工具越多越好"是错觉，超过 20 个后选错率显著上升，宁可按场景拆分。
- 返回值直接透传上游响应，一次查询塞进上万 token——工具层必须做字段裁剪。
- 只测了 happy path，上线第一天就被 429 打爆；限流重试要从第一天就写进适配层。
- 工具 schema 改了但没跑契约测试，模型按旧习惯调用直接报错。
- 忘了给写接口做 dry-run 开关，调试期就真实写进了生产库。

## 可复用建议

- 适配层保持"薄"：鉴权、重试、脱敏、裁剪这四件事做扎实，业务逻辑别塞进工具层。
- 给每个工具写契约测试，schema 变更进 CI。
- 写操作默认 dry-run，显式传 `confirm=true` 才真执行。
- 观测先行：每次工具调用记录耗时、状态码和脱敏后的参数摘要。

## 总结

对接外部服务的本质不是"多接几个 API"，而是把鉴权、错误、限流这些工程语义翻译成 Agent 能理解的协议。工具面收敛、密钥隔离、错误归一化，这三件事做好了，OpenClaw 的 Agent 才算真正握上了手。欢迎在社区里分享你们各自的对接姿势和失败案例。
