# Agent 与 API 的握手：OpenClaw 怎么对接外部服务

## 背景

一个 Agent 的上限，基本由它能触达的外部服务决定。模型再强，没有工具就只是个会聊天的顾问。在 OpenClaw 侧，接入路径主要有两条：走 MCP 的标准化工具，或者用 skill/plugin 包一层自定义 HTTP 调用。这篇帖整理我们社区几个项目对接外部 API 的通用做法，偏实操，不谈玄学。

## 常见问题

对接失败很少是“根本调不通”，更多是这几种：

- 鉴权方式与服务端预期不匹配，token 放错了位置；
- 没设超时、没定重试策略，一次网络抖动拖垮整轮对话；
- 大段响应原样回灌上下文，几轮就把窗口撑爆；
- 密钥混进 prompt 或日志，事后清理成本极高。

## 做法

**1. 选接入形态。** 目标服务已有 MCP server 就直接挂到配置里，省去自己维护协议层；没有的话，写一个薄 skill，只做“参数组装 + 发请求 + 结果裁剪”三件事，别在里面塞业务逻辑。

**2. 鉴权最小化。** API key 走环境变量或密钥文件，由运行时注入，绝不写进 prompt 和工具描述。OAuth 类服务单独做 token 刷新，过期前静默续期。scope 按需申请，只读能解决的事别给写权限。

**3. 把工具描述当文档写。** Agent 选工具、填参数全靠这段描述。写清三件事：什么场景该用、每个参数的含义与示例、出错时返回什么。描述和行为不一致是最阴的坑——模型会“将错就错”，一路错到底。

**4. 超时、重试与确认门。** 所有调用显式设超时；只有确认幂等的接口才允许自动重试，并用指数退避。写操作（下单、发消息、删数据）前置一层确认：让 Agent 先产出意图摘要，人批准后再执行。

**5. 错误要“说人话”。** 服务端报错别原样抛异常，转成模型能理解的一句话加关键字段返回。拿到可读错误，模型才有机会自我修正，而不是卡死重试。

## 踩坑点

- **重试风暴**：给非幂等的创建接口开了自动重试，结果重复建了三份工单。规则很简单：不确定幂等，就不重试。
- **响应裁剪**：某接口默认返回几 KB 的 JSON，直接喂给模型既费 token 又降低准确率。在 skill 里先挑字段、做分页，再交给模型。
- **日志脱敏**：请求头里的 Authorization 会被完整打进日志，落盘前要接一层过滤器。

## 可复用建议

- 沉淀一个通用 HTTP 调用层：统一超时、重试、脱敏、日志，各 skill 只写差异部分。
- 新服务先接 mock 跑通整条链路，验证工具描述和参数流转，再切真实凭据。
- 给每个对接写一条验收脚本：一次成功调用 + 一次故意失败，纳入 CI。

## 总结

对接外部服务，本质是给 Agent 递一张写清楚的使用说明书，再配一套护栏：权限最小、超时必设、写操作留确认、错误可读。这四件事做到位，握手才算稳，Agent 才能从“能聊”走向“能干活”。
