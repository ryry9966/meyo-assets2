## 背景

做自动化久了会发现一个规律：**重试不是异常，是常态**。网络抖动导致的超时、Agent 重新规划后再次调用同一个工具、定时任务重叠触发、人工忍不住多点一次"运行"——这些都指向同一个事实：OpenClaw 里任何一段任务逻辑，生命周期内大概率被执行不止一次。幂等性（Idempotency）要解决的就是：重复执行时，结果仍然正确。

## 问题

举一个典型场景：定时任务把表单提交同步到工单系统，逻辑是"读取未处理记录 → 调用创建接口 → 标记已处理"。某次请求超时，但创建实际成功了、只是响应没回来，上层重试，于是出现两张一模一样的工单。

再比如文件处理任务用 append 写结果，重跑一遍内容翻倍；通知任务重试后同一消息发了两遍。这类 bug 平时完全看不出来，只在"恰好失败一次"时出现，而且往往是事后从下游系统才发现，排查成本很高。

## 做法

1. **盘点非幂等操作**：create/insert、append、计数累加、发消息、移动文件、一切有外部副作用的调用。这些是重试风险点。
2. **定义"逻辑 ID"而非"运行 ID"**：幂等键建议由 `任务类型 + 关键输入的 hash + 时间窗口（定时任务按调度周期取整）` 组成。关键是这个 key 在重试路径上必须保持不变——Agent 重新规划时不要重新生成。
3. **执行前查重、执行后落账**：先查这个 key 是否已成功处理；副作用完成后写入处理记录。数据库层面用唯一约束兜底，不靠应用层自觉。
4. **优先改写成收敛式语义**：把"上传文件"改成"确保远端文件内容等于本地内容"，把"创建记录"改成"确保记录存在且字段正确"。ensure/upsert/sync 这类操作天然可重入。
5. **利用外部系统自带的幂等能力**：不少云服务 API 支持幂等键参数，把逻辑 ID 传过去，重复请求会直接返回首次结果。

## 踩坑点

- **key 设计走极端**：只用输入 hash，会导致"语义相同但确实要再跑一次"的任务被误跳过；用随机 UUID，重试时换了新 ID，等于没做。
- **check-then-act 的并发窗口**：两个 worker 同时查到"不存在"，然后都去创建。唯一约束或原子写入是底线，"先查一下"不算防护。
- **只把最后一步做成幂等**：中间步骤失败留下半成品状态，重跑直接卡死。应该让每一步都能安全重入。
- **不可撤销的副作用**（如已发出的通知）：至少把消息 ID 固定为逻辑 ID 的派生值，方便下游去重；或在发送前先落"待发送"记录。
- **去重存储 TTL 太短**：隔天补跑的重试直接穿透，防护形同虚设。

## 可复用建议

- 设计工具和 MCP 接口时，默认按"可被重复调用"来写，并把幂等性写进接口描述里——Agent 能据此判断失败后是否值得重试。
- 养成一个习惯：任何自动化上线前，在测试环境**手动连跑两遍**，确认第二遍的副作用为零。
- 把"决策"和"执行"分开记录：重试时先读上次决策结果，既避免重复推理，也避免重复执行。

## 总结

幂等不是让任务不失败，而是让失败后的重试变得无害。自动化系统的可靠性，很大程度上取决于你是否默认"每段逻辑都会被执行两次"。把幂等键定义好、把操作改写成收敛式语义、用唯一约束兜底——这三件事做完，绝大多数重复执行问题就消失了。
