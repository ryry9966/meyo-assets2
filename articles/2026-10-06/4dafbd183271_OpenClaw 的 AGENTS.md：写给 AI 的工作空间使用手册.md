## 背景：Agent 也需要一份 README

人类进一个新仓库先看 README，agent 进一个新工作区看的是 AGENTS.md。这个约定最初在编码 agent 社区流行，OpenClaw 把它继承下来并扩展成通用约定：每次会话启动，工作区根目录的 AGENTS.md 会被注入上下文，作为「这里怎么干活」的持久说明。它和 SOUL.md（性格）、USER.md（用户画像）各管一摊，AGENTS.md 管的是环境与流程。

## 问题：没有手册的助理会自由发挥

用了一段时间后，我踩到的典型问题：

- 每次都要口头重复交代：「文件放 docs，别堆在根目录」「删除前先问我」；
- agent 自作主张：文件命名每次不一样，脚本被写进只读目录；
- 换设备、加插件之后，它按旧印象猜环境，路径全错。

这些不是模型能力问题，而是缺少一份稳定的规则源。靠聊天记录纠偏，纠完就忘。

## 做法：把规则当配置写，不当作文写

**1. 控制篇幅，前重后轻。** 建议 100 行以内。注入的是全文，写 500 行只会稀释关键规则，最重要的硬性约束放最前面。

**2. 分块写。** 给一个我在用的骨架：

```markdown
# 环境事实
- Ubuntu 22.04，时区 Asia/Shanghai
- 目录：~/docs 文档 / ~/scripts 脚本 / ~/inbox 待整理
- 已启用工具：web_search、memory、cron

# 硬性规则
1. 删除、覆盖、涉及 ~/.ssh 与密钥的操作，先征询再执行
2. 新文件按「日期-主题.md」命名放入对应目录
3. 回复用中文，代码注释用英文

# 固定流程
## 每日摘要
1. 扫描 ~/inbox 当日新增
2. 生成摘要写入 ~/docs/daily/
```

**3. 区分事实与规则。** 环境是事实（会变，要更新），行为约束是规则（要可执行）。「注意安全」没用，「rm 与密钥相关操作必须先问」才有用。

**4. 和 memory 分工。** AGENTS.md 放稳定规则，MEMORY.md 放会话沉淀的事实。规则写进 memory，重启几次就漂移；事实写进 AGENTS.md，环境一换就全错。

**5. 用「错误回流」迭代。** 我维护一个 errata 文件：agent 每犯一次错，补一条对应规则，攒三五条就合并进 AGENTS.md，同时删掉过时条目。这文件本质上是它的 bug tracker。

## 踩坑点

- **写太长。** 初期我写了近三百行，关键约束反而被淹没，该犯的照犯；精简到 80 行后明显听话。
- **规则和记忆冲突。** 输出目录从 A 改到 B，但 memory 里全是 A 的记录，agent 来回横跳。改规则时要顺手清记忆。
- **写入敏感信息。** key、内网地址不要进 AGENTS.md，工作区可能被同步或备份。
- **忘记维护。** 装新插件、迁移路径后不更新，它就按旧地图开车。我把「更新 AGENTS.md」设为装完插件后的固定动作。
- **层级过深。** 超过三层的嵌套列表，遵循效果明显变差，尽量拍平。

## 可复用建议

- 把 AGENTS.md 纳入 git，改规则像改代码一样有 diff 可查。
- 多工作区用户：通用规则写一份短的，工作区差异各自补一节，别整份复制。
- 每月删一次规则。规则和代码一样需要重构，留下的每一条都应能说出「它防的是哪次事故」。

## 总结

AGENTS.md 的价值不在于写得全，而在于把「我希望助理怎么干活」从重复的口头交代，变成一份版本化、可迭代的配置文件。写它大概只花半小时，之后每次会话省下的重复沟通是持续收益。如果你的工作区还没有这份文件，建议今天就补上，从十条以内的高频规则写起。
