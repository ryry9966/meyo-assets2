# OpenClaw 的 AGENTS.md：写给 AI 的工作空间使用手册

## 背景

OpenClaw 的 agent 每次会话启动，都会先读工作空间里的几份 Markdown：`SOUL.md` 管人格与语气，`TOOLS.md` 管工具备注，`AGENTS.md` 管操作规程。AGENTS.md 本身是一个跨工具逐渐形成的通用约定，OpenClaw 把它放在 workspace 根目录，随系统提示一起注入。可以把它理解为：新同事入职第一天拿到的那份 SOP。

## 问题

不写或乱写 AGENTS.md，症状很固定：

- **跨渠道风格漂移**：Telegram 里简短爽快，转去回邮件也是同样的话痨或同样的极简。
- **工具调用不规范**：不先检索就猜答案，该确认的命令直接执行。
- **同一类错误反复纠正**，聊完就忘——因为规则只存在于聊天记录里。
- **记忆文件越滚越乱**，没有写入和清理的规矩。

本质是：模型的默认行为不等于你要的规范。规范在你脑子里，agent 看不见。

## 做法

1. **先翻记录，再写文档。** 把最近两周你手动纠正 agent 的事项列出来，这就是 AGENTS.md 的原始素材，比凭空设计靠谱得多。
2. **分区块，写短条目。** 我的结构是五块：身份与边界（不冒充真人、不主动加群拉人）；渠道礼仪（每个渠道的回复长度、表情符号、免打扰时段）；工具规程（先搜后答、执行命令前确认、产物统一写到哪里）；记忆卫生（什么值得写进 MEMORY.md、多久清理）；求助规则（什么情况必须停下来问人）。
3. **每条可判断。** 用"如果……则……"的祈使句。"要有礼貌"不可执行；"邮件回复不超过 120 字，先给结论"可执行。
4. **控制长度。** 它会进每次会话的上下文，目标一到两屏。细节下沉到 TOOLS.md 或独立文件，正文只留索引。
5. **进 git。** 行为变了能 diff 出是哪条规则改的，也能整体回滚。

## 踩坑点

- **和 SOUL.md 抢职责。** 人格写进 SOUL，规程写进 AGENTS。两边重复容易出现"一个说必须确认、一个说放开做"的冲突，模型只能随机选边。
- **条目太多。** 一次塞两百条，权重互相稀释，等于没有重点。先留十条最痛的。
- **塞了不该塞的东西。** API key、家庭住址这类信息不要写进去——它会出现在每次会话的上下文里。
- **高估约束力。** 模型不会 100% 遵守文档。涉及安全的动作（删文件、对外发消息）要在工具层配白名单，文档只负责第一道过滤。

## 可复用建议

- 建立"纠错晋升"流程：同一件事手动纠正两次，就考虑写成规则。
- 规则是负债。每季度删一遍没再触发的条目。
- 单条改动的验证周期设为一周，对照行为日志决定去留，别凭感觉。
- 把 AGENTS.md 当代码 review 的对象：改动走 commit，重要条目留二次确认。

## 总结

AGENTS.md 的价值不在于写了多少字，而在于把隐性规范变成可版本化、可迭代、可回滚的显性契约。它不是一次性的 prompt 调优，而是与 agent 长期协作时持续维护的操作手册——写它的过程，其实也是把你自己的工作习惯想清楚的过程。
