## 背景

跑 OpenClaw 一段时间后都会遇到同一个问题：Agent 对"你这台机器"一无所知。它不知道包管理器是 brew 还是 apt，不知道 Python 归 conda 还是 uv 管，不知道 7860 端口已经被常驻服务占用。于是它猜：猜错命令、猜错路径，再花掉你几轮对话来纠错。这些信息其实都在你脑子里，只是一直没显式交给 Agent。tools.md 就是干这个的：一份放在工作区根目录、Agent 开工前会读的环境事实清单。

## 问题

常见的错误做法有三种。一是全塞进系统提示词：换台机器就得改 prompt，多机同步是灾难，而且大部分环境信息没必要每轮都占上下文。二是什么都不写，靠 Agent 现场探索：能试错，但每次会话都要重新踩一遍坑，成本高且不稳定。三是混进 AGENTS.md：环境事实跟机器走，项目约定跟仓库走，混写必然漂移。

## 做法与步骤

在工作区根目录建 tools.md，控制在 100 行以内，固定五个分区：

- **machine**：OS、架构、有无 GPU、代理端口、镜像源
- **commands**：包管理器、Python 管理方式、容器运行时——"该用哪个命令"的事实
- **paths**：工作区、下载目录、日志位置
- **services**：常驻服务与端口约定，如"8080 留给开发服务器，别抢"
- **never**：禁止事项，如"不要全局 pip install""不要动 ~/Documents"

要点是写事实、不写教程。"Python 用 uv 管"是一句事实；"Python 环境配置教程如下"是文档，Agent 不需要后者。

维护上把它当 lockfile 对待：进 git、走 diff review、环境一变就更新。多机场景用 tools.md.example 做模板，每台机器本地覆盖，不进公共仓库。可以写个十行脚本 dump `uname`、`which`、各工具版本号生成初稿，人工裁剪后定稿。

## 踩坑点

- **写成文档而非清单**。超过一两百行，Agent 要么浪费上下文要么直接略读，效果反而变差。
- **放敏感信息**。tools.md 会全文进入模型上下文，密钥、token 一律不写，那是 .env 的职责。
- **与 AGENTS.md 内容重复**。重复必漂移，坚持单一来源，AGENTS.md 里一行引用即可。
- **信息过期**。过期的 tools.md 比没有更糟——Agent 会盲目信任它，拿着旧路径自信地做错事。环境大改后务必核对。
- **假设它一定会被读**。不同接入方式对工作区文件的注入行为不同，先花一分钟验证：问 Agent 一个只有 tools.md 里才有的事实，答得上才算生效。

## 可复用建议

- 五个分区跨机器保持同构，Agent 的读取习惯稳定，换机零学习成本
- 把"脚本生成初稿 + 人工裁剪"固化成流程，新机器十分钟上线
- 每月或每次环境大改后，让 Agent 对照 tools.md 自检实际环境，差异回写
- MCP 与插件有自己的进程级配置，tools.md 只负责 Agent 的认知，别让它接管 .env 或服务配置文件

## 总结

tools.md 的本质是一次认知对齐：把你对这台机器的隐性了解，显式化为 Agent 开工前必读的契约。它解决的不是配置管理，而是省掉那些本不该发生的猜错与重试。写短、写准、保持新鲜，其余交给 Agent 自己发挥。
