## 背景

跑在 OpenClaw 上的 Agent，真正干活的部分大多是工具调用：搜索、抓取、内部 RPC、MCP server 暴露的各类能力，而链路末端几乎都是外部 API。API 一定会挂——限流、超时、5xx、服务商部署事故。人操作时会等、会绕路、会放弃，Agent 的默认表现却往往很糟：要么原地重试直到把对方彻底打死，要么把失败脑补成成功继续往下跑。

最近一次故障复盘里，我们把场景归纳成四类典型表现：

1. **立即重试风暴**：请求超时后，Agent 在推理循环里"再试一次"，没有退避间隔，把一次抖动放大成持续压测；
2. **无限重试**：LLM 每一轮都决定再试，没有次数上限，token 烧完任务也没推进；
3. **假成功**：HTTP 200，但 body 是错误描述或空数据，Agent 拿着垃圾结果继续推理；
4. **静默失败**：工具层吞掉异常返回 None，最后 Agent 汇报"已完成"，没人知道中间少了一步。

根子在于：**重试决策被放在了 LLM 的推理循环里**。正确的分工是——代码负责机械级恢复（退避、计数、熔断），模型只负责业务级决策（跳过、换源、还是上报人类）。

## 做法：三层防线

**第一层：标准客户端封装。** 所有外部调用统一走一个封装层，别让每个插件自己裸写 HTTP 请求：

- 显式 timeout（如 10s），且必须小于整个 run 的剩余时间预算；
- 指数退避 + 随机抖动，最多重试 3 次；
- 区分错误类型：429、5xx、网络超时可重试；参数类 4xx 直接失败，重试没有意义。

**第二层：结构化错误信号。** 失败后既不要把原始 stack trace 塞进上下文（污染对话），也不要静默吞掉。给模型的是结构化结果：

```json
{"status": "error", "retryable": false,
 "error_type": "upstream_unavailable",
 "hint": "数据源暂时不可用，可使用缓存或跳过"}
```

模型看到的是"这个源不可用、是否可重试、有什么替代"，才能做出像样的规划。

**第三层：熔断与降级。** 连续 N 次失败就打开熔断，冷却期内直接短路，不要每个 run 都去撞一遍挂掉的 API。熔断期间走降级路径：带过期标记的缓存、备用数据源，或明确"跳过该步骤并告警"。同时在 run 层面维护总 deadline，防止单步卡死吃光预算。

## 踩坑点

- **在 prompt 里写"失败了就重试"**：等于没有上限，重试逻辑必须在代码里；
- **信任 200**：必须做响应 schema 校验，空结果同样按失败处理；
- **单步 timeout 比总预算还长**：一步挂起，整条流水线陪着等；
- **熔断和缓存每个 run 各自带一份**：并发 run 会同时撞同一个挂掉的 API，这两个状态应该全局共享；
- **最终汇报不体现降级**："来自缓存"和"来自实时数据"必须在结果里说清，否则下游无法判断可信度。

## 可复用建议

1. 抽一个统一的 tool client（timeout + retry + 结构化错误），所有插件和 MCP 工具复用，不要各写各的；
2. 把故障注入加进评测流程：mock 429、500、timeout 三种情况，跑一遍看 Agent 选的是跳过、换源还是上报，而不是当场崩掉；
3. 每次重试和降级都打日志并带上 run id，事后能还原完整决策链；
4. 在工具的能力说明里写清楚哪些有降级模式，模型才知道退路存在。

## 总结

外部 API 挂掉不是异常事件，是常态。区别只在于挂的那一刻，你的 Agent 是在推理循环里原地打转，还是沿着预先铺好的退路走。恢复逻辑放代码层，诚实的信号给模型层，降级路径提前准备好——这三件事做完，API 故障就从"事故"降级成"日志里的一行"。
