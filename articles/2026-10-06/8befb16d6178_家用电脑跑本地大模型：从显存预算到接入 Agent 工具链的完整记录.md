## 背景

做 Agent 和 MCP 插件开发时，两个问题反复出现：一是测试数据走云端不放心，尤其涉及本地文件和自动化脚本；二是调试期高频调用，token 费用累积很快。社区里常见的折中方案是：本地跑一个中等规模模型当"工作模型"，负责工具执行和简单推理，复杂任务再路由给云端。这篇帖子记录我在一台普通家用机上跑通"本地模型 + 工具调用"的全过程，参数和坑都摆出来。

## 问题

我的环境是 8GB 显存的消费级显卡 + 32GB 内存。目标很明确：跑一个能**稳定输出 function call JSON** 的模型，常驻内存，给本地 Agent 当默认后端。

## 做法

1. **先算显存账，再选模型。** 经验公式：模型显存 ≈ 参数量 × 量化字节数 + 约 2GB 开销 + KV cache。8GB 显存选 7B/8B 的 Q4_K_M（约 5GB）比较稳；14B Q4 也塞得下，但上下文会被压得很短。
2. **选运行时。** Ollama 上手最快，自带 OpenAI 兼容接口；追求吞吐和多并发可以上 vLLM，但对显存要求苛刻。我用 Ollama，`OLLAMA_HOST=0.0.0.0` 起服务，方便局域网内其他设备调用。
3. **显式设置上下文长度。** 默认值偏小，Agent 多轮对话很容易被静默截断。8B Q4 上我把 `num_ctx` 设到 8192，显存还有余量；再往上 KV cache 增长很快，需实测。
4. **接进 Agent 框架。** base_url 指向本地端口，超时给到 120 秒以上，keep_alive 设为常驻——冷启动一次要十几秒，模型反复卸载重载非常伤体验。
5. **专门测工具调用。** 拿一两个最简单的 MCP 工具，固定 20 条指令跑批，统计 JSON 解析成功率。我测的 8B 模型约 92%，14B 能到 97% 以上。这个数字直接决定它能不能进 Agent 主流程。

## 踩坑点

- **KV cache 吃显存比想象中凶。** 上下文拉满后直接 OOM，表现为进程被杀且日志极短。排障第一步是降 `num_ctx`。
- **量化越激进，工具调用越容易坏。** Q2/Q3 版本常输出不合法 JSON 或漏参数，Q4_K_M 是我实测的质量底线。
- **温度别开高。** Agent 循环里温度 0.7 以上会出现反复调同一个工具的情况，0.2 左右明显稳定。
- **部分 GPU offload 比预期慢很多。** 显存不够时分层卸载到内存，速度可能掉到个位数 token/s，不如直接换小一号的模型。
- **截断不会报错。** 被截断的对话只让 Agent 行为变傻，不会有任何提示。建议把每轮实际发送的 token 数打进日志。

## 可复用建议

- Q4_K_M 当默认起点，出现质量问题再升，不要一上来追 FP16。
- 任何模型接入 Agent 前，先跑固定的工具调用测试集，用数据说话。
- 把"本地跑简单任务、云端跑复杂推理"做成路由规则：本地失败率超阈值自动 fallback，两边都不浪费。
- 显存换上下文、并发换延迟，这些取舍想清楚再决定买卡还是换机器。

## 总结

家用机跑本地模型已经完全可用：8GB 显存跑 8B Q4 做 Agent 的工具执行层是够用的，瓶颈不在推理速度，而在工具调用稳定性和上下文容量。务实的定位是把它当流水线里一个便宜可靠的工人，而不是全能选手。显存条件允许的话建议 14B 起步，省心程度完全不同。
