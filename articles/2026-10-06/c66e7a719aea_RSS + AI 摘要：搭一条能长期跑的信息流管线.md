## 背景

订阅源越加越多，真正读的越来越少。RSS 本身解决了"聚合"，但没解决"压缩"——大多数源一天几十条，有信息增量的可能只有两三条。我的思路是让 Agent 做第一道过滤器：RSS 负责稳定拿到结构化条目，模型负责把噪声压成摘要，链路用 MCP 工具串起来，尽量不写一次性胶水脚本。

## 做法

整体分四层：

1. **源层**：优先选全文输出的源；只有摘要的源，抓取时用 readability 类工具补全文。源列表放一个 YAML 配置，增删源不动代码。
2. **抓取层**：定时任务触发 Agent，通过 MCP 的 fetch 工具拉 feed，解析出 title / link / published / content。
3. **状态层**：每个条目算一个 hash（link 优先，title 兜底）存进本地 SQLite。已见过的直接跳过——这一步同时是去重和断点续跑的基础。
4. **摘要层**：两段式。第一段用小模型对每条做一句话摘要加三档打分（跳过 / 可看 / 必读）；第二段只把"可看"以上的条目交给大模型，合并成按来源分组的日报。

投递就是一个 webhook：日报落成 markdown，推到群或静态页面。

## 踩坑点

- **summary 字段不可信**。不少源的 description 是截断的前两百字，甚至是导流文案，直接拿去做摘要会得到一堆"本文介绍了……"的废话。必须全文。
- **GUID 不稳定**。同一篇条目换一次 CDN，guid 就变了，导致重复处理。去重键要用 link 的规范化 hash，title hash 做兜底。
- **成本失控**。最初我把全部条目丢给大模型，token 花得心疼。改成小模型先筛、大模型只处理幸存者之后，成本降到原来的十分之一左右。
- **幻觉条目**。让模型"补充背景"时它会热情地编造 feed 里不存在的条目。后来在 prompt 里写死：只允许复述给定文本，不允许引入外部信息。
- **幂等性**。推送失败要能重跑。我的做法是"处理成功 + 推送成功"才落状态，中间任何一步失败，下次定时任务自然重试。

## 可复用建议

- 源配置、状态库、推送目标全部外置；管线保持无状态倾向，状态只落在 SQLite 一处。
- 先人工审一周摘要质量再放开自动推送，prompt 的调优空间比想象中大。
- 用 MCP 把"抓取、抽取、推送"做成独立工具，Agent 只负责编排和摘要，出问题能逐段定位。
- 打分阈值宁严勿松：漏掉一条的代价，远低于日报本身变成新的信息噪声。

## 总结

这套管线跑了几个星期，日均处理两百多条目，日报稳定在十条以内。没有多智能体，没有复杂编排，就是把 RSS 的稳定性、SQLite 的简单可靠和模型的压缩能力各用了一半。自动化的价值不在于全自动，而在于把"筛选"的成本压到愿意每天看一眼的程度。
