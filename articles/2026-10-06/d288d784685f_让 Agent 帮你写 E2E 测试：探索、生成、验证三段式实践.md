## 背景

E2E 测试大概是团队里最难坚持的自动化资产：写起来慢、跑起来脆、改版后维护成本更高。现在有了带浏览器操作能力的 agent 和 MCP 工具，“让 AI 顺手把 E2E 写了”听起来顺理成章。我们最近在一个中等规模的前端项目上做了一轮实践，结论先说：能省力，但不能撒手。

## 问题

直接把 PRD 丢给 agent，让它生成 Playwright 用例，典型产出是：

- **selector 靠猜**。agent 只看代码不看运行时，class 名一改版就全崩；
- **断言质量差**。大量 `toBeVisible()` 这种“跑得过但什么都没验证”的万能断言；
- **flaky**。等待靠 sleep、超时给得极宽，CI 偶发红；
- **一次性生成几十个用例**，没人 review，测试资产反而变成负债。

## 做法

核心思路：把 agent 当成一个不了解业务的新同事，把“探索”和“落笔”拆成两个阶段，并严格控制每次生成的粒度。

1. **先探索，后写码。** 给 agent 挂上浏览器控制类 MCP 工具，让它打开真实测试环境，亲自点一遍核心流程。这一步的产物不是测试代码，而是一份“页面结构 + 交互序列 + 关键状态变化”的探索记录。
2. **固定骨架，只填内容。** 团队预先约定 fixture、page object 分层、选择器策略（一律优先 `data-testid`）和断言库。agent 只负责往骨架里填用例，不允许自创结构。
3. **小批量 + 即时验证。** 一次只生成一条流程的用例，落盘立刻进 CI。红了就让 agent 对照失败 trace 和截图自己修，修不动再转人工。
4. **review 只盯断言。** 人工检查的重点不是代码风格，而是断言是否校验了业务结果——数据是否真的落库、状态是否真的翻转，而不是“页面上出现了某个元素”。
5. **沉淀与归档。** 通过的用例合入独立目录打上 tag；失败 trace 和视频存档，作为下一轮 agent 自修复的上下文。

## 踩坑点

- agent 最爱写“元素可见”式断言，务必在约定里明确要求断言业务结果；
- 不要允许 agent 从 DOM 里猜 selector，探索阶段顺手把 `data-testid` 补齐，比事后补救便宜得多；
- 探索环境要用隔离账号和种子数据，别让 agent 在共享环境里点到“删除”按钮；
- 别迷信一次性全量生成，token 花了，质量完全不可控。

## 可复用建议

- 把选择器规范、断言规范写进项目级的 agent 约定文件（system prompt / 仓库内约定文档），一次投入长期生效；
- agent 生成的用例先进独立目录观察两周稳定性，再决定是否合主干；
- trace / video 归档是让 agent 自修复最有效的上下文，务必自动化保存，不要靠人手动贴链接。

## 总结

Agent 写 E2E 不是“全自动”，而是把最烦的两件事外包出去：从零起 skeleton、根据失败 trace 修 selector。断言质量和业务理解仍然是人的责任。把探索—生成—验证的循环粒度控制住，agent 的产出才配进主干。
