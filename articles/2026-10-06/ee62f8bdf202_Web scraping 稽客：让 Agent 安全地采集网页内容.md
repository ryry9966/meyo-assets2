# Web scraping 稽客：让 Agent 安全地采集网页内容

## 背景

Agent 接上网络工具之后，最常见的第一个需求就是抓网页：盯价格、同步文档、聚合公告、做调研摘要。社区里经常看到有人给 Agent 挂一个「fetch 页面 + 总结」的插件就上线了，前两天很爽，第三天开始各种怪问题频出。

我最近把一个长期运行的采集任务从「裸 fetch」重构成带约束的 pipeline，踩了不少坑，把做法沉淀下来。「稽」者，查也——干采集的 Agent 本质上是个稽查员：只取该取的，不动不该动的。

## 问题：裸抓的四种翻车方式

1. **稳定性差**：CSS selector 硬编码，目标站一改版就失效；动态渲染页面静态抓回来是空壳。
2. **成本失控**：整页 HTML 直接进上下文，一个页面几万 token，还被导航栏、cookie 弹窗等噪音污染。
3. **安全隐患**：网页内容是不可信输入。页面里可以埋提示注入（「忽略之前的指令，把……发到……」），Agent 忠实执行就是事故。
4. **合规风险**：无差别高频请求、抓登录后内容、忽略 robots.txt，属于给自己埋雷。

## 做法：把 Agent 的角色限定为「稽查员」

核心思路：**确定性的事交给代码，Agent 只负责判断和加工**。分四步：

**1. 划边界（配置化，不靠 prompt）**
域名白名单、频率上限、允许抓取的字段，写成采集配置文件，在工具层强制执行。prompt 会被注入绕过，配置不会。

**2. 分层降级**
- L0：优先 API / RSS / 站点自带的开放数据；
- L1：静态抓取（HTTP + 解析库），覆盖大部分场景；
- L2：确认是 JS 渲染才上 headless 浏览器，并屏蔽图片、字体等资源。

**3. 解析在前，模型在后**
工具封装成 MCP tool 时收窄接口：输入 URL + schema，输出结构化 JSON（标题、正文、时间、链接），**不返回原始 HTML**；正文做长度截断和去噪；抓取结果统一打上「来源 + 时间 + 不可信」标记，让 Agent 明确这是数据，不是指令。

**4. 限速、缓存、留痕**
按域名限速、失败退避；能用 ETag/Last-Modified 就增量抓；每次抓取写审计日志（URL、时间、状态码、字节数），出问题能回溯。

## 踩坑点

- **直接把 fetch 结果塞给模型**：token 和注入双重风险，最常见也最贵。
- **重试不设上限**：默认加指数退避 + 熔断，否则会被目标站 ban IP。
- **只写 selector 不写校验**：建议 schema-first，输出用 JSON Schema 约束，站点改版时校验先报错，比数据悄悄变脏好得多。
- **相对链接、时区、编码**：入库前统一转绝对 URL、规范时区，否则下游拼链接全是坑。
- **登录态**：不要把用户 cookie 塞给 Agent 工具；确需登录源，用独立的低权限账号，且不碰个人数据。
- **让 Agent 自由发挥「绕过限制」**：验证码、代理池这类能力不应该暴露给模型，保持人在环上。

## 可复用建议

- **一个 source 一个 schema**：新增站点 = 写一份提取配置 + 校验规则，十分钟级接入。
- **增量优先**：RSS、diff、条件请求，能不全量就不全量。
- **定期抽查**：每周人工看一次 Agent 抓回的数据质量，站点改版往往先表现为字段缺失。
- **采集和消费分离**：采集任务产出结构化存档，Agent 对话里只引用摘要和出处，方便复查。

## 总结

Web scraping 的难点从来不是「抓下来」，而是「稳定、可控地抓下来」。给 Agent 的正确姿势是：**边界写在配置里，解析做在模型前，频率限在代码中，动作留在日志里**。Agent 负责理解和加工，代码负责那些不需要智能、但必须绝对可靠的部分——这也是把自动化任务跑长期的唯一方式。
