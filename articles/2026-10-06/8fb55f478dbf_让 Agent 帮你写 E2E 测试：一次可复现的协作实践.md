## 背景

我们团队维护一个中等规模的前端应用，E2E 测试长期欠债：核心链路只覆盖了登录和支付，其余靠手工回归。手写 Playwright 用例慢、枯燥，写的人往往还不是最懂业务的人。最近我们把 OpenClaw 的 agent 通过 MCP 接到 Playwright 浏览器工具上，做了一轮「AI 起草、人工收编」的补测试实验，两周内补齐了 17 条核心链路用例。本文记录可复现的做法。

## 问题

直接让 agent「给这个网站写测试」基本不可用：它不知道真实业务流，会编造不存在的元素，生成的断言要么恒真、要么极其脆弱。本质问题是 agent 缺少两样东西：**真实的应用状态**和**可执行的验证回路**。

## 做法

1. **圈定范围**：每次只给 agent 一条业务流（如「创建订单并取消」），附一段人工写的验收要点：前置数据、操作步骤、预期结果。
2. **给工具不给答案**：通过 MCP 暴露导航、截图、点击、读取 DOM 等原子工具，让 agent 在测试环境里自己「走一遍」流程，而不是凭想象生成代码。
3. **生成-执行回路**：agent 产出用例后立即在沙箱跑，失败信息回喂给它修选择器和等待条件，最多迭代三轮。
4. **人工收编**：通过的用例进 CR，重点看断言语义是否真的验证了业务结果、选择器是否稳定，合并后纳入 nightly。

## 踩坑点

- **选择器脆弱**：agent 偏爱 text selector，改个文案就挂。约定优先 `data-testid`，兜底用 role。
- **恒真断言**：AI 很容易写出 `expect(visible)` 这类不会失败的断言，CR 时要重点盯。
- **环境漂移**：测试环境数据被手工改过，agent 会把「环境现状」学成「预期行为」，务必用干净的种子数据。
- **迭代失控**：不设上限时 agent 会无限修补，三轮封顶，仍失败就降级为人工处理。
- **上下文过载**：整页 DOM 塞进上下文成本高、噪声大，按需裁剪，只保留结构化摘要。

## 可复用建议

- 把 agent 当初级工程师用：给清晰任务书、可执行反馈、明确验收标准，产出只当草稿。
- 一条流程一次会话，避免上下文互相污染。
- 把「跑测试 → 回读失败 → 修改」做成固定的工具链，别靠人肉搬运报错。
- 分层负责：agent 负责骨架和重复劳动，断言与业务语义必须人写或人审。

## 总结

AI 写 E2E 测试的价值不在「全自动」，而在把覆盖率从一笔欠债变成一份可推进的任务清单。真实收益来自「agent 探索 + 执行器验证 + 人把语义关」这个组合。方法不炫，但每一步都可复现——这正是工程实践该有的样子。
