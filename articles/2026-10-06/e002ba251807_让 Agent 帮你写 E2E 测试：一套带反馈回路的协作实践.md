## 背景

E2E 测试是大多数团队"知道该写但一直欠债"的部分：写起来慢、选择器脆、UI 一改就大面积红。最近我们把 Playwright 和一个通过 MCP 接入浏览器工具的 Agent 组合起来，让它参与测试的生成与修复，跑了一个多月，聊聊真实体感。

## 问题

直接让模型"根据需求写一条 Playwright 测试"，效果通常很差，原因很朴素：

- Agent 没看过真实页面，选择器基本靠猜，`nth-child` 和拍脑袋的文本断言满天飞；
- 生成的测试经常"必过"——它断言了自己刚写进去的内容，等于没有断言；
- 没有执行结果反馈，Agent 写完就交差，对错它自己也不知道。

核心矛盾不是模型不会写代码，而是缺少闭环：**写 → 跑 → 看失败 → 改**。

## 做法：三个角色 + 一条反馈回路

我们把协作拆成三个职责，跑在同一个 Agent 会话里，靠提示词切换：

1. **Explorer（探查）**：通过 MCP 的 browser 工具打开目标页面，抓取可访问性树而非完整 DOM——体积小、语义清楚，还能自然产出 role 级别的稳定定位。输出一份"页面结构摘要 + 推荐选择器"。
2. **Writer（生成）**：拿结构摘要 + 一条用户故事，只生成一个流程的测试。硬性规则写进提示词：禁止 `nth-child`，优先 `getByRole` / `getByTestId`；断言必须校验业务结果（列表条数、跳转 URL、副作用），不允许断言输入回显。
3. **Runner/Fixer（执行与修复）**：调用 `run_tests` 工具跑真实用例，把失败栈喂回去，让它区分三类问题：选择器错、等待策略错、还是产品行为与需求不一致。前两类它修，第三类提 issue 给人。

关键护栏：修复循环最多 3 轮；禁止 Agent 改业务代码来"让测试变绿"；禁止用删断言的方式修复。

## 踩坑点

- **token 爆炸**：一开始把整页 DOM 快照塞进上下文，两轮就爆了。换成可访问性树摘要后，单流程成本降了一个量级。
- **`waitForTimeout` 泛滥**：Agent 很爱写 `sleep(3000)`。提示词里明确要求 web-first 断言（`expect(locator).toBeVisible()`），并在 lint 中禁用固定等待。
- **"完美通过"假象**：有次生成的 8 条用例全绿，人工一看，一半断言是废话。对策：review 时只看断言部分，先删后补。
- **i18n 崩溃**：Agent 偏爱文本定位，切语言全挂。把选择器约定写成仓库里的规范文档，作为系统上下文注入，比临时提示词稳定得多。
- **修复漂移**：第二轮修复时，Agent 偶尔会把"改定位"偷换成"改断言语义"。因此要求每次修复输出 diff 和理由。

## 可复用建议

- MCP 工具面收敛到三四个就够：`get_accessibility_tree`、`run_tests`、`read_failure_log`，多了反而干扰决策。
- 一次只生成一个流程，别让它一口气产整套套件，质量会断崖式下跌。
- 生成结果当草稿看待，走与人工代码完全相同的 review 和 CI 门槛。
- 把选择器规范、断言清单沉淀为项目固定上下文，是投入产出比最高的一步。

## 总结

Agent 写 E2E 的价值不在"替你写"，而在接走最费时的样板劳动：定位、样板代码、跑挂再修。真正决定质量的是反馈回路和人为设定的护栏——Agent 干体力活，人守住断言的意图与边界。目前我们约七成新流程测试由 Agent 起稿、人工修改后合入，维护成本确实降了；但请始终记住，"全绿"从来不等于"测对了"。
