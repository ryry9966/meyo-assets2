## 背景

OpenClaw 的 cron 任务本质上是**定时触发的独立会话**：到点后系统把 instruction 塞给 agent，agent 自己跑完、自己投递结果。和聊天最大的区别是，触发那一刻没有人在线，你不能指望它中途问一句"你是指哪个仓库？"。instruction 就是全部规格说明书。

## 问题

很多 cron 任务失败不是调度问题，而是 prompt 问题。典型症状：

- "每天早上给我整理新闻"，结果每次输出格式都不一样，无法归档；
- 任务跑成功了，结果却发到默认会话，没人看到；
- 数据源当天不可用，agent 编了一段看似合理的内容交差；
- 同一条消息每天重复推送，群里被吐槽。

根源都一样：把 cron instruction 当成了聊天消息来写。

## 做法

我的写法是把 instruction 当作**给值班同事的交接单**，对方不能提问、只能照办。固定五段结构：

1. **目标**：一句话说清这次运行要产出什么；
2. **输入**：数据从哪来（哪个 MCP 工具、哪个 URL、哪个目录），写具体工具名，不要假设 agent 会猜；
3. **边界**：明确只做什么、不做什么，尤其是禁止编造，数据缺失时输出什么占位说明；
4. **输出**：格式（条数、字段、长度上限）、投递渠道（哪个会话/频道）、开头是否带运行日期（方便去重与排查）；
5. **异常**：数据源超时或为空时怎么办——跳过并留一条简短说明，还是触发告警，写死。

举个对比。反例："每天 9 点总结昨天的消息。"正例的关键增补是："读取 `<会话ID>` 中昨日 00:00–24:00（时区 Asia/Shanghai）的消息，输出不超过 10 条要点，每条含话题和结论，以『`<日期>` 摘要』为固定标题，发送到 `<目标频道>`；若消息为空，发送『昨日无消息』，不要臆测内容。"

## 踩坑点

- **日期与时区**：instruction 里写"今天/昨天"必须同时定义时区和边界，否则跨日任务会漂移。
- **没有上下文**：cron 是独立会话，上次运行的结果、你们的聊天历史都不在。需要的背景要么写进 instruction，要么让 agent 先读某个文件。
- **工具依赖**：假设某个 MCP 工具存在，换环境后静默失败。instruction 里显式声明工具，首次运行前手动验证。
- **成本失控**：高频任务加冗长 instruction，token 是按次烧的。指令能压缩就压缩，输出限定条数。
- **静默失败**：任务挂了没人知道。给关键任务加兜底：失败时发告警，或每周跑一次"心跳"任务汇总执行情况。

## 可复用建议

- 先在聊天里手动跑一遍 prompt，确认输出符合预期再转 cron，不要直接上线；
- instruction 存进 Git，和代码一样 review、留变更记录；
- 输出带固定日期标记，既去重又方便事后 grep；
- 新任务从低频开始（每天一次），稳定两周后再提频；
- 定期回看输出质量——prompt 是会"腐化"的：数据源改版、频道改名都可能让它失效。

## 总结

Cron instruction 的本质，是一份交给"不能提问的同事"的 runbook：目标、输入、边界、输出、异常，五要素写全，任务才可靠。写完之后问自己一个问题，如果我是那个凌晨三点被叫起来跑任务的同事，只看这一段话，能一次做对吗？
