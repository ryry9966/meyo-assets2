## 背景

我们的 OpenClaw 实例跑了半年多，接了十几个 MCP 工具，日常任务从代码审查摘要、工单分类到定时巡检都有。早期图省事，所有请求都走同一个云端大模型，一个月下来账单和延迟都不好看——大量任务其实只是结构化抽取和格式转换，用不着那么强的模型。

后来我们把部分流量切到本地模型（vLLM 起的 Qwen 系列），成本降下来了，但也踩过坑：复杂规划任务本地模型接不住，工具调用格式经常错。这篇文章记录我们最终收敛出的一套路由策略。

## 问题

多模型路由的核心难点不是"能不能配"，而是"按什么维度分"。我们试过三种粒度：

- **按任务类型分**：需要事先给每个任务打标，标注本身就有维护成本；
- **按会话分**：粒度太粗，同一个会话里既有规划又有抽取；
- **按 token 长度分**：短任务不等于简单任务。

最后发现比较稳的思路是按 agent 角色分。

## 做法

**1. 角色分层。** 把 agent 分成三类：

- planner（任务拆解、反思、多步规划）→ 云端强模型；
- worker（工具调用、格式化输出、分类抽取）→ 本地模型；
- reviewer（校验 worker 产出）→ 云端模型，但只在低置信度时触发。

**2. 路由配置。** 在 router 配置里按 agent role 绑定 provider，fallback 链设为 local → cloud。注意 fallback 是降级，不是重试。

**3. 敏感数据强制本地。** 凡是输出会落到内网日志的 MCP 工具（比如内部工单查询），在工具元数据里打 `sensitive` 标记，路由层直接锁本地，不走云端。

**4. 度量驱动调整。** 记录每次路由决策：role、model、token 数、重试次数、工具调用成功率。跑两周后按数据调边界，比拍脑袋准。

## 踩坑点

- **本地模型的工具调用格式**：不同模型对 function calling 的输出差异很大。我们加了 schema 校验层，格式不对直接判失败进 fallback，不要试图用 prompt 硬掰。
- **上下文长度**：MCP 工具返回的大 JSON 很容易超本地模型上下文。在工具层做截断和字段白名单，别指望模型自己扛。
- **不要在同一对话链路中途换模型**：风格和指令遵循会漂移。routing 按 agent 绑定，不按单次请求绑定。
- **fallback 风暴**：本地失败切云端、云端限流又切回本地，会形成循环。要加熔断：同一 task 最多切一次，超限直接报错。
- **短任务本地不一定快**：消费级显卡上小模型的首 token 延迟可能比 API 还高，路由前先压测。

## 可复用建议

- 从二八法则入手：先把消耗 token 最多的前两类任务切本地，别一上来全量切。
- 按角色路由比按任务路由好维护，规则数量可控。
- 每个 provider 设独立预算上限，超限告警而不是静默切换。
- routing 日志带上任务 ID 和 agent role，出问题能回放。
- 本地模型升级时，先在灰度 agent 上跑一周再全量。

## 总结

多模型路由的价值不在省多少钱，而在于把"模型能力"当成一种可按需分配的资源。OpenClaw 的配置粒度足够做这件事，关键是想清楚分工边界：规划给强模型，执行给便宜模型，敏感数据不出门，然后用数据而不是直觉去调整边界。我们现在账单降了六成，p95 延迟反而略降——大部分高频短任务不再排队云端了。
