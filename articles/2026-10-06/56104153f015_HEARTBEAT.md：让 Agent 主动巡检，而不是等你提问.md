## 背景

用 OpenClaw 一段时间后，大多数人的用法还是"人找 Agent"：开会前问一句日程、贴段报错让它查。Agent 能力再强，也不主动。OpenClaw 内置了一个很小的机制来改变这件事——heartbeat：守护进程按固定间隔（默认 30 分钟）向 Agent 会话注入一条系统提示，让它去读工作区根目录的 `HEARTBEAT.md`，执行其中到期的事项；如果无事可做，回复 `HEARTBEAT_OK`，这条消息不会推送给你。就这么一个"定时 prompt + Markdown 清单"的原语，把 Agent 从被动应答变成了定时巡检。

## 问题

但很多人写了 HEARTBEAT.md 之后体验很差，常见三种情况：

1. 任务写成"每天看看邮件"，Agent 判断不落地，要么漏执行，要么一天跑八遍；
2. 每次心跳都是一次模型调用，间隔设成 5 分钟，token 账单先于功能崩掉；
3. 任务每次都汇报"一切正常"，一周后你开始无视它，真正的告警反而被淹没。

根因在于：HEARTBEAT.md 的调度判断是模型做的，不是 cron。文件怎么写，决定这套机制是值班员还是噪音源。

## 做法

1. 在工作区根目录建 `HEARTBEAT.md`，每个任务写成 checklist 项，三要素齐全：检查什么、执行窗口、跳过条件。例如：
   ```markdown
   - 检查仓库是否有新增的 CI 失败；仅在出现新增失败时报告；非工作时间跳过。
   ```
2. 文件开头写明默认策略："无事可做时输出 HEARTBEAT_OK；只在异常或有新信息时联系用户。"
3. 在 `openclaw.json` 控制节奏：`agents.defaults.heartbeat.every` 从 30m 起步，观察一两周再调；也可用 `activeHours` 限制心跳时段。
4. 任务动作尽量落在 MCP 工具或脚本上（日历、邮件、git），让模型只做"判断 + 汇总"，不做长任务。
5. 失败要留痕：让 Agent 把巡检结果追加到 `heartbeat-log.md`，而不是只在失败时口头说一句。

## 踩坑点

- **间隔贪短**：每次心跳都带完整会话上下文，30m 是成本与实时性的合理折中；秒级需求请用脚本 + cron，别用心跳。
- **表达模糊**："定期""有空时"会导致执行漂移。写具体时间窗（如 08:00–09:00），并注明时区——容器时区和你的时区可能不一致。
- **心跳与 cron 混用**：精确时间触发（每天 8 点推送）用 cron；"有状态才动作"的巡检（有失败才报）用心跳。混用是告警疲劳的常见来源。
- **大任务阻塞会话**：心跳跑在 Agent 会话里，一个跑 20 分钟的爬虫会把后续心跳全堵住。
- **文件删空即停**：HEARTBEAT.md 为空时 Agent 恒回 OK，机制等于关闭。排查"为什么不动了"，先看文件在不在、有没有内容。

## 可复用建议

把 HEARTBEAT.md 当 SRE runbook 写：每项 = 检查 + 条件 + 动作 + 上报策略；全局控制在 3–6 项；默认"只报异常"；工作区进 git，清单每次修改都可 review。先上 1–2 个低风险任务（如每日日历摘要）跑一周看日志，再逐步加。

## 总结

HEARTBEAT.md 不是新框架，只是"定时 prompt + 一个 Markdown 文件"，但它把主动权交回了 Agent。它的上限和下限都取决于你怎么写这个文件：写得像 runbook，它就是不知疲倦的值班员；写得含糊，它就是烧 token 的背景噪音。小步上线、留日志、只报异常，是让它长期可靠的三条底线。
