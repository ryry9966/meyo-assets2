## 背景

我们团队每天要发一份日报，内容散落在 git 提交、工单系统、服务日志和聊天记录里。以前靠人肉汇总，费时且经常漏项。接入 OpenClaw 后，我把它改造成一条定时流水线：cron 触发 Agent，通过 MCP 工具拉日志，结构化后由模型写成固定格式的报告，最后推送到群 channel。稳定跑了一个月，每天省下 20-30 分钟，覆盖率比人工汇总更稳定。

## 问题

最初的做法很朴素：把当天所有原始日志塞给模型，让它"总结成日报"。跑了三天就暴露三个问题：

1. token 消耗大，日志一多就被截断，报告内容随机缺块；
2. 模型偶尔"补写"日志里不存在的事件，无法溯源；
3. 输出格式每天漂移，下游解析和归档都难受。

根因是分工错了：模型被放在了它不擅长的"采集 + 清洗"环节。

## 做法

现在的流水线分四层，核心原则是：**代码能做的确定性工作，不交给模型。**

1. **采集层（定时 + MCP 工具）**：OpenClaw 的 cron 任务每天 08:30 触发，Agent 通过只读 MCP 工具拉取各数据源——git log、工单 API、服务日志文件。每个源落一份原始产物 `raw_<source>.json`。
2. **清洗层（纯脚本）**：jq / Python 脚本把原始数据归一成统一 schema：`{时间, 主体, 动作, 对象, 状态, 源ID}`，去重、按行数截断、按项目分组，产出 `clean.ndjson`。这一步零模型参与。
3. **汇总层（Agent）**：模型只读清洗后的结构化摘要，往固定 JSON schema 里填内容。Prompt 里只有规则：只允许引用输入中存在的条目、必须带源 ID、无数据就写空。输出过 schema 校验，失败自动重试一次。
4. **输出层**：模板渲染成 Markdown——头部三行 TL;DR，中间按项目分组的明细，尾部附"数据源健康"小节（哪个源失败、各拉了多少条）。先归档到按日期命名的文件，再推送。

时间窗口显式声明为 `[T-1 00:00, T 00:00)` 并写进报告头部，避免"昨天"的歧义。

## 踩坑点

- **时区边界**：cron 一开始跑在 UTC，"昨天"的边界砍掉了晚间提交。后来所有时间在脚本层统一转本地时区，窗口参数显式传入。
- **格式漂移**：即便有 schema，早期模型偶尔多输出一个字段。改为校验失败整单重试，连续两次失败就推送降级版（纯清单），而不是静默失败。
- **重复推送**：手动重跑导致群里出现两条日报。现在每次运行生成 run_id，推送前先查归档里是否已有同日期的成功记录。
- **静默失败**：流水线挂掉最危险的表现是"今天没日报"，但没人第一时间发现。加了心跳检查：超过 09:00 没有成功产物，就往另一个 channel 报警。
- **权限过大**：最初 MCP token 能写仓库，纯属隐患。所有采集工具一律只读。

## 可复用建议

- **中间产物全落盘**：raw / clean / digest 三级产物按日期存档，任何一天的报告都能离线复现和排查。
- **schema 带版本号**：格式调整时升版本，下游按版本兼容解析。
- **Prompt 只放规则，数据走结构化输入**：别把数据拼在 prompt 字符串里，省 token 也好审计。
- **先结论后明细**：三行 TL;DR 的打开率远高于直接甩明细。

## 总结

这条流水线的价值不在于"让模型干活"，而在于划清了确定性代码与 LLM 的边界：采集、清洗、分发交给代码保证可靠性，模型只做它擅长的归纳与表达，且被 schema 约束。日报只是载体，同样的分层结构可以直接迁移到周报、告警摘要、变更通告等场景——换数据源和模板即可。如果你也在 OpenClaw 上做定时任务，建议先从单一数据源跑通全链路，再逐步扩源。
