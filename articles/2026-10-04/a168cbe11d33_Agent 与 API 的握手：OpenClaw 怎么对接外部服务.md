## 背景

OpenClaw 这类 Agent 框架的价值不在模型本身，而在把模型接进真实环境：读数据库、调内部接口、触发自动化流程。对接外部服务的路径主要有两条：**MCP server**（标准化的工具协议，可跨项目复用）和 **OpenClaw 插件/技能**（本地代码直接注册为工具）。选哪条路，直接决定后续的维护成本。

## 问题

实际对接时，难点从来不是“发一个 HTTP 请求”，而是三件事：

1. **工具契约**：模型只按 description 和参数 schema 理解工具，写得含糊它就乱传参；
2. **认证与密钥**：key 放哪、怎么轮换、会不会被打进日志；
3. **失败语义**：超时、限流、部分成功之后，模型拿到什么信息才能自我纠正。

## 做法

**第一步，选路径。** 希望跨项目复用的能力（比如代码仓库、数据库、搜索），封装成 MCP server，stdio 本地跑或远程部署均可；带状态、带权限校验的内部业务逻辑，写成插件更直接。

**第二步，收窄工具面。** 一个工具一个动词：`list_issues`、`create_issue`，不要做 `manage_issues` 靠参数分支。参数用强类型 schema，枚举值写全。description 是写给模型的操作手册，不是写给人看的 API 文档。

**第三步，隔离认证。** 密钥走环境变量或系统 keychain，绝不进配置文件和对话上下文；token 过期在适配层自动刷新，别把这个决策丢给模型。

**第四步，定义失败语义。** 所有外部调用设超时（读 10s、写 30s 起步），错误返回结构化信息：错误码、是否可重试、建议的下一步。写操作加幂等键，或内置“先确认再执行”。

**第五步，控制返回体积。** 外部 API 动辄返回几十 KB 的 JSON，直接塞上下文又贵又乱。适配层做字段裁剪和分页，只留模型决策需要的部分。

**第六步，可观测。** 记录每次工具调用的参数、耗时、状态码。出问题时，这是唯一靠得住的证据。

## 踩坑点

- description 只写“获取数据”，模型开始编造参数；改成带示例和边界说明，问题立减。
- 重试导致重复建单：写操作没做幂等，网络抖一次就双份。
- 远程 MCP server 断连重连后工具列表不刷新，表现为“工具突然消失”，重启会话才恢复。
- 日志打印了完整请求头，把 Authorization 一起带了出去。

## 可复用建议

- 先用只读工具跑通全链路，再逐步放开写操作；
- 已有 HTTP API 不必重写，写一个薄适配层包成 MCP 工具即可；
- 工具 schema 当代码维护：进版本库、走 review、留变更记录；
- 备 5–10 条脚本化用例（输入 → 期望的工具调用与结果），每次改动跑一遍防回归。

## 总结

对接外部服务的本质，是把“不可靠的网络世界”翻译成“模型可理解的确定性契约”。OpenClaw 提供了 MCP 和插件两条路，剩下的功夫全在工程细节：窄接口、明确的失败语义、密钥隔离、可观测。这些做扎实了，Agent 才敢在生产环境里替你干活。
