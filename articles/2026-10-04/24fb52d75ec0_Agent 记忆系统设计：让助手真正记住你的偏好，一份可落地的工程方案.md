这个问题看起来简单，做起来全是细节。下面是我给自己 OpenClaw 实例做记忆系统后沉淀的一版设计，供参考。

## 背景

大模型本身是无状态的，会话一结束，它对“你是谁、你喜欢什么”的认知就清零了。OpenClaw 这类长期运行的助手，价值很大程度上取决于能否跨会话积累对你的了解：技术栈、代码风格、部署环境、沟通习惯。上下文窗口再大，也不可能把历史对话全塞进去——记忆系统的本质，是在有限 token 预算内决定**什么值得记住、什么时候取出来**。

## 问题：三种常见做法为什么不行

1. **全量塞上下文**：token 成本线性上涨，大量无关历史还会稀释注意力，助手反而变笨。
2. **对聊天记录做向量检索**：能召回片段，但召回的是“当时说过的话”，不是“稳定的偏好”。三个月前随口提的部署细节，和“我永远用 pnpm”混在同一个池子里，检索质量不可控。
3. **定期总结**：摘要天然丢细节，两次总结之间的信息直接蒸发。

核心矛盾：写多了污染，写少了没用，检索不准不如不检索。

## 做法：分层记忆 + 受控写入

我实现了一个 memory MCP server，分三层：

- **工作记忆**：当前会话上下文，不持久化。
- **用户画像**：结构化键值事实，如 `语言偏好: zh-CN`、`包管理器: pnpm`、`部署目标: 家庭服务器`。每轮会话必注入，控制在 500 token 以内。
- **情节记忆**：按会话归档的摘要与原文，SQLite + sqlite-vec 混合检索，按需召回 top-k，加时间衰减权重。

**写入路径是关键**。不要让模型实时随手写，而是每 N 轮或会话结束时跑一次抽取：

1. 只抽取“跨会话仍然成立”的稳定偏好，一次性任务上下文直接排除；
2. 与现有画像比对去重，冲突项标记待确认；
3. 高置信度直接更新，低置信度进缓冲区，下次会话开头向用户口头确认一句；
4. 每条记忆带 `source / confidence / updated_at`，冲突时新时间戳覆盖旧值。

同时必须提供管理入口：`memory show`、`memory forget <key>`、`memory export`。用户能看、能删，这是信任的基础。

## 踩坑点

- **记忆污染**：早期我让模型“觉得有用就存”，两周后画像里全是“用户上周在调试某个 bug”这类垃圾。解法是把抽取标准写死：只存稳定偏好，低于置信度阈值不入库。
- **记忆变成注入面**：记忆会被注入 prompt，如果助手读过某个网页，页面里的恶意指令可能被当成事实存下来，之后每次会话都被执行。务必把记忆当数据处理（转义、标注来源），不要让它以指令形式进入上下文。
- **冲突处理偷懒**：用户换了主力语言，只追加不覆盖，助手就会在新旧偏好之间反复横跳。冲突检测比检索本身更重要。
- **纯向量召回噪声大**：关键词 + 向量混合、加 recency 权重，效果好一截。
- **画像无限膨胀**：设条目上限，超限时按“最近被引用频率”淘汰。

## 可复用建议

- **先别上向量库**。一个 YAML 文件存结构化画像，就能满足 80% 的个性化需求。先跑通写入策略，再补检索。
- **schema 先行**：固定几个类别（环境、偏好、工作流、长期项目），比自由文本好维护得多。
- **把“被使用率”当指标**：某条记忆注入后从未影响过回复，它就该被淘汰。
- **写入永远比读取保守**：读错了最多浪费 token，写错了会持续污染之后每一次会话。

## 总结

Agent 记忆更像数据工程问题，而不是模型问题：小而准的结构化画像、带确认的写入策略、可见可删的管理入口，比一个大而全的向量记忆库实用得多。先守住三条底线——每条记忆有来源、有时间、可被用户删除——其余都可以慢慢迭代。
