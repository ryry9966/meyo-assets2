## 背景

信息源越订越多，真正读完的越来越少。RSS 是目前少数不被算法干预、完全自主可控的订阅协议，但它的原始形态只是"把条目递到你面前"，读还得自己读。LLM 出现后，"让模型先读一遍、产出结构化摘要"变得可行。这篇记录我用 OpenClaw 搭的一条 RSS → AI 摘要 → 推送管线，重点讲工程细节而非概念。

## 问题

直接把 RSS 条目丢给 LLM，会撞上几个现实问题：

1. **成本失控**：一条 feed 每天几十条，全部原文进 prompt，token 消耗很快上去
2. **摘要质量平庸**：模型默认输出"本文讨论了……"式废话，扫一眼等于没读
3. **重复推送**：服务重启后游标丢失，同一条目推两次
4. **链接幻觉**：让模型复述 URL，它会编造

## 做法

管线拆成四个独立阶段，每阶段可单独替换：

**1. 抓取**：cron 定时（每 4 小时）拉取 OPML 里的全部 feed，统一带 UA 和超时。单 feed 失败只记日志，不阻塞整体。

**2. 去重与过滤**：以 entry 的 guid / link hash 为主键写入 SQLite。入库前过两道筛：关键词黑名单 + 正文长度阈值（太短的通常是广告位）。只有新条目进入下游。

**3. 摘要**：不逐条调用，而是**按源分批**——同一 feed 的 10-20 条合并成一次请求，要求输出 JSON 数组，每条含一句话摘要、是否值得深读、分类标签。对技术类源追加一句"只保留含代码或可操作内容的条目"，废话明显减少。

**4. 推送与归档**：结果经 webhook 推到 IM，每条附原文链接。链接一律取自 RSS 原始数据，绝不让模型生成。摘要同时落库，形成可检索的底稿。

在 OpenClaw 里，我把抓取和去重封装成了 MCP tool，agent 可以在对话中按需调用"拉一下今天的技术源"——定时管线和交互查询共用同一套存储，不用维护两份逻辑。

## 踩坑点

- **不少 feed 只给 summary 不给全文**，摘要质量取决于模型能否看到正文。抓取后接一步正文提取（readability 类工具），失败再退回 summary
- **pubDate 格式混乱**：有的 feed 用 RFC 822，有的干脆缺日期。别用日期做去重排序，guid 更稳
- **分批摘要会稀释单条信息**，重要条目加一条分支：正文超过阈值就单独处理
- **模型输出 JSON 偶尔不合法**，必须 parse 失败重试，且重试时缩小 batch
- **IM 有消息长度限制**，超限要拆分或折叠，别等推挂了才发现

## 可复用建议

1. 四阶段解耦是最关键的决策：换模型、换推送渠道都不牵动其他环节
2. SQLite 一个文件解决游标和归档，别上重数据库
3. Prompt 按源类别做模板，一个通用 prompt 通吃所有源是幻想
4. 先接 5-10 个源跑两周，观察误报率和成本，再扩源
5. 日志保留原始 entry ID 与摘要的映射，出问题能溯源

## 总结

管线跑起来后，每天的阅读流程变成：扫一遍摘要 → 点开两三条值得深读的原文。模型没有替代阅读，但把"筛选"这个最耗时的环节压缩了九成。整套系统没用任何重型框架，一个 cron + SQLite + 一个 LLM client 就够了——自动化管线的价值在于长期稳定运行，而不是架构炫技。
