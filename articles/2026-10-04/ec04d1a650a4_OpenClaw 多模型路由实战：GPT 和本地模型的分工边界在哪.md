## 背景

OpenClaw 的 gateway 层天然支持挂多个 provider，但社区里常见的做法是两个极端：要么图省事全部走 GPT，月底账单难看；要么激进全换本地模型，结果 agent 循环跑飞、MCP 工具调用解析失败，最后又改回去。多模型路由的前提是承认一件事：**不同任务对模型能力的需求本来就不一样**，全局只挂一个模型本身就是配置错误。

## 问题

真正的难点不是"能不能路由"，而是判断标准要可执行。"复杂任务用 GPT、简单任务用本地"这种话等于没说。你需要的是一条能落进配置文件的边界。

## 做法

**1. 先分类任务，再分类模型。** 把 agent 的日常工作列出来：

- 消息摘要、日程整理、格式转换、抓取结果初筛 → 本地模型（如 Ollama 跑 Qwen）完全够用
- 多步工具编排、代码生成、长上下文分析、对外输出内容 → 走 GPT

**2. 路由粒度放在 skill 层，不做全局。** OpenClaw 的 skill 可以显式指定模型，让分工变成配置而不是代码：

```yaml
skills:
  digest:        # 摘要，高频低风险
    model: ollama/qwen2.5:14b
  code-gen:      # 代码生成，质量敏感
    model: openai/gpt-4.1
```

**3. 加单向降级链。** GPT 限流或超时时 fallback 到本地，保证自动化流程不断。反向不要做——本地失败就升级 GPT，成本会失控，宁可让这一步失败重试。

**4. 打日志。** 每个请求记录模型、token 用量、延迟、是否触发 fallback。跑一周再回头调路由表，比拍脑袋准得多。

## 踩坑点

- **本地模型的 function calling 输出经常不合规范**，MCP 工具调用解析失败。解法：输出校验 + 一次重试，仍失败就把这一步路由回 GPT。
- **上下文截断伪装成"模型变笨"**。本地模型 8k 上下文，长对话塞进去悄悄截断，表现和推理能力差一模一样。先查 token 数再骂模型。
- **本地模型在多轮循环里容易重复调用同一工具**，务必设最大循环次数。
- **embedding 别混用**。同一个索引既用云端 embedding 又用本地 embedding，检索结果会整体错乱，只能重建。
- 用小模型当路由分类器可以，但判断 prompt 压到一句话以内，否则路由本身的开销吃掉收益。

## 可复用建议

1. 路由表做成数据文件，别硬编码在 skill 里，改起来快，也方便回滚。
2. 一条铁律：**质量敏感路径（发消息、写文件、花钱的操作）固定大模型；可丢弃的中间步骤（摘要、打分、去重）用本地。**
3. 保留人工 override 通道，指定会话强制走某个模型，方便 A/B 对比效果。
4. 路由表是活的，每月看一次成本和失败率再调整。

## 总结

多模型路由不是省钱技巧，而是把"模型能力"当成资源来分配的工程问题。先按任务类型分类，在 skill 层绑模型，配单向降级链和完整日志——这套组合拳下来，成本降一半以上、质量不塌，比任何花哨的"智能路由"框架都实在。先跑起来，再优化。
