## 背景

OpenClaw 的 cron 作业，本质是"定时触发的单轮对话"：到点后系统把 instruction 作为 prompt 喂给 agent，跑完把结果投递到指定会话。机制很简单，但社区里不少 cron 任务跑起来不是空转就是刷屏。排查下来，问题大多不在调度表达式，而在 instruction 的写法——很多人按"给自己的备忘录"来写，但 cron 执行时是另一个语境。

## 问题：三种典型失败

1. **上下文缺失**："总结一下今天群里聊了什么。"cron 默认在隔离会话里冷启动，没有"今天""群里"的指代，agent 只能瞎猜或反问。
2. **输出失控**："检查一下服务器状态。"没有任何输出约束，agent 把几十行日志原样贴进群聊。
3. **静默失败**：instruction 里让它调某个 MCP 工具，工具当天挂了，agent 编了个像模像样的结果发出来，没人发现。

## 做法：按"值班交接单"五段式写

一段能稳定跑的 cron instruction，建议固定包含五段：

1. **目标**：一句话说清这次要产出什么，动词要具体（生成、核对、投递），别用"看看""了解一下"。
2. **数据来源**：读哪个文件、调哪个工具、查哪个路径，全部显式声明。cron 会话没有上文，输入不能靠"它应该知道"。
3. **输出约束**：行数上限、格式（列表/表格/一句话）。投递到 IM 的任务，控制在十行以内。
4. **投递目标**：写明发到哪个会话或渠道，不要依赖默认投递。
5. **异常兜底**：数据为空、工具调用失败时怎么办——发一条简短失败说明，而不是臆测或沉默。

另有两个硬性要求：让 agent 先运行 `date` 确认当天日期和时区，别假设它知道"今天"；跨次运行需要状态的（比如"上次处理到的位置"），用 workspace 文件做载体，先读后写，不要指望会话记忆隔天还在。

## 踩坑点

- **指代失效**："按上面说的""接着刚才"在 cron 里全部无效，这是第一大坑。
- **时区错位**：cron 表达式按服务器时区解释，agent 又可能按 UTC 理解"早上九点"，两边都要写死。
- **一单多任务**：一个 instruction 塞三件事，任何一件失败，整个作业就不可信，拆成多个 cron。
- **密钥进 prompt**：instruction 会被记录和展示，凭证走环境变量或文件引用。
- **不试跑直接上线**：先用一次性手动触发跑通全链路，再开周期调度。

## 可复用建议

一个我实际在用的模板，替换占位符即可：

```
【目标】每个工作日生成一次 X 摘要
【时间】先运行 date 确认日期，时区 Asia/Shanghai
【数据】读取 ~/notes/<date>.md，调用 MCP 工具 Y
【步骤】拉取数据 → 按主题归类 → 挑出前 3 条
【输出】不超过 10 行，每行一条，格式「主题：一句话」
【投递】发送到 #daily 频道
【异常】数据为空或工具失败时，只发"今日数据缺失"，禁止编造
```

再补三条经验：

- 写完自问："一个第一次上班、没有记忆的实习生，拿这句话能不能干对？"能，就能跑。
- 改版时保留旧输出文件做对照，方便回归验证。
- 投递宁少勿多，日报合并成一条，比一小时五条消息体面得多。

## 总结

cron instruction 的本质，是把"给自己看的备忘录"改写成"给没有记忆的值班同事看的交接单"：目标、来源、输出、投递、兜底，一段不能少。调度表达式只决定它几点醒，instruction 才决定它醒来后干的是活，还是事故。
