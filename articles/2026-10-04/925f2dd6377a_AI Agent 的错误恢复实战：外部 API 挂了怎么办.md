## 背景

自动化任务跑久之后会发现一个规律：流程本身很少出问题，出问题的几乎都是外部依赖。OpenClaw 的插件、MCP 工具、定时任务背后接的是 LLM 服务商、搜索、推送这些第三方 API，任何一个挂掉，整条链路就断在那里。

生产环境里 API 故障不是概率问题，是时间问题。区别只在于故障发生时，你的 Agent 是优雅降级，还是当场编数据。

## 问题

最常见的三种坏行为：

1. **推理循环里死重试**：工具报错，模型理解为“再试一次”，反复调用直到 token 烧完。
2. **幻觉兜底**：API 没返回，模型自己编一个看起来合理的值继续跑，下游全被污染。
3. **假成功**：任务被标成“已完成”，实际一半步骤失败，三天后想排查已无从下手。

根源是同一个：重试和恢复的逻辑被交给了模型，而它本该属于代码层。

## 做法

**1. 先分类，再重试。** 429/5xx/超时可重试；401/403/400 重试没有意义，直接告警。一个判断函数就能省掉大部分无效重试。

**2. 重试放在工具封装层，指数退避加抖动。** 在插件或 MCP server 里包一层：

```python
for attempt in range(3):
    try:
        return call_api()
    except RetryableError:
        sleep(2 ** attempt + random.random())
raise ToolError("api_unavailable", retryable=True)
```

中间的多次重试对模型不可见，上下文里只出现一次最终失败。

**3. 加熔断。** 连续失败 N 次就短路，冷却期内快速失败。多个定时任务共享同一个下游时尤其需要，否则大家会在同一个限流窗口里互相踩。

**4. 给模型结构化错误，而不是原始报错。** 返回 `{"ok": false, "error": "api_unavailable", "retryable": true, "retry_after": 30}`，别把两百行 HTML 错误页塞进上下文——浪费 token，还可能被当成数据解读。

**5. 降级而非中断。** 提前想好三选一：切备用 API、返回标注“可能过期”的缓存、返回部分结果并列出失败项。让 Agent 或用户基于“知道什么、不知道什么”做决策。

**6. 长任务可断点续跑。** 中间状态落盘，恢复时从失败步骤继续，别从头再来。

## 踩坑点

- **没加抖动**：定时任务整点触发、退避周期一致，下一轮又在同一秒撞限流。随机偏移必须有。
- **对 401 重试**：烧光配额还拖慢任务。鉴权问题要单独的检测和告警路径。
- **客户端超时太长**：默认 120s 超时会让 Agent 假死。外部调用建议 10–30s，超时走重试逻辑。
- **错误页写进记忆**：下次检索时被当上下文捞出来。错误信息一律截断，只留 code 加一句话。
- **降级数据不标注**：缓存兜底没错，但下游拿到过期数据以为是实时的，决策就歪了。字段里多一个 `stale: true`。

## 可复用建议

- 所有外部调用走同一个重试/降级工具函数，按插件配置重试次数和超时，别每个插件各写一套。
- 定一个工具返回契约：`{ok, data, error: {code, retryable, retry_after}}`，系统提示词里写清“可重试错误最多主动重试一次，然后上报”。
- 长任务启动前跑一次 preflight 健康检查，依赖不通就别启动。
- 失败日志带任务 ID，事后能复盘“这一单为什么没发出去”。

## 总结

错误恢复是基础设施工作，属于代码层而不是提示词层。分类、退避、熔断、降级、断点续跑——这五件事在代码里做扎实，模型只需要面对干净的错误契约做策略判断。API 一定会挂，区别在于挂的时候，你的 Agent 是停机，还是绕行。
