## 背景

跑 Agent 做自动化时，最容易被忽视的不是模型能力，而是“环境认知”。同一份任务描述，在你的 Mac 上能跑通，换到一台 Linux 服务器或同事的 Windows 机器就翻车——不是 Agent 变笨了，而是它对本地环境的假设全错了。

tools.md 的思路很简单：把机器相关的事实写成一个约定文件，让 Agent 动手前先读它。它和 AGENTS.md 一脉相承，但更聚焦“工具与环境”这一层。和 MCP 互补理解会很清晰：MCP 告诉 Agent 有哪些工具，tools.md 告诉它这台机器上这些东西怎么用、哪里不能碰。

## 问题

不写 tools.md，Agent 只能靠猜：

- 用 brew 还是 apt？路径在 /usr/local 还是 /opt？
- Python 是 `python` 还是 `python3`？有没有 venv？
- 哪些目录可写，哪些配置绝对不能动？

猜错的代价是反复试错、执行脏命令，甚至在错误目录里留下文件。更麻烦的是这些“猜测”不会沉淀，每次会话从头再来，多机环境互相污染。

## 做法与步骤

1. 在项目或用户根目录建 tools.md，只写事实，不写教程。
2. 按固定结构组织：系统信息、包管理器、常用命令、路径约定、禁区。
3. 写一个检测脚本，让 Agent 首次运行生成初稿，再人工校对——比手写快且不容易漏。
4. 环境差异用分层覆盖：通用模板 + 机器专属覆盖文件（如 tools.local.md），后者加入 .gitignore。
5. 在系统提示里加一句硬规则：动手前先读 tools.md，与环境冲突时以它为准。

一个最小可用的片段：

```markdown
# tools.md
## OS
- macOS 14, Apple Silicon
## 包管理
- 优先 brew；Node 由 fnm 管理，禁止全局直装
## 路径
- 项目统一在 ~/work；临时产物放 /tmp/agent，禁止写 home 根目录
## 禁区
- 不动 ~/.ssh、~/.zshrc；改配置先输出 diff，确认后再执行
```

## 踩坑点

- **把密钥写进 tools.md。** 它会被完整读进上下文，等于明文外泄。密钥走环境变量，文件里只写“密钥从 XX 变量读取”。
- **写成文档而不是事实清单。** 大段说明 Agent 未必细读，短句加硬约束（禁止/必须/优先）才有效。
- **忘记分层。** 团队共享一份文件，个人路径各不相同，最后互相覆盖。必须拆成 base 和 local 两层，覆盖顺序固定：内置默认 < 仓库 tools.md < 机器 tools.local.md。
- **长期不更新。** 系统升级后工具链变了，过期的 tools.md 比没有更危险。建议加一个“最后校验日期”字段，超期让 Agent 主动重跑检测脚本。

## 可复用建议

- 检测脚本 + 生成模板抽成小工具，新机器一键出初稿，人工只做增量修正。
- 每条约束尽量写成“可判定”的规则，减少 Agent 自由发挥的空间。
- 每次翻车后把原因补进禁区清单——tools.md 应该是事故驱动的活文件，而不是一次性文档。

## 总结

tools.md 本质上是给 Agent 补一份“机器说明书”：环境事实集中、差异分层管理、敏感信息隔离。它不提升模型能力，但能把“换个环境就翻车”这类低级损耗消掉大半。建议从一个十行以内的最小版本开始，跑两周，再按实际翻车记录逐步补充。工程上最省心的做法，往往就是把这些隐性知识显式化而已。
