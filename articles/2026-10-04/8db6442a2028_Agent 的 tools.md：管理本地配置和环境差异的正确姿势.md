## 背景

OpenClaw 的 Agent 启动时会把工作区里的一组 Markdown 当作长期上下文读进去：SOUL.md 管人格，AGENTS.md 管行为约束，而 TOOLS.md 的定位是告诉 Agent——这台机器上工具到底怎么用。它不是插件清单，也不是配置文件，本质上是写给模型看的环境说明书。

## 问题

模型对环境的默认假设经常是错的，常见三类翻车：

- **路径和包管理器猜错**：在 NixOS 上让 Agent `apt install`，或者把 venv 写成系统 Python。
- **多机环境漂移**：笔记本是 macOS + Homebrew，家里服务器是 Debian，VPS 只有 2G 内存没装 Docker。同一份指令换台机器就跑不通。
- **口头约定没落盘**：你记得"跑爬虫前先挂代理脚本"，Agent 不记得。

这些问题靠每次对话临时修补很脆弱。TOOLS.md 的价值就是把这类知识落成一份持久、可版本管理的文档。

## 做法

推荐"一份模板 + 每机覆盖"的分层结构：

1. 建一个仓库，放 `tools.base.md`（跨机器通用：编码约定、常用命令模板、禁止事项）和 `tools.<hostname>.md`（每机差异：路径、GPU、内存上限、代理状态）。
2. 各机器工作区里用符号链接或启动脚本把两份文件拼装成实际的 TOOLS.md。
3. 每个条目写成可执行的精确命令，而不是形容词。不要写"用合适的 Python"，要写"统一用 `uv run`，解释器在 `~/.local/bin/python3.12`"。
4. 文件开头维护一个 5–10 行的"环境事实"块：OS、包管理器、GPU、内存、网络代理、最后更新日期。
5. 配一个 `probe.sh` 之类的探测脚本，让 Agent 接手新任务前先跑一遍，用实测结果修正文档，而不是凭记忆回答。

改完环境立刻更新对应条目并提交 git，把 TOOLS.md 当代码对待。

## 踩坑点

- **别放密钥。** TOOLS.md 会整份进入模型上下文，还可能随工作区同步备份。凭据一律走环境变量或密钥管理器，文档里只写"从哪读"。
- **别写成散文。** "网络有时候不太好"模型没法执行，要写成"上传超过 10MB 时改走备用通道"。
- **控制篇幅。** 这份文档每次会话都吃 token，建议硬性限制在 100 行以内，冷知识挪到单独文档按需引用。
- **别和 AGENTS.md 抢职责。** 行为约束（如"不要 sudo"）放 AGENTS.md，环境事实放 TOOLS.md，两边写重了会出现互相矛盾的指令。
- **警惕过期信息。** Agent 对文档信任度很高，文档错了它将错就错。给易变条目标注日期，存疑时先 probe 再动手。

## 可复用建议

- 新机器迁移时复制模板、只改差异块，十分钟完成，不要从零手写。
- 团队场景：base 文档入库共享，个人差异文档留在本地不提交。
- 定期让 Agent 自己审计 TOOLS.md：跑探测脚本、对照实际输出、列出过时条目，比人肉维护省力得多。

## 总结

TOOLS.md 不是配置文件，而是一份持续维护的机器说明书。核心原则三条：**事实与约束分离、精确命令优于模糊描述、文档可验证可版本化**。做到这三点，Agent 跨机器、跨环境干活时的翻车率会显著下降。
