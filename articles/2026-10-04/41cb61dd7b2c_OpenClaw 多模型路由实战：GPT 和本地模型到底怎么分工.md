## 背景

OpenClaw 的模型配置是开放的：可以同时接云端模型（GPT 系列、Claude 等）和本地推理（Ollama / llama.cpp / vLLM）。很多同学的默认做法是二选一——要么全走云端旗舰，要么出于成本和隐私全切本地。自动化跑一段时间后问题就暴露了：全云端，cron 任务每天几百次调用，账单难看；全本地，复杂任务质量明显掉线，工具调用经常失败。

## 问题

真正的需求不是"选哪个模型"，而是按任务特征分流：

- **简单任务**（格式化、信息抽取、定时摘要、关键词分类）：本地足够，快且免费
- **中等任务**（多轮工具调用、文档问答、代码阅读）：中档模型即可
- **复杂任务**（多步规划、架构级代码生成、模糊指令理解）：旗舰模型才稳
- **隐私敏感**（本地文件内容、聊天记录、密钥上下文）：必须留在本地

## 做法

1. **先给任务分层。** 梳理你的 skill / 自动化清单，按上面四类打标签。多数人的结论是：70% 的调用量其实落在第一层。
2. **默认模型设为本地。** OpenClaw 的模型配置支持默认 provider 加按 agent 覆盖：把心跳、定时任务、低风险 skill 指到本地；主 agent 会话指向云端旗舰。
3. **给复杂任务开显式出口。** 在 skill 配置或 prompt 模板里声明该任务用旗舰模型，别指望模型自己"知道自己不行"。
4. **配 fallback 链。** 云端限流或断网时回落本地，保证自动化不中断。反方向不建议——本地失败就升级云端，很容易变成隐性成本黑洞。

## 踩坑点

- **小本地模型的 tool call 很脆**：JSON 结构经常不合法。先在你的真实工具集上跑通，必要时加 schema 校验加一次重试。
- **上下文窗口错配**：本地 8k 模型接上长记忆后静默截断，表现为"突然失忆"。上线前用最长会话实测一遍。
- **别信"本地更快"**：笔记本 GPU 在长输出时 tokens/s 可能远低于云端 API。按实测延迟分流，不按信仰。
- **Embedding 必须统一**：本地和云端混用 embedding 模型，RAG 检索直接乱掉。全链路锁定一个。
- **不要用"路由 LLM"判断该用哪个模型**：判断本身就是一次调用。简单静态规则就够。

## 可复用建议

- 先静态规则，跑两周再谈动态路由。用 OpenClaw 日志记录每次调用的模型、延迟、token 数，数据会告诉你阈值在哪。
- 把分层配置当代码管理，季度回顾一次——模型迭代很快，半年前的分层可能已经失效。
- fallback 要幂等：回落时跳过已完成的工具调用，避免重复执行产生副作用。

## 总结

多模型路由不是炫技，是成本、质量、隐私三者的工程权衡。OpenClaw 的按 agent 模型覆盖加 fallback 机制已经把基础设施铺好了，剩下的是把你的任务清单诚实地分一遍层。结论很简单：**例行公事给本地，难活脏活给旗舰，敏感数据不出门。**
