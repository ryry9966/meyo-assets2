## 背景

用 OpenClaw 搭 Agent 跑了一段时间后，大多数人的模型配置都会经历同一个阶段：一开始全量走 GPT，账单和延迟随任务量线性上涨；后来为了省钱和数据不出机器，把一部分流量切到本地模型（Ollama / vLLM 起的 Qwen、DeepSeek 蒸馏版），结果 Agent 在工具调用环节频繁翻车。多模型路由要解决的不是"哪个模型更好"，而是"哪类请求配哪个模型"。

## 问题拆解

按实际经验，Agent 一次执行的负载大致分四类：

- **规划与复杂推理**：步骤编排、失败后的重试决策，对推理能力敏感；
- **工具调用执行**：参数抽取、结构化输出，格式正确性比"聪明"更重要；
- **高频小任务**：摘要、分类、打标签，量大但单次价值低；
- **Embedding / 检索**：一旦上线就不该随便换。

全走 GPT，小任务烧钱还受限速；全走本地，复杂规划扛不住、长上下文装不下。

## 做法

1. **先给任务打标**。在 OpenClaw 的 workflow 和插件里，给每个节点声明 task type（plan / tool / cheap / embed）。这是路由依据，比按 prompt 长度瞎猜靠谱得多。
2. **建模型池，显式绑定**。gpt-4o 这档绑 plan 节点；本地 7B~14B 绑 tool 和 cheap；embedding 单独固定一款写进配置，不轻易动。
3. **给本地模型做格式约束**。用 vLLM 的 guided decoding 或 Ollama 的 structured output 强制 JSON schema，Agent 侧再包一层校验加一次重试。
4. **配 fallback 链，别裸切**。本地超时或校验连败两次就升级到云端，同时记路由日志：模型、耗时、token 数、失败原因，跑一周再调规则。
5. **上下文裁剪做在中间件层**。路由到本地前统一做历史压缩，别指望 32k 的模型硬吃 128k 的 prompt。

## 踩坑点

- 本地模型的 function calling 兼容性参差不齐，优先走 OpenAI 兼容端点，先小流量灰度再全量切。
- **重试风暴**：本地模型响应变慢时，上游 timeout 加重试会把并发放大好几倍，GPU 队列直接雪崩。熔断必须配。
- **隐性成本**：省下的 token 钱，可能被"本地翻车→云端重跑"的双倍调用吃回去。要按任务成功率算总账，不是按单价。
- Embedding 换型号等于向量全量重建，这条没有回旋余地。

## 可复用建议

- 别一上来做智能路由。先手动分两类——plan 走云、其余走本地，就能覆盖 80% 的收益。
- 给路由质量留一个 30~50 条的评测集，改规则前先跑一遍，避免"感觉变快了"式调优。
- prompt 模板按模型版本化。本地小模型往往需要更短的指令、更少的示例，和云端模板混用容易两头不讨好。
- 预算敏感的场景可以把路由规则倒过来写：默认本地，只有标记为 plan 的节点才允许出云。

## 总结

多模型路由的本质，是把"模型选型"从一个全局问题拆成节点级问题。在 OpenClaw 里落地就三个关键动作：任务打标、显式绑定、失败兜底。先用最笨的规则跑起来，靠日志迭代，比追求一个"聪明的 router"务实得多。
