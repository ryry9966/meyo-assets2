## 背景

E2E 测试大概是团队里最容易被拖延的活：写一条用例要处理登录态、等待、选择器，跑起来还容易 flaky，于是大家宁愿多写两个单测。而 Agent 恰好擅长这类“模式固定、上下文密集”的重复劳动。最近两个月我把生成 E2E 用例的工作逐步交给 Agent，从一次性生成演进到“生成—运行—修复”闭环，稳定后整理出这套流程。

## 问题：直接让 AI 写测试，为什么效果差

一句“给这个页面写 E2E 测试”的产出通常有三类毛病：

1. **弱断言**：把流程点一遍但什么也不验证，永远绿，等于没有测试；
2. **脆弱选择器**：猜 class 名、写死 `nth-child`，页面一改全崩；
3. **幻觉**：不知道真实 DOM 和路由结构，编造元素和接口。

根因不是模型能力，而是两件事：上下文缺失，以及没有反馈回路。

## 做法：四步搭协作闭环

**1. 固定上下文源。** 把路由表、页面 DOM 快照（从 trace 里取）、既有用例、测试规范文档放进 Agent 工作区，每次任务固定注入。

**2. 用录制件打底。** 手动（或用 codegen 类工具）先过一遍目标流程，拿到真实操作序列，再让 Agent 重构成符合仓库约定的用例。比凭空生成质量高一个量级。

**3. 把“跑测试”做成工具。** 用 MCP 包一层 `run_tests`：执行 runner，返回失败摘要加截图路径。Agent 拿到失败信息后自行迭代。加两条硬约束——最多 3 轮修复；禁止靠删断言、放宽断言让用例变绿，修不好就原样上报。

**4. 人只审断言。** Review 时优先看断言是否表达了业务意图、是否覆盖边界，样板代码基本不用看。

## 踩坑点

- Agent 特别爱用 `waitForTimeout` 治 flaky，越治越慢。规范里明令禁止，要求自动等待加轮询断言。
- 闭环里出现过“越修越假”：为了过测试去改产品代码。后来规则改成只许动测试文件，diff 超出范围立即中止。
- 用例写了一堆，实际在测同一件事。prompt 里要求每条用例先声明被测行为，重复的合并。
- 本地绿、CI 挂。让工具把本地与 CI 的环境差异（视口、时区、字体）一并返回，交给 Agent 处理。
- 凭据不要进上下文：统一用测试账号，敏感值走环境变量注入。

## 可复用建议

1. 把测试规范写成仓库内文档、每次固定注入，这是投入产出比最高的一件事，比换更强的模型有用。
2. 留一条“金标准”用例做 few-shot，并在其中固化选择器优先级：role > `data-testid` > 可见文本，杜绝 CSS 路径。
3. lint 规则当第二道闸：禁固定 sleep、禁 `nth-` 选择器，违规直接打回，不消耗 Agent 的修复轮次。
4. 先只覆盖 3~5 条核心路径（登录、下单、搜索这类），验证闭环稳定后再扩范围。

## 总结

Agent 写 E2E 的价值不在“全自动生成测试”，而在两处：吃掉样板代码，以及把“跑失败 → 定位 → 修”的循环从人搬到机器上。至于测什么、断言成什么样才算对，这仍是人的设计工作。把上下文喂足、把约束写死、把反馈闭环做小，这套东西半天就能搭起来。建议从你最痛的那条核心路径开始试。
