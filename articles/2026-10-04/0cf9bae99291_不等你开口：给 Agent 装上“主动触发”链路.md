### 背景

大多数 Agent 的使用方式还是“你问它答”：打开会话、下指令、等结果。一次性任务没问题，但一旦想让助手处理持续性的事情——盯任务队列、看日志有没有异常、每天汇总一次 PR 状态——被动模式就不够用了。所谓 proactive，本质上是把“谁来发起对话”从用户换成事件。

OpenClaw 生态里材料其实都齐了：MCP 提供标准化的工具和数据源，插件系统能挂 webhook 和定时器，缺的是中间那段“事件 → 要不要叫醒 Agent → 怎么叫醒”的管道。这篇记录我搭这段管道的过程。

### 问题

把“定时让 Agent 跑一遍”当成 proactive，会立刻撞上三个问题：

1. **成本失控**：每 5 分钟全量唤醒一次，token 消耗是会话式使用的几十倍；
2. **上下文过期**：Agent 醒来后拿着上次会话的记忆直接行动，判断建立在旧状态上；
3. **骚扰式通知**：不分轻重地主动汇报，一周后用户开始无视所有推送，能力等于作废。

### 做法

我的方案是拆成三层，核心思想是**感知和思考分开**：

**第一层：触发源，只接三类。** cron（固定节奏，如每日摘要）、webhook（外部系统推事件，如 CI 失败）、MCP 资源变更通知（数据变了才触发）。明确不做的：对聊天记录、日志这类高频数据做轮询。

**第二层：廉价预过滤。** 事件先过规则或小模型：“是否值得唤醒主 Agent”。规则举例：同一错误连续出现 3 次以上、PR 超过 24 小时无人 review。九成以上事件在这里被丢弃，放行的必须附带一句结构化的 reason。

**第三层：唤醒会话。** 主 Agent 被唤醒时，注入的不是历史记忆，而是触发 reason，外加一条硬约束：**先调 MCP 工具拉取当前状态，未拉取前禁止下结论**。输出固定三段式：发生了什么 / 我做了什么或建议什么 / 哪些需要你拍板。

权限分两档：只读的观察和汇报全自动；任何写操作（发消息、改文件、调外部 API）要么走预批准的 playbook，要么降级成“待确认”推给用户。

### 踩坑点

- **自触发循环**：Agent 自己发的消息又产生了事件，把自己再次唤醒。加事件来源标记 + 同源事件 5 分钟去重才压住。
- **cron 时区和幂等**：定时任务重复触发导致同一份摘要发两遍。现在每个触发实例带幂等键，发送前查重。
- **预过滤规则腐烂**：上线两周后某条规则误报率涨到 40%。给每条规则加了触发/误报计数，每周看一眼，噪音大的直接关。
- **上下文惯性**：即使写了“先拉最新状态”，模型偶尔还是凭记忆回答。后来把这条从建议升级成唤醒模板里的硬约束，才稳定。

### 可复用建议

1. proactive 的核心不是模型多聪明，而是触发、过滤、权限这三段管道的设计——无聊但关键的工程。
2. 每个主动行为对应一份写下来的 playbook：触发条件、判断标准、动作、升级路径。没有 playbook 的主动行为不配上线。
3. 先只读、后写入。主动权限是挣来的，不是配置出来的。
4. 低优先级信号走 digest：攒起来，固定时间合并成一条，体验远好于实时推送。

### 总结

让 Agent 先开口，难点不在“开口”，在“什么时候闭嘴”。触发源收窄、预过滤做厚、权限分级做实，proactive 才能从演示功能变成日常依赖。整套链路没有任何一行依赖超强的模型能力，用现有的 MCP 工具和插件系统就能拼出来。
