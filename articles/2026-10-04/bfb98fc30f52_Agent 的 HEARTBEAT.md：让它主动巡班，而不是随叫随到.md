## 背景

大多数人用 Agent 的方式还是"你问一句、它答一句"。OpenClaw 里其实埋了一个容易被忽略的机制：heartbeat（心跳）。网关会按固定间隔（默认 30 分钟）唤醒一次 Agent，Agent 醒来后的第一件事是读工作区根目录的 `HEARTBEAT.md`，里面写了什么，它就考虑做什么。如果没事可做，它回一个 `HEARTBEAT_OK`，这一拍就静默过去，不打扰任何人。

这个机制的本质，是把 Agent 从"被动应答器"变成"常驻进程"。

## 问题

实际用下来有两个极端。一类人不知道或没用过它，Agent 始终是问答机器；另一类人把它当愿望清单写，结果要么 Agent 每次醒来都在空转烧 token，要么隔三差五往群里发"一切正常"式的垃圾消息。核心问题不是功能不存在，而是没人告诉你这个文件该怎么写。

## 做法

我的配置分三步：

1. **确认心跳开启**。检查配置里的 heartbeat 间隔，默认 30 分钟，调到 15–60 分钟之间比较合理，设为 0 可关闭。频率越高 token 花得越快，先别贪。
2. **在 Agent 工作区根目录写 `HEARTBEAT.md`**。每条任务用同一句式：触发条件 + 具体动作 + 输出位置，末尾补一句"条件不满足则回复 HEARTBEAT_OK，不要发消息"。例如：
   - 检查 inbox 目录是否有昨天之后新增的文件；有则摘要后发到我的私聊；没有则 HEARTBEAT_OK。
   - 若磁盘使用超过 90%，归档 report 目录最旧的三个文件并通知我；否则 HEARTBEAT_OK。
3. **区分心跳与 cron**。固定时刻要做的事（如每天早报）放 cron；"持续关注、满足条件才出手"的事放 heartbeat。混用会导致重复触发。

## 踩坑点

- **指令太模糊**。"帮我关注一下服务器"这种写法，Agent 每次醒来都要自己猜，猜的成本是 token，猜错了就是误报。条件和动作必须可判定。
- **没有兜底子句**。不写"否则 HEARTBEAT_OK"，Agent 可能把"没发现异常"也当成值得汇报的事，一拍一条消息。
- **把重活塞进心跳**。心跳跑在主会话里，一个执行五分钟的脚本会拖住整个循环。心跳适合做"发现 + 转交"，重执行交给子任务或 cron。
- **文件位置和命名**。必须是工作区根目录的 `HEARTBEAT.md`，名字写错或嵌进子目录，心跳照样跑，只是永远无事可做——这是最隐蔽的失效方式。
- **心跳目标频道**。默认进主会话；如果把投递目标设成某个群，要意识到每条未静默的心跳都会落地成群消息。

## 可复用建议

- 把 `HEARTBEAT.md` 控制在 20 行以内。每次心跳都会读全文，这个文件本身就是持续成本。
- 每条任务过一遍"三要素"检查：条件可判定吗？动作有边界吗？无事发生时安静吗？
- 新任务先观察三五天再收紧措辞，出现一次误报就立刻加限定条件。
- 巡检类、条件触发类进 heartbeat；定时类进 cron；一次性事项别占这里。

## 总结

HEARTBEAT.md 的价值不在"AI 主动了"这个噱头，而在于它提供了一个极简的声明式入口：一个 Markdown 文件，定义一个常驻 Agent 的巡检逻辑。写得好，它是安静的值班员；写得差，它是最吵的群成员。克制地写、小步地加，是这条路唯一靠谱的走法。
