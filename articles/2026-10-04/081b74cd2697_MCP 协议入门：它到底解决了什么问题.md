## 背景

2024 年底 Anthropic 开源了 Model Context Protocol（MCP），随后一年里主流 Agent 框架和网关陆续跟进支持。官方把它类比成 AI 的 USB-C，但对工程实践者来说，更值得先搞清楚的是：在没有 MCP 之前，大家到底痛在哪里。

## 问题：M×N 的胶水代码

假设你有 M 个 Agent 应用，N 个想接入的数据源或工具（文件系统、数据库、浏览器、内部 API）。在 MCP 之前，几乎每个应用都要为每个工具写一份私有集成：

- 各家框架的工具/插件定义格式互不兼容，function calling 的 schema 各写各的；
- 同一个「查数据库」能力，在 A 框架写成插件，换到 B 运行时要重写一遍；
- 鉴权、超时、错误处理这些横切逻辑跟着重复实现；
- 工具和框架深度绑定，缺乏复用价值。

这就是典型的 M×N 问题。MCP 把它压成 M+N：应用侧实现一次 MCP 客户端，工具侧实现一次 MCP 服务端，中间用统一协议对话。

## 做法：MCP 的最小工作模型

MCP 基于 JSON-RPC 2.0，架构分三层：Host（Agent 运行时，内嵌 MCP Client）、Server（独立进程，暴露能力）、传输层（本地常用 stdio，远程用 Streamable HTTP）。

Server 对外核心的三类原语，分工要分清：

- **Tools**：模型可主动调用的动作，有副作用（写文件、发请求）；
- **Resources**：供应用读取的上下文数据，只读（文档、配置）；
- **Prompts**：预置的提示词模板。

接入一个 server 大致四步：

1. 选型或自研。社区已有 filesystem、GitHub、Postgres 等现成 server；
2. 配置 transport，stdio 模式就是声明启动命令：

```json
{
  "mcpServers": {
    "fs": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./workspace"]
    }
  }
}
```

3. 用 MCP Inspector（`npx @modelcontextprotocol/inspector`）单独调试，确认 `tools/list` 正常返回；
4. 挂进 Agent，观察模型是否按预期选择并正确调用工具。

## 踩坑点

- **stdio server 的 stdout 是协议通道**。往 stdout 打日志会直接污染 JSON-RPC 流，日志必须走 stderr，这是新手第一大坑；
- 工具描述就是给模型看的 API 文档，写得含糊，模型要么不调用，要么传错参数；
- 一个 server 塞几十个工具会让上下文膨胀，模型选错工具的概率明显上升，按领域拆分；
- 只声明了入参、没写清「何时该用/不该用」，容易出现误触发；
- 安全别大意：server 以你本机权限运行，工具返回内容可能携带注入指令，写操作务必加人工确认，不要无脑 auto-approve。

## 可复用建议

- 一个 server 只管一个领域，工具面尽量小，命名前缀统一；
- 把工具描述当成面向「实习生」的文档写：何时使用、参数含义、错误语义；
- 先用 Inspector 隔离调试，再接入 Agent，用排除法定位问题；
- 把 server 当成有生命周期的进程来管理：崩溃重启、超时、健康检查；
- 远程部署优先 Streamable HTTP，注意协议版本仍在演进，做好兼容判断。

## 总结

MCP 没有让工具变得更强，它做的是把「接入」这件事标准化：M×N 变 M+N，工具实现一次就能被所有兼容 Host 复用。对个人开发者，意味着你写的工具不再绑定某个框架；对团队，意味着 Agent 的能力扩展有了统一的工程边界。协议本身不复杂，真正花时间的是工具设计和安全边界——建议把精力放在这两块。
