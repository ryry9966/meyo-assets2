## 背景

用 OpenClaw 这类 Agent 干活，最烦的往往不是能力不够，而是"失忆"。每次新会话都要重新交代一遍：代码用 Tabs、部署目标是内网 K8s、commit message 写英文……上下文窗口再大也装不下长期偏好，何况大部分偏好根本不该每次都占 token。

## 问题

常见三种做法各有坑：

1. **全塞 system prompt**：偏好一多，提示词膨胀，成本上升，还会稀释真正重要的指令。
2. **全量进向量库**：什么都存，检索时召回一堆似是而非的旧记录，噪声比信号多。
3. **只靠会话摘要**：摘要适合叙事性上下文，但会丢失硬约束的精确性——"生产环境禁止 rm -rf"这种话被摘要改写一次就危险了。

本质问题：记忆不是单纯的存储问题，而是一个**写入时机 + 分层读取 + 冲突处理**的数据工程问题。

## 做法

我在自己的 OpenClaw 工作流里用了一套三层结构，核心是一个 MCP 记忆插件：

**第一层：稳定画像（profile memory）。** 结构化存储，比如一个 `MEMORY.json`：用户身份、长期硬约束、环境信息。每次会话启动时全量注入，体量控制在几百 token 以内。硬约束放这里，不放向量库。

**第二层：情景记忆（episodic memory）。** 一条条带元数据的记录：`{type, scope, confidence, timestamp}`。scope 区分 global / project，type 区分 preference / fact / procedure。按任务关键词检索，取 top 3~5 注入，不贪多。

**第三层：工作记忆**，就是上下文窗口本身，不用管。

**写入路径是关键。** 不要指望模型"自觉"记，要显式提供 `memory_save` 工具，并在系统提示里约定触发条件：用户纠正行为、表达明确偏好、出现重复操作时调用。每条写入都打日志。

**更新与遗忘。** 偏好会变（这周换 pnpm，下周回 npm）。用"观察计数 + 时间戳"做软更新：同一 key 出现新值时不直接覆盖，先标记冲突请用户确认。同时必须有 `memory_forget`——用户说"别再这样了"，要能删干净。

## 踩坑点

- **一次性场景被固化**：我提过一次"临时用 pnpm"，结果全局记忆里 pnpm 成了永久偏好。教训：scope 默认收窄到 project，全局写入必须用户显式确认。
- **检索噪声**：纯向量召回会带回语义相近但场景错误的记忆，加上 scope 过滤和 recency 权重后才算可用。
- **静默写入**：Agent 偷偷记了一条，两周后行为变了，我完全不知道为什么。所有写入应在会话里回显一行确认。
- **敏感信息入库**：API key、私人路径被当成"事实"存下来。写入口要做过滤。
- **记忆内容可被注入**：读回上下文时要把记忆当不可信输入处理，别因为"是自己存的"就放松。

## 可复用建议

1. 从一个扁平文件 + 两个 MCP 工具（save / search）开始，别一上来上向量库，量级到了再演进。
2. Schema 越小越好：type、scope、confidence、timestamp 四个字段够用很久。
3. 硬约束走结构化配置，软偏好走检索，两者别混。
4. 每周人工 review 一次记忆文件、删掉过时条目，比任何自动衰减策略都有效。
5. 验收标准很朴素：同一个任务跑第二遍，Agent 不再问你已经回答过的问题。

## 总结

记忆系统的价值不在"存了多少"，而在"读回的是不是恰好在用的"。分层设计、显式写入、可审计可遗忘——三件事做对，一个几百行的 MCP 插件就能让 Agent 从"每次从头开始"变成"越用越顺手"。先跑通最小闭环，再谈长期演进。
