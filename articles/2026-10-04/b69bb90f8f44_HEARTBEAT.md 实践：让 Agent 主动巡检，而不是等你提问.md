## 背景

多数 Agent 交互是“你问它答”，会话结束注意力就归零。OpenClaw 的心跳（heartbeat）机制补上了另一半：Agent 每隔一段时间被唤醒，读取工作区根目录的 `HEARTBEAT.md`，按里面的检查项决定做事或说话。机制一行配置就能开，难点在内容怎么写。

## 问题

直接上手通常遇到三件事：

- **噪音**：每次心跳都往频道发消息，两天后没人再看；
- **成本**：每次心跳是一次带完整工具权限的 LLM 调用，不是免费的定时器；
- **发散**：把 HEARTBEAT.md 写成大杂烩 TODO，Agent 醒来后的行为不可预测。

## 做法

1. **建文件**：工作区根目录创建 `HEARTBEAT.md`。文件为空或无可执行内容时，Agent 按约定回复 `NO_HEARTBEAT`，静默跳过本轮、不投递任何消息——这是整套机制的噪音阀门。
2. **写检查项**：每行一个“检查什么 + 判定条件 + 动作 + 沉默条件”。例如“检查备份目录最新文件时间戳，超过 2 小时未更新则在值班频道提醒，正常则不报”。控制在 3–5 行。
3. **调间隔**：配置中修改心跳间隔（`HEARTBEAT_INTERVAL`，毫秒），默认 30 分钟。调试期临时调短观察几轮，稳定后调回。
4. **定向投递**：把心跳输出指到专门频道，与日常对话隔开。
5. **验证**：手动触发一次，确认“该说话时说话，没事时闭嘴”。

我的实际用例：每 30 分钟检查备份目录的文件数量和时间戳，低于阈值才提醒。上线两周，抓到一次同步脚本静默失败，这正是人不会主动去看的东西。

## 踩坑点

- **别放一次性待办**。它是巡检清单不是任务队列，一次性的事用提醒或 cron。
- **条件必须量化**。“看看服务器正不正常”会得到似是而非的动作，“磁盘占用 >85% 才报”才能稳定复现。
- **确定性检查交给脚本**。默认间隔约等于每天 48 次完整调用，心跳只留需要 LLM 理解上下文的部分。
- **心跳是轮询，不是定时**。“每天 8 点发日报”用 OpenClaw 的定时任务；“每隔一段看看有没有异常”才用心跳。
- **限制无人值守的写操作**。心跳期间 Agent 有完整工具权限，破坏性动作要么不配，要么前置确认。

## 可复用建议

- 模板四要素：检查对象、判定阈值、动作、沉默条件。写不出沉默条件的项，多半就是噪音源。
- 让 `HEARTBEAT.md` 随工作区进 git，心跳行为的每次变更可审计、可回滚。
- 直接对 Agent 说“把 X 加进你的心跳清单”，它会自己编辑这个文件，这是教它值班的最低成本方式。
- 数据源走 MCP server，检查项只描述“查什么、怎么判”，不耦合连接细节。
- 每周翻一次心跳日志：删掉从未触发的项，给频繁触发的项收紧阈值。

## 总结

HEARTBEAT.md 的价值不在“自动化”本身，而在把 Agent 的注意力从会话内扩展到会话外。写好它反而要反着来：内容越短越好，沉默越多越好。一个只写三行、大部分时间回 `NO_HEARTBEAT` 的心跳，通常比写满二十条的更可靠。
