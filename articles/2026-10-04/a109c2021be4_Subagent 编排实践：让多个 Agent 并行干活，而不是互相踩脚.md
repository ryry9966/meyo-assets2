## 背景

用单个 Agent 跑长任务，迟早会遇到同一类问题：主对话的上下文被工具输出塞满——一次全量检索能吃掉几千 token，翻几轮之后模型开始"忘记"最初的目标。另一个隐性成本是串行：五个互不依赖的调研子任务排成一队，总耗时就是五段之和。

subagent 编排解决的就是这两件事：把规划和执行拆开，把独立任务并发跑。概念不新，但在 OpenClaw 这类可接 MCP 工具、可装插件的框架里，落地细节值得讲清楚。

## 问题定义

拆之前先确认真的需要拆。三个信号：

1. 主 Agent 上下文膨胀，早期指令被稀释；
2. 存在多个"读完资料 → 产出一份摘要"型的独立子任务；
3. 单点失败会拖死整个流程，希望爆炸半径可控。

如果任务本身强串行（B 必须用 A 的产物），强行并行只会增加编排开销。

## 做法

**1. 父子分工明确。** 父 Agent 只做三件事：拆任务、发任务、收结果，不亲自碰重型工具。子 Agent 拿到自包含的任务说明，在隔离上下文里执行，最后只回传压缩后的结论。

**2. 用"独立性测试"决定并发。** 拆分时问一句：B 的输入依赖 A 的输出吗？不依赖就并行，依赖就串成 pipeline。经验值是一个主任务拆 3~5 个子任务比较舒服，超过 8 个通常说明拆得太碎，编排成本会反噬收益。

**3. 子任务说明用固定模板。** 大致长这样：

```json
{
  "goal": "定位代码库中所有直接拼接 SQL 的调用点",
  "inputs": ["仓库根目录", "目标语言"],
  "constraints": ["只读，不修改文件", "搜索工具最多调用 10 次"],
  "output": "JSON 数组：{file, line, snippet, risk}"
}
```

关键在 `constraints` 和 `output`：不给约束，子 Agent 会自由发挥；不给输出格式，父 Agent 汇总时会很痛苦。

**4. 控制并发度。** 用信号量把并行数压在 3~5。一方面是配额和成本，另一方面下游工具（比如同一个 MCP server）常有速率限制，盲目扇出只会集体撞墙。

**5. 结构化回收。** 每个子 Agent 回传时带上 status（ok / failed / partial）、结论、以及关键细节原文（文件路径、报错信息）。父 Agent 拿到的是"摘要包"，而不是原始工具输出的转述。

## 踩坑点

- **子 Agent"失忆"。** 子 Agent 不继承父对话，这是最常见的翻车点。它不知道你上半场聊了什么，任务说明里必须把所需上下文显式写全。
- **并行写冲突。** 两个子 Agent 同时改同一个文件、写同一张表，结果就是互相覆盖。并行化之前先做副作用分区：按目录、按表、按 key 切开；或者干脆规定子 Agent 只读，由父 Agent 统一落盘。
- **汇总丢细节。** 让子 Agent"总结一下"，它会把报错信息也总结没了。要求原文保留关键字段，排查时你会感谢这条规定。
- **部分失败处理。** 一个子任务失败不应让整批作废。逐个收 status，失败的单独重试一次，仍失败就带着 failed 标记进汇总，交给上层决策。
- **成本失控。** 扇出是 token 放大器，同一份检索结果在父子两层各出现一遍很常见。能缓存就缓存，能限次就限次。

## 可复用建议

- 先把单 Agent 版本跑通、确认任务边界，再拆 subagent；拆分是对成熟流程的重构，不是起点。
- 任务说明模板（goal / inputs / constraints / output）固化下来，团队内复用。
- 每个子 Agent 单独留 trace（输入、工具调用、耗时、status），出问题能定位到具体分支，而不是面对一团合流日志。
- 副作用幂等优先于并发数调优——重试安全了，才敢放心并行。

## 总结

subagent 编排的核心不是"多开几个 AI"，而是上下文管理和写冲突治理：父 Agent 保持轻、子任务自包含、回传结构化、副作用分区。做到这四点，并行提速是稳定的；做不到，扇出只会把一个混乱的对话放大成多路混乱。建议从一个真实的长任务开始，先串行跑通，再按独立性拆两三个子 Agent 对比耗时和 token 消耗，数字会告诉你值不值。
