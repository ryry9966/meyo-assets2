## 背景

跑过一段时间 OpenClaw 自动化任务的人都有体感：一个中等复杂度的 agent 任务，规划、工具调用、结果整理循环下来，几十次模型请求很常见。全部走 GPT，成本随任务量线性上涨，内网数据还要外发；全部走本地，长上下文规划任务的质量下降非常明显。所以真正的问题从来不是“能不能接多个模型”，而是**路由规则怎么定**。

## 问题

我见过两种极端。一种是图省事全量走 API，月底账单很难看；另一种是全量走本地小模型，结果 agent 在工具调用的 JSON 参数上频繁出错，插件校验失败，整个循环卡死。手动切模型在单任务里还行，一旦任务多了就不现实。

## 做法

我的实践分四步：

**1. 先给模型分档。** 强模型负责规划、复杂推理、参数 schema 复杂的工具调用；本地模型负责抽取、分类、摘要、格式化这类“执行型”请求。

**2. 按阶段路由，而不是按轮次。** 在 OpenClaw 的模型配置里定义 profile，规划阶段走强模型，循环内的调用和整理走本地。示意如下（以实际版本 schema 为准）：

```yaml
models:
  planner:
    provider: openai
    model: gpt-4o
  worker:
    provider: ollama
    model: qwen2.5:14b
routing:
  rules:
    - stage: plan        # 规划、复杂推理
      use: planner
    - stage: tool_call   # 循环内的调用与整理
      use: worker
  fallback:
    from: worker
    to: planner
    max_retries: 2
```

**3. 规则优先于智能路由。** 按任务类型、上下文长度、是否含敏感字段写确定性规则。别一开始就上“用小模型判断该路由给谁”的元路由——那只是把问题往上游推了一层。

**4. 配带上限的 fallback。** 本地超时或失败后降级到 API，重试必须有最大次数，然后记录每次路由决策：任务类型、模型、耗时、token 数、是否触发 fallback。跑一周再回头调阈值。

## 踩坑点

- **小模型最大的坑不是答得差，是工具调用不合 schema。** 参数校验一失败，循环直接报废。接进 agent 循环之前，先单独压测本地模型的 function calling 成功率。
- **量化对工具调用的影响远大于聊天。** 14B 模型 Q4 聊天还行，Q4 下工具调用可能崩，显存预算要留够，或者上 Q8。
- **中途切模型有格式漂移。** 不同模型对 system prompt 和工具返回的理解不一致，同一条链里来回切，质量反而降。按“阶段”切，别按“轮次”切。
- **裸重试会打爆两条通道。** 本地半死不活时，没有上限的 fallback 会让请求反复横跳。
- **没有固定评测集就别调规则。** 准备 20～30 个代表性任务，改规则前后各跑一遍，否则分不清收益是真信号还是噪声。

## 可复用建议

- 敏感数据（内网日志、客户信息）**一律本地**，哪怕质量降一点，这是硬规则，不是优化项。
- 经验分配：约 20% 的规划/生成流量走强模型，80% 的执行类请求走本地，成本通常能降一个量级，具体看任务结构。
- 从 2 个模型、不超过 5 条规则开始。规则数量本身就是维护成本。
- 路由日志别省，它是后续一切优化的依据。

## 总结

多模型路由的本质，是给 agent 链路的不同环节匹配不同档位的算力，而不是省钱技巧游戏。先按阶段切分、规则优先、压测工具调用、带上限的 fallback、持续记录——把这五件事做扎实，再考虑更聪明的路由方式。折腾路由之前，先把评测集建起来，这是我最后悔没早做的一步。
