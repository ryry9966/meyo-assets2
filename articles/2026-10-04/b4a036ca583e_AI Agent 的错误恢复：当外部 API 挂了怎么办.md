## 背景

Agent 跑得越久越明白一件事：外部 API 失败不是异常路径，而是常态。OpenClaw 的 skill、MCP server、各类插件，本质上都在替模型"伸手"到外部世界——搜索、数据库、第三方服务。任何一个依赖抖动，整个自动化流程跟着抖。

脚本时代靠 try/catch 加重试就够了；Agent 时代复杂在模型在环里：它会"看到"失败并自己做决定。决定得好叫自愈，决定得差就是灾难。

## 问题

外部 API 故障在 Agent 里通常表现为三种失控：

1. **重试风暴**：prompt 里写了"必须完成任务"，模型对着一个 500 的接口连打十几次，token 和配额一起爆炸。
2. **幻觉补位**：报错没被正确处理，模型把错误 JSON 当成"查询为空"，接着往下编。
3. **静默挂起**：没设超时，一次连接挂起让 cron 任务卡到天亮。

共同根源：错误处理交给了 prompt，而不是工具层。

## 做法

原则一句话：**恢复逻辑做进工具层，模型只做"知情决策"**。

**1. 错误分类。** 失败先归类：超时、429、502/503 属于瞬时故障，可重试；401/403、参数错误属于永久故障，重试无意义；部分数据、过期缓存属于降级可用。

**2. 有限重试 + 指数退避。** 瞬时错误最多重试 2–3 次，间隔 1s→2s→4s 并加随机抖动，避免踩踏。重试放在封装层，不要让模型自己发起。

**3. 熔断。** 连续失败 5 次就标记该 endpoint 冷却 5 分钟，期间直接快速失败。注意按 endpoint 维度隔离，别一个服务挂了把所有工具都熔断。

**4. 降级与回退。** 提前备好 fallback：备用 API、上次成功的缓存、或明确的"跳过该步骤"。让模型拿到的是"主通道不可用，可选降级 A/B"，而不是裸报错。

**5. 结构化回传。** 给模型的错误统一封装：

```json
{"ok": false, "error_type": "rate_limited", "retryable": false, "hint": "改用备用工具，或跳过本步并在回复中说明"}
```

模型看到 `retryable: false` 就不会硬刚，看到 `hint` 就知道换路。

## 踩坑点

- **别把原始报错塞进上下文**。带 2KB HTML 的 502 页面既烧 token 又容易带偏模型，统一在工具层截断、翻译。
- **重试非幂等操作会重复发消息、重复下单**。POST 类调用要么带幂等键，要么失败后转人工确认。
- **区分"失败"和"空结果"**。空数组是合法返回，504 是失败；混在一起，模型就会当成"没查到"。
- **session 级护栏不可少**。除工具层重试外，还要有"同一工具连续失败 N 次即终止任务"的上限。cron 无人值守任务尤其需要——没人帮你按停止键。
- **熔断恢复用半开探测**。冷却结束后先放一个探测请求，直接全量放开，容易在服务半死不活时反复打穿。

## 可复用建议

1. 所有工具统一错误 envelope，字段固定：`error_type / retryable / hint`。
2. 工具描述里写清降级契约："本工具失败时，建议改用 X 或跳过"。这是写给模型看的，不是给人看的。
3. 上线前做故障注入：mock 429、500、超时，观察 agent 行为是否符合预期。
4. 重试与熔断事件落日志，事后才答得出"昨晚那次任务为什么没跑完"。

## 总结

外部 API 挂掉不是会不会遇到的问题，而是何时遇到的问题。错误恢复的核心不是写更温柔的 prompt，而是把分类、重试、熔断、降级做进工具层，让每次失败都以模型能理解、且不会失控的方式呈现。Agent 的可靠性，往往取决于它失败时的样子。
