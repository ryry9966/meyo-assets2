## 背景

跑过 Agent 网关的人都会遇到同一个问题：agent 平时不"醒着"，但有一堆事需要它按时醒来——定时提醒、收件箱巡检、监控指标超阈值后的跟进、MCP 工具异步结果的回收。把 agent 叫醒的机制，基本就两条路：**定时轮询（heartbeat）** 和 **事件推送（push）**。

## 问题

两个极端都不好用：

- **纯轮询**：间隔 1 分钟，绝大多数 tick 是空转，token 和配额白白烧掉；间隔拉到 30 分钟，用户设的"10 点提醒我"变成 10:26 才响。
- **纯推送**：没有外部事件时，状态漂移没人管。到期的提醒不会自己触发——"到时间了"本身就是一个没有 webhook 的事件。
- **两者混用但不做设计**：heartbeat 和 push 同时写同一个会话，出现消息交错、重复回复，事后排查非常痛苦。

## 做法

我们现在的方案，核心是"分源、降本、串行、可观测"四件事：

1. **先分清唤醒源**。时间驱动的（提醒、cron、巡检）走 heartbeat；事件驱动的（频道消息、webhook、工具回调）走 push。不要让一类事件伪装成另一类。
2. **heartbeat 保持便宜**。心跳用独立的极简上下文（一份任务清单，而不是完整对话历史），并且先做一次廉价的本地条件检查：有没有到期任务、有没有待处理标记。无事直接 noop，跳过 LLM 调用。这一步能把心跳成本降一个数量级。
3. **push 走统一入口**。所有推送进同一个队列，带幂等键去重——webhook 重试是常态，不是异常。
4. **单写者原则**。heartbeat 和 push 都串行经过这个队列进入会话。agent 的会话不是线程安全的，别让它并发。
5. **自适应间隔 + 退避 + 抖动**。有挂起任务时把间隔缩到分钟级，空闲时拉长到半小时；上游失败用指数退避，间隔加随机抖动。
6. **记录每次心跳**：耗时、token、动作（noop 还是 task）。noop 比例持续高于 90%，就该拉长间隔了。

## 踩坑点

- 心跳 prompt 带了全量上下文，每次 tick 都是全价调用。心跳上下文必须单独裁剪。
- noop 也调 LLM：在代码层先过滤，比在 prompt 里写"没事别回复"可靠得多。
- 推送没做去重，webhook 重试一次，用户收到两条一模一样的回复。
- 定时任务统一存 UTC 但按本地时间触发，夏令时切换那天集体错位一小时。
- 心跳结果默认推给用户，一晚上刷了十几条"一切正常"。心跳应该默认静默，真正有事才说话。

## 可复用建议

- **推送管及时性，心跳管正确性**：延迟敏感的走 push，时间驱动和状态纠偏走 heartbeat，两者互补而非二选一。
- 心跳上下文最小化，与主对话隔离。
- 所有进入会话的写操作：幂等键 + 串行队列。这两个约束值得为一年的稳定性买单。
- 监控 noop 比例和心跳 P95 耗时，比盯着总 token 量更有用。

## 总结

heartbeat 设计的取舍，本质是"谁为及时性付费"：推送让事件方付费，轮询让 agent 付费。实践里我们最终收敛到——push 为主、heartbeat 为底，配一个串行队列和一套廉价的 noop 判定。真正花时间的不是选型本身，而是把串行化、去重、可观测这三件朴素的事做扎实。
