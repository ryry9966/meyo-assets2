## 背景

Agent 跑起来之后，最大的不确定性往往不是模型，而是它调用的外部依赖：搜索、数据库、第三方 SaaS、MCP 工具背后的各种 API。单次脚本调用挂了重跑就行，但 Agent 是长循环——一个环节失败，后面所有计划都会连锁受影响。错误恢复不是“加个 try/except”，而是要分层设计。

## 问题

实际跑下来，外部 API 挂掉时 Agent 通常有三种糟糕表现：

1. 工具层直接抛异常，整轮任务中断，前面消耗的 token 和已完成步骤全部作废；
2. 模型看到错误后自作主张无限重试，一分钟烧掉几十次调用，还可能触发限流雪上加霜；
3. 更隐蔽的：工具吞掉错误返回空结果，模型把“没查到”当成“没有”，编出一个看似合理的答案继续往下走。

## 做法：分三层处理

**第一层：工具/插件层——确定性兜底。** 重试逻辑不要交给模型判断，写在代码里：

- 只对可重试错误重试：超时、429、5xx、网络抖动；4xx（参数错、鉴权失效）重试没有意义，直接上抛。
- 指数退避 + 随机抖动，尊重 Retry-After 头，硬性上限 3~5 次。
- 每个调用必须有独立超时，且小于整个 Agent 任务的预算超时。

**第二层：Agent 交互层——把错误当输入。** 工具层兜底失败后，向模型返回结构化错误，而不是异常字符串或空值。约定一个统一信封：

```json
{ "ok": false, "error_type": "upstream_unavailable", "retriable": false, "hint": "建议改用备用工具或告知用户" }
```

模型拿到 `error_type` 和 `hint` 才能做出有意义的决策：换工具、降级、还是停下来问用户。

**第三层：工作流层——断点与熔断。** 长任务每完成一步就落 checkpoint，恢复时从断点继续而不是从头跑；对已连续失败 N 次的工具做熔断，冷却期内直接返回“该工具暂不可用”，避免每次都干等一个注定超时的调用。

## 踩坑点

- **重试非幂等操作。** 下单、发消息这类 POST，盲目重试会造成重复提交。客户端生成幂等键由服务端去重，或者把这类工具直接标记为“失败不可自动重试”。
- **错误被吞。** `except: return None` 是 Agent 场景的大忌，模型会基于空值幻觉。宁可让任务失败，也不要给模型假成功。
- **退避缺失。** 遇到 429 立刻原样重试，等于帮对方把你限得更死。
- **超时不对齐。** 工具超时 60s、任务总超时 45s，会出现永远跑不完的僵尸任务。
- **过度信任模型判断。** “让模型自己决定重试几次”在 demo 里没问题，生产环境必须有代码层的硬上限。

## 可复用建议

- 把错误信封做成团队约定，所有 MCP 工具统一返回格式，Agent 的 system prompt 里只需写一次处理策略。
- 重试参数（次数、退避基数、超时）按工具配置化，不要散落在代码各处。
- 记录每次失败：工具名、错误类型、耗时、重试是否成功。跑一周你就知道哪些依赖最脆。
- 用故障注入测试：写一个可以返回 500/超时/慢响应的 mock 工具，专门验证恢复逻辑。别等线上 API 真挂了，才第一次测自己的容错。

## 总结

外部 API 挂掉是常态而不是异常。可靠的 Agent 不是不遇到错误的 Agent，而是错误被分层接住、被结构化表达、被有限次处理之后，仍能继续推进或体面退出的 Agent。核心原则一句话：确定性的事交给代码，判断性的事交给模型，但两边都要有边界。
