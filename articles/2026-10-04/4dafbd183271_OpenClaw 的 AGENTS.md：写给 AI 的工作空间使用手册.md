## 背景

Agent 接手工作区时，本质是个“第一天入职、还不允许提问的实习生”：能力不差，但对项目一无所知。README 是写给人的，人知道去翻 issue、问同事；agent 不会。AGENTS.md 就是补这一层的约定——放在工作区根目录，OpenClaw 在会话开始时自动读取并注入上下文，相当于把每次的口头交代固化成一个随仓库走的文件。

## 问题：没有手册时的典型翻车

实际用下来，缺了这份文件，agent 大概率会出现：

- 在 pnpm 项目里执行 npm install，凭空多出第二份 lockfile；
- 自己“发明”测试命令，跑了个寂寞；
- 绕过 lint 直接交付，代码风格全靠猜；
- 重复实现工具库里早就有的函数；
- 顺手改掉不该动的 CI 配置或生成目录。

这些不是模型能力问题，是上下文缺失。解决方案不该是每场会话人工重复交代一遍。

## 做法：一份最小可用的 AGENTS.md

建议这样起步：

1. **根目录建文件，先写三类内容**：项目一句话说明；可直接执行的命令（构建/测试/lint 给精确命令行，不要写“运行测试”这种模糊描述）；硬性约束（例如“docs/ 是生成产物，不要手改”）。
2. **子目录按需覆盖**。frontend/ 与 backend/ 约定差异大时各放一份，并写明“本目录优先遵循以下规则”。
3. **与工具生态对齐**。配了 MCP 工具或插件的话，把“什么场景用哪个工具”写进去，比如数据库操作统一走某个 MCP 工具，而不是让 agent 现拼脚本。
4. **进版本库**。像 review CI 配置一样 review 它的变更，项目结构调整时同步更新。

## 踩坑点

- **写成第二份 README**。内容重复两边维护，很快漂移。README 讲“这是什么”，AGENTS.md 讲“该怎么操作”。
- **命令不精确**。“用项目自带的测试方式”对 agent 没有意义，必须给完整命令。
- **越写越长**。它会被注入每次会话上下文，几百行会稀释重点也费 token。经验是控制在几十行，细节放子目录文件。
- **忽略 .gitignore 的影响**。有些模板默认忽略根目录 md 文件，队友 clone 下来，agent 又变“新人”。
- **塞入敏感信息**。密钥、内网地址不要写，它会进入模型上下文。
- **层级规则打架**。根目录与子目录冲突时 agent 会犹豫，覆盖关系要写明。

## 可复用建议

- 判断标准很简单：**同一件事你在会话里解释第二遍，就该进 AGENTS.md**。
- 多写事实和命令，少写形容词。“遵循整洁代码原则”没用，“提交前必须通过 X 命令”有用。
- 把它当“操作手册”而非“价值观宣言”，小步迭代，别憋完美版。

## 总结

AGENTS.md 的价值在于把散落在聊天记录和个人习惯里的项目知识，变成一份随仓库走、agent 每次都能读到的约定。成本是十几分钟写作，收益是显著降低 agent 的随机翻车率。建议先写一个十几行的版本，用两周，把翻车案例回填进去——它会自然长成团队最实用的工程资产之一。
