## 背景：给 AI 看的 README

AGENTS.md 不是普通文档。OpenClaw 在每次会话启动时会读取工作空间根目录的这份文件，作为 agent 的运行时上下文注入。可以这么理解：README.md 写给人看，AGENTS.md 写给模型看。它决定了 agent 如何理解这个空间——哪些文件是它的记忆、哪些目录不能碰、接到任务后按什么流程走。

## 问题：没有手册的 agent 会反复犯同样的错

实际跑一段时间后，故障模式很固定：

- 新会话"失忆"，同一件事要反复交代；
- agent 把临时文件堆在根目录，甚至覆盖自己的记忆文件；
- 记忆写入没有约定，MEMORY.md 越滚越乱；
- 工具调用没有边界，顺手就改了 gateway 配置。

这些大多不是模型能力问题，而是工作空间缺一份明确的操作规程。

## 做法：把 AGENTS.md 当契约写

我的写法分五块：

1. **空间地图**：每个文件一句话说明用途；
2. **读写边界**：明确能改什么、禁止改什么；
3. **记忆协议**：何时读 MEMORY.md，什么信息值得写入 memory/，过期数据怎么清理；
4. **流程约定**：模糊任务先反问，执行命令前确认影响范围，多步任务先列计划；
5. **风格约束**：回复语言、代码规范、引用格式。

比如我文件里的几条硬规则：

```markdown
- 禁止在根目录创建新文件，临时产物一律放 tmp/
- 修改 gateway 配置前必须先向用户确认
- 会话结束前，把值得长期保留的信息写入 memory/
```

落地路径：默认模板起步 → 跑真实任务 → 每次犯错，把纠正过程固化成一条规则 → 定期瘦身。

## 踩坑点

- **写太长**。有人把它当 wiki 写到几千字，核心规则被稀释。我控制在 60 行以内，细节拆到 TOOLS.md 等文件，AGENTS.md 只放索引和硬规则。
- **写成愿景文档**。"你要乐于助人"这种句子模型无法执行。规则要可判定："禁止删除 memory/ 下的文件"远好于"请珍惜记忆"。
- **职责越界**。人格归 SOUL.md，身份归 IDENTITY.md，AGENTS.md 只管操作规程。两处写重复内容，规则会打架。
- **只写不养**。升级 OpenClaw 后文件结构变了，过期规则比没有规则更糟。

## 可复用建议

- 建立"错误→规则"流水线：每次手工纠错后问一句"能不能写成规则"，能就追加进去；
- 全部用"必须 / 禁止 / 先……再……"句式，避免形容词；
- workspace 纳入 git，规则变更可回溯，多机同步也省心；
- 改完规则后**开全新会话验证**，旧会话的上下文污染会给你假象。

## 总结

AGENTS.md 的价值不在于"多了一份文档"，而在于把对 agent 的隐性期望变成显性、可版本化、可迭代的运维资产。它是随系统演进的 SOP，不是一次性配置。检验标准很简单：开一个新会话，不用你解释，它就能把活干对。
