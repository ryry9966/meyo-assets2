## 背景

OpenClaw 的 agent 长期运行在一个工作区里：读写文件、调用插件和 MCP 工具、跑定时任务。人接手一个新环境要靠 README，agent 同样需要。`AGENTS.md` 就是这份"写给 AI 的使用手册"——放在工作区根目录，每次会话启动时被注入上下文，成为 agent 对这个空间的默认认知。

## 问题

最初我把工作区当纯数据目录，agent 的行为全靠猜：每次会话风格不一致，同样的任务有时写脚本有时手动敲；让它改配置文件，它直接覆盖了我手工调过的注释；执行不熟悉的命令前也不确认。这些都是"没写手册"的代价——模型不缺能力，缺的是约定。

## 做法

1. **先写一个最小版本。** 不用一次写全，放三块就够：工作区结构（哪些目录干什么、哪些不能动）、交互约定（回复语言、改动前是否确认）、工具红线（哪些命令必须先确认，MCP 工具和插件提供的操作尤其要写清）。
2. **用"必须/禁止"，不用"建议"。** 模糊表述在长会话里会被稀释。
3. **踩坑后回写。** agent 做错什么，就补一条对应规则，一两条即可，别写成检讨书。
4. **分层存放。** 全局偏好放用户级，项目细节放项目工作区，别让一份文件既当宪法又当备忘录。
5. **当代码维护。** 进 git、走 review，每次改动写清楚为什么。

## 踩坑点

- **写太长。** 几百行的 AGENTS.md 会稀释关键规则，重点条目反而失效。我压到一屏以内后，遵守率明显上升。
- **规则冲突。** "永远简洁"和"每步操作都要解释"放一起，模型只能随机选一个。写完自查一遍。
- **改完不重开会话。** 它在会话启动时注入，改完要开新会话才生效，别在旧会话里反复调到怀疑人生。
- **把密钥和敏感路径写进去。** 这些内容会进模型上下文，按公开信息对待。
- **期望它替代记忆。** 它是约定不是数据库，事实性的内容应该放 memory 文件，规则里只写行为。

## 可复用建议

- 每条规则尽量可判定："改配置前先展示 diff"远好于"小心一点"。
- 总量控制在 20 条以内，超了就合并或删除。
- 高频踩坑沉淀成 skill 或脚本，而不是继续堆规则——能用工具解决的别靠提示词。
- 每月审一次，删掉过时条目。规则和实际行为对不上，比没有规则更糟。

## 总结

AGENTS.md 的价值不在于"写了什么"，而在于形成闭环：agent 出错 → 归因 → 回写规则 → 新会话验证。把它当一份持续演进的运行手册，而不是一次性配置，agent 在工作区里的表现才会真正稳定下来。
