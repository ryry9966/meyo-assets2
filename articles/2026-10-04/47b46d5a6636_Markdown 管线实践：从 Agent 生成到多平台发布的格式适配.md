## 背景

社区里做自动化写作的朋友大概都走过同一条路：让 Agent 出初稿，人工过一遍，再分别贴到公众号、知乎、博客——每贴一次就要修一次格式。我们把这条链路固化成了管线，跑了两个多月，这篇帖记录核心设计与踩过的坑。

## 问题

问题集中在三层：

1. **生成端不稳定**：LLM 输出的 Markdown 是“方言”。同一份提示词，今天混进 raw HTML，明天代码块没闭合，标题层级跳来跳去。
2. **平台端差异大**：公众号只收带内联样式的 HTML，外链图片一律失效；知乎对表格和脚注支持有限；GFM 的 task list、mermaid 各家渲染不一。
3. **中间没契约**：prompt、转换脚本、发布脚本各自为政，改一处崩三处。

## 做法

核心思路：把“AI 生成什么”和“平台要什么”解耦，中间用 AST 做规范化。五个步骤：

**1. 定义方言契约。** 写一份 Markdown 子集规范：只允许 h2–h4、fenced code 必须带语言标签、图片一律写 `![alt](img:xxxx)` 占位、禁止 raw HTML 和内联样式。这份规范同时注入 system prompt 和 lint 工具，生成端与校验端引用同一个文件。

**2. AST 规范化。** 用 remark（mdast）解析后过一遍 transformer：标题层级重排、补齐缺失语言标签、图片占位符提取成资产清单。不要用正则链做这件事，mdast 上的操作可组合、可测试。在 OpenClaw 里这一步可以封装成 MCP 工具：Agent 生成完先自检，报错回喂给模型修，省掉一轮人审。

**3. 资产处理。** 占位符在规范化阶段落地为内容寻址的本地文件（哈希命名），压缩并生成本地预览；只有发布适配阶段才上传平台并回填真实 URL。

**4. 平台适配器。** 每个目标平台一个小模块，输入规范化后的 mdast + 资产清单：公众号走 markdown-it + 内联样式主题（代码高亮预渲染成 span）；博客走 remark-rehype + front matter 注入；知乎适配器负责降级——表格转列表、脚注转括号注记。适配器保持纯函数，不碰网络。

**5. 校验与打包。** 发布前跑 smoke render：检查代码块闭合、图片引用完整、链接可达；按 `dist/wechat/`、`dist/blog/` 分目录输出，附 diff 预览。

## 踩坑点

- 公众号会把 class 属性整个剥掉，所有样式必须内联，代码高亮要在生成 HTML 时就渲染成带 style 的 span，不能指望前端 JS。
- 外链图片（包括第三方图床）在公众号里必挂，必须走素材接口上传后回链，这步没法跳过。
- front matter 是重灾区：LLM 生成的 YAML 里 title 带冒号、用 tab 缩进，都会让解析直接失败。建议 front matter 不让模型生成，改由管线注入。
- 表格在移动端几乎必碎。长内容一律要求模型输出列表而非表格——这条要写进方言契约，而不是事后修。
- 数学公式和 mermaid 兼容性最差，目标平台不渲染就提前降级成图片或纯文本，别留到发布时才发现。

## 可复用建议

- **契约先行**：那份 Markdown 子集规范是最值钱的资产，prompt、linter、适配器三处引用它，单点修改全局生效。
- 一切转换基于 AST，正则只做最后一公里的清理。
- 适配器做成纯函数（mdast 进、目标格式出），方便单测和 dry-run。
- 图片用占位 ID 贯穿管线，真实 URL 只在发布最后一步落盘。
- 按内容哈希缓存发布结果，Agent 重跑同稿不重复上传素材。

## 总结

这条管线没用到复杂框架，本质是“契约 + AST + 纯函数适配器”三件事。收益在于：新增一个发布平台通常只是一个适配器文件；Agent 换模型或改提示词，只要方言契约不破，下游全部不动。格式适配的复杂度不会消失，但可以被关进管线的固定一层里。
