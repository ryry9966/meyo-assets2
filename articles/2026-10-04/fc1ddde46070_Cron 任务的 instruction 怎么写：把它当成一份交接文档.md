## 背景

OpenClaw 的 cron 任务本质上很简单：到点之后，框架把一段 instruction 原样交给 agent 跑一次，结束。这段 instruction 就是任务的全部——没有人在旁边补上下文，也没有追问的机会。

很多人（包括我）第一批 cron 都犯同一个错：把当时脑子里想的东西压缩成一句话塞进去，比如"每天早上汇总一下我的 issue"。这句写在当下没问题，因为写的人知道 issue 指什么、汇总给谁看。但 cron 是在未来某个无人值守的时刻执行的，那一刻的 agent 和你之间没有任何共享记忆。

## 问题

写不好的 cron instruction 通常有三种症状：

1. 跑出来的内容泛泛而谈，agent 用通用知识交差，没有真正调用你的数据源；
2. 结果生成了，但不知道发到哪里，静静躺在一个没人看的会话里；
3. 数据拿不到时，agent 要么沉默，要么编一个看起来很像样的答案。

## 做法

我的做法是把 instruction 当成交接文档来写，固定五个要素：

1. **目标**：一句话说清这次运行要产出什么。用可验证的动词（汇总、检查、比对），不用"关注一下""看看"。
2. **来源**：明确工具和路径。读哪个文件、调哪个 MCP 工具、跑什么命令，写进 instruction，不要指望 agent 自己猜。
3. **步骤**：两三步以内的执行顺序，例如"先读取 x，再过滤 y，最后按 z 格式整理"。
4. **输出格式与去向**：几行以内的 markdown？发到哪个 channel？要不要提醒？框架层面虽然可以配置投递目标，但 instruction 里仍要写清输出形态，两者别互相替代。这一项是新手最常漏的。
5. **异常分支**：明确告诉 agent"如果数据源不可用，发一条一句话的失败说明到同一位置，重试不超过一次，不要编造内容"。

另外两个细节：

- **时间锚点**。开头加一句"先运行 date 命令确认当前日期，再据此确定'今天'的范围"。cron 的实际触发时间和你想的不一定一致，尤其在跨时区的服务器上。
- **长材料外置**。参考规则、格式模板放成文件，instruction 里只留路径和"先读取该文件"的指令。instruction 本身保持在一屏以内，高频任务尤甚。

## 踩坑点

- **假设上下文存在**。cron 触发的会话通常不继承你正在聊的内容，所有必要信息必须写进 instruction 或它指向的文件。
- **时区错位**。调度走服务器时区，你脑子里是本地时间。上调度前先确认两边对齐。
- **成本失控**。每 15 分钟跑一次带大段上下文的 instruction，月底账单会教育你。低频任务和高频任务的详略应该完全不同。
- **一次写完直接上线**。正确顺序是手动触发跑两三次、看完整运行日志、修 instruction，再交给调度器。

## 可复用建议

把五要素做成自己的模板，新任务先填空再精简。跑满一个月的任务回头 review 一次 instruction——你会发现至少一半的历史失败，都对应着模板里没填的那一格。这个模板攒多了，就是你的任务编排资产库。

## 总结

Cron instruction 不是备忘录，是写给未来某个无人值守时刻的运行手册。检验标准只有一条：假设执行那一刻没有任何人可以提问，照着这段话，agent 能不能一次跑对。能，就上线；不能，回去补要素。
