## 背景

社区每天要从 RSS、GitHub Release、各论坛手工筛内容发精选帖，重复劳动且容易漏。我基于 OpenClaw 搭了一条「采集 → 总结 → 审 → 发」的流水线，让 agent 干粗活，人只做最后把关。目前已稳定运行一个多月，把设计和踩过的坑记录如下。

## 问题

全自动发帖的风险比想象中大：LLM 输出格式不稳、同一内容重复发、模型补幻觉、目标站限频。直接放开全自动，第一条翻车帖很快就会出现。所以第一个设计决策是：**v1 只做半自动**——agent 产草稿，人确认后才发布。

## 架构与步骤

整体分四层：

1. **采集层**：OpenClaw 定时任务（cron）触发抓取 skill，拉 RSS / GitHub Release，原始条目写入 SQLite，带来源、时间、内容 hash。
2. **总结层**：agent 读未处理条目，按固定模板产出结构化 JSON：一句话摘要、三个要点、原文链接、建议标签。温度调低，system prompt 中禁止补充来源之外的信息。
3. **审核层**：草稿推到我的私聊频道，附「发布 / 丢弃」两个动作，确认后才调用发布工具。
4. **发布层**：社区发帖接口封装成独立的 MCP tool，内部做参数校验、客户端限速、token 刷新，发布成功后回写状态库。

采集、总结、发布三者解耦，中间全靠 SQLite 传状态，任何一环挂了重跑即可。

## 踩坑实录

- **JSON 输出不稳**。模型偶尔在 JSON 前后加一句「好的，以下是……」。解法是 schema 校验 + 失败重试，放弃正则硬抠。
- **重复发帖**。RSS 的 pubDate 根本不可靠，同一条会抓到两次。最后用「标题 + 链接」的 hash 查重才真正堵住。
- **幻觉**。模型自作主张补了一个不存在的版本号。约束改为：事实字段必须逐字来自来源，agent 只做压缩和排序，人审兜底。
- **Markdown 转义**。代码块里的下划线、星号被目标站解析得乱七八糟。发布前按目标站规则本地预渲染一遍，有问题就拒发。
- **限频与凭证**。重启后 token 失效、连续 429。改成客户端令牌桶限速 + token 自动刷新，不赌服务端宽容。
- **时区**。cron 按 UTC 跑，发帖时间漂移 8 小时，被群友提醒才发现。显式指定时区。
- **密钥泄漏**。初期图省事把 key 写进 prompt，结果全在日志里。key 只放环境变量，由工具层注入，prompt 永远不碰。

## 可复用建议

1. 半自动优先，全自动是渐进放权：先跑两周零事故，再放开低风险动作。
2. 发布动作独立成 tool，换一个社区只换一层，采集和总结全部复用。
3. 一切外发内容先落库，可追溯、可回滚，出事能定位到具体一次运行。
4. 幂等、限流、重试都在客户端做，别依赖外部服务的行为。
5. 加心跳监控。静默失败比报错可怕得多——连续两天没发帖没人发现才是事故。

## 总结

机器人本体一天就写完了，真正花时间的是边界、幂等和兜底。agent 负责产能，人负责责任，工具层负责安全，三者分清，这套东西才敢长期挂着跑。表结构和 skill 配置我整理在附件里，欢迎在评论区交流改进。
