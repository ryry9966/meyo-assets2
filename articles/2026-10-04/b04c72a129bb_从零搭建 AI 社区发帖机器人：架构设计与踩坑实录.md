# 从零搭建 AI 社区发帖机器人：架构设计与踩坑实录

## 背景

我们社区的内容一直很分散：GitHub issue、群聊讨论、文档更新各在一处，靠人工整理成周报发帖，坚持了三个月就断了。于是决定做一个发帖机器人：定时拉取数据源，由 Agent 生成草稿，审核后自动发布到社区板块。

选型没有犹豫：OpenClaw 作为 Agent 运行时，工具层全部走 MCP，调度用最朴素的 cron。能少一个依赖就少一个。

## 目标与约束

先立几条硬约束，后面所有设计围绕它们展开：

1. Agent 不直接拥有发布权限，必须经过人工审核队列；
2. 任何一次运行都不能重复发帖（幂等）；
3. 全流程落盘，每篇帖子的数据来源可追溯；
4. 单日 token 成本有上限，不做全量抓取。

## 架构与做法

整体分三层：

**采集层**：一个 MCP server 暴露 `sources.fetch` 工具，内部维护增量游标（上次同步时间），只返回新增的 issue、讨论和文档变更，原始数据连同哈希落盘到本地 JSONL。

**生成层**：OpenClaw agent 以 headless 模式被 cron 拉起，读取当日增量数据，按 skill 中的模板生成结构化草稿——强制 JSON Schema 输出（标题、摘要、正文、标签、引用来源），校验失败自动重试一次。

**发布层**：另一个 MCP 工具 `board.publish`，只接受队列中状态为 approved 的草稿。审核用极简 Web 页面，人工点通过后状态翻转，下一个 cron 周期完成发布。

```
cron → OpenClaw agent → MCP: sources.fetch → 增量落盘
     → 生成草稿（Schema 校验）→ 审核队列 → MCP: board.publish
```

## 踩坑实录

**1. 重复发帖。** 上线第三天同一篇日报发了两次。排查发现 agent 超时重试时，发布工具没有幂等键。修复：以「数据源游标 + 日期」生成 content hash，publish 前先查重。

**2. 结构化输出偶尔失控。** 模型偶发在 JSON 外包裹解释文字，下游解析直接崩。用 Schema 约束加重试解决，同时把重试次数锁死为 1，避免死循环烧 token。

**3. 增量游标的时区坑。** 数据源时间戳是 UTC，调度按本地时区跑，傍晚的数据被漏抓。后来统一全链路 UTC，只在展示层转时区。

**4. 权限一开始给大了。** 最初图省事把发布权限直接挂给 agent，某次抓取到的外部内容里带了注入指令，差点自动发帖。这坚定了拆出审核队列的决心——生成和发布必须在权限上隔离。

**5. Markdown 转义。** 正文里的下划线、尖括号在社区渲染时被吃掉，最后在 publish 工具里统一做了一层转义白名单。

## 可复用建议

- 生成与发布权限物理隔离，agent 永远只写草稿；
- 一切以内容哈希做幂等键，重试才是安全的；
- 增量游标 + UTC 时间戳，能避开八成调度类问题；
- 结构化输出必须 Schema 校验，重试要有上限；
- 每个环节落 JSONL，出问题可以回放定位。

## 总结

机器人现在稳定跑了六周，日均审核 3~5 篇草稿，人工只需两分钟。最大的心得是：这类项目里，难的不是让模型生成内容，而是工程上的幂等、权限隔离和可追溯。MCP 把工具边界切得很清楚，OpenClaw 的 headless + skill 机制让调度侧几乎零胶水代码。建议先跑通「抓取 → 草稿 → 审核 → 发布」的最小闭环，再逐步加数据源，比一开始设计大而全的架构划算得多。
