## 背景

云端 API 用久了，三个问题越来越明显：Agent 频繁调工具，token 消耗惊人；敏感日志不想出本地；偶尔限流断供打断自动化流程。于是把一部分推理搬回家里跑，成了很自然的下一步。这篇记录我在一张 8GB 显存显卡（RTX 4060）+ 32GB 内存的机器上，给 OpenClaw agent 接一个本地模型的完整过程。

## 问题

核心矛盾很清楚：**显存有限，但我既要能塞下模型权重，又要留出长上下文的 KV cache，还得保证工具调用质量不掉档**。很多教程只讲"能跑通"，不讲 agent 场景下真正重要的指标。

## 做法

**1. 先算账，再选模型。** 显存占用 ≈ 参数量 × 每参数字节数 + KV cache。7B 模型 Q4 量化约占 4.5GB，8GB 显卡还能留 2-3GB 给 KV cache，够撑 8K-16K 上下文。低于这个预算就别考虑 14B 密集模型了。

**2. 选模型看三点：** 中文能力、function calling 支持、有没有现成 GGUF 量化版。我最终用了 Qwen 系列的 7B instruct 量化版，工具调用稳定性明显好于同尺寸的通用模型。

**3. 部署走 Ollama，一步到位：**

```bash
ollama pull qwen2.5:7b-instruct-q4_K_M
```

默认在 11434 端口提供 OpenAI 兼容接口，不用自己搭 server。

**4. 接入 OpenClaw：** 把 agent 配置里的 base_url 指向 `http://localhost:11434/v1`，模型名填本地 tag。MCP 工具链路不动，只换底层模型。

**5. 用真实任务压测。** 别拿"写首诗"测试，直接循环跑你日常的 agent 任务，记录 token/s 和工具调用失败率，这才有参考价值。

## 踩坑点

- **显存爆了不报错。** Ollama 会默默把放不下的层卸到 CPU，速度从 40 token/s 掉到 3 token/s，看起来"还在跑"。用 `ollama ps` 确认 GPU 占用率是 100%，别只看有没有报错。
- **上下文不是免费的。** KV cache 随长度线性涨，16K 上下文能多吃 2GB 显存。设 `num_ctx` 之前把总账算清，别照抄别人的配置。
- **量化等级别贪低。** Q2 以下输出的 JSON 经常崩，agent 场景工具调用解析失败等于全链路瘫痪。底线是 Q4_K_M，差的那点显存不如去砍上下文长度。
- **function calling 模板不匹配会静默失败。** 换模型后如果工具突然不被触发，先怀疑 prompt 模板，再看模型卡是否声明了 tool-use 训练。
- **温度墙真实存在。** 夏天长任务跑到 85°C 降频，吞吐直接减半。花五十块整理机箱风道，比换模型划算。

## 可复用建议

- **本地干粗活，云端兜底。** 在 OpenClaw 里做一层路由：摘要、分类、格式化这类高频低难任务走本地，复杂推理和长上下文走 API，失败自动 fallback。成本结构立刻改善，稳定性不受影响。
- **把"能否稳定输出合法 tool call JSON"作为选模型的第一个指标**，通用评测分数往后排。
- **记配置流水账。** 每次改量化版本、上下文长度、参数配置，都用脚本记下实测 token/s。三个月后调优时，这份数据比任何博客都可靠。
- **先跑通再优化，先压测再上线。** 拿 hello world 验证的部署，在真实 agent 负载下大概率要返工。

## 总结

本地部署不是要替代云 API，而是改写 Agent 的成本结构：把高频、低难度、隐私敏感的推理留在家里。一台 8GB 显卡的普通家用机，今天就能稳定跑 Q4 量化的 7-8B 模型，支撑日常 agent 任务。路线很简单——算清显存账、选对量化档、压测真实负载、留好云端兜底。剩下的，就是让它跑着，慢慢攒数据。
