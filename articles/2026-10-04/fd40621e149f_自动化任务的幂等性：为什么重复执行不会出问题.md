## 背景

OpenClaw 上的自动化大致有三类入口：cron 定时任务、webhook 触发、消息或队列驱动的事件。再加上 Agent 本身的多步 MCP 工具调用和各层网络重试，"同一个逻辑操作被执行两次以上"其实不是异常，而是常态：工具调用超时后客户端会重试，webhook 服务端按 at-least-once 投递，长任务跑得慢一点，下一次 cron 就会重叠。写自动化时默认"只跑一次"，迟早翻车。

## 问题

幂等性的定义很朴素：同一操作执行一次和执行 N 次，最终效果相同。不满足这个性质的操作，在自动化里的典型表现是：

- 通知把同一条消息发两遍；
- webhook 重试导致工单或记录重复创建；
- 两个实例并发写同一文件，内容写坏；
- 定时任务重叠执行，数据被处理两次。

这些问题在单次测试里几乎复现不出来，只在网络抖动、进程重启、任务变慢时出现——恰恰是生产环境最常见的时刻。

## 做法

核心思路：给每个"逻辑操作"一个稳定标识，执行前查重，执行后记录。落到实践中，按优先级做四件事：

1. **优先用天然幂等的操作。** 固定路径的原子覆盖写、按 ID 的 upsert、按 ID 删除、"把状态置为 X"的条件更新，这些天然可重放。能用"覆盖"就不要用"追加"。
2. **在入口处做幂等键去重。** webhook 取上游的 delivery ID，消息事件取 message ID，cron 任务用「任务名 + 调度窗口」拼 key。建一张 `processed_events` 表（key 加唯一索引、状态、结果引用、过期时间），处理前 INSERT，冲突则直接返回上次结果。
3. **把查重下沉到数据库约束。** 两个实例并发时，应用层的 check-then-act 必然有竞态；唯一索引加捕获冲突错误才是可靠的。
4. **外部 API 支持幂等键就传。** 不少支付、工单类 API 支持客户端幂等键，把同一个 key 传过去，重试由对方兜底。

## 踩坑点

- **幂等键不稳定。** 用时间戳或每次随机 UUID 当 key，重试时 key 变了，去重形同虚设。key 必须来自逻辑操作本身，而不是某一次执行。
- **作用域错误。** 全局去重会把"每天跑一次的日报"第二天也拦掉。要么给 key 带时间窗口，要么加 TTL。
- **记录与执行不一致。** 先记 key 再执行，执行失败会挡住后续合法重试；先执行再记 key，中间崩溃就会重复。尽量把记录和效果放进同一事务，或保证重放本身无害。
- **分层重试叠加。** HTTP 客户端重试一次、队列再投递一次，实际是 4 次执行。去重应放在最外层入口，而不是链条深处。
- **Agent 生成类步骤。** LLM 重跑结果不一样，幂等不等于输出一致。要明确哪次结果生效并持久化，重试时复用它，而不是重新生成。

## 可复用建议

- 把 `processed_events` 表做成插件和脚本的标配模板，配 TTL 定期清理。
- 日志里始终带上幂等键，排查重复问题时能串起整条链路。
- 把幂等当成测试项：staging 里把同一任务连跑两遍，断言副作用数量为 1。
- 长任务用锁（文件锁或 DB 锁）加幂等双保险：锁防重叠，幂等防重放。

## 总结

幂等性不是加分项，而是自动化的入场券。OpenClaw 的重试、重叠、重投递都是设计内的行为，你的任务脚本只要认真回答一个问题——"这个操作被跑两次会怎样"——并把答案落到唯一约束和幂等键上，自动化才敢真的放手让它跑。
