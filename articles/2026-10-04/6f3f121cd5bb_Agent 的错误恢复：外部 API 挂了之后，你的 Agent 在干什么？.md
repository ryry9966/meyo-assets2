## 背景

Agent 自动化跑了一段时间后会发现：demo 里丝滑的流程，上生产后大部分故障不是模型"变笨"，而是外部依赖挂了——LLM 供应商限流、MCP 工具背后的第三方 API 返回 5xx、某个插件的服务直接超时。传统后端对这类问题有成熟打法，但 Agent 有自己的特殊性：它在循环里做决策，一次失败的工具调用可能污染整条任务链。

## 问题在哪

Agent 场景下，API 故障的破坏路径和普通服务不同：

1. **模型不知道该放弃**。把原始报错丢回上下文，模型大概率选择"再试一次"，无限重试烧 token。
2. **模型会编结果**。工具返回空或报错时，部分模型会"合理脑补"继续往下走，产出看起来正常、实际全是幻觉的结论。
3. **副作用不可回滚**。重试一个非幂等的写操作（下单、发通知），成功两次就是事故。

## 做法：把重试逻辑从模型手里拿走

核心原则一句话：**确定性的事交给代码，模型只负责拿着诚实的信息做规划。**

具体分层：

- **第 0 层：客户端快速失败。** 所有工具调用强制设超时（我一般 30s，长任务 60s），连接限流，绝不让一次调用挂死整个循环。
- **第 1 层：错误分类。** 429/5xx/超时归为可重试；400/401/404 归为不可重试，直接失败并记录。429 优先读 `Retry-After`，别自己猜。
- **第 2 层：有界退避重试。** 指数退避 + 抖动，最多 3 次。写操作带幂等键，或干脆不自动重试，留给上层决策。
- **第 3 层：降级。** 重试耗尽后不要硬抛异常打断任务，而是给模型返回结构化说明：`tool:x 连续 3 次失败(限流)，可用部分数据:…，建议跳过该步骤或询问用户`。用受限的措辞模板，模型乱编的概率会明显下降。
- **第 4 层：熔断。** 连续 N 次失败就把该工具标记为 down，冷却 5 分钟，期间调用直接走降级分支，不再烧重试成本。
- **第 5 层：检查点。** 每次有副作用的外部调用前持久化 Agent 状态，故障恢复后续跑，而不是整个任务从头来。

在 OpenClaw 里，这些逻辑建议收在统一的 tool executor / MCP 中间层，别散落在每个插件里各写一套。

## 踩坑记录

- **让模型自己决定重试策略**：实测基本等于无限循环，重试必须是代码行为。
- **429 和 500 一视同仁**：限流要按配额窗口退避，无脑重试只会更糟。
- **超时设太长**：120s 的超时在循环里就是全局卡顿；太短又会对慢但正常的 API 误判。
- **吞掉错误返回空成功**：Agent 会基于空数据继续推理，比直接失败危害大得多。
- **熔断阈值太敏感**：一次抖动就开闸，降级反而成了常态。

## 可复用建议

1. 所有工具调用过同一个中间层：超时、重试、分类、结构化错误返回，策略集中管理。
2. 给关键工具写降级预案：备用数据源、缓存、还是直接跳过并告知用户。
3. 在 CI 里 mock 429/500/超时，把失败路径当正常用例测，而不是等线上第一次故障才补。
4. 客户端主动限速在供应商配额之下，留安全余量。

## 小结

Agent 的容错不是提示词工程，是系统工程。模型循环之外那一圈确定性代码——超时、分类、退避、降级、熔断、检查点——才决定了外部 API 挂掉时，你的 Agent 是优雅降级，还是一本正经地胡说八道。欢迎在评论区交流你们遇到过的故障案例。
