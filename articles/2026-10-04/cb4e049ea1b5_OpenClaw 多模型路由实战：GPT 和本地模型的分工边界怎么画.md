## 背景

OpenClaw 的 agent 跑一个任务往往不是一次调用：拆解规划、选工具、生成代码、整理输出，每个环节都打到同一个旗舰模型上，账单和延迟很快就撑不住。把主力换成本地模型（Ollama 跑 Qwen 这类）省了钱，但复杂推理和多步工具编排的质量立刻掉一截。多模型路由要解决的，就是“哪类调用给 GPT、哪类留在本地”这条线怎么画。

## 问题

两种常见做法都会翻车。一种是全走 GPT，除了成本，内部数据也跟着出去了；另一种是“本地优先、失败再回退 GPT”，结果质量抖动、重试风暴，trace 里一半都是兜底重跑。路由的核心不是配 fallback，而是按调用分级，而不是按感觉。

## 做法与步骤

1. **先分类调用，再谈模型。** 我们把调用分两档：高风险（多步规划、代码重构、跨工具编排、面向用户的最终输出）走 GPT；低风险（分类、抽取、摘要、改写、embedding、格式转换）走本地。中间态（单工具参数生成）默认 GPT，评测过关后再降级。
2. **隐私红线单独一条规则。** 涉及内网数据、客户 PII 的调用无条件路由到本地，优先级高于一切性能考虑，写死在配置里，不靠 prompt 约束。
3. **规则声明式，进仓库版本化。** 示例：

```yaml
router:
  rules:
    - match: { task: [classify, extract, summarize] }
      model: local/qwen2.5-14b
    - match: { sensitivity: internal }
      model: local/qwen2.5-14b
  default: openai/gpt-4o
  fallback: [openai/gpt-4o-mini]
  timeout_ms: 8000
```

4. **每个路由决策写入 trace。** 命中哪条规则、耗时、是否触发 fallback，先有数据再调策略。
5. **评测集先行，影子流量切换。** 每类任务维护 20–50 条固定 case，本地模型先以影子模式并行跑，pass rate 追平再切真实流量。

## 踩坑点

- **tool-call 格式差异是头号杀手。** 本地模型输出的工具 JSON 经常差一点：字段顺序、多余键、枚举大小写，下游 MCP 工具直接报错。别急着怪路由，先在网关层加 schema 校验和自动修复，能砍掉一大半“本地不行”的误判。
- **兜底会放大故障。** 本地超时 → fallback 重跑整条工具链，成本翻倍还可能重复写数据。兜底前确认步骤幂等，或者记录断点只重跑失败那一步。
- **本地延迟抖动看起来像“变笨”。** GPU 和别的任务共用时排队波动很大，trace 里加上队列长度才能分清是模型问题还是资源问题。给 agent 单独钉一个实例，这个钱别省。
- **摘要降级是隐性的。** 用本地模型做记忆压缩、再用 GPT 继续对话，质量下降不直观但会累积。压缩这一步建议和消费它的调用保持同一档。

## 可复用建议

- 按任务类型路由，不按单次请求的感觉；规则改动走 review。
- 想调策略，先看路由决策日志，没有数据的优化都是玄学。
- 灰度永远先行，影子模式对比一周再切。
- 经验值供参考：典型 agent 负载里本地模型能稳住 60%–70% 的调用量，但第一版建议只放 40%，跑稳了再放。

## 总结

多模型路由本质是工程问题而不是模型问题：一条隐私红线、一套任务分级、一份评测集，比反复换模型有效得多。从两条规则起步，让 trace 里的数据替你做后续决策，这条线自然会越画越准。
