## 背景

OpenClaw 的定时任务让 Agent 按计划无人值守地干活：定点抓数据、总结消息、推送提醒。很多人的第一版任务是“跑几天后悄悄没产出”，或者每天推一堆不相干的内容。问题多半不在调度本身，而在 instruction 怎么写。

## 问题：cron instruction 不是聊天 prompt

聊天可以追问、有完整上下文，cron 任务两者都没有：

- 无人在场，Agent 有疑问只能瞎猜或直接放弃；
- 每次运行上下文很窄甚至空白，“按之前说的”这类话会失效；
- 失败的表现是沉默——你以为它在正常跑，其实早就报错了。

所以 cron instruction 的标准是：**一个没接触过项目的实习生，不问任何人也能一次做对**。

## 做法：五段式骨架

建议把每条 instruction 固定成五段：

```text
[触发上下文] 这是定时任务，每天 09:00（Asia/Shanghai）自动触发，非交互。
[数据源与范围] 只用 <工具名> 查询 <具体对象>，筛选条件：<明确条件>。
[输出格式与渠道] 总结不超过 15 行，推送到 <具体会话>，格式：条目 + 一句话理由。
[失败处理] 无结果：也发一条"今日无结果"。工具报错：重试一次，仍失败则原样上报错误。
[边界] 不要做上述之外的写操作；不要提问；不要自行扩大范围。
```

落地顺序：

1. **先写触发上下文**。开头声明“这是定时任务、非交互”，能明显减少 Agent 的反问倾向。
2. **数据源写死**。工具名、对象名、筛选条件逐字写清，避免“最新的”“热门的”这类模糊词——尤其挂了多个 MCP server 时，不点名工具它就会自己挑。
3. **锁死输出渠道和格式**。不指定渠道，结果可能落在默认会话里；不限长度，总结会越写越注水。
4. **预写失败分支**。“无结果也要发一条消息”是把沉默变成可见信号的关键。
5. **先手动触发几次**。观察三五次输出稳定了，再启用调度。

## 踩坑点

- **相对时间漂移**：“昨天”取决于运行时刻和时区，写“运行时刻前 24 小时”或明确日期。
- **没写输出渠道**：任务显示“成功”，消息却发到你永远不看的地方。
- **沉默失败最贵**：只想 happy path、不写报错处理，结果问题拖一周才发现。
- **instruction 膨胀**：一条指令塞多个职责，Agent 容易漏做，token 也烧得快；一个任务一条，链路拆开。
- **边界动作没测过**：定时任务无人值守，发消息、删文件等写操作必须显式白名单化。

## 可复用建议

- 把 instruction 当代码管理：存文件、进 Git，每次迭代只改一处。
- 每句话可验证：“只输出 star 周增长超 50% 的仓库”优于“挑几个好项目”。
- 单独配一个心跳任务：用低频 job 定期汇报“我还活着”，调度系统自身的健康也要可观测。
- 每次改动后手动触发回归一次，像发布代码一样对待。

## 总结

Cron instruction 的本质是给无人值守的员工写 SOP：上下文、来源、格式、失败处理、边界，五件事说清，再用手动触发验证。它的质量标准不是“能不能跑起来”，而是“包括失败在内的每种状态是否可见”。当你的任务能做到“失败了也会发一条消息”，才算是真的上了生产。
