## 背景

E2E 测试是个老问题：写起来慢、维护成本高、覆盖率常年上不去。团队里通常只有一两个人愿意碰，其他人能躲就躲。Agent + MCP（尤其是浏览器自动化类 MCP，比如 Playwright MCP）成熟之后，这件事有了新解法：**让 Agent 真实操作一遍应用，基于真实交互生成测试**，而不是凭空想象。

## 问题：直接生成为什么不好用

如果你只是丢一句“给登录页写个 E2E 测试”，产出基本没法用：

- 选择器是编的，猜一个 `data-testid`，页面上根本不存在；
- 断言是空话，"期待页面加载成功"等于没断言；
- 等待全是硬编码 `sleep`，CI 里必炸。

根本原因只有一个：Agent 没看过真实 DOM，也不了解你团队的测试规范。它写的是“看起来像测试的代码”，不是“能跑的测试”。

## 做法：五步协作流程

1. **接上浏览器 MCP**。让 Agent 能打开页面、截图、读取可访问性树，这是所有后续步骤的前提。
2. **准备测试规范文档**。目录结构、命名约定、page object 组织方式、选择器优先级（`data-testid` > role > text）、禁止 sleep。放进仓库，要求 Agent 动手前先读。
3. **先探索，后落码**。让 Agent 以探索模式走一遍目标流程，输出它看到的每一步操作和元素定位。你先确认路径对不对，再让它写成测试代码。跳过这一步是生成质量差的头号原因。
4. **建立运行闭环**。让 Agent 自己执行测试、读失败日志、自己修。超时、元素未找到这类报错对 Agent 是很好的反馈信号，通常两三轮就能收敛。
5. **人工 review 断言质量**。重点看它断言的是业务结果（订单状态、数据落库）还是 UI 现象（元素可见）。后者是常见的水测试。

## 踩坑点

- **选择器幻觉**：没经过真实运行的生成代码，选择器大概率是编的。原则很简单：没跑过不许合。
- **语义等待**：发现 `sleep` 就打回，让 Agent 统一改成语义等待（等响应、等状态）。
- **测试数据假设**：Agent 默认环境里有干净数据。提前准备好 seed 脚本和 fixture 工具，并在规范里写明，否则它生成的用例在本地能过、CI 全挂。
- **一次生成太多**：每批 3~5 个用例，review 通过再继续。错误模式会复制扩散，一次生成二十条然后全废，比分批慢得多。

## 可复用建议

- 把**测试规范 + 页面地图 + 常用 fixture** 做成三份小文档放仓库里，Agent 生成质量立竿见影。这三份文档本身也是给新人看的，一鱼两吃。
- **修 bug 时顺手让 Agent 补一条复现用 E2E**。这是它最擅长、最不容易写错的场景：路径已经明确，断言就是复现条件。
- CI 里失败的 E2E，先丢给 Agent 做首轮诊断。大部分失败（等待不足、环境差异）它能给出可信结论，人工只处理它判断不了的。

## 总结

Agent 写 E2E 的正确姿势不是"一键生成”，而是把它当成一个**需要上下文、需要反馈、需要规范的初级工程师**：给足约定，让它真实操作应用，用测试运行结果做闭环。做到这三点，生成代码的可用率会有明显提升，E2E 覆盖的成本也能降到一个团队愿意持续投入的水平。工具不解决纪律问题，但能把纪律的成本降下来。
