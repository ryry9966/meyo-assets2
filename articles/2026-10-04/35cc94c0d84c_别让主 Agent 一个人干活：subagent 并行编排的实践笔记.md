## 背景

用 OpenClaw 做自动化久了，主会话串行执行的问题会越来越明显：一条指令接一条指令地跑，任务一多就慢，而且中间过程会把主会话上下文塞得满满当当，后面干活质量跟着下降。subagent 的价值就在这里——主 agent 把可拆的任务派发给多个子会话并行跑，各自拥有独立上下文，结束后只把结论交回来。听起来很美好，但我们第一次实战就翻了车，这篇记录一下怎么拆、怎么避坑。

## 问题

举个真实场景：周检任务 = 扫一遍代码库的 TODO、检查依赖版本、汇总本周日志里的报错模式。三件事互不依赖，串行做要十几分钟，主会话还堆满文件内容。拆成三个 subagent 并行，理论上三四分钟收工。实际第一次跑：子 agent 返回的东西没法直接用，有的缺文件路径，有的中途失败但主 agent 没察觉。

## 做法

1. **先做依赖分析，再谈并行。** 任务之间没有数据依赖才拆；有依赖的（比如先测后修）留在主会话串行。
2. **契约先行。** 每个 subagent 的 prompt 写死三件事：输入是什么（明确到路径和范围）、产出格式（比如"只返回 JSON：文件、行号、严重度"）、边界（只读，禁止改文件）。
3. **粒度控制在"一次会话能独立完成"。** 一个 subagent 一个目标，两到五步能做完。太粗拆不动，太碎反而亏——每个子 agent 都要重新加载工具和上下文，开销翻倍。
4. **主 agent 只做分发和汇总。** 关键点：子 agent 看不到主会话，它需要的信息必须显式塞进 prompt。汇总时要求三段式返回：状态 / 结论 / 证据。

## 踩坑点

- **上下文隔离是双刃剑。** 你以为它知道的信息它不知道，不传就靠猜，猜出来的结果没法用。
- **并行写文件必冲突。** 我们的约定：读操作随便并行，写操作要么分区（各写各的文件），要么收口回主会话串行执行。
- **失败会静默。** 子 agent 跑挂了不吭声，主 agent 拿到空结果当成功。对策是强制返回状态字段，缺了就重试。
- **MCP 工具有并发上限。** 五个子 agent 同时打同一个 MCP server，直接撞 rate limit。并行度从 2–3 起步，观察再调。
- **别套娃。** subagent 里再开 subagent 很快失控，目前压到两层封顶。

## 可复用建议

- 把 subagent prompt 做成模板：目标 / 输入 / 输出格式 / 禁止事项，四段固定。
- 汇总结果用统一 schema，主会话好校验、好存档、好回溯。
- 流水线跑通后，把分发逻辑固化成 skill 或挂 cron，别每次手写。
- 先验证正确性，再提并行度。宁少勿多。

## 总结

subagent 编排的核心不是"开得多"，而是"拆得对"：任务无依赖、契约清楚、读写分离、失败可见。这四点做到位，多 agent 并行才真正省时间——否则只是把串行的混乱，升级成了并行的混乱。
