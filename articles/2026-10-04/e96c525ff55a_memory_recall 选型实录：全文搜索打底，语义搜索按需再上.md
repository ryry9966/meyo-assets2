## 背景

Agent 跑上几周，memory 目录里就会积下几百条笔记：排障记录、用户偏好、配置片段、当时的决策理由。`memory_recall` 是 agent 回忆这些内容的唯一入口，它选什么检索方式，直接决定 agent 是"记得"还是"自以为记得"。最常见的纠结是：要不要一步到位上 embedding + 向量库。

## 问题

把实际的 recall 查询拉出来看，基本分两类：

- **精确类**：`ERR_CONN_RESET`、某个文件路径、配置项名、版本号。全文搜索几乎必中；语义搜索反而可能把标识符"意译"后偏移，召回了主题相近但 ID 对不上的片段。
- **模糊类**：用中文问"上次登录超时怎么解决的"，而 memory 里是英文笔记 "session timeout fix"。全文搜索直接 miss，语义检索能跨语言、跨措辞召回。

个人级语料（几百到几千条）下，这两类查询通常都存在，但占比因人而异。问题就变成：语义检索带来的增量，值不值得多养一个 embedding 服务和一份向量索引。

## 做法

1. **先建全文基线**。SQLite FTS5、BM25，甚至直接 ripgrep。零依赖、结果可解释、毫秒级响应，个人语料规模完全够用。
2. **记录查询日志**。把每次 `memory_recall` 的 query、命中数、最终被 agent 引用的片段落盘，一周后统计 miss 类型：是标识符没匹配上，还是措辞对不上。
3. **只有"意译类 miss"占比明显时才加语义**。选多语 embedding 模型，按笔记或小节切块，每块带时间戳和来源元数据。
4. **混合检索**。两路各取 top-k，用 RRF（倒数排名融合）按排名合并，最终只回 5~8 条，避免撑爆上下文。
5. **建一个 20~50 条真实查询的评测集**。任何检索改动前后各跑一遍，用命中率说话，不靠感觉。

## 踩坑点

- **中文分词**。FTS5 默认 tokenizer 对中文整段切，查"超时"匹配不上"连接超时"。要么换 trigram，要么分词后入库。
- **向量索引过期**。memory 是 agent 随时改写的，embedding 索引必须挂在写入路径上同步更新，否则召回的是删掉的旧版本。
- **语义搜索"自信的错误"**。返回主题相关但内容不对的片段，模型会当上下文照单全收，比返回空结果更危险。给召回结果附出处和分数，并在 prompt 里注明低分片段可能无关。
- **分数不能直接混排**。BM25 分数和余弦相似度量纲不同，直接加权会一边倒。先各自归一化，或者干脆用 RRF 只看排名。

## 可复用建议

- **写入时为检索服务**。memory 条目头部固定带日期、关键词行、相关 ID，等于给全文搜索留抓手，成本几乎为零。
- **精确标识符永远信任全文/精确匹配**，不要交给语义。
- **语料少于 500 条，大概率全文搜索 + 好的写入习惯就够了**。别为了架构先进性引入向量库，维护成本先于收益到来。
- **保留开关**。两路检索支持独立禁用，召回质量异常时能快速二分定位是哪一路的问题。

## 总结

结论一句话：先用全文搜索打基线，用查询日志证明语义检索有真实增量，再上混合。实践中检索质量的上限，往往不在"更聪明的相似度算法"，而在写入 memory 那一刻有没有想过它未来会被怎样检索。
