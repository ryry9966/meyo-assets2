# 背景

OpenClaw 的 Agent 在一次任务里其实混杂着多种调用：任务规划、MCP 工具调用的参数生成、长文本摘要、检索后的信息抽取，以及高频的小调用（分类、打标签、格式化）。很多团队的初始配置是"一个模型打天下"——要么全接云上大模型，月底账单难看；要么全换本地模型，规划质量下降，Agent 在工具调用上反复重试。多模型路由要解决的就是这个错配。

# 问题

路由的难点不在"能不能切"，而在切错的代价不对称：

- 规划步骤用了弱模型，失败的是整条任务链，重试成本远高于省下的 token 钱；
- 工具参数生成用强模型，绝大多数调用是浪费——这类任务格式清晰、上下文短；
- 隐私数据（内部文档、日志）出网有合规风险，Embedding 和摘要适合留在本地。

# 做法

1. **先给任务分类打标**：plan / toolcall / summarize / extract / embed。OpenClaw 的插件和 MCP 工具在注册时都可以带 route 标签。
2. **建 model pool**：云上强模型作为 plan 通道；本地 14B~32B 级别（vLLM 部署）承担 toolcall、extract；Embedding 固定走本地。
3. **路由策略当配置代码管理**（进版本库）：按 task_type + 风险等级匹配模型，而不是按个人喜好。低风险高频调用走本地，高风险低频调用走云。
4. **配 fallback 链**：本地超时或格式校验失败 → 升级到云模型，重试上限设 2 次，避免两个模型之间来回踢皮球。
5. **加观测**：每次路由记录 task_type、模型、token 数、p95 延迟、成功率，跑一两周再调表。

# 踩坑点

- 本地模型的 tool call JSON 合规率明显低于云模型，务必在 OpenClaw 侧加 schema 校验 + 一次修复重试，别裸信输出。
- 换本地 Embedding 模型后向量维度变了，旧索引必须重建，否则检索会静默劣化，很难第一时间发现。
- 会话记忆/摘要的压缩模型要固定一个。混用会导致摘要风格和口径漂移，Agent 行为不稳定，排查起来非常痛苦。
- 本地 GPU 有冷启动，服务化部署时保持模型 warm，否则第一条 toolcall 的延迟会拖垮整体体验。

# 可复用建议

- 别一开始就全量路由。先单模型跑通，再把高频低风险的 toolcall/extract 挪到本地，这是收益最大的一步。
- 建一个 30~50 条的 golden 任务集做回归评测，每次改路由表先跑一遍，看成功率和成本变化再上线。
- 用"每任务成本 + 成功率 + p95 延迟"三个指标评估路由效果，不凭体感调参。

# 总结

多模型路由本质上是用数据管理一个成本/质量/延迟的三角权衡。经验法则：规划和高风险决策交给云上强模型，格式化、抽取、Embedding 这类高频确定性任务留给本地模型，配上 schema 校验、fallback 和持续观测，路由表就会越调越准。
