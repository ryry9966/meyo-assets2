## 背景

在 OpenClaw 的日常使用里，自动化无处不在：cron 定时任务、webhook 触发的 skill、Agent 在多步流程中反复调用 MCP 工具、插件监听消息后执行动作。这些场景有一个共同前提——**你无法保证任务只被触发一次**。

定时器可能因网络抖动超时后重试；消息通道的投递语义普遍是“至少一次”；Agent 在工具调用超时后，基于对话上下文再试一次也很常见。工程上的现实是：重复触发不是异常，而是常态。

## 问题

判断一段自动化代码是否可靠，有个朴素的检验方法：**把它连续跑两遍，会发生什么？**

- 发消息类任务：群里收到两条重复的日报；
- 写文件/入库类任务：数据重复插入，或文件被追加两份；
- 调外部 API 类任务：建工单、发通知被执行两次。

很多自动化脚本单次运行没问题，一遇到重试、并发或手动补跑就出事故，根源就是非幂等。

## 做法

把幂等落到工程上，核心是三步：

**1. 定义稳定的业务键（task key）。**
从任务输入推导一个确定性 ID，比如日报任务用 `digest-2025-06-01`，webhook 处理直接用事件自带的唯一 ID。注意：不要用时间戳或随机数做 key，否则每次执行 key 都不同，去重完全失效。

**2. 副作用前先落库占位。**
用 SQLite（或一个 JSON 文件）记录已完成的 key。执行副作用前先 `INSERT OR IGNORE`，插入成功才真正执行；唯一约束天然挡住并发场景下的竞态。内存里的 Set 在进程重启后就没了，不要依赖。

**3. 把副作用本身设计成可覆盖。**
优先用 upsert 代替 insert、用覆盖写代替追加写、用“设置状态”代替“累加”。这样即使键控去重失效，重复执行的结果也会收敛。

对不原生支持幂等键的第三方 API，在调用前加自己的去重层；支持的（如支付类接口）直接传 idempotency key。

## 踩坑点

- **“查了再写”不是原子的。** 两个进程同时通过检查、同时执行，是并发触发的经典事故。解法是让数据库唯一约束做最终裁决，而不是信任应用层的 if 判断。
- **超时 ≠ 失败。** Agent 侧收到 timeout 后重试，但第一次调用可能已经在远端成功。工具的返回值要能区分“没执行”和“执行了但响应丢失”，否则重试逻辑怎么写都不对。
- **把去重和幂等混为一谈。** 去重是“拦住第二次”，幂等是“第二次执行也无害”。删除操作、覆盖写天然幂等，追加写和累加不是。有些场景靠幂等就够了，不必强行去重。
- **状态只存在会话内存里。** OpenClaw 重启、换会话、多端运行，状态一丢，去重全部失效。凡是跨执行周期的判断，必须持久化。

## 可复用建议

1. 封装一个小工具 `run_once(key, fn)`：内部用 SQLite 记录 key、状态、执行时间，所有定时任务和 webhook handler 统一走它。
2. cron 任务命名遵循“任务名 + 自然周期”规则，key 自然确定，补跑也不会重复发送。
3. 审计日志按 key 索引，排查时能快速看出哪些任务被重复触发、在哪个环节漏了闸。
4. 写一个“连跑三遍”的测试用例：断言副作用（消息数、行数、文件内容）只发生一次变化。这类测试比 mock 更能暴露设计问题。

## 总结

幂等不是加分项，而是自动化的默认属性。写每个 skill、每个定时任务时，先问一句：“这段代码跑两遍会怎样？”答案如果是“没差别”，这个任务才真正可以交给机器长期运行。
