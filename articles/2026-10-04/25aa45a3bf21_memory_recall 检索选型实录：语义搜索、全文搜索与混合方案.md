## 背景

OpenClaw 的 memory_recall 是 agent 长期记忆的入口：会话中模型调用它，从本地记忆库捞回相关笔记。我目前的记忆库约 800 条 Markdown（决策记录、踩坑记录、环境配置、常用命令），最初只有全文搜索，最近补了语义检索，两条路各跑了一段时间，把结论记下来。

## 问题

全文搜索暴露的典型失败：问“上次端口占用怎么解决的”，笔记标题写的是“3000 端口被占用的处理”，字面对不上，召回为空。语义检索上线后又出现反向问题：查 `ECONNREFUSED`，返回一堆“连接失败相关”的笔记，唯独没有那条精确包含错误码的。两类检索各坏一半。

## 做法与步骤

1. **先建评测集。** 从历史会话里翻出 40 条真实提问，人工标注每条应命中的笔记，指标用 hit@3。没有这个，后面全是凭感觉。
2. **全文路线：** SQLite FTS5，中文分词换 jieba（默认 unicode61 对中文基本不可用），标题和 tags 单独建列、加权。
3. **语义路线：** 笔记按约 300 token 切块，块内拼上标题和 tags；本地 bge-small-zh 出向量，sqlite-vec 存储，查询时实时 embed。
4. **融合：** 两路各取 top10，用 RRF（k=60）合并。试过直接加权原始分数——BM25 和余弦相似度量纲差太远，权重根本没法调，换 rank 融合后才稳定。
5. **对比三版：** FTS-only hit@3 约 0.68，向量-only 约 0.73，RRF 混合 0.85。提升主要来自互补，不是谁碾压谁。

## 踩坑点

- FTS5 默认分词器会把中文整句当一个 token，中文场景必须换分词器，否则召回率约等于掷骰子。
- 别用英文为主的 embedding 模型处理中文记忆，同义改写的召回明显掉；bge-small-zh 这类模型 CPU 上延迟可接受。
- 语义检索会“洗掉”精确标识符。错误码、路径、commit hash、参数名这类 token 必须保留 FTS 通道，或对含标识符的查询直接关键词优先。
- 切块太大稀释相关性，太小丢上下文；块里拼标题和 tags 几乎是零成本的召回提升。
- 编辑/删除笔记后忘重建索引，出现过召回已删除内容的尴尬。索引同步要挂在写入路径上，别靠定时任务兜底。

## 可复用建议

- **默认上混合：** RRF 融合 FTS + 向量，两路各 top10，单一方案的短板能被另一路补上。
- **先测再换：** 20~50 条的评测集半天能建完，比反复调参数有说服力。
- **结构化记忆条目**（标题/tags/日期），召回前先用元数据过滤收窄候选集，比在排序上使劲更划算。
- 记忆量几百条以内、查询偏精确关键词的话，FTS5 + 好分词器已经够用，不必先上向量。

## 总结

语义搜索和全文搜索不是替代关系，是覆盖面互补：语义解决“换个说法还能找到”，全文解决“精确 token 必须命中”。memory_recall 这种高频、低延迟要求的入口，混合方案 + 本地中文模型是当前性价比最高的组合——但前提是先有一套可复现的评测，否则所有调优都是玄学。
