# 本地 LLM 部署：给 Agent 用户的一份务实指南

## 背景

做 Agent / 自动化的都清楚，LLM 调用是高频动作：一个循环跑十轮工具调用，token 费用和延迟都不小。加上部分自动化场景涉及本地文件、聊天记录这类隐私数据，并不想送出去。于是我在一台 32GB 内存的台式机（RTX 4060 Ti 16G + 32G RAM）上搭了本地推理，接入 OpenClaw 的 Agent 流程，稳定跑了两个月。这篇是沉淀，不含营销成分。

## 问题

核心就三个：

1. 手头硬件到底能跑多大的模型；
2. 本地小模型能不能可靠地做 function calling / MCP 工具调用；
3. 怎么无痛接进现有的 Agent 链路，而不是推倒重来。

## 做法

1. **估算资源**。经验值（GGUF Q4_K_M 量化）：7B 约需 5–6GB，14B 约 9–10GB，32B 约 20GB。注意这是权重加 KV cache 的总量，上下文开得越长显存越紧张，别只看模型体积。
2. **装推理服务**。直接上 Ollama，一条命令起服务，自带 OpenAI 兼容端点（`http://localhost:11434/v1`），Agent 框架基本零改造接入。追求极限吞吐可以换 llama.cpp server 或 vLLM，接口协议一致。
3. **选模型**。只选原生支持 tool calling 的模型。我实测 Qwen 系列在中文工具调用上最稳，7B/14B 档位覆盖大多数自动化场景；Llama 系英文任务不错，但中文参数抽取容易飘。
4. **接 OpenClaw**。base_url 指到本地端点，模型名填本地 tag，MCP server 照常挂载。MCP 本来就是本地进程，和本地模型是天然搭配，权限和工具定义完全不用动。
5. **压测**。建一个 10 条固定任务的回归集（含多轮工具调用、参数校验、失败重试），每次换模型或换量化都跑一遍，用数据说话。

## 踩坑点

- **上下文默认值**：Ollama 部分版本默认 num_ctx 很小，长对话直接截断，表现为"模型失忆"。显式设到 8k–16k，同时盯着显存水位。
- **工具调用格式**：不要自己在 prompt 里手写 JSON 约定，用推理层的原生 tool calling，否则模型输出格式时好时坏，排查极痛苦。
- **量化与多步推理**：Q4 以下量化在 5 步以上的工具链里错误率明显上升。宁可换小一档模型用 Q5/Q6，也别用激进量化的大模型跑长链路。
- **采样参数**：Agent 场景把 temperature 压到 0.1–0.3，编造不存在字段的概率会显著下降。
- **并发**：Ollama 默认偏串行，多个 Agent 同时跑要调 `OLLAMA_NUM_PARALLEL`，否则请求排队直到超时，表象还像是模型"卡死了"。

## 可复用建议

- **混合路由**：高频简单任务（分类、抽取、格式化）走本地 7B，复杂推理走云端大模型，整体成本能降一个量级。
- **回归集先行**：先建评测集再换模型，别凭一两次对话的手感下结论。
- **显存留 20% 余量**：给 KV cache 和系统留空间，OOM 排查是最费时间的一类问题。

## 总结

本地部署已经不是玩票：7B–14B 量级 + 原生 tool calling + OpenAI 兼容端点，半天能跑通，日常自动化完全够用。它的定位不是替代云端，而是把高频、隐私敏感、低复杂度的那部分调用收回来。建议先小规模验证，再决定放量。
