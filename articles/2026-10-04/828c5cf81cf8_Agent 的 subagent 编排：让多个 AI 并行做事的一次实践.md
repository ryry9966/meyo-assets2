## 背景

在 OpenClaw 里跑了一段时间单 agent 自动化后，一个瓶颈越来越明显：任务一多，串行执行慢，上下文越滚越长，agent 开始忘事、跑偏。我们的典型场景是批量巡检——十几个服务各查一轮健康状态、日志关键字、慢查询，最后汇总成一份报告。单 agent 顺序跑一轮要二十多分钟，中途一旦幻觉出个不存在的接口，后面的判断全部跟着歪。

这期的解法是 subagent 编排：主 agent 只负责拆任务、派发、裁决，具体活儿丢给并行的 subagent 干。

## 做法

按我们目前跑得比较稳的流程，分五步：

1. **拆任务**。拆的准则是“子任务之间无共享可变状态”。巡检场景天然独立，按服务拆即可。如果子任务要争抢同一个文件或同一条数据，先改任务边界，再谈并行。
2. **定契约**。每个 subagent 的输入是最小上下文（只给它需要的那一个服务的名字和探针地址），输出强制结构化：固定字段的 JSON，比如 `status`、`findings`、`duration`。禁止自由文本汇报。
3. **并行派发，带并发上限**。并发控制在 3–5。这个上限不是性能考虑，而是保护 MCP 工具和下游 API——一旦超过限流，就是一片失败加重试风暴。
4. **主 agent 只做裁决**。收一轮结果、核对 schema、异常的标红，不亲自执行任何查询。主 agent 一旦下场干活，它的上下文就开始膨胀，编排就名存实亡。
5. **失败处理**。每个子任务设超时；失败重试一次；再失败就带着错误原因标记完成，最后统一进报告。绝不让一个卡死的子任务拖住整批。

效果：同样一轮巡检从二十多分钟压到六分钟以内，主 agent 上下文稳定在很小的规模，报告质量反而因为“每个子任务上下文干净”而提升。

## 踩坑点

- **子 agent 返回自由文本**。前两次翻车都在这：聚合时解析不了，主 agent 只好自己去“理解”文本，等于把污染重新引进了主上下文。契约必须带 schema，收到不合格结果直接重试。
- **并行写同一目标**。让 subagent 只产出结果、不落盘，写文件写库统一由主 agent 在收口阶段做，天然避开写冲突。
- **递归派生**。subagent 自己再去拉 subagent，深度不控就是失控。我们硬性限制编排深度为 1，主 agent 之下不再有第二个编排者。
- **日志难排查**。并行日志交错之后基本不可读。给每个子任务生成 run id，工具调用和子 agent 输出都挂在这个 id 下，事后能按条追溯。

## 可复用建议

- 判断要不要拆：子任务如果不独立，硬拆的协调成本会吃掉并行收益，不如老老实实串行。
- 编排的收益只来自两件事：**并行提速**和**上下文隔离**。缺一个都不值得上这套复杂度。
- 心智模型：subagent 是“廉价的、可丢弃的”，主 agent 是“贵的、要保活的”。上下文预算按这个原则分配。
- 聚合层是唯一值得花力气打磨的地方，schema 校验 + 超时降级做好了，整条链路才有稳定性可言。

## 总结

subagent 编排本质上是调度与执行的分离：主 agent 做调度器，subagent 是无状态工人，靠结构化契约通信。它不是万能加速器——任务拆不干净时，它只会放大混乱。但在批量、独立、可结构化验收的场景里，这是我们目前用得最顺手的一种多 agent 形态。欢迎在社区里贴你们的编排参数和失败案例，一起对齐。
