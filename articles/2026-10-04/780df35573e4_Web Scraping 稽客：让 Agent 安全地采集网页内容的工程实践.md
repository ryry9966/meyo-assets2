## 背景

Agent 一旦要回答“现在”的问题——价格、库存、公告、文档更新——就绕不开抓网页。MCP 生态里 fetch/browser 类工具让这件事门槛很低：模型发一句话，内容就回来了。但“能抓到”和“能长期稳定、合规地抓”是两回事。这篇帖子整理我们在 Agent 项目里做网页采集的一些沉淀，供参考。

## 问题

Agent 驱动的抓取和人写爬虫有本质区别：发起方是模型，行为不可预测。常见的翻车姿势：

- 模型循环重试同一批 URL，触发对方风控，整个出口 IP 被封；
- 抓回 500KB 的 HTML 直接塞进上下文，token 爆炸，还混入大量导航噪音；
- 动态渲染页面用 HTTP 抓到空壳，模型却把空壳当“事实”继续推理；
- 遇到登录墙或验证码，模型“聪明地”绕行，留下合规隐患。

## 做法

我们的方案是把抓取收口成一个独立的 MCP 工具，而不是让模型自由发挥。分五步：

1. **白名单 + 频控**。维护允许抓取的域名清单，每个域名设 QPS 上限（我们默认 1 QPS、并发 2），网关层强制执行，模型侧无法绕过。
2. **分层抓取**。先走静态 HTTP + 正文提取（readability 类算法），拿到非空正文直接返回；检测到内容过短或命中疑似 SPA 特征，再降级到 headless 浏览器。绝大多数页面第一层就够了。
3. **清洗与截断**。HTML 转 Markdown，剔除脚本、样式、导航；单页截断到 8K 字符，并在返回值里显式标注 `truncated: true`，让模型知道内容不完整。
4. **缓存与去重**。URL 归一化后做 TTL 缓存（默认 10 分钟），命中缓存的请求不打到对方服务器，Agent 的高频重复提问几乎零成本。
5. **重试与放弃策略**。429/403 走指数退避，最多 2 次；命中验证码页直接返回失败原因，不做任何绕过。这条写死在工具里，模型改不了。

## 踩坑点

- **headless 浏览器必须加内存上限和强制超时**。我们吃过亏：某个页面死循环渲染，浏览器实例内存涨到 3GB，把宿主机拖垮。现在每个会话 60 秒硬超时 + 512MB 上限。
- **编码问题**。不少老站是 GBK/GB2312，不显式处理就是满屏乱码，模型会基于乱码一本正经地回答。检测 charset 后先转 UTF-8 再提取。
- **错误页也是“内容”**。登录墙、软跳转的 404 都会返回 200 加一堆导航文案，模型会当成正文。我们在提取层加了正文长度和链接密度的启发式校验。
- **上下文污染比抓不到更糟**。广告和推荐流一旦进 prompt，回答质量明显下降。清洗这一步不能省。

## 可复用建议

- 工具返回结构化 JSON：`{url, status, fetched_at, content, truncated}`，方便下游判断和审计。
- 多个 Agent 共享一个抓取网关，限速、缓存、日志集中管理，出问题能回溯“模型为什么拿到这段内容”。
- robots.txt 检查放在网关层做一次并缓存结果，不要每个任务重复请求。
- 给模型的能力最小化：不给通用 curl，只给受限的 fetch 工具。

## 总结

让 Agent 安全采集网页，核心不是“抓得更多”，而是“抓得可控”：白名单限速守住边界，分层抓取降低成本，清洗截断保护上下文，明确的失败策略替代模型的“聪明绕过”。工具层做厚一点，模型层就能简单一点。
