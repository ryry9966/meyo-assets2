## 背景

OpenClaw 的 memory 体系本质上是一堆 markdown 笔记加一个 `memory_recall` 工具。助手每次被唤起并不会自动"记得"什么，全靠 recall 从记忆库里捞相关条目塞回上下文。捞得准不准，直接决定它是"靠谱同事"，还是"每次都得重讲一遍"。

我的记忆库目前 400 多条笔记（决策记录、环境配置、偏好、项目上下文），平均每条 100~300 字。`memory_recall` 支持两种检索后端：基于 embedding 的语义搜索，和基于关键词的全文搜索（FTS）。之前一直用默认的语义搜索，直到连续几次明显漏召回，才决定认真对比一次。

## 问题

两个典型翻车现场：

1. 问"上次那个部署超时怎么解决的"，语义搜索返回了三条部署相关的泛泛记录，唯独没命中真正写解决过程的笔记——因为那条通篇没出现"部署"二字，标题是"某服务 504 排查"。
2. 问"我妈生日是几号"，全文搜索一次命中，语义搜索却关联出一堆"家庭""纪念日"的模糊条目。

直觉上"语义更聪明"，但实测是两种失效模式：语义搜索容易泛化过头，全文搜索容易被换词打败。

## 做法

搭了个简易评测：从最近一个月的会话日志里抽出 40 条真实 recall 请求，人工标注期望命中的笔记，分别统计三种方案的 hit@5：

| 方案 | hit@5 | 平均延迟 |
|---|---|---|
| 语义（bge-m3，本地推理） | 72.5% | ~180ms |
| 全文（FTS5 + jieba 分词） | 80% | <10ms |
| 混合（RRF 融合） | 92.5% | ~200ms |

方向很清晰，但样本只有 40 条，数值仅供参考——建议务必用自己的真实流量测，别人的结论不能直接抄。

配置上把两个后端都打开，recall 时双路检索再融合：

```json
"memory": {
  "backends": ["fts", "semantic"],
  "semantic": { "model": "bge-m3", "dim": 1024 },
  "merge": { "strategy": "rrf", "top_k": 5 }
}
```

## 踩坑点

1. **中文分词是全文搜索的命门**。FTS5 默认 tokenizer 对中文基本是按整句切，等于废掉。挂上 jieba（或改用 trigram）之后才真正可用。
2. **换 embedding 模型必须重建向量索引**。中途换过一次模型，维度一致但向量空间完全不同，召回质量肉眼可见地崩，排查半天才发现旧向量没清。
3. **两路分数不能直接加权**。语义相似度和 FTS 分值量纲完全不同，0.5/0.5 相加等于没融合。RRF（按排名倒数打分）简单且稳，推荐直接用。
4. **笔记本身要原子化**。一条笔记只讲一件事，标题尽量带关键词。混合方案再强，也救不了一条塞了五个主题的大杂烩笔记。

## 可复用建议

- 语料在几百条以内、查询多为专有名词时，先跑全文搜索，成本几乎为零。
- 语义搜索的价值在换词、模糊指代、跨语言，但必须配评测集验证，不要信体感。
- 混合 + RRF 是当前性价比最优解，代价只是多一路检索。
- 把 recall 未命中的 case 沉淀成评测集，每次调参跑一遍，避免"越调越差"。

## 总结

没有普适赢家：全文搜索赢在精准和便宜，语义搜索赢在模糊匹配，生产实践里两者互补远大于互斥。我最终的配置是双后端 + RRF，评测集驱动调优。与其争论哪个"更好"，不如先把自己真实的 recall 流量变成可测量的指标——这是比任何选型结论都更值钱的第一步。
