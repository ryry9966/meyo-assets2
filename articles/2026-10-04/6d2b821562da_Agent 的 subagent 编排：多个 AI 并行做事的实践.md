## 背景

单个 agent 干活的典型瓶颈：一个长任务从头跑到尾，上下文越滚越大，工具调用全部排队，中间一步失败就得整段重来。OpenClaw 本身支持多 session，subagent 编排就是利用这一点，把“一个大脑干所有事”改成“一个调度者 + 若干干活的”。最近给一个仓库做依赖升级调研加文档更新，我用这条路线跑通了，记录一下。

## 问题

- 主 agent 上下文被中间产物污染：网页抓取结果、报错日志、搜索摘录全堆在主会话里，越往后越迟钝。
- 串行耗时：五个本可以独立的子任务排队跑，总时长是加法。
- 粒度太粗：整个任务一个会话，无法局部重试、局部回滚。

## 做法

把上面的任务拆成 4 个 subagent：

1. **调研 A**：扫描 `package.json`，列出过期依赖（只读）。
2. **调研 B**：逐个查 changelog 和 breaking changes（只读 + 检索）。
3. **写手 C**：起草迁移文档（独立工作目录）。
4. **审查 D**：对照 diff 检查 C 的草稿（只读）。

关键约束，比拆分本身更重要：

- 每个 subagent 一份 task brief：目标、输入路径、输出格式、工具白名单、预算（调用次数 / 时长）。
- 只读任务不给写权限；写任务各自分配独立目录或 git worktree，避免互相覆盖。
- 并发从 3 开始，跑通再调，不要一上来拉满。
- subagent 回传必须收敛为结构化摘要：结论、风险、涉及文件路径。原始细节留在子会话，主 agent 需要时再取。
- 主 agent 只做四件事：拆分、下发、汇总、冲突仲裁。

## 踩坑点

1. **回传爆炸**。子 agent 把整个文件贴回来，主上下文瞬间撑爆。务必在 brief 里写死“只回摘要 + 路径”。
2. **并发写冲突**。两个 subagent 同时改 README，后者直接覆盖前者。要么按文件划分所有权，要么 worktree 隔离后统一合并。
3. **权限没收紧**。给调研任务挂了 shell，它顺手改了配置文件。工具白名单按任务最小化，MCP 工具分组挂载。
4. **重试放大成本**。一个子任务超时，主 agent 自动重派三次，费用翻倍。设全局预算上限，超了就降级为人工。
5. **拆分过细**。拆出十个只干两分钟活的 subagent，调度开销大于收益。粒度以“独立可交付”为准。

## 可复用建议

- task brief 做成固定模板：目标 / 输入 / 输出格式 / 工具白名单 / 停止条件。
- 读多写少的任务最适合并行；写任务要么串行，要么目录隔离。
- 并发数取 `min(任务数, 3~5)`，先稳定再提。
- 汇总阶段让主 agent 交叉核对子结论，互相矛盾的部分单独仲裁，不要直接合并。
- 给每次编排留一份运行记录：各 subagent 的耗时、调用次数、失败原因，下一轮拆分靠它优化。

## 总结

subagent 编排不是“多开几个窗口”，而是一套带约束的分工协议：上下文隔离、回传收敛、最小权限、明确预算。建议从两三个 subagent 的小流水线跑起，验证回传格式和权限边界没问题之后，再考虑更复杂的依赖编排。工程上，慢一点跑通，比快一步翻车划算。
