## 背景

跑一个长期在线的 OpenClaw 实例，最大的工程难题往往不是工具接得够不够多，而是 agent 的 system prompt 会不受控制地膨胀：MCP 工具用法、日程规则、输出格式……全塞进去之后，最容易被稀释的恰恰是「这个 agent 到底是谁」。OpenClaw 把身份拆成了独立的 `IDENTITY.md`，与 `AGENTS.md`、`MEMORY.md` 平级，每次会话加载。听起来只是个小文件，但我们在几个长期实例上的经验是：它是唯一决定「人格连续性」的地方，值得像代码一样对待。

## 问题

默认的 IDENTITY.md 通常只有几行——名字、emoji、头像。实际使用中会遇到三类典型问题：

1. **人格漂移**：换底层模型、加新插件之后，语气突然变化，长期交互的用户能明显感知到「它不一样了」。
2. **职责混杂**：团队成员图省事，把操作规则、安全边界全都往里写，文件涨到几千 token，挤占上下文预算，且规则与身份互相干扰。
3. **无版本管理**：改坏了不知道改了什么，回滚全靠记忆，同一实例被三个人改出三种风格。

## 做法

我们把迭代流程收敛成四步：

1. **结构化分区**。固定区（name / creature / emoji / avatar，基本不动）、行为区（语气、称呼、幽默感，用具体例句而非形容词堆砌）、边界区（明确「不做」清单，控制在 3–5 条）。
2. **入 git，走 PR 评审**。identity 变更等同代码变更，commit message 写清动机，例如「用户反馈语气过于书面，补充口语化例句」。
3. **小步演进**。一次只改一处，观察 3–5 天真实对话，再决定是否保留。
4. **固定测试集**。准备 6–10 个标准提问（日常闲聊、任务委派、边界试探各几条），每次改完手动跑一遍对比，防止回归。

## 踩坑点

- **形容词堆砌基本无效**。「热情、专业、可靠」十个词，不如一句具体的示范对话片段。模型对具象例句的遵循度远高于抽象标签。
- **频繁修改导致行为抖动**。一天三改，agent 每个会话语气都不同，恰恰摧毁了身份最值钱的「连续性」。
- **把流程规则写进身份**。何时调用哪个 MCP 工具、如何上报结果，那是 `AGENTS.md` 的职责。IDENTITY.md 只回答三个问题：我是谁、我怎么说话、什么坚决不做。
- **过拟合单次对话**。因为一次不愉快的交互就大改身份，是我们回滚次数最多的原因。

## 可复用建议

- 给 IDENTITY.md 设 token 预算，我们实例的上限是 300 token，超出就强制删减，删不动的说明写法有问题。
- 边界区用否定句（「不主动推荐」「不虚构进度」），在抑制行为上比肯定句更可靠。
- 变更节奏固定（比如双周一次），平时只收集观察、记到 issue，不在情绪当口动手。
- 团队共用的实例必须指定唯一 owner，其余人只能提 PR——身份文件的 merge 冲突比代码更难解。

## 总结

IDENTITY.md 不是一个一次性配置，而是一份需要持续维护的产品资产。用管理代码的方式管理它——版本化、小 diff、有评审、有回归测试——agent 才能做到既稳定又成长。所谓「可进化的身份」，核心不在文件本身，而在演进流程的克制：改得慢、改得小、改得有据，身份才能真正长出来。
