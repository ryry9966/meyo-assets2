## 背景

大多数 Agent 的默认形态是问答机：你不开口，它不动。这对查资料没问题，但对"持续关注某件事"这类需求很别扭——你得记得主动去问，问完它又睡了。

OpenClaw 内置了一个简单但常被忽视的机制：**心跳（Heartbeat）**。Agent 每隔一段时间自动醒来，读取工作区根目录下的 `HEARTBEAT.md`；有任务就执行，没有就返回 `HEARTBEAT_OK` 继续休眠，且这条回复不会转发给你。本质上，它是把 cron 的周期性和 Agent 的判断力缝在了一起。

## 问题

传统做法各有短板：

- **cron 定时任务**：能准时执行，但脱离对话上下文，不会根据结果决定"要不要告诉你"；
- **纯靠人问**：记忆负担全在你身上，忘问就是事故；
- **外部监控脚本**：只管告警，不能顺手做事（比如自动 commit、整理笔记）。

我想要的是一份**声明式任务清单**：写下条件和动作，Agent 每次醒来自己核对、自己决策。

## 做法

**1. 定位文件**。工作区根目录（默认 `~/.openclaw/workspace/`）下的 `HEARTBEAT.md`，没有就建一个。多 Agent 配置下每个 Agent 用自己工作区的那份。

**2. 按固定结构写任务**。每个任务四要素：触发条件、动作、通知规则、跳过条件。

```markdown
# 心跳任务（无事勿扰）
静默策略：一切正常时保持沉默，仅异常时通知。

- [ ] 磁盘：工作区所在盘使用率 >85% 时通知我
- [ ] 备份：notes 仓库有未提交改动则自动 commit + push
- [ ] 日程：今天 1 小时内的事件才提醒，其余不打扰
- [ ] 服务：本机 8080 健康检查，连续两次失败才告警
```

**3. 配置间隔**。默认每 30 分钟唤醒一次，在 `openclaw.json` 的 agents 配置里可调。调试阶段建议先调到 2–5 分钟验证行为，跑通后再放回去。

**4. 理解成本模型**。每次心跳是一次真实的模型调用，无论有没有任务。任务写得越含糊，Agent 越容易自由发挥、多绕几步，token 翻倍。

## 踩坑点

- **任务含糊**："帮我盯着服务器"这种写法，每次唤醒都会引发不可预测的动作。必须写成可判定的条件。
- **清单膨胀**：心跳每次全文读取该文件，堆到几十条后既慢又贵。完成的任务及时移走，保留 5 条以内。
- **骚扰式通知**：不写静默策略，它可能每 30 分钟发一条"一切正常"。在文件开头显式声明沉默规则。
- **重活别放心跳**：长任务会占住心跳周期，导致后续唤醒排队。定时重活（全量备份、批量抓取）交给 cron，心跳只做"检查 + 判断 + 轻量执行"。
- **高危操作别自动化**：删文件、发对外消息这类动作，默认不要写进清单，或者加二次确认条件。

## 可复用建议

1. **四要素模板**坚持用：条件 / 动作 / 通知规则 / 跳过条件，缺一个就容易跑偏。
2. **静默策略写在文件头**，作为全局约定压住所有任务。
3. **心跳与 cron 分工**：心跳负责"看情况决定"，cron 负责"到点就干"。
4. **把 `HEARTBEAT.md` 纳入 git**。它就是你 Agent 值守逻辑的源码，改动可追溯、可回滚。
5. **每月修剪一次**。任务和代码一样会腐化，过期的检查项留着只会烧 token。

## 总结

心跳机制的价值不在于"自动化"这个词，而在于它逼你把判断标准写成文字：什么算异常、什么时候该说话、什么时候闭嘴。清单写得越精确，Agent 越像一个可靠的值守同事；写得越含糊，它就越像一个每半小时来问你一次的热心但低效的实习生。从两条任务开始，跑两周再扩——这是我踩过坑之后的建议。
