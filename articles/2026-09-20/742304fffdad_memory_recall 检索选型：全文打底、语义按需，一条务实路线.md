## 背景

OpenClaw 的 `memory_recall` 本质是把历史会话沉淀下来的 memory 文件重新捞回上下文。语料形态很固定：持续追加的 markdown，会话纪要、决策记录、踩坑笔记。检索质量直接决定"助手到底记不记得住事"。

## 问题

实现上通常是两条路线：

- **全文搜索**（ripgrep / SQLite FTS5 / BM25）：关键词精确命中，零额外依赖；
- **语义搜索**（embedding + 向量库）：能兜住"换一种说法问同一件事"的场景。

社区里常见的争论是"上了 Agent 是不是必须上向量库"。我的结论：**多数个人级部署不必先上语义**，先用全文跑起来，让失败案例决定要不要加。

## 做法与步骤

1. **语料先规范化**：每条 memory 一个文件，frontmatter 带 created / updated / tags，正文保持可独立阅读的粒度；
2. **全文索引打底**：SQLite FTS5 建表，中文场景换 trigram tokenizer，或先分词再入库；
3. **封装成 MCP 工具**：入参 query + 可选 tag 过滤，返回 top-5 片段，必带文件路径和时间戳；
4. **观察召回失败案例**：两类——查了没召回、召回了但不是用户想要的；
5. **失败集中在同义改写时再补语义**：本地 embedding 模型（如 bge-small-zh）分块向量化，存 sqlite-vec；
6. **两路结果用 RRF 融合**：`score = Σ 1/(60 + rank)`，避免做两套分数的归一化，省心且鲁棒。

## 踩坑点

- FTS5 默认 unicode61 会把整段中文当成一个 token，**中文必须换 tokenizer**，否则全文检索形同虚设；
- embedding 对错误码、函数名、文件路径这类精确串几乎无用，反而稀释结果——这恰恰是全文的强项；
- 小语料（几百条以内）语义检索的 top-k 常返回"看着相关实则无关"的结果，相似度分数还很高，误导性比召回失败更大；
- memory 文件频繁编辑会留下过期向量，要么定期重建索引，要么按 mtime 做失效；
- 语义检索对短 query 很敏感，"上次那个部署的事"基本召不回；引导 agent 在 recall 前先改写出带上下文的 query，收益比换模型大；
- 别贪多：k 和片段长度都要设上限，recall 结果灌太多会挤占真正的工作上下文。

## 可复用建议

- 语料在几 MB 以内：**全文优先**，成本几乎为零，精确命中率高；
- 加时间衰减或按 mtime 加权，"最近发生的事"通常权重应更高；
- 返回结果永远带路径 + 时间戳，让 agent 需要细节时能自己读原文；
- 留一份 10–20 条的黄金问题集，每次调检索参数跑一遍，别凭感觉调；
- 混合检索既是终点也可以是起点：RRF 对两路各自的质量波动都不敏感，先搭骨架后补路子，比一次性堆基建稳。

## 总结

这不是二选一的问题。全文搜索是确定性的地基，语义搜索补足表述差异的盲区。先用最便宜的方案跑起来，用真实失败案例驱动升级——这比一上来就搭向量库，更符合 OpenClaw 的务实风格。
