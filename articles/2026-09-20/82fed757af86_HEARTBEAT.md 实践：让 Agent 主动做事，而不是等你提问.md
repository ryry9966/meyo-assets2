## 背景

多数 Agent 的默认工作方式是被动式：你开一个会话，敲一句需求，它执行，结束。用 OpenClaw 一段时间后，我发现真正的瓶颈不在模型能力，而在它“不主动关心”——日报汇总、磁盘水位、未读消息、待办提醒，全靠你自己记得去问。用 cron 加定时 prompt 当然能做，但任务一多就散落各处，prompt 不可维护，输出要么太吵要么没声。

OpenClaw 的 Heartbeat 机制提供了一个更集中的解法：Agent 按可配置的间隔周期性醒来，读取工作区里的 `HEARTBEAT.md`，自行判断有没有值得做的事。没有就返回 `HEARTBEAT_OK`，保持沉默。这个“默认沉默”是整个设计的灵魂。

## 问题

朴素做法有三种典型失败形态：

- **任务散落**：每个定时需求独立配 cron，prompt 碎片化，改一处忘三处；
- **成本失控**：Agent 每次心跳都要注入上下文，文件越长、任务越多，token 越烧；
- **噪音轰炸**：Agent 每次醒来都热情汇报“一切正常”，三天后你把它静音——主动性退化成垃圾推送。

核心矛盾一句话：怎么让它主动做该做的事，同时对不该做的事绝对安静。

## 做法

`HEARTBEAT.md` 就是工作区里一个普通 Markdown 文件，每次心跳醒来被注入上下文。我的文件分三层：

1. **常规轻量检查**。例如“检查服务器磁盘占用，超过 85% 才提醒”。每条必须带明确的触发条件和对应的工具调用（MCP 或插件）。
2. **时间门控的汇总**。例如“工作日 9:00–10:00 之间，汇总昨天的未读消息和待办，发一条消息”。不用另配 cron，时间条件直接写进文件。
3. **显式排除项**。文件开头写死一条：“没有任何条件命中时，只返回 HEARTBEAT_OK，不发送任何消息。”

落地步骤：

1. 工作区建 `HEARTBEAT.md`，先只写 1–2 条，跑一周；
2. 每条按“触发条件 + 动作 + 输出规则”三段写，条件必须能被一次工具调用验证；
3. 需要跨醒来持久化的状态（如“已提醒过，勿重复”），落一份 `state.json`，让 Agent 每次先读后写；
4. 观察一周日志，砍掉从未触发的条目，调低触发过频的阈值。

## 踩坑点

- **心跳不是任务队列**。在心跳里跑重型任务会阻塞整个节奏。长任务移到 cron 或独立会话，心跳里只留“检查 + 判断 + 通知”。
- **条件必须可证伪**。“帮我盯着仓库”这种模糊写法，Agent 会自己发明工作。要写成“仅当出现标记为 bug 且无人认领的新 issue 时提醒”。
- **状态一定要落盘**。每次心跳都是相对独立的上下文，它不记得上次说过什么。不写“上次提醒时间”，重复轰炸只是时间问题。
- **盯住 token 成本**。文件每次心跳全量注入，我控制在 40 行以内，每月清理一次。心跳日志里顺手记一下调用次数，异常增长就是某条任务在空转。

## 可复用建议

- **先写沉默条款，再写任务**。这是主动性和垃圾推送之间唯一的防线；
- **粒度标准：一次工具调用能判定的才进心跳**，判定不了的拆解或外移；
- **文件进 git**，每次调整留痕，方便回溯“它为什么突然开始发消息”；
- 用“周触发次数”作为修剪指标：从不触发的删，天天触发的调阈值。

## 总结

HEARTBEAT.md 没有任何黑魔法，它只是一个周期注入的清单文件。但它把 Agent 的姿态从“问答机”改成了“值守岗”：该关心的主动关心，不该出声的保持安静。真正花功夫的不是写，而是持续修剪——让沉默成为默认态，让每一次主动发声都有充分的理由。这大概是目前把 Agent 用成“个人助理”而不是“聊天窗口”的成本最低的一步。
