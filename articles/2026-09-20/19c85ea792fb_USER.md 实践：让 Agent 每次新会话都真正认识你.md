## 背景

Agent 的会话是无状态的。今天聊过的技术栈、你的命名习惯、时区，明天新会话里全部归零。OpenClaw 的工作区里，AGENTS.md 约束 Agent 的行为，SOUL.md 定义"Agent 是谁"，MEMORY.md 记录"发生过什么"，而 USER.md 负责回答另一个问题：**对面这个人是做什么的、怎么协作最顺**。三者分工清楚，USER.md 恰恰是最容易被写糊的一块。

## 问题

没有 USER.md 时，典型体验是：

- 每个新会话都重新交代一遍环境；
- 建议永远泛泛，因为它不知道你跑的是 k8s 还是一台 2C4G 的小机器；
- 明明说过"先给结论"，三天后它又开始长篇大论。

反过来，随手堆料也有问题：三个月前的"正在做 XX 项目"还挂着，Agent 按过期上下文一本正经地回答；简历式自述塞满上下文，真正有用的十行被淹没。**USER.md 的价值不在写得多，而在每一条都能被下个会话用上。**

## 做法

我的 USER.md 按三层组织，控制在 30 行以内：

```markdown
# USER

## 恒定事实
- 角色：后端工程师，主力 Go，顺手维护几个 GitHub Actions
- 环境：macOS + Ubuntu 服务器，时区 UTC+8，终端党
- 仓库习惯：commit 用英文，注释用中文

## 协作偏好
- 先给结论和代码，解释放最后，能三行说完不写十行
- 方案类问题至少给一个备选和取舍
- 不确定我的意思时先问，别自行脑补

## 当前上下文（2025-06 更新）
- 正在把家里服务从 docker compose 迁到单机 k3s
- 本月主线：给公司的消息网关加限流
```

三条维护规则：

1. **易变的进"当前上下文"并标日期**，过季就删；稳定的才进前两段。
2. **让 Agent 参与维护**。它发现新事实（比如你纠正了某个说法）时，让它提议"要不要补进 USER.md"，你审核后落盘。人负责准，Agent 负责勤。
3. **进 git**，和 dotfiles 一起同步。多设备、重装环境都能拉回来，diff 还能看到自己偏好的演变。

## 踩坑点

- **写敏感信息**。真实姓名、公司、内网地址、密钥都别放。USER.md 每次会话被读入上下文，等于随请求外发，也进日志和备份。
- **写能力评价**。"十年资深工程师"这类句子只会让 Agent 减少解释、漏掉关键前提。写事实（用什么、怎么做），不写水平判断。
- **和 SOUL.md 抢活**。"回复要简短"是协作偏好，放 USER.md；"性格直接、不奉承"是人设，放 SOUL.md。混写会出现两边都不管的灰色段落。
- **只写不删**。每月做一次过期审计：这条信息上个会话真的被用到了吗？没用到就降级到 MEMORY.md 或直接删。

## 可复用建议

- 新会话问一句"你目前对我的了解有哪些"，它的复述就是 USER.md 的实际命中率，比肉眼检查有效。
- 模板口诀：**恒定的写事实，易变的标日期，偏好写成可执行规则，雷区写成否定句**。"不要主动升级依赖"远比"注意依赖问题"有效。
- 工作和个人场景差异大时，拆两个工作区、两份 USER.md，比一份大杂烩干净得多。

## 总结

USER.md 本质上是给 Agent 的接口文档：描述调用方是谁、有什么约束、期望什么行为。像维护 API 文档一样维护它——短、准、新鲜，它就会在每个新会话里稳定兑现。一次性成本二十分钟，省下的是之后无数次"这个我说过了"。
