# 背景

OpenClaw 的 agent 每次会话都会把 workspace 里的一组 Markdown 注入上下文：AGENTS.md 管行为规范，MEMORY.md 管长期记忆，而 `TOOLS.md` 的定位最容易被低估——它是写给 agent 看的“本机操作手册”。技能、插件和 MCP server 告诉 agent“能调用什么”，但不会告诉它“这台机器上怎么跑”。Mac mini、家里的 NUC、云上的 VPS，三台机器三种包管理器、三种路径习惯，全靠 agent 现场猜。

# 问题

典型的翻车现场：

- 在 Debian 上调 `brew`，在无 sudo 权限的容器里试图 `apt install`；
- 分不清 `python` 指向 2 还是 3，跑错 venv；
- 项目路径靠翻聊天记录回忆，会话重置后丢失；
- 环境事实零散写进 memory，跨机器同步 MEMORY.md 后互相污染。

根因只有一个：环境知识没有稳定、可维护的落点。

# 做法

1. **建文件**。在 workspace 根目录建 `TOOLS.md`（如 `~/.openclaw/workspace/TOOLS.md`），它随会话注入，相当于常驻指令。
2. **只写环境差异，不复制工具文档**。技能文档已说明的用法不要重复，只写“这台机器的偏差”。
3. **按事实组织**，骨架参考：

```markdown
# TOOLS.md（本机）
- 系统: Debian 12, x86_64；无 brew，用 apt（需 sudo）
- Python: 用 uv，别用裸 pip；venv 在 ./venv，先 source 再跑
- 项目: 在 ~/work/ 下；构建 = make build，测试 = make test
- 禁止: 动 /etc/nginx；不执行带绝对路径的 rm -rf
```

4. **先修后记**。每次 agent 猜错、你纠正之后，顺手把教训写成一行加进去。这是这个文件能活下来的关键纪律。
5. **多机各写各的**。每台机器一份，绝不整文件互拷。公共部分做成模板，机器相关部分可以让 agent 跑一条采集命令（uname、各运行时版本、which）生成草稿，你手工修订。
6. **分层明确**。TOOLS.md 存稳定事实，memory 存事件与偏好。发现 agent 把环境事实写进了 memory，定期“晋升”到 TOOLS.md 并清理 memory。两边冲突时，以 TOOLS.md 为准。

# 踩坑点

- **写太长**。它每轮都进上下文，百来行以内最好，超了会被稀释甚至被忽略。
- **写了密钥**。这文件大概率会被贴进日志、截图、分享。只写位置引用，例如“token 在 ~/.config/xx/token，chmod 600”。
- **过期信息比没有更糟**。改了路径不更新，agent 会反复失败。加一行“最后更新”，每周扫五分钟。
- **模糊措辞**。“尽量试试用 rg”不如“用 rg，别用 grep”。既然每轮必读，写进去的就是指令，别写愿望。
- **和 AGENTS.md 抢地盘**。那边管“该做什么”，这边管“在这儿怎么做”，越界会产生自相矛盾的指令。

# 可复用建议

- 心智模型：把 TOOLS.md 当**交接班记录本**，不是文档工程。一行一条事实，能删则删。
- 团队场景：workspace 若入 git，脱敏后提交 `TOOLS.md.example`，各人生成自己的版本；主机名、内网 IP 留在本机。
- 验收方式：新开会话，让 agent“说出本机的构建与测试方式”，答对即合格。

# 总结

tools.md 的价值不在格式而在纪律：把每一次“agent 又猜错了”沉淀成一行可复用的环境事实。它便宜（纯文本）、可靠（每轮必读）、可审计（git diff 即可回溯）。与其追求更聪明的 agent，不如先把这台机器说清楚。
