# 背景

OpenClaw 的 agent 默认是被动响应式的：你发消息，它才动。但我们把它部署在常驻机器上，配了一堆 skills 和 MCP 工具之后，会慢慢意识到一个别扭的事实——它明明什么都能查，却永远在等你先开口。磁盘满没满、定时任务挂没挂、某个目录有没有新文件，这些事你都记得，但 agent 不提醒，你就忘了问。

OpenClaw 对此给了个很轻的机制：heartbeat（心跳）。Gateway 每隔一段时间（默认 30 分钟）唤醒一次 agent，如果 workspace 根目录下存在 `HEARTBEAT.md`，就把它的内容和一条心跳提示一起注入会话，让模型自己判断要不要执行检查、要不要汇报；没有这个文件，或者文件里只有注释，这个 tick 直接跳过，连模型调用都不发生。

# 问题

被动模式的核心代价不是“慢”，而是上下文浪费：agent 知道你所有的项目状态，但这些知识只在被问到时才变现。心跳机制本质上就是给 agent 加了一个 cron + 一份常备指令文件，把“你可能会忘记问的事”固化下来。

# 做法

**第一步，建文件。** 在 workspace 根目录（一般是 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`：

```markdown
<!-- 心跳清单：只做检查与汇报，写操作先问我 -->

- 若 ~/jobs/sync.log 超过 2 小时未更新，摘录最后 10 行报给我。
- 磁盘使用率超过 85% 时提醒，同一问题一天最多提醒一次。
- 其余情况只回复 HEARTBEAT_OK，不要输出多余内容。
```

**第二步，调频率和投递目标。** 在 `~/.openclaw/openclaw.json` 里：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "45m" }
    }
  }
}
```

默认的汇报会落在主会话里，如果你主要在 IM 上用 agent，记得把心跳结果投递到你实际看的频道，否则很容易“它报了，但没人看见”。

**第三步，验证。** 改完文件不用重启，下一个 tick 生效。可以故意造一个条件（比如把日志文件 mtime 改旧），等一轮心跳确认链路通。

# 踩坑点

- **每个 tick 都是真实的 LLM 调用。** `HEARTBEAT.md` 写得越长、interval 越短，账单越好看不起来。清单保持三五条以内，无事时的 `HEARTBEAT_OK` 约定一定要写上。
- **心跳不是 cron。** 它只保证“最多 N 分钟内会发现”，不保证准点执行。“每天早上八点做 X”这类精确调度请用 cron 工具，心跳适合条件型检查。
- **它跑在主会话里。** 好处是 agent 带全量上下文、懂你的项目；坏处是上下文大、单次成本高，别把它当独立 worker 用。
- **模糊指令会出事。** 写“帮我清理磁盘”，它可能真的就清理了。默认只检查+汇报，所有写操作要求先确认。
- **依赖工具失败会刷屏。** 外部服务挂掉时它可能每轮都报错，在清单里加一条去重/静默规则。

# 可复用建议

把 `HEARTBEAT.md` 当值班手册（runbook）写，每条固定结构：**触发条件 + 判定标准 + 动作边界 + 汇报格式**。清单分三层维护：常驻的廉价检查（文件 mtime、磁盘）、按条件告警（阈值去重）、每日汇总。用 git 管理这个文件，改了什么、为什么改，可追溯。先跑一两周观察 token 消耗，再决定加密度还是调间隔。

# 总结

HEARTBEAT.md 的价值不在于“自动化”这个词，而在于它把 agent 从一个问答接口变成了一个有值守意识的同事。文件很小，机制很朴素，但写好这份清单需要像写运维手册一样克制：条件明确、动作收敛、噪音有预算。建议从两条检查起步，跑一周，再迭代。
