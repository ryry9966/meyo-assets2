## 背景

用 OpenClaw 这类常驻 Agent 一段时间后会有个体会：影响输出质量的因素里，模型占一半，另一半是上下文。OpenClaw 的 workspace 机制约定了几个随会话启动注入的记忆文件：AGENTS.md 定义 agent 怎么干活，SOUL.md / IDENTITY.md 定义它的性格，而 USER.md 用来描述"使用者是谁"。

前两类社区讨论很多，USER.md 反而最容易被忽略——很多人的 workspace 里压根没有这个文件，或者只有一行名字。

## 问题

没有 USER.md 的典型体验：

- 每个新 session 都要重新交代：技术栈、时区、代码风格、回复偏好；
- Agent 前几轮输出"试探味"很重，先猜你的习惯，猜错再改；
- 这些信息散落在历史对话里，不可审计、不可迁移，换个 channel 就丢了。

本质上，你的个人上下文是隐式的、每次靠对话重建的。USER.md 要做的事就一件：把它显式化成一个文件。

## 做法

**1. 建文件。** 在 workspace 根目录创建 USER.md，OpenClaw 启动时会随记忆文件一起加载进上下文。

**2. 只写"长期稳定且影响输出"的事实。** 我的分节结构：

```markdown
# 基本信息
- 时区 / 常用工作时段
- 中文交流，代码注释中文

# 技术环境
- 主力栈：Python 3.12 / Node 22，macOS
- 代码风格：4 空格缩进，必须有类型注解

# 协作偏好
- 结论先行，先方案后解释
- 不确定时列出假设，不要自行其是

# 禁区
- 不要自动 git push
- 不要动 /etc 下的配置
```

**3. 让 Agent 参与维护。** 在 AGENTS.md 里加一条规则：当你明确纠正某个偏好、或给出长期有效的信息时，agent 应提议追加到 USER.md 对应小节，而不是只修正当次回答。配合 git 管理 workspace，每次变更可追溯。

**4. 和 MEMORY.md 分工。** 原则：USER.md 放"我是谁"（以月为单位的稳定事实），MEMORY.md 放"发生了什么"（事件流）。混在一起，两边都会失控。

## 踩坑点

- **写成简历。** 塞进大段履历和临时项目细节。这个文件每次会话都进上下文，100 行以内是合理上限，超了就裁。
- **放敏感信息。** API key、住址、密码别写——它会进每一次会话的上下文，还会随 workspace 同步备份。
- **放任 Agent 自由更新。** 不约束格式的话，重复条目会越堆越多。固定小节名 + 只有明确指示才写入，能挡掉大部分腐烂。
- **过时不清理。** 你换了主力语言，它还按旧习惯输出。文件头加一行"最后更新"日期，每月 review 一次。
- **期望过高。** USER.md 是静态注入的上下文，不是记忆系统。复杂的协作规则应写进 AGENTS.md 变成行为约束，USER.md 只放事实。

## 可复用建议

- 用问题倒推内容："我希望 Agent 默认知道我的哪 10 件事？"答案就是 USER.md 的正文。
- 分层存放：跨项目通用信息放 USER.md；通过 MCP 或插件接入的外部系统习惯（默认分支名、常用命名空间、告警等级）也值得沉淀进来；单项目相关的细节放该项目自己的说明文件，别让一份文件膨胀成大杂烩。
- 每次 Agent"又忘了"，先别怪模型，想想这个事实该不该沉淀进文件。
- 模板直接抄上面的分节，够用再扩。

## 总结

USER.md 的价值不在"智能"，而在工程：把隐式上下文变成显式、可版本化、可 review 的资产。成本是一个 markdown 文件，收益是每次新会话的冷启动成本趋近于零。如果你的 workspace 还没有这个文件，今天花十分钟写第一版，比调任何 prompt 都划算。
