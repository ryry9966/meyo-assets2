## 背景

OpenClaw 的 cron 能力把 agent 变成了定时工：早报、日志巡检、周报汇总，都由一条 instruction 驱动。很多人写第一条定时任务时，会沿用聊天习惯——"早上八点给我一份今天的日报"。调度本身没问题，产出往往不行：要么内容漂移，要么把频道刷成噪音。

## 问题出在哪

定时任务的运行环境和日常对话完全不同：

- **无上下文**：cron 触发的是一个独立会话，主对话里聊过的偏好、约定它一概不知；
- **无人应答**：任务是 headless 跑的，写"先问我一下要哪些来源"，没人回答，任务要么卡住要么自由发挥；
- **产出被反复消费**：结果直接进群、进频道，不稳定的输出会被持续放大。

所以 cron 的 instruction 本质上是一份给无人值守程序的规格说明，不是一句对话。

## 我的写法：五段式模板

拿我跑了一个多月的每日情报任务举例：

```text
【任务】汇总过去 24 小时我关注领域（AI agent / 基础设施）的动态。
【来源】用 browser 抓取以下 3 个固定站点；某源失败就跳过，不要用猜测内容补位。
【输出】不超过 200 字，按"重要 / 一般"两档列条目，每条一句话并标注来源。
【兜底】所有源都失败时，只回复"今日源全部不可用"，不要编造。
【投递】发送到 #daily 频道，不需要 @ 我。
```

对应五个步骤：

1. **定边界**：任务一句话说清范围，宁小勿大；
2. **锁来源**：写死工具、数据源和顺序，不要让模型每次自己挑，否则逐次产出漂移；
3. **限输出**：字数、结构、格式全部固定——固定结构是稳定产出的最大杠杆；
4. **定义失败**：明确"拿不到就明说/跳过"，堵住幻觉的主要入口；
5. **指定投递**：发到哪、是否 mention、要不要标题，写明白。

## 踩过的坑

- **高频 + 重工具调用**：我设过 30 分钟一轮全站抓取，token 消耗直接翻倍。低频任务先用每天 1 次跑一周再调频率；
- **时区**：调度按服务器时区计算，表达式看着对，实际总差 8 小时。写表达式前先确认运行时时区；
- **幂等性**：每轮都是新会话，"只报和上次的增量"这类要求，需要任务自己把产出落盘（比如顺手追加写入文件），否则它根本不知道"上次"是什么；
- **让 agent 反问**：headless 环境没有人在，任何需要"确认"的环节都会变成阻塞或瞎猜。

## 可复用建议

- 把 instruction 当代码管理：存文件、写注释、改一版测一版，别只留在调度器的输入框里；
- 上线前手动触发一次，看完整产出再开调度；
- 给输出留审计口：让任务把结果追加写入本地文件，跑偏时能回看是哪天开始偏的；
- 兜底行为必须显式声明——这是 agent 定时任务和普通脚本的分水岭。

## 总结

cron 任务的 instruction 质量，决定了定时 agent 是提效工具还是消息噪音源。写之前问自己三个问题：它知不知道去哪拿数据？拿不到会怎样？产出最终长什么样？三个答案都能在 instruction 里指出，这个任务才算真正能无人值守。
