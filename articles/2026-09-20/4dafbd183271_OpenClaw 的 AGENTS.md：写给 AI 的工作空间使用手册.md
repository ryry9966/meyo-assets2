## 背景

人类工程师入职第一天看 README，agent 进入工作区看的是 AGENTS.md。这个文件放在工作区根目录，每次新会话启动时由 OpenClaw 注入 system prompt，相当于 agent 的"入职手册"。这个约定已在多家 agent 框架间趋同：与其在对话里反复口头交代，不如把稳定的事实和规则写进一个版本化的 Markdown 文件。

## 问题：没有它时 agent 怎么翻车

- **每次会话重新"考古"**：重新探索目录结构、猜命令，浪费 token 和时间；
- **约定靠嘴传**：代码风格、分支规范、哪些目录不许动，全靠聊天里临时补，换个会话就忘；
- **安全边界模糊**：agent 可能把 `.env`、生产脚本当普通文件顺手读掉；
- **团队各说各话**：每个人向 agent 解释同一套规则，解释质量还参差不齐。

## 做法：五步搭一个可维护的 AGENTS.md

1. **建文件**。在 workspace 根目录创建 `AGENTS.md`，OpenClaw 会在会话启动时自动读取。
2. **只写事实和规则，不写任务**。推荐结构：项目一句话概述、目录约定、常用命令、代码/提交规范、明确禁止项（如"不要修改 infra/ 下的 Terraform 文件"）。
3. **控制篇幅**。整个文件每次会话都会注入，建议 150 行以内，每条规则一行说清。
4. **分层放置**。monorepo 可在子目录再放 AGENTS.md，只描述该子包的特殊约定，避免根文件膨胀。
5. **进 git，走 review**。规则变更和代码一样提交、审查，别让它沦为某个人的本地笔记。

验证方式很简单：新开会话，问 agent"描述一下你对这个工作区的理解"，确认注入生效、内容没被截断。

## 踩坑点

- **太长等于没有**。超出注意力预算后，中后段规则会被系统性忽略。优先删旧规则，而不是继续追加。
- **愿望清单式规则无效**。"始终写测试"不如"改动 `src/api/` 后运行 `pnpm test api`"——模型只能执行可操作的指令。
- **别写死机器相关内容**。绝对路径、本机端口会污染其他人的环境。
- **不要放敏感信息**。文件内容会进模型上下文，密钥、内网地址写进去等于主动泄露。
- **过期规则比没有更糟**。目录重构后忘了更新，agent 会按旧结构自信地犯错。失效的规则要果断删。

## 可复用建议

- **把 debug 经验沉淀进去**：每当 agent 犯了一个"本不该犯的错"，当场补一条规则。这是把踩坑成本转化为资产的最便宜方式。
- **多工具并存时保持单一源**：同时用几套 agent 工具时，用软链或脚本从一份源文件生成，避免三份文件各自漂移。
- **加一行更新日期**：放在文件末尾，review 时一眼判断规则是否还新鲜。

## 总结

AGENTS.md 的价值不在"调教 AI"，而在把团队隐性工程约定显性化、版本化。它是 agent 时代成本最低的基础设施：一个文件、零依赖、每次会话自动生效。写好它，然后像维护代码一样维护它——规则库的质量，基本决定了 agent 在你工作区里的表现上限。
