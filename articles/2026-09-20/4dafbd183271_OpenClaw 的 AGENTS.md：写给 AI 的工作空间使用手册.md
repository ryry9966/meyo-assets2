## 背景

OpenClaw 的 agent 有个特点：会话基本是冷启动。上一轮你千叮万嘱的规矩，下一轮它未必记得。SOUL.md 和 USER.md 解决的是"它是谁、你是谁"，但"这个工作空间怎么干活"这件事，长期没有一个固定落点。

AGENTS.md 补的就是这个位置。它是放在 workspace 根目录的一个 Markdown 文件，agent 在会话启动时会读取，相当于你写给 AI 的一份《工作空间使用手册》：环境路径、工具策略、操作边界、启动流程，都收在这一个文件里。

## 问题：没有手册时会发生什么

我自己踩过的三类典型情况：

1. **行为漂移**。今天它把中间产物写到 `~/tmp`，明天写到工作目录根下，文件散落一地。
2. **重复交代**。每次会话开头都得贴一遍"别动 cron、先查心跳、报告写到哪"，纯消耗 token。
3. **多机不一致**。两台机器跑同一个实例，工作习惯全靠脑子同步，迟早出事。

本质相同：约定只存在于对话历史里，而对话历史不可靠。

## 做法：一份可用的骨架

原则是"手册不是日记"——只写长期稳定的规则，不写一次性任务。我的骨架分六段：

```markdown
# Workspace Manual

## 环境
- workspace 路径、脚本目录、产物输出目录
- 系统概况（OS、时区、可用 runtime）

## 会话启动清单
- 读 MEMORY.md 最新条目
- 检查待办与心跳消息

## 工具与技能策略
- 优先用哪些 skills / MCP 工具
- 什么情况必须先询问再执行

## 安全边界
- 禁止删除的范围、对外发消息的确认规则

## 汇报格式
- 完成后输出什么、写到哪个文件

## 禁止事项
- 明确的 do not 列表
```

每段三五条，全文控制在 100 行以内，放进 workspace 根目录，下次会话生效。

## 踩坑点

- **写太长**。手册每次会话都占上下文，200 行会稀释注意力，agent 反而漏看关键规则。经验是删到不能再删。
- **职责重叠**。"你是谁"归 SOUL.md，"用户是谁"归 USER.md，"怎么干活"才归 AGENTS.md。把人格设定塞进手册，改起来会互相打架。
- **写死绝对路径**。多机同步时路径不同，手册直接失效。用 `~/openclaw` 这类约定路径，或在环境段声明。
- **以为改完立刻生效**。已开的会话不一定重读，改完开个新会话验证。
- **把任务写进手册**。"这周整理照片"这种会过期的内容应该进 MEMORY.md 或待办，手册只收长期规则。

## 可复用建议

- 用 git 管 workspace，AGENTS.md 每次修改有 diff 可查，回滚也方便。
- 发现 agent 重复犯同一个错，先问"这条规则手册里有没有"，没有就补一条，让它慢慢收敛。
- 每月通读一遍删废话，手册和代码一样需要重构。
- 跑多个实例时，把公共部分抽成模板，各实例只保留差异段。

## 总结

AGENTS.md 的价值不在于"多配了一个文件"，而在于把散落在对话里的隐性约定显式化、版本化。它写的是给 AI 的规则，但真正被约束的是写手册的人——你得先想清楚工作空间该怎么运转，才写得出来。建议每个跑了超过一周的 OpenClaw 实例都补一份，从 20 行的最小版本开始。
