# 背景

跑过一段时间 Agent 自动化的人都会遇到同一个瓶颈：单 Agent 串行干活。一个任务里往往混杂着查资料、读代码、改文件、跑验证好几类工作，全塞进一个上下文里，越往后上下文越长、动作越慢、错误率越高，中途走偏一步还没有回滚点。Subagent 编排的思路就是把大任务拆成若干边界清晰的小任务，交给多个子 Agent 并行执行，主 Agent 只负责拆分、分发和汇总。

# 问题

真正动手后会发现，难点不在“能不能并行”，而在三件事：

1. **拆分粒度**：拆太细，调度开销和 token 成本超过收益；拆太粗，等于没拆。
2. **结果质量**：子 Agent 输出格式漂移，主 Agent 汇总时解析失败。
3. **上下文卫生**：如果把子 Agent 的完整输出全部回灌主 Agent，上下文瞬间膨胀，主 Agent 反而变笨。

# 做法

以我实际在跑的一条流水线为例，分五步：

**第一步，先串行验证拆分。** 把任务手写拆成 3~5 个子任务，逐个跑通，确认彼此没有共享可变状态（比如同时改同一个文件），再开并行。这步不能省，大部分并行翻车都是依赖没拆干净。

**第二步，模板化子 Agent 的 prompt。** 固定四段：角色与目标、输入（明确读哪个路径）、输出格式（建议约束成 JSON 或固定段落结构）、边界（明确禁止做什么，比如不动目标目录之外的文件）。如果子 Agent 挂了 MCP 工具，工具权限要按任务收敛，不要全量继承。

**第三步，控制并发度。** 我的经验是 3~5 个并发比较稳，再高容易撞限流，且 token 成本是乘数效应。粗活（检索、归纳）可以交给便宜的小模型，精活（改代码、下结论）留给主模型。

**第四步，收口。** 子 Agent 的产出落盘（写文件或入库），回传主 Agent 的只有“路径 + 200 字以内摘要 + 状态标记”。主 Agent 拿摘要做决策，需要细节时再按路径去读。

**第五步，兜底。** 每个子 Agent 设超时和一次重试，失败的任务标记后跳过，不要让一个卡死的子任务拖住整批。

# 踩坑点

- **隐式依赖**：两个子 Agent 都“顺手”改了同一个配置文件，合并时互相覆盖。拆分时要显式声明各自的写入范围。
- **输出走样**：哪怕要求了 JSON，也总有子 Agent 加一句“以下是结果……”。解析层要做宽容处理，或在 prompt 里给一个最小示例。
- **摘要丢关键信息**：子 Agent 的摘要把报错细节吞掉，主 Agent 误判成功。摘要模板里强制包含“失败原因”字段。
- **日志混写**：多个子 Agent 并发写同一个日志文件，排障时分不清谁是谁。给每个子 Agent 独立的日志前缀或文件。

# 可复用建议

- 把子 Agent prompt 沉淀成模板库，按“检索型 / 生成型 / 验证型”分类，新任务拼装即可。
- 子 Agent 的所有操作尽量幂等：重跑不产生副作用，这是敢开自动重试的前提。
- 先做减法：如果串行十分钟能跑完且不炸上下文，就不要为了并行而并行。

# 总结

Subagent 并行编排的价值不在于“多个 AI 同时跑”的画面感，而在于任务拆得干净、上下文隔离得好、失败能兜住。我的顺序是：先拆对，再并行；先摘要，后细节；先小并发，后加压。守住这三条，并行带来的提速和稳定性提升才真正落得了地。
