## 背景

用 OpenClaw 编排稍复杂的任务时，子 Agent 几乎不可避免：通读一遍陌生代码库、跑一轮带试错的调试、批量处理文件。最初我们图省事，让子任务直接跑在主会话上下文里，结果一两个大任务下来，主会话被几十次工具调用和报错堆栈塞满，主 Agent 后续的回答明显变"糊"。

## 问题

具体有三类：

1. **上下文污染**：子任务的中间过程全部进入主会话历史，有效注意力被稀释，主 Agent 开始重复提问、忘记早期约束。
2. **状态串扰**：子 Agent 改了 session 级共享变量和 MCP 工具内部的缓存态，主会话后续行为被隐性影响，而且很难定位。
3. **不可复现**：想单独重跑某个子任务时，发现它的上下文和主会话缠在一起，拆不出来。

## 做法

我们内部约定一句话：**子 Agent 是被调用的函数，不是共享记忆的同事**。输入显式传，输出显式收。

1. **独立 session 启动**。spawn 子 Agent 时新建 session，不复用主会话历史。具体字段名随版本有差异，核心是确认隔离开关（独立 session id）确实打开。
2. **显式声明输入**。把子任务需要的最小上下文写进任务描述：目标文件路径、硬约束、验收标准、超时时间。不要指望它"记得"主会话聊过什么。
3. **约定返回协议**。子 Agent 结束时只回一段结构化摘要：结论、改动涉及的文件、未解决问题。中间 transcript 留在子 session，需要审计时落盘并把路径放进摘要。
4. **资源隔离**。MCP server 实例按 session 分配；工作目录用独立副本或分支；确需共享的状态走显式文件或数据库，不走隐式 session 变量。
5. **主会话只做合并决策**。拿到摘要后由主 Agent 判断下一步：采纳、追问，或再派一个干净的新子 Agent。

## 踩坑点

- **MCP server 忘了按 session 分**：子 Agent 和主会话共用实例，工具里的登录态、缓存互相覆盖。症状很典型："子任务跑完，主会话的工具突然不好使"。
- **返回了整段过程**：没锁返回协议，等于把污染换个位置存放。摘要必须限长，未解决项要单列。
- **隔离过头**：子任务其实依赖主会话早先定下的约束，输入没带全，子 Agent 自作主张做出了相反的决策。
- **并发写同一工作区**：多个子 Agent 同时改一个目录，git 冲突。要么每个子任务一份工作副本，要么老实串行。
- **子 session 落盘没人清**：审计日志越积越多，清理得进例行任务，别等磁盘报警。

## 可复用建议

- 固化一个"子任务模板"：目标 / 约束 / 验收标准 / 超时 / 返回 schema，五个字段填空即可派发。
- 摘要强制限长（我们压在 30 行内），未解决项为空也要显式写"无"，避免静默吞掉风险。
- 高风险任务默认开 transcript 落盘，路径回传主会话，出问题能回放。
- 定期清理过期子 session，挂进自动化任务即可。

## 总结

session 隔离解决的不是功能问题，而是注意力与状态的边界问题。原则很简单：子 Agent 的中间过程留在自己的 session 里，主会话只接收显式声明的输入与受限的输出摘要。做到这一点，多 Agent 编排的可控性会有肉眼可见的提升。欢迎在社区里贴出你们自己的返回协议模板，一起迭代。
