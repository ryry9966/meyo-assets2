## 背景

Agent 的价值不在于会聊天，而在于能动手。OpenClaw 里的典型场景是：模型规划好步骤后，需要调用外部服务完成实际动作——查订单、触发 CI、写入数据库。这条"握手"链路如果没设计好，Agent 的表现会从"稳定可用"退化成"碰运气"。

## 问题

直接让 Agent 调 API，通常在四个地方翻车：

1. **鉴权**：密钥写死在配置里，随日志、报错一起泄给模型甚至外部；
2. **失败处理**：网络抖动一次，Agent 就把报错原文当结论，要么放弃要么瞎编；
3. **上下文污染**：接口返回 50KB 的 JSON，两轮对话后 token 直接爆掉；
4. **工具语义模糊**：两个描述相近的工具，Agent 分不清该调哪个。

## 做法与步骤

以 OpenClaw 的 tool / MCP 插件对接一个第三方 HTTP API 为例：

1. **先定工具边界，再写实现。** 一个工具只做一件事，参数尽量少。描述里写清楚"什么时候该调我、什么时候不该"，这比反复调 prompt 有效得多。
2. **封装 HTTP 层，不要裸调。** 统一设置超时（建议 10–15s）、指数退避重试（只对幂等 GET 重试，写操作用幂等键），并把上游错误归一化——翻译成一句模型能理解、能据此决策的话，比如"资源不存在，请检查 ID"，而不是甩一段堆栈回去。
3. **收敛返回值。** 只返回模型需要的字段，超长的列表做分页或摘要。宁可多调一次，也不要一次塞爆上下文。
4. **鉴权走环境变量或密钥服务。** 插件启动时读取，报错信息里做脱敏，确保密钥不会出现在 tool result 中回流到模型。
5. **加可观测性。** 每次 tool 调用记录：工具名、参数摘要、耗时、状态码。排查 Agent 行为异常时，这份日志比回放对话有用得多。

## 踩坑点

- **非幂等请求重试**：下单接口超时后重试，结果下了两单。写操作一律带幂等键。
- **工具描述照抄 API 文档**：文档是给人看的，给模型的描述要写清调用时机和前置条件。
- **把原始异常喂回模型**：模型会顺着报错"脑补"，输出看似合理的错误结论。先在插件层翻译。
- **超时给太长**：一个 60s 的慢接口会卡住整个 agent loop，必要时改成异步提交 + 轮询任务状态。

## 可复用建议

- 工具数量超过 10 个时，按领域拆分并动态注册，减少无关工具对模型选择的干扰；
- 为每个外部依赖准备一个 mock 模式，本地调试和 CI 都能跑通全流程；
- 工具 schema 的变更视为破坏性变更，走版本号，不要原地改。

## 总结

对接外部服务不是"接个 HTTP 客户端"这么简单，而是给 Agent 设计一套可靠的感官和四肢：边界清晰、失败可预期、返回够紧凑、密钥不出境。把这层做扎实，即使模型侧的 prompt 写得很朴素，整体表现也会稳很多。
