## 背景

Agent 产出的内容，默认格式基本都是 Markdown。它能进 git、能喂静态站点，也天然适合作为所有下游格式转换的中间表示。问题出在“发布”这一步：公众号、知乎、掘金、个人博客对 Markdown 的支持各不相同，靠复制粘贴手动调整，每发一篇都要重来一遍。我们的做法是把适配做成管线：模型只负责产出符合契约的标准 Markdown，其余交给确定性代码。

## 问题

实践中反复出现三类问题：

- 模型输出不规范：标题层级跳跃、代码块缺语言标注、把裸 HTML 混进 Markdown；
- 平台差异：公众号会过滤样式和大部分标签，部分平台不支持脚注、任务列表甚至复杂表格；
- 资源处理：外链图床有防盗链，本地 `file://` 路径会直接泄漏进正文。

## 做法

1. **约定输出契约并用代码校验。** 写进 system prompt：正文从二级标题开始、禁止裸 HTML、图片用约定占位符。同时用 lint 脚本机器校验——不要信任 prompt 约束本身。
2. **AST 化处理。** 用 remark/unified（Python 侧可用 markdown-it-py）把 Markdown 解析成 mdast，所有转换在 AST 上做。正则直接改原文，迟早会被代码块里的内容反噬。
3. **适配器插件化。** 统一接口：输入 mdast + 元信息，输出字符串 + 结构化 warnings。公众号走“Markdown 转 HTML + 内联样式”路线；知乎、掘金做降级（脚注转文内括号、任务列表转普通列表）；静态站补 frontmatter。适配器注册成 OpenClaw 插件后，Agent 可以通过工具调用直接触发构建。
4. **图片子管线。** 构建时统一上传转存，回填真实链接，顺便校验 alt 非空。
5. **产物落盘。** 源文件不可变，每个平台生成独立产物到 `dist/<platform>/`，git 版本化；warnings 汇总给人工过目，确认后再走发布（CI 或 MCP 工具）。

## 踩坑点

- 公众号不是“支持 HTML”，是“过滤 HTML"：`<style>` 会被剥掉、class 无效、SVG 被清空。代码高亮必须在构建期预渲染成内联色值。
- 脚注和任务列表在不支持的平台是静默丢失，不是报错。降级策略必须显式写出来，否则丢了内容都没人知道。
- 外链图片在编辑器预览里正常，发布后裂图。别信预览，统一转存。
- 转义问题：正文里的尖括号会被当 HTML 解析，在 AST 层统一做实体转义。
- 别把“归一化”结果写回源文件。canonical 源一旦被改，版本回溯就断了。

## 可复用建议

- 准备两三篇覆盖全语法的样本文档，对每个适配器做快照测试（golden file），改样式后 diff 评审，比肉眼检查可靠得多。
- 适配器保持无状态、可单测，warnings 用结构化数据返回，不要只靠日志打印。
- 契约做“提示词 + 代码校验”双保险：前者降低出错率，后者负责兜底。

## 总结

一句话：AI 负责内容，管线负责格式。把“多平台适配”从每次发文的体力活，变成一次写好、长期复用的确定性代码，发布才谈得上稳定和可维护。适配器本身并不复杂，难点在于把各平台的怪癖逐个踩一遍，并固化成测试防止回归。
