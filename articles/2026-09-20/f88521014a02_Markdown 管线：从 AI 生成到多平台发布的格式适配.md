## 背景

用 Agent 批量产出内容之后，真正的麻烦才开始：同一篇 Markdown 要发到静态站、公众号、知乎、掘金、GitHub README，而每个平台的渲染器都是不同的方言。AI 负责写，管线负责“翻译”，这件事必须工程化解决，不能每次发一篇手动调一遍。

## 问题

最常见也最贵的错误，是直接让模型输出“平台格式”。实际会撞上一堆硬约束：

- 公众号剥离几乎全部 HTML 属性，只认内联样式；
- 知乎对 GFM 表格支持残缺，任务列表 `- [ ]` 会原样吐出来；
- 静态站和 GitHub 支持 footnotes、任务列表，公众号全废；
- 代码块语法高亮方案各家不同，语言标签兼容度不一；
- 图片本地路径必须先传图床，部分平台还有防盗链问题。

让 AI 针对每个平台分别生成，等于把适配逻辑散落在 prompt 里，改一处要动 N 处。

## 做法

我们的管线分五步，核心原则：**AI 只产出受约束的“规范 Markdown 子集”，所有平台差异在 AST 层消化。**

1. **约定规范子集**。Prompt 里明确禁用 footnotes、任务列表、内联 HTML、深层嵌套引用；标题最多三级；表格列数设上限。Prompt 约束 + lint 兜底，双保险。
2. **归一化校验**。输出先过 markdownlint 自定义规则集，违规直接在 Agent 循环里打回重写，而不是人工补锅。这一步保证进入变换层的输入是干净的。
3. **AST 变换**。基于 unified 生态（remark-parse → 变换 → remark-rehype → rehype-* 插件）。典型变换：三级以下标题降级为加粗段落、表格套响应式容器、剥离 frontmatter、图片链接替换为图床 URL。
4. **平台适配器**。每个目标平台一个 adapter，输入统一 AST，输出平台方言：公众号走 HTML + 内联样式，知乎/掘金输出各自支持的 GFM 子集，静态站基本零改动。
5. **发布前校验**。golden file 测试：每个平台维护一组 fixture，变换结果 diff 通过才放行。对外再封装一个 MCP 工具做最终预览，其他 Agent 也能复用。

## 踩坑点

- **别在源码上跑正则**。早期我们用正则删 HTML 标签，结果把代码块里的转义示例一起删了。所有变换必须跳过 fenced code 区域，AST 层天然解决。
- **图片是最大的坑**。图床防盗链会让公众号编辑器抓图失败，需要服务端转存。上传要做成管线的显式步骤，别藏在渲染器里。
- **标题层级别贪深**。h4 之后移动端几乎不可读，公众号甚至渲染异常，统一降级为加粗段落观感更好。
- **frontmatter 记得剥离**。部分渲染器会把 `---` 之间的内容当分隔线或正文渲染，很难看。
- **转义二次污染**。星号、下划线、尖括号经过多层变换容易重复转义，测试用例要主动覆盖这些字符。

## 可复用建议

- 把“规范子集”写成两份产物：一份可塞进 system prompt 的规范文档 + 一套对应 lint 规则，两者同步维护。
- adapter 之间不要互相调用，保持扇出结构——出问题时能直接定位是哪个平台的变换坏了。
- fixture 集要包含最恶心的用例：代码块里的 Markdown 语法、嵌套列表、宽表格、特殊字符。
- 新接平台 = 写一个 adapter + 一组 fixture，工作量可控才算管线成立。

## 总结

Markdown 管线的本质是把**内容生产**和**格式适配**解耦：AI 只面对一个稳定的规范子集，平台差异收敛到 AST 层的 adapter。做到这一点，从 AI 生成到多平台发布就从“每次踩坑”变成“加一个模块”，这也是这套东西值得封装成 OpenClaw 插件或 MCP tool 的原因。
