## 背景

OpenClaw 的工作区里有几个固定入口的 Markdown：`AGENTS.md` 管工作规则，`IDENTITY.md` 管名字头像，`USER.md` 存用户上下文，而 `SOUL.md` 负责"这个 Agent 是谁"。它在每次会话启动时随引导文件一起注入 system prompt——等于一份全局生效、永远在线的人格声明。实践中常见两种极端：放着模板不动，或者一口气写成千字散文，两种都不太好使。

## 问题

用下来主要有三类毛病：

1. **空模板**。语气随模型波动，今天正经明天贫嘴，多轮对话后人设漂移，挂到自动化流程里尤其明显。
2. **写太满**。SOUL.md 超过几百行，每个会话都付一遍 token 税，还会稀释关键指令的注意力权重。
3. **误当安全边界**。在 SOUL.md 里写"未经确认不得发消息"，然后发现它照样发出去了——prompt 层的约束是软的，不是权限系统。

## 做法

**第一步，划清文件分工。** 人格、语气、价值观进 SOUL.md；操作流程和工具规范进 AGENTS.md；名字头像进 IDENTITY.md。混着写是规则冲突的主要来源。

**第二步，用四段骨架。** 我的 SOUL.md 固定四节：身份内核（我是谁、为谁服务）、语气（句长、先结论后细节、何时用列表）、原则与红线（不做什么、遇到什么先停下问）、升级规则（什么情况必须汇报而不是自作主张）。每条一行，整体控制在 60 行以内。

**第三步，写可判定的句子。** "保持简洁专业"没法验收，改成"回复默认 200 字以内，先给结论；不确定的事直接说不确定"。能写成 if-then 的，别写成形容词。

**第四步，边界做双层。** prompt 层写行为预期，工具层配硬约束：gateway 消息白名单、高危工具加审批、shell 类操作进沙箱。SOUL.md 说"不发"，权限层做到"发不出去"，两层叠加才算数。

**第五步，版本化 + 小回归集。** 工作区用 git 管理，改 SOUL.md 前后各跑一组日常问题（十来条够用），diff 行为变化。人设回退时能定位到是哪次改动引入的。

## 踩坑点

- **文件间打架**。SOUL.md 要求言简意赅，AGENTS.md 要求逐步解释，模型会随机站队。规则只在一个文件出现，定期 review。
- **把隐私和密钥写进去**。SOUL.md 进每次上下文，等同于全程广播。
- **指望它防注入**。网页内容和 MCP 返回值都可能夹带指令，人格声明挡不住，工具权限和确认机制才是底。
- **一次改太多**。行为变化没法归因，逐条改、逐条验。

## 可复用建议

- 先删后写：把模板里的空话全删掉，再往里加你真正观察到的行为问题，每条对应一次真实翻车。
- 用第二人称、现在时、短句陈述写，不要写背景故事。
- 每月删一次：从没触发过的红线合并掉，一份健康的 SOUL.md 只会越写越短。

## 总结

SOUL.md 是高杠杆、低强度的控制面：塑造风格和倾向很有效，但别把真正的安全边界托付给它。人格写在 SOUL.md，边界落在权限系统，两层各干各的活，Agent 才既像你调教出来的，又不会替你闯祸。
