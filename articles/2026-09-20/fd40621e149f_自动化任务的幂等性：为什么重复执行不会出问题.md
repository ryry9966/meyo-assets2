## 背景

在 OpenClaw 里跑自动化，迟早会遇到同一个现实：**任务不会只执行一次**。

cron 触发器在网关重启后补跑、webhook 因为超时被上游重发、agent 卡死后你手动重试、MCP 工具调用在网络层"成功了但响应丢了"——分布式系统对任务投递的基本承诺是 at-least-once（至少一次），而不是 exactly-once（恰好一次）。幂等性，就是你自己在应用层补上"恰好一次"的手段。

## 问题

不幂等的任务被重复执行，典型事故包括：

- 群里同一条播报发了三遍；
- 报表文件被 append 出重复段落；
- 数据库或笔记库里出现两条一样的记录；
- 调用计费 API，账单翻倍；
- agent 的记忆文件越重跑越臃肿。

根因都一样：**任务把"执行"当成了"产生副作用"的许可证**，而调度层恰恰无法保证只发一次这张许可证。

## 做法：四步把任务改成幂等的

**1. 定义幂等键。** 每个任务实例要有一个稳定的业务键：消息用 `message_id`，webhook 用 `event_id`，日报用 `job_id + 计划触发时段`（如 `daily-report@2025-06-01T08:00`）。键必须来自触发源，绝不能在任务内部随机生成——这是所有坑里最常见的一个。

**2. 执行前查状态。** 维护一张小状态表（SQLite 就够），记录 `key → running/done/failed + 产物位置`。任务开头先查：命中 done 就直接复用已有产物返回，不要重新生成。注意 agent 场景下 LLM 输出不确定，幂等针对的是"效果"而非"输出"。

**3. 写操作改成条件写。** 数据库用 `INSERT ... ON CONFLICT DO NOTHING` 或 upsert；文件用"写临时文件 + 原子 rename"；能 PUT 就别 POST。让重复执行天然收敛到同一个结果。

**4. 有外部副作用的，先记账再执行。** 发消息、调付费 API 这类没有原生幂等保证的调用，先把"即将执行 + key"写入状态表，成功后再更新为 done。顺序很关键：先调用后记账，中间一断电就是重复扣费。

## 踩坑点

- **check-then-act 不是原子的。** 代码里 `if (!exists) create()` 在两个重试并发时会各建一份。靠数据库唯一约束，别靠应用层 if。
- **"先删后建"不等于幂等。** 它消灭了重复，但丢了增量，还可能打断引用关系。目标是 upsert，不是 reset。
- **键粒度不对。** 太粗会误杀合法的第二次执行；太细（比如精确到秒的时间戳）等于没防。
- **只管 done，不管 running。** 上次跑到一半留下的半成品，会让下次执行既看到"没完成"又看到"已存在一部分"，行为不可预测。状态表至少三态：running / done / failed。
- **cron 补跑场景**，计划触发时间和实际执行时间不一致，键要用"计划触发时段"，不能用执行时刻。

## 可复用建议

- 给每个 skill / 插件写清一句话契约："本任务的幂等键是 X，重复执行的效果是 Y"。没写这条的自动化任务，默认视为不可重跑。
- 封装一个 `withIdempotency(key, fn)` 中间件统一维护状态表，别在每个脚本里手写一遍。
- 把"手动重跑昨天的任务，结果不变"纳入上线前的验收动作，和测边界条件一样对待。
- 日志里始终带 key，排查"为什么发了两条 / 为什么没发"时能省一半时间。

## 总结

幂等不是可选的工程美德，而是自动化的准入门槛：调度器和网络只会保证"至少一次"，"效果至多一次"必须由任务自己实现。下次写自动化任务时，先回答一个问题——**这个任务被连续执行两次，世界会变吗？** 答案是"不会"，它才配被放进 cron。
