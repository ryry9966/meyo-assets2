## 背景

跑 Agent 自动化一段时间后，你会接受一个事实：任何任务都迟早被执行两次。定时任务重叠、webhook 重复投递、Agent 超时后重试、手动补跑和计划任务撞车……重试不是异常，而是常态。幂等性就是让"重复执行"变得无害的设计约束：同一个操作跑一遍和跑十遍，最终状态一致。

## 问题在哪

典型场景：Agent 调用工具创建工单，网络超时，Agent 判断失败后重试——但第一次请求其实已经成功，结果系统里出现两张重复工单。类似的还有：通知重复发送、统计被重复累加、文件被重复追加、下游接口被重复调用。共同点是：操作效果随执行次数累积，而执行次数恰恰是我们控制不了的部分。

## 怎么做

1. **先分类**。天然幂等的操作不用处理：设置状态（set）、按唯一键删除、upsert。危险的是"每执行一次就多一份效果"的操作：insert、append、计数、发通知。
2. **用确定性键，不用随机键**。幂等的前提是两次执行能被识别为"同一件事"。键要稳定：`hash(任务类型 + 目标对象 + 业务时间窗)`，而不是每次 `randomUUID()`。同一同步任务在同一时间窗内，跑几次键都相同。
3. **写入语义改成 upsert**。插件工具尽量暴露"设置/覆盖"语义而非"追加"，数据库层面用唯一约束兜底，让第二次插入自然失败或被忽略。
4. **外部调用带幂等键**。调用第三方 API 时，对方支持 idempotency key 就一定带上；不支持的话，发送前先查本地记录"这个键是否已发送过"。
5. **留执行日志，先查后做**。用本地 SQLite 或文件记录"某键已完成"，任务启动时先查日志，已完成的步骤直接跳过。这同时让中断恢复变得简单。

## 踩坑点

- **"先查后做"有竞态**。两个并发实例同时查到"不存在"，然后都去创建。应用层检查挡不住并发，必须靠存储层的唯一约束兜底。
- **超时 ≠ 失败**。最容易踩的坑：请求实际成功但响应丢失，重试造成重复效果。只有幂等键或"执行后回查"能解决，单纯的 try-catch 重试不行。
- **键里混入了变化因素**。键带秒级时间戳或随机后缀，重试就变成"新任务"。键的粒度要对齐业务语义：一次同步、一个对象、一个窗口。
- **批量任务只做整体幂等**。100 条数据跑到第 60 条崩了，重跑必须跳过前 60 条。幂等粒度要下沉到单条记录，而不是整批。
- **外部副作用无法回滚**。邮件、webhook 发出去就收不回来，去重必须发生在"发送前"，不能靠事后补偿。

## 可复用建议

- 设计 MCP 工具/插件时，默认提供 upsert 风格接口，并在文档里标注每个工具"是否可安全重试"。
- 定时任务统一假设"总会被跑两次"，用 reconcile（对账）模式：先算期望状态，再与实际状态 diff，只应用差异。这比 append 式任务健壮得多。
- 把幂等性写进测试：CI 里连续跑两遍任务，diff 两次之后的系统状态，应当完全一致。
- 固定运行时间戳：任务开始时确定"本次业务时间窗"，避免重试时窗口漂移导致键变化。

## 总结

重试不可避免，重复执行是自动化的默认处境而非意外。幂等性不是高级优化，而是自动化任务的及格线：确定性的键、upsert 的写入语义、发送前的去重检查、单条粒度的断点恢复。把这四件事做进工具设计，你的 Agent 才敢放心地"失败就重来"。
