## 背景

在 OpenClaw 的插件和 Agent 自动化链路里，让模型返回 JSON 是最高频的约定。但只要跑得够久，就得承认一个事实：**模型是概率性的序列化器**。即使 prompt 里写死了"只输出 JSON"，实际返回依旧五花八门。我们统计过一条自动化流水线的失败原因，解析失败占比最高，而且几乎全部来自格式漂移，而非业务逻辑错误。

## 问题：五种常见的"混合格式"

同一个 prompt、同一个模型，温度调高一点就会遇到：

1. **代码围栏包裹**：```json ... ```，围栏内可能还有嵌套对象；
2. **自定义标签包裹**：`<json>...</json>`、`<result>...</result>`，不同模型版本偏好的标签名还不一样；
3. **前后夹叙**：`"好的，以下是结果：{...}，希望有帮助"`；
4. **全角标点**：中文语境下偶尔输出全角引号、全角冒号；
5. **截断**：max_tokens 打满，JSON 只剩半截。

裸 `json.loads` 在第 1、3、4、5 种情况直接崩；用贪婪匹配 `r'\{.*\}'` 遇到夹叙就翻车；换非贪婪 `.*?` 又会在嵌套对象处提前截断。

## 做法：分层降级解析

思路是不指望某一条正则通吃，而是像剥洋葱一样逐层处理，任何一层成功就短路返回：

```python
def robust_parse(raw: str):
    # L0: 原文落盘留档，永远最先做
    # L1: 直接 json.loads
    # L2: 剥代码围栏（只匹配行首围栏，避免误伤字符串里的反引号）
    # L3: 标签提取（标签名做成可配置列表，逐个尝试）
    # L4: 括号配平截取：从首个 { 或 [ 开始做深度计数，
    #     并跳过字符串字面量内部的花括号
    # L5: 容错修复：去尾逗号、全角转半角、智能引号替换
    #     （建议直接用 json-repair 类库，别自己造轮子）
    # L6: schema 校验（pydantic / zod），缺字段给默认值或显式报错
```

L6 是最容易被忽略的一层：**解析成功不等于内容可信**。工具调用参数、路径、金额这类字段必须过 schema，而不是把 `None` 静默传给下游。

最后是重试：所有层都失败时，把解析错误信息和原文截断后回传给模型，要求它"按此错误修正输出"。这比换 prompt 重跑便宜得多。

## 踩坑点

- **围栏误伤**：字符串值里含 ``` 时，全局 strip 会破坏内容，剥围栏务必只处理行首；
- **盲目全局替换**：全角标点修复要限定在结构层，字符串值里的全角字符可能是业务数据，替换掉就改了语义；
- **把截断当损坏修**：修复库能"补全"半截 JSON，但补出来的内容是编的。检测到截断应触发重试，不要硬修；
- **多对象拼接**：模型偶尔一次吐两个 JSON 对象，`loads` 报 "Extra data"，解析层要能识别并明确处理；
- **解析即信任**：解析通过 ≠ 可以执行，工具侧对参数再做一遍校验。

## 可复用建议

1. 解析器做成独立模块，Agent、插件、MCP 工具共用一份，别各写各的；
2. 每次线上解析失败，把原文丢进"脏输出语料库"，攒起来做回归测试——这个语料库比任何 prompt 技巧都值钱；
3. 监控解析成功率，按模型版本和 prompt 版本打标，格式漂移会先在指标上显形；
4. 模型支持 structured output / JSON mode 就优先用，但降级路径必须保留，第三方接入的模型不保证都开；
5. prompt 侧三件套：精确 schema + 一个 few-shot + "不要输出任何其他文字"。这能把 L2–L5 的触发概率压低，但永远不要假设它们不会被触发。

## 总结

防御性解析的本质，是把模型输出当成不可信输入处理：**分层降级、留档可查、校验兜底、失败可重试**。这四件事做扎实，自动化链路的长尾故障会肉眼可见地减少。解析层多做的每一层，都是给下游省下的一次凌晨排障。
