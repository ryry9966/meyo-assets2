## 背景

OpenClaw-CN 社区日常有一批稳定的信息要维护：相关项目的 GitHub Release、RSS 更新、值得转述的折腾记录。以前靠人肉搬运，写到第三篇就开始敷衍。于是花了两周，基于 OpenClaw 的 agent + MCP 工具链搭了一个发帖机器人，至今稳定跑了一个月。这篇不谈愿景，只讲架构怎么定、坑踩在哪。

## 整体架构：智能只放在一层

我的核心设计原则是：**LLM 只负责"写"，不负责"发"**。整条链路分四层：

1. **采集层**：cron 定时拉取 GitHub Release API 和若干 RSS 源，落 SQLite，带内容哈希做一级去重；
2. **生成层**：OpenClaw agent 挂两个 MCP 工具（fetch、db_query），按固定模板把原始 changelog 压成 300 字以内草稿；
3. **审核层**：草稿先推到私人 Telegram 会话，回复"ok"才进入发布队列；
4. **发布层**：一个纯确定性脚本，只做一件事——调论坛 API 发帖，不调用任何模型。

## 踩坑实录

**坑一：重复发帖。** cron 任务偶尔重叠，叠加超时重试，同一篇内容发出去三次。修法：以「源 URL + 版本号」哈希做幂等键，发布前先查库，发布结果无论成败先落库，重试时携带同一幂等键。

**坑二：代码块炸排版。** changelog 里的三反引号进入草稿后直接破坏帖子 Markdown 渲染。修法：生成后统一把三反引号围栏升级为四反引号，发帖前再跑一遍渲染校验。

**坑三：模型编造链接和版本号。** 早期允许模型自由改写，出现过幻觉链接。修法：改为工具优先——所有链接、版本号必须来自 MCP 工具返回值，模型只负责组织语言；发布前对每个链接做 HEAD 请求，404 直接打回重写。

**坑四：限流与社区观感。** 无脑重试把论坛 API 打出 429，凌晨自动发文观感也差。修法：指数退避，发布收敛到每天 9:00 / 21:00 两个固定窗口。

**坑五：Agent 死循环。** 任务没达成时 agent 反复调工具不收敛，烧掉不少 token。修法：max_steps 和 token 预算双重兜底，超限自动转人工处理。

## 可复用建议

- 发布动作永远是确定性脚本，别把发帖 API 直接塞给模型；
- 上线初期全量人工审核，误报率稳定后再开自动白名单；
- 每次发布记录 request_id 和完整请求体，出问题有据可查；
- token 走环境变量，权限最小化：只允许发帖和编辑自己的帖子。

## 总结

上线一个月发了 40 篇左右，两次低质量草稿在审核层被拦下，重复发帖归零。最大的体会是：这类机器人的难点不在"让模型会写"，而在"让它按规矩写、按规矩发"。把不确定性关进生成层，把发布交给确定性代码，剩下的就是普通运维。代码已整理成 OpenClaw 插件模板，后续另开帖讲 MCP 工具的具体封装。
