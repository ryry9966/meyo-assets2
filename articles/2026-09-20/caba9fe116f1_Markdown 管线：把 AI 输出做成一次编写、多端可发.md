## 背景

Agent 工作流里，LLM 的输出天然是 Markdown——写文章、发周报、整理文档，初稿几乎都是 `.md`。但发布端是碎片化的：博客（Hugo/Hexo）吃 front matter，知乎接受受限的 HTML 子集，公众号编辑器只认逐元素内联样式，图卡类平台干脆要求渲染成图片。结果就是"AI 写完只是开始"，每次发布都要人工调一遍格式。

## 问题

差异有三层：

1. **AI 输出本身不规范**：任务列表、脚注、行内 HTML、四层嵌套列表、没有语言标注的代码块，甚至自己编一段 front matter；
2. **平台方言**：各家支持的语法子集、标题层级约定、图片外链策略都不同；
3. **媒资处理**：本地路径图片、图床防盗链、平台转存，都需要单独处理。

第一反应通常是用正则做字符串替换，这也是第一个坑——`**加粗**` 的替换规则会污染代码块内容。正确姿势是把 Markdown 当 AST 处理，别碰原始字符串。

## 做法

社区里常见的做法是搭一条"归一化 → 适配"管线，以 AST 为枢纽：

**1. 定义规范子集。** 先在 prompt 层约束模型：二级标题起步、禁用脚注和任务列表、表格不超过四列。生成端预防永远比后端修复便宜。

**2. 归一化。** 用 remark 解析成 mdast，跑自定义 lint/repair 插件：剥行内 HTML、标题层级统一平移、嵌套列表拍平到两层、转义裸露的 `<`、代码块语言映射到平台白名单。输出一份"规范 Markdown"，进 git 作为唯一事实源。

**3. 适配器。** 每个目标平台写一个薄渲染器：博客端注入 front matter；公众号端转成带内联样式的 HTML，经剪贴板或浏览器扩展写入编辑器；图卡平台把 AST 渲染成 SVG 再导出图片。适配器只消费 AST，逻辑互相独立。

**4. 媒资。** 图片统一先传自有图床并在 AST 里重写 URL；对会转存图片的平台（如公众号），发布前再触发一次平台侧上传，避免外链被屏蔽。

**5. 接入 Agent。** 把管线封装成 MCP 工具——`convert(source, target)`、`publish(target)`——Agent 拿到初稿后自主完成转换和分发，人只在发布前看一眼归一化 diff。

## 踩坑点

- 公众号会剥掉 `<style>` 标签，样式必须逐元素内联，SVG 支持也不完整；
- 模型爱写四层嵌套列表，手机端排版直接崩，拍平比渲染端修正省事得多；
- 标题层级：模型常从 `#` 起步，而平台标题来自元数据，记得统一 shift，别在适配器里各改各的；
- 平台编辑器改版不打招呼，归一化规则的快照测试要常跑，输出变了要 fail loudly，而不是静默发出错版；
- front matter 冲突：模型可能自己生成 YAML 头，先剥掉再按元数据生成，避免字段悄悄丢失。

## 可复用建议

- "允许的 Markdown 子集"写进系统提示 + 用 lint 兜底，双保险，别只靠 prompt；
- 每个适配器配一份"大杂烩"夹具文档（表格、代码、列表、引用、图片全都有），做快照测试；
- 归一化过程记录 diff，方便人工抽查模型输出的怪癖；
- 把 AST 当枢纽、适配器当廉价的叶子节点，新平台半天能接上。

## 总结

一句话：别把 Markdown 当最终格式，把它当中间表示（IR）。生成端收敛、归一化自动化、适配器做薄、测试兜底，"一次生成、多端发布"才不是口号。
