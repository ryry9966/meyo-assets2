## 背景

Agent 接上 MCP 和插件之后，能力从「聊天」变成了「动手」：读数据库、写文件、调内部 API、发消息、花钱。能力上一个台阶，风险也跟着上一个台阶。实践里最常见的两种失败，往往不是 Agent 太笨，而是边界没划清：一种是什么都问，人沦为点确认的机器；另一种是什么都干，直到某天在生产库上跑出一条不可逆的语句。

## 问题

「该不该问人」看起来是产品问题，其实是工程问题。难点有三个：

- **影响面差异巨大**：同样是写操作，往本地临时目录写文件和往生产库写数据，完全是两回事；
- **Agent 的自我判断不可靠**：模型对后果的估计来自工具描述，而工具描述经常和真实行为有偏差；
- **人也有成本**：确认弹窗太多，会训练出「无脑点同意」的习惯，比不问还危险。

## 做法：按可逆性 × 影响面分四档

把 MCP server 暴露的每个 tool 盘点一遍，按两个维度打分——**能否撤销**、**影响谁**——然后归档：

1. **自动执行**：只读操作、沙箱内写文件。留日志，不问。
2. **自动执行 + 事后通知**：建分支、提 PR、写内部文档。可逆但别人看得到，干完说一声。
3. **必须确认**：删数据、改生产配置、对外发邮件、任何涉及钱和外部 API 的调用。问，而且要带着「将要发生什么」去问。
4. **永远不做**：写进 deny list，比如删库、批量群发、超预算消费。直接拒绝，不是问。

落地配置可以很薄：

```yaml
tools:
  fs.read:    { tier: auto }
  fs.write:   { tier: auto, scope: "workspace/tmp/**" }
  github.pr:  { tier: auto_notify }
  db.delete:  { tier: ask, require: diff_preview }
  email.send: { tier: ask, rate_limit: "5/hour" }
  payment.*:  { tier: deny }
```

配套四条规则：

- **确认请求必须结构化**：动作、目标、diff、回滚方式，缺一不可。一句「我可以执行吗」没有决策价值；
- **设硬预算**：调用频率、金额上限、时间窗口，超限自动降级为问人；
- **确认设超时**：无人应答默认不执行，绝不默认放行；
- **全量留日志**：每月回看「问了什么、干了什么」，据此把工具在档位之间移动。

一句话原则：**读操作自动，写操作看影响面，钱和外部世界必须问，没把握时降级到问。**

## 踩坑点

- **「只读」不可信**：有些 GET 会触发 webhook 甚至计费，要按真实影响面分级，别看方法名；
- **确认疲劳**：一个工具一周被确认 30 次且从没被拒，说明档位放错了，该下移，而不是继续骚扰人；
- **模糊确认等于没确认**：不带 diff 的确认，人只能盲点，责任其实还在你；
- **批量操作一次性授权**：一次同意覆盖 50 条删除，应该分批预览、分批确认；
- **重试放大副作用**：发送失败自动重试 5 次，外部世界就收到 5 条消息，副作用类调用要有幂等键；
- **粒度太粗**：按整个 MCP server 授权而不是按 tool 授权，一个危险的 tool 会污染整组信任；
- **会话恢复丢状态**：确认状态要持久化，否则 Agent 要么重复问，要么重复执行。

## 可复用建议

- **起步从严，用审计日志决定放宽**，而不是凭感觉；
- **权限策略当代码管**：进 git、走 review、有变更记录，改边界和改代码一样严肃；
- **答不出回滚方案的写操作，默认升档**为必须确认甚至不做；
- **deny list 宁可误杀**，单独立项维护；
- **定期演练**：故意丢给 Agent 一个高危任务，验证权限层是否真的拦住了。

## 总结

权限边界不是一次性设计，而是随工具清单和事故经验持续修订的活文档。判断标准可以很朴素：**这件事错了能不能撤销？影响的是我自己、团队，还是外部世界？**两个问题答不清楚，就问人。Agent 的自主性应该建立在「边界被显式定义」之上，而不是「这次大概没事」的侥幸上。
