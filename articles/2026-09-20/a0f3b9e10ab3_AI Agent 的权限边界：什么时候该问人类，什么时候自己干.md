## 背景

Agent 框架成熟之后，能力边界基本等于它挂载的工具边界：MCP server、插件、shell、HTTP。能力上来以后，真正难的问题不再是"能不能做"，而是"该不该自己做"。每个跑自动化的人，迟早都会撞上这堵墙。

## 问题：两种失败模式

实践中常见两类极端：

**过度谨慎**：agent 每读一个文件、每跑一条命令都停下来问"确定吗？"。人变成流水线上的点击工人，自动化价值归零。更糟的是，高频确认会把人训练成无脑点"是"——真到危险操作时反而没人细看。

**过度放权**：agent 拿着 shell 和全量工具直接上，某次理解偏差执行了 `rm -rf`、force push，或者把消息发到了真实用户群里。不可逆操作没有刹车，一次事故就够还很久。

根源是：权限边界没被当成工程问题来设计，而是靠默认配置加提示词里一句"谨慎行事"。

## 做法：三个维度分四层

先给每个工具调用按三个维度打分：

1. **可逆性**：做完能不能撤销？git 能回滚的文件编辑是可逆的；删数据、对外发消息、花钱不是。
2. **影响半径**：改动落在 workspace 沙箱里，还是生产环境、真实用户、外部系统？
3. **意图清晰度**：指令到动作的映射有没有歧义？照章办事和需要 agent 自行发挥，风险完全不同。

由此分四层：

- **L0 自动执行**：只读 + 范围内。读文件、搜索、`git status`、沙箱里跑测试。
- **L1 自动执行但留痕**：workspace 内可逆写操作。编辑文件、建分支，配合 git 快照随时回滚。
- **L2 首次确认，记住选择**：新工具第一次用、新范围第一次碰。批准一次，记录 scope，同类操作本次会话内放行。
- **L3 必须问人**：不可逆、出边界、花钱、删数据、对外发送。每次都问，而且要带着 diff 和回滚方案问。

在 OpenClaw 里的几个落地抓手：

- 工具网关做白名单/黑名单，规则细到**参数级别**——`git push` 和 `git push --force` 不是一回事。
- 用 git 提交/快照把写操作"制造"成可逆的，很多 L3 就降级成了 L1。
- 把"申请批准"本身做成一个工具：agent 调 `request_approval`，附上改动摘要，人在聊天里批，记录落盘。
- 设预算上限：最大步数、最大花费、速率限制，超了就暂停转人工。
- 危险 shell 命令走策略层拦截，`rm -rf`、`curl | sh` 这类 pattern 直接 deny。

## 踩坑点

- **确认疲劳**：问得太多等于没问。宁可少问，每次问都展示具体后果和回滚方式。
- **"只读"不等于安全**：能读 secrets 又能对外写的组合就是数据外泄通道。读权限也要圈范围，别把 `~/.ssh`、`.env` 挂进 workspace。
- **提示词不是执法层**：system prompt 里写"请不要删除文件"只是礼貌请求，真正的限制必须在工具网关强制。
- **批准要有 TTL**：一次批准悄悄变成永久批准，scope 和有效期都要显式记录。
- **子 agent 和插件会继承权限**：插件内部再调别的工具时，权限链要透传检查，否则白名单形同虚设。
- **别让 agent 问模糊的问题**："我可以继续吗？"没有信息量。要求它先给方案、风险、回滚三件套再问。

## 可复用清单

- 每接入一个工具，先标注：可逆吗？半径多大？出边界吗？花钱吗？
- 默认最小权限；可逆性靠 git/快照主动制造，不是靠祈祷。
- 不可逆操作统一走审批通道，"diff + 回滚方案"是提问的最低标准。
- 审批留痕：谁、何时、批了什么、scope 多大。
- 定期复盘被拒和被批的请求——规则是活的，随事故和经验演进。

## 总结

权限边界不是一条固定的线，而是"可逆性 × 影响半径 × 意图清晰度"的函数。工程方向很明确：尽量把操作变得可逆，能放手就让 agent 自己干；把人类注意力留给真正不可逆、真正模糊的决策。问人不该是兜底，而是被设计出来的一等公民组件——问得少、问得准、问了就有记录，这才是 agent 自动化能长期跑下去的前提。
