## 背景

RSS 是目前仍然可靠的信息聚合方式：无算法干预、源可控、标准统一，问题只在于订阅多了读不完。我的场景是 30+ 个技术博客与新闻源，日均新增 60~100 条，人工筛选成本太高。目标很朴素：让 agent 每天早晚各跑一次管线，产出一份摘要日报——人只看结论，感兴趣的再点原文。

## 问题

最容易想到的做法是"把 feed 直接扔给大模型"，实际有三个硬伤：

- token 成本不可控，全文摘要一天能烧掉几十万 token；
- 相当一部分源的 RSS 只有 summary 甚至只有标题，摘要质量靠猜；
- 跨天重复严重，同一篇文章改个标题就再来一遍。

所以要的不是一段聪明的 prompt，而是一条**可重跑、成本可预算、输出格式稳定**的管线。

## 做法

整体分四层。抓取层做成独立工具（本地脚本或 MCP server 均可），其余交给 OpenClaw：

1. **订阅收敛**：所有源整理成 OPML，按主题分组。重点源走全文摘要，低优先级源只进标题流，不做摘要。
2. **抓取层**：定时拉 feed，以条目链接 hash 做主键入库（GUID 不可靠，不少源会变）；请求带上 ETag / If-Modified-Since，源没更新就不产生新条目；对只有 summary 的源补一次 readability 类正文抽取。
3. **摘要层**：只把"本次新增"条目送模型，prompt 固定成模板，要求结构化输出：

```json
{"title": "...", "point": "一句话要点", "score": 1-5, "deep_read": true}
```

先用便宜的小模型批量跑，score 达标的少数条目再交给强模型深读，两段都锁死输出格式。

4. **分发层**：汇总成 digest，通过 OpenClaw 已接入的聊天渠道推送，同时落一份 markdown 到本地目录按日期归档，方便日后检索。

调度上早晚各一次 cron。抓取、摘要、分发三段解耦：抓取挂了不影响已入库条目，摘要挂了下一轮补跑即可。

## 踩坑点

- **正文抽取失败要降级**：反爬或特殊排版会让 readability 抽出空文本，此时降级用 RSS 自带 summary 并打上"低置信"标记，别硬摘要。
- **去重以数据为准**：早期手动触发和 cron 撞车，同一批条目推了两次。不要依赖 agent 会话内记忆做幂等，去重逻辑放在存储层。
- **预筛比摘要省钱**：第一版全文全送模型，改成"标题+首段预筛 → 小模型摘要 → 大模型深读"三级漏斗后，token 用量降了一个数量级。
- **输出格式要防崩**：小模型偶尔在 JSON 外加一句解释导致解析失败。prompt 里放 few-shot，解析失败重试一次，仍失败就原文入库留给人工，不要静默丢弃。
- **源会腐化**：有的 feed 改版后持续报错或半年不更新，加了个健康检查，连续失败 5 次标记待清理。

## 可复用建议

- 摘要结果一定落本地 markdown，而不只是推消息——半年后还能搜到的才有价值。
- prompt 当代码管理：放进配置文件，改动留 diff，坏了能回滚。
- 三段解耦、每段可独立重跑，是这类管线后期省心的关键。
- 先跑一周再调 prompt：多数"摘要质量差"其实是预筛没做好，不是模型不行。

## 总结

这套管线没有任何黑科技，价值在于把"每天筛信息"的固定开销变成一次性的工程投入。运行一个月后，日报从 60+ 条压到 10 条以内，真正会点开的只有 3~5 条，信噪比提升明显。RSS 不会死，缺的只是一层顺手的自动化。
