## 背景

用 Agent 写技术帖现在是我的常规操作：让模型按模板产出 Markdown，人只做审校。但真正发出去就会发现，"Markdown" 并不是一个统一标准——公众号要 HTML 加内联样式，掘金、知乎各自支持不同的扩展语法，静态博客还要 frontmatter。同一份稿子在三个平台手工改三遍，是最消耗热情的环节。

## 问题

AI 生成还带来额外的坑：

- 输出不稳定：有时混进裸 HTML、脚注、mermaid 图，目标平台未必支持；
- frontmatter 常被原样贴到不支持的平台，页面上裸露一段 YAML；
- 远程图片链接在公众号被防盗链拦截，读者侧直接裂图。

核心矛盾是：生成端想自由表达，发布端各有硬约束。

## 做法

我的思路是"规范收敛 + 定向渲染"，管线分五步：

1. **约束生成端**。在 Agent 的 system prompt 里限定语法子集：只允许标题、段落、列表、表格、围栏代码块，禁止裸 HTML、脚注、mermaid。事前约束比事后修复便宜得多。
2. **lint 门禁**。用 markdownlint 加自定义规则校验：标题层级连续、图片必须带 alt、无裸 HTML、代码语言标签统一小写。lint 报错回喂给 Agent 自修复一轮，不过 gate 不进下一步。
3. **元数据分离**。标题、日期、标签让 Agent 单独输出成 YAML，渲染时按目标平台决定是否拼进 frontmatter，避免泄漏。
4. **图片独立管线**。先上传图床拿到稳定 URL 做映射替换；发公众号再走素材接口二传。资产问题单独处理，不混进文本转换。
5. **按目标渲染**。用 remark / markdown-it 写三个渲染器：公众号走 HTML 加内联样式；知乎、掘金近乎直出，只微调表格和代码块；博客拼 frontmatter。每个渲染器是幂等纯函数，配快照测试。

后来我把 lint 和渲染包成两个 MCP tool：`lint_markdown` 和 `render_for(target)`。在 OpenClaw 里一句话完成"生成 → 自检 → 出三份成品"，发布前我只做一次人工预览。

## 踩坑点

- 公众号会过滤大部分 style 属性和所有外链：a 标签被降级成纯文本，重要链接要么放"阅读原文"，要么写成可见 URL；
- 转义顺序错了会出现二次转义，比如 `&amp;lt;` 这种叠罗汉——渲染器必须单进单出，别在中间态来回横跳；
- 移动端表格三列以上必溢出，宽表提前拆成列表；
- 图床防盗链比想象中普遍：编辑器里"看似正常"的远程图，用户侧打开就是裂图，务必用素材库 URL；
- 代码块语言标签大小写会影响高亮渲染，在 lint 里统一成小写最省心。

## 可复用建议

- **单一事实源**：永远只维护一份 canonical Markdown，不要为平台手改副本；
- **约束前置**：prompt 限语法子集，加 lint 回喂自修复，比正则事后清洗稳定；
- **渲染器纯函数化**：幂等 + 快照测试，改某平台规则不动管线其他部分；
- **保留人工节点**：Agent 负责生成与自检，发布前留一次预览，出问题能兜底。

## 总结

Markdown 多平台适配的本质不是"格式转换"，而是"规范收敛"：生成端收得越紧，渲染端越简单。把 lint 和渲染封装成 Agent 可调用的工具之后，整条管线才算闭环——模型管产出质量，管线管格式确定性，人只管最后那一次点头。
