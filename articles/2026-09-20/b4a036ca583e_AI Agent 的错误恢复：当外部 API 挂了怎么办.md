## 背景

Agent 系统的本质是把不确定性串起来：LLM 调用、MCP 工具、搜索、数据库、第三方 SaaS。任何一个环节超时或报错，整条任务链就可能中断。和传统后端不同，Agent 挂掉的方式更“贵”——不仅请求失败，还可能在重试中反复烧 token，甚至带着半截上下文继续编造结果。

## 问题

实际跑自动化任务时常见的三类故障：

1. **瞬时故障**：429 限流、502/504 网关错误、网络抖动。占绝大多数，等一下就好。
2. **持久故障**：401 鉴权失效、404 资源不存在、参数错误。重试一万次也没用。
3. **静默故障**：请求“成功”但返回空数据或截断结果，Agent 把空结果当事实继续推理，输出幻觉。

很多框架的默认行为要么“抛异常即终止”，要么“原样无限重试”，两种都不可取。

## 做法

我们的经验是把错误恢复拆成四层：

**1. 先分类，再重试。** 只对可重试错误（超时、429、5xx）重试；4xx 类错误直接走失败分支。这个判断写在统一封装的 API client 里，不要散落在各个工具函数中。

**2. 指数退避 + 硬上限。** 重试间隔 1s → 2s → 4s，加随机抖动避免重试风暴；同时设上限：最多 3 次、总耗时不超过 30s、token/金额预算封顶。到上限就放弃，不要和宕机的服务死磕。

**3. 明确的降级路径。** 每个外部依赖准备三选一：备用 API、缓存的近期结果、或跳过该步骤但在最终输出中显式标注“此部分数据不可用”。关键原则：宁缺毋假。

**4. 状态可续跑。** Agent 任务按步骤持久化中间状态，失败后从断点恢复而非从头重跑。前提是每个外部写操作要幂等（带唯一请求 ID），否则重跑会产生重复副作用。

另外，错误信息要结构化后传回 LLM：告诉它“搜索工具超时，已重试 3 次”，而不是甩一段原始堆栈或干脆不说话。模型需要知道发生了什么，才能正确调整计划。

## 踩坑点

- **无退避的立即重试**：自己把自己的限流额度打爆，429 变成永久封禁。
- **重试非幂等操作**：发消息、下单类接口重试一次，用户收到两条通知。
- **超时只在框架层设**：底层 HTTP 客户端没设超时，单次调用悬挂 10 分钟，整条流水线卡死。
- **空结果静默通过**：没有 schema 校验，返回 `[]` 也算成功，Agent 开始自由发挥。
- **降级了但没说**：静默切到旧缓存，用户拿到过期数据还以为是实时的。

## 可复用建议

- 把“分类 → 重试 → 降级 → 记录”封装成一个通用 wrapper，所有 MCP 工具和外部调用统一走它。
- 所有外部返回过一遍 schema 校验（JSON Schema / Pydantic 均可），不合格按失败处理。
- 日志固定记录：工具名、attempt 次数、错误码、耗时，排障时能直接还原时间线。
- 给每个 Agent 任务设总预算（时间 + token + 金额），超了就优雅终止并汇报原因。

## 总结

外部 API 挂掉不是异常路径，而是 Agent 的日常。好的错误恢复不是让任务永不失败，而是让失败**可控、可续、可解释**：该重试的重试，该降级的降级，该承认失败的诚实承认。Agent 的可靠性上限，往往取决于它对下游故障的态度。
