## 背景

日常开发里有两类 Git 操作高频但低价值：写 commit message、管分支（命名、清理、合并前整理）。这些事不难，但每天重复十几次，还容易被赶时间的人做得很随意——`fix`、`update`、`临时改一下` 这样的提交信息谁都没少写。

OpenClaw 这类 Agent 框架的思路是给模型工具调用能力：Agent 能跑 shell、能读文件，那 Git 这种结构化、规则明确的操作恰好适合交给它。本文记录我在自己仓库里落地「Agent 管 Git」的过程和教训。

## 问题

直接让 Agent 操作 Git 有三个坎：

1. **提交信息质量不稳定**。模型如果不看真实 diff，会基于文件名编造提交说明。
2. **危险操作不可控**。`push --force`、`reset --hard`、amend 已推送的提交，一旦被 Agent 自作主张，恢复成本很高。
3. **交互阻塞**。git 在缺凭证或需要编辑器时会挂起，Agent 会话就卡死在那里。

## 做法

我按风险分层推进，而不是一步到位。

**第一步：只读。** 只开只读工具（通过 MCP 工具声明或 shell 白名单）：`git status / diff / log / branch -a`。让它每天输出当前分支状态、未提交改动摘要、超过 30 天未动的本地分支列表。零风险，先验证它的输出可信度。

**第二步：提交信息生成。** 把 `git diff --staged` 喂给 Agent，约束输出 Conventional Commits 格式。关键点是结构化输出（JSON：type/scope/subject/body），外层脚本用正则校验通过后才执行 `git commit -m`；不过就打回重写，最多重试两次。

**第三步：分支整理。** 定死命名规则（`feat/`、`fix/`、`chore/` 前缀），建分支时强制套用；对已合并分支，Agent 只生成清理建议清单，人确认后再删。

**第四步：推送确认闸门。** 所有写操作（commit 除外）走「Agent 生成命令 → 人看过 → 脚本执行」流程。push 一律不带 `--force`，遇到需要 force 的场景直接终止并提示人工介入。

Prompt 和脚本放在仓库的 `.agent/` 目录里随代码版本化，团队成员克隆下来就用同一套规则。

## 踩坑点

- **diff 过大爆上下文**。一次重构改了 40 个文件，整段 diff 直接超限。改成按文件分块生成，再让 Agent 汇总成一条提交信息。
- **提交信息凭空捏造**。有次 Agent 在没拿到最新 staged diff 的情况下「总结」了提交内容，写得头头是道但全是错的。教训：每次生成前强制重跑 `git diff --staged`，禁止复用上轮结果。
- **交互命令挂起**。git 要求输入凭证时 Agent 会傻等。所有 git 调用加 timeout，凭证统一走 credential helper。
- **格式漂移**。模型偶尔输出带句号、subject 大写开头等不一致。正则白名单校验 + 失败重试基本解决，但校验规则本身也要持续维护。

## 可复用建议

1. 权限分三档：只读常开、写操作需确认、破坏性操作禁止。别靠一句话 prompt 管，用工具白名单管。
2. 输出一律结构化，校验后再执行，不要让自然语言直接变成 shell 命令。
3. 每次 Agent 的 git 操作落一份日志（时间、命令、diff 摘要），出问题能回溯。
4. 从提交信息生成这种低风险场景起步，跑稳两周再放开分支管理。

## 总结

Agent 管 Git 的价值不在「全自动」，而在把重复决策（这条提交怎么描述、这个分支该不该删）变成有规则、可校验、可审计的流程，人的角色从执行者变成审核者。这套流程我跑了三周，提交信息质量明显稳定，误操作为零——前提是那道人工确认闸门一直没拆。建议同样从最小风险场景切入，先建立信任，再逐步放权。
