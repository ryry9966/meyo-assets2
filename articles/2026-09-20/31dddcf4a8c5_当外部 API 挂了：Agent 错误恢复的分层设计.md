## 背景

OpenClaw 里的 Agent 和脚本最大的区别：它不是按固定顺序调外部服务，而是在推理循环里动态决定调哪个工具。MCP 工具、第三方 API、内部服务，任何一个抖动，故障都不只是“抛个异常”——错误信息会直接进入模型上下文，影响后续所有决策。

实际跑自动化流水线时见过三类典型翻车：API 返回 503 后，Agent 开始脑补返回值继续往下跑；掉进重试死循环，一晚上烧掉几十万 token；把堆栈原文塞进上下文，模型从中“推断”出不存在的字段。

## 问题出在哪

根因是职责没分清。重试、退避、超时是确定性逻辑，交给模型在 prompt 里“自己决定重试几次”，等于让一个不看表的人控制节奏。反过来，“降级还是中止”“要不要告诉用户”这类判断，代码写死又太僵。另外，工具返回值往往是为程序员设计的：原始堆栈、HTML 错误页，人能看懂，模型只会被污染。

## 做法：按层拆

1. **工具层做分类，不做决策。** 每个调用包一层标准信封 `{ok, error_type, retryable, retry_after_ms}`，区分三类：瞬时故障（429/503/网络抖动）、永久故障（401/403/配额耗尽）、模糊故障（超时、半截响应）。`retryable=false` 的错误绝不该被重试。

2. **重试放在插件代码里。** 指数退避加抖动，上限 2~3 次，Agent 看到的已是重试后的最终结果。只有幂等操作才允许自动重试；下单、支付类写操作必须带幂等键，否则宁可失败也不盲重。

3. **加熔断。** 同一工具连续失败 N 次后短路一段时间，直接告诉 Agent“服务当前不可用，停止调用”。没有熔断，模型会持续敲一扇坏掉的门，把限流越推越紧。

4. **降级要显式。** 缓存数据、备用 provider、只读模式都可以，但结果里必须带 `degraded: true`，让模型在回复用户时说明数据可能不是最新的。

5. **判断留给模型，但给足信息。** prompt 里写明：`retryable=false` 时不要重试，如实报告错误类型；不确定就问用户，不要编造。长任务在每个工具调用前做 checkpoint，挂了从断点恢复，而不是整个重来。

## 踩坑点

- **双层重试叠加成重试风暴**：SDK 自带 retry，Agent 循环里又 retry，流量放大好几倍。只留一层。
- **超时设太短**：慢但成功的调用被判失败后重试，幂等没做好就是重复副作用。
- **熔断没有半开恢复**：冷却期后要放一个探测请求进去，否则服务恢复了，工具还是“死”的。
- **降级不告知**：静默返回三天前的缓存，用户发现后的信任成本远高于一句“服务暂不可用”。
- **错误原文直接进上下文**：堆栈和 HTML 只会诱发幻觉，先截断、结构化再给模型。

## 可复用的建议

- 所有工具返回值统一信封格式：`ok / error_type / retryable / degraded` 四个字段是底线。
- 每个任务设预算：最大重试次数、墙钟时间、token 消耗，超了就停，宁可失败得干净。
- 工具层失败日志和 Agent 推理日志分开记，复盘时才分得清是服务挂了还是决策错了。
- 预发环境故意拔依赖做混沌测试：kill 掉某个 provider，看 Agent 是如实报告还是开始编数据。这一步比任何 prompt 调优都更能暴露问题。

## 总结

错误恢复不是 prompt 技巧，是架构问题。核心一句话：确定性的交给代码——分类、退避、熔断、幂等；判断性的交给模型——降级取舍、用户沟通；两者的接口就是那层结构化的错误信封。外部 API 一定会挂，挂的时候你的 Agent 表现成什么样，取决于它还活着的时候你做了哪些设计。
