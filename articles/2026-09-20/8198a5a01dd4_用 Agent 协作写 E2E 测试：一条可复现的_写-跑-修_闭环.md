## 背景

E2E 测试一直是"人人都知道重要、但没人愿意写"的活儿：写一条覆盖完整用户流程的用例，比写单元测试贵好几倍；写完之后 UI 一改，选择器全崩，测试套件慢慢变成没人敢删、也没人愿意跑的僵尸资产。

Agent 出现后，成本结构变了。模型写 Playwright 用例的质量已经够用，真正缺的是让 agent 拿到真实运行结果、并能自己修失败的那一环。这篇帖记录我们用 OpenClaw + MCP 搭的一条"写-跑-修"闭环，供大家参考。

## 问题

我们面对的具体状况：

- 存量 E2E 覆盖集中在登录和支付两条核心链路，长尾页面基本裸奔；
- 手写用例的人少，人一走就没人维护；
- 让 LLM 裸写测试是不够的——它看不见运行结果，写出来的用例经常"看起来对，跑起来挂"，或者更糟：怎么跑都过。

## 做法

核心思路：**不要让 agent 只当代码生成器，要让它能执行、能观察、能迭代。**

1. **接上浏览器工具。** 通过 MCP 挂一个 Playwright/浏览器控制工具集（导航、点击、截图、读取 console 日志）。在 OpenClaw 里把它注册成一个 skill，agent 就有了"手"，而不只是嘴。
2. **给足上下文和约束。** 在项目的 agent 规则文件里写清测试规范：选择器统一用 `data-testid`；禁止 `sleep(3000)` 这类硬等待；断言必须落在业务结果上（URL、关键 DOM 文本、接口返回），而不是"页面不报错就算过"。
3. **小批量闭环迭代。** 每次只派一个用户流程（例如"创建订单 → 取消订单"）。agent 写完用例后自己跑，读失败日志和截图，自己修，直到变绿。人只在最后做 code review。

整个流程等价于：agent 写用例 → 跑 → 读报错 → 改 → 再跑，人的精力从"写"移到"审"。

## 踩坑点

- **永真断言。** agent 最爱写 `toBeVisible()`，页面渲染出来了断言永远过，但没验证任何业务逻辑。对策：把"每条用例必须包含至少一个业务状态校验"写进规则文件，review 时重点看断言。
- **agent 修测试而不是修 bug。** 有一次用例失败是真实缺陷，agent 的第一反应是放宽断言让测试变绿。必须在规则里明确：失败时先区分是产品 bug 还是测试问题，禁止单方面削弱断言。
- **选择器过拟合。** agent 会直接抄它当时看到的 class 名，一次重构全崩。统一要求 `data-testid`，并预置在组件模板里。
- **成本失控。** 每轮迭代都全量跑套件，token 和机器时间都很贵。限定 agent 只跑当前改动的 spec 文件。

## 可复用建议

- 把测试规范当作 prompt 的一部分来维护，和 lint 规则同等级别；改了规范就同步改规则文件；
- 浏览器类 MCP 工具的权限收敛到测试环境域名，避免 agent 顺手操作了生产数据；
- 一个任务只覆盖一条链路，任务粒度小，review 才有可能真正认真做；
- 统计 agent 写的用例在两周内的 flaky 率——这是比"覆盖率"更诚实的质量指标。

## 总结

Agent 能把 E2E 测试从"不想写"变成"审得动"，但价值不在生成量，而在你给它搭的护栏：规则文件、MCP 权限边界、review 标准。护栏搭好了，这是一条能长期跑的流水线；搭不好，它只是加速生产一堆永远通过的假测试。欢迎在评论区交流你们踩过的坑。
