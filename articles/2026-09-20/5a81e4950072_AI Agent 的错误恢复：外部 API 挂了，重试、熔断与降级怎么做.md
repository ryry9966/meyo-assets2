## 背景

跑过一段时间 Agent 自动化的同学大概率遇到过：工作流白天还好好的，半夜悄悄挂了。排查发现往往不是模型的问题，而是某个外部依赖——搜索、天气、支付网关，甚至模型供应商本身——超时或限流。传统后端服务里这叫“依赖故障”，有成熟预案；但 Agent 场景多了一层 LLM，错误处理的方式和后果都不太一样。

## 问题在哪

1. **错误文本会进入上下文。** 工具调用失败后，如果直接把原始报错（堆栈、HTML 错误页、大段 JSON）塞回模型，轻则污染上下文，重则模型开始自作主张——编造一个看似合理的返回值，或陷入无意义的循环。
2. **LLM 不会自己遵守重试纪律。** 让模型决定“要不要再试一次”，它经常在同一个死接口上反复撞墙，烧 token 也烧时间。
3. **非幂等操作被盲目重试。** 查询接口重试无所谓，但下单、发消息、扣款这类写操作被重试，就是生产事故。

## 做法

我的做法是把所有外部调用收口到一个统一的工具适配层，错误处理在代码里做，不让 LLM 参与决策：

**第一步：错误分类。** 超时、连接失败、429、5xx 归为 `RETRYABLE`；401/403、参数错误、业务拒绝归为 `FATAL`；能降级的场景（如搜索挂了但有缓存）归为 `DEGRADE`。

**第二步：重试只对 RETRYABLE 生效。** 指数退避加抖动，上限 3 次，单次调用 15 秒超时，整条链路设总预算（比如 60 秒）。超预算直接进降级分支。

**第三步：熔断。** 同一工具短时间内连续失败 N 次，标记为不健康，后续调用快速失败，不再发真实请求。恢复用半开探测，而不是等用户来撞。

**第四步：降级要有优先级。** 备用服务商 > 本地缓存（注明数据时间）> 明确告知用户“该能力暂时不可用”。最忌讳静默失败。

**第五步：给模型的错误信息要“翻译”过。** 一两句话，说清发生了什么、建议下一步做什么。例如：“搜索服务暂不可用（已重试 3 次），请告知用户稍后再试，不要编造结果。”这比甩一段堆栈给模型效果好得多。

伪代码大致是：

```python
result = with_retry(call, max_attempts=3, backoff=exp_jitter)
if result.ok:
    return result.data
if result.kind == "RETRYABLE_EXHAUSTED":
    return fallback_or_cache()
return to_model({
    "error": "service_unavailable",
    "hint": "inform user, do not fabricate",
})
```

## 踩坑点

- **只加超时、不加总量预算。** 三次重试各 30 秒，一条链路卡 90 秒，并发一上来就雪崩。
- **重试 POST 不带幂等键。** 下游收到两笔订单。写操作要么下游支持幂等键，要么本地先记请求指纹。
- **熔断状态存在单个会话里。** 每个新会话都重新撞一遍死接口。熔断状态应跨会话共享，放进程级或 Redis。
- **缓存降级不标注时效。** Agent 拿三小时前的天气数据回答“现在”，比不回答更糟。降级数据要带时间戳，并让模型如实转述。
- **日志只记“调用失败”。** 事后没法复盘。至少记下错误分类、重试次数、最终走了哪条降级路径。

## 可复用建议

- 错误分类枚举（`RETRYABLE` / `FATAL` / `DEGRADE`）作为团队约定，所有插件统一实现，别各写各的。
- “降级但诚实”优先于“成功但造假”。宁可告诉用户拿不到数据，也不要让模型补一个。
- 把退避、熔断做成工具层公共组件，Agent 编排层只关心“拿到结果还是拿到降级说明”。
- 定期做故障演练：手动停掉某个 MCP 服务，验证整条链路行为是否符合预期。

## 总结

外部 API 挂掉不可怕，可怕的是 Agent 把失败变成幻觉或死循环。核心原则三条：**重试决策收口在代码层，不交给模型；失败要分类，降级要有交代；非幂等操作先想清重试的代价。** 这套东西不炫技，但决定了你的自动化能不能在半夜无人值守时依然活着。
