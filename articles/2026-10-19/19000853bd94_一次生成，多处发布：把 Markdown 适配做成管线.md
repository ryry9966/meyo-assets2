## 背景

我们的内容流程大致是：Agent 生成初稿 → 人工修订 → 粘贴到公众号、知乎、掘金、博客。平台一超过两个，格式工作就开始吃时间：公众号不吃标准 Markdown，知乎的代码块要手动调，掘金吃 GFM 但图片得传自家 CDN。后来我们把这一段做成了管线：Agent 只负责产出一篇"受约束的 Markdown"，格式适配和发布全部交给下游。

## 问题

核心矛盾是：Markdown 不是一种格式，是一堆方言的集合。表格、脚注、任务列表、数学公式、代码高亮、图片引用，每家支持程度都不一样。把同一份 md 原样粘到五个平台，等于做了五次人工 QA，而且每次改稿都要重来。

## 做法

原则三句话：**单一事实源、AST 中转、平台适配器**。

**1. 收窄输入。** 定义一个内部 Profile：GFM + 脚注，禁用内联 HTML，数学公式统一 `$...$`，图片一律相对路径。Agent 的 prompt 里明确要求按 Profile 输出，解析时用 remark-lint 校验，不合规直接打回重写。

**2. 解析成 AST。** 用 unified/remark 把 md 解析成 mdast，后续所有变换都在 AST 上做，不做字符串替换——这是整条管线里最值的决定。

**3. 按目标做变换插件。** 每个变换是一个小 remark 插件：

```js
unified()
  .use(remarkParse)
  .use(lintProfile)          // 校验内部 Profile
  .use(images, { target })   // 图片上传 + URL 回填
  .use(codeHighlight, { target })
  .use(mathDelims, { target })
  .use(target === 'wechat' ? remarkHtmlInline : remarkStringify)
```

图片：读本地文件传 OSS 或目标平台，回填 URL；代码块：公众号场景预渲染成带内联样式的 HTML，原生 md 平台只做语言名归一（`js`→`javascript`）；数学公式：按平台换定界符；front matter：需要的转换，不需要的剥离。

**4. 渲染与发布。** 原生 md 平台序列化回 md，公众号走 HTML + 内联样式。发布动作封装成 MCP tool，Agent 或 CI 里一条命令触发，每个平台一个适配器注册进来。

## 踩坑点

- **公众号会剥掉几乎所有属性和外链 CSS**，样式必须内联，代码高亮必须预渲染，别指望后处理。
- **图片外链会被防盗链拦截**，必须传目标平台或自己的 OSS；重传后的 alt 和顺序要靠 manifest 对回来。
- **数学定界符**：有些平台把 `$` 当普通字符吃掉，转义要在 AST 层做，字符串层补不干净。
- **平台回吐的 md 和你输入的不一样**（公众号尤其明显），千万别把平台内容当事实源，否则每次改稿全部漂移。
- **锚点和 TOC**：各家 heading id 算法不同，长文目录链接基本要按平台重建。
- 中文排版细节（中西文间空格、全角标点）放 lint 阶段统一处理，不要指望平台帮你排。

## 可复用建议

- Profile 越严越好：宁可写作时受限，也别在适配层无限打补丁。
- 适配器保持薄：只做"变换 + 上传 + 调 API"，业务逻辑一个不放。
- 建一份 manifest（content hash → 各平台稿件 ID、图片映射），实现"没变就不重发"。
- 自动化前先拿草稿箱当金丝雀跑一周，确认每个平台的边缘 case 再放开。
- 平台数量按需长，先做两三个真实在用的，别一上来铺五六个。

## 总结

这套管线没有黑科技，核心就一句话：**把 Markdown 当 AST 处理，输入端收窄方言，输出端按平台展开**。Agent 负责内容质量，管线负责格式确定性，职责分开之后，新增一个发布平台就只是新增一个插件的事。
