## 背景

在 OpenClaw 的自动化实践里，重试几乎无法避免：cron 定时任务在 gateway 重启后补触发、webhook 因超时被上游重发、Agent 规划失败后重新调用同一个工具、插件脚本被手动 rerun。这些路径都会让同一段逻辑被执行不止一次。

## 问题

如果任务不是幂等的，重复执行就是事故：日报往群里发两条、同一张工单建两个、文件被追加两遍、下游 API 收到双份请求。很多人的第一反应是"保证只执行一次"，但在有网络和进程崩溃的环境里，你只能保证"至少一次"投递。真正的解法不是消灭重复，而是让重复无害——这就是幂等性。

## 做法

以"每天定时给群发一份摘要"为例，落地分四步：

1. **定义稳定的任务键**。键必须由任务语义推导，不能执行时随机生成。比如 `digest:2025-06-01:dev群`，由日期+来源+目标拼出，跑一百次也是同一个键。
2. **用唯一约束做第一道闸**。执行前先抢占一个声明记录（SQLite 就够），插入失败说明已有实例在处理：

```sql
INSERT OR IGNORE INTO task_claim(task_key) VALUES (?);
-- changes() 为 0：已被持有，跳过本次触发
```

3. **让副作用本身可收敛**。优先 upsert 而不是 insert，"确保存在"而不是"新建一个"；下游 API 支持幂等键就把任务键透传过去。
4. **定时任务用水位**。记录上次成功处理到的位置，每次只处理之后的数据，而不是假设"这次跑的恰好就是这一次"。

## 踩坑点

- **检查和执行之间不是原子的**。两个并发实例可能同时通过 SELECT 检查。真正的守门是唯一约束或锁，前置查询只是优化。
- **用 UUID 做幂等键**。每次运行都生成新的，等于没做。键必须能从"任务是什么"推导出来。
- **声明与执行之间有崩溃窗口**。先声明后执行，崩了会漏发；先执行后声明，崩了会重发。唯一约束挡得住并发，挡不住进程死亡，所以第 3 步的副作用收敛才是最终兜底。
- **想当然认为下游幂等**。有些接口重复调用就是建两条记录，上线前手动跑两遍验证。
- **追加写不幂等**。生成报告文件用"临时文件 + 原子 rename"，覆盖写天然幂等，append 不是。

## 可复用建议

- 把 `run_once(key, fn)` 做成插件里的通用小工具，所有自动化入口（cron、webhook、Agent 工具）统一走它。
- 设计工具时把"可能被 Agent 重试"当成默认假设，参数里预留稳定的请求标识。
- 验收标准很朴素：同一任务手动连跑两遍，结果和跑一遍完全一致；执行中途 kill 进程再跑，不产生重复副作用。
- 声明状态和业务产物尽量放同一存储，减少"做了一半"的中间态。

## 总结

在 Agent 自动化里，别把"只执行一次"当目标，把"执行多次结果一致"当目标。先设计任务键，再用唯一约束守门，最后让副作用收敛。幂等性不是额外开销，它是你敢给自动化加重试、敢在半夜放心重启的前提。
