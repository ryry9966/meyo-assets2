# 背景：人格散落各处

跑过长期在线 OpenClaw 实例的人大概都遇到过：同一个 agent，凌晨在终端里帮你重构代码，白天在微信群里回话却换了一副腔调。人格散落在各渠道的 system prompt、插件描述和临时对话里，改一处忘三处。SOUL.md 的作用就是把这些收敛成一个文件——workspace 里常驻注入上下文的身份说明，相当于给 agent 的一份入职手册。

# 问题：人格漂移与边界缺失

实践中常见两类故障：

1. **人格漂移**。语气规则写在某个渠道配置里，换渠道就失效；或会话变长后，模型逐渐滑回默认的过度热情风格。
2. **边界缺失**。你说"帮我处理一下消息"，它可能真的替你回复了别人；你说"清理一下服务器"，它可能顺手执行了删除。能力给了，但没约定哪些事要先问。

# 做法：五段式 SOUL.md

在 workspace 根目录建 SOUL.md，建议控制在 60 行以内：

```markdown
## 身份
你是我的个人助理，运行在家庭服务器上。

## 语气
直接、简短、工程化。不确定时直说"我不确定"，不要编。

## 边界（默认先问）
- 对外发送消息、邮件：先给草稿，等确认
- 花费超过 50 元的操作：先问
- 删除超过 10 个文件：先列出清单

## 禁止
- 不主动添加联系人
- 不在群聊里代表我发表观点

## 升级
遇到规则没覆盖的情况，停下来问我，并说明判断依据。
```

写的时候注意三点：每条规则**可判定**（"保持友好"不行，"回复不超过三句"可以）；边界写成"先确认的动作清单"而不是一刀切的禁止；用 git 管理，行为不满意就改一版，commit message 记录触发场景。改完清空 session 再测，拿一个之前翻过车的任务做回归。

# 踩坑点

- **写太长**。三百行的 SOUL.md 会稀释权重，还挤压 MEMORY 和工具描述的空间。实测一页以内最稳。
- **当成安全边界**。SOUL.md 是行为偏好，不是权限控制，真正拦得住的只有工具权限、审批门和沙箱。两者要配对：SOUL.md 写"花钱先问"，gateway 里同时把支付类工具设为需人工审批。
- **规则互相矛盾**。SOUL.md 写"不发社交媒体"，插件列表却挂着自动发帖工具，模型会摇摆。改 SOUL.md 时顺手审计一遍插件清单。
- **写完不测**。不构造"恶意"场景（让它删库、替你答应别人），你不会知道边界是否真生效。

# 可复用建议

- 模板固定为**身份 / 语气 / 先问清单 / 禁止清单 / 升级策略**五段，换 agent 只改内容不改结构。
- 从会话记录里"反向立法"：每周翻一次日志，把 agent 做错的事写成规则，比凭空预想有效得多。
- 规则与测试用例一一对应，改规则必跑回归。
- 多人共用 agent 时，把"代表谁"写进身份段，避免它搞混对谁负责。

# 总结

SOUL.md 解决的不是模型能力问题，而是长期运行 agent 的一致性与可控性。把它当代码维护：短、可判定、有版本、有回归。人格靠一段话，边界靠一份清单，硬约束交给权限层——分层之后，agent 才算真正"可托管"。
