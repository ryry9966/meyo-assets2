## 背景

OpenClaw 的 provider 机制允许同一个 agent 同时挂多个模型：云端走 GPT，本地用 Ollama 或 vLLM 跑 Qwen/Llama。但大多数人的用法是配完就设一个默认模型，结果要么账单难看，要么本地模型在工具调用环节频繁翻车。路由的本质不是"哪个模型强"，而是**任务与模型的匹配**问题。

## 问题

自动化跑起来后，任务差异其实很大：

- 摘要、改写、简单分类：本地 7B~14B 完全够用
- 多步工具编排、长上下文 RAG、复杂结构化输出：GPT 稳定得多
- 深夜批处理：不在乎延迟，在乎成本
- 涉及私有数据：不希望出本机

全走一边的代价很直观：全 GPT，月成本可观；全本地，工具调用的 JSON 解析失败率明显上升，agent 常陷入重试死循环。

## 做法

**1. 先给任务打标。** 跑一周，把历史请求粗分四类：轻生成、结构化输出、多步推理、隐私敏感。

**2. 静态规则起步。** OpenClaw 的路由配置思路大致是：

```yaml
routing:
  rules:
    - match: { tools_required: true }      # 需要工具调用 → GPT
      model: gpt-4o
    - match: { context_tokens: ">8000" }   # 长上下文 → GPT
      model: gpt-4o
    - match: { tag: privacy }              # 隐私数据 → 本地
      model: local/qwen2.5-14b
    - default: local/qwen2.5-14b
  fallback: gpt-4o-mini
```

（字段为示意，以你所用版本的实际 schema 为准。）

**3. fallback 链必须有。** 本地超时或解析失败连续 N 次，自动升级到 GPT 并触发告警，而不是静默重试到天亮。

**4. 路由判断本身要便宜。** 规则优先；规则不够再上一个 3B 级小模型做分类器。千万别用强模型当 router——省下的钱又花回去了。

**5. 打点观测。** 记录每次路由决策、首 token 延迟、重试次数、人工修正率。没有日志的路由是玄学。

## 踩坑点

- **本地模型 function call 不严格**：缺字段、多余引号是常客。开 JSON mode / grammar 约束能缓解，但最省心的做法是让结构化输出强制走 GPT。
- **上下文截断**：8k 本地模型接长会话后，agent 会"悄悄丢记忆"，外在表现是重复提问。按 token 阈值路由，比按任务类型硬分更可靠。
- **静默降级**：fallback 生效后没人发现质量下滑。降级必须通知 + 计数。
- **参数不一致**：温度、max_tokens 两边不同，切模型像换人格，评测数据全部失真。
- **本地模型升级不记版本号**：回滚时行为对不上，排查半天才发现是模型换了。

## 可复用建议

1. 先规则后智能：静态规则能解决 80% 的场景，动态分类是优化项，不是起点。
2. 本地模型固定一两个、量化等级（Q4/Q5）固定下来，别追新。
3. 维护一个 30~50 条的评测集，每次改路由规则跑一遍再上线。
4. 升级条件写进配置：解析失败率超阈值或人工修正率超标，自动切 GPT，事后人工复盘。

## 总结

GPT 买的是稳定性和工具调用可靠性，本地模型买的是成本和隐私，两者不是替代关系而是分工关系。OpenClaw 的正确用法是让规则替你做这个权衡，用日志验证效果——而不是每次出问题就手动换默认模型。先把打点和 fallback 做扎实，路由策略才有迭代的地基。
