## 背景

Agent 的上下文窗口是稀缺资源。接了两三个 MCP server、装了几套插件之后，很多人会习惯性地把所有工具说明、操作规范都塞进 system prompt——短期确实好用，但技能一多就崩：token 常驻开销线性上涨，模型面对几十份“说明书”注意力被稀释，选错工具的概率肉眼可见地上升。

OpenClaw 的 Skills 机制针对的就是这个问题，思路是渐进式披露（progressive disclosure）：启动时只把每个技能的一行元数据——name 和 description——注入上下文，正文完全不加载；等任务真的命中某个技能，agent 再去读取对应 SKILL.md 的全文，按里面的步骤干活。

## 问题

算一笔账：20 个技能，平均每个正文 800 token，全量注入就是 1.6 万 token 的常驻成本，而且不管本轮对话用不用得上都得付。更麻烦的是维护——改一处规范要在巨型 prompt 里翻找，没有版本、没有归属。Skills 把“说明”从 prompt 里拆出来变成文件，才谈得上版本管理和按需加载。

## 做法

核心结构很简单：一个技能一个目录，入口是 SKILL.md。

```markdown
---
name: weekly-report
description: 当用户要求整理、生成或修改周报、周总结时使用
---
# 周报生成
1. 读取 ./template.md 作为格式基准；
2. 将用户要点归入「进展 / 风险 / 下周计划」三段；
3. 调用 ./render.sh 输出 Markdown 文件。
```

启动时只有 frontmatter 里的 name 和 description 进入上下文，正文不进。运行时模型拿任务与各技能的 description 匹配，命中后用读文件的方式取回正文执行。正文里还可以引用同目录的脚本和参考文档，形成三层结构：元数据常驻、SKILL.md 按需、引用资源用到才读。

写的时候有两条原则值得遵守：

1. description 写成“什么时候用我”，包含用户真实会说出的关键词，而不是罗列功能特性。
2. 确定性逻辑写成脚本放进技能目录，正文只告诉模型“何时调用、参数是什么”。让模型用自然语言复述一个算法，不如让它执行一个写好的脚本。

## 踩坑点

- description 太泛：什么任务都命中，等于变相常驻加载，还容易误触发。
- description 太窄：该触发时不触发。拿真实对话日志回放调措辞，比拍脑袋有效得多。
- 正文写成大而全的手册：按需加载也就不“轻”了，正文控制在一屏内，细节下沉到引用文件。
- frontmatter 格式错误（缩进、多余冒号）会让技能静默不加载，启动后去日志里确认实际加载了几个。
- 第三方技能先审正文再装：它本质是能指挥 agent 执行命令的提示词，别裸跑。

## 可复用建议

- 一个技能只做一件事，能用脚本就不用散文。
- 技能目录进 git，团队共享、走版本，改 description 也能回溯。
- 定期清理从不触发的技能——元数据索引本身也占上下文。
- 调优顺序：先看没触发的（改 description），再看误触发的（收窄关键词），最后才考虑拆分或合并技能。

## 总结

Skills 的价值不在“多了一个功能”，而在于把提示词工程从一次性堆料变成可维护的分层加载：常驻的只有索引，重的说明按需进上下文，确定性的事交给脚本。当技能数量涨到几十个时，这套机制基本决定了助手还能不能保持干净可控。建议从一个高频重复的任务开始写第一个技能，跑通“匹配 → 加载 → 执行”的闭环，再逐步迁移存量 prompt。
