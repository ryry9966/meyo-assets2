## 背景

单个 Agent 串行干活的痛点很典型：一个会话里又要调研又要改代码，上下文越滚越长，前一个任务的中间产物污染后面的判断；某一步跑偏，整条链路重来。OpenClaw 这类支持会话派生的运行时给了更务实的选项——主 Agent 把任务拆出去，交给若干 subagent 在各自独立会话里并行执行，自己只负责拆解、分发和汇总。

## 问题

上周遇到一个典型需求：给一个 20+ 模块的仓库做依赖梳理，逐模块确认升级方案并跑测试；同时还要对比 3 个候选 MCP server 的能力差异。串行做下来估时一整天，而且调研笔记会把主会话上下文撑爆。

## 做法

我的编排结构是「主 Agent 拆解 → subagent 并行 → 文件落盘 → 主 Agent 汇总」：

1. **拆解**：主 Agent 先产出任务清单，每个子任务写清输入（涉及哪些文件/链接）、输出（写到哪个文件）、边界（不许改代码，只产出报告）。拆分的关键是子任务之间没有共享写目标。
2. **派生**：通过 `sessions_spawn`（或你所用运行时的等价工具）派生 subagent。spawn prompt 必须自包含——subagent 看不到父会话上下文，别指望它"知道"你刚才说了什么。并发控制在 3~4。
3. **落盘**：约定每个 subagent 把完整结果写到 `results/<task-id>.md`，返回值只带一行摘要加文件路径。
4. **汇总**：主 Agent 等全部收尾后读文件聚合，只对失败的任务重新派生，不整体重跑。

调研类、只读类任务用这套并行收益最大；带写操作的任务见下面第 3 条。

## 踩坑点

1. **返回值太长**。最初让 subagent 直接把全文作为返回值，主 Agent 上下文几轮就爆了。改成"写文件 + 返回路径"后干净得多。
2. **共享写目标冲突**。两个 subagent 同时往一个分支提交，后者覆盖了前者。要么给每个 subagent 独立目录/独立分支（git worktree 很好用），要么把写操作全部收回主 Agent 串行执行。
3. **把有副作用的工具交给并行 subagent**。部署、发消息这类不可幂等的操作并行跑就是赌博。并行只留给只读/纯产出型任务。
4. **无并发上限**。一口气派 8 个，直接撞模型 API 限流，一半失败。加队列、设上限，重试间隔拉开。
5. **subagent 再派 subagent**。默认禁止递归派生，或把深度限制为 1，否则排障会变成套娃。
6. **单个任务挂死拖垮汇总**。给每个 subagent 设超时，超时即标记失败进入重试队列。

## 可复用建议

- 把 spawn prompt 模板化：目标 / 输入 / 输出格式 / 写入路径 / 禁止事项，五段固定，减少每次现编的随意性。
- 通信靠文件，不靠对话。文件是天然的结构化媒介，也方便事后审计。
- 并发数 = min(3~5, 你的 API 配额能承受的值)。
- 先拿两个 subagent 小规模验证，确认落盘路径、超时、重试都符合预期再放量。
- 给每个 subagent 的工具权限做减法：调研任务给搜索和读文件就够了。

## 总结

Subagent 编排的核心不是"开更多 AI"，而是把任务切到互相独立、可用文件交接的粒度。并行读、串行写、文件通信、限流兜底——这四条守住了，多 Agent 并行才真正省时间，而不是换一种方式加班。
