## 背景

单 agent 循环跑长任务，迟早会撞上三个瓶颈：上下文越滚越大、执行全程串行、原始材料和最终结论搅在同一个会话里。我们在 OpenClaw 里做自动化任务时把「调研—汇总」这类活拆成主 agent 调 subagent，最近把多 subagent 并行完整跑通了一轮，把过程和教训整理出来。

## 问题

目标很朴素：一个任务需要扫十几个数据源和文件，串行一轮十几分钟，而且主 agent 上下文塞满原始输出，最后总结质量反而下降。我们想提速，但不想让主 agent 上下文爆炸，也不想引入一堆难以排查的新故障。

## 做法

结构上就是「一个编排者 + N 个工人」，步骤如下：

1. **先判断可拆性**。任务能否拆成互相独立、结果可验证的子任务？不能拆的（比如强依赖上一步输出的重构）老实串行，别硬拆。
2. **定义边界**。每个 subagent 一个独立 session，只给输入清单和固定输出格式（我们用 `result / files_touched / errors / summary` 四个字段），不给全局上下文。
3. **并发上限**。同一时刻最多 3-4 个 subagent：一是 API 限流，二是出问题时人还看得过来。
4. **工作区隔离**。写文件类任务，每个 subagent 有独立子目录，由主 agent 统一合并，避免互相覆盖。
5. **聚合与校验**。主 agent 只读 `summary` 和 `errors`，发现异常再让对应 subagent 重跑或自己下场。原始材料一律不回流主上下文。

OpenClaw 侧实现很薄：一个 `spawn(subagent, task, timeout)` 工具函数加一个简单调度循环就够，重点全在约定和约束上。

## 踩坑点

- **subagent 再生 subagent**：不限深度会自我递归，token 一晚烧完。必须硬编码深度上限（我们限 1 层）。
- **结果回流爆炸**：早期让 subagent 返回完整产出，10 个并行直接把主 agent 上下文打爆。改成强制 summary 限长后才稳。
- **静默失败**：有 subagent 超时返回空结果，主 agent 把它当正常值聚合，结论错得很自信。失败必须是显式状态，不允许「空即正常」。
- **文件竞争**：两个 subagent 改同一个文件，后写的赢，全程无报错。工作区隔离是底线，不是优化项。

## 可复用建议

- 并行适合「读多写少」的任务：调研、扫描、批量转换；强写入强依赖的任务别硬拆。
- 输出格式在 spawn 时写死，字段宁少勿多，拒绝自由文本。
- 每次并行留一份 run log：谁、输入、耗时、状态。排查时这是唯一真相。
- 先串行跑通，再开并行。限流、竞争、成本这些问题在串行阶段就能暴露一半。

## 总结

subagent 并行不是「多开几个就快」，本质是工程问题：隔离、聚合、失败处理。我们的实测提速在 3-5 倍，前提是任务天然可拆、输出结构化、并发有上限。建议从 2-3 个 subagent、只读任务起步，把 run log 建好，再逐步放开。
