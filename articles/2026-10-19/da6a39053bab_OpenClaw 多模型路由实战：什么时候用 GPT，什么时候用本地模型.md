## 背景

OpenClaw 这类 agent 网关的真实负载是混合的：一轮任务里既有需要强推理的规划与工具编排，也有大量低价值密度的步骤——格式化、粗摘要、分类打标、对私有数据的预处理。这些步骤全走云端旗舰模型，账单和延迟都难看；全换本地模型，复杂任务的工具调用成功率又会明显下滑。多模型路由要解决的就是这个分配问题。

## 问题：不是“选一个模型”，而是“定一套分配规则”

在我的场景（个人自动化 + MCP 工具 + 定时任务）里，主要矛盾有三个：

1. **成本**：token 消耗的大头其实在“平庸步骤”上；
2. **隐私**：日志、笔记、聊天记录不该默认离开本地网络；
3. **可靠性**：本地模型挂了或上下文超限时，agent 不能静默失败。

## 做法

**第一步：给任务分类，而不是给会话分类。** 我把任务拆成四类：多轮工具调用的编排（走云）、长上下文代码理解（走云）、结构化抽取/分类/摘要（走本地）、含隐私的预处理（强制走本地）。粒度落到子任务——用 subagent 把“脏活”派给本地小模型，主 agent 保持旗舰模型。

**第二步：配置 provider 和显式回退链。** 云端配 GPT 系，本地用 Ollama/vLLM 起一个量化模型。关键是回退顺序要写死：本地失败后转云端重试，且重试上限设为 1 次，避免“本地超时六十秒 + 云端再跑一遍”的双重浪费。

**第三步：路由用确定性规则，别用 LLM 当路由器。** 按任务类型、上下文长度、是否命中隐私关键词做规则路由，快、可解释、可回归测试。LLM router 听起来聪明，实际是往链路里加了一个新的不确定源。

**第四步：记录每次请求的模型与结果。** 按模型字段聚合 token 用量和成功率，这是后续调整规则的唯一依据，不记录就等于盲调。

## 踩坑点

- 本地模型的 function calling 格式差异比想象中大：同一个 prompt，云端能解析的 JSON，本地经常套着 markdown 代码围栏输出。解法是提示词里强制“只输出 JSON”，外加一次清洗重试。
- 上下文窗口的数字会骗人：本地模型标称 128k，实际超过 32k 后工具调用质量明显劣化。我给本地路由加了硬上限，超限直接转云。
- 回退链要防循环：本地失败→云端兜底→结果又送回本地加工，等于什么都没省。
- 系统提示词别共用一套：本地小模型对冗长的系统提示很敏感，精简之后成功率提升明显。

## 可复用建议

- 分工默认值：规划、编排、长上下文走云；分类、抽取、摘要、隐私预处理走本地。
- 准备一个 20 条左右的自有测试集当“质量绊线”，每次改路由规则后跑一遍，防止静默劣化。
- 路由规则宁可粗不要细：三个维度以内。规则超过这个复杂度，说明该重构任务拆分了。
- 选本地模型先测工具调用，再测问答。工具调用不过关，其他指标都没有意义。

## 总结

多模型路由的价值不在“省了多少钱”，而在于让每个子任务落在合适的执行环境里：隐私数据不出门，简单步骤不吃旗舰算力，关键决策始终由最强模型兜底。先用规则、先做记录、先测工具调用——这三件事比任何“智能路由”方案都更早解决实际问题。具体字段名和配置细节以你所用版本的官方文档为准，思路是通用的。
