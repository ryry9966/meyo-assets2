最近开发者圈里流传一句话：“大家用 AI 都太保守了。”说话的是 Claude Code 负责人 Boris Cherny——他的团队做出了目前最流行的编程 Agent 之一。这话乍听像凡尔赛，实际上点破了一个普遍现象：大多数人手里的 AI 能力已经升级了好几代，用法却还停留在三年前。这篇拆三个问题：保守用法长什么样？为什么会保守？“更有野心”的用法，底气和边界又在哪里。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-19/e6bfea07f0f02bcc.png)

## 一、先自查：你可能正开着 F1 在菜市场排队

对照下面几条，多数人会中至少两条：

- **任务粒度以“分钟”计**：写个正则、改个小 bug、生成几条单测，从不敢派更大的活。
- **把 Agent 当高级搜索**：问“这个需求怎么实现”，然后自己抄答案，AI 只负责出草稿。
- **逐句盯梢**：AI 每输出三行就人工检查一次，节奏像结对编程，效率却是单人开发。
- **上下文反复清零**：每次对话都从头解释项目背景，像雇了一个每天失忆的新同事。

这些行为的共同本质：把一个能跑马拉松的 Agent，当成了自动补全插件。

## 二、保守不完全是你的错：不信任是有历史依据的

保守用法不是性格问题，而是三代技术范式叠加出来的惯性：

1. **历史包袱**。2022 年前后的模型幻觉率不低，上下文窗口普遍只有 4K~8K tokens，塞不下一个像样的代码库。在那个年代，“放手”约等于裸奔，保守是理性策略。
2. **心智模型滞后**。工具从“补全”进化到“对话”再进化到“Agent”，每代能力翻倍，但人的使用习惯更新是按年计的。很多人今天用的，仍是第一代模型教会他们的姿势。
3. **验证成本不对称**。审查一份自己不熟悉的 AI 生成代码，有时比自己写还累。既然验证贵，那就只派小活——但这恰恰是局部最优陷阱：任务越小，验证环节占比越高，总效率反而越低。

## 三、所谓“野心”，是从派步骤变成派项目

把 Cherny 在访谈和官方最佳实践里反复出现的做法归纳一下，“野心式用法”大概长这样：

1. **派目标，不派步骤**。给一个完整的 feature，或者“把模块 A 从旧框架迁移到新框架”，让 Agent 自己读代码、查资料、写实现、跑测试，一跑几个小时。比如“给命令行工具加一个导出报表的功能”，传统做法是拆成十个 prompt 逐步喂，野心式做法是一句话加一份测试清单，然后去冲杯咖啡。
2. **先计划，后放手**。用 plan mode 这类机制：先让它通读代码库、输出技术方案，人确认方向没问题再执行，避免跑到一半发现路线错了。
3. **固化项目记忆**。把团队规范、目录结构、踩坑记录写进 CLAUDE.md 这类约定文件，Agent 每次开局自带上下文，不用每次重新交代“我们用什么测试框架”。
4. **并行开工作台**。用 git worktree 开多条分支，同时跑多个 Agent 干不同的活，人只做汇总和验收。他本人演示过同时开十几个会话。
5. **用机器验证代替人肉盯梢**。让测试、CI、类型检查当闸门，Agent 自己看报错自己修，人只处理真正跑不通的边界情况。

一句话总结角色变化：**人从司机，变成导航加质检员。**

## 四、底气与边界：为什么“放手”这两年才成立

野心式用法不是玄学，背后是三项技术条件的成熟：

- **长上下文**。窗口从早期 4K 涨到如今 200K 级 tokens，一个中型项目的关键代码能整个装进去，模型终于“看得见全图”，而不是盲人摸象。
- **Agentic Loop**。模型不再只输出文字，能执行命令、读写文件、观察报错、自我修正，形成“行动—观察—修正”的闭环。跑偏了能自己拉回来，这是“连跑几小时不翻车”的前提。
- **可验证任务的强化学习**。代码、数学这类任务自带判卷器——测试过没过是硬指标，RL 在这种反馈明确的领域进步最快，所以“放手”的红利最先在编程上兑现。

还有一笔经济账：一次几小时的长任务，token 成本大约几杯咖啡，对应的是工程师几天的工作量。**真正稀缺的不再是算力，而是人的验证时间**——所以才要把验证尽量自动化、前置化。

但边界也要说清楚：需求模糊、纯审美、没有客观判卷标准的任务，放手的风险依然很高。野心派的核心从来不是胆子大，而是**只在可验证的地方放大胆子**。

## 五、野心不等于裸奔：三条校准原则

想从保守派往野心派迁移，不必一步到位，可以像调参数一样渐进：

1. **用“爆炸半径”定放手尺度**。有版本控制、有测试、能一键回滚的领域（代码、文档、分析脚本），可以激进；动生产环境、涉及花钱的操作、直接对外发布的内容，一律保守。先问“搞砸了要赔多少”，再决定派多大的活。
2. **把“完成”写成可判定标准**。放手前先定义清楚什么叫做完：测试全绿、基准性能不回退、接口约定不变。标准可判定，Agent 才有纠错方向，你验收才有抓手，中间就不用逐行盯梢。
3. **像维护置信区间一样维护信任**。定期复盘：哪类任务连续几次全对，就把任务粒度放大一档；哪类反复返工，就退回来加约束。信任不是信仰，是持续更新的数据。

“用得太保守”这句话，与其当名人语录，不如当一面自检的镜子：你手里的 AI 能力，可能早就跑在了你的用法前面。
