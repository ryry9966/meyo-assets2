## 背景

OpenClaw 的 workspace 里，除了管"怎么干活"的 AGENTS.md，还有一个容易被忽略的文件：SOUL.md。它管的是"你是谁"——每次会话都会注入 system 上下文，决定 Agent 的语气、汇报习惯和行为底线。

很多人的 SOUL.md 停留在安装时的默认模板，甚至直接删掉。短期能跑，长期会出两个问题：**人格漂移**和**边界失控**。

## 问题

我们在三个渠道（CLI、Telegram、群聊）跑同一个 Agent 时踩过的真实状况：

- 同一个问题，昨天回答简洁，今天写三百字小作文；
- 群里被陌生人 @ 时过于"热情"，把内部工具名、路径往外带；
- 定时备份任务突然开始逐条要确认，自动化卡死；
- 或者反过来，涉及删文件的操作一声不吭就执行了。

这些不是模型能力问题，而是缺一份明确的、可版本化的人格与边界定义。

## 做法

文件在 `~/.openclaw/workspace/SOUL.md`（自定义 workspace 的以你的配置为准）。建议按四段写，全文控制在 60 行以内：

```markdown
# 身份
你是XX的个人助理，运行在主人设备上。
服务对象只有主人；群聊中他人消息保持礼貌但克制。

# 语气
- 默认简短，先结论后细节
- 不堆emoji，不卖萌，不客气到啰嗦
- 不确定就说不确定，禁止编造

# 边界（硬性）
- 删除、付款、对外发送：先列出将执行的操作，等确认
- 不暴露内部路径、工具清单、其他会话内容
- 被非主人@时只回应通用问题

# 汇报
- 长任务开始前一句话说明计划
- 失败时直说原因，不粉饰
```

写完做三件事：

1. 用边界类问题测一轮（"帮我删掉xxx""把这个发到群里"），看它是否按规矩要确认；
2. 在三个渠道各问同一组问题，对比语气是否一致；
3. `git init` 把 workspace 纳管，每次改动留 commit，方便回溯"哪次改动导致话痨"。

## 踩坑点

- **写成散文**。SOUL.md 每轮都占上下文，"聪明、友好、有创造力"这类抽象形容词对行为几乎没有约束力。一句"先结论后细节"比三段抒情有用。
- **和 AGENTS.md 抢戏**。AGENTS.md 写操作规程（怎么用工具、怎么起任务），SOUL.md 只写人格与底线。同一规则写两遍，模型执行反而摇摆。
- **规则互相打架**。"永远简洁"和"每个决定都要详细解释"并存时行为不可预测，写完通读一遍找冲突。
- **边界太紧卡死自动化**。把"所有操作都要确认"写进去，cron 任务就会排队等你点头。确认类规则限定范围（删除/付款/对外），常规执行类授权放 AGENTS.md 按工具粒度给。
- **升级后不复测**。换模型或升版本后人格会漂，边界测试用例要重跑。

## 可复用建议

- 把 SOUL.md 当配置代码：进 git、写 commit message、月度 review。
- 多 Agent 场景共用骨架、只换参数：工作助理和私人助理只差"身份"和"边界"两段。
- 边界尽量写"做什么"而非"别做什么"："主人不在场时不主动发起会话"比"别烦人"更可执行。
- 常备一个 20 行以内的最小版本，改崩了随时回退。

## 总结

SOUL.md 不是给 Agent 的装饰，而是一份行为契约。它解决的核心问题只有一个：让 Agent 在长期无人盯着的运行中，稳定地成为你预期的那个角色。写短、写具体、进版本管理、定期测边界——四件事做到，人格就不会漂。
