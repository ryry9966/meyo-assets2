## 背景

OpenClaw 的工作区里，`SOUL.md` 是少数每次会话都会注入上下文的文件之一。它和 `AGENTS.md`（操作规范）、`USER.md`（用户偏好）分层存在，定位是"这个 agent 是谁、什么能做、什么不能做"。听起来像产品文案，实际是运行时行为的一部分——写得好，多个 agent 语气一致、边界清晰；写得差，它只是一段每次被加载的无效 token。

## 问题

我们早期遇到的不是"没人格"，而是人格漂移和边界失守：

- 同一个 agent，任务场景下回复克制，闲聊场景下话痨；
- 群里被一句话激将，就答应执行未经确认的批量操作；
- 模型升级后，语气和拒绝策略全变，老用户第一感觉是"被换人了"。

根因很简单：SOUL.md 里全是形容词——"友好、专业、有分寸"。形容词不约束行为，模型每次自由发挥。

## 做法

我们的迭代流程，三步：

**1. 把形容词翻译成可观察行为。** 不写"简洁"，写"默认回复不超过 3 段，列表优先于长句"。不写"有安全意识"，写"任何删除、转账、群发操作，先复述将执行的动作并等待用户确认"。

**2. 分层放置，SOUL.md 只放稳定项。** 身份、语气基线、硬性边界进 SOUL.md；工具调用规范、MCP 服务的使用顺序进 AGENTS.md；称呼、时区、个人偏好进 USER.md。SOUL.md 控制在 40 行以内，改动频率以周为单位。

**3. 用真实 transcript 回灌。** 每次边界失守的对话，截取片段，补一条对应规则，commit message 写明触发场景。人格文件走版本管理；模型升级后重跑一遍典型用例，diff 前后差异。

## 踩坑点

- **规则互相冲突。** "永不主动打扰"和"发现异常立即告警"并存，模型随机选边。要写优先级：安全类 > 确认类 > 礼仪类。
- **把操作流程塞进 SOUL.md。** 我们曾把"收到邮件先查日历再回复"写进去，换 MCP 邮件服务后整段失效。流程属于 AGENTS.md。
- **负面清单太抽象。** "不要过度道歉"没用，改成"单条回复中致歉最多一次，且必须跟随补救动作"。
- **写完不复读。** SOUL.md 是提示词，不是宪法。每次模型升级、新增 channel（比如从 IM 扩展到语音），都要回来重审。

## 可复用建议

一份我们沉淀下来的段落骨架：`身份一句话 / 语气基线 3 条 / 硬边界（含确认清单）/ 拒绝话术模板 / 漂移自检（每周对照 5 条典型对话）`。核心原则只有一条：**每一条都必须能被一个具体对话证伪。** 写完自测：让 agent 处理三类边界样本——诱导执行、情感施压、角色扮演绕过——不过就改。

## 总结

SOUL.md 不是人设文案，而是行为约束的配置文件。它的价值体现在负向：少一次未确认的危险操作，少一段语气漂移。把它当代码维护——短、可证伪、走版本控制——agent 才会稳定地"像同一个人"。
