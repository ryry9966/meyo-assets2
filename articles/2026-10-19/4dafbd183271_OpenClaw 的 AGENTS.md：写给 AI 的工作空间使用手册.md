## 背景

AGENTS.md 是近几年 agent 生态里逐渐形成的约定：在仓库或工作区根目录放一份纯 Markdown 文件，agent（比如 OpenClaw）在会话开始时自动读取，作为它在这个工作区里“怎么干活”的说明书。它和 README 的分工很明确——README 写给人看，AGENTS.md 写给 AI 看。

OpenClaw 的工作区往往不止是代码：脚本、MCP 配置、插件目录、自动化任务混在一起。这类“混合工作区”恰恰最需要一份给 agent 的使用手册。

## 问题

没有 AGENTS.md 时，我们实际踩过的坑：

1. **agent 每次重新摸索**：跑测试用哪条命令、哪个目录不能动、lint 规则是什么，全靠它现场猜，猜错就返工。
2. **规则散落各处**：一部分在 system prompt，一部分在个人备忘和聊天记录里，换个会话就丢。
3. **协作行为不一致**：同事 A 的 agent 提交前会先跑格式化，同事 B 的不会，review 时互相扯皮。

本质问题是：工作区的隐性知识没有被显性化、版本化。

## 做法

我们的 AGENTS.md 控制在 60 行左右，固定五段：

1. **项目地图**：三五行描述目录结构，标明哪些是生成物、哪些是手写代码，比逐文件注释有效得多。
2. **命令清单**：构建、测试、lint 的确切命令，可直接复制执行。agent 对确切命令的服从度远高于描述性语言。
3. **硬性约束**：用祈使句写“不要做”清单——不要动 `legacy/`、不要升级依赖大版本、不要直接提交主分支。
4. **验证方式**：告诉 agent 怎么自证改对了。这是最常被忽略、收益最大的一段。
5. **MCP/插件说明**：本工作区哪些 MCP 工具可用，调用时有什么注意事项。

另外两点工程习惯：**分层放置**——根目录放全局约定，子目录放局部规则（如 `plugins/` 下单独一份），agent 就近覆盖；**当代码管理**——进 git、走 review，构建流程变了同步改它。

## 踩坑点

- **写太长等于没写**。超过一两百行，遵循率明显下降，还挤占上下文。我们砍掉过一半“以防万一”的内容，效果反而更好。
- **多个规则文件互相打架**。曾同时维护 CLAUDE.md、`.cursorrules` 和 AGENTS.md，内容漂移后 agent 行为变得不可预测。后来收敛到单一来源，其他文件只留一行指向。
- **模糊指令无效**。“写出高质量代码”约等于没写，要写成“提交前必须通过 `npm test` 且零 warning"。
- **过期内容比没有更糟**。重构后目录变了但 AGENTS.md 没更新，agent 会一本正经地按旧地图走错路。建议把“改结构必须同步改 AGENTS.md”写进 PR 模板。

## 可复用建议

- 上限 80 行，超了就删，拿不准的内容宁可删。
- 每条指令可执行、可验证：带命令、带路径、带判断标准。
- 做一次"冷启动测试”：新开会话让 agent 完成一个典型任务，观察哪里违背预期，再反推补规则。
- 把它纳入团队 onboarding 清单：新人第一天读一遍，既熟悉项目，也顺手发现文档里的过期描述。

## 总结

AGENTS.md 的价值不在文件本身，而在于把工作区的隐性约定变成可版本化、可 review、可迭代的显性资产。写它的过程也是团队对齐工程规范的过程。维护成本很低，每周可能只有几分钟，但省下的是 agent 每次会话的试错成本。如果你的 OpenClaw 工作区还没有这份文件，建议从“命令清单”和“不要做”清单两段写起，半小时就能看到明显差别。
