## 背景

做 Agent 和自动化的人迟早撞上两个现实：一是模型在任务里被调用几十上百次——工具循环、自检、总结，token 消耗远超普通聊天场景；二是流水线里常带本地文件、日志和聊天记录，走云端 API 总有点不放心。本地部署的意义不是替代云端，而是把高频、低难度、涉隐私的环节收回自己机器上。

## 问题

家用硬件跑模型，矛盾集中在三点：

1. **装不下**：权重之外，长上下文的 KV cache 同样吃显存，很多人只算了前者。
2. **跑不快**：Agent 是串行循环，每步慢 10 秒，一个 20 步的任务就是 3 分钟起步。
3. **调不准**：不是所有小模型都能稳定输出可解析的 tool call，这是本地模型接 Agent 最容易翻车的地方。

## 做法

我的落地路径，五步：

**1. 摸硬件底数。** 关键指标不是"能否加载"，而是 decode 速度。经验法则：显存/统一内存 ≥ 模型体积 × 1.3（给 KV cache 留余量）。8GB 显存跑 7-8B 的 Q4 量化，16GB 碰 14B，24GB 试 32B。Apple Silicon 靠统一内存大带宽，是家用场景的甜点。

**2. 选推理栈。** 不必纠结：Ollama 上手最快，自带 OpenAI 兼容接口；要精细控制采样和模板再上 llama.cpp；有 24GB+ 显卡且追求并发吞吐才考虑 vLLM。家用单机默认 Ollama。

**3. 选模型和量化。** Q4_K_M 是速度与质量的平衡点。选型时优先验证 tool calling 是否被官方模板支持，Qwen 系列在这个尺寸段表现稳定。

**4. 接进 Agent。** 把 OpenClaw 侧的 base_url 指向本机端点（如 `http://localhost:11434/v1`），context 长度按真实负载设，不要拉满。

**5. 用真实任务压测。** 跑通你自己的自动化链路，记录每轮耗时和失败率，比任何跑分都诚实。

## 踩坑点

- **context 拉满直接 OOM**：32k 上下文的 KV cache 能吃掉数 GB，模型可能被挤掉。8k-16k 起步。
- **chat template 不匹配**：tool call 解析失败八成是模板问题，换模型时先确认推理栈的模板是否跟随更新。
- **历史越滚越大**：Agent 每轮重发全部上下文，prompt processing 时间线性上涨，定期压缩或截断，收益立竿见影。
- **小模型多步幻觉**：循环超过三四步，参数编造率明显上升。本地模型适合浅层循环，复杂规划留给云端。
- **swap 雪崩**：模型勉强塞进内存，一跑就卡死，速度掉一个数量级。宁可降一档模型。

## 可复用建议

1. **混合路由最务实**：本地做摘要、分类、格式化、简单抽取，规划和复杂推理走云端。本地模型配合本地 MCP 工具（文件系统、数据库），能形成数据完全不出网的闭环。
2. **维护配置清单**：模型 tag、量化等级、context、采样参数、模板，换机或回滚时省大量时间。
3. **压缩 system prompt**：Agent 每次调用都重复携带它，砍一半等于快一半。
4. **留日志做回归**：换模型后回放真实任务日志，判断升级是赚是亏。

## 总结

本地 LLM 不是玩具，也不是云端替代品，而是 Agent 架构里的成本与隐私控制点。从 8B Q4 + Ollama 起步，用真实任务验证 tool calling 和速度，再决定要不要加大投入——这条路径试错成本很低，值得每个做自动化的人都跑一遍。
