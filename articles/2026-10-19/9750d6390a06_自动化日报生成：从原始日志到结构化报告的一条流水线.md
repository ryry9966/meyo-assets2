## 背景

团队日报的数据源散在服务日志、CI 记录、git 提交、告警和 agent 运行记录里。过去靠值日生下班前人工汇总，格式不统一、经常漏、价值密度低。我把它改造成一条流水线：定时取原始日志，产出结构固定的报告，自动推送到群机器人。跑了三周基本稳定，这里记录做法和坑。

## 问题

原始日志是给调试用的，不是给人读的：噪音多、无结构、量大。最省事的“全量丢给模型总结”试过，不行——超上下文上限只能粗暴截断，信息随机丢失；模型会顺手补数字，错误率这类指标它编得有模有样；输出结构每次漂移，下游渲染经常崩。

所以原则定为：**确定性的部分用代码做，模型只负责把已结构化的事实组织成叙述。**

## 做法

分四步，每步是独立脚本或一个 MCP tool，中间产物全部落盘：

1. **采集**：定时任务拉取各源当天数据，统一转 JSONL 按日期分区，字段至少含 `ts / source / level / event / detail`。单源拉取失败不无限重试，记入死信文件，报告里标注“该源缺失”。
2. **归一**：最关键的一步。过滤 DEBUG 类噪音，按 event 去重聚合（“同一接口报错 400 次”压成一条），分类进固定桶：变更 / 异常 / 容量 / 待办。每桶设条数上限，异常按严重度排序取前 N。构建成功率、错误总数等数字全部由代码算好写成字段。
3. **摘要**：把归一后的 JSONL 和指标喂给模型，prompt 带 few-shot 和输出 JSON Schema，固定输出 `overview / changes / incidents / risks / todos` 五个字段。温度调低，模型不改数字、只写叙述。
4. **校验与投递**：jsonschema 校验，不通过就走兜底模板——宁可怕板地罗列事实，也不发一份漂亮但编造的报告；通过则渲染成 Markdown 推送 IM，并归档备查。

## 踩坑点

- **时区**：日志是 UTC，报告按本地日期切，凌晨边界事件会掉错窗口。时区转换统一放归一层，别放采集层。
- **格式漂移**：某服务改了日志格式，解析会静默失败。解析器要统计失败行数，超阈值（如 5%）就告警，不能吞掉。
- **静默失败最伤**：流水线挂了没人发现，直到有人问“今天日报呢”。加一条心跳，无论成败固定时间报一次运行状态。
- **prompt 别太自由**：早期让模型“自由补充观察”，它开始编趋势分析。现在只允许对已给事实做归纳。
- **条数上限不是可选项**：异常风暴那天 300 条异常直接撑爆上下文，截断得毫无章法。

## 可复用建议

- 分层解耦：换日志平台只动采集层，换模型只动摘要层，其余不动。
- Schema 一次定好，周报、月报只是时间窗口和聚合粒度的差别，后续加周报只改了二十行。
- 中间产物保留若干天，出了问题能复盘“模型当时到底看到了什么”。
- 先手写两周理想中的日报，把它固化成模板和 schema，再让流水线去填——比反过来省很多返工。

## 总结

这条流水线的本质，是把“读日志”这件重复劳动拆成两半：机械归纳交给代码，语言表达交给模型，中间用 schema 卡住质量。它不聪明，但可预期——对日报这种每天必须交付的东西，可预期比聪明重要。
