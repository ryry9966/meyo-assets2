## 背景

OpenClaw 的 Agent 具备文件读写和 shell 执行能力，这让自动化真正能落地，但也带来一个经典焦虑：模型一旦幻觉或路径拼接出错，`rm -rf` 指向不该指的地方怎么办？我们团队在用 OpenClaw 做批量日志清理时认真研究了它的 sandbox 安全模型，结论是：防误删靠的不是在 prompt 里写"请小心"，而是几层结构性防线。

## 问题拆解

误删通常来自三类路径：

1. 模型输出错误路径（幻觉、相对/绝对路径混用）；
2. 通配符与变量展开失控（`rm -rf $DIR/*` 在变量为空时变成灾难）；
3. 越权访问（`../../` 穿透工作区、symlink 指向宿主文件）。

## OpenClaw 的做法

按执行顺序大致有五层：

1. **工作区监狱**：所有文件工具的根被限制在声明过的 workspace 内。请求路径先做规范化（解析 `..`、symlink、Unicode 归一化），再判断是否落在 jail 内，默认 deny。
2. **权限分级**：文件工具拆成 read / write / delete 能力位，在 Agent 配置里显式声明。没有 delete 能力时，删除类调用在工具层直接被拒，根本不进入模型决策链。
3. **命令执行隔离**：shell 命令默认跑在容器沙箱里，宿主文件系统不挂载进去，只挂载 workspace。即使模型生成了灾难性命令，爆炸半径也被限制在一次性容器中。
4. **破坏性操作确认门**：工具层维护危险命令特征库（递归删除、批量覆盖等），命中后返回结构化确认请求，需用户或策略引擎放行，Agent 无法自行跳过。
5. **快照与回滚**：写操作前对目标路径做轻量快照，误操作可一键还原。

关键设计点是：这些校验全部在工具层实现，而不依赖系统提示词。模型可以被骗、可以幻觉，但工具层的路径校验不会。

## 踩坑点

- **symlink 逃逸**：早期我们把 workspace 里一个目录软链到宿主目录做调试，结果 sandbox 对 symlink 解析后放行了写请求。OpenClaw 现在默认 resolve 后再校验，但自己扩展工具时记得同样处理。
- **子进程绕过**：Agent 通过 `bash -c` 调外部脚本时，脚本内部操作不在文件工具校验范围内，只能靠容器隔离兜底。所以容器内不要挂载敏感目录。
- **挂载即漏洞**：把宿主 home 挂进沙箱图省事，等于亲手拆掉第四层防线。调试用临时目录，用完即弃。
- **确认门疲劳**：特征库太宽会频繁弹确认，用户开始无脑点通过，机制形同虚设。特征库应收紧，漏报部分交给快照兜底。

## 可复用建议

- 白名单优先：workspace、可执行命令、网络出口全部显式列举，黑名单永远追不完。
- 校验下沉到工具层：任何 prompt 层的安全约定都当作"不存在的"来设计。
- 假设容器会被打穿：定期做一次演练，直接让 Agent 尝试删除 workspace 外的文件，逐层验证防线是否真的生效。
- 审计日志落盘：所有被拒绝的调用记录在案，误拦和真实攻击都从这里发现。

## 总结

OpenClaw 防误删的思路不是"让模型更聪明"，而是"让单点失误不致命"：路径校验、能力分级、容器隔离、确认门、快照回滚，五层单独看都不完美，叠起来才构成对幻觉和注入的真实防御。准备给 Agent 开文件权限的团队，建议按同样顺序搭防线，并永远保留最后一层回滚能力。
