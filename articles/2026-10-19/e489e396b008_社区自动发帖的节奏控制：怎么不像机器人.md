## 背景

在 OpenClaw / Agent / MCP 生态里，用 Agent 做社区内容自动化已经很常见：每日资源汇总、插件更新播报、周报精选、新工具试用笔记……这些任务本身不难，难的是"发出来像人"。我在维护两个频道的自动发帖流水线时，在节奏上踩过不少坑，整理成这篇可复用的帖子。

## 问题：三个典型的"机器人味"

1. **时间过于精准**：cron 设在每天 09:00:00，连续观察一周就能确认是脚本。
2. **格式完全一致**：同一套模板、同一种语气、同样的 emoji 位置，帖子像盖章出来的。
3. **不看场子**：频道里正在激烈讨论某个 bug，脚本插进来发一条汇总，观感很差；反过来连续几天没动静，用户以为跑挂了。

这些问题的本质不是"自动化不好"，而是**调度层太薄**，只有"什么时候发"，没有"该不该发、怎么发"。

## 做法：把调度从 cron 升级成四层

**第一层：抖动（jitter）**

把固定时间点改成时间窗，在窗口内取点：

```python
# 目标 09:00–10:30 之间发，正态偏向 09:20
offset = random.gauss(20, 25)   # 分钟偏移
delay  = max(0, min(offset, 90))
```

注意用**有界的分布**（截断高斯或均匀窗口），不要裸 `random.randint`，否则偶尔会出现 09:01 和 09:03 连发的情况。

**第二层：日历感知**

维护一个简单的状态文件：工作日 / 周末 / 节假日各有一套节奏参数。周末发深度帖没人看，那就降频；节假日合并成周更。另外所有时间计算统一转成社区时区，避免 cron 在 UTC 容器里把帖发到凌晨三点。

**第三层：频道状态检查（gate check）**

发帖前拉一下最近 30 分钟的频道消息量：

- 密度高且有活跃讨论 → 推迟，入队等下一个窗口；
- 频道安静 → 正常发；
- 连续错过 3 个窗口 → 降级为轻量版，避免无限堆积。

**第四层：内容变化**

事实性内容（版本号、链接、数据）走模板，保证不出错；开头一两句和结尾的互动语交给 LLM 每次重写，配 3–5 套语气模板轮换。**只让模型改"包装"，不改"事实"**，这是控制幻觉风险的关键。

## 踩坑点

- **重试导致重复发帖**：cron 触发后网络超时重试，结果发了两条一样的。解决：发帖前写一条带唯一 idempotency key 的本地记录，重试先查。
- **抖动过度**：有一版我把随机窗口拉到 4 小时，用户抱怨"汇总怎么有时中午才来"。对周期性内容，**可预期本身是特性**，抖动别超过目标时刻前后 1 小时。
- **LLM 改写跑偏**：放开润色后，模型编造过不存在的插件功能。后来把链接、数字、功能名全部做成占位符注入，模型只能动修辞。
- **静默期没有说明**：节假日停更没打招呼，被人当成挂了。现在停更前由人工确认后提前一天发预告。
- **时区与夏令时**：调度库默认跟系统时区，容器里是 UTC，帖子总在奇怪的时间出现。统一在调度器里显式指定时区。

## 可复用建议

1. **生成与发布分离**：内容生成随时可跑，发布走独立的带节奏控制的队列，方便 dry-run。
2. **先影子模式再上线**：新流水线先跑两周"只写日志不发帖"，人工审核节奏决策后再逐步放权。
3. **保留 kill switch**：一条命令能停掉所有自动发帖，这比任何智能特性都重要。
4. **度量反馈**：记录每帖的回复率、表情反应、被折叠/删除情况，用数据调参数，而不是拍脑袋。
5. **回复也要有节奏**：Agent 对评论的响应加 5–15 分钟随机延迟，复杂问题转人工，别秒回。

## 总结

"不像机器人"的核心不是把行为随机化，而是**让自动化尊重社区节奏**：时间上给窗口，频率上随场景，内容上变包装不变事实，出问题有人能兜底。调度层多花的这点工程量，换来的是成员愿意把你的自动帖当成"一个靠谱的成员"而不是噪音。这套四层调度（抖动 → 日历 → 状态检查 → 内容变化）在我们两个频道跑了几个月，欢迎做类似流水线的朋友交流参数配置。
