# Agent 记忆系统设计：怎么让 AI 助手真正记住你的偏好

## 背景

大模型本身是无状态的，会话一结束，上下文就清零。对于 OpenClaw 这类常驻在本地、长期陪伴用户的 Agent 来说，“记住我”不是锦上添花，而是它和网页聊天框拉开差距的核心能力。如果助手每次都要重复交代“回复简洁点、代码带注释、别用 emoji"，体验就是倒退的。

## 问题

很多人第一步就做错：把记忆实现成一句 system prompt——“请记住用户告诉你的所有信息”。跑两周通常会遇到三类问题：

1. **记忆膨胀**：什么都存，几轮下来上下文被塞满，token 成本上升，有效信息被稀释；
2. **记忆污染**：用户随口一句“今天累死了”被提取成偏好，之后每次回答都刻意关心你；
3. **记忆冲突**：三个月前存的“部署用 Docker”和上周说的“迁移到 K8s”并存，Agent 随机选一个。

## 做法

我们的方案分三层，核心思路是“小而常驻，大而按需”：

**第一层：核心画像（always-on）。** 一个结构化文件（YAML/JSON 都行），只存高置信度、长期稳定的偏好：语言、代码风格、回复长度、常用工具。每次会话启动时全量注入 system prompt，控制在几百 token 内。

**第二层：事件日志（append-only）。** 所有值得记的信息按时间追加到 SQLite 或 JSONL，字段包括 `timestamp / source / content / confidence / tags`。只写不改，这是记忆的账本，用于审计和回溯。

**第三层：语义检索（on-demand）。** 日志超过几百条后再上向量检索，按话题召回 top-k 历史临时注入。不要一上来就做 RAG，很多时候第一层就够用。

写入侧建议做成独立管线，而不是让主 Agent 顺手写：

1. 会话结束或每 N 轮触发一次提取任务；
2. 用独立 prompt 判断这是事实、偏好、决定还是闲聊，给出置信度；
3. 与已有画像合并：新信息覆盖旧的（带时间戳），矛盾的标记出来，下次向用户确认；
4. 写入前人工过目一遍，前期这一步非常值得。

## 踩坑点

- **提取即真相**：LLM 提取的结果不一定对，保留 confidence 字段，低置信度不进核心画像；
- **没有遗忘机制**：加时间衰减或 `last_used` 字段，半年没命中的降权归档；
- **把指令当偏好**：用户说“这次用中文回”是会话级指令，不是永久偏好，提取 prompt 里要区分；
- **上下文静默膨胀**：检索 top-k 控制在 3~5 条，注入前做相关度阈值过滤；
- **隐私**：本地部署也建议把密钥、地址等敏感信息显式排除在提取范围外，别靠模型自觉。

## 可复用建议

- 先用“一个 profile 文件 + 一个 append 日志”跑起来，观察一周再决定要不要向量库；
- 把记忆操作封装成 MCP tool（`memory_read / memory_write / memory_search`），Agent 通过工具调用存取，而不是靠 prompt 自觉，行为更可控；
- 写一个回放测试：拿历史会话脚本重跑记忆管线，对比提取结果，改 prompt 不至于盲改；
- 把记忆的查看、修改、导出做成一等公民功能，用户能看到自己被记住了什么，信任感完全不同。

## 总结

记忆系统的难点不在存储，而在“什么该记、什么该忘、冲突听谁的”这三个策略问题。从最小结构（画像 + 日志）起步，把提取做成独立管线，带上时间戳和置信度，就能覆盖 80% 的场景。剩下的坑基本都是缺遗忘机制和不做冲突处理导致的——这两件事，比上向量检索重要得多。
