## 背景

OpenClaw 接多后端模型是很自然的事：云端 API 能力强但按 token 计费，本地模型（Ollama / vLLM 跑 7B~14B）零边际成本但能力有上限。我的实例常驻跑定时任务、消息摘要和 MCP 工具编排，之前全走云端，账单和隐私顾虑都摆在台面上。这篇记录我把流量按任务类型拆分路由的过程。

## 问题

路由要解决的不是"哪个模型更强"，而是"哪类请求值得花云端的钱"。我的三个具体痛点：

1. 约八成请求是摘要、分类、格式化这类低复杂度任务，却占了大头 token 成本；
2. 真正需要推理和工具编排的请求占比低，但本地模型做这些失败率明显更高；
3. 部分原始数据（聊天记录、日志、客户信息）不想出本地。

## 做法

**第一步：先观测，别急着配规则。** 跑一周"全云端"基线，给每次调用打任务类型 tag，统计各桶的 token 消耗和失败率。没有这份数据，后面全是拍脑袋。

**第二步：按"任务特征 × 上下文长度"分桶。** 我的划分：

| 任务特征 | 路由目标 |
| --- | --- |
| 多步规划、工具编排、代码生成 | 云端 GPT |
| 摘要、分类、打标、格式转换 | 本地 14B |
| 含敏感原文的处理 | 本地跑原文，只回传结论 |
| 超过 32k 的长上下文 | 云端 |

**第三步：写路由规则。** 示意如下（字段名以所用版本文档为准）：

```yaml
routing:
  rules:
    - match: { task: [summarize, classify, format] }
      model: local:qwen-14b
    - match: { task: [plan, tool_orchestration] }
      model: cloud:gpt
    - match: { ctx_tokens: ">32768" }
      model: cloud:gpt
  fallback: local -> cloud
```

**第四步：降级链方向是本地失败落云端，而不是反过来。** 云端失败落本地，经常得到"看起来像回事但工具调用是错的"结果，比直接报错更难排查。

**第五步：持续观测。** 每条路由结果带 tag 落日志，每周看两个数：各桶成本、各桶失败率。失败率突增通常意味着该桶该挪模型了。

## 踩坑点

- **本地模型 tool call 格式漂移**：小模型输出的参数 JSON 会断、会幻觉出不存在的字段。本地 agent 最多挂 5~6 个 MCP 工具，再多选择错误率直线上升。
- **上下文截断伪装成"能力差"**：32k 窗口在长会话里被裁掉开头的工具定义后，模型开始答非所问。表现为模型笨，实际是上下文被切，排查了半天。
- **降级风暴重复计费**：本地超时→云端兜底→本地恢复，同一条消息被两个模型各处理一次。加去重：任务已有云端结果就丢弃迟到的本地结果。
- **冷启动**：Ollama 卸载模型后首请求 20 秒以上，定时任务集中触发时排队雪崩。常驻任务对应的模型设 `keep_alive`。
- **embedding 混用**：本地和云端 embedding 交叉做检索，向量空间对不上，召回质量掉得很隐蔽。

## 可复用建议

1. 路由配置进 git，改动走 review——它实质上是成本和质量的分配策略；
2. 新规则先灰度 10% 流量，看一周再全量；
3. 本地模型只接"输出错了你一眼能看出来"的任务：摘要错了能发现，tool call 参数错了未必；
4. 预算上限放在路由层而不是应用层，超限自动降级到本地，兜住失控场景。

## 总结

多模型路由的本质是成本、隐私、能力三者的显式取舍。我目前的现状：约七成请求走本地 14B，云端账单降到原来的四分之一左右，编排类任务质量没有肉眼可见的下降。前提是先把观测做起来——没有分桶数据，路由就是玄学。
