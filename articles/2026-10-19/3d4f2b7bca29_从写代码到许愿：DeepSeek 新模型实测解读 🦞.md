最近 36kr 一篇实测把“许愿式编程”送上了热议：对着 DeepSeek 新模型说一句“帮我做一个 XX 应用”，几分钟后就能得到一个直接能跑的完整程序。评论区两极分化——有人惊呼“前端要变天”，有人吐槽“又是 demo 玩具”。这篇文章不站队，只拆三件事：它到底强在哪、为什么是现在、以及普通开发者该怎么用。而热搜标题里那句“没有小更新”，指的是 DeepSeek 几乎每次迭代都同时动三样东西：能力、价格和开源策略。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-19/5fada906b74d8fda.png)

## “许愿式编程”是什么，新在哪

- **定义**：用一句自然语言描述需求，模型单次生成完整可运行的程序——页面、样式、交互、逻辑全都有；之后靠追加对话继续迭代。
- **举例**：输入“做一个番茄钟：25 分钟倒计时、结束播放提示音、按天记录专注时长”，输出一个打开就能用的单页应用。
- 它和 2023 年那波“AI 写代码”不是一回事。Copilot 时代的体验是**补全**：你写一半它猜一半，人始终是主驾；许愿式编程是“你提需求，它交活”，人退到验收位。这个玩法由 Andrej Karpathy 在 2025 年初概括为 vibe coding，“许愿式编程”算是中文社区给的更形象的名字。
- 真正的分水岭不是“能不能生成代码”，而是**一次成功率**：以前要来回喂报错三五轮，现在不少小应用能一把过。这才是“没有小更新”的底气所在。

## 为什么是 DeepSeek，为什么是现在

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-19/91eecfa8bd81d4e3.png)

一次成功率的跃迁不是玄学，是四件事恰好叠在了同一段时间：

1. **注意力变便宜了。** V3.2 一代引入 DeepSeek Sparse Attention（DSA）：不再让每个 token 和全部上下文做精细计算，而是先筛出相关的少数 token 再精算，官方口径下 API 价格大约降了一半。长上下文便宜了，模型才“装得下”整个项目的代码和报错。
2. **代码是强化学习的完美赛道。** 代码能编译、能跑测试，对错可以自动判定，天然适合可验证奖励（RLVR）这类训练方式——模型在“写完能不能跑”这件事上被打磨了无数轮。
3. **补上了审美课。** 这一代模型普遍在高质量前端数据上下了功夫，布局、留白、配色不再像 2010 年的办公 PPT，“能用”和“看起来专业”的差距被拉近。
4. **Agent 式工作流。** 生成 → 运行 → 读报错 → 自修，模型开始自己调用工具，而不是等人喂错误信息。这一环对“一把过”的贡献，不比模型本身小。

## 实测体感：能许出什么，许不出什么

综合各方实测和我自己跑下来的体感，边界大致清晰：

- **能许出的**：单页工具（番茄钟、汇率换算）、小游戏（贪吃蛇、2048）、数据可视化 demo、一次性脚本。改需求也快——“按钮挪到右上角、换暗色主题”，几十秒交付。
- **许不出的**：多人权限体系、真实支付与登录链路、需要长期演进的架构。共同点是“错一次代价大、正确答案依赖业务上下文”。
- 更隐蔽的坑是**错误的位置变了**：从“编译报错”挪到了“运行时的沉默失败”——页面看着正常，边界条件、并发、异常处理这些不性感的部分却埋着雷。实测里最常见的翻车是幻觉 API：模型自信地调用一个不存在的函数，或者样式在 Chrome 里完美、在 Safari 里塌掉。
- 一句话总结：**许愿能出 demo，许愿出不了 SRE。** 毕竟凌晨三点告警响起时，许愿机不会爬起来看日志。

## 更深一层：成本曲线正在改写分工

- **试错成本趋近于零。** token 单价持续下探后，生成一个完整页面的 API 开销已经到几毛钱量级。过去“要不要专门做这个小工具”的决策，如今变成“顺手许个愿试试”。
- **评测主战场换了。** HumanEval 这类老基准早就刷爆，现在看的是 LiveCodeBench、SWE-bench Verified 这种在真实仓库里修 bug 的硬仗，国产开源模型已在第一梯队站稳。
- **开源 + 降价的组合拳**（DeepSeek 的权重一直走 MIT 协议）改变的不是名次，而是“用不用得起”——这对独立开发者和中小团队的意义，远大于对大厂。
- 冷静面：模型提升的是平均水平，不是方差。从 0 到 1 的门槛被打下来了，从 1 到 100 的工程化难度一点没变。

## 给开发者的三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-19/ecbb9a1bdf5876a5.png)

1. **把大愿望拆成小愿望。** 一次许一个核心功能，跑通再叠加。一句话许一座城，得到的往往是哪儿都通、哪儿都脆的代码。
2. **先定验收，再许愿。** 把“怎么算做完”写成可检查的标准——输入输出示例、边界条件、性能预期——直接放进 prompt，一次成功率会明显上涨。
3. **生成 ≠ 合格。** 上线前过三道人工闸门：安全审查（密钥别进前端、用户输入要转义）、依赖审查（别盲目安装来路不明的包）、最小测试集。这三样，目前还替代不了人。

技术演进有意思的地方在于：当“写出来”越来越便宜，“想清楚要什么”和“判断对不对”就越来越贵。许愿式编程许出来的从来不是终点，而是一个可以立刻上手改的起点——工程师的价值没有消失，只是换了位置。
