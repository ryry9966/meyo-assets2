# 本地 LLM 部署：在家用电脑上跑大模型的实践指南

## 背景

玩 Agent 的人迟早会碰到两件事：一是自动化流程要读你的聊天记录、文件、日程，全走云端 API 心里不踏实；二是 Agent 是高频调用，一个跑循环的任务一天几千次请求，账单比电费贵。所以我在一台家用机上把常用 Agent 链路换成了本地模型，跑了一个多月，把经验整理成这篇。

## 问题

家用硬件的现实是：单卡 8–24GB 显存，或者干脆是核显 / Mac 统一内存。而 Agent 负载和普通聊天不一样——它要求模型稳定输出结构化 tool call、长上下文不崩、还要容忍和 embedding 模型抢显存。很多模型跑分好看，接上 MCP 工具一跑就露馅。

## 做法

**1. 按显存定量级，别按愿望。** Q4 量化下，8GB 显存跑 7–8B，12GB 跑 14B，24GB 跑 32B，这是给 KV cache 留了余量的安全线。Mac 统一内存可以上探一档，但要给系统留 8GB 以上。

**2. 后端选型看需求。** 图省事用 Ollama，要精细控制（KV cache 量化、上下文长度、聊天模板）用 llama.cpp，显存充裕且要并发用 vLLM。三者都提供 OpenAI 兼容接口，OpenClaw 这类 agent 框架改个 base_url 就能接入。

**3. 优先验证 function calling。** 拿一个最简单的 MCP 工具（读文件、查天气）做冒烟测试：模型能不能正确发起调用、参数 JSON 是否合法、失败后会不会重试。这个尺寸段里，Qwen 系列和 Llama 3.1 以上的工具调用相对稳。

**4. 配好上下文与驻留。** 显式设置 context 长度——很多后端默认只有 4k/8k，agent 会被静默截断；常用模型把 keep_alive 设长一点，避免每次调用冷加载等半分钟。温度压到 0.2–0.6，小模型跑工具要稳不要浪。

**5. 建一个自己的小评测集。** 从真实自动化场景里挑 20–30 个任务，每次换模型跑一遍记成功率。这比看任何榜单都有用。

## 踩坑点

- **只算权重不算 KV cache**：14B 模型权重约 9GB，上下文拉到 32k 后 KV cache 再吃几个 GB，直接 OOM。开 flash attention 和 KV cache 量化能省不少。
- **量化档位太激进**：Q2/Q3 的模型 tool call 经常输出残缺 JSON。宁可用 Q4 的更小模型，别用 Q2 的大模型做 agent。
- **声称的上下文 ≠ 可用上下文**：128k 是宣传数字，实际上下文过 16k 后指令遵循明显劣化。长文档交给 embedding + 检索处理。
- **后端模板不匹配**：模型嘴上说“我要调用工具”但框架收不到调用，多半是 chat template 或 tool-call 解析配置没对上，去后端日志看原始输出。
- **小模型爱编参数**：会往 tool call 里塞不存在的字段。MCP 服务端务必做 schema 校验，非法参数直接拒绝并返回错误信息让模型重试。

## 可复用建议

1. 先用云端 API 把 agent 流程跑通，再逐环节替换成本地模型，哪里掉链子一目了然。
2. 本地模型的工具列表控制在 5–8 个以内；工具多就做两级路由，先让小模型选分类，再给子集。
3. GPU 上常驻一个主力对话模型 + 一个本地 embedding 模型就够，别同时加载一堆。
4. 保留降级路径：本地模型连续失败 N 次自动切回 API，自动化任务别陪模型一起死磕。

## 总结

在家用电脑上跑本地模型做 Agent，7B–32B 配合 Q4 量化是一条被验证过的路线。它适合隐私敏感、高频调用、工具结构清晰的任务；不适合追求复杂推理和超长上下文的场景。务实的做法是混合部署：本地扛日常，云端兜底。硬件不变的前提下，决定体验上限的不是模型跑分，而是你对自己任务集的评测数据。
