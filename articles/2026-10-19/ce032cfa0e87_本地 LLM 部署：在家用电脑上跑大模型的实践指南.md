## 背景

做 Agent 和自动化的人对 LLM 的调用频率远高于普通聊天场景：一轮任务里可能有十几次工具调用，每次都是一次推理请求。全走云端 API，一是费用随任务复杂度线性上涨，二是数据要出网，三是断网或限流时整条自动化链路就停摆。

过去一年，7B~14B 级别的量化模型在家用硬件上的可用性明显提升，"把一部分 Agent 流量收回到本地"从玩具变成了可操作的工程选项。这篇帖子记录我在一台普通台式机上把本地模型接进 Agent 工作流的完整过程。

## 问题

动手前先明确三个约束：

1. **显存是硬上限**。模型权重和 KV cache 都吃显存，上下文拉得越长，留给权重的空间越小。
2. **小模型的 function calling 质量参差**。模型卡上写"支持 tool use"，不等于在你的 Agent 框架里能稳定生成合法调用。
3. **Runtime 生态碎片化**。Ollama、llama.cpp、LM Studio 各有默认模板和参数，同一模型在不同 runtime 下表现可能不同。

## 做法

**第一步：按显存定模型档位。** 我实测的大致分界：8GB 显存跑 7B Q4；12~16GB 跑 14B Q4 或 7B Q8；24GB 以上可以尝试 32B Q4。量化首选 Q4_K_M，再低的话 tool call 格式破坏开始明显。

**第二步：选 runtime。** 新手直接 Ollama，一条命令起服务；想精细控制采样参数和模板就用 llama.cpp 或 LM Studio。三者都提供 OpenAI 兼容端点，接入成本很低。

**第三步：接进 OpenClaw。** 把 base_url 指到本地端点，在模型配置里填好模型名即可。关键动作是冒烟测试：挂一个最简单的 MCP 工具（比如读文件或发 HTTP 请求），跑 20 个真实任务，统计 tool call 的生成成功率——这比任何公开 benchmark 都真实。

**第四步：压上下文。** 把一段真实的多轮 Agent 会话灌进去，记录 tokens/s，确认在你常用上下文长度下速度可接受。

## 踩坑点

- **上下文别拉满**。我开满 32k 上下文后 KV cache 直接吃掉 4GB 显存，系统开始 swap，速度从 40 tokens/s 掉到 3。按实际会话长度设 8k~16k 就够。
- **温度调低**。Agent 场景要的是稳定格式，不是创造力，temperature 建议压到 0.2 以下。
- **先怀疑模板再怀疑模型**。同一个模型在 Ollama 下偶发 tool call 格式错误，换到 llama.cpp 指定正确的 chat template 后消失。
- **embedding 单独跑**。向量检索用几百 MB 级的小 embedding 模型就够了，别占用主模型的显存和上下文。

## 可复用建议

1. **建一个 10~20 条的私有评测集**，全部来自自己的真实 Agent 任务，每次换模型、量化或参数跑一遍，几分钟出结论。
2. **做路由而不是全盘本地化**：格式转换、简单摘要走本地 7B，复杂推理和长链路规划走云端大模型，成本和质量都可控。
3. **维护一张"显存-模型-上下文"对照表**，换硬件或换模型时直接查，不重新踩坑。
4. **模型更新慢半拍**。新模型发布后等两周，看社区的 tool calling 实际反馈再上，别当小白鼠。

## 总结

本地部署不是替代云端，而是给 Agent 工作流加一层成本、隐私、可用性都更可控的兜底。核心方法论三句话：按显存选档位，用真实任务做评测，用路由策略分层。家里的旧显卡先跑起来，比对着参数表纠结有用得多。
