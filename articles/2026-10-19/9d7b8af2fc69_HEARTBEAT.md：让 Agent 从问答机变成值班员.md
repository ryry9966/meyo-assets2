## 背景

大多数人对 Agent 的用法还是"拉"式的：打开会话、提问、拿答案、关掉。但真正想要的是一个值班员——它按自己的节奏巡检，有事才找你。OpenClaw 里承担这个角色的就是 HEARTBEAT.md：一个放在 agent 工作区根目录（默认 `~/.openclaw/workspace/HEARTBEAT.md`）的文件，网关按固定间隔（默认半小时左右）把它作为指令喂给模型，模型读完后自行判断"这一轮有没有活"。

## 问题

没有心跳机制时，痛点很具体：

- 日程汇总、收件箱清理、CI 状态盯梢这类事，靠人记得去问，等于没做；
- cron + 脚本能顶一部分，但"是否有事"的判断是硬编码的，稍微需要语义理解就写不动；
- 直接让 LLM 定时自由发挥，又会烧 token、刷屏、重复打扰。

心跳机制要解决的就是：定时 + 语义判断 + 成本可控 + 不打扰。

## 做法

**1. 定间隔与通道。** 在网关配置里设心跳间隔（不同版本叫 `every` 或 `intervalMs`，如 `30m`），先别激进；部分版本支持 activeHours 限制投递时段。

**2. 写 HEARTBEAT.md，建议三段式：**

```markdown
# Heartbeat

## 固定任务
- 每天 09:00（Asia/Shanghai）汇总今日日程，投递到 #morning

## 条件检查
- ~/notes/inbox.md 有新增未处理条目时提醒（与上次相比）
- CI 失败且上轮未报告过，才通知

## 安静规则
- 无事可做，只回复：HEARTBEAT: ok
- 23:00–08:00 不投递，除非标记为紧急
```

**3. 用好 no-op 约定。** 模型回复恰好是 `HEARTBEAT: ok` 时，这轮会被当作空转吞掉，不投递到任何会话。这是控打扰的关键，务必写死在文件里。

**4. 状态外置。** "与上次相比"需要记忆。让 agent 把上轮结论写进工作区一个小状态文件（如 `.state/last-check.md`），下一轮先读它。心跳本身没有内存，你得给它一个。

**5. 动作放心交给工具链。** 心跳里模型带着完整工具集（内置能力、MCP、插件都能调），所以检查动作就是它平时会做的事，不需要额外接线。

## 踩坑点

- **文件写成说明书。** HEARTBEAT.md 每轮都进上下文，200 行 × 每天 48 次心跳，token 全是白烧的。控制在 30 行内，一行一条、可判定。
- **间隔太密。** 先 30m 跑一周看日志再调。盯状态类 15m 足够，日报类每天一次就够。
- **模型过度热心。** 不写"仅在变化时投递"，它会每次都"发现"点什么。安静规则比任务列表更重要。
- **no-op 没生效。** ok 约定对格式敏感，回复必须就是那几个字符；发现刷屏先查这里。
- **动作不幂等。** 心跳触发发通知/建文件前，先检查是否做过，否则重跑会重复动作。
- **"每天一次"会漂移。** 模型对时间的判断有 ± 一个间隔的误差，写明时区和判定规则，接受这个精度。

## 可复用建议

- HEARTBEAT.md 进 git，改文件 = 改值班职责，有 diff 可审计、可回滚；
- 指令公式：`触发条件 + 判定依据 + 投递目标`，缺一个就容易瞎报或漏报；
- 只放通知类、低风险、可重复的事，需要人拍板的动作不要自动化；
- 观察期看两个指标：空转比例（越高越省钱）和实际投递条数（越少说明规则越有效）。

## 总结

HEARTBEAT.md 的价值不在"AI 能主动做事"，而在把主动性约束成一份可审计的配置：文件要短、规则可判定、空转要静默、状态要外置。做好这四点，agent 就能从问答机变成一个不烦人的值班员——有事找你，没事装死，这才是心跳该有的样子。
