## 背景

Agent 跑得久了你会发现：链路里最脆的从来不是模型，而是外部 API。搜索、天气、数据库、第三方 SaaS，任何一环 5xx 或超时，整个任务就卡在半路。传统后端处理这些有一套成熟打法，但 Agent 场景多了个变量——中间还有一层 LLM 在做决策。错误处理不当，轻则浪费 token，重则模型开始"编"。

## 问题

实际遇到的三类典型故障：

1. **瞬时抖动**：429 限流、偶发超时。直接把异常抛给模型，模型立刻道歉放弃，任务其实明明能救回来。
2. **持续故障**：上游挂了十分钟。Agent 在循环里反复重试，一晚上烧掉大量 token，什么都没干成。
3. **最危险的一种**：工具层把异常吞掉，返回空数据。模型拿着空结果继续推理，输出一本正经的错误答案。

## 做法：四层防线

**第一层：错误分类。** 重试只对"可重试错误"生效——超时、429、5xx。401、400、参数错误重试一万次也没用，直接短路返回。工具层别偷懒，把 HTTP 状态码翻译成语义化错误再上抛。

**第二层：受控重试。** 指数退避 + 随机抖动，上限 3 次；上游带 `Retry-After` 就照做。重试必须放在工具执行器里，绝对不要让模型自己决定"再试一次"——它没有退避的概念，只有热情。

**第三层：熔断与降级。** 连续失败达到阈值就熔断，后续请求快速失败，不再打上游。降级按优先级走：备用 provider → 缓存的旧数据（必须标注数据时间戳）→ 明确告知用户"这个数据现在拿不到"。顺序不能反。

**第四层：结构化错误传给模型。** 不要把 stack trace 甩给 LLM，返回一个简洁的结构：

```json
{
  "status": "upstream_unavailable",
  "retryable": true,
  "hint": "已自动重试3次，建议稍后再试或切换数据源"
}
```

模型拿到这个才能做合理决策：换工具、换路径，或者诚实地告诉用户拿不到。

## 踩坑点

- **让模型主导重试**：token 无限烧，任务日志里全是"让我再试一次"。
- **重试非幂等的 POST**：下单接口重试三次，产生三份订单。
- **没加抖动**：多个 Agent 并发时同时重试，把刚恢复的上游又打挂。
- **降级用了旧缓存但不标新鲜度**：模型拿两周前的数据当实时数据推理。
- **写操作不带幂等键就重试**：等于埋雷。

## 可复用建议

1. 所有工具调用收口到统一执行器，超时、重试、熔断在执行器里统一配置，不要每个工具各写一份。
2. 错误响应定义统一 schema：`retryable` 是给重试逻辑用的，`hint` 是给模型决策用的。
3. 按工具维度统计失败率，某工具错误率突增时，先看监控面板再排查 Agent 行为——多数时候是上游的事，不是你的 prompt 写坏了。
4. 所有写操作一律带幂等键，重试才是安全的。

## 总结

Agent 错误恢复的核心就一句话：**基础设施层负责"扛"——重试、熔断、降级；模型层负责"选"——基于结构化错误做决策。** 该代码做的交给代码，该判断的交给模型，两边都别越界。外部 API 挂不挂你控制不了，但挂了之后 Agent 是体面降级还是当场胡说，完全取决于你今天下午写的那几十行代码。
