## 背景

OpenClaw 的 agent 跑久了会积累大量记忆条目：日志摘要、配置备忘、排查记录。`memory_recall` 的职责是在对话中按需召回这些片段，塞进上下文。常见实现里有两路检索可选：语义搜索（embedding 向量检索）和全文搜索（SQLite FTS5 这类关键词检索）。我最初的直觉是"语义搜索更先进"，直到它连续几次漏掉我记录的 API 报错码，才决定认真做一次对比。

## 问题

我的记忆库约 600 条，混合两类内容：

- **精确 token 类**：报错码、函数名、服务器 IP、commit hash；
- **自然语言类**：某次排查思路、"当时为什么把超时调到 30s"这类叙述。

实测发现两者各有清晰的失败模式：语义搜索对精确 token 几乎无能为力——embedding 之后，两个不同的报错码在向量空间里距离毫无区分度；而全文搜索对同义改写完全失明——用"连接超时"搜不到我写的"socket hang up"。所以真正的问题不是谁更好，而是内容类型和检索方式是否匹配。

## 做法

搭了个小基准，步骤可直接复用：

1. 从历史会话里挑 30 个真实召回场景，每条标注期望命中的记忆条目（top-5 命中即算对）；
2. 同一份数据分别跑 FTS5 和本地 embedding 检索（bge-small-zh），记录命中率与延迟；
3. 加一路混合检索：两路各取 top-10，用倒数排序融合（RRF）合并，去重后截断。

结果：纯 FTS 命中 17/30，纯语义 19/30，混合 26/30，且混合方案对两类内容都没有明显短板。延迟上 FTS 是毫秒级，本地 embedding 单条约 20ms，都不是瓶颈。

## 踩坑点

- **中文分词**：FTS5 默认 tokenizer 对中文基本失效，需要换 trigram 或先 jieba 分词再入库，否则中文查询命中率会虚低，容易误判"FTS 不行"；
- **embedding 模型语言错配**：早期用过英文为主的模型，中文查询召回一塌糊涂，换成中文模型后立刻恢复正常；
- **chunk 太大**：按整条笔记切片时，一条 800 字的排查记录会稀释关键句的向量，改成按段落切后召回明显变准；
- **索引滞后**：写入记忆后忘记重建索引，出现过"刚记的查不到"的假故障，现在写入流程末尾固定带一步增量索引。

## 可复用建议

- 记忆库在几百条以内时，别急着上向量库，FTS 够用且零维护成本；
- 精确 token 占比高（运维、开发类记忆）就给 FTS 更高权重；叙述性内容多就偏向语义；
- 拿不准就直接上混合检索 + RRF，二十行代码的事，容错性最好；
- 结论必须用自己的真实数据测。别人的 benchmark 在你的记忆分布上基本不可迁移，这条最重要。

## 总结

语义搜索和全文搜索不是替代关系，而是互补关系。`memory_recall` 的选型取决于你的记忆长什么样：精确标识符靠全文，模糊语义靠向量，RRF 混合融合是工程上最稳的默认解。先测再选，别让"先进"两个字替你做决定。
