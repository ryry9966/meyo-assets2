## 背景

跑 Agent 的人迟早会碰到这个场景：一条 MCP 工具链里，某个外部 API 超时或 5xx，然后整个任务的表现开始变得诡异——要么 Agent 卡在重试循环里持续烧 token，要么工具层把异常吞掉返回了"成功"，模型开始一本正经地编造结果。

传统服务里我们有熔断、降级、限流一整套方案；但 Agent 场景多了一层不确定性：**错误会被喂回 LLM，由它决定下一步**。处理不好，错误本身就成了幻觉的燃料。

## 问题拆解

外部 API 挂掉时，实际会在四个层面出问题：

1. **请求层**：超时、连接拒绝、429 / 5xx；
2. **Agent 循环层**：模型看到报错后反复重试，甚至换着姿势重试；
3. **数据层**：部分写入成功、部分失败，状态不一致；
4. **体验层**：任务"假死"，没有可观测的失败原因。

很多框架的默认行为是把异常字符串直接塞回上下文，这既浪费 token，也容易诱导模型瞎猜。

## 我们的做法

核心思路：**错误恢复全部做在工具 / MCP 封装层，不依赖模型自觉。**分四步：

**1. 错误分类先行。**在封装层把错误归为四类：可重试（超时、429、5xx）、不可重试（4xx 参数错）、部分成功、未知。每类返回统一结构：`{ok, error_type, retryable, hint}`，其中 `hint` 用一句自然语言告诉模型"建议等 30 秒再试"或"参数有误，请修正后重试"。模型需要的是可决策的信息，不是堆栈。

**2. 重试策略收敛在代码里。**指数退避 + 抖动，最多 3 次，且只在 `retryable=true` 时触发。绝不让模型自由发挥重试次数——我见过 Agent 连续重试 20 次的账单。

**3. 熔断 + 降级。**同一工具连续失败 N 次就短路一段时间，直接返回"该服务当前不可用，建议跳过或换方案"。关键路径准备降级源：备用 API、缓存快照，或者干脆明确告诉用户"这一步失败了，其余结果仍然有效"。

**4. 幂等与断点。**非幂等操作（下单、发消息）必须带幂等键；长任务落 checkpoint，恢复时从断点继续，而不是从头跑。

## 踩坑点

- **把 HTTP 200 当成功。**不少 API 挂了之后返回 200 + 错误体，必须校验业务码。
- **重试非幂等 POST。**结果是三条重复记录，而且 Agent 还认为任务成功了。
- **退避时间超过上游编排超时。**重试还没跑完，外层先超时了，等于白配。
- **熔断器按实例隔离。**并行的多个 Agent run 各自持有熔断状态，谁也熔不断，状态要集中存储。
- **让模型看到原始异常。**一段 stack trace 进上下文，输出质量肉眼可见地变差。

## 可复用建议

- 把 `{ok, error_type, retryable, hint}` 做成团队所有 MCP 工具的统一返回契约，写进工具开发规范。
- 每个工具的退避参数走配置文件，不同上游的容忍度不一样。
- 上线前做故障注入：mock 一个必 500 的接口，看 Agent 能否在 3 次重试后体面收场。
- 高危动作失败时走人工确认，而不是自动降级。
- 日志带 trace id，把"模型决策 + 工具结果 + 重试次数"串起来，事后排障全靠它。

## 总结

外部 API 挂掉不可怕，可怕的是错误被吞掉或者被无限放大。核心原则就三条：**错误结构化后交给模型决策、重试和熔断收敛在代码层、失败要体面**——要么降级，要么明确告诉用户哪一步坏了。Agent 的可靠性上限，往往不取决于模型多聪明，而取决于工具层把这些脏活处理得多干净。
