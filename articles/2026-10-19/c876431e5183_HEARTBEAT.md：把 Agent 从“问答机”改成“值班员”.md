## 背景

用 OpenClaw 一段时间后，多数人的用法还是一问一答：你发消息，agent 响应，然后它挂起等下一条。但很多事本质上不需要你先开口——收件箱有没有新邮件、磁盘是不是快满了、早上该不该给你一份今日摘要。这些事的共同点是：触发条件是时间到了，而不是你提问了。

heartbeat 机制就是为此设计的：gateway 按固定间隔（默认约 30 分钟，可配置）向主会话发一次心跳。默认情况下 agent 没什么可干，回一个 `HEARTBEAT_OK` 继续沉默。而 HEARTBEAT.md 是放在 workspace 根目录（默认 `~/.openclaw/workspace/`）的清单文件——agent 每次心跳都会读它，把检查项过一遍，有值得汇报的才打扰你。

## 问题

没有 HEARTBEAT.md 时，主动任务通常这么凑：系统 cron 跑脚本，脚本再想办法把结果推进对话。调度和判断分属两套逻辑，改一个条件要同时动两处。

把判断逻辑写进 HEARTBEAT.md 后，调度归 heartbeat，判断和执行都归 agent——清单是唯一的逻辑载体，改需求只改一个 markdown 文件，能 diff、能 review。

## 做法

1. 在 workspace 下建 `HEARTBEAT.md`，先写一条最简单的验证链路：

```markdown
- 如果本地 git 仓库有超过 3 天未推送的提交，提醒我
- 否则不要发消息
```

2. 等下一次心跳确认 agent 真的执行了检查且无事时保持沉默。等不及就把间隔临时调短，或直接对 agent 说“现在按 HEARTBEAT.md 跑一轮”。

3. 验证通过后再逐条加任务，推荐每条都带明确的静默条件：

```markdown
## 收件箱
- 检查未读邮件，只把标题匹配"账单|告警"的报给我
- 其他一律跳过

## 日报
- 每天早上 9 点后的第一次心跳，给我昨日提交 + 今日日程摘要
- 其余时间跳过
```

4. 清单条目多、单条耗时长的话，适当拉长心跳间隔，别让心跳排队。

## 踩坑点

- **token 成本是线性的**。每次心跳都是一轮完整调用，哪怕所有检查项都无事发生。清单从 3 条涨到 20 条后，先看消耗再谈需求——我最后留下的长期项只有 4 条。
- **"无事不打扰"必须显式写**。不写的话，部分模型每次心跳都汇报"一切正常"，一天下来比任务本身还吵。
- **心跳不是精确调度器**。设备休眠、gateway 忙时心跳会顺延甚至跳过。"每天 9:00 整点发"这种硬性时间交给 cron 更可靠；heartbeat 适合"9 点后第一次心跳顺便做了"这种模糊语义。
- **模糊指令没法执行**。"帮我盯着点服务器"这种条目，agent 每次都在纠结要不要报。改成可判断的条件："CPU 连续两次心跳超过 90% 才报，否则跳过"。

## 可复用建议

- 把清单当代码维护：每周删一次，连续两周没触发过汇报的条目直接删。
- 时间窗口约束（"只在 9:00–19:00"）是降噪最有效的手段。
- 需要外部数据的检查（天气、RSS），让 agent 通过 MCP/插件取数，不要在清单里贴死链接。
- 值得长期留下的心跳任务有个共同特征：低频、有明确判断条件、触发时你确实需要被打断。

## 总结

HEARTBEAT.md 的价值不在“自动化”三个字，而在它把主动行为的判断逻辑收进了一个可 diff、可 review、可随手删改的文件里。先调短间隔验证链路，再一条条加任务，控制清单长度，剩下的交给时间，让它帮你筛掉伪需求。
