## 背景

大多数助手的交互模型是"你问它答"：不发消息它就是一块石头。但真正的效率差距在另一半场景——那些你忘了开口、却确实该被处理的事：CI 挂了没人提醒、明早的会没准备材料、盯着的页面已经变了。Proactive（主动式）能力，就是让 Agent 在无人发消息时，基于时间、事件或状态变化自己发起动作。

## 问题

主动不等于勤快。实践里最难的从来不是"让它动起来"，而是三件事：

1. **触发从哪来**：定时、事件、状态轮询，各自适合什么场景；
2. **判断谁来做**：每次触发都烧一次 LLM 调用，还是先用确定性规则过滤；
3. **权限怎么收**：主动执行写操作的风险远大于被动回答。

## 做法

我在 OpenClaw 上把 proactive 拆成四层，跑通了两个场景（GitHub webhook 触发的 CI 失败告警 + cron 触发的每日日程摘要），步骤如下：

**1. 触发层：事件优先，定时兜底**
- 时间驱动：cron 注册任务，每天 8:30 推日程摘要；
- 事件驱动：webhook 打到本地 HTTP 端点，直接唤起对应 skill；
- 状态驱动：低频轮询（如 30 分钟一次）抓外部状态，diff 后再决定是否进入下一层。

关键原则：触发层全部是确定性代码，**不经过 LLM**。

**2. 判断层：LLM 只回答"值不值得说"**
触发命中后，把新鲜状态快照 + 最近一次同类推送记录塞进上下文，让模型回答三个问题：有变化吗、值得打扰吗、现在说还是攒着批量说。无变化的触发在此静默终止——这是省钱的核心闸门。

**3. 执行层：三级自治**
- 只读动作（查状态、汇总、生成草稿）：直接执行并推送；
- 写操作（给第三方发消息、改文件）：生成计划后回到聊天渠道请求确认，回复确认才执行；
- 高危动作：永远人工。

**4. 回路层：可观测**
每次主动行为写一条结构化日志（触发源、token 消耗、是否被忽略）。跑一周回看，你会发现约一半推送是噪音——这就是调参依据。

## 踩坑点

- **心跳太勤，账单感人**：最初 heartbeat 每 5 分钟一次且每次都调模型，一天 token 消耗是正常对话的 3 倍。改成"先 diff 再调模型"后降到约 1/10。
- **主动变骚扰**：推送没有上限，用户三天后就把通知静音了。给每类任务设每日配额，超了就攒到下一次批量发。
- **上下文过期**：事件触发后让模型"自己再去查一下"，查到的是 20 分钟前的缓存，结论全错。触发时必须携带 fresh snapshot，别让模型二次取数。
- **静默失败最危险**：主动任务挂了没人知道，用户以为"没事"，其实是"没跑"。加一条死信通道：连续失败 2 次就降级为一条"任务异常"的被动提示。
- **时区**：cron 按 UTC 跑，东八区用户的 8:30 摘要变成了 16:30。调度统一存 UTC，展示层转本地时区。

## 可复用建议

1. **确定性触发 + LLM 判断**，顺序不能反。模型不擅长"准时"，但擅长"权衡要不要说"。
2. **自治分级**：notify < draft < execute，逐级放开，每级稳定观察一周再升级。
3. **每条主动消息都带"为什么现在说"**：一句话说明触发原因，用户才会信任下一次推送。
4. **先做一个高价值低风险场景**（如 CI 告警），跑稳了再横向扩。Proactive 的口碑是靠"不烦人"一点点攒出来的。

## 总结

Proactive 不是一句 system prompt 就能"开启"的开关，而是触发、判断、执行、回路四层的工程组合。OpenClaw 的插件与 MCP 体系恰好能把这四层拼起来：cron/webhook 管触发，规则管过滤，模型管权衡，日志管进化。先让它在一件小事上可靠地"多嘴"一次，比让它包办一切重要得多。
