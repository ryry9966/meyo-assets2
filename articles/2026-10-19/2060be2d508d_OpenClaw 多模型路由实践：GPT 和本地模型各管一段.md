## 背景

OpenClaw 的 agent 跑真实任务时，两 类需求经常打架：多步规划、复杂工具调用这类活，云端强模型（GPT-4o 这个级别）明显更稳；但摘要、格式化、分类、Embedding 这类高频低难度调用，全走 API 又贵又不必要，还可能碰到数据不能出内网的合规问题。多模型路由解决的就是一件事：**同一个 agent 里，不同环节用不同的模型**。

## 问题

常见的错误做法有两种：

1. **全走云端**：月账单难看，内网数据合规过不去；
2. **全走本地小模型**：规划阶段频繁跑偏，MCP 工具调用格式错乱，debug 花的时间比省下的 API 费还贵。

核心问题有三个：路由粒度怎么定、按什么规则路由、失败了怎么兜底。

## 做法

**1. 建模型池，给模型打角色标签**

```yaml
models:
  primary: gpt-4o          # 规划 / 多步工具调用
  fast: qwen2.5:14b        # 本地：摘要、抽取、分类
  embedding: bge-m3        # 本地：向量化
```

**2. 先用静态规则路由，别急着上智能路由**

规划类、需要跨多轮调用 MCP 工具的任务 → primary；摘要、重写、结构化抽取 → fast；向量化 → embedding。规则确定性高、可日志化，出了问题能回放。

**3. 设兜底链**

本地模型输出解析失败（比如工具调用 JSON 不合法）、或上下文超限时，升级到 primary 重试一次，并记录升级原因。

**4. 敏感数据先本地后云端**

涉及内网文档的 MCP 工具结果，先让本地模型做一次脱敏摘要，只把摘要交给云端模型继续推理。

**5. 埋点统计**

记录每次调用的模型、tokens、时延、失败率，跑一周后按数据调整路由规则，而不是凭感觉。

## 踩坑点

- **本地模型 function calling 实现不一**：Ollama 和 vLLM 的 tool call 格式有差异，直接复用云端的 schema 会解析失败。给本地模型单独维护一套 prompt 模板。
- **上下文长度**：本地模型常见 8k~32k，MCP 工具返回的大段结果直接塞进去，截断位置往往很莫名。工具结果先过一遍本地摘要再进主流程。
- **时延错觉**：消费级显卡上本地模型生成长输出，实测可能比 API 还慢。"本地 = 快"不成立，路由决策要看 P95 实测数据。
- **让 LLM 自己做路由决策**看似聪明，但每次决策本身也是一次调用。简单场景下规则路由更便宜也更稳定。
- **structured output 支持参差**：本地模型侧记得关掉不兼容的 JSON mode 参数，否则表现为偶发解析失败，很难排查。

## 可复用建议

- **80/20 起步**：先只切"规划 vs 杂活"两档，跑稳了再细分，不要一上来做五六个路由分支。
- **路由规则必须落日志**：出问题时能回放是哪条规则把请求送错了模型，这是排障的生命线。
- **升级条件收敛到两三个明确信号**：解析失败、上下文超限、任务标签为规划类。模糊条件堆多了，路由行为就不可预测了。

## 总结

多模型路由的价值不在省多少钱，而在于**让每个环节的确定性可控**。先用静态规则把明显错配的任务分出去，靠数据逐步收紧规则；智能路由等静态规则覆盖不住真实流量时再考虑。OpenClaw 的插件和 MCP 生态让换模型成本很低，真正贵的是路由策略设计不对带来的排障时间——先把日志和兜底做好，再谈优化。
