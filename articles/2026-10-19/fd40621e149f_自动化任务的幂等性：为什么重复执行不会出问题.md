# 背景

跑过一段时间的自动化都会遇到同一个事实：任何任务都会被执行不止一次。定时器重叠、webhook 重投、Agent 对同一个工具发起重试、MCP 服务断连后重放请求——这些都是常态，不是异常。调度器和队列大多提供“至少一次”投递，而不是“恰好一次”。所以问题从来不是“会不会重复”，而是“重复之后会发生什么”。

# 问题出在哪

副作用型操作天然不耐重复。同一个任务跑两遍，可能产生：两条重复工单、两条重复通知、数据库里两行一样的记录、对外 API 创建了两份资源。更隐蔽的是 Agent 场景：模型在一次会话里对同一个工具发起两次语义相同的调用，或者上游重试导致整个 run 重放，前几步已完成的工作被再做一遍。这类问题在测试时几乎不暴露，因为测试只跑一次。

# 落地做法

核心思路一句话：给“同一次逻辑操作”一个稳定的键，写入前先占位。

1. **盘点副作用边界。** 只处理会写外部状态的操作：建单、发消息、写库、调第三方 API。纯只读操作不需要幂等。
2. **设计幂等键。** 优先用上游给的自然键（事件 ID、消息 ID）；没有就用确定性派生，比如 hash(任务类型 + 目标对象 + 事件ID 或时间窗口)。键必须在重试之间保持不变。
3. **原子占位。** 执行前先写一条记录，靠数据库唯一约束或 Redis SETNX 保证并发下只有一个执行者拿到执行权——拿到即执行，拿不到直接跳过。
4. **写操作本身做成可重复。** 插入用 upsert（`ON CONFLICT DO NOTHING`），更新带条件或版本号，避免“先查再写”的裸竞争。
5. **分步任务做检查点。** 多步任务记录每步完成状态，重试从断点续跑，而不是从头重放。
6. **在 MCP 工具描述里写明幂等契约**，让调用方（包括模型）知道哪些工具重复调用是安全的。

# 踩坑记录

- **每次尝试生成新 UUID 当幂等键。** 重试之间键变了，等于没做。键必须由任务上下文决定，不能由执行时刻决定。
- **时间窗口粒度选错。** 精确到秒，同一个 run 拆成多个键；精确到天，合法的第二次执行被误拦。窗口要对应业务语义。
- **只在数据库层去重，通知照发两次。** 多步副作用要么每步各带键，要么用事务性 outbox，把业务提交和“待通知”记录一起落库。
- **键记录没有清理策略。** TTL 太短拦不住延迟重试，永不清理则表无限膨胀。按上游最大重投时间设定 TTL。
- **相信队列的“恰好一次”。** 主流队列给的都是至少一次，消费端不做幂等就是裸奔。

# 可复用建议

- 把“每个任务至少执行两次”当作默认假设来设计。
- 幂等放在写入边界的工具处理器里，而不是指望提示词或规划层自觉。
- 验收标准很简单：在预发环境故意把同一个任务跑两遍，再注入一次“执行到一半失败后重试”，观察副作用数量。这两个用例过了，才算过。

# 总结

幂等不是重试配置，是设计属性。成本很低——一张去重表、一个稳定键、一次原子占位——换来的是整条自动化链路可以放心地重试、重放、重跑。对靠 Agent 和调度器驱动的系统来说，这是少数“越早做越省事”的基础工作。
