## 背景

现在的 Agent 普遍能调工具：读文件、跑 shell、写数据库、发 HTTP 请求。MCP 把接工具的门槛降到几乎为零，但工具是有副作用的，而模型的判断是概率性的。它天然不知道 `ls` 和 `rm -rf` 有什么本质区别——除非你在系统层面替它划清界线。

## 问题

实践中常见两个极端。一种是全部要确认：Agent 每写一个文件都弹窗，人很快疲劳，变成闭眼点“允许”，确认机制形同虚设。另一种是全部放行：跑得确实爽，直到某天它“顺手”删了共享分支，或把测试邮件发给了真实客户。核心矛盾在于：问得太多，自动化失效；问得太少，事故必然发生。

## 做法：三维度打分，四档放行

建议把“要不要问人”拆成三个维度评估：**可逆性**（能不能撤回）、**影响半径**（只影响自己工作区，还是共享仓库、生产环境、外部他人）、**意图明确度**（用户明确要求过，还是 Agent 自己推断的）。据此分四档：

- **T0 自动执行**：只读操作。查文件、搜索、跑测试，不确认，但记日志。
- **T1 自动执行 + 审计**：沙箱内的可逆写入。改代码走分支，邮件先进草稿箱。
- **T2 必须确认**：不可逆或影响他人的动作。push 共享分支、对外发送、超预算的消耗类调用。确认时必须带上完整参数和回滚方式，而不是一句“可以吗”。
- **T3 禁区**：生产数据变更、真实付款、给真人发消息、共享凭据。工具层直接不注册，不提供确认选项。

关键原则：**边界写在工具层，不写在提示词里**。提示词会被注入绕过，工具层不会。

## 落地步骤（以 OpenClaw + MCP 为例）

1. 工具按风险分级挂载：只读工具正常接，写类工具包一层确认 gate（hook/中间件），T3 干脆不接。
2. 写操作默认 dry-run：先输出 diff 或预览，人批了再真执行。
3. 拒绝要有返回值：deny 时带回原因反馈给 Agent，让它调整方案，而不是抛异常导致它胡乱重试。
4. 外部通信一律草稿模式：Agent 生成内容，人负责点发送。审批人和操作域要匹配，别谁在线谁批。

## 踩坑点

- **确认疲劳**是最常见的失败模式。一周弹 200 次，人就会无脑批。解法不是加确认，而是把更多操作降级到沙箱内自动跑，把 T2 名单收得非常窄。
- **安全动作链**：单看每一步都无害，读个配置、调个接口，拼起来就是越权。审计要按任务链看，不能只看单次调用。
- 弹窗信息太薄等于没确认，必须展示将要执行的具体命令、参数和影响范围。
- 长任务中途暂停确认时注意状态持久化，恢复后别让 Agent 从头重跑已完成的步骤。

## 可复用建议

- 冷启动策略：所有工具先按只读跑两周，根据日志和险情逐个开放写权限。
- 分级策略写成版本化的配置文件，像代码一样 review 和回滚。
- 每次确认都落库（谁批的、批了什么参数），每月回看一次，动态调整分档。
- 准备一个显式暂停开关，出问题能立刻冻结，而不是拔网线。

## 总结

权限边界不是一个开关，而是一张按“可逆性 × 影响半径 × 意图明确度”划出的分级表，并且必须在工具层强制执行。目标不是让人类参与得最少或最多，而是让每一次打断都值得被认真读一眼。做到这一点，自动化才敢真正放手跑。
