## 背景

OpenClaw 的 agent 流水线里，LLM 调用从来不止一种。一次完整任务往往串联十几次调用：意图分类、参数抽取、工具规划、代码生成、结果总结。把这些全部压给 GPT 级云模型，账单和延迟都难看，敏感数据还要出网；全部换成本地模型，复杂步骤的质量又明显掉。多模型路由要解决的就是这个分配问题。

## 问题

实践里常见两种极端：

- **一把梭云模型**：内部代码分析、含 PII 的日志处理也直接上云，合规压力和成本都不可控。
- **一把梭本地模型**：工具调用 JSON 频繁崩坏、长上下文被静默截断，链路在中间步骤悄悄劣化，最后只表现为“效果变差”，很难定位。

路由的本质不是选模型，而是给每次调用定义约束：**能力下限、敏感级别、延迟预算、成本预算**。

## 做法

按这个顺序落地：

1. **给调用打标**。在插件 / MCP 封装层约定两个元字段：`task_type`（classify / extract / plan / code / summarize）和 `sensitivity`（public / internal / pii）。所有 LLM 调用必须带上，进 code review。
2. **建模型别名层**。prompt 和工具定义里只写别名（如 planner、worker、guard），别名在配置里解析到具体模型。改路由策略不动业务代码。
3. **先写三条规则跑起来**：
   - `sensitivity != public` → 本地模型，硬规则，不允许 fallback 回云；
   - `task_type ∈ {classify, extract, summarize}` → 本地量化小模型（7B~14B 档）；
   - `task_type ∈ {plan, code}` → 云端旗舰模型。
4. **加 fallback 链和校验**。云模型设超时与限流重试；本地模型输出必须过 schema 校验，不过就升级到更强模型重试，而不是原地重试三次。
5. **记路由日志**。每次调用记录：task_type、命中规则、实际模型、首 token 延迟、token 数、是否 fallback。没有这份数据，后面的优化全是拍脑袋。

## 踩坑点

- **本地模型吐坏 JSON**：往往不是模型不行，是没校验。工具调用步骤必须接 schema 校验 + 跨模型升级重试。
- **静默截断**：本地模型上下文窗口小，长文档路由过去被悄悄截掉。路由前加长度检查，超限走云端或先分段摘要。
- **本地服务冷启动**：推理服务默认会卸载闲置模型，agent 间歇性调用导致每次重新加载，延迟反而高于云模型。要么固定 keep_alive，要么确认调用频率够高再路由到本地。
- **版本漂移**：云模型悄悄升级、本地量化版本变更，都会让同一条链路结果波动。别名绑定到具体版本号，路由变更先过评测集。
- **规则膨胀**：从三条规则起步。一上来写十几条条件组合，维护成本会反噬。

## 可复用建议

- 别名层是路由的前提，**先做别名，再做路由**。
- 每种 task_type 维护 20~50 条回归样例，改路由策略先跑评测集，对比通过率和成本再上线。
- 默认方向建议“敏感数据本地化，其余云端”，然后依据路由日志，把高频低难度任务逐步下沉到本地，而不是反过来。
- 每周看一次路由分布：如果 80% 调用都落在同一条规则上，说明分类维度定错了，先修打标再调规则。

## 总结

多模型路由不是技术炫技，是约束建模。把能力、敏感度、延迟、成本四个维度写清楚，规则自然浮出来。从三条规则加一份路由日志起步，比任何“智能路由框架”都更快见效。OpenClaw 这类框架的价值在于链路可控——你的路由策略也应该是自己能读懂、能回滚的那一种。
