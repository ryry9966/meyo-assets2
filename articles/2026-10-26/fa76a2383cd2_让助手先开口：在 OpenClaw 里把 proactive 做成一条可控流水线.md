## 背景

大多数 agent 的使用方式还是“你问它答”。但 OpenClaw 这套体系里，定时器、webhook 钩子、MCP 工具其实早就齐了——原料都在，只是大部分人只用了对话这一个入口。把触发源接上之后，助手完全可以在你开口之前就把事办了，或者至少把事备好。

## 问题

Proactive 真正的难点不是“自动执行”，而是**什么时候该出手**。做宽了是通知垃圾制造机，两周后必然被整体关掉；做窄了等于没做。约束就三条：不打扰、不误伤、可回溯。下面是我们把这条链路跑起来之后的拆法。

## 做法

按四步搭：

1. **触发源分层**。定时（cron）、事件（webhook、文件监听）、状态轮询（用 MCP 工具读指标）三类分开管，触发器全部写成声明式配置，和执行逻辑解耦。
2. **规则前置的过滤管线**。阈值、去重、冷却窗口先用便宜规则挡掉九成噪音，LLM 判分只处理剩下的灰色带。顺序反了就是成本灾难。
3. **动作分级**。L0 只记录，L1 备好草稿等人确认，L2 推送通知，L3 白名单内直接执行。新场景一律从 L1 起步。
4. **打断预算**。每个 agent 每天的主动触达上限写进配置，超了只进日志、不发通知。

配置大致长这样：

```yaml
proactive:
  budget: { max_notify_per_day: 5, cooldown_minutes: 30 }
  action_policy:
    default_level: draft
    execute_whitelist: ["calendar.reschedule"]
```

## 踩坑点

- **触发风暴**：webhook 抖动导致一小时触发几十次评估调用，token 费直接翻倍。去抖 + 规则前置，缺一不可。
- **LLM 判分不稳**：同一事件两次打分能差一档。别拿它当唯一闸门，规则阈值兜底。
- **上下文过期**：agent 被唤醒时不知道用户最近在干嘛。唤醒时注入最近几条会话摘要，判断质量明显回升。
- **副作用动作没跑 dry-run**：上线的自动重排日程直接改了协作方的日历。任何 L3 动作先用观察模式跑一周。
- **通知疲劳**：预算宁紧勿松，第一条主动消息就别翻车。

## 可复用建议

- 每个主动动作必须能回答五个问题：谁触发、证据是什么、置信度多少、做了什么、怎么回滚。答不全就不上线。
- 每周复盘日志，统计主动动作采纳率，低于三成就收紧触发条件，而不是去调 prompt。
- 触发器配置化，让不写代码的同事也能自己调开关。

## 总结

Proactive 的核心不是更多自动化，而是更克制的出手判断。把它拆成信号、过滤、预算、分级、审计五段，每段单独可测，整条链路才敢常开。先从“备好草稿”做起，信任攒够了再逐步放权。
