## 背景

Agent 默认是失忆的。每次新会话，你都要重新交代一遍：主写 Go、包管理用 pnpm、注释写英文、先给方案别废话。这些信息反复输入，本质上是把“用户画像”当成了临时上下文。

AGENTS.md / CLAUDE.md 已经解决了“项目上下文”的问题，但它们描述的是代码库，不是你。项目会换，偏好跟着人走。USER.md 补的就是这一层：一份跟随你、而不是跟随仓库的用户描述文件。在 OpenClaw 里，它就放在 workspace 下（如 `~/.openclaw/workspace/USER.md`），随会话启动注入。

## 问题

没有用户画像时，常见三类损耗：

1. **重复沟通**：同一套自我介绍每个会话讲一遍，时间长了不同会话里还出现互相矛盾的版本。
2. **错误假设**：Agent 看到仓库里有 lock 文件就猜 npm；遇到模糊需求，默认补全成它熟悉的样子而不是你的样子。
3. **黑盒记忆**：一些工具自带“记忆”功能，但写了什么你看不到、没法 review、没法版本化，行为出问题无从排查。

## 做法

核心思路：把用户画像当成配置文件，而不是对话产物。

**1. 建文件。** 放固定路径，内容控制在 60 行内，全部用事实陈述：

```markdown
# User Profile
- 10 年后端，主写 Go，辅助 TypeScript；pnpm，不用 yarn
- 回复默认中文；代码、注释、commit message 用英文
- 先给结论和方案，解释按需展开；不要客套
- 不确定时问一句，不要自行脑补业务规则
- 当前焦点：消息队列削峰改造（2025-Q1）
```

**2. 注入上下文。** 推荐在会话启动时把文件内容拼进 system prompt，一个小 hook 就够，行为最确定。也可以封装成 MCP resource 让 Agent 按需读取，或 symlink 到工具约定的位置。注入方式选一种，别叠加。

**3. 定优先级。** 全局 USER.md 描述“我是谁”，项目内 AGENTS.md 描述“这个仓库怎么干活”，冲突时项目优先。把这条规则写在 USER.md 文件头，避免两个来源打架。

**4. 做维护。** workspace 放进 dotfiles 仓库做版本管理，换机器、换工具链都带着走。

## 踩坑点

- **写成小作文**。“资深”“严谨”这类形容词对模型没有约束力，只写可执行的事实和规则。
- **信息过期**。换了技术栈没更新，Agent 会拿旧偏好持续犯错。文件头加日期，每月扫一遍，当前焦点一栏强制更新。
- **塞敏感信息**。真实姓名、公司名、内网域名都可能随请求发到云端 API，写职位方向即可，别写具体身份。
- **和会话记忆混用**。记忆是“发生过什么”，USER.md 是“我是谁”。把对话细节往里倒，文件会迅速膨胀失效。

## 可复用建议

- **两次法则**：同一个纠正对 Agent 说了两次，就写进 USER.md。这是成本最低的沉淀机制。
- **按规则写，不按印象写**：“代码注释英文”可用，“专业一点”不可用。
- **团队场景加一份 TEAM.md**：代码规范、发布流程等共享上下文和用户画像分开，个人偏好不污染协作规范。
- 模板四块就够：技术环境、沟通偏好、边界规则、当前焦点。

## 总结

USER.md 不是一个功能，是一个习惯：把对 Agent 的重复要求收敛成一份可版本化、可 review 的小配置。成本半小时，收益是每次会话省掉的开场白和少踩的假设。先从 10 行写起，跑两周，再按两次法则慢慢补。
