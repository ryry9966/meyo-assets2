## 背景

做 Agent / MCP 自动化久了，会遇到三类实际问题：定时任务批量调用云端 API，账单涨得很快；本地日志、文件这类敏感数据不想出网；高峰期限流重试让流水线变得不可靠。本地模型不是为了替代云端，而是给 Agent 加一个"够用的工人"——量大、敏感、对推理深度要求不高的活，交给它。

## 问题

我的硬件是 12GB 显存的消费级显卡 + 32GB 内存，属于最常见的家用配置。目标有三个：跑一个 7B~14B 的指令模型；暴露 OpenAI 兼容接口；最关键的——作为 OpenClaw 的备用模型时，MCP 工具调用成功率要能看。

## 做法

1. **选运行时**：Ollama 上手快，llama.cpp 的 `llama-server` 控制粒度更细（上下文长度、KV cache 量化、GPU 层数都能调），两者都提供 OpenAI 兼容端点。我最后用 llama.cpp，因为需要精细控制显存。
2. **选模型和量化**：中文 + 工具调用场景，Qwen2.5-14B-Instruct 的 Q4_K_M 是甜点位，权重约 9GB，12GB 卡在 16k 上下文内能跑稳；想留余量就上 7B 的 Q4。
3. **启动参数**：`-ngl 99` 全量卸载、`-c 16384`、开 flash attention、KV cache 用 `q8_0` 量化，端口起在 `127.0.0.1:8080`。
4. **接入 OpenClaw**：模型配置里把 base_url 指到 `http://127.0.0.1:8080/v1`，temperature 压到 0.2~0.4，再配好到云端模型的 fallback。
5. **真实压测**：写了个 20 条任务的脚本，覆盖文件读取、shell 执行、网页抓取三类 MCP 工具，跑通率作为唯一验收指标。

## 踩坑点

- **量化先伤工具调用，后伤对话质量**。Q4_K_M 基本无感，Q3 以下 JSON 参数开始畸形、漏发 tool call。别用聊天流畅度判断模型好坏，用工具调用成功率。
- **上下文是显存黑洞**。Agent 一次读个大文件，KV cache 直接顶爆显存。MCP 插件层面一定要做输出截断，50KB 的日志灌进上下文谁都救不了。
- **温度要压低**。默认 0.7 会出现幻觉出的工具名，0.4 以下明显稳。
- **版本漂移**。llama.cpp 升级后 chat template 行为会变，升级前固定版本，升级后重跑压测集。
- **部分卸载是伪优化**。显存不够时分层卸载 `-ngl`，速度会塌方，不如直接换小一号的模型。

## 可复用建议

- 沉淀一个最小压测集（任务清单 + 期望的工具调用），任何变更前后各跑一遍，比任何公开 benchmark 都贴近你的真实场景。
- 路由策略明确化：本地模型接批量、隐私类任务，难推理仍走云端，模型 fallback 正好承接这个分工。
- 显存永远留 1~2GB 余量，给上下文峰值。
- 模型文件保留带版本号的文件名，回滚方便。

## 总结

12GB 显存 + 14B Q4 量化，是当前家用机跑 Agent 工作模型的甜点位。真正的工程量不在"把模型跑起来"，而在让工具调用可靠、让压测和 fallback 成为习惯。本地模型的价值，是用工程手段把"够用"变成"可依赖"。
