## 背景

Agent 的可靠性不取决于它多聪明，而取决于它调用的外部依赖有多脆。OpenClaw 里一个典型的 agent 任务往往串着好几个 MCP tool：搜索、数据库、第三方 SaaS API。这些 API 的可用性从来不是 100%，超时、限流、5xx 是日常。人操作时挂了会等一会儿再试，agent 不会——它默认拿到什么就信什么。

## 问题

实际跑 agent 时最常见的三类故障表现：

1. 工具抛异常直接打断主循环，任务死在半路，中间状态全部丢失；
2. agent 收到错误后"脑补"一个结果继续跑，最后自信地汇报成功；
3. 无脑重试放大故障：不带退避的重试把限流打成雪崩，或对下单、发消息这类非幂等操作重试造成重复提交。

## 做法

核心原则：把错误恢复做在工具层，不要指望模型自觉。步骤如下：

1. **每个 tool call 显式设超时**。宁可 10 秒失败，不要让 agent 挂 120 秒。
2. **错误结构化返回**。不要抛异常，返回机器可读的错误对象，例如 `{"error":"rate_limited","retryable":true,"retry_after":30}`。agent 看得懂错误类型，才能做出"重试 / 降级 / 上报"的正确分支。
3. **限定重试策略**。只重试瞬态错误（429、5xx、超时），指数退避加抖动，最多 2~3 次。401、参数错误这类不要重试，直接失败。
4. **熔断与降级**。同一工具连续失败 N 次就标记不健康，后续调用直接走 fallback：读缓存、切备用 API，或如实告诉用户"这个数据源暂时不可用"。
5. **写操作加幂等键**。所有产生副作用的调用带上唯一 idempotency key，重试才是安全的。
6. **多步任务做检查点**。每完成一步把状态落盘，失败后从断点续跑，而不是从头再来。
7. **在 system prompt 里写死规则**：工具报错时必须如实转述错误，禁止编造结果。

## 踩坑点

- **重试所有错误**：最贵的学费。401 重试一百次也不会通，只会烧 token。
- **退避不加抖动**：多实例同时重试，形成同步波次，把正在恢复的服务再打挂一次。
- **错误信息太模糊**：只返回 "request failed"，agent 无从判断，只能瞎猜。错误对象里务必带错误码和建议动作。
- **超时设太长**：上层 agent 循环被阻塞，用户侧表现为"卡死"。
- **只测 happy path**：上线前用 mock 注入 500 / 429，观察 agent 是重试、降级还是编结果，这一步能暴露 80% 的问题。

## 可复用建议

- 给所有 MCP tool 包一层统一错误 schema，`retryable` 字段是关键。
- 默认参数起步：timeout 10s、max_retries 3、backoff 1s 起步 ×2、熔断阈值连续 5 次失败。
- 把每次 tool call 的结果（成功 / 错误码 / 耗时）记日志，复盘时你会感谢它。
- 幂等键直接用「任务 ID + 步骤序号」拼接，够用。

## 总结

外部 API 挂了不是异常，是常态。好的 agent 架构把"失败"当成一等公民：工具层兜住超时和重试，用结构化错误给模型一个可决策的接口，用幂等和检查点保证重试安全。模型负责判断，工程负责兜底——别让 agent 在故障时刻自由发挥。
