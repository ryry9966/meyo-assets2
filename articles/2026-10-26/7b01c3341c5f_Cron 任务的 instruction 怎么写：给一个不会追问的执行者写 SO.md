## 背景

OpenClaw 的 cron / 定时任务是我们用得最多的自动化能力之一：每天汇总 GitHub 通知、巡检 issue、定时抓数据落盘、给群发日报。它和交互会话有两个本质区别：

- **冷启动**：每次运行都是新会话，没有上下文记忆；
- **无人澄清**：跑的时候你不在场，agent 遇到模糊点不会来问你。

所以 cron 的 instruction 不是 prompt，而是一份**交接文档**——你要把所有信息一次性交底给一个不会追问的执行者。

## 问题：按聊天 prompt 写 cron 会翻车

典型写法：「每天早上帮我看下 GitHub 通知，有重要的告诉我。」上线后通常出现三类问题：

1. **输出漂移**：今天是列表，明天是散文，后天带上了表情包式点评；
2. **范围失控**：「重要」由 agent 自行裁量，有时漏报有时刷屏；
3. **静默失败**：MCP 工具报错后，agent 不好意思交白卷，编一段看起来正常的总结。

根因都一样：聊天 prompt 默认有上下文、有追问机会，cron 任务两者都没有。

## 做法：六段式模板

我们内部沉淀了一个固定结构，直接给例子：

```
[任务] 每天 09:00（Asia/Shanghai）汇总 GitHub 未读通知中的 issue/PR 动态。
[数据源] 只用 github MCP 的通知接口；不要浏览网页，不要用其他来源。
[步骤] 1) 拉取通知列表 2) 过滤 issue/PR 类型
       3) 与 state/last_seen.txt 中的时间戳比对，只处理新增
       4) 处理完成后更新该文件。
[输出] 固定三段：未读总数 / 需要我回复的（repo、标题、一句话原因）/ 仅提及我的。
       总长不超过 20 行。
[异常] 接口失败：发送"通知接口失败：<错误摘要>"；列表为空：发送"今日无新通知"。
       任何情况下不要编造条目。
[禁止] 不回复消息、不执行写操作、不自行决定跳过本次。
```

关键点逐条说：

- **任务**里写死时区和绝对时间，别用「今天早上」；
- **数据源**明确到具体工具和路径，冷启动的 agent 什么都不知道；
- **步骤**里必须有状态比对和落盘，这是去重的基础；
- **输出**是契约，格式和长度都锁死，下游（人还是脚本）才好接；
- **异常**分支比正常分支更重要，把「失败长什么样」提前定义好；
- **禁止**用来收窄权限，定时会话尽量只读。

## 踩坑点

- **写「不确定就问我」**：没人应答，任务空转。所有分支必须写死。
- **依赖记忆不落盘**：上一次处理到哪了，必须进文件，读—比对—更新—写回，缺一步就会重复推送或漏报。
- **输出不设上限**：数据一多 token 就失控，行数上限要写进 instruction。
- **无更新时静默**：建议每次都发一条，哪怕是「无更新」。静默即故障，「多久没收到」本身就是监控信号。
- **状态文件不防崩**：先完成任务再更新状态文件，别反过来，否则中断后会漏处理。
- **一个 cron 塞多个任务**：拆成多个小任务，或者先跑一个前置任务产出中间文件，主任务只做汇总。

## 可复用建议

1. **上线前手动触发 3–5 次**，覆盖正常、空数据、工具失败三条路径，再挂调度。
2. **让 agent 把关键中间结果 append 到日志文件**，排障不用靠猜。
3. **像 code review 一样迭代 instruction**：跑一周，把漂移的输出格式钉死，再跑一周。
4. **权限最小化**：定时会话默认只读，写操作单独走需要确认的任务。

## 总结

Cron instruction 的本质，是给一个没有现场记忆、也不会追问的执行者写 SOP。把数据源、输出契约、异常分支、状态落盘这四件事写清楚，定时任务就能从「碰运气」变成「可运维」。它值得你像对待代码一样花时间打磨。
