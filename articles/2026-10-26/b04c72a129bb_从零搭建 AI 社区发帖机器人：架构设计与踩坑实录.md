# 背景

社区运营有个老问题：好内容散落在 issue、群聊和文档里，没人有精力每周整理成帖。于是我给 OpenClaw 挂了个定时任务，做了一个发帖机器人：每周从指定信源抓取动态，生成一篇 digest 帖，经审核后发到社区。跑了一个多月，这里把架构和踩过的坑记录一下。

# 问题定义

动手前先明确了三条硬约束，后来证明这三条决定了整个架构：

1. **内容可溯源**：帖子里出现的每个链接、数字必须来自抓取结果，不允许模型自由发挥；
2. **频率可控**：宁可少发不能刷屏，发布前必须有去重和限额检查；
3. **故障可见**：机器人挂了必须主动报错，而不是安静地“看起来在运行”。

# 总体架构

按数据流分成六层，每层一个独立模块：

- **触发层**：OpenClaw 的 cron/heartbeat，固定时间唤起 agent；
- **抓取层**：两个 MCP tool，分别封装 RSS 解析和社区 API，只返回结构化 JSON；
- **生成层**：prompt 模板 + 白名单信源，要求模型只基于抓取结果写作；
- **审核层**：规则校验（域名白名单、长度、标签范围）+ 一轮 LLM 自查；
- **发布层**：论坛发帖 API 封装成第三个 MCP tool，带幂等键；
- **状态层**：SQLite 存已发布帖子的内容哈希、时间戳和运行日志。

关键决策是：**agent 只负责“决策和写作”，所有副作用（抓取、发帖、查重）收敛到 MCP tool 里**。这样排障时可以绕过模型直接测工具。

# 踩坑实录

**坑一：语义重复没拦住。** 最初只按标题哈希去重，第二周就发了两篇内容高度相似的帖——信源更新了，但可写的变化很小。后来改成把“新内容 + 已发内容摘要”一起送进审核层做相似度比对，阈值卡在 0.85 才放行。

**坑二：重试导致重复发帖。** 网络超时后 agent 重试，论坛端其实已成功，出现双帖。解法是发帖 tool 先用幂等键（信源周期 + 日期）查库，命中就直接返回已有帖子 ID，不真正调用发帖接口。

**坑三：静默失败最伤人。** 有次论坛 API 改了返回结构，工具解析报错，但 cron 本身正常退出，机器人“健康”地空转了三天。加了两件事：每次运行无论成败都写一条心跳记录；连续两次无成功发布就推送告警消息给我。

**坑四：上下文膨胀。** 一开始把整个 issue 列表塞进上下文，token 消耗大且模型经常漏项。改成抓取层先做筛选和摘要，只把候选条目（每条不超过三行）交给生成层，成本降了一个量级。

**坑五：标签幻觉。** 模型会发明论坛不存在的标签，导致发帖失败。把标签改成从枚举列表中选择，校验不过就默认落到“综合讨论”。

# 可复用建议

- **先 dry-run 两周**：所有产出只写日志不发帖，人工确认质量后再放开发布权限；
- **幂等键必须落在工具层**，不要指望模型“记得”自己发过什么；
- **副作用全部收敛为 MCP tool**，保持 agent 逻辑可单独测试；
- **假定任何外部 API 都会变**，解析失败要显式报警，而不是抛进日志就完事；
- **给 LLM 调用设每日预算上限**，防止循环重试烧钱。

# 总结

这个机器人代码量不大，难点全在工程细节：幂等、去重、可观测性。最大的心得是——不要让 agent 直接做有副作用的事，把它降级为“决策者”，把“执行者”做成可测试、可重放的工具。对想练手 OpenClaw + MCP 的同学，发帖机器人是比问答机器人更好的切入点，因为它是真的会在生产环境里翻车的那种项目。欢迎在评论区交流你们的定时任务实践。
