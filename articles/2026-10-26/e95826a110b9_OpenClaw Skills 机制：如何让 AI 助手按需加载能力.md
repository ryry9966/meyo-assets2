## 背景

Agent 的上下文窗口是稀缺资源，能力怎么组织，直接决定了成本和稳定性。OpenClaw 的 Skills 机制采用的是渐进式披露（progressive disclosure）：每个 skill 是一个目录，会话启动时只向模型注入它的 `name` 和 `description` 两行元数据；只有当模型判断当前任务与描述匹配，才会用读文件工具加载完整的 SKILL.md 正文。常驻成本极低，能力上限不缩水。

## 问题：让能力"常驻"通常是错的

常见的反模式有两类。一是把所有操作说明塞进 system prompt，几千 token 每次会话都付一遍，低频能力还在高频任务里制造噪音；二是挂一堆 MCP server，光工具 schema 就占掉大块上下文，指令之间还会互相串扰——模型把 A 场景的规则错用到 B 场景。Skills 机制就是针对这个矛盾设计的。

## 做法：写一个最小可用的 skill

1. **建目录。** 在 workspace 下的 `skills/` 里建子目录，如 `skills/meeting-notes/`，目录名用小写加连字符。
2. **写 SKILL.md。** frontmatter 里给 `name` 和 `description`。description 是整个机制的命门：用第三人称写清楚"这个 skill 做什么、什么时候该用"，把你期望用户说出的关键词自然嵌进去。例如："整理会议录音转文字稿并提炼行动项。当用户提到会议记录、待办梳理时使用。"
3. **分层放内容。** 正文控制在几百行内，只写决策流程和注意事项；大块参考资料（模板、长示例）拆到同目录的独立文件，正文中指明"需要时读取"；确定性操作写成脚本放 `scripts/`。

验证方法：准备两组 prompt，一组应触发、一组不应触发，重载后各跑一遍，看命中是否精准。也可以用 skills 列表命令确认加载状态。

## 踩坑点

- **description 太泛**：几乎所有任务都命中，正文变回常驻上下文，等于白做；**太窄**则永远不触发。写完先自测。
- **name 与目录名不一致**，部分版本会静默不加载，排查时先看这里。
- **别把 API key 写进 SKILL.md**——它会被读进上下文。密钥走环境变量。
- 避免正文里出现"永远""一律"这类全局指令，会泄漏到不相关任务。限定为"当处理 X 类型输入时"。
- **别假设脚本会自动执行。** 脚本只是普通文件，模型必须主动调用，正文要写清调用时机和参数格式。
- skill 数量失控后，光 description 就能吃掉几百 token。超过二三十个就该合并或清理。

## 可复用建议

- **一个 skill 只做一件事**，职责模糊时宁可拆开。
- 确定性步骤交给脚本，判断类内容写散文；别用散文描述本该脚本化的流程。
- 分工要清楚：MCP 适合实时数据、需要鉴权的外部 API；Skills 适合流程性知识和团队规范。两者不要互相替代。
- 把 `skills/` 目录纳入 git，改动走 PR 评审——它本质上是给模型看的代码。
- 维护一个小型触发测试集，每次改动后回归，防止"改了 A 坏了 B"。

## 总结

Skills 的价值不在"多"，而在"准"。它的本质是上下文工程：把有限的注意力预算，花在当前任务真正需要的那部分知识上。description 写得越接近一句真实的用户意图，按需加载就越可靠。把 skills 当成需要持续经营的资产，而不是一次性配置，收益会随时间复利。
