## 背景

做 Agent 自动化绕不开一个问题：助手怎么“知道”该干活了？OpenClaw 的答案是 heartbeat——按固定间隔向 agent 注入一次轻量心跳提示，由它对照检查清单决定是否有事可做。这是典型的轮询模型。社区里经常有人问：为什么不直接上 webhook/事件推送，事件驱动不是更优雅吗？

## 问题

两种模型的真实成本经常被低估：

- **轮询**：延迟上限等于间隔。间隔调短，token 消耗线性上涨——每次心跳都是一次完整的模型调用，哪怕结论只是“无事发生”。检查项里若还涉及 MCP 工具调用，成本更高。
- **推送**：延迟低，但要求 agent 网关有可公网到达的入口、稳定鉴权、以及能扛住重启断网的事件缓冲。个人部署场景里，这三样往往都缺。

一句话概括：轮询用 token 换简单，推送用复杂度换延迟。

## 做法

我的取舍原则是：**轮询做骨架，推送做肌肉**。

1. **给任务按延迟容忍度分级**。分钟级可容忍的（日志巡检、邮件摘要、清单核对）全走 heartbeat；秒级敏感的（CI 失败告警、即时回复）才考虑外部触发。
2. **心跳侧收敛**：检查项写进 `HEARTBEAT_CHECKLIST.md`，只留“值得唤醒”的事。约定无事时返回最小响应，避免每次心跳都往会话里灌噪音。
3. **高频检查下沉给哑组件**：用 cron/脚本做秒级或分钟级的原始轮询（探针、文件 mtime、API 状态码），只有命中条件时，才通过 CLI 把一条消息投给 agent。模型只处理“已确认有事”的场景。
4. **真需要推送时，webhook 接收端做薄**：验签、去重、落盘到本地队列文件就返回 200，由心跳周期或直接投递消费。接收端不跑任何推理逻辑。

## 踩坑点

- **心跳间隔贪短**：30 秒一次，一天 2880 次调用，账单和上下文污染双杀。从默认间隔起步，按清单命中率往上调。
- **响应不设最小化约定**：agent 每次心跳都礼貌汇报“一切正常”，频道很快被刷屏。
- **webhook 裸奔**：没有验签和限流的接收端等于公开写接口，至少上 HMAC 校验加来源限制。
- **假设网络永远在线**：笔记本合盖、容器重启都会丢事件。没有落盘队列的推送，可靠性反而不如最笨的轮询。
- **事件风暴**：上游抖动触发重试会造成重复投递，消费端必须幂等，用事件 ID 或时间戳去重。

## 可复用建议

- 画一张三列决策表：延迟容忍度 × 事件频率 × 是否需要模型判断。绝大多数格子的答案是“哑轮询 + 条件唤醒”。
- 把“唤醒模型”当成系统里最贵的操作：能用 grep 和脚本判断的事，别用 token 判断。
- 心跳是兜底不是主通道：它保证“没人推也能活”，推送只是加速器。

## 总结

轮询 vs 推送不是二选一，而是分层：heartbeat 提供存活保证和简单性，外部触发提供低延迟，两者通过本地队列和解耦的接收端衔接。对个人与中小团队部署，先用好 OpenClaw 自带的心跳机制，把复杂度留给真正需要它的那一两个场景，是性价比最高的路径。
