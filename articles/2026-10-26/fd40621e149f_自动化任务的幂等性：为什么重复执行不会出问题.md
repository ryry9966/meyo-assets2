## 背景

跑自动化的人迟早会撞上同一件事：任务被重复执行了。定时器抖动、webhook 重试、Agent 自行决定重跑某个 MCP 工具调用、失败后你手动再触发一次——触发源五花八门，结果往往一样：数据库多了重复行、群里发了两条同样的通知、issue 系统里出现三张相同的工单。

幂等性（Idempotency）解决的就是这个：同一个任务执行一次和执行多次，最终状态一致。

## 问题出在哪

多数自动化脚本的写法默认"只跑一次"：

- 追加式写入（append、无唯一约束的 INSERT）
- 递增/递减类操作
- 对外部系统发"创建"类请求（发消息、建工单、下单）

这类操作天然不幂等。而重试不是异常路径，是自动化的常态——网络超时、调度器的 at-least-once 语义、Agent 的自主重试，都会让"跑一次"变成"跑 N 次"。

## 做法

1. **给任务一个稳定的键**。键从触发上下文派生，而不是运行时随机生成。比如每日同步 issues 的任务，键就是 `hash("sync-issues" + 当天日期)`，重跑三次键也相同。
2. **先写记录，再执行动作**。执行前把任务键写入持久化状态（SQLite 一张表、一个 JSON 文件都行），用唯一索引 `INSERT OR IGNORE`。插入成功才继续；失败说明已跑过，直接跳过。
3. **把非幂等写改成幂等写**。append 改 upsert，"创建"改"按业务键创建或更新"。很多 API 支持 idempotency key，用上它。
4. **区分意图与完成两个状态**。先标 `started`，动作成功后再标 `done`。重启后扫描到"started 但未 done"的记录，做补偿或清理，而不是无脑重跑。

## 踩坑点

- **检查和写入不原子**。"先查有没有、再执行"在并发下会双跑。必须依赖数据库唯一约束，不能靠应用层 if 判断。
- **键里混入了当前时间**。用 `now()` 而不是调度槽位时间派生键，每次重试键都不同，去重形同虚设。这是最常见的错误。
- **完成标记写早了**。动作没完成就标 done，进程一挂，任务永远不会重跑。顺序必须是：started → 执行 → done。
- **状态只存内存**。重启后去重状态清零，等于没做。状态必须落盘或进外部存储。
- **Agent 侧的键不稳定**。LLM 重试时若每次重新生成参数，键就变了。键的输入必须是稳定的业务字段，不能包含随机数或临时变量。

## 可复用建议

- 默认假设"任何任务都会跑两次"，按这个前提设计写入逻辑。
- 固定一个模式：稳定键 + 唯一索引 + started/done 两阶段标记，几十行代码就能复用到所有插件和定时任务。
- 验证方式很朴素：把同一个任务连跑两遍，diff 结果。一致才算幂等。
- 日志里带上任务键，出问题时能直接回答"是否重复执行过"。

## 总结

幂等性不是额外负担，而是自动化的安全垫。在 Agent 和插件生态里，触发是模糊的、重试是常态的，"跑两次等于跑一次"是性价比最高的可靠性投资。下次写自动化任务时先问自己一句：如果这条消息被投递两次，我的系统会变成什么样？
