## 背景

跑 OpenClaw 或 Agent 自动化一段时间后，你会发现一个规律：任何任务都迟早会被重复执行。cron 重叠、webhook 重投、MCP 调用超时后 Agent 自行重试、人工“再跑一遍看看”……重试不是异常，是常态。所以问题从来不是"怎么避免重复执行"，而是"重复执行时怎么不出事"。这就是幂等性：同一操作执行一次和执行 N 次，最终状态一致。

## 问题

非幂等操作在重试下的典型翻车：

- 发消息类工具：超时重试后，群里连发三条同样的内容
- 创建资源类工具：工单、日历事件、云资源被重复创建
- 追加写：同一文件被 append 两次，数据翻倍
- 状态累加：计数器、余额被重复加减

共性是：这些都是"做一次加一次"的命令式动作，而自动化系统天然会在你不知情时把它们做多次。

## 做法

按三步把任务改造成幂等的：

1. **分类**。把任务里每个副作用标注为幂等（查询、覆盖写、设状态）或非幂等（创建、追加、累加），只处理后者。
2. **设计确定性幂等键**。键必须从业务语义推导，比如 `task_id + 逻辑日期 + 目标对象`，而不是时间戳或随机 UUID——后者每次都不同，等于没防。
3. **先写意图，再执行**。用一张执行日志表配合唯一约束：

```sql
CREATE TABLE job_log (
  idem_key   TEXT PRIMARY KEY,
  status     TEXT,   -- running / done
  updated_at INTEGER
);
```

任务启动时先 `INSERT`，冲突说明跑过或正在跑，直接跳过；执行完把 status 改为 done。这样超时重试、并发触发、人工重跑都只会命中同一把锁。

再配两个习惯：能用 upsert 就不用 insert；能"把状态设为目标值”就别"执行一次动作"。前者天然幂等，后者让重复执行变成无效操作。

## 踩坑点

- **检查-再执行的竞态**：先 SELECT 再 INSERT，并发下两个进程都可能通过检查。必须靠数据库唯一约束或锁兜底，不能只靠代码判断。
- **幂等键混入随机因素**：时间戳、UUID、自增序号都会让重试变成"新任务"。
- **整体幂等 ≠ 步骤幂等**：任务跑到一半挂了，重跑面对的是"半成品"状态。要么每个步骤单独幂等，要么整体设计成对账式——每次运行都把世界修正到目标状态。
- **超时不等于失败**：请求可能已成功、只是响应丢了。没有幂等键就盲目重试，是重复创建的最大来源。下游 API 支持幂等键就一定带上。
- **锁不能替代幂等**：锁只防并发，不防"上次失败后重跑"，两者都要有。

## 可复用建议

- 单机部署直接用 SQLite 的 `INSERT OR IGNORE` + 执行日志表，十几行代码解决大部分问题。
- 封装一个 `ensure_once(key, fn)` 帮助函数，让所有带副作用的工具调用走同一入口。
- 在 MCP 工具描述里写明该工具是否幂等，Agent 规划重试时才有依据。
- 日志里始终带上幂等键，排障时能快速对齐"是哪次执行"。
- 心法：把任务写成声明式的"收敛到目标状态"，而不是命令式的"执行动作"。前者重跑一百次都安全。

## 总结

幂等性不是锦上添花，而是自动化的入场券。重试、并发、人工干预迟早发生，区别只在你有没有提前兜住。一个确定性键、一张执行日志表、一个"设状态而非做动作"的习惯，成本很低，换来的是敢让任务随便重跑的底气。
