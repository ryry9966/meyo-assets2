## 背景

Agent 跑久了，记忆条数从几十涨到几千，`memory_recall` 的检索质量直接决定助手"记不记得住"。条目少的时候怎么搜都能命中，一旦上量，检索方案的选择就开始真实地影响回复质量。我们在自己的 assistant 上把语义搜索（embedding + 向量召回）和全文搜索（FTS5 关键词）各跑了一段时间，记录一下对比结论和最终做法。

## 问题

三个典型翻车场景：

1. **语义搜不到精确 token**。用户问"那个 ERR_1042 怎么处理"，向量召回把措辞相似但编号不同的错误全排在前面，精确编号反而沉底。
2. **全文搜不到换说法的查询**。用户问"上次那个部署脚本的路径"，原文存的却是 "release.sh 在 /opt/ci/ 下"，关键词完全对不上。
3. **不分新旧**。半年前的旧结论经常压过昨天刚写入的修正版。

单用任何一路，都会在不同场景里各自失灵。

## 做法

最终方案是双路混合，流程不复杂：

1. **存储层**：每条记忆 = 正文 + metadata（`created_at`、来源会话、topic tags）。一个事实一条，不做大段拼接。
2. **索引层**：SQLite FTS5 建全文索引，sqlite-vec 存本地 embedding，零外部依赖。
3. **查询侧分流**：先从 query 里抽精确 token（编号、路径、命令、专有名词）。含精确 token 的走全文加权，纯自然语言走语义召回，不确定就两路都跑。
4. **融合**：用 RRF（Reciprocal Rank Fusion）合并两路排名，k 取 60。不要直接平均分数——两路分数量纲完全不同。
5. **重排**：RRF 分数 + 时间衰减，再按 tag 过滤。
6. **top-k 控制在 3~5 条**，宁少勿多。

另外准备了一个 20~30 条 query→memory 的黄金评测集，每次调参数跑一遍命中率，避免"感觉变好了"。

## 踩坑点

- **FTS5 默认分词器对中文基本不可用**，整句会被切成一个 token。用 trigram 或者接 jieba，这一步不做中文全文等于没做。
- **chunk 粒度**：一段太长，embedding 被稀释；切太碎，丢上下文。按"一条记忆承载一个事实"切最稳。
- **语义检索的"看起来相关"陷阱**：措辞相似但属于不同项目的记忆会被高置信度召回，只靠语义路会翻车。
- **换 embedding 模型 = 全量重建索引**，提前把 reindex 脚本写好，别到时候手搓。
- **top-k 给太大**会污染上下文窗口，模型注意力被无关记忆带偏，回复质量反而下降。
- 双路 + 重排会增加几十毫秒延迟，embedding 可以在写入时算好缓存，查询侧只算 query 一次。

## 可复用建议

- **先全文、后语义**。全文零依赖、结果可解释、调试直观；实测命中率不够再加语义，不要一上来就堆向量库。
- 混合检索用 **RRF 合并排名**，别做原始分数加权。
- 每条记忆务必带 metadata，**先过滤、后排序**，时间衰减默认打开。
- 留一份 **recall 日志**（query、命中条目、是否被采纳），线下复盘 miss 案例是迭代检索质量最快的路径。
- 评测集常备，改动前后必跑。

## 总结

语义搜索解决"换了个说法还记得"，全文搜索解决"精确 token 一击命中"，两者覆盖的失败模式几乎不重叠。生产上最稳的组合是：FTS5 打底 + 语义召回补盲 + RRF 融合 + 时间衰减 + 一个小评测集兜底。先跑通全文，按需加语义——检索这块，简单方案跑通之后再做加法，比一开始就上重架构划算得多。
