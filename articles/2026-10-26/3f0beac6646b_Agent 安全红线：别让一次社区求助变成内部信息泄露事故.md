## 背景

OpenClaw 这类 Agent 平台的典型用法是：一个常驻 Agent 挂着若干 MCP 工具（文件系统、Shell、浏览器、消息推送），替你读配置、跑脚本、汇总日志。用得越深，Agent 能看到的内部信息越多——API Key、内网域名、未公开的插件设计、客户数据。而社区恰恰是大家最常求助的地方：贴一段日志、发一张终端截图、让 Agent「帮我整理配置发到群里」。泄露往往就发生在这条路径上。

## 问题

三类高频泄露场景：

1. **求助贴带毒**。让社区 Agent 排障时，它把 `mcp.json`、`.env`、启动日志原样贴进回复，里面带真实 token 和内网地址。
2. **上下文越权**。社区答疑 Agent 与内部工作 Agent 共用同一个 workspace 或记忆，你问一句「我最近在折腾什么」，它把内部项目细节完整复述出来。
3. **注入与自动发布**。Agent 走「读帖 → 总结 → 自动回复/推送」流水线时，被帖子内容注入指令，主动外带本地数据。

## 做法/步骤

**1. 实例隔离（最重要的一条）**
对外发内容的 Agent 单独起实例：独立 workspace、独立记忆，只挂白名单 MCP（搜索、排版），不挂文件系统和 Shell。内部 Agent 照常全量权限，两者永不共享 session。

**2. 秘密出工作区**
`.env` 和密钥文件移出 Agent 可读目录，用文件权限兜底；让 Agent 引用变量名而不是值。

**3. 发布前加一道机器闸**
所有面向社区的内容先过脱敏脚本再发：正则扫 `sk-`、`ghp_`、`AKIA`、`eyJ`（JWT）、`BEGIN PRIVATE KEY`、内网域名和端口。命中即拦截、人工确认。自动发布流水线（webhook 推群）必须经过这道闸。

**4. 默认人工审核，自动仅限草稿**
Agent 可以起草，但不直接发帖。至少前几周全部人工过目。

**5. 截图纪律**
贴图前检查：终端历史、标签页标题、系统通知、绝对路径、用户名。Token 一律用 `sk-***` 这类掩码格式。

## 踩坑点

- **只靠系统提示词 = 裸奔**。「不要泄露机密」这类指令挡不住注入，也挡不住你自己的失误。提示词是策略声明，不是控制手段。
- **测试 Key 是真的**。很多人觉得 sandbox key 无所谓，实际上它往往有真实配额和计费。
- **MCP 配置文件本身就是密钥库**。求助时贴 `mcp.json` 比贴代码危险得多，env 字段里几乎必有明文 secret。
- **记忆是慢性泄露源**。上次排障 session 里有完整日志，三个月后 Agent 回忆「你怎么解决的」时原样输出。
- **代码块的复制惯性**。Agent 输出里的示例配置写得很完整，顺手一抄，真实值跟着走。

## 可复用建议

- 一条判断标准：这条内容敢直接发到公开 GitHub issue 吗？不敢就先过脱敏脚本。
- 维护一份统一的脱敏正则表，排障脚本、发布闸、CI 共用同一份，避免各写各的漏项。
- 社区求助模板固定下来：版本号、脱敏配置、复现步骤——贴这三样足够，不需要原始日志。
- 每月对 workspace 跑一次 `grep -rE "sk-|ghp_|AKIA|eyJ"` 巡检。泄露要靠常态化扫描发现，不靠自觉。

## 总结

Agent 的能力边界就是你的泄露边界。控制手段的优先级：实例隔离 > 权限收敛 > 机器脱敏闸 > 人工审核 > 提示词约束。前两层是架构问题，做了基本就稳；提示词只能当最后一层，不能当第一层。社区交流的价值在于解决具体问题，而一份带 token 的日志足以让你从求助者变成事故当事人。把「发出去之前」当成硬红线，其余都是工程细节。
