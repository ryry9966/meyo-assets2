## 背景

OpenClaw 生态里，Agent 的能力很大程度上依赖外部服务：搜索、数据库、各类 MCP 工具、HTTP 插件。这些依赖注定不可靠——限流、5xx、超时、证书抖动、上游悄悄改接口。单次调用失败重试就行，但对一个多步 Agent 工作流来说，一次 API 故障可能让整条链路卡死、空转烧 token，甚至诱导模型编造结果。错误恢复不是加分项，是 Agent 工程的基础设施。

## 问题：失败的三种坏姿势

复盘社区里几个出过事故的自动化流程，失败时的典型表现有三类：

1. **无限重试**：模型看到工具报错，自己决定“再试一次”，循环十几次，token 账单翻倍，问题依旧。
2. **幻觉兜底**：工具返回空结果，模型没理解这是失败，顺势编了一段“看起来合理”的数据继续往下走。这比报错更危险。
3. **静默挂起**：没设超时，一个不响应的端点把整个工作流吊死，下游任务排队等一个永远不会回来的响应。

## 做法：四层防线

我们最终沉淀为一个工具层的统一封装，核心原则是：**让重试发生在代码里，而不是模型的决策循环里**。

**第一步，一切调用先加超时。** 单次调用硬超时（比如 10–15 秒），整个工作流再设总预算。超时是所有容错的前提，没有它后面都免谈。

**第二步，错误分类。** 429 / 503 / 超时 / 连接失败 → 可重试；400 / 401 / 404 → 不可重试，重试没有意义。只对可重试错误做最多 3 次指数退避 + 随机抖动。

**第三步，熔断。** 同一端点连续失败 N 次后标记为 degraded，冷却期内直接走降级路径，不再真的发请求。这既保护了上游，也让用户更快拿到失败反馈。

**第四步，结构化错误返回给模型。** 不要抛裸异常，返回 `{ok: false, error_code, retryable, hint}` 这样的结构。模型看到 `retryable=false` 会主动换方案或询问用户，而不是傻等。

降级路径按业务定：读类工具用最后一份缓存，并明确标注“数据为 X 分钟前”；写类工具直接失败并报告，绝不伪造成功。

## 踩坑点

- **重试必须带 jitter**。纯指数退避在多实例并发下会形成同步风暴，一起打挂刚恢复的上游。
- **POST 重试要配幂等键**。否则一次网络抖动可能创建两条订单。写操作的一致性比可用性更重要。
- **熔断状态要考虑进程重启**。简单做法是落盘或写 Redis，否则每次重启都重新撞一遍已经挂掉的服务。
- **别把重试交给模型**。模型重试不可控、不可观测、烧 token。工具代码内解决重试，模型只负责决策“这条路走不通，换哪条”。
- **空 ≠ 失败**。工具失败时必须显式返回错误状态，返回空列表会被模型误读为“没有结果”。

## 可复用建议

- 把“超时 + 分类 + 有界重试 + 熔断 + 结构化错误”做成通用包装器，所有 MCP 工具和 HTTP 插件统一过一遍，别逐个手写。
- 给每个工具暴露健康状态字段，Agent 和监控都能读。
- 用一个可注入 500/超时的 mock 服务做故障演练——容错逻辑不演练等于没写。
- 重试策略外置成配置。不同上游的容忍度差异很大，硬编码迟早要还债。

## 总结

外部 API 一定会挂，Agent 工程要解决的不是阻止失败，而是让失败变成一个清晰、可决策的状态。四层防线——超时、有界重试、熔断、结构化错误——覆盖了绝大多数场景，实现成本不高，收益是工作流从“一挂全死”变成“有损运行”。如果只做两件事，先补超时和幂等：这两项最便宜，也最救命。
