# 背景

OpenClaw 里的 agent 默认是被动应答：有消息进来才跑一次。但真正好用的助理需要主动性——定时日报、邮箱巡检、监控告警跟进。OpenClaw 用 heartbeat（心跳）解决这件事：agent 每隔 N 分钟被唤醒一次，读一遍工作区的 `HEARTBEAT.md` 清单，判断有没有值得做的事。

但“什么时候醒”其实有两条路线：**轮询**（定时唤醒主动看）和**推送**（事件发生时外部触发）。选型直接影响 token 成本、实时性和工程复杂度。

# 问题

- **轮询**：简单可靠、不会漏周期性任务，但空转烧 token——每次唤醒哪怕啥也不做，也是一次模型调用；实时性受间隔限制。
- **推送**：webhook、文件监听、消息队列触发，实时性好、不空转，但要处理并发冲突、事件防抖、安全暴露面，而且“没有事件时”它什么都不做——“每小时检查一次日历冲突”这类任务天然不适合事件驱动。

单选一边都有明显短板。

# 做法：轮询做骨架，推送做触发器

我的配置分三层：

1. **低频轮询兜底。** 心跳间隔设 30 分钟，`HEARTBEAT.md` 只写必须周期检查的条目。关键是在心跳提示词里加一条硬规则：没有值得做的事就直接返回 OK，不输出长文。
2. **便宜的前置门禁。** 唤醒后先跑一段不调模型的规则判断：事件队列文件是否为空、是否在静默时段、距上次动作是否够久。通过了才进模型调用，空转成本从“一次 LLM 调用”降到“一次文件读取”。
3. **推送只给真实时事件。** 告警、关键词命中的邮件走 webhook 写入事件队列文件，带 5 分钟去抖窗口合并同类事件。紧急事件立即唤醒 agent；非紧急的留给下一次心跳统一消化——agent 永远单线程消费队列，避免并发会话打架。

# 踩坑点

- 心跳提示词写得太模糊，模型每次都想“找点事做”，出现过幻觉任务。清单必须写成可判定的条目，宁可少不可泛。
- 推送高峰把事件队列写爆，agent 处理失败又没设重试上限，队列无限增长。后来加了重试上限和死信文件。
- webhook 直接暴露公网等于给 agent 开了个无鉴权入口。至少做签名校验，或只绑定网关本机。
- 心跳定时器在进程重启后丢失，静默时段没考虑时区，凌晨三点被唤醒给用户发消息。

# 可复用建议

- 轮询是默认骨架，只有“延迟超过一个心跳间隔就不可接受”的事件才值得配推送。
- 事件处理必须幂等：推送和心跳可能让同一事件被碰到两次。
- 把每次心跳的“做/不做”决策记进日志，跑一周再回头调间隔和清单，比一开始凭感觉猜准确得多。

# 总结

轮询 vs 推送不是二选一，而是分层：轮询保证“不会漏”，推送保证“够快”，便宜的前置判断保证“不烧钱”。OpenClaw 的心跳机制足够开放，配合 MCP 工具和事件文件，十几行配置就能搭出这套混合模型，成本和实时性都能拿到。
