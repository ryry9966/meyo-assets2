# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

Agent 接上 MCP 和插件之后，能力上限往往不取决于模型，而取决于你敢给它开哪些工具。实践里常见的两种失败：一种是事事请示，一个改配置的任务中断五次，自动化形同虚设；另一种是图省事直接放开 `shell` 权限，agent 自作主张删了目录、把消息发给了错误的人。这不是"要不要人机确认"的问题，而是缺少一条事先画好的边界线。

## 问题

多数框架的权限模型停留在工具级：允许或禁用某个 tool。但风险实际由参数和上下文决定——同一个 HTTP 工具，GET 一份文档和 POST 一笔付款完全是两回事；`gh pr create` 和 `gh pr merge` 的风险等级也天差地别。边界必须定义在"操作"粒度，而不是"工具"粒度。

## 做法：四步落地

**1. 按"爆炸半径 × 可逆性"给操作分级。**
- 只读、本地、可回滚：直接执行；
- 写入但可回滚（本地文件改动、开分支、写草稿）：直接执行并记录；
- 有对外副作用但可补救（发消息、建 issue、调内部 API）：默认干跑，输出计划让人确认一次；
- 不可逆或高影响（删数据、生产部署、花钱、群发）：逐次确认，没有例外。

**2. 用工具切分落实分级。** MCP server 按读写拆成两组挂载；写操作封装成独立 tool 并接确认钩子；外部访问走域名白名单。特别提醒：不要给裸 `run_shell`，它会让你前面定义的所有策略失效。

**3. 计划审批优先于步骤审批。** 长任务先让 agent 产出操作清单（含 diff、影响范围和回滚方式），人批一次计划，之后执行不再逐步打断。审批对象应该是"即将发生的真实调用"，干跑和实跑必须走同一条链路，否则审批没有意义。

**4. 写死升级规则。** 重试超过 N 次、指令有歧义、参数落在白名单之外 → 停下来问人。宁可多问一次，不允许 agent 自己找替代路径绕过。

## 踩坑点

- **确认疲劳**：问得太频繁，人就会闭眼点"允许"，比不问更危险。少问，但每次都值得看。
- **deny 不是真 deny**：禁了写 API，agent 换 shell 的 `echo` 绕过去。拒绝必须是跨工具的语义级拒绝，否则只是把风险挪了个位置。
- **没有审计日志**：哪些调用被自动放行没有记录，边界永远调不准。日志是后续放宽权限的唯一依据。

## 可复用建议

- 起步从紧，依据日志逐步放宽：每一次人工确认，都是"这类操作可以自动做"的证据积累。
- 把提问成本降到最低：附上 diff、后果说明和回滚命令，让人十秒内能做决定，而不是抛一句"我可以执行吗"。
- 预算兜底：单次运行限制外部调用次数与金额上限，超限即触发确认。
- 只读工具尽量放开挂载，让 agent 在低风险区域自给自足，把人的注意力留给真正的高危操作。

## 总结

权限边界不是一张静态白名单，而是"影响面 × 可逆性 × 频率"的函数。先分级，再落到工具和参数层面，用计划审批替代逐步打断，配好升级规则和审计日志。目标不是让 agent 更听话或更大胆，而是让每一次"自己干"都发生在你事先画好的圈子里。
