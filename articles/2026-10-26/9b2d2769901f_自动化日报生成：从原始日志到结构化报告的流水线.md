# 自动化日报生成：从原始日志到结构化报告的流水线

## 背景

团队每天需要一份“昨天发生了什么”的日报：服务报错、定时任务失败、部署变更、几个关键指标。这件事不难，但手工整理重复、容易漏，而且每天稳定吃掉一个人十几分钟。这篇帖子记录我搭的一条日志 → 日报流水线，跑了两周后基本无人值守，把思路和踩坑分享出来。

## 问题

改造前的原始状态：

- 日志散在多处：应用日志文件、cron 任务输出、两个内部 API
- 格式不统一，光时间戳就有三种写法
- 直接把原始日志丢给 LLM：上下文塞不下，成本高，且它会“编”细节
- 人工写的日报格式每天不一样，读者抓不住重点

## 做法

整体思路一句话：**统计归代码，叙述归模型**。所有数字必须可复现，LLM 只负责把结构化结果组织成人话。

分四步：

1. **采集**：cron 脚本每天固定时间拉取各来源日志，落到 `raw/YYYY-MM-DD/` 目录。来源各自一个文件，保留原始内容不改写——原始层永远可回溯。

2. **预处理**：第二个脚本做归一化和聚合——统一时间戳为 UTC、过滤 DEBUG 噪音、按规则分类（error / deploy / job-fail / metric），然后对每类做计数、Top N、时间分布统计。输出一份 JSON，这是流水线的中间产物，落盘、可调试。

3. **摘要**：把 JSON 交给 OpenClaw agent。prompt 里只给模板 schema（昨日概览 / 异常事件 / 变更记录 / 待关注四段），要求严格按字段填充。关键指标段由代码直接写入，模型不参与任何计算。

4. **渲染分发**：用固定模板把 JSON + 摘要渲染成 Markdown，通过 webhook 推送到群。发送前查一个记录文件保证幂等，同一天重跑不会重复发。

## 踩坑点

- **时区**：日志里 UTC 和本地时间混用，第一版日报把前天 16:00 的事件算进了“昨日”。现在采集阶段统一转 UTC，展示时再转回来。
- **LLM 算数**：早期让模型“统计错误总数”，同一份输入跑两次差了 3 次。改成代码算完写进 JSON，模型只引用字段。
- **上下文溢出**：某天一个死循环报错刷了 20 万行。预处理里加了对相同错误做签名合并（按 message 归一化去重 + 计数），顺带把 token 成本降了一个量级。
- **静默失败**：webhook 挂了流水线也“成功”退出，连着三天没人收到日报才发现。现在发送失败会重试，仍失败则把错误写进下一次日报的第一段。
- **schema 漂移**：模型偶尔自作主张加字段。解决方式是 prompt 里给空模板让它填空，渲染层再做一次字段白名单校验。

## 可复用建议

- **中间产物一定落盘**。排查问题时直接看预处理后的 JSON，不用重跑模型。
- **模板即契约**。段落和字段固定下来，读者才可能“扫读”，下游想加工（比如汇总成周报）也容易。
- **数据获取走 MCP 工具让 agent 主动拉取**，而不是把大段日志贴进对话。前者可控、可缓存、可复现；后者两者都做不到。
- **给模型输出留降级路径**：调用失败时日报退化为“纯数字版”——有总比没有强。
- **每一步独立可执行**（脚本或子命令），cron 只负责编排，方便单独调试和重放某一天的数据。

## 总结

这条流水线本质上是把“人读日志”拆成“代码读日志 + 模型写人话”。真正花时间的不是接模型，而是预处理规则和 schema 约束这两处笨功夫——但恰恰是它们决定了日报每天是否可信。如果你已经在用 OpenClaw 做其他自动化，建议把日报当成一个带严格输出校验的 agent 任务来接，一天内可以跑通第一版，之后逐步把数据源接进来即可。
