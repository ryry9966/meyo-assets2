## 背景

我们用 OpenClaw 搭了一条内容自动化流：Agent 产出 Markdown 初稿，人工过一遍事实审校，然后发到公众号、掘金和自托管博客。跑了一个多月，最大的感受是：瓶颈不在"写"，而在发布前那段格式折腾——每次都要手工调标题、修代码块、重传图片。

## 问题

两个源头叠加：

1. **平台渲染器差异大。** 公众号不认 Markdown，只接受带内联样式的富文本/HTML；掘金吃 GFM 但会剥部分 HTML；静态博客最宽容，还能吃 mermaid 和数学公式。
2. **AI 输出不受控。** 即便 prompt 里写了要求，模型仍会时不时塞进脚注、mermaid 图、裸 HTML 标签、任务列表，以及指向本地路径的图片链接。

任何一环没兜住，发出去就是格式事故。

## 做法

把发布前的处理拆成四段，每段独立可测：

**1. 上游约束。** 在 Agent 的 system prompt 里明确"允许的 Markdown 子集"：最多三级标题、GFM 表格、标注语言的围栏代码块、引用；明确禁止脚注、mermaid、行内 HTML。同时给一个骨架模板让它填。上游约束一次生效，比下游修补便宜得多。

**2. 归一化。** 用 unified/remark 把稿子 parse 成 AST，跑一遍 lint：节点类型白名单、标题跳级修正、frontmatter 剥离、图片链接是否为外链的检查。核心原则是**把 Markdown 当树处理，别用正则改字符串**。

**3. 平台适配。** 每个平台一个 adapter，输入同一棵 AST，输出目标格式。公众号 adapter 把代码块转成内联样式的 `<pre>`、把标题映射到预设字号；知乎 adapter 直接删掉不支持的节点并记录日志。adapter 全部是纯函数，用 golden file 快照测试锁行为，改一处跑全量对比。

**4. 校验与发布。** adapter 的产物先过断言：无空段落、无残留 frontmatter、图片全部外链、代码块无未闭合围栏。通过后才交给对应的 MCP 工具推送。任何断言失败直接中断并回报，不做静默降级。

## 踩坑点

- 正则清洗嵌套结构（表格里的加粗、列表里的代码）几乎必坏，我们交过学费后才统一改 AST。
- 公众号会剥掉 class，样式必须内联；走剪贴板粘贴会丢代码高亮，改走接口/插件通道更稳。
- 图片必须先传图床并回填链接，否则平台防盗链会让文章挂图。
- 模型偶尔无视约束输出 mermaid，validator 要能在源头拒绝，而不是让转换在半路产出残缺 HTML。
- 中文语境下 `_` 和 `*` 容易被误当强调符号，上游 prompt 里直接要求避免在中文词两侧使用。

## 可复用建议

- 写一份"规范 Markdown 子集"文档，人和 Agent 共用同一份约定。
- adapter 保持纯函数 + 快照测试，新平台接入就是新增一个文件。
- 校验失败要 fail loud，转换日志落盘，发布后可 diff 回溯。

## 总结

管线化之后，单篇多平台发布从十几分钟的手工调整降到秒级，出错从"肉眼漏检"变成"断言失败、有栈可查"。经验浓缩成三句：**上游约束比下游修补便宜，AST 比字符串可靠，失败中断比静默降级安全。**
