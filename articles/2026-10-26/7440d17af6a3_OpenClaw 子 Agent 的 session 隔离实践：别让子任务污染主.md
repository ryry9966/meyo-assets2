## 背景

主会话跑长任务时，最大的敌人不是模型能力，而是上下文被慢慢塞满：工具返回的大段 JSON、中间推理、失败重试的残骸。子 Agent 本来就是用来解决这个问题的——把脏活外包出去。但如果子会话和主会话共享上下文，或者返回时不做裁剪，污染只会来得更快。

## 问题：污染的三个信号

我们在实际跑批和自动化任务里观察到三个典型信号：

1. 主会话 token 消耗随任务数近似线性甚至超线性增长；
2. 主 Agent 开始"记得"子任务的中间过程，后续决策被无关细节带偏；
3. 子任务失败重试后，错误堆栈和半成品结果被带回主会话，主 Agent 陷在对已废弃路径的反复讨论里。

## 做法：四步隔离

**1. 明确边界，不传历史。** spawn 子 Agent 时只给三样东西：输入、目标、返回契约。使用独立 session id，系统提示单独写，不携带主会话历史。子 Agent 不需要知道"为什么做"，只需要知道"做什么、交回什么"。

**2. 落盘优先。** 约定子 Agent 把中间产物写到自己专属的工作目录（路径在 spawn 参数里指定），返回值只带摘要和文件引用。子会话可以很大，主会话只收报告。

**3. 定义返回契约。** 规定返回结构：结论、产物路径、状态、耗时，四项封顶。主 Agent 拿到的是结论而不是过程。返回体建议设硬上限，超限就让子 Agent 自己压缩成文件。

**4. 管好生命周期。** 任务结束显式关闭子 session；可重试任务加幂等标记，避免重试留下多个孤儿会话。

## 踩坑点

- **工具列表全量继承**：子 Agent 默认拿到主 Agent 的全部工具，权限过大，工具描述本身也吃 token。按需裁剪。
- **共享目录并发写**：多个子 Agent 写同一个文件必炸。每个子 session 一个独立子目录。
- **MCP 连接级状态**：部分 MCP server 有登录态、游标这类连接级状态，跨 session 复用连接会把状态"借"给不该有的会话。要么每个 session 独立建连，要么确认工具无状态再用。
- **返回时偷懒 append 全文**：等于没隔离，前面做的一切归零。
- **调试残留**：手动在子 session 里试跑完忘记清理，会话列表越积越乱，排查问题时互相干扰。

## 可复用建议

把子 Agent 当**纯函数**设计：明确的输入、明确的输出、受限的副作用（只准写自己的目录）。再配两条运维习惯：给每个子 session 打标签记录来源，出问题能回溯到哪一次 spawn；定期列一次活跃 session，清掉孤儿。

## 总结

隔离的本质不是"少给上下文"，而是约定数据流：过程留在子会话和文件里，只有结论回流主会话。做到这一点，主会话跑几天的长任务也能保持稳定。
