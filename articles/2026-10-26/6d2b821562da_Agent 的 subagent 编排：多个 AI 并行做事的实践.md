# Agent 的 subagent 编排：多个 AI 并行做事的实践

## 背景

最近在用 OpenClaw 做一个偏工程化的场景：给一个多模块仓库批量做依赖梳理和文档补全。最初用单个 agent 串行跑，一个模块动辄十几轮工具调用，全部塞在同一个上下文里，跑到第三个模块就开始“失忆”，中间产物互相污染，速度也慢。

于是改成了 subagent 编排：主 agent 只负责拆任务和收结果，每个子任务交给一个独立上下文的 subagent 去执行，互不干扰。

## 问题

单 agent 串行方案有三个核心痛点：

1. **上下文污染**：模块 A 的中间日志混进模块 B 的推理过程，错误会传染。
2. **串行慢**：任务之间明明无依赖，却只能排队。
3. **容错差**：一个子任务卡死，整条流水线停摆。

## 做法

我的编排结构分五步：

**1. 拆任务，定边界。** 按模块拆成独立子任务，每个任务写清楚三件事：输入（文件路径/需求描述）、输出（固定 JSON schema）、允许调用的 MCP 工具清单。拆分原则是子任务之间不共享可变状态。

**2. 定义 subagent。** 每个 subagent 单独配置角色 prompt 和工具白名单。只读任务的 agent 不给写权限，这一步用 MCP 的 tool 过滤就能实现。

**3. 控制并发。** 一个简单队列加信号量，并发数压在 3～4。主 agent 派发后轮询收集结果，而不是阻塞等待。

**4. 结构化回收。** subagent 只返回约定格式的摘要（改动文件列表 + 一句话结论），不回传完整日志。主 agent 上下文里只放汇总层。

**5. 失败隔离。** 每个子任务设超时和一次重试；失败的单独记入待处理列表，不阻塞其他结果的合并。

实测同样 8 个模块的任务，串行约 40 分钟，并行后 11 分钟左右，主上下文的 token 消耗还降了一半以上。

## 踩坑点

- **并发开太高就翻车。** 8 个 subagent 同时跑，API 限流和 token 突发直接触发 429。并发数不是越大越好，3～4 是我实测比较稳的区间。
- **输出格式不稳定。** 前期 subagent 偶尔返回自由文本，汇总环节解析直接失败。后来在 prompt 里强制 JSON schema，加了格式校验，不合格就重试。
- **共享文件竞争。** 两个 subagent 同时往同一个 changelog 追加，互相覆盖。改成各自写独立文件、最后由主 agent 合并，问题消失。
- **忘了设超时。** 一次 MCP 工具挂起，整个并发池被占满。现在所有子任务都带显式 timeout。
- **结果回传太贪心。** 最初让 subagent 把整份文件内容传回来，主上下文瞬间膨胀。改成只传路径和摘要。

## 可复用建议

1. **先串行跑通，再并行化。** 拆分逻辑有问题时，串行更容易定位。
2. **subagent 定义模板化**：角色、工具白名单、输出 schema、超时，四件套写进配置，新场景只改参数。
3. **子任务设计成幂等的**：重跑不产生副作用，重试才是安全的。
4. **每个 subagent 打 trace id**，日志分文件落盘，事后排查才有依据。
5. **设 token 预算**：给每个 subagent 一个上限，防止单个失控任务烧穿成本。

## 总结

subagent 编排的本质不是“多开几个 AI"，而是工程上的关注点分离：主 agent 管调度和决策，subagent 管隔离执行。实践中上下文隔离带来的质量提升，往往比并行带来的提速更值钱。建议从一个小而独立的批处理场景开始试，把拆分、并发、汇总这条链路跑稳，再逐步扩展到更复杂的工作流。
