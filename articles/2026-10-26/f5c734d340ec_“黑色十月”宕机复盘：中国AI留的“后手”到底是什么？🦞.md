2025 年 10 月，全球互联网在十天内连着“翻车”两次。10 月 20 日，AWS 弗吉尼亚北部区域出故障，半个互联网跟着打了个盹；10 月 29 日，微软 Azure 前端服务又出状况。社交、游戏、银行、智能家居集体转圈加载。有意思的是，风暴中心里有一类服务格外坚挺——那些权重早已开源、随处可跑的大模型。36kr 的报道把这件事称为“中国 AI 在风暴来临前留了后手”。这篇文章就拆开看：事故是怎么发生的，“后手”又到底是什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-26/492c1b56037e85fd.png)

## 一、黑色十月：时间线复盘

- **10 月 20 日**：AWS 美东 us-east-1 区域的 DynamoDB 数据库出现 DNS 解析异常，随后 EC2 内部网络问题又拖慢了恢复速度。核心故障持续约 6 个多小时，残余影响拖到深夜。故障监测平台累计收到数百万次报告，受影响服务数以千计：Alexa 语音助手、Snapchat、Reddit、一堆银行 App、游戏登录，甚至智能门锁。
- **10 月 29 日**：Azure Front Door 一次配置变更引发全球前端服务异常，Microsoft 365、Azure 门户再中一枪。
- **共同点**：都不是“机房断电”这种低级事故，而是**控制面（control plane）出了问题**——数据本身还在，但“门禁和导航”失灵，所有人都进不了门。

## 二、一次 DNS 故障，凭什么放倒半个互联网

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-26/a593b31b3bfe6277.png)

1. **us-east-1 的特殊地位**：它是 AWS 最老、最大的区域，很多服务的全球控制面就“住”在这里。别的区域数据在本地，但鉴权、元数据这类操作得回 us-east-1“盖章”。老家一断，全球分公司跟着停摆。
2. **故障传播链**：DynamoDB 的 DNS 记录出错 → 依赖它的服务连不上数据库 → 上层应用全链路报错。这条链上任何一环缺降级方案，都会把上游故障原样放大。
3. **重试风暴（retry storm）**：客户端发现失败就疯狂重试，恢复期间形成流量洪峰，把刚爬起来的服务又按了回去。宕机事故里，压垮系统的往往不只是第一次故障，还有全世界的“再试一次”。
4. **结构性集中**：云计算高度集中，AWS 一家约占全球云基础设施市场三成；AI 推理需求又进一步向少数 GPU 集群集中。“共模失效”（common-mode failure）的爆炸半径因此越来越大。

打个比方：全城的龙虾船共用一个码头。码头一塌，不管你的船多先进，海鲜一样上不了岸。

## 三、“后手”：把模型变成可迁移的资产

这次风波里最狼狈的，是把业务焊死在单一闭源 API 上的团队：供应商的后端恰好在出事的云上，整条产品线跟着停摆。而以 Qwen 系列为代表的国产开源模型生态，提前铺好了几条退路：

- **权重开源**：Qwen 家族已开源上百款模型，全球衍生模型超过 10 万个，累计下载量数亿次；DeepSeek-R1 等也以宽松协议开放权重。任何人都能下载、微调、私有部署。云 API 挂了，本地 vLLM、Ollama 还能跑，只是慢点。
- **多云与自建**：国产云近几年在全球铺了几十个 Region，头部 AI 公司普遍自建 GPU 集群，关键服务讲究“两地三中心”（同城双活 + 异地灾备）。同一朵云的故障，不再等于自家业务全灭。
- **工具链解耦**：主流推理框架和 coding agent 都支持“换后端”——兼容 API、可插拔模型。切换备胎的成本，从“重写架构”降到了“改一行配置”。

翻译成工程语言：闭源 API 是把命交给别人，开源权重是给自己留一套备胎。这不是玄学，是标准的灾备思路——**冗余平时看着像浪费，宕机当天是命。**

## 四、宕机不是黑天鹅，是灰犀牛

- 2017 年，AWS S3 一名工程师手滑删多了服务器，Slack、Trello 等一批产品瘫痪数小时；
- 2021 年，Fastly 一次错误配置，全球大量媒体网站集体 503；
- 2024 年，CrowdStrike 一版坏更新，让约 850 万台 Windows 机器蓝屏，机场和医院都受波及；
- 2025 年，AWS、Azure 双连击，11 月 Cloudflare 又补了一刀。

规律很清楚：**越集中，越脆弱**。云厂商把可靠性做成了商品，但“所有鸡蛋放一个篮子”的风险并没有消失，只是换了个篮子。AI 时代尤其如此——推理流量向少数几朵云集中，下一次“黑色十月”的爆炸半径只会更大。这也解释了为什么“开源权重 + 多云部署”这种看似笨拙的后手，会在风暴来临时突然显得珍贵。

## 五、三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-26/fa8b476a53310a49.png)

1. **架构上**：关键路径至少跨两个可用区或两个区域部署，配好自动故障切换（DNS failover + 健康检查）。更重要的是定期演练——没演过的预案，等于没有预案。
2. **AI 选型上**：优先选权重可迁移、API 兼容性好的模型，别把业务焊死在单一供应商的私有特性上。给自己留一条“本地跑开源模型”的降级通道，哪怕性能打折。
3. **客户端上**：重试加指数退避和抖动（backoff + jitter），并设熔断上限。别让你的“勤奋重试”，在故障恢复期变成对自家服务的第二次攻击。

最后一句冷思考：冗余的终极悖论是，它 99% 的时间看起来毫无必要，剩下 1% 的时间价值连城。龙虾有两只螯，断一只照样吃饭——做工程也一样，永远给自己留一只。
