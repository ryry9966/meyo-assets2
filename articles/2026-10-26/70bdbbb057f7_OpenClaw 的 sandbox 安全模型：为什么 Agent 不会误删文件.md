## 背景

给 Agent 接上 shell 和文件系统工具之后，第一件让人睡不着觉的事就是：它在某次长任务里自作主张执行了 `rm -rf`。这不是杞人忧天——LLM 在长上下文中误解指令、参数幻觉、或被注入内容带偏，都可能导致危险调用。OpenClaw 的 sandbox 模型不是靠在 prompt 里写一句"请小心"来解决的，而是一套分层防御。

## 核心机制：三层防线

1. **文件系统层：workspace 隔离**。Agent 的文件工具默认只挂载一个 workspace 目录，宿主机的其他路径在工具层根本不可见。Agent 不是"不敢删"，而是"看不到、够不着"。
2. **命令策略层**。shell 工具跑在受限容器里，所有调用先过策略引擎：allowlist 放行常用命令，命中危险模式（递归删除、提权、chmod 777 之类）直接拦截，无论模型怎么包装参数。
3. **确认层**。落在 workspace 内的写/删操作，超过阈值或命中敏感路径时进入人工确认队列，可配置"全自动 / 高危确认 / 全确认"三档。

再加一道兜底：每次批量写操作前对 workspace 做快照，误删可秒级回滚。

## 一次典型误删是怎么被拦下的

Agent 想清理构建产物，生成了 `rm -rf ./build`，但路径解析出错变成了仓库根目录。实际执行链路：命令先过策略引擎 → 命中递归删除模式 → 路径规范化检查发现目标越出 workspace 允许范围 → 拦截并写审计日志 → Agent 收到结构化错误，自我修正为精确路径后重试成功。整个过程没有人工介入，也没有任何文件丢失。

## 踩坑点

- **挂载贪多**。为图方便把整个 home 目录挂进 sandbox，隔离等于没做。只挂任务需要的最小目录。
- **symlink 逃逸**。Agent 在 workspace 里建一个指向宿主机的软链接，再"删除链接指向的内容"。路径校验必须先做 realpath 解析再判断，不能只看字面路径。
- **denylist 永远不完备**。base64 编码、变量间接引用都能绕黑名单。策略上优先 allowlist，denylist 只做第二层。
- **容器内 root**。容器隔离了命名空间，但若把宿主目录以 root 读写挂载，删了就是真删。参考类文件用非 root 用户 + 只读挂载。
- **忽略审计日志**。拦截记录是最有价值的调优素材，每周过一遍能发现策略盲区。

## 可复用建议

- 默认拒绝、显式放行：新工具接入先给最小权限，再按需扩。
- 防线分层独立：文件系统、命令策略、人工确认任意一层失效，其余两层仍能兜住。
- 用对抗性 prompt 做回归测试：专门写几条诱导删除的用例进 CI，策略改动后跑一遍。
- 快照成本很低，别省。

## 总结

"Agent 不会误删文件"不是模型的功劳，而是架构的功劳：不可见、不可达、需确认、可回滚。OpenClaw 的 sandbox 思路是把安全问题从"信任模型"转移到"约束执行环境"——前者不可靠，后者可以工程化。如果你的自动化还在裸跑宿主机权限，建议今天就把它搬进 sandbox。
