## 背景

写 OpenClaw 插件和自动化流程多了会发现一个规律：Agent 的能力上限往往不由模型决定，而由它依赖的外部调用决定——LLM API、搜索、数据库、各类 MCP 工具。任务跑得越长，遇到 429、超时、5xx 的概率越接近 100%。

大多数"自动化失败"的案例里，API 本身只是抖了几秒，真正把任务搞砸的是 Agent 面对错误时的反应。

## 三种典型翻车

1. **误判放弃**：工具抛出异常字符串，模型理解为"任务不可行"，直接向用户告终；或者更糟——编一个看似合理的结果交差。
2. **重试风暴**：遇到 429 后立刻原样重试，间隔为零，把本就紧张的限流窗口彻底烧穿。
3. **重复执行**：发消息、下单、写库这类非幂等操作在超时后重试，造成双发。超时意味着"结果未知"，不是"失败"。

根因一致：错误没有被分类，重试没有策略，模型拿到了不该由它处理的决策。

## 做法

**第一步：在封装层分类错误。** 不要把原始异常透给模型。在 tool-call 封装层把错误归为三类：可重试（超时、429、502/503/504）、不可重试（400/401/404、业务校验失败）、结果未知（请求已发出但响应丢失）。MCP 工具的返回值里带上这个分类。

**第二步：重试收归封装层。** 指数退避加抖动，设硬上限（如 3 次、总耗时 30 秒）。关键是不要在 Agent 循环里让模型自己决定"要不要再试"——它几乎总是倾向于再试，token 和时间都是成本。模型只应看到重试后的最终结果。

**第三步：幂等与对账。** 写操作统一带幂等键；结果未知的请求先查询状态再决定是否重试。工具返回 `status: "unknown"` 加一个查询接口，比直接抛异常有用得多。

**第四步：结构化回报。** 失败信息包成 JSON 再交给模型：

```json
{
  "ok": false,
  "error_type": "upstream_timeout",
  "retried": 3,
  "unknown_outcome": false,
  "suggestion": "switch_to_cache_or_report"
}
```

模型拿到结构化输入，才能走对分支：换工具、读缓存，还是如实告诉用户"数据源暂不可用"。

**第五步：预留降级路径。** 主 API 要有 B 计划：备用 provider、带时间戳的过期缓存、或干脆的能力声明。没有降级路径的工具，失败时就让 Agent 明确说"做不到"，比硬编强。

## 踩坑点

- **抖动不能省**。多个 Agent 并行时，固定间隔重试会同步成波次攻击，jitter 是必需品。
- **封装层全量 catch 后返回 "success" + 错误字符串**是最隐蔽的坑，Agent 会以为自己成功了。
- **别把 stack trace 喂给模型**，长 traceback 会诱导模型复述甚至模仿报错。
- **重试预算要全局算**。单工具 3 次没问题，十个工具链式各试 3 次，任务窗口就没了。

## 可复用建议

- 做一个统一的调用中间件，重试、分类、幂等、日志都在这一层收口；
- 每个工具声明 `retry_policy` 和 `idempotent` 两个元字段，中间件按声明行事；
- 全链路 request_id，失败可回放；
- 上线前做失败注入：手动断掉依赖 API 跑一遍完整流程，比任何 code review 都有效。

## 总结

外部 API 挂掉是常态，不是异常。Agent 的可靠性不取决于依赖的可用性，而取决于错误如何被分类、被表达、被预算。原则就两条：把重试从模型手里拿走，交给封装层；把结构化的失败信息还给模型，让它做正确的决定。
