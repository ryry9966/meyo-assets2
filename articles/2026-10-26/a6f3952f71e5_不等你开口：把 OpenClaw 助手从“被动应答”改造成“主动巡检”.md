## 背景

多数 AI 助手的工作模式是被动的一问一答：你不发消息，它就是一段安静的进程。OpenClaw 提供了两个让 agent “自己醒来”的原语——心跳（heartbeat）和 cron 定时任务，配合聊天渠道的推送能力，理论上能搭出一个不等你开口就干活的助手。但实际跑下来，难点不是“能不能主动”，而是“什么时候该主动、主动到什么程度”。

## 问题

我最初的目标很简单：每天早上汇总 GitHub 通知和日历，仓库 issue 异常时即时提醒。落地时遇到三个工程问题：

1. agent 默认不会自己醒来，缺可靠的唤醒调度；
2. 主动和骚扰只有一线之隔，规则没写好时，我的 Telegram 一天被推了二十多条；
3. 主动执行的动作缺确认机制，误操作没有兜底。

## 做法

**第一步，配置心跳。** 在 workspace 下创建 `HEARTBEAT.md`，把巡检清单写成显式规则，重点写清“什么情况下保持沉默”。心跳默认约 30 分钟一轮，可用 `HEARTBEAT_INTERVAL` 调整。每轮心跳是一次完整的 agent 调用，模型读到清单后自行判断：无事则结束，有事才输出。

**第二步，心跳和 cron 分工。** 确定性任务（每天 8 点的晨报）交给 cron，不消耗判断；心跳只留给需要“看情况”的巡检。这个分工能明显压成本。

**第三步，输出分级。** 我定义了三级结果：无事不发；低优先级写入独立的每日笔记，不推送；高优先级才发到聊天渠道。核心原则是默认沉默。

**第四步，危险动作加确认门。** 发消息、删除、花钱这类写操作一律先生成草稿等我确认；只读巡检可以自动跑。配合 Docker 沙箱，把主动能力的爆炸半径限制住。

**第五步，接真实数据源。** 通过 MCP server 和技能接日历、监控、仓库数据，主动才有内容可巡检，否则 agent 只能对着空上下文编任务。

## 踩坑点

- **心跳清单写得太宽泛。** 早期我写的是“检查仓库状态”，结果每轮心跳都有“发现”。改成带阈值的条件句（“仅当新增 issue ≥ 3 时通知”）后才安静下来。
- **成本失控。** 30 分钟一轮 × 24 小时，一个月 token 花销可观。我把夜间间隔拉长到 2 小时，固定任务全部迁去 cron。
- **巡检结果污染记忆。** 最初所有结果都写进主 memory，几轮后上下文全是噪音。改用独立每日笔记文件后恢复正常。
- **重复提醒。** 同一个异常每轮心跳都报一次。加了一个“已报告”标记文件，报告过就跳过，状态变化才重新提醒。
- **忘了加确认门。** 测试期 agent 主动调用了发送类工具，幸好目标是自己的小号。此后所有写操作默认需要确认。

## 可复用建议

1. 把“该不该打扰”写成显式规则，不要指望模型自觉；
2. 先只读后写入：让主动能力从汇总推送起步，稳定跑两周再放开写操作；
3. 调度和判断解耦：确定性任务用 cron，判断型巡检用心跳，频率和成本才可控；
4. 动作分级：静默记录 < 推送提醒 < 生成草稿等确认 < 自动执行，逐级放开。

## 总结

Proactive 能力本质上不是让模型更聪明，而是一组工程决策：用什么调度唤醒（心跳 + cron）、什么阈值触发打扰（显式规则）、什么权限允许执行（确认门 + 沙箱）。建议从单一场景、只读巡检开始，把“默认安静”作为第一原则，再逐步扩大主动范围。
