最近，Linux 基金会发布的一份新报告在开发者圈里刷了屏：开源项目收到的 PR（Pull Request，合并请求）中，约四分之一被判定为低质量内容，其中相当一部分是 AI 批量生成的"AI slop"——中文社区直译为“AI垃圾”。而报告同时引用的多项测量显示，AI 让开发者写代码的速度提升了约 52%。一边是生成效率暴涨，一边是维护者更累。这两个数字放在一起并不矛盾，恰恰是同一枚硬币的两面。这篇文章把它拆开：快出来的时间去哪了，堵住的又是哪一环。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-26/dfd709d65237d46b.png)

## 先看数据：52% 和 25% 测的根本不是一件事

- **52% 提速**：来自对 AI 编程工具的任务计时研究（GitHub 早年 Copilot 对照实验、后续多家企业内部测量大致在这个量级），它测的是“从接任务到代码写完”的**生成环节**。
- **25% 低质**：来自维护者与社区对 PR 的质量反馈，判定依据包括幻觉 API、重复实现、测试不过、与项目方向冲突等，它测的是**审核与合并环节**。
- 旁证不少：GitClear 分析海量真实提交后发现，代码重复率和“复制粘贴式”改动连年上升；METR 的对照实验更扎心——资深开发者主观感觉快了 20%，实测反而慢了 19%。
- 一句话总结：**52% 是生产曲线，25% 是质量曲线，两条曲线不在同一个坐标系里。**

## 机制拆解：瓶颈从“写”挪到了“审”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-26/82bd4782d4daa12c.png)

软件交付是一条流水线：写代码 → review → 测试 → 合并 → 长期维护。AI 目前只冲刷了第一格，后面全是人力。

1. **提交成本骤降**：以前写一个像样的 PR 要花几小时查文档、跑测试、写说明；现在一句话十秒生成，边际成本趋近于零。
2. **审查带宽不变**：维护者是人，一天能审的 PR 数量是固定的，不会因为 AI 出现而增加。
3. **于是出现“审查赤字”**：经济学上这几乎是必然——当提交免费，提交数量必然上涨，质量分布整体下移。
4. **算笔账**：一个日均收到 50 个 PR 的热门项目，人工审一个普通 PR 约 30 分钟，每天需要 25 小时审查时间；而其中一半可能是 AI 一分钟生成的。

一句话概括：AI 管下锅，维护者管尝馅——锅越来越快，舌头只有一条。**AI 把成本从提交者转移给了审查者**，而开源世界的审查者，大多是不拿工资的志愿者。公司省下的是工时，社区付出的是周末。

## AI 垃圾长什么样：五种典型形态

1. **幻觉 API**：调用根本不存在的函数或包，严重时撞上与官方同名的恶意包，形成所谓 slopsquatting（垃圾包抢注）的安全风险。
2. **表面正确**：语法漂亮、能编译、单测还过，但空输入、并发、时区这些边界条件全军覆没——审查者只能靠脑内执行来抓错。
3. **风格漂移**：修一行 bug 顺手“重构”半个文件，diff 大到没法看，一个小修变成一次大手术。GitClear 数据里 churn 上升就是这么来的。
4. **重复造轮子**：不看 issue 列表和 roadmap，闭门实现一个早就存在、甚至上周刚被否决过的功能。
5. **政绩型 PR**：只改一个标点，描述写得冠冕堂皇。这类刷存在感的提交早已有之，AI 只是让它实现了批量化。

给维护者一个快速识别口诀：**看 diff 体积、看 issue 关联、看测试是否覆盖失败分支、看引用的 API 是否真实存在。** 四关都过，才值得花时间细读。

## 为什么开源社区首当其冲：一笔不对称的账

- **公司内部**：AI 提速省的是发工资的时间，审查者是同一家公司的同事，成本在内部消化，账是平的。
- **开源社区**：一个团队用 AI 一天能提 20 个 PR，审查时间却由全球志愿者无偿承担——省下的成本被“外部化”了，教科书级的负外部性。
- **历史上不是第一次**：垃圾邮件面对的是完全相同的结构——发送近乎免费，过滤极其昂贵。维基百科的反破坏编辑、Hacktoberfest 活动期间的刷量 PR，都是同一个剧本的重演。
- **社区已经开始反应**：不少项目要求 PR 必须关联 issue、要求声明是否使用了 AI；OpenBSD 走得更远，明确宣布不接受疑似 AI 生成的代码贡献。
- **如果不管会怎样**：维护者倦怠 → 收紧贡献门槛 → 认真的人类新人被误伤 → 社区长期活力下降。垃圾的代价，最后由整个生态支付。

## 收尾三条：分别写给贡献者、维护者和管理者

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-26/367b54077e7b8d83.png)

1. **贡献者：先对齐，再动手。** 先开 issue 说清要解决什么、方案为什么合理，拿到维护者点头再写码；单个 PR 控制在 200 行以内，diff 越小越容易合并；用了 AI 就主动声明，并且自己完整跑一遍测试——你省下的十分钟，可能要别人花一小时来还。
2. **维护者：把审查自动化前置。** 把“关联 issue、DCO 签名、CI 通过、diff 体积上限”做成硬门槛，用机器挡掉八成机械问题，把宝贵的人力留给真正需要判断的部分；同时把项目的 AI 政策写进贡献指南，模糊地带越少，扯皮越少。
3. **团队与管理者：换掉度量指标。** “AI 生成代码行数”“周 PR 数”这类指标只会催生 slop；改看合并后的缺陷率、返工率和 review 耗时。把 AI 当一个不用睡觉的初级工程师用——产出快，但产出必须经过 review。这不是对 AI 的不信任，而是软件工程几十年来没变过的底线。

最后一句冷思考：技术史上每次“生产成本暴跌”，几乎都会跟着一次“验证成本暴涨”，从印刷术到互联网皆是如此。这次轮到代码。就像剥龙虾——出肉快不等于能吃，壳挑干净才算数。我们缺的从来不是更快的生成器，而是更聪明的过滤器。
