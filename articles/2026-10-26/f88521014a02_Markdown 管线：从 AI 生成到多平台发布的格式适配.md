## 背景

用 OpenClaw 做 Agent 内容生产，LLM 输出天然是 Markdown，但“生成完”和“能发布”之间距离很远：公众号只认内联样式的 HTML，知乎对标签限制严格，静态站点要 frontmatter，掘金和 GitHub 的 GFM 方言也不一致。我们把格式适配从人肉粘贴改成了一条可执行管线。

## 问题

跑起来后暴露三类问题：

1. **模型输出不稳定**：同一 prompt，有时产出干净 Markdown，有时混入裸 HTML、跳级标题、缩进不一致的嵌套列表；
2. **平台方言差异**：脚注、任务列表、公式、表格对齐的支持程度各不相同，外链图片还常被防盗链拦下；
3. **流程不可复现**：每个平台手工调一遍，改一处内容要同步改 N 处，出错全靠肉眼。

## 做法

核心思路是“单一源稿 + 平台适配器”，分四步：

**1. 约束生成。** 在 Agent 系统提示里明确输出子集：只用二级及以下标题、不写行内 HTML、公式用 `$$...$$`、图片一律用占位符 `![img-1]`。模型遵循度比预期高，剩下交给 lint 兜底。

**2. 规范化。** 用 unified 生态（remark）解析成 AST，跑一组 remark-lint 规则：统一列表缩进、禁止跳级标题、剔除裸 HTML、智能引号转普通引号。lint 不过直接失败，不做静默修复。

**3. 适配转换。** 每个平台一个无状态适配器，输入 mdast，输出目标字符串：

- 公众号：rehype 转 HTML 后全部内联样式，占位符在发布前替换为素材库 URL；
- 静态博客：注入 YAML frontmatter，图片替换为 CDN 地址；
- 知乎/掘金：脚注降级为文末列表，公式降级为代码块或图片。

**4. 快照测试。** 每个适配器挂一组黄金样本，跑 diff 防止转换逻辑被无意改坏。

整条管线在 OpenClaw 里封成一个 Skill/MCP 工具，Agent 只管产出规范源稿，发布时按平台取结果。

## 踩坑点

- **别指望“渲染时再处理”**：公众号编辑器粘贴即定型，所有转换必须落在最终 HTML 字符串上，包括内联样式。
- **基于正则的后处理先排除代码块**：代码里的 `_`、`*` 是重灾区，务必用 AST 而不是全文正则。
- **frontmatter 对部分渲染器是致命的**：会被整段当正文渲染，适配器里要显式剥离。
- **占位符要选模型不愿改写的形式**：`![img-1]` 是合法图片语法，比 `[图1]` 这类自由文本安全得多。
- **表格对齐信息常被丢弃**：关键数据别只放表格里。

## 可复用建议

1. 把“允许的 Markdown 子集”写成明确文档，人和模型共用一份；
2. 适配器保持无状态：进一份 AST，出一份字符串，方便测试和并行开发；
3. 失败要早：lint 阶段拦截的成本远低于发布后发现；
4. 图片路径永远延后解析，源稿只留稳定占位符。

## 总结

多平台发布本质上不是“格式转换”，而是“输入约束 + 确定性变换”：把不稳定性挡在生成阶段，把方言差异收敛进适配器，剩下的就是普通工程问题。这条管线我们跑了一个多月，人工干预基本只剩发布前的预览确认。
