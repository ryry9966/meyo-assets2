## 背景

用 Agent 批量产出技术内容的团队，基本都会走到同一步：模型生成的 Markdown 在本地渲染很正常，一发到公众号、知乎、静态站，格式就崩了。我们把发布链路做成一条显式的 Markdown 管线之后，这个问题才真正收敛。分享一点实践。

## 问题

三层麻烦叠在一起：

1. **模型输出不稳定**：同一个 prompt，今天输出 fenced code，明天夹一段裸 HTML；列表标记 `-` / `*` 混用，标题层级跳跃。
2. **平台方言差异**：公众号剥离 `<style>` 标签、代码高亮必须内联样式；知乎对任务列表和脚注支持有限；Hugo/Hexo 需要 front matter。
3. **图片是重灾区**：相对路径、防盗链、平台只认自家 CDN，链接得重写。

## 做法

整条管线构建在 remark（mdast AST）之上，分五步：

**1. 收紧模型契约。** System prompt 里明确：纯 Markdown、代码块必须带语言标注、禁用内联 HTML；元数据用单独的 tool call 结构化返回，而不是让模型自己写 YAML。契约靠校验兜底，不靠自觉。

**2. 规范化。** `remark-parse` 转 AST 后跑一轮归一化：统一列表标记、压平标题层级跳变、全半角标点统一、剥离意外混入的 HTML 节点，产出一份“标准中间稿”。

**3. Lint 闸门。** 在 remark-lint 基础上加自定义规则：图片必须有 alt、禁用节点类型（如 `<details>`）、字数边界。不过关直接打回，让 Agent 自修复一轮再过闸，最多重试两次。

**4. 平台适配器。** 每个平台一个小型纯函数变换：公众号走 AST → 内联样式 HTML（高亮在编译期展开）；知乎和静态站走 Markdown 方言投影（降级任务列表、注入 front matter）。图片单独一个 handler：下载 → 上传素材库 → 拿到 URL 映射表 → 回写 AST。

**5. 预览 + 人工确认。** 每个平台产出发 golden snapshot，diff 后进预览页，发布动作由人确认，Agent 不直接触达平台 API。

## 踩坑点

- **不要让模型直接产 HTML**。看似省事，实际把格式问题从编译期推到了运行期，而且没法 diff。
- **表格是隐藏成本**。公众号里带嵌套列表的表格基本不可用，我们在 lint 阶段直接降级为定义列表。
- **高亮内联展开后体积爆炸**，注意公众号字数硬限制，长文按块截断加提示。
- **图片上传要有幂等键**（内容 hash），否则重跑一次管线就重复上传一版素材。
- **脚注和数学公式**在多数平台要么不支持要么语法不同，能不用就不用，要用就走图片化。

## 可复用建议

- 把 Markdown 当编译产物，源头是“结构化元数据 + 约束下的生成”，重发布永远可重放。
- 平台适配器保持小而纯：输入 AST、输出平台方言，单元测试加 golden 文件快照即可覆盖。
- 维护一份“平台怪癖清单”，每踩一个坑就沉淀成一条 lint 规则，坑才会越踩越少。

## 总结

这条管线的核心不是某个工具，而是把格式适配从发布时的手工动作，前移成构建期的确定性变换：AI 负责内容，AST 负责结构，适配器负责方言，人负责最后那一下确认。落地后我们单篇发布从十几分钟的手工修格式降到基本零干预，稳定性也肉眼可见地好了。
