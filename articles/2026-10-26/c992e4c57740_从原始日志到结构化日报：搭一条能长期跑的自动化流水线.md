# 从原始日志到结构化日报：搭一条能长期跑的自动化流水线

## 背景

我们社区里跑着不少长期任务：定时 agent 作业、MCP 工具调用、各类插件事件。运行日志散落在 JSONL 文件、容器 stdout 和一张 SQLite 表里。之前每天的日报靠人翻日志手写，写了半个多月，暴露出两个问题：太费时间，且不同人写的口径对不上，周会没法横向比较。

## 问题

拆开看，日报自动化有三个硬点：

1. **原始日志噪音大、格式乱**。DEBUG 输出、重试产生的重复记录、同一错误的不同写法混在一起。
2. **不能把日志直接丢给 LLM 总结**。一天的日志几十万 token，塞不进去；就算塞进去，数字也是模型"编"的，不可信。
3. **报告必须有固定结构**。今天的日报和昨天的结构不一致，后续做趋势对比就废了。

## 做法

核心思路是**分层**：脚本管数字，LLM 管叙述，模板管结构。整条流水线五步：

**1. 统一采集层。** 所有来源的日志先归一成 JSONL，字段固定：`ts, source, level, actor, action, duration_ms, status, extra`。无法归一的原样塞进 `extra`，先保住信息不丢。

**2. 预处理。** 一个脚本做清洗：去掉 DEBUG、按重试 ID 合并重复记录、错误码归一（比如把 `E_TIMEOUT`、`timeout error`、`ctx deadline exceeded` 映射到同一类），输出 `day-YYYYMMDD.jsonl`。

**3. 统计聚合。** 数字全部由脚本算，不让模型碰：

```python
metrics = {
    "total_tasks": len(rows),
    "success_rate": ok_count / len(rows),
    "p95_latency_ms": percentile([r["duration_ms"] for r in rows], 95),
    "top_errors": top_k(normalized_errors, 5),
}
```

**4. LLM 摘要层。** 只把 `metrics.json` 加上抽样出的少量异常片段喂给模型，要求输出固定 schema：变化点、可能原因、建议关注项。temperature 设 0，给两个 few-shot 示例稳住格式。

**5. 模板渲染与推送。** Jinja2 把指标数字和摘要拼进固定 Markdown 模板，落盘 `reports/2025-06-12.md`，再由 OpenClaw 的定时任务推到频道。整条链路用 cron 触发，早上 8 点出昨天的报。

## 踩坑点

- **时区边界**。日志全部是 UTC，但日报按本地时区切天。第一版没在预处理层做转换，结果晚上 8 点后的任务全算到了"明天"，前后两天的成功率对不上。切天逻辑必须收敛在一个地方。
- **让模型算数**。早期偷懒让 LLM 顺便给个百分比，出现过成功率和明细对不上的幻觉。现在数字 100% 来自脚本，模型只写叙述。
- **输出不稳**。模型偶尔漏字段。渲染前加了一步 schema 校验，缺字段就走降级模板（纯数字版日报），保证每天必有产出。
- **幂等性**。定时任务重跑会重复推送。报告文件名带日期，推送前先查当天文件是否已生成、已推送，直接短路退出。
- **错误归一没做之前**，Top 错误列表里"同一个故障"出现十几种写法，榜单完全没有参考价值。

## 可复用建议

1. **schema 先行**：采集层字段宁多勿少，原始信息进 `extra`，后续想加指标不用改上游。
2. **数值与结论分层**：这条纪律是整条流水线可信度的基础，别为了省一步让模型碰数字。
3. **先做子集再扩张**：我们先用三周只出"任务成功率 + Top 3 错误"两个字段，跑稳后再加耗时分布、事件计数。指标一次上太多，坏了都不知道从哪查。
4. **保留 30 天原始 JSONL**：聚合逻辑改了之后可以回溯重算历史，对比才连续。

## 总结

日报自动化不复杂，复杂的是让它在三个月后依然可信。经验浓缩成一句：**采集层保证不丢数据，聚合层保证数字正确，模型层只负责把数字讲成人话，模板层锁死结构**。四层各司其职，日报才能真正替代人工。
