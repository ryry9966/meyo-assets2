## 背景

OpenClaw 这类本地运行的 Agent，价值不在"能聊天"，而在"能动手"。动手的落点基本都一样：调外部 API——发工单、查库存、触发 CI、写数据库。但 API 是为人设计的，不是为模型设计的：文档面向人类阅读、鉴权靠密钥、错误是一坨上游堆栈。Agent 要真正接上，中间需要一层明确的"握手协议"。

## 问题

实际对接时，卡住的从来不是"能不能发 HTTP 请求"，而是三件事：

1. 工具描述模糊，模型靠猜传参，猜错就报错，重试纯烧 token；
2. 密钥管理混乱，环境变量、配置文件、对话日志里到处是敏感信息；
3. 错误语义没有约定，Agent 收到 500 只会盲重试，遇到幂等性差的接口就直接闯祸。

## 做法

按集成成本从低到高，我一般三条路线里选：

**路线一：现成 MCP Server（默认优先）。** 目标服务已有 MCP server 就直接在 OpenClaw 的 MCP 配置里挂上，工具描述、鉴权、错误格式都有人维护，不要重复造轮子。

**路线二：自写薄封装。** 没有现成 server 时自己包一层，原则是"薄"——不做业务逻辑，只做三件事：

- 把 API 文档翻译成严格的 JSON Schema：参数、类型、枚举、必填全写死，不留自由发挥空间；
- 从环境变量读密钥，绝不写进配置正文或工具描述；
- 把上游错误归一化成结构化返回：`ok / retryable / fatal` 三态，让 Agent 知道该重试还是该放弃。

**路线三：通用 HTTP 工具兜底。** 一次性、低风险的调用可以直接用内置 HTTP 工具，但务必配域名白名单，防止 Agent 被 prompt 注入后随意外联。

落地步骤：先盘 API（鉴权方式、限流、幂等性）→ 选路线 → 写工具 Schema → 本地 dry-run 验证 → 只读权限灰度 → 再放开写操作。

## 踩坑点

- **Schema 太宽。** 描述里写"可选参数随意传"，模型真的会乱传。枚举值和取值范围要写进 Schema 本身，不是写在注释里。
- **盲重试。** POST 建单这类非幂等操作，重试前先查一遍是否已创建；接口支持幂等键的一定要传。
- **密钥进上下文。** 把 token 拼进工具返回值，等于写进对话历史。返回值只留业务字段，鉴权留在封装层。
- **长调用阻塞。** 跑几分钟的任务让 Agent 干等没有意义。改成异步：提交后返回任务 ID，单独提供查询工具。
- **错误直接透传。** 上游堆栈喂给模型不但没用，还会诱导它编造原因。封装层先翻译成一句人话加一个错误码。

## 可复用建议

- 工具数量克制：一个服务暴露 3~5 个高内聚工具，比 20 个细碎工具的调用成功率高得多。
- 所有写操作默认带 dry-run 参数，上线初期强制开启。
- 同一服务的所有工具保持一致的返回结构，Agent 学会一次就会用全部。
- 限流和退避重试放在封装层，不要指望模型自己判断"等多久再试"。

## 总结

对接外部服务的本质，是把"为人设计的 API"翻译成"为模型设计的工具"。翻译质量决定 Agent 的可靠程度：Schema 越严、错误越结构化、权限越小，握手越稳。OpenClaw 给了足够的扩展位，但真正的工程质量都在那层薄封装里——值得花时间慢慢磨。
