# 背景

云端 API 用着顺手，但有两类场景总让人不踏实：一是涉及私有数据的自动化流程（日志分析、本地文档问答），数据出域要走合规；二是长期挂着的 Agent 任务，token 费用累积下来不算小。于是我把家里一台闲置主机改成本地推理节点，跑了两三个月，把过程和坑记录下来。

# 问题

家用硬件上跑模型，核心矛盾有三个：

1. 显存/内存有限，模型大小和上下文长度互相挤压；
2. Agent 场景对模型要求比聊天高：要稳定输出 JSON、要可靠调用工具，7B 级量化模型在这些点上经常翻车；
3. 吞吐低、并发基本为 1，Agent 里的并行调用会排队。

# 做法

**第一步：算清内存账。** 经验公式：模型占用 ≈ 参数量 × 每参数字节数（Q4_K_M 约 0.6 字节）+ KV cache。KV cache 别拍脑袋：7B 模型 8K 上下文大约再吃 1GB 出头，拉到 32K 翻四倍。8GB 显存跑 7B Q4 可行但勉强，16GB 跑 14B Q4 比较从容；Mac 统一内存可以更激进，32GB 的 M 系列跑 14B~32B Q4 都能接受，只是慢。

**第二步：选推理后端。** 建议用 Ollama 起步：一条命令拉模型，自带 OpenAI 兼容接口，后续换 llama.cpp 或 vLLM 时上层代码不动。追求极限性能再上 llama.cpp 手调参数；Linux + NVIDIA 且需要并发，才考虑 vLLM。

**第三步：选模型。** 中文场景我固定用 Qwen 系列的 Instruct 版本，量化从 Q4_K_M 起步。重点确认两件事：模型卡是否声明支持 tool calling；上下文窗口够不够 Agent 用（至少 16K，建议 32K）。Embedding 单独跑一个小模型，别用主模型硬凑。

**第四步：接入 Agent/MCP。** 对 Agent 框架来说，本地端点就是换个 base_url，OpenClaw 里把 provider 指向本地地址即可。但要加三道保险：temperature 降到 0.1~0.3；工具定义尽量精简、参数用 JSON Schema 约束；工具调用加超时和一次重试。

**第五步：建自己的验收集。** 从真实业务里挑 20 条样例（10 条普通对话、10 条带工具调用），每次换模型或量化跑一遍，记录成功率和 tokens/s。这比看任何榜单都有用。

# 踩坑点

- **量化模型的工具调用不可靠**：同一模型，高精度下工具调用成功率 95%，Q4 可能掉到 70%。用框架层 Schema 强约束加重试可缓解，复杂编排仍建议走云端。
- **上下文占用被低估**：Ollama 默认 `num_ctx` 很小，不显式调大，长对话会被静默截断，Agent“变笨”但没有任何报错。
- **模型卸载延迟**：Ollama 默认闲置几分钟后卸载模型，下次调用冷启动几十秒。定时 heartbeat 或调 `keep_alive` 解决。
- **并发阻塞**：本地推理默认串行，Agent 里 `Promise.all` 发三个请求会排队。要么后端开批处理，要么在 Agent 层把本地调用限流为 1。

# 可复用建议

- **分层路由比全本地更务实**：简单分类、格式转换、本地文档摘要走本地；复杂推理、多工具编排走云端。一个按任务类型分发的路由函数就够了。
- **配置即代码**：Modelfile、启动参数、上下文长度全部进仓库，换机器重放一遍即可复现。
- **监控两个数就够**：tokens/s 和内存水位，其余指标在家用场景意义不大。

# 总结

本地 LLM 在家用硬件上已经可用，但定位要摆正：它是 Agent 体系里“便宜、私密、离线”的那一档，不是云端替代品。先算内存账，再验工具调用，最后用自己业务的评测集说话——三步走完，基本不会踩大坑。
