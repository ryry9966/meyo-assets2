## 背景

LLM 本身无状态，每次会话都是"失忆重启"。一次性问答无所谓，但用 OpenClaw 这类 Agent 做日常自动化时，每次都要重复交代"用 pnpm 不用 npm""时区 UTC+8""commit message 写英文"，这种摩擦会迅速累积。MCP 的出现让记忆有了标准接口——把 memory 做成一个 MCP server，Agent 按需调用即可。但接口好接，记忆本身怎么设计才是真正的难点。

## 问题

两个极端都会翻车：

- **什么都不存**：每个 session 冷启动，体验差；
- **什么都存**：把聊天记录整段塞进一个 memory.md，几千条之后检索噪声爆炸、新旧偏好互相矛盾，Agent 开始"记错事"。

核心矛盾在于：记忆既要够用，又要小、新鲜、可信。这不是存储问题，是数据工程问题。

## 做法：三层记忆 + 严格读写规则

**先分层，按生命周期拆三层：**

1. **稳定偏好层**：技术栈、代码风格、语言时区、沟通习惯。条目少（几十条内）、变化慢，维护成一个结构化文件，每次会话整体注入 system prompt，不做向量检索——这个量级全文注入比检索更准。
2. **项目上下文层**：按命名空间隔离，存"这个仓库走 monorepo""部署先 staging 再上 prod"这类中等时效信息。
3. **事件流水层**：append-only 的会话摘要，带时间戳，默认不注入，仅用于回溯审计。

**写入要克制**，三条规则：

- 只存蒸馏后的事实，不存原文；用户明确表达的才写，Agent 自己猜的一律标 `confidence=low` 进待确认队列；
- 写前查重 + 冲突检测：新事实带 `updated_at`，同 key 覆盖旧值，旧值进历史不删除；
- 批量抽取放在 session 结束时跑一次，不在对话中途抢写。

**读取要分区**：稳定层全文注入；项目层按当前命名空间取；事件层只在用户问"我们上次聊了什么"时才检索。**遗忘要显式**：提供 `memory_delete` 工具和 TTL 机制，临时偏好（比如"这周优先做 A"）到期自动降级。

## 踩坑点

- **把猜测当事实存**。早期版本让 Agent 自由总结记忆，结果存了一堆"用户可能喜欢 X"，后面每次都错。改成只记明确表达、低置信度进 review 队列后才稳定。
- **不做命名空间隔离**。工作项目的记忆串到私人任务里，Agent 推荐一堆不相关的东西。`scope` 字段必须从第一天就有。
- **记忆注入位置随意**。稳定偏好塞在长 prompt 尾部会被"稀释"，放头部并明确标注"以下为用户长期偏好"效果好得多。
- **对稳定层用向量检索**。几十条数据上搞 embedding 纯属自找麻烦，纯文本文件 + 固定注入即可，检索只留给事件层。
- **不给用户查看/删除入口**。记忆系统一旦让人觉得是黑箱，信任就没了。哪怕第一版只是个 `memory list` 命令，也必须有。

## 可复用建议

- 每条记忆固定 schema：`{content, scope, confidence, source, created_at, updated_at}`，别裸存字符串；
- 稳定层设 token 上限（比如 500），超了强制触发合并淘汰；
- 用"重放测试"验证：拿历史 session 重跑，对比有记忆/无记忆的行为差异，比拍脑袋靠谱；
- 先做人审再上全自动：抽取候选记忆 → 出 diff → 用户确认，跑顺两周再放开。

## 总结

记忆系统的本质不是"存得多"，而是"存得准、取得对、忘得掉"。分层控制生命周期，写入克制、读取分区、遗忘显式，再配上可审查的 schema，一个几百行代码的 MCP memory server 就能让 Agent 的长程体验明显上一个台阶。建议从稳定偏好层做起，事件层最后加——先把最值钱的 20% 做对。
