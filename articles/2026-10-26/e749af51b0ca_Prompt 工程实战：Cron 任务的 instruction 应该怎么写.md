## 背景

OpenClaw 的 cron 任务本质上是“无人值守的冷启动会话”：到点触发，agent 拿着你写的 instruction 从零开始执行，跑完即结束。它和聊天窗口里随口一句“帮我看看 XX”完全是两回事——聊天里有上下文、有你在场；cron 里两者都没有。所以 cron 的 instruction 不是普通提示词，更像一份交接文档。

## 问题

我早期的 cron instruction 大多长这样：“每天早上汇总一下我的 GitHub 通知”。跑了两周，问题接连出现：

- 汇总有时发出来了，有时静默消失，发到哪个渠道全看 agent 心情；
- 某天数据源挂了，agent 自己“脑补”了一份看起来很合理的日报；
- “早上 8 点”到底是哪个时区的 8 点，我没写清楚；
- 两周后连我自己都说不清这个任务的确切边界。

核心矛盾：instruction 沿用了人与人聊天的口语习惯，而执行方是一个没有上下文、会自主调用工具的 agent。

## 做法

把每条 cron instruction 当成给“只来这一次、不会再问你任何问题的新同事”写的工单。我现在的模板固定七段：

```text
【目标】一句话说清要产出什么
【数据源】用哪个工具/命令，写全，如：gh api notifications
【步骤】1/2/3，不超过五步
【输出】字数上限 + 固定结构
【投递】发到哪个渠道，是否 deliver
【异常】拿不到数据时：明确报错，禁止编造
【禁止】不追问、不做清单之外的额外操作
```

一条实际在跑的 GitHub 日报，供对照：

```text
【目标】生成过去 24 小时 GitHub 通知摘要
【数据源】执行 gh api notifications
【步骤】拉取列表→按 repo 分组→只保留提及我的 issue/PR
【输出】200 字内，每条一行：repo 名 + 一句话说明
【投递】发送到 #dev 渠道，deliver 为真
【异常】命令失败或返回为空：发送“数据源异常：<原因>”，不得编造
【禁止】不执行任何 git 写操作
```

写完先手动触发验证一遍，再挂到定时上。

## 踩坑点

- **默认 agent 记得上次。** cron 各次执行之间没有共享对话记忆，“继续上次的报告”必翻车。状态要么落盘成文件并在 instruction 里写明路径，要么每次自包含。
- **输出格式不锁定。** 如果输出还要喂给下一段自动化，格式漂移迟早把下游搞炸。可以要求 agent 末尾固定输出一行状态（OK / FAILED + 原因），排查时救命。
- **范围写太宽。** “看看有什么新东西”会让 agent 自由发挥，token 消耗和跑偏概率一起涨。宁可窄而明确。
- **忽略时区与重叠。** 确认调度器用的是哪个时区；耗时任务要防止上一轮没跑完、下一轮又起。
- **长期打补丁。** 改需求就往末尾追加一句，最后前后矛盾。要改就整体重写，像 review 代码一样过一遍。

## 可复用建议

1. 七段模板直接抄，缺哪段补哪段；
2. 上线前做两次测试：正常手动触发一次，再故意断掉数据源，验证异常分支真的会报错而不是编数据；
3. 单条 instruction 控制在一屏以内，写不下说明任务该拆成多个 cron；
4. 任务名起得自解释一点——半年后唯一的维护者是你自己。

## 总结

Cron instruction 的质量决定了无人值守自动化的下限。原则只有一条：假设执行者对你的项目一无所知，也没有机会回头问你。把目标、数据源、格式、投递、异常全部写死，留给 agent 的自由发挥越少，定时任务越稳。
