## 背景

OpenClaw 的长期记忆落在 workspace 的 memory 目录里，`memory_recall` 负责在对话中把这些内容找回来。默认走全文/关键词检索，社区常见的改造方向是接 embedding 做语义检索。问题来了：值得吗？我用自己的记忆库跑了一轮对比，把结论和数据整理在这里。

## 问题

两个典型症状：

- **全文搜索**：换个说法就搜不到。当时记的是“公司 VPN 配置”，三个月后问“在家怎么连内网”，关键词对不上，recall 返回空。
- **语义搜索**：查询模糊时返回一堆“看起来相关”的结果，但精确 token 丢失。搜项目代号、一串命令，经常给出语义相近但不是那条的记录。

## 做法分三步，建议照顺序来，别跳步

1. **先建评测集**。从历史会话里挑 30 条真实的回忆请求，人工标注期望命中的 memory 文件/段落。没有这一步，后面全是玄学。
2. **跑全文基线**。SQLite FTS5 + BM25（或直接 ripgrep），记录 recall@5 和 MRR。
3. **加语义，做混合召回**。embedding 召回 top20 + BM25 召回 top20，用 RRF 合并取 top5 进上下文。

实测数据（个人记忆库约 600 条笔记）：

| 方案 | recall@5 | 备注 |
|---|---|---|
| 纯全文 | ~78% | 改写类查询丢分严重 |
| 纯语义 | ~81% | 精确 token 类查询反而不如全文 |
| 混合 | ~92% | 每次 recall 多一次 embedding 调用，延迟 +150ms 左右 |

混合方案在中间场景就已经拉开差距，结论很清楚。

## 踩坑点

- **FTS5 默认分词器对中文基本是按字符切**。裸用 unicode61，混排词命中率看运气，要上 trigram 或接 jieba，别直接开箱用。
- **embedding 模型关键是“一致性”而非榜单名次**。写入和查询必须同一个模型，中文短句检索用 bge 系列够用；换模型 = 全量重建索引，没有捷径。
- **chunk 粒度**。整篇 md 入库，200 行的笔记向量被稀释；按标题切分成 200-400 字一块、带上标题元数据后，语义命中率明显回升。
- **索引过期**。memory 是活的，人工编辑后向量索引不会自己更新。我把重建挂在 workspace 文件变更事件上，600 条全量重建也就几秒，别为了省这点事做增量。
- **分数不可比**。BM25 分数和余弦相似度不在一个量纲，直接加权调参是深坑，RRF 按排名合并稳得多。

## 可复用建议

- 记忆库在几百条以内时，**先只用全文**。检索组件的维护成本经常被低估，够用就别上向量。
- 引入语义的唯一判断标准：评测集上**改写类查询的 miss 率**。miss 超过两成再动手。
- 混合召回用 RRF，不要手调权重。
- recall 空结果时记日志——评测集应该是从日志里长出来的，不是拍脑袋造的。

## 总结

这不是“语义 vs 全文”的二选一，而是“什么时候需要语义”的时机问题。全文便宜、可解释、对精确 token 强；语义抗改写但糊。对 `memory_recall` 这种高频小请求场景，我的答案是：**全文打底 + 语义补召回 + RRF 合并**，实测投入产出比最好。先量化，再动手。
