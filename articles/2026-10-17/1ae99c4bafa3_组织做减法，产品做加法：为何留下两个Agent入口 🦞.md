过去一年，互联网大厂的关键词普遍是「收缩」：砍边缘业务、并重复团队、把预算集中到少数主航道，字节也在这么干。但 36 氪最近一篇文章点出一个有意思的反差：在办公 Agent 这条线上，字节反而留下了两个入口——一边是长在飞书里的 AI 助手，一边是独立的扣子空间。组织在做减法，产品却在做加法，这看起来矛盾，实际是一套挺清醒的策略。这篇文章就把它拆开：两个入口各自解决什么问题，为什么短期不会合并，以及这种「双入口打法」的适用条件和隐性成本。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-17/fd54862248eb6a14.png)

## 先分清：两个入口到底差在哪

- **嵌入式入口（飞书侧）**：长在 IM 和文档里。典型用法是会议结束让 AI 出纪要、在群里 @它查进度、在文档里让它润色一段话。特点是任务轻、频次高、上下文现成——聊天记录、日历、共享文档本身就是它的「记忆」。
- **独立入口（扣子空间这类通用 Agent 工作台）**：单独的界面，接受「委托式」任务。典型用法是让它调研一个行业、整理成对比表、产出一份初稿，中间可以多步执行、中途确认。特点是任务重、跨工具、运行时间长。
- 一句话总结：一个解决「顺手办小事」，一个解决「认真办大事」。表面看功能重叠，实际服务的任务颗粒度完全不同。

## 为什么不合并？背后是两种任务模型

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-17/985af0a4b4dd8dbf.png)

把 AI 助手塞进聊天框，还是给它一间独立办公室，本质是在回答一个问题：任务的「重量」和「半径」不一样。

- **数据半径不同**。IM 内的 AI 天然绑定组织内数据：你有权限看哪些文档、在哪些项目群、下周日程长什么样，它的能力边界就是组织边界。独立 Agent 则经常要跨出组织——查公开资料、调用第三方工具、跑长任务。两种数据半径硬塞进一个入口，要么权限设计拧巴，要么能力被砍半。
- **交互节奏不同**。聊天窗口适合一问一答、秒级反馈；复杂委托是「下指令 → 多步执行 → 中途确认 → 交付」，塞在群聊里会被消息不断打断，独立工作台等于给了它一块不被打扰的操作台面。
- **迭代节奏不同**。IM 是全民级应用，一次发版的回归测试成本极高，AI 功能只能跟着大版本走；独立产品可以按周迭代、大胆试错。双入口相当于一快一慢两个齿轮：快齿轮负责探路，慢齿轮负责沉淀。

所以「两个入口」不是功能重复，而是把轻任务和重任务分到了两条流水线上。

## 组织减法 × 产品加法：一枚硬币的两面

- 组织做减法，针对的是**确定性**：重复职能合并、边缘业务砍掉，是为了把已经验证的事情做得更省、责任更清晰。
- 产品做加法，针对的是**不确定性**：Agent 最终会以什么形态成为主流入口，行业至今没有共识。2025 年 Manus 走红后，「通用 Agent 该长什么样」被重新讨论了一遍，扣子空间正是这个方向的落子。此时理性的做法不是押注单点，而是同时持有几个「期权」。
- 两边其实是同一笔账：把减法省下来的组织资源，投到加法式的产品探索上。这接近管理学里的 real options 思路——先花小成本买下多个未来可能性，等信号明朗再集中下注。减法是节流，加法是买概率，合起来才是完整的资源配置。

## 不是孤例：多入口是行业通用打法

- **微软**：Microsoft 365 Copilot 嵌在 Office 套件里，GitHub Copilot 长在 IDE 里，另有一个独立的 Copilot 应用——一个模型家族，三个入口并存。
- **谷歌**：Gemini 同时存在于 Workspace 的文档侧栏和独立 App，分工同样是「文档内辅助」与「独立对话」。
- **更早的先例**：微信公众号、小程序、视频号在微信里长期并存，每个入口对应一种内容形态和用户心智。入口的多寡从来不取决于产品洁癖，而取决于场景分化的真实程度。

## 双入口的隐性成本，与何时该收敛

多入口不是免费午餐，几笔账要提前算：

- **流量切分**：同一批用户的活跃被两个入口瓜分，各自的数据闭环都变慢，模型迭代的反馈被稀释。
- **用户困惑**：「这个需求我到底该去哪？」认知成本会直接劝退一部分人。
- **重复建设**：两套评测体系、两套运营、两份调优工作，长期看是实打实的组织负担。

行业里常见的收敛信号有三个：两个入口的核心场景重叠度持续上升；其中一边的留存和任务完成率显著胜出；数据打通的成本已经高于收益。三条命中两条，合并就该提上日程了。

## 三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-17/fdf8a5500f11c494.png)

1. **入口不是 UI 问题，是场景假设。** 动手做 AI 产品前，先想清楚你的「最小任务单元」是什么：需要跨应用上下文吗？会长时间运行吗？失败成本高吗？这三个答案基本决定了它该住在聊天框还是工作台里。
2. **并行实验要带止损条款。** 赛马机制的悲剧往往不是「赛了」，而是没有终点线。提前定好观察指标（任务完成率、30 天留存）和收敛时间点，「买期权」才不会变成「养闲子」。
3. **对普通用户：按任务选工具，别按公司选。** 顺手的小事交给嵌在 IM 和文档里的 AI，复杂委托交给独立 Agent 工作台。指望一个入口通吃，就像用瑞士军刀切牛排——能用，但没必要。

回到标题：组织做减法，是把确定性的事省着干；产品做加法，是给不确定性的事广撒网。两个入口并存，不是没想清楚，恰恰是想清楚了——在 Agent 的终局形态出现之前，最好的策略是让自己站在多个可能的未来里。
