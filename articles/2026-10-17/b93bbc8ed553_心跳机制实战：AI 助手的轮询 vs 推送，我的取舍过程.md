## 背景

OpenClaw 这类常驻型助手有个天然矛盾：模型本身是被动触发的，但用户期望它"主动"。心跳（heartbeat）就是补上这一层的机制——让 agent 周期性醒来，检查任务清单、跟进未完成事项。默认实现是轮询：每隔 N 分钟跑一次轻量 prompt，读一下 HEARTBEAT.md，有活干活，没活闭嘴。

## 问题

跑了一段时间后我发现两个极端都不对：

- 间隔设 30 分钟：Token 花销可预测，但 CI 失败、监控告警这类事要等半小时才知道，"主动性"形同虚设。
- 间隔压到 1 分钟：响应快了，但一天几百次空转，token 账单难看，大量"无事发生"的输出还会污染会话记录。

推送（webhook / MCP notification）看起来是正解，但每个事件源都得具备推送能力，还要自己维护接收端点、鉴权和去重——复杂度只是从"等待"转移到了"接收"。

## 做法

我的方案是分层混合，步骤如下：

1. **事件源盘点**。把 agent 需要感知的东西分两类：能原生推送的（GitHub、告警系统、Home Assistant）和只能轮询的（本地文件、无 webhook 的内部 API）。
2. **保底轮询**。保留 30 分钟低频心跳作为基线和兜底，心跳 prompt 压到最简，明确"无事项则不输出"。
3. **高价值事件走推送**。写了个小插件做本地 webhook 接收器，校验 shared secret 后把事件注入会话队列；MCP server 侧用 notification 上报状态变化。
4. **中间加一层聚合**。推送不直接触发模型调用，先进队列去重、按优先级分层：紧急事件立即唤醒，普通事件等下一次心跳统一消化。
5. **记录唤醒原因**。每次醒来打一条日志：heartbeat 还是 push、消耗多少 token、有没有实际动作。这是后续调参的依据。

## 踩坑点

- **心跳 prompt 太胖**。早期心跳复用了完整会话上下文，一次空转烧几千 token。后来单独建精简心跳上下文，成本降了一个数量级。
- **webhook 端点裸奔**。没加鉴权跑了一周才意识到，任何人都能伪造事件唤醒 agent——本质上是免费的提示注入入口。务必校验来源 + secret。
- **推送风暴**。某次监控抖动，两分钟打了二十多个 webhook，agent 疯狂空转。接收器必须做冷却和合并，同一来源 N 分钟内只留最新一条。
- **宿主机休眠丢事件**。笔记本合盖，推送直接丢了。接收器要落盘队列，心跳醒来后补消化——这也是保留轮询兜底的另一个理由。

## 可复用建议

- 一条经验法则：**晚发现无所谓的状态用轮询，晚发现会出代价的状态用推送**。
- 不要二选一。低频心跳当兜底 + 推送保时效，心跳顺便充当推送丢失的"清扫器"。
- 给主动唤醒设每日 token 预算，超了自动拉长间隔。
- 推送先进队列、由心跳或阈值触发消化，比每条推送都直接打模型便宜得多。

## 总结

轮询简单、稳、成本可预算，代价是延迟和空转；推送及时、省 token，代价是接收端的可靠性、鉴权和去重全得自己扛。个人助手这个量级，我的结论是混合制：心跳做地基，推送做快车道，中间一层队列做缓冲。先量化再调参——没有唤醒日志，一切优化都是猜。
