## 背景

Agent 的价值不在对话本身，而在它能替你动手。一个只会聊天的模型意义有限，真正让 OpenClaw 有生产力的，是它背后那层“工具面”：查数据、发通知、调内部服务。这层面对接得好不好，直接决定 Agent 是玩具还是同事。

## 问题

第一次对接外部服务时，常见的两条弯路：

- 把 API 文档整段塞进 system prompt，指望模型自己拼请求；
- 一口气注册几十个工具，结果模型选错、参数乱填。

两条路的共同问题是：没把“模型擅长的事”和“工程该兜底的事”分开。模型擅长理解意图、编排步骤；而鉴权、重试、幂等、脱敏，必须由代码层兜住。

## 做法

我目前总结出三层接法，按维护成本从低到高：

1. **脚本即工具（skill 化）**：把一个 API 调用封装成独立技能，参数收窄到 3 个以内，描述里写清“什么时候用我、什么时候别用”。OpenClaw 负责调度，脚本负责执行。
2. **MCP server 统一托管**：同一家服务的接口超过五六个，就别一个个写 skill 了。起一个 MCP server，把鉴权和会话管理收敛在一处。工具粒度按业务动作切（“创建工单”），不要按 HTTP 动词切（"POST /tickets"）。
3. **插件层做横切逻辑**：重试、限流、日志、密钥轮换这类逻辑放进统一 client 或插件，别散在各个工具里。

无论哪层，有几条硬规则：

- 密钥只走环境变量或本地配置，绝不进 prompt 和对话历史；
- 读操作先放开，写操作默认人工确认，且尽量幂等（带 client 生成的请求 ID）；
- 响应体做裁剪，只回传模型需要的字段——几十 KB 的原始 JSON 会瞬间吃掉上下文。

## 踩坑点

- **工具描述含糊**：“查询数据”这种描述，模型会拿它去查任何东西。描述里要写清操作对象、返回什么、典型用法。
- **429 不退避**：没加退避的重试等于放大攻击，指数退避加抖动是底线。
- **POST 重试造成重复下单**：写接口务必带幂等键，否则 Agent 一次“卡顿重试”就是生产事故。
- **响应里的敏感字段**：日志和回传内容都要脱敏，token、手机号在 client 层就拦掉。
- **MCP server 版本漂移**：上游接口改了、你的 server 没动，Agent 会拿幻觉参数硬调。给 server 锁版本，上线前跑一次健康检查。

## 可复用建议

- 工具数量控制在 10 个以内，模型的选择准确率随工具数明显下降，宁少勿多；
- 每个工具配一条“反例说明”（何时不该调用），比十条正例更省 token；
- 所有外呼加统一超时（我设 15s）和结构化错误返回，让模型拿到可读的错误信息而不是裸堆栈；
- 准备一个只读的“探活工具”做冒烟测试，Agent 启动时先探一次，再干活。

## 总结

对接外部服务本质上是一次握手：模型伸出手表达意图，工程层握住它确认边界。OpenClaw 的正确打开方式，不是让模型更像工程师，而是让工程层足够可靠，模型只做它擅长的那一半。建议先从一个小而清晰的 skill 跑通全链路，再逐步上 MCP 和插件层——稳比快重要。欢迎在社区贴出你自己的工具封装结构，一起对齐最佳实践。
