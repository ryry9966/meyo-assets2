## 背景

Agent 的能力上限，往往不在模型本身，而在它能调用哪些工具。OpenClaw 这类框架把"模型决策"和"工具执行"分开之后，对接外部服务就成了绕不开的一步：查库存、发工单、读内部数据库……模型只负责"决定调什么"，真正握手的是你写的那层适配代码。

## 问题

实践中对接失败，很少是"模型不会调"，更多是工程细节没兜住：

- 工具描述含糊，模型靠猜填参数，调用频繁落空；
- 上游接口慢或抖动，整个会话被卡死；
- 密钥散落在提示词或代码里，日志一打印就泄露；
- 报错把原始堆栈直接塞回上下文，模型看不懂，人也看不懂。

## 做法

我的惯用路径分五步，以对接一个内部 REST 服务为例：

1. **选接入形态**。一次性调用直接封成 HTTP 工具；多个 Agent 复用、或上游有独立鉴权逻辑，就单独起一个 MCP server，把该服务的操作收敛进去。工具数量克制，一个上游尽量不超过十个。
2. **认真写 schema**。名称用动词加宾语（如 `query_order_status`），description 写清"什么时候该用、不该用"，参数给 enum 和示例。这部分本质是给模型看的接口文档，值得花时间。
3. **鉴权收口**。密钥放环境变量或密钥管理服务，在适配层注入，绝不经手模型；日志统一做脱敏。
4. **错误翻译**。上游 4xx/5xx 不能原样返回，转成一句模型可执行的指令，例如"订单号不存在，请先向用户确认格式"，并区分可重试与不可重试两类。
5. **超时与重试**。所有调用设硬超时；GET 类幂等操作做指数退避重试，POST 类生成幂等键，避免网络抖动导致重复下单。

## 踩坑点

- **长任务阻塞**：导出报表跑三分钟，同步等待会拖死会话。改成"提交任务返回 job_id，再轮询或回调"，模型每次只做一步。
- **返回值过大**：一次塞 200 条记录回上下文，token 烧得快且模型抓不住重点。适配层先做分页和摘要，只回必要字段。
- **非幂等重试**：支付类接口重试两次就是两笔钱。先确认上游语义，再决定要不要上重试。
- **schema 漂移**：上游悄悄加了个必填字段，Agent 静默失败一周才发现。给关键工具写冒烟脚本，挂进 CI 定期跑。

## 可复用建议

- 每个 MCP server 只对接一个上游，工具命名带前缀，避免多 server 挂载后撞名。
- 上线前用 dry-run 跑通主链路：请求打到测试环境，验证参数组装和各错误分支。
- 每次工具调用记录 trace_id、入参摘要、耗时和结果状态，事后排障基本全靠它。

## 总结

对接外部服务没有魔法，本质是把"给模型的接口文档"和"给系统的工程护栏"都写扎实。schema 决定模型调得准不准，超时、重试、脱敏决定系统稳不稳。把适配层当成一个正经的小服务来维护，Agent 与外部世界的握手才算真正握住。
