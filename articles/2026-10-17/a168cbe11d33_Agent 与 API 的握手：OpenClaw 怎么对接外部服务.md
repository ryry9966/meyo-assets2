## 背景

Agent 的能力上限，基本取决于它能调用哪些服务。OpenClaw 本身不自带业务能力，真正的生产力来自把外部 API——内部微服务、SaaS、数据库网关——封装成 Agent 可用的工具。这件事看起来只是"发个 HTTP 请求"，但一旦调用进入 Agent 的自动决策回路，很多平时不会出问题的环节开始接连出问题。

## 问题在哪

人调 API 时，每一步都有人盯着，看到报错会停下来想。Agent 不是。它会在几秒内连续调用，并根据返回内容自行决定下一步。于是三个老问题被放大：

1. **契约不清**：模型只能靠工具的 name、description 和参数 schema 理解接口，描述含糊就会传错参数；
2. **失败不可预期**：没有超时和重试策略，一次挂起就卡死整轮会话；
3. **权限过大**：一个全权限 token 打天下，出事没有边界。

## 做法与步骤

以 MCP server 或插件方式对接时，建议按这个顺序来：

1. **先定契约，再写实现。** 工具描述就是给模型看的 API 文档。写清楚这个工具做什么、每个参数的语义与格式、失败时返回什么。宁可啰嗦，不要简略。
2. **密钥不进上下文。** 密钥放环境变量或密钥管理服务，OpenClaw 侧只持引用；绝不出现在 prompt、日志或工具返回值里。
3. **超时、重试、幂等三件套。** 读操作设短超时、快速失败；写操作必须幂等（幂等键），因为 Agent 天然会重试。
4. **错误要"说人话"回给模型。** 不要把原始堆栈塞回去，返回结构化信息：错误码、原因、建议动作（重试/放弃/换参数）。模型下一步的决策质量，取决于你返回的错误质量。
5. **裁剪返回体。** 只返回任务需要的字段，大结果集做分页，别让一次列表查询撑爆上下文。
6. **灰度上线。** 先 dry-run 模式跑通参数生成，再放开真实调用；写操作加确认门。

## 踩坑点

- 工具描述只写"发请求"三个字，模型自然乱传参；
- 没设超时，上游服务一抖，整轮会话干等；
- 原始报错直接回灌上下文，几千 token 的 JSON 让模型"消化不良"；
- 上游 API 改了字段名，工具静默失败——没有契约测试根本发现不了；
- 调试时把真实密钥贴进对话，之后既忘不掉也删不干净。

## 可复用建议

- **每个外部服务一个薄适配层**：统一处理超时、重试、日志、字段裁剪，业务逻辑不散落各处；
- **记录调用摘要**：请求参数摘要 + 结果摘要 + 耗时，出问题能回放；
- **契约测试锁 schema**：CI 里对上游响应结构做断言，漂移当场报警；
- **最小权限 token**：按服务拆凭据，一份泄露不至于全线失守。

## 总结

对接外部服务，本质不是"会发 HTTP 请求"，而是把一套为人设计的接口，翻译成 Agent 能稳定、安全、可预期使用的工具。契约写清楚、失败可预期、权限收到最小，这三件事做到位，握手才算真的握上了。
