## 背景

Agent 的实际价值，很大程度取决于它能触达哪些真实系统。OpenClaw 的定位是 agent 网关：模型负责决策，外部服务负责执行，中间靠一层工具完成"握手"。这层握手做不好，agent 要么只能聊天，要么到处闯祸。

## 问题

对接外部 API 时，社区里反复出现三类问题：

1. **裸调 vs 封装**：直接在 prompt 里贴一段 curl 让模型"自己想办法"，偶尔能跑通，但鉴权、超时、错误处理全靠运气。
2. **凭据暴露**：API key 出现在配置文件、日志甚至对话上下文里。
3. **粒度失控**：工具拆得太碎，模型选不对；包得太粗，参数一大堆，模型乱填。

## 做法：三条对接路径

按工程成本从低到高：

**1. Skill / 提示层（原型期）**
只做只读、无副作用的查询，把接口文档压缩成一段描述放进 skill。用来验证"这个服务值不值得接"，不要上生产。

**2. 轻量 HTTP 工具（生产首选）**
为服务写一个专用工具插件，核心四件事：

- 用 JSON Schema 定义参数，工具描述是"写给模型看的文档"：动词 + 对象 + 约束，例如 `query_ticket_status`——按工单号查询状态，工单号格式 TKT-xxxx。
- 鉴权走环境变量，运行时注入 header，不进 prompt、不进配置仓库。
- 设超时（建议 10–30s）与有限重试，且只对幂等的 GET 重试。
- 错误结构化返回：`{"error": "...", "hint": "..."}`，让模型能按 hint 自愈，而不是拿到一坨 HTML 报错页。

**3. MCP Server（多端复用）**
如果同一个服务要被多个 agent/客户端使用，包成 MCP server 一次，处处挂载。OpenClaw 对 MCP 工具的发现与调用是标准化的，长期维护成本最低。

一个最小工具定义大致长这样：

```json
{
  "name": "create_issue",
  "description": "在工单系统创建问题，需先经用户确认",
  "parameters": { "title": "string", "severity": "P0|P1|P2" },
  "timeout_s": 20
}
```

## 踩坑点

- **返回体不裁剪**：几 KB 的 JSON 直接塞进上下文，两三轮就把窗口吃光。在工具层做字段过滤和截断。
- **写操作没有确认闸门**：create/send/delete 这类非幂等调用，务必加"先复述、后执行"或人工确认环节。
- **工具描述含糊**："查询数据"这种描述会让模型猜参数。每个参数都要写清格式和示例。
- **没设超时**：外部服务挂了，agent 表现为"卡住思考"，排查半天发现是请求没配超时。
- **key 进了 git**：环境变量 + `.env` 进 gitignore，CI 里加一次密钥扫描。

## 可复用建议

1. 命名约定：读操作 `get_/query_/list_`，写操作 `create_/update_/delete_`，方便统一挂确认策略。
2. 每个错误响应带 `hint` 字段，把"下一步怎么办"写给模型看。
3. 一个服务一组工具，不要做万能的 `call_api(url, body)`——那等于把安全问题原样丢回给模型。
4. 上线前用固定脚本回放一批调用，验证 schema 和错误路径，别只靠手测。

## 总结

对接外部服务不是"模型能发出 HTTP 请求"就算完成，而是把鉴权、超时、错误语义、副作用控制这些工程问题在工具层解决掉，让模型只做决策。Skill 验证方向，轻量工具承接生产，MCP 承担长期复用——按这个顺序走，握手才算握稳。
