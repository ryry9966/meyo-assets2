## 背景

OpenClaw 里 Agent 的能力边界，基本由它能调用的工具决定。模型本体只负责"想"，真正"做到"靠工具层——不管是内置插件、自研工具，还是通过 MCP server 挂进来的外部能力。社区里最常见的问题不是"接不上"，而是"接上了但不稳"：偶发超时、重试打出重复请求、凭据泄漏到日志、Agent 拿到一坨 JSON 后开始胡乱解读。

这篇帖把我们团队对接外部 HTTP 服务的经验整理一下，侧重工程细节，不谈选型玄学。

## 问题：握手不是调通就完了

把一个 REST API 包成 OpenClaw 工具，demo 级别大概 20 行代码。但生产上要回答几个问题：

- API 挂了或慢了，Agent 会不会无限等待？
- 重试会不会产生副作用（下单、发消息）？
- 返回 401/429 时，Agent 能不能"看懂"并采取正确动作？
- API key 存在哪、谁能看到？

这些问题不解决，对接就只是"看起来能用"。

## 做法：四步握手

**1. 收窄工具边界。** 不要把整个 API 面暴露成一个万能工具。按业务动作拆，比如 `query_order(order_id)`，而不是 `call_api(path, params)`。参数 schema 越窄，Agent 误用概率越低。工具描述里写清"什么时候该用、什么时候不该用"，比堆参数说明更有效。

**2. 凭据走环境变量 + 最小权限。** API key 一律从环境变量读，配置文件和日志里禁止出现明文。有条件就用只读 scope 的 key 先跑通，再按需放开。OpenClaw 的插件进程与模型是隔离的，凭据只停留在插件侧，这是默认安全边界，别破坏它。

**3. 超时、重试、幂等三件套。** 每个出站调用设显式超时（我们一般 10s）。只对幂等操作（GET、幂等的 PUT）自动重试并做指数退避；有副作用的 POST 重试前先查一次状态，上游支持幂等键就带上。遇到 429 优先读 `Retry-After` 头，别自己拍脑袋。

**4. 收敛返回值。** 上游返回 200 行 JSON 时，插件要负责裁剪：只保留 Agent 决策需要的字段，错误统一转成 `{ok, error_code, message}` 三段式。Agent 的上下文很贵，也更容易被噪音带偏。

## 踩坑点

- **重试打出重复订单。** 早期我们对所有 5xx 一律重试，结果上游实际已受理，超时后重发，出现两笔单。现在写操作必须带幂等键才允许重试。
- **工具描述太"文学"。** 只写"查询订单信息"，Agent 会拿它查任何东西。改成"仅根据订单号查询单笔订单状态，不接受其他参数"后，误调率明显下降。
- **把原始异常抛给模型。** `ConnectionResetError` 这类堆栈进了上下文，Agent 会开始编原因。统一映射成可读的错误码。
- **MCP schema 与上游版本漂移。** 上游 API 加了必填字段，MCP schema 没更新，Agent 反复重试到天荒地老。给工具层加 schema 版本检查，启动时校验一次。

## 可复用建议

对接新服务前过一遍清单：超时设了吗？重试有幂等保护吗？错误码收敛了吗？凭据进环境变量了吗？返回值裁剪了吗？工具描述写了"不该用"的场景吗？全部为"是"再上线。

另外建议每个工具留一个 `dry_run` 参数，测试环境先空跑，比事后回滚便宜得多。

## 总结

OpenClaw 对接外部服务的本质，是把一个不稳定的网络世界翻译成 Agent 能稳定理解的工具语义。握手协议不复杂：窄接口、密钥隔离、超时重试幂等、返回收敛。做好这四件事，大部分"Agent 乱来"的问题会消失一大半。欢迎在回帖里补充你们踩过的具体坑。
