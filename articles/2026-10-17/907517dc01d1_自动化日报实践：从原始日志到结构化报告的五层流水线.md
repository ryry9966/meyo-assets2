## 背景

做自动化的人大多有类似经历：一天下来，git 提交、CI 结果、Agent 会话记录、服务告警散落各处，第二天早上花半小时拼一份日报，大部分时间在复制粘贴。OpenClaw 侧的 cron + Agent + MCP 工具链足够把这件事跑成流水线，难点不在能不能跑，而在产出是否稳定、可信、可回溯。

## 问题：别把原始日志直接丢给 Agent

最直觉的做法是写个 cron，把当天所有日志塞进上下文让 Agent 总结。我们试过，三个问题：

1. **token 成本失控**：一天的原始日志轻松几十万 token，有信息量的内容不到 5%；
2. **输出不稳定**：同样的日志，昨天漏了部署失败，今天补一段“一切顺利”；
3. **无法回溯**：报告写“完成 X”，依据在哪条日志里，查不到。

结论：LLM 该做归纳，不该做检索和清洗。

## 做法：五层流水线

最终落地结构是五层，每层落盘中间产物：

1. **采集层**：cron 定时拉取各源日志（git log、CI API、Agent 会话记录），按 `raw/YYYY-MM-DD/` 存快照。关键点：所有源先转本地时区，再按 00:00 截断日期边界。
2. **结构化层**：纯规则解析，每类日志一个独立小脚本，输出统一 JSONL：`{time, source, project, event, status, ref}`；解析失败的行进 `unparsed` 桶，只记行数，不丢弃。
3. **聚合层**：用 jq 做去重、按项目分组、错误率统计，产出 `stats.json`，纯确定性计算，可单测。
4. **生成层**：Agent 只拿 `stats.json` + unparsed 摘要 + 固定模板（今日完成 / 进行中 / 风险 / 明日计划）生成 markdown。prompt 里明确约束：只允许引用输入中出现的事实，没有数据的小节写“无”。
5. **投递层**：推送 IM 群，报告末尾附 raw 快照路径，方便回查。

## 踩坑点

- **时区边界**：CI 用 UTC、本地用 CST，第一版把前一天下午的提交全算错了日期。修复：采集层统一做时区转换。
- **格式漂移**：某天上游改了日志字段，正则静默返回空，日报照发但内容为空。修复：解析层加 schema 校验，unparsed 占比超过 10% 时在报告顶部打警告。
- **静默失败**：流水线挂了三天没人发现。修复：加一条自检 cron，08:30 未检测到当天报告文件就让 Agent 单独发告警。用 cron 监控 cron，朴素但有效。
- **敏感信息**：日志里混着内网地址和临时 token。修复：投递前加一步正则脱敏，替换成占位符。

## 可复用建议

- **规则先行，LLM 兜底**：能用 jq 提取的字段就不让模型猜，LLM 只处理规则覆盖不了的模糊文本。
- **每层落盘**：raw → parsed.jsonl → stats.json → report.md，任何一层出错都能单独重跑。
- **模板与 prompt 分离**：报告骨架放模板文件，prompt 只管填充约束，改版式不用动 prompt。
- **解析器小而独立**：每个 50 行以内，配最小单测，上游改格式时改起来快。
- **保留证据链**：被质疑“数据哪来的”时，raw 路径能直接定位。

## 总结

这条流水线上线两个月，日报从每天 30 分钟人工降到 0，期间修过三次格式漂移、一次时区问题——都靠落盘的中间产物和 unparsed 计数在十分钟内定位。核心经验一句话：**确定性的工作交给脚本，模糊的工作交给 Agent，失败必须可见**。日报本身是小事，但“分层、落盘、自检”这套模式可以平移到周报、告警摘要、会议纪要等任何“原始数据 → 结构化输出”的场景。
