## 背景

OpenClaw 的 agent 不是跑在真空里，它跑在你的某台具体机器上。workspace 里的 tools.md 本质上是写给它的"本机说明书"。很多人的用法停留在罗列"我装了哪些工具"，但它真正的价值在另一件事上：**记录环境差异**。同一套 skills 和提示词，往往要跑在 macOS 笔记本、Linux 服务器、家里那台 NAS 上，而机器之间从来没有完全一致过。

## 问题

Agent 面对不确定的环境信息时，默认行为是猜：猜该用 brew 还是 apt，猜 python 在哪个路径，猜能不能直连外网。猜错一次，就是一轮报错、一次装错包，甚至一次误改文件。把这些差异硬编码进 prompt 或 skill 也行不通——换台机器整套配置就静默失效，而且你很难第一时间发现它"悄悄错了"。

## 做法

1. **划定记录范围**：只写"与默认假设不同"的事实。操作系统与包管理器、运行时的版本管理方式、代理与网络约束、关键路径、明确不能碰的目录。
2. **按可执行事实来写**，每条一行，附一句用法，例如：
   - 运行时：python 由 pyenv 管理，禁止全局 pip 安装；
   - 网络：出网走本机 7890 代理，git 已配置好，不要重复设置；
   - 禁区：某个数据目录只读，改动前必须先询问。
3. **一台机器一份文件**：workspace 用 git 管理，通用行为约定放 AGENTS.md，本机事实放各自分支/独立文件。不要一个文件混写多台机器，再让 agent 猜当前在哪台。
4. **让 agent 探测回填**：新机器接入时，先让 agent 跑一轮探测命令（系统版本、which、端口连通性），把结果整理成 tools.md 草稿，人工核对后提交。它写下的是自己验证过、能执行的事实，比手写可靠。
5. **定期校验**：系统升级或迁移后，让 agent 对照 tools.md 自检偏差，输出 diff 由你确认。

## 踩坑点

- **写成教程或愿望清单**：大段背景介绍，事实密度极低。tools.md 只认可执行的事实。
- **记录会漂移的信息却不标注验证时间**：端口、路径迟早会变，注明"何时实测过"，能提醒你何时该更新。
- **把密钥直接写进文件**：tools.md 会进入上下文，等于明文。密钥放环境变量或独立 secret 管理，文件里只写"去哪取"。
- **与 AGENTS.md 职责混淆**：跨机器的约定进 AGENTS.md，机器专属事实进 tools.md，放错位置迟早同步打架。
- **写太长**：它可能每轮都占上下文，控制在几十行内，密度优先于全面。

## 可复用建议

- 固定五节模板：机器概况 / 运行时 / 网络 / 路径与禁区 / 已知坑，每节限行数。
- 把"探测回填"固化成一个小 skill，新机器接入基本零手写。
- agent 修改 tools.md 时强制走 diff 确认，防止它顺手"编造事实"。
- 机器差异宁可分文件，也不要靠注释和命名约定挤在一个文件里。

## 总结

tools.md 的本质，是你和 agent 之间关于"这台机器长什么样"的契约。原则就四条：**只写事实、只写差异、控制长度、定期校验**。守住这四条，跨机器、跨环境的自动化才不会在某个深夜，因为一条过期的路径悄悄崩掉。
