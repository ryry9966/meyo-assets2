# 背景

社区内容运营有个老大难：有价值的信息源不少（GitHub Release、技术周报、精华帖归档），但人工整理发帖费时，拖久了就断更。我的目标是做一个“定时采集、自动起草、审核后发帖”的机器人，跑在 OpenClaw 的 Agent 体系里，发帖能力用 MCP tool 封装社区 API。

# 最初的问题

第一版很天真：cron 拉数据 → 整包丢给模型 → 直接调发帖接口。跑了三天被迫下线：

- 模型自己“编”了两个不存在的链接，评论区马上有人指出来；
- 任务重试导致同一篇内容发了两次；
- 发帖频率没控制，触发了论坛的反垃圾限流。

结论：把 Agent 当“发布者”是错的，它只能当“起草者”。

# 现在的架构

改成四段式流水线，各段解耦：

1. **采集段**：cron 每 6 小时抓 RSS / Git Release / Issue 关键词，原始数据落 SQLite，带 `source_url` 和 `content_hash`。
2. **起草段**：OpenClaw Agent 读“当日未处理素材表”，只输出草稿 JSON（标题、正文、引用的素材 ID）。链接一律从素材表带出，模型不负责生成 URL。
3. **审核段**：草稿写库，状态 `pending`。规则校验（链接是否在素材表、长度、敏感词）通过后人工确认；前两周全人工点审，稳定后才切自动发布。
4. **发布段**：一个很薄的 MCP tool，只做“接收草稿 ID → 调论坛 API → 回写 post_id”，带指数退避。

# 踩坑实录

- **幻觉链接**：让模型“附上来源”必出事。改法是素材 ID 作为唯一合法引用，发布前逐个校验 URL 是否在库里，不在就拒发。
- **去重**：标题相似度误杀率高。改成 `content_hash` 精确去重 + 同主题 48 小时窗口内只发一篇，简单可靠。
- **重复发布**：cron 超时被调度器重拉，同批素材发了两次。修复是“取出素材”时即写入 `processing` 状态（数据库层原子占用），发布成功才置 `done`。幂等必须做在状态机里，不能指望 Agent“记得”。
- **限流**：论坛 API 有每分钟配额。发布段加令牌桶，发帖时间错开整点，避开社区高峰。
- **风格漂移**：升级模型版本后文风突变，老用户直接问“是不是换人了”。现在 prompt 里固定三篇历史样例做 few-shot，模型版本 pin 死，升级先跑一周影子模式（只存草稿不发）。

# 可复用建议

- 数据流单向：素材 → 草稿 → 待审 → 已发布，每步落库，出问题能回放。
- Agent 只碰文本；“是否发、发到哪、发几次”这类状态决策交给确定性代码。
- MCP tool 尽量薄，鉴权 token 放服务端配置，绝不进 prompt。
- 灰度期的人工审核不能省，那是你发现 prompt 问题的唯一窗口。
- 日志记录 post_id 与草稿 ID 的映射，方便撤回与复盘。

# 总结

上线两个月发了百余篇汇总帖，撤回 3 篇，全是审核段拦下的。最大体会：自动化发帖的难点不在“让模型写出帖子”，而在工程侧的幂等、去重和限流。Agent 负责内容，确定性代码负责纪律，边界画清楚，系统才敢长期挂着跑。
