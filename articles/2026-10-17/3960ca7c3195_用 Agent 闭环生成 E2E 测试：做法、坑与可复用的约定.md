## 背景

E2E 测试是团队里最容易被拖延的活：写起来慢、断言难定、UI 一改就崩。我们最近在一个中等规模的前后端项目里做了次尝试：让 OpenClaw 的 Agent 通过 MCP 工具直接操作浏览器和测试运行器，闭环生成并修复 Playwright 测试。结论先说：可行，但前提是把它当成"会写代码的新同事 + 一套严格的工程约定"，而不是"一键生成测试"的魔法。

## 问题：直接丢给模型会发生什么

最初的做法很朴素——把页面代码和需求贴给模型，让它输出测试文件。结果三类问题反复出现：

1. **幻觉 API**：混用 Cypress 和 Playwright 的写法，调用根本不存在的方法；
2. **同义反复断言**：输入一个值再断言输入框等于这个值，测了等于没测；
3. **廉价选择器**：大量 `nth-child` 和文本匹配，页面稍一动就崩。

根因是模型只有"看"，没有"跑"。它不知道真实 DOM 长什么样，也不知道测试是否真的通过。

## 做法：闭环交给 Agent，标准留给自己

我们最终收敛成五步流程：

1. **收敛范围**：每次会话只做一个核心流程（如下单、登录+权限），明确入口 URL、账号和环境。不要让 Agent"把整个站覆盖了"。
2. **给眼睛**：接入 Playwright MCP，让 Agent 能真实打开页面、读取 accessibility snapshot，而不是凭想象编选择器。
3. **给手**：把 `run_tests`、`seed_db`、`get_trace` 封装成项目内 MCP 工具。Agent 写完自己跑，失败输出和 trace 直接回喂。
4. **限制循环**：约定最多 5 轮修复，每轮必须过类型检查和真实运行；超限就停下交人工。否则 token 会安静地烧光。
5. **人工审断言**：重点只看一件事——断言是否检验了业务结果（接口返回、数据库状态），而不是检验 UI 回声。

## 踩坑点

- **等待滥用**：Agent 特别爱写 `waitForTimeout(3000)`。在约定里强制 web-first 断言后基本绝迹。
- **测试互相污染**：Agent 默认假设环境干净。把种子数据脚本暴露成工具、每条测试自带 setup/teardown 后才稳定。
- **本地通过、CI 挂**：Agent 不了解 CI 的时区和并发限制，关键流程建议先在隔离任务里跑一两周，再进主干门禁。
- **约定没有落盘**：口头要求"用 data-testid"没用，写进仓库的 AGENTS.md，Agent 每次会自动遵守。

## 可复用建议

- 测试规范写成仓库内文档（选择器规则、断言标准、禁止 sleep），比长 prompt 有效得多；
- 项目专属能力一律走 MCP 工具，不要塞 prompt；
- 一个会话一个流程，控制上下文长度和爆炸半径；
- 把 Agent 产出的测试当成实习生的 PR：可用，但必须审。

## 总结

Agent 擅长的是"写—跑—修"这个机械循环，它不擅长、也不应该负责定义"什么算对"。闭环 + 工具化 + 明确约定之后，我们三周补齐了 6 条核心流程的 E2E，维护成本没有明显上升。这不是替代测试工程师，而是把最枯燥的那段循环自动化了。欢迎在社区里交流你们闭环里跑出来的失败率数据。
