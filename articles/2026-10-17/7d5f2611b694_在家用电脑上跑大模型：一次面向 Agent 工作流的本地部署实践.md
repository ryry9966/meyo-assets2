## 背景

做 Agent 和自动化的同学，大部分时间在调云端 API。但有两类需求会把你推向本地部署：一是隐私敏感的数据——本机日志、聊天记录、内部文档——不想出机器；二是高频低价值的调用，比如意图分类、格式清洗、摘要，量大了以后账单越来越显眼。我属于后者：一条本地自动化工作流每天有几千次小调用，全部走云端既慢又贵，于是决定把这部分收回来，在自己那台游戏机上跑。

## 问题

动手前有三个问题要想清楚：

1. 这台机器到底能跑多大的模型？
2. 跑起来之后，能不能胜任 Agent 里的工具调用，而不是只会聊天？
3. 怎么以最小改动接进现有工作流？

## 做法

**第一步：摸清硬件。** 显存是硬约束。粗算：7B 模型 Q4 量化约占 4–5GB，14B 约 9GB，32B 约 20GB——这只是权重，还要给 KV cache 留余量，上下文越长吃得越多。纯 CPU 也能跑，但多步 Agent 循环下每步五到十秒的延迟，体验上等于不可用。

**第二步：选推理引擎。** Ollama 上手最快，自带 OpenAI 兼容接口；llama.cpp 参数更可控；需要并发就上 vLLM（建议 Linux + 显存充裕）。个人工作流用 Ollama 足够。

**第三步：选模型。** 评价标准是工具调用稳定性，不是榜单分数。同尺寸下 Qwen 系列的 function calling 实测明显更稳。建议先拉 7B 验证整条链路，再决定是否上 14B/32B。

**第四步：接入工作流。** Ollama 默认监听 11434 端口，协议 OpenAI 兼容，把 base_url 指过去即可。MCP server 侧一行不用改——对工具层来说，模型只是换了个 endpoint。

**第五步：用真实负载压测。** 挑工作流里最难的一条 trace（多工具、长上下文）跑十遍，统计成功率与参数错误率，别用演示 prompt 自欺欺人。

## 踩坑点

- **上下文长度陷阱**：Ollama 默认 `num_ctx` 很小，Agent 一挂长 system prompt 加一堆工具定义就静默截断，表现为模型"忘了"某些工具。手动调大，同时留意 KV cache 的显存增长。
- **显存溢出是静默降速**：请求超过显存会部分 offload 到 CPU，不报错，但 tok/s 掉一个数量级。要看推理日志确认实际驻留 GPU 的层数。
- **小模型的工具幻觉**：7B 级别在参数多、嵌套深的工具上会编造字段、格式对不齐。对策是简化工具 schema，或者这一步回退云端。
- **并发是单请求世界**：本地推理基本串行，Agent 并行发起的多个调用会排队。要么调 `OLLAMA_NUM_PARALLEL`，要么在工作流层串行化。

## 可复用建议

- **分层路由**：本地模型只接"便宜活"——分类、打标、摘要、格式转换；规划与复杂工具链留给强模型。按调用量算，本地通常能吃掉六七成流量。
- **统一走 OpenAI 兼容协议**接模型，换模型只换 endpoint 不换代码。
- **用自己的 trace 评测**，公开榜单的任务分布和你差太远，参考价值有限。
- 显存按"权重 + 2–4GB 余量"规划，余量全部留给 KV cache。

## 总结

本地部署的定位不是替代云端，而是把工作流里量大、价值密度低的调用收回来，顺便多一条离线兜底路径。折腾下来的结论：16GB 显存是舒适的入门线，跑 14B Q4 做工具调用够用；再往上边际收益递减，不如把精力花在路由策略和工具 schema 的简化上。
