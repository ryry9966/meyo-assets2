## 背景

OpenClaw 里的自动化任务，大多不是"只跑一次"的。定时触发器可能重叠执行，webhook 来源会重推同一条事件，Agent 执行到一半超时后会重放整个计划，MCP 工具调用在网络抖动下也会被客户端重发。换句话说，**失败重试是自动化的常态，不是异常**。

## 问题

如果操作本身不幂等，重复执行就是事故：重复建单、重复发通知、重复消耗 API 配额、写入脏数据。

举一个有代表性的场景：一个每天清理过期会话的插件，因为上游响应超时被重试了两次。第二次执行时它按"当前时间"重新计算了过期集合，把两个本不该删的活跃会话也清掉了。问题不在重试机制——重试本身是对的——而在操作没有保证"执行一次和执行多次结果一致"。

## 做法

**1. 先给操作分类。** 天然幂等的操作（upsert、按唯一键覆盖、按 key 删除）可以直接放心重试；非幂等操作（insert、发消息、递增计数）才需要额外设计。

**2. 为非幂等操作引入幂等键。** 从任务语义生成稳定 key，比如 `task_id + 调度周期 + 参数哈希`。关键是：同一个任务重试时，key 必须不变。

**3. 执行前先落库。** 把运行记录（key、状态、时间戳）写进一张带唯一索引的表，靠数据库约束挡住重复，而不是靠应用层的 if 判断。

**4. 正确处理"未知状态"。** 超时不等于失败——请求可能已经在远端生效。重试前先查询远端实际结果，再决定是跳过还是补偿。

**5. Agent 侧按 step 粒度重试。** 让计划里的每个 step 声明自己的幂等性，失败后从断点继续，而不是重放整个流程。

## 踩坑点

- **"先查后写"的竞态**：两个并行实例都查到"不存在"，然后都插入。唯一索引永远比 if-not-exists 检查可靠。
- **幂等键不稳定**：把时间戳或随机 UUID 掺进 key，重试时 key 变了，去重形同虚设。
- **key 作用域错配**：粒度太粗，把本该周期性执行的任务误判为重复；太细，又挡不住真正的重推。
- **部分成功后的重放**：三步任务在第二步失败，重试必须能识别并跳过第一步已完成的部分。
- **MCP 工具端不配合**：客户端带了幂等键，服务端根本不看。幂等必须两端约定，只做一半等于没做。

## 可复用建议

- 每个自动化任务上线前，回答一个问题："**这个任务连续跑两次会怎样？**"答不上来就先别开调度。
- 优先用"设为目标状态"代替"增量修改"——能 upsert 就不 insert。
- 在 MCP server 层做幂等：接受客户端传入的 key，对近期处理过的 key 缓存并返回原响应。
- 测试清单加两条：staging 里把同一个任务连跑两遍；人为制造超时后触发重试，核对结果是否与单次执行一致。

## 总结

幂等性不是锦上添花，而是自动化的地基。重试和重复触发一定会发生，区别只在于：是你提前设计了它，还是事后被它设计。
