## 背景

跑 Agent 自动化的人迟早会碰上同一件事：一个任务明明执行过了，日志里却出现两次。原因并不神秘——网络超时触发重试、调度器重复派发、用户手动再点一次、Agent 自己判断"没成功"又来一轮。在 OpenClaw 这类把 LLM、MCP 工具和定时任务串起来的链路里，重试是常态而不是异常。

## 问题

基础设施层面的重试是合理的，但如果工具调用本身不幂等，每次重试都会产生新的副作用。典型症状：同一份内容推了两遍通知、工单系统出现重复记录、数据库里多出一行"看起来一样"的数据。

常见的错误解法是"让 Agent 别重复调用"。这条路走不通：LLM 无法确认上一次调用是否真正落库，也不该承担一致性职责。幂等必须做成工程约束，而不是模型自觉。

## 做法

1. **写操作强制带幂等键。** 在 MCP 工具的 schema 里加一个必填的 `request_id` 参数，由调用方基于业务语义生成（比如 任务ID + 操作类型 的哈希），而不是时间戳或随机数。
2. **工具侧用唯一约束兜底。** 幂等键上建唯一索引，用 upsert 或捕获冲突代替"先查后写"；命中冲突时返回上一次的结果，把"重复"翻译成"成功"。
3. **外部副作用单独去重。** 发通知、建工单这类调用第三方 API 的动作，本地维护一张去重表（幂等键、状态、时间戳、TTL），执行前先查。
4. **长任务状态机化。** 分步落盘进度，重试时从断点续跑，而不是从头再来。

## 踩坑点

- **幂等键用时间戳或随机 UUID。** 每次重试生成的键都不同，等于没做。
- **把"先查后写"当成兜底。** 并发重试时两个请求可能同时通过检查、各写一次。唯一索引 + 冲突捕获才是保障，先查只是性能优化。
- **只覆盖成功路径。** 第一步写库成功、第二步发通知失败，重试时会连第一步一起重跑。需要分步记录状态。
- **重试返回值不一致。** 首次返回"创建成功"，重试却报错，Agent 会判定失败再换条路走。重复调用应返回与首次一致的结果。
- **去重表 TTL 设得太短。** 隔天补跑的任务命中不了记录，照样重复。

## 可复用建议

- 把"所有写操作必须接受 request_id"写进团队的 MCP 工具规范，code review 时当硬性检查项。
- 读操作天然幂等，但警惕"读 → 判断 → 写"的复合操作：检查结果有时效，别拿三分钟前的状态决定现在的写入。
- 定时任务不要依赖内存里的"上次跑到哪"，同步点落盘。
- 最简单的验证方式：把同一条任务消息投递两遍，观察系统行为是否与投递一遍完全一致。可以做成 CI 用例。

## 总结

自动化系统的可靠性，不取决于"任务不重复"，而取决于"重复了也没关系"。LLM 的不确定性决定了重试无法根除，幂等性是把这种不确定性挡在业务外的最后一道闸门。设计工具时默认假设每个调用都会来两次，系统自然就稳了。
