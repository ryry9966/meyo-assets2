## 背景

跑过一段时间自动化的人多半遇到过这种场景：每天早上的定时摘要任务，某天因为网关重启多触发了一次，群里出现两条一模一样的推送；或者一个 webhook 处理器因为响应超时被上游重试，同一个工单被创建了两次。

自动化和手动操作最大的区别在于：**重试不是异常，而是常态**。定时器重复触发、消息通道重投递、Agent 失败后自动重跑、用户手动再点一次——都会发生。幂等性要回答的就是一个问题：同一个任务执行一次和执行多次，最终结果是否一致。

## 问题

非幂等的操作单次执行时一切正常，问题只在重复执行时暴露：

- **推送类**：重复发消息、重复发通知
- **写入类**：重复追加文件、重复插入数据库记录
- **调用类**：重复创建第三方资源（工单、issue、订单）

引入 Agent 后情况更微妙：LLM 输出本身有随机性，如果不做约束，一次重试可能生成完全不同的参数，连"判断是否执行过"都变得困难。

## 做法

核心思路一句话：**用确定性幂等键 + 原子化记账，把"是否执行过"变成一个可查询的事实，而不是靠运气。**

1. **定义幂等键**。从确定性输入推导，比如任务类型 + 时间桶 + 目标对象：`digest:2025-06-07:group-a`。键必须来自触发上下文，不能让 LLM 现场生成。
2. **原子化检查并占位**。执行副作用前先记账，用 Redis `SET key value NX EX ttl` 或捕获 SQLite 唯一索引冲突。检查和写入必须是同一个原子操作，否则并发下两个进程都能通过检查。
3. **副作用尽量收敛为覆盖写**。文件用固定文件名覆盖而不是 append，数据库用 upsert，能编辑已有消息就不要发新消息。这样即使记账层被绕过，重复执行的破坏也有限。
4. **处理失败窗口**。如果"标记完成"之前进程崩了，任务会卡在"已占位未完成"。给占位记录加状态和租约（TTL），超时后允许带条件的重试。

## 踩坑点

- **检查与写入不原子**：先 `GET` 再 `SET` 在并发下必出问题，两个实例同时跑同一个定时任务是常见场景。
- **幂等键粒度错误**：键里带随机时间戳永远去不了重；粒度太粗（比如只有任务类型）又会挡住合法的重新执行。
- **TTL 比重试窗口短**：记账记录十分钟过期，上游重试却持续一小时，后面的重试全部穿透。
- **先标记后执行**：状态写成 done 之后副作用才失败，这次执行就永久丢了。正确顺序是占位 → 执行 → 标记完成。
- **时钟问题**：跨时区、夏令时、机器间时钟漂移都会让时间桶错位，键尽量基于 UTC。

## 可复用建议

- 写一个 `acquire(task_key, ttl)` 小工具，所有有副作用的任务入口统一走它，代码量不大，但能拦住大部分事故。
- 给幂等键留一个 `force:` 前缀命名空间，作为人工兜底出口。
- 验收标准很简单：在测试环境把同一个任务连跑两次，观察副作用是否只发生一次。
- 把 task_key 写进执行日志，排查"到底跑了几次"时非常省时间。

## 总结

幂等性不是额外的工程负担，而是让重试变得安全的前提。自动化系统里重试不可避免，与其祈祷它别发生，不如把每个有副作用的任务都设计成"跑多少遍结果都一样"。这件事做完，你会发现很多之前不敢加的自动重试、断点续跑，自然而然就变得可以做了。
