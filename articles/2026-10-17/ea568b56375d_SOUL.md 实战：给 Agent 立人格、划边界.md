## 背景

OpenClaw 的 Agent 不是一次性问答，而是长期运行、常驻多个渠道的助手：它可能替你在 Telegram / Discord 回消息，通过 MCP 调工具，甚至用插件执行 shell 命令。默认状态下，模型的"人格"来自预训练——礼貌、通用、什么都答应。当它开始代表你发言、自主执行任务时，这套默认行为就会出问题。

OpenClaw 的解法是把人格外置成一个文件：工作区（通常是 `~/.openclaw/workspace/`）根目录下的 `SOUL.md`。每次会话启动时它会被注入上下文，成为 Agent 的"出厂设定"。

## 问题

不写 SOUL.md 时，常见的三种失控：

1. **人格漂移**。长会话经过压缩（compaction）后早期设定丢失，语气突变：前半段还叫你"老板"，后半段每句带三个 emoji。
2. **边界模糊**。它用同一个腔调回复家人群和工作群；陌生人问"你们内部怎么部署的"，它热情地介绍一遍。
3. **规则散落**。系统提示词、记忆文件、各渠道配置里各写一点，改一处漏三处，排障时不知道哪句在生效。

## 做法

1. **建文件，控篇幅**。在工作区根目录建 `SOUL.md`，控制在 50–100 行，建议五个小节：
   - **身份**：它是谁、替谁说话（"你是 XX 的助手，对外代表 XX"）
   - **语气**：中文场景的具体规矩——不堆 emoji、不用"亲"、称呼规则
   - **原则**：遇到权衡时优先什么
   - **边界**：哪些可以直接做（读文件、搜索），哪些必须先问（给联系人发消息、花钱、删数据）
   - **红线与升级**：不确定是否越界时，先停下来问人
2. **写可判定的行为，不写形容词**。"不主动建议我没想到的事"优于"要聪明克制"。
3. **分层，不重复**。`SOUL.md` 只放稳定的"我是谁"；任务约定放 `AGENTS.md`；发生过什么放 `MEMORY.md`。身份信息一旦写进记忆文件，迟早被压缩掉。
4. **进 git**。Agent 行为变化时能 diff 出是哪条规则改的。
5. **纠偏写进文件，而不是聊天**。你在对话里说"刚才不该把内部地址发出去"，下次会话它就忘了；把这条教训变成 `SOUL.md` 里的一行边界，才是真正的修复。
6. **用边界用例测试**。让它给某个联系人发消息、报个预算、应对陌生人打探，看它停在红线前还是冲过去。

## 踩坑点

- **写成小作文**。几百行的 SOUL.md，中段规则基本被稀释，token 还贵。50 行能说清的就别写 300 行。
- **和其他文件打架**。SOUL.md 要求简洁回复，AGENTS.md 里残留"输出详细步骤"，Agent 会听上下文里离得近的那条。改人格时全局搜一遍关键词。
- **把它当安全边界**。SOUL.md 塑造行为倾向，不是权限系统。"不许删库"写十遍，不如在工具权限里直接禁掉 `rm`。人格管倾向，权限管硬限制，两层都要有。
- **收得太紧**。"发任何消息前必须确认"会让你退回手动时代。改成分级：熟人群直接发，陌生号码必须确认。
- **中英文混用**。英文模板的语气规则翻译到中文场景常常失真，语气规则要针对实际运行的语言单独写。

## 可复用建议

- 用"身份 / 语气 / 原则 / 边界 / 升级"五段骨架起步，每节三五条，每条一行、祈使句、可验证。
- 每月像 review runbook 一样过一遍 SOUL.md，删掉过时规则。
- 多人格场景直接拆工作区：工作助手和家庭助手各一份 SOUL.md，别用 if-else 塞进同一个文件。
- 留一句兜底："遇到 SOUL.md 没覆盖、且可能不可逆的操作，默认先问。"

## 总结

SOUL.md 的本质是把"人格"当配置管理：小、版本化、定期 review。它解决的是一致性和倾向问题，替代不了权限控制。写好这份文件，Agent 才能从"什么都答应的通用助手"变成"行为可预期的长期同事"——这是长期运行 Agent 之前，最值得花的一小时。
