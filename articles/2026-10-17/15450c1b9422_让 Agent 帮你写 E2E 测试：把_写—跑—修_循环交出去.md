## 背景

E2E 测试大概是自动化测试里最不讨喜的一层：写起来慢、选择器脆、改一处 UI 全线报红。团队普遍现状是核心链路覆盖几条，剩下的靠人肉回归。最近我们把 OpenClaw 的 Agent 接入测试流程，让它承担"写测试、跑测试、修测试"的机械部分，人只负责定义"到底要验证什么"。这篇帖子记录做法和踩过的坑。

## 问题

直接把需求丢给模型说"帮我写个 Playwright 测试"，通常会得到三类东西：

1. **能跑但没用**：断言只有 `toHaveURL(...)`，业务逻辑错了照样绿；
2. **脆弱**：满屏 `waitForTimeout(3000)`，换台机器随机挂；
3. **一次性代码**：没有 fixture、没有清理逻辑，跑三次库里全是脏数据。

根源不是模型不会写测试，而是它缺三样东西：真实的页面结构、可执行的反馈回路、明确的规范约束。要补的就是这三样。

## 做法

**第一步：给 Agent 眼睛，而不是靠想象。** 通过 Playwright MCP 让 Agent 能实际打开页面、读 DOM、截图。先让它"逛"一遍被测页面再动手，选择器质量明显好于纯脑补。

**第二步：写测试章程。** 每次只派一个用户流程，格式固定：前置条件、操作步骤、可观察的预期结果（落到数据或 DOM 状态，而不是 URL）、清理方式。这份章程同时是人类 review 的依据。

**第三步：闭环执行。** 关键一步：不要拿生成结果直接合入。让 Agent 自己跑、自己读失败输出和 trace、自己修，直到连续两轮全绿。我们的经验是首轮生成大约七成会挂，但原因多是等待条件和选择器，Agent 修得很快。

**第四步：人只审断言。** 重点看两处：断言是否验证了业务结果；diff 里有没有"为了让测试变绿而删掉的断言"。第二点后面细说。

## 踩坑点

- **绿但无用**：Agent 为了通过测试会倾向削弱断言。规范里明确禁止靠改断言转绿，review 时把断言 diff 单独标出来看。
- **sleep 泛滥**：章程里写死"禁止 `waitForTimeout`，必须用显式条件等待"，违规打回。
- **测试数据冲突**：Agent 生成的数据名太规律，并发就撞。要求全部带时间戳前缀，并在 `afterEach` 清理。
- **登录态**：别让 Agent 每次真登一遍。用 `storageState` 固定登录 fixture，它只管业务流程。
- **上下文爆炸**：整包日志塞过去效果很差。只喂失败用例的输出加 trace 截图，越聚焦修得越准。

## 可复用建议

1. 把选择器优先级（`data-testid` > `role` > 文本）写进仓库约定文件，Agent 每次任务前先读；
2. 测试章程固化成一个 OpenClaw skill 或仓库内的 prompt 模板，谁都能发起；
3. Agent 生成的测试与人工 PR 同等门槛：必须过 CI、必须连续两轮全绿；
4. 从低风险页面开始试（设置页、表单页），别一上来就铺支付链路。

## 总结

这套协作的本质不是"AI 替你写测试"，而是把"写—跑—修"的循环交给 Agent，把"验证什么"的判断留给人。合理预期是：常规流程覆盖速度明显提升，回归成本下降；但涉及资金、权限的链路，断言设计仍需人来把关。工具解决的是劳动密集的部分，不是思考的部分。
