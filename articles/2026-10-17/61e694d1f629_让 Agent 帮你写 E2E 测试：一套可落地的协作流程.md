## 背景

E2E 测试是大多数团队"都知道该写、但一直欠债"的部分。单测好写，E2E 难写：要搭环境、造数据、处理异步、维护选择器。我们一个中等规模的 Web 项目，E2E 覆盖长期停留在登录和支付两条主链路。最近我们尝试把 OpenClaw 接入测试工作流，让 Agent 通过 MCP 工具参与 E2E 的编写和维护，跑了一个多月，有些经验值得记录。

## 问题

手工写 E2E 的痛点很具体：

1. **写得慢**——一条登录加表单校验的 spec，熟手也要半天；
2. **死得快**——前端改个 class 名，十几个用例一起红；
3. **断言弱**——很多"看起来在跑"的用例，实际只验证了页面没报错；
4. **补不上**——业务迭代快，测试永远追不上。

Agent 恰好擅长其中三件事：读代码理解页面结构、批量生成样板代码、反复执行并自我修复。所以思路不是"AI 替代测试工程师"，而是把 E2E 里机械的部分交给 Agent，人负责定义契约和做最终验收。

## 做法

技术栈是 Playwright + TypeScript。Agent 侧用 OpenClaw 跑任务，通过 MCP 接入两类工具：Playwright MCP（浏览器操作）和文件系统 MCP（读写仓库）。

**1. 先固化约定，再谈生成。** 写一份 `TEST_CONVENTIONS.md`：目录结构、命名规则、必须用 `data-testid` 定位、断言下限（必须有业务结果断言，不能只看 URL）。这份文件是 Agent 的"宪法"，比任何 prompt 技巧都管用。

**2. 让 Agent 先逛后写。** 任务的第一步不是生成代码，而是让它用 Playwright MCP 打开目标页面，把关键交互路径走一遍，输出页面结构摘要：可定位元素、异步等待点、边界状态。这一步能显著减少后面瞎编选择器。

**3. 小批量生成，失败回喂。** 每次只写一条链路的 spec，生成后立刻 headless 跑一遍，报错原文回喂给 Agent 让它自己修，循环 2~3 轮。人只在收敛后 review。

**4. 选择器契约化。** Agent 生成的定位，统一补 `data-testid` 后进 PR。这个动作把"长期测试维护成本"换成了"一次性开发成本"，非常划算。

**5. CI 里闭环。** 挂掉的用例把 trace 和报错摘要丢回 Agent 做初步分诊：是产品 bug、环境问题还是测试脆弱，打上分类标签，人再处理。

## 踩坑点

- **Agent 很会写"假测试"**：结构漂亮、断言为空或恒真。约定里必须明确断言下限，review 时优先看断言而不是流程。
- **别让它自由发挥等待逻辑**。它偏爱写固定 sleep。超时策略统一收进工具函数，生成时强制引用。
- **一次生成太多必翻车**。失败信息堆积后它会"修一个坏一个"，控制批次大小比调 prompt 有效。
- **测试数据是隐形炸弹**。Agent 会调真实接口造脏数据。后来规定所有用例必须走 seed/factory，不允许现造。
- **成本失控体现在反复重跑上**。给每轮循环设上限，到顶就交给人。

## 可复用建议

- 约定文件 > prompt 技巧：团队规范落成文档，Agent 和新人都能用。
- MCP 工具越少越好：只开浏览器和文件系统，权限最小化。
- 把 Agent 定位成"无限耐心的初级工程师"：产出必须过 review 才能进主干。
- 优先覆盖金额、权限、数据删除这类高风险路径，而不是追求用例数量。

## 总结

一个多月下来，E2E 用例从两条主链路扩到十一条，新增用例约七成由 Agent 产出初稿。更重要的是维护模式变了：选择器契约化之后，前端改动导致的批量红灯基本消失。Agent 没有让测试工作消失，它把最消耗人的部分——搭骨架、修定位、跑循环——自动化了，判断和验收仍然在人手里。这套流程不依赖黑科技，核心就四句话：**先定契约，小批生成，失败回喂，人来收口。**
