## 背景

用 Agent 干活久了，最消耗耐心的一件事是重复交代偏好：代码用 pnpm 不用 npm、回复要给可运行的最小示例、commit 信息遵循某套规范……每条都不大，但每天说三遍，体感就是“这个助手根本不认识我”。

模型本身无状态，会话结束上下文就没了。要让它“认识你”，得在模型外补一层记忆系统。OpenClaw 的插件和 MCP 机制正好给了我们挂载这层能力的位置。这篇帖记录我在自己工作流里落地的方案，偏最小可用，不追求大而全。

## 问题：为什么“记住”比听起来难

多数人第一版会这么做：把用户说过的话全存下来，下次拼进 system prompt。跑一周就会发现三个问题：

1. **上下文爆炸**。两百条记忆全量注入，token 成本上去了，关键偏好反而被稀释。
2. **记忆打架**。“用 pnpm”和三个月前的“用 npm”同时在场，模型行为随机。
3. **垃圾记忆**。“我今天嗓子疼”被当成永久偏好，之后每次对话都被提醒多喝水。

核心矛盾是：记忆系统难的不是存，而是**什么时候写、写什么粒度、怎么更新和遗忘**。

## 做法：一条最小可用的记忆管线

### 1. 先分三类，别混着存

- **核心偏好**：稳定、低频变更，如代码风格、沟通语气、常用工具链。
- **情境事实**：项目相关，如“在维护某个内部服务”“团队用 Kotlin"。
- **过程经验**：踩过的坑，如“这个仓库跑测试前要先起本地 DB"。

分层的意义在于注入策略不同：核心偏好每次硬注入（很小，几十 token），其余两类按任务检索。

### 2. 写入：结构化 + 过一道闸

不要存原文。会话结束时（或检测到偏好信号时）用便宜模型抽取成结构化条目：

```json
{
  "key": "package_manager",
  "value": "pnpm",
  "scope": "global",
  "confidence": 0.95,
  "source": "user_explicit"
}
```

`source` 区分"用户明说”和“模型推断”，推断类 confidence 压低，必要时下次向用户确认。写入前必须回答一个问题：**这条信息在未来会话里还会被用到吗？**答不上来就不写。

### 3. 读取：预取 + 分层注入

任务开始时检索 top-k 相关条目，与核心偏好块一起注入。检索放在任务分发前做，不占用交互等待时间。实测注入上限控制在 300 token 内效果最稳。

### 4. 更新与遗忘

- 新旧条目语义冲突时**显式覆盖**并保留旧值历史，不要两条并存。
- 长期未被检索命中的条目降权，超阈值进入待清理区。
- 给用户一个 `memory_list` / `memory_delete` 入口（做成 MCP tool 即可）。用户能看到、删得掉的记忆，才敢让它继续记。

## 踩坑点

- **把推断当事实写入**。模型会很自信地把猜测存成偏好，用 `source` + `confidence` 兜底，低置信度先挂起。
- **冲突不处理**。覆盖必须发生在写入时，别指望读取时模型自己裁决——上下文里两条矛盾记忆，模型选哪条基本看运气。
- **一次性上下文入长期库**。“这周在赶版本”这类信息要带 TTL，否则会污染几个月后的对话。
- **没有评测**。改一版检索策略不知道好坏，建议攒 20 条左右的回归集：给定会话历史，断言期望行为。

## 可复用建议

1. 先定 schema 再做召回，字段必须有 scope / confidence / updated_at。
2. 写入用便宜模型，读取零额外延迟（预取）。
3. 每条记忆可追溯来源，能解释“我为什么这么认为”。
4. 从低风险高价值的偏好开始记（代码风格、格式约定），别一上来记情绪和人际信息。
5. 把记忆系统做成独立 MCP server，暴露 write / search / list / delete 四个工具，Agent 侧和插件侧都能复用。

## 总结

记忆系统的本质不是“存得多”，而是**写入有闸门、读取有分层、冲突有裁决、用户有控制权**。先用最简单的表加检索把闭环跑通，再逐步加衰减和合并策略。当助手第二次见面就默认用 pnpm 给你写脚本时，这层系统才算真正上线。
