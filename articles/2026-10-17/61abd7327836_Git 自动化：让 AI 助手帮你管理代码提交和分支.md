## 背景

日常开发里，Git 操作占了不小比重：写 commit message、切分支、合并后清理、整理暂存区。这些事不难，但琐碎且容易不规范。OpenClaw 这类 Agent 平台接上 MCP 的 Git 工具后，AI 助手理论上可以接管这些活。真正的问题在于：怎么让它干得好，又不出事。

## 问题

把 shell 权限直接丢给 Agent，等于把整台机器交给一个实习生。实际会遇到三类麻烦：

1. **破坏性操作**：`reset --hard`、`push --force`、`clean` 一旦被 Agent 自主执行，损失的是真数据；
2. **提交质量差**：没有约定时，Agent 倾向生成 "update files" 这类无信息量的 message；
3. **分支堆积**：Agent 每个任务开一个分支，任务结束没人清理，两周后仓库里躺着几十个 `agent/xxx` 残留。

## 做法

我的原则是：**读操作放开，写操作白名单，推送必须人审**。具体分四步：

**第一步：收缩工具面。** 不要直接给 bash，用 MCP 的 Git server，或者自己包一层插件，只暴露这些命令：

```
读：status / diff / log / branch -l
写：add（限显式路径）/ commit / branch / checkout -b
禁：reset --hard / push --force / clean / rebase
```

push 单独封装成"提案"动作：Agent 只生成命令，不执行。

**第二步：把规范写进仓库。** 在项目里放一份约定文件（Conventional Commits 格式、`feat/`、`fix/`、`agent/` 分支前缀），在 Agent 系统提示里指向它。Agent 会自己读，比你写五十行 prompt 有效。

**第三步：先规划后执行。** 定一个两段式流程：任务完成 → Agent 输出 diff 摘要 + 拟提交的 message + 目标分支 → 你确认 → 它才真正执行 `add` 和 `commit`。push 永远留给你。

**第四步：加审计日志。** 插件层把每次 git 调用（参数、时间、会话 ID）追加到日志文件。出了问题能回放，比事后猜"它到底干了什么"省太多时间。

## 踩坑点

- **`git add -A` 是重灾区**。Agent 顺手把无关改动和临时文件全提交了。强制它走显式文件列表。
- **多个会话共享一个工作区会打架**。两个 Agent 同时 checkout 分支，互相覆盖。要么串行化，要么给每个会话用 `git worktree` 隔离。
- **pre-commit hook 会让 Agent 卡死循环**：hook 报错 → Agent 重试 → 再报错。在提示里明确：hook 连续失败两次就停下来报告，不要自行改 lint 配置。
- **分支清理要写进流程末尾**。合并后的 `branch -d` 让 Agent 在任务收尾时执行，别靠人记得。

## 可复用建议

- 新项目先只开读权限跑一周，观察 Agent 的判断质量，再逐步放开写权限；
- commit 风格给 3~5 个真实范例（few-shot），比描述规则管用；
- 把"禁用命令清单"做成插件配置而不是 prompt——代码层面兜底，防止提示词被长上下文稀释。

## 总结

Git 自动化的难点不在让 Agent 会跑 git 命令——那十分钟就能接上，而在划定它"可以自作主张"的边界。把规范沉淀进仓库、把破坏性操作挡在工具层、把推送留给人类，Agent 就是一个守规矩的初级提交者。做到这三点，每天的琐碎 Git 操作基本可以放心交出去。
