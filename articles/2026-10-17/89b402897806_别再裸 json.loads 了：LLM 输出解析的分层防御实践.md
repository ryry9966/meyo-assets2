## 背景

跑 Agent / MCP 工具链的同学几乎都遇到过：让模型"只输出 JSON"，它有时很乖，直接给一个对象；有时外面裹一层 ` ```json ` 围栏；偶尔还先寒暄一句"好的，以下是结果"。只要下游是裸的 `json.loads()`，这条链路迟早炸。

结构化输出 API 和 tool calling 能消掉大部分问题，但现实中总会碰到不支持这些特性的模型、第三方网关或老插件。所以输出解析这一层，值得按防御性编程来写。

## 问题：输出格式是一条连续谱

实际见过的输出大致包括：纯 JSON；` ```json ` 围栏包裹；无语言标注的围栏；JSON 前后有解释文字；内容带尾逗号、单引号、Python 风格的 `True/None`；中文全角引号；甚至多个代码块里只有一个是要解析的。任何单一策略都会在某个分支失效，所以必须分层。

## 做法：一条五级解析流水线

核心思路：从代价最低的策略开始逐级升级，每一级失败都记录原因。

```python
import json, re

def parse_llm_json(text: str):
    text = text.strip().lstrip('\ufeff')
    # L1: 直接解析
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        pass
    # L2: 剥代码围栏，优先取最后一个完整围栏
    fences = re.findall(r"```(?:json|JSON)?\s*\n(.*?)```", text, re.DOTALL)
    for f in reversed(fences):
        try:
            return json.loads(f.strip())
        except json.JSONDecodeError:
            continue
    # L3: 括号配平提取第一个完整对象/数组
    candidate = extract_balanced(text)
    # L4: 低风险修复后重试（尾逗号、全角引号等）
    ...
```

几个实现要点：

1. **剥围栏用非贪婪 + DOTALL，优先取最后一个匹配**——不少模型会先复述 few-shot 示例再给答案。
2. **不要用正则匹配嵌套 JSON**。写一个 20 行的括号配平扫描器，跟踪 `in_string` 和转义状态即可，比任何正则都稳。
3. **L4 修复只做低风险操作**：删尾逗号、处理全角引号。单引号加 `True/None` 的 Python 字典风格可交给 `ast.literal_eval`，千万别用 `eval`。
4. **解析成功不等于结束**。必须再过一层 pydantic / jsonschema 校验，通过才进业务逻辑。

## 踩坑点

- 围栏正则写成贪婪匹配，正文里恰好出现三个反引号时，会把两段内容粘在一起。
- 全局替换 `“ ”` 为 `"` 看省事，但会把 JSON 字符串值里正常的中文引号一起改掉，造成语义污染。修复只应在字符串外做，或者接受风险并记日志。
- 清尾逗号的正则 `,\s*[}\]]` 会误伤字符串值里的 `",]"`。先配平提取、缩小修复范围，误伤面会小很多。
- 流式输出拿到的是半截 JSON，别急着解析，等围栏闭合或缓冲到括号配平再处理。
- 失败时只打一行 "parse error" 等于没打。把 raw 输出（注意脱敏）和每级失败原因都留下，否则没法区分是 prompt 问题还是解析器问题。

## 可复用建议

1. 把这套逻辑封装成单一模块，统一入口返回 `(ok, data, raw, error)` 四元组，全项目只用这一个解析点。
2. 加个轻量遥测：统计 L1–L4 各命中多少次。L2 占比持续偏高，说明该改 prompt 或上 tool calling，而不是继续堆补丁。
3. 兜底策略是**带错误信息重试一次**：把 `JSONDecodeError` 的行列号喂回模型，命中率远高于干巴巴的"再来一次"。
4. 维护一份真实失败样本的测试语料，每次改动解析器都全量跑一遍。

## 总结

LLM 的文本输出本质上是一种不可信的外部输入。防御性解析不是把某条正则写得更聪明，而是承认"任何单一策略都会失败"，然后用分级流水线把失败变成可观测、可重试、可修复的常规路径。结构化输出能用就用，但这个解析器，永远是最后一道闸。
