## 背景

在 OpenClaw 插件和 MCP 工具链开发里，让模型输出 JSON 是家常便饭：工具参数、中间推理结果、配置片段。理想情况是模型返回一段干净 JSON，`json.loads` 一次通过。但跑过真实流量就知道，模型实际输出形态远比 prompt 里约定的丰富。防御性解析不是可选项，是工程必需。

## 问题：同一份 prompt，五种输出

从真实日志里捞到的失败样本大致分几类：

1. Markdown 围栏包裹：```` ```json { ... } ``` ````
2. 自创标签包裹：`<json>{...}</json>`、`<output>...</output>`
3. 带前后说明文字："解析结果如下：{...}"
4. 语法瑕疵：尾逗号、单引号、全角引号
5. 截断：max tokens 打断，只写半截

我们最初的解析就是一个 `json.loads` 加一条正则兜底。上线两周后统计，约 7% 的调用走了兜底路径，其中一半兜底也失败。这就是重写的起点。

## 做法：分层解析管道

核心思路：从"猜一种格式"改成"按代价从低到高逐层尝试"，每层命中都打日志。

```python
def parse_llm_json(text: str):
    # L0 直接解析（理想路径）
    # L1 剥最外层代码围栏后重试
    # L2 括号配对扫描，取第一个平衡的 {...} / [...]
    # L3 标签提取 <json>...</json>
    # L4 json_repair 容错修复
    # L5 抛类型化异常，交上层决定是否重试
```

几个实现要点：

- **L2 不要用贪婪正则**。`\{.*\}` 遇到多个 JSON 对象拼接或字符串内含花括号必挂。写个小状态机：逐字符扫描，跟踪是否在字符串内、是否转义，括号深度归零时截取。
- **L1 只剥最外层围栏**。模型经常在内容里嵌套代码块（比如生成一段脚本），全局剥围栏会把合法内容剥坏。
- **L4 修复后必须过 schema 校验**。json_repair 能把 `{a: 1,}` 修好，也可能把类型"修"成另一回事——修复成功不等于语义正确，pydantic 校验是最后一道闸。
- **重试有上限且带反馈**。失败重试时把具体的 JSONDecodeError 信息和期望 schema 塞回 prompt，一次为限，不要无限循环烧 token。

## 踩坑点

- **贪婪正则吞对象**：我们最初的 `\{.*\}` 在两个 JSON 对象拼接的样本上把两个吞成一个，pydantic 报错完全对不上，排了一下午才发现是解析层的问题。解析层必须能报告"命中了哪一层、原文长什么样"。
- **全角引号**：中文语境下模型会把 `"` 输出成 `“ ”`，直接 parse 必挂。修复时只处理结构位置的引号，字符串内部的不能动。
- **流式截断**：流式场景下半截 JSON 是常态，解析层要能区分"格式错"和"没写完"——后者走续写或放弃，不要试图修复。
- **temperature 影响**：temperature=0 时稳定的格式，调高后失败率明显上升。防御代码按最坏情况设计，把兜底命中率做成指标。
- **MCP 场景别重复解析**：MCP 工具的 arguments 到达时通常已解析过，防御解析针对的是模型生成的自由文本中间产物，不要对已结构化的数据再套一层。

## 可复用建议

1. **解析收敛到一个模块**，全项目只 import 这一处，返回值带上命中层级，方便观测。
2. **维护失败样本语料库**：从线上日志捞真实坏样本做成单测 fixture，每次线上新坑都往里加。这是防御代码最有价值的资产。
3. **防御解析是兜底不是首选**：能用 function calling / response_format / JSON Schema 约束解码就优先用约束；prompt 侧同时要求"只输出 JSON、不要解释"，双保险。
4. **观测兜底命中率**：某层命中率突升，往往意味着模型版本变更或 prompt 回归，是很好的报警信号。

## 总结

LLM 输出解析的防御性编程，本质是一套按代价排序的降级管道加完整可观测性：快速路径优先，逐层兜底，每层留痕，修复后必校验，重试有上限。它不能替代结构化输出约束，但只要 Agent 还在自由文本和结构化数据之间做转换，这套管道就是稳定性的下限。先把日志和语料库建起来，防御代码才有迭代依据。
