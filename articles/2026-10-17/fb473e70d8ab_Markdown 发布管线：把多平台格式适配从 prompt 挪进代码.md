## 背景

用 Agent 产出内容后，真正的耗时往往不在写作，而在“发得出去”：同一篇 Markdown 要进公众号、知乎、掘金和自建站点，各平台对 HTML 标签、代码块、图片、公式的支持差异很大。我们最初的方案是让模型“直接生成适配某平台的版本”，跑了一段时间发现不可控——每次微调提示词，另一个平台的格式就悄悄坏掉。

## 问题

实际踩到的差异主要有四类：

1. **标签白名单**：公众号只接受一小部分标签和内联样式，脚注、任务列表直接被吞；
2. **扩展语法**：GFM 表格、数学公式、脚注在不同平台支持度完全不同；
3. **图片链路**：外链图床防盗链、微信域图片外站不可用、宽度限制；
4. **代码渲染**：各平台高亮主题、换行策略不一致，长行溢出。

## 做法

把适配从 prompt 里拿出来，做成确定性管线，核心三个阶段：

**1. 收紧生成端。** Agent 只输出一个受限 Markdown 子集，写成 lint 规则：禁 raw HTML、禁脚注语法、禁任务列表；图片必须带 alt 和稳定路径；front-matter 固定为 title / tags / digest / cover 四个字段。生成时违反直接报错重试，比发布端兜底便宜得多。

**2. 归一化到 mdast。** 用 remark-parse 解析成 AST，front-matter 先剥离。这一步做两件事：图片统一下载后上传图床并替换 URL（按 hash 去重、失败可重试）；代码块补齐语言标注。所有变换在 AST 上做，不用正则改 HTML——正则在嵌套结构上必翻车。

**3. 平台适配器。** 每个目标一个 adapter：

- 公众号：mdast → rehype → 白名单 sanitize → 内联样式注入，表格超 4 列转图片；
- 知乎 / 掘金：基本直出 GFM，只处理图片域名和公式转图；
- 自建站点 / RSS：完整 HTML，公式走 KaTeX。

最后加一层 dry-run：各平台渲染结果做快照，上游 prompt 或依赖更新后跑 diff，样式炸没炸一眼可见。

## 踩坑点

- **正则替换 HTML**：最早的版本用字符串替换注入样式，标签嵌套稍复杂就错位，全部改成 AST transform 后才稳定。
- **公式转图的 DPI**：默认分辨率在公众号里发糊，按 2x 输出才够；深色模式下白底公式图也很刺眼。
- **剪贴板发布**：程序生成的富文本粘进编辑器会丢样式，这条链路最好走官方接口，别自己模拟粘贴。
- **图片双重要求**：微信图床的图外站挂，外站图在公众号里偶发不显示，管线里按目标平台各存一份。
- **front-matter 漏出**：某次适配器忘了剥离，分隔线连着 `key: value` 直接发出去，靠快照 diff 才抓到。

## 可复用建议

- 受限子集即契约：schema 写清楚，lint 前置到生成端，越早报错成本越低。
- 图片上传独立成幂等步骤，带 hash 去重，可单独重试。
- 原始 md 是唯一事实源，每次发布记录 target + 内容 hash，方便回溯哪次改动影响哪个平台。
- 适配器输出一律快照化，进 CI 跑 diff，别靠肉眼验收。

## 总结

多平台发布的格式问题，本质是把不确定性从模型侧挪到代码侧：AI 只负责产出符合契约的受限 Markdown，归一化和适配交给确定性管线。这套结构不绑定具体工具，remark/rehype 或 pandoc 都能搭，关键是“先收紧输入，再按目标发散”。
