## 背景

用 OpenClaw 做日常自动化久了，迟早会撞到单 Agent 的天花板：让主 Agent 一次性调研五个候选 MCP 插件，或者把一份长文档拆成十段逐段处理，结果是上下文越滚越大、工具调用全程串行，中途一旦某个调用失败，整条链路作废重来。

subagent 的价值就在这里：主 Agent 可以派生出若干拥有独立上下文窗口的子 Agent，干完活只把结论交回来。本质上，它解决的不是"算力不够"，而是**上下文隔离**和**并行调度**两个问题。

## 问题拆开看

- **上下文污染**：调研类任务的中间过程（网页原文、长日志）没必要留在主上下文里。
- **串行等待**：多个互相独立的任务排队执行，总时长是累加的。
- **单点脆弱**：一长串串行调用中任何一环失败，前面的成果难以复用。

## 做法

我目前稳定使用的是"只读并行 + 主 Agent 统一收口"模式，五步：

1. **拆任务**。先判断任务是否真的可并行：互相独立、不写同一批文件。典型场景是多路调研、批量代码阅读、多方案对比评估。
2. **写任务卡**。每个子 Agent 拿到的是结构化指令，而不是一句口语化描述，核心字段：

```json
{
  "scope": "只调研插件 A 的能力边界，不评估其他候选",
  "output": "JSON，含 summary / risks / sources 三个字段，不超过 400 字",
  "constraints": ["禁止写文件", "禁止再派生子 Agent", "失败返回 error 字段"]
}
```

3. **并行派发**。主 Agent 一次性发起，宽度控制在 3–5 个。这个数字是权衡出来的：太少没有并行收益，太多会撞 API 限流，回收时主上下文也处理不过来。
4. **结构化回收**。强制子 Agent 按约定格式返回摘要，主 Agent 负责合并、去重、交叉验证。原始过程数据留在子 Agent 会话里，需要时再取。
5. **兜底**。给每个子 Agent 设超时；失败的子任务单独重跑，不影响已成功的结果。

## 踩坑点

- **并发写冲突**。早期我让子 Agent 直接改文件，两个子 Agent 改同一模块，互相覆盖。现在子 Agent 一律只读，所有写入动作收归主 Agent 串行执行。
- **回收内容太肥**。不约束输出格式时，子 Agent 会把整段调研原文塞回来，主上下文瞬间膨胀。必须硬性限制返回长度和字段。
- **递归套娃**。子 Agent 再派子 Agent，深度不可控，token 消耗指数增长。我的规则是深度固定为 1。
- **边界重叠或遗漏**。任务卡里要明确"你只负责 X"，并在派发前列出完整任务清单，保证每项恰好有一个负责人。

## 可复用建议

- **任务卡模板化**：scope / output / constraints 三段式存成固定模板，每次只改内容。
- **子 Agent 定位成"研究员"而不是"执行者"**：读、比、验证都可以并行，写操作保持单点。
- **每个子 Agent 留独立 trace**：出问题时能回放完整过程，而不是只看到一句失败的结论。
- **先从最小场景切入**：比如"并行调研三个 MCP 插件再汇总对比"，跑通闭环后再扩到写场景。

## 总结

subagent 编排的核心不是"Agent 越多越好"，而是把上下文隔离和任务边界设计清楚。宽度克制、输出收敛、写入单点——做到这三条，多 Agent 并行才是一条能长期跑的工程路径，而不是 demo 玩具。
