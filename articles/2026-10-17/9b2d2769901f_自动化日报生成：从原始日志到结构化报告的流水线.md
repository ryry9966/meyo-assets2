## 背景

我们团队每天要在群里发一份"昨日动态"：服务报错数、Agent 任务成功率、MCP 插件调用异常、待办事项。之前靠人工翻日志、复制粘贴、手写摘要，每天 30 分钟起步，而且每个人总结的口径都不一样，周报对不上月报是常态。这篇帖子记录我们把它改成自动化流水线的过程，思路可以复用到任何"原始日志 → 结构化报告"的场景。

## 问题

最容易想到的方案是：把当天全部日志丢给 Agent，让它"总结一下"。实际跑下来有三个硬伤：

1. 日志量动辄几十万行，直接塞上下文要么超限要么成本爆炸；
2. LLM 每次归纳的重点和格式都不同，报告无法横向对比；
3. 日志里有大量重复堆栈和调试噪音，模型容易被带偏，甚至编出不存在的"趋势"。

结论：LLM 只适合做最后一层的归纳与措辞，前面的清洗、聚合、结构化必须由确定性代码完成。

## 做法

流水线分五步，由一个定时任务驱动（cron 触发 OpenClaw 的任务入口）：

1. **采集与切片**：按本地时区的自然日切分日志，来源包括服务日志、Agent 运行记录、MCP 调用审计，每条归一化成 `{time, source, level, event, attrs}`。
2. **降噪与聚合**：确定性脚本先跑——剔除 DEBUG、按指纹合并重复堆栈、按 `source × event` 计数。这一步把几十万行压成几百行摘要数据。
3. **LLM 归纳**：把聚合后的 JSON 喂给 Agent，用 JSON Schema 约束输出，温度设 0：

```json
{
  "summary": "string, ≤120字",
  "incidents": [{ "event": "string", "count": 0, "severity": "high|mid|low" }],
  "metrics": [{ "name": "string", "value": 0, "delta": 0 }],
  "todos": ["string"]
}
```

4. **校验与兜底**：对返回做 schema 校验，失败重试一次，仍失败则降级为纯模板报告（只有数字没有分析），保证日报永远能发出去。
5. **渲染与投递**：模板引擎渲染成 Markdown，推送群 webhook，同时归档到内部 wiki 供回溯。

核心原则是分层：数据层（确定性代码）→ 语义层（LLM）→ 展示层（模板），每层可单独测试、单独替换。

## 踩坑点

- **时区**：日志时间戳是 UTC，日报按本地自然日切，一开始没转换，每天 8 点前的日志全被算进前一天。切分逻辑必须显式声明时区。
- **JSON 输出不稳**：早期没用 schema 约束，模型偶尔在 JSON 外包一层"好的，以下是……"。加校验加重试后才稳定。
- **噪音被当成事件**：某插件每分钟刷一条心跳日志，被 LLM 总结成"高频调用异常"。教训是心跳/探活类日志要在降噪阶段打标剔除。
- **流水线本身静默失败**：有天 cron 没跑成，没人发现，日报直接缺了一天。现在流水线自身的执行结果也写审计日志，连续失败两次触发告警。

## 可复用建议

- 先定义报告的 JSON Schema，再写 Prompt——Prompt 是 Schema 的说明文档，不要反过来；
- 计数、去重、聚合放代码里，别指望 LLM 做算术，它不可靠；
- 原始聚合数据要归档，报告只是视图，随时可以换模板重渲染；
- 把"日报是否按时产出"当成一个被监控的服务，而不是一次性脚本。

## 总结

上线后，日报的人工成本从每天 30 分钟降到 0，口径统一，历史数据可对比可回溯。核心经验就一句：**确定性代码处理数据，LLM 处理语义，模板处理展示**。Agent 生态里很多自动化需求都能套这个分层结构，欢迎在自己场景里试试，踩到新坑回来补充。
