## 背景

我们的 OpenClaw 实例上跑着十几个常驻 agent 和插件，每天产生大量执行日志：任务启停、工具调用、失败重试、定时触发。之前日报靠人翻日志写，一次十几二十分钟，而且每个人关注的口径不一样，昨天看耗时、今天看错误数，日报本身没什么可比性。

## 问题

拆开看是三件事：

1. 日志散落在文件、SQLite、插件回调里，格式各异；
2. 噪音多，重试和 debug 级别记录占了八九成；
3. 最关键的：不能把原始日志直接丢给模型总结。实测 token 消耗爆炸，而且模型会把日志里的中间状态当成结论写进报告。

## 做法

后来做成一条 cron 触发的流水线，五个阶段：

**1. 采集与归一化。** 脚本从各来源拉取日志，统一成 JSONL，schema 固定为 `{ts, source, event_type, level, payload}`。新来源接入只写适配器，不动下游。

**2. 清洗与聚合。** 按 `event_type + payload 哈希` 去重；同一任务的多次重试合并为一个事件并记重试次数；丢弃 debug 级别。产出按小时分桶的聚合表。

**3. 指标计算。** 纯代码，不过模型：任务成功率、平均耗时、Top-N 慢任务、按错误码聚类的失败分布，输出中间 JSON。

**4. LLM 叙述层。** 只把聚合 JSON 和 Top-N 原始异常片段喂给模型，让它写「今日概述」和「异常解读」两段。prompt 里明确约束：只允许引用输入中出现的数字，缺数据就写"无数据"，不许推断。

**5. 渲染与投递。** Markdown 模板固定栏目（概览 / 指标表 / 异常 / 变更 / 待办），代码填数字，模型填叙述，落盘 `archive/YYYY-MM-DD.md` 后 webhook 推送。发送带幂等键。

## 踩坑记录

- **时区**：日志是 UTC，日报按本地日切，头两天数据对不上。归一化阶段统一转时区，日切时间做成显式配置。
- **跑批时机**：原定 00:00 跑，尾巴上的日志还没写完就漏了。改成 00:05，采集阶段读快照而非实时流。
- **模型输出漂移**：让它直接输出 Markdown，格式隔几天就变形。改成要求 JSON，由代码渲染，解析失败降级为纯指标表——日报永远能发出去。
- **聚合掩盖异常**：平均耗时很健康，但有个任务卡了 40 分钟被摊平了。聚合前必须先把 Top-N 异常摘出来单独保留。
- **重试重复推送**：流水线重跑导致群里连发两份。加幂等键，发送前检查 archive 目录。

## 可复用建议

- 先定 schema，再谈自动化，否则每个来源都要改一遍下游；
- 数字由代码算，模型只写叙述——确定性部分不要交给概率性组件；
- 每个阶段独立可重跑，中间产物落盘，出问题可以按阶段回放；
- prompt 和模板进仓库，跟代码一起 review 和版本化；
- 给流水线自己也留运行日志，日报出错时你能查到是哪一环。

## 总结

这条流水线跑下来，日报从"人肉活"变成无人值守，更重要的是口径稳定、可对比。回头看，价值不在"让模型写报告"，而在前四步把日志变成了结构。模型只是最后一公里，不是整条路。
