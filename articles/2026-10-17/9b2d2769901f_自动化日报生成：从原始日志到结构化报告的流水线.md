## 背景

我们组每天要出一份日报：昨日任务执行情况、错误统计、需要关注的风险。之前靠人工翻日志，费时且口径不稳。OpenClaw 侧有定时触发、agent 编排和 MCP 工具能力，正好把这件事做成流水线。跑了两三周，稳态运行，把做法整理出来。

## 问题

从原始日志到"能看的日报"，中间隔着三件事：

1. **噪声与格式不齐**：多个服务的日志混着 JSON 行和纯文本，时区有 UTC 也有本地时间，DEBUG 噪声淹没有效信息。
2. **LLM 不可信于数字**：直接把日志丢给模型总结，错误次数、耗时这类数字经常编错，长日志还会撑爆上下文。
3. **输出漂移**：日报要推到 IM webhook 和表格，模型输出格式不稳定，下游解析容易挂。

## 做法

流水线分五步，每步产出中间文件落盘：

1. **采集与归一化**（纯脚本）：固定时间拉取当日日志，时间戳统一到本地时区，过滤 DEBUG，按服务分桶，输出 JSONL。
2. **统计先行**（纯代码）：错误数、成功率、P95 耗时、Top 错误类型全部由脚本算好，写入 stats.json。**数字永远不经过 LLM**。
3. **Agent 叙述化**：把 stats.json 和 3~5 条有代表性的错误样本（堆栈只取首尾）交给 agent，prompt 里明确"只允许引用给定数字"，要求输出固定 schema 的 JSON（title / summary / highlights / risks）。
4. **校验与降级**：用 JSON Schema 校验输出，不通过重试一次；再失败就走模板降级——直接拼 stats 渲染纯数字版日报，保证当天一定有产出。
5. **投递与存档**：webhook 推群，Markdown 与当日 JSONL 存进按日期命名的目录，方便回溯。

## 踩坑点

- **时区错位**：第一版"昨日"窗口按 UTC 切，实际早上八点前的数据被划进了前一天。归一化必须发生在入口，而不是分析时。
- **静默失败**：定时任务偶尔不跑，"没收到日报"比"日报有错"更容易被忽略。加了一个哨兵：到点未检测到产出文件就告警。
- **JSON 包壳**：模型偶尔在 JSON 外面再包一层代码块围栏，解析前先剥壳，别指望 prompt 一次根治。
- **样本截断**：完整堆栈喂进去既费 token 又稀释重点，首行加末尾 N 行足够定位。

## 可复用建议

- 中间产物按步骤落盘，任何一步可独立重跑，调试不必从头来。
- 把 LLM 定位成"叙述者 + 格式化器"，计算、过滤、聚合交给代码——这是整条流水线可靠性的根基。
- 结构化输出必过 schema 校验，且一定配降级路径。
- 日报骨架用固定模板，LLM 只填 summary 和 risks 这类真正需要语义理解的部分，版式就不会漂。

## 总结

这条流水线的核心思路是**把不确定性收敛到最小环节**：代码负责事实，模型负责表达。OpenClaw 的 agent 与工具编排能力适合承担中间的叙述与调度，但数据正确性要靠工程手段兜底，不能指望 prompt。落地成本不高，一个下午能搭出可用的第一版，之后按踩坑点逐步加固即可。
