## 背景

我们维护着一套多节点服务和若干长期运行的 agent 任务。每天早上要在群里发一封日报：昨天跑了多少任务、失败多少、失败集中在哪、有没有需要人工介入的事。这活过去是人工做的——打开几台机器的日志肉眼扫一遍，凭记忆拼一封消息。耗时不谈，两个人写出来的日报口径完全不一样，周一对不上周五。

## 问题

拆开看，痛点有三个：

1. **日志分散**：服务日志、agent 执行记录、定时任务输出分布在多台机器和对象存储里，格式还不统一。
2. **口径漂移**：人工日报里"失败"的定义每天都在变，有时算超时有时不算，周报没法做同比。
3. **收尾机械**：数字统计完，还要人肉套模板、发群、归档，纯体力活。

## 做法

最终落地的流水线分四段，每段一个独立脚本，中间产物落盘：

1. **采集层**：cron 每天 06:10 触发，按日期拉取前一天的分片日志，同步到统一目录。关键约束是幂等——文件按日期命名，重跑直接覆盖，不追加。
2. **结构化层**：确定性脚本做解析——正则提取字段、按错误码聚合、算失败 TopN，产出一份中间 JSON。这一层不用 LLM，能用规则解决的不交给模型。
3. **摘要层**：LLM 只读中间 JSON，负责把数字组织成人话，加一两句趋势判断。数字永远来自统计结果，模型不碰原始日志。
4. **分发层**：Markdown 模板渲染，固定四个章节——总量、失败 TopN、环比、待跟进事项；推送到 webhook，同时归档一份到对象存储当台账。

和 OpenClaw 的结合点：解析和摘要封装成一个 skill，agent 定时触发整条链路；中间 JSON 通过 MCP 暴露成查询工具，白天有人问"昨天失败为什么涨了"，agent 直接查数回答，不用重跑。

## 踩坑点

- **时区**：服务器是 UTC，日报按本地时区切天，最初跨天切片错位，凌晨的任务被算进前一天。解决：统一按 UTC 存储，切片时换算边界。
- **重跑不幂等**：推送失败后手动重跑，群里收到两封日报。改成"日期+版本号"命名，发送前查重。
- **摘要幻觉**：早期让模型直接读原始日志，它会编出统计里不存在的数字。退回"模型只读 JSON"后问题消失。
- **日志轮转**：按文件修改时间采集会漏掉轮转边界上的行，改成按行内时间戳过滤。
- **敏感信息**：有次把带内网地址的堆栈直接发进了群。分发前加一道脱敏正则，匹配 IP、token 类字段。

## 可复用建议

- **中间 JSON 是核心资产**，日报只是它的一个视图。后来加周报、加告警，都只是换模板。
- **每段落盘 + 写状态文件**，任何一段挂了能断点续跑，不必从头再来。
- **模板和口径一次定死**，别频繁改章节。日报的价值在可比性，不在华丽。
- **先影子模式跑两周**：正常生成但不发送，人工核对数字与真实日志是否一致，再切正式。

## 总结

这套东西没有高深技术，就是"规则统计 + 模型措辞 + 固定模板"的组合，一个晚上写完，跑了两个月没再人工碰过。最大的心得是：日报这种天天要的东西，必须让口径固化在代码里，而不是固化在某个人的习惯里。
