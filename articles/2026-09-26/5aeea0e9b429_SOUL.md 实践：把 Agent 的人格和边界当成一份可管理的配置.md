## 背景

OpenClaw 的 workspace 里有一组以 Markdown 组织的常驻上下文文件：`AGENTS.md` 管任务流程，`USER.md` 管用户偏好，`MEMORY.md` 管记忆。而 `SOUL.md` 回答的是一个更基础的问题——这个 agent 是谁、说话什么风格、哪些事不做。

很多人把人格和边界硬编码在启动脚本或 system prompt 里，改一次要同步多处。SOUL.md 的价值在于把这部分变成纯文本资产：可版本管理、可 review、可回滚。

## 问题

没有稳定人格定义的长期运行 agent，常见三种漂移：

1. **语气漂移**：周一像客服，周三像黑客，Telegram、CLI、微信多个渠道表现不一致。
2. **边界漂移**：今天敢帮你 `rm -rf`，明天又突然谨慎；或者反过来，对危险操作永远过度热情。
3. **过度承诺**："马上帮你处理”说出口，但工具链路上根本没有对应能力。

本质原因：人格与边界如果只存在于开发者脑子里，模型每次会话都在重新猜。

## 做法

我的 SOUL.md 目前是五段式骨架：

```markdown
## Identity
一句话身份 + 与用户的关系定位

## Voice
可判定的语气规则："回复默认不超过三段"
"先给结论再给理由""不用感叹号"

## Values
排序过的原则："准确性 > 速度""不确定就说不确定"

## Boundaries
每条写成 触发 → 动作：
- 删文件 / 转账 / 给第三方发消息 → 先复述操作，等确认
- 不了解的领域 → 明说不知道，不编

## Escalation
什么情况停止执行、转人工
```

几条实践要点：

- **总量控制在 500–1200 字**。超过 2000 字，权重会被明显稀释。
- **用 git 管理**。改人格像改代码一样提 commit，写清楚为什么改。
- **职责分离**。AGENTS.md 只管流程，不重复 SOUL.md 的内容；USER.md 放偏好；保持单一事实来源。
- **翻车就回写**。每次行为跑偏，回写一条规则进去，像写 post-mortem——这是它持续变准的唯一途径。

## 踩坑点

- **形容词陷阱**。"保持专业”“友好一点”这类描述模型会自行脑补，必须翻译成可判定的行为标准。
- **职责混淆**。用户习惯（"我喜欢表格”）该进 USER.md，事实记忆该进 MEMORY.md，全塞进 SOUL.md 只会互相污染。
- **红线稀释**。一长串“永远不要”会让最关键的两三条失去权重。红线放文件最前面，且不超过 5 条。
- **边界不等于权限**。SOUL.md 是行为层的软约束，真正的兜底在工具层——MCP server 和插件的权限配置。不要指望一段 Markdown 挡住一个有写权限的工具调用。
- **改了不生效**。长会话仍持有旧上下文，改完 SOUL.md 记得新开会话验证，别误判成“没起作用”。
- **多 agent 串味**。几个角色不同的 agent 不要共用一份 SOUL.md，哪怕 80% 相同也要拆文件。

## 可复用建议

- 骨架直接抄：**Identity / Voice / Values / Boundaries / Escalation** 五段。
- 每条边界都配“触发 → 动作”，没有动作的边界是装饰。
- 用真实聊天日志校准人格，而不是凭想象写。
- 把 SOUL.md 当 IaC 对待：有变更记录、有 review、有回滚。

## 总结

SOUL.md 不是给 agent“注入灵魂”的玄学，而是把人格和边界从隐式经验变成显式资产的一次工程化。它解决的不是模型能力问题，而是**行为一致性问题**——这恰恰是长期运行的私人 agent 最先崩坏的地方。写得短、写得具体、用 git 管、翻车就回写，这四件事做到，人格就稳了。
