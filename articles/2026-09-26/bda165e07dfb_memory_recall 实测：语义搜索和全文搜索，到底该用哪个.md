## 背景

OpenClaw 的 memory_recall 是 Agent 记忆系统的入口：对话中 Agent 决定"回忆一下"，就调这个工具去检索历史记忆。检索质量直接决定 Agent 是"记得你说过的话"还是"一本正经地编"。

默认配置走的是语义搜索（embedding + 向量相似度），我也一直这么用。直到上周它反复想不起我三个月前记录的一个报错码，我才认真对比了一次。

## 问题

语义搜索的短板在**精确标识符**上暴露得很明显：

- 查 `ECONNREFUSED 5432`，它返回了一堆"数据库连接问题"的泛化记忆，唯独漏掉那条原样记着报错码的；
- 查具体路径 `/etc/openclaw/gateway.toml`，同样是语义匹配赢不了字面命中。

反过来，纯全文搜索（BM25 / LIKE）也有坑：换个说法就查不到。你记的是"部署脚本偶发超时"，半年后问"CI 偶尔卡住"，全文搜索直接空手而归。

一句话：**语义搜索赢在意图，全文搜索赢在事实**。我的记忆库里两类内容都有，单选哪个都不对。

## 做法

我没急着换方案，先做了个小基准，三步：

1. **抽样构建查询集**：从记忆库里挑 30 条真实记忆，每条手写 2 个查询——一个同义改写，一个含精确标识符（报错码、路径、版本号）。共 60 个查询。
2. **分别跑两种检索**：同一批查询分别过语义管道和全文管道，人工标注 Top-5 是否命中原记忆。结果：同义改写类，语义命中 24/30，全文 9/30；精确标识符类，全文 27/30，语义 11/30。差距非常不对称。
3. **上混合检索**：两种召回各取 Top-10，合并去重后按简单加权排序（语义分 0.6 + BM25 归一化分 0.4），再裁到 Top-5 喂给 Agent。

改成混合后，两类查询的 Top-5 命中都稳定在 26/30 以上，代价是每次 recall 多一次检索开销，本地跑基本无感。

具体配置上，如果用的是内置记忆插件，开混合检索选项即可；如果自己拼的 MCP 工具，就是在 recall 工具里并行走两个查询，合并逻辑放在工具层，Agent 侧无感知。

## 踩坑点

- **中文分词别裸用默认配置**。全文索引若按空格切词，中文基本退化成整句匹配。上 jieba 或选择支持中文的 BM25 实现，召回率差好几倍。
- **Embedding 模型的中文能力要实测**。部分小模型中文向量区分度很差，语义搜索看着有结果，实际排序接近随机。用你自己的查询集测，别信榜单。
- **chunk 切分粒度**。按固定长度切会把"报错码"和"上下文解释"切到两个 chunk，语义检索命中了上下文却没有报错码。按条记忆整体入库（我的记忆本来就是短条目）效果好得多。
- **权重别拍脑袋定死**。0.6/0.4 是我这批数据的经验值，你的记忆类型分布不同就该不同，基准集才是依据。
- **改了索引策略记得重建索引**。我换分词器后忘了 rebuild，查了半天为什么新配置"没生效"。

## 可复用建议

- 先建 30~60 条的评测查询集，任何检索改动跑一遍再上线，半小时成本，避免凭感觉调参；
- 记忆条目里带上元数据（时间、来源、项目标签），必要时在检索前加过滤，比纯靠相似度靠谱；
- 定期翻 recall 的失败日志——Agent 实际调了 recall 但没用到结果的那部分，是最好的补测试集来源。

## 总结

语义 vs 全文不是二选一，而是召回互补。我的结论很朴素：**混合检索 + 自建评测集**。前者解决"查得到"，后者保证"改得对"。memory_recall 是 Agent 记忆系统的地基，值得花一个下午把它做扎实——Agent 所有"越用越懂你"的体验，都是从这里长出来的。
