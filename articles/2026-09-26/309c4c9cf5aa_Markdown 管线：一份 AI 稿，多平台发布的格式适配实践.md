## 背景

现在让 Agent 写初稿已经不是瓶颈，瓶颈在发布。同一篇 Markdown，要投到公众号、知乎、掘金和自己的静态博客，各平台对 Markdown/HTML 的支持差异很大。我们的做法是把"格式适配"从写作流程里剥离出来，做成一条独立的 Markdown 管线，接入 OpenClaw 的工具体系后，Agent 只负责生成和修改原文，发布动作全部由管线完成。

## 问题

实际对接时遇到的差异集中在四类：

1. **语法子集不同**：公众号不支持原生 Markdown，要转成带内联样式的 HTML，且大部分 class 会被过滤；知乎、掘金支持 GFM，但对脚注、数学公式的处理不一致。
2. **图片协议不同**：自建图床的 URL 在公众号必须走素材上传接口换回平台 CDN 链接，知乎粘贴时还会二次转存。
3. **元数据需求不同**：静态博客要 front matter，其他平台大多只要正文。
4. **AI 生成稿本身不规范**：多个 h1、代码块语言标签随意、正文里混入裸 HTML 标签。

## 做法

管线分四步，每一步都是纯函数式转换，输入输出都是文件，方便做快照测试：

**1. 规范化（normalize）**。以 CommonMark + GFM 子集为"正典"格式，用 markdownlint 加自定义规则收敛：全文只允许一个 h1；正文禁止裸 HTML；代码块语言标签对照映射表统一（如 `shell`/`bash` 归一）；front matter 的 title 强制加引号（标题带冒号会炸解析）。中文场景记得把 proseWrap 关掉，否则格式化工具会把中文段落折行。

**2. 平台适配（transform）**。每个目标平台一个 adapter，由一张能力矩阵驱动：该平台支不支持脚注、公式、alerts、表格对齐，不支持的语法在转换层降级（脚注降级为文末列表，`> [!NOTE]` 降级为普通引用）。公众号 adapter 在 md 转 HTML 后再跑一遍内联样式注入，代码高亮必须预渲染成 span，编辑器不会帮你高亮。

**3. 图片处理（assets）**。上传前对图片做内容 hash，维护"源图 URL → 平台 URL"的映射缓存，重发时直接复用，不然重复上传很快撞素材库限额。映射表和文章一起入库。

**4. 编排（publish）**。把前三步封装成 MCP 工具暴露给 Agent：`lint_md` / `transform` / `upload_images` / `publish`。两条硬约束：源文件只读，Agent 只能通过工具产出派生文件；`publish` 必须先出 dry-run 的 diff 预览，确认后才真发。

## 踩坑点

- 公众号的安全过滤比想象中激进，`style` 里部分属性会被剥离，复杂布局别指望，老老实实用它支持的子集。
- prettier 默认会重排表格对齐，遇到内容长的中文表格会产生大 diff，建议表格跳过格式化或走独立规则。
- 平台锚点链接（`[](#section)`）在公众号、知乎上基本无效，lint 阶段直接禁掉。
- Agent 改稿时容易"顺手"重排全文，导致图片映射缓存全部失效。规范化的意义正在于此：源格式稳定，hash 才稳定。

## 可复用建议

- 一份正典，多份派生。派生文件永远不手改，要改就改正典重新生成。
- 能力矩阵写成数据（JSON/YAML）而不是硬编码在 adapter 里，新平台接入成本会低很多。
- 每个转换器配 golden file 快照测试，AI 改完稿先跑测试再发布，比人眼校对格式靠谱。

## 总结

这套管线没用到什么新东西，本质是"正典 + 适配器 + 缓存"的老三样，但它把格式问题从 Agent 的上下文里彻底移走了：Agent 只管内容和一次规范化，剩下的平台差异由确定性代码消化。发布成功率从"碰运气"变成"跑测试"，这是我们认为最值得的一点。
