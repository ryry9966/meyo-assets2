## 背景

OpenClaw 这类 Agent 框架的核心能力是"让模型动手"：读写文件、执行 shell、调用 MCP 工具。能力越大，误操作半径越大。任务描述里一个含糊的路径、一条注入在网页或文档里的指令，都可能让模型得出"删掉这个目录"的结论。所以真正的问题从来不是"模型会不会犯错"，而是"错误发生时，执行层能不能兜住"。

## 误删是怎么发生的

复盘实际案例，误删基本来自三条路径：

1. **路径解析错误**：模型把相对路径、`~`、符号链接拼错，落到了工作区外；
2. **工具越权**：某个插件或 MCP server 注册了自己的文件工具，绕过了主策略；
3. **Shell 旁路**：文件工具限制得很严，但 bash 工具没做隔离，模型直接 `rm -rf`。

这三条路径决定了 sandbox 不能只做一层。

## OpenClaw 的四层做法

**第一层：工作区 jail。** 所有文件工具的路径在进入实现前统一走一个 resolve 入口：先解析绝对路径和 `..`，再做 realpath（解符号链接），最后校验结果必须落在 workspace root 内，否则直接拒绝。关键是"解析后再校验"，而不是字符串前缀匹配——后者会被 `../` 和软链轻松绕过。

**第二层：破坏性操作降级。** Agent 发起的删除默认不调 unlink，而是移动到工作区内的 `.trash/` 并记录元数据，保留 N 天。不可恢复的操作（如 `git clean`、覆盖无备份文件）标记为高危，走确认门：工具调用挂起，把 diff 和目标路径推给人审批。

**第三层：shell 沙箱。** bash 执行放进容器/namespace 隔离环境：workspace 读写挂载，其余目录只读或不挂载，网络默认关闭，子进程自动继承限制。这一层堵住了"文件工具守规矩、shell 乱来"的旁路。

**第四层：审计与回滚。** 每次文件变更记录 before/after 快照和完整调用链（哪次会话、哪个工具、哪段 prompt 触发）。真删错了，恢复靠数据，不靠回忆。

## 一次可复现的验证

配置完别急着上生产，做三个演练：

1. 在工作区外的 `/tmp` 放一个 canary 文件，让 Agent "清理 /tmp 旧日志"，确认被拒绝；
2. 在工作区内建一个指向 `~/.ssh` 的软链，让 Agent 读取并删除它，确认 realpath 校验生效；
3. 让 Agent 执行 `rm -rf ~`，确认 shell 沙箱将其拦截。

三个演练都应以 Agent 侧失败告终，并在审计日志里留下记录。没有留下日志的拦截，等于没拦。

## 踩坑点

- **符号链接是第一大坑**。jail 不做 realpath 等于没做。
- **插件自带工具必须过同一个策略入口**。MCP server 引入的文件工具如果直接落盘，前两层全部失效。OpenClaw 中所有工具调用都应经过 policy engine 注册与拦截。
- Docker socket、宿主机家目录挂进沙箱，等于沙箱白做。
- macOS 注意 NFD/NFC 文件名归一化差异，路径校验前先归一化。
- 模型生成的脚本里再起子进程，沙箱必须作用到整棵进程树，而不是只管直接调用。

## 可复用建议

- 默认拒绝，显式放行；白名单只加真正需要的路径。
- Agent 的删除一律软删除，硬删除只留给人。
- 把 sandbox 当代码维护：每一种已知绕过手法都写一条回归测试。
- 工具清单越短越好，每个工具都是攻击面。

## 总结

模型的输出是概率性的，所以安全必须建立在确定性的执行层上：路径解析收口、破坏性降级、进程隔离、审计回滚——四层单独看都不完美，叠起来才构成"Agent 不会误删文件"这个承诺。信任来自架构，不来自 prompt 里那句"请小心操作"。
