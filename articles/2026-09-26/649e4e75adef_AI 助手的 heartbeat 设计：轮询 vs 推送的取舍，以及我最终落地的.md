## 背景

OpenClaw 这类常驻 Agent 默认是被动的：用户不发消息，它就不动。但自动化场景恰恰需要它会"自己醒"——定时巡检目录、盯着下载任务、到点推提醒。heartbeat 就是干这个的：让 Agent 周期性或被事件驱动地醒来一次，检查有没有活干。

OpenClaw 自带的 heartbeat 本质是轮询：按间隔唤醒，检查心跳清单文件里有没有待办。用久之后我开始遇到瓶颈，于是把推送方案也试了一遍，这里记录取舍过程。

## 问题

轮询的问题很直白：间隔短，大量心跳是空转，每次唤醒都是一次模型调用，token 在烧；间隔长，事件响应的延迟上限就是间隔本身。推送看起来优雅，但坑不少：事件源（webhook、文件监听、消息队列）各接各的，去重、削峰、可靠性都要自己做，而且"事件到达"和"该不该唤醒模型"是两回事。

## 做法：轮询打底，条件门控，推送加速

1. **保底轮询**：默认 30 分钟一次心跳，加 10% 随机抖动避免共振；夜间拉长到 2 小时。
2. **条件门控前置**：心跳先跑一段宿主侧脚本，只查条件——inbox 是否非空、文件 mtime、任务状态位。有活才唤醒模型，没活直接结束。这一步把 90% 以上的空转挡在了模型调用之前。
3. **推送走收件箱**：外部事件不直接打断会话，而是写入 inbox 文件，带事件 ID 和时间戳。心跳醒来先消费 inbox，天然获得去重与合并的机会。
4. **合并与限频**：同一来源事件在 60 秒窗口内合并为一条；每小时唤醒模型的次数设上限，超了排队到下个周期。
5. **用户会话优先**：检测到用户正在活跃对话，心跳只入队不打断，等静默后再处理。

## 踩坑点

- **空转烧 token**：最初每条心跳都直接进模型，一晚上烧几千 token 只为回答"没事"。加上条件门控才降回正常水位。
- **文件监听风暴**：编辑器保存会连触发多次事件，inbox 瞬间堆积。60 秒合并窗口解决。
- **休眠后补课**：机器休眠恢复后定时器连发积压心跳。改成醒来只执行最近一次，跳过积压。
- **事件重复投递**：webhook 是至少一次语义，同一任务跑了两遍。靠事件 ID 去重表解决，记录保留 24 小时。

## 可复用建议

- 巡检逻辑放宿主侧，模型只做决策不做扫描，这是省 token 最有效的一刀。
- 轮询保证下限（事件最多延迟一个周期被发现），推送保证上限体验（快），不是二选一。
- 每次心跳记日志：触发源、是否唤醒模型、耗时、token 消耗。没有这份数据，间隔参数是拍脑袋调的。
- 心跳失败必须静默降级加退避重试，不能把主会话搞挂。

## 总结

纯轮询简单可靠但浪费，纯推送高效但工程量与兜底成本都高。对个人和小团队部署，"低频轮询 + 宿主侧条件门控 + 事件进 inbox"的混合方案，百来行代码就能落地，成本与延迟都可控。先跑起来，再看日志决定往哪边调。
