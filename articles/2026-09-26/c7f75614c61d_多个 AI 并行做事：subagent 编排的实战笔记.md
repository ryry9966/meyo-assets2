## 背景

单 agent 干长活有两个老问题：一是上下文越滚越脏，探索过程的中间细节把主对话塞满，跑到后半段模型开始"失忆"；二是纯串行太慢——排查 6 个模块、比对 5 份日志这类活，本质互相独立，排队执行纯属浪费。

subagent 的思路很直接：主 agent（parent）把任务拆成若干份，每个子 agent 在独立上下文里跑，结束后只把结论带回主对话。OpenClaw 里派生子会话、MCP 工具调用都能落地这个模式，关键不在工具，在拆法和收法。

## 问题

上周的实际场景：给一个多模块仓库做依赖升级影响面排查。单 agent 跑了两次都失败——第一次扫到第三个模块时上下文被压缩，前面的调用点细节丢了；第二次虽然跑完，报告里混着大量探索噪音，没法直接给同事看。

## 做法

1. **先判断可拆性**。并行有三个前提：子任务之间无依赖、以读为主、结果能压缩成短结论。强顺序的编码类活不要硬拆。
2. **给每个 subagent 写任务简报**。模板就三行：目标一句话（"只排查 payments 模块对旧版 SDK 的调用点"）、边界（"只读，不改文件，不执行命令"）、输出格式（"≤10 行：风险调用点 + 文件路径 + 一句建议"）。
3. **让 parent 派活并控并发**。主提示里明确："以下 6 个模块各派一个 subagent，最多同时 3 个"。并发 3–5 是比较稳的区间，再高容易撞限流，报告也会把主上下文灌爆。
4. **聚合时要求交叉核对**。收完结果让 parent 做三件事：去重、标记互相矛盾的结论、原始细节落盘只留路径。最终汇报只进结论层。

这么跑下来，墙钟时间大约降到串行的三分之一，主对话始终干净，报告可直接复审。

## 踩坑点

- **简报太虚，子 agent 乱逛**。只说"看看这个模块"会烧掉大量 token。目标、边界、输出格式缺一不可。
- **只读任务没锁权限**。有次子 agent"顺手"改了配置文件。排查类任务一定显式声明只读，最好跑在受限沙箱里。
- **报告直通直出**。parent 偷懒把 6 份结果原样拼接，两份矛盾的结论一起进了报告。聚合必须做核对，冲突项单独标注。
- **嵌套派生失控**。子 agent 又派生孙 agent，深度和成本都失控。给递归设上限，一般两层足够。
- **共享可变状态**。两个子 agent 同时写同一个临时文件会互相覆盖。用 copy-in / copy-out，各写各的结果文件。

## 可复用建议

- 简报模板固定下来：一句话目标 + 边界 + 输出格式，贴在项目里让 parent 照着填。
- 记住"扇出调查、单点收口"：并行只用于只读调查，所有写操作回到 parent 或单一执行者，避免并发写。
- 子 agent 返回尽量短，原始材料写文件、回传路径。
- 把每次的简报和结果存档，复盘时能看出哪份简报写得差导致返工。
- 先算账：并行省下的时间 vs 多花的 token。小任务串行反而干净。

## 总结

subagent 编排解决两件事：上下文隔离和并行提速。工程量不在"会调 spawn"，而在拆任务的判断和聚合时的核对。建议从只读类排查任务起步，把简报模板跑顺，再往生成类、执行类扩展——写操作的并行要谨慎得多。
