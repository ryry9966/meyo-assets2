## 背景

自动化流程里，Agent 的能力大多靠外部调用撑着：MCP 工具、搜索接口、模型供应商、业务 API。一个环节抖动，整条任务链就可能跟着挂。我复盘了自己几条流水线的失败记录，真正“代码写错”的很少，多数是依赖不稳定时，Agent 缺少一套明确的恢复策略。

## 问题

API 挂掉时，常见三种崩法：

1. **重试风暴**：工具层在重试，模型看到失败又自己重试，两层叠加，把摇摇欲坠的上游彻底打挂，token 也烧掉。
2. **静默失败**：异常被 catch 后返回空字符串，模型以为调用成功，基于空数据编造结论。这是最危险的一种。
3. **一挂全挂**：某个非核心接口超时，整个任务卡死，核心步骤反而没完成。

## 做法

我现在的方案分五层，按顺序生效：

1. **超时**：每个工具调用必须显式设超时（HTTP 10s，LLM 调用单独放宽），且工具层超时要小于网关超时，避免套娃等待。
2. **分类重试**：429/5xx/超时走指数退避加抖动，1s→2s→4s，最多 3 次；4xx 不重试，直接把结构化错误返回给模型；非幂等操作（建工单、发消息）重试前先查询确认没成功。
3. **熔断**：同一工具连续失败 5 次即打开熔断，60 秒内直接走降级，不再打真实请求。这层做在工具封装里，对模型透明。
4. **降级**：每个关键工具准备一条退路——带时间戳的缓存、备用供应商、或明确跳过。优先缓存加时间戳，模型能自己判断数据还能不能用。
5. **把失败写回上下文**：失败时不只抛异常，而是返回结构化描述，例如“搜索服务暂不可用，已重试 3 次，建议改用本地知识库”。模型拿到这种信息通常能自己绕行；拿到模糊报错就只会反复撞墙。

最后加一个总预算：单任务的重试次数、总耗时、token 上限，超了就终止并输出已有的中间结果。配置大致长这样：

```yaml
retry: { max_attempts: 3, backoff: exponential+jitter }
circuit_breaker: { threshold: 5, cooldown: 60s, half_open_probe: true }
fallback: [cache_with_timestamp, backup_provider, skip]
budget: { max_retries_per_task: 12, wall_clock: 5m }
```

## 踩坑点

- **两处都在重试**：早期我在工具层和 prompt 里都写了“失败就重试”，一次上游抖动被放大成六倍请求。原则改成：重试只在一处做，另一处明确说“不要重试，报告失败”。
- **降级链太长**：主服务切备用，备用慢再切缓存，单次调用延迟叠到 40 秒，上层早就超时。降级路径最多两级。
- **熔断恢复抖动**：冷却结束直接全量放行，刚好撞上对方半死不活。改成半开状态，先放一个探测请求。
- **报错太“客气”**：给模型的错误写成“出错了，请稍后再试”，它就真的稍后再试。错误信息必须带决策线索：类型、已重试次数、建议动作。

## 可复用建议

- 超时、重试、熔断统一封进工具包装层，新插件接入即自带恢复能力；
- 工具 schema 里写明错误语义：失败时返回什么、调用方该怎么反应；
- 每次外部调用打结构化日志：工具名、错误类型、重试序号、是否降级，复盘全靠它；
- 定期手动压测降级路径——降级代码平时不跑，出事时多半是坏的。

## 总结

外部 API 挂掉不是异常，是常态。错误恢复的目标不是“永不失败”，而是失败发生时：快速失败、按类恢复、给模型留足绕行信息、永远有成本上限。这套分层方案不复杂，难在每一层都要真的落进代码和 prompt，光指望模型自己聪明，扛不住生产环境。
