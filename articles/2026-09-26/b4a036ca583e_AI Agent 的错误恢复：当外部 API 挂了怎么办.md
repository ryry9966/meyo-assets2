## 背景

跑 Agent 自动化的人基本都遇到过这个场景：流程在本地测得好好的，某天上线后外部 API 一挂，整条链路瘫掉。LLM 调用、MCP 工具、第三方插件——每一环都依赖外部服务，而外部服务的可用性从来不归你管。

Agent 和普通后端服务的区别在于：**失败之后，模型还会参与决策**。处理不好，轻则任务中断，重则 token 烧穿、写操作重复执行。

## 问题：三种典型翻车现场

1. **无限重试**：循环里收到 429 就立刻重试，没退避、没上限，直到把当天额度烧完。
2. **把堆栈喂给模型**：异常信息原样塞进上下文，模型开始一本正经地"修复"一个根本不归它管的问题，产出看似合理实则 hallucination 的方案。
3. **重试副作用**：发通知、下单这类非幂等写操作重试三次，用户收到三条重复消息。

## 做法：一套可落地的分层恢复策略

**1. 先分类，再重试。** 可重试：网络超时、429、502/503/504；不可重试：401/403、400 参数错。分类错了，后面全白搭。

**2. 指数退避 + 抖动 + 硬上限。** 1s → 2s → 4s，加随机抖动防止重试风暴，最多 3~5 次。做成插件层的统一中间件，别让每个 MCP 工具各写一遍。

**3. 熔断与降级。** 连续 N 次失败即熔断，直接走降级路径：缓存兜底、备用 API、或明确标记"该步骤跳过"。部分成功好过整体失败。

**4. 给模型结构化错误，不是堆栈。** 工具返回统一 schema，例如：

```json
{"retryable": false, "step": "fetch_weather", "reason": "auth_failed", "suggestion": "skip_or_ask_user"}
```

模型拿到这个才知道该跳过、换工具还是询问用户。

**5. 写操作必须幂等。** 带 idempotency key 或请求 ID，重试前先查状态，避免重复扣款、重复发送。

**6. 长任务做检查点。** 中间状态落盘，恢复时从断点继续，而不是从头重跑——否则前面已成功的写操作会再执行一遍。

## 踩坑点

- **超时拍脑袋**：设 60s 以上，Agent 看起来"卡死"；设太短又把慢请求误判为失败。建议按目标 API 的 P99 耗时来定。
- **`except Exception: pass` 式兜底**：把配置错误也吞了，排查时日志一片祥和、一无所获。
- **降级路径没测过**：真出事时才发现缓存是空的、备用 API 的 key 早就过期了。
- **只重试不记录**：失败率多少、重试几次全靠猜，永远等用户反馈才知道出了问题。

## 可复用建议

- 在工具层抽一个统一的 `with_retry` + 熔断包装器，所有 MCP 工具默认套上。
- 定义统一的错误返回 schema，让上层 Agent 的"跳过/重试/换路/问用户"决策逻辑可跨工具复用。
- 做故障注入演练：mock 一个永远 503 的 API，把降级路径当正式功能来测。
- 观测先行，三个指标就够：重试次数、熔断触发次数、任务降级率。

## 总结

Agent 的错误恢复不是 try-catch，而是设计出来的：**失败要分类、重试要限次、路径可降级、状态可恢复、指标可观测**。外部 API 一定会挂，问题只在于挂的那一刻，你的 Agent 是优雅降级，还是在循环重试里烧 token。建议先把重试中间件补上，再谈更复杂的自动化。
