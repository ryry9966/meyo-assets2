## 背景

跑 OpenClaw 这类长期在线的 Agent，能力几乎全部来自工具调用：搜索、数据库、第三方 MCP server、自建插件。我的一次实际教训是：凌晨的定时任务里，上游一个 REST API 返回 503，Agent 连续重试了十几轮，烧掉不少 token，最后还把缓存里的旧数据当成新结果发了出去。从那以后，我把"外部 API 会挂"当作默认前提来设计工具层。

## 问题

失败时的典型表现有三种，比"直接崩掉"更麻烦：

1. **原地死循环重试**。模型看到报错，第一反应是再调一次同样的工具，没有上限。
2. **把失败当成功**。API 返回 200 但 body 是错误结构，或超时后拿到部分数据，Agent 照样往下推理。
3. **编造结果**。工具返回空或异常时，模型有时会"补"一个看起来合理的数据——这是最危险的。

核心矛盾在于：重试、退避、熔断是确定性的工程逻辑，交给模型用自然语言判断，既贵又不可靠。

## 做法

我的原则：**机械的重试放在工具层代码里，模型只负责策略层的重新规划**。分四步：

**1. 统一封装所有外部调用。** 超时、重试次数、退避间隔全部显式配置，不允许无限等待：

```python
def call_tool(fn, *, timeout=10, retries=3, fallback=None):
    for i in range(retries):
        try:
            return fn(timeout=timeout)
        except TransientError:
            sleep(backoff(i) + jitter())
    return fallback  # 结构化的降级结果
```

**2. 错误分类。** 429 / 5xx / 超时属于瞬时错误，值得重试，且必须读 `Retry-After`；401 / 404 / 参数错误属于永久错误，重试没有意义，直接返回失败。

**3. 结构化错误返回给模型。** 不要把堆栈丢给模型，返回类似：

```json
{"status": "error", "code": "upstream_timeout", "retried": 3,
 "suggestion": "use cached data or ask user"}
```

模型拿到这种信息才能做出像样的决策：换数据源、降级输出，或者停下来问人。

**4. 熔断与预算。** 同一工具连续失败 N 次后进入冷却，冷却期内直接返回"已知不可用"，不再真的发请求。同时给每次任务运行设 token / 时间预算，超了就终止，避免凌晨三点无人在场时的死亡螺旋。

## 踩坑点

- **在系统提示词里写"失败了就重试"**。模型会紧凑循环重试，token 消耗远超预期。重试节奏必须由代码控制。
- **重试非幂等操作**。POST 下单、发消息这类调用，超时可能意味着"已成功但响应丢了"，盲目重试会重复执行。要么只重试幂等操作，要么带 idempotency key。
- **降级数据不带时间戳**。用缓存兜底时一定要标注数据新鲜度，否则 Agent 会把三小时前的天气当实时数据播报。
- **429 立刻重试**。只会让限流更久，务必尊重 `Retry-After`。
- **熔断没有恢复机制**。冷却结束后应放一个探测请求（半开状态），否则一次网络抖动会让服务在 Agent 眼里"永久下线"。

## 可复用建议

1. 所有外部调用走同一个 helper，错误契约统一，别每个插件各写一套。
2. 每个工具声明自己的超时 / 重试 / 降级策略，写在插件配置里，而不是散落在代码各处。
3. 上线前做一次混沌测试：手动把某个 API 域名指向不存在的地址，观察 Agent 的完整行为路径。
4. 日志里区分"工具层重试"和"模型层换方案"，事后复盘才知道哪一层出了问题。

## 总结

Agent 的错误恢复本质是系统工程，不是提示词工程。在工程层把确定性的重试、退避、熔断做完，再让模型拿到干净的结构化状态去规划下一步，模型应该是决策链的最后一环。做到这一点，外部 API 挂掉时，你的 Agent 才是"降级运行"，而不是"失控运行"。
