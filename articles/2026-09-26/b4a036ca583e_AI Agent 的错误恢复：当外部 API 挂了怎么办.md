## 背景

在 OpenClaw 的实际部署里，Agent 很少只靠模型干活：查数据、发消息、调内部系统，几乎都走 MCP 工具或插件，最终落到外部 API 上。而外部 API 的可用性从来不是 100%，限流、超时、5xx、证书过期都是日常。很多人把“调不通”当异常路径处理，结果一次普通的接口抖动，就演变成整条自动化链路的故障。

## 问题：Agent 遇到 API 故障时的三种典型坏行为

1. **原地死循环重试。** 模型收到报错倾向于“再试一次”，且没有任何退避，几秒内烧掉大量 token，还可能加剧上游限流。
2. **拿报错硬编。** 原始堆栈塞进上下文，模型要么胡乱解释，要么编一个“看起来合理”的结果。
3. **静默失败。** 插件返回空列表，Agent 分不清是“真没数据”还是“接口挂了”，直接基于空结果继续推理，产出错误结论。

共同根源只有一个：错误处理被放在了错误的层级——交给模型临场发挥，而不是工程层兜底。

## 做法：把恢复逻辑下沉到工具层

**第 1 步，错误分类。** 在插件内部先把错误分成瞬态（超时、429、503）和永久（401、404、参数非法），只有瞬态错误值得重试。

**第 2 步，代码内重试。** 瞬态错误在插件里做指数退避加抖动，比如 1s/2s/4s，硬上限 3 次。重试节奏必须由代码控制，不要指望模型“等会儿再试”——它不会等。

**第 3 步，设计给模型看的错误信息。** 重试耗尽后返回给 Agent 的不是堆栈，而是结构化语义：错误类型、是否可重试、建议动作（换备用工具 / 稍后再试 / 上报用户）。模型需要的是决策依据，不是日志。

**第 4 步，降级路径。** 为关键工具准备至少一条备选：备用 API、带陈旧度标记的缓存数据，或“输出部分结果并显式声明缺失”。宁可答案不完整，不要答案错误。

**第 5 步，熔断。** 连续 N 次失败后把该工具标记为不可用，冷却窗口内直接告诉 Agent 绕路规划，避免继续撞墙。

**第 6 步，断点续跑。** 长任务把中间状态落盘，恢复时从断点继续，而不是从头再来一遍。

## 踩坑点

- **重试没加抖动**：多个定时任务同一时刻集中重试，形成惊群，把本来快恢复的 API 打得更死。
- **分不清“空结果”和“失败”**：200 加空列表是合法响应，必须与接口报错区别处理，日志里也要分开记。
- **退避无上限**：把退避总时长纳入任务超时预算，别让重试把整个任务拖过期。
- **熔断状态只存在单进程内存**：多实例部署时各实例各自重试，熔断形同虚设，状态要放共享存储。
- **系统提示里没写降级行为**：工具层返回了“不可用”，但没告诉 Agent 该怎么办，它仍会反复尝试调用。

## 可复用建议

- **统一工具响应 schema**：所有外部调用返回 `ok / data / error / retryable / hint` 五个字段，Agent 侧处理逻辑只写一份。
- **重试与熔断参数按工具独立配置**，不要全局一套：内部服务和第三方服务的容忍度完全不同。
- **在系统提示里预置降级指令**，例如“当某工具标记为不可用时，改用备选方案或明确告知用户”，把降级写成约定，而不是临场反应。
- **错误事件结构化落日志**，事后能回答“那次故障是被哪一层兜住的”，这比事后复盘聊天记录有用得多。

## 总结

API 故障不是异常，是常态。错误恢复本质是系统设计问题，不是提示词问题：重试、超时、熔断在工具层用代码兜住，模型层只负责根据语义化的错误信息做路径决策。把这套分层做完，Agent 才能从“一挂就崩”变成“挂了也能体面降级”——这也是自动化任务敢长期挂机的前提。
