## 背景

我们团队用 OpenClaw 做自动化流水线时，主 agent 经常接到"复合任务"：比如每周仓库巡检，要同时做依赖审计、文档过期检查、issue 归类。单 agent 串行跑，一条 20 分钟的任务链要排队一小时以上，而且上下文越堆越长——巡检日志、报错堆栈全塞进主会话，后半段的任务质量明显下降。

OpenClaw 的 agent 支持派生 subagent：主 agent 把拆好的子任务交给独立会话的 subagent 执行，各自跑各自的，完成后把结果汇回主 agent。听起来简单，真用起来有几个必须想清楚的点。

## 问题

1. 串行执行慢，长链路任务没有并行度；
2. 主 agent 上下文被中间过程污染，影响后续判断质量；
3. 子任务之间有隐性依赖，盲目并行会互相踩。

## 做法

核心原则：能并行的不是"步骤"，而是"边界清晰的子任务"。

1. **拆解**：主 agent 先把任务写成 3~5 份自包含的子任务描述，每份包含输入、产出物、验收标准，不假设 subagent 知道父任务的任何背景；
2. **派发**：一次 fan-out 派生 subagent，每个只领一个子任务，约定返回结构化摘要（JSON 或固定小节），不要求贴全量日志；
3. **隔离执行**：subagent 各写各的产物文件（按子任务命名），主 agent 不参与中间过程；
4. **汇聚**：主 agent 收齐结果后做一轮汇总校验——核对产物是否齐全、结论是否互相矛盾，再生成最终报告。

伪代码示意：

```
主 agent:
  tasks = 拆解(原始需求)        # 自包含的子任务列表
  并行派发(tasks)               # 每份独立 subagent
  results = 收集(等待完成/超时)
  汇总校验(results) → 最终产物
```

## 踩坑点

- **把父会话记录直接丢给 subagent**：等于没拆。subagent 的上下文应最小化，只给任务描述和必要的文件路径；
- **并发数不设限**：一晚把 MCP 工具的限流打爆。后来固定 fan-out ≤ 4，超出的进队列排队；
- **多个 subagent 写同一个文件**：互相覆盖，结果拼不上。改成"一任务一文件"后彻底消失；
- **subagent 卡死没人管**：给每个子任务加超时和失败兜底，超时即标记失败，由主 agent 决定重试还是降级；
- **汇总时偷懒直接拼接结论**：矛盾结论会混进报告。汇总这一步必须由主 agent 真正"读一遍"再下笔。

## 可复用建议

- **粒度**：一个 subagent 一件事，预计 5~15 分钟完成为宜。太碎则调度开销占比过高，太粗则失去并行意义；
- **接口**：约定统一的返回结构（状态 / 结论 / 产物路径），主 agent 的汇总逻辑就不用反复改；
- **隔离**：subagent 只写自己的输出文件，需要共享的数据走约定目录，绝不共享会话；
- **收敛**：并行只是手段，最后一定要保留一道主 agent 复核的串行关口。

## 总结

subagent 编排解决的不是"模型不够聪明"，而是"单会话装不下、串行跑不完"。拆得清边界、管得住并发、兜得住失败，这个模式就能稳定用于巡检、批量处理、多源调研这类场景。它不神秘，本质是工程上的分治 + 队列 + 汇聚，只是执行者换成了模型。建议从一个每天重复的串行任务开始改造，跑一周再谈扩展。
