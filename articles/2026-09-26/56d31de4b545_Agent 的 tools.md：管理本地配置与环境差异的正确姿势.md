## 背景

跑过本地 Agent 的人多半遇到过这种场景：同一套提示词、同一组插件，在自己机器上顺滑运行，换台电脑或丢进 CI 就开始报错——Agent 找不到 `brew`、用了不存在的路径，或者自作主张装了一堆全局依赖。根因很朴素：Agent 对“这台机器长什么样”一无所知，只能靠猜。

MCP 和插件解决了“能力从哪来”的问题，但没解决“环境是什么样”的问题。社区里已有 AGENTS.md 这类约束行为的约定，但环境信息一直缺一个固定的沉淀位置：这台机器用 apt 还是 brew、Python 是系统自带还是 pyenv、出网要不要走代理——这些散落在各处 prompt 和脚本里，改一处漏三处。

## 做法

我的方案是收敛成一个文件：在工作区根目录维护一份 `tools.md`，内容分五块：

1. **系统概况**：OS、架构、shell 及版本，两三行即可。
2. **工具清单**：Agent 可能调用的命令，每行一条，写清版本和路径，如 `node 20.11.0 (/usr/local/bin/node)`。
3. **偏好与约束**：包管理器优先级（“装 Node 依赖一律用 pnpm”）、禁止事项（“不要改动 shell rc 文件”）。
4. **已知怪癖**：这台机器的坑，比如“docker 需要 sudo”“出网必须走代理”。
5. **敏感项占位**：只写“连接串在 `.env` 的 `DB_URL`”，绝不写真值。

初版不用手写，一个十几行的 shell 脚本把常用命令的 `--version` 输出 dump 出来，再手工补怪癖和约束就够。

接入方式按成本从低到高：直接在系统提示里要求 Agent 开工前先读这个文件；或用 MCP 把它暴露成 resource；团队协作场景下，仓库放通用模板 `tools.md`，机器差异放进 gitignore 的 `tools.local.md`，Agent 两份都读，后者覆盖前者。

## 踩坑点

- **密钥入库**。tools.md 很容易被顺手写进真实连接串然后 commit。原则：文件里只允许占位符，配 pre-commit 检查兜底。
- **写成了散文**。Agent 扫读的是清单，不是文章。长篇背景只会稀释关键信息，每条尽量压到一行。
- **信息过期**。装了新工具忘了更新，Agent 还按旧清单走。让 dump 脚本可反复执行，挂到 git hook 或定期跑。
- **无脑信任**。清单说有 `rg`，不代表 PATH 里真有。关键命令让 Agent 先 `command -v` 验证——清单是先验，不是契约。
- **上下文膨胀**。文件超过一两百行就该砍，Agent 用不到的（比如 GUI 软件列表）不要写。

## 可复用建议

- 把模板和 dump 脚本放进团队仓库，新人十分钟就能生成自己机器的版本。
- CI/容器里用同一模板生成对应环境的 tools.md，本地与流水线的行为差异会明显缩小。
- 分层比写全更重要：共性进模板，差异进 local，别为“一份文件走天下”塞成大杂烩。

## 总结

tools.md 本质上不是文档，而是给 Agent 的环境接口声明。它解决的不是“Agent 能不能干”，而是“Agent 在这台机器上该怎么干”。做到可生成、分层、最小化这三件事，换机器、换环境时那些啼笑皆非的报错，基本就消失了。
