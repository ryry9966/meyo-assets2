## 背景

很长一段时间里，我和主 agent 的协作是纯串行：调研一轮、改一轮代码、跑一轮测试，全在一个会话里排队。任务一多就暴露两个问题：一是慢；二是主会话上下文越塞越满，agent 开始"忘事"，注意力被稀释后输出质量明显下滑。

OpenClaw 的 subagent 机制提供了另一条路：主 agent 可以把任务派发给多个子 agent 并行执行，每个子 agent 有独立的上下文和 workspace，干完把结果交回来。主会话保持干净，只做拆分和汇总。

## 问题

我当时的真实需求：对二十多个插件仓库做一轮体检——读代码、核对配置、给出升级建议。串行跑一遍要一个多小时，而且做到后半段，主会话里已经堆了十几个仓库的细节，结论质量肉眼可见地变差。

## 做法

先定拆分原则：任务之间无共享写状态、单任务上下文自包含、输出有固定契约。

具体步骤：

1. **主 agent 先生成任务清单**，每个任务写成一份"任务书"：目标、输入文件路径、输出文件路径、格式要求。任务书必须自包含，不能假设子 agent 知道主会话里的任何事。
2. **通过 spawn subagent 派发**，并发限制在 3~4。每个子 agent 把结果写到自己的文件（如 `reports/<repo>.md`），绝不写同一个文件。
3. **回收只读摘要层**：约定子 agent 在结果末尾附固定格式的短摘要，或者最后单独派一个"汇总 agent"合并。主会话永远不直接消化全量原始输出。
4. **失败处理**：子 agent 失败重试一次，再失败就标记跳过，留给人工，不让主流程卡死在单个任务上。

20 个仓库的体检从一小时以上压到十来分钟，主会话上下文几乎没膨胀。

## 踩坑点

- **任务书不自包含**。最常见的问题：子 agent 拿到模糊指令后自由发挥，产出没法用。宁可任务书写长一点，把背景、边界、禁止事项全写进去。
- **多个子 agent 写同一个文件**。试过让它们追加到一份报告，结果互相覆盖。改成一人一个文件后问题消失。
- **并发开太大**。有一回开到 8，直接撞 API 速率限制，整批重试反而更慢。3~4 是我现在的默认值。
- **子 agent 输出全量回灌主会话**。上下文爆炸原地复现，等于白拆。输出契约里必须写明"摘要不超过 N 行"。
- **子 agent 里再 spawn 子 agent**。个别场景看似合理，实际很容易递归失控烧 token。在任务书里明确禁止。

## 可复用建议

- 把任务书模板固化成五段式：目标 / 输入 / 输出路径 / 输出格式 / 禁止事项。
- 输出契约用固定文件名 + 固定摘要格式，回收逻辑就能完全自动化，不需要人工盯。
- 并发数从 3 起步，观察 rate limit 表现再逐步上调。
- 一切落盘：任务书、子 agent 输出、失败标记都写文件，方便断点续跑和事后复盘。

## 总结

subagent 编排的本质不是"多开几个 AI 显得能干"，而是**用隔离换质量、用并行换时间**。前提是任务拆得干净、契约写得清楚。拆不干净的任务强行并行，只会把混乱放大几倍——先练好拆任务，再谈并行。
