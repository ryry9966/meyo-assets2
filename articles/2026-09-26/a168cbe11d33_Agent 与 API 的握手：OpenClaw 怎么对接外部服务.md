## 背景

Agent 的价值在于"能做事"，而做事几乎绕不开外部 API：查工单、发消息、读写数据库、触发 CI。在 OpenClaw 里，对接外部服务主要两条路：一是把 HTTP 接口包成 tool 插件，二是跑一个 MCP server，把一组能力以标准协议暴露给多个 Agent 复用。无论哪条路，本质都是同一件事：让模型在正确的时机、用正确的参数，调到正确的接口，并拿到它能消化的返回。

## 问题

实际对接时，常见的失败不是"调不通"，而是：

- **参数幻觉**：schema 写得太宽，Agent 自由发挥传参，接口报 400；
- **超时与重试**：慢接口拖死主循环，或者盲目重试把写操作执行了两遍；
- **返回值失控**：接口一次吐 50KB JSON，几轮下来上下文被撑爆；
- **密钥泄漏**：key 出现在对话、日志或报错信息里。

## 做法

以"包一个内部工单 API"为例，我的步骤：

1. **选路径**。单接口、内部用，直接写 tool 插件；要暴露一组能力给多个 Agent，就起一个 MCP server，统一鉴权和限流。
2. **收紧 schema**。参数只留必要的，能用 enum 就不写 free string；状态、优先级给枚举值，分页给默认值。schema 越窄，幻觉越少。
3. **鉴权放配置**。key 走环境变量或 secret 管理插件，注入在请求层，不进对话上下文，日志里做脱敏。
4. **超时 + 退避重试**。读操作超时 10s、重试 2 次带指数退避；写操作必须带幂等键（用任务 ID 派生），重试才安全。
5. **裁剪返回值**。插件层只回 Agent 需要的字段，列表默认截断到前 N 条并注明"是否还有更多"，详情让 Agent 按 ID 主动再查。
6. **留观测钩子**。每次 tool 调用记一条结构化日志：工具名、参数摘要、耗时、状态码、请求 ID，排障时能串起来。

## 踩坑点

- 把 OpenAPI 文档原样转 schema，参数上百个，模型必翻车。手写精简 schema 的十分钟，换来的稳定性远超自动生成。
- 重试非幂等的 POST，制造了重复工单。所有写接口默认按"有副作用"处理。
- 插件里吞掉异常只返回"调用失败"，Agent 只会反复重试。要返回结构化错误：错误码 + 人话描述 + 建议动作，Agent 才能决策。
- 分页没处理，Agent 拿到第一页就宣布"查完了"。
- MCP server 长连接没心跳，半天后静默失联，表象是 Agent "变笨了"，根因在连接层。

## 可复用建议

- **插件做薄**：只做参数校验、鉴权、裁剪，业务逻辑留在服务端。
- **先 dry-run**：新工具以只读模式上线，观察一周参数分布再放开写权限。
- **描述里写"什么时候不该用我"**：比夸自己好用更能降低误调用率。
- **版本化工具名**：改语义时新开 v2，别原地改，避免老任务行为漂移。

## 总结

对接外部服务不是把接口"塞给" Agent，而是做一层负责任的握手：窄 schema 管住参数，配置管住密钥，超时重试管住网络，裁剪管住上下文，日志管住事后。这五件事做完，Agent 调 API 会从"偶尔能用"变成"可以托付"。欢迎在回帖里贴出你的插件 schema，一起迭代出社区模板。
