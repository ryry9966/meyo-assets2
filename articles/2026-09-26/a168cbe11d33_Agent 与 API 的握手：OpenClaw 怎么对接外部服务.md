## 背景

OpenClaw 的价值在于让 Agent 从"能聊"变成"能办事"，而办事的入口几乎都是外部 API：工单系统、数据库、监控平台、内部 RPC。OpenClaw 提供了三条对接路径：**MCP server**（标准协议、可跨项目复用）、**原生插件**（进程内调用、延迟低）、以及**通用 HTTP 工具**（快速验证）。这篇帖子里，我以接一个内部工单 API 为例，把整个握手过程拆开讲。

## 问题

真正卡人的从来不是"发一个 HTTP 请求"，而是三件事：

1. **模型怎么知道该传什么参数**——schema 描述含糊，Agent 就会瞎填；
2. **失败时模型怎么自愈**——返回裸堆栈，模型只会道歉然后原地重试；
3. **凭据怎么不泄露**——密钥混进 prompt 或日志是最高频的事故。

## 做法

**1. 按场景选对接形态。** 一次性验证用通用 HTTP 工具加内联描述跑通即可；团队要复用就封装成 MCP server，把 schema、鉴权、限流集中管理；高频调用路径写原生插件，省掉序列化开销。

**2. Schema 写给人看，也给模型看。** 每个字段写清单位、格式、取值范围。比如 `priority` 是枚举 `["low","mid","high"]`，就别只写"优先级"两个字。

**3. 鉴权放环境，不进上下文。** 密钥从环境变量或密钥管理服务读取，在工具实现层注入请求头；工具输出和日志统一过一遍脱敏。

**4. 错误返回要"可行动"。** 把上游错误翻译成模型能决策的结构，例如 `{"retryable": true, "hint": "rate limited, wait 30s"}`。模型拿到这个就知道该等待还是该改参数，而不是盲目重试。

**5. 超时、重试、幂等三件套。** 读接口可以自动重试加指数退避；写接口必须带幂等键，否则 Agent 重试一次就多开一张工单。

**6. 控制返回体积。** 上游返回大 JSON 时先做字段裁剪或分页，别把 50KB 的响应直接灌进上下文，-token 和注意力都是成本。

## 踩坑点

- 工具描述只写"用于操作工单"，模型各种猜测调用姿势。描述里要写清**什么时候该用、什么时候不该用**。
- POST 不幂等却开了自动重试，一晚上重复建了 40 张单。写操作必须幂等键，或直接禁止自动重试。
- 429 被当成致命错误抛出，Agent 直接放弃任务。限流错误应归入"可重试"分支。
- 返回体里带了内部邮箱和临时 token，原样进了会话记录。返回前先过脱敏层。
- 时间参数没约定时区，查询区间整体偏移 8 小时，查了个寂寞。

## 可复用建议

- **做一层薄适配器**：上游 API 变动只改适配器，工具 schema 层不动；
- **capability 分级**：read / write / admin 分开注册，默认只挂载 read；
- **上线前跑 dry-run**：先让模型只输出调用意图、人工确认，再放开真实写权限；
- **给工具加版本号**：schema 变更时旧调用可以灰度过渡。

## 总结

Agent 对接外部服务，本质是一次**双向契约**：schema 契约让模型会用，错误契约让模型能自愈，安全契约让系统敢放权。这三件事都落在工具实现层，OpenClaw 的 MCP 与插件机制只是载体。实践中风险最低的路径是：先小范围 dry-run 验证调用质量，再逐步放开写能力。握手握稳了，Agent 才算真正接入了你的系统。
