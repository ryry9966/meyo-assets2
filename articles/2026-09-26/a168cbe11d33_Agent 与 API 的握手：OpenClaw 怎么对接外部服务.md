## 背景

Agent 的能力边界，基本等于它能调用的工具边界。模型再强，碰不到真实世界的 API，就只能输出“看起来对”的文本。OpenClaw 的对接层做的就是这件事：把外部服务的能力，翻译成模型可理解、可安全调用的工具。社区里反复出现同一类问题，这篇把对接的通用做法和踩坑整理一下。

## 问题

对接外部服务，失败往往不在“能不能调通”，而在调通之后：

- 鉴权信息散落各处，日志里泄漏 key；
- 工具描述含糊，模型传参与 API 实际要求对不上；
- 出错时只抛一段原始堆栈，模型无从自愈，只会盲目重试；
- 限流、超时、重试没设计，跑批量任务时把对方服务打挂。

## 做法

OpenClaw 对接外部服务有三条路径，按场景选：

1. **内置插件（plugin）**：服务稳定、调用高频、需要精细控制时用，schema 和错误处理完全自己定义；
2. **MCP server**：服务有现成 MCP 实现，或想让同一个工具服务多个 agent 时用，标准化最好；
3. **通用 HTTP 工具**：一次性、低频调用，声明一个带参数模板的工具即可，不值得写插件。

无论哪条路径，核心步骤一致：

1. **写好工具描述**。描述是写给模型看的“接口文档”，参数含义、单位、必填/可选、典型取值都要说清。"id" 和“用户 ID（数字，平台侧主键，不是手机号）”是两种效果。
2. **收窄工具面**。一个服务暴露 3–5 个工具足够，组合逻辑交给 agent，不要把 API 文档一比一搬进来。
3. **鉴权收敛**。密钥走环境变量或 OpenClaw 的 secret 机制，工具内部读取，日志统一脱敏。
4. **设计可被模型理解的错误**。返回结构化错误：错误码、一句话原因、下一步建议（如“date 格式应为 YYYY-MM-DD”）。模型拿到这个才可能自我修正。
5. **超时与重试**。统一默认超时；只对幂等操作重试并做指数退避；写操作带幂等键。

## 踩坑点

- **工具太多**：一个 agent 挂 40+ 工具，选择准确率明显下降。按场景拆分，按需挂载。
- **返回值不裁剪**：原始 JSON 整包塞回上下文，一次吃掉几千 token，还让后续推理被噪声干扰。只返回模型需要的字段。
- **重试不幂等**：下单接口超时自动重试，结果下了两单。写操作要么带幂等键，要么把重试决策留给上层。
- **长任务阻塞**：同步等待一个跑两分钟的导出接口，超时后模型判定失败。应改成“提交任务 + 轮询状态”两个工具。
- **描述与实现漂移**：API 改了参数但没同步工具描述，模型按旧描述传参，错得非常稳定。描述和 schema 必须放同一处维护。

## 可复用建议

- 把“工具描述 + 错误格式 + 超时重试策略”当成一份对外契约来写，纳入 code review；
- 所有外部调用统一走一层封装，鉴权、日志、限流在这一层做，工具本身只写业务逻辑；
- 提供 dry-run 模式，先验证参数和权限，再真实执行；
- 用录制好的 fixture 写工具单测，别在 CI 里打真实 API。

## 总结

对接外部服务的本质，是把“人的 API 契约”翻译成“模型的调用契约”。OpenClaw 提供了插件、MCP、HTTP 三条路径，但决定成败的是细节：描述是否精确、错误是否可读、重试是否安全。把这层做扎实，agent 的能力上限才真正取决于模型本身。
