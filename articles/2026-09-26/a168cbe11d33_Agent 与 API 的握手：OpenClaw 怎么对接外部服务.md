## 背景

Agent 的能力上限，往往不取决于模型本身，而取决于它能"摸到"哪些外部服务。查数据库、发消息、调内部系统，这些都要通过 API 完成。在 OpenClaw 里，这条链路通常由 tool / 插件 / MCP server 承担，但真正动手接的时候，问题比想象中多。

## 常见问题

把 API 粗暴包成 tool 丢给模型，经常出现这几种情况：

- 模型填错参数，调用频繁失败；
- 返回一大坨原始 JSON，上下文被撑爆；
- 网络抖动后自动重试，同一个写操作被执行两次；
- 工具注册了十几个，模型该用哪个全靠猜。

这些问题不是模型的锅，是握手协议没设计好。

## 我的做法

**1. 先划边界，再定工具。** 不要把一个服务的所有 endpoint 都暴露出去。一个服务收敛成 2~4 个语义清晰的 tool，比如 `query_order`、`create_ticket`，而不是把 `GET /api/v2/orders?xxx` 原样注册。

**2. 用 MCP server 或插件做统一封装层。** 鉴权、超时、重试、限流全部收在这一层，tool 定义里只留业务参数。token 过期刷新也在这里处理，模型永远不需要接触凭据。

**3. description 和 schema 认真写。** 这两样是模型唯一能"读懂"的文档。参数用 enum 约束取值，必填/可选标清楚；description 里写一句"什么时候该用我、什么时候不该用"，比十句功能介绍都有用。

**4. 返回结构化、可读的结果。** 我统一了返回协议：`{ok: true, data: ...}` 或 `{ok: false, error: "timeout", hint: "可重试"}`。带 `hint` 的错误让模型能自我修正，而不是反复撞墙。

**5. 写操作加幂等键和二次确认。** 凡是会改状态的调用，客户端生成幂等 ID，插件层做去重；高危操作先让 agent 输出意图，确认后再执行。

**6. 加最简单的观测。** 每次调用记录 tool 名、耗时、成败。一个文本日志就够，出问题时能分清是模型选错了工具，还是服务端真的挂了。

## 踩坑点

- **重试不幂等**：我交过最贵的学费。对 POST 类接口，先确认服务端支持幂等键，否则不要自动重试。
- **schema 太松**：一路 `type: string` 放行，模型就自由发挥。能用 enum、数值范围约束的都加上。
- **返回体不裁剪**：列表接口默认截断到前 N 条加总数，别把 200 条记录塞回上下文。
- **工具膨胀**：tool 超过 15 个之后，选择错误率明显上升，该合并的合并，该按场景拆的拆。
- **MCP server 无隔离**：一个下游服务挂了会拖死整个进程，注意超时控制和进程级隔离。

## 可复用建议

- 每个外部服务一个独立的 MCP server / 插件，故障不扩散；
- 错误协议里永远带 `hint` 字段，这是模型自纠的关键；
- 只读接口加一层短 TTL 缓存，省 token 也省配额；
- 新 tool 先在灰度会话里跑一周，看失败日志再回头改 description；
- 文档是写给模型看的，不是写给人看的——描述使用时机，而不是实现细节。

## 总结

Agent 与 API 的握手，本质是三份契约：模型能看懂的 schema、插件层统一的鉴权与容错、服务端保证的幂等与限流。OpenClaw 提供了承载这些契约的骨架，但契约的具体内容得自己写。工具不在多，在于模型每次都选得对、调得稳——做到这一点，对接外部服务就从"碰运气"变成了一个可工程化的问题。
