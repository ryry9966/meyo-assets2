## 背景

大多数 Agent 的使用模式是被动的：你发消息，它回答，然后闲置。真正跑在家庭服务器或 VPS 上的 Agent 明明具备持续运行的条件，却缺一个"定时醒来"的机制。OpenClaw 的方案很朴素——工作区里放一个 `HEARTBEAT.md`，网关按固定间隔把文件内容作为输入喂给 Agent，Agent 自己判断有没有活干：没有就返回 `HEARTBEAT_OK`，有就执行。

## 问题

用 HEARTBEAT.md 之前，做"每日简报""盯 CI 失败"这类事只有两条路：自己记得问，或者写一堆 cron 脚本。前者靠人脑调度，后者和 Agent 完全脱节——脚本挂了 Agent 不知道，Agent 收到的通知也带不上它已有的对话记忆。HEARTBEAT.md 补的正是这个缝隙：定时触发 + 共享主会话上下文 + 一份 Agent 可以自己维护的任务清单。

## 做法

1. 在工作区（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`，用 checklist 语法写任务；
2. 通过 `agents.defaults.heartbeat.secs` 调整间隔，默认约 30 分钟一次；
3. 任务写成祈使句，自包含、可验证，并显式写明触发条件，例如"如果当前是本地时间 08:00–08:30 且今天尚未发送简报，则发送"；
4. 让 Agent 完成后自己编辑文件、勾掉或删除已完成项——这份文件对 Agent 是可写的；
5. 需要精确时间的任务（比如每天 9 点整）改用 Cron，payload 直接指定动作；HEARTBEAT.md 留给"轮询型"任务。

我的文件里长期只有三条：早报、检查自建服务存活与磁盘水位、看指定仓库有无新 commit 且仅在变化时通知。

## 踩坑点

- **间隔设短了就是烧钱**。每次心跳都是一次真实的模型调用，60 秒级频率除非路由到小模型，否则账单很难看。默认 30 分钟对多数监控场景够用。
- **心跳跑在主会话里**。心跳产生的内容会进入日常对话上下文，任务输出要克制，让它"没消息就是好消息"。
- **任务描述模糊会导致两个极端**：要么 Agent 瞎干活，要么直接跳过。每条任务写清条件、动作、去重规则。
- **重复通知**。不写"仅在状态变化时通知"，它每次心跳都可能吵你一遍。去重规则必须显式写进文件。
- **它是轮询不是定时器**。别指望秒级精度，时间敏感逻辑不要寄托在这上面。
- **文件腐烂**。任务过时后 Agent 会一直执行旧任务，要像维护代码一样定期清理。

## 可复用建议

- 把 HEARTBEAT.md 当作"Agent 可自修改的任务队列"，而不是静态配置文件；
- 分工明确：心跳管态势感知（有没有异常），Cron 管精确调度（几点几分做什么）；
- 监控逻辑下沉到脚本或 MCP 工具，心跳任务只做"调用 + 判断 + 通知"，压缩单次心跳的耗时和 token；
- 无事时约定返回 `HEARTBEAT_OK`，并把每次心跳的实际动作写进日志，方便审计成本；
- 从一两条只读任务起步，观察一周再扩。

## 总结

HEARTBEAT.md 本质上只是一个 markdown 文件加一个定时器，但它把交互模型从"拉"改成了"推"。真正的价值不在机制本身，而在于它逼你把"希望 Agent 主动做什么"想清楚、写成可执行的文字。建议先放一条低风险的只读任务进去，跑一周，看成本和行为，再决定要不要养大这份清单。
