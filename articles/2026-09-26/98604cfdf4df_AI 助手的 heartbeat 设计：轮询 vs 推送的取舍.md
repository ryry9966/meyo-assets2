## 背景

跑 OpenClaw 这类常驻 agent，绕不开一个问题：助手怎么"知道该干活了"。触发路径基本就两条——定时醒来轮询（heartbeat / cron），或者外部事件直接推进来（webhook、MCP 通知、消息平台回调）。社区里常见的争论是"该选哪种"，但实际跑下来，答案几乎都是分层混合，区别只在于每层的厚度。

## 问题

纯轮询的代价：心跳 30 分钟一拍，大多数 beat 其实无事可做，但模型照样被拉起，token 和运行时间都在烧；间隔缩到 5 分钟，成本立刻可见。纯推送的代价：延迟低、按需触发，但要求 agent 有可达入口——公网端点、鉴权、防重放，家庭宽带加内网穿透这一套就劝退不少人。更麻烦的是语义层：推送只解决"事件到了"，不解决"该不该现在打扰用户、要不要合并"。二者都不是银弹。

## 做法

我们落地的结构是"心跳兜底 + 推送入箱 + 模型前预过滤"：

1. **任务分档**。按延迟容忍度分三档：分钟级（提醒、监控告警）、半小时级（邮件摘要、日报）、小时级以上（整理、巡检）。只有第一档才值得为推送付出运维成本。
2. **心跳做基线**。默认 25~30 分钟一拍，加随机抖动避免整点扎堆；beat 时先读一份任务清单文件，无事则按约定返回固定的短哨兵词，禁止展开长文。
3. **模型前预过滤**。心跳先跑一个便宜脚本，对比上次状态快照（mtime、hash、API 游标），没变化就不拉模型。这一步能砍掉九成空转。
4. **推送只做入箱**。Webhook 收到事件后只写进本地 inbox（文件或队列），带来源和时间戳；由下一次心跳统一消化，延迟敏感的事件才直接触发 run。
5. **并发锁 + 去重**。心跳和推送触发的 run 共用同一把锁；同一事件在冷却窗口内只入箱一次。

## 踩坑

- **空 beat 烧钱**：早期没做预过滤，一晚上几百次心跳白跑，账单很诚实。教训是"拉起模型"必须是最后一道门，前面尽量用脚本挡。
- **心跳进行中又来推送**：没锁时出现过两个 run 同时改同一份状态文件。锁必须在触发层做，别指望模型自己"注意"。
- **休眠丢拍**：笔记本睡眠、容器暂停时心跳是 best-effort，别拿它做精确计时；关键提醒交给系统级 cron 或推送兜底。
- **推送风暴**：监控抖动会瞬间灌满 inbox，入库前必须做合并与冷却。

## 可复用建议

- 默认轮询，测出延迟真的疼了再上推送，顺序别反。
- inbox 作为触发源和 agent 之间的唯一契约：来源可以很多，入口只有一个。
- 心跳间隔跟着任务 SLA 定，不拍脑袋。
- 每个 beat 记录触发源、耗时、token 消耗，跑一周再调参，比争论有说服力。

## 总结

轮询是兜底，推送是优化，inbox 是两者之间的解耦层。先把心跳做得便宜、可靠、可观测，再谈事件实时性——这套顺序，比"选哪种"这个二元问题重要得多。
