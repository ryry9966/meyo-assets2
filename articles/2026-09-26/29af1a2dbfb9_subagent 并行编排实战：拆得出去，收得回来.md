## 背景

用 OpenClaw 搭日常自动化一段时间后，最先撞到的瓶颈不是模型能力，而是单 agent 的串行结构：让它"审 PR、清理日志、过一遍文档目录"，三件事只能排队，前面卡住后面全等，上下文还越滚越长。subagent 编排就是针对这个问题的：主 agent 只负责拆解和汇总，执行交给多个带独立上下文的子 agent 并行跑。

## 问题

三个典型痛点：慢（串行长任务动辄十几分钟）、上下文污染（A 任务的过程记录干扰 B 的判断）、脆（一个任务抛异常全链路停摆）。而真正的功夫在回收端——子 agent 看不到主对话，结果怎么结构化回传、失败怎么兜底，比"拆出去"难得多。

## 做法

1. **拆任务，过三条硬标准**：子任务间无共享写状态（尤其不能同时改同一个文件）；输入描述能自包含；单任务 token 在一次会话内装得下。过不了就继续拆或合并。
2. **写"工单式" prompt**。把子 agent 当成看不到聊天记录的新同事：目标、输入的绝对路径、输出格式、禁止事项一次写全。输出强制结构化（JSON 或写入约定路径的文件）。
3. **并行派发，控制并行度**。OpenClaw 里可由主 agent 循环派发，也可用脚本批量起 session。并行度从 2–3 起步。MCP 工具有并发上限的（浏览器、本地索引类），在编排层加信号量，别指望子 agent 自己谦让。
4. **汇总走"摘要 + 产物"**。子 agent 返回结构化摘要，产物落盘，主 agent 只把摘要收进上下文，做去重和冲突合并。否则回收环节会把上下文重新撑爆。
5. **失败兜底**。每个子任务设超时；失败的单独重跑一次，仍失败就标记跳过，部分成功照常回收——编排层的价值就在"8 个成了 6 个，照样交付 6 个"。

## 踩坑点

- **上下文自包含最容易翻车**。我早期把主对话里的代词式描述（"刚才那个文件"）原样派发，子 agent 全部答非所问。工单必须写绝对路径和明确约束。
- **写冲突**：两个子 agent 同时改同一个配置文件，后写覆盖先写。解法是按文件/模块划边界，或子 agent 只产出 diff，由主 agent 统一落盘。
- **结果膨胀**：子 agent 回传全文日志，主上下文反而更大。强制"摘要 + 路径"。
- **并行度不是越高越好**：token 消耗近似线性放大，还容易触发限流。先测单任务成本再定并发数。
- **重试要幂等**：子任务有副作用（发通知、写数据）时，重跑前先确认上次是否生效，否则宁可跳过转人工。

## 可复用建议

- 先串行验证拆分正确，再开并行——串行都拆不对，并行只会放大错误。
- 子 agent 的 prompt 模板化保存，同类周期任务直接复用。
- 每次编排记一条 trace：拆几个、成几个、耗时、token 消耗，复盘全靠它。
- 只读型任务（检索、审查、分析）最适合并行；写操作保持串行或收敛到主 agent。

## 总结

subagent 编排本质是工程问题而非模型问题：拆分粒度、上下文隔离、结果回收做扎实，并行收益自然出来。经验就三条：并行度保守起步、结果结构化落盘、失败可降级。OpenClaw 的插件与 MCP 工具链足以支撑这套玩法，缺的往往只是编排纪律。建议从一个真实的三任务场景试起，跑通再泛化。
