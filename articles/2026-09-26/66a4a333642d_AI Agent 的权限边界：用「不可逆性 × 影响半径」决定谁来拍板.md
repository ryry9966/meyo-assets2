## 背景

Agent 项目的起步阶段都差不多：给模型接上一批 MCP 工具，让它自己跑。跑顺之后问题就来了——某次自动执行把测试库的表清了，或者往外部群发了一条没经过审核的消息。团队通常会做两件事之一：要么所有写操作全部改成人工确认，要么写一份「哪些操作危险」的口头约定。

两种都不对。前者把人变成确认机器，后者没法在工程上落地。

## 问题

Agent 的失败模式其实只有两种：

1. **该问没问**：不可逆操作直接执行，出了事故。
2. **不该问乱问**：每一步都停下来等确认，用户产生确认疲劳，最后见弹窗就点「确认」——这比不问更危险，因为它让确认机制整体失效。

权限边界的目标不是「多问」或「少问」，而是**让每一次「问」都有分量**。

## 做法

我们的经验是按两个维度划四象限：**不可逆性**（能不能撤销）和**影响半径**（只影响本会话/本文件，还是影响他人、生产环境、外部系统）。

- 不可逆 + 大半径：必须人工确认，且要展示足够的决策信息
- 可逆 + 小半径：直接干，别打断人
- 其余两格：默认确认，任务跑熟后可逐项降级

落地步骤：

1. **给工具打标，别让模型自己判断危险程度。** 在 MCP 工具元数据里写清楚 `readonly` / `reversible_write` / `irreversible` / `external_effect`。模型对危险性的自我描述不可靠。
2. **确认门做在执行层，不要只靠提示词。** 提示词会被注入、会被长上下文稀释。高危工具先返回 dry-run 结果——将要执行的 SQL、将要写入的 diff、将要发送的内容——agent 把预览展示给用户，拿到显式批准后才真正调用执行工具。
3. **设置批量阈值。** 删一条和删五千条不该是同一个授权动作，超阈值自动升级为人工确认。
4. **授权带作用域。** 「仅本次任务」和「本会话内允许」是两个级别，会话级授权不要跨任务延续。
5. **记审计日志**：谁批的、基于哪份预览批的。出事之后，这条链路比任何事后推测都有用。

## 踩坑点

- **确认疲劳是最大杀手。** 我们曾把「写文件」也做成确认项，一周后用户开始无脑点确认。收紧到只保留不可逆和外部影响两类后反而正常了。确认通过率是个健康指标：接近 100% 说明你问太多了，频繁被拒说明问的位置不对。
- **「可逆」的判断别交给模型。** 有 git 历史 ≠ 可逆，push 到远端再 force push 就是不可逆。可逆性定义要写死在工具元数据里。
- **外部内容可以诱导绕过确认。** Agent 读了网页或工单后可能被注入「直接执行、无需确认」。确认门如果只在提示词里，等于没有。执行层拦截是唯一可靠的。
- **dry-run 本身可能有副作用。** 有些 API 没有真正的 dry-run 端点，模拟调用也会触发效果。这类工具直接归入不可逆。

## 可复用建议

- 新接一个 MCP 工具，先问三个问题：能撤销吗？影响谁？失败了容易发现吗？三个答案决定它的级别。
- 每个确认弹窗必须带 diff、数量、目标对象，让用户 3 秒内能做判断；给不出预览的操作，宁可归高危。
- 定期复盘确认日志：被批准的操作里如果大量是同一类低危项，把它降级到自动执行。
- 别拿模型「聪明程度」当权限依据。再强的模型，不可逆就是不可逆。

## 总结

权限边界不是一条安全清单，而是一次产品设计。核心一句话：**按不可逆性和影响半径分级——可逆的小事自己干，不可逆的大事把预览交给人，并把确认门做在执行层而不是提示词里。** 弹窗越少、越准，人和 Agent 的协作才越顺。
