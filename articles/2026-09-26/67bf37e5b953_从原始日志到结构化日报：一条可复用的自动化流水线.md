## 背景

我们团队此前每天由值班同学手动翻日志写日报：从应用日志、CI 记录、工单系统各扒一遍，复制粘贴再拼一段总结，全程 40 分钟起步，且经常漏掉关键异常。这篇帖子分享我们用 OpenClaw 搭的一条自动化流水线，把这件事压到"每天早上自动出现在群里，人工只做抽检"。

## 问题

拆开看，手工日报有三个根因上的麻烦：

1. **数据散**：日志分散在四五个来源，格式互不相同；
2. **动作机械但易错**：统计数字靠人肉，抄错、漏抄是常态；
3. **总结有模板无信息**：大部分篇幅在复述"今天跑了多少任务"，真正有用的异常被淹没。

## 做法

流水线分五层，每层是独立脚本，中间结果全部落盘：

1. **采集层**：定时任务（cron 触发 OpenClaw 插件）拉取各来源日志，按日期归档到 `raw/YYYY-MM-DD/`。只负责搬运，不做解析。
2. **归一化层**：每个来源一个解析器，输出统一 JSON Schema：`{时间戳, 来源, 事件类型, 关键数值, 严重级别}`。无法解析的行进 `rejected.log`，不静默丢弃。
3. **聚合层**：纯脚本做确定性计算——任务总量、失败数、P95 耗时、Top 异常类型、环比变化。这一层没有 LLM，数字不允许出错。
4. **摘要层**：Agent 通过 MCP 工具读取聚合结果和异常样本（每类最多 5 条），按固定模板生成 Markdown 日报。Prompt 明确约束：只允许引用输入中的数字，缺失字段写"数据缺失"，不许编造。
5. **分发层**：推送 IM 群 webhook，同时归档进 Git 仓库，形成可 diff 的日报历史。分发前有校验脚本：抽取日报中出现的所有数字与聚合结果比对，不一致即拦截告警。

## 踩坑点

- **日志格式漂移**：上游改了一次字段名，流水线静默产出空日报，两天后才被发现。现在每层校验行数与非空率，低于阈值直接告警，不生成日报。
- **时区错位**：日志是 UTC，日报按本地时区切天，凌晨任务被算错日期。修复方式是采集层统一转带时区时间戳，切天逻辑全流水线只写一处。
- **LLM 编造数字**：早期把原始日志直接丢给模型"总结"，数字对不上是大概率事件。改成"数字预计算 + 分发前校验"后基本绝迹。
- **定时任务本身没监控**：cron 挂了没人知道。加了心跳通知，失败或超时即推送。
- **上下文超限**：别把全量日志喂给模型，只给聚合结果加抽样，token 消耗降一个量级，效果反而更稳。

## 可复用建议

- **Schema 先行**：先定稿日报最终字段，倒推每层需要什么数据，避免边做边改。
- **抽取与摘要分离**：确定性计算交给脚本，语言组织交给模型，边界清晰才能各自测试。
- **中间结果落盘**：出问题时逐层回放定位，而不是靠猜。
- **Prompt 当代码管**：进 Git、走 review，改动可追溯。
- **先灰度一周**：自动生成、人工审核后再发，比对无误再切全自动。

## 总结

这条流水线跑了一个多月，日报耗时从 40 分钟降到约 3 分钟（含人工抽检），更重要的是数字可核对、过程可回放、失败会告警。自动化日报的价值不在于"写得像人"，而在于整条链路可信。欢迎在评论区交流你们的日报结构与踩坑经验。
