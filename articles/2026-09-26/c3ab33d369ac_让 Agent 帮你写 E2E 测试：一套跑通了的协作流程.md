## 背景

E2E 测试一直是最难自动化的那块：写起来慢、维护成本高、还容易脆弱。多数团队只有一两个人愿意写，覆盖率长期追不上需求迭代。Agent 加上浏览器类 MCP 工具链成熟之后，"让 Agent 探索真实页面、生成测试代码"第一次变得实际可用。这篇记录我在实际项目里跑通的一套流程，核心思路一句话：**Agent 负责生成和修复，人负责业务判断**。

## 问题

手工写 E2E 的三个核心痛点：

1. **选择器脆弱**：页面一改版，`nth-child(3)` 这类定位全挂；
2. **流程靠人记忆**：登录过期、重复提交这类边界场景容易被漏；
3. **维护断档**：测试红了没人修，慢慢变成摆设。

这三件事恰好是 Agent 擅长的：探索、枚举场景、机械性修补。

## 做法

**第一步：先给 Agent 一份测试规约。** 包括：必须用 `data-testid` 定位、禁止依赖 CSS 层级、断言写什么（URL、可见文本、接口状态码）、命名规范。这份规约放仓库里，作为会话的前置上下文。这一步比任何 prompt 技巧都重要。

**第二步：让 Agent 通过浏览器 MCP 工具真实走一遍流程。** 关键是操作真实页面而不是凭空想象。它会边走边记录：每一步点了什么、页面状态如何变化，产出一条"操作轨迹"。

**第三步：生成 Playwright spec 并本地跑通。** 让 Agent 把轨迹转成测试代码，跑了失败就看报错自己改。建议限制迭代轮数（比如 3 轮），防止无限循环烧 token。

**第四步：人审 PR。** 重点审两件事：断言是否真的验证了业务结果（而不是只断言页面没报错）；有没有编造不存在的流程。

后续维护也交给 Agent：CI 挂了，把失败日志和截图丢回去，让它定位并提修复 PR，人只做确认。

## 踩坑点

- **选择器退化**：首次生成经常用文本定位或层级定位，改版即挂。规约必须强制 `data-testid`，且第一轮落地后人工补一遍。
- **"通过的假测试"**：Agent 很容易写出不断言任何东西、等页面加载完就 pass 的测试。要求每条测试至少一条业务断言，且断言对象在规约里列清楚。
- **测试数据污染**：Agent 默认会用真实环境造数据，跑几次环境就乱了。务必走独立测试环境并每次清理。
- **成本失控**：带浏览器循环调试很烧钱，长流程尤其明显。把流程拆短、每段单独生成，效果好很多。

## 可复用建议

1. 规约先行：50 行以内的测试规约文档，投产出比最高；
2. 把 `data-testid` 当作前后端与测试的共同契约，纳入 code review；
3. 小步提交：一次只让 Agent 生成一条流程，别一次铺开；
4. 失败回喂：CI 日志 + 截图 + 页面 HTML，是给 Agent 最好的排障上下文；
5. 保留人审：Agent 产出的是草稿，业务正确性判断永远在人这边。

## 总结

这套流程跑下来，我们的 E2E 覆盖从核心三条主流程扩到了十多条，写测试的时间成本降了一半以上。更重要的是维护模式变了：测试挂了不再没人管，Agent 出修复草稿，人只做确认。Agent 不是替代你写测试，而是接走了"写"和"修"这两件机械活，把"测什么、怎么算对"留给你。
