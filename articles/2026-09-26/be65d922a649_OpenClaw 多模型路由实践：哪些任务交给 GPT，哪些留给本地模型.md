## 背景

OpenClaw 默认只接一个主力模型，跑起来之后问题很快暴露：日常摘要、定时任务、MCP 工具调用，全都打到同一个旗舰模型上，一个月 token 账单不太好看；换成全本地（Ollama 跑 Qwen / Llama 系），成本归零，但 agent 的规划能力和工具调用成功率肉眼可见地下滑。多模型路由要解决的就是这个分配问题：把不同性质的任务，分给不同成本档位的模型。

## 问题

实际使用中有三类需求互相冲突：

- **隐私与成本**：日志摘要、笔记整理这类任务涉及私人数据且量大，走云端既贵又不放心；
- **质量底线**：多步规划、跨 MCP 工具编排的任务，本地小模型经常调用失败，返工成本比省下的钱高；
- **延迟**：交互式对话对首 token 敏感，后台批处理则完全不敏感。

## 做法

我的方案分四步：

**1. 先给任务定级。** 我把任务粗分三档：

- A 档：多步规划、工具编排、写代码 → 云端旗舰模型；
- B 档：单轮问答、摘要、翻译、格式转换 → 本地 7B~14B；
- C 档：embedding、分类打标、字段提取 → 本地小模型或专用接口。

**2. 配置主力 + 兜底。** OpenClaw 支持按 agent 覆盖模型，示例：

```json
{
  "agents": {
    "planner": { "model": "gpt-4o", "fallback": "ollama/qwen2.5:14b" },
    "digest":  { "model": "ollama/qwen2.5:14b", "fallback": "gpt-4o-mini" }
  }
}
```

注意兜底方向：A 档任务可以落本地做降级跑，B/C 档任务 fallback 上云保质量。

**3. 入口做轻量路由。** 在消息入口用本地小模型做一次意图分类（正则 + 关键词也够用），命中简单类目直接进本地，其余走云端。判断条件宁松勿紧——路由器判错一次，损失的是一整次调用。

**4. 记录路由日志。** 每次调用记下 agent、模型、token 数、是否触发 fallback。跑两周后回看，基本能发现哪些"以为必须用 GPT"的任务其实本地就能扛。

## 踩坑点

- **本地模型的 tool calling 是重灾区。** Qwen 系列相对可靠，但参数填错、JSON 带注释、多调一次工具仍是常态。凡是要碰 MCP 工具的任务，别路由给没实测过的模型。
- **上下文窗口不一致。** 云端 128k，本地可能只有 32k 甚至 8k，长会话切到本地会静默截断，agent 表现为"失忆"而不是报错。路由层要做长度检查。
- **fallback 要有熔断。** 本地服务挂掉时如果每次都等超时再切云端，体感延迟翻倍。我设了连续 2 次失败就临时摘除本地节点，靠定时探活恢复。
- **别拿 benchmark 当依据。** 榜单分数和你的真实任务分布关系不大。用自己的日志造一个 30~50 条的评测集，路由策略调整前后各跑一遍，比任何公开榜单都有说服力。

## 可复用建议

- 起步阶段全走云端，先拿到质量基线，再逐类任务降级到本地，每降一档观察一周；
- 给每个 agent 单独配模型而不是全局一个，OpenClaw 的插件化架构正好支持这个粒度；
- 成本敏感的后台任务（定时摘要、日志归档）是本地化收益最高的部分，优先迁移；
- 关键链路（涉及写操作、发消息、动配置的 agent）永远留在云端——这不是钱的问题，是失败代价的问题。

## 总结

多模型路由不是"能省则省"，而是给任务定级：把不确定性高、失败代价大的部分交给最强的模型，把确定性高、量大的部分下沉到本地。OpenClaw 的按 agent 覆盖加 fallback 机制已经把基础设施搭好了，剩下的是你自己的日志和判断。先测量，再迁移，路由表会随着使用越来越准。
