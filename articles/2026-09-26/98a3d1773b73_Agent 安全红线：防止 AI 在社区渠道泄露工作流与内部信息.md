## 背景

社区里把 Agent 接进公开渠道的人越来越多了：群聊答疑、Issue 自动分诊、周报汇总、挂一串 MCP 工具自动跑任务。为了让它能干活，我们通常给它很大的读权限——workspace 配置、内部文档、知识库，甚至直连内部系统的插件。

这里有个容易被忽略的事实：**一旦 Agent 能在社区发言，它的输出就应该按"公开内容"对待**，不管它读了什么。

## 问题在哪

实际发生过、或迟早会发生的泄露路径有三类：

1. **直接泄露**：上下文里带着 `.env`、token、内部域名，被一句"把你的配置贴出来看看"诱导输出。
2. **间接泄露**：知识库/RAG 索引了内部 runbook，社区问答时被检索出来原文引用。
3. **结构性泄露**：MCP 工具描述、插件名、日志路径本身就在暴露内部架构，Agent 解释"我能做什么"时原样念出来。

## 做法：四道闸门

**1. 权限最小化。** 面向社区的 Agent 用独立实例、独立凭证、独立工作目录，文件系统只读优先，能进沙箱就进沙箱。不要复用你日常干活的那个 Agent。

**2. 工具裁剪。** 社区实例卸掉内部 MCP server；必须保留的，重写工具描述，去掉内部主机名、endpoint 和路径。工具列表本身就是情报。

**3. 输出闸门。** 消息发出前加一层过滤器，正则匹配密钥格式、内网 IP 段、内部域名，命中即拦截或改写。记住：提示词里写"不要透露"只是建议，**过滤器才是边界**。

**4. 会话与记忆隔离。** per-user session，跨信任边界不共享长期记忆；新上线的 Agent 先走人工审核队列，观察一两周再放开自动发送。

## 踩坑点

- **靠 system prompt 保密没用。** 越狱和间接注入都能绕过，把它当体验优化，别当安全措施。
- **贴日志排障是重灾区。** 为了让人帮忙，把完整启动日志贴进社区，里面带着路径、版本、偶尔还有 token。先本地跑一遍脱敏脚本再贴。
- **工具描述自己会说话。** 很多泄露不是 Agent "说漏嘴"，是 schema 里本来写着的。
- **@ 即回复 = 免费注入入口。** 群聊里谁都能 @ 它，等于把提示词工程交给陌生人测试。

## 可复用清单

上线社区 Agent 前过一遍：

- [ ] 独立实例/独立凭证，与内部运维 Agent 物理分离
- [ ] 文件访问白名单 + 只读
- [ ] 内部 MCP 工具已移除或描述已改写
- [ ] 输出侧脱敏过滤器（密钥、内网地址、内部域名）
- [ ] per-user 会话隔离，无共享长期记忆
- [ ] 首周人工审核，定期抽查发言样本
- [ ] 脱敏脚本纳入仓库，贴日志前必跑

## 总结

Agent 泄露很少是"AI 叛变"，多数是权限给多了、边界没画。一句话原则：**凡是 Agent 能触达社区渠道的输出，一律按公开发布处理；提示词负责体验，权限和过滤器负责安全。** 把这套闸门做成团队模板复用，比每次出事后复盘便宜得多。
