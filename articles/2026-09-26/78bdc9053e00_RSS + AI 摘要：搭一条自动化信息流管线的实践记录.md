## 背景

信息获取的老问题：源太多、质量参差、没时间读。RSS 虽然老，但仍是唯一完全可控的订阅协议——没有算法干预、可以自建、输出是结构化数据。配上 AI 摘要，可以把"每天扫 200 条"压缩成"读 20 条摘要 + 精读 3 条"。这篇记录我在 OpenClaw 里搭的一条管线，跑了两周多，够稳定，值得沉淀成模板。

## 问题定义

要解决的不是"能不能抓 RSS"（工具一大堆），而是四个具体问题：

1. 无 RSS 的站点怎么覆盖；
2. 抓回来多是标题和截断摘要，不能直接喂模型；
3. 摘要本身不能变成新噪音——去重、分级、聚合节奏都要管；
4. Token 成本可控。

## 做法

整体四段式：**抓取 → 清洗 → 摘要 → 投递**。

**1. 源管理。** 源列表放一个 YAML 文件，每条含 url、分类、抓取频率。没有 RSS 的站点用 RSSHub 补齐，自建实例比公共实例稳定得多。

**2. 抓取与状态。** 用 OpenClaw 的 cron 定时任务每 2 小时跑一次抓取脚本，feedparser 解析。条目指纹取 `link` 归一化后的哈希（别用 title，很多源标题会微调），已处理 ID 存 SQLite。幂等是整条管线不崩的底线。抓取也可以包成小 MCP 工具让 agent 按需调用，但定时批处理场景直接跑脚本更省事。

**3. 正文补全。** 多数源只有 summary，先判断截断比例，超过阈值就走 readability 提取全文，带 3 秒超时和单次重试；失败的条目标记后跳过，不阻塞批次。

**4. 两级摘要。** 这是省成本的关键。第一级用便宜模型对标题+摘要做批量分诊，输出 JSON：`{score, tags, reason}`，低于阈值的直接归档；第二级只对高分条目做全文摘要，prompt 强制"只基于原文，不确定就写不确定"，并附原文链接。

**5. 投递。** 按分类聚合成日报，通过 OpenClaw 消息通道推到 IM；原文全文存档到本地，摘要只是索引。

## 踩坑点

- **guid 不可信。** 有源换 guid 但 link 不变，有源反过来。指纹用 link 哈希最稳。
- **编码与 CDATA。** 少数老站是 GBK，feedparser 一般能兜住，自己手写解析必翻车，别手写。
- **摘要幻觉。** 模型会把推测包装成结论。约束输出结构、要求贴合原文后，幻觉明显减少；数字、日期一律让它照抄。
- **cron 重叠。** 抓取慢于间隔时会并发跑两份，加文件锁或用 SQLite 事务锁。
- **别全量深摘要。** 最初对所有条目跑大模型，一天成本不小；改成两级分诊后降了一个数量级。

## 可复用建议

- 每一步落状态、可重放；LLM 调用前后写日志，出问题能定位到单条。
- 源配置、阈值、prompt 全部外置，换模型不动代码。
- 结构化输出用 JSON schema 约束，解析失败重试一次，再失败进死信队列人工看。
- 先跑一周"只记录不投递"，校准重要性阈值后再上线推送。

## 总结

这条管线没有黑科技：RSS 解决"拿到什么"，状态存储解决"不重复"，两级模型解决"花多少钱"，结构化输出解决"可不可信"。OpenClaw 在这里的价值是把 cron、工具调用和消息投递捏在一个 agent 里，省掉了大量胶水代码。两小时一次、日均百条量级，单日成本可以压得很低。后续打算加语义去重（多源转载同一篇的合并），那是下一个迭代的事。
