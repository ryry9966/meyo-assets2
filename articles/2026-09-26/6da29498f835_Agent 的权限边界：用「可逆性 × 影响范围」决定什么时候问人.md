## 背景

Agent 接上 MCP 工具和插件之后，就从「能聊」变成了「能动手」：跑 shell、写文件、调内部 API、发消息。OpenClaw 这类框架让接工具变得足够容易，但同时也把一个问题推到每个团队面前——哪些动作 agent 可以直接执行，哪些必须停下来问人。

## 问题

实践中常见两种失败方向：

- **问得太勤**：每一步都确认，人很快退化成「无脑点同意」的橡皮图章，自动化价值归零。
- **问得太少**：一条 `rm`、一次对外发布、一笔扣款，模型一次「很自信」的调用就能造成不可逆损失。

好的边界不是「多问」或「少问」，而是让每一次询问都值得认真读。

## 做法：两个维度切四级

用**可逆性**（能否撤回）和**影响范围**（炸的是自己还是别人）给所有工具动作分级：

- **L0 只读**：查询、检索、dry-run。直接放行，不问。
- **L1 可逆写**：工作区内写文件、改草稿、幂等的内部接口。放行，但全量记审计日志。
- **L2 外部副作用**：发消息、发邮件、部署、对外发布、花钱。必须问，并展示「将发生什么」的具体参数。
- **L3 不可逆高危**：删数据、改生产配置、支付。默认拒绝，或走「计划级审批」。

三个配套机制：

1. **计划级审批**。让 agent 先输出带参数和影响说明的动作清单，人对计划签一次字；执行中只对计划外偏差二次询问。比逐步确认少 80% 的打扰。
2. **环境感知**。同一动作在 dev 自动放行，在 prod 必问。把环境作为策略输入，别指望 prompt 里一句「小心点」。
3. **默认中止**。人未回复时，fallback 是放弃而不是继续。这条要写进代码，不写进 prompt。

补充一句 MCP 相关的：`readOnlyHint` 这类工具注解可以做初始分级，但它是提示不是保证，真正的拦截要在网关/执行层落地。

## 踩坑点

- **事后通知 ≠ 审批**。消息已经发出去再「告诉你」，那是报丧不是边界。副作用发生前拦截才算数。
- **确认框没信息量**。「确定继续吗？」没人会认真看。要给 diff：目标、参数、影响范围、回滚方式。
- **安全链里藏不可逆步骤**。典型如「备份脚本」顺手 prune 了旧数据——一个隐形 L3 混进了 L1。
- **审批疲劳是策略问题**。如果确认率长期 90%+ 且没人真读，说明 L2 划得太宽，应该聚合成计划级审批。
- **权限漂移**。调试期顺手放开的权限，上线后忘了收。策略要跟部署走，不跟会话走。

## 可复用建议

- 给每个工具/插件写一张三列表：**动作、级别、默认策略**，进仓库、过评审，和代码一起演进。
- **从最严开始**，靠审计日志逐步放宽；反过来做（先宽松再收紧）一定会先出事故。
- 所有不可逆动作必须落一条**含完整参数、可回放**的日志。
- 定期红队自己：故意丢给 agent 一个「看起来合理但会删库」的任务，验证边界真的拦得住。

## 总结

权限边界本质是产品决策加工程护栏，不是 prompt 措辞问题。可逆且影响小的自己干，不可逆或影响别人的必须问——而且问在计划层，不问在步骤层。先严格后放宽，让审计日志而不是直觉驱动策略迭代。
