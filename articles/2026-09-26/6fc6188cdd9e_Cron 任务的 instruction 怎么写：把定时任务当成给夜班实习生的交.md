## 背景

OpenClaw 的 cron 任务本质上是一件事：到点把一个无状态的 agent 叫醒，塞给它一段 instruction，让它独自跑完、交付结果、再睡回去。没有上下文历史，没有可以追问的人，也没有第二次机会。很多人把聊天里随手写的 prompt 直接搬进 cron，结果时好时坏——不是模型不稳，是 instruction 没把"无人值守"这个前提写进去。

## 问题的本质

交互场景下 agent 缺什么可以问，cron 场景下只能猜。绝大多数踩坑同源：**instruction 假设了它没交代的东西**。典型表现：

- "整理一下最近的新闻"——凌晨两点触发时，"最近"指什么？
- 工具拉取失败，模型出于好意编了一份摘要；
- 上次发过哪些条目完全不知道，隔天重复推送。

## 做法：写一份"值班交接单"

我把 cron instruction 当成交接单来写，结构固定，直接给一个可套用的骨架（以每日 RSS 摘要为例）：

```
任务：每天 08:00 生成昨日 RSS 摘要。
时间基准：以本次触发时间为准；"昨日"= 触发日的前一个自然日（Asia/Shanghai）。
数据来源：调用 rss_reader 工具读取 feeds.json 中的订阅列表。
容错：工具失败或条目为空时，原样发送"今日无更新"，禁止推测或补写。
输出：不超过 300 字，按重要/一般分组，附原文链接，发送到 #daily 频道。
去重：读 state/processed.json 跳过已发送条目，发送成功后追加写入。
```

对应六个必答题：

1. **做什么**：一句话说清目标，不给 agent 自由发挥的空间。
2. **时间基准**：所有相对时间词显式换算成触发时间锚点加时区。
3. **数据来源**：用哪个工具、读哪个文件，路径和工具名写死。
4. **容错**：失败时做什么、不做什么，"禁止编造"要写成显式禁令。
5. **输出契约**：格式、长度、语言、投递目的地，全部落成可判定条件。
6. **状态去重**：跨次运行的状态外置到文件，instruction 里写明读写路径。

## 踩坑点

- **留判断题给 agent**。"觉得值得发就发"这类指令会让行为逐次漂移，要么给量化标准（如条目数超过 3 才发），要么删掉这个判断。
- **依赖记忆**。每次触发都是全新会话，"接着上次的继续"这种说法必然失效。
- **契约被埋没**。前面铺垫太多背景，模型到最后反而忘了往哪发、发多少。输出契约放在显眼位置，或加一句"以上字段为硬性要求"。
- **一上来就高频**。先手动触发验证，再挂每小时，稳定后再降频，别让调试期刷屏正式频道。

## 可复用建议

- instruction 存成独立文件进版本库，改动走 commit，出问题可回滚 diff。
- 给每个任务配一条测试投递通道，先跑通再切正式目的地。
- 失败路径至少写一行：发告警还是静默跳过，二选一，不留空白。
- 定期翻 cron 的历史输出，instruction 的退化通常是渐进的，肉眼翻比事后排查便宜。

## 总结

Cron instruction 不是聊天 prompt，而是一份小型程序规格说明：目标、时间锚点、数据来源、容错、输出契约、状态管理，一个不能省。检验标准很简单——把它交给一个独自上夜班、没人可问、不敢编数据的实习生，他能否只靠这页纸把活干对。能，这条 cron 才算写完了。
