## 背景

Agent 上了生产，最大的不稳定因素往往不是模型本身，而是它依赖的一堆外部 API：LLM 供应商、搜索、数据库、各类 MCP 工具。传统应用里接口挂了会抛异常、报 500；但 Agent 的调用链是"模型 → 工具 → 模型"的循环，一次失败处理不好，轻则任务中断，重则模型自己编一个结果交差。

## 问题

实际跑下来，常见故障形态有三类：

1. **瞬时故障**：超时、502、限流，过几秒就恢复；
2. **持续性故障**：配额耗尽、鉴权失效，重试也没用；
3. **半完成任务**：五步流程在第三步断掉，状态丢失或残留脏数据。

最麻烦的是第二类被当成第一类无限重试——token 烧光了，任务还在原地打转。

## 做法

我们在 OpenClaw 插件层沉淀了一套做法，核心原则是：**重试交给确定性代码，Agent 只负责策略和沟通**。

**第一步：错误结构化。** 工具不要把原始堆栈丢给模型。统一返回 `{ok, error_code, retryable, hint}` 这类结构，模型看到的是 "API_TIMEOUT, retryable=true"，而不是三页 traceback——后者只会诱导它胡编解释。

**第二步：分层重试。** 在工具包装层做指数退避加抖动，比如 3 次、1s/2s/4s，只对超时和 5xx 重试；429 要读 Retry-After；401/400 直接判死。这些逻辑写在代码里，别让模型在对话循环里自己决定"再试一次"——它会在烧完预算前一直试。

**第三步：降级路径。** 每个工具声明 required 或 optional。可选步骤失败就跳过并在结果里标注；有缓存的上游可以回旧数据，但必须带"数据为 N 分钟前"的标记。降级可以，静默降级不行。

**第四步：熔断。** 插件层记录滑动窗口内的失败率，连续失败 N 次就把该工具标记为不健康，冷却期内 Agent 不再调用，直接向用户报告或切换方案。

**第五步：断点续跑。** 多步任务每完成一步就持久化状态，恢复时从断点继续，避免整个流程重跑。

## 踩坑点

- **非幂等操作重试**：创建工单、发消息这类 POST，盲目重试会重复执行。要么服务端支持幂等键，要么重试前落一条本地去重记录。
- **无抖动的重试**：多个 Agent 同时恢复会形成惊群，把刚喘过气的上游再次打挂。
- **把降级结果当正常结果**：用户基于过期数据做了决策，比任务失败更糟。
- **模型看到堆栈**：它会礼貌道歉然后继续编。给模型的错误信息要短、要可执行。

## 可复用建议

1. 写一个统一的 tool-call 中间件：超时、重试、熔断、日志、错误归一化都收在这一层，所有 MCP 工具共享。
2. 把故障当测试用例：staging 里 mock 一个必超时的接口，观察 Agent 行为是否符合预期，比线上出事再补逻辑便宜得多。
3. 给每个不稳定的上游维护一条 runbook：已知故障模式、恢复特征、升级渠道。

## 总结

外部 API 挂掉不是异常路径，而是 Agent 的日常。判断一个 Agent 是否可靠，看的不是它顺的时候跑多快，而是断的时候怎么表现：响亮地失败、诚实地降级、干净地恢复。把这三件事做进基础设施，Agent 才敢交给别人用。
