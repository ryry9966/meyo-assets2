## 背景

E2E 测试是很多团队"都知道该写、但一直没写"的部分：搭环境、挑定位器、处理等待与 Mock，单条用例的成本比单元测试高一个量级。Agent + MCP 把这件事的经济性改变了——模型可以读代码、开浏览器、跑测试、读失败日志。但实践下来会发现，"让 AI 一句话生成测试"和"让 AI 协作写测试"完全是两回事。这篇帖分享一套在 Agent 工作流里跑通的做法。

## 问题：为什么"一次性生成"不可用

直接把 URL 和需求丢给模型，产出通常有三类问题：

- **定位器是编的**：`getByText('提交')` 实际渲染成了 aria-label，一跑就挂；
- **没有断言**：打开页面、截个图、通过。测试是绿的，但什么都没验证；
- **脆弱等待**：依赖 sleep 或 networkidle，本地能过，CI 里随机挂。

根因只有一个：模型没跑过测试，它写的是"看起来像测试的代码"。解法不是更精妙的 prompt，而是把执行结果喂回给它。

## 做法：闭环驱动

**第一步：给 Agent 装上手和眼。** 通过 MCP 接三类工具：文件系统（读代码与现有测试规范）、Playwright 浏览器（真实打开应用、抓取可达性树）、测试执行（运行命令并返回 stdout 与 trace 路径）。

**第二步：先让它"用"，再让它"测"。** 要求 Agent 先用浏览器工具手工走一遍核心用户路径，记录真实的 role、label、接口时序。产出不是测试代码，而是"场景清单"——人工先审清单，确认覆盖登录、核心操作、异常分支。

**第三步：逐条生成，逐条运行。** 每次只写一条用例，写完立刻执行；失败就把报错和 trace 截图发回给 Agent 修复。限制最多 3 轮迭代，修不好就标记下来转人工。

**第四步：固化规范。** 把定位器优先级、等待策略、断言要求写进仓库的测试规范文档，让 Agent 每次开工前读。相当于把 code review 标准前移成 prompt 资产。最小约束示例：

```text
- 断言必须针对用户可见结果，禁止只断言 URL
- 禁止 sleep，统一用 expect(...).toBeVisible()
- 单条用例失败必须附带 trace 文件路径
```

## 踩坑点

- **一次生成十条再统一跑**：失败日志混在一起，Agent 修复准确率明显下降。小步提交在这里同样成立。
- **重试掩盖问题**：Playwright 的 retry 会让 flaky 用例"看起来稳定"。建议先关 retry 跑一遍，把真实的不稳定暴露出来，再区分环境问题和竞态。
- **给 Agent 生产凭据**：只给测试环境账号和 seed 数据，并在 MCP 工具层做白名单，而不是靠 prompt 里写"不要碰生产环境"。
- **无人审的绿**：Agent 很擅长把测试改到通过，包括把断言改弱。review 时重点看 diff 里的断言，而不是只看 CI 颜色。

## 可复用建议

- 把 `run_tests` / `read_trace` / `screenshot` 做成三个独立 MCP 工具，比一个万能 shell 更安全、更好排障；
- 仓库里维护一份"测试规范"文档，它同时是给人看的文档和给 Agent 的上下文；
- 选一条高价值流程（登录 → 核心动作 → 结果可见）试点两周，再横向扩展；
- 把 flaky 率当指标看，周环比上升就回到用例层排查，而不是调超时。

## 总结

Agent 没有消灭 E2E 测试的人力成本，只是把它从"编写"挪到了"审查与维护"。真正让 AI 产出可用测试的，是"写—跑—读日志—修"的执行闭环，加上人在断言与场景两个环节的最终决定权。这套流程不绑定特定框架，Playwright、Cypress 都能套用。欢迎在社区贴出你们的 MCP 工具配置和踩坑记录。
