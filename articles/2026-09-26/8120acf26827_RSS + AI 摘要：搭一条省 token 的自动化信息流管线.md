## 背景

信息源越来越散，算法推荐又不可控。RSS 虽老，但它是唯一能"只订阅、不被投喂"的开放协议。真正的问题是：订阅一多就读不过来，而直接把全文丢给 LLM，又贵又容易跑偏。这篇记录我在 OpenClaw 里搭的一条管线：定时抓 RSS → 清洗去重 → 分层摘要 → 推送 IM，日均成本基本可以忽略。

## 问题定义

动手前先明确三条硬约束：

1. 很多 RSS 只有首段，抓不到全文的摘要不如不做；
2. token 成本可控，不能每天把几十个 feed 的全文塞给模型；
3. 摘要必须可追溯到原文，模型不许编。

## 做法

**第一层：采集。** 用 Miniflux 或 FreshRSS 做聚合，没有 RSS 的站点用 RSSHub 补路由。开启 full-text 抓取（如 Miniflux 的 scraper），或在管线里自己用 readability 类库抽正文。统一产出 `{guid, url, title, published, text}`。

**第二层：清洗与去重。** 这是整条管线性价比最高的一步：

- 按 guid/url hash 维护一个 `seen.json` 状态文件，天然幂等，重跑不重复推送；
- 标题做归一化后的相似度比较（分词 Jaccard 够用），同一件事多家报道只留信源评分最高的一条；
- 正文截断：每条取前 3000 字符，足够摘要使用。

**第三层：分层摘要。** 不要把整个 feed 当一个 prompt 发，用 map-reduce：

- map：每条文章单独调用一次，输出结构化 JSON——`{一句话, 关键点[], 是否深读}`；
- reduce：把当日所有一句话合并生成日报，自然带链接。

在 OpenClaw 里封装成一个工具 / MCP server，注册 `summarize_item` 和 `digest_day` 两个 action，定时任务触发，跑完走 webhook 推到 Telegram 或飞书。Prompt 里的关键约束，可直接复用：

> 只基于给定文本总结，不得补充外部信息；文本为空或无法理解时返回 skip；关键点最多 3 条，每条不超过 25 字。

**第四层：推送。** 日报按分类分组，超长分段，每条附原文链接。

## 踩坑点

- **抓不到全文**：大量官方 feed 只给摘要。scraper 能解决大半，剩下 JS 渲染页需要 headless，我选择直接放弃这类源——信源质量 > 覆盖面。
- **重复推送**：有些 feed 会改 pubDate，按时间判断会重发。务必以 guid 为准，状态文件落盘。
- **模型编造**：早期日报里出现过原文没有的数字。加上"只基于文本 + 空内容返回 skip"后消失。评估别靠感觉，每周抽 10 条对照原文人工看。
- **token 失控**：第一版整 feed 一个 prompt，长 feed 直接超限。改成逐条 map 后成本降一个量级，还顺手解决了单条重试。
- **RSSHub 路由不稳**：自建实例 + 定期更新镜像，挂掉的路由要有告警，别让静默失败吃掉信息源。

## 可复用建议

1. 先用脚本 + JSON 状态文件跑通，别上来就上队列和工作流引擎；
2. 采集与摘要拆成可独立重跑的两个阶段；
3. 摘要输出永远是结构化 JSON，渲染层自己控制；
4. 记录每次运行的 token 消耗，成本可见才能优化；
5. 信源定期做减法：连续一周"深读"标记为零的源，退订。

## 总结

管线跑了一个多月，日均处理 200+ 条目，产出一份 10 条以内的日报，5 分钟读完。最大的体感不是省时间，而是信息重新可控了：RSS 负责稳定供给，清洗层负责降噪，AI 只做最后一步压缩。AI 摘要的上限取决于上游清洗质量——所以整篇里最值得抄的是去重和截断那几行，而不是 prompt。
