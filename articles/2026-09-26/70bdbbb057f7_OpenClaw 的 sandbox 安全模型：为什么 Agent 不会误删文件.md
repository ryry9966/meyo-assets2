## 背景

给 Agent 接上 shell 和文件系统工具之后，第一个真实的问题不是"它能不能干活"，而是"它会不会把不该动的东西动了"。社区里出现过不止一次类似事故：Agent 在重构过程中执行一条清理命令，把 workspace 之外的用户配置一并带走。OpenClaw 的 sandbox 安全模型就是围绕这类事故设计的，核心目标只有一个：让"误删"在结构上不可能发生，而不是靠 prompt 里写一句"请小心"。

## 问题：删除事故的四条真实路径

复盘这些案例，误删几乎都不是 Agent"发疯"，而是四条很普通的工程路径：

1. **路径解析偏差**：Agent 拼接相对路径，实际 cwd 和它认为的不一致；
2. **软链接逃逸**：workspace 里有一条指向家目录的 symlink，顺着写就出去了；
3. **通配符失控**：`rm -rf build/*` 在错误的目录下展开；
4. **工具封装被绕过**：Agent 用 shell 调脚本，脚本内部做了文件操作，工具层的检查根本没经过。

## 做法：四层防御

**第一层：workspace jail（文件系统层）**。所有文件工具绑定到一个 workspace root，任何路径访问前先做 `realpath` 解析，解析结果必须仍落在 root 之内，否则直接拒绝。这一层同时堵住 symlink 逃逸和 `../` 回溯。

**第二层：能力声明（工具层）**。每个 MCP 工具注册时声明能力范围：read-only、workspace-write、host-write。host-write 默认关闭，开启时必须在配置里显式列出允许的宿主目录，白名单之外一律拒绝。

**第三层：执行层策略检查**。这是最容易被忽略、也最关键的一层。shell 命令执行前，policy engine 解析命令行，识别删除、递归、通配符指向等危险模式：目标路径越出 jail 直接拦截；批量删除先转 dry-run，输出影响文件清单等待确认。因为检查在执行层，无论走原生工具还是绕道脚本，都会经过同一道闸门。

**第四层：回收站与审计**。沙箱内的删除默认进 trash 目录，保留期内可恢复；所有写入与删除操作落审计日志，事后能回答"它到底动了什么"。

## 踩坑点

- **cwd 漂移**：Agent 执行 `cd` 后，后续相对路径必须基于新 cwd 重新 resolve。早期版本在这里漏过一次，靠第三层兜底才暴露。
- **挂载过宽**：图省事把整个 `$HOME` bind 进 sandbox，第二、三层瞬间形同虚设。挂载粒度决定安全上限。
- **确认疲劳**：每个写操作都弹确认，用户会训练成无脑 yes。只对不可逆操作（真删除、越界写）设确认，常规写放行。
- **自然语言确认不可靠**：Agent 回一句"好的我确认"不算确认，OpenClaw 要求工具调用的结构化确认结果，否则视为未授权。

## 可复用建议

1. 默认最小挂载，按需扩白名单，扩之前先想清楚越界后果；
2. 删除一律走 trash，不要直连 `unlink`；
3. 策略检查放执行层，工具层封装只当第一道筛子，不当最后防线；
4. 放一个"金丝雀文件"在 jail 外，定期跑 Agent 任务验证它真的出不去；
5. 越界尝试即使被拦截也应触发告警——被挡住的攻击也是信号。

## 总结

Agent 的安全性不来自它"聪明到不会犯错"，而来自系统设计让错误的代价可控。OpenClaw sandbox 模型的本质，是把信任边界从 prompt 下沉到文件系统和执行层，让越界操作在结构上失败。四层各自都不复杂，组合起来才能让"误删"从偶发事故变成不可能事件。
