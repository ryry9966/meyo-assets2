## 背景

OpenClaw 的 Agent 默认具备执行能力：读写文件、跑命令、调 MCP 工具。能力越大，误操作的代价越高。社区里最常被问的一个问题是：让 Agent 直接碰文件系统，它会不会某天顺手把 `~/projects` 给 `rm -rf` 了？

答案是在默认配置下，这件事在架构上就很难发生。不是因为模型“很听话”，而是 OpenClaw 的 sandbox 模型把删除路径拆成了几层，任何一层都会把事故拦下来。

## 问题：误删是怎么发生的

复盘真实的 Agent 事故，误删几乎都不是模型主动作恶，而是三条路径：

1. Agent 在宿主机上下文里直接执行 shell，`rm` 的相对路径解析出错；
2. 工具参数路径逃逸：`../../` 拼接，或软链接指向工作区之外；
3. 提示注入诱导 Agent 执行“看起来合理”的清理命令。

所以安全模型要解决的不是“让模型更谨慎”，而是反过来假设：模型一定会犯错、一定会被注入，然后让单点错误无法穿透到宿主数据。

## 做法：四层防线

**第一层：容器边界。** 配置 `sandbox.mode: all` 后，Agent 的所有执行（包括 shell 和文件工具）都发生在隔离容器里，宿主机文件系统对它不可见。容器里没有你的照片库、没有 SSH 私钥，删除无从谈起。

**第二层：工作区收敛。** 宿主机只有 workspace 目录以 bind mount 方式进入容器，且 OpenClaw 对所有文件工具的入参做规范化：解析 `..`、追踪软链接、拒绝 workspace 根之外的路径。即使模型拼出了 `/etc/passwd`，工具层直接拒绝。

**第三层：工具策略。** 危险操作走 deny 优先的规则表。默认策略下，跨出工作区的删除、递归删除、覆盖式写入会被拦截，或降级为“移入回收站目录”而非真删。MCP 工具同理，scope 没声明的操作在网关处就被拒。

**第四层：审批门 + 审计。** 策略判定为高危的操作升级为人审，在消息通道里弹确认；同时每次文件操作落审计日志，出问题可以回放定位。

## 踩坑点

- **把 Docker socket 挂进 sandbox**：等于把宿主机 root 交出去，是最常见的自毁配置。
- **bind mount 范围过大**：图省事挂 `/home` 甚至 `/`，第二层防线直接作废。
- **workspace 里的软链接**：指向工作区外的软链接可能被部分工具解析，升级 OpenClaw 后建议重跑一遍路径逃逸测试。
- **为省事全局关审批**：审批门只在策略判定高危时触发，频率很低，关掉它省不了多少事，风险却指数级上升。
- **MCP 工具 scope 过宽**：第三方 MCP server 声明了整个 home 目录读写，网关再严也拦不住“合法作恶”。

## 可复用建议

1. **最小暴露面**：一个 Agent 一个 workspace，按项目隔离，不共享目录。
2. **金丝雀文件测试**：在工作区内、外各放一个标记文件，跑一轮典型任务，确认不该动的真没被动。
3. **deny 优先**：规则表先写拒绝项，再写放行项，默认拒绝。
4. **审计驱动调优**：定期看审计日志，把高频拦截项沉淀成显式规则，而不是一刀切放宽策略。
5. **把 MCP 当不可信第三方**：逐个审查工具 scope，宁窄勿宽。

## 总结

OpenClaw 防误删的思路不是“信任模型”，而是分层假设失效：容器保证看不到，挂载保证够不着，工具策略保证进不去，审批和审计兜底。模型会犯错是常态，架构的意义是让每一个错误都停在可以恢复的那一层。
