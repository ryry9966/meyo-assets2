## 背景

E2E 测试是最有价值、也最没人愿意写的测试。单元测试写起来快，E2E 要搭环境、造数据、等渲染，一条下单主路径的用例动辄上百行。多数项目的现状是：核心路径留着一两条镇宅用例，其余靠手工回归。

OpenClaw 生态里大家已经在用 Agent 做各类自动化，浏览器侧有 Playwright MCP 这类工具，让 Agent 参与测试生成是顺势的事。但直接丢一句「给这个站点写 E2E」，产出基本不可用。这篇记录我们在两个前端项目里跑了一个多月的协作流水线。

## 问题

让单个 Agent 直接写 E2E，典型翻车有三种：

1. **自证式断言**：点完按钮就断言「按钮可见」，测试永远绿，什么都没验证。
2. **脆弱定位**：满屏 `nth-child(3)` 和绝对路径 XPath，页面改个布局全红。
3. **硬等待**：到处 `waitForTimeout(3000)`，CI 上忽快忽慢，flaky 率飙升。

根因是 Agent 只看得到当前页面快照，分不清哪些行为是「契约」、哪些是「实现细节」。这需要人来定义——或者更准确地说，需要被写进规则里。

## 做法

拆成三个角色的流水线（同一个模型扮演不同角色即可，关键是上下文隔离）：

1. **探索者**：通过 Playwright MCP 打开应用，按 `flows.yaml` 里声明的关键路径逐条走查，记录每步的 DOM 结构、网络请求和跳转结果。
2. **作者**：拿到探索者的结构化记录 + 团队测试规范（AGENTS.md 里写死：只用 data-testid 定位、断言网络响应和最终业务状态、禁止硬等待），生成 Playwright 用例。
3. **审查者**：只读代码不看页面，检查断言密度、是否有自证断言、是否覆盖失败分支。不达标打回重写。

`flows.yaml` 由人维护，十行以内，只回答一个问题——「什么流程必须永远工作」：

```yaml
flows:
  - name: 登录到下单主路径
    steps: [login, search, add_to_cart, checkout]
  - name: 支付失败提示
    steps: [login, checkout_declined_card]
```

生成后跑 headless，失败时把 trace 截图喂回作者 Agent。这里有条铁律：**Agent 只许修定位器和等待逻辑，不许改断言**。断言一改就成了「测试迁就代码」，回归形同虚设，这类改动必须走人工 PR 评审。

## 踩坑点

- **DOM 快照很大**：探索者走一个流程吃掉几十万 token 很正常。限定每步只取可交互元素和关键区域，能砍掉 80%。
- **测试数据失控**：别让 Agent 连共享环境造数据，给它专用沙箱账号 + 跑完即清理的 hook，否则脏数据越积越多。
- **自愈要有边界**：只自愈选择器；断言发生变化一律报警，而不是自动通过。
- **产物要当正式代码**：进仓库、进 CI、进 code review，别堆在临时目录里自生自灭。

## 可复用建议

- 先手写一条黄金用例作为 few-shot 范例，比任何 prompt 描述都管用。
- 在 AGENTS.md 里固化三条规范：定位器约定、断言标准、等待策略，所有 Agent 角色共享同一份。
- 用指标验收生成质量：断言数/用例数、flaky 率、失败后的自动修复成功率——而不是「生成了多少行」。

## 总结

Agent 擅长的是 E2E 里最枯燥的 70%：样板代码、定位器、等待逻辑、把人工操作翻译成脚本。而「什么算对」仍然得由工程师定义——`flows.yaml` 和测试规范就是那个定义。把人和 Agent 的分工卡在这里，生成的测试才能真正进 CI，而不是变成一堆永远绿着的摆设。
