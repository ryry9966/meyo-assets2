## 背景

写 Agent 或 MCP 工具链的人迟早会撞上同一件事：跑得好好的自动化流程，某天因为一个上游 API 超时、限流或宕机，整条链路要么原地报错，要么更糟——模型开始"脑补"缺失的数据继续往下走。单体脚本时代，API 挂了抛个异常就完了；但在 Agent 场景里，错误会被模型消化，**错误的处理方式比错误本身影响更大**。

## 三种典型死法

实际观察下来，Agent 面对外部依赖失败的反应大概三种：

1. **无限重试**：同一个工具调用循环几十次，token 烧完，任务超时。
2. **幻觉兜底**：工具返回空，模型基于训练数据"猜"一个结果填进去，下游全错，还很难发现。
3. **整体崩溃**：一个非关键工具（比如日志上报）挂了，拖死核心流程。

## 做法：五道防线

**第一道：错误分类。** 重试前先分清 429/5xx/timeout 这类可重试错误，和 400/401/404 这类不可重试错误。后者重试一百次也一样，只会浪费配额。封装一层统一的错误契约：

```json
{ "ok": false, "code": "RATE_LIMITED", "retryable": true, "hint": "retry_after_30s" }
```

**第二道：指数退避 + 抖动。** 1s → 2s → 4s，加随机抖动，设硬上限（3~5 次）。没有 jitter 的固定间隔重试，在多 worker 场景会形成惊群。

**第三道：熔断与降级。** 连续失败 N 次后把该工具标记为 degraded，一段时间内快速失败，不真发请求。同时准备降级路径：备用供应商、带时间戳标记的缓存结果、或"跳过该能力继续执行"。降级不等于假装成功。

**第四道：把"挂了"如实写进上下文。** 这是最容易被忽略的一步。不要吞掉错误让模型自由发挥，而是注入结构化失败信息：「搜索工具当前不可用，预计 5 分钟恢复，任务改为基于已有资料完成」。模型拿到明确约束后通常能给出合理的替代方案；拿到含糊的空结果，它就会编。

**第五道：检查点。** 长流程在每步工具调用后落盘中间状态，恢复时从断点续跑，而不是从头再来——这直接决定一次故障的成本是一步重试还是整单重来。

## 踩坑点

- **非幂等操作盲目重试**：下单、发消息这类操作重试等于重复执行。要么上游支持幂等键，要么重试前查一次状态。
- **熔断状态不共享**：多实例部署各自计数，熔断形同虚设。计数放 Redis 或集中配置。
- **备用服务 schema 不一致**：fallback 返回字段名不同，下游静默出错。降级链路也要做契约测试。
- **子超时大于总预算**：单工具超时 60s，Agent 整体预算 90s，连挂两个就死。子超时必须小于总预算。

## 可复用建议

- 所有 MCP 工具走同一个错误契约，编排层只认这个格式。
- 重试策略配置化，按工具粒度覆盖默认值。
- 结构化日志带 trace_id，故障复盘时能还原整条调用链。
- 上线前做故障演练：手动断掉某个依赖，看 Agent 是优雅降级还是当场表演幻觉。

## 总结

API 挂掉不是异常，是日常。错误恢复的目标不是"永不失败"，而是失败得可预期、低成本、且对模型和人都诚实。先分类、再退避、会熔断、敢降级、能续跑——这五件事做到了，Agent 的可靠性会上一个台阶。
