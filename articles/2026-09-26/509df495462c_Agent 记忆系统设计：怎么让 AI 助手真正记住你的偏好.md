## 背景

Agent 天然无状态。每次新会话，你都要重新交代一遍：代码风格、时区、输出语言、用 pnpm 不用 npm……上下文窗口再大，也扛不住把全部历史塞进去。社区里最常见的做法是把"重要信息"手写进 system prompt，但两周之后它就变成一段没人敢删的历史遗留。

这篇帖子的核心观点只有一句：**记忆是数据，不是 prompt 片段**。围绕这个思路，给一套在 OpenClaw 里可落地的分层设计。

## 问题

先对症状：

1. **记不住**：新会话冷启动，偏好全部丢失；
2. **记太多**：什么都往里存，检索噪音大，agent 行为漂移；
3. **记错了**：把一次性的偶然要求当成长期偏好，而且改不掉。

## 做法

### 1. 先分三层

- **工作记忆**：当前会话上下文，不持久化；
- **偏好库**：结构化 KV，以显式声明为主，长期保存；
- **情景库**：会话摘要 + 向量，用于召回"上次是怎么做的"。

大部分场景只做中间这层就够，别一上来就上向量库。

### 2. 偏好库最小 schema

```json
{
  "key": "package_manager",
  "value": "pnpm",
  "scope": "global",
  "source": "explicit",
  "confidence": 0.95,
  "updated_at": 1717000000
}
```

`scope` 分 global / workspace / project 三级，检索时先窄后宽；`source` 区分用户亲口说的和模型推断的。

### 3. 写入与读取

- 用 MCP 暴露 `memory_write` / `memory_search` / `memory_list` 三个工具，agent 在对话中自主调用；write 前走一遍抽取 → 去重 → 冲突检查。
- 显式信号直接写入；隐式信号（比如连续三次纠正输出格式）以低 confidence 起步，命中次数够了再升级。
- 会话启动时按 scope 过滤 + 关键词/向量混合检索，取 top-N（建议 ≤10 条）注入 system prompt，不要全量灌。

### 4. 冲突与遗忘

- 显式覆盖隐式，新时间戳覆盖旧值，旧值进 history 字段；
- implicit 记忆按 last_hit 衰减，长期未命中自动降权直至清理；
- `memory_list` 对用户开放，能看、能删。**用可见性换信任，这一步不能省。**

## 踩坑点

- **隐式推断太激进**：用户说了句"这次给我表格"，被记成"永远输出表格"。implicit 必须低置信起步、多次验证再固化；
- **短语句向量检索不稳**："用 pnpm"这类偏好的 embedding 召回很差，关键词索引必须保留，别迷信纯向量；
- **一次会话写几十条**：给 write 频率设上限，宁可漏记，不要污染；
- **scope 串味**：项目级偏好泄漏到全局，换个项目行为全歪；
- **只增不改**：没有冲突检查，新旧偏好同时注入，模型随机听一个，表现为"时好时坏"，最难排查。

## 可复用建议

1. 先只做显式偏好，跑稳两周，再考虑开隐式推断；
2. 记忆要有完整 CRUD 和审计日志，别让它变成黑盒拼接；
3. 建 20 条左右的回归评测集：每次改动后用全新会话冷启动，验证偏好是否生效；
4. 每条记忆都要能回答"我为什么记得这个"——source 和 confidence 就是干这个的。

## 总结

记忆系统的关键不是存得多，而是**取得准、改得动、删得掉**。把偏好当一等数据来设计 schema、检索和生命周期，用 MCP 工具让 agent 参与维护，用可见性换用户信任。一个 SQLite 文件加三个 MCP 工具就能起步，比纠结选哪个向量数据库重要得多。欢迎在评论区贴你们的 schema，一起踩坑。
