## 背景

在信息摄入这件事上，人与人效率的差距，往往不在读多少，而在信息源是否机器可读。网页改版、App 限流、推荐流掺噪，而 RSS 至今仍是最稳定的增量订阅协议：结构化、无需登录、没有反爬包袱。手上有 Agent 之后，我做的第一件事就是把它变成自动化管线：抓取、过滤、摘要、投递全部定时执行，人只负责最后一步阅读。

## 问题

把 RSS 直接喂给 LLM 点「帮我总结」，一周内就会废弃：

- 源质量参差，全量喂模型既烧 token，产出又全是噪声；
- 很多 feed 只给 summary，拿全文要自己抓网页，撞上反爬逻辑；
- 同一条新闻被五个源转载，不查重的话摘要读起来像结巴；
- 推送节奏失控，你很快会亲手把这个渠道静音。

目标要先想清楚：不是「替我读完」，而是把值得读的部分压缩成你每天愿意打开的形态。

## 做法

管线分四层，层与层之间落 JSONL 中间产物，任何一步都可以独立重跑：

1. **源层**：`source.yaml` 维护源清单并分级。必读源走强模型全文摘要；观察源走便宜模型、只给标题。
2. **抓取层**：Miniflux 做聚合器，统一处理 etag / last-modified 增量；没有 RSS 的站用 RSSHub 补齐。OpenClaw 侧若有 fetch-rss 类 MCP 工具直接复用，不必重复造轮子。
3. **过滤层**：先规则后模型——关键词黑名单、来源权重、标题 simhash 查重，这一步通常能砍掉六到七成条目。
4. **摘要与投递**：过滤后的条目分批摘要，prompt 里写死三条：只基于原文；输出三个要点加一句「为什么值得读」；必须附原文链接。结果写入 SQLite，日更一份 digest Markdown 落到笔记仓库，同时把标题+链接推到 Telegram 频道。

调度用 cron 触发 OpenClaw 定时任务，四个阶段串成 MCP 工具链；任何一步挂掉，中间产物都在，断点重跑即可。

## 踩坑点

- **pubDate 无时区**：有的 feed 给本地时间，同一条目被判成两条。以 guid 去重为主，时间统一归一到 UTC。
- **只有摘要的源**：高频抓全文必触发限流。控制频率、准备降级方案，别让单个源阻塞整批任务。
- **成本失控**：第一版全量喂模型，一天的量顶半个月。加规则粗筛层后，成本降到原来的五分之一。
- **幻觉**：模型编出原文没有的「细节」时直接拒收。要求带链接不只是方便跳转，更是逼模型给得出出处。
- **feed 质量**：CDATA 截断、编码错误、XML 转义异常都很常见，解析降级策略必须写，别假设源是干净的。

## 可复用建议

- 原始条目永远先落盘，改 prompt 后随时重跑，不浪费一次抓取——这是整条管线最值得的设计。
- 源清单配置化驱动，增删源不动代码。
- 源治理没有捷径：每月砍掉一次没点开过的源，起步 10~15 个就够，别一上来订一百个。
- 摘要风格提前定边界：客观摘录与主观判断分字段存，别混在一段里，回看时无法溯源。

## 总结

这条管线的价值不在 AI，而在前面那些朴素工程：源治理、增量抓取、规则粗筛。AI 只是最后一层压缩。建议先用最朴素的版本跑两周，记录自己实际点开了哪些推送，再回头调源清单和过滤规则——管线会越用越准。
