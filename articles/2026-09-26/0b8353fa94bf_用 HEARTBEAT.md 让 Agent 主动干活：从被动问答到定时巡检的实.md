## 背景

大多数人对 Agent 的使用模型是“一问一答”：你想起来，才去问它。但真正用起来之后会发现，很多有价值的事恰恰是“你没想起来问”的——日历里有个会要迟到、磁盘快满了、盯的那条 CI 又红了。

OpenClaw 内置了一个心跳（heartbeat）机制：Agent 会按固定间隔自动醒来，读取工作区根目录下的 `HEARTBEAT.md`（默认在 `~/.openclaw/workspace/` 下），根据文件内容决定是执行任务还是继续沉默。这个文件就是把 Agent 从被动应答转成主动巡检的开关。

## 问题

监控类需求传统做法是 cron + 脚本，但最难的部分不是跑任务，而是**判断“值不值得打扰用户”**：每天报一次磁盘占用是骚扰，超过阈值不报是失职。这段判断逻辑手写很痛苦，而它恰好是 LLM 擅长的。心跳机制本质上是把“何时开口”的决策权交给 Agent——前提是你把规则写清楚。

## 做法

**1. 定位文件。** 心跳醒来时默认读工作区的 `HEARTBEAT.md`，没有就创建。

**2. 写任务条目。** 每条包含三个要素：触发条件、执行动作、汇报规则。示例：

```markdown
# 只在有内容时汇报
- 每天上午第一次心跳：汇总今日日历 + 未读 GitHub 通知
- 检查 /data 磁盘使用率，超过 85% 才提醒，附最大的三个目录

# <!-- 临时停用某条任务，注释掉即可 -->
```

**3. 配置心跳参数。** 在配置文件的 heartbeat 段落里设间隔（默认约 30 分钟）和 target 渠道——即主动消息发到哪个会话。具体键名以你所用版本文档为准。

**4. 验证。** 先写一条必然触发的任务，把间隔临时调到 1–2 分钟观察一个周期，确认消息渠道、格式、频率都符合预期后再调回。

**5. 迭代。** 观察一周的 token 消耗和误报率，再收紧条件。

## 踩坑点

- **空文件不等于不花钱。** 心跳开着，每个周期就有一次模型调用；文件只写注释时 Agent 会沉默（返回 NO_REPLY），但调用照发。彻底不用就关掉心跳或拉长间隔。
- **任务太模糊。** “帮我盯着邮件”这种写法，结果要么乱报要么永不报。条件必须可判定，输出格式最好也定死。
- **消息发错地方。** 不显式配置 target 时，主动消息可能落到“最近活跃”的会话，体验很怪，务必指定。
- **心跳不是调度器。** 精确到分钟的定时任务请用系统 cron；心跳擅长的是“轮询 + 判断是否值得说”，两者别混用。
- **失败不可见。** 主动运行意味着没人盯着，让 Agent 把每次心跳的结果追加到一个日志文件，出问题能回溯。
- **权限放大。** 无人确认的主动执行 + 完整工具/MCP 权限是危险组合，删除、支付类操作强制要求确认。

## 可复用建议

- 每条任务都写“沉默条件”：什么情况下不说，比说什么更重要。
- “检查”与“执行”分级：只读检查放心跑，写操作加确认。
- 间隔从 30–60 分钟起步，看完一周账单再调。
- 用 Markdown 注释临时停用单条任务，保留上下文。
- 心跳日志单独存文件，排查误报时非常有用。

## 总结

HEARTBEAT.md 的价值不在“能定时跑任务”——cron 早就做到了——而在把“什么时候值得打扰用户”这个判断交给 Agent。写好它的关键不是堆任务数量，而是把沉默条件、汇报格式、权限边界定义清楚。先从一两条低风险检查起步，跑稳了再扩展，你会发现 Agent 第一次有了“同事感”而不是“工具感”。
