## 背景

LLM 本身是无状态的，所谓"记住你"，本质是把信息存到上下文之外，再在合适时机塞回去。听起来简单，但大多数人第一步就是往 system prompt 里堆"用户偏好 X"——前期有效，两周后记忆超过二十条就开始互相打架。这篇分享我在自己 Agent 工作流里落地的一套方案，思路不新，胜在工程上可维护。

## 问题出在哪

失败的记忆系统通常死在四个地方：

- **什么都记**：会话里 90% 的内容不值得持久化，全量写入后噪声淹没信号；
- **只加不改**：用户三个月前说"用 tab 缩进"，上周改口"还是空格吧"，旧记忆没人清理；
- **检索全靠向量**：召回一堆"语义接近但场景不对"的记忆，反而污染输出；
- **写入时机不对**：对话中途同步抽取记忆，又慢又打断流程。

## 我的做法：三层记忆 + 一条异步写入管线

**分层存储。** 记忆拆三层：

- **profile 层**：稳定偏好（代码风格、回复语言、常用工具链），JSON 存 SQLite，每条带 confidence 和 updated_at，总量压在 30 条内，每次会话开头全量注入，也就几百 token；
- **facts 层**：项目相关事实，如"部署用 Compose 不用 K8s"，按命名空间隔离（个人 / 项目）；
- **episodic 层**：具体事件和长尾细节，进向量库，只在相关时按 top-k + 相似度阈值召回。

**写入走异步管线，不在对话中抽取。** 会话结束后跑一次抽取 pass：把对话记录喂给模型，输出候选记忆列表，每条带类型、置信度、来源（显式指令 / 行为推断）。接着三步：与已有记忆做语义去重；冲突时按"显式指令 > 新时间戳 > 行为推断"的优先级覆盖；低置信度先进观察队列，二次出现才转正。

**读取有预算。** 注入总量设上限：profile 全量，facts 按命名空间，episodic 只取 top-3 且必须过相似度阈值。宁可少注入，不要塞满。

**留逃生口。** "忘掉这条""以后都这样"要映射成显式的 delete / upsert 操作，优先级最高，不走置信度判断。

## 踩坑记录

- 抽取太激进，把"我这周在赶版本"这种临时状态也存了，一周后全是过期信息。后来在抽取 prompt 里强制区分"长期偏好"和"临时状态"；
- 向量库按句子粒度切，召回碎成渣。改成"一条记忆 = 一个自包含的完整事实"后明显改善；
- 忘做命名空间隔离，A 项目的记忆串进 B 项目会话，排查了半天；
- 记忆库用户自己看不到，调试全靠猜。加了个 dump 命令导出可读 JSON，问题定位快了一个数量级。

## 可复用的建议

1. 先做 profile 层（结构化 + 全量注入），它解决 80% 的问题，向量检索可以后加；
2. 写入必须有去重和冲突覆盖逻辑，append-only 的记忆系统活不过一个月；
3. 每条记忆带时间戳和来源，过期与降级才有依据；
4. 记忆对用户透明可编辑，既是调试手段也是信任问题；
5. 用 MCP 暴露 memory_read / memory_write 两个 tool，比在 system prompt 里硬编码灵活得多；
6. 做回放测试：攒 20 个典型历史会话，改记忆逻辑后跑一遍，防止回归。

## 小结

记忆系统的本质不是"存得多"，而是"该出现的时候出现、不该出现的时候闭嘴"。分层控制注入量，异步管线控制写入质量，显式指令控制覆盖优先级——三件事做到位，Agent 的记性基本够用了。剩下的迭代靠回放测试和真实使用反馈，别指望一次设计到位。
