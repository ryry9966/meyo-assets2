## 背景

OpenClaw 的主会话是长期累积的上下文：系统提示、历史消息、工具结果、记忆文件都堆在里面。跑自动化任务时经常需要并行或长耗时的工作（批量改文件、爬数据、跑分析脚本），如果全在主会话里做，工具输出会把上下文撑爆，compaction 开始吃掉早期历史，模型逐渐"失忆"。

## 问题

典型的污染路径有三条：

1. 工具结果直接进主会话历史——一个 curl 返回 20KB JSON，之后每一轮都要背着它跑；
2. 子任务的中间过程（思考、重试、报错）混入主线，把主 agent 的注意力带偏；
3. 多个并发任务写同一个 session，消息交错，状态互相覆盖。

## 做法

OpenClaw 的思路是"子会话 + 回传摘要"：

1. 主 agent 用 `sessions_spawn` 起子会话，session key 独立（形如 `agent:main:subagent:<id>`），子 agent 有自己的系统提示和消息历史；
2. 任务描述写在 spawn 的 message 里，包含三要素：目标、边界（允许碰哪些目录/工具）、输出格式；
3. 子 agent 的所有工具调用、中间重试都留在子会话内，跑完后只有最终结果回传主会话；
4. 需要更强隔离时，子会话可以指定独立 workspace 甚至 sandbox，避免它直接改主工作区的文件；
5. 主会话用 `sessions_list` 查子会话状态，长任务可开 thread 模式留痕，不必傻等。

一个可以直接抄的 spawn prompt 模板：

```
任务：统计 src/ 下所有 TODO 注释并归类
边界：只读，不修改文件；不要向频道发消息
输出：JSON 数组，字段 file/line/tag，最多 50 条
```

## 踩坑

- **权限默认继承**：子 agent 能用到主 agent 的大部分工具。shell、发消息这类高危工具要么收紧，要么在任务里明确禁用——"不要发消息"一定要写，否则它可能替你回复了用户。
- **摘要本身也会爆**：让子 agent 返回"过程叙述"而不是结构化结果，等于把污染换个位置发生。输出格式要卡死，宁可在模板里写死字段名。
- **嵌套别太深**：子 agent 再 spawn 子 agent，两层基本是极限，再深排障会很痛苦。
- **并发写冲突**：多个子 agent 同时写同一个文件或记忆，后写的覆盖先写的。写操作收敛到主会话统一做，子 agent 只读和产出结果。
- **session 残留**：子会话结束后 key 不会自动清，长期运行的实例记得定期清理 session 存储。

## 可复用建议

- 原则一句话：**主会话只保留"决策 + 摘要"，过程全部下沉到子会话**。
- 子任务单一职责，一次一个目标；要多目标就开多个子 agent 并行，而不是塞给一个。
- 回传统一用 JSON 或固定段落结构，主会话解析稳定，也方便事后审计。
- 在 `AGENTS.md` 里写清楚"什么情况下该 spawn"，让模型形成习惯，而不是每次靠人提醒。

## 总结

session 隔离的本质，是把"干活的上下文"和"决策的上下文"分开。OpenClaw 用独立 session key 加回传摘要实现这一点，再配合收紧的工具权限和固定的输出格式，主会话就能长期保持干净。建议先挑一个批处理任务试水，观察主会话 token 曲线的前后变化——比读十篇文档都直观。
