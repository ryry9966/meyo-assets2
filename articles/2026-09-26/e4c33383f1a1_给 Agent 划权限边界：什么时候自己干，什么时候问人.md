## 背景

Agent 能接的工具越来越多：本地 shell、文件读写、MCP server 暴露的各种能力、插件里的第三方 API。能力上去了，边界问题就浮出来：哪些事 agent 自己干，哪些必须停下来问人？

## 问题：确认弹窗不是越多越好

两种极端都不对。一种是每步都确认——读个文件也要点同意，人很快疲劳，最后见弹窗就点"允许"，这比没有弹窗更危险，确认机制退化成了仪式。另一种是全自动——直到某天它把 `rm -rf` 用错目录、把测试消息发给了真实用户、或者一晚上烧掉了预算。

关键认知：**每次确认都在消耗人的注意力，而注意力是稀缺资源**。目标不是"多问"，而是问得少、问得准、问的时候人真的能做出判断。

## 做法：两轴分类 + 三级策略

用两个轴给操作分类：

1. **可逆性**：出错后能否回滚？git 仓库内的文件改动可逆；force push、删生产数据、对外发消息基本不可逆。
2. **爆炸半径**：只影响工作区，还是影响外部世界（别人会看到、会花钱、有真实副作用）？

由此得出三级策略：

- **T0 自动执行**：只读操作、沙箱内的读写。搜索、读文件、列目录，不用问，记日志即可。
- **T1 受限自动**：可逆但影响面不小——工作区内写文件、在 feature 分支上 commit、调测试环境。自动执行，但配配额 + 全量审计日志。
- **T2 必须问**：不可逆、出工作区、动钱、动凭据。问的时候给结构化提案：确切要执行的命令或 diff、影响范围、回滚方案。不是"我可以继续吗？"，而是"我将执行以下操作，diff 如下，批准还是拒绝？"

落到 OpenClaw / MCP 实践：MCP 的好处是工具显式列出。给每个工具在配置里标注风险等级，策略写成 allowlist/denylist 文件进版本库。危险工具尽量拆成 `preview` + `execute` 两个，先看预览再执行。人批准过的模式可以沉淀为策略（"本项目允许跑测试"），减少重复打断。

## 踩坑点

1. **让模型自己判断风险**。它会自我合理化。风险等级必须写在工具配置里，模型只能升级（拿不准就问），不能降级。
2. **伪确认**。只给 y/n、不给上下文的确认，人根本无法评估，等于没确认。
3. **"只读"工具的隐性副作用**。有的 GET 会触发 webhook，有的调用按 token 计费。只读 ≠ 免费，盘点时逐个核实。
4. **"总是允许"范围失控**。会话级授权要限定到具体工具加具体参数模式，不能一把梭。
5. **子 agent / 插件继承全部权限**。权限应该沿调用链收窄，而不是原样复制。
6. **策略腐化**。半年前的 allowlist 对应的项目早变了，定期审计。

## 可复用建议

- 策略即代码：权限清单进 git，改动走 review。
- 默认值原则：不可逆 → 默认问；只读且沙箱内 → 默认放行。
- 每个危险工具配 dry-run。
- 自动执行的动作全部进 append-only 审计日志——自主权的代价是可追责。
- 用批准率校准边界：如果 95% 都在点同意，说明问得太多；如果确认真拦下过事故，说明边界有效。
- 升级是单向的：agent 随时可以选择问人，但永远不能跳过该问的。

## 总结

权限边界本质是产品设计问题，不是配置问题。核心不是"怎么让 agent 安全"，而是人的判断力应该花在哪。便宜且可逆的事放给 agent，人保留对不可逆、大爆炸半径决策的否决权——并且只在能真正做出判断时被问到。边界划对了，自动化才敢加速。
