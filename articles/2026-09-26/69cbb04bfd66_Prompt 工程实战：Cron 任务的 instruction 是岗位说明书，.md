## 背景

OpenClaw 的 cron 能力让 Agent 按计划自动醒来干活：每天早上汇总一次信息、每周巡检一次服务、定期整理目录。听起来和聊天没区别，反正都是给一句 instruction。但跑过几周你会发现，同一个任务，在交互对话里表现正常，放进 cron 就开始"自由发挥"。

核心差异只有一个：**cron 是无人值守执行**。没人在场回答追问，跑挂了也没人立刻发现。这决定了 cron 的 instruction 本质上是一份岗位说明书，而不是一句聊天消息。

## 问题

踩过的坑集中在几类：

1. **指令太模糊。** "帮我看看今天有什么值得关注的"——Agent 只能猜，每次猜的方向还不一样。
2. **没写输出去向。** 结果发到哪、什么格式，全凭模型当时的心情。
3. **没有失败分支。** 数据源挂了，Agent 有时会硬编一段"总结"交差，连挂三天你都不知道。
4. **时间语义没钉死。** "今天"是哪个时区的今天？跨零点触发的任务尤其混乱。
5. **不会去重。** 每天把同样的内容重新总结一遍。

## 做法

我现在的 cron instruction 固定用六段式骨架：

```text
【目标】只做一件事：……
【来源】用 xx 技能/MCP 工具获取……，不要用其他来源。
【时间语义】"今日"指 Asia/Shanghai 时区的当天，任务在早 8 点触发。
【输出】按以下模板输出：……（给出字段）
【投递】结果发送到 <channel>；无更新时只发一句"今日无更新"。
【失败处理】来源不可用时明确说明"xx 获取失败"，禁止用推测补全。
```

几个关键点：

- **一次一个目标。** 想做日报加周报，拆成两个 job。单个 instruction 塞太多事，失败率和 token 消耗都会失控。
- **把"自包含"当硬约束。** 交互对话里 Agent 可以追问，cron 里追问等于永久阻塞。它需要的路径、频道、格式模板必须全部写死在 instruction 里。
- **失败要显式。** 明确要求"来源不可用时如实报告"，并在投递目标里给失败通知留位置。
- **幂等与去重。** 有状态的任务（比如总结进度），让它先读上次的落盘结果，只处理增量。

## 踩坑点

- 上线前先在交互会话里手动跑几遍这条 instruction，确认行为再挂 cron，能省掉大部分调试时间。
- 不要堆大量 few-shot 示例，每次触发都付这笔 token 成本，一个精简的输出模板通常就够。
- instruction 是配置不是代码，改完留一行版本注释，出问题方便回溯是哪次改动引入的。
- 输出落一份运行日志，事后排查"它那天到底干了什么"全靠这个。

## 可复用建议

- 把六段式骨架存成代码片段，新建任务时直接填空。
- 高频任务的结果和失败都写日志文件，cron 的可观测性基本等于"有没有日志"。
- 定期审查：跑了两周的任务，往往能删掉三分之一的冗余措辞。

## 总结

写 cron instruction 的心智模型很简单：想象你雇了一个能力很强但从不主动提问的夜班员工，而你看不到他的工作过程。你会怎么写交接文档，就怎么写这条 instruction——**目标单一、来源明确、格式固定、失败可感知**。做到这四点，定时任务基本就能长期稳定地跑下去。
