## 背景

我们的 OpenClaw 实例日常要干不少"批量杂活"：每周跑一遍仓库依赖检查、扫描文档失效链接、整理消息渠道里的待办。以前都是主 agent 一条线串行做，一轮下来十几分钟，而且中间过程的输出全堆在主上下文里，聊几轮就开始"忘事"。

## 问题

串行的三个代价很实在：

1. **慢**：任务之间明明没有依赖，却老老实实排队；
2. **上下文污染**：子任务的中间日志、报错堆栈把主对话撑爆，主 agent 的判断力肉眼可见地下降；
3. **单点阻塞**：一个任务卡住，后面全部干等。

解法自然想到 subagent：主 agent 只做拆分和汇总，执行下沉到子 agent，各自独立上下文。但真用起来，坑比想象多。

## 做法

我们现在的编排流程固定成四步：

**1. 拆任务，先分读写。** 只有"只读 + 互不依赖"的任务才允许并行。比如三个目录的文档扫描可以并行；而"改配置 → 重启服务 → 验证"这种有状态依赖的，坚决串行。这一条过滤掉了一半乱并发的冲动。

**2. 每个 subagent 给三样东西**：明确的输入（具体路径/链接，不要"你看着办"）、明确的交付物（结构化摘要 + 产物文件路径）、明确的禁区（不得修改工作区以外的文件，禁止再派生子任务）。

**3. 并发限流。** 同时运行的 subagent 钉在 3 个。实测再多就撞模型端速率限制，失败重试反而更慢。MCP 工具调用也要留意，有些下游服务扛不住并发，需要在 skill 层加信号量。

**4. 汇聚只看摘要。** subagent 结束后只回传：结论、异常列表、产物路径。详细日志落盘成文件，主 agent 需要时再按路径读取。主上下文占用从几万 token 降到千级。

## 踩坑点

- **共享工作区互相覆盖**：两个 subagent 同时改一个文件，后写的赢。只读任务也建议各自独立工作目录、输出写到约定路径，别赌"应该没人动这个文件"。
- **subagent 谎报完成**：早期有子 agent 返回"已完成"，实际脚本根本没跑通。现在强制交付物带证据——文件路径、命令退出码，主 agent 抽查。
- **嵌套失控**：subagent 又起 subagent，几分钟烧掉一晚额度。直接在编排层禁掉二层嵌套。
- **错误策略没预设**：某个子任务失败后，主 agent 会"热心"地连试三次。现在统一约定：失败重试一次，再失败就标记跳过，汇总里列出来人工看。

## 可复用建议

- 并行只给只读任务，写操作永远串行或加锁；
- subagent 的 prompt 模板固定三段：输入、交付物、禁区；
- 并发数从 3 起步，按限流报错频率再调；
- 主上下文是稀缺资源，中间产物一律落盘、按需读取；
- 先拿"每周跑一次的只读批量任务"练手，成本低、收益直观。

## 总结

subagent 编排的本质不是"更多 AI"，而是**上下文隔离 + 失败隔离**。把主 agent 从执行者变成调度者之后，一轮批量任务的耗时从十几分钟压到三四分钟，主对话也干净了很多。它不神奇，本质上更像多年前的多进程编程——老道理，新载体。核心就一句话：能并行的只有无状态的事，其余都老老实实排队。
