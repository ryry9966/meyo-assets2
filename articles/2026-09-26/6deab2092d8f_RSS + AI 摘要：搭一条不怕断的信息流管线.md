## 背景

信息源越订越多，真正读进去的越来越少。RSS 是目前少数还开放、稳定、可自主掌控的分发协议，但它只解决"聚合"，不解决"读完"。把 RSS 和本地 Agent 的定时任务、LLM 摘要能力串起来，可以做到每天一份低成本、可审计的信息摘要。这篇记录我用 OpenClaw 搭这条管线的完整过程。

## 问题

直接订阅 40+ 个 feed 会遇到三个具体问题：

1. **噪声高**：真正值得看的信息每天不超过 10 条，但原始条目可能上百；
2. **只有标题和截断摘要**：大量 feed 出于引流考虑不给全文；
3. **无法持久追踪**：看过的、推过的、跳过的没有状态，第二天重复出现。

所以目标不是"把 feed 扔给 LLM"，而是搭一条分阶段、可重跑、幂等的管线。

## 做法

管线拆成四个阶段，各自独立脚本，用 SQLite 串状态：

**1. 采集**：用 OpenClaw 的定时任务每 2 小时跑一次，`feedparser` 拉取 OPML 里的全部源。每个 entry 计算 `hash(guid + link)` 存入 `entries` 表，只有新条目进入下一阶段。

**2. 清洗**：正文太短（< 300 字符）就回源抓全文，用 readability 提取正文，顺手处理 HTML 实体和编码。规则层先过滤：命中黑名单关键词、来源权重低、纯广告的直接标记 `skip`，不进 LLM。

**3. 摘要**：攒批处理，每批 10 条，prompt 要求只基于原文输出结构化 JSON：`{title, one_liner, tags, score}`，score 是 0-10 的相关度自评。温度 0.2，模型选个便宜的就行——摘要任务对模型要求不高，成本敏感。也可以把这步封装成 MCP tool，让 Agent 在对话里按需调用。

**4. 分发**：score ≥ 7 进当天日报，5-7 进"可看可不看"分区，其余只留标题索引。日报由 Agent 汇总成一条消息推到 IM，同时落一份 Markdown 归档。

## 踩坑点

- **时间字段不可信**。不少 feed 的 `published` 是错的或干脆缺失，去重和排序都别依赖它，用入库时间 + guid 哈希。
- **全文抓取被反爬**。个别站点对无 UA 的请求直接 403，加 User-Agent 和 3 秒延迟后基本解决；真不行的就接受只有摘要，别硬刚。
- **重复推送**。最初分发阶段失败重试导致同一条推了三遍。后来所有推送前先查 `digest` 表里当天有没有同 entry 记录——幂等要在设计时就做，不是事后补。
- **摘要幻觉**。模型偶尔给出原文没有的结论。在 prompt 里加"不得引入原文未出现的信息"，schema 里加一个 `grounded` 字段让模型自检，再配合人工抽查。
- **成本失控**。一开始所有条目都过 LLM，token 的 80% 花在垃圾上。规则过滤前置后，进 LLM 的量降了七成。

## 可复用建议

- 分阶段 + SQLite 状态表是这类管线最省心的骨架，每个阶段都能单独重跑、单独调试；
- prompt 和 schema 模板化放配置文件里，换模型、调字段不动代码；
- 先接 5-10 个高频源灰度跑两周，人工抽查摘要质量，再扩量；
- 别追求全自动：score 阈值、黑名单这些参数就是你的编辑品味，值得手动调。

## 总结

这条管线跑了一个多月，每天早上收到一份 10 条左右的日报，信噪比比刷 timeline 高得多。它没有用到什么新技术，价值在于把 RSS 的稳定性和 LLM 的压缩能力用工程方式拼在一起：规则先省钱，摘要再提效，状态表保证不重不漏。代码量不大，两个晚上能写完，建议从自己最常看的 5 个源开始试。
