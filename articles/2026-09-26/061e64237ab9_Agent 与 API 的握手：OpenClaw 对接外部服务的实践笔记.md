## 背景

Agent 真正产生价值的分水岭，在于能不能"够得着"真实系统。OpenClaw 本体解决的是规划、记忆和工具调度，但要查订单、发工单、调内部网关，就必须和外部 API 打交道。这篇帖子汇总了社区几个落地案例沉淀下来的对接路径和坑，供后来者少走弯路。

## 问题

实际对接中反复出现三类故障：

1. **工具描述不清**，Agent 猜参数、自由发挥填字段；
2. **返回体失控**，原始 JSON 又大又深，塞爆上下文且 Agent 理解不了；
3. **鉴权与容错散落在对话里**，token 泄漏到日志、超时挂死、写操作重复执行。

## 做法

OpenClaw 对接外部服务主流三条路：MCP server、自定义工具（plugin）、让 Agent 直接发 HTTP。优先级建议：**MCP > 自定义工具 > 裸 HTTP**。裸 HTTP 只适合临时验证，不该进生产。

具体步骤：

1. **先包一层薄封装，不裸调。** 一个工具对应一个明确意图（如 `query_order`），不要做一个万能 `call_api` 把所有 endpoint 塞进去。
2. **把 schema 当产品文档写。** 参数名、类型、是否必填、业务含义全部写进工具描述。Agent 选工具全靠这些描述，含糊一个词它就会自己补全。
3. **鉴权放环境变量，刷新逻辑封在封装层。** 密钥不进对话上下文、不进日志，token 过期由封装层静默处理，Agent 无感知。
4. **收口返回值。** 在封装层做裁剪：只留业务字段、分页截断、错误归一化为 `{ok, error, hint}` 结构。让 Agent 看到的是"结论 + 下一步建议"，不是原始响应。
5. **写操作加确认与幂等。** 涉及 POST/PUT/DELETE 的工具，先只读版本跑通再放开写，带幂等键保证重试不重复下单。

## 踩坑点

- **描述里写"尽量"必出事。** "date 参数尽量填今天"，Agent 会当成可选项。要么标记必填，要么封装层兜底默认值。
- **没设超时。** 上游卡 30 秒，Agent 会反复等待重试，把重试风暴传导到上游。统一 5–10 秒超时，失败返回结构化错误。
- **返回大 JSON。** 一次回 2 万 token，Agent 会漏读字段甚至幻觉。宁可封装层做聚合摘要。
- **工具数量贪多。** 挂 30 个工具后选择准确率明显下降，按场景拆分会话或做动态加载。
- **日志带 token。** 调试图省事打全量请求头，事后清理非常痛苦，日志层统一脱敏。

## 可复用建议

- 封装层是唯一知道"真实 API 长什么样"的地方，Agent 只接触业务语义。
- 新接口按**只读 → 写入 → 自动化**三步走，不要一步到位。
- 每个 MCP server 独立进程或容器，崩了不影响主 agent。
- 给 Agent 的错误信息带上建议动作，例如 `rate_limited, retry after 60s`，比裸错误码好用得多。

## 总结

对接外部服务的本质，是把"不稳定的外部世界"翻译成"稳定的工具语义"。OpenClaw 侧做好 schema、鉴权、超时、返回收口四件事，Agent 的表现会从"偶尔能用"变成"可以托付"。所有跑得顺的案例只有一个共性：**封装层薄而清晰**。
