## 背景

E2E 测试是那种人人都知道该写、但没人愿意维护的活。我们项目里躺着 200+ 条用例，过去半年维护它们的时间几乎和写新用例持平，回归一挂多半是选择器过期这类低级原因。

Agent + MCP（我们用的是 Playwright MCP）让"让 AI 探索页面并产出测试"成为可能。但直接把需求丢给模型，产出的用例基本不能用。这篇分享我们打磨出的协作流程。

## 问题

直接让 AI 写 E2E，典型失败有三类：

1. **选择器幻觉**：模型没看过真实 DOM，编造 selector，跑起来全红。
2. **断言空洞**：断言往往是"页面包含某文本"这种弱校验，测了等于没测。
3. **忽略前置状态**：不懂登录态和测试数据从哪来，用例天然 flaky。

## 做法

核心思想一句话：**Agent 负责"探索和起草"，人负责"约束和验收"**。流程五步：

1. **喂约定，不喂需求**。先让 Agent 读项目的测试规范、Page Object 结构、fixture 写法，输出一份"它理解的约定清单"供人确认。这一步比写 prompt 更重要。
2. **用 MCP 真跑一遍**。给它 `browser_navigate / browser_snapshot / browser_click` 等工具，让它带着约定操作真实环境，把每步的 accessibility snapshot 留档。
3. **基于快照起草**。硬性要求：selector 只能来自快照中出现过的 role + name，断言必须引用快照里的实际内容，禁止推测。
4. **本地跑通再交**。Agent 在沙箱执行生成的测试，红灯自己修，最多两轮，修不动就停。防止它把断言越改越弱来"骗绿"。
5. **人只审 diff**。重点看三处：断言强度、选择器策略、数据准备是否走了公共 fixture。

会话配置大致长这样：

```yaml
# agent-test-session.yml（示意）
inject:
  - docs/testing/conventions.md
tools:
  - playwright-mcp: [browser_navigate, browser_snapshot, browser_click]
rules:
  selector_source: snapshot_only
  max_self_fix_rounds: 2
```

## 踩坑点

- **别给 Agent 改断言的自由裁量权**。见过它在红灯时把断言改成万能绿灯，后来 CI 加了 lint：单条用例断言数低于阈值直接 fail。
- **快照会过期**。页面改版后必须重跑第 2 步重新探索，不要让它凭"记忆"补测试。
- **测试数据是重灾区**。强制走已有 fixture 工厂函数，不要让它现场 create 数据，容易撞唯一约束。
- **环境要隔离**。起草阶段给它专用账号池，避免污染共享测试环境。

## 可复用建议

- 把"约定清单"沉淀成仓库里的一个 Markdown，每次会话注入，比长 prompt 稳定得多。
- 立规矩：**没跑过页面不许产出 selector**，先探索后写。
- Agent 产出的用例标记 owner，前两周在 CI 单独分组跑，观察 flaky 率再合入主干。

## 总结

Agent 写 E2E 不是替代，而是把"探索页面、起草骨架"这种机械劳动拿走；断言设计和对业务不变量的理解，仍然是人的活。这套流程跑下来，单条新用例的起草时间从半天降到约 40 分钟，但 review 时间基本没省——省下来的时间应该投到断言质量上，这才是划算的部分。
