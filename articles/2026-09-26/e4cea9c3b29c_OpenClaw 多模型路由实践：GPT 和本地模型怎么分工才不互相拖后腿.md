## 背景

Agent 跑起来之后，账单和延迟是绕不开的两件事。我们的场景是内部数据处理 agent：一次任务链平均 15~20 次模型调用，其中真正需要强推理的只有两三次，剩下都是抽取、格式化、摘要这类轻活。全走 GPT 明显浪费，全走本地模型又会在规划环节翻车。OpenClaw 支持在配置里挂多个模型，多模型路由就是为这个矛盾准备的。

## 问题

“支持多模型”和“用好多模型”是两回事。实际要解决三个问题：

1. 哪些步骤值得用云端大模型，哪些本地小模型就够了；
2. 路由逻辑放在哪一层，怎么避免路由本身变成新的故障点；
3. 本地模型的工具调用和结构化输出不如 GPT 稳，怎么兜底。

## 做法

我们的方案分四步。

**第一步：按“步骤类型”拆任务链。** 把一次运行拆成：规划/决策、工具调用参数生成、文本抽取与格式化、RAG 答案合成。不要按内容猜难度，按步骤类型定，路由才能做到确定性。

**第二步：建路由表。** 在 OpenClaw 的模型配置里明确映射：

- 规划、多工具编排、代码生成 → GPT（云端强模型）
- 抽取、摘要、格式转换、高频分类 → 本地 14B 级模型
- embedding / rerank → 本地

每条路由配 fallback：本地失败重试一次，仍失败才升云端，同时记日志。

**第三步：先用规则路由，别急着上分类器。** 初期路由就是“步骤类型 → 模型”的查表逻辑，几十行代码。跑稳之后再考虑用本地小模型做意图分类实现动态路由——我们实测，动态路由带来的收益远小于它引入的不确定性。

**第四步：加监控。** 每次调用记录路由决策、模型、首 token 延迟、token 数、结构化输出是否通过校验。没有这份数据，路由表就是拍脑袋。

## 踩坑点

- **本地模型的 function calling 是最大的坑。** 4-bit 量化模型聊天很流畅，但让它输出严格的 tool call JSON，失败率明显上升。对策：所有结构化输出过 schema 校验，失败重试一次，仍失败降级到云端。
- **上下文长度。** 工具返回一大段日志，塞给 8k 窗口的本地模型直接截断失效。路由层要先做预截断/预摘要——这一步本身也交给本地模型。
- **静默 fallback 会烧预算。** 本地偶发超时自动升云端，一旦本地服务整体出问题，账单会安静地翻几倍。给云端路由加每日 token 上限，超限直接报错，不要硬扛。
- **路由器别变成单点。** 路由逻辑保持纯函数、无外部依赖，路由自身异常时默认走一个保守的兜底模型。

## 可复用建议

1. 建 30~50 条真实任务的回归集，每次换模型、改量化版本都跑一遍，只看通过率和延迟，不看感觉。
2. 路由表进版本管理，和 agent 配置一起 review。
3. 默认本地、例外上云，而不是反过来——省钱的策略应该同时是最省心的那条路径。
4. trace 里带上路由决策字段，排障时能一眼区分“是模型不行”还是“路由错了”。

## 总结

多模型路由的价值不在“用了几个模型”，而在于把成本和延迟花在真正需要的步骤上。规则路由 + 结构化输出校验 + 云端预算上限，这三件事做到位，GPT 和本地模型就能各干各的活，谁也不添乱。
