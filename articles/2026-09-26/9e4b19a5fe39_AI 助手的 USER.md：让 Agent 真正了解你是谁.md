## 背景

调 Agent 这半年，我在系统提示词上花的功夫不少：工具怎么调、语气怎么定、边界怎么画，都写进了 AGENTS.md。但有个问题一直没解决——它不知道"我"是谁。

每次新会话，我要么重新自我介绍一遍，要么接受一堆错误假设：默认我在东八区、默认我用 Python、默认我想要详尽的解释。AGENTS.md 解决的是"怎么干活"，SOUL.md 解决的是"什么性格"，但"为谁干活"这件事，一直没有归属。

OpenClaw 的工作区约定里正好留了这个位置：USER.md。

## 问题

没有 USER.md 时，实际会遇到三类麻烦：

1. **重复输入**：时区、设备、常用技术栈这类稳定事实，每个会话都要重说一遍。
2. **错误假设**：Agent 拿不到事实就用常识补，而常识经常错——比如把"今晚发"理解成 UTC 的今晚。
3. **信息混装**：有人把个人偏好直接堆进系统提示词，和工具规范搅在一起，改的时候不敢动，越攒越乱。

## 做法

USER.md 放在工作区根目录，和 AGENTS.md 并排。写法上建议控制在 60 行以内，只放稳定事实：

```markdown
# USER

## 基本
- 称呼：老陈；时区 Asia/Shanghai；中文交流
- 代码注释和 commit message 用英文

## 环境
- 主力机：macOS，终端 zsh + tmux
- 常用：Python / Go，编辑器 Neovim
- 主项目：OpenClaw 自托管在工作服务器（内网）

## 偏好
- 回答先给结论，细节放附录
- 方案对比最多两档，别列五六个
- 改我的代码前先说明改哪几行

## 边界
- 不要主动发消息到 Telegram 群
- 不要动 crontab，除非我明确要求
```

核心标准是**事实、可执行、能改变行为**。"先给结论"Agent 能照做；"我喜欢简洁"就太虚，等于没写。每写一行问自己：这行会让它做什么不一样？

更新节奏分两手：环境大变动时手动改一次；同时在 AGENTS.md 里加一条规则——"确认到 USER.md 缺失或过时的用户事实时，先向用户提议，确认后追加"。让长期事实被慢慢沉淀下来。

## 踩坑点

- **写成简历**：头衔、经历全塞进去，没有一条能改变 Agent 的行为，纯浪费上下文。
- **塞临时信息**：本周任务、调试中的 bug 应该进 MEMORY.md 或每日记忆。USER.md 只放以月为单位不变的东西。
- **放敏感信息**：USER.md 会被注入每次会话上下文，API key、密码、真实住址不要写。真有需要就写引用，比如"密钥在 1Password，条目名 xxx"。
- **过期比缺失更糟**：三个月前写的"项目在 A 仓库"，现在指向 B，Agent 会理直气壮地用错。文件头标注更新日期，git 管起来，发现过期当场删。
- **职责混淆**：行为规范进 AGENTS.md，人设进 SOUL.md，用户事实进 USER.md，动态记忆进 MEMORY.md。混着写，后期没法维护。

## 可复用建议

- 把 USER.md 纳入 dotfiles 仓库做版本管理，换机器不丢，变更可回溯。
- 前两周做"惰性校验"：让 Agent 在关键回答前标注"依据 USER.md 哪条假设"，错了立刻修文件，比一次性回忆全部事实快得多。
- 多用户场景按 `USER.<name>.md` 拆分，会话启动时按操作者加载对应文件。
- 每月跑一次自检：让 Agent 通读 USER.md，列出"已过时 / 互相矛盾 / 从未用到"的条目，删掉。

## 总结

USER.md 不是一个文档技巧，而是把"Agent 对用户的认知"从会话级提升到资产级。它便宜——一个 markdown 文件，几十行；收益却持续存在：每个新会话开场就带着正确的你。花二十分钟写第一版，之后交给增量更新就够了。
