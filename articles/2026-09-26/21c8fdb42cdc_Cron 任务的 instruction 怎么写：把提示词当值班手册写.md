## 背景

OpenClaw 的 cron 任务机制很简单：到点之后，框架把 instruction 当成一条用户消息，交给一个**全新冷启动**的 agent 会话，跑完即结束。没有上下文，没有上一次的记忆。

这个模型决定了 cron instruction 和日常对话提示词是两种东西——它更像运维 runbook 里的一步，而不是聊天。社区里不少任务"写了能跑，跑了对不上预期"，问题大多不在调度，而在 instruction 本身。

## 三类典型故障

1. **输出没有去处。** "检查一下报错然后告诉我"——发给谁？哪个会话？结果 agent 在无头环境里自言自语，或把消息发进默认会话制造噪音。
2. **空结果时自由发挥。** 每天 9 点的巡检，绝大多数日子是"没异常"。instruction 没定义空结果行为时，agent 为了"完成任务"会强行总结点什么，甚至去翻别的东西凑内容。
3. **无人值守的越权。** instruction 里带一句"顺手修一下"，等于给定时任务开了写权限。凌晨三点没人盯着，修复动作本身可能就是事故。

## 写法：五要素模板

每条 cron instruction 按五段写：

- **目标与范围**：查什么、时间窗多大。时间以运行时刻为基准（"过去 24 小时"），别用"今天早上"这类模糊表述。
- **数据来源**：具体到命令、路径、MCP 工具名。冷启动 agent 没有任何上下文，"上次那个服务"是无效信息。
- **输出路由**：发给谁、什么格式、长度上限。
- **空结果与异常行为**：无异常时静默还是落日志？工具调用失败时报告错误原文，不要猜。
- **禁止事项**：明确只报告不执行，禁用重启、删改等高危操作。

对比：

坏：`每天检查一下服务报错，有问题告诉我。`

好：

```
【目标】检查本机今天新增的 ERROR 行。
【来源】用 exec 执行：grep ERROR /srv/app/logs/error.log | grep "$(date +%F)"
【输出】若非空，汇总为条目（时间/摘要/次数），每条不超两行，发送到 Telegram 会话 <chat_id>。
【空结果】不发消息，仅向 ~/.openclaw/state/err-watch.log 追加一行 "OK <ISO8601>"。
【禁止】不重启服务，不修改清理日志，不尝试修复，只报告。
```

## 踩坑点

- **状态不会自己存在。** 需要"和上次对比"的任务，必须在 instruction 里指定状态文件：先读后写。agent 不记得上一次跑了什么。
- **静默 ≠ 心跳。** 全静默任务一旦 agent 本身挂掉，你分不清"没异常"和"没运行"。低频任务至少落一行日志，或按周发一次汇总心跳。
- **先手动验证再上日程。** 写完先手动触发一次（或原样粘贴到会话里执行），确认命令和数据源没问题再挂 cron。定时任务的调试成本远高于会话内。
- **一个任务一件事。** "检查报错顺便清理磁盘"这种复合指令，失败时很难定位，拆成两个 cron。

## 可复用建议

- 把 cron instruction 当 runbook 写：可执行、可验证、有边界。
- 沉淀 2~3 个自己的模板（巡检类、汇总类、提醒类），新任务改参数不改结构。
- 涉及写操作的定时任务，拆成"定时只报告 + 人工确认后执行"两步。

## 总结

Cron instruction 的读者，是一个没有任何记忆、跑完就消失的值班同事。补全上下文、写死输出路由、定义清楚空结果和禁止事项，cron 任务就能从"碰运气"变成可靠的基础设施。
