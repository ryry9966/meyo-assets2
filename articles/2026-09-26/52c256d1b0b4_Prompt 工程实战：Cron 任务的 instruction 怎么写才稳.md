## 背景

OpenClaw 的 cron 任务大概是自动化里最"便宜"的能力：一行调度，让 agent 每天定时给你发早报、巡检数据、汇总群消息。但真正跑过几周的人会发现一个规律——**任务挂上去很简单，instruction 写得稳很难**。同一个任务，前三天输出漂亮，第四天开始格式飘了、日期错了、甚至开始编内容。

核心原因只有一个：cron 的 instruction 不是聊天 prompt，而是**无人值守的接口契约**。

## 问题：cron 任务和交互对话的三个差别

1. **没有上下文补充**。任务触发时用户不在场，模型没法追问，prompt 里没写的信息就是没有。
2. **每次运行基本是独立会话**。你写"和上次一样""参考昨天的结果"，模型根本看不到"上次"。
3. **输出直接进渠道**。格式失控就是刷群消息，失败无声就是永远没人发现。

## 做法：把 instruction 当一次性工单写

我的模板分六段，按顺序写：

1. **目标一句话**：做什么、给谁看。例："汇总过去 24 小时 XX 仓库的 issue，发到 Telegram。"
2. **数据来源与工具**：明确指定用哪个 skill/MCP 工具取数，禁止凭记忆回答。这是防编造的第一道闸。
3. **时间基准**：写死时区，"以 Asia/Shanghai 的今天为准"；拿不准就让任务先执行 `date` 再继续。
4. **输出格式硬约束**：给模板，且给上限。例如"第一行结论，之后最多 5 条要点，每条不超过 30 字，不要寒暄、不要 emoji。"
5. **异常路径**：工具调用失败怎么办——"获取失败时只输出'今日数据未获取到'，不要猜测、不要重试超过 1 次。"
6. **状态落盘**：需要增量对比的任务（比如"只报新增"），让它把上次结果写到 workspace 下的固定文件，每次先读再写。

## 踩坑点

- **"和昨天一样"**：独立会话里没有昨天，模型只能编。
- **没写时区**：早报在凌晨触发，把"今天"算成了昨天，连续一周没人察觉。
- **让它"搜最新消息"但没挂搜索工具**：模型会用训练数据凑，看起来像真的。
- **失败重试风暴**：报错后 agent 自行反复重试，一晚上烧掉不少 token。异常路径里必须写"失败即退出"。
- **把密钥写进 instruction**：任务配置是明文存的，敏感信息走环境变量或凭据配置。

## 可复用建议

- **先手动跑，再挂 cron**。把 instruction 直接发给 agent 跑一遍，稳定了再加调度，能提前暴露 80% 的问题。
- **从每天一次起步**，观察一周再提频。agent 任务不是秒级任务，5 分钟一轮的巡检成本很贵。
- **输出留档，每周复盘**。cron 发出的消息顺手存一份，跑偏是可以被"看见"的。
- **instruction 进 git**。改 prompt 和改代码一样要有回滚能力。

## 总结

Cron 任务的 instruction 写作，本质是替一个不在场的用户写需求文档。三个最值钱的原则：**自包含、格式硬约束、异常路径明确**。做到这三点，你的定时任务才能从"跑一次惊喜一次"变成真正可依赖的自动化。

欢迎在评论区贴出你跑得最久的 cron 任务 instruction，一起对照改进。
