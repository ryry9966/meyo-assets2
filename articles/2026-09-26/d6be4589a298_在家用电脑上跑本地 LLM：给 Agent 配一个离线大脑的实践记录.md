## 背景

把模型搬到本地，动机通常有三个：一是数据不出门——代码、日志、私有文档交给云端总有顾虑；二是成本可预期——agent 循环跑一次任务几十次调用，API 账单很容易失控；三是离线与低延迟，本地推理没有网络抖动。这篇文章记录我在一台 16GB 显存的工作站上，给 OpenClaw agent 配一套本地模型链路的完整过程。

## 问题

新手最大的困惑不是“怎么装”，而是“我这张卡到底能跑哪个模型、量化选哪一档”。第二个问题更隐蔽：云端旗舰模型的工具调用很稳，换成本地小模型后，agent 经常生成残缺的 JSON 参数，整条任务链直接断掉。

## 做法

1. **选运行时**。起步用 Ollama，一行命令拉模型就跑；需要精细控制量化与采样换 llama.cpp；批量并发上 vLLM（显存要充裕）。
2. **按显存选模型**。经验法则：Q4_K_M 量化下，模型文件大小约等于显存需求，再预留 2–4GB 给 KV cache。16GB 卡跑 14B Q4 很稳；纯 CPU 跑 7B 约 5–10 tok/s，做后台批处理可接受。
3. **暴露 OpenAI 兼容接口**。`ollama serve` 后把 agent 的 base_url 指向 `http://localhost:11434/v1`，模型名一换即通。MCP 工具走 stdio/SSE，与底层模型解耦，不用改。
4. **用真实任务验证**。别只测聊天。直接让 agent 跑一条完整链路（读文件 → 调 MCP 工具 → 写回结果），观察工具参数是否稳定、长上下文下是否退化。
5. **嵌入模型也本地化**。RAG 场景再起一个小尺寸 embedding 模型（bge 系列够用），避免一半云一半本地导致向量空间不一致。

## 踩坑点

- **OOM 往往不在启动时**。上下文从 4k 拉到 32k，KV cache 让显存占用翻倍，长任务跑一半才崩。限制 context 长度，或开启 KV cache 量化。
- **7B 级模型工具调用不稳**。升到 14B 或换 function-calling 微调版改善明显；同时在工具描述里写清参数示例。
- **量化不是免费的**。Q4 以下在代码生成和长推理上能感知退化，关键链路用 Q5/Q6。
- **换 embedding 模型必须重建向量库**，旧向量直接作废。
- Windows 桌面本身占 1–2GB 显存，WSL2 里实测可用空间更少，规划时留余量。

## 可复用建议

- 存一版“显存→档位”速查：8GB→7B Q4；12GB→14B Q4；16GB→14B Q5；24GB→32B Q4。
- 本地主力 + 云端兜底做失败降级，模型选择放进 agent 配置，别写死在代码里。
- 基准测试用你自己的 agent 真实任务，别只看公开榜单分数。

## 总结

本地 LLM 已经能承担中等复杂度的 agent 任务，瓶颈不在推理速度，而在小模型的工具调用可靠性。落地上就三步：从 Ollama + 一个 14B 起步，用真实任务链做验收，把模型选择做成配置。跑通之后，你的 agent 就有了一个不按 token 计费、断网也能干活的本地方案。
