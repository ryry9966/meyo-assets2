## 背景

大多数人把 OpenClaw 的 agent 用成了“呼叫台”：你发消息，它才动。其实 OpenClaw 里有个容易被忽略的机制——**HEARTBEAT.md**。这个文件放在 workspace 根目录（默认 `~/.openclaw/workspace/HEARTBEAT.md`），agent 会按固定间隔（默认约 30 分钟，可配置）被“叫醒”一次，读取文件内容，然后自己决定要不要做点什么。

它的设计里有两个关键点：**文件为空时，这次心跳直接跳过、不调用模型，零成本**；agent 判断无事可做时可以保持沉默（约定的回复是 `NO_REPLY`），不会给你推消息。这两点决定了它和“定时任务轰炸机”是两回事。

## 问题

没有心跳的 agent 有个结构性缺陷：它只对“被问到的事”负责。磁盘快满了、证书要过期了、仓库三天没提交了——这些没人主动提的事，它永远不会管。用系统 cron 直接跑脚本虽然能巡检，但缺判断力：脚本只会机械报警，不会结合上下文掂量“这事值不值得现在打扰你”。

HEARTBEAT.md 补的就是这一层：一份用自然语言写的**值班手册**，每次心跳照着巡一遍。

## 怎么做

**1. 建文件，写规则，不是堆 TODO。** 推荐三段式：

```markdown
# 巡检项
- 检查 /srv 磁盘占用，超过 85% 才告诉我，附最大的三个目录
- 检查 workspace 是否有未提交改动，有就 git commit 一次

# 沉默规则
- 未命中上述条件时一律 NO_REPLY，不要汇报"一切正常"
- 23:00–08:00 只处理，不推送

# 临时任务
- （临时任务写这里，做完删掉）
```

**2. 配置频率。** 在 `~/.openclaw/openclaw.json` 里调整 `agents.defaults.heartbeat.every`（如 `"45m"`，字段名以你的版本文档为准）。分钟级以下的精确调度别用心跳，交给 cron。

**3. 观察一两个周期。** 看 gateway 日志确认心跳触发，重点检查它是不是“太话痨”——初次部署几乎都要回来补沉默规则。

## 踩坑点

- **话痨问题**：不显式写沉默规则，agent 容易每次心跳都汇报。第一次部署务必写明“无事则 NO_REPLY"。
- **成本**：心跳 = 定期模型调用。文件非空，每次都走一遍模型，所以巡检项要少而硬，别让它读整段日志。
- **共享会话**：心跳默认跑在主会话里，它做的 commit、写的记忆会延续到日常对话中——是特性也是风险，文件类操作务必幂等。
- **时区**：容器里多半是 UTC，“每天早上提醒”会错位。要么统一时区，要么把精确时间任务交给 cron。

## 可复用建议

- **低频巡检类**：磁盘/内存阈值、证书与域名到期、备份完整性——超阈值才说话。
- **维护类**：定期整理 MEMORY.md、清理过期的临时任务、给 workspace 自动提交。
- **摘要类**：每天一条非高峰时段的汇总，一天最多一条，宁缺毋滥。
- **一条原则**：每个巡检项 = 明确条件 + 明确动作 + 明确的说话/沉默边界。写不出这三样的，先别放进心跳。

## 总结

HEARTBEAT.md 的价值不在“自动化”本身——cron 早就有了——而在于**把判断权交给模型**：脚本只会执行，agent 会掂量。正确的使用姿势是克制：空文件省钱，沉默是常态，打扰必须是例外。从一两条低频巡检起步，跑一周再扩。
