## 背景

OpenClaw 允许同时挂多个模型 provider，典型的组合是：云端 GPT/Claude 负责推理，本地 Ollama 跑 qwen 或 llama 系列。动机无非三个：省钱、私敏数据不出域、离线可用。但很多人配完之后要么全走云（月账单难看，日历邮件全上传），要么全走本地（agent 循环频繁失败），最后不了了之。

## 问题

极端配置的真实代价：

- **全走云**：定时摘要、格式转换这类琐碎任务也烧 token，一个月下来大头都是低价值调用；私人数据被动出域，出问题才想起来。
- **全走本地**：复杂规划和多工具链任务上，本地模型的 function calling 质量不稳，工具调用吐不出合法 JSON，重试循环一开，时间成本远超省下的钱。

所以核心问题不是"选哪个模型"，而是**加一层显式的路由策略**。

## 做法

**1. 先给任务分类，不要拍脑袋。** 我的四分法：

| 任务类型 | 推荐 | 理由 |
|---|---|---|
| 多工具规划、复杂推理 | 云端 | function calling 稳定性优先 |
| 长上下文摘要 | 看长度 | 超本地窗口就走云 |
| 格式化、轻量改写 | 本地 | 质量足够，零成本 |
| 涉私数据 | 本地优先 | 必要时先脱敏再上云 |

**2. 配置层实现路由。** 简单场景用 OpenClaw 的 primary/fallback 模型链；规则复杂时在 OpenAI 兼容网关层按模型名前缀分流，agent 侧无感知。

**3. 规则优先于分类器。** 按任务类型标签、预估 token 数、关键词做 if 判断就够了。见过有人用 GPT-4o 给每次调用做"路由分类"，省的 token 还不够付分类的。

**4. 加观测。** 记录每次调用的模型、耗时、token 数、是否触发 fallback。没有这个数据，路由规则就是玄学。

## 踩坑点

- **本地模型窗口太小**：系统提示加工具 schema 就吃掉大半，4k 窗口的模型基本没法跑 agent 循环，本地至少 32k 起步。
- **本地不一定快**：7B 模型在 CPU 上一次回答 30 秒以上，体感反而不如云。路由规则里别写"本地=低延迟"。
- **fallback 方向要想清楚**：云挂了落本地没问题；反过来默认开"本地失败升云"会把复杂任务悄悄降级成"看似成功"，错误很隐蔽。
- **模型升级后规则会过期**：本地模型换版本后 function calling 行为可能变，旧路由规则要重测。

## 可复用建议

1. 先全云跑一两周，统计调用分布，数据会告诉你哪些任务值得迁本地，顺序别反。
2. 给本地路径留"逃生门"：重试超限或输出校验失败时自动升级到云，并打日志。
3. 私敏数据默认本地，宁可质量降一档，这个约束应该是硬性的。
4. 每月回看一次失败日志和账单，路由是持续调参，不是一次性配置。

## 总结

多模型路由的价值不在于省那点 token 费用，而在于把**数据出域、延迟、成本**这三个约束显式化，变成配置里可审计的规则，而不是散在各处的默认值。从最简单的规则路由开始，配好观测，再逐步精细化——工程上成立的做法往往不够聪明，但够稳。
