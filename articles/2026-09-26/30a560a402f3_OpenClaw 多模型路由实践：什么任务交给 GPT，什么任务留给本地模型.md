## 背景

跑了一段时间 OpenClaw 之后，账单和隐私是两个绕不开的问题。主力对话、复杂工具调用确实需要云端强模型，但 agent 体系里大量任务是"体力活"：定时摘要、日志归纳、消息分类、格式转换。这些全走 GPT，成本涨得很快；全压到本地模型，质量和工具调用稳定性又会崩。多模型路由要解决的就是分工问题，而不是单纯的省钱问题。

## 问题：路由不是省钱开关

我最初的配置很粗暴：primary 挂 GPT，fallback 挂本地 qwen2.5:14b。结果碰到两个典型故障：

1. 某次云端接口限流，任务静默落到本地模型，function calling 格式不对，agent 卡在重试循环，日志里只有模糊的 parse error。
2. 本地模型上下文窗口小，长输入被截断后它"自信地"继续输出，看起来格式正常，事实全错。

结论：路由的核心不是"优先用谁"，而是"什么任务配什么模型，出错时如何暴露"。

## 做法

我的落地分三步：

**第一步：按 agent 角色分层，而不是按单次请求分层。** 主对话和需要多轮工具调用的链路留在云端强模型；subagent 里的一次性任务（摘要、提取、打标签）切到本地。OpenClaw 支持在配置里按 agent 指定 model，比在脚本里写 if-else 干净得多：

```json
{
  "agents": {
    "defaults": { "model": { "primary": "openai/gpt-4.1" } },
    "list": [
      { "id": "digest", "model": { "primary": "ollama/qwen2.5:14b" } }
    ]
  }
}
```

（字段名以你当前版本为准，思路是按 agent 粒度控模型。）

**第二步：fallback 链要"降级可感知"。** 本地模型只作为显式指定的第二档，不要挂在自动 fallback 里吞错误。我在 cron 任务外面包了一层校验：本地模型输出缺少预期的 JSON 字段就直接告警，而不是让 pipeline 继续往下跑。

**第三步：记录每个任务的模型、耗时、token。** 跑两周后数据很直观：约七成调用量走本地，成本降了六成左右，摘要类任务抽样质量没有明显下降。这是继续扩大本地覆盖的依据，不是拍脑⽎。

## 踩坑点

- **工具调用是分水岭。** 本地模型对 function calling 的格式遵循参差不齐，凡涉及 MCP 工具、插件调用的链路默认回云端，纯文本加工才走本地。
- **上下文长度不是摆设。** 给本地模型的任务要在入口做裁剪，别指望它自己消化超长输入。
- **冷启动延迟。** Ollama / LM Studio 闲置后首次请求要重新加载权重，cron 类任务建议加预热或保活。
- **静默降级最危险。** 错误要显式抛出，宁可任务失败重跑，也不要拿到一份格式正确但内容错误的输出。

## 可复用建议

1. 两档起步（云端主力 + 本地廉价档），用数据说话后再加档位。
2. 路由规则全部放配置文件，禁止在代码里硬编码模型名。
3. 每类任务维护 10–20 条 eval 样本，换模型前先跑一遍对比。
4. 把"是否涉及工具调用"作为路由的第一判据，比"是否敏感"更可靠。

## 总结

多模型路由的真正价值，是逼你把 agent 的任务分型做清楚：哪些任务需要推理深度，哪些只需要格式正确。分型清楚了，模型选择、成本、可靠性都是自然结果。建议从摘要类 cron 任务切本地开始，稳定跑一周再扩大范围。
