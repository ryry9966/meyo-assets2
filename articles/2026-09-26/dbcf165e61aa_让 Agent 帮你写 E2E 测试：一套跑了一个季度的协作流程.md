## 背景

E2E 测试是性价比最难衡量的测试层：写起来慢、断言脆、DOM 一改就全线飘红，团队里真正愿意维护它的人通常只有一两个。Agent + MCP 改变了这件事的可行性——浏览器自动化能力（比如 Playwright MCP）可以直接挂在 Agent 上，让它自己打开页面、点按钮、观察结果，再把操作过程沉淀成测试代码。我们团队跑了约一个季度，把这套流程整理出来。

## 问题

直接丢一句"帮我写 E2E 测试"给 Agent，产出通常不可用：选择器靠猜、断言空洞、大量 `sleep`、甚至访问根本不存在的路由。根本原因是 Agent 缺两样东西：**真实页面状态的反馈回路**，和**一份明确的测试规范**。没有前者它在盲写，没有后者它在自由发挥。

## 做法

流程分四步：

1. **接工具 + 给规范**：给 Agent 挂上 Playwright MCP，限定只访问测试环境域名。同时在仓库的 AGENTS.md 里写清楚约定：选择器优先 `data-testid`、禁止显式 sleep、一个用例只覆盖一条用户路径、测试数据用 fixture 注入。

2. **先探路，再写码**：不让 Agent 直接写测试，而是先让它以"用户视角"走一遍核心链路（登录 → 核心操作 → 结果确认）。MCP 返回的截图和 DOM 快照就是它的眼睛。走通之后，让它把刚才**实际发生的操作序列**翻译成 Playwright spec。

3. **人审断言层**：实操下来，Agent 写的"操作"部分基本靠谱，但断言容易过松（只判断元素存在）或过紧（断言死的具体文案）。断言层必须人工过一遍，操作代码大多可以保留。

4. **闭环修错**：测试进 CI 后，失败时把 trace 文件路径丢回给 Agent，让它读 trace、定位原因、自己提修复 PR。这是协作价值最大的一步——E2E 的维护成本大头在失败后的排查，不在初写。

## 踩坑点

- **选择器回退到 nth/text**：拿不到 testid 时 Agent 会退而求其次，写出一堆脆弱选择器。解法是先给关键页面补 testid，再让 Agent 上手，顺序不能反。
- **Flaky 来自时序**：Agent 非常爱写 `waitForTimeout`。规范里明确禁止，要求用 `waitForSelector` / `expect` 轮询，flaky 率肉眼可见地降下来。
- **幻觉路由**：Agent 会对没访问过的页面编造路径。规定所有用例必须基于它实际走过的 MCP 操作记录生成，不接受凭空产出。
- **token 成本失控**：探索阶段截图 + DOM 快照很烧 token。给探索范围设页面白名单，限制每条链路最多 N 步。
- **测试数据污染**：并行跑时 fixture 互相冲突。让 Agent 统一用带随机后缀的数据工厂，每次运行自建自清。

## 可复用建议

- 测试规范写成仓库内的静态文档，Agent 每次自动读到，比在对话里反复强调有效得多。
- 定位清晰：**Agent 是作者，人是审者**。操作层外包，断言层必审。
- trace 回灌是闭环核心。没有这一步，Agent 写的测试挂了还是得人来查，协作意义减半。
- 优先覆盖钱和权限相关的链路，别指望 Agent 一次性补全所有页面。

## 总结

Agent 写 E2E 的可行解法不是"一键生成"，而是给它工具（MCP）、给反馈回路（截图 / DOM / trace）、给规范（仓库文档），然后把人放在断言审查的位置上。一个季度下来，E2E 从两个人维护变成"Agent 起草 + 任何人可审"，新增核心链路的测试成本降到原来一半以下。它没有消灭维护工作，只是把最枯燥的"写操作序列"外包了出去——这恰好是它擅长的部分。
