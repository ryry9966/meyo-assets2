## 背景

订阅源积了几十个：技术博客、周刊、GitHub Release、几个论坛板块。RSS 没死，死掉的是我的阅读时间——阅读器未读数常年四位数，真正点开的不到 5%。目标不是“读完”，而是让机器把每天值得看的内容挑出来、压成一条摘要，在固定时间推到我常用的 IM 里。

## 问题

拆开是三件事：

1. **聚合**：源格式不统一，不少站点 RSS 只给摘要，正文要另抓；
2. **成本与噪音**：每篇都过 LLM 既贵也没必要，大部分内容根本不值得摘要；
3. **交付**：摘要是消耗品，躺在文件里等于没做，必须推到随手可见的地方，而且最好能追问。

## 做法与步骤

管线分五段：**采集 → 入库 → 过滤 → 摘要 → 推送**。由 OpenClaw 的 cron 定时触发一个 skill 完成，模型调用封装成 MCP 工具，没有常驻服务。

1. **采集**。没有 RSS 的站点用 RSSHub 补齐。每 2 小时拉一次，按 GUID + 内容 hash 双重去重，失败单条记日志跳过。
2. **入库**。SQLite 一张表：feed、title、url、published、content、hash、score、summarized。原始内容先落库，摘要之后回填——采集与处理解耦，任何一步挂了都能重跑。
3. **过滤**。规则 + 便宜模型粗筛：关键词命中、来源权重、时效。低于阈值的直接不进大模型，这一步通常砍掉 60%~70% 的量。
4. **摘要**。过批不做单篇：10~20 条拼进一个 prompt，要求输出固定 schema 的 JSON 数组（title、url、one_liner、why_care），校验通过才入库。再做分层汇总：单篇摘一篇一档，每日摘要把当天结果再压一档。
5. **推送**。渲染成一条消息发到 Telegram。对某条感兴趣就回复编号，agent 再去拉全文展开——追问能力是这条管线最值钱的部分。

skill 配置大致长这样：

```yaml
schedule: "0 8,20 * * *"
steps:
  - fetch_feeds   # 拉取 + 去重 + 落库
  - filter        # 规则打分，低于阈值跳过
  - summarize     # 批量摘要 + schema 校验
  - push          # 渲染并推送到 channel
```

## 踩坑点

- **只有 summary 的 feed**：优先解析 RSS 自带的 content 字段，缺失再抓网页；部分站点封固定 UA，换 UA + 随机间隔能解决大半。
- **脏 XML**：未转义实体、非法字符、非 UTF-8 都见过。别手写解析，用 feedparser 这类容错库；仍失败的记日志跳过，别让一条脏数据打断整轮任务。
- **去重失效**：同一篇会在多个源出现，甚至改标题重发。hash 只取正文规范化后的前 N 字符，标题改动就不影响。
- **成本失控**：源一多，单篇摘要模式账单直接起飞。坚持“先过滤、再批处理、最后分层汇总”，月成本能压到几块钱级别。
- **输出不稳定**：模型偶尔不守 schema。prompt 里给 schema、失败重试一次，再失败降级为纯文本，别让 digest 卡在格式上。
- **cron 时区**：默认 UTC，早上推送会错位，先确认运行环境时区。

## 可复用建议

- 采集、处理、推送三段解耦，每段幂等；坏一段不丢数据。
- 结构化输出 + schema 校验当作第一道防线，别指望模型的格式自觉。
- 过滤先于摘要，token 只花在值得的内容上。
- 原始内容单独落盘，摘要质量出问题时可以回放输入、离线重跑。

## 总结

这套管线核心就几百行脚本加 OpenClaw 的调度能力，胜在稳定可演进：换模型、加源、改推送渠道都是改配置的事。信息流管线比拼的不是单次摘要多聪明，而是能不能每天都可靠地跑完——先做到“每天都能收到”，再谈摘要质量。
