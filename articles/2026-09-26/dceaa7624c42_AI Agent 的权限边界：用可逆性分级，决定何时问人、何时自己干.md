## 背景

Agent 接上 MCP 工具、能读写文件、能调 API 之后，"让它自己干还是先问我"就从哲学问题变成了工程问题。社区里常见的两个极端：要么所有动作都要确认，Agent 沦为昂贵的自动补全；要么全放权，直到某天它把测试环境的表 drop 了才回头补权限。

## 问题

"事情重不重要"不是好的分级标准，太主观、每个团队口径都不一样。实践中更稳定的三个维度：

- **可逆性**：能不能撤销？git 里的文件改动可逆，删库、给客户发消息不可逆。
- **影响半径**：动作只碰 Agent 自己的 workspace，还是越过了机器边界（网络、生产环境、真实用户）？
- **出错代价**：判断错了，修复成本是多少？

三者组合决定分级，而不是指望模型"自觉"。

## 做法：四级权限模型

- **T0 全自动**：只读操作、沙箱内写入、幂等动作。直接干，不用问。
- **T1 干了再说**：workspace 内的可逆写操作（走 git 的文件改动、草稿 PR）。直接干，但全部留日志。
- **T2 先出方案再问**：越过机器边界的副作用操作——发消息、部署、调计费接口。先展示 diff / 执行计划，人确认一次后批量执行。
- **T3 永远问人**：不可逆 + 大半径：删生产数据、对外发送、花钱、改权限和凭证。

关键实现原则：**分级写在工具层，不是提示词里**。在 MCP 网关 / 工具调用层做白名单和参数校验，T2/T3 的工具走结构化确认回调。提示词规则会随上下文漂移，权限层不会。

另外要让"问"变得便宜：别问"我可以继续吗"，直接贴出将要执行的三条命令和一个 diff，人扫一眼就能批。T2 里的低风险确认尽量合并成一批，减少打断。

## 踩坑点

1. **规则只写在 system prompt 里**。长上下文或嵌套工具链下，模型会"忘"。必须在调用层兜底。
2. **确认疲劳**。问得太频繁，人会养成闭眼点"允许"的条件反射——这比不问更危险。宁可合并批量确认。
3. **模糊提问**。"是否继续？"没法审。没有 diff 和计划可看的确认，等于没确认。
4. **凭证不分级**。给 Agent 一个全能 token，分级行同虚设。T2/T3 动作应该用独立的、最小权限的凭证。
5. **提问丢状态**。多步任务中途停下来问人，恢复时上下文丢失。要把执行计划持久化，确认后从断点继续，而不是整个重跑。

## 可复用建议

- 默认拒绝一切越过机器边界的动作，从 T2 起步，观察一段时间再降级。
- 每周复盘 T1/T2 日志：某动作连续几周零事故，才考虑降一级；逐级降，不要跳。
- "问"和"通知"分开：T1 只需要事后汇报，别混进确认流打断人。
- 把分级规则沉淀成团队文档，每接一个新 MCP 工具，先归类再上线。

## 总结

权限边界 = 可逆性 × 影响半径 × 出错代价。一句话原则：能撤销的让它干，越边界的先出方案，不可逆的永远留给人。用工具层强制执行，用便宜的确认保持人在回路不疲劳。这套分级本身不复杂，难在持续运营——对 Agent 的信任，是一级一级挣出来的。
