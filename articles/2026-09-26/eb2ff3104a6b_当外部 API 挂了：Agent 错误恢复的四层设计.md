## 背景

跑过自动化 Agent 的人多半有体会：链路里最脆弱的一环往往不是模型，而是外部 API。搜索接口超时、第三方限流、自建服务半夜重启，都是常态。模型本身可以重试，但如果 MCP 工具层没有设计错误恢复，轻则任务卡死烧 token，重则 Agent 拿着一段错误信息"脑补"出结果继续往下跑。这篇文章把我们踩过的坑整理成一套可复用的四层防护。

## 问题：三种典型故障表现

1. **挂起**：没设超时，HTTP 请求悬着，整个任务队列被堵死。
2. **重试风暴**：失败就立刻重试，指数级烧钱，还可能触发对方更严的限流。
3. **幻觉兜底**：工具返回错误字符串，模型把它当成数据，编出一个看似合理的结论。

## 做法：四层防护

**第一层：结构化的错误输出。** 不要让工具抛裸异常或返回 HTML 报错页。约定统一 schema：

```json
{"ok": false, "error": "upstream_timeout", "retryable": true, "hint": "use cache or try later"}
```

让模型"看见"失败这件事，是一切后续策略的前提。

**第二层：超时 + 有穷重试。** 每个工具调用必须有连接和读取双超时。重试只针对 429、5xx 和网络错误，指数退避加随机抖动，上限 3 次左右。4xx 不要重试——那是参数问题，重试只会浪费配额。

**第三层：熔断。** 连续 N 次失败后直接 fail fast，一段时间内不再请求，之后用半开状态试探恢复。这保护的不只是对方服务，更是你自己的任务队列和 token 预算。

**第四层：降级路径。** 重试耗尽或熔断后，按业务决定：切换备用数据源、返回带时间戳的缓存并明确标注"数据可能过期"、或者跳过该步骤向用户如实说明。宁可信地失败，不可假地成功。

两个工程细节：非幂等操作（下单、支付、发通知）重试必须带幂等键；长任务做状态检查点，恢复时从断点续跑，而不是从头再来。

## 踩坑点

- 只重试不设上限，一个坏掉的 API 把当天 token 预算烧光；
- 重试作用在非幂等的 POST 上，用户收到两条一模一样的通知；
- 缓存兜底没标时效，下游把三小时前的数据当实时数据用；
- 熔断恢复瞬间所有 worker 一起打过去，刚复活的服务又被压垮（退避抖动要贯穿始终）；
- 把原始堆栈塞进模型上下文，错误日志污染推理质量。

## 可复用建议

给所有 MCP 工具统一包一层错误处理中间件：超时 → 分类 → 限次重试 → 熔断 → 降级，五个动作做成公共组件，不要每个插件各写一套。同时把错误 schema 写进 Agent 的系统提示词，明确告诉模型：遇到 `retryable: false` 就停止重试并汇报，不要自行发挥。

## 总结

外部 API 挂了不可怕，可怕的是 Agent 不知道它挂了，或者知道了还假装没事。错误恢复的本质，是把"失败"变成链路里的一等公民：显式、可分类、有边界、有出口。把超时、重试、熔断、降级这四层做扎实，你的自动化流程才敢在没人盯着的情况下跑过夜。
