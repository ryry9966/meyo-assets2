# 背景

OpenClaw 的 Agent 负载其实很杂：一段是日常问答和摘要，一段是多跳工具调用和长上下文推理，还有一段要处理本地私有文件。全走云端大模型，账单和延迟都难看；全走本地小模型，复杂任务又容易翻车。多模型路由要解决的就是这个"任务异构"问题——不同请求值得用不同的模型。

# 问题定位

我们团队的 OpenClaw 实例原先只挂一个云端模型，跑了一周后发现：约六成请求是低复杂度任务（格式转换、单工具调用、简单问答），token 花销却占了小一半；另涉隐私文件的处理被迫上云，合规上说不通。于是改成两档路由：云端 GPT 系列管"难活"，本地模型管"碎活"。

# 具体做法

1. 注册两个 provider：云端走 OpenAI 接口，本地走 Ollama（我们用 Qwen 14B，上下文开到 32k）。
2. 默认模型设为本地，云端配为 fallback；再给云端加一条显式路由规则：会话涉及私有目录、工具链深度超过 3 步、或上下文超过 16k 时切换。
3. 加一个轻量 router skill：入口先用本地小模型做一次任务分类（简单 / 复杂 / 涉隐私），结果写进会话元数据，主循环按元数据选模型。
4. 观测上给每轮回复记录 model 字段，一周后拉出来复盘各模型的接管比例与失败率。

# 踩坑点

- 本地模型上下文不够时，OpenClaw 会截断历史，工具调用格式容易损坏，表现为反复重试同一工具。务必确认本地模型的实际上下文 ≥ 会话典型长度。
- function calling 兼容性差异很大：部分本地小模型输出的工具参数 JSON 不合规，会卡进循环。路由判定里"工具链复杂"的权重必须高于"成本低"。
- 不要路由 embedding。RAG 的向量必须由同一模型生成，换了模型等于重建索引。
- 两档模型的 system prompt 行为要拉齐，否则切换时用户能明显感到"人格跳变"。
- fallback 别设无限重试：云端和本地都失败时，快速报错远好于静默循环。

# 可复用建议

- 按"能力"路由，不按"牌子"路由：长上下文、复杂工具链、强推理 → 云端；高频低复杂度、涉隐私 → 本地。
- 给每个模型维护一张能力卡（上下文长度、工具调用可靠性、延迟、单价），路由规则照着卡写，而不是拍脑袋。
- 从两档起步，等日志证明有必要再加第三档。一上来搭五层路由，调不动也查不了。
- model 字段的日志是路由调优唯一可信的依据，先有观测，再谈策略。

# 总结

多模型路由不是炫技，而是把成本、延迟、隐私三个约束显式化的工程手段。OpenClaw 的 provider + fallback + router skill 组合，足够支撑两档路由稳定落地。我们的经验浓缩成一句：先用日志摸清请求分布，再定路由规则；规则宁可粗一点，也不要抖。
