## 背景

E2E 测试是典型的“人人都知道该写、但没人愿意维护”的资产。我们仓库里 60 多条 Playwright 用例，每次改版导航结构，平均要手改十几个文件。今年开始把 agent 接进测试流程，跑了几个月，目前稳定在“人工写核心链路，agent 补长尾 + 修 flaky”的模式。

## 问题

直接丢一句“给这个页面写 E2E”给 agent，结果基本不可用：

1. agent 没见过真实 DOM，生成的选择器全靠猜，第一行就挂；
2. 断言要么形同虚设（只点了不验），要么过重（整页截图对比）；
3. 用例一多，整个站点结构塞不进上下文。

核心矛盾在于：写测试需要的不是“会写代码”，而是“知道页面长什么样、数据从哪来”。这两样恰好可以通过工具喂给它。

## 做法

我们用三个 agent 分工，通过 MCP 工具共享同一个浏览器会话：

**1. 探索 agent**：挂载 Playwright MCP（navigate / click / fill / snapshot / screenshot），按 PRD 摘要走一遍主流程。关键约束：只允许输出操作轨迹（每步动作 + 从可访问性快照里取到的 role 和 name），禁止直接生成代码。

**2. 编码 agent**：拿操作轨迹 + 团队选择器规范（优先 data-testid，其次 role + name，禁用 nth），把轨迹翻译成 Playwright 用例。测试数据统一走项目已有的账号池 fixture。

**3. 审查 agent**：只做静态检查——有没有硬编码等待、断言是否验证了业务结果而非 UI 细节、有没有重复登录步骤。只输出修改建议，不直接改文件，最终由人合入。

跑通后再加一层：CI 里失败的用例，把 trace + 报错 + 截图回喂给编码 agent，产出修复 diff 挂在 PR 上，人工确认后合入。flaky 自愈是这套流程里收益最大的部分。

## 踩坑点

- **别让 agent 读整页 HTML**。几百 KB 的 DOM 会撑爆上下文，且噪声极大。改用可访问性快照，体积小一个量级，语义还更准。
- **探索和编码必须拆成两步**。合并时 agent 会跳过“真实点一遍”直接脑补；拆开后它被迫先用工具。
- **等待策略要写进系统提示**。不约束的话，十个用例里能塞八个 `waitForTimeout(3000)`。
- **测试数据要接真 fixture**。agent 特别爱编造邮箱和订单号，本地能跑、CI 必挂。
- 生成的用例当作 PR review，不要直接合。前两周合进去的用例约三成是“看起来能过但什么都没验证”的。

## 可复用建议

- 工具集最小化：导航、点击、填表、快照、截图，五个够用，别一次塞几十个。
- 把选择器规范和断言规范写成一份短文档，三个 agent 共享同一段上下文，避免各写各的风格。
- 想清楚分工边界：我们长尾页面用例的维护时间从每迭代约 6 小时降到 1.5 小时，但核心链路仍然手写——agent 写的用例一致性不如人，别指望全托管。
- 修 flaky 的回喂链路单独建 PR 标签，方便统计 agent 修复的采纳率，低于五成就说明提示词或工具上下文有问题。

## 总结

Agent 写 E2E 的价值不在“零成本生成用例”，而在把最烦的两件事——补长尾场景和修 flaky——变成半自动流程。先接浏览器工具、拆开探索与编码、保留人工 review，这三点做对，剩下的就是慢慢调提示词和验收标准了。
