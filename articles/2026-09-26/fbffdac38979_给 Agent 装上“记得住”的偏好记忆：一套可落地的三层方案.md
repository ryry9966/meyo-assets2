## 背景

LLM 本身无状态，每次对话都是“失忆重启”。做 OpenClaw 这类常驻 Agent 时问题更明显：用户上周明确说过“部署用 pnpm 别用 npm”“报告写简体中文”，今天 Agent 又问一遍，体验直接崩掉。

上下文窗口再大也解决不了——不是因为装不下，而是“记在哪、何时取、何时忘”没有默认答案。最近我在自己的 Agent 上迭代了一版偏好记忆系统，把思路记下来。

## 问题：三种常见做法为什么不行

1. **全塞 system prompt**。所有历史偏好写进提示词，成本线性涨，大量过期记忆变成噪声，模型反而开始执行半年前的旧习惯。
2. **只做对话日志 + 向量检索**。对话里“事实”和“闲聊”混在一起，召回质量差；而且没有冲突处理，两条矛盾记忆同时命中时，Agent 行为随机摇摆。
3. **指望模型自己记得**。实测超过十几轮就丢，不讨论。

核心结论：记忆必须是显式的数据层，有独立的写、读、忘三条路径。

## 做法：三层结构 + 异步写入

存储分三层，SQLite 一张表就够起步：

- **L1 用户画像**：几十条以内的硬偏好（语言、时区、代码风格），每次构建 prompt 全量注入，预算控制在 500 token 内。
- **L2 偏好/事实库**：结构化条目，schema 大致是 `{content, scope, confidence, source, created_at, last_hit, hit_count}`。按相关度 + 时间衰减 + 命中频率打分，取 top N 注入。
- **L3 情景摘要**：会话结束后生成摘要并做 embedding，只参与检索，不常驻 prompt。

写入路径是关键。我踩的第一个坑是边聊边抽——抽取调用打断主对话，延迟明显。改成**会话结束后异步跑一次抽取**（规则兜底：用户显式说“记住 xx”的直接写，跳过 LLM），然后和库内条目做去重与冲突判定：

- 语义重复 → 合并，confidence +1
- 直接矛盾 → 新覆盖旧，旧条目标记 superseded 保留追溯
- 一次性语境（“今天先吃辣的”）→ 打 ephemeral 标签，默认不注入

读取在 prompt 组装时执行：按当前任务检索 L2/L3，低于阈值的宁可不带。**宁可少记，不可错记**——错误记忆比没有记忆伤害大得多。

## 踩坑点

- **没有遗忘机制**。前期只写不删，三个月后两千条，大量过时内容被召回。加了 last_hit 超 30 天自动降权、低 confidence 定期清理才稳住。
- **scope 没分层**。“用 pnpm”是全局偏好，“这个项目用 vitest”是项目级，混在一起会在别的项目乱触发。至少分 global / project / session。
- **记忆对用户不可见**。排查过一次“Agent 坚持用我不要的格式”，最后发现是三个月前一条错误记忆。必须提供查看/删除命令，这也是信任问题。
- **抽取 prompt 太宽**。一开始让 LLM“提取所有有用信息”，垃圾一堆。限定只抽显式偏好、稳定事实、纠正性反馈后，噪声少了一半。

## 可复用建议

- 起步别上向量库，SQLite/JSON + 关键词先跑通闭环，量大了再升级。
- 把记忆写入做成独立 MCP 工具暴露给 Agent，让它能主动调 `remember`，比纯后台抽取多覆盖一类显式表达。
- 建一个 20 条左右的回归问题集（“我用什么包管理器？”），每次改检索逻辑跑一遍，别凭感觉调参。
- 合并/衰减/清理做成定时 consolidation 任务，别依赖在线逻辑。

## 总结

偏好记忆的本质不是“存得多”，而是**写入时机克制、读取带打分、有遗忘与冲突处理、对用户透明**。先用最简单的结构把写-读-忘闭环跑通，再逐步提升检索质量。Agent 的可信度，很大程度上取决于它“不记得错的东西”。
