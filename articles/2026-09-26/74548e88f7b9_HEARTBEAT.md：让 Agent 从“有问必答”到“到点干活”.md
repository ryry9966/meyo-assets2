## 背景

大多数人用 Agent 仍是“一问一答”：你发消息，它回复，会话结束一切归零。但自动化场景里最有价值的，往往是没人提问时也该发生的事——每天早上汇总 CI 失败、仓库出现新 issue 就提醒你、周五下午生成本周变更清单。

OpenClaw 用一个很轻的机制解决这件事：心跳（heartbeat）。Agent 每隔一段时间被唤醒一次，读取工作区里的 `HEARTBEAT.md`，按其中指令决定“要不要做事、要不要说话”。文件为空或标记为无需处理时直接跳过，一次模型调用都不花。

## 问题

把“主动”做对并不容易。朴素做法是写个 cron 每小时调一次模型，但很快会遇到三个问题：

1. **没有常设指令**：每次唤醒都是新会话，模型不知道自己该干什么；
2. **控制不了沉默**：没事干也硬要回复，消息轰炸比不干活更糟；
3. **状态不持久**：做过的检查、上次的结论，下次醒来全忘了。

`HEARTBEAT.md` 本质上是把这三件事压进一个文件：常设指令 + 行为约定 + 可由 Agent 自己维护的状态。

## 做法

最小可用配置五步：

1. 在工作区根目录建 `HEARTBEAT.md`；
2. 写入检查项，每项结构化：触发条件（如“工作日 9 点后”）、数据来源（MCP 工具或命令）、动作与输出格式；
3. 明确沉默规则：所有条件都不满足时回复 `NO_REPLY`，不产生任何推送；
4. 调整间隔（默认约 30 分钟，`heartbeat.interval` 可改），高频检查建议换小模型；
5. 让 Agent 完成任务后自己更新该文件（打勾、写结论），你通过 git diff 审查。

一个我实际在跑的例子（节选）：

```markdown
## 检查项
- [ ] 工作日 9:30 后：拉取仓库新 issue/PR，按 repo 分组摘要
- [ ] 每天 18:00：汇总今日 commits，生成三句话日报
- [ ] 异常触发：CI 连续失败 ≥2 次，附日志前 20 行

## 规则
- 无匹配项：回复 NO_REPLY
- 结论写入本文件状态区，过期条目删除
```

## 踩坑点

- **指令太模糊**。“帮我盯着仓库”这种写法，Agent 要么不动要么瞎动。每个检查项都要能回答：什么条件、查什么、输出到哪。
- **成本失控**。检查项数量 × 频率 = token 消耗。先跑一个检查项观察一周再加；心跳这种常驻任务换便宜模型，收益立竿见影。
- **时间感不可靠**。模型对“现在几点”并不总准，条件判断前让它先用工具取当前时间。
- **静默失败**。工具报错时心跳可能悄悄空转。加一条检查项：异常写进独立日志，每周自我巡检一次。
- **文件变垃圾场**。`HEARTBEAT.md` 只放周期性主动任务；身份与长期规则放 SOUL.md / AGENTS.md，临时资料放普通文档。混在一起，Agent 的注意力会被稀释。

## 可复用建议

- 固定四段结构：状态区 / 检查项 / 输出规则 / 变更日志，人和 Agent 都好维护；
- 工作区纳入 git：你 review diff，Agent 提交变更，等于免费拿到审计日志；
- 数据源优先走 MCP，别在文件里写死路径和密钥；
- 观测两个指标：每天实际心跳次数、其中 `NO_REPLY` 占比。沉默占比掉到 50% 以下，通常是检查项太多或太宽。

## 总结

`HEARTBEAT.md` 只是一个 markdown 文件，但它把 Agent 的交互模型从“拉”改成了“推”：你不再需要记得去问，Agent 到点自己巡检——有事说话，没事闭嘴。把它当成给 Agent 写的一本 SRE runbook：条目具体、规则明确、持续迭代，它就能从聊天工具变成真正跑在你机器上的自动化同事。
