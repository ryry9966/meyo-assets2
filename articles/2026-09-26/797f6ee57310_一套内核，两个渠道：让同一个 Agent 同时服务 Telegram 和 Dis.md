## 背景

我们的社群长期同时分布在 Telegram 和 Discord 上。最初的方案很直接：给每个平台各跑一个 Agent 实例，各自配置、各自记忆。跑了两个月，问题开始显现——同一个用户在两边问同一个问题，得到两套不一致的回答；提示词改了一版忘了同步另一边；token 成本直接翻倍。于是我们把两个实例合并成共享一个内核的 Agent，中间加了一层消息路由。这篇文章记录改造思路和踩过的坑。

## 问题拆开看

跨平台不是“多接一个 SDK”的问题，真实成本在三处：

1. **协议差异**：Telegram 是 Bot API（long polling / webhook），Discord 是 Gateway WebSocket + REST。心跳、重连、限流模型完全不同。
2. **消息模型差异**：Markdown 方言、mention 格式、回复引用结构、附件类型（语音、贴纸）都不一样。
3. **会话与身份**：同一用户在两个平台是不同 ID，session key 怎么定、状态存哪里，直接决定这个“一个 Agent”是不是真的一个。

## 做法

核心原则一句话：**适配层只做翻译，不做业务。**

**第一步：定义统一信封。** 所有入站消息归一化为内部结构：渠道标识、发送者身份、纯文本、附件引用、回复指向、时间戳。附件不传原始文件，统一落对象存储后传 URL。

**第二步：写两个薄适配器。** 各只负责两件事——入站归一化、出站渲染。Telegram 侧处理 MarkdownV2 转义和 4096 字符切分；Discord 侧处理 2000 字限制、mention 格式和 reply 结构。适配器无状态，入站消息先进队列，挂了重启不丢数据。

**第三步：路由与会话层。** 在 OpenClaw 里让两个 channel 指向同一个 agent workspace，关键是 session key 的生成规则：我们默认用 `渠道:平台用户ID`，身份打通不做自动合并——同一自然人在两边的账号需显式绑定指令确认，避免误合并。

**第四步：内核保持平台无感。** Agent 内核和 MCP 工具链看到的永远是统一信封，出站时把结构化内容交给对应适配器渲染。限流用一条简单的 FIFO 队列吸收，Discord 侧按频控节奏发送。

## 踩坑点

- **别透传 Markdown。** LLM 输出直接塞给 Telegram MarkdownV2，转义错误率极高（下划线、点号都要转义）。正确做法是内核输出结构化内容，适配器各自渲染。
- **切分按平台限制来。** 4096 和 2000 的差异是小事，但切分点必须避开代码块中间，否则渲染全乱。
- **Discord 交互确认只有 3 秒窗口**，长任务先 ack 再异步补发，否则用户会看到“交互失败”。
- **不要让两个进程 poll 同一个 Telegram bot token**，会互相抢 update；用 webhook 则要处理幂等，Telegram 会重推。
- **同一用户双端并发**：两边同时发消息时按 session key 排队串行处理，避免记忆写入竞争。

## 可复用建议

- 统一信封 schema 加版本号，日后接 Slack、微信等渠道只写新适配器，内核零改动。
- 每条消息日志带 `渠道:trace_id` 前缀，跨平台排障效率提升明显。
- 每个渠道留 dry-run 开关，新渠道灰度时先只记录不回复。
- 适配器越薄越好——任何业务判断出现在适配层里，都是设计味道。

## 总结

改造后两个平台共享同一份记忆、同一套工具、同一份提示词，行为一致性和成本问题同时解决，代价是多了几百行适配代码和一条队列。结论很简单：**让平台差异死在边界上，别让它渗进 Agent 内核。** 渠道以后还会加，内核不需要为此改一行。
