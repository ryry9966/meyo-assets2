## 背景

AGENTS.md 是一个正被越来越多 Agent 工具采用的约定：在工作区根目录放一个同名 Markdown 文件，Agent 每次启动会话时自动读取，作为对这个工作区的先验知识。可以理解为 README.md 的镜像——README 写给人看，AGENTS.md 写给 AI 看。OpenClaw 的 agent 加载工作区时会优先消费这份文件，它直接影响 Agent 的每一次决策。

## 问题

实际用下来，Agent 最常见的翻车不是能力不行，而是缺上下文：

- 每次会话都要重新交代"用 pnpm 别用 npm""测试先跑 tests/unit"；
- 生成代码风格和仓库既有约定不一致，review 负担转嫁到人；
- 乱动不该动的目录（构建产物、锁文件、本地配置）；
- 同类错误反复出现，靠聊天记录纠正，换个会话就忘。

本质是同一个问题：工作区的隐性约定没有被固化成 Agent 可消费的显性输入。

## 做法

我们的 AGENTS.md 固定为六段，全文控制在 80 行以内：

1. **项目概览**：三五句话说清这是什么、技术栈、入口在哪；
2. **常用命令**：构建、测试、lint 的准确命令，保证可直接复制执行；
3. **目录约定**：哪些目录放什么，新文件应该落在哪；
4. **代码规范**：只写仓库特有的约定，通用规则交给 lint 工具；
5. **禁区清单**：明确列出不要修改的路径和文件类型；
6. **工具与 MCP 说明**：可用插件、MCP 服务的调用前提和已知限制。

维护方式比内容更重要：Agent 每犯一次同类错误，就把纠正写成一条规则；同一个错误出现第二次，必须沉淀进 AGENTS.md。这个文件本身进 git，改动走 PR review，和代码同权重。

## 踩坑点

- **写太长**。它占的是每次会话的上下文，超过百行后 Agent 会漏读重点，精简比全面有用。
- **写废话**。"写高质量代码""注意安全"这类不可验证的指令等于没写。每条规则都应可对照检查，比如"提交前跑 `pnpm lint` 并保证零报错"。
- **规则冲突**。迭代几个月后常出现前后矛盾的条目，Agent 表现会变得不稳定，需要定期清理。
- **关键信息只放在链接文档里**。Agent 不一定会主动去读被引用的文件，硬性约束要直接写在 AGENTS.md 正文里。
- **环境耦合**。写死绝对路径或本机特有的环境变量，换台机器就失效，统一用相对路径和通用命令。

## 可复用建议

- 把 AGENTS.md 当"规则集"而不是"文档"：祈使句、一行一条、可验证；
- monorepo 可在子目录放嵌套的 AGENTS.md，只写该子包特有约定，根文件保持全局规则；
- 团队约定一个触发信号：谁在 review 里说"Agent 又……"，就有人负责补规则；
- 每次升级 OpenClaw 或更换模型后，跑一轮老任务回归，观察是否有规则失效。

## 总结

AGENTS.md 的价值不在文件本身，而在于把"人肉纠错"变成"规则沉淀"。它的成本极低——一个 Markdown 文件——但要求团队把它当作和 CI 配置同级的工程资产来维护。写好它的过程，其实就是把工作区隐性知识显性化的过程，这件事对人和 AI 都有收益。
