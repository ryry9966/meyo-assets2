## 背景

OpenClaw 的 agent 每次启动都会读取工作空间里的 `AGENTS.md`（默认在 `~/.openclaw/workspace/` 下），并把它注入上下文。换句话说，这是唯一一份"每一轮都在场"的稳定指令：模型换了版本、会话开了又关，这份文件始终生效。它更像新人入职第一天拿到的工作手册，而不是一份写完就能忘的配置。

## 问题

没有 AGENTS.md，或者写法不对时，症状很固定：

- agent 每次把笔记建在不同位置，目录约定靠猜；
- 输出风格漂移，今天简洁明天啰嗦；
- 同一个坑反复踩，尤其是工具调用顺序这类流程问题；
- 反过来，有人把所有偏好全堆进去，几千行下去，关键规则被稀释，每轮 token 开销也不小。

## 做法

**1. 分层放置。** workspace 根目录放一份全局 AGENTS.md；子目录可以放更具体的版本，就近生效。如果 workspace 里跑多个项目，每个项目根目录再各放一份。

**2. 内容写五块就够：**

- **身份与边界**：替谁办事，哪些操作必须先确认；
- **空间地图**：`notes/`、`docs/`、`tmp/` 各放什么，文件命名约定；
- **工具约定**：什么场景优先用哪个 skill / MCP 工具，调用前检查什么；
- **硬性规则**：删除、对外发送、涉及费用的动作必须过确认；不允许写入密钥；
- **输出风格**：语言、格式、长度的默认值。

**3. 写成可判定的短规则。** 一条一行，是操作规程而不是散文。"写入 notes/ 前先确认同名文件是否存在"远比"请注意整理文件"有用。

**4. 错误驱动迭代。** 行为不符合预期时，把失败案例翻译成一条新规则补进去。用 git 管理这份文件，每条改动留一行注释记录日期和原因。

一个我实际在用的骨架：

```markdown
# AGENTS.md
## 身份
- 中文回复；技术名词保留英文
## 空间约定
- 笔记进 notes/，按 YYYY-MM-DD-topic.md 命名
- 临时产物一律进 tmp/，可随时清理
## 硬性规则
- 删除文件、对外发送消息前，先复述操作内容并等确认
- 禁止在文件中写入任何密钥
```

## 踩坑点

- **写成简历。** 段落式的自我介绍模型基本不遵守，可判定规则才有效，总量控制在几十行。
- **上下层规则打架。** 根目录说"默认先搜索"，子目录又说别的，行为就随机。正确姿势是上层写默认、下层只写例外。
- **当成记忆用。** 一次性事实进 memory/notes，手册只放长期约定，否则很快膨胀失效。
- **塞敏感信息。** AGENTS.md 全量进上下文，也会随 workspace 备份、同步，密钥只放环境变量。
- **写完不管。** 过时的地图比没有地图更危险——agent 会按它自信地走错路。

## 可复用建议

- 每次踩坑先问一句：这条写成 AGENTS.md 里的规则能防住吗？能就写进去，别指望下次口头提醒。
- 详细用法交给各 skill 自己的文档，AGENTS.md 只回答"什么时候用、多个 skill 怎么选"。
- 每月花十分钟通读一遍，删掉没再触发的规则。手册和代码一样需要瘦身。

## 总结

AGENTS.md 的价值不在写了多少，而在于它是唯一每轮必然生效的注入层。把它当成一份持续维护的操作手册——短、可判定、随失败迭代——agent 的行为稳定性会有肉眼可见的提升。如果你的 workspace 还没有这份文件，建议今天就建一个，从十条规则开始。
