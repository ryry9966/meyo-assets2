## 背景

社区日常有几类重复劳动：每周精华帖整理、GitHub issue 动态同步、定期技术周报。人工做太耗时间，于是我用 OpenClaw 搭了一个发帖机器人，跑了六周、发帖 80+，翻车 3 次。这篇记录架构与踩坑，供有同样需求的伙伴复用。

## 问题定义

动手前先明确约束，这决定了后面所有设计：

- **输入不稳定**：RSS、GitHub API、站内数据格式各异
- **输出要求高**：LLM 直接生成的内容可能编造链接，语气容易飘
- **社区有频控和反垃圾机制**，不能当批量接口打
- **出错成本高**：帖子发出去再撤，很难看

## 架构：五段式流水线

整体是「定时触发 → 采集 → 生成 → 审校 → 发布」，Agent 本体只做编排：

1. **触发层**：cron 每 6 小时跑一次，加文件锁防止重复触发
2. **采集层**：每个数据源封装成独立的 MCP 工具，RSS 一个、GitHub 一个，输出统一 JSON schema
3. **生成层**：Agent 拿结构化素材生成草稿，prompt 明确禁止编造 URL，只允许引用素材里已有的链接
4. **审校层**：草稿先落 SQLite 置为 pending，跑规则校验（链接可达性、长度、去重哈希），再进人工审核队列
5. **发布层**：审核通过后调社区 API 发布，记录 post_id 与内容哈希作为幂等键

关键决策只有一条：**Agent 无状态，所有状态进数据库**。机器人挂了重启即可，不丢任务。

## 踩坑实录

1. **LLM 编造引用**。第一版允许它“自由补充背景”，结果生成了一个看起来很合理但不存在的博客链接。修复：链接必须来自采集层原始数据，发布前用正则提取所有 URL 逐个 HEAD 验证，404 直接打回。
2. **重复发帖**。cron 偶尔重叠触发，同一条周报发了两次。修复：启动时抢文件锁，发布前用内容哈希查库，命中即跳过。
3. **Markdown 转义**。标题里的下划线和反引号进了模板后被渲染器吃掉，格式错乱。修复：发布前统一过一遍转义函数，不要信任 LLM 输出的格式。
4. **token 权限过大**。最初图省事用了管理员凭据，审计时吓一跳。修复：单独申请仅发帖权限的账号，凭据走环境变量，日志脱敏。
5. **没有 dry-run**。前两周每次调试都在真实发帖。后来加了 `DRY_RUN` 环境变量，所有写操作只打日志不落库不发，调试成本直线下降。

## 可复用建议

- **工具粒度宁小勿大**：一个 MCP 工具只干一件事，排障时能立刻区分是采集问题还是生成问题
- **发布层必须幂等**：内容哈希 + 外部 post_id 双重记录
- **保留人工审核兜底**，至少前一个月别全自动
- **全链路带 run_id**：采集、生成、发布共用同一个 id，出问题一查到底

## 总结

这个项目里 LLM 反而是最简单的部分，真正的工作量在状态管理、幂等和失败处理。自动化的价值不在于省下发帖那两分钟，而在于流程被代码固化之后，内容的质量和节奏变得可预期。模板代码已整理好，欢迎评论区交流你的踩坑经历。
