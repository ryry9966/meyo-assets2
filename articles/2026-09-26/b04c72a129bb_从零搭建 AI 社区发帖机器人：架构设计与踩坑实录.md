### 背景

社区有几个固定栏目（每周精选、版本速递、答疑汇总），过去一直人工整理再发帖，单次耗时 40 分钟起步，还经常拖更。这次目标很明确：让 OpenClaw agent 承担「选题 → 初稿 → 排版」的流水线，人只在最后做一次审核。不是要做全自动无人值守，而是先把重复劳动砍掉。

### 问题定位

最直接的思路是「agent 生成完直接调 API 发出去」，试了一周就放弃了，三个问题：

1. 质量不稳定，偶尔出现编造的链接和过期的版本号；
2. 素材池更新后，同一话题会被反复改写重发；
3. 本地预览正常的 markdown，到社区渲染端代码块会坏。

所以架构上必须把「生成」和「发布」拆开，中间加一层可观测的校验。

### 架构与实施步骤

整体是三段式流水线：

**素材池**：cron 任务每天凌晨跑一次，通过 MCP 工具抓取仓库 issue、精华讨论、更新日志，清洗后写入本地 SQLite，字段包括 `source_url`、`content_hash`、`status`（初始 raw）。抓取用 ETag 做增量，避免全量重扫。

**草稿生成**：按 `status=draft` 取素材，先做相似度过滤（embedding 与最近 20 篇已发帖比对，阈值 0.85），再套模板 prompt 生成 markdown 初稿。prompt 里显式约束：禁止编造链接，引用必须来自素材原文。

**校验与发布**：规则校验（长度区间、代码块闭合、外链白名单）+ 中低分档触发一次 LLM 自审打分。通过的进 approved 队列，人工在管理面板确认后，由发布插件调社区 API。发布请求带客户端生成的幂等键，重试上限 3 次，超限告警转人工。

### 踩坑实录

- **渲染不一致**：社区端对嵌套代码块的处理与本地不同，正文出现两个 ``` 会吃掉后半段内容。现在发布前会拉一次渲染结果做快照比对，不一致直接打回。
- **时区漂移**：cron 跑在容器里是 UTC，国内读者的「早上八点」变成了下午。改为任务内显式指定时区，执行开头校验当前小时，不在窗口内直接退出。
- **重复发帖**：标题改写让 `content_hash` 失效，同一素材二次入池。最终方案是 embedding 相似度 + 近 N 篇标题比对双保险，光靠 hash 不够。
- **重试不幂等**：API 超时后重试导致双发。加幂等键之前先用「先查后发」过渡，别赌服务端帮你去重。
- **token 成本**：全量 LLM 自审烧钱明显。改成只有规则校验落在中分档才触发复审，成本降了七成。

### 可复用建议

1. 状态机五态：`raw → draft → reviewed → approved → published`，每一步可回退，出问题能定位到具体环节。
2. 人工审核前两周别省，攒够 badcase 再逐步放宽阈值。
3. 所有外部调用打结构化日志（输入摘要、耗时、状态码），排障靠回放而不是猜。
4. 凭据走环境变量或密钥管理，别写进 agent 的 system prompt。

### 总结

这类机器人的难点不在「让 agent 写出帖子」，而在把发布变成可控、可回滚、可观测的流程。生成只占两成工作量，剩下八成是校验、幂等和排障。把状态机和审核环节做扎实，自动化才敢往前推。欢迎在评论区交流你们的流水线设计。
