## 背景

绝大多数 agent 的使用模式是"拉"式的：人提问，模型回答，会话结束。OpenClaw 生态里大家接了不少 MCP 工具，但大部分场景仍是用户主动发起。真正的 proactive，是指助手能在没人开口的情况下，基于事件、时间或状态变化自主发起一轮任务——早上自动汇总昨晚 CI 失败原因，磁盘告警触发时先收集上下文再决定是否打扰你。

技术上这事不难，难在两个问题：什么时候该主动，主动到什么程度。

## 问题

把触发器和模型直接焊在一起，通常会出三类事故：

1. **触发风暴**：agent 的动作本身产生新事件（比如它发了条消息，消息又进了监控队列），形成循环；
2. **越权执行**：为了让它"能办事"，一开始就给了写权限，一次误判直接改了线上配置；
3. **成本失控**：每个触发点都是一轮完整推理，高频事件源一天跑掉一周的 token 预算。

## 做法

我的方案是把 proactive 拆成三层，触发层完全用确定性代码写，不让 LLM 参与：

**1. 触发层**。cron、webhook、文件 watch、MCP 资源轮询都行，关键是三要素：事件源 + 判定条件 + 去重键。判定条件用规则（阈值、状态变化），去重键保证同一事件只触发一次。比如 CI 失败事件，以 `repo+branch+commit` 作为去重键。

**2. 执行层**。触发后组装上下文（事件数据 + 最近相关状态）喂给 agent 跑一轮。这一轮里 agent 只做判断和调度：查日志、读指标、决定下一步。MCP 工具按风险分级——只读工具直接放行，低风险写操作执行后落审计日志，高风险写操作只生成"提案"，等人确认。

**3. 反馈层**。每轮主动运行写一条记录：为什么触发、用了什么上下文、做了什么决定、结果如何。这是后续调整触发条件的唯一依据，别省。

上线顺序建议：先跑"只报告不动手"模式一两周，人工核对其判断是否靠谱，再逐步放开低风险写权限。

## 踩坑点

- **循环触发**：agent 的输出如果会回流到事件源，必须加环路检测。简单办法是给事件打来源标记，来源是自己的事件默认丢弃。
- **重试与幂等**：网络抖动导致的重试，可能让"发一条通知"变成三条。所有写操作带幂等键。
- **静默时段**：没有 quiet hours 的主动通知撑不过三天就会被用户关掉。非紧急事件攒批，到点一起报。
- **上下文过期**：主动运行发生在用户不在场时，别假设它知道你五分钟前的口头决定。关键上下文要么落库，要么这轮就别做。
- **权限只升不降**：写权限一旦给了就很难收回，宁可从提案模式开始，多等几天。

## 可复用建议

- **动作三分类 + 三门槛**：只读/低风险写/高风险写，对应放行/审计/提案。这套矩阵几乎可以直接抄进任何 agent 项目。
- **触发逻辑留在代码里**，LLM 只负责触发后的判断。让模型决定"何时主动"，等于把稳定性交给概率。
- **预算先行**：给每个触发源设每日推理上限，超限降级为只记录不执行。

## 总结

proactive 不是给模型加一个"主动人格"，而是一套工程系统：可靠的触发层、分级授权、完整审计。模型的价值在于触发之后那一步的判断质量，而不是决定什么时候触发。先把报告模式跑稳，再谈放手办事。
