## 背景

把 OpenClaw 跑过一段时间，你多半见过这类现象：定时任务偶尔重复触发、Agent 在工具调用超时后自动重试、插件对同一条 Webhook 事件处理了两遍。这不是偶发 bug，而是自动化系统的常态——网络抖动、进程重启、Agent 重新规划，都会让"同一步"执行不止一次。底层能承诺的最好语义是 at-least-once：至少送达一次，但不保证只送达一次。

## 问题

典型场景：cron 任务每天九点把日报发进群，实际发送成功但确认超时，框架判定失败并重试，群里出现两条一模一样的日报。写操作更麻烦：Agent 调用 MCP 插件"创建工单"，插件已执行成功，只是响应丢失，重试之后就多出一张重复工单。

重复执行本身不可怕，可怕的是副作用被叠加。幂等性要解决的就是这件事：**同一个操作执行一次和执行多次，最终效果一致。**

## 做法：幂等键 + 执行记录 + 唯一约束

核心思路：给每个业务动作定义一个稳定的幂等键，执行前抢占、执行后落账，用唯一约束兜底。

1. **定义幂等键**。用业务语义拼装，比如 `hash(任务ID + 业务日期 + 目标ID)`。不要用随机 UUID 或时间戳——那会让每次重试看起来都像新任务。
2. **落库去重**。建执行记录表，幂等键加唯一索引。执行前先 INSERT，冲突说明做过，直接返回上次结果。靠约束兜底，而不是只靠"先查后做"。
3. **优先天然幂等的写法**。能用 upsert 就不用 insert，能用"把状态置为目标值"就不用自增，删除按唯一键删。改写比事后补救便宜。
4. **外部调用**。对方 API 支持 Idempotency-Key 就一定带上；不支持就记录"请求-响应"对，重试前先查历史。
5. **处理中间态**。记录要有 running / success 状态，running 超过租约时间才允许被接管，避免两个实例同时接手。

伪代码大致是：

```text
key = hash(task_id, biz_date, target_id)
if insert(exec_record, key) conflicts:
    return last_result
do_side_effect()
mark_success(key)
```

## 踩坑点

- **用时间戳或随机 UUID 当幂等键**：重试永远被判为"新"，等于没做。
- **只查不约束**："先查后执行"存在竞态，两个并发实例可能同时通过检查。查询只做快速路径，唯一约束才是保底。
- **副作用成功、记录失败**：进程恰好死在两步之间。最好让副作用和记账在同一事务里；做不到就先写记录（标记 running）再执行。
- **把幂等当成并发安全**：去重解决的是顺序重试，并发冲突仍需要锁或租约。
- **忽略补偿任务**："清理临时文件"天然幂等，"追加一行统计"不是，后者重跑会把数算重。

## 可复用建议

- 评审新的定时任务或 MCP 工具时，把"幂等键是什么"当第一问，答不上来就先别上线。
- 把去重逻辑抽成公共装饰器或中间层，所有插件复用，不要每个任务各写一套。
- 对"发消息"这类不可撤销的外部操作，保留最近 N 次请求指纹，重试前先比对。
- 把"重复跳过率"做成监控指标：长期为零说明可能缺少重试路径，突然升高说明上游不稳。

## 总结

重试不是异常，而是自动化的默认行为。幂等性做的事情，是把底层的 at-least-once 变成业务上的 effectively-once。记住三件事：业务语义的幂等键、唯一约束兜底、天然幂等写法优先。做到之后，cron 重跑、Agent 重试、Webhook 重投，就只是日志里的普通一行，而不是群里多出来的那条消息。
