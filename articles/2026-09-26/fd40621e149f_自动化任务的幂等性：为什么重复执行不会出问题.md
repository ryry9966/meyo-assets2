## 背景

跑过一段时间自动化的人几乎都遇到过同一个现象：任务明明"只该执行一次"，日志里却出现了两次、三次。原因通常很朴素——cron 触发重叠、Webhook 超时重发、Agent 某一步超时后上层重跑、插件网络抖动后客户端重试。在长链路自动化里，"至少一次"投递是常态，"恰好一次"反而是需要自己构造的保证。

## 问题

幂等性（Idempotency）指同一操作执行一次和执行多次，最终状态一致。不满足幂等的任务，重复执行会表现为：通知群收到两条相同的日报；数据库同一记录插了两行；文件被重复追加；下游 API 因重复调用触发限流。更隐蔽的是"半成功"：上次执行写了一半挂掉，重跑时逻辑分支走偏，留下脏数据。

## 做法

给任务加幂等性，实践上可以拆成四步：

1. **定义幂等键。** 用任务的"业务身份"，而不是时间戳或随机 ID。比如"每日日报"的键是 `日期 + 目标频道`，"同步某仓库 issue"的键是 `repo + issue_id`。同一次重试天然共享同一个键。
2. **把状态落在可查询的地方。** 执行前先查：这个键处理过吗？结果是什么？用一个持久化账本（数据库表、SQLite，甚至带文件锁的 JSON）记录键、状态、完成时间。
3. **让写入操作可重放。** 数据库写入用 upsert 或唯一索引兜底；文件操作用覆盖代替追加；发消息前先比对上次已发送内容。
4. **把唯一性约束放存储层。** 代码层的"先查再写"有并发窗口，唯一索引才能在两个 worker 同时跑时保证只有一条成功。

## 踩坑点

- **用 UUID / 时间戳当幂等键。** 每次重试生成新键，等于没做幂等。键必须来自业务语义。
- **记账和干活不是原子的。** 先记账后执行，崩在中间就是"账上有、事没办"。要么放进同一事务，要么设计成"先干活、后记账，执行前检查产出物"。
- **状态文件非原子写。** 直接覆写 JSON，进程中断会留下半个文件。先写临时文件再 rename。
- **只防了重复，没防并发。** 幂等键解决先后重复；两个实例同时跑还需要文件锁或分布式锁。
- **重试叠加。** 上层 Agent 重试 + 任务内部重试，指数放大。重试只留一层，其余靠幂等兜底。

## 可复用建议

- 所有定时 / 事件驱动的插件任务，默认按"至少一次投递"设计，幂等是标配而不是优化项。
- 幂等键 = 业务身份，键设计先于代码；账本持久化，别放内存。
- 能 upsert 不 insert；能覆盖不追加；能查重再发不盲发。
- 验收标准：同一任务手动连跑三遍，最终状态与跑一遍完全一致。把它写成回归用例。

## 总结

自动化系统的可靠性不在于"不出错"，而在于出错和重试之后仍能收敛到正确状态。幂等性就是把"恰好一次"的幻想，换成"至少一次执行 + 幂等收敛"的工程保证。对 OpenClaw 这类任务编排场景，先给每个任务定好幂等键和账本，大部分重复执行的坑就提前填掉了。
