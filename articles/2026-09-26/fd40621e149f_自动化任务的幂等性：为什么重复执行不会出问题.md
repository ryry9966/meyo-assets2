## 背景

在 OpenClaw 里写自动化——定时摘要、webhook 触发的 agent、MCP 工具调用——跑久了会发现一条规律：**任何任务都至少会被执行两次**。定时器重叠、网络超时后 agent 自动重试、进程崩溃后队列重放、用户手滑多点一次。这不是异常路径，是常态。

## 问题：重试没错，错在任务不幂等

幂等性没做好的任务，一次失败加一次重试，就是双倍副作用。常见翻车现场：

- 每日推送的定时任务因服务重启跑了两遍，频道里出现两条一模一样的日报；
- agent 调"创建工单"工具时超时，框架重试后系统里多了张重复工单；
- 同步脚本用追加写，重跑一次，数据翻倍。

根源不在重试机制——重试本身是对的——而在任务本身不幂等。

## 做法：四步改造

1. **给副作用分类。** 读操作天然幂等；"把状态设为目标值"（upsert、整文件覆盖）天然幂等；追加、自增、发消息这类操作默认不幂等，是重点改造对象。

2. **设计稳定的幂等键。** 从任务输入推导，而不是执行时随机生成。比如日报任务的 key 用「任务名 + 逻辑日期 + 目标频道」拼成确定性 ID，重试多少次都不变。

3. **先记录意图，再执行副作用。** 执行前把 key 写入本地存储，标记 in-flight；成功后标记 done。重试时先查 key：done 直接跳过；in-flight 且超过合理时长，再谨慎核实。

4. **把"累加"改写成"设置"。** 文件写入用临时文件加原子改名覆盖；数据库用 `ON CONFLICT DO NOTHING` 或 upsert；调用外部 API 时带上客户端生成的去重 token，让服务端兜底。

## 踩坑点

- **在任务内部现场生成 UUID 当幂等键**：每次重试都是新 key，等于没做。
- **key 里掺了时间戳或随机数**：去重永远不命中；反过来 key 太粗，两次本该独立的执行被误合并。
- **只在成功后记录状态**：最危险的窗口是"副作用已发生、记录还没写"就崩了，意图记录必须前置。
- **先查后做的竞态**：两个并发实例都查到"不存在"，然后都去创建。去重必须落到存储层唯一约束，不能只靠应用层 if 判断。
- **框架自动重试叠加工具追加写**：Agent 框架会按策略重试工具调用，如果你的工具每次都 append，重试就是在放大错误。

## 可复用建议

- 写新任务前过一遍清单：有副作用吗？能表达成"设为目标状态"吗？幂等键是什么、存在哪？中断在副作用和记录之间怎么办？
- 幂等键格式固化成习惯：`hash(任务名 + 逻辑日期 + 业务主键)`。
- 给第三方的非幂等工具统一包一层去重中间件，比逐个改调用点划算。
- 执行日志里带上幂等键，出问题时能对账。

## 总结

自动化的可靠性不取决于"会不会失败"，而取决于"失败后重跑安不安全"。把每个任务都当成至少会跑两次来设计：**运行两次，生效一次**。做到这一点，重试、超时、崩溃恢复才真正是恢复，而不是事故放大器。
