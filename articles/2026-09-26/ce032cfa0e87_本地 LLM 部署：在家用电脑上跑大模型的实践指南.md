## 背景

做 Agent/MCP 开发的人大多有两个痛点：API 账单随调试轮数线性上涨，以及敏感数据不方便交给第三方服务。过去一年量化技术和推理运行时成熟得很快，一台 16GB 内存的普通电脑跑 14B Q4 模型已经是日常操作。本地模型在 Agent 工作流里的合理定位是：高频、廉价、对隐私敏感的“工种”——摘要、抽取、分类、格式转换，而不是替代云端模型做深度推理。

## 问题

很多教程停在“装好 Ollama、能对话”就结束了。但接入 Agent 是另一回事：一轮任务要跑十几次工具调用，考验的是工具调用成功率、上下文管理、持续吞吐和并发，任何一环掉链子，整条流水线就卡住。这篇帖记录我从“能跑”到“能干活”之间踩过的坑。

## 步骤

1. **盘点硬件**。经验值：Q4_K_M 量化下，7B 约占 5GB，14B 约 9GB，32B 约 19GB，还要给 KV cache 留余量——长上下文会额外吃掉几个 GB。8GB 显存跑 7B-8B，12GB 跑 14B，Mac 统一内存按同样量级估算。
2. **选运行时**。Ollama 当默认（自带 OpenAI 兼容接口），需要精细调参用 llama.cpp server，GUI 调试用 LM Studio。
3. **选模型**。第一条硬标准：原生支持工具调用。不少社区 GGUF 转档会丢 chat template，工具调用直接残废。量化从 Q4_K_M 起步，显存富余再上 Q5/Q6。
4. **起服务，调三个关键参数**：`num_ctx` 显式设大（默认值对 Agent 太小）、`keep_alive` 设长避免反复冷启动、内存紧张时开 flash attention 和 KV cache 量化。
5. **接入 Agent**：base_url 指向本地端点，temperature 压到 0~0.3，优先用结构化输出/JSON schema。上线前先跑一个 3~5 步的工具调用循环做冒烟测试。
6. **分层路由**：本地模型接高频简单任务，难任务路由到云端模型。按任务类型主动分流，不要只靠失败降级。

## 踩坑点

- `num_ctx` 默认太小，Agent 跑着跑着“失忆”；盲目调大又撑爆 KV cache，长对话后期 OOM。
- 第三方量化包丢模板，模型对工具调用输出纯文本，解析全挂——换模型前先跑最小调用脚本验证。
- `keep_alive` 默认只驻留几分钟，Agent 每轮都撞上几十秒冷启动。
- Agent 单轮上下文很大，真实 prompt 长度下的 tok/s 比跑分重要得多，务必实测。
- 并发请求会让显存占用成倍放大，`num_parallel` 别乱开；24GB 卡跑 32B 加并发很容易翻车。

## 可复用建议

- 把 base_url、模型名、量化版本、num_ctx 写进配置文件提交仓库，出问题先核对配置。
- 自建 10~20 条带工具调用的固定评测样本，每次换模型/量化跑一遍，记录成功率和 tok/s。
- 结构化输出 + schema 校验，失败重试一次，再失败路由到云端模型兜底。
- 别逼本地模型做它不擅长的事，把它当高频廉价工种用，整体成本和稳定性都会更好。

## 总结

家用电脑跑大模型在今天是成立的，但要把它当成流水线里的一个工程节点去设计：选原生支持工具调用的模型、显式管好上下文和驻留、用真实负载测吞吐、做分层路由。做到这四点，本地模型就能稳定接进你的 Agent 工作流。
