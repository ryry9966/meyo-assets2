## 背景

用 OpenClaw 跑 agent 自动化一段时间后，几乎所有人都会撞上同一个问题：全量走 GPT 类云端模型，成本压不住；全量切本地模型，任务质量又明显掉一截。多模型路由就是为这个场景准备的——让不同任务走不同档位的模型，在成本、质量、延迟之间找平衡点。这篇帖整理我们在几个生产工作流里的做法，给正在纠结的邻居一个可参考的起点。

## 问题：路由依据到底是什么

路由不是"哪个便宜用哪个"，真正要回答的是三个问题：

1. 任务对推理能力的要求有多高？
2. 数据是否敏感、能不能出本地？
3. 这条链路对延迟和成本敏感到什么程度？

凭感觉配规则的后果是：规则越加越多，效果没人说得清，最后退化成"全走大模型保平安"。

## 做法

### 第一步：给任务分档

先别急着配模型，把 agent 干的活分类。我们的经验是分三档：

- **轻任务**：意图识别、字段抽取、格式化、简单改写 → 本地 7B 级别足够
- **中任务**：单工具调用、摘要、常规 RAG 问答 → 本地较大模型或云端中档模型
- **重任务**：多步规划、复杂代码生成、跨 MCP 工具编排 → 云端旗舰模型

### 第二步：写路由规则

OpenClaw 的路由本质是"规则 + 模型池"，简化示例如下：

```yaml
routing:
  rules:
    - match: { task_type: extract|classify, sensitivity: low }
      target: local-7b
    - match: { sensitivity: high }
      target: local-*
    - match: { task_type: plan|codegen }
      target: gpt-flagship
  fallback:
    - from: local-7b
      to: gpt-mid
      on: [timeout, low_confidence]
```

要点：**敏感度在数据入口统一打标**，路由规则只读标签，不要在规则里再解析内容本身。

### 第三步：配 fallback 链

本地超时或置信度低时切云端，云端配额耗尽时降级本地。但必须记日志——静默降级是质量事故的头号来源。

### 第四步：建观测

每个请求记录：命中规则、实际模型、延迟、token 成本、结果标记。按任务类型聚合看，不要按单条看。

## 踩坑点

- **长上下文陷阱**：本地模型 context window 小，长文档任务截断后效果崩，规则里要加 token 长度条件。
- **structured output 差异**：不少本地模型的 function calling 格式不稳，JSON 解析失败率明显高于云端，重工具链路慎用本地。
- **量化版本坑**：评估用全精度，上线跑 Q4，效果对不上，评估和上线必须同版本。
- **规则爆炸**：规则超过十条就该考虑合并，否则半年后没人敢动这套配置。
- **fallback 掩盖劣化**：本地切云端成功率高，反而掩盖了本地模型的持续退化，降级率要单独监控。

## 可复用建议

1. 从两档起步（一个本地小模型 + 一个云端旗舰），跑稳了再细分。
2. 建 30~50 条代表性任务的评估集，每次改路由规则前后各跑一遍，用数字说话。
3. 路由决策日志必须落盘，出问题能回放。
4. 敏感度打标放在数据入口统一做，别散落在各插件里。
5. 成本报表按任务类型聚合，才能看清哪类任务最烧钱。

## 总结

多模型路由不是一次性配置问题，而是持续的工程权衡。原则很简单：敏感数据和轻任务下沉本地，重任务上云端，fallback 必须可观测，规则改动必须过评估集。先把两档路由跑出数据，再谈精细化——没有观测数据的路由优化，都是玄学。
