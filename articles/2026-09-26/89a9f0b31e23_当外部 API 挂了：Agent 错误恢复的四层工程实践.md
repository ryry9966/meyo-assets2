## 背景

Agent 任务的可靠性上限，往往不取决于模型，而取决于它依赖的**最不稳定的那次工具调用**。一个典型的自动化流程里，Agent 可能串起搜索、LLM、数据库、第三方业务 API 十几次调用，任何一次 429 或超时都可能让整条链断掉。跑一次性问答无所谓，跑无人值守的 cron 任务就很致命——凌晨三点没人盯着。

## 问题：三种比"崩溃"更糟的失败形态

实际观察下来，直接抛异常中断反而是最好的结果。更麻烦的是这三种：

1. **静默失败**：工具层捕获异常后返回空字符串，模型拿到空数据继续编，最后输出一份看起来完整、内容全错的报告。
2. **模型自行兜底**：报错信息太模糊（比如只返回 `error`），模型基于训练数据"脑补"一个答案，用户完全无法分辨真假。
3. **无限重试**：Agent 循环里模型反复重试同一个失败调用，配额烧完、token 烧完，任务还是没跑成。

## 做法：把错误恢复做成显式的四层

**第一层：错误分类，别一视同仁。**
- 瞬时错误（429、503、超时、连接重置）→ 可重试；
- 持久错误（401/403、404、参数不合法）→ 重试没有意义，直接走失败分支。

**第二层：重试加约束。**
指数退避 + 随机抖动，限次（如 3 次）并设总预算。关键点：重试只作用于幂等操作。查询类随便重；下单、发消息、写库这类操作，要么带幂等键，要么不要自动重试，宁可停下来让人确认。

**第三层：超时预算分层。**
单次调用超时（如 10s）和整个任务超时（如 5min）要分开设。只设单次超时的常见后果是：Agent 每一步都"合法"，整体却卡死一小时。

**第四层：给模型结构化的失败信号。**
不要让工具在失败时返回空串，返回明确结构，让模型知道"这次是真的没数据"：

```json
{ "status": "error", "retryable": false, "reason": "upstream_401" }
```

同时在 system prompt 里写死规则：工具返回 error 时，如实告知用户哪一步失败，**禁止用推测数据填补空缺**。这一条比任何重试逻辑都重要。

**降级路径要有，但要显式声明。**
主 API 挂了可以切备用源或读缓存，但输出必须标注"数据来自缓存/降级源，时间点为 X"。降级不可怕，降级了还装作正常才可怕。

## 踩坑点

- 备用 API 返回结构和主源不一致，切换后下游解析全崩——降级适配层要提前写好、提前测。
- 把"配额用完"当成"服务挂了"无限重试，越重越完。
- 日志只记 `tool_call failed`，没有原始状态码和响应体，事后没法复盘。
- 长流程没有断点，第 9 步挂了从第 1 步重跑，前 8 步的副作用全部重复执行。

## 可复用建议

1. 给所有工具调用包一层统一 wrapper：分类、限次重试、结构化错误返回，一处修改全局生效。
2. 长任务按步骤持久化 checkpoint，恢复时从断点续跑。
3. 每个非幂等操作带幂等键。
4. 定期做故障演练：故意把某个 API 的 key 改错，观察 Agent 是崩、是编、还是按预期降级——测出来的答案会颠覆你的自信。

## 总结

错误恢复不是加个 try/except 的事，它由错误分类、重试策略、超时预算、对模型的反馈协议四层组成，缺任何一层，都会以"静默出错"的方式还回来。对 Agent 来说，最贵的问题不是失败，而是**失败得看不出来**。
