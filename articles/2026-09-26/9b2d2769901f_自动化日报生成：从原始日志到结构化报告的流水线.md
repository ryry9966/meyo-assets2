## 背景

团队的日报大多靠人肉拼凑：翻 git log、看 CI 面板、回忆昨天做了什么。数据散在多个系统里，报告常有遗漏，还每天吃掉半小时。我们用 OpenClaw 的定时任务加 MCP 工具把这件事改造成流水线：事实由脚本拉取，Agent 只负责组织语言，产出固定结构的报告推送到群。

## 问题

直接对 Agent 说"帮我写日报"效果很差，主要三个坑：

1. **上下文装不下**。一天的 commit、CI 事件、告警日志轻松几十 K token，全塞进去既贵又容易截断。
2. **数字不可信**。让模型自己数"部署了几次"，它会编。统计必须由确定性代码完成。
3. **格式漂移**。每次生成的章节和字段顺序都不一样，下游没法归档和 diff。

## 做法

流水线分四段，各自独立可测：

**1. 采集（脚本 + MCP 工具）**：三个小采集器分别拉 git commits、CI/部署事件、告警增量，统一输出 `{source, timestamp, actor, action, meta}` 的中间 JSON。这一步全是确定性代码，不过模型。

**2. 规约（map-reduce 摘要）**：不要把原始记录一次性喂给 Agent。按来源分片，每片让 Agent 输出 3-5 条要点（map），再合并成当日变更清单（reduce）。分片控制在 2K token 内，单次调用便宜且不易截断。

**3. 结构化渲染**：用固定 JSON Schema 约束输出：`summary / deploys / incidents / risks / tomorrow`。Agent 只填字段，模板负责转 Markdown。Schema 校验失败直接重试，半成品不出门。

**4. 推送与归档**：cron 每天 18:30 触发，报告推群 webhook，原始中间 JSON 和最终报告都按日期落盘，方便第二天 diff 核对。

## 踩坑点

- **时区**：git 和 CI 返回的都是 UTC，第一次跑出来把今天凌晨的记录算进了"昨天"。所有采集器统一先转本地时区再过滤。
- **重复计数**：commit 被 rebase 后 hash 会变，按 hash 去重会漏。改为按 `(repo, message 前缀)` 粗去重。
- **告警风暴**：一次服务抖动产生 300 条告警，reduce 阶段配额直接打爆。采集层加聚合：同类告警在 5 分钟窗口合并为一条，附 count 字段。
- **幻觉**：即便给了要点，模型偶尔会"补充"没发生的事。对策是调低温度，并在 prompt 里明确要求只使用输入中的事实，缺失就写"无"。

## 可复用建议

- 数字一律由脚本算好放进 meta，Agent 只做措辞，不做计算。
- 中间产物（原始 JSON + 要点）落盘，报告出错时能区分是采集错了还是摘要错了。
- 加 `--dry-run` 模式，上线前空跑三天人工比对，再放开推送。
- Schema 做版本管理，字段变更留 changelog，否则下游归档脚本会静默坏掉。

## 总结

核心思路一句话：**确定性代码管事实，Agent 管表达**。上线后日报从人工 30 分钟变成定时推送即达；结构固定后，周报也能直接聚合日报生成。这套做法不绑定特定框架——采集、规约、渲染、推送四段拆开，任何能调 MCP 工具加 cron 的环境都能搭起来。
