## 背景

我们团队每天要发一份工程日报，内容来自 Git 提交、CI 流水线、工单系统和几个服务的运行日志。以前靠值班同学手动整理，平均花 30–40 分钟，格式还因人而异。这篇帖子记录我们用 OpenClaw 的 Agent + MCP 工具搭的一条自动流水线：定时拉取原始日志，归一化为结构化数据，再由模型汇总成日报。核心思路一句话：**LLM 只负责"摘要"这一段，采集和校验交给确定性代码。**

## 问题

一开始直接把"生成本日报告"丢给 Agent 端到端跑，效果很差，主要有三类问题：

1. 原始日志格式不统一，时间戳、级别、字段名各异，模型经常漏读或误读；
2. debug 和心跳类噪音太多，直接撑爆上下文，摘要质量骤降；
3. 模型自由发挥，写进报告里一些没有依据的"进展"，复核成本比手写还高。

结论很明确：必须先做结构化，再谈摘要。

## 做法

流水线分四段，每段独立可运行：

**1. 采集（cron 触发）**：每天固定时间由 cron 触发 Agent 跑一次，通过两个 MCP server 拉数据：一个对接 Git/CI 的 API，一个读日志服务的查询接口，只取时间窗内的增量。

**2. 归一化**：脚本把各类日志映射到统一的 JSON Schema：`{source, timestamp, actor, type, summary, ref}`。噪音在这一层过滤——心跳、重复告警按 fingerprint 去重后只保留计数。敏感信息（token、内网 IP）也在这里最先脱敏。

**3. 摘要（LLM）**：把结构化 JSON 喂给 Agent，prompt 约束三条：只允许引用输入中的条目；每条结论必须带 `ref` 指回原始记录；输出同样过 Schema 校验。temperature 设 0。

**4. 渲染与投递**：模板渲染成 Markdown，推到群机器人，同时归档一份到对象存储。失败时发告警，绝不沉默。

## 踩坑点

- **时间边界**：日志服务用 UTC，团队按本地时区下班，第一次跑出来的"昨日"少了 8 小时数据。现在所有阶段统一传入显式的窗口起止时间，不让任何一段自己算"今天"。
- **重跑不幂等**：一次失败后手动重跑，群里收到两份日报。现在每次运行带 `run_id`，投递前查重。
- **模型编造 ref**：光约束"必须引用"不够，模型会引用不存在的条目。加了后置校验：输出里每个 `ref` 必须能在输入 JSON 中找到，否则该条丢弃并记录日志。
- **静默失败**：有两天 cron 挂了没人发现。补了失败告警，比日报本身更重要。

## 可复用建议

1. **中间 Schema 是契约**：先定 Schema 再写各段，段与段之间用文件或消息解耦，随时可以替换某一段的实现；
2. **每段留独立 CLI 入口**：排障时单跑归一化或摘要即可，不必整条重放；
3. **原始日志落盘留档**：prompt 迭代后可以回放同一份输入，对比新旧输出质量；
4. **Schema 和 prompt 一起做版本管理**：日报格式变更时能追溯是哪次改动引入的。

## 总结

流水线上线后，日报耗时从人工 30 分钟降到约 2 分钟复核。最大的经验是：不要让 Agent 端到端包揽，把它放在"结构化之后的摘要"这一小段，前后用确定性代码兜住，稳定性完全不在一个量级。整套东西就是一份 Schema 定义加四个阶段脚本，两三百行，有日报/周报需求的团队可以直接搬走改。
