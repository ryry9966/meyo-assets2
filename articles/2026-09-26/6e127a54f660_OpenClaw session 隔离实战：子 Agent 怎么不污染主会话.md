## 背景

用 OpenClaw 跑了一段时间后最直观的感受是：主会话的上下文是消耗品。每个频道的对话默认落在一条主 session 里，模型每轮看到的都是这份 transcript 的累积。日常问答没问题，但一旦让主 Agent 亲自去翻大仓库、跑构建、抓网页，几万 token 的工具输出灌进去，早上的对话很快被挤出有效上下文，compaction 变频繁，行为也会“变笨”。

## 问题

典型翻车现场：让主 Agent 直接读目录结构加几个源文件来回答架构问题。单次任务能完成，但主会话从此背上这批 token；连续做几次，旧上下文基本被冲光，用户得重新交代背景。更隐蔽的是并行需求——两个独立任务串行塞在主会话里，既慢又互相干扰。

核心诉求是分工：**主会话负责对话状态和决策，重活、脏活、一次性活交给子 Agent，做完只带结果回来。**

## 做法

OpenClaw 的隔离主要靠 `sessions_spawn`（工具名以你运行版本的文档为准）：

1. 主 Agent 调 `sessions_spawn`，给子 Agent 一段自包含的任务描述：文件路径、约束、期望产出，需要的上下文一次性给足。
2. 子 Agent 拿到一个全新 session，有自己的 transcript 和工具调用记录，与主会话完全隔离。
3. 子 Agent 跑完后只把最终 result 返回，中间过程（比如读文件的原始输出）不会回流到主会话。
4. 需要并行就多开几个；异步模式下主会话可以继续干别的，结果稍后回来。
5. 极少数需要回看时，用 `sessions_history` 按需拉取，而不是默认全量带入。

配套动作是给子 Agent 写“返回契约”：明确要求它返回结论 + 关键数据 + 失败原因，而不是一句“做完了”。

## 踩坑点

- **以为父会话能看到子 Agent 的一切。** 默认只有 result 回流。子 Agent 中途发现的重要线索如果没写进结果，主会话就是不知道。spawn prompt 里必须写清返回什么。
- **为小事开子 Agent。** spawn 有固定开销，“算个时间差”这种直接做更快。判断标准：这次工具调用的输出量值不值得隔离。
- **子 Agent 工具面太宽。** 它继承整套配置，可能拿着全部工具到处逛。给探索类任务约束范围，或用精简配置的专用 agent。
- **异步结果没对齐。** async spawn 后忘了等结果，或结果回来时对话已经换了话题，要做关联。
- **嵌套 spawn。** 子 Agent 再开子 Agent，横向铺开后排查很痛苦，尽量控制在单层。

## 可复用建议

- 一句话心智模型：**主会话是工作内存，子 Agent 是一次性沙箱。**
- 凡是预计产生大块输出的操作（批量读文件、长构建、抓取、批处理），优先 spawn。
- 把“返回结论 + 关键数据 + 没做成的原因”固化成 spawn prompt 模板，复用。
- 用 `sessions_list` 留意残留的子会话，配合清理策略，别让磁盘上堆孤儿 session。
- cron / webhook 这类无头触发本来就跑在独立 session，正好复用同一套“结果带回主会话”的思路。

## 总结

session 隔离不是高深机制，本质是让**过程留在子会话、结论回到主会话**。把返回契约写清楚、把 spawn 用在真正重的地方，主会话就能长期保持轻量，长对话的可控性会有肉眼可见的改善。
