# 背景

OpenClaw 作为常驻的个人 Agent 网关，一天处理的请求量远比直觉中大：定时任务、频道摘要、插件回调、多轮对话。如果所有流量都走 GPT，账单和延迟都很直观；如果全部切到本地模型（Ollama / LM Studio），简单任务没问题，但复杂工具链一跑就崩。多模型路由要解决的不是"选最强的模型"，而是"按任务分配算力"。

# 问题

实际使用中常见两个极端：

- **全云端**：一条消息摘要也调 GPT，月成本难看，且敏感数据全部出网；
- **全本地**：7B/14B 模型做改写和闲聊够用，但多步工具调用、长上下文会话的失败率明显上升。

核心矛盾是：路由决策没有标准，全靠手感。

# 做法

**1. 先给任务分层。** 我的经验分三档：

| 档位 | 任务类型 | 模型选择 |
|---|---|---|
| 高频低风险 | 消息改写、定时摘要、格式转换 | 本地 |
| 中等 | 单次工具调用、短代码片段 | 本地优先，失败转云端 |
| 低频高风险 | 多步工具链、长上下文、代码重构 | 直接 GPT |

**2. 配置显式 fallback 链。** 在 `agents.defaults` 里声明主模型和兜底序列（字段名以你所用版本文档为准）：

```json
{
  "agents": {
    "defaults": {
      "model": "openai/gpt-5.2",
      "models": {
        "openai/gpt-5.2": { "alias": "cloud" },
        "ollama/qwen3:32b": { "alias": "local" }
      },
      "modelFallbacks": ["ollama/qwen3:32b"]
    }
  }
}
```

思路通用：主模型 + 显式兜底序列，`alias` 方便命令行临时切换。

**3. 会话级覆盖。** 自动化流水线里的预处理 agent（如消息归一化）在插件配置里固定用本地模型；主对话会话保持云端。路由粒度到会话/agent 就够，不必精确到单条消息，维护成本太高。

**4. 让本地模型做"预路由"。** 用本地模型先做分类和上下文压缩，把裁剪后的内容交给 GPT。实测能砍掉相当一部分输入 token，这一条对成本最敏感的场景收益最大。

# 踩坑点

- **工具调用质量差异被低估。** 本地模型生成的 JSON 参数常有格式瑕疵，云端能自动纠正的场景本地会直接失败。切换前先跑一轮固定 prompt 的工具调用回归。
- **上下文长度不对等。** 云端 200k 级别，本地常见 32k，长会话直接 fallback 会静默截断，需要自己做摘要回灌。
- **fallback 循环。** 两端都失败时会来回重试，务必设重试上限，否则一条消息能卡几分钟。
- **参数语义不一致。** thinking budget、温度这类参数在不同 provider 下行为不同，照抄配置会得到意外结果。
- **按代价分层，不按频率。** 路由判断出错在闲聊里代价低，在代码生成里代价高。分档标准应该是"失败一次要花多少时间补救"，而不是"这个任务出现得多不多"。

# 可复用建议

1. 维护一个 20 条左右的回归脚本：固定输入 + 期望的工具调用序列，换模型前跑一遍，十分钟换来很大的心里踏实。
2. 记录每个会话的 token 消耗，跑一周后你会自然知道哪类任务值得上云端，不再需要猜。
3. 本地模型选型优先看工具调用稳定性，其次才是通用 benchmark 分数。
4. 兜底方向可以反过来：日常本地优先，只在检测到多步任务标记时升级到 GPT，成本曲线更平。

# 总结

多模型路由的价值不在"全自动智能调度"，而在把分配标准显式写进配置和流程：任务分层、显式 fallback、会话级覆盖、回归验证。做到这四点，成本和稳定性就都可预期。落地路径建议先跑通"云端主力 + 本地兜底"这一条链，再逐步把低风险任务下沉到本地——每一步都可回滚，比一步到位安全得多。
