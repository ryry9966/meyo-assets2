## 背景

跑过 Agent 日常自动化的人都遇到过同一个矛盾：能力接得越多越好用，但上下文也越塞越满。把工具手册、MCP 工具列表、各种操作规范全堆进系统提示词，结果模型注意力被稀释，简单任务开始跑偏，token 账单也难看。OpenClaw 的 Skills 机制就是针对这一点：把"能力"拆成独立单元，启动时只注入一句话级的元信息，模型判断当前任务需要时才把完整说明读进上下文，也就是所谓的渐进式披露（progressive disclosure）。

## 问题

假设你接了十几个 MCP、写了二十条 SOP，全量塞进 system prompt，实践中通常出现三种症状：

1. **干扰**：无关的长指令占据上下文，模型在引用参数时串味；
2. **成本**：每一轮对话都为整套指令付费，哪怕当前任务只用到一项能力；
3. **混淆**：不同 SOP 的步骤被错误拼装，错误动作看起来还挺合理。

本质是把上下文当成了无限大的黑板。Skills 的思路是把它当成需要分配的稀缺资源。

## 做法

一个 Skill 本质上就是一个目录，核心是一份 `SKILL.md`。接入一个 Skill 只需三步：

**第一步：建目录，写 SKILL.md。** frontmatter 里写 `name` 和 `description`。description 要写清"什么时候该用它"，它是触发的唯一依据。启动时 OpenClaw 只把这一句话注入上下文，正文完全不进入。

**第二步：控制正文。** 正文写成可执行的步骤清单，尽量控制在一百行内。长篇背景、参考资料拆到同目录的其他文件，正文里只注明"需要时读取 xxx.md"，模型会按需单独加载。

**第三步：确定性逻辑下沉到脚本。** 调 API、格式转换、批量改名这类固定流程，写成同目录下的脚本。Skill 正文只负责"指挥"：何时调用、传什么参数、失败怎么办。这样既省 token，结果也更稳定。

## 踩坑点

- **description 写得太泛**。"帮你处理文件"这种描述几乎每个任务都会触发，等于没拆。把它当搜索查询来写，放进用户真实会说出口的关键词。
- **职责重叠**。两个 Skill 都管"部署"，模型会随机挑一个。每个 Skill 保持单一职责，实在重叠就合并。
- **正文写成百科**。一触发就吃掉一大块预算。记住分层原则：元信息常驻、正文按需、细节进子文件。
- **只测正向路径**。不仅要验证"该触发时触发"，还要准备一组不该触发的负例，确认它不会乱入。
- **脚本不幂等**。Agent 执行失败可能重试，非幂等脚本会造成重复副作用，写脚本时先想清楚重跑一遍会发生什么。

## 可复用建议

1. **把 Skill 当代码管**：放进 git，改动走 review。description 是"触发契约"，每次改动都回归一遍触发测试。
2. **公共约定收敛**：代码风格、发布流程这类通用约定抽成一个共享 Skill，不要复制十份。
3. **定期审计触发率**：长期没触发过的 Skill，要么重写 description，要么删掉。能力清单贵在准，不在多。

## 总结

Skills 的价值不在于"能力多"，而在于改变了上下文的分配方式：一句话元信息常驻，完整说明按需加载，重活交给脚本。三层分开之后，能力清单可以持续增长而不拖垮基线表现。建议先把最常用的那条 SOP 迁成 Skill，跑两周观察触发行为，再逐步迁移其余的——比一次性全搬稳得多。
