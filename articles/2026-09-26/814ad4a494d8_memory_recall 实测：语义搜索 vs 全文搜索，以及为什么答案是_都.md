## 背景

OpenClaw 的 `memory_recall` 是 agent"想不起来"时的兜底环节：从 memory 目录（MEMORY.md、daily notes、长期笔记）里捞出相关片段塞回上下文。这一步的召回质量，直接决定助手是"记得"还是在瞎编。社区里常见两条路线：全文检索（BM25/grep）和语义检索（embedding + 向量相似度）。官方两种都支持，但大多数人选哪条是拍脑袋定的。我也一样，所以干脆做了个小实验。

## 问题

我的使用场景：日常运维记录、项目决策、踩坑笔记，中英混杂，且经常出现精确标识符——错误码、文件路径、模型名、服务名。目标很朴素：当用户问"上次那个 502 是怎么解决的"时，对应片段能进 top-3。

## 做法

1. 从近三个月真实对话中抽出 42 条 query，人工标注每条期望命中的 memory 片段；
2. 同一份语料（约 380 个片段）分别建索引：FTS 用 BM25，向量用本地 embedding 模型、按主题分块；
3. 统计 hit@5 和 top-1 命中率，另跑一版混合方案（两路结果 RRF 融合）做对照。

| 方案 | hit@5 | top-1 |
| --- | --- | --- |
| 纯全文 | 71% | 43% |
| 纯语义 | 76% | 48% |
| 混合（RRF） | 90% | 62% |

拆开看更说明问题：query 含精确标识符的 17 条，全文 hit@5 88%，语义只有 59%；query 是同义改写（"当时说过的备份方案"这类）的 15 条，语义 87%，全文 53%。两类 query 几乎完全互补。

## 踩坑点

- **中文 embedding 模型差异巨大**。第一版用的通用英文模型，中文 query 掉到 60% 出头，换多语言模型才追平。选型务必拿自己的中文 query 验证，别只看榜单。
- **全文检索对中文反而稳**。子串匹配不依赖分词，"502"、"memory_recall" 这类标识符命中率天然高；但对换个说法的提问几乎无能为力。
- **索引过期很隐蔽**。手动编辑 MEMORY.md 后向量索引不自动重建，召回的是旧片段，症状只是"它答得怪"，很难第一反应想到索引。现在我把重建挂在 memory 写入钩子上。
- **top-k 别给太小**。k=3 时混合方案的优势被截断，k=8 才吃得满融合收益，代价是上下文变长，需要权衡。
- **分块粒度**。一开始按 daily note 整条切，一条长笔记就是一个大 chunk，向量召回整块很浪费 token。改成按主题切小块后再融合，上下文开销降了约三成。

## 可复用建议

- **别二选一**。BM25 + 向量做 RRF 融合是明确赢家，实现代价可控，几十行代码。
- 如果只能先上一个：memory 里标识符多、语料在几百条以内，先上 FTS——零依赖、可解释、最好排障；语义检索后补。
- **固化评测集**。这 42 条 query 我留成了回归集，每次换 embedding 模型或调分块策略都跑一遍。数字比"感觉变好了"可靠。
- **写入时就为检索铺路**：一条一事、带日期和关键词，比事后调检索参数划算得多。

## 总结

这本质上不是"语义 vs 全文"的选型题，而是"你的 query 长什么样"的问题：精确标识符靠字面匹配，模糊意图靠向量，融合后 hit@5 从七成出头拉到九成。花半天建一个小评测集，比读十篇检索综述有用。
