## 背景

OpenClaw 的工作空间里，`AGENTS.md` 是少数每一轮对话都会注入系统提示词的文件。分工大致是：`SOUL.md` 管人格与语气，`USER.md` 管用户画像，`MEMORY.md` 管长期记忆，而 `AGENTS.md` 管的是"操作规程"——文件放哪、什么时候写记忆、哪些操作必须先确认。可以把它理解成一份写给 AI 的 runbook，只是读者不是人，是模型。

## 问题

实践里常见两种极端。一种是保持默认不动，Agent 只能靠猜：日志写到工作区根目录、该沉淀的事没进 `MEMORY.md`、执行删除类命令前不做确认，每次会话表现都不一样。另一种是反着来，把项目说明、MCP 工具清单、聊天风格全塞进去，结果指令互相冲突、常驻 token 膨胀、注意力被稀释——规则越多，遵守得越差。

## 做法

我的写法归纳成四步：

1. **划清边界。** 人格相关的一句都不要出现在 `AGENTS.md`，那是 `SOUL.md` 的事；单项目细节放到项目自己的 `AGENTS.md`，工作空间层面只留跨项目通用的规程。
2. **只写可判定的规则。** 用"触发条件 + 动作 + 反例"的格式。比如"凡是产生可复用结论的对话，结束前向 `MEMORY.md` 追加一条日期开头的条目；闲聊不写"。这比"记得好好记笔记"有用得多。
3. **按区块组织，控制在 150 行内。** 我固定用五段：工作区约定（路径、命名）、例行流程（日报、记忆写入策略）、安全边界（删除/支付/外发必须确认）、工具与 MCP 备注（哪个 server 干什么、已知坑）、输出格式。
4. **当配置文件养，进 git。** Agent 每做错一件事，就回头补一条针对性规则，而不是在对话里反复纠正。改完开个新会话验证，像跑 CI 一样。

## 踩坑点

- **规则互相矛盾。** `SOUL.md` 说口语化、`AGENTS.md` 要求正式报告体，Agent 会在两种风格间漂移。改之前先全文搜一遍冲突。
- **形容词不可执行。** "小心一点""尽量别"这类表述模型无法落地，必须换成具体条件和动作。
- **中间内容被忽略。** 文件过长时，中段规则遵守率明显下降，重要的边界条件尽量放头尾。
- **密钥写进去。** 它是明文且每轮都发给模型，token、密码一律走环境变量。
- **记忆策略没定义。** 不写清触发条件和格式，Agent 要么刷屏式写 `MEMORY.md`，要么从来不写。

## 可复用建议

- 每条规则写成"如果 X，则 Y，不要 Z"，方便日后增删和 review。
- 安全边界放在文件开头第一段，这是遵守率最高的位置。
- 每月剪枝一次：删掉一个月内没触发过的规则，项目相关的下沉到项目级文件。
- 维护一个最小新会话测试集：挑三个最容易出错的场景，每次改完跑一遍再提交。

## 总结

`AGENTS.md` 的价值不在写了多少，而在每条都真实生效。把它当成 prompt 化的配置文件来维护——小、具体、版本化、持续迭代——Agent 的行为才能从"每次开盲盒"变成"可预期的工程系统"。
