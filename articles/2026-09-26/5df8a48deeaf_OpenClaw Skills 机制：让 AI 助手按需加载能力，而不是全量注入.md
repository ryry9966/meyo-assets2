## 背景

跑 Agent 一段时间后，几乎所有人都会撞上同一个瓶颈：上下文。为了让助手会部署、会查日志、会操作内部系统，最直觉的做法是把所有操作手册塞进 system prompt。结果是常驻 token 动辄上万，指令互相干扰，模型反而变“笨”。

OpenClaw 的 Skills 机制就是针对这个问题设计的：把能力拆成独立文件，平时只有一行描述常驻上下文，命中时才注入正文。思路接近渐进式披露（progressive disclosure）——先让模型知道自己“有什么”，再决定“翻哪本手册”。

## 问题

没有 Skills 之前，两条路都有代价：

- **全塞 prompt**：token 成本高，低频指令会稀释高频指令的注意力权重；
- **全靠 MCP**：工具描述全量注册，工具一多，模型在几十个 tool 之间挑，误调用率明显上升。

Skills 和 MCP 不是替代关系：MCP 适合标准化的外部接口（数据库、API），Skills 更适合**流程性知识**——有固定步骤、带私有约定的操作方法，比如“我们团队内部服务怎么发布”。

## 做法

一个最小可用的 Skill 就是一个目录加一个文件：

```markdown
---
name: deploy-internal
description: 当用户要求部署或更新内部服务、提到上线/发布/回滚时使用
---

## 步骤
1. 先跑 scripts/preflight.sh 确认环境
2. 执行 scripts/deploy.sh <服务名>，不要直接调底层命令
3. 部署后检查 /healthz，失败按回滚章节处理

## 注意
- 周五下午禁止发布
```

加载分两层：

1. 启动时扫描 skills 目录，把每个技能的 `name + description` 注入常驻上下文，单个通常只占几十 token；
2. 对话命中某条 description 时，模型主动读取对应 SKILL.md，完整正文和脚本引用才进入工作上下文。

关键认知：**description 不是简介，是触发器**。写“这是一个部署工具”没用，要写“什么时候用”。

## 踩坑点

- **description 写成功能介绍**。写“用于部署”的技能经常不触发，改成“当用户提到上线/发布/回滚时使用”后命中率明显提升。
- **触发条件重叠**。两个技能都覆盖“发版本”，模型会随机挑一个。一个领域只留一个入口，其余合并。
- **脚本用相对路径**。SKILL.md 里引用脚本要写从技能根目录出发的路径，否则工作目录一变就挂。
- **技能数量失控**。50 个技能的 description 本身就是几千 token，按需加载的前提是索引足够小。长期不触发的，删掉或合并。
- **把高频操作做成技能**。每天都用的能力，直接进 prompt 或做成 MCP tool 更稳，还省一次检索。

## 可复用建议

- **一技能一事**：一个技能解决一类任务，别做“大而全”的万能手册；
- **统一句式**：description 全部用“当用户要求……/提到……时使用”，方便批量审查触发逻辑；
- **脚本同仓管理**：脚本和 SKILL.md 放同一目录、同一仓库，技能演进有 diff 可查；
- **用真实对话做回归**：拿过去一周的历史 query 跑一遍，看哪些该触发没触发；
- **先 Skill 后 MCP**：私有流程先落地成 Skill 验证，跑稳定且标准化后再抽成 MCP。

## 总结

Skills 的价值不在“能加载”，而在“平时不占地方”。它把 Agent 的能力管理从“往 prompt 里堆料”变成“维护一个可检索的索引”，token 成本随使用量增长，而不是随能力数增长。实践中它更像文档工程而非编程：写好触发条件、控制数量、定期清理，比任何高级配置都有效。
