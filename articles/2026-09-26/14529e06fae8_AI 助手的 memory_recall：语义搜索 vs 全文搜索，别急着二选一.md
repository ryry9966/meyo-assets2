## 背景

OpenClaw 的 `memory_recall` 是 agent 回看历史的唯一入口。早期实现只有 SQLite FTS5 全文搜索，简单粗暴；后来社区里不少人接了向量库，改成 embedding 语义召回。群里经常吵：到底哪个好？我把自己这套跑了几个月的混合方案拆开讲讲，供正在选型的同学参考。

## 问题

两种检索的失败模式完全不同：

- **全文搜索**：对人名、ID、报错关键字、精确日期命中率很高，可解释性强。但用户换个说法就丢——你存的是“部署失败回滚”，问“上次上线出问题那次”基本搜不到。
- **语义搜索**：换措辞能命中，对口语化提问友好。但对专有名词、数字、代码片段不敏感，而且容易召回“语义相近但实际无关”的内容，比如所有提到“部署”的历史一股脑涌进来。

单用任何一路，都会在真实对话里翻车，只是翻车姿势不同。

## 我的做法

1. **写入结构化**。每条记忆除了正文，带上元数据：时间戳、来源会话、主题标签。这一步比检索算法重要，后面细说。
2. **双通道索引**。全文走 SQLite FTS5；语义用本地跑的小模型（bge-small-zh-v1.5 这个量级够用，别一上来就上大模型）。文本按 200–500 字分块，块间留 overlap，避免语义被切断。
3. **混合召回**。查询时两路各取 top-8，用 RRF（Reciprocal Rank Fusion）融合排序，再叠加时间衰减因子和去重。不要手写固定权重，RRF 免调参且稳。
4. **建小评测集**。攒了 40 条真实问答对（query + 期望命中的记忆 ID），每次调参数跑一遍，看命中率变化。没有这个，调优就是玄学。

## 踩坑点

- **FTS5 默认分词器对中文基本无效**。unicode61 会把整句中文当成一个 token，搜什么都搜不到。要么用 trigram tokenizer，要么写入前用 jieba 预分词。这是中文用户必踩的第一个坑。
- **换 embedding 模型 = 全量重建向量**。维度变了旧向量全废，数据量大时要有重建脚本和过渡方案，别在线上边跑边换。
- **语义召回偏爱旧内容**。三个月前的旧方案和昨天的结论语义都相近，但没有时间信号时会排错序。时间衰减或强制时间窗过滤必须加。
- **垃圾进垃圾出**。写入时不清洗， agent 的中间碎碎念全存进去，检索算法再好也是在一堆噪声里捞针。
- **top-k 贪大**。召回 20 条塞进上下文，agent 反而被无关信息带偏。我最终收敛在 5–8 条。

## 可复用建议

- **先全文后语义**。全文便宜、可解释、零依赖，先跑通写入链路，确认召回缺失的模式，再决定是否上向量。
- **默认混合 + RRF**。两路信号互补，融合成本极低。
- **召回日志从第一天就记**。每次 recall 记下 query 和命中结果，跑两周就是现成的评测集。
- **元数据设计前置**。时间、来源、标签字段后补成本极高，动手前想清楚。

## 总结

语义搜索 vs 全文搜索不是选择题，是工程权衡：全文管精确，语义管模糊，融合管兜底，元数据管秩序。先把写入质量和评测闭环搭好，检索方案怎么换都不会太差。欢迎在评论区贴你自己的召回失败案例，比空谈架构有用得多。
