## 背景

E2E 测试的价值没人否认，但写起来贵、维护起来更贵：selector 飘了、异步没等够、测试数据对不上后端，很多团队的 E2E 套件最后变成“只在本地跑过一次的摆设”。LLM 出现后，“让 AI 写测试”听起来很自然，但直接丢一个 URL 给模型说“帮我写 Playwright 测试”，拿回来的代码通常跑不起来——selector 是编的、断言是空的、等待全靠 sleep。问题不在模型能力，而在你没给它看真实世界。

## 做法：三个角色，一条流水线

我们把这件事拆成三步，用 agent 编排 + 浏览器类 MCP 工具串起来：

1. **探索者。** 给 agent 挂上浏览器 MCP 插件，让它真实打开页面，抓取可访问性树（a11y tree）而非原始 DOM。产出不是代码，而是一份“用户流程清单”：关键路径、每步的可操作元素、预期的状态变化。
2. **撰写者。** 把流程清单 + 仓库里已有的测试范例 + 一份测试规范文档，交给第二个 agent 生成测试代码。关键在“喂范例”：page object 怎么组织、fixture 怎么命名、断言粒度多大，全靠范例约束，不靠 prompt 里喊话。
3. **修复者。** 生成的测试直接进 CI 跑，失败日志回喂给 agent，限定 3 轮自修复。修不好就标成待人工，不硬撑。

人在两个点介入：审批探索者的流程清单（决定**测什么**），review 合并前的最终代码（决定**能不能进主干**）。

## 踩坑点

- **让模型凭空写 selector，必挂。** 截图也不够稳，a11y tree 是目前性价比最高的输入，短小且语义清楚。
- **agent 很爱写 `sleep(3000)`。** 在规范文档里明确禁止，要求语义等待，review 时重点盯这一条。
- **一次生成一整个套件，质量会塌。** 按用户流程逐条生成、逐条验证，小批量迭代明显更稳。
- **断言偏弱是隐性问题。** 测试绿了不代表测了东西。我们要求断言对齐“用户可感知的业务结果”——订单状态、跳转后的关键元素，而不是某个 class 存在。
- **别让 agent 用 retry 掩盖 flaky。** 重试只做兜底不做解法，flake 率要单独统计。
- **测试数据要钉死。** 环境用 seed 数据，agent 只引用 fixture，不允许现场编数据，否则和后端对不上会白烧好几轮。

## 可复用建议

- 把测试规范写成仓库里的一份 markdown，作为 agent 的固定输入。规范文档比 prompt 措辞更持久，团队也能复用。
- 先只覆盖冒烟路径（登录、核心下单、核心查询），稳定跑两周再扩。
- 监控两个指标就够：关键流程覆盖率、CI flake 率。覆盖率涨而 flake 率不涨，说明这套流程在正循环。
- 给 agent 的定位是“初级作者 + 不知疲倦的修复工”，架构判断和合并门槛仍然在你手里。

## 总结

Agent 写 E2E 测试的杠杆，不在“生成代码”这个动作，而在它把“探索真实页面 → 沉淀流程 → 生成 → 自修复”这条流水线自动化了。给 agent 真实环境、用范例约束风格、小批量验证、人把住测什么和合什么这两道闸门——做到这几点，E2E 套件才从成本项变成能自己长大的资产。
