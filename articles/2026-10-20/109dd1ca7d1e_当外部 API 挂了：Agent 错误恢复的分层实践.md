## 背景

Agent 自动化链路里，外部依赖远比想象中多：模型厂商 API、MCP 工具背后的第三方服务、插件里嵌的邮件/存储/支付接口。写 demo 时一切正常，一上生产就会发现：任何一个环节抖动，整条任务链轻则中断，重则 agent 在重试循环里烧 token，甚至拿着错误信息"脑补"出一个结果继续往下跑。这不是提示词问题，是工程问题——执行层缺少一套应对真实世界不可靠性的机制。

## 三种常见的错误模式

1. **把错误当数据**：API 返回一段 HTML 错误页被塞进上下文，模型开始认真"解读"，产出看似合理的幻觉结论。
2. **无界重试**：遇到 429 立刻原样重发，无退避，几分钟内把限流打成封禁。
3. **状态丢失**：任务第 5 步挂了，恢复时从第 1 步重来，已执行的写操作（发通知、下单）全部重复。

## 我们的分层做法

**错误分类**。所有工具调用统一收敛为结构化信封：`{ok, error_code, retryable, hint}`。仅超时、429、502/503/504 标记可重试；401/404、参数校验失败直接判死。这层做在工具 wrapper 里，不依赖模型自觉。

**有界退避**。指数退避加抖动（1s → 2s → 4s），封顶 3 次；同时给整个任务设总 deadline，重试预算不能超过它，超了就转入降级。

**给模型看"翻译过的错误"**。永远不要把原始报错体直接丢进上下文。wrapper 转译成明确指令，例如："目标服务暂不可用，已重试 3 次失败。可选：a) 换备用数据源 b) 稍后重试 c) 输出部分结果并标注缺口"。让模型做决策，而不是猜错因。

**熔断与降级**。同一工具连续失败达阈值，熔断器打开，后续调用快速失败，改走备用源或缓存。降级必须显式：在最终输出标注"本部分来自缓存/备用源"，避免新旧数据被模型混用。

**幂等与断点**。有副作用的调用带幂等键，重试不重复执行；任务状态按步落盘，恢复时从最近检查点续跑。

## 踩坑点

- **非幂等操作裸重试**是最贵的一课：加幂等键之前，一次网络抖动让同一条通知发了三遍。
- **熔断阈值太敏感**：设成失败 1 次即熔断，结果一次抖动把整条链路切到降级源。改成滑动窗口失败率 + 最少样本数才稳。
- **退避超过任务 deadline**：第 4 次重试成功了，但上游调度器早已判死任务。重试预算要全局统一管，不能各工具各算各的。
- **降级源 schema 不一致**：备用 API 少一个字段，模型毫无察觉照样推理。降级数据要过和主源一样的校验器。

## 可复用建议

1. 所有工具调用过统一 wrapper（错误信封 + 重试 + 熔断），配置驱动，不要每个插件各写一套。
2. 提供"降级模式"开关，演练时用 mock 注入必然失败的故障，观察整条链路行为是否符合预期。
3. 错误日志带 trace id 结构化落盘。agent 吞掉异常是事后最难排查的一类问题。

## 总结

外部 API 挂掉不是异常路径，而是常态路径。核心就四条：错误先分类、重试要有界、失败要显式地告诉模型而不是喂原始报错、副作用必须幂等可恢复。把这些做在执行层而不是指望提示词约束，agent 的可靠性才能从"碰运气"变成"可工程化保证"。建议从最常挂的那个工具加 wrapper 开始，比一次重构整个框架现实得多。
