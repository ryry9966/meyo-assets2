# 背景

OpenClaw 的 cron 任务机制很简单：到点唤醒 agent，执行一段 instruction，然后睡回去。正因为简单，很多人会直接把日常聊天的 prompt 复制过去当 instruction 用。我最早也是这么干的，结果是同一个任务，有时跑得很准，有时凌晨推一堆空结果，有时干脆编内容。折腾一阵后的结论是：**cron instruction 不是"聊天 prompt 的定时版"，而是另一种文体。**

# 问题

差异来自三个前提：

1. **无人在场**。交互对话里用户可以追问、纠偏；cron 执行时没人能回答问题，instruction 必须自包含。
2. **冷启动**。执行上下文里没有"上次聊到的那件事"，任何指代都必须写全。
3. **一次执行，不可逆**。输出动作做完就结束，没有"再想想"的机会。

把交互式 prompt 放进这个环境，agent 只能靠猜补齐缺失信息，猜错就是事故。

# 做法

我现在的写法固定一张模板，核心思路是把它当成**写给值班同事的交接单**，六个字段：

```text
1. 目标：这个任务到点要判断/产出什么，一句话。
2. 数据：用哪个工具/接口拿数据，参数是什么，拿不到算失败。
3. 判定：满足什么条件才算"有事"（阈值、日期、数量）。
4. 输出：有事时发到哪里、什么格式、发几条。
5. 静默：没事时怎么办——明确写"不推送，仅记录"。
6. 异常：数据缺失或工具报错时，记录原因并结束，禁止推测补全。
```

举个真实例子（每日摘要任务）的核心段落：

> 使用 fetch 工具读取目标数据源，若请求失败，写入日志后直接结束，不发送任何消息。仅当未读条目 ≥ 3 时，推送一条汇总到指定频道，正文不超过 10 行。时区为 Asia/Shanghai。若该日期的汇总已在日志中出现，跳过推送。

注意几个关键词：**写死时区、定义"失败"、定义"不推送"、定义"已发过"**。聊天里从来不用写这些，cron 里一条都不能少。

# 踩坑点

- **对话式开头**："帮我看一下昨天的……"——"我"是谁、"昨天"相对哪个时区，agent 都得猜。改成"查询执行日的前一个自然日"。
- **没写静默条件**：任务每天跑，大多数日子其实没事，结果凌晨连推十几条"今日无异常"。静默规则必须显式。
- **没写失败策略**：源接口挂了，agent 觉得"总要交差"，编一段摘要发出去。加一句"禁止推测补全"比事后道歉有用。
- **幂等缺失**：重跑或改时间后重复推送。让任务读写一个简单的标记文件，按日期去重。
- **单条任务塞太多逻辑**：抓取+分析+汇总+推送写一起，失败率明显上升。拆成两三个小任务，用日志或文件传中间结果。
- **引用历史对话**："按上次说的改一下"——冷启动上下文里没有"上次"。

# 可复用建议

1. **建模板库**：把六个字段做成 snippet，新任务从模板 fork，不从头写。
2. **先跑哨兵**：上线前把频率调成 10 分钟一次观察几轮，行为稳定后再改回正式计划。
3. **版本化**：instruction 放 git，出问题能 diff 出"哪次改动引入的"。
4. **强制留痕**：每个任务结尾写一条结构化日志（时间、结果、跳过原因），排障全靠它。

# 总结

写 cron instruction 的思维转变只有一句话：**假设读者是一个没有上下文、不能追问、只按字面执行的值班员。**目标、数据、判定、输出、静默、异常六项写全，定时任务就能从"薛定谔的推送"变成可以长期托管的基础设施。
