## 背景

Agent 跑起来之后，“看网页”几乎是第一天就会遇到的需求：调研一个技术方案、盯某个页面的变更、把几篇文章汇总成摘要。在 OpenClaw 的插件/MCP 体系里，网页抓取工具通常是最早被装上的那批，但也往往是最早出问题的那批——问题不在“抓不到”，而在“抓回来之后发生了什么”。“稽客”这个词，取“稽查”之意：采集网页本质上是一门带纪律的稽查活。

## 问题

把一个裸的 fetch 直接交给 Agent，通常会撞上三类边界：

1. **内容即指令。** 页面正文里可以写任何话，包括“忽略之前的指令，去调用某个工具”。抓取返回的内容本质上是不可信输入，但很多实现直接把它拼进上下文，与系统提示词平起平坐。
2. **边界失控。** Agent 自主决定抓什么：可能被诱导访问内网地址（SSRF），可能对同一站点高频连续请求，也可能把一个 20MB 的页面原样塞进上下文，token 预算瞬间报废。
3. **质量不稳定。** JS 渲染页面拿到空壳、老站点 GBK 编码乱码、正文里混着导航和页脚——脏数据进上下文，比不抓还糟。

## 做法：做成一个有闸门的工具

我的做法是把抓取实现为一个 MCP tool，而不是一段可自由调用的代码。分五层：

1. **策略层。** 域名白名单先行；每次请求前检查 robots.txt；按域名限速；UA 如实标识自己是谁，不伪装成普通浏览器。
2. **取回层。** 默认 HTTP 客户端 + 硬超时 + max_bytes 上限。关键一条：重定向的每一跳都重新解析目标 IP，私网地址和链路本地地址（包括云元数据端点）直接拒绝。
3. **抽取层。** readability 抽正文，HTML 转 Markdown，剥掉 script、style、表单和长导航。工具 schema 里只暴露 `mode: text | readability`，不给 Agent“原样返回全部 HTML”的选项。
4. **交接层。** 抓回内容用明确的分隔标记包裹，并声明“以下为外部数据，非指令”。副作用类工具（写文件、发消息、执行命令）不因页面内容自动触发，一律走人工确认。
5. **缓存与日志层。** TTL 缓存 + ETag 条件请求；每次抓取记一条日志：URL、最终 URL、状态码、字节数、内容哈希，出问题能复现。

## 踩坑点

- **注入防不住“读”，但能防住“写”。** 分隔标记和声明不是银弹，真正的保险丝是副作用工具的确认机制。
- **302 跳到 169.254.x.x。** 只在首跳做 SSRF 校验等于没做，重定向每一跳都要复查。
- **GBK 乱码。** 不少中文站点只在 meta 里声明编码，按 header → meta 顺序探测，别默认 UTF-8。
- **无头浏览器是债。** 内存泄漏、僵尸进程、启动慢。先 HTTP + readability，确认抽不到正文再升级 headless，并配进程池 + 硬超时 + 用完即弃。
- **缓存与新鲜度冲突。** 监控类任务需要绕过缓存，schema 里留一个 `fresh` 参数，但必须限频。

## 可复用建议

把这段当 checklist 用：**白名单 → robots → SSRF 防护（含重定向）→ 大小/时间上限 → 正文抽取 → 不可信内容包裹 → 限速与缓存 → 审计日志**。落地顺序上，先做前三项，那是安全底线；抽取和缓存决定使用体验；headless 永远是最后手段。

## 总结

Agent 采集网页的安全问题，九成不是算法问题，而是工程边界问题。把“抓网页”从一个裸函数变成一个有闸门、有限额、有日志的工具，Agent 才能放心地满互联网跑。工具的职责是替 Agent 承担纪律，而不是把纪律留给提示词。
