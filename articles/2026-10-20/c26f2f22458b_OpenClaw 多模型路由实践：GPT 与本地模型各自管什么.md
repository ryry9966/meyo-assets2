## 背景

OpenClaw 默认把所有请求打到一个主模型上，用久了就会发现两件事：一是账单里大量 token 花在“总结这条消息”“给这段文本分类”这类低难度任务上；二是涉及本地敏感文件的任务，其实并不想送到云端。OpenClaw 本身支持多 provider（OpenAI、Anthropic、OpenRouter，以及 Ollama / LM Studio 这类 OpenAI 兼容的本地端点），路由能力是现成的，缺的是一套分工策略。

## 问题

核心矛盾是三个维度的取舍：能力（复杂工具编排、长上下文）、成本（云端按 token 计费）、隐私（数据不出本机）。单一模型必然在某个维度吃亏。我们踩过的典型状况：cron 定时任务里跑着旗舰模型做摘要，一个月白烧几十块；反过来为了省钱把 agent 主循环换成 7B 本地模型，工具调用开始乱填参数，循环直接卡死。

## 做法

1. **先给任务分类**。四类：会话主循环、复杂规划/多工具编排、批量轻任务（摘要、分类、格式化）、涉隐私任务（读凭证、私人文件）。
2. **主循环用云端旗舰模型**。这是能力基线，工具调用质量直接取决于它，不建议省。
3. **批量轻任务下沉**。在配置里给子 agent / cron 任务单独指定便宜模型或本地模型，思路是 primary + fallback 两层（示意，具体键名以你版本的文档为准）：

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4.1",
        "fallbacks": ["ollama/qwen2.5:32b"]
      }
    }
  }
}
```

4. **涉隐私强制本地**。凡是会读到 `~/.ssh`、密码库、私人笔记的任务，写死路由到本地端点，不留自动判断的空间。
5. **fallback 链兜底**。云端限流或超时时自动降级到本地，保证自动化流程不中断。

## 踩坑点

- **小模型 function calling 很不稳**。7B~14B 做纯文本没问题，一旦进工具循环就容易重复调用或参数幻觉。本地模型只路由纯文本任务。
- **上下文长度差一个量级**。云端 200k、本地常见 32k，长会话切过去会静默截断，表现为“模型突然失忆”。先查路由日志确认实际用了哪个模型，别急着改 prompt。
- **Ollama 默认会卸载模型**，cron 触发时要等 30 秒以上冷加载。把 `keep_alive` 拉长，或在任务前跑一个空请求预热。
- **fallback 静默切换会让同一段对话“换人格”**，输出风格突变时先怀疑降级，再怀疑别的原因。

## 可复用建议

- 按“任务类型”路由，不按时间段或拍脑袋路由，规则写死行为才可预测。
- 所有 provider 统一走 OpenAI 兼容端点封装，切换模型只改配置不动代码。
- 每周看一次 token 消耗分布，哪个模型占比异常就回头查路由规则。
- 大规模下沉本地之前，先双轨跑一周对比输出质量，再决定切多少。

## 总结

多模型路由本质上是排班：高风险高复杂度的活给云端旗舰，确定性强的批量活和涉隐私的活给本地。先用云模型把能力基线立住，再逐步把任务下沉，比一步到位省钱靠谱得多。
