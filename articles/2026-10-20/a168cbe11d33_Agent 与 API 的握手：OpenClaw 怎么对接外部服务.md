## 背景

OpenClaw 这类 agent 的能力上限，基本等于它能碰到的外部服务总和。模型本体只负责理解和编排，查天气、写工单、拉库存这些动作全靠工具调用落地。OpenClaw 对接外部服务主要有两条路：挂一个 MCP server，或者自己写插件注册 tool。这篇帖基于最近给内部服务做对接的过程，把踩过的坑和沉淀出的模式整理出来，供要动手的同学参考。

## 问题

对过几个服务之后发现，"调通"是最容易的一步，麻烦的是稳定性和可控性：

- 密钥管理混乱，API key 明文写在配置文件里被提交进仓库；
- 模型偶尔幻觉出参数，调用带着空值就发出去了；
- 网络抖动 + 盲目重试，同一个写操作被执行了两次；
- 工具描述写得太随意，agent 该调的时候不调，不该调的时候乱调。

这些都不是 API 本身的问题，而是适配层没做工程化。

## 做法与步骤

1. **先找现成 MCP server。** 常见服务（代码托管、消息平台、数据库这类）社区基本都有实现，直接在 OpenClaw 的 MCP 配置里挂上，stdio 启动即可。造轮子之前先搜一遍。
2. **没有就写薄适配插件。** 原则：一个服务一个插件，插件里只做参数校验、鉴权注入、响应裁剪，不塞业务逻辑。
3. **认真写工具 schema。** 参数砍到最少；description 里明确写"什么时候该用、什么时候别用、失败怎么办"。这段文案的质量直接决定 agent 的调用准确率。
4. **密钥走环境变量。** 插件里只读 `process.env`，配置文件只留变量名，不落盘、不进日志。
5. **超时和重试分开治理。** 所有调用设硬超时；重试只对幂等的 GET 开启，写操作要么不重试，要么带唯一 request id 让服务端去重。
6. **错误结构化返回。** 插件捕获异常后统一吐 `{ok, data, error}` 格式，agent 拿到的是一句话人话错误，不是 30 行堆栈——堆栈对模型没用，还污染上下文。

## 踩坑点

- **大 JSON 直接塞给模型**：某接口单次返回 40KB，几轮对话上下文就满了。后来在适配层做字段白名单，只留模型需要的部分。
- **写操作没幂等保护**：一次重试创建了三张重复工单。此后所有 POST 请求强制带 request id。
- **漏设超时**：上游服务挂了，agent 干等不报错，看起来像死机。现在默认 10s 超时，超时即返回可读错误。
- **描述含糊**：两个工具都能"查订单"，agent 随机二选一。在描述里写清各自负责的订单类型后解决。

## 可复用建议

1. 上线前先用 curl 走一遍真实 API，别迷信文档；
2. 先只接只读接口跑稳，再放开写操作；
3. 每个工具配一组固定 prompt 回归用例，改完插件就跑一遍；
4. 日志一律脱敏，URL 里的 token 全部打码。

## 总结

对接外部服务，工程重心不在"能不能调通"，而在适配层把鉴权、超时、幂等、错误格式这些脏活全部兜住，让 agent 层看到的工具又小又干净。适配层做得越厚，agent 行为越稳。这套模式放到任何工具型 agent 上都适用，欢迎跟帖补充你们实践中的变体和坑。
