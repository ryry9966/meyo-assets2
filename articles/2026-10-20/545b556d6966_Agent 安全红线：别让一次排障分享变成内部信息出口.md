## 背景

在 OpenClaw 这类社区里，把 agent 的 system prompt、MCP 配置、执行 trace 贴出来求助，是最高效的排障方式；另一种常见场景是让 agent 定时整理"本周自动化工作流"，通过插件自动发到社区频道。两者都合理，但 agent 的上下文天然混着三类东西：配置里的凭证、prompt 里写死的内部流程、运行时检索到的内部文档。泄露面因此从代码仓库扩展到了对话记录和配置文件。

## 问题的三个层面

- **配置层**：MCP server 的 JSON 配置里，env 字段经常直接内联 token、内网地址、数据库连接串。发出去的就是钥匙本身。
- **上下文层**：system prompt 里沉淀的内部工具命名、审批链路、业务规则，单看不算机密，拼起来就是一张攻击面地图。
- **行为层**：当 agent 拥有对外发布能力（webhook、社区发帖插件），自动摘要时可能把 RAG 检索到的内部文档原句带出去，而且没人逐字审过。

## 我们的做法

1. **先定密级，再动手**。三档：可公开、内部、敏感，写成一页纸规范。判断标准很简单——这条信息能不能帮人绕过我们的某道流程。
2. **配置脱敏脚本化**。token 一律走环境变量引用，不硬编码。写了个 scrub 脚本，正则匹配 `sk-` 前缀、`Bearer`、内网网段和内部域名，作为发配置前的强制步骤。
3. **prompt 分层**。内部 workflow 细节放在私有模块，社区求助只贴结构和占位符；替换占位符时连长度、格式一起改，不留结构线索。
4. **发布通道加闸门**。给 agent 的发帖类插件加 human-in-the-loop 确认；无人值守的自动化场景，限制它只能引用指定目录下的公开文档。
5. **trace 先脱敏再导出**。关掉 full payload 导出，或加一层 redact 中间件处理 tool arguments。

## 踩过的坑

- **截图比配置更容易漏**：终端上方的历史命令、浏览器标签页标题，都是无意识泄露。
- **"编辑过就没事"不成立**：群消息的编辑记录和引用还挂着原文。
- **占位符替换保真反而帮倒忙**：同长度的假 token 等于替攻击者确认了真实凭证的格式结构。
- **memory 文件被顺手打包**：agent 的长期记忆里沉淀了大量内部细节，分享项目时经常跟着一起走。
- **内部工具名被低估**：工具名加参数 schema，足以让外部拼出可尝试的调用面。

## 可复用的建议

- scrub 脚本做成 pre-commit 或发帖模板的一部分，靠流程兜底，不靠自觉。
- 社区提问模板只要求最小复现：框架版本、报错信息、脱敏后的配置结构。
- 每次给 agent 挂新工具前先问一句：它有没有对外输出通道？
- 定期 review system prompt，删掉不再需要的内部细节——prompt 不该是历史档案。

## 总结

Agent 的上下文本质上是一份持续生成的内部文档，它的边界就是我们授予的权限和开放的发布通道。安全不靠事后撤回消息，靠默认约束：最小权限、发布前脱敏、对外输出加人工确认。这三条守住，社区分享才能既高效又安心。
