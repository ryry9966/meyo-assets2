## 背景

我们的 OpenClaw agent 日常要处理三类活：复杂规划、批量文本处理、结构化抽取。早期全部走云端强模型，agent 循环里每步都带全量上下文，月底账单不好看；后来试图全换本地模型，又在多步工具调用上频繁翻车。多模型路由就是在这两个极端之间找平衡，而不是选边站。

## 问题

核心矛盾有三个：

- **成本**：强模型跑“改写一段话”这种任务纯属浪费，但这类任务往往占了大头流量；
- **隐私**：日志分析、内部文档摘要类数据不适合出网；
- **质量陷阱**：本地小模型对复杂推理会“安静地失败”——不报错、不抛异常，只是输出变差，问题拖到下游工具调用阶段才暴露，排查成本极高。

## 做法

**第一步，给任务分层，而不是给模型排名：**

- A 层（规划、代码生成、多工具编排）：云端强模型；
- B 层（摘要、改写、分类、抽取）：本地 7B~14B 足够；
- C 层（格式转换、字段拼接）：直接写代码，别过任何模型。

**第二步，在 OpenClaw 配置里按任务标签建 model profile 路由（示意）：**

```yaml
routes:
  planner:   cloud/gpt-4o-class
  extractor: local/qwen2.5-14b
  formatter: rules   # 确定性规则，不走模型
```

**第三步，加降级链路**：本地输出先过 JSON schema 校验，失败或置信度低就回退云端，同时设置重试上限，避免“本地失败 → 云端重跑 → 双倍开销”。

**第四步，建一个小评测集**（30~50 条真实 case），每次调整路由后跑一遍。路由对不对，用数据说话，不靠体感。

## 踩坑点

1. **长上下文别交给本地模型。** 超过 20~30k token 后小模型质量明显下滑，这类请求直接路由云端，别指望降级兜底。
2. **工具调用格式是重灾区。** 本地模型生成的 tool call 参数经常不合规，重试成本比省下的 token 还高。schema 校验必须前置，不合格直接切模型。
3. **路由器本身别用大模型。** 用规则（任务标签、预估 token 数、是否带工具调用）判断。引入“用 GPT 决定该不该用 GPT”是本末倒置。
4. **本地延迟要实测。** GPU 上同时跑 embedding 和 RAG 时，本地推理延迟和官标差很远，压测环境必须贴近生产。
5. **静默降级要留痕。** 每次回退云端都打日志。一周下来，你会拿到本地模型真实的可靠率，而不是 benchmark 上的那个数字。

## 可复用建议

- 先只路由最高频的两三类任务，覆盖 80% 流量即可，别一上来做通用路由框架；
- “便宜模型优先、失败升级”在工程上比“贵模型兜底再省钱”稳定得多；
- 每类任务维护一张记分卡：成功率、平均 token、P95 延迟，路由调整只看这张表；
- 模型配置收敛到一处，禁止在插件和脚本里散落写死模型名；
- 能用确定性代码解决的，永远不要交给任何 LLM。

## 总结

多模型路由本质上是个成本与可靠性的工程问题，不是模型排行榜问题。结论可以压缩成一句话：**规划和编排交给云端强模型，批量文本交给本地小模型，格式和拼接交给代码，然后用评测集和降级日志持续校准。** 我们跑了一个月后，token 成本降了约 60%，P95 延迟反而更稳——这比任何跑分都有说服力。欢迎在评论区贴你们的路由规则和记分卡数据。
