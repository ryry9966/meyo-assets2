## 背景

现在大多数 AI 助手还是被动应答式：用户提问，agent 回答。MCP 和插件让 agent 有了动手能力，但动手时机仍握在用户手里。而实践中大量高频需求本质是周期性或事件驱动的：盯 CI 状态、看磁盘水位、扫订阅源、等某个审批通过。这类事用户得自己记着来问，agent 的价值就打了对折。

## 问题

把"定时跑个脚本"当成 proactive 是常见误解。真正的 proactive 要同时回答三个问题：**什么时候动**（触发）、**动什么**（权限与范围）、**什么时候闭嘴**（打扰控制）。三者缺一，就会滑向两种失败：要么永远沉默，要么变成每小时刷屏的噪音机器。

## 做法：拆成三层

**1. 触发层。** 三类来源：cron/heartbeat 兜底周期任务；事件订阅（webhook、文件变更、MCP resource 通知）；带阈值的状态轮询（磁盘 > 85% 才报，不是每分钟报一次）。触发条件全部用确定性规则表达，不交给模型临场判断。

**2. 决策与执行层。** 每个 proactive 任务用一份 manifest 声明：触发条件、可调用的工具白名单、动作分级、冷却时间。读操作默认自动执行；写操作一律 dry-run，产出"将要做什么"的报告，或进入审批队列。agent 被触发后只做两件事：核对条件是否仍成立、生成消息内容。

**3. 反馈层。** 每条主动消息强制带三个字段：触发来源、证据（数据或链接）、建议动作。用户可点赞/点踩，结果回写到阈值与冷却配置。每天主动消息设硬上限。

## 踩坑点

- **心跳风暴**：没加冷却和去重，磁盘 84% 这种没到线的状态每分钟报一次。解法：触发时记录状态指纹，状态未变不重复触发。
- **静默失败**：调度器挂了 agent 不说话，用户误以为一切正常。解法：加 watchdog 心跳，N 小时没动静主动报一句"我还活着，跑了 X 次检查"。
- **越权自动化**：为了省一步把重启服务放进自动路径，出事无法回滚。解法：写操作永远 dry-run 或审批，kill switch 常开。
- **上下文污染**：主动消息混进会话历史，把对话带偏、把 token 撑爆。解法：proactive 走独立通道，用户回复时才注入。
- **让模型决定"要不要打扰"**：LLM 判断不稳定，同样状态有时报有时不报。解法：模型只负责内容生成，达不达标由规则说了算。

## 可复用建议

1. 用声明式 manifest 管理所有主动任务，别散落在 system prompt 里。
2. 权限按"只读 → 写 → 自主"逐级放开，每级观察一两周再进下一级。
3. 打扰预算是产品决策不是技术细节，阈值和用户一起调。
4. 所有主动行为可追溯：日志里必须能回答"它为什么在这个时刻说话"。

## 总结

proactive 的本质不是让 agent 更自由，而是把"何时行动"从隐式 prompt 搬进显式工程契约：触发确定、执行分级、反馈闭环。做到这三点，"不等你开口"才不会变成"不听你指挥"。建议从一两个只读监控任务起步，跑通全链路后再逐步扩展——主动能力是长出来的，不是一次性开关。
