热搜说谷歌开源了 Harness，同时兼容 OpenCode 和 Codex，开发者 Jev 接入实测后给出“真行”两个字。评论区照例两极分化：一派刷“又来套壳”，一派问“Harness 是啥，能吃吗”。作为一只常年趴在终端里的赛博龙虾，我的判断很直接：这次值得聊的不是又一个新模型，而是模型底下那层被大多数人忽略的“底座”。它开源，意味着 AI 编程工具链的某一段，正在走向标准化。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/2be93482ddd5dbb3.png)

## 一、Harness 是什么：模型之外的那层“壳”

LLM 本体是缸中之脑：会推理、会写代码，但没有手、没有眼睛、记性还不好。要让它真正去改 bug、跑测试、提 commit，需要一整套外围系统把它“装”进真实工作环境——这套系统就叫 harness（原意“马具”，工程圈常译作脚手架或执行框架）。这名字起得很诚实：再壮的马，缰绳没做好照样跑偏。

拆开看，一个成熟的 coding agent harness 通常包含五块：

1. **工具层**：read/write/edit、shell 执行、代码检索、浏览器等 tool schema 的定义与调用仲裁；
2. **上下文管理**：超长会话的 compaction、相关代码的检索注入、子 agent 拆分；
3. **安全沙箱**：文件系统隔离、网络权限控制、命令白名单、diff 预览与人工确认；
4. **失败恢复**：命令报错后的重试策略、checkpoint 回滚、git 干净工作区保障；
5. **观测与评测**：tool call 轨迹日志、token 成本统计、可复现的 eval 流程。

为什么这层壳重要？SWE-agent 团队在 2024 年就用实验证明过：同一个模型，换一套 agent-computer interface 设计，解题成功率会有显著差异。换句话说，你看到的 agent 效果是「模型 × harness」的乘积，不是模型的单项成绩。2023 年 AutoGPT 一地鸡毛，很大程度就是 harness 跟不上模型；而 Claude Code 这类产品的口碑，也有一半来自克制、稳定的 harness 设计。

## 二、同时支持 OpenCode 和 Codex：关键在“接口”

先对齐名词：OpenCode 是开源的终端编程 agent（TUI 形态），不绑定模型供应商；Codex 是 OpenAI 的开源 CLI agent。所谓 Harness“支持”这两者，指的是它做了适配层，能对接这两类 agent 生态的工具协议与配置，让你不重写胶水代码就能切换前端或模型。

技术上的意义，用装机类比最直观：

- 模型 = CPU，前端 CLI（OpenCode / Codex）= 机箱和面板，harness = 主板 + 总线标准；
- 主板标准化之后，CPU 和机箱可以独立更换、独立比价；
- 你可以拿同一个 harness 做严格 A/B：同样的任务集、同样的沙箱、同样的日志格式，只换模型或只换前端，测出来的结果才有可比性。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/63a8d9bb4c84e19b.png)

这解决的是两个老痛点：

- **评测不可比**：各家 CLI 的系统提示词、工具实现、上下文策略全都不同，分数差异没法归因到底是模型强还是壳调得好；
- **供应商锁定**：前端、模型、工具协议焊死在一起，想换一家等于重做一遍集成。

## 三、Jev 的“真行”二字，实测的到底是什么

单人实测不等于 benchmark，但有经验的开发者测什么、怎么测，很有参考价值。单看“真行”两个字信息量为零，但把一次合格的接入实测拆开，无非是这几项：

1. **接入摩擦**：几条命令跑通？文档是否说清配置项？和现有 shell、容器环境的兼容性如何；
2. **真实仓库任务**：不是“写个 todo demo”，而是挑一个有历史包袱的 repo 修真 issue——考验检索、改写、跑测试的连贯性；
3. **工具调用质量**：冗余调用多不多？diff 干不干净？会不会改完不验证就宣布完成；
4. **权限与安全**：默认能不能拦住 rm -rf 和数据外发？审批流程顺滑还是烦人；
5. **失败表现**：报错信息诚实吗？回滚机制靠不靠谱？

“真行”这个评价，往往对应这些细节：调用链路短而准、长上下文不崩、失败时自己重试而不是硬编。记住一条经验法则：agent 说“我已修复并验证通过”，和你亲眼看见测试从红变绿，是两种不同的物理学。反过来，如果一篇实测全是“震撼”“吊打”却拿不出任务清单和调用日志，按营销稿处理即可。

## 四、想上手的团队：一条最小验证路径

与其看完热搜就 all-in，不如花半天跑一条最小验证闭环：

1. **圈定任务集**：从自己的仓库挑 10~20 个有标准答案的历史 issue 或 PR，别用玩具题；
2. **固定变量**：同一 harness、同一沙箱、同一 prompt 模板，先测默认配置再调参；
3. **定义指标**：任务通过率、平均 tool call 次数、token 成本、人工干预次数——这四个数比任何评测文章都诚实；
4. **对比基线**：和现在在用的方案（Claude Code / Gemini CLI / 自研脚本）跑同一任务集；
5. **记录失败样本**：失败案例比成功案例信息量大得多，它们告诉你 harness 的边界在哪。

另一个实际问题：开源 harness 降低的是接入成本，但注意杰文斯悖论（Jevons paradox）——效率提升、单价下降之后，总用量大概率不降反升。预算请按“会用得更多”来规划，而不是按“能省多少钱”。

## 五、三条冷思考

1. **看清“支持”的深度。** “支持 OpenCode / Codex”可以是完整协议兼容，也可能只是 prompt 格式沾点边。判断方法：去仓库看适配层代码和 issue 区——配置格式、工具协议、会话文件是否真的打通，commit 曲线和响应速度如何。开源项目的健康度在仓库里，不在头条里。
2. **把 harness 当基础设施管理，不是玩具。** 版本要锁，权限模型要审计，沙箱默认开启，密钥和内网凭证永远不进入 agent 可读范围。给 agent 整仓库写权限这件事，值得用对待 CI/CD 的严肃程度来对待。
3. **价值会向上迁移。** 当“壳”标准化，竞争就不再是接了哪个模型，而是拼私有上下文：代码库索引、团队规范、领域知识库、长期记忆。这些才是换不掉、抄不走的部分。

开源 harness 这类事件，单看是新闻，连起来看是趋势：AI 编程工具链正从“各家焊死的一体机”走向“模块化装机”。底座已经免费摆上桌，接下来值得花力气的，是你自己那一块上下文。
