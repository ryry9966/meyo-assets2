## 背景

我们团队的服务日志、Agent 任务执行记录、各插件回调散落在三处：主机上的 log 文件、几张数据库表、以及若干 webhook 的原始 payload。日报一直靠人晚上手工整理，经常漏项，格式也不稳定。这篇记录用 OpenClaw 把这件事做成无人值守流水线的过程，思路可直接迁移。

## 问题

真正卡住自动化的不是“写日报”本身，而是三件事：

1. 日志格式不统一，没法直接喂给模型；
2. 直接让 LLM 总结原始日志，会漏数据、算错数字，结果不可信；
3. 流水线自己挂了没人知道，日报缺失往往隔天才被发现。

## 做法

整条流水线拆成 **normalize → aggregate → narrate** 三段：

**1. 归一化（normalize）**。写一个独立收集脚本（不经过模型），把三类来源统一转成固定 JSON Schema：`{timestamp, source, level, service, metrics, message}`，每天落一份到 `logs/YYYY-MM-DD.jsonl`，时区统一转 UTC+8 存储。

**2. 聚合（aggregate）**。同样是纯代码，零模型调用：按服务统计错误数、耗时分布、环比变化，输出中间产物 `digest.json`。所有数字在这一步定死。

**3. 叙述（narrate）**。这一步才用 OpenClaw。建一个定时 Agent 任务，每天 09:00 触发：通过 MCP 只读工具读取 `digest.json` 和日报模板，按模板生成 Markdown 日报，异常项单独成段，推送到群 webhook，并把成品与 `digest.json` 一起归档。

关键在分工：**代码负责“算”，Agent 负责“说”**。LLM 只拿到聚合后的几百行 JSON，不接触原始日志，token 可控，几乎没有自由发挥的空间——这正是我们要的。

## 踩坑点

- **别让 LLM 直接读原始日志**。第一版偷懒直接喂 jsonl，几千行日志漏读近半，还编了一个不存在的环比。教训：模型上下文不是数据库。
- **数字必须由代码产出**。哪怕让模型“只做个求和”，错误率也不可接受。
- **水位线问题**。收集脚本要记录上次处理到的位置，否则补跑一次就重复计数，环比直接失真。
- **权限最小化**。给日报 Agent 的 MCP 工具只有两个：读文件、发 webhook。不要图省事复用通用工具集。
- **流水线要自监控**。聚合失败或推送失败走独立告警通道（不要发日报群）——日报群收不到消息本身就是异常，但没人会主动注意到。

## 可复用建议

- 三段式 normalize → aggregate → narrate 同样适用于周报、告警汇总、复盘材料，不只是日报；
- Schema 先行：先定中间数据结构，再写收集与渲染，返工最少；
- 中间产物落盘：`digest.json` 留档后，排查“日报里这个数字哪来的”只需看两个文件，不用回放 Agent 会话；
- 模板版本化进仓库，日报格式变更走 review。

## 总结

这套流水线上线两个月，日报从每天约 20 分钟的人肉活变成零操作，准确率反而高于人工。核心经验一句话：**把确定性的事情交给代码，把 LLM 放在最小、最可控的位置上**。Agent 在这里的真正价值不是“全自动”，而是稳定的格式化输出和低成本的接入成本。
