## 背景：上下文预算才是硬约束

玩 Agent 的人迟早会撞上同一个问题：能力越多，上下文越贵。把所有工具说明、操作手册全塞进 system prompt，几千上万 token 起步，而且每轮对话都在重复付费；指令一多，模型遵循单条指令的概率反而下降，这是注意力机制的物理现实。

OpenClaw 的 Skills 机制本质上是把"能力"从常驻内存改成按需分页（progressive disclosure）：启动时只注入每个技能的一行名字和描述，正文只有当任务真正匹配时才被读进来。思路和操作系统的虚拟内存一样——不常用的页不占物理内存。

## 问题：为什么不是"全都写进 prompt"

- token 成本随能力数量线性增长，长对话尤其明显；
- 指令堆积稀释注意力，流程越复杂越容易走偏；
- 想给助手加私有工作流（比如内部发布流程），改源码或堆 prompt 都不可维护。

Skills 用"一个文件夹即一个能力"解决了扩展性问题：不写代码，写文档就行。

## 做法：五步接入一个自定义 Skill

1. 在技能目录（workspace 内的 `skills/` 或用户级 `~/.openclaw/skills/`）下建目录，例如 `deploy-check/`，里面放一个 `SKILL.md`。
2. 头部写 YAML frontmatter，`name` 和 `description` 是关键字段。description 是路由依据，要写清"什么场景用、覆盖什么任务"，例如"当用户要求检查线上发布状态或回滚时使用"。
3. 正文用 Markdown 写操作流程：步骤、判断条件、命令示例。模型读的就是这份文档。
4. 细节再拆一层：长表格、边界情况放进 `references/`，确定性操作写成脚本放在技能目录里，正文只写"执行 `scripts/check.sh`"。SKILL.md 控制在几百行内，脚本和参考文件才是懒加载的主体。
5. 重启 gateway 或触发热重载，问一句"你现在有哪些能力"，验证路由是否生效。

## 踩坑点

- **description 含糊**，技能永远不会被触发；**写得太宽**，又会抢别的技能的活。把它当搜索引擎关键词来写，尽量包含用户实际的问法。
- **frontmatter 格式错误**（缩进、冒号后没空格）会导致技能静默失效，日志里不一定明显。改完务必实际对话验证。
- **把所有内容堆进 SKILL.md**，等于把 prompt 膨胀换了个地方存放。技能被加载后照样吃上下文，分层要分到第二、第三层。
- **SKILL.md 是指令不是代码**。脚本依赖的环境（Python 包、CLI 工具）要自己保证装好，模型只会照着跑。
- **多个技能描述语义撞车**时，路由结果不可预测。上线新技能前先全局搜一遍有没有重叠。

## 可复用建议

- 一个技能对应一个任务域，别做"大而全"的超级技能；
- 判断类内容用文字写，确定性步骤写成脚本，让模型少自由发挥；
- 把 skills 目录放进 git——技能就是 prompt 资产，要有版本和 review；
- 排查路由最快的方法：直接问 agent "针对 X 你会用哪个技能、为什么"，路由逻辑立刻现形。

## 总结

Skills 机制没有黑魔法，它只是把一个朴素的工程原则做进了产品：常驻的只留索引，详情按需加载。对个人用户，它是低成本扩展助手能力的入口；对团队，它是把操作规程沉淀成可复用资产的载体。写好 description、做好分层、保持克制，技能数量上去之后系统依然可控。
