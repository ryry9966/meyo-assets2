## 背景

OpenClaw 的主会话按 session key 持久化完整上下文：用户每句话、每次工具调用、每段工具返回值，都进同一个上下文窗口。日常问答没问题，但一旦跑自动化——MCP 工具链、网页抓取、批量文件处理——中间产物会迅速把主会话撑大。

## 问题

最常见的翻车姿势，是把子任务直接跑在主会话里。后果有三层：

1. **上下文膨胀**：一个抓 20 个页面的研究任务，中间返回值可能吃掉几万 token，提前触发 compact，摘要丢细节；
2. **跨话题污染**：上一次任务的搜索结果残留在上下文里，模型后续回答会"记得"不该记得的东西，行为漂移；
3. **成本失控**：每轮对话都背着历史中间产物付费。

## 做法

OpenClaw 提供了 `sessions_spawn` 这类派生工具，核心机制是：子 agent 拿到一个**独立的 session key**，拥有自己的干净上下文，跑完后只把最终结果作为一次工具返回值送回父会话。落地上分四步：

1. **定义单一任务**：一次 spawn 只干一件事，目标和约束写清楚；
2. **限定工具白名单**：只给完成该任务所需的最小工具集，给得越少，跑偏概率越低；
3. **约定返回契约**：明确"返回 JSON、不超过 300 字、只含结论和来源"这类硬约束——返回值本身也会进父会话；
4. **验证隔离生效**：用会话列表或日志确认子会话 key 独立，主会话里应当只看到一条 spawn 调用和一条干净结果。

多个子任务可以并行 spawn，各自隔离、互不可见。

## 踩坑点

- **文件系统不隔离**：子会话隔离的是上下文，不是磁盘。子 agent 往共享的 MEMORY 或工作区写文件，会以另一种方式"漏"回主会话。这是显式通道，要么有意利用，要么在 spawn 提示里明确禁写；
- **返回值超长**：忘了设返回契约，子 agent 回来一篇长文，污染只是从 20 条工具调用变成 1 条巨长消息；
- **递归嵌套**：子 agent 里再 spawn 子 agent，链路失控且难排障，默认禁止；
- **复位范围误解**：`/new` 只重置主会话，残留的子会话要单独清理；
- **会话归属搞混**：群聊和私聊是不同 session key，注意 spawn 出去的会话挂在哪个 key 下。

## 可复用建议

- 把委派模板沉淀成固定片段：**任务 / 约束 / 返回契约** 三段式，每次复用只改任务段；
- 委派前自问一句：中间产物真的需要进主上下文吗？绝大多数时候不需要；
- 定期用 `/status` 看 token 占用，隔离生效时主会话增长应明显放缓；
- 高频子任务固化成脚本或插件配置，避免每次手写 spawn 参数。

## 总结

子会话隔离不是花活，而是控制上下文成本、保持模型行为稳定的基础工程手段。一句话原则：**主会话只保留决策，执行细节全部下沉**。上下文窗口是稀缺资源，把它留给真正需要长期记住的东西。
