## 背景

单个 agent 串行干活的老问题大家都遇到过：上下文越滚越大，中途产物把主对话挤爆，一个长任务跑半小时，中途改个需求就得重来。我们在几条自动化流水线里（批量代码审查、多仓库依赖升级、日志巡检）引入 subagent 编排后，同样的任务耗时从 40 分钟压到 8 分钟左右，更重要的是——主 agent 的上下文终于干净了。

## 问题

典型场景：让主 agent 扫描 20 个仓库，各写一份升级评估，最后汇总。串行模式下：

- 中间结果全堆在主对话里，跑到第 7 个仓库就开始“忘事”；
- 任何一步出错，整条链路重跑；
- 想并行，但默认执行循环就是单线程的，工具级并行救不了任务级串行。

## 做法

我们的编排结构不复杂，四步：

1. **拆任务**：主 agent 把目标拆成互相独立的子任务，每个子任务写成一个描述文件，包含任务边界、输入路径、输出格式。
2. **派发**：为每个子任务起一个 subagent。每个 subagent = 一段固定的系统提示 + 最小工具白名单 + 独立上下文窗口。父上下文不整体下发，只给任务文件路径。
3. **执行与落盘**：subagent 之间不直接通信，结果各写各的文件（如 `results/task-03.md`），固定 markdown 结构：结论 / 风险 / 明细三段。**文件就是消息总线**。
4. **汇总**：主 agent 不参与执行，只读结果文件做去重、交叉比对、写最终报告，且要求每个结论标注来源文件路径。

并发控制在 3~4 路，单任务超时 10 分钟，失败重试一次，再失败降级为串行补跑。

## 踩坑点

- **工作区冲突**：两个 subagent 同时改一个文件，git index 锁直接报错。按目录分片、给每个 subagent 独立 scratch 目录后才解决。
- **上下文继承的浪费**：起初把父对话整段传下去，token 开销翻了 5 倍，效果反而变差——subagent 被无关信息带偏。只传任务描述和必要路径即可。
- **subagent 越界**：让它评估依赖升级，它顺手“修”了两个不相关 bug。提示词必须写死边界：“只做 X，不修改任务范围外的任何文件”。
- **汇总幻觉**：主 agent 汇总时编造了结果文件里没有的细节。强制结论挂来源文件后收敛。
- **速率与配额**：4 路并发就是 4 倍 token 消耗速率，容易撞限流，加了信号量 + 指数退避。

## 可复用建议

- 把 subagent 当成“带契约的无状态 worker”：提示词模板化、工具白名单、固定输出结构，三者齐了才允许上线。
- 文件通信优于内存通信：可 grep、可 diff、可事后审计，排障成本最低。
- 先跑 2 并发测一轮，看 token 曲线和错误率，再决定扩到几路。
- 任务设计成幂等的：任何 subagent 挂了都能单独重跑，不影响其他分片。
- 每个 subagent 留一份运行日志，出问题先查日志再猜。

## 总结

subagent 编排的本质不是“多个 AI 一起跑”，而是**拆解 + 隔离 + 契约 + 汇总**这四件事。收益最大的其实是上下文隔离——主 agent 保持清醒，子任务互不污染。提示词写得再花哨，不如把任务边界、输出契约、失败重跑这三件工程活做扎实。建议从手头一个真实的批量任务开始，2 路并发起步，跑通再扩。
