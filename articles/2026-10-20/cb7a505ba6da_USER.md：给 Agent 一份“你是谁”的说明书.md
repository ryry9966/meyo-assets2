## 背景

用 OpenClaw 这类常驻 Agent 一段时间后，你会发现一个尴尬的现实：会话会过期，但你的偏好不会。今天告诉它“我在 UTC+8，回复用中文”，三天后新会话它又开始输出英文、按 UTC 算时间。system prompt 是静态的，改一次要走一遍配置流程；而 workspace 里的 USER.md 是给“用户”这一侧准备的持久化上下文——Agent 冷启动加载上下文时会读取它，相当于一份自动生效的自我介绍。

## 问题

没有 USER.md 时，典型的重复成本包括：

- 每个新会话重新交代时区、机器环境、常用技术栈；
- Agent 凭默认假设行事：在你的 Windows 机器上给 bash 命令，在深夜给你排“上午的任务”；
- 多人共用一个 Agent 实例时，它分不清现在在跟谁说话。

都是低级错误，但高频出现，每次纠正都在消耗耐心和 token。

## 做法

在 OpenClaw 的 workspace 目录（默认 `~/.openclaw/workspace/`，以你的实际配置为准）下建一个 `USER.md`，建议按这个骨架写：

```markdown
# 关于我
- 时区：UTC+8，工作时间 10:00–19:00
- 环境：macOS + Linux 服务器，shell 是 zsh
- 技术栈：Python / Go 为主，前端只求能跑

# 偏好
- 回复用中文，代码注释用英文
- 结论先行，不要铺垫
- 给命令前先说明它做什么

# 边界
- 不要主动执行 rm、git push --force
- 涉及付费 API 调用先确认

# 当前项目
- 网关改造（预计本月底收尾）
```

几个实践要点：

1. **控制篇幅**。这个文件每次会话都进上下文，50 行以内为宜，超了就该做减法。
2. **让 Agent 自己维护**。直接说“把这条偏好写进 USER.md”，比手动编辑更不容易遗漏。
3. **分清 USER.md 和 MEMORY.md**。前者是稳定的“我是谁”（身份、偏好、边界），后者是事件性的“发生过什么”。把“这周在调试 X”写进 USER.md，两周后它就是误导信息。
4. **进 git**。偏好的变更历史本身就是排障线索。

## 踩坑点

- **写敏感信息**。API key、密码绝对不要放进来——它会随上下文进入每次会话，日志和缓存里到处都是。
- **写成小作文**。叙事性段落让模型抓不住重点，用祈使句加短列表：“回复用中文”比“我平时比较习惯中文交流”有效得多。
- **与系统提示词冲突**。如果 system prompt 或 SOUL.md 里已有类似规则，两处说法不一致时行为会漂移，改一处要同步另一处。
- **只写一次**。环境换了、项目结了，文件不更新就成了负资产。建议每月扫一遍，删过时项。

## 可复用建议

- 新写完 USER.md 后，让 Agent 复述一遍它的理解，能立刻暴露歧义。
- 边界类规则要“可执行”：与其写“小心一点”，不如写“删除类命令先列出文件清单再确认”。
- 项目级上下文不要塞进 USER.md，放到项目内的 AGENTS.md，保持分层。
- 工作和个人两套身份差异大时，考虑两个 workspace 各自维护，别硬塞一个文件。

## 总结

USER.md 是成本极低、杠杆很高的一类配置：十几行 Markdown，换来的是 Agent 不再反复问、不再瞎猜。把它当成给 Agent 的“接口文档”来维护——有变更就提交，有冗余就裁剪。这个习惯建立之后你会发现，很多之前靠“多聊几句”弥补的问题，其实一行配置就能解决。
