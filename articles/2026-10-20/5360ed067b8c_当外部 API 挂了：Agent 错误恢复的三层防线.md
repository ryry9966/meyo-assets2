## 背景

一个 Agent 的能力边界，基本取决于它能调多少外部服务：LLM 本身、搜索、数据库、各类 MCP 工具。这些依赖没有一个是 100% 可用的。传统后端处理下游故障有成熟套路（重试、熔断、降级），但 Agent 有个特殊之处：**模型坐在调用链中间**，它会对故障做出"自己的解读"，而这套解读经常是错的。

## 问题：API 挂掉时的三种典型翻车

1. **幻觉兜底**。搜索 API 返回 500，模型不承认失败，而是"根据已有知识"编一个答案，语气还很自信。
2. **无限重试**。把重试决策完全交给模型，它可能在一个 429 上反复撞十几次，token 烧完为止。
3. **上下文污染**。原始 stack trace 或大段 HTML 错误页被塞进上下文，后续多轮推理全被带偏，甚至把密钥、内网路径带进输出。

三种问题的根因一致：错误没有被工程化地处理，而是被原样丢给了模型。

## 做法：三层防线

**第一层：调用层，代码兜底。** 每个外部调用都要有：明确超时（比如 10s，别让一次卡死拖住整个 loop）、指数退避重试（加 jitter，避免服务恢复瞬间被打穿）、以及区分可重试与不可重试——429/503/超时可重试，401/400 重试没有意义。

**第二层：工具层，把错误"翻译"给模型。** 不要把异常直接抛出去，用统一结构返回：

```json
{ "ok": false, "error_type": "upstream_timeout", "retryable": true, "hint": "search 暂不可用，可稍后重试或改用 cached_results 工具" }
```

关键是 `hint` 字段：告诉模型**还有哪些路可走**，而不只是告诉它失败了。模型只能在你给定的选项里做降级决策。

**第三层：策略层，降级与止损。** 在系统提示里写清楚故障策略：失败时如实告知用户、允许的降级路径（换备选工具、读缓存、标记数据可能过期）、总重试预算（如"最多 3 次，总耗时不超过 30s"）。注意预算要在代码里强制执行，提示词只是让模型配合。

## 踩坑点

- **对非幂等接口自动重试**。POST 下单重试三次 = 三个订单。写操作必须带幂等键，或者干脆不自动重试。
- **退避不加 jitter**。服务恢复瞬间，所有 Agent 同时发请求，二次打挂。
- **熔断阈值照抄大厂配置**。低频场景下连续 5 次失败可能是一个小时攒出来的，熔断器永远打不开。按自己的调用量调参。
- **降级不标注**。回退到缓存数据却不说，用户拿到三天前的价格还以为是实时的。降级输出必须显式声明。
- **只测 happy path**。本地起个 mock 固定返回 429 和 500，把故障路径跑一遍，很多问题（包括模型乱编）都能提前暴露。

## 可复用建议

1. 给所有工具封装统一的错误信封（ok / error_type / retryable / hint），一个装饰器能解决的事，不要每个工具各写一遍。
2. 重试用**预算**而不是次数：总时间 + 总 token 双上限。
3. 维护一份降级路径表：主工具挂了用什么顶上，写进系统提示或工具描述。
4. 日志记录结构化失败事件（工具名、错误类型、重试次数、最终结果），故障率上升要能告警，而不是等用户来报。

## 总结

外部 API 挂掉不是异常路径，是常态路径。核心原则一句话：**代码负责兜底和止损，模型只负责在给定选项里选择**。让模型直面原始错误，等于把系统可靠性押注在一次生成的概率上。把重试、熔断、降级做进工具层，Agent 才算一个能长期跑的服务，而不是一个演示。
