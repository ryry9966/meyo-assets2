## 背景

给 Agent 接上 shell 和文件工具之后，团队最担心的从来不是它“做不了”，而是它“做了不该做的”。误删文件是最典型的一类事故：一次路径解析错误、一个没写好的通配符，就足以让例行清理变成灾难现场。

OpenClaw 在设计上做了一个明确的取舍：**不指望模型永远正确，而是让模型即使错了也出不了边界**。

## 问题：提示词约束为什么靠不住

很多人的第一反应是在 system prompt 里写“不要删除重要文件”。实践中这基本无效：

1. **模型输出是概率性的**。同一条指令，在长上下文和工具结果的干扰下，遵循率会明显下降。
2. **删除往往不是显式的**。Agent 想清理构建产物，落到工具层可能是 `rm -rf ./build`，而 `./` 到底解析到哪取决于进程 cwd——模型经常算错。
3. **破坏发生在工具层**。即使意图正确，shell 展开、软链接、相对路径拼错，都可能让最终落盘路径偏离预期。

结论：安全边界必须放在**确定性的代码层**，而不是概率性的模型层。

## 做法：sandbox 的四层拦截

OpenClaw 的文件安全不是单一机制，而是四层叠加，任何一层放行了还有下一层兜底：

**1. 视图隔离（workspace root）**
会话启动时绑定一个 workspace 根目录，所有文件工具只接受该目录内的路径。外部路径在工具入口直接拒绝，模型“看不到”也“摸不到”系统其他部分。

**2. 能力声明（capability scope）**
每个 MCP 工具/插件注册时声明读写范围，deny 优先于 allow，且匹配发生在 `realpath` 解析之后的真实路径上：

```yaml
filesystem:
  allow: ["src/**", "docs/**"]
  deny:  ["**/.git/**", "secrets/**"]
```

**3. 危险操作策略门**
策略层对删除、递归写、批量覆盖做模式识别，命中后不直接执行，而是转入 dry-run：先产出变更集（哪些路径将被删除/改写）交用户确认，低风险项可按会话策略批量放行。

**4. 事务化落盘**
写操作先写临时文件、校验 diff 再原子替换；删除默认进 workspace 内的 `.trash/`（带时间戳），而非直接 unlink。配合快照，任意会话可整体回滚。

## 踩坑点

- **软链接逃逸**最容易漏：workspace 里的 symlink 指向外部目录，字符串校验全过，实际写穿了边界。必须对最终路径做 realpath 后再比对。
- **通配符展开发生在 shell 里**。策略层拿到的是展开后的参数，只匹配命令原文没用，要校验展开后的路径集合。
- **确认疲劳**。每个操作都弹确认，用户很快会无脑 yes。按风险分级：低风险批量授权，删除/覆盖类强制确认。
- **`.` 的歧义**。不同工具对相对路径 base 的解析可能不一致，统一在工具适配层归一化一次。

## 可复用建议

- 自己封装 MCP 文件工具时，路径校验写进工具实现，不要信任调用方传入的任何路径。
- 删除一律走回收站目录，成本极低，出事时救命。
- 每次工具调用记录 resolved paths 和操作摘要，日志可重放才能复盘。
- 定期做对抗测试：故意让 Agent“清理整个项目”，验证策略层是否接得住。

## 总结

Agent 安全的本质，是把 LLM 的不确定性关进一个确定性的执行环境。OpenClaw 之所以能防住误删，不是因为模型更聪明了，而是因为**模型根本没有机会触达不该触达的路径**——提示词负责引导，代码负责兜底。这套思路不依赖具体框架，任何做 Agent + 文件自动化的团队都值得照搬。
