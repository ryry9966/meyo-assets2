## 背景

OpenClaw 的 agent 每次会话启动时会读取工作区里的一组 Markdown 文件，AGENTS.md 是其中最核心的一份。可以把它理解为"写给 AI 的 README"：人类协作者靠 README 了解项目，agent 靠 AGENTS.md 了解你的工作区怎么用。

它不是配置文件，也不参与权限控制，本质上是注入给模型的一段上下文。正因为如此，怎么写、写多少，直接决定 agent 在你工作区里的行为质量。

## 问题

没有 AGENTS.md 或写得敷衍时，问题很固定：

- 每次会话都要在对话里重复交代："先跑测试再提交""别动 scripts 目录"；
- agent 行为在多次会话间漂移，今天守规矩，明天忘；
- 团队里每个人各自攒一份 prompt，经验不沉淀；
- 更糟的是写了一版就不再维护——仓库重构了，AGENTS.md 还是张旧地图，agent 按旧地图走路，比没地图更糟。

## 做法

我的经验是把它当作一份持续迭代的规格说明，分五步：

1. **先观察，后动笔。** 让 agent 在工作区里跑一两周，把反复出现的错误记下来。AGENTS.md 最好的素材不是你希望它做什么，而是它实际做错了什么。
2. **分区组织。** 建议结构：项目定位（一句话）→ 目录结构 → 常用命令 → 工作流约定 → 红线。
3. **写可执行的规则。** "提交前跑 `pnpm test`，失败不要 commit"远比"请保证代码质量"有效。规则里出现具体命令、具体路径，执行率明显更高。
4. **控制长度。** AGENTS.md 每个会话都占上下文预算。我的原则是单屏能看完，超了就砍——每条规则都在稀释其他规则的权重。
5. **进 git，定期审计。** 改动要有提交记录说明为什么改，每月花十分钟删掉过时条目。

一个可以直接套用的骨架：

```markdown
# AGENTS.md

## 项目定位
一句话说明这个工作区是什么、给谁用。

## 目录结构
- src/     业务逻辑，入口 src/index.ts
- scripts/ 运维脚本，改动后必须本地跑一遍

## 常用命令
- 测试：pnpm test
- 格式化：pnpm fmt

## 工作流约定
- 改动前先读相关模块，不顺手改无关文件
- 提交信息写清"为什么"

## 红线
- 不读取、不修改 .env 与任何密钥文件
- 不执行发布类命令
```

## 踩坑点

- **写成愿景文档。** "写高质量代码""保持谨慎"这类表述对模型几乎没有约束力，等于没写。
- **越写越长。** 加规则是下意识动作，删规则没人做。三个月后 500 行的 AGENTS.md 基本失效。
- **用它当记忆。** 过程性记忆（比如"用户偏好浅色主题"）应该进 MEMORY.md 之类的记忆文件，AGENTS.md 只放规则，不写日记。
- **期望它是硬约束。** 它是上下文，不是沙箱。真正的红线要靠工具权限配置兜底，AGENTS.md 里写的"红线"只是提前告知，不是保险丝。
- **别放敏感信息。** 它是纯文本，会整段进入模型上下文，密钥、内网地址一律不写。

## 可复用建议

- 每条规则尽量用"当 X 时，做 Y"的格式，比祈使句更稳。
- 分层维护：根目录放全局约定，子目录可以放更细的补充说明，agent 会就近参考。
- 团队场景下把它纳入 code review：改 AGENTS.md 和改代码走同样的流程，避免个人悄悄加规则。
- 新人入职让 TA 通读一遍 AGENTS.md，往往比读代码更快理解工程约定——这份文件同时对人和 agent 有效，这是一石二鸟的地方。

## 总结

AGENTS.md 本质上是你和 agent 之间的一份接口约定。它不神秘，也不万能：价值来自具体、简短、持续维护这三件事。把它当代码对待——有版本、有 review、有过期清理——agent 在你工作区里的表现就会稳定得多。反过来，这份文件写不好，调多少模型参数都补不回来。
