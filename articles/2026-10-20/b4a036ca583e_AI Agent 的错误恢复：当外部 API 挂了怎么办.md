## 背景

跑过稍长一点的 Agent 任务的人都有体会：链条越长，外部依赖越多，"挂"就不是会不会的问题，而是什么时候的问题。LLM API 限流、MCP 工具超时、第三方搜索接口 503，任何一环出问题都可能让一次跑了十分钟的任务前功尽弃。错误恢复不是加个 try/except 那么简单，它是 Agent 工程里真正影响可用性的部分。

## 问题

实际故障中最常见的三类现象：

1. **盲目重试**：收到 429 后立刻原样重发，越打越死，还在烧 token。
2. **假装成功**：API 失败后，模型不愿"承认失败"，基于上下文编造一个看似合理的返回值，后续步骤全部建立在假数据上。这是最危险的一种。
3. **状态丢失**：一次失败导致整个任务从头重跑，重复执行已经成功过的写操作。

## 做法

我们的经验是把错误恢复拆成四层，由内向外：

1. **错误分类**。先分清瞬时错误（429 / 503 / 超时 / 连接重置）和永久错误（401 / 404 / 参数校验失败）。瞬时错误才值得重试，永久错误重试纯属浪费。收到 429 必须读 `Retry-After`。

2. **有预算的重试**。指数退避加抖动（如 1s / 2s / 4s，±20% jitter），同时设三个上限：最大次数（3 次）、最大耗时、最大花费。任一预算耗尽即停止，不要依赖单一条件。

3. **降级路径**。每个关键依赖准备一个降级选项：备选供应商、本地缓存，或"跳过该步骤并如实说明"。降级要显式写进 Agent 上下文，例如"搜索接口不可用，本结论仅基于已有资料"——让模型和用户都知道数据的边界。

4. **断点续跑**。把每步结果持久化（哪怕只是写个 JSON 文件），恢复时跳过已完成步骤。写操作用幂等键：同一个 `task_id + step_id` 在服务端去重。

代码层面核心模式很短：一个统一的 resilient client 包装所有外呼，内置超时、重试、熔断（连续 N 次失败则熔断 X 秒）。上层工具只面对两种结果：成功，或一个明确的结构化失败。

## 踩坑点

- **非幂等操作直接重试**。发消息、下单类接口重试会重复执行。要么服务端支持幂等键，要么重试前先查状态。
- **只设单次超时，不设总预算**。每次调用 30 秒超时没问题，但 20 步循环照样能把任务卡死一整晚。
- **降级供应商 schema 不一致**。换了搜索 API，返回字段名不同，Agent 解析出空结果还以为"没有搜索结果"。降级层必须做适配，输出统一结构。
- **失败信息不回流**。API 挂了只体现在日志里，Agent 上下文看不到，下一轮它还会用同样方式调同一个挂掉的接口。要把"该工具当前不可用，上次失败原因 503"写进对话状态，Agent 才会换路。

## 可复用建议

- 所有外呼收口到一个 client 层，别在每个工具里散落 try/except。
- 给每个依赖维护轻量健康状态（可用 / 降级 / 熔断中），让 Agent 规划时能读到。
- 失败要结构化：`error_type`、`retryable`、`partial_result`，而不是一个字符串。
- 定期演练：手动停掉某个 API，看 Agent 是优雅降级还是当场去世。演练暴露的问题比压测多。

## 总结

外部 API 挂掉不可怕，可怕的是 Agent 对此一无所知。错误恢复的目标不是"永不失败"，而是失败发生时能快速识别、有节制地重试、明确地降级、诚实地告知。做到这四点，你的 Agent 才算从"演示能跑"迈向"线上能活"。
