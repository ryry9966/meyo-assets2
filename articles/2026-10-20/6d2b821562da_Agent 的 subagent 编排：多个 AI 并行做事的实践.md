## 背景

用 OpenClaw 跑了一段时间日常任务后，最明显的瓶颈不是模型能力，而是串行。主 agent 在一个会话里按顺序干活：抓 10 个网页、读 20 个文件、补 5 个模块的测试，每步都要等上一步结束。长任务还会把中间过程全堆进主会话，跑完一轮，上下文里全是网页正文和文件片段，有用的结论反而被稀释了。

subagent 编排就是冲着这两件事来的：**并行提速、上下文隔离**。主 agent 负责拆任务、派活、收结果；每个 subagent 有独立会话，干完只把压缩后的结果交回来。

## 什么样的问题适合并行

不是所有任务都值得拆。我只对同时满足三个条件的任务启用 subagent：**可切分**（能拆成 3 个以上粒度相近的子任务）、**无共享写**（子任务互不写同一文件、不依赖彼此的中间产出）、**结果可合并**（主 agent 能按固定格式拼起来）。典型场景：多仓库调研、批量补单测、对一批候选方案做独立评估。反过来，重构一个强耦合模块这种任务，强行拆只会制造冲突。

## 具体做法

以「调研 12 个开源项目的鉴权方案」为例：

1. **先串行跑一个样本**：挑 1 个项目，验证 subagent 的 prompt 能产出可用结果。这步省不掉，直接铺开 12 个，返工就是 12 份废结果。
2. **模板化派发**：给 subagent 的指令当成交接文档写——目标、输入位置（repo 地址/文件路径）、输出格式（固定 JSON 字段：结论、证据链接、置信度）、边界（不做无关分析、不改文件）。
3. **控制并发**：起步 3~5 个并行，观察 API 限流和本机负载再逐步上调。并发不是越大越好，token 成本是线性翻倍的。
4. **只收摘要**：subagent 返回结构化结果，不回传全过程。主 agent 拿到 12 份 JSON 后聚合、去重、出报告，主会话上下文始终干净。
5. **失败降级**：子任务失败重试一次，仍失败就标记未完成，不阻塞整体，报告里如实标注。

## 踩坑点

- **指令太模糊**：只说「帮我调研 X」，返回格式每次都不一样，没法聚合。输出 schema 必须写死在 prompt 里。
- **套娃**：subagent 又去开 subagent，层级一深，成本和排查难度指数上涨。我的做法是只允许一层。
- **写文件冲突**：多个 subagent 抢写同一个汇总文件，互相覆盖。改成各写各的临时文件，主 agent 统一合并。
- **回传过大**：有次 subagent 把整页正文塞回主会话，上下文瞬间爆掉。现在 prompt 里明确「摘要不超过 N 字」。
- **不抽查**：并行跑完不核对，等于把质量押在概率上。聚合前随机抽两份，确认证据链接真实存在。

## 可复用建议

- 把 subagent prompt 做成模板放进 skill/插件，改参数复用，不要每次现写；
- 记录每个子任务的耗时和成败，跑几轮就能估出合理的并发度和任务粒度；
- 聚合留在主 agent 做，subagent 只做独立可完成的事，子任务之间不要有协调依赖；
- 成本敏感的任务，subagent 用小模型，主 agent 用强模型做拆分和聚合。

## 总结

subagent 编排的核心不是开得越多越好，而是三件事：**把任务切干净、把上下文隔开、把结果收拢**。先串行验证、小并发起步、固定输出格式，这三条习惯能避开大部分坑。并行放大的是你任务分解的质量——拆得好，快十倍；拆得烂，废十份。
