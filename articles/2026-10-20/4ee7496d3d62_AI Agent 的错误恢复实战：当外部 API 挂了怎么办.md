## 背景

跑自动化任务的 Agent 很少只依赖一个服务。一条典型链路里，模型侧可能配置了多个 provider，工具侧通过 MCP 挂着搜索、数据库、webhook、第三方 SaaS。任务跑得越久、链路越长，「某个 API 在中途挂掉」就不是异常路径，而是每周都会遇到的常态。社区里不少翻车案例，问题往往不在 API 本身，而在 Agent 没有设计恢复路径。

## 问题

先看清三种典型故障形态：

1. **瞬时错误**：429、5xx、网络抖动，重试大概率能好；
2. **硬错误**：401/403、参数非法、配额耗尽，重试只会浪费资源；
3. **静默失败**：最危险的一种——工具返回了错误文本，LLM 把它当成正常结果继续推理，最后「成功地」产出一份基于报错信息编造的报告。

## 做法

- **加超时**：给所有工具调用设超时。没有超时的调用等于允许整个 workflow 无限挂起。
- **错误分类**：在统一的调用封装层把结果归一化成结构化对象 `{tool, error_type, retryable, hint}`。只对幂等操作重试，指数退避加随机抖动，上限 3 次。
- **把决策交还模型**：将结构化错误交回 LLM，让它在「换备用工具 / 跳过并标记 / 上报人工」之间选。不要吞掉错误，也不要把原始堆栈塞进上下文——又贵又容易带偏。
- **checkpoint**：链路上每个成功步骤落盘一次状态，失败后从断点恢复，而不是从头重跑。
- **熔断**：连续失败 N 次后进入冷却期，停止调用，窗口过了再探测。避免在对方限流时火上浇油。

## 踩坑点

- **对非幂等接口重试**：重复扣款、重复发消息都出过事故。要么加幂等键，要么重试前先查状态。
- **无限重试循环**：Agent 反复调同一个挂掉的接口，直到把 token 和账单烧穿。给每个任务设工具调用次数预算。
- **LLM 把报错当数据**：务必在代码层校验工具返回的 schema，发现错误字段直接拦截，不进模型。
- **超时两极化**：单调用超时太长会阻塞全局，太短会误杀慢接口。单工具超时和整个任务的 deadline 要分开设。

## 可复用建议

- 把「超时 + 分类 + 重试 + 结构化错误」做成一个统一的 resilient call 封装，所有插件共用，策略改一处生效。
- 维护一张错误分类表，放进系统提示或插件文档，让 Agent 对「能不能重试」有一致的判断。
- 主动做故障演练：写一个按概率返回 500 的 mock 工具，专门验证恢复路径。没被演练过的恢复逻辑，等于没有。

## 总结

错误恢复的目标不是消灭故障，而是控制故障的爆炸半径：分类、有界重试、断点续跑、降级、必要时交给人。一个可靠的 Agent，标准不是「从不出错」，而是出错后要么自己爬起来，要么大声喊人——最怕的是默默交出一份看似完整的垃圾结果。
