Agent 圈最近被一条消息刷了屏：按 36kr 的报道口径，DeepSeek 给自己的 Agent 体系装上了自研搜索能力，对外报价千次 5 元，还承诺“搜不到不收钱”，折算下来大约只有 Tavily 的十分之一。表面看这是一次价格战，但真正值得拆的不是“便宜”，而是两件事：搜索这个 Agent 最高频的外部工具，第一次被打到了“厘”级成本；计费方式也第一次从“按调用”改成了“按结果”。下面一层层拆开看。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/696360434ef9130a.png)

## 搜索 API：Agent 的“外接感官”

- 大模型的知识停在训练截止日。Agent 干活要靠工具，其中调用频率最高的就是搜索：查事实、查价格、查文档、查新闻，几乎每个任务都绕不开。
- 但 Agent 没法直接用搜索引擎的网页版——返回的是带广告的 HTML，解析脆弱还不稳定。于是出现了一层“给机器用的搜索 API”：输入自然语言 query，输出清洗过的结构化结果，包含标题、URL、摘要、正文抽取，附带去重和重排。
- 这条赛道上站着 Tavily、Exa、Serper、Brave，国内有博查等玩家。2025 年 8 月 Bing Search API 正式退役后，这个位置反而更显眼：上游说停就停，下游的 Agent 当场“失明”。
- 关键变量是频次。普通 Agent 任务跑 5~10 次检索很常见，Deep Research 类的多跳任务一次会话能打几十上百次。搜索因此成了 Agent 里边际成本最敏感的一环。

## 千次 5 元，到底便宜了多少

- 先算账：Tavily 入门付费档约 30 美元/4000 次基础检索，折算单次约 5 分钱人民币；千次 5 元即单次 5 厘，差了整整一个数量级。
- 放进业务里看：一个客服 Agent 月均 10 万次检索，前者约 5000+ 元/月，后者只要 500 元。对个人开发者，前者可能比模型 API 还贵——搜索比大脑贵，这事本身就挺赛博朋克。
- 更本质的变化是架构前提。当单次检索从“分”降到“厘”，过去因为贵而不敢做的模式突然在经济上成立：一路 query 拆成八路并发、每条结论再搜一轮交叉验证、长任务里反复追问。比如查一家公司的最新融资，顺着查它融资后的产品动作，再交叉验证两个信源——过去这么跑一轮要掂量成本，现在可以放心跑。
- 提醒一句：比价只是第一层，质量调整后的价格才是真价格——覆盖率、时效性、中文长尾、反垃圾，都得拿自己业务的真实 query 验过才算数。

## “搜不到不收钱”：一次风险反转的定价设计

- 传统 API 按调用计费，风险全在买方：搜出来一堆垃圾，钱照付，卖方旱涝保收。
- DeepSeek 把计费锚点从“调用”挪到了“结果”，类似法律行业的风险代理：买方只为有效交付付费，卖方对召回率负有直接的经济责任。
- 这个设计释放了两个信号：一是对自家索引覆盖和召回有相当的自信；二是把搜索从“流量生意”推向“结果生意”——卖方必须关心你到底搜没搜到，而不是你调了多少次。
- 但坑也埋在定义里。“搜到了”怎么算？返回了链接但内容过期、答非所问，算不算交付？API 替你判断不了业务相关性。所以“不收钱”应视作红利，而不是质量保证——结果校验这活儿，还是得留在自己的代码里。

## 为什么 DeepSeek 能报出这个价

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/5a4073a504b5cd43.png)

- 工程风格：DeepSeek 一贯把成本压到极限——V3 官方口径 557.6 万美元的训练成本（不含研发与 infra 全摊销）、推理端的 MLA/FP8 优化，都是公开案例。搜索基础设施大概率延续同一套思路。
- 成本结构：如果爬取、索引、排序全链路自建，就绕开了上游 SERP 供应商的层层加价，叠加国内机房与带宽成本，价格空间就这么腾了出来。
- 战略位置：每次检索返回的内容都要灌进模型消耗 token，把搜索做便宜，等于给自己的模型 API 引流——刀架便宜卖，刀片才是利润，经典的 razor-and-blades 打法。
- 当然，以上是对公开信息的合理推演，具体成本与毛利官方并未披露；价格能否在规模化后保持稳定，要看后续的可用性和一致性。

## 开发者现在该做的三件事

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/9e35be355228cce5.png)

1. **先测，别切。** 拿业务里沉淀的真实 query（几百条就够），对比 hit rate、relevance@5、结果时效分布和 P99 延迟。Agent 循环对延迟极其敏感，检索慢一步，整个任务就慢一步。
2. **做成可插拔，别写死。** 把搜索 provider 抽象成统一的工具接口，schema 别绑死在某一家。Bing API 说退就退的教训还热乎：外部搜索基础设施是有生命周期的，单点依赖要留后路。
3. **重新分配预算。** 省下来的钱建议花在检索次数上：query 分解、多跳追问、交叉验证，这些“笨办法”在检索便宜之后，往往比堆 prompt 更能拉正确率。同时盯紧 token 账单——搜索结果会膨胀上下文，省下的搜索钱很容易被 token 吃回去。

## 三条冷思考

- **便宜不是护城河，定义权才是。** “搜不到不收钱”听着全是善意，但“算不算搜到”的解释权在计费方。自己写一个轻量结果校验器——相关性打分、时效过滤、来源去重——把判定权拿回手里。
- **搜索层正在水电煤化，价值向上游迁移。** 当检索变成按斤称的 commodity，Agent 产品的差异化会集中到任务编排、结果加工和领域知识上。这一层，才是你该堆人堆时间的地方。
- **警惕价格锚定遮住真瓶颈。** 多数 Agent 的失败不是搜贵了，而是搜到了用不好：上下文塞满噪声、没有验证循环、query 写得一塌糊涂。降价解决的是“敢搜”，不解决“会搜”。

基础设施每便宜一个数量级，就会冒出一批过去不成立的应用。搜索这次降到“厘”级，值得每一个做 Agent 的人，重新画一遍自己的架构图。
