## 背景

OpenClaw 这类常驻 agent 的特点是"一直在跑"：消息通道的日常应答、定时摘要、告警归类，一天下来几百上千次调用。全走云端旗舰模型，成本和尾延迟都不好看；为了省钱全切本地模型，多工具编排和长上下文任务的成功率又会明显下滑。

所以真正要解决的不是"选哪个模型"，而是"让不同任务落到合适的模型上"。

## 三条判断标准

1. **失败成本**：摘要错了重跑就行，改配置、删文件的 agent 出错就是事故。失败成本高的走云端强模型。
2. **工具调用次数**：零到一次调用的轻任务，本地 14B 级别基本能扛；三次以上的多步编排，交给云端。
3. **数据敏感度**：涉及私人消息、密钥、内网拓扑的上下文，默认本地，除非明确降敏。

## 做法

分四步：

1. **给任务分层**。把自己的 skill 和定时任务列出来，手动打三个标签：轻、重、敏感。这步别偷懒，路由规则的质量取决于分层质量。
2. **配 primary + fallback**。每个常驻 agent 固定一组模型，本地为主云端兜底（或反过来），不让 agent 在运行时随机漂移。
3. **复杂路由做成薄预筛**。需求超出配置能表达的（按上下文长度、按会话是否带代码等），写一个很小的预路由 skill：本地小模型做一次分类，输出 local/cloud 再分发。预筛本身要足够便宜、足够快。
4. **加升级与熔断**。本地连续两次工具调用失败、或输出被校验拒绝，升级到云端重试一次；云端超时回退本地要设次数上限，防止来回踢皮球。

配置示意（字段名以你本地版本为准）：

```jsonc
{
  "agents": {
    "digest-bot": { "model": { "primary": "local/qwen-14b", "fallbacks": ["openai/gpt-4o-mini"] } },
    "ops-agent":  { "model": { "primary": "openai/gpt-4o",  "fallbacks": ["local/qwen-14b"] } }
  }
}
```

## 踩坑点

- **工具调用格式兼容性**：本地推理框架暴露的 function calling 与云端不完全一致，MCP 工具 schema 一复杂就容易解析失败。上线前先跑一轮工具调用冒烟测试，别只测闲聊。
- **上下文窗口陷阱**：云端跑了几十轮长会话，fallback 到 16k 的本地模型后历史被截断，agent 表现为"突然失忆"。你会先怀疑记忆系统，最后才发现是路由。
- **回退风暴**：云端超时→回本地→本地干不了→报错重试→又打回云端，一晚烧掉平时一周的量。fallback 必须有上限和熔断。
- **量化差异**：同一个 14B，Q4 和 Q8 的工具调用成功率差距很大，demo 表现不能外推到你的量化版本。
- **隐私别只看模型**：任务路由到本地了，某个 MCP 工具照样把上下文 POST 给第三方 webhook。敏感任务要把工具白名单一起收窄。

## 可复用建议

- 按**失败成本**路由，不要按"问题看起来简不简单"路由。
- 现实目标是把云端调用量降一个量级，而不是 100% 本地化：本地做草稿和预筛，云端做终审。
- 每次路由留一条日志：任务标签、实际命中的模型、重试次数。每周看一次命中率，再回头调阈值。
- 每个 agent 的模型组合固定下来写进它的说明里，避免"这周行为怎么变了"其实只是换了模型。

## 总结

多模型路由不是配置技巧，是任务分层问题：先按失败成本、工具复杂度、敏感度把活分清楚，再用 primary/fallback 和熔断把链路稳住，最后靠路由日志校准。做到这三层，本地模型能稳稳接住六到七成日常调用量，云端留给真正需要它的地方。
