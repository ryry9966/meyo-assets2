## 背景

OpenClaw 原生支持多 provider 接入，同一套 agent 配置里可以同时挂云端模型和本地模型。但群里被问得最多的问题之一是：到底什么时候该走 GPT 这类云端强模型，什么时候走本地？常见做法是两个极端——全程云端，月底账单吓人；或者全程本地，agent 在多步任务里频繁犯傻。这篇记录我这几个月在跑的分工方案，供参考。

## 问题

拆开看其实是三个矛盾：

1. **成本**：日志摘要、批量打标签这类活占了七成调用量，用强模型纯属浪费；
2. **能力**：规划、多工具编排、代码修改，本地 7B~14B 模型的 tool calling 成功率明显不行；
3. **隐私**：聊天记录、内网日志这类数据，团队要求不出本机，云端再便宜也不能碰。

一个模型满足不了三件事，所以只能路由。

## 做法：按"能力下限"分，不按心情分

先把任务分三类：

- **重活**：规划、工具编排、代码修改 → 云端强模型；
- **量活**：摘要、格式转换、通知文案 → 本地模型（我用 Ollama 跑 Qwen 系列）；
- **敏感活**：涉及本地日志和聊天记录的任务 → 强制本地。

配置上的思路是"强模型兜底，局部覆盖"，我的配置节选：

```jsonc
{
  "agents": {
    "defaults": { "model": { "primary": "openai/gpt-4o" } },
    "list": [
      { "id": "summarizer", "model": { "primary": "ollama/qwen2.5:14b" } }
    ]
  }
}
```

默认 agent 走 GPT 保质量，给干杂活的 summarizer 单独覆盖成本地模型，量最大的那部分开销就砍掉了。云模型限流或超时走 fallback，本地 provider 也可以放一条，但必须配告警，原因见下。

最后是观测：日志里记 model、耗时、token 数，每周扫一眼分布。路由规则对不对，数据会告诉你。

## 踩坑点

- **本地模型的 tool calling 不稳**：JSON 断裂、漏参数是常态。结论：本地只派单轮、无工具的活，一碰工具链就回云端。
- **上下文静默截断**：本地模型窗口小，接了长会话直接被截头，且不报错，agent 表现变差但你查不出异常。长上下文任务别路由给本地。
- **VRAM 争抢**：OpenClaw、嵌入模型、本地 LLM 挤同一台机器，峰值直接爆显存，路由配置得再好也没用。上线前先算显存账。
- **fallback 风暴**：云模型限流后请求全砸到本地，质量塌方且无告警，用户先于你发现。fallback 必须挂监控。
- **重试吃掉收益**：本地输出不合格、云端重试一次，省的 token 钱就回去了。别为了路由而路由。

## 可复用建议

1. 攒一份 20 条左右的固定评测任务集，改任何路由规则前先跑一遍，避免"感觉变好了"；
2. 路由规则写进配置仓库、走 review，别在运行时手改；
3. 每类任务只定一个主模型、一条 fallback，规则越多越难排障；
4. 默认模型宁可强一点，agent 智力水平的波动比账单更伤信任。

## 总结

多模型路由不是省钱技巧，而是把任务难度和模型能力对齐的工程手段。先分类、再配置、靠日志迭代，大部分纠结会自己消失。有更好的分工实践欢迎在群里拍砖。
