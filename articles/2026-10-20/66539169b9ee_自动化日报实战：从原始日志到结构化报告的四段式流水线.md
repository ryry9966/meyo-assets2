## 背景

做自动化之后最大的感受是"数据都在，报告不在"。git 提交、agent 会话日志、cron 执行记录、服务告警，每天都在产生原始记录，但真要回答"今天干了什么、哪里出了问题"，还是得靠人翻日志拼记忆。日报这件小事，恰好是最适合让 Agent 先跑起来的场景：输入明确、输出格式固定、出错也不致命。

## 问题

直接把日志丢给模型"总结一下"，效果通常不行：

1. 原始日志又长又脏，token 轻易超限，重点被稀释；
2. 模型倾向"凑内容"，日志里没有的事也能写出一段像模像样的描述；
3. 每次输出结构不一致，没法归档、对比和二次加工。

所以关键不是"能不能总结"，而是搭一条可控的流水线：**先收窄输入，再固定输出**。

## 做法

流水线分四步，跑在一台常驻机器的 OpenClaw 实例里，由定时任务每晚 22:30 触发。

**1. 采集与收窄。** 用脚本（或 MCP 工具）拉取当天数据：`git log` 提交记录、agent 会话的关键事件行、服务日志里的 WARN/ERROR。原则是"先过滤再进模型"，进 prompt 的内容压到 2k token 以内，每条只保留时间戳和摘要行。

**2. 结构化抽取。** 不让模型直接写报告，而是先输出 JSON：完成事项（必须附来源日志行号）、异常与处理、明日计划、无数据的字段。schema 写死在系统提示里，温度调低。这一步是核心——JSON 是契约，报告只是渲染结果。

**3. 校验与渲染。** 用代码（不是模型）校验：字段齐全吗、日期对吗、事项数是否超过来源日志能支撑的条数。通过后套固定的 Markdown 模板渲染，撑不起来的条目宁可标"数据不足"也不编。

**4. 推送与留档。** 报告推到群里，同时把"原始日志快照 + JSON + 最终报告"三件套按日期落盘，出问题能回放整条链路。

## 踩坑点

- **时区**：定时任务跑在 UTC，"今天"变成了昨天。所有时间判断显式带时区，别依赖机器默认值。
- **重复触发**：手动测试跑了一次，定时任务又跑一次，群里两份报告。后来加了当日幂等锁（落盘文件存在即跳过）。
- **幻觉条目**：早期报告里出现过日志中完全不存在的"优化了查询性能"。对策是强制每个事项携带来源行号，校验时抽查比对，对不上就打回。
- **敏感信息**：日志里有 token 和内网地址，脱敏正则放在采集最前面，别指望模型替你保密。
- **schema 漂移**：模型偶尔自作主张加字段，解析时用严格模式，多余字段直接丢弃并记一条告警。

## 可复用建议

1. **JSON 先行，渲染在后**：生成和排版拆开，模型管归纳，代码管样式，改版式不用动 prompt。
2. **降噪别交给模型**：日志过滤是确定性工作，脚本做又快又稳，模型只负责它擅长的归纳。
3. **数据不足就明说**：报告的可信度来自"没有就是没有"，宁可空着，不要脑补。
4. **三件套留档**：原始输入、中间 JSON、最终报告各存一份，是排障和复盘的生命线。

## 总结

整条流水线脚本加 prompt 一两百行，把"写日报"从每天十分钟的机械劳动变成零操作。更重要的是它验证了一个模式：凡是固定输入、固定输出、容错性高的重复劳动，都可以套用"采集收窄 → 结构化抽取 → 代码校验 → 模板渲染"四段式。日报只是第一个落地场景，周报、变更通报、值班小结，都是同一套路子的延伸。欢迎大家在自己环境里跑一遍，把踩到的坑贴出来一起补全。
