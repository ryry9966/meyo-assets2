## 背景

跑了一段时间 OpenClaw 之后，多数人的 Agent 工作流会分化成两类活：一类是任务规划、复杂推理、多步工具编排，另一类是摘要、抽取、分类、格式转换这种“体力活”。前者对模型能力敏感，后者只要求格式稳定、跑得快、跑得起。

OpenClaw 本身支持多后端接入——云端大模型（GPT 系列）和本地推理（Ollama/vLLM 起的小模型）可以同时挂在同一个 Agent 进程里。问题在于，很多人要么全走云端（账单难看），要么全走本地（规划和工具调用质量掉得厉害）。这篇帖记录我们团队把路由规则做稳定的过程。

## 问题

单模型方案的两个典型失败模式：

1. **全云端**：一个批处理任务跑几千次摘要调用，90% 的 token 花在“把 JSON 抽出来”这种本地 7B 模型就能干的事上。
2. **全本地**：小模型在多步规划里漏调工具、参数填错，重试几次之后任务整体失败率明显上升，排障时间比省下的钱贵。

另外还有一条硬约束：涉及客户数据、内部代码的请求，我们不希望出网。

## 做法

我们的路由分四步落地：

**第一步，给任务分类。** 不按 Agent 分，按“这一步在干什么”分。我们最终收敛成四类：planning（规划/推理）、tool-call（参数生成）、summarize/extract（结构化抽取）、chat（兜底对话）。

**第二步，在配置里声明模型档案和路由规则：**

```yaml
models:
  gpt-main:    { provider: openai, model: gpt-4o }
  local-small: { provider: ollama, model: qwen2.5:14b }

routing:
  - match: { task: planning }
    use: gpt-main
  - match: { task: [summarize, extract] }
    use: local-small
    fallback: gpt-main
  - match: { contains_pii: true }
    use: local-small
    pinned: true   # 禁止 fallback 出网
```

**第三步，设置 fallback 链，但方向要明确。** 抽取类任务：本地优先，失败降级云端并打告警日志。规划类任务：只走云端，不为了省钱降级——降级导致的连锁失败更贵。

**第四步，建立可观测。** 每次路由决策记录：命中规则、实际模型、首 token 延迟、token 消耗、是否 fallback。用 50 条左右的固定评测集跑周报，对比各路由规则的失败率和成本。

## 踩坑点

- **上下文窗口不匹配**：MCP 工具返回的大段输出，本地 8k 窗口的模型直接截断，抽取结果缺字段。解法是在路由规则里加长度条件，超长请求强制走云端或先做预裁剪。
- **小模型的工具调用格式不稳定**：JSON 里混注释、参数漏填，触发重试风暴。给本地模型的路由加“连续 2 次格式失败则本任务会话升级到云端”的规则。
- **fallback 掩盖问题**：本地模型悄悄挂了三天，全是云端在兜底，账单翻倍才发现。fallback 必须有独立的告警，不能只写日志。
- **同一任务中途换模型**：规划和执行用不同模型，风格和上下文理解会断裂。原则是一条任务链内 pin 住一个模型，路由粒度到“步骤”而不是“会话”。
- **便宜优先反而更贵**：小模型失败重试三次的成本，往往超过一次云端调用。按“成功一次的期望成本”算，不要按单价算。

## 可复用建议

- 先只路由两三类边界清晰的任务（典型是摘要/抽取），别一上来做全量分流。
- PII 和内部代码相关请求一律 `pinned` 到本地，宁可牺牲质量也不出网。
- 路由规则放配置而不是写死在插件代码里，方便灰度和回滚。
- 每条规则配一条指标：失败率、fallback 率、单次期望成本。没有指标的规则等于没有规则。
- 本地模型选型看两点就够：JSON 输出合规率和 8k 上下文下的吞吐，别只看跑分。

## 总结

多模型路由不是“能省则省”的优化，而是把能力、成本、数据边界三类约束显式化的工程手段。GPT 留给规划和工具编排，本地模型吃掉高频、结构化、敏感的活，用 fallback 兜底、用指标说话。我们的实际结果是：token 成本降了约六成，任务成功率反而因为拆分后各自稳定而略有上升。规则不在多，在于每条都 measurable。
