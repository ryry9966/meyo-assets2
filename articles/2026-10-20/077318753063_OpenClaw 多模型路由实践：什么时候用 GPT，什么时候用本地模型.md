## 背景

OpenClaw 挂上多模型之后，最常见的问题不是"接不接得上"，而是"该派谁上场"。我的实例里同时接了 GPT 系（走 API）和本地 Ollama 跑的 Qwen，最初的策略很粗暴：默认 GPT，本地模型当断网备份。跑了一个月，账单告诉我一个事实：大量 token 花在了根本不需要顶级模型的环节，改写、摘要、格式转换、循环里的中间推理。

## 问题

Agent 场景会把这个问题放大。一个典型任务链十几步，每步都打云端大模型，成本和延迟线性叠加；而其中真正需要强推理的往往只有一两步（工具规划、模糊指令理解），其余都是"体力活"。反过来全用本地模型也不行——复杂规划会翻车，尤其是工具调用格式一不稳定，整个 loop 就开始空转重试，比贵更可怕的是慢且不可控。

## 做法

我的路由规则按**任务性质 + 风险等级**划分，而不是简单按模型大小：

1. **本地模型承接**：摘要、改写、固定 schema 的结构化抽取，以及已经跑通的确定性流程步骤。这些任务即使出错，也能被下游校验兜住。
2. **云端强模型承接**：首次工具规划（决定调哪个 MCP 工具、参数怎么填）、多步模糊任务的拆解，以及涉及外部副作用的操作（发消息、写库、删改文件）前的最终决策。
3. **升级机制**：本地模型先跑，输出校验失败（JSON parse 失败、工具参数缺失）时自动升级到云端重试，路由决策写进日志。

OpenClaw 侧的实现要点：把模型池配成主备链而不是二选一；router 层只看任务类型标签和校验结果，不做花哨的意图分类——分类本身也是一次调用，得不偿失。

## 踩坑点

- **本地模型的 function calling 格式差异**：Qwen 和 Llama 系的工具调用格式不同，直接切模型会解析失败。我在中间加了一层统一的 tool-call 规范化，才把切换成本降下来。
- **上下文静默截断**：本地模型窗口小，长对话被截断时不报错，只是答非所问。路由层要带 token 预算判断，超预算直接走云端。
- **升级链掩盖故障**：本地模型持续失败、每次都升级到 GPT，你会误以为"本地也能跑"，实际是云端在兜底。路由日志必须记录最终由谁完成，每周看一眼占比。
- **嵌入和生成是两套逻辑**：embedding/重排这类任务本地跑性价比极高，别混进生成模型的路由策略里。

## 可复用建议

- 用自己真实的 20~30 条任务做小型基准集，每周回归一次，别信通用 benchmark。
- 路由决策要可观测：模型名、升级原因、耗时、token 数，四个字段就够用。
- 涉及外部副作用的动作，宁可多花一次云端调用的钱。
- 阈值先保守，本地模型占比慢慢提，出问题能随时回退。

## 总结

多模型路由的核心不是"省 token"，而是把每个环节的调用放在它该在的地方：确定性、可校验的活给本地，规划与副作用给云端，中间靠校验和升级链兜住。先把路由日志跑起来，跑两周，数据会告诉你边界在哪。
