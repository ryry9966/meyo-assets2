## 背景

E2E 测试是很多团队"知道该写、但一直欠债"的部分：手写慢、易碎、维护成本高。LLM 出现后，"让 AI 写测试"听起来很美，但直接把需求文档丢给模型，得到的多半是编造的 selector、同义反复的断言，以及一跑就红的用例。最近我们基于 OpenClaw + MCP 浏览器工具摸索了一套协作流程，让 AI 产出的 E2E 用例从"看起来能用"变成"真的在跑"。

## 问题：为什么直接生成不好使

三个典型失败模式：

1. **Selector 幻觉**：模型靠猜写 `page.locator('.btn-primary')`，页面一改就碎。
2. **同义反复断言**：断言它刚填进去的值，测试永远绿，但什么都没验证。
3. **缺少业务语义**：AI 不知道哪些路径是核心链路，用例平均用力，覆盖不到真正的风险点。

根因有两个：模型没有"运行环境"，也没拿到团队的测试约定。

## 做法：三段式闭环

**第一阶段：探索与计划。** 让 Agent 通过 MCP 工具实际打开页面，读取 accessibility tree（不要原始 DOM，token 能省一半以上），输出一份用例计划清单：每条包含操作路径、前置数据、预期结果。人来删改这份清单——这是整条流程里投入产出比最高的动作。

**第二阶段：生成与约束。** 把清单加上仓库里的《测试约定》文档一起喂给 Agent，硬性要求：

- 统一 Page Object 模式；
- 只允许 `data-testid` 作为定位器；
- 一个用例只验证一个行为；
- 禁用 `waitForTimeout`，必须等网络请求或元素状态。

**第三阶段：运行与修复。** Agent 调 Playwright 跑测试，失败时把 trace 和报错喂回去迭代。要限定它只能改测试文件、不许碰业务代码——否则它会为了绿灯去改实现。

## 踩坑点

- **别让它读截图。** 视觉方式定位元素不可靠，accessibility tree 又便宜又稳。
- **全绿不等于测到位。** 抽检方法：手动把断言里的期望值改错，看用例会不会红。不会红的就是废话测试，直接删。
- **修 flaky 用例时它最爱加 sleep。** 约定文档里要显式禁止，否则债越欠越多。
- **Token 成本失控。** 整页 DOM 动辄几十万 token，限定只读取目标区域的子树。

## 可复用建议

- 把《测试约定》沉淀在仓库里，作为每次生成的前置上下文，比在 prompt 里临时解释省事得多，团队里其他人也能直接复用。
- 把 `data-testid` 当成前端、后端、Agent 三方之间的契约，写进 code review 清单。
- 坚持"先计划、后代码"的两阶段，比一步到位生成的用例质量高一大截，人也更容易把关。
- 保留失败 trace 的目录结构，Agent 排障时直接引用路径，减少来回对话。

## 总结

Agent 写 E2E 的正确姿势不是"一键生成"，而是把它当成一个新来的初级工程师：给它环境访问权，给它团队规范，让它跑自己写的测试，由人来审断言和优先级。流程跑顺后，我们核心链路的用例补充速度大约是纯手写的 3-4 倍，flaky 率没有上升。真正省下来的不是"写测试"本身，而是写之前的页面探索和写之后的排障时间——这两块恰恰是最耗人的部分。
