这周技术圈有条消息值得多看两眼：36kr 报道，谷歌开源了一套 Agent Harness，并且兼容 OpenCode 与 Codex 两套生态。国内不少开发者第一时间接上自己的模型跑了真实项目，评价出奇一致——“真行”。多数人的第一反应是：Harness 是个啥？模型都已经卷成这样，开源一个“外壳”有什么好看的？恰恰相反，在当下的 AI 编程语境里，Harness 才是决定体验上限的那一层。这篇把它拆开讲清楚。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/cf3086b8ada69e8c.png)

## Harness 是什么：模型是引擎，它才是底盘

- Harness（线束/挽具）这个词在工程圈早有出处：软件测试里的 test harness，机器学习社区的 lm-evaluation-harness，指的都是“包在模型外面、负责喂数据、收结果、判分”的那套脚手架。
- 到了 agent 时代，含义升级：一个编码 agent 的 harness 包括 system prompt、工具定义、文件系统与终端的访问通道、沙箱、上下文管理、错误重试、权限控制——所有模型之外的工程总和。
- 一个类比：同一台 F1 引擎，装在不同底盘上，圈速能差出一大截。模型是引擎，harness 是底盘、悬挂和变速箱。
- 这不是修辞，是有实证的。SWE-agent 的论文专门提出 ACI（Agent-Computer Interface）概念：给模型设计的接口好不好用，能显著改变同一模型的解题成功率。各路 SWE-bench 类评测里，同一模型换不同 scaffold，分数差距可以大到和换代一个模型相当。反过来看，Claude Code、Codex CLI 这类产品的护城河，模型只是一半，另一半就是长期打磨的 harness。

## 拆开看：一次 agent 循环里到底发生了什么

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/d8ca10597721f9ad.png)

把一次“帮我修这个 bug”的任务拆开，harness 的循环大致是五步：

1. **勘察**：建立仓库索引、依赖图、目录树摘要，决定哪些内容有资格进入上下文；
2. **打包**：上下文窗口再大也不是无限的。哪些文件给全文、哪些只给函数签名、哪些压成摘要，是纯工程决策，直接决定模型“看得清不清”；
3. **执行**：模型输出动作——编辑文件、执行命令、调用工具；harness 先做校验：diff 格式对不对、路径合不合法、有没有危险命令要拦截；
4. **反馈**：在沙箱或容器里跑命令和测试，把 stdout、测试失败栈、生成的 diff 回传给模型；
5. **迭代与止损**：失败重试、上下文压缩，到达步数或花费上限就停。

关键在第 4 步：**自动跑测试的反馈回路，是 agent 和补全式工具的本质区别**。模型负责“想”，harness 负责“让它想得到的都能做、做错的都能被看见”。日常体验的差距，往往不在模型聪明多少，而在错误信息回传得干不干净、重试策略合不合理。

## 兼容 OpenCode 和 Codex：行业在向“标准接口”收敛

- OpenCode 是开源的终端编程 agent，OpenAI 的 Codex CLI 也早已开源——它们本质上是“harness 的两种开源实现”。
- 谷歌主动兼容两者，指向一个行业共识：**harness 层不该绑死模型，模型层也不该绑死客户端**。工具调用有 MCP 协议，agent 与客户端之间的通信也有 ACP 这类标准在推进，接口层正在快速收敛。
- 对开发者的直接好处是换模型不改工作流：今天接 Gemini，明天换 DeepSeek、Qwen 或本地开源模型，多数情况改一个 base URL 和 key 就完事。
- 对谷歌的好处也直白：参考当年 Android 的打法，把底盘开源出去，赢的是生态入口和自家模型的调用量。开源 harness，本质是给自家模型铺分发渠道——这笔账并不复杂。

## 国内开发者实测：能跑通，但卡点要提前知道

接入路径基本三条：

1. **官方 API**：Gemini API 有免费额度，拿 key 填进配置即可，上手门槛最低；
2. **换模型**：这类 harness 普遍支持 OpenAI 兼容接口，DeepSeek、Qwen、GLM 的 API 指过去就能用，成本可控；
3. **本地化**：vLLM 或 Ollama 起本地模型，数据不出内网，适合有合规要求的团队。

实测里的真实卡点：

- 第一道门槛往往不是代码，而是网络与账号；
- 仓库一大，上下文压力立现，索引与摘要策略直接决定好不好用；
- agent 一次任务几十次模型调用很正常，延迟和 token 花费都要心里有数，跑前先设预算；
- 自动执行 shell 有安全面，沙箱和权限确认不要图省事关掉。

至于“真行”的评价，一半功劳在模型，另一半在 harness 把脏活和错误处理做扎实了。这也是为什么同一套 harness 换个稍弱的模型依然能交付：底盘稳，引擎差点也能把货送到。

## 三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-20/4196dff5604a1950.png)

1. **评估工具时，把 harness 单独打分。** 别只看模型榜单，重点看三件事：失败后会不会自动跑测试并回传干净的信息？上下文怎么压缩？危险命令有没有闸门？这些细节决定你是早下班还是陪跑整晚。
2. **把 harness 当可替换组件来架构。** 团队侧统一走 OpenAI 兼容接口或 MCP，模型与客户端都不锁死；这个赛道以季度为单位换代，今天最香的方案未必是下个季度的。
3. **给 agent 立规矩，再让它上车。** 分支隔离、容器沙箱、token 预算、敏感目录白名单——四件事应该在第一次跑 agent 之前配好，而不是出了事故再补。

模型之争看参数，工具之争看细节。Harness 开源这件事，值得放进你的技术雷达。
