## 背景

OpenClaw 这类常驻 Agent 的能力越来越像初级工程师：能读代码、跑命令、调 MCP 工具、发消息。但初级工程师有同事盯着，Agent 只有你。权限给少了，每一步都来问你，你退化成人肉按钮；给多了，某天它"顺手"清了分支、发了不该发的消息。所以问题从来不是"要不要给权限"，而是边界画在哪。

## 问题：两个失败方向

实践中常见两种翻车：

1. **过度请示**。每次写文件都确认，一天弹四十次。人对重复弹窗的处理方式是盲点同意——第三天开始你只会按 y，权限系统形同虚设。
2. **过度自信**。读工具和写工具同权，Agent 在一次"优化脚本"的任务里直接触达了外部系统。事后翻日志，每一步它都"有理由"。

两种失败的根因相同：**所有动作共用一套默认策略**，没有分层。

## 做法：按三个维度给动作分级

给工具链里的每个动作打三个标签：

- **可逆性**：一条命令能撤销吗？`git checkout` 能，`rm -rf` 和发出去的邮件不能。
- **影响半径**：只碰本机，还是触达外部的人/系统？读本地文件 vs 给客户发消息，是两个世界。
- **成本**：本地跑 vs 调付费 API，花的是不是真金白银。

由此得出三层策略：

- **自动执行**：只读、本机、可逆、低成本。干完在会话里汇报即可。
- **带护栏执行**：可逆但有副作用，如本地写文件、`git reset`。先 dry-run / 展示 diff，或限制在白名单路径内。
- **必须确认**：不可逆、对外、超成本阈值。执行前给结构化确认卡。

落到 OpenClaw/MCP 侧，策略配置大致这个思路：

```yaml
tools:
  fs.read:    { mode: auto }
  shell.run:  { mode: guard, dry_run: true }
  mail.send:  { mode: ask, budget: 5/day }
  db.drop:    { mode: deny }
```

格式不重要，三条规则才重要：

1. 默认只读放行，默认对外拦截。
2. 确认卡必须带上下文：要执行什么、为什么、预期结果、怎么回滚。一句"可以继续吗"等于没问。
3. 批量请示。让 Agent 先出计划，一次确认整段执行，而不是十步打断十次。

## 踩坑点

- **确认疲劳**：ask 列表日均超过十几次，说明该收紧护栏层，而不是让你习惯弹窗。
- **工具描述含糊**：MCP tool 的 description 写不清副作用，模型就会自己误判层级。`send_message` 和 `send_message_to_external_recipient` 是两个东西。
- **always allow 永不过期**：会话级授权要带作用范围和 TTL，别让一次信任变成永久放行。
- **问得太晚**：确认点应放在计划阶段，而不是干到一半才问"要不要继续"。
- **拿生产环境当测试场**：Agent 自作主张调真实外部接口来"验证"，是典型的半径误判。

## 可复用建议

- 给自己的工具链写一张动作分级表，放进策略文件或系统提示词，别指望模型自觉。
- 自动执行的动作全部留审计日志，每周翻一次：高频且从没出过错的下移到 auto，惊到你哪怕一次的上移到 ask。
- 阈值用数字不用感觉：单次花费上限、每小时外发次数上限，超了自动进确认队列。

## 总结

权限边界不是开关，是滑块，而且应该随证据移动。标准可以压成一句话：**可逆且只碰自己——自己干；不可逆或触达他人——先问人。** 让 Agent 每次问人都值得你停下来看一眼，每次自己干都能在日志里说清楚，这个系统才算真正可托管。
