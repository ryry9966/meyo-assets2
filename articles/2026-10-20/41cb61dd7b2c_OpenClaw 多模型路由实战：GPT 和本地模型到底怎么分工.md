## 背景

OpenClaw 默认是单模型跑全套：规划、工具调用、回复生成压在同一个模型上。实际跑一段时间就会发现任务差异极大——频道里一句"帮我总结这条链接"，和"重构这个 500 行的脚本"，用同一个模型处理，要么浪费，要么不够用。

## 问题

- **云端 GPT 级模型**：规划能力强、工具调用稳定，但贵、有延迟、数据出域。
- **本地模型（Ollama / vLLM）**：免费、低延迟、数据不出机器，但长工具链容易跑偏，函数调用格式偶尔崩。

单选任何一边都有明显短板。路由要解决的就是：把任务按难度和敏感度分流，各取所长。

## 做法

我落地的是三层结构，可以直接抄：

1. **快车道**：本地小模型处理寒暄、格式化、单工具的简单任务。判断依据：预估输入 token < 2k，且本轮工具调用 ≤ 1 个。
2. **主车道**：GPT-4.1 级云端模型作为默认，负责规划、多工具编排、代码生成。
3. **重车道**：复杂任务显式升级（长上下文 / 多文件 / 用户 @ 指定），或主车道失败后 fallback。

实现上别过度设计，两层就够：

- **配置层**：`providers` 同时挂云端和本地，设 fallback 链 `cloud → local`，保证云端挂了 agent 还能应答。
- **规则层**：在 plugin 里加一个前置 hook，按 channel + 估算 token + 工具数打分，输出模型选择。规则比"再训一个小分类器"好维护得多。

配置示例（节选）：

```json
{
  "models": {
    "primary": "gpt-4.1",
    "fallback": "ollama/qwen2.5:14b"
  },
  "plugins": {
    "model-router": {
      "local_threshold_tokens": 2000,
      "max_local_tools": 1
    }
  }
}
```

## 踩坑点

1. **别只按 token 数路由。** 短 prompt + 深度代码任务照样需要强模型。我后来加了一条：命中代码文件路径则强制上云。
2. **本地模型工具链跑偏是静默失败。** 它不报错，只会一直把参数调错。给本地模型设工具调用上限（比如 5 次），超限转云端重试。
3. **会话中途切模型，语气和记忆连贯性会突变**，用户看得出来。路由决策要按会话粘住，至少同一轮对话内不换。
4. **fallback 循环烧钱又烧时间**：云→本地→云来回摆。fallback 只允许一次，之后降级回复。

## 可复用建议

- 维护一份 20~30 条的"金标准任务"清单，每次改路由规则跑一遍，看命中率，不凭感觉。
- 把每次路由决策（原因、所选模型、耗时）打进日志，一周后你会感谢自己。
- 隐私敏感的 channel（家庭、内网）默认钉死本地，不要依赖运行时判断。
- 阈值按你们实际的 token 分布调，2000 是我的场景，不是普适值。

## 总结

多模型路由不是堆功能，而是把"任务难度"显式建模出来。三层结构 + 简单规则 + 可观测性，两三个小时就能落地。我这边的收益是成本降了大约一半、隐私可控、云端故障时 agent 不至于瘫痪。建议先从"简单任务走本地"这一条规则跑起来，观察一两周，再逐步收紧。
