## 背景

社区论坛需要稳定的内容供给，但纯靠人力编辑，节奏很难维持。我的目标很朴素：让机器人每天从固定信息源（GitHub Releases、RSS、群里讨论）筛出值得发的内容，生成草稿，经人工确认后自动发到论坛。整条链路基于 OpenClaw 的 agent 能力加一个自写的 MCP server，两周跑通，目前稳定运行一个多月。

## 问题

最初的版本是 cron + 一次性 prompt + 论坛 API 直调，三天就翻车：同一内容重复发了两次；一次总结 changelog 时编造了不存在的版本号；还有一次因连续发帖触发了论坛限流。根本原因是我把发帖当成"一次生成"问题，而它实际是一个带状态、带审核、带外部依赖的流水线。

## 做法

最终架构分四层，每层职责单一：

1. **采集层**：两个轻量脚本定时拉 GitHub Releases 和 RSS，输出结构化 JSON，附带源条目唯一 ID。
2. **生产层**：OpenClaw agent 挂载一个 skill，输入 JSON，输出标题 + 正文 Markdown。prompt 里明确约束：只允许转述源内容，不允许补充"背景知识"。
3. **审核层**：草稿先推送到 Telegram，附两个快捷操作（发布/丢弃）。人工确认后，才走下一步。
4. **发布层**：自写 MCP server 封装论坛 API，agent 只能通过工具调用发帖，凭据放在服务端环境变量里。

状态全部外置到 SQLite：每条源内容记录指纹、状态（待审/已发/丢弃）、发布时间。agent 本身无状态，随时可重启、可重放。

## 踩坑点

- **去重不能依赖文本相似度**。模型每次改写措辞，simhash 全部失效。后来直接用源条目 ID + 日期做指纹，稳定得多。
- **凭据不能进 prompt**。早期图省事把 API key 写进 system prompt，调试日志里密钥全裸奔。改成 MCP server 注入后，agent 只见工具、不见密钥。
- **定时触发要串行**。cron 和手动触发撞车时出过并发双发。加了一个简单的任务锁，同一时刻只允许一个发帖会话。
- **限流要有退避**。论坛返回 429 后无脑重试只会更糟。MCP 工具内置了指数退避和每日配额上限。
- **human-in-the-loop 别省**。关掉审核跑过一天全自动，产出质量明显漂移，标题越来越像营销号。保留人工确认后，草稿采纳率反而稳定在 80% 以上。

## 可复用建议

1. 先跑影子模式一周：只产草稿不发布，用人工审核数据校准 prompt。
2. 工具按最小权限设计：发帖工具只暴露 createTopic，不暴露管理接口。
3. 监控两个指标就够：草稿采纳率、单篇返工次数。指标恶化先查数据源，再查 prompt。
4. 所有外部调用封装在 MCP 层，agent 只负责编排，方便单独测试和故障重放。

## 总结

发帖机器人本身不复杂，复杂的是让它"持续不闯祸"。核心经验一句话：**agent 做编排，状态放外面，风险动作过审核，外部依赖进工具层**。这套结构不限于发帖，换成发周报、发公告同样成立。细节和配置片段欢迎在本帖下交流。
