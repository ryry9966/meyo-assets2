# 从零搭建 AI 社区发帖机器人：架构设计与踩坑实录

## 背景

我们社区每周都有高质量讨论散落在各个帖子里，人工整理精选摘要既耗时又容易漏。目标很朴素：做一个定时运行的机器人，自动汇总近期有价值的讨论，生成一篇摘要帖发回社区。注意这不是营销自动化，而是一个"消化-产出"型的内容流水线。

## 问题

最直觉的做法是一段 prompt 搞定一切："读最近的帖子，写一篇摘要，发出去"。我们跑了一版，三天内暴露了所有典型问题：内容重复、编造不存在的引用链接、语气飘向营销腔、发布失败后无法恢复。结论是：LLM 的不确定性必须用工程手段关进笼子，而不是指望 prompt 一次写对。

## 架构与做法

最终架构很克制，核心是**解耦**：

- **调度层**：cron 定时触发 OpenClaw agent，统一 UTC 时间。
- **Agent 层**：agent 只负责编排，通过 MCP 工具与外界交互，不直接持有社区凭据。
- **MCP 工具**：`fetch_recent_threads`（只返回结构化数据：线程 ID、热度、摘要）、`dedup_check`、`save_draft`、`publish_post`、`write_log`。
- **状态层**：SQLite 一张库管所有事——发帖历史、草稿队列、运行日志。

关键设计决策：

1. **选题与写作分离**。模型不接触原始全量内容，只消费工具返回的结构化摘要，从源头压缩幻觉空间。
2. **生成与发布解耦**。agent 只产出草稿落库，独立的 publisher 进程消费队列。任何一步挂掉都能重跑，不会发一半。
3. **两段式生成**。drafter 写初稿，reviewer 用独立的 checklist prompt 审一遍（引用是否真实、语气是否克制、是否与近 30 天历史重复），不过审就打回。
4. **灰度门槛**。前两周所有帖子进人工审核队列，一个 CLI 命令批准或驳回；攒够样本、确认准确率后再放开自动发布。

## 踩坑点

1. **去重只做标题精确匹配**，第二周就发出两篇高度相似的帖子。补救：加 embedding 相似度阈值，发布前比对近 30 天历史。
2. **模型编造引用链接**。约束方式不是"请不要编"，而是 prompt 里只允许引用工具返回的线程 ID，链接由代码模板拼接，模型根本拿不到生成 URL 的机会。
3. **cron 时区配置错误导致双发**。统一 UTC 之后，发布前再查一次库确认当日是否已有成功记录，双保险。
4. **MCP 工具超时后 agent 自动重试，造成重复发布**。把 `publish_post` 拆成幂等的 create + confirm 两步，客户端生成 ID，重试安全。
5. **语气跑偏**。早期稿子满篇"赋能""抓手"。在 reviewer 的负向清单里禁掉这类词、限制感叹号数量，比正向描述"要有技术感"有效得多。
6. **跳过灰度直接自动发布**，第一条翻车帖就教育了我们：任何自动化程度都应该与错误成本挂钩。

## 可复用建议

- 外部写操作一律幂等，ID 由客户端生成，不要信任服务端去重。
- 生成与发布之间必须有队列，哪怕只是一张 SQLite 表。
- 去重至少两层：规则层兜底，语义层查相似。
- prompt 当代码管理，进 git，改 prompt 和改代码一样走 review。
- 准备固定的回归样本集，每次改 prompt 跑一遍，别靠肉眼感觉。

## 总结

发帖机器人本身不难，难的是让一条含 LLM 的流水线敢无人值守。回头看，真正兜底的只有四件事：**解耦、幂等、去重、灰度**。先把这四件事做扎实，再谈让 agent 更聪明——顺序反过来，基本都会在第一周付出代价。
