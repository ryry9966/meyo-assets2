## 背景

OpenClaw-CN 社区的日常运营里有一类高频但低创造性的工作：把仓库动态、精选 Issue、新教程整理成帖子发出去。人工做两三个星期后，我们发现真正的瓶颈不在写作，而在"收集—排版—定时—检查是否发重"这条流水线上。

于是决定搭一个发帖机器人。先明确定位：**它是编辑助理，不是主编**——自动起草、自动排队，但发布前必须过一道人工确认。

## 问题与约束

动手前列了三条硬约束：

1. **不刷屏**：单日发布有上限，选题必须有来源；
2. **不编造**：引用的链接、Issue 号必须来自真实数据源，不允许模型凭记忆写 URL；
3. **出错可回滚**：任何一次发布失败或重复，都能定位并恢复。

## 架构与步骤

整体分五层，全部通过 MCP tool 暴露给 Agent 调用：

```
数据源层 → 起草层 → 审核队列 → 发布适配器 → 反馈层
```

1. **数据源层**：GitHub Issues、论坛新帖、社区精华区，封装成一个只读 MCP server，Agent 每次起草前必须先取数。
2. **起草层**：Agent 按 Markdown 模板生成草稿，模板强制包含"来源链接"字段，取不到就不生成。
3. **审核队列**：草稿写入队列并推送到运营群，附上 diff 预览，一键通过或驳回。
4. **发布适配器**：唯一有权调用社区发帖 API 的模块，带全局限流和幂等键。
5. **反馈层**：记录每篇的阅读/回复数据，回流到下一轮选题。

## 踩坑实录

**1. 重试导致重复发帖。** 最早网络超时直接重试，结果同一篇发了三次。修复方式：发布适配器为每个草稿生成幂等键，社区侧按键去重，客户端失败后先查再发。

**2. 模型编造链接。** 即使 prompt 里写了"不要编 URL"，偶尔还是会输出看似合理的 Issue 地址。最终方案是不靠 prompt 约束，而是结构上封死：草稿里的链接字段只允许从 MCP 返回的数据填充，模型只能做摘要。

**3. 定时任务时区。** 服务器 cron 按 UTC 跑，本地预览一切正常，上线后帖子固定在凌晨发布。现在调度统一用 UTC 存储，展示层做时区转换。

**4. 触发社区限流。** 批量补发历史内容时被限流，重试又加剧了拥塞。改成全局发布队列 + 指数退避，峰值速率写进配置而不是散落在代码里。

**5. 内容同质化。** 连续两周的精选帖结构雷同，被群友吐槽"AI 味"。加入两点：选题时对近 N 篇做相似度去重；模板保留一段人工填写的"编者按"。

## 可复用建议

- **先做草稿箱，再谈全自动**。人工审核这一步不能省，它同时是质量闸门和信任积累。
- **所有对外动作收敛到一个适配器**，幂等、限流、审计日志都只写一次。
- **让结构约束替代 prompt 约束**。凡是能通过数据流设计避免的错误，就不要指望模型自觉。
- **完整记录每次的 prompt、工具调用和结果**，复盘质量问题时这是唯一可靠的证据。

## 总结

两周迭代后，机器承担了约八成的机械工作，人工只负责选题判断和最终把关。最大的收获不是省了多少时间，而是这套"取数—起草—审核—发布—反馈"的骨架可以平移到周报、公告等其他场景。自动化做到最后，拼的不是模型多聪明，而是工程上够不够克制。
