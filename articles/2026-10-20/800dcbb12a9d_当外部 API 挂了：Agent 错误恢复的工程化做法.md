## 背景

跑 Agent 自动化时间长了，大家都会接受一个事实：**外部依赖一定会挂**。LLM 网关限流、搜索接口超时、第三方服务 5xx、配额用尽……在传统服务里这些只是报错日志，但在 Agent 循环里，一次工具调用失败会被放大成幻觉结果、无限重试、token 烧穿，甚至整条工作流卡死。这篇整理一下我们在 OpenClaw 插件和 MCP 工具接入中沉淀的错误恢复做法。

## 问题：API 失败在 Agent 里的放大效应

1. **幻觉兜底**：工具返回报错，模型不承认失败，编一个"看起来合理"的结果继续往下走，下游全是错的。
2. **重试失控**：模型自己决定重试策略，要么一次失败就放弃任务，要么死循环重试把配额烧完。
3. **长阻塞**：一个没设超时的工具调用能把整条编排链挂住十几分钟。
4. **状态残留**：多步任务跑到一半失败，重跑不知道从哪继续，产生重复副作用（重复下单、重复发消息）。

## 做法：五层防线

核心原则：**重试和熔断放进代码（工具包装层），模型只负责拿到结构化错误后做业务决策。**

**第一步：错误分类。** 把错误分成三类返回给模型：`RETRYABLE`（超时、429、5xx）、`FATAL`（401、参数错、配额尽）、`PARTIAL`（拿到部分结果）。别把原始堆栈直接喂给模型——费 token 还容易把它带偏；也别只返回一句"工具失败"——模型无法判断该等待还是该换路。给一个错误码 + 一句短原因就够。

**第二步：超时兜底。** 所有外部调用同时设连接超时和总超时，默认宁短勿长。Agent 循环里"超时 × 重试 × 多工具"是乘法关系，一个 60 秒的超时就能把单轮拖到几分钟。

**第三步：有界重试。** 只对 `RETRYABLE` 类做指数退避 + 随机抖动，上限 3 次。非幂等操作（下单、发通知）必须带幂等键，且幂等键按"任务步骤"生成，而不是按"尝试次数"生成。

**第四步：降级路径。** 关键工具预先想好 Plan B：备用服务商、带过期标记的缓存数据，或者明确告诉模型"此能力暂不可用，请调整方案"。最怕的是没有降级逻辑，模型只能瞎编。

**第五步：断点续跑。** 多步工作流每步落盘状态，失败后从最后一个成功步骤恢复，而不是从头重跑——这同时解决了重试副作用问题。

## 踩坑点

- **退避不加抖动**：多个 Agent 实例同时恢复会形成惊群，把刚缓过来的 API 又打挂。
- **熔断状态放进程内存**：多实例部署时各熔断各的，等于没熔断，至少共享到 Redis。
- **混淆"API 挂了"和"我的 key 配额没了"**：前者等待即可，后者等再久也没用，告警策略完全不同。
- **缓存了错误响应**：上游 500 的响应体被当成正常结果缓存，故障恢复后还在吐坏数据。
- **只测 happy path**：用一个会返回 429/500 的 mock 服务把失败路径跑一遍，很多问题只有这时才暴露。

## 可复用建议

- 在工具接入层做统一的"弹性调用"中间件：分类 + 超时 + 重试 + 熔断 + 结构化错误，所有 MCP 工具走同一套，不要每个插件自己实现一遍。
- 给每个工具维护两个指标：**失败率**和**平均恢复时长**，失败率漂移时告警，通常比用户反馈更早发现故障。
- 每个关键工具写一行"降级预案"文档，故障发生时不用现场想方案。

## 总结

错误恢复的目标不是消灭故障，而是让故障**可读、有界、可恢复**：模型能读懂发生了什么，重试和熔断有明确边界，中断后能接着跑。把弹性逻辑从 prompt 挪到代码里、从临时处理挪到统一中间件，Agent 的稳定性会上一个台阶。欢迎大家贴出自己工具链里的失败案例，一起补全这套实践。
