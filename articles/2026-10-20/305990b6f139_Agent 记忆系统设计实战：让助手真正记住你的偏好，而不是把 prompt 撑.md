## 背景

LLM 本身是无状态的。会话一结束，模型对"你是谁、你喜欢什么"一无所知。OpenClaw 的 workspace 里虽然可以放 MEMORY.md 这类持久化文件，但很多人用着用着就走向两个极端：要么什么都不记，每次重头调教；要么把所有历史摘要全塞进去，几轮之后 prompt 膨胀、响应变慢、输出还容易跑偏。

这篇帖子分享一套我在个人助手项目里跑了几个月的记忆系统设计。核心思路一句话：**把记忆当成一条数据管道来建，而不是当成一个"功能"。**

## 问题：三种常见失败模式

1. **全量注入**：历史记忆全塞 system prompt。上下文占用、成本、噪音三重上涨，无关记忆反而干扰输出。
2. **只靠会话**：记忆只在当前 session 生效，重启清零，用户每次都得重复"我喜欢简洁的回复"。
3. **无脑全记**：把"用户今天问了一下 Rust"记成"用户偏好 Rust"，一次性行为被泛化成长期偏好。

## 做法

### 1. 先分层

- **短期记忆**：当前 session 上下文，不额外处理。
- **长期偏好**：结构化 KV，形如 `{category, content, confidence, source, updated_at}`。类别收敛到几类就够：交互风格、技术栈偏好、禁用项、背景事实。
- **情景记忆**：具体事件（"上周部署过 X 项目"），量大、价值密度低，用 SQLite + embedding 做向量检索即可。

### 2. 写入：显式优先，隐式补充

- **显式**：注册一个 `remember` MCP 工具，用户说"记住……"时调用。这是最可靠的数据源，source 标记 explicit，confidence 直接给高。
- **隐式**：每轮对话结束后用小模型跑一次抽取，输出严格符合 schema 的 JSON，confidence 初始给低（比如 0.3）。同一偏好在后续对话再次出现才提升置信度。

### 3. 读取：检索注入，不是全量倒入

session 启动时按 `relevance × recency × confidence` 排序，取 top-K（我设 15~20 条）注入 system prompt 的独立段落。情景记忆按当前任务做向量检索，只带相关那几条。

### 4. 更新与衰减

- **去重**：新条目与已有记忆 embedding 相似度超阈值就合并，不新增。
- **冲突**：新的显式记忆覆盖旧偏好，旧条目归档不删除，方便回溯。
- **衰减**：N 天未被命中的记忆 confidence 逐次下降，低于阈值自动归档。
- **负向偏好单独一类**：用户说"别再推荐 X"是禁用项，处理逻辑和正向偏好完全不同。

## 踩坑点

- **抽取模型会幻觉出偏好**。schema 校验 + 低置信度门槛能挡掉大半，剩下的靠定期人工清理。
- **注入太多反而降智**。超过 30 条明显感觉输出变啰嗦。top-K 是硬约束，不是建议值。
- **一定要让用户可见可删**。提供 `list_memories` / `forget` 工具，既是隐私要求，也是最好的调试手段——你会惊讶于很多记忆根本不是你以为的那样。
- **hit rate 要埋点**：哪些记忆被注入了、哪些真的影响了输出。没有这个数据，调参全靠猜。

## 可复用建议

- 先做显式记忆（一个 MCP 工具就够），跑稳了再上隐式抽取，顺序别反。
- 记忆 schema 加版本号，后期迁移会感谢你。
- 注入格式固定为独立段落，方便 A/B 对比有/无记忆的输出差异。
- 存储别一上来就上独立向量库，SQLite 全文检索 + embedding 字段够用很久。

## 总结

记忆系统的本质是"**抽取 → 结构化存储 → 检索注入 → 衰减清理**"的数据管道，每一步都可以单独测试和观测。从最小可用版本（一个 remember 工具 + 一个 JSON 文件）开始，根据实际 hit rate 迭代，比一上来设计复杂架构有效得多。欢迎在评论区交流你们踩过的坑。
