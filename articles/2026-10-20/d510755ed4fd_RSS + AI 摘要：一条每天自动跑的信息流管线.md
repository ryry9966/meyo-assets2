## 背景

我的 RSS 订阅这两年只增不减，几十个 feed 散落各处。RSS 依旧是最稳的订阅协议——没有推荐算法干预，但代价是噪声全靠自己过滤，每天真正值得读的可能不到十分之一。于是我用 OpenClaw 的 Agent 加上几个 MCP 工具，搭了一条「抓取 → 清洗 → 去重 → 摘要 → 推送」的管线，每天早上产出一份摘要日报。稳定跑了一个多月，分享一下做法。

## 问题

原始痛点有三个：

1. **噪声高**：多数 feed 一天十几条，真正相关的不到两三条；
2. **阅读成本高**：直接把原始 HTML 喂给模型，token 消耗大且摘要质量差；
3. **LLM 输出不稳定**：让模型自由发挥，每天的日报格式都不一样，没法聚合排序。

## 做法

整体分五步，由 Agent 定时任务编排，工具层用 MCP server 提供：

**1. 源管理**。订阅导出成 OPML，管线启动时解析成 feed 列表，加一个 `enabled` 字段方便随时开关某个源。

**2. 抓取与清洗**。定时触发 fetch 类 MCP 工具拉取 feed，解析成统一条目结构：`title / link / published / content`。HTML 剥离标签转纯文本，截断到 4000 字符左右——实测大多数技术博客的核心内容都在前 3000 字。

**3. 去重与初筛**。两层：第一层对 link 去掉 host 差异和 utm 参数后做 URL 指纹；第二层对标题做编辑距离相似度判断，跨源同题文章只留最早一条。最后过一遍关键词黑名单。

**4. 结构化摘要**。这是关键一步。不要让模型写散文，用 JSON Schema 约束输出：

```json
{
  "one_liner": "一句话概括",
  "key_points": ["要点1", "要点2"],
  "tags": ["分类"],
  "score": 3
}
```

temperature 设 0.1，score 是 1-5 的相关性打分，作为日报排序依据。逐条摘要虽然调用次数多，但单次 token 少、失败可单独重试，比整批喂进去更可控。

**5. 聚合推送**。按 score 取 top N 拼成 Markdown 日报，通过 webhook 推到 IM。原始条目和摘要全部落库留档，方便回溯和后续评测。

## 踩坑点

- **部分 feed 只有摘要没有全文**，需要再抓一次原文页。个别站点有反爬，遇到 403 就把该源降级为"仅标题摘要"，别让单个源拖垮整条管线。
- **跨源重复比想象中严重**。同一媒体的 syndication feed 和主 feed 经常各推一遍，URL 指纹挡不住，标题相似度这层不能省。
- **格式漂移**。即使有 Schema，模型偶尔会在数组里塞多余字段。解析侧要做宽容处理：未知字段忽略、缺字段填默认值，不要直接报错中断。
- **调度时区**。定时任务默认 UTC，第一次跑出来的"早报"实际是下午发的。调度器里显式指定时区。
- **成本失控**。一开始按条数无脑全摘要，一天几百次调用。加了两级策略（便宜模型粗筛打分、高分条目再用好模型精摘）后成本降了 70% 以上。

## 可复用建议

- 起步 10-20 个源足够，管线跑稳再加量；
- 一天一次日报比实时推送好：批量摘要便宜，也不被打断；
- 原始数据务必留档，摘要质量靠抽查对比原文来校准 prompt；
- prompt 里写明"不复读标题、不编造原文没有的细节"，这两条对可读性提升最明显；
- 去重、打分、推送做成独立可测的模块，出问题时能快速定位在哪一层。

## 总结

这条管线的核心思路是：RSS 负责稳定供给，代码负责确定性的脏活（抓取、清洗、去重），LLM 只做它擅长的压缩与判断，并用结构化输出守住格式的确定性。跑通后每天维护成本接近零，读到的内容却比刷时间线精准得多。实现本身不复杂，更有价值的是想清楚"哪层用工具、哪层用模型"的边界——这也是这套思路能迁移到其他自动化场景的原因。
