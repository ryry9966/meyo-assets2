## 背景

Agent 接上 MCP 和各类插件之后，能做的事从"读"扩展到了"写"甚至"对外"。发消息、改配置、调付费 API、删文件——这些动作一旦执行，影响的是真实环境。多数框架给了工具调用能力，但没回答一个更关键的问题：哪些调用可以直接执行，哪些必须停下来等人确认。

## 问题

实践中常见两种失败模式，方向相反但都很典型：

- **问得太多**：每个写操作都弹确认，用户很快产生"确认疲劳"，开始无脑点"允许"。这比不问更危险，因为确认环节已经形同虚设。
- **做得太自由**：system prompt 里写了一句"谨慎操作"，agent 就认为获得了授权，把删分支、给外部用户发邮件这类不可逆动作也顺手做了。

核心矛盾在于：agent 无法自己判断边界画在哪，而人也不可能逐条审核所有调用。

## 做法

我们的思路是把权限从"提示词约束"下沉到"代码层强制"，分四步：

1. **枚举能力**：列出 agent 可触达的所有工具（MCP server、插件、shell 命令），一项不漏。
2. **按四个维度分级**：
   - 可逆性：只读 / 可回滚写入 / 不可逆操作
   - 影响范围：本机 / 仓库 / 外部用户
   - 成本：免费调用 / 付费资源
   - 意图覆盖：动作在用户明确指令范围内，还是 agent 自行推断的
3. **定义四级策略**：自动执行、自动执行但记录、需人工确认、禁止调用。策略写在配置文件里进版本库，像代码一样 review。
4. **把确认做成好的 UX**：需要确认时不问"是否继续"，而是展示将执行的操作 diff、影响对象、成本和撤销路径。人只有在看得懂的前提下才能做出有效决策。

## 踩坑点

- **只靠 prompt 约束等于没有约束**。模型对"谨慎"的理解和你的预期未必一致，高危动作必须在工具包装层拦截。
- **看似可逆的操作可能不可逆**。发出去的消息撤不回，"移到回收站"和"硬删除"要区别对待。
- **分级要静态**，按工具本身定级，参数是否越界单独检查。让 agent 临场判断"这个操作安不安全"不可靠。
- **会话内授权不要跨任务复用**。用户批准了一次删除，不代表批准下一个删除。
- **自动执行也要留痕**。审计日志应覆盖所有调用，包括没问你的那些。

## 可复用建议

- 默认拒绝"不可逆 + 涉及外部"的组合，其余可以放宽。
- 确认请求降噪：把同一任务的多个待确认项合并成一次预览，而不是逐条打断。
- 每周回顾一次升级记录：哪些确认其实多余，哪些自动执行后来出了问题，据此调整分级。
- 边界策略本身也是代码，改策略走 review，不要顺手改。

## 总结

权限边界不是"多问"或"少问"的问题，而是把有限的人工介入放在不可逆、大范围、意图模糊的位置上，其余交给自动化并留下记录。判断标准进配置、执行落在代码层、决策过程可审计——做到这三点，agent 才能在真实环境里放心放手。
