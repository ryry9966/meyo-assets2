## 背景

单主 Agent 的典型瓶颈：一次会话里塞三件事——查两个仓库的 CI 状态、读一批日志定位构建失败、顺手整理结论。主 Agent 只能串行处理，日志原文大量涌入上下文，跑完一轮对话已经很难继续。OpenClaw 的 agents 工具提供了 `sessions_spawn`：主 Agent 可以拉起独立会话的 subagent，把脏活外包出去，自己只收结构化结果。

## 问题

难点不是"能不能并行"，而是三个工程问题：

1. 主上下文污染——子任务的中间过程不该进主会话；
2. 串行耗时长——互不依赖的任务没有理由排队；
3. 结果不可控——subagent 返回一大段散文，主 Agent 还得自己消化。

## 做法

**第一步：先拆任务，再写 prompt。** 只拆满足两个条件的任务：交付物明确（一份结论/一个文件），且彼此无共享可变状态。三个仓库的 CI 排查天然满足；"改配置然后验证配置"就不满足，老老实实留在主 Agent 串行做。

**第二步：给 subagent 的 prompt 定死边界。** 我的模板固定四段：目标（一句话）、上下文（只给必要信息：路径/仓库/分支）、约束（不许派生子代理、不改指定范围外的文件、预算 X 步内完成）、输出格式（3 行以内结论 + 结果文件路径）。最后一条最重要，踩坑部分细说。

**第三步：控制并发。** 一次 spawn 2–4 个，多了 API 限流和 token 成本都会失控。主 Agent 等待期间不做写操作，避免和 subagent 抢同一批资源。

**第四步：文件中转结果。** 让 subagent 把详细内容写到约定路径（如 `/tmp/task-a-report.md`），会话里只回传短摘要。主 Agent 聚合时按需读文件，而不是把全文拉进上下文。

## 踩坑点

1. **子代理输出失控。** 早期没限输出格式，一个 subagent 回了 2000 字分析，主上下文直接被灌满。强制"3 行内 + 文件路径"后问题消失。
2. **递归派生。** subagent 拿到同样的工具权限，遇到难题又 spawn 新的 subagent，层级失控。prompt 里必须显式禁止，或在配置层收紧工具范围。
3. **同文件写入冲突。** 两个 subagent 同时改一个文件，后写覆盖先写。要么把改动范围划成不相交集合，要么各自用独立 worktree/目录，由主 Agent 统一合并。
4. **token 成本翻倍。** 3 个并行 subagent 各自重复读同一份大文件，成本直接 3 倍。公共上下文在 spawn 前由主 Agent 裁剪，只传各自需要的部分。
5. **没有完成判据。** "帮我分析一下"这种目标会让 subagent 无限游走。每个任务写清停止条件：跑完这几个命令、回答这几个问题即止。

## 可复用建议

- 先串行跑通一次，确认拆分合理，再改并行——并行化只会放大好设计或坏设计。
- subagent 保持单一职责、无状态、用完即弃，不要复用长会话。
- 主 Agent 只做编排和聚合；一旦忍不住掺和子任务细节，说明拆分有问题。
- 失败是常态：给 subagent 设步数/时间预算，超时取部分结果，并在聚合时明确标注哪些分支失败。

## 总结

subagent 编排的价值不在"多个 AI 显得高级"，而在隔离与并行：脏上下文隔离在子会话，独立任务同时跑。工程上关键就三条——任务拆得干净、输出格式锁死、结果走文件不走对话。做到这三条，2–4 路并行的收益是实打实的，调试成本也可控。
