# 为什么 Agent 不会误删你的文件：拆一下 OpenClaw 的 sandbox 模型

## 背景

给 Agent 接上 shell 和文件工具之后，第一反应通常是“它会不会把我的东西删了”。这不是杞人忧天：模型会算错路径、会把相对路径拼出歧义、会在多轮对话里被一句注入文本带偏。OpenClaw 的思路不是“相信模型”，而是**假设模型一定会犯错**，然后用沙箱把错误的爆炸半径限制住。

## 误删是怎么发生的

真实场景里几乎没有“Agent 发疯乱删”，出事的方式都很平庸：

- 用户说“清理一下项目里的临时文件”，Agent 把 `tmp/` 解析成了家目录下的另一个 `tmp`；
- workspace 里的软链接指向外部目录，`rm -rf` 跟着链接走了出去；
- 插件或 MCP server 自带的 exec 工具没走同一套限制，成了旁路。

所以防线要挡的不是某条具体命令，而是这三类路径。

## OpenClaw 的三层防线

**1. 运行时隔离。** Agent 的文件和 exec 工具默认跑在容器沙箱里。`sandbox.mode` 建议设为 `all`，或至少 `non-main`（子 agent 全部沙箱化、主 agent 例外）。注意：沙箱一旦设为 `off`，后面两层都是摆设。

**2. 收敛文件系统视图。** 沙箱内只挂载 workspace，并通过 `workspaceAccess` 控制读写：`ro` 时模型看得见改不了，`rw` 也只对 workspace 生效。宿主机的其他路径对 Agent 来说不是“禁止访问”，而是“不存在”——这比维护一份 denylist 可靠得多，因为你永远列不全。

**3. 工具策略与审批。** exec 走白名单和审批网关，命中高危模式的命令（递归删除、写系统路径）会被拦下要求人工确认。工程上建议把“删除”降级为“移入 workspace 内的 `.trash/`”，再加一层快照兜底。

路径校验的关键一步：**先 `realpath` 再判断**。把符号链接解析成真实路径后，确认仍落在 workspace 内才放行；判断“是否在目录里”必须用解析后的路径做前缀比较，不能拿原始字符串。

## 怎么验证自己的配置

- `docker ps` 确认会话真的进了容器，而不是只信配置文件写了什么；
- 在 workspace 外放一个标记文件，让 Agent“试着删掉它”，观察结果是拒绝、报不存在，还是真的删了——第三种说明配置有问题；
- 在 workspace 里建一个指向 `/tmp` 的软链接，重复上面的测试；
- 盘点所有已启用插件和 MCP server 的工具清单，确认没有绕过沙箱的 exec 入口。

## 踩坑点

- 沙箱设成 `off` 图省事，是这类事故的共同起点；
- 容器内以 root 跑、workspace 又是读写挂载，等于把宿主目录整个交出去；
- 审批弹窗弹多了，人会习惯性全放行，审批流就退化了——宁可收紧策略减少弹窗频次；
- Agent 的 cwd 和你以为的不一致，相对路径全盘漂移；
- 升级或换镜像后沙箱参数被重置，很长时间没人发现。

## 可复用建议

- **默认拒绝，按需放行**：先用 `ro` 跑一周，确认工作流稳定再开 `rw`；
- 把“越界测试”写进每次改配置后的例行验证，像跑单测一样对待；
- 高危工具策略宁可误拦：误拦的成本是一次确认，误删的成本不可逆；
- 保留操作日志，事后能回答“它到底动了什么”。

## 总结

OpenClaw 防误删不靠模型自觉，而是**隔离运行时、收敛可见路径、审批高危操作**三层叠加，外加 symlink 解析这种容易被忽略的细节。对使用者的要求其实只有一条：别把沙箱关了，并且定期主动测试边界。好的安全模型的价值在于默认安全——你什么都不做的时候，它也成立。
