## 背景

Agent 的默认输出格式就是 Markdown。我们团队的内容流是：OpenClaw 里的写作 Agent 出稿 → 人工审核 → 同步到博客、掘金、公众号、GitHub README 四个渠道。最初每发一个平台就手工调一遍格式，改到第三次时决定把"格式适配"沉淀成一条管线。

## 问题

坑其实分三层：

1. **生成层**：AI 产出的 Markdown 不稳定——标题层级随机、代码块缺语言标签、偶尔夹带内联 HTML 和 frontmatter 残留；
2. **渲染层**：各平台解析器不一致，微信只认白名单标签、外链会被吞，掘金支持 GFM 但脚注不行，GitHub 又有自己的扩展；
3. **资产层**：图片外链有防盗链，表格在移动端溢出，公式和任务列表支持参差。

单点修补永远修不完，必须在管线里统一解决。

## 做法

核心思想是"一个中间表示，多个适配器"，共五步：

**第一步：输出契约。** 在 Agent 的 system prompt 里固定格式约束：标题从 h2 起头、代码块必须带语言标签、禁用内联 HTML、表格不超过 4 列、图片只写占位符（发布前才真正上传）。让模型先"写对"，比事后修补便宜得多。

**第二步：规范化。** 入管先过 remark-lint 加一组插件：抽离 frontmatter、统一列表缩进、补全代码块语言（缺标签的按 text 兜底并打警告）、清理 AI 爱写的多余分隔线和连续空行。

**第三步：转 AST。** 全文 parse 成标准 mdast（GFM），这是唯一的中间表示，所有平台产物都从这里派生，不允许直接改原始文本。

**第四步：平台适配器。** 每个适配器只做减法：

- 公众号：外链转文末脚注，AST 渲染成内联样式的 HTML（它不支持 class，高亮全靠内联 style）；
- 掘金/知乎：GFM 直出，表格包一层横向滚动容器；
- 博客/GitHub：基本原样输出，只替换图片真实地址；
- PDF：pandoc 走独立模板。

**第五步：门禁与发布。** lint 不过不发；先出预览快照人工确认，再由 OpenClaw skill 调 MCP 工具逐平台推送，失败渠道单独重试，不影响其他平台。

## 踩坑点

- 微信会直接剥掉 `<a>` 标签，外链必须转脚注，别指望平台兜底；
- 图床要选无防盗链的，先传图床再替换链接，否则公众号图片全部裂开；
- 代码块缺语言标签时高亮库会**静默失败**，最好在生成层就卡住，而不是靠兜底；
- 表格列数一多手机端必溢出，契约里直接限死；
- `$...$` 公式和 `- [ ]` 任务列表并非所有平台支持，管线里统一降级成纯文本。

## 可复用建议

- 格式契约写进 system prompt，lint 做双保险：提示词负责"少错"，lint 负责"必对"；
- 适配器只做减法不做加法；任何新格式先确认所有适配器都能处理，再进契约；
- 保留中间 AST，新平台接入成本就是写一个几十行的适配器；
- 预览快照别省，"发布成功但排版稀烂"比发布失败更伤信任。

## 总结

这条管线的关键不在某个具体工具，而在分层：生成层约束、规范化层兜底、AST 层统一、适配器层做减法、门禁层拦截。做完之后，四个渠道的发布从半天手工活变成一条命令，格式类问题基本归零。思路可以直接搬到任何 Agent 内容发布场景，适配器本身不长，值得动手试一次。
