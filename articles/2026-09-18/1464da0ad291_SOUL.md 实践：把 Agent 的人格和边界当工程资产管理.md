## 背景

OpenClaw 的 Agent 不是一问一答的聊天机器人，而是长期驻留、跨多个消息渠道（Telegram、Discord、本地 CLI 等）持续工作的个人助手。人格一致性直接决定使用体验：今天干练克制，明天热情啰嗦，后天突然把系统细节全盘托出。

OpenClaw 把「人格与边界」独立成了 workspace 里的一个文件：`~/.openclaw/workspace/SOUL.md`。它与 `AGENTS.md`（怎么干活）、`TOOLS.md`（工具备注）、`MEMORY.md`（长期记忆）并列，每次新会话作为系统上下文加载。定位很清晰：SOUL.md 回答「你是谁、底线在哪」，而不是「任务怎么做」。

## 问题

不写或乱写 SOUL.md，常见三类故障：

1. **行为漂移**：多会话、多渠道下语气和判断标准不一致；尤其 MEMORY.md 越滚越大后，记忆内容会悄悄盖过风格约束。
2. **边界失控**：过度讨好——破坏性命令不确认就执行，把路径、密钥位置当闲聊输出，或用户不在线时自作主张。
3. **提示词腐化**：人格、流程、安全规则全堆在一段 system prompt 里，改一条动全身，无法维护。

## 做法

我的 SOUL.md 控制在一屏以内，分四段：

1. **身份与语气**：用第一人称写，定位明确。例：「你是一个务实的工程助手，先结论后依据，不用客套开场白」。写具体行为，不写形容词。
2. **价值观排序**：规则冲突时怎么选。例：「诚实 > 风趣；安全 > 帮忙；不确定就说不确定，不编造」。
3. **硬边界**：列出不做的事——不主动执行删除/格式化类操作，不输出环境变量和凭据内容，不代替用户做不可逆决策，涉及金钱和对外发消息前必须确认。
4. **协作模式**：是「等指令」还是「有建议主动提」？被反驳时坚持还是顺从？这些日常摩擦点写清楚，行为才稳定。

配套分工原则：SOUL.md 管是谁，AGENTS.md 管怎么干活，USER.md 管用户是谁，MEMORY.md 管发生过什么。人格类内容一律不进 AGENTS.md。修改后重启会话生效，一次只改一条，观察几天再迭代。

## 踩坑点

- **写太长**：超过两页，关键边界被稀释，token 成本也上去了。每条规则都应是「观察到反例才写进去」。
- **软约束当硬约束用**：SOUL.md 是提示词层面的约束，长会话、强诱导下会被绕过。真正的安全边界（目录权限、命令白名单、MCP 工具鉴权）要在工具层强制，两层配合。
- **和 AGENTS.md 打架**：矛盾指令会让 Agent 行为随机化。定期检查各文件，同一件事只在一处定义。
- **形容词堆砌**：「友好、专业」没有信息量。写「被指出错误时先复述对方观点再回应」这种可执行句子。
- **改了没生效**：先确认 workspace 是否真的重新加载了，而不是继续往上加规则。

## 可复用建议

- 从 10 行以内的最小版本起步，遇到具体 bad case 再加一条，每季度修剪一次。
- 文件头部留几行变更记录，人格是迭代出来的，不是一次设计出来的。
- 上线前用对抗性 prompt 自测：让它删文件、让它吐配置、让它无依据地断言，看边界是否守住。
- 多渠道场景：SOUL.md 定基调，渠道差异（如群聊回复更短）交给 AGENTS.md 的场景规则。

## 总结

SOUL.md 的价值不在「让 Agent 更像人」，而在把人格变成可版本化、可回滚、可 review 的工程资产。硬边界放工具层强制执行，软约束放 SOUL.md 柔性引导，各司其职。写得短、写得具体、持续修剪，比一份一步到位的「完美人格说明书」有用得多。
