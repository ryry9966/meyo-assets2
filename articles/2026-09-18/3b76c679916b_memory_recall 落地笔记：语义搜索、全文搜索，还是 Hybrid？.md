## 背景

给 OpenClaw 助手接长期记忆时，写进去不难，难的是 `memory_recall` 取回来的东西对不对。我给自己的助手迁移记忆库时，把语义搜索和全文搜索各跑了两周，记录了一些真实失败案例。结论比想象中朴素。

## 问题：两种召回各在哪里翻车

**语义搜索**（embedding + 向量相似度，sqlite-vec / pgvector）：

- 换说法能命中：当时记的是“发布流程阻塞”，用户问“之前部署卡住的事”，照样召回。这是它的核心价值。
- 精确信息反而漏：用户问“那个报错码是什么”，召回了五六条“关于报错的讨论”，唯独漏掉唯一记着 `ECONNRESET` 原文的那条。相似度被泛化语义稀释了。

**全文搜索**（SQLite FTS5 / BM25）：

- 错误码、命令、配置项、函数名这类精确 token 一击命中，且排序可解释。
- 但换个措辞就空手而归，中文分词没处理好的话更严重。

单选哪边都会在真实对话里翻车，因为用户的 query 天然分两类：模糊回忆 vs 精确引用。

## 做法：双写、双召回、RRF 融合

1. **写入时双轨**：正文进 FTS 索引；同时按块（中文建议 ≤512 token）过 embedding，连同 metadata（时间戳、来源会话、标签）一起落库。
2. **recall 时两路并行**，各取 top 8，用 RRF（倒数排名融合）合并，不上 reranker 也能得到稳定排序。
3. **query 预处理**：检测到错误码、命令、反引号内容这类精确 token 时，强制走 FTS 或抬高其权重。
4. **时间衰减**：score 乘以按天衰减因子，避免半年前的旧偏好盖过本周刚确认的决定。
5. 返回给模型的结果带 source 和时间，让它自己判断新旧，而不是在检索层硬排序。

整体代码量不到百行，两路检索本地都能跑。

## 踩坑点

- **中文分词是最大的坑**：FTS5 默认 tokenizer 对中文基本按整句切，搜“部署”匹配不到“发布部署流程”。要么上 ngram，要么 jieba 预分词后入库。英文教程不会告诉你这个。
- **块太大，embedding 被稀释**：一开始我拿整段对话做一个向量，召回粒度粗到没法用。按语义单元切块，宁小勿大。
- **改写记忆后旧向量没删**，召回出现新旧两份互相矛盾的内容。向量库要和主表同步做 upsert / delete。
- **没有 GPU 就别上 cross-encoder rerank**，延迟翻倍收益有限，RRF 已经够用。
- **embedding 模型对专有名词不敏感**（插件名、MCP 工具名），这类内容天然该走 FTS。

## 可复用建议

- 只能选一个起步的话，选 FTS：便宜、可解释，而 agent 场景里精确匹配（命令、路径、配置项）是高频需求。
- Hybrid + RRF 是性价比最高的落点，别在“选哪个”上纠结太久。
- 建一份 20 条左右的召回质检集：真实问题 + 人工标注意图，每次改检索逻辑跑一遍回归。这比任何公开 benchmark 都实在。

## 总结

语义搜索解决“换了说法也能找到”，全文搜索解决“精确 token 一击命中”，agent 的记忆两种需求都存在。真正决定 recall 体验的不是算法选型，而是分块、中文分词、元数据和删除同步这些脏活。先把脏活做对，两种检索都能用；做不对，换什么模型都救不回来。
