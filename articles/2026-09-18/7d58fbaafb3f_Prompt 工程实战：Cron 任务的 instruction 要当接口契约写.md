## 背景

OpenClaw 的 cron 任务本质上是「无人值守的 prompt」：到点由调度器拉起一个新会话，把你写的 instruction 交给 agent 执行。它和聊天里随手一句话最大的区别是——**没有人在线上接话**。写得好，它是个稳定的自动化节点；写得差，就是每天准时产出一条废话，甚至一次事故。

我维护着十几个 cron 任务（日报汇总、仓库巡检、RSS 摘要推送），踩过不少坑，总结出一套可复用的写法。核心观点一句话：把 instruction 当接口契约写，而不是当聊天消息写。

## 问题

新手 cron instruction 大多有四个毛病：

1. **依赖上下文**：「按我们上次说的方式整理」——定时任务是新会话，什么上下文都没有。
2. **数据源模糊**：「看看邮件」——agent 自己猜用哪个工具、查什么范围，猜错就是空结果或幻觉。
3. **没有失败分支**：数据为空、工具报错时模型该怎么办？不写清楚，它多半会编一条出来交差。
4. **输出没定义**：发到哪、什么格式、多长，全靠模型发挥，每次跑出来风格还不一样。

## 做法

我现在的 instruction 都按固定骨架写，六段：

1. **任务与时区**：一句话说清做什么、几点执行、用什么时区。时间窗口用「过去 24 小时」这类相对表达，别写死日期。
2. **数据来源**：点名具体工具/MCP 和查询条件。「用 gmail 工具查询过去 24 小时未读邮件」远优于「看看邮箱」。
3. **处理逻辑**：过滤、排序、聚合规则，尽量可判定：「只保留带附件的」「按发件人去重」。
4. **输出契约**：目标会话/频道、格式、条数上限，最好附一个输出示例。示例比形容词管用。
5. **异常分支**：空数据发什么、报错重试几次、重试失败怎么办。明说「没有就发『今日无更新』，不要编造」。
6. **权限边界**：只读还是可写？涉及发消息、调接口这类有副作用的动作，要么禁止，要么要求先输出待执行清单、等人工确认。

一个真实例子的骨架：

```
任务：每日 08:00（Asia/Shanghai）执行
输入：用 <工具名> 拉取过去 24 小时的 <数据>
处理：过滤 <条件>，按 <规则> 排序
输出：发送到 <目标会话>，3-5 条 bullet，每条含 <字段>
异常：无数据发「今日无更新」；工具报错重试 1 次，仍失败则在输出末尾注明
限制：只读，不要回复、转发或修改任何数据
```

## 踩坑点

- **口吻太像聊天**。「帮我看下哈」这种写法，agent 可能在无人会话里反问，然后卡死或超时。
- **时区错位**。调度器按容器时区跑，instruction 里再写「早上」，两边对不上。时区在 cron 配置和 instruction 里都要写死。
- **一个任务塞一条流水线**。拉数据、清洗、分析、推送全写进一个 instruction，中间断了不知道断在哪。拆成多个 cron，或让 agent 调脚本/插件，每步可单独验证。
- **让定时任务发挥创意**。cron 要的是确定性，措辞越收敛越好；需要风格的场景，把风格写进示例里，而不是指望它自己拿捏。
- **改了 instruction 不做回归**。改完先在普通会话里手动跑一遍同样的 prompt，确认输出符合契约再上线。

## 可复用建议

- 写之前先答三个问题：数据从哪来、没数据怎么办、结果给谁看。答不上来就别急着建任务。
- 上线后前两周人工盯输出，把每次跑歪的样本反写成更严的约束，迭代两三轮基本就稳了。
- 在输出契约里加一行「元信息」：让 agent 附上数据来源和拉取时间，出问题时能快速定位是数据层的锅还是指令层的锅。

## 总结

Cron 的 instruction 不是提示词技巧问题，是接口设计问题：输入要指名道姓，输出要有格式和去向，异常要有分支，权限要有边界。把每次失败当成一次接口缺陷来修，定时任务才能从「抽卡」变成基础设施。
