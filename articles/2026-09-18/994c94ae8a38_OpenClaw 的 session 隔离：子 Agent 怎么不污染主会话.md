## 背景

在 OpenClaw 里，主会话（main session）是长期存在的：每个渠道/agent 一条 session，用户消息、工具调用、工具结果按轮次全部追加进上下文。它本质上是一本“只增不减”的账本。一旦你直接在主会话里跑一个长任务——比如让模型连续调用十几次工具做一次调研——中间过程会全部留在主 session 里：挤占上下文窗口、抬升 token 成本，还会让后续对话的注意力被无关内容稀释。

## 问题

几个典型的翻车场景：

- 主会话里直接派活，子任务的几十条 tool call 全部写进主 session 文件；
- 子 agent 复用了主会话的 session key，历史互相穿插，排障时根本分不清哪轮是谁产生的；
- 子 agent 拿到了主会话完整历史，把上一轮的私密上下文带进了并行任务。

表象不同，根因是同一个：上下文边界没守住，主会话被污染。

## 做法

我们现在的固定流程是四步：

1. **派生而非共享**：用 subagent 机制启动子任务，子 agent 获得全新 session，独立文件落盘，与主会话互不读写。
2. **只传任务，不传历史**：给子 agent 的输入是自包含的任务描述 + 工具白名单。主会话里需要它知道的事实，由父会话提炼成几句话写进任务 prompt，绝不整段塞历史。
3. **单向回流**：子任务结束后，只有最终 result 作为 tool result 注回父会话。中间的 tool call、重试、报错全部留在子 session 文件里，排查时去看落盘日志。
4. **产物走文件，不走上下文**：长输出（报告、diff、数据表）让子 agent 写到工作区文件，父会话只收“一句话摘要 + 文件路径”。

另外要收口：给子任务设 timeout 和迭代/token 上限，结束即清理临时 session，避免僵尸子进程继续烧资源。

## 踩坑点

- **result 不截断**：一个三千字的子任务结果注回主会话，等于换了个方式污染。我们约定 result 上限五百字左右，超了就写文件。
- **复用 session key 图省事**：并发跑两个子任务时历史串线，是这类问题里最难查的一种。每个子任务必须用独立 id/label。
- **子 agent 带外发言**：如果子 agent 也能调用发消息的工具，它可能把中间结论直接推到渠道里。子任务默认关闭外发类工具。
- **共享工作区写冲突**：多个子 agent 写同一个文件会互相覆盖，给每个子任务分配独立子目录。
- **MCP 资源占用**：每个子 session 各自拉起一份 MCP server，并发一多端口和内存就紧张了，能复用的 server 配置尽量共享实例。

## 可复用建议

把模式固化成一句话：**task in, artifact out**。进的是自包含任务描述与工具白名单，出的是短摘要 + 文件路径。父会话永远只做调度和决策，子 agent 是无状态工人；子 session 日志按 id 归档，排障只看子日志，不动主会话。

## 总结

session 隔离的本质是控制上下文边界：主会话只保留“决策所需的信息”，过程性内容全部下沉到子 session 和文件系统。守住四条——只传任务、单向回流、产物落盘、及时收口——主会话就能长期保持干净，长任务再多也不会把上下文撑爆。
