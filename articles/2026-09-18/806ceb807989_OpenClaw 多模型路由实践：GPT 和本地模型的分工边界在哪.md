## 背景

跑 Agent 工作流之后才发现，真正的成本大头不是某一次调用，而是调用次数。一个带 MCP 工具循环的任务，跑完动辄几十次模型请求，全走 GPT 的话月末账单很难看。OpenClaw 本身支持在配置里挂多个模型（模型池 + 路由规则），但很多人装完之后要么全走云端，要么全走本地，两头都没占到便宜。

这篇分享我们在几个自动化项目里摸索出的分工方式，不求最优，求稳定可复现。

## 问题

两个极端各有代价：

- **全走 GPT**：成本高、偶尔被限流；而且有些任务（格式转换、简单摘要）用大模型纯属浪费。
- **全走本地模型**：复杂推理和长上下文任务明显掉链子，尤其是工具调用环节，本地模型经常格式不稳，Agent 卡在循环里出不来。

核心问题不是"哪个模型好"，而是**按任务特征分流**。

## 做法

我们的路由策略分三层，逐步收敛，不建议一上来就搞复杂规则。

**第一步：按任务类型分桶。** 我们把 OpenClaw 里的工作拆成三类：

1. 结构化输出类（JSON 抽取、格式转换、分类打标）→ 本地模型（Qwen / Llama 系 7B~14B，量化后单卡能跑）
2. 推理编排类（多步规划、代码生成、复杂工具调用）→ GPT
3. 嵌入和检索 → 本地 embedding，保持向量库一致性

**第二步：按 Agent 角色绑定模型 profile。** 不在全局设一个默认模型，而是每个 agent 声明自己的 `model` 字段。比如一个数据处理 pipeline 里，"清洗 agent" 指向本地，"决策 agent" 指向 GPT。这样路由规则本身就是声明式的，改配置就行。

**第三步：配置降级链。** OpenClaw 的路由配置里支持 fallback，我们设了两个方向：

- GPT → 本地：应对限流和网络故障，宁可质量降级也不要任务卡死
- 本地 → GPT：低置信度任务上调，比如本地模型输出 JSON 解析失败超过两次，自动换云端重跑

## 踩坑点

- **上下文长度静默截断**。本地模型标称 8k，我们一个带 MCP 工具返回的 prompt 实际超过 12k，模型不报错，直接丢了中间内容，排查了一下午。现在路由前会检查 token 数，超限直接走云端。
- **工具调用格式差异**。部分本地模型对 function calling 的支持是"能跑但不稳"，参数偶尔缺字段，Agent 就陷入重试循环。建议工具调用密集的 agent 锁死云端，别为了省钱赌。
- **embedding 模型混用**。中途换过一次 embedding 模型，旧向量全部失效，检索质量莫名其妙下降。向量模型一旦定下来，换模型必须重建索引。
- **本地并发上限**。批处理 50 个任务时本地模型排队，整体延迟反而高于云端。本地模型适合低并发、高重复的场景。

## 可复用建议

1. **先按角色路由，别上智能路由**。用分类器动态选模型听起来高级，但引入新的失败点。角色固定、任务固定的场景，静态规则足够。
2. **给每次调用记日志**：模型名、耗时、token 数、成本。攒两周数据再调路由，比拍脑袋准。
3. **建一个 20~30 条的固定评测集**，每次改路由规则跑一遍，防止"省了钱但质量崩了"的回归。
4. **降级链必须有，但要有告警**。fallback 静默触发太多说明主路由有问题，别让它变成常态。

## 总结

多模型路由的价值不在省那几个点的 API 费，而在于让每类任务都在它该待的地方跑：重复性、结构化的活交给本地，贵的推理能力留给真正需要的地方。OpenClaw 的模型池 + 声明式 profile + fallback 链这套组合，配置量不大，但上线前一定要在真实 Agent 轨迹上验证，尤其是工具调用和长上下文这两个最容易翻车的环节。
