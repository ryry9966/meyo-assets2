## 背景

大多数 AI 助手的默认形态是"应答机"：你发消息，它回复，会话结束就沉寂。但 OpenClaw 这类常驻型 Agent 天然具备做 proactive 的条件——有常驻进程、消息通道、cron 调度和 MCP 工具生态，Agent 完全可以在你没说话时自己"醒来"干活。

问题在于：proactive 做好了是效率工具，做不好就是骚扰源。这篇记录我把 OpenClaw 从纯被动改造成"半主动"的过程，重点讲触发设计和约束，不谈概念。

## 问题拆解

"主动做事"可以拆成三个子问题：

1. **什么时候醒**（触发源）
2. **醒来后要不要出手**（决策门槛）
3. **出手到什么程度**（动作边界）

## 做法

### 1. 三类触发源

- **时间驱动**：cron 任务。我配了每天早上的邮件摘要、每周的周报草稿。
- **事件驱动**：webhook 钩子。Git push、CI 失败、服务器告警，通过 webhook 打进指定会话。
- **状态驱动**：heartbeat。OpenClaw 的 heartbeat 让 Agent 定期自检，配合 MCP 工具轮询状态（日历冲突、磁盘水位、库存变化）。

建议把触发源封装成独立的 MCP server 或轻量脚本，Agent 只消费结构化事件，不直接轮询原始 API——职责清晰，也方便单独限流。

### 2. 决策门槛：先判断，再出手

醒着不等于要说话。我在 system prompt 里加了硬性三条件：事件必须**与用户相关 + 有时效性 + 有可执行动作**，缺一就只写日志、不发消息。第一周我甚至开了"哑巴模式"：Agent 只把"我本想提醒你 XX"写进日志，我每晚 review 一次，用真实数据调阈值，避免一上来就被刷屏。

### 3. 动作边界：读多写少

- 只读动作（查状态、汇总、草拟）直接执行；
- 有副作用的动作（给第三方发消息、改文件）必须带确认，等你点头；
- 高危动作（支付、批量删除）只提示、不代办。

### 4. 可观测性

所有 proactive 行为走同一个 session 日志，记录触发源、判断依据、执行结果。出问题时能回放"它当时看到了什么"。

## 踩坑点

- **heartbeat 频率**：一开始设 5 分钟，token 消耗和噪音双爆。现在固定 30–60 分钟，且 prompt 里明确"无事就不输出"。
- **重复提醒**：CI 连续失败会连环轰炸。加了去重键（事件类型 + 资源 ID + 时间窗），同类事件 2 小时内只报一次。
- **cron 时区**：默认 UTC，早上 8 点的摘要变成下午 4 点。配置里务必显式写时区。
- **webhook 安全**：触发接口等于"唤醒 Agent 的后门"，要加签名校验和密钥，别裸奔。
- **上下文陈旧**：事件触发时 Agent 拿到的可能是几小时前的会话记忆，判断前必须强制重新拉取 MCP 最新状态，别凭记忆办事。

## 可复用建议

1. **先只读、后写入**：前两周零外发，纯日志观察，再逐步放开。
2. **感知与决策分离**：MCP/脚本管"感知"，prompt 规则管"决策"，各自独立迭代。
3. **给主动性上预算**：每日触发次数上限 + 单日 token 上限，防止失控。
4. **把克制写进 prompt**：明确告诉 Agent"沉默是合法输出"，这条比任何技术配置都重要。

## 总结

Proactive 的本质不是让 Agent 更聪明，而是给它一套带刹车的唤醒机制：可靠的事件源、严格的出手门槛、清晰的动作边界、完整的审计日志。OpenClaw 的 cron、heartbeat 和 MCP 生态恰好把这四块积木备齐了。建议从"每天一条摘要"这类低风险场景起步，跑稳了再扩展——主动式 Agent 的信任，是一天一天攒出来的。
