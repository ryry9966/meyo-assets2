## 背景

Agent 接上 MCP 和插件之后，问题就从"它能不能调工具"变成了"它该不该调"。OpenClaw 这类常驻型 agent 尤其明显：跑在你自己的机器上，长期在线，能读文件、能执行命令、能往群聊里发消息。权限给少了，它就是个需要全程盯着的执行器；给多了，一次误判的推理就足以删掉没备份的目录，或者把内部讨论发进客户群。

## 问题的两个极端

实际用下来，失败模式基本只有两种：

- **事事都问**：每条命令都弹确认，三天之后用户开始无脑按 yes，确认机制形同虚设；
- **完全放手**：agent 自己删了关键目录，或未经确认就对外发了消息。

真正的工程问题是：确认本身有成本。权限控制的目标不是"最安全"，而是**把人的注意力花在真正需要的地方**。

## 我们的分级做法

按三个维度给动作分级：**可逆性、影响范围、出错代价**。落到规则上：

1. **只读 + 本地**（读文件、查询、搜索）：直接执行，不确认。
2. **可逆写操作**（git 提交、沙箱内改文件）：自动执行，但强制留审计日志，记录指令原文和结果。
3. **外部副作用**（给他人发消息、调用付费 API、动生产环境、删数据）：必须确认，且确认要带具体参数——不是"我可以发消息吗"，而是"即将把这段内容发给 XX，确认吗"。
4. **高频出现的确认**：不要忍，固化成配置。同一操作确认超过三次，说明它该进白名单或被规则显式允许。

实现上，硬约束放工具层，不放在提示词里：

- OpenClaw 的 exec 审批和工具白名单负责"能不能调"；系统提示词只负责"什么情况下该主动问"。提示词是软约束，会被长上下文稀释。
- MCP 侧用最小权限 token：文件系统 server 别带网络权限，能只读就不给写。
- 对危险模式（递归删除、force push、批量外发）做匹配，命中即升级为必确认。

## 踩坑点

- **确认疲劳**最隐蔽。问得越多，每次确认价值越低，最后用户条件反射点同意，比不问更危险。
- **群聊里的批准权**：agent 在群里问"要执行吗"，任何人回个"好"算不算批准？我们的规则是只认配置指定的 owner，且确认必须是对该次询问的直接回复。
- **权限放大**：两个各自安全的工具，组合起来未必安全——"读文件"+"发消息"等于"可外泄任意本地内容"。分级要看组合，不只看单个工具。
- **批准后的上下文漂移**：agent 发起确认，用户十分钟后才回，中间计划可能已变。确认通过后让它先复述将要执行的动作，不要直接沿用旧意图。

## 可复用的建议

- 先默认全确认跑一两周，把确认日志拉出来分类，再据此定白名单。白名单应从真实使用里长出来，不是拍脑袋。
- 每接一个工具先回答一句话：它最坏能造成什么损失、能不能撤销。答不上来就按最高风险处理。
- 审计日志和确认机制同样重要：前者事后可追，后者事前拦截，缺一不可。

## 总结

权限边界不是一道墙，而是一个随使用不断校准的闸门。判断标准可以压成一句话：**可逆且影响小的自己做，不可逆或出圈的问人，问得太多就改配置而不是改习惯。** Agent 的自主性和安全感，最终来自这套被认真维护的边界，而不是提示词里的几句叮嘱。
