## 背景：被动应答的天花板

多数 Agent 的交互是纯问答式：你不发消息，它就一动不动。用久了会发现一个尴尬的角色错位——你自己成了 Agent 的调度器，得记得提醒它查邮件、盯任务、跑巡检脚本。OpenClaw 提供了一个更符合"助理"定位的机制：心跳（heartbeat）。Agent 按固定间隔自动醒来，读取工作区根目录的 `HEARTBEAT.md`，逐条判断有没有该做的事，然后自己决定行动还是沉默。

## 问题：主动不等于瞎忙

心跳机制真正的难点不是"怎么醒"，而是"醒来之后做什么"。写得不好，agent 要么每跳空转烧 token，要么频繁推送无意义通知，最后你只能把它关掉。主动性是个需要设计的特性，不是开关。

## 做法

1. **建文件**：在工作区根目录创建 `HEARTBEAT.md`，按 Markdown 分节。每节写清三件事：检查什么、满足什么条件、触发什么动作。
2. **定义沉默**：在文件开头明确告诉 agent——如果所有条件都不满足，直接静默跳过，不要输出任何"本轮无事可做"的流水账。
3. **调间隔**：先用长间隔（30–60 分钟）观察，再按需调短。精确到分钟的定时需求应交给真正的调度器（cron、系统定时任务），心跳只负责"值不值得看一眼"级别的巡检。
4. **留痕**：约定一个 `heartbeat-log.md`，要求 agent 每次实际执行动作时追加一行（时间、检查项、动作、结果），方便回溯和调参。
5. **分层**：心跳回合内 agent 有完整工具权限，可以把"检查"委托给脚本或 MCP 服务。`HEARTBEAT.md` 当策略层，工具当执行层，文件里不放实现细节。

## 踩坑点

- **每跳必触发**：条件写得太宽（如"看看有没有新消息"），agent 每次都会报告，通知很快变成噪音。条件必须是可判定的布尔式描述。
- **重活塞进心跳**：心跳回合应保持轻量。耗时几分钟的任务，心跳只负责"发现该跑并启动"，不在心跳回合内执行。
- **上下文会重置**：不要假设 agent 记得上一跳发生了什么。状态必须落盘——上次结果写文件，下次读文件判断增量。
- **不可逆动作无闸门**：删除、发送、下单这类动作，在 HEARTBEAT.md 里显式标注"仅准备、待确认"，或限定为只通知不动手。
- **文件腐烂**：HEARTBEAT.md 会退化成没人维护的 TODO。给自己立个规矩：加一项检查项，顺手删一项失效项。

## 可复用建议

- 把 HEARTBEAT.md 当**巡检策略**而不是任务清单：只写条件和动作，不写目标和口号。
- 一节一件事，每节不超过五行。
- 先看一周日志再调参，别凭感觉调频率。
- 心跳的价值大部分来自**沉默质量**：只在必要时说话的心跳，比事事汇报的心跳有用十倍。

## 总结

HEARTBEAT.md 把 agent 从应答器变成了常驻巡检员，但工程重心在于设计"什么值得检查、什么值得沉默"。条件写窄、状态落盘、重活外移、动作留痕——这四条做到位，这套机制才真正省你的注意力，而不是变成另一个需要照看的子系统。
