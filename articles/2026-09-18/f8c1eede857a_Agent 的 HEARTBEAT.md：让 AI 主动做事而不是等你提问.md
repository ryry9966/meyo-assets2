## 背景

大多数人用 Agent 的方式是纯被动的：你提问，它回答，然后各自离线。OpenClaw 里有一个容易被忽略的机制——**心跳（heartbeat）**：每个 agent 会按固定间隔（默认 30 分钟）自动醒来一次，读取其工作区下的 `HEARTBEAT.md`，把里面的内容当作本轮指令去执行。如果文件不存在，agent 只会收到一个极简 ping，回一句约定好的 `HEARTBEAT_OK`，这条回复会被系统吞掉，不会打扰你。

也就是说，`HEARTBEAT.md` 是你留给 agent 的"值班手册"。写好它，agent 就从问答工具变成一个定时巡检的值守角色。

## 问题

被动模式有三个真实的痛点：

1. **重复输入**：同一句"看看 ~/inbox 有没有新文件"每天要说 N 遍。
2. **时效依赖人**：日历提醒、备份检查这类事，忘了发起就等于没发生。
3. **Agent 没有自己的节奏**：它只有在你想起它时才存在。

## 做法

**第一步：写一份具体的任务清单。** 在 agent 的 workspace 下创建 `HEARTBEAT.md`，示例：

```markdown
- 检查 ~/inbox 是否有新文件；有则总结要点并推送通知，无则跳过
- 当天 09:00 后的第一次心跳：汇总主仓库昨日 git 提交，写入 daily-report.md
- 检查磁盘占用，超过 80% 时提醒
```

**第二步：配置间隔与活跃时段**（字段名以所用版本文档为准，示意）：

```yaml
heartbeat:
  interval: 30m
  activeHours: "08:00-23:00"
```

**第三步：理解执行规则。** 心跳触发时 agent 逐项判断清单，无事可做就回复 `HEARTBEAT_OK`（静默）；有任何实际输出，才会作为消息推送给你。这是整个机制最重要的一个开关：**你的指令措辞决定了它是静默值守还是定时轰炸**。

**第四步：加状态去重。** 让 agent 把"已报告过的异常"写入 memory 或独立的状态文件（如 `heartbeat-state.md`），下轮心跳先对照，同一问题不重复报警，恢复后报"已恢复"。

## 踩坑点

- **没写"仅异常时输出"**：agent 会把巡检过程当成果汇报，每 30 分钟发你一段流水账。
- **任务写得模糊**："帮我盯着项目"会导致每次心跳都产生长推理，token 烧得快，输出还不稳定。每条任务必须有明确的触发条件、检查动作、输出格式三要素。
- **间隔太短 + 重工具**：5 分钟一次配合浏览器抓取或大目录扫描，成本会失控。重活交给 cron 和脚本，心跳只做"读结果、做判断、发通知"。
- **没有去重状态**：磁盘一直 85%，你会每半小时收到一次同样的提醒，直到把它关掉。
- **不设 activeHours**：凌晨三点的心跳提醒通常不受欢迎。

## 可复用建议

- 把 `HEARTBEAT.md` 当**运维值班手册**写，而不是愿望清单：宁少勿滥，一条任务一个判定条件。
- 定期裁剪：连续两周没触发过实际输出的任务，删掉。
- 输出分级：需要立即知道的走推送，周期性报告落盘成文件，别混在一个通道里。
- 和 MCP 工具组合（邮件、日历、文件系统）扩大巡检面，但每轮心跳只挑 1–2 个轻量数据源。
- 记住边界：心跳擅长的是**低频判断类**任务，不是定时执行重计算的地方。

## 总结

`HEARTBEAT.md` 的本质，是把 cron 的定时能力接到 LLM 的判断能力上：cron 负责"什么时候醒"，模型负责"醒来后值不值得说话"。它适合轻量、有明确判定条件的巡检与提醒场景。写好它的关键不是多写，而是**写少、写具体，并给 agent 一个记住"上次说过什么"的地方**。从两条任务开始跑一周，再决定加还是删。
