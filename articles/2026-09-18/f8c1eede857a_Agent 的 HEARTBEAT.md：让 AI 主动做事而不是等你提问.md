## 背景

多数人用 OpenClaw 的方式还是“你问我答”：不发消息，agent 就一直躺着。但 agent 真正的价值往往在你不盯着它的时候——早上的一份摘要、对某个目录变更的巡检、每周清点一次待办。OpenClaw 提供了一个很轻的机制解决这个问题：heartbeat 心跳循环，配合同工作区里的 HEARTBEAT.md 文件。

## 问题：被动响应撑不起值守场景

我最初的做法是外部 cron + 推送脚本，把指令硬编码在 shell 里。问题是逻辑全在脚本中，agent 只是个通知管道；想改巡检规则就得改代码，agent 的推理能力完全没用上。反过来，纯靠在对话里叮嘱“每天早上给我汇报”，会话一重置就丢了。我需要一个持久、可版本化、agent 自己能读懂的任务源。

## 做法

1. 在工作区根目录（如 `~/openclaw/workspace/`）新建 HEARTBEAT.md。
2. 心跳触发时（默认每 30 分钟一次，间隔可在配置中调整），agent 读取该文件，判断哪些任务到期，执行并汇报。
3. 把任务写成带节奏的清单，例如：

```markdown
# HEARTBEAT

## 每天
- 早上 8 点（Asia/Shanghai）：汇总过去 24 小时的日历与未读，发到 Telegram。
- 检查 ~/sync 目录有无超过 3 天未处理的文件，有则提醒。

## 每周一
- 清点 RSS 待读队列，输出 Top 5。
```

4. 让 agent 维护状态：约定它完成后回写文件（勾选、记“上次执行”日期），避免重复触发。
5. 无事可做时让它只回 `HEARTBEAT_OK`，这是约定的最小回复，省 token。

## 踩坑点

- **token 成本会静默累积**。文件每次心跳都会被读一遍，写太长就是常驻开销。我压到 20 行以内，成本才稳定。
- **心跳跑在网关所在机器上**。笔记本合盖、容器停了，任务就静默消失，且不报错。值守类任务务必确认宿主机常开。
- **指令漂移**。“帮我关注一下服务器”这种模糊描述，agent 每次理解都不一样。每条任务要写清工具、范围、输出渠道。
- **时区**。agent 拿到的系统时间未必是你本地时间，涉及具体钟点要显式写时区。
- **别把记忆塞进来**。HEARTBEAT.md 是触发器，执行结果和长期上下文应写进 MEMORY.md，否则文件会越滚越大。

## 可复用建议

- 用三段式模板：每日摘要 / 观察列表 / 定期维护，全文控制在一屏内。
- 先只上一个低风险任务（如每日摘要）跑一周，观察 token 消耗和输出质量，再逐步加监控、告警类任务。
- 用 git 管这个文件，改动即审计，回滚也方便。
- 不需要主动行为时，把心跳间隔设为 0 彻底关掉，而不是留一个空文件空转。

## 总结

HEARTBEAT.md 本质上是你和 agent 之间的一份最小契约：文件定义“何时做什么”，心跳循环保证“一定会被读到”。它不炫技，但把 agent 从聊天窗口里解放出来，变成一个真正能值守的助手。建议从一条每日任务开始，跑稳了再扩展。
