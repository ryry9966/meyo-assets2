## 背景

跑 Agent 做自动化久了，三个问题绕不开：API 费用随调用量线性上涨、敏感数据出网不放心、断网或限流时整条自动化链路瘫掉。本地部署大模型不是要替代云端，而是把高频、低难度、涉隐私的环节收回来。这篇记录我在一台普通家用机（32G 内存 + 12G 显存）上的落地过程。

## 问题

Agent 场景和聊天场景对模型的要求完全不同：

- **长上下文**：工具返回结果会被反复塞进上下文，轻松膨胀到几万 token；
- **结构化输出**：tool call 的 JSON 只要格式崩一次，整轮任务就失败；
- **循环放大**：一个任务跑十几轮推理，单轮延迟会被成倍叠加。

在这三个约束下，家用硬件怎么选型，才是真正要解决的问题。

## 做法

1. **先盘硬件**。显存/内存决定量化档位：Q4_K_M 的 7B 约需 5–6G，14B 约需 9–10G，以此倒推可选模型上限。
2. **选推理运行时**。Ollama、llama.cpp（llama-server）、LM Studio 都提供 OpenAI 兼容接口，接 Agent 框架零成本；追求吞吐再考虑 vLLM，但它对显存要求高得多。
3. **选模型**。优先官方支持 function calling 的系列（Qwen、GLM 的小尺寸版本），量化从 Q4 起步，不要低于 Q4。
4. **接入 Agent**。base_url 指向本地端口，temperature 压到 0.1–0.3，提高 JSON 输出稳定性。
5. **压上下文**。工具返回结果做裁剪，历史轮数设上限，system prompt 精简。本地跑 8K 上下文比硬上 128K 现实得多。

## 踩坑点

- **量化太狠**（Q2/Q3）会导致 tool call 输出格式崩坏、标签缺失，Agent 直接解析失败。省的那点显存不值得。
- **chat template 不匹配**：表现为模型"知道要用工具但格式总错"，多为运行时模板与模型 tool-call 模板对不上，升级运行时或换 GGUF 转换版本可解。
- **标称上下文 ≠ 免费**：KV cache 随长度线性吃显存，32K 上下文可能直接 OOM。
- **延迟叠加**：本地 20 tok/s 对云端 100 tok/s，在十几轮的循环里体验差距是 5 倍以上。先测单轮延迟，再决定是否全本地。
- **MoE 陷阱**：激活参数小、速度快，但全部权重要常驻内存，16G 机器别碰 30B 级 MoE。

## 可复用建议

- **自建评测集**：攒 10–20 条你自己的真实 Agent 任务，每次换模型或量化档跑一遍，比看任何榜单都有用。
- **混合路由**：意图识别、格式转换等简单环节走本地，复杂推理走 API，成本和体验都能兼顾。
- **解耦部署**：把推理服务当独立进程管理（systemd 或守护进程），Agent 侧只依赖 OpenAI 兼容接口，随时可换后端，不锁定任何一家。

## 总结

本地 LLM 的价值不在"全面替代云端"，而在把合适的环节收回来。目前家用硬件下最稳的组合是：7B/14B 量化模型 + OpenAI 兼容运行时 + 严格的上下文管理。先测量、再选型、后接入——别追求一步到位，逐步替换，每一步都有回退方案。
