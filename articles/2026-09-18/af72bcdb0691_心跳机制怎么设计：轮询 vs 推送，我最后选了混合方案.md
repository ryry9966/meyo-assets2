## 背景

OpenClaw 这类常驻 agent 有个绕不开的问题：它大部分时间无事可做，但必须在"该做事的时候"醒来。定时摘要、阈值监控、文件变化、MCP 工具的状态回传，都需要某种唤醒机制。社区里常见的两条路线：固定间隔轮询，或者事件推送。两条路我都跑过一段时间，说说实际体会。

## 问题

纯轮询的问题很直接：为了低延迟就得缩短间隔，间隔一短，token 消耗和 API 调用立刻上去，而且大多数心跳醒来后发现无事可做，纯属浪费。纯推送看起来优雅，但工程坑不少：agent 离线期间的事件会丢，需要持久化队列；多个来源的推送可能重复触发；长连接在笔记本休眠、网络切换时并不可靠。单独选哪条都不省心。

## 做法：低频轮询兜底 + 高优事件推送

我的方案是分层处理，步骤如下：

1. **事件分级。** 把所有唤醒源分三档：定时类（日报、cron 任务）、状态类（磁盘、进程、价格阈值）、交互类（用户消息、webhook）。只有状态类和交互类走推送，定时类留在心跳里。
2. **兜底心跳保持低频。** 默认 30 分钟一次，心跳 payload 只带上次心跳以来的增量变更摘要，不带全量上下文。
3. **推送统一入口。** webhook 或本地事件先写入持久化队列（SQLite 一张表就够），由队列消费者把事件合并后注入 agent 消息流。agent 醒来先消费队列再执行。
4. **合并与去重。** 同一资源 5 分钟内的多次告警合并成一条；每条事件带 event_id 去重，避免重试导致动作重复执行。

配置大致长这样：

```yaml
heartbeat:
  interval: 30m
  payload: delta-only
push:
  queue: sqlite://events.db
  coalesce_window: 5m
```

## 踩坑点

- **心跳风暴。** 三个插件各自注册了 5 分钟定时器，agent 实际每 100 秒醒一次，token 账单很难看。所有定时器必须收敛到统一调度器，插件只注册任务不持有 timer。
- **上下文重建成本。** 每次心跳都注入完整 system prompt + 记忆，成本远超预期。心跳消息要尽量轻，重上下文按需拉取。
- **推送丢失。** webhook 打到本机端口，合盖就全丢。没有持久化队列的推送等于没有推送。
- **MCP 连接假活。** stdio 型 MCP server 逻辑上挂了但进程还在，心跳健康检查必须带真实工具调用，不能只看进程是否存在。

## 可复用建议

- 定时器一律合并，全局只留一个调度器。
- 心跳 payload 默认增量，全量信息唤醒后再拉。
- 推送必须落盘，恢复后补投递，接受"迟到但不丢"。
- 给每次唤醒记录时长和 token 消耗，一周后你一定需要这份数据。
- 演进路径：先纯轮询跑通，延迟确实不满足再引入推送，不要一上来就自建消息队列。

## 总结

轮询和推送不是二选一：轮询保证"不会漏"，推送保证"够快"。低频兜底轮询 + 高优推送 + 持久化队列，是个人 agent 场景下成本与可靠性的一个务实平衡点。关键是先量化自己的唤醒成本和延迟需求，再决定往哪个方向加码——大多数场景下，30 分钟一次的心跳加一条可靠的事件通道，已经够用了。
