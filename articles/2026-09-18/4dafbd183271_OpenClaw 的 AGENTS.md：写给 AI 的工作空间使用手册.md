## 背景

OpenClaw 的工作空间是 agent 的“作业现场”：长期记忆、每日记录、技能目录、草稿脚本都在里面。每次会话启动，agent 不会带着上一轮的记忆，它唯一稳定的输入就是工作空间本身，而 `AGENTS.md` 是它启动时第一个读取的文件。

在 OpenClaw 的语境里，这个文件的定位很明确：它不是 prompt，也不是人设（那是 SOUL.md 的事），而是一份**工作空间使用手册**——说明这里是什么地方、东西放在哪、干活要遵守什么规矩。

## 问题

我最初没写这个文件，跑了几周后遇到三个典型问题：

1. agent 自创目录结构，记忆和临时文件散落各处；
2. 同类任务有时写入 MEMORY.md，有时另开文件，粒度完全看运气；
3. “改代码前先跑测试”这类约定，每次会话都要重新交代。

根源是同一个：这些规则只存在于我脑子里，agent 每次都在猜。猜不一定错，但一定不稳定——自动化最怕的就是这个。

## 做法

我最终收敛的结构，全文控制在 60 行以内：

- **工作空间布局**：每个目录一句话说明用途，并明确“只有这些位置可写”；
- **记忆规范**：什么进 MEMORY.md，什么进每日记录，何时合并整理；
- **工具使用规则**：改文件前后的验证步骤、定时任务交给 cron 而不是自旋轮询、MCP 工具优先于手写脚本；
- **安全边界**：不执行删除类脚本、不推送 git、涉及生产路径必须先确认；
- **任务模板**：把“整理每日记录”“写周报”这类高频任务的固定步骤写清楚。

写作过程建议三步走：先让 agent 自己描述一遍它对工作空间的理解，把它的说法整理成初稿；再人工补充你的私有约定；最后在文件里写一条“更新条款”——发现实际结构和手册不一致时，先提出来，不许擅自改结构。

## 踩坑点

- **写太长**。第一版我写了 200 多行，关键规则的执行率反而下降。这是手册不是文档，人都不愿意读的篇幅，agent 也不会认真读。
- **和 SOUL.md 职责重叠**。性格、语气一旦写进 AGENTS.md，后期维护会打架。守住分工：人设归 SOUL，规则归这里。
- **硬编码绝对路径**。工作空间一迁移全部失效，尽量用相对路径。
- **当成 prompt 写**。满篇“你必须”不如一条陈述式约定——“测试统一放 tests/ 目录”比命令式口吻更稳定，也更容易验证。

## 可复用建议

- 放进 git 管理，像改代码一样用 PR 改它。你会惊讶于有多少约定从来没被明确写下来过；
- 每月做一次“审计”：直接问 agent“按 AGENTS.md，你改完文件后会做什么”，答错的地方就是手册该修的地方；
- 插件和 MCP 工具的使用细节抽到 TOOLS.md 之类的单独文件，AGENTS.md 只留索引，别让它变成杂物间。

## 总结

AGENTS.md 的核心是一次视角转换：把 agent 当成一个会认真读手册、但对你一无所知的新同事，而不是“应该心领神会”的老搭档。把手册写下来，自动化才会稳定；而写手册的过程本身也是一面镜子——很多你以为的常识，其实只存在于你自己的脑子里。
