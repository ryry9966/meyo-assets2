## 背景

AGENTS.md 是近几年逐渐沉淀下来的一个约定：在仓库或工作区根目录放一个 Markdown 文件，专门写给 AI agent 读。它不是给人看的 README，而是把「这个项目怎么构建、哪些目录别碰、提交前跑什么检查」这些上下文固化成机器可读的操作指南。OpenClaw 的 agent 在工作区内执行任务时，会把它当作长期记忆的补充自动加载。

## 没有它会遇到什么问题

实践中常见三类摩擦：

1. **重复交代**：每次会话都要说明「测试用 pnpm，别用 npm」「生成物别放进 src」，费 token 还容易漏。
2. **行为漂移**：agent 按通用习惯行事，比如直接修改只读目录、绕过 lint，产出和团队规范冲突。
3. **不可依赖**：同一种任务两次执行结果不一致，自动化流水线没法放心接在后面。

## 怎么写：一个够用的结构

```markdown
# 项目概述（两三句说清是干什么的）
# 环境与命令（构建/测试/lint 的准确命令）
# 目录约定（哪些只读、生成物放哪）
# 代码风格要点（只写工具管不到的）
# 提交与验证流程
```

三条写作原则：

- **命令可直接复制执行**，不要写「参考 CI 配置」这种转述。
- **负面指令优先**：「不要改 migrations/ 目录」比罗列正面习惯有效得多。
- **控制篇幅**：一个屏幕内读完最好；超过 100 行说明该删或该拆。

## 踩坑点

1. **写成第二个 README**。堆背景故事和历史沿革，agent 读一堆用不上的信息，关键指令反而被稀释。
2. **和全局配置打架**。工作区文件与全局配置对同一件事给出不同答案时，行为不可预测。层级要清楚：全局放通用偏好，工作区放项目事实，不要重叠。
3. **内容过期**。重构后目录变了但 AGENTS.md 没跟上，agent 会照着错误地图走路。把「更新 AGENTS.md」纳入重构 checklist 是最便宜的保险。
4. **指令不可判定**。「写出高质量代码」这类话没有信息量。要写可验证的规则，比如「提交前必须通过 `pnpm lint` 且零告警」。

## 可复用的建议

- **monorepo 用二级文件**。在子目录放各自的 AGENTS.md，agent 会就近读取生效，比一个巨型根文件清晰得多。
- **用最小任务冷启动验证**。跑一个典型小任务，逐条观察 agent 是否遵守约定，把被违反的点补回文件。写 AGENTS.md 本身也应该用 agent 来测。
- **从 code review 反向提炼**。团队里经常被打回的问题（命名、目录、测试缺失）是最高 ROI 的条目来源， review 意见簿就是素材库。

## 总结

AGENTS.md 的本质是把团队工程约定从「口口相传」变成「随仓库分发」。检验标准很简单：一个新 agent 只读这一个文件，就能在不打扰任何人的前提下正确完成一次典型任务。花一小时写扎实，换来的是之后每一次会话的稳定输出——在自动化场景里，这可能是单点投入回报最高的一份文件。
