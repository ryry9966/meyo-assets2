## 背景

用 OpenClaw 做 Agent 自动化的人大概都遇到过类似场景：每次开新会话，agent 都要重新"探索"一遍工作区——猜构建命令、误碰生成文件、提交信息格式随机。人类有 README，但 README 是写给人看的，模型需要的是另一套东西。AGENTS.md 就是这个约定：放在工作区根目录的 Markdown 文件，agent 会话启动时自动读取，相当于一份专门写给 AI 的工作空间使用手册。

## 问题

没有这份手册时，痛点很具体：

- **每次会话重复试错**。agent 靠猜来确定怎么跑测试，猜错了还要烧掉几轮工具调用。
- **口头约定留不住**。你在聊天里说过"别动 lockfile"，换一个会话它就忘了。
- **团队规则散落各处**。每个人在自己的 prompt 里贴一遍同样的注意事项，纯体力活。
- **踩过的坑还会再踩**。上一次它改坏了 `gen/` 目录下的生成代码，这一次照样犯。

## 做法

我的实践分四步：

1. **根目录建 AGENTS.md，写五块内容**：项目结构速览、常用命令、代码风格约定、禁区清单、提交规范。
2. **命令写成可直接执行的形态**，不要写描述性文字。`make test` 就好过"运行测试套件"。
3. **Monorepo 做分层**。根目录放全局规则，子目录按需覆盖，agent 涉及哪个目录就吃哪份规则。
4. **迭代式维护**。agent 犯错且同类错出现第二次，就沉淀一条规则进去。

一个可参考的骨架：

```markdown
# 常用命令
- 构建：make build
- 测试：make test（勿用 go test ./...，缺 build tags 会假失败）

# 禁区
- 不要修改 api/gen/ 下任何文件（自动生成）
- 不要手动编辑 pnpm-lock.yaml

# 提交
- Conventional Commits，描述用中文
```

## 踩坑点

- **别写成 README 或宣传文**。模型需要祈使句和约束，不需要项目介绍。
- **别太长**。单屏读完最好，规则一多，关键条目在上下文里就被稀释了。
- **过期信息比没有更糟**。构建命令换了、AGENTS.md 没更新，agent 会一直跑错的那条。
- **严禁放密钥和敏感信息**。这个文件会被完整读进每次会话的上下文。
- **别神化它**。它是手册不是合同，涉及关键路径的变更，review diff 这一步省不掉。配合 MCP 工具调用时也一样，命令约定只能提高选对工具的概率，不能替代确认。

## 可复用建议

- **让 agent 自己维护**：修完一个问题后追加一句"把这次的结论写进 AGENTS.md"，效果出乎意料地好。
- **纳入版本库**，规则变更走 PR，团队对"AI 该怎么干活"有统一共识。
- **一条规则对应一个可验证的行为**，写完自问：这条规则被违反时我能看出来吗？
- **定期瘦身**，删掉已经固化的规则，给新问题腾上下文空间。

## 总结

AGENTS.md 的价值不在于文件本身，而在于把个人反复口述的 prompt 经验，沉淀成团队可版本化、可演进的资产。写它的成本是半小时，回报是每次会话少掉的试错轮次——这笔账在自动化场景下很好算。如果你还没在工作区放一份，建议从今天的第一个坑开始写。
