## 背景

装完 OpenClaw 后，工作区里会躺着几个 Markdown 文件：SOUL.md 管人格，USER.md 管用户信息，而 AGENTS.md 是那个最容易被忽略的——它相当于新同事入职第一天拿到的内部手册：工作区怎么用、哪些事能做、哪些路径不要碰。区别在于，这份手册每一轮会话都会被注入模型上下文，是真正在“生效”的提示词，不是摆设。

## 问题

没有认真维护过的 AGENTS.md，通常会带来三类麻烦：

1. **Agent 反复“重新探索”**：路径靠猜、命令靠试，把临时文件写进不该写的地方，每个会话都交一遍学费。
2. **行为不稳定**：约定只存在于你的聊天记录里，同一个任务昨天一个做法、今天另一个做法。
3. **上下文被废话占据**：你不得不每轮重复“用 pnpm 别用 npm”“不要动那个目录”。

## 做法

**第一步：先读默认模板，别急着删。** 模板里的条目大多是有人踩过坑才写进去的，先理解每一行的意图，再决定取舍。

**第二步：只写事实和可验证的规则。** 好的条目长这样：

- 构建一律用 `pnpm build`，不要用 npm / npx
- 日志统一写 `logs/`，临时文件用完即删
- 动 `core/` 之前先跑测试

差的条目是“请认真负责地完成任务”这类无法验证的口号，模型只能礼貌地忽略。

**第三步：控制篇幅。** AGENTS.md 每轮都消耗 token，核心内容建议压在一两百行内。细节（比如某个插件的特殊用法）拆到独立文件，这里只留一行索引。如果某个子项目有自己的约定，可以在该目录下放一份嵌套版本，就近生效。

**第四步：用失败反哺。** Agent 做错一次，就补一条一行规则，最好带反例。具体的“不要把 X 写进 Y”对模型的约束力，远强于抽象描述。

**第五步：把工作区放进 git。** AGENTS.md 的每次修改都应像代码一样可追溯，改坏了能回滚。

## 踩坑点

- **写太长**。规则一多，中间内容会被“稀释”，agent 开始选择性失明，token 也是真金白银。
- **把 README 复制进来**。AGENTS.md 是给 AI 的操作指令，不是项目介绍，受众完全不同。
- **规则互相冲突**。你加的条目和模板默认条目打架时，agent 只会随机听一边，先消解冲突再谈别的。
- **写敏感信息**。密钥、token 不要出现在这里——它每轮都会进模型上下文。
- **当安全边界用**。真正的权限限制要在配置层做，手册里的“请不要删库”只是提示，不是护栏。
- **只加不删**。环境变了规则没变，过时的手册比没有手册更糟，因为它听起来很权威。

## 可复用建议

- 三段骨架：**身份与边界 → 环境事实（路径/命令/依赖）→ 工作流程与索引**，按这个顺序组织，模型检索效率最高。
- 每条规则一行、可验证、尽量配正反例。
- 每月做一次审计：通读一遍，删掉不再成立的条目。手册和代码一样需要重构。
- 多设备或团队场景下，工作区进版本库，改手册必须有 commit message。

## 总结

聊天记录会丢，记忆会漂，但 AGENTS.md 是你和 agent 之间唯一稳定、可沉淀的接口。一份维护良好的手册能让每次会话从 80 分起步，而不是从 0 分重新认识你的工作区。把它当代码写、当代码审——投入很小，复利很大。
