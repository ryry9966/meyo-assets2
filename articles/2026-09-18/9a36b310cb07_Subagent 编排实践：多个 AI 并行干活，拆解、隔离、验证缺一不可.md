# 背景

单个 Agent 串行干活有两个明显的瓶颈：上下文窗口被中间结果塞满，以及串行工具调用太慢。比如"给这 12 个模块补齐单元测试""调研 5 个候选方案再对比"，主 Agent 一路做下来，上下文爆炸、耗时长，中途一个环节出错还会污染后面的推理。

Subagent 编排是常见的解法：主 Agent 只负责拆解、派发、汇总，把自成一体的小任务交给并行的 subagent，各自用独立的上下文窗口跑完，只把结构化结果交回来。

# 问题

听起来简单，但第一批并行任务就暴露了几个问题：

1. 两个 subagent 同时改同一个文件，后写的覆盖先写的；
2. subagent 返回一大段自然语言，主 Agent 汇总时上下文反而更臃肿；
3. 某个 subagent 卡死，整批结果被拖住；
4. 自称"已完成"的 subagent，实际测试跑不过。

核心结论：并行不是把任务复制几份同时发出去，而是**拆解、隔离、验证**三件事的组合。

# 做法

以"批量给历史模块补测试"为例，我们的流程固定成了四步：

**1. 主 Agent 先拆解，不动手。** 把任务切成 N 个互不重叠的子任务，每个子任务明确输入（文件范围、相关接口签名）、目标和禁止事项（不改生产代码、不引新依赖）。子任务边界尽量按目录/模块切，天然降低写冲突。

**2. 给每个 subagent 一份自包含的 prompt。** Subagent 看不到主会话，所有必要上下文必须塞进派发 prompt 里。同时规定输出格式：统一 JSON，包含 `changed_files`、`summary`、`status` 三个字段。返回结构化数据是后面能自动汇总的前提。

**3. 并行派发 + 隔离工作区。** 会写文件的 subagent 各自从一个 git worktree 出发，互不干扰；只读类任务（调研、review、文档梳理）可以放心并发，因为没有共享可变状态。并发度控制在 3–5 个，再多收益递减，汇总成本反而上升。

**4. 主 Agent 汇总 + 确定性验证。** 收齐结果后合并 worktree，跑一次全量 lint + 测试。这一步是唯一的裁决标准——subagent 的自我报告只作参考。

# 踩坑点

- **上下文不是免费的。** 8 个 subagent 各返回 2k token 的"详细汇报"，主 Agent 一样会爆。要求 subagent 只返回结论 + diff，过程日志落盘到文件，需要时再读。
- **共享 MCP 服务要限流。** 两个 subagent 同时打同一个搜索类 MCP 工具，触发限流，表现为"任务莫名变慢"。高并发派发前先确认各 MCP server 的配额。
- **没有超时的编排等于裸奔。** 每个 subagent 必须带超时和失败分支，单个失败返回部分结果，不能阻塞整批。
- **别把强耦合任务硬拆。** 有一次把"改接口 + 改调用方"拆给两个 subagent，两边各写各的，合并时全对不上。有依赖关系的任务就串行，或由主 Agent 串好骨架后只并行叶子任务。

# 可复用建议

- 写一个 subagent prompt 模板：目标 / 输入 / 约束 / 输出 schema / 禁止事项，五段固定，每次只填空。
- 先从只读任务练手（批量 review、多源调研），零写冲突，收益立现；写类任务等隔离机制就绪后再上。
- 并发度 3–5 起步，观察汇总阶段主 Agent 的上下文占用再调。
- 每次编排留档：派发了什么、各自结果、验证是否通过。复盘时才能定位到底是拆解的问题还是执行的问题。

# 总结

Subagent 并行的价值不在"多开几个 AI"，而在任务边界是否清晰、工作区是否隔离、结果是否有确定性验证。任务定义得好，并行是乘法；定义得差，并行只是把混乱放大了几倍。建议从只读、幂等的任务开始，把模板和验证门固定下来，再逐步放开写类任务。
