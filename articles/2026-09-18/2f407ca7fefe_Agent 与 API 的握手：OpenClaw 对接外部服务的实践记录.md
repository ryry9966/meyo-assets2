## 背景

Agent 的价值在于能"动手"，而动手的对象几乎都是外部服务：工单系统、内部数据库、第三方 SaaS。在 OpenClaw 里，无论你走 MCP server 还是自写插件，本质上都在做同一件事——把一个 HTTP 服务翻译成模型能理解和调用的工具。这篇帖整理了社区几个实际对接案例（工单、查询类内部服务、公开 API）沉淀下来的一套做法。

## 问题出在哪

最常见的错误做法有两种：把 API 文档整段塞进 system prompt；或者注册一个"万能工具"，参数是一个大 JSON 字符串让模型自己填。结果都很一致：模型选错工具、编造参数、报错后盲目重试，直到烧完上下文。

核心问题是握手协议没定义清楚。模型实际依赖三样东西：**工具描述、参数 schema、返回值结构**。这三者的工程质量决定了调用成功率，和提示词技巧关系不大。

## 做法：把握手拆成三步

### 1. 接入路径：MCP 优先，插件兜底

目标服务已有现成 MCP server 的（GitHub、Slack 这类），直接用，不要重复造轮子。OpenClaw 配多个 MCP server 很直接：

```yaml
mcp_servers:
  - name: ticketing
    command: npx
    args: ["-y", "@scope/ticket-mcp"]
    env:
      TICKET_API_KEY: ${TICKET_API_KEY}
```

没有现成 server 的内部服务，写一个薄适配器注册成插件，别在适配器里堆业务逻辑。

### 2. 工具定义：描述、schema、裁剪

- **一个工具对应一个明确动词**：`create_ticket`，而不是 `ticket_manager` 带个 `action` 参数让模型自己选分支。
- **描述里写正例也写反例**："用于查询工单状态；不要用它创建工单"这种句子对模型选工具帮助很大。
- **返回值裁剪**：外部 API 动辄返回几十个字段，只挑模型需要的，控制在几百 token。分页结果返回摘要加游标，别一次灌完。

### 3. 鉴权与错误：别让模型猜

密钥放环境变量，配置文件里只留 `${VAR}` 引用，启动时校验、缺失即 fail fast。错误返回统一成结构化格式：

```json
{ "ok": false, "error_type": "rate_limited", "hint": "等待 30 秒后重试，最多 2 次" }
```

网络错误和参数错误必须分开，`hint` 告诉模型下一步是改参数、退避重试还是直接放弃。抛一个裸异常让模型看到半截 traceback，是重试风暴的主要来源。

## 踩坑记录

- **描述含糊导致选错工具**：模型在该查库时调了搜索工具。补了反例描述后才稳定。
- **慢接口打爆下游**：某内部接口平均延迟 8 秒，超时后模型立刻重试，高峰期形成重试放大。解法是明确的退避策略加重试上限，写进 `hint`。
- **日志泄密**：适配器曾打出完整请求头，密钥进了日志文件。脱敏必须在适配器层统一做，不能指望每处调用自觉。
- **上游静默变更**：API 改了字段名，schema 没报错但返回空数据。对外部响应加最小校验（关键字段存在性检查）能提前暴露。

## 可复用建议

- 适配器五件套固定下来：超时、带退避的重试、脱敏日志、响应校验、错误映射。
- 上线前用 mock server 把异常路径跑一遍：429、500、超时、畸形响应。
- **描述即契约**：改了工具行为必须同步改描述，模型不会自己发现。
- 每个 MCP server 单独进程跑，崩了不拖垮主 agent。

## 总结

对接外部服务不是"接上就行"。握手质量取决于工具描述、参数 schema、错误结构这三者的工程投入。把每个外部 API 当成一个需要契约和容错的依赖服务来对待，Agent 的调用表现才会从"碰运气"变成"可预期"。欢迎在社区帖里补充你们自己的对接案例。
