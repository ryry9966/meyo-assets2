## 背景

OpenClaw 的 agent 默认靠系统提示词加 MCP 工具列表工作。能力一多，问题就来了：每接入一个 MCP server 都会注入一批工具描述，十个 server 下，schema 就能吃掉上万 token;更麻烦的是注意力稀释——上下文越长，模型对关键指令的遵从度越差。

Skills 机制的思路是**渐进式披露**：启动时只加载每个技能的元数据(name + description,几十 token),模型判断当前任务相关时，才去读完整的 SKILL.md 和附带资源。相当于给能力建了一层极薄的索引。

## 问题

没有 Skills 时，实际用下来有三类典型浪费：

1. **长尾能力常驻上下文**。比如“每月导出服务器账单”这类一月用一次的操作，它的说明 24 小时占着窗口。
2. **工具重复**。三个 server 都有“执行 shell 命令”，描述各不相同，模型经常选错。
3. **prompt 维护困难**。所有能力写在一个大 system prompt 里，改一处要全文 review。

## 做法

写一个技能大致是四步：

**1. 建目录。** 在工作区 `skills/` 下为每个技能建独立文件夹，核心文件是 `SKILL.md`:YAML frontmatter 里写 `name` 和 `description`,正文写操作指引。

**2. 打磨 description。** 这是唯一的路由信号——模型在决定是否加载时只看这一行。写法要同时覆盖“做什么”和“什么时候用”，例如：“导出指定月份的服务器账单为 CSV,当用户提到账单、用量统计、月度成本时使用”。它是写给模型看的搜索关键词，不是写给人看的文档标题。

**3. 拆分资源。** SKILL.md 正文建议控制在几百行以内。参考资料、API 细节放到 `references/` 子目录，让模型按需再读；确定性操作写成脚本放 `scripts/`,通过执行工具调用，而不是靠自然语言步骤自由发挥。

**4. 验证触发。** 开个会话问一个相关问题，观察是否加载了技能内容。不触发，就回头改 description 而不是改正文——路由阶段正文根本没被看到。

## 踩坑点

- **description 太泛或太窄。** “处理数据”什么都匹配不上；只写具体命令名，用户换个说法就漏。要在两者之间找粒度。
- **全塞进正文。** 把所有细节写进 SKILL.md 等于放弃了渐进披露，只省了个目录结构。
- **脚本依赖没写清。** 路径、环境变量、运行时不注明，模型跑到一半报错会反复重试，烧 token 还不一定收敛。
- **技能堆积不清理。** 几十个技能之后，语义相近的 description 会互相抢触发，路由质量明显下降。定期翻会话日志，从未触发的技能要么改写要么删。

## 可复用建议

- 把 description 当“关键词 + 一句话广告”写，时刻记住读者是没读过正文的模型。
- 能脚本化的不要用自然语言描述——脚本是确定性的，自然语言步骤不是。
- 个人偏好类配置(语气、回复格式)不值得做成技能，放全局配置更省一层路由开销。
- 技能之间尽量正交：一个技能一个场景，避免“万能技能”。

## 总结

Skills 的本质是把“能力描述”和“能力实现”分离，用一层几十 token 的索引换取按需加载，把常驻成本从正比于全部工具降到正比于实际触发的那几个。它的主要成本在 description 的打磨上——这部分值得花时间，因为路由错了，正文写得再好也用不上。
