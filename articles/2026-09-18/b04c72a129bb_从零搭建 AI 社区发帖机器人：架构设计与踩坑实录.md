## 背景

社区日常运营里有一类工作高度重复：每周整理本周热门讨论、定期发布活动预告、把 GitHub 上的 issue 动态同步成周报帖。这些任务流程固定、格式固定，但耗时。我们的思路是用 Agent + MCP 工具链把它自动化：一个定时触发的 Agent，负责抓取素材、起草内容、提交到社区，人只做最后一道审核。

本文记录这个机器人从设计到稳定运行的完整过程，重点是架构取舍和踩过的坑。

## 问题定义

动手之前先划边界，避免做成"什么都能发"的黑箱。我们的机器人只做三件事：

1. **聚合**：定时抓取指定信源（论坛 API、仓库动态）；
2. **起草**：调用 LLM 按固定模板生成帖子草稿；
3. **入队**：草稿进入待发队列，人工确认后才真正发布。

明确不做的事：不自动回复、不自动点赞、不处理任何需要判断语义边界的内容。边界越窄，出事半径越小。

## 整体架构

```
cron 调度器
   │
   ▼
Agent 运行时（OpenClaw）
   ├── MCP 工具：fetch_source   拉取信源
   ├── MCP 工具：draft_post     生成草稿
   ├── MCP 工具：enqueue        写入待发队列
   │
   ▼
SQLite 状态库（任务记录 / 内容哈希 / 队列）
   │
   ▼
人工审核 → MCP 工具：publish → 社区 API
```

几个关键决策：

- **草稿与发布权限分离**。Agent 只拿到 `enqueue` 权限，`publish` 是独立脚本，人工触发。这一条是安全底线。
- **SQLite 而不是内存**。机器人会重启、会超时，所有中间状态必须落盘。
- **每次发布带幂等键**（信源 ID + 日期的哈希），重复执行不会发重复帖。

## 实施步骤

1. **先写 dry-run 模式**。前两周机器人只输出草稿到本地文件，不发任何请求。用它校准 prompt 和模板。
2. **实现三个 MCP 工具**。每个工具单一职责，输入输出用 schema 约束，超时设 30 秒，失败重试两次、指数退避。
3. **去重层**。发布前对草稿正文做归一化哈希，与库内近 30 天记录比对，相似度过高直接拦截并记日志。
4. **灰度上线**。先从每周一帖开始，稳定后再加频次。

## 踩坑实录

**坑一：LLM 输出不稳定导致内容漂移。** 同一个模板，跑三次能写出三个标题风格。解法是把标题、结构段全部模板化，LLM 只填充变量段，并在 system prompt 里给两个固定的正反例。

**坑二：Markdown 转义翻车。** 草稿里的下划线和反引号进入社区渲染器后格式全乱。后来在 `publish` 前加了一步格式校验，用社区自己的渲染器本地预演一遍，不通过就退回队列。

**坑三：重试引发的成本失控。** 一次信源接口抖动，Agent 循环重试了 7 轮，token 花掉平时一周的量。解法：给单次任务设硬性预算上限（次数和 token 双维度），超限熔断、留待人工。

**坑四：时区问题。** cron 按服务器 UTC 跑，周报在周五就发出去了。所有调度统一显式声明时区，别依赖系统默认值。

**坑五：密钥差点进了 git。** 社区 API 的 token 一度写在配置文件里提交过一次。全部改成环境变量注入，并在 CI 里加了密钥扫描。

## 可复用建议

- 任何会对外发声的自动化，都必须有**人工闸门**，没有例外；
- 幂等键 + 状态落盘，是所有定时任务机器人的标配；
- dry-run 至少跑两周再接真实 API，成本极低、收益极大；
- 给 LLM 调用设预算熔断，不要相信"它不会循环"；
- 工具权限按最小化分配，Agent 需要什么就开什么。

## 总结

这个项目技术上并不复杂，难点全在工程纪律：边界、幂等、审核、成本控制。上线三个月，周报和动态帖基本零事故，人工审核耗时从每周两小时降到十分钟。对想动手的同学，建议从最小闭环开始——一个信源、一个模板、一条队列，先让它稳定跑起来，再谈扩展。
