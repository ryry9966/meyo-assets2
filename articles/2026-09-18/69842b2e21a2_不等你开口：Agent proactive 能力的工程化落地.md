## 背景

大多数人对 Agent 的用法还是"一问一答"：你打字，它回复，会话结束就归档。这套模式没什么问题，但你其实是整个系统里唯一的调度器——忘了问，事情就停了。

OpenClaw 这类常驻助手提供了另一种可能：它一直在跑，有 heartbeat、cron、webhook、MCP 工具这些"感知器官"，完全可以在你开口之前发现并处理事情。但把 proactive 做好，工程上比想象中难。

## 问题

我们最早的尝试很粗暴：给 agent 挂一个每 15 分钟的心跳，让它"看看有什么值得汇报的"。三天后就放弃了：

1. 每次心跳都带全量上下文，token 消耗是平时对话的好几倍；
2. agent 为了"显得有用"，10 次里有 8 次在汇报"一切正常"，通知很快沦为噪音；
3. 有一次它主动执行的清理脚本把一个工作目录清掉了一半——无人值守时没人拦得住。

结论：proactive 的难点不在"能不能主动"，而在"什么时候值得主动"。

## 做法

现在跑的这套结构，核心是把**触发、决策、行动、发声**四层拆开：

**1. 低成本触发层。** 触发源只做感知不做推理：cron 定时、webhook 事件、文件变更监控。触发本身用一条 shell 命令判断"CI 是否变红""目录是否有新文件"，不满足条件直接退出，根本不进模型。

**2. 主动任务清单作为唯一入口。** 参照 HEARTBEAT.md 的思路，维护一个清单文件：每条任务写清楚检查命令、判断阈值、通知方式。心跳或事件只负责读清单、逐条执行检查，避免每次自由发挥。

**3. 决策门槛前置。** "要不要打扰用户"写成显式规则：数值超过阈值、状态发生翻转、连续 N 次异常才发声，否则只追加到本地日志。判断优先用规则和退出码，确实需要模型参与时，也只喂增量 diff。

**4. 行动分级。** 无监督场景只允许只读操作；写操作和对外发送必须走白名单，且单次运行有 token 和工具调用次数上限，防止失控。

**5. 发声合并。** 同类事件在时间窗口内合并成一条 digest，而不是逐条轰炸。

## 踩坑点

- **心跳频率**：15 分钟一次全上下文心跳，一天近百次推理。改成"哨兵命令便宜跑、异常才升级给模型"后，成本降了一个数量级。
- **自触发循环**：agent 主动写状态文件，又触发了挂在文件变更上的 watcher，循环了十几轮才发现。任何事件源都要配去重和冷却时间。
- **重复汇报**：不记"上次说过什么"，每次心跳都把同一个告警再发一遍。已通知状态必须持久化。
- **权限默认过大**：无人值守 ≠ 全权委托，默认只读、显式申请写权限是底线。

## 可复用建议

- 把每个 proactive 任务当成"带 SLO 的小服务"来写：有触发条件、有判断标准、有关闭开关、有日志。
- 触发便宜、决策严格、发声克制，三者的成本应该依次递增。
- 每个主动任务配独立开关和静默时段，出问题能一键摘除，不用停整个 agent。
- 新任务先跑"只记日志不通知"模式一周，看完日志再定通知策略。

## 总结

proactive 的价值不是"多做了多少事"，而是"在对的时刻做对的事"。工程上的答案很朴素：让触发尽可能便宜，让发声尽可能吝啬，让每一步可审计。做到这三点，agent 才能从"等你提问的工具"变成"安静靠谱的同事"。
