## 背景

跑自动化的人迟早会接受一个事实：你的任务不会只执行一次。MCP 工具调用超时后客户端会重试，Agent 循环里模型可能对同一个工具重复发起调用，cron 配置重叠会并发触发，人工排查时你也会手动再跑一遍。重试不是异常，是这类系统的常态。

## 问题

如果操作本身不可重复，这些"正常机制"就会变成事故来源。典型的非幂等操作：append 写文件、POST 创建资源、计数器自增、发送通知。最麻烦的场景是"超时但实际成功"——请求已经生效，只是响应没回来，重试一次就多一份：工单建了两张、消息发了两遍、积分加了两倍。

很多人的第一反应是"那就不要重试"，但在网络不可靠的环境里，不重试等于把偶发故障放大成必现失败。正确的方向不是避免重复，而是让重复无害——这就是幂等性。

## 做法

1. **先分类**。把任务拆成原子操作，逐个标注：天然幂等（按 ID 置状态、按 ID 删除、upsert）和天然不幂等（创建、追加、自增、发送）。只有后者需要额外处理。
2. **定义稳定的幂等键**。从业务身份派生，比如 `order_id + action`、`source_file + step`，而不是每次运行随机生成 UUID——随机键等于没键，这是最常见的错误。
3. **把去重下沉到存储层**。用唯一索引 + `ON CONFLICT DO NOTHING/UPDATE`，而不是应用层先查后插。并发下"先查再写"有竞态，两个进程可能同时判定"不存在"。
4. **副作用单独处理**。数据库去重了，邮件照样发两遍是常见翻车点。通知类操作要么携带稳定业务键让接收方去重，要么把"已发送"标记与业务写入放进同一事务。
5. **外部 API 用提供方的幂等机制**。多数创建类接口支持传入幂等键，重复提交会返回第一次的结果。
6. **分步任务做检查点**。长任务每步完成后记录进度，重试从断点续跑，而不是从头再来——从头再来意味着每一步都必须幂等，成本更高。

落到 MCP 工具设计上：写类工具可以显式接收 `idempotency_key` 参数，服务端按键缓存首次结果，重放请求直接返回原结果并标记 `replayed: true`。

## 踩坑点

- **随机 UUID 当幂等键**：每次执行都不同，去重逻辑永远不命中。
- **应用层 check-then-act**：没有唯一约束兜底，并发一上来照样重复。
- **幂等记录 TTL 太短**：重试可能在几小时后才到，键早被清了。
- **只幂等了写入，没幂等副作用**：数据对了，消息还是重复。
- **用"今天是否已跑"做判断**：时区、时钟漂移、任务跨零点都会让它失效，业务键更可靠。

## 可复用建议

- 写每个写操作前先问一句：这条操作执行两次，结果会怎样？答不上来就先设计幂等。
- 能用 set-state（"置为完成"）就不要用增量（"完成数 +1"）。
- 做一个通用包装器：按幂等键记录执行结果，命中则短路返回，所有写类任务统一走它。
- 把幂等写进测试：CI 里对关键任务连跑两遍，断言终态不变、副作用计数为一。
- 重放请求返回原始结果而非报错，让上游的重试逻辑可以放心工作。

## 总结

幂等性不是锦上添花，而是自动化的安全底线。重试解决"失败"，幂等解决"重试带来的重复"，两者配套才构成完整的可靠性。你的自动化能不能放心地"多跑一次"，取决于写每一个操作时有没有想过这个问题。
