## 背景

写自动化脚本或 Agent 工作流时，最常见的一个隐含假设是：这段代码只跑一次。现实恰恰相反——网络超时后 Agent 会重试工具调用，定时任务可能重叠触发，webhook 会重复投递，人也会手痒再点一次执行。在 OpenClaw 这类可以被模型反复调用的自动化环境里，**重试不是异常路径，而是常态路径**。

## 问题

操作分两类：读操作天然安全；写操作才是分水岭。"append 一行日志""创建一条 issue""发一条通知""计数器 +1"这类操作，执行两次就有两次效果。典型故障形态：同一个 bug 被建了三个 issue、通知群里被重复轰炸、数据文件越写越乱。更隐蔽的是**部分成功**：任务里有三步写操作，第一步成功后崩了，重试时第一步又完整再来一遍。

## 做法

1. **定义幂等键**。用业务身份而非运行身份：同步任务的键可以是"源数据 ID + 目标系统"，而不是"本次运行的时间戳"。
2. **把"创建"改写成"确保存在"**。先查后建：`ensure_issue(key)` 内部先按唯一键检索，命中就返回已有对象。写数据库用 upsert（`INSERT ... ON CONFLICT`），HTTP 接口支持 `Idempotency-Key` 头就带上。
3. **留执行标记**。多步任务在本地状态（marker 文件、一张 sqlite 表）里记录"第几步已完成"，重入时跳过已完成步骤，类似流水线断点续跑。
4. **有原生能力就用原生的**。目标系统的唯一约束、消息队列的去重 ID、git 的内容寻址，都比自己在脚本里拼逻辑可靠。
5. **安排好顺序**：把难以撤销的操作（发通知、对外发布）放到最后一步。前面全部幂等之后，最后一步失败重试的代价最小。

## 踩坑点

- **幂等键用了时间戳或每次生成的 UUID**：每次重试都是新键，等于没做。键必须来自业务事实，不能来自运行过程。
- **check-then-act 的竞态**：两个并发实例同时通过存在性检查，然后各建一份。要么加锁（文件锁 / DB 锁），要么把唯一性交给服务端约束，靠捕获冲突错误兜底。
- **本地状态与真实状态漂移**：marker 标了"已完成"，但目标系统里其实没有——比如上次写完被人手工回滚了。定期拿目标系统做校准，别迷信本地记录。
- **只把读操作做安全了，写操作照旧 append/insert**。
- **工具描述里没写副作用**。模型不知道这个工具能不能安全重跑，重试策略只能瞎猜。在 MCP 工具的 description 里明确"重复调用效果等同一次"，模型的重试行为会稳很多。

## 可复用建议

- 优先写**对账式任务**：描述期望状态，每次执行都是"把现状拉齐到期望"，天然幂等。这比"按顺序做一串动作"的结构健壮得多。
- 验收标准很简单：**同一个任务连跑三遍，第三遍结束后的系统状态和第一遍结束时一致**。写个冒烟测试把它固化下来。
- 拿不准的操作，先在沙箱或测试空间重跑三遍再上线。
- 设计工具 / 插件时，把幂等性当作接口契约的一部分，和参数、返回值一样写进文档。

## 总结

幂等性不是工程洁癖，而是自动化值得被信任的前提。你敢让 Agent 无人值守地重试，前提是它重跑一百次也不会把事情做重。把"只跑一次"的假设从代码里删掉，换成"跑多少次结果都一样"，自动化的维护成本会肉眼可见地降下来。
