## 背景

Agent 的价值不在对话，而在“能动手”。一个只会在聊天里回答问题的 Agent，和一个能查工单、发消息、跑部署的 Agent，工程价值差一个量级。OpenClaw 的扩展体系——skills、MCP、插件——本质上都在解决同一件事：让模型安全、稳定地调用外部服务。

## 问题

真正动手对接时，通常在三个地方卡住：

1. **对接层选型**：让 Agent 直接发 HTTP 请求，还是包一层 MCP server，还是写成 skill？
2. **凭据管理**：API key 放哪里，怎么保证不进上下文、不进日志？
3. **稳定性**：超时、重试、限流、非幂等操作，谁来兜底？

## 做法

**第一步：先分类，再选对接层。**

- 服务已有现成的 MCP server → 直接接，成本最低，标准化最好；
- 只有 REST API → 写一个窄封装的 skill，把认证、参数拼装、结果裁剪都收在代码里，只暴露两三个语义明确的工具；
- 一次性脚本类需求 → 用 exec 跑 curl 也可，但仅限只读、低频操作。

原则：模型看到的应该是“意图级”工具（如“创建工单”），而不是“传输级”工具（如"POST /api/v1/tickets"）。

**第二步：凭据只走环境变量。** API key 通过 gateway 的 env 配置注入，进程内读取。任何情况下不要把 key 写进系统提示词、工具描述或对话历史；skill 返回结果前做一次脱敏检查。

**第三步：工具描述就是 API 文档。** 模型选工具、填参数全靠描述。每个工具写清楚：什么时候该用、什么时候不该用、参数含义、失败时返回什么。描述含糊是“Agent 乱传参”的头号原因。

**第四步：读操作和写操作分开对待。** 读操作可以让 Agent 自主调用；写操作（创建、删除、付款、发消息）封装成需要确认的两段式流程，或在 skill 里强制要求确认参数。返回给模型的结果做裁剪：分页数据只回摘要和总量，别把 10MB 的 JSON 塞进上下文。

## 踩坑点

- **重试引发重复创建**：POST 类接口没做幂等键，超时后模型重试，结果建了三份一样的资源。写接口务必带幂等键，或在 skill 层去重。
- **限流打满**：Agent 的调用频率和人类不一样，循环任务容易触发 429。skill 里加退避重试，别指望模型自己“等一下再试”。
- **日志泄漏凭据**：debug 日志把 headers 全打出来了。日志只记脱敏后的摘要。
- **工具粒度过细**：暴露二十个细粒度接口，模型经常选错组合。收拢成 3~5 个高层工具，成功率明显更高。

## 可复用建议

- 新接服务时，按"MCP > 窄封装 skill > exec"的顺序评估；
- 每个 skill 强制做三件事：参数校验、错误结构化返回、结果裁剪；
- 上线前用固定的测试指令集跑回归——工具描述改一行，模型行为就可能变。

## 总结

对接外部服务的本质，是给模型一个**说得清楚、算得准确、出错能兜住**的接口面。MCP 解决标准化，窄封装解决安全与稳定，凭据管理和幂等设计守住底线。这三层做扎实，Agent 与外部服务的“握手”才算真正握上。
