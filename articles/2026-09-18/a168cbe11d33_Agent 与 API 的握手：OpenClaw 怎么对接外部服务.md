## 背景

Agent 本身只会推理，真正干活的都是工具。OpenClaw 的定位可以理解成"网关 + 执行器"：模型负责决策，外部服务负责执行。所以对接外部 API 的质量，基本决定了 Agent 的能力上限。这篇帖记录一次把第三方 HTTP 服务接入 OpenClaw 的完整过程，以 MCP 为主线，顺带说说插件和裸 HTTP 的取舍。

## 问题：能调通 ≠ 可用

很多人对接 API 的路径是：curl 调通 → 塞给 Agent → 完事。实际跑起来会发现一堆问题：

- 模型不知道什么时候该调、传什么参数，开始乱猜字段；
- API 超时或返回 5xx，Agent 拿着报错当答案继续编；
- 密钥写死在配置里，仓库一提交就泄露；
- 大段原始 JSON 直接灌进上下文，几轮对话就爆 token。

核心矛盾在于：传统 API 是为人设计的，而 Agent 需要的是为模型设计的接口。

## 做法：四步接稳一个服务

**1. 优先走 MCP。** OpenClaw 对 MCP 是第一梯队支持，有现成 server 就不要自己造轮子。在配置里注册：

```json
{
  "mcpServers": {
    "crm": {
      "command": "npx",
      "args": ["-y", "crm-mcp-server"],
      "env": { "CRM_API_KEY": "${CRM_API_KEY}" }
    }
  }
}
```

关键点是密钥放环境变量，配置文件里只留占位符。

**2. 没有现成 MCP 就自己包一层。** 写一个薄封装，只暴露业务需要的动作，不要把 REST 的全部端点透传。每个工具的 description 要写清"什么时候该用我"，参数写清类型和约束——这是给模型看的文档，不是给人看的。

**3. 加超时、重试和结果裁剪。** 所有出站调用统一加超时（建议 10~30 秒），只对幂等的 GET 做有限重试。返回值在工具层先裁剪摘要，只回传模型需要的字段。

**4. 高危操作加确认。** 写操作（下单、删除、外发消息）不要让 Agent 直接执行，先走 dry-run 或要求人工确认，这层闸门值得多写五十行代码。

## 踩坑点

1. **description 写得太泛。** "查询数据"这种描述，模型会在不该调的时候调。要写清边界，比如"仅查询近 7 天订单，不支持历史数据"。
2. **没有超时。** 上游一挂，整条会话跟着挂，用户看到的就是 Agent 假死。
3. **裸返回原始 JSON。** 10KB 的响应裁到 1KB，上下文寿命能翻好几倍。
4. **忽略限流。** Agent 的重试频率远高于人，务必在封装层做节流，否则容易被对方封 key。
5. **密钥进 git。** 用 `.env` + 占位符，CI 里加 secrets 扫描，一次性把习惯立好。

## 可复用建议

- 一个工具只做一件事。宁可拆三个小工具，也别做一个 20 个参数的大工具；
- 工具返回统一结构：状态 + 数据 + 错误信息，方便模型判断下一步；
- 封装层独立成包，OpenClaw 侧只做注册和编排，以后换框架封装层可以平移；
- 每次工具调用留日志（入参、耗时、状态码），出问题时能回放定位。

## 总结

对接外部服务，工程量的大头不在"调通"，而在鉴权隔离、错误处理和接口收敛。MCP 解决的是协议标准化，剩下的可靠性工作仍然要自己补。把每个外部 API 当成一个需要认真设计的产品接口来对待，Agent 的稳定性才有下限。
