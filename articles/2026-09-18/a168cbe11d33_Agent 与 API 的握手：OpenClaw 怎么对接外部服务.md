## 背景

Agent 的能力上限，往往不是模型决定的，而是它能“够到”哪些系统。一个只会聊天的 OpenClaw 实例价值有限；一旦它能查工单、发消息、操作数据库，才真正开始替你干活。OpenClaw 对接外部服务主要有三条路径：MCP server、skill/插件脚本、网关 channel。这篇帖子以一次对接内部 REST 服务的经历为例，梳理一套可复用的流程。

## 问题

直接把一个 API 扔给 Agent，通常遇到三类麻烦：

1. **凭证散落各处。** API key 一半写在脚本里、一半在提示词里，出问题时没法统一审计和轮换。
2. **模型用不对工具。** 工具描述含糊、参数结构随意，Agent 只能靠猜，失败两三次后开始编造结果。
3. **错误不可读。** 接口返回一段 500 的 HTML 或十屏堆栈，模型既无法理解，也无法向用户解释。

## 做法

我按六步走，基本一次调通：

**一、先选通道。** 只读低频的查询，写一个 MCP server 注册成结构化工具；流程类操作（如“每天汇总再推送”）放进 skill 脚本由定时触发；消息出入口走网关 channel。别为了“统一”把所有东西塞进一种形态。

**二、收敛凭证。** 密钥只放配置/环境变量，注入给 MCP server 进程，脚本一律读环境。每个服务一个最小权限 key，方便单独吊销。

**三、把工具描述写给模型看。** 工具名用动词+对象（`search_ticket`、`create_issue`），描述里写清：何时该用、何时不该用、参数格式、分页怎么翻。这一步投入产出比最高。

**四、设计错误语义。** 返回结构里区分“参数错”“权限不够”“上游超时”，各带一句人话说明。模型拿到可读错误会自己修正重试；拿到堆栈，只会复读堆栈。

**五、控住返回体。** 上游吐 200 条记录时，工具层先截断、先摘要，只透出模型需要的字段。上下文是贵的，别拿原始 JSON 糊它。

**六、加防护再上线。** 客户端设超时（我默认读 10s、写 30s），幂等操作重试一次，非幂等绝不重试；日志对 key 和敏感字段脱敏。

## 踩坑点

- **工具越多越笨。** 一个服务拆了十几个细粒度工具后，模型选错率明显上升；合并成 4 个、参数里加 action 区分后稳定多了。
- **长任务阻塞会话。** 一个跑两分钟的任务把整个会话卡死，改成“提交返回 job id + 单独工具查进度”才解决。
- **联调直打生产。** 第一次就创建了十几条脏数据。之后固定用可配置 base_url 的 sandbox 先跑通。

## 可复用建议

- 每个外部服务一个独立 MCP server，故障隔离、按需启停。
- 描述里写反例（“不要用于 XX 场景”），比十行正面说明更管用。
- 每个工具加一层薄封装，统一埋点、限流、脱敏。
- 联调时开着会话日志，观察模型实际怎么调用工具——这比你对使用方式的想象更重要。

## 总结

对接外部服务这件事，工程量七成在接口之外：凭证治理、错误语义、返回体裁剪。模型只负责“决定调什么”，把“调得对、看得懂、不出事”做扎实，Agent 与 API 的握手才算真正握上。欢迎评论区聊聊你们的工具拆分粒度和错误处理方案。
