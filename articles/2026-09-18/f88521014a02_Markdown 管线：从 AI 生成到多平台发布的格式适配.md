## 背景

做 Agent 自动化写作的团队迟早会遇到这个问题：模型输出的内容天然是 Markdown，但最终发布渠道——公众号、知乎、掘金、自建博客——对格式的接受度各不相同。公众号编辑器不认原生 Markdown，知乎会剥离大部分内联 HTML，掘金对 GFM 支持最好但也有限制。如果为每个平台手工调一遍格式，自动化就名存实亡。

## 问题

实际跑管线时，问题集中在三层：

1. **生成层不稳定**。即使 prompt 里明确约束，模型仍会偶发输出 `<br>`、`<div>`，或以二级标题开头、混用 `*` 和 `-` 的列表。
2. **平台方言差异**。表格、脚注、任务列表、代码高亮，每个平台支持的子集都不一样。
3. **资源链接失效**。外链图片会被防盗链拦截，公众号要求图片走自己的 CDN。

## 做法

我们的管线分四步，核心思想是**一份中间表示，多个渲染目标**：

**第一步：规范化（normalize）**。模型输出后先过一道清洗脚本：统一列表标记、剥掉内联 HTML、保证 H1 唯一、代码块强制围栏加语言标注。正则加 AST 遍历就能覆盖九成情况。

**第二步：转 AST**。用 unified/remark 把清洗后的内容解析成 mdast，后续所有操作都在 AST 层做，不再碰原始字符串。这是整条管线最重要的决定——字符串层面的替换永远是脆弱的。

**第三步：按平台渲染**。每个目标平台写一个 renderer，遍历 AST 输出对应格式：

- 公众号：AST → HTML，样式全部内联（class 会被剥离），代码块预先转成带颜色 span 的 HTML，宽表格在 AST 层降级为列表；
- 知乎/掘金：序列化回 Markdown，砍掉不支持的节点；
- 博客：走完整 remark-rehype 链路，样式交给站点主题。

样式不写死在 renderer 里，而是维护一份 token → CSS 的样式字典，换主题只改字典。

**第四步：校验与发布**。渲染前跑 lint（标题层级、死链、图片可达性），渲染后用平台预览做 smoke test。图片资源在发布步骤统一转存，不依赖源站。

在 Agent 侧，我们把「清洗 + 渲染」封装成一个 MCP tool：Agent 只负责产出规范化 Markdown，格式适配完全下沉到工具层。

## 踩坑点

- **“不要输出 HTML” 的约束不可靠**。清洗必须做，不能只靠 prompt，实测拦截率最高的是 `<br>` 和 `<u>`。
- **公众号的内联样式白名单**。部分 `display` 值会被静默剥离，样式字典里只保留确认可用的属性，别照搬 Web CSS。
- **表格是重灾区**。窄屏上宽表格必然溢出，超过 4 列建议直接降级为列表。
- **松散列表 vs 紧凑列表**。remark 和各平台解析器对空行的处理不同，规范化阶段要统一。
- **frontmatter 泄漏**。模型偶尔把 YAML 头当正文输出，发布前要检测剥离。

## 可复用建议

1. 中间表示用 AST，不要维护 N 份 Markdown 变体；
2. 建一份覆盖全部节点类型的 smoke 文档（标题/列表/表格/代码/图片/引用），每次改 renderer 先跑它；
3. 渲染结果按内容 hash 缓存，迭代样式时不必重跑生成；
4. lint 规则宁可严格——发布失败的代价远高于误报。

## 总结

这条管线本质上是把 Markdown 当作 IR：生成层只保证「够规范」，适配层负责「够兼容」，校验层兜底。分层之后，新增平台只需写一个 renderer，而不是改一遍流程。对做内容自动化的团队来说，这套结构比任何具体的转换脚本都更值得投入。
