## 背景

内容自动化做深之后，绕不开一个场景：让 Agent 起草技术帖，人工审校后发到公众号、知乎、博客等多个平台。AI 产出 Markdown 本身不是问题，问题在"最后一公里"——同一份 md 在不同平台的渲染差异很大，手工逐平台调格式既低效又容易走样。我为此搭了一条管线，核心原则只有一条：AI 只负责产出一份规范 Markdown，所有平台差异交给代码解决。

## 问题

平台差异集中在四类：

1. **HTML 支持度不同**。公众号只保留白名单标签并剥离 class 与外部样式，知乎对 HTML 几乎不认，静态站什么都能跑。
2. **方言不同**。脚注、任务列表、TOC 锚点，各平台支持参差不齐。
3. **换行语义不同**。有的平台把单个换行渲染成换行，有的严格按 CommonMark 合并成空格。
4. **资源链路不同**。图床防盗链、代码高亮方式、外链跳转策略，各有一套。

而 AI 生成恰好爱踩这些雷：混写原生 HTML、出现多个 H1、列表嵌套过深、代码块里再嵌代码块。直接把原始输出喂给各平台 API，等于把不确定性放大 N 倍。

## 做法

管线分三层，AI 只对第一层负责。

**第一层：约束生成。** 在 Agent 的提示词里定义一个"安全子集"：只用标准 GFM，禁止内联 HTML 和脚注，全文唯一 H1，代码块标注语言，图片必须有 alt。生成后立刻跑 markdownlint，不合格打回重写，而不是人工修。

**第二层：规范化。** 用 unified/remark 把 md 解析成 AST，做确定性变换：标题层级压平、图片 URL 统一换成本地图床、按 frontmatter 注入元信息。这一步的产物是中间表示（IR），之后所有适配都基于它，不再碰原始 AI 输出。

**第三层：平台适配器。** 每个目标平台一个渲染器：静态站走 remark-rehype 加高亮插件，能力全开；公众号则在 DOM 层把样式全部内联化，代码块退化为带底色的 pre；知乎、掘金直接上传 IR 对应的标准 Markdown，几乎零转换。

整条管线在我这里是一个 OpenClaw skill，底层封装成 MCP 工具：输入一份 md 和目标平台列表，输出各平台预览链接，人工确认后才真正发布。

## 踩坑点

1. **别用提示词解决格式问题。** 我试过让 AI"直接适配公众号"，输出漂移严重。格式适配是确定性工作，交给代码；提示词只管内容质量。
2. **内联样式只保留最小集。** 公众号对内联属性有取舍，font-family 基本被忽略，字号、行高、颜色最稳。
3. **宽表格在移动端必炸。** 超过四列的表提前转成列表或截图，这是规则，不是例外。
4. **变换必须幂等。** 重试和多端触发会让适配器重复执行，不幂等就会出现双重转义。
5. **预览要用真实环境。** 本地渲染正常的 HTML，过一遍目标平台的编辑器可能就丢样式，最后一步必须人眼确认。

## 可复用建议

- 把 Markdown 方言写成 lint 规则并进 CI，所有 AI 生成过同一道闸门。
- 一份 IR 配 N 个渲染器，永远不要维护 N 份源文件。
- 对渲染结果做快照测试，平台规则变化能第一时间发现。
- 图片压缩、图床上传独立成一步，别混进文本变换里。

## 总结

这条管线本质上是把"格式适配"从提示词工程降级成普通代码工程：AI 负责内容，AST 变换负责规范，适配器负责差异。落地后一次多平台发布从半小时手工排版降到确认一次预览。做 Agent 内容自动化越久越有一个感受：越是追求全自动，越要把中间环节做成确定性的工程件。
