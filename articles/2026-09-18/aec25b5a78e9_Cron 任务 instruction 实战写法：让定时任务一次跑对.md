## 背景

OpenClaw 里 cron 任务的本质是**无人值守的 prompt 执行**：到点触发，agent 拿着你写的 instruction 在一个全新会话里跑完，把结果投递出去。它和交互式对话最大的区别是——没有追问的机会。你写得不清楚，任务就照着不清楚的方向跑完，然后安静地给你一个离谱的结果。

## 问题

我第一批 cron 任务翻车的方式很集中：

1. **指令太口语**："帮我看看今天有什么值得关注的"——"值得关注"的标准完全没定义，每天跑出来的东西都不一样。
2. **引用上下文**："按上次说的格式整理"——cron 是无状态会话，"上次"根本不存在。
3. **没定输出落点**：跑完了，结果发到哪、什么格式、多长，全靠模型自由发挥。
4. **没定义失败行为**：工具调用失败时，它会自己编一个看起来合理的结果。

## 做法

后来我把 instruction 固定成五段结构，照着填就行：

```text
【任务】一句话说明要做什么。
【输入】用什么工具/MCP 拿数据，参数写死（仓库、路径、关键词）。
【逻辑】步骤化：先做什么、怎么过滤、什么算异常。
【输出】固定格式 + 长度上限 + 投递目标（哪个渠道/哪个文件）。
【失败】数据为空或工具报错时的行为：跳过、占位说明，还是发告警。
```

举个实际例子，我每天早上跑的仓库巡检任务：

```text
【任务】检查某仓库过去 24 小时新增的 open 状态 issue。
【输入】用 github 工具查询，repo 固定，按 created 时间过滤近 24h。
【逻辑】过滤掉带 wontfix 标签的；按 bug/feature/question 分组；
每组按创建时间倒序。
【输出】消息不超过 200 字；每组最多列 3 条，格式"标题 + 链接"；
发到指定群。
【失败】查询失败或结果为空，只发一句"今日无新增或查询失败"，
不要猜测原因，不要发空分组。
```

## 踩坑点

- **相对时间是重灾区**。"今天""昨天"依赖模型对时区的理解，明确写"按 Asia/Shanghai 时区当天 0 点到 24 点"。
- **"有异常就通知我"没有可执行性**。异常要定义成可判断的条件：数值超阈值、接口非 200、结果为空。
- **一个任务塞太多事**。我试过让一个任务同时查三个数据源再汇总，中途一个调用失败，整个结果就废了。拆成多个小任务，各自只做一件事。
- **输出不设长度上限**，长消息在推送渠道会被截断，尾部信息直接丢。
- **改完忘了验证**。OpenClaw 的 cron 支持手动触发，任何 instruction 修改都应该先手动跑一次，再等定时。

## 可复用建议

1. 把 instruction 当**"给新同事的值班交接文档"**写：他不知道任何历史背景，只看这一页纸能不能把事做对。
2. 输出模板固定下来，别每次换花样——稳定的格式是下游（人工阅读或另一个 agent 解析）的前提。
3. 判断类标准全部写成**可枚举的条件**，不要留给模型"感觉"的空间。
4. 定期下线跑了几天没产生价值的任务，instruction 也会腐烂。

## 总结

Cron instruction 的核心不是写得花哨，而是**消灭歧义**：输入明确、逻辑可判断、输出有格式、失败有兜底。写完问自己一个问题——如果是一个完全不知道背景的人替你执行这条指令，他能一次做对吗？能，这个任务基本就稳了。
