## 背景

Agent 接上 MCP 之后，能力从"聊天"变成了"动手"：能读文件、跑 shell、调内部 API、对外发消息、花钱。能力上得很快，权限模型却往往还停留在"工具白名单 + 人工盯着"。demo 盯得住，长任务盯不住。

## 问题

实际运行里反复出现两种失败：

- **问太多**：每一步都停下来确认，人变成点击机器，最后条件反射式点"允许"，确认机制名存实亡。
- **问太少**：一次不可逆操作（删表、发正式消息、调大额付费 API）直接执行，事后无法回滚。

核心矛盾在于：确认的价值随次数递减，而风险集中在少数几步。所以真正的问题不是"要不要问"，而是**哪几步必须问，其余怎么放**。

## 做法：按可逆性和影响范围分四档

判断维度只有两个：**能不能撤销**、**出事影响多大**。据此把动作分档：

- **T0 只读**：查文件、list 接口、grep。自动执行，只记日志。
- **T1 可逆写**：工作区内的文件修改、草稿、本地分支提交。自动执行，但必须先有快照/回滚点。
- **T2 出边界或难撤销**：对外发消息、调三方付费 API、删除、改共享资源。必须停下确认，且带着计划摘要问，不是单步问。
- **T3 禁区**：生产凭证、自我修改权限配置、关闭审计。直接拒绝，不留"询问后放行"的口子。

落地到 OpenClaw / MCP 的三个抓手：

1. **按工具分档，不按会话分档**。在 MCP 配置里给每个 tool 标注 tier，T0/T1 直接放行，T2 挂确认钩子。粒度到工具，不要笼统开"全自动"或"全手挡"。
2. **计划确认代替单步确认**。T2 操作让 Agent 先输出计划（要调什么、影响哪些资源、如何回滚），人批一次计划，执行中的 T0/T1 不再打断。确认次数从几十次压到一两次。
3. **T2 强制带回滚方案**。确认提示里必须包含影响对象、预计成本、回滚命令。没有回滚方案的 T2 操作，默认拒绝。

## 踩坑点

- **"只读"工具不一定只读**。有的 GET 会触发 webhook，有的"查询"会写缓存或发测试邮件。接新工具先做副作用审计，别信描述里的 read-only。
- **确认提示太泛等于没有确认**。"我即将执行操作，是否继续？"——人根本无法评估，只会点同意。提示必须具体到资源名和命令本身。
- **上下文压缩后权限被"重新发明"**。长任务经过压缩或重启，Agent 可能忘了自己的边界，把 T2 当 T1 干。边界要写进系统级约束，不能放在可能被压缩掉的记忆里。
- **dry-run 不是真干跑**。验证时要看它实际发出的请求，而不是看它嘴上说"我只会查询"。

## 可复用建议

- 新接一个 MCP 工具，先归档：判 T0–T3，写清回滚方式，再允许 Agent 使用。
- 设确认预算：单任务打断人类的次数设上限（比如 2 次），超了说明分档有问题，回头调工具档位。
- 审计日志与放行同等重要：T0/T1 自动执行的一切，事后可追溯是底线。
- 定期抽样回放：从日志里抽自动执行的操作人工复查，校准分档是否过松。

## 总结

权限边界不是信任问题，是工程问题。可逆的交给 Agent 快跑，不可逆的收敛到少数几次高质量的人工确认，禁区写死在配置里。判断标准长期只需要一句话：**这一步如果 Agent 判断错了，你能不能在五分钟内恢复？** 能，就让它干；不能，就先问。
