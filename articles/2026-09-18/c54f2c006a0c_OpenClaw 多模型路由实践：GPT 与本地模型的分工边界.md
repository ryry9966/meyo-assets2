## 背景

OpenClaw 允许你给 agent 配置主模型和备选链路，但真实部署里很少有人只用一个模型。云端模型擅长复杂推理、长上下文和稳定的工具调用，代价是贵、慢、数据出网；本地模型（Ollama / vLLM 起的 Qwen、Llama 等）便宜、隐私可控，但能力和上下文有限。多模型路由要解决的不是"能不能接"，而是**哪个任务交给谁**。

## 问题

我早期把所有 session 都跑在一个旗舰云模型上，月底一算，成本里约七成来自高频但低价值的调用：会话摘要、消息预分类、定时任务的状态检查。反过来也试过全本地，结果主 agent 在多步工具编排上频繁出现参数幻觉，chain 经常断在第三四步。两头都不对。

## 做法

**1. 先给任务分层，而不是给模型排队。** 把 OpenClaw 里的工作拆成三类：

- 重决策：规划、写代码、复杂 MCP 工具编排 → 云端旗舰
- 轻负载：摘要、分类、格式转换、cron 例行检查 → 本地小模型
- 敏感数据：涉及私人文件、密钥、聊天记录 → 本地，不出网

**2. 配置主备链路。** 全局用云端旗舰做 primary，本地做 fallback；再对轻负载 agent 单独 override 成本地为主：

```jsonc
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4.1",
        "fallbacks": ["ollama/qwen2.5:14b"]
      }
    }
  }
}
```

（字段名随版本有差异，以你本地 `openclaw.json` 的 schema 为准。）

**3. 按 agent 路由。** OpenClaw 的 agent 体系天然适合按角色分模型：跑 MCP 编排的主 agent 用旗舰，负责消息预分类的辅助 agent 用本地 7B–14B 足够。

**4. 用 trace 驱动调整。** 记录每次会话实际使用的模型，跑两周看数据再迁移，不要拍脑袋。

## 踩坑点

- **本地模型的 tool calling 是最大的坑。** 很多小模型 function call 格式不稳定，工具编排会静默失败或参数幻觉。原则：轻负载路由只接"不调工具"的任务，一涉及工具就回云端。
- **fallback 链会掩盖故障。** 云端限额打满后悄悄降级到本地，你以为服务正常，其实质量已经掉了。降级事件必须打日志，最好触发通知。
- **上下文长度不匹配。** 本地 8K 窗口接了长会话会被截断，工具结果一丢，模型就开始编。把上下文长度作为路由的硬条件，而不是参考项。
- **本地推理的冷启动。** Ollama 默认几分钟空闲就卸载模型，cron 任务每次重新 load，p95 延迟比预期差很多。常驻任务记得设置 keep_alive。

## 可复用建议

- 默认"一个旗舰 + 保守 fallback"起步，别一上来做智能路由——路由决策本身也是一次调用，开销经常大于省下的钱。
- 按**任务类型**路由，别按 token 数路由。任务类型在划分 agent 时就已经确定，零额外成本。
- 每周看一次按模型维度统计的成本与失败率，数据会告诉你该把哪个 agent 挪走。
- 本地模型版本锁定，关闭自动升级——工具调用行为可能随版本变化。

## 总结

多模型路由的价值不在"接了多少模型"，而在分层是否清晰：重决策、带工具的交给云端旗舰保质量；高频、无工具、涉敏感数据的交给本地保成本和隐私。先跑通单模型，让 trace 告诉你迁移时机，路由规则越简单越好维护。
