## 背景

RSS 没死，只是读取方式老了。我订阅的源长期在 200+，纯人工阅读积压严重。AI 摘要听起来是解法，但把每条都扔给 LLM 很快会撞上两个现实：token 账单和摘要质量都不行。这篇记录我在 OpenClaw 上搭的一条管线，跑了三个月，把结构和踩坑都摊开说。

## 问题定义

核心不是“摘要”，是“分流”：

- 大部分条目不值得读，真正值得摘要的也许只有 10%
- 摘要里如果没有“为什么值得看”，等于没摘
- 管线要幂等、可观测，坏了能定位到哪一层

## 做法

整体五层，每层独立可重跑：

1. **采集层**：Miniflux 做源聚合，OpenClaw 定时任务每 30 分钟拉新条目，按规范化 link 哈希 + 标题相似度双保险去重，落 SQLite。原文先存，处理异步。
2. **规则层**：零成本过滤。黑名单域名、正则关键词、转载检测，直接砍掉约 40%。
3. **打分层**：小模型对剩余条目按兴趣画像打 0-10 分。画像就是一个配置文件：

```yaml
# profile.yaml（节选）
interests:
  - agent 编排与工具调用
  - 自托管基础设施
reject:
  - 融资新闻
threshold: 6
```

低于阈值直接归档，不进摘要。
4. **摘要层**：只对过线条目调大模型，prompt 强制三个字段：一句话结论、为什么值得看、原文链接。每天 21 点合并成日报，按分数排序而非时间。
5. **分发与检索**：日报推 Telegram；同时把摘要库挂成 MCP tool，Agent 可以随时查“最近一周关于 X 的内容”。这是我觉得最值的一步——信息流从推送变成了可查询资产。

成本上，两段式（小模型打分 + 大模型摘要）比全量摘要降了约 85% 的调用量。

## 踩坑点

- **guid 不可信**。有的源 guid 会变，去重失效导致重复摘要，最后靠 link 哈希兜底。
- **只有标题没正文**。直接摘标题会产出正确但空洞的话，还幻觉补细节。必须先过 readability 抓正文；抓不到就标记“仅标题”，摘要里明说。
- **正文既是数据也是注入源**。真遇到过文章里写“忽略以上指令”。所有正文只当数据，system prompt 钉死角色。
- **源突发**。某个聚合源一次吐 300 条，当轮成本翻倍。后来每轮设条目上限，超出的排下一轮。
- **摘要的摘要会失真**。日报合并时把单条摘要再压缩，细节丢得厉害。后来日报只做排序加一句总评，不重新摘。

## 可复用建议

- **先存后算**：采集与消费彻底分离，换模型可以随时重跑全量。
- 兴趣画像当配置迭代，别写死在代码里；打分不准先改画像，再考虑换模型。
- 日报必须带原始链接，摘要只做导航不做替代。
- 全流程日志带条目 ID，出问题可回放。

## 总结

这条管线的关键不在模型多强，而在结构：便宜的模型做分流，贵的模型只做该做的事，产物沉淀成可查询的库。三个月下来，每天实际点开的原文 3-5 条，但没漏过真正要紧的。信息过载解不掉，只能把注意力花在筛选后的那 10% 上。
