## 背景

OpenClaw 的 Agent 跑久了会积累大量记忆：会话摘要、用户偏好、项目决策、临时约定。`memory_recall` 是把这些记忆捞回来的那一步，它直接决定 Agent 是"真记得"还是"装记得"。社区里常见两派做法：向量语义搜索（embedding + 余弦相似度）和全文搜索（SQLite FTS5 / BM25）。两种声音都有，但拿真实数据对比的不多。

## 问题

我们拿自己跑了几个月的记忆库做了实测。语料约 3000 条记忆，单条 50–200 字。翻日志后发现 recall 请求明显分两类：

1. **精确实体查询占六成**：找某个 token 名、某个文件路径、某次约定的截止日期，查询关键词和记忆原文高度重合；
2. **模糊转述占四成**：问"上次说部署要注意啥"，而记忆里存的是"发布流程评审结论"。

直觉上这两类查询的最优解不是同一个，值得分开验证。

## 做法

1. 从日志抽 120 条真实 recall 请求，人工标注应命中的记忆条目，做成评测集；
2. 全文侧：SQLite FTS5 + trigram 分词（中文必需，踩坑细说）；
3. 语义侧：本地跑 bge-small-zh-v1.5，入库时算 embedding，查询时暴力算余弦——3000 条根本不需要独立向量库；
4. 混合方案：两路各取 top10，用 RRF（倒数排名融合）合并；
5. 指标：hit@3 和 MRR。

结果：实体类查询全文搜索 hit@3 约 91%，语义只有 78%——embedding 会把精确 token"磨平"。转述类查询语义反超，85% vs 64%。混合方案整体 hit@3 到 94%，MRR 也是最高。结论不意外，但数据值得记录：**没有全能选手，混合是明确的最优解**。

## 踩坑点

- FTS5 默认的 unicode61 分词器基本不能处理中文，整段中文会被当一个 token。SQLite 3.34+ 自带的 trigram 分词器是最低成本解法；
- 别用纯英文 embedding 模型跑中文短文本，相似度会大面积虚高，务必选中文向量模型；
- 记忆条目别写成长段落，一条一个事实。条目过长会稀释语义相似度，召回位置明显下滑；
- 余弦阈值不可跨模型复用，0.8 在这个模型合适、换一个就是灾难，不要硬编码进配置；
- 纯相关性排序会翻出一年前的陈旧记忆，按时间做衰减加权是必须项。

## 可复用建议

- 个人助理规模（万条以下）不上独立向量库：FTS5 + 本地小模型 + RRF，复杂度低一个量级，效果反而更稳；
- 把 recall 未命中当运维问题：记日志，每周人工扫一遍 miss 样本，这是提升记忆质量最有效的动作；
- 记忆条目入库时带时间戳和来源会话 ID，后续做时间衰减和排障都靠它。

## 总结

语义搜索和全文搜索是互补关系，不是替代关系。实体查询靠全文，转述查询靠语义，RRF 融合是性价比最高的落点。别迷信"向量数据库"这个名词——先把评测集建起来，用自己日志里的真实请求说话。
