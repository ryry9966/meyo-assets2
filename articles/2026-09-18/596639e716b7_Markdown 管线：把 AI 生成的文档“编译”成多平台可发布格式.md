## 背景

我们的 Agent 工作流里，大部分内容产出最终都是 Markdown：模型写稿、定时任务写周报、技能生成操作文档。生成环节已经足够稳定，真正的摩擦在发布端——公众号、知乎、掘金、GitHub README、自建博客，各平台渲染规则差异很大。同一份 Markdown，在 GitHub 上完美，贴进公众号编辑器就散架。

## 问题

- 公众号编辑器只接受白名单标签，`style` 属性大量被剥离，代码块没有高亮，外链图片有防盗链。
- 单换行、任务列表、脚注、数学公式，各平台支持程度参差。
- AI 输出本身不完全可控：有时夹带内联 HTML，有时整段包进代码围栏，有时带出 frontmatter。

这些不是渲染 bug，是“方言”问题。靠手工修格式不可持续，必须管线化。

## 做法

核心思路是把这件事当成一次编译：**受限的中间表示 + 按目标平台的序列化器**。

1. **收敛源格式**。约定只允许 GFM 子集：标题、段落、列表、表格、围栏代码块、图片。禁内联 HTML、禁脚注，公式按需开关。写进 prompt 的同时，落成 lint 规则，两边共用一份规则文件。
2. **AST 化处理**。用 unified/remark 解析成 mdast，所有转换在 AST 上做，不拿正则替换字符串——正则方案我们已经吃过亏。
3. **平台适配器**。每个目标一个插件：
   - 公众号：mdast → rehype → 内联 CSS 的 HTML；代码块在构建期用 highlight.js 切成带颜色的 span；图片先走公众号素材接口上传，拿回微信域名 URL 再回填。
   - 掘金 / GitHub：GFM 基本透传，只做图片转存和 frontmatter 剥离。
   - 博客：保留最全，走正常静态站点管线。
4. **收口成 CLI + MCP 工具**。`publish --target wechat|juejin|blog` 一条命令产出对应产物，Agent 可以直接调用这个工具完成发布，不需要人介入格式环节。

## 踩坑点

- 公众号对 `class` 几乎不认，`style` 部分标签保留部分不保留，只能构建期全部内联，并且按移动端逻辑宽度（375px）验证，别在桌面浏览器里目测。
- 数学公式别指望 KaTeX 的 HTML 输出存活，要么转图片，要么放弃这个平台。
- 表格列多必炸，移动端阅读控制在 3 列以内，超了降级成列表。
- 图片转存后必须回填新 URL 并校验 200。我们遇到过转存成功、但文档里仍指向旧外链的情况，发布后图挂了。
- AI 偶发输出“围栏里套围栏”，lint 要有嵌套检测，否则整段正文变成代码块。

## 可复用建议

- 把 Markdown 子集当成 API 契约维护，prompt 和 lint 读同一份规则，改一处生效两头。
- 适配器一个文件一个平台，新增平台的成本接近写一个序列化函数。
- 固定几篇样例文档做快照测试，渲染产物变化 CI 直接报错。
- 别在 prompt 里解决外观问题。prompt 只负责语义正确和子集合规，格式全部交给构建期，这样换模型不用重调样式。

## 小结

这件事本质不难，难的是克制：源格式越自由，下游适配越贵。收敛语法、AST 化处理、按平台序列化、快照兜底，四步走完，AI 生成到多平台发布这条链路基本可以无人值守。以后再来新平台，你的边际成本只是一个新适配器。
