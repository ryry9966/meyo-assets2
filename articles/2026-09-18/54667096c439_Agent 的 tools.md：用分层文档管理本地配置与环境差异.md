## 背景

跑 Agent 这一年多，最深的体会是：同一个 agent，换一台机器就是另一个 agent。笔记本上有 `uv`，家里服务器只有系统 Python；公司网络要走代理，VPS 上直连；本机 MCP 端口、工作目录、GPU 有无，全都不一样。这些事实如果不落盘，agent 每次冷启动都要重新踩一遍坑。

多数 agent 框架（包括 OpenClaw 系）支持在项目里放一份 markdown 作为环境说明——常见名字就是 `tools.md` 或 `AGENTS.md`，启动时注入上下文。它是控制 agent 行为性价比最高的一份文件，但也是最容易腐化的一份。

## 问题

我踩过三类典型事故：

1. **跨机器复制的陈旧文档**。把 A 机器的 tools.md 原样拷到 B 机器，agent 上来就执行 `apt`，而那台是 macOS。
2. **机密入库**。为省事把 API key 直接写进 md，后来仓库共享，git 历史里擦不干净。
3. **文档膨胀**。越写越长，塞满一年前的旧路径，agent 读到自相矛盾的描述后开始瞎猜，还不如不写。

本质问题是：tools.md 里混了三种变更频率完全不同的内容——团队共识（稳定）、机器事实（易变）、机密（不该出现）。

## 做法：按变更频率分层

我的方案是三层拆开：

1. **`tools.md`（共享层，进 git）**。只写与机器无关的约定：代码风格、提交规范、工具链调用方式、MCP server 的语义说明。团队所有人一致。
2. **`tools.local.md`（本机层，gitignore）**。写这台机器的事实：OS 与包管理器、Python/Node 路径、代理地址、GPU、本机 MCP 端点。第一天就把 local 文件加进 `.gitignore`，同时提交一份 `tools.template.md` 作脚手架。
3. **生成事实段（脚本产出）**。易变信息不手写。写一个幂等的探测脚本，跑 `uname`、`which`、`python3 -V`、端口探测等，把结果写进 local 文件的 Facts 段，带生成时间戳。环境变了重跑一遍，不靠记忆更新。

结构上给 local 文件定一个稳定的 section schema（network / runtimes / paths / mcp / quirks），每条事实尽量写成「事实 + 原因 + 验证命令」三段式，让 agent 能自己跑命令确认，而不是盲信文档。

两条配套规则：优先级写死在共享层——local 覆盖 shared，冲突以 local 为准并记录原因；机密一律不落 md，只写环境变量名，并明确告诉 agent「从环境读取，不要要求我粘贴」。

## 踩坑点

- **生成段忘记刷新**：Python 升级了，文档还指向旧解释器。时间戳 + agent 启动时发现超过 N 天就提示重跑，能兜住大部分。
- **两份文档打架**：AGENTS.md 写"用 poetry"，tools.md 写"用 uv"。上下文里出现矛盾指令时行为不可预测。约定只有一个信源。
- **太长**：local 文件超过两三百行，关键信息被稀释。每季度删一次，删不掉的要么升入共享层，要么本来就该删。
- **缺冷启动验证**：改完文档没测过。我的习惯是新开会话跑一个冒烟任务（拉仓库、装依赖、跑测试），全靠文档能走通才算合格。

## 可复用建议

- 模板 + bootstrap 脚本一起进仓库，新机器 `clone && ./bootstrap.sh` 五分钟出一份可用的 local 文档。
- `.gitignore` 第一天就配好，别等泄密。
- 事实条目带验证命令，把"文档"变成"可自检的文档"。
- 共享层用 git 管理，出问题可以 diff 回溯。

## 总结

tools.md 不是笔记，是 agent 的运行时输入。按变更频率分层：共识进共享层、机器事实进本机层、易变信息交给脚本生成、机密只留变量名。配上冷启动冒烟验证，这套方法论能让你在任何一台新机器上，十分钟内把 agent 拉到可用状态。
