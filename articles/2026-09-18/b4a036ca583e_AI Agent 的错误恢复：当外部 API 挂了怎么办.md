## 背景

Agent 的能力边界基本由外部依赖决定：模型 API、搜索、网页抓取、MCP 工具、自建服务……只要有一条链路不稳定，整个任务就可能中断。和传统后端不同，Agent 的调用链更长、更异构——一次任务里可能串着 LLM、MCP 工具、HTTP 插件，任何一环超时都会向上传播。所以错误恢复不是锦上添花，而是 Agent 能否在真实环境里长期跑的前提。

## 问题

最常见的三种翻车方式：

1. **裸重试**。工具抛错后原样再调，连续 20 次全是 429，token 和配额一起烧完。
2. **无差别重试**。把 401、400 也当瞬时故障反复打，结果必然失败，还把总耗时拖爆。
3. **副作用重复**。对"发消息""下单"这类非幂等操作直接重试，服务端其实收到了两次，只是第二次超时没返回。

还有个隐蔽问题：Agent 把原始堆栈或 HTML 错误页塞进上下文，模型被噪声带偏，开始编造"已重试成功"。

## 做法

核心思路：**把错误分类，分级处理，每一步都有预算上限。**

1. **错误分类**，至少四档：
   - 网络层（超时、DNS、连接重置）→ 可重试
   - 429 / 503 → 可重试，优先读 `Retry-After`
   - 4xx 业务错误（401/403/400）→ 不重试，走凭证刷新或参数修正
   - 5xx → 指数退避重试，设上限
2. **重试策略**：指数退避 + 抖动（jitter），如 1s/2s/4s 起步，最多 3~5 次；同时设**总时间预算**（如 30s），超了就放弃这条路。
3. **降级与兜底**：主工具失败后按链条走——备用 API → 本地缓存（标注"可能过期"）→ 跳过可选步骤并如实告知用户。宁可降级完成，不要静默出错。
4. **熔断**：同一工具连续失败 N 次（如 5 次）进入冷却期（如 60s），期间直接走兜底路径，不再撞墙。
5. **幂等保护**：写操作必须带幂等键，或重试前先查询是否已生效。这是最容易被忽略的一条。
6. **错误信息结构化**：回传给模型的不是堆栈，而是 `{tool, error_type, retryable, hint}` 这样的紧凑摘要，让模型据此决策。

## 踩坑点

- 每次重试各有 timeout，但没有全局 deadline，单步耗时可到几分钟，Agent 主循环被卡死。
- 429 重试太快，配额没恢复，反而进入更长的封禁窗口。
- 把 401 当瞬时错误重试；正确动作是刷新凭证。
- 熔断阈值太敏感，一次偶发抖动就把工具切进降级模式太久。
- 兜底缓存不标注时间，模型把旧数据当最新结论输出。
- MCP 工具/插件本身没设超时，一个挂起请求拖垮整个会话。

## 可复用建议

- 所有外呼统一走同一个封装：超时 + 重试 + 熔断 + 结构化日志，别在每个工具里各写一套。
- 每个工具单独配置 `max_retries`、`backoff_base`、`timeout`、熔断阈值。搜索类和支付类的容错策略不该一样。
- 开发环境做故障注入：模拟 429、超时、断连，验证降级路径真的走得通。
- 记录每个工具的失败率指标，失败率曲线是最早的报警信号。
- 降级提示要诚实："X 服务暂不可用，本次基于 2 小时前的缓存数据"。

## 总结

外部 API 一定会挂，问题不是"会不会"，而是挂的时候 Agent 表现得多体面。**有界的重试、明确的错误分类、幂等写操作、熔断加诚实的降级**——这四件事做好，Agent 就能从"一次故障全盘报废"变成"带伤也能把任务收尾"。错误恢复的本质是控制失败的成本，而不是消灭失败。
