## 背景

Agent 的能力边界，基本等于它能调用的外部服务边界：搜索、天气、数据库、支付、各类 MCP 工具。这些依赖没有一个是为你保证可用的。单机脚本挂了重跑就行，但 Agent 是多步编排，一步工具调用的失败会被放大：要么卡死整个流程，要么把错误信息当上下文继续推理，产出似是而非的结果。

## 问题

实际跑过长任务的人基本都撞见过三类故障：

1. API 超时或 5xx，Agent 反复重试，token 烧了一圈还在原地；
2. 错误响应（甚至一整页 WAF 的 HTML）被塞进上下文，模型开始对报错"脑补"；
3. 上游彻底不可用，任务既不成功也不失败，悬在那里占资源。

根因通常只有一个：把容错逻辑交给了提示词，而不是代码。

## 做法

### 1. 错误分类前置

在工具封装层（MCP server 或插件）就把错误归一化，别透传原始响应。建议统一返回结构：

```json
{ "ok": false, "error_type": "upstream_timeout", "retryable": true, "hint": "上游搜索服务超时，可稍后重试或改用备用源" }
```

模型拿到的是结构化、可决策的信息，而不是一段需要它自己猜的报错文本。

### 2. 重试收敛在代码层

- 只对幂等操作自动重试；创建订单、发消息这类操作失败后，交给上层决策；
- 指数退避 + 随机抖动，最多 2~3 次，遵守 `Retry-After`；
- 连接超时和读取超时分开设。很多 MCP 工具默认没有超时，会无限挂起。

### 3. 熔断与降级

同一上游连续失败 N 次（比如 5 次）就熔断：冷却期内直接快速失败，不让每个请求去探测一个已死的服务；冷却后半开探测，恢复后自动闭合。熔断期间 Agent 走降级路径：备用数据源 → 过期缓存 → 跳过可选步骤 → 带着失败清单优雅终止。

### 4. 预算与可观测

给整个任务设总时限和 token 预算，循环每一轮检查剩余额度。每次工具调用记录 trace、错误类别、耗时。失败要进最终报告——明确告诉用户哪一步失败了、跳过了什么，而不是假装成功。

## 踩坑点

- 让模型在循环里"自己决定重试几次"：成本不可控、行为不稳定，重试永远放代码里；
- 对非幂等接口重试：重复订单、重复消息，这类事故在社区里隔三差五就能见到；
- 只设了连接超时没设读取超时，上游 hang 住照样拖死整个 Agent；
- 降级用了过期缓存却不标注数据时间，用户把三小时前的数据当实时数据用；
- 为了"用户体验"吞掉错误详情，排查时两眼一抹黑——对用户友好和对日志诚实并不冲突。

## 可复用建议

- 做一个统一的 resilient client：超时 + 重试 + 熔断 + 结构化错误，所有外部调用都过这一层；
- 给工具结果定义错误契约（`error_type` / `retryable` / `hint`），写进 MCP 工具的接口约定里；
- 用 mock 主动制造故障，把失败路径完整跑一遍，比等线上事故便宜得多。

## 总结

错误恢复是基础设施问题，不是提示词工程问题。把超时、重试、熔断、降级压到代码层，给模型的是干净的结构化错误和有限的选项，把"放弃还是换路"的最终决策留给它。Agent 的可靠性不在于不出错，而在于出错之后的行为可预期、可解释、可收场。
