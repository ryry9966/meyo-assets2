## 背景

E2E 测试一直是最"吃人工"的一层：用例好写不好养，页面一改版选择器就崩，覆盖率往往止步于登录和下单两条主路径。过去一年，随着 Agent 框架和浏览器类 MCP 工具（如 Playwright MCP）成熟，"让 AI 实际操作页面、再把它做过的事翻译成测试代码"这条路线变得可行了。我在两个内部项目上跑通了这套流程，把经验整理出来。

## 问题

直接让 AI 写 E2E 测试，常见三种失败方式：

1. **凭空幻觉元素**：只给截图或需求文档，AI 会编造按钮文本和选择器，跑起来全红。
2. **一口气生成几十条用例**：看着覆盖很全，实际一半因为数据依赖互相污染。
3. **没有运行反馈**：AI 拿不到失败日志，修不动，最后还是人兜底。

核心矛盾在于：写测试需要的是"对页面真实结构的认知"，而这恰恰是纯语言模型缺失的。

## 做法

思路是把 Agent 当成一个"会自己点页面的初级测试工程师"：先探索，再确认，最后生成。

**第一步：接上浏览器 MCP。** 给 Agent 挂上 Playwright MCP 或等价的浏览器控制工具，让它能 navigate、click、snapshot。关键是用 accessibility snapshot 而不是截图——前者带真实的 role 和 name，是选择器的可靠来源。

**第二步：让 Agent 探索并产出"页面档案"。** 提示词只要求它走完目标路径，每一步记录 URL、关键元素的可访问性快照、建议断言点，产出存成 YAML 或 Markdown 放进仓库。这份档案是人和 AI 的共同语言。

**第三步：人工审档案，再生成代码。** 档案审过之后，让 Agent 按团队测试模板（我们用 Playwright + 固定的 page object 结构）填空式生成代码。注意是"按模板填空"，不是自由发挥。

**第四步：失败自动回喂。** CI 挂了之后，把 trace 和错误日志喂回 Agent，让它先给修改建议，人工确认后落盘。大部分选择器失效类问题能在这个循环里自愈。

## 踩坑点

- **别让 Agent 用 text 选择器**。多语言环境一跑就挂，模板里写死规则：只允许 `getByRole` / `getByTestId`。
- **测试数据必须显式注入**。AI 很爱用 `test-user-001` 这种"看起来存在"的账号，要求每个用例开头先创建自己的数据。
- **探索和生成要分开跑**。合成一步，Agent 会边点边写，档案质量明显下降。
- **限速生成**。一次只要一条用例，跑绿再要下一条，否则调试成本指数上升。

## 可复用建议

- 把"页面档案"当一级资产维护：它比测试代码更稳定，页面改版后重跑一次探索即可刷新。
- 失败回喂做成固定脚本，而不是临时复制粘贴日志，否则没人坚持得下去。
- 模板约束 > 提示词约束：能在 page object / fixture 层解决的问题，不要指望提示词管住模型。

## 总结

这套流程跑下来，两条主路径加六条分支用例，从零到 CI 常绿大约两个下午；之后版本迭代产生的选择器修复，多数由回喂循环消化。AI 并没有取代测试设计——路径规划和断言点仍然由人决定——但它接走了最枯燥的部分：点页面、抄选择器、修断言。对已有 Agent 基础设施的团队来说，接入成本主要集中在浏览器 MCP 配置和模板建设上，值得一试。欢迎在社区里交流你们各自的模板结构和回喂方案。
