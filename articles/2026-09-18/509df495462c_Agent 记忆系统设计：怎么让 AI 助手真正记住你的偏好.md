## 背景

跑过一段时间 Agent 自动化的人基本都遇到过：每次新会话，助手把上个月说过的偏好忘得一干二净——代码注释用什么语言、部署脚本放哪个目录、回复要不要带解释。上下文窗口再大，跨会话照样归零。所谓"记忆"，本质是个工程问题：提取、存储、检索、更新，四件事哪件做糙了都不行。

## 问题

常见的两种失败做法：一是把历史记录全塞进 system prompt，几轮之后 prompt 膨胀到不可用，关键偏好被噪声淹没；二是完全依赖会话内记忆，重启即失忆。真正难的是三个问题：什么信息值得记？记成什么结构？怎么在正确时机取出来、过期的怎么处理？

## 做法：分层 + 结构化

**1. 分层。** 工作记忆（当前会话）、情景记忆（会话摘要日志）、语义记忆（结构化事实与偏好）、程序记忆（固化成配置或 skill）。“记住偏好”这个需求，核心是语义记忆这一层。

**2. 定义条目结构，别存自由文本。** 建议形如 `{key, value, scope, source, confidence, updated_at}`。`source` 区分 explicit（用户明说）和 inferred（模型推断），explicit 永远优先。比如"我在写 Rust”是临时事实，“注释用中文”才是偏好——抽取时要能区分这两者。

**3. 提取。** 会话结束时（或每 N 轮）用小模型跑一次抽取，prompt 里明确限定：只记稳定偏好，忽略一次性上下文，判断时效性。

**4. 存储。** 本地 SQLite 起步就够。偏好类记忆通常几百条以内，key 精确匹配 + scope 过滤比向量检索更可靠；等确有模糊检索需求再上 embedding，别一上来就堆技术栈。

**5. 检索注入。** 组装 prompt 时按 scope（全局/项目级）+ 相关性 + 新鲜度排序，设 token 预算（比如 500 封顶）。在 OpenClaw 里建议把记忆做成独立 MCP server，只暴露 `memory_search` / `memory_write` / `memory_delete` 三个工具，天然获得可审计性。

**6. 更新与失效。** 冲突时新值覆盖旧值但保留历史；给 inferred 记忆加降权或 TTL，超龄记忆提示用户确认。

## 踩坑点

- **一次性上下文被固成长期偏好。** 用户说“这周别打扰我”，被记成永久规则。解法：抽取时强制判断时效；inferred 记忆要求出现两次以上才固化。
- **记忆投毒。** 测试语句、玩笑话混进记忆库。source 标记 + 用户可查看可删除是底线，否则出了怪行为根本查不到来源。
- **注入过多反而劣化。** 实测塞 50 条记忆不如 8 条相关的——超出预算后助手会开始忽略核心偏好，宁可少注。
- **只靠相似度检索。** 否定式约束（“回复不要用 emoji"）用 embedding 很容易漏，这类规则应走结构化 key 直接命中。

## 可复用建议

- explicit 与 inferred 分开存、分开注入，信任级别不同。
- 做一个 debug 命令，打印“本次会话注入了哪些记忆、为什么”，排障效率天壤之别。
- 准备一组回归用例：改偏好→新会话验证生效；只说一次的反话→验证没被固化。
- 本地优先，偏好数据别默认上云。

## 总结

记忆系统不是“多存点东西”，而是提取标准、存储结构、检索预算、失效机制四件事的组合。先用最土的 SQLite + 结构化条目跑通闭环，再按真实痛点决定要不要上向量检索。能被用户查看、纠正、删除的记忆，才是真正可用的记忆。
