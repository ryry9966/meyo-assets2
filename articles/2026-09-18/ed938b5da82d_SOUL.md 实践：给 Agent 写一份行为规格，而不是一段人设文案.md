## 背景

OpenClaw 里每个 Agent 启动时会加载一份 SOUL.md，它和 AGENTS.md 的分工很明确：AGENTS.md 管这个 Agent 会做什么，SOUL.md 管它是什么样、什么不做。听起来像玄学，实际上它是注入 system prompt 的高优先级上下文，直接决定模型在模糊场景下的默认倾向——而自动化场景里，模糊场景恰恰是最多的。

## 问题

我最早没写 SOUL.md，跑了一个月后遇到三类问题：

1. **人格漂移**。长会话里语气越来越随意，凌晨的 heartbeat 消息像喝多了的群友，白天帮我回工作邮件也是这个味儿。
2. **边界靠临场发挥**。让它"清理一下下载目录"，它对"清理"的尺度判断每次不一样，有一次差点把还没归档的发票删了。
3. **行为打架**。SOUL.md 写了"永远不主动发消息"，MCP 插件的调度逻辑却要求定时汇报，模型开始随机挑一个执行。

共性是：我把人格当文案写，而不是当约束写。

## 做法

重写时按四段结构，控制在 40 行以内：

```markdown
# Identity
一句话说清角色和语气基调，例如：
冷静、简短、工程口吻，不说客套话。

# Boundaries
硬规则，用"不要 + 具体行为"描述：
- 不要删除白名单目录之外的任何文件
- 涉及花钱、对外发送、改生产配置时，先停下问我
- 不要替我做出承诺性回复

# Style
可观察的表达规则：
- 回复默认 3 段以内
- 不确定时明说"我不确定"，不要编

# Escalation
必须升级给人的情况：金额、不可逆操作、新工具首次调用。
```

关键变化三条：第一，把形容词换成可判定行为，"专业"没用，"不超过 3 段"才有用；第二，边界写成白名单/黑名单，不写意愿表达；第三，显式声明自动化例外——heartbeat 和 cron 汇报属于"我授权的行为"，写进文件，避免模型自己裁决。

## 踩坑点

- **写太长**。第一版 200 行，token 成本翻倍，规则互相稀释，谁都不严格执行。实测 40 行左右比较稳。
- **职责混了**。把"部署前跑 lint"这种操作流程写进 SOUL.md，结果它有时执行、有时当成"性格"理解。操作归 AGENTS.md，倾向归 SOUL.md。
- **只写正面约束**。"要谨慎"没有约束力，模型对"不要做 X + 接近 X 就问我"的遵守率明显更高。
- **写完不测**。人格文件也要回归用例：我固定拿 5 个边界场景（删文件、花钱请求、陌生插件调用）做测例，改一次跑一遍。

## 可复用建议

- 用 git 管 SOUL.md，每次调整一个 commit，出问题能 diff 回滚。
- 边界规则和 MCP 工具清单对齐：每加一个有副作用的工具，检查 SOUL.md 是否覆盖它。
- 团队共用 Agent 用"共享模板 + 个人 override"两层结构，避免各写一套。

## 总结

SOUL.md 不是人设营销文案，是一份给模型的行为规格。核心动作三个：把形容词翻译成可判定规则，把"不做的事"写成硬边界，把自动化例外显式声明。40 行以内，进 git，配测例——这比任何"调教技巧"都可靠。
