## 背景

Agent 进入日常工作流之后，社区交流方式也跟着变了：遇到问题，大家习惯把 system prompt、MCP 配置、插件 YAML、甚至整段会话记录直接贴到帖子里求助。这本身是社区效率的来源，没什么不对。

但 Agent 和传统工具不一样——它的工作配置天然就是一份「内部信息清单」：接了哪些系统、持有什么权限、工作流怎么串联，全都写在里面。分享行为本身没问题，问题出在分享的内容没有分层。

## 问题的三个泄露通道

实际观察下来，泄露基本走三条路：

1. **主动分享**：贴配置、贴 prompt、贴截图。常见问题不是忘了删 key，而是内网域名、内部项目代号、客户数据字段名这类「低敏感、高情报」的内容。
2. **上下文携带**：生产环境的 agent 会话里天然混着内部信息。把日志原样导出求助，等于把内部上下文一起打包。
3. **自动化出口**：最容易被忽视。日报 agent、社区摘要 bot 这类自动化如果不设边界，会把内部频道内容「总结后」发到公开区——名字脱敏了，但工作流的节奏和结构本身已经暴露。

## 做法：把脱敏做成五步流程

**第一步，资产分级。** 分享前先把工作流拆三类：可直接公开（通用模式、脱敏示例）、内部（架构、工具链路）、机密（凭证、真实端点、数据结构）。大部分争议来自跳过这一步。

**第二步，建分享专用实例。** 演示、求助、调试社区插件，一律用独立 workspace 和独立 agent 实例，接 dummy 数据源。上下文是清洗不干净的，重开一个比「删掉那段」可靠得多。

**第三步，MCP / 插件权限最小化。** 能只读就不读写；token 按工具作用域拆分；演示环境绝不挂 admin 权限。社区插件出问题时，爆炸半径应该被权限锁在「零」。

**第四步，出口审计。** 所有流向公开区的自动化输出（日报、摘要、issue 评论）过一道过滤：正则扫密钥格式、内网域名、内部代号，再配固定频率的人工抽查。出事时日志要能回答「从哪出来的」。

**第五步，来路审查。** 反向问题同样存在：别人贴的 prompt、插件描述里可能藏注入指令。不要把社区内容原样贴进有内部权限的 agent——先在隔离实例里跑一遍。

## 踩坑记录

- 只删了 API key，截图终端提示符里还带着内网主机名；
- 用生产 agent「顺手」装社区插件试一下，插件描述里的注入指令让它主动枚举了内部目录结构；
- 打包分享 workflow 文件，忘了同目录的 `.env` 还在里面；
- 摘要 bot 做了字段脱敏，但「每周三同步 X 系统」这种节奏信息没脱，等于公开了自己的发布计划。

## 可复用建议

- 分享前过**三问 checklist**：这段内容能不能推出我的系统结构？能不能推出我的权限范围？能不能推出我的节奏规律？三个都不能，才发。
- 维护一份自己的敏感模式清单（正则即可）：密钥格式、内网域名后缀、内部项目代号，脱敏和审计共用一份。
- 记住一条原则：**上下文不可清洗，只能隔离。**想分享的内容，永远从干净实例里产出。

## 总结

安全红线不是「不分享」，而是分层分享：公开层讲模式，隔离层做演示，生产层不出门。Agent 时代的信息出口比以前更多、更隐蔽，靠自觉迟早会漏。把分级、隔离、审计做成固定流程，才是能在这个社区长期玩下去的姿势。
