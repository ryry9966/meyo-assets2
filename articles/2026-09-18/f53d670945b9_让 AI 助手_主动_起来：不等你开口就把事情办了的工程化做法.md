## 背景

我们日常用的助手几乎都是"反应式"的：你不发消息，它就永远安静。但很多真实的自动化需求是长在时间和事件上的——CI 挂了、收件箱堆积了、磁盘快满了，这些事不会等你开口。

在 OpenClaw 生态里，通过 MCP 挂工具、用插件接外部系统已经很成熟，缺的往往反而是"触发侧"：Agent 有手，但没有闹钟。这篇帖子记录一套给 Agent 补上时间和事件感知的轻量做法。

## 问题

让主动性可用，要先回答三个问题：

1. **谁来触发？** 用什么机制在定时或事件发生时唤醒 Agent。
2. **什么时候该开口、什么时候该忍住？** 没有决策策略，要么沉默，要么变成通知轰炸。
3. **开口之后能做什么？** 一个主动型 Agent 手握全部权限，是事故制造机。

## 做法

**第一步：搭触发层。** 两类来源：定时心跳（cron，比如每 30 分钟做一次全量检查）和事件钩子（webhook、文件变更、消息队列）。触发层只做一件事：把"发生了什么、详情在哪"的最小上下文打包进唤醒 payload，不要把大段原始数据塞给模型。

**第二步：先过滤，再推理。** 唤醒后不要直接调主模型。先用纯代码或小模型跑一层规则：阈值检查、白名单检查、去重检查。通过了才进入 Agent 推理。这是成本和稳定性的生命线。

**第三步：决策输出结构化。** Agent 每次唤醒的结论只能是三选一：`act`（执行一个预先授权的动作）、`defer`（攒进 digest，等下次汇总）、`noop`（什么都不做）。每次决策落一条日志，记录触发源、理由摘要、执行结果。

**第四步：权限边界。** 发外部消息、建 PR、删文件这类不可逆动作，走"提案待确认"流程；可逆且低风险的动作放白名单直接放行。主动唤醒时可调用的工具集，应该显式小于交互会话。

**第五步：去重与冷却。** 按（事件源，实体，动作类型）三元组做去重；同类事件重复出现就提高阈值或进入冷却期。"已提醒过"的状态要持久化到长期记忆，不要依赖会话上下文。

## 踩坑点

- **自触发循环。** Agent 的动作触发了 webhook，webhook 又唤醒 Agent。解法：给事件源打标，自己触发的直接丢弃。排查循环问题时第一个看这里。
- **越主动越烦人。** 频率不控制，用户一周内就会把整套东西关掉。设每日主动动作配额，低于阈值的统统进 digest。
- **唤醒后记忆过期。** 带着旧会话缓存醒来，基于过期状态做动作，错得非常离谱。每次唤醒强制重载关键状态。
- **心跳成本。** 心跳全天跑大模型，账单会很诚实。过滤层 + 分级模型不是可选项。
- **时区与休眠时段。** 调度参数要显式配置，否则深夜的消息轰炸会替你收获投诉。

## 可复用建议

- 把触发器定义成声明式三元组：**条件、动作、预算**。三者缺一就不要上线。
- 一条原则贯穿始终：**不可逆的操作，必须有人确认**。
- 主动行为必须可审计，每条日志能回溯到触发源和当时的理由。
- 新场景先用 digest 模式（每天一条汇总），观察误报率后再升级到实时通知。

## 总结

主动性不是能力问题，是纪律问题。工程上的难点从来不是"让 Agent 动起来"，而是"让它知道什么时候不该动"。可靠的触发层、便宜的过滤层、严格的权限边界、畅通的审计日志——这四件事做扎实，你得到的是一个在关键时刻开口的助手，而不是一个 24 小时骚扰你的闹钟。
