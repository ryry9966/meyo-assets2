## 背景

OpenClaw 这类常驻 agent 有个朴素的需求：不等用户开口，也能在合适的时机自己动一动。社区里最常见的实现就是 heartbeat——每隔 N 分钟醒一次，检查任务清单（比如 HEARTBEAT.md），有事就干，没事接着睡。但跑一段时间就会发现，触发这件事还有另一条路：外部系统直接推事件过来（webhook、消息回调）。两种方式各有代价，值得认真取舍。

## 问题

纯轮询的痛点很具体：

- 每次心跳都可能唤醒一次模型调用，没事干也在烧 token；
- 最坏延迟等于间隔，30 分钟的心跳意味着事件最多等 30 分钟才被处理；
- 心跳太频繁，agent 会开始"找活干"，主动发一些没人要的消息。

纯推送也不是免费午餐：

- webhook 需要公网可达的入口、鉴权和重试语义；
- 事件源不支持推送（本地文件、部分 API）时还是得轮询；
- 事件风暴时每次触发都跑模型，成本会失控。

## 做法

我现在的分层方案：

1. **事件分类**。把触发源列一张表：延迟敏感吗？支持推送吗？频率多高？日历提醒、CI 失败这类走推送；本地文件监控、无 webhook 能力的服务留给心跳兜底。

2. **心跳加"廉价预检"**。心跳处理器先跑一段确定性脚本（读文件、查 MCP 工具状态），无信号直接退出，不进模型。只有预检命中，才拼 prompt 唤醒 agent。这一步是省 token 的关键。

3. **推送走队列**。webhook 入口只做鉴权和快速 ack，事件进队列，由 worker 消费后再拉起 agent。带去重键和最小触发间隔，避免同一事件重试三次就跑三遍。

4. **冷却与合并**。agent 两次激活之间设最小冷却时间；同类事件在窗口内合并成一次。实践中 5 分钟冷却加事件合并，能消掉大部分噪音。

5. **记录每次决策**。每次心跳/推送都记一行：为什么醒、为什么跳过、花了多少 token。调参全靠这份数据，不靠感觉。

## 踩坑点

- webhook handler 里同步干重活，上游超时重试导致重复执行；务必快速 ack、异步处理、加幂等键。
- 机器夜间休眠，早上一醒来心跳积压连跑十几次；补跑策略要定成"只补一次"。
- 推送事件撞上进行中的会话，出现并发冲突；按会话串行化或直接排队。
- 心跳间隔写死不分时段，半夜也在跑；加上活跃时段配置能省不少。

## 可复用建议

- 推送做主路径，心跳做兜底，两者不互斥；
- "先廉价检查，后模型调用"是通用原则，写插件和接 MCP 工具时同样适用；
- 触发卫生三件套：去重、冷却、合并；
- 心跳参数显式化：间隔、活跃时段、单次心跳最多执行的动作数，别散落在代码里。

## 总结

heartbeat 不是落后的设计，它是确定性最强的兜底层。推送解决了已知事件源的延迟和成本问题，但引入了入口暴露、队列和幂等这些基础设施成本。对大多数个人部署来说，"推送管外部事件 + 低频心跳兜底 + 预检门槛"的组合，比押注任何单一机制都稳。先跑起来记录数据，再按实际触发分布去调，比一开始就追求"完美架构"务实得多。
