## 背景

OpenClaw 里的 agent 默认是被动的：有消息进来才跑。但自动化场景做深之后，你迟早会碰到"主动性"需求——定时巡检服务器、盯一个数据源、到点提醒。社区目前的原生方案是 heartbeat：按固定间隔（默认 30 分钟）给 agent 发一条轻量 prompt，agent 读完 HEARTBEAT.md 决定要不要说话。这本质上是轮询。

## 问题

轮询的代价很直白：每次心跳都是一次真实的模型调用。哪怕 agent 最终回一句 HEARTBEAT_OK 短路掉，token 和排队成本都在发生。而推送（webhook / 事件驱动）看似省 token，工程成本却不低：需要常驻可达的入口，gateway 跑在家里的同学还要处理 NAT、证书和鉴权。两条路都不免费，取舍的锚点是三个变量：事件有多紧急、来源有多可靠、你愿意为实时性付多少固定成本。

## 我的做法

分两层，不要二选一：

1. **低紧急、周期性的**走 heartbeat 轮询。写一份克制的 HEARTBEAT.md，明确约定"无事返回 HEARTBEAT_OK，不要执行任何额外动作"。间隔调到业务能容忍的下限，我的巡检类任务设 60 分钟。
2. **高紧急、来源明确的**走推送。CI 失败、告警类事件直接 POST 到 gateway 的 webhook，由插件转成普通消息注入会话，跳过心跳等待。
3. 推送端做去重和节流：同一来源 5 分钟内合并，避免告警风暴把会话刷穿。
4. 心跳与活跃会话互斥：检测到 session 正在跑长任务就跳过本轮，避免两条执行流互相踩。

## 踩坑点

- 早期 HEARTBEAT.md 写得太宽泛，agent 每次心跳都"顺手"扫一遍日志并生成总结，一晚上烧掉的 token 是平时三倍。现在第一行就是硬约束：无事不许输出、不许调工具。
- 心跳默认走主会话。如果主会话正被手动占用，心跳结果会挤进上下文，污染对话。多 agent 路由可以隔离，但注意每个 agent 是独立计费的。
- webhook 的失败重试要设上限。曾经一个配置错误的告警源每 30 秒重推一次，叠加无限重试，差点把队列打满。
- 容器里跑定时心跳注意时钟语义：重启后第一次心跳可能立即触发，逻辑务必做成幂等。

## 可复用建议

- 判断标准就一条：**事件价值随时间衰减快的用推送，衰减慢的用轮询**。
- 心跳 prompt 必须可短路，返回值约定成固定 token（如 HEARTBEAT_OK），并在日志里记录每次决策，事后可审计 token 消耗。
- 推送入口一律过鉴权和限流，哪怕只暴露在内网。
- 宁可心跳间隔长一点，也别让 agent 在无事时"找事做"。

## 总结

轮询和推送不是对立的架构选型，而是按事件特征分配的路由策略。OpenClaw 的 heartbeat 机制提供了一个便宜的兜底，推送通道负责补上实时性短板。先跑通轮询、量化 token 成本，再对真正需要秒级响应的来源上推送——这是我实践下来最不容易返工的顺序。欢迎在评论区贴你们的心跳间隔和 HEARTBEAT.md 写法。
