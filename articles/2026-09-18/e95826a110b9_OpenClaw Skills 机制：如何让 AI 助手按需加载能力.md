## 背景

在典型的 Agent 架构里，能力通常以两种形式存在：写死在系统提示里的说明，以及启动时一次性注册的工具（比如一组 MCP server 暴露的 tools）。能力少的时候没什么问题，但当你把十几个 MCP server、几十个自定义脚本都挂上去之后，代价就开始显形了。

## 问题

- **上下文成本**：所有工具的 schema 常驻上下文，而绝大多数会话只用到其中两三个；
- **选择干扰**：工具越多，模型选错工具、绕远路的概率明显上升；
- **维护困难**：能力定义散落在提示词、配置、脚本各处，改一处怕崩全局。

OpenClaw 的 Skills 机制针对的就是这个问题：把"能力"收敛成一个可独立分发的小包。每个 Skill 是一个目录，核心是 `SKILL.md`——只有 name 和 description 会进入主上下文，正文和附带的脚本、参考文件在需要时才被读取。本质上就是渐进式披露（progressive disclosure）。

## 做法

1. **划分粒度**：一个 Skill 对应一个能一句话说清的场景，例如"汇总月度账单 CSV"、"生成周报草稿"。不要把整个领域塞进一个 Skill。
2. **打磨元数据**：name 保持简短；description 写"什么时候该用"，用用户真实的提问措辞来写，这是路由能否命中的关键。
3. **正文控制在一屏内**：写清步骤、约束、输出格式。超过一屏就拆分，或把细节外置成参考文件。
4. **确定性逻辑落成脚本**：Skill 目录里可以带可执行文件，让模型去调用，而不是每次靠"复述流程"还原结果。
5. **验证触发**：准备十条左右的测试问法（包含应触发和不应触发的各一半），做回归验证。

## 踩坑点

- **description 写成功能介绍**而不是触发条件，结果是永远不被选中；反过来写得太宽泛，又会在不相关的会话里反复抢占。
- **Skill 嵌套 Skill** 容易链式调用失控，建议控制在一层以内。
- **脚本依赖本机环境**（绝对路径、特定 Python 版本），换台机器就哑火。依赖要写明，路径尽量用相对路径。
- **安全**：Skill 正文本质是注入给模型的指令。第三方 Skill 要当作不可信输入来审，不要默认授予免确认的执行权限。
- **僵尸 Skill**：重构工具后忘了更新 Skill 里的引用，留下一堆指向失效命令的包。

## 可复用建议

- 把 description 当作检索 key 来打磨，而不是文档摘要；
- 元数据预算要算账：几十个 Skill 的 description 本身就是上下文开销，定期清理低频 Skill；
- Skill 进 git，走和代码一样的 review 流程，改动可追溯；
- 在正文开头注明它依赖的工具和命令版本，降低环境漂移带来的隐性故障。

## 总结

Skills 不是要替代 MCP 或插件，而是把"什么时候需要什么知识"从常驻变成按需。对个人助手场景，一个务实的起点是：把你最常复制粘贴的三段提示词迁移成 Skill，先感受触发机制是否可靠，再逐步收敛其余能力。小步验证，比一次性重构几十个包靠谱得多。
