## 背景

团队日常会产生大量原始日志：CI 构建记录、错误告警、Agent 任务执行日志、插件调用统计……以前日报靠人工翻日志拼凑，每天花 20–30 分钟，还经常漏掉关键事件。这篇帖记录我们把这件事流水线化的过程，思路可以迁移到任何"原始数据 → 定时摘要"的场景。

## 问题

人工日报有三个结构性缺陷：

1. **信息密度低**。日志按时间流式写入，日报却要按主题组织，人工搬运等于做了一遍无标准的 ETL。
2. **不可复现**。同一天的日志，两个人写出的重点完全不同，事后无法追溯"当时为什么没报这个"。
3. **不可扩展**。日志源一多（超过 3 个系统），人工就开始稳定漏报。

## 做法

流水线分五步，跑在一个定时触发的 OpenClaw Agent 上，工具通过 MCP 暴露：

**第 1 步：采集与归一化。** 各日志源先经过一个轻量 normalize 脚本（不让 LLM 干这个），统一成 `{ts, source, level, event_type, payload}` 的 JSON Lines，落到当日分区目录。

**第 2 步：规则预聚合。** 用确定性代码先算死数据：错误总数、Top N 报错类型、任务成功率、耗时分布。输出是纯数字表，直接可校验。

**第 3 步：LLM 摘要。** 把归一化日志 + 预聚合表喂给 Agent，要求按固定 schema 输出：`概述 / 异常事件 / 趋势变化 / 建议关注项`。Prompt 里明确"数字只能引用预聚合表中的值，不得自行计算"。

**第 4 步：校验层。** 独立脚本对 LLM 输出做断言：数字能否回溯到预聚合表、schema 是否完整、时间范围是否正确。失败重跑一次，仍失败则降级为"纯规则版日报"。

**第 5 步：投递与留档。** 成品通过 MCP 工具推到群机器人，同时把原始日志、预聚合表、LLM 原始输出、最终报告四样按日期归档，形成完整证据链。

## 踩坑点

- **别让 LLM 算数。** 早期直接丢原始日志让它总结，错误计数偶尔对不上。所有数字必须由代码先算好，LLM 只做组织和解释。
- **时区错位。** 日志源分布在 UTC 和本地时区，"今天"的边界一度差了 8 小时，跨天事件被重复统计。统一在采集层转成带时区的 ISO8601。
- **格式漂移。** 上游改了一个字段名，流水线静默产出三天空报告才被发现。后来在 normalize 脚本里加了字段断言，解析失败直接告警，而不是输出空结果。
- **重试幂等。** 投递失败重试时发过重复报告。现在每份报告带当日日期作幂等键，投递端去重。

## 可复用建议

1. **Schema 先行**：先定义日报输出结构，再倒推流水线，比从日志顺推更稳。
2. **确定性优先**：能用代码算的绝不让模型算，模型只负责"人话翻译"和归因推测。
3. **保留中间产物**：原始日志、聚合表、LLM 原始输出分开存，出问题能定位到具体层。
4. **留降级路径**：LLM 环节挂了，规则版日报也能发，有比没有强。
5. **Prompt 当代码管**：进版本库，改动写明动机，方便复盘"那天的报告口径为什么变了"。

## 总结

上线后，日报耗时从每天 20 多分钟降到接近零，更重要的是输出变得可复现、可追溯。核心经验一句话：**LLM 适合做摘要和组织，不适合做统计和计算**。确定性的事交给代码，解释性的事交给模型，中间用校验层兜底——自动化才敢真的放手。
