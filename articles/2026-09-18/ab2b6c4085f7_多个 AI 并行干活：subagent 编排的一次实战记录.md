## 背景

单 agent 串行干活的问题很直接：任务一大，上下文塞满，主循环被工具调用拖慢，一个环节失败整条流程停摆。最近我们把一次「全仓库文档重构」任务改成了 subagent 编排：主 agent 只做拆解和汇总，扫描、起草、校对交给并行的子代理，总耗时从两小时压到二十分钟左右。这篇记录做法和踩过的坑。

## 问题

最初的版本是主 agent 一个人包办：读文件、分析、写文档、跑校验。上下文很快超预算，模型开始遗忘前文的约定，输出风格漂移。更麻烦的是串行——任何一个 MCP 工具慢，整条流水线就跟着慢。我们缺的不是更聪明的模型，而是更合理的分工。

## 做法

结构上是一个主 agent 加若干子代理：

1. **拆解**：主 agent 把任务切成互不重叠的子任务，按目录或模块分区，明确每个子任务的输入文件范围。
2. **派发**：通过自定义工具（内部起一个新的 agent 会话）派发子任务。每个子代理拿到一份**自包含**的 prompt：目标、范围、允许用的工具、输出格式、禁止事项。
3. **并行控制**：用信号量把并发压在 3~4。子代理分两类——只读的（扫描、分析）放开并发；会写文件的收紧到 1~2，且按目录隔离。
4. **汇总**：每个子代理返回结构化结果（状态、改动文件列表、摘要、遗留问题），主 agent 只消费汇总做校对整合，不把原始日志塞回上下文。

## 踩坑点

- **子代理 prompt 不自包含**。写过一句「按上面的要求处理剩余模块」，子代理根本看不到「上面的要求」，输出全废。现在每个子任务 prompt 都是完整独立的。
- **并行写冲突**。两个子代理同时改同一个索引文件，直接冲突。改成写操作按目录分区，共享文件由主 agent 统一收口。
- **汇总爆上下文**。让子代理返回原始日志，三轮就把主 agent 打爆。改成强制结构化摘要，超长截断。
- **限流和成本**。并发开到 8，很快触发 API 限流，重试又放大请求量。并发上限和每个子代理的 token 预算都要设。
- **静默失败**。一个子代理超时被吞掉，汇总看着完整，实际少了一个模块。必须显式上报失败状态，由主 agent 决定重试还是降级。

## 可复用建议

- **优先只读并行**：扫描、分析类任务最安全，先在这里拿到收益。
- **子代理 prompt 模板固定五个字段**：目标、范围、工具、输出格式、禁止事项。
- **写操作要么分区，要么串行收口**，不要赌模型不会撞车。
- **每个子代理留独立 trace 日志**，编排出问题能定位到具体分支。
- **先跑通单个子代理，再开并行**。直接上并行等于同时调试 N 个东西。

## 总结

Subagent 编排的本质不是「更多 AI」，而是把上下文隔离和任务并行当成工程问题来解：拆解要干净、通信要结构化、并发要有闸门、失败要可见。收益明显，但前提是纪律。建议从只读任务开始小规模验证，再逐步放开会写文件的子代理。
