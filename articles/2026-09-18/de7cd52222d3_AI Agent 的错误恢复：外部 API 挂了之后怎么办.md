## 背景

Agent 的能力边界，基本等于它能调到的外部 API：LLM 供应商、搜索、数据库、各类 MCP server。而这些依赖没有任何一个承诺 100% 可用。跑一次长任务，五次工具调用里挂一次，是常态而不是意外。所以错误恢复不是锦上添花的健壮性，而是 Agent 能不能上生产的前提条件。

## 问题：Agent 的故障处理和普通服务不一样

普通服务的重试逻辑写在代码里，行为可预测。Agent 场景多了两个特殊之处：

1. **模型会"脑补"恢复。** 工具调用失败后，如果把原始报错或空结果直接丢回给模型，它很可能编一个看起来合理的结果继续往下走。这不是恢复，是污染下游。
2. **让模型自己决定重试很危险。** LLM 在循环里"再试一次"，往往变成无退避的密集重试——本来只是限流，硬生生打成封禁。

另外还有工程侧的老问题：多步任务做到第三步挂了，状态怎么办？写操作重试会不会重复执行？

## 做法

**第一步：错误分类，结构化返回。** 给每个工具调用包一层，返回统一信封 `{ok, error_code, retryable, data}`。429 / 5xx / 超时标记为可重试，4xx、鉴权失败、配额用尽标记为不可重试。给模型的是枚举和布尔值，不是原始堆栈。

**第二步：重试放在代码层，不给模型自由裁量。** 指数退避加抖动，最多 3 次，尊重 `Retry-After`。模型只做策略决策——跳过、降级、换工具、问人——不负责"什么时候再试"。

**第三步：给每个工具预定义降级路径。** 常见三种：读上次成功的缓存（带 TTL）、切备用供应商、返回明确的"该工具不可用"占位结果，让规划层绕路。实在没有降级路径的工具，至少要做到快速失败。

**第四步：检查点 + 幂等。** 每步产出落盘，恢复时从断点继续，而不是从头跑；所有写操作带幂等键，保证重试不会重复发通知、重复下单。

**第五步：熔断。** 同一工具连续失败 N 次就打开熔断器，冷却窗口内直接快速失败，别再烧 token 去撞墙。

## 踩坑点

- **重试不加抖动**：多个 Agent 实例同时恢复，整齐划一地打到刚喘过气的上游，二次雪崩。
- **对非幂等 POST 重试**：重复 webhook 是这类系统最常见的事故来源。
- **超时拍脑袋**：设太长阻塞整个循环，设太短误杀慢但正常的 API，按工具分别配。
- **降级缓存没设 TTL**：三天前的搜索结果被当成新鲜数据用。
- **吞掉错误返回空字符串**：模型会把空结果理解成"成功了，只是没数据"。

## 可复用建议

- 统一工具信封 + 按工具的错误策略配置（超时 / 次数 / 退避 / 降级），一份 YAML 管住所有工具。
- 上线前用一个故意不稳定的 mock server 把故障路径跑一遍，别只测 happy path。
- 记录每次工具调用的成败和错误码，没有这些数据，你不知道哪个工具在拖后腿。
- 给模型准备一段固定的"降级话术"模板，明确告诉用户哪些步骤没完成——比编造一个完整结果可信得多。

## 总结

错误恢复是系统工程问题，不是 prompt 问题。原则一句话：**边界管重试，模型管策略，检查点管续跑，幂等管安全，诚实管信任。** 外部 API 一定会挂，Agent 的价值在于挂了之后还能给出一个明确、可追溯的"部分完成"，而不是一个看起来完整的谎言。
