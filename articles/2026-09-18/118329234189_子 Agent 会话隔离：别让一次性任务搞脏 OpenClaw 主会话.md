## 背景

OpenClaw 的 gateway 会为每条对话维护独立 session，而主会话（你日常聊的那个）是状态最重的地方：系统提示、注入的记忆文件、全部工具输出都堆在同一条历史里。子 agent（通过 `sessions_spawn` 拉起的独立 session）本该是“干完活、交结论就走”的临时工，但很多人没真正把它用在刀刃上。

## 问题

最常见的反模式是让主 agent 直接跑重活：批量读文件、逐页翻网页、长链路排障。所有中间产物都写进主会话历史，token 成本一路涨，关键指令被稀释，压缩（compaction）之后细节还会丢。我们有个自动化日报任务，主会话被一次探索式抓取塞进几十万 token，之后一整周模型都在“走神”，直到手动重置才恢复。

## 做法

核心原则：**主会话只做调度和状态持有，重活全部 spawn 给子 agent。**

1. spawn 时给自包含任务书：目标、边界、可用工具、返回格式。别指望子 agent 能看到主会话上下文——默认看不到，这是特性不是 bug。
2. 约定回传契约：只回结论（比如不超过 300 字的要点 + 明细文件路径），过程数据落盘不回传。
3. 给子 agent 独立 workspace 子目录，限制可写路径，明确禁止直接回复用户渠道。
4. 设超时和轮次上限，任务结束顺手清掉子 session，避免僵尸会话。

任务书模板大意：

```
目标：…（一句话说清）
边界：只读 data/inbox/，可写 work/<task-id>/
禁止：调用 message 工具，不修改 memory/
返回：≤300 字要点 + 明细文件路径
```

## 踩坑点

- **污染不止 session 一个面。** 子 agent 往共享 memory 目录写东西，会直接改掉主 agent 的“人格”和长期记忆——这种脏连重置会话都救不回来。
- 任务书不自包含，子 agent 只能乱猜，产出比不隔离还脏。
- 两次任务误用同一个 session key，上下文串台。
- 子 agent 拿着 message 工具直接给用户发消息，渠道里全是噪音。
- 并行 spawn 抢同一批文件，记得每任务一个子目录。

## 可复用建议

- 把“调度纪律”写进系统提示词：主会话遇到超过 N 步的任务必须 spawn，不许自己埋头跑。
- 大输出一律落盘，回传路径 + 摘要；需要人看再单独推送。
- 长期记忆收敛到 memory 文件，定期重置主会话，别把会话历史当数据库用。
- 排障时先查子 agent 的写路径和 session key，再看模型行为——十次里八次是隔离没做干净。

## 总结

一句话：**主会话是控制面，子 agent 是数据面。** 隔离的要义不是“分开跑”，而是只回传结论、不回传过程，并把 session、磁盘写路径、消息渠道三个面一起管住。做到这三点，长任务再多，主会话也能保持干净。
