## 背景

我平时维护几条自动化流程：定时抓数据、整理归档、调 MCP 工具干活。之前全部走云端 API，问题很明显——私有数据要出网、token 账单随任务量线性涨、内网断外网就全停。于是决定把其中“够用就好”的部分迁到本地模型。

硬件环境：一台 8G 显存的 RTX 4060 台式机，一台 16G 统一内存的 M2 MacBook。两台都跑通了 7B–14B 级别模型接入 Agent 流程，过程记录如下。

## 问题

本地把模型跑起来不难，难的是让它当“Agent 的大脑”。实际遇到三个坎：

1. **显存/内存预算**：模型权重和 KV cache 都吃显存，上下文一长就 OOM；
2. **工具调用质量**：小模型的 function calling 远不如云端旗舰稳定，参数编造、格式跑偏很常见；
3. **静默失败**：上下文截断、模型被卸载这类问题，表面上看就是“Agent 逻辑抽风”，排查方向容易被带偏。

## 做法

**第一步：算账选模型。** 粗略估算，Q4 量化的显存占用 ≈ 参数量（B）× 0.6，再预留 KV cache。8G 显存跑 7B/8B 从容，14B 要压缩上下文；Mac 统一内存默认只有 65–70% 可分配给 GPU，按这个上限估。

**第二步：选运行时。** 图省事用 Ollama，自带 OpenAI 兼容接口；追求吞吐上 vLLM（N 卡）；要精细控制用 llama.cpp server。三者都暴露 `/v1/chat/completions`，无论 OpenClaw 还是其他 Agent 框架，接入侧只改 base_url。

```bash
ollama pull qwen2.5:14b-instruct-q4_K_M
ollama serve   # 默认监听 11434
```

**第三步：接进 Agent。** base_url 指向 `http://localhost:11434/v1`，api_key 随便填。先别上复杂流程，拿一个单工具的 MCP 插件做冒烟测试：连续跑 20 轮，确认模型能稳定吐出合法的工具参数。

**第四步：压测记录。** 记下 tokens/sec（4060 上 7B Q4 约 45 tok/s，M2 跑 14B 约 13 tok/s）、峰值显存、工具调用成功率。没有这组基线数据，后面换模型就是盲调。

## 踩坑点

- **上下文默认值太短。** Ollama 默认上下文只有 2K–4K（看版本），Agent 的系统提示加工具描述直接被截断，且不报错。必须显式设 `num_ctx`。
- **keep_alive 默认 5 分钟。** 闲置后模型卸载，下次调用重新加载几十秒，表现为“Agent 偶发卡死”。常驻场景把 keep_alive 设长。
- **显存碎片。** 浏览器开着占几百 MB，推理时就随机 OOM，报错位置还很迷惑。跑长任务前清场。
- **Q4 以下别碰。** Q3/Q2 的结构化 JSON 输出崩得厉害，宁可降一档参数量（14B Q4 → 7B Q5），也别压量化等级。
- **工具描述要瘦身。** 小模型的上下文是硬通货，把工具 schema 精简之后，编造参数的频率明显下降。

## 可复用建议

1. **用 OpenAI 兼容层做抽象。** 云端/本地只差一行 base_url，方便按任务路由：隐私、高频、简单任务走本地，长链路推理走云端。
2. **版本钉死。** 模型 tag 写全（如 `qwen2.5:14b-instruct-q4_K_M`），别用 latest，否则某次静默升级后 Agent 行为漂移，你根本查不出原因。
3. **把指标做成常规项。** tokens/sec 和工具调用成功率，每次换模型前后各测一轮，用数据说话。
4. **先 7B 后 14B。** 用最小模型先验证整条链路（运行时 → 接口 → 工具调用闭环），再上更大的，避免多个变量混在一起调。

## 总结

家用电脑跑 7B–14B 模型，在如今的软件生态下已经接近“装好即用”；真正的工作量在接入 Agent/MCP 链路之后——上下文预算、工具调用稳定性、静默失败的排查，这些才是踩坑集中区。本地模型不会替代云端，但作为自动化流程里常驻的廉价算力，把简单任务吃掉之后，账单和隐私两头的压力都会小很多。建议从一条最小流程开始验证，逐步迁。
