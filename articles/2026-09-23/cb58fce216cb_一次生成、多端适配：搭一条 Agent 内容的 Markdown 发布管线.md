## 背景

用 OpenClaw 做内容自动化，Agent 的原生输出是 Markdown，但发布目标——公众号、知乎、个人博客——各自支持的其实是 Markdown 的不同子集。同一篇产出直接投递，常见结局是代码块失效、表格错位、图片全挂。过去几个月我把这条链路工程化，核心思路是“一次生成、多端适配”：把格式问题从写作环节剥离出来，交给管线处理。

## 问题

踩过的坑集中在三类：

1. **语法差异**：任务列表、脚注、数学公式、内联 HTML，各平台支持度参差不齐；
2. **资源差异**：本地图片路径出不了机器，公众号要求图片先传素材库、替换 URL 后再进正文；
3. **版式差异**：公众号对行距、代码块样式有自己的渲染规则，裸 Markdown 粘进去基本没法看。

用正则做替换只能救急，规则一多就互相打架。可靠的做法是基于 AST 做转换。

## 做法

管线分四段，每段独立可测：

1. **规范化**：把 AI 输出统一为规范 GFM。压平标题层级（不允许出现 h3 以下）、剥掉内联 HTML、补齐表格表头。这一步与平台无关，保证下游拿到同一种输入。
2. **校验**：按平台 profile 跑 lint。规则文件和适配器放在一起，比如知乎 profile 声明“不支持任务列表、链接需脚注化”。lint 失败时返回结构化错误列表，喂回给 Agent 触发自修复——这是全管线 ROI 最高的一环。
3. **转换**：用 remark/rehype 写 AST 变换，每个平台一个小适配器。以公众号为例：代码块转为带内联样式的段落、图片节点抽出来排队上传、投递前回填 URL。
4. **投递**：图片先行，文本后行。图片全部拿到永久 URL 再整体投递，失败可整篇重试。

目录大致是：

```text
pipeline/
  normalize.ts
  lint.ts
  adapters/
    wechat.ts
    zhihu.ts
    blog.ts
```

## 踩坑点

- **表格最脆**。知乎会把复杂表格直接拍平，别恋战，检测到多列表格就降级为列表输出。
- Agent 非常爱用脚注和任务列表，lint 必须在投递前卡住，而不是渲染后兜底。
- 公众号正文里的外链会变纯文本，重要链接要么进“阅读原文”，要么脚注化，别指望原地保留。
- 公众号编辑器基于 Safari，行高、间距都是人工调出来的魔法数，直接抄别人的样式表大概率对不上，只保留自己验证过的值。
- 平台规则会静默变化。渲染结果按（内容 hash + 平台版本）缓存并留样，方便 diff 出“哪天悄悄改了”。

## 可复用建议

- 把管线包成 MCP 工具暴露给 Agent：Agent 只负责写作和消费 lint 错误，不感知平台细节。
- 每个适配器控制在百行内，规则全部文件化，新增平台只是加一个 profile。
- 维护一份“格式样本集”——表格、代码块、长链接、公式各来一段——平台有变更就跑一遍做回归。
- 不要一上来做通用方案，先覆盖你真实在发的两三个平台。

## 总结

格式适配本质是个编译问题：规范化是中间表示，平台 profile 是目标后端，lint 是类型检查。把这条链路从 Agent 对话里拆出来做成管线，写作端和发布端就解耦了——换平台不改提示词，加平台不动流程。
