## 背景

接上 MCP 和插件之后，Agent 就不再是聊天工具了，它能读文件、调 API、写数据库、发请求。这时真正的问题往往不是模型够不够聪明，而是权限边界画在哪：哪些事它自己干，哪些事必须停下来问人。

## 问题

这条边界有两种典型的失败方式：

- **问太多**：每步都弹确认，人沦为点击机器，最后养成“无脑全同意”的习惯，闸门形同虚设。
- **问太少**：一条误删命令、一次群发邮件，损失在你翻日志之前已经发生。

麻烦在于这个问题没有通用答案，取决于业务和工具。下面是我踩了一轮坑之后沉淀下来的一套做法。

## 做法：按 可逆性 × 影响面 分四档

两个维度基本够用：**能不能撤销**，以及**影响的是本地还是外部世界**。

| 档位 | 典型操作 | 策略 |
|---|---|---|
| 只读 | 查询、搜索、列目录 | 自动执行 |
| 可逆写 | 写本地文件、dev 环境插数据、建分支 | 自动执行 + 审计日志 |
| 不可逆、影响面小 | 删单个文件、关一个 issue | 单次确认 |
| 不可逆、对外 | 花钱、发邮件、生产部署、对外发布 | 硬闸门，人工批准 |

落地步骤：

1. **盘点工具并打标**。在 MCP server 配置或插件元数据里给每个工具标 danger level，别指望模型现场判断。
2. **凭证最小化**。给只读数据库账号、作用域受限的 API key，而不是图省事先给 root。
3. **高危操作先 dry-run**。Agent 先输出执行计划（跑什么命令、动哪些资源），人批准后再真跑。
4. **加熔断**。设单日调用次数和花费上限，防止 Agent 陷入失控循环。
5. **审计日志 + 每周复盘**。出问题时能回答“它到底做了什么”。

## 踩坑点

- **确认疲劳**：确认弹窗每天几十次，说明分档错了。确认应该少而准——频率本身就是策略失效的信号。
- **权限蔓延**：“先给大权限、以后再收”基本收不回来，宁可一开始麻烦。
- **别让模型自评风险**：问 Agent“这操作危险吗”，它多半说没事。危险等级写在配置里，这是工程决策，不是推理结果。
- **组合风险**：单独都安全的调用，串起来可能有害（读通讯录 + 发邮件 = 群发）。至少在两个高危工具之间强制插入人工环节。
- **工具描述含糊**：Agent 选错工具，八成是描述没写清副作用。把“这个工具会改什么”明确写进 description。

## 可复用清单

- [ ] 每个工具有 danger level 标注
- [ ] 高危操作支持 dry-run 预览
- [ ] 凭证按最小权限发放
- [ ] 有预算 / 频率熔断
- [ ] 审计日志可检索
- [ ] 确认交互带上下文：人能看到 Agent 为什么想做这件事，而不是一个裸的 yes/no

## 总结

权限边界不是一次配完的开关，而是随业务持续调整的策略层。一句话原则：**可逆的放手让 Agent 干，不可逆且对外的必须人类拍板；确认要少而准，否则闸门迟早退化成装饰。**
