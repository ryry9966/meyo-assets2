## 背景

Agent 自动化跑了一段时间后，大多数人都会撞上同一个问题：MCP 工具越挂越多，Agent 能干的事越来越宽，但"它到底能自己干到哪一步"始终是笔糊涂账。要么每步都弹确认，人变成流水线上的盖章机器；要么一路放行，某天发现它把测试环境的清理脚本跑到了生产库上。

## 问题：失败是双向的

- **问得太多**：自动化失去意义。人被确认框淹没后，会进化成无脑点允许，确认机制形同虚设。
- **问得太少**：不可逆操作一旦失控——外发消息、删除数据、调用付费接口——代价没法用一次重跑弥补。

核心矛盾在于："该不该问"不能靠 system prompt 里一句"谨慎行事"，它得变成可执行的工程约定。

## 做法：按可逆性 × 影响面分级

用两个维度给所有工具动作打标：**可逆性**（能否撤销）和**影响面**（波及自己 vs 波及他人/生产），分三级：

- **绿灯（自动执行）**：只读、沙箱内、可逆、低成本。搜索、读文件、工作区内写草稿、纯计算。
- **黄灯（带护栏执行）**：项目范围内的写入和批量操作。要求先 dry-run、有审计日志、有回滚路径、有批量上限——单次超出阈值（比如改 20 个文件）就升级为红灯。
- **红灯（必须问人）**：不可逆操作、有外部副作用的操作（发消息、发布、支付）、任何触碰生产环境和真实用户的行为。

## 落地步骤

1. **盘点工具**：列出 Agent 可调的全部 MCP 工具，逐一打级。新工具默认红灯，观察后逐步降级。
2. **拆分工具面**：读写分离，只读工具和写入工具挂不同 MCP server；权限配在网关/白名单层，不靠提示词。
3. **把"问人"做成一等工具**：Agent 调用 ask-human 时必须带结构化上下文——做什么、为什么、后果、有无替代方案，而不是干巴巴卡住等人。
4. **写入类工具强制 dry-run**：先返回 diff，确认后才真正执行。
5. **绿灯也记审计日志**：做了什么、为何判为绿灯，作为后续复查的原料。

## 踩坑点

- **只写在 prompt 里不行**。提示词是建议不是权限系统，上下文够长、任务够复杂时模型一定会越线，约束必须落在工具调用层。
- **确认疲劳**。一个任务弹 30 次确认，人第 5 次就开始盲批。批量操作应该"问一次计划，而不是问 30 次步骤"。
- **伪可逆**。"移到回收站"可逆，"覆盖保存"不可逆；"删草稿"可逆，"发出去"不可逆。分级按最坏情况打标。
- **只测正常路径**。上线前要做负面测试：构造诱因，验证 Agent 在红线前真的会停下来问，而不是嘴上说会停。

## 可复用建议

- 每个 Agent 维护一张动作分级表，加新工具时同步更新，纳入 review 流程。
- 定期抽查审计日志里的绿灯记录，把"其实该是黄灯"的动作往上调。分级标准随信任度演化，而且通常应该越收越紧。
- "问人"本身要设计好：上下文给足、默认选项明确、超时策略写清楚（超时后是放弃还是按最保守方案执行）。

## 总结

权限边界不是一句"请谨慎操作"，而是分级表 + 工具层强制执行 + 审计回查组成的工程设施。判断标准可以很简单：可逆且影响面小就放行，不可逆或涉及外部世界就停下来问。Agent 的自主性是靠边界换来的——边界划得越清楚，你敢给它的自由度才越大。
