## 背景

跑 OpenClaw 一段时间后，大多数人的环境里会同时存在两类模型：GPT 级云端模型（质量高、按 token 计费、数据出域）和本地模型（Ollama / vLLM 起的 Qwen、Llama 之类，免费、数据不出机器、能力上限明显更低）。OpenClaw 的配置支持给不同 agent 指定不同 model，但常见的两个极端是：要么全走 GPT（月底账单心疼），要么全走本地（多步工具调用频繁翻车）。这篇记录我们摸索出的分工边界，供参考。

## 问题

路由的本质不是“哪个模型更好”，而是：**这个任务对质量、成本、隐私的敏感度分别是多少**。三类典型任务：

- **长链规划 / 复杂工具编排 / 模糊指令理解** → 质量敏感，云端强模型
- **批量摘要、格式转换、简单抽取** → 成本敏感，本地小模型足够
- **涉及日志、个人数据、内网代码** → 隐私是硬约束，强制本地

## 做法

1. **按 agent 角色分，不按单条消息分。** 主控 / planner 类 agent 固定用 GPT，executor、格式化类 subagent 固定用本地。按消息动态路由需要额外的 router 模型，本身又引入一个故障点，第一版别做。
2. **规则先行。** 用确定性规则做初始分流：输入命中敏感路径 / 密钥特征 → 本地；预估上下文超过本地窗口（如 8k）→ 云端；其余默认本地。
3. **失败升级（escalation）。** 本地模型工具调用失败或 JSON 解析失败连续超过 N 次，自动切 GPT 重放同一任务，并在日志里标记升级原因。
4. **先量再迭代。** 每个 agent 记录 token 花费、端到端延迟、任务成功率（人工抽查 5% 即可），跑一周再决定要不要加第三层。

## 踩坑点

- **本地模型上下文窗口**：工具返回的大段 JSON 直接撑爆 8k，报错还很隐晦。在 executor 前加裁剪/摘要步骤，或这类任务直接锁云端。
- **function calling 质量差异**：不少本地模型多步工具调用成功率明显低于 GPT，表现为漏参数、幻觉工具名。别指望同一段 prompt 表现一致，给本地模型维护一份精简版工具集。
- **本地 ≠ 低延迟**：GPU 被别的任务占着时，本地反而比云端慢。延迟看 P95，别看均值。
- **路由规则别写业务词**：规则一旦和具体项目耦合，换个项目全失效。只保留“敏感度 / 长度 / 历史失败率”这类通用信号。

## 可复用建议

- 两层起步（本地默认 + 云端升级），不要一上来搞三层路由。
- prompt 尽量模型无关，但 system prompt 给云端/本地各维护一份变体，本地版本更啰嗦、更强调输出格式约束。
- 升级决策必须落日志，否则两周后没人记得当时为什么切模型。
- 隐私是硬约束不是加权项：命中即本地，不参与成本权衡。

## 总结

多模型路由的价值不在省多少钱，而在让**贵的模型只花在难的地方**。先用最笨的规则加失败升级跑起来，再靠日志数据驱动迭代。我们从全 GPT 切到这套方案后，月度 token 成本降了约 60%，任务成功率基本没动——数字不一定能复制，但方向是可验证的。
