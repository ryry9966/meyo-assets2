## 背景

OpenClaw 的长期记忆本质上是一堆 markdown 笔记（memory 目录 + 会话摘要），`memory_recall` 负责在主任务里按需把这些内容捞回来。捞得准，agent 就“记得住事”；捞不准，要么答非所问，要么该想起的没想起。

记忆检索主流就两条路：**语义搜索**（embedding 向量 + 相似度）和**全文搜索**（BM25/FTS 这类关键词匹配）。OpenClaw 支持向量、混合等检索模式，所以问题从来不是“能不能用”，而是“哪种该在什么时候用”。

## 问题：两种失败模式

我翻过的两类车，正好各对应一种检索：

- **语义搜索的失败**：问“上次数据库超时怎么解决的”，recall 捞回三段聊过超时的内容，却漏掉了记录具体错误码 `ETIMEDOUT 3306` 的那条笔记——向量把“超时”泛化得太宽，精确标识符反而沉底。
- **全文搜索的失败**：笔记里写的是“连接池打满”，后来问法是“并发高了数据库连不上”，关键词完全对不上，空手而归。

一个输在精确匹配，一个输在换个说法。这就是要实测的原因。

## 做法：用 20 条查询跑个对照

不想凭感觉站队，我做了个小实验：

1. 从历史记忆里挑 20 条真实笔记，每条写 2~3 种可能的问法，凑成约 50 条查询的迷你评测集（精确标识符类、同义改写类、混合类各占三分之一）。
2. 分别用纯向量、纯全文、混合（两路召回 + 合并排序 + 时间衰减加权）各跑一遍，人工标注 hit@1 / hit@3。
3. 同时记录每次 recall 注入上下文的 token 量，避免“捞得多”掩盖“捞得准”。

结果不意外：精确标识符（错误码、路径、配置键）全文近乎全胜；同义改写语义领先；混合模式两项都不垫底，hit@3 稳定最高，代价是多一路索引和一点延迟。

## 踩坑点

- **中文全文检索的默认分词基本不可用**。SQLite FTS5 默认 tokenizer 对连续中文处理很差，换 trigram（或外挂中文分词）后才正常。
- **embedding 模型对中文行话的表征质量参差**（“连接池打满”这种词），换模型要重灌索引，先小样本验证再全量。
- **索引滞后**：笔记持续追加改写，向量索引不重建就会“明明改了却搜到旧版”。把重建挂到写入钩子上，别靠手动。
- **分块太大**：一条笔记整段入库，命中一次就注入几百 token，主任务的上下文预算被记忆吃掉。按主题切块、附带日期和标题元数据效果好得多。
- **top_k 别贪大**：k=8 时准确率没涨，主回答质量反而下降——记忆抢戏是真实存在的。

## 可复用建议

- 默认上**混合检索**，两路召回 + 合并排序，别纠结二选一。
- 在工具描述里写清触发时机：出现“之前/上次/历史”类字样、或涉及精确标识符时才 recall；每轮全量检索纯属浪费。
- 维护那 20 条评测集，换模型、调参后重跑，比感觉可靠。
- **时间衰减很重要**：agent 记忆的时效性远强于文档检索，最近一周的笔记权重应明显更高。

## 总结

语义搜索赢在“换个说法也能找到”，全文搜索赢在“一个字都不能错”。真实记忆里两种查询都存在，所以答案是混合 + 持续评测，而不是站队。半天搭个迷你评测集，比读十篇对比文章有用。
