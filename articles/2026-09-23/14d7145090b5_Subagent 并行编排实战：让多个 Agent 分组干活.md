## 背景

我们的 Agent 日常有两类典型负载：一类是**批量型任务**，比如对 20 个模块逐一做代码审查、给十几个仓库做依赖升级调研；另一类是**探索型任务**，比如同时评估三个技术方案的可行性。过去这些都走主 Agent 单线程：一个做完再做下一个，一轮下来几十分钟，而且上下文越堆越长——到第七八个任务时，主 Agent 已经开始"失焦"，前面任务的中间结论会污染后面的判断。

## 问题

拆开看其实是三个独立的问题：

1. **串行瓶颈**：批量任务之间无依赖，排队纯属浪费；
2. **上下文污染**：所有中间结果堆在一个会话里，token 膨胀、注意力稀释；
3. **错误传染**：某个任务产出的一段错误结论，会被当作"已知事实"影响后续步骤。

## 做法：切分 → 并行 → 收敛

以批量代码审查为例，我们的编排分四步：

**1. 主 Agent 只做切分，不做执行。** 按模块把任务拆成 N 个子任务，每个子任务的 prompt 必须自包含：文件路径、审查维度、输出格式，一个都不能假设子 Agent "应该知道"。

**2. 逐个 spawn subagent，最小化上下文。** 每个子 Agent 只拿到自己那份输入，天然干净。

**3. 约定结构化返回。** 强制 JSON schema（issues 数组，每条含 severity / file / line / suggestion）。自由文本没法聚合，这一步不能省。

```json
{ "issues": [ { "severity": "high", "file": "src/a.ts", "line": 42, "suggestion": "..." } ] }
```

**4. 主 Agent 只做聚合。** 去重、按严重度排序、生成报告。子 Agent 的原始输出先落盘，聚合层像纯函数一样只读这些文件——任何子任务出问题，可以单独重跑，不必全链路重来。

并发用队列控制：同时跑 3~4 个，跑完一个补一个。

## 踩坑点

- **并发开满撞 rate limit**：第一版同时开 10 个，触发限流后进入重试风暴，比串行还慢。解法是保守并发 + 指数退避。
- **子 Agent "看不到"主会话**：主 Agent 以为之前聊过的背景子 Agent 知道，实际上子 Agent 是独立上下文。所有信息必须显式写进子任务 prompt。
- **写冲突**：两个子 Agent 同时改同一个文件，后写的覆盖先写的。解法：子 Agent 只读、只返回结论，所有写操作收敛到主 Agent 串行执行。
- **聚合丢细节**：只回传摘要，排查时无法追溯。解法：原始输出落盘，摘要只是索引。
- **切分不均**：一个大模块的子任务跑 10 分钟，其他早结束了。切分时按工作量大致配平，或改成动态认领队列。

## 可复用建议

1. 子任务 prompt 自包含，是编排可靠性的第一前提；
2. 结构化输出 + schema 校验，聚合层才可能稳定；
3. 并发从 3 起步，观察限流和耗时再调；
4. 子 Agent 只读，写操作收敛；
5. 每步结果落盘、全链路幂等，任何子任务失败可单独重跑。

## 总结

subagent 编排的价值不是"更多的 AI"，而是三件事：**干净的上下文边界、可控的并发、可追溯的结果**。它解决的是批量与探索型任务的工程化问题，而不是把简单任务复杂化。建议先用 3 个子任务把"切分—并行—聚合—重跑"整条链路跑通，再扩规模；链路没通之前，并发数越高，返工越多。
