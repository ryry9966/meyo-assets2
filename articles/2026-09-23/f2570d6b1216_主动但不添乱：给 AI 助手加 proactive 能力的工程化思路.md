## 背景

现在大部分 agent 还是被动应答模式：你发一条消息，它回一条，然后 dormancy。其实 OpenClaw 这类框架已经把 proactive 的地基打好了——heartbeat 心跳、cron 定时任务、webhook 事件入口、MCP 工具挂载，全是现成的。缺的不是能力，而是"什么时候该开口"的判断层。

## 问题

直接打开主动性会遇到三件事：

1. **骚扰**：每次心跳都触发一次"有没有要汇报的"，一天给你发二十条"一切正常"
2. **成本**：心跳带全量上下文跑 LLM，token 消耗轻松翻几倍
3. **风险**：agent 自作主张执行了写操作，你事后才发现

所以 proactive 的核心工程问题是**信噪比和权限边界**，不是"能不能主动"。

## 做法

**第一步，盘点数据源。** 日历、邮件、GitHub、监控告警，能走 MCP 的走 MCP，能推 webhook 的推 webhook。这步和主动性无关，但它是原料。

**第二步，触发器分三类，按确定性排序：**

- **定时类（cron）**：确定性最高，比如每天早 8 点生成一条汇总。先做这个。
- **事件类（webhook）**：PR 挂了 CI、服务器告警，推给 agent 让它判断要不要转达。
- **判断类（heartbeat）**：低频心跳（2–4 小时一次），agent 扫一眼上下文，没有值得说的事就静默返回，不发消息。

**第三步，在系统提示词里写清"开口规则"。** 这是关键。明确写：只有满足可判定条件（错误数超阈值、日程冲突、某渠道超过 X 小时未处理）才主动发消息，否则保持沉默。给标准，不要"看着办"。

**第四步，动作分级。** 观察类（读、汇总）可自主；建议类（"发现 XX，要处理吗"）先说再做；写操作必须等你确认。确认门槛在提示词和工具层双重限制。

**第五步，建反馈回路。** 每条主动消息记录：发了什么、你有没有回、有没有照办。每周看一眼，回复率低于三成就收紧阈值。

## 踩坑点

- **心跳太频繁**。哪怕静默返回也有基础开销，先用规则预筛（有新事件才触发 LLM），别每次心跳都跑模型。
- **webhook 重复投递**。GitHub 重试、消息队列 at-least-once，同一事件可能到两次，需要幂等键去重。
- **忘了免打扰时段**。凌晨三点一条"温馨提示"，足以让你卸载整套自动化。加 quiet hours。
- **提示词漂移**。跑两周后 agent 要么话痨要么装死。别靠感觉调，看回复率数据。
- **提示词不是权限系统**。哪怕提示词里禁了写操作，工具层也要留闸门。

## 可复用建议

按"定时 → 事件 → 判断"的顺序渐进，别一上来全开。第一个场景选高信号、低风险的，比如固定时间的每日摘要。度量只需三个数：主动消息数、回复率、误报数。原则一句话：proactive 的价值不在于做了多少事，而在于**它开口时，你愿意听**。

## 总结

OpenClaw 把触发器和工具层都备齐了，剩下的 proactive 是提示词工程 + 权限分级 + 数据反馈的组合活。从一条 cron 摘要开始，先把信噪比调对，再逐步放权。主动是特性，克制才是设计。
