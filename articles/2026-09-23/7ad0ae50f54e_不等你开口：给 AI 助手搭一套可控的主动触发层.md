## 背景

大多数 agent 的使用模式是被动的：你发消息，它回话。OpenClaw 这类常驻助手的真正优势在于它常驻、有工具（MCP server / 插件）、有状态——但大部分时间在空转。Proactive 能力指的是助手在没人提问时也能基于条件做事：定时汇总、监控巡检、到期提醒、事件触发的自动处理。

## 问题

最直觉的做法是"让模型自己决定什么时候行动"——高频心跳、自由判断要不要通知你。实际跑起来几乎必然翻车：

- token 成本不可控，心跳一次就是一轮完整推理；
- 通知判断交给模型，结果抖动：该报的不报，不该报的连环轰炸；
- 没有去重和限流，同一个问题每五分钟推一次，一周后你开始无视所有推送；
- 写操作不受控，自动化变成事故来源。

结论：proactive 不是 prompt 问题，而是触发、判断、执行、通知四层的工程问题。

## 做法

我把它拆成四层，职责单一：

**1. 触发层（确定性）**：只用 cron 和 webhook。cron 负责时间驱动（每日摘要、定期巡检），webhook 负责事件驱动（git push、监控告警）。触发条件全部写在配置里，不让模型参与"要不要触发"的决策。

**2. 判断层（廉价）**：触发后先跑纯代码检查——读状态文件、比对阈值、算 diff。只有命中条件才升级到模型。模型在这一层只做两件事：判断"是否值得打断用户"和生成摘要文案，且用便宜模型。

**3. 执行层（受限）**：写操作统一走沙箱 + 审批门。主动任务默认只读；要写文件、发消息、调外部 API，必须在任务定义里显式声明权限，高危动作留给人确认。

**4. 通知层（去重）**：维护一个状态存储（SQLite 或 JSON 文件），记录每个任务的 `last_run`、`last_notified`、dedup key。同类告警设冷却时间，夜间静默，单任务设每日推送上限。

一个典型的心跳任务模板：

```
每 30 分钟：
1. 代码预检：拉取 CI 状态 + 未读 issue
2. 命中失败/新增 → 调模型生成 3 行摘要
3. 与上次通知比对，去重
4. 推送到 Telegram，写回状态
```

## 踩坑点

- **心跳频率**：一开始设 5 分钟，一天烧掉的 token 比主动对话还多。降到 30 分钟 + 代码预检后，成本降了一个数量级。
- **判断交给模型**：让 LLM 决定"要不要通知"，连续三天出现漏报和重复报。判断逻辑能写代码就写代码，模型只做摘要。
- **自触发循环**：agent 自动 commit 触发了 webhook，webhook 又唤醒 agent。事件源要打 tag，agent 自己产生的事件默认不再入队。
- **上下文过期**：定时任务复用了几小时前的会话，拿旧记忆做判断。主动任务建议每次开新 session，需要的上下文显式注入。
- **静默失败**：cron 任务挂了三天没人发现。每个任务必须有失败可见性——至少写日志，或者失败时反向通知。

## 可复用建议

- **先只读，后写入**：让主动任务先跑两周"汇报类"工作，建立信任后再放开执行权限。
- **每个任务一份独立配置**：prompt 模板、权限、预算、冷却时间，全部显式、可版本化。
- **预算硬编码**：单任务每日 token 上限、推送上限，超了就熔断。
- **通知要能被关掉**：任何推送附带取消指令，否则用户会直接关掉整个渠道。

## 总结

Proactive 的价值不在"模型有多聪明"，而在触发是确定的、判断是廉价的、执行是受限的、通知是去重的。把"要不要做"交给配置和代码，把"怎么做"才交给模型——这样主动助手才是一个能长期挂着的系统，而不是一个定时炸弹。欢迎在评论区贴你们的主动任务配置，互相抄作业。
