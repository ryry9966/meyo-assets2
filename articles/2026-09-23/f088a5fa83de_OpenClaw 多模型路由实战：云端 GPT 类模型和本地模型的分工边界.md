## 背景

我的 OpenClaw 网关跑了大半年，最初是纯云端模型单配置，稳定但账单难看；后来接上 Ollama 想省钱，结果 agent 任务频繁卡死。折腾几轮后形成了一套相对稳定的路由策略， share 出来供参考。

## 问题：按什么标准分流

试下来真正有效的判断维度只有四个，按优先级排：

1. **工具调用可靠性**——agent 场景的硬门槛，模型吐不出合法的 tool call 参数，后面全白搭
2. **上下文长度**——OpenClaw 会注入记忆、工具结果、频道历史，8k 窗口的本地模型很容易撑爆
3. **隐私边界**——哪些数据绝对不出本机，这个要在算成本之前先划清楚
4. **成本与延迟**——排最后，前三个不满足时省的钱没有意义

## 我的分工方案

**给任务分类（先跑两周统计再动手）**。在日志里标出每类请求的性质，不猜。

**云端模型（GPT/Claude 类）负责**：
- 多步工具调用的 agent 主循环
- 代码修改、重构类任务
- 复杂规划和长会话的主 agent

**本地模型（Ollama/LM Studio）负责**：
- 消息分类、摘要、格式转换这类单次短文本变换
- 高频低价值任务（心跳检查、频道消息预处理）
- 涉及隐私的原始数据处理，处理后摘要再上云

**配置层面**：`openclaw.json` 的 `models` 段挂多个 provider，主 agent 指向云模型，子 agent 和专用 agent 覆盖为本地模型；配好 fallback 链（云挂了落本地保底）。

**建回归集**：攒 10–20 条真实任务，每次改路由配置跑一遍，避免“感觉上没问题”。

## 踩坑点

- **别只看聊天质量测本地模型**。7B 模型日常对话像模像样，function calling 却经常吐残缺参数，agent 循环反复重试直到超时。工具调用要单独压测。
- **上下文静默截断**。本地模型窗口小，超限后行为是“看起来还能跑但开始胡说”，比报错更隐蔽。把记忆注入和工具结果算进预算。
- **量化版本差异大**。同一个模型 q4 和 q8 在工具调用上表现可能是两回事，换了量化等级要重跑回归集。
- **会话中途换模型**。主循环 fallback 到本地后，输出风格和工具用法会突变，记忆格式也可能乱。fallback 尽量只在故障时触发，不作为常规省钱手段。
- **fallback 风暴**。云模型限流时全量流量砸向本地，弱机器直接拖垮网关。设并发上限和告警，宁可降级响应也别静默塌方。

## 可复用建议

- 一条粗判规则：**连续两次以上工具调用、或涉及改代码 → 云端；单次短文本变换 → 本地**。命中率很高。
- 模型版本 pin 死写进 git，云端和本地都会静默升级，别让路由在背后漂移。
- 隐私边界优先于成本。本地模型的第一价值是数据不出机器，省钱只是副产品。
- 路由是持续运维问题，不是一次性配置。留好按模型统计的 token 和调用日志，每月复盘一次。

## 总结

多模型路由的本质不是“哪个便宜用哪个”，而是把任务按**工具调用复杂度和数据敏感度**分层，让云端模型只干它不可替代的活。OpenClaw 的多 provider 和 per-agent 覆盖机制足够支撑这套玩法，关键约束在模型本身的能力边界——先测清楚，再分流。
