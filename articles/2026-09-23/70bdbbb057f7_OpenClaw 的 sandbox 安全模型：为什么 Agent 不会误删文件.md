## 背景

OpenClaw 的 Agent 拿到的是真实工具：shell 执行、文件读写、HTTP 请求。它不是聊天机器人，而是能对文件系统造成实际变更的运行时。所以很多人接入后第一个问题就是：如果模型“想错了”，它会不会把我的项目目录、甚至整个 home 删掉？这个问题值得认真回答，因为答案不在模型里。

## 问题：提示词不是安全边界

在 system prompt 里写“不要删除文件”，是行为引导，不是隔离。模型输出是非确定性的，提示注入随时可能改变它的行为——Agent 读到的某份文档、某个网页里藏着一行指令，就可能让精心写的约束失效。真正可靠的做法是把边界放在执行层。OpenClaw 的 sandbox 模型核心就一句话：默认权限收窄，破坏性动作显式放行。

## 做法：四层防御

1. **Workspace 根目录隔离。** Agent 的文件工具默认以 workspace 为根解析路径，越界尝试（`../`、绝对路径出根、符号链接逃逸）在规范化校验后被拒绝。你的 home 目录默认根本不在它的可写视图里。
2. **容器级 sandbox。** 开启 sandbox 模式后，整个 agent 运行时跑在容器内：只有 workspace 以 bind mount 挂进去，参考资料挂只读，rootfs 尽量只读，网络按需关闭。容器里的 `rm` 再失控，删的也只是挂载范围内的东西。
3. **工具策略与审批。** `exec` 这类高风险工具走策略：白名单命令直接放行，破坏性模式（递归删除、覆盖式重定向、提权）触发审批或直接拒绝。审批结果写入审计日志，事后可回放。
4. **插件和 MCP 同规则。** 第三方工具不是法外之地：它们注册的 tool 同样套用路径校验和审批策略，调用记录进同一条审计流。配置细节各版本略有差异，以你所用版本文档为准。

## 踩坑点

- **把 $HOME 挂进容器图省事**——等于亲手拆掉第一层防线。
- **workspace 里的软链接指向外部目录**：如果路径检查只做字符串前缀匹配就会绕过，务必确认 symlink resolve 之后再校验。
- **把 Docker socket 挂进 sandbox 容器**：等于授予宿主机 root，常见于想让 Agent“顺手”管理容器的人，不要这么干。
- **MCP/插件进程跑在沙箱外**：工具调用不经审批直接落地，模型再规矩也没用。
- **只写提示词然后以为有安全模型**：模型可以换，提示词可以变，隔离层才是恒定的。

## 可复用建议

- 每个 agent 独立 workspace，最小挂载：要改的目录读写，参考资料只读。
- 上线前做金丝雀测试：放一个 canary 文件和一个诱饵目录，跑一天任务，翻审计日志看它是否尝试越界。
- 破坏性命令默认拒绝、按需白名单，比默认放行再补救便宜得多。
- 定期复盘审计日志，把高频通过的审批项沉淀成白名单规则，减少人工介入。
- 升级 OpenClaw 后重跑 canary 测试——路径校验是有回归风险的代码，不要默认它永远正确。

## 总结

“Agent 不会误删文件”不是模型可靠，而是执行层里不可靠的路径被堵死了。OpenClaw 用的是经典的纵深防御：workspace 边界、容器隔离、工具策略、审计日志各挡一层。提示词可以被注入改变，但这四层不动，破坏性操作就没有从“可能”变成“发生”的通路。别把 sandbox 当玄学信任，把它当成一个可验证、可测试的边界——这才是能放心让 agent 干活的底气。
