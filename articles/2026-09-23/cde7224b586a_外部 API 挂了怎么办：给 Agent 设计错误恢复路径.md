## 背景

跑过长时间自动化任务的人都有体会：Agent 流程里最不可控的不是模型，而是外部依赖。LLM 供应商限流、MCP server 掉线、第三方接口超时——这些几乎必然发生。单次交互失败了重发一次就行，但在 OpenClaw 这类无人值守的自动化场景里，一次没处理好的失败可能意味着整条链路报废，或者更糟：Agent 拿着残缺数据继续往下走。

## 问题

裸奔的 Agent 遇到 API 失败，常见三种坏行为：

1. **把报错原文塞回上下文**，让模型自己猜，猜出幻觉式的"成功"；
2. **无脑重试**，429 也重试、401 也重试，烧完配额才停；
3. **直接崩掉**，中间状态全部丢失，重跑要从头再来。

核心矛盾是：错误处理全靠模型即兴发挥，不可靠；完全写死在代码里，又失去灵活性。务实的分界线是，**代码负责恢复，模型负责决策**。

## 做法

**第一步：错误分类。** 在工具封装层把错误分成可重试（超时、网络错误、429、5xx）和不可重试（401/403、参数错误、余额不足）。返回给 Agent 的值带上结构化字段，比如 `{"status":"unavailable","retryable":true,"hint":"rate limited, wait 30s"}`，而不是原始堆栈。

**第二步：带退避的重试。** 指数退避加抖动，比如 1s / 2s / 4s，最多 3 次；429 优先读 `Retry-After`。每次调用必须有超时，connect 和 read 分开设。

**第三步：降级路径。** 关键工具要有 plan B：备用供应商、本地缓存的上次结果，或明确标注"数据可能过期"。降级结果要在返回值里标来源，避免模型把缓存当实时数据用。

**第四步：熔断。** 连续失败 N 次后快速失败一段时间，别让每个后续调用都去撞一遍已经挂掉的服务。批量任务尤其需要，否则一次故障会把所有并发 worker 拖进重试地狱。

**第五步：断点与上报。** 长任务按步骤持久化中间状态，恢复时从最后一个成功节点继续。恢复失败且无法降级时，带着上下文摘要明确抛给人工，别让 Agent 自己编一个结局。

## 踩坑点

- **对写操作重试导致重复下单、重复发消息。** POST 类接口必须配幂等键，或者只对查询类操作开重试。
- **退避不加抖动。** 多个 worker 同时重试会产生周期性流量尖峰，把半死的服务彻底打死。
- **把 429 当普通错误快速重试。** 限流时越重试越限，等于主动延长封禁。
- **降级源的数据结构不一致。** 要校验返回 schema，否则拿到的是"格式的成功、内容的错误"。
- **超时设太长。** 30s 超时 × 10 步流程 = 一次故障卡五分钟；短超时 + 多次重试通常体验更好。

## 可复用建议

- 所有工具调用走统一的 retry 包装器，参数集中配置，不要每个插件各写一套。
- 工具返回值永远结构化：成功给数据，失败给 `{retryable, hint}`，让模型做的是"选策略"而不是"解析报错"。
- 给每个关键依赖写一行降级预案，没有预案的依赖视为单点故障。
- 上线前故意拔掉依赖做演练：mock 一个 500 和一个持续 429，看 Agent 是恢复、降级，还是装作没事。

## 总结

错误恢复不是锦上添花，而是 Agent 能否无人值守的分水岭。原则可以压缩成三句：可重试的，别烧配额地退避重试；不可重试的，快速失败；都不行，带着上下文找人工。模型负责在策略之间做选择，代码保证策略被执行，这条边界划清楚，大部分"Agent 半夜挂掉"的问题都能消掉。
