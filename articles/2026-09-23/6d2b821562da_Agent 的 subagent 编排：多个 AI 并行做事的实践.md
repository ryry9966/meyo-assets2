## 背景

单 Agent 串行干活有两个瓶颈：上下文窗口被中间结果撑爆，以及任务本身可并行却被顺序执行拖慢。OpenClaw 里主 Agent 可以派生 subagent——每个子会话有独立上下文，干完把摘要交回主会话。听起来像免费午餐，但编排做不好，效率没提，token 消耗和混乱先翻倍。

## 问题

举个上周的典型任务：给一个多模块仓库做依赖升级的影响面分析。单 Agent 的做法是逐个模块读代码、记结论，读到第五个模块时早期结论已经被上下文压缩，而且全程串行。正确的目标是：拆成 N 个互相独立的子任务并行跑，主 Agent 只负责拆分与合并。

## 做法

1. **先判断可拆性。** 并行任务需满足：输入独立、不写同一资源、结果能压缩成短摘要。不满足就老实串行。
2. **派发时给足契约。** 每个 subagent 的指令要包含三件事：范围（只看哪些目录/文件）、工具边界（只读还是可执行）、输出格式（固定字段，比如结论/风险/证据位置）。
3. **写操作隔离。** 涉及改文件的子任务，各自在独立的 git worktree 或临时目录里做，主 Agent 统一审查合并，避免并行写冲突。
4. **汇聚层收敛。** 要求 subagent 只返回结构化摘要而不是全程日志；主 Agent 拿到摘要后做二次校验（抽查证据路径），再合并成最终报告。
5. **控制并行度。** MCP 工具和上游 API 都有速率限制，2–4 路并行通常是最优区间，别开满。

## 踩坑点

- **上下文传递不足：** subagent 看不到主会话历史，派发指令里没写的它就不知道。“猜它知道”是最常见的失败原因。
- **摘要变全文：** 子会话把中间过程全量吐回，主上下文照样爆炸。输出契约里必须写明“只返回结论与证据位置”。
- **并行写冲突：** 两个 subagent 同时改同一个配置文件，后写的覆盖先写的。写操作必须落隔离目录。
- **失败静默：** 某个子任务超时报错，主 Agent 没感知，报告缺一块。派发时带重试上限，汇聚时核对子任务完成数。
- **成本翻倍：** 每个 subagent 都要重新注入背景，任务切太碎时总开销反而超过串行。小任务不值得拆。

## 可复用建议

- 把派发指令做成模板存下来：范围、工具边界、输出格式三段式，每次只改参数。
- 结果校验永远抽查证据（文件路径、命令输出），不直接信结论。
- 汇聚阶段用 checklist 核对：子任务总数、失败数、证据覆盖率。
- 并行是手段不是目的：先跑通单 Agent 版本，确认瓶颈确实在串行或上下文，再上编排。

## 总结

subagent 编排解决的是“上下文不够 + 串行太慢”这两类问题，本质是分布式系统的老原则在 Agent 上的重演：隔离写、契约化通信、有界重试、幂等操作。把每个 subagent 当成一位不了解项目背景、可能出错的同事来写交接文档，成功率会高很多。
