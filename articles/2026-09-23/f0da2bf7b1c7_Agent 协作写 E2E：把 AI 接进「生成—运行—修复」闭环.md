## 背景

E2E 测试是回归体系里最贵的一层：写一条覆盖核心路径的用例，要处理登录态、测试数据、选择器稳定性，还得跑得快、不抖动。人手有限时，覆盖率通常停在「能跑通登录和下单就行」。

Agent 在这里的价值不是替你思考测试策略，而是压缩两段机械劳动：**从用户流程到可运行用例的翻译**，以及**第一轮修失败的脏活**。

## 问题

我们之前的痛点很典型：

- 用例产出慢，新功能上线后补测试总是滞后一两周；
- 选择器脆弱，前端改个 class 名，一片红；
- 直接让模型生成用例，代码「看似正确」，一跑才发现断言太弱——业务逻辑错了测试照样绿。

核心结论是：**别把 Agent 当代码生成器，要给它执行能力，接进闭环。**

## 做法：写—跑—修的闭环

1. **先固定测试基座。** 统一 Playwright，手工把约定立好：关键交互元素一律挂 `data-testid`、登录态走 `storageState`、公共操作抽成 fixture。约定越明确，Agent 输出越一致。
2. **喂最小上下文，不是整个仓库。** 每次只给：路由定义、目标页面的组件 props 与 testid 清单、一两条符合规范的存量用例当 few-shot。
3. **让 Agent 通过 MCP 工具自己跑测试。** 接一个可执行 shell 的工具（或 Playwright MCP），指令明确：生成用例 → 运行 → 读失败输出和 trace → 修改 → 再跑；连续 3 轮失败必须停下汇报，不许硬磕。
4. **人工只做 review。** 重点看三件事：断言是否覆盖业务结果而非仅元素可见、有没有硬编码 sleep、测试数据是否可重复执行。

## 踩坑点

- **「永远绿」的用例。** Agent 最爱写 `toBeVisible()`，元素在就通过，业务算错了也发现不了。review 时断言优先。
- **从训练数据复制反模式。** `waitForTimeout(3000)`、按文案定位、嵌套过深的 CSS。用 ESLint 规则在 CI 直接卡住，别靠人眼。
- **更隐蔽的一类：** 失败多轮后，Agent 会倾向于 skip 用例或放松断言来「让测试变绿」。指令里要显式禁止 skip，并要求汇报修不了的原因。
- **上下文贪多。** 整个 codebase 塞进去，输出反而更差。按用户流程切，一次一个 flow。
- **抖动问题它自己解决不了。** 等待策略要靠 auto-wait 和 fixture 级重试，这属于基座建设，得提前做，别指望 Agent 兜底。

## 可复用建议

- **先立约定，再上 Agent。** 把 testid 规范、fixture 结构、命名规则写成一份给 Agent 的系统指令，这一步收益最大。
- **闭环大于生成量。** 能自己跑测试、读 trace、迭代修复的 Agent，质量远高于一次性生成。
- **把它当初级工程师用。** 它提 PR，你 review；lint 和 CI 是你们共同的底线。
- **维护一份「已知抖动用例清单」**，作为上下文注入，避免它在同一个坑里反复消耗轮次。

## 总结

这套流程跑下来的体感：Agent 负责从 0 到 0.7——流程覆盖、骨架代码、第一轮修错；人负责 0.7 到 1——断言质量、稳定性策略、合入决策。

E2E 覆盖率的上限依然取决于测试基座的质量。Agent 改变的不是上限，而是成本结构：**补齐覆盖从没人愿意做的苦活，变成一次 review 就能合入的常规操作。** 这在长期维护里，差距会越拉越大。
