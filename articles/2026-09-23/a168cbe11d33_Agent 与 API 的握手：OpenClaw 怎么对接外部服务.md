## 背景

Agent 本身只会"想"，真正落地靠的是工具。OpenClaw 的核心价值之一，就是把模型的意图翻译成对外部服务的真实调用：查数据、发工单、触发 CI、操作内部系统。但不少团队第一次对接时，会把"模型能调 API"等同于"调得对、调得稳"，等跑到真实会话里才发现问题一堆。

## 问题：为什么不能让模型裸调 API

最常见的做法是把 API 文档塞进 system prompt，让模型自己拼 URL、带 header。这条路线有三个硬伤：

1. **鉴权信息进上下文**。密钥一旦写进 prompt，就会随日志、会话记录外泄；
2. **参数没有 schema 约束**。字段名、类型、枚举值全靠模型猜，成功率不稳定；
3. **响应原样进上下文**。几个大 JSON 回来，token 就被吃光了，后续推理质量直线下降。

## 做法：薄封装 + 明确契约

推荐的路径是三步走。

**第一步，为每个外部服务包一层 skill/plugin。** 工具层不做业务，只做适配：从配置读密钥、拼请求、裁剪响应。粒度宁小勿大，`create_ticket` 远好过一个笼统的 `manage_service`，模型在小而清晰的工具之间选择，出错率明显更低。

**第二步，写死入参 schema。** 用 JSON Schema 或函数签名约束参数，枚举值直接列全。模型面对受限选项的准确率远高于自由填写。返回值也要定义清楚：状态、关键字段、错误码，缺什么就明确说缺什么。

**第三步，控制进入上下文的内容。** 响应在工具层做投影，只留模型需要的字段；分页结果返回 cursor 而不是全量列表；错误信息用人话重写，比如"rate limited, retry after 30s"，不要把原始 stack trace 喂给模型。

## 踩坑点

- **密钥进日志**。调试时顺手打印请求头，API key 就落盘了。工具层要统一做脱敏。
- **非幂等操作被重试**。超时后框架自动重试，结果工单建了三条。写操作必须带幂等键，或在工具层去重。
- **超时层层放大**。模型等 60 秒、底层 HTTP 超时 120 秒，用户早就走了。对外超时要小于整条链路的时间预算。
- **时间与时区**。API 要 UTC，用户说"明天"，模型给的日期可能就错了。让工具层接收相对时间自己算，或强制参数带时区。
- **错误时模型脑补**。工具失败如果只返回空字符串，模型会当作成功继续编。错误必须是结构化返回。

## 可复用建议

- **给每个外部工具留一条自检路径**：加一个 dry-run 参数，只验证连通性和鉴权，不产生副作用。接入新服务先跑它，再谈自动化。
- **最小化调用日志**：时间、耗时、状态码、token 消耗，四项记全，排障基本不缺线索。
- **把权限当回事**："这个 API 该不该让 Agent 调"要按权限审——只读优先，写操作走确认流，高危操作干脆不暴露给模型。

## 总结

Agent 对接外部服务的核心，不是"教会模型调 API"，而是把不确定性关在工具层里：鉴权不进上下文、参数有 schema、响应有裁剪、失败有结构。模型负责决策，工具负责可靠执行。这条边界划清楚了，OpenClaw 上的自动化才敢说能跑在生产环境里。
