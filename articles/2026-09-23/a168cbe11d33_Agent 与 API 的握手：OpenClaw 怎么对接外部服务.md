## 背景

Agent 跑通 Demo 容易，落到真实业务难。难的不是对话质量，而是"握手"：模型怎么安全、稳定地调到外部服务的接口。OpenClaw 的思路是让模型专注决策，工具层负责执行，外部服务对接是工具层的事。落到实现上，常见三条路：直接封装 HTTP 调用、起一个 MCP server、或写成长驻插件。路径没有绝对优劣，看调用频率、鉴权复杂度和维护成本。

## 问题

实际对接时反复遇到四类问题：

1. **鉴权**：密钥放哪、怎么避免进上下文和日志；
2. **错误回传**：调用失败后模型只看到"失败了"，无法修正参数重试；
3. **响应体积**：一个大 JSON 直接塞满上下文窗口；
4. **副作用**：发消息、创建工单这类写操作，重试就是重复执行。

## 做法与步骤

**第一步：梳理调用面。** 把要对接的服务列清楚：端点、鉴权方式（Header / Bearer / OAuth）、限流阈值、是否幂等。这一步决定接入路径——低频简单调用用 HTTP 工具封装即可；多工具、多服务的场景优先 MCP server，一套协议统一管鉴权和工具描述；需要订阅事件、维持长连接的再考虑常驻插件。

**第二步：收紧工具 schema。** 参数能加枚举就加枚举，能限范围就限范围。描述写给模型看，不是写给人看：说明"这个参数什么时候用、单位是什么、传错的后果"。

**第三步：设计错误回传。** 这是体验差异最大的地方。返回结构化错误：错误码、原因、建议动作。比如限流报错时带上"建议 60 秒后重试"，模型会自己等待而不是硬来。

**第四步：管住密钥和大响应。** 密钥走环境变量或本地配置文件，由工具层注入 Header，永远不进模型上下文。大响应在工具层做分页、截断和字段裁剪，只回传决策需要的部分。

**第五步：写操作加确认层。** 非幂等操作提供 dry-run 参数，或在执行前把"将要执行的动作摘要"回给用户确认一次。重试逻辑放在工具层、带退避，且只对幂等操作自动重试。

**第六步：留观测。** 每次工具调用记一条日志：工具名、参数摘要、耗时、状态码。出问题时能复盘是模型选错工具，还是服务端故障。

## 踩坑点

- 工具描述含糊，模型高频乱传参。描述里写清楚**反例**比写正例有效；
- 只返回"调用失败"四个字，模型陷入盲目重试循环；
- 忽略限流，批量任务跑到一半全挂；
- 密钥被完整打印进调试日志；
- 把十几个散装小工具全塞给模型，选择准确率明显下降——按服务聚合比按动作拆分好。

## 可复用建议

- 一个服务一个 MCP server，暴露给模型的工具数量控制在十几个以内；
- 超时、重试、限流处理全部下沉到工具层，模型只管决策；
- 错误信息永远包含"下一步怎么办"；
- 上线前用固定脚本回放一批真实调用，验证 schema 和错误路径，别只测成功分支。

## 总结

对接外部服务本质上是工程问题，不是提示词问题。把鉴权、错误、副作用、观测这四件事在工具层做扎实，模型的稳定性会跟着上来。OpenClaw 提供了足够的挂载点，剩下的是把接口契约想清楚再动手——先画清调用面，再写第一行工具代码。
