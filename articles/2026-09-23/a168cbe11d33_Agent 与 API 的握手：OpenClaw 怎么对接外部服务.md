## 背景

OpenClaw 的价值不在于对话本身，而在于 agent 能实际“动手”：查数据、发通知、操作工单系统。这些动作背后全是对外部 API 的调用。OpenClaw 提供了几条对接路径——现成的 MCP server、skill/插件封装、或者让 agent 通过脚本直接发 HTTP 请求。路径多了，怎么选、怎么管好鉴权和错误，就成了绕不开的工程问题。

## 问题

实践中最常见的三类故障：

1. **鉴权混乱**：API key 硬编码在 skill 里，或者被带进会话日志，出事才知道疼。
2. **工具描述含糊**：agent 该调的时候不调，不该调的时候乱调，参数格式全靠猜。
3. **错误处理缺失**：上游返回 429/500，原始报错直接堆给模型，agent 开始“自由发挥”。

## 做法

以对接一个内部 REST API 为例，我的步骤：

1. **选路径**：服务有现成 MCP server 就直接挂到 gateway 配置里（stdio 或 SSE 均可）；没有就自己写一层薄封装，别让 agent 直接拼原始 HTTP 请求。
2. **鉴权隔离**：API key 走环境变量，skill 里只引用变量名，由 gateway 配置统一注入，避免散落各处。
3. **写清工具描述**：写清楚“什么时候用、什么时候不用、参数格式、返回结构”。agent 选工具基本靠这段话，写三分钟省三小时调试。
4. **包装错误语义**：把 429 映射成“稍后重试”，把 404 映射成“资源不存在，建议换查询词”，返回结构化结果而不是原始 JSON。
5. **灰度验证**：先在本地 gateway 跑，用固定的测试 prompt 集做回归，确认调用频率和参数都对，再放到常驻环境。

## 踩坑点

- **stdio 模式的 MCP server 子进程挂了不会自动重启**，表现为“工具突然消失”，排查时先看进程再怀疑配置。
- **工具返回太长会撑爆上下文**，分页和截断要在封装层做，别指望模型自己省着用。
- **环境变量改了 gateway 不一定热加载**，先重启一次再排查别的地方。
- **幂等问题**：agent 偶尔会重试，写操作（发消息、建工单）务必带幂等键或做去重。

## 可复用建议

- 每接一个服务，固定产出三样东西：**封装脚本、工具描述模板、最小测试 prompt 集**。下一个服务能复用七成。
- **读操作和写操作拆成两个工具**暴露给 agent，显著降低误触概率。
- 封装层统一打日志，但只记请求摘要，不记 key 和敏感参数——出问题时能快速判断是 agent 的锅还是上游的锅。

## 总结

对接外部服务的本质不是“能不能调通”，而是让 agent 在正确的时机、用正确的参数调用，并且在失败时有可预期的行为。把鉴权隔离、工具描述、错误语义这三件事做扎实，剩下的交给迭代。握手握得稳，agent 才真的能干活。
