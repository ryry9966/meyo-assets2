## 背景

E2E 测试是大多数团队"知道该写但一直欠账"的部分：交互链路长、选择器脆、维护成本高。我们最近用 OpenClaw 的 Agent 加 Playwright MCP server 做了一个多月的实验，让 AI 承担写测试中机械性最强的部分——交互编排，人只保留断言和验收标准的所有权。目前产出 60+ 条用例，flaky 率控制在可接受范围，把流程和坑整理如下。

## 问题的本质

直接"让 AI 生成测试"基本不可用，典型失败有三类：

1. **选择器过拟合**：生成 `nth-child` 这类脆选择器，DOM 一改全挂；
2. **断言过弱**：只验证 URL 或元素存在，测试绿了但什么都没证明；
3. **幻觉 API 与编造数据**：写出不存在的 Playwright 方法，编造测试账号。

根因是 Agent 缺少两样东西：**团队规范**和**环境事实**。解决思路就是显式把这两样喂给它。

## 做法：五步流水线

1. **规范文件化**。把团队测试规范写成一份 markdown（命名、Page Object 结构、优先 `data-testid` / role 选择器、断言上限、超时上限），放进 Agent 常驻上下文。比每次在 prompt 里口头描述稳定得多。
2. **环境事实工具化**。用 MCP 暴露几个只读工具：查测试账号、查 fixture、查路由表。Agent 要什么查什么，不靠猜。这一步对消灭幻觉数据效果最明显。
3. **交互由 Agent 驱动浏览器完成**。Agent 通过 Playwright MCP 实际操作页面，记录验证过的选择器和等待点，再按规范生成用例骨架。它"亲手点过"的路径，选择器基本可靠。
4. **断言人工审**。生成后只 review 两件事：断言是否覆盖验收标准、有没有弱断言。交互代码基本不看。
5. **稳定性门禁**。新用例连跑 10 次全绿才合入；挂了就把 trace 和视频喂回 Agent 让它修等待策略。禁止用拉长超时来"修"不稳定。

## 踩坑点

- 一次生成一批再 review，成本爆炸。小步走：一次 1~2 条，过了再加。
- Agent 会把 CI retry 当万能药。retry 只兜底网络抖动，逻辑性 flaky 必须改用例本身。
- 连共享测试环境，别人改数据它就挂。用固定的隔离环境或快照。
- 别让它自由发挥命名和目录结构，规范里写死模板，违反就打回。

## 可复用建议

- "规范 markdown + 事实型 MCP 工具"这套组合不限于测试。任何让 Agent 产出团队代码的场景都适用：**规范管风格，工具管事实**。
- 断言与交互的 ownership 分开，是整套流程里最关键的分工。AI 写它能验证的部分，人写只有人能负责的部分。
- 保留每次生成的 trace，排障时比日志好用。

## 总结

Agent 写 E2E 的真实收益不是"全自动生成测试"，而是接走交互样板代码和维护中机械的部分，让人把精力放在断言质量和验收标准上。规范文件化、事实工具化、小步合入加稳定性门禁——做到这三点，AI 生成的 E2E 才敢进主干。
