## 背景

跑自动化的人迟早会遇到同一个瞬间：定时任务触发的 Agent 作业跑到一半网络断了，日志里只留下一句"结果不明"，你盯着重跑按钮犹豫——点了会不会发两条通知、写两份重复数据？

重试不是例外，是常态。MCP 工具调用有超时重试，webhook 会因对端无响应而重发，人手也免不了"再跑一次"。一套健康的自动化系统，必须假设**同一个任务会被执行不止一次**。

## 问题：哪些操作天然怕重复

把操作分三类就清楚了：

1. **只读操作**：查询、检索，重复执行无害。
2. **覆盖写**：`set state = X`、写入固定路径的文件，跑一百遍结果一样。
3. **累积写**：append 一行、计数加一、发一条消息、建一个工单——每多执行一次就多一份副作用。

幂等性要解决的就是第三类：让"累积写"在重复执行时，表现得像前两类一样安全。

## 做法：三步改造

**1. 定义幂等键。** 从业务上下文派生稳定标识：任务 ID + 时间槽（如当天日期）+ 输入哈希。注意别用随机 UUID——重试时会生成新 key，等于没做。落地可以就是一张 sqlite 表：`key, status, result`，执行前先插入占位记录，唯一约束冲突说明已在跑或已完成，直接跳过。

**2. 用原子占位代替"先查后做"。** 不要写"先查发过没有，没发过就发"——两个并发实例可能同时查完、同时发。用 `SETNX`、`INSERT ... ON CONFLICT` 或 `UPDATE ... WHERE status='pending'` 这类原子操作抢占执行权，抢到的才动手。

**3. 把副作用改成"声明目标状态"。** 能改写法的尽量改：与其"每天追加一条汇总记录"，不如"确保今天的汇总文件内容为 X"，写入固定路径，内容一致则跳过。对外副作用（发消息、调第三方 API）改不了，就在载荷里带上幂等键作去重标记，或优先选支持幂等键参数的 API。

## 踩坑点

- **幂等键粒度太细**：把秒级时间戳拼进 key，两次触发就是两个 key。时间槽要取业务口径（天/小时），不是执行时刻。
- **只做了入口幂等**：工作流五步，第三步挂了重跑，前两步又执行一遍。幂等要落到每一步的副作用上，不是只包住任务入口。
- **TTL 过短**：key 几分钟后过期，迟到的重试直接穿透。TTL 必须大于你最长的可能重试延迟。
- **占位后进程崩溃**：状态永久卡在"运行中"。给占位状态加超时兜底，过期可被重新抢占。
- **MCP 工具语义不明**：插件工具若是 append 语义，调用方的任何重试策略都是风险。工具描述里写清幂等性，并支持可选的去重键参数。

## 可复用建议

- 建"执行台账"表是性价比最高的改造：一张表加一列唯一索引，解决大半问题。
- 日志和产物里带上 run ID，出问题时能一眼看出"这份数据是谁、第几次跑写的"。
- 把幂等当测试项：staging 里故意连跑两次，diff 结果是否一致。
- 心态倒过来：默认假设"重复执行是安全的、删除重复数据是危险的"，按这个顺序设计。

## 总结

幂等性不是为了保证一次都不失败，而是承认失败和重试必然发生后，让系统对它们的反应是"无事发生"。重试按钮之所以敢按，是因为按下去的世界和没按过一样。写自动化任务前先问一句：**这段代码跑两遍，会发生什么？** 答不上来，就先补上幂等键。
