## 背景

写自动化任务久了，会接受一个事实：任何任务都可能被执行不止一次。Agent 超时后的自动重试、MCP 工具调用失败后的 fallback、cron 的重复触发、webhook 的 at-least-once 投递，甚至用户手动点一下"再跑一次"。在 OpenClaw 里挂定时任务的第一周，大多数人都会撞上同一种事故——重复执行。

## 问题

幂等性（idempotency）指同一操作执行一次和执行多次，最终状态一致。而大多数"写"操作天然不幂等：发消息会刷屏，建工单会重复，append 日志会膨胀。最常见的场景：Agent 调 MCP 工具往群里发通知，网络超时，框架重试，群里出现两条一样的消息。更隐蔽的是状态类任务：脚本每天同步数据并累加计数，重跑一次后悄悄加了两次，没人发现，直到对账时对不上。

## 做法

我的原则是把"防重"做成工具层的基础设施，而不是指望每个任务自己记得。分四步：

1. **生成确定性任务键**。用任务标识 + 输入哈希 + 业务周期拼一个 idempotency key，例如 `sync-orders:{params_hash}:2024-06-01`。关键是"确定性"：同样的触发条件，重跑得到的 key 必须相同。
2. **原子化查重**。执行前先写入 key（SQLite 唯一约束，或 Redis SETNX），写不进去说明已在跑或跑过，直接返回上次结果。不要用"先查有没有、再执行"的两步逻辑，并发下必出竞态。
3. **记录执行账本**。key 对应的记录带状态字段：running / success / failed。只有 success 才算完成，failed 要允许重跑。把失败当成"已完成"锁死，是新手最常犯的错。
4. **写操作尽量改成 upsert**。能"设置目标状态"的，不要"追加一次动作"。同步类任务声明"应该是什么样"，diff 后对齐，天然幂等。

在 OpenClaw 里，我习惯在 MCP 工具 handler 外包一层中间件统一做 1–3 步，业务代码不感知：

```python
@idempotent(key="{tool}:{hash(params)}:{today}")
def send_notify(params): ...
```

## 踩坑点

- **key 粒度错**：带秒级时间戳等于没做幂等；完全不带时间，任务永远只跑一次。粒度要跟业务周期对齐（当天、当次触发）。
- **防重状态只存内存**：进程一重启记录全丢，至少落 SQLite。
- **TTL 太短**：重试发生在 10 分钟后，key 5 分钟就过期了。TTL 要盖住最大重试窗口。
- **下游不配合**：第三方 API 不支持幂等键时，用"先查后写 + 唯一外部单号"兜底。
- **并发双过**：两个进程同时通过了 if 判断。答案永远是用唯一约束、SETNX 这类原子操作，不是加判断。

## 可复用建议

- 把幂等中间件做成公共模块或插件，所有写操作默认走它，不让业务方各写各的。
- CI 里加一条断言：同一任务连跑两遍，第二次的结果与状态必须和第一次一致。
- 实在无法幂等的动作（发短信、支付），挪到人工确认节点，让自动化停在"准备执行"这一步。

## 总结

幂等性不是高级技巧，而是自动化能长期无人值守运行的前提。核心就三件事：确定性的 key、原子的查重、能区分成败的执行记录。第一次接入多写几十行代码，之后每个新任务都在白嫖这套底座——这才是与重复执行和平共处的方式。
