## 背景

在 OpenClaw 这类自动化体系里，一个任务的链路通常很长：定时器或消息触发 → Agent 规划 → 调用 MCP 工具 → 写外部系统。任何一环都可能失败，而失败之后的自然反应就是重试。重试再叠加几类常见情况——调度重叠、webhook 重复推送、Agent 超时后重新规划又执行一遍——结果就是：同一段逻辑，跑了不止一次。

## 问题

如果操作本身不幂等，重复执行就是事故：

- 同一条通知在群里发了三遍；
- 同一张工单被创建了两条；
- 积分、配额、余额被扣了两次；
- 定时任务 overlap 后，数据整体翻倍。

幂等性的定义很朴素：同一操作执行一次和执行 N 次，最终效果相同。它不是性能优化，而是"敢不敢开自动重试"的前提。

## 做法

1. **先分类。** 天然幂等的操作不用处理：读操作、把状态设为固定值（`set status = done`）、按固定文件名覆盖写入、upsert。真正要处理的是"追加型"操作：insert、发送、创建、扣减。
2. **给任务一个稳定的幂等键。** 键必须来自业务语义，而不是每次重试随机生成。常用构造：`hash(事件ID, 任务类型, 目标对象, 时间窗口)`。同一源事件触发的所有重试，共享同一个键。
3. **执行前后落库。** 用一张小表（SQLite 就够）记录 `key → 状态/结果`：执行前查重，执行后写入。并发场景下，用 `INSERT ... ON CONFLICT` 或 Redis `SET NX` 保证"检查 + 占位"是原子的。
4. **能用外部系统原生幂等就用原生。** 很多 API 支持幂等键；数据库用 upsert 和唯一约束兜底。
5. **改不了的调用，记意图账。** 对无法改造的外部调用，先写一条"准备执行 X"，成功后再标记完成；重启或超时后靠这张账本对账，而不是盲目重发。
6. **防并发，不只是防重试。** 调度重叠、多实例同时跑时，用锁或带 TTL 的租约保证同一任务同一时刻只有一个执行者。

## 踩坑点

- **幂等键在重试循环里生成**：每次重试都是新键，等于没做。键要在任务派发时就确定。
- **键太粗或太细**：少了时间窗口，跨天的合法任务会被误去重；带了毫秒时间戳，则永远匹配不上。
- **查重和写入不原子**：两个并发执行同时查到"没有记录"，然后都执行了。必须用事务或 NX 语义。
- **超时后的假失败**：请求实际已到达且成功，本地却标记失败后重试 → 重复。这类只能靠查询对账或下游幂等键，不能靠"再试一次"。
- **多步流程只做任务级幂等**：任务重跑时，前几步已完成的结果要能被识别并跳过，幂等要下沉到步骤级别。

## 可复用建议

- 把常用写操作封装成幂等版工具：`upsert_record`、`send_once(key, ...)`，在插件层默认带键。
- 在 Agent 的工具描述里明确标注哪些工具可安全重试、哪些不行，让模型在失败后做出正确选择。
- 上线前做个简单验证：同一任务连跑两遍，断言外部系统状态不变。
- 去重记录的保留期要覆盖最大的重试/延迟窗口，过期太早等于窗口漏了。

## 总结

重试在自动化里不是异常，是常态。幂等性决定了重试是"自愈"还是"事故放大"。核心就三件事：稳定的幂等键、原子的查重写入、对不可控下游的意图账本。做到"跑两次，效果一次"，自动重试才真正敢开。
