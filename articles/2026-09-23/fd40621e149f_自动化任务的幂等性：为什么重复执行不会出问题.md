## 背景

自动化跑起来之后，你会接受一个事实：**任何任务都会被执行不止一次**。定时器重复触发、网络超时后的重试、agent 规划失败后重新规划、人工怀疑没跑成再手动补跑——这些都是常态。指望"只执行一次"的假设，在真实环境里几乎必然失效。

## 问题

不幂等的任务重复执行，典型症状：

- 定时同步任务创建了重复的工单/记录；
- webhook 重试导致同一事件处理了两遍，通知发了两条；
- agent 在 MCP 工具上重试，目标系统里落了两份数据；
- checkpoint 没落盘，上次做了一半的工作这次又从头来。

根源都一样：写操作没有设计"重复执行也安全"的语义。

## 做法

我们的实践按这几步走：

1. **先分类再动手。** 把任务的每个步骤标成读操作和写操作。读操作天然幂等，风险全在写操作上。
2. **给写操作定一个稳定的业务键。** 不要用随机 ID，用内容派生的确定性 ID，比如"源事件 ID + 动作类型"的哈希。同一次业务动作无论重试几次，键不变。
3. **写入走 upsert，唯一约束兜底。** "先查再插"有竞态，两个并发实例可能同时通过检查。唯一约束是最后一道防线，冲突时捕获异常按已存在处理。
4. **状态变更用条件更新。** 形如 `UPDATE ... SET status='done' WHERE status='pending'`，影响行数为 0 就说明别人已处理过，直接跳过。
5. **调外部 API 带幂等键。** 对方支持就用对方的幂等键机制；不支持就先落一条"意图记录"，成功后再翻状态。
6. **工具设计上保持确定性。** MCP 工具不要在实现里偷偷生成新 ID，同参数重复调用应返回同一结果。

## 踩坑点

- **"先查后写"不是幂等，只是碰运气。** 并发场景必须靠数据库约束。
- **用"上次运行时间"做增量会踩时钟偏移。** 任务重叠或提前触发时窗口算错，宁可记 checkpoint 水位，再配合唯一键。
- **多层重试叠加。** 插件层重试 + 网络库重试 + 外层循环重试，层层放大。重试只留一层，其他层透传。
- **通知类副作用最容易漏。** 发消息、发邮件没有天然键，要自己生成消息键去重。
- **agent 重新规划时换 ID。** 规划器每次生成新 UUID，去重键就废了。键必须来自业务内容，不来自执行过程。

## 可复用建议

每个定时任务、webhook handler、agent 工具上线前问一句："这段代码连续跑两遍会怎样？"答不出来就不该上线。**能安全地手动复跑一次，是自动化任务的基本验收标准。**把"重跑测试"写进插件的验收清单，比任何文档都管用。

## 总结

幂等不是加一个开关，而是一种设计立场：承认重复执行不可避免，让每次写操作在重复面前保持稳定。键确定、写入收敛、状态可判断、副作用有去重——这四件事做到，重复执行只是浪费一点资源，而不是制造事故。
