## 背景

日常工作里有一类高频但低价值的 Git 操作：拉分支、写提交信息、清理已合并的本地分支。这些事不需要很强的判断力，却很打断心流。我们的做法是把 OpenClaw 接上终端和 MCP 工具，让 agent 以"受限实习生"的角色承担这部分工作。跑了几个月，踩了不少坑，这里沉淀一套可复制的配置。

## 问题

直接让 agent 操作 git 有三类风险：

1. **提交信息失真**：模型会根据任务背景"脑补"提交内容，message 和实际 diff 对不上；
2. **危险操作**：`push -f`、对共享分支 rebase、`reset --hard`、`clean -fd`，一次误操作就是事故；
3. **提交污染**：`git add -A` 把 `.env`、日志、临时文件一并带进仓库。

所以核心思路不是放开权限，而是收窄工具面 + 固化流程 + 保留人工确认点。

## 做法

**第一步：收窄工具面。** 不要给裸 shell。写一个 git 包装脚本，只放行 `status / diff / log / branch / switch / add / commit` 这类只读或可逆命令，`push`、`reset`、`rebase`、`clean` 直接拒绝。MCP 侧同理：暴露的 tool 越少，犯错面越小。

**第二步：把规范写进常驻指令。** 在 agent 工作区放一份约定文件：提交信息用 Conventional Commits 风格，分支命名 `feat/xxx`、`fix/xxx`，禁止向 main 直接提交。agent 每次会话都会读到，比在对话里反复叮嘱可靠得多。

**第三步：固定提交流程。** skill 里规定的顺序：`git status` 确认工作区 → 看 `git diff --staged`（大改动先 `--stat` 概览再分块）→ 参考 `git log --oneline -10` 对齐历史风格 → 生成 message 并列出本次提交包含的文件 → 等确认 → 执行。关键约束：message 只允许基于 diff 描述，不许引用任务背景。

**第四步：分支自动化。** 开新任务前，agent 先检查当前分支和未提交改动，从最新 main 拉出 feature 分支再动手；每天收尾跑一次清理，列出已合并的本地分支，逐条向我确认后删除。这一步收益最大——"忘了删分支"是最常见的仓库腐化源头。

## 踩坑点

- **切换分支带脏改动**：未提交状态下 `switch`，改动会漂到新分支。流程里加了前置检查：工作区不干净就先报告，不自动 stash。
- **大 diff 撑爆上下文**：几千行 diff 直接读会失控，也写不准 message。先 `--stat` 概览，再按文件分块。
- **`add -A` 的惯性**：要求逐文件暂存，先列清单再执行；另在 pre-commit 里检查密钥特征（`BEGIN PRIVATE KEY` 之类）兜底。
- **工作目录漂移**：多仓库场景下 agent 在错误的 cwd 执行了 commit。现在每个 skill 第一步都强制校验仓库路径。
- **过度自信的 rebase**：哪怕只留一条 rebase 能力，它也会找到用武之地。直接禁掉，需要时人工做。

## 可复用建议

1. 把 git 约定固化成常驻指令文件，而不是每次对话重复；
2. 用白名单包装脚本替代裸 shell，push 永远留人工确认；
3. agent 的每次 git 操作落一份审计日志，出问题能回放；
4. 自动化范围从"仅提交"起步，稳定两周后再扩展到分支管理；
5. 把 agent 当权限受限的新同事来设计流程，而不是全能管家。

## 总结

Git 自动化的价值不在"全自动"，而在把高频低风险的部分交给 agent，把不可逆操作留给人。收窄工具、固化流程、保留确认点——这套配置跑了几个月，提交质量和分支整洁度都有肉眼可见的改善，也没出过一次需要回滚的事故。护栏不是效率的敌人，恰恰是自动化的前提。
