## 背景

大多数人用 OpenClaw 的方式是典型的问答式：发一条消息，Agent 回答，然后各自下线。这没什么问题，但存在一个盲区——Agent 只知道你问它的那一刻发生了什么。日程里的死线、没回的消息、磁盘快满了，这些事不会因为你没问就不发生。

OpenClaw 内置了一个朴素但容易被忽略的机制：**HEARTBEAT.md**。把它放在工作区根目录，Agent 每隔一段时间（默认约 30 分钟）会醒来读一次，按里面的指令决定要不要做事、要不要打扰你。相当于给 Agent 装了一个心跳。

## 问题：用 cron 做“主动”有三个尴尬

要实现定时主动，最直接的思路是 cron，但实践中有三个痛点：

1. **小任务用 cron 太重**。为了“每天看一眼日志”写脚本、维护路径、处理输出，性价比很低。
2. **cron 不懂上下文**。脚本只会机械执行，而“这件事值不值得报告给人”恰恰是 LLM 擅长判断的。
3. **大多数时段无事可做**。关键是需要一个“保持沉默、别吵我”的出口。

## 做法

**第一步：创建 HEARTBEAT.md。** 在工作区根目录建文件，每行一个任务，用祈使句，尽量具体：

```markdown
- 每天早上第一次心跳，简要汇报今天日程和待办。
- 检查 ~/projects 下 git 仓库有无超过 2 天未推送的提交。
- 磁盘使用率超过 85% 才提醒，否则保持沉默。
```

**第二步：调心跳参数。** 在 `openclaw.json` 里配置间隔和模型：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": {
        "every": "30m",
        "model": "<比主对话更便宜的模型>"
      }
    }
  }
}
```

**第三步：用好静默约定。** 心跳结果默认不推送给用户；如果 Agent 判断无事可做，回复约定的标记即静默结束。在 HEARTBEAT.md 里明确写出“无事时保持沉默”，能显著减少噪音。

## 踩坑点

1. **把文件当任务清单堆满**。每次心跳都会把整个文件喂给模型，条目越多 token 越贵，判断质量也下降。建议控制在 5 条以内，重活交给 cron job。
2. **指令太模糊**。“帮我看看消息”这类写法会导致频繁误报或反向确认。每条任务写清：检查什么、什么阈值、要不要通知。
3. **缺静默出口**。没写“无事保持沉默”，部分模型会每次心跳都汇报一句“一切正常”，半小时轰炸一次。
4. **在心跳里做重活或有副作用的操作**。心跳应该是巡检，不是批处理；长任务容易超时，自动执行类动作（如自动回复）务必先经过你确认。
5. **忽略通知时段**。心跳默认发到主渠道，凌晨的提醒会很烦。把“允许通知的时间段”直接写进 HEARTBEAT.md 是个低成本的解法。

## 可复用建议

- 分层设计：HEARTBEAT.md 做“低频巡检层”，cron 做“确定性调度层”，两者互补而非替代。
- 每条任务遵循三要素模板：**检查项 + 触发条件 + 通知渠道**。
- 心跳用便宜模型，主对话保持高档，长期成本能差一个量级。
- 跑一周心跳日志再调参，多数噪音来自初期配置太激进，而不是机制本身。

## 总结

HEARTBEAT.md 没有任何黑科技，它只是把“Agent 定期醒来、读一个文件、决定做不做”这件事工程化地落地了。它的真正价值是把一部分注意力外包出去：不需要你记得去问，异常才浮出水面。建议从一条任务起步，比如“每天早上汇报日程”，跑稳了再逐条增加。
