## 背景

我们组有七八个服务，日志分散在各自的机器和 CI 上。每天的日报基本都是同一个人花二十分钟翻日志、复制粘贴拼出来的。信息本身没问题，但两个痛点：一是靠人记，容易漏；二是格式靠手，谁写谁一个样。

OpenClaw 支持 cron 触发 agent 会话，配合 MCP 工具能读文件、发请求，理论上完全可以让这件事自动跑。最近花一个周末搭了起来，稳定运行两周多，这里记录思路和踩过的坑。

## 问题

最初的想法很直接：定时触发，让 agent 读当天日志、写日报。试了两版就放弃了：

- 日志一天几十万行，塞进上下文要么溢出，要么 agent 自己"抽样"，关键告警恰好被抽掉；
- 输出格式漂移，今天三级标题、明天列表，下游没法固定解析；
- 偶发幻觉，把昨天的错误数安到今天头上。

结论：不能让 agent 直接面对原始日志。

## 做法

把流水线拆成四层，agent 只承担中间的"翻译"：

1. **采集**：独立聚合脚本（也可以封装成 MCP 工具），按天拉日志、过滤噪音、聚合计数，脱敏后输出两个固定 schema 的 JSON：`metrics.json`（各服务请求数/错误数）和 `events.json`（关键事件时间线，每条带时间戳和来源）。
2. **汇总**：OpenClaw cron 每天 08:30 触发会话。prompt 里只放这两个 JSON 和一份严格模板，明确要求"只输出正文，不要解释"，一级标题固定为 `## 概览 / ## 异常 / ## 变更`。
3. **校验**：脚本对产出做 schema 校验——三个标题是否存在、数字字段是否为数值。失败自动重试一次；再失败就推送降级报告（只有 metrics 表格）并打告警。
4. **分发**：写入按日期命名的文件，同时推 IM webhook。文件名带日期，天然幂等。

目录大致是：

```
daily-report/
├── collect.py        # 聚合 + 脱敏，产出 JSON
├── schema.json       # 中间产物与产出双重校验
├── prompt.md         # 汇总模板，版本化
└── runs/2025-06-10/  # 每天落盘，方便回放
```

## 踩坑点

- **让 agent 直接读日志**是最大的坑，所有不稳定的根源都在这。先聚合再进模型，费用和稳定性都好一个量级。
- **时区边界**：cron 走 UTC，日志按本地日期切，跨八点的记录会算错天。统一成一种时区，在聚合脚本里显式指定。
- **格式漂移**：不要塞很多历史日报当示例，两三份就能把模型带偏。留一份最近的，加上"只输出正文"的硬约束，解析时再按分隔符截取兜底。
- **重跑幂等**：失败重试会在 IM 里重复推送。用日期做 run id，推送前检查当天是否已发。
- **脱敏要在聚合阶段做**。不要指望模型"注意别输出 token"——那是把责任放错了地方。

## 可复用建议

- 中间产物用 JSON + schema，是整条流水线稳定的关键。agent 负责把结构化数据翻译成人话，不负责搬运数据。
- 每个环节落盘。出问题时回放某个 run 的输入输出，十分钟就能定位是采集的锅还是汇总的锅。
- 模板放 `prompt.md` 单独维护，改格式不动代码，diff 也好审。

## 总结

这条流水线跑了两周，日报准点率 100%，人工介入只有一次（上游日志服务改了字段，采集脚本抛错被校验层拦下）。核心经验一句话：把 agent 当"格式翻译器"用，而不是"数据处理引擎"用。数据清洗、校验、幂等这些脏活交给普通脚本，稳定性反而上来了。后续计划把周报、月报复用同一套中间产物，只是换模板。
