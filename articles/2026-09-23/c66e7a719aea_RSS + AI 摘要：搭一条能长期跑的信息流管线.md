## 背景

订阅源越攒越多，真正读完的比例越来越低。RSS 是少数不依赖平台、可以自己持久的输入协议，而 LLM 恰好擅长做压缩。把 RSS 当输入层、AI 当摘要层，是 OpenClaw 用户做自动化的性价比起点：不需要爬虫，不需要碰反爬前线，契约清晰。

## 问题

最常见的做法是"抓 RSS → 整包丢给模型 → 输出摘要"，跑两天就会撞上三件事：**重复内容**（同一事件五六个源都在写）、**幻觉**（摘要里出现原文没有的结论）、**成本失控**（每条都调大模型）。所以这条管线的核心工程量不在"接模型"，而在去重、约束和预算控制。

## 做法

1. **订阅源收敛**：用 OPML 管理订阅，10–20 个源起步。每个源记录健康状态（最近成功抓取时间、条目数），死链及时下线。
2. **抓取与状态**：cron 定时拉取，SQLite 存每条目的 guid、规范化 URL、发布时间。有了状态库，去重是免费的，且每一步都可重跑、幂等。
3. **两阶段处理**：先用规则或便宜模型做粗筛（关键词、时效、黑名单），只有候选条目才进摘要阶段。实测过滤后通常只剩 10%–20% 的条目需要真正调模型。
4. **结构化输出**：要求模型返回 JSON——一句话摘要、类别、是否值得精读、支撑原句。用 schema 校验，失败就重试或降级为"只出原文链接"，绝不让坏输出污染下游。
5. **聚合推送**：按天聚合生成 digest，推到 webhook 或 IM。每条摘要必须带原文链接，保证可回溯。

OpenClaw 侧用 agent 的定时任务调度，加上 MCP 的 fetch 类工具做抓取即可，管线本身几百行脚本的事。

## 踩坑点

- **全文缺失**：很多源只给前 200 字，摘要质量天然差。对重点源补一步正文抓取，但注意编码——我踩过 GBK 和 HTML 实体没处理的坑，摘要全是乱码。
- **多源同事件**：先按 URL 规范化 + 标题相似度合并，再对合并后的簇做一次摘要，token 直接省一半，阅读体验也更好。
- **幻觉约束**：prompt 里明确"只允许使用原文信息"，要求引用支撑原句，并每周抽查 10% 的输出。
- **时间戳陷阱**：各源时区混乱，别用"当天日期"过滤，用"上次成功抓取时间"做水位线，否则总会漏条目。
- **成本**：不要在摘要阶段用最强模型处理全部条目，粗筛 + 按需升级才可持续。

## 可复用建议

- 状态库是整条管线的地基，优先级高于任何模型调优。
- Prompt 放进仓库做版本管理，和代码一起 review、一起回滚。
- 定义一个最简单的验收指标：每周人工抽样标注"值得读"的命中情况。没有这个闭环，摘要质量只会悄悄漂移。
- 先窄后宽：信息管线的价值在信噪比，不在覆盖面。源越多越要克制。

## 总结

这套东西代码量不大，真正的工作量在去重逻辑、输出约束和验收机制。RSS 提供稳定的输入契约，AI 只负责压缩，保持每一步可观测、可回溯，信息流才不会退化成"AI 二次噪声"。
