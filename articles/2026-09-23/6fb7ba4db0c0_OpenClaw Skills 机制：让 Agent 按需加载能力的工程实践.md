## 背景

用 Agent 做日常自动化一段时间后，最直观的瓶颈往往不是模型能力，而是上下文。早期我把所有工具说明、MCP 使用约定、操作规范全塞进系统提示词，结果 token 开销随能力数量线性增长，长会话里模型经常"忘记"某条约定，或在几十条描述里选错工具。

OpenClaw 的 Skills 机制针对的就是这个问题：能力不预先全量加载，而是按需渐进注入。核心是三层结构——**元数据**（name + description，常驻索引，开销很小）、**SKILL.md 正文**（任务命中后才读入）、**正文引用的脚本和资源**（真正用到才执行或读取）。本质上是把"能力路由"从模型记忆挪到了检索层。

## 问题

具体要解决两件事：

1. 提示词膨胀：所有指令常驻上下文，成本和注意力干扰都随能力增多而恶化；
2. 手动切换成本：每个会话手动开关 MCP server、粘贴操作手册，不可复用、不可沉淀。

## 做法

以我沉淀的一个"日志排障" skill 为例：

1. 在 workspace 的 skills 目录下建文件夹，写 `SKILL.md`。frontmatter 里 name 用小写短横线（如 `log-triage`），description 是路由关键：**用用户实际会说的话描述触发条件**，中英文问法都覆盖。
2. 正文控制在几十行内，写成 runbook：先跑什么命令、看哪几项指标、什么情况升级。只写指令性内容，不写背景科普。
3. 复杂逻辑配可执行脚本，SKILL.md 只写"何时调用、参数含义"。模型执行脚本而不是现场生成代码，稳定性和 token 双省。
4. 重启 gateway 或开新会话刷新索引，然后测试：先显式点名 skill，再换成自然说法，确认隐式触发也命中。
5. 翻日志确认每轮实际加载了哪些 skill，以此为依据迭代 description。

## 踩坑点

- **description 写得太抽象就不触发**。"帮我处理日志"这种写法路由不起来，它是匹配用的配置，要按任务现场语言写，覆盖多种问法。
- **skill 多了以后描述互相重叠**，会选错或重复加载。一个 skill 只管一个工作流，按场景拆，不按工具拆。
- **SKILL.md 越写越长等于把膨胀换个地方**。长参考资料拆成独立文件，正文只留路径，用到再读。
- **改完不重启，新会话还是旧索引**，很容易误判"没生效"。
- **别把密钥写进 SKILL.md**——正文会被读进上下文，敏感信息走环境变量。

## 可复用建议

- 把 description 当接口契约维护：它是检索的输入，改动要像改 API 文档一样谨慎。
- 一个 skill = 一个可完成的任务闭环；能用脚本固化的步骤就固化成脚本。
- skills 目录直接进 git，随工作区一起版本化，方便回滚和团队共享。
- 定期看加载日志：从不触发的去补触发词，总误触发的去收窄描述。

## 总结

Skills 机制的价值不在"能装插件"，而在把 Agent 能力组织成可检索、可按需加载的单元。工程上可以理解成两层：description 是路由层，SKILL.md 正文是 runbook 层。把这个边界守清楚，能力越多，上下文反而越干净——这是我实际跑下来最直接的收益。
