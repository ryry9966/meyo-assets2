## 背景

OpenClaw 的 agent 日常会跑大量自动化任务：定时摘要、消息分流、插件结果整理、MCP 工具输出的解析。这些活如果全走旗舰云模型（GPT-4o / Claude 这类），成本和延迟都不划算；但如果全压到本地小模型，复杂任务的工具调用准确率会明显掉。多模型路由要解决的就是这个分配问题。

## 问题

实际使用中困惑往往集中在三点：

- 哪些任务可以安全降级到本地模型
- 降级后失败了怎么兜底
- 怎么确认降级没有伤到输出质量

## 做法

**1. 按任务分层做路由表。** 我们的做法是分三级：

- L0：高频轻任务（摘要、格式转换、简单问答兜底）→ 本地模型，比如 Ollama 跑 qwen2.5 7B 或 deepseek 蒸馏版
- L1：常规 agent 任务、单工具调用 → 云端中档模型
- L2：多步规划、长链路工具编排、代码生成 → 旗舰云模型

**2. 配置层面按 agent 分工。** OpenClaw 的多 agent 结构天然适合这个玩法：轻 agent 挂本地模型处理高频事务，重任务 agent 走旗舰模型，skills 和 MCP 工具按重要性分配到对应 agent。

**3. 显式升级链。** 本地模型先跑，触发以下任一条件就把完整上下文透传给云端重跑：输出 JSON 解析失败、工具调用参数不合法、超时、规则判断置信度低。注意是透传**完整上下文**，不是只发错误信息，否则云端模型等于盲跑。

**4. 加观测。** 每个请求记一个 `model` 字段，周报看各模型的任务分布、失败率和 token 消耗，路由决策才有依据。

## 踩坑点

- **本地模型上下文窗口小。** 长 MCP 工具输出直接被截断，工具调用静默失败。我们在网关层对超长输出先做裁剪/摘要再喂给本地模型。
- **工具调用格式差异。** 部分本地模型的 function calling 输出不规范，OpenClaw 解析失败就跳过工具，表现为“模型突然变笨”。切路由前一定要小流量验证工具调用成功率，而不是只看对话质量。
- **本地不一定快。** GPU 被其他进程占着时，本地推理延迟反而比云端高。路由策略不能建立在“本地=快”的假设上。
- **升级链失控。** 本地失败→云端失败→重试风暴。升级链要设硬上限，我们目前最多两级，超过就落盘告警。
- **Prompt 不可移植。** 同一份 system prompt 在两个模型家族上表现差异很大，关键格式约束最好按模型家族各写一版。

## 可复用建议

1. 切路由前用 20~30 个代表性任务跑固定测试集做基线，别凭感觉。
2. 升级条件写成显式规则，可执行、可审计，拒绝“看起来不对就升级”。
3. 本地模型锁定量化和版本号，别让模型管理器自动更新把基线换掉。
4. 预算敏感场景，把 L2 任务的 token 上限也写进配置，超限降级到 L1。

## 总结

多模型路由的本质是三件事：**任务分级 + 显式升级规则 + 可观测**。OpenClaw 不需要额外的路由网关，用多 agent 挂不同主模型就能落地，中间用明确的失败条件衔接。先把路由表和日志跑起来，数据攒两周，再谈调优——顺序别反了。
