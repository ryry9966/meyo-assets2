## 背景

团队要求每天一份日报，内容涵盖服务异常、任务执行情况、变更记录。写日报本身不难，难的是"每天坚持写得不走样"。我们用 OpenClaw 的定时任务加 MCP 工具把这件事彻底自动化，跑了三周、输出稳定之后，才敢说这套流程站住了。这里记录做法和踩过的坑。

## 问题

原始信息散在几处：服务运行日志、agent 任务执行记录、CI 与部署事件。靠人工汇总有三个明显问题：

1. 信息分散，靠记忆拼凑容易漏；
2. 口径不一，今天的"严重"和昨天的"严重"可能不是一回事；
3. 一到高峰期，日报最先被牺牲。

## 做法

整体思路是分层：确定性的事情交给脚本，需要"理解"的事情才交给模型。

**第一步：归集与规范化。** cron 脚本每天凌晨拉取前一天日志，统一转成 JSONL，字段固定为 `timestamp / source / level / event / duration / status`。纯脚本，不涉及模型。

**第二步：预聚合。** 另一个脚本对 JSONL 做统计：错误按类型计数取 Top 5、任务成功率、耗时分布、变更条数，产出一个几 KB 的聚合 JSON。

**第三步：结构化抽取与叙述。** Agent 只读聚合 JSON（不碰原始日志），必要时通过 MCP 工具补充上下文（比如某次部署的 commit 列表），按固定模板填空：概况、异常明细、趋势备注。模板里每个段落都对应 JSON 里的一个字段。

**第四步：校验与分发。** Agent 输出先过 JSON Schema 校验，不合格就带错误信息重试一次（上限两次）；通过后渲染成 Markdown，推送到群 webhook，同时按日期存档到仓库。

## 踩坑点

- **别让模型直接读原始日志。** 第一版我们这么干，token 消耗大，模型还会"脑补"日志里不存在的因果。改成脚本聚合后，模型只负责把数字写成通顺的句子，幻觉基本消失。
- **时区。** 容器里的 cron 跑在 UTC，日志时间戳是东八区，第一天日报漏掉了晚上八点后的全部事件。结论：用带时区的窗口切割，别依赖运行环境默认时区。
- **格式漂移。** 模型偶尔自由发挥，加一段模板外的"建议"。加 Schema 校验后强制回模板——格式稳定，横向比对才有可能。
- **静默失败最危险。** 流水线挂掉那天群里没有日报，反而有人以为"今天没事"。改成：日志为空也发一份"今日无事件"；流水线自身异常则发错误通知。空报告本身是信息。
- **Top N 之外的盲区。** 低频但严重的错误可能被截断。聚合时保留"其他"桶，报告末尾附原始日志链接兜底。

## 可复用建议

- 能用脚本算的数字不要让模型算，模型只做叙事和异常解读；
- 报告模板当代码维护，配 Schema 校验，重试要有上限；
- 中间产物（规范化 JSONL、聚合 JSON）落盘保留，方便回溯和重跑某一天；
- 日报流水线自己也要有监控：心跳加空报告兜底。

## 总结

这套流水线的核心不是"用 AI 写日报"，而是把日报拆成**取数—聚合—叙述—校验—分发**五段，只在叙述段引入模型。三周跑下来，日报从每天约 20 分钟人力降到零介入，且格式稳定可比。对想做类似自动化的同学，建议从小切口开始：先自动化最格式化、最重复的部分，跑稳后再逐步扩展范围。
