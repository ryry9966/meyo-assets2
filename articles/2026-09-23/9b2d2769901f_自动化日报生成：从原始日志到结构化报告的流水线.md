## 背景

团队每天要发的运维/项目日报，多数还是人肉流程：翻日志、拉数据、贴模板、补几句分析。重复度高、格式固定，却没人愿意做，还容易漏掉真正的异常。我们在 OpenClaw 上搭了一条日报流水线：定时采集原始日志 → 规则清洗聚合 → Agent 归纳分析 → 模板渲染 → 自动投递。跑了月余，稳定性和准确度都到了可用水平，这里把做法和坑整理出来。

## 问题

最初思路很简单：脚本把当天日志全量丢给模型，让它"总结成日报"。实际跑下来有三个硬伤：

1. **上下文装不下**。一天的日志动辄几十万行，截断后模型看到的只是碎片，总结失真。
2. **幻觉难验证**。原始日志没有结构，模型的"结论"对不回原始数据，出错没人发现。
3. **输出不稳定**。同一批日志两次生成的报告结构都不一样，下游没法自动消费。

结论：让模型从零读原始日志，方向就不对。

## 做法

流水线分四层，核心原则是**规则做确定的事，模型做归纳的事**。

**1. 采集层。** 用 OpenClaw 定时任务或系统 cron，拉取过去 24 小时的服务日志、变更记录、告警事件，按日期落盘。这一步不用模型。

**2. 清洗聚合层。** 纯规则脚本：解析日志行，按错误码/模块分类，去重计数，抽取次数、起止时间、影响服务等字段，输出结构化 JSON。比如"checkout 服务 500 错误 47 次，集中在 14:02–14:19"。这份 JSON 是全流程的事实基础。

**3. Agent 层。** 数据查询封装成 MCP 工具（查聚合结果、查历史同期、查变更单），Agent 的职责被收窄为：基于 JSON 写"异常分析"和"建议"两段。提示词里明确要求只引用 JSON 中已有的数字，不新增事实。

**4. 渲染投递。** 报告主体是固定模板，数字部分由脚本直接填充，模型只负责两段分析文字。渲染后走 webhook 投递到群，本地同时归档一份 Markdown。

## 踩坑点

- **时区与时间窗口**。采集最初用 UTC 算"昨天"，与团队时区差了 8 小时，日报里的"今天"其实是别人的昨天。窗口计算收敛到一处，别散落在各个脚本里。
- **重复投递**。重试机制遇上网络抖动，同一个群收到两份日报。投递环节加了幂等键（日期 + 版本号），同键拒绝重发。
- **敏感信息**。日志里有用户 ID 和内网 IP，脱敏必须放在清洗层，即进入模型之前。事后处理来不及——中间产物已经落盘了。
- **Agent 工具调用失败**。MCP 工具偶发超时，最初整条流水线跟着挂。改成：分析段生成失败时填入占位文案并标注"待人工补充"，日报照发，降级状态显式写在报告头部。

## 可复用建议

1. **中间产物落盘**。清洗后的 JSON、渲染前的模板数据都存档，出问题能定位到具体一层重跑，不必从头来。
2. **收窄模型职责**。模型只写分析，事实与数字全部来自规则层，报告的可验证性会高很多。
3. **模板先行**。先和读报告的人定好固定结构，再决定哪些槽位交给模型，顺序别反。
4. **报告带版本与状态位**。降级、数据源缺失、重跑都显式标注，别让下游猜。

## 总结

这条流水线没有用到什么精巧的模型技巧，价值主要来自工程分层：采集、清洗、归纳、渲染各司其职，模型被限制在它擅长且可校验的环节。"规则出事实 → Agent 出解读 → 模板出交付物"这个结构，可以直接平移到周报、告警复盘等场景。建议先跑通最小闭环，再逐步扩展数据源。
