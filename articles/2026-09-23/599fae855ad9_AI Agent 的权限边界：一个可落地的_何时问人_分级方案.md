## 背景

Agent 接上 MCP 和插件之后，能力上限不再是"生成文本"，而是"执行动作"：读写文件、调 API、改配置、发消息。能力上去了，新问题也来了——每步都问人，人类成了瓶颈，Agent 退化成一个昂贵的输入法；每步都不问，一次误操作就可能把生产配置清掉。权限边界本质上是把"信任"工程化的问题，靠 prompt 里写一句"请谨慎操作"是解决不了的。

## 问题

实际项目里常见两个极端：

- **全确认模式**：每个工具调用都弹确认。前三天用户还认真看，第七天开始无脑点"允许"，确认机制形同虚设。
- **全自动模式**：Agent 拿到数据库写权限后自主"清理"数据，删了它认为冗余的表。事后复盘发现，模型对"风险"的自评完全不可靠。

核心矛盾：确认太频繁会失效，太少会出事。需要的是一个可执行的分级标准，而不是拍脑袋。

## 做法

我们把工具按两个维度分级：**可逆性**（能否撤销）和**影响半径**（出错波及范围）。

1. **只读操作**：查询、搜索、读文件。默认自动执行，记审计日志即可。
2. **可逆的小范围写入**：写草稿、改测试环境、创建带前缀的文件。自动执行，但必须可回滚（版本化、软删除、命名隔离）。
3. **不可逆或大半径操作**：删数据、生产变更、对外发消息、付费 API。必须人工确认，且确认时带上下文：改什么、为什么、怎么回滚。
4. **禁区**：支付、权限变更、合规相关。Agent 只准备方案，执行永远留给人类。

工程上落成三件事：

- MCP 工具注册时打上风险等级元数据，Agent 侧按级别路由：auto / confirm / deny；
- 确认门禁不只返回"是/否"，要展示 diff 或操作摘要——人看到的是"将删除 orders 表 3200 行"，而不是"是否调用 delete_tool"；
- 给自动执行加预算：单位时间调用次数、单次成本上限，超限自动降级为确认模式。

## 踩坑点

- **确认疲劳**：确认请求一旦超过每分钟几次，人类就变成自动批准器。宁可在源头减少确认点，也不要稀释确认的分量。
- **批量操作一次放行**：Agent 说"我要执行 50 个删除"，一次确认等于放行 50 次危险调用。批量要么拆分，要么整体按高风险处理。
- **让模型自评风险**：不可靠。风险等级必须是人写死的配置，模型只能引用，不能覆盖。
- **确认超时没定义**：审批挂在队列里几小时，Agent 要么傻等要么重试导致重复执行。超时策略要显式写清。
- **"问人"这个动作也有副作用**：如果"问"的实现是往群里发消息，确认请求本身就可能打扰真实客户。问询通道要和业务通道隔离。

## 可复用建议

- 新接插件一律从只读跑两周，观察它真实调用了什么，再逐级放开。
- 审计日志同时记"自动执行了什么"和"为什么请求确认"，后者是调边界最值钱的数据。
- 高风险工具必须先有回滚方案，再接入 Agent。
- 定期回看：被确认拦下的操作里，如果九成本来是安全的，说明边界太紧；反过来一次都没拦下，要么太松，要么 Agent 根本没在干活。

## 总结

权限边界不是一道墙，而是一把随使用数据持续调整的滑动标尺。原则就一句：**错误可逆且影响小，让它自己干；不可逆或影响大，把决定权还给人类，并给人类足够的上下文做判断。** 先小后大、先读后写、配置先于模型判断——这套做法在我们几个自动化项目里都稳住了。
