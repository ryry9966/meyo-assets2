## 背景

过去几个月我们把 OpenClaw 的几条自动化流从「全 GPT」逐步迁到「本地 + 云端混合」。动机很朴素：全 GPT 的月账单涨得比任务量快，涉及内部数据的流程走云端还有合规顾虑；但反过来全换本地模型（Ollama 跑 Qwen / Llama 系）之后，多步工具编排类任务的首过成功率明显下滑。

## 问题

真正的难点不是「哪个模型强」，而是任务本身异构。同一个 agent 里既有摘要、抽取、格式化这类低复杂度高频任务，也有需要跨多个 MCP 工具推理、规划的多步任务，插件产出的结构还各不相同。一刀切的路由，要么浪费钱，要么浪费质量。

## 做法

我们的路由分三层：

1. **静态规则层**：按任务类型路由。先翻一周的运行日志，给每条记录打标——任务类型、token 数、首过是否成功，据此列路由表：摘要/翻译/简单抽取 → 本地；规划、多工具编排、超长上下文 → GPT。
2. **校验与回退层**：本地先行，输出必须过验证器（JSON Schema 校验、工具调用参数检查、插件侧格式检查），失败则升级到 GPT，并记录升级原因。
3. **预算层**：交互式链路优先低延迟（本地常驻），后台批处理允许排队走便宜路径。

路由表放配置里，别写死在代码：

```yaml
routes:
  - match: { task: [summarize, extract, translate] }
    model: local-qwen-14b
  - match: { task: [plan, orchestrate], tools_gt: 2 }
    model: gpt-4o
    fallback_chain: [local-qwen-14b]
```

## 踩坑点

- **函数调用格式差异**：本地模型常输出「接近 JSON」的串，解析器直接崩。别指望模型自觉，验证器 + 修复重试是必需品。
- **上下文长度错配**：本地 8k/32k，云端 128k。MCP 工具返回的长结果被静默截断后，agent 基于残缺信息做决策，表现像「模型变笨」，实际是路由层没拦住超长输入。
- **冷启动与显存争抢**：Ollama 首次加载动辄十几秒；embedding 和 LLM 同卡并发还容易 OOM。常驻模型 + 显存预算要提前规划。
- **回退风暴**：无上限的升级重试会让账单翻倍，每个任务设升级次数上限和退避。

## 可复用建议

- 按任务类型 + 校验结果路由，不按「信仰」路由。
- 每个任务记录：类型、模型、验证结果、token、延迟。一个月后用数据说话，比拍脑袋准。
- 敏感数据链路直接关掉云端回退，宁可失败也不要静默外发。
- 每月回顾一次路由表，任务分布会漂移，规则不更新就会失效。

## 总结

多模型路由本质是个运营问题而非选型问题：规则 + 校验起步，用日志驱动迭代。先跑通「本地处理高频简单任务、云端兜底复杂编排」这条基线，再谈精细化。我们目前的混合方案把月成本压到原来的四成，首过成功率反而略升——主要功劳在验证器，不在模型。
