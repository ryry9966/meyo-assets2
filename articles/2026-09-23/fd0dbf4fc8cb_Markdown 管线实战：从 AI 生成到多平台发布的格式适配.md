## 背景

用 OpenClaw 这类 Agent 做内容自动化时，产出的标准格式是 Markdown。但"生成完"和"发出去"之间隔着一段经常被低估的工作量：公众号不支持标准 Markdown，知乎对 HTML 白名单卡得很严，掘金和静态博客相对宽松，图片防盗链、代码高亮、数学公式又是各玩各的。如果最后一步靠手工复制粘贴，自动化就断在了一公里外。

## 问题

实践中差异集中在三个层面：

1. **AI 产出不"干净"**：常混入内联 HTML、深层嵌套列表、脚注、任务列表，各平台渲染器支持度参差不齐。
2. **平台能力不对称**：语法子集（表格/脚注/公式）、样式能力（公众号只认内联 style）、资源策略（图片必须转存到自己素材库）三个维度互相独立，排列组合很多。
3. **正则改写不可靠**：直接对原始文本做替换，嵌套结构和代码块内容极易被误伤，且难以回溯排查。

## 做法

核心原则：**以 AST 为单一事实源，一次解析，多端渲染。**

1. **归一化**：用 remark 或 markdown-it 把原始输出解析成 AST，先做清洗——剥掉 frontmatter、折叠内联 HTML、限制嵌套深度，得到规范 Markdown。
2. **生成端约束**：在 Agent 的系统提示里直接限定语法子集（只用 GFM、禁内联 HTML、表格不超 N 列）。源头约束比事后修复便宜得多。
3. **平台适配器**：每个目标平台一个 renderer，吃同一份 AST。公众号适配器负责样式内联、公式转 SVG、超宽表格转图片；掘金/博客适配器基本直出。
4. **资源处理**：把"图片转存""发布到某平台"分别封装成独立的 MCP 工具，带重试，Agent 只做编排。
5. **发布前 lint**：对目标平台跑语法白名单校验，不通过就拦截，把错误回传给 Agent 修正，而不是带病发布。

## 踩坑点

- **正则处理 Markdown 是重灾区**：嵌套列表和代码围栏内的文本必被误伤，变换务必在 AST 层做。
- **公众号会剥掉 `<style>` 标签和 class**：只认内联 style，代码高亮需要把 token 展开成带内联颜色的 span，工作量不小但躲不掉。
- **图片防盗链**：GitHub 和多数图床外链在公众号里直接裂图，必须转存到素材库；转存接口有频率限制，用内容 hash 做去重键保证幂等。
- **数学公式**：绝大多数平台不渲染 KaTeX/MathJax，统一转 SVG 图片最稳。
- **登录态过期是常态**：发布节点要能区分"格式失败"和"鉴权失败"，否则重试逻辑会无限空转。

## 可复用建议

- 每平台的**语法白名单做成配置文件**，lint 和 renderer 共用同一份，避免两处规则漂移。
- 用 **golden file 快照测试**：固定输入 AST，比对各平台渲染产物，平台规则一变立刻暴露。
- 全管线**幂等**：同一次生成重复发布不产生重复内容，重试才安全。
- 内容 ID 贯穿全链路，日志按 ID 串联，排查"哪一步改坏了格式"才有抓手。

## 总结

多平台发布本质上是个编译问题：Markdown 是源码，AST 是中间表示，各平台 renderer 是后端。把适配逻辑收敛到 AST 层，把约束前置到生成端，把失败拦截在发布前——管线就能从"能用"走向"稳定"。这套结构不绑定具体平台，换目标站点时只需要新写一个 renderer 和一份白名单。
