## 背景

团队每天需要一份运维/业务日报：昨天错误多少、部署了什么、有没有异常事件。之前的流程是人工 SSH 上服务器 grep 日志，复制到文档里再润色一遍，每天稳定花 40 分钟，还经常漏。这篇文章记录我把它改造成自动化流水线的过程：三个脚本、一个定时任务、一个模板，现在每天只剩“扫一眼”。

## 问题

拆开看，人工日报的痛点有三个：

1. **日志分散**：nginx、应用日志、git 提交记录、CI 结果散在不同机器和不同格式里；
2. **汇总费时易漏**：格式不统一，靠肉眼扫容易漏掉关键错误；
3. **直接丢给模型不可行**：一整天的原始日志塞进上下文，token 爆炸，重点被淹没，模型还容易在细节上幻觉。

## 做法

核心思路是**分阶段流水线，每个阶段读文件、写文件**，模型只处理聚合后的结构化数据：

1. **采集**：systemd timer 定时拉取当天日志，按日期落盘到 `data/raw/YYYY-MM-DD/`；
2. **归一化**：用 jq/awk 把各种格式转成统一 JSONL，字段固定为 `timestamp / source / level / event / count`；
3. **聚合**：一个统计脚本产出 `rollup.json`，包含错误 TopN、请求量趋势、部署记录、异常事件列表；
4. **生成**：OpenClaw 的定时任务读取 `rollup.json`，按固定 Markdown 模板生成日报。模型只做归纳和措辞，不做任何计算；
5. **交付**：推送到 Telegram 群，同时归档到 git 仓库，方便回溯。

关键一条：**数据先变小，再进模型**。

## 踩坑点

- **时区**：服务器是 UTC，日报按本地时区切天，凌晨的日志算错了天。最后在采集阶段就统一按本地时区打标，后面不再碰时区。
- **日志轮转**：logrotate 半夜切割，当天数据散在两个文件里。改成按行内时间戳过滤，而不是按文件名。
- **输出格式漂移**：一开始让模型自由发挥，第三天格式就变了。改成模板 + 槽位填充，模型只填变量，结构永不变形。
- **静默失败**：某次模型调用挂了，日报没生成，也没人发现。补了心跳机制：成功推日报，失败推错误消息，宁可吵也不要静默。
- **重复推送**：补跑数据时发出两份日报。现在日报文件名带日期，已存在即跳过，保证幂等。

## 可复用建议

- 各阶段做成独立脚本，中间产物全部落盘，任何一环出问题都能单独调试、单独补跑；
- 报告结构定义成 JSON schema（或固定模板），和 prompt 一起进版本控制，改动可 review；
- 确定性的活（采集、清洗、统计）交给脚本，不确定性的活（归纳、措辞）才交给模型；
- 日报末尾附一个原始数据归档的链接，需要深挖时能一键回查。

## 总结

这条流水线没有用任何复杂框架，本质是“脚本 + 定时器 + 模板”的组合，但收益很实在：每天 40 分钟的人工缩减到 1 分钟的检查。经验可以浓缩成一句话——**不要让模型看原始日志，让模型看统计结果**。管道里每一层只解决一个问题，出问题时你才知道该去查哪一层。

欢迎在评论区交流你们的日报/周报自动化实践，特别是多人团队的版本。
