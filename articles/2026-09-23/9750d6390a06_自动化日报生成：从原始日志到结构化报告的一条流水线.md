## 背景

团队的"日报"通常散落各处：服务日志、git 提交、CI 记录、Agent 会话日志，加上 IM 群里的零散讨论。每天人肉汇总费时且容易漏。我的目标很朴素：让机器每天定时跑一遍，产出一份格式稳定、数据可回溯的 Markdown 日报，推送到群里。整条流水线挂在 OpenClaw 的定时任务上，采集和推送各写了一个小插件，中间的清洗聚合是纯脚本。

## 问题

最初的做法很直接：把当天日志整坨塞给模型，让它"总结一下"。跑了一周暴露出三个问题：

1. **噪音太大**。心跳、DEBUG、重试日志占了 90% 以上的 token，摘要质量差且贵。
2. **输出不稳定**。有时表格有时段落，关键字段时有时无，没法归档对比。
3. **数字不可信**。模型会"顺手"给出一个错误率，事后核对对不上。

结论：LLM 不适合做采集和统计，只适合做最后的归并与措辞。数据必须先变成结构。

## 做法

流水线拆成五步，每步独立，中间产物全部落盘：

1. **采集**：三个适配器分别拉日志增量、git log、Agent 会话记录（内部工单走 MCP 接入），统一输出 JSON 事件：`{time, source, project, type, payload}`。
2. **清洗**：规则过滤——去重、丢 DEBUG 和心跳、合并 30 秒内的重试。日志体积压到原来的 5% 左右。
3. **聚合**：按项目分组，算出事件数、失败数、耗时分布，输出纯统计 JSON，不含自然语言。
4. **摘要**：统计 JSON 交给 LLM，提示词明确"所有数字必须原样引用，禁止计算和推测"，输出约束到固定 JSON schema，校验失败重试一次。
5. **渲染推送**：模板渲染成 Markdown（昨日概览 / 异常与风险 / 各项目明细 / 数据来源索引），经通道插件推送，同时归档到按日期命名的目录。

每天 09:05 跑一次，覆盖前一个自然日。

## 踩坑点

- **时区**：源日志是 UTC，日报按本地时区切天，第一版把凌晨告警算进了前一天。现在采集层统一转带时区时间戳，聚合层只按业务日切分。
- **重跑幂等**：一次推送失败后手动重跑，群里出现两份日报。现在每次运行先按日期查重，已存在则覆盖归档并标记修订版。
- **静默失败**：流水线挂了没人知道，第二天群里没日报才被发现。加了一个独立心跳：09:30 检查产物文件，缺失即告警。空数据也要发报告，写明"当日无记录"，而不是不发。
- **上下文超限**：项目多了统计 JSON 也超长，改成 map-reduce——先按项目分别摘要，再合并一次。

## 可复用建议

- 阶段之间只通过 JSON schema 通信，任何一步都能单独重跑和单测，这是流水线能长期维护的关键。
- 原始日志和中间产物按日期留档，出问题可回放到任意一步。
- 数字一律由聚合层产生，LLM 只做归并与措辞——这条约束值得写进提示词和评审标准。
- 先接一个数据源跑通全链路，再横向扩展适配器，不要一上来就搭大而全。

## 总结

这套东西没用什么复杂框架，核心就三句话：结构化前置、LLM 后置、每步落盘可重放。上线两个月，日报从每天约 20 分钟人工变成一次核对，模型调用量比最初方案降了一个量级。如果你也有散落各处的日志和一份每天要交的汇总，建议从清洗规则和输出 schema 这两件事开始动手，其余环节都是水到渠成。
