## 背景

OpenClaw 里跑多 Agent 任务时，主会话负责拆解任务、分发指令，子 Agent（通过 spawn 或 MCP 工具调用拉起）负责具体执行。默认配置下，子 Agent 与主会话共享上下文链路，执行过程中的工具调用、中间推理、报错信息都会往主会话里灌。

## 问题

我们在一个自动化巡检插件里第一次踩到：某个子 Agent 连续调了十几次 MCP 工具，主会话上下文直接被撑爆，后续对话里主 Agent 开始“记得”一堆与自己无关的中间步骤，回答质量肉眼可见地下降，token 消耗翻倍。症状归纳：

- 主会话上下文膨胀，长对话后响应变慢；
- 子任务的中间结论混进主 Agent 的决策，把方向带偏；
- 子 Agent 的报错堆栈原样进入主会话历史；
- 多个子 Agent 并发时互相覆盖共享状态。

## 做法

1. **spawn 时显式声明隔离**。在子 Agent 的启动配置里打开 session 隔离（不同版本字段名略有差异，常见是 `isolated: true` 或指定独立 `session_id` 前缀），确保它拿到独立会话文件，而不是继承主会话句柄。

2. **简报进，摘要出**。给子 Agent 的输入只带三样：任务描述、涉及文件路径、必要约束。回收时只取结构化摘要（结论 + 关键路径 + 是否成功），不回收完整 transcript。

3. **工作区分离**。子 Agent 的 scratchpad / 临时目录按任务粒度分配，避免并发子 Agent 写同一目录，任务结束后按策略清理或归档。

4. **验证隔离生效**。用 `openclaw sessions list`（或对应版本的会话查看命令）确认子 Agent 是独立会话条目；跑一次典型任务，对比前后主会话上下文大小的差异。

5. **MCP 工具侧收敛**。给子 Agent 挂的 MCP server 裁剪工具集，只留任务所需，减少无关调用往子会话写数据。

## 踩坑点

- **隔离 ≠ 断联**：隔离的是会话，不是信息。输入简报给少了，子 Agent 输出跑偏，反而多轮返工，总成本更高。
- **结果回灌**：最容易犯的错——子 Agent 跑完后把完整输出原样贴回主会话，隔离等于白做。务必在主 Agent 侧只解析摘要字段。
- **环境与密钥继承**：子 Agent 默认继承主会话的环境变量，执行不信任的任务前记得裁剪。
- **僵尸会话**：异常退出的子 Agent 会留下孤立 session 文件，建议用定期清理脚本兜底。

## 可复用建议

- 把 spawn 配置做成模板：隔离开关、工具白名单、输出 schema 三件套固定下来，新任务直接套；
- 给子会话打任务标签，方便事后审计和排障时快速定位；
- 在 CI 里加一条检查：主会话上下文增长超过阈值就告警，能提前发现“回灌”类问题。

## 总结

session 隔离的本质是控制信息流：子 Agent 需要的上下文显式传入，产生的结果显式回收摘要，其余过程数据留在自己的会话里。做到“简报进、摘要出、工作区分离”，主会话就能保持干净，多 Agent 流水线才跑得稳。有不同做法欢迎在评论区交流。
