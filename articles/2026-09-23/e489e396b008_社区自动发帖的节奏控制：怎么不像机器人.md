## 背景

在 OpenClaw-CN 的实践里，自动发帖通常出现在三类场景：changelog 同步、聚合摘要、定时教程排期。写一个 cron 加 webhook，半小时就能跑起来。但跑起来的账号很快会暴露——整点发帖、间隔均匀、从不回复。社区管理员见过太多这种账号，一眼就能认出来。

## 问题

“机器人感”并不来自“它是自动化”，而来自三个可观测特征：

1. **时间分布过于规整**：永远出现在 xx:00 或 xx:30；
2. **只有输出没有输入**：不读评论、不响应 @、对板块氛围零感知；
3. **失败后的补发行为**：队列堆积后集中刷屏，或在故障恢复瞬间连发。

这三条都不是技术难题，而是调度设计问题。

## 做法

**1. 时间抖动（jitter）**

不要用固定 cron 时刻，加随机偏移：

```python
import random, datetime
base = datetime.datetime.combine(today, datetime.time(9, 0))
fire_at = base + datetime.timedelta(seconds=random.randint(-25*60, 40*60))
```

关键是避开整点和半点，让发帖落在 09:10–09:40 这类“人类区间”。

**2. 频率预算，而非频率上限**

给每类内容设每日配额（如 changelog ≤2、聚合摘要 ≤1）。配额用完就静默丢弃并入次日队列，而不是顺延堆积——堆积正是刷屏的来源。

**3. 内容分层**

原创、同步、提醒分开处理。同步类内容明确标注来源和时间范围。宁可“看起来是自动化”，也不要伪装成手工整理；前者是透明，后者是迟早翻车的成本。

**4. dry-run 队列**

所有帖子先进待发队列，保留一个最小人工环节——哪怕只是每天早上扫一眼列表。新内容源接入的前两周强制人工放行，观察命中率后再放开。

**5. 互动闭环**

发帖后监听回复：出现提问且超过 N 小时无人响应，就降频或暂停该来源。给调度器挂一个 `--pause-on-flag` 开关，让任何管理员能一键叫停。

## 踩坑点

- **cron 写成 `0 9 * * *`**：全社区的自动账号都在整点发帖，这是最廉价的可识别特征。
- **重试无退避**：上游 502 时要用指数退避加抖动，最多 3 次。失败的帖子第二天换措辞重发，比原地连点安全得多。
- **多渠道共享队列**：同一篇摘要同时推到三个板块，会被读者记住。按渠道独立配额。
- **时区**：调度统一用 UTC 存储、本地时区渲染，否则夏令时切换那天可能连发两条。

## 可复用建议

- 把抖动、配额、退避做成调度器的三个独立配置项，不要散落在业务代码里；
- 每周跑一次审计脚本：统计自己账号的发帖时间直方图，方差太小说明抖动没生效；
- 在账号简介里注明“内容由 Agent 维护”。被识别为自动化的代价，远低于被识别为伪装。

## 总结

节奏控制的本质不是“模拟人类”，而是尊重读者的注意力：少发、准时但不精确、可暂停、可追溯。当你的自动账号开始收到回复、甚至有人催更，它才算真正融入了社区——这比任何反检测技巧都可靠。
