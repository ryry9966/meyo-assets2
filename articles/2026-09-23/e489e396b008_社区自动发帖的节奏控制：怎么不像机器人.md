## 背景

用 OpenClaw 挂一个定时 Agent，通过 MCP 工具往社区发日报、changelog、聚合摘要，是很多人上手自动化的第一个场景。跑通很容易，但跑两周就会发现问题：帖子每天 9:00:00 准时出现，结构一模一样，长度几乎相同，节假日也不停。用户未必说得出哪里不对，但"机器感"会直接压低互动，严重的还会被平台反垃圾规则盯上。

## 问题：机器人感来自哪

拆开看，暴露自动化的往往不是内容本身，而是节奏特征：

- 时间戳过于精确：cron 触发，秒级准时；
- 无休息时段：7×24 均匀输出，没有深夜和周末；
- 突发：一个事件触发后 1 秒内连发多条；
- 不看社区状态：没内容也硬凑一条；
- 失败重试变成重复轰炸。

## 做法：把节奏做成独立的限流层

我的做法是把"什么时候发、发不发"从业务 Agent 里拆出来，做成独立的 gate 服务，所有发帖请求都过这道闸。核心机制六个：

1. **抖动调度**：目标时间叠加随机偏移，比如 09:00 ±30 分钟内按高斯分布取值，避免每次卡整点。
2. **活跃窗口**：按星期配置可发时段（如工作日 9:00–22:00，周末只留一个下午），窗口外入队等待。
3. **配额与冷却**：每天硬上限（如 5 条），两条之间最小间隔 20–40 分钟随机取值，用令牌桶实现，超了就顺延。
4. **事件防抖**：commit、issue 这类触发源先聚合 10 分钟窗口再合成一条，而不是来一个发一个。
5. **空输出路径**：内容评分低于阈值直接跳过当天。这条比任何抖动都重要——人类运营也有没话说的时候。
6. **反馈降速**：记录每条的回复、点赞、被折叠/删除信号，负反馈超阈值就把全局频率系数乘 0.5，持续一天。

实现不需要复杂设施：一个 SQLite 存最近发帖时间和配额状态，一个 MCP 工具包装层在真正调用发帖前先向 gate 要"许可证"，拿不到就返回等待时长，Agent 自行安排下次尝试。

## 踩坑点

- **均匀随机 ≠ 自然**：全时段均匀抖动会产出凌晨四点发帖这种更可疑的模式，分布要贴合真实活跃时段。
- **时区坑**：服务器 UTC、社区 UTC+8，不显式声明时区，"活跃窗口"整体错 8 小时。
- **重试风暴**：失败后立即重试，叠加抖动反而制造间隔极近的重复帖。要用指数退避加幂等键。
- **补发堆积**：跳过的天数如果下次一口气补四五条，比准时更假。队列要有丢弃策略，过期内容直接放弃。
- **内容别随机过头**：结构和长度可以变，人设和语气要稳定，否则从"机器感"变成"精神分裂感"。

## 可复用建议

- 节奏参数全部配置化，按频道分 profile，从保守低频起步，看互动数据再加。
- 每次决策（post / delay / skip + 原因）落日志，复盘靠记录不靠感觉。
- 留一个 kill switch，一条命令全局静默。
- 心态上：目标不是伪装成人类，而是"不打扰"。该声明的 bot 身份照常声明，节奏控制解决的是质量与观感问题。

## 总结

自动发帖的"机器感"本质是节奏工程问题：抖动、窗口、配额、防抖、空输出、反馈降速，六个机制把 cron 的机械性磨掉。把限流独立成层，业务 Agent 保持简单，参数可调可复盘。上线头两周宁可少发——节奏收紧容易，社区信任丢了补不回来。
