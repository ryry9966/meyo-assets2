36kr 消息，GPT-6 这次一口气端上两个版本：主打高速响应的 Sol 和主打深度推理的 Luna，API 定价相比上一代直接腰斩。评论区一半在喊"真香"，一半在问"凭什么降得动"。这篇不聊情绪，拆三件事：双模型是什么打法、降价的成本账怎么算、以及落到开发者和普通用户头上，实际会变什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-23/4b1694516dfe3913.png)

## Sol 与 Luna：双模型是行业收敛后的标准打法

- 命名本身就在传递产品逻辑：Sol（太阳）对应"全天候在线、低延迟、随叫随到"的日常档；Luna（月亮）对应"慢下来、想得深"的重推理档。和 GPT-4o 与 o1 的组合、Claude 的 Haiku/Opus 分档、Gemini 的 Flash/Pro 是同一套思路——头部厂商已经用脚投票，放弃"一个模型打天下"。
- 背后是任务分层：大约 90% 的日常请求（改写、分类、信息抽取、简单问答）并不需要深度思考，用轻量模型又快又省；剩下 10% 的硬骨头（数学推导、复杂代码、多步 agent 规划）才值得动用重推理。举个例子：从合同里抽取关键条款，Sol 半秒搞定、几分之一美分；换成 Luna，时间和价格都翻几倍，但能把条款之间的冲突点也揪出来。选错档位，要么浪费钱，要么返工挨骂。
- 更值得注意的是自动路由：新一代 API 普遍支持系统先判断任务难度，再决定派 Sol 还是 Luna。对开发者来说等于"一个接口、两种大脑"，不用自己维护两套调用和降级逻辑。

## 价格腰斩，技术上靠什么降？

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-23/421d52230ca75537.png)

- MoE 稀疏化：Mixture of Experts 架构下模型总参数很大，但每个 token 只激活一小部分"专家"网络，算力花在刀刃上，推理成本接近按需付费。
- 蒸馏：用 Luna 这类重模型的输出当教材，把能力蒸馏进 Sol 这类轻量模型。上一代旗舰的能力，这一代用低一个数量级的成本复现——这是降价最大的底气。
- 推理优化全家桶：FP8 量化、KV cache 与 prefix caching、speculative decoding、continuous batching，单项各砍百分之几十的开销，叠起来就是数量级差异。
- 硬件与规模效应：新一代加速卡叠加自建推理集群，token 越多、边际成本越低，典型的高固定成本、低边际成本生意。
- 放进历史坐标看：GPT-4 发布时百万 token 输入约 30 美元；两年多后，能力相近的模型单价已跌进 1 美元区间，累计跌幅超过 95%。这次"腰斩"不是突变，只是这条陡峭下行曲线上最新的一段。

## 单价降一半，厂商为什么抢着降？

- 杰文斯悖论（Jevons Paradox）：蒸汽机效率提高后，煤的总消耗不降反升。token 同理——单价降 50%，愿意放手让模型跑的场景多了，总用量涨个五倍十倍，厂商总收入反而更大。
- 生态卡位：开发者的代码、prompt、缓存、评测流程都围着某家 API 建。先用低价把你请进来，之后的迁移成本就是你留下的理由。
- 数据与路由飞轮：调用量越大，真实任务分布的数据越多，路由判断和蒸馏效率越高，成本进一步下探——降价本身在喂养下一轮降价。
- 竞争现实：开源模型和激进定价的对手已经把地板价打了下来。这时候守利润率不如守调用量，份额比毛利更值钱。

## 对开发者和普通用户，变化落在哪

- 应用的单位经济学变了。以前一个 agent 循环跑 20 轮可能烧掉几美元，产品经理看了直摇头；现在成本进入"可以放手让它跑"的区间，长链条自动化任务才真正划算。粗算一笔：假设一次多轮客服会话消耗 2 万 token，单价腰斩直接让每千次会话成本减半，再叠加缓存命中，账单可能只剩原来的三分之一。
- 体验分层更细：日常对话 Sol 秒回，复杂问题自动升级 Luna，"免费档也够用"的分级产品变得可行。
- 但留意隐性成本：长上下文输入、多模态、高峰期限流，这些不一定体现在"单价"里，却决定实际体验和真实账单。

## 冷思考：三件事比"腰斩"更重要

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-23/99e7ac23ccf813c4.png)

1. 用自己的任务做基准，别只信发布会 demo。拿 50 条真实业务样本，对比新旧模型的成功率、延迟和成本，一小时就能算清楚要不要迁移。
2. 留一层 provider 抽象，但别过度设计。接口层做薄，方便随时切换；同时把单家的 prompt caching、批量折扣这些专属优化吃透——省钱的真正大头往往在这里，不在挂牌价。
3. 按场景算总账，而不是盯单价。"单价腰斩 + 用量翻十倍"是常见组合，账单完全可能不降反升；给每个场景设 token 预算和告警，比欢呼降价更像工程师的活法。

价格战对用户是短期福利、长期迁移题。龙虾钳已就位，评论区聊聊：你会先把哪条业务线迁过去？
