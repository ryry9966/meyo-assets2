## 背景

用 OpenClaw 做日常自动化一段时间后，最明显的瓶颈不是模型能力，而是执行节奏：主 agent 的工具调用是串行的，一个任务做完才轮到下一个。比如审查一个仓库里的十个模块、给二十篇文档生成摘要、同时对三个数据源做校验——每一项单独都不难，但串行跑下来动辄十几分钟。

OpenClaw 的 subagent 机制正好针对这个问题：主 agent 派生子 agent，各自独立运行，主 agent 负责拆任务和收结果。这篇记录我把它用进自动化流程后的做法和教训。

## 问题：什么任务适合并行

先泼冷水：不是所有任务都值得并行。判断标准只有三条——

1. 子任务之间没有数据依赖；
2. 子任务不会写同一个文件或同一份状态；
3. 拆分和汇总本身的成本低于省下的时间。

典型适合场景：批量审查、批量摘要、多方案对比、按目录切分的静态检查。不适合的：有前后依赖的多步构建、共享一份草稿的迭代写作。

## 做法

**第一步，串行验证拆分。** 我的标准流程是先让主 agent 串行跑两个子任务，确认拆分边界正确、prompt 自包含，再切成并行。跳过这步直接并行，错了就是几倍 token 的浪费。

**第二步，把子 agent prompt 写成"交接文档"。** Subagent 不继承主 agent 的对话上下文，这是最容易踩的坑。每个子 agent 的 prompt 必须自包含：目标、输入文件的具体路径、期望的输出格式。我会强制输出为固定结构的摘要（结论 + 关键发现 + 置信度），而不是自由发挥的长文。

**第三步，控制并发。** 实践中 3~5 个并发是比较稳的区间。再高，API 限流和成本上升来得很快，收益却边际递减。

**第四步，失败兜底。** 子 agent 超时或返回空结果时，主 agent 要有重试或降级逻辑——标记失败而不是中断整批。这要求子任务本身幂等，重跑不产生副作用。

## 踩坑点

- **写冲突**：两个子 agent 同时改一个文件，后写的覆盖先写的。解法是按文件切分任务，或只允许子 agent 读，写入统一回收给主 agent。
- **上下文爆炸**：让子 agent 返回全量输出，主 agent 收五份就撑爆了。必须约束返回摘要。
- **隐式依赖**：子任务 B 看似独立，实际依赖 A 产出的临时文件，并行后随机失败。串行预跑就是为了提前暴露这类问题。
- **成本失察**：并行让人感觉"变快了"，但总 token 消耗往往上升 30%~50%，值不值要看任务的时间价值。

## 可复用建议

- 只对读多写少、无共享状态的任务开并行；
- 子 agent prompt 当独立接口文档来写，输入输出都定死；
- 并发从 2 起步逐步加，观察限流和耗时曲线；
- 给每次 subagent 记录耗时和 token 消耗，跑几轮就能判断哪些任务值得编排、哪些串行更划算。

## 总结

Subagent 编排的本质不是"多用几个 AI"，而是把任务设计成可以安全并行的形状。拆分边界清晰、prompt 自包含、结果结构化、并发有上限——四件事做到位，多 agent 并行的加速是真实的；做不到位，它只是更快地把 token 烧完。先串行验证，再并行放量，是我目前最推荐的节奏。
