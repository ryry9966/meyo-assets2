## 背景

OpenClaw agent 的行为由两部分决定：固定的系统提示词，以及 workspace 里一组按约定命名的 Markdown 文件。`IDENTITY.md` 是其中最"轻"的一个——它不定义能力，也不定义流程，只回答一个问题：这个 agent 是谁。每次新会话启动时它会被注入上下文，成为 agent 自我描述的基准。

## 问题

跑了一段时间后，团队通常会撞上三类情况：

1. **语气漂移**。今天像客服，明天像技术博主，多会话之间没有稳定的人格锚点。
2. **调教散落在对话里**。每次说"你再正式一点"，只修了当前会话，重启后全部丢失。
3. **多 agent 场景分不清谁是谁**，排查日志时无法快速定位"这句话是哪个角色说的"。

根因是：身份没有被当作持久化、可版本化的配置，而是被当成了聊天时的临时情绪。

## 做法

1. 在 workspace 根目录（默认 `~/.openclaw/workspace`）创建 `IDENTITY.md`。
2. 字段保持最小集：`Name`、`Creature/Emoji`、`Avatar`，以及 `Vibe`——两三句语气描述，外加少量明确的负面约束（"永不做什么"）。
3. **职责切干净**：价值观和底线放 `SOUL.md`，用户画像放 `USER.md`，任务流程放 `AGENTS.md`，`IDENTITY.md` 只放"是谁"。一旦发现自己在里面写"收到消息先做 X"，就该挪走。
4. **进 git**。身份的每次修改走 commit，能 diff，能回滚。
5. 进化的方式不是重写，是 patch：发现某类回复不对劲，改一行 Vibe 描述，下个会话生效，观察几天再决定去留。

## 踩坑点

- **写太长**。它每个会话都会加载，几百字足够；上千字既浪费 token，也稀释重点。
- **与系统提示词冲突**。系统层已规定回复风格，`IDENTITY.md` 再写一套相反的，agent 行为会忽冷忽热。单一事实来源原则同样适用于人格。
- **会话内改了不生效**。它在会话启动时读取，改完要新开会话（或触发 reload）再验证。
- **把礼貌写成讨好**。Vibe 里堆满"亲切、热情、永远耐心"，在排障场景反而产出冗长的安抚性废话。工程场景的语气约束建议克制。
- **多实例共享 workspace 导致身份串味**：每个 agent 独立目录，避免互相覆盖。

## 可复用建议

- 把 `IDENTITY.md` 当代码评审对象：改人格也要有 commit message，写清楚"为什么改"。
- 一次只改一个变量，否则效果无法归因。
- 负面约束比正面描述更稳："不用表情符号"比"保持专业"更可执行。
- 准备三个固定测试问题（日常闲聊、故障排查、越权请求），每次改完跑一遍，当作人格的回归测试。

## 总结

`IDENTITY.md` 的价值不在"让 AI 有个性"，而在把身份从对话中的偶然，变成仓库里的必然。它很小，但它是 agent 与你长期协作的接口约定——接口值得被认真设计，也值得被版本化。
