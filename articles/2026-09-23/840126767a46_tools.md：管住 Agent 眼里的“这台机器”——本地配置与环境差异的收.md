## 背景

OpenClaw 的 agent 不是只靠模型“猜”你的机器。工作区里的那几个 markdown（AGENTS.md、TOOLS.md 等）会在会话开始时注入上下文，其中 TOOLS.md 的定位很明确：告诉 agent **这台机器上的工具和事实**。

我的部署横跨三台设备：家里的 Mac mini 挂日常网关，一台 Ubuntu VPS 跑定时任务，还有一台出差用的笔记本。同一套 skill，三套环境。

## 问题

没有 TOOLS.md 约束时，踩过的坑很典型：

- agent 在 Ubuntu 上执行 `brew install`，在 Mac 上试图改 `/etc/nginx/...`，包管理器和路径全靠模型的默认印象；
- VPS 出站受限必须走代理，agent 不知道，任务卡死反复重试；
- 我曾在 AGENTS.md 里堆满“如果是 A 机器就……如果是 B 机器就……”的条件句，prompt 越来越臃肿，且和真实环境逐渐脱节。

本质上这是**配置漂移**：环境事实散落在对话历史和我的记忆里，缺少一个机器维度的单一事实源。

## 做法

我现在的结构分三层：

1. **AGENTS.md 只放跨机器通用的行为约定**：安全红线、回复风格、任务流程，不含任何机器特定信息。
2. **TOOLS.md 按 host 维度写“机器事实”**，每台设备只描述自己：
   - 系统与包管理器（`apt` / `brew`）；
   - 网络边界（能否直连出站、代理地址端口）；
   - 路径约定（笔记目录、下载目录、服务目录）；
   - 凭据“在哪里”，绝不写凭据“是什么”。
3. **差异尽量下沉到脚本**。三台机器打开 URL 的方式不同，就写一个 `~/bin/open`，TOOLS.md 里只写“用 `~/bin/open <url>`”。**文档描述接口，脚本吸收实现。**

再配一个 `doctor.sh`：换机或环境变更后跑一次，输出系统信息、包管理器、代理连通性、关键路径是否存在，人工核对后更新 TOOLS.md 对应段落。文档更新有了固定触发点，不再靠自觉。

## 踩坑点

- **把密钥写进 TOOLS.md**。整个文件会进模型上下文，等同明文提交。只写位置和获取方式。
- **文档和脚本两套真相**。改了脚本忘了改文档，agent 会坚持按文档执行然后失败。原则：能下沉到脚本的差异不留文档，文档只留接口。
- **写太长**。超过一两百行，agent 实际是“扫读”，关键约束反而被淹没。每条事实配一句“如何验证”，删掉没有操作含义的描述。
- **过期信息比没有信息更糟**。agent 对文档的信任高于对报错的推理，换包管理器、迁移目录后不更新，它会反复撞同一堵墙。

## 可复用建议

- 新机器接入：先跑 doctor 脚本生成环境报告，再手写 TOOLS.md，不要从旧机器复制粘贴。
- 每条目固定三段式：**是什么、为什么需要、怎么验证**。
- 用 git 管理 TOOLS.md，每台机器一个目录，diff 一眼看出环境差异。
- 每次环境变更后重跑 doctor，把 TOOLS.md 当作有保鲜期的资产来维护。

## 总结

TOOLS.md 的价值不在“写了多少”，而在把环境事实收敛成一个 agent 可信、人也维护得动的单一来源。差异交给脚本，事实交给文档，验证交给固定流程——三层各司其职，agent 换到哪台机器都不会“失忆”。
