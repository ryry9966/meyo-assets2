## 背景

OpenClaw 接入的 agent 多了之后，"用哪个模型"就从个人偏好变成了工程问题。我们目前同时跑两条路：云端 GPT 系列（推理和工具调用强，但按 token 计费、数据要出网），以及本地 vLLM 部署的 Qwen / Llama（数据不出内网，边际成本趋近于零，但能力上限低一些）。早期每个 agent 在配置里写死一个模型，结果要么账单难看，要么明明是个分类任务也在排队等 GPU。

## 问题

人工选模型有三个绕不开的矛盾：

1. **能力与成本**：复杂推理、多轮工具调用确实需要强模型，但 agent 一个任务里约 80% 的中间步骤是摘要、改写、格式化。
2. **合规与效率**：涉及内部文档、客户数据的步骤不能随便出网，但全走本地又拖慢整体延迟。
3. **静态配置 vs 动态负载**：本地模型单条快，并发一上来队列堆积，没有降级路径就整体卡死。

## 做法

核心思路一句话：**按任务形态路由，而不是按模型好坏路由**。在 OpenClaw 路由层配置规则（示意）：

```yaml
routes:
  - when: { privacy: internal }
    use: local/qwen2.5-14b
    fallback: none            # 内网数据禁止出网
  - when: { task: [classify, summarize, rewrite], est_tokens: "<3000" }
    use: local/qwen2.5-14b
    fallback: cloud/gpt-4o-mini
  - when: { needs_tools: true }
    use: cloud/gpt-4o         # 工具调用成功率优先
  - default: cloud/gpt-4o-mini
```

落地分四步：

1. **给任务打标**。在 agent 的 skill / 插件定义里加 `task` 和 `privacy` 标签，路由才有依据。这步别偷懒，标签质量决定路由质量。
2. **路由前置估算**。进路由器前用 tokenizer 粗估 token 数、判断是否需要工具调用，避免长上下文任务被塞进 8K 窗口的本地模型。
3. **降级带审计**。本地超时或校验失败可以 fallback 到云端，但必须记日志、发告警；`privacy: internal` 的路由直接禁止 fallback。
4. **观测收敛**。记录每次路由决策（命中规则、实际模型、耗时、是否降级），每周看一次命中率与降级率，再回来调阈值。

## 踩坑点

- **本地模型 function calling 不稳定**。同一 prompt 偶尔产出不合法 JSON。我们加了 schema 校验 + 一次重试，仍失败才降级云端，工具调用成功率从约 92% 拉回 99% 以上。
- **量化掉点被低估**。4-bit 量化后 7B 模型在内部分类集上准确率掉了 6 个点。路由阈值别照抄别人的，用自己那 50 条评测集说话。
- **静默降级最危险**。曾有一次本地服务故障一周，全部流量悄悄走了云端，账单翻倍才发现。降级率必须设告警线。
- **延迟要看并发下的延迟**。压测别用单条请求；本地队列深度超阈值就应主动降级，而不是等超时被动切换。

## 可复用建议

- 路由规则当代码管理：版本化、灰度、可回滚。
- 每类任务维护 20–50 条评测集，改规则前跑一遍，防止"优化"变成退化。
- 成本看"每成功任务成本"，不是每 token 单价——降级加重试，可能让便宜模型反而更贵。
- 本地只部署评测过的一两个模型，模型一多，维护成本很快吃掉收益。

## 总结

多模型路由的价值不在省钱技巧，而在于把**能力边界、数据边界、延迟预算**变成显式规则。先给任务分类，再写规则，最后靠评测集和路由日志收敛。三个月下来，我们云端 token 成本降了约 60%，p95 延迟基本持平，内网数据零出网——这三个数字，比任何"哪个模型更强"的争论都有说服力。
