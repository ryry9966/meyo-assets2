## 背景

Agent 系统的可靠性下限，往往不是由模型决定的，而是由它调用的外部 API 决定的。一次典型任务里，Agent 可能同时依赖 LLM 接口、MCP 工具、第三方 SaaS 和自建服务，任何一环超时、限流或返回 5xx，整条链路就卡住。模型本身不会"自然地"处理好失败——如果不在工具层做设计，它要么傻等，要么编一个结果继续往下走。

## 问题

常见的三类翻车：

1. **无脑重试**：429 和 500 一律立刻重试，把限流打成雪崩；
2. **错误信息不透明**：工具层把异常吞掉，只返回一个布尔值，模型只能靠猜；
3. **状态丢失**：重试成功后，前面的中间产物（已创建的记录、已发送的流程）对不上号，重复执行。

## 做法

我目前的分层策略，按顺序执行：

**第一层：分类。** 先分三类再谈处理：

- 可重试：429、5xx、网络超时；
- 不可重试：400、401、403、参数校验失败——重试只会浪费 token；
- 语义失败：API 正常返回但业务失败（比如"库存不足"）。

**第二层：重试。** 只对可重试类做指数退避 + 随机抖动（jitter），比如 1s/2s/4s 加 ±20% 随机量，上限 3 次。响应带 `Retry-After` 就直接用，别自己算。写操作必须带幂等键，否则重试可能落两条记录。

**第三层：熔断与降级。** 同一工具连续失败 N 次就熔断，短时间直接跳过，别让 Agent 反复撞墙。关键路径准备降级：主模型挂了切备用模型，搜索 API 挂了返回缓存，或明确告知"该数据暂不可用"。

**第四层：把错误结构化地还给模型。** 不要返回裸 stack trace，也不要只返回 false。用统一信封：

```json
{
  "status": "upstream_error",
  "retryable": true,
  "retry_after_ms": 2000,
  "hint": "搜索服务限流中，建议稍后重试或跳过该步骤"
}
```

模型拿到 `retryable` 和 `hint`，才能做出"重试"还是"换路"的合理决策。

**第五层：断点续跑。** 长任务在每步完成后落一个 checkpoint（本地 JSON 就够），恢复时从最后成功步骤继续，而不是从头再来。

## 踩坑点

- **超时不匹配**：MCP 客户端超时 30s，上游函数实际跑 60s，客户端早已报错、上游还在执行，重试就变成并发重复请求。两端超时必须对齐，且写操作先确认幂等。
- **重试 4xx**：看到失败就重试是本能，但 401 重试一百次还是 401。分类错了，后面全白搭。
- **让模型自己"看着办"**：不给结构化错误、不给预算上限，模型可能循环重试二十轮，token 烧完任务也没推进。重试次数和总耗时要有硬上限。
- **降级路径没测过**：fallback 写了但从未触发，真出事时它自己也挂。

## 可复用建议

1. 所有工具调用过一层统一的包装器：超时、重试、分类、结构化返回都在这一层做，不要散落在每个工具里；
2. 写操作默认设计为幂等，或在信封里显式标注 `retryable: false`；
3. 给任务设"失败预算"：连续失败超过阈值就转人工或终止，并带上完整错误上下文；
4. 定期做故障演练：故意断掉某个 API，验证降级和 checkpoint 是否真的工作。

## 总结

外部 API 挂掉是常态而非异常。Agent 的错误恢复本质上是工程问题而非 prompt 问题：分类错误、限制重试、结构化反馈、可降级、可续跑。把这五件事做进工具层，Agent 才算从"演示可用"走向"生产可用"。
