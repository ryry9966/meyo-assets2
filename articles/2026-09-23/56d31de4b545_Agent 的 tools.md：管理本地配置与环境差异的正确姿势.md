## 背景

跑 OpenClaw agent 时间长了会发现一个规律：任务指令大多稳定，真正经常变的是环境。这台机器用 brew、那台用 apt；公司内网要走代理；本机装了哪些 MCP server；项目用什么命令跑测试。这些"环境事实"决定 agent 第一步走不走得通。

OpenClaw 的 workspace 里有一个专门的文件：`TOOLS.md`，agent 启动会读它。它的定位是"本机环境卡"——但很多人要么不写，要么把它写成了第二份 prompt。

## 问题

不管理环境事实，通常有三种症状：

1. **system prompt 越写越长。** 环境说明、工具偏好、注意事项混在一起，换台机器整段作废，上下文被静态描述占掉。
2. **环境变了，描述没变。** prompt 里写"用 brew 安装"，到了 Linux 服务器上 agent 硬试半天；代理地址换了没人更新，agent 反复超时。
3. **协作时人人环境不同。** 共享的 prompt 覆盖不了差异，每个人都在打口头补丁。

根因只有一个：环境事实和任务指令没有分层。

## 做法

把事实收进 TOOLS.md，按两层组织：

**全局层：`~/.openclaw/workspace/TOOLS.md`**。描述这台机器的共性：OS 与 shell、包管理器、语言版本管理方式（uv / nvm 之类）、代理设置、常驻 MCP server 及启动脚本路径、个人目录习惯。

**项目层：仓库内的 TOOLS.md 或等效笔记**。描述项目特有事实：启动/测试命令、端口、目录结构、代码风格、禁改目录。进版本库，团队共享。

**敏感信息不进 TOOLS.md。** 密钥和 token 走环境变量，文件里只写一句"API key 从环境变量 `XX_KEY` 读取"。

写法上遵循四条：

- 每行一条可执行事实，不写散文。"包管理器：uv，禁止 pip 装全局"比一段解释有用。
- 只写"是什么、怎么做"，"为什么"放 README。
- 控制长度：全局层建议 60 行内，项目层 40 行内。每行都要进上下文，行数即成本。
- 写完做一次校验：让 agent 复述"你当前可用的包管理器和测试命令是什么"，和实际环境 diff。

## 踩坑点

1. **把任务流程写进 TOOLS.md。** 和 skill 职责重叠，改流程要改两处，迟早漂移。TOOLS.md 只放环境事实，流程归 skill / AGENTS.md。
2. **过期信息比缺失更危险。** 换机后忘更新代理，agent 撞墙的次数比你发现的次数多。环境大改后必跑一遍复述校验。
3. **两层冲突时行为不可预测。** 明确约定项目层覆盖全局层，冲突项在项目层显式写一句"覆盖全局：xxx"。
4. **当成日志写。** 历史决定、踩坑记录越堆越长。它是注入上下文的配置，不是文档，定期删，过期条目直接砍。
5. **MCP 配置两处维护。** TOOLS.md 手抄一份 server 清单，启动脚本又是另一份。单一事实来源：TOOLS.md 只写脚本路径和注意事项，不复制内容。

## 可复用建议

- 模板分区固定六块：Runtime / Package / Network / MCP / Conventions / Never-do，新人拿到就能填。
- 项目层随仓库走；涉及个人本地覆盖的部分，提交一份 `TOOLS.md.example`，各人复制成本地版并 gitignore。
- 换机或每季度清一次：逐行问"这条还成立吗"，答不上来的删。
- 把 agent 自检当例行动作：开场让它输出环境摘要，与预期不符就是 TOOLS.md 该更新的信号。

## 总结

TOOLS.md 解决的是"环境事实与任务指令分离"的问题：全局层管机器，项目层管仓库，密钥走环境变量，行数即上下文成本。做好分层和定期修剪，agent 在换机、协作、排障三个场景的摩擦会明显下降。它不性感，但属于那种写一次、长期省事的基础设施。
