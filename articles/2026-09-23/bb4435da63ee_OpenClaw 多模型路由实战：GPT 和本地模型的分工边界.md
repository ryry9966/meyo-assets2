## 背景

OpenClaw 天然支持多 provider：云端模型和本地模型（Ollama、LM Studio 跑的开源权重）可以同时挂在一个 gateway 里。很多用户的默认做法是"一把梭"——所有 agent 全走云端旗舰，账单不好看；另一部分人为了省钱或隐私全切本地，结果 agent 变笨、工具调用频繁失败。

多模型路由的核心问题不是"选哪个模型"，而是**哪些调用点值得花钱**。

## 问题

把一次 agent 会话拆开看，token 消耗和任务难度分布极不均匀：

- 意图识别、路由分类、格式转换、摘要压缩：占比高，难度低
- 多步工具编排、代码生成、长文档推理：占比低，但决定成败

用旗舰模型跑前一类是浪费，用本地小模型跑后一类是事故。路由的目标就是把这两类调用分开。

## 做法

**第一步：盘点调用点。** 列出所有触发 LLM 调用的位置：主 agent 的对话循环、插件内的辅助调用、MCP 工具结果的后处理、定时任务的摘要生成。很多消耗其实藏在插件和后处理里，不在主对话里。

**第二步：按三档分配模型。**

| 档位 | 典型任务 | 建议模型 |
|---|---|---|
| 轻量 | 意图分类、格式化、简短摘要 | 本地 7B 级量化模型 |
| 中档 | 单工具调用、常规对话、邮件草稿 | 云端中档或本地 30B+ |
| 旗舰 | 复杂推理、多步编排、代码任务 | 云端旗舰 |

**第三步：在配置层落地。** OpenClaw 允许按 agent/会话指定模型：主 agent 的 model 设为旗舰，插件内辅助 agent 显式指到本地 endpoint。主链路配 fallback 链（旗舰 → 中档 → 报错），本地任务反向配（本地 → 云端）。

**第四步：观测。** 开启 token 用量日志，跑一周再调整分档。先测量再路由，不要凭感觉。

## 踩坑点

- **本地模型的工具调用格式不稳。** 量化后的 7B 模型 function calling 兼容性参差，MCP 工具参数经常幻觉。涉及工具编排的任务不要下沉到本地。
- **长上下文本地降智。** 输入超过本地模型有效上下文一半时质量明显下滑，长文档总结宁可上云端。
- **路由判断本身是成本。** 如果为了"该用哪个模型"再调一次 LLM，小任务的开销反而翻倍。规则路由（按调用点/按插件固定）优先，模型判别路由只在调用量足够大时才值得。
- **静默降级最难排查。** fallback 触发时必须有日志和标记，否则你以为在用旗舰，实际早就在跑中档了。

## 可复用建议

1. **80/20 法则**：大多数部署里，约 80% 的 token 消耗可以安全下沉到轻量模型，成本能降一个数量级。
2. **中文任务单独评测**本地模型，开源模型的中英能力差距比 benchmark 上显示的更大。
3. **fallback 方向要和任务价值一致**：低价值任务允许降级，高价值任务宁可失败也要把报错暴露出来。
4. **模型选型写成配置**而不是写死在代码里，方便按场景 A/B 对比。

## 总结

多模型路由不是追求"全用最便宜的"，而是给每个调用点匹配它实际需要的能力。OpenClaw 的便利在于调用点本来就是分开的——主 agent、插件、MCP 后处理各归各，路由只需要在配置层做一次清晰分工。先盘点、再分档、跑一周数据、然后收敛：一个下午就能把账单砍到原来的几分之一，同时保住关键链路的稳定性。
