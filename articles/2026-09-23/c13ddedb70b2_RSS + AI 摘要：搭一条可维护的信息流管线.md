## 背景

订阅源的问题从来不是没有信息，而是信息太便宜。RSS 依旧是结构化程度最高的公开信息源：字段规整、无算法干预、去留完全由自己控制。但人肉阅读 scale 不上去，于是很自然的分工是：抓取交给程序，初筛交给规则，摘要交给模型，人只看最终产物。

## 问题

直接"把每篇喂给 LLM 总结"跑几天就会撞上三个现实：

1. **成本失控**。技术向订阅源一天几十上百条，全量摘要的 token 消耗很可观，而其中大半内容根本不值得看。
2. **摘要质量不稳**。模型对无关内容会硬编要点，标题党文章的摘要甚至比原文更有误导性。
3. **产物没人看**。摘要只是塞进数据库或推到群里，没有分层，很快变成新的信息噪音。

## 做法

最终收敛成一条四段式管线，在 OpenClaw 里跑成一个定时插件：

**抓取层**：Miniflux 自托管统一收口，开 ETag / If-Modified-Since，对源站礼貌。个别只有列表页的站用 RSSHub 补源。

**过滤层**：便宜的规则先跑——关键词黑名单、域名权重、标题相似度去重（本地 embedding，阈值 0.88 左右）。这一层能砍掉 60–70% 的条目。

**摘要层**：只对幸存者调 LLM。prompt 强约束输出结构：一句话定位 + 三个要点 + "为什么值得读"，并要求只基于原文，不确定就写"原文未说明"。始终附带原文链接，摘要不替代出处。

**分发层**：按重要度分两档，高优实时推 webhook，低优汇成日报。原始条目和摘要都落 SQLite，摘要是派生数据，可随时换模型重新生成。

另外把"查询最近摘要 / 按主题检索"包成了 MCP tool，Agent 需要背景资料时直接问管线，而不是现场抓网页。

## 踩坑点

- **全文缺失**：不少源只给 summary，直接摘要等于"摘要的摘要"。要抓回链接后用 readability 抽正文，清洗 HTML 再进模型。
- **编码与转义**：老源里 CDATA、HTML entity 混着来，入库前统一 normalize，否则去重和检索会静默失败。
- **抓取节律**：并发拉几十个源容易被大站限流，控制在 2–3 并发、错峰执行，重试必须带退避。
- **去重阈值**：卡太紧会误杀跟进报道，后来改成"同主题聚类后合并成一条，保留最新"。
- **摘要漂移**：换模型后输出风格突变，日报读感不一致。prompt 里固定结构和长度下限，比调 temperature 有用。

## 可复用建议

1. **两段式预算分配**：便宜规则粗筛，贵的模型只处理幸存者，成本能降一个量级。
2. **摘要只做派生数据**，原始条目永远保留——换模型、改 prompt 都可以重放。
3. **每个阶段落日志和计数**（进多少、筛掉多少、失败多少）。管线安静地坏掉比不跑更危险。
4. **先跑日报再上实时推送**，确认信噪比之后再收紧过滤，别一上来就追求即时性。

## 总结

这套东西单看每一步都不新鲜，价值在于分层和可重放：便宜的计算挡在前面，贵的计算花在刀刃上，原始数据不动，所有中间产物可重建。信息管线的本质不是"AI 替你读"，而是把"读什么"的决定权收回自己手里。欢迎在评论区交流各自的过滤规则和 prompt 结构。
