# OpenClaw 多模型路由实战：GPT 与本地模型的分工边界

## 背景

OpenClaw 这类 Agent 网关最大的便利是模型可插拔：`models.json` 里同时挂 GPT 和本地推理服务（Ollama / vLLM 跑 Qwen、Llama 都行），再配一层路由规则，同一个 Agent 就能按任务分流。我们从"全部走 GPT"迁到多模型路由，跑了三个月，API 成本降了约 60%，也踩了不少坑，这篇把判断标准沉淀下来。

## 问题

单一模型的痛点很直接：全走 GPT，账单和限流扛不住，私有数据出域还有合规压力；全走本地，复杂任务的工具调用成功率和推理质量明显下滑。真正的缺口是**没有任务级的分流标准**，"感觉这个简单就给本地"这类拍脑袋规则撑不过一周。

## 做法

我们把任务拆成四类，分别路由：

1. **规划与编排**（Agent 主循环、多步拆解、复杂工具链）：走 GPT。这类任务失败一次的重试成本远高于 token 差价。
2. **结构化抽取**（MCP 工具参数填充、表单解析、JSON 输出）：优先本地量化小模型，路由层加 schema 校验，失败重试两次后升级到 GPT。
3. **私有数据与批量后台任务**（内部文档摘要、日志打标）：强制本地，出域是红线。
4. **交互式对话**：混合模式，本地小模型做意图分类，命中复杂意图再切 GPT。

落地三步：

- 给每个模型打能力标签：`tool-call`、`long-context`、`json-mode`、`vision`，路由按标签匹配，不按模型名硬编码；
- 路由规则写成独立配置文件，支持热更新，调整不用重启 Agent；
- 每条路由记日志：任务类型、token 数、耗时、是否回退，每月复盘一次失败率。

## 踩坑点

- **本地模型的 JSON 输出不稳**。别指望 7B 模型裸跑就能稳定填 MCP 参数，务必上 grammar 约束或 json schema 强制解码，否则重试率会很难看。
- **别只看首 token 延迟**。本地模型 TTFT 快，但长输出吞吐低，生成两千字摘要反而比 GPT 流式更慢。按任务的预期输出长度选型。
- **有效上下文 ≠ 标称上下文**。本地模型标 32k，实际超过 16k 就开始丢细节。路由时用真实 token 数判断，别只看任务标签。
- **降级风暴**。GPT 限流时全量回退本地，GPU 被打满后雪崩式超时。回退链路必须带队列和限流。
- **本地不是免费**。GPU 折旧、电力、运维都要算进去，日均几千次以下的小规模场景，纯 API 可能更划算。

## 可复用建议

- 先建 50~100 条评测集（覆盖四类任务），任何路由规则改动都跑一遍再上线；
- 保留 5% 流量走默认模型做对照，防止规则悄悄劣化没人发现；
- system prompt 按模型分版本维护，GPT 调好的 prompt 直接丢给本地模型大概率水土不服。

## 总结

多模型路由不是省钱开关，而是把"任务-模型匹配"变成可度量、可回滚的工程问题。我们的默认规则：私有数据和高频低难度任务走本地，复杂推理和质量敏感任务走 GPT，边界情况交给评测数据说话。先把路由日志跑起来，两周后你就知道该往哪调了。
