## 背景

现在大多数 agent 的默认形态还是"你问它答"。聊天窗口是它的全部世界，你不发消息，它就一直待机。但真正有价值的自动化场景往往不是这样：磁盘快满了你才想起来、CI 红了半小时才有人发现、每天站会前忘了准备摘要。这些事的共性是——需要有人**记得去触发**。proactive 能力的本质，就是把"触发权"从用户手里部分移交给系统。

## 问题

"主动"很容易做成"骚扰"。常见失败形态有三种：一是无差别推送，agent 每小时汇报一次"一切正常"，三天后用户直接静音；二是误触发，条件写得宽，鸡毛蒜皮也执行动作；三是成本失控，每次触发都带全量上下文跑一遍大模型，token 账单比人还贵。所以核心问题不是"能不能主动"，而是**在什么条件下主动、主动到什么程度**。

## 做法：三段式结构

我们在 OpenClaw 里跑通了一套触发-决策-执行分离的方案：

**1. 触发层（Trigger）**。把主动来源显式化，通常三类：定时（cron 类）、事件（webhook / MCP 工具变更通知）、阈值（轮询指标超水位线）。关键原则：触发条件写在配置里而不是埋在 prompt 里，可审计、可随时关闭。

**2. 决策层（Gate）**。触发不等于执行。触发后先跑一次轻量判断：这件事是否值得打扰用户、是否在被授权的动作集合内、过去 24 小时是否已报告过类似事件。可以是一个规则引擎，也可以是一次便宜模型的分类调用。输出三档：执行、静默、转人工确认。

**3. 执行层（Act）**。动作集合显式声明且收窄，比如只允许"整理摘要 + 发到指定频道"，不允许顺手重启服务。所有动作要求幂等：带事件 ID 去重，重复触发不会发两条一样的通知。

示意配置：

```yaml
triggers:
  - type: cron
    schedule: "0 9 * * 1-5"
    context: check_ci_status
  - type: webhook
    event: issue.opened
    filter: label in [bug, urgent]
gate:
  dedup_window: 24h
  quiet_hours: "22:00-08:00"
actions:
  allow: [summarize, notify]
  deny: [restart, delete]
```

## 踩坑点

- **触发风暴**：上游一次抖动会放大成几十次触发。Gate 层必须做窗口聚合，5 分钟内同类事件合并成一条。
- **上下文过期**：定时任务拉到的快照，执行时可能已变。执行前重新校验关键状态，宁可慢一步。
- **在 prompt 里写触发逻辑**：模型对"每次都记得检查"这类指令的遵守是概率性的。时间相关的事交给调度器，模型只负责判断和表达。
- **静默时段形同虚设**：quiet hours 只挡通知不挡执行，半夜照样跑了删除操作。高风险动作要同时受时间窗和确认阈值约束。
- **没有反馈回路**：用户从没机会说"这类别以后别报"，agent 就永远学不会收敛。哪怕只做一个忽略按钮，也要把信号写回配置。

## 可复用建议

- 从一个"高频、低风险、强周期"的场景起步，比如每日 CI 播报，跑两周再扩。
- 三层各自独立开关和日志。出问题时你能立刻定位是哪层的锅。
- 给主动性定预算：每天最多主动发言 N 次，超了就合并或丢弃——宁可漏报，不要轰炸。
- 所有主动行为打标记录（触发源、决策依据、执行结果），每周复盘误报率，这是调 gate 阈值唯一可靠的数据来源。

## 总结

proactive 不是让 agent 更"聪明"，而是给它一套克制的反射弧：什么时候醒、醒了先想、想清楚再动手、动手留痕。把触发做成配置、把判断做成门槛、把执行做成白名单，主动的 agent 才是资产而不是噪音源。建议从最小闭环开始，让误报率数据驱动你逐步放开权限。
