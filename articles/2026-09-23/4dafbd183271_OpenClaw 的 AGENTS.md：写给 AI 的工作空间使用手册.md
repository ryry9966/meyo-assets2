## 背景

Agent 有个容易被忽略的特性：每次新会话，它对这个工作区的记忆是零。你可以花十分钟解释"这个仓库用 pnpm、测试跑 `make check`、别碰 generated 目录"，下个会话又得重来一遍。

AGENTS.md 就是解决这个问题的约定：在 workspace 根目录放一份 Markdown 文件，OpenClaw 在会话启动时自动读取并注入上下文，相当于给 AI 一份常驻的《工作空间使用手册》。这套思路在多个 agent 工具里已是事实标准，OpenClaw 也兼容它——如果你已经有 CLAUDE.md 之类的文件，迁移成本很低。

## 问题

没有这份手册时，实践中反复出现三类问题：

1. **约定靠口口相传。** 构建命令、目录结构、代码风格全靠聊天里临时交代，换个会话就丢。
2. **Agent 自作主张。** 它按通用习惯操作：`npm install` 一把梭、在根目录随手建文件、commit message 写成三段小作文。
3. **Prompt 散落各处。** 同样的要求在十次对话里重复十次，没人知道哪句是最新版。

## 做法

我的 workspace 现在是三层结构：

- **全局层**：`~/.openclaw/workspace/AGENTS.md`，只放个人偏好——回复语言、注释风格、"不要主动重启服务"这类跨项目规则。
- **项目层**：仓库根目录的 AGENTS.md，固定五段：项目结构速览、常用命令（build/test/lint）、代码风格与提交规范、禁区（不要动哪些文件）、环境注意事项。
- **目录层**：子目录可再放一份覆盖上层，比如 `docs/` 里注明"此目录文档允许自由改写"。

两个原则比内容本身更重要：

**短而硬。** 控制在一两屏内，只写"必须遵守"和"绝对禁止"，不写背景故事。长文档的正确处理是拆成独立文件，AGENTS.md 里只留一行索引，agent 需要时会自己去读。

**命令要可直接执行。** 写 `pnpm test`，不要写"运行测试套件"。agent 对具体命令的执行准确率，远高于对自然语言描述的理解。

如果项目接了 MCP 或插件，分工可以这样切：MCP server 负责"能力"（怎么查库、怎么调接口），AGENTS.md 只负责"策略"（什么场景用哪个工具、查完要不要二次确认）。

## 踩坑点

- **写成 README 复制品。** README 是给人看的，照抄一遍没有增量信息，纯浪费上下文窗口。
- **指令互相冲突。** AGENTS.md 写 pnpm，CI 脚本里是 npm，agent 会随机站队。落笔前先跑一遍确认。
- **敏感信息入库。** 密钥、内网地址写进去，等于每次会话都注入上下文。手册要进 git，先按公开仓库的标准审一遍。
- **不更新比没有更糟。** 代码重构后手册没跟上，agent 按旧路径操作反而制造新问题。

## 可复用建议

- **错误驱动更新**：agent 犯的每个错，如果根因是"它不知道"，就沉淀一条进 AGENTS.md。这个文件应该和代码一起进版本控制、走 review。
- **定期自审**：每月让 agent 自己读一遍手册，逐条核对"这条还成立吗"，过时的删掉。
- **模板起步**：结构 / 命令 / 风格 / 禁区 / 环境，五段各三五条，十分钟就能写出第一版。

## 总结

AGENTS.md 的本质，是把团队的隐性工程约定显性化，交给一个"每轮都失忆但执行力极强的同事"。写它的过程也是在逼自己回答：这个项目的规则，我到底说清楚过没有？约束要少而硬，文档要短而新——做到这两点，一份两屏的 Markdown，抵得上无数次重复交代。
