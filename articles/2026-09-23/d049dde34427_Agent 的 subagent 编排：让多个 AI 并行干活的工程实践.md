## 背景

单个 Agent 干大活的瓶颈往往不在模型能力，而在上下文。搜资料、读代码、改文件、跑测试全塞进同一个会话，很快会碰到三个问题：上下文膨胀导致早期指令被遗忘、工具调用串行导致耗时线性增长、无关中间结果污染主对话。

subagent 编排是目前比较务实的解法：主 Agent 只做拆解、分发和验收，把独立子任务交给拥有独立上下文的子代理去跑，能并行的就并行。在 OpenClaw 这类支持 MCP 工具和插件扩展的运行时里，这套模式落地成本不高。

## 问题

拿一个真实场景举例：给一个中型仓库做「依赖升级 + 补测试 + 更新文档」。串行模式下主 Agent 一项项来，一轮几十次工具调用，中途容易因为上下文过长丢掉早期约束（比如"不要动 lock 文件"）。拆成 subagent 后，三类工作各自持有干净上下文，互不干扰，总耗时能压到原来的一半以下。

## 做法

**第一步：判断任务能不能拆。** 三个标准：输入输出明确；子任务之间没有共享可变状态；单个子任务上下文可自洽，不需要反复回头问主 Agent。

**第二步：写子代理任务卡。** 不要一句"帮我看看测试"就打发，任务卡建议固定五要素：

```yaml
goal: 为 auth 模块补齐单元测试
scope: 只允许修改 tests/auth/ 目录
tools: [read_files, write_files, run_tests]
return_format: JSON（passed / failed / coverage_delta / notes）
failure_policy: 连续 2 次测试不过即终止并上报，不硬试
```

**第三步：并发控制。** 并行度从 3 开始，别一上来开十几个。原因有二：API 限流会让所有子代理一起变慢甚至报错；并行写文件极易冲突。给每个子代理分配独立工作目录或文件范围，是并行的前提。

**第四步：结构化回收。** 主 Agent 聚合时只收 JSON 摘要，不收子代理的完整过程。验收标准写在任务卡里，主 Agent 只做比对和抽查，比如随机挑一个子代理的产出复跑验证。

## 踩坑点

1. **伪并行**：子代理之间其实要改同一个文件，跑起来才发现互相覆盖，回滚成本很高。拆分阶段就要做依赖分析。
2. **上下文没省下来**：把主对话完整历史塞给子代理，等于没拆。子代理只拿任务卡和最小必要上下文。
3. **子代理谎报完成**：模型倾向于乐观结论。return_format 里强制要求附证据（测试输出片段、diff 摘要），主 Agent 抽查。
4. **失败静默**：某个子代理超时崩溃，主 Agent 没感知就往下走。编排层要有超时、重试和部分失败上报机制。
5. **成本失控**：并行放大调用量，Token 消耗可能是串行的数倍。先小规模验证收益再放量。

## 可复用建议

- 任务卡模板固化成插件或 prompt 片段，团队内复用，别每次现写。
- 先串行跑通一个子代理，验证任务卡质量，再开并行——两者调试成本差一个数量级。
- 给每个子代理留 trace 日志（输入、工具调用、返回 JSON），排障时救命。
- 工具权限按子代理裁剪：只读任务不给写权限，能显著缩小事故面。

## 总结

subagent 编排的价值不是"多个 AI 很酷"，而是把上下文隔离、并行加速和职责边界变成可以管理的工程问题。核心就三件事：任务拆得干净、任务卡写得明确、结果收得结构化。建议从一个真实的小场景起步，串行验证、再并行放量，把超时重试和 trace 日志这些"不性感"的部分补齐，这套模式才真正稳定可复用。
