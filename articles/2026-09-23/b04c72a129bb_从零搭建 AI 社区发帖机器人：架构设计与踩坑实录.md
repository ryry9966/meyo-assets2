## 背景

社区运营里有类活儿重复度高但格式固定：每周把仓库的 release notes 整理成公告帖、把新合并的 PR 汇总成动态。人肉做，每次二十来分钟，还容易漏。于是我基于 OpenClaw 搭了一个发帖机器人，稳定跑了两三个月，这里记录架构取舍和踩过的坑。

## 问题

最初的想法很简单：定时让 agent「看看仓库有什么更新，写个帖子发出去」。实际跑起来发现三个硬问题：

1. LLM 自由发挥，会编版本号、编 PR 链接；
2. 定时任务偶尔重叠触发，同一个帖子发两遍；
3. 没有审核环节，一次格式错乱就直接暴露给全社区。

## 做法

最终架构拆成四层：

```
数据源（Git API / RSS）
   → 采集脚本（结构化输出）
   → OpenClaw Agent（写作 + 决策）
   → 审核与发布层（dry-run 或 MCP 调社区 API）
```

**1. 采集与生成解耦。** 采集用独立脚本，把 release、commit、discussion 拉下来，存成带内容 hash 的 JSON。Agent 只消费这些结构化数据，不允许直接「上网查」。

**2. 写作约束写进 system prompt。** 规定：版本号、链接、日期只能从输入 JSON 取，禁止补全；输出走固定模板（标题、摘要、变更列表、讨论入口）。宁可无聊，不可惊艳。

**3. 去重与幂等。** 以「内容 hash + 目标版块 + 周期」作为幂等键，发帖前查本地 SQLite；cron 加文件锁，防止上一轮没跑完下一轮又启动。

**4. 先 dry-run 两周。** 所有「发布」动作默认落到本地 drafts 目录并推给我私聊确认，确认后才真正调社区 API。发布接口在 MCP 工具里单独封装，带速率限制和指数退避。

**5. 失败可见。** 任何一步异常，把错误摘要发到我的私聊而不是只写日志——日志没人看，私聊不看不行的。

## 踩坑点

- **幻觉最先炸。** 第一版让 agent 自由写作，它把上周的版本号写成了「预计下周发布」。解法就是上面说的：数据只进不出，模板锁死。
- **Markdown 方言不兼容。** 论坛不支持标准 Markdown 的表格和部分强调语法，渲染出来一片乱码。加了一层格式白名单转换，只保留标题、列表、代码块、链接。
- **429 限流。** 连发三条公告被限流，固定间隔重试雪上加霜。改成指数退避 + 单次运行内最多 N 次发布。
- **时区问题。** cron 按服务器 UTC 跑，「每周一早上九点」实际是下午五点发的。定时类任务务必显式声明时区。
- **凭据最小化。** 发帖账号只给发帖权限，不给管理权限；token 走环境变量，不进仓库、不进日志。

## 可复用建议

1. **状态外置**：幂等键、上次运行时间都落库，agent 本身保持无状态，随时可重建。
2. **工具窄化**：暴露给 agent 的 MCP 工具越少越好，「读数据」和「写出去」拆成两个工具，后者默认要人工确认。
3. **dry-run 优先**：任何直接面向社区的动作，先跑两周影子模式再放开。
4. **每步可重放**：采集、写作、发布三步都能单独执行，排障时不必从头跑。

## 总结

这个机器人没什么高深技术，核心是工程纪律：把 LLM 当成一个「能力很强但需要约束的模块」来设计——数据可控、动作可审、失败可见。做到这三点，它就能稳定替你省下每周那二十分钟。下一步计划把 FAQ 自动回复也接进来，但会继续沿用同一套审核流程，先影子跑起来再说。
