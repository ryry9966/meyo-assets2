## 背景

OpenClaw-CN 社区每周都沉淀不少内容：issue 讨论、群聊精华、成员的实践笔记。我们想把这些整理成一篇「社区周报」自动发出去。人工做了一期，耗时约三小时，第二期就断了。于是决定写一个发帖机器人，让 OpenClaw agent 来干这活。

目标很克制：不做全自动无人值守，而是「agent 起草 + 人工审核门禁 + 自动发布」。全自动化听起来酷，但对社区账号来说，一次翻车内容的成本远高于节省的时间。

## 问题拆解

整件事拆开是五段：定时触发、素材采集、内容生成、人工审核、发布回执。核心思路是把每一段做成独立、可单独测试的环节，而不是一个大 prompt 全包。

## 架构与实现

- **触发层**：用 OpenClaw 的 cron 能力每周一早上拉起任务，不引入额外调度器。
- **采集层**：写了一个小插件封装三个数据源。RSS 直接解析；issue 走 REST API 带 token；群消息从 webhook 落的本地 SQLite 读。统一输出结构化 JSON：`{source, url, title, summary, ts}`。
- **生成层**：agent 拿到 JSON 后按模板生成草稿。模板固定了「本周热点 / 新教程 / 热门讨论」三个栏目，每条必须带原文链接。
- **审核层**：草稿写到本地 markdown 并推送通知，人工确认或编辑后放行。这一步是强制门禁，没有跳过选项。
- **发布层**：一个薄的发布插件，调社区 API 发帖，携带幂等键（周报日期哈希），返回帖子链接。

## 踩坑实录

**1. 幻觉链接。** 第一版让 agent 自由总结，它给两条讨论编造了不存在的 issue 链接，格式完全正确，肉眼难辨。修复：链接只允许从采集层 JSON 原样复制，发布前逐一 HEAD 请求验证返回 200。这类问题靠 prompt 约束不可靠，必须在代码层做白名单校验。

**2. 重复发帖。** 重试逻辑没做幂等，一次网络超时导致发出去两篇一样的周报。修复：发布前按幂等键先查存在性，且幂等键在采集阶段就确定，不依赖生成结果。

**3. 素材噪声。** 群聊精华混了大量闲聊，直接喂模型会导致周报跑题。加了一层规则前置过滤（关键词 + 消息长度 + 去重），只把「疑似有信息量」的条目交给模型，token 消耗降了约 60%，内容反而更稳。

**4. API 静默失败。** 论坛升级后发帖接口字段名变了，机器人静默失败了一周。教训：发布插件必须对非预期响应抛错并告警到群里，不能只写日志。

**5. 文风漂移。** 连跑四周后发现内容越来越「营销腔」，溯源发现是模板里的 few-shot 示例被某次改动换成了夸张版本。现在 prompt、模板、示例全部进 git，改动走 diff 评审。

## 可复用建议

- 生成内容中所有事实性元素（链接、数字、ID）必须有代码级校验，不要信任模型输出。
- 发帖类自动化必须有幂等键 + 发布前存在性检查。
- 人工审核门禁建议保留，哪怕只在初期——它能暴露的不只是内容问题，还有采集和生成层的问题。
- prompt 和模板当代码管理，进版本库，走 review。
- 每个环节独立可测：采集层用固定样本离线跑通，生成层可单独重跑，发布层提供 dry-run 模式。

## 总结

机器人现在每周稳定产出周报，人工介入时间从三小时降到十分钟以内。最大的收获不是省时间，而是把内容质量从事后补救变成了流程保障：链接可验证、发布可幂等、风格可追溯。架构上没有炫技——cron + 插件 + MCP 工具 + 一道强制审核门禁，每个环节都能独立替换和重跑。如果你也想做类似自动化，建议先从「半自动 + 强门禁」起步，跑稳一个月再考虑放开权限。
