## 背景：无状态的会话，有状态的诉求

LLM 会话本质无状态。无论用 OpenClaw 还是自建 Agent 流水线，默认都是新会话从零开始，于是用户每天重复交代同样的事：“提交信息用英文”“回复尽量短”“这个项目测试过了再提交”。这类偏好高度稳定，却每次都要手动注入。记忆系统的目标很朴素：把这类信息沉淀下来，让注入自动化。

## 问题：两种常见的错误姿势

一是全量堆进 system prompt。条目越攒越多，几千 token 之后开始互相冲突，模型行为不可预测。二是每次把历史对话原样拼接，成本高、噪声大，上周的临时任务会干扰今天的判断。

共同根因：没把记忆当成一个有写入标准、有生命周期、可人工维护的子系统，而是当成“存了就行”的日志。

## 做法：五个步骤

1. **分层**：会话内记忆交给上下文本身；跨会话记忆单独存，且只存两类——偏好（稳定、可复用）和事实（可能过期，必须带时间戳）。
2. **收紧写入标准**：写入需同时满足三条——稳定、跨场景可复用、用户不想每次重复。宁漏勿错，错记的修复成本远高于漏记。
3. **结构化存储、人类可读**：起步阶段一个 Markdown/YAML 文件足够，按域分组（代码风格 / 沟通偏好 / 工具习惯），每条带来源和写入时间。关键是用户能直接打开改——记忆不该是黑盒。
4. **按需读取**：会话开始时按当前任务匹配，只注入 top-k 相关条目，不搞全量，注入位置放在指令区而非正文。
5. **更新与遗忘**：同域冲突时新条目覆盖旧条目；提供显式的 forget 动作；定期人工审一遍。

在 OpenClaw/MCP 实践里，我把它封装成独立的 MCP server，只暴露 remember / recall / forget 三个工具。所有写入走统一入口，去重和审计都在这一层做，Agent 本身只负责调用。

## 踩坑点

- **写入太激进**：一句“这次顺便把文档更新了”被存成永久偏好，之后每个任务都“过度理解”。临时性指令要明确排除在外。
- **只增不删**：条目互相矛盾，模型每次随机听一条，行为看起来像出了 bug。
- **静默改变行为**：Agent 按记忆换了做法却不说明，用户第一反应是“它坏了”。应显式交代：“按你之前定的偏好，我这样处理了，不合适可以说。”
- **隐私边界**：记忆文件很容易混进密钥、内网地址这类敏感信息，别默认同步到云端，也别让它进版本库。
- **别一上来就上向量库**：条目在一两百以内，关键词加分域匹配完全够用，先把写入标准和更新流程跑通。

## 可复用建议

- 最小可行版本 = 一个记忆文件 + 一条写入规则 + 一个注入点，跑通之后再考虑升级存储。
- 把记忆当配置文件管：可读、可改、可 diff，出问题时能回溯是谁在什么时候写进去的。
- 用重放验证：同一任务连续跑两遍，确认第二遍真的复用了记忆、行为一致，而不是碰巧表现正常。

## 总结

记忆系统的难点不在存储选型，而在写入标准和长期可维护性。写入有门槛，记忆才不会变成互相矛盾的垃圾场；用户看得见、改得动，Agent 才敢真的去用。先从一个小文件开始，比任何框架都管用。
