## 背景

信息源这几年越来越散，算法推荐又不可控。RSS 虽然老，但仍是唯一"你说了算"的订阅协议。以前它的瓶颈是：订阅一多根本看不完。现在 LLM 够便宜、够快，"抓取 → 过滤 → 摘要"这条管线终于值得认真搭一次。

## 问题

直接订阅的痛点很具体：

- 标题党多，点进去经常浪费时间
- 多个源重复报道同一件事
- 部分 feed 只给两百字的 summary，缺正文
- 人肉筛选完全不可扩展

我的目标是：每天早上自动跑一次，产出一份 15 分钟能读完的日报，推送到 Telegram。

## 做法

用 OpenClaw 搭的，cron 定时任务驱动，整体分四步：

**1. 源管理。** feed 列表放 YAML 配置，不写死在代码里。一个人维护 10~20 个源就够了，宁缺毋滥。

**2. 抓取与去重。** cron 触发，走 MCP 的 fetch 工具拉 feed。对 guid/链接先做规范化（去 utm 参数、域名统一小写），再写入 SQLite，已见过的直接跳过。请求带 `If-Modified-Since`，省流量也不给对方添堵。

**3. 过滤与摘要。** 两段式。先用便宜模型按主题相关性打分，输出 JSON（score + reason），低于阈值的直接丢弃；过线的才进摘要环节。摘要 prompt 里强制两条约束：只基于给定正文；信息不足就明说，不许编。输出固定结构：一句话结论 / 三个要点 / 值不值得深读。

**4. 推送与归档。** 汇总成 markdown 日报，经消息通道发出，同时落一份本地归档。

整条链路：`cron → fetch → normalize → dedup → filter → summarize → digest → push`。

## 踩坑点

- **正文缺失**：不少 feed 只给 summary，摘要出来干巴巴。加一步 readability 抽取，直接抓原文页面再喂模型，质量差距立竿见影。
- **幻觉**：早期版本让模型"补充背景"，它真的会编。改成严格摘录式摘要 + 允许输出"信息不足"之后才稳定。
- **去重不彻底**：同一 URL 带不同 utm 参数会被当成两条。规范化必须放在去重之前；跨源同题报道用标题相似度兜底，简单编辑距离就够用。
- **cron 重叠**：一次全流程要跑十几分钟，间隔设太短会叠跑。加了个朴素的锁文件解决。
- **成本失控**：第一周没设阈值全量摘要，账单很难看。过滤先行 + 小模型分流后，token 消耗降了约八成。

## 可复用建议

1. **阶段间落日志**：抓了多少、去重剩多少、过滤剩多少、摘要几条。出问题时一眼定位是哪个环节。
2. **原始条目永远归档**：摘要可以随时换模型重生成，原始数据只有一份，删了就没了。
3. **源的质量决定一切**：管线再精细，喂垃圾源出来的还是垃圾。建议每月清一次源。
4. **摘要 prompt 强制结构化输出**：下游排版、推送都依赖这个，别让模型自由发挥。

## 总结

这条管线代码量不大，真正的工作量在调 prompt 和挑源上。跑了一个多月，现在每天早上一份日报替代了原来刷 reader 的一小时。RSS 没死，它只是在等一个值得自动化的理由。
