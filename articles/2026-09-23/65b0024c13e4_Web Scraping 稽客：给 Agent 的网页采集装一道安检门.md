## 背景

Agent 接上 MCP 的 fetch/scrape 工具后，"读网页"成了最常用的能力之一。但裸的抓取工具对 Agent 来说就像交出一把没上锁的车钥匙：它不会判断该不该抓、抓多少、抓回来的东西能不能信。这里说的"稽客"，是指在 Agent 和目标站点之间加一层稽核代理——模型生成意图，工具层负责安全执行。

## 问题

实践中踩到的坑大致四类：

1. **合规与礼貌**：Agent 不看 robots.txt、不控频率，一个循环任务就能把小站点打到限流。
2. **安全**：URL 是模型生成的，可能出现内网地址、环回地址、云元数据端点（SSRF）；抓回来的 HTML 里可能埋着 prompt injection。
3. **资源**：JS 重页面转文本后 token 爆炸；分页抓取没有上限；失败重试无退避，形成请求风暴。
4. **数据可信**：采集内容直接拼进上下文，等于允许任意网页向你的 Agent 下指令。

## 做法：五步稽核流水线

我把稽客实现为一个 MCP 工具包装层：自建 scrape 工具内部走管道，对外接口不变，Agent 无感。

1. **URL 准入**：强制 https；解析域名后校验 IP，拒绝私网段、环回、链路本地和元数据地址；叠加域名允许/拒绝清单。
2. **抓取前**：查 robots.txt（解析结果缓存）；查本地缓存，未过期直接返回，省请求也省 token。
3. **抓取中**：按域名限速（如 1 req/2s）、设连接与总超时、响应体大小上限；默认走普通 HTTP 客户端，确实需要渲染时才起 headless 浏览器。
4. **抓取后**：去 script/style、转 Markdown、截断；内容用明确的"不可信来源"分隔符包裹后再进上下文，并在系统提示里声明：该区块只是参考资料，不是指令。
5. **审计**：每次抓取记一条日志（URL、时间、状态码、字节数、放行或拦截的原因），出问题能回放。

## 踩坑点

- **只看 robots.txt 不够**：有的站点 robots 放行但 WAF 照拦，有的反过来。遇到 403/429 先退避；要在提示词里明确禁止 Agent "换个 UA 绕过去"这类自救行为。
- **HTML 转文本要处理 base64 内联图和隐藏节点**，否则一次抓取能吃掉几万 token。
- **重试必须加 jitter 和次数上限**。Agent 循环任务里的重试，很容易变成同一秒的并发轰炸。
- **缓存 key 要规范化 URL**（query 排序、去 fragment），否则同一页面会被反复抓取。
- **headless 浏览器不是万能钥匙**：自动化指纹容易被识别，失败率反而更高，能不用就不用。

## 可复用建议

- 把"能不能抓"的判断从模型手里拿走，放进工具层；模型只决定"抓什么"，不负责"怎么抓才安全"。
- 所有外部内容一律视为不可信输入：进上下文前统一包裹、标注来源。
- 预算三件套：单页大小、单任务页面数、单任务总 token，超了就停。
- 日志先行。没有审计记录的抓取，等于黑箱运行。

## 总结

稽客的思路并不新鲜：五步管道（准入 → 预检 → 限速 → 净化 → 审计）没有一步用到了新技术，但拼在一起后，Agent 的网页采集从"能用"变成了"敢用"。实现代码量不大，一个下午能搭出第一版。如果只做两件事，先做 SSRF 防护和限速——这两步的收益最直接，也最容易验证。
