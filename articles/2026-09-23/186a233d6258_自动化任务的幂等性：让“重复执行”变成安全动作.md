## 背景

跑 OpenClaw 自动化任务久了会承认一个事实：重试不是异常，而是常态。cron 触发可能因网络抖动重发，消息通道的 webhook 可能投递两次，agent 执行超时后被上层重跑，MCP 工具调用可能卡在“实际成功但客户端没收到响应”的边界上。所以自动化任务的真实语义几乎都是**至少执行一次**（at-least-once），而不是恰好一次。

问题在于，我们写的多数操作是“每执行一次就多一份副作用”的。

## 问题

典型翻车场景：定时任务给频道发日报，重试后发了两份；同步脚本把同一条记录 append 进文件两遍；agent 判定工具超时后重试，结果工单被建了两张。这些都不是逻辑 bug，而是操作本身**不幂等**——执行 N 次和执行 1 次结果不同。

## 做法

1. **给每次逻辑执行定一个确定性幂等键。** 不要用随机 UUID（每次重试都会变），用“任务名 + 计划日期 + 关键参数”做哈希，比如 `daily-report@2025-06-01`。同一次计划执行，无论重试几次，键不变。
2. **执行前查、执行后记。** 用一个轻量状态存储（SQLite 一张表就够）记录已完成的键。拿到任务先查：键存在且 done，直接跳过。
3. **崩溃窗口用三段式。** 先写入 in-progress，执行成功后标记 done；发现长期停留 in-progress 的记录（超过超时阈值），再重新执行或转人工核对。
4. **能用天然幂等操作就不绕路。** 固定路径覆写文件而不是 append；upsert（`INSERT OR REPLACE`）而不是 create；编辑已有消息而不是再发一条。
5. 外部 API 支持幂等键的就透传，很多支付、工单类接口有现成的 `Idempotency-Key`。

## 踩坑点

- **幂等键粒度错。** 只按任务名做键，当天第二次合法执行会被误杀；按请求 UUID 做键等于没做。粒度必须是“一次逻辑执行”。
- **先执行后记账留了崩溃窗口。** 执行成功、记录没写、进程挂了，重试照样重复。
- **状态过期时间不合理。** 永久保留会膨胀，过期太快会漏。TTL 要盖住最大重试窗口（比如 48 小时）。
- **agent 层的重复调用。** 工具实际成功但返回超时，agent 以为失败又调一次。工具返回里带上明确的执行 ID 和状态，别让 agent 靠猜。
- **别假设所有 MCP 工具同等危险。** 读操作天然幂等，写操作才需要键。把工具按副作用分级，只在必要时加防护，避免过度设计。

## 可复用建议

- 写一个 30 行左右的 `with_idempotency(key, fn)` 包装器，SQLite 存键，所有写类工具统一走它。
- 设计新工具时先问一句：“同样的输入再跑一次会怎样？”答案不是“会重复”就算合格。
- 日志里始终带 run_key 和状态，排查重复问题时这是唯一线索。
- 接受这个工程等式：**至少一次投递 + 幂等处理 ≈ 实际恰好一次**。不要试图在传输层追求恰好一次，那是没有结果的坑。

## 总结

幂等性不是锦上添花，而是自动化任务能放心重试的前提。确定性幂等键、先记账后执行、优先天然幂等操作——这三件事覆盖了绝大多数重复执行场景。自动化任务越跑越多之后，你会感谢当初给每个写操作加上的那一个键。
