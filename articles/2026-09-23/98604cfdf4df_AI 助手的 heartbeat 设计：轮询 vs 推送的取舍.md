## 背景

OpenClaw 的 heartbeat 本质是一个定时唤醒机制：agent 按固定间隔（默认 30 分钟）醒来，读一遍 HEARTBEAT.md 里的清单，决定有没有事要做。这是典型的轮询模型。另一条路是推送：webhook、插件事件直接唤醒 agent，事件发生即触发。两条路不冲突，但我最初只用轮询，后来又矫枉过正全改成推送，各踩了一遍坑，这里把取舍整理出来。

## 问题

核心权衡只有两个维度：**时效性**和**成本**。

- 轮询：实现简单、不需要公网暴露，但平均延迟是间隔的一半，且每次唤醒都付 token 成本——哪怕无事可做。
- 推送：即时响应、按需触发，但要求事件源能到达你的 gateway（公网 endpoint 或内网组件），还要自己处理鉴权、重放和去重。

多数需求其实是混合的：每日站会摘要适合轮询；「群里有人 @ 我」「CI 变红」适合推送。

## 做法

1. **盘点任务，按触发源分类。** 真周期的（晨报、磁盘巡检）留轮询；事件驱动的（git push、邮件到达、webhook）迁移到推送。
2. **轮询收敛到一份清单。** 不要为不同任务跑多套心跳配置，所有周期性检查统一进 HEARTBEAT.md，一次唤醒内让 agent 自行判断哪些项需要动作。
3. **清单写成「条件 + 动作」，不是任务列表。** 例如「若有未读邮件含发票关键词，则摘要私发」，而不是「检查邮件」。同时务必利用 HEARTBEAT_OK 短路：无事时只返回标记，不落主会话、不打扰群。
4. **间隔按重要性分级。** 例行监控 30 分钟足够；只有「必须及时知道」的事才压到 5–10 分钟，再低就要先算 token 账单。
5. **事件走 gateway webhook 或插件直调 agent，** payload 结构化，事件源带签名或 token 做鉴权，入口处附去重键。

## 踩坑点

- **心跳 prompt 膨胀**：清单涨到几十行后，每次唤醒白烧几千 token。低频项应移出 heartbeat，交给 cron。
- **忘了 HEARTBEAT_OK**：agent 每次唤醒都输出一句话并推到主频道，我被消息轰炸一个周末才定位到。
- **轮询和推送同时做一件事**：加 webhook 后没删对应轮询项，同一通知发两次。每类事件要有唯一去重键。
- **心跳任务过重**：一次唤醒里做长爬取，阻塞后续 tick。长任务交给后台会话，心跳只负责触发和查结果。
- **推送端点裸奔**：任何包都能触发 agent，等于把会话入口交给公网。至少做签名校验 + 限流。

## 可复用建议

- **轮询做基线，推送做例外。** 新需求先用 heartbeat，跑一两周，延迟确实不达标再换推送。
- **清单即接口。** HEARTBEAT.md 里每一项就是 agent 主动行为的完整集合，改动要像 review 代码一样审。
- **让每次 tick 可观测。** 记录「是否触发、做了什么、耗多少 token」，没有数据就无法调间隔。
- **幂等优先。** 无论轮询还是推送，同一事件触发两次不应产生两次副作用。

## 总结

轮询和推送不是二选一，而是两类问题的两个工具：轮询用 token 买省心，推送用工程复杂度买时效。在 OpenClaw 里比较稳的组合是：heartbeat + HEARTBEAT_OK 短路兜底周期任务，事件类走 webhook 直调，清单文件作为唯一入口。从默认 30 分钟轮询起步，等你能看清每次 tick 的产出，自然知道哪里需要推送。
