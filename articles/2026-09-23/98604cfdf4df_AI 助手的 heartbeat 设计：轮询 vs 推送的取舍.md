## 背景

个人 Agent 跑起来之后，第一个绕不开的机制就是 heartbeat：它决定助手“多久醒一次、醒来干什么”。消息汇总、日程提醒、记忆整理、插件状态巡检，几乎都挂在心跳上。OpenClaw 里的 HEARTBEAT.md 就是这个思路的落地——每次心跳读一份清单，有活干活，没活就睡。

问题在于，heartbeat 看起来只是个定时器，实际上决定了三件事：响应延迟、token 成本、系统复杂度。这三者怎么分配，就是轮询和推送的核心取舍。

## 问题：两种模型的边界

**轮询**：Agent 按固定间隔自检。实现极简，一个 cron 或 `setInterval` 就够，无状态、可预测、断线自愈（下一轮自动兜底）。缺点是空闲时段白烧：如果每个心跳都触发一次模型调用，哪怕无事发生，一天下来 token 开销非常可观。

**推送**：外部事件（webhook、消息队列、长连接）主动唤醒。延迟低、空闲零成本，但要求可被触达的端点或持久连接。家用网络在 NAT 后面，通常得加隧道或反向代理；断线重连、消息去重，都是额外工程量。

结论不新：没有一种方案通吃，工程上的正解是分层。

## 做法：三层结构

1. **廉价 tick 与昂贵 think 分离**。心跳本身只做零成本检查：读 HEARTBEAT.md 的修改时间、扫标记文件、查队列是否为空。只有命中条件才升级为一次模型调用。这一层能砍掉 90% 以上的无效开销。
2. **默认轮询打底**，间隔 15–30 分钟，加 ±15% 抖动。抖动是为了避免多 Agent / 多插件在同一秒齐射。
3. **关键路径才上推送**。对延迟敏感的触发（邮件到达、CI 失败、IM 提及）用 webhook 直接唤醒；轮询作为兜底，负责捡漏推送丢掉的事件。

落地步骤：先把心跳职责写成清单放进 HEARTBEAT.md（每项标注“每次都查”还是“仅标记时查”）；再在网关层挂 webhook 接收器，收到事件写一个标记文件；轮询循环里先扫标记，再决定是否唤醒模型；最后给每次心跳打日志，包括空转。

## 踩坑点

- **笔记本合盖**：suspend 之后定时器不触发，醒来需要 catch-up 逻辑——对比上次心跳时间戳，超过 N 个周期就补跑一次幂等汇总。cron 用户同理，建议用 anacron 语义或自己补。
- **重连没有退避**：推送链路断了立刻无限重试，服务端直接被打挂。指数退避 + 抖动是底线。
- **心跳处理不幂等**：补跑意味着同一段逻辑可能执行两次，所有 handler 必须能安全重复。
- **每次心跳都喊模型**：最贵的错误。宁可心跳便宜、频繁，也不要每次都完整推理。
- **时区和 DST**：定时任务按本地时间配置，夏令时切换那天会少跑或多跑一次。

## 可复用建议

- 心跳配置声明式、进版本库，改间隔和清单走 diff review。
- 空转也记日志。排障时“心跳是否按时发生”和“发生时做了什么”要能分开查。
- 连续失败翻倍间隔，封顶 2 小时，恢复后重置。
- 先轮询上线，跑两周看日志，再决定哪几个事件值得引入推送。大部分个人场景，轮询 + 廉价门禁已经够用。

## 总结

heartbeat 的本质是成本分配问题：轮询把钱花在空闲时，推送把钱花在复杂度上。对个人 Agent，先用带抖动的轮询加廉价前置检查兜住基本盘，再对真正延迟敏感的事件单独开推送通道，是验证过最省心的组合。别让“实时”成为默认要求——大多数心跳任务，晚十五分钟没人会发现。
