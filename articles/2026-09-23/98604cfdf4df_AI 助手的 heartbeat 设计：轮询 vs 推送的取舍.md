## 背景

OpenClaw 这类常驻型个人助手，核心能力之一是"主动"：不需要用户发消息，agent 自己按节奏醒来，巡检任务、检查待办、汇总提醒。这套机制就是 heartbeat。实现上只有两条路：轮询（定时唤醒）和推送（事件驱动唤醒）。这是老话题，但放进"每次唤醒都烧 token、每次唤醒都可能打扰用户"的 agent 场景，取舍逻辑和传统后端服务并不一样。

## 问题

我们最早的做法很直接：固定 5 分钟一次心跳，把 HEARTBEAT.md 的检查清单整体注入上下文。跑一周暴露三个问题：

1. **成本线性放大**。一天 288 次唤醒，每次都带完整会话上下文，哪怕 90% 的结果是"无事可做"，token 照付。
2. **延迟不匹配**。每日巡检 5 分钟可以忍；但 git push 触发任务、告警类事件靠轮询就明显迟钝，调短间隔成本又爆炸。
3. **推送不是银弹**。接上 webhook 后发现要处理验签、重试、去重、agent 离线时的事件补偿——省下的轮询成本，换成了事件管道的维护成本。

## 做法

现在采用"轮询兜底 + 推送加速"的混合结构：

1. **按事件源分类任务**。源本身能推（消息平台、git、监控告警）走 webhook 唤醒；源只能拉（无回调的网页和 API）保留轮询。不要强行统一成一种模式。
2. **分层心跳间隔**。默认 15 分钟一档做低频巡检；进行中的活跃任务临时切到 1–2 分钟的 fast lane，任务结束即回落。
3. **推送只做"唤醒信号"**。webhook 负载只带最小上下文（来源、事件类型、ID），agent 醒来后自己去拉全量数据。这样天然幂等去重，也避免把不可信 payload 直接灌进 prompt——这条是安全底线。
4. **心跳输出短路**。约定心跳轮次的输出默认不回给用户，只有命中 HEARTBEAT.md 里"需要上报"的条件才产出消息。没有这条，用户会被"我检查了一下，一切正常"淹没。
5. **加抖动和静默窗**。固定间隔容易整点对齐形成唤醒高峰，间隔加 ±20% 抖动；夜间设 quiet hours，只保留关键推送通道。

## 踩坑点

- token 成本按"唤醒次数 × 上下文长度"算，不是按任务数。清单塞得越长心跳越贵，控制在 20 行内，无关任务移出去。
- webhook 忘了验签，等于向互联网开放一个"唤醒我的 agent 并注入内容"的接口。payload 必须按不可信输入处理。
- 推送到达时 agent 正在跑任务：要么排队要么丢弃。我们选排队，会话结束后合并处理，不要假装支持中断。
- 容器或笔记本休眠会让定时器漂移，醒来后补一次"对账轮询"，别信任错过的那个时间点。

## 可复用建议

一条决策规则：**源能推且你守得住安全边界，就推；否则轮询；混合时推送负责低延迟，轮询负责对账兜底。** 从保守轮询起步（15 分钟 + 输出短路），先让成本可见，再逐个把高价值事件源迁到推送。上线后记录每次唤醒的触发原因和 token 消耗，一周后你自然知道该优化哪条路径。

## 总结

heartbeat 设计本质是在延迟、成本、可靠性三角里找位置。轮询简单可靠但贵且慢；推送高效低延迟，但引入安全与运维复杂度。对个人助手场景，"轮询兜底、推送加速、输出短路"是性价比最高的起点，也最容易逐步演进。欢迎在社区帖里晒你们的 HEARTBEAT.md 和唤醒成本账单。
