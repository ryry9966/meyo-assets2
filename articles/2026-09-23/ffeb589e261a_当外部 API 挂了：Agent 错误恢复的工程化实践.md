## 背景

在 OpenClaw 的典型场景里，Agent 的工具链往往横跨多个 MCP Server、HTTP 插件和第三方 API——搜索、天气、企业内部系统、各类 SaaS。任何一环抖动，整条任务链都会受影响。和传统后端不同，Agent 的失败模式更隐蔽：模型拿到空结果或报错文本后，常常不会承认失败，而是"脑补"一个像模像样的答案继续往下走。

## 问题：三类典型故障表现

1. **重试风暴**：超时后模型自主决定"再试一次"，没有上限，token 和配额被烧光。
2. **幻觉兜底**：工具返回 500，Agent 把错误信息当作数据解读，输出错误结论。
3. **级联阻塞**：一个慢接口卡死整个 workflow，后续任务全部排队。

## 做法：把恢复逻辑放在工具层，而不是提示词里

核心原则：超时、重试、熔断属于工程层，LLM 只负责消费结构化的失败信息。

1. **错误分类**：429 / 5xx / 超时 / 网络错误标记为可重试；400 / 401 / 403 / 404 为不可重试，直接失败并上报。
2. **显式超时**：每个工具调用都设 connect + read 双超时（如 3s / 15s），避免 MCP 长连接被挂死。
3. **有限重试**：指数退避 + 抖动（jitter），最多 2~3 次。退避不加抖动，多个 Agent 同时恢复时会形成惊群。
4. **熔断与降级**：连续 N 次失败后把该 provider 标记为 down，冷却期内快速失败，切到备用 API 或缓存。缓存必须带时间戳，降级输出要注明"数据可能过期"。
5. **结构化错误上抛**：工具返回 `{ok, error: {code, retryable, message}}`，让模型基于 retryable 决定：可重试 → 告知用户稍后重试；不可重试 → 换路径或终止。绝不能把空字符串或原始堆栈喂给模型。
6. **幂等保护**：只有幂等操作允许自动重试；写操作带幂等键，防止重复下单、重复发消息。

## 踩坑点

- **让模型自己决定重试**：在提示词里写"失败了就多试几次"，几乎必然演变成死循环。重试必须封装在工具层。
- **把 429 当普通失败熔断**：限流只需要放慢节奏，不该触发熔断，两者要区别处理。
- **吞掉异常返回空结果**：这是幻觉的头号来源，宁可返回明确的结构化错误。
- **备用链路从没测过**：主 API 挂了才发现 fallback 的鉴权早过期了。建议在预发环境定期做故障演练，直接 kill 掉依赖，观察 Agent 的真实表现。

## 可复用建议

- 所有外部调用收敛到一个统一的 resilient client（超时 + 重试 + 熔断 + 结构化错误），不要每个插件各写一套。
- 给关键 provider 配 preflight 健康检查，Agent 启动时先探活再开跑。
- 每次重试和降级决策都落日志，事后能复盘"当时为什么这么选"。
- 在系统提示里明确行为边界："工具报错时如实告知用户，不要编造结果。"

## 总结

Agent 的错误恢复不是提示词工程，而是系统工程。把超时、重试、熔断做进工具层，用结构化错误给模型一个诚实的输入，再给它一条体面的降级路径——API 挂了不可怕，可怕的是 Agent 假装一切正常。
