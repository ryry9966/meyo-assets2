## 背景

大部分 Agent 的工作模式是被动的：你发一条消息，它回一条。能力再强，也只是"问一句答一句"。真正让助手体验上一个台阶的，是 proactive——在你不说话的时候，它自己发现该做的事，办掉或者提醒你。

OpenClaw 这类常驻型助手天然具备做 proactive 的条件：有持久进程、有插件体系、能挂 MCP 工具、有稳定的消息通道。缺的不是能力，而是一套克制的触发与决策机制。

## 问题

把"主动"做砸的案例比做成的多，常见三种失败形态：

1. **噪音机**：每小时推一条"没什么大事"，第三天被静音。
2. **自嗨循环**：agent 主动跑的任务产生了新事件，又触发 agent，形成回环。
3. **越权代办**：没确认就执行写操作，删了文件或发了消息，信任一次性归零。

核心矛盾是：主动性的价值来自"少而准"，而调度器天然倾向"多而勤"。

## 做法

我在 OpenClaw 里用三层结构落地，思路可直接复用：

**第一层：触发源收敛。** 不要让所有事件直达 agent。我先写了一个 scheduler 插件，只接三类输入：cron 定时（如每天早上的汇总）、webhook 事件（CI 失败、监控告警）、轮询型检查（每小时扫一次仓库 issues）。其余信号先进队列。

**第二层：决策过滤。** 触发不等于行动。每个事件过一个小判断 prompt，输出三选一：忽略、入日报、即时推送。判断标准写在配置里：影响面（是否阻塞我）、时效（几小时内会恶化吗）、是否重复。去重靠本地 SQLite 记事件指纹，同指纹 24 小时内只推一次。

**第三层：分级出口与确认闸门。** 低优先级攒到固定时间的日报里，高优先级走即时通道。所有写操作（发消息、改文件、调 MCP 的 mutation 类工具）一律不直接执行，而是生成待确认卡片，点确认才跑；读操作放行。

这样 agent 有了"腿"，但每条腿上都有刹车。

## 踩坑点

- **循环触发**：主动任务写回状态文件，又触发了一次事件。解法是给事件加来源标记，来源为 agent 自身的一律丢弃，只允许一跳。
- **幂等性**：cron 任务网络重试后跑了两遍，日报发了两份。现在所有主动任务带任务 ID，执行前查重。
- **上下文膨胀**：主动触发时把全部记忆塞进去，token 费用翻了三倍。改成按事件类型注入最小上下文。
- **静默时段失效**：配置了 23 点后不推送，结果时区按服务器的 UTC 算了。定时类逻辑统一改用用户本地时区。
- **通知渠道泄露**：监控 payload 里带密钥片段，被原样推到群里。推送前加了一道脱敏过滤器。

## 可复用建议

- 给 proactive 定密度指标：目标是每周主动推送个位数，宁可漏报，不可滥报。
- 把"忽略 / 入报 / 推送"的阈值外置成配置，跑两周后按实际打扰率调。
- 主动 ≠ 自动完成。执行类动作默认加确认，除非操作可逆且影响范围可枚举。
- 给每个主动行为记日志，定期回看哪些被忽略——被连续忽略的规则直接下线。

## 总结

proactive 不是让 agent 更勤快，而是让它更会挑时机。触发收敛、决策过滤、分级出口、确认闸门，四件事做到位，助手才会从"工具"变成真正省心的协作者。建议先从一条每天一报的定时任务起步，跑稳了再逐步放开，比一上来就全自动化靠谱得多。
