## 背景

让助手"主动做事"是自动化的第一个分水岭。在 OpenClaw 这类常驻型 Agent 框架里，唤醒机制基本只有两种范式：**heartbeat 轮询**——Agent 定时醒来，读一份任务清单（比如 `HEARTBEAT.md`），自己判断干不干活；**推送**——外部事件（webhook、监控回调）直接把消息注入会话。两种我们都在生产里跑过，这篇记录一下取舍逻辑。

## 问题

轮询的代价是**空转**：绝大多数心跳周期里其实无事可做，但模型调用和上下文加载照常发生。推送的代价是**基础设施**：需要可达的入口、鉴权、事件路由，而且 Agent 离线或网关重启时事件直接丢失，没有补偿。

实际观察是：多数人高估了推送的必要性，低估了轮询的隐性成本。单独押注任何一边都会踩坑。

## 做法：分层混合

1. **底座用低频轮询**。30–60 分钟一次即可，醒来读任务清单，无事则返回一个极短的确认（如 `HEARTBEAT_OK`），不落主会话上下文，把空转成本压到接近一次 no-op 调用。
2. **高价值事件走推送**。只给"晚 30 分钟就没意义"的事件开推送：支付回调、CI 失败、关键告警。webhook → 网关 → 以系统消息注入。
3. **心跳只做判断，不做重活**。发现待处理任务时派生子会话执行，心跳本身只等摘要返回。
4. **推送侧做幂等与去重**。每条事件带去重键，网关层合并重试风暴。
5. **记决策日志**。每次心跳记录"触发/跳过 + 原因"，这是后续调间隔的唯一依据，比拍脑袋强得多。

## 踩坑点

- 间隔设成 5 分钟 + 清单太长，一天烧掉的 token 比正常对话还多，我们第一周就中招。
- 心跳回复直接写进主会话，用户对话历史被污染成日志流，检索质量明显下降。
- 推送没做去重，告警系统重试三次，助手连发三条一模一样的消息。
- 纯推送方案在网关重启窗口内静默丢事件，事后无人知晓——这是纯推送最隐蔽的坑。
- 忘了配置静默时段，凌晨三点被心跳触发的通知叫醒。
- 清单文件沦为垃圾场，什么都往里塞，单次心跳的判断时间越拖越长。

## 可复用建议

- **轮询兜底、推送加速**：轮询保证"最终会做"，推送保证"及时做"，两者是互补不是二选一。
- 心跳的成本红线：无事时一次心跳应近似一次 no-op，超了就先砍清单或拉长间隔。
- 三个指标定好再调参：日心跳成本、推送平均延迟、事件丢失数。
- 间隔宁可先长后短，根据决策日志逐步收紧，反向操作很难回头。

## 总结

心跳设计的本质不是"选轮询还是选推送"，而是给不同时效要求的事件分配不同的唤醒路径。低频轮询做安全网，事件驱动做加速器，再用决策日志和三个指标持续校准——这套结构在我们环境里稳定跑了数月，日心跳成本降到最初的十分之一以下，且没有再丢过关键事件。
