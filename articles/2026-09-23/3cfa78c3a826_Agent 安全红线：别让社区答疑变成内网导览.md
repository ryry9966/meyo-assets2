## 背景

社区里挂常驻 Agent 做群聊答疑、工单初筛、日常自动化的人越来越多。不少实例为了省事，直接跑在日常工作机上，MCP 一开就是 filesystem + shell + browser 全家桶。出问题往往不是被攻击，而是 Agent 在"正常回答"里把内部信息原样带了出来。

## 问题：三类高频泄漏源

1. **上下文泄漏**：Agent 能读本地文件和仓库，回答时顺手引用了内部路径、内网域名、配置片段。
2. **凭证泄漏**：`.env`、shell 历史、运行日志被读进上下文随回复输出；更常见的是调试时直接贴了带 token 的日志。
3. **工作流泄漏**：分享出去的 prompt、skill、插件配置里写满内部服务名、目录结构、审批链路——别人拿到的等于一张内网导览图。

还有更隐蔽的一条：社区消息本身就是不可信输入。一条构造过的 prompt injection，可能诱导有 shell 权限的 Agent 把文件内容主动发出去。

## 做法

1. **实例分离**。社区答疑实例和干活实例彻底分开：独立 workspace、独立凭证、独立会话存储。社区实例默认只读文件系统、不给 shell、不配任何内网可达的 MCP。
2. **权限收敛到刚好够用**。filesystem 指向一个干净的只读知识目录而不是家目录；shell 用命令白名单；网络出口走代理白名单。装新插件先看它声明了哪些能力，再决定给不给。
3. **系统提示词写红线，但别指望它兜底**。明确禁止输出：密钥与 token、`.env` 内容、内网域名和 IP、绝对路径（要求脱敏成 `~/` 或 `<project>/`）。真正的兜底靠下一层。
4. **出站过滤**。在回复管道上加一层正则/DLP 规则，匹配常见 key 格式、内网网段、token 前缀，命中即拦截或替换。实现成本很低，收益极高。
5. **调试先脱敏**。贴日志前过一遍 webhook 地址、Authorization 头、session 文件路径，这三个是最高频漏点。本地备一个脱敏脚本，形成肌肉记忆。
6. **审计留痕**。记录每次工具调用的时间、工具名、参数摘要，每周扫一遍异常；Agent 用到的 key 定期轮换——按"已经泄漏过"处理。

## 踩坑点

- **把提示词当安全边界**。注入可以覆盖指令，提示词只是"礼貌请求"，权限和过滤才是边界。
- **白名单的传递权限**。允许 `git` 约等于允许读全部历史；允许搜索约等于允许读索引覆盖的一切。按最坏情况评估每条授权。
- **memory 带私货**。内部上下文被长期记忆存下来，换个场景又被带出来。社区实例建议直接关掉长期记忆，或定期清空。
- **插件升级不复审**。新版本悄悄加了权限，旧的权限结论就作废了。升级 = 重新过一遍 scope。

## 可复用建议

- 沉淀一份**社区实例基线配置**：只读 FS + 无 shell + 出站过滤 + 无长期记忆，新实例直接套模板。
- 上线前自查五问：它能读哪里、能执行什么、能连哪里、记忆里有什么、回复有没有人定期抽检。
- 把脱敏脚本和过滤规则放进仓库，和 Agent 配置一起做版本管理，改动可追溯。

## 总结

Agent 泄漏很少是高技术攻击，多数是权限给多了、边界没设、回复没人看。把社区实例当成"随时可能被投屏到会议室"来配置，红线就守住了大半。最小权限、出站过滤、审计留痕这三件套不性感，但足够把事故概率压到可控范围。安全配置做得越早，后面省掉的事故复盘越多。
