## 背景

Agent 接上 MCP 工具和插件之后，真正的问题往往不是“它能不能做”，而是“该不该自己做”。我们团队跑自动化流程一段时间下来，最深的体会是：权限边界不是在提示词里加一句“请谨慎操作”就能解决的，它是需要在工具层显式设计的工程问题。

## 问题：两种典型失败

- **问太多**：每一步都要人工确认，用户很快进入“无脑点允许”状态，确认机制形同虚设。
- **问太少**：Agent 在一次批量操作里改了共享仓库的主分支，或者发出一封不该发的邮件，事后只能回滚道歉。

这两个失败是同一条曲线的两端，核心矛盾就一个：**确认成本 vs. 不可逆操作的爆炸半径**。

## 做法：两轴分类 + 运行时强制

**第一步：注册工具时就打两个标签。**

- 可逆性：操作能否用一次反向操作恢复？（git revert 可以；删数据、发邮件、调付费 API 不行）
- 影响范围：只碰本地临时文件，还是触及共享仓库、外部服务、真实用户？

**第二步：映射到四种策略。**

| 组合 | 策略 |
|---|---|
| 可逆 + 范围小 | 自动执行，记日志 |
| 可逆 + 范围大 | 自动执行，事后通知 |
| 不可逆 + 范围小 | 先 dry-run 输出 diff，再确认 |
| 不可逆 + 范围大 | 硬确认，且必须当轮确认，不接受预授权 |

**第三步：在 harness 层强制，不靠提示词。** 在 OpenClaw 侧把策略落到工具注册和确认钩子上：写类工具默认 deny，读类工具走 allowlist；不可逆工具强制走确认回调，执行前把 diff 摘要注入确认卡片，让人审的是“改了什么”，不是“它说它要干嘛”。

**第四步：加预算和护栏。** 单会话花费上限、可写路径白名单、分支隔离（Agent 只能在 feature 分支工作）——这些都是把软约束变硬约束的便宜手段。

## 踩坑点

1. **把权限规则只写进 system prompt。** 长会话下必然漂移，跑到第 40 轮它就“忘了”。规则必须由运行时兜底，prompt 只负责解释。
2. **确认疲劳。** 我们早期所有写操作都确认，一周后用户已经闭眼点允许。砍掉一半低风险确认之后，剩下的高风险确认反而被认真看了。
3. **让 Agent 自己评估风险。** 它对自己操作的置信度不可信——它以为“只是改个配置文件”，实际触发的是线上热更新。风险等级由人定，写死在工具元数据里。
4. **预授权过期。** “本次会话都允许”听着方便，但两小时后上下文已经完全变了。不可逆操作要求确认发生在执行的那一轮。

## 可复用建议

- 新工具接入先填分类卡（可逆性 / 范围 / 建议策略），没填完不上线。
- 写操作默认 dry-run，把确认动作变成“审 diff”。
- 全量审计日志：哪个会话、调了什么、参数是什么、结果如何，出事能回放。
- 每月过一遍工具清单，权限策略跟着实际使用数据调整。

## 总结

权限边界本质是产品决策，不是提示词调优。一句话版本：**可逆的让它跑，不可逆的给 diff，范围大的当轮确认，拿不准的默认问人。** 先把这条线画清楚，自动化才敢真正交到它手上。
