## 背景

OpenClaw 的 cron 任务本质上是“定时唤醒的 agent”：到点拉起一个会话，把你的 instruction 喂给模型，跑完把结果送出去，然后结束。它和聊天交互是两种完全不同的模式——聊天里有上下文、能追问、可以随时纠偏；cron 里没有，指令发出去的那一刻就是无人值守状态。

我维护着七八个定时任务：晨报、监控摘要、RSS 精选、周报汇总。早期踩了不少坑，这里整理成一套可复用的写法。

## 问题

新手写 cron instruction 最常见的错误，是把它当成聊天消息来写。典型症状：

- **依赖上下文**：“继续昨天那件事”“按之前说的方式来”。cron 每次唤醒的会话是新的，模型根本不知道“昨天”发生了什么。
- **歧义交给模型猜**：“帮我整理一下最近的新闻”。什么算“最近”？整理成什么格式？每次跑的结果都不一样。
- **没有失败路径**：API 挂了、文件不存在时，模型倾向于编一个看起来合理的结果。无人值守场景下这是灾难。

## 做法

核心原则：**把 instruction 当成给新同事的交接文档，假设它对之前的一切一无所知。**

结构上分五块：

1. **上下文**：一句话说清任务背景和数据来源。路径、URL、目标 ID 写具体值，不要写“那个文件”。
2. **步骤**：编号列表，一步一个动作，写明用什么工具。步骤有依赖就显式写“完成第 2 步后再执行第 3 步”。
3. **输出**：给固定模板。比如晨报任务规定：首行为日期，正文分三节，每节不超过 N 条。固定格式既方便下游解析，也方便你肉眼核对。
4. **失败策略**：明确写“任何一步失败，输出错误原文并停止，不要猜测、不要编造数据”。这句看着啰嗦，关键时刻救命。
5. **边界**：“只执行以上步骤，不要发送计划外消息，不要修改配置。”无人值守的任务，宁可能力小一点，也不要出格。

写完先手动触发一次（`openclaw cron run <id>`），翻完整会话日志，确认它实际调了哪些工具、结果投递到了哪里，再上正式频率。

## 踩坑点

- **时区**：cron 表达式按宿主机时区跑，instruction 里说“今天”时模型理解的“现在”可能对不上。涉及日期尽量以运行时注入的时间为准，或在指令里写明时区。
- **重复执行的状态**：任务是周期性的，要考虑“第二次跑”。比如只报增量，就得明确增量的判定方式（对比某文件、某时间戳），否则每次输出全量。
- **投递目标**：先确认任务是投递到某个渠道，还是只落在隔离会话里。不少人任务跑成功了，却找不到结果在哪。
- **敏感信息明文入指令**：token、密码用环境变量或凭证文件引用。cron 指令是明文存储、随时可查看的。
- **往指令里塞大段历史数据**：数据应外置到文件，指令里只给路径。数据更新不用改指令，也不会撑爆每次执行的开销。

## 可复用建议

- 沉淀一个五段式模板（上下文/步骤/输出/失败/边界），新任务先填模板再微调。
- 把跑歪那次的会话日志存下来，分析模型当时为什么那样理解，把歧义点写死进指令——instruction 的迭代本质是消歧。
- 一个任务一个独立 session，避免不同 cron 互相污染。
- 用 diff 思维改指令：每次只改一处，观察一轮再改下一处，否则你不知道是哪句话起了作用。

## 总结

Cron 任务的 prompt 工程，核心不是写得更“聪明”，而是写得更“防呆”：假设执行者失忆、无法追问、并且会犯错。上下文自包含、步骤可枚举、输出有模板、失败有出口、行为有边界——做到这五点，定时任务才能真的稳定跑起来，而不是隔三差五给你一个“惊喜”。
