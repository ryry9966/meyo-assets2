## 背景

我这边的常态是：让 OpenClaw 的 agent 起草技术文章和周报，模型输出 Markdown，这没问题。问题出在下游——同一篇稿子要发公众号、知乎、掘金和自己博客，四处的渲染能力完全不同。之前靠手工逐平台调格式，一篇稿子后排版时间比写作还长，于是把整条链路收成了一个人肉只过目一次的 Markdown 管线。

## 问题

拆开是三层：

1. **源头不干净**。LLM 产出的 Markdown 常见毛病：标题层级跳跃（H1 直接跳 H3）、加粗滥用、代码块不标语言、嵌套列表过深，偶尔还有编造的链接。
2. **平台方言**。公众号编辑器不吃标准 Markdown，会剥掉 `<style>` 和 class，代码高亮、表格、脚注全要特殊处理；知乎和掘金接近 GFM 但细节各异；自建博客侧最自由。
3. **资源处理**。相对路径图片、外链图床防盗链、GIF 体积限制，每个平台规则都不一样。

## 做法

整条管线分五步，全部落在仓库里：

**1. 单一源头。** 内容只有一份 `src/` 下的 Markdown，frontmatter 里声明 `targets: [blog, juejin, wechat, zhihu]` 和元信息。平台产物进 `dist/`，直接 gitignore。

**2. 规范化先行。** 发布前先跑 markdownlint（自定义规则：标题层级连续、代码块必标语言、禁止三层以上嵌套列表），配一个 remark 脚本自动修掉大部分问题，修不了的报错停下来，别带病发布。

**3. AST 转换，不写正则。** 用 unified/remark 把 Markdown 解析成 mdast，再按平台写转换插件。正则在嵌套结构和代码块面前必然翻车，AST 是唯一靠谱的路。

**4. 平台适配器。** 博客侧 frontmatter 直接可用；掘金/知乎基本 GFM 直出，只需处理目录和脚注；公众号最重——mdast 生成**内联样式**的 HTML，代码块预先分词着色成 span，超宽表格降级成列表。图片统一走 asset manifest，发布前上传对应平台素材库并替换 URL。

**5. 接进 OpenClaw。** 这套东西包成一个 skill：agent 读取草稿，跑 lint → 转换 → 输出 `dist/` 下各平台文件和预览 HTML。我人工过一遍预览，确认后才让它调公众号草稿箱 API 推送。机器排版，人把最后一道关。

## 踩坑点

- **公众号会剥 class 和 `<style>` 标签**，样式必须逐元素内联，别指望一次转换两端通用。
- **代码块在手机上横向滚动体验很差**，我在 lint 里加了 80 列软限制，比事后压缩字号有效得多。
- **相对路径图片发出去就是裂图**；外链图床在微信内还可能被防盗链拦掉。结论是别省事，老老实实传素材库。
- **frontmatter 忘过滤**，直接见报。转换插件的第一个测试用例就应该是它。
- **别手改 `dist/` 里的产物**。一改源头就分叉了，下次构建全部冲掉。

## 可复用建议

- 把发布当编译：源文件一份，产物可随时重建，删了也不心疼。
- 转换规则收敛成 remark 插件进仓库，可 review、可回滚，别散落在临时脚本里。
- lint 作为硬门禁，不过不发布。
- 任何自动推送前留 dry-run + 预览环节，API 重试也走同一入口，避免重复建稿。

## 总结

这套管线没有黑科技，核心就一句话：**把格式适配从每次发布的临场劳动，变成一次建好、持续复用的工程资产**。AI 负责生产内容，管线负责让它体面地到达每个平台，人只对内容本身负责。
