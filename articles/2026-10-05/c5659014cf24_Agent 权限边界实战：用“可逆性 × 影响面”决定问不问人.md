## 背景

这一年下来，社区里 Agent 的能力边界明显外移了：MCP 让模型能直接调 shell、写文件、发 HTTP 请求，插件让它能碰数据库和第三方 SaaS。能力上来之后，真正的工程问题只剩一个：**哪些动作它可以自己做，哪些必须停下来问人。**

## 问题

两种失败模式都很常见：

- **过度请示**：每步都要确认，Agent 退化成一个很贵的自动补全，人被弹窗淹没，最后开始无脑点“允许”。
- **过度放权**：一条 `rm`、一封发往真实用户的邮件、一次生产库 schema 变更，模型觉得“逻辑上没问题”就执行了。

这两种都不是靠 prompt 能根治的，本质是权限分层没做。下面是我们在 OpenClaw 环境里跑了三个月后沉淀的一套做法。

## 做法：两轴四层

把每个工具调用按两个维度打分：**可逆性**（能不能撤销）和**影响面**（会不会波及工作区之外），交叉出四层：

| 层级 | 特征 | 策略 |
|---|---|---|
| L0 | 只读、沙箱内 | 直接执行 |
| L1 | 工作区内可逆写 | 执行 + 全量日志 |
| L2 | 不可逆，影响面小 | 结构化确认：先展示 diff 再放行 |
| L3 | 不可逆且影响面大 | 人发起，Agent 只起草 |

落地三件事：

1. **在工具注册层做闸门，别指望模型自律。** 每个插件/工具注册时声明自己的层级；新增工具默认 L2，跑稳两周再降级。
2. **确认必须结构化。** 展示将要执行的具体命令、diff、收件人，附一句模型自己的风险评估。纯“是否继续？”的确认没有信息量。
3. **让 Agent 先自报层级再行动。** 如果它自评 L1 但工具注册的是 L2，这个不一致本身就是信号，直接拦截并记录。

## 踩坑点

- **确认疲劳是真问题。** L1 事件也弹窗，一周后人就会条件反射点允许，L3 的确认也就形同虚设。宁可少问，问就必中。
- **dry-run 不一定干。** 有些“读接口”有副作用（触发 webhook、消耗配额），幂等性要逐个验证，不能按方法名猜。
- **TOCTOU**：确认通过到实际执行之间环境可能已变——分支被合、文件被改、库存没了。高危操作放行后要重新校验前置条件，不能拿批准时的快照直接跑。
- **别信模型自评的风险。** 它能准确描述计划，但对“删这个目录会让 CI 挂多久”这种业务影响，它和新人一样没数。L3 的判定标准要人写死。
- **异步审批要设过期。** 等了六小时才拿到批准的 Agent，醒来执行的是六小时前的计划——中间世界已经变了。

## 可复用建议

- 新环境第一天就是默认拒绝，逐个工具开权限，和防火墙一个思路。
- 每周复盘一次 ask-log：问得太多说明分层过保守；一条都没问过，先怀疑闸门漏了。
- 区分“确认”和“知会”：L2 阻塞等批准，L1 只需事后通知。很多团队把两者混成一个弹窗。
- 权限配置进代码走 review，别躺在某个人的本地配置文件里。

## 总结

权限边界不是“信不信任模型”的态度问题，而是把每个工具调用按可逆性和影响面分层、在框架层强制执行的工程问题。一句话原则：**可逆的小事让它自己干并留下日志；不可逆的大事让它起草，由人扣扳机。** 模型的判断力会越来越强，但扣扳机的手，应该一直是人的。
