## 背景

社区内容运营有个老大难：每天都有值得整理的动态——新插件发布、GitHub release、群里的高频问题——但人肉筛选、撰写、排版、发帖，坚持两周就倦怠了。我的目标是做一个"每日精选"发帖机器人：自动收集、过滤、起草，人工审核后发布。核心约束只有一条：**模型永远不直接碰发布按钮**。

## 问题

拆下来其实是四个：

1. 信息源杂、格式脏，直接塞给模型既浪费 token 又容易跑偏；
2. 生成内容质量不稳定，语气会随时间漂移；
3. 定时任务重复触发、失败重试，极易造成重复发帖；
4. 自动化一旦出错是公开出错，撤回成本高。

## 做法

整体架构刻意做成"确定性管道 + 单点智能"：

```
cron 调度 → 采集脚本(纯代码) → 清洗/去重(SQLite)
   → Agent 起草(唯一用模型的一步) → 草稿队列(markdown)
   → 人工审批(聊天渠道回复固定指令) → 发布脚本(幂等) → 归档日志
```

1. **采集不用 Agent**。RSS、GitHub API、群消息导出全用普通脚本拉取，清洗成统一的 markdown 片段，连同 URL hash 存进 SQLite。
2. **去重在进模型之前**。对 URL 和标题做 hash 比对，重复的直接丢弃，不浪费一次调用。
3. **Agent 只做起草**。把过滤后的条目、固定模板、两三条人工写过的范例喂给 OpenClaw 的 agent session，输出就是一篇待审草稿。prompt 放在 git 里，随代码一起 review。
4. **审批走人**。草稿推送到我的聊天渠道，我回复一个固定指令才触发发布。发布脚本带幂等 key（日期 + 内容 hash），同一 key 只会成功一次。
5. **日志闭环**。每次运行记录输入/输出 hash、耗时、结果，每周扫一眼。

## 踩坑点

- **第一版让 Agent 直接调发布 API**，第二天就重复发了两条：一次是 cron 重叠触发，一次是重试没带幂等。教训：生成和发布必须是两个独立进程，中间隔一道闸门。
- **时区**。服务器 cron 默认 UTC，机器人每天早八小时发帖。现在所有调度显式写 TZ，加锁文件保证单实例。
- **prompt 漂移**。跑了两周，模型开始写营销腔。把模板收紧、范例换成人工写的旧帖、明确"禁止感叹号堆叠"后稳定下来。prompt 也是代码，要版本化。
- **原始 HTML 直接进上下文**，token 翻倍且模型容易被页面噪音带偏。先清洗成纯文本再喂，成本降了六成左右。
- **重试风暴**。发布接口限流后脚本退避重试，但重试前没查重，限流恢复后连发三条。任何重试前必须先查幂等表。

## 可复用建议

- 确定的逻辑用代码，模型只承担"创造性"那一步；
- 任何对外写操作前加闸门：人工审批或强幂等，最好两者都有；
- prompt、模板、范例进 git，改动走 review；
- 采集和去重放在模型之前，省钱且稳；
- 日志记 hash 而非全文，可审计又不泄露内容。

## 总结

回头看，这个机器人约 20% 的代码在调用模型，80% 在处理调度、去重、幂等、重试和审批。模型是整条链路里最不可靠的组件，架构设计的本质就是把它圈在最小的影响面里。现在它每天稳定产出一条草稿，我花三十秒审完发布——自动化没有替代判断，只是把判断压缩到了一次点击。
