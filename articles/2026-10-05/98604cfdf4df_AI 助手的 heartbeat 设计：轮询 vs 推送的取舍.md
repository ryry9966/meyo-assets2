## 背景

Agent 跑起来之后，第一件和"对话"无关的事，往往是让它主动干活：定时提醒、盯 CI、跟进未完成任务。这都需要一个"醒来"的机制。OpenClaw 里最直接的方案是 heartbeat——按固定间隔唤醒 agent，读一遍任务清单（比如 HEARTBEAT.md），没事就短促返回。另一种思路是推送：外部事件（webhook、消息队列、cron 触发器）直接把消息打进会话。两种都很常见，但放错场景代价不小。

## 问题

- **轮询的代价**：间隔设短了，token 成本线性上涨——哪怕每一拍都"无事发生"，模型调用照跑；设长了，事件响应延迟最坏等于一个周期。
- **推送的代价**：需要可达入口（公网 endpoint 或本地网关），要处理重试、幂等、乱序；agent 离线或重启窗口内的事件，没有队列就直接丢。
- 真实系统里两者不是非此即彼，难点在划界。

## 做法

1. **先按延迟要求和事件来源分类**。要秒级响应、且来源能发 webhook（CI 失败、新邮件、git push）→ 推送；分钟级可接受、本质是"查状态"（盘点任务清单）→ 轮询。
2. **轮询做底座**：heartbeat 间隔从 15–30 分钟起步，别一上来 5 分钟。heartbeat 的 prompt 保持极短：只说"读清单，无事返回 HEARTBEAT_OK"，让空转一拍的成本趋近于零。
3. **推送做快路径**：外部系统有事件钩子就接进来，消息只带最小标识（事件 ID + 类型），agent 醒来后自己拉全量状态，别把大 payload 塞进会话。
4. **混合兜底**：heartbeat 除轮询自身任务外，兼任 sweeper——扫一遍推送事件的落地队列，补上投递失败或离线期间丢的通知。这是"最终一致"的保险丝。
5. **观测**：每一拍记一行日志（时间、耗时、是否空转），一天下来 token 花在哪一目了然。

## 踩坑点

- **空 heartbeat 不等于零成本**：prompt 每拍都重放，系统提示一长，30 分钟一拍也能烧出可观的月账单。空转分支必须短路。
- **webhook 没做幂等**：上游重试一次，agent 就重复跑一遍任务。用事件 ID 去重，落盘再执行。
- **推送到达时 agent 正在长会话里**：事件插进来会打断上下文。要么排队到会话结束，要么明确标注为系统级插队。
- **心跳和用户会话共用一个 session**：上下文被心跳内容污染，回复质量下降。心跳走独立会话，或至少打标签隔离。
- **间隔写死、忽略时钟漂移**：cron 类触发器注意时区和抖动，长间隔加随机偏移，避免整点集中打爆下游 API 限流。

## 可复用建议

- 决策口诀：**有 webhook 就推，没 webhook 且能查就轮；延迟要求高必推，成本敏感必轮加长间隔。**
- 推送负责"快"，心跳负责"全"。任何纯推送架构，都值得加一个低频 sweeper 兜底。
- 心跳输出收敛成固定短 token（如 `HEARTBEAT_OK`），方便日志过滤和成本归集。
- 给每个 heartbeat 来源设每日预算上限，超限报警，而不是默默烧钱。

## 总结

轮询是正确性的底线——简单、可恢复、不需要公网入口；推送是延迟和成本的最优解——事件驱动、不空转。生产上几乎都是混合形态：推送走快路径，低频心跳做对账和兜底。先从 30 分钟的 heartbeat 起步跑通闭环，再按延迟需求逐个接入推送，比一上来搭事件总线靠谱得多。
