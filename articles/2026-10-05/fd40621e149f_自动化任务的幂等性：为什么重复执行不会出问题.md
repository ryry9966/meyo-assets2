## 背景

在 OpenClaw 里做自动化，重复执行几乎是必然事件：cron 任务可能因为网关重启被补跑；webhook 可能因为对端超时而重发；agent 调工具失败后，模型自己会重试；你自己也可能手动重跑一次"看看是不是坏了"。本地单机脚本尚可人工兜底，但当任务开始写外部系统——发消息、建 issue、写数据库、调计费 API——"多跑一次"就变成了真实事故。

幂等性的定义很朴素：同一操作执行一次和执行 N 次，最终状态一致。它是分布式系统里"恰好一次"这个不可能目标的工程替代品——放弃保证只执行一次，转而保证重复执行无害。

## 问题

看一个常见反例：定时任务每天检查日历，有新日程就推送到群里，实现是"查日程 → 发消息 → 追加一条记录"。某天网关重启，任务被补跑，群里出现两条一模一样的通知。更隐蔽的是链式写操作：任务先创建文件，再调外部 API，第二步失败后重跑，文件被创建了两份。

问题不在重试机制本身，而在我们默认了"只执行一次"这个假设。

## 做法

我的做法分四步，多数场景够用：

1. **区分读和写。** 读操作天然幂等，不用管；精力全放在产生副作用的写操作上。
2. **给每次执行一个稳定的幂等键。** 不要用随机 ID，用可推导的：cron 任务用 `任务名 + 计划执行时间`，webhook 用事件自带的 event id。关键是重试时键不变。
3. **执行前查去重记录，先落状态再动手。** 去重存储不需要复杂，一张 SQLite 表即可：

```js
if (db.get(taskId)) return skip;   // 已执行过
db.set(taskId, "running");         // 先落记录，再执行
await doWrite();                   // 真正的写操作
db.set(taskId, "done");
```

4. **优先用幂等的表达方式改写操作本身：** upsert 代替 insert，"设置为 X" 代替 "在 X 上加 1"，按 key 覆盖文件代替 append。操作越接近"声明最终状态"，天然越幂等。

如果外部 API 自带幂等参数（不少支付、消息类 API 有），直接传，比自建去重可靠。

## 踩坑点

- **只靠 if 判断去重，没有兜底约束。** 两次触发在毫秒级同时到达，检查都通过，写了两遍。去重记录要加唯一索引，靠冲突失败兜底，而不是靠时序。
- **幂等键里掺了每次都变的成分**（精确到毫秒的时间戳、随机 UUID），重试时键变了，去重形同虚设。
- **半路失败不记进度。** 任务有五步，第三步失败，重跑从第一步来，前两步重复执行。长任务要按步骤记录状态，从断点续跑。
- **忽略"读也可能有副作用"：** 标记已读、消耗配额的查询接口，重放一样出事。
- **去重记录只增不删**，半年后查重变慢。给记录加过期时间，过期即视为可重跑。

## 可复用建议

- 把去重逻辑收敛到插件统一入口，做成一个 `withIdempotency(taskId, fn)` 包装器，业务代码不必各自实现。
- 写插件时在工具描述里明确幂等语义："重复调用安全，会覆盖旧值"或"重复调用会产生重复副作用"——agent 会据此决定是否重试。
- 设计任务时先问一句：这个任务被跑两遍会发生什么？如果答案让你不舒服，先改设计再上线。

## 总结

重复执行不是需要消灭的异常，而是自动化的常态。与其追求"只执行一次"这种脆弱保证，不如把每个写操作设计成跑多少遍结果都一样。在 OpenClaw 里成本很低——一个稳定的幂等键加一张去重表——但它把"至少一次投递 + 幂等消费"这个成熟模式搬进了个人自动化体系。先假设任务会被跑两遍，再动手写第一行代码。
