## 背景

OpenClaw 的 cron 任务本质很简单：到点拉起一个 agent 会话，把 instruction 作为用户消息发进去，跑完把结果推送出来。它和日常聊天有三个关键区别：**没有上下文、没有追问机会、没有人盯着**。很多定时任务效果不稳定，根源不在调度，而在 instruction 仍按聊天 prompt 的思路在写。

## 问题

我早期的 cron instruction 大概长这样：

> “每天早上帮我看一下仓库的 issue，有重要的告诉我。”

跑起来后三种症状轮流出现：输出时长时短；工具调用失败后模型自己编数据凑结果；明明没有任何变更也照发不误，推送很快变成噪音，最后只能关掉。

## 做法：把它当成给值班同事的任务简报

核心转变是假设执行者是一个能力很强但**完全不了解背景**的新同事，他只能看到这一段话。于是 instruction 需要五个部分：

1. **任务目标**：一句话说清做什么；
2. **数据来源**：明确用哪个工具 / 命令 / MCP skill，禁止“凭记忆回答”；
3. **执行步骤**：可操作的判断逻辑，而不是笼统的“分析一下”；
4. **输出格式**：固定模板，最好带状态行；
5. **异常与静默规则**：失败时报告失败，无变化时明确不推送。

一个实际例子（每日 issue 巡检）：

```text
任务：检查仓库近 24 小时的 issue 动态。
数据来源：仅使用 github 工具查询，不要凭已有知识回答。
步骤：
1. 拉取近 24 小时新建/关闭的 issue；
2. 按 bug / feature / question 分类；
3. 标出标题含 crash 或 regression 的条目。
输出格式：
状态：OK / EMPTY / ERROR
摘要：一行
明细：每条一行，[类型] #编号 标题
异常处理：工具失败只输出 ERROR 和原因，禁止编造数据。
静默规则：无变更时只输出 EMPTY，不补充任何内容。
```

改造之后输出稳定了，下游用一行 grep 判断状态行就知道这次要不要推送。

## 踩坑点

- **“和上次一样”**：cron 会话没有记忆，这类指代必然落空。所有上下文必须内联在 instruction 里。
- **模糊时间词**：“今天早上”依赖模型猜时区。要么写相对窗口（“近 24 小时”），要么确认运行环境会注入当前时间。
- **时间写两遍**：执行频率归 cron 表达式管，instruction 里不要再写“每天”，两处不一致时只会埋雷。
- **没有异常分支**：工具报错后模型倾向于“体面地”补一个结果，这是编造的主要来源，必须显式封死。
- **一个任务塞十件事**：单次运行超时或半途而废，拆成多个小任务，各自带独立输出。
- **输出无格式**：只要下游有脚本解析，自由文本迟早出事。

## 可复用建议

- **新同事检验法**：把 instruction 发给一个不了解背景的人，他能否不追问就完成？不能，就补上下文。
- **先手动后挂载**：新 instruction 先直接贴进对话里跑几天，稳定后再挂 cron；排查时也用这个方法二分问题在调度还是在指令。
- **instruction 入库**：每个 cron 的指令存成文件进版本管理，改动有 diff 可查，出问题能回滚。
- **状态行是刚需**：OK / EMPTY / ERROR 三个值覆盖大多数场景，值得成为默认模板。

## 总结

Cron instruction 的目标不是写得聪明，而是写得**可执行**：无状态假设、明确数据源、固定输出格式、显式异常出口。把它当成一份给值班同事的任务简报，而不是一句随口的嘱托，无人值守任务的成功率会有立竿见影的改善。
