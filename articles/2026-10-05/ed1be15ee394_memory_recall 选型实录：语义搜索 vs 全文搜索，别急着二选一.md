## 背景

Agent 跑久了，记忆必然堆积：会话摘要、用户偏好、踩过的坑、临时决定。OpenClaw 的 `memory_recall` 负责在每轮任务前把这些"捞回来"。捞得准，省 token、回答稳；捞不准，要么漏关键事实，要么塞一堆无关内容占满上下文窗口。

捞取靠什么检索？社区最常见的争论就是：上 embedding 做语义搜索，还是老老实实用全文检索（BM25 / grep）。

## 问题

我最初的直觉是"语义搜索更智能"，第一版直接上了向量库。跑了两周，出现两类高频翻车：

1. **精确标识符检索失败**。查"ERR_CONN_RESET 那次"，语义搜索返回一堆"网络异常相关"的记忆，偏偏漏掉真正记录这个错误码的那条。embedding 对错误码、函数名、路径、UUID 这类 token 基本无感。
2. **换一种说法就查不到**。反过来，全文检索遇到"当时怎么解决 Webhook 重试的"这种换过措辞的查询，如果记忆里写的是"回调丢失补偿"，就一个字都对不上。

结论：两者各有明确的失效模式，不是谁取代谁。

## 做法

现在的方案是混合检索，步骤如下：

1. **先建评测集再动手**。从真实使用中攒了 40 条查询，人工标注期望命中的记忆条目，算 recall@5。没这个，后面全是凭感觉调参。
2. **全文检索打底**。BM25 足够，毫秒级延迟、零额外成本。
3. **语义搜索补盲区**。记忆按"一条事实一个条目"切 chunk，embedding 模型选中文效果过得去的即可，不必追新。
4. **两路结果用 RRF 合并**（Reciprocal Rank Fusion），比调相似度阈值稳得多。
5. **结构化条件走过滤不走检索**。时间、项目名、来源这类字段，检索前先过滤，别指望 embedding 搞定"上个月的"这种语义。

## 踩坑点

- **中文全文检索别裸切**。按空格分词等于没有分词，实测 bigram + BM25 比精确子串匹配的召回好很多。
- **相似度阈值是个伪解**。cosine 0.78 在 A 类查询是垃圾，在 B 类是精确命中。RRF 只看排名不看分数，绕开了这个坑。
- **索引和记忆库会漂移**。记忆更新后忘重建索引，recall 命中的还是旧版本，现在把重建挂在写入钩子上。
- **别拿"相似"当"相关"**。语义搜索最擅长把一大堆"都挺像"的结果排前面，评测集里要专门留几条"看着像但没用"的负例。

## 可复用建议

- 先全文后语义：全文是基线，语义是补丁。没有评测数据证明盲区存在，别引入向量库的复杂度。
- 给 `memory_recall` 加日志：记录 query、返回 ID、agent 实际引用了哪条。这是最便宜的反馈信号，也是迭代依据。
- 若走 MCP 封装，把两路检索合并成一个 `memory_recall` 工具暴露给上层，agent 不需要感知实现细节。
- 延迟敏感场景算笔账：全文毫秒级，embedding 一来一回 100–300ms 加 API 费用，高频调用时差距会放大。

## 总结

语义 vs 全文不是二选一，而是分工：标识符、专有名词交给全文；换措辞、模糊意图交给语义；RRF 合并，评测集说了算。先测量、再上马，检索层才不会变成玄学调参现场。
