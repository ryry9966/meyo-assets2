## 背景

团队每天要写日报，但信息散落在 git 提交、服务日志、任务看板里。人工整理费时、容易漏，质量也因人而异。OpenClaw 侧我们已经接好了 agent 和若干 MCP 工具，于是顺手把这件事做成了一条自动流水线。跑了大约一个月，把做法和问题记录一下。

## 问题

最初的设想很直接：让 agent 读日志、写日报、定时推送。试了两周，暴露出三类问题：

- 原始日志异构且嘈杂，不同来源格式各异，直接塞进上下文既费 token 又稀释重点；
- 模型输出不稳定，数字和段落结构隔天就变，幻觉风险真实存在；
- 调度不可靠，cron 明明跑了，agent 却静默失败，没人知道今天缺了一份日报。

## 做法

流水线分四段，每段是独立脚本，中间产物以 JSON 落盘，可单独重跑：

1. **采集**：三个脚本分别拉 git log、服务日志、任务状态。git 用时间窗参数限定当天，日志先按关键字过滤再截断，输出统一为带 `source / timestamp / payload` 字段的 JSON 行。
2. **清洗聚合**：去重、按模块分桶、做计数统计。这一步把几千行日志压成一两百行的“事实清单”——所有数字在这里算好，不交给模型算。
3. **Agent 汇总**：OpenClaw agent 接收事实清单和固定模板，prompt 里的约束只有三条：

```text
- 只允许引用输入中出现的数字，不得推算
- 按约定 schema 输出 Markdown 段落
- 信息不足时写"今日无相关记录"，禁止编造
```

4. **校验与分发**：先做 schema 校验（必需段落、字段完整性），不通过就携带错误信息重试一次；通过后推送 IM webhook，并归档一份 Markdown。最外层由总控脚本包住 cron，跑完检查产物时间戳，失败就告警。

## 踩坑点

- **让模型算数**：早期把原始日志直接丢给 agent，统计数字时对时错。改为脚本算数、模型只负责组织语言后，问题消失。
- **时区**：git log 的时间窗按本地时间，服务日志却是 UTC，第一天日报“丢了半夜的提交”。采集层统一转 UTC，展示层再转回。
- **cron 环境**：手工能跑，cron 下 PATH 和环境变量不对，MCP 插件连不上。总控里显式加载环境，别依赖登录 shell。
- **静默失败**：agent 抛过异常但进程退出码为 0，日报没出也无人察觉。现在每个阶段都写状态文件，总控据此决定是否告警。
- **输出漂移**：模型隔段时间就“创造性”地调整段落结构。few-shot 范例冻结进模板，配合 schema 校验兜底，漂移会被重试拉回来。

## 可复用建议

- **中间产物落盘**：排查问题时逐段重放即可定位，不必重跑全链路。
- **每段幂等**：重跑同一天不应产生重复推送，分发层按日期做幂等键。
- **先干跑一周**：日报先只写文件不推送，人工比对质量后再开自动分发。对自动化的信任要靠一段时间的观察建立。
- **prompt 当代码管理**：模板改动走版本化，出问题能回滚到上一版。

## 总结

这条流水线的核心思路不是“让 AI 写日报”，而是把工作切开：采集、清洗、校验交给确定性脚本，模型只做它可靠的那一段——组织语言。跑通之后，日报质量比人工稳定，数字全程可追溯；省下的时间反而是次要收益。
