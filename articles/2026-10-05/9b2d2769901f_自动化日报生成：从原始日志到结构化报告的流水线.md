## 背景

团队里每天要写日报的人不少：研发写进展、运维写变更、值班写告警。而这些信息的原始形态早就存在——git 提交、CI 记录、告警日志、工单系统。问题从来不是“没数据”，而是数据散落、口径不一，最后靠人肉拼凑。

我用 OpenClaw 搭了一条日报流水线，稳定跑了一个多月，下面是实测的做法和踩过的坑。

## 问题

最初的方案很朴素：cron 定时把当天原始日志直接丢给 Agent，让它“总结成日报”。跑了一周就暴露出几个问题：

- 日志一多就超上下文，报告随机缺内容；
- 数字常被模型“顺手改过”，和原始记录对不上；
- 输出格式持续漂移，群里的人得反复适应；
- 某天流水线静默失败，没人发现，日报空缺。

本质上这不是提示词问题，而是一条数据管道的可靠性问题。

## 做法

现在拆成五步，“取数”与“写作”严格分离：

1. **采集**：三个小脚本分别拉 git log、CI 记录、告警日志，统一输出 JSONL，每条带时间戳和来源标记；能封装成 MCP tool 的就封装，Agent 只负责调用。
2. **过滤**：按固定时间窗（前一天 00:00–24:00，时区写死）截取，剔除健康检查等噪音；单源超过阈值就按仓库/服务预聚合，控制进入模型的体量。
3. **结构化提取**：Agent 按预定义 JSON Schema 输出四类字段：完成事项、异常事件、关键指标、待确认项。所有数字在脚本侧算好传入，模型只做归类和转述，不做计算。
4. **渲染**：结构化数据套固定 Markdown 模板生成日报。格式由模板保证，不由模型保证。
5. **投递与兜底**：经消息通道推到群，同时落一份 JSON 快照保留 14 天；Schema 校验失败带报错自动重试一次；采集为空时照常生成“零事项日报”并单独告警，杜绝静默失败。

## 踩坑点

- **时区错位**：日志时间戳是 UTC，人按本地时间读日报，第一天窗口错开 8 小时。窗口边界必须写进配置，并且印在日报头部（“数据窗口：xx 至 xx”）。
- **别让模型算数**：让它数 commit 数，它会给你个“大概”。数字一律脚本算好，模型只引用。
- **日志量突变**：某天 CI 抽风产生几千条记录，直接打爆上下文。预聚合加硬上限是刚需，超限时降级为按服务汇总，而不是让任务失败。
- **格式漂移**：最初让模型直接输出成品 Markdown，两三天格式就变。拆成“模型提取 + 模板渲染”后才稳定。
- **静默失败最危险**：脚本挂了不报错，群里只是没消息，最容易漏。现在零产出会触发独立告警。

## 可复用建议

- 把日报当“数据 + 视图”：中间产物是带 Schema 的 JSON，Markdown 只是其中一个视图，以后接邮件、面板都不用改上游。
- 日报头部带上数据窗口和各来源条数，读者自己能判断可信度。
- 原始快照保留一段时间，排查“这个数哪来的”全靠它。
- 先接一个来源跑稳，再横向加，别一次铺满。

## 总结

这条流水线没有用到什么复杂技巧，核心是工程习惯：固定时间窗、结构化中间产物、模板渲染、空产出告警。模型在其中只承担“归类与转述”这一小段，其余都交给确定性代码。自动化日报这件事，可靠性设计的比重远大于提示词本身。
