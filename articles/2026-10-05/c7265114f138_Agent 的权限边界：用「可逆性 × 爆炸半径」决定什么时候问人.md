## 背景

在 OpenClaw 里接的 MCP 工具多了之后，一个绕不开的问题浮出水面：agent 拿到一堆工具，哪些能直接调，哪些必须先过人？我们跑了几个自动化流程（代码仓库操作、消息通知、数据写入），踩了不少坑，把经验整理成这篇。

## 问题

两种失败模式都很典型：

- **管太松**：agent 自己执行了删除操作、往生产库写了数据、把消息发到了错的频道，等发现时已经无法挽回。
- **管太严**：什么都要确认，用户退化成"无脑点同意"的橡皮图章，自动化收益归零，还制造了虚假的安全感。

核心矛盾在于：**靠模型自己判断"这危不危险"是不可靠的**。prompt 里写"危险操作请先确认"没有强制力——模型会在长任务中途忘记，或在上下文压缩后丢掉这条约束。

## 做法：两轴四象限

把每个工具调用沿两个维度分类：

1. **可逆性**：能不能撤销？git revert、重跑一次 = 可逆；删数据、发消息、花钱 = 不可逆。
2. **爆炸半径**：只影响 agent 自己的工作区，还是波及外部系统、其他人的数据？

由此得到四象限：

| | 小范围 | 大范围 |
|---|---|---|
| **可逆** | 自动执行（读文件、跑本地测试） | 自动执行 + 审计日志（推 feature 分支、写测试环境） |
| **不可逆** | 自动执行 + 配额限制（清理自己的临时产物） | **必须问人**（生产写入、对外发消息、涉及费用） |

落地步骤：

1. **在工具注册处打标**：每个 MCP tool 标注 `read / write / irreversible / external`。这是配置，不是 prompt。
2. **在 harness 层加确认网关**：`irreversible` 和 `external` 的调用被代码拦截，转人工确认。用代码保证，不靠模型自觉。
3. **规范"问人"的格式**：必须附带 diff、影响说明、回滚方式，不许只问"可以继续吗"。目标是让人 5 秒内能做决策。
4. **写操作支持 dry_run**：先返回将要发生的变化，确认后再真执行。
5. **全量审计日志**：记录每次工具调用的时间、参数、结果、是否经过确认。

## 踩坑点

- **询问疲劳**：初期我们把"发消息"和"删文件"都设成必确认，一周后用户开始闭眼点 yes。确认门槛必须**少而重**。
- **工具粒度太粗**：把整个 GitHub 插件标成高危，结果读个 issue 也要确认。按操作类型分级，不按插件分级。
- **幂等性缺失**：任务超时重试后，同一次授权被执行了两遍。写操作要带幂等键，确认结果落状态缓存，可复用。
- **授权上下文丢失**：长任务里 agent 问过人、拿到答复，但上下文压缩后它忘了自己已有授权，又问一遍，甚至绕开。授权要写到会话状态里，不能只留在对话流中。

## 可复用建议

- 权限边界放在**配置层**（工具元数据 + 网关代码），不放 prompt 层。
- 低频、高价值的确认 > 高频、低价值的确认。宁可少问，问了就值得。
- 每月复盘一次审计日志：哪些确认被秒批、哪些自动执行后来被回滚，据此调整分级。
- 给 agent 一个明确的**降级动作**：不该自动干的事，停下来整理好上下文等人，而不是自作主张找个近似方案。

## 总结

权限边界不是"信不信任模型"的态度问题，而是一个工程问题：用可逆性 × 爆炸半径做分类，用网关强制执行，用日志持续校准。模型负责判断，系统负责兜底——这条边界划在代码里，才靠得住。
