## 背景

现在大多数 AI 助手是"应答式"的：你发消息，它回消息。但真正省时间的往往是另一类动作——CI 挂了它先告诉你、每天早上它把昨天的 issue 汇总好、某个配置文件变了它主动跑一遍 lint。这就是 proactive（主动式）能力：不等指令，由外部事件或时间驱动 Agent 自己动起来。OpenClaw 生态里这类需求很常见，但落地质量差别很大，多数问题不在提示词，而在架构。

## 问题

把"定时跑一下 Agent"当成 proactive，通常会撞上三件事：

1. **成本失控**：心跳频率高、每次都唤醒大模型，账单先爆；
2. **噪音失控**：什么都推，用户两周内静音所有通知，主动变成骚扰；
3. **动作失控**：无人值守时 Agent 拿着写权限自主执行，出一次事故就全盘下线。

核心矛盾是：**主动的频次应该由价值决定，而不是由 cron 表达式决定。**

## 做法

把 proactive 拆成四层，每层独立可替换：

**1. 触发层。** 三类来源：定时（cron / MCP 暴露的 scheduler 工具）、事件（webhook、文件 watcher、git hook、收件箱）、阈值（指标越线）。事件源尽量复用现有基础设施，不要为 Agent 单独造一套。

**2. 闸门层（关键）。** 触发不等于行动。先过一道便宜的检查：规则匹配（比如"只在失败时继续"）→ 不确定时用小模型判断 → 只有值得处理才唤醒完整 Agent：

```python
def on_event(evt):
    if not rule_match(evt):      # 规则先行，零成本
        return log.skip(evt)
    if small_model.worth(evt):   # 小模型兜底判断
        agent.run(evt, budget=1) # 限预算执行
```

**3. 执行层。** 单次任务限定工具白名单：观察类任务只给读权限；写操作默认走"草稿 + 人工确认"，跑稳两周再逐项放开。每次执行带幂等键，防止同一事件被重复处理。

**4. 送达层。** 分级投递：常规事项进每日摘要（digest），异常才即时推送。每条主动消息必须自含三件事：**为什么触发、做了什么、需要你做什么决定**。同时写一份 journal，让 Agent 知道自己主动做过什么，用户也能审计。

## 踩坑点

- **心跳循环没分级**：5 分钟一次大模型心跳，一个月烧掉半年订阅费。先规则后模型，绝大多数心跳应该死在规则层。
- **事件回环**：Agent 发的修复 commit 又触发 CI webhook，Agent 再修……必须做去重和幂等，出现两次相同动作自动熔断。
- **重复汇报**：状态只存内存，重启后忘了"昨天已报过"，用户连收三份相同摘要。状态要落盘，幂等键持久化。
- **cron 时区**：服务器 UTC、本地 UTC+8，摘要每天下午四点才到，甚至触发两次。
- **权限一步到位**：第一天就给写权限，出一次事之后团队再也不信任 proactive。

## 可复用建议

- 第一个场景选"高频、只读、失败成本低"的：每日 repo 摘要、CI 失败通报、依赖更新提醒。别一上来做自动执行。
- 给主动行为定预算：每天最多 N 条即时推送，超出合并进摘要。预算写进配置，不靠自觉。
- 观察两周 journal 再放开权限，用数据决定哪些动作可以无人值守。
- 闸门逻辑独立成模块，让不同场景复用同一套"值不值得叫醒 Agent"的判断。

## 总结

Proactive 不是一个提示词技巧，而是一个管道问题：触发、闸门、执行、送达、状态，五件事各司其职。实际工作量分配大概是 10% 写触发器，90% 调闸门和降噪。当你的助手第一次在你开口之前，把一件真正要紧的事送到位，这套架构就值回来了。
