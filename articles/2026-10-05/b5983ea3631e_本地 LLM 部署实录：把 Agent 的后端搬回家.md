# 背景

对写 Agent、挂 MCP 工具的人来说，跑本地模型的动机通常不是"省 API 费"这么单一：自动化任务经常携带隐私数据（本地文件、日历、相册、家庭设备事件流），走云端有顾虑；Agent 循环一次任务可能几十次调用，调试阶段 token 烧得心疼；家里断网时链路还不能瘫。本地模型解决的是这三个具体问题，而不是替代一切。

# 问题

真正的门槛不是"能不能跑起来"，而是三件事：

1. 硬件预算决定模型上限，选错档位很常见；
2. Agent 场景的瓶颈是**工具调用质量**，不是聊天流畅度——不少榜单分高的模型一接 MCP 工具就开始编参数；
3. 显存/内存是动态预算：权重 + KV cache + 系统占用要一起算。

# 做法

我的参考环境：一台 32GB 统一内存的 Mac + 一台 4060Ti 16G 的台式机。

1. **选运行时**。Ollama 上手最快，自带 OpenAI 兼容端点；要细粒度控制（KV cache 量化、flash attention 开关）用 llama.cpp；要 GUI 管理用 LM Studio。三者 API 形态一致，随时可换。
2. **按硬件定档位**：
   - 8GB 显存 / 16GB 内存：7-8B，Q4 量化，能跑但工具调用不稳；
   - 16GB 显存 / 24GB 统一内存：14B，Q4/Q5，是"Agent 可用"的起步线；
   - 24GB 显存 / 32GB+ 统一内存：27-32B，Q4，工具调用才接近云端水平。
3. **部署一条命令**：`ollama pull qwen2.5:14b-instruct-q4_K_M`，确认 `localhost:11434/v1` 可用。
4. **接入 Agent**：把 base_url 指到本地端点，先跑一个只挂一个 MCP 工具（如文件读取）的最小 Agent 验证调用链路，再逐步加回完整工具集。

# 踩坑点

- **上下文默认值是陷阱**。Ollama 默认 num_ctx 很小，长对话被静默截断，Agent 表现为"忘事"而非报错。显式设置 num_ctx，且注意 KV cache 随长度线性涨——权重刚好塞满显存时，长上下文必然 OOM。
- **工具调用必须实测**。我脚本化跑了自己的 20 个真实 MCP 任务各 20 轮：7B 正确率不到一半，14B 稳定在八成以上，32B 才基本可用。别信通用榜单，用你自己的工作流当 benchmark。
- **思考型模型会污染输出**。部分模型把推理过程混进 content 字段，Agent 的 JSON 解析直接崩。要么关思考模式，要么解析器做兼容。
- **笔记本注意散热**。持续 Agent 循环下很多机器中途降频、吞吐腰斩。评估要测持续负载，不是单次问答。

# 可复用建议

1. 把模型和运行时版本当依赖锁死（模型 tag + runtime 版本写进配置），避免"换了个量化版本，行为全变"。
2. **混合路由最务实**：本地模型接简单任务（分类、摘要、格式转换、低风险自动化），复杂推理走 API。在网关层按任务标签路由，两边协议一致，切换零成本。
3. 显存粗算：按量化位数估权重，加 num_ctx 对应的 KV 开销，宁可留 20% 余量。
4. 有 Mac 的话，统一内存是性价比最高的路线，同价位能装的模型比独显大一到两档。

# 总结

本地部署不是替代云端，而是多一层选择：隐私敏感、高频、低难度的任务下沉本地，难任务留在云端。真正的门槛不在安装，而在用真实工作流评估工具调用质量、算清显存账、锁好版本。这三件事做扎实，家用电脑跑大模型就是个普通的工程问题，不是玄学。
