## 背景

OpenClaw 默认一个主模型跑所有会话，但实际负载并不均匀：复杂规划、多步工具调用、长上下文推理只占少数请求；大量的是心跳总结、通知分类、记忆压缩这类轻任务。全走 GPT/Claude 这类云端模型，成本和延迟都浪费；全走本地模型，agent 循环的质量又撑不住。多模型路由要解决的就是这个分流问题。

## 问题

难点不在"能不能配"，而在"怎么判"。有三个判断维度：

1. **任务复杂度**：是否涉及多步工具调用和规划；
2. **上下文长度**：本地模型窗口普遍偏小；
3. **隐私敏感度**：日志、私聊内容是否愿意出网。

很多讨论只讲成本，忽略了一个更关键的事实：本地模型在 function calling 上普遍不稳。一旦被路由进 agent 主循环，工具调用格式出错，整条链路就废了——而且这种失败往往是静默的。

## 做法

1. **分层定义模型**。第一档：云端强模型（GPT-4o / Claude），负责主会话、规划、工具调用；第二档：云端轻模型，负责摘要、改写；第三档：本地模型（Ollama 跑 Qwen / Llama），负责批量分类、记忆整理、日志压缩。
2. **按任务类型路由，不按时间路由**。在插件和 sub-agent 里显式指定模型：记忆压缩的定时任务固定走本地；主 agent 的 fallback 链设为「云端强 → 云端轻」。
3. **用 MCP / 插件拆任务**。把不需要强推理的环节（比如网页正文提取后的摘要）独立成子任务，指定本地模型跑，结果回传主循环。
4. **用 trace 数据驱动切档**。每次请求记录 model 字段，一周后回看：哪些任务降级后质量没掉，就正式切到低档。

## 踩坑点

- **本地模型进主循环**：工具调用格式错、参数幻觉，表现为 agent 反复重试。教训：agent 循环只用确认支持 tool calling 的模型。
- **会话中途切模型**：记忆和风格出现断层，上下文续不上。切档时宁可新开会话。
- **上下文超窗**：长会话塞给 8k 窗口的本地模型会被静默截断，答案看起来通顺，其实丢了信息。路由前先估 token。
- **本地模型冷启动**：Ollama 首次加载可能要几十秒，定时任务需要预热或保活。
- **fallback 死循环**：云端限额后反复降级重试，务必加退避和告警，否则一夜跑完额度。

## 可复用建议

- 路由按任务类型，不按时段；
- 主循环用强模型，边缘任务用本地；
- 所有降级决策基于 trace 数据，不凭感觉；
- 隐私敏感任务（涉及私聊内容、密钥处理）默认本地或本地优先；
- 路由规则保持三层以内，规则越多越难排查。

## 总结

多模型路由的本质是分层：把「需要推理能力」和「只需要格式正确」的任务分开。OpenClaw 的插件和 sub-agent 机制天然适合这种拆分。先用 trace 数据定位可降级任务，再逐步切换，比一开始就设计一套复杂路由规则靠谱得多——路由是长出来的，不是设计出来的。
