## 背景

日常开发里，Git 操作占掉大量碎片时间：写 commit message、切分支、清理合并后的旧分支、整理提交历史。这些事不难，但重复、打断心流。OpenClaw 这类支持 MCP 的 Agent 框架成熟之后，很自然的想法是：把这部分机械劳动交给 AI 助手。

## 问题

先把要解决的痛点列清楚：

1. **commit message 质量差**——`fix`、`update` 满天飞，半年后回看完全不知道改了什么；
2. **分支堆积**——本地几十个已合并分支不敢删，远程还有一堆 `experiment/*`；
3. **上下文切换出错**——在错误的分支上改了一通才发现。

目标不是让 AI 全权接管 Git，而是让它做一个**有边界的代办员**。

## 做法

### 1. 接入 MCP Git 服务，权限做减法

在 OpenClaw 里挂 git MCP server：读操作（status / diff / log / branch）全开；写操作只放行 commit 和 branch 创建；push、rebase、reset、force 一律不进白名单。

### 2. 提交信息自动化

定义一个 skill，流程是：`git diff --staged` → 生成符合 Conventional Commits 的 message → 回显确认 → commit。核心提示词大致是：

```
角色：Git 提交助理
输入：git diff --staged 输出
输出：type(scope): subject，subject 不超过 50 字符
规则：只描述改了什么，不猜测业务意图；不确定的破坏性变更标注出来
禁止：静默提交、自动 push
```

关键点：message 必须回显给用户确认，不要静默执行。

### 3. 分支清理走提案制

一条定时任务：每周让 agent 跑 `git branch --merged main`，列出可删分支，输出清单等人确认。agent 只建议，不执行删除。

### 4. agent 分支命名约定

AI 创建的实验分支统一加 `ai/` 前缀。来源清晰，后续一行命令批量清理。

## 踩坑点

1. **AI 不懂"为什么改"**：它只看得到 diff，看不到你的业务意图。生成的 message 描述"改了什么"没问题，但 scope 划分和 breaking change 判断经常出错。复杂提交别偷懒，自己补上下文。
2. **`git add -A` 是雷**：让 agent 自主 staging 很容易把 `.env`、临时文件带进去。staging 范围要显式指定，并配合 pre-commit hook 做最后防线。
3. **工作目录漂移**：多仓库环境跑久了，agent 可能搞错 cwd，把操作落在别的仓库上。在 skill 里加一步 `git remote -v` 校验，确认是目标仓库再动手。
4. **push 权限绝对不给**：自动 push 到个人分支看起来省事，但一次错误的 force push 就够你回滚半天。push 永远人工触发。

## 可复用建议

- **权限最小化是前提**：在 MCP 层做命令白名单，而不是靠 prompt 里写"请不要 force push"。
- 所有写操作走**"生成 → 回显 → 确认 → 执行"**四步，一步不省。
- agent 的 git 操作留日志，出问题能回溯。
- 从只读场景起步：比如让 agent 汇总两周提交记录生成 changelog 草稿，验证输出质量稳定后，再逐步放开写权限。

## 总结

AI 管 Git 的正确姿势是**提案者 + 受限执行器**，不是决策者。提交信息、分支清单、历史整理这类活它干得比人快；但 push、删除、历史改写这些不可逆操作，确认权必须留在人手里。这套流程搭起来大概半天，之后每天省下的碎片时间远超投入——前提是边界先划好。
