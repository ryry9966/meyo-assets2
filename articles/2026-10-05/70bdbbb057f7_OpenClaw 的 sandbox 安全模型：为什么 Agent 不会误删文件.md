## 背景

OpenClaw 的 Agent 默认带一整套工具链：读写文件、执行 shell、跑定时自动化。能力越全，风险越具体——你本地跑着一个能执行 bash 的进程，而它的"大脑"是概率模型。sandbox 就是为这个矛盾设计的。

## 问题：误删不是玄学，是必然概率

真实的误删路径很少是"模型发疯"，大多是工程化错误：

- **相对路径歧义**：Agent 猜错 cwd，`rm -rf ./build` 落在了别的目录；
- **变量为空**：`rm -rf "$TMP_DIR"/cache` 里 `TMP_DIR` 没赋值，命令退化成危险形态；
- **通配符过宽**：`rm -f *.log` 在错误的目录层级执行；
- **链式传播**：一步"清理"只是长自动化链的中间环节，上下文不足以判断它危险。

这些错人类也犯，区别是人类会怕，模型不会。所以防线不能建立在"模型会小心"上。

## 做法：四层防线

OpenClaw 的 sandbox 不是单一开关，而是叠加的四层：

1. **工作区边界**。Agent 启动时绑定 workspace，文件类工具默认以此为根，路径解析被约束在这棵目录树内。workspace 之外不是绝对禁止，而是"降权"——需显式配置才能访问。
2. **容器沙箱**。对不信任的自动化任务，把工具执行放进 Docker 容器：宿主机文件以只读或白名单方式挂载，容器内删得再狠，宿主机无损。这是唯一能真正兜住 `rm -rf` 的一层。核心开关示意（具体键名以当前版本文档为准）：

```json
{ "agents": { "defaults": { "sandbox": { "mode": "all" } } } }
```

3. **工具策略**。每个工具三档：allow / ask / deny。日常只放行读写和受限 exec；能落地任意 shell 的 `exec` 设为 ask，危险命令需要人工点头。
4. **执行审批 + 快照**。批处理、递归删除、覆盖写入前，先做快照或让流程停在审批点。审批不是不信任 Agent，是给链式自动化留一个人工断点。

一个最小的心智模型：前两层管"能不能碰到"，后两层管"碰到了要不要过问你"。

## 踩坑点

- 本地直跑模式默认**没有**容器沙箱，很多人误以为有。去配置里确认 sandbox 状态，别凭感觉。
- 图省事把整个 HOME 挂进容器，等于没有沙箱。挂载白名单宁可小、不可大。
- 审批疲劳：ask 档设太多，人会本能地"总是允许"，防线悄悄退化。只把不可逆操作留在 ask。
- 把 docker socket 挂进沙箱容器——经典逃逸路径，整个沙箱直接作废。
- sandbox 外测试通过 ≠ sandbox 内行为一致：挂载路径、运行用户、环境变量都可能不同。

## 可复用建议

- **默认拒绝**：新 Agent 先 deny 大部分工具，按需逐个放行。
- 破坏性自动化只跑在容器沙箱里，宿主机永远不保留直跑路径。
- 跑批处理的 workspace 独立、可整体删除重建——"可丢弃"是最强的安全属性。
- 保留工具调用审计日志，事后能回答"它到底执行了什么"。
- 用对抗性 prompt（如"帮我清理所有临时文件"）在测试 workspace 里演练一遍，确认防线真的会触发，而不是在脑子里确认。

## 总结

Agent 不会误删文件，不是因为模型聪明，而是架构上让它**删不到**（边界+沙箱）、**删前有人拦**（策略+审批）、**删了能恢复**（快照）。sandbox 的价值不在于防止某一次事故，而在于把"模型会犯错"从祈祷变成假设。假设它会犯错，然后让犯错的代价变得便宜。
