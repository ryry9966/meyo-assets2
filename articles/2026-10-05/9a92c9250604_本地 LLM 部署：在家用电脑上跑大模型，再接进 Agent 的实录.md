## 背景

把 LLM 接进 Agent/MCP 工作流之后，一个现实问题很快浮现：你的文件、日程、自动化日志都在往云端 API 发。对个人自动化场景来说，把"执行层"放到本地，隐私和成本都会好看很多。这篇帖记录我在家用台式机（RTX 4070 Ti 12GB）上部署本地模型、并接入 OpenClaw 工具链的完整过程。

## 问题

大多数教程停在 `ollama run xxx` 就结束了，但 Agent 场景真正要回答的是三个问题：

1. 这张卡到底能跑多大的模型？
2. 用什么推理栈，遇到瓶颈怎么换？
3. 模型接进 Agent 后，function calling 和长上下文稳不稳？

第三点最容易被忽略——demo 里能调工具，跑一晚上自动化循环就崩了。

## 做法

**第一步：按显存定模型规格（Q4 量化）**

- 8GB：7B～9B，够做分类、摘要类任务
- 12～16GB：14B，或 Qwen3-30B-A3B 这类 MoE（激活参数少，出字速度很快）
- 24GB：32B Q4，本地体验的甜点位

**第二步：选推理栈**

- Ollama：省心，自带 OpenAI 兼容端点，先跑通
- llama.cpp：需要精细控制时再上（KV cache 量化、grammar 约束、layer 分配）
- vLLM：吞吐高，但要求 Linux + 显存富余，家用卡一般用不上

**第三步：接入 Agent/MCP**

- 把 base_url 指向本地 `/v1` 端点
- 确认 chat template 真的支持 tool call（llama.cpp 记得加 `--jinja`）
- 结构化输出用 JSON schema 强约束，别靠 prompt 里礼貌请求
- 每个工具调用设超时和一次重试
- 上下文给 16k～32k 就够，不要拉满

## 踩坑点

- **上下文一长就爆显存**：KV cache 是显存大头。降 context、开 flash attention、KV cache 用 q8_0 量化，30k 上下文就能稳住。
- **工具调用"声明支持"但实测解析失败**：小模型吐的 JSON 会崩。schema 约束 + 失败重试必须做，不要裸奔。
- **CPU offload 后速度崩塌**：部分层放内存，token 速率掉到个位数，Agent 循环体感像死机。宁可换小一档的模型。
- **跑分高 ≠ 工具调用强**：我最后自建了 20 条真实任务的回归集，比看榜单有用得多。
- **模型文件混乱**：同名不同量化、不同 commit，启动参数必须和文件版本一起记录。

## 可复用建议

1. 用一个 shell 脚本或 docker-compose 固化启动参数（模型文件、ctx 长度、fa、kv 量化），做到一键复现。
2. 写个 30 行的评测脚本：喂 20 个你自己的真实任务，diff 输出结果，换模型前先跑一遍。
3. 做混合路由：高频、低风险的步骤走本地，复杂推理回退云端 API，成本和可靠性兼顾。
4. 持续记录三个指标：tokens/s、首 token 延迟、工具调用失败率。数字比体感诚实。

## 总结

本地模型在 Agent 场景里的定位不是替代云端，而是承担隐私层和高频执行层。路径是：按显存选规格 → Ollama 先跑通 → 按瓶颈决定是否迁移 llama.cpp；工具调用必须用 schema 约束加回归集验证。整个流程两天能落地，之后每次换模型都变成一次可控的实验。欢迎在评论区贴你的显卡规格和实际跑通的配置，攒一份社区实测表。
