## 背景

跑 OpenClaw 久了，最直观的瓶颈往往不是模型能力，而是"一个 agent 串行干活"。让它同时整理一批文档、给几个仓库跑迁移脚本、再查一轮资料，单 agent 只能排队做，上下文越堆越长，后面任务的输出质量肉眼可见地下滑。

subagent（子 agent）编排就是针对这个问题的：主 agent 负责拆任务、发任务、收结果，子 agent 各自带着独立上下文并行干活。OpenClaw 的多 agent 运行时天然支持这种模式，MCP 工具也能按子任务分别挂载。

## 问题

真正动手前，难点不在"能不能开多个"，而在三件事：

1. **任务怎么拆**——粒度太细，编排开销超过收益；太粗，并行度上不去。
2. **上下文怎么给**——子 agent 看不到主对话，prompt 不自包含就会瞎干。
3. **结果怎么收**——多个子 agent 返回的东西格式各异，主 agent 汇总容易翻车。

## 做法

我目前稳定的做法是四步：

**1. 主 agent 只做两件事：拆分和汇总。** 在主 agent 的 prompt 里明确禁止它自己动手执行子任务，防止它"顺手"串行干完，并行就名存实亡了。

**2. 子任务 prompt 自包含。** 每个子 agent 的 prompt 必须写全：目标、输入路径、可用工具、输出格式。我强制要求返回固定结构的 JSON（比如 `status / result / files_changed`），主 agent 汇总时解析成本几乎为零。

**3. 权限按子任务收敛。** 子 agent 只挂载它需要的 MCP 工具：写文件的任务才给写权限，纯调研任务连 shell 都不给。

**4. 并发从 2 开始压测。** 先跑 2 个并行，确认 API 限流和结果质量，再逐步拉到 4、6。失败的任务单独重试一次，仍失败则降级为主 agent 串行兜底，保证整体任务不卡死。

## 踩坑点

- **上下文污染**：早期我把主对话历史一并塞给子 agent，结果它继承了主任务的"预设立场"，跑偏了。子 agent 的上下文应该从零构造，只喂它需要的那部分。
- **权限没收敛**：一个调研类子 agent 拿到了写权限，"热心"地改了不该改的配置。现在权限是子任务定义的一部分，不是全局默认。
- **输出格式靠自觉**：不强制 JSON 的时候，子 agent 有时返回大段散文，主 agent 汇总时丢信息。格式约束必须写进 prompt 并附示例。
- **粒度太细**：试过把"整理 10 篇文档"拆成 10 个子任务，编排和汇总的开销比串行还慢。经验值是 3-5 个子任务，每个约 5-15 分钟的工作量。
- **限流打爆**：6 个并行 agent，每个还带工具调用，请求数直接翻倍撞限流。并发上限要按"agent 数 × 平均工具调用数"估算，不能只看 agent 数。

## 可复用建议

- 把子任务 prompt 做成模板，参数只留目标和路径，跑同类任务时直接复用。
- 主 agent prompt 里写死汇总格式，例如"按子任务编号逐条列出结果，失败项单独成段"。
- 子 agent 之间不直接通信，统一通过共享工作区（文件）交接，主 agent 做仲裁，避免消息风暴。
- 每次编排留日志：子任务数、耗时、失败数。跑几次就能摸到自己环境里的并发甜点。

## 总结

subagent 编排不是"开多开快"那么简单，核心是**隔离与约束**：上下文隔离、权限隔离、输出格式约束。把这三件事做扎实，3-5 个并行子 agent 的模式在真实任务里是稳定可复用的。建议先小并发验证，再逐步放大，别一上来就梭哈。
