## 背景

用 OpenClaw 做日常自动化一段时间后，最明显的瓶颈不是模型能力，而是主会话的上下文。主 agent 是长期驻留的会话：读代码、跑命令、查文档、处理消息，所有中间输出都堆在同一个窗口里。任务一多，就会出现"前面塞满日志，后面答非所问"的典型症状。

subagent 编排就是针对这个问题：主 agent 只做拆解和汇总，具体执行交给若干个拥有独立上下文的子 agent，能并行的就并行跑。

## 问题

上周一个典型场景：让 agent 同时做三件事——统计仓库本周改动、检查依赖是否有安全更新、汇总成一份周报草稿。串行跑有三个毛病：

1. **慢**。每步都要等上一步，总时长是累加的。
2. **上下文互相污染**。统计改动时翻了几十个 diff，轮到查依赖时，窗口里全是无关内容。
3. **汇总质量差**。主 agent 要从一大堆中间过程里"回忆"结论，容易漏。

## 做法

我们的拆法分五步：

**1. 先判断任务能不能拆。** 标准是：子任务能独立完成、结果能压缩成一段话。"分头收集、最后汇总"的结构天然适合；强依赖前序结论的任务别硬拆。

**2. 写清任务描述。** 每个 subagent 的输入是一段自包含的 prompt：目标、范围（限定目录/仓库）、禁止事项（不许改共享文件、不许 push）、返回格式（结论 + 变更文件列表 + 风险点）。子 agent 看不到主会话历史，别指望它"自己知道上下文"。

**3. 收敛工具与权限。** 只读任务就不给写权限；MCP server 按子任务单独挂——统计改动的挂 git 类工具，查依赖的挂 registry 查询工具。权限收敛比并发本身更重要。

**4. 并行有前提：写操作隔离。** 多个子任务都要写文件时，用独立目录或 git worktree 隔开，最后由主 agent 统一合并。读操作天然可并行。

**5. 结果必须压缩。** 要求 subagent 返回固定格式的短摘要，而不是完整过程。主 agent 只消费摘要——这是整个方案成立的关键，否则上下文只是从主会话挪到了子会话，汇总时照样爆。

另外把并发数控制在 2–3 个：既压时长，失败时也好排查。

## 踩坑点

- **并行写同一文件**：两个 subagent 同时改一个 README，后写的覆盖先写的。写操作必须隔离或串行。
- **任务描述塞太多背景**：把主会话历史复制给子 agent，等于没拆分，token 翻倍。
- **subagent 再开 subagent**：嵌套 spawn 难以控制深度和成本，我们直接在规则里禁止。
- **失败静默**：子 agent 超时后返回半成品，主 agent 当正常结果汇总了。要约定"失败必须显式说明"，并在主 agent 侧做基本校验。
- **成本意识**：并行 = token 消耗叠加。批量跑之前先单任务跑一次，确认产出质量再放量。

## 可复用建议

- 沉淀一个任务描述模板：**目标 / 范围 / 禁止事项 / 返回格式**，四个字段填空即可复用。
- 写操作统一走 git worktree，主 agent 只负责 merge 和 review。
- 子任务设计成幂等的，失败重跑不产生副作用。
- 先串行跑通，再开并行；串行能跑对，并行才有意义。

## 总结

subagent 编排不是"并发魔法"，本质是两件事：**上下文管理**（独立窗口 + 结果压缩）和**权限隔离**（工具按任务收敛）。把这两点做扎实，主 agent 才能保持清醒，多个子 agent 并行才真正换来时长和质量的收益。欢迎在社区里贴出你们的编排结构和踩坑记录。
