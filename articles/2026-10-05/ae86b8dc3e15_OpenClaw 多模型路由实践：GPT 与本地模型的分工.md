## 背景

OpenClaw 的价值在于 agent 跑在自己机器上、贴着自己的数据。但模型这一层，多数人最后都会遇到同一个分叉：云端模型（GPT 系列、Claude 等）能力强、上下文长，但按 token 计费，消息原文还要出网；本地模型（Ollama/vLLM 起一个 Qwen 或 Llama）免费、数据不出门，能力上限却和你的显存上限高度相关。

我的结论是不站队：按任务类型分流，混合使用。

## 问题

一开始我全走云端，月底看日志才发现：60% 以上的调用是消息摘要、格式转换、定时报告这类轻活，用旗舰模型纯属烧钱。反过来试过全走本地，MCP 工具调用频繁翻车——小模型生成的工具参数经常不合 schema，agent 卡在重试循环里。

于是问题变成：路由策略怎么定，才既省钱又不牺牲成功率。

## 做法

**1. 先分类，再路由。** 翻一周会话日志，把请求归成四类：轻量文本处理（摘要/翻译/格式化）、意图判断与转发、工具调用（MCP）、复杂推理与代码。顺手统计每类的 token 量和失败率——这份数据比任何"最佳实践"都好用。

**2. 建静态路由表。** OpenClaw 支持在 agent 级别绑定模型，这比在对话里手动切模型靠谱得多。我的分配：

- 日常摘要、定时任务、频道速览 → 本地 8B 级模型
- MCP 工具调用、代码相关 → 云端旗舰
- 涉及私信原文、密钥、账单的内容 → 强制本地

**3. 规则优先，不要上分类模型。** 渠道来源、触发方式（cron 还是消息）、内容关键词，在网关层用规则就能判断。先跑一个本地小模型做意图分类再分发，看着高级，实际多一跳多一次出错机会，延迟也翻倍。

**4. 设计升降级路径。** 云端为主的应用，本地做 fallback，应对限流和断网；本地为主的应用，定义质量信号——JSON 解析失败、用户重试、响应超时——触发升级到云端，同时设最大重试次数，防止 A 挂了切 B、B 挂了又切回 A 的死循环。

**5. 落日志。** 每次路由记录：任务类型、命中模型、首 token 延迟、token 消耗、是否成功。这张表是后续调路由的唯一依据。

## 踩坑点

- **小模型的 function calling 不能裸用。** 参数 JSON 坏、选错工具是常态。要么加 schema 校验加重试，要么规定工具调用固定走强模型，别省这个钱。
- **本地模型上下文窗口小，且截断是静默的。** 长对话塞进去不报错，但中间内容已经丢了。路由前先估 token，超限直接走云端。
- **冷启动。** 本地模型首次加载可能十几秒，容易被误判成卡死。常驻技能把模型预热好，或配置预加载。
- **量化版本差异比想象中大。** Q4 和 Q6 在工具调用上可能差一截，别看榜单，拿自己的任务集跑分。
- **显存争抢。** 网关、embedding、本地 LLM 挤一台机器，一个服务启动另一个就 OOM，给本地模型留够余量，或干脆分机。

## 可复用建议

- 建 20–50 条真实任务的评测集，路由表用数据定，不拍脑袋
- 先静态路由跑两周，日志证明某类任务浪费明显，再考虑动态路由
- 留一条手动逃生通道：消息带特定标记（比如 escalate）强制走云端，排查问题时救命
- 模型组合"少而强"优于"多而弱"，每多一个模型就多一份维护成本

## 总结

多模型路由的本质，是把模型能力和任务需求对齐，而不是炫技。OpenClaw 的 agent 级模型配置足够支撑静态路由起步；动态路由、质量门控这些，等日志告诉你需要时再上。先跑两周日志，再调路由表——顺序别反。
