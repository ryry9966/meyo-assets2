## 背景

跑 Agent 这两年，我的主力工作流早已从"聊天"变成"让模型调工具"：MCP 服务读文件、查数据库、触发自动化脚本。但云端 API 有两个问题：按调用计费，高频 Agent 循环下成本涨得快；且部分本地数据不适合出内网。把模型搬回家用电脑，成了很自然的一步。这篇记录我在一台 32GB 内存 + 12GB 显存消费级显卡上的完整部署过程，以及挂到 OpenClaw 里跑真实的工具调用任务后踩过的坑。

## 问题

Agent 场景和纯聊天不一样，有三个硬要求：

1. **工具调用必须稳定**：模型要能可靠输出结构化参数，丢一个字段整条自动化链路就断；
2. **上下文要够长**：system prompt + MCP 工具 schema + 多轮观察结果，轻松上万 token；
3. **接口要兼容 OpenAI 格式**，才能直接挂进 OpenClaw 的 provider 配置，插件和 MCP 侧不用改。

## 做法

1. **盘硬件**：显存决定上限。12GB 显存跑 14B 的 Q4 量化比较稳；32B 会溢出到内存，速度直接掉一个数量级。
2. **选运行时**：Ollama 上手最快，llama.cpp 可控性最强。我最终用 llama.cpp 的 server 模式，打开 `--jinja` 让模板支持工具调用。
3. **选模型**：优先查社区里实际的 tool calling 反馈，而不是只看榜单分数。
4. **起服务**：监听本机端口，暴露 OpenAI 兼容接口，OpenClaw 里把 baseURL 指过去即可。
5. **建回归集**：写 20 条固定任务（含参数抽取、多工具编排），每次换模型或量化档位都跑一遍，人工核对输出。

## 踩坑点

- 某些 14B 模型榜单很好看，但实际调用工具时会漏字段或编造参数，只能换；
- **KV cache 很吃显存**：上下文从 8k 拉到 32k，显存占用几乎翻倍，别只按模型文件大小估算容量；
- Q4 以下量化偶尔产出不合法 JSON，结构化输出建议开 grammar 约束；
- 嵌入模型单独跑一个轻量的，别让主模型兼职 embedding；
- 权重溢出到内存后速度崩溃，宁可换小一号的模型。

## 可复用建议

- **分层路由**：意图分类、格式化这类轻任务用 7B，规划和多工具编排才上 14B/32B，延迟和显存都友好；
- 模型文件用哈希固定版本，配置里写清 tag，避免"升级后行为变了"却查不到原因；
- 回归脚本进仓库，换模型像升级依赖一样有记录、可回滚。

## 总结

本地模型不会全面替代云端 API，但在隐私敏感、高频、低难度的 Agent 任务上完全够用，且延迟可控。关键路径是：先明确"哪些任务值得下放"，再按显存选型，最后用回归集守住质量。跑通之后，整条 OpenClaw + MCP 的自动化链路就可以在断网环境下稳定工作了。
