## 背景

订阅源没有死，只是没人有时间读。相比推荐流，RSS 的输入完全可控：来源自己选、算法不掺和。我在 OpenClaw 里搭了一条「抓取 → 过滤 → 摘要 → 推送」的管线，跑了六个多星期，现在每天信息摄入压缩成一份几分钟就能扫完的 digest。这篇记录做法和踩坑，不谈宏大叙事。

## 问题

把 RSS 条目直接丢给模型，实际会遇到三个具体问题：

1. **噪音远多于信号**，全量摘要的话 token 成本完全不可控；
2. **摘要质量不稳定**，模型爱脑补原文没有的细节；
3. **管线中断后补跑混乱**，重启容易重复推送，或者漏掉中断期间的条目。

## 做法

整体分四层，每层都是普通函数加一次 agent 调用，刻意不做复杂编排：

1. **抓取层**：cron 每 2 小时拉一次订阅列表（部分没有 RSS 的站走 RSSHub 转换），解析出 guid、link、title、published、content，写入 SQLite。幂等键用 guid 的 hash，重复直接跳过。
2. **过滤层**：用便宜模型做二分类打分（相关 / 无关 + 一句话理由），prompt 里放 10 个我认可的正例标题，只保留达标条目。这一步砍掉约七成。
3. **摘要层**：对过滤后的条目做批次摘要，每批 5 条，模板固定为「背景 / 要点 / 与我的关联 / 值得深挖的点」，用比过滤层更强的模型。
4. **推送层**：通过 MCP 工具或 webhook 推到 IM，digest 格式固定，方便扫读。

另外挂了一个手动触发的 reindex 命令，中断后按 hash 补跑，已推送的不会重推。

## 踩坑点

- **content 字段不可信**。很多源只给截断摘要，必须对相关条目再抓一次全文，否则摘要只能复述标题。
- **跨源重复**。同一条新闻常在多个源出现，仅靠 URL 去重不够，加了一层标题 3-gram 相似度，超过 0.7 就合并。
- **摘要脑补**。初版经常补原文没有的细节，后来在 prompt 里加硬约束："只允许使用提供的原文内容，信息不足就写信息不足"，改善了一个数量级。
- **时间格式五花八门**（RFC822、ISO、缺时区都有），统一在入库时归一化为 UTC，否则 digest 排序会乱。
- **源偶发 503**。做指数退避 + 连续失败计数，连续 5 次失败就在 digest 末尾提示该源疑似失效。

## 可复用建议

- 别一上来做 agent 编排。先写成纯函数管线跑稳，再把摘要那一步换成 agent 调用，排查问题时心智负担小很多。
- SQLite + hash 幂等是这类管线的万金油，成本几乎为零，任何时候都能安全重跑。
- 过滤和摘要拆成两次模型调用，比一个巨型 prompt 又快又省，各自迭代互不影响。
- prompt 模板进版本库。摘要质量回退时能 diff 出改了什么，而不是靠记忆猜。

## 总结

这条管线真正的价值不是"AI 摘要"本身，而是把阅读从被动刷变成主动筛。跑稳之后，每周花十分钟迭代一次 prompt 和订阅源列表就够了。核心逻辑两百行以内，想动手的建议从抓取层开始，当天就能跑通第一版。
