## 背景

OpenClaw 的 cron 任务让 agent 定时醒来干活：每天早上汇总资讯、盯一轮指标、扫一遍收件目录。很多人第一次配置时的做法，是把聊天里的 prompt 直接粘过去——“帮我看看最近有什么值得关注的，整理一下发我”。跑起来多半是三种结果：有时输出很长，有时啥也没干还硬编了几条，有时任务越跑越慢。

原因很简单：交互式 prompt 默认旁边有人补上下文、回答追问、判断“差不多了”。cron 任务没有这个人。所以 cron instruction 不是对话开场白，而是一份**任务契约**。

## 问题

无人值守运行时，instruction 必须自己回答四件事：

1. 醒来后读什么——数据源、路径、时间窗口
2. 什么算“有事”——判定标准
3. 结果写到哪——渠道、格式、长度
4. 没事怎么办——no-op 路径

缺任何一条，agent 都会用“看起来合理的默认行为”补上，而默认行为通常是话多、发散、假装有产出。

## 做法

我们现在所有 cron instruction 都按这个骨架写，以每日资讯汇总为例：

```
任务：汇总 <指定来源>，发送到 <指定会话>
时间窗：仅统计过去 24 小时（时区 Asia/Shanghai）
判定：只报告满足 <明确条件> 的条目，宁缺毋滥
输出：3-5 行 bullet，每行包含 <字段>；超过 5 条只留优先级最高的
空结果：输出"今日无更新"一行，不补充任何内容
限制：最多读 N 个来源，不追踪外链第二跳
异常：某来源不可达时用一行注明并继续，不重试
```

几个关键动作：

- **一次一个职责。** 别写“顺便也看看 XX”，scope 膨胀是任务越跑越慢的第一原因。
- **时间窗口写死。** “最近”是模糊词，换成“过去 24 小时”“自上次运行以来修改过的文件”。
- **no-op 必须显式。** 不写这条，agent 为了“有产出”会硬凑内容，这是最贵的坑。
- **状态外置。** cron 大概率是冷启动，别指望它记得昨天的对话；让 instruction 去读状态文件，而不是依赖会话记忆。

## 踩坑点

- **聊天语气残留：** “帮我”“麻烦”“看看有什么有意思的”——“有意思”无法判定，输出每天都会漂。
- **频率错配：** 每 5 分钟跑一次、且指令里没有任何判断逻辑的任务，应该写成脚本挂系统 cron；agent 只用在需要语言推理的环节。
- **输出无去处：** agent 写了文件但没人看。要么明确发送渠道，要么约定“无异常则静默”。
- **没有边界：** “深入调查一下”会让任务跑飞，必须给步骤数和来源数上限。

## 可复用建议

- **一句话测试当准入门槛：** 说不清成功标准（一句以内）的任务，还不适合进 cron。
- **instruction 当代码迭代：** 先手动触发一次看输出，再收紧条件；效果漂移时 diff instruction，而不是凭感觉重写。
- **搬运与判断分离：** 数据搬运交给脚本，判断交给 agent，instruction 里只留判断逻辑和交付约定。

## 总结

写 cron instruction 的心智模型：你在给一个每次醒来都失忆、不能提问、报告只被扫一眼的实习生下书面指令。约束越具体，输出越稳；契约写得越像聊天，跑得越像抽卡。
