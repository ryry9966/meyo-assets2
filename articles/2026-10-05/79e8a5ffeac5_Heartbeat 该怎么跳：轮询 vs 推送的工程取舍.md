## 背景

OpenClaw 的 agent 有一个容易被忽视的默认行为：heartbeat。agent 按固定间隔被唤醒一次，读取工作区里的 `HEARTBEAT.md`，判断当前有没有值得做的事——没有就保持静默，有就主动干活。

很多新用户的第一反应是：这不就是轮询吗？为什么不用 webhook 推送，事件来了再触发？这个问题值得认真拆一下，因为两者没有绝对优劣，只有场景匹配。

## 问题在哪

**轮询的三个本质问题：**

- 延迟上限等于间隔。间隔 30 分钟，最坏情况事件要等 30 分钟才被发现。
- 每次唤醒都是一次真实的模型调用，哪怕无事发生也在烧 token。
- 唤醒内容会进入会话上下文，频繁心跳会稀释主对话的记忆质量。

**推送的三个本质问题：**

- 可达性。webhook 依赖网络、网关和鉴权，任何一环断了事件就静默丢失，而且你不知道丢了。
- 并发与顺序。事件密集时可能同时触发多轮 agent 运行，产生竞争。
- 每类事件都要单独接线，维护成本随事件源数量线性增长。

## 我现在的做法

分层，不二选一：

1. **低频巡检走 heartbeat。** 把「每天早上看一眼日历」「检查某目录有没有新文件」这类容忍分钟级延迟的任务写进 `HEARTBEAT.md`，间隔 30 分钟，配 activeHours 避免半夜空转，约定静默输出，无事不说话。
2. **时效敏感走推送。** CI 失败、监控告警这类事件，经 webhook 网关收敛后投递到 agent 的消息通道，秒级触达，每个事件带幂等 ID。
3. **精确定时走 cron。** 「9 点整发日报」这种需求不要靠 heartbeat 撞时间点，直接 cron 触发。
4. **推送失败落队列，heartbeat 巡检时补扫。** 让轮询给推送兜底补漏，而不是互相替代。

## 踩过的坑

- 把心跳间隔调到 2 分钟试过一天，token 账单直接翻倍，收益几乎为零。间隔低于 10 分钟，基本是在用钱换焦虑。
- heartbeat 默认跑在主 session，巡检产生的中间输出会污染主对话上下文。后来把巡检任务迁到独立 session 才干净。
- webhook 直连 agent 那段时间，一次告警风暴触发了几十次并发运行，互相抢工具锁。加了网关做合并去重才解决。
- 推送通道的凭证过期过一次，静默丢了三天通知。从那以后 heartbeat 里固定加一条任务：检查最近一次成功推送的时间戳。

## 可复用的建议

- 选型只看一个指标：**能接受的最大延迟**。小时级 → heartbeat；分钟级 → cron；秒级 → 推送。
- 推送必须有幂等 ID 和落地队列，别指望任何通道 100% 可达。
- heartbeat 必须有静默约定和 activeHours，否则它会变成一个喋喋不休的成员。
- 监控心跳本身：记录最近一次心跳时间，超时报警。不然你分不清 agent 是没事做，还是已经死了。

## 总结

heartbeat 不是落后设计，推送也不是银弹。轮询用可预测的成本换兜底能力，推送用接线成本换实时性。OpenClaw 实践里最稳的形态是：**推送管时效，heartbeat 管兜底，cron 管准时**——三者各司其职，比争论「哪个更好」有用得多。
