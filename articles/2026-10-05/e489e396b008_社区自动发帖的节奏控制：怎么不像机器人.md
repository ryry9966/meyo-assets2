## 背景

在 OpenClaw 生态里做自动化的人，迟早会走到"让 Agent 替我维护社区内容"这一步：定时摘要、RSS 二次分发、周报整理、MCP 工具触发的公告发布。技术上都不难，难点不在能不能发，而在发出去之后账号还能不能长期活着。

我们复盘过不少跑自动化发布的账号，被封、限流、进垃圾过滤的，很少是因为内容违规，绝大多数是**行为特征太像机器**。

## 问题

人类作者的发布行为有几个天然特征：时间有抖动、有活跃时段、间隔呈长尾分布、发完会回来看评论。而最容易写出来的自动化恰好全反着来：

- cron 定在整点，每天 09:00:00，秒级精确；
- 间隔恒定，两次发布误差不超过几秒；
- 24 小时匀速，凌晨三点照发；
- 发布即退出，从不互动；
- 内容攒够一批，一次全推出去。

这些都是低成本的机器人特征，风控不需要读内容就能识别。

## 做法

我们的方案是把节奏控制抽成一个**独立组件**，所有发布动作必须过它，而不是各写各的定时器。

1. **间隔抖动**。基础间隔之外叠加随机偏移，且不要用均匀随机——真实间隔更接近对数正态。简单近似：`interval = base * exp(normal(0, 0.4))`，偶尔出现长停顿是正常的，人就是这么发帖的。
2. **活跃时间窗**。统计目标社区的回帖高峰时段，把发布限制在窗口内。窗口之外不要降频，是**零发布**。另外务必检查时区，cron 默认 UTC 是最常见的低级错误。
3. **令牌桶 + 日配额**。允许短时突发，但日配额硬顶。发帖、点赞、评论走同一个节奏器但配额分开——互动比发帖更容易暴露，连点十个赞比连发十帖还像机器人。
4. **发布后驻留**。发完不立刻退出，驻留 10–30 分钟处理回复。哪怕只是自动补一句"收到，稍后细看"，也比发了就跑强。
5. **状态持久化**。桶状态和上次发布时间要落盘。否则每次重启都会把积压任务扎堆发出去——这是实际事故里最常见的突发来源。

## 踩坑点

- 抖动写成了 `random(0, 60)` 秒叠在整点上，分布一眼假，等于把特征从"分钟级规律"降到了"秒级规律"。
- 多个 worker / 多个 Agent 实例共用同一套参数，行为完全同步。每个实例要有独立的 jitter 种子，或者干脆错开时段。
- 失败重试没有退避。收到 429 后立刻重试三次，风控比你自己先知道你被限流了。用指数退避加抖动。
- 内容全走同一模板。节奏做得再像人，标题结构一模一样也没用，长度、附图、段落组织都要留出变化空间。

## 可复用建议

- 把节奏器做成 MCP 工具或插件层的公共依赖，配置里放 `min_interval / max_interval / active_hours / daily_quota`，别散落在各处硬编码。
- 留一个 dry-run 模式：把所有"计划发布时间"只打日志不真发，跑一周画出间隔直方图，肉眼扫一眼比任何指标都直观。
- 灰度上线：初期配额压到目标值的三分之一，观察一两周再逐步放开。
- 给节奏器加自检：如果间隔分布的方差低于阈值，说明抖动参数失效了，主动告警。

## 总结

节奏控制的本质，是给一个确定性系统加上克制的非确定性，让它的行为落在人类分布里。但要想清楚目的：不是骗过风控，而是不打扰社区。如果自动化内容本身没有价值，节奏做得再像人也只是延迟被忽略的时间。先保证内容值得被读，节奏控制才有意义。
