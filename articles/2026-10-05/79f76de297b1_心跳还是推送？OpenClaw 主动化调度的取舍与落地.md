## 背景

OpenClaw 的 agent 不是常驻进程，而是"被唤醒才干活"的模型。想让助手主动做事，本质上只有两条路：一是**心跳轮询**——gateway 按固定间隔唤醒 agent，读一份 `HEARTBEAT.md`，无事则回一个短标记（如 `HEARTBEAT_OK`）结束本轮；二是**事件推送**——外部系统在事情发生时通过消息接口直接触发 agent。第一次配主动化时，大多数人都会在两者之间摇摆。

## 问题

取舍的核心是三个变量：

1. **时延**：轮询的感知延迟下限就是间隔，30 分钟的心跳意味着最长 30 分钟才发现问题；推送可以做到秒级。
2. **成本**：每次心跳都是一次完整的 agent 调用，token 和上下文都在花钱；推送只在有事时发生。
3. **接入面**：轮询对事件源零要求，agent 自己去查即可；推送要求每个源都改造成能调你的接口，集成成本随源数量线性增长。

## 做法：分层混用

1. **先给需求分类**。能容忍 10~30 分钟延迟的（日报、构建结果巡检、文件整理）全走心跳；必须秒级感知的（告警、别人的直接消息）走推送。
2. **心跳侧**：`HEARTBEAT.md` 只放检查清单，控制在 5 行以内，每行一个可独立判定的动作；细节放到其他文件，命中了再去读。无事就回固定短标记，且心跳跑在独立 session，不落主对话。
3. **推送侧**：每个事件源配一个小脚本，事件发生时通过 gateway 消息接口给 agent 发一条结构化消息。cron 只负责定时类任务，事件类不进 cron。
4. **兜底设计**：推送落地先写本地 journal 文件（一行一事件，带唯一 id），agent 处理完打标；心跳顺带扫一遍 journal。推送丢了，下一轮心跳能捡回来。

## 踩坑点

- **间隔太短**：曾设 5 分钟一跳，一天几百次调用，token 成本翻倍，收益几乎为零。改成无事时 30 分钟一跳，发现待办再加速。
- **心跳污染对话**：早期心跳结论直接进主会话，主线程被噪音淹没。必须独立 session + 静默回复，有结论才说话。
- **推送重试导致重复动作**：webhook 端到端重试，同一条告警发了三遍。靠 journal 的 id 去重解决。
- **笔记本合盖心跳直接停**：gateway 跑在本机要意识到这点，依赖心跳的任务别放会休眠的机器上。
- **`HEARTBEAT.md` 变垃圾场**：清单一长，每次心跳都在为读它付费，成本随行数固定增长。

## 可复用建议

- 判断式：**时延要求大于轮询间隔 → 推送；否则轮询**。拿不准就先轮询起步，等事件源稳定、且确实嫌延迟大，再针对那一个源换推送。
- 推送 + 心跳兜底 + id 去重，是个人级系统里最省心的"至少一次"投递组合，不需要引入消息队列。
- 给心跳记日志：每次唤醒的时间、耗时、token 消耗，每周看一眼。成本失控会有明显信号，比用户先发现要好。

## 总结

心跳不是偷懒的实现，它是零接入成本的调度器；推送也不是更高级，它是和每个事件源签订的契约。我的心智模型：**心跳是骨架，覆盖默认情况；推送只给那一两个真正需要实时性的源**。先跑便宜的那条路，拿到证据再升级，比一开始就搭全套事件系统划算得多。
