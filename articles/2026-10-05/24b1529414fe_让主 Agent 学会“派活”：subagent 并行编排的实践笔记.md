## 背景

单个 Agent 干久了，两类瓶颈很明显：一是上下文越滚越长，主线程塞满中间产物后推理质量肉眼可见地下滑；二是任务天然可拆分（比如“同时审三个模块”），串行跑就是纯浪费等待时间。OpenClaw 的 subagent 机制，加上 MCP 侧的工具编排能力，给了一个朴素的解法：主 Agent 只做拆解、调度、汇总，执行下沉给子 Agent。

## 问题

第一次跑并行编排时踩了不少坑：

- 把主 Agent 的完整上下文原样传给子 Agent，token 直接翻倍，成本和延迟都难看；
- 多个子 Agent 同时写同一个文件、同一个分支，互相覆盖；
- 子 Agent 返回一大段自由文本，主 Agent 汇总前还得“消化”一遍，噪音很大；
- 没设并发上限，一口气起 8 个子 Agent，直接撞 API 限流；
- 子 Agent 半路挂掉没有超时兜底，整条流程卡死。

## 做法

1. **先拆任务，再谈并行**。只有边界清晰、无共享写状态的任务才值得并行。我们的经验是按“目录 / 模块 / 数据分片”来切，宁可切粗一点。
2. **给每个子 Agent 三样东西**：一段自包含的任务描述（不依赖父上下文）、一个独立 workspace（文件隔离）、一份收窄后的工具清单（最小权限）。
3. **约定结构化返回**。要求子 Agent 只回固定 schema：`status`、改动路径列表、不超过 20 行的 summary。主 Agent 只消费摘要，需要细节时按路径读产物。
4. **控制并发**。用队列/信号量把并行度压在 3~4，超出的排队。这个数字和 API 配额、机器负载相关，先压低，稳了再加。
5. **加超时与重试**。每个子 Agent 设硬超时；失败任务带错误信息重试一次，仍失败就标记为 partial，由主 Agent 决定人工介入还是降级处理。
6. **合并阶段单独跑**。汇总不要和调度混在同一个 prompt 里。等所有子任务落盘后，主 Agent 专门跑一轮“只读汇总”，逐个读取产物生成总报告。

## 踩坑点补充

- 子 Agent 日志必须单独落盘、按任务 ID 索引，否则排查全靠猜；
- 不要让子 Agent 之间直接通信，一旦引入点对点依赖，并行就退化成分布式调试地狱；
- 结构化返回里的路径用相对 workspace 的路径，避免迁移后绝对路径失效。

## 可复用建议

- 写一份“拆解检查清单”：能否并行？有无共享写状态？失败可否降级？返回能否结构化？四问都过了再拆；
- 把“任务描述模板 + 返回 schema”固化成项目配置，主 Agent 每次照着生成子任务，减少随意性；
- 先用小任务验证编排逻辑（比如三个子 Agent 各写一段 README），跑通再上真实负载。

## 总结

subagent 编排的本质不是“更多 AI”，而是更严格的角色分工：主 Agent 管拆解、调度与合并，子 Agent 只做边界清晰的单件事。并行收益的大小，取决于拆任务的纪律性，而不是开了多少并发。建议从 2~3 个并行度、结构化返回、独立 workspace 这三件小事做起，跑顺了再扩。
