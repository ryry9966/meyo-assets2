## 背景

多数 Agent 的默认形态是"应答机"：用户不发消息，它就永远沉默。但真正省时间的场景往往是反过来的——CI 挂了你还没看到，它已经把失败日志和可疑 commit 整理好了；明天的会你有冲突，它已经拟好了改期草稿。这类"主动出击"（proactive）能力，在 OpenClaw 这类可编排的 Agent 框架里不难搭，难的是做得不烦人、不出格。

## 问题：为什么大多数"主动提醒"活不过一周

做过一轮就会发现，失败模式高度一致：

1. 噪音太大，推送十次九次没用，用户直接关掉通知；
2. 上下文不足就行动，把"我猜"当成"我知道"，产出错误结论甚至错误操作；
3. 自触发循环：Agent 自己的写操作又产生新事件，再次唤醒自己；
4. 出了事没法复盘，因为没有任何触发与决策的留痕。

## 做法：一条最小可用的 proactive 流水线

把"主动"拆成五个阶段，每个阶段独立可测：

**1. 触发层**。统一事件入口：cron 定时任务、webhook 接收器、文件 watcher、git hook，全部归一到同一个事件队列。事件只带原始信号，不做判断。

**2. 预过滤层**。用规则和阈值做第一道筛（关键词、状态码、变化幅度），砍掉 80% 以上的噪音。这一层不要上大模型——便宜、快、可解释。

**3. 上下文装配**。通过 MCP 拉取与事件相关的状态：相关仓库的最近 commit、日历、历史处理记录。判断质量的上限由这一步决定。

**4. 决策与分级**。每个事件三选一：只通知（低风险）、生成草稿待确认（中风险）、直接执行（高风险）。直接执行只允许命中预授权的工具白名单，且每次执行前重查权限范围。

**5. 反馈回路**。用户对每条主动消息的忽略/点击/撤销回流成统计指标，用来调阈值和冷却时间。

跑通后整体包成一个 OpenClaw 插件：事件队列和调度器常驻，Agent 本体按需唤醒，成本可控。

## 踩坑点

- **冷却与静默时段是刚需**。同类事件必须有去重和 cooldown，否则一次 CI 抖动能推十五条；静默时段宁可延迟也别推。
- **警惕自触发**。给 Agent 自己产生的写操作打上来源标记，预过滤层直接丢弃这类回声事件。
- **权限后置授予**。不要一上来就给写权限，先跑两周"只报告"模式，误报率降到可接受再逐个放开白名单。
- **每个动作必须可撤销**。主动执行的写操作，撤销成本必须低于用户自己重做的成本，信任丢一次就很难回来。
- **日志要留完整证据链**：event_id、触发原因、装配的上下文摘要、最终动作。复盘全靠它。

## 可复用建议

- 先"报告"后"行动"，把误报率当成第一优化指标；
- 主动消息与用户主动对话走不同通道，避免污染会话历史；
- 给每天的 proactive 运行次数设预算上限，防止事件风暴烧 token；
- 通知/草稿/执行的分级做成配置而非硬编码，不同场景挂不同档位。

## 总结

Proactive 不是让模型更聪明，而是把触发、过滤、上下文、分级、反馈这五件事工程化地接起来。真正的门槛在于克制：推得少、推得准、每个动作有据可查、可撤销。先把"只报告"模式跑稳，再谈替用户办事。
