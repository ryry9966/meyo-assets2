## 背景

大多数助手交互是拉式的：你问，它答。真正省时间的往往是推式场景——磁盘快满、日程冲突、监控日志连续报错，这类事不需要你盯着，但需要有人盯着。OpenClaw 里其实已经有做 proactive 的原材料：heartbeat（周期自唤醒）、cron（定时任务）、hooks（事件触发）和 MCP 工具。问题在于，多数人要么没用起来，要么用成了“每五分钟骚扰我一次”的噪音机器。

## 问题

Proactive 难的不是“让模型主动说话”，而是三件事：**何时开口**（条件要可判定，不能每轮让 LLM 猜）、**不重复打扰**（指标抖动会让同一条告警每轮都发）、**行动边界**（只读可直接办，写操作必须有确认）。

我最初的版本就是在 heartbeat prompt 里写“检查一下服务器，有问题告诉我”，结果 token 烧得飞快，同一条磁盘告警还连发了三遍。

## 做法

后来重构成四层结构，跑了几周比较稳：

1. **把检查做成便宜的 MCP 工具。** 别让 LLM 每轮读原始日志。写个小 MCP server，暴露 `check_disk`、`list_errors_since` 这类返回结构化结论的工具，heartbeat 只拿结论不拿原料。
2. **heartbeat prompt 只做判断。** 每轮指令压缩到几行：调哪些检查、什么阈值算“值得说”、说的时候必须带证据（如“磁盘 91%，三小时前 85%”）。prompt 越短，单轮成本越低。
3. **状态去重放工作区文件。** 用一个 `proactive-state.json` 记录上次告警时间与数值，条件连续 N 轮成立才触发，触发后进入冷却期。CPU、延迟这类抖动指标，这一步是刚需。
4. **动作分级，各归各的机制。** 只读结论直接推送；写操作一律走草案确认——助手把要做的事写成一句话，等你回复再执行。时间明确的交给 cron，有事件源的交给 hooks，heartbeat 只留给需要“判断”的场景。

## 踩坑点

- **心跳太频**：5 分钟一轮看似无害，一天就是几百次 token 消耗，低频场景 30–60 分钟足够。
- **让 LLM 看原始数据**：一次 heartbeat 读完整日志，成本是调一次结构化工具的几十倍。
- **没有静默时段**：凌晨三点被叫醒一次，你就会想把它关了。加 quiet hours，非紧急消息攒到早上。
- **告警没证据**：只说“磁盘有问题”和说“91%，是昨天三倍”，用户信任度完全不同。
- **写操作不设闸**：有一次它“贴心地”直接回了一封邮件，之后所有写路径我都加了确认。

## 可复用建议

给每个 proactive 场景过一遍“三问”：**值得打扰吗**（频率与重要性）、**条件可判定吗**（能否写成阈值或明确规则）、**该告知还是该行动**（只读 vs 写）。三问过不了的就别上。另外，上线后把每次主动触发的决策记进一个日志文件，跑一周回头审计误报率再调阈值——这套机制本质是调参，不是一次性开发。

## 总结

Proactive 的价值不在于助手做更多事，而在于用更少的打扰传递更高的信号。便宜的工具采集、短 prompt 判断、状态去重、静默时段、写操作确认，这五件事做完，“不等你开口就把事情办了”才从演示效果变成能长期开着的日常能力。
