## 背景

Agent 跑久了，`memory_recall` 是决定"这助手到底记不记得你"的关键。我的场景：一个跑了大半年的个人助理 agent，记忆库 3000+ 条（对话摘要、决策记录、配置笔记）。早期用纯全文检索，最近改造成混合方案，两种搜索的坑都踩了一遍，记录如下。

## 问题：两者各有一类致命盲区

**全文搜索（SQLite FTS5 / BM25）**：

- 同义改写命中不了。"上次那个部署脚本报错"搜不到标题写着"CI 流水线失败排查"的记忆。
- 中文分词是重灾区，FTS5 默认的 unicode61 分词器基本不可用。
- 但对精确 token 极强：错误码、路径、版本号、项目代号，一搜一个准。

**语义搜索（embedding 向量检索）**：

- 改写、口语化甚至跨语言 query 都能召回，这点确实好。
- 但对精确标识符很拉胯：`ECONNREFUSED`、`v0.3.2`、`/etc/openclaw/config.yaml` 这类 token 在向量空间里区分度很低。
- 相似度阈值难调；换 embedding 模型等于全库重嵌。

单用任何一个，recall 都有明显漏洞。

## 做法：混合检索 + RRF 融合

现在的管线，改动量不大，一天能落地：

1. **写路径**：每条记忆入库时同时写 FTS5 表（jieba 预分词），并调用 embedding 存向量（本地 bge-small-zh-v1.5，768 维，CPU 能跑）。
2. **读路径**：`memory_recall` 收到 query 后并行跑两路——FTS5 `MATCH` 按 BM25 取 top 20；向量余弦相似度取 top 20。
3. **融合**：用 Reciprocal Rank Fusion 合并，`score = Σ 1/(60 + rank)`，不依赖两路分数可比，取 top 8 给 LLM。
4. **过滤**：融合前按 metadata 过滤（项目 tag、时间窗口），避免陈年记忆刷屏。

核心逻辑就是两路查询加一次排名融合，伪代码十行以内。

## 踩坑点

- **FTS5 中文分词**：默认分词器会把整句中文当一个 token；trigram 分词器能用但索引膨胀明显。最后用 jieba 预分词后以空格写入，最省事。
- **模型一致性**：索引和查询必须用同一个 embedding 模型。我中途换过一次模型忘了重建索引，召回质量悄悄劣化一周才发现。现在把模型名写进索引 metadata，启动时校验。
- **query 改写**：直接拿用户原话当 query 效果一般。加一步让 LLM 生成 2-3 个检索 query（一个关键词版、一个语义版），两路各喂对应的版本，命中率明显提升。
- **别硬调阈值**：两路分数分布完全不同，与其调阈值，不如信任 RRF 的排名融合，用"取几条"控制噪声。
- **chunk 别太碎**：按对话轮切分会丢上下文，改成以"一个决策/一个事件"为最小单元存，效果最稳。

## 可复用建议

- **第一天就用混合检索**。纯向量方案后补全文索引，迁移成本比想象大。
- **建一个 30-50 条的真实 query 评测集**：从实际日志里挑 recall miss 的 case，每次改参数跑一遍，比肉眼感觉靠谱。
- **精确标识符走结构化**：错误码、路径这类信息的最好归宿是 metadata 字段 + 过滤，而不是指望任何一种搜索。
- 每次调参前先跑评测集，召回率是可以量化的，不玄学。

## 总结

语义搜索解决"说法不一样"，全文搜索解决"词就是那个词"，`memory_recall` 的高质量召回基本注定是混合方案。我的结论：FTS5 + 向量 + RRF 是当前性价比最高的组合，一天工作量，把召回 miss 率从大约三成压到一成以内。别纠结"哪个更好"，真正的问题是让它们各干各的活。
