## 背景

RSS 至今仍是最可控的信息入口：没有算法插手，源完全自选。但订阅多了，老问题就回来了——我手上有 40 多个源，每天更新上百条，真正值得读的不到十篇。让 agent 每天早上把过去 24 小时的更新压缩成一份摘要、推到聊天窗口，是目前性价比最高的解法。

## 问题拆解

一条能长期运行的信息流管线，核心不是"调一次摘要 API"，而是四个环节：

1. **抓取**：拿到新条目，且不折腾对方服务器
2. **过滤与去重**：只处理没看过的、大概率值得看的
3. **摘要**：结构化、可聚合、不编造
4. **分发**：固定节奏推送，失败可恢复

## 做法

整体跑在 OpenClaw 里：定时任务每天 8 点触发一次 agent run，流程定义在一个 skill 中；工具侧通过 MCP 挂一个 RSS 解析器；推送直接复用已接入的消息渠道。

**Step 1 源管理**：用一份 JSON 维护订阅列表放在 workspace 里，agent 可读写。想加源，对 agent 说一句话即可。

**Step 2 抓取与增量**：逐源抓最新条目，用链接规范化后的 hash 做 seen-store（SQLite 足够），只留新条目。请求带 ETag，返回 304 就跳过。

**Step 3 粗筛**：关键词黑白名单打分，砍掉公告、招聘、营销类条目。纯规则、零 token，通常能减掉一半。

**Step 4 分层摘要**：先做条目级摘要（结构化输出：一句话要点、分类、推荐理由、分数），再对全量结果做一次日报级聚合——按主题归组、排序、生成导读。典型的 map-reduce，条目多时不会撑爆上下文。

**Step 5 推送与落库**：生成 Markdown 日报推到私聊，"已推送"状态写回 seen-store，重跑不重复。

摘要 prompt 的关键约束就一句：只基于条目原文输出 JSON，信息不足时如实标注，禁止补充外部知识。

## 踩坑点

1. **guid 不可靠**。部分源的 guid 会变、同文重复出现。统一用链接 hash 做主键，重复推送会直接毁掉信任感。
2. **全文抓取是深坑**。多数 feed 只有摘要，要全文就得抓原文页加正文提取，遇反爬更麻烦。我最后接受"feed 给什么摘什么"，覆盖九成场景。
3. **摘要幻觉**。模型会给空条目"脑补"。强制 schema + 原文约束 + 每天抽查，才压下来。
4. **时间窗口**。按"过去 24 小时"取数，会碰到缺时间戳的 feed。兜底：无时间的条目按"上次运行之后抓到的"算。
5. **token 成本**。条目级摘要是 O(n) 的，粗筛必须放在摘要前面，并给每个源设单次上限（如 10 条），超出只记标题。
6. **失败恢复**。中途挂掉后，要么丢数据要么重推。把"抓取成功"和"推送成功"拆成两个状态落库，各自幂等。

## 可复用建议

- **seen-store 是地基**，先做它再做摘要。
- **结构化输出 + 严格 schema**，比自由文本稳定得多，也是后续过滤排序的前提。
- **分层摘要**是通用模式，换成播客、邮件、GitHub Release 都适用。
- **留反馈通道**：觉得某条不该出现，直接回复 agent，规则写回粗筛配置——管线要能被自己训练。

## 总结

这条管线约两百行代码加一个 skill 定义，跑了两周，日均推送 8–15 条，误报在可接受范围。它没有让信息变多，而是把"我该看什么"变成每天自动完成的筛选问题。对 OpenClaw 用户来说，难点从来不在接模型，而在去重、幂等、成本这些工程细节——做扎实了，换任何模型都只是换引擎。
