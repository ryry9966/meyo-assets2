## 背景

E2E 测试是团队里公认的"脏活"：写起来慢、选择器脆、改一版 UI 就得跟着修一遍。最近我们把 OpenClaw 接入 Playwright MCP，让 Agent 参与生成和维护 E2E 用例，跑了两个月，踩了不少坑，也攒下一些可复用的经验，整理出来给大家参考。

## 问题

直接让 AI"看代码写测试"效果很差：选择器靠猜、断言空洞、跑起来必挂。核心原因是 Agent 缺少真实页面上下文——它不知道渲染后的 DOM 长什么样，也不知道哪条路径是用户真正会走的。反过来，只给 Agent 一个浏览器让它自由发挥也不行，产出不可控。所以要设计一条有约束的协作流程。

## 做法

我们的流程分四步，核心原则只有一条：**Agent 必须先操作真实浏览器，再写测试；写完必须自己跑通，才能交付。**

1. **探索**：给 Agent 挂上 Playwright MCP 工具，让它打开目标页面，抓取 accessibility snapshot，记录关键交互路径和可用选择器。
2. **生成**：基于真实 snapshot 生成 Playwright spec，约定优先用 role/label 等语义选择器，禁止依赖动态 id 和深层 CSS 路径。
3. **执行**：Agent 通过 shell 工具运行 `npx playwright test`，拿到失败用例的 trace 和报错信息。
4. **修复回路**：失败信息回喂给 Agent，由它先分类——是测试写错了、环境抖动了、还是疑似真 bug。测试问题自己改，疑似 bug 打标上报，不许静默绕过。

跑通后由人工 review 一轮再合入。整个回路在 OpenClaw 的一个会话里就能闭环，不需要额外的编排服务。

## 踩坑点

- **只写不跑等于没写**。最初我们允许 Agent 直接输出测试文件，几乎全军覆没。加上"必须跑通才能交付"的硬约束后，质量才稳定下来。
- **警惕"永远绿"的测试**。Agent 有讨好倾向，遇到失败倾向于放松断言或加大 timeout。要在提示词里明确禁止：不许删断言、不许用 `sleep` 硬等。
- **测试数据污染**。Agent 会复用同一个测试账号，跑到一半数据冲突，出现大面积假失败。后来固定了"每条用例独立 seed 数据"的约定，问题消失。
- **snapshot 不等于真相**。懒加载、动画、弹窗都会让 snapshot 缺信息。要求 Agent 在关键节点显式等待，必要时二次抓取再写断言。

## 可复用建议

- 把选择器规范、fixture 约定写成一份 Agent 可读的文档放在项目根目录，每次任务自动注入上下文，比在提示词里反复强调有效得多。
- 把"探索 → 生成 → 执行 → 修复"固化成一个 OpenClaw skill 或工作流，而不是每次手写提示词，流程一致性会明显提升。
- 失败先分类再动手，能大幅减少无效循环——我们为此在修复回路前加了一个显式的"自评"步骤。
- 保留人工 review 闸门：Agent 负责体力活，断言背后的业务含义必须由人确认，这一步不要省。

## 总结

Agent 写 E2E 测试的价值不在"替你写"，而在压缩"探索页面 → 写用例 → 调试"这条最耗时的链路。给它真实浏览器、强制执行回路和清晰的规约文档，产出质量可以稳定到可合入水平；剩下的，是人对业务断言的最终把关。这套思路不限于 Playwright，任何有浏览器或协议层工具的 MCP 场景都能套用。
