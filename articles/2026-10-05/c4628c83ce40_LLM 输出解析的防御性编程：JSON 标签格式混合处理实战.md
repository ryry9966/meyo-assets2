做 Agent 插件和 MCP 工具链的同学对这类场景不陌生：你让模型「只输出 JSON」，然后拿 `json.loads` 解析，喂给下游工具。本地测试一次通过，上线后隔三差五报 `JSONDecodeError`。把 raw 日志拉出来一看——模型包了一层 ```json 围栏，或者在前面加了一句「好的，以下是解析结果：」。

同一个提示词，不同模型、不同版本、甚至不同温度下，输出格式就是不一样。这就是所谓「混合格式」：裸 JSON、markdown 围栏、围栏外加说明文字、甚至两个代码块并存。解析层是自动化流水线里失败率最高的一环，值得做防御性设计。

## 常见失败形态

- 输出被 ```json ... ``` 围栏包裹（最常见）
- JSON 前后有寒暄、解释、结尾总结
- 输出了两个代码块，第一个是示例、第二个才是结果
- 被 max_tokens 截断，括号不闭合
- 语法噪音：尾逗号、智能引号、注释

## 做法：分层解析流水线

**第 1 层，剥围栏。** 用非贪婪正则匹配围栏内容，命中就取围栏内的部分：

```python
FENCE_RE = re.compile(r"```(?:json)?\s*\n?(.*?)```", re.S)
m = FENCE_RE.search(raw)
text = m.group(1) if m else raw
```

注意用 `search` 而不是 `match`，且要处理多代码块的情况——逐块尝试，取第一个能通过括号配平校验的。

**第 2 层，定位边界。** 找到第一个 `{` 或 `[`，然后做括号配平扫描：维护计数器，遇到字符串进入「跳过模式」（正确处理转义符），直到配平为止。兜底策略是取「第一个左括号到最后一个右括号」。

**第 3 层，解析与修复。** 先直接 `json.loads`；失败后按固定顺序尝试修复：删尾逗号 → 替换智能引号 → （谨慎）单引号转双引号。每做一次修复就重试解析，命中即停。

**第 4 层，schema 校验与反馈重试。** 用 pydantic 或 jsonschema 校验字段结构；校验失败时，把具体错误信息拼回提示词让模型重试，最多 1–2 次，不要无限重试。

提示词侧也要同步加固：明确写「不要使用 markdown 代码块包裹」。如果模型或网关支持原生结构化输出 / function calling，优先用，这套解析器是兜底而非主力。

## 踩坑点

- 正则贪婪匹配会把两个代码块之间的内容也吞进来，一定用非贪婪 + `re.S`
- 括号扫描不跳过字符串内容的话，`{"a": "}"}` 这种输入会被提前截断
- 单引号修复最容易误伤英文撇号（don't、O'Brien），把它排在修复链最后
- 截断不是格式问题，修复救不回来；应检测 finish_reason 为 length 或括号长期不闭合，直接重新生成
- 别迷信 temperature=0，换个模型版本格式照样漂移
- 原始输出一定要落日志，排查时 raw 比 parsed 有用得多

## 可复用建议

1. 封装成统一的 `parse_llm_json(raw)` 工具函数，全项目唯一入口，禁止散落各处的裸 `json.loads`
2. 把解析失败率做成指标上报，它是流水线健康度的领先信号
3. schema 校验放在工具调用之前，坏数据宁可拒绝重试，不要将错就错传下去
4. 修复逻辑按「低风险到高风险」排序，每次修复后立即验证

## 总结

对待 LLM 输出的正确姿势，是把它当成一个不可靠的上游服务：剥离、定位、解析、修复、校验、重试，各层职责单一、逐层兜底。提示词加固能降低格式漂移的概率，但消灭不了它；真正让自动化流程半夜不挂的，是解析层那几行看起来不太优雅的防御代码。
