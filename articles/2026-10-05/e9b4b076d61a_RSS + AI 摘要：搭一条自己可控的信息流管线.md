## 背景

信息源越加越多，真正读进去的越来越少。RSS 依然是最可控的订阅协议：结构化、无算法、可自托管。缺的从来不是源，而是把几百条 entry 压缩成"值得我花十分钟"的那一层。LLM 恰好补上了这一环。这篇记录我用 OpenClaw 定时任务 + MCP 工具搭的管线，跑了两个月，日均处理 300+ 条目。

## 问题

直接把 RSS 喂给模型，有三个不成立：

1. **成本不成立**——大部分条目不值得花钱摘要，先过模型再筛是反向操作；
2. **时效不成立**——逐条实时调用又贵又慢，没有批量意义；
3. **可信不成立**——摘要一旦混入模型发挥，你就分不清哪些是源里说的、哪些是它编的。

所以管线的核心设计原则是：**便宜的判断在前，贵的生成在后，原始数据永远留底**。

## 做法

整条管线五步，每步独立可测：

**1. 抓取。** 有 RSS 的直接拉；没有的用 RSSHub 自托管实例生成源。落地成 SQLite 表：guid、链接、标题、正文、发布时间、内容 hash。hash 用来去重，防止源站改标题导致重复推送。

**2. 预过滤。** 关键词规则 + 来源权重，打一个 0–3 的粗分，0 分直接归档不进模型。这一步纯本地、零成本，实测砍掉 60–70% 的量。

**3. 摘要。** 剩余条目按源分组批量送模型，用 OpenClaw agent 跑，输出强制 JSON：`{要点: [], 是否值得深读: bool, 分类: string}`。prompt 里明确三条：只用原文信息、原文不足就写"信息不足"、不输出观点。

**4. 合并去重。** 同一事件被多源报道时合并，保留最早出处。放在摘要层做，比逐条处理省很多 token。

**5. 投递。** 定时跑一次，产出 Markdown 日报，webhook 推到自己的 IM。重试逻辑放这层，摘要层某组失败就跳过、下轮再补。

## 踩坑点

- **改稿重复推送。** 源站常改标题再发布，guid 不变但内容变了。解法：guid + 内容 hash 联合判重，hash 变了标记为"更新"而非新条目。
- **摘要幻觉。** 部分源只有标题没有正文（付费墙/反爬），模型会硬编。JSON 里加 `confidence` 字段，低于阈值只给标题不生成摘要。
- **日期解析。** 相当多 feed 的 pubDate 格式是错的，直接 parse 会抛异常。兜底：解析失败就用抓取时间，宁可排序略偏也不丢条目。
- **成本失控。** 第一版没做预过滤，一天 token 费用是预期的 5 倍。加回预过滤后恢复正常。建议按源记录消耗，每周看一次，只产噪音的源直接砍。
- **正文获取。** 只有 summary 的源需要抓原文，记得带常规 UA 和超时，别用默认爬虫头——不少站会直接 403。

## 可复用建议

- **先落库再处理。** 原始 entry 永远保留，摘要可随时换 prompt 重跑，源挂了也有备份。
- **过滤规则外置。** 每个源单独配置关键词、权重、摘要风格，别写死在代码里。
- **分层埋点。** 每层记录进出条数，一眼看出是抓取挂了还是模型挂了。
- **先小后大。** 拿 3–5 个核心源跑两周，确认推送节奏和摘要质量再扩量，否则只是生产第二座信息垃圾山。

## 总结

这套东西没有一步是新技术，价值全在组合与约束上：便宜的过滤挡在贵的前面，原始数据留底兜住幻觉，每层独立可观测。跑两个月下来，日均 300+ 条目压缩成 20 条左右的日报，漏报可接受，成本稳定。如果你已经在用 OpenClaw 跑定时任务，加一个 RSS 抓取的 MCP tool 和一个摘要 prompt，半天就能跑通第一版。
