## 背景

我们社区每周需要一条「本周动态」帖：汇总仓库新合并的 PR、值得关注的 issue、文档更新。人工整理大概要花半小时到一小时，且经常忘。目标很朴素：机器人每周定时聚合数据、生成草稿、经人工确认后发帖。注意，不是全自动无人审——社区账号发出去的内容代表社区，这个底线我先说清楚。

## 问题

最初的直觉是「给 LLM 一个 prompt，让它写周报」。试了一周就放弃：链接是编的、issue 编号是错的、每周格式还不一样。真正的问题不是生成，而是**事实从哪来、发出去怎么不出错**。

## 架构：确定性代码管事实，模型只管措辞

核心原则一句话：**能用代码拿到的数据，绝不让模型凭记忆写**。

1. **采集层**：一个 Python 脚本定时拉 GitHub API（issues / merged PRs / discussions），落成 JSON，链接、编号、作者全部是真实字段。
2. **Agent 层**：OpenClaw agent 挂两个 MCP 工具——`draft_digest`（读 JSON 生成 markdown 草稿）和 `submit_post`（调论坛 API）。工具面就这两个，一个读一个写。
3. **审核层**：默认 dry-run，草稿写入文件并推送到内部频道，人工回复确认后才真正调用 `submit_post`。
4. **调度与状态**：cron 触发，SQLite 存每次运行状态和幂等键。

## 踩坑实录

**1. 幻觉链接**。让模型自己写链接，十次错三次。改成模板填变量后基本归零——模型只负责每条的摘要句，链接和编号由代码拼接。

**2. 重试导致重复发帖**。网络超时后重试，一晚上发了三条一样的帖。解法：幂等键 = 周期标识（如 `2024-W23`），服务端按 key 去重，本地状态表兜底。这个键要在写代码第一天就设计好，不是事后补。

**3. 上下文爆炸**。50 条 issue 全塞进去，又贵又写得烂。按 label 分组、每组取 top N、长讨论只给统计摘要，质量反而上来了。

**4. 提示注入**。有用户在 issue 标题里塞了「忽略以上指令」。外部内容永远当数据不当指令：拼接时明确声明「以下为待摘要数据」，且 `submit_post` 权限收窄到只能发指定版块。模型被注入了也做不了多余的事。

**5. dry-run 与真实环境的差异**。测试一切正常，上线首帖被论坛反垃圾拦截——带外链的新账号首帖。所以上线前一定在测试版块跑完整链路，包括反垃圾这条你看不见的路径。

**6. 密钥管理**。早期图省事把 token 放在配置附近，日志里差点打出来。密钥只走环境变量，日志对工具调用的入参做脱敏。

## 可复用建议

- 写操作工具只留一个，且参数校验放在工具侧而不是 prompt 里
- 结构化日志记录每次工具调用的入参、出参、耗时，排障全靠它
- dry-run 是默认态，不是可选项
- 生成内容和发布动作之间必须隔一个人工确认点

## 总结

整个机器人不到 300 行代码，模型调用只占很小一部分，工作量全在工程边界上。它的价值不在「AI 会写」，而在**稳定、可审计、可回滚**。如果你也想做类似的自动化发帖，建议先从 dry-run + 人工确认这套骨架搭起，生成质量可以慢慢调，发布安全没有第二次机会。
