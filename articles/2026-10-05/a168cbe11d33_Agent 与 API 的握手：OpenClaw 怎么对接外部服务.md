## 背景

OpenClaw 的价值不在会聊天，而在能动手。Agent 每次帮你"做成一件事"，背后基本都是一次对外部 API 的调用：查工单、发消息、触发 CI、读写数据。怎么把外部服务接进来、接得稳，决定了它是演示玩具还是日常工具。

## 问题

直接把 API 丢给 Agent，通常会撞上三类问题：

1. Agent 不知道何时调用、参数怎么填，全靠猜；
2. 认证信息散落在对话或脚本里，不安全也不好维护；
3. 出错时回一大坨原始 JSON 或堆栈，Agent 读不懂，用户看不明白。

## 做法

以一个典型场景为例：让 OpenClaw 定时查内部工单系统并汇总到群里。

1. **圈定最小接口集**。别把整个服务的 OpenAPI 全量注册，只挑真正需要的 2-3 个端点，比如 `list_issues` 和 `get_issue_detail`。工具越少，选择越准。
2. **写一层薄封装**。不管落地成 skill 脚本还是 MCP server，认证、重试、超时都收在这一层，Agent 只看到干净的输入输出。密钥放环境变量或配置文件，永远不进对话上下文。
3. **认真写工具描述**。这是最容易被敷衍、收益却最大的一步。写清楚：什么场景该用它、参数格式、一个正例一个反例。Agent 选工具基本靠这段话。
4. **收敛返回内容**。API 返回 500 行 JSON？封装层先裁剪，只回传决策所需字段（ID、状态、标题），再附一句"完整数据已落盘 /path/to/file"。
5. **灰度验证**。先在私聊跑 dry-run，让 Agent 打印"我将调用 X，参数是 Y"，确认无误再放行真实调用，逐步开放到群聊和定时任务。

一个描述的参考骨架：

```json
{
  "name": "list_issues",
  "description": "查询工单列表。用于询问待处理工单、本周新增、或需先浏览再深入的场景。不要用于读取单条工单详情。返回前 20 条：id、标题、状态、负责人。",
  "parameters": { "status": "open|closed", "assignee": "可选" }
}
```

## 踩坑点

- **描述含糊导致误调用**：两个工具区分度不够，Agent 频繁选错。在描述里显式写"不要用于……"，比堆正例更有效。
- **非幂等操作被重试打两次**：发消息、建工单这类操作，务必在封装层加幂等键，否则网络超时 + Agent 重试 = 重复执行。
- **慢接口拖死会话**：某 API 平均响应 8 秒，Agent 看着像挂了。设合理超时，超了就返回"任务已提交，稍后可查询结果"，用异步轮询兜底。
- **日志泄密**：调试时把完整请求打进日志，token 跟着泄。日志层做脱敏。
- **错误写给机器看**：别只回 `Error 500`，要回"工单系统暂不可用，建议 10 分钟后重试，或改查缓存"。Agent 才能据此向用户解释，甚至自愈。

## 可复用建议

- 每个外部服务一个独立 skill/工具组，单一职责，坏了单独下线。
- 薄封装永远只做三件事：认证、裁剪、错误翻译。
- 每个工具维护一句"反例"写进 description。
- 上线后保留调用日志（参数、耗时、结果摘要），排障全靠它。

## 总结

对接外部服务的本质，是把"人类工程师调用 API 的经验"翻译成"Agent 能读懂、能安全执行的契约"。OpenClaw 不缺执行能力，缺的是边界清晰、描述准确、返回收敛的工具。把薄封装做扎实，Agent 的每一次握手才既稳、又可审计。
