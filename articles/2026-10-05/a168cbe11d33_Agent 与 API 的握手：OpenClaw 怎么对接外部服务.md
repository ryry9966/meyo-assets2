## 背景

OpenClaw 的定位是个人 Agent 网关：上游接模型，下游接消息渠道，中间靠工具把 Agent 的"意图"落到真实世界。但 Agent 本身并不会发 HTTP 请求——它只负责决定"该调哪个工具、传什么参数"，真正和外部服务握手的那一步，靠的是我们提前装好的工具层。这篇记录我在 OpenClaw 里对接几个内部服务（查询类 REST API 加一个带写操作的工单系统）的过程。

## 问题

对接外部服务，典型矛盾有三个：

1. Agent 只认工具，不认接口文档。直接把四十个端点全暴露给它，调用准确率断崖式下跌。
2. 鉴权与密钥管理：密钥既不能被模型读到，也不能出现在日志和错误回显里。
3. 错误传播：上游超时、限流、报 500，如果不处理，Agent 会拿着错误原文继续自由发挥。

## 做法

OpenClaw 原生支持 MCP，我的首选路径是为每个外部服务写一个薄薄的 MCP server，而不是让 Agent 直接碰 REST。步骤如下：

1. **圈定工具面。** 一个服务通常只暴露三到五个工具。把"查询订单"设计成一个工具，而不是拆成按 ID 查、按手机号查、按时间查三个。
2. **认真写 schema 和 description。** 工具描述是给模型看的 prompt，不是给人看的注释。"查询订单详情，返回状态和金额"远好于一个含糊的 `get_data`。参数尽量用 enum 约束，能不给 free string 就不给。
3. **鉴权放环境变量。** MCP server 启动时从 env 读 token，OpenClaw 侧配置只引用变量名。模型全程只看到工具名和参数，碰不到密钥。
4. **出口收敛。** server 拿到上游响应后裁剪再返回：只留模型需要的字段，错误统一转成一句话加结构化错误码。返回体积从几 MB 压到几百字节，context 和稳定性都受益。
5. **写操作单独隔离。** 创建工单这类非幂等操作单独成一个工具，description 里明确"会产生副作用"，并在 OpenClaw 侧开启确认机制。

## 踩坑点

- **描述含糊导致误调用。** 有个工具叫 `get_data`，Agent 查什么都调它。改成动词明确的 `get_order_status` 后消失。
- **超时没设。** 上游偶尔三十秒不响应，整个 Agent 循环卡死。现在 server 内统一十秒超时，仅对幂等查询做一次重试。
- **限流被放大。** Agent 失败会自动重试，上游已经 429 还重试等于雪上加霜。改为 429 原样透传并附冷却提示。
- **日志泄露。** 第一版把完整请求打进日志，密钥就在 header 里。改为只记方法、路径和状态码。

## 可复用建议

- 工具宁少勿多、宁窄勿宽，一个工具一个意图。
- 所有外部调用必须设超时，必须区分幂等与非幂等，错误必须转译成人话。
- 密钥走 env 或 secret 管理，context、日志、错误三条路径都不落盘。
- MCP server 打版本号。工具 schema 变更时 Agent 行为可能突变，先灰度再全量。

## 总结

对接外部服务的本质，不是"让 Agent 能调 API"，而是"替 Agent 把 API 收拾干净"。OpenClaw 加 MCP 的组合给出了清晰的落点：server 层负责收敛、隔离和防御，Agent 层保持简单的决策逻辑。工具层越干净，Agent 的行为越可预期——这是目前性价比最高的一层防护。欢迎在社区里交换各自的工具封装经验。
