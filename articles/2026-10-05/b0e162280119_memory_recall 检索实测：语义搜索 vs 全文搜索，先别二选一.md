## 背景

OpenClaw 的 `memory_recall` 是 Agent 回忆长期记忆的主入口，它好不好用，基本决定了助手“记没记住事”。底层默认走混合检索：一路向量语义相似度，一路关键词/全文打分，加权合并后返回 top-k。社区里常有人问“能不能只用语义”或“只用全文”，我的实测结论是：两类查询的失败模式完全不同，先别急着砍掉任何一路。

## 问题：各自的失败样本

- **全文检索输掉的案子**：我问“上次部署超时最后怎么定的”，原文记的是“docker timeout 事故复盘：改了健康检查窗口”。字面零重叠，纯关键词召回为空。
- **语义检索输掉的案子**：排障时查 `ERR_CONN_RESET` 或某个日志路径，向量模型把它泛化成“网络错误、日志文件”，最需要的精确串反而被挤到后面。

前者是“人话问答”，后者是“精确标识符”——这就是为什么混合才是合理的默认。

## 做法：用回归集说话

1. **盘点 memory 形态**。我是“一日一档 + MEMORY.md 做索引”，先确认文件数、单文件大小，清掉超大杂烩文件。
2. **建 15~20 条真实查询当回归集**：一半改述型（口语问法、字面不重叠），一半字面型（错误码、路径、命令、专有名词）。
3. **三档跑分**：只关键词、只语义、混合默认权重，各记 top-5 命中情况。半天工作量，结论很直观。
4. **按查询分布调权重**：日常笔记多、问法口语化 → 调高语义权重；运维开发场景错误码满天飞 → 调高关键词权重。字段名和取值范围以你手上版本的 memory 文档为准，思路不变。
5. **中文用户重点看 embedding 模型**：本地默认小模型对中文改述能力一般，中文为主的库建议换多语言模型或远程 embedding——代价是记忆原文会上传出网，隐私自己掂量。

跑分脚本可以直接挂进自动化：升级 OpenClaw 或换模型后定时跑一遍，命中率掉了第一时间知道，不用靠“感觉变笨了”。

## 踩坑点

- **中文别指望纯全文检索**：默认按空格/词元切分，中文整段连成一串，关键词路基本废掉。中文场景下混合里语义那一路权重大概率要给足。
- **改了 memory 文件不重建索引**，recall 一直翻旧账。批量导入或大改之后，主动触发一次重建再测。
- **单个 md 越写越长**，切分粒度变差，召回片段两头不靠。保持一日一档、小节标题写清楚，别堆长文。
- **本地 embedding 首次加载慢、常驻内存不小**，机器配置紧的注意这点，不是 bug。

## 可复用建议

- 记忆的“写法”本身就是检索质量的一半：小节标题用人话写结论，正文保留错误码、路径等精确 token，两路检索同时受益。
- 回归查询集单独存档，它比任何调参直觉都可靠；每次升级或换 provider，把跑分当升级验收的一部分。
- 如果你是通过 MCP 或自定义工具接的 recall，同理：把跑分对准你实际的调用入口测，别测了底层却绕过了自己的封装。

## 总结

语义搜索擅长“换个人问法也能找到”，全文搜索擅长“一个字符都不能错”。混合检索给了你旋钮，别懒得拧——用 20 条真实查询量出自己的使用分布，把权重拧到匹配为止，比争论谁更好有用得多。
