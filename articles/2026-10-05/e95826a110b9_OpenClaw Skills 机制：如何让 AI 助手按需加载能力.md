## 背景

用 Agent 做日常自动化久了，最先撞上的不是能力问题，而是上下文问题。MCP 工具的 schema、系统提示里的各种流程指令，不管当次对话用不用得上，都会常驻 token。指令塞得越多，模型注意力越散，指令之间还容易互相干扰。

OpenClaw 的 Skills 机制就是针对这个问题的：把“能力”拆成独立目录，平时只向模型暴露一行描述，命中需求时才把完整说明加载进上下文。本质上是 prompt 层面的懒加载。

## 它和 MCP 的分工

MCP 提供的是工具：结构化的输入输出，由客户端代为调用。Skill 提供的是“怎么做”的说明书：告诉模型在什么场景下、用哪些已有工具（通常是 bash 加脚本）完成一件事。两者不冲突，我的实践是——确定性强的操作走 MCP，流程性、经验性的知识沉淀成 Skill。

## 做法

1. **建目录**。放在 `~/.openclaw/skills/<name>/` 下（工作区级则放在 workspace 的 skills 目录），核心是一个 `SKILL.md`。
2. **写 frontmatter**。`name` 保持简短；`description` 是关键字段，模型就靠这行决定是否加载。把它写成触发条件，而不是功能简介。
3. **正文只写操作步骤**：前置条件、具体命令、失败时怎么办。能用脚本承载的逻辑就写成脚本放在同目录，正文里只写“运行 xx 脚本，检查退出码”。
4. **验证**。重启会话后问一个相关问题，看它是否主动读取并执行；用 `openclaw skills list` 确认被扫描到。

举个自己的例子：我有一个 `db-snapshot` skill，description 写的是“当用户要求备份数据库或生成快照时使用”。正文只有十几行：调用目录下的 `snapshot.sh`，脚本报错时把日志贴给用户并确认是否重试。平时它不占上下文，触发时约几百 token。

## 踩坑点

- **description 写成功能清单**。“这是一个数据库工具”这类描述几乎不会命中，要写“何时用”。
- **正文里再塞一层间接**。如果正文又让它去读十个文件，懒加载就变成了瀑布加载。尽量一跳之内解决。
- **脚本没加执行权限**。忘了 `chmod +x`，模型会反复尝试替代方案，白白烧 token。
- **frontmatter 格式错误会静默失效**。YAML 缩进错了，skill 直接不被扫描，日志里也不明显，排查时先怀疑格式。
- **数量失控**。超过二三十个后，描述之间的触发边界开始模糊，该触发的没触发、不该触发的乱触发。需要定期清理合并。

## 可复用建议

- description 用固定句式：「当……时使用；产出……；依赖……」，三段说清。
- 一个 skill 只做一类事，宁可拆小。小 skill 的触发更精准，组合也更灵活。
- 脚本要幂等、退出码清晰，把“人怎么排查”翻译成“模型能执行的检查”。
- 常驻指令保持极简，能降级成 skill 的都降级，别把系统提示当垃圾桶。

## 总结

Skills 不是一个炫技特性，而是一种上下文经济学：把“可能有用”的信息从常驻区挪到按需区，换回更干净的注意力。写好一行 description，配一个能跑的脚本，往往比再挂一个大型 MCP server 更划算。建议从清理现有 prompt 开始，把其中流程性的内容逐个抽成 skill，观察实际触发率，再决定去留。
