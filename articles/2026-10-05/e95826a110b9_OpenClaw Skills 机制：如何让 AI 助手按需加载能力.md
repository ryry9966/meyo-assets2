## 背景

做 Agent 项目最直观的矛盾是：能力越多，上下文越贵。早期我们习惯把所有工具说明、操作手册、约定规范一股脑塞进 system prompt，结果一个 agent 挂了十几个能力后，光常驻指令就吃掉几千 token，模型注意力被稀释，反而更容易选错工具。

OpenClaw 的 Skills 机制走的是另一条路：**渐进式披露（progressive disclosure）**。启动时只加载每个技能的元数据（name + description），模型判断当前任务相关时，才去读取正文和附属资源。本质上是用"目录页"换"全书"。

## 问题

把能力全量注入 prompt 有三个实际代价：

- token 成本随技能数量线性增长，多轮对话里反复支付；
- 指令互相混杂，模型在相似工具之间路由抖动；
- 能力更新必须改 prompt、重启发会话，无法独立演进。

## 做法

**1. 定义技能目录结构**

每个技能是一个独立文件夹，核心是 `SKILL.md`：

```yaml
---
name: pdf-report
description: 将 Markdown 转为带样式的 PDF 周报，当用户要求导出报告或周报时使用
---
```

正文写执行步骤、参数约定、边界情况。frontmatter 是常驻部分，正文是按需部分。

**2. description 写"做什么 + 何时用"**

这是整个机制的路由关键。只写功能名（"PDF 处理"）模型无法判断触发时机；要写成动词加场景，让模型在读完元数据那一行就能做路由决策。

**3. 理解三层加载**

- L1：元数据常驻，每个技能控制在一两行内；
- L2：正文在触发时才读取；
- L3：技能目录里的辅助文件、脚本，只在执行阶段被引用。

**4. 逻辑下沉到脚本**

确定性的操作（模板渲染、格式转换、依赖检查）写成技能目录下的脚本，让 agent 调用执行，而不是用自然语言描述流程。prompt 负责"何时做"，脚本负责"怎么做"。

**5. 验证路由**

新开一个会话，问"你现在有哪些能力、分别什么时候用"，观察模型复述的触发条件是否和预期一致。这一步比写技能本身更能暴露问题。

## 踩坑点

- **description 太泛或太窄**。太泛（"处理文件"）永远不触发；太窄（"处理 2024 年 Q3 的周报"）该触发时不触发。建议动词加通用场景。
- **技能职责重叠**。两个技能都能"导出文档"，路由就会不稳定。要么合并，要么在 description 里显式划边界。
- **脚本依赖本地环境**。写死 Python 路径或假设某 CLI 已安装，换台机器就挂。脚本开头自查依赖，并给出降级路径。
- **技能数量失控**。三十个以上之后，元数据本身就成了上下文负担。按项目或按 profile 分组挂载，别把所有技能挂在一个 agent 上。
- **正文无条件加载**。有些实现会把 SKILL.md 全文注入——等于没做分层。确认你的运行时确实只注入 frontmatter。

## 可复用建议

1. 一个技能只对齐"用户的一次请求"，粒度宁小勿大；
2. skills 目录纳入版本控制，description 的改动走 review——它是路由逻辑，改一行可能改变触发行为；
3. 沉淀 5-10 条评测用例（哪些输入该触发、哪些不该），每次改技能后跑一遍回归；
4. 通用技能（文档转换、代码审查）放全局目录，业务技能跟项目走，避免重复维护。

## 总结

Skills 的价值不是"给 AI 更多能力"，而是**控制它何时看见什么**。元数据是路由层，正文是执行层，脚本是确定性层——三层各司其职，token 成本和输出准确性才能同时达标。如果你的 agent 常驻 prompt 已经超过两三千 token，值得花一个下午把能力拆成 Skills 试试，收益通常立竿见影。
