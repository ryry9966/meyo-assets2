## 背景

Agent 的能力和它依赖的外部 API 强绑定：LLM 供应商、搜索、MCP 工具、业务系统。传统服务挂了会返回错误，Agent 的麻烦在于错误会进入推理循环——模型看到失败结果后，可能盲目重试、编造数据、或带着错误继续跑完全流程。所以错误处理不再是"返回 500"这么简单，而是要设计"失败之后 Agent 该干什么"。

## 常见的失败表现

- **幻觉型**：模型把空结果当真数据，继续往下推理
- **循环型**：无限重试同一个挂掉的接口，token 白白烧掉
- **阻塞型**：一个工具挂了，整条自动化流程卡死
- **静默型**：捕获异常后返回空字符串，上游毫无感知

## 做法：把恢复分成五层

1. **传输层重试**。只对 5xx、429、网络超时重试，指数退避加随机抖动，最多 3 次。401/403/400 这类 4xx 不要重试，重试只会放大问题。
2. **调用层超时预算**。每个工具调用设硬超时，且必须小于 Agent 单步预算。常见坑：HTTP client 超时 60 秒，Agent 循环跑一整晚。
3. **结构化错误上报给模型**。工具失败时返回标准信封，例如 `{ok:false, error_type:"upstream_timeout", retryable:true, hint:"30 秒后重试或改用缓存"}`。不要把原始 stack trace 塞给模型——浪费 token，还可能诱导模型"解读"出不存在的原因。
4. **降级策略**。按代价从低到高：返回带标注的过期缓存 → 切换备用工具/供应商 → 暂停并向用户提问（HITL）→ 落 checkpoint 终止任务。关键原则：宁可明确说"这是 2 小时前的数据"，也不要无声替换。
5. **熔断**。在插件/MCP server 层做简单熔断：连续 N 次失败后 fail fast 一段时间，避免 Agent 循环里每一步都去撞一次死接口。

## 踩坑点

- **重试非幂等操作**。POST 创建订单重试三次 = 三张订单。非幂等调用要么加请求 ID 去重做成幂等，要么不自动重试，交还给人。
- **吞错误**。catch 之后返回 `""` 或 `null`，模型会当"查询结果为空"处理，错得更远。
- **退避无抖动**。上游恢复瞬间所有实例同时重放请求，二次打挂。
- **靠 prompt 约束重试**。"最多重试三次"写在 system prompt 里，模型兴奋起来不守约。重试次数应在代码层硬性截断，prompt 只负责解释。
- **没测过失败路径**。CI 里 mock 429/500/超时，跑一遍 Agent 的降级行为，比上线后凌晨排障便宜得多。

## 可复用建议

- 所有工具统一包一层错误信封，`error_type` 用小集合枚举，模型和监控都好认。
- 给任务设总预算（时间 + token），超预算强制进入降级分支，而不是继续跑。
- 日志记录每次工具调用的 outcome（成功/重试/降级/失败），能回放就能定位。
- 遵循"报告并询问"优于"静默替代"：降级结果标注来源和时效，交给用户判断。

## 总结

外部 API 挂掉不是异常路径，是 Agent 的日常。把恢复机制做成代码层的硬约束 + 结构化的错误信息 + 明确的降级阶梯，Agent 才能在依赖抖动时保持"知道自己不知道"的状态——这比任何一次成功调用都更决定自动化流程的可信度。
