## 背景

Agent 的能力边界，基本等于它能稳定调用的外部 API。搜索、数据库、支付、通知，甚至上游模型本身，都是网络调用。在 OpenClaw 的插件和 MCP 工具链里这一点更明显：一个任务往往串起五六个工具调用，任何一个挂了，整条链路就停摆。Happy path 人人都会写，真正决定可用性的是错误恢复。

## 问题：三种典型翻车现场

1. **重试风暴**：LLM 看到工具报错，倾向于“再试一次”，而且没有退避概念，连打十几次，烧 token 还可能触发对方限流。
2. **幻觉兜底**：工具返回一段错误文本，模型没把它当成错误，脑补出一个看似合理的结果继续往下走，错得悄无声息。
3. **级联阻塞**：API 是慢而不是挂，没设超时，整个 Agent 循环被一个调用卡死，后面所有步骤排队等死。

## 做法：把恢复逻辑放进工具层

核心原则一句话：**重试和错误分类写在代码里，不要交给 LLM 决定。**

1. **错误三分类**：可重试（429 / 503 / 超时）、不可重试（400 / 401 / 404）、未知。分类逻辑写死在适配器里。
2. **统一错误契约**：返回给模型的不应是 stack trace 或 HTML 错误页，而是结构化结果 `{ok: false, error_code, retryable, hint}`，hint 明确告诉模型下一步该做什么（换参数 / 跳过 / 问用户）。
3. **有界重试**：最多 3 次，指数退避加随机抖动，在代码里循环，不进模型上下文。
4. **全链路超时**：连接超时、读取超时、单工具总超时分开设，超时按可重试处理。
5. **熔断与降级**：连续 N 次失败后把工具标记为 degraded，直接短路返回“此能力暂不可用”，并附降级方案——带时间戳的缓存数据、部分结果、或明确跳过该步骤。熔断器要有半开探测，否则 API 恢复了，工具还“死”着。
6. **幂等保护**：写操作全部带幂等键，重试才不会重复下单、重复发消息。

## 踩坑点

- **让 Agent 自己重试**是最常见的坑。LLM 的重试没有节奏，必须由代码接管。
- **静默吞错、返回空结果**：模型会当作成功处理，比直接报错更危险。
- **把上游错误页塞进上下文**：污染上下文不说，模型可能把乱码当数据用。
- **抖动不能省**：多个 Agent 实例同时恢复时，无抖动重试会形成惊群，把刚缓过来的 API 再打挂一次。
- **混淆 MCP 传输层错误和业务 HTTP 错误**：server 进程挂了和接口 500 是两回事，处理方式完全不同，混在一起会导致误重试。

## 可复用建议

- 所有外部调用套同一个适配器模板：超时 + 重试策略 + 错误归一化，新插件直接复用。
- 暴露给模型的永远只有三种结果：成功 / 可重试失败（已代为重试仍失败）/ 永久失败。
- 工具失败日志带 trace id，事后能还原一次任务里每个工具的完整调用链。
- 对 MCP server 做定期健康检查，别等第一次真实调用才发现它挂了。

## 总结

错误恢复不是 prompt 问题，是工程问题。工具层负责吸收重试、分类错误、执行降级；Agent 层只需要拿到清晰、可行动的结论。把“API 会挂”当作默认假设来设计，Agent 才能在生产环境里站得住。
