## 背景

OpenClaw 里每个会话——主会话、群聊、定时任务——都对应一份独立的 session 记录，模型每一轮看到的上下文就是这个 session 的完整历史。主会话是你和助手日常对话的地方，它的历史一旦混进不该有的内容，后续每一轮都要为此买单：上下文只会越来越重，没有天然的"遗忘"机制。

## 问题

最常见的污染源是子任务。比如让主 Agent"调研三个框架并给选型建议"，如果所有中间过程——搜索输出、读文件、试跑命令——都写进主会话，几轮之后过程噪音就会填满上下文：token 成本上升、注意力被稀释，模型甚至把中间结论当成"用户说过的话"。另一个坑是并发：多个子任务如果共用主会话的 session key，写入会交错甚至互相覆盖。

## 做法

1. **用 `sessions_spawn` 派生子会话。** 子 Agent 拿到独立的 session key（含 runId）和独立 transcript，与主会话物理隔离，这是隔离的起点，不要绕过它手工拼会话。
2. **任务简报要"蒸馏"，不要"转发"。** spawn 的 prompt 只放四样东西：目标、约束、交付格式、禁止事项。不要把主会话整段历史粘进去——子 Agent 需要的是结论，不是聊天记录。
3. **约定回传通道。** 子 Agent 默认不直接对用户说话，结果通过完成通知或 `sessions_send` 回给父会话，由父 Agent 决定怎么呈现。这条必须写进子 Agent 指令。
4. **用完即清。** 给子会话设 TTL 或在完成后清理，避免 session 列表堆满一次性任务的残留。
5. **定时任务同理。** cron / heartbeat 触发的任务本身就走隔离会话，别为了省事让它复用主会话 key。

## 踩坑点

- 子 Agent 调了消息类工具直接回复用户，主会话随后又总结一遍，用户收到两份。指令里明确写"不要主动给用户发消息"。
- spawn 时把父会话 transcript 整段塞进去，子会话成本反超主会话，隔离变成了搬运。
- 并发 spawn 没带唯一标识，两个子任务的输出混进同一个 key，排障时根本分不清谁写的。
- 子会话不继承主会话的 cwd 和部分环境变量，文件操作记得用绝对路径。
- 排障时在主会话历史里找不到子 Agent 的过程——它的记录在自己的 session 文件里，排查要去对应的 transcript 看。

## 可复用建议

- 一条边界原则：**父会话留决策，子会话留过程，跨边界的只有摘要。**
- 把 spawn 简报做成固定模板（目标 / 约束 / 交付格式 / 禁止事项），团队内统一，减少每次现编的随意性。
- 需要多个 Agent 协作时，单独开一个群聊式会话做 agent-to-agent 通信，主会话只接收最终结果，不要把中间讨论引回主会话。
- 定期审计 session 列表，清掉孤儿子会话；保留子会话 transcript 用于复盘，但永远不要把它回灌进主上下文。

## 总结

session 隔离不是某个开关，而是一种边界纪律：主会话是用户的记忆，子会话是任务的草稿纸。草稿纸可以随便画，但交回来的只能是答案。守住这条边界，长任务的上下文成本和混乱程度都会明显下降——而且这套纪律不依赖特定版本，今天就能在你的工作流里落地。
