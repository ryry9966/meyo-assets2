# Agent 的 tools.md：管理本地配置和环境差异的正确姿势

## 背景

跑 OpenClaw / Agent 这类能执行本地命令的自动化流程，最不可控的变量往往不是模型，而是机器本身：同样是“装依赖再跑测试”，mac 上是 `uv sync`，CI 容器里是 `pip install -r`，内网环境还得先挂代理。这些差异如果靠每次对话口头补充，或者不断堆进 system prompt，迟早出事。

我们团队半年前开始用一个很轻的做法：给每个 agent 工作区配一份 `tools.md`，作为“环境说明书”。落地后，反复试错和“在我机器上是好的”这类问题明显减少。

## 问题

没有 tools.md 时，常见三类故障：

1. **配置散落**。路径、端口、代理地址同时出现在 `.env`、shell rc、任务描述里，三处互相漂移，没人知道哪份是对的。
2. **Agent 猜测执行**。不知道本机用哪个包管理器、服务起在哪个端口，于是挨个试。失败几轮后开始自由发挥——我见过它擅自改了全局 pip 配置。
3. **没有单一事实来源**。换机器、交接、CI 复跑时，环境知识全在某个人脑子里。

## 做法

核心思路：**把环境差异文档化，并让 agent 能主动消费它**。

**第一步：建文件，和人看的文档分开。** 在项目根目录建 `tools.md`，定位是给 agent 读的；README 继续给人看。两者混写的结果是两边都读不明白。

**第二步：固定章节骨架。** 我目前用的结构：

- 运行环境：OS、shell、Python/Node 由什么工具管理（pyenv/fnm 等）
- 依赖管理：明确用哪条命令装依赖，禁止什么（如禁止全局 pip install）
- 标准命令：构建 / 测试 / lint 各一条，可直接复制执行
- 服务与端口：本地服务地址、数据库连接方式、已占用端口
- 网络与代理：镜像源、代理地址、需绕过的域名
- 禁区：不允许触碰的目录和命令

**第三步：引导文件只留一句话。** 在 AGENTS.md 或系统提示里写“执行任何工具调用前，先读 tools.md”，细节全部下沉。提示词从两百行缩到十几行，稳定性反而更好。

**第四步：配一个环境探测脚本。** 写个 `scripts/env_probe.sh`，输出 Python 版本、包管理器、代理可达性等关键信息。tools.md 里注明：“对环境没把握时先跑它，不要猜。”

**第五步：分层与版本化。** tools.md 进 git；机器特有内容放 `tools.local.md` 并 gitignore。模板保证结构一致，本地覆盖保证真实，团队共享公共层。

## 踩坑点

- **写成第二份 README**。大段背景介绍 agent 根本不需要，要短、命令化。我的经验是超过 80 行就该砍。
- **硬编码个人路径**。`/Users/xxx/...` 换台机器就废，统一用 `~` 或由 probe 脚本输出。
- **与 .env 双写**。tools.md 只写“密钥在 .env 的哪个键”，绝不复制值，否则必然漂移。
- **密钥入库**。token 写进 tools.md 再 push 是真实发生过的事故。文件头加红线声明，CI 里加一道正则扫描。
- **更新不闭环**。装了新工具没回写文档。我们在 PR 模板里加了一条“环境有变更则更新 tools.md”，靠流程兜底。
- **层级优先级不明**。全局与项目各有 tools.md 时，必须在文件头写明“项目覆盖全局”，否则 agent 行为不可预测。

## 可复用建议

- 把 tools.md 当接口文档维护：改环境等于改接口，必须过 review。
- CI 里对文档中的命令做 smoke test（至少 `--version` 级别），防止文档悄悄烂掉。
- MCP 场景同样适用：server 启动方式、依赖的本地路径，都值得写进去。
- 新成员或新 agent 接入时，先跑 probe 脚本再跑任务，作为标准 onboarding 动作。

## 总结

tools.md 解决的不是技术问题，而是信息架构问题：把环境知识从对话上下文和个人记忆里搬出来，变成版本化、可探测、分层的单一事实来源。原则就五条：短、可执行、可探测、分层、不藏密钥。它不性感，但 agent 每少试错一轮，省下的都是实打实的 token 和时间。
