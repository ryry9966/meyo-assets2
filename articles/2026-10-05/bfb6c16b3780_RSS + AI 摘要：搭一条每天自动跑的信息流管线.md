订阅了几十个技术博客和周刊，RSS 本身很稳定，问题是我读不过来——unread 囤到三天以上基本就放弃了。目标很明确：每天早上固定时间，把过去 24 小时的新条目抓下来、过滤、让模型做摘要，生成一份日报推到 IM，同时落盘存档。

## 问题

一开始试过直接让 agent「自己去网上看看今天有什么新东西」，效果很差：慢、贵、结果不可复现。后来想清楚了一件事：

**不要让模型负责流程。让管线负责确定性，模型只负责「把已知内容压缩成摘要」这一个环节。**

## 做法

整体四层，每层独立可替换：

```
聚合层         处理层            摘要层       分发层
Miniflux   →   去重/预过滤/   →   分批调LLM →  IM推送
(FreshRSS)     正文提取                     + notes落盘
      └── OpenClaw cron 每日 8:00 触发 skill 脚本 ──┘
```

1. **聚合层**：Miniflux 自托管，负责抓取、标记已读、暴露 API。没有 RSS 的站点用 RSSHub 补源。也可以把抓取封装成 MCP tool，但流程固定的话，一个脚本更省事。
2. **触发层**：OpenClaw cron 任务，每天早上触发一次 skill 脚本，跑完写日志。
3. **处理层**：拉取 unread，用 link 归一化后的 hash 去重；关键词白/黑名单 + 来源权重做预过滤；对留下的条目做正文提取（readability）和 HTML 清洗。
4. **摘要层**：过滤后的条目分批喂模型，prompt 固定输出 schema——每条不超过两句、附原文链接、打一个分类标签。
5. **分发层**：渲染成日报 Markdown 推送到 IM；同时写入 notes 目录，攒够一周自动出周报。

## 踩坑点

1. **别直接总结 RSS 的 description**。很多源只有标题加一两句摘要，模型会顺着标题编内容。必须回抓原文；抓不到就标记「仅标题收录」，不要硬总结。
2. **去重不能只看标题**。跨源转载很常见，标题略改就漏过。用归一化后的 link 做 hash 相对可靠。
3. **成本会失控**。全量条目都进 LLM，一个月 token 相当可观。规则预过滤通常能砍掉 70% 以上，这步比换便宜模型有效得多。
4. **HTML 残留会污染 prompt**。标签、CDATA、实体字符没清干净，输出格式也跟着崩。清洗必须发生在模型之前。
5. **输出格式漂移**。模型偶尔不按 schema 来，下游渲染就挂。加一层校验：失败重试一次，再失败降级成纯链接列表，别让整条管线挂掉。
6. **幂等**。处理完就把条目标记 read，cron 意外重复触发时直接跳过，避免日报出现重复段落。

## 可复用建议

- 四层解耦，任何一层单独替换都不影响其他层：聚合层换 FreshRSS、摘要模型随便换，都不用动其余代码。
- prompt 模板放配置文件，别写死在代码里，方便版本化和回滚。
- 每次运行记录：总条目数、过滤后数量、token 消耗、失败原因——这是后续调过滤规则唯一靠谱的依据。
- 摘要永远保留原文链接。模型给的是「值不值得点进去」的判断依据，不是阅读的替代品。
- 先把日报跑稳两周，再考虑加周报和分类，别一上来堆功能。

## 总结

这套管线里模型只做一件事：把确定抓到的内容压缩成可读摘要；抓取、去重、过滤、分发全部交给确定性代码，OpenClaw 负责调度。架构不复杂，一个下午能跑通第一版。之后的精力主要花在过滤规则和 prompt 迭代上——日报的质量最终由这两块决定，而不是模型本身。
