## 背景

OpenClaw 类 Agent 大部分时间是“被动”的：用户发消息才跑。但自动化场景经常需要它主动——定时巡检仓库状态、盯一个文件变化、等一个外部长任务收尾。这就绕不开 heartbeat（心跳）机制：要么你定期叫醒它（轮询），要么外部事件来了推它一把（推送，webhook 或 MCP 通知都算）。

## 问题

两条路线各有硬伤：

- **轮询**：每次心跳本质上是一次模型调用，哪怕无事发生也在烧 token。间隔太密成本爆炸，太疏响应滞后。更隐蔽的是心跳本身会往会话里写内容，几轮之后上下文被“我检查了一下，没事”刷满，真正重要的信息反而被稀释。
- **推送**：及时、省调用，但要求有一个可达入口。本地跑的 Agent 要么开公网 webhook（NAT 和安全都是麻烦），要么挂隧道。而且推送只覆盖“有事件”的情况，覆盖不了“没事件但状态漂了”——比如某个后台任务悄悄死了。

## 做法

我们的结论是混合架构：**推送管及时性，低频心跳管兜底**。落地步骤：

1. **给任务分类**。延迟敏感的（消息、回调）走推送；周期性的（每日巡检）走固定心跳；其余只保留一条兜底心跳。
2. **心跳要“先查后想”**。调度器触发时先跑一段 shell 门禁：比对文件 mtime、git status、队列深度这类廉价信号，命中条件才调模型。无事的轮次，模型根本不该被调用。
3. **推送侧做一个本地桥**。webhook 打到 127.0.0.1 的小服务，落队列，带 idempotency key；Agent 从队列消费，桥负责去重和合并。
4. **间隔自适应**。连续 N 次 no-op 就拉长间隔，一旦有事重置回去；系统休眠唤醒后只补跑一次，不追帧。

## 踩坑点

- **心跳写进主会话**：上下文污染重灾区。改用旁路会话或临时 session，只在需要行动时注入一条摘要。
- **webhook 重试没有幂等键**：一次告警触发三遍任务，队列里全是重复项。
- **用进程内 timer 做心跳**：机器睡眠、进程重启后悄悄失效。换系统 cron + 错峰 jitter 更稳。
- **门禁检查也交给模型**：等于没省。判断必须发生在模型调用之前，这是整个设计里最容易做错的一步。

## 可复用建议

- 一句话原则：**便宜地查，贵贵地想**。判断逻辑放 shell/脚本，推理留给模型。
- 事件合并：Agent 睡着期间积累的多个事件，醒来合并成一条处理，别逐条唤醒。
- 推送优先走本地回环 + 队列，确实需要外部可达再上隧道，并加签名校验。
- 给心跳做观测：记录每次心跳的触发原因、是否命中门禁、是否真的调了模型。跑一周，你自然知道该调哪一档间隔。

## 总结

轮询和推送不是二选一，而是分工：推送解决“有事件要快”，心跳解决“没事件也要对”。真正决定成本和可靠性的，是模型调用之前那层便宜的判断。先把门禁做好，再去谈间隔和通道。
