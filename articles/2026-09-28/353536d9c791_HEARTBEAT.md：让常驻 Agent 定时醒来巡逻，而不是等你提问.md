## 背景

大多数 Agent 的使用模式是被动的：你提问，它回答，会话结束就沉寂。但 OpenClaw 的常驻网关架构其实留了另一个入口——agent 一直在线，完全可以定时醒来自己做点事。`HEARTBEAT.md` 就是这个机制：放在 agent 工作区（默认 `~/.openclaw/workspace/`）下的一个 Markdown 文件。每隔一个周期（默认 30 分钟），agent 被唤醒读一次这个文件，然后自己判断：有事就做、就报告；没事就继续沉默。

## 问题

主动性的反面是噪音和成本。如果直接写一句"每隔半小时帮我检查一切"，你会在一周内收获：token 烧穿、消息轰炸、以及几条毫无价值的晨间问候。所以真正要解决的问题是：**怎么把"主动"约束成"值得主动"**。

## 怎么做

1. **写检查项，不写愿望。** 每条必须包含路径、阈值、动作三要素。比如："检查 `/var/log/app/` 下是否有 ERROR 级别的新增日志，超过 5 条则摘要发到我当前会话；否则返回 HEARTBEAT_OK。"而不是"帮我盯着服务"。
2. **把沉默规则写死在文件开头。** HEARTBEAT_OK 是约定信号：无事可做时 agent 返回它，网关保持安静。这条不写清楚，agent 会倾向于"汇报点什么"。
3. **调试期调短间隔。** 把 heartbeat 间隔临时改成 5 分钟，观察日志里它每次醒来实际调了哪些工具、说了什么，跑顺后再调回 30 分钟或更长。
4. **重活分流。** 心跳适合轻量检查。备份、全量扫描这类批处理交给系统 cron，心跳只负责"看一眼 cron 的结果文件，决定要不要通知你"。

## 踩坑点

- **检查项太模糊。** "看看邮件"会导致每次唤醒行为随机、消耗不可控，这是最常见的失败原因。
- **心跳跑在主会话上下文里。** 频繁心跳会把日常对话的上下文撑得很长，劣化响应质量。重活拆到独立 session，心跳只留结论。
- **权限等于放到了定时器上。** 心跳是无人确认自动执行的，你授给 agent 的 MCP 工具和插件写权限会被周期性行使。放开心跳之前，先审计一遍工具权限。
- **一次性任务会永远跑下去。** 临时加的检查项没人记得删。建议在文件里划一个"临时任务"区，每周清理。

## 可复用的建议

- 把 `HEARTBEAT.md` 当配置代码管理：进 git，改动留痕，出问题能回滚。
- 让心跳把每次执行结果 append 到一个状态日志文件，事后可审计"它这段时间到底干了什么"。
- 通知策略全部写成阈值式："只有 X 超过 Y 才发消息"，其余一律 HEARTBEAT_OK。
- 从 2~3 条高价值检查起步：磁盘水位、关键服务存活、今日待办提醒。跑满一周、确认它安静且有用，再逐条增加。

## 总结

HEARTBEAT.md 的价值不在于"自动化"这个概念，而在于它强迫你把"什么值得主动打扰我"写成显式规则。写得严谨，agent 会变成一个安静、可审计的值守者；写得随意，它只是一台定时烧 token 的机器。我的建议始终是：最小集合起步、日志审计兜底、阈值控制噪音，然后慢慢信任它。
