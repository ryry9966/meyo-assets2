## 背景

大多数 Agent 的默认形态是被动应答：你不发消息，它就不存在。演示里没问题，日常使用中空窗很明显——磁盘满了没人提醒，PR 挂了三天没人催，每天早上你还是得自己问一遍“昨天有什么要紧事”。所谓 proactive，就是给 Agent 补两个能力：在无人触发时被唤醒（定时、事件、状态变化），以及自己判断“这件事值不值得打扰你”。

## 问题

把 proactive 做砸的团队，几乎都栽在同一个坑上：把“能主动”理解成“多说话”。第一周用户觉得新鲜，第二周消息刷屏，第三周机器人被静音，proactive 能力宣告死亡。所以要解决的核心不是触发，而是过滤和分级。

## 做法

我们在 OpenClaw 侧把主动行为拆成四层，插件各管一段：

1. **触发层**。三类入口：cron 定时（固定节奏的汇总类工作）、webhook 事件（CI 失败这类外部推送）、轮询加阈值（自己查状态，超标才算事件）。关键约束：轮询本身不进模型，先用普通代码判断是否达标，达标才唤醒 Agent。

2. **唤醒上下文**。主动唤醒时没有会话历史，需要拼一份固定模板：触发原因、原始证据（日志、指标原文）、用户偏好（安静时段、粒度）。证据必须原文注入，不要让模型凭记忆脑补。

3. **决策门**。Agent 拿到上下文后先输出结构化判断：等级（打扰 / 汇总 / 可忽略）、理由、建议动作。规则层按等级路由：打扰级走即时通知，汇总级进每日摘要缓冲区，可忽略只记日志。

4. **反馈回路**。每条主动消息带一个“不需要这类提醒”的快捷操作，点击后调低该类触发的阈值。没有这个回路，阈值永远靠拍脑袋。

## 踩坑点

- **自触发死循环**：Agent 写回外部系统，写回又产生事件，再次唤醒自己。解法很朴素：所有事件带 actor 标记，自己的动作产生的事件直接丢弃。
- **无记忆的重复提醒**：每次唤醒是独立会话，同一问题能连催五天。要按主题维护“已提醒”状态表，带过期时间。
- **模型高估严重性**：LLM 天然倾向把事情说得紧急。分级 prompt 里要给明确标准和反例，拿不准时默认降级。
- **主动写的风险远大于主动读**。第一版只允许主动通知，写操作必须用户在场确认，跑稳一个月再逐类放开。

## 可复用建议

- **先规则后模型**：能用 if 判断的不要浪费 token，模型只评估“候选事件”。
- **渠道分级比调 prompt 更有效**：打扰、摘要、归档三条通道分开，比反复改提示词管用。
- **一切主动行为可追溯**：记录触发源、证据、决策理由，否则没法排查“它为什么半夜给我发消息”。
- **从低风险场景起步**：先上一个固定时间、只读、低频的场景（比如每天八点半的摘要），验证过滤逻辑后再上事件驱动。

## 总结

proactive 的核心不是让 Agent 更勤快，而是更克制：低成本地感知，严格地自我过滤，在正确的渠道用正确的频率出现。触发、上下文、决策门、反馈回路四层搭起来，主动助手才不会变成一个讨人厌的闹钟。欢迎大家贴出自己调阈值翻车的记录，这类数据比成功案例有用得多。
