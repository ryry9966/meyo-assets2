## 背景

把 Agent 工作流跑起来之后，有两件事会越来越明显：一是 API 账单，二是"数据出了我这台机器"的不安。本地部署大模型解决的就是这两个问题——数据不外流、没有按 token 计费、断网也能跑。对 OpenClaw / MCP 用户来说，本地模型更实际的价值是三个角色：隐私敏感工具调用的隔离层、批量任务的廉价工人、云端不可用时的兜底。

## 问题

动手前先回答三个问题，别跳过：

1. 这台机器的显存/内存，到底能舒服地跑多大的模型？
2. 用哪个推理运行时？
3. 接进 Agent 工作流后，工具调用（function calling）质量是否过关？这是最容易被忽略、也最影响体验的一点。

## 做法与步骤

**1. 盘点硬件。** 决定性指标是显存。粗略估算：模型占用 ≈ 参数量 × 量化字节宽 + KV cache。16GB 显存舒服跑 14B 的 Q4；8GB 跑 7B/8B 的 Q4；纯 CPU + 32GB 内存能跑 14B Q4，但只有个位数 token/s，适合离线批处理，不适合交互。

**2. 选运行时。** 从 Ollama 起步：开箱即用，自带 OpenAI 兼容接口。需要细粒度控制再上 llama.cpp / LM Studio；Linux + NVIDIA 的批量吞吐场景才考虑 vLLM，家用大多是杀鸡用牛刀。

**3. 选模型与量化。** Q4_K_M 是默认起点，别为了省显存压到 Q2。选型时优先看官方是否做过工具调用训练——agent 场景对这点远比对"聊天聪明"敏感。

**4. 接入工作流。** 把 base_url 指到本地端点即可。但先显式设置上下文长度，不要用默认值（见踩坑第 1 条）。

**5. 压测。** 用你真实的 agent 任务跑，而不是通用榜单。记录三件事：token/s、多轮工具调用成功率、长上下文下是否开始胡编。

## 踩坑点

- **默认上下文极小。** Ollama 默认 2048/4096，agent 跑几轮就悄悄截断，还未必报错。务必显式设置。
- **量化过狠，工具调用先崩。** 表现是 JSON 括号不闭合、参数幻觉，Q4 以下慎用。
- **KV cache 吃显存。** 上下文开到 32k，实际占用可能翻倍，先算再开。
- **笔记本降频。** 长任务跑十分钟散热压不住，token/s 掉一半，散热是真需求。
- **模型放机械盘。** 首次加载等好几分钟，统一放 SSD。
- **小模型在多工具 agent 里迷路。** 工具超过五六个就容易跑偏。要么精简工具集、强化系统提示词，要么换架构：规划交给云端大模型，执行交给本地小模型。

## 可复用建议

1. **分层使用。** 本地模型负责分类、抽取、草稿和隐私任务的执行；复杂推理留给云端。别指望本地 8B 平替前沿模型。
2. **固化压测脚本。** 一份能重复跑的评测脚本，比任何评测榜单都有说服力。
3. **建模型档案卡。** 每个模型记一行：量化等级、显存占用、token/s、工具调用表现。半年后你会感谢这张卡。
4. **配置进 git。** 运行时参数、系统提示词、评测脚本全部版本化，换机器可复现。

## 总结

本地部署已经足够成熟，能真正进入 agent 生产链路，但它不是云端前沿模型的平替，而是架构里的一个分层。务实的路径：Ollama + 8B Q4_K_M 起步，用真实任务压测，让数据告诉你本地与云端的边界划在哪。跑起来之后你会发现，最有价值的不是省下的 API 费，而是整条自动化链路终于完全跑在自己手里。
