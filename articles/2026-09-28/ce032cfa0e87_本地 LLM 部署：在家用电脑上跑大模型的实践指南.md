## 背景

过去一年我主要用云端 API 跑 OpenClaw 的 agent 流程，直到两类需求把本地部署提上日程：一是部分自动化任务涉及私有文档和数据，不方便出网；二是高频的结构化小任务（抽取、分类、格式转换）走大模型 API 属于高射炮打蚊子。于是我在一台 32GB 内存 + RTX 3060 12G 的台式机上做了完整验证，这篇记录过程与结论。

## 问题

动手前要回答三个问题：

1. 这台机器“能跑多大”的模型？
2. 跑起来的模型，能否稳定承担 Agent 的工具调用，而不是只会聊天？
3. 长期挂在本机跑自动化，资源占用和稳定性是否可接受？

第三个问题最容易被忽略：能跑通一次 demo，和能扛住每天几百次调用，是两回事。

## 做法与步骤

**1. 盘点硬件，估算规模。** 经验公式：Q4_K_M 量化下，模型文件约为参数量 × 0.6 GB。7-8B 约 5GB，14B 约 9GB，32B 约 20GB。显存能装下权重 + KV cache 才有全速推理；12G 显存的现实上限是 14B Q4（16k 上下文），32B 必然部分落 CPU，速度掉到个位数 token/s。

**2. 选运行时。** 直接上 Ollama 或 llama.cpp，两者都暴露 OpenAI 兼容接口，OpenClaw 侧只需改 base_url 和模型名，不用写适配层。LM Studio 适合前期手动试模型，定型后换回命令行方案。

**3. 选模型。** 中文能力 + 工具调用两个硬指标下，Qwen 系列的 7B/14B Instruct 是性价比最高的起点。量化优先 Q4_K_M，比 Q8 小一半，质量损失在 agent 任务里基本无感；低于 Q4 就必须重新跑评测。

**4. 压上下文。** 别默认开 32k/128k。Agent 的系统提示词加上 MCP 工具的 schema 很容易吃掉 2-4k token。把 ctx 控制在 8k-16k，KV cache 能省 1-2GB 显存，还给工具返回结果留出余量。

**5. 接入验证。** OpenClaw 指向本地端点后，先跑一个只有 1 个 MCP 工具的最小 agent，再逐步加到 5 个、8 个。每轮记录：调用格式正确率、参数字段完整率、端到端延迟。

## 踩坑点

- **小模型的函数调用很脆。** 7B 级别模型在工具多、参数复杂时会输出残缺 JSON 或编造参数名。对策：工具数压到 10 个以内、温度降到 0.1-0.2、schema 枚举值写死，能救回大部分。
- **部分层落 CPU 后速度崩塌。** 宁可换更小的模型全量进显存，也不要 14B 半载硬跑，后者体验远差于全量 7B。
- **上下文悄悄膨胀。** 某个 MCP 工具返回大段文档，直接把会话顶爆。给工具结果做截断或摘要，在本地小模型场景是刚需。
- **别指望小模型做复杂多步规划。** 单步、结构化、边界清晰的任务它干得不错；让 7B 自己拆解十步工作流，成功率惨不忍睹。

## 可复用建议

- **建一个 20 条左右的工具调用测试集**，每次换模型、换量化、改上下文后回归一遍，五分钟出结论，比“感觉变笨了”可靠得多。
- **分层路由**：本地模型接结构化小任务和敏感数据任务，规划与长文写作仍走云端 API，OpenClaw 里按任务类型配不同模型即可。
- **固定模型版本**。`qwen2.5:7b` 这类浮动 tag 会在上游更新后悄悄变化，自动化场景务必 pin 到具体版本。
- **记原始请求/响应日志**。本地部署最大的红利就是数据全在自己手里，出问题时能完整回放。

## 总结

家用电脑跑本地 LLM 如今已是成熟方案，但它的正确定位是“Agent 体系里的一个专用节点”，而非云端模型的平替。12G 显存 + 14B Q4 + 收敛的上下文 + 少量工具，这套组合足以稳定承担日常自动化的结构化任务。先跑通最小闭环，再谈规模，比一步到位省心得多。
