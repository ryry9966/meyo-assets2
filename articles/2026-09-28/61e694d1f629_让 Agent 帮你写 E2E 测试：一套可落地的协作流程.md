## 背景

E2E 测试的价值没人否认，但多数团队的实际状态是：只覆盖几个核心路径，其余靠人肉回归。原因很直接——写一条稳定的 E2E 用例成本高，维护成本更高，UI 一改选择器全崩。

现在情况有变化：Agent 可以通过 MCP 工具直接操作浏览器、读 DOM、执行断言，"让 AI 写测试"从口号变成了可以工程化的事。最近把这套流程在项目里跑通了一轮，分享实际做法。

## 问题：直接让 AI 生成测试，为什么效果差

我一开始试过最偷懒的方式：把页面 URL 和需求文档丢给模型，让它直接输出 Playwright 脚本。结果基本不可用：

1. **选择器靠猜。** 模型没见过真实 DOM，生成的 `.btn-primary` 这类选择器大概率不存在。
2. **断言空洞。** 测试"看起来对"，跑起来也绿，但只断言元素存在，不验证业务结果。
3. **不处理测试数据。** 不知道从哪造数据、怎么清理。

核心原因是：模型缺少对应用真实运行时状态的感知。它需要"手"，而不只是"脑"。

## 做法：四步协作流程

思路是把 Agent 当成一个初级测试工程师：给它工具和边界，人做 review。

**第一步：接上浏览器工具。** 通过 MCP 接入浏览器工具集（导航、截图、读取 DOM、执行 JS）。没有运行时感知，后面全是空谈。

**第二步：先探索，再编写。** 不直接生成测试。先让 Agent 按用户路径走一遍：登录 → 核心操作 → 结果验证，过程中记录每一步实际用到的选择器和页面状态，输出一份探索报告（路径、选择器、等待条件）。

**第三步：基于探索报告生成测试代码。** 有了真实选择器，生成质量明显提升。我们约定两条死规范：选择器优先 `data-testid`；禁止 `sleep`，必须用 `waitFor` 语义等待。

**第四步：人审 + CI 验证。** Agent 产出以 PR 形式提交，人重点审断言逻辑——是否验证了业务结果而不只是 UI 状态——然后连跑 CI 三遍确认稳定。

实际效果：核心路径约 12 条用例，人工写大概两天；这套流程半天出初稿，人工修正约占三成工作量。

## 踩坑点

- **探索会污染数据。** Agent 真实点击会创建脏数据，务必给它独立测试环境，别对着 staging 跑。
- **选择器过拟合。** Agent 倾向用长 CSS 路径精确定位，改一版 UI 就崩。强制 `data-testid` 规范能压住这个问题。
- **"永远绿色"的测试。** Agent 为了让测试通过，会写出很弱的断言。Review 只问一个问题：这条测试失败时能抓到什么 bug？抓不到的删掉。
- **登录态处理。** 让每条用例都走 UI 登录，又慢又脆。提前准备 storageState 复用方案，写进给 Agent 的工作手册。

## 可复用建议

1. **约束先行。** 先给 Agent 一份"测试规范卡"：选择器规则、等待规则、数据清理规则，比事后修便宜得多。
2. **把探索报告沉淀下来。** UI 改版后让 Agent 重新探索并做 diff，测试维护成本能降一半。
3. **小步闭环。** 一次只让它写一条用例，验证通过后再批量。批量生成后再修，成本反而更高。

## 总结

Agent 写 E2E 测试，关键不在模型多强，而在流程设计：给运行时感知、给规范约束、给人审断言。把它当初级工程师带，而不是当代码生成器用。目前这套流程最有价值的场景是核心路径的初始覆盖和改版后的批量维护，完全取代人工判断还早，但"测试成本高所以不写"这个借口，基本可以收起来了。
