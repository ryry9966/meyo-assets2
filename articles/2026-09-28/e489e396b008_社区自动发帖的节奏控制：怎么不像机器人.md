## 背景

我们把 OpenClaw 接上 MCP 的论坛插件后，跑通了一条「聚合每日讨论 → 生成摘要 → 自动发帖」的流水线。技术上很顺利，但跑了三周，社区里出现了这类反馈：帖子太准点了，每天 09:00:00 前后 30 秒内必到，结构一模一样，连 emoji 的位置都一样。有成员直言「一看就是脚本」。

严格说，流水线没有任何故障——但结果上就是失败的：大家开始默认忽略这类帖子，摘要等于白发。

## 问题

人判断「像不像机器人」，看的不是单条帖子，而是**时间序列**。固定间隔、固定结构、零互动，三者叠加就是特征。所以节奏控制不是写死一个 `sleep`，而是把调度从 cron 思维改成队列思维：发布器独立于生成器，才有地方做抖动、限流和撤销。

## 做法（我们目前的配置）

1. **生成与发布解耦。** Agent 生成后先入队，由独立发布器按窗口投放。
2. **活动窗口内抖动。** 基础间隔 + ±25 分钟随机抖动，但限定在社区活跃时段（我们后台数据显示是工作日 9–11、14–17、20–22 点）。凌晨 4 点的「随机」发帖比准点更像机器人。
3. **频率上限与冷却。** 每天上限 2 条；某条回复热度高就进入 4 小时冷却，避免刷屏感。
4. **发帖前自检。** 发布器通过 MCP 读最近 12 小时频道历史：已有相似内容就跳过、合并进下一条；当天额度用完就顺延。
5. **结构轮换 + 风格约束。** 准备 3–4 种摘要骨架（列表式 / 叙事式 / 问答式），并在 prompt 里明确禁止默认的「三段式 + emoji 清单」。不约束的话，模型会自己漂回默认文风。
6. **互动降速。** 不秒回评论，回复进同一个队列，延迟 10–40 分钟分批处理；争议性回复直接升级人工。

最小配置长这样：

```yaml
pacing:
  active_windows: ["09:00-11:00", "14:00-17:00", "20:00-22:00"]
  base_interval_min: 240
  jitter_pct: 25
  daily_cap: 2
  cooldown_after_hot_min: 240
  dedup_window_h: 12
```

## 踩坑点

- **定时器重试导致重复发帖。** 一次发布超时后 cron 重发，同一内容出现两条。后来给每条内容算 hash 作幂等键，发布前查重，才算堵住。
- **模板轮换被看穿。** 只准备两个模板，等于换了一个更明显的规律；轮换池至少三套，且长度、语气也要变。
- **灰度期太快。** 新接入的自动化头两周应把频率压到最低，先让社区习惯它的存在，再谈节奏。一上来就日更两条，必然被贴标签。
- **忽略周末和节假日。** 周末还按工作日窗口发，本身就是异常信号。

## 可复用建议

- 基础间隔 + ±20%~30% 抖动，且抖动只发生在活跃窗口内；
- 日上限 + 热度触发冷却，两条腿缺一不可；
- 内容 hash 幂等，防重发是底线工程；
- 发布前自检三问：最近 N 小时有无相似内容？当前在活跃窗口吗？今天额度还剩吗？
- 上线前两周人工过审，之后转为每周抽查一次实际发布时间分布。

## 总结

所谓「不像机器人」，本质不是伪装，而是**别打扰**。规律性才是最大的破绽：把准点改成窗口，把固定结构改成轮换，把无限流改成上限加冷却，把秒回改成延迟分批。调度器越「笨」，输出越像人。
