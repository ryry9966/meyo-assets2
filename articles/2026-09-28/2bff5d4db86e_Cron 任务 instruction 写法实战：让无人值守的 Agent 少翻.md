## 背景

OpenClaw 的 cron 任务，本质是定时唤醒 Agent 执行一段 instruction。它和交互式会话有两个关键差异：一是**无人值守**，跑的时候你大概率不在场，没人回答 Agent 的追问；二是**上下文干净**，每次触发都是全新会话，没有历史记忆。

这两点决定了：cron 的 instruction 不是随手一句"每天帮我总结下新闻"，而是一份写给无人值守执行者的 SOP。写得好不好，直接决定任务是稳定交付，还是三天两头翻车。

## 常见问题

翻自己踩过的坑和社区里的问题，失败案例高度集中在几类：

1. **指令太模糊**："帮我看看今天的动态"——范围、来源、输出格式全靠模型猜，每次结果都不一样。
2. **假设了会话记忆**："继续上次的整理"——cron 会话里没有"上次"。
3. **没有输出契约**：Agent 回一段千字长文，或干脆反问一句然后卡住，消息通道里躺着一个没人理的问题。
4. **没有降级路径**：工具调用失败、token 过期、网络超时，任务静默失败，第二天才发现日报断更。

## 做法：六段式模板

我的做法是把 instruction 固定成六段，新建任务时照着填：

1. **触发上下文**：写明时区约定。时区以 cron 表达式配置为准，instruction 里不要再用"早上"制造第二次歧义。
2. **任务定义**：一句话，动词 + 对象 + 范围。"汇总以下 3 个 RSS 源的昨日更新"远好于"看看新闻"。
3. **输入来源**：显式列出文件绝对路径、URL、MCP 工具名，不要指望 Agent 自己找。
4. **输出契约**：格式（几条要点、字数上限）、投递目标（哪个通道/会话），并约束"不附加解释"。
5. **边界与禁止**：模型很擅长"好心"扩展任务，比如顺手改了你的文件，必须用禁止清单拦住。
6. **降级路径**：输入不存在怎么办、发送失败怎么办。常见写法是"跳过并静默结束"或"写入失败日志"，二选一，别留空白。

一个日报任务的实际 instruction 大概长这样：

```text
[触发] 每日 08:00（Asia/Shanghai），由 cron 调度。
[任务] 汇总 3 个 RSS 源过去 24h 的更新。
[输入] 调用 mcp__rss__fetch，源列表见 workspace/sources.json。
[输出] 不超过 5 条要点，每条 ≤ 40 字，发送到 Telegram「日报」会话。
[禁止] 不修改任何文件，不调用列表外工具，不附加解释。
[降级] 输入为空则直接结束；发送失败则写入 logs/report-fail.log 后结束。
```

写完别急着上线，手动触发一次 dry-run，看输出是否符合契约，再迭代一版。

## 踩坑点

- **时区双重定义**：cron 表达式和 instruction 各写一次时间，配置改了指令忘改，任务时间错乱。以 cron 为准。
- **可变数据写死在指令里**：源列表一变就得改 cron。把可变部分抽到 workspace 文件，指令只引用路径。
- **长指令 ≠ 好指令**：塞一堆无关背景会稀释关键约束，六段之外的内容尽量删。
- **幂等性**：任务重试可能重复发消息、重复写文件。有副作用的任务，指令里写明去重依据（比如按日期生成文件名）。
- **没有失败信号**：重要任务加一条兜底——连续失败时换一条通道通知你。

## 可复用建议

1. 把六段式模板存成 snippet，新建 cron 任务时直接套用。
2. cron instruction 纳入 git 管理，改动可回溯、可 diff。
3. 上线前必须手动 dry-run 至少一次，别等第二天看结果。
4. 定期审视：跑了一个月没出问题的任务，指令往往是合格的；频繁跑偏的，先查指令再看工具。

## 总结

Cron 任务的 instruction，本质是给一个无人值守、没有记忆、但很听话的执行者写操作手册。把触发上下文、输入、输出、边界、降级写清楚，大部分"Agent 不靠谱"的问题会消失——不靠谱的往往不是 Agent，是那段随手写的指令。
