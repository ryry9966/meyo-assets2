## 背景

OpenClaw 的 agent 每次进入一个工作空间，最先读的不是你的聊天记录，而是 AGENTS.md。它放在工作空间根目录（以及各级子目录）的纯文本说明书，作用类似 Makefile 之于构建、README 之于人类协作者——只不过读者是模型。没有它，agent 只能靠猜测和历史对话拼凑上下文，行为全凭运气。

## 问题

实际用下来，最常见的三类翻车：

1. agent 不知道怎么跑测试、跑 lint，自己发明命令，顺手装了一堆不该装的依赖；
2. 项目有隐含约定（目录职责、命名、提交格式），agent 每次都违反，你每次都要在对话里纠正一遍；
3. 危险操作没有边界：直接改配置、动数据库、往 main 上推提交。

这些本质上都不是模型能力问题，而是上下文缺失。你缺的不是更强的模型，是一份写清楚的工作空间手册。

## 做法

我的 AGENTS.md 从十几行开始，按需增长，结构大致是：

- **项目概览**：两三句话，这个工作空间是干什么的，技术栈是什么。
- **常用命令**：跑测试、格式化、构建的确切命令，只写验证过能跑通的。
- **约定**：目录职责、命名规则、提交信息格式。写“做什么”，别写“为什么”，背景放代码注释里。
- **边界**：明确禁止的操作，比如“不要修改 config/ 下的文件”“涉及写数据库时先停下来问我”。
- **已知坑**：模型反复犯的错，一条一行。

子目录可以放各自的 AGENTS.md，OpenClaw 会就近加载、覆盖上层，比如 `plugins/` 下单独写插件开发规范。

每条指令尽量写成可验证的形式。“测试用 pnpm test:unit，跑通再交付”比“请保证质量”有用得多。

## 踩坑点

- **写太长**。超过一两百行，后面的内容命中率明显下降。手册不是文档，长文档链接出去，这里只留索引。
- **过期指令比没有指令更糟**。命令改名了、目录搬了，AGENTS.md 还写着旧的，agent 会理直气壮地错。把它当代码的一部分，改动进 PR review。
- **写成愿望清单**。“写高质量的代码”这种话模型无从执行，等于没写。
- **根目录和子目录打架**。规则冲突时 agent 行为不可预测，改完记得全局搜一遍。
- **往里塞敏感信息**。AGENTS.md 会进上下文，也常会进 git，密钥和内网地址不要写。

## 可复用建议

1. **当配置文件而不是文档**：进版本控制、进 code review、有变更记录。
2. **两次原则**：同一个错误纠正到第二次，就写进 AGENTS.md。这是性价比最高的维护方式。
3. **用新会话验收**：开一个全新会话，只靠 AGENTS.md 完成一次典型任务（比如“加一个接口并跑通测试”），跑不通说明手册有缺口。
4. **定期做减法**：删掉模型已经稳定遵守的条目，把上下文额度留给真正容易错的地方。

## 总结

AGENTS.md 的价值不在于写得漂亮，而在于把“你脑子里默认知道、模型不知道的东西”固化下来。它是对话之外的持久记忆，也是团队内保证 agent 行为一致的手段。从十几行开始，每次 agent 犯错就补一条，一个月后你会得到一份真正贴合自己工作空间的操作手册。
