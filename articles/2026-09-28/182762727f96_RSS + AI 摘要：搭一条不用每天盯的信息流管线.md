## 背景

RSS 是我至今仍在用的信息获取方式：来源可控、无算法干预、随时退订。问题是订阅源一多，未读条目就变成新的负担。过去半年我的订阅涨到 40+ 个源，每天纯扫标题要花 40 分钟，而其中大部分条目并不值得点开。

## 问题

直接"让 agent 读 RSS"通常有两种失败姿势：

- 每次现拉现读，agent 反复调用 fetch 工具，慢且贵，还容易超时；
- 不过滤就把全部条目丢给 LLM 摘要，token 开销失控，产出还是一锅粥。

我想要的效果很朴素：每天固定时间收到一条结构化摘要，按来源分组，每条 2-3 句话，附原文链接，重复报道自动合并。

## 做法

管线拆成四段，抓取和摘要严格分离：

1. **抓取（纯代码，不走 LLM）**：用 OpenClaw 的定时任务触发一个脚本，rss-parser 拉取全部源，顺手做 URL 规范化（去掉 utm_* 参数）和编码修复，结果写入本地 SQLite，用状态字段记录已处理条目。
2. **预过滤（规则层）**：关键词黑名单、来源权重、标题粗打分，每天能砍掉约 70% 的条目。这一层省的是真金白银。
3. **摘要（LLM 层）**：剩余条目按来源分批，每批 8-10 条，prompt 里写死"只允许使用给定文本，信息不足就输出『信息不足』，禁止推测"。输出用固定模板：来源 / 标题 / 一句话摘要 / 链接 / 值得读的理由。
4. **推送**：digest 拼成一条消息，经 OpenClaw 推到我的即时通讯频道；同一份内容另存 Markdown 到笔记目录，留给周末精读。

整个脚本不到 200 行，LLM 只承担第 3 步。

## 踩坑点

- **只给摘要的 feed**：不少博客 feed 只输出截断的前 200 字，摘要质量直接崩。解法是在抓取层加一步 readability 正文抽取，抽取失败的条目标记降级，不要硬摘要。
- **跨源重复**：同一条新闻三个源都发。URL 去重不够用（各家追踪参数不同），我用"域名无关化 + 标题 3-gram 相似度"合并，超过阈值只保留权重最高的源。
- **cron 重叠**：某天 LLM 接口变慢，任务跑了 25 分钟，下一轮定时又触发，消息推重。加了个简单的锁文件，任务启动先抢锁。
- **静默失败**：管线挂了的表现是"早上没收到消息"，但无法区分"今天真没新闻"和"管线挂了"。加了一条心跳：抓取层无论如何都推一条运行状态，附带条目数和处理耗时。
- **摘要幻觉**：模型偶尔补全原文没有的细节。把温度降到 0.2，并要求摘要中每个事实都能在原文定位，抽查一周后基本干净。

## 可复用建议

- 状态存本地 SQLite 或 JSONL，别指望 agent 的会话记忆，跨次运行必须持久化。
- 抓取、过滤、摘要、推送各自独立，出问题才能二分定位。
- 给 LLM 层设硬上限：单次最多 N 条、最多 M token，超了就截断保留最高分条目。
- 习惯 MCP 的话，可以把抓取层封装成一个 MCP tool 供其他 agent 复用，但调度仍留在 cron，别让模型自己决定"什么时候拉"。
- 模板即契约：输出格式固定后，推送和归档的下游逻辑都变简单。

## 总结

这条管线跑了两个多月，每天早上一条 digest，阅读时间从 40 分钟压到 10 分钟以内，月均 LLM 花费在个位数人民币量级。核心思路不新鲜：确定性的交给代码，模糊判断交给模型，中间用一层廉价规则控制成本。想动手的话，从一个源、一个定时任务、一个固定模板开始，先跑通再扩。
