## 背景

OpenClaw 的 agent 开箱默认是一套通用助手人格：礼貌、面面俱到、什么都敢聊。跑玩具项目没问题，但当你把它挂到 Telegram 当私人助理、接 MCP 工具执行 shell 命令、或放进团队共享 workspace 做自动化时，通用人格就成了风险源。OpenClaw 在工作区约定里留了 `SOUL.md`——每次会话启动自动注入上下文的人格定义文件，这是给 agent 立规矩的正确入口。

## 三个典型症状

1. **人格漂移**：会话开头是简洁工程腔，二十轮之后漂回百科式长篇回答。
2. **越界执行**：让它清理下载目录，它顺手"优化"了相邻的配置文件——因为没人告诉它不能。
3. **渠道不一致**：同一个 workspace，Discord 里表现正常，切到 Telegram 像换了个人，缺少统一的人格锚点。

## 做法：四步写一个可维护的 SOUL.md

**1. 建文件。** workspace 根目录创建 `SOUL.md`，控制在一屏以内（40 行左右），它每次会话都占上下文。

**2. 只写四块内容**，参考骨架：

```markdown
# 身份
工程助理，说话直接，先结论后细节。

# 语气
- 中文回复，报错与代码保留英文原文
- 不确定就说不确定，不编造

# 边界（可判定，不是愿望）
- 不删除任何未被明确点名的文件
- 发消息、消费、改线上配置：先列出操作，等确认
- 连续两次尝试失败即停止，报告已试路径

# 升级
触及上述边界时，宁可多问一句。
```

**3. 职责切分。** SOUL.md 只管"我是谁、我不做什么"；操作流程写进 AGENTS.md，事实记忆写进 MEMORY.md。三者混写是最常见的结构问题。

**4. 版本化 + 回归。** SOUL.md 进 git。每次翻车后把触发场景提炼成一条规则，改完用固定几句指令做回归测试——比如让它执行一次带风险的操作，看是否触发确认。

## 踩坑点

- **愿望式规则无效。** "要有礼貌、要负责任"无法执行。要写成可判定条件："用户情绪激动时不回应情绪，直接回到任务"。
- **别把它当安全边界。** SOUL.md 是 prompt 级约束，注入攻击可以绕过它。删库、付款、对外发消息这类高危操作，真正的闸门必须在工具/MCP 权限层：白名单、只读挂载、二次确认。人格文件是第一道减速带，不是保险丝。
- **越长越稀释。** 有人写成三千字散文，结果 agent 一条都记不住。规则密度比数量重要。
- **渠道差异别塞进 SOUL.md。** 多渠道不统一的正确解法是拆 profile / workspace，而不是在人格文件里堆 if-else。

## 可复用建议

- 每条边界规则跟一个触发场景。模型对"什么情况下做什么"的遵循度，远高于抽象原则。
- 团队协作时把 SOUL.md 当代码 review：改人格要有 diff、要有理由。
- 每月 review 一次，把 MEMORY.md 里的冲突对话迁移成规则——SOUL.md 应该是活的。

## 总结

SOUL.md 是 OpenClaw 里成本最低、杠杆最高的配置之一：几十行文字换来的语气一致性和行为边界，比你调十次温度参数都有效。但记住它的层级——它是人格层和减速带，不是安全层。人格归 SOUL.md，流程归 AGENTS.md，权限归工具层，三层各就各位，agent 才算真正可托付。
