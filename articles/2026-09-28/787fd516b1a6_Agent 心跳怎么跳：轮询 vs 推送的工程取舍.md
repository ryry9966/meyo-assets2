## 背景

在 OpenClaw 的自动化场景里，Agent 大量时间处于"待命"状态：定时摘要、监控收件箱、刷新凭证、检查外部任务进度。让一个 LLM 驱动的 Agent "活着"，绕不开心跳（heartbeat）设计——它决定了 Agent 何时醒来、醒来后做什么、以及每次醒来花多少钱。

常见两条路线：**轮询**（按固定间隔自检）和**推送**（外部事件主动触发）。

## 问题

两条路线各有硬伤：

- **轮询的代价是空转**。间隔 5 分钟，一天 288 次心跳，绝大多数醒来后发现无事可做。如果每次心跳都走一遍 LLM，token 成本和限流压力会被无效唤醒吃掉；事件延迟则被间隔上限锁死。
- **推送的代价是基础设施**。要暴露 webhook 端点、做签名校验、处理重试与去重，还要面对"事件丢了没人补偿"的问题。排障时，"没收到"和"没发生"很难区分。

多数团队最终不是二选一，而是混合。难点在于边界画在哪。

## 我们的方案

按**事件价值**分桶，而不是按技术偏好：

1. **低价值、可容忍延迟的任务走轮询**：日报、缓存预热、Token 刷新。全局心跳 15 分钟，叠加 ±10% 随机抖动（jitter），避免多实例同时唤醒触发限流。
2. **心跳本身要便宜**。每次唤醒先执行零成本的本地检查（读状态文件、查本地队列长度），无事则直接退出，不进 LLM。模型只在"有活干"时被调用。
3. **高价值、低延迟的事件走推送**：用户消息、告警通知。webhook + HMAC 签名校验 + 幂等键（事件 ID 去重）。
4. **推送失败有兜底**：所有推送事件同时落一条待处理记录，下个心跳周期扫描补处理。推送丢了，轮询能捡回来。
5. **故障退避**：连续 N 次心跳失败后指数退避（15min → 1h → 4h），避免上游宕机时反复撞墙。

## 踩坑点

- **空转心跳全量调 LLM**。早期版本每次心跳都让模型"看看有什么要做的"，一个月 token 账单翻倍。改成前置本地检查后才压下来。
- **没加 jitter**。三台实例共用同一 cron 表达式，整点同时唤醒，直接撞上供应商限流。
- **推送没做幂等**。webhook 重试导致同一条消息被处理三次，用户收到重复回复。
- **心跳掩盖故障**。日志显示"每 15 分钟都在跑"，实际连续失败两天没人发现。心跳的"运行"和"成功"必须分开记录、分开告警。
- **时区与 DST**。夏令时切换当天定时任务错位一小时，日报凌晨四点发出。

## 可复用建议

- 默认轮询，延迟敏感再加推送。轮询几乎零基础设施，是安全的基线。
- 心跳决策要便宜：先判断"要不要思考"，再决定"是否调用模型"。
- 间隔按任务配置，不要全局一刀切。
- 推送处理器必须幂等，事件 ID 去重做在入口处。
- 记录每次心跳的决策（跳过 / 触发 / 失败），这是成本审计和排障的第一手数据。

## 总结

轮询换来简单可靠，推送换来低延迟和低成本，但两者都不免费。实践中更稳的结构是：轮询做兜底和廉价任务，推送做高价值低延迟事件，推送丢失由轮询补偿。心跳设计的核心不是"多久醒一次"，而是让每次醒来的判断成本尽可能接近零。
