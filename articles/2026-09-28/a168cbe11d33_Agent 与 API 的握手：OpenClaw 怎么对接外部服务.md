## 背景

OpenClaw 这类常驻 Agent 网关的价值，很大程度上取决于它能调动多少外部服务：查工单、发通知、跑 CI、读写内部系统。但 Agent 调 API 和后端服务之间互调不一样——调用方是一个会"理解"接口描述、也会犯错的模型。握手协议没设计好，轻则调用失败，重则重复下单、密钥泄漏。

## 问题

实践中故障集中在三类：

1. **工具太泛**：把一整套 OpenAPI 文档丢给模型，它选错接口、传错参数；
2. **返回体过大**：一个 50KB 的 JSON 灌进上下文，既撑爆 token 又淹没关键信息；
3. **缺约束**：没有超时和幂等设计，Agent 卡死，或者对写操作反复重试。

## 做法

建议把对接拆成五步，每步只解决一个问题：

**1. 包最小工具，不裸暴露 API。** 从业务里挑出真正需要的 3~5 个 endpoint，各写成一个 skill/工具，参数收窄为枚举或带校验的字段。工具描述里写清"什么场景该用我"，比罗列参数更重要。

**2. 鉴权出上下文。** API key 放环境变量或配置层，工具运行时注入，不进对话历史。对话里只保留"已授权"这类状态描述。

**3. 裁剪返回体。** 在工具层做字段过滤、分页截断和摘要，只返回模型做决策所需的部分。宁可让信息不够、模型追问，也别让它读原始大 JSON。

**4. 超时、重试、幂等三件套。** HTTP 客户端设 10~30 秒超时；幂等的查询可以自动重试；写操作必须带客户端生成的幂等键，并在描述里声明"本操作不可撤销"。

**5. 有现成 MCP 就别自研。** GitHub、数据库、浏览器这类常见 MCP server 已经把鉴权和分页处理好了，OpenClaw 挂配置即可。自己写工具留给内部系统和私有 API。

一个工具定义大致长这样（示意，字段以你自己的注册格式为准）：

```json
{
  "name": "query_order",
  "description": "按订单号查询状态；只读；超时 15s；返回字段已裁剪",
  "params": { "order_id": "string, 必填" },
  "idempotent": true
}
```

## 踩坑点

- **描述语气失衡**：写得太像宣传文案，模型会过度调用；写得太冷像接口文档，模型又不敢调。中性、具体、附一个正反例最好。
- **错误透传**：上游 500 的 HTML 页面直接回给模型，它会瞎猜重试。应在工具层翻译成"参数 X 缺失 / 服务暂不可用，建议放弃或换参数"。
- **Webhook 误判**：对方回 200 只代表收到，不代表成功，要校验签名并异步查终态。
- **日志泄密**：调试日志会原样记录工具入参，密钥字段记得在工具层脱敏后再落盘。

## 可复用建议

- 新接一个服务，先用 curl 手工走通"鉴权 → 请求 → 分页 → 错误码"四件事，再包装成工具；
- 每个写操作工具配一个只读的"影子工具"，让模型先查后写；
- 灰度上线：先只在一个测试会话挂新工具，观察一周调用日志再放开；
- 工具总数超过 15 个左右，按业务域分组或动态加载，否则模型的选择准确率会明显下滑。

## 总结

Agent 对接外部服务的本质，是把人的工程判断编译进工具层：鉴权、裁剪、幂等、脱敏都在模型看不见的地方完成，模型只面对一小撮语义清晰的工具。所谓握手，握住的是约束，而不是自由。
