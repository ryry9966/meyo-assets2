## 背景

OpenClaw 的 Agent 能力不止于内置工具和 MCP。Skills 是一套「用 Markdown 描述能力」的机制：每个技能是一个文件夹，核心是一个 `SKILL.md`——frontmatter 写 `name` 和 `description`，正文写操作步骤。关键设计在于：**系统提示词里只注入技能名和描述，正文只有在模型判断需要时才被读进上下文**。这是一个懒加载结构，而不是全量注入。

## 问题

最常见的反模式是把所有操作手册塞进系统提示词。技能一多，token 开销线性上涨，模型在超长指令里选错路径的概率也随之变高。我们真正想要的是「平时轻装上阵，用时按需取货」：上下文保持精简，知识在触发时才进场。

## 做法

1. **定位目录**：workspace 下的 `skills/`（项目级）或 `~/.openclaw/skills/`（全局），也可以通过配置指向一个 git 仓库，方便团队共享。
2. **建 SKILL.md**，结构如下：

```markdown
---
name: web-research
description: 当需要查证网络资料、抓取页面并提炼要点时使用。触发词：搜索、查证、抓取网页。
---

# Web Research
1. 先用 web_fetch 拉取页面，失败再换备用源。
2. 提炼要点时保留原始 URL，禁止编造引用。
3. 页面要求登录时，直接告知用户而不是猜测内容。
```

3. **description 写成触发条件句**：什么时候用、输入是什么、产出是什么。它是模型决定是否加载的唯一依据，值得反复打磨。
4. **正文写程序性步骤**：命令、参数、边界条件（明确不要做什么），不要写背景故事和客套话。
5. 可在 frontmatter 声明依赖（需要的 CLI、环境变量、OS），排障时省很多事。
6. **验证懒加载生效**：抛一个相关问题，翻日志确认 `SKILL.md` 是被按需读取的，而不是常驻上下文；再抛一个不相关的问题，确认没有误触发。

## 踩坑点

- **description 太泛**：写成「处理各种任务」的技能，结果是永不触发或乱触发。
- **正文过长**：几百行的技能让懒加载失去意义，建议单技能控制在 100–200 行。
- **多技能描述重叠**：会竞争触发。边界必须互斥，必要时在 description 里写清「不适用于 X 场景」。
- **依赖缺失**：技能被加载后第一步就报错。在正文开头写一条检测命令，先验环境再执行。
- **密钥泄露**：SKILL.md 会进仓库、会被读进上下文，任何凭据都不要写。
- **和 MCP 职责混淆**：Skills 是「知识/流程」，MCP 是「工具接口」。已有 MCP 工具的操作，别在 skill 里重复描述接口，skill 只写编排顺序和注意事项。

## 可复用建议

- **一个技能 = 一个完整工作流**，粒度到「能独立完成一件事」为止，不拆太碎也不贪大。
- description 模板：「当____时使用，输入是____，产出是____」。
- 技能目录纳入 git，团队共享时重点 review description，正文反而次要。
- 用刁钻 prompt 做回归测试：不相关问题不应触发，边界问题应明确拒绝。
- 分工原则：高频、结构化的调用交给原生工具/MCP；低频、步骤细节多的流程才值得做成 skill。

## 总结

Skills 的价值不在「能力更多」，而在上下文经济学：提示词保持精简，知识按需进场。把 description 当触发器写，把正文当 SOP 写，技能库才能长期可维护。建议从一个你每周手工重复两次以上的流程开始，把它落成第一个技能。
