## 背景

我是社区的一名普通成员，平时帮着整理每周的讨论串。人工做摘要重复劳动太多，就决定用 OpenClaw 搭一个发帖机器人：定时抓取论坛和 GitHub 的新动态，过滤、摘要、生成周报草稿，审核后发到社区板块。目标不是全自动"水帖"，而是把人的时间从搬运里解放出来。

## 最初的问题

第一版很天真：cron 触发 → 把所有源塞进上下文 → 让模型写帖 → 直接调 API 发布。跑了三天就出事：同一主题重复发帖、摘要里出现编造的链接、一天发了五篇被论坛反垃圾机制拦进待审。复盘下来，问题不在模型，在架构。

## 重构后的架构

现在拆成五层，各自可独立测试：

1. **采集层**：两个 MCP server，一个拉论坛 API，一个拉 GitHub Releases 和 RSS。只负责取数，输出结构化 JSON，不做任何判断。
2. **过滤层**：小模型加规则，按关键词和热度打分，对源条目去重后只留 Top N。这一步省掉了 80% 的 token。
3. **生成层**：主 Agent 只拿过滤后的条目写稿，链接以变量注入，禁止模型自己生成 URL。
4. **审核层**：草稿推送到我的私聊会话，回复"发"或改完再发，这是唯一的人工关卡。
5. **发布层**：独立的发帖工具持有 API key，带每日配额、冷却时间和幂等键。

所有状态落 SQLite：源条目指纹、草稿、审批记录、发帖日志。Agent 本身无状态，随时可以重跑。

## 踩坑实录

- **去重做错了对象。** 一开始对生成的文本做相似度去重，没用——同一批源换个措辞照样重发。改成对源条目做 URL + 标题指纹，问题消失。
- **模型会"好心"补链接。** 摘要里出现了一条根本不存在的帖子链接。修复方式：提示词明确禁止生成 URL，所有链接由代码从 API 结果注入模板。
- **重试导致双发。** 网络超时后重试，帖子发了两遍。给发布层加幂等键（源指纹哈希），发布前先查库，命中即跳过。
- **时区坑。** cron 按容器默认 UTC 跑，周报变成周六早上发出。显式声明时区后恢复正常，这类问题最好在第一周就排查。
- **自动发帖的头两天最好关掉。** 审核层上线前，机器人发过一篇语气很"营销号"的帖子，还被顶到了首页。人工审核保留至今：每天一分钟成本，换风险归零，值。

## 可复用的建议

- **生成和发布必须分离**，发帖凭证永远不要进入生成链路，只放在发布工具里。
- **先 dry-run**：所有"发布"动作先落日志空跑一周，人工抽查没问题再放闸。
- **过滤用便宜模型，写作用好模型**，成本能差一个量级，质量几乎不受影响。
- **幂等键 + 外置状态**是所有定时类 Agent 的底线，别相信"就跑一次"。
- **MCP server 保持"傻"**：只取数不决策，决策留给 Agent 和人。

## 总结

这个机器人现在每周稳定产出两篇帖子，人工介入只剩点一次"发"。最大的体会是：Agent 项目里，模型能力往往不是瓶颈，发布权限、状态管理和幂等设计才是。把这三件事做扎实，自动化才敢真的开闸。欢迎在社区帖下交流各自的审核策略。
