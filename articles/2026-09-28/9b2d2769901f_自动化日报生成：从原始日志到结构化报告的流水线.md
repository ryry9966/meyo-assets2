## 背景

我们团队维护着十几个定时任务、若干常驻服务和几个 Agent 日常跑的自动化流程。日志分散在服务器文件、CI 输出和 MCP 工具的执行记录里。之前日报靠人肉：每天早上花 20 分钟翻日志、复制粘贴、拼一段总结，信息经常漏，格式也每天不一样。

这篇帖记录我们把这个过程做成流水线的实践。思路不绑定具体框架，落地用的是 OpenClaw 的定时 Agent 任务加几个自写的 MCP 工具。

## 问题

拆开看，日报生成有三个核心问题：

1. **格式异构**。日志有纯文本、JSON、表格输出，统一口径是前提。
2. **噪音大**。一天几万行日志，能进日报的有效信息可能就几十条，直接塞给模型既贵又不稳定。
3. **数字必须准**。失败次数、耗时、成功率是决策依据，模型编一个数比不报还糟。

## 做法

流水线分四段，关键设计是**确定性聚合与叙述生成分离**：

1. **采集**：cron 触发的采集脚本，把各源日志（文件、CI API、任务执行记录）拉平成中间格式，落成 JSONL。schema 固定：`{ts, source, level, event, duration_ms, ok, extras}`。
2. **聚合**：纯代码（不用模型）按事件聚合，算出次数、成功率、p95 耗时、Top 错误。每个数据点记录来源日志行号，方便回查。
3. **叙述生成**：把聚合结果（不是原始日志）交给定时运行的 Agent，prompt 只要求它做两件事：解释异常、列出需人工跟进的条目。输出走严格 JSON，解析失败自动重试一次，仍失败就降级为“仅数据版”日报。
4. **渲染推送**：套固定 Markdown 模板渲染，推送群 webhook，同时归档一份带日期的文件。

## 踩坑点

- **模型写数字必翻车**。第一版让模型直接读日志写总结，成功率是编的。改成模型只写叙述、数字全部来自聚合层之后才稳。
- **日期边界**。跨零点的任务归属混乱。最后统一用 UTC 记录、以“昨天 00:00 UTC”为切分点，脚本里写死，不让 Agent 自行判断时间范围。
- **重跑去重**。采集脚本失败重跑会把同一段日志算两遍。加了游标（记录上次处理偏移量）和 `(source, ts, event)` 幂等键。
- **流水线自己会死**。最坑的一次：采集脚本静默挂了三天，日报“正常”地重复旧数据。补了新鲜度检查——日报头部带数据截止时间，超过阈值就在标题标 `[数据过期]`。
- **上下文超载**。别把原始日志直接喂模型，先聚合。上下文压力小了，输出质量反而更稳。

## 可复用建议

- 中间 schema 就是契约，先定 schema 再写其他部分；改 schema 要留兼容期。
- 报告模板进版本管理，格式变更可追溯。
- 原始 JSONL 保留两周，报告有争议时能回放验证。
- 任何“模型参与”的环节都要有确定性降级路径。

## 总结

这套东西代码量不大：采集加聚合不到 300 行，Agent 侧就是一个定时任务加一段严格 prompt。真正的收益不在省下每天 20 分钟，而在于日报变成可信的——数字可回查、格式稳定、流水线自己也有监控。自动化报告这件事，工程量的大头永远在数据侧，而不是生成侧。
