## 背景

我们团队以前的日报流程是：每天早上几个人各自翻一遍昨天的服务日志、告警群和任务系统，手动拼一份 Markdown。问题很明显——耗时、口径不一、经常漏掉凌晨的异常。后来我把这件事交给 OpenClaw 做成一条自动化流水线，跑了两个多月，输出稳定。这篇把设计和踩过的坑整理一下，方便直接复用。

## 问题拆解

日报本质上是三类信息：

1. **量化数据**：请求数、错误率、任务完成量，来自日志和数据库；
2. **事件信息**：告警、发布、异常，散落在告警系统和聊天记录里；
3. **汇总判断**：哪些值得写进日报、趋势如何。

前两类是确定性数据，第三类才需要模型参与。最初的失败尝试是直接把原始日志丢给 agent：token 爆炸、摘要飘忽，关键数字还会算错。

## 流水线设计

核心原则一句话：**确定性的交给脚本，模糊的交给模型。**

1. **采集层**：定时任务触发 OpenClaw 的 skill，拉取昨日日志切片，按服务分文件落盘。注意按业务时区切 24 小时窗口，不是 UTC 自然日。
2. **预聚合**：用 jq/SQL 做计数、去重、按错误码分组，产出一份紧凑的 JSON 摘要（几十 KB 以内）。原始日志只留引用路径，不进 prompt。
3. **模型层**：agent 读预聚合结果加事件列表，按固定 JSON schema 输出 `{highlights, metrics, incidents, risks}`。MCP 工具只开放只读查询，防止 agent 一兴奋去写数据。
4. **校验层**：schema 校验失败就带着错误信息重试，最多两次；数字字段与预聚合结果交叉核对，不一致直接报错，不静默通过。
5. **交付层**：渲染成 Markdown 模板推送，附原始数据快照链接，便于追溯。

## 踩坑点

- **时区**：cron 在服务器上是 UTC，第一次跑出来的是"前天 8 点到昨天 8 点"，日报数字全错。切窗逻辑必须显式指定时区。
- **幂等**：任务重跑会重复推送。现在用「日期 + 版本号」做幂等键，同 key 只投递一次。
- **schema 漂移**：模型偶尔自作主张加字段或改字段名，靠校验层兜底；重试时把校验错误原文塞回 prompt，基本一次就能修好。
- **数字幻觉**：早期让模型自己算环比，错两次之后改为脚本算好比值，模型只做定性描述。

## 可复用建议

- 先写输出 schema 再写 prompt，把日报当 API 设计，不当前文章写；
- 给模型的数据宁少勿杂，预聚合做得越狠，输出越稳；
- 每条结论要能回溯到数据来源，报告里带引用路径；
- 保留每次运行的原始快照，出了问题可以 diff。

## 总结

这条流水线的价值不在"省了十分钟"，而在口径统一和可追溯。分工上把握一条：脚本能算的绝不给模型，模型只负责它擅长的归纳和措辞。目前唯一没自动化的，是"什么值得写进日报"这个判断标准本身——仍然由人来定，只是从手工整理变成了审核确认。这个边界目前看是合理的。
