## 背景

我们的服务散在好几台机器上：Nginx 访问日志、应用日志、CI 记录、git 提交历史。每天下班前写日报，基本是登录各处 grep 一遍再拼一段话，纯重复劳动。OpenClaw 本身支持定时任务和自定义技能，很自然地想到把这件事交给 agent——但直接“把日志扔给模型总结”跑过一次就放弃了：上下文爆掉、数字编造、格式漂移，报告看着顺眼但没法用。

最后落地的是一条“确定性取数 + 模型写文”的流水线，跑了一个多月，稳定。

## 问题

核心矛盾在于：日志是海量非结构化文本，而日报需要的是准确数字和固定结构。LLM 擅长后者、不擅长前者。所以关键不是写更好的 prompt，而是把“算数”和“说话”拆开——数字必须来自脚本，模型只负责组织语言。

## 做法

流水线分三层：

**1. 采集层（纯脚本，无模型参与）**

写一个 `collect_daily.sh`，按日期窗口抽取指标：

- 各服务 error 数、5xx 比例
- Top 10 访问路径与耗时 P95
- 当日部署事件（git tag / CI 记录）
- 磁盘与内存峰值

输出统一为固定 schema 的 JSON，例如 `{ "date": "...", "errors": {...}, "deploys": [...] }`。schema 一旦定下来就不要轻易动，它是后面所有环节的契约。

**2. 调度层**

系统 cron 每天固定时间触发，调用 OpenClaw 的 CLI 入口并把日期作为参数传入。agent 侧注册一个技能（或 MCP 工具）`fetch_daily_stats(date)`，内部就是读采集层产出的 JSON 文件。

**3. 生成层**

系统提示词里约定报告模板：概览 / 异常 / 变更 / 待办四段。明确要求：所有数字必须原样引用工具返回值，禁止推算和四舍五入；数据缺失时写“数据缺失”而不是编造。产出 markdown 归档到 git 仓库，并通过插件推送到群通道。

## 踩坑点

- **时区**：日志时间戳是 UTC，cron 按本地时间跑，跨天边界会漏一小时数据。采集脚本统一用 UTC 计算窗口，展示时再转本地。
- **数字漂移**：早期模型会把 3.2% 写成“约 3%”。后处理加了一步校验：正则抽出报告里的数字逐个比对 JSON，不一致就重试。
- **日志轮转**：凌晨采集正好撞上 logrotate 切文件，漏数据。改为通过 journalctl / 时间窗口查询，而不是直接读文件。
- **静默失败**：采集脚本挂了，agent 却照样“编”了一份报告。现在脚本非零退出码会中断流水线——宁可当天没有日报，也不发假日报。

## 可复用建议

1. **取数与写文分离**是这类任务最值钱的原则。凡是要求数字准确的场景，都不要让模型接触原始数据。
2. 固定 schema 的 JSON 作为中间层，采集脚本可以独立测试、独立重跑。
3. 报告模板进版本库，和提示词一起 review。
4. 流水线要幂等：同一天重跑覆盖旧报告，而不是追加。
5. 自检成本低、收益高：让 agent 生成后对照 JSON 核数，一次不一致就重试。

## 总结

这条流水线没有用到任何复杂技术，本质是把 agent 放在正确的位置：不做它不擅长的计算，只做它擅长的归纳与表达。日报只是第一个应用，“脚本取数 → JSON 契约 → 模型写文 → 校验回推”这套结构，周报、值班交接、告警摘要都能直接套。如果你也在用 OpenClaw 做自动化，建议先从这条最薄的流水线跑通，再逐步扩展数据源。
