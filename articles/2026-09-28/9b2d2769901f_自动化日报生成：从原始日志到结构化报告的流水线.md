## 背景

每天的日报，本质上是把散落各处的"发生了什么"压缩成一页人能读的东西：服务日志、告警、Git 提交、部署记录。数据都在，但手动汇总费时且容易漏。我最早的做法是把当天日志整段丢给 Agent 让它"总结一下"，前两周看起来还行，第三周开始出现数字编造、重点漂移。后来把它拆成一条真正的流水线，稳定性才上来。

## 问题

"日志进、日报出"有三个硬伤：

1. **噪音比信号大**。一天几万行日志里，真正需要人关注的可能只有十几条，全量塞给模型又贵又不可靠。
2. **数字不可信**。模型复述日志时会把"接近"说成"精确"，错误次数、耗时这类指标必须由脚本算出来。
3. **流水线本身也会挂**。日报没生成比日报写得差严重得多，必须有兜底告警。

## 做法

整条链路分四层，目录结构固定：

```
daily-report/
  raw/       # 当日原始日志快照，只增不改
  cleaned/   # 清洗后的结构化 JSON
  reports/   # 最终 Markdown 报告归档
```

**第一步：采集**。定时任务在固定时间把各来源数据拉进 `raw/`：按天切片的服务日志、git log 导出、告警 CSV。关键是时间窗口切干净，带时区。

**第二步：清洗**。全部用确定性脚本，不经过模型。做的事很朴素：按错误码聚类去重、过滤心跳噪音、提取指标（错误总数、Top 5 异常、部署次数、PR 合并数），输出固定 schema 的 JSON。schema 稳定是整条流水线的地基。

```json
{
  "date": "2025-06-12",
  "window": { "tz": "Asia/Shanghai" },
  "metrics": { "error_total": 47, "deploys": 3 },
  "top_errors": [ { "code": "TIMEOUT_DB", "count": 31, "sample": "..." } ]
}
```

**第三步：摘要**。这里才是 Agent 的位置。给它的是 `cleaned/` 里的 JSON 而非原始日志，任务限定为"把结构化数据组织成叙述"：今日概况、异常分析、明日关注点。模板写死，模型只填内容不发明结构。

**第四步：输出与归档**。渲染成 Markdown 推到群里，同时在 `reports/` 留档，文件名带日期，方便事后审计"那天到底发生了什么"。

## 踩坑点

- **时区与时间窗口**。服务器是 UTC，人是东八区，"昨天"的定义不一致，漏过早上八点前的日志。窗口计算收口到一个函数里，别散在各采集脚本中。
- **同类错误刷屏**。一次重试风暴一天能产生两万条相同堆栈，先聚类取 Top N 和一条样本，再交给模型。
- **数字幻觉**。让模型只引用 JSON 字段，指标计算永远在脚本侧。有一次模型把 47 写成 74，之后就没让它再接触过原始计数。
- **静默失败**。定时任务挂了没人发现。加了反向检测：每天固定时间检查 `reports/` 是否有今天的文件，没有就发告警。

## 可复用建议

- 一句话原则：**数字脚本算，故事模型讲**。LLM 负责叙述和组织，不负责事实采集与计算。
- `raw/cleaned/reports` 三级目录几乎可以套到任何日报场景，包括个人工作日志。
- schema 先行：先定输出 JSON 字段，再写采集清洗，最后才接模型。
- 归档 + 反向告警，是流水线能长期跑下去的两个保险。

## 总结

日报自动化的价值不在省十分钟，而在于把"发生了什么"的判断从人肉扫描变成可靠的数据管道加一次受限的模型调用。四层各司其职，模型只待在它该待的那一层。整套东西用 OpenClaw 的定时任务加两个 MCP 工具（读文件、发消息）就能搭起来，一个下午的工作量，换来的稳定性远超预期。
