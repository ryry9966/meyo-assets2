## 背景

订阅源越攒越多：技术博客、GitHub Release、几份周刊、arXiv 目录。RSS 阅读器常年挂着四位数未读，真正点开的不到一成。后来我换了个思路：把"读"降级成"筛"——让 OpenClaw 定时拉订阅源，做抽取、摘要、打分，每天推一份日报。跑了一个多月，日均 token 消耗可控，未读焦虑基本消失。

## 问题

手动粘链接让模型总结当然可行，但不自动化就撑不下去：

1. 源多且杂，有的 feed 只给摘要不给全文；
2. 全量喂 LLM 太贵，也没必要；
3. 同一条内容会从多个源重复出现；
4. 摘要必须可溯源，否则读者（就是我自己）不敢信。

## 做法

管线拆成四段，中间结果落库（SQLite），每段可独立重跑：

1. **采集**：订阅源集中在一个 YAML 配置里，按"必读 / 可扫 / 存档"分三档。OpenClaw 定时任务每 6 小时遍历拉取，带 ETag/Last-Modified，304 直接跳过。已见条目按 GUID + 归一化链接写库去重。
2. **抽取**：feed 只有 summary 的条目，抓原文页面抽正文；抓不到就降级用 feed 摘要，并打上 `degraded` 标记，方便后续排查。
3. **摘要与打分**：不逐条调模型。按类目把 10-20 条的标题 + 首段合并成一次请求，要求输出结构化 JSON：一句话摘要、要点、兴趣相关分。低分条目只留标题进"其余更新"清单。提示词强制"只使用给定内容，不补充外部信息"。
4. **投递**：每天早上汇总成 Markdown 日报推到频道，原文链接永远跟着摘要走。

## 踩坑点

- **feed 截断**：不少博客 feed 只输出前几段，抽取环节不能省；注意合理的 UA 和限速，别并发轰同一个站。
- **去重不彻底**：同一篇文章在不同 feed 里 GUID 不同，链接还带 utm 参数。链接去白噪声 + 标题相似度兜底，才压得下来。
- **结构化输出偶尔崩**：模型有时在 JSON 后多补一段说明。解析失败重试一次，再失败就原文透传，别让管线卡死。
- **幻觉**：批式摘要最容易出现"合理但不存在"的细节。只基于给定内容 + 摘要旁带原文链接，是两条底线。
- **发布时间不可信**：很多源的 pubDate 是错的，排序一律以"首次入库时间"为准。

## 可复用建议

- 各阶段解耦、中间落库，换模型或改提示词时直接重放摘要段，不用重新采集。
- 摘要的定位是"过滤器"不是"替代品"，链接必须保留。
- 起步 10-20 个源就够，先跑通再扩；token 用量单独记账，超预期先砍"可扫"档。
- 走 MCP 路线的话，把"抓 feed""抽正文"封装成两个独立 tool，摘要逻辑留在 agent 侧，每段都能单独测试。

## 总结

这套管线没有高深的东西：定时任务 + 去重 + 抽取 + 批式摘要 + 投递，全是朴素工程活。价值在于把"刷信息"变成"审信息"——每天五分钟过一遍日报，点开的都是真想读的。OpenClaw 在这里更多扮演调度与粘合角色，各段工具化之后可独立替换。建议从自己真实的订阅列表出发搭一版小的，跑两周再谈优化。
