## 背景

我们用 Agent 做自动化时，最常见的模式是主 Agent 一条线打到底：自己查资料、自己跑命令、自己写结果。任务一多，两个问题立刻暴露：一是串行执行慢，十个独立小任务排队跑完要二十分钟；二是中间过程全部挤进主会话上下文，跑几个任务后主 Agent 开始"失忆"，忘了最初的目标。

OpenClaw 的 subagent 机制正好针对这件事：主 Agent 可以拉起多个子会话并行干活，各自返回结果。下面是我们把一批"扫描 + 汇总"类任务改成并行编排的实践记录。

## 问题

串行慢只是表象，真正的坑在上下文。改造前，主 Agent 逐个处理十几个数据源，每个子任务的中间输出（几百行日志、大段抓取内容）都留在主会话里，很快把窗口吃满，后续任务的判断质量明显下降。

## 做法

我们的编排流程分五步：

1. **先判断能不能拆。** 只并行"彼此独立、无共享可变状态、交付物明确"的任务。涉及同一个 git 工作区或同一份配置文件的，宁可串行。
2. **给每个 subagent 写任务简报。** 子会话不继承主会话的上下文，简报必须写清四件事：目标、范围与涉及路径、验收标准、返回格式。简报质量直接决定产出质量。
3. **控制并发数。** 同时最多 3~4 个，其余排队。并发一高，先是撞 API 限额，然后是账单。
4. **结果落盘，不在对话里搬。** 每个 subagent 把完整结果写进自己独立的目录，返回时只给一行状态加文件路径。主 Agent 汇总时按需读文件，而不是把长消息全量塞回上下文。
5. **设超时、查状态。** 每个 subagent 带超时参数；结束后主 Agent 核对状态，失败的任务单独串行重跑，方便定位。

## 踩坑点

- **共享资源竞争：** 两个 subagent 同时往同一个仓库提交，直接冲突。现在给每个子任务分配独立目录或分支，物理隔离。
- **简报太含糊：** 早期只写"帮我整理一下 X"，子 Agent 自由发挥，产出没法用。补上验收标准和返回格式后才稳定。
- **误以为子会话知道一切：** 项目约定、路径别名都得在简报里重新写一遍，别省这几行字。
- **静默失败：** 有个子 Agent 超时挂了，主 Agent 干等。加超时和状态检查后，失败能被立刻发现并兜底。
- **汇总阶段爆上下文：** 十个结果全量读回来，主会话照样被撑爆。汇总时只读摘要段，细节留在文件里按需取。

## 可复用建议

- 任务简报固定四要素：目标 / 范围与路径 / 验收标准 / 返回格式，直接做成模板复用。
- "落盘 + 短回报"是并行的关键：subagent 返回越短，主 Agent 越稳。
- 并发从 2~3 起步，跑顺再加。
- 判断口诀：IO 密集且互相独立就并行；共享状态就串行，或先做分区。
- 每个任务一个独立目录，日志、结果、临时文件都放里面，事后好排查。

## 总结

Subagent 并行不是"多开几个就快"的银弹。收益来自两件事：任务边界划得干净，以及结果以结构化方式回收。做到这两点，跑批类任务的耗时可压到串行的三分之一以下；做不到，并行只会更快地制造混乱。建议从小规模试起，把简报模板和落盘约定固化下来，再逐步放大。
