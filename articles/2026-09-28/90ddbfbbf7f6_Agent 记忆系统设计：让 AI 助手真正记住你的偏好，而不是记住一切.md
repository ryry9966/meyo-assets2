## 背景

用 Agent 做日常助手最烦的一点：每次新会话都要重新交代一遍偏好——缩进用 tabs、回复要短、部署默认走 staging。上下文窗口再大也装不下所有历史对话，而且全塞进去模型也未必听。记忆系统要解决的不是"存得下"，而是"该记的记对、该忘的忘掉、要用时捞得准"。

## 问题：三种常见失败模式

1. **全量入库**：对话原文全存向量库，检索回来一堆上周的闲聊，相关性稀烂。
2. **只增不改**：偏好变了（从 pip 换到 uv），旧记忆还在，模型随机抽一条用，行为漂移。
3. **不分层次**："今天三点开会"和"我永远不写递归 SQL"存成一个等级，重要记忆被琐事淹没。

## 做法：分层 + 结构化 + 混合检索

**1. 分三层存储**
- 工作记忆：当前会话上下文，不落盘；
- 情景记忆：具体事件事实，带时间戳；
- 画像记忆：稳定偏好与规则，这是核心资产。

**2. 写入走双通道**
显式指令（"记住我喜欢 X"）直接写画像层；隐式抽取在会话结束时跑一次，LLM 判断"能跨会话复用"才写入，单次事实只进情景层。

**3. 记忆要有 schema，别存裸文本**

```json
{
  "key": "code_style.indent",
  "value": "tabs",
  "confidence": 0.9,
  "source": "explicit",
  "updated_at": "2025-06-01",
  "superseded_by": null
}
```

`source` 区分显式/推断，`superseded_by` 做软删除链，避免旧偏好复活。

**4. 检索用混合策略**
向量召回 + key 精确匹配 + 时间衰减排序，取 top 3~5 条注入 system prompt，设 300 token 预算上限。宁可少注入，不要灌满。

**5. 冲突仲裁**
新写入时查同 key 旧记录：显式声明或高置信度的覆盖旧的，被覆盖的打标记不删；低置信度冲突进待确认队列，下次会话顺口问用户一句。

## 踩坑点

- **embedding 单路检索不可靠**。偏好描述很短，向量相似度区分度差，key 精确匹配兜底后效果立竿见影。
- **隐式抽取太激进**。早期我把带"我"的句子全存了，两周后画像层 400+ 条垃圾；收紧抽取 prompt、加每日写入上限才稳住。
- **注入位置有讲究**。埋在长 system prompt 中间容易被忽略，靠近用户消息的位置权重更稳。
- **别忘了遗忘**。情景记忆 90 天衰减，画像记忆靠覆盖更新，没有衰减机制的记忆库只会越来越脏。

## 可复用建议

- MCP 工具开三个就够：`memory_read`（带 query）、`memory_write`（结构化）、`memory_delete`，别做十几个细碎接口。
- 显式指令永远优先于推断，这条规则写进系统 prompt。
- 留一个 dump/导出能力，出问题时能人工审计——你迟早会需要。

## 总结

记忆系统的本质不是数据库选型，而是一条"写入过滤 → 结构化存储 → 混合检索 → 冲突仲裁"的流水线。先做好显式记忆，隐式抽取灰度上线，定期人工清理，比一上来堆向量库靠谱得多。助手的记忆和人一样：克制，比贪婪好用。
