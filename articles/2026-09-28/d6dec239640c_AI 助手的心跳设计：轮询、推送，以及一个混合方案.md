## 背景

任何常驻的 AI 助手都会遇到同一个问题：用户不说话时，它该怎么"醒"？定时摘要、监控告警、文件变更检查、群消息兜底——这些主动行为都需要唤醒机制。OpenClaw 里的做法是 heartbeat：按固定间隔给模型发一个轻量 prompt，让它判断"现在有没有事要做"。但用久了会发现，心跳只是唤醒方式之一，另一个选项是推送（webhook / 事件注入），两者的取舍直接决定成本、延迟和可靠性。

## 问题

纯轮询的代价很好算：间隔 5 分钟，一天就是 288 次模型调用，其中绝大多数的结论是"无事可做"。间隔放大到 30 分钟能省钱，但提醒类任务最多迟到半小时。更隐蔽的问题是上下文污染——心跳和主对话共用 session 时，心跳记录会插在用户对话中间，既浪费 token，又容易产生"助手自言自语"的观感。

纯推送也不是银弹。Webhook 要求网关可达（家用网络还有 NAT 问题）、要做鉴权；事件到达时 agent 若在跑别的任务，直接注入会打断当前会话；重启期间到达的事件没有落盘，就永久丢了。

## 做法

我目前的方案是"推送写入、心跳消化"的混合结构，步骤如下：

1. **按延迟需求给事件分类**。提醒、监控告警走推送（要求分钟级触达）；日报、例行巡检走低频心跳（30–60 分钟足够）。
2. **所有事件统一写入持久化收件箱**（本地文件或 SQLite 都行），每条带时间戳和 TTL。Webhook 只负责投递，不直接驱动模型。
3. **心跳保留，但降级为兜底**：间隔拉长，且在心跳 prompt 之前做一次无 LLM 的预检——收件箱为空就跳过本次调用。这是省 token 最大的一刀。
4. **事件加去重与合并**：同一来源 60 秒内的事件 debounce 成一条，避免监控风暴。
5. **处理完成后 ack 并清理**，重启后从队列续读，保证 at-least-once。

推送解决延迟，心跳解决可靠性，两边都不必做到极致。

## 踩坑点

- **心跳复用主 session** 是我犯过最贵的错误，上下文被撑爆后主对话质量明显下降。心跳要么用独立 session，要么用即用即弃的临时上下文。
- **没有静默时段**，凌晨三点在家庭群里发了条例行汇报。active hours 必须在代码层硬编码，不能只靠 prompt 约束。
- **心跳 prompt 写得太开放**（"看看有没有什么要做"），模型会开始"发明任务"。要显式规定：无事可做时返回 no-op，不输出任何面向用户的消息。
- **Webhook 没加鉴权**，被扫描器撞上后触发了一堆垃圾任务。任何推送入口都要有 token 校验和频控。
- **只做推送不做队列**时，agent 忙碌期间的事件全部丢失——后来才真正理解"到达"和"被处理"是两件事。

## 可复用建议

- 先问延迟需求再选机制：秒级/分钟级 → 推送；小时级 → 心跳。不要用一个机制硬扛所有场景。
- 持久化收件箱是混合方案的地基，事件先落盘，再谈处理。
- 心跳开销要显式度量：记录每次 tick 是 skip 还是触发，一周后你对成本会有直观感受。
- MCP 工具天然适合"推送写入"这一侧——外部系统通过 MCP 工具往收件箱投事件，agent 侧逻辑完全不用改。

## 总结

轮询和推送不是二选一。轮询提供确定性的兜底，推送提供低延迟的触达，而连接两者的是一个可靠的持久化队列。把"事件何时到达"和"agent 何时醒来"解耦之后，heartbeat 就不再是一个让人焦虑成本的定时器，而是整个系统的节拍器。
