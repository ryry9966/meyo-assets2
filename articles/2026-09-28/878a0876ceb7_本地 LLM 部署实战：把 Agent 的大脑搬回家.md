## 背景：为什么把模型搬回家

OpenClaw 用久了，两个现实问题会浮出来：一是大量 token 花在摘要、分类、路由这类重复任务上，按量计费看着肉疼；二是消息记录、日程、设备状态这些数据，不想频繁出网。本地部署的目标不是替代云端大模型，而是把"高频、低难度、含隐私"的流量留在家里。

## 问题：Agent 场景和聊天场景不是一回事

不少人跑通一个 7B 聊天模型就以为本地化成了，一接 Agent 就翻车，原因有三：

1. **上下文长**：系统提示词 + 工具定义 + 多轮历史，轻松上万 token，KV cache 显存占用远超模型权重；
2. **工具调用质量敏感**：输出一段不合规范的 JSON，整条工具链就断，比聊天跑题严重得多；
3. **吞吐要求高**：一次 Agent 循环动辄十几次工具调用，15 tok/s 体感是卡死，30 tok/s 起步才像样。

## 做法：五步落地

**1. 盘点硬件，显存优先。** 8GB 显存跑 7B~8B 的 Q4 量化，够做摘要和路由；12~16GB 上 14B，常规工具调用稳定；24GB（3090/4090）跑 32B Q4，是当前 Agent 可用性的甜点位；Mac 统一内存是另一条路，32GB 可跑 30B 级 MoE。

**2. 选推理引擎。** 图省事用 Ollama，要控制感用 llama.cpp 的 llama-server，大显存可上 vLLM。三者都暴露 OpenAI 兼容端点，对上层透明。

**3. 选模型。** 不看跑分，只看两点：原生 function calling 支持、长上下文下的指令遵循。Qwen 系列工具调用比较稳，是我目前的默认。量化别低于 Q4_K_M，再低 JSON 质量会明显劣化。

**4. 接入 OpenClaw。** 把模型配置指向本地端点（如 `http://127.0.0.1:11434/v1`），上下文窗口按显存实际设置，温度压到 0.1~0.3——Agent 不需要创造性，需要确定性。

**5. 真实任务压测。** 挑 10~20 个你日常真实会跑的任务做成脚本，每次换模型跑一遍，记录成功率和 tokens/s。这是唯一可信的评测。

## 踩坑点

- **Ollama 默认上下文只有 2k~4k**，Agent 对话被静默截断，表现为模型"失忆"，必须显式调大；
- **上下文拉满等于显存爆炸**，128k 的 KV cache 能吃掉十几 GB，按任务需要设，别贪大；
- **温度没压下来**，工具调用偶发格式错误，容易误判成引擎 bug；
- **Windows 桌面和浏览器也占显存**，实测可用量比标称少 1~2GB，留足余量；
- 部分模型靠 prompt 模拟工具调用而非原生支持，引擎兼容性要逐个实测，别信文档想当然。

## 可复用建议

- 建**混合路由**：本地小模型做分类、摘要、意图识别，复杂任务回落云端，成本和隐私兼顾；
- **精简系统提示词**：本地模型对长 prompt 的遵循弱于云端旗舰，能砍一半就砍一半；
- **固定模型版本**（记录文件 hash），升级前先跑压测脚本，通过再切换；
- 显存决策一句话：8GB→8B、16GB→14B、24GB→32B，超配不如把余量留给上下文。

## 总结

本地 LLM 如今不是玩具：一张二手 3090 加 32B 模型，就能稳定支撑轻量 Agent 的日常工作流。方法论只有一句——**用你自己的真实任务测，而不是用别人的跑分选**。先把压测脚本建起来，选型和升级就从玄学变成了工程。
