## 背景

OpenClaw 天然是多模型形态：每个 agent 可以在配置里单独指定 model，provider 层既支持云端 API，也能把 Ollama、LM Studio 这类 OpenAI 兼容端点挂进来做本地推理。问题从来不是"能不能接"，而是接进来之后怎么分活。

## 问题

两种极端都不好：

- **全走云端**：个人助手的上下文里全是聊天记录、日程、文件路径，隐私全过第三方 API；高频轻任务持续烧 token；网络或配额一抖，整个 agent 停摆。
- **全走本地**：开源模型在多步工具调用上明显不稳，参数格式错一点，agent 循环就崩；长上下文下质量衰减也快。

所以真正要回答的是：哪些环节必须用强模型，哪些环节本地模型足够。

## 做法与步骤

1. **主 agent 固定用云端强模型。** OpenClaw 的主循环承担规划、工具编排和 fallback，这层对 tool call 格式正确率最敏感，不值得省这个钱。
2. **把高频轻任务拆成独立 agent**：会话摘要、消息打标、结构化提取这类单轮短任务，在各自 agent 配置里覆盖成本地模型。先跑一周看效果，再放量。
3. **配 fallback 链**：云端为主、本地兜底，保证断网或额度耗尽时至少还能响应。配完务必去日志里确认一次真实的降级路径。
4. **本地端调参**：Ollama 记得把 `num_ctx` 拉到模型实际支持的长度；选明确支持 function calling 的 instruct 模型，量化别贪高。

## 踩坑点

- **本地小模型做工具编排是最大的坑**，表现为 JSON 参数缺字段或编造工具名，别让本地模型承担任何编排职责。
- **Ollama 默认上下文很小**，超了是静默截断，外在表现是"模型突然变笨"而不是报错，非常难查。
- **fallback 静默降级**：key 写错、额度用尽，你以为在用云端，实际早就在本地跑了，只有翻日志才发现。降级事件至少要留痕或告警。
- **显存估算要留余量**：长上下文时 KV cache 增长很快，看着够的卡跑着跑着 OOM。

## 可复用建议

- 分流判据按**任务类型**定，不拍脑袋：涉及工具调用链、多步规划的 → 云端；单轮、输入输出都短、调用频繁的 → 本地。
- 固定一组 10~20 条的评测 prompt，换模型前后各跑一遍对比，别凭单次体感下结论。
- 拿捏不准的场景用**升级模式**：本地先答，置信度低或用户追问时升级到云端。
- 配置里模型名写到具体版本，避免 provider 静默替换默认模型。

## 总结

多模型路由的本质，是让"贵而强"和"便宜可控"各守各的环节。OpenClaw 的 per-agent model 加 fallback 机制刚好能支撑这套结构。建议从"主 agent 云端、杂活本地"这个最小配置跑两周，看日志和成本曲线，再决定要不要加更细的分流规则——对大多数个人部署来说，到这一步就够了。
