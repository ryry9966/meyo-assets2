# 背景

Agent 的价值在于能"动手"：查工单、拉数据、发通知。但在 OpenClaw 里，Agent 本身并不直接接触外部世界，中间隔着一层工具层——可能是 MCP server，也可能是插件注册的 skill。所谓"握手"，就是让外部 API 以 Agent 能稳定理解、安全调用的方式暴露出来。这一层做不好，上层再聪明的模型也是空中楼阁。

# 问题

最常见的失败模式不是"连不上"，而是"连上了但用不对"：

- 把 OpenAPI 文档整份丢给模型，Agent 猜参数、编字段；
- 工具返回几万字符的原始 JSON，上下文瞬间被吃光；
- 鉴权 token 写死在配置里，日志一打全部泄露；
- 遇到 429 或超时没有约定行为，Agent 陷入重试循环，或者干脆幻觉一个结果。

本质问题：API 的契约是为人写的，不是为 Agent 写的。握手失败，多半是契约没翻译好。

# 做法

我们实践的路径是"薄适配层"，分三步：

**1. 收敛工具面。** 不把整张 API 搬进来，只挑 Agent 真正会用的 3~5 个动作，各自包装成独立 tool。命名用动词短语（如 `query_order`、`create_ticket`），description 写清楚"什么时候该用我、什么时候不该用我"。

**2. 处理鉴权与参数。** 凭证走环境变量或密钥管理，适配层启动时注入；入参做一层 schema 校验，日期、枚举这类易错格式在适配层先归一化，不指望模型每次都输出标准格式。

**3. 重写返回与错误。** 返回值只保留 Agent 决策需要的字段，超阈值就截断加摘要；错误统一成 `{code, message, hint}` 结构，hint 是给模型的下一动作建议（"请缩小时间范围后重试"）。写操作统一加 dry-run 开关和幂等键。

MCP 的优势在这里体现得很直接：tool schema、鉴权、错误语义都收敛在 server 一侧，Agent 侧零改动就能替换底层 API。

# 踩坑点

- **description 太短**：两个相似工具分不清边界，Agent 调用错乱。写清使用边界比罗列参数更重要。
- **原始响应直通**：一个列表接口返回 200 条记录，直接撑爆上下文。适配层必须做分页和裁剪。
- **静默吞错**：适配层 catch 后返回空结果，Agent 以为"查到了但没数据"，实际是鉴权过期。错误要显式、可读。
- **写操作无确认**：删数据、群发消息这类动作，建议在 OpenClaw 侧加人工确认或二次校验，别指望模型自律。
- **日志打全量请求**：header 里的 token、body 里的 PII 都可能进日志，脱敏必须在适配层做掉。

# 可复用建议

- 适配层只做三件事：鉴权、参数映射、错误翻译。业务逻辑留在 API 侧，别在适配层长出第二套业务。
- 每个 tool 配一个最小可运行示例输入，进 CI 跑通鉴权和 schema，防止上游 API 改版时静默失败。
- 错误 hint 直接写成给模型的指令，实测能把无效重试率降一大截。
- 灰度上线：先只放开只读工具，稳定运行一段时间后再开写操作。

# 总结

Agent 与 API 的握手，本质是把"人的契约"翻译成"模型的契约"：工具面收敛、鉴权外置、返回裁剪、错误可行动。OpenClaw 与 MCP 提供了管道，但契约质量取决于适配层的设计。少给模型自由度，多给它确定性，握手就稳了。
