## 背景

OpenClaw 的 cron 任务，本质是一次**无人值守的定时 prompt**：到点后新建一个冷启动会话，把 instruction 交给 agent 执行，结果投递到你指定的 channel。它不是"给助手发条消息"，而是没有上下文、没人接话的单向执行。

很多定时任务跑不稳，问题不在调度配置，而在 instruction 本身。

## 问题：把 cron 写成了聊天

典型的翻车写法：

> "每天早上帮我看一下昨天群里有什么重要的事，整理一下发我。"

这句话在对话里没问题，因为人随时可以补充信息。放进 cron 里会踩空：

- 冷启动会话里没有"我"、"群里"、"重要"的定义；
- "昨天"靠 agent 自己推断执行时间，时区一偏就错位；
- 没说输出到哪、什么格式，agent 可能在 cron 会话里自言自语，没人看到；
- 没说拿不到数据怎么办，缺数据时 agent 倾向于编一个像样的答案。

## 做法：按"交接文档"的结构写

我固定把 instruction 拆成六段：**语境、目标、数据来源、输出契约、降级路径、禁止项**。举个例子：

```text
这是一次定时任务，没有人会回复你的追问，不要提问。
任务：汇总过去 24 小时 #alerts 中 level=error 的日志。
步骤：
1. 先取系统时间，再计算时间范围；
2. 用 mcp__logs__query 拉取该范围的日志；
3. 按错误类型聚合，统计次数和最近一次出现时间。
输出：向 #daily-report 发送不超过 15 行摘要，
固定三列：错误类型 | 次数 | 最近时间。
降级：如果日志拉取失败，只发送"日志拉取失败：<原因>"，
重试不超过 2 次，禁止编造数据。
禁止：不回复历史消息，不执行任何写操作。
```

三个关键点：

1. **补齐上下文**。时间范围、频道名、工具名、字段名全部显式给出。让 agent 先取系统时间再算"昨天"，比让它猜可靠得多。
2. **输出定死**。投递目标、行数上限、列结构写明。格式稳定，下游才能解析和归档。
3. **失败有出口**。明确"拉不到就说拉不到"。没人接话的场景里，降级文案是防幻觉最便宜的手段。

## 踩坑点

- **"接着上次的"**：cron 是新会话，没有上次。需要跨次状态，就让任务把结论写入固定文件，下次 instruction 里指明去读。
- **复杂逻辑塞在 instruction 里**：解析、过滤、统计这类确定性逻辑，下沉到脚本或 MCP 工具，instruction 只做编排和转述。prompt 越长，执行漂移越多。
- **高频任务 + 大读取量**：五分钟一次还让它读全量频道，token 和会话都会膨胀。改成让任务维护增量水位（比如记录上次处理到的时间戳）。
- **漏了禁止项**：不写"不要回复历史消息"，agent 偶尔会把摘要当对话回出去，触发连锁反应。

## 可复用建议

- 写 cron instruction 的心态：**你不是在聊天，是在给一个冷启动、无人值守的同事写交接文档**。
- 固定六段模板；每个新任务先手动触发一次验证输出，再挂到 cron 上。
- 输出模板长期保持稳定，格式漂移是定时任务腐烂的第一信号。
- instruction 里出现"应该""大概""看看情况"这类词时，停下来改写成可判定的条件。

## 总结

Cron instruction 的质量，决定了定时任务是"自动化的资产"还是"每周翻车的彩票"。核心就三件事：补齐冷启动缺的上下文，把输出契约定死，给失败留一条明确的路。做到这三点，多数不稳定的定时任务都能变稳。
