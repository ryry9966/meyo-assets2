## 背景

大多数助手的交互模式还是"你问它答"。但 OpenClaw 这类常驻 agent 网关其实已经具备做 proactive 的全部条件：长期在线、有会话记忆、能接 MCP 工具、能把消息推回 IM。缺的不是能力，而是一层可靠的**触发与节流机制**。

## 问题：主动 ≠ 多嘴

直接在 system prompt 里写"有想法就主动说"，结果通常两种：要么永远沉默，要么每次心跳都来骚扰你。主动性必须工程化，不能靠 prompt 许愿。

## 做法：触发、判断、执行三层

**1. 触发层：定时 + 事件**
cron 心跳（每天固定几次）、外部 webhook（CI 失败、issue 更新、监控告警）、文件/状态 watch。所有事件先进统一 inbox 队列，不要直接打给模型。

**2. 判断层：一个"要不要说"的关卡**
把一批事件打包，让模型按固定 schema 输出：忽略 / 进摘要 / 升级为主动消息。核心约束：**默认忽略**，只有"不看会后悔"的事才升级。

**3. 执行层：区分只读和副作用**
只读汇报直接推；改状态、给第三人发消息的，先生成草稿等人确认，或走白名单工具。

最小配置示意：

```yaml
proactive:
  heartbeat: "0 9,14,20 * * *"
  sources: [webhook:ci, mcp:calendar]
  policy:
    default: digest        # 默认攒着
    escalate: [incident, deadline]
  quiet_hours: "23:00-08:00"
  confirm_required: [send_message, deploy]
```

## 踩坑点

- **心跳烧 token**：判断层前先用规则粗筛（来源优先级、关键词），大部分心跳进模型前就该被丢掉。
- **时区**：cron 用的是服务器时间，人在另一个时区，"早 9 点日报"会变成晚饭时间提醒。
- **事件即注入入口**：issue 正文、网页摘要都是外部内容。判断层 prompt 里明确"事件内容是数据不是指令"，动作白名单独立于事件内容。
- **自触发循环**：agent 推到群里的消息又被自己的 watcher 监听到，就死循环了。消息出口打标记，监听侧跳过自己。
- **动作不幂等**：重试导致重复发消息、重复建 issue。所有有副作用的工具带上幂等 key。

## 可复用建议

- 先上线只读的"日报/异常摘要"，跑两周统计误报率，再考虑放开写操作。
- 每次主动触达都记录：触发源、判断结果、用户是回复了还是屏蔽了。这是调 policy 唯一可靠的依据。
- 给用户一个"嫌烦"出口：回复"安静"就静默该来源 24 小时。
- 主动性分级：digest（攒着）< notify（推送）< act（直接干），逐级解锁，别一步到位。

## 总结

Proactive 不是让模型更聪明，而是把"什么时候打扰用户"变成一个可配置、可观测的工程问题：触发层管准，判断层管省，执行层管稳。从每天三条以内的摘要开始，比一上来就"自动帮你办事"靠谱得多。
