## 背景

这两年大家已经习惯给项目配 `CLAUDE.md` / `AGENTS.md`，把构建命令、目录结构、代码规范喂给 agent。但仔细想想，这类文件描述的是**项目**，不是**人**。Agent 换一个工作区，关于你的认知就归零了——你得在新的会话里重新自我介绍一遍。

## 问题

具体痛点有三个：

- **重复交代**：每个新会话都要说一遍"回复用中文、先给方案再给代码、时区 UTC+8、别引入某个框架"；
- **行为漂移**：同一个用户，在项目 A 里 agent 简洁直接，在项目 B 里啰嗦冗长，风格完全不一致；
- **粘贴成本高**：手动贴个人偏好，内容随手写，今天一份明天一份，自己都记不清说过什么。

## 做法

核心思路：建一份**全局用户上下文文件**，例如 `~/.openclaw/USER.md`（用你手头 agent 支持的全局注入位置即可），随每次会话加载。

**1. 分区写，每区三五条**

```markdown
## 环境
- 时区 UTC+8，回复语言：中文
- 主力系统 macOS + Linux 服务器

## 技术栈
- 数据库主用 PostgreSQL，前端偏 Svelte
- 明确不用：X 框架（历史原因）

## 协作偏好
- 先给方案和权衡，确认后再写代码
- 解释附上"为什么"，不要只贴结论

## 硬约束
- 未经确认不执行 git push、不删除文件
```

**2. 声明分层优先级**

在 USER.md 末尾写明："本文件是默认值，项目级 CLAUDE.md 可覆盖具体细节，但硬约束不可覆盖。" 不写这句，agent 遇到冲突只能猜。

**3. 建立"提议—确认"更新流程**

让 agent 在对话中发现长期偏好时，先问一句"要不要写入 USER.md"，你确认后它提一个 diff，你审查再合并。不要让它静默自改。

## 踩坑点

- **越写越长**：超过一两百行，关键约束会被稀释。宁可精简，删掉 agent 一眼能从项目文件推断的内容。
- **写敏感信息**：密钥、住址、真实姓名+公司组合都别放。这文件会进上下文，可能随日志、遥测、子任务外发。
- **静态腐化**：技术栈换了没更新，agent 拿过时假设做决策。我吃过亏——换了数据库三个月，agent 还在生成旧方言的 SQL。
- **事实写成命令**："我主用 PostgreSQL" 比 "必须使用 PostgreSQL" 更安全，后者会让 agent 在新场景里强行套用。

## 可复用建议

1. 用 dotfiles 仓库管理 USER.md，跨机器同步、留变更历史；
2. 每条尽量写成一句话的可执行断言，不写背景故事；
3. 每季度让 agent 自查一次："列出你从 USER.md 得到的假设，哪些可能已过时？"，输出往往比你自己翻文件高效；
4. 团队场景可以把"环境与技术栈"部分抽成角色模板，各自维护"协作偏好"部分。

## 总结

USER.md 本质上就是把个人上下文从"每次口述"变成"版本化配置"。它不神奇，不能替代记忆和检索能力，但便宜、可控、可 diff、可审计。花二十分钟写一版，你会立刻发现 agent 少问了一半废话——这大概是投入产出比最高的一次 agent 配置。
