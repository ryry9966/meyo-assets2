## 背景

OpenClaw 里单 agent 串行跑任务久了，会遇到三个典型症状：上下文越滚越大，中间产物把有效信息挤出去；任务互相阻塞，一个长耗时步骤卡住后面所有事；调试困难，一个会话里混着多件事的痕迹，回放时根本分不清哪步出了问题。

Subagent 机制就是针对这个的：主 agent 退到编排位，把独立任务派给子 agent 并行执行，各自维护自己的上下文，跑完只交回摘要。听起来很美，但实际用下来，能不能拿到收益，取决于拆任务的方式，而不是并发数。

## 问题

举个真实场景：让主 agent 一口气做"调研技术方案 + 改三个模块的代码 + 更新文档"。结果是上下文塞满了调研摘录，改模块 C 的时候已经"忘了"模块 A 的约定；文档更新被排到最后，往往不了了之。这三类任务其实上下文独立、互不依赖，完全可以拆给三个 subagent 同时跑。

## 做法

1. **先判定可并行性**。拆之前画一下依赖：任务之间没有共享可变状态、没有先后依赖（或者依赖可以由编排层串成链），才值得拆。强耦合任务拆开只会增加通信成本。
2. **定义窄边界**。每个 subagent 一个目标，输入是最小上下文：任务描述 + 相关文件路径 + 明确的约束，而不是把父会话整段转发过去。
3. **按需挂 MCP 工具**。子 agent 只给它完成该任务所需的工具，最小权限。写文件的 agent 不需要联网搜索能力，反之亦然。
4. **约定交付格式**。要求 subagent 把产出写到 workspace 里独立的文件，返回结构化摘要：状态、产物路径、遗留风险。
5. **控制并发**。同时跑 2–4 个比较稳。API 限流之下，并发拉满并不会更快，只会更快触发重试。
6. **编排层合并**。主 agent 读各产物文件、交叉检查一致性，发现冲突就降级为串行重跑或转人工。

## 踩坑点

- **文件冲突**：两个 subagent 同时改一个文件，后写的覆盖先写的。给每个子任务分配独立产物文件，合并动作收归主 agent。
- **上下文泄漏**：把父上下文整段传下去，等于没拆，token 照旧爆炸。
- **虚假完成**：subagent 报告"已完成"但没验证。要求返回证据——文件路径、diff、命令输出片段，没有证据按未完成处理。
- **失败传染**：一个子任务挂了不该终止整批。编排层要有重试和降级逻辑。
- **成本失控**：并行是 token 消耗的乘法。先用小任务试跑一轮，估算单任务开销再放大。

## 可复用建议

- 固化一个 subagent 任务模板：**目标 / 边界 / 交付物 / 返回格式**，四项填齐再派发。
- 产出落盘不落消息，主 agent 只读摘要和文件。
- 每个子任务保留独立 transcript，出问题能单独回放，不用翻主会话。
- 任务尽量设计成幂等：重跑不产生副作用，重试才敢放开手。

## 总结

Subagent 编换来的吞吐和上下文整洁是真实收益，但它把复杂度从"执行"转移到了"编排"：拆分、边界、合并、容错，每一环都要自己负责。它适合 IO 密集、彼此独立的任务批量处理；对强耦合、需要频繁互相参照的工作，老老实实串行反而更省。建议从两个子任务的小规模拆分开始验证，跑顺了再扩。
