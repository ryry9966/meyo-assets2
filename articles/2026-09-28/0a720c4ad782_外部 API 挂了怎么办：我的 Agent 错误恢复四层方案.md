## 背景

跑过长时间自动化任务的人都有体会：Agent 的大部分故障不是模型推理挂了，而是外部依赖挂了——LLM 供应商限流、MCP server 崩溃、第三方 API 超时。一次 40 分钟的自动化流程，往往因为第 35 分钟一个 429 就整体报废，中间产物全部丢失。

## 问题

默认写法下，工具调用是“单向”的：发请求 → 拿结果 → 继续推理。这个假设在真实网络里不成立。常见的三种烂尾方式：

1. **裸重试**：429 一来立刻重发，触发更严格的限流，账号被拉黑；
2. **无恢复**：直接抛异常终止，前面所有上下文作废；
3. **假装成功**：把报错堆栈塞回上下文，模型“脑补”一个结果继续跑，下游拿到的全是幻觉数据。

## 做法

我现在的方案分四层，从里到外：

**第一层：错误分类。** 在统一的 tool wrapper 里把错误分成三类——可重试（429/5xx/timeout/连接重置）、不可重试（401/403/404/参数错误）、结果可疑（200 但字段缺失或格式变了）。用状态码加轻量 schema 校验就够。

**第二层：指数退避 + 抖动 + 上限。** 重试间隔 1s/2s/4s 递增，加随机抖动，最多 3~5 次，并设总时长上限。别让一次调用卡住整个 agent。

**第三层：熔断与降级。** 连续失败超过阈值就熔断该工具 5~10 分钟，期间走降级路径：备用 provider、上一次成功的缓存、或更便宜的备用模型。降级返回要打标记，让主流程知道数据可信度下降了。

**第四层：checkpoint 续跑。** 长任务每完成一步就把状态落盘（SQLite/JSON 均可）。恢复时读 checkpoint、跳过已完成步骤，而不是从头再来。对多阶段 pipeline，这一步收益最大。

另外，把错误信息“翻译”后回灌给模型：保留关键报错，附一句“该 API 当前不可用，你有备选工具 X，或跳过此步并告知用户”。让 LLM 做路由决策，比代码里写死 if-else 灵活。

## 踩坑点

- **幂等性没做，重试变重复。** 写操作（发消息、下单、建文件）重试前必须有去重键，否则一次超时重试 = 两条重复消息。
- **超时给太长。** 我曾把 HTTP timeout 设 120s，一个卡死的连接拖住整个事件循环，看起来像 Agent 假死。外层超时要远小于内层。
- **降级 provider 格式不一致。** fallback 模型输出结构对不上主 provider，下游解析全崩。降级层要做输出归一化。
- **熔断太敏感。** 偶发两次失败就熔断，Agent 频繁走降级路径，结果质量悄悄变差还难察觉。阈值宁可保守。

## 可复用建议

- 所有工具调用过同一个 wrapper，错误分类、重试、熔断只写一次；
- 写操作默认视为不幂等，除非显式声明；
- checkpoint 粒度是“一次成功的工具调用”，不是“一轮对话”；
- 给降级路径留观测：日志里单独打 fallback 计数，别让降级变成静默劣化。

## 总结

Agent 的可靠性不取决于模型多聪明，而取决于失败路径设计得是否完整。错误分类 → 有限退避 → 熔断降级 → 断点续跑，这套组合不复杂，但能把“一次故障全盘报废”变成“降级跑完 + 明确告知用户”。建议先把 wrapper 和 checkpoint 做起来，其余逐步补。
