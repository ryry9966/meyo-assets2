## 背景

LLM 本身无状态。每次新会话，模型对你一无所知：你用 pnpm 不用 npm、时区是 UTC+8、commit message 不写 emoji——这些偏好如果不落盘，就得每次重新交代。在 OpenClaw 这类长期运行的 Agent 环境里，会话会跨天、跨项目重启，记忆是基础设施问题，不是锦上添花。

## 问题：三种常见的错误做法

1. **全塞进 system prompt**：简单粗暴，但两个月后 prompt 膨胀到几千 token，真正相关的偏好被稀释，成本也上去了。
2. **对聊天记录做 RAG**：偏好通常散落在闲聊里，嵌入检索回来的多为噪音，"不要用 var"这种否定式偏好几乎检不准。
3. **完全交给模型自觉**：模型没有跨会话状态，所谓"记住"只是当次上下文里的幻觉。

## 做法：分层记忆 + 明确的读写策略

结构上分三层，全部用普通文件存，不引入数据库：

- **L0 核心画像**（profile.md）：常驻注入，控制在 300 token 内，只放最稳定的偏好：语言、时区、技术栈、代码风格。
- **L1 结构化记忆**（memory/*.json）：每条记录含 type（preference / fact / decision）、content、source（哪个会话）、timestamp、confidence。
- **L2 会话摘要**（episodes/）：按项目归档的对话摘要，只在需要时检索。

**写入策略**分两条路径：

1. 显式指令："记住这个""以后都这样"——直接入 L1，confidence 置高。
2. 会话收尾的抽取步骤：会话结束时跑一个轻量任务，列出候选记忆，去重后与 L0 做冲突检测；冲突时以新覆盖旧（保留版本历史），而不是追加。

**读取策略**：L0 常驻；L1 按 tag + 关键词匹配注入相关条目；L2 只在用户提到历史任务时才检索。在 OpenClaw 里我把抽取挂到 session hook，合并任务用 cron 每周跑一次。

## 踩坑点

- **记忆腐烂**：最早存的"用户用 npm"半年后已失效，没有时间戳的过期偏好会一直污染输出。后来每条加 timestamp，抽取时旧条目默认降权。
- **过度抽取**：一开始把"帮我看看这个报错"也当成"用户常遇到构建报错"存下来，两周攒了几百条噪音。解法是收紧 type 定义 + 置信度阈值，宁缺毋滥。
- **记忆投毒**：一条错误信息被记住后会反复出现。所有条目必须带 source，并给用户一个"查看 / 修正"入口，忘却（/forget）要做成一等操作。
- **否定式偏好检索不到**："不要写分号"这类记录，我统一改写成正向规则"代码风格：无分号"再入库，命中率明显提升。
- **命名空间混乱**：多项目共用记忆会把 A 项目的习惯带到 B 项目。L1 按 workspace 隔离，L0 只放全局项。

## 可复用建议

1. v1 用 markdown / JSON 文件，别急着上向量库。可 git 版本化、可人肉审查、出问题直接 diff。
2. 稳定偏好、易变事实、会话流水三者分离，生命周期不同。
3. 每条记忆必须有：类型、来源、时间戳。没有来源的记忆不可信。
4. 提供"忘记"和"修正"命令，让用户能治理自己的记忆。
5. 建一个验收清单：会话 1 告知偏好，会话 5 验证是否生效；再加一个反向用例——告知偏好已变更，验证旧记录被覆盖而非并存。

## 总结

Agent 记忆本质是一个数据生命周期问题：采集、存储、检索、衰减、遗忘，缺一环都会烂掉。别追求"像人一样记忆"，先把最枯燥的部分做扎实：小而准的常驻画像 + 可审计的结构化条目 + 明确的覆盖规则。记忆系统越无聊、越透明，Agent 反而越好用。
