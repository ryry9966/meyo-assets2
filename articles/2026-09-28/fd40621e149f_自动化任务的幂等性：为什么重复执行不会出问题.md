## 背景

在 OpenClaw 上把自动化任务跑起来很容易，难的是让它安静地跑上几个月。迟早有一天你会发现：同一个任务被执行了两次。

触发源比想象中多——cron 到点触发、heartbeat 周期唤醒、消息渠道的 webhook 重投递、MCP 工具调用超时后 Agent 的自动重试，甚至你自己手动补跑一次。调度层和传输层把「再试一次」当作可靠性手段，但对有副作用的任务来说，重试就等于重复执行。

幂等性的定义很朴素：同一任务执行一次和执行多次，最终状态一致。这不是可选项，是无人值守任务的入场券。

## 问题

几个真实会翻车的场景：

- cron 触发的日报任务，进程重启后补偿触发，群里收到两条一模一样的日报；
- Agent 调用发消息工具超时后重试，其实第一次已经发成功了，收件人收到两条；
- 同步插件按「追加」写数据，重跑一次，文件里多出一批重复条目；
- 渠道因网络抖动重发消息，Agent 当成新指令又执行了一遍。

共同点只有一个：副作用没有被去重。

## 做法

按四步来，成本很低：

1. **定一个稳定的幂等键。** 用有业务含义的组合，比如「日期 + 渠道 + 任务名」。不要用每次随机生成的时间戳或 UUID——那样每次都是新任务，查重永远查不到。
2. **执行前先查记录。** 落地方式随意：SQLite 一张表、workspace 里一个 JSON 状态文件、外部系统的唯一约束都行。关键是查和写必须在同一个可靠存储里，不要只放内存。
3. **写操作用 upsert / 覆盖语义，而不是 append。** 「把状态置为 X」天然幂等，「再追加一条」不是。能覆盖就别追加。
4. **发送类动作先查后发，并记录回执。** 超时不等于失败——先查询确认结果，再决定补偿还是跳过。

最后一步是验证：把同一个任务手动连跑两次。第二次应该被跳过，或产生相同终态。这是最便宜的回归测试。

## 踩坑点

- 幂等键里掺了时间戳，精度到秒，等于没去重；
- 状态只记在插件内存里，OpenClaw 一重启全部失效；
- 用「先删后建」代替 upsert，中间挂掉就留了个空窗；
- 并发触发没加锁：cron 和手动同时到，两个进程都通过了查重，用文件锁或 SQLite 事务可以挡住；
- 假设渠道不会重复投递消息——实际上都会。

## 可复用建议

- 把幂等做成 skill 的默认行为，而不是每个任务单独处理。写一个 `ensure_once(task_key, handler)` 之类的小工具函数，所有自动化入口统一走它；
- 日志里打印幂等键。出问题时第一件事就是查这个键命中了几次，比翻聊天记录快得多；
- 读操作不用过度设计，天然幂等，把精力留给有副作用的写路径。

## 总结

幂等不是什么高级架构，拆开就是三件事：稳定的键、可靠的存储、覆盖式的写。一旦打算让任务无人值守跑超过一周，就默认它一定会被重复触发，然后按这个假设去设计。调度器和网络总会重试，幂等设计保证重复执行无害——这层保险只花几十行代码，但决定了你的自动化能不能真的撒手不管。
