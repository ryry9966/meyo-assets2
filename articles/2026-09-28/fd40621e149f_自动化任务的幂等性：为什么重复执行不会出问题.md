## 背景

写自动化任务的人迟早会接受一个事实：**任何任务都不止会跑一次**。定时器重叠触发、webhook 重投、Agent 层重试、工具调用超时后的人工重跑——重试不是异常路径，而是常态。尤其在用 Agent 编排工具调用时，模型输出不确定、网络时好时坏，「只执行一次」这个假设几乎守不住。

幂等性（idempotency）就是针对这个现实的工程设计：同一个任务执行一次和执行多次，系统的最终状态一致。它不是锦上添花的优化，而是自动化能不能被信任的前提。

## 问题

不幂等的操作在重复执行时会直接产生脏数据，常见几类：

- **消息/通知类**：同一条告警发了两遍，群里立刻有感知；
- **创建类**：重复建单、重复建文件、重复写库；
- **追加类**：日志/清单被 append 两次，状态重复累积；
- **事务类**：最危险，重复调用外部接口可能双倍扣费、双倍发货。

Agent 场景还有个特殊难点：**一次工具调用「超时」不等于「失败」**。服务端可能已经处理成功，只是响应没回来。Agent 看到报错去重试，就产生了第二次真实生效的副作用。再叠加 SDK 内部重试和 Agent 层重试，重复概率是相乘的。

## 做法

我们的实践可以归纳成四步：

1. **先分类。** 只读操作天然幂等，不用管；覆盖型操作（写文件、set 状态、upsert）也天然幂等，尽量把任务往这个形态靠；只有「创建/追加」类才需要专门处理。
2. **给任务一个稳定的 run key。** 用「触发源 + 业务键 + 时间窗口」推导确定性 ID，而不是 `now()` 或随机数。重试必须复用同一个 key，否则去重无从谈起。
3. **原子地「占坑」。** 执行副作用前先占位：SQLite 唯一索引、Redis `SETNX`、文件锁都行。占到了才执行，占不到说明已有人做过，直接跳过。注意是「原子占位再执行」，不是「先查一下没有再执行」——后者有并发竞态。
4. **副作用尽量设计成 upsert。** 自己写 MCP 工具或插件接口时，形态上往 `ensure_state(x)` 而不是 `append(x)` 靠。调用外部 API 时，优先使用对方支持的幂等键（支付、消息类 API 基本都有）。

## 踩坑点

- **check-then-act 竞态**：两个并发实例都查到「没做过」，然后都执行。必须用唯一约束 / `SETNX` 这类原子原语，不能靠先查后写。
- **幂等键混入了易变时间源**：key 里带了每次重试都会变的时间戳，等于没做去重。key 必须在重试之间保持不变。
- **把「未知」当「失败」**：超时后不做检查直接重试，是最容易出重复的地方。正确姿势是先查 key，再决定跳过还是重做。
- **去重记录无限增长**：key 要有过期策略，但 TTL 不能太短，否则慢重试会绕过去重。
- **按输出内容去重**：LLM 相同输入会生成不同文本，哈希对不上。去重必须挂在任务/业务键上，不要挂在生成结果上。

## 可复用建议

- 把「这个任务至少会被执行两次」当成默认假设来写代码；
- 在技能库里沉淀一个 `ensure_once(task_key, fn)` 之类的公共助手，所有创建类操作强制走它；
- 去重决策留痕：命中 key 被跳过的运行也要写日志，事后可审计；
- 验收加一条固定用例：同一任务连跑两遍，断言无重复副作用。

## 总结

幂等性的本质，是把「重试安全」从运气变成设计。Agent 层可以不确定、可以重试，但效果层要收敛到同一个状态。做到这一点，自动化任务才敢放心交给定时器和重试机制——重复执行不再是风险，而只是正常的容错路径。
