## 背景

社区里不少同学的工作流已经是：Agent 写初稿 → 人工审校 → 发多个平台。Markdown 是这条链路事实上的中间格式。但“写完”只是开始：公众号不认原生 Markdown，知乎编辑器会吞部分 HTML，静态博客要 frontmatter，掘金的代码高亮规则又不一样。同一篇稿子手工适配三四个平台，每次修订都重来一遍，很快就会失控。

## 问题拆解

实际做下来，痛点集中在三层：

1. **AI 输出不稳定**。同一个 prompt，模型有时把正文包进代码围栏，有时列表符号 `-`、`*` 混用，有时表格前后多出空行。预览里看不出，进了渲染器就炸。
2. **平台格式分歧**。公众号只接受内联样式的 HTML，`<details>`、脚注直接被剥掉；静态站要 YAML frontmatter；部分平台对图片外链有防盗链或压缩。
3. **修订成本**。多平台各改各的，版本立刻分叉，没有单一事实来源。

## 做法：清洗 → AST → 平台渲染器 → 发布

核心原则一句话：**AST 优先，正则兜底**。

**第一步，输出契约 + 清洗。** 约定 Agent 必须输出带 frontmatter 的纯 Markdown，不许包围栏。清洗脚本负责剥掉模型偶尔加的“以下是正文”类前后缀、统一列表符号、修多余空行，且必须幂等。

**第二步，解析成 AST。** 用 unified/remark 解析成 mdast，之后所有变换都在树上做：规范标题层级、把脚注降级为普通段落（给不支持的平台）、任务列表转普通列表。每个变换是独立的 transformer，可自由组合。

**第三步，平台渲染器。** 每个目标平台一个渲染插件，注册到统一入口：公众号渲染器遍历 AST 输出内联样式 HTML；博客渲染器透传 Markdown 并补全 frontmatter；掘金基本透传，只替换不支持的语法。新增平台就是加一个插件，不动主流程。

**第四步，资产与发布。** 图片先传图床、回写 URL、压缩到平台限制内；发布脚本带 `--dry-run`，先生成本地预览和 diff，人工确认后再推。

最小骨架大致是：

```js
const tree = remark().parse(rawMd);
const cleaned = transformers.reduce((t, fn) => fn(t), tree);
const out = wechatRenderer(cleaned); // 或 blogRenderer / juejinRenderer
```

## 踩坑点

- **正则改 Markdown 迟早出事**：代码块里的 `#`、`*`、反引号会被误伤。要么先摘出代码块，要么老实用 AST。
- **模型会“热心”包一层围栏**，或在前后加解释性文字。清洗必须幂等，跑几遍结果一致。
- **公众号样式白名单很窄**：只认内联 style，`position`、外链脚本全剥；表格必须每个单元格带样式，否则渲染稀碎。
- **图片相对路径是隐形炸弹**：发布前强制校验所有图片 URL 可达且有 alt。
- **代码围栏语言别名不一致**，各平台高亮差异大，建一张别名映射表统一。

## 可复用建议

1. **单一事实来源**：canonical Markdown 只存仓库，各平台内容都是构建产物，改稿只改源头。
2. **给 Agent 定输出契约**并用 schema 校验，不合格直接打回重生成，别让脏数据进管线。
3. **变换用 AST，正则只做收尾修补**。
4. **渲染器插件化 + dry-run diff**，新平台接入成本能压到半天以内。
5. **维护一张平台怪癖表**（不支持什么、限制什么），比记忆可靠。

## 总结

多平台发布的问题本质不是“格式转换”，而是把不稳定的 AI 输出，经一条规范化管线收敛成确定性产物。AST 是这套管线的地基，插件化的平台渲染器让新增渠道变成常规操作，dry-run 和单一事实来源保证改稿时不炸。这套结构不绑定具体工具，remark、Pandoc 或自研解析器都能落地——关键是把格式适配从手工动作，变成可重复的构建步骤。
