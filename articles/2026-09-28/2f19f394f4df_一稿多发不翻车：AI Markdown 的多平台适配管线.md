## 背景

最近把「AI 写稿 → 多平台发布」跑成了固定管线。动机很朴素：模型写内容没问题，但同一份 Markdown 贴到静态博客、公众号、社区和 RSS，渲染结果各不相同。人工逐平台调格式比写稿还耗时，且不可复现。

## 问题在哪

LLM 输出的 Markdown 是「方言自由」的，坑集中在几类：

- **单换行语义**：CommonMark 单换行不断行，公众号恰好相反，正文常被压成一段或裂成两段。
- **扩展语法兼容差**：任务列表、脚注 `[^1]`、数学公式，各家支持参差。
- **HTML 白名单**：公众号剥离大部分行内 HTML，代码高亮必须转成内联样式。
- **资源链接**：相对路径、外站图床防盗链、图片 alt 丢失。
- **frontmatter**：部分平台把 YAML 直接渲染进正文。

根因：格式适配被留给了发布时的人肉环节，而它本该是确定性代码。

## 做法

核心决策只有一条：**模型只产出受限的「规范方言」，平台差异全部由代码侧 adapter 消化。**

1. **约束生成端**。在 agent 的 system prompt 里固化一份 Markdown 子集规范：仅 GFM 安全子集、禁止行内 HTML、段间空行分隔、不依赖单换行断行、代码块必须带语言标签。同时把这份规范落成 markdownlint 自定义规则，prompt 与 lint 共用同一份定义，避免两处漂移。

2. **规范化层（lint gate）**。remark 解析成 AST 后跑 lint，违规项以结构化错误（行号、规则名）回喂模型修复，最多重试两轮，仍失败即中断，不硬发。

3. **平台 adapter 层**。每个平台一个纯函数 adapter，输入 canonical AST：博客 adapter 基本直通；公众号 adapter 用 shiki 把代码块转内联样式、脚注降级为文末列表、表格补样式；RSS adapter 剥离 frontmatter、图片转绝对地址。

4. **资源先行**。发布前把图片转存到自己的图床并替换 URL，这一步放在 adapter 之前，保证各平台拿到同一份稳定链接。

5. **快照人审**。每个 adapter 产物生成渲染快照（HTML diff 或截图），确认后才触发发布。发布动作在 OpenClaw 里封装成 MCP tool，带 dry-run 参数，方便 agent 自助排障。

## 踩坑点

- **别让模型直接输出平台特化格式**。试过让它一次生成「公众号版」，每次措辞和结构都漂移，diff 不可用。格式转换必须是确定性的。
- **单换行统一在规范化层处理**。别指望 prompt 让模型永远记得段末加两个空格，它偶尔会忘。
- **脚注语法在多数平台无效**，降级策略写死在 adapter 里，不要临时手改。
- **平台会改版**。公众号某次更新吞掉了代码块语言标签，靠快照 diff 才发现；快照对比是最后的兜底。
- **图床防盗链与 URL 失效是静默故障**，预检步骤里加 HEAD 请求检查。

## 可复用建议

- 把「规范方言」沉淀为一份 lint 配置 + 一段 prompt 片段，进仓库、随项目走。
- adapter 保持纯函数：AST 进、平台格式出，不碰网络和文件系统，测试就是快照测试。
- 守住边界：模型负责内容，代码负责格式，中间用结构化错误衔接。

## 总结

多平台适配本质是编译问题：定义源语言（规范方言）、写 lint、写目标端 adapter、用快照做回归。跑通之后，一稿多发从「逐平台手工修」变成「跑一次管线、看一眼快照」，新接一个平台只是新增一个 adapter。成本一次性，收益长期。
