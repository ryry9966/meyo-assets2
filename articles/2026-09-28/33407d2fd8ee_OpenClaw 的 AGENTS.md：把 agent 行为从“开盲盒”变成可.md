## 背景

OpenClaw 的 agent 不是每次会话都从零开始"懂你"。会话启动时，workspace 里的几个固定文件会被注入上下文，其中 AGENTS.md 是最核心的一份——它是写给模型看的工作空间使用手册，定义这个 agent 该怎么干活：用哪些工具、什么时候要确认、什么绝对不能碰。

问题在于，很多人装完插件、接好 MCP 就直接跑，AGENTS.md 还是默认模板。于是你只能在聊天里反复纠正它："发消息前先问我""别动那个目录""用 X 工具不是 Y"。这些纠正只活在当次对话里，重开一个会话，一切重来。

## 问题：行为不可复现，规则没有落点

agent 行为不稳定，根源通常不是模型能力，而是规则没有落点。口头纠正是一次性的；MEMORY.md 记的是事实和状态，不是操作规程。你需要一个地方，专门放"这个工作空间里，你怎么干活"。

## 做法：把 AGENTS.md 当运维手册写

我的写法，可直接抄：

1. **定位文件**：默认在 `~/.openclaw/workspace/AGENTS.md`，可在配置里改路径。
2. **按主题分节**，每节三五条，每条一行祈使句：
   - 工具使用：哪个 MCP/插件负责什么，禁用的工具写明禁用原因；
   - 消息纪律：哪些操作要先确认、哪些渠道不许主动发；
   - 安全红线：不删文件、不执行涉及花钱的操作、不提交未审查的代码；
   - 升级条件：什么情况必须停下来问我。
3. **规则写成"条件 + 动作 + 边界"**。例如："要删除超过 10 个文件 → 先列清单等我确认 → 拿不到确认就不执行。"
4. **改动走 git**。workspace 直接 `git init`，每次调规则一个 commit，行为回归时能 diff 出是哪条改动引起的。

注意：改完要开**新会话**验证，旧会话加载的是旧版本，测不出效果。

## 踩坑点

- **写成散文**。模型对短祈使句的服从度明显高于大段落背景介绍，描写越少执行越准。
- **多处规则打架**。SOUL.md、USER.md、AGENTS.md 各写一套口吻要求，模型只能随机站队。口径统一：AGENTS.md 管操作规程，MEMORY.md 管事实状态。
- **规则过期**。换掉一个 MCP server 后忘了更新对应章节，agent 会按旧工具名硬调，然后开始编参数。工具变更时把 AGENTS.md 当依赖清单过一遍。
- **往里塞敏感信息**。AGENTS.md 全文进上下文，等于全文发给模型供应商。密钥、内网地址放环境变量或凭证管理，文件里只写"在 X 处获取"。
- **绝对化规则堆太多**。"永远不要 X"多了，正常需求也会被卡死，红线要配例外路径。

## 可复用建议

- 把 AGENTS.md 的改动当代码 review：每条规则问一句"什么场景触发？触发时该做什么？"
- 出事故再补规则：agent 做错一次，就把对应的"条件 + 动作 + 边界"写进去，这是最有效的迭代方式。
- 每月删一次规则：一个月没触发过的规则大概率是过期描述，删掉比留着强。
- 控制总长度：手册膨胀到几百行，遵守率会肉眼可见地下降；砍不动的部分移到独立文档，AGENTS.md 里只留一句"需要时读 X"。

## 总结

AGENTS.md 不是配置文件，是这个 agent 的值班手册。它的价值不在写了多少，而在每一条都真的会在某次执行里被用到。写短、写成规则、进版本控制、随事故迭代——这四件事做到，agent 的行为就会从"每次开盲盒"变成"基本可预期"。
