## 背景

在 OpenClaw 的实际使用里，Agent 很少单独干活：查资料要调搜索接口，发通知要走第三方服务，MCP 工具背后连着一堆内外部 API。跑 demo 时一切正常，一旦进入自动化流程就会发现：**外部 API 的故障是常态**——限流 429、读超时、5xx、证书过期、字段悄悄变更。

传统服务挂了会报错，Agent 挂法不太一样：模型收到报错后会“自行处理”，而它处理的方式经常是编一个看起来合理的答案，或者陷入无限重试。故障没有被修复，只是被藏起来了。

## 问题

实际踩下来，Agent 面对工具故障主要有四种失控模式：

1. **幻觉兜底**：工具返回失败，模型基于“常识”补全结果，用户拿到的是编造数据；
2. **重试风暴**：模型看到报错就立刻再调一次，上下文来回几轮，token 烧掉，任务毫无进展；
3. **上下文污染**：原始 HTML 错误页、长堆栈被塞进对话，模型注意力被打散，后续步骤全部跑偏；
4. **级联阻塞**：一个慢接口卡死整个 workflow，其他本可完成的步骤跟着超时。

## 做法

我们的原则只有一句：**重试和兜底放在工程层，模型只负责决策，不负责机械操作。**

**第一步：工具层统一封装。** 所有外部调用走同一个 client：超时起步（连接 3s、读 10s），指数退避 + 随机抖动重试，且只重试幂等操作；对同一上游做熔断，连续失败 N 次后快速失败一段时间，不反复撞墙。

**第二步：错误结构化后再给模型。** 不要把原始异常丢进上下文，统一转成 `{error_code, retriable, hint}` 三个字段。`retriable=false`（如鉴权失败、参数错误）明确告诉模型“禁止重试，换路径或上报用户”；`retriable=true` 的注明框架已完成重试，模型只需决定下一步。

**第三步：编排层设硬上限。** 无论模型多“坚持”，单任务的重试次数、总耗时、token 预算都要有天花板，超限即终止，并输出明确的失败原因。

**第四步：准备降级路径。** 高频查询类工具缓存一份“最近一次成功结果”，故障时返回并标注数据时间；写操作失败则入队延后重放；都没有时，让 Agent 明确说“此步骤暂时不可用”，而不是硬编。

## 踩坑点

- **让模型控制重试节奏**是最常见的坑，它几乎总是立即重试。退避逻辑必须写在代码里，模型的 prompt 里只保留“失败后如何选择路径”的规则。
- **超时 ≠ 失败**。请求超时后服务端可能已执行成功，写操作必须带幂等键，否则重试会重复下单、重复发消息。
- **空返回也要防幻觉**。API 返回 200 但结果为空时，模型容易脑补，prompt 里要写明：空结果就如实说空。
- **熔断状态要全局共享**。每个会话各自重试等于没有熔断，一个挂掉的 API 会拖垮所有并发会话。

## 可复用建议

- 沉淀一个统一的 tool client 模板：超时、重试、熔断、幂等键四件套内置，新工具接入只写业务逻辑。
- 在 system prompt 里加一段固定的故障处理约定：工具报错时禁止编造数据、必须声明失败、按 hint 走降级路径。
- 混沌测试纳入联调流程：故意断开某个工具，观察 Agent 的行为是否符合预期，比任何 prompt 调优都更能暴露问题。

## 总结

外部 API 挂掉不可怕，可怕的是 Agent 用幻觉把故障掩盖掉。核心思路一句话：**机械性的恢复动作（重试、退避、熔断、缓存）交给工程层，模型只在结构化的失败信息面前做“换路、降级还是上报”的决策。** 把这条边界划清，Agent 的自动化流程才能在真实网络环境里稳定跑下去。
