## 背景

Agent 的核心能力是推理与决策，但它本身没有“手”。要查天气、发工单、操作数据库，最终都要落到一次真实的外部 API 调用上。OpenClaw 的思路是通过工具调用和 MCP（Model Context Protocol）把外部服务暴露给 agent，让模型像调函数一样使用它们。听起来简单，真正落地时坑不少。

## 问题

我们在对接几个内部服务时踩过三类典型问题：

1. **schema 定义不当**：参数描述模糊，agent 传参五花八门，接口报错率高；
2. **返回值失控**：一个列表接口返回上万 token 的 JSON，直接把上下文撑爆；
3. **副作用不可控**：重试机制叠上非幂等接口，同一个 webhook 被触发了两次。

## 做法

现在我们沉淀了一套四步流程：

**第一步：先写 adapter，再谈 agent。** 每个 API 包一层薄封装，只暴露 agent 真正需要的动作。比如订单系统不需要 20 个接口，拆单、查单、改状态，三个工具够了。

**第二步：schema 收紧。** 参数用 enum 限定取值，required 字段宁多勿少，描述里写清楚单位、时区、格式。写完先别接 agent，自己在 CLI 里调一遍，确认参数解释没有歧义。

**第三步：错误翻译。** API 返回 429、500 时，不要把原始报错原样丢给模型。统一转成结构化短文本，比如 `{"error": "rate_limited", "retry_after": 30}`，让 agent 能做出“等待后重试”的决策，而不是换着花样连调三次。

**第四步：鉴权与配置分离。** token 走环境变量或配置文件，adapter 里只读不写；日志对敏感字段脱敏——agent 的对话记录往往会被完整保存，这一点容易被忽略。

## 踩坑点

- **工具越多，选择越乱。** 一次性挂 30 个工具，agent 经常选错。按场景拆 profile，一个会话只挂相关的几个。
- **返回值要裁剪。** 列表类接口默认只回前 N 条 + 总数 + 游标，agent 需要更多就显式翻页。
- **幂等键自己生成。** 写操作带上客户端生成的 idempotency key，重试才安全。
- **超时设短一点。** 同步调用 10 秒封顶，长任务改异步 + 轮询任务状态，避免 agent 干等到上下文堆积。
- **dry-run 先行。** 新工具上线先跑 dry-run 模式，只打印将要发出的请求，人工确认后再放开真实调用。

## 可复用建议

把上面这些沉淀成团队模板：统一的 adapter 骨架（鉴权、重试、超时、脱敏各留一个钩子）、统一的错误返回格式、统一的 MCP server 配置。新人对接一个新服务时照模板填空，半天内能跑通端到端流程，而不是每个人重新发明一遍重试逻辑。

## 总结

对接外部服务本质上是个接口设计问题，不是提示词问题。schema 收紧、错误可读、副作用可控，这三件事做到位，agent 调 API 的成功率会明显高于单纯堆 prompt 调优。OpenClaw 生态里 MCP 已经把协议层标准化了，剩下的拼的是每个团队自己的工程纪律。先写 adapter、先跑 dry-run、再交给 agent——这个顺序建议固化下来。
