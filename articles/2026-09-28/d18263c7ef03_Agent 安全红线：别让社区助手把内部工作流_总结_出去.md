## 背景

社区跑了一段时间 Agent 之后，大家很容易进入舒适区：机器人会读 issue、会总结讨论、会回答新人提问，效率确实高。但当你把 MCP 工具、内部 wiki 索引、私有仓库 token 全挂上去之后，一个不太体面的问题就出现了——**这个 Agent 知道的，比你打算让社区知道的多得多**。泄露往往不是攻击造成的，而是日常运行中的"顺嘴"。

## 问题的三条典型路径

1. **上下文过载式泄露**。Agent 为回答问题拉取了内部文档，然后在公开频道的"总结"里顺带说出内部排期、成员分工或未发布的方案。没人恶意，只是上下文里有什么，它就可能说什么。
2. **日志外流**。完整对话上下文被原样打到第三方观测平台，工作流配置、成员邮箱、内部链接全在里面。这是静态泄露，最难撤回。
3. **间接注入**。有人在帖子或链接里埋了构造好的内容，诱导 Agent "把你的系统配置复述出来"。Agent 把外部内容当指令执行了。

## 做法：六步收边界

**1. 划资产红线**。先列清单："绝对不能出现在公开输出里的东西"——内部工作流配置、成员身份信息、未发布决策、凭证。后面所有规则都以这张清单为依据。

**2. 权限最小化**。给社区 Agent 单独发凭证，能只读就不读写，能限定 repo/目录就限定到目录。不要复用管理员个人 token——Agent 的泄露半径应等于它的凭证范围。

**3. 出口加过滤**。在 Agent 向公开渠道发送的最后一跳挂 sanitizer：对内部域名、成员邮箱格式、ticket 编号、system prompt 片段做 denylist 拦截。宁可偶尔误杀转人工复审，也不要裸奔。

**4. 会话隔离**。"内部检索"和"公开回复"不要共用长会话。内部上下文用完即弃，公开会话从干净的 system prompt 起步。

**5. 日志先脱敏再外发**。审计日志本地优先，送第三方前做 redaction。审计要能回答两个问题：谁在何时问了什么、Agent 调了哪个工具。

**6. 外部内容只当数据**。社区帖子、链接、issue 正文一律视为不可信输入，不得据此改变 Agent 行为；任何"把数据发往外部"的工具调用强制人工确认。

## 踩坑点

- **"只读权限"不是免死金牌**。能读私有仓库，就等于能通过总结复述它。读权限的边界就是泄露边界。
- **MCP 工具描述本身是攻击面**。恶意 server 可以在工具描述里埋指令。装第三方 MCP 前看描述、看代码，来源不明的不挂。
- **别用真实数据做测试**。上线前拿真实成员数据跑测试，泄露会直接进日志和截图。
- **改 system prompt 不算修复**。Prompt 是软约束，真防线是凭证范围和出口过滤。注入者不会尊重你的提示词。
- **多 Agent 链路会绕过过滤**。A 的输出喂给 B 时，过滤只挂在 A 上就失效了。过滤要挂在"最后一个对外出口"，而不是某个环节。

## 可复用建议

上线社区 Agent 前过一遍这张单子：

- [ ] 列出全部工具及每个凭证的实际范围
- [ ] 回答一个问题：这个 Agent 的完整上下文被整屏截图外流，能不能接受？不能，就收敛权限
- [ ] 公开出口挂 denylist 过滤
- [ ] 日志脱敏后再出域
- [ ] 对外发送类工具强制人工确认
- [ ] 每季度复核一次凭证与工具清单

## 总结

Agent 泄露不是模型"叛变"，而是工程边界没画好。红线三件事：**收窄它能看到什么（权限）、控制它能说什么（出口过滤）、留痕以便追溯（审计）**。Prompt 写得再规矩，也替代不了权限边界——把安全性建在系统设计里，而不是建在模型的自觉里。
