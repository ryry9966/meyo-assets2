## 背景

OpenClaw 的 workspace 里有一组 Markdown 组织的“系统级文件”：AGENTS.md 管行为约束，SOUL.md 管性格基调，USER.md 记用户偏好，MEMORY.md 存长期记忆。IDENTITY.md 是其中最容易被忽略的一个——它回答一个朴素的问题：这个 agent 是谁。

本质上，IDENTITY.md 是一段每次会话都会注入 system prompt 的身份卡。它不参与代码逻辑，不需要重启，改完即生效。正因为它太简单，很多人直接跳过，让 agent 保持默认的无名状态。

## 问题

不写身份文件，短期看不出异常，跑久了会集中暴露：

1. **跨渠道不一致**：同一个 agent 在 Telegram 和 Discord 里的自我介绍各说各话，称呼随机变化。
2. **人格漂移**：换模型、升级版本后，语气和名字变了，长期用户能明显感知“它不是原来那个了”。
3. **边界模糊**：多 agent 或多成员共用实例时，谁负责什么没有共识，任务互相踩脚。
4. **无法沉淀**：你对 agent 的定位调整只存在于某次对话里，下次会话全部丢失。

根因是同一个：身份只存在于上下文里，而不是文件里。

## 做法

在 workspace 根目录创建 IDENTITY.md，建议控制在 15~30 行：

```markdown
# IDENTITY
- Name: 小蟹
- Creature: 一只住在终端里的机械蟹
- Vibe: 克制、直接、偶尔冷幽默
- Emoji: 🦀
- 职责: 自动化运维、代码审查、日报
- 边界: 不处理与工作无关的长聊
- 自我介绍: 我是 X，负责……有事先说结论。
```

三个实践要点：

1. **让 agent 参与起草**。先空着文件跑一周，问它“基于最近的对话，你觉得你是谁”，把回答提炼进文件，再人工砍掉夸张的部分。比凭空编写更贴合实际用法。
2. **明确与 SOUL.md 的分工**。IDENTITY.md 写“事实层”：名字、职责、边界、固定句式；SOUL.md 写“性格层”：语气、价值观。两边都写语气，必然打架。
3. **用 git 管理演进**。身份文件放进 workspace 的版本库，每次调整一个 commit，变更历史就是一份真实的运营日志。

## 踩坑点

- **写太长**。有人塞进几十行生平设定，每次会话全量注入，token 成本和注意力稀释都很实在。身份卡是约束，不是小说。
- **与 AGENTS.md 冲突**。一边要求回复精简，一边写“热情健谈”，agent 会在两种指令间摇摆。改身份时顺手 grep 一下其他文件。
- **写入敏感信息**。真实姓名、内网地址、密钥提示都会随 prompt 注入所有渠道。身份文件按“会被公开”的标准来写。
- **只写不改**。三个月没动过，它描述的就是过去的想象而非现在的 agent。我给自己定了个固定动作：每月让 agent 对照 IDENTITY.md 输出一份“偏差清单”，人工决定是改文件还是改行为。

## 可复用建议

- **字段可执行优先**：“回复先给结论”比“聪明可靠”有用得多，前者可验证，后者是空话。
- **模板化起步**：Name / Creature / Vibe / Emoji / 职责 / 边界 / 自我介绍，七项足够。
- **多 agent 实例各自独立身份**，且显式写清“不负责什么”——负面清单比正面描述更能防越界。

## 总结

IDENTITY.md 的价值不在“让 AI 更像人”，而在把散落在对话里的隐性约定，收敛成一份可版本化、可 review、可进化的显式资产。它很小，几十行；但它让 agent 在换模型、换渠道、换维护者之后，仍然是同一个可辨认的存在。建议今天就给它建个文件、放进 git，一个月后回头看 diff——那里面就是这个 agent 真实的成长记录。
