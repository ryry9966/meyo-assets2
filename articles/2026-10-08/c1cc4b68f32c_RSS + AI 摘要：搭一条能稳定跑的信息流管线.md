## 背景

信息源越来越碎，但 RSS 依然是少数"你说了算"的订阅协议：无算法干预、可导出、机器友好。过去几个月，我把几十个信息源收进了一条由 OpenClaw 驱动的管线：定时抓取 → LLM 摘要 → 定点推送日报。稳定运行后，每天早上一条消息就能看完所有重要更新。本文记录做法和踩坑，供直接复刻。

## 问题

单纯聚合 RSS 有两个老问题：

1. 条目太多，未读堆积，最后沦为"收藏即读完"；
2. 逐条丢给 LLM 总结，token 花得多，且脱离上下文的单条摘要价值有限。

目标很明确：**压缩信息量，但不压缩事实**。摘要必须可溯源，宁可短，不可编。

## 做法

整条管线分四层，每层独立可替换：

**1. 源层**：精选 15–20 个高质量源，先控总量再谈质量。没有 RSS 的站点用 RSSHub 生成；导出一份 OPML 存档，换环境可直接迁移。

**2. 抓取层**：OpenClaw 定时任务每 2 小时拉一次增量。条目写入本地 SQLite，判重主键用 `hash(link + title)`，而不是 feed 自带的 GUID——GUID 质量参差不齐，是重复推送的头号元凶。

**3. 处理层**：不逐条总结，按"同源合并、跨源分桶"批量送入模型。Prompt 只做三件事：按来源分组给一句话摘要、标出跨源重合话题、输出"今日值得点开 Top 5"。两条硬约束：只允许使用给定内容；无实质信息时明确输出"无"。模型用便宜的批量档即可，这一步不需要强推理。

**4. 输出层**：摘要 + 原文链接拼成日报，走 OpenClaw 已有的消息通道推送，同时落一份 Markdown 到笔记目录。链接一定保留——摘要是索引，不是替代。

## 踩坑点

- **摘要幻觉**。早期 Prompt 没加"仅基于给定内容"的约束，模型会脑补结论。加上硬约束和空值兜底后基本消失。
- **只有标题没有正文**。不少 feed 只给 title，摘要质量很差。对这类源补一步正文抓取 + readability 提取，效果提升明显。
- **重试打爆预算**。抓取和摘要解耦后，重试只发生在队列里，失败不阻塞整条管线；否则一次 API 抖动会让同一批条目被重复总结三遍。
- **时区与发布时间**。部分源的 pubDate 不准，按"最近 N 小时"过滤会漏也会重，改成按库里是否已存在判重更稳。
- **成本不可见**。最初没记 token 消耗，某天接了一个日更大源，当天费用翻了三倍才发现。现在每次运行都记用量。

## 可复用建议

- **先落库，再加工**。原始条目永远先入库，摘要可随时重跑；摘要缓存与原始数据分离。
- **把摘要做成独立工具**。我把它包成了一个 MCP tool / skill：输入一组条目，输出结构化摘要，管线之外也能手动调用、单独调试。
- **给自己留反馈回路**。日报里顺手记一下"点开了几条"，两周后你就知道哪些源该删。管线价值不在抓得多，在信噪比。
- **宁可漏，不要编**。摘要出错的代价远大于漏掉一条。

## 总结

这条管线没用到任何新奇技术，价值全在工程细节：判重键选对、批处理省 token、失败不扩散、成本可观测。RSS 负责稳定输入，LLM 负责压缩，OpenClaw 负责把它们粘起来定时跑。半天内可以完成搭建，建议从 5 个源开始小步验证，再逐步扩容。
