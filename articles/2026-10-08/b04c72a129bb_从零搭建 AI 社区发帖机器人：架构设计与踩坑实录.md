## 背景

社区运营里有不少重复劳动：每周精选整理、新帖摘要、FAQ 沉淀。这些事规则清晰、格式固定，适合交给 agent 半自动完成。我的目标很收敛：让 OpenClaw 每天定时抓取社区动态，生成一篇摘要帖，经人工确认后发布。注意是"半自动"——发布前必须有人点头，这个决定帮我省掉了后面一大半麻烦。

## 整体架构

分四层，各层只通过数据打交道：

1. **调度层**：cron 触发 OpenClaw 定时任务，每天 09:00 执行一次；
2. **采集层**：一个 MCP 工具 `fetch_updates`，拉论坛 API 和 RSS，返回结构化 JSON；
3. **生成层**：agent 读数据，按固定模板产出草稿，写入本地 drafts 表；
4. **发布层**：人工审核通过后调用 `publish_post`，携带幂等键。

关键取舍：采集和发布拆成两个独立 MCP 工具，而不是一个大而全的"发帖"工具。工具越窄，agent 越不容易自由发挥。

## 实施步骤

1. 先定状态机：`draft → in_review → published / failed`，全流程状态落库（SQLite 即可），不依赖对话上下文记忆；
2. 写 MCP 工具，用 schema 严格约束参数，工具描述里写清"什么时候不该调用"；
3. Prompt 模板固化：字数上限、口吻、必须引用来源链接；
4. 审核回路复用 OpenClaw 的消息通道：草稿推到审核频道，回复确认后才触发发布；
5. 跑两周观察期，把误判 case 反哺回模板和工具描述。

发布工具的核心 schema 大致长这样：

```json
{
  "name": "publish_post",
  "description": "发布已审核通过的草稿。仅当草稿状态为 in_review 且经人工确认后才可调用。",
  "inputSchema": {
    "type": "object",
    "required": ["draft_id", "idempotency_key"],
    "properties": {
      "draft_id": { "type": "string" },
      "idempotency_key": { "type": "string", "description": "正文内容 sha256；重复提交返回已有帖子 ID，不新建" }
    }
  }
}
```

## 踩坑实录

1. **重试导致重复发帖**。上线首日遇到网络超时，脚本重试，社区连发三篇一样的帖子。解法：幂等键（内容 hash）强制下发，服务端见重复键直接返回既有帖子。
2. **模型编造链接**。草稿里出现过一条不存在的帖子 URL，格式完全正确、肉眼难辨。解法：发布前加校验步骤，所有 URL 必须能在采集层数据里溯源到原文，否则打回重写。
3. **cron 重叠**。抓取加生成偶尔超过 10 分钟，下一次调度又起来了，两份草稿互相覆盖。解法：任务加文件锁，拿不到锁就跳过本轮。
4. **MCP 工具描述太宽泛**。早期 `publish_post` 描述只写"发布帖子"，agent 有一次把草稿标题当成正文发了出去。把描述补上参数语义和反例之后，再没出过错。工具描述本身也是 prompt，值得认真写。
5. **时区问题**。调度按 UTC 跑，帖子标题里的"今日"经常差一天。解法：生成层显式传入日期参数，绝不让模型自己推算时间。

## 可复用建议

- 一切写操作必须幂等，幂等键在动手前就设计好；
- 工具宁小勿大，一个工具只做一个动作；
- 进入草稿的每一条外部事实（链接、数字）都要可溯源、可校验；
- 状态落库，别赌上下文记忆；
- 留一个 kill switch 配置项，能让机器人整体停写。

## 总结

机器人现在每天稳定产出，人工审核耗时约两分钟。最大的体会：agent 那部分难度不高，真正的工作量在把"发布"这种不可逆操作包上工程护栏——幂等、校验、状态机、人工确认，缺任何一个都会在某个凌晨还你惊喜。建议同样想做发帖自动化的同学，先把审核回路和幂等键做扎实，再逐步提高自动化程度。
