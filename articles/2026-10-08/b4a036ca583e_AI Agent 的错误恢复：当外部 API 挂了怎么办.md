## 背景

跑过稍长一点的 Agent 任务就会体会到：可靠性瓶颈往往不在模型，而在它调用的外部世界——LLM 供应商限流、MCP 工具超时、第三方 SaaS 抽风。传统服务挂了返回个 502 就结束了，Agent 的麻烦在于它处于任务中段：计划走到一半，一个工具失败可能让整轮 run 报废。更糟的情况是模型不肯认输，脑补一个"已成功"的结局继续往下走。

## 问题

外部 API 的失败形态不止一种，处理方式完全不同：

- **可重试**：超时、429、5xx，等一等可能就好
- **不可重试**：401 鉴权失败、400 参数错误，重试纯属浪费
- **部分成功**：批量写入挂了一半，全量重试会产出重复数据

而不加约束地让 Agent 自己在对话里重试，常见结局是 token 烧穿、上下文爆炸，或者陷入死循环。

## 做法

**1. 把重试下沉到工具封装层。** 所有外部调用过一层统一 wrapper：指数退避加随机抖动，最多 3 次，单步超时独立设置。401/403/400 直接抛终态错误，不进重试队列。收益是策略集中一处可调，模型上下文里只会看到"重试后仍失败"这一个结论。

**2. 给模型返回结构化错误，不是原始报错。** 把 stack trace 塞给模型，它要么反复道歉要么瞎编。失败时返回紧凑结构：`status / retryable / reason / suggestion`，让 Agent 能分支决策——换备用工具、跳过可选步骤、或如实告知用户。

**3. 写操作一律幂等。** 重试最大的坑是非幂等写入：重发消息、重复下单。写 API 带上由 `run_id + step_id` 派生的幂等键，批量操作记录已完成子项，断点续传而非全量重来。

**4. run 级别做检查点。** 长任务每完成一步持久化中间状态。API 挂掉导致整轮失败时，恢复运行从断点继续，而不是从零把前面的 token 花费再来一遍。

**5. 降级路径提前定义。** 每个关键工具都要预先回答"挂了怎么办"：查询类 → 读缓存并标记数据可能过期；生成类 → 切备用模型；关键动作 → 挂起转人工。没有预案的降级就是临场发挥，模型会替你做最差的决定。

**6. 熔断与观测。** 连续 N 次失败后冷却一段时间再碰该 API，避免重试风暴。每次工具调用记录 status、耗时、重试次数——事后才能区分这是限流、超时还是配额耗尽，三者的修法完全不同。

## 踩坑点

- **让模型自己循环重试**：没有预算上限，token 和时间都会失控。重试必须由代码层执行，模型只拿最终结论。
- **立即重试无抖动**：多个并发 run 同时重试，把半死的 API 彻底打死。
- **HTTP 超时设太长**：单线程 runtime 里一次 120 秒超时会卡住整个事件循环。
- **把"API 挂了"和"key 配额用完"混为一谈**：后者重试一万次也没用，还可能触发封禁。

## 可复用建议

- 统一 wrapper + 错误分类，是 Agent 工具层的第一块基建，越早做越省
- 写操作默认幂等，读操作默认可降级
- 设 run 级预算（总时长 / token / 重试上限），超了就 checkpoint + 暂停 + 通知，不硬撑
- 测试时故意 mock 一个挂掉的 API，用验证成功路径的认真程度去验证失败路径

## 总结

错误恢复的目标不是消灭故障，而是让故障**有界且可读**：重试有上限、降级有预案、状态可续传、失败可归因。一个 Agent 的成熟度，往往体现在它挂掉时的样子——是优雅降级并如实上报，还是编造一个看似完成的结果。
