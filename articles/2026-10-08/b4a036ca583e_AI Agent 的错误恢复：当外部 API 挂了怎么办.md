## 背景

Agent 的价值在于编排外部能力：MCP 工具、第三方 API、内部服务。链路一长，外部依赖的可用性就成了整条任务链的短板。和传统后端不同，Agent 面对故障时的"重试决策"是由模型做出的——它没有固定的重试策略，只有对错误信息的理解和随即生成的反应。这既是灵活性来源，也是事故放大器。

## 问题：API 挂掉时 Agent 通常会发生什么

实际跑过自动化任务的人多半见过这几种：

1. **重试风暴**：工具返回 429，模型立刻原样重试，越重试越被限流；
2. **幻觉兜底**：接口报错后，模型基于自身知识"补全"了结果，下游拿到一份看起来正常、实际编造的数据；
3. **死循环烧 token**：失败 → 换个参数再试 → 再失败，循环到预算耗尽；
4. **重复副作用**：写操作超时，但服务端其实已执行成功，Agent 重试造成重复下单、重复建单。

## 做法：把错误恢复从模型手里拿回来

核心原则：**重试、熔断、降级是工程问题，不要交给模型**。模型只负责在"结构化失败信息"面前做路由决策。

**第一步，工具层统一封装。** 每个 MCP 工具或 API 调用套一层 wrapper：设置连接/读取超时；对可重试错误（429、5xx、timeout）做指数退避加抖动的重试，上限 2–3 次；对 400/401/404 这类确定性失败绝不重试。有条件再加简单熔断：连续 N 次失败后直接短路一段时间。

**第二步，错误结构化后喂给模型。** 不要把堆栈原文丢进上下文，返回类似：

```json
{"ok": false, "error_type": "rate_limited", "retry_after_ms": 5000, "hint": "use_cache_fallback"}
```

`error_type` 建议收敛成小集合：`rate_limited / timeout / auth / not_found / upstream_down`。模型据此决定换路、等待还是上报，而不是自由发挥。

**第三步，写操作必须幂等。** 给每个写请求带幂等键（或先查后写），超时的写操作先查询确认再决定是否重试，避免"响应丢失 ≠ 执行失败"导致的重复执行。

**第四步，任务级预算与降级路径。** 整个任务设 token/时间/重试总预算，超了就停。每个关键工具预先写好降级方案：备用数据源、带过期时间的缓存、或"部分结果 + 明确标注失败项"。同时在系统提示里明确允许模型报告失败——很多幻觉兜底就是被"必须完成任务"的指令逼出来的。

## 踩坑点

- 在 prompt 里写"失败就重试"，时序和次数全靠模型发挥，几乎必然失控；重试逻辑要放代码层；
- 熔断缺失：多步任务里每个节点都去撞同一个挂掉的 API，一步拖垮全程；
- 只捕获异常不分类，模型看到一串 500 文本开始脑补原因；
- 忽略"成功但响应丢失"，这是写操作场景里最隐蔽的一类。

## 可复用建议

- 制定团队级错误信封规范，所有工具统一格式，Agent 侧只写一次处理逻辑；
- 每次工具调用（入参、返回、耗时、重试次数）落日志，故障后能回放；
- 开发环境 mock 故障：超时、429、返回脏数据，把恢复路径当成功能来测。

## 总结

外部 API 迟早会挂，问题不是"会不会"，而是挂的时候 Agent 行为是否可控。把重试、熔断、幂等下沉到工具层，给模型结构化的错误类型和明确的降级选项，再用任务级预算兜底——这套组合拳做完，大多数 API 故障就从"事故"降级成"一条告警日志"。
