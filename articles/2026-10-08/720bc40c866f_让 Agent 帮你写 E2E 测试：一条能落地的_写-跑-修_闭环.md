## 背景

E2E 测试是所有测试层里投入产出比最难平衡的一层：写起来慢、维护成本高、一改版就大面积红。我们团队 40 多条核心链路的 E2E，历史上一直是"有人有空才补"的状态。今年把 Agent 接进测试流程，跑了几个月，有些经验值得记录。

## 问题：直接让 AI 写测试，为什么不行

最直觉的做法是把页面 URL 丢给模型，说"帮我写 Playwright 测试"。结果测试看起来很专业，跑起来问题一堆：

- 选择器从渲染后的 DOM 抄 CSS 路径，改个样式就挂；
- 大量 `waitForTimeout(3000)` 这类硬等待，CI 上时快时慢；
- 断言很弱，只判断"页面打开了""元素存在"，该校验的业务数据完全没碰；
- Agent 不知道登录态怎么处理，要么每条测试重复走登录，要么干脆绕过，把真实问题藏起来。

核心原因：模型没有"运行"的能力，它只能凭想象写。凭想象写的测试，本质上还是需要人来验证的第一版草稿。

## 做法：给 Agent 一个"写-跑-修"闭环

我们基于 MCP 接了一个浏览器工具（Playwright MCP 这类都可以），让 Agent 具备打开页面、查 DOM、执行测试、读失败日志的能力。流程改成了这样：

1. **准备上下文，而不是丢整个仓库。** 每次给 Agent 三样东西：测试规范文档（选择器约定、fixture 用法、命名规则）、被测路由的定义、一两条人工写好的"金标准"测试当示例。
2. **小批量生成。** 一次只让它写 3~5 条，覆盖一条业务链路。生成后要求它自己跑一遍，读失败输出，自己修，直到全绿。
3. **强制红绿验证。** 全绿不代表测试有效。要求 Agent 故意把被测功能改坏一个点（比如禁用提交按钮），确认对应测试真的会红，再恢复。这一步过滤掉了大量"永远绿"的无效测试。
4. **人工只做两件事：** 决定"测什么"，以及审查断言强度。断言必须落在业务结果上——订单状态变化、落库字段、返回数据——而不是 DOM 存在性。

跑下来，人工写一条链路的 E2E 大概半天；Agent 闭环跑一轮 20 分钟左右，人工审查再加 10 分钟。

## 踩坑点

- **Agent 会"迁就现状"。** 页面上有 bug，它会把 bug 行为写进断言，测试从此永远绿。红绿验证加人工看断言，是唯一解。
- **retry 别开太狠。** Agent 为了让测试稳定，倾向于把重试次数拉满。我们统一收敛到框架默认值——稳定性靠等待策略解决，不靠重试掩盖。
- **上下文不是越多越好。** 把整个 repo 塞给它，输出质量反而下降，还会幻觉出不存在的工具方法。一份精简的规范文档每次复用，比堆代码有效。
- **测试数据要隔离。** Agent 生成的测试默认共用同一批账号和数据，并发一跑就互相污染。后来在规范里强制要求每条测试自建数据、自己清理。

## 可复用建议

- 把测试规范写成独立文件，作为 Agent 上下文随任务注入。这是收益最大的单点投入。
- 优先让 Agent 补"重复劳动型"覆盖：表单校验、权限跳转、边界输入。支付、结算这类核心链路仍然人工主导。
- 维护一张测试债清单，每次迭代让 Agent 认领 2~3 条消化，比一次性大规模生成可控得多。

## 总结

Agent 写 E2E 的价值不在于"一键生成"，而在于写-跑-修的闭环把人的角色从"编写者"变成了"定义者和审查者"。它像一个不知疲倦的初级工程师：机械覆盖做得又快又好，但判断什么重要、什么是 bug，仍然得靠你。工具接好之后，真正决定质量的是你给它的规范文档，和你愿不愿意认真看它交上来的每一条断言。
