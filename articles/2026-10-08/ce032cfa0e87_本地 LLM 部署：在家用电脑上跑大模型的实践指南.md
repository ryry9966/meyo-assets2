## 背景

日常折腾 OpenClaw / Agent / MCP 自动化的同学大概都有类似需求：批量整理文档、跑数据清洗、让 Agent 做一些琐碎的分类任务。这些活儿多数不需要顶级模型，但数据又不想交给第三方 API。本地跑一个中小参数模型，隐私可控、零边际成本、断网可用，实际价值比想象中高。

## 问题

我踩的第一个坑是"配置幻想"：以为 16GB 内存的笔记本能随便跑 14B 模型。实际上决定能不能跑的，不只是参数量，还有量化精度、上下文长度和 KV cache。第二个坑是模型选型：很多模型聊天表现不错，接进 Agent 框架做工具调用就翻车——function calling 的支持质量参差不齐。

## 做法

1. **盘点硬件**：显存优先。经验法则：Q4_K_M 量化的 7B 模型约占 4-5GB 显存，14B 约 9-10GB，32B 起步 20GB。纯 CPU 也能跑，但吐字速度掉到个位数，只适合离线批处理。
2. **选运行时**：图省事用 Ollama（一条命令拉模型，自带 OpenAI 兼容接口）；追求性能和可控性用 llama.cpp 或 vLLM；不碰命令行就用 LM Studio。
3. **选模型**：优先选官方声明支持 tool calling 的模型系列，Q4 量化起步，先小后大。
4. **接入 Agent**：绝大多数 Agent 框架认 OpenAI 兼容协议，把 base_url 指到本地服务（Ollama 默认是 `http://localhost:11434/v1`）即可。MCP 这层完全不用改，本地模型只替换推理层。
5. **压测**：用真实任务（别拿 hello world）跑一轮完整工具调用，观察显存占用和吐字速度，再决定要不要上探更大的模型。

## 踩坑点

- **上下文吃显存比想象中凶**：8K 上下文的 KV cache 可能额外占 1-2GB，Agent 的系统提示词普遍很长，32K 上下文直接爆显存是常事，务必留余量。
- **量化不是越低越好**：Q2 以下模型在工具调用这类"格式敏感"任务上错误率明显上升，建议 Q4 起步，重要链路用 Q5/Q6。
- **GPU 层数没设满**：llama.cpp 的 `n-gpu-layers` 默认值可能只放一半层上显卡，速度腰斩，还以为是显卡不行。
- **Windows 模型缓存默认在 C 盘**：几十 GB 很快撑爆系统盘，记得改模型目录到数据盘。

## 可复用建议

- **分层路由**：草稿生成、分类、摘要用本地 7B-14B；复杂推理、长上下文、关键决策走云端大模型。在 Agent 里做一个 fallback 路由，两边的钱和隐私都省了。
- **固化模型清单**：把模型名、量化档位、实测显存占用、tool calling 表现记成一张表，群里/团队里直接复用，避免每个人重新踩一遍。
- **调 `keep_alive`**：Ollama 默认几分钟就卸载模型，Agent 每次调用都要重新加载。把 keep_alive 设长一点，首 token 延迟能从半分钟降到秒级，体感差距巨大。

## 总结

本地部署的价值不是"替代云端"，而是在 Agent 自动化链路里多一层可控、便宜、离线可用的兜底。务实的路径是：先把 7B 级别模型跑通工具调用，验证整条 Agent + MCP 链路，再逐步上探更大的模型。一上来就冲 32B，大概率卡在显存和速度上，反而耽误了真正要做的自动化。
