## 背景

OpenClaw 的 cron 任务本质上很简单：按调度表达式定时触发，把一条 instruction 投递给 agent，让它在会话里执行，再把结果送到你指定的渠道。听起来像设个闹钟，实际上更像给一位不知情的值班同事派工单，他不知道你之前的任何对话，也不会来问你第二个问题。

多数 cron 任务效果差，不是调度表达式配错了，而是 instruction 被写成了备忘录。

## 问题

三个典型症状：

1. **跑完没动静**。instruction 写的是"提醒我看一下邮件"，agent 复述一句就结束，结果没有落点。
2. **每次执行不一致**。今天摘要五行，明天翻了三倍，动作路径全靠模型发挥。
3. **失败时静默或刷屏**。数据源挂了，任务既不报错也不降级；或者反过来，每 5 分钟推一条"我检查过了"。

根因一致：默认 agent 拥有你脑子里的上下文，而它没有。

## 做法

我惯用的骨架是六段式，按顺序填：

```text
【目标】一句话说清这个任务要产出什么。
【输入】确切路径 / 命令 / API，禁止"最近的""相关的"这类模糊词。
【步骤】编号列出动作，一步一个动作。
【输出】格式（如 ≤10 行摘要）+ 投递渠道（发到哪个 channel / 写到哪个文件）。
【异常】数据为空、工具调用失败时怎么办：写日志、静默、还是降级推送。
【边界】明确"不要做"的事：不改配置、不额外联网搜索、不追问。
```

两个容易忽略的点：

- **时间语义写死**。"检查今天的任务"里的"今天"以什么时区、什么时点为准，直接写进 instruction，别指望 agent 猜对。
- **先手动后定时**。上线前手动触发几次，再用高频试跑间隔（比如每 5 分钟）观察会话日志，措辞稳定后再调回真实频率。

## 踩坑点

- **隔离会话没有记忆**。cron 触发的会话通常不继承你聊天窗口里的上下文，"继续刚才的事"必挂，所有前提条件要写进 instruction。
- **任务太大**。一个 job 塞 20 步工作流，中途一次工具调用失败就全盘报废。拆成多个小 job，各管一段。
- **没写输出落点**。agent 默认回复只留在会话里，没人看。要么显式投递，要么落文件，二选一。
- **静默条件缺失**。没有"无事发生就不推送"的约定，低价值消息很快会逼你把通知全部关掉。
- **在 instruction 里放密钥**。instruction 会随日志留存，敏感信息走环境变量或配置文件，prompt 里只写引用名。

## 可复用建议

- 每个 cron job 用独立 session + 独立日志文件，排障时只看一份日志。
- 输出格式锁死（固定三行：状态 / 关键数字 / 异常项），扫一眼就能判断要不要点进去。
- 措辞当代码维护：改 instruction 前先手动跑一次留存基线，改完对比结果，提交版本库。

## 总结

评价一条 cron instruction 是否合格，标准只有一条：一个不知情的 agent 拿到它，不需要追问，就能执行完并把结果送到你指定的位置。把它当工单写，而不是当备忘录写，定时任务就从"抽卡"变成了可靠的管道。
