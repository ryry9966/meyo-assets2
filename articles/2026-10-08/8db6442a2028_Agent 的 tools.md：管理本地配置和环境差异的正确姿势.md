## 背景

跑本地 Agent（OpenClaw 网关 + agent workspace）一段时间后，会发现一个尴尬的事实：模型对你这台机器一无所知。每次会话它都要重新猜——python 在哪个 venv、node 是不是 nvm 管的、docker 要不要 sudo、代理端口是多少。猜错了就一路试错，烧 token 还浪费时间。

工具调用层（MCP、插件、脚本）解决了"能调什么"，但"在你这台机器上怎么调对"始终是缺口。tools.md 就是补这个缺口的最低成本方案：一份放在 workspace 里的纯文本事实清单，agent 每次会话开始读一遍，按图索骥。

## 问题

没有 tools.md 时常见三类事故：

1. **环境猜测错误**。macOS 上裸敲 `python` 摸到的是系统旧版本，Linux 同事那边却是 3.12；Windows 的路径分隔符让同一份脚本直接挂。
2. **每次会话重复探测**。agent 反复跑 `which`、`ls` 摸环境，上下文被无关输出填满，真正任务反而挤不进去。
3. **团队配置漂移**。同一个 skill 在 A 机器能跑、B 机器报错，排障全靠口口相传，没人说得清差异在哪。

## 做法

核心原则：**把环境写成"事实"，不写成"教程"**。推荐分四层：

1. **全局约定**（进 git）：工具调用的通用规则——优先用 uv 不用裸 pip、docker 统一加 `--rm`、密钥一律从环境变量读。
2. **机器事实**（不进 git，命名 `tools.local.md`）：OS、shell、包管理器、关键路径、版本号。全部按命令输出原样记录，比如 `node: v20.11.0 (fnm)`，不要写"大概""一般"这种模糊表述。
3. **项目覆盖**（进 git，放项目根）：某项目需要特殊版本或启动方式时，在项目内再放一份，覆盖全局。
4. **反馈回写**：agent 排障成功后，让它把新发现追加到 tools.local.md。这份文件应该是越用越准的，不是写完就烂掉。

会话启动时让 agent 依次读全局、local、项目三份做合并，规则很简单：近的覆盖远的。

## 踩坑点

- **别放密钥**。tools.md 会进模型上下文，也可能被日志和快照带走。只写"从环境变量读取"，不写值本身。
- **过期信息比没有更糟**。agent 会无条件信任文件里的版本号，升级后忘了改，它会照着错信息继续调。建议配一个 check 脚本，重跑命令对一遍真实输出。
- **控制长度**。超过百行，agent 的注意力就被稀释了。只留"会导致调用失败"的信息，编码风格之类的东西别塞进来。
- **它既是数据也是指令**。markdown 里每句话都可能被当成行为依据，别在文件里写反讽、示例恶意命令这类内容。
- **Windows 单独维护 local 文件**。路径、引号、换行符差异靠约定解决不了，靠文件分开才能解决。

## 可复用建议

- 模板固定五段：Environment / Tools / Paths / Quirks / Never-do，新机器十分钟填完。
- 每条事实必须带来源命令，方便日后重跑校验。
- 把 `tools.local.md` 加进 `.gitignore`，把全局那份当代码做 review。
- 排障 SOP 的最后一行固定写上"更新 tools.local.md"，让知识回流成为流程的一部分。

## 总结

tools.md 不是什么新协议，就是一份诚实维护的环境事实清单。它的价值在于把 agent 从"每次会话重新猜你的机器"变成"直接读你写好的事实"，把团队从"各机器玄学差异"变成"分层覆盖、可 review 的配置"。搭建成本半天，收益是之后每一次工具调用的确定性。
