## 背景

Agent 接上 MCP 和插件之后，能力从“会聊”变成“会动手”：读写文件、调 API、跑命令、发消息。能力上来之后，一个绕不开的设计问题随之出现——每一步是自动执行，还是停下来问人？这个问题值得被显式设计，而不是交给模型“自觉”。

## 问题：两个失败方向

- **过度请示**：每写一个文件都弹确认，人退化成点击机器，自动化形同虚设。更糟的是，团队很快会养成闭眼点“允许”的习惯。
- **过度自主**：一次误删、一封发给客户的邮件、一笔线上扣款，事后才发现 agent“以为”这是你要的。

前者浪费人时，后者消耗信任，两边都有真实代价。

## 做法：先分类，再分档

不要问“要不要加确认”，先给所有工具调用按三个维度打分：

- **可逆性**：能否撤销？git revert 可以，删库、已发出的邮件不行；
- **影响面**：只动工作区，还是碰生产、碰外部第三方；
- **置信度**：指令是否明确，工具返回是否符合预期。

据此分三档：

1. **自动执行**：只读操作、可逆且影响小的写操作（改本地文件、查数据、跑测试）。
2. **确认后执行**：不可逆但影响有限的操作（合并分支、改配置、调付费 API）。确认消息必须带上下文：做什么、为什么、dry-run 结果、拒绝后的替代方案。
3. **默认拒绝**：对外发送、资金操作、生产变更、接触凭据。注意这不是“确认”，而是必须由人主动发起，agent 只负责准备材料。

落地步骤：

1. 权限落在**工具层**而不是提示词里：MCP 工具按读 / 写 / 外发拆开注册，高风险工具默认不进 allowlist；
2. 高风险写操作强制先 dry-run，把 diff 摘出来给人看；
3. 低风险的逐条确认改成 **plan-then-execute**：一次给出完整计划，批准后整批执行；
4. 每次自动 / 确认决策写审计日志，方便复盘；
5. 给自主执行加预算护栏：频率上限、花费上限、时间窗口。

## 踩坑点

- 只写在 system prompt 里的权限规则，在长上下文、注入或模型漂移下会被绕过。prompt 是说明，不是边界，边界必须在工具层硬性执行。
- **确认疲劳**：弹得越多，人点“允许”越不假思索。宁可提高单次确认质量，也不要增加次数。
- 无上下文的确认等于把推理甩回给人。“是否继续？”不如“将删除 3 个文件，diff 如下，回滚方式如下”。
- **假 dry-run**：预演环境与目标环境不一致，预演通过不代表能上线执行。
- 工具粒度太粗：给 agent 一个万能 database 工具，等于放弃分类。拆成只读查询与受控写入，边界才有意义。

## 可复用建议

- 一句话规则：**可逆且影响小 → 自动；不可逆或对外 → 确认；花钱、碰凭据、动生产 → 拒绝，由人发起。**
- 权限配置当代码管：进 git、走 review，和业务代码同一套流程。
- 确认消息模板化：动作 / 目标 / diff / 回滚路径，四项齐了再弹。
- 定期回看审计日志里“自动执行”的记录，出现意外就降档。权限模型是活的，跟着事故迭代。

## 总结

Agent 的权限边界不是一个开关，而是“可逆性 × 影响面 × 置信度”上的连续谱。核心就两条：低风险路径要足够顺滑，否则人会绕过你的防线；高风险路径要靠工具层硬拦，不能指望模型每次都守规矩。把问人的成本降下来，把自主干的风险兜住，agent 才敢真正放手用。
