## 背景

我们团队的服务日志散在好几个地方：nginx access log、几个业务服务的应用日志，还有 OpenClaw agent 自己的执行记录。日报长期靠人肉：登录各台机器 grep 一遍、复制粘贴、再凭感觉写段总结。写了两个月后问题很明显——慢、口径不统一、总有人忘。

这篇帖子记录我最近用 OpenClaw 搭的一条日报流水线：从原始日志到一份结构化、可推送到群里的日报。思路对其他自动化场景应该也通用。

## 问题

拆开看，"日报"其实是四个独立问题：

1. **取数**：日志格式不统一，时间窗口要对齐；
2. **聚合**：原始日志量太大，不可能直接喂给模型；
3. **生成**：要求结构稳定、字段固定，不能每天一个文风；
4. **可靠性**：流水线静默失败比"没人写日报"更危险。

## 做法

整条链路五步，一个 OpenClaw 定时任务串联：

**1. 归一化。** 小脚本按配置拉取各处日志，统一转成 JSONL，公共字段固定为 `ts / source / level / metric`。不做语义处理，只做格式收敛。

**2. 预聚合。** 进模型之前先算好：按 type 分桶的错误计数、Top N 慢请求、与前一天的差值，产出一份几 KB 的 digest JSON。这是全链路性价比最高的一步——token 消耗降一个数量级，且所有数字可复算。

**3. 结构化生成。** digest 交给 OpenClaw agent，系统提示词要求严格按 JSON Schema 输出；日期由脚本注入，不让模型自己猜"今天"；摘要文案只允许基于 digest 里的数字。

**4. 校验与兜底。** 用 pydantic 校验输出，失败重试一次；再失败就降级为模板报告（直接拼 digest），保证每天 10 点前群里一定有一条消息，哪怕是降级版。

**5. 推送与归档。** webhook 推送，digest JSON 按日期落盘。归档不为好看——它是后续周报、月报二次聚合的原料。

## 踩坑点

- **直接喂原始日志**是最早的坑：token 爆炸是次要的，主要问题是模型会"编数字"。聚合前置后这类幻觉基本消失。
- **时区**：cron 默认 UTC，日报悄悄少一小时数据，肉眼很难发现。所有时间窗口在脚本里显式指定时区。
- **字段漂移**：模型第三天开始把 `error_count` 写成 `errors`。没有 schema 校验等于裸奔。
- **不可追溯**：现在每个数字都附来源（日志文件路径 + 行号范围），验收时能对回原始日志。立规矩比写代码更重要。
- **静默失败**：加了心跳——失败也发通知。宁可群里多一条"日报生成失败"，也不要什么都没有。

## 可复用建议

- 聚合规则全部配置化（一份 YAML），新增数据源只加配置，不动流水线代码；
- 把日报 Schema 沉淀为 MCP tool 的输入输出契约，其他 agent 复用同一套校验；
- 上线前先跑一周"影子模式"：生成但不推送，人工比对无误再切换；
- LLM 只放在链路最后一环，前面全是确定性代码：模型负责"把话说好"，不负责"把数算对"。

## 总结

自动化日报的价值不在文案漂亮，而在链路扎实。取数、聚合、校验、推送都是普通工程问题，LLM 只是最后一个格式转换器。把数字的正确性交给代码，把表达交给模型——这条流水线跑了三周，日均维护成本接近零。
