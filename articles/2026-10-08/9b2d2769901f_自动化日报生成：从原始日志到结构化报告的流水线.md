## 背景

我们团队有多个长期运行的 Agent 任务和一批自托管服务，日志散落在几个地方：服务 stdout 日志、Agent 会话记录、git 提交、CI 流水线状态。之前每天下班前要花二十多分钟手工翻日志拼日报，格式还经常不统一。后来把这件事做成一条固定流水线，由 OpenClaw 的定时任务驱动，每天早上自动产出并推送到群里。跑了一个多月基本稳定，记录一下方案和踩过的坑。

## 问题

直接让 LLM“看日志写日报”有两个致命问题：

1. **上下文装不下**。一天的日志动辄几十 MB，塞进上下文又贵又容易截断，模型只能看到片断。
2. **会编数字**。让模型“总结今天发生了什么”，它会倾向补全一个看起来合理的叙述，错误次数、请求数这类精确值尤其容易幻觉。

所以核心思路是：**采集和统计交给脚本，模型只负责组织和措辞**。

## 做法

流水线分四段，每段独立、幂等：

**1. 采集（脚本，cron 触发）**
定时拉取各数据源：日志按日期切片、`git log --since` 拿提交、CI API 拿构建结果，统一落到 staging 目录，按 `YYYY-MM-DD/` 归档。

**2. 结构化（脚本，不过模型）**
把原始日志压成一份 JSON：错误总数、Top 错误类型、新增部署、关键告警、提交摘要。每个字段带“数据源健康”标记——拉取失败就标 `missing: true`，不静默跳过。这一步把几十 MB 压到几 KB。

**3. 生成（Agent + 固定模板）**
把 JSON 交给 Agent，prompt 明确约束：“只使用输入数据中的数字，禁止推断；有 missing 数据源时，对应小节写‘数据缺失’。”模板是仓库里版本化的固定 Markdown 文件，直接读进 prompt 要求逐节填充。

**4. 推送与归档（插件）**
生成的 Markdown 通过通道插件推到群，同时按日期归档保留 30 天；推送失败重试，并在下一期日报里提示。

## 踩坑点

- **时区**：cron 用系统时区，服务日志是 UTC，第一天把凌晨的告警算到了前一天。现在所有采集统一转成带时区的 ISO 时间再切片。
- **模板漂移**：早期没锁模板，模型隔三差五自创小节。模板文件进 prompt 并要求逐节填充后才稳定。
- **敏感信息**：日志里的 token、内网 IP 原样进了日报被推到群。脱敏正则必须加在结构化脚本里、推送之前——放在模型之后不可靠。
- **流水线自身静默失败**：最难排查的一次是脚本抛异常但 cron 无人知晓，群里连续三天收到“昨日无异常”。现在末端会校验 staging 目录非空、JSON 字段齐全，异常时直接推送告警。

## 可复用建议

- **三段分离**：采集、结构化、生成交界清晰，坏了能单独定位，模型环节随时可替换。
- **模板进仓库**：日报格式和 prompt 都是代码，改格式走 review。
- **数据缺失是信息**：宁可写“此源缺失”，不要让流水线假装一切正常。
- **先做最小版**：第一版只接一个日志源加 git log，跑通全链路再逐个加源。

## 总结

日报本身不值钱，值钱的是“每天必达、格式稳定、数字可信”。把统计从模型手里拿走、把模板从模型手里锁住，LLM 只做它擅长的措辞组织，这条流水线就基本不会出幺蛾子。方案没有引入新组件，全是 cron + 脚本 + OpenClaw 定时任务和通道插件的组合，一个下午能搭出最小可用版。
