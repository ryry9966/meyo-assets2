## 背景

团队里的运行数据散落在各处：定时任务的 cron 输出、Agent 的执行日志、CI 结果、服务端的错误计数。每天日报基本靠人肉翻日志、复制粘贴，写出来既不稳定也难回溯。这篇帖子分享一条我们跑了几个月的流水线：把原始日志自动加工成结构化日报，核心思路是"先确定性处理，再进模型"。

## 问题

直接用 LLM 总结日志，通常撞上三个坑：

1. 原始日志量大且噪声多，整包丢给模型，token 成本高，关键信息反而被淹没；
2. 模型输出不可控，格式飘忽，数字偶有幻觉；
3. 流水线出错往往静默失败，第二天才发现没产出报告。

## 做法

整体分四层，每层职责单一：

1. **汇聚层（采集脚本）**：cron 定时拉取各数据源，统一转成中间 JSON 格式，字段固定：时间窗口、任务名、状态、计数、异常样本（截断后的前 N 条）。
2. **规则层（纯脚本）**：去重、过滤心跳类噪声、算聚合值——错误总数、Top 变更、与前一日的差值。这一步完全不用模型，输出即可信数字。
3. **模型层（OpenClaw Agent / MCP 工具）**：把结构化 JSON 喂给 Agent，固定 Markdown 模板和输出 schema，temperature 压低，让模型只做"把数字组织成人话"，不做推断和计算。
4. **输出层**：渲染成 Markdown 推送到群 webhook 和 wiki，同时把输入快照和报告一起归档，方便事后对账。

调度上由 cron 触发一个入口脚本串起四层；模型调用通过本地 MCP server 暴露的 `daily_report` 工具完成，方便复用和替换。

## 踩坑点

- **时区**：cron 跑在 UTC，"昨天"和本地日报对不上。统一在采集层固定时区，报告头部写清时间窗口。
- **输出格式漂移**：只靠 prompt 约束不够，加了 JSON schema 校验，不合格重试一次并告警。
- **脱敏**：日志里混着 token 和内网地址，采集层统一正则替换，别指望模型帮你脱敏。
- **静默失败**：加心跳——流水线正常结束发一条成功信号，超时未收到就单独告警，和日报本身分开。
- **幻觉**：模型层禁止计算，所有数字必须来自输入 JSON，schema 里把数值字段标为"引用"而非"生成"。

## 可复用建议

- 先定中间 JSON schema，再写采集脚本，schema 就是整条流水线的契约。
- 每层用固定输入做快照测试，改动后 diff 一下，防止上游变化悄悄破坏下游。
- 把"日报"抽象成 pipeline 配置，换数据源只改采集器，规则层和模型层不动。
- 报告与输入快照一起归档，出争议时能对回原始数据。

## 总结

这条流水线的核心不是"让模型写日报"，而是拆分职责：确定性脚本负责数字，模型负责叙述。跑下来日报稳定、可回溯，维护成本集中在采集层。建议从单个数据源起步，先小步搭起来，再逐步接入新数据源。
