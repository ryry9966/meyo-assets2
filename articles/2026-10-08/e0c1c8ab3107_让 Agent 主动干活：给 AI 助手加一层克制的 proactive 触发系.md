## 背景

大多数人用 Agent 还是"拉"模式：打开终端或 IM，敲一句指令，等它跑完。这个模型稳定，但浪费了 Agent 最大的潜力——它不困、不怕重复，可以在你睡觉时干活。OpenClaw 这类可扩展的 Agent 框架加上 MCP 工具生态，其实已经具备把交互从"拉"翻转为"推"的全部零件，缺的只是一个设计良好的触发层。

## 问题

直接把事件接到 Agent 上会翻车。我们最早的 naive 版本是：cron 每小时跑一次、仓库 webhook 一有 push 就触发、某目录出现新文件就总结。三天后暴露三个问题：token 账单翻倍（大量事件根本不值得跑一次 LLM）；通知轰炸（用户开始无视推送，等于没有）；以及一次经典事故——Agent 自己写的日志又触发了文件监听器，形成自激循环，跑了一整夜。

结论：proactive 不是"加个定时任务"，而是一个需要认真设计的子系统。

## 做法

我们把触发链路拆成五段，每段职责单一：

1. **Trigger（触发源）**：cron、webhook、文件监听、IM 关键词监听。原则：这层不放任何智能，只把原始事件打包成统一格式 `{source, type, payload, occurred_at, event_id}`。
2. **Prefilter（预过滤）**：纯规则，不用 LLM。按 event_id + 时间窗去重、按阈值判断（变更超过 50 行才触发）、静默时段入队不执行。这一层干掉约 80% 的噪音，成本为零。
3. **Context Builder（上下文组装）**：把事件 + 相关状态快照拼成一次 run 的输入。关键是给"快照"而不是让 Agent 自己去查——后者意味着每个事件多跑 3-5 次 MCP 工具调用。
4. **Agent Run**：正常的 LLM + MCP 工具循环。唯一区别是 system prompt 明确告知"这是主动触发，输出精简，不要复述事件原文"。
5. **Response Router（响应路由）**：按风险分级。低风险（写日报、整理待办）直接执行；中风险（生成邮件草稿）进待确认队列；高风险（改配置、发外部消息）只通知不执行。

## 踩坑点

- **自激循环**：Agent 的输出目录必须加进文件监听器的 ignore 列表；所有 agent 产生的事件打上 `origin: agent` 标记，prefilter 直接丢弃。
- **幂等性**：webhook 重试很常见。每个主动动作必须带幂等键（从 event_id 派生），执行前查表。
- **权限隔离**：主动触发的 run 使用独立的、最小化的凭证集，不要复用交互会话的全量 token。它半夜跑挂了，不该有能力删库。
- **成本失控**：给每类触发器设每日 run 上限和 token 预算，超限自动降级为"只记录不执行"。
- **时区**：cron 统一用 UTC，静默时段按用户本地时区算，两者别混。

## 可复用建议

- 触发器按三类规划：定时类（日报、巡检）、事件类（PR、邮件）、阈值类（磁盘、错误率），别用一套逻辑硬套。
- 动作三级策略（auto / draft / notify-only）是系统的安全阀，宁可从全 notify 起步，跑稳了再逐级放开。
- 每次主动 run 落审计日志：触发源、上下文摘要、执行动作、token 消耗。一周后回看，你会砍掉一半触发器。
- 留一个总开关。proactive 系统出问题时，你要能在 10 秒内让它闭嘴。
- 从一个场景开始。我们最终保留的是"每日站会摘要"和"CI 失败超阈值才推送"两个。少而准，比多而吵有价值得多。

## 总结

Proactive 能力的核心不是让 Agent 更聪明，而是让触发更克制：规则挡噪音、快照省成本、分级控风险、审计保可控。Agent 只该在值得跑的时候醒来，醒来后做的事要让人敢不看。当推送不再被无视，"不等你开口就把事情办了"才算真正成立。
