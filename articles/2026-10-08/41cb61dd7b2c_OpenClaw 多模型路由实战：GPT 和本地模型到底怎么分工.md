## 背景

OpenClaw 的 agent 链路里，任务其实是异构的：规划、代码生成这类步骤吃推理能力；工具参数抽取、格式转换这类步骤只是“体力活”。同时团队普遍面对三个约束：成本、延迟、数据不出域。云端 GPT 级模型质量和上下文长度都好，但贵且有合规边界；本地 7B~14B 便宜、可私有化，但能力有明显天花板。多模型路由要解决的不是“哪个模型更好”，而是“哪类任务配多大智能量”。

## 问题

最常见的做法是把默认模型一配了事，结果走向两个极端：全走云端，月度账单失控；全走本地，复杂任务质量崩、工具调用格式频繁出错。路由缺位的代价，往往在上线两三周后才集中爆发。

## 做法

我们在 OpenClaw 里用三层路由，思路是先规则、后兜底、再护栏：

1. **按任务角色路由**。给 agent 定义角色：planner（规划/复杂推理）、worker（工具调用/参数抽取）、summarizer（摘要润色）。planner 固定走 GPT 级云端模型；worker 和 summarizer 默认走本地 7B，质量不达标再升级。
2. **按数据边界路由**。带 sensitive 标记的输入强制 local-only。这是硬约束，在路由层直接拦截，不靠模型自觉。
3. **兜底与预算**。云端限流/超时降级到本地；日预算超限自动 downgrade。

配置大致长这样：

```yaml
routing:
  planner: gpt-4o
  worker: local/qwen2.5-7b
  summarizer: local/qwen2.5-7b
  fallback:
    worker: [gpt-4o-mini, local/qwen2.5-7b]
  budget:
    daily_usd: 5
    on_exceed: downgrade_to_local
  rules:
    - when: input.sensitive == true
      force: local_only
```

一个简单的分工参考：

| 任务类型 | 首选 | 理由 |
| --- | --- | --- |
| 规划、多步决策、代码 | 云端 GPT 级 | 错一次的代价远大于省的钱 |
| 工具参数抽取、格式化 | 本地 7B | 量大、模式固定、可校验 |
| 摘要、改写 | 本地，失败升级 | 质量波动可接受 |
| 隐私数据预处理 | 本地硬约束 | 合规问题没有 fallback |

## 踩坑点

- **小模型 JSON/工具调用格式不稳定**。必须做 schema 校验 + 单次重试，别盲目 retry 三次，失败直接升级云端更省时间。
- **上下文长度差异**。本地 8k/32k，云端 128k，路由切换时截断历史会丢关键信息，切换前先做上下文预算。
- **fallback 死循环**。云端限流 → 本地失败 → 再打云端，要设 max_hops，否则故障时反而放大成本。
- **别用 LLM 做路由分类器**。路由判断本身要近乎零成本，规则或轻量分类头足够。
- **量化版本要重新评测**。同一个 7B，量化后工具调用准确率可能掉好几个点，上线前拿自己的评测集跑一遍，别只信榜单。
- **日志必须记录每步实际用的模型**。否则质量回退时，你根本不知道从哪查起。

## 可复用建议

- 用“角色”而不是“模型列表”组织配置，换模型只改一处。
- 维护 30~50 条覆盖典型任务的回归用例，任何路由改动跑一遍，五分钟的事，能省一整晚排查。
- 观测三件套：每步记录 model、tokens、latency，攒两周数据再谈优化。
- 隐私边界做成路由层硬约束，不要靠 prompt 里写“请注意保密”。

## 总结

模型路由的本质是按任务分配智能量：贵模型花在错不起的地方，本地模型消化量大、格式化的体力活。先规则、后兜底、再护栏，配上观测和回归评测，这套结构在 OpenClaw 里一个配置文件就能落地。不要追求一步到位的“智能路由”，先把规则路由跑稳，数据自然会告诉你下一步该优化哪里。
