## 背景

Agent 一旦接上真实世界，外部依赖就排着队来了：LLM 提供商限流、搜索引擎超时、MCP 服务器背后的 SaaS 接口直接 503。Demo 阶段没人拔网线，所以这些问题看不见；一旦任务链拉长、跑在定时自动化里，外部 API 挂掉就不是"会不会发生"，而是"多久发生一次"。

## 问题出在哪

观察下来，故障模式基本是三种：

1. **无差别重试**。把 429 限流和 400 参数错误一视同仁，要么疯狂重试把配额烧穿，要么在不可恢复的错误上空转几十轮。
2. **错误文本污染上下文**。原始异常栈、HTML 报错页被原样塞回模型，模型开始在垃圾信息上推理，轻则跑偏，重则编一个"已完成"。
3. **半完成状态**。前三步写库成功、第四步失败，没有检查点，只能从头重放，副作用重复执行。

## 做法

**第一步：错误分类放在代码里。** 在每个工具适配器里先分拣：可重试（超时、429、5xx）与不可重试（401/403/400/404）。模型不参与判断——它对"该不该重试"没有可靠概念。

**第二步：指数退避 + 抖动。** 重试上限 2~3 次，间隔指数增长并加随机抖动；写操作带幂等键，重放不会重复发邮件、重复下单。

**第三步：熔断与降级。** 连续失败 N 次后熔断该工具，冷却期内直接走 fallback：备用数据源、本地缓存，或者如实告知"该数据当前不可用"。降级路径必须提前设计好，而不是熔断后临时想。

**第四步：给模型结构化错误信号。** 工具返回统一 schema，而不是原始报错：

```json
{
  "status": "unavailable",
  "reason": "upstream_timeout",
  "retryable": true,
  "retry_after_sec": 30
}
```

配合系统提示词明确：失败时如实上报，禁止用猜测填充结果。模型负责理解失败并向用户解释，调度归代码。

**第五步：检查点。** 长任务按步骤持久化状态，恢复时从断点续跑。这是自动化场景里最容易被忽略、也最省命的一环。

## 踩坑点

- 把"失败了就再试一次"写进 prompt 让模型自己调度，常见结果是无限循环或过早放弃。
- 固定间隔、无抖动的重试：多实例同时打到同一个 API，限流雪上加霜。
- 只看 HTTP 状态码：不少接口返回 200 但 body 里是错误，漏判后脏数据直接进下游。
- 熔断后没有降级，agent 直接摆烂结束任务，体验比明确报错还差。
- MCP 工具超时和 LLM 请求超时共用一套配置，调优时互相干扰，排查半天发现改错了地方。

## 可复用建议

- 做一个统一的外部调用封装：超时、重试、分类、幂等键四处逻辑一次写好，所有插件和 MCP 工具复用，别每个插件各写一套。
- 做失败注入：mock 一个随机 500、随机超时的工具，专门跑故障演练，验证降级路径真的存在。
- 记录重试与熔断事件，事后能回答"那天任务为什么没完成"，而不是靠回忆。

## 总结

错误恢复不是给模型加一句"失败请重试"，而是代码层面的可靠性工程：分类、退避、熔断、降级、检查点。原则只有一条——模型的职责是理解失败并如实转述，代码的职责是扛住失败。两者分开，Agent 才谈得上跑在生产环境里。
