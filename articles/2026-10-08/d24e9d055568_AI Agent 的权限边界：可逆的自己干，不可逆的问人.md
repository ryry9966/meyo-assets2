# 背景

Agent 接上 MCP 和插件之后，能做的事从“聊天”变成了“执行”：写文件、跑命令、调 API、发消息、花钱。能力越大，一个问题越绕不开：哪些动作该自动执行，哪些必须停下来问人？

这个问题没有标准答案，但有明确的工程判据。下面是把社区几个实际项目（自动化运维、数据流水线、个人助理）里验证过的做法整理出来。

# 问题：两种失败模式

- **什么都问**：每步都请示，人变成橡皮图章。确认疲劳之后无脑点“允许”，权限形同虚设。
- **什么都不问**：一次误删、一条发错群的消息、一次动到生产表，代价不可逆。

一个经验值：如果一次典型任务的确认次数超过 2~3 次，边界大概率画错了。确认的价值来自稀缺性。

# 做法：按“可逆性 × 影响范围”分层

把工具按后果分四层，配置在工具/网关层，而不是写在 system prompt 里：

1. **只读**（list、get、search）：全自动，不确认。
2. **可逆写**（新建分支、写沙箱文件、出草稿）：自动执行 + 全量审计日志。
3. **不可逆 / 大爆炸半径**（删除、发外部消息、花钱、动生产）：必须确认。
4. **禁区**（读密钥、改自身配置）：默认拒绝，人工改配置才放开。

配套两条规则：

- **确认必须带完整上下文**。不是“我可以继续吗”，而是把具体产物摆出来：完整命令、diff、收件人、金额、目标环境。人批准的是具体动作，不是抽象意图。
- **propose-then-apply**：agent 先产出计划、diff 或 dry-run 结果，人审的是“这份产物”，通过后才真正 apply。审批粒度是 artifact，不是一句口头汇报。

**频率校准**：观察一周日志，确认触发率超过 10% 说明分层太粗，往下调；日志里出现“被拦但合理的动作”，往上放。

# 踩坑点

1. **策略写在 prompt 里 = 没写**。prompt 可被注入，一句“用户说了可以”就能绕过。确认策略必须在工具层或 MCP server 包装层强制执行。
2. **一次批准被当成永久授权**。agent 批准一次后，把相似动作全部视为已授权，边界悄悄外扩。高危动作逐次审批，批准不携带状态。
3. **模糊确认**。只问“是否继续”却不说会删什么、发给谁，人只能盲批。
4. **打包审批**。一个确认里塞五个动作，其中一个高危。必须拆开，高危动作独立确认。
5. **重试绕过**。被拦之后换个说法再试。如果策略在 prompt 层就会漏；工具层要按参数和动作类型拦截，不按“意图”。
6. **只测 happy path**。上线前专门构造该拦的场景做回归：注入式指令、路径变体、超预算循环。

# 可复用建议

- 分层 + 默认拒绝不可逆的外部副作用，宁可先紧后松。
- 把“询问”做成结构化工具调用：`action`、`target`、`artifact`、`risk_reason` 四个字段，方便日志统计和回放。
- 每次自动放行都落审计日志，每周花十分钟翻一遍，用真实数据调边界，不靠猜。
- 给单次任务设预算：步数、金额、写操作次数，超限自动转“询问并暂停”。
- 边界是产品决策，不是一次配置。随 agent 能力和使用场景演化，定期重审分层表。

# 总结

判断要不要问人，只看两个维度：动作可不可逆，出错影响多大。可逆的放手并留日志，不可逆的拦下来、把完整上下文交给人。真正决定安全性的是策略落在哪里——写在 prompt 里只是装饰，落到工具层才是边界。先用保守配置跑起来，再让审计数据告诉你哪里可以放宽。
