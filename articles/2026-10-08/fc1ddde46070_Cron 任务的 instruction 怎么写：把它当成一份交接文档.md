## 背景

OpenClaw 的 cron 任务，本质上是**无人值守的单轮 agent 会话**：到点触发，agent 按你写的 instruction 干活，把结果投递到指定渠道。很多人第一次配定时任务，会习惯性把平时聊天用的 prompt 直接粘进去，跑一两周后开始出现结果飘、格式乱、该报警时静默等问题。原因不在模型，而在于 cron instruction 和聊天 prompt 是两种文体。

## 问题：聊天式 prompt 在 cron 里为什么失效

聊天 prompt 有三重隐性依赖：用户在线（可以追问、纠正）、上下文共享（"按之前说的"能被理解）、结果即时可见（不满意立刻重试）。cron 任务这三样全没有——到点执行时没人回答它的疑问，会话是全新的，输出发出去就发出去了。

所以聊天 prompt 里省略掉的所有信息，在 cron 里都必须显式写出来。

## 做法：按"交接文档"五步写

1. **一句话目标 + 数据来源。** 写清做什么、用哪个工具 / MCP / skill 取数。别让 agent 自己猜用什么插件，猜错就是整场白跑。
2. **显式时间语义。** "统计昨日"要写成"统计 UTC+8 昨天 00:00 到 24:00 的数据"。cron 表达式只管触发时机，不管业务时间窗，两者必须在 instruction 里对齐。
3. **固定输出模板。** 给一个明确的 Markdown 或 JSON 结构，字段名写死。下游要解析、要做 diff，格式稳定比文笔重要。
4. **写清投递与异常。** 结果发到哪个渠道、是否 @人；数据源超时或结果为空时怎么办——建议明确写"发一条失败说明"，宁可吵闹，不可静默。
5. **先手动跑一次再上周期。** 改完 instruction 手动触发验证输出，确认无误再交给下一周期，别让定时任务替你做测试。

## 踩坑记录

- 用"帮我看看……谢谢"这类口语开头，agent 容易反问或自由发挥。开头直接写动作和范围。
- 让 cron 任务"总结咱们上次聊的"，但定时会话没有历史。需要上下文的任务，把状态放外部（文件 / 数据库），指令里写明去哪读。
- "今天 / 昨天"不写时区，统计口径能错半天。
- instruction 越改越长，新旧要求互相打架。定期 review，删掉过时条款，一个任务只做一件事。
- 在无人值守任务里安排需要确认的动作（群发、删除、下单），必须显式写权限边界：哪些事绝不做。

## 可复用建议

一条合格的 cron instruction 至少包含六段：**目标 / 数据来源与工具 / 时间范围与时区 / 输出模板 / 投递渠道 / 异常与禁止事项**。

把它当代码维护：改一处，跑一次，diff 一次输出。高频任务尤其要克制步骤数，成本和超时风险都随指令长度线性增长。

## 总结

cron instruction 不是聊天 prompt 的复制品，而是写给未来某个无人会话的交接文档。你不在场时它能靠什么运转，就把什么写进去：来源、时间、格式、去向、兜底。把这五件事写清楚，定时任务才能从"偶尔能用"变成"可以信任"。
