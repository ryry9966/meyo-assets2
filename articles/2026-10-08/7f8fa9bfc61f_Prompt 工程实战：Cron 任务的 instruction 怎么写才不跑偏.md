## 背景

OpenClaw 的 cron 能力，本质上是：到点触发一条消息，让 agent 在一个干净的会话里执行任务。很多人第一次用会把它理解成"给 agent 定个闹钟"，但更准确的类比是——**每小时派一个什么都不记得的新员工去值一次班**。他不了解你的聊天历史，也不知道之前发生了什么。

和 heartbeat（心跳，在主会话里轻量巡检）不同，cron 触发的是独立任务载荷，默认不继承上下文。我自己跑了十几个定时任务：release 监控、每日摘要、日志巡检、RSS 过滤，跑偏的方式五花八门。复盘下来，90% 的问题不在 cron 表达式，而在那段 instruction 写得不像给无人值守场景用的。

## 问题

几个典型的翻现场景：

- instruction 写"帮我看看仓库有没有更新，有就告诉我"。cron 会话里没有"我"，agent 只能猜，或者把结果回复在一个没人看的会话里。
- 没写静默条件，于是每天准时收到一条"今日无更新"，一周后受不了把任务关了。
- 写"检查一下昨天提到的那个问题"——冷启动会话里没有"昨天"。
- 工具调用失败后没有兜底，任务静默死亡。你以为在监控，其实早就断了。

核心矛盾在于：交互式会话里，上下文可以补救模糊的指令；cron 会话里没有补救机会，**instruction 必须自洽**。

## 做法：一个可复用的骨架

我现在把 cron instruction 当 SOP（标准作业程序）写，固定六段：

```text
【目标】一句话：检查 X 是否发生 Y。
【范围】只看 A 仓库 / 只读 B 目录 / 关键词限定 C，禁止额外探索。
【步骤】1) 调用工具 X；2) 对比记录文件 P；3) 生成差异摘要。
【判断】仅当出现新 release / 错误日志 ≥3 条时才输出；否则直接结束，不发消息。
【输出】发送到指定渠道/会话，格式：时间 + 变化点，5 行以内。
【异常】工具失败重试 1 次；仍失败则发送含错误摘要的消息，不要静默。
```

一条真实在跑的任务（每日 release 监控）：

```text
【目标】检查 github.com/foo/bar 是否有新 release。
【范围】只调用 repo 工具查最近 1 条 release，不做其他操作。
【判断】若 release 日期晚于 /path/last_seen.txt 中的记录，视为新版本。
【输出】发送到 Telegram 指定会话：版本号 + 一句变更摘要 + 链接。
【收尾】更新 last_seen.txt。若无新版本，直接结束，不发消息。
【异常】API 失败重试 1 次，仍失败则发"检查失败:<错误>"。
```

## 踩坑点

1. **主语和指代**。禁止"我""刚才""上面说的"。收件目标写具体渠道和会话，不要写"告诉我"。
2. **没有静默条件**。明确"无变化 → 结束不发言"，否则通知疲劳会杀死整个任务。
3. **依赖记忆**。cron 会话不继承聊天历史，关键路径、文件位置、会话 ID 要么写进 instruction，要么让它去读固定文件。
4. **时间语义**。让工具返回精确时间戳再做比较，少用"今天的""最新的"；涉及时区就写死时区。
5. **开放式任务**。"看看有什么有意思的"必翻车。限定来源、设数量上限（如最多列 3 条）、输出格式定死。
6. **需要确认的工具调用**。无人值守时会卡在确认上。监控类任务只用只读工具；写操作单独开任务，并留好回滚路径。

## 可复用建议

- 写完自检三个问题：**不看历史能不能执行？没有变化会发生什么？失败会发生什么？** 答不上来就补。
- 上线前先手动触发一次——直接把同一段 instruction 发到会话里验证，观察 2~3 个周期再放开通知。
- 多个任务共享的规则（输出渠道、格式、静默策略）沉淀到一个文件，instruction 里一行"先读 X 再执行"即可。instruction 本身保持短，规则保持可维护。
- 巡检类任务把判断阈值写成明确数字，不要写"异常情况"这种主观词。

## 总结

Cron instruction 的写法一句话就能概括：**把它当成给夜班值班员的交接单，而不是聊天消息**。目标、范围、判断规则、输出去向、异常兜底，五要素齐了，定时任务才从玩具变成基础设施。
