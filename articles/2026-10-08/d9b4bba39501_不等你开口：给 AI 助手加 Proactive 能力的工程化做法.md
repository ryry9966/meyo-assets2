## 背景

过去绝大多数 Agent 是被动问答机：你不说话，它不动。当 OpenClaw 这类框架把定时任务、Webhook、MCP 工具做成基础设施之后，"主动"从产品概念变成了工程问题——难点不再是"能不能主动找你"，而是"怎么让它主动找你但不把你逼疯"。

## 问题：Proactive 直连 cron = 灾难

最常见的第一版做法：cron 每小时推一条消息给 Agent，Agent 总结后转发给你。结果可以预期——消息轰炸、token 成本起飞，如果定时任务还挂了写权限的工具，半夜自动发邮件、建 issue 都发生过。

根因是把"主动"理解成了"自动执行"。它实际上应该拆成三件事：**感知事件、判断是否值得打扰、执行或上报**。

## 做法：三层架构

**1. 触发层（保持笨）。** cron / Webhook / 文件监听只负责产生事件，事件带去重键和时间戳，写入会话或事件队列。这一层不允许出现任何 LLM 调用。

**2. 判断层（用便宜模型）。** 挂一个小模型做门卫，依据 proactive policy（一段 system prompt）对每个事件做三选一：立即行动 / 累积进摘要 / 直接丢弃。实践中约九成事件应该死在这一层。

**3. 动作层（最小权限）。** MCP 只读工具可以直接走；写类工具强制走草稿态——Agent 把邮件正文、diff 写好存成待办，用户一键确认。确认动作也可以攒进每日晨报里批量处理。

policy 里的关键项大致是：

```yaml
proactive:
  trigger: cron(0 9 * * *) + webhook(/ci-failed)
  gate: cheap-model
  interrupt_budget: 3/day      # 每日主动打扰上限
  write_tools: draft_only      # 写操作只出草稿
  feedback: reply-to-memory    # 用户回复写入偏好
```

## 踩坑点

- **自触发循环**：Agent 改完代码 commit → CI Webhook 触发 → Agent 又处理 → 又 commit。必须给事件标记发起方，Agent 自己产生的动作直接丢弃。
- **重复执行**：定时任务重试后，通知或 issue 发了两遍。写操作要带幂等键，执行前先查。
- **通知疲劳**：初期什么都想推。实测每日主动消息超过三条，用户就会整个静默。宁可全攒进晨报，也别实时零碎打扰。
- **权限蔓延**：为省事给定时任务挂长期写权限账号。建议为它签发限时、窄范围的 token，动作默认产出"草稿"而非"结果"。
- **陈旧记忆**：Agent 基于上个月的偏好主动说话，翻车感比不说话更强。判断层引用记忆时带上时间戳，过旧默认忽略。

## 可复用建议

- Proactive 的默认姿态是"草稿 + 摘要"，不是"执行 + 推送"。信任攒起来要几周，毁掉只要一次误操作。
- 触发层永远保持笨，智能全部收敛到判断层，调策略、看日志都有单一入口。
- 每次主动行为都落日志：触发源、判断依据、做了什么。这是后续调 policy 的唯一依据。
- 给用户留短指令反馈通道（"这类别推了""这个升级处理"），让用户参与调参，proactive 就成功了一半。

## 总结

Proactive 不是把自动触发器堆得更多，而是在"事件"和"打扰"之间建一层过滤：触发层负责感知，判断层负责克制，动作层负责留后路。当你的 Agent 能连续一周忍住不说话、只在关键时刻一针见血，这个能力才算上线。
