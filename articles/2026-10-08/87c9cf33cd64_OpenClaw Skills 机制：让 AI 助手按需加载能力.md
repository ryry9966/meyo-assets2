## 背景

OpenClaw 这类常驻 Agent 网关的能力边界，基本由两样东西决定：工具（tools/MCP）和提示词。早期常见做法是把所有流程说明全量塞进 system prompt——十几个能力还行，沉淀到三四十个之后，每次对话光是"说明书"就吃掉几千 token，模型注意力也被稀释，反而容易选错工具。

Skills 机制就是针对这个问题：能力以文件夹为单位组织，系统提示里只保留一行名称和描述，正文只在模型判断"本次任务相关"时才注入。思路是渐进式披露——先看目录，再翻那一页。

## 问题：全量注入的三宗罪

1. **上下文成本**：用不到的能力也在每次请求里付费；
2. **注意力稀释**：候选越多，选择越差；
3. **不可维护**：改一段流程要动巨型 prompt，也没法单独分发。

## 做法

一个最小可用的 skill 就是一个目录加一个 SKILL.md：

```
~/.openclaw/skills/release-notes/
└── SKILL.md
```

frontmatter 只有两个字段：

```yaml
---
name: release-notes
description: 当用户要求为某个版本整理发布说明或 changelog 时使用。覆盖从 git log 提取、分类到 Markdown 排版的完整流程。
---
```

正文是给模型看的操作手册：步骤、注意事项、可引用的脚本路径。

关键在 description——加载判定完全依赖它。它不是简介，是触发条件，写"是什么"不如写"什么时候用"。写完重启 gateway（或用管理命令刷新），确认 skills 清单里条目出现，再丢一个真实任务验证：只有命中时正文才会被注入，日志里能看到加载动作。

## 踩坑点

- **描述太泛或太窄**。"辅助处理文档"等于没写；限定太死，同义表述就触发不了。建议描述里放 2-3 个典型触发说法。
- **正文贪长**。SKILL.md 是操作手册不是百科，超几百行就该拆：正文留主干，细节放 reference.md，正文里引用、用到才读。
- **多个技能描述重叠**。两个技能都说"处理日志"，模型会随机偏向一个。要么合并，要么在描述里按来源、格式划清边界。
- **依赖缺失**。技能里写了 `./scripts/diff.sh`，目标机器上却没有。技能激活不代表工具可用，部署时把依赖一起带上。
- **改了不生效**。skills 是启动时扫描的，常驻进程里改文件不会热加载，记得重启或刷新。

## 可复用建议

- **沉淀高频流程，不做一次性任务**。每周跑的发布流程值得做成 skill；一次性的迁移步骤写在当次对话里就好。
- **用 git 管理 skills 目录**，共享、评审、回滚的成本几乎为零。
- **按触发条件而非功能命名**。排查"不触发"问题时，把自己当成那个做选择的模型，通读所有 description。
- **做一次回放测试**：拿三个历史真实任务，确认该触发的触发、不该触发的不抢戏。

## 总结

Skills 的价值不在"能力多"，而在"该出现时才出现"。它把 prompt 工程从维护一篇大而全的说明，变成维护一批入口清晰的卡片——上下文省下来，命中率反而上去了。建议从重复次数最多的那条流程做起，跑两周，再决定要不要继续拆。
