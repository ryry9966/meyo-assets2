## 背景

OpenClaw 里的 Agent 默认是被动的：你发消息，它响应，然后沉寂。但很多任务本质上是周期性的——每天早上汇总邮件、盯一下磁盘水位、周一出个上周 commit 摘要。这类事靠“想起来去问”必然遗漏，靠系统 cron 又缺上下文。HEARTBEAT.md 就是补这个缺口的机制：Gateway 按固定间隔（默认 30 分钟）触发一次心跳，Agent 读取 workspace 下的这个文件，判断该不该做事，做就调工具执行，不做就回一句轻量的 HEARTBEAT_OK。

## 问题

被动模式有两个痛点：

1. 周期性任务依赖人的记忆，遗漏率高；
2. 传统 cron 只有时间触发，没有判断能力——磁盘超过 85% 才告警、只在有未读邮件时才推送，cron 做不到。

心跳的本质是“有判断力的定时任务”，但要用好它，写法和成本控制都有讲究。

## 做法

**1. 建文件。** 在 workspace 根目录创建 `HEARTBEAT.md`，Agent 每一跳会拿到它的内容作为本轮 prompt 的一部分。

**2. 写可判定的任务。** 用 checkbox 语法，每条包含触发条件、动作、推送渠道和抑制规则：

```markdown
# HEARTBEAT

- 08:00 后第一跳：汇总邮箱未读，筛出需回复项，推送到 Telegram
- 磁盘占用 > 85%：告警一次；4 小时内不重复
- 周一 08:00 后第一跳：生成上周 git 提交摘要
- 其他情况：HEARTBEAT_OK
```

**3. 调频率。** 通过 `HEARTBEAT_INTERVAL`（或对应 session 配置）控制间隔。新上线路径建议先设 60 分钟观察一周，再按需收紧。

**4. 看日志验证。** 心跳是独立 session，去日志里确认：该做事的跳是否真的执行了、不该做的跳是否安静地回了 HEARTBEAT_OK。

## 踩坑点

- **任务写得太模糊。** “帮我盯着服务器”这种条目，Agent 每跳都要重新猜意图，输出不稳定。必须写成可判定条件 + 明确动作。
- **没有去重状态。** 告警类任务很容易每 30 分钟重复轰炸。要么在文件里写清抑制窗口，要么让 Agent 把上次告警时间落盘到状态文件，跨 session 也能续。
- **重活阻塞心跳。** 心跳是串行的，一跳里跑个 10 分钟的爬虫，后续全堵。耗时任务应转后台或丢给子 Agent。
- **忽略 token 成本。** 每一跳都是一轮真实调用。清单写满一页，一个月下来费用不小——HEARTBEAT_OK 兜底不是装饰，是省钱的开关。
- **假设用户在看。** 心跳 session 里做的事，用户默认不知情，推送渠道必须在文件里显式指定。

## 可复用建议

- 把 HEARTBEAT.md 当 runbook 写：条件、动作、抑制规则三要素齐全，人能读、Agent 能执行。
- 它的价值依赖工具面：配合邮件、日历、监控类 MCP 工具才有意义，纯靠 LLM 推理的“巡检”是空转。
- 时间类任务在文件里用统一格式标注时刻，让 Agent 自行判断“这一跳是否到点”，比依赖精确调度更有弹性。
- 定期回顾日志，删掉频繁误触发或从不触发的条目——心跳清单和代码一样需要维护。

## 总结

HEARTBEAT.md 的意义不在“自动化”本身，而在于把“什么值得被主动做”沉淀成一份人类可维护的声明式清单。它不替代 cron，而是补上 cron 之上“有上下文、有判断力”的那一层。先从一两条低频任务跑通，再逐步扩展，是投入产出比最高的路径。
