## 背景

RSS 没死，只是退到了幕后。对做自动化的用户来说，它依然是成本最低、最稳定的内容获取协议：结构清晰、无算法干扰、随时可抓。但原始 RSS 的信息密度很低——标题党、跨源重复、大量条目不带正文。AI 摘要正好补上这一环。这篇记录我用 OpenClaw 定时 Agent 搭的一条管线，目标是每天早上收到一份成本可控的摘要日报，目前已稳定跑了几周。

## 问题

直接"抓到什么喂什么"会踩三个坑：

1. 很多源不带全文，摘要等于让模型基于标题编故事；
2. 同一事件在多个源重复出现，日报注水；
3. token 成本随源数量线性上涨，信噪比反而下降。

所以这条管线的核心不是"接上 LLM"，而是**先过滤、再去重、最后才摘要**。

## 做法

管线分五步，由一个 OpenClaw 定时 Agent 任务串起来：

1. **源管理**：维护一份 YAML 源清单，分两档——必读源走全文提取，泛读源只取标题和摘要。没有 RSS 的站点先用 RSSHub 之类转一层。
2. **抓取**：Agent 通过 MCP fetch 工具拉 feed，解析后统一成 `{id, source, title, link, published, content}` 结构。增量判断不用 feed 自带的 pubDate（时间戳经常不可靠），改为自己记录上次抓取时间。
3. **去重**：link/guid 哈希后写入 SQLite 的 seen 表，这是全管线唯一的持久状态。跨源重复用标题分词后的 Jaccard 相似度粗判，阈值 0.6 以上合并。
4. **摘要**：按源分批送模型，强制 JSON 输出 `{summary, keypoints[], tags[], score}`。score 让模型自评重要性，低于阈值的直接丢弃。prompt 里写死两条：只允许使用给定文本作答，禁止输出任何链接。
5. **推送**：汇总成 Markdown 日报，经 webhook 推到 IM，同时落一份本地 md 存档，方便回溯。

## 踩坑点

- **正文提取别省**。readability 类插件先清洗正文，比让模型直接读原始 HTML 又便宜又准。
- **别让模型生成链接**，幻觉率很高；链接一律从原始条目原样带过去。
- **重试要幂等**：抓取和去重放同一步，seen 表先写后推，中途崩了重跑不会推重。
- 调试期把定时换成手动触发，先跑通全链路，再上 cron。
- 中文源常见 GBK 编码和未转义的 HTML 实体，解析层统一转 UTF-8 并 decode 一次。

## 可复用建议

- 先接 10 个源跑两周，观察 score 分布再调阈值，别一上来 100 个源。
- 摘要 schema 固定后，换模型只需改一层调用，管线其余部分不动。
- seen 表加 30 天过期清理，否则越跑越慢。
- 每次运行记一行日志（源数、条目数、token 消耗），成本失控时能第一时间发现。

## 总结

这条管线没有用到任何复杂组件：一个定时任务、一个 fetch 工具、一张去重表、一段结构化输出的 prompt。它真正解决的不是"读不完"，而是"不该读的太多"。过滤和去重做扎实了，LLM 只负责最后一公里的压缩，成本和效果都可控。建议从 10 个源开始复刻，跑稳了再扩。
