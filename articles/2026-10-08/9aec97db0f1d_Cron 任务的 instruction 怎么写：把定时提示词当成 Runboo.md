## 背景

OpenClaw 的 cron 任务，本质是：到点唤醒一个**全新会话**的 agent，把一段 instruction 交给它执行。它和你平时聊天有三个关键区别——没有上下文、没人在线答疑、跑完没人立刻看。所以 instruction 的质量几乎直接决定任务成败，容错空间比交互对话小得多。

## 问题

我最早写的定时指令都是聊天腔：“帮我看看仓库有没有新 PR，有的话告诉我。”实际跑起来的结果：agent 要么报一堆无关紧要的改动，要么工具调用失败后自己编了个结论，要么把结果回复在会话里——而那个会话根本没人打开。

后来想明白了：我把 instruction 当成了聊天消息，但它其实是一份交给**不知情值班同事**的 runbook。新同事不知道你们之前聊过什么，一切都要写在纸上。

## 做法

我现在所有 cron 指令都套这个骨架：

```markdown
## 目标
一句话说清这个任务做什么。

## 环境
- 先用时间工具获取当前时间（时区 Asia/Shanghai），不要假设。
- 数据来源：MCP 工具 xxx，参数固定为 yyy（写全称，不留简称）。

## 判定规则
- "异常"定义为：xxx（具体阈值 / 字段名 / 条件，可执行）。
- 数据获取失败时：不要推测，输出"数据缺失"并发告警。

## 动作
- 有异常：按模板发到 #ops 频道。
- 无异常：不发消息，只追加一行记录到 /path/to/log.md。

## 输出模板
【Cron 摘要】时间：{now}；结论：{summary}；来源：{tool}
```

落地步骤：

1. **显式注入时间和数据源**，禁止模型凭感觉补全；
2. **判定规则写死成条件**，不写“自行判断”这种留白；
3. **写明无事时的行为**——通常是“什么都不发”，否则 agent 会硬凑输出；
4. **失败路径必须写**：工具超时、返回空、权限报错分别怎么处理；
5. **上线前手动跑一遍**：把 instruction 直接发给 agent 看输出，符合预期再启用定时；跑 3~5 天回看会话记录，迭代指令。

## 踩坑点

- **“接着昨天的来”**：cron 是全新会话，没有“昨天”。需要跨次状态的任务（比如对比上次结果），要写明状态文件路径，以及首次运行没有状态时怎么办。
- **相对时间**：“明早”“工作日”必须换成明确时区和具体日历规则。
- **一个 cron 塞多件事**：职责拆开，聚合需求由上游任务合并结果，否则输出越来越不可控。
- **没指定输出渠道**：结果留在会话里等于没跑。
- **高频 + 长指令**：token 成本直接翻倍，先低频验证，稳定后再加密度。

## 可复用建议

- instruction 存进仓库、走 review，像维护代码一样维护提示词；
- 输出固定三段式：数据摘要 → 判定结论 → 建议动作；
- 指令末尾加一段自检：“输出前确认：数据来自真实工具调用、时间正确、渠道正确”；
- 从**通知型**任务（每日摘要、异常告警）起步，跑稳之后再做**执行型**（自动整理、自动建 issue），风险完全不同。

## 总结

写 cron 的 instruction，不是 prompt 技巧问题，而是交接文档问题。把执行者当成一个不在场、不知情的新同事，把时间、数据源、判定规则、失败路径、输出渠道全部写死，任务才稳定。口诀就一句：先手动跑通，再交给时间。
