# 背景

团队里的日报大多靠人肉：翻服务日志、看 git 提交、回忆今天干了什么，再拼成一段话。问题不在"写"，而在信息散落各处、口径不统一、每天格式还不一样，事后想对比根本没法比。我们基于 OpenClaw 搭了一条从原始日志到结构化日报的流水线，跑了一段时间，把设计和踩坑记录如下。

# 问题

直接拿原始日志做日报，有三个硬伤：

1. **噪声大**。健康检查、debug 输出、重复告警占九成以上体积，真正有信息量的事件被淹没。
2. **模型直接归纳不可靠**。全量日志远超上下文窗口，截断后容易漏关键事件；不约束输出格式的话，每天日报结构都不一样，无法归档。
3. **无人兜底**。流水线挂了没人知道，第二天大家对着一篇空日报猜。

# 做法

核心原则一句话：**确定性的事交给脚本，模糊归纳才交给模型**。整条链路分五步：

1. **采集**。cron 定时触发，收集前一天的 git log、错误日志、任务状态变更。可以封装成 MCP 工具让 agent 按需调用，但调度本身别依赖 agent——cron 更可靠，agent 只做编排和兜底重试。
2. **清洗聚合**。脚本完成去重、时间戳统一时区、按错误类型聚合计数。比如 300 条同一堆栈的报错，压成"某服务某异常 ×300，首末时间、保留一条完整样本"。
3. **结构化摘要**。把聚合结果喂给模型，输出强制走 JSON schema：今日变更、异常 TOP3、待办风险、一句话总结。校验失败带着错误信息重试，最多三次。
4. **渲染分发**。JSON 按固定模板渲染成 Markdown，关键指标前置，推送群机器人；同时归档一份带日期的文件，原始日志路径作为引用附在末尾，方便回查。
5. **自监控**。每步中间产物落盘（`raw/`、`digest.json`、`report.md`），失败时发独立告警。日报可以丑，但不能静默消失。

# 踩坑点

- **时区混着算**。日志里 UTC 和本地时间都有，第一版统计区间对不上，"昨天 23 点"还是"今天凌晨"扯不清。采集层统一时区是前置条件，不是可选项。
- **去重太狠**。早期把相似告警全合并，一次真实故障被压成一行，没人注意到。改成"聚合计数 + 保留首条完整样本"后，宁可长一点也不丢现场。
- **让模型自由发挥**。没约束 schema 时它时不时输出散文，渲染脚本天天崩。上 schema 校验加重试之后才稳定。
- **日报被当监控用**。有人开始等着日报发现问题——但日报是 T+1 统计，不是告警。该走告警的走告警，日报只做回看，这个边界要在团队里说清楚。

# 可复用建议

- 先定日报 schema，再倒推每个字段需要什么数据、从哪个源采集。反过来做一定返工。
- 中间产物全部落盘。排查问题直接看 `digest.json`，不用重跑整条链路，也方便做增量对比。
- 模型只出现在"摘要"这一环：输入是聚合后的结构化摘要而非原始日志，输出是 schema 约束的 JSON。其余环节越"笨"越稳。
- 渲染和推送做成幂等，重跑不会发出两份日报。
- 插件化拆分：采集、清洗、摘要、推送各自独立，换数据源只改第一环，换推送渠道只改最后一环。

# 总结

这条流水线没有用到复杂技术，本质是把"人肉翻日志"拆成采集、清洗、归纳、渲染、分发五步，其中只有归纳需要模型参与。上线后日报从每天 20 分钟的负担变成 cron 里的一行配置，格式稳定、可归档、可对比。如果你也想做类似的事，建议从 schema 设计和中间产物落盘这两件事开始，其余都是增量。
