## 背景

Agent 已经不只是"生成文本"了。接上 shell、文件系统和几个 MCP server 之后，它能真正执行动作：改代码、装依赖、调外部 API、发消息。OpenClaw 这类可扩展 agent 的问题在于：能力边界等于你接了什么插件，但权限边界往往没人认真设计过——默认要么全问，要么全干。

## 问题

两种典型失败模式：

- **过度请示**：每一步都弹确认，用户最后变成闭眼按 y 的机器，自动化价值归零。
- **过度自主**：悄悄删了工作区外的目录、force push、给真实用户发邮件、调了计费 API。

本质原因是两个缺失：没有按"可逆性 × 影响范围"给工具分级；策略写在 prompt 里，而不是强制在工具层。

## 做法

一个可落地的方案：三色分级，四步实施。

1. **盘点工具**。把 agent 能调的所有工具列出来，逐个标注两个维度：可逆吗（能不能 undo）、影响面多大（仅沙箱 / 本地 / 外部他人 / 生产 / 涉钱）。
2. **分级**：
   - 绿灯（自动执行）：只读操作、沙箱内读写、幂等且可 dry-run 的操作。
   - 黄灯（带护栏执行）：工作区内可逆的写操作——先 commit 或打快照，执行完汇报 diff。
   - 红灯（必须请示）：不可逆操作、有外部副作用、涉及生产环境/密钥/金钱，以及一切"定时类"动作——agent 创建的 cron、延迟发送，执行时没人在看，一律按红灯处理。
3. **策略强制在工具层**。在 MCP server / 插件侧做 allowlist 和 denylist（命令前缀、目标域名、路径白名单），让 agent 跑在最小权限账号或容器里。记住：prompt 里的约束只是建议，代码里的才是边界。
4. **请示要带上下文**。不要抛一句"可以吗？"，给三件套：打算做什么、影响是什么、怎么回滚。红灯超时未确认，默认拒绝（fail safe）。

## 踩坑点

- **确认疲劳比风险更隐蔽**。问得太频繁，用户会闭眼 yes。正解不是提高问的频率，而是把动作"可逆化"——先打快照再执行，让更多动作从红灯降级到黄灯。
- prompt 里写"请你谨慎操作"没有强制力，换个模型、对话变长之后就失效了。
- **"读"也有副作用**：付费搜索 API 每次调用都计费，某些 GET 会改状态。按外部副作用和成本归类，别只看读写的字面语义。
- 会话级授权要限 scope 和时效："本次会话允许执行 shell"远比"永远允许"安全。
- 工具描述含糊，agent 就无法判断可逆性。给 MCP 工具把副作用写清楚，这本身就是权限设计的一部分。

## 可复用建议

- 把权限矩阵写成文档，随代码一起 review 和版本化。
- 新接入的工具默认红灯，观察一段时间再升级到黄/绿。
- 每个黄灯动作前自动打 checkpoint，这是整个方案里性价比最高的一件事。
- 定期翻 audit log，根据真实误操作重新校准分级。

## 总结

权限边界不是"信不信任模型"的态度问题，而是一个工程问题：给工具分级、在工具层强制执行、用可逆性减少请示次数、请示时带足上下文。目标是让绿灯跑得够快，让红灯停得住——而不是在"全自动"和"全自动确认"之间二选一。
