## 背景

如果你经常让 OpenClaw 的 agent 进工作区干活，大概率遇到过这种情况：每次新会话，agent 都像第一次来的实习生——先 `ls` 一圈，猜包管理器，猜构建命令，然后在你不希望的目录里建文件。AGENTS.md 就是为解决这个问题而存在的约定：在工作区根目录放一份 Markdown 文件，agent 每次会话启动时自动读取，作为对当前工作空间的先验说明。可以把它理解为 README.md 的镜像——README 写给人类贡献者，AGENTS.md 写给 AI。

## 问题

没有这份文件时，成本是隐性的但持续发生：

- **重复试探**：每个会话都花几轮摸索项目结构，token 和时间都在交学费；
- **错误复现**：同类问题反复出现，比如用 npm 而不是 pnpm、把构建产物提交进仓库、绕过已有 MCP 工具直接跑 shell 命令；
- **行为不可追溯**：没人说得清 agent 为什么做了某个决定，因为约束只存在于某次聊天记录里；
- **工具选择无约定**：同类能力有多个 MCP 工具时，agent 每次的选择可能都不一样。

## 做法与步骤

推荐"四段式"起步，控制在 30 行以内：

1. **结构与权限**：一句话说明目录布局，明确哪些目录可写、哪些只读（如 `vendor/`、`dist/` 不要动）；
2. **命令清单**：写出 build / test / lint 的准确命令，禁止 agent 自行猜测；
3. **禁区与红线**：不要执行的命令、不要提交的路径、不要碰的配置；
4. **工具优先级**：明确"查文档优先用某个 MCP 工具""文件搜索先于 shell 命令"这类偏好。

然后进入迭代循环：让 agent 跑一个真实任务 → 观察偏离预期的行为 → 把修正写成一条祈使句，写回 AGENTS.md。子目录有特殊约定时，再放一份精简版，agent 会级联读取。

## 踩坑点

- **写太长**：几百行的文件会稀释关键指令，实测 agent 对中段内容的遵循度明显下降，保持一到两屏；
- **写成介绍文档**："本项目采用 XX 框架"这类描述没用，要写祈使句："构建一律 `pnpm build`，不要用 npm run build"；
- **信息过期**：命令改了没同步，agent 会自信地执行错误指令，重构后顺手检查一遍；
- **与 README 冲突**：两份文件说法不一致时 agent 行为摇摆，优先保证 AGENTS.md 与实际一致；
- **写入敏感信息**：这份文件会整体进入上下文，密钥、内网地址一律不放。

## 可复用建议

- 把 AGENTS.md 当作**人工纠错的沉淀池**：每次你纠正 agent，就问一句"这能否固化成一条规则"，多数时候可以；
- 把它当代码管理：改动走 review，用 diff 审查 agent 自己提出的修改；
- 团队维护一份四段式模板，新项目十分钟起步；
- monorepo 场景用"根目录通用规则 + 子目录特化规则"分层，避免单文件膨胀。

## 总结

AGENTS.md 的本质，是把"你希望 agent 怎么干活"从聊天记录里的口头默契，变成版本化、可 review、可继承的配置。它的价值不在于一次写得多全，而在于持续迭代——agent 每犯一次错，都是一次把经验固化成规则的机会。建议每个 OpenClaw 工作区至少放一份，从 30 行开始，用起来再长。
