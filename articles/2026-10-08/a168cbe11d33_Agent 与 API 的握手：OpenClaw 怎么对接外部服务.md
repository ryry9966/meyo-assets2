## 背景

Agent 的价值不在"会聊"，而在"能做"。要让 OpenClaw 真正落到日常工作里，绕不开一件事：把它接到外部服务上——工单系统、监控平台、内部数据库、第三方 SaaS。我们最近陆续接了几个内部 API，这篇帖子把过程里的思路和坑记一笔，重点是方法论，不是某段具体代码。

## 问题

常见的错误做法有两种。一是把 API 文档整段塞进 system prompt，指望模型自己"看文档调接口"——结果是上下文爆炸、参数靠编。二是为每个服务写一次性脚本，Agent 只能调用固定动作，需求稍变就得改代码。两种方式本质上都把"握手"做成了"硬编码"：模型没有稳定的动作面，集成也没有演进空间。

## 做法

我们的方案是把每个外部服务包成一个 MCP server（或插件），分四步走：

1. **收敛接口面。** 不要照搬上游 API 的全部端点，只暴露 Agent 真正需要的动词级操作，比如 `create_ticket` / `query_status` / `add_comment`。工具越少，选择越准。
2. **写"给模型看"的描述。** tool description 不是给人读的文档，要写清楚什么时候该用、什么时候不该用、参数的合法边界。这一步的投入产出比最高。
3. **认证走环境变量或密钥管理服务**，在 server 启动时注入，绝不进配置明文，更不进 prompt。
4. **设计"可自我纠错"的返回值。** 出错时返回结构化错误加下一步提示（例如"缺少 ticket_id，请先调用 query"），模型就能自己走通重试路径，而不是原地卡死。

## 踩坑点

- **返回原始 JSON。** 一个 list 接口吐回几千条记录，一轮对话就吃掉大半上下文。后来统一做裁剪：默认分页、只返回必要字段、大结果给摘要加 ID 列表。
- **重试撞上非幂等操作。** 网络超时后 Agent 重试 create，产生重复工单。写操作必须带幂等键，或提供 `dry_run` 参数先验证。
- **描述含糊导致误选。** 两个工具都叫"查询"，模型经常挑错。改成按数据对象命名后，歧义基本消失。
- **上游悄悄改版。** 对方 API 加了必填字段，我们的 schema 没跟上，开始批量失败。给 MCP server 加了启动时 schema 校验和版本记录，问题能第一时间暴露。

## 可复用建议

- 一个领域一个 server，别做万能大杂烩；
- 只读操作放开，写操作默认 dry-run 加人工确认；
- 把工具返回值当作"给模型读的 UI"来设计，而不是当作日志；
- 日志脱敏，并保留工具调用链，方便事后回放定位。

## 总结

对接外部服务的本质，是把 REST/RPC 翻译成模型能稳定推理的动词集合。OpenClaw 提供了通道（MCP、插件机制），但握手质量取决于你怎么切接口、怎么写描述、怎么设计错误返回。做窄一点、做慢一点，Agent 的动作就会稳很多。欢迎在评论区交流你们对接时遇到的 schema 漂移和鉴权方案。
