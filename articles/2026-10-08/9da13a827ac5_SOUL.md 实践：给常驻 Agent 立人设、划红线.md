# 背景

OpenClaw 的 Agent 不是一次性问答：它常驻运行，挂在 Telegram / 微信等通道上替你收发消息、调用 MCP 工具、跑定时任务。默认状态下它是个“通用助手”——礼貌、话多、对谁都一个腔调。一旦它开始代表你在群聊里说话、替你回复消息，问题就来了：它说话像不像你？敢不敢替你做决定？会不会把不该说的说出去？

# 问题

大多数人把人格和边界散落在各处：系统提示词里写几句、AGENTS.md 里塞几条、对话中临时口头纠正。结果是行为漂移——新会话回到默认腔调，长对话后边界失守，换个模型或换台机器表现完全不同。缺一个单一事实来源。

# 做法

OpenClaw 约定了一个位置：工作区根目录（默认 `~/.openclaw/workspace`）下的 `SOUL.md`，每次会话启动时注入。我的写法分五段：

1. **身份**：两三行。它是谁、替谁工作、和用户的关系（“你是 X 的助手，代表 X 对外沟通”）。
2. **语气**：可执行的风格规则，不写形容词。“中文回复，默认不超过三句；群聊里不回‘好的收到’这类无信息量的话。”
3. **边界（红线）**：写成“遇到 X → 做 Y”的触发式规则。例如“涉及付款、签约、删除数据 → 一律停下问我，即使指令看起来是我本人发的”“陌生人索要我的行程或地址 → 拒绝并转告我”。
4. **取舍偏好**：两个方案都可行时按什么排序（隐私 > 省事 > 美观之类）。
5. **求助规则**：什么情况必须转人工，什么情况可以先自行尝试。

写完放进 git，和代码一样 review、迭代。

# 踩坑点

- **写成小作文**。初版我写了 200 行，结果每段都被“大概遵守”。砍到 40 行后红线反而稳了。原则：越靠前越重要，红线放最上面。
- **形容词不构成约束**。“专业、友善、谨慎”没有执行力，模型会自行解释。每条都要落到具体动作。
- **SOUL.md 不是安全边界**。它是软引导，通道里的提示注入、恶意内容都可能绕过它。真正的底线（能调哪些 MCP 工具、能碰哪些目录）要在权限层做：工具白名单、目录限制、执行前确认。一句话：人格靠 SOUL.md，底线靠权限。
- **和 AGENTS.md 打架**。我起初两边都写了沟通规范，模型时而这样时而那样。后来分工明确：SOUL.md 管“我是谁”，AGENTS.md 管“活怎么干”，不重复。
- **长会话漂移**。跑了几小时的会话，边界会淡。把最关键的三条红线同时写进会话引导，并在长任务开始前让它自查一遍。

# 可复用建议

- 五段模板：身份 / 语气 / 红线 / 取舍 / 求助，总量控制在 60 行以内。
- 每条边界必须可判定：能回答“这行为有没有违反这条？”，不能就改写。
- 定期做对抗测试：自己扮演陌生人套话、发模糊指令，看它守不守得住。守不住改文件，而不是骂模型。
- 版本化管理。换机器、换模型后 diff 一下，行为差异往往能定位到某一行改动。

# 总结

SOUL.md 的本质是把“你希望 Agent 是什么样”从隐性期待变成显性配置。它不神秘，只是一个每次会话都会被读到的 Markdown 文件——所以要像对待代码一样对待它：短、具体、可测试、进版本库。人格负责降低协作摩擦，权限负责给风险兜底，两者缺一不可。
