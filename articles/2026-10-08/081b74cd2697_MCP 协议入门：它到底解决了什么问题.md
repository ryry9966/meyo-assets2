## 背景

过去一年，Agent 从"会聊天"走向"会干活"，核心变化是工具调用。但要给 Agent 接上数据库、内部 API、文件系统，每家的接入方式都不一样：有的框架自定义 function calling 格式，有的靠插件目录约定，接一个新的数据源就得写一份胶水代码。

MCP（Model Context Protocol）是 Anthropic 在 2024 年底开源的协议，目标只有一个：把"Agent 怎么连工具"这件事标准化。目前主流客户端和大量服务端实现都已跟进，它基本成了这个层面的事实标准。

## 它到底解决什么问题

一句话：把 M×N 的适配问题降成 M+N。

没有 MCP 时：M 个 Agent 客户端 × N 个工具，最坏要写 M×N 份适配代码，鉴权、传输、schema 各搞一套。有了 MCP：工具方写一次 MCP Server，客户端实现一次 Host 协议，两边即插即用。

协议基于 JSON-RPC，提供三类原语：

- **Tools**：模型可主动调用的动作（查库、发消息、执行命令）
- **Resources**：可读取的上下文数据（文件、配置、文档）
- **Prompts**：预置的提示词模板

传输层常用两种：本地用 stdio（客户端拉起子进程），远程用 Streamable HTTP。

## 最小可用步骤

以 Python SDK 为例，把一个"查询工单"能力暴露给任意 MCP 客户端：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("ticket")

@mcp.tool()
def query_ticket(ticket_id: str) -> str:
    """按工单号查询状态，返回状态、负责人、最近更新时间。"""
    return db.lookup(ticket_id)

mcp.run(transport="stdio")
```

落地流程：

1. 明确一个窄场景，先只读后写。
2. 用官方 SDK（Python/TypeScript）写 Server：工具函数 + 描述。
3. 用 `mcp dev` / Inspector 单独调试，确认工具列表和参数 schema 正常。
4. 再接入真实客户端验证端到端链路。
5. 本地跑通用 stdio；要共享给团队就套一层 HTTP + 鉴权。

## 踩坑点

- **stdio 传输下 print 会毁掉会话**：stdout 被 JSON-RPC 占用，任何 print/日志打到 stdout 都会让客户端解析失败。日志一律走 stderr。
- **工具描述就是提示词**：模型靠 description 决定调不调、怎么传参。写得含糊，工具召回率和参数填对率都会崩。描述要写清"做什么、什么时候用、参数含义"。
- **工具不是越多越好**：注册几十个工具后选择准确率明显下降。按业务域拆分 Server，控制单个服务器的工具数量。
- **schema 要严谨**：可选参数、类型、默认值写清楚，否则模型会瞎填。
- **安全别裸奔**：Resource 内容可能携带注入指令；写操作务必加确认或白名单；远程部署必须加鉴权，不要把无鉴权的 MCP Server 暴露在公网。

## 可复用建议

- 把 MCP Server 当独立服务维护：独立目录、锁定依赖版本、配最小测试。
- 描述文案与代码同评审：改工具行为时同步改 description。
- 优先只读工具起步，写操作先加 dry-run。
- 调试顺序固定：Inspector → 单一客户端 → 自家 Agent，逐层缩小问题面。

## 总结

MCP 不会让模型变聪明，它只是把管道标准化了。价值在于：你为一个 Agent 写的工具，换一个 Host 还能用；团队沉淀的工具箱可以跨项目复用。如果你在维护多个 Agent 或多个内部系统，现在就值得把接入层迁到 MCP；如果只有一个 Agent、两三个工具，自定义函数调用也够用——不必为标准而标准。
