# Agent 记忆系统设计：让助手真正记住你的偏好

## 背景

LLM 本身是无状态的，所谓“越用越懂你”，全靠外挂的记忆层。OpenClaw 场景下 Agent 经常要跨会话工作：你上周说过“部署一律先走 staging 验证”，今天它就该直接遵守，而不是等你再说一遍。MCP 生态让这件事可以工程化——记忆封装成一个 MCP server，暴露读写工具，任何 Agent 都能接入。

## 问题

多数人的第一版做法很粗暴：把历史对话整段塞进 system prompt。跑两周就会撞上三件事：

1. 上下文膨胀，token 成本线性上涨，关键指令反而被淹没；
2. 偏好和临时状态混在一起，“今天不想加班”被当成永久设定；
3. 同一条偏好被改写成五种说法存进库，越攒越乱。

## 做法

我现在的方案是分层 + 结构化，核心原则：**写入收敛，读取按需**。

**第一步：分三层。** 工作记忆（当前会话上下文，不落盘）；会话摘要（会话结束时生成 3-5 条要点写入短期库，30 天过期）；长期偏好库（显式确认后才写入，永久保存）。

**第二步：固定 schema。** 每条记忆是一个结构化对象：`{key, value, scope, confidence, source, updated_at}`。scope 分 `global / project / session` 三级——“代码风格用 black”是 global，“这个仓库用 pnpm”是 project。schema 一旦固定，宁可字段少，不要临时加。

**第三步：MCP 工具面。** 只封装三个工具：`memory_write`（写入前带确认）、`memory_search`（向量召回 + scope 过滤）、`memory_update`（覆盖旧值，保留历史版本）。Agent 遇到疑似偏好陈述时先走确认，而不是自动落库。

**第四步：注入策略。** 不要全量塞 system prompt。每轮只按当前任务检索 top 3-5 条，拼进上下文，并标注来源和更新时间，让模型知道这条偏好有多“新鲜”。

## 踩坑点

- **自动抽取不可靠。** 让模型自己判断“这是不是长期偏好”，误报率很高，“我今天不想吃辣”几乎必然被错存。宁可多一次确认交互。
- **key 重复。** 同一偏好用不同措辞写了五条，召回时互相稀释。定期跑合并 job：相似度超阈值的条目交给模型或人工合并。
- **全量注入是负优化。** 实测超过 10 条无关记忆后，回答质量反而下降——噪声比遗忘更伤。
- **偏好会漂移。** 加 `updated_at` 和 `hit_count`，长期未命中的条目降权，避免两年前的旧偏好绑架现在的行为。
- **敏感信息别进库。** 写入前过脱敏规则，密钥、地址类信息直接拒收。

## 可复用建议

1. 第一版只做两件事：**写入前确认 + 读取时检索**，跑通再谈自动化。
2. scope 字段从第一天就要有，后补的代价是把全库重洗一遍。
3. 建一个 20 条左右的评测集，覆盖“应该记得 X”的典型场景，改完策略跑一遍，别凭感觉调参。
4. 记忆层做成独立 MCP server，不耦合在某个 Agent 里，换模型、换框架时记忆可以平移。

## 总结

记忆系统的本质不是“存得多”，而是“召得准”。收敛写入、结构化存储、按需召回、定期修剪，四件事做好，Agent 就会表现出稳定一致的“记住你”。剩下的都是迭代。
