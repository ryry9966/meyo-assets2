## 背景

跑过长时间自动化的人都有体会：Agent 流程里最脆的不是模型，是外部依赖。LLM 供应商 429、搜索工具超时、某个 MCP server 进程悄悄退出——这类故障在 demo 里不会出现，但在每天几百次调用的自动化任务里，一天总会有几次。错误恢复做得好不好，直接决定 Agent 是“偶尔降级”还是“整条链路报废”。

## 问题在哪

常见的失败模式有三种：

1. **裸重试**：Agent 循环里 catch 到异常就再调一次，上游已经 503，还以每秒一次的频率打过去，把限流打成封禁。
2. **静默吞错**：插件把异常吃掉，返回空列表，模型拿到空结果后一本正经地编造结论——这比直接报错更糟。
3. **无脑放弃**：一次超时就让整条工作流失败，前面烧掉的 token 和时间全部作废。

## 一个可落地的做法

按五步搭恢复机制，大部分场景够用。

**1. 错误分类。** 把异常分成可重试（超时、429、500、503）和不可重试（401、400、404、参数错误）。不可重试的错误重试没有意义，直接走失败分支。分类写成常量表，别让模型自己判断。

**2. 有界重试 + 指数退避 + 抖动。** 重试上限设 3 次，间隔 1s、2s、4s，再加随机抖动。关键是“有界”：到上限就走降级，而不是无限循环。

**3. 熔断。** 同一个 endpoint 连续失败 5 次，标记为不可用，冷却 60 秒内直接拒绝调用、不走网络；冷却结束后放一个探测请求确认恢复。注意熔断粒度是 endpoint，不是整个插件。

**4. 降级 + 告知。** 降级手段按成本从低到高：读缓存 → 换备用 provider → 把结构化错误塞回 Agent 上下文，让模型改路线或询问用户。重点是“告知”而不是指望模型自愈——返回 `{status: "degraded", reason: "search_unavailable"}` 这样的结构，比给一个空结果让模型瞎猜强得多。

**5. 断点续跑。** 任务状态持久化到本地（哪步完成、哪步在等重试），恢复后从断点继续，而不是从头再来。

## 踩坑点

- **别让 LLM 决定重试策略。** 模型对次数和间隔没有稳定概念，重试必须由代码控制。
- **非幂等操作不能裸重试。** 下单、发消息这类 POST，重试可能造成重复扣款，必须带幂等键。
- **退避不加抖动**，恢复瞬间所有任务同时打过去，雪崩二次触发。
- **熔断期间别忘了降级路径**，否则等于把本来可用的工具也关了。
- **超时要逐层设置**：HTTP 超时、工具超时、整步超时，缺一层就会挂死。

## 可复用建议

把上述逻辑做成统一的调用包装层（装饰器或 MCP gateway），所有工具调用都过这一层，错误分类、重试、熔断、结构化上报只在一处维护。再配一张“依赖健康表”，启动时和定期探测各依赖状态，Agent 调度前先查表。

## 总结

外部 API 一定会挂，问题只是何时。错误恢复的目标不是消灭故障，而是让故障的影响有边界：可重试的有界重试，不可恢复的快速失败，不可用的熔断隔离，全程结构化告知。做到这四点，Agent 才能从“挂了就废”变成“挂了能绕”，自动化任务才敢放到无人值守的环境里跑。
