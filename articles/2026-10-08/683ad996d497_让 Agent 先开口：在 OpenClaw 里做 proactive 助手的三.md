# 背景

绝大多数 AI 助手的交互模式是"你问它答"，典型的 reactive。但很多高价值场景——日历冲突、CI 失败、到期事项、日志异常——用户根本不会主动去问，等问到时损失已经发生。OpenClaw 这类常驻 Agent 天然具备常驻进程、cron/heartbeat、工具调用和消息通道，做 proactive 的基础设施是现成的，缺的其实是触发与约束的工程设计。

# 问题

把 agent 从"被动应答"改成"主动出手"，要回答三个问题：

1. **怎么知道该出手**——触发源从哪来；
2. **怎么判断值不值得打扰**——决策门控放哪一层；
3. **怎么保证出手是安全的**——执行边界怎么划。

这三个做不好，proactive 会退化成定时群发。

# 做法

我们的最小闭环分三层：

**感知层**：定时场景用 cron/heartbeat 唤醒，事件场景用文件监听和 webhook。关键是"先 diff 再唤醒"——文件哈希、时间戳、游标（比如上次读到的 issue 编号）存本地，没变化就不进 LLM，纯休眠。

**判断层**：唤醒后先跑一段廉价判断：事件是否满足触发规则（阈值、关键词、状态变更），再决定走静默记日志、进每日摘要、还是立即通知。规则放配置文件，不写死在 prompt 里。

**执行层**：动作分级。只读动作（查询、汇总、生成草稿）直接执行；写动作（改文件、发消息、调 MCP 工具改状态）默认 dry-run，输出"我打算做什么"，确认后才落盘。每次动作带幂等键写入 audit log，防止 heartbeat 重复触发同一件事。

一个实际例子：每天早八点扫一次日历、issue 列表和昨夜告警，聚合成一条摘要推送；某定时任务连续失败两次时，自动拉日志做归因，把根因和修复建议打包推出来。

# 踩坑点

1. **心跳太密**。早期 5 分钟全量唤醒一次，token 账单一周翻倍。改成变化检测 + 指数退避后，成本降了一个数量级。
2. **无状态重复**。heartbeat 唤醒时上下文为空，agent 第二天把昨天的事又干了一遍。解法是持久化"已处理事件表" + 幂等键。
3. **打扰失控**。接了五六个 hook 各自发消息，用户两周就把通知静音了。收敛到单一通知通道 + 三级分级（静默/摘要/即时）后，连续两周没被点开的消息类型自动降级。
4. **自作主张**。agent 拿到写权限后曾"顺手"重构了一个脚本。之后所有写操作必须过确认门，白名单外一律 dry-run。

# 可复用建议

- 把 proactive 拆成"感知—判断—执行"三段，每段独立可测，别把规则糊在 prompt 里；
- 一切主动触发必须有幂等键和审计日志，这是排障的生命线；
- 默认沉默原则：没有值得说的就闭嘴，每日摘要兜底；
- 把打扰当预算管理：用打开率/处理率做指标，自动升降级；
- 从一条最小闭环起步（比如每日摘要），稳定运行两周，再放开下一种触发源。

# 总结

proactive 的目标不是让 agent 话更多，而是让它在正确的时间做正确的事，其余时间保持安静。工程上核心就三件事：便宜可靠的触发、有门槛的判断、有边界的执行。OpenClaw 的常驻进程 + cron + MCP 组合足够搭出这套闭环。建议从每日摘要这种低风险场景开始，逐步交出自主权——每一步都留确认门和日志。
