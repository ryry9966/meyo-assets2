# 背景

OpenClaw 生态里最常见的自动化链路之一：定时任务触发 Agent → 汇总/生成内容 → 通过 MCP 插件发到社区（论坛、群、Discussions）。这条链路一个下午就能跑通，但大多数这类机器人活不过两周：要么被静音，要么被管理员请出去。原因通常不是内容太差，而是节奏错了。

# 问题：三种"机械感"

1. **时间机械**：cron 固定整点发，每天 3 条、间隔精确 8 小时。人看两天就能背出它的时刻表。
2. **体量机械**：不管社区当天热闹还是冷清，输出恒定。没人说话它也说，刷屏的时候它跟着刷。
3. **形态机械**：同一套模板、同样的开头句式、同样的长度。人写东西有波动，机器人没有。

严格说这不算"被识破"的问题，而是骚扰问题。节奏失控的自动发帖，本质上是对社区带宽的 DoS。

# 做法

核心思路：把"生成"和"发布"拆开，中间加一层发布队列和节奏控制器。

1. **生成不入库，入库才可发**。Agent 产出先写进待发队列（一张 SQLite 表就够），由独立 worker 按节奏消费，生成失败和发布失败互不影响。
2. **三层节奏参数**：
   - 日上限：按社区规模定，百人级群一天 1–2 条封顶；
   - 最小间隔：两条之间至少隔 4–6 小时；
   - 抖动：在目标时间窗内随机偏移 ±30–90 分钟，避免整点；
   - 静默时段：按**社区所在时区**（不是服务器 UTC）设定夜间不发；
   - 突发抑制：token bucket，防止某天内容多时一口气倾泻。
3. **内容质量门，比时间控制更重要**：
   - 去重不能只做精确匹配。LLM 会把同一件事换措辞发三遍，要用 embedding 相似度或 simhash 设阈值拦截；
   - 设"价值下限"：没有新信息、没回答问题，直接丢弃。**不发言永远优于说废话**；
   - 模板轮换要克制，2–3 套就够，轮换太频繁反而怪。
4. **人在回路分层**：低风险日报/摘要可全自动；@人、回复争议、首次进入新频道，先进草稿队列等人点一下发送。
5. **身份透明**：固定一个账号、固定一条署名。不要做小号矩阵，不要伪装个人口吻——那不是节奏问题，是诚信问题，且一定翻车。

一个最小配置：

```yaml
pacing:
  daily_cap: 2
  min_interval_hours: 5
  jitter_minutes: [15, 75]
  quiet_hours: "23:00-08:00"
  timezone: "Asia/Shanghai"
dedup:
  simhash_threshold: 0.85
fallback:
  on_error: drop_and_log   # 绝不自动重试发送
```

# 踩坑点

- **抖动分布**：别把随机偏移套死在整点上，要整个窗口随机，否则仍能看出"每小时一发"的痕迹。
- **时区坑**：服务器是 UTC、社区是中国时间，静默时段写错等于白设。
- **重试风暴**：发帖失败后无脑重试，故障恢复瞬间连发十几条重复帖。发布必须带幂等键，失败宁可丢弃并记日志。
- **去重只查文本不查语义**，换皮重复帖照样出去。
- **参数照抄别人**：千人论坛和二十人群的合理上限差一个数量级。

# 可复用建议

- 用两个指标验收节奏：**回复率**（自动帖获得真实回复的比例，应稳定大于零）和**打断率**（被删除/静音/投诉次数，应趋近于零）。
- 每周人工翻一遍机器人发帖记录，比任何自动监控都有效。
- 节奏参数做成配置而非硬编码，不同社区用不同 profile。

# 总结

"不像机器人"的关键，不是把机器人伪装成人，而是先把机器人身份讲清楚，然后在行为上克制：少发、错峰、带抖动、没料就不发。节奏控制本质上是限流和尊重。做到这些，社区不但不会排斥它，反而会把它当成一个守规矩的成员。
