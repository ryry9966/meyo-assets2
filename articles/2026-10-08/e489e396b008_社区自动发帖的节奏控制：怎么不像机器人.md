## 背景

我们在社区跑了一个基于 OpenClaw Agent + MCP 插件的自动发帖流程：定时抓取群内讨论，生成日报/周报，再通过 MCP 工具发回论坛。跑了两周，有成员直言“这 bot 一到整点就发，比闹钟还准”。这不是内容质量问题，是节奏问题。

## 问题：机器味从哪来

复盘下来，“像机器人”的观感主要来自四个信号：

- **间隔过于规律**：cron 固定整点触发，发帖时间戳几乎可以预测；
- **突发连发**：重试或队列积压恢复后，几条帖子在同一分钟内出现；
- **活跃时间错位**：凌晨三点照发，社区没人在线，纯噪音；
- **对现场无感知**：人类刚讨论完同一话题，bot 又发一遍高度重复的内容。

这些信号叠加后，即使内容本身有价值，也容易被当作垃圾源，严重的会被管理员限流。

## 做法

1. **基准间隔 + 抖动**。放弃裸 cron，改为“期望时间 ± 随机抖动”。抖动比例建议 20%–35%，且不要用均匀分布，避免“随机得很均匀”。
2. **贴着社区活跃曲线发**。先离线统计目标频道的历史消息时间分布，得到一条活跃曲线；发帖时刻从活跃窗口内加权采样。白天活跃的社区，就别在深夜发。
3. **队列 + 合并 + 每日上限**。所有待发内容先进队列，设 `daily_cap`（如 3 条/天）和合并窗口：窗口期内产生的多条事项合成一条摘要。宁可少发，不可刷屏。
4. **发帖前看现场**。通过 MCP 的频道读取接口拉取最近 N 条消息，做相似度比对：如果有人刚发过相似内容，本次任务降级为跳过或延后一个周期。
5. **幂等与退避**。每次发帖带幂等键，发送前核对最后一条已发消息，防止重试导致重复；收到限流或警告信号后进入指数退避，最短冷却 24 小时。

一段可复用的配置骨架：

```yaml
schedule:
  base_interval: 4h
  jitter_ratio: 0.3
  active_hours: ["09:00", "22:00"]   # 按社区时区
  daily_cap: 3
  merge_window: 30m
guard:
  context_check: last_20_messages
  dedupe_similarity: 0.85
  idempotency_key: digest_date_topic
  backoff_on_warning: exponential_min_24h
```

## 踩坑点

- 抖动用均匀随机，仍会出现“平均每 4 小时一条”的规律感，改用活跃曲线加权采样更自然。
- 时区错误：调度器跑 UTC，社区在 UTC+8，结果天天凌晨发帖。上线前先打印一次实际触发时间，人工确认。
- 断网恢复后的惊群：重连瞬间队列全量释放。队列释放本身也要限速，比如每条间隔 2–5 分钟。
- 只控节奏不控内容：模板句式每次一模一样，间隔再随机也像机器。开头和结构保留少量变化，但别为变化牺牲可读性。
- 明确一条边界：目标是“节奏像人”，不是“伪装成人”。账号该标 bot 就标 bot，节奏控制是社区礼仪，不是欺骗手段。

## 可复用建议

- 三个数字先定死：`daily_cap`、`jitter_ratio`、`merge_window`，其余参数围绕它们调。
- 监控两个指标：发帖间隔分布（画直方图，看是否过度集中）和人工干预次数（被删帖/被警告）。
- 给管理员留一个“一键静默”开关，比任何智能策略都管用。
- 新策略先在低价值时段灰度跑一周，再全量。

## 总结

自动发帖的“机器味”，本质是调度层缺乏对社区节奏的建模。把固定 cron 换成抖动 + 活跃曲线采样，加上队列合并、上下文检查和幂等退避，观感会有明显改善。核心原则只有一句：**发的频率和时机应该由社区的活跃状态决定，而不是由你的 cron 表达式决定。**
