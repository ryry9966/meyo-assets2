## 背景

OpenClaw 的 agent 主循环并不绑定单一模型。配置里可以同时挂云端（GPT-4o / o 系列）和本地推理端点（Ollama、vLLM、llama.cpp server），再配合多 agent 结构，天然支持"不同任务走不同模型"。但官方只给了能力，没给策略——怎么分，得自己定。

## 问题

社区里的典型场景是个人自动化：24 小时挂着，处理消息分类、日报汇总、代码草稿、MCP 工具编排。全部走 GPT，账单和隐私都难受；全部走本地，7B/14B 模型在多步工具调用上掉链子，agent 循环经常产生错误调用甚至卡死。核心矛盾是：**多数流量其实不需要强模型，但少数关键步骤不能省**。

## 做法

我目前的分层策略，供参考：

1. **按任务类型静态分派**：起两个 agent——主 agent 挂 GPT，负责规划、代码、复杂 MCP 编排；副 agent 挂本地 Qwen 14B（Ollama），负责消息分类、摘要、格式化、定时巡检这类高频轻任务。
2. **敏感数据强制本地**：涉及本地文件路径、密钥、聊天记录的处理，规则里直接写死走本地，不做动态判断。
3. **升级式兜底**：轻任务先走本地，输出做轻量校验（JSON 可解析、工具参数合法）；失败或结构异常就带上原上下文升级到 GPT 重跑一次。
4. **记录路由日志**：每次调用记下模型、token 数、耗时、是否升级。跑一周再调规则，比拍脑袋准得多。

## 踩坑点

- **本地模型的工具调用格式不一致**：Ollama 的 function calling 和 OpenAI schema 有细微差异，嵌套参数容易崩。MCP 工具描述要精简，参数尽量扁平。
- **上下文窗口差一个量级**：本地 8k/32k，GPT 128k+。长会话中途切模型会截断历史，升级重跑前记得先做摘要压缩。
- **别只按 prompt 长度路由**：短 prompt 也可能是难任务（比如一段很短的代码调试）。长度只能当辅助信号，不能当主信号。
- **路由器本身有成本**：用小模型当智能路由，多一次往返；关键词规则又太脆。先静态规则跑起来，别过早优化。
- **流式行为不同**：本地端点首 token 快、长输出慢，超时和重试策略要分开配。

## 可复用建议

- 先用静态规则 + 双 agent 起步，跑一周看日志再优化
- 维护一个 20~30 条真实任务的评测集，每次改路由规则都跑一遍
- 默认"便宜优先、失败升级"，而不是反过来
- 给每类任务写一行"模型卡"：谁负责、为什么、失败谁接

## 总结

多模型路由的价值不在省几个 token，而在于把**关键路径的可靠性**和**高频任务的低成本**分开处理。OpenClaw 已经把管道铺好了，策略从简单开始、用日志说话，比一上来就搞复杂智能路由靠谱得多。
