## 背景

Agent 跑起来之后，token 消耗的大头往往不是那几步“高光推理”，而是海量的意图分类、槽位抽取、结果摘要、格式转换。这些活儿 GPT 干得很好，但用大炮打蚊子，成本和延迟都难看。另一边，本地模型（Ollama/vLLM 跑 7B 级开源模型）便宜、数据不出机器，但一上复杂任务就容易翻车。OpenClaw 的多模型路由解决的就是这个矛盾：把请求按规则分发到合适的后端，而不是全走一条道。

## 问题

实践中常见两个极端：一是“全云端”，月底账单劝退；二是“为省钱全本地”，重试率暴涨、任务频繁失败，最后人工兜底的时间比省下的钱贵得多。真正的难点不是配路由，而是判断标准——什么信号说明这个任务该走云端？

## 做法

我的做法分四步：

1. **给任务打标**。在 agent 的子任务定义里区分类型：classify / extract / summarize / format 归为轻任务，plan / code / multi-tool 编排归为重任务。标签不准，后面全白搭。

2. **三层规则**：
   - 数据层：带密钥、客户隐私的工具调用强制走本地，或先脱敏再出网；
   - 成本层：单次预算超限或触发限流时自动降级到本地；
   - 质量层：本地输出结构化校验失败或置信度低于阈值，升级到 GPT 重试一次。

3. **用 fallback 链，不要二选一**。默认本地先行，云端兜底，路由配置大致长这样：

```yaml
routes:
  - match: { task: [classify, extract, summarize] }
    target: local/qwen-7b
  - match: { task: [plan, code] }
    target: cloud/gpt
  - default: local/qwen-7b
    on_fail: escalate: cloud/gpt
```

4. **观测两周再调**。记录每次调用的命中规则、模型、耗时、重试次数，看分布说话，不要拍脑袋改规则。

## 踩坑点

- **长上下文误伤本地模型**：本地模型窗口小，工具返回的大段 JSON 塞进去直接截断，输出质量差被误判成“本地模型不行”。先压缩、截断，再路由。
- **校验过严导致路由失效**：JSON 校验一票否决，本地稍有格式瑕疵全被升级到云端，路由形同虚设。校验要分级：结构错误才升级，风格问题放行。
- **本地“免费”是假象**：显存占满挤掉同机的向量库，并发一高就排队，电费和机器折旧也要算进成本。
- **prompt 不通用**：同一模板在两个模型上表现差异很大，对比测试要按模型各维护一版，否则结论不可信。

## 可复用建议

- 先跑一周全云端基线，拿到每个任务的真实 token 和成本，再决定哪些下放本地——顺序不能反。
- 路由决策必须写进日志（命中哪条规则、为什么升级），事后能复盘。
- 用“校验通过率 + 平均重试次数”做本地模型的健康指标，跌破阈值自动回切云端，别硬扛。
- 很多“本地模型不行”其实是任务没拆细。先拆任务、收敛 prompt，最后才考虑微调。

## 总结

多模型路由不是省钱技巧，而是把“任务难度分级”工程化。判断顺序记住三步：先看数据敏感性，再看任务难度，最后才算成本。规则宁少勿多，每条都要可解释、可观测。路由配好后，成本降下来只是结果，系统可控才是目的。
