# 背景

OpenClaw 的 Agent 是长期运行的：跨会话、跨天、跨设备。但模型上下文并不持久，每次新会话，Agent 对你的认知基本归零。workspace 里的引导文件解决了另一半问题：SOUL.md 定义"Agent 是谁"，而 USER.md 定义"你是谁"。这份文件会在每次会话启动时注入上下文，是唯一稳定承载用户侧信息的位置。

# 问题

没有 USER.md 时的典型症状：

- 每个新会话都要重复自我介绍：称呼、时区、技术栈；
- 沟通风格漂移，有时啰嗦客套，有时过度简洁，全看模型当天的心情；
- 给出的命令不适用你的环境——它不知道你本地是 macOS、生产在 Ubuntu；
- 偏好靠单次口头约定，下次会话就丢。

本质是：用户侧的稳定上下文没有被持久化、结构化，Agent 每次都在重新猜。

# 做法

**第一步：建文件，分五区。** 在 workspace 根目录创建 USER.md：

```markdown
# 基本信息
- 称呼：老周
- 时区：Asia/Shanghai，工作日 10:00–19:00 在线
- 语言：中文交流；代码与提交信息用英文

# 环境
- 日常机：macOS + Docker；生产环境 Ubuntu 22.04
- 技术栈：Python (FastAPI) / TypeScript

# 偏好
- 直接给结论，先答案后解释；不要过度道歉
- Python 一律带类型注解，ruff 做 lint

# 边界
- 不要未经确认执行 git push
- 23:00 后不触发任何通知类任务

# 当前
- 主线：数据管道重构，目标月底下线旧 job
```

**第二步：区分稳定区和动态区。** 前四区几个月不动，"当前"区每两周扫一眼即可。

**第三步：让 Agent 参与维护。** 会话中直接说"把这条偏好写进 USER.md"，比手写省力。Agent 有 workspace 写权限，这是原生能力，不需要额外工具。

**第四步：用 git 管。** USER.md 本质是配置文件，像 dotfiles 一样对待，改动可回溯、可回滚。

**第五步：验证加载。** 新会话问一句"你现在对我的了解有哪些"，确认读的是最新版本、没有漏项。

# 踩坑点

1. **写太多。** USER.md 每个会话都进上下文，是持续性 token 开销。超过一屏就该删。判断标准：这一行会不会改变 Agent 的行为？不会就删。
2. **写感受不写事实。** "我喜欢高质量的代码"没有信息量；"提交信息用英文、50 字符以内"才可执行。
3. **敏感信息。** 密钥、证件号、详细住址不要写——它会被注入每一次 prompt，还可能随 workspace 同步。
4. **信息过期。** "当前"区三个月不更新，Agent 会拿废弃项目当上下文做决策，比没有更糟。
5. **与记忆抢职责。** 稳定事实归 USER.md，事件性记忆归 memory 文件。同一事实两处出现且值不一致，Agent 行为会明显不稳定。

# 可复用建议

- 把 USER.md 当"给 Agent 的接口文档"写，不是日记。读者是模型，不是未来的自己。
- 控制在 60 行以内，每季度审一次 diff，删掉不再改变行为的条目。
- 团队场景可派生一份同结构的 ROLE.md 给工作型 Agent，职责分离更清晰。
- 冷启动别留空文件：先填时区、语言、技术栈三行，用一周再补，比一次性憋一份全的更实际。

# 总结

USER.md 的价值不在文件本身，而在于把用户侧上下文从会话级提升到持久级。小而准、可执行、常更新——做到这三点，Agent 的输出稳定性会有可感知的提升。它大概是最便宜的 Agent 优化手段之一：半小时的写作，换来之后每个会话的少废话、少猜错。
