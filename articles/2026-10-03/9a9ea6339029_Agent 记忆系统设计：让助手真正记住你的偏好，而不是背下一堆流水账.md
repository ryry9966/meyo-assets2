## 背景

LLM 本质上是无状态的。上周你告诉助手“commit message 用英文、别加 emoji”，这周开新会话它就全忘了。对 OpenClaw 这类常驻自动化 agent 来说问题更明显：它每天替你跑任务、回消息，每次都得从头交代一遍偏好，既烦人也容易漏。

context window 不是解药。历史全塞进去，token 成本线性上涨，中间内容还会被模型“看漏”。记忆系统得自己设计。

## 问题：三种常见错误做法

1. **全量写进 system prompt**：偏好一多，prompt 膨胀、条目互相冲突，模型反而抓不住重点。
2. **全量进向量库**：检索噪声大，“用户喜欢简洁回复”和“用户昨天随口提了部电影”权重一样，召回一堆无关内容。
3. **让模型自由发挥地“记住”**：没有结构、没有审计，记错了你都不知道，排查起来像玄学。

核心矛盾在于：记忆要够小（能稳定注入 prompt）、够准（召回了就是对的）、可审计（错了能改能删）。

## 做法：分三类，三条路径

先把记忆拆成三类，存储和读写策略分开：

- **偏好记忆**：稳定、低频变化，如代码风格、语气、常用技术栈。用结构化存储（一个 JSON / SQLite 一张表就够），不要用向量。
- **情景记忆**：具体事实和事件，如“项目 X 的部署脚本在 Y 目录”。向量检索，按需召回。
- **会话状态**：只在当前任务内有意义，放内存，会话结束丢弃或摘要归档。

实现上我把它做成一组 MCP 工具：

1. **读取**：偏好记忆整体注入 system prompt（很小，通常不到 1KB）；情景记忆由 agent 通过 memory_search 按需查询。
2. **写入**：每次会话结束后跑一遍轻量提取 pass，用便宜模型从对话中抽出“值得记的偏好变更”，输出结构化 diff（key、旧值、新值、来源、置信度）。不确定的标记待确认，不直接覆盖。
3. **冲突与更新**：新值覆盖旧值但保留历史，带 updated_at。当前会话里用户的明确指示永远优先于记忆——这条写进 system prompt，明确优先级。

## 踩坑点

- **过度捕获**：不设门槛的话，模型会把“用户三点说了句 hi”也记下来。提取 prompt 里必须给硬标准：可复用、跨会话有效才记。
- **记忆腐化**：半年前你用 Vue，现在换 React 了，旧记忆还在生效。除了时间戳，最好对“低置信 + 长期未确认”的条目做再确认提示。
- **黑盒记忆**：最坑的一条。agent 行为变怪了，你不知道是哪条记忆导致的。解法很土但有效：所有写入留变更日志，给个 `/memory` 命令让用户随时查看、编辑、删除。
- **只做向量检索**：偏好是典型的键值型知识，“commit message 用英文”用 embedding 搜纯属浪费，直接按 key 读。
- **隐私**：记忆文件基本是明文。至少支持一键清空和按条删除，敏感字段考虑加密。

## 可复用建议

- 先用一个 JSON 文件起步，覆盖八成需求，跑顺了再上向量库。很多人一上来搭 RAG 全家桶，其实偏好记忆根本不需要。
- 每条记忆必须带来源：哪次会话、哪句话提取的。没有 provenance 的记忆没法审计。
- 写个回归测试：同样的提问跨会话问三次，看偏好是否稳定生效。记忆系统没有测试，改一处崩一处。

## 总结

记忆系统的本质不是“存得多”，而是“注入得准、错了能改”。结构化偏好 + 按需召回情景 + 可审计的写入路径，这套组合在 OpenClaw 插件里百来行代码就能落地。先让它可靠地记住三五条核心偏好，比堆一万条模糊记忆有用得多。
