## 背景

跑自动化任务的人和交互式用户最大的区别是：你不在场。定时任务、Agent 重规划、MCP 工具重试、webhook 重投递——这些场景里，“同一段逻辑被执行两次”不是异常，而是常态。网络超时后客户端重试、cron 到点触发但上一轮还没跑完、Agent 判断上一步失败后重新规划，都会造成重复执行。幂等性（idempotency）就是保证“执行一次和执行多次，最终状态一致”的工程手段。

## 问题

读操作天然幂等，麻烦全在写操作。典型翻车现场：

- 定时任务给群发了两次同一份日报；
- Agent 重试时重复创建了工单、文件或数据库记录；
- 部署脚本重复执行，把 append 型配置写了三遍。

根因都一样：操作被建模成“做一件事”（create / send / append），而不是“达到某个状态”（ensure / set / put）。前者重复执行必然叠加副作用。

## 做法

给写操作加幂等键，是最通用的一层防护。步骤：

1. **区分操作类型。** 只读的直接放过；有副作用的进入下一步。
2. **设计幂等键。** 键要能从任务上下文确定性推导，比如 `daily-report::2025-01-15::group-a`——同一逻辑任务 + 同一目标 + 同一周期，键相同；换个周期，键不同。
3. **选一个支持原子操作的存储。** SQLite 的唯一约束、Redis 的 `SET NX`、甚至文件锁都行，关键是“抢占”必须原子。
4. **先抢占，再执行。** 执行前先写入键（带状态字段 pending / success / failed），写不进去说明已有人在跑或已跑过，直接退出。
5. **执行完回写终态。** 失败要回写 failed 并标记可重试——这一步最容易偷懒。

对能改造的操作，尽量改成声明式：`upsert` 代替 `insert`，`set-config` 代替 `append-config`，“确保文件内容为 X” 代替 “往文件追加 X”。让操作本身幂等，比外面包一层去重更可靠。

## 踩坑点

1. **先查后写的竞态。** 两个 worker 同时查“键存在吗”，都不存在，然后都执行。查和写必须合成一个原子操作。
2. **键粒度不对。** 太粗（只有任务名），合法的重跑被挡掉；太细（掺了随机 id），每次生成的键都不同，去重完全失效。幂等键必须来自稳定的业务语义，不能用时间戳或随机数。
3. **成功标记太早。** 先标 success 再执行，中途崩溃就出现“记录说成功、实际没做”的幽灵任务。反过来，“做了但没来得及标记”也无法彻底避免，只能靠对账，或按业务分级容忍重复——消息重发一条通常可接受，订单重复一笔不可接受。
4. **键只增不减。** 没有 TTL 或清理策略，记录表会无限膨胀。
5. **层级错位。** Agent 在规划层做了重试去重，但 MCP 工具内部没有幂等保护，一次重规划照样打出两次写请求。防护要做在离副作用最近的那一层。

## 可复用建议

- 把“幂等执行器”封装成公共插件或工具函数：输入 task_id 和执行函数，内部处理抢占、状态回写、失败释放，所有定时任务统一走它。
- 每个定时任务必须有稳定的 task_id 和执行日志表（键、状态、时间、错误信息），排障时这就是时间线。
- 优先利用天然幂等：目标状态的存在性检查（文件在不在、记录有没有）本身就是最便宜的幂等手段，能靠外部状态判断的，不要引入额外存储。
- 为重复留后路：设计时问一句“这条消息发两次会怎样？”，把不可接受的副作用收敛到少数几个点，重点防护。

## 总结

无人值守的自动化里，重复执行是常态而非异常。幂等性的核心就三件事：稳定的幂等键、原子的抢占、准确的终态回写；再进一步，把操作本身改造成声明式。做完这些，重试、超时、重规划就都不再让人心慌——因为多跑几次和跑一次，结果一样。
