## 背景

在 OpenClaw 这类自动化场景里，「同一个任务被执行多次」不是异常，而是常态：

- LLM 调用工具超时后自动重试；
- 定时任务重叠触发，上一轮没跑完，下一轮 cron 已到；
- Agent 重新规划后再次调用同一个 MCP 工具；
- 人肉补跑历史任务。

调度层、网络层、模型层都会制造重试。区别只在于：你的任务是「重复执行也无害」，还是「跑两次就出事」。

## 问题

非幂等操作的典型翻车现场：

- **追加写文件**：每次执行 append 一段摘要，重试后出现两份相同内容；
- **创建类动作**：Agent 调 `create_issue`，超时重试，issue 建了两个；
- **发通知**：本地状态显示「待发送」，实际已发出，补跑又发一遍。

根因相同：副作用依赖于「这是第几次执行」。

## 做法

几个实践中够用的手段，按成本从低到高：

1. **确定性输出路径**。不要 append 到 `reports.md`，而是写 `reports/2025-05-20.md`。同一天执行多少次都是覆盖同一份文件，天然幂等。
2. **用业务键做幂等键**。给每次调度生成稳定 ID：`hash(任务名 + 计划执行日期)`，而不是 `hash(任务名 + 当前时间)`。执行前先查本地状态表，处理过就跳过。
3. **改写为 upsert 语义**。自定义 MCP 工具时，尽量提供「存在则更新，不存在则创建」的接口。插件层也可以包一层：先查状态存储（sqlite/json 足够），再决定是否真正调外部 API。
4. **两阶段写入**。先写临时文件，校验通过后原子 rename 到目标位置，避免写一半被重试打断留下脏数据。

最简的去重示意：

```python
key = f"{task_name}:{scheduled_date}"
if state_db.seen(key):
    return
result = do_work()
state_db.mark_done(key)
```

注意：`do_work` 失败时不要 mark，让下一轮自然重试接上。

## 踩坑点

- **「先查后写」有竞态**：两个实例同时查都显示未处理，然后各跑一遍。并发场景要么加文件锁，要么用支持原子操作的存储。
- **幂等键混入了执行时时间戳**：重试时时间变了、键也变了，去重形同虚设。键必须来自计划时间、数据日期这类稳定量。
- **外部系统「成功但超时」**：请求实际已生效，客户端却收到超时，重试必然重复。本地记账防不住这种情况，幂等键需要透传给服务端。
- **LLM 输出不确定**：同一个键两次生成的内容可能不同。先定策略，一般「首次写入为准」，别让重试结果覆盖已确认的结果。

## 可复用建议

给每个自动化任务过一遍三问：

1. 同一轮手动跑两次，结果会坏吗？
2. 执行到一半超时重试，会产生重复副作用吗？
3. 两个实例同时触发，会互相踩吗？

三个都能答「不会」，这个任务才配挂上调度器。另外，写 MCP 工具时把「是否幂等」写进工具描述，Agent 决策重试时能少走弯路。

## 总结

幂等性不是调度器给的保障，而是任务设计里主动构造的性质。Agent 自动化中重试不可避免，要做的不是消灭重试，而是让「重复执行」和「执行一次」产生同样结果。确定性路径、幂等键、upsert 这三件小事养成习惯，大部分补跑事故就与你无关了。
