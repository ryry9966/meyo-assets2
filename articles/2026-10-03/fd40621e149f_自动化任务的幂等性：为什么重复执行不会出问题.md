## 背景

跑过一段时间自动化的人，基本都撞见过同一类事故：定时任务重叠触发、webhook 重试、agent 循环里某一步超时后整个任务重跑。结果往往是评论发两条、记录插两行、通知发三遍。

在 OpenClaw 的典型工作流里，"重复"不是异常，而是常态：调度器可能重叠触发，MCP 工具调用超时后由上层重试，插件在网络抖动时收到同一事件的两次回调。所以真正的问题不是"如何避免重复执行"，而是**"如何让重复执行无害"**——这就是幂等性。

## 问题

一个操作是幂等的，指执行一次和执行 N 次，最终状态相同。反例很常见：

- "往群里发一条日报"，执行两次就是两条日报
- "创建一个工单"，重试后出现两个工单
- "调用一次计费接口"，重复扣了款

最容易踩的关键场景是：任务在服务端其实成功了，但响应超时，调用方只能当它失败并重试。这不是 bug，是分布式系统的默认行为。没有幂等设计，重试就不敢开；不敢重试，可靠性又上不去。

## 做法

我在 OpenClaw 的自动化实践中按四步处理：

1. **优先写"确保状态"，而不是"执行动作"。** 把"创建工单"改写成"确保标题为 X 的工单存在"：先查有没有，有就跳过或更新。设置状态类操作（PUT、改配置为指定值、先删后建）天然幂等，尽量把任务往这个方向改。

2. **给任务造一个确定性的幂等键。** 不要用随机 UUID——每次重试都生成新键，等于没防。用任务内容的稳定组合，比如 `任务ID + 日期 + 步骤名`。同一任务无论重跑多少次，键不变。

3. **执行前查、执行后记。** 用 SQLite、文件甚至一个 JSON 都行：执行前查这个键处理过没有，处理过直接返回上次结果；没处理过才真正执行，然后立刻落盘标记。

4. **并发场景加锁或唯一约束。** 两次运行同时到达时，"查了都没有"会双双执行。把幂等键设为数据库唯一索引，靠约束冲突兜底，比应用层判断可靠得多。

## 踩坑点

- **幂等键里混入时间戳或随机数。** 重试时键变了，去重完全失效。键必须只由稳定的业务语义组成。
- **业务写入和标记落盘不是原子的。** 业务写成功、标记没写，下次重跑照样重复。要么放进同一事务，要么先写标记再执行、失败时清除标记。
- **幂等记录清理太早。** 为省空间 24 小时就删记录，但上游重试窗口是 72 小时，照样重复。清理周期必须大于最大重试窗口。
- **agent 重新规划后任务 ID 变了。** agent 循环重试时若每次重新生成上下文，上层防重就形同虚设。幂等键要绑定在最初的任务语义上，而不是某次运行的元数据。

## 可复用建议

- 每写一个定时任务/插件/工具，先回答："它被执行两次会怎样？"答不上来就先补幂等。
- 对外工具按声明式设计：入参是目标状态，工具负责对齐现状，而不是盲目追加操作。
- 幂等键 + 存储 + 唯一约束这三件套，可以做成 OpenClaw 插件的通用基建，所有带副作用的工具默认接入。
- 保留"上次执行结果"，重复触发时直接返回，对 agent 来说比抛错友好得多，也减少无效重试。

## 总结

幂等不是靠"保证不重复执行"实现的——在自动化的世界里，重复执行无法避免，重试机制本身也依赖它才能工作。真正的思路是把操作改写成可安全重复的形态：确定性键、先查后记、状态声明。把这层做扎实，调度器、agent 循环和网络重试才会从事故来源，变成可靠性的保障。
