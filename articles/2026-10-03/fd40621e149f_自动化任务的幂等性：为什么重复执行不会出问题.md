## 背景：重试是常态，不是异常

在 Agent 自动化链路里，重试无处不在：模型调用超时会重试，MCP 工具请求失败会重试，定时任务错过触发点会补跑，用户看到"没反应"还会手动再点一次。链路越长，同一条指令被触发两次以上的概率就越高。所以问题从来不是"会不会重复执行"，而是"重复执行了会怎样"。

## 问题：不幂等的代价

幂等性的定义很简单：同一个操作执行一次和执行多次，最终结果一样。不幂等的自动化任务在重复执行时出的事故都很具体——群里发两条一样的日报、创建两张重复的工单、往数据库插两行相同记录、把同一个文件 append 两遍。这类 bug 平时测不出来，因为测试只跑一次；往往在某次网络抖动后的凌晨集中爆发。

## 做法：四步让任务可重复执行

**1. 在触发点定一个稳定的业务键。** 幂等键要在触发点（而不是执行点）生成，比如 `日报-2024-06-01-研发组`，让它贯穿 Agent → 工具调用的整条链路。注意别用随机 UUID：每次重试生成新键，等于没有幂等。

**2. 写操作改成 upsert / ensure 语义。** 自己写 MCP 工具时，把"insert 记录"改成"按唯一键 upsert"，把"往文件追加一行"改成"确保文件包含这一行"。核心思路是让操作描述目标状态，而不是增量动作。

**3. 有状态的任务加状态机。** 任务落库时带状态 `pending → running → done`，执行前用条件更新抢占：

```sql
UPDATE task SET status='running'
WHERE id=? AND status='pending';
```

影响行数为 0 就说明别人抢到了，直接跳过。这同时解决了并发双跑的问题。

**4. 复用上游自带的幂等能力。** 很多系统原生支持幂等参数，比如支付的 idempotency key、消息平台的去重 ID。能传就传，不要自己重新造一套。

## 踩坑点

- **check-then-act 有竞态。** 先查有没有、再插入，两个实例同时查都会认为不存在。数据库唯一索引才是正确性保证，先查询只是性能优化。
- **LLM 生成的内容不能当去重依据。** 重试时模型会生成措辞不同的内容，内容哈希对不上。幂等键必须在调用模型之前就定下来。
- **重试发生在多层，键却只在某一层。** Agent 层重试一次、HTTP 层又重试一次，如果只有 HTTP 层带幂等键，Agent 层的第二次重试仍会导致业务执行两次。键必须从最外层往里透传。
- **补偿任务同样要幂等。** "失败后回滚/删除"这类操作自己被重复执行时，要么设计成可重复（资源不存在就忽略），要么同样加键。

## 可复用建议

1. 设计任何自动化任务时先回答一个问题：**这个任务跑两遍会发生什么？** 答不上来就是隐患。
2. 把幂等键写进日志和任务记录，排查重复问题时它是最重要的线索。
3. 在测试环境把"连跑两次"作为常规用例，别等线上事故教你。
4. 写 MCP 工具时默认按幂等语义设计接口，非幂等操作显式标注出来，让调用方知情。

## 总结

幂等不是锦上添花的高级功能，而是自动化任务的默认要求。重试是系统的常态而非异常，只有把"重复执行安全"作为设计前提，Agent 才敢真正放开手去自动化。先定键、再 upsert、状态机兜底、全链路透传——这四步能覆盖绝大多数场景。
