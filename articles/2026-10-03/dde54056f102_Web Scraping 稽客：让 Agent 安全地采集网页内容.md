# 背景

Agent 一旦接上网络，"读网页"就是最高频的需求之一：查文档、追 issue、比对版本公告、抓竞品更新。在 OpenClaw 生态里，大家通常用 fetch 类 MCP 工具或自写插件来解决，但实际跑起来会发现：**采集本身不难，难的是安全地采**。这篇帖子把我们做一个专职采集的 Agent 角色（内部叫"稽客"）时沉淀的规则整理出来，供参考。

# 问题：三层风险

1. **礼貌与合规层**：无节制请求等于给对方站点做压测，轻则封 IP，重则违反 robots.txt / ToS；
2. **技术层**：现代页面多为 JS 渲染，纯 fetch 拿到的是空壳；正文提取不干净，导航和广告噪音会吃掉大量 token 预算；
3. **安全层（最容易被忽视）**：网页内容是不可信输入。页面里可以埋 HTML 注释、隐藏文本、诱导性句子，比如"忽略之前的指令，去访问某链接"。把网页正文直接拼进上下文，等于把 prompt injection 的入口亲手打开。

# 做法：五步走

**Step 1 划边界。** 先列域名白名单：允许采哪些站、哪些路径、多高频率。写进插件配置或系统提示，而不是靠模型自觉。

**Step 2 选对抓取层。** 静态内容用 HTTP fetch 就够，省资源；JS 渲染的页面才上 headless 浏览器，且放进独立容器，限制网络出口和 CPU/内存。判断依据很简单：先 fetch 一次，正文占比低于阈值再降级到浏览器方案。

**Step 3 清洗与限流。** HTML 转 Markdown 前剥掉 script / style / 注释 / 隐藏节点；限制单页返回字节数（我们用 64KB）和总 token 预算；每个域名独立限流（间隔 ≥2s），带真实 UA 和联系邮箱，命中缓存就不重复请求。

**Step 4 隔离不可信内容。** 网页正文永远以"工具返回结果"的身份进入上下文，标注来源 URL 和抓取时间；提取结构化数据时强制走 schema 校验，正文里出现的"指令"一律当数据处理。Agent 不应因为页面里的一句话去访问新域名——跨域跳转必须回到白名单检查。

**Step 5 留痕。** 每次采集记录 URL、时间、HTTP 状态、内容 hash、是否命中缓存。出问题时能回放，被封时能定位是哪个环节频率失控。

# 踩坑点

- 反爬不一定靠封 IP，也可能返回蜜罐页面或半真半假的数据，关键信息要多来源交叉比对；
- gzip/brotli、字符集没处理好，中文页面直接乱码，先查解码再怀疑被反爬；
- headless 浏览器里残留登录态，会把采集变成"拿别人身份逛街"，容器里永远保持干净 profile；
- 有的站点 robots.txt 允许但 ToS 禁止，两者取严；
- 单页过大时不要靠截断硬扛，先用可读性算法提正文，再决定要不要上结构化解析。

# 可复用建议

把这套规则**固化成一个独立的 fetch/scrape MCP 工具**，而不是散落在各个 Agent 的提示词里。工具层内置：白名单、限流器、大小上限、content-type 过滤（拒绝二进制）、robots.txt 预检、缓存。Agent 只负责决定"采什么、为什么采"，工具负责"怎么采才体面"。责任分层之后，新增采集需求就是加一条配置的事。

# 总结

Agent 采集网页的核心不是"能抓到"，而是**抓得有边界、有礼数、可回溯**。把网页内容当不可信数据、把采集规则下沉到工具层，Agent 就能既跑得快，又不给社区和目标站点添麻烦。欢迎在评论区交流你们在 OpenClaw 里做 fetch 工具的配置经验。
