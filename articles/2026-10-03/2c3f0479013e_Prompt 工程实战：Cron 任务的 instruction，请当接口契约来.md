## 背景

Agent 跑顺之后，很多人会开始把重复工作交给 cron：每天早上拉一次告警邮件做摘要、每周整理一次 issue、定时巡检服务状态。触发端（cron 表达式）没什么好说的，真正决定成败的是 instruction——交给 agent 的那几句话。我维护了十几个定时任务之后，翻车基本都翻在 instruction 上，这里把经验整理一下。

## 问题：定时任务的 prompt 和聊天 prompt 不是一回事

聊天时有上下文、有追问、有人兜底；cron 触发的运行是**冷启动**：没有上一轮对话，出错没人现场纠正，输出直接进频道或文件。三个典型现场：

1. **写成聊天语气**：「帮我看看昨天的数据怎么样」——“看看”是什么粒度？“怎么样”以什么格式输出？agent 每次猜得都不一样，第三天输出格式就开始漂移。
2. **假设有记忆**：instruction 里写「和上次结果对比」，但每次运行是独立会话。除非你持久化了状态文件并明确告诉 agent 去哪读，否则“上次”根本不存在。
3. **没定义失败路径**：数据源挂了，agent 不会报错，它会编一份看起来像样的摘要。定时任务最大的风险不是失败，而是安静的假成功。

## 做法：六段式模板

我把 instruction 当接口契约写，固定六段，缺一段都不稳定：

```text
【运行上下文】时区 Asia/Shanghai；"今天"以运行时刻为准；只处理最近一个周期。
【数据源】用 gmail 工具，搜索过去 24h 内来自 alerts@example.com 的邮件。
【处理范围】只做统计与摘要；不回复、不标记已读、不调用范围外工具。
【输出契约】固定三段：结论（≤3 行）/ 明细 / 异常项。
【异常路径】数据源不可用：输出 status: skipped + 原因；禁止编造数据；重试至多 1 次。
【禁止事项】任何发送类动作；任何超出上述范围的写操作。
```

几条原则展开说：

- **调度逻辑只留在 cron 表达式里**。「每周一执行」这种话别写进 prompt，两边迟早漂移，以 cron 为准，prompt 只管“做什么”。
- **数据来源具体到工具名或路径**。「查一下邮件」改成「用 X 工具搜索过去 24 小时来自某地址的邮件」，模糊来源是幻觉的主要入口。
- **输出结构固定**。哪怕是给人类看的，也固定成“结论 / 明细 / 异常”三段，长期才能横向对比、才能被下游解析。
- **长参考资料不要内联**。放工作区文件里让 agent 自己读。定时任务高频运行，instruction 又长又不稳定，token 和漂移是双重成本。

## 踩坑点

- **时区与日界**：容器是 UTC，人在东八区，“昨天”能差出八小时。instruction 里显式写时区。
- **大任务拆小**：一个 cron 干“拉数据 + 分析 + 发报告 + 清理”，失败时不知道断在哪。拆成多个任务，或至少让输出标注所处阶段。
- **副作用任务先加确认门**：让 agent 先把草稿写到文件，人工看过再放开发送权限，跑稳一周再自动化。
- **instruction 也要版本管理**：改一个词可能改变输出结构。一次只改一处，旧版本留着能回滚。

## 可复用建议

1. **上线前手动触发跑 3–5 次**，用历史数据对比输出是否稳定，再开调度。
2. **每次运行的输出落盘到固定路径**，出问题有据可查，也便于发现格式漂移。
3. **把六段模板存成 snippet**，新任务从模板改起，不要从零写。

## 总结

Cron 的 instruction 本质是用自然语言写的一个小函数：输入明确、输出定型、失败路径有定义。写的时候少一点聊天感，多一点接口思维，定时任务才能长期无人值守地跑下去。它不值得写得华丽，但值得写得较真。
