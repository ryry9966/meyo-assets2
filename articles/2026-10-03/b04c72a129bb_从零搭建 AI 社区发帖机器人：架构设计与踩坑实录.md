## 背景

社区内容运营的日常大概是这样：从几个信息源里挑内容、写摘要、排版、发帖，每天重复。人工做了两周后我决定用 OpenClaw 把这条流水线自动化。目前机器人稳定跑了一个多月，日均发帖 3 篇，人工介入约 10%。本文记录架构取舍和踩过的坑，偏工程视角，不聊提示词玄学。

## 问题定义

“调 API 发帖”本身不难，真正的难点在别处：

1. **内容质量不可控**——agent 自由发挥，容易写出发营销号味道的东西；
2. **幂等性**——网络超时重试，同一篇内容发两遍；
3. **凭证安全**——API key 绝不能进 prompt 和日志；
4. **失败可观测**——静默失败比失败本身更可怕。

## 架构：四层结构

```
触发层 → 内容层 → 审核层 → 发布层
              ↓
          SQLite 状态库
```

- **触发层**：用 OpenClaw 内置的定时任务拉起 agent，每次运行使用全新会话。不自己写 crontab，复用 OpenClaw 的会话管理和工具权限，省掉一层胶水代码。
- **内容层**：给 agent 挂两个 MCP 工具——`fetch_sources`（抓信息源）和 `community_api`（社区接口封装）。关键约束：要求 agent 只输出结构化 JSON（标题/正文/tags/source_url），模板渲染交给确定性代码完成。
- **审核层**：草稿先推到我的私聊会话，回复确认后才发布。第一版没有这层，差点翻车（见踩坑 1）。
- **发布层**：薄封装，只做两件事——调接口、把结果（成功/失败/post_id）写回本地 SQLite。

状态库就一张表：`content_hash + status + post_id`，去重和幂等全靠它。

## 踩坑实录

**1. 全自动发布后质量滑坡。** 标题全是“重磅！”“一文读懂”，第三天有社区成员私聊问我是不是被盗号了。解法：加回人工审核层，同时在提示词里写死风格约束（禁感叹号、限标题长度）。每天成本约 2 分钟，值得。

**2. 重试导致重复发帖。** 接口超时后 agent 自动重试，实际第一次已成功，于是同内容发了两遍。解法：发布前按 `content_hash` 查库，成功立即写 `post_id`；接口侧支持幂等键。两层防护，缺一不可。

**3. MCP 工具描述太模糊。** `fetch_sources` 的描述最初只写了“获取信息源”，agent 经常漏传分类参数。把每个参数的语义、取值范围、示例补进 tool schema 后，调用准确率明显提升。教训：工具描述就是提示词的一部分，别省。

**4. 时区坑。** 定时任务部署在容器里，默认 UTC，预期早上 8 点实际下午 4 点触发。显式设置 TZ 环境变量解决。

**5. 凭证进了日志。** 调试期把完整请求打进日志，key 就在里面。现在凭证只走环境变量，日志层统一脱敏，并作废轮换了那把 key。

## 可复用建议

- **结构化输出 > 自由文本**：agent 负责 JSON，渲染交给代码，质量下限立刻抬高一截；
- **人工审核不是妥协，是质量阀门**：先加后拆，比出事故再补强得多；
- **幂等做两层**：本地状态库 + 服务端幂等键；
- **MCP 工具描述按提示词标准写**：语义、参数、示例缺一不可；
- **观测最小集**：每次运行落一条结构化日志（触发时间/耗时/结果/错误码），排障效率天壤之别。

## 总结

机器人本身不难，难的是把 agent 的不确定性关进确定性的笼子里：结构化输出约束生成、状态库约束幂等、审核层兜底质量。下一步打算让 agent 对信息源做质量评分，学会“不发烂内容”。代码骨架和 MCP schema 已在整理，之后会在社区仓库开一个模板 repo，供直接套用。
