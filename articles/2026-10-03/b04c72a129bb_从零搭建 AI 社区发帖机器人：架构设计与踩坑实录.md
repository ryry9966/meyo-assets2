## 背景

社区运营里有一类典型的重复劳动：每天从 issue 区、RSS、仓库动态里筛内容，整理成一条「今日动态」发到论坛。单次十分钟，难的是每天坚持。于是我用 OpenClaw 搭了一个发帖机器人，跑了六周，累计发帖 40+，误发 2 次（均已撤回）。这篇记录架构和踩坑，供想自己搭的同学参考。

## 问题

目标朴素，约束不少：

- **内容必须真实**：链接、标题都不能由模型编造；
- **发布要有闸门**：不能让 agent 直接对外发帖；
- **可停可恢复**：进程挂了重跑，不能重复发帖。

## 架构

整体四层，全部跑在一台 2C4G 的小机器上：

1. **触发层**：OpenClaw cron 任务，每天 09:30 拉起一个 agent 会话；
2. **生产层**：agent 挂载自建 MCP server，工具只有三个——`fetch_sources`（拉订阅源）、`load_template`（读帖子模板）、`publish_post`（发布）；
3. **闸门层**：`publish_post` 内部先校验（链接可达、去重、字数），通过后写入草稿区，人工确认才真正落库；
4. **审计层**：每次运行落一条 JSON 日志：输入源、草稿、校验结果、最终动作。

核心原则一句话：**模型只负责写，所有事实来自工具返回值，发布权不交给模型。**

## 落地步骤

1. 先写 MCP server，百来行的 Python 文件，stdlib + requests 够用，别急着上框架；
2. 在 OpenClaw 注册技能，系统提示词只约束三件事：风格、字数上限、禁止编造 URL；
3. cron 定时 + 状态文件（记录已处理源条目的 hash）做幂等；
4. 前两周只发草稿到内部群，人工确认，稳定后再放开自动发布。

## 踩坑实录

- **重复发帖**：cron 触发超时重试，同一内容发了两遍。修复：把草稿 ID 写入状态文件，发布前查重。教训是幂等要做在写入侧，不能指望调度器。
- **模型编链接**：早期版本 agent 偶尔把标题和 URL 拼错位，甚至补全出 404。修复：`fetch_sources` 只返回校验过的 URL 列表，提示词明确「仅可使用工具返回的 URL」，发布前再 HEAD 一遍。
- **Markdown 方言**：论坛渲染器不支持部分表格语法，本地好看、上线就乱。修复：用论坛同款渲染器预渲染，失败降级为纯文本段落。
- **时区**：cron 按 UTC 跑了三天，「今日」全是昨天的内容。配置里显式写时区，别猜。
- **风格漂移**：换模型版本后草稿明显啰嗦。把模型版本钉死，提示词里保留负面示例。

## 可复用建议

- 生成和发布必须是两个阶段，中间有显式闸门；
- 状态持久化比上下文记忆可靠，幂等做在发布侧；
- 工具粒度宁小勿大，三个小工具比一个全能工具好排查；
- 从低频（每周）起步，观察两周再加频；
- 日志记全，出问题能回放到「哪一步、哪个输入」。

## 总结

这个机器人真正的价值不在省下的十分钟，而在强迫你把「内容从哪来、谁能发布、出错怎么办」想清楚。OpenClaw + MCP 做这件事性价比很高：agent 负责语言，工具负责事实，闸门负责兜底。两周的人工确认期值得保留，别省。
