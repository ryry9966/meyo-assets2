## 背景

OpenClaw 的 cron 任务，本质是「让 agent 在固定时间带着一段 instruction 独立跑一轮」。它看起来很像给 agent 发消息，但上下文完全不同：对面没有真人、没有追问的机会、结果直接投递到 IM 或日志。不少人把平时聊天的 prompt 直接粘进去，第一跑就翻车。

## 问题

我自己和群里朋友跑定时任务时收集到的典型翻车姿势：

- instruction 写得太口语，agent 回一句「你想看哪个仓库？」——cron 没人接话，任务卡死；
- 相对时间交给模型自由发挥，「昨天」跨了凌晨边界，取错窗口；
- 没有输出规则，没更新也发「今天没有新动态」，刷屏还烧 token；
- 对工具（包括 MCP 工具）没有约束，一轮跑出连环读写操作。

根因就一句：cron instruction 不是聊天，而是一个没有人在场的定时程序，instruction 就是作业规格说明。

## 做法

我现在的 cron instruction 固定骨架五段，写在同一条消息里：

1. **触发上下文**：开头声明「这是每日 08:00（Asia/Shanghai）定时任务的自动运行，非用户发起，不要等待确认、不要反问」；
2. **目标与时间窗**：相对时间一律换算成「以当前时刻为准，往前 24 小时」；
3. **步骤与工具预算**：列 2–4 步，写明用哪个工具，限制调用次数；
4. **输出格式**：固定一条消息、给出模板、限定长度；
5. **静默与失败规则**：没东西可报时回复固定哨兵词（如 `SKIP`），由投递层过滤；工具报错时说明卡在哪一步，重试至多一次，禁止编造。

精简对比：

```text
# 差
帮我总结一下昨天的 GitHub 通知，发到群里
```

```text
# 好
[定时任务] 每日 08:00 cron 运行（Asia/Shanghai），非用户发起。
目标：汇总最近 24h 的 GitHub 通知。
步骤：调用 gh 拉取通知，仅保留 mention 和 review request，≤10 条。
输出：一条消息，首行一句话总览，随后列表（repo: 摘要）。
约束：只读操作；若无内容，仅回复 SKIP；出错则说明失败步骤，重试至多一次。
```

## 踩坑点

- **忘了写「定时运行」**：agent 以为有人在聊天，陷入等待或自问自答。这一句能解决大半卡死问题。
- **时区没钉死**：服务器是 UTC，任务实际比预期偏 8 小时；调度配置和 instruction 里都要确认时区。
- **工具调用无上限**：一次失控的运行能吃掉一天 token 预算，建议把步骤总数封顶在 5 步内。
- **让 cron 做写操作**：定时任务默认只读；确实要写，用白名单加显式变量，不留自由发挥空间。
- **大段资料内联进 instruction**：每次运行全量计费，频率乘长度双重烧钱；长资料放文件，instruction 里按需读取。
- **多个杂活塞进一个任务**：排查问题时是噩梦，一个 cron 只交付一件事。

## 可复用建议

- 把 instruction 当代码对待：上线前手动触发一轮验证，改版留历史版本；
- 哨兵词要在下游（心跳/投递层）过滤，否则 SKIP 会原样发到群里；
- 让任务把运行摘要追加到日志文件，排障先看日志，别靠猜；
- 模型需要的所有参数都在 instruction 里预先定死，不留任何开放式问题。

## 总结

写好 cron instruction，核心是心态切换：它不是对话式 prompt，而是定时程序的参数表——输入确定、工具有界、输出固定、静默有规则。把这几条写清楚，定时任务才能从「碰运气」变成可以长期稳定运行的东西。
