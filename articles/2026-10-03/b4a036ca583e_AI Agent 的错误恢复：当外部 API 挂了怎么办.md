## 背景

跑自动化 Agent 的人迟早会撞上同一个场景：流程执行到一半，某个外部 API 超时了——可能是 LLM 供应商限流、某个 MCP 工具背后的 SaaS 抽风，或者只是网络抖了一下。这时候 Agent 的表现往往比故障本身更糟糕：无限重试烧 token、把错误信息当数据继续推理，甚至编出一个"看起来合理"的结果往下走。

## 问题在哪

外部 API 故障对 Agent 的伤害和对普通程序不一样，主要三点：

1. **LLM 分不清"工具挂了"和"工具返回了空结果"**——在上下文里两者都是一段文本；
2. **重试策略写进 prompt**（"失败了就再试一次"），和工具适配层里的重试逻辑相乘，实际重试次数远超预期；
3. **多步流程里上游失败但流程继续走**，产出半成品数据：工单建了、通知发了，但关键数据是错的。

## 做法：四层防线

**第一层：调用包装。** 在 MCP 工具/插件适配层统一加超时和重试，按错误类型区分：4xx 不重试（参数问题，重试没意义）；429 按 Retry-After 退避；5xx 和网络错误用指数退避加随机抖动，一般 3 次封顶。给整个调用设总时间预算，而不是只数次数。

**第二层：结构化错误上抛。** 别把原始堆栈直接塞给模型。返回统一信封：错误码、是否可重试、建议动作（换工具 / 降级 / 告知用户）。模型拿到清晰的错误语义，才能做出正确决策。

**第三层：降级路径。** 每个关键工具至少准备一条退路：缓存数据、备用供应商，或者明确输出"此步骤失败，以下是部分结果"。宁可让流程带缺口结束，也不要让模型靠想象力补全。

**第四层：断点与幂等。** 长流程在执行有副作用的调用前落盘状态（checkpoint）；所有写操作尽量幂等，或带幂等键。这样恢复时是"接着跑"而不是"从头来"，重试也不会造成重复下单、重复发消息。

## 踩坑点

- **非幂等接口直接重试。** POST 建单类操作重试三次 = 三个重复工单，先确认接口幂等再开重试。
- **两处同时写重试逻辑。** prompt 里写一次、适配层写一次，退避时间一长直接把对话卡死。
- **超时不设总上限。** LLM 调用 60s、HTTP 30s、重试 3 次，最坏一个工具调用挂 4 分钟，编排层必须有总 deadline。
- **把失败吞掉返回空数组。** 模型会把空结果当真实数据继续推理，比报错更危险。
- **退避没有抖动。** 服务恢复瞬间所有实例同时重试，刚缓过来又被打挂。

## 可复用建议

- 重试策略只写在工具适配层这一个地方，对话层永远不承担重试职责。
- 错误信封结构固化下来，团队所有插件共用同一套。
- 给失败步骤建"死信"记录：哪个步骤、什么错误、输入是什么，事后能补跑。
- 用 mock 服务做故障演练：随机 500、随机超时，看 Agent 走不走降级路径。故障路径不测试，等于没写。

## 总结

外部 API 挂了不是异常情况，是常态。工程上的目标不是让故障不发生，而是让故障被明确识别、有界处理、可恢复执行。把超时、重试、降级、幂等这四件事从对话逻辑里拿出来，沉到工具层，Agent 的稳定性会有质的变化。
