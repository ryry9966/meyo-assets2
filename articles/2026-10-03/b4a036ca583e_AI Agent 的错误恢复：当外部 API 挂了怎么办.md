## 背景

Agent 化之后，可靠性瓶颈往往不在模型，而在外部依赖。一个 OpenClaw 工作流里可能同时挂着搜索、数据库、第三方 SaaS 的 MCP 工具，任何一个 API 抖动，整条自动化链路就可能中断——或者更糟，静默产出错误结果。

## 问题

实际遇到的失败分三类：

1. **明确失败**：429、503、超时、连接拒绝；
2. **伪装成功**：HTTP 200，但 body 里是错误信息或空数据；
3. **半成功**：请求已到达对方但响应丢失，盲目重试会产生重复副作用。

LLM 本身不适合处理这些：它倾向于无限重试，或者在拿不到数据时"编"一个看似合理的答案。所以错误恢复必须下沉到代码层。

## 做法

**1. 工具封装层做错误分类。** 每个 MCP 工具/插件调用统一包一层，把异常归一化为结构化结果：

```json
{ "ok": false, "error_type": "rate_limit", "retryable": true, "hint": "60s 后可重试" }
```

关键是 `retryable` 由代码判定：429/503/超时为 true，400/401/404 为 false。不要把原始堆栈丢给模型。

**2. 重试交给代码，带上限和抖动。** 指数退避 + jitter，最多 3 次，写死在封装层。不要在 prompt 里让模型"重试几次"——它数不准，还会死循环烧 token。

**3. 只自动重试幂等操作。** 读操作随便重试；写操作（下单、发消息、写库）必须带幂等键，否则不自动重试，把决定权交回上层流程或人工。

**4. 熔断 + 降级阶梯。** 连续失败 N 次后熔断，跳过该工具，走预置的降级路径：备用 API → 本地缓存 → 明确告知"此步骤不可用"。每一级都要提前写好，而不是事故现场现想。

**5. 给模型的是决策信息，不是原始错误。** 恢复后注入上下文的应该是"搜索工具暂不可用，已切换到 2 小时前的缓存数据"，让模型据此调整回答口径，而不是让它对着 stack trace 自己猜。

## 踩坑点

- **没校验 200 的 body**：某 API 故障时返回 200 + 空数据，Agent 拿着空结果继续跑，产出整篇"看起来正常"的垃圾。响应必须过 schema 校验。
- **退避没加 jitter**：多个定时任务同时触发、同时重试，把刚恢复的 API 又打挂。
- **超时设太长**：单次 120s 超时会卡死整个 agent 循环，外部依赖的超时应远小于任务整体时间预算。
- **熔断了不会恢复**：熔断器要有半开状态，定期放一个探测请求过去。
- **恢复后重放副作用**：从 checkpoint 恢复时把已成功的写操作又执行了一遍。checkpoint 要精确到"哪个副作用已确认完成"的粒度。

## 可复用建议

- 写一个通用的 `safe_call(tool, ...)` 包装器，所有插件统一接入，错误信封格式固定；
- 降级阶梯做成配置而非硬编码分支，方便按工具调整；
- 每次失败带 request_id 落日志，事后能串起完整调用链；
- 上线前做故障注入：把依赖 API 的 base_url 指向一个必超时的地址，看整条链路的真实表现。

## 总结

错误恢复本质是工程问题，不是 prompt 问题。原则一句话：**代码决定"要不要重试、何时放弃"，模型只接收"发生了什么、还剩哪些选项"**。把这两件事分开，Agent 面对外部 API 故障时才能表现得像样——该重试的重试，该降级的降级，该承认失败的诚实承认失败。
