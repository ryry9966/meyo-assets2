## 背景

Agent 接上 MCP、插件和 shell 之后，能力上限就不再是模型本身，而是我们愿意给它开多大的口子。这个边界画不好，会掉进两个坑：要么事事请示，把人变成点击确认的机器；要么放手太多，某天发现它替你给客户发了消息，或者在生产库上跑了一条 DELETE。

## 问题

实践中真正的难点不是"给不给权限"，而是平衡两个失败模式：

- **确认疲劳**：人被问烦了会不读内容直接批准。确认机制形同虚设，比不确认更危险——它制造了虚假的安全感。
- **粒度错位**：按步骤逐项确认会把任务流切碎，一圈审批下来比人自己做还慢。
- **边界写错地方**：很多人把规则写进 system prompt（"删除前先问我"）。Prompt 是请求不是约束，长任务高压下模型一定会漏。

## 做法

核心思路：把"问不问"从主观判断变成一张**可配置的分级表**。判断维度四个：可逆性、影响范围、成本、外部可见性。

1. **盘点工具面**。列出 agent 能触达的全部动作：MCP server 的每个 tool、插件注册的每个能力、常用 shell 命令模式。
2. **分级**：
   - T0 只读（读文件、search、list）→ 自动执行
   - T1 可逆写（工作区内写文件、建分支、本地 commit）→ 自动执行 + 全量日志
   - T2 不可逆或外显（发消息、调付费 API、改共享状态、push 远端）→ 暂停请示，请示内容必须带 diff、目标和预估成本
   - T3 破坏性（rm -rf、drop table、force push、批量删除）→ 默认拒绝，白名单 + 单次显式确认
3. **落在工具层**。用 MCP 网关或插件层的权限配置按 tool 名拦截，不指望模型自觉。
4. **计划级确认代替步骤级确认**。多步任务先让 agent 产出动作清单，人批一次计划；T3 类动作仍单独拦截。
5. **加熔断**。预算上限（单日 API 花费）、频率上限（每小时外部请求数）做成自动闸门，超限即停并汇报。
6. **定期回看审计日志**，根据误报和漏报调整分级。

## 踩坑点

- **确认疲劳是头号杀手**。如果一周内 T2 触发了两百次，说明分级太粗——人从第三十次开始就会闭眼批准。
- **批准复用问题**：人批了一次"向 X 发消息"，agent 不应推断以后都能发。批准默认单次有效，放开需显式声明。
- **dry-run 不是万能的**：发邮件、支付这类副作用 API 往往没有 dry-run，只能靠分级加沙箱账号兜底。
- **共享 MCP server 会击穿边界**：一个全权限 server 挂上来，前面所有分级都白做。权限要按 server 收敛。
- **日志只记"已批准"没用**：要记完整上下文——动作参数、diff、当时的任务目标，否则事后无法审计。

## 可复用建议

- 默认拒绝一切工作区之外的副作用动作，白名单逐步放开。
- **投资可逆性**：分支、备份、暂存环境做得越好，能自动化的 T1 就越多。可逆性是最值得花钱的权限手段。
- 分级表写成配置进版本库，可 review、可回滚，不靠口头约定。
- 确认弹窗要有信息量：看 diff 批 diff，看成本批成本，别让人批一句"是否继续？"。

## 总结

权限边界不是开关，是一张随工具演进的分级表。原则压缩成三句：**只读自动、副作用问人、破坏性默认拒绝**。确认机制的设计目标是对抗疲劳而不是制造流程；执行约束放在工具层而不是 prompt 层。Agent 的自主性是放出来的，也是边界圈出来的——边界画得越准，你能放心交给它的就越多。
