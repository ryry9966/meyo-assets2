## 背景

用 Agent 做自动化，第一周很兴奋，第二周就会撞上同一个瓶颈：它只会被动响应。你问它才动，你不问，它就静静躺着。但真正有价值的事情往往不是发生在“我问的时候”，而是“该发生的时候”——磁盘快满了、日报该发了、某个指标连续三次异常。OpenClaw 为此提供了一个很轻的机制：**HEARTBEAT.md**。

## 问题

传统方案是 cron + 脚本，但 cron 不会判断，逻辑全写死；Agent 有判断力，却没有“时钟”。HEARTBEAT.md 做的事就是把时钟接到判断力上：网关按固定间隔（默认 30 分钟）触发一次心跳，Agent 醒来读取工作区里的 HEARTBEAT.md——有内容就执行，没内容就继续睡。关键区别在于：**文件为空或不存在时，不会产生实际的模型调用，Agent 完全静默**。它不是永远在跑的后台循环，而是按需上电的值班机制。

## 做法

1. 确认文件位置：默认在 `~/.openclaw/workspace/HEARTBEAT.md`，不存在就新建。
2. 用“三段式”写任务：检查什么 → 触发条件 → 汇报策略。
3. 在 `openclaw.json` 的 gateway 配置里按需调整心跳间隔。
4. 观察几天日志，再迭代任务清单。

一个可参考的最小示例：

```markdown
# 心跳任务
- 每次心跳检查 logs/gateway.log 是否出现 ERROR 关键字
- 每天 8 点后的第一次心跳：汇总昨日 git 提交，追加到 daily.md
- 仅在异常时发消息；一切正常时不要回复任何内容
```

第三条“静默条款”非常重要，见下文。

## 踩坑点

- **把心跳当秒级 cron 用。** 心跳粒度是分钟级，精确调度请交给系统 cron + exec 工具，心跳只放“判断型”任务。
- **任务写得太模糊。** “帮我看看有什么值得关注的”只会换来一堆正确但无用的汇报。每个任务必须有明确的检查对象和触发条件。
- **没写汇报策略。** Agent 默认倾向于汇报，每 30 分钟一条“一切正常”很快会让你关掉整个功能。务必显式声明“只在异常时推送”。
- **无人值守 ≠ 无限权限。** 心跳是无人审批的自动执行，把 MCP 工具和 exec 命令按白名单收紧，高危操作必须走人工确认。
- **成本随任务数线性增长。** 每次心跳都是一轮真实的模型调用，任务清单控制在 3～5 条以内，长周期任务挪去 cron。
- **注意上下文膨胀。** 心跳与主会话共享上下文，长期运行后记得清理无关的中间产物。

## 可复用建议

- **把 HEARTBEAT.md 当代码管理**：纳入 git，每次修改写清楚 commit message，每周固定清理失效任务。
- **三层分工**：心跳提供“意图”，MCP/插件提供“能力”，cron 提供“精度”，分层使用而不是互相替代。
- **汇报落盘**：让 Agent 把心跳结果追加到固定文件（如 `reports/heartbeat.md`），消息只在异常时推送——把“主动汇报”变成可审计的日志流。

## 总结

HEARTBEAT.md 的价值不是“AI 会主动了”这类玄学描述，而是一个工程上完全可控的循环：固定间隔、显式任务清单、可配置的汇报策略。它把 Agent 从问答机变成值班员——值班员的职业素养恰恰是：大部分时间安静，出事时才说话。把任务写得像 SLA 一样明确，这套机制就能长期稳定地替你盯梢。
