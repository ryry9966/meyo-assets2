## 背景

单个 agent 干活有两个天然瓶颈：一是串行执行，工具调用一个接一个，跑批任务时等待时间线性累加；二是主上下文有限，中间结果全堆在对话里，跑到后半程 agent 开始“忘事”，前面定好的约定悄悄走样。

OpenClaw 这类框架提供了 subagent 机制（比如通过 `sessions_spawn` 派生子会话），主 agent 可以把任务拆给多个子 agent 并行跑，各自有独立上下文，结束后只把结果收回来。听起来很美好，但真正用起来，问题都在细节里。

## 问题

上周一个典型场景：给仓库里 18 个模块批量补充单元测试。让主 agent 串行做，预计 40 分钟起步，而且写到第 10 个模块时它已经开始混用前面模块的 mock 风格。另一个场景是同时调研 5 个 MCP 服务的能力边界并输出摘要，串行调研时前面读的文档到后面基本忘光。

这类任务的共同点：**子任务之间彼此独立，只和最终汇总有关**。这正是 subagent 的适用面。

## 做法

我们的编排流程固定成了五步：

1. **判断可拆性**。先让主 agent 自检：任务能否切成不共享可变状态、不互相依赖输出的块？按文件、目录、模块切是最稳的粒度。
2. **写自包含的任务书**。子 agent 看不到主对话，任务书必须带全：目标、输入路径、输出格式、禁区（比如“不要动 xxx 目录”、“不要 git commit”）。
3. **控制并发**。实测 3~5 个并发比较稳，再多容易出现 API 限流和结果回收混乱。
4. **规定回报格式**。要求子 agent 把完整产物写到约定路径的文件里，只返回一段结构化摘要（成功/失败、改了哪些文件、遗留问题）。
5. **主 agent 统一收口**。汇总、跑全量校验、处理失败重试。

派发模板大概长这样：

```text
任务：为模块 {name} 补充单元测试
输入：src/{name}/，参考 tests/_style.md 的既有风格
输出：测试文件写入 tests/{name}/，摘要按 JSON 返回
边界：不要修改 src/ 下任何文件，不要执行 git 写操作
```

效果：18 个模块的测试补全从 40 分钟压到 9 分钟，主上下文始终干净。

## 踩坑点

- **子 agent 再派子 agent**。不限制的话会出现套娃，token 成本指数级。我们的做法是在任务书里明确“禁止继续派生”。
- **并行写同一资源**。两个子 agent 同时改一个文件或同一个 git 分支，冲突很难收拾。按文件/目录切分基本能规避，但要在任务书里写死边界。
- **任务书不自包含**。子 agent 拿到“参考之前的做法”这种描述只能瞎猜，返工率极高。每个任务书都当成给新同事的交接文档来写。
- **中间结果回流**。早期让子 agent 返回完整日志，主上下文照样被撑爆。改成“产物落盘 + 摘要回报”后才真正解决。
- **失败静默**。有子 agent 跑挂了但汇总时才发现缺一块。给每个任务编号，失败可以单独重跑，不用整批重来。

## 可复用建议

- 把派发模板固化下来：目标 / 输入 / 输出 / 边界，四项缺一不可。
- 产物一律落盘，上下文里只走摘要，这是控制成本和噪声的关键。
- 放量前先用 2 个子 agent 小规模验证一轮任务书质量。
- 判断“能不能并行”这件事可以交给主 agent，但要在系统提示里给出明确判据，否则它倾向于全部串行求稳。

## 总结

Subagent 编排本质上就是分治：拆得开就并行，拆不开老老实实串行，不必为了并行而并行。实践中真正决定成败的不是框架能力，而是任务书的工程质量和结果回收的纪律。把这两件事做成固定模式，多 agent 并行才从演示变成日常生产力。
