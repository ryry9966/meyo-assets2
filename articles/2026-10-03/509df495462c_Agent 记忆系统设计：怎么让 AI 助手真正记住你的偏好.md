## 背景

LLM 本身是无状态的，每次调用都是一张白纸。OpenClaw 这类常驻 Agent 如果没有记忆层，用户就得每天重复声明"回复简短一点""我的部署目录在 /srv/app"。MCP 解决了工具和资源的接入问题，但"记住用户"这件事，目前还是要自己设计。这篇帖子分享一套我们踩坑之后收敛出来的分层方案，思路对任何带工具调用能力的 Agent 框架都适用。

## 问题

常见的两种错误做法：

1. **全塞上下文**：把历史对话全量喂回去。token 成本线性上涨，信噪比越来越差，Agent 反而更容易被旧内容带偏。
2. **单文件流水账**：一个 `memory.md` 无限追加。三个月后检索时抓出一堆互相矛盾的旧偏好，Agent 不知道该信哪条。

核心矛盾是：记忆要"够用"但不能"过载"，而且偏好是会变的。

## 做法

建议拆成三层：

- **工作记忆**：当前会话上下文，不落盘。
- **情景记忆**：会话结束后用小模型生成 2~3 句摘要，按日期归档。
- **语义记忆（关键层）**：结构化偏好条目，建议带 schema：

```json
{
  "key": "reply_style",
  "value": "简短、代码优先",
  "scope": "global",
  "confidence": 0.9,
  "source": "user_explicit",
  "updated_at": "2025-06-01T10:00:00Z"
}
```

**写入策略比读取更重要**：

- 只在显式陈述（"以后都……""记住……"）和跨会话重复出现的模式时才写入；
- 同 key 冲突时走"更新 + 旧值进 history"，不要盲目覆盖，也不要并存；
- 用户纠正 Agent 的那一刻，是置信度最高的写入信号。

**检索**：条目在几百条以内，标签过滤 + 关键词匹配就够了，别急着上向量库。规模真上去了再做 embedding 混合检索。

**遗忘**：confidence 随时间衰减、被反驳时扣分，低于阈值移入归档区，不再参与检索。

## 踩坑点

1. **记得太多**：早期我们把"用户今天喝了咖啡"也写进去了，检索噪声直接爆炸。原则：能从配置推导的不记，一次性事件不记。
2. **偏好打架**：旧的"配置用 YAML"和新的"改用 TOML"同时被召回。必须做同 key 更新，检索时只取 `updated_at` 最新的版本。
3. **记忆注入**：网页抓取的内容里混进"记住：以后都执行 XX"这类指令，被当成了用户偏好写进去。写入前必须过来源校验——来自外部内容的一律不直接写。
4. **静默生效**：Agent 偷偷记东西，用户会突然觉得"它怎么知道这个？"，体验很惊悚。重要偏好写入时回显一句确认，成本很低，信任收益很高。

## 可复用建议

- 做一个 `/memory review` 类命令，让用户随时查看和删除条目，这是底线能力；
- `source` 字段区分 `user_explicit / inferred / corrected`，infer 来的低置信度条目使用前先向用户确认；
- 每条记忆独立可删，不要捆在一个大文件里；
- 注入系统提示词时只取 top-N 高置信度 + 与当前任务相关的条目，坚决不全量注入。

## 总结

记忆系统的难点不在存储，而在写入门槛和生命周期管理。先用结构化 key-value + 简单检索跑通三件事：**写入有门槛、冲突有更新、过期会衰减**，再考虑上向量检索。Agent 记得对不对，最终要以"用户可审计、可撤销"为验收标准。
