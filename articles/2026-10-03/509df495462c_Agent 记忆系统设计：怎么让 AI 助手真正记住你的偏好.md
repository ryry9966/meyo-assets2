## 背景

LLM 本身无状态，OpenClaw 这类 Agent 框架解决了工具调用和自动化编排的问题，但"记得你是谁"仍然要自己设计。最常见的错误做法是把历史聊天整段回灌进上下文：token 消耗翻几倍，噪音比信号多，助手照样记不住"这个项目用 pnpm、回复要短"这类关键偏好。

## 问题

把记忆等同于聊天记录，会撞上三个结构性问题：

1. **全量回放不可扩展**：历史越长，每次会话成本越高，而真正相关的信息占比很低；
2. **没有写入标准**：什么都存等于什么都没存，检索精度反而被稀释；
3. **偏好会过期、会冲突**："全局偏好 Python"和"这个项目必须用 Go"同时存在时，没有覆盖机制就是随机命中。

## 做法：三层存储 + 三条通路

**分层存储**：
- 用户画像层：不超过 20 条稳定偏好，每次会话固定注入；
- 情景记忆层：项目相关的事实与约定，带 scope（全局 / 项目 / 会话）；
- 工作记忆层：仅当前会话，不入库。

**写入路径**：不要逐轮实时写。会话结束或每 N 轮触发一次提取，用一个小模型把对话转成结构化条目：`{category, content, scope, source, created_at, hit_count, last_hit}`。类别白名单只收偏好、事实、约定三类，置信度低于阈值的直接丢弃。

**读取路径**：画像层全量注入；情景层用混合检索（embedding + 关键词）取 top 3–5 条，先按 scope 过滤再排序。

**更新路径**：内容 hash 去重；同 scope 冲突时新条目覆盖旧条目并保留版本号；情景记忆按 last_hit 做衰减，长期未被检索的条目定期清理。

**接口层**：把 memory_read / memory_write 做成 MCP 工具暴露给 Agent，支持显式查询与保存；所有写入落日志，用户可审计、可撤销。

## 踩坑点

- **提取过宽**："用户今天开了深色模式"也入库，一个月后画像全是垃圾。宁可漏存，等同一信号重复出现再升级为画像条目。
- **只用向量检索**：命令名、文件路径这类精确 token 召回效果很差，必须混检。
- **注入无上限**：画像加 top-k 超过 800 token 就要警惕，记忆系统自己变成上下文污染源。
- **静默写入**：用户不知道助手记了什么，信任崩得极快。至少提供一个查看记忆列表的入口。

## 可复用建议

- 存储用 SQLite 加一列 embedding 就够了，关键是可导出、可 diff，别上来就引重型向量库。
- 做回放回归：拿历史会话跑一遍，断言"应该被召回的记忆确实被召回"，这是记忆系统唯一可靠的测试方式。
- 提取 prompt 的质量比存储选型重要一个数量级，先迭代它，再优化检索。

## 总结

记忆系统的本质不是"存得多"，而是写得严、取得准、清得勤。落地顺序建议：先跑通画像层固定注入，再补情景层混合检索，最后加审计与衰减清理。按这个节奏，一个可靠的最小版本两周内可以跑起来，之后的所有优化都建立在能被回放验证的基础上。
