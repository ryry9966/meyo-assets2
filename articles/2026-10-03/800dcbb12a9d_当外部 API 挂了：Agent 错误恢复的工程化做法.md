## 背景

跑过长期自动化的人都有体感：Agent 的故障大多不是模型不行，而是外部依赖出问题——LLM 供应商 429、搜索接口超时、MCP server 背后的业务 API 503。单次成功率 99% 的 API，在一天几百次工具调用的流水线里，"挂"是常态而不是异常。

## 问题

默认情况下，Agent 遇到 API 故障通常是这几种表现：

1. 框架层抛异常，整条任务链直接中断；
2. 模型收到原始报错后自作主张，反复重试，白烧 token；
3. 更糟的是模型"脑补"一个结果继续往下跑，产出看起来正常，实际是假的；
4. 多个并发任务同时重试，把刚恢复的服务又打挂（重试风暴）。

共同根源是：错误处理被交给了最不该负责重试决策的一层——模型本身。

## 做法

核心原则：**重试和降级放在代码层，模型只做决策，不做机械操作。**

**1. 先分类，再重试。** 区分可重试（429、502、503、超时）和不可重试（401、403、配额耗尽、参数错误）。后者重试一百次也没用，只会浪费配额。

**2. 有限次指数退避 + 抖动。** 建议 2~3 次，间隔 1s/4s/16s 加随机抖动，有 `Retry-After` 头就遵守。重试上限硬编码，绝不让模型在循环里自己数。

**3. 每个 MCP 工具调用强制设超时。** 别依赖 SDK 默认值，连接、读取分开设。很多"卡死"本质是没超时的 HTTP 请求挂着不返回。

**4. 结构化错误回传给模型。** 工具层 catch 之后，给模型的不是 stack trace，而是：

```json
{
  "ok": false,
  "error": "upstream_timeout",
  "retryable": false,
  "hint": "检索服务暂不可用，可跳过检索基于已知信息回答，并在结果中标注数据缺失"
}
```

模型拿到 `hint` 才能做出合理降级：跳过、换数据源，或如实告诉用户失败。

**5. 断路器 + 降级路径。** 同一上游连续失败 N 次后短路，后续调用直接走降级：读缓存、切兜底数据源、或把该步骤标记为"跳过待补"。长任务做 checkpoint，恢复时从断点续跑，不从头重来。

**6. 明确失败 > 假装成功。** 最终报告里要有"哪些步骤降级了、哪些数据来自缓存或缺失"的声明。宁可交付八成完整但可信的结果，不要十分完整但掺假的结果。

## 踩坑点

- **幂等性没做就上重试。** POST 类操作（下单、发消息）重复调用就是重复扣款。要么带幂等键，要么只对 GET 重试。
- **只 catch 了 timeout。** 连接拒绝、DNS 失败、TLS 错误是另一类故障，漏了就是裸奔。
- **把错误响应当成功缓存了。** 降级缓存要区分成功结果和错误信息，后者过期时间必须极短。
- **并发任务的重试预算没隔离。** 十个任务各重试三次就是三十次请求，恢复期的服务受不了，需要全局并发上限。
- **日志只写 "API failed"。** 必须带时间点、重试次数、错误分类，否则复盘全靠猜。

## 可复用建议

- 把 timeout + 重试 + 断路器 + 结构化错误封成统一的工具调用 wrapper，所有 MCP 工具走同一入口，别每个插件各写一套。
- 定期做故障演练：手动断掉某个上游，验证降级路径真的触发、报告里真的如实标注。
- 盯三个指标：上游失败率、重试总次数、降级触发次数。最后一项突然归零往往不是好事——可能监控自己先挂了。

## 总结

Agent 的错误恢复，核心不是让模型更聪明，而是让工程层"更笨但更可靠"：分类、退避、断路、降级、留痕——这些是分布式系统十年前的老手艺，放到 Agent 时代一样管用。模型擅长的是在降级之后决定"接下来怎么办"，而不是在故障现场亲自重试。把这两层职责分开，你的自动化才敢真正无人值守地跑。
