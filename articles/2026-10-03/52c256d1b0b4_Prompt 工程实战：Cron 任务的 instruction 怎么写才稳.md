## 背景

OpenClaw 的 cron 任务本质上是"无人值守的定时 prompt"：到点触发，agent 拿着 instruction 独立跑一遍，结果发到通知渠道或落成文件。它和交互式对话最大的区别是——**没有人在线回答问题，也没有上一轮的上下文**。这个前提决定了 instruction 的写法必须和聊天 prompt 区分开。

## 问题

我最初的做法很偷懒：把会话里用得顺手的 prompt 直接粘进 cron。结果连续翻车：

- agent 在输出里反问"您指的是哪个仓库？"，那次调度直接浪费了；
- "总结一下昨天的工作"这种指令，三天产出了三种格式，下游解析脚本崩了；
- 一次上游 API 挂掉，agent 自己重试了七八次，token 烧了不少，没有有效产出。

根因都一样：交互式 prompt 默认"人在场"，可以随时纠偏；cron 场景里人不在，含糊的地方就变成事故。

## 我的写法

后来我固定了一个六段式骨架，每个 cron 任务往里填：

```
【目标】每天 09:00 汇总 org/xxx 仓库过去 24h 的 open PR。
【输入】只看这个仓库，不要扫描其他来源。
【步骤】1) 列出 open PR；2) 过滤掉 draft；3) 按"待我 review / 其他"分组。
【输出】Markdown 列表，每条一行：PR 号、标题、作者、+/- 行数；最多 10 条。
【边界】只读操作，不要 approve / merge / 评论，不要主动发消息。
【失败处理】拉不到数据就输出一行 SKIP 加原因，重试不超过 2 次。
```

几个要点展开：

1. **一个任务一个交付物。** 多步流水线就拆成多个 cron 或上游脚本，别把十条指令塞进一个 instruction。
2. **上下文自带。** 仓库地址、文件路径、工具名全部写死在 instruction 里，不依赖记忆和历史会话。
3. **输出格式给模板。** 让 agent 自由发挥，等于把解析风险留给未来的自己。
4. **明确失败行为。** "失败就跳过并说明原因"远比"尽力完成"可靠。

## 踩坑点

- **指代词是隐形炸弹。**"上次那个项目""我们说好的方案"，在隔离会话里全部失效。
- **时区和"今天"。** 服务器多半是 UTC，"汇总今天的日报"可能错位八小时。要么注入时间变量，要么在步骤里让 agent 先执行一次 `date`。
- **权限没收紧。** 交互时说"顺手处理一下"没问题，无人值守时"处理"可能意味着发消息甚至改文件。默认只读，写操作必须白纸黑字列出。
- **上线前没试跑。** cron 的 instruction 一定先在交互会话里原样跑一遍，确认产出符合预期，再挂上调度。

## 可复用建议

- 把 cron instruction 当代码管理：进仓库、写注释、改动留版本，不要只存在调度器的表单里。
- 新任务先以只读模式跑一周，稳定后再逐步放开写权限。
- instruction 控制在 10~20 行，超长通常说明这个任务该拆了。

## 总结

Cron instruction 的核心不是写得花哨，而是把"人不在场"这个前提刻进每一条：上下文自带、输出定式、边界收紧、失败有出口。六段式骨架不一定适合所有人，但"自包含、可验证、有止损"这三条，建议作为所有定时任务的底线。
