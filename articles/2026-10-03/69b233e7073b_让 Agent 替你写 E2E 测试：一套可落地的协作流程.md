## 背景

E2E 测试一直是自动化里性价比最尴尬的一层：覆盖关键路径价值高，但编写慢、维护苦、坏得快，团队里往往只有少数人愿意写，大部分流程裸奔上线。有了浏览器类 MCP 工具（Playwright MCP 这类）之后，“让 Agent 以用户身份实际操作一遍页面、顺手产出测试”变成了可行路线。我们在两个项目上跑了几个月，整理一下经验。

## 问题

直接对模型说“帮我写个登录的 E2E 测试”，产物通常是三种：凭想象写的、跑不过的；能跑但断言很弱（点完按钮只检查接口 200）；或者依赖 sleep 和按钮文案，三周后就 flaky。根因有两个：模型没有真实执行轨迹，也没有你们项目的测试约定。

## 做法

1. **先让 Agent 跑一遍流程。** 用浏览器 MCP 连 staging，让 Agent 实际填表、提交、等结果。关键是拿到真实的无障碍树快照和网络请求记录，而不是让它凭空编。
2. **基于执行轨迹生成测试。** 要求输出 Playwright 用例，等待只用 `expect` 轮询和网络断言。
3. **把项目约定喂给它。** 我们维护一份简短的 TEST_GUIDE：

```text
- 选择器只用 data-testid，禁止 getByText / nth
- 等待只用 expect 轮询与网络断言，禁止 waitForTimeout
- 每条用例自带 seed 与清理，禁止依赖执行顺序
- page object 按既有目录组织，参考 golden/ 下三个示例
```

   短约定加两三个高质量示例，比长篇 prompt 有效得多。
4. **人审断言，Agent 修失败。** 用例红了让 Agent 自己看 trace 修复，但断言部分必须人审——这是唯一不能外包的环节。
5. **做断言强度检查。** CI 加一个轻量 mutation 步骤：故意改坏一个业务条件，对应用例必须红。不红说明断言是摆设。

## 踩坑点

- **弱断言最常见。** Agent 倾向于“元素出现就算通过”，要把交互后的状态断言明确写进约定。
- **文案选择器。** 它很爱 `getByText('提交')`，一改版全挂。约定强制 data-testid，lint 兜底。
- **它会编造测试账号和接口。** 提供专用测试账号与 seed 端点，并在 MCP 工具层把生产环境域名屏蔽，别靠 prompt 自觉。
- **上下文超载。** 整页 HTML 太大，喂无障碍树快照加关键请求，稳定且省 token。
- **幻觉 API。** 偶尔会用不存在或已废弃的方法。把本地类型定义暴露给它读，比在 prompt 里背 API 可靠。

## 可复用建议

- 约定文件化（AGENTS.md / TEST_GUIDE.md），短、可 lint、随代码演进。
- 示例即规格：维护 2~3 个金标准用例，生成质量直接对齐。
- 把 Agent 产出的测试当实习生的 PR：必须人审，必须过 mutation 检查。
- 记一个指标：生成用例上线后三个月内的失效次数，用它判断这条路到底省没省时间，而不是靠体感。

## 总结

Agent 写 E2E 的价值不在“省敲代码”，而在于把“执行流程”和“产出测试”合并成一步，让覆盖关键路径的成本低到可以随手做。前提是三件事：让它基于真实执行轨迹工作、用约定和示例约束它、用 mutation 检查兜住断言质量。做到这三点，E2E 覆盖率才能从“看心情”变成“看流程”。
