## 背景

OpenClaw 这类 Agent 网关的价值不在"会聊天"，而在"能动手"：查工单、拉报表、发告警、操作内部系统，这些动作本质都是 API 调用。Agent 本体并不懂任何一家服务的协议，它依赖工具层——本地 skill 或 MCP server——把 HTTP 请求翻译成模型可理解的工具描述。所以"对接外部服务"实际是三层握手：模型选工具、工具发请求、服务返回结果。任何一层没设计好，最终表现都是同一句话："这个 Agent 不好用。"

## 我们遇到的问题

接手第一个内部系统时，踩了三类典型坑：

1. **密钥管理混乱**——有人把 API key 直接写进系统提示词，日志里全裸奔；
2. **工具描述含糊**——模型分不清"查订单"和"查物流"该调哪个，乱选；
3. **失败无兜底**——上游限流返回 429，Agent 收到原始报错后胡言乱语，甚至死循环重试。

## 做法

**第一步，选接入形态。** 一次性、单端点的调用，写个本地 skill 包一层 HTTP 即可；要多工具、跨项目复用、带状态（比如 token 刷新），就起一个 MCP server。判断标准很简单：会被第二个 Agent 用到的东西，才值得做成 MCP。

**第二步，收紧工具边界。** 一个工具只做一个动作，参数尽量少。description 里写清"何时用、何时不用"，比罗列参数说明有用得多。不要把整份 API 文档塞进上下文——只暴露 Agent 真正需要的两三个端点。

**第三步，密钥走注入。** key 放环境变量或配置中心，skill 运行时读取，不进对话、不进日志。轮换密钥只改配置，不动代码。示意配置（节选）：

```yaml
tools:
  - name: query_order
    type: http
    endpoint: ${ORDER_API}/orders
    auth_env: ORDER_API_KEY
    timeout: 8s
    retry: 2
```

**第四步，错误语义化。** 超时设短（10 秒内），网络类错误重试 2 次加退避；4xx 则把"原因 + 建议（如：凭证失效，不要重试）"返回给模型，让它能自我纠正，而不是盲目再来一次。写操作必须带幂等键，或在工具层加一步人工确认。

**第五步，留审计日志。** 每次工具调用记录：时间、工具名、参数摘要、状态码。出问题时能回放，比任何猜测都省时间。

## 踩坑点

- 工具把原始 JSON 全量塞回上下文，几轮就 token 爆炸。工具层做字段裁剪，只回 Agent 需要的几个字段；
- 写接口没做幂等，Agent 重试一次，客户收到两条重复告警；
- 401 之后模型反复重试，白白烧 token——错误信息里必须明确"停止重试"；
- SSE/长轮询接口用同步工具死等结果，必然超时。拆成"提交任务 + 查询状态"两个工具更稳。

## 可复用建议

- **先读后写**：接任何服务，先只开放查询类工具，跑稳一周再放写操作；
- **粒度宁小勿大**：小工具组合的容错性远好于一个"万能大工具"；
- **建脚手架**：做一个内部 MCP server 模板，把鉴权、重试、日志、字段裁剪都固化进去，新服务接入只剩"填端点、写 description"两件事。

## 总结

对接外部服务不是"调通 API"就结束，真正的工程量在握手协议之外：密钥、边界、错误语义、幂等、审计。把这五件事模板化，Agent 的可靠性才能从"看运气"变成"可交付"。下次再有人问"怎么接 XX 服务"，先看这五项有没有落位，再谈别的。
