## 背景

E2E 测试是很多团队"知道该写但一直欠债"的部分。手写 Playwright 用例要处理选择器、等待、mock 数据，一条核心链路写下来就是一两天，页面一改版又得跟着维护。最近我把这块活儿交给 agent 试了试：用 OpenClaw 起一个带浏览器 MCP 工具的 agent，让它基于真实页面结构生成用例骨架，人只负责审断言。跑了一个月，核心链路的覆盖从零到了能看的水平，维护成本确实降了——但中间踩的坑不少，值得记录。

## 问题

直接把需求丢给 agent 说"帮我写 E2E 测试"，通常会得到三类结果：

- 凭想象编 DOM 选择器，跑起来全挂；
- 大量固定 sleep 的"能过但不稳定"用例；
- 断言照着操作复述一遍（点了个按钮就断言按钮存在），测了个寂寞。

根因是 agent 缺两样东西：**真实页面上下文**和**明确的验收标准**。要做的事就是补上这两块。

## 做法

流程五步，都可以在 OpenClaw 里落：

1. **喂真实上下文。** 不用截图，通过 Playwright MCP 拿页面的 accessibility tree 和关键交互元素的 role/name。a11y 树比整个 DOM 紧凑得多，而且天然贴近 `getByRole` 的写法。
2. **人先写断言清单。** 每条链路用三五行列出"做完这件事后世界应该是什么样"，比如"下单后列表出现新条目、购物车计数加一"。这是业务判断，不该外包给模型。
3. **agent 生成骨架。** 在 skill/runbook 里写死约束：只用 Page Object、只用 `getByRole`/`getByLabel`、禁止固定 sleep、等待一律用可重试的断言。
4. **真实跑，失败回灌。** 用例进 CI 跑一遍，把报错和 trace 原文贴回给 agent 让它修。多数失败是选择器和等待问题，它修得动；逻辑性的失败它会承认改不了，这时人介入。
5. **沉淀 golden 用例。** 挑三五条跑得稳的作为 few-shot 样例放进 skill 文件，之后新生成用例的风格和稳定性明显收敛。

## 踩坑点

- **别让 agent 既当运动员又当裁判。** 生成和验证必须是两个环节：验证只能来自真实 runner 的输出，不能来自它自己"我觉得能过"。
- **断言必须人审。** 我第一版偷懒让 agent 自拟断言，结果约 30% 的用例是同义反复。断言清单前置后，这个问题直接消失。
- **截图喂模型性价比很低。** 视觉模型对选择器基本靠猜，a11y 树一次就能给准。
- **限制单次生成数量。** 一次要 20 条，会收获 20 条半斤八两的；一次 3 条、跑通再继续，质量高得多。
- **mock 数据让它问你要。** agent 编造的测试账号和返回体，跑一次挂一次，别省这个沟通成本。

## 可复用建议

- 把第 1、3 步固化成一个"测试生成" skill 文件，团队复用同一份 agent 配置，不用每次口头交代。
- 选择器规范（只准 role/label）写进约束，比事后 code review 省一半时间。
- 失败回灌的 prompt 模板值得保存：报错原文 + trace 片段 + 当前用例，三段式，修复成功率明显更高。
- 项目里已有手写用例的话，先让 agent 读一遍再生成，风格一致性会好很多。

## 总结

Agent 写 E2E 测试，价值不在"全自动"，而在把最枯燥的骨架和选择器工作接走，把断言和验收这个真正需要业务判断的环节留给人。用 OpenClaw 加 MCP 浏览器工具搭这条流水线，半天能跑通，之后维护一个 skill 文件就够了。别指望它替代测试设计，但作为测试基建的加速器，目前是够格的。
