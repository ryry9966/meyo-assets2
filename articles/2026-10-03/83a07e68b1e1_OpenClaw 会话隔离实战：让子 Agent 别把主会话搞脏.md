## 背景

OpenClaw 的主会话是长期存活的：上下文里积累着你的偏好、项目背景、历史纠错结论。它好用，靠的就是"干净"。而子 Agent（sub-agent）解决的是另一类活：批量抓取、长文档梳理、反复试错的浏览器操作——这些任务的中间产物又多又碎，和主会话需要的"长期有效信息"完全是两种东西。

## 问题

如果把重活直接丢在主会话里干，通常会发生：

- 每次工具调用的返回值都进主上下文，一次抓 20 个页面，几轮之后主会话就被过程数据填满；
- 模型开始"看到"大量无关细节，后续正常对话质量肉眼可见地下降；
- 上下文触发压缩时，琐碎的爬虫日志占着位置，真正重要的长期记忆反而可能被挤掉。

这就是"污染"：一次性任务的过程数据，永久占据了主会话的注意力预算。

## 做法

我的工作流三步：

1. **识别重活**。凡是"过程数据多、结论少"的任务（批量检索、长文件分析、密集试错），默认不开在主会话。
2. **spawn 子 Agent**。主 Agent 派生子 Agent，后者拥有独立的 session 文件，工具调用、观察、试错全部落在自己的 transcript 里，主会话只接收最终报告。
3. **写死返回约定**。派生时明确要求：只返回结论 + 关键产出路径，控制在几百字以内；中间产物写到指定工作目录或 tmp，不要贴回正文。

验证方法很直接：跑完一个重任务后查看各 session 的体积，主 session 应该只增长几百 token（那封报告），子 Agent 的 session 则会有几十 KB。这个差值就是隔离生效的证据。

## 踩坑点

- **共享工作区是最大的隐性通道**。子 Agent 和主 Agent 默认共用 workspace，如果它顺手改了共享笔记或记忆文件，等于绕过会话隔离直接污染主上下文。重活给独立子目录，或明确禁止写共享文件。
- **并发子 Agent 写同一个文件**会互相踩。要么各写各的文件、由主 Agent 汇总，要么干脆串行。
- **别让子 Agent 反问**。它没法把澄清问题送回给你，派生前把上下文写足，宁可多给一段背景。
- 子 Agent 自己也会膨胀。超长任务拆成两段 spawn，别让单个子 Agent 在自己会话里经历压缩，结果质量会掉。

## 可复用建议

- 把"哪些任务进子 Agent"写进 AGENTS.md 或系统提示，让路由变成默认行为，而不是每次临时判断；
- 给子 Agent 的返回定模板：结论 / 产出文件路径 / 未解决项，三段式最好用；
- 主会话保持"调度者"心态：读报告、做决策、派活，不亲自搬砖。

## 总结

会话隔离的本质不是"多开几个 session"，而是控制信息流的方向：过程数据留在子会话里自生自灭，结论和决策才回流主会话。守住这条边界，主会话才能在长期使用中保持稳定的高质量。
