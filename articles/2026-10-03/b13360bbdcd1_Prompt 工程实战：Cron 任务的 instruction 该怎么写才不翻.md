## 背景

在 OpenClaw 里给 agent 挂一个 cron 定时任务，本质上是给未来某个无人值守的时刻留一张字条。交互式对话里 prompt 写得糙没关系——agent 会反问，你可以补充，来回几轮就修正了。cron 没有来回：到点触发，agent 独自执行，结果要么落地要么丢失。所以 cron 的 instruction 不是普通 prompt，更像一段要跑在生产环境的脚本。

## 三类典型翻车

- **上下文悬空**："把刚才整理的内容发出去"——凌晨三点没有"刚才"，agent 只能猜，或者干脆编。
- **输出失控**："看看今天的新闻，有值得说的就发群里"——什么算"值得"、发几条、多长，全没约束，轻则刷屏，重则格式漂移导致下游自动化解析失败。
- **失败静默**：API 挂了、文件不存在，agent 自行"灵活处理"，你以为任务在跑，其实已经空转一周。

## 做法：按脚本的方式写 instruction

我用一个固定骨架，六个字段，缺一项就补：

```
任务：一句话说清做什么
输入：数据从哪来（具体路径/关键词/ID），拿不到怎么办
步骤：2-4 步，每步一个动作
输出：写到哪（文件/频道/消息），给格式样例，定长度上限
边界：明确禁止项（不回复历史消息、不额外调用工具、最多重试 N 次）
异常：任何一步失败，把错误追加到日志文件，本次不发通知
```

两个关键点：

1. **自包含**。所有路径、日期、频道名都写死在 instruction 里，不留任何"如前所述"。
2. **结果有落点**。每次运行要么产出文件、要么发一条消息、要么写日志，三选一必须发生——否则你无法判断它到底跑没跑。

上线前先手动触发一次 dry run，翻一遍运行记录（transcript），看 agent 实际调了哪些工具、输出长什么样。这一步能拦掉八成问题。

## 踩坑点

- **时区**。cron 调度和 instruction 里的"每天"分别用什么时区，两边都写明（如 Asia/Shanghai），别依赖默认值。
- **幂等**。任务重跑很常见，加一句"若目标文件已含今日日期则跳过"，比事后清理重复消息便宜得多。
- **工具可用性**。交互会话里能用的 MCP 工具，cron 会话里未必已加载。instruction 里写清依赖哪些工具，首跑时逐一确认。
- **别依赖"记忆"**。跨运行的持久状态写文件，别指望 agent 记得上次干了什么——很多 cron 会话是隔离的。
- **单次要小**。一个任务让 agent 连做五十次工具调用，失败率高还难排查；宁可拆成两个任务、提高频率。

## 可复用建议

- 把 instruction 当代码：放进仓库版本化，改 prompt 等于改代码，留 commit 记录。
- 挂了先看 transcript 再改 prompt，像修 flaky 测试一样迭代，而不是凭感觉加形容词。
- 每类任务沉淀一个模板（日报、监控、备份通知），新任务从模板复制，不从零写。
- 交互对话里调好的 prompt 不要直接搬去 cron：语义相同，约束完全不同。

## 总结

cron instruction 的核心不是写得聪明，而是写得**可验证**：自包含、输出有落点、失败有分支、边界写得死。它是一段无人值守的脚本，用脚本的纪律去写，agent 才能稳定替你值夜班。
