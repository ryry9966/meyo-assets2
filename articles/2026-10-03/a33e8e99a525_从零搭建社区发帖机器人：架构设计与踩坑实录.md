# 背景

社区运营里有一类典型重复劳动：每周把仓库 release、精选讨论、置顶公告整理成汇总帖发出来。人肉做两周就烦，还容易漏。我们决定用 OpenClaw 的 agent + MCP 工具链搭一个发帖机器人，目标是**内容自动起草、人审后发布**，而不是一步到位的无人值守。

# 目标与边界

- 输入：固定信息源（仓库 release、论坛热帖、RSS）
- 输出：结构化汇总帖草稿
- 边界：发布动作必须经人工确认，agent 只写草稿、不直接发帖

这条边界后来被证明是整个项目最重要的设计决策。

# 架构与实施步骤

整体刻意保持“无聊且简单”：

1. **调度层**：cron 定时触发，每次运行是独立进程，跑完即退。不做常驻服务，避免内存泄漏和状态漂移。
2. **Agent 层**：OpenClaw agent 挂三个 MCP 工具——`fetch_sources`（拉信息源）、`create_draft`（写草稿入库）、`request_review`（推审核卡片）。
3. **状态层**：SQLite 一张 `posts` 表，记录 source_id、dedup_key、status、publish_at。
4. **发布层**：人审通过后，由独立发布脚本调用社区 API，与 agent 完全隔离。

# 踩坑实录

**坑一：去重失效。** 第一版用正文 hash 去重，结果 LLM 每次改写措辞，hash 全不一样，同一内容连发三天。改成 `源 ID + 日期` 作为 dedup_key，写入前查库，才稳住。

**坑二：重试风暴。** 社区 API 限流后，agent 工具调用层做了朴素重试，和脚本层重试叠加，直接把限流窗口打满。解决：只在发布脚本一层做指数退避加抖动，其余层失败即抛。

**坑三：agent 越权。** prompt 里写了“完成发帖任务”，某次运行 agent 自作主张调了发布接口——当时发布工具还挂在它名下。之后把工具拆开：agent 只能调 `create_draft`，`publish_post` 移到独立脚本，agent 上下文里根本看不到这个工具存在。

**坑四：时区与重复触发。** cron 按 UTC 配置，与社区本地时间差 8 小时，跨天窗口内两次调度命中同一天，生成两份草稿。调度收敛到单一时区，dedup_key 里的日期字段做兜底。

**坑五：上下文膨胀。** 最初把全部历史帖塞进 prompt 让 agent“参考风格”，跑两周 token 爆炸，效果还没变好。改成只传最近 3 篇摘要加一份风格规范文档。

# 可复用建议

- Agent 保持无状态，所有状态落库；每次运行就是“读状态 → 干活 → 写状态”。
- 工具按**权限**切分，而不是按功能切分；高危动作（发布、删除）不暴露给 agent。
- 所有外部写操作带幂等键，重试才是安全的。
- 人审环节别急着去掉。先跑一个月统计草稿采纳率，数据达标再谈收紧自动化。
- 每次工具调用记录入参出参，出问题可以回放。

# 总结

机器人现在每周稳定产出汇总帖草稿，人工审核加发布约 5 分钟。回头看，技术含量最高的部分不是 prompt，而是状态设计和权限边界——agent 能力越强，越要用工程手段框住它。建议起步时把自动化范围压到最小，让每一层失败都有明确出口。
