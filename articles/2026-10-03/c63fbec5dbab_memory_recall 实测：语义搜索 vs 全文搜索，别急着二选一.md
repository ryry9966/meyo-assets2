## 背景

我们把 OpenClaw 当长期个人助理跑了几个月，记忆层就是 memory 目录下的一堆 markdown：memory.md、按日期拆分的 session 笔记。助手靠 `memory_recall` 把历史笔记捞回上下文。默认检索是全文匹配，后来社区不少人换成 embedding 语义检索。两种方案我都在生产里跑了一个月，给个真实结论。

## 问题

全文检索的痛点是**换说法就搜不到**：当时记的是“部署脚本在 /srv/deploy”，三周后问“上线流程”，一条都召回不了。语义检索正好反过来，专有名词召回很差——文件路径、错误码、报错 ID 这类精确 token，embedding 经常给你几条“意思差不多”的噪声，还把真正的命中挤出 top-k。两边都不是全能选手。

## 做法

1. **先建评测集**：从真实对话里挑 30 条“问题 → 期望命中的记忆片段”，这是后面一切调参的地基，没有它全靠感觉。
2. **跑全文基线**：FTS5 + BM25，中文注意分词，我用 ngram 兜底，避免口语化切分导致漏召回。
3. **加语义通道**：embedding 模型本地起服务，chunk 控制在 300–500 字、带 overlap，cosine 取 top-5。
4. **混合融合**：两路结果用 RRF 合并，再按时间衰减微调排序。
5. **回归验证**：每次改动跑一遍评测集，看 hit@3 和平均延迟。

## 踩坑点

- 语料太小（几百条以内）时语义检索优势不明显，反而引入模型依赖和额外延迟；
- top-k 别贪多，召回 10 条塞进 prompt，噪声会拉低回答质量，3–5 条最好；
- 记忆文件更新后忘重建索引，语义库里全是旧向量，这个 bug 排查了一整晚；
- 同一短语在不同分词器下行为差异很大，评测集必须覆盖口语化问法。

## 可复用建议

- **默认上混合**：全文打底保证精确命中，语义补充兜住换说法，RRF 融合成本低、效果稳；
- 文件路径 / 命令 / 错误码走全文或前缀匹配，别指望向量；
- markdown 保持唯一事实源，索引只是派生物，随时可重建，别往索引里塞没有源文件的数据；
- 如果把 `memory_recall` 包成 MCP 工具，记得暴露 top-k 和时间过滤参数，让上层 Agent 能自己控召回范围。

## 总结

这不是二选一的题。中小规模记忆库下，“全文打底 + 语义补充 + 一套简单评测循环”是目前性价比最高的组合。语义检索是补充不是替代——精确 token 的检索，永远是全文的主场。
