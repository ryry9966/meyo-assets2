## 背景

E2E 测试是前端团队最不想写又躲不开的活：写起来慢、选择器脆、UI 一改全红。但它恰好有个特点——大量重复模式（打开页面、填表单、断言结果），同时又需要对真实应用的理解。这正好是 Agent 与人的分工点：Agent 干机械活，人定“测什么”。

我们在内部项目里用 OpenClaw 的 agent 挂 Playwright MCP 做了一轮实践，目标是让 Agent 产出能进主干 CI 的 E2E 用例，而不是玩具 demo。以下是跑通后的流程和教训。

## 核心问题

直接把 PRD 扔给模型“帮我写 E2E”，基本不可用：

1. 模型没见过真实 DOM，选择器全靠猜，跑起来一片飘红；
2. 生成断言太弱，典型症状是“页面包含我刚输入的内容”——永远通过，测了个寂寞；
3. 一次性生成没有反馈回路，失败后不会自己修。

所以关键不是打磨提示词，而是给 Agent 一个**带真实环境、能运行、能读失败输出的闭环**。

## 做法：四步闭环

**1. 准备环境与上下文。** 提供可登录、数据可重置的 dev 环境；写一份测试规范（目录结构、命名、fixture 用法、等待策略），连同 1~2 个人写的标杆用例放进 agent 上下文。标杆用例比十条规则管用。

**2. 先探索，再写。** 通过 MCP 浏览器工具打开页面，用可访问性树快照（而非整页 HTML 或截图）了解真实结构。先产出一份“用户旅程清单”（登录 → 建单 → 提交 → 验证），人确认后再生成。这一步是防止它虚构功能的关键。

**3. 生成即运行，失败即修复。** 用例立刻在 dev 环境执行，把失败 trace 和报错喂回 agent，让它自己改选择器、补等待。限制最多 3 轮修复，修不好的标出来留给人。

**4. 人工只审断言语义。** 选择器、等待、样板代码可以不看，重点审两条：这条用例失败时，是否真的意味着功能坏了？断言覆盖的是业务结果，还是表面文案？

## 踩坑点

- **永远通过的用例**：Agent 默认断言“自己刚做的事”。要求它对每个断言回答“什么情况下这行会红”，答不上来的删掉。
- **sleep 硬等**：Agent 很爱写 `waitForTimeout(3000)`。规范里明确禁止，统一用 `expect(...).toBeVisible()` 这类自动轮询断言，否则 CI 必然偶发红。
- **上下文爆炸**：整页 DOM 快照轻松几十 K token。统一走 a11y 快照，按需展开局部。
- **改应用代码迁就测试**：权限上明确只允许改测试文件。我们出现过一次它为了通过测试改了组件渲染逻辑，此后权限收紧。
- **选择器过拟合**：它倾向抓当下恰好唯一的 class。约定优先 `data-testid`，没有就先补上再生成。

## 可复用建议

1. 把“测试规范 + 标杆用例”沉淀成 OpenClaw 的 skill 文档，所有 agent 复用同一套约定；
2. 每次人工修正后，把 diff 回灌进上下文作为 few-shot，两三轮后同类错误基本消失；
3. 按关键旅程排优先级，别追覆盖率数字——10 条高价值旅程用例胜过 50 条凑数的；
4. UI 大改后让 agent 重跑探索步骤，对比结构快照，主动报“该页面结构变更，涉及 X 条用例”。

## 总结

这轮实践后，E2E 初始编写时间约降到原来的三分之一，但真正值钱的是角色变化：Agent 负责“怎么写对”，人负责“写什么、为什么写”。建议从一条最关键的用户旅程开始，先跑通闭环再扩量——没有运行和修复回路，生成再多用例也只是代码的搬运。
