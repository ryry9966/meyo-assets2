## 一、背景：Agent 干活要"伸手"

LLM 本身只会生成文本。要让 Agent 真正做事——读数据库、查文件、发工单——就必须让它调用外部系统。在 MCP 出现之前，这件事的做法很朴素：宿主应用（比如 OpenClaw 这类 Agent 框架、IDE 助手）针对每个目标系统写一套胶水代码，自己定义工具格式、鉴权方式、错误处理。

## 二、问题：M×N 的集成成本

问题不在能不能跑通，而在规模。3 个宿主 × 10 个系统，就是 30 份互不相通的连接代码：

- 各家工具描述格式不同，同一个系统的接入逻辑要写多遍；
- 鉴权、分页、错误语义各自为政，换宿主等于重做；
- 模型看到的工具 schema 千奇百怪，调用准确率参差不齐。

本质上，这就是"每对客户端-服务端都要定制"的 M×N 问题。

## 三、MCP 的做法：把两边解耦成协议

MCP 很克制：不碰模型，只规范"宿主"与"工具提供方"之间的通信层。

三个角色先分清：

- **Host**：跑模型、发起请求的应用；
- **Client**：宿主内部与某个 Server 保持 1:1 连接的连接器；
- **Server**：独立工具进程，本地走 stdio，远程走 Streamable HTTP。

Server 暴露三类原语：**Tools**（模型可调用的操作）、**Resources**（可读数据如表结构）、**Prompts**（预置模板）。底层是 JSON-RPC 2.0，方法名统一：`initialize` 握手、`tools/list` 发现、`tools/call` 调用。于是 30 份胶水代码变成 3+10：宿主实现一次协议，每个系统只写一个标准 Server。

## 四、上手：四步跑通

1. **先跑现成的**：用官方 SDK 自带的 filesystem 或 sqlite server，不改代码先体验。
2. **在 OpenClaw 里注册**：配置 MCP 段（command/args 或 URL），启动后确认宿主日志里出现 `tools/list` 返回的工具清单。
3. **用真实任务验证**：比如"列出某目录最近修改的文件并汇总"，观察模型是否选对工具、参数是否正确。
4. **写一个最小 Server**，Python FastMCP 十几行就够：

```python
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("ops-tools")

@mcp.tool()
def disk_usage(path: str) -> str:
    """返回指定路径的磁盘占用摘要。"""
    import shutil
    total, used, _ = shutil.disk_usage(path)
    return f"used {used // 2**30}G / total {total // 2**30}G"

mcp.run()
```

## 五、踩坑点

1. **工具描述是写给模型看的**。描述含糊、参数没写清副作用，模型就会选错工具传错参。`delete_file` 和 `move_file` 描述不清，后果完全不同。
2. **工具数量会吃掉上下文**。每个 schema 都进 prompt，一个 Server 塞 50 个工具等于每轮对话先交一笔固定税，按场景拆分。
3. **stdio 进程生命周期**。本地 Server 起不来，八成是虚拟环境路径、npx/uvx 版本或环境变量没传进去；宿主重启后能否拉起 Server 也要提前验证。
4. **权限就是运行用户的权限**。MCP 目前没有细粒度沙箱，装第三方 Server 约等于运行一个能读写本地文件的程序，先只读跑稳，再放开写操作。
5. **规范和 SDK 还在演进**，版本间偶有行为差异，生产环境把 SDK 版本 pin 死。

## 六、可复用建议

- 一个 Server 只做一件事，工具面越小越稳；
- 工具命名用"动词+宾语"，描述里写清参数约束与副作用；
- 危险操作在 Server 层加 dry-run 或二次确认；
- 把每次 `tools/list`、`tools/call` 的原始报文落日志，90% 的排障靠它。

## 七、总结

MCP 没有让模型变聪明，它只是把集成成本从 M×N 压到 M+N，把"工具怎么描述、怎么发现、怎么调用"变成了公共基础设施。协议本身不复杂，真正决定落地质量的是工具设计、上下文开销控制和权限治理——这三件事，是每个团队自己的功课。
