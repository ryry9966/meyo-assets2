## 背景

OpenClaw 这类 agent + MCP 工具链跑起来之后，最先撞上的往往不是能力问题，而是权限问题。模型能调 shell、能写文件、能发 HTTP 请求，问题就从"它会不会做"变成了"该不该让它自己做"。这个问题没有默认答案，但不提前想清楚，上线第一周就会还债。

## 问题

实践中常见两个极端：

- **全自动派**：为了跑通长任务把工具全开，结果一次 `rm -rf` 或一次误发的对外请求，毁掉整个工作目录甚至波及外部系统。
- **全确认派**：每一步都弹确认，人被确认框淹没，最后机械地点"允许"，确认机制形同虚设。

真正缺的不是"多问"或"少问"，而是一套可执行的判断标准。

## 做法：按"影响面 × 可逆性"分级

把每个工具调用放进二维矩阵，划成四档：

1. **只读操作**（可逆、影响面小）：读文件、查询、检索。直接放行，不要问。
2. **工作区内写入**（可逆、影响面小）：在 workspace 内改文件、写草稿。放行，但配限额，并用 git 兜底。
3. **有副作用的对外操作**（不可逆或影响面大）：shell 命令、发消息、调付费 API、`git push`。必须过确认。
4. **破坏性操作**（不可逆 + 影响面大）：删数据、改生产配置。默认禁止，仅白名单放行。

落地步骤：

1. 盘点 MCP server 和插件暴露的所有 tool，逐个标注等级；
2. 在 agent 配置里按等级设策略：放行 / 限额 / 确认 / 禁用；
3. 对第 3 类做"打包确认"：任务开始前让人审一次计划，而不是每步打断；
4. 全量调用日志 + 会话回放，出问题能定位到具体哪次调用。

## 踩坑点

- **确认疲劳**：确认频率一旦超过每分钟一两次，人就开始无脑点允许。宁可合并确认点，也不要高频打断。
- **粒度错位**：问"是否执行这条命令"太细，问"是否允许联网"太粗。按能力域授权（如"允许操作这个仓库"）比按单条调用授权稳定得多。
- **前缀匹配白名单**：`git` 开头就放行，等于把 `git push --force` 也放了。枚举子命令，不要匹配前缀。
- **权限漂移**：调不通就顺手加权限，三个月后权限表没人敢动。权限变更必须走 review。

## 可复用建议

- **默认拒绝，按需放行**——和防火墙同一个思路；
- 不可逆操作永远拆两步：先产出 diff 或预览，人看过再执行；
- 给 agent 留"降级出口"：拿不到权限时能明确说"这一步需要你确认"，而不是自己编绕路方案；
- 定期审计权限日志，把从没用过的授权收回来。

## 总结

权限边界的本质不是"信不信任模型"，而是把不可逆的决策留给人，把可逆的执行交给 agent。判断标准一句话：**出错之后能不能用一条命令恢复？** 能，就让它自己干；不能，就把确认点放在人还能保持注意力的地方。
