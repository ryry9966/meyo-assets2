## 背景

我们团队每天要发一封工程日报：服务异常、任务失败数、关键指标变化、待跟进事项。之前由值班同学手动从日志平台和监控面板里抄数，写一遍约 20 分钟，而且每天格式都不一样，下游没法做趋势对比。

## 问题

核心痛点有三个：

1. 原始日志量大、噪声多，人眼扫不过来；
2. 日报里的数字全靠手抄，容易错、容易漏；
3. 每个人写法不一致，数据无法积累和回溯。

一句话：人应该做判断，不该做搬运。

## 做法

整条流水线用 OpenClaw 编排，拆成四步：

**1. 定时采集。** cron 每天早上 07:30 触发一个 OpenClaw 任务，通过 MCP 调两个数据源插件：日志插件拉前一天 00:00–24:00 的原始日志，监控插件拉 P95 延迟、错误率、队列积压。

**2. 确定性聚合。** 关键数字不由模型算。用一个脚本插件先清洗聚合：按错误类型分组、计数、与前一日对比得环比，输出字段固定的中间 JSON：`error_groups`、`metrics_delta`、`slow_tasks`。

**3. Agent 总结。** 把中间 JSON 喂给 Agent，prompt 只要求两件事：结合日志上下文解释数字变化原因、把异常项按严重程度排序。输出用 JSON Schema 约束，校验失败重试一次，再失败就降级为纯数据版日报。

**4. 渲染与推送。** Markdown 模板固定格式，数据注入后通过 webhook 推到群里，同时归档一份到内部 wiki，文件名带日期，便于后续拉趋势。

## 踩坑点

- **模型算数不可靠。** 第一版让模型直接读原始日志统计次数，100 条以上就开始漏。改成脚本聚合后才稳定。原则：数字走代码，叙述走模型。
- **时区坑。** 日志平台是 UTC、服务器是本地时区，第一次跑出来的"昨天"实际截到了早上 8 点。所有数据统一先转 UTC 计算，展示时再转本地。
- **日志洪峰。** 某次发布产生几十万条重复报错，塞爆了上下文。聚合阶段必须先去重、做 top-N 截断，模型只看摘要。
- **输出漂移。** Agent 偶尔自作主张加"建议"字段或改标题。Schema 校验 + 重试 + 降级三件套是必要的，不要裸奔。

## 可复用建议

- 把日报拆成"数据层"和"叙述层"，两层分开演进，互不拖累；
- 中间产物 JSON 落盘，出问题可离线重跑，不必重新采集；
- 模板保留一个"人工备注"区块，值班同学补模型看不到的上下文；
- 先跑两周影子日报（自动版与人写版并行），比对无误后再切主流程。

## 总结

这套流水线上线一个多月，日报生成从人工 20 分钟降到 1 分钟内的确认动作，数字再没出过错。经验一句话：自动化日报的价值不在"让 AI 写文章"，而在把采集、聚合、校验这些确定性环节锁死，让模型只负责它擅长的解释与排序。越简单、越可校验的流水线，越能长期跑下去。
