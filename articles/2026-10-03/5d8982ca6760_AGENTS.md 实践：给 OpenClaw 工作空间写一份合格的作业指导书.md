## 背景

AGENTS.md 现在已经是个事实标准：Codex、Cursor 这类编码工具都会读取仓库里的同名文件作为上下文。OpenClaw 沿用了这个约定，agent 工作空间根目录下的 `AGENTS.md` 会在每轮会话开始时注入系统提示，属于常驻上下文里优先级最高的一份静态文件。它和 `SOUL.md`（人格）、`MEMORY.md`（动态记忆）分工明确——AGENTS.md 管的是“在这个工作空间里怎么干活”。

## 问题

没有这份文件、或者写得随意时，常见三类毛病：

1. **行为漂移**：同样的任务两次执行方式不一样，这次顺手 `git commit`，下次只吐 diff 等确认；
2. **权限感混乱**：分不清哪些事可以直接做（读文件、跑本地脚本），哪些必须先问（发消息、删数据），表现要么越权要么过度胆小；
3. **重复踩坑**：出错后对话里口头纠正了，下次新会话照犯——因为没有沉淀成规则。

## 做法

从最小版本开始，骨架大致这样：

```markdown
# 工作空间说明
## 环境与路径（关键目录、常用脚本入口）
## 工具使用规则（哪些直接用，哪些先确认）
## 安全红线（明确禁止的操作）
## 输出与沟通规范（格式、语言、汇报粒度）
## 记忆维护（何时更新 MEMORY.md）
```

执行顺序建议：

1. 只写你已经在对话里**口头纠正过两次以上**的事，其余先不写；
2. 每条规则写成“条件 + 动作”，例如“commit 前必须先把 diff 贴给我确认”；
3. 新开会话（或 `/reset`）验证规则是否真的生效；
4. 把 workspace 纳入 git，规则变更可回溯；
5. 定期裁剪，删掉不再触发的条目。

## 踩坑点

- **写太长**。我第一版写了四百行，token 占用高不说，关键规则被稀释，agent 开始“选择性失忆”。压到百行以内后稳定性明显改善。
- **规则冲突**。`SOUL.md` 里写“主动汇报”，AGENTS.md 里写“别打扰我”，行为就变成抛硬币。同一件事只在一处定义。
- **写愿望不写规则**。“保持专业、认真负责”没有任何约束力，等于没写；可执行的条件句才有。
- **把敏感信息写进去**。AGENTS.md 是明文，且会完整发给模型。密钥、内网地址一律走环境变量，文件里只留占位说明。
- **改完不重启**。旧会话里的系统提示还是上一版，误以为规则没生效，白调半天。

## 可复用建议

- **增量维护**：agent 做错 → 口头纠正 → 确认改对 → 立刻沉淀为一条规则。这个循环跑顺了，文件会自己长成你们团队的真实规范。
- **三档权限清单**：“可直接做 / 需先确认 / 禁止”明确列出，比散落的句子可靠得多。
- **和 TOOLS.md 分工**：AGENTS.md 管行为，TOOLS.md 管能力说明，别在 AGENTS.md 里重复解释工具参数。
- **分层放置**：工作空间级的管通用习惯，具体项目仓库里再放一份项目级 AGENTS.md（编码类子 agent 会读），避免一份文件越写越臃肿。

## 总结

AGENTS.md 的价值在于把调试 agent 的过程从“对话内修补”变成“配置内沉淀”。它写得越像操作规程、越不像作文，agent 的表现就越稳定。如果你现在还在靠反复口头纠正过日子，先花半小时把最近一周纠正过的事情列成十条规则，收益立竿见影。
