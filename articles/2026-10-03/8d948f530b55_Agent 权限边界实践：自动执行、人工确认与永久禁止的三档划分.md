## 背景

Agent 接上 MCP 和插件之后，核心问题就从"能不能做到"变成了"该不该自己做"。我们在内部自动化里见过两种极端：一种是什么都问，用户每五分钟点一次确认，很快变成无脑点"确定"；另一种是什么都自己干，直到某天 Agent 替人给外部客户发了一封措辞不对的邮件。权限边界不是安全口号，而是决定 Agent 能否长期用下去的产品设计。

## 问题

多数团队配权限是拍脑袋的：按工具名放行或拦截。但同一个工具，参数不同风险天差地别——读文件没问题，删除操作的路径不同后果完全两样。缺一套按"动作 + 参数 + 上下文"分级的方法，结果要么问太多，要么问太少。

## 做法：三档划分

先按四个维度给每次工具调用打标：

- **可逆性**：能否撤销（git revert 可以，发出去的邮件不行）
- **影响范围**：本地沙箱、个人工作区、还是共享/生产环境
- **资金与外部**：是否花钱、是否触达外部的人
- **批量性**：一次一条，还是一次几百条

再映射到三档：

1. **自动执行**：只读操作、沙箱内写入、完全可逆的变更。直接干，事后留日志。
2. **人工确认**：写共享资源、对外通信、产生花销、不可逆删除。Agent 必须先给出具体计划——改哪些文件、diff、发给谁、花多少钱——人确认后才执行。
3. **永久禁止**：除非改配置文件，任何 prompt 都不能解锁，比如直连生产库的写接口。

关键实现点：权限判断放在工具层（MCP server / 插件网关），**不要写进系统提示词**。提示词能被注入绕过，工具层白名单不能。写操作先 dry-run 生成摘要，确认时人看到的是 diff，而不是一句"确认执行吗"。批量操作设硬上限，超限自动升级为逐条确认。

## 踩坑点

- **问太多等于没有门槛。** 审批疲劳后人会机械点确认，高危动作混在低危里被顺手放行。宁可让低风险操作默认自动跑，把确认额度留给真正危险的。
- **确认信息太笼统。** "我准备执行删除操作"没法判断；"将删除 ~/projects/foo 下 37 个未跟踪文件"才有人类判断的价值。
- **权限写在提示词里。** 改一句话模型就"想通了"，注入攻击也能改。
- **只按工具分级，不按参数分级。** 同一个 shell 工具，`ls` 和 `chmod -R` 应该走不同通道。
- **没有审计日志。** 出了事连"它当时有什么权限、谁点的确认"都查不出来。

## 可复用建议

- 默认拒绝、白名单放行，而不是反过来。
- 资金、对外通信、不可逆删除，这三类永远人工，别图省事。
- 权限矩阵做成版本化配置，和代码一起 review。
- 每周扫一次执行日志，统计确认被拒绝的比例——拒绝率异常说明分级错了，不是太松就是太紧。

## 总结

权限边界本质是产品决策：你希望用户信任 Agent 到什么程度，用什么换效率。三档划分 + 工具层强制 + 全程可审计，是我们验证过成本最低的组合。原则一句话：可逆的自己干，不可逆的问人，碰钱的永远别自作主张。
