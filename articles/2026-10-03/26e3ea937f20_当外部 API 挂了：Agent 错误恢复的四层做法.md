## 背景

Agent 系统本质上是一条长调用链：LLM 推理 → 工具调用 → 外部 API → 结果回灌 → 继续推理。链路上任何一个外部依赖（LLM 供应商、搜索接口、数据库、第三方 SaaS、MCP 服务）都可能超时、限流或直接 5xx。传统后端挂了会报错、告警、回滚；但 Agent 挂了的表现往往更隐蔽——它可能"以为"自己成功了。

## 问题：Agent 的失败方式和普通程序不一样

三个典型场景：

1. **工具调用失败后，模型开始编。** MCP 工具返回超时，Agent 没拿到结构化错误，下一轮推理直接"脑补"一个结果继续往下走，最终产物看起来完整，数据是错的。
2. **无脑重试放大故障。** 上游 429 限流时，Agent 循环每次失败立即重试，把限流窗口彻底打满，还顺带烧掉 token 预算。
3. **长任务没有断点。** 一个 20 步的自动化流程跑到第 18 步 API 挂了，从头重跑意味着前面 17 步的副作用全部重复执行。

## 做法：把错误处理做成四层

**第一层：错误分类。** 在工具封装层（插件层或 MCP wrapper）把错误分成三类：可重试（429/5xx/超时）、不可重试（401/400/404）、未知。分类结果决定后续所有行为，不要把原始异常直接抛给模型。

**第二层：受限重试。** 指数退避 + 抖动，上限明确：最多 3 次、总耗时不超过 30 秒这类硬预算。写操作必须带幂等键，重试才安全。

**第三层：熔断与降级。** 连续 N 次失败后熔断，直接走降级路径：备用供应商、缓存数据、或明确返回"该能力暂不可用"。降级不是失败，是设计出来的一部分。

**第四层：结构化错误上抛。** 重试和降级都失败后，把错误以结构化形式返回给模型：

```json
{
  "status": "failed",
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": false,
  "hint": "可用缓存数据继续，或询问用户"
}
```

模型拿到 `retryable: false` 和 `hint` 才能做出合理决策：换路径、跳过、或停下来问人。关键是错误状态必须显式进入上下文，不能被吞掉。

对于长任务，在每个有副作用的步骤后落一次检查点（状态写文件或数据库），恢复时从断点继续，而不是整个重跑。

## 踩坑点

- **把错误吞掉只打日志。** 模型看不到失败，就会幻觉出成功，这是 Agent 数据造假的头号来源。
- **重试没有上限。** 没有次数和总时长预算的重试，在连环故障时会变成成本事故。
- **对非幂等操作重试。** 发消息、下单类接口不带幂等键就重试，会出现重复副作用，比失败更难收拾。
- **单次调用超时设太长。** 外部 API 挂死时，一个 120 秒的超时能卡住整个 Agent 循环，后续所有步骤全部排队等待。

## 可复用建议

1. 所有工具调用走统一封装层，错误分类、重试、熔断、日志集中在这一层做，Agent 本体不感知细节。
2. 给每次 Agent 运行定义"错误预算"：重试次数、总耗时、token 上限，超了就升级为人工介入。
3. 关键写操作前先问自己：这一步重跑会怎样？答不上来就先补幂等设计。
4. 定期做故障演练：手动把某个 MCP 工具指向一个必超时的地址，观察 Agent 行为是否符合预期。演练过的降级路径才是真的降级路径。

## 总结

外部 API 挂掉不是异常路径，而是 Agent 生产环境的日常。核心思路三句话：错误要分类，重试要克制，失败要显式。让模型在信息充分的情况下决策，让系统在有断点的情况下恢复，剩下的交给告警和人。
