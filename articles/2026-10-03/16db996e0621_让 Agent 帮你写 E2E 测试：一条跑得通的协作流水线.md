## 背景

E2E 测试是最难坚持自动化的那一层：写起来慢、选择器脆、页面一改就得跟着修。很多团队的现状是"有框架、没用例"。另一边，MCP 已经把浏览器操作标准化了（比如 Playwright MCP），Agent 可以真的打开页面、点按钮、读 DOM，而不是靠想象写代码。这两件事凑到一起，值得认真试一次：让 Agent 参与写 E2E。

## 问题

直接丢一句"给这个系统写 E2E 测试"，效果通常很差：

- Agent 没见过真实页面，选择器全靠猜，十有八九是幻觉；
- 一次生成十几个用例，跑挂之后日志塞满上下文，越修越乱；
- 生成的代码看着像测试，断言是空的或恒真的，跑绿了也没意义。

本质是把"探索页面"和"写测试"两个动作压成了一次生成。要拆开做。

## 做法

以 OpenClaw 接入 Playwright MCP 为例，我们的流程分四步：

1. **先探路，再写码。** 让 Agent 通过 MCP 打开本地被测环境，走一遍核心路径（登录 → 创建订单 → 取消），要求每一步记录实际选择器和页面状态，输出操作轨迹。这一步不产出测试代码。
2. **基于轨迹生成骨架。** 把轨迹喂回去，并限定规则：只用 `data-testid` 定位、断言必须验证业务结果、禁止 sleep、依赖 Playwright 的 auto-wait。一次只生成一条路径的用例。
3. **失败回喂，单点修复。** 跑一次，把失败的 trace、截图、报错单独贴给 Agent，只修这一个失败，修完立刻重跑。以退出码为准——Agent 自己说"应该可以了"不算数。
4. **沉淀成 skill。** 把第 2 步的规则和第 3 步积累的报错修法，写成 OpenClaw 的项目级提示词/插件配置提交进仓库，团队复用同一套约束。

## 踩坑点

- **没有 data-testid 就先补规范。** 我们让 Agent 按 `page-section-element` 格式先给关键组件补属性，再写测试。靠文本定位，改文案那天必挂。
- **上下文爆炸。** 一次贴超过三个失败用例的日志，Agent 会开始张冠李戴。坚持一轮只处理一个失败。
- **假数据过不了后端校验。** 提前准备测试账号和固定测试数据清单，写进 Agent 的项目上下文，比让它现场编手机号靠谱得多。
- **本地绿、CI 红。** headless 下的视口、字体、动画时序都有差异。第一条用例跑通后立刻去 CI 验证，别攒一批再验。

## 可复用建议

- 给仓库加一份《Agent 写测试约定》：定位策略、断言要求、禁止事项。这份文档同时也是给人看的 review 标准。
- 人工只 review 断言，不逐行看实现。断言错了测试就是自欺欺人，实现风格可以放开让 Agent 写。
- 把"报错 → 修法"的对应关系持续追加进 skill，一个月后 Agent 的首次通过率会明显上升。

## 总结

Agent 写 E2E 的真实价值不是"全自动生成测试"，而是两件事：把第一版用例的成本从一天压到半小时；把修失败用例从"没人想干"变成"随手让 Agent 跑一轮"。稳定性仍然来自工程约束——选择器规范、断言审查、单点迭代。约束写清楚，Agent 是合格的测试搭档；写不清楚，它就是一台会跑绿的幻觉制造机。
