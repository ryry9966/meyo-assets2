最近，Andrej Karpathy 提出一个有意思的判断：AI 时代写软件的瓶颈，正在从“写代码”转向“写规格”（spec）。他给那些爱说废话、爱自由发挥的 LLM 开出的药方，居然是 40 年前航空业的一套老规矩——1985 年发布的机载软件规范 DO-178 及其衍生的适航体系。一套管飞机软件的老标准，凭什么能治大模型的“话痨病”？这篇把来龙去脉和可上手的做法拆开讲清楚。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-03/3d0e01a09731be3e.png)

## 一、先对症状：AI 的“废话病”长什么样

- **复读机式开场**：“这是一个很好的问题”——先把你的问题复述一遍，再慢悠悠展开；
- **万金油答案**：什么都沾一点，什么都不落地，全是“正确的废话”；
- **边界装死**：让它输出 100 字，它写 300 字；让它只改一个函数，它顺手“优化”了半个仓库；
- **写代码时更致命**：没说清输入输出，它就自作主张编造 API、引入多余依赖、跳过错误处理。

先说结论：这不是模型“态度不好”，而是概率模型的天然行为。怎么治，往下看机制。

## 二、40 年前的老方子：航空业怎么跟“不靠谱的代码”打交道

上世纪 80 年代，电传操纵（fly-by-wire）让软件直接接管飞控，代码出 bug 就可能摔飞机。于是 1985 年 RTCA 发布 DO-178《机载软件注意事项》，后来演进为 DO-178B/C。它的核心理念放到今天依然锋利：

1. **代码本身不可信，可信的是“可验证的需求”**；
2. **可追溯性（traceability）**：每一行代码都要能追溯到某条需求；
3. **基于需求的测试**：每条需求都要有对应的测试用例；
4. **验证独立性**：验证者与开发者分离，防止“自己验自己”；
5. **按失效后果分级（A~E 级）**：后果越严重验证越狠，最高级别要求 MC/DC 覆盖率。

反面教材也足够经典：Therac-25 放疗机因软件缺陷造成多名患者受到过量辐射伤害；1996 年 Ariane 5 首飞，复用了 Ariane 4 的惯性导航代码，但新火箭的飞行包线超出了老代码的规格范围，浮点转整数溢出，升空 37 秒后自毁。两次事故的共同教训：**不是代码写得糙，而是规格边界没人管**。

## 三、机制拆解：为什么“规格”能压住概率模型的废话

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-03/3bad4748e3475252.png)

- **LLM 本质是条件概率机器**：给定前文，预测下一个 token。你给的约束越模糊，输出就越向“互联网平均语感”回归——而互联网的平均语感，恰恰就是客套、对冲、面面俱到的废话。
- **Spec 的作用是收窄输出分布**：目标、输入输出、边界条件、禁止行为，每一条都是在给概率云画边界，把“可能的回答”压到“你想要的回答”附近。
- **更关键的是可判定性**。航空规范的精髓是“每条需求必须可验证”。放到 LLM 上，就是把“帮我写好一点”这种主观题，改写成“测试跑不过即失败”的判断题。验收标准从形容词变成布尔值：模型说一百句漂亮话，测试不通过就是 0 分——废话没有生存空间。
- **于是形成自动化闭环**：规格 → 生成 → 验证 → 修复。Karpathy 的洞察正在于此：当生成足够便宜，稀缺的就不再是产出，而是清晰的规格与严格的验收。

## 四、上手示范：把一句话需求改写成“航空式规格”

Before：**“帮我写个 Python 脚本清理服务器日志。”**

模型只能猜：清哪些？留几天？删错了怎么办？于是输出里一半是猜测，一半是免责声明。

After，规格化改写：

- **目标**：清理 `/var/log/app` 下修改时间超过 N 天的 `*.log` 文件
- **参数**：目录路径、保留天数 N（默认 30）
- **边界条件**：目录不存在 → 退出码 1 并打印错误；文件被占用 → 跳过并记录；空目录 → 正常退出
- **必须提供**：`--dry-run` 只打印待删除清单不执行；结束时输出删除统计
- **禁止行为**：不得递归处理子目录；不得删除任何非 `.log` 文件
- **验收标准**：先在 3 组构造好的测试目录跑通，再上生产

写完这份 spec，模型基本没有发挥空间——“自由发挥”的空隙被你用规则提前填满了。而且这份 spec 可以进 Git、可以 review、可以复用，它本身就是资产。

## 五、冷思考：规格不是银弹

1. **spec 自己也会有 bug**。需求错误比代码错误更贵——Ariane 5 摔的其实是“复用超出规格范围”这笔账。spec 同样需要 review 和版本管理。
2. **发散型任务别硬套**。头脑风暴、创意探索阶段，过早收敛成硬规格会扼杀惊喜；规格适合目标明确、重复执行、出错代价高的场景。
3. **有前期成本**。给一个只跑一次的脚本写完整规格不划算；但任务要重复执行十次以上，或者要交给 agent 自主运行，spec 的回报率就极高了。

## 六、写在最后：三条可直接抄走的建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-03/177f065f4d42f25c.png)

1. **先测后码**：让模型根据你的需求先写验收测试，再生成实现，跑不过就修——用布尔值逼走形容词。
2. **需求三件套**：边界条件 + 禁止行为 + 输出格式。经验上，“禁止项”比“要求项”更压废话。
3. **把 spec 当源代码养**：写进仓库、走 review、打版本号。AI 时代，“写清楚”正在成为比“写出来”更稀缺的工程能力。

飞机上装不下废话，你的上下文窗口也一样。
