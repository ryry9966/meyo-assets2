## 背景

我们手上几个服务跑在自建机器上，日志散落在 journald、应用目录和 git 提交里。每天早上的日报，本质是重复劳动：翻日志、数错误、摘重点、套模板。这套动作没有判断难度，只有重复成本——正好是 cron + Agent 该干的活。但在把整条链路交给 OpenClaw 之前，我先走了两个月弯路。

## 问题

最初的偷懒做法是定时让 Agent 直接读原始日志"总结一下"，踩了三个坑：

1. 原始日志一天几十 MB，token 爆炸，还经常被截断，总结基于半份数据；
2. 数字不可靠，模型会"估"错误次数，和实际 grep 结果对不上；
3. 输出格式每天不一样，没法归档、没法横向对比。

结论很明确：**不能让 Agent 直接面对原始日志**。

## 做法

现在这条流水线分四步，核心原则是"脚本做聚合，Agent 做叙事"：

**1. 采集**。纯 shell 脚本拉数据：`journalctl` 导出昨日错误日志、nginx access log 统计、git log 汇总，落到固定目录 `workspace/daily/YYYY-MM-DD/`。Agent 完全不参与采集。

**2. 预结构化**。用 jq / grep / awk 把每类日志压成统一 schema 的 JSON，例如 `{"source":"nginx","5xx":12,"top_paths":[...],"sample_errors":[...]}`。单文件控制在几百行内，错误只留计数 + 少量样本。

**3. Agent 撰写**。定时任务触发一个 skill，prompt 里只有两条硬规则：只读当天的 JSON；报告中的任何数字必须能在 JSON 里找到，找不到就写"数据缺失"。输出走固定 Markdown 模板：概览 / 异常 / 变更 / 待办。

**4. 校验投递**。一个校验脚本从报告中正则抽出所有数字，回查 JSON，不一致就拒绝发送并告警。通过后推送到群频道，同时归档。

## 踩坑点

- **时区**：cron 跑在 UTC，日志却是本地时间，曾连续几天统计错日期。现在脚本统一显式指定 TZ，日期参数由脚本算好传入。
- **空数据日**：某天日志没滚动，流水线不应报错中断。转换脚本要能产出空 schema 的 JSON，Agent 按模板写"今日无数据"即可。
- **格式漂移**：模型偶尔自作主张加小标题、加感叹。模板约束 + 校验脚本兜底之后基本稳定。
- **别把采集塞给 Agent**：试过让 Agent 自己跑命令采集，一次 shell 报错整条链就卡住。采集必须是确定性脚本，失败要有明确退出码。

## 可复用建议

- **Schema 先行**：先定中间 JSON schema，再接数据源。之后每接入一个新日志源，只需写一个转换脚本，撰写和投递环节完全不动。
- **留 dry-run**：校验脚本支持 `--dry-run --date`，方便补报和回溯历史日期，调试时也不用真的推送。
- **日报即记忆**：归档的 Markdown 放在 workspace 里，周五让 Agent 检索本周日报生成周报，一条流水线复用两次。

## 总结

这条流水线的价值不在于"让 AI 写日报"，而在于职责切分：确定性的事交给脚本，归纳表达交给 Agent，幻觉风险交给校验兜底。三段各司其职后，日报已经连续稳定跑了一个多月，维护成本接近零。日志源和模板大家按需替换即可，骨架是通用的。
