## 背景

E2E 测试的问题从来不是“不会写”，而是“没人愿意维护”。一个中型前端项目，核心链路十来条，每条用例平均 60~100 行，UI 一改，断言全崩。多数团队的现状是发布前手工点一遍了事。

现在 Agent + MCP 工具链够用了：让 Agent 起草用例、人来审、CI 来验，是当前性价比最高的分工方式。下面是我们实际跑通的一套流程。

## 直接丢一句“帮我写个 E2E”会发生什么

实测下来，单轮 prompt 生成的用例有四类典型问题：

1. **选择器脆**：大量 `nth-child` 和动态 class，页面一改就红；
2. **断言水**：只断言“页面跳转成功”，对数据、状态、边界只字不提；
3. **环境错配**：不知道你们的 fixture、登录态、测试账号约定；
4. **偶尔“作弊”**：为了让测试通过，顺手改产品代码或放宽断言。

这决定了不能一句话交给模型，得做流程。

## 做法：四步闭环

**1. 把规范固化成 Agent 可读的上下文。** 在仓库里维护一份测试约定：统一用 `data-testid`、禁止基于样式类断言、每条用例必须写清前置条件。通过 MCP resource 暴露（或直接进系统提示），保证 Agent 每次生成前都能读到。

**2. 配最小工具集，权限切干净。** 两个 MCP server 基本够：一个封装 Playwright 的执行能力，一个只读访问仓库（读 PR diff、现有 spec）。关键约束：测试 Agent 对 `src/` 只读，对 `tests/` 可写。

**3. 分阶段生成。** 先让 Planner 角色读 PR diff 和需求描述，输出测试大纲——覆盖哪些路径、每条断言什么；大纲确认后再由 Writer 生成 spec 代码。**一次只生成一个文件**，不要一口气全量生成。

**4. Runner 自动闭环。** 生成后立刻跑单条 spec，失败日志裁剪后回喂 Agent，最多迭代 3 次；3 次不过就标记“需人工”，不硬磕。CI 里对 Agent 产出的用例连跑 3 次统计稳定性，失败率超阈值直接打 flaky 标签。

## 踩坑点

- **别给测试 Agent 产品代码写权限。** 它“顺手帮你修”的冲动比你想的强。
- **日志必须裁剪。** Playwright 一次失败能输出几千行，全量回喂会挤爆上下文，只传 error 摘要加定位行。
- **flaky 是重灾区。** Agent 会把“重跑过了”当成功，必须看多次运行的失败率，不是单次结果。
- **并发写冲突。** 多个 Agent 任务按文件粒度分片，别让两个任务碰同一个 spec。

## 可复用建议

- **断言清单模板**：生成前先让 Agent 列出“这条用例断言什么、不断言什么”，人工 30 秒扫完，能拦掉大半“断言水”问题。
- **度量两个数**：Agent 用例的一次通过率、三个月后的维护 diff 量。前者决定流程能不能留，后者决定它是不是真省事。
- **保持 diff review**：Agent 生成的 spec 和人写的一样走 PR，不要 auto-merge。

## 总结

Agent 写 E2E 的价值不在替代人，而在把启动成本压到接近零——以前是“这条链路太麻烦，先不测”，现在是“PR 一合并，草稿已经在那儿了”。把约定工具化、权限切干净、验证交给 CI，这套协作就能长期跑下去。
