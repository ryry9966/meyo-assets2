## 背景

用 OpenClaw 做日常自动化一段时间后，最明显的瓶颈不是模型能力，而是串行执行。比如"调研三个候选方案并各自产出对比摘要"这类任务，主 Agent 一个个做，单轮耗时轻松超过十分钟，期间主会话完全阻塞。后来我把这类任务改成 subagent 并行编排，整体耗时降到原来的三分之一左右。这篇记录一下做法和踩过的坑。

## 问题

- 主循环串行：子任务之间明明没有依赖，却在排队。
- 上下文污染：所有中间过程堆在主会话里，几轮之后主 Agent 开始"忘事"。
- 单点失败：中间某一步卡住，后面的全部跟着等。

## 做法

我的编排流程分四步：

**1. 任务切分。** 先让主 Agent 输出一份子任务清单，明确每个子任务的输入、边界和产出物。切分原则只有一条：读操作可以并行，写操作必须串行。

**2. 定义子任务契约。** 每个 subagent 的 prompt 固定三段：只做哪件事、允许用哪些工具或只能读哪些路径、返回什么格式。我强制要求返回结构化摘要（结论 + 关键文件路径），原始过程写到独立文件里，不回传主会话。

**3. 并行派发。** 并发上限压在 2–3 个。超过 3 个后，收益会被工具限流和调度开销吃掉，出问题也更难排查。派发时给每个子任务设超时（我用 5 分钟），超时记为失败，不自动重试。

**4. 主 Agent 聚合。** 收齐结果后统一对比，合并成最终产出。某个子任务失败时降级处理：在最终报告里标注缺口，而不是整体重来。

## 踩坑点

- **写冲突**：两个 subagent 同时改同一个文件，后写的覆盖先写的。现在写操作全部由主 Agent 串行收口，subagent 只产出各自的草稿文件。
- **范围漂移**：子任务 prompt 写得含糊，subagent 会"热心"地把别的子任务也做了，token 直接翻倍。契约里要写明"只做这一件，发现其他问题返回 TODO"。
- **隐性依赖**：以为是三个独立调研，其实第二个要用第一个的结论。切分完后先人工过一遍依赖关系，别全信模型的判断。
- **限流**：并行打同一个 MCP 工具，429 接连出现。要么给不同 subagent 错开工具，要么降并发。
- **结果太长**：subagent 回传两千字总结，主会话瞬间被撑爆。返回格式必须卡死在一百字以内，细节一律进文件。

## 可复用建议

1. 只读任务放心并行，写任务一律串行收口到主 Agent。
2. 子任务契约模板固定下来：范围、工具白名单、返回格式、超时，四项缺一不可。
3. 并发从 2 开始，跑稳了再往上加。
4. 每个 subagent 的 token 消耗单独记，成本异常时能立刻定位到是哪个子任务。
5. 失败降级比整体重试划算，报告里留缺口比卡死强。

## 总结

subagent 编排的核心不是"开得越多越快"，而是把并行用在真正独立的部分，用契约把每个子任务的边界和产出钉死，主 Agent 只做切分和聚合。我的经验是：切分清晰加上契约严格，比任何高级调度方案都管用。建议先拿一个纯调研类任务试跑，验证稳定后再扩展到更复杂的自动化场景。
