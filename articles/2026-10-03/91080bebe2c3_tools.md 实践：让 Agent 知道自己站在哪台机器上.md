# 背景

跑 OpenClaw 的机器往往不止一台：一台开发本、一台家里的小主机、一台 VPS。技能文件、提示词这些"软"的部分可以随 git 走，但环境是硬的——ffmpeg 装没装、Python 在哪个 venv、要不要走代理、服务是 systemd 还是 compose，每台都不一样。模型对"一台标准 Linux"的想象，和你的真实机器之间总有差距。

tools.md 就是补这个差距的：一份放在 workspace 里、随会话注入给 Agent 的本地事实清单。它不是配置文件，也不是文档，而是 Agent 眼里"这台机器长什么样"的唯一事实来源。

# 问题

不写 tools.md 时，环境差异的坑都变成对话里的现场返工：

- Agent 调了不存在的命令，或用了错误的绝对路径；
- 同一个 skill 在 A 机正常，在 B 机因缺依赖直接失败；
- 每次都要口头纠正"这台机器要用 xxx"，纠正本身花 token，下个会话可能还忘；
- 机器上已有的东西（自建脚本、别名、内网服务）Agent 完全不知道，绕远路重造轮子。

# 做法

我的流程分五步：

1. **盘点**。跑一个采集脚本（uname、发行版、`which` 常用 CLI、版本号、代理变量、服务运行方式），生成原始清单。
2. **裁剪成 tools.md**。按"机器概况 / CLI 与路径 / 网络与代理 / 服务管理 / 禁忌区"分节，控制在几十行。每条只写事实和调用方式。
3. **验证注入**。直接问 Agent："根据 tools.md，这台机器的 python 指向哪里？"答不上来说明没加载，先修加载链路再谈内容。
4. **建立回写习惯**。Agent 每踩一次环境坑，就补一条进 tools.md。这份文件是长出来的，不是一次写完的。
5. **多机各一份**。每台机器的 tools.md 只描述自己，不共享。公共部分放进技能或全局指令，机器差异只留在本地这份里。

# 踩坑点

- **写成 README**。塞满历史和解释，关键事实被稀释。tools.md 只放 Agent 当前需要知道的事实。
- **记录会漂移的值**。IP、动态路径写死在里面，两周后全是错的。改写成"查询方法"：写"用 `docker ps` 确认服务名"，不写容器名快照。
- **把规则混进来**。"回复要简洁"这类偏好属于 AGENTS.md；tools.md 只描述环境。职责混了以后两边都难维护。
- **敏感信息入文件**。key、密码写进去，等于让 Agent 读、进日志、可能随备份外流。只写"去哪取"（哪个文件、哪个变量名），不写值。
- **改了不生效**。部分运行方式会缓存 workspace 内容，改完要确认新会话真的读到了新版本。

# 可复用建议

- 每条记录统一格式：`工具 | 用途 | 怎么调 | 限制`，可 grep、可 diff。
- 心法一句话：**写事实不写值，写查询方法不写快照**。
- tools.md 是给 Agent 的索引，不是配置源；真正的配置仍归 dotfiles / compose 管，它只负责"告诉 Agent 去哪看"。
- 每月把采集脚本重跑一遍，diff 清掉过期条目。

# 总结

环境差异不会消失，只能被显式管理。tools.md 的价值不在文件本身，而在于把"机器之间不一样"从一个反复踩的坑，变成一份持续维护、随上下文生效的事实清单。先从最常报错的那台机器写起，二十行就够。
