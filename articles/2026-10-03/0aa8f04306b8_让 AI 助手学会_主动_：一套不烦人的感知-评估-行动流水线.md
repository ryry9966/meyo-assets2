## 背景

我们接好了 MCP 工具、接好了消息渠道，但 agent 大多数时候还是"你问它答"。真正的 proactive 能力是：agent 自己感知信号、判断要不要开口、再决定做什么。我给自己跑了一套流水线，两个多月下来有些经验值得记下来。

## 问题

朴素的 proactive 只有两种结局：

1. **哑火**：定时任务跑了，agent 每次都说"没什么值得报告"，等于没做；
2. **骚扰**：每条 RSS、每封邮件都推给你，三天后你把通知全关了。

所以核心问题不是"让 agent 能主动做事"，而是"让它在 99% 的时间里保持安静"。

## 做法

三层结构：**感知层、评估层、行动层**。

1. **感知层（只读）**：cron 定时拉信号——日历、git 仓库动态、服务器指标、订阅源。全部走只读 MCP 工具，拉完丢进一个"信号池"。
2. **评估层（便宜）**：关键设计。评估 prompt 很短，只放信号 + 明确的判断标准 + 少量正反例，要求输出结构化 JSON：`{decision: "ignore" | "digest" | "act", reason, dedup_key}`。规则能挡的先规则挡（比如静默时段直接 ignore），剩下的用小模型跑。
3. **行动层（克制）**：decision 三档——`ignore` 只记日志；`digest` 追加进每日摘要；`act` 触发动作，但**默认只做可逆的事**：写草稿不发送、建文件不覆盖、生成建议等用户确认。

再加三个机制：静默时段、每日主动消息上限（我设 5 条）、`dedup_key` 去重（同一事件多源触发只处理一次）。

## 踩坑点

- **反馈循环**：agent 自己产生的 commit 触发了 git 信号，又被评估了一遍。给所有感知源加"排除 agent 自身产物"的过滤。
- **模型高估重要性**：前期 80% 的信号被评为 act。在评估 prompt 里放负面例子（"这条为什么只值 digest"），一两周校准一次标准。
- **dedup_key 设计不当**：换了措辞的同一事件被当成新事件。key 用内容哈希，别用标题。
- **时区 bug**：cron 按 UTC 跑，静默时段按本地算，结果半夜推消息。全链路统一时区。
- **成本失控**：评估层一开始用主模型，账单不难看。换成小模型 + 规则前置，成本降一个数量级。

## 可复用建议

- 先做**每日摘要**，跑顺了再放开实时打断和 act 档。
- 把"要不要开口"当成分类问题来运营：记录每次 decision + reason，每周复盘误报和漏报。
- 主动消息设预算，超了自动降级成 digest。
- MCP 工具分两级：只读观察工具随便给，行动工具走白名单；proactive 路径只允许可逆动作。
- 所有主动行为留痕，用户能问"你今天为什么推这条"并得到回答。

## 总结

Proactive 不是给 agent 加个定时器，而是一套"感知—判断—克制"的系统。判断标准、去重粒度、行动边界，都要当成工程参数持续调。最难的不是让 agent 做事，而是让它在该闭嘴的时候闭嘴——这恰恰是它值得被信任的前提。
