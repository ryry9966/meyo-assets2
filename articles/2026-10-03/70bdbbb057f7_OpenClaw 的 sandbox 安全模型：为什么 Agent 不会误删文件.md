## 背景

让 Agent 接上 shell 和文件工具之后，大家最担心的从来不是它“干不了活”，而是它“干错活”。一条拼错路径的 `rm -rf`、一次理解偏了的“清理一下目录”，损失都是不可逆的。OpenClaw 在这块的思路很明确：sandbox 不是可选插件，而是默认能力。核心原则一句话——**能力默认最小化，破坏性动作必须过闸**。

## 问题

要承认一个现实：LLM 的输出是概率性的。它会拼错路径，会把“清理临时文件”理解成删除整个构建产物目录，会在长对话里忘记你三小时前的叮嘱。所以只靠系统提示词里写“请小心操作文件”，等于把安全边界押在模型心情上。防线必须落在执行层，而不是提示词里。

## 做法

OpenClaw 的 sandbox 大致分五层，从外到内：

1. **工作区隔离**：Agent 默认跑在容器化的 workspace 里，宿主机路径根本不在它的视野内。它看不到的文件，它删不了。
2. **路径先解析再执行**：所有文件操作在落地前先做 canonicalize（realpath）。解析结果一旦跳出 workspace 边界——包括符号链接跳出去的情况——直接拒绝。这一步挡住了大部分“路径逃逸”。
3. **工具分级**：read-only 工具默认放开；write/delete 类工具需要配置里显式声明；exec 类走独立的执行策略。示意配置大致长这样：

```yaml
sandbox:
  workspace: /data/agent-ws
  tools:
    fs.read:   allow
    fs.write:  allow
    fs.delete: confirm
    exec:      deny   # 按需打开
```

4. **破坏性动作闸门**：命中删除/覆盖/批量写模式的调用不会直接执行，而是进入 confirm 队列，或者先跑 dry-run 输出受影响文件列表，人确认了再放行。
5. **快照兜底 + 审计日志**：每次会话开始前对 workspace 打快照，删除类操作可回滚；每次工具调用记录参数、解析后的真实路径、决策结果（allow / deny / confirm），事后能完整复盘。

## 踩坑点

- **图方便把宿主机 home 挂进 sandbox**。隔离形同虚设，一个 symlink 就跳出去了。要挂就挂子目录，只读优先。
- **拿提示词当唯一防线**。“不要删文件”这种约束在长上下文里会失效，注入也能绕过。提示词是软约束，执行层才是硬边界。
- **为了跑批效率关掉 confirm**。一次误删抵消所有效率收益。合理的做法是只对 read-only 操作免确认，删除类永远过闸。
- **glob 展开的时机没搞清楚**。`*.log` 这类通配符，策略匹配必须作用在展开后的真实路径上，否则规则看似配了、实际漏了。
- **快照从没测过恢复**。能回滚和回滚得动是两回事，恢复流程要演练。

## 可复用建议

- 把文件策略写成声明式规则（路径前缀 + 操作类型 + 动作），不要散落在系统提示词里。规则可版本化、可 review、可回滚。
- 删除类操作强制两步：先列受影响文件，再执行。多花几秒，省一晚上抢救。
- 定期做红队自测：直接丢给 Agent 一句“清理一下项目目录”，看它停在哪一层。停得越早，边界越稳。
- deny 次数接告警。突增说明要么策略配错了，要么模型行为漂移了，两者都值得看一眼。

## 总结

sandbox 的价值不是让模型变聪明，而是让错误的代价可控。提示词是第一道软约束，路径解析和工具分级构成硬边界，闸门与快照负责兜底。三层叠起来之后，“Agent 会不会误删文件”才从一个概率问题，变成一个可以被配置、被测试、被审计的工程问题。这也是我愿意让 OpenClaw 碰真实目录的前提。
