## 背景

多数 Agent 的工作模式是被动应答：用户发消息，模型处理，返回结果。但真正省时间的场景往往是反过来的，证书快过期了、PR 卡了三天没人 review、磁盘涨到临界值——这些事不需要你先开口。

OpenClaw 提供了两个原语：**heartbeat**（周期唤醒）和 **cron**（定时任务），配合 MCP 工具接入外部数据源，Agent 就具备了"无人在场时检查状态、自行决定是否行动"的能力。这就是 proactive 的最小实现面。

## 问题

把"主动"做对，比做出来难得多。我踩过三个典型失败模式：

1. **噪音**：心跳每 15 分钟跑一次，每次都汇报"一切正常"，三天后用户手动关掉了心跳。
2. **幻觉触发**：数据源超时或返回为空，模型脑补出一个"待处理事件"并郑重其事地通知你。
3. **环路**：Agent 主动发出的消息进入了会话历史，下一轮心跳把它当作"新事件"再次处理。

本质问题都一样：缺一个判断层——**什么信号才值得打扰用户**。

## 做法

我的方案是两段式：detect（便宜）+ decide（贵）。

1. **触发标准写进 HEARTBEAT.md**：只报告同时满足"可操作、有时限、有证据"的事件，缺一即静默。给出反例帮模型校准——"磁盘 75%"不算事件，"磁盘 92% 且持续增长"才算。
2. **数据源走 MCP 工具**：证书到期、issue 超时、监控指标、日历，各自返回结构化结果。心跳 prompt 只塞摘要，不塞原始数据。
3. **心跳 prompt 极简化**：一段 checklist + 最近状态文件，不带全量对话历史。能用规则挡的先规则挡（阈值判断放进脚本），过线的才交给模型。
4. **输出分级**：紧急事件走直达消息；非紧急的攒进每日 digest，由 cron 在固定时间汇总一次。
5. **留反馈回路**：每条主动消息带编号并落日志，每周统计"被回复 / 被忽略"的比例，据此调阈值。

## 踩坑点

- **心跳带全量上下文**：第一版 token 消耗一晚翻了数倍，改成最小 prompt 后降了一个量级。
- **重复通知**：cron 和 heartbeat 各配了一份证书检查，同一事件推了两次。原则：一个信号只能有一个 owner。
- **时区与免打扰**：heartbeat 按 UTC 算时间，凌晨三点推消息。免打扰判断要在脚本和 prompt 两层都做，不能只靠模型自觉。
- **自触环路**：主动消息被下一轮心跳当作新输入。给主动消息打标记，心跳检索时过滤掉。
- **权限过大**：定时运行的 Agent 拿着全量工具权限，等于无人值守的高危操作。给 proactive 路径单独配最小工具集，并设 kill switch——一个状态文件，存在即全局静默。

## 可复用建议

- 两段式结构可迁移到任何自动化 Agent：**便宜的规则层 + 贵的模型层**，规则层过滤掉 90% 的噪音。
- "可操作、有时限、有证据"三条件写成模板，让每个用户按自己的场景填空。
- digest 模式是降低打扰感性价比最高的手段，先做 digest，再做实时推送。
- 一切主动行为必须落日志。没有日志，阈值调整就是玄学。

## 总结

Proactive 不是让 Agent 多说话，而是让它在**该说话的时候**说话。OpenClaw 的 heartbeat/cron 加 MCP 已经给了足够的地基，剩下的都是工程问题：怎么省钱、怎么防误报、怎么不被自己烦死。建议从"每日 digest + 三条件触发"起步，跑两周拿到忽略率数据后，再考虑实时推送——这是我能验证过的最稳路径。
