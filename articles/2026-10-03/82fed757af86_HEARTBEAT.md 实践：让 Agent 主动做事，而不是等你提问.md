## 背景

用 Agent 久了会发现一个模式问题：绝大多数交互都是被动的——你问，它答。但很多事恰恰是「没人问也要有人管」的：日报、邮箱巡检、磁盘告警、订阅摘要。OpenClaw 里有个容易被低估的机制专门干这个：工作区根目录的 `HEARTBEAT.md`。

它的原理很朴素：Gateway 按固定间隔（默认 30 分钟）唤醒一次 agent，注入一条固定提示，大意是「读一下你的 HEARTBEAT.md，处理到期的任务；没事就回 HEARTBEAT_OK」。这个文件就是 agent 的值班表。

## 问题

纯被动 agent 有三个典型痛点：

1. **周期性事务没人接**：每次都得人来提问，等于自己当了人肉 cron。
2. **cron + 脚本能解决一半**：「要不要报警、怎么汇总」这类模糊判断写脚本很啰嗦，而这正是模型擅长的部分。
3. **任务散落在聊天记录里**：agent 下次会话并不记得你上周让它「每天看一眼 CI」。

## 做法

**第一步：写文件。** 在 workspace 根目录建 `HEARTBEAT.md`，一行一个任务，务必带触发条件和动作：

```markdown
- 每天上午汇总 GitHub notifications，仅当有 @我 或分配给我的条目才播报
- 每 6 小时运行 df -h，磁盘使用率超过 85% 才提醒，否则静默
- 无事可做时回复 HEARTBEAT_OK，不要汇报"一切正常"
```

**第二步：调间隔与投递。** 在 `openclaw.json` 的 `agents.defaults.heartbeat` 下改间隔（字段名随版本略有差异，以文档为准），建议把心跳输出定向到一个专门的低噪音频道，别混进主会话。

**第三步：降本。** 心跳用小模型跑足够了，判断型任务它完全够用；主对话保留强模型。

## 踩坑点

- **任务写太虚**。「帮我盯着服务器」每半小时都能解读出不同动作，要么空转要么过度反应。条件、动作、静默规则三样缺一不可。
- **心跳不是精确调度器**。它只是「每隔 N 分钟想起来看一眼清单」，别指望 9:00 整点发日报。要精确定时用系统 cron 调 agent，两者分工：cron 管时刻，心跳管巡检。
- **文件会腐烂**。任务做完不删，agent 每次心跳都白读一遍，甚至重复执行。做完就删，或把状态落盘让它自己判断「已做过」。
- **Token 成本**。间隔越短烧得越多，30 分钟起步，观察一两周再调。
- **多 agent 场景**。每个 agent 有自己的心跳文件，同一个任务别写两份，否则一个告警收到两遍。

## 可复用建议

- 任务分三类最稳：**摘要类**（日报、周报）、**阈值类**（跑脚本、超阈值才说话）、**收件箱类**（notifications、邮件分诊）。
- 阈值类让模型只做「解读」，执行交给确定性脚本或 MCP 工具，别让它每次现场想命令。
- 把 `HEARTBEAT.md` 纳入 git，像配置一样 review，改任务走 PR。
- 输出克制：默认静默，有事才说。一个安静的心跳才是健康的心跳。

## 总结

`HEARTBEAT.md` 不是调度器，更像一块「什么值得被注意」的共享清单。它把周期性、判断型的杂事从你手里挪给 agent，代价是持续的小额 token 消耗和维护清单的纪律。起步建议：一两个任务、30–60 分钟间隔、独立频道，跑稳了再加。等它第一次在你没开口的情况下主动把该说的说给你听，你会回不去的。
