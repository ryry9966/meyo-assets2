## 背景

团队每天要发一份服务日报：接口调用量、错误分布、发布记录、待办事项。以前是值日同学早上花二十分钟，从几个日志平台和 git log 里复制粘贴，再拼进模板。这事不难，但枯燥、容易漏、格式还经常跑偏。

我们已经在用 OpenClaw 跑日常 Agent 任务，MCP 也接了几个内部工具，就顺手把日报做成了流水线。稳定运行两个月，这里把做法和踩过的坑记下来。

## 问题

核心难点不是“生成文本”，而是三件事：

1. **原始日志不适合直接喂给模型**。一天的日志几十万行，上下文塞不下；硬塞，模型就会开始编数字。
2. **下游要的是稳定格式**。日报发到群里，读者只认固定栏目，Agent 每次自由发挥就是灾难。
3. **流水线不能静默失败**。日报没发出来，比晚发十分钟糟糕得多。

## 做法

流水线分四步，确定性脚本和 Agent 各干各的：

**第一步：归集（脚本）。** cron 触发采集脚本，把前一天的各来源原始日志（服务日志、git 提交、工单导出）拉到 `reports/2025-06-12/raw/` 这样的日期目录，统一时间戳、去重。纯文件操作，无模型参与。

**第二步：结构化（脚本）。** 解析脚本把原始日志转成 JSONL，字段固定：`time / service / level / event / count`，再做一轮规则聚合：按服务×级别统计、错误 Top N、新增提交列表，输出 `metrics.jsonl`。纯代码，解析失败会抛异常。

**第三步：叙述（Agent）。** OpenClaw 定时任务启动 Agent，通过 MCP 读 `metrics.jsonl`，prompt 只要求一件事：按固定模板组织数据，输出严格遵守给定 JSON Schema 的对象——含“总览 / 异常 / 变更 / 风险”四个字段，temperature 压到 0.2。

**第四步：校验与投递（脚本 + 插件）。** 用 JSON Schema 校验第三步输出，通过就渲染 Markdown，经一个十来行的 OpenClaw 插件走 webhook 推群；不通过则把校验错误信息拼回 prompt 重试一次，再失败就标记降级并发告警，而不是硬发残缺报告。

原则一句话：**数字交给代码，措辞交给模型。**

## 踩坑点

- **最初让 Agent 直接读原始日志**，数字几乎必错。改成“先聚合、后叙述”后问题消失。
- **日期边界没对齐**：日志源是 UTC，日报按本地时间算“昨天”，第一天起就对不上。现在在归集阶段统一做时区转换，明确“日报窗口 = 本地 00:00–24:00”。
- **日志格式变更是静默的**：某服务改了日志格式，解析脚本产出空数据，日报连续三天“一切正常”。现在解析失败直接中断并告警。
- **重试导致重复推送**：校验重试后群里收到两份。把“报告日期”作为幂等键，投递前查重。
- **输出格式漂移**：即使有模板，隔几天也会多字段或漏字段。Schema 校验 + 带错误信息重试是必需品，不是可选项。

## 可复用建议

1. **中间产物全部落盘**。raw / jsonl / 最终 Markdown 分目录存放，任何一步可独立重放，排查不用重跑全链路。
2. **模板即契约**。模板和 Schema 是步骤之间的接口，改模板要像改 API 一样谨慎。
3. **先影子运行一周**。新流水线先小范围对比人工日报，确认数字一致再替换，避免信任崩塌。
4. **失败路径先于成功路径设计**。告警、心跳、幂等，这三样在写正常逻辑之前就该想清楚。

## 总结

这套东西没有黑魔法：三段确定性脚本加一个窄职责的 Agent，总共两百来行代码。收益是每天省十几分钟人力，更重要的是日报格式稳定、每个数字可回溯。下一步计划把异常检测前移到结构化阶段，让 Agent 只负责解释异常而非发现异常——继续把不确定性压缩到最小的那一格。
