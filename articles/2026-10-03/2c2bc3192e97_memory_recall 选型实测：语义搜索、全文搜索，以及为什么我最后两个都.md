## 背景

OpenClaw 助手跑久了，memory 会积累几百上千条记录：用户偏好、部署细节、报错处理过程、某台机器的特殊配置。`memory_recall` 就是助手在对话中检索这些记忆的工具，检索质量直接决定"它到底记不记得"。我们最初图省事直接上了向量检索，跑了一个月，陆续发现一些明显该召回的 case 没召回，才认真做了对比。

## 问题

两类典型失败：

1. **语义检索挂掉的 case**：用户问"上次那个 502 怎么解决的"，记忆里存的是"nginx upstream timeout，调大 proxy_read_timeout"。语义模型能理解"502 ≈ 网关错误"，但反过来，记忆里只有精确标识符时——比如 `--enable-feature-x`、`ERR_CONN_RESET`、某个文件路径——向量相似度经常排不进 top-5。
2. **全文检索挂掉的 case**：用户换个说法问"之前部署卡住的事"，记忆里写的是"构建阶段阻塞"。关键词零重叠，全文检索直接空结果。

## 做法

自建了一套 40 条的评测集做对比，步骤可以直接复用：

1. 从真实会话里捞 40 组「用户原始提问 + 应命中的记忆条目」，覆盖四类：报错码、配置项、口语化描述、中英混合。
2. 语义方案：记忆切 200–300 token 块，embedding 入库，查询取 top-5。
3. 全文方案：SQLite FTS5，正文加时间戳等元数据一起进索引。
4. 混合方案：两路各取 top-10，用 RRF（倒数排名融合）合并出 top-5。

结果：语义 recall@5 约 72%，全文约 61%，混合 89%。语义赢在口语化改述，全文赢在精确标识符，混合把两边短板都补上了，且延迟增量可忽略。

## 踩坑点

- **中文全文检索别用默认 tokenizer**：FTS5 默认按空格分词，中文整段成一个词，等于废掉。要么接 jieba 预分词，要么用 trigram tokenizer。
- **换 embedding 模型 = 全量重建**：新模型出的向量和旧向量不可比。所以向量只是衍生品，原文和元数据永远留底，随时可重建索引。
- **分块大小别拍脑袋**：切太大，一条记忆混多个主题，相似度被稀释；切太小，缺上下文。200–300 token、按段落边界切，目前没再动过。
- **别迷信相似度阈值**：试过卡 0.75 以上才返回，结果口语化提问的得分普遍偏低，整批被滤掉。改回固定 top-k、把判断交给模型更稳。

## 可复用建议

- 别二选一，**默认上混合检索**。一个 SQLite 库就能同时跑两路，实现成本远低于收益。
- 评测集从真实失败 case 长出来，比造数据有用。20–50 条就足以区分方案优劣。
- 给 recall 加日志：query、命中条目、助手最终是否采纳。攒两周日志，你就知道该优化哪一路。
- 记忆写入时就把"可检索性"当验收标准：一条记忆里如果既有结论又有精确标识符，两路检索都能吃到。

## 总结

语义搜索擅长"换个说法也能找到"，全文搜索擅长"精确串一定找到"。memory_recall 的 query 风格完全不可控，混合检索 + RRF 是性价比最高的默认解。先建评测集、再动手换方案，这个顺序比先挑 embedding 模型重要得多。
