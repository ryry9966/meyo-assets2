最近一条新闻在开发者圈刷屏：Linux 之父 Linus Torvalds——那位曾当众说 AI「90% 是营销，10% 是现实」的硬核老头——据报道已经用 Claude Code 给内核写了 8 个补丁，其中一组在特定代码路径上带来约 3 倍的性能提升（36kr 等媒体报道）。评论区照例吵翻：一派喊「真香定律永不缺席」，另一派说「8 个补丁也配吹？」。这篇文章不站队，只拆三件事：到底发生了什么、AI 写内核代码卡点在哪、以及「3 倍」这个数字该怎么读。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-16/43dd2d3e78c8c25c.png)

## 先把事实捋清楚：他到底做了什么

- **时间线**：2025 年年中的 Open Source Summit 上，Linus 的原话大意是 AI「90% 是营销，10% 是现实」，但他同时补了一句——那 10% 才是真正会发生事情的地方。随后在下半年（欧洲站前后）的访谈中，他确认自己开始实际使用 Claude Code 这类 AI coding 工具，处理内核维护相关的具体工作。
- **两个关键限定词**：第一，这些补丁集中在「维护性、机械性」的工作上（脚本、小模块、局部优化），不是「AI 重写了内核调度器」；第二，「3 倍」是特定代码路径的局部 benchmark 数字，不是整个系统快 3 倍。
- **体量参照**：Linux 内核近 4000 万行代码，一年发 6~7 个大版本，每个版本合并上万个 commit。8 个补丁在这盘子里，约等于往太平洋倒一桶水——但热搜的点从来不在量，而在「谁」倒的。

## 为什么「谁写的」比「写了多少」更重要

- Linus 是内核合并的最终门禁（gatekeeper）。任何补丁进 mainline，都要经过 maintainer 层级逐级 review、走 LKML 邮件列表讨论，最后由他或子系统负责人点头。他个人的工具选择，等于向整个社区发信号。
- 内核社区文化一贯保守：代码风格有 checkpatch.pl 把关，内存与并发语义有苛刻惯例，历史上 Linus 长期对 C++ 关门、对激进的语言特性说不。这不是守旧，是这个项目的错误成本实在太高。
- 所以「Linus 亲手用 AI 写补丁并走完流程」这个动作，比性能数字更有信息量：它意味着 AI 的产出第一次**穿过了**内核社区最挑剔的 review 链路。注意，是穿过，不是跳过——这是很多人读新闻时漏掉的一环。

## 机制拆解：AI 写内核代码，卡点到底在哪

为什么早不真香、晚不真香，偏偏是现在？把场景拆开看就明白了：

1. **LLM 擅长的部分**：模式补全、样板代码、维护脚本、注释、patch 格式转换——这些是「高模式密度、低上下文依赖」的任务，命中率高。Linus 自己也说，交给 AI 的先是这类 mechanical 的活。
2. **LLM 容易翻车的部分**：内核代码要考虑内存安全、锁的顺序（lock ordering）、中断上下文、不同架构的边界情况，还有 30 多年积累的隐式约定。模型可能生成「看起来很合理」的调用，但那个函数在当前版本根本不存在，或者在不持锁的场景下调用了需要持锁的东西。
3. **审查是兜底，不是装饰**：AI 产出的补丁依然要过 checkpatch、maintainer review、邮件列表讨论、kernelci 这类持续集成测试。真正的门槛从来不是「能不能写出代码」，而是「能不能让一群最挑剔的人签字」。

更准确的描述是：AI 的能力曲线，恰好跨过了「内核维护工作中低风险部分」的可用性阈值。Linus 的转变不是被打脸，而是他口中那「10% 现实」，终于涨到了他日常工作的水位线。

## 读数之前先冷静：「性能 3 倍」的正确打开方式

工程师看到性能数字，先问三个问题：

- **测的是什么范围？** 微基准还是系统级 benchmark？一段热路径代码（比如某个哈希函数、字符串处理）优化后快 3 倍完全可能，整个系统快 3 倍基本是天方夜谭。
- **负载是什么？** 同一段代码，在小包转发、大文件拷贝、OLTP 场景下表现可能天差地别。没有 workload 描述的数字，默认打折。
- **基线是什么？** 对比上一版本、对比未优化实现，还是对比某个故意写得很慢的实现？基线不同，3 倍的含金量差一个数量级。

内核历史上不缺「局部暴涨」的先例：memcpy 这类高频原语经过 SIMD 与架构特化后，特定负载下提升数倍是常规操作。所以「3 倍」值得高兴，但它证明的是「这个补丁质量不错」，不是「AI 让 Linux 快了 3 倍」。把后者当结论转发的人，正好掉进 Linus 嘲讽过的那「90% 营销」里。

## 三条实用建议：把这条热搜翻译成自己的行动

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-16/2c915098b49e85bf.png)

1. **给 AI 产出设 review 门禁，像内核一样**。按风险给任务分层：脚本、测试用例、文档、样板重构这些低风险高模式的活，放心交给 AI；涉及并发、安全边界、核心逻辑的部分，AI 只出草稿，人来签字。团队可以定一条硬规则：AI 参与的 PR 标注生成范围，reviewer 重点盯边界条件。
2. **对工具的态度用「跑过再说」替代「站队」**。Linus 最值得学的不是他夸了谁，而是路径：先嘴硬，再亲手实验，最后基于自己的使用体验更新判断。听十篇评测，不如给自己 30 分钟做个小实验。
3. **看到性能数字先复述测量条件**。下次见到「性能暴涨 N 倍」，把它翻译成「在 X 场景、Y 基线、Z 范围内快了 N 倍」——翻译不出来就别转发。这个习惯在做技术选型、写方案、汇报数据时都救命。

最后一点冷思考：这条新闻最有价值的部分，不是「AI 赢了」，也不是「老头服了」，而是展示了一条健康的判断路径——门禁者的观念更新，靠的不是 hype，是亲手跑过的补丁和看得见的 benchmark。对一个技术社区来说，这比再开十场圆桌都有说服力。
