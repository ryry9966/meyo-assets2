## 背景

做自动化久了会发现，真正稳定的信息源还是 RSS。社交平台抓取方案三天两头失效，而 RSS 便宜、可自托管、格式统一。问题是订阅源一多，原始条目噪声极大——每天几百条里值得看的可能不到十分之一。这篇记录我用 OpenClaw 搭的一条「抓取 → 过滤 → AI 摘要 → 定时推送」管线，跑了一个多月，成本和稳定性都比较可控。

## 问题定义

核心诉求三条：

1. **降噪**：多源重复、软广、标题党要在摘要前过滤掉；
2. **压缩**：几十条原始内容压成几分钟读完的日报，且保留原文链接可回溯；
3. **可控**：摘要质量能审计，坏源能自动发现，不能是个黑盒定时给我灌幻觉。

## 做法

整体分四段，各自独立，用 SQLite 做中间存储：

**1. 抓取层**。cron 每 30 分钟跑一次 fetcher，rss-parser 解析，按 `guid`（缺失时退化为链接 hash）去重后入库。源列表放配置文件，每个源记录 `last_fetch_at` 和连续失败次数。

**2. 过滤层**。两条规则：一是标题+摘要的关键词黑名单（招聘、活动、软广类）；二是跨源标题相似度去重，分词后算 jaccard，阈值 0.6 左右就够。实测这一层能砍掉一半以上条目，比让模型过滤便宜得多。

**3. 摘要层**。过滤后的条目按主题分组，调用 agent 批量生成摘要，输出严格走 JSON schema：`{topic, items:[{title, url, one_line, why_matters}]}`。system prompt 里写死约束：只基于给定内容概括，信息不足就写「原文信息不足」，禁止推断。最后对整份内容做一次总排序。

**4. 推送层**。digest 渲染成 Markdown，webhook 推到 IM，同时落一份静态页存档，每条带原文链接。

我把第 2、3 步封装成 MCP tool 挂到 OpenClaw agent 上，平时对话式问「今天这个领域有什么值得看的」，agent 调工具返回分组结果；定时日报只是同一条链路的 cron 触发形态，两套入口共享同一份缓存。

## 踩坑点

- **编码**：不少老源是 GBK，解析前必须探测编码，否则中文全乱码，用 iconv 兜底。
- **摘要截断**：部分源只给 summary 不给全文，摘出来空洞。对这类源加了正文抓取（readability 提取），失败就降级为「仅标题列表」，别硬摘。
- **幻觉**：早期模型会给短内容「补充背景」，看着专业全是编的。解法是 prompt 明确禁止，输出校验时把长度异常、出现原文没有实体的结果打回重试。
- **token 成本**：一开始每条单独摘，一天烧掉不少，改成按主题分批后成本降到约三分之一。
- **静默失败**：fetcher 挂了没人知道，日报照发（内容是旧的）。加了两个检查：源连续失败 3 次自动标灰并通知；digest 条目数明显低于历史均值时告警。

## 可复用建议

1. **四段解耦**，任何一段坏了能单独重跑，别写成一个大函数；
2. **摘要必须可回溯**：存储层保留原始条目与摘要的关联，抽查时能一键跳回原文；
3. **过滤放在模型前面**，规则能解决的不花钱；
4. **schema 校验失败重试一次**，再失败就人工介入，宁可少一份日报也别发错的；
5. 源列表当成资产维护：每季度清一次死源、补一次新源，比调 prompt 提升更大。

## 总结

这条管线的价值不在技术难度，而在信息源自有、过程可审计、成本可预估。RSS + AI 摘要是 agent 落地里少数几周就能稳定见效的场景，建议从 10 个以内的源起步，把去重和校验做扎实再扩量。欢迎在评论区交换各自的源列表和过滤规则。
