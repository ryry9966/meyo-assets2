## 背景

大多数人对 Agent 的用法是被动的：打开会话、提问、拿答案、关掉。但 OpenClaw 的 Agent 通常本来就 7×24 跑在服务器上，大部分时间在空转。OpenClaw 内置了心跳（heartbeat）机制：主 Agent 会按配置的间隔被周期性唤醒，读取 workspace 根目录下的 `HEARTBEAT.md`，自行判断要不要干活；没事的应答会被系统吞掉，不会推给你。这个文件本质上是给 Agent 的"常备指令清单"——问题在于怎么写才有用而不吵人。

## 问题

实践里常见的两个极端：

1. 从没写过 `HEARTBEAT.md` → 心跳空转，Agent 依然只是个问答机器；
2. 写得太随意 → 每 30 分钟收到一条"一切正常"，通知轰炸，最后干脆把心跳关了。

根因都一样：主动行为需要明确的"上报规则"和"静默规则"，而多数人没把这两条写下来。

## 做法与步骤

1. **确认心跳开启并设好间隔**。在配置里设 `heartbeat.every`（如 `30m`），设 `0m` 可整体关闭。注意 tick 不是精确时钟，会和正在进行的会话串行，别指望它做秒级调度。
2. **在 workspace 根目录创建 `HEARTBEAT.md`**。路径必须精确，文件不存在就等于没开启。
3. **用清单式短句写**，参考模板：

```markdown
## 每次心跳检查
- 磁盘使用率 > 85% 或内存持续紧张 → 发到运维频道
- 有失败的 systemd 服务 → 发到运维频道
- 08:00–09:00 之间的那次心跳：汇总昨晚 CI 结果，发一条日报
其他情况一律保持安静，不要汇报"一切正常"。
```

4. **先只做"检查 + 上报"，不做自动修复**。跑几天、翻日志，确认误报率可接受后，再逐条放开低风险动作（比如允许重启某个指定服务），一次只放开一项。
5. **配合 MCP / 插件**：心跳只是调度器，能力靠工具。每个检查项应映射到明确的工具调用，避免让模型"随便看看"。

## 踩坑点

- **噪音**：没写静默规则。LLM 天然倾向"给点反馈"，必须显式写"其他情况保持安静"。
- **成本**：每次 tick 都是一次模型调用。5 分钟间隔挂大模型，一个月账单不难看。低频检查用长间隔，或把心跳会话路由到便宜模型。
- **文件膨胀**：塞 20 条任务后模型开始漏项。保持在一屏内、按优先级排，两周没触发过的直接删。
- **时间漂移**：模型对"当前时间"的感知不稳，日报类任务写时间窗口（08:00–09:00），别写"每天早上"。
- **无人工确认**：心跳是全自动执行的，不要写删除、批量清理类指令，除非你真的想清楚了回滚方案。
- **放错目录**：只在 workspace 根目录生效，放进子目录等于没写。

## 可复用建议

- 每个 Agent 一份 `HEARTBEAT.md`，纳入 git 管理，行为变化可追溯、可回滚。
- 两个通用模式直接抄：「异常才说话」（监控类）和「每日一份摘要」（日报类），先跑通再改。
- 上报规则写清三件事：触发条件、发到哪个渠道、聚合一条还是逐条。
- 每月回顾一次：删掉没产生价值的检查项。心跳的价值恰恰在于克制。

## 总结

`HEARTBEAT.md` 把 Agent 从"被动应答"升级成"定时值守"，但它不是 crontab 的替代品，也不该承载复杂工作流——那种活交给专门的调度加脚本更可靠。给它少量、明确、带静默规则的任务，它就是个不吵人的值班员；写满宏大目标，它就是通知轰炸机。建议从一条磁盘检查开始，跑一周，再谈扩展。
