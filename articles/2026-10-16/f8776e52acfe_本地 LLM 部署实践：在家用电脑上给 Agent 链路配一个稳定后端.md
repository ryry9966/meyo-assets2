## 背景

最近半年我把不少自动化流程搬回了家里一台老台式机：12GB 显存（RTX 3060）、32GB 内存、i5 十代。动机很实际——Agent 循环太烧 token，一次多轮工具调用跑下来，云端 API 账单肉眼可见地涨；另外很多任务要读本地文件和日志，数据不想出门。这篇文章记录我把本地模型接进 OpenClaw Agent / MCP 链路的完整过程，重点不是“怎么跑起来”，而是“怎么稳定地跑”。

## 问题

聊天场景和 Agent 场景对本地模型的要求完全不同。聊天只需要回答一次，Agent 需要连续十几轮保持格式稳定、正确发起工具调用、撑住长上下文。我一开始按“能聊天”的标准部署，结果链路跑两轮就崩，排查了三天才定位到根因。

## 做法

1. **硬件盘点定上限**：12GB 显存的甜点区是 7B~14B 的 Q4 量化模型。注意 KV cache 也吃显存，上下文开到 16k 至少再预留 2~3GB。
2. **运行时选择**：Ollama 上手最快，自带 OpenAI 兼容接口，Agent 框架改个 base_url 就能接；需要更细的量化/采样控制再下沉到 llama.cpp。vLLM 吞吐好但显存门槛高，家用不划算。
3. **模型选择**：优先选官方明确支持 function calling 的 instruct 版本，Q4_K_M 起步，工具调用不稳再升 Q5。别追跑分榜第一名。
4. **接入链路**：把 Agent 的 `base_url` 指向本地端点，MCP 工具的 description 重写一遍——小模型对模糊描述极其敏感，“查询订单”和“根据订单号查询物流状态并返回 JSON”是两个世界。
5. **参数显式固定**：`temperature` 压到 0.2~0.6，`num_ctx` 显式设到 8k 以上，`keep_alive` 设长。

## 踩坑点

- **上下文默认值是头号杀手**。Ollama 默认 `num_ctx` 只有 2k/4k，system prompt 加几轮工具结果就被静默截断，表现为“模型失忆”。这个问题最难排查，因为不报错。
- **小模型工具调用不稳定**：JSON 格式错、参数幻觉、该调用时不调用。缓解手段：精简同时挂载的工具数量（5 个以内）、描述写死参数 schema、失败重试一次。
- **keep_alive 默认 5 分钟**。定时任务间隔一长，模型就卸载，下次调用冷启动十几秒，Agent 看起来像卡死。改 `OLLAMA_KEEP_ALIVE` 后消失。
- **显存 OOM 不一定是模型的锅**：浏览器硬件加速、截图工具都会抢显存，长上下文场景建议独占。
- **跑分高 ≠ 工具调用稳**。最后是拿自己 20 条真实 Agent 任务样本做评测选的型，比榜单靠谱。

## 可复用建议

- **分层路由**：分类、抽取、格式化这类高频确定性调用走本地小模型，复杂推理和长文写作走云端，网关按任务类型分流，成本能砍掉大半。
- **把模型名+量化版本当依赖锁进配置**。换模型=换依赖版本，全链路行为都可能变，要回归测试。
- **本地部署的真正价值**是数据不出门、离线可用、没有速率配额——特别适合夜间批量跑本地文件的自动化任务。
- **先定评测再选模型**，用真实 trace，不用公开 benchmark。

## 总结

12GB 显存级别跑本地 LLM 已经完全可用，核心工程量在于把它稳定地接进 Agent 链路：上下文显式设够、加载策略调对、工具描述写清。建议从 7B Q4 起步，用真实任务验证一周，再决定要不要为它升级硬件。省钱是副产品，可控才是目的。
