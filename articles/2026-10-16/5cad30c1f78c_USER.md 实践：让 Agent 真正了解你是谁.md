# 背景

OpenClaw 的工作区里有一组约定文件：`AGENTS.md` 管行为，`SOUL.md` 管人格，`MEMORY.md` 管事件记忆。还有一个最容易被忽略的：`USER.md`——agent 每次会话都会加载的"用户档案"。

多数人的 USER.md 是空的，或者只有一行名字。结果就是 agent 每次都问时区、每次都用你不喜欢的口吻、每次都从零开始猜你是谁。

# 问题：你的 Agent 对你一无所知

典型表现：

- 新会话反复确认基本信息："你在哪个时区？""用什么语言回复？"
- 你是后端工程师，它还在解释 Python 基础语法
- 明明说过偏好中文短答复，过两天又用英文长段落轰炸
- 每次都要重复交代项目背景

这些不是模型能力问题，是上下文缺失。USER.md 是补这块上下文最便宜的手段。

# 做法：把 USER.md 当配置文件写

位置：工作区根目录（如 `~/.openclaw/workspace/USER.md`），会话启动时自动读取。

建议结构，五个小节、每节几行即可：

```markdown
# 用户画像
## 基本事实
- 昵称 X，时区 UTC+8，主要用中文交流
## 技术背景
- 熟悉：Go、K8s、PostgreSQL
- 不熟：前端、机器学习
## 沟通偏好
- 先给结论再给依据；代码不用逐行解释
## 环境与设备
- macOS + Docker，常用 MCP：filesystem、github
## 边界与红线
- 涉及生产库的操作必须先确认
```

写法原则：**写事实，不写愿望**。"我要变强"没用，"当前在做支付网关重构，目标 Q2 上线"有用。

维护方式：直接告诉 agent"把我现在在做的事记到 USER.md"，它会自己追加。但务必把工作区纳入 git——agent 的改动你需要 review，否则三个月后这个文件会膨胀成一锅粥。

# 踩坑点

1. **写成日记。** USER.md 每次会话都进上下文。事件、过程类记录应进 MEMORY.md，USER.md 只放稳定事实。判断标准：这条半年后还成立吗？
2. **塞行为指令。** "回复要幽默""不要用 emoji"属于 AGENTS.md/SOUL.md，混进来会让两份文件职责纠缠。
3. **放敏感信息。** 密码、API key、详细住址都不要写——这份文件会进每一次模型调用，还可能被日志留存。
4. **信息过期不清理。** 旧的项目名、旧的偏好留着，agent 会拿去过时信息推理，比没有更糟。
5. **偏好互相矛盾。** 既写"要简洁"又写"每步详细解释"，agent 只能随机选一个，你得不到稳定体验。

# 可复用建议

- **核心 + 时间戳分区**：上半部分是长期事实，下半部分按日期放"当前关注"，每月 review 一次、删掉过期项。
- **用对话校准**：开个新会话问 agent"复述一下你对了解多少"，看它实际读到了什么，比肉眼检查更接近真实效果。
- **控制体积**：30 行以内收益最高；超过 100 行后边际收益为负，关键事实会被稀释淹没。
- **明确分工**：USER.md = 我是谁，MEMORY.md = 发生了什么，TOOLS.md = 怎么干活。各管各的，不要互相越界。

# 总结

USER.md 本质上是一个成本极低、由你自己维护的上下文注入点。它不会让模型变聪明，但能省掉大量重复交代，让 agent 的默认行为贴合你的真实环境。工程化地对待它——有结构、有边界、有版本控制、定期修剪——它就是长期人机协作里投入产出比最高的一个文件。
