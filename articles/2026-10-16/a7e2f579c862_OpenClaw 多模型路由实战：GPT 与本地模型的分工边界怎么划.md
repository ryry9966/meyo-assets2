## 背景

OpenClaw 的 agent 链路里，模型调用远不止一次：意图理解、工具编排、参数抽取、结果总结，一个任务跑十几轮很常见。全部走 GPT 这类云端模型，账单和延迟都会失控；全部换成本地模型，复杂任务的工具调用又经常翻车。所以多模型路由要回答的不是"哪个模型最强"，而是"哪类调用配哪档模型"。

## 问题：一刀切的代价

我们最早的做法是全走云端——稳定，但一个每天几千次调用的自动化流程，八成调用只是抽字段、改格式，纯粹在烧钱。后来一刀切换本地模型，节省立竿见影，但多步规划任务的成功率明显下滑，报错还都是间接的：工具调错了参数、漏了一步。问题必须拆开看。

## 做法

**1. 按角色拆分，不按名字路由。** 把链路里的调用归成三类：

- 编排/规划类：多步推理、决定调哪个工具、出错恢复 → 云端强模型；
- 结构化类：抽字段、格式改写、摘要、翻译 → 本地模型（Ollama 跑 Qwen/Llama 级别足够）；
- 嵌入/向量化：一律本地，省心省成本。

在 OpenClaw 的模型配置里按角色定义 profile，工具和 skill 绑定角色而不是模型名：

```yaml
models:
  planner: gpt-high       # 编排/规划
  worker: local-qwen-32b  # 抽取/摘要
routes:
  extraction: [worker, planner]  # 本地失败升级云端
  planning: [planner]            # 不降级
```

换模型只改一处，agent 代码不动。

**2. 显式降级链。** 便宜任务本地先行，解析失败再升级云端，重试上限 1 次；昂贵任务云端先行，限流/超时回落本地——宁可慢，不可断。

**3. 用数据定边界。** 上线前准备 30~50 条真实样本做小评测集，记录每条路由的准确率和 P95 延迟。边界是调出来的，不是拍脑袋出来的。

## 踩坑点

- **本地模型 function calling 格式漂移**：字段漏填、把 JSON 包在自然语言里。MCP 工具的 schema 要做严格校验，失败走一次修复重试，别裸信输出。
- **上下文长度错配**：云端 128k 用惯了，本地 8k/32k 一接长对话就静默截断，agent 记忆悄悄断掉。路由前先查 token 数。
- **显存冲突**：两个本地模型同时加载直接 OOM。要么一个本地模型兼任多个角色，要么做好模型卸载。
- **降级风暴**：本地失败→云端→限流→回本地，单次任务延迟翻四倍。降级链必须有上限和熔断。
- **质量回归是无声的**：换路由不报错，只是抽取准确率从 96% 掉到 88%，两周后才发现。评测集就是保险丝。

## 可复用建议

- 一句话版本：**规划上云，执行落地**。
- 路由键用能力标签（reasoning / extraction / embedding），别写死厂商名，方便以后换模型。
- 每类任务设 token 预算，超预算告警。
- 降级是策略不是异常，日志里单独打 `route_fallback` 事件，方便统计真实升级率。
- 改路由之前先跑评测集，任何"感觉差不多"都是回归的开始。

## 总结

多模型路由不是炫技配置，是成本、延迟、隐私三者的工程权衡。在 OpenClaw 里按角色拆 profile、设显式降级链、用小评测集守边界——三件事做完，GPT 花在该花的地方，本地模型干它擅长的活。从"全走云端"迁到分层路由，一两天就能落地，收益是长期的。
