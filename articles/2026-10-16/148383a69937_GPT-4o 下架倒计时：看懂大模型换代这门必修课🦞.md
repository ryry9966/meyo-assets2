据 36kr 报道，GPT-5.5 正式在 ChatGPT 上线，与此同时，旧版 GPT-4o API 被官方挂上了 3 个月下架倒计时。对普通用户来说，这是一次"对话变聪明了"的静默升级；对开发者来说，这是一封措辞礼貌的搬家通知。两件事拼在一起，恰好构成了大模型行业"怎么换代"的完整样本：产品端如何切换、API 端如何退场，以及夹在中间的每一个依赖方该做什么。这篇把机制、历史和迁移路径一次讲透。

## 先拆消息：产品换代不等于 API 直接关闸

- **产品线**：ChatGPT 界面里默认模型切换，用户感知平滑，基本无感。
- **开发者线**：API 不搞突然断电，而是走 deprecation（弃用）流程——先公告"哪个版本、何时停服"，留出缓冲窗口。这次的窗口是 3 个月，约 90 天。
- **关键概念 snapshot vs alias**：以 gpt-4o 为例，`gpt-4o` 是别名（alias），始终指向最新的稳定快照；`gpt-4o-2024-11-20` 这类带日期的才是快照（snapshot），行为被彻底冻结。下架针对的是旧快照，别名会自动改指向。
- 换句话说：一直用别名、没做过精细调优的团队，可能只是"模型悄悄变了"；而锁定某个快照并围绕它调过 prompt 的团队，90 天后调用会直接返回 model not found。

## 为什么旧模型必须退场：算力是硬约束

- 一块 GPU 同一时刻只能服务有限的 token 吞吐。同代际保留 N 个旧模型，等于把有限算力切成 N 份，直接摊薄新模型的可用容量和响应速度。
- 推理服务的经济学很朴素：显存常驻、批量调度、峰值冗余，每一项都要真金白银。而一个只占 1% 流量的旧模型，维护成本远不止 1%——安全复评、漏洞修补、对齐验证都要按版本重复做一遍。
- 生产环境里，请求高度集中在最新一两个模型上，长尾旧模型的"单位请求成本"高得离谱。关掉它们是资源优化，不是情怀问题。
- 还有安全与一致性考虑：在架版本越多，同一能力在不同版本间的行为差异越大，官方越难给出统一的安全承诺。
- 一句话总结：旧模型下架不是上游不厚道，而是把水槽里的水重新灌回主池。

## 历史视角：退役不是第一次，也不会是最后一次

- 2023 年 3 月，Codex 系列模型停止服务，一批"自然语言转代码"工具连夜迁移。
- 2023 年 7 月起，GPT-3 家族（davinci、curie 等 base 模型）陆续进入退役名单，随后一年内分批关停。
- 更细粒度的快照级下架从未停过：gpt-3.5-turbo-0301、gpt-4-0314/0613 这类带日期的版本，都经历过"公告—缓冲—停服"的标准三段式。
- 对比传统软件更有体感：Windows XP 从发布到停止支持走了 12 年以上，而大模型快照的生命周期常常只有 6~18 个月。"半年一换代，一年清一代"不是某家公司的任性，而是算力成本与迭代速度共同决定的结构性节奏。

## 谁受影响最大：三种高危姿势

1. **代码里写死快照号、没有预案的团队**：倒计时归零直接报错，客服先炸。
2. **没有评测集（eval set）的团队**：换完模型说不清"变好还是变坏"，只能靠感觉——而感觉在工程里不值钱。
3. **深度调优过 prompt 的应用**：比如客服机器人的语气、拒答边界、格式遵循全贴着 4o 的脾气调，换到 5.5 之后，同样的 prompt 可能输出更长、更啰嗦，JSON 偶尔漂移出格式。
- 别忘了成本也要重算：新模型常伴随定价结构调整（缓存输入折扣、分档计价），只盯单价容易得出错误结论。

## 90 天迁移实操：一张行动清单

1. **盘点（第 1 周）**：全局搜索代码与配置里的模型名，列出所有在用快照。没人说得清系统里到底有几处调用——这是迁移项目的经典开胃菜。
2. **固化基线（第 1~2 周）**：从真实流量里抽 100~200 条代表性请求，记录当前输出，做成"黄金集"。
3. **小流量 A/B（第 2~4 周）**：切 5%~10% 流量到新模型，在黄金集上对比质量、延迟、成本三项指标。
4. **Prompt 重校准（第 4~6 周）**：新模型指令遵循通常更强，很多手把手的约束可以精简；格式化输出加 schema 校验兜底。
5. **架构解耦（第 6~8 周）**：把模型调用收敛到统一网关层，用别名跟随升级，同时保留切换其他供应商的余地。
6. **收尾（第 8~12 周）**：全量切换；在 T-30 天和 T-7 天各设一次日历提醒，盯紧官方 deprecation 页面和邮件公告。
- 经验值供参考：有评测集的团队，这类迁移一般 3~5 个工作日收工；没有的，基本靠熬夜和运气。90 天说长不长，够开两次迭代会，不够还一次技术债。

## 收尾：三条冷思考

1. **把模型当耗材，不当信仰**。API 时代的模型更像数据库版本——你会为 PostgreSQL 升级写迁移脚本，也该为模型升级做同样的准备。
2. **评测能力才是真护城河**。模型每半年换一代，谁的黄金集和自动化评测跑得快，谁就能把"被动搬家"变成"主动升级"。
3. **对外承诺别绑死模型名**。给客户的 SLA 和产品文档里写"智能助手能力"，别写"由某模型驱动"——上游换代，不该变成你的违约现场。
