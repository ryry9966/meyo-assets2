## 背景

Agent 有个尴尬的现实：能力越强，越衬得它"记性差"。你上个月说过"回复尽量简短""这个项目用 pnpm"，今天开新会话它又全忘了，只能再教一遍。

对 OpenClaw 这类可接 MCP、跑长任务的 Agent 来说，上下文窗口再大，也不该靠"把历史对话全塞进去"解决。记忆必须单独设计，当成一等公民。

## 问题拆解

拆开看是三个子问题：

- **记什么**：偏好（稳定、结构化，如包管理器、时区、语气风格）和事实（易变、零散，如"部署在一台 VPS 上"）要区别对待；
- **什么时候记**：会话中实时写，还是会话后批量抽取；
- **怎么取**：新会话注入多少、按什么优先级排序。

## 做法：三层记忆

**1. Profile 层（结构化，全量注入）**

JSON 键值对，数量控制在几十条内：

```json
{
  "reply_style": "concise",
  "pkg_manager": "pnpm",
  "timezone": "Asia/Shanghai"
}
```

每次会话启动整体注入 system prompt，成本可忽略。

**2. Episodes 层（追加日志，按需检索）**

Markdown 文件，一行一条，带元数据：

```
- [scope:infra] 部署目标是 4C8G 的 VPS | conf:0.8 | 2024-05-11
```

检索时先按 scope 和关键词过滤，取 top 3~5 注入。条目超过一百条再考虑 embedding，别一上来就上向量库。

**3. Working 层**

当前会话上下文，不落盘，不用管。

**写入策略**：会话结束后跑一次抽取 pass，让 LLM 从对话产出候选条目和置信度，过阈值才写入；同 key 冲突时新值覆盖旧值，旧值进历史。会话中不实时写，避免打断任务节奏。

## 踩坑点

1. **什么都记等于什么都不记。** 噪声稀释检索结果，还吃 token。判断标准只有一条：这信息会改变未来行为吗？
2. **抽取模型会脑补。** 用户提过一次的临时需求常被存成永久偏好。用置信度门槛，多次复现才升级进 Profile。
3. **冲突条目同时被检索。** 两条矛盾记忆都进上下文，Agent 行为漂移。写入时必须去重和覆盖。
4. **scope 没隔离。** 工作项目的偏好泄漏到私人对话，尴尬且危险。
5. **没有退出机制。** 记忆只增不减，三个月后全是过时信息。

## 可复用建议

- 从最土的方案开始：一个 `MEMORY.md` + 一个 MCP 写入工具，用 git 管理，可 diff、可回滚、可手改；
- 提供一个 `/memory` 查看命令。记忆必须对用户可见可编辑，黑箱记忆没人敢用；
- 每条记忆带 `last_used` 字段，低置信度且长期未命中的条目定期清理；
- 加一行观测日志：本次回复引用了哪条记忆。跑两周你就知道该删什么、该留什么。

## 总结

Agent 记忆的难点不在存储，而在**写入门槛**和**检索精度**。核心原则：少记、结构化、分层注入、可编辑。先用文件加规则跑起来，遇到真实瓶颈再升级，别被"必须上向量数据库"带偏了第一步。
