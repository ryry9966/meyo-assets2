## 背景

我在自己的 OpenClaw 工作区里跑了一套长期记忆方案：助手每次会话把值得记的结论写成 markdown 存进 notes 目录，`memory_recall` 负责在下一次对话时把相关片段捞回上下文。攒了小半年，两千多条笔记，开始明显感觉"记了但想不起来"，于是认真做了一轮检索方案对比。

## 问题

失败案例集中在两类：

- 问"上次那个部署超时最后怎么解决的"，相关笔记标题其实是《CI runner 超时排查记录》。纯关键词搜不到——**用词对不上**。
- 问"`memory_recall` 的 `top_k` 参数怎么配"，语义搜索返回一堆讲"记忆系统设计"的泛泛笔记，偏偏漏掉那条写满配置键名的笔记。

前者是语义搜索的强项，后者是全文搜索的强项。所以答案不是二选一。

## 做法

最终落地的是混合召回，结构不复杂：

1. **两路索引并行**。语义路：笔记按 300–500 token 切块（带 50 token 重叠），过 embedding 模型建向量索引；全文路：SQLite FTS5 建 keyword 索引。
2. **RRF 融合排序**。两路各取 top-20，用 Reciprocal Rank Fusion 合并。别用加权分数——两路分数量纲完全不同，归一化能调到怀疑人生；RRF 只看排名，稳。
3. **时间衰减 + 置顶**。融合分乘一个基于时间戳的衰减因子，重要结论手动 pin。半年前的老笔记和昨天的笔记不该同权。
4. **先过滤后搜索**。recall 入口支持按 tag / 来源 / 时间范围先缩小候选集，比纯靠排序兜底靠谱得多。
5. **建回归集**。手写 40 条查询（一半口语化转述、一半精确 token），每次换 embedding 模型或调参就跑一遍，人工核对 recall@5。

## 踩坑

- SQLite FTS5 默认 tokenizer 会把中文整句当一个 token，**全文路对中文基本失明**。必须上 jieba 分词或 trigram，这步不做，混合召回等于白搭。
- 切块太大（整篇一块）召回分数被稀释，太小又全是碎片上下文，300–500 token 实测比较稳。
- `top_k` 别贪多。超过 10 条后模型对召回内容的利用率明显下降，还容易引入干扰，5–8 条是甜点区。
- 中英混排（中文叙述 + 英文报错码）的笔记，部分 embedding 模型表现很差。换模型前务必跑回归集，别只看 demo 效果。

## 可复用建议

- 默认答案就是**混合**。只有余力做一路时：工作负载以精确 token 为主（配置键、报错码、函数名）先做全文；以口语化经验记录为主先做语义。
- 花一周记录 recall 实际命中了什么、模型真的用了哪几条，比任何 benchmark 都诚实。
- 回归查询集是迁移模型时唯一的安全网，40 条一晚上能写完，性价比极高。

## 总结

语义搜索解决"换个说法还能找到"，全文搜索解决"精确 token 一击命中"，真实的记忆系统两个都需要。而真正决定体验的往往不是检索算法本身，而是切块粒度、top_k、时间衰减这些工程细节。先用最小 hybrid 方案跑起来，再用回归集持续校准，比纠结选型有用得多。
