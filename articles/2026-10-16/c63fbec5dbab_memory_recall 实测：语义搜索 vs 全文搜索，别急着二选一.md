## 背景

OpenClaw 的 memory_recall 是 agent 访问长期记忆的统一入口，但底层检索路线不止一条：语义搜索（embedding + 向量检索）和全文搜索（关键词/BM25）都能接。社区里常见说法是"语义更智能"，我最近把自己那套 agent 的记忆检索重做了一遍，实测结论是：二者各有明确的失败模式，混合方案才是正解。

## 问题

我的记忆库里大量条目是短句、命令、路径、版本号，比如"gpt-4o-mini 的速率限制笔记""deploy.sh 踩过的坑"。跑了一周发现两类典型故障：

- 语义搜索查"gpt-4o-mini rate limit"，排前面的是一堆讲大模型限流原理的条目，真正那条笔记反而靠后；
- 换全文搜索，用户问"上次那个部署脚本为什么失败"，措辞对不上，完全召回不到。

单选任何一路，都有系统性盲区。

## 做法

1. **先建评测集**：从真实会话抽 40 组"用户问题 → 应命中的记忆条目"，这步最花时间也最值钱。别让 LLM 生成"理想问法"，真实问法更短、更口语。
2. **双路索引**：同一批记忆分别建 SQLite FTS5 全文索引和向量索引（小模型 embedding 就够），查询时并行执行，各取 top-10。
3. **归并**：两路结果用 RRF 合并；再加一个简单兜底——全文命中且包含完整关键词的条目直接置顶。
4. **回归评测**：每次调权重、换模型、换 tokenizer，重跑评测集，盯 hit@5。

## 踩坑点

- **中文分词**：FTS5 默认 tokenizer 对中文几乎不可用，需要 trigram 或 jieba 预分词，否则中文全文搜索形同虚设。这是我最大的返工点。
- **chunk 粒度**：单条记忆尽量不切块。切了之后语义检索命中的片段缺上下文，recall 回来 agent 也用不上。
- **语义分数区分度低**：短查询下 top-10 分数挤在一起，别直接用分数阈值过滤。
- **换 embedding 模型必须全量重建索引**，模型版本写进元数据。我吃过新旧版本混存的亏。
- **RRF 权重别调过头**：全文置顶逻辑会让错别字、单个汉字命中污染结果。

## 可复用建议

- 判断口径很简单：记忆里专有名词、代码、路径占比高 → 全文权重大；叙述性内容多、中英混杂 → 语义权重大。
- 记忆量小于 5000 条时，SQLite FTS5 + 单路向量完全够用，别急着上独立向量库。
- 把评测脚本沉淀下来，它比检索实现本身更有长期价值——换模型、换存储时都是同一把尺子。

## 总结

语义搜索不是全文搜索的升级替代，而是互补的召回通道。memory_recall 的效果上限取决于评测集质量和融合策略，而不是 embedding 模型多大。先用真实问法建评测，再决定架构，顺序别反。
