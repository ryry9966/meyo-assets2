## 背景

现在大部分 Agent 的交互模型还是"你问我答"：用户发消息 → 模型推理 → 调工具 → 返回。这在 chat 场景够用，但在自动化场景里暴露一个本质缺陷：Agent 没有主动感知，所有洞察都依赖用户先发现问题。盯一个目录的新文件、等一封关键邮件、每天汇总 CI 失败——这些事用户不想记，Agent 却"睡着"等调用。

OpenClaw 这类常驻型助手天然适合做 proactive：有持久进程、有 MCP 工具生态、有会话上下文。缺的只是一条从"事件"到"行动"的受控通路。

## 问题

把"定时调一下模型"直接当成 proactive，会立刻撞上三件事：

1. **打扰**：Agent 兴奋地报告一切，一天推 20 条消息，用户两周后把它静音，能力等于清零。
2. **失控**：Agent 自己的动作产生新事件，再次触发自己，形成环路。
3. **成本**：每 5 分钟拉全量上下文做"要不要说话"的判断，token 账单比干活的还贵。

所以 proactive 的核心不是触发器，而是触发之后的过滤与克制。

## 做法：一条最小管线

我在自己的实例上跑的方案分四层，全用现成组件拼出来：

1. **事件源层**。三类来源足够起步：cron（固定节奏任务，如每日摘要）、webhook/文件监听（新 PR、新文件）、MCP 工具的低频轮询（30 分钟查一次状态接口）。事件只携带轻量 payload，不做任何判断。
2. **门卫层**。用规则 + 便宜的小模型给事件打分：这值得打断用户吗？规则先行——发送人白名单、关键词、静默时段（22:00–8:00 只入队不打扰）；规则拿不准的再过一次小模型分类。大部分事件在这一层进"摘要池"。
3. **行动层**。过门卫的事件组装成一次 Agent 调用，system prompt 明确身份："你由事件 X 触发，不是用户消息"，同时注入当前预算：今天还剩几条主动消息额度。Agent 可以行动，或只写进待办。
4. **审计层**。每次 proactive 行动落一条日志：触发源、评分、最终动作、是否打扰了用户。这是后续调阈值的唯一依据。

MCP 在这里的角色很干净：事件源和执行动作都封装成 tool，proactive 管线只是另一个调用方，Agent 本身的工具面不用改。

## 踩坑点

- **自触发环路**：Agent 写日志 → 文件监听捕获 → 再次触发。解法是给事件打 source 标记，来自 Agent 自身动作的事件默认静默。
- **误报高峰**：第一版门卫只用小模型，周末把促销邮件判成"紧急"。白名单 + 静默时段这两个土办法比调 prompt 有效得多。
- **上下文漂移**：事件触发时带上整个会话历史，长会话会把判断带偏。proactive 调用建议用独立最小上下文，只注入事件描述和固定人设。
- **额度形同虚设**：只设"每天最多 5 条"没用，得让 Agent 在 prompt 里真的看到剩余额度，否则它每次都认为自己是例外。

## 可复用建议

- 先上 digest 再上实时：所有 proactive 输出先进每日摘要，跑一周看日志，再决定哪些升级为即时通知。
- 每条主动消息留一个负反馈入口（哪怕用户回一句"别推了"），用这个词反查日志调阈值。
- proactive 是权限敏感的：只读动作可自动执行，写类动作（发消息、改文件）默认 dry-run，用户确认一次后放行同类操作。
- 门卫和 Agent 分开部署：门卫挂了最多漏提醒，不会让 Agent 失控。

## 总结

proactive 的价值不在"主动"本身，而在克制下的主动：绝大多数事件沉默地进摘要，少数高置信事件才打断用户，所有动作可审计、可回滚。先用最土的规则把噪音挡在门外，再逐步把判断交给模型——顺序反过来，项目通常活不过两周。
