## 背景

RSS 没死，只是被藏起来了。博客、GitHub Release、期刊、播客都有订阅源，配合 RSSHub 还能把很多没有 RSS 的服务转出来。问题不是“没有信息”，而是信息过载——我订阅了 60 多个源，每天新增条目 300+，逐条读不现实，全量扔给 LLM 总结又贵又吵。

这篇记录我用 OpenClaw 搭的一条 RSS → 过滤 → 打分 → 日报管线，核心原则是：省该省的钱，不省不该省的步骤。

## 问题

直接让 Agent“帮我看看今天的 RSS”会撞上三件事：

1. **无差别摘要**：300 条全量过模型，token 成本高，而且大部分是噪音；
2. **摘要不可比**：自由文本没法排序、去重、聚合；
3. **内容缺失**：不少源只给截断正文，模型容易幻觉补全。

## 做法

整体思路是“两级漏斗”：便宜的第一级决定看不看，贵一点的第二级决定怎么说。管线拆成四个独立阶段，用 OpenClaw 的定时任务串联。

**阶段 1：抓取与归一化。** 每小时抓一次，统一转成 JSON 存本地 SQLite：`{id, feed, title, url, published, content, content_hash}`。content 优先取 `content:encoded`，fallback 到 readability 正文抽取。这一步不做任何智能判断。

**阶段 2：规则过滤。** 关键词黑名单、标题正则、来源权重、URL 去重。零成本砍掉 60–70% 的条目。不要跳过这步直接上模型。

**阶段 3：AI 相关性打分。** 剩余条目按 20 条一批发给小模型，结构化输出 `{score, reason, tags}`。prompt 只放标题 + 前 500 字。score ≥ 7 进入下一阶段。

**阶段 4：深度摘要与聚合。** 入选条目逐篇生成三句话摘要 + “值得读的理由”，聚合成日报，经 OpenClaw 推送到 IM。打分和摘要都落库，同一 URL 永远只算一次钱。

Agent 在这里的角色是**编排和兜底**：解析失败的源、打分异常的批次，由 Agent 通过 MCP 工具去修，而不是每一步都让它亲自动手。

## 踩坑点

- **正文抽取是最大的坑。** 约 30% 的源 feed 里只有摘要，直接摘要等于让模型编故事。我的规则：正文不足 800 字且与 feed 摘要高度一致时，标记 `insufficient`，跳过 AI，只保留标题链接。
- **Prompt injection。** 正文里真的出现过“忽略以上指令”。打分输入要加转义说明，结构化 schema 本身就是护栏——模型再被带偏也只能输出 score 和 reason。
- **编码与时间戳。** 中文源里 GBK、RFC822、ISO8601 混用，入库前必须归一，否则去重和排序会莫名出错。
- **抓取节流。** 同域名并发拉会吃 429，按域名限速 1 req/3s 加随机 jitter。
- **模型别贪大。** 打分用小模型足够，只有最终摘要用大模型，成本降一个数量级。

## 可复用建议

1. 四阶段解耦，各自可独立重跑，出问题能定位到层；
2. 一切落库，摘要可缓存；
3. 结构化输出优先于自由文本，下游才好聚合；
4. 先规则后模型，规则能解决的不要花钱；
5. 每个源记成功率，连续失败自动降频或告警。

## 总结

管线跑了一个多月，日报从 300+ 条压到 10 条左右，月 API 成本几块钱。没有任何花哨组件——SQLite、定时任务、一个打分模型、一套 schema。自动化信息流的价值不在“AI 多聪明”，而在每一层只做自己该做的事。源列表和 prompt 模板没有标准答案，欢迎在评论区贴出你自己的过滤策略。
