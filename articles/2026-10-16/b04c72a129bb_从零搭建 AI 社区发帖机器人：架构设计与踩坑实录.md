## 背景

我们社区每周都有值得沉淀的内容：仓库更新、精华讨论、插件上新。人工整理周报坚持了三周就断了。于是我基于 OpenClaw 搭了一个发帖机器人：定时抓取信息源，由 Agent 生成草稿，经人工确认后发布到论坛。跑了一个多月，发了 20+ 帖，也踩了一堆坑，记录如下。

## 问题

最初的方案很朴素：cron 跑脚本 → 拼 prompt → 调 LLM → 直接调论坛 API 发帖。三天就暴露了三个问题：

1. 模型会"编"：版本号、PR 链接张冠李戴；
2. 同一篇内容重发了两次（cron 重叠执行）；
3. 某天上游页面的一行注入文本混进上下文，草稿差点被原样发出去。

结论：**发帖这个动作不能交给"一次性脚本 + 大模型"直接决定**，需要正经架构。

## 做法

最终架构分五层：

- **数据源层**：GitHub Releases / Discussions / RSS，统一抽象成结构化条目（id、url、时间、正文），只喂给 Agent 事实，不给原始 HTML。
- **Agent 层**：OpenClaw agent 负责摘要、拟标题、组稿。系统提示词明确约束：只允许引用工具返回的链接与数字。
- **工具层**：用 MCP 暴露三个工具——`fetch_sources`、`save_draft`、`publish_post`。发布工具使用单独的低权限 token，并支持 dry-run 参数。
- **调度层**：OpenClaw cron 触发，任务锁 + 幂等键（条目 id 的 hash）写入 SQLite，防止重跑。
- **门禁层**：草稿先进待审队列，我在聊天端回复确认才真正发布；稳定两周后，才对"周报"这类低风险内容放开自动发布。

## 踩坑点

- **模型幻觉**：约束 prompt 不如改流程。把"找链接"从生成阶段挪到工具阶段，幻觉直接归零。
- **时区**：cron 默认 UTC，周报晚发了 8 小时。调度层显式指定时区，日志里打印本地时间。
- **重复发帖**：除幂等键外，发布前再查一遍"最近 N 帖标题相似度"，双保险。
- **MCP 工具超时**：RSS 源偶发慢，默认 30s 超时导致整次任务失败。改成单源超时 + 部分失败降级，能抓几个算几个。
- **格式**：论坛 Markdown 对表格和嵌套列表支持一般，而模型酷爱写表格。提示词里限定排版白名单，另加一个后处理清洗函数。
- **权限**：最初图省事用了管理员 token，出过一次误删草稿。发布 token 现在只开"发帖 + 编辑自己"两个权限。

## 可复用建议

1. **发布动作做成独立 MCP 工具，强制 dry-run 通道**——任何 Agent 都不该裸调目标平台 API。
2. **状态一定落盘**：幂等、去重、审计全靠它，SQLite 足够。
3. **人在环上不是妥协**，是发布类自动化的默认配置：先审后发，再按风险分级逐步放开。
4. **给整条链路挂一个失败 webhook**，比事后翻日志省心得多。

## 总结

这个项目代码量不大，真正的成本在流程设计：数据从哪来、谁能发、发错了怎么办。Agent 负责写，系统负责兜底——工具拿事实、状态防重复、门禁控风险。把这三件事做扎实，发帖机器人就能从"玩具"变成可以长期跑的基础设施。欢迎评论区交流你们的审核门禁策略。
