## 背景

LLM 本身无状态。你在 OpenClaw 里搭的 Agent，每次调用都是一张白纸，context window 只是"临时草稿纸"，不是记忆。要让助手跨会话记住"我用 pnpm 不用 npm""部署脚本在 deploy/staging.sh"这类偏好，必须自己设计一层记忆。社区里不少同学第一步就上向量库，结果维护成本远超收益。这篇帖把我们踩过的路整理成一套可落地的最小方案。

## 问题：三个真实痛点

1. **记不住**：会话结束偏好就丢，每次重新交代一遍；
2. **记错**：一次性需求（"这次先走 mock 数据"）被当成永久偏好；
3. **记太多**：记忆无限膨胀，全量塞进 prompt，反而稀释指令、拉高成本。

## 做法：三层记忆 + 受控写入

**L0 会话工作记忆**：直接用上下文，不落盘。

**L1 结构化偏好库（核心）**：SQLite 一张表就够：

```json
{ "key": "package_manager", "value": "pnpm",
  "confidence": 0.9, "source": "explicit",
  "updated_at": "...", "history": [] }
```

**L2 情景记忆（可选）**：对话片段向量化，仅在偏好库命不中时兜底检索。

写入走两条通道：

- **显式捕获**：用户说"以后都……""默认用……"，直接写 L1，confidence 置 1.0；
- **隐式抽取**：会话结束时用小模型抽偏好候选，过阈值（如 ≥0.7）才入库，标记 `source=implicit`。

读取：会话开始注入 top-N 偏好（按 confidence × 近期命中加权），控制在 200 token 内；需要检索时用关键词 + 语义混合，别只靠向量。

更新：新记忆与旧 key 冲突时覆盖，旧值推进 `history` 可回滚；长期未命中的记忆自动降权。

工程上建议把这套东西封装成一个 MCP server，只暴露 `memory_get` / `memory_put` / `memory_search` 三个工具，任何 Agent 都能挂上复用。

## 踩坑点

- **全量注入是最大的坑**。记忆超过 30 条后指令遵循明显下降，坚持只注 top-N。
- **别用 JSON 文件存**。Agent 并发写几次文件就坏了，第一天上 SQLite。
- **隐式抽取误判率高**。"这次""先""暂时"这类临时性表述，抽取 prompt 里必须显式排除。
- **换 embedding 模型等于全库重算**。模型选型稳定之前，只用 L1 就好。
- **工具输出不要直接写记忆**，否则一条报错信息就可能污染偏好库。写入只允许来自用户消息或经过校验的抽取结果。
- **用户看不到记忆就不信任它**。务必提供 `/memory list` 和 `/memory forget <key>`，让记忆可查看、可删除。

## 可复用建议

- 写入前过三问：跨会话有用吗？长期有效吗？能一句话说清吗？三个都是才写。
- 优先做 L1 的 KV 偏好，能覆盖 80% 场景；向量库是锦上添花，不是地基。
- 记忆必须有 TTL / 降权机制，否则半年后全是陈旧偏好。
- 把记忆当产品功能而非技术细节：可查看、可删除、可导出。

## 总结

记忆系统的难点不在存储，而在**写入策略的克制**和**召回的精准**。先用一张 SQLite 表管理结构化偏好，配显式 + 隐式双通道写入和 top-N 注入，Agent 就能从"每次重新认识你"变成"越用越顺手"。向量库、遗忘曲线这些，等真遇到瓶颈再加不迟。欢迎回帖贴出你的记忆 schema，一起对齐。
