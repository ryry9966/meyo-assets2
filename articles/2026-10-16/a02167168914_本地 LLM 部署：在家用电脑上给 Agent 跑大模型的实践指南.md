## 背景

做 Agent 和 MCP 插件开发，最常接触的两类数据就是本地文件和自动化指令。全走云端 API 固然省事，但当工具链能读邮件、动文件、控家居时，“每一步都把上下文发给第三方”这件事总归让人不安。另外，Agent 循环里大量调用其实是小任务——分类、摘要、记忆整理——这些活一个本地小模型足够胜任，还能省下 token 费。

## 问题

家用硬件和 Agent 工作负载天然不匹配，主要卡在三点：

1. 显存/内存有限，跑不动原生权重的模型；
2. Agent 单次会话的系统提示 + 工具定义 + 多轮工具结果，上下文轻松超过 16k，KV cache 会把显存吃穿；
3. Agent 是串行多次调用，首 token 延迟和 tokens/s 直接决定体验，5 tok/s 的模型会让整个循环难以忍受。

## 做法

我的机器是 32GB 内存 + RTX 3060 12GB，跑 Qwen3-8B Q4_K_M 量化版，方案如下：

1. **后端选 llama.cpp 的 llama-server**（Ollama 也行），前提是暴露 OpenAI 兼容接口，方便与现有 Agent 配置对接；
2. **量化从 Q4_K_M 起步**。它是精度和体积的甜点位，显存富余再上 Q5/Q6，不建议低于 Q4；
3. **显式设上下文长度**。启动参数把上下文开到 32768，同时给 KV cache 开 q8_0 量化，8B 模型约占 10GB，12GB 卡刚好放下；
4. **只选支持原生工具调用的模型**。Qwen3、Llama 3.1+ 这类；接入前先 curl 一次 tools 接口，确认返回的 tool_calls 结构正确；
5. **分层路由**。高频小任务走本地，规划、写代码、复杂推理走云端。Agent 配置允许按任务类型指定 provider，本地模型当“常驻打杂工”。

## 踩坑点

- **上下文默认值坑**：不少运行时默认 4096 甚至 2048，Agent 跑到一半工具结果被截断，报错还很隐晦，务必显式指定；
- **函数调用格式不一致**：同一模型换后端，tool_calls 解析可能出问题，表现为 Agent 静默失败。先跑一个只含单个工具的最小回路验证；
- **keep_alive 问题**：Ollama 默认空闲几分钟就卸载模型，间隔性调用会反复冷启动，首 token 慢十几秒。把它设成 -1；
- **别信跑分**：跑分高的模型不一定乖乖按 schema 传参数。用自己的真实 MCP 工具跑十条真实任务记录成功率，比任何榜单都准。

## 可复用建议

- 从最小可用模型起步，先验证链路，再逐步加大；
- 统一走 OpenAI 兼容接口，后端随时可换，配置不用重写；
- 把自己的“硬件 + 模型 + 量化档 + 上下文参数”记录成一张卡，同配置的人少走弯路；
- 显存紧张时，优先砍上下文、开 KV 量化，而不是砍模型能力。

## 总结

本地部署不是替代云端，而是给 Agent 补一层可控、离线、零边际成本的执行底座。家用硬件跑 4B~14B 量化模型是现实可达的区间，把它用在正确的任务分层上，收益比追大模型实在得多。欢迎在评论区贴你的硬件和配置组合，攒一份社区实测表。
