## 背景

跑 Agent 的人大多遇到过这种场景：同一句话，在这台机器上它能找到 `ffmpeg` 顺利转码，换一台就 `command not found`；新开会话，它又忘了你的 Node 是 nvm 管的、Docker 要走代理。这些信息不在任何配置文件里，只存在于 shell 历史和上一次对话中。

OpenClaw workspace 里的 `tools.md` 就是为这个准备的：一份写给 agent 读的环境说明。它没有执行语义，也不是强制 schema，本质是“约定位置 + 约定格式的备忘”，agent 干活前查阅，用来对齐你的本地环境。

## 问题：环境知识没有落点

常见的三种落点都有毛病：

- 散落在聊天记录里，新会话即失忆；
- 塞进系统提示，跨机器、跨项目不可复用；
- 写成正式文档，面向人而非面向 agent，粒度不合适。

结果就是执行成功率随环境差异波动：macOS 和 Linux 路径不同、容器内外包管理器不同、MCP server 在某台机器上起不来。工具调用失败的根因，往往不是模型能力，而是它拿到的是一套默认假设。

## 做法

**1. 按“机器画像”组织结构。** 固定分区：环境概况（OS、shell、包管理器、代理）、工具清单（名称、绝对路径、版本、一句话用途）、路径约定（项目根、临时目录、产物命名）、禁做事项（不要 sudo、不要动某目录）、MCP/插件入口（哪些 server 已配置、启动方式、已知坑）。每条尽量一行一个事实。

**2. 公共与本地分离。** `tools.md` 只放机器特有内容；跨机器通用约定抽到 `tools.common.md`。同步到新机器只改差异段，避免整份复制带来的路径冲突。

**3. 模板进 git，本地覆盖不提交。** 公共文件和模板纳入版本控制，`.gitignore` 掉本地差异。环境变更有据可查，团队协作可评审。

**4. 让 agent 参与维护。** 在 AGENTS.md 里加一条约定：发现工具路径不存在、缺依赖、或实际行为与 tools.md 冲突时，先修正 tools.md 再继续。文档由此获得自愈能力，而不是靠人肉记得更新。

**5. 用脚本校验漂移。** 十几行脚本就够：解析 tools.md 里的路径声明，逐个检查存在性和可执行位，输出缺失项。开会话前跑一遍，比事后排查便宜得多。

## 踩坑点

- **别写 secrets。** tools.md 会进模型上下文，密钥只写“存在哪”（keychain、`.env`），不写值。
- **别假设自动加载。** 确认你的版本是否自动注入 tools.md；如果不会，在 AGENTS.md 里显式加一句“开工前先读 tools.md”。
- **别写成散文。** 长段落里抽取事实的可靠性明显下降，用列表、绝对路径、短句。
- **控制篇幅。** 它占上下文预算，只留高频事实，冷门细节单独放。

## 可复用建议

最小模板骨架：

```
# 环境
- macOS / zsh / Homebrew / 代理 127.0.0.1:7890
# 工具
- ffmpeg: /opt/homebrew/bin/ffmpeg，视频转码
# 约定
- 临时文件放 ./tmp，产物命名 yyyymmdd-*
# 禁止
- 不要 sudo，不要全局 pip install
```

模板 + git + 校验脚本，三件套可原样搬到任何 agent 项目。MCP 用户额外建议：把每个 server 的启动命令和上次失败原因记进去，排障时能省一半时间。

## 总结

tools.md 的价值不在“多一个文件”，而在于把环境知识从对话记忆搬进受版本控制的声明式资产：经过校验、可评审、可同步。agent 每次读到的不再是默认假设，而是一份与你机器一致的描述——这是跨环境稳定执行的地基。从给当前机器写第一份开始，剩下的让 agent 帮你越写越准。
