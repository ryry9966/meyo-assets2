## 背景

OpenClaw 的定时任务和工作流一旦跑得久，外部依赖几乎必然出问题：搜索 API 限流、上游模型 5xx、MCP 工具背后的第三方服务超时。演示时一切正常，无人值守跑半天的那种自动化，才真正考验工程。错误恢复不是"加个 try/catch"，核心是让 Agent 知道发生了什么、还能做什么、失败后从哪里继续。

## 问题：三种失败模式

1. **瞬时故障**：429 / 502 / 超时，重试大概率就好。
2. **持续故障**：欠费、key 失效、接口改版，重试只是浪费。
3. **静默失败**：HTTP 200 但返回错误页或空数据，Agent 拿着垃圾数据继续往下跑——最危险的一种。

## 做法：按优先级五条

**1. 错误分类前置到工具层。** 不要让 LLM 面对原始报错去猜。工具返回结构化错误：

```json
{"ok": false, "error": "upstream_timeout", "retryable": true, "fallback": "cache"}
```

**2. 重试在代码层做，别让模型做。** 指数退避 + 随机抖动，上限 3 次。让 Agent 循环里"决定要不要重试"既贵又不稳定。

**3. 准备降级路径。** 主 API 挂了切备用 provider 或本地缓存；都没有就返回"降级结果 + 明确说明"，并在结果里打标，禁止把降级结果当正常结果输出。

**4. 断路器。** 同一工具连续失败 3~5 次直接熔断，本轮任务跳过该步骤走降级，下个调度周期再半开探测。避免每轮都去撞同一堵墙。

**5. 状态落盘。** 多步任务每步完成后写 checkpoint（含步骤索引和产出），恢复时从断点续跑，而不是重头再来重复扣费。

## 踩坑点

- **无限重试**：退避没上限，叠加限流雪上加霜，恢复机会和 token 一起烧光。
- **超时设太长**：单调用 120s 超时会让整个调度串行卡死，外部 API 建议卡在 15~30s。
- **只校验状态码**：200 里也可能是 `{"error": ...}` 或空结果，响应内容必须校验。
- **checkpoint 缺进度**：只存数据不存步骤号，恢复后重复执行已成功的步骤——写操作场景尤其致命。
- **失败静默吞掉**：最终失败一定要走通知通道，沉默的失败等于没做恢复。

## 可复用建议

- 封装统一的 `safe_call` 工具包装器，重试、降级、断路器全部配置化，所有插件共用一套，不要每个技能各写一遍。
- 维护一张错误分类常量表，新接 API 先归类再上线。
- 定期演练：故意把 key 改错、把限流阈值调低，验证降级路径和通知真的能触发——没演练过的降级等于不存在。

## 总结

Agent 长期可靠运行的地基不是模型多强，而是失败时行为是否可预期。三句话：**错误要分类，重试在代码层做；失败要可见，降级要打标；恢复从断点，不是从零。** 先把这三条做进工具层，再谈更复杂的自愈逻辑。
