## 背景

大多数 agent 默认是被动式的：用户发消息 → 模型响应 → 返回结果。这个模式在问答场景没问题，但在"助理"场景下效率偏低——真正有用的助理应该在你开口之前就发现事情。OpenClaw 这类本地常驻的 agent 框架天然具备做 proactive 的条件：常驻进程、定时任务、消息通道、工具调用都现成，缺的只是把「触发 → 判断 → 执行 → 汇报」这条链路自己搭起来。

## 问题

把 agent 变主动，难点不在"能不能跑"，而在三个边界：

1. **什么时候触发**：事件源怎么选，避免噪音；
2. **要不要打扰用户**：不是每件事都值得弹消息；
3. **主动执行时权限给多大**：没人看着的时候，它能动什么。

这三个问题处理不好，产物就是一台半夜给你发消息、每次都喊"发现重要事项"的噪音机器。

## 做法：三层拆分

我用三段式结构改造了自己的实例：

**第一层：触发。** 三类事件源覆盖 90% 场景：

- 定时：cron / heartbeat，比如每早拉日历和天气生成当日摘要；
- 事件：webhook 接入 CI 失败、监控告警；
- 状态：低频轮询（目录新文件、RSS 更新）。

触发层只负责"叫醒"，不做判断。

```yaml
proactive:
  triggers:
    - { type: cron, schedule: "0 8 * * *", task: daily-brief }
    - { type: webhook, path: /ci-failure, debounce: 5m }
  quiet_hours: "23:00-07:30"
  budget: { actions_per_day: 20 }
```

**第二层：判断。** 事件先过规则过滤器（静默时段、优先级标签、去抖窗口），再让便宜模型做二分类："是否值得打断用户"，判断理由写日志。不值得的进 digest 队列，每天固定时间汇总一条。

**第三层：执行。** 主动任务用独立会话 + 最小权限工具集。只读操作（查询、汇总）直接执行；写操作（发消息、改文件、调外部 API）降级为"提议"——agent 把建议和待执行命令发给你，确认后才落地。

## 踩坑点

- **触发风暴**：一个 webhook 重试 17 次，agent 连发 17 条消息。加幂等键 + 5 分钟去抖窗口解决。
- **模型没有"成本感"**：默认提示词下它觉得一切都紧急。后来强制要求引用具体证据（哪条日志、哪个字段）才能判为紧急，误报明显下降。
- **权限蔓延**：主动会话图省事复用了主会话凭证，等于给了全量工具。务必隔离。
- **时区与补跑**：机器休眠恢复后 heartbeat 连补三次执行，任务重复跑。调度侧加"跳过过期窗口"。

## 可复用建议

- 先做"提议-确认"，再逐步放开"自动执行"，权限是一点点挣来的；
- 低优先级一律走每日 digest，别相信"多通知没关系"；
- 每次主动行为记结构化日志（触发源、判断理由、动作、结果），跑一周回看日志再调阈值；
- 判断层用便宜模型，执行层才上主力模型，成本能降一个量级。

## 总结

Proactive 不是让 agent 更"聪明"，而是把工程重心从对话质量移到触发设计和边界控制上：触发层管"何时醒"，判断层管"该不该说"，执行层管"能做什么"。三层各自可配置、可回滚，主动式助手才能从 demo 变成日常真敢开着的东西。建议从一个只读的每日摘要场景起步，跑两周日志再逐步放权。
