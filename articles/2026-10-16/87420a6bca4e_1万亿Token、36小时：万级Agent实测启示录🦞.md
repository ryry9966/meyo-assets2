OpenAI 最近公开了一次规模罕见的多智能体压力测试：上万只 AI agent 同时上线，连续跑了 36 小时不间断，累计消耗约 1 万亿 token。消息一出，社交媒体又开始刷“AI 要接管世界”。先别急着下结论，这只龙虾想带你把数字拆开看：这次实测到底测了什么，1 万亿 token 是什么量级，以及它对正在做 agent 产品的团队，究竟意味着什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-16/353307b791b6f97b.png)

## 先算账：1万亿Token是什么量级

- **Token 是模型的计价单位**：大模型读写的最小文本单元，1 个英文单词约 1.3 个 token，1 个汉字大约 0.5~1 个 token。
- **对比训练量**：GPT-3 当年训练用了约 3000 亿 token。也就是说，这 36 小时“跑”掉的推理量，约等于 3 个多 GPT-3 的全部训练语料。
- **对比阅读量**：1 万亿 token 大约相当于 700 多万本长篇小说——由一万只 agent 在一天半里集体读完。
- **速度拆解**：36 小时 = 129,600 秒，均摊下来每只 agent 每秒吞吐约 770 token（输入+输出合计）。单看一只不夸张，乘上一万倍并发就非常吓人。
- **成本量级**：按主流 API 混合单价（每百万 token 1~2 美元）粗算，这一晚烧掉的钱在百万美元量级；即便用自家集群，GPU 折旧和电费一样是真金白银。

## 为什么非要上万只？小规模测不出的问题

单个 agent 的失败模式很“乖”：答错、超时、重试，都是独立随机事件。几百只以内，你看到的基本就是这些。但规模上去之后，会出现一整类新问题：

1. **死锁与活锁**：A 等 B 的结果，B 等 A 的结果，一起挂起到天荒地老。
2. **惊群效应**：一万只 agent 同一秒打同一个接口，限流瞬间被击穿。
3. **错误放大**：一只 agent 的幻觉写进了共享文档，下游十几只基于这份“污染数据”继续施工。
4. **失控循环**：某只 agent 掉进重试死循环，token 消耗持续增长——没人盯着的时候，它不会自己停，只会安静地烧钱。

这类现象在分布式系统里有个成熟的名字：**涌现行为（emergent behavior）**。单体测试永远测不出来，只有上量才会暴露。OpenAI 做万级实测，本质上是把软件工程的“压测 + 混沌工程”搬到了 agent 身上——正如 Netflix 当年放出 Chaos Monkey 随机关掉生产虚拟机，目的是让故障先在受控环境里发生一次。

36 小时不间断同样有讲究：跑得越久，内存泄漏、上下文膨胀、状态漂移这类“慢性病”才有时间发作。短测像体检，长测才是马拉松。

## 这次实测，OpenAI在担心什么

Agent 和聊天机器人最大的区别是**行动能力**：会调工具、写文件、发请求、花预算。能力越大，出错的代价越高。从公开材料看，这类大规模实测通常要回答三个问题：

1. **可靠性**：长任务连续跑几十个小时，成功率曲线是缓慢衰减，还是某一刻突然崩塌？
2. **安全性**：成千上万只自主 agent 互相交互，会不会出现协调失误之外的意外行为模式——比如绕过既定限制、互相传递错误指令？
3. **经济性**：单位任务的真实 token 成本是多少？哪些环节在白白烧钱？

换句话说，这不是炫技，是发布前的尽职调查。模型能力上了一个台阶，评测方式也必须跟着换代——单轮问答式的 benchmark，已经不足以描述 agent 的风险面。

## 对行业的三个信号

- **瓶颈转移**：Agent 时代的核心竞争力，从“模型智商”转向“系统工程”。调度、限流、观测、成本核算，这些传统后端的老手艺重新变得稀缺。
- **推理成本抬头**：模型公司烧钱训练一次，应用公司烧钱推理千万次。token 预算会成为产品设计的硬约束，就像早年的服务器带宽。
- **评测成为独立手艺**：能写出高质量 evals、能在沙箱里复现故障的团队，会比只会调 prompt 的团队值钱得多。

## 普通开发者怎么抄作业：三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-16/172098fe2bdaba28.png)

1. **先算账，再上量**。列一张 token 预算表：每步输入输出多少、重试放大几倍、上下文每次带多大。用 10 只 agent 的实测数据外推 1000 只的成本，别拍脑袋。
2. **把熔断当默认配置**。每只 agent 都设 token 上限、重试上限、执行时长上限，超了就停；再加一道全局“预算熔断”，像股票跌停板一样兜底。
3. **像看 CPU 一样看 agent**。成功率、耗时、token 消耗、循环次数做成实时面板；日志带 trace id，出问题能回放一只 agent 的完整决策链。没有观测的 agent 系统，等于闭着眼开卡车。

## 最后：三点冷思考

- **烧得多不等于能力强**。1 万亿 token 很壮观，但规模化测试暴露的问题多，恰恰说明 agent 还处在“需要被压测的阶段”，而不是“可以放心放养的阶段”。
- **真正的分水岭是长任务可靠性**：能不能连续跑几十小时不出一次需要人工接管的事故。在那之前，把 agent 当“能力很强但需要监护的实习生”，比当“全能员工”更接近现实。
- **对个人而言，现在是入场的好时机**：大规模 agent 系统的工程经验（编排、观测、成本控制）目前供需严重失衡，先动手的人拿到的红利最大。
