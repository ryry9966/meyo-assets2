## 背景

做 Agent 自动化的人迟早会撞上同一个问题：助手怎么知道“该干活了”。定时跑一轮任务是一回事，但更多场景是外部状态变了——CI 挂了、消息到了、文件更新了——你希望 agent 在合适的时机被唤醒，而不是靠人手动戳一下。这就是心跳（heartbeat）问题：谁来触发、多久触发一次、每次触发花多少钱。

## 问题：两种方案都不完美

**轮询**（cron / 固定间隔）：简单、可控、天然兜底。但空转成本高，如果每轮探测都落到模型层，token 消耗随频率线性上涨；间隔拉长又牺牲时效。

**推送**（webhook / WebSocket / SSE / MCP notification）：时效好，理论上零空转。但它是“最好情况”的设计——连接会断、回调会丢、对端挂了也不会通知你。推送失效又没有兜底时，agent 会安静地失联，比轮询浪费更危险。

## 我的做法：推送优先，轮询兜底，模型后置

核心原则三条：

1. **心跳探测放脚本层，不进模型层。** 用几十行的 shell/Python 定时任务（或 OpenClaw 的 cron 触发器）做检查：拉状态、算指纹、和上次比对。大部分轮次什么都没变，直接退出，成本为零。
2. **有意义的变更才唤醒 agent。** 给每个监控对象定义状态指纹（内容 hash、etag、时间戳+大小），指纹没变不触发；变了才组装上下文去调模型或发通知。
3. **推送是加速器，不是依赖。** 能接 webhook 的服务（告警、代码仓库、IM 机器人）尽量接；但低频轮询始终保留，可以放到 15–30 分钟一次，作用是校准推送通道是否还活着。

落地步骤：

- 列出 agent 需要感知的状态清单，区分“秒级必须响应”和“分钟级可接受”
- 秒级走推送 + 本地去重队列；分钟级走指纹轮询
- 心跳结果落盘（last_seen、上次指纹、最近错误），下次会话直接恢复上下文
- 设置 `max_silent` 阈值：连续 N 个周期无心跳记录，按故障处理并告警

## 踩坑点

- **心跳本身触发 LLM 调用。** 最早我把检查逻辑写进 agent 的定时指令，每 5 分钟烧一次 token，一天下来什么都没干光花预算。挪到脚本层后才正常。
- **推送的静默失败。** webhook 服务端重启后没恢复注册，agent 停更了 6 小时没人发现——这就是 max_silent 阈值存在的意义。
- **重试风暴。** 对端 5xx 时脚本无退避地猛试，把小故障放大。加指数退避 + 随机抖动即可。
- **去重缺失。** 推送和轮询同时命中同一变更，agent 被唤醒两次。按事件 ID 或指纹做幂等。

## 可复用建议

- 先问时效需求再选机制：多数自动化场景“分钟级”就够，别为秒级支付推送架构的复杂度
- 心跳日志独立保存，排障时先看心跳记录，再看会话记录
- 轮询间隔宁长勿短——有指纹检测在，间隔对成本几乎无影响，对稳定性反而是加分

## 总结

轮询和推送不是二选一，而是分工：**轮询负责不失联，推送负责低延迟，指纹负责不空转，模型只负责处理变化。** 把这四件事拆开，心跳机制就从成本黑洞变成了可靠的脉搏。如果你的 agent 目前只靠单一定时器或单一 webhook 活着，建议按上面的清单补齐另外两条腿。
