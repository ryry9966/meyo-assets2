## 背景

做 Agent 和 MCP 工具链这一年，我逐渐发现不少场景其实不需要云端大模型：本地文档问答、日志脱敏后的意图分类、自动化流程里的路由判断。这些任务对模型能力要求不高，但对隐私和成本敏感。于是我把实验环境整体搬到了本地，跑了几个月，把过程沉淀成这篇帖子。

## 问题

本地部署的第一道坎不是技术，是预期管理：家用硬件跑不了最强模型，要接受"够用"而不是"惊艳"。剩下的三个实际问题：

1. 模型和量化版本怎么选；
2. 显存/内存怎么算；
3. 小模型的工具调用（function calling）是否可靠——这直接决定它能不能接进 Agent 流程。

## 做法

**硬件盘点。** 16GB 显存的显卡可舒服跑 14B Q4；8GB 显存建议 7B-8B Q4；纯 CPU 或 Mac 统一内存看内存大小，32GB 可到 14B 左右。经验公式：Q4_K_M 量化大约每 1B 参数占 0.6GB，再预留 2-4GB 给 KV cache 和运行时。

**选运行时。** Ollama 上手最快，自带 OpenAI 兼容接口；llama.cpp 更可控，适合调参和量化实验；要吞吐上 vLLM，但对消费级显卡不算友好。建议先用 Ollama 跑通，再按需迁移。

**选模型。** 给 Agent 用的模型，重点测三件事：结构化输出稳定性、工具调用格式正确率、中文指令遵循。社区榜单分数和你的实际负载经常对不上。

**接进工作流。** Ollama 默认在 11434 端口提供 OpenAI 兼容 API，把 base_url 指过去，Agent 框架基本无缝。MCP 侧不受影响——MCP server 本来就和模型解耦，变的只是推理后端。

## 踩坑点

1. **上下文是显存黑洞。** 声明 128K 的模型，把 num_ctx 拉满后 KV cache 可能吃掉十几个 GB。按需设置，多数 Agent 任务 8K-16K 够了。
2. **量化等级别贪。** Q4 以下工具调用错误率明显上升，JSON 输出容易截断。宁可小一号模型用 Q4，不要大模型硬压 Q2。
3. **并发是串行的。** 消费级显卡同时来两个请求会排队，前端看起来像"卡死"。加 loading 状态或限制并发。
4. **别迷信默认参数。** 不同模型对 temperature、stop token 敏感度差异很大，接入前单独压测一轮。

## 可复用建议

- 写一个模型切换脚本，统一管理别名和启动参数，避免每次手敲；
- Embedding 单独跑一个小模型，与生成模型解耦，互不抢资源；
- 记录 tokens/sec 和显存占用，形成自己硬件的基线表，下次选型直接查。

## 总结

本地部署的价值不在替代云端，而在给 Agent 和自动化流程提供一个便宜、私有、离线的兜底层。"最小够用的模型 + 合理量化 + OpenAI 兼容接口"这套组合，一个周末就能搭好。剩下的时间花在测试你自己的真实负载上——这才是判断模型好不好的唯一标准。
