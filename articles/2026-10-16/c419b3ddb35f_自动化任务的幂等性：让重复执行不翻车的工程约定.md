## 背景

跑过一段时间 OpenClaw 自动化的人多半遇到过：定时任务重复触发、同一条消息被发两遍、Agent 调 MCP 工具超时后重试、插件断线重连后把队列里的指令又执行了一次。触发层几乎做不到"只投递一次"，实践中默认都是 at-least-once——至少一次，可能多次。

所以重复执行不是异常，而是常态。幂等性（Idempotency）就是应对它的工程约定：同一个操作执行一次和执行 N 次，最终状态一致。

## 问题

副作用型任务最怕重复。典型翻车现场：

- `create_issue` 跑了两遍，出现两张一样的工单；
- 定时摘要重试后，群里收到两条几乎相同的消息；
- 同步插件断点重连后，把同一段数据 append 了两次。

这类问题单次测试测不出来，只有重试真的发生时才爆。而 LLM Agent 恰恰放大了重试概率：模型可能自行判断"上一步好像失败了"就重发指令，参数还会微妙地变化。

## 做法

按优先级三步：

**1. 固定幂等键。** 在调度时就生成确定性 key，比如 `hash(task_id + 目标对象 + 业务日期)`，随指令一路透传到工具层。执行器先查执行记录，命中就直接跳过并记日志。key 必须在调度层生成，不能让模型重试时重新生成。

**2. 优先用 upsert 类操作。** 工具接口设计成"确保状态"而不是"追加一次"：`ensure_file` 优于 `append_file`，`sync_record` 优于 `insert_record`。写文件用临时文件加原子 rename，天然幂等。

**3. 把键下推到外部 API。** 幂等只在本地生效是不够的，外部系统照样会重复扣款、重复建单。对接的服务只要支持 Idempotency-Key 之类的头，一定透传。

MCP 工具定义里建议统一加一个可选的 `idempotency_key` 参数，让幂等成为插件协议的一部分，而不是每个工具各自发明。

## 踩坑点

- **key 里掺时间戳或随机数**：每次重试 key 都不同，等于没做。key 必须来自业务语义。
- **去重状态只存内存**：进程一重启记录就没了，重试照样穿透，至少落一个本地 journal 文件。
- **先查再写的竞态**：两个并发任务同时查到"不存在"，然后都创建。查和写必须原子，或靠 key 在下游做唯一约束兜底。
- **半失败后的重试语义没想清楚**：有的 API 会把 key 关联的错误响应缓存下来，重试拿到的还是上次的错。要么换 key，要么先显式取消上次操作。
- **模型重试时改写入参**：key 固定了，但参数一变语义就变了，入参也要在调度层固定下来。

## 可复用建议

- 心态上：定时、webhook 触发的任务，一律按"会被执行两次"来设计。
- 协议上：统一幂等键的生成规则和透传链路，写进插件开发规范。
- 观测上：记录 key 和结果（执行/跳过/重复命中），排查时一眼看出重试发生在哪层。
- 测试上：把"同一任务连跑两遍、断言无重复副作用"加进 staging 常规验收。

## 总结

幂等性不是锦上添花，而是让重试变安全的契约。调度层兜不住"只投递一次"，就让执行层做到"执行多次也没事"。在 Agent 这种模型可能自发重试、链路层层重连的系统里，这条契约就是自动化的安全带——系上它，才敢把任务真正交给无人值守。
