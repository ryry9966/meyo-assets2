# 背景

社区里跑 OpenClaw 的典型形态是：一个常驻 gateway 接着几个 IM 渠道，agent 循环里挂着搜索、文件、HTTP 等工具。多数人起步只配一个模型——要么全走云端旗舰，要么全走本地。前者的账单和隐私边界撑不久，后者在多轮工具调用里崩得很快。多模型路由要解决的就是分配问题：哪类请求值得花云端的 token，哪类请求本地小模型就够了。

# 问题

两条极端路线各有明确症状：

- **全 GPT**：频道摘要、日常闲聊这类低价值任务也在烧旗舰模型，月成本高出预期一个量级；内网数据顺手就发给了云 API。
- **全本地**：7B 级模型规划能力不足，工具调用参数漏字段、格式崩，agent 循环反复重试，最后人工接管——省下的 API 费全变成了时间成本。

# 做法

我们分流的第一判据只有一条：**这一步要不要碰工具**。要，走强模型；不要，走本地。

1. 主 agent（负责规划、工具调用）固定用云端强模型，这是 agent 循环稳定性的底线。
2. 拆出独立的轻量子 agent 处理确定性任务：消息摘要、网页正文转 Markdown、会话分类打标，全部路由到本地 7B~14B 模型（Qwen 系列实测可用）。
3. 在 gateway 配置里按 agent 指定模型，而不是全局默认。示意：

```json
{
  "agents": {
    "defaults": { "model": "openai/gpt-4.1" },
    "digest":   { "model": "ollama/qwen2.5:7b" }
  }
}
```

4. 云端调用配 fallback 链（主模型超限或超时自动降级），本地调用配短超时加失败上抛——宁可报错，别让小模型硬答。
5. 隐私敏感会话（内网地址、客户数据）在 skill 层直接禁用云端工具，而不是靠路由"尽量"绕开。

# 踩坑点

- **function calling 兼容性参差**：同为 7B，有的模型输出能直接解析，有的得加一层 JSON 修复。修复代码的维护成本常常超过省下的 API 费，换模型前先跑一轮工具调用压测。
- **上下文长度**：本地 8k 上下文模型接一个长会话，历史被直接截断，表现为"模型突然失忆"，排查半天其实是 token 上限。
- **冷启动**：Ollama 首次加载模型要几十秒。摘要子 agent 如果低频触发，每次都撞冷启动，体感比云端还慢。用 keep_alive 或定时预热解决。
- **隐私判断别只看模型**：本地模型 + 云端搜索工具，数据照样出网。路由策略必须覆盖工具层。
- **同机部署**：GPU 被 gateway 占满后，人还要在同一台机器上干活，记得设并发上限。

# 可复用建议

- 先写一张两列表格（任务 → 模型 + 理由），评审后再落配置，避免路由规则散落各处没人认账。
- 每月翻一次会话日志，统计"本地任务被兜底到云端"的比例；比例升高说明该升级本地模型了。
- 路由粒度做到 agent 级就够，不要上请求级动态路由，收益配不上复杂度。

# 总结

多模型路由不是省钱技巧，而是给不同任务匹配合适的可靠性等级：碰工具的给强模型，确定性的给本地，隐私边界画在工具层而不是模型层。先用最粗的两级分流跑起来，再按日志数据微调，比一开始设计精巧的调度器务实得多。
