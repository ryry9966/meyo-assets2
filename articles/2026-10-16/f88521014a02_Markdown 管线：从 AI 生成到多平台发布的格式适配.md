## 背景

最近在搭一个自动化内容工作流：让 Agent 每周产出技术周报，再分发到 Hugo 博客、掘金和微信公众号。跑起来才发现，「生成一篇 Markdown」只占 20% 的工作量，剩下 80% 全在格式适配——这就是本帖的主题。

## 问题

多平台发布看起来只是复制粘贴，实际至少有四类冲突：

1. **方言差异**：GitHub 支持 footnotes 和 task list，掘金对 HTML 标签有白名单，公众号干脆不吃 Markdown，只收受限 HTML。
2. **图片链路**：本地相对路径、图床外链、平台转存是三套逻辑。公众号不支持外链图，必须重新上传。
3. **元数据**：静态站要 frontmatter，公众号要标题摘要，掘金要标签。而 AI 生成的正文里常常还塞了一个 H1，和平台标题字段重复。
4. **LLM 输出不稳**：标题层级跳跃、中英文标点混用、代码块缺语言标注，偶尔还有幻觉链接。

## 做法

方案是把管线拆成四段，核心思路：**用 AST 做中间表示，适配器只写纯函数变换**。

**第一步：约束生成。** 在 Agent 的输出契约里写死规范：CommonMark + GFM 子集、正文不带 H1、代码块必须标语言、链接必须是真实域名。生成后先过一道 markdownlint 风格的 lint 门禁，不过就打回重写。

**第二步：归一化。** 用 remark（unified 生态）解析成 mdast，做确定性清洗：标题层级压平、标点统一、去重复标题、补 fence 语言。所有操作基于 AST 节点判断，不要在原始字符串上跑正则。

**第三步：平台适配器。** 每个目标平台一个 transformer：

- Hugo：注入并校验 frontmatter，图片路径转相对路径；
- 掘金：task list 降级为普通列表，footnote 改文内引用；
- 公众号：mdast → HTML → 样式内联，图片走转存队列。

**第四步：发布与预览。** 发布动作封装成 MCP tool / 插件，强制支持 dry-run 模式，输出各平台渲染后的 diff 预览，人工确认才真正提交。

## 踩坑点

- **正则改 Markdown 必翻车**：嵌套代码块里的 `#` 会被误当标题处理。切到 mdast 之后这类 bug 清零。
- **图片转存要幂等**：按内容 hash 建缓存，否则重跑管线会往图床塞一堆重复文件。
- **frontmatter 泄漏**：部分平台会把 YAML 原样渲染出来，适配器的第一步永远是剥元数据。
- **别用通用转换器转公众号 HTML**：默认样式太重，内联后还得主动清理不支持的属性，否则排版会飘。

## 可复用建议

1. 把 mdast 当作管线唯一契约，适配器写成纯函数，方便单测；
2. lint 门禁放在管线最前面，AI 输出的稳定性问题在源头解决成本最低；
3. 每个平台维护一份「能力清单」，适配器按清单做语法降级，而不是硬编码特判；
4. 一定保留 dry-run + diff 预览：发布失败可以重试，发布错了很难撤回。

## 总结

管线跑通后，新增一个发布平台只需写一个 transformer，半天工作量。真正值得投入的不是「一键发布」的噱头，而是中间那层稳定的 AST 表示和生成阶段的输出契约。格式适配本质上是工程问题，不是提示词问题。
