## 背景

Agent 上生产后最常见的故障不是逻辑写错，而是依赖出问题：LLM API 突发 429、搜索类 MCP 超时、第三方插件的配额半夜悄悄耗尽。交互式对话里挂了可以让人点一下重试，但定时任务、长流程、批处理这类自动化场景没人守着。错误恢复能力做得好不好，直接决定一个 Agent 是 demo 还是可以托管的生产件。

## 问题：Agent 挂掉的三种典型姿势

观察社区里跑挂的任务，基本逃不出三类：

1. **无限重试**。工具调用失败后，模型自己决定“再试一次”，没有上限，token 和时间一起烧光。
2. **错误被当成数据**。堆栈、HTML 错误页被原样喂回模型，模型一本正经地解读乱码，输出看似合理的错误结论。
3. **单点崩盘**。一个可选 API 挂了，整条工作流直接中断，跑到 80% 的成果全部作废。

根因是同一个：把错误处理的决策交给了 LLM，而 LLM 是最差的执行者——贵、不确定、容易被污染的上下文带偏。

## 做法：处理下沉，决策上收

核心原则一句话：**机械的重试逻辑下沉到工具层，“接下来怎么办”的判断留给模型。**

**1. 先给错误分类**
- 瞬态错误：超时、429、502/503，值得重试；
- 永久错误：401/403、404、400，重试无意义，立即失败；
- 未知错误：按瞬态处理，但设硬上限。

**2. 重试放在工具包装层，不放进 Agent 循环**

```
callExternal(tool, args):
  for attempt in 1..3:
    try: return await tool.call(args, timeout=10s)
    catch TransientError:
      sleep(backoff * 2^attempt + jitter)
  return { ok: false, error_type: "unavailable", retryable: true }
```

指数退避加抖动，别让所有任务同一秒齐射。

**3. 给模型的是结构化错误，不是堆栈**

至少三个字段：`error_type`（能否重试）、`hint`（如“30 秒后重试”）、`partial_data`（已拿到的部分结果）。模型据此选择换工具、跳过该步，或向上汇报失败，而不是对着 traceback 自由发挥。

**4. 提前设计 Fallback**
- **多供应商**：关键能力备一个替代 API，主路挂了自动切；
- **缓存快照**：实时数据拿不到就用最近一份，并明确标注时效；
- **降级模式**：可选项直接跳过，保主路径完成。

**5. 断点续跑 + 预算控制**

长任务每步落盘状态，失败后从断点继续，而不是从头再跑。同时设全局预算：总重试时长、token 上限，超了就停下并报警，而不是默默烧到天亮。

## 踩坑点

- **对非幂等操作重试**。下单、支付这类 POST 重试三次可能产生三个真实订单。非幂等调用必须带幂等键，否则宁可不重试。
- **把“超时”等同于“没发生”**。请求可能已在对方侧执行成功，直接当失败重跑会造成重复副作用。正确姿势是先查询确认状态，再决定补偿还是重发。
- **混淆“空结果”和“错误”**。搜索返回零条和搜索 API 挂了是两回事，混在一起模型会得出错误结论。
- **在 prompt 里写“最多重试 3 次”指望模型自觉**。模型的计数能力不可靠，上限必须由代码强制执行。

## 可复用建议

1. 所有外部调用收敛到统一的工具客户端，timeout / 重试 / 错误分类三件套强制启用；
2. 自建 MCP 工具和插件约定统一的错误返回结构，带 `retryable` 字段；
3. 对连续失败超阈值的依赖做熔断：标记后自动跳过 N 分钟，避免雪崩式重试；
4. 失败报警永远推给人，不要让 Agent 自己决定“要不要上报”。

## 总结

Agent 的可靠性不取决于模型多聪明，而取决于工程层有没有接住失败。记住一句话：**重试交给代码，判断留给模型，且只给模型结构化的、可用于决策的信息。**上线前把错误分类、fallback、断点续跑这三层补齐，能避开绝大多数“半夜起来重跑任务”的时刻。
