## 背景

OpenClaw 这类自托管 Agent 的工作区里有几个固定角色：`AGENTS.md` 管行为规则，`SOUL.md` 管人格语气，`MEMORY.md` 管长期记忆。但决定“这个 Agent 到底在为谁工作”的 `USER.md`，很多人要么空着，要么塞满无效信息。我持续用了两个月，聊聊它值不值得写、怎么写。

## 问题

没有 USER.md 时的典型摩擦：

- 每开一个新会话，都要重新交代一遍技术栈、部署方式、命名习惯；
- Agent 按“通用开发者”猜你：你用 Arch 它给 apt 命令，你写 Go 它回 Python 脚本；
- 多设备、多入口场景下表现不一致，因为哪个入口的它都不了解你。

这些不是模型能力问题，是上下文缺失。能力问题靠升级解决，上下文问题只能靠你自己补。

## 做法

`USER.md` 放 workspace 根目录，Agent 启动时自动读取。我的结构是五段：

1. **身份与角色**：一句话，如“后端工程师，主要维护 X 项目”；
2. **环境**：操作系统、shell、语言版本、部署方式（“Ubuntu 22.04，zsh，Go 1.23，systemd 部署”）；
3. **偏好**：回复语言、代码风格、解释深度（“默认中文，示例直接给完整可运行版”）；
4. **边界**：不希望它做的事（“不要主动重构我没要求的代码”）；
5. **变更记录**：两三行，标注最近更新日期。

写法上有个关键区别：**写事实，不写愿望**。“我习惯 MIT 协议”是事实；“请始终遵守最佳实践”是废话——规则归 `AGENTS.md` 管，别在这里重复。

## 踩坑点

- **写太长**。USER.md 每次会话都占上下文。我第一版写了 40 行，砍到 15 行后效果反而更好，Agent 抓得住重点。
- **混入敏感信息**。API key、内网 IP、家庭地址不要写。这个文件会被 Agent 引用、复述，还可能进备份同步。
- **和 SOUL.md 抢戏**。SOUL.md 定义“Agent 是谁”，USER.md 定义“用户是谁”，混着写会导致人格漂移。
- **写完不更新**。过期信息比没有更糟——它会自信地引用你半年前的 Go 版本。

## 可复用建议

- **冷启动**：让 Agent 读你现有仓库后自己起草 USER.md，你只做删改，比从零写快得多，而且它总结你的视角经常有意外发现；
- **分层**：稳定事实（环境、身份）和易变偏好（当前项目、临时约定）分开，后者每月 review 一次；
- **多用户共用一个 Agent**：USER.md 只放共性，个人差异走各自的 session 上下文；
- **审查心态**：默认这份文件会被 Agent 记住并外发引用，写之前先过一遍“这条能被别人看到吗”。

## 总结

USER.md 本质上是一次低成本、高杠杆的上下文注入：十几行文本，换来 Agent 从“每次都要重新认识的工具”变成“知道你在哪台机器上、用什么语言、讨厌什么回复风格的合作者”。它不提升模型能力，但消除了大量重复沟通。建议从环境段开始写，两周迭代一次，控制在一屏以内。

文件在 workspace 里，改起来零成本——这正是它比任何配置面板都值得先写的原因。
