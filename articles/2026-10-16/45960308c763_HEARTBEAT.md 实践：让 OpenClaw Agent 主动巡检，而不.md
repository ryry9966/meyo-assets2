## 背景

大多数 Agent 的交互模型是“你问它答”：不提问，它就永远静止。OpenClaw 提供了一个改变这个模型的机制——心跳（heartbeat）。运行时按固定间隔（默认 30 分钟）向 agent 会话注入一次提示词，agent 据此读取工作区根目录下的 `HEARTBEAT.md`，逐条检查是否有该做的事；如果没有，回复 `NO_REPLY`，这条消息会被吞掉，你完全无感。本质上，它是把 agent 从应答终端变成一个后台巡检进程，而 `HEARTBEAT.md` 就是巡检手册。

## 问题

常见的错误尝试有三种。一是把“请主动一点”写进系统提示词——agent 在两次对话之间根本没有运行机会，纯属自我安慰。二是在 `HEARTBEAT.md` 里写“每天下午三点提醒我开会”——心跳不是定时器，agent 对“三点”没有可靠感知，那是 cron 的职责。三是指望 agent “自己记得”检查什么——没有这份文件，每次心跳注入的提示词就是唯一的契约，不写就不会发生。

## 做法

第一步，在工作区（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`，每条任务写清三个字段：触发条件、动作、通知策略。例如：

```markdown
# Heartbeat checklist（逐条检查，未触发则保持沉默）
- 每次心跳：git -C ~/projects fetch && git status；
  若有未 push 的提交超过 48 小时，发一句话提醒，附仓库与分支名。
- 每次心跳：读取磁盘监控 MCP 的最新数据；仅当挂载点 >85% 时告警并附路径。
- 每次心跳：检查网关进程是否存活；异常则通知，正常则不回复。
```

第二步，在 `openclaw.json` 里调间隔（以实际版本字段为准）：`agents.defaults.heartbeat.every: "45m"`。注意每次心跳就是一次真实的模型调用，间隔是成本开关。

第三步，验证。不要凭感觉认为“它在跑”：查会话日志确认心跳确实触发、agent 是否回复了 `NO_REPLY`，必要时手动发一次心跳提示词做冒烟测试。

## 踩坑点

- **噪音**：把任务写成“每次汇报状态”会导致刷屏。所有条目都应是异常驱动的——没事就闭嘴。
- **Token 成本**：`HEARTBEAT.md` 每次心跳都会注入上下文。两百行的清单 × 一天几十次心跳是真金白银，控制在 30 行以内。
- **幽灵任务**：条目引用了心跳会话里没接入的工具或 MCP，agent 会静默失败甚至编造结果。上线前先确认该会话能真正调到这个工具。
- **定位错位**：“每天 9 点查天气”应该用 cron；心跳只做周期性的状态检查与决策。
- **静默失效**：文件路径写错或内容为空时，agent 什么都不做，而你也永远不知道。可以临时加一条“无条件回复一次”的自检项确认链路存活，验证后删除。
- **上下文污染**：心跳默认跑在主会话里，冗长的巡检输出会持续占用上下文，动作输出尽量一行以内。

## 可复用建议

- 条目模板固定为“条件 + 动作 + 通知策略”，一行一条，不写散文。
- 任务分流：状态巡检归心跳（仓库脏了没、磁盘满没、服务活着没），固定时刻归 cron，其余归对话。
- 心跳轮次绝大多数以 `NO_REPLY` 结束，条件允许就给它配轻量模型，省下的都是纯利润。
- 把 `HEARTBEAT.md` 放进 git：diff 历史就是 agent 的值班记录。
- 每月做一次清理：从没触发过的、每次都触发的条目，前者删掉，后者改成 cron。

## 总结

`HEARTBEAT.md` 的本质，是把“我希望 agent 关心什么”从隐含期望变成一份机器可执行的清单。检验它写得好不好只有一个标准：连续一两周，心跳既没有漏报，也没有打扰你一次——这份清单就算合格了。
