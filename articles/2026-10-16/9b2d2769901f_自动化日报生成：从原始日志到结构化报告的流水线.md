## 背景

团队每天要发一份日报，内容无非是：昨天合了什么、哪些服务出过错、待办进展如何。动作不难，但日复一日的复制粘贴很磨人。我们用 OpenClaw 的定时任务 + Agent + 几个 MCP 工具搭了一条流水线，把日报从"每天半小时的手工活"变成"早上九点自动推到群里的一条消息"。这篇记录做法和踩过的坑。

## 问题

一开始直接让 Agent 读日志写日报，试了一次就放弃了：

1. 日志量大，动辄几十万行，token 成本高，模型根本读不完；
2. 原始日志噪声多，关键报容易被漏掉，数字还会被编造；
3. 每天生成的格式都不太一样，没法归档和对比。

核心矛盾在于：把"提取信息"和"组织语言"都压给模型，两头都做不好。

## 做法

流水线分四层，原则是**代码管事实，模型管叙述**：

**1. 采集层（定时触发）**
cron 触发 OpenClaw 任务，通过 MCP 工具拉三路数据：git log、CI/告警记录、工单状态。每路数据落成本地 JSON 并带时间戳存档——原始快照一定要留，出问题可以回放。

**2. 结构化层（纯脚本）**
这层不用模型。脚本负责去重、按服务分桶、统计次数、抽取错误级别和时间戳，输出一份符合自定义 JSON Schema 的中间产物。数字全部由代码算，模型只引用、不计算。

**3. 叙述层（Agent + MCP）**
Agent 拿到的不是日志，而是结构化 JSON。Prompt 固定报告模板（概况 / 异常 / 变更 / 风险四段），明确要求只基于输入数据写，不允许补充外部信息。生成后跑一遍 Schema 校验，字段缺失自动重试。

**4. 输出层**
报告先与前一天做 diff（异常数突增时高亮），再通过 webhook 推送到群。流水线自身有心跳检测，连续两天无产出就在群里告警——日报工具不能自己先静默挂掉。

## 踩坑点

- **时区**：日志是 UTC，日报按本地日期切分，第一天把凌晨的告警算错天。统一在采集层转成带时区的时间再切。
- **日期边界**："昨天"是 00:00–24:00 还是工作时间，必须写死定义，否则日报和人的记忆对不上。
- **格式漂移**：模型各段落的详略不稳定，后来把模板收敛为"每段不超过 3 条要点"，并在校验层检查段落数量。
- **模型数数不可信**：早期让模型统计报错次数，同一份日志两次运行结果不同，全改成代码统计后才稳定。

## 可复用建议

- 中间 JSON Schema 单独建文件、带版本号，采集端和叙述端都对着它开发，改字段走版本演进；
- 先接一个数据源跑通再扩到三个，不要一上来全量接；
- 留 dry-run 模式：只生成不推送，调 prompt 时用来验证；
- 报告末尾固定输出"数据来源与时间范围"，方便读者判断可信度。

## 总结

这条流水线的核心不是某个聪明的 prompt，而是分工：确定性的工作交给脚本，模型只做它擅长的归纳和表达。日报只是最小应用，"采集 → 结构化 → 叙述 → 校验 → 投递"这套骨架，换成周报、变更摘要、值班交接都能直接复用。自动化真正的收益不在省那半小时，而在于口径统一、可回溯，不再依赖"谁今天记得写"。
