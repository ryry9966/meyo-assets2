# 背景

OpenClaw 的 workspace 里除了 AGENTS.md、MEMORY.md，还有一个默认生成但常被忽略的 SOUL.md。它每次会话都会注入 system 上下文，回答三个问题：这个 Agent 是谁、说话什么调性、哪些事不做。很多人的这个文件装完就吃灰，结果 Agent 在群聊里过于热情、执行任务前反复道歉、或者该确认的不确认直接动手。

# 问题

没有明确人格与边界的 Agent 会出现三类典型漂移：

1. **风格漂移**：同一套配置，交互问答像工程师，cron 定时推送像客服。
2. **边界漂移**：默认“有求必应”，收到群消息就回、拿到工具就调，在自动化场景里很危险。
3. **认知漂移**：多个指令文件互相打架——SOUL 里写“谨慎”，AGENTS.md 里写“自动执行常规任务”，行为开始随机。

# 做法

我的 SOUL.md 稳定在 40 行以内，分四段：

- **身份**：两三句说清定位，例如“运行在用户自建设备上的助理，主要服务 Telegram 和本地 shell 任务”。
- **语气**：用目标语言写，给具体样例比堆形容词有效。“回复不超过三句、先给结论”比“简洁专业”可靠得多。
- **边界**：写成可判定的规则，比如“向超过一个人的群发消息前必须先向用户确认”“不主动执行删除类命令”。
- **不确定时的行为**：明确“不确定就说不确定，然后追问一句”，抑制幻觉式热心。

写完放进 git。之后每次对行为不满意，改完看 diff、重启会话验证，像改配置一样对待它。

# 踩坑点

- **写太长**。SOUL.md 不是文档而是常驻上下文，两三千字会稀释关键约束，还吃 token 预算。宁短勿长。
- **和 AGENTS.md 职责混淆**。我的分工：SOUL.md 管“我是谁、什么不做”，AGENTS.md 管“怎么做、流程怎么走”。两边写重复内容迟早打架。
- **把它当安全边界**。SOUL.md 是软约束，靠上下文提示就能被绕过。真正的硬边界要放在工具白名单和网关权限上：不能让它碰的工具，从配置层禁掉，而不是在人格文件里求它别碰。
- **人格跨场景复用**。给私聊调的毒舌人格会被定时任务继承，自动报告里也带梗。要么拆成独立 workspace，要么在 AGENTS.md 里为定时任务覆盖语气。

# 可复用建议

- 边界写成“触发条件 + 动作”的可测试规则，方便回归验证。
- 每个独立用途的 Agent 一份 SOUL.md，不要共用。
- 修改后用一组固定测试问题跑一遍：正常请求、越界请求、模糊请求，观察是否按预期拒绝或追问。
- 软约束（SOUL.md）+ 硬约束（工具权限、沙箱）双层设计，缺一不可。

# 总结

SOUL.md 是成本极低、杠杆极高的文件。把它当配置代码对待：短小、版本化、可测试。人格决定 Agent 好不好相处，权限决定它危不危险，两层分开治理，自动化才敢真正放开跑。
