# 背景

OpenClaw 的 agent 并不是每次会话都“记得”你。它有一个固定的 workspace（默认在 `~/.openclaw/workspace`），里面除了 `SOUL.md`、`USER.md` 这类人设与画像文件，还有一份最容易被忽视、却最影响日常体验的文件：**AGENTS.md**。可以把它理解为“写给 AI 的员工手册”——`SOUL.md` 决定它是谁，`AGENTS.md` 决定它怎么干活。

# 问题

没写 AGENTS.md 的 workspace，常见症状有三个：

1. **行为漂移**：今天让它用 pnpm，明天又给你 npx 的命令；
2. **重复踩坑**：上周明确说过“别动 /etc 下的配置”，这周它又去试；
3. **工具调用随意**：接了七八个 MCP server 和插件之后，agent 会自己“发明”调用路径，该读本地文件的跑去联网搜。

这些不是模型能力问题，而是缺一份稳定的环境约定。AGENTS.md 就是补这个的。

# 做法

AGENTS.md 放在 workspace 根目录，纯 Markdown，agent 会作为持久上下文读入。建议分五块写：

1. **环境事实**：操作系统、常用路径、包管理器、有没有 GPU。写事实，不写愿望。
2. **工具优先级**：明确“查资料先走哪个 MCP、什么时候允许联网、哪个插件只在我显式要求时调用”。
3. **工作流约定**：回复语言、代码风格、是直接执行，还是先给方案再确认。
4. **红线**：禁止的命令类别、不许碰的目录、不许把 key 打进日志。
5. **记忆协作方式**：告诉 agent 哪些事该写进 `MEMORY.md`、多久整理一次。

每条尽量一行，用祈使句。写完先跑两天，把 agent 做错的地方逐条补成新规则——这份文件是迭代出来的，不是一次写完的。

# 踩坑点

- **太长**。超过一两百行后，关键规则会被稀释，遵循率明显下降。把低频内容挪到子文件，AGENTS.md 里只留索引和最高优先级规则。
- **指令冲突**。AGENTS.md 和 SOUL.md、系统提示词打架时，行为会变得不可预测。改规则前先全局搜一遍，确认没有矛盾表述。
- **写敏感信息**。API key、内网地址别明文放进去，workspace 可能被插件读到。用环境变量引用代替。
- **当成精确程序**。它是概率性遵循，不是 if-else。关键操作写“执行前先向我确认”，比写“永远不要 X”更可靠。

# 可复用建议

- **规则模板化**：统一用“遇到 X 时，做 Y，拿不准就问我”的句式，可读性和遵循率都更好。
- **让 agent 参与维护**：每周让它自查一遍最近违反过的约定，回写进 AGENTS.md，你只做审校。
- **分层管理**：全局习惯放 workspace 根，单个项目的特殊约定放项目内的 AGENTS.md，离代码近的那份优先。
- **纳入版本管理**：每次修改都 commit，出问题时有据可查、可回滚。

# 总结

AGENTS.md 的价值不在“写得全”，而在“稳定、短、可信”。把它当成团队里那份唯一真实的 onboarding 文档来维护：小步迭代、及时删过期条目、让 agent 自己补作业。手册写扎实了，agent 的下限就被抬高了——而在自动化场景里，下限往往比上限更重要。
