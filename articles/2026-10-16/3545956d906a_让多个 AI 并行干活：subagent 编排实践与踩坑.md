## 背景

单 agent 干活有两个天然瓶颈：一是长任务会把主会话上下文撑得很脏，抓取的原始内容、中间报错全堆在一起，后半程推理质量明显下降；二是所有工具调用只能排队串行，抓十个页面就得等十次。OpenClaw 这类框架支持主 agent 派生 subagent，每个 subagent 持有独立上下文和工具白名单，跑完只把结论交回来。听起来很美，实际用起来坑不少，这篇记录我跑稳一套并行编排的过程。

## 问题

先明确什么任务适合并行，我的判断标准只有两条：任务之间没有共享的写资源；单个任务的产出能被压缩成结构化结果。最开始我让三个 subagent 同时整理同一个 workspace 下的文档，结果互相覆盖文件；后来浏览器工具并发开五个实例，全部超时。并行不是提速开关，本质是资源调度问题。

## 做法

以「每周汇总 N 个开源仓库的更新摘要」为例，流程分四步：

1. **任务拆分**：主 agent 把仓库列表切成互不重叠的分组，每组生成一张任务卡，五个字段写死：目标、输入、允许的工具、输出格式（固定 JSON）、超时时间。
2. **受控派发**：并发度设为 3，每个 subagent 独立 session，工具白名单最小化——纯读取任务不给写权限。
3. **结论回传**：subagent 只回传压缩后的结构化结果，原始抓取内容留在自己的上下文里，不污染主会话。
4. **失败隔离**：单个 subagent 超时或报错就标记失败，该分组降级为串行重试，不拖垮整批。

一句话概括：subagent 是「带合同的外包工」，不是「共享屏幕的同事」。合同（任务卡）写得越死，合并结果时越省心。

## 踩坑点

- **共享写资源必须串行化或隔离目录**。文件锁的语义比想象中模糊，不如一开始就分目录。
- **MCP 工具有隐性并发上限**。先拿 2~3 个并发压测，看超时率再放量。
- **输出格式不在任务卡里写死，回传结果就没法合并**。主 agent 会被迫二次清洗，成本反而更高。
- **全并行的 token 成本可能是串行的 2~3 倍**，跑之前先算账，低价值任务不值得。
- **日志必须按 subagent 分开落盘**。混在一份日志里，排障等于盲人摸象。

## 可复用建议

- 先把任务跑成串行流水线，确认产出质量达标，再并行化，顺序不能反。
- 并发度默认 3 起步，这是大多数工具链的舒适区。
- 任务卡模板沉淀成固定格式，五个字段缺一不可，别让主 agent 即兴发挥。
- 幂等任务优先并行；有副作用的任务（发消息、改配置）保持串行或加人工确认。
- 不要让 subagent 之间互相通信，所有汇合点都在主 agent——拓扑越简单，越好排障。

## 总结

Subagent 编排的本质不是「更多 AI」，而是更严格的任务契约和更清晰的资源隔离。并行带来的速度收益，只有绕开共享资源和上下文污染这两个坑才真正落袋。建议从一个低风险、幂等的任务开始，把任务卡模板打磨稳定，再逐步扩大到日常工作流。
