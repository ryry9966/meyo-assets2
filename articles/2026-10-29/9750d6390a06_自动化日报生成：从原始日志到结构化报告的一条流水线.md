## 背景

我们团队用 OpenClaw 跑了几个常驻 Agent，负责日常巡检、数据处理和内部工具维护。跑了一段时间后发现：Agent 每天产生大量会话日志和工具调用记录，但“今天到底干了什么、有没有异常”，还是得靠人翻日志或手动汇总。日报这种事，靠自觉是撑不过两周的。

## 问题

原始日志有三个特点，导致它不能直接当日报用：

1. **体量大**：一天几百条会话记录，全量塞给模型摘要，要么超上下文，要么成本失控；
2. **噪声高**：重试、心跳、探活这类例行调用占了七八成，真正有价值的事件被淹没；
3. **不可信**：直接让模型“总结一下今天的日志”，它会很自然地编出看似合理的数字——这种日报比没有日报更危险。

核心思路由此确定：**数字一律由脚本统计，模型只负责把统计结果组织成人话。**

## 做法

流水线分四步，每天定时触发一次：

**① 采集与切片。** 从会话日志目录按天拉取 JSONL 记录，统一时区（我们踩过 UTC 与本地时间混用的坑），按会话 ID 去重。

**② 脚本聚合。** 这一步不涉及模型，纯规则：统计每个会话的工具调用次数、错误数、耗时分布；过滤心跳类例行事件；同类错误聚合成计数。产出一份中间 JSON，它是日报里所有数字的唯一来源。

**③ 结构化摘要。** 把聚合 JSON 和固定模板 prompt 喂给模型，强制按 JSON schema 输出四个字段：今日概览（两三句）、重点变更、异常与风险、待办建议。温度设 0.1，禁止输出 schema 之外的数字。

**④ 校验与投递。** 用 schema 校验输出，失败带错误信息重试一次，再失败就发降级版（纯统计数字、不摘要）。通过后渲染成 Markdown，一份推群 webhook，一份落档仓库，方便周报二次聚合。

## 踩坑点

- **别让模型碰数字。** 早期让模型直接读日志写日报，出现过实际 3 次失败、日报写“零异常”的情况。改成脚本统计后彻底消失。
- **先聚合再摘要。** 全量日志直接进模型，token 成本是聚合后的 20 倍以上，摘要质量反而更差。
- **流水线自己也要被监控。** 日报最大的失败模式是静默失败：某天脚本挂了没人发现。我们加了一条：无论成败，流水线跑完必发一条状态消息，哪怕内容是“今日日报生成失败”。
- **同类事件要合并。** 某个依赖抖一下，重试日志能有几十条，不合并的话日报全是重复告警。

## 可复用建议

- 把 schema 和 prompt 模板做成配置文件，换报告格式不用改代码；
- 中间 JSON 一定要落盘——它既是数据源，也是排查“日报为什么这么写”的依据；
- 先跑通最小闭环（采集 → 聚合 → 一段话摘要 → 推送），再逐步加字段，别一上来设计大而全的模板。

## 总结

这套流水线没有复杂技术，本质是“脚本管事实、模型管表达”的分工。上线两个月，日报从每天十几分钟手动整理变成零干预，而且因为数字可追溯，可信度反而比人工整理更高。对已经在跑常驻 Agent 的团队来说，这是投入产出比很高的自动化切入点。
