# 背景

OpenClaw 的 agent 不是每次都从零开始工作的：它有一个常驻的工作空间（workspace），里面放着文件、脚本和你沉淀的各类资料。但「工作空间里有什么」和「agent 该怎么用这个空间」是两件事。前者靠目录结构，后者需要一份明确的说明书——这就是 AGENTS.md 的定位：放在工作空间根目录、agent 每次开工都会读取的 Markdown 操作手册。

可以把它放进分层配置里理解：人格与语气归 SOUL.md，身份信息归 IDENTITY.md，而「在这个空间里怎么干活」，归 AGENTS.md。

# 没有它会怎样

- 每个新会话都要重复交代：启动命令是什么、测试怎么跑、哪个目录别碰；
- 行为漂移：同一类任务，不同会话的产出步骤和风格不一致；
- 边界缺失：agent 可能在你没交代的情况下直接 push、删构建产物、对外发消息；
- 教训丢失：上次踩坑的总结留在聊天记录里，下次会话等于没发生过。

# 怎么写

1. 在工作空间根目录创建 `AGENTS.md`，纳入 git 管理；
2. 按区块组织，每个区块回答一个明确问题：
   - **项目概览**：一两句话说明这个空间是干什么的、关键目录的职责；
   - **常用命令**：启动、测试、构建、部署的准确命令，可直接复制执行；
   - **约定**：命名风格、文件归属、commit 格式、回复语言；
   - **红线**：哪些目录只读、哪些操作必须先向用户确认（push、删除、对外发送）；
3. 控制篇幅，高频规则放前面；细节性的东西交给 skills 或 TOOLS.md，AGENTS.md 只留一行索引；
4. 像维护代码一样维护它：踩了新坑，就把对应规则补回去。

# 踩坑点

- **写太长**：规则一多，注意力被稀释，最关键的红线反而容易被忽略。几十行能说清的不要写几百行；
- **指令冲突**：文件里说「提交前必跑测试」，会话里又说「这次跳过」，行为就会不稳定。建议显式写一条：会话中的明确指令优先于本文件；
- **硬编码环境**：绝对路径、机器名写进文件，换个环境就失效，尽量用相对路径；
- **模糊表述**：「小心处理数据库」没有约束力，应写成「删除任何数据前必须先询问」；
- **一次成型不迭代**：它不是配完就完事的东西，价值恰恰在持续沉淀。

# 可复用建议

- 把它当「给 agent 看的 README」：README 面向人，AGENTS.md 面向 agent，两者互相校对能发现不少遗漏；
- 错误驱动迭代：agent 做错一次，就沉淀一条规则，比凭空预设一堆规则有效得多；
- 红线用祈使句加确认机制，保证可执行、可验证；
- 团队场景下把 AGENTS.md 提交进仓库，让所有人和所有 agent 共享同一套约定。

# 总结

AGENTS.md 解决的不是能力问题，而是协作一致性问题。它的本质是把「你希望 agent 怎么工作」从聊天记录和记忆里搬出来，变成一份可版本化、可 review、可持续迭代的工程资产。花半小时写好第一版，之后每次踩坑补一条，一段时间后你会发现：与 agent 的沟通成本明显下降，产出也稳定多了。
