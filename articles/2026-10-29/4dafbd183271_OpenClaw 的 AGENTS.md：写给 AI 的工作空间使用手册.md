## 背景

OpenClaw 每次启动会话时，会把工作区里的 `AGENTS.md` 读入作为系统级上下文。如果说 `README.md` 是写给人看的，那 `AGENTS.md` 就是写给 agent 看的：它决定了 agent 如何理解这个工作区——项目结构、常用命令、边界约束、输出偏好。这份文件的质量，直接决定你在每次会话里要重复多少话。

## 问题

没有 AGENTS.md（或写得不好）时的典型症状：

- 每次会话开头都要口头重申规范：“测试用 vitest，别用 jest”
- agent 反复犯同一个错：改了不该动的文件、用了已废弃的命令
- 团队成员各自在工作区里“口口相传”，agent 行为因人而异

这些纠正只存在于聊天记录里，会话结束即失效。本质上，是把工作区知识存放在了最不可靠的介质——对话上下文中。

## 做法

1. 在工作区根目录建 `AGENTS.md`，先写四块内容：环境事实（OS、运行时版本、包管理器）、常用命令（构建/测试/lint 的准确命令）、边界约束（哪些目录不能动、哪些操作需确认）、输出偏好（提交信息格式、注释语言）。
2. 多项目工作区用分层：根目录放全局约束，子目录放项目细节，OpenClaw 会按就近原则合并加载。
3. 每条规则保持“可执行、可验证”。参考骨架：

```markdown
# 环境
- Ubuntu 22.04 / Node 20 / pnpm 9
# 常用命令
- 测试：pnpm test
- 构建：pnpm build
# 边界
- 不要修改 infra/ 下的 Terraform 文件，需要时先询问
- 任何删除操作必须先确认
# 输出
- 提交信息格式：模块: 变更摘要
```

4. 纳入版本管理，改规则像改代码一样走 review。

## 踩坑点

- **写成 README**：项目历史、愿景、介绍性内容对 agent 是纯噪音，会稀释有效指令的权重。
- **太长**：超过一两屏，模型注意力被摊薄，尾部规则基本不生效。我的经验是控制在 60 行以内。
- **规则互相矛盾**：两处对同一行为给出不同指令，agent 会随机选一个，而且极难排查。
- **写入敏感信息**：API key、内网地址一旦写进文件，会随工作区同步和备份一起扩散。
- **更新滞后**：命令换了文件没改，agent 会按过时规则稳定地失败。过时信息比没有信息更糟。

## 可复用建议

- 一条检验标准：这一行如果不写，agent 行为会变差吗？不会就删。
- 用新会话做回归测试：改完 AGENTS.md，开一个干净会话跑一个典型任务，观察行为是否按预期变化。
- 让 agent 参与维护：它犯错被纠正后，让它把这条纠正写进 AGENTS.md 并提交 diff，规则积累最快。
- Monorepo 按目录拆分，不要把所有规则塞进根文件。
- 把它当配置而不是文档：每次改动写清 commit message，说明为什么改。

## 总结

AGENTS.md 的价值不在“写了多少”，而在“省掉了多少重复沟通”。它把散落在聊天记录里的口头纠正，固化成可版本化、可 review 的工作区配置。花 20 分钟写第一版，之后每次 agent 犯错就补一条，一个月后你会得到一份真正贴合自己工作区的操作手册——而且是写给 AI、也经得起 AI 反复执行的那种。
