## 背景

我们团队的日志分散在几处：服务日志在机器上，CI 结果在流水线里，还有一部分靠手工记录在文档中。之前每天的日报靠人肉汇总，写的人累，看的人也未必能从十几段粘贴里找出重点。

OpenClaw 的定时任务 + MCP 数据源 + Agent 总结能力，刚好能拼出一条"日志进、报告出"的流水线。本文记录这条流水线的做法和踩过的坑。

## 问题

拆开看，日报自动化有三个核心难点：

1. **采集不稳定**：来源多、格式杂，手工收集经常漏；
2. **总结不可控**：直接把原始日志丢给 Agent，它会编数字、漏关键事件、每次格式还不一样；
3. **没有校验**：报告写错了没人发现，第二天才被业务方指出。

## 做法

核心思路一句话：**确定性的活交给脚本，Agent 只负责它擅长的归纳和表述**。流水线分五步：

**1. 采集**：每个数据源写一个独立脚本（或封装成 MCP tool），输出统一 JSON：`source`、`timestamp`、`events[]`、`metrics{}`。数量指标由脚本算好，Agent 不做任何算术。

**2. 归一化**：合并各来源数据成当日快照，存到 `reports/raw/YYYY-MM-DD.json`。原始快照留档，报告出错时可回溯。

**3. Agent 总结**：prompt 里固定输出模板（段落标题锁定，引用指标必须带来源字段）。上下文只放摘要级数据——Top N 错误、聚合指标、关键事件时间线，不放全量日志。

**4. 校验**：轻量脚本比对报告中的数字与快照是否一致、必填段落是否为空。不过就打回重试，最多三次。

**5. 投递**：Markdown 发群，同时归档入仓。失败时发一条告警，不静默。

用 OpenClaw 定时任务每天固定时间触发，整条链路一两分钟跑完。

## 踩坑点

- **别让 Agent 算数**。最初把原始计数丢给它算环比，±10% 的误差是常态。所有数字脚本算好，Agent 只引用。
- **上下文别塞满**。全量日志一进来，Agent 开始"总结"无关细节，尾部内容还容易被忽略。只喂聚合结果。
- **schema 要强约束**。不锁格式，第三天报告就开始自由发挥。模板固定 + 校验兜底，两个都要有。
- **时区问题**。任务按 UTC 触发，第一次跑出来的"日报"实际覆盖的是前一天 8 点到当天 8 点。采集起止时间要在任务里显式指定。
- **重试要幂等**。失败重跑生成两份报告、群里发两条，比报告写错还尴尬。按日期命名 + 幂等写入。

## 可复用建议

- 采集层做成可独立调用的 MCP tool，日报只是消费者之一，周报、告警都能复用。
- 校验规则和报告模板放同一目录做版本管理，改模板时校验同步改。
- 上线初期保留人工确认：报告先生成预览，人回一句"发"再进群，跑稳两周再关。
- 每份报告附带生成参数（时间窗、数据源清单），方便排查"这天怎么没数据"。

## 总结

这条流水线没有什么高深的东西，价值在于把"人肉粘贴"变成"脚本算数 + Agent 写作 + 脚本校验"的三段式。Agent 只出现在中间一段，输入输出都被 schema 管住，整条链路才敢无人值守。如果你也在用 OpenClaw 做自动化，建议从单一数据源、单一报告起步，先跑通校验环节，再逐步扩数据源——采集面一宽，没有校验的流水线就是在批量生产错误报告。
