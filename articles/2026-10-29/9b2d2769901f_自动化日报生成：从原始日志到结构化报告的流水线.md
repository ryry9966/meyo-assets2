## 背景

团队日报这事，做起来简单，坚持下来难。我们的场景：多台服务器的运行日志、Git 提交、CI 结果分散在不同位置，之前靠人每天下班前手动拼一份 Markdown 发到群里——写的人烦，看的人也未必信里面的数字。

于是用 OpenClaw 搭了一条流水线：定时触发 → 拉数据 → 清洗 → Agent 摘要 → 校验 → 推送。跑了一个多月，质量和人写的差不多，但数字永远是对的。

## 问题

真正的问题不是“生成一段文字”，而是三个：

1. **原始日志不适合直接喂给模型**。一天几十万行远超上下文，而且模型从非结构化文本里“数数”极不可靠。
2. **数字幻觉**。日报里最关键的是变更数、失败率、P95 耗时这类硬指标，模型一旦自己算，就不可信。
3. **投递可靠性**。重试后重复发送、静默失败无人发现，比没有日报更糟。

## 做法

核心原则一句话：**模型只负责组织语言，所有数字来自结构化数据**。

**1. 采集与清洗（纯脚本，不经模型）**：Python 脚本按当日窗口拉取数据——日志按服务聚合错误 TopN、请求量、耗时分布；Git 按 repo 汇总 commit；CI 汇总任务成败。写入一份 schema 固定的 JSON，同时落盘归档，作为原始快照。

**2. Agent 摘要（MCP 工具注入）**：给 Agent 配一个 MCP 工具，返回第 1 步的 JSON。prompt 里明确约束：只允许引用 JSON 中的数字，不得推算、不得补充数据里没有的内容；输出遵循固定 Markdown 模板。模型做的是挑重点、写人话，不做计算。

**3. 规则校验**：脚本抽取报告中的所有数字，与 JSON 做键值级比对，并检查模板段落是否齐全。不过就重生成一次，再不过就降级——直接把 JSON 渲染成表格版发出，宁可丑也不出错。

**4. 调度与投递**：cron 触发，每次任务生成 `report-YYYYMMDD` 幂等键，已存在即跳过，重试不会重复推送。报告走群 webhook 发出并归档；任务失败时单独发告警——日报缺失本身也要可见。

## 踩坑点

- **时间窗口与时区**。日志按 UTC 切割、按东八区统计，第一天的“昨日”混入了前天下午的数据。所有数据源统一换算到本地时区再取窗口。
- **模型输出格式漂移**。跑几天后模型偶尔把表格换成列表，下游校验就挂了。把模板硬编码进 prompt，并把段落结构列为校验项，漂移触发重试。
- **校验别只查数字存在性**。早期只检查“数字出现了”，没查来源，模型把两天的失败数拼在一起也能过。改成键值级比对才堵住。
- **日志里的敏感信息**。错误详情偶尔带 token 和内网地址，清洗阶段统一脱敏后再给模型，不要指望事后人工把关。

## 可复用建议

- 数据 schema 和报告模板当两份独立资产维护：改报告不动采集，改采集不动 prompt 逻辑。
- 每份报告保留对应的原始 JSON 快照，出了争议随时回溯，这比模型本身重要。
- 校验层是这套东西的核心投入点，键值比对一开始就做，别事后补。
- 同一骨架可复用到周报、事故简报：换数据源和模板，流水线不变。

## 总结

这套流水线没有用到什么复杂技术，本质是**脚本干脏活、模型干表达、规则做兜底**。Agent 的价值在于把结构化数据翻译成团队愿意读的叙述，而不是替你计算。把数字的信任链从模型身上摘下来，日报才敢自动发——这也是我们目前用 Agent 做自动化最稳的一条经验。
