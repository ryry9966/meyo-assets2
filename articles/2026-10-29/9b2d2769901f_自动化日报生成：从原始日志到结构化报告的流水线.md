## 背景

我在一台自托管机器上长期跑着 OpenClaw 网关和若干 agent 会话，日常会积累三类原始日志：session 的 JSONL 记录、网关运行日志、MCP server 的 stderr。以前是出问题再翻，但"昨天 agent 都干了什么、哪几个工具调用失败、消耗花在哪"这类问题靠人肉翻日志不可持续。于是搭了一条定时日报流水线，稳定跑了两周多，把过程记录一下。

## 问题

直接把日志丢给模型生成日报，会撞上三件事：

1. **上下文与成本**：一天的日志几千到上万行，全量塞给模型既贵又容易截断；
2. **格式漂移**：模型自由发挥，每天日报结构都不一样，没法横向对比；
3. **数字不可信**：让模型数日志里的错误次数，数错是常态。

所以核心结论先放在前面：**统计交给代码，叙述交给模型；模型是流水线的可选增强，不是必经之路。**

## 做法

流水线分五层，cron 每天本地时间 07:30 触发：

```
采集(cron+脚本) → 清洗(规则) → 统计(纯代码) → 生成(LLM, 可降级) → 分发(推送+存档)
```

**1. 采集**：按日期切片拉取三处日志，统一转成本地时区后落盘到 `daily/YYYY-MM-DD/raw/`。中间产物一定落盘，方便回放。

**2. 清洗**：规则层过滤心跳、轮询、debug 这类噪声条目；JSONL 直接解析，纯文本用正则抽字段。这一步纯代码，可单测。

**3. 统计**：聚合成几十行的结构化 JSON：任务次数、工具调用 TopN、失败分类计数、耗时分布、消耗汇总。压缩比通常在 100 倍以上。

**4. 生成**：给 agent 的指令只做两件事——对"失败 TopN + 异常条目样本"写两三句归因，给出 1~3 条待办建议。日报骨架是固定 Markdown 模板，统计数字由代码预填，模型只填叙述段，温度 0.2。

**5. 分发**：渲染成品推送到频道，同时存档 `report.md`。LLM 调用失败时降级发"纯统计版"，保证日报永不缺席。

核心骨架十几行：

```python
stats = aggregate(clean(load(raw_dir)))      # 纯代码，不经过模型
narrative = llm_fill(TEMPLATE, stats) or FALLBACK_TEXT
push(render(TEMPLATE, stats, narrative))
```

## 踩坑点

- **时区切分**：日志时间戳是 UTC，报告按本地日期切，第一天就出现条目跨天归属错乱。现在统一在采集层转本地时区再落盘。
- **心跳污染统计**：不过滤的话"调用次数 Top1"永远是心跳类工具，统计失去意义。清洗层维护一份噪声模式清单，持续补充。
- **格式漂移**：早期让模型整段生成日报，三天后字段就开始增删。改成代码预填 + 模型填空后彻底稳定。
- **cron 静默失败**：日报任务自己挂了没人知道，等于没做。加了一条 watchdog：07:45 检查当天报告文件是否存在，不存在就走另一条链路告警。监控自动化任务本身，别信任它。

## 可复用建议

1. **分层解耦**：五层各自可独立运行、可重放，出问题先定位在哪一层。
2. **中间产物 JSON 落盘**：日报格式想调整，重放统计层即可，不必重新解析原始日志。
3. **模型输出只进"叙述槽"**：数字、字段、结构全部由代码决定。
4. **降级路径优先设计**：LLM 不可用时日报照样出，只是少了归因段。

## 总结

这套东西本质是"数据管道为主、LLM 为辅"的组合：规则代码负责压缩与准确性，模型负责它真正擅长的归因叙述，MCP 工具只是生成层的一个可选项。如果你也在用 OpenClaw 跑长期任务，建议从"cron + 清洗脚本 + 固定模板"这个最小版本起步——先让日报天天能到，再逐步把生成层交给 agent。
