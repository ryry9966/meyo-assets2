# USER.md 实践：让 Agent 第一秒就知道你是谁

## 背景

大模型本身无状态。每次新会话，Agent 对你的认知都归零：你用 pnpm 还是 npm、偏好简短结论还是完整推理、测试机是什么环境——全得重说一遍。OpenClaw 的 workspace 里，大家已经很熟悉 AGENTS.md（约束 Agent 怎么干活），但 USER.md（描述 Agent 为谁干活）常常是个空文件。这两个文件解决的是不同的问题，而后者对日常体验的影响往往更大。

## 问题

没有用户画像时，摩擦主要有三类：

- **重复输入**：同一个会话里第三次解释"用 pnpm，别动 lock 文件"。
- **通用化输出**：Agent 给的永远是最普遍的方案，而不是适合你技术栈和习惯的方案。
- **上下文误判**：它不知道你管着哪些项目、机器有什么约束，建议经常"正确但没用"。

## 做法

1. **建文件**。在 workspace 根目录创建 USER.md，目标控制在 60～80 行、约 1500 token 以内。
2. **分区写**。推荐四个固定分区：

```markdown
# 身份与环境
- 时区：UTC+8
- 主力机：macOS + zsh，包管理 pnpm
- 常用语言：Python 3.12 / TypeScript

# 偏好
- 回答先给结论，最多三个要点，代码优先于解释
- 中文交流，技术名词保留英文

# 禁区
- 不未经确认执行 rm、git push --force
- 需要权限的操作：先列出完整命令等我确认

# 当前上下文（易变，每周更新）
- 正在做：xxx 数据管道迁移
- 本周目标：完成 MCP 工具的鉴权重构
```

3. **验证加载**。重开会话后直接问几个事实性问题："我用什么包管理器？""哪些命令不许直接执行？"答不上来说明文件没被注入，先查 workspace 路径配置。
4. **建立迭代机制**。规则很简单：每次发现自己在对 Agent 重复一句话，就回 USER.md 补一行。这份文件是长出来的，不是一次写完的。

## 踩坑点

1. **写太长**。超过两千 token 后，关键偏好会被淹没在注意力噪声里，效果反而下降。宁可精简，也不要写成自传。
2. **信息过期**。把"项目 A 还没上线"写死后不更新，Agent 会基于旧事实推理，比不知道更糟。易变内容单独放"当前上下文"区，显式标更新频率。
3. **敏感信息**。每次会话 USER.md 都会进上下文；走云端模型时等于每次都上传。API key、内网地址、真实手机号一律不写。
4. **只写禁令**。"别用 sudo"不如"需要权限时先列命令等我确认"。给 Agent 替代动作，比单纯堵路有效。

## 可复用建议

- **Profile as code**：USER.md 进 git，多台机器和多个 Agent 实例共享同一份，改动有据可查。
- **稳定与易变分离**：USER.md 放长期稳定的事实，项目状态拆到独立的 CONTEXT.md，只重写后者。
- **负面清单 + 正面动作**：每条"不许"后面跟一个"应该怎么做"。
- **月度 review**：日历上定个 15 分钟回顾，删过时项比加新项更重要。

## 总结

USER.md 的本质，是把散落在聊天记录里的"你对 Agent 的口头约定"，固化成一份可版本管理的声明式配置。第一版花 20 分钟就够，之后靠"重复即补一行"的机制自然生长。Agent 不需要真正"认识"你，它只需要在每次开局时，读到一份足够准确、足够新鲜的档案。
