## 背景

单 agent 串行干活的问题大家应该都遇到过：让主 agent 检查 8 个仓库的依赖升级、批量处理一批文档、或者"先调研再写报告"，它会一步步来，工具调用的中间结果把上下文窗口越塞越满，后半程质量明显下滑。

OpenClaw 这类框架里，agent 可以派生 subagent（独立上下文的子会话）。这给了一个很自然的解法：把可拆分的任务分发出去并行跑，主 agent 只负责拆分、分发和聚合。

## 问题

实践中真正的难点不是"能不能并行"，而是三件事：

1. **上下文污染**：subagent 的中间过程如果回流主会话，等于白拆。
2. **结果聚合**：多份原始输出直接拼给主 agent，聚合侧上下文爆炸。
3. **失败隔离与副作用**：两个 subagent 改同一个文件，或者一个失败后留下半成品。

## 做法

以一个真实场景为例：让 agent 每周检查 6 个上游项目的 changelog，各产出一份要点摘要，最后汇总成周报。

1. **先确认任务边界**。6 个项目互相独立、没有共享写入目标，才拆。有依赖的部分（最终汇总）留在主 agent 串行做。
2. **给每个 subagent 一个窄 prompt**。只放三样东西：任务目标、自包含的输入（仓库地址、时间窗）、输出契约（"不超过 200 字要点 + 变更文件路径列表"）。不要把主会话历史带过去。
3. **控制并发**。同一批 3~4 个为宜。太多会撞限流，排障时日志也看不过来。
4. **约定返回格式**。统一要求 subagent 返回结构化短结果（要点 + 结论 + 产物路径），原始 trace 留在 subagent 自己的会话里，出问题再翻。
5. **主 agent 只做聚合**。拿到 6 份短摘要后去重、排序、成稿。聚合时的上下文始终是可控的小尺寸。

## 踩坑点

- **输入给太少**。只丢一句"看看这个仓库有什么更新"，subagent 会自己脑补范围。范围、时间窗、输出格式必须一次说清。
- **共享可变状态**。两个 subagent 往同一目录写文件必炸。给每个 subagent 独立工作目录，由主 agent 合并。
- **没有幂等设计**。subagent 跑一半挂了，重跑要能覆盖而不是叠加。产物先写临时目录，确认完整再挪正式位置。
- **"看起来独立"不等于"真的独立"**。两个任务都要先拉同一个远程仓库并更新本地缓存，并行就互相踩。有共享前置步骤的，先串行做完前置，再并行分支。
- **并发过高**。超过 6 路之后，聚合侧的上下文压力和成本会抵消收益。

## 可复用建议

- 一个 subagent 只干一件事、只交付一个产物。如果你需要写很长的 prompt 才能解释清楚任务，说明拆分粒度不对。
- 输出契约比自由发挥可靠：长度上限、结构化字段、产物路径，三项固定。
- 每个 subagent 独立工作区 + 独立 trace，排障按 subagent 粒度看，别混在一起。
- 主 agent 的价值在拆分判断和聚合质量，别让它自己下场干 subagent 的活。

## 总结

subagent 编排本质是工程上的分治：**任务边界清晰、上下文自包含、产物有契约、失败可重试**。做到这四点，并行带来的速度和上下文隔离是实打实的；做不到，并行的只是混乱。建议从一路 2~3 个 subagent 的小任务开始，把返回格式和目录约定固化下来，再逐步放大规模。
