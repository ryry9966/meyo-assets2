Agent 圈今天这条新闻有点技术含量：据 36kr 报道，一款 350 亿参数的扩散大模型正式瞄准 Agent 场景，速度是对标速度优化型自回归模型（报道中称 Jev）的两倍。过去一年，扩散语言模型（diffusion LLM）从 LLaDA、Dream 7B 一路补课到 Gemini Diffusion，如今终于带着「能扛生产的参数量」杀进 Agent 主场。这篇文章讲清三件事：它到底怎么工作、为什么 Agent 最吃这套、以及现在入坑要注意什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-29/a32ab0c596ad487e.png)

## 一、先补课：打字机 vs 显影液

- **自回归（Autoregressive, AR）**：GPT 系的标准姿势，像一台打字机，从左到右一次吐一个 token，前一个字是后一个字的条件。生成 N 个 token 就要 N 次前向计算，延迟随输出长度线性上涨。
- **扩散（Diffusion）**：图像界的老熟人（Stable Diffusion 就是它），搬到文本上叫掩码扩散。开局整段全被遮成 [MASK]，模型每一轮同时对整块「画布」去噪：有把握的位置先揭出来，没把握的继续猜，几十轮之后一整段同时显影。
- **关键差异一句话**：AR 生成 1000 个 token 大约要 1000 步解码；扩散模型只要十几到几十步去噪步，且每步并行处理所有位置。
- 已有的速度数据点：Inception Labs 的 Mercury Coder 在单张 H100 上跑到 1000+ tokens/s；Google 的 Gemini Diffusion 实测约 1400 tokens/s；字节 Seed Diffusion 在代码任务上报过 2146 tokens/s。这次的「快一倍」，是这条路线的自然延续。

## 二、为什么偏偏是 Agent 主场

Agent 对速度的渴望和聊天机器人不是一回事，四个原因：

1. **延迟被循环放大**。一个 Agent 任务 = 感知 → 规划 → 调工具 → 观察结果 → 再规划，循环 N 轮，每轮都是一次完整 LLM 调用。假设单轮要生成 300 token 的工具调用，AR 模型按 60 tok/s 算要等 5 秒，10 轮下来光「看模型打字」就 50 秒；速度翻倍直接省 25 秒，任务链越长省得越多。
2. **输出短且结构化**。Agent 的调用大多是 JSON、函数签名、路由判断，毫无「流式观赏价值」，没人想欣赏 JSON 一个字段一个字段蹦出来。低首 token 延迟 + 整段并行吐出，正好打在痛点上。
3. **双向注意力 + 迭代修正**。AR 写出去的字泼出去的水，错了只能重 roll；扩散每一轮都能全局回看、反复改，先搭骨架再填细节，天然适合结构化输出，还能做约束解码，强制结果符合 schema。
4. **高并发更从容**。延迟不随长度线性涨，同卡吞吐稳定，对多租户 Agent 平台是实打实的单位成本优化。

另外注意「快一倍」的含金量：对比基线是被 speculative decoding 等手段榨过速度的速度优化款，不是随便挑的软柿子。

## 三、350 亿参数，意味着过了「规模关」

- 2022–2023 年的文本扩散尝试基本卡死在小模型上，质量追不上同尺寸 AR，社区一度判了死刑。
- 2025 年，人大的 LLaDA（8B）和 Dream 7B 先证明「同规模能打平 LLaMA3 / Qwen 同级」；Mercury 和 Gemini Diffusion 再补上速度证据。
- 如今冲到 35B（350 亿），说明 scaling law 在扩散范式上依然成立。参数量上去，工具调用、长上下文、复杂指令这些 Agent 的硬需求才撑得住——7B 级扩散模型做 demo 够用，扛生产 Agent 很勉强。
- 速度数字背后是工程花活而非魔法：Fast-dLLM 给扩散模型也整出了近似 KV cache 和并行解码；block-wise 半自回归解码（块间顺序推进、块内并行去噪）兼顾长文本一致性。

## 四、冷水区：AR 不会因此退场

1. **质量天花板还没破**。同尺寸打平不等于越级碾压，前沿 AR 旗舰在深度推理上仍领先。而且扩散模型每步去噪都要对全序列做完整 attention，单位 token 的 FLOPs 其实更贵——快是因为并行，不是因为省算力。
2. **生态在 AR 这边**。vLLM、SGLang、量化方案、微调和 RLHF 工具链全是围着 AR 建的，dLLM 的推理优化和训练工具还在补课，换范式的迁移成本要算进 TCO。
3. **变长生成别扭**。扩散在固定长度画布上很舒服，遇到「输出长度未知」的自由生成，得靠填充与裁剪策略兜底。
4. 更可能的结局是**混血而非替代**：AR 管骨架与强推理，扩散管填空和草稿，甚至反过来当 speculative decoding 里的 draft 模型，推理框架层面拼积木。

## 五、收尾：三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-29/7259644e4b041e03.png)

1. **按延迟结构选型，别按范式站队**。首 token 延迟敏感、输出短且结构化、高并发——优先试扩散模型；长链路深度推理、追求单点智能上限，AR 旗舰仍是默认答案。
2. **把 tokens/s 换算成业务账**。用「单任务端到端时延 × 日均任务量」估算收益，并看清新闻里的对比基线（是不是速度优化版）、测试硬件和负载类型。demo 快，不等于你的 workload 快。
3. **盯紧工程栈成熟度**。上生产前，用自己的真实 Agent trace 做回归测试，重点看工具调用成功率、结构化输出合规率、显存占用和并发下的长尾延迟。范式新不新不重要，指标稳不稳才重要。
