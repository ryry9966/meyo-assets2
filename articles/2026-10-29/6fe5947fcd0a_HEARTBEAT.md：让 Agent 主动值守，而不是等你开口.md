## 背景

多数对话式 Agent 的工作模式是被动应答：你不问，它不动。但日常自动化里大量需求恰好相反，盯一个构建、巡检一个服务、整理昨日提交，这些本质是"它该主动来找你"。OpenClaw 在网关层内置了心跳机制：按固定间隔（默认 30 分钟）向 agent 发一个系统级 prompt；如果工作区里存在 `HEARTBEAT.md`，其内容会随 prompt 一起发给模型，agent 每次醒来带着全部工具（exec、browser、MCP 工具）去执行检查，再决定是否主动汇报。

## 问题

没有心跳时的常见做法：要么自己写 cron 调 API 再推消息，判断逻辑（"这条值不值得打扰我"）硬编码在脚本里，很僵硬；要么人肉去问 agent"最近有什么事"，把值守成本转嫁回人。`HEARTBEAT.md` 的定位介于两者之间：定时触发交给网关，检查动作和汇报条件用自然语言写，判断交给模型。

## 做法

1. 进入 agent 工作区（默认 `~/.openclaw/workspace/`），新建 `HEARTBEAT.md`。
2. 清单式书写，每项写清：检查什么、什么条件下才汇报、无事时保持安静。
3. 在配置里调整节奏与成本：`agents.defaults.heartbeat.every` 控制间隔，`heartbeat.model` 指定轻量模型，也可配置送达目标（默认主会话）。多 agent 各自工作区独立生效。
4. 文件每个心跳都会重新读取，改完下轮即生效，无需重启；验证时可临时调短间隔观察两轮。

示例：

```markdown
# Heartbeat 任务
- 检查 my-org/api 仓库的 open issues，出现 P0/P1 标签才汇报，附链接。
- curl 健康检查接口，非 200 连续两次才告警，恢复时通知一次。
- 每天上午首个心跳产出日报（昨日 commits + 待办）。
- 无事可报时只回复 HEARTBEAT，不要输出多余内容。
```

## 踩坑点

- **把精确定时写进清单**。心跳是"到点看一眼"，不是 cron。写"每天 8:00 提醒"而心跳 30 分钟一次，agent 需自行判断该不该发，容易漏发或重发。准点任务交给 OpenClaw 的 cron，心跳留给"巡检 + 判断"。
- **成本失控**。文件存在时每个心跳都跑一次模型。对策：调大间隔、换轻量模型、及时删掉已完结任务（文件不存在时网关直接短路，不调模型）。
- **噪音**。不写静默条件，agent 可能每轮都客套一句。明确要求无事只回纯 ack，这类回复不会被转发到聊天。
- **无监督执行**。心跳带全套工具权限，清单里不要出现删除、批量写等不可逆操作，检查尽量只读。
- **状态没落盘**。"连续两次失败才告警"这类条件，让它把状态写进工作区的状态文件，下次心跳先读再判，别依赖会话记忆。

## 可复用建议

- 把 `HEARTBEAT.md` 当 SOP 写：触发条件 + 检查动作 + 汇报格式 + 静默条件，四要素齐一个任务。
- 分工：心跳管巡检，cron 管准点，交互会话管操作。
- 汇报格式固定成"一行结论 + 链接"，方便扫读；清单和状态文件进 git，改动可追溯。
- 职责拆分到独立 agent：值班 agent 清单极简，主 agent 不开心跳，互不干扰。

## 总结

`HEARTBEAT.md` 本质是一个用自然语言写的巡检清单，加一个由网关驱动的定时循环。它的价值不在于"AI 会自己动了"这类叙事，而在于把"要不要打扰人"的判断交给模型，把"什么时候醒"交给配置。清单写得越像运维 SOP 就越可靠，写得越像许愿池就越费 token。建议从一条只读检查加明确静默条件的最小清单跑两周，再逐步加任务。
