# 背景

手上维护着十来个常驻服务（自建 API、几个爬虫、若干 OpenClaw agent 的定时任务），日志散在 systemd journal、应用文件和 agent 运行记录里。之前每天早上人工 grep 一遍，费时且容易漏。目标很朴素：每天固定时间，收到一份覆盖「异常、变更、关键指标」的结构化日报。

# 问题

第一直觉是写个 cron，把昨天的日志整坨塞给 agent 让它总结。试了一周就放弃了：

- 原始日志一天几百 MB，远超上下文，只能截断，截断后的「摘要」基本是随机的；
- 噪声占比高，大量重复的 INFO 行会把模型带偏；
- 输出格式每次不一样，没法对接下游脚本；
- 失败是静默的，某天没收到日报才发现流水线挂了。

结论：LLM 不适合干粗活。粗活交给确定性代码，LLM 只做最后一步精加工。

# 做法

流水线拆四层，每层落盘中间产物：

**1. 采集。** 一个 Python 脚本按来源拉取昨日日志，统一成 JSONL：`{ts, source, level, msg}`，时间戳一律存 UTC。系统 cron 触发即可，不强依赖 agent 常驻。

**2. 预处理。** 纯规则、无模型：过滤 DEBUG/INFO，按 `(source, 错误指纹)` 去重聚合，统计错误计数、Top 关键词、慢请求。输出一份几 KB 的「素材 JSON」。这一步决定了整条流水线的质量下限。

**3. 汇总。** 素材 JSON 交给 OpenClaw agent。system prompt 里写死硬约束：只允许基于素材写作、数字必须原样引用、未知字段留空不许编。输出用 JSON Schema 校验，字段固定为 `incidents / changes / metrics / suggestions`。校验失败自动重试一次，再失败降级为纯模板渲染——没有摘要，但数字准确。

**4. 投递。** 渲染成 Markdown 推到 IM 群机器人，本地按日期归档。写 `.done` 标记 + 日期幂等键，防止 cron 重叠触发时重复推送。

# 踩坑点

- **时区**：日志里混着 UTC 和本地时间，第一版日报的「昨天」算错了一天。统一 UTC 存储、渲染时转本地。
- **敏感信息**：日志里的 token、内网 IP 会原样进 prompt，补了脱敏正则才敢长期跑。
- **格式漂移**：即使有 Schema，模型偶尔在字符串里夹额外说明。Schema 校验 + 降级模板双保险。
- **幻觉数字**：早期模型会「脑补」错误率。prompt 明确数字只能来自素材，且定期抽查比对。
- **幂等**：加锁文件 + 幂等键，解决 cron 重复执行。

# 可复用建议

- 分层落盘是排障关键：出问题能立刻区分是采集漏了、过滤狠了，还是模型漂了。
- 日志来源多的话，可以把「日志查询」包成 MCP server，让 agent 按需拉取，比一次性塞文件稳。
- 报告模板字段化并带版本号，下游消费脚本才不会因为加字段而崩。
- 先跑通最小闭环（一个日志源 + 一个投递渠道），再横向扩，别一上来铺五六个来源。

# 总结

核心思路一句话：确定性代码做采集、过滤、聚合，LLM 只面对小而干净的输入做摘要和措辞。跑通之后日报稳定率接近 100%，人工介入只在调整报告结构时发生。全部实现是两个脚本加一个 skill，照着分层思路复现的门槛不高。
