## 背景

E2E 测试是大多数团队“知道该写、但一直欠债”的部分。手写 Playwright 用例成本高：要理解业务流程、调选择器、造数据，写完还要跟着 UI 改动反复修。我们在 OpenClaw 里接上 Playwright MCP 之后，尝试让 Agent 参与整个 E2E 流程，跑了一个多月，有些经验值得记录。

## 问题

直接把需求文档丢给 Agent 说“帮我写测试”，效果很差，主要有三类问题：

1. **断言很弱**：生成的用例往往只验证“页面没报错”，跑起来全绿，但什么都测不出来；
2. **选择器脆弱**：依赖 DOM 结构，`nth-child` 满天飞，UI 一改全崩；
3. **不懂业务**：边界条件（优惠券叠加、库存为 0）完全靠猜。

核心矛盾是：**Agent 缺少运行时的真实反馈**，写出来的测试是纸上谈兵。

## 做法

我们把流程改成“跑起来 → 看失败 → 自己修”的闭环：

**第一步：给 Agent 浏览器能力。** 通过 Playwright MCP 让 Agent 能打开页面、截图、读 DOM 快照和控制台日志。这是整个方案的前提，没有运行时反馈，一切退化成代码补全。

**第二步：先出测试计划，人审后再写代码。** 让 Agent 根据需求文档列出用例清单（覆盖路径 + 断言点），人工确认边界条件，然后再生成代码。这一步能拦住大部分“无效测试”。

**第三步：跑失败自己修。** Agent 执行 `npx playwright test`，失败后读取 trace 文件和截图，自行判断是选择器问题还是真实 bug：前者修复重跑，疑似 bug 则停下输出复现步骤，交给人工确认。

**第四步：约定选择器规范。** 在仓库里沉淀一份测试约定，Agent 每次生成都能读到：优先 `data-testid`、禁止 `nth-child`、公共操作封装成 Page Object。让 Agent 遵守约定，远好于事后重构。

## 踩坑点

- **全绿幻觉**：Agent 的断言倾向于“验证自己写的东西”，会出现 `expect(page.url()).toContain('/success')` 这种弱断言。要求每个用例至少一个业务级断言：金额、状态、列表条数。
- **auto-wait 掩盖问题**：自动等待会让 Agent 误以为慢接口没问题。CI 里保留超时阈值，超过 3s 的等待让 Agent 显式标记，而不是默默吞掉。
- **测试数据污染**：Agent 图省事会复用同一批测试账号，并发跑 CI 时互相干扰。约定跑前造数、跑后清理，造数脚本也交给 Agent 维护。
- **上下文超限**：大项目别让 Agent 一次理解全站，按模块拆，每次只给一个 flow 的文档加相关页面。

## 可复用建议

1. 仓库根目录放一份 `TESTING.md`，写清断言要求、选择器规范、数据管理规则，Agent 生成前必读；
2. 把 `trace.zip` 作为 Agent 的标准输入，比口头描述“登录后点了个按钮”精确得多；
3. 分工原则：**Agent 负责骨架、选择器、跑通修复；人负责断言的业务正确性**。断言错了，测试就是负资产。

## 总结

Agent 写 E2E 测试的价值不在“替你写”，而在把写测试从一次性成本变成可持续迭代的闭环。给 Agent 运行时反馈（MCP + trace），用约定约束输出，人守住断言正确性——这套组合跑下来，我们的 E2E 覆盖率从约 20% 提到 60% 以上，维护成本反而降了。工具不是重点，反馈闭环才是。
