## 背景

在 OpenClaw 这类 Agent 环境里，"这个任务只会跑一次"是个危险的假设。定时任务可能因调度器重试触发两次，Agent 调 MCP 工具可能因超时重发请求，插件脚本可能在崩溃后被人手动再跑一遍，webhook 也从不保证恰好投递一次。重复执行不是异常路径，而是常态。

幂等性指同一个操作执行一次和执行多次，最终结果一致。它不是锦上添花，而是自动化任务敢不敢放心重跑的底线。

## 问题

看一个典型的非幂等脚本：

```bash
curl -X POST https://api.example.com/subscribe
cp report.xlsx "backup/report-$(date +%F-%H%M).xlsx"
echo "synced at $(date)" >> sync.log
```

跑一次没问题。跑第二次：订阅重复创建、备份目录堆满几乎相同的文件、日志追加出第二条记录。如果任务链末端还挂着"完成后发通知"，群里会连续出现两条一模一样的消息。问题不在代码写错，而在于操作语义是"追加/新增"，而重复执行的场景天然存在。

## 做法

核心思路一句话：让"执行 N 次"收敛到与"执行 1 次"相同的状态。

1. **区分"创建"和"同步"语义。** 创建类操作（下单、发消息、注册）天然不幂等，必须引入幂等键；同步类操作（覆盖写文件、对齐配置）可以设计成幂等。
2. **用稳定键代替时间戳。** 备份文件按业务日期命名如 `report-2025-01-15.xlsx`，重跑时覆盖同一天的文件，而不是无限追加。
3. **写操作尽量用 upsert。** 数据库用 `INSERT ... ON CONFLICT DO UPDATE`；文件用"写临时路径 + 原子 rename 覆盖"；配置用"计算期望状态，直接写入"。
4. **给外部副作用挂幂等键。** 调用会创建资源的 API 时，带上由任务 ID + 业务日期派生的 key（如 `sync-2025-01-15`），由服务端去重。消息类、支付类 API 大多支持。
5. **Agent/插件侧统一约定。** 封装 MCP 工具时在参数里显式暴露 `idempotency_key`，而不是让每个调用方自己发明；执行前先查该 key 是否已完成，已完成的直接返回上次结果。

## 踩坑点

- **check-then-act 有竞态。**"先查文件是否存在，不存在才创建"在两个进程并发时会双双通过检查。条件写入或文件锁比"先查后做"可靠。
- **时间戳藏在路径里。** 最常见的翻车点：输出目录、日志文件名里带 `$(date +%s)`，重跑一次多一份垃圾。
- **通知是被忽略的副作用。** 数据操作做了幂等，"完成后发消息"没做，照样重复轰炸。通知也应 keyed by 任务 ID。
- **先删后建留空窗。** `rm config && write config` 在中间崩溃时服务直接挂掉，改成临时文件加 rename。
- **状态只存内存。** 上次跑到哪一步如果只靠脚本变量，进程一死全丢，断点信息必须落盘。

## 可复用建议

- 写任务时默认假设"它至少会被执行两次"。最便宜的验证：把脚本连跑两遍，看第二次的输出是否与第一次一致。
- 优先用"期望状态"思维：描述目标是什么，而不是要执行什么动作。前者天然可重入，后者容易叠加副作用。
- 给每个任务一个稳定 ID，贯穿日志、幂等键和通知，排查时能串成一条线。
- 确实无法幂等的操作（如只能发一次的通知），至少做到"可检测"：记录已执行清单，重跑时跳过。

## 总结

幂等性不是高级技巧，而是自动化任务的基本卫生习惯。本质是把"操作"改写成"状态对齐"：用稳定的键定位目标，用覆盖/更新代替追加/新增，把通知这类外部副作用也纳入 key 管理。做到这一步，重试、重跑、并发触发就从事故变成了无害事件——这也正是把任务放心交给 Agent 和调度器的前提。
