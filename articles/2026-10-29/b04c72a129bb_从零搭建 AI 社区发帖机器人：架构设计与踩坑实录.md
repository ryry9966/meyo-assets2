## 背景

我们社区每天要跟进的上游信息不少：几个核心仓库的 GitHub Release、issue 动态，外加零散的技术博客。以前靠人工筛选、改写、发帖，一个熟手每天要花将近一小时，还经常漏。这个月的 side project 就是把这条链路自动化：一个基于 OpenClaw Agent 的发帖机器人，采集 → 生成 → 审核 → 发布，全流程可回溯。

## 问题

最早的原型很直接：cron 拉源，把内容塞给模型，让它写完直接调发布 API。跑了一周就暴露出四类问题：

1. **重复发帖**。同一篇上游文章因为 URL 带了不同 tracking 参数，被当成两条新内容发了两次。
2. **事实性错误**。模型会"脑补"版本号和更新日期，甚至生成一个看起来很像真的、实际 404 的链接。
3. **频率失控**。某天上游集中发版，机器人一口气发了六帖，触发了社区的反垃圾阈值。
4. **问题定位难**。出事之后分不清是采集错了、生成错了还是发布错了——日志里什么都没有。

结论：不能把"决定发什么""写内容""发出去"交给模型一步做完。

## 架构与做法

重构后是五层结构：

- **采集层**：cron 定时触发，RSS 和 GitHub webhook 双通道，只抓原始数据，不做任何判断。
- **预处理层**：清洗 HTML，URL 归一化（去 tracking 参数、统一协议头和大小写），内容哈希写入 SQLite，命中即丢弃。
- **Agent 层**：OpenClaw agent 挂载三个 MCP 工具——`list_recent_posts`（查最近已发内容）、`draft_post`（生成草稿）、`publish`（发布）。工具返回全部是结构化 JSON，模型不负责"回忆"事实。
- **审核层**：草稿先入队列。前两周强制人工 approve，之后只对高置信度来源放开自动发布。
- **发布层**：社区 API 的薄封装，带幂等键（内容哈希 + 日期）、全局限流（每小时最多 2 帖）、失败退避重试。

关键取舍：限流和幂等做在发布层的代码里，而不是写在提示词里。提示词可能被忽略，代码不会。

## 踩坑点

- **URL 归一化不够狠**。除了去参数，还要处理 http/https、末尾斜杠、UTM 全家桶。多清理一轮后重复率归零。
- **幻觉链接最阴险**。后来规定：正文里的链接和版本号必须来自采集层透传的原文，模型只做摘录和改写；`publish` 工具在发布前用正则校验链接域名白名单。
- **MCP 工具描述太含糊**。早期 `publish` 的 description 只写了"发布帖子"，模型会在草稿还没过审时就调用它。改成"仅当收到已 approve 的草稿 ID 时才可调用"，误调用消失。工具描述是给模型看的接口文档，值得认真写。
- **重试导致重复**。网络超时后无脑重试，同一帖发了两次，幂等键上服务端去重后解决。
- **时区**。cron 用了容器本地时间，错过早八点窗口，改成显式 UTC+8。

## 可复用建议

1. 决策、生成、发布三层分离，每层独立可测。
2. 所有工具调用的参数和返回值落库，事后能复盘模型"为什么这么干"。
3. 上线初期保留人工审核闸门，攒两周三五十条样本再谈自动化比例。
4. 一切"不要做 X"的约束，能用代码校验就不要只写进提示词。
5. 给发布层做熔断：连续失败 N 次自动停机并告警，别让机器人带病运行。

## 总结

机器人现在稳定跑了三周，日均 1-2 帖，人工只需扫一眼草稿队列。回头看，真正的难点不在"让模型写出像样的帖子"——那反而是最简单的部分——而在工程侧的去重、幂等、限流和可观测性。Agent 项目里，模型是引擎，但决定它能不能上路的是底盘。
