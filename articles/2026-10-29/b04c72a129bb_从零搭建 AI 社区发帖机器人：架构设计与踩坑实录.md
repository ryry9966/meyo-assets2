## 背景

我负责一个技术社区的日常运营，每天的内容精选帖之前全靠手工：翻信息源、挑条目、写摘要、发帖，一轮下来 40–60 分钟。这次动手的目标很明确——不是做"无人值守的全自动"，而是把人工压缩到"一次确认"。技术栈就是手头现成的：OpenClaw 定时任务 + 两个 MCP 工具 + 一个强制的审核环节。

## 问题

拆开来是三件事：

1. **采集要稳**：RSS 和论坛 API 的时间戳、失败重试、增量去重；
2. **质量要控**：LLM 写摘要容易编造链接、夸大总结，不能直接往外发；
3. **发布要安全**：频率、重复内容、以及机器人和自己互动的风险。

## 做法

最终架构是三段式，段与段之间硬切断：

- **采集层**：cron 触发 OpenClaw 定时任务，调 MCP fetch 工具拉源，原始条目写 JSONL，另用一个状态文件记录"上次处理时间"。
- **生成层**：独立的第二次 Agent 运行，读待处理条目，按固定模板产出**草稿帖**。标题、链接、作者全部来自原始数据，模型只负责摘要文字。
- **发布层**：草稿先落"待审目录"，我用 `/approve` 命令确认后才调 MCP 发帖工具；只有"纯链接聚合"这类低风险模板走白名单自动发。

核心设计就一句：**生成和发布是两个进程，审核门禁强制存在**。看起来不够酷，但它救过我。

状态结构压到最简：

```json
{"item_id": "...", "status": "pending|approved|posted", "dedup_hash": "..."}
```

## 踩坑点

1. **机器人转发了自己**。上线第一周，采集层把机器人自己发的精选帖抓回来当成了信息源，第二天它给自己写的摘要做了摘要，信息反馈回路放大噪声。修法：发帖内容打身份标记，采集层硬过滤。
2. **模型编造链接**。早期让 LLM 顺带输出"来源链接"，十次里约一次是幻觉 URL。修法：永远不让模型产出事实字段，链接由模板从原始数据注入。
3. **幂等**。一次任务重试导致同一条目发了两遍。修法：dedup_hash（标题 + URL 哈希）贯穿全流程，发布前强校验。
4. **时区**。cron 按本地时间写，服务器迁移后精选帖时间漂了 8 小时。修法：调度统一按 UTC 存储计算。
5. **静默失败**。fetch 工具抛错没人看见，精选帖断了三天才发现。修法：失败写死信文件并触发通知，让"没有产出"本身变成可监控的信号。

## 可复用建议

- 先跑一周 **dry-run**，所有产出只进日志不进社区，观察误报率再放行；
- 审核门禁别省，自动发布最多开放给低风险模板；
- 幂等键、死信处理、结构化日志三个 Hygiene 项第一天就做，事后补很痛；
- Prompt 做成带版本号的文件模板，风格跑偏时能回溯是哪次改动；
- 发布层加限速：最小间隔 + 每日上限，比事后删帖便宜得多。

## 总结

这版机器人最终形态并不花哨：一个 cron 触发、两次 MCP 调用、一次人工确认，代码三百行以内，日常维护时间从一小时降到五分钟左右。最大的体会是：Agent 流水线的价值不在于"替代人"，而在于把人的参与收敛到唯一必须由人做的判断——"这条该不该发"。把这一步守住，其余交给流程。
