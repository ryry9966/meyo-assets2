## 背景

用 Agent 干活的人大概都有类似体验：每次新会话都要重新交代一遍——"commit message 用中文""部署先走 staging""别用 tab 缩进"。这些偏好非常稳定，但模型本身无状态，会话一断就归零。

多数人的第一反应是把偏好塞进 system prompt 或全局配置文件。能解决一部分，但用户、项目、场景一多，就变成没人维护的长文本堆。真正的问题不是"记不记"，而是记忆的写入、存储、检索、更新这条链路怎么设计。这篇贴分享我在 OpenClaw 里用插件 + MCP 工具落地的一套方案。

## 问题：常见的几种失败形态

- **全量塞上下文**：记忆越堆越多，token 成本上升，关键指令反而被稀释。
- **只有会话内记忆**：换个会话就失忆，等于没记。
- **自动提取太激进**：用户随口一句抱怨也被存成"偏好"，噪音持续累积。
- **没有更新机制**：半年前的旧偏好和新偏好冲突，Agent 行为飘忽。

## 做法

**1. 分层。** 工作记忆（会话上下文，不用管）；偏好记忆（结构化 KV，核心层，每条含 key、value、scope、updated_at、source）；情景记忆（可选，历史任务摘要，向量化存储，按需检索）。

**2. 写入要保守。** 不要后台默默全量提取。两种触发：显式（用户说"记住/以后都这样"）；隐式（同一模式出现 ≥3 次才写）。写入前过一道敏感信息过滤，密码、token 直接丢弃。

**3. 存储结构化优于自由文本。** SQLite 一张表就够，别急着上向量库。偏好是少而稳定的条目，只有结构化存储才能支持编辑、去重、冲突处理。情景记忆再考虑 embedding。

**4. 读取分时机。** 会话启动时按 scope 匹配注入，设 token 预算（比如 500），按命中度和 updated_at 排序取 top-K。任务中途涉及部署、发版这类动作时，再检索一次相关记忆。

**5. 更新留痕。** 同 key 新写入默认覆盖旧值，保留最近一两版历史。值差异明显时宁可抛回给用户确认，别静默覆盖。

**6. 用户可控。** 提供 memory_list / memory_edit / memory_delete 命令。记忆系统想被信任，前提是用户看得见、改得动、删得掉。

## 踩坑点

- **写入门槛太低是最大噪音源。** 宁可漏记，不要错记——漏了用户会再说一遍，错了用户未必发现。
- **只在启动时注入不够。** 实测中途检索能解决大半"它明明记得却不用"的问题。
- **必须有 debug 手段**：能打印本次实际注入了哪些记忆，否则排查行为异常全靠猜。
- **隐私过滤放在写入侧**，别指望读取侧兜底。

## 可复用建议

- 先覆盖 5–10 类高频偏好就够：输出语言、代码风格、commit 规范、常用路径、回复详略。
- 元数据（来源/时间/置信度）第一天就设计进表结构，后补很痛苦。
- 把记忆封装成独立 MCP 工具（memory_write / memory_search），换 Agent 框架时迁移成本最低。

## 总结

Agent 记忆不是一个"功能"，而是一个数据工程问题：写入保守、存储结构化、检索分时机、更新留痕、控制权在用户手里。先跑通小而准的偏好集，验证整条链路，再考虑向量化、遗忘曲线这些进阶话题。欢迎在评论区交流你们落地时遇到的检索和冲突处理问题。
