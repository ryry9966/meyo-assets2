## 背景

用 OpenClaw 做自动化任务一段时间后，最明显的瓶颈不是模型能力，而是串行执行。主 agent 在一个循环里"取数 → 整理 → 写报告 → 取下一组"，一轮任务跑十几分钟是常态。subagent 机制允许主 agent 把任务派发给多个子 agent 并行处理，听起来很美好，但真正跑起来才发现：并行不是"多开几个就快了"，编排本身有自己的工程问题。

## 问题

最早我直接在提示里写"遇到多个独立任务就并行开 subagent"，结果踩了三类坑：

1. subagent 拿不到主对话上下文，输出答非所问；
2. 两个 subagent 同时往同一个文件写数据，互相覆盖；
3. 并发一高，MCP 工具调用触发限流，整批任务一起失败。

核心矛盾在于：subagent 是"失忆的新员工"，你给它什么上下文它才知道什么；而文件、MCP server、API 配额这些资源是共享的，不隔离就会打架。

## 做法

跑顺之后，我沉淀出一套步骤：

1. **先做任务切分判断。** 只有满足"任务间无共享可变状态、每个任务能独立描述完整"才拆。扫描三个不同数据源的日报、对多个目录分别做代码审查，适合拆；单文档多角度修改，不适合。
2. **给每个 subagent 写自包含的 prompt。** 文件路径、期望输出格式、边界条件全部写进子任务描述，默认它什么都不知道。
3. **收窄工具范围。** subagent 只挂它需要的 MCP 工具，能只读就不给写权限。
4. **约定结构化返回。** 要求 subagent 返回固定 JSON 加三行以内摘要，避免子结果把主上下文撑爆。
5. **控制并发。** 从 2–3 个起步，跑稳再加。每个子任务设超时，失败重试一次，仍失败就降级为主 agent 串行补跑。
6. **写操作收敛到主 agent。** subagent 只在各自独立的工作目录产出中间结果，最终落盘由主 agent 统一执行。

## 踩坑点

- **上下文传递成本被低估。** 主 agent 组装子任务 prompt 本身就消耗不少 token，任务太小不划算。我的经验阈值：单个子任务预期超过主 agent 两轮以上的工作量，才值得拆。
- **git 工作区是典型共享资源。** 多个 subagent 在同一工作区跑 git，index 冲突极难排查。现在统一给每个 subagent 分配独立临时目录。
- **MCP server 大多不是为并发设计的。** 有的 server 内部是串行队列，开八个 subagent 吞吐不变，还更容易超时。并行前先确认 server 端的并发能力。
- **失败传播。** 一个 subagent 卡死且没有超时，整个编排就挂起。超时和"接受部分结果"必须显式写进编排逻辑，不能靠默认行为。

## 可复用建议

- 并行前先问一句：这些任务共享什么？共享的都要隔离或收敛。
- 子任务 prompt 当接口文档写，宁多勿少。
- 汇总层保持薄：主 agent 只做合并和最终写操作。
- 并发数、超时、重试是三个必须显式配置的参数。
- 算一笔账：拆分收益 = 并行省下的时间 − 上下文组装成本 − 排障成本，算不过来就别拆。

## 总结

subagent 编排的本质不是"更多 AI"，而是把并发工程的老问题——资源隔离、接口契约、失败处理——搬到 agent 场景里重新做一遍。我的体感：收益最大的场景是"多数据源批量采集 + 结构化汇总"，提速约 3 倍且质量不降；收益最差的是任务切得太碎、组装成本反超并行收益的场景。先串行跑通，找到瓶颈再拆并行，比一上来就堆复杂编排靠谱得多。欢迎大家补充自己的并发参数和 MCP 限流经验。
