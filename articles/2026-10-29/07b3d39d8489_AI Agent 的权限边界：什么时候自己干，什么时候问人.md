## 背景

跑过一段时间 OpenClaw 的人大概都遇到过类似时刻：给 Agent 接上 MCP 工具、shell、定时任务之后，某天它自作主张做了一件你没预期的事——把未整理的草稿直接发进了群里，或者在工作区外动了不该动的文件。这时你会意识到：工具接得越多，"它到底能自己干到哪一步"这个问题越重要。

## 问题

实践中两个极端都不好用：

- **全放权**：Agent 执行力很强，但一次不可逆操作（删除、外发、花钱）就足以摧毁信任；
- **全审批**：每步都问，人沦为橡皮图章，三天后看到弹窗就无脑确认，审批形同虚设。

所以真正要解决的不是"要不要问"，而是**问的时机和问的质量**。

## 做法：三个维度，四层权限

判断一类操作该不该自动执行，我习惯看三个维度：

1. **可逆性**：能否一键撤销？git revert 和 rm -rf 是两个世界。
2. **影响半径**：只影响本地工作区，还是触达外部（别人会看到、会花钱、会改线上）？
3. **是否在场**：是交互式会话，还是 cron/心跳触发的无人值守任务？

据此分四层：

- **L0 只读查询**：本地搜索、读文件、查状态。直接放行。
- **L1 可逆的本地写入**：工作区内建文件、写草稿、改配置。放行，但全部落日志。
- **L2 难撤销或对外可见**：git push、发消息、装依赖。默认先问；高频场景可以预声明规则（如"每天 9 点生成日报草稿，发不发送等我确认"），把"每次问"变成"草稿放行、卡住最后一步"。
- **L3 高危**：花钱、批量删除、动凭据、动生产环境。永远人工确认，无人值守直接禁用。

落地的关键：**卡在最后一个不可逆动作上，而不是每一步**。一个十步任务里前九步都可以自动跑，第十步要 push 才停下来问。

## 踩坑点

- **审批疲劳**：问得太多，人就开始盲批。宁可收窄 L2 清单，也要保证"它开口时你真的会看"。
- **无效确认**：只弹一句"可以继续吗？"等于没问。每次询问必须带具体内容：完整命令、diff、收件人。看不到细节的确认就是在替 Agent 背锅。
- **权限只增不减**：为省事临时加的放行规则，加了就没人删。建议每月过一遍 allowlist，清掉一个月没用过的条目。
- **只读不等于无害**：读 + 发的组合本质上是泄露。Agent 能读凭据文件、又能发消息，两条边界各自合法，合起来就是事故。边界要按"操作组合"设计。
- **无人值守沿用交互权限**：定时任务应该用最保守的一档配置——出问题时你不在场。

## 可复用建议

- 默认策略一句话：**可逆 + 本地 → 放行；不可逆 或 触达外部 → 先问**。
- 所有询问带预览，所有执行落日志，每周翻一遍日志比事后追责有用得多。
- 重复出现的审批，尽早固化成预声明规则，减少弹窗数量。
- L3 操作宁可打断工作流，也不要提供"下次默认同意"的选项。

## 总结

权限边界不是一条线，而是可逆性、影响半径、是否在场三个变量算出来的函数。目标不是让 Agent 更听话或更自由，而是让"它开口问"这件事保持足够稀缺、足够有信息量——这样每一次询问才是真正的人在决策，而不是橡皮图章。建议从最保守配置起步，再根据日志证据逐步放宽。
