# 背景

OpenClaw 这类常驻本机的 Agent，干活靠的是一组 CLI/API 工具：跑命令、改文件、调接口。工具自带的描述是通用的，但每台机器的现实并不通用——包管理器、运行时版本、路径约定、代理、容器化与否，全都不一样。

tools.md 的定位很朴素：一份 Agent 会读取的文档，专门记录"这台机器上怎么干活"。它不是工具说明书，而是本机环境的事实清单。

# 问题

几个典型翻车场景：

- 机器用 brew，Agent 却给出 apt 命令；系统只有 `python3`，它非要调 `python`。
- 本机走公司代理，Agent 下载依赖一直超时，但它不知道原因。
- 同一个任务，在公司电脑和家庭电脑上表现不一致，每次都要口头纠正。
- 纠正方式散落在聊天记录里，换个会话就丢，换台机器更没法复现。

这些问题的共性：环境知识只存在于人的脑子里和聊天上下文里，没有落到一个稳定、可版本化的地方。

# 做法

1. **先盘点，再动笔。** 跑一组探测命令把事实收齐：`node -v`、`python3 --version`、`which brew apt`、`echo $HTTP_PROXY`、docker 是否在跑。别凭记忆写。
2. **按"本机差异"组织内容。** 建议分节：包管理、运行时、路径约定、网络、已知限制。每条一行，尽量带上验证命令，让 Agent 能自查而不是猜。
3. **分层管理。** 全局一份（用户级，跨项目通用），项目仓库里一份（覆盖全局）。优先级明确：项目 > 全局。项目里写"这个仓库用 pnpm、Node 20"，全局里写"本机用 brew、代理地址是 X"。
4. **失败驱动迭代。** Agent 每次用错，就把正确做法补一条进 tools.md，而不是只在对话里纠正一次。一两周后，重复翻车会明显减少。
5. **入版本库，注意脱敏。** 和 dotfiles 一起管理，多机同步；提交前检查没有密钥。

# 踩坑点

- **别把密钥、token 写进去。** tools.md 会进模型上下文，等于明文上报。
- **别复述工具文档。** 只写"这台机器和默认假设不一样的地方"，否则上下文预算全浪费了。
- **控制长度。** 几十行以内为宜，过期条目果断删。我见过 300 行的 tools.md，Agent 反而抓不住重点。
- **保持单一事实源。** AGENTS.md、README、tools.md 三处说法冲突时，Agent 行为会不稳定。环境事实归 tools.md，协作规范归 AGENTS.md。
- **改动后验证一次。** 别假设它每次都重新读取，明确让它按新配置重跑一个典型任务确认。

# 可复用建议

一个简单的判断标准：**如果这条事实换台机器就不成立，它就该进 tools.md；如果放哪台机器都成立，进 AGENTS.md。** 按这个标准写，两份文档不会越长越乱。

另外给 tools.md 标一个更新日期，每月 review 一次，删掉已经不成立的条目——环境会漂移，文档不跟着漂移就会变成误导源。

# 总结

tools.md 的价值，是把"口口相传的本机经验"变成声明式、可版本化、可复现的配置。投入很小，换来的是 Agent 在不同机器、不同会话里行为的一致性。如果你的 Agent 已经稳定运行，花半小时写第一版 tools.md，大概率是本月性价比最高的一次配置。
