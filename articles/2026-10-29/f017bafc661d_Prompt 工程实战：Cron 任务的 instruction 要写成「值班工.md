## 背景

OpenClaw 的 cron 任务本质上就两件事：定时唤醒，加一段 instruction。agent 在一个隔离会话里醒来，执行你写的那段话，把结果投递到指定 channel。听起来简单，但群里常见的写法是一句「每天早上汇总一下 HN 热点发给我」，跑起来时好时坏。这篇把我自己踩过的坑和现在稳定运行的任务写法整理出来。

## 问题

cron instruction 和对话 prompt 有一个根本区别：**没有上下文**。对话里你可以说「继续刚才的」，agent 知道「刚才」指什么；cron 里 agent 醒来时手里只有你写的那几行字。所有靠「默契」的部分——指代、时间、格式、失败兜底——全都会变成随机数。

典型症状：

- 输出格式每次不一样，有时一条消息，有时刷屏十条
- 「今天」算错日期，因为 agent 在猜时间
- 数据源挂了，agent 用记忆里的旧信息编一份看起来合理的假数据
- 换设备或换 session 后，同一个任务行为完全变了

## 做法：五段式模板

写 instruction 时，把它当成交给一位**不知情值班同事的工单**，五段写全：

```text
[任务类型] 定时任务，每天 08:30，Asia/Shanghai。
先用工具获取当前日期，不要自行推断。

[目标] 汇总 microsoft/vscode 仓库过去 24 小时的
release 和新增高赞 issue。

[数据源] 使用 github MCP 工具查询，不要依赖训练记忆。

[输出] 投递到 Telegram；不超过 6 条要点，每条一行；
无更新则只回复「今日无更新」。

[异常] 任一步失败：回复失败原因，不要编造内容，不要静默。
```

写完对照三问：agent 醒来时知道今天几号吗？知道去哪拿数据吗？拿不到数据时该说什么？任何一问答不上来，就往对应段落里补。

## 踩坑点

1. **时区**。cron 表达式按宿主机时区触发，instruction 里的「今天」又是 agent 自己理解——两头都可能出错。明确写时区，并要求用 `date` 命令或工具获取当前时间。
2. **指代依赖**。「上次说的那个项目」「我关注的那个仓库」在隔离会话里无法解析。仓库名、路径、频道 ID 全部写死在 instruction 里。
3. **输出失控**。IM 渠道里长输出会被截断或刷屏。给硬性约束：条数上限、单行长度、空结果时的固定回复。
4. **失败编造**。最危险的一条。不写兜底，agent 倾向于「把任务完成」，抓取失败时会拿旧记忆凑数。必须明确「失败就报失败」。
5. **频率与成本**。每 10 分钟跑一次的监控任务，每次都是完整的 agent 调用。先用低频率验证效果，再按需加密。

## 可复用建议

- instruction 存文件、进 git，改版留记录。任务「腐化」（数据源改版、接口变动）时方便回溯。
- 新任务先手动触发一次再挂 cron，确认输出格式和数据源都正常。
- 同类任务抽成模板，每次只改「目标」和「数据源」两段。
- 密钥和敏感信息不要写进 instruction，走环境变量或凭据配置。
- 每季度 review 一遍在跑的任务，删掉已经没人看的通知。

## 总结

cron instruction 的质量直接决定定时任务能不能从「时好时坏」变成「可以依赖」。核心就一句话：**写给一个没有记忆、必须照章办事的值班员，而不是给一个心有灵犀的助理**。时间基准、目标边界、数据源、输出格式、失败路径——五段写全，剩下的交给 cron。
