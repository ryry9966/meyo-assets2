## 背景

让 Agent 直接操作文件系统，是自动化收益最大、也最让人手心出汗的场景。模型本身并不"想"删文件，风险来自两点：一是它可能对路径和上下文产生误判，二是我们常常给了它远超任务所需的工具权限。OpenClaw 的设计立场很明确：安全边界不应建立在"模型这次应该不会犯错"上，而应建立在运行时的强制约束上。

## 问题：误删是怎么发生的

复盘常见的故障，误删几乎都不是"模型发疯"，而是几个平淡的工程失误叠加：

- **相对路径歧义**：Agent 在错误的 cwd 下执行了清理命令；
- **权限过宽**：为了让任务跑通，直接把整个 HOME 挂给了文件工具；
- **软链接逃逸**：workspace 里的 symlink 指向外部目录，删除跟随链接穿透；
- **插件旁路**：某个 MCP 插件自带 shell 能力，绕过了文件工具的白名单。

## 做法：四层防线

OpenClaw 的 sandbox 是分层生效的，缺一层都会留下口子：

1. **Workspace jail**。所有文件工具的路径参数先做规范化，再强制约束在 workspace 根目录内。绝对路径、`..` 回溯、符号链接展开后越界的请求会被直接拒绝，并记入审计日志。
2. **读写分离**。workspace 内可再声明只读区（如参考资料、`.git`）。写入类工具碰到只读路径会失败，读取不受影响。
3. **破坏性命令拦截与审批**。shell 工具对匹配到高危模式的操作（递归删除、批量覆盖、磁盘与权限类命令）默认挂起，转人工确认；确认动作本身同样写入审计记录。
4. **工具级作用域**。每个 MCP server / 插件只拿到任务声明的工具子集，并继承同一个 sandbox 上下文——不存在"插件自带免检通道"。

配置示例（字段名以所用版本文档为准）：

```yaml
sandbox:
  root: ./workspace
  read_only: [./workspace/reference, ./.git]
  deny_globs: ["~/.ssh/**"]
  destructive_confirm: true
```

## 踩坑点

- **路径规范化时机**：校验必须在 symlink 解析之后做，否则等于没校验。
- **审批疲劳**：拦截规则太宽，人很快会变成无脑点确认。把审批收紧到真正高危的模式上。
- **插件隐式 shell**：有的插件会通过子进程调命令，接入前先审它的工具清单，别只看声明的能力。
- **没开快照**：sandbox 防的是误操作，不是备份。快照 / 回收站机制要单独启用并定期演练恢复。

## 可复用建议

- 按任务最小授权，宁可多跑几轮补授权，也不要开一个万能 workspace。
- 用金丝雀文件做演练：放几个诱饵文件，观察 Agent 的删除行为和被拒日志。
- 把审计日志接入日常告警，"越界请求被拒"是比成功记录更有价值的信号。
- sandbox 配置纳入版本管理，和 prompt 一起 review，改动要有 commit 记录。

## 总结

"Agent 不会误删文件"，不是因为模型更聪明了，而是因为错误路径上的每一步都被运行时拦下：越界路径被拒、只读区写不进、高危命令等人确认、插件拿不到多余权限。信任模型的能力，验证系统的边界——这是 OpenClaw sandbox 模型给出的答案，也适用于所有 Agent 工程实践。
