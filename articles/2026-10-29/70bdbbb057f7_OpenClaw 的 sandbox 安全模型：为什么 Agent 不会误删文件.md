## 背景

给 Agent 接上 exec 和文件工具之后，第一件事不是让它干活，而是问自己一个问题：它如果执行了 `rm -rf`，我会损失什么？在 OpenClaw 的默认配置下，答案应该是"几乎没有"。这不是靠模型自觉，而是靠一套分层的 sandbox 设计。这篇帖子把这套模型拆开讲清楚。

## 问题：提示词不是安全边界

很多人第一反应是在 system prompt 里写"请不要删除文件"。这在工程上是不成立的：

- 模型输出是非确定性的，长会话中行为会漂移；
- Agent 处理外部内容（网页、消息、文档）时可能遭遇提示注入，"删除文件"的指令可能来自数据而不是用户；
- 提示词约束没有强制力，一次越界就是事故。

结论很简单：**安全必须由执行环境保证，不能由模型保证**。

## OpenClaw 的四层防线

1. **Workspace 边界**：文件工具的访问范围默认锁定在 workspace 内。关键细节是——路径检查发生在 `realpath` 解析之后，也就是先展开软链接再判断是否越界，越界直接拒绝。这挡住了绝大多数"顺着符号链接跳出去"的路径。
2. **Docker sandbox**：Agent 进程运行在容器中，workspace 以 bind mount 挂入，容器外文件系统不可见。可进一步配置只读挂载、非 root 用户、关闭容器网络。
3. **工具策略与审批**：exec 这类高危工具走 approvals 机制，配合命令 allowlist/denylist。策略写在配置文件里，而不是靠每次对话口头约束。
4. **审计与快照**：写操作留日志；workspace 建议纳入 git，任何破坏性操作都可回滚。

四层是叠加关系：即使模型"想"删文件，它在第一层就会被路径检查拦下；即使配置失误漏了一层，后面还有兜底。

## 实操步骤

1. 启用 Docker sandbox，确认 agent 进程以非 root 运行；
2. 把不需要写入的资料目录挂成只读；
3. 在工具策略里对 exec 设置审批 + 命令白名单，先收紧再逐步放开；
4. 做一次破坏性演练：在一个可丢弃目录里让 Agent 执行删除，观察拦截日志，确认防线真实生效。没验证过的安全配置等于没有配置。

## 踩坑点

- **软链接逃逸**：workspace 里放了一个指向 `$HOME` 的软链，旧版实现按字面路径检查导致越界。务必确认你的版本是 realpath 之后再做边界判断。
- **挂载过宽**：把整个 `$HOME` 挂进容器，sandbox 形同虚设。挂载粒度最小化。
- **审批疲劳**：图省事把 approvals 设成 always-allow，第三层防线直接报废。审批提示要认真读，尤其是长会话里突然出现的删除类命令。
- **容器内 root**：即使文件系统隔离了，root 用户仍可能在挂载点上做超出预期的事。
- **上下文漂移**：长任务中模型会逐步"合理化"危险操作。这恰恰说明防线不能建立在模型判断上。

## 可复用建议

- **分级 workspace**：可丢弃实验区 / 只读资料区 / git 管理的产出区，三类分开挂载；
- **快照优先**：让 Agent 动手前先 commit，回滚成本决定事故成本；
- **定期演练**：每次升级配置后重跑破坏性测试；
- **审计日志落宿主机**：容器可丢弃，日志不能丢。

## 总结

"Agent 不会误删文件"的正确表述是：即使 Agent 试图误删，执行环境也会让它失败。OpenClaw 的 sandbox 模型本质是纵深防御——路径边界、容器隔离、工具审批、快照回滚，四层各自独立，互为兜底。把安全当配置问题而不是提示词问题，Agent 才敢放心让它干活。
