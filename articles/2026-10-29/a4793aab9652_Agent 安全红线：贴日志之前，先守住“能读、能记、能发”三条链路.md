## 背景

OpenClaw 这类常驻 Agent 的特点是权限大、记忆久、出口多：能读工作区文件，有长期 memory，还能通过消息通道对外发言。效率之外，这条链路也有一个容易被忽视的后果——当我们在社区贴日志、发配置、求助排障时，工作流细节和内部信息可能顺着它一起出门。这篇不谈宏大叙事，只聊社区场景里可执行的几条红线。

## 三条典型泄露路径

1. **贴日志带出上下文**。排障时把完整会话记录贴进社区，里面可能有内部 URL、含用户名的绝对路径、memory 摘要，甚至上一轮“顺便”处理的敏感事项。
2. **配置里留了凭证**。分享 MCP/插件配置求教，JSON 里还挂着真实 token、内网域名和本机挂载路径。
3. **Agent 自己当传声筒**。让它“帮我把这个问题整理成帖子”，它会把 memory 和工作区摘要一起打包进上下文，产出的“求助帖”里混着内部信息。

一个关键认知：**工具返回的内容会进入上下文，而上下文会被复述**。一个返回完整文件内容的 MCP 工具，等于把密钥送进了对话历史。

## 做法：分四层收口

**第一层：收窄可读范围。** `.env`、密钥、客户数据不要放进 agent 工作区；单独建一个“对外调试”目录，只放脱敏后的最小复现。exec/读文件类工具按需开启，不图方便全开。

**第二层：管住出口。** 消息通道分级：能对外发言的通道只挂只读或低敏工具；“读外部内容 + 对外发消息”这类组合必须人工确认，不给注入链路留通道。群聊场景尤其要限制可触发的人群。

**第三层：脱敏再发帖。** 贴任何东西前过一遍固定检查：凭证、内网域名、绝对路径、memory 摘要、会话上下文。建议写个小脚本，用正则扫常见凭证格式（`sk-`、`Bearer`、`AKIA` 等），比肉眼可靠。

**第四层：MCP 与插件按不可信对待。** 第三方 server 最小授权、尽量只读；token 按 server 分发，不复用一个主密钥；定期 review 已装插件的权限范围。

## 踩坑点

- **换了 token 却留下内网域名和路径**。路径里的用户名、目录结构本身就是信息。
- **以为“测试配置”没 secrets**，实际是从旧项目复制来的真 key。
- **memory 是慢性泄露源**。它会自动沉淀会话摘要，几个月不清就什么都有。密钥永远写进环境变量或密钥管理工具，不进 memory。
- **截图不等于脱敏**。侧边栏文件树、标签页标题经常带敏感路径。
- **代码块不提供任何保护**，贴出去就是公开。

## 可复用建议

发帖前五问：这份日志里有没有凭证？有没有内网地址和绝对路径？有没有 memory 或上下文摘要？最小复现能不能再小一点？这条内容被搜索引擎收录，我会不会难受？

再加一个习惯：**社区求助用“公共沙盒工作区”**——一个没有任何敏感内容的干净目录，专门用来复现问题、生成贴文素材。成本几乎为零，红线基本就守住了。

## 总结

Agent 泄露通常不是模型“不听话”，而是权限、记忆、出口三条链路里至少一条没收紧。把“能读什么、能记住什么、能发出什么”当成三个独立开关来管理，配合发帖前的脱敏流程，大部分风险在动手之前就消掉了。安全不是加一道墙，而是把默认值改对。
