## 背景

OpenClaw 跑了一段时间后，大多数人会撞上同一条成本曲线：所有任务都走云端旗舰模型，账单线性上涨，而 Agent 的请求里很大一部分是低价值调用——定时摘要、消息分类、日志整理、格式转换。反过来，全部换成本地模型（Ollama / LM Studio / vLLM 都行）后，成本和隐私问题解决了，但复杂任务的失败率明显上升。多模型路由就是在两头之间找平衡。

## 问题

我的场景：一个 7×24 挂着的 OpenClaw 实例，接了几个 channel、十几个 cron 任务和若干 MCP 工具。统计两周调用记录后发现：约 70% 的请求是摘要、分类、抽取类轻任务，30% 是规划、写代码、长上下文分析类重任务。全走 GPT 级模型，成本高且私有数据全送出去了；全走本地 7B 模型，重任务经常在工具调用环节断链。

## 做法

我的配置思路是三条：

1. **按 agent 分模型**。OpenClaw 支持给每个 agent 单独指定 model。重 agent（coding、planning）固定云端旗舰；轻 agent（digest、triage、格式化）固定本地模型。只做这一刀，成本就降了一半以上。
2. **配置 fallback 链**。在 models 配置里把本地模型作为云端的降级项：云端限流或网络抖动时，轻任务可以无缝落到本地；重任务宁可失败也不降级，避免拿到一份“看起来能用、其实质量很差”的输出。
3. **规则路由优先于模型路由**。不要用 LLM 来决定走哪个模型——那等于每次请求多付一次推理。用任务类型、channel、token 长度这些确定性信号在配置里写规则，可版本化、可回滚。

配置层面就是把两个 OpenAI 兼容端点（一个云厂商、一个本地推理服务）挂进 providers，再在各 agents 里分别引用，没有更黑魔法的东西。

## 踩坑点

- **本地模型 context 默认值太小**。Ollama 默认上下文窗口很小，Agent 的 transcript 一长就被静默截断，表现为“模型突然失忆”。显式把 num_ctx 开到 transcript 长度以上。
- **小模型的 tool call 不稳定**。不是所有本地模型都可靠支持 function calling，格式错误会让 MCP 工具调用直接失败。选型时先单独压测工具调用，别只看聊天效果。
- **静默降级**。fallback 触发时用户无感知，但质量在下降。务必在日志里记录实际服务的模型名，定期对账。
- **重任务降级比失败更贵**。重任务落到弱模型，输出看似合理实则错误，排查成本远高于一次云端调用费用。

## 可复用建议

- 从两档开始（一个旗舰 + 一个本地小模型），不要一上来搭三四层路由。
- 路由规则写进配置仓库，跟着代码一起 review。
- 每类任务记录“模型 / 耗时 / token / 成功率”四项指标，用数据决定哪类任务还能继续下沉到本地。
- 本地模型固定版本。模型一升级行为就变，所有路由阈值都得重测。

## 总结

多模型路由的本质不是省钱技巧，而是给不同价值的任务匹配不同成本的算力：硬推理和长上下文交给云端旗舰，高频轻任务和敏感数据留给本地模型。先用最简单的规则路由跑起来，再用日志驱动调整。这条路径在我们实例上把月成本压到原来的三分之一，重任务成功率没有变化——先跑通，再优化，别倒过来。
