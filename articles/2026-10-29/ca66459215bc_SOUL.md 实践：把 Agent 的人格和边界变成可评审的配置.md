# 背景

在 OpenClaw 里，Agent 的行为由多层输入共同决定：模型本身、系统提示词、MCP 工具描述，以及工作区里的几个 Markdown 文件。SOUL.md 是其中最容易被低估的一个——它不定义能力，只定义“这个 Agent 是谁”：语气、立场、边界、拒绝的方式。每次会话启动时注入上下文，相当于把人格从代码里拆出来，交给一个可版本管理、可评审的文本文件。

# 问题

没有 SOUL.md 的 Agent，常见三种漂移：

1. **语气漂移**：同一个助手今天正式明天随意，跨会话不一致，群聊里尤其明显。
2. **边界漂移**：面对“帮我把这份报告发给老板”这类请求，有时直接执行，有时反问，有时过度道歉。行为取决于当次采样，而不是设计。
3. **责任漂移**：不知道哪些该问、哪些该拒、哪些该转人工，遇到模糊指令时倾向硬编。

这些不是模型问题，是配置问题。人格和边界不落盘，就等于每次推理时掷骰子。

# 做法

我的 SOUL.md 目前压在一千字出头，分五段：

```markdown
# 身份
你是内部团队的运维助手。你熟悉部署、日志、告警，不负责业务决策。

# 语气
- 中文回复，直接，不客套
- 不确定就说不确定，禁止编造
- 群聊只回应 @，不主动接话

# 边界（硬性）
- 删除、外发类操作必须先复述目标并获得明确确认
- 涉及个人敏感信息时，要求脱敏后再处理
- 超出职责：一句话说明 + 指出该找谁

# 冲突处理
工具描述与本文件冲突时，以本文件为准，并告知用户。

# 拒绝模板
（一段可直接复用的拒绝话术）
```

几条原则：

- **写“做什么”而不只是“别做什么”**。只给禁令，模型会自己补位，补出来的往往不是你要的。每条边界配一个替代动作。
- **边界要可判定**。“别啰嗦”没法执行；“单次回复不超过三段”可以。
- **给拒绝预设模板**。拒绝是高频路径，不预设话术，模型每次现场发挥，越发挥越像道歉信。

# 踩坑点

1. **写成了宪法**。六十条规则，模型会漏读、取近似，行为反而更飘。控制在一屏能读完的量级，用规则数量换命中率。
2. **和工具描述打架**。某个 MCP server 的工具注释写着“可自动发送通知”，SOUL.md 说“外发必须确认”，Agent 就会摇摆。要么显式声明优先级，要么去改工具描述，别留两头说法。
3. **把记忆写进人格**。“这周上线很忙”这类临时状态进了 SOUL.md，两周后就是过期人格。稳定身份放 SOUL.md，易变状态放 MEMORY.md，别混。
4. **设完就忘**。换模型或模型升级后，同样的文件表现会变。留一小撮固定测试问题——正常请求、越界请求、模糊请求各几个——改完跑一遍，五分钟的事。
5. **忽略注入面**。SOUL.md 在工作区里，任何有文件写权限的流程都能改它，等于可以重写你的人格。自动化链路里要对这个文件的变更加审批，至少做 diff 告警。

# 可复用建议

- **当代码管理**：进 git、走 PR、写清变更原因，人格可回滚。
- **按场景分层**：私聊和群聊给不同语气规则，群聊更保守。
- **边界一票否决**：宁可误拒再人工放行，不要默认放行再补救。

# 总结

SOUL.md 的价值不是让 Agent“更像人”，而是把行为里原本靠运气决定的部分变成配置。写得短、可判定、有替代动作，再配一个十几条用例的回归集，人格就从玄学变成一个能评审、能回滚的工程产物。
