## 背景

跑自动化的人都有一个共识：Agent 链路里最不稳定的部分，往往不是模型，而是外部依赖——搜索 API、天气接口、企业内部服务、MCP 工具后面包着的各种第三方。本地脚本挂了你第一时间能看到，但一个无人值守跑了六小时的定时 Agent，中间某个 API 抖了两次，结果可能就是静默产出一份靠幻觉补全的报告。

## 问题

外部 API 的故障形态很杂：

- 限流（429）和临时性 5xx，属于"等等就好"
- 超时和连接重置，属于"不知道成没成"
- 401/400/404，属于"重试一百次也不会好"
- 最阴险的一类：接口正常返回，但 schema 变了，解析静默失败

裸写的 Agent 通常三种死法：直接崩；无限重试烧 token；或者更糟——LLM 拿到报错后"善意地"编了一个答案继续往下跑。第三种最难发现，因为流程看起来一切正常。

## 做法

社区里比较收敛的一套做法，按顺序：

1. **先给错误分类，再谈重试。** 只对可重试错误（超时、429、5xx）做自动重试；4xx 一律上抛，让上层决定。
2. **指数退避 + 抖动，封顶次数。** 比如 1s/2s/4s 起步，加随机抖动，最多 3~5 次。重试逻辑写在工具封装层，不写进 prompt。
3. **加熔断。** 连续 N 次失败后进入冷却期，冷却期内直接走降级路径，不再打已经挂掉的服务；冷却结束后半开探测。
4. **降级要有明确语义。** 可选三种：返回带时间戳的缓存数据、切换备用源、跳过该步骤并把产出标记为"部分完成"。关键是把降级状态写进 Agent 上下文，让它知道自己拿到的是旧数据——但不能给它"自由发挥补数据"的权限。
5. **状态要可续跑。** 长任务每完成一步就落盘 checkpoint，恢复时从断点继续，而不是从头再来。
6. **非幂等操作单独处理。** 下单、发消息这类 POST 必须带幂等键，否则超时重试会造成重复副作用。

## 踩坑点

- **把重试决策交给 LLM。** 模型对"第几次重试、间隔多久"没有可靠概念，实践中很容易死循环。重试是确定性逻辑，归代码管。
- **超时 ≠ 失败。** 请求可能已经到达对端并执行成功，盲目重试就是重复执行。这正是幂等键存在的理由。
- **退避不加抖动。** 一批定时任务同时被限流、同时恢复、再一起被打挂，经典雪崩。
- **静默降级。** 用了缓存数据却不声明，Agent 会拿着三天前的价格一本正经地做分析。降级必须显式。
- **熔断阈值拍脑袋。** 高并发下几次失败可能只是瞬时拥塞，阈值太低会频繁误熔断，建议按时间窗口内的错误率来判断。

## 可复用建议

- 给所有 MCP 工具调用套统一的弹性封装：重试、熔断、超时、日志四件套，插件作者不必各自造轮子。
- 错误分类做成社区约定：插件对外暴露结构化错误码，而不是把异常字符串直接丢给模型。
- 定期做故障演练：主动把某个依赖掐掉十分钟，看 Agent 是优雅降级还是装死。没演练过的恢复逻辑等于没写。
- 告警盯两个指标：熔断打开次数、降级产出占比。它们比平均延迟更能提前暴露依赖劣化。

## 总结

外部 API 挂了不是异常路径，是常态路径。好的 Agent 和差的 Agent 差别不在于永不失败，而在于失败之后：错误能否被正确分类、重试是否可控、降级是否诚实、状态能否续跑。把这四件事做进工具层而不是 prompt 里，无人值守的自动化才真正睡得着觉。
