## 背景

OpenClaw agent 跑久了，memory 目录会积累大量条目：排查记录、配置片段、协作约定。memory_recall 的质量直接决定助手"记不记得住事"——召回不准，要么漏掉关键上下文，要么塞一堆无关内容污染窗口。我的记忆库目前 400 多条，此前一直用 SQLite FTS5 做全文检索，最近跑了轮向量检索对比，把过程和结论记下来。

## 问题

两套方案各有明显盲区：

- **全文搜索**：查"nginx 502 怎么解决的"能命中，关键词都在；但问"服务器当时为什么会挂"，一条都召不回——存的是"502 排查记录"，query 里没有一个词对得上。
- **语义检索**：改述类问题解决得不错，但精确 token 翻车。搜 `ERR_CONN_RESET` 或某个具体配置路径，返回的全是"大概相关"的段落，真正条目反而靠后。另外多了 embedding 依赖：本地模型吃资源，API 方案每次写入有延迟和费用。

## 做法

不想凭感觉选，做了个最小评测：

1. **建评测集**：从真实记忆挑 50 条 query，人工标注期望命中的条目。一半是日常真实问过的，一半是故意构造的改述、错别字、中英混合。
2. **分路测试**：FTS 用 FTS5 + BM25；向量用本地 bge-m3 加 sqlite-vec。各取 top-5，统计 hit@5。
3. **结果**：FTS 在错误码、代码片段、精确 token 上明显占优；向量在改述和跨语言（中文 query 命中英文条目）上更强。两路 top-5 重叠只有四成，互补性比预想强。
4. **上混合**：两路各取 top-5，用 RRF（倒数排名融合）按排名合并，不融合分数——不同模型的分值没有可比性。query 里出现路径、大写常量、错误码样式时，再加一路前缀匹配兜底。
5. **召回后处理**：按条目 front-matter 的 type 过滤，日期做衰减，最多注入 5 条，宁缺毋滥。

改完后评测集 hit@5 从 FTS 单路的 62% 提到 88%。

## 踩坑点

- **中文分词**：FTS5 默认 tokenizer 对中文基本不可用，整句会被当成一个 token。换 trigram 后才正常，代价是索引体积翻倍。
- **代码混存拉低向量质量**：自然语言和代码片段混在一个库里，相似度会失真。给代码类条目标了 type，向量召回时降权。
- **绝对阈值不可靠**：cosine 0.75 在一个模型里算高分，在另一个模型里是噪音。改成相对判断：top1 与 top5 分差过小说明整体不相关，直接放弃注入。
- **索引一致性**：手动改过记忆文件忘了重建索引，向量库和源文件对不上，排查了很久。现在写入走统一入口，写完即同步索引。

## 可复用建议

- **先建评测集再动检索**。50 条真实 query 加人工标注，半天工作量，省掉后面所有"感觉不准"的玄学调参。
- **小规模别过度工程**。记忆不到 200 条时，FTS 甚至全量塞进系统提示就够，向量检索是规模上来之后的事。
- **混合 + RRF 是默认解**，只融合排名不融合分数，实现不超过 20 行。
- **写入时带结构化元数据**（type、tags、date），检索时过滤比事后补救便宜得多。
- **把召回失败的 case 持续喂回评测集**，让检索质量可回归、可度量。

## 总结

语义和全文不是二选一，两者的失败模式几乎完全互补：一个丢精确性，一个丢泛化性。怎么选取决于记忆库的规模、语言构成和条目类型，而这些只有靠自己的评测集才能回答。先测量，再选择，最后混合。
