大模型圈刚被扔进一颗深水炸弹：Inception Labs——由斯坦福教授 Stefano Ermon 创办的公司——发布了 350 亿参数的扩散式大语言模型 Mercury，主打代码生成与 Agent 场景，在 H100 上跑到每秒 1000+ tokens，据称比同类速度优化模型快约一倍。这不只是又一次跑分胜利：它挑战的是自 GPT 以来几乎所有大模型默认的底层生成范式。扩散模型凭什么杀进 Agent 主场？又有哪些坎还没迈过去？这篇一次讲清。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-29/84d837dfa1df94bf.png)

## 先补课：自回归模型的“打字机模式”慢在哪

- GPT 这类模型是自回归（autoregressive）架构：逐个 token 生成，下一个 token 依赖前面所有已生成内容，只能严格串行。生成 1000 个 token，就是 1000 次完整前向计算——像一只一次只挥一只钳子的虾，稳，但快不起来。
- 延迟可以粗略写成：首 token 延迟 + token 数 × 单步耗时。token 越多等得越久，线性上涨，没有捷径。
- Agent 场景雪上加霜。一个完整任务动辄几十次 LLM 调用——规划、选工具、写代码、解析结果、反思重试。单次 500ms 没什么感觉，串行 20 次就是 10 秒起步，用户早就跑了。
- 业界目前的补救都是“外挂式”的：推测解码（speculative decoding）用小模型猜、大模型验证；Groq、Cerebras 靠堆 SRAM 压单步耗时；再加上各种 KV cache 优化。这些都有效，但没跳出“必须一个字一个字往外蹦”的根本框架。

## 扩散语言模型：先铺一摊噪声，再整体“显影”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-29/f9c83994cd69d092.png)

- 原理可以直接类比 Stable Diffusion 出图：从纯噪声出发，多步去噪逼近目标图像。扩散语言模型把去噪对象从像素换成了 token，年初人大等团队开源的 LLaDA、谷歌演示的 Gemini Diffusion 都在验证同一方向。
- 具体工作方式：先按预估长度铺开一段全是 [MASK] 的序列，模型每一步并行预测、修正一整片 token，经过少则几步、多则十几步的迭代，整段文本像照片显影一样一次性浮现。
- 三个结构性差异值得记住：
  1. **并行度**：每步同时计算所有位置，1000 个 token 不需要走 1000 步，十几次迭代即可收敛，这是速度优势的根源；
  2. **可修改**：去噪过程中允许全局重写、反复调整，不像自回归那样“落子无悔”，前面写错后面只能将错就错；
  3. **可填充（infilling）**：天然支持填空式生成，在文本中间挖个洞也能补上。
- 代价也明确：每一步要对整个序列做完整的 Transformer 前向计算，“步数少、单步重”。它用单步更大规模的并行计算，换掉了成百上千次的串行小步。

## 为什么 Agent 恰好是它的主场

- Agent 负载的特点是“短、平、快、多”：大量几百 token 的小调用，输出多为结构化 JSON、工具调用参数、代码片段，长度可控。这恰好避开了扩散模型在超长文本生成上的不确定性，同时放大了它的延迟优势。
- 代码场景天然契合。写代码本来就是“写—跑—改—再跑”的迭代过程，扩散模型的整体重写与 infilling 能力，可以直接映射到编辑器里的补全、重构和 diff 修复。官方报告其代码能力已对齐速度优化的同级商业模型。
- 错误自愈是隐性加分项。Agent 对输出格式极其敏感，tool call 的 JSON 少一个引号就整链报错。扩散模型在迭代去噪中能回头修正早期错误，格式合规率和代码一次可跑率更稳。
- 算的是成本账：同样的 H100，吞吐翻倍意味着单位 token 成本近似砍半。对并发巨大的 Agent 平台来说，这是实打实的毛利率改善，而不只是演示视频里的数字好看。

## 冷水时间：三个还没迈过去的坎

1. **质量上限未证**。目前扩散 LLM 在长链推理、超长文本一致性上仍落后于最强的自回归模型；优势集中在代码与中短输出，跑分必须分场景看。
2. **生态惯性太大**。现有推理栈——KV cache、张量并行、流式输出接口、各家 SDK——全部围绕自回归设计。换生成范式等于工具链重建，迁移成本常被低估。
3. **步数与质量的跷跷板**。去噪步数越少越快，但质量下滑明显；多少步算“够”仍是经验活，不像自回归“多生成 200 个 token”那样直观可控。

## 收尾：三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-29/692b37bb24af7a4b.png)

1. **把它当“延迟优化选项”，而不是替代品**。在自己的 Agent pipeline 里做 A/B 测试，重点盯 p99 延迟、tool call JSON 合法率、代码一次通过率这三项，别只看社区跑分。
2. **关注 infilling 带来的交互红利**。如果产品里充满改写、补全、重试类动作，扩散模型可能比“整段重新生成”省下大量时间与成本，值得专门设计调用方式。
3. **架构层留好抽象**。路由层做到扩散模型与自回归模型可插拔，别把系统绑死在任何单一范式的私有优化上。范式之争远未结束，单边押注的迁移成本可能比想象中高。

技术史反复证明：底层范式切换的初期，赢家往往不是发明者，而是最先把它用对场景的工程团队。扩散模型这一枪，打响的未必是取代自回归的战争，而是“按场景选生成范式”的时代。
