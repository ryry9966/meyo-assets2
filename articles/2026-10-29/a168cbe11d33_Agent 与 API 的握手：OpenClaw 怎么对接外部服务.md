## 背景

模型本身只会生成文本。让 Agent 真正"干活"的，是它和外部服务之间的那层接口：查库存、发工单、读日历、调内部 RPC。在 OpenClaw 生态里，这层接口通常以 tool、MCP server 或插件的形式出现。这层做得好不好，直接决定 Agent 是"能用的自动化工具"，还是"偶尔抽风的 demo"。

## 问题

对接外部服务时，实践中反复出现三类问题：

1. **描述失真**：工具描述和真实 API 行为不一致，Agent 按描述传参，服务端报错，进入"猜参数"循环。
2. **错误不可读**：返回的是原始堆栈或 HTML 错误页，Agent 无法判断该重试、改参数还是放弃。
3. **副作用失控**：写操作没有幂等保护和确认环节，一次重试就是两次下单。

## 做法

我们的做法是把对接拆成三层，各层职责明确：

**第一层：HTTP 客户端。** 统一封装鉴权、超时、限流退避。API key 从环境变量或密钥管理读入，绝不进 prompt、不进日志。默认超时 10 秒，429/5xx 指数退避，最多 3 次。

**第二层：工具封装。** 每个 API 端点包成一个 tool，描述按"一句话职责 + 参数语义 + 错误语义"写。返回值做裁剪，只保留 Agent 决策需要的字段，大结果落盘后给个引用 ID。错误统一转成结构化格式：

```json
{ "ok": false, "error_type": "invalid_param", "hint": "date 参数需要 YYYY-MM-DD 格式" }
```

`hint` 字段是关键——它不是给人看的，是给模型看的自我修正线索。

**第三层：Agent 侧。** 读操作直接放行；写操作加确认门，或在工具层生成幂等键，保证重试不产生新副作用。工具数量超过 15 个就按场景分组，用 MCP 按需加载，避免上下文被工具描述占满。

测试上，按真实 schema 起一套 mock server 做录制回放，先跑通再切生产，比直接拿生产 API 试错便宜得多。

## 踩坑点

- **描述只写"查询订单"没用。** 要写清传什么参数、返回什么、什么情况报什么错。含糊的描述是 Agent 乱猜的第一诱因。
- **不要把整个响应原样塞回上下文。** 一次 50KB 的 JSON 能吃掉大半对话窗口，后续推理质量明显下降。
- **非幂等 POST 千万别裸重试。** 要么服务端支持幂等键，要么把重试决策留给上层。
- **英文堆栈对模型几乎无价值。** 翻译成一句话语义加修正建议，自我修正成功率差别很大。
- **日志脱敏要早做。** 请求体带 token 的情况，上了生产再补就晚了。

## 可复用建议

1. 团队建一个工具描述模板，强制三段式：职责 / 参数 / 错误语义。
2. 统一错误返回结构，`error_type` 枚举收敛在 5–8 个以内。
3. 读工具放权、写工具设门，是成本最低的安全边界。
4. 每个 MCP server 配一个 mock 实例，CI 里跑契约测试，防止上游 API 静默变更。

## 总结

Agent 对接外部服务，本质是把一份"人能读懂的 API 文档"，翻译成"模型能读懂的工具协议"。OpenClaw 侧没有太多黑魔法：客户端管健壮性，工具层管语义，Agent 层管决策，三层各守边界。把错误信息当 prompt 来写，把写操作当危险操作来防，大多数对接问题就能提前消失。
