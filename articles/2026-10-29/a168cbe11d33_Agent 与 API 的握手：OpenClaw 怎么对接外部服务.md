## 背景

OpenClaw 本地跑通之后，第一件真实需求几乎都是“让它去调点外面的东西”：查日程、建工单、拉内部数据。Agent 本身不产出能力，能力来自它握手的那些 API。这一步做不好，后面所有自动化都是空中楼阁。

## 问题

最常见的起步形态是“临时脚本”：提示词里塞一段 curl，或者让 agent 直接 shell 调 python。能跑，但三个问题立刻出现——凭证散落在提示词和会话历史里；模型自己拼参数，错了没有任何约束；出了问题无法定位是模型、脚本还是接口的锅。

## 做法

1. **先盘能力清单**。把 agent 要做的动作列成“读/写”两栏，写操作（下单、建工单、发消息）单独标记，权限区别对待。
2. **选对接路径**。标准化服务优先走 MCP server，工具描述、参数 schema、调用协议都是现成的；内部接口或格式古怪的接口，写一个薄插件包一层，别让模型直接面对原始 API。
3. **凭证进配置，不进提示词**。API key 放环境变量或 OpenClaw 配置层，工具运行时注入，绝不出现在 system prompt 和对话记录里。
4. **schema 写严**。参数能 enum 就 enum，日期格式、单位、必填项在描述里写清楚。模型对模糊 schema 的容错远比你想象的差。
5. **出入口都要处理**。入口设超时和重试（指数退避，写操作不自动重试）；出口裁剪返回值，别把两百行 JSON 原样塞回上下文，只留模型需要的字段。
6. **留观测**。每次工具调用记一行日志：工具名、参数摘要、耗时、状态码。排障时这是唯一救命的东西。

## 踩坑点

- **工具太多、描述含糊**：模型会选错工具或编造参数。总数控制在十个以内，相关接口合并成一个带 mode 参数的工具。
- **写操作没有闸门**：加一层“预览-确认”或幂等键，否则模型一次幻觉参数就是一次真实下单。
- **裸错误直传**：第三方接口抽风返回原始报错，丢给模型它会开始脑补。在适配层统一包装成结构化的失败说明。
- **长任务同步阻塞**：几分钟才返回的接口会卡死整个会话，改异步加轮询或回调。

## 可复用建议

- 默认只读，写操作单独开权限。
- 一个服务一个适配层，模型永远不直连原始 API。
- 工具 schema 当代码维护，走 review，改动跑回归。
- 拒绝“万能工具”，宁可三个边界清楚的小工具。

## 总结

Agent 对接外部服务的本质不是“能不能调通”，而是握手过程是否可控：凭证可控、参数可控、失败可控。OpenClaw 提供了 MCP 和插件两条路，选哪条不重要，重要的是接口契约由你定义，而不是由模型的即兴发挥定义。守住这三件事，后面接入多少服务都不会乱。
