## 背景

Agent 跑起来之后，接到的第一件“真活”几乎都是调外部服务：查库存、发工单、读数据库。模型本身只会生成文本，真正让 Agent 有执行力的，是它和外部 API 之间那条通道。在 OpenClaw 里，这条通道通常有三种形态：MCP Server、插件、以及最原始的 function tool。不管哪种形态，本质都是同一件事——设计一份**模型能读懂、机器能执行、出错能兜底**的握手协议。

## 问题

社区里见到最多的不是“接不上”，而是“接上了但不好用”：

- 工具描述含糊，模型瞎猜参数；
- 鉴权信息散落在配置和 prompt 里；
- 出错时返回一坨原始 stack trace，模型不知道该重试还是该放弃；
- 上线后 API 改了字段，Agent 静默失败。

握手协议没设计好，后面全是补丁。

## 做法：六步走

**1. 盘点，别照搬。** 先用 curl 把要用的 3~5 个接口跑通，只包业务上真正需要的动作。不要把整个 OpenAPI 规格翻译成几十个工具——工具越多，模型选错的概率越高。

**2. 一层薄封装。** 写一个 MCP Server（或插件），每个工具对应一个“业务意图”而不是一个 HTTP 端点。比如叫 `create_ticket`，而不是 `post_v2_tickets`。

**3. 描述即说明书。** 工具的 description 和参数 schema 是模型唯一能看的文档。写清楚：参数含义、单位、必填/可选、典型取值。这里多写两句话，胜过线上排查两小时。

**4. 鉴权收口。** key 放环境变量或密钥管理，wrapper 内部处理 token 刷新。绝不让凭据出现在工具描述、示例或 prompt 里。

**5. 错误要“可读”。** 返回结构化错误：`{code, message, retryable}`。4xx 标记为不可重试（引导模型修输入），5xx 和超时标记为可重试（wrapper 内做指数退避，别把重试压力丢给模型）。

**6. 先脚本后对话。** 封装好先用独立脚本验证一遍，再进 Agent 会话测全流程。每一层都留调用日志。

## 踩坑点

- **幂等性**：带重试的写操作必须做幂等（幂等键或先查后写），否则一次超时重试就是两条一样的工单。
- **返回体裁剪**：别把几百 KB 的 JSON 原样塞回模型。字段挑重点、列表做分页，token 是真金白银。
- **隐形约定**：时区、金额单位、ID 类型（数字 vs 字符串）——文档不写但一错就是资损，写进 description。
- **静默失败**：API 改版不报错、只变字段，Agent 会“自信地”拿错误数据继续跑。对关键响应做最小 schema 校验。

## 可复用建议

把这套东西沉淀成模板：**薄封装 + 显式 schema + 结构化错误 + 凭据收口 + 调用日志**。接一个新服务时，90% 的工作是照模板填接口，10% 才是真正的定制。建议给每个工具配一份 fixture/mock，回归测试不依赖外网，也不烧配额。

## 总结

Agent 与 API 的握手，表面是工程问题，实际是契约设计问题。模型的可靠性上限，很大程度上由你给它的工具描述和错误信息决定。把每个工具当成写给“一个聪明但不了解你系统的实习生”的接口文档，方向就对了。接好一个服务，模板就多一块积木——这才是 OpenClaw 生态该有的复利。
