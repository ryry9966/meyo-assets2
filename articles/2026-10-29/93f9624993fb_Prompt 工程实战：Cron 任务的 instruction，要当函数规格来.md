## 背景

Cron 定时任务是 OpenClaw 里最容易被低估的功能。多数人第一次配置时只写一句「每天早上发一份 AI 新闻总结」，前两天效果尚可，一周后开始漂移：格式变了、长度失控、偶尔静默失败。

根本原因在执行上下文的差异：聊天时 agent 有对话历史可以补全意图，而 cron 是冷启动执行，instruction 就是它拥有的全部信息。写 cron instruction 本质上是在写一个无人值守函数的规格说明，不是在聊天。

## 问题

把上面那句需求拆开，至少有五处歧义：

- 「早上」是几点？哪个时区？
- 「AI 新闻」范围多大？用什么工具、去哪搜？
- 发到哪里？什么格式？多长？
- 搜不到东西时发不发？
- 失败了要不要通知我？

这些歧义在聊天里会被上下文自然吸收，在 cron 里就变成每次执行的随机数。

## 做法：把 instruction 当函数签名写

我在自己实例上跑了几个月，沉淀出一个六段模板：

```text
任务：一句话说明目标
时间：每天 08:00（Asia/Shanghai）
数据源：用什么工具查什么，关键词是什么
输出：投递渠道 + 固定格式模板 + 长度上限
边界：空结果、失败、超时时的行为
禁止：不要做的事
```

以每日早报为例，实际写出来是这样：

```text
任务：生成 AI 领域每日早报
数据源：用 web_search 搜索过去 24 小时的
  LLM / agent / 开源模型新闻
输出：发到 Telegram「AI 早报」会话，格式为：
  - 首行：日期 + 一句话总结
  - 3-5 条要点，每条不超过 40 字，必须附来源链接
  - 不加寒暄、不写结束语
边界：
  - 结果不足 3 条时，只发已有条目并注明信息较少
  - 搜索失败时发一条「今日早报失败：<原因>」，禁止静默
  - 禁止编造没有来源的内容
```

核心原则只有一条：**让每次执行的输出分布尽量窄**。固定模板、限制长度、规定异常路径，都是在收窄分布。

## 踩坑点

- **日期写死在 instruction 里。**「今天是 3 月 15 日」三个月后就是错的。日期让运行时注入，或指示 agent 先查当前时间。
- **时区没写。** cron 表达式的时区和 agent 的时区可能不一致，早报会变晚报。
- **一个任务干三件事。** 早报 + 日程提醒 + 邮件摘要塞进一个 cron，任何一环失败整体报废。拆开，一个 cron 只做一件事。
- **空结果静默。** 不规定空结果行为时，agent 倾向于什么都不发——你以为它跑了，其实没数据。
- **没控制长度。** 不写上限，早报迟早长成论文，token 成本跟着涨。
- **写完直接挂 cron。** 先手动触发跑三五次，观察输出方差，稳定了再上定时。

## 可复用建议

1. 把每条 cron instruction 存进仓库，改动走 commit，出问题能回溯。
2. 上线后观察一周，重点盯两类漂移：格式漂移（结构变了）和范围漂移（自作主张加了别的信息），出现就在「禁止」段补规则。
3. 异常路径宁可吵闹不可静默：失败发通知，好过你以为它在跑。
4. 高频任务注意成本，「长度上限」和「数据源范围」是最有效的两个旋钮。

## 总结

Cron instruction 的写法可以概括成一句话：假设执行时没有任何上下文，把时间、来源、格式、异常全部显式写清。它不像聊天 prompt 那样讲究技巧和文采，更像写 README——枯燥，但决定了无人值守任务能不能活过第一周。
