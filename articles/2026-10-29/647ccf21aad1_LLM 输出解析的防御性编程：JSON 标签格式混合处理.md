## 背景

在 OpenClaw 插件和 MCP 工具链里，让模型"只输出 JSON"是最常见的约定。但只要跑过真实任务就知道：即使 prompt 里写了三遍"不要带代码块"，返回里仍然会出现 ```json 围栏、`<json>` 标签、前置说明文字，甚至全角引号。格式契约是软约束，解析必须按硬约束来设计。

## 问题

典型故障链是这样的：`json.loads` 直接抛异常 → 上游 Agent 任务中断 → 笼统重试烧 token → 最后发现只是多了两行 markdown 围栏。更隐蔽的是解析"成功"但数据不对：字符串里嵌套的花括号截断了正则匹配，或者 `NaN` 混进了合法对象。单点解析在真实流量面前是不够的。

## 做法：分层解析，逐级降级

把解析收敛到一个模块，按成本从低到高走五层：

```python
def parse_llm_json(text: str):
    # L1: 直接解析
    try:
        return json.loads(text)
    except Exception:
        pass
    # L2: 剥离代码围栏与 <json> 类标签后重试
    # L3: 字符串感知的括号配平扫描，截取首个完整对象/数组
    # L4: 常见脏字符修复：尾逗号、全角符号、NaN
    # L5: 宽松解析库兜底，仍失败则带错误信息回问模型
```

三个关键点：

1. **L3 别用贪婪正则**，要写感知字符串状态的括号计数器，否则 `"msg": "{"` 这种内容会毁掉匹配。
2. **解析成功 ≠ 数据合法**。parse 之后必须过 schema 校验（pydantic 之类），类型、枚举、必填字段缺一不可。
3. **L5 回问要带结构化错误**："第 3 行多了尾逗号"比笼统重试省一半 token。

## 踩坑点

- **贪婪正则跨块匹配**：模型有时输出两段 JSON，`.*` 会把中间的闲聊一起吞进来。
- **修复库静默改语义**：宽松兜底可能把畸形数据"修"成完全不同的值，修复层结果要打标记、降信任级别。
- **全角字符**：中文语境下 `：` `，` 混入极常见，统一替换要小心别误伤字符串内容。
- **`json.loads` 接受 `NaN`**：这不是标准 JSON，后续序列化会埋雷，parse 阶段就该拒绝。
- **没留原始输出**：排查时只剩修复后的数据，等于丢了案发现场。

## 可复用建议

- 一个仓库只留一个解析入口，禁止散落的 `replace()` 各修各的。
- 每次失败都把原始输出、prompt id、模型版本落盘，攒出"脏样本测试集"，回归测试直接跑它。
- 能用 API 原生 structured output / JSON mode 就用，手写解析是降级层而非首选层。
- 修复层输出打上 `repaired: true`，下游按信任级别区别处理。

## 总结

LLM 的输出格式本质上是概率性的，解析代码要把这一点当公理。分层降级 + schema 校验 + 失败留痕，三件事做齐，插件和 Agent 流水线对格式漂移的免疫力会上一个台阶。防御性编程不是多写几个 try/except，而是承认"约定会被打破"，并提前安排好每一条退路。
