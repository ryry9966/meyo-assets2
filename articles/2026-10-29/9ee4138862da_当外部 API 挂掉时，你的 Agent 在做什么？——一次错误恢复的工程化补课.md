## 背景

做 Agent 自动化久了会发现一个规律：大多数“翻车”不是模型能力问题，而是外部依赖出了状况。LLM API 限流、MCP server 进程挂了、第三方接口超时——这些在演示时不会出现，但在长期运行的自动化流程里几乎必然遇到。

我最近踩了一次坑：一个定时任务依赖搜索 API，某天对方返回 503，Agent 自己决定连续重试了十几轮，烧掉不少 token，最后还把“搜索失败”包装成了一段看起来很合理的分析输出。这促使我把错误恢复这块认真补了一遍。

## 问题出在哪

裸奔的工具调用有三个典型毛病：

1. **错误对模型失真。** 工具层把异常吞掉、返回空字符串，模型会脑补结果；直接抛整段 stack trace，模型又容易被无关信息带偏。
2. **重试失控。** “再试一次”由模型自由决定，没有次数和预算上限，遇到持续性故障就是无限循环。
3. **副作用不幂等。** 重试写操作（发通知、建工单）可能造成重复执行。

## 我的做法

核心思路：把错误处理从“模型的自由发挥”收回到工程层，分四步。

1. **错误分类与结构化透传。** 工具封装层统一捕获异常，返回错误信封：`{ok: false, error_type: "rate_limit" | "server_error" | "bad_request", retryable: true/false, hint: "..."}`。关键是把 retryable 明确告诉模型，而不是让它猜。
2. **重试放在代码层，不交给模型。** 对 429、超时、5xx 做指数退避加随机抖动，最多 2–3 次；4xx 参数错误不重试，把错误信息回给模型修正参数。模型负责“换个方案”，代码负责“同一路径重试”。
3. **加熔断和降级。** 连续失败 N 次进入熔断，短时间内直接走降级路径：读缓存、切备用 provider，或明确产出“此部分数据不可用”的部分结果。宁可残缺，不要编造。
4. **设总预算和检查点。** 每个任务有整体 deadline，风险操作前把状态落盘，失败后从检查点恢复，而不是从头跑。

## 踩坑记录

- **对非幂等操作盲目重试**：给写操作加 request_id 让服务端去重，否则重试一次就是双倍副作用。
- **200 不等于成功**：有些 API 故障时返回 200 加错误 body，封装层必须校验业务字段。
- **退避没加抖动**：多个并发任务同步重试，把刚恢复的服务又打挂了。
- **降级结果没标注**：下游不知道拿到的是缓存还是实时数据，出现过拿一天前的数据做判断的事故。
- **交互场景退避太长**：无人值守的任务可以等 30 秒，有人盯着的前台 5 秒就该给反馈。

## 可复用的几点

- 所有工具调用过同一个封装：错误信封 + 重试 + 超时 + 日志，request_id 贯穿全链路。
- 把 retryable 语义写进工具描述文档，让模型和工程层对齐预期。
- 定期做故障演练：直接把依赖 API 断掉跑一遍流程，观察 Agent 表现。没演练过的降级路径等于没有。

## 总结

Agent 的可靠性 = 模型能力 × 工程兜底。API 挂掉不可怕，可怕的是错误信息在链路中失真、重试逻辑失控。核心原则三条：让模型看到真实但结构化的失败、把机械重试交给代码、永远准备一条不编造数据的降级路径。这套东西不炫技，但决定了自动化任务能不能安心过夜。
