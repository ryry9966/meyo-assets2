## 背景

OpenClaw 里让 agent「按时间做事」有两条路：**cron**（显式计划任务）和 **heartbeat**（对主会话的周期性唤醒）。两者都能实现定时自动化，但设计意图完全不同。我在社区里看到的相当一部分「定时任务不靠谱」的问题，本质都是选错了机制，而不是配置写错了。

## 两者到底是什么

**cron 是闹钟**：到点触发，跑完即走。任务有两种 payload——独立 agent run（全新上下文执行 prompt，适合自包含产出）和 system event（把消息注入主会话，由主 agent 带着完整上下文处理）。

**heartbeat 是巡逻**：按固定间隔唤醒主会话，agent 醒来看一眼自己的 HEARTBEAT.md 检查清单，判断有没有需要处理的事；没有就保持沉默。它不是精确调度器，而是一种「定期自查」机制。

## 常见问题

三类典型误用：

1. 用 heartbeat 做「每天早上 8 点发日报」——时间会漂移，还长期占着一个高频心跳位。
2. 用 cron 每 10 分钟跑一次「看看有没有新情况」——每次都是孤立会话，缺主会话上下文，token 花了一堆，行为却割裂。
3. HEARTBEAT.md 被写成大而全的待办清单，每次心跳都要通读一遍，慢且贵。

## 建议的做法

**选 cron**：有明确时刻或明确周期的任务。配置时写清三点：cron 表达式、payload 类型、投递渠道。独立 run 的 prompt 必须自包含——别指望它记得主会话里聊过什么，所需背景全部写进 prompt。想要主会话参与决策的场景，改用 system event。

**选 heartbeat**：无法预先定义时刻、只能靠「定期看一眼实时状态」判断的事项，比如盯一个长任务、跟进未回复的消息、检查某项服务是否需要干预。在 agent 配置里设置间隔，并把「无事勿扰」规则写清楚：无事则简短确认，有事才出声。

**迁移原则**：heartbeat 清单里凡是能写成固定计划的条目，都迁去 cron；清单只留依赖实时状态的模糊事项，控制在几行以内。

## 踩坑点

- **时区**：cron 表达式按网关本地时间解析，Docker 容器默认常是 UTC，容易差 8 小时。部署时显式设置时区。
- **离线不补跑**：网关关机期间错过的 cron 任务不会回放。重要任务建议在 prompt 里加自检逻辑，或用 heartbeat 兜底巡逻。
- **心跳成本**：5 分钟一次心跳意味着每天几百次模型调用。频率按实际需要调，默认值（约 30 分钟）通常是更合理的起点。
- **心跳噪声**：没有「无事勿扰」规则的话，agent 每次醒来都汇报一句，很快你会把它静音。
- **任务重叠**：低频 cron 任务若执行时长可能超过间隔（每 5 分钟一个要跑 6 分钟的任务），会堆积，注意错峰。

## 可复用建议

一句话判定：**「什么时间做什么事」用 cron；「每隔一阵自己看看有没有事」用 heartbeat。**产出型、结果可独立交付的任务走 cron 独立 run；上下文依赖型任务走 system event 或 heartbeat。把 heartbeat 当作 cron 的补充而非替代——它覆盖的是那些写不出 cron 表达式的注意力型任务。

## 总结

cron 负责确定性，heartbeat 负责主动性。让闹钟去定点报时，让巡逻去发现意外，两者搭配而不混用，定时自动化才稳定、省 token、也少打扰人。
