# 从零搭建 AI 社区发帖机器人：架构设计与踩坑实录

## 背景

社区运营有个老问题：内容节奏靠人肉维持。每周固定栏目（工具推荐、问题精选、版本速递）重复性高，人一忙就断更。我的目标很朴素：用 OpenClaw 的 Agent 能力搭一个发帖机器人，负责选题、起草、查重、发布，人只做最后一道审核。跑了两个多月、四十多篇帖子，目前能稳定工作，中间踩的坑比想象的多，记录一下。

## 总体架构

没有用单一大 prompt 硬扛，而是拆成四层：

- **触发层**：cron 定时任务，每天早九点触发一次 agent run；
- **Agent 层**：OpenClaw agent 负责编排，读取选题池和历史记录，产出草稿；
- **工具层**：三个 MCP server——`draft`（调模型生成）、`dedup`（向量查重）、`forum`（论坛 API 客户端），各自独立进程；
- **状态层**：SQLite 存已发帖记录、草稿、幂等键。

流程：cron 触发 → agent 选主题 → 生成草稿 → 查重 → 推送到审核群（IM webhook）→ 人工确认 → 带幂等键调论坛接口发布 → 写入历史。

## 踩坑实录

**1. 第一版直接全自动，一次翻车毁掉信任。** 最初图省事没加审核，模型某天把一个未验证的 API 变更写成了“正式发布”，帖子发出去半小时才被发现。教训是灰度发布：现在是 dry-run → 人工审核 → 半自动三档，配置切换。

**2. 查重只做精确匹配等于没做。** 前期用标题 hash 去重，结果模型换个措辞就把旧话题重发了一遍。后来改用 embedding 相似度，阈值 0.85，超过即拦截并要求 agent 换角度。历史语料跑一次索引即可，成本可忽略。

**3. 模型会编版本号和链接。** 草稿里出现过不存在的 release 版本和 404 链接。两个手段：一是限制 agent 只能基于抓取到的素材写作，禁止凭记忆补事实；二是加一个 `verify` 工具，发布前对所有链接发 HEAD 请求，失败就打回。

**4. 论坛限流与崩溃恢复。** 连续发帖触发 429，最初的裸循环重试越试越糟。改成发布队列 + 随机抖动（5–15 分钟间隔）+ 指数退避。更隐蔽的坑是进程崩溃在“已调接口、未写状态”之间，重启后重发。解法是幂等键：发帖前先把 key 落库，论坛端按 key 去重。

**5. Markdown 转 HTML 格式错乱。** 论坛接口只收 HTML，最初用正则替换，代码块里的 `<` 全被转义错。换成标准渲染库，并保留原始 Markdown 存档，出问题方便对比，回滚也有依据。

## 可复用建议

- 工具全部封装成 MCP server。论坛客户端后来被另一个摘要机器人直接复用，几乎零改动；
- 状态一律落 SQLite，别信内存，也别靠 grep 日志；
- 发布链路必须幂等，这是一切自动化的底线；
- 每篇草稿与最终版本都归档，出问题能回溯是模型、素材还是工具的责任；
- 速率控制别省，社区接口不比大厂 API 宽容。

## 总结

这个机器人技术上没有神秘成分，难度全在工程细节：状态一致性、内容质量控制、失败恢复。收益是每周省下约三小时机械劳动，更重要的是内容节奏不再依赖某个人的记性。如果你也在做类似自动化，建议从 dry-run 模式起步，宁可慢一点上线，也别让一次事故消耗掉社区对你机器人的信任。欢迎在评论区交流你们的编排方案和查重策略。
