## 背景

团队每天要发一封日报，内容大致是：昨日构建/部署情况、告警统计、变更与待办。以前的做法是各人手动摘录，再由值班同学拼装，耗时且容易漏项。这篇帖记录我用 OpenClaw 搭的日报流水线：定时任务拉原始日志，脚本做聚合，Agent 通过 MCP 工具补上下文做摘要，最后产出固定 schema 的结构化报告并推送。

## 问题

“把日志直接丢给模型写日报”有两个硬伤：

1. 原始日志量大且噪，token 成本高，关键信息容易被稀释；
2. 模型对数字不可靠，告警次数、构建失败数这类硬指标一旦由模型“复述”，就可能对不上源数据。

日报的价值在于准确，所以设计原则很明确：**数字由脚本算，模型只负责解释。**

## 做法

流水线分五步，每步落盘中间产物，方便回放排查：

1. **采集**：cron 定时触发，脚本从三个来源拉数——CI 记录、监控告警、issue 平台的变更事件，统一转成 JSONL，时间戳统一存 UTC。
2. **聚合**：纯脚本完成，不经过模型。按天分桶，输出各来源计数、Top 错误类型、变更清单，产出几百行以内的聚合快照。
3. **结构化抽取**：Agent 读聚合快照，通过 MCP 工具补上下文（如查某条告警对应的 runbook 链接），输出符合预定义 JSON schema 的字段：事件摘要、影响面、建议动作。
4. **生成报告**：模板渲染数据区 + 模型写一句话总评。数据直接来自第 2 步快照，不重算。
5. **校验与投递**：脚本做一致性检查——报告中每个数值必须与快照逐项相等，schema 校验不过就打回重试；通过后推送到 webhook。

## 踩坑点

- **时区**：CI 平台与监控平台时区不一致，第一版统计窗口错了 8 小时。教训：采集层统一 UTC，只在展示层转本地时间。
- **让模型算数**：早期让 Agent 直接读原始日志统计失败次数，同一输入跑两次结果不同。改成脚本计数后彻底解决。
- **输出格式漂移**：不加约束时，模型偶尔把字段写成散文。抽取步骤强制 JSON schema + 失败重试后才稳定。
- **静默失败**：流水线挂过两天没人发现，日报照发旧数据。补了心跳检测，并在报告里显式标注“数据统计窗口”字段。

## 可复用建议

- **先定 schema 再写 prompt**。字段即契约，上下游解耦全靠它。
- **中间产物落盘**。出问题可从任意一步回放，不必重跑全链路。
- **数值与叙述分离**。数据区永远来自脚本，模型只填解释与建议。
- **用历史数据回放一周**，确认统计口径无误后再上定时任务。
- 采集、聚合、生成拆成独立命令，方便单测与手动触发。

## 总结

上线后，日报从每天约 30 分钟的手工活变成 3 分钟的核对。核心经验只有一条：**让模型做它擅长的事（归纳、解释），把确定性的事（计数、校验）交给脚本**。Agent + MCP 的价值不在替代脚本，而在把脚本产物翻译成人能直接使用的判断。
