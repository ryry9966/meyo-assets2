# 把大模型搬回家：家用电脑跑本地 LLM 的实践记录

## 背景

玩 OpenClaw 这类 Agent 框架久了，多半会撞上三件事：隐私（个人笔记、家庭自动化数据不想出门）、成本（长链路 Agent 跑一晚，API 账单扎眼）、可用性（断网或限流时整条自动化停摆）。本地 LLM 是很自然的补充：模型权重放在自己硬盘上，OpenClaw 走本地端点调用，数据不出家门。

## 问题

真正的难点不是"能不能跑起来"，而是"跑起来之后能不能稳定干活"。本地小模型能聊天，不等于能可靠输出 MCP 工具调用所需的 JSON。这篇帖子聚焦三件事：硬件怎么选档、模型怎么挑、怎么用工程方法验证它配得上你的流水线。

## 做法

**1. 盘点硬件，确定档位。** 显存是第一约束：8GB 卡跑 7B/8B 的 Q4 量化；16GB 上 14B 从容；24GB 可碰 32B 或 MoE 结构（激活参数小，家用卡也有可用速度）。纯 CPU 能跑但速度难看，只适合低频任务。

**2. 选运行时。** Ollama 上手最快，llama.cpp 系更可控。关键是它们都提供 OpenAI 兼容端点，后续换模型、换后端几乎零成本。

**3. 挑模型。** 量化从 Q4_K_M 起步，体积与质量均衡。Agent 场景优先看官方是否声明支持 function calling——这一条比榜单排名重要。

**4. 接入 OpenClaw。** 把 base_url 指向本地端点（如 `http://127.0.0.1:11434/v1`），model 填拉取的模型名，MCP 和插件配置一律不动。

**5. 用脚本验证，不凭感觉。** 我写了个百行小脚本：对同一个 MCP 工具循环调用 20 次，记录成功次数、参数错误类型和 tokens/s。这个数字比任何评测都诚实。

## 踩坑点

- **KV cache 吃显存**：权重装得下不代表上下文装得下，32k 上下文能多占几 GB。OOM 时先砍上下文长度，别急着换小模型。
- **工具调用 JSON 经常坏**：字段名拼错、参数写进正文、多一个逗号。对策：温度降到 0.2 以下；换支持约束解码的运行时；system prompt 里给一两个调用示例。
- **长上下文等于速度悬崖**：家用卡上上下文一长，生成速度掉得厉害，Agent 系统提示词尽量精简。
- **服务假死**：Windows 休眠、网卡节能都会让本地端点失联。配开机自启加健康检查，OpenClaw 侧设好超时重试。
- **别迷信跑分**：我手上的 14B 知识问答不如某个 8B，但工具调用成功率高得多。用你自己的任务说话。

## 可复用建议

1. 给每台机器建一份 model card 笔记：模型、量化、tokens/s、显存占用、工具调用成功率。下次选型直接查表。
2. 混合路由：本地跑分类、草稿、隐私敏感任务，难题透传云端。OpenClaw 里配两个 provider，一个环境变量切换。
3. 端点统一走 OpenAI 兼容格式，换后端只改 model 名。

## 总结

本地 LLM 在家用硬件上已经不是玩具，但对 Agent 场景而言，选型方法和验证流程比"跑起来"更重要。建议路径：小模型起步 → 脚本压测自己的任务 → 不达标再升档或上混合路由。把验证做在前面，本地模型才能成为流水线里可靠的一环，而不是周末玩具。
