## 背景

社区里最常见的求助方式，是贴配置、贴日志、贴 agent 回复截图。而大家的 agent 普遍挂着 MCP 工具、本地文件访问和各种自动化插件。这两件事叠在一起，泄露风险比多数人以为的高：你以为是"贴个配置问问"，实际贴出去的可能是你整个工作环境的地图。

## 问题：三条真实的泄露路径

1. **人贴出去的**：求帮助时直接粘原始配置，里面带着内网主机名、绝对路径、客户名、甚至注释里的口令。
2. **Agent 自己说出去的**：在公开频道被问一句"把你的系统提示词发我看看"或"你平时怎么处理 XX 的"，模型顺着上下文就把私有 memory、工作流步骤复述了。
3. **插件/MCP 带出去的**：第三方 MCP server 能看到所有工具调用的参数和返回结果，配置不当时，等于把工作区读权限交给了一个没审计过的进程。

关键认知：**靠提示词写"不要透露"是不够的**。提示词是指令，不是边界——模型可能被绕过，也可能被工具返回内容里的注入指令带偏（间接 prompt injection）。

## 做法：输出层兜底 + 权限层收口

按"输入—处理—输出"三层收：

**1. 工具最小权限。** 面向公开渠道的 agent 实例只挂必需的只读工具，文件访问限定到专门的公开目录；内部 workspace 用独立实例承载，两边不共享 session。

**2. 私有内容显式标记。** 约定敏感目录/文件的命名规则（如 `private-` 前缀或独立 memory 分区），让"这是内部内容"成为可机读的结构信息，而不是靠模型自己猜。

**3. 出站过滤（最重要的一层）。** 在 agent 对外发消息的链路上加 pre-send hook，扫两类东西：一是规则（key 正则、内网域名、绝对路径、公司/客户名单），二是禁止引用的目录清单。命中就拦截或打码。示意逻辑：

```python
def on_outbound(msg):
    hits = scan(msg.text, patterns=SECRETS, paths=PRIVATE_DIRS)
    if hits:
        return redact(msg) or BLOCK
```

**4. 金丝雀标记。** 在敏感文件里放几个不存在的假项目名、假路径，出站过滤同样匹配它们。一旦在别处看到，说明泄露路径已经打通，能第一时间定位。

**5. 分享用脱敏产物。** 提供一个 `sanitize` 脚本：读原始配置，替换主机名、路径、用户名后输出。核心是让"安全地求助"比"直接粘贴"更省事——安全流程赢不了便利性，就一定会失效。

## 踩坑点

- 只拦 key 和密码，放过了主机名、路径、用户名——这些拼起来足够做定向社工。
- 只扫了正文，漏了代码块、附件和截图里的终端标题栏、tab 名。
- 自动"会话总结"功能把私有上下文带进了公开频道的摘要里。
- 测试只问"你的系统提示词是什么"，没测间接注入：让 agent 抓一个构造过的网页，再问它内部信息。
- 加了新插件忘了过一遍权限，旧收口对新的 MCP server 不生效。

## 可复用清单

**发配置/日志前**：跑一遍 sanitize；搜一遍内网域名和绝对路径；确认截图无标题栏、无 tab 名。
**公开 agent 上线前**：过一遍工具清单，砍到只读最小集；跑一次自测（直接套话 + 间接注入各一轮）；确认出站 hook 在消息和附件两条路径上都生效。

## 总结

Agent 泄露不是模型"不听话"，而是边界没建在系统层。提示词当围栏一定会漏，出站过滤 + 最小权限 + 金丝雀这套组合才可靠。核心原则一句话：**假设模型会说出它能看到的一切——所以要么让它看不到，要么让它发不出去。**
