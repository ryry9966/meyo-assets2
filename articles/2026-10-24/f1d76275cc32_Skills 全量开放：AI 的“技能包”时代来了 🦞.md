今天被 36kr 那条《刚刚，你每天在用的 Skills 发生了一件大事》刷屏的，估计不止我一个。主角是 Anthropic 的 Agent Skills：据官方公告与多家媒体报道，Skills 向所有用户开放（免费档也能用）、官方技能库整体开源、还支持在对话里“说一句话就生成一个技能”。一个上线才一个多月的功能突然按下加速键，背后到底发生了什么？这篇文章用大白话把它拆开：它是什么、怎么工作、为什么值得关注。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/eaaa4a1fb7a8c685.png)

## 先补课：Skills 到底是个啥

一句话定义：**Skills 是把“怎么做一件事”打包成文件夹的机制**。

- **结构上**，一个 Skill 就是一个文件夹，核心是一份 `SKILL.md`：开头用 YAML 写 name 和 description（给模型看的路由信息），正文用 Markdown 描述流程、规范、注意事项；文件夹里还可以塞 Python/Bash 脚本、模板、参考文档。
- **内容上**，它装的是**程序性知识**，不是“XX 是什么”，而是“XX 该怎么做”。比如官方自带的 pdf、docx、xlsx、pptx 处理技能，或者公司内部的“周报生成规范”“代码审查流程”。
- **类比**：与其反复给模型上课（微调），或每次长篇叮嘱（超长 prompt），不如直接发一本**岗位 SOP 手册**。模型接活时翻一眼手册，照着流程干活。

2024 年以来，行业试过预设指令、插件市场、知识库挂载，大多停在“能聊”的层面。Skills 的差异点在于它同时解决了两件事：知识怎么注入，以及上下文预算怎么省。后者是它最巧的地方。

## 核心机制：Progressive Disclosure，把书架变成索引卡

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/4fc335665cdadb81.png)

Skills 最值得细看的设计是**渐进式披露（Progressive Disclosure）**，分三层加载：

1. **元数据层**：启动时，模型只读到每个技能的 name + description，大约几十个 token。装了 50 个技能，常驻开销也就一两千 token。
2. **触发层**：当对话命中某个技能时，才把 `SKILL.md` 正文完整加载进上下文。
3. **资源层**：正文里链接的参考文档按需读取；脚本甚至不用读进上下文，直接执行、只把运行结果带回来。

这解决的是**上下文经济学**问题。上下文窗口就像行李箱：出发前觉得能装下全世界，落地才发现超重的是自己。如果把几十份完整 SOP 全塞进系统提示，一个中型团队就能把窗口撑爆，还会互相干扰。抽屉式加载之后，技能数量增加的边际成本趋近于零。

脚本那层还有个隐藏好处：**确定性**。算税、日期换算、批量转 PDF 这类活儿，让模型“心算”又贵又不稳；写成脚本跑一遍，模型只负责调度，省 token 且结果可复现。

## 为什么说是“大事”：从产品功能到开放标准

免费可用、对话式创建，这些是顺水推舟的产品动作，真正值得注意的是另外两个信号：

- **官方技能库整体开源**。放到 GitHub 上、采用宽松协议，意味着任何人可以学习、修改、复用这些技能。官方等于公开了“标准写法”：元数据怎么起、脚本怎么组织、长流程怎么拆。
- **格式开放带来的生态卡位**。技能本质是纯文本文件夹，不绑定私有运行时，理论上任何实现了类似约定的 agent 框架都能复用同一批技能。这是在复述 GitHub 之于代码、App Store 之于应用的故事：先把“包格式”定下来，网络效应会自己滚过来。

行业叙事也随之从 prompt engineering 悄悄换成了 context engineering：竞争焦点从“怎么问模型”转向“上下文里放什么”。对开发者，这意味着**一次编写、多端运行**（Claude 应用、Claude Code、API 通用）；对企业，流程知识可以固化成可版本管理、可审计、可交接的文件，而不是散落在老员工的脑子里。护城河的形态，正在从“模型多强”变成“流程知识整理得多干净”。

## Skills、MCP、RAG、微调：不是互相替代，是分层

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/c8fa71607e9a03de.png)

讨论区最常见的争论是“Skills 会不会干掉 MCP”。拆开看就知道，它们根本不在同一层：

- **MCP**：标准化协议，负责连接外部工具和数据，是 agent 的“手脚”。
- **Skills**：打包流程与方法，是 agent 的“操作手册”。
- **RAG**：检索事实与资料，是“资料库”。
- **微调**：改动模型权重，是“改底子”，贵、慢、迭代周期长。

一个客服 agent 的典型组合：RAG 查订单记录，MCP 连工单系统，Skills 里装“七天无理由退货处理 SOP”，四者各司其职。真正该问的不是“哪个替代哪个”，而是“我这条流程，每一层该放什么”。

## 三条实用建议 + 一点冷思考

1. **从“每周重复三次以上”的事开始写**。周报、月度数据整理、固定格式文档输出，是性价比最高的第一批技能。description 一定写得像搜索关键词——它是模型的路由信号，写得模糊，技能就永远沉睡。
2. **确定性步骤用脚本，别用自然语言描述算法**。能用代码跑的不要让模型发挥；同时坚持一个技能只做一件事，小而专的组合远胜大而全的巨无霸。
3. **安全和可移植别偷懒**。第三方技能先审再装，警惕藏在文档里的提示注入；核心 SOP 用纯 Markdown 维护并进 Git，别把自己绑死在任何一家的私有格式上。

最后一点冷思考：**格式开放不等于生态繁荣**。写一个 SKILL.md 的门槛很低，但把业务流程讲清楚、拆干净、写成机器可执行的步骤，才是真正的稀缺能力，这件事，工具替不了你。
