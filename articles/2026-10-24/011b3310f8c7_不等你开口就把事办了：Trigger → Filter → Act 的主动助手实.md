## 背景

现在大多数助手是“应答式”的：你问一句，它答一句，本质上是个高级输入框。而 OpenClaw 这类常驻网关加 MCP 工具链的组合，其实已经具备让助手“主动出手”的全部原料——常驻进程、定时任务、事件 webhook、可以读写外部系统的工具。问题不在能力，在于怎么让它主动得**不烦人、不烧钱、不出事**。

## 问题

我最早的做法很粗暴：加一个每分钟跑一次的 cron，让 agent 检查 CI 状态、磁盘、日历，有异常就汇报。跑了一周，结论是负资产：

- 每天几百次模型调用，其中九成检查结果是“没事”，token 成本直接翻倍；
- 同一个问题反复告警，群里刷屏，同事差点 mute 掉它；
- 有一次它“自作主张”重写了一个配置文件。

主动能力如果不过滤、不授权，就是骚扰机器。

## 做法：拆成 Trigger → Filter → Act 三段

**1. 触发层：便宜的事在脚本层做完。**
三类触发源：低频 cron（30 分钟级）、事件 webhook（git push、邮件到达）、脚本级状态检查。关键原则是——能用 shell 判断的就别唤醒模型。比如磁盘阈值就是一个 `df` 加数值比较，超了才唤醒 agent，不满足直接退出，一个 token 都不花。

**2. 过滤层：结构化决策，失败即沉默。**
agent 被唤醒时，拿到的不是“自由发挥”的 prompt，而是触发上下文加一个输出契约：只允许返回 JSON，分类为 `ignore / batch / act` 三档。`ignore` 直接丢弃；`batch` 写进待办池；`act` 才允许调用工具。解析失败一律按 `ignore` 处理——宁可漏报，不可误扰。

**3. 执行层：读写分离，写走白名单。**
读类工具（查日志、查日历）放行；写类工具（发消息、改文件、调 API）走 allowlist，高风险操作要求确认。非紧急事项默认进每日 digest，晚上九点打包推一次；只有明确定义的高优先级条件（比如主干 CI 挂了）才允许即时打断。

另加一个去重状态：用告警指纹（服务名 + 错误类型）加 TTL 存本地小文件，同一问题两小时内不重复报。

## 踩坑点

- **触发风暴**：cron 间隔太密、每次触发都全量注入上下文，成本立刻失控。上下文按需给，能十行别给两百行。
- **提示漂移**：没有严格输出契约时，agent 会在该沉默的触发上“聊两句”，甚至主动总结一堆没人问的东西。结构化输出加失败即忽略，是底线。
- **重复告警**：没有状态记忆，同一个问题每次检查都报，用户很快失去耐心。指纹加 TTL 这几十行代码最值。
- **权限混放**：读写工具混在同一个 MCP server 里，一激动就写出去。读写分离，写默认关闭。

## 可复用建议

1. 从 2~3 个高价值低风险场景起步：CI 失败、日历冲突、磁盘阈值。别一上来做“全自动管家”。
2. 打扰人的门槛要高：默认批处理，即时推送是例外而非常态。
3. 每次主动决策落一条日志（触发源、分类、理由、动作），一周后回看，过滤规则自然就调出来了。
4. 盯三个指标：日均打扰次数、误报率、token 日成本。任一超标，先收紧再放权。

## 总结

主动能力不是模型强不强的问题，是工程约束的问题。触发便宜化、决策结构化、执行分级授权——这三件事做到位，助手才敢在你开口之前把事办了，而且办得让你不烦。它更像在调一个告警系统，而不是在驯服一个天才。
