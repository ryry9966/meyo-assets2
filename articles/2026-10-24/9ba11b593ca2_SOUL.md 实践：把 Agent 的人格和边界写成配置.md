## 背景

OpenClaw 这类常驻 Agent 和一次性对话不同：它挂在聊天渠道上，连着 MCP 工具、定时任务和一堆插件，一跑就是几周。默认状态下，模型是"通用助手"人格——客气、啰嗦、什么都答应。时间一长你会看到它在群里抢话、擅自执行重操作、语气忽正式忽油腻。这些多半不是能力问题，而是人格和边界从来没被显式定义过。

## 问题

常见的做法是在对话里现场调教：话多了就说"简洁点"，越权了就说"下次先问我"。这种调教有三个致命伤：

1. **不持久**：会话重置、模型切换、上下文压缩之后，约束就丢了。
2. **不可复现**：换台机器部署、给团队成员用，人格完全对不上。
3. **互相打架**：人格要求散落在 workspace 各文件和插件提示词里，改一处漏三处。

SOUL.md 就是收敛点。OpenClaw 每次组装系统上下文时，会把 workspace 下的 SOUL.md 注入进去，相当于 Agent 的"出厂人格"。

## 做法

**第一步：建文件。** 在 workspace 根目录（一般是 `~/.openclaw/workspace/`）创建 SOUL.md。用第二人称祈使句写，模型对这种写法的遵循度最好。

**第二步：分层写内容**，建议四个区块：

- **身份**：我是谁、服务谁、语气基调。两三行即可，写"你是一个工程向助手，默认中文，回答直接，不堆客套话"这类可执行的描述。
- **行为边界**：什么时候必须先确认（花钱、删文件、对外发消息），什么时候直接拒绝（转述密钥、私聊内容）。
- **风格约束**：回复长度上限、emoji 政策、群聊是否主动发言。
- **升级规则**：什么情况必须停下来问人，而不是自己猜。

**第三步：和其他文件分工。** SOUL.md 管"你是谁"，AGENTS.md 管"你怎么干活"，USER.md 管"你服务的人有什么偏好"。别把操作规范塞进 SOUL.md。

**第四步：当配置维护，不当散文写。** 进 git；行为不符合预期时往里加一行规则，而不是在聊天里争论。

## 踩坑点

- **写太长**。SOUL.md 每轮都进上下文，我见过 4KB 的人格文件把有效指令稀释得干干净净。控制在 100 行以内，超了就拆去 AGENTS.md。
- **把它当安全边界**。SOUL.md 只是软约束，长会话和注入攻击面前模型完全可能"忘了"。真正的边界——工具权限、目录白名单、花费上限——必须在网关和 exec 审批层强制执行。一句话：prompt 不是 permission。
- **规则不可测**。"保持友善、积极向上"等于没写。写成"未经确认不得向任何群聊发送主动消息"，出问题才能定位是哪条没生效。
- **换模型不复测**。不同模型对人格文件的敏感度差异很大，升级或切换后把高频场景手动跑一遍。

## 可复用建议

一份可直接抄的骨架：身份 3 行、边界 5–8 条、风格 3 条、升级规则 2–3 条，20–30 行起步，跑两周再按实际越界行为逐条补充。配套两个习惯：workspace 进 git；每次改 SOUL.md 写一句 commit message 说明是哪个行为触发的修改，半年后你会感谢这份变更日志。

## 总结

SOUL.md 的价值不在"让 Agent 更像人"，而在把不可复现的现场调教，变成可版本化、可审计的配置。人格即代码：写它、测它、review 它。花半小时写好这份文件，比之后几十次"你能不能别这样"省事得多。
