## 背景

OpenClaw 的 agent 并不是“裸跑”的。每次新会话启动时，它会把 workspace（默认 `~/.openclaw/workspace/`）下的几个 markdown 文件注入上下文：`SOUL.md` 管人格，`USER.md` 管用户背景，而 `AGENTS.md` 是其中最像“运维手册”的一份——工具怎么用、消息怎么发、哪些事不能自作主张，都靠它约束。默认模板能跑，但用一两周后，多数人都会遇到行为漂移。

## 问题

我实践中遇到三类典型失控：

1. **消息风格不稳定**：同样的指令，有时长篇大论，有时惜字如金；
2. **工具误用**：一条 `exec` 能搞定的事，agent 反复开浏览器抓页面；
3. **边界失守**：heartbeat 周期任务里，自作主张执行了未确认的清理命令。

根因不是模型变笨，而是这些约束只散落在聊天记录里，没有沉淀成一份 agent 每次都会读的静态契约。

## 做法

我按四步重构了自己的 AGENTS.md：

**1. 摸清加载机制。** 确认 workspace 路径（可在 `~/.openclaw/openclaw.json` 里调整），修改后新开会话才生效——旧会话仍挂着旧提示词，这是排障时最容易忽略的一点。

**2. 分层组织内容。** 我的模板固定四节：

- **环境事实**：时区、常用路径、网络环境；
- **工具规则**：什么场景用 `exec`、什么时候该先问再执行、消息长度与分段规范；
- **安全边界**：删文件、对外发消息、支付类操作一律先确认；
- **输出风格**：日志类回复给结论加一行原因，不堆过程。

**3. 把规则写成可判定语句。** “回复简洁点”没法执行；“单条消息不超过 150 字，超了就分段”可以。每条规则都要让 agent 能判断出“我违反了没有”。

**4. 建立回写习惯。** agent 每做错一件事，就把对应纠偏规则补进 AGENTS.md，用 git 提交，commit message 记录事故。跑一个月后，这份文件基本覆盖了我 90% 的日常摩擦点。

## 踩坑点

- **越长越好是错觉。** AGENTS.md 属于系统提示词，我试过 400 行的版本，后三分之一基本被忽略。现在控制在 60–80 行，命中率明显更高。
- **职责不要越界。** 人格语气归 `SOUL.md`，工具细节归 `TOOLS.md`，AGENTS.md 只管操作规范。两处写同一件事，一旦矛盾，行为就不可预测。
- **别写敏感信息。** 文件内容会整体进入上下文发给模型 API，密钥、内网地址都不要放。
- **别过度约束。** 每一步都写死，agent 遇到没覆盖的场景就不会变通。边界写清楚，路径留自由。

## 可复用建议

- 把 workspace 纳入 git，AGENTS.md 的每次变更都可回溯；
- 用负面案例驱动规则：与其凭空设计，不如等真实事故发生再补一条，规则天然带验证；
- 每月做一次删减 review，失效规则留着只会稀释有效规则；
- 换模型后用同一套任务清单跑一遍，观察哪些规则需要按模型特性调整。

## 总结

AGENTS.md 本质是你和 agent 之间的接口契约。它不是配置完就忘的模板，而是随使用不断演进的活文档——像维护 CI 配置一样维护它，agent 的行为下限会稳定得多。
