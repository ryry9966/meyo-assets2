# 社区自动发帖的节奏控制：怎么不像机器人

## 背景

我维护着一条社区内容流水线：OpenClaw 定时汇总本周的 issue 精选、版本动态和精华帖，通过 MCP 插件自动发到论坛和频道。内容质量本身没问题，但跑了两个月，收到的反馈很一致——**帖子没问题，但“发帖的样子”太机器了**。

## 问题

复盘下来，机器感来自三个具体行为：

1. **时间太准**。cron 固定在每周一 09:00:00，连续十周分秒不差。真人做不到，读者感觉得到。
2. **结构太稳定**。固定的模板开头、一成不变的小节顺序、同样的 emoji，回复率逐周下滑。
3. **节奏太均匀**。任务一旦积压（比如 API 超时重试），补发时一次性连发四五条，直接刷屏。

这些不是玄学，是可观测的行为特征。解决思路也不是“伪装成真人”，而是把发布节奏当成一个工程问题来控。

## 做法

### 1. 固定 cron 换成“基准时间 + 抖动”

不让平台定时器直接触发发布，而是让 Agent 自己计算下一次时间：

```ts
function nextSlot(baseHour = 9, jitterMin = 35): Date {
  const d = new Date();
  d.setDate(d.getDate() + 1);
  d.setHours(baseHour, 0, 0, 0);
  const offset = (Math.random() * 2 - 1) * jitterMin * 60_000;
  return new Date(d.getTime() + Math.round(offset));
}
```

要点：**先定基准、再加抖动，每次发完才调度下一次**。不要在“每次运行时随机决定发不发”——方差不可控，容易撞车或漏发。

### 2. 队列化 + 令牌桶限速

所有发帖先入本地队列，消费端限速：单频道每小时最多 1 条，全局每天上限 3 条。积压时按优先级丢弃而非补发，过期快讯宁可不发。

### 3. 内容做“结构性变化”，不做“随机洗词”

- 轮换 3–4 套开头和小节顺序；
- 高价值帖子走“草稿 → 人工确认”闸门，Agent 只出初稿；
- 同义词随机替换要克制，只会让文本变怪。

### 4. 保持透明

帖尾固定标注自动化来源和反馈入口。目标从来不是骗过读者，而是让自动化产出的内容值得读。

## 踩坑点

- **重试导致重复发帖**：没有幂等键，超时重试发了两条一模一样的内容。现在每条内容生成哈希作为幂等键，发布前查重。
- **时区错了 8 小时**：调度全按服务器 UTC 时间，“早上 9 点”实际是读者的深夜。统一显式指定时区。
- **抖动实现反了**：早期在每次执行前随机 sleep，发布时间漂移到了中午。抖动应加在调度时刻，而不是执行前。
- **停机后的报复性补发**：队列积压 20 条，恢复后瞬间清空。加了“单次唤醒最多消费 N 条”的闸。

## 可复用建议

1. **先统计再调参**：记录每次发布的时刻、间隔、互动率，节奏参数靠数据调，不靠感觉。
2. **日历感知**：节假日、社区大事件（如版本发布日）主动避让，这些时段真人流量本身就异常。
3. **留 kill switch**：一个环境变量让整条流水线静默，这比任何精细调参都重要。
4. **频道差异化**：公告频道和闲聊频道的节奏参数分开配置，别共用一份。

## 总结

“不像机器人”的本质不是模仿人类的随机性，而是**尊重读者的注意力**：别在错误的时间刷屏，别用同一张脸说同样的话，出问题时有刹车。把节奏做成显式参数（基准时间、抖动幅度、频次上限、静默时段），配合幂等查重和人工闸门，自动化内容完全可以长期留在社区里不招人烦。我们的周报回复率比模板时期高了一倍多，这大概是最好的验证。
