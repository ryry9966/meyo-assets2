## 背景

大多数 Agent 的默认形态是"你问我答"：一条消息进来，一轮工具调用，一条回复出去。这个模式跑通很容易，但用久了会发现一个尴尬的事实——真正值得办的事，往往发生在你没盯着它的时候：明早有个会但材料没准备、某个仓库的 CI 红了三天没人管、一个监控指标悄悄越过了阈值。

OpenClaw 这类常驻型个人 Agent 的价值恰恰在这条时间线上。它不是网页里的对话框，而是跑在自己机器上、常年在场的进程。但要说清楚一点：**"主动"不是模型自带的能力，而是一套触发 + 决策 + 克制的工程系统。** 这篇讲讲我把它跑稳的过程。

## 问题：主动 ≠ 多说话

直觉做法是"每隔几分钟让模型看一眼环境，有事就说"。跑起来立刻遇到三个问题：

1. **噪音。** Agent 把每次心跳看到的东西都汇报一遍，两天后你就开始已读不回，主动推送彻底失效。
2. **成本。** 心跳带着完整上下文跑大模型，Token 消耗是被动模式的好几倍。
3. **风险。** 主动意味着无人确认的动作，一旦默认给了写权限，一次误判就够喝一壶。

核心矛盾是：主动能力的难点不是让 Agent 行动，而是**让它在该闭嘴的时候闭嘴**。

## 做法：三层拆开

我把 proactive 链路拆成触发、决策、执行三层，各自可独立替换。

**第一层：触发源。** 目前用三类：

- 心跳（heartbeat）：低频自检，我设 30 分钟一次，prompt 只有一句话——"检查是否有值得打断用户的事，没有就返回空"；
- 定时任务（cron）：固定时刻触发，比如每天早上 8 点的晨报；
- 事件 webhook：外部系统推进来，CI 失败、仓库来了新 PR、邮件到达。

**第二层：决策。** 关键是给 Agent 一份明确的"打断标准"，而不是让它自由发挥。我的标准是三条：有时效性（过期就没用）、需要我输入（它自己办不了）、影响面可控。三条都不满足，写入日志、保持沉默。另外用一个便宜模型做预筛，明显不值得打断的直接过滤，贵模型只处理过筛后的。

**第三层：执行与记忆。** 这层最容易漏。Agent 必须记得"自己说过什么"，否则每次心跳都会把同一个发现再报一遍。我维护一个 JSON 状态文件：每条主动消息记录触发源、证据、时间戳，下次触发前先比对，内容没变化就不发。写操作全部走确认流——主动消息里附一个待确认动作，回复关键词才执行。

## 踩坑点

- **自激循环。** Agent 自己发出的消息也触发了 webhook，又回到 Agent，形成回路，排查了很久才发现。解法是给自产事件打标，触发层直接丢弃。
- **状态文件被忽略。** 早期只靠 prompt 里写"别重复汇报"，模型偶尔还是忘。把去重做成工具调用（先查状态、再决定说不说），比纯靠指令可靠得多。
- **群聊里的主动消息。** 同样的推送发到群里，打扰面被放大。后来改成静默时段：夜间只积累，早上合并成一条摘要。
- **权限蔓延。** 图省事给 proactive 流程挂了全套工具，某次它"顺手"删了一个它认为过期的草稿。之后主动流程默认只读，写工具按场景白名单。

## 可复用建议

1. 从一个低风险场景起步（晨报最安全：只读、固定时间、内容天然聚合），跑一周再扩。
2. 设"主动预算"：每天未请求消息上限 3 条，超了就合并进下一次摘要。
3. 所有主动决策落日志：触发源、证据、决定、理由。出问题基本靠这份日志回溯。
4. 每周复盘一次"已读不回率"——如果你忽略了大部分推送，说明打断标准太松，先收紧标准，而不是加功能。

## 总结

Proactive 不是一个开关，而是触发、决策、记忆、安全边界四件事的组合。模型负责判断"值不值得说"，工程负责保证"说了不算错、不说是因为没必要"。当你的 Agent 学会安静地忽略 95% 的心跳，剩下那 5% 才真正开始有价值。
