## 背景

过去几个月我把一部分自动化流程迁到了本地模型上：日志分类、周报汇总、MCP 工具调用的前置意图识别。动机很朴素——这些场景涉及代码片段和私有数据，走云端 API 总归不踏实；而且本地推理没有按量计费，跑批量任务不心疼。但要说明：本地模型和聊天场景的选型逻辑完全不同。Agent 关心的是长上下文、工具调用稳定性和首 token 延迟，不是"会不会写诗"。

## 问题

我的环境很典型：一台 32GB 内存的工作站，一块 12GB 显存的卡。要让它老老实实给 OpenClaw 的 Agent 当后端，有三个坎：

1. 显存/内存预算内能塞下什么规模的模型；
2. 小模型做 function calling 的格式漂移，动不动吐出 Agent 解析不了的 JSON；
3. 上下文长度默认值太小，MCP 的工具定义一多就被截断，而且失败是**静默**的。

## 做法

**第一步：按硬件定档位。** 粗略经验：8GB 显存跑 7B~9B 的 Q4 量化；12~16GB 跑 14B；24GB 可以摸到 32B Q4。纯 CPU + 32GB 内存跑 14B Q4 也能用，速度受内存带宽限制，每秒十来个 token，批处理任务可以接受。

**第二步：选运行时。** 图省事用 Ollama，一条命令起服务；想精细控制 KV cache 和量化细节就用 llama.cpp 的 server 模式；有大显存、要并发再上 vLLM。三者都提供 OpenAI 兼容端点，Agent 侧切换零成本。

**第三步：量化选档。** 工具调用场景建议不低于 Q4_K_M。我试过 Q3，对话看着还行，但结构化输出错误率明显上升，排查成本远超省下的显存。

**第四步：显式设置上下文。** 8k~16k 对大多数自动化任务够用。开 flash attention，KV cache 用 q8 量化还能再省一半。注意 KV cache 开销随上下文线性增长，不是把权重塞进去就完了。

**第五步：接进 Agent。** 端点指向本地服务后，先拿**真实的** MCP 工具 schema 跑一轮冒烟测试，别用框架自带的玩具示例。

## 踩坑点

- **上下文静默截断**：忘了设上下文长度，默认 4k，工具定义被吃掉后模型开始胡编参数。症状是"偶尔抽风"，极难定位。
- **模型空闲卸载**：Ollama 默认几分钟后卸载模型，Agent 触发式运行时第一轮请求慢十几秒，记得设 `keep_alive`。
- **TTFT 比吞吐重要**：Agent 循环里每一步都在等模型，首 token 延迟决定整体节奏，参数量优先往小了选。
- **JSON 格式漂移**：小模型爱把参数包进 markdown 代码块、加注释。优先用运行时的结构化输出 / grammar 约束，比在 prompt 里求它靠谱。
- **显存预算留余量**：权重 + KV cache + 运行时开销，算到 100% 必 OOM。

## 可复用建议

1. **分层路由**：本地模型处理分类、摘要、格式化这类轻任务，硬推理留给云端大模型。成本和质量的平衡点在路由层，不在单个模型。
2. **建自己的基准脚本**：放真实工具 schema 和历史样本，每次换模型、换量化档跑一遍。十分钟，避免一次线上事故。
3. **锁版本**：同一模型不同量化文件、不同运行时版本之间差异不小，升级前先跑基准。
4. **日志留全**：prompt、工具调用、耗时全记下来。本地部署最大的红利就是你拥有全部数据，别浪费。

## 总结

家用电脑跑本地模型，现在的问题已经不是"能不能"，而是"划不划算"。三个月下来的结论：给 Agent 当唯一后端还没到火候，但承担三到五成的轻量调用完全现实。别追参数规模——把模型对准任务和硬件，守住上下文配置，用真实 schema 验证工具调用。这三件事做对，本地后端就能稳定地跑在你的自动化链路里。

欢迎在评论区贴你的硬件配置和实测 token 速度，攒一份社区真实数据。
