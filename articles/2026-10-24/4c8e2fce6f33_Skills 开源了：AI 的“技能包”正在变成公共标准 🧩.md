刷到 36kr 那条热搜时，不少人的第一反应是：Skills？我每天都在用吗？答案是：只要你在让 AI 帮你做 PPT、处理 Excel、读 PDF，大概率已经受益于它了，只是它低调得像空气。这次的大事是，Anthropic 宣布把 Agent Skills 开放为开放标准（open standard），规范与参考实现放上 GitHub，任何 Agent 产品都能按同一套格式加载技能。一个“文件夹”级别的小改动被抬到标准的高度，值得展开聊聊：它到底是什么，为什么开放，又会砸出什么水花。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/bc24f9a4393c6238.png)

## 先把概念讲清：Skills 是“技能说明书”，不是插件商店

- **形态上**，一个 Skill 就是一个文件夹：核心是 SKILL.md，头部用 YAML 写 name 和 description，正文写操作流程；旁边可以挂 scripts（可执行脚本）、references（参考资料）、assets（模板素材）。
- **触发上**，用户不需要手动“点开”它。Agent 运行时只在上下文里保留每个技能的 name + description，量级在几十到几百 token；当任务描述命中某个 description，才加载完整说明书；涉及精确操作时，再去执行脚本。
- 这套机制叫**渐进式披露（progressive disclosure）**。打个比方：模型没有把整座图书馆背在脑子里，而是随身带一盒索引卡，翻到哪本读哪本，上下文预算省得很精明。
- 举例：官方示例里的 pptx skill，写明了创建与编辑 PowerPoint 的步骤、处理版式的脚本。模型不需要“天生”精通 OOXML 格式，照着说明书调用脚本就能干活。

## 真正的大事：从一家厂商的私有功能，到公共标准

- 先看一个前例：2024 年 11 月 Anthropic 开源了 MCP（Model Context Protocol），外界起初只当它是一家公司的接口方案；随后被 OpenAI、Google 等主流厂商与大量工具链宣布兼容，如今已是 Agent 连接外部数据与工具的事实标准。
- Skills 这次走的是相似剧本：规范和参考实现开放后，SKILL.md 的读写不再绑定单一产品，第三方 Agent 框架、IDE 插件、开源 runtime 都可以直接兼容这套格式。
- 生态效应有两个：
  1. **对技能作者**：一份 SKILL.md，多处运行；分发路径从“上架某个商店”变成“提交一个仓库”，门槛和迁移成本同步下降。
  2. **对企业**：内部 SOP 可以沉淀成技能库，做版本管理、跨工具复用；更妙的是格式稳定——底下的模型换了，技能照用。
- 一句话总结：技能包从“品牌专用的卡带”，变成了“通用接口的软盘”。

## 为什么写个 Markdown 就能让模型“学会”新东西

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/3985f3e886b784c3.png)

- 这里要区分两类知识：预训练权重里的**陈述性知识**（模型“知道什么”），和上下文里的**程序性知识**（“什么时候做、按什么步骤做”）。
- 大模型并非不会做表格，缺的往往是执行细节：用哪个库、注意哪些坑、异常怎么兜底。Skill 补的就是这一层，相当于把资深工程师的操作 SOP 贴在模型手边，用 in-context learning 的方式即时生效。
- 更关键的是**确定性问题**。涉及计算、格式转换、批量处理时，让模型逐格“脑补”表格内容，既贵又容易出错；Skill 附带的脚本把这类步骤变成确定性代码执行，模型只负责判断和调度。概率性的大脑 + 确定性的双手，配合才稳。
- 经济账也很直白：不改一个参数、不跑一次训练，能力扩展成本从“几次微调”降到“一份文档加几个脚本”。这是它和传统 fine-tuning 最本质的分野。

## 谁受益，谁要小心

受益面：

- **普通用户**：你嘴里那个“会做 PPT 的 AI”，背后大概率就是一个 skill；未来自定义助手会更像攒技能包，而不是反复堆提示词。
- **开发者**：入场券是“会写文档 + 会写脚本”；好技能靠口碑和 star 传播，相当于多了一条不卷算力的赛道。
- **企业**：老师傅脑子里的隐性流程，第一次有了显性化、可交接、可审计的载体。

风险面：

- Skill 内容会进入模型上下文，description 和附件文件都可能成为 prompt injection 的载体。第三方技能要像对待开源依赖包一样做安全审查，来路不明的别直接挂进生产环境。
- 脚本权限要收敛：能读写哪些目录、能不能联网，需要沙箱和白名单管住，否则“说明书”可能变成“后门”。
- description 写得含糊，技能约等于不存在——模型根本“看不见”它，加载永远不会被触发。

## 三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/0e4dfaf448a83ea1.png)

1. **把 description 当检索关键词写，别当广告写。** 它是模型决定是否加载的唯一线索，要说清“我是什么、什么任务该用我”，具体、可命中、不堆形容词。
2. **能脚本化的操作，别让模型即兴发挥。** 凡是格式固定、步骤确定的环节，固化成代码；模型负责判断，代码负责执行，出错面会小一个数量级。
3. **用软件工程的方式管理技能。** 进版本库、过评审、留测试用例，一样都别省——技能是长期资产，不是一次性笔记，尤其在它开始跨平台运行之后。

标准化的意义从来不在当下某个具体功能，而在于让“能力”第一次可以像零件一样在不同系统之间流动。Skills 这一步不算轰烈，但方向值得盯住：下一波 Agent 生态的竞争，很可能就从“谁的技能仓库更繁荣”开始。
