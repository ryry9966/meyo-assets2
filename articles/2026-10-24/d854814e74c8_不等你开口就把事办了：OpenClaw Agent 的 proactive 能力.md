## 背景

大多数 Agent 的默认形态是应答机：你说一句，它回一句。但自托管助手的真正价值在于"值守"——它比你在线时间长、能接的工具多，天然适合做主动汇报。OpenClaw 提供了两个现成入口：cron 定时任务和 heartbeat 心跳轮询，Agent 每次被唤醒都可以自主决定"干活、记录，还是开口说话"。这篇文章记录我把一个纯被动 Agent 改造成半主动值守员的过程。

## 问题

最初的做法很朴素：加一个每小时的 cron，让 Agent 检查 GitHub 通知、服务器磁盘、日历，有东西就发消息。跑了一周，暴露三个问题：

1. **噪音失控**。同一条 issue 的更新提醒了三次；磁盘从 81% 涨到 82% 也报告，消息价值趋近于零，我很快开始无视它——这比没有提醒更糟。
2. **Token 消耗翻倍**。每次心跳都是一次完整 agent run，带全套工具上下文，大部分 run 的结论是"无事发生"。
3. **一次危险动作**。某次 proactive run 判断"这个 PR 可以合"，差点直接执行写操作。没有人在回路里。

核心矛盾：**能发起 ≠ 该发起**。Proactive 的本质不是让 Agent 更聪明，而是一门噪音控制工程。

## 做法

**第一步，分离会话。** proactive run 用独立 session，不污染主对话上下文；跑完只把结论写入 memory，主会话需要时再引用。

**第二步，状态外部化 + diff。** 每类信号存一份上次快照（JSON 文件即可），本次拉取后先 diff：状态没变化，直接结束 run，一个字不发。磁盘告警从"每小时报一次"变成"越过阈值才报一次"。

**第三步，三级输出。**

- `silent`：低价值变化只追加到日志文件；
- `digest`：攒着的 silent 项由每日一条 cron 汇总成摘要；
- `alert`：越过明确阈值（磁盘 >90%、CI 失败、日历 15 分钟内开会）才直发消息。

**第四步，把判断写进 prompt。** 在工具调用前显式加一步：先读快照、判断级别，再决定调不调发送工具。同时硬性约束：proactive run 只读 + 通知，任何写操作必须转成待确认消息，由我回复后才执行。

改造后一周，直发消息从日均二十多条降到两三条，且每条都值得看。

## 踩坑点

- **心跳别开太密。** 15 分钟一轮的意义远小于 1 小时一轮 + 阈值触发，token 成本差 4 倍。
- **去重要在 Agent 外做。** 指望模型自己记住"上次说过了"不可靠，快照 diff 才是幂等的。
- **静默时段必须硬编码。** 凌晨三点被"日历摘要"叫醒一次就够了；Agent 判断不了"现在合不合适"，用配置判断。
- **proactive run 的权限要单独收窄。** 它若拿着和你聊天时一样的工具权限，等于值班员揣着仓库管理员钥匙。

## 可复用建议

- 任何主动通知先过三问：状态变了吗？用户能行动吗？现在能行动吗？三个都是"是"才发。
- 信号分级定 SLA：实时 / 小时级 / 日级，分别绑定不同的 cron 周期。
- 所有 proactive 产出先落盘，digest 是兜底——漏发的信息一定能在文件里找回来。
- prompt 里显式写上"**沉默也是合法输出**"，否则模型倾向于每轮都生产点内容证明自己在工作。

## 总结

Proactive 能力拆开看是三件事：定时唤醒（cron/heartbeat）、状态对比（快照 diff）、分级输出（silent/digest/alert）。前两件是纯工程，最后一件是产品判断。先让 Agent 学会闭嘴，它开口时你才会听。
