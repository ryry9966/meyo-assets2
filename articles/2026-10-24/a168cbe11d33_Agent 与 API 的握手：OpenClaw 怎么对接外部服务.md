## 背景

Agent 的价值最终落在“能办事”上：查数据、调接口、回写系统。OpenClaw 通过 MCP 和插件机制对接外部服务，门槛很低——写一个工具定义就能被 Agent 调用。但门槛低不等于工程量小，很多人 demo 跑通之后，一上生产就遇到 401、超时、参数乱飞、密钥进日志这些典型问题。这篇帖整理一次对接内部服务的完整过程，重点是“握手”阶段该做哪些事。

## 核心问题

对接本质上是三方握手：Agent、OpenClaw 的工具层、外部 API。问题几乎都出在边界上：

1. **鉴权归属**：API key 放在哪一层？塞进 Agent 上下文等于公开。
2. **工具描述质量**：Agent 完全靠工具的 description 和参数 schema 决定怎么调用，描述含糊就会乱传参。
3. **工程兜底**：外部服务必然超时、限流、偶发 500，Agent 需要能读懂的错误反馈。

## 对接步骤

**第一步：梳理能力，收敛成工具集。** 不要把外部 API 的几十个 endpoint 全部暴露，按 Agent 的真实任务挑 3~5 个，每个工具单一职责。工具越少越准，Agent 的选择成本越低。

**第二步：鉴权下沉到中间层。** key 放在工具实现侧（环境变量或密钥管理服务），由 MCP server 或插件持有凭据，Agent 只看到“工具名 + 参数 + 返回值”。上下文里永远不出现明文 key。

**第三步：把 description 当接口文档写。** 说明这个工具“什么时候该用、什么时候不该用”，参数单位是什么，返回结构长什么样，参数 schema 加枚举和必填约束。这一步的投入回报率最高。

**第四步：超时、重试、幂等。** 工具层设硬超时（比如 15s），只对幂等请求做有限重试；写操作先设计幂等键，避免 Agent 重试造成重复下单、重复发消息。

**第五步：错误信息面向 Agent 优化。** 不要只透传 HTTP 状态码，把错误翻译成可操作的提示，比如“参数 X 缺少单位，应为小时数”，Agent 才能自我修正。同时记录每次工具调用的入参出参，方便排查。

**第六步：返回值裁剪。** 大 JSON 直接返回会撑爆上下文。在工具层做字段筛选、分页、摘要，只给 Agent 需要的部分。

## 踩坑记录

- **工具描述写得太短**：某工具描述只有一句话，多工具场景下 Agent 频繁选错，补上使用边界后错误率明显下降。
- **同步等长任务**：一个报表生成接口要跑 2 分钟，同步等待直接超时。拆成“提交任务 + 轮询状态”两个工具就稳了。
- **返回内容带出敏感字段**：上游接口默认返回全量字段，工具层加白名单过滤后才敢上。
- **日志泄漏**：早期把请求头原样打进日志，key 跟着进了日志系统，后来统一做了脱敏。

## 可复用建议

1. 鉴权、限流、裁剪都放中间层，Agent 层保持“纯”。
2. 新工具先上 dry-run 模式，只打印将执行的动作不真正执行，确认无误再放开写权限。
3. 给每个工具标注版本，schema 变更时让调用方同步感知，避免隐性破坏。
4. 把高频错误整理进工具描述的“注意事项”，相当于给 Agent 一份 FAQ。

## 总结

对接外部服务，协议层（MCP/插件）只是最薄的一层，真正的工作量在鉴权归属、描述质量、错误反馈和工程兜底上。一个朴素的心法：把 Agent 当成“会读文档但需要明确边界的新同事”来设计接口，握手就顺了。欢迎在评论区交流你们对接时遇到的具体报错场景。
