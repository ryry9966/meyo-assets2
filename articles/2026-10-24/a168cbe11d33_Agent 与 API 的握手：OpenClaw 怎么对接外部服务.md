## 背景

Agent 的价值很大程度取决于它能"够到"多少真实世界：查工单、发通知、读数据，最后都落到对外部 API 的调用上。在 OpenClaw 里实际做了几个对接之后，我发现"能调通"和"能稳定跑"之间隔着不少工程细节。这篇帖子把做法沉淀一下，供后来人少踩坑。

## 问题在哪

直接把第三方 API 暴露成工具，通常会撞上四类麻烦：

1. **工具描述没人读得懂**——读它的是模型。描述含糊，模型就会传错参数、选错工具。
2. **返回值失控**——一个列表接口动辄返回几十 KB 的 JSON，几轮对话就把上下文吃满。
3. **错误不可推理**——模型收到 500 加一段堆栈，只能瞎猜着重试。
4. **密钥管理混乱**——key 散落在配置、日志甚至 prompt 里，事后清理非常痛苦。

## 我的做法：三层结构

我把对接拆成三层，各管各的：

- **适配层（adapter）**：每个外部服务一个独立模块，负责 HTTP 细节、鉴权、超时、重试。关键原则是**裁剪 API 面**——不要 1:1 映射所有端点，只暴露业务真正需要的 3~5 个动作。工具越少，模型选择越准。
- **工具定义层**：工具名用动词短语（`list_open_orders` 而不是 `orders`）；description 是写给模型的操作说明书，讲清参数含义、单位、时区、返回结构，也讲清"什么情况下不该调用我"。
- **返回规整层**：不透传原始响应，统一做三件事——截断（列表只回前 N 条加总数）、降噪（去掉无关元数据）、错误归一化（统一成 `{ok, error_code, hint}` 结构，hint 既是给人的排查建议，也是给模型的下一步提示）。

## 接入步骤

1. 适配层封装 API，先用 curl 验证鉴权，跑通最小调用。
2. 挑 3~5 个高频动作定义成工具，认真写 description。
3. 密钥走环境变量或专用配置，禁止出现在工具参数里——模型不应该经手 secret。
4. 每个调用加超时（我统一 15s），并标注幂等性：GET 可自动重试，POST/DELETE 只允许带确认的重试。
5. 开着调用日志 dry-run 一天，看模型实际传参和你的假设差多少，再回头改 description。

## 踩坑记录

- **description 写太简**：`search_user` 没写清是模糊还是精确匹配，模型拿昵称去查精确字段，排查了一下午。补一句话就好了。
- **分页漏掉**：模型拿到第一页就以为拿全了。解法是返回里带 `has_more` 和游标，description 写明"结果可能不完整时继续翻页"。
- **重试打爆对方**：一次 429 限流后模型原地疯狂重试。现在 429 统一交给适配层退避，模型只收到"稍后再试"。
- **工具太多**：一口气注册了 20 个工具，模型开始选错。砍到 8 个以内，准确率明显回升。

## 可复用建议

- 工具是给模型用的接口，不是给人用的 SDK——按模型视角设计。
- 响应永远先裁剪再返回，上下文比流量贵。
- 破坏性操作（删、写、付钱）单独加确认门槛，别靠 prompt 求模型"小心点"。
- 每次会话结束扫一遍调用日志，异常模式大多藏在那里。

## 总结

Agent 调外部 API，本质是在设计一个人机接口：模型负责决策，适配层负责工程兜底。把鉴权、超时、重试、裁剪这些脏活从 prompt 挪进代码，Agent 的稳定性会上一个台阶。OpenClaw 的工具与 MCP 机制足够灵活，值得把这套分层习惯固定下来。欢迎在回帖里聊聊你们对接时遇到的具体案例。
