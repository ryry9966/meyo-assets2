## 背景

多数 Agent 默认是"应答机"：你不发消息，它就静默。但个人助理场景里，大量有价值的工作是"没人问也要做"的——早报摘要、日志巡检、待办提醒、定期清理。OpenClaw 为此提供了一个极简机制：**HEARTBEAT.md**。它是 workspace 下的一个普通 Markdown 文件（默认在 `~/.openclaw/workspace/HEARTBEAT.md`），网关按固定间隔触发一次"心跳"，Agent 醒来读这个文件：有该做的事就执行，没有就回一个 `HEARTBEAT_OK` 继续沉默。

## 问题

把主动任务交给传统 cron，问题在于每个任务一个 job，逻辑分散，改需求要重写脚本；把所有事塞进对话上下文，Agent 又记不住、不稳定。HEARTBEAT.md 的思路是把"什么时候想"和"想什么"分离：调度交给网关的固定 tick，内容交给你随时用自然语言编辑的一个文件。文件即任务清单，改文件就是改行为，git 可管、diff 可审。

## 做法

**1. 用"任务卡"格式写，别写散文。** 每个任务写清三件事：触发条件（每天一次 / 当某现象出现时）、数据来源（读哪个文件、调哪个 MCP 工具、抓哪个 URL）、输出动作（发到哪个频道、写回哪个文件、什么情况下保持沉默）：

```markdown
## 每日早报（每天上午 8 点后的第一个心跳）
- 读取 inbox/summary.md 与日历 MCP，生成不超过 10 行的摘要
- 发送到 Telegram 的 daily 频道；内容为空则不发任何消息

## 仓库巡检（每 4 小时）
- 检查 ~/proj/logs/error.log 是否新增 ERROR
- 有则附最后 5 行发给我，无则静默
```

**2. 配置节奏。** 心跳间隔与主动消息投递目标在网关配置里调整，不同版本键名有差异，动手前翻一下当前版本文档。默认间隔是 30 分钟量级——这个粒度决定了它适合做"巡检"，不适合做"闹钟"。

**3. 验证。** 把间隔临时调到 1~2 分钟跑半天，确认任务如期触发、静默规则生效，再调回去。

**4. 总开关。** 把文件内容写成 `HEARTBEAT_OK`（或清空），心跳即跳过模型调用，等价于暂停所有主动任务。

## 踩坑点

- **token 成本是隐形的**：每次心跳都是一次真实的模型调用，哪怕最后只回 `HEARTBEAT_OK`。文件越长、任务越多，空转越贵。常驻任务控制在个位数，低频任务合并写。
- **指令含糊会诱发幻觉式提醒**。别写"关注一下错误"，要写"读哪个文件、匹配什么关键词、按什么格式发"。心跳时 Agent 往往没有对话上下文，任务必须自包含。
- **它不是 cron**。心跳会漂移、会排队，"每天 9:00 整点必须发"这类精确调度交给 cron job，心跳只做间隔性巡检。
- **防骚扰**：不设静默条件的任务迟早把你刷屏。每张任务卡都加"无事不发""每天最多一次""夜间不投递"之类的约束。
- **幂等性**：网关重启或上一轮未结束时任务可能重跑。写文件、发消息等动作尽量设计成可重复执行不出错的形态（覆盖写而非追加写）。

## 可复用建议

- **把 HEARTBEAT.md 当 SOP 管**：进 git，每次改动用 diff 审一遍，让"这个 Agent 每天自己会干什么"成为一份可审查的文本。
- **模板化三段结构**：常驻任务 / 条件触发 / 静默规则，新任务照格式填。
- **渐进上线**：先上一个只读任务（如早报）跑两周，确认输出质量后，再加有写动作的任务。
- **数据源走 MCP，别让 Agent 猜**：给它明确的工具和路径。主动任务的质量，取决于输入的确定性。

## 总结

HEARTBEAT.md 的价值在于用最小机制完成"被动 → 主动"的转变：一个文件承载任务，一个 tick 驱动执行，静默规则守住边界。它不追求精确调度，而是给 Agent 一个持续醒着的理由。写好它的关键只有一个词——克制：任务少而具体，成本可预期，行为可审计。
