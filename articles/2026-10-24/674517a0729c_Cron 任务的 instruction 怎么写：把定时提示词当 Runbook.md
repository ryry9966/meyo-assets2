## 背景

OpenClaw 的 cron 任务本质上很朴素：到点唤醒一次 agent，注入你预设的 instruction，让它带着工具自主执行，再把结果投递到指定会话或频道。我在自己的实例上跑了十几个这类任务——每日仓库巡检、服务健康检查、定时摘要——回头看，早期翻车的原因几乎一样：**instruction 是按"聊天消息"写的**。

## 问题

三个典型故障：

1. **日期不对**。早报里的"今天"经常是模型猜的。cron 会话没有你交互会话的上下文，也没有人在场实时纠正它。
2. **该报的不报，不该报的刷屏**。instruction 里没写输出条件，agent 默认"每次都得有话说"，一周后你自己就把通知频道 mute 了。
3. **静默失败**。cron 用的会话、身份、插件开关和你日常交互的可能不是一套。某个 MCP 工具没启用，agent 跑到一半自己换了条"看起来合理"的路径绕过去，结果完全不是你要的。

根因是：cron 触发的执行是**无人值守、无上下文、失败不显眼**的。所以 instruction 不能写成对话，得写成 runbook。

## 做法：五段式模板

我现在把每条 cron instruction 都拆成五段，稳定性明显提升：

```markdown
【触发上下文】这是一次定时触发，没有对话历史。
当前时间请用系统时间工具查询，不要猜测；所有日期判断基于该时间。

【目标与范围】检查 org/repo-a 和 org/repo-b 最近 24 小时的 open PR。
不要检查其他仓库，不要执行任何写操作。

【执行步骤】
1. 调用 GitHub 工具列出 open PR；
2. 过滤：阻塞超过 24 小时、或缺少 reviewer 的；
3. 对每条命中项取最近一条评论做一句话摘要。

【输出规则】
- 有命中项：按「仓库 / PR / 原因 / 建议」四栏格式发到 #dev-alert；
- 无命中项：不发送任何消息。

【异常兜底】工具调用失败时重试一次，仍失败则在输出中
标注"数据不完整"，禁止用猜测或旧数据顶替。
```

要点就五个词：**自包含、范围封闭、步骤可验证、默认静默、失败有出口**。

## 踩坑点

- **"接着昨天的继续"**：cron 会话没有昨天。跨次执行的状态要么落盘到文件，要么每次在 instruction 里重新声明。
- **相对词漂移**："最近""大概""比较活跃"这类词，模型每次理解都不一样。全部换成显式条件和数字。
- **假设权限一致**：新任务先手动触发一次（或把同一段 instruction 直接发条消息），确认工具、MCP、投递目标全通，再挂上调度。
- **重叠执行**：上一轮没跑完下一轮又触发，会产生重复通知甚至重复写操作。长任务在 instruction 里加去重判断，或者干脆设计成只读。
- **输出格式随意**：凡是下游要解析、你要统计的，格式必须写死在 instruction 里，一个字段都别让模型发挥。

## 可复用建议

1. **把 instruction 当代码维护**：存版本，每次修改留注释，出问题能 diff、能回滚。
2. **先观察后上线**：新任务先跑一周"静默模式"（只写日志不投递），确认误报率可接受再开通知。
3. **定期审计**：每月抽一次实际输出样本，修剪任务范围——scope 只会膨胀，不会自己收缩。

## 总结

Cron instruction 的本质，是给一个没有记忆、没人盯着、失败也不吵闹的执行者写操作手册。自包含、范围明确、输出有条件、失败有兜底——做到这四条，定时任务才算从玩具变成基础设施。
