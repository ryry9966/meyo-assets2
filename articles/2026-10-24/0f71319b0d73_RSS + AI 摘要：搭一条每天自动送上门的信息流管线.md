## 背景

RSS 没死，只是从大众工具退回了工程圈。相比推荐流，它的优势是源可控、无算法干预、天然可机器处理。但订阅一多，未读数本身就是负担。把 LLM 接进管线的目标不是"替代阅读"，而是把每天几十上百条原始条目压缩成一份能扫一眼的日报——值得深读的，再点进原文。

## 问题

直接把 RSS 条目丢给模型，会撞上几个现实问题：

1. 很多源只给 summary 不给全文，摘要质量没保障；
2. 同一事件多源转载，重复率极高；
3. 全量喂强模型，token 开销和延迟都不划算；
4. 摘要容易出现"看起来合理但原文没有"的句子。

所以管线设计围绕四件事：**去重、分层、控成本、可溯源**。

## 做法

以 OpenClaw 定时任务 + 一个脚本/MCP 工具为例（纯脚本也能跑通）：

1. **源清单配置化**。`feeds.yaml` 维护源列表，每个源打标签（tech / weekly / community）和优先级。起步 10–20 个源就够，宁少勿多。
2. **抓取与落库**。用 rss-parser 之类定时拉取，条目写入 SQLite，字段含 guid、链接、时间、源标签。guid 做主键天然去重。
3. **粗筛层（不用大模型）**。关键词过滤 + 24h 时间窗 + 标题相似度去重（分词后 Jaccard，阈值 0.6 左右）。这一步通常能砍掉 40–60% 的量。
4. **分层摘要**。普通源走便宜模型，输出"一段话摘要 + 要点列表"；高优先级源才抓全文交强模型做精读。输出固定结构 JSON：`title / one_liner / key_points / source_url`。
5. **日报渲染与推送**。按标签分组渲染 Markdown，cron 定点推到 IM 或写入笔记，每条保留原文链接。
6. **反馈回路**。日报里手动标"有用/没用"，累计几周后用来调 prompt 或直接砍源。

## 踩坑点

- **全文缺失**：相当一部分源只有 summary。对高优先级源加正文抓取，务必带 UA，部分站点会直接 403。
- **guid 不等于唯一**：有些源 guid 缺失或变动，用「链接规范化后取 hash」做兜底键。
- **摘要幻觉**：prompt 里明确要求"只输出原文中出现的信息，无法确认就留空"，key_points 尽量引用原句。宁可输出空，不要编造。
- **cron 重复执行**：失败重试 + 幂等入库（写前查重），否则一次抽风会收到三份日报。
- **成本失控**：一上来就全量喂强模型，一周账单不低。粗筛 + 分层是省钱关键，粗筛层必须先于模型层执行。

## 可复用建议

- **prompt 当代码管**：模板放仓库里带版本号，改动走 commit，方便回溯哪个版本效果好；
- **输出永远是结构化 JSON**：渲染和推送单独一层，换渠道（IM / 邮件 / 笔记）不动核心逻辑；
- **长度写死**：如 one_liner ≤ 40 字，防止模型越写越长；
- **源季度清理**：连续两周"有用"为 0 的源直接删；
- **先跑最小闭环**：3 个源 + 1 份日报先稳定两周，再谈扩展。

## 总结

这条管线没有黑科技，核心是工程取舍：去重省成本，分层提质量，结构化保稳定。RSS + LLM 的真正价值，是把"刷信息"变成"收日报"，把注意力留给值得点开的原文。先小规模跑两周，用反馈数据决定加不加源、换不换模型——管线是养出来的，不是一次设计出来的。
