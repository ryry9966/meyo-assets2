## 背景

用 OpenClaw 跑日常自动化之后，模型调用成了成本与隐私的双重顾虑：本地文件、对话记录、执行日志都要过一遍云端 API。本地部署的定位要想清楚——不是替代云模型，而是补一层“低价常驻”：高频、低难度、隐私敏感的任务走本地，深度推理留给云。

## 问题

家用硬件跑 Agent 和跑聊天是两回事：

- 显存/统一内存有限，模型尺寸被硬性约束；
- Agent 依赖稳定的 function calling 和足够长的上下文，小模型恰恰在这两点上最容易翻车；
- 主流运行时的默认配置按聊天场景调优，直接拿来跑 Agent 会踩很多暗坑。

## 做法

1. **先算显存预算**。粗略公式：显存 ≈ 权重 + KV cache。Q4_K_M 量化下，7~8B 约 5GB、14B 约 9GB、32B 约 20GB，上下文每加 8k token 再多 1~2GB。8GB 显存跑 7~8B，16GB 舒适跑 14B，Mac 24GB 统一内存可摸 32B Q4。
2. **选运行时**。起步推荐 Ollama：OpenAI 兼容、一条命令跑起来；要精细控制采样与量化选 llama.cpp；显存富余且有并发需求再上 vLLM。
3. **选模型**。Agent 场景第一优先级是工具调用可靠性，其次才是“智力”。宁可要工具调用稳的 14B，不要量化到 2bit 的 32B。
4. **改关键配置**：显式调大上下文窗口，拉长 keep_alive，给 KV cache 留余量。
5. **接入 OpenClaw**：provider 的 base_url 指向本地兼容端点（如 `http://127.0.0.1:11434/v1`），模型名对齐，先跑一组与你 MCP 工具定义对应的固定调用用例，通过后再上真实任务。
6. **做任务路由**：总结、整理、简单脚本走本地；复杂规划、长链推理走云，按场景切换。

## 踩坑点

- **上下文默认值**：Ollama 默认上下文很小，Agent 跑几轮就“失忆”、工具列表被截断——最高频的坑，务必显式设置。
- **显存“够用”假象**：权重装下了不等于稳了，上下文一长 KV cache 把显存顶爆，轻则 OOM，重则静默回退 CPU，速度差一个数量级。用 `ollama ps` 看真实占用。
- **工具调用格式不兼容**：模型卡写支持 tools，实际输出和框架解析器对不上，产出畸形 JSON。必须用真实 Agent 循环验证，只测聊天没有意义。
- **冷启动延迟**：keep_alive 默认几分钟，超时后重新加载模型，首 token 卡好几秒，自动化场景体验极差。
- **采样参数**：小模型做工具调用建议压低温度，能明显降低 JSON 畸形率。

## 可复用建议

- 沉淀一份 10 条左右的固定测试集：单工具调用、并行调用、长上下文回忆、严格 JSON 输出。换模型就跑一遍，五分钟出结论。
- 显存预算表格化，每次换模型先算“权重 + KV”再定量化档位。
- 把本地端点作为降级方案常驻配置，云服务限流或异常时随时切换。
- 用日志和实测 tokens/s 说话，不凭体感。

## 总结

本地 LLM 对 Agent 用户是个工程问题，不是信仰问题。核心约束是“显存 = 权重 + KV cache”，核心门槛是工具调用可靠性。把它定位成高频、隐私敏感任务的常驻层，深度任务仍交给云模型——在 16GB 显存级别的家用机上，这套组合今天就能落地。
