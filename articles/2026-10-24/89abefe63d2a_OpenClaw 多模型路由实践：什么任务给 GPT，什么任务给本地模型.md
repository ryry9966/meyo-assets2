## 背景

OpenClaw 的典型用法早已不是"一问一答"：主循环里挂着 MCP 工具、定时任务、各种插件，一个跑上几天的 agent 会产生海量模型调用。全走 GPT 这类云端模型，成本和延迟都压不住；全走本地模型，复杂规划和工具调用又经常翻车。多模型路由，就是在这两者之间找平衡。

## 问题

真正的问题不是"哪个模型强"，而是：哪些任务值得为它付云端的溢价？我把一个长期运行的 agent 的调用记录拉出来统计，发现约 70% 的 token 花在三类低难度任务上：会话摘要、记忆整理、日志压缩。这些活本地 7B 级别模型完全够用，但当时全走了云端——钱花在了不该花的地方。

## 做法

**1. 先分类，再选型。** 把 agent 任务分成三档：

- 规划/编排：多步推理、决定调用哪个 MCP 工具 → 云端强模型
- 生成/加工：摘要、翻译、格式转换、回复润色 → 本地模型
- 敏感数据：涉及本地文件、密钥、私有日志 → 默认本地，或脱敏后再上云

**2. 在 OpenClaw 里建两个 model profile**（比如 `cloud-strong` 和 `local-fast`），在路由插件里按任务类型绑定，而不是全局一个模型。

**3. 挂 fallback 链：** 低成本任务先走本地，JSON 解析失败或工具调用连续报错时，升级到云端重试一次。

**4. 记录再迭代：** 每个任务记下模型名、token 数、耗时，跑一周回头看路由规则该不该调。

简化后的路由配置大致长这样：

```yaml
router:
  rules:
    - match: task_type=planning
      model: cloud-strong
    - match: task_type=summarize
      model: local-fast
  fallback: [local-fast, cloud-strong]
```

（字段名以你版本的 OpenClaw 文档为准，思路一致即可。）

## 踩坑点

- **本地模型的 function calling 不稳**，是我踩得最深的坑。同一套工具 schema，云端模型一次过，本地小模型经常字段缺失或格式漂移。缓解办法：开 grammar/JSON schema 约束，外加一次解析失败重试，别指望模型自觉。
- **一次对话中途切模型会丢上下文。** 路由要按"会话/任务"粒度，不要按"单条消息"粒度。
- **别被单次延迟骗了。** 本地模型推理快，但失败重试两次，端到端反而比云端慢。看 P95，不看平均值。
- **embedding 模型别随手换。** 记忆检索的向量一旦换了模型，旧记忆基本作废，需要重建索引。
- **在自己的任务集上评测。** 榜单分数和你 MCP 工具链上的实际表现，是两回事。

## 可复用建议

- **先量化再路由：** 统计一周的 token 分布，把量最大的重复性任务迁到本地，通常这一步就能省一半以上成本。
- **规则保持简单可审计：** 规则表 + fallback 足够了；等规则表撑不住，再考虑用小模型做分类路由，别一上来就上复杂调度层。
- **敏感数据默认本地：** 这是默认值而不是选项，需要上云必须显式声明。
- **给插件留 override：** 个别 skill 在自己的配置里指定模型，别让全局路由一刀切。

## 总结

多模型路由本质是经济学问题叠加可靠性问题：用本地模型吃掉高频低价任务，把云端预算留给真正需要推理能力的环节。先规则、后测量、再迭代——OpenClaw 自带的路由能力足够撑起这套做法，不需要引入更重的调度框架。
