## 背景

Agent 系统的可靠性上限，往往不是模型决定的，而是它调用的外部 API 决定的。LLM 提供商、MCP 工具、第三方 SaaS、内部微服务——任何一环超时或 5xx，整个自动化流程就可能卡死、重复执行，或者更糟：Agent 编造一个"看起来成功"的结果继续往下跑。错误恢复不是锦上添花，是 Agent 上生产的前置条件。

## 问题：失败不可怕，失控才可怕

实际排障中常见三类失控：

1. **无脑重试**：遇到 429/503 立即重试，把限流打成封禁。
2. **假成功**：工具调用抛错，LLM 却基于上下文"脑补"了结果，后续步骤全部建立在虚构状态上。
3. **半完成的副作用**：写操作已发出（比如工单已创建），但响应超时，Agent 不知道成败，重试导致重复创建。

## 做法：把"重试"变成一套机制

**1. 先分类，再重试。** 把错误分成可重试（超时、429、502/503/504）和不可重试（401/403、404、参数校验失败、schema 变更）。不可重试的错误试一百次也不会成功，应立即上抛；429 要读 `Retry-After`。

**2. 指数退避 + 抖动 + 熔断。** 重试间隔 1s → 2s → 4s，加随机抖动避免雷群效应。连续失败达到阈值（比如 5 次）就熔断：一段时间内快速失败，不再打这个 API。熔断期间 Agent 应走降级路径，而不是干等。

**3. 幂等是重试的前提。** 只对幂等操作自动重试。写操作必须带幂等键（如 workflow run ID + step ID），由服务端去重。做不到幂等的外部 API，宁可失败后人工介入，也不要盲重试。

**4. 把结构化错误还给模型。** 别把原始堆栈丢给 LLM。统一封装成错误信封：`{ok: false, error_type: "rate_limit", retryable: true, hint: "wait 30s"}`。模型看到结构化字段才能正确决策——等待重试、换工具，或明确告诉用户"这一步失败了"，而不是编一个结果。

**5. 断点续跑。** 每个工具调用完成后持久化 checkpoint。挂在第 7 步就从第 7 步恢复，而不是从头再跑 6 步——既浪费 token，还可能重复前面的副作用。

## 踩坑点

- **超时设太长**：单个调用 120s 超时，整个 workflow 被一个死 API 拖住。外层超时要小于内层。
- **在 LLM 循环里重试**：让 Agent 自己"再试一次"十几次，token 烧完还没结果。重试应发生在工具层代码里，且有硬上限。
- **把限流当宕机**：429 换个 key 或降速就能过，不该和真宕机共用熔断策略。
- **吞掉错误返回 OK**：插件里 catch 之后 return None，Agent 以为成功了。这是"假成功"的主要来源。

## 可复用建议

- 所有工具调用过同一个包装器：重试、退避、熔断、幂等键、结构化错误、带 correlation ID 的日志，一处实现，全局受益。
- 给每次 Agent 运行设总预算：最大重试次数 + 最大墙钟时间，超了就进降级模式（读缓存 / 排队 / 通知人工）。
- 关键依赖准备 fallback：备选 provider、本地缓存，或干脆一个"诚实失败"的提示。
- 定期做混沌演练：手动把某个 MCP 工具指向一个必超时的地址，看 Agent 是恢复、降级，还是失控。

## 总结

外部 API 挂掉是常态而非异常。工程目标不是"永不失败"，而是失败时行为可预期：快速失败、正确重试、不重复副作用、不虚构结果、可断点恢复。把这五件事做进工具层，Agent 才配得上"自动化"三个字。
