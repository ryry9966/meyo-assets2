刷到 36kr 那条热搜——"刚刚，你每天在用的 Skills 发生了一件大事"，不少人的第一反应不是激动，是懵：Skills？我每天用的到底是啥？这恰恰说明这件事值得聊：一个大多数人还叫不出全名的东西，正在悄悄改写 AI Agent 的协作方式。这篇文章分两层：先花三分钟把 Skills 的机制讲透，再分析这次"大事"到底大在哪、以及普通人怎么搭上这班车。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/530d1391d6bcba2a.png)

## 先补课：Skills 到底是个什么东西

Agent Skills 是 Anthropic 在 2025 年 10 月推出的机制，名字唬人，拆开看朴素得可爱——它的本质是"一个文件夹 + 一份说明书"：

```text
my-skill/
├── SKILL.md      # 说明书：元数据 + 操作指引
├── scripts/      # 可直接执行的脚本
└── references/   # 按需查阅的参考资料
```

SKILL.md 顶部是一段 YAML 元数据，核心只有 name 和 description 两个字段；正文用自然语言写清楚"什么时候用我、怎么用我、用完注意什么"。配合脚本和参考文件，一个 Skill 就是一个可分发、可组合的能力包。

真正的精髓在加载策略，业内叫渐进式披露（progressive disclosure），分三级：

1. **常驻层**：Agent 启动时，只把每个 Skill 的 name + description（每个约几十 token）放进系统提示，相当于图书馆的索引卡；
2. **触发层**：模型判断当前任务和某条描述相关，才去读取 SKILL.md 的正文；
3. **执行层**：真要干活了，才加载脚本和参考文件，甚至直接执行代码。

类比一下：以前的做法是把每一本书全文背进脑子；Skills 是先记住索引卡，要用哪本翻哪本。

## 算一笔账：上下文窗口的经济学

为什么费这么大劲搞三级加载？因为模型的上下文窗口是稀缺资源，而且不是越大越好。

- **token 成本**：假设给 Agent 配 50 个工具，每个说明 500 token，常驻系统提示就是 25000 token；换成 Skills，起步只要 50 × 60 ≈ 3000 token，省下的都是真金白银的 API 账单。
- **注意力稀释**：研究里有个著名现象叫 "lost in the middle"——超长上下文中，模型对中间部分的召回率明显下降。塞得越满，重要指令越容易被淹没。
- **响应速度**：输入 token 越少，首 token 延迟越低，这在 Agent 的多轮循环里会被指数放大。

一句话总结：Skills 是上下文窗口的"分页加载"，用索引换空间。

## 为什么说这次是"大事"：从私有功能到事实标准

机制讲完了，再看事件本身。此前 Skills 是某一家的私有功能——你写的 SKILL.md 只在它自家产品里生效，换个平台全部作废。这次据 36kr 等多方报道，格局变了：Skills 的文件格式开始被其他主流厂商采纳，走向跨平台通用。

这个剧本我们在技术史上见过很多次：

- **RSS**：一个极简 XML 格式，让"订阅"成为互联网基础设施；
- **Markdown**：因为足够简单，从程序员笔记一路蔓延到全行业写作；
- **MCP**（Model Context Protocol）：开放协议让"模型接工具"有了统一插座。

规律都一样：**一个足够简单的格式，一旦跨过平台边界，生态就会指数繁殖。**对开发者，这意味着"一次编写、多处运行"；对普通用户，意味着沉淀的技能可以跟着你走，不被单一平台锁死。更深一层：个人和团队那些散落在聊天记录、网盘、老员工脑子里的 SOP，第一次有了一个标准化的物理载体。

## 动手示范：一个最小可用的 Skill 长这样

空谈不如上手，写周报是成本最低的练手场景：

```markdown
---
name: weekly-report
description: 当用户要求写周报、周总结、
  项目进展汇报时使用，输出团队统一格式
---
# 周报生成规则
1. 固定结构：本周进展 / 风险与阻塞 / 下周计划
2. 每条进展必须带量化数据，没有数据就标注"待补充"
3. 语气克制，不用形容词堆砌
4. 遇到信息缺口，先列清单向用户提问，不要编造
```

存进对应目录、发布，Agent 下次运行时就能自动发现并调用它。一条经验之谈：**description 是整个 Skill 的路由器**——正文写得再漂亮，description 没写清"何时触发"，这个 Skill 就永远沉睡。写 description 的心法是像写检索关键词一样写它，把用户可能说的原话都预判进去。

## 冷思考：Skills 不是银弹

热闹归热闹，几个坑得提前看见：

- **安全面**：Skill 文件本质是"喂给 Agent 的指令"，来源不明的 Skill 等同于供应链投毒入口——一个恶意脚本或一句注入指令，可能让 Agent 泄露数据或执行危险操作。企业使用必须先审核来源。
- **质量参差**：人人能写不等于人人写得好。description 含糊、指令互相冲突的 Skill，轻则不被触发，重则带偏 Agent。
- **它不替代 MCP**：MCP 解决"接入什么能力"（管插座），Skills 解决"怎么把能力用好"（管说明书），是互补关系，不是竞品。
- **兼容格式 ≠ 兼容行为**：不同模型对同一份 SKILL.md 的执行一致性需要实测，别想当然。

## 写在最后：三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-24/002712c045f2fda8.png)

1. **把"解释过三次的事"写成 Skill**：写周报、代码规范、客服话术、数据分析口径——凡是你在团队里重复输出过的知识，都值得变成一个文件夹。
2. **80% 的功夫花在 description 上**：写清触发场景、覆盖用户原话，这一行字段决定 Skill 的生死。
3. **来源审核 + 最小权限 + 版本管理**：只用可信来源的 Skill，脚本先人工过目再执行；把 Skill 目录放进 git，谁改了什么、什么时候改的，全程可回溯。

Skills 这件事的有趣之处在于，它没用任何黑科技——就是一份 Markdown 加一个文件夹。但历史反复证明：简单格式 + 开放标准，历来是生态爆发的前置条件。这一次，值得盯紧。
