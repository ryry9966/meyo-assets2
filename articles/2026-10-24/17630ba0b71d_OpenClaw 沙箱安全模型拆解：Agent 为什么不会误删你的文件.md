## 背景

OpenClaw 的 Agent 默认拿到文件读写和 shell 执行能力——这是它干活的基础，也是最大的风险面。模型偶尔会幻觉出不存在的路径、拼错通配符，或者在"清理临时文件"时理解跑偏，一条 `rm -rf` 的破坏力大家都清楚。很多人的第一反应是在系统提示词里写"不要删除文件"，但这属于采样层面的口头约定，没有机制保证。

## 问题：口头约束为什么会失效

Prompt 是建议，不是边界。原因有三：模型输出是概率性的，长任务里约束会被稀释；工具层拿到参数就直接执行，中间没有人把关；上下文被注入或污染时，"别删文件"这条指令本身可能被覆盖。结论很直接：**安全边界必须放在执行层，而不是提示词里**。

## OpenClaw 的做法：分层的沙箱模型

OpenClaw 的思路是默认拒绝、显式放行，大致四层：

1. **路径规范化与边界校验**。所有文件工具的路径先做 realpath 解析，再校验是否落在 workspace 根目录内。`../` 逃逸、绝对路径越界直接拒绝，工具收到的是明确报错而不是静默失败。
2. **Symlink 二次校验**。解析符号链接后对最终目标再做一次边界检查，防止 workspace 里一个指向 `/` 的软链绕过整个沙箱。
3. **命令分级与拦截**。文件工具属于低危通道；shell 命令走规则引擎，命中 `rm -rf`、`sudo`、向 workspace 外重定向等模式就拦截，或转人工审批。递归删除、批量覆盖默认要求确认，并附带 diff 预览。
4. **能力声明与审计**。工具和 MCP server 声明所需 capability，运行时按会话授予；每次越界尝试写入审计日志，可回放，也能直接沉淀为回归测试用例。

配置大致长这样：

```yaml
sandbox:
  root: ./workspace
  deny_patterns: ["rm -rf", "sudo ", "dd if="]
  require_confirm: ["delete", "batch_overwrite"]
```

## 踩坑点

- **workspace 给太大**。图省事把 root 设成 `$HOME`，隔离形同虚设。只放当前任务需要的文件。
- **软链逃逸**。只查路径字符串不解析 symlink，等于没防。必须 realpath 之后再校验。
- **双通道不一致**。绕过文件工具、直接用 execute 跑命令，就能跳出校验。文件通道和命令通道要挂同一套边界规则。
- **拦截正则太窄**。`rm  -rf` 多个空格、变量拼接都能漏过去。deny 规则要持续补，高危操作宁可走审批。
- **临时目录越界**。缓存写在 workspace 外，任务要么报错，要么诱导模型自己找"替代路径"，反而更危险。

## 可复用建议

- 沙箱只对"执行"负责，prompt 只对"意图"负责，别指望任何一层包办另一层。
- 默认拒绝，放行清单显式维护，不做隐式豁免。
- 破坏性操作一律过审批门，模型自己的判断不作为放行依据。
- 把每次拦截记录沉淀成测试集，规则变更后跑一遍回归。
- 定期做红队演练：故意诱导模型删文件，验证的是整条拦截链，不是单点。

## 总结

Agent 安全的核心，是把"大概率不会出错"变成"出错了也出不了圈"。OpenClaw 的沙箱不追求让模型更聪明，而是让危险操作在机制上不可达。意图层和执行层各自兜底，Agent 才敢真正放进自动化流水线跑。
