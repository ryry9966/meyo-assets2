## 背景

在 OpenClaw 这类常驻 agent 网关里，heartbeat 指让 agent 每隔一段时间自主醒来，检查"有没有该做的事"：到期任务、HEARTBEAT.md 里的检查项、需要主动跟进的会话。它解决的本质问题是——LLM agent 默认被动唤醒，没人说话就永远沉睡，而自动化场景恰恰需要它"自己找活干"。

OpenClaw 默认走轮询：按配置间隔（默认 30 分钟）醒来，HEARTBEAT.md 为空则直接跳过模型调用。这个模型简单可靠，但实际跑自动化时，纯轮询和纯推送都不够用。

## 问题

**轮询的两个硬伤：**

- 延迟下限等于心跳间隔。配 30 分钟，任务平均要等 15 分钟才被捡起；调短到 1 分钟，唤醒次数和 token 成本立刻失控。
- 心跳本身有成本。哪怕大部分唤醒无事可做，只要进了模型就是一次推理开销。

**推送的两个硬伤：**

- 可靠性完全依赖事件源。webhook 丢失、进程重启窗口内的事件，没人补投就永远丢了。
- agent 失去自主性。"没人通知但其实该做"的事（文件变化巡检、久未响应的跟进），事件驱动天然覆盖不了。

单选任何一边，都是在延迟、成本、可靠性三者里挑一个放弃。

## 做法：轮询兜底 + 推送加速

1. **心跳只做检查，不做执行。** 唤醒后先走一段纯代码的判定逻辑：查到期任务表、查未处理事件、查待跟进会话，全部为空就直接返回，不进 LLM。这一步是省钱的关键。
2. **时效性事件全部走推送。** cron 到点直接注入任务队列；webhook 收到事件后向 session 发一条 system 事件做定向唤醒，绕过心跳等待。
3. **心跳上下文隔离。** 心跳产出写入独立存储，不进主会话，避免污染日常对话质量。
4. **推送侧本地落盘。** 事件先持久化再分发，重启后补投递；即使推送全丢，最长也只晚一个心跳周期。

## 踩坑点

- **空转烧钱**：早期心跳每次都进模型，一天几百次白烧 token，改成代码层预判后才降下来。
- **上下文污染**：心跳日志曾直接写进主 session，几天后正常对话明显变味，务必隔离。
- **心跳风暴**：一次心跳里派生了新定时任务，新任务又立刻触发心跳，形成循环。对心跳内派生的唤醒要加去抖延迟。
- **凌晨骚扰**：没配静默时段，半夜主动提醒被投诉。心跳型主动行为必须尊重免打扰窗口。
- **推送单点**：webhook 接收端与 agent 同进程，重启那几秒的事件全丢，落盘补投递后才解决。

## 可复用建议

1. **判定放代码，执行放队列**：要不要醒用确定性逻辑判断，别让模型决定。
2. **间隔分级**：文件巡检 5 分钟、日报 1 天、跟进类半天，别用一个全局心跳包打天下。
3. **假设推送一定会丢**：任何事件通道都要有兜底轮询接住。
4. **观测先行**：记录每次心跳的触发原因、耗时、是否进模型、token 消耗，没有数据调间隔就是拍脑袋。

## 总结

轮询保证"该发现的事最终会被发现"，推送保证"知道的事立刻被处理"，二者不是二选一。heartbeat 设计的工程本质是把边界画清楚：心跳负责兜底检查，事件负责即时加速，中间用代码层判定 + 持久化队列把成本和可靠性都接住。我们目前 30 分钟兜底心跳 + 全量事件推送 + 静默时段的组合，稳定跑了数周，账单和漏事问题都没再出现。
