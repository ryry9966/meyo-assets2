## 背景

社区里不少人已经在用 Agent 自动产出周报、教程和发布稿。生成端基本统一了：LLM 输出 Markdown。但发布端碎片化严重——博客吃完整 Markdown+HTML，公众号只认白名单标签，知乎/掘金是受限子集，RSS 又是另一套。同一份 md，人工调格式的时间常常比写内容还长。

## 问题

让 LLM 直接“输出适合 XX 平台的格式”是条死路：模型对平台规则的记忆不可靠，每次结果不一致，而且无法审计。正确思路是把适配从生成阶段剥离出来，做成一条确定性的构建管线。

## 做法

1. **约束生成端**。系统提示词里定义一份“最小公共集”规范：标题从 `##` 起、代码块必须带语言、禁用行内 HTML、图片只允许占位符 token（如 `{{IMG:1}}`）。让模型只在这个子集内输出。
2. **规范化**。落盘后先过 remark-lint + Prettier（markdown 模式），统一标题层级、列表缩进、CJK 与西文之间的空格。这一步与平台无关，只做一遍。
3. **AST 化**。用 remark 解析成 mdast，后续所有转换基于 AST 写，不要对原始文本跑正则——这是整条管线最关键的决定。
4. **平台序列化器**。每接一个平台写一个 serializer：
   - 博客：mdast → HTML，完整保留；
   - 公众号：mdast → 受限 HTML，外链转文末引用列表，样式全部内联；
   - RSS：mdast → 严格 XHTML 子集。
   
   一个 mdast 源，N 个出口，互不污染。
5. **资产处理**。发布前把 `{{IMG:x}}` 替换为上传后的真实 URL，顺带检查 alt 是否为空。
6. **Dry-run + diff**。每次发布先生成预览，与上次成功版本做 diff，人工扫一眼再确认。别让 Agent 直接对生产环境写入。

把上面整条管线封装成一个技能或 MCP tool，Agent 的职责就收敛为：产稿、调发布命令、读结果。

## 踩坑点

- 模型特别爱输出 `<br>`、`<u>` 这类行内 HTML，公众号会**静默丢弃**，渲染出来就是段落粘连。在 lint 层直接报错，比事后人工修靠谱得多。
- 代码块语言标签不稳定：同一份 shell 内容，有时标 `bash` 有时标 `sh`，高亮插件直接崩。建一个语言别名映射表兜底。
- 转义过度：模型偶尔把 `*` 写成 `\*`，AST 化之前这类问题几乎查不出来。
- frontmatter 泄漏：Agent 有时会自作主张加 YAML 头，发布器必须显式剥掉，而不是假设它不存在。
- 中文排版空格规则别指望模型，交给 formatter。

## 可复用建议

- 管线设计成**幂等**的：同一输入跑两遍结果一致，才敢接进自动化。
- 用 golden file 做快照测试，每次改 serializer 全量跑一遍 diff。
- 每个 transform 输出结构化日志（改了什么、在哪个节点），排查格式问题从二分原始文本变成看日志。
- 占位符 token 是解耦生成与发布的最低成本手段，远比让模型理解平台规则便宜。

## 总结

一句话：**LLM 负责内容，确定性代码负责格式**。生成端约束到最小公共集，中间用 mdast 做单一事实源，平台差异全部收敛进各自的 serializer。做完之后，接入新平台的成本从“重写适配逻辑”降为“新增一个 serializer”——这才是可持续的多发布姿势。
