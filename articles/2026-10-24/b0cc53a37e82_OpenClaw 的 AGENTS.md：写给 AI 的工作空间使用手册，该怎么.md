## 背景

OpenClaw 每次会话启动时，会把工作区（默认 `~/.openclaw/workspace`）里的几个固定文件注入上下文，AGENTS.md 是其中最先加载、权重最高的一份。它相当于你写给 Agent 的岗位说明书：工作区怎么布局、日常流程怎么走、哪些事可以直接做、哪些必须先确认。系统提示词由框架控制，AGENTS.md 完全归你编辑，是普通用户干预 Agent 行为最直接、杠杆最高的一个点。

## 问题

多数人的用法是反的：Agent 做错了，就在聊天里纠正一遍，下次会话照错不误；或者把所有要求堆成几千字的大杂烩，重要规则被稀释，行为反而更不稳定。本质是两个问题：纠错没有沉淀，规则没有结构。

## 做法

我目前在用的 AGENTS.md 结构，供参考：

1. **硬边界置顶**：不发未确认的消息、不删文件、不碰涉及钱的操作。放最前面，防止被长文稀释。
2. **工作区地图**：一屏以内说清各目录和文件的用途，Agent 找东西不再靠猜。
3. **日常流程**：用祈使句写步骤，比如"每天早上先读 MEMORY.md，再汇报待办"。
4. **工具规则**：什么场景用浏览器、什么场景走本地脚本、exec 的允许范围。
5. **记忆约定**：什么值得写进 memory、按什么格式写。

节奏上遵循"一次错误，一条规则"：Agent 每犯一次错，就把教训改写成一条祈使句规则提交进去，而不是在心里骂完就翻篇。整个文件用 git 管理，行为一旦回退，diff 一下就知道是哪条规则改坏的。

## 踩坑点

- **写成散文**。Agent 要的是无歧义的祈使句，"尽量主动一些"这种规则等于没写。
- **规则互相打架**。既写"主动推进"又写"每步先确认"，Agent 只会随机选一个。按场景拆开措辞：哪类任务允许自主，哪类必须先问。
- **文件膨胀**。AGENTS.md 每个会话全量进上下文，我控制在两三屏以内；细节下沉到 TOOLS.md、USER.md、SOUL.md，别都塞一个文件。
- **忘了 Agent 自己也能改这个文件**。要么在规则里明确限制，要么靠 git 兜底。
- **把密钥写进去**。它会进上下文、进日志，API key 只放环境变量。
- **改完不生效**。它是会话启动时加载的，改完记得开新会话再验证。

## 可复用建议

- 把它当 SRE runbook 写：分节、编号、祈使句，别当博客写。
- 每月裁剪一次：过时的规则比没有规则更糟，会持续误导行为。
- 改动后跑一遍固定任务做回归验证，就像改完配置要过冒烟测试。
- 团队/多设备场景下，把 AGENTS.md 纳入版本库同步，保证各处 Agent 行为一致。

## 总结

AGENTS.md 是 OpenClaw 工作区里性价比最高的文件。把它当成给新同事的入职文档来维护：小、准、可版本化、随事故迭代。做到这四点，Agent 的稳定性提升是肉眼可见的。
