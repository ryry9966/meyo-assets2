## 背景

OpenClaw 的 cron 任务本质上是"无人值守的定时 prompt"：到点后 agent 冷启动，没有上下文、没有对话历史，也没有人在线回答它的问题。很多坑其实都源于这一点——大家习惯把聊天场景里跑得不错的 prompt 直接搬进 cron，结果同一个任务跑三次能得到三种输出。

## 问题

我们内部跑过的定时任务大概有十几条：每日简报、仓库巡检、RSS 摘要、价格监控。踩过的坑可以归为三类：

1. **上下文缺失**。instruction 里写"总结今天的讨论"，cron 触发时 agent 根本不知道"今天"指哪个会话，只能瞎猜或空转。
2. **输出没有契约**。没说发到哪、发多长、什么格式，agent 要么把 2000 字丢进群聊，要么发到错误的会话。
3. **失败被吞掉**。工具调用失败后 agent 自己"合理发挥"，产出看起来正常但内容是编的；或者反过来，卡在无限重试里。

## 做法

我把 cron instruction 当成一份"自包含的迷你 spec"来写，固定六个部分：

1. **触发与时间窗**：写明时区和时间范围。用"最近 24 小时"而不是"今天"，避免跨时区歧义。
2. **数据来源**：每个来源单独一行，写清工具名和路径。agent 不会读心，MCP 工具要点名。
3. **执行步骤**：能编号就编号，一步一件事。
4. **输出契约**：投递目标（哪个频道/哪个文件）、长度上限、固定结构。
5. **失败规则**：允许重试几次、失败时如何降级、何时放弃。
6. **禁止交互**：明确写"不要向任何人提问，数据缺失就用默认值"。

一个真实的每日简报任务（节选）：

```
任务：每天 08:30（Asia/Shanghai）投递昨日工作简报。
数据来源：
1. 读取 ~/notes/journal/ 最近 24 小时新增的 md 文件；
2. 用 github 工具列出昨日合并的 PR 标题。
输出：发送到 #daily-standup，200 字内，分「进展/风险/计划」三段，只列事实。
规则：不要提问；某来源失败则跳过并注明，最多重试 1 次；
全部为空时也发送一条极简占位消息。
```

## 踩坑点

- **默认它有记忆**。cron 是冷启动，凡是依赖"上次对话"的写法都要改成显式引用文件或数据源。
- **让它自由发挥输出**。没有长度上限和结构约束，token 花费和群聊噪音都会失控。
- **一个任务干三件事**。简报+巡检+备份塞进一条 instruction，任何一环失败都会拖垮整体。拆开，用文件传递中间结果。
- **忘了占位输出**。"没查到就什么都不发"是最糟的策略——你无法区分"没数据"和"任务挂了"。宁可发一句"昨日无记录"。
- **上线前不手动跑**。OpenClaw 支持手动触发，先跑两遍看输出再定时，能省掉大半夜的排查。

## 可复用建议

- 把六段式模板存成 snippet，新任务只填空；
- instruction 也要版本化，和代码一样进 git，改动可回溯；
- 中间数据落文件比塞在 prompt 里可靠，也让任务之间可以解耦串联；
- 定期翻一遍任务的历史输出，prompt 漂移和工具变更往往先从输出形态上露馅。

## 总结

Cron 任务的 instruction 不是聊天 prompt 的缩写版，而是一份交给"实习生"的一次性工单：时间、来源、步骤、交付物、异常处理、禁止事项，一个都不能少。把这六件事写清楚，定时任务的稳定性会上一个台阶——毕竟没有人愿意每天早上八点半收到一条支离破碎的简报。
