## 背景

写自动化任务的人迟早会撞上这个场景：cron 脚本因机器重启多跑了一次、webhook 被上游重发、Agent 的定时任务超时后被调度器重新拉起。第一次遇到通常会慌——文件写了两遍？消息发了两条？数据重复入库？

自动化和人工操作最大的区别，是"执行次数"从来不受你控制。重试是常态，不是异常。所以与其祈祷任务只跑一次，不如把任务设计成"跑几次结果都一样"。这就是幂等性。

## 问题

先界定什么叫"出问题"。一个任务执行两遍，如果最终状态和执行一遍完全一致，它就是幂等的；如果不一致——多了一行数据、多了一条通知、文件追加了一次——它就是不幂等的。

常见的不幂等模式：

- **追加写入**：`echo "result" >> report.log`
- **无条件创建**：每次执行都新建一条记录、发一条消息
- **增量同步**：按"上次时间"拉数据，重复执行就重复插入
- **调外部 API 无幂等键**：重试导致重复下单级别的故障

## 做法

几个成本从低到高、我实际在用的做法：

**1. 写入改成"目标状态"而非"操作指令"。** 命令式写法是"追加一行"，声明式写法是"让文件内容等于 X"。落地方式：先写临时文件，再原子 rename 覆盖目标。执行多少次，结果都是同一份内容。

**2. 用业务幂等键去重。** 给每次逻辑执行算一个稳定 key：输入内容 + 目标对象 + 业务周期（比如当天日期），而不是用时间戳。执行前先查"这个 key 做过没有"，做过就跳过。存哪里都行——SQLite 表、带 TTL 的 Redis key，甚至一个以 key 命名的标记文件。

**3. 外部副作用单独封装。** 发消息、调第三方 API 没法"覆盖重写"，只能靠幂等键。好在多数现代 API 支持 `Idempotency-Key` 之类的头；不支持的话，本地先落"待发送"记录，成功后再标记，重试时跳过已成功的。

**4. Agent/MCP 场景的加一层。** 让模型在执行写操作前先输出结构化 plan，对 plan 求幂等键；插件内部对"写"类工具做 key 校验，"读"类操作天然幂等不用管。

## 踩坑点

- **check-then-act 的竞态。** "先查再写"在单进程够用，但任务可能并发触发（定时 + 手动撞车）时，查询和写入之间仍有窗口。用数据库唯一约束或文件锁兜底。
- **幂等键里掺了随机因素。** key 里带执行时间、随机 ID、LLM 生成的变体话术，每次 key 都不同，去重形同虚设。key 只能从业务语义派生。
- **只防了重试，没防乱序。** 抓取类任务两次结果不同，覆盖写会更新成新数据，这通常是对的；但任务间有依赖时，光幂等不够，还需要版本号或时间戳做乐观锁。
- **标记和动作顺序颠倒。** "先标记已发送，再发消息"，一旦标记成功、发送失败，这条就永远丢了。应该"先做事，后标记"，或引入中间态允许重放。

## 可复用建议

- 写新任务前先问一句："这个任务跑两遍会怎样？"答不上来就先补幂等。
- 把所有写操作收敛到少数几个函数/插件出口，统一加幂等键逻辑，别散落各处。
- 优先声明式（目标状态）而非命令式（操作序列），很多幂等问题会自然消失。
- 每个任务留一份执行记录（key、时间、结果），排查问题时它是唯一线索。

## 总结

幂等不是高级技巧，本质是一次假设转换：把"假设任务只执行一次"换成"假设任务会被执行任意次"。前者靠运气，后者靠设计。自动化规模越大、链路越长，重试和重复越不可避免——让重复变得无害，自动化才敢真正放手跑。
