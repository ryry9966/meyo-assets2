## 背景

玩 Agent 和 MCP 久了，迟早会遇到两个问题：一是工具调用经常带敏感上下文——本地文件、聊天记录、剪贴板内容，全量过云端总归不踏实；二是 agent 循环一次任务几十次调用，API 费用悄悄累积。把一个中等规模的模型搬到自己机器上，做隐私敏感任务和高频简单任务的后端，是个性价比不错的折中方案。

## 问题

实际落地时，真正的难点不是“跑起来”，而是这三件事：

1. 显存不够，长上下文一动就爆；
2. 量化之后模型“降智”，工具调用成功率明显下滑；
3. agent 循环把单次延迟放大几十倍，本地推理速度撑不住。

## 做法

**第一步：盘点硬件。** 显存是硬通货。8GB 显存跑 7B/8B 的 Q4 量化；12–16GB 跑 14B；24GB 可以碰 32B Q4 或 MoE 结构的 30B 级模型（激活参数小的那种）。Mac 用户按统一内存的 60–70% 估算可用额度。注意内存带宽直接决定 tokens/s，对 agent 体验的影响比峰值算力更大。

**第二步：选推理后端。** Ollama 起步最快；需要细控 KV cache 量化、上下文上限、线程数就用 llama.cpp；多卡或高并发场景再考虑 vLLM。三者的共同点是都暴露 OpenAI 兼容接口，接入成本一致。

**第三步：选模型。** 优先选原生做过 tool calling 训练的模型，这一点比参数量重要。量化等级 Q4_K_M 是默认起点，先验证工具调用成功率，再谈别的。

**第四步：接入 OpenClaw。** 模型配置指向本地 endpoint（形如 `http://127.0.0.1:11434/v1`），把 context 上限设小一点，采样参数保持简单，不要开太多花活。

**第五步：压测。** 准备一个 10 步左右的典型 agent 任务，记录三个数：端到端耗时、工具调用成功率、长上下文下是否爆显存。这三个数决定了这套部署能不能进日常工作流。

## 踩坑点

- **KV cache 才是显存杀手。** 8B Q4 权重约 5GB，但 32K 上下文的 KV cache 能把总占用直接翻倍。别只盯着模型体积算账。
- **量化过低毁工具调用。** Q3 及以下时模型输出的 JSON 经常格式崩坏，agent 表现突然变差，先查量化等级。
- **不是所有模型都会 function call。** 有些只是“看起来会”。实测失败率超过 10% 就换模型，别靠改 prompt 硬救。
- **延迟在循环里被放大。** 单次响应 3 秒，乘以三十次调用就是灾难。tokens/s 低于 20 的模型在 agent 场景基本不可用。
- **冷启动。** Ollama 默认会卸载闲置模型，常驻服务记得设 keep_alive，避免每次调用都重新加载。

## 可复用建议

- **分层路由：** 隐私敏感、高频简单任务走本地；复杂推理任务 fallback 到云端。OpenClaw 里配两组模型，先手动切换跑通，再考虑自动路由。
- **建立基线任务集：** 每次换模型或换量化等级，固定跑同一组任务，用数据对比，不凭感觉。
- **context 能小则小：** 精简系统提示词、让 MCP 工具返回值做截断，省下来的显存往往比换更大的模型更划算。

## 总结

本地部署的门槛不在“能不能加载模型”，而在“能不能在 agent 循环里稳定干活”。显存算清楚、工具调用实测过、延迟压得住，一台中端主机就能承接相当一部分日常自动化任务。原则很简单：先小后大，先测后换。
