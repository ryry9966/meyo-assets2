## 背景

OpenClaw 的主会话按通道维护，一条会话里所有消息、工具调用、exec 输出、浏览器快照都会持续堆进上下文。日常问答没问题，但一旦在主会话里直接跑重活——批量重构、日志分析、多页抓取——几十轮工具调用的原始输出就全留在历史里。常见后果是：响应变慢、模型开始"忘事"、token 成本肉眼可见地涨。

## 问题

所谓"污染"，落到工程上是三种：

1. **上下文污染**：子任务的中间产物留在主会话历史，挤占有效上下文，触发不必要的 compaction。
2. **状态污染**：子任务改了共享工作区文件、装了全局依赖、动了后台进程，主会话后续步骤踩坑。
3. **语义污染**：中间的失败与重试把主会话的规划带偏，比如让它误判某个方案"跑不通"。

## 做法

1. **重活一律 `sessions_spawn`**。子 agent 拿到独立的 session id 和独立上下文，跑完后只有一条结果（first result）回传主会话，过程细节全部留在子会话里。
2. **任务提示词自包含**。spawn 的 task 里写清五件事：目标、输入路径、输出约定、约束、返回格式。不要整段粘贴父会话历史，需要上下文就给文件路径让它自己读。
3. **工件落盘，结论回传**。要求子 agent 把长输出写进工作区文件，返回值只留结论摘要和文件路径。主会话要细节时用 `read` 去取，或按需用 `sessions_history` 回查子会话，而不是让一切默认回流。
4. **收紧子 agent 能力**。spawn 时配好 tools 允许列表和独立 cwd/工作区，敏感操作放 sandbox。子会话能碰的东西越少，能污染的面就越小。
5. **验证隔离生效**。跑完后先 `sessions_list` 看会话清单，再翻主会话历史：里面应该只有那条结果摘要，没有子 agent 的工具调用流水。给子会话加 label，方便审计和事后续聊。

## 踩坑点

- 把父会话整段历史塞进 task：等于把污染原样带过去，隔离白做。
- **session 隔离 ≠ 文件隔离**。工作区可能是共享的，子 agent 在共享目录里 `mv`/`rm` 一把，主会话照样遭殃，务必确认 cwd 或上 sandbox。
- spawn 是一次性任务，返回即结束。想多轮交互要用 `sessions_send` 加 label 定向发消息，别在原地等它"回来"。
- 返回值超长会被截断，主会话拿到半截结论。约定"结论 + 路径"格式基本能避开。
- 密钥和环境变量随默认配置透传给子 agent，按最小权限裁剪。
- 并行 spawn 多个子 agent 时，让它们各写各的输出文件，别约定写同一个路径。

## 可复用建议

团队内固定一个 spawn 模板：目标 / 输入 / 输出 / 约束 / 返回格式，五段式，缺一段不 spawn。再立一条约定：**工件落盘、结论回传、路径可查**。执行侧的判断标准很简单——预计超过十轮工具调用的任务，默认走子 agent，主会话只做规划和验收。定期用 `sessions_list` 清理不再需要的子会话，避免僵尸会话占资源。

## 总结

session 隔离的本质，是把"过程"留在子会话，把"结论"交给主会话。上下文隔离靠 spawn，状态隔离靠独立工作区或 sandbox，语义隔离靠自包含的任务提示词和固定的返回格式。三件事都做到位，主会话才能长期保持干净、可审计、可预测。
