## 背景

Agent 跑了几个月后，memory 里会积下几千条记录：用户偏好、项目决策、踩过的坑、一次性任务的上下文。`memory_recall` 是这些记忆的唯一入口，检索质量直接决定 agent "记不记得住"。社区里常见的争论是：上向量库做语义搜索，还是老老实实用全文检索？

## 问题

两条路线各有翻车现场：

- **纯语义**：问"上次那个部署脚本的端口改成多少了"，召回回来一堆"部署流程讨论"，真正那条记录排在第 8 位之后。语义模型擅长"意思相近"，但对错误码、配置项、路径这类强实体很钝。
- **纯全文**：关键词换个说法就空手而归。搜"权限"找不到写着"鉴权"的记录，中文分词不对时更糟。

单独用哪条都有明显短板，真正的问题是怎么组合。

## 做法

我做了个轻量实测加落地改造，步骤如下：

1. 从 memory 库抽 60 条真实 recall 请求和期望命中的记录，手工标注成评测集。
2. 同一份数据跑两路：embedding 召回（bge-m3，中文场景表现稳）和 SQLite FTS5 全文（配 jieba 分词）。
3. 分别统计 hit@5：语义约 72%，全文约 65%，但两者命中的记录重合度只有六成左右——互补性很强。
4. 上混合检索：两路各取 top 20，用 RRF（倒数排名融合）合并，hit@5 提到 88%。
5. 再加一条路由规则：query 里含错误码、端口号、文件路径这类高置信实体词时，调高全文权重；纯自然语言描述则偏向语义。

## 踩坑点

- **chunk 切分切断上下文**：一条"决定把超时从 30s 改成 60s，因为 X"被切成两块，语义召回只捞到后半句，事实不完整。改成一条 memory 一个 chunk 存储后消失。
- **embedding 对短 query 里的实体词基本无感**：只测长句时以为没问题，换短查询立刻露馅。
- **FTS5 默认分词对中文按单字切**，召回质量很差，必须显式换 jieba 或 simple 分词器。
- **向量索引有写入延迟**，写入后立刻 recall 会漏。改成写入时同步 upsert 单条向量，成本可接受。

## 可复用建议

- 别二选一。混合检索是性价比最高的解法，RRF 几十行代码就能实现，暂时不需要上重排序模型。
- 动手前先建个小评测集（哪怕 50 条），凭感觉调参纯属浪费晚上时间。
- memory 写入时就定好结构：一条记录一个主题一个 chunk，别指望事后切分。
- "高实体词 query 走关键词优先"这条规则，收益比换 embedding 模型大得多。

## 总结

memory_recall 的检索质量不是"选哪个搜索引擎"的问题，而是"理解你的记忆数据长什么样"的问题。语义搜索解决换个说法也能找到，全文搜索解决精确实体一击即中，两者叠加再加一条简单路由，几十行代码就能把召回率从七成拉到九成。先建评测集，再动手改，是这个问题的正确打开方式。
