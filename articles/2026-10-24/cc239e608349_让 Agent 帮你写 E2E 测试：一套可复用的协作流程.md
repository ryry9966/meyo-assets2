## 背景

E2E 测试大概是前端工程里性价比最难平衡的部分：价值真实，但编写慢、维护累。我们在把 OpenClaw 接入日常工作流之后，尝试让 Agent 参与测试生成，跑了两三个月，沉淀出一套还算稳定的做法，分享出来供参考。

## 问题

手工写 E2E 的痛点很集中：

- 选择器靠猜，写完跑一遍才发现错；
- 断言写得敷衍，只验证"页面没崩"；
- 流程一改，测试成批失效，没人愿意修。

直接把需求丢给 Agent"帮我写个测试"，产出往往更好看但更不可信——它会编造不存在的选择器。本质原因有二：Agent 缺少对真实页面的感知，也没有团队测试规范的上下文。

## 做法

我们把它拆成四步：

1. **喂规范，不喂全库。** 给 Agent 的上下文固定为三样：路由表、Page Object 目录、2~3 个团队认可的示例测试。示例的作用是锚定风格——命名、fixture 用法、断言粒度都从示例里学，比任何文字说明都有效。

2. **让它真的打开浏览器。** 通过 Playwright MCP 这类浏览器工具，让 Agent 实际执行一遍用户流程，从 DOM 里取真实选择器，而不是凭训练数据想象。这一步是整套方案能跑通的关键。

3. **探索与生成分离。** 实践中让同一个会话既走流程又写代码，上下文很快被中间输出污染。我们改成两段式：先让 Agent 以"探索者"身份记录每步操作和真实元素信息，输出结构化的步骤清单；再开新会话，以"实现者"身份把清单翻译成测试代码。产出质量明显更稳。

4. **失败回喂。** 测试跑挂后，把失败截图、错误信息和对应测试文件一起丢回给 Agent 修。修两轮还挂的，人工接手——这通常意味着流程本身有竞态或测试数据问题，不该让 Agent 硬绕。

## 踩坑点

- **断言必须人审。** Agent 默认写的断言偏弱，"能打开"不等于"对了"。我们的规则是：Agent 负责操作序列和选择器，断言语义由人补齐或逐条确认。
- **警惕固定 sleep。** Agent 很爱写 `wait(3000)`，本地能过，CI 上就是 flake 源。发现即替换为显式等待条件。
- **测试数据要种子化。** 让 Agent 现造测试账号，迟早撞上环境里的脏数据。固定 fixture 优先。
- **上下文别贪多。** 塞整个仓库进去，反而让它写出不符合项目约定的代码。三个好示例胜过一万行源码。

## 可复用建议

- 把 Agent 当成"打字很快的初级工程师"：初稿成本趋近于零，但正确性的归属永远在你。
- 在仓库里维护一份测试规范文档，让 Agent 每次自动带上，避免依赖口头约定。
- 用真实用户路径（bug 单、埋点里的 top 流程）决定让 Agent 生成哪些测试，别追求覆盖率数字。
- Agent 生成的测试单独开 PR，按正常 code review 流程走，不因为"是 AI 写的"就放宽标准。

## 总结

Agent 写 E2E 测试不是"一键全自动"，而是一次工作流重构：感知交给浏览器工具，风格交给示例，初稿交给模型，正确性留给人。按这套分工跑下来，我们把关键路径测试从零补齐的时间，压缩到了纯手工的大约三分之一。它没有消灭测试工作，只是让"写"这个环节不再痛苦——维护和断言设计，依然是工程师的活，也应该是。
