## 背景

用 OpenClaw 搭过长期记忆的都知道，`memory_recall` 的检索质量直接决定助手“记不记得住事”。我们的场景是：助手沉淀了几千条会话片段、用户偏好、项目决策记录，每次对话前召回 top-k 条注入上下文。一开始只用了语义搜索，跑了一个月后发现召回结果时好时坏，才认真把两条技术路线都测了一遍。

## 问题

两条路线的分歧点很典型：

- **语义搜索**（embedding + 向量库）：对“换一种说法”的查询友好，比如问“之前那个部署失败的事”能召回记录为“CI 流水线报错”的条目。
- **全文搜索**（BM25 / SQLite FTS5）：对精确关键词、命令、专有名词召回极准，比如搜 `--force-rebuild` 这种 token，语义模型基本无能为力。

单独用任何一个，都会在另一类查询上翻车。

## 做法

最后我们落地的方案是**双路召回 + RRF 融合**，步骤如下：

1. **记忆入库时**统一按条目切分，每条控制在 200 字以内，同时写入 FTS 索引和向量索引（embedding 用的是 bge-m3，中文效果稳定）。
2. **查询时**两路并行：BM25 取 top-20，向量检索取 top-20。
3. 用 **Reciprocal Rank Fusion** 合并：`score = Σ 1/(60 + rank)`，取融合后的 top-5 注入上下文。
4. 加了简单的**时间衰减系数**，30 天前的记忆权重乘 0.8，避免陈年旧事压过近期决策。

伪配置大概长这样：

```text
recall:
  fulltext: { top_k: 20, tokenizer: jieba }
  vector:   { top_k: 20, model: bge-m3 }
  fusion:   { method: rrf, k: 60, final_top_k: 5 }
  decay:    { after_days: 30, factor: 0.8 }
```

## 踩坑点

- **中文全文检索别用默认分词器**。FTS5 默认按空格切词，中文直接失效，必须接 jieba 或者用 trigram 方案。这个坑让我们第一轮测试全文搜索“看起来完全不能用”，其实是配置问题。
- **embedding 对短查询效果差**。用户输入“那个 bug 修了吗”这种不到十个字的查询，向量召回很飘。解决方法是召回前先用小模型把查询扩写成一句完整描述。
- **记忆条目切太长会稀释向量**。一条 800 字的混合内容，向量会变成“什么都有一点”，单条主题聚焦在 100~200 字效果最好。
- **RRF 的 k 值不用迷信 60**。60 是论文里的经验值，我们试了 30~100，体感差别不大，不用花时间调。

## 可复用建议

- **别一上来就上向量库**。记忆量在几千条以内时，先做好全文检索 + 好的分词，收益可能已经够用。
- **建一个小评估集再动手**：准备两类查询（同义改写类 + 精确关键词类）各 20 条，改完检索方案跑一遍，比肉眼感觉可靠得多。
- **混合检索优先考虑 RRF**，不需要归一化两路的分数量纲，实现成本低，效果稳定。
- 记忆条目**入库时就定好粒度和衰减策略**，事后清洗的成本远高于事前设计。

## 总结

这不是一个“哪个更好”的问题，而是“哪类查询多”的问题。语义搜索解决说法不一致，全文搜索解决精确命中，生产环境里两者缺一不可。我们的结论：BM25 打底、向量补盲、RRF 融合，是当前性价比最高的组合。整套方案在单机 SQLite 上就能跑，几百行代码，建议有同样需求的同学直接从这个起点开始。
