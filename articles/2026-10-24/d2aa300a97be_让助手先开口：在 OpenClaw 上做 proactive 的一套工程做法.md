## 背景

大多数助手的默认形态是"你问，它答"。OpenClaw 网关接好聊天频道和工具之后，本质上还是一个 reactive 系统：不触发，不运行。但很多事并不需要你记得去问——CI 昨晚红了、日历十点有个会、某张工单三天没动静。事件早就发生了，缺的是有人把它们捞出来、判断值不值得打扰你。OpenClaw 手里有 cron 任务、webhook 入口和 MCP 工具三块积木，proactive 并不需要新框架，缺的是中间那层策略。

## 问题

我们最早的做法很直接：监控告警 webhook 直连一个 skill，让模型润色后推到私聊。跑了三天暴露出三个问题：

1. **噪音**。一条抖动的告警 40 分钟内推了 40 多遍，用户（也就是我自己）当天就把频道静音了。主动能力一旦被静音，等于永久失效。
2. **成本**。每个事件都过一遍 LLM，token 花费是之前的 3 倍，而大部分事件根本不值得打扰。
3. **无法回溯**。想知道"为什么这条推给我"，没有记录可查。

## 做法

改造后的链路分五步，全部用 OpenClaw 现有能力实现：

1. **接事件源**。cron 任务每天早上拉日历和待办做摘要；webhook 入口接 GitHub 和监控告警；再加一个下午的"陈旧工单巡检" cron，用只读的 MCP 工具查询工单系统。事件先落到 append-only 的事件日志（一张 SQLite 表），这一步不调 LLM。
2. **廉价预过滤**。写一个纯规则的 gate：关键词匹配、阈值比较、状态边沿触发（比如只对 new→firing 触发，不对 firing→firing 重复触发）。规则挡掉 80% 以上，通过的才进模型。
3. **LLM 判断"值不值得打扰"**。用小模型、低温度，输出三档：silent（只记日志）、digest（进每日摘要）、push（立即推送）。判断标准写在 prompt 里：与用户当前工作是否相关、是否有时效、能否自行恢复。
4. **状态与限流**。SQLite 里存 dedupe key、cooldown 窗口和每频道的 quiet hours。同一 key 在冷却期内直接 silent；夜间只放行高严重度的 push，其余顺延进 digest。
5. **提议而非执行**。push 消息固定三段式：发生了什么、为什么值得你看、可选哪些动作（"要我重启吗？""要不要静音两小时？"）。助手不主动执行任何不可逆操作，只给选项。

## 踩坑点

- **冷却时间最容易漏**。第一次上线没做 dedupe，同一告警十分钟把推送预算耗光。
- **时区**。cron 跑在 UTC，quiet hours 写的本地时间，"夜间免打扰"形同虚设。现在统一在策略层换算。
- **别让 LLM 当第一道闸**。它太擅长"把一切解释成紧急"，规则先挡一道，模型只做剩余的判断。
- **干扰要有预算**。现在每频道每天 push 上限 5 条，超出的自动降级进 digest。数字定下来后，用户才敢不静音。

## 可复用建议

- 三档分级（silent / digest / push）比二档好用得多，摘要档承接了大部分"重要但不紧急"。
- 事件日志坚持 append-only，每条 push 能对应回原始事件，排障时间省一半。
- 策略全部收敛到一个 YAML：事件源、规则、冷却、预算、静音时段，改行为不用碰代码。
- 先在沙箱频道跑一周，把 push 统计导出来看分布，再定预算数值。

## 总结

proactive 不是让模型话多，而是让打扰变少。真正的能力在策略层：什么时候安静、什么时候说话、说什么、给不给选项。用 OpenClaw 现成的 cron、webhook 和 MCP 工具，加上一个廉价的预过滤和分级输出，一个晚上就能搭出第一版。先让用户相信"它不会乱喊"，主动能力才留得下来。
