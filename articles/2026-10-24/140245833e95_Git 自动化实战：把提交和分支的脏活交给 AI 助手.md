## 背景

团队日常里最耗时间的往往不是写代码，而是代码之外的机械操作：写 commit message、切分支、清理已合并分支、整理暂存区。这些活重复、琐碎，但又不能乱来。OpenClaw 这类能接 MCP 工具的 Agent，天然适合接管这一层——前提是你给它划好边界。

## 问题

直接把 shell 权限丢给 Agent，会撞上三个典型坑：

1. **状态不一致**：Agent 拿到的 `git status` 可能是几轮对话前的结果，基于旧状态做操作就是事故来源。
2. **权限过大**：能 push 就意味着能 force push，能改历史就等于能覆盖同事的工作。
3. **语义偏差**：diff 只能说明"改了什么"，不能说明"为什么改"。Agent 只看 diff 生成的 commit message，经常写得很像但不对。

## 做法

我们的思路浓缩成三条规则：**读操作放开，写操作加护栏，破坏性操作只留给人**。

**第一步：只读工具先行。** 通过 MCP 先暴露 `git status / log / diff / branch`，让 Agent 空跑一到两周，观察它的判断质量——尤其是"哪些分支可以删"这种判断。

**第二步：写操作走包装脚本，不走裸 shell。** 不要给 Agent 直接的 `git commit` 权限，包一层脚本：

```bash
#!/bin/bash
# agent-commit.sh：只允许在 feature/* 分支提交
branch=$(git branch --show-current)
[[ "$branch" == feature/* ]] || exit 1
git add -- ':!*.env*' && git commit -m "$1"
echo "$(date) | $branch | $1" >> ~/agent-git.log
```

三个要点：分支白名单、排除敏感文件、每次操作落日志。

**第三步：提交流程拆两段。** 让 Agent 先输出 message 草稿和理由，你确认后再执行。跑熟之后，只对 non-trivial 提交保留人工确认。

**第四步：分支清理用"提案-确认"模式。** Agent 定期列出已合入 main 且超过 N 天的分支，生成删除清单，你回一个确认词才真正执行 `git branch -d`。

## 踩坑点

- **每次操作前强制重跑 `git status`**，不要信对话里的旧状态。
- **`git add -p`、`git rebase -i` 这类交互式命令在 Agent 的非交互 shell 里会卡死**，改用 `git add -A` 加明确路径参数。
- **push 一律不允许**。Agent 本地提交，push 留给人，这一条能挡掉九成灾难。
- **合并冲突不要让 Agent 自己解**，它倾向随便选一边。检测到冲突就停，交还给人。
- message 生成准确率大概七八成，**正式仓库保留人工确认**，个人实验仓库可以全自动。

## 可复用建议

- 工具粒度越小越好：一个"生成 commit message"的工具加一个"安全提交"脚本，好过一个万能 git 工具。
- 所有 Agent 的 git 操作写进同一个日志文件，出问题能回放。
- 禁止清单（force push、改历史、动 main）不能只写在系统提示词里——提示词可能被绕过，**要在脚本层面硬拦**。

## 总结

Git 自动化的收益不在省下敲命令的那几十秒，而在消除"忘记提交""message 乱写""分支堆积"这类慢性病。关键是把 Agent 当成一个手速很快但需要明确 SOP 的初级同事：给它读的自由、写的护栏，和一条不可逾越的红线。
