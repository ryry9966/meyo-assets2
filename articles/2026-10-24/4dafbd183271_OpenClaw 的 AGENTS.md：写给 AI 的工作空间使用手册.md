## 背景

OpenClaw 每次会话启动时，对工作空间的了解几乎为零。它不知道这个仓库用 pnpm 还是 npm，不知道测试怎么跑，不知道哪些目录是生成物不能碰。README 是写给人看的——讲愿景、讲安装；而 agent 需要的是另一类信息：操作性的、约束性的、可执行的事实。

AGENTS.md 就是补这个缺口的约定：放在仓库根目录（或子目录）的 Markdown 文件，OpenClaw 在会话开始时读取，作为它在本工作空间行动的默认依据。可以理解为"写给 AI 的 CONTRIBUTING.md"。

## 问题

没有 AGENTS.md 时，我们反复遇到三类摩擦：

1. **重复试错**：agent 用错包管理器、现写一个已存在的脚本、忽略项目命名约定，每次会话都要重新踩一遍。
2. **上下文浪费**：大量 token 花在让它"重新发现"这些事实上，真正干活的预算被挤占。
3. **产出不稳**：同一个任务，这次符合规范，下次就跑偏，因为规范只存在于老成员的脑子里。

## 做法

我们目前用的模板，控制在 100 行以内：

```markdown
# AGENTS.md
## 项目概览
三句话讲清楚这是什么、技术栈、入口在哪。
## 常用命令
构建/测试/lint 只写命令本身，复杂逻辑收进 Makefile，这里引用目标名。
## 目录结构
只列"不看会出事"的部分：生成物目录、不能手动改的文件、核心模块位置。
## 约定
命名、错误处理、提交信息格式——只写 agent 猜不到的那部分。
## 禁止事项
不要升级依赖、不要动迁移文件、不要绕过 lint。
```

两条原则贯穿始终：

- **短**。整个文件每次都进上下文，它就是 prompt 预算，每多一行都在稀释重点。
- **具体**。"写出高质量代码"没有用；"用 pnpm，提交前跑 `pnpm test`"才有用。

维护方式是错误驱动：agent 犯了同一个错两次，就把对应规则写进去。Monorepo 场景可以在子包再放一份 AGENTS.md 覆盖根文件的局部约定，但只写差异，不复制。

## 踩坑点

- **把 README 抄进来**。两份文件受众不同，重复内容还会在重构后各自腐烂。
- **和 CI/工具链矛盾**。文件里写 npm，CI 实际用 pnpm，agent 会忠实地执行错误版本。命令类信息保持单一来源，AGENTS.md 只做引用。
- **写完就忘**。重构后命令失效，文件就从资产变成误导源。我们把它挂进 PR 模板：动了构建流程或目录结构，先检查是否需要同步更新。
- **塞敏感信息**。它会被读进上下文、可能随仓库同步到各处，token 和密钥绝对不能出现。
- **嵌套文件静默覆盖**。子目录的 AGENTS.md 生效时并不总是直观，排查 agent 行为异常时，先确认它实际读到了哪几份、以哪份为准。

## 可复用建议

- 从最小模板起步：概览 / 命令 / 约定 / 禁止事项，四段足够，别急着扩。
- 命令逻辑收进 Makefile 或脚本，AGENTS.md 只留一层薄引用，避免两处维护。
- 像评审代码一样评审它的 diff，规则变更走同样的 review 流程。
- 定期做一次"冷启动测试"：新开会话让 agent 跑一遍主流程，看它还需要问什么问题——每一个问题都是一条缺失的规则。

## 总结

AGENTS.md 是投入产出比最高的一类自动化：写一次，之后每个会话都受益。它不神秘，本质上就是一份认真维护的操作手册——区别只在于读者是 AI。把它当代码的一部分进版本库、走 review，它会持续回报你省下的那些重复解释。
