## 背景

用 Agent 批量产出内容后，真正的工程量往往不在生成，而在分发。LLM 输出 Markdown 很稳定，但目标平台——公众号、知乎、掘金、静态站、RSS——对格式的接受度差异很大。我们的做法是把"格式适配"从每次发布的手工操作，收敛成一条可复用的 Markdown 管线，由 OpenClaw 的自动化任务和 MCP 工具串起来。

## 问题

直接把 AI 生成的 Markdown 投到各平台，会遇到三类问题：

1. **生成质量不稳定**：标题层级跳跃、代码块缺语言标注、图片链接是编造的相对路径、列表嵌套被截断。
2. **平台能力不一致**：公众号不认 Markdown，且会剥离 class 只保留内联样式；部分平台不支持 GFM 表格和脚注。
3. **重复发布与状态丢失**：重跑任务产生重复文章，发布状态没有回流，无法幂等。

## 做法

管线分四段，每段是纯函数式转换，便于单独测试：

**1. 归一化**。对原始输出做 lint 与修复：标题统一从 H2 开始、补齐代码块语言、校验图片 URL 可达、剥掉模型偶尔夹带的 HTML。用 markdownlint 规则集加少量自定义规则，放进 CI 跑。

**2. 元数据收敛**。所有内容统一为一份带 frontmatter 的 Markdown 作为唯一事实源：title、slug、tags、cover、平台开关。Agent 只负责正文，元数据由管线从任务上下文注入，不让模型自由发挥。

**3. 平台适配器**。每个适配器输入归一化后的 Markdown，输出平台载荷：

- 公众号：MD → 内联样式 HTML，主题参数化；
- 掘金/知乎：MD 直传，图片先上传再重写 URL；
- 静态站：保留 MD，仅转换 frontmatter。

适配器不访问网络、不读全局状态，输入输出可用 golden file 做快照测试。

**4. 发布与回执**。默认 dry-run，输出 diff 供人工确认，真实发布需显式参数。以内容 hash 作幂等键，重复执行直接跳过，回执写回任务状态。

## 踩坑点

- **图片是重灾区**。模型给出的路径几乎都不可用，必须在归一化阶段统一"上传图床 → 重写绝对 URL"，否则公众号会把相对路径渲染成死链。
- **公众号的样式剥离比想象中激进**。class 全丢、部分嵌套标签被拍平，主题必须编译成内联样式，行高字号要在微信内置浏览器实测。
- **frontmatter 的 `---` 会被某些编辑器当水平线**，直传前先确认平台解析行为。
- **GFM 表格、任务列表别假设可用**，适配器里准备降级方案，比如表格转列表。
- **全自动发布不可取**。我们保留人工确认门，Agent 负责到"待发布"为止。

## 可复用建议

- 把"平台能力矩阵"（支持的语法、图片限制、审核规则）维护在仓库里，适配器开发照着写，新人也能快速上手。
- 适配器做成纯函数加快照测试，主题改版时跑一遍就知道影响面。
- 内容 hash 幂等加回执状态回流，是任务能反复重跑的前提。

## 总结

这条管线的核心思路是：**生成归生成，分发归分发**。Agent 只产出规范的 Markdown，格式适配交给确定性的转换代码。做到这点后，新增一个发布平台通常一天以内的工作量，而内容质量问题能在 CI 阶段就拦住，不必等到发布后才返工。
