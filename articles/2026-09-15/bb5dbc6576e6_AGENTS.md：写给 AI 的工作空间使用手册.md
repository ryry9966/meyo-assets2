## 背景：Agent 缺一份"入职手册"

OpenClaw 的 workspace 是 agent 真正干活的地方：读写文件、跑脚本、调 MCP 工具、触发插件自动化，都发生在这个目录里。人类协作者有 README 和团队默契兜底，而 agent 每次会话都像第一天入职的新员工——没有记忆，只有上下文。

之前社区里常见的做法是把约定散在系统提示词、插件配置和口头经验里，换个人接手就断档。AGENTS.md 的价值在于把这些约定收敛到一个标准位置：OpenClaw 挂载 workspace 时会自动读取它，作为 agent 的常驻说明书。

## 问题：没有手册时，agent 会怎么"自由发挥"

几个我们实际遇到过的场景：

- 同一个 Python 仓库，agent 一会儿用 pip 一会儿用 uv，装出一堆冲突依赖；
- 直接改 `dist/` 里的生成物，而不是改源文件再构建；
- 改完代码不跑测试，或者一跑就是全量测试拖十分钟；
- 每次会话都要重新解释目录约定，解释得不一致，行为也跟着不一致。

单看都不大，叠起来自动化任务的可靠性会被明显拉低。

## 做法：五步写出能落地的 AGENTS.md

**第一步，盘点"不写就会错"的信息。** 只收四类：命令、目录约定、禁区、验证方式。如果 workspace 挂了多个 MCP 工具，"什么场景优先用哪个"也值得写一条。别把所有文档都塞进来。

**第二步，结构化分节。** 参考骨架：

```markdown
# AGENTS.md
## 概览        # 三行以内说清技术栈和入口
## 常用命令    # 每条都能直接复制执行
## 约束与禁区  # 不要动什么、不要怎么改
## 验证方式    # 改完后如何确认没坏
## 不确定时    # 先提问，还是先读哪个文件
```

**第三步，控制篇幅。** 建议 100 行以内。完整 schema 之类的细节放独立文档，这里只留一句指针。上下文越长，单条指令的约束力越弱。

**第四步，分层放置。** monorepo 场景在根目录放全局约定，子目录放局部覆盖——子包的测试命令、特殊构建规则就近写。

**第五步，进版本库并持续迭代。** AGENTS.md 和代码一样走 review。最有价值的迭代来源是 agent 犯的错：同类错误出现两次，就回头补一条规则。

## 踩坑点

- **写太长。** 三百行的 AGENTS.md 等于没有，agent 会"部分遵守"。
- **规则自相矛盾。** 两节冲突时，agent 会挑对自己方便的那条，而且每次挑的还不一样。
- **愿望式规则。** "写出优雅的代码"没有约束力，"提交前执行 `ruff check`"才有。
- **重复信息失同步。** 命令同时写在 README 和 AGENTS.md，改一处忘一处。要么单点维护，要么由脚本生成。
- **塞敏感信息。** 密钥、内网地址写进去，等于随上下文发给模型。
- **想当然的优先级。** 根目录与子目录规则同时存在时，以实际加载行为为准——自己跑一次验证，别只信文档描述。

## 可复用建议

1. 当 onboarding 文档来写：读者很聪明，但零上下文。
2. 每条规则尽量配一条可执行命令，让"遵守"可以被验证。
3. 固定一个回归任务（比如"给指定模块加接口并跑测试"），每次修改 AGENTS.md 后跑一遍，对比行为差异。
4. 公共骨架抽成模板仓库，新项目直接复用，团队约定保持一致。

## 总结

AGENTS.md 没有任何魔法，它只做一件事：把团队里"大家都知道但没人写下来"的约定，变成 agent 每次都能读到的机器可读手册。成本低、见效快，是 workspace 级自动化里性价比最高的第一步。如果你现在每次会话都在重复解释同样的规矩，今天就值得花半小时写第一版。
