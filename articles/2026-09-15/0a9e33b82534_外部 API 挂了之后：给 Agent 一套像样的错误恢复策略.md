## 背景

跑 OpenClaw / MCP 这类 Agent 系统一段时间后你会发现：Agent 的能力上限往往不取决于模型，而取决于它调的那些外部 API。搜索、天气、数据库、内部服务……这些依赖迟早会挂：限流、超时、发版中、网络抖动。传统脚本挂了就报错退出，但 Agent 是个循环——失败处理做得好不好，直接决定这套系统是“生产可用”还是“只能在演示里用”。

## 问题：Agent 的挂法和网页不一样

三个典型症状：

1. **死循环重试**。工具报错，模型倾向于“再试一次”，没有人为上限时它会一直试到 token 烧完。
2. **幻觉式兜底**。更危险的情况：工具返回报错文本，模型却据此编出一个看起来合理的答案，故障被静默吞掉。
3. **副作用翻倍**。重试写操作（下单、发消息）时没做幂等，一次故障变成两笔订单。

根因是同一个：重试、降级、放弃这些**策略**被交给了模型，而模型不是做策略的地方。

## 做法：四层防线

**第一层：错误分类。** 在工具 / MCP server 层按状态码分流：429、5xx、超时属于可重试；400、401、403、404 属于不可重试，重试只会浪费预算。判断逻辑写在代码里，不要让模型读原始响应去猜。

**第二层：受控重试。** 指数退避加抖动，设硬上限（比如 3 次、总耗时 8 秒）。写操作必须带幂等键；上游不支持的，就在自己这层做请求去重。

**第三层：熔断与降级。** 连续失败 N 次后短路一段时间，直接走 fallback：带时效标注的过期缓存、备用 provider，或明确声明“该能力暂不可用”。降级结果必须打标，不能伪装成正常结果。

**第四层：把失败说清楚。** 给模型的结构化返回里带上状态和建议动作：

```json
{
  "status": "degraded",
  "source": "cache",
  "stale_minutes": 42,
  "hint": "上游超时，以下为缓存数据，时效性下降"
}
```

同时给模型留一条合法路径：报告失败、请求用户介入。很多幻觉兜底，本质是提示词里只允许“成功”这一种结局。

## 踩坑点

- 让模型自己决定重试次数：要么不重试，要么死循环。策略必须固化在代码。
- 对 4xx 重试；或者超时设置互相矛盾——每个工具 30 秒、任务总预算也是 30 秒，一个卡住全线超时。
- 把“服务挂了”和“我的配额用完了”混为一谈：前者等恢复，后者等也没用。
- 降级缓存不打时效标记，三天前的数据当实时数据答给用户。

## 可复用建议

- 在 MCP server / 插件层做一个统一的 tool client，retry、熔断、fallback 收口在一处，别每个插件各写一份。
- 所有工具返回统一 schema：`status / data / reason / hint` 四件套。
- 用 mock server 注入故障做测试：随机 500、固定超时、慢响应，验证 Agent 走的是降级路径而不是幻觉路径。
- 日志记录完整失败链路（哪层拦的、走了哪个 fallback），出事能回放。

## 总结

错误恢复不是“多试几次”，而是一套组合工程：先分类，再受控重试，然后熔断降级，最后把失败语义清晰地交还模型。核心原则四句话：**策略写进代码，失败要说清楚，降级必须打标，永远给模型留一条退出路径。** 把这四条做进工具层，你的 Agent 才算真正跨过“演示可用”到“生产可用”这道坎。
