## 背景

用 Agent 生成技术内容已经不新鲜：LLM 默认输出 Markdown，结构清晰、可版本化、易于二次处理。真正麻烦的是后半段——发布。同一篇 Markdown，公众号要内联样式的 HTML，知乎会剥掉大部分标签，掘金和站点对扩展语法的支持各不相同，RSS 又是另一套渲染环境。多数人的做法是复制粘贴再逐个手调，一篇内容发三个平台，格式工作占掉的时间往往超过写作本身。

## 问题

归纳下来是三个：

1. **没有单一事实源**。各平台的修改各自为政，改一处要同步三处，很快就会漂移。
2. **格式语义不对等**。表格、脚注、任务列表、原生 HTML，这些语法在不同平台的存活率完全不同。
3. **AI 输出并不干净**。模型经常生成嵌套过深的列表、非标准的代码围栏语言标签、以及莫名其妙的 HTML 混写，直接投喂渲染器就是隐患。

## 做法

思路是把发布拆成一条显式管线，核心三个概念：

**1. 规范 Markdown（Canonical Markdown）**

先定义一个“最小公共子集”作为内部标准：CommonMark 为主，加受控扩展（GFM 表格、fenced code、任务列表），明确禁止脚注和原生 HTML 入库。所有 AI 产出先过归一化——用 remark/mdast 的 AST 遍历做清洗：拍平过深嵌套、修正代码语言标签、剥离 HTML 节点——落到规范层。

**2. 平台适配器（Adapter）**

每个平台一个适配器，输入规范 Markdown 的 AST，输出目标格式：

- 公众号：AST → 带内联样式的 HTML，宽表格降级为键值对列表；
- 知乎/掘金：走各自的导入格式，保留代码高亮标记；
- 自建站点/RSS：基本保留原样，只处理相对链接和 front-matter。

适配器是纯函数，不做 IO，方便单测。

**3. 校验层**

发布前跑一轮平台规则检查：外链图片域名是否在白名单、代码块行数是否超限、链接是否为绝对路径。不过就阻断，把问题留在管线内，而不是读者评论区。

在 OpenClaw 侧，我把渲染和校验封装成一个 MCP tool：入参是规范 Markdown 的文件路径加目标平台，出参是渲染结果和 diff 日志。Agent 负责生成内容、调用工具，格式决策全部下沉到管线，模型不碰具体样式规则。

## 踩坑点

- **图片热链是最大的坑**。平台抓取外链图重新上传后 URL 会变，回链就失效。后来统一走自己的图床，发布后再验证一次可访问性。
- **表格降级别用截图兜底**。截图在手机上不可读，宽表拆成键值对列表效果反而更好。
- **归一化别太激进**。早期版本顺手删掉了所有强调标记，结果全文语气全平。原则是：只修语法不合法，不改表达意图。
- **快照测试要固定输入**。golden sample 用固定版本的样例文件，否则每次重跑快照全变，测试形同虚设。

## 可复用建议

- 规范层越薄越好，语法只做减法，不轻易加扩展；
- 适配器用 AST 变换实现，别用正则全文替换；
- 每个平台维护一份 golden sample 加快照断言，渲染结果一变就能看出来；
- 校验规则和适配器放在一起维护，别散落在各个脚本里。

## 总结

多平台发布的本质问题是格式语义不对等，靠人肉同步不可持续。把“规范 Markdown → AST 适配 → 平台校验”做成显式管线，AI 只负责产出内容，格式适配交给确定性代码，这套东西才可能长期维护。管线不追求覆盖全部语法，只保证入管的每一篇内容，都能可预期地走到每个平台。
