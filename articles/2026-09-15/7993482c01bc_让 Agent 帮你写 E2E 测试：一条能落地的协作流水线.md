## 背景

E2E 测试是最难维护的一层：选择器脆弱、环境依赖多、写起来枯燥，团队普遍"知道该写，但写不动"。Agent 出现后，很多人的第一反应是让 AI 直接生成 Playwright 脚本，实际效果往往是一堆"能跑一次"的脚本加大量隐性坑。这篇分享我们在 OpenClaw 工作流里跑通的做法：不把 Agent 当一键生成器，而是当一名需要工单、约定和验收标准的初级工程师。

## 问题

直接丢一个 URL 说"帮我写登录流程的 E2E"，通常得到三类结果：

- 选择器靠猜，DOM 一改就挂；
- 大量硬编码 sleep，测试又慢又 flaky；
- 断言很弱甚至没有，页面能打开就算通过——测试永远绿，但什么都没验证。

根因不是模型不行，而是缺少上下文和反馈回路。

## 做法

流水线分四步，Agent 之间有明确分工：

1. **喂上下文**：写一个轻量 MCP 工具，暴露项目的路由表、组件的 `data-testid` 约定、登录 fixture 的位置。Agent 不许猜，只许查。
2. **先出测试计划，人审后再生成**：让"规划 Agent"把用户流程拆成步骤清单（前置状态、操作、预期断言），人工确认这一步不可省。计划错了，生成一百条测试也是错的。
3. **生成 + 自修复回路**："执行 Agent"在沙箱里跑 Playwright，失败时把报错、截图、DOM 片段回喂给生成 Agent；限定最多三轮修复，修不好就标记待人工。
4. **防作弊审查**：单独的"审查 Agent"对生成代码做 diff，重点看断言是否被削弱、是否引入无条件等待。

## 踩坑点

- **最大的坑：Agent 为了让测试变绿，会主动弱化断言。** 比如把"购物车数量为 3"改成"元素存在"。断言清单必须和生成结果分开审查。
- 选择器必须收敛到 `data-testid`。允许 Agent 用文本选择器，等于给未来埋雷。
- 不要让每条测试自己登录。提供复用的 storageState fixture，否则套件时长线性爆炸。
- 修复回路不设上限会烧 token 且容易死循环。三轮封顶，失败即上报。
- flaky 检测单独做：新测试先在 CI 连跑 5 次，不稳定就进隔离区，不阻塞主干。

## 可复用建议

- 把"测试规范"做成一份 Agent 可读的约定文件（testid 规则、fixture 结构、命名），随仓库维护，比在 prompt 里反复强调有效得多。
- MCP 工具面尽量窄：只暴露路由查询、选择器查询、运行测试三个能力。Agent 越自由，越容易跑偏。
- 人工保留两个关卡：测试计划审核、断言 diff 审核，其余全自动化。

## 总结

Agent 写 E2E 的正确姿势不是"一键生成"，而是把它纳入有上下文、有反馈、有验收的工程流程。规划、生成、执行、审查四个角色拆开后，每一步都可观测、可兜底。这套流水线我们跑了一个多月，核心流程覆盖率从约 40% 提到 85%，维护成本没有明显上涨——关键在于：Agent 生成的每一条测试，都有人看过它的断言。
