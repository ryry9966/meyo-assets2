# 背景

目前大部分 agent 的使用方式仍然是"人问机答"：用户发消息，agent 回复，会话结束。但对 OpenClaw 这类常驻型 agent 来说，这个模式其实浪费了它的本质优势——它一直在跑，有工具、有记忆、有消息通道，天然适合做 proactive：不等用户开口，自己发现该做的事并推进。

很多人的配置停在"装了一堆 MCP 插件，但我喊它才动"。问题不在插件不够多，而在缺一套结构。

# 问题

Proactive 不是"多加几个定时任务"。真正的核心是三件事：

- **谁来触发**（trigger）：定时、事件还是状态变化；
- **做什么**（standing intent）：长期有效的指令，而不是每次现想；
- **敢不敢做**（risk gating）：无人值守时的动作边界。

三件事缺任何一件，结果要么是静默失败没人知道，要么是高频骚扰让用户直接关掉通道。

# 做法

我的落地结构分五层，供参考：

1. **触发层**：cron 心跳 + webhook + 仓库/文件 watcher，全部收敛到统一入口（一个 MCP server 或 gateway），每个触发打上 `source` 标签，方便后续过滤和审计。
2. **常备意图层**：把长期指令写进持久记忆/配置，例如"工作日 9:00 汇总 GitHub 上 @ 我的未读项；main 分支 CI 失败立即通知并附日志链接"。意图与触发解耦，调整行为不用改代码。
3. **判定层**：触发先过一道"值不值得打扰"的判断——去重、静默时段、重要度分级。低级写进日报，中级批量推送，高级立即推送。
4. **执行层**：按风险分级。只读/通知类直接执行；写自己工作区的低风险操作自动执行并留审计日志；有外部副作用的（给别人发消息、调付费 API）必须确认，回复关键词放行。
5. **兜底层**：心跳上报 + 失败专用通道。任务没跑成，也要让你知道"它没跑成"。

# 踩坑点

- **自触发循环**：agent 自己发出的消息又被 webhook 捕获，形成回环。解法是 source 过滤 + 幂等键。
- **通知疲劳**：前期什么等级都想推，一周内用户就会关掉整个渠道。先只放行"高"级，观察后再放开"中"级。
- **静默失败**：无人值守任务挂掉后没人发现，是最伤信任的故障。每个 proactive 任务必须有明确的失败路径。
- **时区与补跑**：cron 按写死的本地时区跑，机器迁移后全部错位；停机期间错过的任务要不要补跑，必须有明确策略。
- **凭证放大**：主动性意味着无人值守运行，token 必须按任务最小授权，不要复用全能 key。

# 可复用建议

- **先只读后写入**：第一版 proactive 只做"观察并报告"，跑两周看误报率，再逐步加写操作。
- **建 proactive 台账**：每次未经请求的动作记一行（触发源、动作、结果、是否被撤销），每周复盘一次。
- **确认分级固化成配置**，而不是散落在各处 prompt 里，否则行为不可预测。
- **盯三个指标**：误报触发率、被撤销动作数、静默时段违规次数。三者趋近于零，再扩大 proactive 范围。

# 总结

Proactive 能力 = 触发器 × 常备意图 × 风险分级。模型能力决定"能不能做对"，这套结构决定"该不该做、什么时候做"。建议从最小闭环起步：一条 cron + 一条常备指令 + 一条失败通道，跑通之后再谈规模。主动性是工程问题，不是模型问题。
