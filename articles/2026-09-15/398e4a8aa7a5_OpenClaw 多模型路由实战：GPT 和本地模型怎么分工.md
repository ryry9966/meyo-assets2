## 背景

用 OpenClaw 搭自动化工作流，接的模型多了之后都会遇到同一个问题：什么时候把任务交给 GPT 这类云端旗舰，什么时候丢给本地跑的小模型。我一开始图省事全挂旗舰模型，token 账单和限流都很头疼；后来激进地全换本地模型，结果 agent 在多步工具调用里频繁出错。这篇记录我现在的分流方案，能跑，但不是银弹。

## 问题

三个实际痛点：

1. **成本**：摘要、格式化、翻译这类高频低复杂度任务占了我约 70% 的调用量，用旗舰模型纯属浪费。
2. **隐私**：日志分析、个人笔记整理这类任务，数据不该出本机。
3. **可靠性**：7B~14B 的本地模型做单轮问答没问题，但 function calling 格式经常漂移，多步规划基本不可用。

## 我的分流做法

**第一步，给任务打标。** 我把工作流里的任务分四类：规划与写码、长上下文阅读、结构化工具调用、轻量文本处理。前三类给云端强模型，第四类走本地。判据很朴素：一旦任务涉及“决定下一步做什么”或“生成机器要解析的输出”，就别信小模型。

**第二步，按 agent 分模型。** OpenClaw 支持给不同 agent 配不同默认模型。主对话 agent 用旗舰模型；跑定时任务的批处理 agent、做摘要的后台 agent 全走本地。配置示意如下（键名以你版本的实际配置为准）：

```json
{
  "agents": {
    "main":       { "model": "cloud/flagship" },
    "summarizer": { "model": "local/qwen-14b" },
    "scheduler":  { "model": "local/qwen-14b", "fallback": "cloud/flagship" }
  }
}
```

**第三步，加 fallback 链。** 本地服务超时或 OOM 时自动降级到云端，比任务卡死强。反过来不建议：云端失败降级到本地跑复杂任务，失败率会很难看。

**第四步，给本地输出加护栏。** 所有走本地模型的工具调用，我在插件层加了 JSON schema 校验，解析失败重试一次，再失败就升级到云端。这一步让本地模型的可用性从“碰运气”变成“可接受”。

**第五步，用数据调阈值。** 每周看一次调用统计：各模型的 token 消耗、失败率、平均延迟。发现某类任务本地失败率连续低于 2%，就把它从云端名单挪下来。

## 踩坑点

- **function calling 格式漂移**：本地小模型对工具 schema 遵循度差。温度压到 0.2 以下 + 校验重试，缺一不可。
- **上下文截断**：本地模型 8k 窗口，塞长文档进去会静默截断，输出看着像模像样其实丢了关键段。路由前先估 token。
- **fallback 抖动**：本地超时设 5 秒太激进，高峰期频繁降级，账单反升。后来调到 30 秒，并区分“首 token 超时”和“总超时”。
- **prompt 不通用**：同一份 prompt 在两个模型上表现差异很大。改路由后要重新过一遍评测，别想当然。

## 可复用建议

1. “隐私敏感 → 强制本地”写成硬规则，其余任务才谈成本与质量的权衡。
2. 模型选择做成每个 agent 的配置项，永远不要全局写死。
3. 维护 20~50 个真实任务的小评测集，改路由策略后跑一遍回归，比任何直觉都可靠。
4. 先上监控再谈优化，没有调用统计的路由策略都是拍脑袋。

## 总结

多模型路由的本质，是用可量化的失败率和成本数据把任务和模型做匹配。OpenClaw 的 agent 结构天然适合按 agent 粒度分流，而护栏（校验 + fallback + 评测集）比路由规则本身更重要。这套方案我迭代了三版，预计还会继续改——模型在变，任务也在变。
