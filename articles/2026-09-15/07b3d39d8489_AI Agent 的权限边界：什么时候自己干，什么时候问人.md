## 背景

Agent 能调工具之后，权限问题就从理论变成了运维问题。在 OpenClaw 这类框架里，一个 agent 可能同时挂着文件读写、shell、若干 MCP 工具和外部 API 插件。全自动驾驶效率最高，但删错目录、发错消息的代价也真实存在；反过来每一步都弹确认，人会迅速进入"无脑点允许"模式，审批形同虚设。

## 问题

核心矛盾是：**确认次数与风险覆盖不成正比**。实践中常见两种翻车方式：

- 问得太多：用户疲劳后一律选允许，边界等于没有；
- 问得太少：agent 把"清理临时文件"理解成递归删除，或者自作主张给客户发了邮件。

## 做法：按四个维度分级

先给每个工具/动作打标，维度有四个：

1. **可逆性**：能不能撤销；
2. **影响范围**：沙箱内，还是生产环境/外部世界；
3. **出错代价**：重试成本多高；
4. **意图明确度**：是不是用户指令的直接执行。

据此分成四档：

- **T0 自动执行**：只读、沙箱内、可逆。搜索、读文件、跑测试。
- **T1 自动 + 留痕**：工作区内的写操作、特性分支上的 commit。正常执行，写审计日志。
- **T2 确认一次**：装依赖、写工作区外、调用新的外部 API。本次会话内记住选择，会话结束重置。
- **T3 必问**：删除、生产部署、对外发消息、涉及钱和凭据的操作。

落地步骤：

1. 在工具注册层（MCP server 配置或插件 manifest）显式声明风险级别，不要散落在 system prompt 里靠模型自觉；
2. 写操作默认 dry-run，先产出 diff，用户过目后再 apply；
3. 审批界面展示 **diff 本身**，而不是一句意图描述；
4. T1 以上动作全部进审计日志，带时间戳和参数；
5. 把整张权限矩阵写成配置文件，进版本库，改边界走 review。

## 踩坑点

- **审批疲劳**：T2 弹得太频繁，等于在训练用户无脑点确认。宁可收紧 T2 的定义、减少弹窗，也别稀释每次确认的分量。
- **批准了计划而不是 diff**：用户同意"清理临时文件"，实际 glob 匹配到了别的东西。审批对象必须是最终要执行的内容。
- **信任工具描述**：某个 MCP 工具名叫 `read_xxx`，实际带副作用。接入任何新工具，先人工验证一遍真实行为。
- **链式不可逆**：单步看都安全（生成内容 → 发送邮件），拼起来不可逆。跨档组合动作按最高档处理。
- **"总是允许"不过期**：一个月前顺手点的授权还在生效，定期清理授权状态。

## 可复用建议

- 底线只有一条：**不可逆 + 对外动作，默认拒绝，必须问人**。
- 展示 diff，不展示意图；展示参数，不展示标题。
- 权限配置当代码管理，边界变更有记录、可回滚。
- 每周翻一次审计日志——你大概率会发现 agent 的实际行为和你的想象有偏差，这正是调边界的输入。

## 总结

"问不问人"不是哲学问题，是接口设计问题。边界画在"可逆且在范围内 → 自己干；不可逆或出范围 → 必须问"这条线上，再把这条线从 prompt 里的一句话变成一份可版本管理的配置，agent 才真正敢放开手用。
