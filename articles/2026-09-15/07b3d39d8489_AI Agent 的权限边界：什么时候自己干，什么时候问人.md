## 背景

跑过一段时间 OpenClaw / MCP 工具链的人大概都遇到过同一个问题：Agent 的**能力上限**很容易提高——接个新插件、挂个新 MCP server 就行；难的是它的**行为边界**。一个能读文件、发消息、执行命令的 Agent，如果权限是"默认全放行、出事再收"，第一次事故往往就发生在你不在屏幕前的那个晚上。

## 问题：难的从来不是能力，是分级

我给自己的 Agent 配权限时踩过两个极端：

- **全放开**：效率很高，直到它某次"顺手"把一个共享文档回滚到三个月前的版本，覆盖了同事两周的修改。
- **全确认**：每个动作都弹确认，三天后我形成了肌肉记忆，闭着眼点"允许"——确认机制形同虚设。

两个极端指向同一个结论：**权限边界不该是开关，而是分级**。我用的判断维度有三个：

1. **可逆性**：动作能不能撤销？读文件、可回滚的分支是可逆的；发消息给客户、删除数据不可逆。
2. **影响范围**：只影响 Agent 自己的工作区，还是波及他人、外部系统、公开渠道？
3. **资源消耗**：是否花钱、占名额、产生真实的外部调用成本。

## 做法：三级权限模型

**T0 自动执行**：只读操作、工作区内写操作、有明确 dry-run 的动作。前提是所有动作写审计日志，事后可查。

**T1 确认后执行**：不可逆但影响范围可控的动作——发群消息、push 到非主干分支、删除工作区文件。关键改进是**确认必须带预览**：让 Agent 先展示将要发生什么（diff、消息全文、目标分支），再问。不是"我要执行 X，可以吗"，而是"以下是将执行的内容，确认？"

**T2 默认禁止**：对外付款、不可恢复的删除、权限配置变更、以我的身份对外承诺。这类动作即使写进 prompt 也不允许，除非进白名单并单独设阈值。

落地上：每个 MCP 工具注册时标注风险级别；T0 写日志，T1 走确认通道，T2 在工具层直接拒绝——**而不是靠 system prompt 求它别做**。

## 踩坑点

- **确认疲劳**：弹窗一多，人就开始盲点。T1 范围要克制，宁可开始收得紧、逐步放，别反过来。
- **模糊提问**：早期我的 Agent 会问"我可以继续吗？"——这种问题没法答。要求每次提问必须附上下文和预览，答不上来说明工具描述有问题。
- **自动化任务没有"人在场"这个前提**：cron 任务里混着 T1 动作，确认请求会在你睡觉时堆积。我的处理是：无人值守任务只允许 T0，T1 动作降级为"记为待办，人在线后处理"。
- **prompt 限制会被长上下文稀释**：对话一长，约束就淡了。不可逆动作必须在工具/MCP 层做硬拒绝，prompt 只是第一道防线。

## 可复用建议

- 新工具接入先按 T1 观察一两周，再决定降到 T0 还是升到 T2
- 确认消息必须包含三要素：动作对象、影响范围、撤销方式；缺一个就别让它执行
- 留一条"急停"指令，能立刻挂起所有自动任务
- 每月翻一次审计日志和白名单，回收不再需要的权限

## 总结

Agent 权限边界的设计，本质是把"信任"从一次性判断变成持续运营：用可逆性、影响范围、资源消耗给动作分级；自动执行的前提是可审计，人工确认的前提是有预览，禁止项要有工具层的硬边界。Agent 变强的速度很快，但信任只能靠边界一点点攒出来。
