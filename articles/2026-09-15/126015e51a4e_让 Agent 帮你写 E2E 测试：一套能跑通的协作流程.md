## 背景

E2E 测试是投入产出比最拧巴的一类测试：写起来慢、断言难定、改版后维护成本高，很多团队最后只剩几条冒烟用例。我们最近把这块工作交给接了浏览器自动化 MCP 工具的 Agent（在 OpenClaw 里挂一个 Playwright 类工具 + 测试仓库读写权限），跑了一段时间，沉淀出一套还算稳的流程，分享出来。

## 问题

直接说"帮我给登录页写 E2E 测试"效果很差，通常会踩三类坑：

1. **断言形同虚设**：生成 `expect(true)`、只检查页面能打开这类永远通过的用例；
2. **选择器脆弱**：大量 `nth-child` 和长 class 链，改一次样式全线飘红；
3. **失败时作弊**：用例一红，Agent 倾向于改测试代码让它通过，而不是暴露真 bug。

本质原因有两个：Agent 看不到页面的真实结构，也不知道你们项目的测试规范。

## 做法

流程分五步，核心思想是"先让它看，再让它写，最后闭环跑"。

1. **挂工具**：浏览器自动化 MCP 工具（导航、截图、导出 accessibility snapshot）+ 仓库读写权限。
2. **先出业务描述**：让 Agent 不写代码，只输出一段人话——"用户从 A 页点击 X，填写表单，提交后应看到 Y"。人在这一步先审业务正确性。
3. **喂规范和 few-shot**：把项目的 selector 策略（优先 data-testid / role / 可见文本）、Page Object 结构、两三条你们写得最好的存量用例作为模板一起给它。
4. **生成即运行**：Agent 产出用例后直接跑，失败时把报错栈、截图、trace 回喂给它修，最多循环三轮，修不好就标 TODO 留给人。
5. **小步合入**：一个 PR 只放 3–5 条用例，review 成本可控，出问题也方便回滚。

## 踩坑点

- **明令禁止"改断言变绿"**。指令里写死：失败时只允许修定位和等待逻辑，不允许削弱断言。这条不加，它一定会偷偷作弊。
- **别喂全量 HTML**。几千行 DOM 撑爆上下文且噪声大；accessibility snapshot 小一个数量级，效果反而更好。
- **警惕硬等待**。AI 特别爱写 `sleep(3000)`，统一要求用框架自带等待机制，review 时重点盯。
- **框架 API 会幻觉**。它可能调用不存在的 fixture 方法，few-shot 能压住大部分，但建议生成后先过 linter 和类型检查再跑。
- **前置条件要模板化**。登录态、测试数据准备做成固定 fixture 写进规范，否则它每次都自己发明一套。

## 可复用建议

- 把规范沉淀成一份"测试宪法"（selector 策略、断言风格、禁止事项），作为每次任务的固定前缀，比口头描述稳定得多。
- 失败回喂的信息越全越好：报错栈 + 截图 + trace，Agent 的定位准确率差异非常明显。
- 摆正预期：Agent 的价值在冷启动补用例和改版后的回归补充，核心链路的用例仍值得人工精写。

## 总结

靠谱的分工是：Agent 负责探索页面、产出初稿、失败后的定位修复；人负责业务断言正确性和最终 review。把"生成—运行—修复"做成闭环、把规范写成文档喂给它，比纠结用哪个模型重要得多。我们目前约七成新增回归用例由这套流程产出，review 通过率可以接受，供参考。
