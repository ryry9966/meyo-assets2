## 背景

OpenClaw 这类 Agent 框架普及后，一个老问题变成了新问题：Agent 挂上 MCP 工具、能读写文件、能调外部 API，那每一步都要人点头，还是放手让它跑？

两种极端社区里都见过。一种是全手动模式，每个工具调用都暂停等人批准，跑一个十步任务要盯十分钟，最后大家干脆无脑点确认，审批形同虚设。另一种是完全放手，Agent 半夜跑批时把生产配置覆盖了，第二天才发现。

问题的本质不是"要不要人审"，而是"哪些操作值得人审"。

## 做法：按"可逆性 × 影响范围"分级

用两个维度切分所有工具调用：**可逆性**（出错后能否低成本回滚）和**影响范围**（只影响本次会话，还是波及数据、资金、外部他人）。据此分三档：

**第一档：自动执行。** 只读操作、查询搜索、沙箱内临时写入。即使错了代价几乎为零，审了反而打断心流。

**第二档：预览后执行，事后可撤销。** 有副作用但可逆：在工作目录改文件（有 git）、发草稿、创建测试资源。做法是 Agent 先输出 diff 或摘要再执行，保留撤销命令。不等人，但留痕。

**第三档：强制人工确认。** 不可逆或越界的操作：删数据、动生产、对外发布、花钱。必须停下来，把"做什么、为什么、风险是什么"压成十秒能读完的摘要，等明确批准。

落到 OpenClaw 里，就是在工具注册层给每个 MCP 工具标注权限等级，而不是在 prompt 里写"删除前请确认"——后者在长对话里一定会被稀释。

## 踩坑点

1. **审批疲劳是最大敌人。** 确认弹窗频率一高，用户就养成秒批习惯，这时强制审批比没有审批更危险——它制造虚假安全感。
2. **权限规则写在 prompt 里不可靠。** 模型会遗忘、会被上下文覆盖。边界要落在工具层（代码层），prompt 只负责解释。
3. **忽视批量操作。** 删单个文件可以放第二档，递归删目录就该升到第三档。粒度按实际影响算，不能只看工具名。
4. **确认信息太长。** 三百字的确认框等于没有确认。摘要必须短：做什么、动哪里、能不能反悔。
5. **没有超时策略。** 第三档等不到批准怎么办？默认应该是放弃而非继续，且放弃也要留日志。

## 可复用建议

- 每个 MCP 工具先定三选一的默认档位，宁从高档开始再往下放。
- 第二档操作必须配套撤销方案，没有 undo 就归入第三档。
- 定期回看审批日志：永远被秒批的确认，降级它；自动执行出过错的，升级它。权限边界应该是活的。
- 会话开始时向用户声明当前权限配置，别让人猜 Agent 能干什么。

## 总结

权限边界不是一个开关，而是一张随使用不断校准的分级表。判断标准可以很简单：错了能不能低成本撤回？撤不回就问人，撤得回就放手并留痕。Agent 的自主性是靠可信的边界换来的，不是靠大胆的 prompt。
