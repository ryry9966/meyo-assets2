## 背景

OpenClaw 的 cron 任务本质上是：到点唤醒一个 agent，把你写的 instruction 当作**唯一的需求文档**去执行。它和交互对话最大的区别是没有人在场——用户不会追问，agent 也无处澄清。instruction 写得含糊，跑偏就是必然，只是早晚和成本的问题。

## 问题

一个典型的反例：

> 每天早上 8 点，整理一下昨天群里的重要消息发给我。

这条指令看着没问题，实际跑起来通常有三种结局：要么把无关水群消息全搬过来（"重要"没有定义）；要么什么都不发（遇到 API 报错就静默结束）；要么发进一个没人看的会话（没写投递目的地）。我翻过自己跑挂的十几次 cron 记录，几乎全部是 instruction 层面的问题，而不是调度没触发。

## 做法：把 instruction 写成五段式规格

我的模板固定五段，每段都在收窄模型自由发挥的空间：

1. **目标与范围**：一句话说清做什么、不做什么。例如"只处理 XX 群，不处理私聊"。
2. **数据源与工具边界**：允许读哪些会话、调哪些工具，禁止越界。cron 场景下尤其重要，否则 agent 可能为了"完成目标"去翻不相关的上下文，白白烧 token。
3. **时间窗口的显式计算**：不要写"昨天"，写"以当前时间减 24 小时为起点，时区 Asia/Shanghai"。服务器多半是 UTC，这一条能避开最常见的差八小时事故。
4. **输出契约**：固定结构（如：摘要三条 + 待办两条；无事则只回一句"今日无重要事项"）、字数上限、投递目的地写到具体会话。再加一句"不要寒暄，不要复述任务描述"。
5. **异常与空数据处理**：明确"数据源为空或不可用时，只报告一行原因，禁止编造内容"。这条反编造条款是 cron 与交互任务差异最大的地方——没人盯着时，模型倾向于"显得完成了"而不是"承认失败"。

## 踩坑点

- **模糊形容词**："重要""简要""及时"每次执行的理解都不一样。要么换成可判定规则（"含 @我 或出现关键词 X"），要么删掉。
- **假设有记忆**：每次 cron 运行基本是干净上下文，"按上次的格式"等于没写。需要跨次状态就落状态文件，instruction 里写明读写哪个文件。
- **没测空数据路径**：假期、没人说话的日子，恰恰是 cron 最容易幻觉的时间点。
- **任务比间隔长**：5 分钟一次的重任务会堆积重叠。要么降频，要么在 instruction 里先检查状态文件锁。

## 可复用建议

- **一事一任务**：日报、巡检、提醒拆开写，别堆在一条 instruction 里，长指令的漂移和成本都会恶化。
- **像代码一样维护**：instruction 存文件、进版本管理，改一句话就留一条记录；上线前用相同 payload 手动触发一次，再补一个空数据用例。
- **留一行运行痕迹**：让任务每次往日志文件追加时间戳和结果摘要，排查时能省一半时间。

## 总结

Cron 任务的 instruction 是一段用自然语言写的小程序：自包含、有明确的输入输出契约、处理了失败路径。把它当代码对待——版本化、测试、复盘——定时任务的可靠性就从"碰运气"变成了工程问题。
