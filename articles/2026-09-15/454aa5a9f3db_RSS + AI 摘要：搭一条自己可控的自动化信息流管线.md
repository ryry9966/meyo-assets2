## 背景

信息源散落各处：技术博客、GitHub Release、邮件列表、论坛。RSS 协议虽然老，但仍是唯一“我主动拉取、格式统一、随时可弃”的订阅方式。问题不在获取，而在消化——每天几百条更新，逐篇人工阅读不现实。这篇文章记录我用 OpenClaw 搭的一条 **RSS → 清洗 → LLM 摘要 → 推送** 管线，跑了一个多月后的经验与坑。

## 问题定义

目标不是“摘要一切”，而是三件事：

1. **过滤**：低相关信息在进入 LLM 之前就丢掉；
2. **摘要**：输出结构化结果——一句话摘要 + 标签 + 相关度评分；
3. **去重**：同一事件多源报道只保留一份。

明确不做的：不做情感判断、不“替我读全文”。摘要只是路由信号，值得深读的仍要点开原文。

## 管线结构

分四层，每层独立可替换：

```text
抓取层         清洗层          摘要层           分发层
RSS/定时  →  正文提取    →   LLM 结构化    →   即时推送 / 每日日报
        全链路 SQLite 落库，带状态
```

- **抓取层**：原生 RSS 优先，缺失的源用 RSSHub 补。记录 etag / last-modified 做增量拉取；条目以 guid 为唯一键落库，天然防重放。
- **清洗层**：readability 类算法提取正文，剥掉 HTML 与 CDATA 转义。这一步质量直接决定摘要质量，不要省。
- **摘要层**：温度压到 0.1–0.2，prompt 强制“只基于给定文本，禁止补充外部信息”，要求 JSON 输出（summary / tags / score / quote）。score 低于阈值直接归档不推送。
- **分发层**：高 score 进即时推送，其余汇成每日 digest。我用 webhook 推到 IM，也见过朋友把它封装成 MCP 工具，喂给自己的常驻 Agent 做进一步处理。

编排用 OpenClaw 的任务调度加插件机制，每层一个独立插件，失败重试三次后进死信表，次日人工抽查。

## 踩坑点

- **全文缺失**：约三成源只给摘要段，“摘要的摘要”必然失真。这类源回退抓原文页；遇到反爬就果断换源或放弃，不值得硬刚。
- **幻觉**：即使限定了上下文，通用模型仍会脑补结论。两个缓解手段：要求 quote 字段从原文复制一句支撑句并校验其存在；温度压低。
- **跨源重复**：标题去停用词后算 Jaccard 相似度能解决八成，剩下用 embedding 余弦相似度兜底，阈值 0.85 左右实测可用。
- **成本失控**：最初所有条目都过大模型，一天几千次调用。加一道便宜的粗筛（关键词 + embedding 相关度）后，调用量降到原先的一成。
- **时区与乱序**：各源 pubDate 格式不一，统一转 UTC 存储，digest 再按本地时区聚合，否则日报会漏掉凌晨的条目。

## 可复用建议

- 先跑一周“只入库不推送”，人工抽检各源全文质量，淘汰差源——这比反复调 prompt 有效得多。
- 摘要 prompt 当版本化资产管理，每次修改记录效果对比。
- 结构化输出务必校验 JSON schema，解析失败按脏数据处理，别让一条坏数据堵住整条管线。
- SQLite 起步完全够用，单机日万级条目没有压力，不要过早引入消息队列。

## 总结

RSS 没死，它只是缺一个更好的消化层，LLM 恰好补上了这一环。但管线的可靠性取决于最朴素的部分：去重、重试、增量拉取、脏数据处理。把摘要当路由信号而非最终结论，这条管线就能稳定地把“每天要看的东西”压缩到几分钟。代码并不复杂，值钱的是分层设计和克制。
