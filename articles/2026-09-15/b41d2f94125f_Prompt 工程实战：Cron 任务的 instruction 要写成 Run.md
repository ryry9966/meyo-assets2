## 背景

OpenClaw 的定时任务本质很简单：到点之后，系统把你写的 instruction 作为一条消息，投递给一个**全新会话**里的 agent。没有昨天的对话历史，没有你脑子里的背景信息，只有这一段文字。

所以 cron instruction 的质量，直接决定自动化是"省心"还是"每天早上给你惊喜"。社区里看到的失败案例，大多不是模型能力问题，而是 instruction 写法问题。

## 典型问题

1. **写得太像人类备忘录**："看下昨天的日志，有问题告诉我"，什么算"有问题"？通知发到哪？
2. **依赖不存在的上下文**："和上次一样处理"，每次都是新会话，没有"上次"。
3. **没有输出契约**：结果丢在会话里没人看；或者反过来，每 5 分钟往群里推一条消息。
4. **没有异常路径**：MCP 工具挂了、文件不存在，agent 就地自由发挥。

## 做法：六段式模板

把每条 cron instruction 按这个骨架写：

```text
【目标】一句话说清要产出什么。
【输入】数据来源：具体文件路径 / 具体工具名 / 具体命令。
【步骤】3–6 步，按顺序，每步一个动作。
【输出】写到哪（文件/频道/静默）、什么格式、什么条件下不发消息。
【异常】任一步失败：记录原因到固定文件，本次结束，不要猜测补救。
【约束】不要做什么；条数/长度预算；如何避免重复执行。
```

一个改写示例，每日检查日志的任务：

```text
反例：每天早上检查一下服务器日志，有问题通知我。

改写：
【目标】生成昨日 error 日志摘要，仅超阈值时通知。
【输入】/var/log/app/error.log 中昨天日期的部分；阈值表 /home/me/ops/thresholds.json。
【步骤】1) 读阈值表；2) 按错误类型统计次数；3) 筛出超标项；4) 写摘要到 reports/。
【输出】仅存在超标项时发送不超过 5 行摘要；否则不发消息，只写报告文件。
【异常】文件不存在或读取失败：错误写入 reports/last_error.txt，本次结束。
【约束】不要尝试修复服务；重试不超过 1 次。
```

核心原则一句话：**你在给一个失忆的值班同事写 runbook。**

## 踩坑点

- **时区**：cron 跟随网关/宿主机时区，不是你脑子里的那个。"今天"从几点到几点，先手动触发一次确认。
- **幂等**：失败重跑或调整间隔后，同一件事可能执行两次。要求 agent"写完成标记，发送前检查标记"。
- **沉默失败**：最危险的不是报错，而是任务静默不产出。约定"即使无事发生也写一行状态"，方便对账。
- **输出失控**：不限长度，agent 会把整份日志贴给你。摘要类任务务必写"不超过 N 行"。
- **一个任务干多件事**：拆开。合并 instruction 一旦某步出错，排查成本翻倍。

## 可复用建议

- 新 instruction 先用"立即执行"入口手动跑一次，看完整会话再上线。
- 频率宁低勿高：每天一次稳定跑一周，再考虑加密。
- 数据来源写绝对路径或明确工具名，不要写"通常在"。
- 涉及发消息的任务，一定写清"什么情况下不发"。
- 每月 review 一遍定时任务列表，删掉僵尸任务，它们是最容易被忽略的成本。

## 总结

Cron instruction 不是提醒便签，而是交给一个没有记忆、严格照做、不会替你判断的执行者的 runbook。目标、输入、步骤、输出、异常、约束六段写全，大部分"定时任务不稳定"的问题会自然消失。上线前手动跑一次，永远是性价比最高的那一步。
