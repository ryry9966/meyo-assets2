## 背景

大多数 Agent 的默认形态是"问答机"：你不发消息，它就不动。但很多真实需求是周期性的——盯磁盘、看 CI 状态、提醒未提交的代码。OpenClaw 提供了一个朴素但容易被忽视的机制：心跳（heartbeat）。Agent 会按固定间隔（默认约 30 分钟）自动醒来一次，读取工作区根目录的 `HEARTBEAT.md`，按清单决定要不要做事、要不要说话。这个文件本质上是你和 Agent 之间的一份"主动行为契约"。

## 问题

让 Agent 做周期性任务，传统路径有两条，都不理想：

1. **cron + 脚本**：精确可靠，但脚本没有上下文、没有判断力，输出格式和 Agent 的消息渠道割裂，等于维护两套系统。
2. **让模型常驻轮询**：有判断力，但每次调用都烧 token，成本不可控。

HEARTBEAT.md 是两者的折中：低频醒来、清单驱动、条件触发，平时静默，有事才开口。

## 做法

**第一步：建文件。** 在 Agent 工作区根目录新建 `HEARTBEAT.md`，没有它，心跳醒来后无事可做。

**第二步：写清单。** 每行一个任务，按优先级排序，便宜的检查放前面。推荐"检查 → 条件 → 动作"三段式：

```markdown
# HEARTBEAT.md

- 检查 ~/projects 下 git 仓库，若有未提交改动超过 3 天，提醒我
- 检查磁盘占用，超过 85% 且与上次记录不同时，报告
- 检查 GitHub notifications，有新增未读时汇总一次
- 都没问题就保持沉默
```

**第三步：接输出。** 确认 Agent 绑定了你实际会看的消息渠道，否则主动汇报等于没有发生。

**第四步：控制成本。** 清单没有触发任何条件时，Agent 会静默结束本轮心跳，这比正常对话便宜，但不是免费。从 2~3 条任务起步，观察一周再加。

## 踩坑点

- **心跳不是 cron。** 间隔是"大约 30 分钟"，不是精确定时。需要每天 9:00 准时干活的任务，用系统 cron 触发 Agent 的一次性会话，别放心跳里。
- **重复告警。** Agent 默认无状态，磁盘连续三天 86%，它可能报三次。解法是让它维护一个状态文件（如 `heartbeat-state.json`，记录上次告警时间和数值），任务里写明"与上次状态比较，无变化则跳过"。
- **文件膨胀。** 心跳时整个文件会被加载进上下文，长注释、完整文档都别塞，保持在一屏以内。
- **重活别放心跳。** 批量抓取、跑测试这类分钟级任务，心跳窗口里做不完，交给 cron 调度，心跳只放轻量巡检。
- **"每天第一次心跳"这种写法不可靠。** Agent 对时刻的感知很弱，改成显式条件："距上次汇总超过 20 小时"。

## 可复用建议

1. **清单分两区**：检查区（静默、廉价、无条件不说话）和汇报区（有条件才触发），写的时候物理分开，review 时一目了然。
2. **状态外置**：任何"只报一次"的需求，都配一个状态文件，这是心跳任务从玩具变成可用的分水岭。
3. **标准句式**："检查 X；若 Y 成立且与上次状态不同，则通过 Z 渠道通知；否则沉默。"照着写，不易跑偏。
4. **每月清理**：删掉连续一个月没触发过的任务，清单越长，每次心跳的成本越高。

## 总结

HEARTBEAT.md 的价值不在功能多强，而在把"主动性"从写代码变成编辑一个文本文件。它逼你回答一个平时不会想的问题：你到底希望 Agent 在没人看着的时候做什么。从两三条低成本检查开始，跑两周再扩展，比一上来写满一整页靠谱得多。
