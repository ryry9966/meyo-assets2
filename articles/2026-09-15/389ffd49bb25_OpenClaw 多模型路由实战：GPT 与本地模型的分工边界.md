## 背景

我们的 OpenClaw 实例跑着一组 7×24 的自动化 Agent：日报生成、工单分类、通过 MCP 编排内部工具。早期图省事，所有请求全部打到一个 GPT 端点上。跑了一个月，三个问题浮出来：账单超预算、云端 API 的 P95 延迟抖动卡住自动化流水线、以及内部日志和文档不允许出集群。于是我们把本地模型（vLLM 起的 Qwen2.5-14B）接了进来，开始做路由。

## 问题

踩过一轮之后，核心矛盾其实很清楚：

1. **成本错配**：约八成调用是结构化抽取、工具参数生成、简单分类，根本用不上 GPT 级的推理能力；
2. **能力错配**：本地模型在长上下文规划、多步工具编排上明显掉链子，全量切本地会让任务成功率崩掉。

所以问题从来不是“GPT 和本地模型哪个好”，而是**分工边界画在哪**。

## 做法：按任务类型分层路由

**第一步：任务画像。** 我们把 Agent 子任务打上标签：planning（规划）、tool-call（工具调用参数）、extraction（结构化抽取）、summarization。分别用本地模型跑样本，统计成功率和 schema 合法率，拿到第一手数据再定层级，不拍脑袋。

**第二步：配置路由规则。** 在 OpenClaw 的模型配置里定义三个 profile：`planner` 指向 GPT-4 级模型，`worker`（工具调用、抽取）指向本地 14B，再加一条 fallback 链。路由依据是 Agent 角色和任务元数据，不做内容级别的动态判断——简单、可解释、好排查。

**第三步：质量闸门 + 升级。** 本地模型的输出一律过 JSON Schema 校验；失败先本地重试一次，仍失败则带着原始上下文升级到 GPT。升级次数设上限，防止死循环。

**第四步：观测。** 每次调用记录路由决策、模型、延迟、token 消耗、校验结果。每周复盘一次，看哪些路由该重新分级。

## 踩坑点

- **Function calling 格式差异**：本地模型的工具调用输出和 GPT 有微妙差别（比如参数被字符串化），解析必须严格，别信“看起来对”。
- **上下文窗口错配**：Agent 长对话历史超出本地模型 8k 窗口后被静默截断，Agent 会“忘掉”之前的工具结果。每个 profile 显式设 token 预算。
- **Prompt 不通用**：给 GPT 调好的系统提示词直接搬到本地模型，效果明显劣化。插件配置里保留分模型的 prompt 变体。
- **升级风暴**：本地模型状态差的那天，所有请求都在升级，成本直接翻倍。后来加了熔断——升级率超阈值就告警并暂停路由切换。
- **GPU 争抢**：vLLM 和 Embedding 服务共用一张卡，KV cache 被挤掉导致延迟尖刺。要么隔离，要么老老实实设 memory fraction。

## 可复用建议

1. **从两层起步，别上来就搞 N 层**。一个本地 worker + 一个云端 planner 覆盖大多数场景。
2. **用结构化校验当路由信号**，比让模型自评可靠得多，也便宜得多。
3. **路由决策必须落日志**。没有观测数据的路由策略等于没做。
4. **Fallback 是安全网，不是负载均衡器**。升级率长期偏高说明分级画错了，去修根因。
5. **隐私敏感链路直接钉死本地模型**，路由表里不允许该链路出现云端选项，别依赖运行时判断。

## 总结

OpenClaw 的多模型路由，难点不在算法多聪明，而在于诚实地做任务画像，加上严格的校验闸门。GPT 负责规划和兜底升级，本地模型承担高频结构化工作——先测量、再分级、持续复盘，这套流程在我们环境里把月度 token 成本压掉了六成，任务成功率反而略有提升。供参考。
