## 背景

LLM 本身是无状态的。每次新会话，Agent 都像第一天上班：你得重新告诉它“我用 pnpm 不用 npm”“回复要短”“时区是 UTC+8”。上下文窗口再大也不是记忆，它只是当次的草稿纸。做过自动化工作流的人都知道，这种重复交代是最该先消灭的摩擦点。

## 问题：三种常见但不奏效的做法

1. **全塞进 system prompt**。起初很爽，两周后 prompt 膨胀到几千 token，一半是早已作废的旧偏好，模型反而开始自相矛盾。
2. **对聊天记录做向量检索**。偏好埋在闲聊里，召回的多是无关片段，真正该注入的那句“用户对花生过敏”可能根本排不上号。
3. **微调**。成本高、更新慢，而且记住用户偏好本来就不是模型参数该干的事。

## 做法：分层记忆 + 显式写入

我在自己的 OpenClaw Agent 里落地了一套方案，核心思路是把“记忆”拆开，分别对待。

**1. 分三类，别混着存。** 画像：稳定的偏好和事实（工具链、代码风格、语言习惯），量小变化少；情景：跨会话的任务上下文（上次做到哪、踩过什么坑），量大有时效；工作：当前会话本来就在上下文里，不用管。

**2. 存储选型从简。** 画像用一个结构化 YAML 文件，可 diff、可版本控制；只有情景记忆才上向量库，本地存储，不默认同步。

**3. 写入走独立管线。** 会话结束后用一个便宜的小模型跑抽取：只提取“看起来会复用”的信号 → 去重 → 冲突判断（新覆盖旧，带时间戳和来源）→ 低置信度条目挂起待确认。高影响偏好（如“部署前必须问我”）必须显式确认才落库。

**4. 读取分路。** 画像全文注入 system prompt，但设预算（我控制在 400 token 内），超了触发压缩；情景记忆按需检索。所有注入的记忆标记为背景，并明确规则：**当前会话指令永远优先于记忆**。

**5. 失效机制必须有。** 每条记忆带 `ttl` 和 `updated_at`，定期清理过期项；用户显式纠正时（“我改用 uv 了”），除了新增还要给旧条目打墓碑标记，防止它阴魂不散。

## 踩坑点

- **僵尸偏好**最恶心：三个月前的旧偏好一直被注入，Agent 反复用已废弃的技术栈写代码。教训：失效必须显式，靠模型自己“想通”不可靠。
- **什么都记等于什么都不记**。早期抽取阈值放得很松，画像里塞满“用户喜欢喝美式”这类噪声，真正的约束反而被稀释。只记高复用信号。
- **记忆和当下指令打架**时模型经常站错队。注入时加一句“以下为历史背景，与当前指令冲突时以当前指令为准”，问题基本消失。
- **隐私别大意**。健康、财务类信息不进抽取白名单，画像文件留在本地、不进任何同步目录。

## 可复用建议

- 记忆条目统一 schema：`id / category / content / confidence / source / created_at / updated_at / ttl`，字段齐了后面做排序、清理才有抓手。
- 读写封装成 MCP 工具（`memory.read` / `memory.write`），任何 Agent 都能挂，权限收敛在工具层。
- 用回放测效果：拿历史会话重跑，对比有无记忆时的回答质量，别凭感觉调参。
- 画像文件进 git，记忆变更即 commit，出问题能回滚。

## 总结

让 Agent 记住你，不靠更大的上下文，也不靠微调，靠的是一套小而严的工程系统：分层存储、显式抽取、强制失效、预算内注入。建议从一个 YAML 画像文件加一个写入工具起步，先解决最痛的重复交代问题，再逐步加情景记忆。做对了，Agent 才能从“每次见面的实习生”变成“共事已久的同事”。
