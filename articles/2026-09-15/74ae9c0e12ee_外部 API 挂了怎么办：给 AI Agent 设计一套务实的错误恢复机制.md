## 背景

跑 Agent 自动化任务久了会发现一个规律：流程越长，依赖的外部服务越多，上游出问题就不是"会不会"，而是"什么时候"。LLM API 限流、搜索接口超时、通过 MCP 挂的数据库工具返回 503——这些在日常批处理里是常态，不是例外。

多数时候大家把精力放在"功能能不能跑通"上，等真正上量跑长任务时，才发现错误处理才是稳定性的分水岭。

## 问题

外部依赖的故障大致分三类：

1. **瞬时故障**：429 限流、503、超时，重试大概率能过；
2. **持续故障**：供应商宕机几分钟到几小时，重试无意义；
3. **静默劣化**：响应变慢、返回被截断，不报错但数据不对。

而 Agent 侧常见的三种坏反应是：裸重试死循环烧 token；工具报错被吞掉后模型幻觉出一个"成功"结果继续跑；或者一次失败直接放弃整个长任务，前面已完成的工作全部浪费。

## 做法

建议分层处理：

**1. 先分类，再重试。** 可重试（429 / 5xx / 超时）和不可重试（401 鉴权、400 参数错）分开。不可重试的立即失败上报，不要消耗重试预算。

**2. 指数退避 + 抖动。** 基础 1s 起步、翻倍增长，设上限（比如 5 次、60s 封顶），每次加随机抖动，避免大量任务同一时刻重试。

**3. 熔断。** 连续 N 次失败后进入熔断状态，直接走降级路径，冷却期后半开探测恢复。

**4. 降级链。** 主 API → 备用供应商 → 缓存的旧数据 → 明确标记"此部分不可用"。注意备用源 schema 往往不同，中间必须加一层适配和校验。

**5. 状态持久化 + 断点续跑。** 长任务每完成一步就落盘，恢复时从断点继续，而不是从头执行。

**6. 错误结构化透传给模型。** 工具返回类似 `{"status":"error","retryable":true,"reason":"upstream_timeout"}` 的结构，让模型能基于真实状态重新规划，而不是靠猜。

**7. 幂等保护。** 请求带唯一 ID，服务端去重，防止重试造成重复下单、重复发消息。

## 踩坑点

- 对非幂等操作裸重试，结果同一封邮件发了两遍；
- 退避没加 jitter，几十个并发任务同时重试，把刚恢复的 API 又打挂；
- 超时被当成失败，但请求实际已在服务端成功执行，重试制造了重复副作用；
- `try/except` 吞掉异常，模型在错误状态上继续推理，产出看似合理实则错误的结果；
- 熔断阈值太敏感，一次网络抖动就熔断整个流程，恢复比故障本身还折腾。

## 可复用建议

- 所有工具调用统一过一层封装：超时、重试、错误结构化、日志，别在每个插件里各写一套；
- 给任务设全局预算：最大尝试次数、最大耗时、最大花费，超了就停下并汇报，而不是无限消耗；
- 定期做故障演练：在 staging 把上游 API 掐掉，观察 Agent 是重试、降级还是幻觉，比线上炸了再修便宜得多；
- 错误日志带上 request ID 和调用上下文，保证事后能复盘。

## 总结

错误恢复不是引入一个 retry 库就完事。它是系统设计（退避、熔断、降级、幂等、状态持久化）和提示词设计（让模型看见真实错误并有能力重新规划）的结合。目标从来不是永不失败，而是失败时**可控、可恢复、可解释**——这三个词，值得写进每个 Agent 项目的验收标准里。
