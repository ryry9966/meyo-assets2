## 背景

Agent 干活的质量，一半取决于模型，另一半取决于它对本地环境的认知。包管理器是 brew 还是 apt、Python 在系统里还是在 venv、node 是全局装的还是 nvm 管的、走不走代理、用哪个镜像源——这些信息模型默认全靠猜，而猜的先验来自训练数据里的"通用机器"，你的机器几乎一定不是那台机器。

tools.md 就是解决这个问题的载体：放在固定位置、agent 启动时读取的本地事实清单。

## 问题

没有 tools.md 时，三类翻车最常见：

1. **幻觉参数**：调用不存在的 CLI flag，或使用某工具早已移除的子命令。
2. **环境错位**：在 WSL 里用 macOS 的路径约定，往全局 pip 里装包而项目实际用 uv，国内网络下直连官方源卡死。
3. **环境漂移**：同一段指令在你机器上能跑，到同事机器或 CI 就挂，因为两边 agent 猜出的环境不一致，排障时你甚至意识不到差异在哪儿。

根因相同：环境知识没有被显式化，每次执行都是重新掷骰子。

## 做法

核心思路：**分层 + 事实化 + 可校验**。

**1. 分两层。** 全局层放机器级事实（OS、shell、包管理器、代理、镜像源），放 agent 全局配置目录；项目层放项目特有内容（运行时版本、虚拟环境位置、本地脚本约定），放仓库根目录。冲突时项目层覆盖全局层，这条规则要写进文件开头。

**2. 写事实，不写散文。** 每个条目固定三段：工具名、探测命令、差异说明。例如：

```markdown
- node: `node -v` → v20.x，nvm 管理，勿全局 -g 安装
- python: `which python` → ~/.venv/bin/python，项目用 uv
- 网络: `echo $https_proxy` → 走本地代理，git 走镜像
```

**3. 脚本生成基线，人工补注释。** 写个二三十行的 shell 脚本收集 OS、运行时版本、关键 PATH、代理变量，输出 tools.md 草稿；人工只补机器探测不出的语义，比如"这个 ffmpeg 是打过补丁的版本"。机器生成防腐化，人工注释补上下文。

**4. 只写差异。** agent 不需要知道你装了 curl，它需要知道 curl 被 alias 到了别的东西。判断标准：如果一台"通用机器"也会这样，就不用写。

**5. 约定更新时机。** 换机、升大版本、改代理时更新；更进一步，在 agent 系统指令里加一条：发现实际环境与 tools.md 不符时，先报告差异，确认后更新文件。让文档跟着现实走，而不是相反。

## 踩坑点

- **过期信息比没有更糟。** agent 会默认信任文档，一条过期路径能让它绕很久。没把握的条目宁可删掉，留探测命令让 agent 现场跑。
- **写成操作手册。** 长篇叙述浪费上下文窗口，模型提取关键事实的精度反而下降，控制在几十行内。
- **塞进敏感信息。** API key、内网域名不要进 tools.md，它会被读进模型上下文，还可能随仓库提交。
- **两层文件没有覆盖规则。** 全局和项目同时描述同一工具时，agent 行为不可预测，规则必须显式。
- **生成脚本只跑一次。** 基线脚本应留在仓库 `scripts/` 下，随工具链演进同步维护。

## 可复用建议

- 条目模板：名称 / 探测命令 / 差异说明，缺一不收。
- 全文 40 行以内；超了说明你把"全集"当成了"差异"。
- 像 review 代码一样 review tools.md 的变更。
- 新机器初始化时先跑生成脚本、再补人工注释，五分钟完成。

## 总结

tools.md 的本质，是把"环境即代码"的思想用到 agent 的上下文管理上：环境知识显式化、分层化、可校验、可版本化。目标是让 agent 从"每次猜"变成"启动查"，让"在我机器上是好的"变成一句可以定位、可以修复的工程问题。先从给最常翻车的那台机器写 20 行开始，就够了。
