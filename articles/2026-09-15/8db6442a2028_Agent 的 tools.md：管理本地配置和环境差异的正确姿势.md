## 背景

Agent 跑在本地之后，一个长期被低估的问题浮出水面：模型对环境的认知来自训练语料，而不是你手里这台机器。OpenClaw 和 MCP 解决了"Agent 能不能调工具"，但"这台机器上有哪些工具、装在哪、什么版本、有什么怪癖"，这些信息塞不进系统提示词，更不该写死在插件配置里。

## 问题

几个典型翻车场景，多数人应该都遇到过：

- 在 macOS 上，Agent 顺手就用了 `apt`，因为语料里 Linux 命令占比更高；
- 同一份 Agent 配置，在公司电脑、家里服务器、CI 容器上行为不一致；
- Agent 记得的 CLI 参数是两三年前的老版本语法；
- 多机同步配置时，机器特定的路径和代理设置互相污染。

根因只有一个：**环境事实没有单一可信来源**，散落在对话历史、临时脚本和模型记忆里，每次会话都是重新猜。

## 做法

思路是把环境认知收敛成一份声明式清单 `tools.md`，分层维护：

**1. 全局层**。放在 Agent 配置目录，会话启动时注入。只写事实，不写观点：

```markdown
# last verified: 2025-05-20
## 环境
- os: macOS 15 / arm64
- package-manager: brew（无 apt，勿用）
## 关键工具
- python: 3.12（pyenv，项目内以 .python-version 为准）
- ffmpeg: 7.x，/opt/homebrew/bin
## 网络
- 代理 http://127.0.0.1:7890，git/curl/pip 均需显式设置
## 已知怪癖
- docker 需手动启动：open -a Docker
```

**2. 项目层**。项目根目录再放一份，只写项目特有内容：虚拟环境、启动命令、端口约定。项目级覆盖全局，后加载优先。

**3. 保持新鲜**。写一个十几行的 shell 脚本，批量输出 `tool --version`，拼成版本表。每周或换机器时跑一次，人工确认后更新文件顶部的 verified 日期。

**4. 事实与约定分离**。环境事实归 tools.md；代码风格、回复语言这类个人偏好放另一个文件。混在一起，同步和审查都会变难。

## 踩坑点

- **写成散文**。Agent 提取信息依赖结构，长段落不如键值对和列表。
- **塞密钥**。tools.md 会进上下文，一旦随 dotfiles 仓库同步就是事故。密码、token 一律走环境变量，文件里只写"从哪读"。
- **与 MCP 描述重复**。MCP server 已声明的能力不要再抄一遍，两处声明漂移只是时间问题。tools.md 管"系统级事实"，MCP 管"能力声明"，边界要清楚。
- **没有过期机制**。三个月前的版本表比没有更危险——它看起来很可信。verified 日期是底线。
- **贪多**。这份文件常驻上下文，建议压在两百行以内。超了，说明该拆分层级或者该删了。

## 可复用建议

- 把 tools.md 当代码：进 git、走 review、有提交记录，改动可追溯；
- 每一行尽量满足"可以被一条命令验证"，验证不了的就不要写；
- 配一个 doctor 脚本，逐条校验文件里的事实是否仍成立，失败项高亮；
- 新机器初始化清单里固定加一步：跑生成脚本 → 人工过一遍 → 提交。

## 总结

tools.md 的本质，是把"Agent 对环境的认知"从模型猜测变成显式契约。它不会让模型更聪明，但能显著减少幻觉和跨机器的行为漂移。成本是几行 Markdown 加一个校验脚本，收益是同一个 Agent 在你的每台机器上，都表现得像一个真正熟悉这台机器的人。这件事值得在做自动化之前先做。
