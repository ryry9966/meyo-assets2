## 背景

用 OpenClaw 搭 agent 一段时间后，很多团队的用法会自然演化成“全部走 GPT”：规划、工具调用、总结、甚至格式校验，每一步都打到云端旗舰模型。跑 demo 没问题，任务量一上来，先爆的是账单和延迟。反过来的极端是全部本地化，钱是省了，但复杂规划任务的质量肉眼可见地下滑。多模型路由就是在两者之间找一条可维护的中间路线：让每类请求走“刚好够用”的模型。

## 问题

agent 的日常任务分布其实很不均匀。粗略统计下来：大量请求是轻量的——改写一段话、检索后做个总结、校验 JSON 结构；只有两三成需要真正的多步推理和复杂工具编排。用同一个模型服务所有请求，要么为简单任务付冤枉钱，要么让复杂任务勉强跑在能力不足的模型上。路由要解决的就是这个分配问题。

## 做法

1. **给模型建档。** 每个模型在 OpenClaw 里注册成 profile，标注能力标签：function calling 是否稳定、上下文窗口、结构化输出可靠性、单次成本、典型延迟、数据是否出网。
2. **任务分三档。** 简单档（改写、分类、抽取）本地 7B–14B 级别足够；标准档（单工具调用、中等长度总结）用本地大模型或性价比云端模型；复杂档（多步规划、跨工具编排、长上下文分析）交给 GPT 这类旗舰模型。
3. **落一个 router 节点。** 在 agent 入口前加一层路由插件，先走规则：按任务类型标签、上下文长度、是否命中敏感数据关键词做静态分流。规则覆盖不了的，再用本地小模型做一次轻量分类，输出档位。
4. **配降级链。** GPT 限流或超时，回退到本地大模型兜底；本地模型结构化输出连续失败两次，升级到云端重试。
5. **记录路由决策。** 每次请求记下：命中哪条规则、最终用了哪个模型、是否回退。没有这份日志，后面所有调优都是盲调。

## 踩坑点

- **别用贵模型当分类器。** 有段时间路由判断本身走了 GPT，结果省下的钱不够分类花掉的。分类用本地小模型甚至关键词规则就够。
- **工具调用能力差异比想象中大。** 本地模型对话流畅，但 function calling 经常漏字段、错字段，agent 会卡在重试循环。凡是重工具编排的链路，路由看能力标签，别只看成本。
- **回退链要考虑幂等。** 云端超时回退重跑时，如果副作用工具（发消息、写库）已经执行过，重跑就是事故。副作用调用前建议加执行记录检查。
- **长上下文别硬塞本地模型。** 超窗口截断后的质量崩得很隐蔽，不如直接路由给长上下文云端模型。

## 可复用建议

- **三档封顶。** 档位越多规则越难维护，误路由排查成本指数上升。
- **盯两个指标：** 升级率（本地升到云端的占比）和回退率。升级率突然升高，先查本地模型服务和任务分布，再动规则。
- **隐私做成硬约束。** 敏感数据默认走本地，显式打标才允许出网，别把它做成可选项。
- **先规则后模型。** 规则能覆盖七成流量，就别急着上分类器。

## 总结

多模型路由不是什么高级架构，本质是把“哪些请求值得花钱”变成一条可观测、可回退的显式策略。先建 profile、再分档、规则先行、留好日志，在 OpenClaw 里百来行配置就能跑起来。真正的收益不在省的那点 token 费，而在系统第一次具备了“按任务分配算力”的能力——后续的成本优化和质量优化，都建立在这层之上。
