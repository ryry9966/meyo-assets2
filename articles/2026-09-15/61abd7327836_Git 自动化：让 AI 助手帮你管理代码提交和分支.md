# 背景

日常开发里，commit message 质量参差、分支越堆越多、忘了切分支就开写——这些小事单看不致命，积累起来很耗人。OpenClaw 这类常驻 agent 接上 shell / MCP 工具后，很自然会被问到"帮我提交一下"。但把 git 权限直接交给 agent，风险和收益一样大。这篇记录我在个人仓库跑了一段时间的折中方案：让 agent 干脏活，人守关键闸口。

# 问题

裸跑 agent 管 git，通常踩三类坑：

1. **提交信息不可信**——模型爱写 "update files" 这类废话，或者过度发挥、编造改动动机；
2. **危险操作不可控**——`push --force`、对共享分支 rebase、`reset --hard` 丢工作区；
3. **上下文不够**——agent 拿不到完整 diff，或一次塞爆窗口后开始幻觉。

# 做法

核心思路：**命令白名单 + 固定信息源 + 人工确认点**。

1. **收窄工具面。** 不给全量 shell，通过 MCP git server 或包装脚本只暴露：`status`、`diff`、`add`（必须带路径）、`commit`、`branch`、`checkout -b`、`log`。push 交给触发式脚本或人工执行。
2. **固定提交信息规范。** 在 agent 常驻规则里写死 Conventional Commits 格式，并要求 message 只描述 diff 中可见的变化，禁止推测意图。每次提交前以 `git diff --staged` 作为唯一信息源。
3. **分支操作模板化。** 统一 `feat/xxx`、`fix/xxx` 前缀，agent 根据 issue 描述生成名字并创建；切换前必须确认工作区干净。
4. **保留本地钩子。** pre-commit 里跑 lint 和 gitleaks，agent 的提交一样会被拦。这道防线不要为了"自动化"拆掉。
5. **危险操作走确认。** rebase、merge、reset 一律让 agent 先输出执行计划再停住，等人回复确认。冲突不自动解，直接报回。

# 踩坑点

- **大 diff 塞爆上下文**：一次重构改了几十个文件，agent 开始编 message。解法：先给 `--stat`，再只挑重点文件的 hunk 分批喂。
- **`git add -A` 带进垃圾**：日志、临时文件混进提交。让 agent 永远显式列文件路径，`.gitignore` 只作兜底。
- **detached HEAD 迷路**：review 时 agent checkout 了旧提交，后续 commit 直接悬空丢失。规则里明确禁止 checkout 到非分支提交，需要时先建分支。
- **让 agent 解冲突**：看着省事，实际经常把两边逻辑各留一半，编译都过不了。冲突必须人来。

# 可复用建议

- 把上述约束沉淀成一段 20 行左右的 agent 规则文件，放进仓库版本化，比每次对话临时叮嘱可靠得多。
- 给 git 封装加 dry-run 模式：先输出将要执行的命令和提交信息，人点头再真跑。
- 提交信息用 `commit -F` 从临时文件读取，避免引号转义把命令炸掉。
- 先在一个低风险仓库跑两周，稳定后再扩大范围。

# 总结

AI 管 git 的价值不在"全自动"，而在把写 message、理分支、翻 log 这类机械劳动接过去。真正的可靠性来自三件事：收窄的工具面、固定的信息源、几个不可绕过的人工闸口。自动化程度是渐进调出来的，不是一次配置出来的。
