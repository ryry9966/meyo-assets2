## 背景

我维护着几台服务器上的若干服务，日志散落各处。过去每天早上花二十分钟翻日志、凑一份日报发到群里，重复且容易漏。接入 OpenClaw 之后，我把这件事做成了三段式流水线：脚本采集归一化 → 确定性统计 → Agent 生成结构化报告，定时推送到群。跑了一个多月，日报稳定，人也省出来了。

## 问题

最直接的想法是把当天日志整个丢给 Agent："帮我总结今天的日志"。实践下来有两个硬伤：

1. **上下文装不下**。高峰日日志几十 MB，截断后 Agent 看到的是残缺样本，结论随机。
2. **数字不可信**。LLM 数数不可靠，"错误 137 次"可能被写成"约 150 次"，而日报恰恰需要精确数字。

结论：数字必须由代码算，Agent 只负责把数字讲成人话，并给出归因猜测和关注建议。

## 做法

流水线分三段，各自可独立验证：

**第一段：采集与归一化（纯脚本）**。定时任务触发，按时间窗拉取昨日日志，解析为统一 JSON 行格式：时间戳统一到业务时区、level 归一化、按 trace_id 去重，输出 `raw.jsonl`。

**第二段：确定性统计（纯脚本）**。十几行 Python 算出固定指标：请求总量、各 level 计数、TOP5 错误码及样本一条、环比昨日变化。输出 `stats.json`，这一步没有任何 LLM 参与。

```json
{
  "date": "2025-06-12",
  "total_requests": 48210,
  "errors": {"count": 312, "rate": "0.65%", "delta": "+0.12%"},
  "top_errors": [{"code": "DB_TIMEOUT", "count": 187, "sample": "..."}]
}
```

**第三段：Agent 叙事（封装成 skill）**。输入 `stats.json`，要求按固定 JSON Schema 输出：`summary`（三句话内）、`highlights`（异常点）、`suggestions`（最多三条）。输出先做 schema 校验，不合格带报错重试一次；通过后渲染成 Markdown 推送到群。中间产物按日期落盘，出问题可回溯。

## 踩坑点

- **时区坑**。最初用 UTC 切窗口，"昨日"实际是前天 08:00 到昨天 08:00，直到有人对不上数才发现。时间窗统一用业务时区，并在报告头部写明统计区间。
- **输出格式漂移**。Agent 偶尔把 suggestions 写成一段散文。靠 schema 校验加重试解决；重试仍失败就降级为只发 `stats.json` 渲染的表格——保证日报每天都发得出去。
- **日志量突刺**。某天上游重试风暴导致日志超两百万行。加了行数上限和按比例抽样，并在 stats 里记录 `sampled: true`，让 Agent 明确标注"数据经过采样"。
- **流水线静默失败**。脚本挂过一次，当天群里没有日报也没人催。补了兜底：任务异常时推送"日报生成失败，原因：xxx"。失败可见比沉默重要。

## 可复用建议

1. **"代码算数、Agent 叙事"是通用分工**，任何要求数字准确的报告类自动化都适用：周报、监控摘要、发布回顾。
2. **Schema 先行**。先定输出结构再写 prompt，格式稳定才有人长期看，也方便做环比和趋势。
3. **中间产物落盘**。Agent 说的每句话能追溯到数字，数字能追溯到原始日志。
4. **区分日报和告警**。日报解决"了解"，告警解决"行动"，不要混在一起做。
5. **支持补跑**。脚本按日期参数化，任何一天都能重跑出当时的报告，排查历史问题很有用。

## 总结

这件事的核心不是"用 Agent 写日报"，而是把流程拆成确定与不确定两半：统计交给代码，语言交给模型。边界清晰后系统才可靠。OpenClaw 在这里承担定时调度、skill 封装和推送通道的角色，并不需要复杂编排。如果你也有一份重复的"翻日志写报告"，照这个三段式起步即可：先让数字跑对，再让话说得漂亮。
