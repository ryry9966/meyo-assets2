# 背景

订阅源多了之后，RSS 阅读器会从工具变成负担：每天几百条未读，真正值得点开的不到一成。我的目标是让 AI 先读一遍，只把“值得花时间”的内容压缩成一份日报。这套管线已经在 OpenClaw 的定时任务上跑了一个多月，稳定输出，日均成本几分钱。

# 问题

RSS 只解决聚合，不解决注意力分配。直接把 feed 塞给 LLM，会撞上几个现实问题：

1. 很多源只有 summary 没有全文，摘要质量差；
2. 同一新闻多源重复，日报冗余；
3. LLM 容易在标题、链接上“发挥”，编造不存在的字段；
4. token 成本随源数量线性增长，不做控制很快失控。

# 做法

整体是一条五段流水线，每天早上定时跑一次：

**抓取 → 清洗 → 去重 → 摘要 → 推送**

1. **抓取**：源列表放 YAML 配置里（名称、URL、分类、备注），用 rss-parser 拉取，原始条目先落库（SQLite），摘要失败可以重放。
2. **清洗**：对只有简介的源做全文抓取，readability 提取正文，截断到 2000 字符。
3. **去重**：URL 规范化（去掉 utm 等跟踪参数）+ 标题相似度比对，高于阈值只保留一条，但记录所有来源。
4. **摘要**：不要一条一调。把 8–10 条编号后拼进同一个 prompt，要求输出严格 JSON：`title`、`url`（原文照抄）、`one_liner`、`tags`、`score`。score 低于 6 的直接丢弃，不进日报。
5. **推送**：按分类渲染 Markdown，webhook 推到群或邮箱，保留原始链接——摘要只帮你筛，点击与否的判断仍留给你。

提示词里加了三条硬约束：不得改写标题、不得补全链接、信息不足时输出 `insufficient` 而不是猜。

# 踩坑点

- **全文抓取是最脆的一环**。部分站点反爬，readability 会提出导航栏或评论区。做法是提取后做长度和关键词校验，不达标就降级用 RSS 自带 summary，并在日报里标注“基于简介”。
- **LLM 编字段**。早期版本让它“生成标题+链接”，链接全是编的。改成元数据全部由代码透传、模型只产出摘要和评分后，问题消失。原则：模型不做搬运工。
- **批量摘要的串扰**。10 条一起摘要时，偶尔会把 A 的内容混进 B 的 one_liner。给每条加编号并要求输出带对应编号，校验完整性，缺了就单条重试。
- **评分漂移**。同一套 score 标准跑两周会松。在 prompt 里放 3 个 few-shot 锚点（明确的高/中/低分示例），每月人工抽查校准一次。
- **单源失败拖垮全局**。抓取和摘要都做 try/except + 失败计数，连续失败 3 次的源自动静默，只在日报末尾提示，而不是每天报错刷屏。

# 可复用建议

- 配置驱动源列表，加源只改 YAML，不动代码；
- 原始数据先落库，prompt 迭代后可随时离线重放；
- 管线做幂等：同一天重跑不产生重复日报；
- 先接 5–10 个源跑两周，把 score 阈值调稳再扩容；
- 批量 + 截断之后，百级源量的摘要调用成本基本可以忽略。

# 总结

RSS + AI 摘要的价值不在“自动读文章”，而在把非结构化信息变成可筛选的结构化数据。整条管线没有黑魔法，难点全在工程细节：抓取的健壮性、去重的准确率、提示词的约束力。建议从最小闭环起步，让日报先跑起来，再逐段加固。
