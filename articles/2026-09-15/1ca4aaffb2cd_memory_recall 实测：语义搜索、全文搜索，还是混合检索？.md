## 背景

OpenClaw 助手的 `memory_recall` 负责在每轮对话前，把相关历史记忆捞回上下文。我们的助手跑了几个月，记忆库约两万条，检索一直用全文搜索（SQLite FTS5）。最近切到语义检索，把两条路都压了一遍，记录一些实测结论。

## 问题

切换的直接动因是一次排障：用户问“上次数据库连接池报错怎么解决的”，全文检索没命中——记忆里写的是"connection pool exhausted"，这次用户用中文描述。反过来也翻过车：问“某同事的 GitHub id”，语义检索返回几条“关于代码协作”的模糊记忆，精确字符串反而排后面。

核心问题：memory_recall 该用哪种检索，还是混着来？

## 做法

先搭评测集再动手：

1. 从真实对话抽 120 条查询，人工标注期望命中的记忆 ID，以 recall@5 为主要指标。
2. 基线：FTS5 全文检索，中文用 trigram 分词（原因见踩坑）。
3. 语义侧：记忆入库时切块（每块 200~400 字），bge-small-zh 向量化，sqlite-vec 做余弦检索。
4. 混合：两路各取 top 10，用 RRF（Reciprocal Rank Fusion，k=60）融合排序。
5. 加时间衰减：score × 1/(1 + 天数/30)，抑制陈旧记忆。

结果：FTS 基线 recall@5 约 0.62，纯语义 0.71，混合 0.84。混合明显最优，前面两类失败案例正好互相补上。

## 踩坑点

- FTS5 默认 unicode61 分词器对中文基本不可用（整句变一个 token），要么接 jieba 扩展，要么 trigram。我们选 trigram，索引大一圈但省事。
- 记忆块切太大（>500 字）会稀释向量语义，太小（<100 字）丢上下文，200~400 字体感比较稳。
- 换 embedding 模型必须全量重建索引。混用两代向量会引入诡异的相关性噪声，模型版本要写进记忆元数据。
- 纯语义对错误码、用户名、日期这类精确串是灾难，这类查询必须留给全文兜底。
- top_k 别贪多。k=8 以上后上下文污染开始超过收益，模型会被无关记忆带偏，比检索不准更难查。

## 可复用建议

- 默认上混合检索。纯二选一在真实查询分布下都会漏，这不依赖具体模型版本。
- 全文列和向量列都保留原文，别只存向量，全文是精确匹配的最后防线。
- 给每条记忆记时间戳和来源标签，时间衰减和过滤都靠它。
- 留一份 50~120 条的评测查询集，任何检索改动跑一遍再上线，前后十分钟的事。
- 延迟预算：两路并行 + RRF，两万条记忆库 P95 约 80ms，在对话场景可接受；记忆库再大十倍就该考虑预过滤了。

## 总结

语义搜索解决“换个说法还能找到”，全文搜索解决“精确字符串必须命中”，memory_recall 两个都需要。对我们的数据，混合加时间衰减比任何单路高 13 个点以上。先建评测集，再谈方案选型——这是这轮迭代唯一值得沉淀的方法论。
