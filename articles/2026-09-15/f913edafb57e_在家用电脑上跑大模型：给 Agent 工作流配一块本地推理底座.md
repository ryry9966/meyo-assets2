## 背景

社区里不少工作流围绕 Agent、MCP 和插件自动化展开。这类场景对模型的要求和日常聊天很不一样：调用频繁、依赖稳定的工具调用（tool calling）、对延迟和成本敏感，而且经常要碰本地文件和内网数据。把推理放到本地，一方面解决隐私和离线问题，另一方面让 Agent 调用不再受配额和账单约束。这篇帖记录我在一台普通台式机上把本地模型接进 Agent 工作流的全过程，供大家对照复现。

## 问题

动手前先认清三个硬约束：

1. **显存/内存预算**。Agent 场景上下文普遍 8K–32K，KV cache 会额外吃显存，实际占用比模型卡片标注的高不少。
2. **工具调用质量**。小参数量模型能否稳定输出合法的 function call，直接决定 Agent 是否可用，这不是跑分能看出来的。
3. **吞吐**。一轮自动化任务可能串十几次调用，10 tokens/s 和 40 tokens/s 的体验差距是断崖式的。

## 做法

我的硬件是 RTX 3060 12GB + 32GB 内存，属于社区常见配置。

1. **选运行时**：直接上 Ollama 或 llama.cpp 自带的服务端，两者都提供 OpenAI 兼容接口，Agent 侧改个 base_url 就能切换。
2. **选模型**：中文场景优先 Qwen2.5 系列。12GB 显存跑 7B 的 Q4_K_M 量化绰绰有余；14B 需要部分层放到内存，速度会掉一档，适合对质量更敏感的任务。
3. **量化档位**：Q4_K_M 是性价比拐点。再往下压，工具调用的格式错误率会明显上升，省的显存不划算。
4. **接入 Agent**：模型名指向本地 tag 即可。MCP 工具的 schema 尽量精简，减少每轮 prompt 体积——上下文是本地推理最贵的资源。
5. **验证先行**：写一个 20 条用例的工具调用测试集（覆盖并行调用、参数缺失、中文参数名、嵌套对象），先跑通再接真实工作流。

## 踩坑点

- **上下文超限不会报错，只会静默变笨**。长任务必须做 token 预算，超了就做摘要压缩而不是硬塞。
- 部分层溢出到内存后速度断崖式下跌。优先减参数量档位，不要靠过度量化硬塞大模型。
- 不同运行时的 tool calling 解析行为不一致，切换运行时必须重跑测试集，不能想当然。
- Ollama 默认串行处理请求，Agent 的并行分支会排队。注意 `OLLAMA_NUM_PARALLEL`，同时评估显存是否扛得住并发。
- 温度别照抄聊天默认值，工具调用场景 0.1–0.3 明显更稳。

## 可复用建议

- **分层路由**：简单抽取、分类、格式转换走本地；复杂规划和多步推理走云端。一个 if 判断就能省下大量 token 开销。
- **embedding 单独跑小模型**（如 bge-m3），别占用主模型的上下文窗口。
- **持续记录每次调用的 tokens/s 和失败率**。攒一周数据，就知道该不该升级硬件、该不该换模型，而不是凭感觉。

## 总结

本地 LLM 不是用来替代云端的，而是给 Agent 工作流补一块确定性的底座：离线可用、数据不出门、调用不计费。普通家用硬件跑 7B–14B 量化模型，支撑日常自动化完全够用。关键工程动作就三件——选对量化档位、验证工具调用质量、控制上下文预算。把这三件事固化成可复用的测试脚本，之后换模型、换硬件都是半小时的事。

欢迎在评论区贴出你们的硬件配置和实测 tokens/s，攒一份社区真实数据表。
