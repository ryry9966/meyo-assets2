## 背景

LLM 本身无状态，每次会话结束上下文清零。对偶尔聊天来说可以接受，但对每天使用的 OpenClaw Agent 来说，反复交代"我用 pnpm 不用 npm""提交信息写中文"非常消耗耐心。我们想要的效果很简单：偏好说一次，之后所有会话自动生效。

## 问题

把历史记录全塞进 system prompt 是最常见的第一版方案，很快会撞上三个问题：

1. 上下文膨胀，无关记忆稀释注意力，Agent 行为反而变差；
2. 无法区分"这次的任务要求"和"长期偏好"，一次性指令被固化为永久设定；
3. 记忆之间会冲突，旧偏好覆盖新指令，用户感觉"它不听话了"。

本质上记忆系统要解决三件事：什么该记（写入）、什么时候想起来（读取）、什么该改或忘（更新与淘汰）。

## 做法

我们分四层实现，全部通过一个 MCP server 暴露给 Agent：

**1. 结构化存储。** 每条记忆是一条结构化记录：

```json
{
  "key": "commit_message_language",
  "value": "zh-CN",
  "type": "preference",
  "scope": "global",
  "confidence": 0.9,
  "updated_at": "2025-01-15"
}
```

关键是 `type` 字段：preference（长期偏好）、fact（项目事实）、task_state（进行中的任务状态）。三者生命周期不同，混在一起必然污染。

**2. 写入路径。** 两条通道：显式写入（用户说"记住……"时调用 `memory_write`）和隐式提取（会话结束后用轻量 prompt 异步抽取候选偏好，初始 confidence 设 0.4）。显式优先级高于隐式。

**3. 读取路径。** 会话启动时只注入 top-N 高置信度全局偏好，硬性限制 10 条以内；其余靠 `memory_search` 按需检索。不要贪多——实测注入 50 条后，Agent 会开始过度套用旧偏好。

**4. 更新与淘汰。** 同 key 新写入采用置信度加权合并而非直接覆盖；被用户明确纠正时降权；30 天未命中且置信度低于阈值的条目转入冷存档，不再注入。

## 踩坑点

- **一次性指令污染**："这次用递归实现"被记成"偏好递归"。解法是提取时强制判断时效性，带"这次/今天"限定的写进 task_state。
- **隐式提取幻觉**：小模型会把推测当事实。所有隐式条目 confidence 上限设 0.6，需二次确认才升权。
- **记忆不可见**：早期用户不知道 Agent 记了什么，出问题无从排查。加了 `memory_list` 工具后记忆完全可审计、可编辑，信任问题解决一大半。
- **过早引入向量库**：几百条以内的规模，tag + key 匹配比 embedding 检索稳定得多，别急着上向量检索。

## 可复用建议

1. 先做结构化 KV + 置信度，跑通闭环再考虑语义检索；
2. 写入必须区分类型和时效；
3. 注入预算硬编码上限（我们用 10 条 / 约 800 token）；
4. 记忆可枚举、可删除、可编辑——这是用户信任的底线；
5. 隐式提取用便宜模型异步跑，不阻塞主对话。

## 总结

好的记忆系统不是"记得多"，而是"记得准、忘得对、看得见"。先从显式写入、结构化存储和硬性注入预算做起，让闭环跑起来，再逐步加自动遗忘和语义检索。记忆是 Agent 的长期资产，值得像数据库 schema 一样认真设计。
