## 背景

OpenClaw 的 workspace 里默认有几个会被注入上下文的文件：AGENTS.md 管行为规范，TOOLS.md 管工具约定，而 USER.md 管的是「对面这个人是谁」。大多数人愿意花一晚上调 system prompt，却让 Agent 对自己一无所知——每次会话都在重新自我介绍。

## 问题

没有 USER.md 时的典型症状：

- 你主力写 Go，它默认给你 Python 示例；
- 每次都要解释「我是后端出身，别科普消息队列是什么」；
- 回答风格漂移：有时过度客套，有时啰嗦绕远；
- 换会话后靠记忆文件东拼西凑，事实互相矛盾。

根因是：Agent 对你的认知分散在几十条历史对话里，检索全凭运气。USER.md 的作用是把这份认知收敛成一个稳定、可控、可版本化的文件。

## 做法

**第一步：建文件。** 在 workspace 根目录放 USER.md，它会随系统上下文一起加载。

**第二步：只写「稳定属性」。** 推荐五个 section：

```markdown
# 用户画像
## 基本情况
- 角色：后端工程师，负责支付网关
- 时区：UTC+8，工作日 10:00-19:00 在线
- 语言：中文交流，代码注释与 commit message 用英文

## 技术栈
- 主力：Go、PostgreSQL、K8s
- 熟悉但不常用：Python（仅写脚本）

## 协作偏好
- 先给结论，再给推理
- 代码给可直接运行的版本，不要伪代码
- 不确定的点明确说不确定，不要硬编

## 禁区
- 不要主动推荐新框架
- 不要解释我已知的基础概念

## 当前关注（动态区）
- 本季度：部署流水线迁移到 ArgoCD
```

**第三步：控制体积。** 全文 40 行以内，动态区不超过 5 条。超了就删，宁可少而准。

**第四步：纳入 git。** 变更走 commit，出问题能 diff、能回滚。

**第五步：让 Agent 参与维护，但你裁决。** 每月让它基于近期对话提议「哪些信息该更新进 USER.md」，输出建议 diff，人工确认后合并。

## 踩坑点

1. **写成简历。** 工作经历、教育背景对日常协作没有信号量，只会稀释重点。
2. **和 AGENTS.md 抢职责。** 「回复要简洁」是行为规范，该进 AGENTS.md；「我是后端，先给结论」才是用户事实。两边重复甚至冲突时，Agent 表现会不稳定。
3. **明文敏感信息。** 手机号、住址、key 都不要写。USER.md 注入每次上下文，同步或分享截图时容易泄露。
4. **信息过期不清理。** 我留过一条早已弃用的框架，结果 Agent 连续两周在示例里用它。文件内容的可信度高于对话，过期信息的危害也被同比例放大。
5. **塞满项目细节。** 项目约定属于各项目自己的 CLAUDE.md/AGENTS.md，USER.md 只放「跟着你走」的属性。

## 可复用建议

- 用「事实 / 偏好 / 动态」三分法自查每一行：客观事实？稳定偏好？临时状态？临时状态不该出现在这里。
- 时区、语言、代码风格三项收益最高，优先写。
- 每季度让 Agent 做回顾生成 diff，人工 merge，形成维护闭环。
- 多设备使用时，git 同步比手动复制可靠得多。

## 总结

USER.md 本质上是一份压缩到极致的「用户接口文档」。它不玄学，就是工程：控制体积、只放稳定事实、版本化、定期修剪。花二十分钟写完第一版，比再调十轮 system prompt 的边际收益都高。
