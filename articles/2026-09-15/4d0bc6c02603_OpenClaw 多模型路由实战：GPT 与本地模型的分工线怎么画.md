## 背景

跑 Agent 的同学现在手上基本都有两类模型：一类是 GPT 这种云端模型，一类是 Qwen、DeepSeek 蒸馏版这类用 Ollama/vLLM 跑在本地的模型。OpenClaw 把模型路由做成了配置层能力，支持在任务/步骤粒度上指定模型和 fallback 链。但社区里问得最多的不是"怎么配"，而是"怎么分"——全走云端成本高还有隐私顾虑，全走本地质量又撑不住复杂工具调用。

## 问题

把路由简化成"贵的就是好"或"本地的就是免费"都会踩坑。真实情况是：同一条 Agent 链路里，不同步骤对模型能力的需求差异极大。规划、工具选择、报错诊断这类决策步骤，需要稳定的 tool-calling 和长上下文，本地小模型经常掉链子；而摘要、信息抽取、格式转换这类加工步骤，本地模型完全够用。路由的本质是**按任务画像分配算力**，不是选"最强模型"。

## 做法

我的思路是按"步骤角色"路由，而不是按 Agent 整体路由：

1. **拆步骤**。把链路里的步骤分成三类：决策类（规划、工具选择、故障诊断）、加工类（摘要、抽取、分类）、批量类（embedding、批量打标）。翻一周的执行日志比拍脑袋准。
2. **定归属**。决策类走云端，加工类和批量类走本地。
3. **配 fallback 链**。两种策略二选一：本地优先 + 校验失败升级云端（省钱向），或云端优先 + 限流降级到本地（稳定向）。配置大概是这个形状（字段名以你手头版本为准）：

```yaml
routing:
  rules:
    - match: { step_role: planner }
      model: gpt-4o
    - match: { step_role: [summarize, extract, classify] }
      model: qwen2.5-14b@local
      fallback: [gpt-4o-mini]
```

4. **建评测集**。整理 20~30 条真实 golden task，路由上线前后各跑一遍，对比成功率和成本。没有这一步，路由调优就只是感觉。

## 踩坑点

- **本地模型的工具调用格式不完全兼容 GPT**，JSON 偶尔会坏。务必在插件侧加 schema 校验，校验失败再升级云端，别裸信返回值。
- **有效上下文会静默缩水**。本地模型标称 32k，长文档下的召回质量下滑明显，而且截断发生时不会有任何报错。
- **延迟直觉会骗人**。批量任务本地快；交互式长输出本地反而更慢，别一刀切。
- **embedding 不要混用**。向量库用本地模型建的，换云端 embedding 会全库失效，反之同理。
- **fallback 重试必须设上限**。我见过两个模型互相踢皮球循环重试 20 次的，账单和时间一起爆炸。
- **缓存会被路由打穿**。同一 prompt 被分到不同模型，缓存命中率直接归零，先在日志里确认。

## 可复用建议

- 按步骤角色路由，别按 Agent 整体一刀切。
- 保留路由决策日志（任务 tag + 模型名 + token 数 + 是否触发升级），这是后续调路由的唯一依据。
- 升级条件写死成显式规则：schema 校验失败、工具连续报错、自评置信度低于阈值。
- 敏感数据默认只走本地，云端访问用白名单显式开启。

## 总结

多模型路由不是"哪个模型更强"的问题，而是把任务画像对齐到模型成本曲线。先用日志分清三类步骤，配一条带升级条件的 fallback 链，再用固定评测集验证——路由就从玄学变成可维护的配置。我这边跑了约一个季度，云端调用量降了六成左右，决策类任务成功率没有下降。数字未必能复制，方法论可以直接搬。
