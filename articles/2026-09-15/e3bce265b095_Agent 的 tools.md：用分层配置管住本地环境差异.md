## 背景

跑本地 Agent 的人大概都经历过这个阶段：为了让模型用上本地工具，把 Python 路径、conda 环境名、某个脚本的位置直接写进 system prompt。换一台机器，prompt 里全是失效信息；同事拉了仓库，跑通的第一件事是手动改配置。

tools.md 的思路很简单：把“这台机器上有什么、怎么用”从 prompt 里拆出来，变成 Agent 启动时读取的结构化文档。它不是给人看的 README，而是 Agent 运行时契约的一部分。

## 问题

不加管理的环境描述会积累三类债务：

1. **环境漂移**：文档写 node 18，机器已经升到 22，Agent 按文档执行直接报错。
2. **配置散落**：一半在 prompt、一半在 .env、一半在 shell rc，没人说得清全貌。
3. **共享与隔离的矛盾**：提交个人路径污染仓库，不提交又丢掉团队共知的工具约定。

## 做法

核心是**分层 + 可校验**。

**第一步：建立基线层 `tools.md`**，进版本库，只写团队共识。每个工具一个条目，字段固定：

```markdown
## ffmpeg
- 调用: ffmpeg
- 版本约束: >= 6.0（旧版 concat 行为不同）
- 前置条件: 输入文件需先转 mp4
- 常见失败: 缺 libx264 时退出码为 1，报错信息有误导
```

**第二步：加个人层 `tools.local.md`**，进 `.gitignore`。同名条目覆盖基线，路径、端口、本机特有脚本都放这里。

**第三步：接入启动流程**。会话初始化时合并两层注入上下文，顺序写死：基线在前，本地在后，本地优先。

**第四步：加漂移检查**。写一个几十行的校验脚本：解析 tools.md 里的命令，逐个 `which` / `--version`，与声明的版本约束比对。挂到 pre-commit 或 CI，文档与现实不一致直接失败。

## 踩坑点

- **写成散文**。Agent 解析自然语言文档不稳定，条目必须结构化、字段固定。
- **把密钥写进去**。tools.md 会被整体注入 prompt 和日志，密钥只应出现环境变量名，不放值。
- **覆盖规则不明确**。两层文件定义了同一个工具却没声明优先级，Agent 挑哪个全看运气，规则要在加载逻辑里固化。
- **越写越长**。单条目超过十行就该拆：tools.md 只放“存在性 + 调用方式 + 约束”，细节链接到普通文档，避免撑爆上下文。
- **只写不复查**。没有校验的 tools.md 活不过一个月，漂移检查不是可选项。

## 可复用建议

- 仓库里放 `tools.md.template`，新成员复制成 local 层再改，避免直接动基线。
- 写个探测脚本自动生成草稿：扫描 PATH 里的常用工具，输出待人工确认的条目，比手写快得多。
- 多项目场景做三层：用户级（`~/.openclaw/tools.md`）→ 项目基线 → 项目本地，逐层覆盖。
- 条目加 `since` 日期字段，半年没动过的条目优先怀疑过期。

## 总结

tools.md 的价值不在“写了文档”，而在把环境知识变成**分层的、可校验的、机器可读的运行时输入**。基线管共识，本地层管差异，校验脚本管漂移。做到这三件事，换机器、换环境的成本会从“改一圈 prompt”降到“改一个 local 文件”。
