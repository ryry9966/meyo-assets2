## 背景：从“应答机”到“值班员”

大多数人对 Agent 的使用是被动式的：你提问，它回答，会话结束就停机。但 OpenClaw 内置了一个容易被忽略的机制——heartbeat。框架会每隔一段时间（默认 30 分钟，可在配置里调整 `heartbeat.every`）用一段极简的 prompt 唤醒 agent：读取工作区根目录的 HEARTBEAT.md，逐条核对，有事就执行并汇报，无事则回复 HEARTBEAT_OK 静默结束。

本质上，HEARTBEAT.md 是一份"agent 能读懂的巡检清单"，配上一个由框架驱动的定时器。

## 问题：被动等待覆盖不了的场景

提醒类（明早有会）、巡检类（服务是不是又挂了）、汇总类（今天攒了多少通知）——这些事不需要对话智能，只需要定期"看一眼、做判断、决定要不要说话"。用裸 cron 脚本能解决一部分，但当判断逻辑涉及多个工具、跨系统关联时，还是得让 agent 来做。矛盾在于：想让 agent 多干活，又不想它每半小时烧一次 token，还半夜给你推消息。

## 做法：把清单写成"三要素"

**第一步，定位文件。** HEARTBEAT.md 放在 agent 工作区根目录（和 SOUL.md、AGENTS.md 同级），没有就新建。

**第二步，每条任务写清三要素：何时检查、做什么、何时闭嘴。** 几个实际在跑的例子：

- **日历巡检**：检查未来 24 小时事件；若有未提醒过的会议且当前时间在 8:00–22:00，发提醒到绑定频道；否则不说话。
- **服务探活**：通过 MCP 工具请求一次 status 接口；连续两次失败才告警，恢复后补报一次；正常时静默。
- **每日摘要**：若今天尚未发过摘要且已过 9:00，汇总 GitHub 通知后发送；状态记录在 workspace 下的 state 文件，发过就更新标记。

**第三步，控制空闲成本。** 在文件顶部加一条策略："无事可做时只回复 HEARTBEAT_OK，不输出解释"。整个清单压在 10 行以内，一行一个任务。

**第四步，明确分工。** 需要"每天 8:00 整"的准点任务，交给系统 cron + openclaw 的 system 事件触发；HEARTBEAT.md 只放"条件型"任务。条件型放心跳，时间型放 cron。

## 踩坑点

1. **心跳不是秒级调度**。默认 30 分钟一次，别指望分钟级精度，准点需求一律走 cron。
2. **空闲不等于免费**。每次心跳都是一次带工具的完整模型调用。我最初把清单写到 50 行，一天几十次全量 prompt，账单很难看。10 行以内是实测合理的上限。
3. **任务不幂等会刷屏**。摘要任务没做状态检查时，一早上发了三遍同样的内容。解法是让 agent 自己维护状态文件，或在任务描述里写死"已执行过则跳过"。
4. **无人值守不等于放开权限**。心跳走同一套工具白名单和审批流程，危险命令别放行；推送类动作限制在 active hours 内。
5. **观测先行**。改完清单先在日志里观察几次心跳的输出和 token 消耗，确认静默逻辑真的生效，再放开真实推送。

## 可复用建议

- 把 HEARTBEAT.md 当运维巡检清单，不当愿望清单。每条任务必须能回答一个问题："什么情况下闭嘴？"
- 能力边界由 MCP 工具决定：日历、代码仓库、家庭设备接入之后，清单才有内容可写，否则是巧妇难为无米之炊。
- 低价值检查用心跳 + 低成本模型即可，需要复杂推理的环节在任务里显式说明，避免每次心跳都用旗舰模型硬跑。
- 从一到两个任务开始，稳定运行一周再加新条目。

## 总结

HEARTBEAT.md 的价值不在于"自动化"这个词本身，而在于它把调度、状态、静默策略压缩成了一个 agent 每次醒来都会读的文件。清单短、任务幂等、无事静默、准点交给 cron——做到这四条，主动式 Agent 才是省心的，而不是烧 token 的。
