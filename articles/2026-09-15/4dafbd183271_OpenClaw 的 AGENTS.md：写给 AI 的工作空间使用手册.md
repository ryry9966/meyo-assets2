## 背景

OpenClaw 的 agent 不是每次醒来都失忆，但它确实依赖 workspace 里的几份固定文件建立上下文：SOUL.md 管人格，USER.md 管用户画像，而 **AGENTS.md 管操作**——每次会话启动时它会被注入 system prompt，相当于 agent 上岗前必读的工作空间手册。AGENTS.md 本身也是一个跨工具的社区约定，不少编码类 agent 都认这个文件名，一份写好可以多处复用。

## 问题

多数人刚上手时习惯靠对话反复交代：路径在哪、用什么语言回复、哪些目录别动。聊得越多越发现两个问题：一是每次新会话都要重复一遍；二是 agent 在长对话里会"漂移"，前文答应过的事后面就不认了。

于是大家开始往 AGENTS.md 里堆规则，堆到几百行，结果新问题出现：上下文预算被吃掉、规则互相冲突、agent 反而变得迟疑。**AGENTS.md 的问题本质是：它同时承担环境说明、行为边界和提示词工程三种角色，混着写必然失控。**

## 做法

我的经验是分层写、命令式写、定期修剪：

1. **最小可用起步**。第一版只写三块：工作区结构（哪些目录可写、哪些只读）、常用命令（构建/测试/部署的确切命令行）、回复约定（语言、格式、是否先确认再执行）。
2. **可判定的写法**。不写"尽量注意安全"，写"删除 `workspace/media` 之外的文件前必须先向我确认"；不写"代码要规范"，写"提交前跑 `pnpm test`，失败不得 commit"。Agent 执行的是判定条件，不是愿望。
3. **单一事实来源**。某个约定如果 SOUL.md 或插件配置里已有，AGENTS.md 就不要再抄一遍，否则改动时必然漂移。
4. **和自动化联动**。cron 任务、heartbeat 的行为约束也写进来，比如"夜间任务只追加日志，不修改源文件"。
5. **当代码维护**。走 git，每次改动写清原因；每修一个 agent 反复犯的错，就沉淀一条针对性规则；每月删一次再没触发的规则。

## 踩坑点

- **长度失控**：每行都吃上下文，规则越多冲突概率越高。我目前控制在 80 行以内，效果反而更好。
- **密钥入文**：AGENTS.md 会进上下文、可能进日志，凭据一律放环境变量，文件里只写"密钥从 env 读取"。
- **写成散文**：大段叙述 agent 抓不住重点，短句 + 列表 + 明确主语最有效。
- **忘了 agent 视角**：写"按我们的规范来"却不给路径和平台差异，agent 只能靠猜，猜错就是事故。
- **只写不验**：改完不测，等于没改。

## 可复用建议

每次改完 AGENTS.md，新开一个干净会话，丢三个典型任务进去：一个日常任务、一个边界情况、一个它以前犯过错的任务，看它是否遵守——相当于给手册做回归测试。结构上建议固定为五段：**环境 / 边界 / 流程 / 禁忌 / 常见任务**，方便在多个项目间直接复制。

## 总结

AGENTS.md 的价值不在于写了多少，而在于每次会话帮你省掉多少重复沟通、拦住多少次越界操作。小而准的规则集，几乎总是优于大而全的说明书——把它当代码维护，agent 才会像同事一样可靠。
