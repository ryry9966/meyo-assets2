## 背景

我们在社区里用 OpenClaw 挂了几个长期任务：每周摘要、版本通告、新帖自动归档回复。内容生成走 Agent + MCP 工具链，发布统一进队列。第一版上线两周就有人私聊问"你们是不是换机器人运营了"——不是内容问题，是节奏问题：每晚 21:00 准点一条，间隔误差为零，周末照发。人一眼就能看出来。

## 问题

定时任务天然是"机器味"的来源：

- cron 固定触发，发帖间隔方差为零；
- 凌晨深夜照发，不符合社区真实活跃窗口；
- 失败重试后补发，形成短时连击；
- 每条帖子长度、结构、措辞高度一致。

## 做法

核心思路：把"生成"和"发布"解耦，中间加一层节奏调度器。

1. **定义活跃度画像。** 按社区历史数据划出工作日/周末的活跃窗口，比如工作日 10:00–22:00，周末压缩到 14:00–21:00。发布器只在窗口内出队。
2. **用分布采样代替固定间隔。** 不要 uniform，更不要定值；按窗口内的历史发帖密度做加权采样，叠加少量 jitter，同时设硬下限（相邻两条至少隔 40 分钟）。
3. **允许"缺席"。** 人不会每天准点出现。给每个日槽 10–15% 的丢弃概率，配合每周总量配额，不为凑数硬发。
4. **事件优先于时钟。** 版本发布、CI 完成这类有真实触发源的内容直接事件驱动发布，不走节奏队列——真实事件本身就是最好的拟人化。
5. **内容层同步去同质化。** 模板池至少 3–4 套，长度分布拉开，落款随机省略。
6. **观测先行。** 调度器每次决策都落日志：为什么选这个时间、为什么丢弃。先跑两周 dry-run（只记录不发布），人工看曲线再放行。

调度采样伪代码：

```python
def next_slot(now):
    window = profile.active_window(now)   # 今天的活跃窗口
    while True:
        t = sample_from_density(window)   # 按历史密度采样
        if t < now + MIN_GAP: continue
        if random() < SKIP_RATE: continue # 模拟缺席
        return t
```

## 踩坑点

- **uniform 随机不等于像人。** 方差过大反而更假：人发帖是聚簇的——坐下来连发两三条，然后消失几小时。后来改成 session 模型：一个 session 内 2–3 条短间隔，session 之间长间隔。
- **时区。** 服务器 UTC、社区 UTC+8，第一批帖子全落在本地凌晨。所有窗口判断强制先转社区时区。
- **重试风暴。** API 429 的指数退避要和节奏队列联动，否则恢复瞬间连发一串，前功尽弃。
- **别把节奏和内容生成耦合。** jitter 只应影响发布时间，不该触发重新生成，否则同一条摘要会产出两个版本。

## 可复用建议

- 把节奏抽成 cadence profile 配置：窗口、密度曲线、skip 率、session 参数。一个社区一份，不要全局共享——每个板块的活跃结构不一样。
- 上线初期保留人工确认：队列先走 shadow 模式，人点一下才发，攒两周真实节奏数据再放开自动化。
- 用反馈信号校准：跟踪每条的回复率/点击率，某时段持续低迷就下调该时段权重。节奏控制的目标不是"骗过谁"，而是让信息出现在人愿意看的时候。

## 总结

不像机器人的关键不是堆随机数，而是让调度行为贴合社区真实的活跃结构：有窗口、有聚簇、有缺席、有事件驱动。生成与发布解耦、一层可观测的节奏调度器、内容层去同质化——三件事做完，大部分"机器味"就没了，剩下的靠数据慢慢调。
