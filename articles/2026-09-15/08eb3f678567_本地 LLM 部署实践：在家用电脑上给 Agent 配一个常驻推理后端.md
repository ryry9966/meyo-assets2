## 背景

做 Agent 和自动化的同学，大部分推理都走云端 API。动机很直接：Agent 常驻循环烧 token 很快，按量计费月底一看不便宜；本地文件、聊天记录发给第三方也有顾虑；再加上限流和断网，链路随时可能断。OpenClaw 这类跑在自己机器上的 Agent 网关，天然适合再接一个本地模型当备胎或主力。

我拿家里一台 8GB 显存的旧台式机和一台 16GB 统一内存的 Mac 试了一个月，把链路跑通了，这里记录实际过程。

## 问题

动手前真正要回答的是三个问题：

1. 我的硬件到底能跑多大的模型？
2. 用什么推理栈，怎么对外暴露接口？
3. 本地模型能不能撑住 Agent 的工具调用——长上下文加稳定的 JSON 输出？

## 做法

**第一步，摸清硬件。** 显存优先，经验值：7B 的 Q4 量化约占 5-6GB，14B 约 9-10GB，32B 要 20GB 起，还得给 KV cache 留余量。8GB 显存踏实跑 7B，12GB 可以碰 14B，24GB 才谈 32B。Mac 统一内存可以大方一些，但速度看带宽。

**第二步，选推理栈。** 入门用 Ollama，一条命令拉模型，自带 OpenAI 兼容接口；要细控参数（上下文长度、卸载层数、量化方式）直接用 llama.cpp；多卡高并发才需要 vLLM，家用场景用不上。

**第三步，选模型。** 从 7B-14B 的 Instruct 版 Q4_K_M 起步，先打通链路再谈升级。别一上来就追参数量。

**第四步，接入 Agent。** 把 base_url 指到 `http://localhost:11434/v1`，模型名对上即可，MCP 工具的 schema 原样透传。

**第五步，用真实任务压测。** 不要拿"你好"测，跑一遍带多轮工具调用的完整 Agent 循环，记录 tokens/s 和工具调用成功率，这才是有效数据。

## 踩坑点

- **上下文长度**：默认 `n_ctx` 往往只有 2K-4K，而 Agent 的 system prompt 加工具 schema 轻松吃掉大半，必改 16K 起。注意 KV cache 显存随长度线性涨，改完实测别 OOM。
- **量化太狠毁掉工具调用**：Q2/Q3 的小模型经常输出非法 JSON，函数调用一断整个 Agent 循环就废。宁可用 Q4 的小模型，也别用 Q2 的大模型。
- **冷启动尖刺**：Ollama 默认 5 分钟卸载模型，定时任务隔久了再调会卡 30-60 秒，把 `keep_alive` 设长。
- **部分 GPU 卸载是陷阱**：offload 一半层受 PCIe 带宽限制，速度可能不如预期，全上或全下都实测一遍再定。
- **温度参数**：别照搬云端习惯的 0.7，工具调用场景建议 0-0.2，输出才稳定。
- 显存紧张时开 flash attention 加 KV cache 量化（q8_0），质量损失基本无感，能省不少。

## 可复用建议

- **分层路由最稳**：意图识别、摘要、格式化这类轻活交给本地小模型；复杂推理和写代码仍走云端；隐私敏感数据强制本地。别指望本地模型一步替代云端。
- **建立自己的回归基准**：固定三个真实任务（单轮对话、多工具调用、长文档摘要），每次换模型或换量化后跑一遍，数据说话。
- **显存预算公式**：模型权重 + 1.2~1.5 倍目标上下文的 KV cache，再留 10% 给系统。

## 总结

家用电脑跑本地 LLM，如今不是能不能的问题，而是怎么配的问题。对 Agent 用户来说，本地模型的价值不是替代云端，而是提供一个常驻、免费、可控的底座。先小模型打通全链路，再按真实任务的数据决定升级幅度，这条路最少走弯路。欢迎在评论区交流各自的硬件配置和实测数据。
