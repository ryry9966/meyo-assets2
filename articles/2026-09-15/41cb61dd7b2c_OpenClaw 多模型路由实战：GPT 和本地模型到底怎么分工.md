## 背景

在 OpenClaw 的 agent 链路里，模型调用通常占掉大部分成本和延迟。很多团队的起步做法很简单：全部走 GPT，效果稳，但月底账单一拉，发现 70% 的 token 花在了"格式化输出""简单分类""重试补全"这类低复杂度环节；而另一些涉及内网数据的任务，因为合规原因根本不该出网，却也被迫走了同样的通道。

## 问题

单模型策略的两个极端都不划算：

- **全云端**：贵、慢、敏感数据有出网风险；
- **全本地**：复杂推理和长上下文任务质量明显下降，工具调用成功率不稳定。

路由要解决的核心问题是：**在任务粒度上做区分，而不是在应用粒度上一刀切**。

## 做法

我们的路由层只做三件事：任务打标、规则路由、失败降级。

**1. 任务打标**。在 OpenClaw 插件入口处给每次调用打上 `task_type`（classification / extraction / reasoning / tool_call / summary）和 `sensitivity`（是否涉及内网数据）。

**2. 规则路由**。用一张简单的路由表决定去向：

```yaml
routes:
  - match: { task_type: [classification, extraction], sensitivity: internal }
    model: local/qwen2.5-14b
  - match: { task_type: reasoning, ctx_len_gt: 8000 }
    model: cloud/gpt-4o
  - default: local/qwen2.5-14b
fallback: cloud/gpt-4o
```

**3. 失败降级**。本地模型工具调用解析失败或超时，自动降级到云端重试一次，并记录降级原因，作为后续调整路由表的依据。

经验值：分类、抽取、格式转换这类任务，本地 14B 模型基本够用；多步推理、跨工具编排、长上下文摘要，留给云端。

## 踩坑点

- **别只按上下文长度路由**。我们最初用"超过 4k token 就走云端"，结果很多短任务其实是多步推理，本地模型反复输出格式错误，降级率反而比长任务还高。任务类型比长度更重要。
- **工具调用格式差异**。不同模型对 function calling 的 schema 遵循度差距很大，本地模型容易漏参数或多包一层。建议在插件层做统一参数校验，不要信任模型原始输出。
- **降级风暴**。某天本地服务 OOM，全部流量瞬间打到云端，账单一天翻了三倍。降级必须带熔断和流量上限。
- **Embedding 不要跟着换**。路由切换时顺手换了 embedding 模型，导致向量库检索质量莫名下滑。Embedding 一旦定下来就不要动。

## 可复用建议

1. **先测量再路由**：跑一周"全云端"作为 baseline，记录每个 task_type 的调用量、耗时、成本，路由表应该从这份账单里长出来，而不是拍脑袋。
2. **给路由层留观测**：每次调用记录 model / task_type / 是否降级 / 耗时。没有这些数据，路由表无法迭代。
3. **新规则先影子跑**：新路由只记日志不生效，对比一周输出质量后再切流量。
4. **路由表保持简单**：三条规则能解决就不要写十条，复杂的路由逻辑本身会变成新的故障点。

## 总结

多模型路由不是单纯的"省钱技巧"，而是把任务复杂度、数据敏感性和成本放进同一个决策框架。在 OpenClaw 侧，需要的只是插件入口打标 + 一张简单路由表 + 降级熔断，百来行代码就能跑起来。正确的顺序是：先用数据找出哪 20% 的调用贡献了 80% 的成本，把它们迁到本地模型，剩下的留给云端。顺序反过来做，基本都会返工。
