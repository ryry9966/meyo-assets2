## 背景

信息源越来越散，但 RSS 反而是最稳定的机器可读输入——结构清晰、无需爬虫适配。对玩 Agent 和自动化的用户来说，RSS 天然适合做管线的数据入口。问题在于订阅一多，瓶颈从"找不到信息"变成"没时间读"。于是很自然的想法：用 LLM 把"每天扫 50 篇"压缩成"读 1 份摘要日报"。

## 问题

直接把 feed 扔给模型，实际会遇到三个坎：

1. **正文残缺**：很多源只输出 summary，模型看到的本身就是二手信息；
2. **噪音稀释**：抓回来的条目大量重复、低价值，直接摘要既烧 token 又降低信噪比；
3. **没有出口**：摘要生成完躺在日志里，等于白做。

所以重点不是"接个 LLM"，而是搭管线：**抓取 → 清洗去重 → 摘要 → 分发**。

## 做法

我的方案是在 OpenClaw 里跑一个定时任务，配几个轻量脚本：

1. **源配置化**：用 YAML 维护订阅源，每条带分类和关键词过滤规则，加源只改配置不动代码；
2. **抓取与去重**：定时拉 feed，解析 guid、标题、正文，用 guid + 标题哈希去重，已处理记录落 SQLite，保证幂等；
3. **正文兜底**：正文短于 500 字符时回退抓原页提取全文——这一步决定摘要质量上限；
4. **分批摘要**：按分类分批喂给模型，prompt 要求输出"一句话结论 + 2-3 个要点 + 是否值得深读"，让模型排优先级而不是平均用力；
5. **双出口**：产出 Markdown 日报落本地（可回溯，也给 Agent 留作检索语料），同时 webhook 推送到 IM。摘要只做入口，永远附原文链接。

## 踩坑点

- **编码转义**：feed 正文常有 CDATA 和 HTML 实体，不清洗的话模型在处理标签噪音，先 strip 再截断；
- **截断策略**：长文从头截断会丢结论，我的做法是头尾各取一段拼接，要点常在结尾；
- **幻觉**：prompt 必须写明"信息不足就写信息不足，不要补全"，宁可空一点；
- **更新型重复**：guid 不变但内容更新的文章，只按 guid 去重会漏。折中方案：guid 已处理但内容哈希变了才重新摘要；
- **限流 403**：并发压到 1-2，加随机间隔，配个正常 User-Agent；
- **成本失控**：摘要前加一层规则过滤，无关条目拦在 LLM 之外，token 能省一半以上。

## 可复用建议

- **三层解耦**：抓取、处理、分发各自独立，单层坏了不影响其他层重跑；
- **状态落盘**：处理过什么、摘要过什么都要持久化，管线必须能幂等重跑；
- **prompt 当配置**：摘要模板放配置文件，方便对比不同模板的输出质量；
- **给 Agent 留接口**：日报落成结构化 markdown 后，可以让 Agent 随时检索历史，回答"上周某领域有什么动静"——这才是管线的长期价值。

## 总结

这条管线的关键不是"AI 摘要"本身，而是围绕它的工程化：去重、兜底、状态、分发。AI 只负责压缩信息，压缩前的清洗和压缩后的落盘，才决定它能不能长期稳定跑。整体一个周末的工作量，之后每天省下的阅读时间远超投入。
