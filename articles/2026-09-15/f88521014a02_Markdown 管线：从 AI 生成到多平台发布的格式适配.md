## 背景

用 Agent 产出内容后，真正费时间的往往不是写，而是发。同一篇 Markdown 要发公众号、知乎、掘金、自建博客，各平台规则差异很大：公众号只吃受限的内联样式 HTML，知乎对表格和代码块支持有限，博客相对宽容。人工逐平台改格式既琐碎又容易漏，这类确定性劳动非常适合沉淀成管线。

## 问题

最常见的错误做法是让 Agent 直接“帮我生成公众号 HTML”。这有两个硬伤：一是输出不可控，每次生成的样式有细微出入，无法做回归测试；二是内容与格式耦合，改一处就要全量重新生成。正确的分层是：**AI 只负责产出规范化的源 Markdown，格式适配交给纯确定性的转换层**。

## 做法

1. **定义规范源格式**：约定 frontmatter（title、tags、目标平台列表）、全文唯一 H1、代码块必须带语言标注。写一个 linter，AI 输出不合规就打回重写，而不是人肉修。
2. **构建 canonical AST**：用 remark 把 Markdown 解析成 mdast，后续所有操作在 AST 上做，杜绝字符串替换。
3. **平台适配器**：每个平台一个纯函数 adapter。公众号走 rehype + 内联样式注入 + 图片本地化重传；知乎做表格降级、代码块简化；博客几乎直出。
4. **图片处理**：外链防盗链是重灾区，管线里统一做下载 → 重命名 → 上传目标图床 → 回写 AST 节点。
5. **冒烟验证**：对各平台产物做渲染快照测试，同时静态检查是否残留 frontmatter、是否存在死链、图片是否上传成功。
6. **接入自动化**：整条管线封装成一个 MCP tool，Agent 侧只调用 `publish(markdown, platforms)`，错误信息结构化返回，方便 Agent 自我修正。

## 踩坑点

- 公众号会剥掉大部分标签和 class，样式必须全部内联，且部分属性（如 position）直接失效，不要指望规则表一次写全；
- AI 生成的代码块语言标注经常缺失或写错，高亮会默默退化成无色，必须在 linter 层拦截；
- 数学公式最脆：KaTeX / MathJax / 平台私有方案互不兼容，建议先做能力检测，不行就降级为图片；
- 图片回写后务必校验 URL 可达，上传失败宁可终止发布，也不要留死链；
- 中文排版（全角标点、中英文间距）在 linter 里统一处理，别指望平台兜底。

## 可复用建议

- 适配器保持纯函数、无副作用，单测和快照才好写；
- 每个平台维护一份“能力清单”（支持表格？支持脚注？图片是否需重传？），adapter 按能力矩阵分支，而不是散落的 if-else；
- 快照测试远比肉眼比对可靠，一次接入长期受益；
- 职责边界划清：**不要让 Agent 碰转换层，它的职责止于规范化 Markdown**。

## 总结

这条管线本质上是把“格式适配”从 LLM 的随机性里剥离出来：AI 管内容质量，AST + 纯函数 adapter 管确定性转换，快照测试守住回归。跑通之后，发一篇多平台内容的边际成本接近于零，Agent 也能以一个工具调用的方式稳定复用。建议从小做起——先只做“源规范 + 公众号 adapter”两个环节打通，再逐步横向扩展平台，避免一开始就铺满矩阵。
