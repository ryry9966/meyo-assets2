## 背景

RSS 没死，只是退到了角落。技术博客、GitHub Release、安全公告、项目 changelog，这些高质量信源几乎都还提供 feed。问题是我每天真的没时间逐条打开 reader。目标很朴素：**每天早上收到一份针对我个人兴趣过滤过的摘要**，来源可追溯，失败可见。

## 问题

拆开看有四个子问题：

- 信源更新时间分散，需要定时抓取而非被动等推送；
- 很多 feed 只给 summary 不给全文，直接喂模型摘要质量很差；
- 通用摘要工具不理解"我关心什么"，粒度要么太粗要么全是噪音；
- 自动化管线最怕静默失败——挂了一周没人发现，比没有还糟。

## 做法

技术栈：OpenClaw agent 的 cron 能力做调度 + 一个不到 300 行的 Python 脚本 + 任意 LLM API。全文抓取可接一个 readability 类的 MCP tool，不接也行。

分层来做：

1. **订阅层**：所有源收进一份 OPML，RSSHub 补齐没有原生 feed 的站点，新增信源只改配置。
2. **抓取层**：每 6 小时拉一次各 feed，取最近 24h 条目；如果 entry 没有正文，用 readability 兜底抓网页。
3. **去重层**：以 `guid`/`link` 的哈希写入 SQLite，处理过的直接跳过。这一步同时是后面"改 prompt 不重抓"的基础。
4. **摘要层**：两级结构。单条摘要要求模型输出结构化 JSON：100 字以内摘要、3 个标签、1-10 相关度评分、信息不足时明确写 `unknown`。再把高分条目聚合成当日 digest。
5. **推送层**：digest 写成 Markdown 落盘，同时推一个 webhook 到我的聊天渠道。

核心的 prompt 骨架大概长这样：

```text
基于以下正文（可能被截断）输出 JSON：
{"summary": "...", "tags": [...], "score": n, "confidence": "high|low"}
正文不完整时 confidence 必须为 low，不要推测缺失内容。
```

## 踩坑点

1. **只有摘要的 feed** 是最大的质量杀手。必须抓正文；截断时保留结尾，技术文结论常在尾部。
2. **一次塞 50 条超上下文**。改成每批 10 条分别摘要，再做二级聚合，顺便让评分更稳定。
3. **幻觉**：给截断文本总结，模型会补全它想象中的内容。硬性要求 `confidence` 字段 + 允许留空，比反复调措辞管用。
4. **静默失败**：feed 改版、403、DNS 失效都会悄悄发生。抓取错误记日志，并在 digest 末尾固定附一段"本轮失败源清单"，失败本身进入信息流。
5. **时区**：agent 的 cron 跑的是 UTC，digest"每天 8 点"其实对应北京时间 16 点。调度表达式里显式写时区。
6. **成本**：大 feed 全量过模型不划算。先用关键词和来源权重做规则过滤，只把候选条目送模型，调用量降了一个数量级。

## 可复用建议

- 把**相关度评分**放进输出 schema，低分条目只进标题索引，digest 长度自然可控。
- 摘要 prompt 和抓取逻辑彻底解耦，换模型做 A/B 时不动管线。
- SQLite 里存原始条目全文，prompt 迭代后可以离线重放，不用重新抓。
- 每周花十分钟人工 review 一次评分分布，阈值漂移了就校准——这个环节没法全自动。

## 总结

管线跑了一个多月，最大的收益不是"省时间"，而是把信息摄入从**被动刷**变成了**定点审**：每天一个固定入口，来源可查，噪音可调。回头看，真正决定摘要质量的不是模型，而是正文抓取、去重和失败可见性这些脏活——模型只是管线的最后一环。代码量很小，建议有类似需求的直接从抓取和去重两层开始搭。
