# 从零搭建 AI 社区发帖机器人：架构设计与踩坑实录

## 背景

OpenClaw-CN 社区的资讯散落在 GitHub Release、博客 RSS 和群聊里，人工整理发帖既耗时又容易漏。我花了两周写了一个发帖机器人，跑了一个月，期间发过重复帖、断链帖，也发过质量明显下滑的水帖。这篇记录架构取舍和真实的坑。

## 问题定义

目标很克制：**自动聚合信息源 → LLM 摘要成帖 → 人工审核 → 定时发布**。不做全自动无人审核，不做互动回复。核心约束是三个：不重复、不断链、不出戏（语气符合社区风格）。

## 架构与步骤

整体是四段式流水线，各段解耦，用消息队列（Redis 即够用）串联：

1. **采集层**：cron 每 30 分钟拉取 RSS / GitHub API / 关键词监听，产出原始条目，先过一层 URL 去重（布隆过滤器 + 数据库唯一索引双保险）。
2. **生成层**：Agent 通过 MCP 工具拿到条目正文，按固定模板生成草稿——标题、摘要、来源链接、标签。提示词里塞了 5 篇历史精选帖做 few-shot。
3. **审核层**：草稿写入待审队列，我在一个轻量后台里点通过/驳回。驳回的条目连同理由回写，作为下次生成的负例。
4. **发布层**：到点后走社区 API 发帖，带全局限速（每小时 3 篇）和失败重试（指数退避，最多 3 次）。

```
[采集 cron] → [去重] → [Agent+MCP 生成] → [人工审核] → [限速发布]
                              ↑______ 驳回样本回流 ______|
```

## 踩坑实录

- **重复发帖**：早期只用 URL 去重，结果同一事件被三个源转载，发了三篇角度雷同的帖。后来加了基于 embedding 相似度的语义去重（阈值 0.88），才真正压住。
- **幻觉链接**：LLM 偶尔会把链接写错或“补全”。解法很土：链接不允许模型生成，只允许从采集层原样透传，模型只负责文字部分。
- **重试风暴**：社区 API 限流后，重试逻辑没有退避，几分钟内打了上百次请求，账号被临时封禁。加上指数退避 + 熔断（连续 5 次失败暂停 30 分钟）后稳定。
- **质量漂移**：跑一周后帖子越来越像模板腔。原因是 few-shot 样本里混进了早期质量一般的帖子。改成人工精选样本 + 每周更换后恢复。这也说明**生成质量的上限就是样本质量**。
- **时区坑**：cron 用 UTC 配的“每天 9 点”，实际在国内凌晨发帖，曝光很差。统一用 Asia/Shanghai 并在发布层再校验一次。

## 可复用建议

- **审核环节不要省**。全自动发帖省下的人力，会在一次事故（发错内容、断链刷屏）里加倍还回去。
- **链接、数据等事实性内容走管道透传，不走模型生成**，这条原则适用于所有内容类 Agent。
- 去重做两层：精确层（URL/ID）+ 语义层（embedding），成本不高，收益极大。
- 所有外部调用默认“会失败会限流”，退避、熔断、全局限速从一开始就写上。
- 把驳回样本当资产，定期回流到提示词里，机器人会越用越准。

## 总结

这个项目技术上没有难点，难的是把“看起来能跑”和“敢让它天天发帖”之间的距离走完。架构上每一段都简单可替换，出问题时能快速定位到层。下一步计划把审核数据做成小规模偏好集，微调或优化打分模型，把驳回率从现在的 15% 再往下压。代码整理后会开源到社区仓库，欢迎一起踩坑。
