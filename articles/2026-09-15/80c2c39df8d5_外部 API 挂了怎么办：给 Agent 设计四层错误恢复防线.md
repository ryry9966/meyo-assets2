## 背景

现在的 Agent 很少只调一次模型。一个典型任务里，LLM 要串联 MCP 工具、插件、第三方 HTTP 服务，任何一环抖动都会传导到整条链路。传统微服务里的重试、熔断、降级经验依然有用，但 Agent 场景多了一个变量：调用失败后做决策的，是一个会"自由发挥"的模型。失败路径设计不好，挂掉的不只是接口，还有输出的可信度。

## 我们踩过的三类事故

1. **无限重试烧预算**：上游返回 429，agent 循环重试没有上限，token 和费用翻倍，上游也被打得更死。
2. **模型拿堆栈当上下文**：工具抛出的原始异常直接喂回模型，结果要么陷入道歉循环，要么干脆编一个"看起来合理"的结果。
3. **副作用重复执行**：非幂等的写操作（下单、发消息）在超时后被重试，用户收到两条一样的消息。

还有一个更隐蔽的：某工具调用没设超时，整个 agent 循环被卡死，用户以为程序崩了。

## 做法：四层防线

**第一层：传输层超时与重试。** 每个外部调用必须有显式超时；只重试可重试错误（429 / 5xx / 网络超时），4xx 参数错误重试没有意义；指数退避加随机抖动，重试次数和总时长都要有硬上限。

**第二层：工具包装层统一错误信封。** 所有工具调用走同一个 wrapper，向上返回结构化错误而不是堆栈：

```json
{"ok": false, "error": "upstream_timeout", "retryable": true, "hint": "switch to fallback tool or report to user"}
```

模型拿到这种信息，才能做出"换工具 / 降级 / 如实上报"的决策。熔断也做在这一层，粒度按上游 endpoint 划分，而不是按"工具名"。

**第三层：任务层幂等与断点。** 写操作带幂等键，重试天然安全；长任务每完成一步就落盘状态，恢复时从断点续跑，而不是从头再来一遍。

**第四层：Agent 层降级与预算熔断。** 每个关键依赖准备降级剧本：备用工具、可接受的缓存新鲜度、"如实告知用户数据源暂不可用"的话术。同时给整个任务设预算熔断——重试次数、总耗时、token 花费任一超标就停下来问人，绝不静默烧完。

## 踩坑点

- **退避不加抖动**：多个 agent 实例同时到期重试，惊群效应把半死的服务彻底打死。
- **吞错误假成功**：catch 之后返回空数组继续跑，agent 拿空数据推理，错得更远也更难排查。
- **熔断粒度错位**：按工具名熔断，同一上游的不同方法互相牵连，该熔的不熔、不该熔的全熔。
- **只测 happy path**：降级逻辑上线后从未被真正触发，真出事时才发现备用工具的鉴权早就过期了。

## 可复用建议

1. 统一工具包装器，错误信封格式固定，新插件零成本获得重试、熔断、trace 日志能力。
2. 每个外部依赖维护一页"降级剧本"，写清主备切换条件和缓存可用策略。
3. 日志带 trace_id 串联一次任务的完整调用链，复盘时才能定位是哪层先挂。
4. 定期在 staging 做故障注入：手动关掉依赖，观察 agent 是优雅降级还是原地发疯。

## 总结

Agent 的可靠性不取决于模型多聪明，而取决于失败路径设计得多清楚。三句话概括：**错误要分类，副作用要幂等，失败要可见。** 把重试、熔断、降级下沉到工具包装层，让模型始终拿到可决策的结构化信息——这样 API 挂掉时，agent 给出的是"我暂时拿不到数据"，而不是一个编造的答案。
