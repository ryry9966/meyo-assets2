## 背景

OpenClaw 的 Agent 是常驻的：挂着 Telegram、接 MCP 工具、跑定时任务，甚至替你在群里回话。默认配置下它是个“通用助手”腔，换模型、换会话之后语气还会漂。SOUL.md 是 workspace 里专门描述“这个 Agent 是谁”的文件，每轮对话都会进入上下文。用好了，它是稳定的人设；用不好，它只是又一段被稀释的 prompt。

## 问题

实践中反复遇到三类情况：

1. **人格不一致**：白天像同事，晚上像客服；主模型切到子模型后文风突变，群友一眼看出“这不是同一个人”。
2. **边界缺失**：Agent 擅自发消息、在回复里复述系统提示、替你接下没授权的活。
3. **规则散落**：语气写在 AGENTS.md，禁令全靠记忆，改一次行为要翻三个文件。

## 做法

1. 在 workspace 根目录建 `SOUL.md`，只写四块：**身份**（它是谁、和你的关系、对外怎么自称）、**语气**（中文为主？句长？用不用表情）、**优先级**（诚实说“不确定”优先于猜答案，隐私优先于热情）、**硬边界**（未经确认不主动给 X 发消息、不讨论 Y、不触碰 Z 工具）。
2. **写行为，不写形容词**。“回复前先核对收件人”可执行；“要谨慎”不可执行。
3. **控制篇幅**：50–80 行以内。SOUL.md 每轮都占上下文，10 KB 的“灵魂”模型会自己跳读。
4. **边界做双保险**：prompt 里的禁令是软约束，真正的边界放到工具权限层——不给 shell、发送类操作加确认门、sandbox 限制可写目录。
5. **用 git 管 workspace**：每次翻车修一条规则，commit message 直接写事故本身，几个月后就是一份行为演化史。

## 踩坑点

- **冲突规则不标优先级**，模型每次随机站队。显式写“冲突时以硬边界为准”。
- **把密钥、通讯录写进 SOUL.md**。它可能被引用进回复，秘密只放环境变量。
- **规则语言和对话语言不一致**：规则用英文、日常全中文，语义有偏移，规则要跟主语言一致。
- **禁令堆太多**，Agent 开始过度拒答。定期删掉从没触发过的规则。
- **把它当安全边界**。SOUL.md 是提示词级约束，挡不住 prompt injection，硬边界必须落在权限层。

## 可复用建议

- 起步模板五段：身份 / 语气 / 优先级 / 硬边界 / 已知翻车记录。
- **事故驱动迭代**：Agent 每犯一次错，回来加或改一条，比一次性憋一份大而全有效得多。
- 职责分清：SOUL.md 管“是谁、不做什么”，AGENTS.md 管“怎么做”，别混着写。
- 换模型后，重跑几段老对话样本，验证人设有没有漂。

## 总结

SOUL.md 的价值不在“人设有趣”，而在把不可预期的行为收敛成一份可维护的配置。把它当成需要长期维护的 config 文件来对待，每次事故回写一条，两三周后你会发现 Agent 稳定得像换了一个人——这次是好的那种。
