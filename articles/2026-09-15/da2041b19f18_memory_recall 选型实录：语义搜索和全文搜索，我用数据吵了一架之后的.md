## 背景

Agent 的 `memory_recall` 大概是最容易被敷衍过去的组件：能查到就行。但在实际跑自动化的过程中，召回质量直接决定 Agent 是"记得上次的决定"还是"每次重新犯一遍错"。我们的记忆库条目很杂：用户偏好、项目决策、排障记录、口头约定，单条通常只有一两句话。

检索层摆着两条路：**语义搜索**（embedding + 向量相似度）和**全文搜索**（FTS/BM25 关键词匹配）。团队里两边都有拥趸，于是干脆各跑一套，用真实查询对拍。

## 问题

各自单独用，失败模式互补且都很刺眼：

- 纯语义：查 `ERR_5023` 这类精确错误码、模块名、版本号，embedding 把它们糊成一团相似度，排障记录基本召回不了。
- 纯全文：用户问"上次拍板的方案"，记忆里存的是"最终决定采用方案 B"，字面不重叠，直接空手而归。

结论先行：**这不是二选一的问题，是分层融合的问题**。但融合之前，两层各自得先能用。

## 做法

1. **盘点语料**：导出全部记忆条目，粗分四类：决策记录、用户偏好、事实性备忘、带标识符的排障记录。排障记录是全文检索的主战场。
2. **搭全文层**：SQLite FTS5。注意默认 tokenizer 对中文几乎是废的（后面踩坑详述），换 trigram 或先做分词预处理再入库。
3. **搭语义层**：本地跑一个中文 embedding 模型，一条记忆 = 一个 chunk（条目太短，别切）。向量旁边存元数据：时间戳、来源会话、项目标签。
4. **双路融合**：两路各取 top-20，用 RRF（倒数排名融合）合并，取最终 top-5~8，叠一个时间衰减因子压旧记忆。
5. **建评测集**：从真实会话里攒了 40 条查询，人工标出应命中的条目，跑 hit@5。没有这一步，后面全靠感觉。

## 踩坑点

- **FTS5 默认分词器把整句中文当一个 token**，全文检索形同虚设。这是最大的坑，且报错不会提示你，只会表现为"查不到"。
- **短文本的向量距离不稳定**。一条"偏好深色主题"和长篇排障记录混在一个库里，相似度排序会被长度分布带偏。对策：检索前对查询和条目做一致的归一化，或给短条目补上下文再 embed。
- **别调相似度阈值，调排名**。embedding 的分数尺度跟模型强绑定，换模型全部作废；RRF 用的是排名，跨模型稳定得多。
- **旧决策会压过新决策**。项目方向改过三次，语义检索会把三条都拉出来且旧的排前面。必须有时间衰减或显式失效标记。
- **远端 embedding API 在 recall 高频路径上不可接受**，单次几十毫秒的本地推理可以，走网络就影响主流程响应。

## 可复用建议

- **默认方案就是 hybrid + RRF**，单独吹任何一边都是没跑过评测集。
- 查询预分类很便宜且有效：包含错误码/版本号/路径的查询加权全文路，自然语言问句加权语义路。
- 元数据（项目、时间段）放在打分之前做硬过滤，别指望相似度自己分辨。
- recall 未命中的查询打个日志，每周翻一次，就是天然的新评测集——评测集不是一次性工程。

## 总结

语义搜索解决"换个说法还记得"，全文搜索解决"精确标识符一击即中"，失败模式恰好互补。工程答案不性感：两层索引 + RRF 融合 + 元数据过滤 + 一个 40 条的评测集。额外成本主要在中文分词那一晚上和一份向量索引，换来的召回提升是可量化的。先建评测集，再做选型，顺序别反。
