# Agent 记忆系统设计：怎么让 AI 助手真正记住你的偏好

## 背景

模型本身是无状态的。每次会话结束，上下文清空，你昨天说的"提交信息用中文、测试文件放 `tests/` 下"今天就归零。对偶尔聊天无所谓，但对 OpenClaw 这类把 Agent 当长期协作者跑任务的场景，反复声明偏好既浪费 token 也消耗耐心。

社区里常见两条捷径：把所有偏好塞进 system prompt，或者把完整会话日志存下来。前者在偏好超过十几条后开始互相冲突、挤占上下文；后者本质是存储不是记忆，噪音太大，检索出来的东西经常帮倒忙。

## 核心问题

记忆系统的真正难点不是"存"，而是三件事：

1. **写什么**：不是所有对话内容都值得记，误记比漏记危害更大；
2. **怎么读**：一次会话能注入的记忆有限，排名和作用域必须准；
3. **怎么改**：偏好会变，过时记忆必须有出口。

## 我目前的做法

**分层存储。** 把记忆拆成三类：

- **Profile**：稳定的用户偏好（代码风格、回复语言、常用工具），量小、低频更新；
- **Episodic**：任务级的事实（某个项目的部署命令、踩过的坑），带项目 scope；
- **Working**：当次会话的临时状态，不落盘。

**结构化存储。** 用本地文件（JSON 或 Markdown 都行），每条记忆带元数据：

```json
{
  "id": "pref-014",
  "scope": "project:api-server",
  "content": "commit message 使用中文，格式为 type: 描述",
  "confidence": 0.9,
  "hits": 12,
  "updated_at": "2025-06-01"
}
```

**写入走过滤。** 每次会话结束后跑一次提取，规则从严：只收录用户的**明确指令**，或同一模式**重复出现三次以上**的行为。新增记忆先进入待确认区，和已有条目冲突时标记出来而不是直接覆盖。宁可漏一条，不要存错一条。

**读取做排名。** 会话启动时按 scope 匹配（项目级优先于全局）+ `updated_at` 新鲜度 + `hits` 使用频率，取 Top 10 注入 system prompt。超出的不硬塞——记忆多了说明该做合并压缩了。

**留修正通道。** 用户一句"以后别这样"要能触发更新或删除，这是整个系统最重要的一个工具调用。

## 踩坑点

- **一次性指令被固化。** 用户随口说"这次先跳过测试"，被提取成"该用户不喜欢跑测试"。提取 prompt 里必须明确排除临时性、条件性表述。
- **Scope 泄漏。** 某个项目的偏好混进全局，污染所有会话。scope 校验要放在写入路径上，不能只靠读取时过滤。
- **无限膨胀。** 没有上限的记忆文件三个月后变成小作文。给单用户设 50~100 条硬上限，触发后做合并，冷记忆降权或归档。
- **冲突记忆导致行为漂移。** 两条矛盾的偏好同时注入，Agent 行为时对时错，极难排查。写入时检测冲突、读取时只留最新，二选一执行。
- **不可审计。** 记忆一旦变成黑盒，用户只能整段清空。所有记忆必须是用户能直接打开看的纯文本文件。

## 可复用建议

1. **存储用 plain file + git 管理**，可 diff、可回滚、可审计，别急着上向量库；
2. **每条记忆必带 `confidence` 和 `hits`**，这是后续做淘汰和排名的基础；
3. **用 MCP 把记忆封装成 `memory_read / memory_write / memory_search` 三个工具**，任何接入的 Agent 都能复用，不用各自实现；
4. **先控制规模再谈智能**：50 条以内的结构化记忆，效果往往好于几千条的语义检索；
5. **给用户一个 `memory list` 类命令**，随时看 Agent 记住了什么，这是建立信任的关键。

## 总结

Agent 记忆不是"让模型更聪明"，而是一个工程问题：**写入端从严过滤，读取端做 scope + 排名，存储端保持透明可编辑**。三个环节里任何一环偷懒，系统都会在几周后变成负债。先用最朴素的文件方案跑起来，等真实使用数据告诉你瓶颈在哪，再考虑引入向量检索或更复杂的淘汰策略。
