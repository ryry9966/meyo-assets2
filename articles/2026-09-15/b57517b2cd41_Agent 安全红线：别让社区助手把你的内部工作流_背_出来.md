## 背景

社区里跑 Agent 的人越来越多：接 MCP 工具、挂内部文档做 RAG、自动答疑、定时发频道摘要。效率提升是真实的，但一个被反复验证的事实是——**Agent 不会区分"该说的"和"知道就能说的"**。只要检索范围里混进一份内部运维手册，它就可能在公开频道里复述其中一段，而且语气看起来毫无破绽。

## 问题：三条常见泄露路径

1. **上下文混用**：同一个 Agent 既答社区问题又跑内部自动化，历史消息和工具返回互相污染，"内部知识"顺着对话漏出来。
2. **检索越权**：RAG 索引了整个目录，里面混着排班表、密钥占位符、未公开的路线图。模型只是如实引用。
3. **输出无闸门**：Agent 有直接发帖权限，回复不经人工确认，被诱导（有意或无意）贴出 stack trace、内部端点，甚至系统提示词本身。

Prompt injection 值得单独强调：MCP 工具返回的内容、抓取的网页、用户粘贴的文件，**都是不可信输入**。攻击者不需要"黑"你，只要让 Agent 把敏感内容"引用"出来就赢了。

## 做法：按这个顺序落地

1. **先做资产分级**。给文档打可见性标签（public / member / internal），在检索层过滤。提示词里写"不要泄露内部信息"是请求，过滤器才是约束。
2. **拆分上下文**。对外答疑和内部自动化用两个独立 Agent / 会话 / 凭据，MCP server 分开部署，scope 各发各的、只给最小权限。别让一个进程同时握着"公开的嘴"和"内部的钥匙"。
3. **收紧工具权限**。文件系统只读、目录白名单、shell 默认禁用；发帖、删数据、外呼这类高危工具一律要求人工确认。
4. **输出侧加防线**。对出站内容跑规则：密钥格式（`sk-`、JWT 形态等）、内部域名/路径、异常长的报错堆栈，命中即拦截并要求重写。
5. **出站写操作走审核**。Agent 起草，人点发送。自动化摘要类任务先在私有频道试运行一到两周。
6. **留审计日志**。记录 Agent 读了什么、调了什么工具、输出了什么。出事能回溯，平时也能发现"它怎么读到了这个文件"。

## 踩坑点

- 把密钥写进系统提示词，以为"藏在提示词里就不算泄露"——系统提示词恰恰是最容易被诱导吐出的内容之一。
- 测试只走正常路径。真实注入往往藏在用户粘贴的报错日志、外部网页、第三方工具的返回值里。
- 做 RAG 时顺手全量索引目录，某天有人丢进去一个含真实 token 的 `.env`，之后每次问答都在帮它"复习"。
- 对外 Agent 的对话记录公开可查，等于把你的检索语料间接公开。
- 只靠关键词黑名单当防线，绕过方式一抓一把。黑名单只能兜底，替代不了前面的层。

## 可复用建议

- 一句话判断标准：**如果一个 Agent 的输出你不敢直接贴到公网，它就不该有公网写权限。**
- 接入新工具先问三个问题：它能读什么？能写什么？坏掉时最坏泄什么？
- 可见性过滤做在检索层，出站审核做在发布层，两层都不依赖提示词自觉。
- 定期做一次"红队对话"：让同事用各种话术套内部信息，成功的套路整理成回归用例。

## 总结

Agent 安全不是给模型立规矩，而是给系统立边界。提示词会忘、会被绕；权限、过滤、审核、日志这四样才是真的红线。社区环境天然混杂可信与不可信输入，把 Agent 当成一个权限被严格约束的实习生来管理，基本不会错。
