## 背景

大多数 Agent 演示停在"能聊"，但落地价值在"能做"：查工单、拉报表、触发部署。OpenClaw 对接外部服务的思路很直接——把服务抽象成工具，模型按 schema 发起调用，框架负责传输与鉴权。真正花时间的不是"接线"，而是让这条链路在生产环境里稳定。

## 问题

跑通第一个 demo 之后，不稳定会集中出现：

- 模型选错工具，或在没有合适工具时硬编参数；
- 接口返回全量 JSON，几轮对话就把上下文撑爆；
- 写操作遇到超时自动重试，结果重复建单；
- 密钥图省事写进配置明文，随日志一起被带走。

每一个都不难修，但每一个都真实消耗过排查时间。

## 做法与步骤

**1. 盘点服务，先分读写。** 只读接口（查询、搜索）先接，写操作（创建、删除）后接且必须走确认。这一步决定后面的灰度节奏。

**2. 选对接路径。** 优先级：现成 MCP server > 自己封装 skill/插件 > 通用 HTTP 工具兜底。现成的能省掉协议细节，但用之前看一眼它的鉴权方式和返回结构是否干净。

**3. 认真写工具定义。** 名字用动词短语；描述写清"什么时候用、什么时候不该用"，最好给一个反例；参数尽量加 enum、default 和 required。工具定义就是给模型的契约，写得越含糊，行为越随机。

**4. 鉴权与密钥。** 凭证放环境变量或密钥文件，绝不进对话和 prompt。模型只需要知道"调用会带上凭证"，不需要看到凭证本身。

**5. 加防御层。** 每个调用设超时；只有幂等操作才允许自动重试；返回结果做裁剪——字段白名单加分页，必要时返回摘要加引用，模型要细节再二次拉取。

**6. 灰度验证。** 先用 dry-run 把调用意图打印出来人工确认，同时把每次工具调用的入参、耗时、返回码落日志。日志是后面排查的唯一抓手。

## 踩坑点

- **描述含糊的代价是隐性的。** 两个工具都能"查数据"，模型就轮流试，浪费轮次还可能触发限流。合并或改名，别留歧义。
- **非幂等写操作 + 自动重试 = 事故。** 重试前确认接口支持幂等键，或干脆关掉重试留给人工。
- **返回体不加裁剪，上下文先死。** 一次 50KB 的 JSON 够废掉一整段对话。
- **工具改名或下线后不清理注册表，会静默失败。** 模型拿到"工具不存在"却继续绕路，表现很像幻觉，其实是对接腐化。
- **把异常堆栈直接抛给模型没用。** 返回"可行动"的错误：发生了什么、哪些参数可能有问题、下一步能试什么。

## 可复用建议

- 只读先行，写操作永远过确认门；
- 一个工具只做一件事，组合逻辑放在上层流程里；
- 外部调用统一走一层封装，超时、重试、日志集中管理，别散在各个 skill 里；
- 把工具调用日志当成一等功能，定期回看选错率和失败率，它们是对接质量的直接指标。

## 总结

Agent 与外部服务的握手，本质是契约设计：工具定义是给模型的契约，超时重试是给网络的契约，鉴权是给安全的契约。OpenClaw 提供了挂载点，但契约质量取决于写定义的那个人。用"每个工具都是一个小型对外 API"的态度去做，链路自然就稳了。
