# 背景

我们团队每天要发一份运维加业务的日报，里面大部分数字来自几台机器的日志、Agent 任务执行记录和若干 webhook 落盘事件。此前是人工整理，耗时 40 分钟左右，且口径靠人脑记、请假就断更。后来用 OpenClaw 搭了一条流水线，跑了两个多月基本稳定，这里把设计和踩过的坑记录一下。

# 问题

原始输入有三类：服务运行日志（JSONL 按天滚动）、Agent 任务执行结果、第三方 webhook 原始事件。痛点不在“没有数据”，而在于：

1. 格式不统一，字段名随上游版本漂移；
2. 指标口径不稳定，昨天的“请求数”和今天未必是同一个东西；
3. 让 LLM 直接读原始日志写日报，token 成本高，数字还会编。

# 做法

核心思路一句话：**数字用代码算，文字交给模型写。** 流水线分五段：

1. **落盘归一**。所有来源统一转成中间格式 JSONL：`{ts, source, kind, level, payload}`。采集脚本只做格式转换，不做业务判断。
2. **聚合**。一个纯 Python 脚本按天扫中间文件，产出 `metrics.json`：总数、错误率、Top N、与前一日差值。全部确定性计算，可单测。
3. **叙述**。把 `metrics.json` 喂给 Agent，配合版本化的 prompt 模板，只负责生成趋势描述、异常归因提示、待办建议。模板里明确约束：不得输出输入数据之外的数字。
4. **渲染与投递**。Markdown 模板填充后推送 IM webhook，同时把当天的 md 和 `metrics.json` 按日期归档。
5. **调度与兜底**。OpenClaw 定时任务触发，失败时推送“流水线失败 + 原因”，绝不静默。

# 踩坑点

- **时区**。日志按 UTC 存储，“一天”的边界按本地时区切。第一版直接按文件名日期聚合，导致早上 8 点前的日志被划进前一天。
- **别让模型直接读日志**。试过把当天原始 JSONL 整段丢给 Agent，几万 token 不说，产出的数字存在幻觉。先聚合再喂是关键。
- **格式漂移无感知**。上游改了字段名，聚合脚本不报错，指标只是悄悄变 0。后来在聚合阶段加 `parse_fail` 计数，并把“解析失败条数”作为指标写进日报——日报自己监控自己。
- **重复投递**。手动补跑会发两遍。改成幂等：输出路径按日期，投递前查当日 manifest，重跑只覆盖不重发。
- **空数据静默**。某天上游没日志，日报照发但章节空白，没人发现。现在空聚合走告警分支。

# 可复用建议

- **先定中间 schema，再谈自动化**。schema 稳了，采集端随便换，下游不动。
- **分层独立**：采集 / 聚合 / 叙述 / 投递各自可单独重跑，排障能定位到段。
- **prompt 模板当代码管**：进 git、改动走 review，避免某天日报语气突变没人知道为什么。
- **存快照**：每天的 `metrics.json` 归档，周报、环比、回溯都靠它，成本几乎为零。
- **失败要可见**：自动化最怕的不是报错，是没人知道它没跑。

# 总结

这条流水线的核心经验是边界划分：确定性的事交给代码，语言表达交给模型，两者之间用一个固定的 JSON 契约衔接。两个多月下来，日报从“有人写”变成“有人看”，人力投入从 40 分钟降到 5 分钟检查。如果你也在用 OpenClaw 做定时任务，建议从最小的一类日志开始接入，先跑通再扩源。
