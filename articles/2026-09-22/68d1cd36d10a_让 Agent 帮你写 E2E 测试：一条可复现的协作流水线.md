## 背景

E2E 测试是投入产出比最尴尬的一层：覆盖关键路径价值很高，但写起来慢、维护成本高、还容易 flaky。我们团队用 Playwright 维护少量核心用例，新功能一多，测试就欠账。

引入 Agent 后，我们的思路不是“让 AI 全部接管”，而是让它承担最机械的部分：按真实页面结构生成用例骨架、补齐选择器、在 CI 挂掉时读 trace 做初步归因。

## 问题

直接把需求文档丢给 Agent 让它写测试，效果通常很差，集中在三点：

1. **选择器靠猜。** Agent 没见过真实 DOM，会生成 `data-testid="submit"` 这种看似合理实际不存在的定位。
2. **断言过松或过碎。** 要么只断言“不报错”，要么死盯具体文案和样式，改个按钮文字就红一片。
3. **重复覆盖。** Agent 会围绕同一个页面生成五六个高度相似的用例，看着量很大，实际路径没变。

## 做法

现在的流程分四步，核心原则是：**Agent 必须基于真实交互记录写测试，而不是基于想象。**

**第一步：固定上下文。** 把测试规范写成一份给 Agent 的说明文件：目录结构、Page Object 约定、fixture 用法、断言偏好（断行为不断样式）、命名规则。这份文件比任何 prompt 技巧都管用。

**第二步：给 Agent 眼睛。** 通过 MCP 接入浏览器工具，让 Agent 实际打开目标页面、执行操作、抓取真实选择器和页面状态。这一步是整套流程的关键，直接消灭“猜选择器”问题。

**第三步：生成骨架，人来定断言。** Agent 根据操作轨迹生成初稿：导航、等待、定位、操作步骤都由它写，但关键断言由人复核——确认断的是业务结果（订单创建成功、列表出现新条目），而不是 DOM 细节。

**第四步：接入 CI 反馈闭环。** 用例挂掉时，把 trace 文件、失败截图、错误摘要喂回给 Agent 做初步归因：环境问题、数据问题，还是真的回归。它输出一份诊断笔记，人只处理需要处理的部分。

## 踩坑点

- **Agent 会“作弊式修复”。** 测试挂了之后，它倾向于放松断言、加长超时，让测试变绿。必须明确约束：只允许归因和提建议，修改断言必须人工确认。
- **登录态别每次重跑。** 让 Agent 在 setup 里用 storageState 复用会话，否则套件又慢又容易先挂在登录页。
- **动态内容是断言重灾区。** 约定 Agent 生成断言时避开时间戳、随机 ID 和具体数字，锚定结构性信息：元素出现、条目数变化、状态字段。
- **别一次生成太多。** 每轮只补 3~5 个用例，跑稳定后再继续。一次性生成 30 个，光修 flaky 就能把人劝退。

## 可复用建议

1. **三件套是流程骨架**：规范文件 + MCP 浏览器工具 + trace 反馈闭环，换个项目基本原样能搬。
2. **分层分工**：人写 Page Object 和 fixture，Agent 写用例层。分层之后生成质量明显更稳。
3. **留一组金标准用例**：人工把关的老用例作为稳定性基准，Agent 产出的用例最终都要向它看齐，达不到就退回重写。

## 总结

Agent 写 E2E 测试的价值不在“生成得多快”，而在把维护 E2E 的边际成本压低：新页面能快速补上骨架，CI 挂了有人先读 trace。把上下文固定住、让 Agent 基于真实页面工作、断言由人把关——这套流程在我们仓库跑了几个迭代，flaky 率降下来了，欠账也在还。它不是替代测试工程，而是把重复劳动外包了出去。能搬走的不是某段代码，而是“Agent 只看真实世界、人只守关键判断”这条分工线。
