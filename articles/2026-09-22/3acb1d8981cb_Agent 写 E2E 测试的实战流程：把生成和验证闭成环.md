## 背景

E2E 测试大概是自动化里投入产出比最难看的一环：用例写得慢、选择器脆弱、页面一改就得跟着改，多数团队只有核心流程有覆盖，剩下靠人肉回归。

LLM Agent 加上浏览器自动化工具链（如 Playwright MCP）成熟之后，“让 AI 参与 E2E”开始变得可落地。最近我在内部项目跑通了一套协作流程，覆盖提升明显，也踩了不少坑，记录如下。

## 问题：直接“让 AI 写测试”为什么不行

最直觉的做法是把页面 URL 或截图丢给模型让它输出用例，实际通常有四类问题：

1. **选择器靠猜**：模型没真的打开页面，写出的 class 和文本路径大概率不存在；
2. **断言是“永真”的**：生成 `toBeVisible()` 这类永远通过的断言，用例看着绿，实际什么都没验；
3. **没有执行反馈**：一次生成几十条，跑挂一半，人工修的成本比手写还高；
4. **环境误操作**：Agent 拿到执行权限后，可能对着预发甚至生产环境跑写操作。

核心矛盾是**生成用例与验证用例脱节**。Agent 协作要解决的就是把这两步闭环。

## 做法：一套可跑通的闭环

**1. 给 Agent 装“手和眼”。** 用 MCP 把浏览器操作接给 Agent（`navigate / click / snapshot`），再配上 `run_tests` 执行 Playwright、`read_trace` 读失败 trace 和截图。关键是后两项——Agent 必须能亲眼看到自己写的东西挂掉的样子。

**2. 一次只交付一个用户流。** 不要说“把登录、下单全写了”，而是：

> 覆盖“访客加入购物车后用测试账号结算成功”这条路径，统一用 data-testid，断言订单号出现且跳转结果页。

约束越具体质量越高，跑通一条再加下一条。

**3. 让 Agent 自己跑到绿。** “运行—读失败—修改”的循环交给 Agent，人工只设上限（比如 5 轮）。实践中多数用例 2-3 轮收敛；收敛不了的，往往暴露的是测试环境本身的问题（慢接口、脏数据），这本身就有价值。

**4. 人工做最后审查。** Agent 说“全绿”不等于可合入，重点查三件事：断言是否真的在验业务结果、有没有隐式 sleep、失败分支是否覆盖。审完再进 CI。

## 踩坑点

- **别让它滥用 `networkidle`**：Agent 极爱写 `waitForLoadState('networkidle')`，遇长轮询页面必超时，统一改成断言具体元素；
- **快照不等于断言**：它倾向于“截图确认没问题”，prompt 里必须强制输出显式 expect；
- **上下文膨胀**：单会话生成超过 5-6 条用例后质量明显下滑，及时开新会话；
- **权限收窄**：测试账号单独建、数据库固定 seed，避免写出依赖真实用户数据的用例；
- **限定改动范围**：明确只许写 spec 文件，防止它顺手“重构”你的 page object。

## 可复用建议

1. 把第 2、3 步的指令固化成团队 prompt 模板，Agent 输出结构会稳定很多；
2. 规范 `data-testid` 是前置工程，比任何 prompt 技巧都管用；
3. 失败 trace 永远回喂给 Agent，而不是自己看一眼改一版；
4. 每周跑一次“只读巡检”，让 Agent 对存量用例标记脆弱点，做预防性维护。

## 总结

Agent 写 E2E 的价值不在“零人力”，而在于把最枯燥的初稿和调试循环自动化，人退到设计与审查的位置上。**生成→执行→读失败→修复**的闭环是整套方法的骨架，缺了执行反馈，生成质量无从谈起。先从一条核心路径试起，比一次性铺开现实得多。
