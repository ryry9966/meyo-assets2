## 背景

聊 Agent 记忆的内容很多，大多在讲 agent 怎么“记住你”——对话历史、向量库、MEMORY.md。但很少有人讨论反方向：你怎么主动、结构化地告诉 agent“我是谁”。OpenClaw 的 workspace 里预留了 USER.md 这个文件，不少用户从来没认真写过它，或者写了两行就丢在那。这可能是一份性价比被严重低估的配置。

## 问题

没有 USER.md 时，通常会发生这些事：

- 每个新会话，agent 对你的认知归零，全靠你临时口头补充；
- 同一件事反复纠正：“回复用中文”“别帮我加注释”“我用 pnpm 不是 npm”；
- 偏好散落在各个项目的 AGENTS.md 里，版本不一，互相矛盾；
- 你以为它“应该知道”，它其实每次都在猜。

Agent 没有常识意义上的“了解你”，它只有上下文。你不写进去，它就只能从历史对话里碰运气。

## 做法

USER.md 放在 workspace 根目录，会话启动时随 workspace 上下文一起注入。建议控制在 40–60 行，分五块写：

1. **身份与环境**：角色（后端 / 运维 / 学生）、主要语言、时区、常用设备；
2. **技术栈事实**：操作系统、包管理器、主力语言和版本、部署环境。写事实，不写愿望；
3. **协作偏好**：回复语言、代码风格、解释深度（要不要讲原理）；
4. **禁区**：不自动 git push、不替你做采购决定、哪些目录不许动；
5. **上下文指针**：只放一句“项目细节见 ~/work/xxx/AGENTS.md”，别展开。

写完做一次验证：新开会话，问 agent“根据你对我的了解，我平时怎么布置任务？”看它复述的和你写的是否一致。

## 踩坑点

- **写太长**。USER.md 每轮都占上下文，见过 300 行的自我介绍，token 花费惊人，关键约束反而被淹没。原则：一行一条，可删的删。
- **写成简历**。“五年 Java 经验”对 agent 没用；“注释用中文、测试用 vitest”才有用。写约束，不写履历。
- **放易变信息**。本周进度、当前 bug 状态应进 MEMORY.md 或每日笔记。USER.md 只放季度级稳定内容，否则一个月后全是过期误导。
- **放敏感信息**。住址、证件号、API key 别写。它是明文文件，且每次会话都会被注入。
- **层级冲突**。USER.md 说中文回复，某项目 AGENTS.md 要求英文产出，agent 会随机选一个。明确约定：项目级覆盖用户级，并且两处都写明白。

## 可复用建议

- **让 agent 参与维护**：偶尔问它“基于最近对话，USER.md 哪些条目该增删？”它对你纠正行为的观察往往比你的自我记忆准。
- **每月 review 一次**，把它当 onboarding 文档对待，而不是写完归档的一次性产物。
- **多设备 / 多 agent 场景**，把 USER.md 收进 dotfiles 仓库，改一处全局生效。
- **别抄模板**：从“本周被 agent 惹恼的三件事”倒推条目，那是最真实的信号源。

## 总结

USER.md 的本质，是把“调教 agent”从无数次口头纠正，压缩成一次工程化的静态配置。它不神秘，二十分钟能写出第一版，但需要像代码一样持续迭代。你写得越准，agent 猜得越少——这大概是当前成本最低、收益最确定的一项 agent 优化。
