## 背景

Agent 用得越久，越会发现一个问题：它的"人格"散落在各处。system prompt 里写了一半，插件配置里藏了几句，某个自动化脚本的说明里又补了一段。时间一长，没人说得清这个 agent 到底被定义成了什么样。

OpenClaw 社区这半年实践下来，逐渐收敛出一个简单做法：把身份抽成一个独立的 `IDENTITY.md`，放在工作区根目录，用 git 管理，随代码一起演进。它不是什么新协议，就是一个被认真对待的 Markdown 文件。

## 问题

没有集中身份文件时，常见症状有四种：

1. **改动不可追溯**。prompt 直接改在配置里，三个月后没人记得当初为什么加那句"回复保持克制"。
2. **多入口不一致**。同一个 agent 从 CLI、webhook、定时任务进来，加载的身份片段不同，行为漂移。
3. **身份是死的**。想调整语气或边界，得重启、重部署，于是大家干脆不改。
4. **协作缺评审**。prompt 是团队资产，但从来没走过 code review。

## 做法与步骤

我们的最小实践分四步：

**第一步：建文件。** 在工作区根目录放 `IDENTITY.md`，建议五个区块：

- 定位：一两句话，这个 agent 是干什么的
- 语气与边界：克制/直接，不说什么
- 能力声明：能做什么、明确不能做什么
- 行为准则：遇到不确定时，先确认还是先尝试
- 演进记录：changelog，每次改动一行

**第二步：接入加载链。** 在 agent 启动流程里读取该文件注入上下文。如果用 MCP，可以做一个极简的 identity server，只暴露一个 `get_identity` 工具，让任何客户端按需拉取，避免各处硬拷贝。

**第三步：进 git，走 PR。** 身份变更和代码变更一样提评审，PR 描述里写清"为什么改"，这就是最好的决策日志。

**第四步：定期回收。** 每周翻一次对话日志，把 agent 表现不好的场景提炼成一句修正，写回文件。身份由此开始真正"进化"。

## 踩坑点

- **写太长**。超过一屏基本等于没写，长文档会稀释关键约束的权重，我们控制在 40 行以内。
- **规则堆砌代替身份描述**。二十条"必须/禁止"不如一段清晰的自述，模型对描述性身份的遵循更稳定。
- **两处定义打架**。旧的硬编码 system prompt 记得删干净，否则冲突时行为随机，排查很痛苦。
- **改坏了无法回滚**。changelog 别偷懒，一行日期加一句动机，回滚时救命。
- **敏感信息入库**。身份文件会被各端加载，别写 key 和内网地址。

## 可复用建议

- **做分层结构**：核心身份保持稳定，场景层（面向客服、面向开发）单独一个区块可替换。
- **改动前跑回放**：挑十个典型对话做固定用例，对比改动前后表现，别凭感觉上线。
- **多 agent 继承**：子 agent 继承核心身份区块，只覆写场景层，保证团队口吻一致。

## 总结

IDENTITY.md 的价值不在文件本身，而在它把"agent 是谁"从隐性的、散落的口头约定，变成显性的、版本化的工程资产。改身份像改代码一样有评审、有回滚、有演进记录——这才是"可进化"的真正含义。从一个 20 行的文件开始就够了。
