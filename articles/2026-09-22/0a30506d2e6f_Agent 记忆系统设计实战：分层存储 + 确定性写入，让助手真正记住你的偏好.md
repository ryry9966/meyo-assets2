## 背景

Agent 单次会话表现再好，关掉窗口就清零。代码风格、回复语言、常用部署方式这类偏好，每次都要重新交代。在 OpenClaw 这类可插拔框架里，记忆通常走两条路：往 system prompt 塞一个不断增长的 memory 文件，或接向量库做语义检索。两条路我都踩过坑，最后收敛出一套分层方案，在这里完整拆解。

## 问题

实践里最常见的四个失败模式：

1. **记忆文件无限膨胀**：什么都往里写，一个月后几千行，每轮全量注入，token 开销大，且多数记忆与当前任务无关。
2. **写入不可控**：靠模型"觉得该记就记"，同一偏好反复出现、措辞不一，还会互相矛盾。
3. **检索相似 ≠ 相关**：向量召回的"记忆"常常只是字面相似，注入一堆噪声反而干扰行为。
4. **没有遗忘机制**：用户半年前说"不要写测试"，如今早改了主意，过期偏好仍在生效。

## 做法

核心思路八个字：**分类存储、确定性写入**，再加分层读取和显式遗忘。

**第一步，按变化频率分三层：**

- **稳定偏好**（语言、代码风格、常用工具链）：存成一份 YAML 键值对，每条带 `updated_at` 和 `source` 字段；
- **项目事实**（构建命令、部署目标）：按项目命名空间分文件；
- **会话痕迹**（临时决定、一次性上下文）：进向量库，带 TTL，默认 30 天过期。

**第二步，写入走工具，不走模型自觉。** 在任务结束或用户明确表态时触发一个"蒸馏"步骤：独立回答"这轮对话里用户是否表达了持久偏好？"，有则输出结构化记录，按 key 去重后写入——相同 key 直接覆盖旧值并保留版本历史，而不是追加。用 MCP 把它暴露成 memory 工具，Agent 只能通过工具调用写入，禁止自由改文件。

**第三步，读取分两层。** 稳定偏好层控制在 300 token 以内，每次会话整体注入 system prompt——文件足够小时，全量注入比检索可靠。会话痕迹和项目层只在语义相关时检索，限制 top-3，召回后先按时间戳和来源做一轮过滤。

**第四步，给用户一扇窗。** 做一个 `/memory` 命令，随时查看、编辑、删除记忆。记忆对用户透明可修正，是系统能长期用下去的前提。

## 踩坑点

- **冲突处理要早做**：两条偏好打架时按 `updated_at` 新者胜，旧值进版本历史，否则用户改主意后想反悔都找不到原文。
- **敏感信息不进记忆**：API key、密码、私人细节一律拒收，蒸馏步骤里加一条正则黑名单，成本低收益大。
- **警惕过度泛化**：用户说过一次"这个项目不用测试"，Agent 可能在所有项目里都不写。给每条记忆加 `scope` 字段（global / project / session），读取时只注入匹配范围。
- **评估别靠感觉**：攒十几段历史会话做回放，统计 Agent 输出是否真正体现了对应偏好，长期没被用到的记忆降级或清理。

## 可复用建议

- 起步别上向量库：一份 git 管理的 YAML + 全量注入，能覆盖八成偏好记忆需求。
- 每条记忆四元组：`key / value / updated_at / source`，缺一个将来都是坑。
- 写入必须走工具调用，模型不直接碰文件。
- 遗忘与记忆同等重要：TTL、去重、版本历史，三件套缺一不可。

## 总结

Agent 记忆本质是数据工程问题，不是 prompt 技巧。分类存储控制规模，工具化写入保证一致性，分层读取控制成本，显式遗忘避免过期偏好作祟。先把最简单的 YAML 方案跑通跑稳，再考虑向量检索和记忆压缩——对多数个人和团队场景，这条路够走很久了。
