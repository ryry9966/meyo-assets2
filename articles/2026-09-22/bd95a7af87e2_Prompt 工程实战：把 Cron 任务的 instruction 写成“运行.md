## 背景

OpenClaw 的 cron 任务本质上是无人值守的 agent 运行：到点唤醒、执行 instruction、把结果推到指定渠道，然后结束。很多人写 cron 指令时沿用聊天习惯——“每天早上帮我看一下有什么重要的更新”。在交互对话里这样写没问题，因为人随时能追问和纠偏；但定时任务没有人在场，写法必须换一套。

## 问题

按聊天习惯写的 cron instruction，常见失败模式有三种：

1. **语义漂移**。“重要的更新”由 agent 自行解释，每次运行理解不一样，输出范围忽大忽小。
2. **输出失控**。没定义发到哪、什么格式、多长，结果有时一句话，有时刷屏三屏。
3. **静默失败**。工具超时、数据为空时指令没给出口，agent 要么编造内容，要么每次发一条毫无信息量的“今天没有内容”。

根因是同一个：聊天 prompt 依赖人在场补全上下文，cron instruction 必须自带完整契约。

## 做法：五段式结构

我把 cron instruction 拆成五段来写，每段回答一个问题：

1. **运行语境**——这次是什么运行？开头一句“这是每日 08:00（Asia/Shanghai）的定时运行，任务：晨报摘要”，给 agent 明确锚点，避免它以为还在对话中。
2. **数据源与工具**——用什么做？写明工具名和调用顺序，失败时的降级路径一并写上。
3. **时间与范围**——“今天”是什么？把时区、起止时间钉死，比如“昨日 00:00 至运行时刻”。
4. **输出契约**——结果长什么样？目标渠道、条数上限、字段、排序规则。给一次格式示例，比十个形容词管用。
5. **边界与失败分支**——出问题怎么办？空数据、工具报错、不确定的内容，各给一条明确出口，顺带写清禁止事项。

一个可参考的最小示例：

```text
这是每日 08:00（Asia/Shanghai）的定时运行，任务：晨报摘要。
1. 用 github 工具读取本仓库昨日 00:00 至今的 issue 与 PR，按重要度排序。
2. 输出到 #daily 频道：不超过 5 条，每条一行「标题 — 一句话摘要」，末尾注明总数。
3. 无新条目只回复「今日无更新」，不要罗列旧内容。
4. 工具失败重试一次，仍失败则回复「数据源异常：<原因>」，不要编造。
5. 禁止：修改文件、调用发帖类工具、扩展任务范围。
```

落地步骤建议四步：先当普通消息手动跑通；同一指令连跑三次观察漂移点，把漂移处写死；注入真实失败（断网、清空数据源）验证失败分支；上线后观察一周再收紧。

## 踩坑点

- **“和上次一样”**。cron 每次是独立运行，没有对话记忆。要跨次状态就落文件：指令开头先读工作区里的状态文件，结束时写回“上次处理到的位置”，顺带解决重复推送的幂等问题。
- **一个任务塞多件事**。晨报加周报加备份，范围蔓延后哪个都做不稳。一次运行一个职责，多任务拆成多条 cron。
- **指令里背知识库**。cron 按频率烧 token，把稳定知识放工作区文件，指令里只给路径让 agent 按需读，别把内容全量塞进 instruction。
- **时区错觉**。容器里多半是 UTC，你以为的早上八点不是它以为的八点，指令里显式写时区。

## 可复用建议

把 cron instruction 当“给值班同事的交接文档”来写，而不是聊天消息：背景、输入、输出、异常，四要素齐了才算写完。建议在仓库里维护一个五段式模板，新建任务复制改参数；每月回看一次 cron 的实际输出历史，没人看的任务直接砍掉——无人值守的任务，最贵的不是写错，而是没人发现它一直在错。

## 总结

Cron instruction 的本质，是把“有人在场的对话提示”改写成“无人值守的运行规格”。你多写的不是形容词，而是约束、上限和失败分支。一句话：给人看的 prompt 靠默契，给 cron 的 prompt 靠契约。
