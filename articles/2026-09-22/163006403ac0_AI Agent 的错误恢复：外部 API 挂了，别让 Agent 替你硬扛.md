## 背景

跑过自动化 Agent 的人都有体会：demo 和生产之间隔着的不是模型能力，而是一堆外部依赖。查天气、搜网页、调企业内部接口、甚至 LLM 本身——任何一个 429 或超时，都可能让一条跑了十几步的任务链当场断掉。传统服务挂了返回 500 就完事，Agent 挂掉的方式要难看得多。

## 问题：Agent 的故障模式更糟

同一个 API 故障，在 Agent 场景下会放大成三种事故：

1. **无限重试烧钱**。模型看到报错，本着“再试一次”的精神反复调用，一晚上把配额和账单刷爆。
2. **幻觉式兜底**。拿不到真实数据，模型选择“编一个看起来合理的”，下游任务拿着假数据继续跑，比直接失败危害更大。
3. **半途状态泄漏**。任务链前半段已经写了数据库、发了消息，后半段挂掉，重跑一遍就重复建单、重复扣款。

三个问题的共同根源：恢复逻辑交给了 LLM，而不是代码。

## 做法：把恢复放进 Harness，不放进 Prompt

### 1. 错误先分类，再谈策略

在工具调用层统一捕获异常，分成三类：

- **可重试**：429、5xx、超时、网络抖动；
- **不可重试**：401/403（凭证问题，重试只是刷日志）、400（参数错了，重试结果一样）；
- **内容级失败**：HTTP 200 但 body 是 error 或 schema 不对——这类最容易被漏掉。

### 2. 有界重试：指数退避 + 抖动

可重试错误走代码层的重试：指数退避（1s → 2s → 4s），加随机抖动避免踩踏，上限 3~5 次，同时尊重服务端返回的 Retry-After。关键是**重试决策在代码里，不进模型上下文**——失败信息以结构化摘要喂给模型，避免它自行发挥。

### 3. 熔断而非硬刚

连续 N 次失败后直接熔断：一段时间内对该工具的调用快速失败，而不是排队等超时。冷却结束后放一个探测请求试探恢复。对 Agent 来说熔断还有个好处：失败的 tool call 立刻返回明确的“服务暂不可用”信号，模型可以据此走降级路径而不是干等。

### 4. 降级路径要提前定义

每个关键工具至少想清楚一条退路：备用数据源、带时间戳的缓存（明确标注“这是 2 小时前的数据”），或者干脆诚实上报“这一步失败，任务暂停在 X，已完成的步骤不回滚”。**诚实上报本身就是一种合法的恢复结果**，比编数据强一百倍。

### 5. 写操作加幂等键 + 断点续跑

涉及写入的操作（建单、发消息、支付）必须带幂等键，保证重试和续跑不产生重复副作用。长任务链把每步结果持久化，恢复时从断点继续，已付费的调用不重跑。

## 踩坑点

- **对非幂等接口裸重试**：最常见的重复扣款来源。
- **退避没加抖动**：依赖方恢复的瞬间所有实例一起打过去，二次雪崩。
- **把原始堆栈丢给模型**：模型会拿报错文本自由发挥，重试策略要收敛为结构化消息。
- **只看状态码不看 schema**：200 但内容是错的，脏数据直接进上下文。
- **熔断窗口拍脑袋**：太短等于没熔断，太长会把短暂抖动放大成长时间不可用，按依赖方 SLA 调。

## 可复用建议

1. 写一个统一的 tool wrapper：分类、限次重试、熔断、超时、结构化报错，五件事一处收口，所有 MCP 工具复用。
2. 每个外部依赖配一张“故障卡”：预期错误类型、是否幂等、降级路径、熔断阈值。
3. 用故障注入做测试：mock 出 429 和 500，验证恢复路径真的走得通——没被故障打过的恢复逻辑等于没写。
4. 监控里单独看“工具层错误率”和“重试放大系数”（实际调用数 / 业务调用数），后者飙高说明重试策略失控。

## 总结

外部 API 一定会挂，区别只在于什么时候。Agent 的可靠性不是 prompt 写出来的，而是 harness 里的工程决策：分类、限次、熔断、降级、幂等，五件事做扎实，任务链就能从“一挂全断”变成“挂了也知道怎么走”。最坏情况下，让 Agent 诚实地告诉你它卡在哪，也比让它自信地编一个结果强。
