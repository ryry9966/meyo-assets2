## 背景

大模型本身是无状态的：会话一结束，"偏好"就没了。做过 Agent 的人很快会遇到同一个诉求——"我希望它记得我用 pnpm 不用 npm、提交信息写中文、部署只走 staging"。听起来简单，做对不容易。这篇帖把社区里几个自动化项目实际跑通的记忆层方案整理一下，给一个可以直接抄的最小实现。

## 问题：三种典型失败

1. **全塞 system prompt**：几十条偏好常驻上下文，token 翻倍，且大部分与当前任务无关，反而稀释指令。
2. **只靠会话摘要**：摘要有损压缩，"用户偏好"和"事件细节"混在一起，三五个会话后就找不回来了。
3. **指望模型"自己记住"**：没有显式读写接口，记忆是否存在、何时被使用完全不可观测，出问题没法排查。

## 做法：分层存储 + 显式读写

核心思路是把记忆当数据库设计，而不是当魔法。

**1. 分层**

- 工作记忆：当前会话上下文，不落盘
- 情景记忆：会话摘要 + 关键事件，按时间组织
- 画像记忆（重点）：结构化用户偏好，单独一张表

**2. 最小 Schema**

每条偏好一条记录：`type`（偏好/事实/约束）、`content`（一句话，如"构建工具偏好 pnpm"）、`evidence`（来源会话 ID + 原文引用）、`confidence`（0~1，重复出现越多越高）、`last_used` 与 `created_at`（用于衰减）。

**3. 写入策略**

不要每轮都写。只在两类时机触发提取：用户显式说"以后都……"，或同一信号出现 ≥2 次由模型判重。新条目先与已有记忆做 embedding 相似度比对，>0.85 视为同一条，走更新而非新增。

**4. 读取策略**

检索用混合方式：embedding 召回 + 关键词精确匹配（工具名、路径这类实体，向量检索很不靠谱）。注入数量硬上限 10 条，按 `confidence × 时间衰减` 排序，衰减按"半衰期 30 天"起调。

**5. 冲突处理**

新旧矛盾时不覆盖，把旧条目标记为 `superseded`，保留历史。用户换技术栈很常见，覆盖写会让你丢掉"他曾经是 Ruby 后端"这类仍有价值的背景。

在 OpenClaw 里，这套东西落地为两个 MCP 工具：`memory_write` 和 `memory_search`。读写权限和阈值都在插件层控制，模型只拿结果。

## 踩坑点

- **记忆污染**：一次性请求（"这次先用 yarn"）被当成永久偏好。写入必须带 evidence，回答时能溯源，用户可一键删除。
- **过度注入**：阈值设太松，每轮塞 20 条记忆，主任务质量反而下降。我们实测注入超过 8 条左右，指令遵循率开始掉。
- **embedding 搜不准实体**：`pnpm` 和 `npm` 的向量距离很近，必须叠关键词匹配。
- **只增不改**：没有置信度和冲突机制，三个月后记忆库里全是互相矛盾的条目。

## 可复用建议

- 先做画像记忆（结构化偏好），再做情景记忆，反过来价值密度太低。
- "衰减排序 + 硬上限注入"这两条能解决 80% 的"记了但用不好"。
- 给用户一个 memory 面板：能看、能删、能改。可观测性的优先级高于算法调优。
- 评估用回放：攒 20 组"新会话应召回哪些记忆"的标注 case，改参数就跑一遍，别凭感觉调。

## 总结

记忆系统的本质不是"让模型更聪明"，而是工程问题：明确的 schema、克制的写入、带衰减的读取、可解释的溯源。先用百来行代码把 `memory_write` / `memory_search` 跑通，再谈向量库选型和更花哨的召回策略。欢迎在评论区贴你们的 schema 设计，尤其是冲突处理这块，大家踩的坑可以互相抄作业。
