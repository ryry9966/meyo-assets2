## 背景

大模型本身是无状态的。每次新会话，Agent 对你的了解都归零——你上周明明说过"部署用 pnpm 不用 npm"、"回复尽量简短"，这次它照样给你一大段带 emoji 的长文。想做出"越用越顺手"的助手，记忆层绕不开。

在 OpenClaw 的实践里，这层不该是玄学，而应是一条明确的管线：**提取 → 存储 → 检索 → 更新 → 遗忘**。

## 问题：三种常见错误做法

1. **全量塞进 system prompt**：上下文爆炸，且大部分记忆与当前任务无关，反而稀释注意力。
2. **只存聊天记录原文**：检索时全是流水账，"偏好"被对话噪声淹没。
3. **只加不删**：三个月前的一次性指令（"帮我用调试模式跑一次"）被当成永久偏好反复注入。

核心矛盾不是"存得下"，而是**召回得准、过期得快、冲突能裁决**。

## 做法：五步搭一个能用的记忆层

**1. 分层设计。** 把记忆拆成三类：
- 用户画像：长期稳定偏好（技术栈、沟通风格、默认参数），key-value 存储；
- 情节记忆：具体事件（"上周处理过某服务故障"），向量库存储；
- 工作记忆：当前会话状态，无需持久化。

**2. 提取用结构化 schema，不存原文。** 每条长这样：

```json
{ "key": "deploy.tool", "value": "pnpm", "confidence": 0.9,
  "updated_at": "2025-01-12", "ttl_days": null }
```

会话结束或每 N 轮触发一次提取，让模型只输出候选记忆，置信度低于阈值直接丢弃。

**3. 检索走混合策略。** 画像类直接全量注入（几十条也就几百 token）；情节类按"向量相似度 × 时间衰减"取 top-k。注入用固定分隔的结构块，别混在指令正文里。

**4. 更新要有裁决规则。** 同 key 新值覆盖旧值并保留历史；语义冲突（"喜欢简洁" → "希望详细解释"）标记 supersede，拿不准就问用户一句。绝不纯 append。

**5. 用 MCP 工具暴露，别写死在某个 Agent 里。** 定义 `memory_read` / `memory_write` / `memory_search` 三个工具，接入的 Agent 复用同一份记忆。写操作在工具层做校验（schema、长度、敏感内容），不信任模型发起的写请求。

## 踩坑点

- **提取过猛**：模型倾向于什么都想存。限制每轮最多 2-3 条，且要求"能改变未来行为"才算记忆。
- **会话结束才写库**：进程一崩记忆全丢。改成增量写入，至少每轮 flush 一次。
- **缺时间戳**：没有 `updated_at` 就做不了衰减和冲突裁决，这是最常见的事故来源。
- **注入格式随意**：记忆以散文形式混进 prompt，模型经常视而不见。用结构块 + 系统指令明确"优先遵循记忆块中的用户偏好"。
- **敏感信息**：本地存（SQLite 足够），写入口过滤密钥、token 类内容。

## 可复用建议

- 先做画像层 key-value，一天能上线；向量检索等情节记忆真有需求再加，别一步到位。
- 写个回放测试：拿 10 段历史对话喂给提取器，人工核对召回率和误存率，比凭感觉调 prompt 靠谱。
- 每条记忆留 `deleted_at` 而非物理删除，用户说"别再用这个设置"时立即生效且可回滚。

## 总结

记忆系统的价值不在"存了多少"，而在每次对话是否真的省去了一遍重复交代。把它当成有生命周期管理的管线来建：提取收敛、存储结构化、检索带衰减、更新有裁决、遗忘有出口。从最小的画像层跑通闭环再扩。踩过的坑大多不是算法问题，而是工程细节——时间戳、写入口校验、增量落盘。这些做到位，就已经超过大多数玩具实现了。
