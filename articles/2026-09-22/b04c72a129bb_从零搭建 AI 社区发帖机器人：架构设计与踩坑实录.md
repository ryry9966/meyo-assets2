## 背景

社区每周都要人工整理新增 issue、已合并 PR 和插件动态，发一篇周报帖。事情不难，但重复、枯燥，还容易漏。于是我用 OpenClaw 搭了一个发帖机器人：数据自动采集，内容由 agent 生成，草稿走审核后发布。跑了一个多月，周报稳定产出，中途踩了不少坑，记录如下。

## 目标与边界

动手前先划边界，比选模型更重要：

- 只做聚合类内容（周报、动态汇总），不做观点输出；
- 先草稿、后发布，任何自动发布必须有审核开关；
- 每一步失败可追溯、可回放。

## 整体架构

四层结构，层与层之间只传结构化数据：

1. **采集层**：两个 MCP 工具 `list_merged_prs`、`list_new_issues`，从 GitHub 拉数据，返回 JSON；
2. **生成层**：OpenClaw agent 按固定模板生成草稿，系统提示词与风格指南放在 repo 里版本化；
3. **校验层**：结构校验（frontmatter、链接可达、代码块 lint）+ 内容 hash 去重；
4. **发布层**：`forum_post` 工具带 `dry_run` 参数，默认进人工审核队列，通过后才真正发帖。

## 实施步骤

1. 先写 MCP 工具，不动 agent。工具返回的错误信息要"人能读懂"，模型才能据此自纠；
2. 影子模式跑两周：每天生成草稿落盘到 `drafts/`，人工对照打分、调整提示词；
3. 上审核队列：草稿进 pending 状态，人工点头才发；
4. 逐步放开：目前只有周报帖全自动，其余类型仍走审核。

## 踩坑实录

**1. 重试导致重复发帖。** 发布接口超时，agent 自动重试，同一篇周报发了两遍。解法：发布前对内容算 hash 查重，`forum_post` 加幂等键，重试命中直接返回已有结果。

**2. 模型编造不存在的 PR。** 工具偶发超时返回空列表，模型"脑补"了三条像模像样的动态。解法：提示词硬性规定只能引用工具返回的条目，校验层逐条比对链接，对不上就打回重生成。

**3. 文风漂移。** 多轮会话里文风越写越像营销号。解法：每次生成开全新会话，风格指南放系统提示词而不是对话历史，改提示词要像改代码一样写变更记录。

**4. 触发社区频控。** 测试阶段连发几帖被反垃圾机制限流。解法：发布加最小时间间隔，测试一律走测试版块，上线前用 `dry_run` 全量验证。

**5. 日志泄露敏感信息。** 初期把请求 headers 全量打进日志，token 直接可见。解法：日志统一脱敏，密钥只走环境变量。

## 可复用建议

- MCP 工具粒度要小，命名动词化，错误信息是写给模型看的；
- 自动化发布必经 `dry_run` + 审核队列，影子模式先行，别跳步；
- 幂等和去重放在发布层做，不要指望模型"记得"发过什么；
- 提示词当资产管理：版本化、有 changelog、可回滚；
- 每篇产出带 trace id，出问题能定位到是哪次生成。

## 总结

这个项目里，最难的不是"让模型写帖"，而是工程化约束：边界、校验、幂等、审核。模型能力是乘数，工程底座是基数，基数为零则一切归零。建议想做发帖自动化的朋友从窄场景切入，先把发布链路的可靠性做扎实，再谈扩展。
