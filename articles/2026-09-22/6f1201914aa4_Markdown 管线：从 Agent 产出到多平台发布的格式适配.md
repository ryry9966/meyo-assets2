## 背景

我们的内容生产基本交给了 Agent：选题、初稿、配图说明都由 OpenClaw 工作流跑完，产出统一是一份 Markdown。但真正麻烦的环节在后面——同一段 Markdown 要发到博客、公众号、知乎、掘金和 RSS，各平台对 Markdown 的支持参差不齐。最初的应对是每次发布前人工改一版，两周后就撑不住了，于是把格式适配独立成一条管线。

## 问题

盘点下来，平台差异集中在四类：

1. **语法子集**。有的平台不支持脚注、任务列表、删除线，HTML 块一律被过滤。
2. **链接与图片**。公众号正文不保留外链 `<a>`，部分站点图片有防盗链，直接引用第三方图床会裂图。
3. **代码高亮**。有的吃 class 名，有的只认内联 style，主题还不通用。
4. **AI 输出噪声**。front-matter 残留、把整篇内容再包一层代码围栏、全角标点混进代码块。

单看都是小事，叠起来就是每次发布半小时的机械劳动，还容易漏。

## 做法

管线分四步，核心思路是**把 Markdown 当作中间表示（IR），平台差异全部收敛到适配器层**：

**第一步，归一化。** Agent 产出后先过 cleaner：剥掉 front-matter、处理围栏嵌套、统一换行和标点，输出标准 GFM。这一步只做减法和规范化，不掺平台相关逻辑。

**第二步，AST 化。** 用 remark 的 mdast（pandoc AST 也行）作为操作对象，所有转换基于节点树，不写正则。

**第三步，平台适配器。** 每个 adapter 是一个纯函数：`mdast → 平台 HTML/文本`。公众号 adapter 把外链转成文末引用列表加文内序号；掘金 adapter 做代码块 class 映射；知乎 adapter 做表格降级。

**第四步，校验。** 发布前跑一遍 lint：图片可达性、标签白名单、表格列数、链接去重。不过关就拦截，进 dry-run 预览，而不是直接推。

## 踩坑点

- **外链转换别用正则。** 早期在字符串层面替换 `<a>`，遇到链接里带引号或嵌套强调就崩，切到 AST 后一次修好。
- **图片必须转存。** 我们信过一次“源站比较稳”，三天后文章里全是裂图。现在归一化阶段就强制下载并上传到自己的对象存储。
- **宽表格是移动端杀手。** AI 很爱生成六列以上的对比表，超过四列自动转图片或列表，规则写进 lint。
- **在源头约束输出。** 与其在下游修，不如在 Agent 的系统提示里明确：“只输出 GFM，禁用脚注和 HTML 块，表格不超过四列。”成本最低。
- **智能引号。** 某些模型会把代码块内的引号“美化”成中文引号，直接导致渲染异常，归一化时要检查 code 节点内的字符集。

## 可复用建议

1. 每个 adapter 配一份 golden file 快照测试，平台改版时 diff 一眼看出影响面。
2. 平台怪癖沉淀为一份配置（支持标签、图片规则、链接策略），adapter 只读配置，别把规则散落在代码里。
3. 上线 dry-run：所有目标平台渲染出预览，人工确认后才实发。
4. 管线与 Agent 解耦，通过 MCP 或普通 HTTP 接口对接——谁生成内容不重要，进来的是标准 GFM 就行。

## 总结

这条管线跑下来，单篇内容从生成到五平台发布的边际成本，从半小时降到了一次 dry-run 确认。核心经验一句话：**AI 只负责产出，格式纪律交给管线；Markdown 是 IR，平台是适配器，差异永远是配置问题，而不是人肉问题。**
