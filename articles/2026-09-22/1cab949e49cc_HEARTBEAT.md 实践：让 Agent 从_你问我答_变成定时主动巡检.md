## 背景

大多数 Agent 的使用模式是**你问它答**：不提问，它就安静待着。但真实场景里很多事需要"定时看一眼"——CI 状态、日历冲突、GitHub 未读、服务器指标。OpenClaw 内置了心跳机制来补这一环：Agent 每隔固定间隔（默认 30 分钟）自动醒来，读取工作区里的 `HEARTBEAT.md`，把文件内容当作本轮要处理的事项清单；没事可做就回一个 `HEARTBEAT_OK`，直接短路后续消息投递，开销很小。

## 问题

传统做法是 cron + 脚本，但脚本和 Agent 的上下文、工具链、判断力是割裂的；靠人肉提醒 Agent 检查，则回到了"助理还得靠主人记事"的悖论。心跳机制的价值在于：**把什么时候检查、检查什么、什么情况才打扰你，写进一个 markdown 文件就够了**，判断逻辑留在 Agent 上下文里。

## 做法

1. **定位文件**：`HEARTBEAT.md` 在工作区根目录（默认 `~/.openclaw/workspace/` 下），没有就新建。
2. **写任务**：用普通 markdown 列表，每条任务写清三要素，触发条件、执行动作、通知策略。例如："每天上午查一次 GitHub 通知，只汇总未读 issue；无异常保持沉默"。
3. **配间隔**：心跳间隔可在配置里调整（如 `HEARTBEAT_INTERVAL_MS`），巡检类 30 分钟够用，报告类可以拉长。
4. **控制投递**：心跳产生的消息默认推到主会话，容易刷屏。在任务里指定投递目标（如 "Announce to: 某个专用渠道"），把例行汇报和日常对话分开。
5. **联动工具**：心跳里可以直接调用 Agent 已有的 skills 和 MCP 工具（fetch、日历、shell 等），复杂巡检也只是多一行任务描述。

## 踩坑点

- **任务写得太虚**。"帮我盯着服务器"会让 Agent 每次心跳都做一轮大而全的检查，token 烧得快还容易误报。要写明检查对象、阈值、什么才算"值得报告"。
- **通知风暴**。连续告警会连环轰炸。加去重语义：维护一个状态文件，任务里写明"上次已报告过的告警不要重复发"。
- **成本意识**。哪怕无事可做，每次心跳也是一次模型调用。默认 30 分钟一天 48 次，小模型无所谓，换大模型前先算账。
- **任务堆积**。`HEARTBEAT.md` 很容易变成垃圾场，过期任务会一直被执行。建议每周清一次，做完的删掉，重活转 cron。
- **上下文膨胀**。例行报告写多了会把上下文撑大，让 Agent 把结果落到独立日志文件，只在异常时才说话。

## 可复用建议

- 任务描述固定三段式：**【条件】【动作】【通知策略】**，缺一项别上线。
- "晨报模式"是最稳的起步场景：固定时段汇总日历 + 未读 + CI 状态，低频、只读、容错高。
- 巡检和报告分离：巡检求快求静，报告走专用渠道。
- 超过 10 条任务就该拆：心跳只留"值得在 Agent 上下文里做判断"的事。
- 把判断逻辑写进文件而不是靠模型自觉：明确写"什么情况保持沉默"。**沉默比误报更值钱。**

## 总结

`HEARTBEAT.md` 机制本身很小：定时醒来、读文件、做事或沉默。但它把 Agent 的价值从"问答质量"扩展到了"值守质量"。真正决定效果的不是机制，而是你写的任务描述够不够工程化，条件明确、动作收敛、通知克制。建议从一两个高频低风险的检查起步，跑一周看 token 账单和误报率，再决定铺开多少。
