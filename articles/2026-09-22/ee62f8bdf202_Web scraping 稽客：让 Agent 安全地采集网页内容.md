## 背景

Agent 一旦要回答"最新"的问题——文档版本、价格、公告、issue 状态——就绕不开网页采集。在 OpenClaw 里，常见做法是把 scrape 封装成 MCP 工具暴露给模型。但"能抓下来"和"抓得安全、干净、可追溯"是两回事，后者才是生产环境真正花时间的地方。

## 问题

实践里的问题集中在三类：

1. **礼貌与合规**：不查 robots.txt、不限速，跑两天 IP 就被封，还可能给目标站和社区添麻烦。
2. **内容质量**：大量页面是 SPA，拿到的是空壳 HTML；或者正文混着导航、页脚、推荐位，模型被噪音带偏。
3. **安全**：网页内容本质是**不可信输入**。它会直接进入模型上下文，可能藏着针对 Agent 的注入文本，超长内容会撑爆上下文，目标 URL 还可能构成 SSRF。

## 做法

我目前的管道分五层，每层独立可测：

**1. 准入层**：维护域名 allowlist；抓取前检查 robots.txt；每域名限速（1 req / 2s 左右）；UA 里带可联系的标识。

**2. 抓取层**：先用纯 HTTP 请求，检查正文长度；不达标再升级 headless 浏览器，同时拦截图片/字体，超时 15s。同 URL 结果缓存（TTL 1 小时）。

**3. 提取层**：readability 类算法取正文，去导航页脚，保留标题、发布时间、原始 URL。

**4. 消毒层**：剥离 script/iframe/HTML 注释，**特别要剔除 display:none 的隐藏文本**——这是 prompt injection 最常见的藏身处；输出截断到 8k tokens。

**5. 交付层**：返回结构化结果 `{url, status, fetched_at, content}`，引用有据可查，日志留一份审计记录。

## 踩坑点

- **SPA 空壳**：静态抓取返回 200 但正文只有几百字符，模型开始幻觉补全。对策：正文低于阈值时标记 `content_truncated` 或触发 headless 重抓，绝不把空壳交给模型。
- **登录墙与无限重定向**：重定向上限 5 次；401/403 直接返回失败，不要降级去抓登录页。
- **编码**：不少老站是 GBK，按 UTF-8 解就是乱码。做 charset 探测，别只看 header。
- **SSRF**：目标 URL 先解析 DNS，命中私网段（127.0.0.1、10.x、169.254.x）直接拒绝。容器化部署里这条尤其关键。
- **抓太快**：被封往往是指数级的——先慢后封。限速 + 缓存 + 失败退避，三件套缺一不可。

## 可复用建议

- scrape 做成独立 MCP 工具，别让模型自己拼 HTTP 请求——参数不可控。
- 失败要"显式失败"：宁可返回明确错误状态，也不要返回半截内容让模型猜。
- 缓存、去重、限速在工具层统一做，不指望模型自觉。
- 每次抓取记日志：目标 URL、耗时、返回规模，出问题能回溯。

## 总结

安全采集没有黑科技，就是**准入 → 抓取 → 提取 → 消毒 → 交付**五层普通工程。核心心法一句：把网页当不可信输入，把 Agent 当会犯错的调用方。把每层的边界条件想清楚，这套东西就能在真实流量下稳定跑。
