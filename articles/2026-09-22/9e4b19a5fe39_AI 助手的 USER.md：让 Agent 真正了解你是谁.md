## 背景

OpenClaw 的工作区里有一组约定俗成的 Markdown：SOUL.md 管人格，TOOLS.md 管能力，而 USER.md 管的是"你是谁"。它会在会话启动时被注入上下文，是 Agent 认识你的第一手资料。但很多人装完就把它留在模板状态，或随手写两行，等于浪费了这个最便宜、最可控的定制入口。

## 问题

不写 USER.md 的后果很具体：

- 每次都要重新交代技术栈："我用 Python 3.12，别再建议 pip 了"
- 时区靠猜，"今天下午"能给你排到错误的半天
- 回复风格忽冷忽热，有时过于客套，有时过于放肆
- Agent 反复问一些本该记住的问题

这些不是模型能力问题，是上下文缺失。与其在对话里反复纠偏，不如把稳定事实固化成文件。

## 做法

我的 USER.md 控制在 40 行以内，分五段：

```markdown
# 用户画像

## 环境
- 时区：Asia/Shanghai，工作日 10:00–19:00 在线
- 主力机：macOS + Linux 服务器，终端为主

## 技术栈
- Python 3.12 / Go，包管理用 uv
- 格式化：ruff，不用 black
- 编辑器：Neovim，别推荐 IDE

## 沟通偏好
- 中文回复，代码注释用英文
- 直接给结论，不确定就说不确定
- 别用 emoji，别客套

## 当前项目
- 网关重构（Go），优先级最高

## 红线
- 不自动推送代码，git push 前必须确认
```

要点是"一段一事，一行一事实"。写完直接问 Agent："你现在知道我什么？"即可验证注入是否生效。

## 踩坑点

1. **写太长**。USER.md 每次会话都占 token，两百行的人物小传只会稀释重点，稳定事实才配进来。
2. **写愿望不写事实**。"希望代码优雅"没有操作性，"ruff、不用 black"才有。
3. **放敏感信息**。USER.md 会进模型上下文，如果走云端 API，或 Agent 挂了外发类工具，密钥、住址、证件号一律不写。
4. **信息过期**。项目和作息会变，建议每月 review 一次。Agent 回答开始"不对劲"时，我第一件事就是查这份文件。
5. **职责混淆**。人格归 SOUL.md，今天的动态归 MEMORY.md，USER.md 只放中期稳定的用户事实。混着写会改一处、乱三处。

## 可复用建议

- 把 workspace 放进 git，USER.md 的每次修改都有据可查
- 可以让 Agent 在对话中发现新事实后提议更新，但由你确认写入——事实的最终解释权在人
- 用 MCP 接了日历、时区类工具的话，USER.md 里的时区可作为兜底默认值，工具调用失败时 Agent 不至于瞎猜
- 团队场景可平移这套思路做 PROJECT.md，承载协作约定

## 总结

USER.md 是成本最低的 Agent 定制手段：一个纯文本文件，改完即生效。它的价值不在写得多，而在写得准——把那些你不愿意每次重复交代的事实固化下来，其余交给对话和记忆。写好这份文件，相当于给 Agent 递了一张靠谱的名片。
