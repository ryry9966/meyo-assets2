## 背景

给 Agent 接上 MCP 工具和插件之后，第一周很爽，第二周开始纠结：它到底该有多大自主权？完全人工确认，每个读文件、查库的操作都要点一次"允许"，自动化就退化成人肉循环；完全放权，一次误操作的代价可能远超它省下的时间。权限边界不是安全团队的专属话题，是每个跑 Agent 的人都要面对的设计问题。

## 问题

核心矛盾是两个失效模式的对偶：

- **确认疲劳**：弹窗太多，人类开始无脑点"是"，确认机制形同虚设；
- **过度授权**：出事之后回看日志，发现关键操作是在没人看的时候执行的。

多数框架只给"允许/拒绝"两档粒度，缺一个中间态：什么时候问、问的时候给什么信息、问完怎么落地。把权限策略写在 system prompt 里靠模型"自觉"，是最常见的错误起点。

## 做法

我们把每次工具调用按两个维度分类：**可逆性**（能否撤销）和**影响半径**（波及范围是否可控），得到一个决策矩阵：

1. **可逆 + 范围小** → 自动执行。读文件、查库、沙箱里跑测试归这类。
2. **可逆 + 范围大** → 自动执行但留检查点。批量改代码先建分支、发消息先落草稿，可整体回滚。
3. **不可逆 + 范围小** → 问一次，但把问题问对：展示将执行的命令、目标资源、diff，而不是一句"是否继续？"。
4. **不可逆 + 范围大**（删数据、对外发布、真实付款）→ 默认拒绝自动执行，人在环上，最好拆成多步分别确认。

落地时再叠三道闸：

- **默认拒绝 + 白名单**：权限写成结构化规则（工具 × 操作类型 × 资源模式），不用自然语言描述；
- **预算闸**：调用次数、费用、时长设上限，触顶自动降级为询问模式；
- **执行前快照**：写操作前自动打 checkpoint，让"不可逆"尽量变成"可逆"。

## 踩坑点

- **在错误时机问**：Agent 已删了半个目录才来确认，等于没问。确认点必须卡在副作用之前——先出计划、先审、再跑。
- **无效提问**："我可以继续吗？"是坏问题。不带上下文的确认只会训练人类养成点击反射。
- **会话级放权**："本次会话内允许"听着合理，但长会话里任务早就漂移了。授权应绑定具体任务，任务结束自动回收。
- **让模型自评风险**：问 Agent"这个操作危险吗"，它倾向于说没事。风险分级必须是外部规则，不能由被评估者自己打分。

## 可复用建议

- 权限矩阵做成配置文件进版本库，事故复盘后直接改规则，而不是改 prompt。
- 记录所有自动放行的操作日志，每周抽样审计一次——这是发现确认疲劳最直接的信号。
- 询问界面给三个选项：批准 / 修改后批准 / 拒绝并说明原因。拒绝原因喂回上下文，Agent 下次才知道边界在哪。

## 总结

权限边界不是一道墙，而是随任务动态调整的闸门。原则一句话：**可逆的放开跑，不可逆的看半径，问人时把上下文给足**。先让默认行为安全，再用白名单逐步放权，比一开始全放、事后补漏洞的路径便宜得多。
