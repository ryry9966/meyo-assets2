## 背景

跑 OpenClaw 一段时间后，多数人会经历两个阶段：初期什么都让 Agent 问一遍，很快被"我可以继续吗？"刷屏；后来嫌烦，把确认全关掉，直到某天它把清理脚本跑在了错的目录上。权限边界不是开关，是需要设计的东西。

## 问题的本质

"该不该问人"其实不是模型能力问题，而是三个维度的问题：

- **可逆性**：操作能不能撤销？`ls` 可以随便跑，`rm`、`git push --force`、给客户群发消息不行。
- **影响面**：只影响自己的工作区，还是会触达外部系统（发布、支付、发消息）？
- **确认成本**：等 20 分钟人工确认一个无关紧要的删除，比让 Agent 自己判断更伤效率。

三个维度组合，就能把工具动作分成档位。注意一点：**不要让模型自己评估风险**——模型对"重要性"的判断不稳定，风险等级必须来自静态规则和工具声明。

## 做法

1. **盘点工具，按副作用分类**。把 shell、文件、浏览器、MCP 工具逐个过一遍：只读、本地写、外部副作用、不可逆，各自标记。
2. **定义四档权限**：
   - L0 只读：自动执行；
   - L1 本地写：自动执行，但必须留审计日志（命令、路径、diff）；
   - L2 外部副作用：发消息、调第三方 API，需要确认，确认卡片必须带"做什么、发给谁"的预览；
   - L3 不可逆/高危：push、删除、支付类，默认拒绝，白名单逐条放行，每次都要确认。
3. **让"问人"变便宜**。确认请求要有上下文：打算做什么、为什么、改动 diff。只弹一句"可以执行吗？"，人只会无脑点通过。
4. **定超时策略**。确认请求挂起多久算失败？建议显式超时后放弃并记录，而不是自作主张换条路执行。
5. **定期复盘升降级**。每周看审计日志：某类 L2 操作连续一个月零差错且低风险，降为 L1；出过一次事故的，直接升 L3。

## 踩坑点

- **确认疲劳**：一天弹 30 个确认框后，人就是橡皮图章。宁可收紧 L2 的范围，也别把低价值确认糊到人脸上。
- **粒度太粗**：把整个 shell 工具一刀切到"必须确认"，等于没设计。至少按命令白名单拆分。
- **MCP 凭据共享**：一个只读检索类的 MCP server 拿着能写仓库的 token，权限分层在它那里就失效了。每个 server 给最小凭据。
- **忘记超时**：确认没人理，Agent 干等两小时或擅自换方案——比直接拒绝更糟。
- **把问人当兜底**：拿不准就问，本质是把风险判断推给人。正确动作是先做只读侦查，缩小不确定性，再决定要不要问。

## 可复用建议

- 默认最小权限，白名单放行，而不是黑名单拦截。
- 不可逆 = 必须确认；外部可见 = 必须确认；其余尽量自动。
- 确认必须带预览和理由，否则等于没有确认。
- 审计日志是权限体系的输入，没有日志就没有升降级依据。
- 风险分级写进配置和工具声明，不要靠 prompt 祈祷。

## 总结

权限边界问题不是"信任这个模型吗"，而是"错了怎么办"。可逆的小错让 Agent 自己承担并留下记录，不可逆的大错在流程上就不给它机会。这套档位跑起来之后，你会发现真正需要人介入的决策比想象中少得多——剩下的每一次确认，才有分量。
