## 背景

用 AI 助手写代码之后，一个反直觉的现象是：代码产出变快了，git 记录反而更乱。改动一大，人就随手一句 `git commit -m "wip"` 糊过去；任务切换频繁，本地堆着十几条没清理的 feature 分支。Git 本身高度结构化、可脚本化，恰恰适合交给 Agent 通过 MCP 工具或受限 shell 去打理。真正的问题是：怎么交，交多少。

## 问题

直接给 Agent 完整 git 权限有两类风险。一是误操作不可逆：`push --force`、`reset --hard`、`clean -fd` 任何一条都可能毁掉工作成果。二是提交质量不可控：Agent 倾向于 `add -A` 一把梭，message 和实际 diff 对不上，甚至把 `.env` 这类文件带进历史。

## 做法

核心思路是把「便宜操作」和「昂贵操作」分开管理：

1. **收窄工具面**。不直接暴露 git，而是包一层受限 CLI（或 MCP 工具），白名单只放行 `status / diff / add <path> / commit / branch / switch / log`，历史改写和远端操作一律拒绝，所有调用落日志。
2. **约定提交格式**。在项目内的 Agent 指导文件里写死 Conventional Commits：`type(scope): subject`，body 说明为什么改，且 message 必须从真实 diff 推导，禁止凭任务描述脑补。
3. **按逻辑单元提交**。每完成一个任务单元，Agent 先 `diff` 自查，按模块拆分、显式指定路径 stage，分多次 commit，而不是一次全塞。
4. **分支生命周期**。任务开始先建 feature 分支；每周期跑一次分支巡检，用 `git branch --merged` 列出可删分支生成报告，删除需人工确认。
5. **钩子兜底**。pre-commit 跑 lint 和密钥扫描；钩子失败时要求 Agent 读错误信息修复，明确禁止 `--no-verify` 绕过。
6. **push 留给人**。commit 本地可逆，放开做；push、开 PR、rebase 已推送分支，必须人工确认后才放行。

## 踩坑点

- `add -A` 是最大事故源，临时文件、本地配置全进历史，必须强制显式路径。
- 钩子失败重试循环：Agent 不读报错、盲目重跑。指令里要写明先解析错误再动手。
- message 幻觉：写得头头是道，diff 里根本没有对应改动。要求 message 逐条对应 diff 片段。
- 让 Agent 做 rebase，冲突全靠猜，比不做还糟。冲突一律上交人工。
- 上下文长度：大 diff 塞不进去时 Agent 会偷懒概括，改为按文件逐个提交。

## 可复用建议

- 把 git 约定写进仓库内的 Agent 指导文件，跟着代码走，换工具不失效。
- 给 git 操作做两层权限：本地可逆操作自动放行，远端/破坏性操作走确认。这是这类自动化能放心用的核心。
- 分支治理用「报告 + 确认」，不要全自动删除，误删成本远高于省下的时间。
- 所有 Agent 的 git 调用记日志，出问题可回放。

## 总结

Git 自动化的重点不是让 AI 会跑 git 命令，而是把它能跑的命令收窄到「错了也能撤回」的范围。从本地提交规范和分支巡检做起，push 和历史改写留在人工手里，Agent 就能真正分担 git 负担，而不是制造新的麻烦。
