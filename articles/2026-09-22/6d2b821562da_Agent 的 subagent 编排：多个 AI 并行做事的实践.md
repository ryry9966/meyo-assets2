## 背景

日常用 OpenClaw 跑自动化任务，单 agent 大多够用。但有一类任务天然是「批量 + 相互独立」的：同时调研 8 个开源仓库的许可证和活跃度、给 20 个日志文件做异常扫描、为一批文档生成结构化摘要。这类活让主 agent 顺序做，一是耗时长，二是所有中间结果都堆在同一个上下文里，做到一半上下文就膨胀了，模型开始「遗忘」前面的结论，质量明显下滑。

## 问题

直接在系统提示里告诉主 agent「你可以派 subagent 并行干活」，实际效果往往很差。常见的三种翻车：

1. **子任务描述不完整**：子 agent 拿到的 prompt 缺前提，只能猜主 agent 脑子里默认的上下文，输出方向跑偏。
2. **结果回灌爆炸**：子 agent 返回大段原文，主 agent 的上下文反而更臃肿，违背了拆分的初衷。
3. **并发失控**：不限流触发 API 429，或者两个子 agent 同时写同一个文件互相覆盖。

## 做法

踩过几轮坑后，我收敛出一套固定流程：

1. **先判断能否并行。** 有依赖链的任务别拆；「独立、同构、可枚举」的批量任务才值得 fan-out。
2. **把子任务当成写函数签名。** 每个 subagent 的 prompt 必须自包含：目标、输入路径、输出格式、边界条件、禁止事项，一样不缺。主 agent 不要假设子 agent「知道」任何没写进去的东西。
3. **用工作区文件当接口，不靠对话传内容。** 固定模式：子 agent 把完整结果写到 `output/<task-id>.md`，会话里只回 3~5 行摘要加文件路径。
4. **控制并发。** 3~5 个一批，跑完再发下一批；写文件的任务各分配独立输出目录，规避竞争。
5. **汇总时抽样核对。** 主 agent 只读摘要做聚合，对关键结论打开原始文件抽查一两个，再给最终答复。子 agent 自信地报错结果是常态，这一步不能省。

## 踩坑点

- **幻觉上下文**：prompt 里没写「只看最近 30 天」，子 agent 就把全部历史都分析了。教训：所有隐含前提必须显式写进任务描述。
- **摘要不摘**：不限定长度，子 agent 会回 500 字「摘要」。后来直接写死「最多 5 行，每行一个结论」。
- **输出互相覆盖**：两个子 agent 默认都写 `results.md`，改成按 task-id 分文件后消失。
- **并行不是免费的**：有次把串行依赖的任务也拆了并行，子 agent 之间靠猜接力，返工两轮。判断标准很简单——A 的输入依赖 B 的输出，就不能并行。

## 可复用建议

- 沉淀一个五段式任务模板：**目标 / 输入 / 输出路径 / 输出格式 / 禁止事项**，每次派发填空即可。
- **文件即消息总线**：子 agent 之间、子 agent 与主 agent 之间，一切通过工作区文件交换，会话里只传指针。
- 结构化返回（摘要 + 路径 + 状态）优于自由文本。
- 单个子 agent 失败不拖垮整批，主 agent 汇总时标记缺项，单独重试。

## 总结

Subagent 编排的本质不是「多开几个 AI」，而是**任务边界的工程化**：能并行的拆干净、接口定清楚、结果收敛回主 agent。做到这三点，批量任务的耗时会从串行的 N 倍压缩到接近一批的时间，主 agent 的上下文也始终保持干净。建议从一个你已经手动跑通过一遍的批量任务开始，先做一个 3 并发的最小批次验证模板，再谈规模化。
