## 背景

日常开发里，Git 操作大半是重复劳动：写提交信息、切分支、删掉早已合并的旧分支。这类事 AI 助手完全能干，而且比人稳定。我在自己的 OpenClaw 工作区里跑了一套 Git 自动化，用了两个多月，这里把配置思路和踩过的坑整理出来。

## 问题

自动化之前，我的痛点很具体：

- 提交信息质量取决于当天状态，history 里一半是 `update`、`fix`；
- 分支只建不清，远程堆了三十多个已合并分支；
- 切分支忘了推，回来发现基于旧分支改了一堆；
- 直接给 agent 开 shell 全量权限有风险——它一旦学会 `--force`，就晚了。

## 做法

### 1. 选工具层

两条路：一是跑一个 MCP git server，能力全但权限粒度要自己收；二是用 shell 插件配命令白名单。我选了后者，更可控：

```
允许: git status / diff / log / show / branch / add / commit -m / switch -c
禁止: push --force / reset --hard / clean / rebase -i / --no-verify
```

原则是：读操作放开，写操作收口，破坏性操作干脆不出现在白名单里。

### 2. 把规范写成 SKILL.md

规范固化成 skill，agent 每次会话自动加载，不靠对话里反复强调：

- 提交信息走 Conventional Commits，scope 从改动文件推断；
- 分支命名统一 `feat/xxx`、`fix/xxx`、`chore/xxx`；
- 任何写操作前，先输出将要执行的命令和 diff 摘要，等我确认再动手；
- pre-commit 失败就如实报告，禁止绕过。

### 3. 两个高频流程

**提交流程**：一句"看看当前改动，给我一版提交信息"，agent 跑 `git diff --staged`，按规范起草 message，我确认后它执行 add + commit。关键点是只喂真实 diff，不让它猜。

**分支清理**：每周 cron 一次，agent 跑 `git branch --merged main` 列出可删分支，输出清单等确认，确认后批量 `-d`（小写，非强制）。

## 踩坑点

1. **只给 status 不给 diff，agent 会"脑补"提交信息**，写得像模像样但和改动对不上。必须把真实 diff 塞进上下文。
2. **自我提交循环**：agent 在改自己工作区文件时会顺手 commit 中间态。后来在 skill 里写死：每次会话最多一次 commit，且必须有我的确认。
3. **钩子冲突**：pre-commit 在 agent 沙箱里跑得慢或失败时，它会试图 `--no-verify` 绕过去。这一条必须显式禁止，否则早晚会提交脏代码。
4. **交互式命令会挂起**：`rebase -i`、不带 `-m` 的 commit 都会等编辑器。skill 里统一要求非交互参数。
5. **编码**：Windows 下 message 里的中文偶尔乱码，统一 UTF-8 后解决。

## 可复用建议

- 权限分三档：读默认放开、写需确认、强推/重置/清理永远不进自动流程。
- 规范写进 SKILL.md，而不是每次对话临时说，避免行为漂移。
- 留审计：让 agent 把每次执行的 git 命令追加到日志文件，出问题能回溯。
- 灰度上线：先跑一周"只生成提交信息、不执行"，观察 message 质量，再放开执行权限。

## 总结

这套东西代码量接近零，价值全在约束设计上：AI 助手管 Git 的关键，不是让它会跑命令，而是想清楚哪些命令允许跑、跑之前要不要问人。跑了两三个月，分支列表干净了，commit history 也能读了——对个人开发者来说，这就够回本了。后面如果多人仓库有需求，再把 push 环节加进确认链路里。
