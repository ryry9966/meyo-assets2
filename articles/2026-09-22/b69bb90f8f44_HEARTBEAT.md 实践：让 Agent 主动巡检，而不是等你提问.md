## 背景

大多数 Agent 的交互模型是"你问我答"：你不发消息，它就永远沉睡。但 OpenClaw 的 Agent 跑在常驻的 gateway 上，本身就是一个长期在线的进程——这给了一种很少被用好的能力：主动做事。

OpenClaw 的解法是 HEARTBEAT.md：Agent 每隔一段时间自动醒来一次，读一遍工作区里的这个文件，自己判断有没有值得做的事。没有，就回一个 `HEARTBEAT_OK`，什么都不发；有，就把结果主动推给你。

## 问题

它填的是 cron 和人工提问之间的空档：

- cron 能定时，但没有判断力。脚本只能写死"磁盘超 80% 就报"，逻辑一复杂就得写成程序。
- 人工提问有判断力，但你得记得问。"帮我看看邮件里有没有要紧的"——你不问，它不做。
- 很多巡检类需求的本质是：低频检查 + 阈值判断 + 异常才说话。这恰好是模型擅长而脚本不擅长的。

## 做法

三步：

**1. 开启心跳。** 在 `openclaw.json` 里给 agent 配置 heartbeat 周期，建议从 30m 起步：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "30m" }
    }
  }
}
```

**2. 写 HEARTBEAT.md。** 放在 agent 工作区根目录（默认 `~/.openclaw/workspace/`），内容就是希望它定期过一遍的自然语言清单。关键是把"判断标准"和"静默规则"写清楚：

```markdown
# 常驻检查
- 服务器磁盘：只有超过 80% 才告诉我，否则保持沉默
- 未读邮件：只汇报需要我决策的，广告和通知直接跳过

# 一次性任务
- 整理周报素材（做完后从本文件删除这一行）

# 规则
- 默认沉默，无异常就回复 HEARTBEAT_OK
- 同一问题连续三次出现才升级提醒
```

**3. 指定投递目标。** 把主动消息发到一个专门的"告警"群或频道，而不是主对话，避免打断正常交互。

## 踩坑点

- **刷屏。** 最常见的失败模式：每 30 分钟收到一句"一切正常"。根源是文件里没写静默规则。写明"默认沉默，只有异常才发"，并依赖 `HEARTBEAT_OK` 的约定。
- **Token 成本。** 每次心跳都会把 HEARTBEAT.md 和上下文灌进一次推理。5 分钟一次、文件 200 行，账单会很诚实。文件控制在几十行内，周期别低于 30m。
- **重复告警。** 磁盘 81% 的问题会连报多次。要么写升级规则（连续 N 次才提醒），要么让 Agent 处理完直接编辑 HEARTBEAT.md——这个文件它是可以改的，处理完的行就删掉。
- **长任务。** 心跳跑在主会话里，别让它每次醒来干重活。巡检保持轻量，重任务交给 cron 触发的独立会话。
- **半夜打扰。** 配置活跃时间段（activeHours），否则它凌晨三点也会尽职地告诉你磁盘满了。

## 可复用建议

- **心跳管"模糊判断"，cron 管"精确时间"。** 整点日报用 cron，"有空时看看有没有异常"用心跳，别混用。
- **把 HEARTBEAT.md 纳入 git。** 它决定了 Agent 的自主行为边界，改了什么应当可追溯。
- **每条检查项都写成幂等的。** 心跳会反复执行，检查本身必须能安全重复。
- **只给需要自主性的主 Agent 开心跳。** 工具型子 Agent 不需要，开了只是浪费。

## 总结

HEARTBEAT.md 的价值不在"自动化"——cron 早就能自动化——而在于把"要不要做、做到什么程度"的判断交给模型，把"什么时候醒、醒了读什么"留给一个极简的文本协议。写好这个文件的核心手艺只有一条：明确什么情况下它应该闭嘴。静默规则写得越清楚，主动 Agent 越有用；写不清楚，它就只是一台烧 token 的唠叨机器。
