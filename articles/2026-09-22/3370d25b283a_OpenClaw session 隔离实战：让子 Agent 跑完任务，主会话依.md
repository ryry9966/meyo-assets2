## 背景

OpenClaw 的主会话是长期载体：你和助手的每轮对话、工具轨迹、系统备注都会沉淀在里面，影响后续所有回答。而日常使用中大量工作其实不属于“对话”——定时任务、MCP 工具编排、多步自动化，这些都是子 Agent 的活，中间产物又多又脏。子 Agent 怎么跑、跑完留下什么，直接决定主会话还能不能用。

## 问题

我最早的做法很糙：自动化任务直接在主会话里跑。抓网页、调工具、排错，几轮下来主上下文塞满了中间输出。后果有三个：token 消耗失控，压缩后噪声反而更集中；助手被带偏，反复引用几小时前的过期中间结果；想 reset 时发现任务记录和正常聊天混在一起，没法分开清理。

## 做法

现在的流程拆成五步：

1. **子任务独立 session**。派发子 Agent 时指定独立 session key（如 `sub:report-0712`），全部工具调用和中间输出落在它自己的会话文件里，主会话只收到“任务已派发”。
2. **约定返回口径**。子 Agent 结束时只回一条结构化摘要：状态、结论、产物文件路径。长输出一律写文件，不回传。
3. **主会话只沉淀摘要**。摘要作为一条简短系统备注写入主会话，控制在一两百字内，之后对话能引用结论，但不背过程。
4. **生命周期管理**。子 session 设 TTL，或任务完成后直接清理；每周跑一次 `openclaw sessions` 巡检，删掉孤儿会话。
5. **环境隔离**。子 Agent 用最小权限 profile 和独立工作目录，避免并发任务互写文件。

## 踩坑点

- **假隔离**：子 Agent 最后一条消息是几 KB 的原始输出，全量回传主会话，等于白隔。必须在 spawn 提示词里强制“先自我总结再返回”。
- **session key 复用**：两个任务用了同一个 key，上下文串台。key 里带日期或任务 ID，保证唯一。
- **忘清理**：sessions 目录越滚越大，某次 reset 直接恢复到旧任务现场。TTL + 巡检脚本兜底。
- **无超时**：子 Agent 死循环烧 token。spawn 时设 timeout 和最大轮数，超时即杀。
- **摘要夹带敏感信息**回流主会话，返回前做一层脱敏。

## 可复用建议

- 沉淀一个 spawn 模板：固定头部写清目标、边界、返回 schema、超时，每次只改任务描述。
- 记住一句话：**文件是事实，会话是过程**。产物全部落盘，会话里只留指针。
- 命名规范（`sub:<任务>-<日期>`）+ 定期巡检，是成本最低的卫生习惯。

## 总结

session 隔离的本质是分工：主会话留给对话和长期记忆，子 Agent 的一切留在自己的 session 里，回流时只过一道“摘要闸门”。做到这三点，自动化跑得再重，主会话也不会被污染。
