## 背景

在 OpenClaw 里挂一个写作 Agent，产出统一是 Markdown，但发布端是三套规则：公众号要 HTML 加内联样式，知乎的 Markdown 支持有限，掘金和自建博客相对原生但图床要求不同。同一份稿子，手工适配一次半小时起步，而且每次都踩不一样的坑。这篇文章记录我把这段链路管线化的过程。

## 问题

- **上游不完全可控**：AI 产出的 Markdown 会混入 raw HTML、脚注、四层标题、非标准表格写法。
- **下游能力矩阵参差**：公众号不支持外链图床，会剥掉 `<details>` 和 class；知乎的代码块会吞内联 span；掘金需要图床 URL 替换。
- **最常见的错误做法**：用一串正则脚本做转换，改一处崩一处，代码块里的 `# 注释` 被当成标题是经典事故。

## 做法

1. **收敛源头**。给 Agent 的产出加硬约束：单一 H1、最多三级标题、禁 raw HTML、图片统一用 `![alt](placeholder-id)` 占位。再加一层 lint（remark-lint 加自定义规则），不合格直接打回重写，不在下游兜底。
2. **解析成 AST**。整条管线用 unified/remark 走 mdast，所有变换基于节点操作，不碰字符串。这是管线能长期维护的前提。
3. **平台适配器写成纯函数**。每个适配器 = 一组 transform + 一个渲染器。公众号适配器负责 md→HTML、样式内联、代码块预高亮成带内联颜色的 HTML、宽表格转图片；掘金/知乎适配器负责剥离 frontmatter 和重写图片 URL。
4. **资产步独立出来**。图片先上传到目标平台（公众号必须传素材库，外链发布后会变成"未经允许不可引用"），拿到最终 URL 回填 AST，再渲染。
5. **能力矩阵 + 快照测试**。维护一张表记录每个平台支持什么、不支持什么；每个适配器配几份 fixture 跑快照，防止改一处崩别处。
6. **封装成 MCP 工具**。暴露 `render(platform, markdown)` 和 `publish(platform, doc_id)`，Agent 写完稿可以自助渲染预览，发布保留人工卡点。

## 踩坑点

- 正则替换在代码块内的 Markdown 语法上必炸，必须走 AST。
- 公众号只认内联 style，class 全部被清洗。
- 预高亮的代码块发到知乎会被去 span，颜色全丢——知乎就让它用平台自带高亮，别强行内联。
- frontmatter 忘剥离，发布出去开头一排 `---`。
- 顺序不能错：先渲染再传图会导致 AST 里还是占位符，渲染结果作废。正确顺序是传图 → 回填 → 渲染。
- LLM 偶尔输出 HTML 实体（`&nbsp;` 之类），加一步实体归一化。

## 可复用建议

- 适配器的输入输出都是纯数据（AST → payload），测试和并行开发都容易。
- 约束上游比下游兜底便宜十倍，prompt 里的产出规范值得认真写。
- 不要为平台 fork 内容分支；只有"表达本身需要不同"时才分叉，格式差异一律交给适配器。
- 每一步的中间产物落盘（md → mdast.json → 各平台 payload），排障时能直接定位是哪一层坏了。

## 总结

这条管线核心就三件事：源头收敛、AST 变换、适配器纯函数化。做完之后多平台发布从半小时降到一次人工确认，Agent 也能通过 MCP 工具自助预览。格式适配没有银弹，但把"内容"和"格式"的边界画清楚，维护成本会从随平台数线性增长变成近似常数。
