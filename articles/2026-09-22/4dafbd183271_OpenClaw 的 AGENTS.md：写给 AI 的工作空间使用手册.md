## 背景

OpenClaw 的默认工作空间里有一组约定文件：`SOUL.md` 管人格，`USER.md` 管用户画像，而 `AGENTS.md` 是唯一一个每轮对话都会注入上下文的"操作手册"。它不定义 agent 是谁，而是定义"在这个工作空间里，事情该怎么做"。很多新用户把它当普通 README 随手写几行，跑一段时间才发现：行为漂移、重复犯同样的错，大多能追溯到这里。

## 问题

不写 AGENTS.md 的 OpenClaw 有几个典型症状：

- 每次让它跑脚本，它都重新猜目录结构和命名约定；
- cron / heartbeat 触发的任务，回复风格和交互式对话不一致；
- 接了 MCP 工具和插件后，agent 在多个功能重叠的工具之间反复横跳；
- 你纠正过一次的错，过两天它又犯。

这些不是模型能力问题，而是缺少一份稳定、可维护的工作空间约定。AGENTS.md 就是承载这些约定的地方。

## 做法

我的写法分四步：

1. **先列清单再动笔**。把 agent 高频动作列出来：跑哪些脚本、读哪些目录、用哪些工具、什么情况该问人。清单本身比文笔重要。
2. **按场景而非功能组织**。"日常汇报：先查 xx 目录，用 xx 插件发消息，失败时降级为本地写文件"，比罗列工具参数有效得多。
3. **写裁决规则**。多个工具功能重叠时明确优先级，比如"文件操作用内置工具，外部 API 查询走 MCP"。这是消除工具横跳最有效的一条。
4. **版本化**。放进 git，每当 agent 行为不符合预期、你靠口头纠正解决后，把纠正沉淀进文件并提交。这是把"调教"变成"工程"的关键。

一个可参考的最小骨架：

```markdown
# 工作空间约定
## 目录与脚本
- 脚本统一放 scripts/，输出写 out/<日期>/
## 工具优先级
- 文件操作用内置工具；外部 API 查询走 MCP
## 汇报规则
- 长任务结束必须附结果路径；失败必须给出可执行的下一步
## 禁止事项
- 不修改 .env；不删除历史产物
```

## 踩坑点

- **写太长**。AGENTS.md 每轮都进上下文，两千行的手册等于让 agent 背着背包跑马拉松。超过一屏就该合并，或外置到 TOOLS.md 和脚本注释里。
- **和 SOUL.md 抢活**。说话风格、人设归 SOUL.md；"怎么做"归 AGENTS.md。两边写重复规则，冲突时行为会很不稳定。
- **塞敏感信息**。API key、内网地址写进去等于进上下文，也容易随工作空间同步泄露。放环境变量，文件里只写"密钥从环境变量读取"。
- **只写一次**。最贵的坑。agent 犯错后你口头纠正，它当时听话、下轮遗忘。没有沉淀回文件，等于白调。

## 可复用建议

- 把 AGENTS.md 当代码 review：改动走 commit，让历史可回溯。
- 每条规则尽量带"失败时的行为"。agent 对明确降级路径的执行，远比对模糊的"尽量"可靠。
- 用 heartbeat 做自检：每月让它读一遍自己的 AGENTS.md，报告哪些规则已过时。
- 团队共享工作空间时，AGENTS.md 就是人和 AI 的接口契约，值得像 API 文档一样维护。

## 总结

AGENTS.md 的价值不在"写了一份文档"，而在把对 agent 的每次人工纠正变成可持续积累的资产。写短、写裁决规则、写失败路径、随错误迭代——做到这四点，同一个模型在同一个工作空间里的表现会有肉眼可见的差距。
