# 背景：agent 没有默认记忆

跑一段时间 OpenClaw 之后，多数人会撞上同一个尴尬：上次明明说过「这个仓库用 pnpm，别用 npm」，两个会话之后 agent 又生成了一份 package-lock.json。原因不神秘——agent 没有跨会话的默认记忆，工作区里也没有任何东西告诉它「这里怎么干活」。

AGENTS.md 就是补这个缺口的。它是一份放在工作区里的纯文本手册，作为社区约定被多家 agent 工具采纳，OpenClaw 在会话启动的引导阶段会把它注入上下文。它和 README 面向人类读者不同，是写给 AI 的：短句、祈使、可判定。

# 问题：三种典型的失控

1. **约定靠聊天记录续命。** 每个新会话都要重新交代一遍目录结构、启动命令、风格偏好，交代漏一条，agent 就按自己的默认习惯来。
2. **行为不可预测。** agent 自作主张执行 `git reset --hard`、把临时脚本写进仓库根目录、用没装过的依赖。
3. **引导文件打架。** OpenClaw 工作区里 SOUL.md 管人格，TOOLS.md 管工具说明，MEMORY.md 管长期记忆。如果没有一份明确的「操作守则」，多处指令冲突时 agent 只能猜。

# 做法：从二十行写起

**第一步，先定位。** AGENTS.md 只写「影响每一次任务执行」的内容。一次性任务交给会话，长文档放别的文件，这里只留路径让它按需去读。

**第二步，建骨架。** 一个够用的最小模板：

```markdown
# 项目地图
- core/ 调度逻辑；plugins/ 插件；scripts/ 运维脚本
# 常用命令
- 测试：pnpm test（不要用 npm）
# 硬性规则
- 不执行 rm -rf、git push --force；删除类操作先向用户确认
- 新增依赖必须同步进 README 依赖表
- 进入子项目目录时，先读该目录下的 AGENTS.md
```

**第三步，控制篇幅。** 建议 150 行以内。上下文是稀缺资源，写得越长，单条规则的权重被稀释得越厉害。

**第四步，分层放置。** 工作区根目录放全局守则，子项目目录放细化规则，并在根文件里写明读取顺序，避免子项目约定覆盖不了全局约定。

**第五步，版本化并定期校验。** 把 AGENTS.md 纳入 git，和代码一起评审。校验方式很朴素：新开会话，直接问 agent「这个仓库怎么跑测试」「改完代码要做什么」，答错即文档过期。

# 踩坑点

- **写成散文。** 大段背景介绍没人读，agent 也一样。规则要短、可判定，「注意安全」等于没写。
- **写入机密。** AGENTS.md 会进入模型上下文，token、内网地址、密码不要放，泄密路径最短的就是这条。
- **规则互相冲突。** SOUL.md 要求谨慎确认，AGENTS.md 要求自动执行，agent 只能随机站队。定期通读全部引导文件，保证口径一致。
- **指望它兜底安全。** AGENTS.md 是提高遵守概率的约束，不是沙箱。高危命令要靠权限边界和沙箱挡，文档只做第一道提醒。
- **过期比缺失更糟。** 目录改名后忘更新，agent 会理直气壮地走老路，还显得很有依据。

# 可复用建议

- 一条规则一年用不上三次，就别放进来。
- 用祈使句加具体命令，不用形容词。
- 「为什么」放进长文档，「做什么」留在 AGENTS.md。
- 把 agent 每次犯的错沉淀成一条新规则，这份手册会逐步长成你最值钱的配置文件。

# 总结

AGENTS.md 的价值不在写了什么漂亮话，而在把个人或团队的工程约定从聊天记录里搬进版本库，变成 agent 每次开机都能读到的确定性输入。先从二十行写起，让它跟着真实错误生长，比一次性写一份完美手册有效得多。
