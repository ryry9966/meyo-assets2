## 背景

OpenClaw 的 agent 在工作区里有真实的执行能力：读写文件、跑 shell、调用 MCP 工具和插件。能力越大，“它不知道本地约定”的问题越明显。AGENTS.md 就是为此存在的约定：在工作区根目录放一份 Markdown，agent 接任务时自动读取，把它当作这份工作空间的使用手册。它不是 OpenClaw 专属，而是跨工具的开放惯例，但 OpenClaw 初始化工作区时已经放了一份默认模板——很多人的问题只是从没打开过它。

## 问题

没有维护 AGENTS.md 时，常见症状：

- 每次会话都口头重复“测试命令是 xxx”“docs/ 别动”；
- agent 自作主张改了生成文件或锁文件，diff 一塌糊涂；
- 团队里每人一套提示词，agent 行为因人而异；
- 同样的坑反复踩，经验没有沉淀。

本质是：项目知识散落在人脑和聊天记录里，没有落成 agent 可稳定消费的形式。

## 做法

1. 打开工作区根目录的 AGENTS.md（如 `~/.openclaw/workspace/AGENTS.md` 或项目工作区），默认模板只是骨架，必须本地化。
2. 控制在一百行以内，六段结构：项目概览 / 目录关键点 / 常用命令 / 代码与提交规范 / 禁区 / 异常处理。
3. 命令必须可直接复制执行，写 `pnpm test --filter core`，不要写“运行测试”。
4. 禁区写具体：`migrations 已有基线，禁止新增文件`、`禁止 git push --force`。
5. 约定工具边界：哪个 MCP server 只读、哪类操作执行前需向人确认。
6. 某个子目录规则更细时，在该目录再放一份，就近生效。
7. 纳入版本控制，像代码一样走 review；agent 犯一次错，就补一条对应规则。

## 踩坑点

- **写太长。** 上下文虽大但注意力有限，塞成百科全书反而稀释关键规则。保持精炼，细节让 agent 按需读链接文档。
- **照抄 README。** README 面向人类理解，AGENTS.md 面向执行：命令、边界、禁忌，概念解释一概不要。
- **规则不可执行。** “代码要优雅”没用，“commit message 遵循 conventional commits”才有用。
- **硬编码敏感信息。** 密钥只写位置和策略：`凭据在 .env，禁止读取并输出内容`。
- **文档腐化。** 写完就不管，三个月后全是过期命令。建议每次发版 review 一遍。

## 可复用建议

- 用六段模板起步，先窄后宽，只写“agent 真的会做错”的事。
- 把散落在 system prompt、个人 rules 里的项目级约定迁进来，个人偏好与项目约定分离。
- 让 agent 参与维护：修完 bug 后让它提议一条防再犯规则，人工审核合入，这个闭环很有效。
- 多个工作区有共同习惯时，抽公共段落做成 snippet，各处按语境微调后粘贴。

## 总结

AGENTS.md 是性价比极高的基础设施：一个 Markdown 文件，换来 agent 行为的可预测和团队经验的沉淀。它的价值不在初始写得多全，而在持续迭代——把每次踩坑变成一条规则。把它当代码对待，agent 才会像同事一样可靠。
