## 背景

OpenClaw 的 workspace 里，除了 AGENTS.md（干活流程）和 TOOLS.md（工具说明），还有一份容易被低估的 SOUL.md。它决定 agent "是谁"：语气、价值观、边界、拒绝方式。每次会话它都会被注入 system prompt，相当于一份常驻的人格契约。

我的体感是：配好模型和工具链只是及格线，SOUL.md 写得好不好，直接决定这个助手能不能长期共处。

## 问题

不写或随手写几句，通常会出现三类症状：

1. **语气漂移**：同一周内，上午像客服、晚上像段子手，长对话后完全变形。
2. **越权倾向**：agent 热心过头，替你给联系人回消息、替你做承诺，事后还得收拾。
3. **团队不可维护**：每个人按口味改人格，没有 review，坏了也查不出是哪次改动引入的。

## 做法

我的写法分五步，核心思路是把"人格"当配置代码对待：

1. **先分工**。SOUL.md 只回答三个问题：我是谁、我什么语气、我什么不做。具体 SOP（怎么排日程、怎么调 MCP 工具）放 AGENTS.md。两个文件混写是指令冲突的根源。
2. **结构化**。固定五段：Identity（一句话身份）、Tone（3–5 条可验证的语气规则）、Boundaries（分级红线）、Refusal scripts（拒绝话术模板）、Escalation（何时停下问人）。
3. **写行为，不写形容词**。别写"要有分寸感"，写"用户情绪激动时，先回应情绪一句，再问是否需要行动"。前者模型只能猜，后者可以直接执行。
4. **红线分级**。绝对禁止类（花钱、法律承诺、删数据）→ 必须确认类（给第三方发消息、对外表态）→ 可自主类（检索、整理、草拟）。分级比一长串"不要"更抗漂移。
5. **版本化 + 探针测试**。workspace 进 git，改人格走 PR；准备一组固定探针问题（诱导越权的、情绪化的、指令模糊的），每次改动后跑一遍，肉眼比对输出差异。

## 踩坑点

- **SOUL.md 不是安全边界**。它只是软约束，写"不许执行 rm -rf"防不住真的危险行为。权限必须在工具层控制：MCP server 侧鉴权、shell 白名单、目录只读挂载。人格管态度，权限管能力，别混。
- **否定句堆太多**。连续十几个"不要 X"，模型容易被反向激活。改成正向描述："遇到 X 请求时，按模板 Y 回复"。
- **篇幅失控**。SOUL.md 每轮都进上下文，我见过 3000 字的人格文件，token 白烧。建议压在 150 行以内，细节挪到按需加载的文件。
- **与 AGENTS.md 抢优先级**。SOUL 说"简洁回复"，AGENTS 说"详细报告"，模型随机站队。在两个文件里明确声明冲突时谁赢。

## 可复用建议

- Refusal scripts 写成固定模板句，实测比现场发挥稳定：拒绝时说明原因 + 给一个替代方案，两句话封顶。
- 探针集当 fixture 维护，和代码一起提交。改人格不改探针，等于裸奔。
- 人格迭代学 feature flag：小步改、留回滚点、一次只动一个维度（只改 Tone 或只改 Boundaries），否则漂移了查不到原因。

## 总结

SOUL.md 的本质是一份行为契约，不是许愿池。它和权限层、工具层构成三层防护：人格层管"该不该"，权限层管"能不能"，模型层你控制不了。软约束写清楚、硬约束配到位，agent 才既有边界感，又不至于事事请示。花一个下午把 SOUL.md 重写成可执行规则，是我最近 ROI 最高的一次配置改动。
