## 背景

用 AI 写代码之后，产出速度上来了，提交纪律反而塌了。一个下午改十几个文件，commit message 全是 "update"、"fix again"，分支开了忘删，回头看历史自己都读不懂。OpenClaw 的 agent 本来就能执行受控命令、能接 MCP 工具，与其人肉兜底，不如把 Git 流程里的一部分交出去。

## 问题

手工处理有三类典型痛点：

1. **提交粒度失控**：AI 的改动是一波一波产出的，人容易积攒到深夜一次性 commit，diff 巨大没法 review；
2. **规范难维持**：Conventional Commits、分支命名前缀这些事，靠人记迟早漂移；
3. **分支垃圾堆积**：已合并的分支、过期 stash，永远没人清理。

## 做法

我在自己的 OpenClaw 实例里搭了一个最小可用的 Git 自动化流程，四步：

**第一步：给能力，但给小。** 通过 MCP 的 git server（或受控 shell）暴露 Git 操作，默认只放行 `status / diff / log / add / commit / branch` 这类低危命令；`push`、`reset`、`rebase`、`clean` 全部进"需人工确认"名单。

**第二步：把规范写进仓库，而不是写进提示词。** 在项目根目录放一份给 agent 读的说明文件：commit 格式用 Conventional Commits，分支用 `feat/`、`fix/` 前缀，每个逻辑单元一次提交，提交前必须先跑 lint 和测试。规范从"人的记忆"变成"仓库的一部分"，换模型、换工具都不用重写。

**第三步：设人工闸门。** 本地 commit 允许 agent 自动完成；push、开 PR、动 main 分支必须停下来问一句。这条在系统级配置里写死，实测能挡住绝大多数危险操作。

**第四步：周期性清理。** 给 agent 加一个定时任务：每周列出已合并分支和超过 30 天未动的分支，生成清单，人确认后批量删除。

## 踩坑点

- **过度提交**：最初 agent 每改一个小文件就 commit，一天几十个提交，历史直接被冲烂。改成"完成一个任务单元且测试通过才提交"才恢复。
- **message 与 diff 不符**：agent 偶尔会"脑补"提交内容，写出来的描述和实际改动对不上。要求它提交前先输出 diff 摘要自行核对，才压住。
- **权限过大出过事故**：早期图省事直接给了完整 shell，agent 处理冲突时自己跑了 `git reset --hard`，丢了半小时工作。之后坚决走命令白名单。
- **多任务共用工作区互相踩**：两个任务并行改同一个目录，状态混乱。用 `git worktree` 给每个任务独立目录后问题消失。

## 可复用建议

- 规范放仓库里，不要散落在 agent 配置里，可移植性最好；
- 权限按"读默认放开、写按任务授予"原则，危险命令宁可多确认一次；
- 让 agent 把每次 Git 操作追加写入日志文件，出问题能审计；
- 自动化边界画在**可逆性**上：可逆操作（commit、建分支）放手让它做，不可逆操作（push、reset、删分支）留给人。

## 总结

让 AI 助手管 Git，不是为了炫技，而是把提交粒度、命名规范、分支清理这类"低判断力、高纪律性"的工作交出去，人只在不可逆节点做决策。跑了几周下来，提交历史干净了，review 负担明显变小。最大的体会是：给 agent 的权限越小、规则写得越明确，它反而越可靠。
