## 背景

过去一年我把大部分自动化流程跑在云端 API 上，但有两类场景始终不顺手：一是自动化脚本要处理家庭照片、日程、笔记这类私密数据，全部发出去心里不踏实；二是 agent 高频调用的小任务（摘要、分类、格式转换），按 token 计费月底账单不好看。于是尝试把一个中等规模的模型搬回家里那台带显卡的台式机，作为 agent 的默认后端。跑了两个多月，记录一条可复制的路径。

## 问题

家用硬件跑本地模型，卡点不在"能不能跑起来"，而在三个工程问题：

1. 显存/内存预算与模型尺寸的匹配；
2. 量化档位的选择，直接决定工具调用的可靠性；
3. 小模型当 agent 后端时，function calling 的稳定性远低于云端旗舰模型。

## 做法

**第一步，盘点硬件。** 我的机器是 32GB 内存 + 12GB 显存。经验公式：Q4 量化的 7B 模型约占 5GB，14B 约占 9GB，再留三成给 KV cache 和运行时开销。12GB 显存跑 14B-Q4 刚好压线。

**第二步，选运行时。** 图省事用 Ollama，一条命令拉模型且自带 OpenAI 兼容接口；要精细控制采样参数和 prompt 模板就上 llama.cpp；显存 24GB 以上且有并发需求再考虑 vLLM。我最终固定在 Ollama，因为 agent 侧只依赖 OpenAI 兼容协议。

**第三步，选模型。** 中文场景下 Qwen2.5-7B/14B-Instruct 是稳妥起点，推理需求可试 DeepSeek-R1-Distill 系列。起步一律 Q4_K_M，先跑通再谈升档。

**第四步，接入 agent。** 在 OpenClaw 的模型配置里把 base URL 指向本地端点，模型名填 Ollama 里的 tag。MCP 工具链不用改，请求仍走原来的工具调用协议。

**第五步，真实任务验证。** 不要跑通用 benchmark，直接让 agent 执行你日常的 10~20 个真实任务，记录成功率和 token/s。

## 踩坑点

- **上下文长度是显存杀手。** 默认 4K 上下文很安静，一旦把 num_ctx 拉到 32K，KV cache 直接把显存顶爆，进程被 OOM 杀掉。长文档任务改用分段摘要，而不是无脑加长上下文。
- **量化不是免费午餐。** Q4_K_M 以下（Q3、Q2）模型在结构化输出上明显退化，会出现 JSON 截断、漏调参数。宁可换小一号的模型，也别用太狠的量化。
- **并发基本是 1。** 消费级显卡跑本地推理，agent 并行调用多个工具时会排队。超时配置要放宽，或在 agent 侧改成串行执行。
- **小模型会"幻觉式调用"。** 7B 模型偶尔编造不存在的工具参数。对策是工具描述写得更严格，系统提示里给一两个调用示例，必要时在插件层做参数校验兜底。
- **散热。** 连续推理两小时后，我的卡降频约 15%，token/s 掉得肉眼可见。压好功耗墙比堆参数更实际。

## 可复用建议

- 建一个本地评测集：20 条你的真实任务，每次换模型或量化跑一遍，比看任何榜单都有用。
- 做混合路由：分类、摘要走本地，复杂规划走云端 API，agent 侧一个路由函数就能实现。
- 固定"模型 + 量化 + 运行时版本"的组合并写进文档，升级前先跑评测集回归。
- 把 token/s 和显存占用打进日志，问题往往先在这两个指标上露头。

## 总结

家用电脑跑本地 LLM 在今天已经不是玩票：7B~14B 的 Q4 量化模型完全够承担 agent 的高频小任务，隐私数据不出门，边际成本为零。但它替代不了旗舰模型的规划能力，正确的姿势是本地模型干体力活、云端模型干脑力活。先用真实任务验证，再谈规模化——这条路径在家用硬件上是成立的。
