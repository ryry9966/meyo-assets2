## 背景

最近半年，我把一个长期运行的 Agent 从“全家桶式”配置迁到了 Skills 机制。之前的做法很典型：所有 MCP server、全部工具说明、所有业务规则，一股脑塞进系统提示词。Agent 一启动，上下文里就背着几十个工具定义和上万字的操作手册。

小规模时没问题，但工具一多就开始出状况：模型在无关任务里频繁误触工具、单次请求的 input token 明显膨胀，排查问题时也很难还原“模型当时到底看到了什么”。

## 问题

核心矛盾是：能力的**声明**和能力的**使用**耦合在一起。哪怕 99% 的会话用不到某个技能，它的完整说明也始终占着上下文。这不只是费钱——指令越多，单条指令被遵守的概率越低，这是实际踩出来的教训。

Skills 机制解决的就是这件事：把能力拆成独立单元，启动时只注册“目录”，用到了才展开“正文”。

## 做法

**1. 拆分技能单元。** 每个技能一个目录，入口是带 frontmatter 的说明文件（name + description），旁边放可选的脚本、模板和参考文档。比如 `pdf-processing/`、`db-ops/`、`report-gen/` 各自独立，互不依赖。

**2. 利用三级渐进加载。** 启动时只有各技能的 name + description 进入上下文（单个几十 token）；模型判断当前任务命中某技能，才去读它的完整说明；说明里引用的脚本和子文档，到执行时才读。单技能成本从“常驻”变成“按需”。

**3. 确定性操作写成脚本。** 之前让模型每次现场写导出 SQL、拼报表格式，改成脚本后，技能说明里只保留“何时调用、参数含义、异常如何处理”。模型负责判断，脚本负责执行，稳定性提升明显。

## 踩坑点

- **description 写得太笼统。** 早期我写了“处理文档相关任务”，结果几乎从不触发。改成“当用户要求合并/拆分 PDF、提取表格、批量加水印时使用”，命中率立刻上来。description 是路由键，值得花时间打磨。
- **一个 SKILL.md 塞所有细节。** 正文超过几百行后，模型经常漏读后半段。解法是正文只留核心流程，长尾细节拆到 `references/` 下的子文档，按需再读。
- **技能边界重叠。** “数据导出”和“周报生成”都声明能处理 CSV，模型会随机选。后来明确划界：导出只管取数，周报只管编排，互相引用而不是重复声明。
- **文档与脚本漂移。** 脚本改了参数、文档没跟上，模型按旧文档调用直接报错。现在脚本变更和文档更新强制走同一个 PR。

## 可复用建议

- 把 description 当搜索关键词写：包含具体动词、文件类型、触发场景，必要时写清“何时不该用”。
- metadata 层本身也是成本，技能总量要控制，长期不触发的果断删。
- 宁可多个小技能，不要一个大而全的技能。
- 新技能上线前，拿十几条真实历史提问做回归，观察触发是否符合预期。

## 总结

Skills 机制本质上是给 Agent 的上下文做预算管理：声明常驻、内容按需、执行走脚本。迁移后我们系统提示词的固定开销降了一个量级，工具误触率也明显下降。它不算新范式，更像是对提示词工程做了一次模块化重构——而模块化的收益，做过工程的人都懂。
