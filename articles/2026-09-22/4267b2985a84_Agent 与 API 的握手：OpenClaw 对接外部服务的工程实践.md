## 背景

Agent 的价值不在"会聊"，而在"能做事"。一个只能操作沙箱内文件的 agent 只是离线助手；一旦能查工单、写数据库、调第三方服务，才算进入真实业务。在 OpenClaw 里，对接外部服务主要走两条路：写插件 / 自定义 tool，或者起一个 MCP server 把能力标准化暴露出去。这篇帖子聊的是：无论走哪条路，"握手"阶段该做对哪些事。

## 问题

我们第一次让 agent 调真实 API 时踩了三类坑：

1. 模型传参经常错，比如把分页的 `limit` 传成带单位的字符串；
2. 接口超时或限流时，agent 拿着报错原文也能编出一个"操作成功"；
3. 密钥管理混乱，日志里直接打出了 Authorization 头。

复盘下来，这些都不是"模型不够聪明"，而是接口层没设计好。Agent 调 API 不是简单的 HTTP 请求转发，而是一次双向契约：你给模型的工具语义有多清晰，它的调用就有多可靠。

## 做法

1. **先选接入方式**。只给单个 agent 用的能力，直接写 tool；要跨多个 agent 或客户端复用，就封装成 MCP server。MCP 的好处是 schema、能力发现、权限边界都有标准，生态里也更容易被人复用。
2. **把 tool schema 当 API 文档写**。每个参数写清类型、单位、可选值；描述里写"这个工具做什么、什么时候该用"。模型读的就是这段文字，写得含糊它就靠猜。
3. **认证与密钥**。密钥走环境变量或 secret manager，由 MCP server / 插件层持有，agent 侧不接触凭证。日志脱敏是底线，不是加分项。
4. **错误语义对模型友好**。超时、限流、参数错误要能区分，统一返回 `{code, message, hint}` 三字段，别把 HTML 错误页原样丢给模型——它真的会引用里面的内容作答。
5. **超时与重试**。所有出站调用设显式超时；只对幂等操作自动重试并加指数退避。非幂等操作（下单、发消息）要么要求服务端支持幂等键，要么把失败交还模型决策。
6. **返回裁剪**。大 JSON 在 tool 层先做字段筛选和摘要，别让一次查询吃掉半个上下文窗口。
7. **先 mock 后真打**。用本地 mock server 跑通全部路径（成功 / 超时 / 429 / 500），确认 agent 行为符合预期，再切真实环境。

## 踩坑点

- 描述里只写"查询订单"，模型就会拿它去做删除操作。边界要显式写"只读"，能用 MCP 的 readOnly 注解就加上。
- 分页接口不设上限，模型会自己翻 100 页，一晚上烧掉配额。
- 重试不加退避，429 直接打成 503，服务方直接封 key。
- 把底层异常堆栈原样返回给模型，它会把堆栈内容当成事实复述给用户。

## 可复用建议

- 每个对外 tool 三件套：显式超时、幂等策略、脱敏日志。
- schema 描述里固定加一句"何时不应使用本工具"。
- 接入新服务时，先写一个 5 分钟能跑通的 curl 脚本验证鉴权和关键接口，再动手写 tool。
- 给每个 tool 建一个最小 mock 用例集，放进 CI，schema 改动时同步更新。

## 总结

Agent 对接外部服务，工程上的重点不是"能不能调通"，而是把 schema、错误语义、超时重试、密钥管理这四件事做扎实。OpenClaw 提供了 tool 和 MCP 两条路，但握手质量取决于你自己写的那一层。把契约写清楚，agent 才能在真实 API 世界里稳定伸手。
