# 背景

Agent 和 MCP 工具链跑起来之后，很多人会遇到三件烦心事：API 账单随调用量线性上涨、敏感数据不想出本机、自动化任务被速率限制卡脖子。本地部署 LLM 能一次性解决这三个问题——数据不出门、没有配额、断网也能跑。但对 Agent 场景来说，本地化的要求比"能聊天"高得多，这篇文章记录我在一台 32GB 内存 + 12GB 显存的家用机上跑通的完整流程。

# 问题：聊天能用 ≠ Agent 能用

Agent 对模型的要求和聊天完全不同：

- **稳定的 function calling**：工具调用 JSON 格式错一点，整条链路就断；
- **足够长的上下文**：多轮工具返回结果塞进 prompt，几轮就爆；
- **一定的并发能力**：并行调工具时不能排队等到超时。

家用硬件又限制了模型上限。这三组矛盾是本地部署真正的难点。

# 做法

**1. 盘点硬件，算显存账。** 经验值：Q4_K_M 量化的 7B 模型约需 5–6GB 显存，14B 约 10–12GB，再给 KV cache 留 20–30% 余量。纯 CPU 能跑，但 10 tokens/s 以下时多轮 Agent 任务会慢到不可用。

**2. 选运行时。** Ollama 上手最快，llama.cpp 的 `llama-server` 参数更可控，vLLM 需要较好的卡。三者都提供 OpenAI 兼容端点，对上层透明。

**3. 选模型。** 只考虑原生支持 tool use 的系列（Qwen、Llama 3.1 这类社区验证充分的），量化从 Q4_K_M 起步。别追最新发布，先选踩坑记录多的。

**4. 起服务，显式设参数。**

```bash
OLLAMA_NUM_PARALLEL=2 ollama serve
# 拉起模型后务必设置上下文长度
```

**5. 接入 OpenClaw。** 把 base_url 指到 `http://127.0.0.1:11434/v1`，模型名对应即可。RAG 场景把 embedding 模型也本地化（bge-m3 之类），避免链路里混着一次外部调用。

**6. 用真实任务验收。** 挑一个带 MCP 工具调用的典型任务跑 10 轮，统计 JSON 解析失败率和死循环率，比任何 benchmark 都诚实。

# 踩坑点

- **上下文默认值是隐形杀手**。Ollama 默认 `num_ctx` 很小，工具结果一塞就静默截断，表现为模型"失忆"或开始编造。必须显式设到 8192 以上。
- **小模型的 function calling 不稳**。温度降到 0.1–0.3，Agent 侧加 JSON 校验和重试，能救回大半。
- **量化损失对结构化输出比对聊天敏感**。Q4 以下慎用；对路由、抽取这类关键节点，宁可换小一号模型上 Q6/Q8。
- **内存超卖触发 swap**。chat 模型和 embedding 模型同时常驻容易爆，用 `keep_alive` 控制驻留，别让系统开始刷盘。
- **默认串行推理**。Agent 并行调工具会排队，注意 `OLLAMA_NUM_PARALLEL` 和显存的平衡。

# 可复用建议

1. 先跑通最小链路（一个 7B + 一个工具），再谈升级，不要一上来就堆多模型编排；
2. 用真实 Agent trace 评估，不用跑分软件；
3. 把模型拉取、参数配置、服务启动写成脚本或 docker-compose，坏了一键重建；
4. 确有需要再分层——小模型做路由和摘要，大模型做规划——但单模型方案能撑住就别加复杂度。

# 总结

本地部署的核心不是"能跑起来"，而是"能稳定服务 Agent"。预算显存、选对量化、显式设上下文长度、用真实任务验收——四步走完，7B–14B 的本地模型足以覆盖大量自动化场景。剩下的瓶颈，交给下一轮硬件升级或者模型迭代。
