## 背景

订阅源没有死，只是读不过来了。我长期订阅了 40+ 个 RSS 源，过去靠碎片时间扫标题，信噪比很低。LLM 摘要的成本降下来之后，"让 agent 先读一遍、人只看结论"这件事终于可行了。这篇记录我用 OpenClaw 搭的管线：定时拉取 → 过滤去重 → 分级摘要 → 推送频道，核心逻辑加起来不到 200 行。

## 问题

三个核心痛点：

1. **量**：每天 200+ 条更新，人工扫不过来；
2. **噪**：同一条新闻被五六个源先后转载；
3. **泛**：直接丢给模型"帮我总结"，产出千篇一律，等于没读。

## 做法

整体分四步，全部跑在 OpenClaw 的工作区里：

**1. 源管理。** 用一个 YAML 文件维护订阅源，分"必读""扫描""观察"三档，不同档位走不同的摘要策略。

**2. 定时拉取。** 用 OpenClaw 的 cron 定时任务每小时触发一次 agent，通过 RSS 的 MCP 工具拉增量，落盘成 JSONL（标题、链接、正文、时间）。原始数据一定要存，后面调提示词全量重跑全靠它。

**3. 两级过滤。** 第一级是规则：标题哈希去重、关键词黑名单、来源权重打分，先砍掉七成；第二级用嵌入相似度，把同一事件的多篇报道聚成一簇，只留信息量最大的一篇进摘要。省 token，也省注意力。

**4. 分级摘要 + 推送。** 必读源逐篇生成三句话摘要（是什么 / 为什么重要 / 对我的影响）；扫描源只进日报，由模型把当日条目压成十条以内的卡片。最后经推送插件发到 Telegram 频道，附原文链接。

## 踩坑点

- **摘要源只给摘要**：不少博客 RSS 只有前 200 字，直接总结等于二创。现在检测到正文过短就走 readability 抓网页正文，抓不到就标记"信息不足"——宁可少一条，也不编。
- **HTML 直接进模型**：早期把原始 HTML 喂给模型，token 直接爆。先剥标签、截断到 2000 字符。
- **定时任务重叠**：抓取慢的时候下一轮 cron 又起了，造成重复推送。加了个简单的文件锁解决。
- **时区与编码**：pubDate 格式五花八门，GBK 编码的老源还在。统一在落盘前转 UTC + UTF-8。
- **提示词比模型重要**：换更强的模型，提升有限；把提示词从"总结这篇文章"改成"这是给做后端开发的我看的，只保留会影响我决策的信息"后，效果立竿见影。

## 可复用建议

- 先跑通"5 个源 + 每日日报"的最小闭环，再扩规模。一上来挂 40 个源，只会收获一堆没人看的摘要。
- 把拉取、过滤、摘要拆成独立的 MCP 工具，agent 只负责编排，其他 agent 也能直接复用。
- 中间产物全部落盘成结构化文件，换模型、改提示词后可以全量重放对比。
- 保留原文链接。摘要永远是索引，不是替代品。

## 总结

这条管线最大的价值不是"省时间"，而是把阅读从被动刷变成主动收：每天早上十分钟扫一遍日报，值得深入的点进去看原文。回头看，整套东西里没有一行"智能"代码是必需的——规则过滤占了大头，AI 只在最后一步发力。这也是我做自动化的一贯体会：先把工程做扎实，模型才有用武之地。
