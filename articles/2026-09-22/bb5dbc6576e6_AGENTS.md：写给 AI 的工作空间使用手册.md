## 背景

用 OpenClaw 这类长期驻留的代理，工作区（workspace）就是它的工位。但用得越久越能感觉到一个问题：**代理每次会话都是一次冷启动**。它不知道构建用 pnpm 还是 npm，不知道测试怎么跑，不知道 `generated/` 目录是脚本产物不能手改。这些信息对人是常识，对 AI 是空白——每个新会话都要重新摸索一遍。

OpenClaw 的解法很朴素：工作区根目录放一个 `AGENTS.md`，每次会话启动时自动读入上下文。它就是写给 AI 的操作手册。

## 问题

没有这份手册时，我们的现状是典型的知识散落：构建命令在 README 第三节，提交规范在 CONTRIBUTING，“别动那个目录”只在群里口头说过。README 是写给人类的导览，回答“这是什么”；代理需要的是“在这里怎么干活”。于是代理反复踩同样的坑，用户反复纠正同样的事，最后只能在 system prompt 里堆一段复制粘贴的说明——换工具就失效，改流程就过期。

## 做法

我们的落地步骤，按优先级排：

1. **先写最影响正确性的三样**：构建、测试、lint 的确切命令。必须实测可跑，写“通常用 pnpm test”不如写清带参数的完整命令。
2. **写约束，不写介绍**。代理不需要项目愿景，需要红线：不要手改生成物、不要主动升级依赖、commit message 格式、哪些目录禁止触碰。
3. **分层放置**。工作区根目录放全局约定，子项目目录里放局部特例，代理干活时会就近读取。
4. **控制篇幅**。我们压在 60 行以内，每条一行说清、可验证。
5. **纳入版本管理，走 review**。流程变了就同步改，把它当 CI 配置对待。

## 踩坑点

- **命令过期是最大的坑**。代理会忠实执行错命令，比没有手册更糟。我们已把“改了构建流程必须同步 AGENTS.md”写进 PR 检查项。
- **写太长会稀释注意力**。上下文预算有限，长文反而导致关键条目被漏读。删掉所有“欢迎贡献”式的客套。
- **和 README 冲突**。两边构建方式不一致时，代理可能随机选一个。约定冲突时以 AGENTS.md 为准，但最好别制造冲突。
- **别写密钥和内网地址**。它会进 git 历史，也会进模型上下文。
- **子模块特例只写在根目录等于没写**。代理在子目录干活时看不到，照样踩坑。

## 可复用建议

- **起步不必完美**：先写 10 行能跑的命令，之后代理每踩一个坑就补一条，两周基本收敛。
- **让代理起草初稿**：扫一遍工作区结构自动生成，人工修剪事实错误，效率很高。
- **用“事实 + 命令”格式**，避免形容词。每条内容都应能被一条终端命令验证。
- **当团队口头约定的沉淀处**：以前在群里说的规矩都写进去，新人和新代理同时受益。

## 总结

AGENTS.md 的价值不在文件本身，而在于把隐性工程知识显性化、可版本化。成本极低——一个 Markdown 文件——但直接决定了代理每次干活的质量下限。我们的经验就一句话：先跑起来，再迭代，把它当成工作区基础设施的一部分来维护。
