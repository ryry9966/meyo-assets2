## 背景

我们组的日报数据散在三处：git 提交记录、服务错误日志、任务看板的变更。以前的做法是每天下班前花二十分钟人工拼一份，费时、口径不稳定，还经常漏掉当天的异常。OpenClaw 本身具备 cron 触发、插件采集和 MCP 工具调用能力，我花了一个周末把这件事改造成流水线，稳定跑了一个多月，这里把设计和踩过的坑记录下来。

## 问题：为什么不能直接把日志丢给 Agent

第一版很朴素：定时任务把当天原始日志拼成一大段文本，扔给 Agent 说"总结一下"。跑了两天就暴露三个问题：

- **上下文放不下**。一天的 access log 轻松几十万行，截断后信息失真；
- **数字不可信**。模型会"合理地"编造汇总数字，格式每次也不一样；
- **不可复现**。同一天的日志跑两次，产出两份不同的报告，没法追溯。

结论很明确：原始日志是给脚本看的，不是给模型看的。

## 做法：四段式流水线

原则一句话：**数字由脚本算，文字由 Agent 写**。

1. **采集**：cron 在每天固定时间触发，脚本分别拉取三个数据源的当天增量，落盘为中间文件；
2. **结构化**：纯脚本做过滤、去重、聚合，产出固定 schema 的 JSON——提交列表、Top 5 错误及次数、关键指标快照。这一步没有任何 LLM 参与；
3. **叙述生成**：Agent 通过 MCP 只读这个 JSON，只负责组织语言、给异常段写归因提示，禁止自行计算或补数；
4. **校验与投递**：JSON Schema 校验关键字段，套模板后推送到群和邮件；失败自动重试一次，仍失败则单独告警。

## 踩坑点

- **时区错位**。cron 跑在 UTC，日志时间戳是本地时间，统计窗口错位，日报连续几天"少一天的数据"。后来统一在采集脚本里把时间转成带时区的 UTC 再切窗口。
- **格式漂移**。模型偶尔自作主张把正文改成表格。解法是给两个 few-shot 样例，加上校验失败自动重试，基本压住了。
- **Agent 想自己查数**。中间有一版给 Agent 配了查询工具，它兴致勃勃去"核实"，结果数字和脚本对不上。改成 MCP 侧只暴露一个只读 JSON 读取工具，权限收死。
- **静默失败**。流水线挂了一周没人发现——没有报错，只是没产出。补了一条心跳规则：超过约定时间群里没收到日报，机器人自己发告警。

## 可复用建议

- 先用单一数据源跑通全链路，再横向加源；每加一个源只扩 JSON schema 的一个字段，保持向后兼容；
- 中间 JSON 落盘保留七天，出问题可回放，定位是采集、聚合还是生成环节的锅；
- LLM 的输出永远不当事实源，只当"翻译层"；
- 给流水线本身打日志：每次运行的输入行数、耗时、重试次数，这是排障的第一入口。

## 总结

这条流水线的价值不在于"Agent 变聪明了"，而在于把 Agent 放到了正确的位置：确定性的事交给脚本，语言组织交给模型，校验和告警兜底。日报只是第一个场景，同一套骨架我已经复用到周报汇总和告警摘要上，改动基本只在结构化那一段。
