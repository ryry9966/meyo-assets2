## 背景

OpenClaw 本质上是个调度器：理解意图、拆任务、决定调用什么工具。但 Agent 的真正价值不在调度本身，而在它能触达多少外部服务——查订单、提工单、跑脚本、调内部系统。对接外部 API 这件事，看起来只是"发个 HTTP 请求"，实际是整条链路里最容易出事故的一环。

## 问题

直接让 Agent 裸调 API，通常会撞上四类问题：

1. Agent 自己拼 URL、拼参数，错一次就错得莫名其妙；
2. 返回的 JSON 一股脑塞进上下文，几百 KB 的响应直接把对话撑爆；
3. 调用失败后 Agent 自作主张重试，碰上非幂等接口就是重复下单、重复发消息；
4. 密钥散落在配置文件甚至提示词里，谁来都能看到。

## 做法

我们的经验是分四步走：

**第一步：选对接形态。** 优先考虑 MCP server——标准化、可复用，社区已有大量现成实现；有深度定制需求（维护会话态、复用内部 SDK）再写原生插件；简单的只读接口可以直接注册成 HTTP 工具。别一上来就造轮子。

**第二步：暴露语义化工具，而不是裸接口。** 不要给 Agent 一个 `get("/api/v2/orders?id=...")`，而是封装成 `query_order(order_id)`。工具描述里写清楚：什么时候该用、参数含义、返回什么。Agent 的调用准确率几乎完全取决于工具描述的质量。

**第三步：在工具层做减法。** 裁剪返回字段、强制分页、必要时先摘要再返回。原则是：给 Agent 看的数据，够做决策就行，不求全。

**第四步：鉴权和重试收进工具层。** API key 放环境变量或凭据管理，token 刷新在工具内自动完成；重试只对幂等操作开启，遇到 429 做指数退避，超时设置成显式参数。

## 踩坑点

- **工具描述含糊**：描述里没写"仅在用户明确要求时调用"，Agent 就会在无关对话里乱触发；反过来写得太窄，它又不敢用。描述要经过几轮真实对话打磨，不是一次写完就完事。
- **非幂等 + 自动重试**：发通知类接口被重试两次，用户收到三条一样的消息。写入类工具要么自带去重键保证幂等，要么显式禁止框架层重试。
- **响应体失控**：一个列表接口默认返回 500 条记录，直接把上下文打满。分页参数要写死在工具内部，不能指望 Agent 每次都记得传。
- **缺 dry_run**：上线初期建议所有写入类工具都带 `dry_run` 参数，先让 Agent 打印将要执行的操作，人工确认后再放开。

## 可复用建议

1. 先只读、后写入，按风险分级逐步放开权限；
2. 一个工具只做一件事，粗粒度的复合操作拆开，Agent 自己会编排；
3. 每次工具调用记日志：入参、耗时、状态码——出问题时这是唯一的排查入口；
4. 优先 MCP，除非有明确的定制理由。

## 总结

Agent 对接外部服务，核心不是"能调通"，而是把鉴权、限流、重试、数据裁剪这些工程细节都收进工具层，给 Agent 留一个语义清晰、行为可控的接口面。握手协议定得越干净，Agent 的自由度才越有价值。
