## 背景

Agent 框架跑起来之后，最先遇到的天花板往往不是模型能力，而是"手够不够长"。模型能推理，但查订单、发工单、拉监控数据，最终都要落到一次真实的 HTTP 调用上。OpenClaw 的工具层（工具定义 + MCP Server + 插件）就是干这个的：把外部服务包装成 Agent 可以调用的动作。这一步做得糙，后面所有自动化都会跟着晃。

## 问题

实际对接时常见的三类翻车：

1. Schema 写得含糊，Agent 传参全靠猜，调用成功率低；
2. 接口返回几百 KB 的原始 JSON 直接灌进上下文，几轮对话就把 token 打满；
3. 没有超时和重试策略，一个慢接口把整条 Agent 循环卡死，或者盲目重试把非幂等接口打重复。

## 做法

我们的路径是把每个外部服务收敛成一个独立的 MCP Server，步骤如下：

1. **先定边界，再写工具**。一个服务只暴露 3-5 个高频动作，每个工具参数不超过 5 个，描述里写清单位、格式和限制（"page 从 1 开始""date 格式 YYYY-MM-DD"）。
2. **凭证隔离**。Token 走环境变量注入，不进配置文件、不进对话上下文；每个服务的凭证独立管理，方便轮换和吊销。
3. **统一出口封装**。所有调用过一层 adapter，固定做三件事：timeout 10 秒且连接/读取分开设；重试只针对幂等请求（GET/PUT），指数退避最多 3 次；响应裁剪——服务端先分页和过滤字段，返回给 Agent 的只留摘要 + 必要字段，原始报文落盘供排查。
4. **错误结构化返回**。不抛裸异常，统一返回 `{ok, error_code, hint}`，hint 用一句话告诉 Agent 下一步怎么办（"token 过期，请提示用户重新授权"）。
5. **灰度上线**。先只开只读工具跑一周，观察调用日志里的参数错误率，再放开写操作，写工具前加一道确认门。

一个最小配置大致长这样：

```yaml
tool: crm.query_order
auth: env:CRM_TOKEN
timeout: 10s
retry: { idempotent_only: true, max: 3 }
response:
  trim: [summary, top_5_items]
```

## 踩坑点

- **描述即契约**：工具描述里少写一句"金额单位是分"，Agent 就会把 19900 当成一万九千块。描述按接口文档的标准写，别省字。
- **POST 别盲目重试**：带幂等键再重试，否则下单类操作会重复提交，这种事故账面上才看得见。
- **MCP 进程生命周期**：stdio 模式下子进程崩了要能被拉起。我们用 supervisor 托管加心跳检测，否则表现是"Agent 突然说工具不存在"，很难第一时间定位。
- **日志脱敏**：请求日志会带用户数据，上下文里也不该出现原始 token，两者都要在 adapter 层统一拦掉。

## 可复用建议

- 把"接服务"拆成三层：协议层（MCP/HTTP）、适配层（超时/重试/裁剪）、语义层（工具描述与错误提示）。新人接新服务只动语义层，前两层不动。
- 给每个服务留一个 `health_check` 工具，Agent 启动时先探活，比跑到一半失败便宜得多。
- 建立"工具变更 = 发版"的纪律：schema 改动必须过回归用例。Agent 对接口变更比人敏感得多，一行没同步的文档就是一次线上抖动。

## 总结

对接外部服务的本质不是"把 API 塞给模型"，而是替模型做减法：更少的工具、更小的响应、更明确的错误。OpenClaw 的工具层把挂点都留好了，剩下的功夫在约定和纪律——schema 严谨、出口统一、权限渐进。握手握得稳，Agent 才敢放手干活。
