## 背景

OpenClaw 这类常驻 Agent 的能力边界，基本由它能调到的工具决定。模型本身只会生成文本，真正去查数据、发消息、调内部接口的是工具层。所以“对接外部服务”不是写几个 curl 就完事，而是给 Agent 造一条可靠、可描述、可控权的握手通道。

## 问题

实际接服务时常见三类麻烦：

1. **模型选不对工具**：工具描述含糊，Agent 在相近工具之间摇摆，参数瞎填。
2. **凭证与安全**：API key 散落在配置文件和日志里，随手就被提交进仓库。
3. **错误处理缺失**：接口一报错就把整段 JSON 堆给模型，token 烧掉，Agent 还学不到任何东西。

## 做法

以接一个内部 HTTP 服务为例，我推荐走 MCP 路线：

**第一步：写一个薄封装的 MCP server。** 封装层不要塞业务逻辑，只做三件事：把 API 翻译成 tool、管好鉴权、把错误收敛成短结构。每个 tool 的 description 写清楚“什么时候该用我”，参数用 JSON Schema 标注类型和取值范围。

**第二步：注册到 OpenClaw。** 在配置里挂载该 MCP server，密钥走环境变量注入，不要写进任何会被 git 追踪的文件。

**第三步：先只读，再放开写。** 第一版只暴露查询类工具，观察 Agent 能否稳定选对、参数是否合理，确认后再加写入类工具——写操作务必叠加确认环节，宁可多一步对话。

**第四步：真实链路验证一次。** 直接对话让它查一遍数据，检查三件事：是否选对工具、失败时是否如实报错而不是编造、日志里有没有泄漏 key。

## 踩坑点

- **工具数量贪多**：一个 server 塞 20 个工具，选择准确率明显下降。按领域拆分，单个 server 保持 3–8 个工具。
- **description 写成 API 文档**：模型需要的是“使用时机”，不是字段罗列。写“用于查询 X 系统中某用户近 7 天的订单”，比列一串参数名有效得多。
- **无超时、无重试**：上游接口一卡，Agent 会话直接挂住。封装层必须设 timeout，且只有幂等的 GET 才值得重试。
- **错误原样透传**：把上游 500 返回的 HTML 整段喂给模型是灾难。统一收敛成 `{ok, error, hint}` 三个字段，hint 告诉模型下一步该怎么办。
- **大返回值直接入上下文**：列表接口默认分页，或封装层先做摘要，别一次塞几千条记录进去。

## 可复用建议

- 一个领域一个 MCP server，工具命名带版本号（如 `crm-v1`），上游改接口时可以平滑迁移而不是原地爆炸。
- 凭证统一走环境变量 + 最小权限 scope，日志层对 key 做脱敏。
- 每个写操作工具都设计确认机制，把“Agent 想做什么”先亮出来。
- 封装层保持“薄”：翻译、鉴权、收敛错误，仅此而已。升级 API 时只改一处。

## 总结

对接外部服务的核心不是“能不能调通”，而是让 Agent 在正确的时机、用正确的参数、安全地调通，并在失败时体面收场。把工具描述当产品文案来写，把错误处理当核心功能来做——这层握手才算真正握上。欢迎在社区贴出你们的封装实践和失败案例，踩坑记录往往比成功范例更有价值。
