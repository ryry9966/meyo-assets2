## 背景：被动 Agent 的天然短板

OpenClaw 里的 Agent 默认是一问一答：你不发消息，它就停在那。但真正用起来会发现，最有价值的几类需求全是周期性的——早上汇总未读邮件、盯服务器磁盘、检查 CI 挂没挂、每周收一次 commit 摘要。这些事让用户记着去问，等于自动化只做了一半。

HEARTBEAT.md 就是补上另一半的机制：网关按固定间隔发起一次"心跳"，Agent 被唤醒后读取工作区里的 HEARTBEAT.md，逐条判断"现在有没有该做的事"。有就执行，没有就静默返回，不产生任何打扰。

## 问题：大多数人的心跳清单是无效的

我把 HEARTBEAT.md 当普通笔记写过的第一批条目基本全军覆没，典型症状三个：

1. **条目不可判定**。"关注一下项目动态"——Agent 每次都要长篇输出一遍"动态"，token 烧得快，结论却没有。
2. **没有通知阈值**。每 30 分钟推一条"一切正常"，一天 20 条，第二天我就把通知关了，机制等于白建。
3. **任务超出心跳体量**。把"重新部署整个服务"塞进清单，心跳超时，任务半途而废。

## 做法：把清单写成 SLA

现在我的 HEARTBEAT.md 长这样（节选）：

- 每天北京时间 09:00 后的第一次心跳：检查 GitHub 通知，存在 @我 或待 review 才推送
- 根分区使用率 > 85% 时提醒一次，之后每小时最多重复一次
- 每周五 17:00：汇总本周 commit 与 PR，生成周报草稿存入 notes/
- 以上都不满足时：只回复 HEARTBEAT_OK

写法上有三条硬规矩：**每条必须包含触发条件、动作、通知策略**；动词可判定（用"检查/汇总/提醒"，不用"看看/关注"）；显式写明时区。间隔用 `HEARTBEAT_INTERVAL` 调整，日常跑 30 分钟，调清单期间临时改 5 分钟方便观察。最后在 AGENT.md 里约定"心跳结果默认只记日志，满足阈值才推送"——这一条决定了它是助手还是骚扰源。

## 踩坑点

- **心跳是真实计费调用**：30 分钟一次、每次都过一遍模型，清单务必控制在 10 条以内，无关条目全砍。
- **时区坑**：容器默认 UTC，"每天 9 点"可能实际发生在下午，务必显式声明。
- **静默失败**：心跳报错往往只躺在日志里。我加了一条"每周日自检：报告本周心跳执行摘要"，异常才浮出水面。
- **长任务别放心跳**：让 Agent 在命中条件后自己起子任务或写 cron 脚本，心跳只负责"发现"，不负责"执行重活"。

## 可复用建议

按三层组织清单：**高频轻检查**（进程、磁盘）、**中频汇总**（邮件、日历）、**低频报告**（周报素材）。新清单先跑一周"只记日志不推送"的静默模式，翻日志看 Agent 的判断质量，达标再放开推送。清单用 git 管理，每次误触发都能回溯是哪条写坏了。

## 总结

HEARTBEAT.md 的本质，是把你对 Agent 的期待从对话里抽出来，固化成一份机器可执行的巡逻表。写好它靠的不是文采，而是把每条写成可判定、有阈值、有通知策略的检查项。建议从两条最痛的日常检查起步，跑稳了再扩——主动的 Agent 不是更聪明的 Agent，是被更清晰地交代过期待的 Agent。
