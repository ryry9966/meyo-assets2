## 背景

跑过长任务 Agent 的人都明白：外部 API 挂掉不是“如果”，是“多久”。LLM 供应商限流、MCP 工具背后的第三方服务 503、网络抖动、证书过期——在一次持续几小时的自动化任务里，这些几乎必然发生。

传统脚本报错就退，人来看日志。Agent 不一样：它会把工具调用失败的上下文喂回模型，让模型“想办法”。这个机制既是能力也是风险——处理不好，轻则无限重试烧 token，重则模型编造一个看似合理的答案。

## 问题拆解

实际踩到的失败模式大致三类：

1. **崩溃型**：异常直接冒泡，任务中断，前面跑了一半的成果全部丢弃。
2. **空转型**：Agent 看到失败后反复重试同一调用，没有退避、没有上限，账单和耗时一起失控。
3. **幻觉型**（最危险）：错误被吞掉或表述模糊，模型基于“工具大概会返回什么”自行脑补，输出一本正经的错误结论。

## 做法

核心思路：把错误恢复从“模型的临场发挥”变成“工具层的确定性工程”。分五步：

**1. 先分类，再重试。** 在工具调用包装层区分可重试错误（429、503、超时、网络错误）和不可重试错误（401、400、参数错误），只有前者进重试队列。

**2. 指数退避 + 抖动。** 基础间隔 1s，倍增，上限 30s，加随机抖动避免雷群效应。重试次数按任务预算定死，比如 5 次，而不是“直到成功”。

**3. 把错误结构化地还给模型。** 重试耗尽后不要吞异常，也不要把原始堆栈直接塞给模型。返回统一格式：

```json
{"ok": false, "error_type": "upstream_timeout", "retryable": false, "hint": "可尝试备用数据源"}
```

字段够模型做决策，又不给它编造的空间。

**4. 熔断与降级链。** 连续失败 N 次触发熔断，停调该工具一段时间，走降级路径：备用 API → 缓存的上次有效数据 → 明确告知用户“这部分拿不到”。降级必须显式，宁可见丑话，不要静默的质量劣化。

**5. 检查点续跑。** 长任务每完成一个关键步骤就持久化状态，恢复时从检查点继续，而不是从头再来——对重复计费的工具尤其重要。

## 踩坑点

- **幂等没做就重试**：下单、发消息这类有副作用的调用，重试等于重复执行。先确认服务端有没有幂等键，没有就自己加一层请求去重。
- **把错误缓存成结果**：缓存层不区分成功响应和失败响应，导致熔断恢复后还在读那份 500。
- **降级不告知**：Agent 悄悄切到旧数据源继续答，用户不知道答案基于三天前的数据。降级信息要写进最终回复。
- **错误上下文太长**：整段堆栈喂给模型会带偏注意力并诱发幻觉，给结构化摘要就够了。
- **只在成功路径上测试**：不做故障注入，第一次真正遇到 429 就是在生产环境。

## 可复用建议

- 所有工具调用走统一的 `safe_call` 包装器，分类、重试、熔断逻辑只写一次，MCP 工具和插件全部接入。
- 故障注入做成开发环境开关，mock 429/500/超时，完整跑一遍降级链再上线。
- 每次重试和降级都落日志，事后能还原“这个答案当时为什么降级了”。
- 给每个任务设硬预算：最大重试次数、最大耗时、最大 token 消耗，超了就停在检查点等人介入。

## 总结

错误恢复的目标不是消灭失败，而是让失败**可读、有界、可恢复**：可读——模型拿到的是结构化事实而不是含糊报错；有界——重试和花费有硬上限；可恢复——状态有检查点，断了能续。做到这三点，外部 API 挂掉就只是任务里的一个普通分支，而不是一场事故。
