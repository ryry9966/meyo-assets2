## 背景

OpenClaw-CN 里不少人已经在用 Agent + MCP 做社区运营自动化：每周摘要、版本公告、issue 汇总转发。我自己跑过一个 weekly digest bot 三个月，前两周差点被管理员当 spam 处理。原因不是内容质量，是节奏——每天 09:00:00 整点准时出现，误差为零秒。人不会这样。

## 问题

调度器的默认输出是确定性时间序列。对平台风控和对社区成员的直觉来说，“过于规律”本身就是最强的机器人特征：

- 时间戳精确到秒，且天天复现；
- 每日固定条数，从不缺席也从不超额；
- 发帖间隔方差为零；
- 内容模板高度一致。

问题不在自动化本身，在于把调度当成 cron 来写。

## 做法

**1. 发送时间加抖动。** 设定目标窗口（如 09:00–09:40），在窗口内取随机偏移。用近似正态分布而不是均匀分布——均匀分布会均匀踩进冷门时段，反而更假。每次运行重新取种子。

**2. 对齐社区活跃时段。** 先离线统计真实成员的发言时间直方图（论坛 API 或日志都能拿到），把发送窗口放在活跃峰值前 10–20 分钟，而不是拍脑袋定早九点。时区必须显式声明，服务器 UTC 和社区本地时间对不上是常见事故。

**3. 频控。** token bucket，日上限 + 最小间隔下限（如 40 分钟），间隔下限同样加抖动。队列空了就跳过，不要为了“凑今天的量”硬发。

**4. 内容节奏和发送节奏分开处理。** 公告类可以固定周期——周报固定发是合理的，用户预期如此；对话性回复（自动答疑、跟帖）则必须随机化，且冷启动前两周全部走人工审核队列。

**5. 失败退避。** 指数退避 + 失败后冷却 30 分钟，禁止立即重试。重试风暴比规律发帖更容易触发封禁。

自用 pacing 模块的核心字段：

```yaml
window: "09:00-09:40"
jitter: gaussian
daily_cap: 3
min_gap_minutes: 40   # ± 15 jitter
quiet_hours: "01:00-07:00"
on_failure:
  backoff: exponential
  cooldown_minutes: 30
```

## 踩坑点

- **固定随机种子**：jitter 写了但 seed 固定，跑一个月仍是规律序列。
- **均匀抖动的反效果**：全窗口均匀取值意味着半夜时段也会中，比不抖动更暴露。
- **服务器时区**：容器默认 UTC，配置里的 09:00 实际是北京时间 17:00，恰好撞上晚高峰，看似巧合实则错位。
- **内容抖动过度**：为了不像模板，把每篇标题风格都改得不同，读者反而记不住这个 bot 是干嘛的。变化应放在措辞和篇幅，结构保持稳定。
- **别伪造人类痕迹。** 故意打错字、假装“刚看到”这类做法不可取——节奏控制的目的是守社区礼仪、降低噪音，不是伪装成人类。平台要求标注 bot 身份就老实标注。

## 可复用建议

- 节奏参数全部进配置，不硬编码，方便按平台分别调整。
- 每周拉一次自己 bot 的发帖间隔分布直方图，肉眼一看就能发现规律残留。
- 记录互动率：间隔调宽后打开率没降，说明原间隔本来就太密。
- 上线先以 1/3 频率跑两周，观察平台反馈再逐步放开。

## 总结

“不像机器人”的本质不是模拟人类，而是消灭确定性时间序列这个技术特征：抖动、对齐活跃时段、频控、退避，四件事做完，风控表现和社区观感都会明显改善。剩下的部分，交给诚实的身份标注和稳定的内容质量。
