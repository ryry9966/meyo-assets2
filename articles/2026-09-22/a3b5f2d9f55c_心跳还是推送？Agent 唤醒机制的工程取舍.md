## 背景

Agent 要"活"起来，前提是有人叫醒它。OpenClaw 的 heartbeat 机制是最朴素的方案：每隔 N 分钟主动醒来一次，检查 HEARTBEAT.md 里的待办、订阅源、定时任务，没事就继续睡。这套逻辑简单可靠，但用久了两个极端都很痛：间隔太短，token 账单难看；间隔太长，提醒慢半拍，用户感知就是"这助手反应迟钝"。

另一条路是推送：webhook、消息事件、MCP 工具回调，事件来了直接唤醒 agent。及时性好，但引入一堆基础设施，而且故障模式更隐蔽。

## 问题

两者本质差异是"谁来承担实时性成本"：

- **轮询**：成本可预期（固定频率的 wake），但延迟下限就是心跳间隔，且大部分 wake 是空转。
- **推送**：延迟低，但每个事件源都要接入；推送丢了没人知道，重试风暴还会打爆队列。

实际没人需要在纯轮询和纯推送里二选一，真正的问题是：**哪些事件值得推送，剩下的怎么用合理的心跳频率兜底。**

## 做法

我们内部收敛成三步：

1. **事件分级**。把所有唤醒源列出来，按"能容忍多久延迟"分三档：秒级（用户消息、告警）、分钟级（邮件、日历开始前提醒）、小时级（订阅汇总、仓库巡检）。秒级走推送，其余用心跳。
2. **推送只做"入队"，不做"唤醒"**。webhook 收到事件后只写进一个轻量队列，由队列统一触发 wake。这天然去重：10 封邮件在心跳间隔内到达，合并成一次 wake。
3. **心跳做兜底和巡检**。基础间隔 30 分钟，活跃会话期降到 5 分钟；同时心跳承担看门狗职责——超过 2 个周期没有成功 wake 记录，说明推送链路或调度进程挂了，发告警。

心跳本身的 prompt 要极简：只带 checklist 文件和当前时间，指示"无事则直接返回"。实测一次空转心跳的 token 消耗可以压到正常会话的 5% 以下。

## 踩坑点

- **空转心跳不便宜**。每次 wake 都要加载系统提示词和上下文框架，一分钟一次一天就是上千次 wake，账单会教育你。
- **推送没有幂等**。webhook 平台普遍会重试，我们最早没做去重，一次故障重放导致同一条提醒发了三遍。
- **心跳挂了是静默失败**。调度进程崩溃后 agent 永远不会醒，且没有任何报错——必须有针对 last_heartbeat 时间戳的外部监控。
- **心跳里调用慢工具**。有次心跳里挂了个抓外部 RSS 的 MCP 工具，目标站超时 60 秒，直接堵死心跳线程。心跳内所有工具调用必须带短超时。
- **静默时段算错时区**。夜间免打扰用了 UTC 判断，凌晨三点被自己的定时摘要吵醒。

## 可复用建议

- 一句话判断规则：**要求的响应延迟 < 你能接受的心跳间隔，就上推送；否则心跳够了。**
- 推送必须经过队列合并，不要直连 wake；队列本身就是你的限流器和缓冲区。
- 心跳间隔做成动态的：活跃期短、闲置期长、深夜静默，比全局固定值省一半以上。
- 给每次 wake 记录 reason（heartbeat / queue / user），事后看分布就知道设计是否合理——如果 90% 的 wake 都是空转，该砍频率了。

## 总结

轮询和推送不是对立选项，而是分层：推送负责"快"，心跳负责"稳"和"兜底"。OpenClaw 的 heartbeat 机制足够简单，简单意味着可观测、可兜底。把实时性需求交给队列化的推送，把可靠性交给心跳看门狗——这套组合在我们环境跑了两个多月，token 开销降了约 60%，延迟投诉归零。先分级，再入队，最后兜底，顺序别反。
