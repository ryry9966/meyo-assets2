## 背景

OpenClaw 里 memory_recall 的链路大致是：助手把对话摘要、决策、用户偏好写成一条条 memory 条目；下次会话或执行任务时，用当前 query 去库里召回相关条目，拼进上下文。召回质量直接决定助手"记不记得住事"。

实现召回有两条主流路线：**语义搜索**（embedding + 向量相似度）和**全文搜索**（分词 + BM25，比如 SQLite FTS5）。社区里经常一边倒地推荐语义搜索，理由是"高级""智能"。我最近把自己那份几百条的 memory 库两种方案都跑了一遍，结论是：各有明确的适用边界，混用往往才是正解。

## 问题

我最初的版本只用了语义搜索，跑两周后发现两类典型失败：

1. 查"上周部署报错 exit code 137 那件事"，召回回来一堆"部署流程总结"，真正的错误记录排在十几名开外——错误码、命令行这类精确 token，embedding 很容易糊掉。
2. 反过来，纯全文搜索查"那个容器老是被杀的问题"，而 memory 里写的是"OOMKilled"，分词后完全不匹配，一条都召不回。

## 做法

最后落了一个简单的混合方案：

1. **写入时规范化**：每条 memory 同时存 title、正文和一列显式 keywords（错误码、服务名、日期）。写入质量比检索算法更影响效果。
2. **双路召回**：语义一路（本地 embedding 模型 + cosine，top-k=10），全文一路（FTS5 + BM25，top-k=10）。中文先用 jieba 分词再建 FTS 索引。
3. **融合排序**：用 RRF（倒数排名融合）合并两路结果，取 top-5，再按时间衰减给新条目加权。
4. **回归评测集**：手写 30 条真实 query 和期望命中的 memory id，每次调参跑一遍，避免"感觉变好了"。

## 踩坑点

- **小语料别高估语义搜索**。几百条以内的 memory 库，关键词命中已能覆盖大部分 case，embedding 的优势要等语料上千、表述差异大时才明显。
- **embedding 模型和语料语言要匹配**。拿英文为主的模型索引中文 memory，召回质量明显下降，选型前先用自己的数据试 20 条。
- **FTS5 默认对中文按整句切分**，不加 jieba/trigram 基本不可用，这是最容易漏的坑。
- **相似度阈值别跨模型复用**。0.8 在不同模型下含义完全不同，建议用评测集定相对阈值，而不是拍脑袋。
- **缺时间衰减会召回陈年旧事**，加上按天数的指数衰减后，误召回少了很多。

## 可复用建议

- 有明确实体、错误码、ID 的记忆 → 依赖全文搜索，写入时把关键词显式存一列。
- 表述多样、口语化的记忆 → 依赖语义搜索。
- 拿不准就上 RRF 混合，成本只是多建一个索引，鲁棒性提升明显。
- 先建 30 条规模的评测集再调参，比换更大的 embedding 模型有效。

## 总结

这不是"哪个更先进"的问题，而是"你的 memory 长什么样"的问题。精确 token 多就重全文，表述差异大就重语义；大多数真实场景介于两者之间——双路召回 + RRF 是性价比最高的默认选项。工具本身不复杂，真正决定效果的是写入时的 memory 规范化，和一套能反复跑的评测集。
