## 背景

在 OpenClaw 插件和 Agent 工作流里，我们大量依赖模型输出结构化结果：工具调用参数、自动化任务的回执、流水线中间产物。提示词里通常约定一种格式，比如用 `<result>...</result>` 标签或 ` ```json ` 围栏包裹。但实际跑起来会发现，同一个模型在不同温度、不同上下文长度下，输出的"格式纪律"并不可靠。

## 问题

真实的失败样本大致分几类：

- 约定了 `<result>` 标签，模型却输出 ` ```json ` 围栏，甚至两者嵌套；
- 裸 JSON 直接输出，标签缺失；
- JSON 本身带瑕疵：尾逗号、全角引号「」""、字符串内未转义的换行；
- 输出被 max_tokens 截断，括号不闭合；
- 顶层有时是对象，有时是数组。

解析代码如果只按约定格式写"正则 + json.loads"，线上失败率往往比评测时高一个量级。

## 做法

核心原则：**解析管线分层、逐级降级、失败可观测。**

```python
def parse_llm_output(raw: str) -> Parsed:
    text = normalize(raw)                 # 去 BOM、零宽字符
    body = extract_tag(text) or strip_fence(text) or text
    for repair in (noop, light_repair, balance_brackets):
        try:
            data = json.loads(repair(body))
            return validate(data)         # Schema 校验，异常类型区分
        except ParseError:
            continue
    raise UnrecoverableOutput(raw=raw[:2000])
```

**第一步，清洗与标签归一化。** 标签匹配统一转小写，容忍前后空白和属性（如 `<result lang="zh">`）；用非贪婪匹配提取标签体；多次出现时取最后一个闭合的。

**第二步，三级解析降级。** 先直接 `json.loads`；失败后做轻量修复（尾逗号、全角标点、智能引号映射回 ASCII）再试——注意只在第一级失败后才动文本；最后做括号配平检测，若 `finish_reason` 为 `length` 或配不平，走截断分支：要么补右括号，要么判定失败交给上层重试，不要硬猜。

**第三步，解析与校验分离。** 解析成功不等于数据可用。用 JSON Schema 或 pydantic 做第二道门，两类错误抛不同异常，日志附带原始输出片段（截断存储），方便回放。

**第四步，错误结构化回喂。** 把具体错误（"第 12 列出现全角引号"）拼进重试提示让模型自纠，重试上限设 2 次，避免死循环烧 token。

## 踩坑点

- **贪婪正则跨代码块吞内容**：多个 ` ```json ` 块时会提取出拼接文本，必须非贪婪且锚定闭合标签；
- **嵌套围栏**：字符串值里本身含 ` ``` `，按围栏切分会截断 JSON；
- **修复做过头**：把字符串内部的撇号也替换了，语义被改。降级修复永远做最小改动；
- **不看 finish_reason**：截断场景任何修复都是猜，宁可失败重试；
- **顶层类型假设**：解析成功直接当 dict 用，遇到数组就崩。

## 可复用建议

1. 收敛到一个 `parse_llm_json` 模块，全项目禁止散装 `json.loads`；
2. 解析结果旁保留 `raw` 字段，调试和回放全靠它；
3. 把线上真实失败样本攒成 golden fixtures 跑回归，这是投入产出比最高的防线；
4. 打点各提示词模板的解析失败率，突增往往意味着上游改动了模板；
5. 供应商支持 structured output 时优先用，但保留文本解析兜底保证可移植性。

## 总结

LLM 输出解析的本质是**不信任 + 可降级 + 可观测**。约定格式只是快路径，防御逻辑才是主路径。分层降级不追求救回每条坏输出，而是保证：能救的救，救不了的带着足够上下文失败，让上层（人或 Agent 循环）能低成本接管。这套做法我们在多个插件里跑了很久，解析失败率从双位数百分比压到了千分级。
