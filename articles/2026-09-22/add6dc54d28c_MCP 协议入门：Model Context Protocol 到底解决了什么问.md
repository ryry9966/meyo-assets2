## 背景

在 MCP 出现之前（2024 年 11 月由 Anthropic 开源），给 Agent 接数据源基本是体力活。你写了一个桌面助手、一个 IDE 插件、一个自建 Agent 框架，每一个都要单独对接 GitHub、数据库、文件系统、内部 API。工具数量乘以宿主数量，就是典型的 M×N 集成问题——每个组合一份胶水代码，格式不统一、鉴权各自为政、改一处要同步多处。

MCP 的定位就是把 M×N 压成 M+N：工具方实现一次 MCP Server，宿主方实现一次 MCP Client，中间走统一协议。OpenClaw 这类支持 MCP 的 Agent 框架，正是这个模型的直接受益者。

## 它到底解决了什么

拆开看是三件事：

1. **接口标准化**。工具发现、工具调用、资源读取都有统一 schema，Agent 不用为每个工具写定制解析逻辑。
2. **上下文注入规范化**。除了函数调用，MCP 还有 resources 和 prompts 两类原语，让"把文件、数据喂给模型"有了标准通道，而不是全塞进 system prompt。
3. **进程与权限边界**。每个 MCP Server 是独立进程（常见 stdio 或 HTTP 传输），崩了不拖垮宿主，权限可以按 server 粒度控制和审计。

## 实践步骤

最小可用路径：

1. **选传输方式**：本地工具用 stdio，远程或多人共享的服务用 streamable HTTP。
2. **起 Server**：用官方 SDK（Python/TypeScript 为主）包一层现有 REST API，几十行就能跑通。
3. **宿主注册**：在 OpenClaw 的 MCP 配置里声明 command、args、env，宿主启动时拉起进程并完成工具发现。
4. **验证**：先用 inspector 类调试工具确认工具清单和 schema 符合预期，再接入 Agent 实测完整调用链。

## 踩坑点

- **工具描述就是 prompt**。模型靠 description 决定何时调用哪个工具，写得含糊会导致误调用或无限重试。花在描述上的时间不比代码少。
- **工具数量爆炸**。挂十几个 server、上百个 tool 后，tool 定义本身就吃掉大量 token，选择准确率也会下降。按任务场景拆配置、按需加载。
- **stdio 的环境变量陷阱**。Server 子进程继承的是宿主的 env，PATH、代理、虚拟环境和你的终端经常不一致。本地能跑、宿主拉不起来，八成是这个原因。
- **不要盲目信任返回值**。MCP 只规范传输，不保证 Server 本身安全。第三方 Server 要限制文件系统和网络访问范围，敏感操作保留人工确认环节。

## 可复用建议

- 优先复用社区现成 Server，只在内部系统没有实现时自己包一层。
- 把高频内部系统（CI 状态、工单、知识库）聚合成一个 Server，比散装挂一堆更可控。
- 给每个工具补一句"何时不该用"，能显著减少误触发。
- 配置即代码：MCP server 配置进 Git，权限变更走评审。

## 总结

MCP 没有魔法，它做的是一件朴素但关键的事：给 Agent 和工具之间定了一套通用的插座标准。对工具作者，写一次到处能接；对 Agent 使用者，生态从"各自适配"变成"即插即用"。但它不解决安全问题，也不保证工具质量——这些仍要靠你自己的权限设计和工程判断。如果维护着多个 Agent 或多个内部系统，MCP 值得尽早接入；如果只是玩具项目，先用 SDK 包一个最小 Server 感受协议形状，再决定投入程度。
