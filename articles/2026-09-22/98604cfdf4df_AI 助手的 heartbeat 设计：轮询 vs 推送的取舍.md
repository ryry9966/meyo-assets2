## 背景

跑过 OpenClaw 的都知道，agent 平时是"睡着"的：gateway 按固定间隔（默认 30 分钟）把它唤醒一次，agent 读工作区里的 `HEARTBEAT.md`，按清单检查有没有该做的事，没有就静默回去继续睡。这是很典型的轮询（polling）模型。

而另一类需求天然不适合轮询：CI 挂了要立刻知道、监控告警要秒级触达、邮件到了想马上处理。这些走推送（push）更合理——webhook 打到 gateway，或者插件 / MCP server 直接把事件投给 agent。

## 问题

两种模型的账不一样：

- **轮询**：实现简单、不依赖对外暴露入口、丢一次心跳无所谓（下个周期补上）；代价是延迟上界等于间隔，且每次唤醒都有 token 成本，哪怕最后什么都没做。
- **推送**：延迟低、按需触发、不浪费唤醒；代价是要暴露入口、处理鉴权、重试、去重，事件一多 agent 容易被打爆，还可能和进行中的会话抢队列。

所以真正的问题是：**你的每个主动任务，到底需要多快被感知？** 别按技术偏好选，按延迟需求选。

## 做法

我的做法是三档分类，然后混合使用：

1. **需求按延迟分档**：小时级（巡检、日报、磁盘水位）、分钟级（告警、新消息）、精确时刻（定时提醒）。
2. **小时级交给 heartbeat**：`HEARTBEAT.md` 只放 5–10 行检查清单，明确写"无事则静默"。间隔先用默认值，跑一周看 token 账单再调。
3. **分钟级走推送**：gateway 的 webhook 接收外部事件，转成消息投给 agent；或者自己写个小 MCP server 暴露一个 notify 工具，让监控脚本、git hook 主动调用。
4. **精确时刻用一次性定时唤醒**（cron 式），不要靠把轮询间隔缩到 1 分钟硬凑——那是用成本换精度，最亏的一种换法。
5. **混合兜底**：heartbeat 是骨架，推送是神经。推送链路挂了，下一轮心跳还能把事情兜住——这是轮询最被低估的价值。

## 踩坑点

- **HEARTBEAT.md 写成了长文**：每次唤醒全文进上下文，token 直接翻倍。清单归清单，细节放别的文件，按需再读。
- **忘了静默约定**：agent 每次心跳都往群里汇报"一切正常"，第三天就被群友抗议。把 `HEARTBEAT_OK` 这类"无事不发言"的约定明确写进指令。
- **webhook 没做幂等**：上游重试导致同一条告警触发 agent 跑三遍。给事件带唯一 ID，在接收侧去重。
- **推送撞上心跳**：agent 正在跑心跳回合时推送进来，怎么排队、会不会合并，先在本地验证清楚再上生产。
- **入口安全**：webhook 端点务必带 token 鉴权，别默认"内网就安全"。

## 可复用建议

- 一句话决策规则：**延迟要求 < 轮询间隔，就上推送；否则轮询。高频噪声事件，先聚合再推。**
- 心跳日成本 ≈ (24 × 60 ÷ 间隔分钟) × 单次唤醒 token。调参前先算这笔账——很多"觉得慢"的问题，其实是"觉得贵"。
- 观测先行：记下每次唤醒的触发源、耗时、token 数，一周后数据会告诉你哪些心跳在白烧。
- 把 `HEARTBEAT.md` 当代码管理：改动走 review，防止有人随手加条目把成本抬上去。

## 总结

轮询和推送不是二选一，而是分工。轮询买到的是简单、可靠、可自愈；推送买到的是延迟和效率。OpenClaw 的 heartbeat 机制足够便宜，适合当系统的底噪；webhook / MCP 推送适合当事件通道。先用轮询把主动行为跑通，再按延迟需求逐个升级成推送——比一上来就搭一套事件系统务实得多。
