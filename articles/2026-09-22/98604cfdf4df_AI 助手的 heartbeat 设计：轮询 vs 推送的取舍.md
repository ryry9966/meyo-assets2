# AI 助手的 heartbeat 设计：轮询 vs 推送的取舍

## 背景

OpenClaw 类的个人 Agent 常驻后台，用户不在场时也需要"活着"：定时整理收件箱、盯服务器磁盘、在日历事件前提醒。让 Agent 感知时间的机制通常就是 heartbeat——每隔一段时间醒来一次，检查任务清单，决定要不要干活。

但"多久醒一次、醒了干什么"只是表象。真正要决策的问题是：**状态变化的感知，靠轮询还是靠推送？**

## 问题

两种单一模式的痛点都很具体：

- **纯轮询**：为了把告警延迟压到 5 分钟内，把间隔从 30 分钟调到 5 分钟，模型调用和 token 消耗涨了 6 倍，而 95% 的心跳周期里其实无事发生。
- **纯推送**：每个事件源都要一条 webhook 通路。本地跑的 Agent 没有公网入口，要么开隧道要么引消息队列；事件源一多，接入成本线性上涨，且 Agent 宕机期间的事件直接丢失。

问题于是变成：**怎么分层组合。**

## 做法

我们的原则：**推送管"及时"，轮询管"兜底"，两者共享一份去重状态。**

```text
heartbeat 唤醒
  → 脚本预检（事件积压? 清单过期?）
    → 无事: 返回 OK（0 token）
    → 有事: 调模型处理 + 写 dedup key
```

1. **事件分级。** 把 Agent 关心的事件分两类：紧急（磁盘 >90%、服务 down、用户 @）和例行（收件箱整理、日报汇总）。只有紧急类走推送。
2. **推送通路做减法。** 不给每个工具单独建 webhook，而是收敛到一条事件总线：轻量 ingest 服务收所有推送，写入 Redis Stream，Agent 通过 MCP 工具消费。本地没有公网入口时，ingest 部署在 VPS 上，Agent 用 outbound WebSocket 反向拉取，避开开洞。
3. **轮询兜底。** heartbeat 保留默认 30 分钟间隔，但醒来后不直接调模型，先跑零成本脚本预检：Stream 有无积压、心跳清单里哪些项过期。有情况才升级给模型。
4. **去重与冷却。** 每个事件带 dedup key（如 `disk:server-a`），推送处理完即写入已处理集合，轮询扫到同一 key 跳过；同一 key 一小时内不重复告警。

结果是：紧急事件延迟秒级，例行工作保持低频，模型调用量回落到接近 30 分钟轮询的水平。

## 踩坑点

- **心跳直接 prompt 模型。** 最初每次心跳都让模型"看看有什么要做的"，一个月 token 比正常对话烧得还多。改成脚本预检后才降下来——这条对成本影响最大。
- **推送和轮询重复触发。** 同一磁盘告警，推送处理完后轮询又跑一遍，用户收到两条一模一样的消息。dedup key + 冷却窗口是必须项，不是可选项。
- **Stream 没设上限。** 下游故障积压了几万条事件，Agent 恢复后一股脑消费，又触发十几条"迟到的告警"。给 Stream 加 MAXLEN，超过阈值的事件丢弃并合并成一条汇总。
- **静默时段缺失。** 深夜推送直接响到手机。告警通道单独加 quiet hours，非紧急事件顺延到下一个心跳。

## 可复用建议

- 心跳间隔 30 分钟起步，只上调不下调；延迟敏感的需求交给推送解决。
- 醒来先跑确定性脚本，再决定是否调用模型。
- 事件总线一条就够，工具侧收敛接入，别为每个集成建独立通道。
- dedup key、冷却窗口、静默时段是推送系统标配，第一天就要有。

## 总结

轮询和推送不是二选一，而是分工：推送把"必须现在知道的事"压到秒级，轮询保证"任何事最终都会被看到"。heartbeat 的价值不在于醒得勤，而在于每次醒来都能**廉价地判断要不要真的干活**。把检查逻辑从模型挪到脚本，把紧急感知从轮询挪到推送，成本和延迟就都有了交代。
