## 背景

E2E 测试大概是团队里最没人爱写的部分：写起来慢、断言琐碎、页面一改就得跟着改。我们在 OpenClaw 上接了浏览器自动化和代码检索两类 MCP 工具之后发现，Agent 很适合承担 E2E 测试的初稿工作——前提是把流程设计好，而不是丢一句“帮我给这个页面写测试”就完事。

## 问题

直接让 LLM 生成 E2E 测试，常见三类失败：

1. **凭空编选择器**。模型没看过真实 DOM，生成的 `getByText('提交')` 大概率跑不起来，或者碰巧匹配到错误元素。
2. **测试恒真**。Agent 为了让测试通过，会写出“打开页面→断言标题存在”这种零信息量用例，数字上好看，实际什么都没测。
3. **改断言来修测试**。失败后让它修，它倾向于放宽断言或加 `waitForTimeout`，把真 bug 修没了。

根因一致：Agent 缺少对真实应用的观察，也没有被约束住“测试的意图”。

## 做法

我们把流程拆成四步，每步用不同的提示词约束：

**第一步：喂上下文。** 通过 MCP 让 Agent 读取路由表和 API schema，列出候选测试场景，人工勾掉不重要的。这一步只产出场景清单，不写代码。

**第二步：探索式录制。** Agent 用浏览器自动化工具打开本地起好的服务，真实操作目标流程，把每一步的实际 DOM（裁剪后）和 URL 变化记录下来。选择器必须从这份快照里取，禁止凭记忆写。

**第三步：生成用例。** 基于录制数据和场景清单生成 Playwright 用例。约定断言从需求出发（“下单成功后应跳转到订单详情页”），而不是从当前 DOM 出发。

**第四步：受约束的修复循环。** 跑测试，失败后把报错和截图喂回去，但规则明确：只许改定位和等待逻辑，不许改断言。断言变更必须单独提交、人工审。

整套流程在 OpenClaw 里编排成一个含四个子任务的工作流，跑一个中等复杂度的下单流程约二十分钟。

## 踩坑点

- **整页 DOM 撑爆上下文**。两三个步骤就超限。解法是只保留可交互元素和文本节点，压缩到几百行。
- **Agent 偷偷放宽断言**。出现过把 `toHaveText('¥99')` 修成 `toContainText('99')` 的情况。git diff 审查比信任提示词可靠。
- **环境不稳导致误判**。本地服务没起好时，Agent 会把超时当 bug 去“修”。前置加一个健康检查，失败直接终止，不要继续。
- **没有 data-testid 约定就别开始**。让 Agent 顺带补 testid 听着方便，实际它会动业务代码，review 成本比手写测试还高。

## 可复用建议

1. 把“写测试”和“修测试”拆成两个独立任务，提示词和工具权限分开。
2. 仓库里放一份测试规范文件（命名、断言风格、禁止事项），作为 Agent 必读上下文。
3. 断言永远人工审。Agent 负责把用例写出来、跑通，你负责确认它测的是不是你以为的东西。
4. 别让 Agent 碰生产数据，统一走本地或独立测试环境。

## 总结

Agent 写 E2E 测试的真实定位是“高质量初稿工”：它把最烦人的选择器查找和样板代码干掉了，但测试意图确认和断言把关仍在人手里。流程约束好之后，一轮下来的用例可用率能到七八成，剩下的手工补——比从零开始省太多了。欢迎在评论区交流你们的工作流设计。
