## 背景

跑 Agent 链路一段时间后你会发现一件事：链路里大部分环节不在你的控制范围内。LLM 供应商会抖，MCP 工具背后的第三方搜索、天气、支付 API 会挂，网络会抽风。写 demo 时一切顺利，上生产之后，**外部依赖故障不是异常路径，而是日常**。

普通程序遇到 API 挂掉会抛异常、进重试逻辑、打日志。Agent 遇到同样的问题会"表演"，而且往往是三种典型翻车方式。

## 问题在哪

1. **幻觉式兜底**：模型把工具返回的错误信息当成了数据，编造一个看起来合理的答案，用户完全无法察觉。
2. **循环自燃**：模型自己决定重试，在 LLM 循环里反复调用同一个挂掉的 API，token 成本和延迟一起指数上涨。
3. **写操作重复执行**：POST 超时后盲目重试——超时不代表失败，可能服务端已经成功，重试就是重复下单、重复扣款。

## 做法：分四层处理

### 第一层：工具/MCP 层兜住瞬时错误

- HTTP client **必须设超时**，默认值可能很长甚至无限。
- 区分错误类型：429 / 5xx / 网络超时可重试；其他 4xx 直接失败，重试没有意义。
- 指数退避 + 抖动，**2~3 次封顶**。关键点：重试发生在工具内部，而不是 agent 循环里。
- 写操作带幂等键，让服务端能去重。

### 第二层：给模型结构化的错误信息

不要把原始错误页、HTML、堆栈扔给模型。返回统一信封：

```json
{
  "ok": false,
  "error_type": "upstream_timeout",
  "retryable": false,
  "hint": "search provider unavailable, inform the user"
}
```

模型其实是很好的错误路由器——前提是你给它结构化输入，而不是噪声。`retryable: false` 时在 hint 里直接告诉它"不要重试，告知用户"。

### 第三层：降级与熔断

- 只读工具：返回带时间戳的缓存数据，并明确标注数据是过期的。
- 有条件的话准备备用供应商，主源挂了自动切换。
- 错误率超过阈值就熔断，后续请求直接走降级路径，别让每个请求都去撞墙。

### 第四层：诚实面对用户

所有兜底都失败时，让 agent 明确说"这个数据源现在不可用"。这比编一个答案强一百倍——用户可以接受"暂时拿不到"，不能接受被错误数据误导。

## 踩坑点

1. **在 agent 循环里重试**：最贵的重试方式。模型每次重试都消耗上下文和 token，而且它不懂退避，会连续撞。
2. **把 429 当宕机**：429 是限流，需要更长的退避窗口甚至暂停调用，按宕机处理只会让限流更严重。
3. **fallback 数据不标注**：拿三天前的缓存当实时数据讲给用户，比直接报错更糟。
4. **重试预算超过整体超时**：工具层退避总共 30 秒，agent 整体超时 20 秒，重试永远跑不完，白烧。
5. **错误信息塞满堆栈**：污染上下文窗口，还可能诱导模型从中"解读"出不存在的结论。

## 可复用建议

- 写一个**统一的 tool call wrapper**，所有插件和工具走同一套错误信封与重试策略，策略按工具名配置化，不要每个插件各写一套。
- 给关键外部依赖加探活探测，错误率上报 metrics。**告警看错误率，不看单次失败**——单次抖动是常态。
- 每次工具调用记录 request id。出了事故，你要能在日志里还原是哪个环节、哪次请求出的问题。

## 总结

错误恢复的目标不是消灭故障，而是**让故障时的行为可预测**：工具层吸收瞬时抖动，模型拿到结构化、有边界的错误信息，用户听到真话。这三件事做扎实，Agent 才算具备上生产的资格。
