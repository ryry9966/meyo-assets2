## 背景

Agent 自动化跑久了，外部 API 出问题是常态而非意外：LLM 供应商限流、MCP 工具背后的上游服务超时、搜索或数据库接口偶发 5xx。短对话里可以人工兜底，但在无人值守的定时任务和长流水线里，一次失败可能导致整条链路停摆——或者更糟，Agent 悄悄编一个"看起来没问题"的结果。

## 问题

实际踩到的三类故障模式：

1. **无限重试烧 token**：循环里没有退出条件，对 401 这类不可恢复错误也重试，一晚上烧光配额。
2. **静默幻觉兜底**：工具调用失败后模型不报错，而是基于自身知识"补"出答案，下游全是脏数据。
3. **半途崩溃无状态**：任务执行到第 5 步挂了，重启后从第 1 步重跑，重复下单、重复发通知。

核心矛盾：重试是必要的，但无分类、无上限、无状态的重试会把小故障放大成事故。

## 做法

一套最小恢复框架，按顺序落地：

1. **先分类，再重试。** 只对 429、5xx、超时、网络错误重试；400/401/403 直接走失败分支。有 `Retry-After` 就照做，没有就指数退避加抖动（1s → 2s → 4s，±20% 随机），上限 3~5 次。
2. **设重试预算和整体 deadline。** 单工具重试之外，整个任务要有总时长约束，超时进入降级流程，不让一个环节拖死全局。
3. **设计降级路径。** 三选一或组合：备用供应商、带时间戳标记的本地缓存结果、跳过可选步骤并在产出里显式标注"该部分未完成"。
4. **熔断。** 连续 N 次失败后短路，直接走降级，期间用轻量健康检查间隔探测，恢复后再切回主路径，避免对着已死的服务高频敲门。
5. **状态检查点。** 每个成功步骤落盘（JSON/数据库），恢复时从检查点续跑；对有副作用的写操作加幂等键，保证重放不产生重复副作用。
6. **约束模型行为。** 在 system prompt 里明确"工具返回错误时报告失败原因，禁止用自身知识补全结果"，并在代码层校验工具输出结构，异常输出一律拦截。

## 踩坑点

- **对 4xx 重试**：最常见的浪费，401 重试一百次也不会好，先修凭证。
- **固定间隔无抖动重试**：多实例同步重试会形成重试风暴，反而延长故障。
- **非幂等写操作直接重试**：下单、发消息类操作，重试前必须先解决幂等性。
- **熔断阈值拍脑袋**：太敏感频繁误切降级，太迟钝等于没有，建议按时间窗口内失败率判断。
- **日志缺上下文**：只记 "API error" 不记任务 ID、步骤、入参，复盘时两眼一抹黑。
- **降级结果不标记**：缓存数据和实时数据混在同一字段，下游无法区分新旧。

## 可复用建议

- 所有外部调用收敛到一个统一 client/网关模块，重试、超时、熔断、日志在一处实现，业务侧只管调用。
- 任务设计成"可续跑"优先于"可重跑"：检查点粒度按步骤，不按整个任务。
- 坚持 fail loud：宁可任务显式失败并告警，不要带病输出。
- 用一个可返回各种错误码的 mock API 专门测失败路径，上线前把恢复逻辑完整跑一遍。
- 给每个工具调用定义三类出口：成功 / 可重试失败 / 最终失败，不允许出现第四种"看起来成功"。

## 总结

外部 API 挂掉不可避免，错误恢复的目标不是消灭失败，而是**控制失败的爆炸半径**：分类决定能不能重试，退避决定怎么重试，熔断决定何时停止，降级决定停止后怎么办，检查点决定从哪里重来，行为约束决定模型不会替你圆谎。这套逻辑不难写，难的是在故障发生前就把它放进代码里。
