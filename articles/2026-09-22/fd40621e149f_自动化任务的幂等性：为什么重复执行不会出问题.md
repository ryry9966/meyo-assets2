## 背景

跑 OpenClaw 自动化任务一段时间后，你会遇到一个绕不开的现象：同一个任务被执行了不止一次。原因很日常——调度器重试、Agent 判定超时后自作主张重跑、MCP 工具调用响应丢失触发上层重试、人工觉得"好像没跑"手动补一次。你没法保证执行次数永远是一，所以真正的问题变成：执行两遍、三遍时，结果还能和对吗？

这就是幂等性：同一个操作执行一次和执行多次，最终状态一致。

## 问题

非幂等任务在重复执行时的典型翻车现场：

- 定时同步任务重跑后，目标库数据翻倍；
- Agent 调用"创建工单"工具，接口超时但实际已成功，重试后建出两张重复工单；
- 通知类任务补跑，同一个群被 @ 三遍；
- 手动补昨天的任务，和今天正在跑的实例同时写同一批记录，产生竞态。

根因相同：任务把"执行动作"当成了产出，而不是把"达到某个状态"当产出。

## 做法：三层防线

**1. 幂等键要可推导，不要随机生成。** 从任务语义里派生键，而不是每次运行随机造一个：

```text
idempotency_key = hash(task_type + target + business_date)
```

同一任务对同一目标在同一业务日，键永远相同。注意 LLM 生成的 task_id 不可靠——每次输出可能都不同，用它去重等于没做。

**2. 写入用 upsert，不裸 insert。** 目标存储支持就把"插入"改成"存在则更新"。数据库层的唯一索引是最后防线：应用层判断有竞态窗口，唯一约束没有。

**3. 调下游 API 时带上幂等键。** 主流 API（工单、支付、云资源）大多支持 idempotency key。超时重试时带同一个键，服务端会返回第一次的结果，而不是再执行一次。

删除类任务反过来更好办：直接删，"删不存在的东西不算错"天然幂等；但删除后触发的通知不幂等，要单独处理。

## 踩坑点

- **check-then-act 竞态**：先查"跑过没"再执行，两个并发实例同时查到"没跑"，然后都跑了。检查和写入必须原子（唯一约束或锁），不能只靠查。
- **把响应超时当失败**：接口实际成功但响应丢了，上层重试。没有幂等键时这必然翻车。
- **键的粒度错**：键里带运行时间戳，每次都不同；或者太粗，把本该执行两次的合法操作也去重掉了。
- **Agent 场景特有**：重规划后任务被拆成不同表述，语义相同但文本不同，哈希对不上。键要绑业务对象，不要绑任务文本。

## 可复用建议

1. 验收标准很简单：同一个任务连续跑两遍，第二遍结束后数据、通知、工单数量都不变。把它写成自动化测试。
2. 优先用声明式描述任务目标（期望状态），而不是命令式步骤，让框架自己决定要不要执行。
3. 三层防线缺一不可：应用层检查（快）、数据库唯一约束（兜底）、下游 API 幂等键（防响应丢失）。
4. 每次执行留去重日志，出问题时能回答"这次到底执行了几遍、哪一遍生效"。

## 总结

自动化系统里，重试和重复执行不是异常，而是常态。幂等性不是高级技巧，而是让 Agent 和流水线敢于重跑、敢于重试的前提。写任务时先问一句：这个任务被多触发一次，会发生什么？答不上来，说明还没做完。
