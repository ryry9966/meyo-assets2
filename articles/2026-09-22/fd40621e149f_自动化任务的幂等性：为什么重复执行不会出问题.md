## 背景

跑自动化的人迟早会遇到同一件事：任务被执行了不止一次。

在 OpenClaw/Agent 这类工作流里，重复执行的来源比想象中多：

- 定时任务重叠：cron 间隔 5 分钟，任务实际跑了 8 分钟；
- Agent 重试：工具调用超时后，编排层自动重跑整个计划；
- Webhook/消息队列重投：对端没及时 ack，投递方按策略重发；
- 人为因素：以为没触发，手动又点了一次。

## 问题

这些场景本身都正常，问题在于**任务的副作用不可重放**。

典型翻车：一个通过 MCP 工具给频道发日报的定时任务，超时重试后发了三条；一个"给新用户初始化配置"的 agent 流程，队列重投后写了两份配置，后续读哪份全看运气。

幂等性（idempotency）的含义很朴素：**同一个任务执行一次和执行 N 次，最终状态一致**。它不是可选项，而是任务能否被安全重试的前提。

## 做法

围绕一个核心问题展开：这个任务重跑一遍，会发生什么？

**1. 用稳定的业务键做任务标识**

幂等键必须从业务语义派生，不能是随机数：

```
✅ daily-report:2024-06-01:channel-a
❌ task-{uuid}   # 每次生成都不同，去重失效
```

关键纪律：幂等键在首次执行时生成，**重试时复用**。把生成逻辑放进重试循环里，是最常见的自毁方式。

**2. 优先声明式副作用**

能"设置目标状态"就不要"追加一次操作"：写配置用 upsert，不用 insert；改状态用 `UPDATE ... SET status='done' WHERE id=?`，不用 append；删除天然幂等，报"不存在"不算失败。

**3. 去重表 + 唯一索引兜底**

副作用真正发生前，先以幂等键落一条记录，`task_key` 上建唯一索引，重复执行直接撞约束。数据库层的约束是最后防线——应用层判断永远有竞态。

**4. 条件更新抢占执行权**

多 worker 场景，用条件更新替代"先查后改"：

```sql
UPDATE task SET owner=me, status='running'
WHERE task_key=? AND status='pending';
-- 影响行数为 0，说明已被领走，直接退出
```

## 踩坑点

- **先查后写的竞态**：两个进程同时查到"没执行过"，然后都执行了。解法只有唯一索引或原子条件更新。
- **标记成功太早**：先写 done 再发消息，消息发失败后任务永远不会重跑。正确顺序是副作用全部完成，最后落终态。
- **只幂等了写库，漏了外部副作用**：库 upsert 了，但发消息、调第三方 API 没有。对方不支持幂等键时，先本地落"意图记录"，执行完再更新。
- **部分失败不可续跑**：第 3 步挂了重跑，前两步又执行一遍。要么每步自带幂等保护，要么设计成可从中间状态恢复。
- **幂等键里掺时间戳**：`report:{now()}` 每次都不同。用时间戳做键前先想清楚：业务上"同一次执行"的边界到底在哪。

## 可复用建议

1. 写任务前先做"重跑演练"：心里过一遍连跑两次会怎样，答不上来就先补设计。
2. 上线前在测试环境把同一个任务**故意跑两次**，作为验收项。
3. 日志里始终带 task_key，事后审计和排障都靠它。
4. 敢重试的系统才敢放手自动化，而重试安全的前提就是幂等，两者是配套的。

## 总结

自动化系统的可靠性不在于"不出错"，而在于**出错后重跑是安全的**。幂等性就是把"重复执行"从事故变成正常运维的开关：稳定业务键定身份，声明式副作用减麻烦，唯一索引做兜底，终态最后落。这四件事成本很低，但对 agent 编排、MCP 工具链、定时任务这些场景是真正的分水岭——有了它，重试、重投、手动补跑都只是普通操作。
