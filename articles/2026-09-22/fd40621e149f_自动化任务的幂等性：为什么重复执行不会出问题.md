## 背景

Agent 化的自动化有个特点：触发源不可控。定时任务在进程重启后会补跑，MCP 工具调用在网络超时后会被上层重试，插件回调、webhook 投递也只保证"至少一次"而不是"恰好一次"。写多了自动化脚本你会发现，真正稳的任务不是"从不出错"，而是"出错了重跑也没事"——这就是幂等性：同一任务执行一次和执行多次，最终状态一致。

## 问题

非幂等任务的典型翻车姿势：

- 每次运行都往数据表 insert 一条记录，重跑三次就有三条重复数据
- 失败重试导致同一封通知发两遍，用户被打扰两次
- 输出文件用时间戳命名，重跑后产生一堆"哪个才是最新"的歧义
- 任务半途崩溃后重跑，状态被叠加，越跑越偏

## 做法

按副作用类型分三类处理：

1. **只读任务**：天然幂等，不用管。
2. **覆盖型写入**：改用 upsert / PUT 语义，"确保目标状态是 X"，而不是"再追加一次 X"。报告输出用固定文件名覆盖写，需要历史再单独归档。
3. **追加型操作**：必须引入幂等键。用触发事件本身派生 key（事件 ID、`任务名+业务日期`、内容 hash），执行前查执行台账，已执行就直接跳过。

一个通用模板，给定时任务、MCP 工具、插件入口都能套：

```text
key = sha256(task_name + trigger.event_id)
if ledger.exists(key): return ledger[key]
result = do_work()        # 内部用 upsert / create-if-not-exists
ledger.put(key, result)
```

台账就是一张表或一个 Redis key，字段三个足够：幂等键、状态、时间。

## 踩坑点

- **先查后写有并发漏洞**：两个实例同时查到"不存在"，然后同时插入。要用数据库唯一约束、`SETNX` 或文件锁，把"检查 + 写入"做成原子操作。
- **幂等键粒度**：key 里带随机 UUID，每次重试都变成"新任务"，等于没做；粒度太粗（比如只按日期），又可能吞掉合法的多次执行。key 必须来自业务语义，不是来自执行过程。
- **时间锚点**：任务里用 `now()` 生成数据，两次执行结果就不可比。应锚定到触发事件携带的时间，而不是执行时刻。
- **半完成状态**：写到一半崩溃，重跑不是"跳过"而是"续传或先清理"。设计时先回答：跑到一半死了，再跑一遍会发生什么？
- **副作用要逐个审**：业务写库幂等了，告警照样可能重复发。通知、外部 API 调用要单独去重。

## 可复用建议

- 优先写成"对账式"任务：声明期望状态，任务负责把现实拉齐，而不是做增量动作。这一条能消掉大半幂等问题。
- 建一个全局共享的执行台账，所有自动化任务复用，别每个脚本自己造一套。
- 把"连续跑两次，结果一致"加入自动化脚本的上线前检查，和单元测试同级对待。
- 给重试设上限和告警。幂等保证的是重试安全，不是无限重试合理。

## 总结

幂等性不是高级技巧，而是自动化能"放心交给机器"的前提。核心动作就三件：识别副作用、设计幂等键、把检查和写入做成原子。下次写定时任务或 MCP 工具时，先问自己一句：这条任务被重复触发三次，世界会变成什么样？正确的答案是——和触发一次一样。
