## 背景

我们的内容生产已经跑在 Agent 上：OpenClaw 编排写作 agent 产出初稿，人工审校后发布到公众号、知乎、掘金和自建博客。AI 生成的 Markdown 看着规整，但真到发布才明白，"一份 Markdown 走天下"是幻觉——每个平台的渲染器支持的方言都不一样。

## 问题

痛点集中在四类：

1. **方言差异**：公众号对 HTML 白名单极严，不支持脚注和任务列表；知乎会把部分语法降级成纯文本；掘金接近 GFM 但对表格宽度敏感。
2. **AI 生成习惯**：模型爱用引用式链接、嵌套列表、H1 开头、正文夹 HTML，恰好都是兼容性最差的部分。
3. **资源问题**：本地图片路径、图床外链失效、代码高亮依赖前端库，公众号全不吃。
4. **流程问题**：每发一个平台手工改一遍，格式劳动吞掉自动化省下的时间，还引入人为不一致。

## 做法

解法是一条三层管线，核心原则：只维护一份 canonical Markdown，平台差异全部交给代码。

**第一层，约束生成。** 在 agent 的 prompt 里写死输出契约：标题用 ATX 且从 H2 开始、只用行内链接、代码围栏必须带语言、禁 HTML 和脚注。这一步能砍掉一大半后处理量。

**第二层，AST 归一化。** 用 remark 解析成 AST，不做正则替换。跑一遍规则集：标题统一降级、引用式链接转行内、清理空段落、标记超宽表格。结果入库，作为唯一事实来源。

**第三层，平台适配器。** 每个目标平台一个小模块，输入 canonical MD，输出平台可用载荷：

- 公众号：MD 转行内样式 HTML，代码块预高亮成 inline CSS，图片先传素材库再回填 URL；
- 知乎/掘金：基本直出，剥离不支持节点，表格压到 4 列以内；
- 博客：注入 front-matter（标题、日期、tags），其余原样保留。

适配器全是纯函数，注册成 MCP tool 后，OpenClaw 主 agent 按发布目标逐个调用，最后接一个预览步：渲染截图或推草稿箱，人工确认后才真正发布。

## 踩坑点

- **别用正则处理 Markdown。** 早期在正则里替换链接，把代码块里的字符串一起改了，事故一次就够。要处理就过 AST，至少先做 fence 感知。
- 公众号会剥掉 `<style>` 和大部分属性，样式必须全部内联，主题 CSS 别指望带过去。
- AI 很爱 `# 一级标题`，平台标题栏再填一遍就是双标题，归一化时统一降级，别信模型。
- `[^1]` 脚注和 `- [ ]` 任务列表在不少渲染器里就是裸文本，宁可转换别赌。
- 表格是移动端重灾区，超 4 列建议转图片或列表，在 AST 阶段判断列数。

## 可复用建议

- 每个平台的方言写成一份 YAML 配置（支持哪些节点、样式映射），适配器读配置而非写死逻辑。
- CI 放一道 lint 闸门：目标平台不支持的节点直接 fail，别等发布失败才发现。
- 用 golden file 做快照测试，适配器改动后 diff 一眼可见。
- 平台变体永远是生成物，禁止手改，否则下次重新生成就丢。

## 总结

多平台发布本质是方言翻译，不是格式美化。canonical Markdown + AST 变换 + 配置化适配器 + lint/预览闸门，就能把"每次发布改半小时"压成"看一眼预览点确认"。管线本身不复杂，难的是忍住手改生成物的冲动——守住这条，自动化才真正成立。
