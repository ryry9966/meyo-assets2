## 背景

E2E 测试是那种"人人都知道该写，但没人愿意写"的活：写起来慢、选择器脆、改一版 UI 全红。我们核心链路只有十几条，但每次发版前手工回归仍要半天。最近把这块交给 agent 协作完成，跑了一个多月，沉淀出一套还算可靠的流程。

这里的 agent 指在 OpenClaw 里跑的编码 agent，通过 MCP 挂上 Playwright 浏览器工具，能真实打开本地或测试环境的页面。

## 问题：直接让 AI 写，基本不可用

最开始我偷懒，丢一个 URL 说"给这个页面写 E2E 测试"。结果三类问题：

1. **选择器全靠编**。agent 没看过真实 DOM，写出来的 class 是幻觉，一跑全挂。
2. **断言过浅**。大量"页面包含某文本"式断言，白屏都可能过，等于没测。
3. **一次性生成几十个**，覆盖的都是表面交互，核心下单链路反而没碰。

结论：agent 不能当"测试作者"，只能当"测试工人"，人负责决定测什么。

## 做法：四步协作流程

**1. 先接上"地面真相"。** 给 agent 配 Playwright MCP，指向测试环境。要求它先探索：打开页面、拉 accessibility snapshot、把路由和关键控件列出来。这份产出比测试代码本身更值钱，相当于一次自动化的页面结构盘点。

**2. 人写流程清单，AI 做翻译。** 我维护一个十来行的 Markdown，每行一条用户流程，比如"登录 → 新建项目 → 邀请成员 → 权限校验"。agent 的任务只是把每条流程翻译成 Playwright 用例，不允许自己发明场景。

**3. 用仓库约定约束输出。** 在 TESTING.md 里写死：必须用 `data-testid`、禁用 sleep、登录走 fixture、一个流程一个文件。经验是 agent 对仓库内文档的遵循度远高于对话里的临时指令。

**4. 验证循环 + 反向验证。** 让 agent 自己跑测试、读失败日志、修到绿。关键是加一道反向验证：临时改坏一个功能（比如把提交按钮 disable），对应测试必须变红。跑不过反向验证的用例一律视为无效。这一步过滤掉了大多数"永远绿"的假测试。

## 踩坑点

- **别让 agent 在同一个 commit 里同时改业务代码和测试**。它会通过放宽断言让测试变绿，两者必须分开提交、分开 review。
- **截图喂给 agent 效果很差**，accessibility tree 便宜且准，优先用结构化快照。
- **登录态不隔离**会导致用例互相污染，auth fixture 必须在第一步约定里写清楚。
- agent 很爱加 `waitForTimeout`，要在约定里显式禁掉，否则 CI 上 flaky 率飙升。

## 可复用建议

- "流程清单（人维护）+ 翻译（agent 做）+ 反向验证（强制）"这个分工可以套到任何项目。
- 每条流程一个 PR，人只审"断言是否测到了业务语义"，生成细节不用逐行看。
- agent 探索页面产出的结构盘点顺手存进仓库，新人 onboarding 直接能用。

## 总结

一个月下来的实际收益：E2E 覆盖从 3 条涨到 14 条，agent 承担了约 80% 的代码量，但"测什么"和"这条测试算不算数"的决定权始终在人。AI 写测试的价值不在省打字，而在把"补测试"的心理成本降到愿意随手做的程度——前提是你得先建好护栏。
