## 背景

我日常用 OpenClaw 跑了不少定时任务：Agent 会话、代码提交、服务巡检、内容采集，日志分散在各自的 cron 输出里。每天人工汇总一份日报，翻日志、拼格式，稳定消耗二十分钟，还不保证不漏。于是搭了一条「采集 → 规则预处理 → LLM 汇总 → 定时投递」的流水线，跑了一个多月，把做法和踩过的坑整理如下。

## 问题

最初的偷懒方案：把所有日志拼一起直接丢给模型总结。结果有三个：

1. 原始日志量大且噪音多，容易撑爆上下文，关键事件反而被淹没；
2. 模型自由发挥输出格式，日报每天长得不一样，无法归档对比；
3. 成本不可控，日志越多越贵。

结论很直接：**LLM 适合做「归纳」，不适合做「解析」。解析必须是确定性代码。**

## 做法

流水线分四层，每层中间产物落盘，方便排障和重放：

1. **采集层**：每个数据源（agent session 日志、cron 输出、git log、服务日志）由独立脚本归一化为 JSONL，按日期分目录存放，如 `logs/2025-06-01/`。原始产物只追加、不修改。
2. **预处理层**：纯 Python/jq，做三件事——过滤（丢弃心跳和重复重试）、聚合（同类错误按错误码归并计数）、标准化（每条统一 `ts / source / level / summary` 字段）。产出一份「digest」，体积通常只有原始日志的十分之一。这一层完全不碰模型。
3. **汇总层**：digest 加固定 prompt 模板交给 agent，要求输出符合预定义 schema 的 JSON（日期、要点列表、异常列表、待办事项）。拿到结果先用 jsonschema 校验，失败则把报错附加后重试，最多两次。
4. **渲染与投递层**：JSON 渲染成 Markdown 模板，推送到 IM webhook；原始 JSON 归档，供后续做周报统计回填。

cron 每天 21:30 触发。每层完成后写心跳文件，超过 30 分钟没心跳，由另一个告警 cron 发出提醒。

## 踩坑点

- **时区**：日志是 UTC，日报按本地日期算，跨天消息会算错归属。采集层统一转本地时间，并显式写入 `report_date` 字段。
- **敏感信息**：原始日志里有 token 和内网地址，预处理层先做脱敏（正则匹配替换），之后才允许进模型上下文。
- **幂等性**：同一天重跑任务曾覆盖报告。改成「生成幂等、投递带去重 key」，重复推送在 IM 侧直接丢弃。
- **静默失败**：cron 挂了没有任何感知。加心跳 + 告警后，第一次模型 API 配额用尽就被及时抓到了。
- **Schema 漂移**：模型偶尔漏掉可选字段。所有字段强制必填、允许空值，比允许缺字段稳定得多。

## 可复用建议

- **分层是第一原则**：确定性工作交给代码，模型只负责归纳和措辞，分工比例大约 9:1。
- **Schema 先行**：先定输出 schema 再写 prompt，比反复调 prompt 措辞省事。
- **中间产物落盘**：任何一层出问题，从上一层产物重放即可，不必全链路重跑。
- **每层独立 CLI 入口**：调试时单层运行验证，不依赖 cron 才能测。

## 总结

日报听起来是小事，但很适合练「流水线化」的思维：每层职责单一、产物可落盘、校验有兜底。这套骨架搭好后，周报月报只是换聚合窗口，新数据源只需在采集层加适配器。模型是流水线中的一环，而不是流水线本身。
