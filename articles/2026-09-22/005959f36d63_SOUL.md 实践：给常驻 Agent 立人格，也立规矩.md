## 背景

OpenClaw 这类常驻 Agent 的特点是长生命周期：连续跑几周，跨多个会话、多个渠道（Telegram、微信、终端）响应请求。人格和边界如果只写在某次对话的开场白里，重启一次就丢。SOUL.md 的意义就在于把这部分"软性配置"固化成一个 Markdown 文件，每次会话启动时注入系统提示词，跟代码一样可以版本化。

## 问题

不写 SOUL.md 时，常见三类翻车：

1. **语气漂移**：前几天回复简洁，跑久了话越来越多；
2. **越界动作**：深夜主动发消息、没确认就执行删除类操作、替用户对外承诺；
3. **风格分裂**：不同会话里同一个 Agent 像两个人。

根因是人格和边界既没有版本化，也没有被测试，全靠模型每次"自由发挥"。

## 做法

**第一步：建文件，分四段写。** 在工作区根目录建 SOUL.md，建议结构：

- 身份与语气：一句话说清"我是谁、用什么口吻说话"；
- 响应风格：长度上限、默认语言、格式偏好；
- 行为边界：一份"不做清单"；
- 升级规则：什么情况必须停下来问人。

**第二步：控制篇幅。** SOUL.md 每次会话都进上下文，建议 30–60 行以内。规则尽量写正面、可验证的行为："回复不超过 5 句"比"不要啰嗦"有效得多。

**第三步：进 Git。** 每次改动写清楚 commit message，才能回溯"哪次改动让它变得话多"。

**第四步：建回归集。** 准备 10 条左右固定问题，包含边界试探类（比如"直接帮我删掉这个目录"），每次改完 SOUL.md 跑一遍对比行为。

一个可参考的最小骨架：

```markdown
# Identity
- 语气克制、直接，默认中文

# Response
- 单条回复 ≤ 5 句，代码块优先于长解释

# Boundaries
- 23:00–08:00 不主动发消息
- 不可逆操作（删除/发送/支付）先复述意图，等待确认
- 工具报错时如实转述，不得编造结果

# Escalation
- 涉及权限变更或对外发送时，先停下询问
```

## 踩坑点

- **只写"不要 X"不给替代方案**，模型通常会换个方式犯同类错；
- **多份指令打架**：SOUL.md、AGENTS.md、MCP 工具描述如果互相冲突，行为会变得不可预测，人格规则保持单一来源；
- **把 SOUL.md 当安全沙箱**：它只是提示词层面的软约束。危险工具的权限必须在配置层收掉——文件管人格，权限管兜底；
- **改完不测**：改一次漂一次，没有回归集的人格调优基本是玄学。

## 可复用建议

- 三层分离：人格（SOUL.md）、任务指令（会话内 prompt）、工具权限（config），别混在一起写；
- 规则必须"可测试"：写不出判据的规则直接删掉；
- 小步修改 + 回归集，把 SOUL.md 当生产配置维护，而不是许愿池。

## 总结

SOUL.md 的写入成本很低，写坏的成本很高。核心就三件事：篇幅克制、规则可验证、改动有回归。做到这三点，Agent 的人格才是稳定可预期的工程产物，而不是每次会话开盲盒。
