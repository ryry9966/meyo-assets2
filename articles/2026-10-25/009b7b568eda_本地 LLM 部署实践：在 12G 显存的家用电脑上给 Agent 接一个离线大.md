## 背景

Agent 自动化跑起来之后，LLM 调用变成了高频操作：解析文档、摘要、意图路由、工具调用决策。全走云端 API 有两个现实问题——数据敏感的流程过不了合规，高频调用的账单也不好看。我的解法是给家里的主力机（4070Ti 12G + 32G 内存）跑一个本地模型，专接这两类任务。这篇记录完整过程，重点是给 Agent/MCP 场景的接线经验，不是通用的"跑个大模型玩玩"教程。

## 问题

本地部署的核心矛盾在于：Agent 框架普遍假定 OpenAI 兼容接口 + 稳定的 function calling，而家用硬件装不下"工具调用能力完整"的大模型。模型选小了会编造参数、漏 JSON 字段；选大了显存爆掉或上下文被截断。需要在中间找一个能用的平衡点。

## 做法

**1. 先算显存账。** Q4_K_M 量化下，模型权重大约是参数量 × 0.6 GB，再加 KV cache 开销（上下文越长越吃）。7B Q4 权重约 4.5G，8G 显存能跑但上下文紧张；14B Q4 约 9G，12G 显存比较从容。先量化自己的卡，再选模型。

**2. 选运行时。** 日常用 Ollama，一条命令拉模型，自带 OpenAI 兼容端点；批处理任务切 llama.cpp server 榨性能。Linux 服务器且显存充裕时可以考虑 vLLM，家用场景多数用不上。

**3. 量化别太激进。** Q4_K_M 是质量与体积的平衡点。工具调用对量化很敏感，Q3 以下经常出现参数格式错误。优先选官方发布过 tool-use 微调版的模型。

**4. 接入 Agent。** base_url 指向 `http://localhost:11434/v1`，api_key 随意填，模型名与 `ollama list` 输出严格一致。

**5. MCP 工具冒烟测试。** 本地模型跑 MCP server 没有障碍，瓶颈在模型侧的 function calling 稳定性。先挂 3-5 个简单工具（文件读写、HTTP 请求）验证跑通率，再逐步加复杂度。

## 踩坑点

- **context 默认值陷阱**：Ollama 默认 `num_ctx` 很小，Agent 的长对话和工具定义会被直接截断。显式设到 8k-16k，同时盯显存水位。
- **"支持工具"≠"调得好"**：给工具 schema 加 `enum` 和必填项约束，小模型的编造率明显下降。
- **循环不停止**：部分模型在 Agent 循环里不吐 stop token，导致无限续写。框架侧必须设 max_tokens 上限加重试逻辑。
- **长上下文延迟**：消费级显卡的 prefill 可能只有几百 token/s，系统提示 + 工具定义堆到 5k token，每次冷启动好几秒。对策是精简工具描述、缓存固定前缀。

## 可复用建议

- **用自己的 workload 评测**：准备 20 条真实请求（含工具调用），跑通率比榜单分数诚实得多。
- **分层路由**：意图分类、格式化走 4B 级小模型，推理写作用 14B，延迟和显存都压得下来。
- **配置进代码**：模型名、num_ctx、温度写成仓库里的 profile 文件，别人 clone 下来即可复现。

## 总结

12G 显存的家用机器，已经能稳定支撑中小规模的 Agent 自动化。代价是要自己管好上下文预算和工具调用容错。它不会替代云端模型做复杂推理，但让"数据敏感"和"高频调用"两类任务有了现实解。先跑通最小链路，再谈优化。
