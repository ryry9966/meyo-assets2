## 背景

接上 MCP 和一堆插件之后，Agent 的能力上限往往不再是模型，而是我们敢给它开多大的口子。社区里常见的形态是：Agent 能读写本地文件、跑 shell、操作浏览器、调第三方 API。能力一多，"这件事该不该它自己干"就从哲学问题变成了工程问题。

## 问题

实践里常见两种极端：

- **全自动**：工具全挂上，出事再收权。删错目录、误发消息、跑飞的 token 账单，基本都是这么来的。
- **全确认**：每个动作都弹窗等人。前三天你还认真看，之后全是无脑点"允许"，确认机制形同虚设。

两种都会失败，区别只是快慢。核心不是"问不问"，而是**按什么标准问、问的时候给人看什么**。

## 做法：给工具分层，把规则写进代码

我们把所有工具按风险分四档，在工具注册的元数据里标好，由策略层统一执行，而不是指望 system prompt 里的一段话：

- **T0 只读**：读文件、查询、搜索。直接放行，记日志。
- **T1 可逆写**：工作区内写文件、开分支、草稿区操作。放行，但必须留回滚路径（快照、git）。
- **T2 有外部副作用的写**：发消息、提 PR、调第三方 API、花钱。执行前确认，确认时附带 diff 或参数摘要。
- **T3 不可逆/高危**：删数据、动生产、支付、外发密钥。永远人工，默认拒绝，白名单放行。

判断维度就四个：**可逆性、爆炸半径、成本（钱/token/时间）、意图歧义度**。前三个决定档位，第四个是叠加项——参数含糊时降级处理，宁可多问一次，也别替用户猜一个 `--force`。

两个配套机制：

1. **计划先行（dry-run）**：T2 以上的操作，先输出"做什么、为什么、怎么回滚"三段式，人看完再放行。
2. **预算闸门**：单次 token、金额、调用次数设硬上限，超限自动停下问人。这比事后对账有效得多。

## 踩坑点

- **确认疲劳**：T0/T1 也弹窗，人很快会机械点允许。确认频率本身是资源，只花在 T2/T3。
- **无上下文的确认**：只问"是否继续？"等于让人类盲签。必须附操作内容、影响范围、回滚方式，否则确认环节没有信息量。
- **授权范围失控**："允许执行这条命令"被泛化成"允许这一类命令"。授权要带作用域和有效期，过期重新问。
- **规则只写在 prompt 里**：模型不保证遵守。T2/T3 的拦截必须实现在 MCP 包装层/策略层，prompt 只是第一道筛子，不是闸门。
- **先斩后奏**：Agent 先做再汇报，本质是取消了边界。执行前的同步阻塞确认要用代码保证，不能靠"记得先问我"这种约定。

## 可复用建议

- 工具接入时就打风险标签，比事后审计便宜一个数量级。
- 默认拒绝优于默认放行，尤其是 T3。
- 每周复盘一次确认记录：哪些询问可以降级为自动，哪些自动行为该升档。边界是活的，要跟着事故调。
- 确认产物（谁批的、批了什么）进独立审计日志，别只留在会话记录里。

## 总结

权限边界不是给 Agent 设限，而是把"信任"变成可配置的工程参数：T0/T1 靠日志和回滚兜底，T2/T3 靠结构化确认和硬闸门。判断标准始终是那四条——可逆吗、炸了多大、花多少、我确定吗。拿不准就问人，但要让人类在五秒内做出有依据的决定。
