## 背景

社区内容运营有个老问题：优质内容的整理和分发靠人肉，节奏不稳定。我们想做一个发帖机器人，定时把仓库 issue 精华、周报要点、技术摘要在社区自动成帖。听起来简单，实际做了两周，推翻了两版方案。这篇记录最终架构和踩过的坑。

## 问题

最初方案很朴素：cron 定时跑脚本，调 LLM 生成正文，直接调社区 API 发布。上线三天暴露三个问题：

1. 失败重试导致同一内容重复发了三遍；
2. LLM 编造了不存在的 issue 链接和标签；
3. 发布频率失控触发社区反垃圾，账号被限流。

核心矛盾在于：LLM 负责“写”，但“发”这个动作必须有确定性控制。

## 做法

最终架构分四层，跑在一个 OpenClaw agent 实例里，通过 MCP 接入工具：

1. **数据采集层**：MCP tool 封装 GitHub API 和 RSS 拉取，输出结构化 JSON 条目，不给 LLM 自由发挥的空间。
2. **草稿生成层**：agent 按模板生成帖子，结果先落 SQLite，状态为 `draft`。
3. **校验层**：轻量插件做规则校验——链接逐一 HEAD 请求验证、标签必须来自白名单、正文长度与格式检查。不过关打回重写，最多 2 次，仍失败进人工队列。
4. **发布层**：独立 cron 只消费 `approved` 状态的草稿，发布前用幂等键查重，发布后写回 post_id。

关键设计是**生成与发布彻底解耦**：LLM 挂了不影响已批准内容正常发出；发布层不依赖模型，行为完全可预测。

## 踩坑点

- **幂等键别只用内容 hash**：同一天两个版块发同主题摘要属于正常需求，改成 `hash + section + date` 三元组才对。
- **MCP tool 返回要克制**：早期把 RSS 原文整个塞给 agent，上下文爆炸且容易跑偏。改成 tool 内先做字段裁剪，只返回结构化摘要。
- **打回重写会死循环**：模型对同一个校验错误反复用同样方式修。加上“每次打回附具体失败原因 + 已失败次数”后才收敛。
- **时区**：cron 按 UTC 跑，帖子总在凌晨三点发出。调度统一显式声明时区，别依赖宿主机默认值。
- **内容漂移**：跑两周后帖子风格越来越水，根因是 prompt 模板被历次“微调”堆了太多补丁。最终模板收进 git，改动走 review。

## 可复用建议

- 任何 LLM 参与的写入操作，前面必须有确定性校验层；
- 用状态机管理内容生命周期（draft → approved → published / failed），别用一个布尔字段；
- 先 dry-run 一周，把“本应发布”的内容落到日志人工抽检，再放开真实发布；
- 给模型的数据做减法，不是加法；
- 幂等、限流、重试上限，三个参数上线前必须显式配置。

## 总结

这个项目里 LLM 真正的价值只在草稿生成那一步，约占代码量的 15%。其余 85% 是采集、校验、状态管理、幂等和运维——恰恰是传统工程能力。结论很朴素：把 agent 当成一个有才华但不太靠谱的实习生，流程和护栏由你来建，效果反而最好。
