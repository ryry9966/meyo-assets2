## 背景

交互式对话里，instruction 写错一点无所谓——用户在旁边，追问一句就能纠正。Cron 任务没这个待遇：它单发、无人值守，失败往往几天后才被发现。OpenClaw 的 cron 触发，本质上是一条定时投递给 agent 的消息，多数场景跑在隔离会话里：没有昨天的上下文，没有人在对面接话。

一个实用的心智模型：**你不是在写聊天指令，你是在深夜给一个能力很强但完全失忆的实习生发一条交接消息。**

## 问题

三类最常见的失败，都源于把 cron 当聊天写：

1. **上下文假设错误**。instruction 写"把今天的日报发到群里"，agent 不知道"今天"是哪天、之前的口径是什么，只能猜。
2. **输出契约缺失**。只写"整理一下数据"，产出的格式、长度、目的地每次都在漂移；有时 agent 干脆停在追问状态，没人回答，任务空转。
3. **失败语义未定义**。被要求"必须产出"的 agent，在数据源挂掉时倾向于编一份看起来完整的报告。定时任务的幻觉比交互场景危险，因为没人当场看。

## 做法：五要素模板

把每条 cron instruction 拆成五个固定块，缺一不可：

```text
【触发上下文】本任务由定时器每天 09:00 触发；执行时先获取当前系统时间，
以它为"今天"，不要凭感觉推断日期。

【范围与工具边界】只允许读取 {数据源/目录/API}，不要访问其他来源，
只执行读取类操作。

【输出契约】把完整结果写入 {文件路径}，Markdown 格式，含 A/B/C 三节；
再向 {目标频道} 发一条不超过 200 字的摘要，附文件路径。

【失败语义】数据源拉取失败或返回为空时，不要编造数据；
在摘要中说明失败环节、时间和原因，本次产出标记为失败。

【幂等与禁止项】目标文件如已存在，直接覆盖，不要追加；
不要向 {白名单外} 的任何联系人或频道发消息；不执行写入/删除类命令。
```

逐块说：触发上下文解决时间歧义；工具边界是 prompt 层面的最小权限；输出契约把**目的地、格式、长度**三件事钉死；失败语义显式授权"报错也是合格产出"，压掉幻觉动机；幂等与禁止项防重跑、防误伤。

## 踩坑点

- **改完不实测**。instruction 就是代码，改完必须手动触发跑一次，检查真实产物（文件内容 + 消息落点），再挂回 schedule。
- **时区错位**。cron 表达式的时区、系统时区、agent 理解的"今天"是三回事。要求以系统时间为准，能消掉大部分偏差。
- **产物只在对话里**。只发消息不留文件，事后无法审计。"文件 + 摘要"的组合是对的。
- **权限给满**。为了省事挂全量工具，一次 prompt 偏差就可能删文件或群发消息。宁可先收窄，跑不通再加。
- **指令越写越长**。塞太多业务知识，不如把知识固化成脚本和数据源，instruction 只管调度和契约。

## 可复用建议

- instruction 存进 git，和代码一样走 review 与回滚。
- 上线后盯完第一个真实周期再放手——异常大多在第一次真实触发时才暴露。
- 需要长期稳定的产出，优先让 agent 调用封装好的脚本，而不是用 prompt 描述整个流程：**prompt 管契约，脚本管执行**。

## 总结

Cron instruction 的质量标准只有一条：一个失忆的执行者拿着它单独过夜，早上醒来产物正确、可审计，坏了会自己喊。按五要素写，先手动触发，再信任它。
