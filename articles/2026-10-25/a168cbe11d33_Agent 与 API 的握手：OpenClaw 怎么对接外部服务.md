## 背景

Agent 从“能聊天”到“能干活”，中间隔着的其实就是工具层。在 OpenClaw 的落地场景里，最常见的诉求是让 Agent 查订单、发通知、写工单——这些能力几乎都长在外部服务上：REST API、内部 RPC、第三方 SaaS。怎么把这些服务干净地接进来，是每个团队绕不开的一步。

## 问题

把 API 直接丢给 Agent，通常有三种翻车方式：

- 让模型自己拼 HTTP 请求，参数随缘，鉴权头经常丢；
- 密钥散落在 prompt 和配置文件里，一次日志导出就泄密；
- 网络抖动一重试，非幂等接口重复下单。

本质问题是：API 是给程序调用的，而 Agent 需要的是“带说明书、带护栏”的工具。

## 做法

OpenClaw 对接外部服务，建议走 MCP / 插件工具这条路径，核心四步：

1. **盘点服务，划定边界。** 先列出 Agent 真正需要的能力（查库存、创建工单……），不要一上来全量暴露。
2. **做薄封装。** 一个业务动作对应一个工具，用 JSON Schema 把参数写死：字段名、类型、必填、枚举值。描述里写清“什么时候该用我、什么时候不该用”。
3. **鉴权下沉到工具层。** 密钥走环境变量或 secrets 管理，运行时注入，永远不进 prompt、不进日志。
4. **加护栏。** 超时设短（5–10s），POST 类接口强制带幂等键，返回体做裁剪——大结果落盘，只回传摘要和引用。

最后补一层观测：每次工具调用记一条结构化日志（工具名、参数摘要、耗时、状态码），出问题能回放。

## 踩坑点

- **工具描述含糊。**“查询数据”这种描述会让 Agent 在多个工具之间摇摆。描述要写成决策依据，不是功能简介。
- **重试没考虑幂等。** 写操作要么带幂等键，要么改成“先查再写”。
- **返回体撑爆上下文。** 一次拉全表，对话直接报废。分页 + 裁剪 + 引用是标配。
- **工具数量失控。** 单个 Agent 挂 30 个工具，选择错误率明显上升。按场景拆 Agent，或做工具分组。
- **错误直接抛异常。** 应该把结构化错误（错误码、原因、建议动作）返回给 Agent，给它自我修正的机会。

## 可复用建议

- **封装粒度：** 一个业务动作一个工具，不要一个工具塞多个动词。
- **Schema 从严：** 能枚举就枚举，能必填就必填，可选字段越少越好。
- **工具带版本号：** 接口变更时，线上 Agent 不至于静默失效。
- **影子流量验证：** 新工具上线先跑 shadow call，对比 Agent 产生的参数和人工基线的偏差，再放开真实流量。

## 总结

对接外部服务，工程量在“握手协议”而不是“发请求”。OpenClaw 的 MCP/插件机制价值就在于：把鉴权、Schema、护栏、观测统一收进工具层，Agent 只负责决策。工具层稳了，Agent 才稳——反过来，工具层每一处模糊，最后都会变成 Agent 的幻觉。
