## 背景

OpenClaw 的价值在于 agent 不止会聊天，还能动手。动手的接口就是外部 API：查数据、发通知、操作工单系统、调用内部服务。社区里常见的对接路径有三条：MCP server（标准化工具协议）、自定义插件/skill（代码级封装）、以及最朴素的 fetch 加提示词约定。三条路最后都面对同一件事：让一个**概率性调用者**（LLM）去调用一个**确定性接口**（API）。握手协议没设计好，拿回来的就是幻觉和事故。

## 问题

把 API 直接丢给 agent，通常死在四个地方：

1. **凭证暴露**——密钥被写进 SKILL.md 或 system prompt，一次提示词注入就全盘泄漏；
2. **副作用失控**——POST 类接口被模型重试两次，重复下单、重复发通知；
3. **参数乱填**——工具描述含糊，模型把 `user_id` 填成邮箱；
4. **返回体失控**——列表接口返回 40KB JSON，直接撑爆上下文。

## 做法

以对接一个工单系统为例：

**第一步：选路径。** 接口标准、操作固定 → 封装成 MCP server；需要编排和状态 → 写插件；一次性简单调用 → skill 里写 fetch。别为一个小接口起一个 MCP 服务，也别用 skill 承载十几个复杂操作。

**第二步：隔离凭证。** 密钥只放环境变量或 gateway 配置，工具函数运行时读取。skill 文档里只写“需要 `TICKET_API_TOKEN`”这件事，绝不写值。

**第三步：收窄工具面。** 每个工具只做一件事；JSON Schema 的 `required` 写全；`description` 用模型能读懂的自然语言讲清字段格式与约束（比如“ID 是数字，不是邮箱”）。工具描述是给模型看的 API 文档，花在它上面的时间往往比实现还多。

**第四步：超时、重试与幂等。** 显式设置超时，默认值通常太长，会阻塞 agent 主循环；GET 可重试，POST 一律不自动重试，必要时带幂等键；出错不抛裸异常，而是返回结构化错误 `{ error, hint }` 给模型，给它自纠的机会。

**第五步：裁剪返回。** 分页、截断、字段过滤都在工具函数里做完，只把决策所需的最小字段送进上下文，原始响应留在日志里。

**第六步：灰度。** 先开 dry-run，所有写操作只打印意图不执行；跑稳后放开，并配域名白名单。

## 踩坑点

- 把 token 写在 SKILL.md 的示例里“方便调试”，忘了删——最常见泄漏源；
- 重试逻辑写在通用封装里，没区分幂等性，重复发消息事故基本都源于此；
- 工具报错直接抛堆栈，模型看到后开始自由发挥；
- fetch 跟随重定向把请求带去第三方域，密钥连着 header 一起过去；
- 日志明文记录请求头——脱敏永远比事后补救便宜。

## 可复用建议

一把钥匙一个环境变量；先写失败路径再写成功路径；写操作默认 dry-run；返回给模型的数据控制在 2KB 以内；每个工具留一条脱敏调用日志，出问题能回放。把这些做成团队模板，下一个服务的对接成本会从一天降到一小时。

## 总结

Agent 调 API 不是“能跑通就行”，而是给一个不确定的调用者设计一份确定的契约：凭证隔离、工具面收窄、幂等明确、返回裁剪。OpenClaw 给足了扩展位，真正的工程量在握手时的这些约束上。约束先行，agent 才能真正放心地把“手”伸出去。
