## 背景

Agent 的能力上限，基本由它能调用的工具决定。模型本身只负责推理，真正"做事"的那一步——查库存、发工单、拉日志——都要落到外部服务上。OpenClaw 的定位是把模型和工具接在一起，而对接方式主要有三条路：MCP server、skill/插件、裸工具封装。这篇帖聊聊我们实践中怎么选、怎么写、踩过哪些坑。

## 问题：API 不是天生就能给 Agent 用的

直接把一个 REST API 丢给 Agent，通常会出三类问题：

1. **表面太大**。一个服务几十个 endpoint，Agent 在工具选择阶段就开始猜。
2. **响应不友好**。原始 JSON 几十 KB 塞进上下文，token 爆炸，还可能截断在数组中间，Agent 拿着半截数据继续推理。
3. **写操作不安全**。Agent 重试一次，订单创建两次；或者缺少确认环节，一句话就把生产数据改了。

本质上，API 是为"确定性的调用方"设计的，而 Agent 是个"概率性的调用方"。握手之前，需要一个中间层做翻译。

## 做法

我们目前的流程，供参考：

**第一步：选对接形态。** 优先 MCP。它是标准工具协议，鉴权、schema、生命周期都有约定，换模型或换宿主不用重写。只有强耦合的内部逻辑（比如要直接读会话上下文）才写成 skill。

**第二步：收缩工具面。** 不按 endpoint 封装，按"意图"封装。比如 CRM API 不暴露 `GET /contacts`、`PATCH /contacts/:id`，而是封装成 `search_contact`、`update_contact_field` 两个工具。工具数量控制在个位数，每个工具一个清晰意图。

**第三步：写好描述。** 工具描述是写给模型看的，不是写给人看的。参数 schema 里加 example，描述里写清"什么时候不该调用我"。这一步的投入产出比最高。

**第四步：处理鉴权。** 密钥全部走环境变量或配置文件，绝不出现在对话上下文里；先申请只读 scope 跑通，再逐个放开写权限。

**第五步：修整响应。** 适配器层负责截断、分页，把 HTTP 错误码翻译成结构化的 `{ok, error, hint}`——hint 告诉 Agent 下一步该干嘛：换参数、缩小范围，还是直接放弃。

**第六步：写操作加闸门。** 关键写操作加 `dry_run` 参数或显式 confirm，配合幂等键防重试副作用。

## 踩坑点

- **工具描述太模糊**：Agent 会在相近工具之间乱选。描述里写清边界，比反复改 prompt 有效得多。
- **返回整页 JSON**：一次没截断，上下文直接被打爆。适配器强制只返回必要字段 + 数据 ID，详情按需再取。
- **重试导致重复写**：Agent 对超时的第一反应就是重试。没有幂等键的写接口，等于埋雷。
- **长任务同步等**：一个跑 90 秒的导出任务把 Agent 卡死。改成"提交任务 + 轮询状态"两个工具。
- **限流没在适配器处理**：指望 Agent "礼貌重试"不现实，退避逻辑必须写死在封装层。

## 可复用建议

- 一把尺子：每个工具 = 一个意图 = 一句话能说清。说不清就拆。
- 渐进放权：只读 → 带确认的写 → 自动写，每一步观察一段时间再往下走。
- 适配层保持薄但独立：上游 API 改版只动这一层，不动 prompt 和工具描述。
- 上线前用对抗性输入测一轮：故意诱导 Agent 误用工具，看错误提示能不能把它拉回来。

## 总结

对接外部服务的核心不是"能调通"，而是给概率性的调用方一个确定性的边界。MCP 解决协议层，适配器解决数据层，工具设计和权限收敛解决行为层。三层都做扎实，握手才算握稳。欢迎大家在这个帖子里补充各自的封装模式。
