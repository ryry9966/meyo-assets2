## 背景

跑自动化迟早会撞上这种场景：定时任务重叠跑了一次、agent 超时后自己重试、MQ 消息重投、或者你手动补跑了一遍历史任务。只要任务里混着"追加一行""创建一条工单""发一条通知"这类操作，结果就是重复数据、重复通知，运气差一点就是重复扣款级别的事故。

在 OpenClaw 这类 agent + MCP 工具链的实践里，重复执行的来源比传统脚本更多：模型的不确定性会让它对同一个工具发起两次调用；MCP 工具超时重试，但服务端其实已经执行成功；调度器不知道上一轮任务还没结束。所以幂等性不是加分项，是这类系统的底线设计。

## 问题：重复从哪来

四条常见路径：

1. **重试**：网络超时 ≠ 执行失败。对端做完了，只是响应没回来，客户端按失败重试，动作就做了两遍。
2. **调度重叠**：任务耗时 90 秒，cron 间隔 60 秒，两个实例并行。
3. **至少一次投递**：webhook 和消息队列普遍承诺 at-least-once，去重是消费方的责任。
4. **Agent 自身**：模型怀疑"上一步可能没成功"，再次调用同一个工具。

幂等的定义很朴素：同一操作执行 N 次，效果与执行一次相同，即 f(f(x)) = f(x)。工程上的全部工作，就是把副作用改造成满足这个性质。

## 做法：三步改造

**1. 给副作用分类。** 天然幂等的不用管：把配置项设为固定值、覆盖写文件、按主键 upsert。危险的只有三类：追加类（append、insert）、增量类（累加、减一）、外发类（发消息、建工单）。

**2. 定义幂等键。** 一个执行前就能算出的确定性键，推荐 `hash(任务ID, 时间窗口, 参数摘要)`。比如日报任务的键就是"日报 + 当天日期"，天然一天一条。

**3. 执行前占位，执行后落账。** 一张 SQLite 表就够：

```sql
CREATE TABLE done_keys (k TEXT PRIMARY KEY, result TEXT, ts INTEGER);
```

执行前 `INSERT OR IGNORE`，插入成功才执行真正的副作用；插入失败说明做过，直接返回上次结果。Redis 等价写法是 `SET key val NX EX 86400`。MCP 工具同理：工具内部先查状态再决定是否执行，并把幂等键写进返回值，方便上层判断。

## 踩坑点

- **先查后做不是原子的。** 两个并发实例都查到"没做过"，然后都执行。占位必须原子：唯一约束、SETNX、文件锁任选其一。
- **把超时当失败。** 捕获异常就重试，是最大的重复来源。正确姿势是带着幂等键去查真实状态，而不是相信异常的语义。
- **键的粒度错了。** 键里掺时间戳或随机数，重试永远对不上；粒度太粗，合法的第二次执行被误杀。键由业务意图决定，不由"这一次运行"决定。
- **整条流水线重试。** 第 3 步失败从头跑，前两步的副作用又来一遍。重试粒度压到单步，每步有自己的键。
- **去重记录过期太快。** TTL 比最大重试窗口短，晚到的重试就漏过去了。

## 可复用建议

- 所有定时/队列任务默认带"任务 ID + 时间窗口"的键，一行判断能挡住九成重复。
- 能"设置目标状态"就不要"增量修改"：把库存设为 42 天然幂等，库存减一不是。
- 外发动作实在无法幂等时，先落本地记录再外发，失败后拿记录去对账，不要盲发。
- 写一个"连跑两遍"的用例：同一任务执行两次，断言副作用只发生一次。这条用例比任何 code review 都可靠。
- 在 MCP 工具或插件的描述里注明是否幂等，让 agent 规划重试时能利用这个信息。

## 总结

幂等不是引入某个库就自带的特性，而是每一个副作用边界上的设计决策。在 agent 和自动化系统里，重试、重叠、重投是常态而非异常。把"每个任务都会被执行两次"当作默认假设来设计，第二次执行就只是一次查表，而不是一条重复数据、一条重复通知。这件事做在前面是十分钟的设计，做在后面就是凌晨清洗数据。
