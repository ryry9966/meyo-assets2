## 背景

OpenClaw 里最容易被低估的配置之一，是 cron 任务的 instruction。很多人把它当成“一句话提醒”来写，但它的本质是：在指定时间，用一个全新的、没有任何对话历史的会话唤醒 Agent，这段 instruction 就是它醒来时拿到的全部信息。

交互聊天里你可以追问、可以纠正；cron 触发时你大概率在睡觉。所以 instruction 的质量，直接决定这条自动化是“稳定产出”，还是每周静默失败几次。

## 问题

一个真实感很强的反例：

> 每天早上 8 点帮我整理一下 GitHub 通知

这条任务跑起来的典型结果是：Agent 八点醒来，不知道用哪个工具、不知道“整理”的标准、不知道结果发到哪。要么自作主张发一大段没人看的消息，要么为了证明自己干了活，编一份“看起来合理”的汇报。

## 做法：拆成五个模块

我的习惯是把每条 cron instruction 写成一份“交接文档”，固定五个模块：

1. **时间锚点**：让 Agent 先跑 `date`，或显式写明时区。别假设它知道今天几号。
2. **任务目标**：一句话，只说一件事。
3. **数据来源**：用哪个工具、哪条命令、哪个 MCP 资源，写到可以直接执行的程度。
4. **判断标准**：什么算“有事”、什么算“没事”，阈值写死。
5. **输出契约**：发到哪个渠道、什么格式、没事怎么办（通常是“不发”）。

改造后：

```text
先运行 date 确认当前时间，再执行以下任务：
1. 用 gh 列出过去 24 小时的未读通知
2. 只保留 mention 和 review request，忽略 CI / bot 通知
3. 按 repo 分组，每条一行：repo / 标题 / 需要我的动作
4. 结果发到 #github-daily；若无符合条件的通知，不发消息
5. 完成后把最后处理时间追加到 ~/notes/gh-cron.state
```

区别不在文笔，在于它把所有“Agent 醒来后要做的决定”提前替它做完了。

## 踩坑点

- **每次运行都是新会话**。不要写“和上次一样”“按之前说的办”。跨次的状态落文件，instruction 里给路径。
- **没有“没事”分支**。没写“没有异常就不发”，Agent 往往会硬凑出一条汇报。空结果也是结果，要明确它的出口。
- **时区不一致**。cron 按主机时区触发，instruction 里的“今天”“早上”必须有明确锚点，否则夏天冬天各偏一次。
- **重复通知**。通知类任务必须幂等：用 state 文件记录上次处理位置，只报增量。否则一天三条重复消息，你很快会亲手把它关掉。
- **一条 instruction 塞多个任务**。频率不同、失败难排查，拆成多条 cron，每条一个职责。

## 可复用建议

- 新任务先在交互会话里把 instruction 原文跑一遍，确认输出符合预期，再挂到 cron 上——别用生产调度当测试环境。
- instruction 和 state 文件都放 workspace 里，进版本管理。改 prompt 就是改代码，要有 diff 可查。
- 从“每天一次、失败无损失”的任务起步（日报、摘要），稳定跑两周后，再提高频率或交给它写操作。

## 总结

Cron 任务的 instruction 不是提醒，是交接文档。交接对象是一个失忆、可靠、联系不上你的同事——它醒来时手里只有你写的那段话。时间、来源、标准、出口，四件事写清楚，这条自动化才配得上“自动”两个字。
