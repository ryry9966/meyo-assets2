## 背景

大多数时候，Agent 是被动的：你不问，它不动。OpenClaw 里有个容易被忽略的机制改变了这一点——workspace 根目录的 `HEARTBEAT.md`。Gateway 按固定间隔（默认 30 分钟，可配）触发一次心跳，Agent 读到这个文件后自行判断"现在有没有该做的事"：有就执行并汇报，没有就静默返回。

## 问题

cron 这类定时任务解决的是"固定时间做固定事"，但很多真实需求是状态驱动的：上游仓库有新提交吗？磁盘快满了吗？某项待办到期了吗？你希望 Agent 在"发现条件满足"时主动处理，而不是每天准点跑一遍脚本、或在群里刷存在感。心跳机制正好补上这一层，但配不好会走向两个极端：要么烧 token 却什么都没干，要么每隔半小时往你的聊天里发废话。

## 做法

1. **创建文件**：在 workspace 根目录建 `HEARTBEAT.md`，用 checklist 写任务，每条尽量包含三要素——触发条件、动作、沉默条件。例如：
   - 每次心跳执行 `git -C ~/blog pull`，有新提交才汇报，否则静默；
   - 检查磁盘用量，超过 80% 才发告警。
2. **调整间隔**：观察期建议 30–60 分钟，稳定后再拉长；设为 0 可整体关闭。
3. **写死静默协议**：没有值得汇报的事，Agent 应返回一个短确认（HEARTBEAT ack）而不是向聊天渠道发消息。把这条写进 HEARTBEAT.md 或 AGENT.md，作为硬性约束。
4. **分层放置**：低优先级任务放进单独小节（如 Optional），上下文紧张时可被跳过，保证核心任务稳定执行。

## 踩坑点

- **成本**：即使无事可做，每次心跳也是一次模型调用。任务越长、间隔越短，账单越难看。固定时间的重复事交给 cron，心跳只留状态驱动的检查。
- **行为漂移**：任务描述含糊（"帮我看看服务器"）会导致执行不可预期。写成"条件 + 动作 + 阈值"，越像 SLO 越好。
- **消息轰炸**：没写沉默条件时，Agent 可能把"一切正常"也汇报出来。经验是默认静默、异常才开口。
- **别当精确调度器**：心跳不保证准点，误差取决于队列负载。"到点必须做"的事用 cron。

## 可复用建议

- 从 1–2 个任务起步，跑几天看行为再扩，别一上来写满一页。
- 让心跳的执行结果落盘到一个日志文件，方便审计"它到底背着我干了什么"。
- 和 MCP 工具组合：心跳检查本身可以调用工具（拉 API 健康状态、读文件、跑脚本），这让它从"提醒器"变成真正的后台 worker。

## 总结

HEARTBEAT.md 的本质是给 Agent 一个定时的"自检机会"，但主动性来自设计而非机制本身：默认静默、条件明确、成本可控。把它当成低频、谨慎的后台巡检进程来写，它就可靠；当成自由发挥的助理来写，它就会用噪音教你删掉它。
