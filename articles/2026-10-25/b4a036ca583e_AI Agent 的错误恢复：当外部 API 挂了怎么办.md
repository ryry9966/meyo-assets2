## 背景

Agent 的能力边界，基本等于它能调到的工具。在 OpenClaw 里，无论是 MCP server、HTTP 插件还是自己写的 skill，底下都是外部 API。和传统单体应用不同，Agent 的调用是链式的：一次任务往往串着五六个外部依赖，任何一环抖动，整个任务就断掉。更麻烦的是，重试决策是 LLM 做的——它不像代码那样精确，处理不好就是烧 token、编数据。

## 问题：三种典型翻车现场

1. **裸异常进上下文**：工具抛 500 加完整堆栈，模型看到报错后开始"自由发挥"，要么瞎猜原因，要么编一份看起来合理的假数据交给用户。这是最危险的一种——不报错，但结果是错的。
2. **无限重试**：模型收到"请求失败"后原地重试，每轮都带着完整历史上下文，几轮下来 token 账单难看，对方限流也更狠。
3. **非幂等写操作被重试**：下单、发消息、建工单这类操作，超时时你根本不知道对方成没成功，盲目重试就是重复扣款。

## 做法：把重试从模型手里接走

核心原则一句话：**模型负责决策"接下来怎么办"，基础设施负责"怎么重试"。**

**第一步：统一错误信封。** 所有工具调用包一层，失败时不抛异常，而是返回结构化结果：

```json
{ "ok": false, "error_code": "UPSTREAM_TIMEOUT",
  "retryable": true, "hint": "5s 后可重试，最多 2 次" }
```

`retryable` 字段很关键——模型不需要理解 HTTP 语义，只需读这个布尔值。

**第二步：分层处理。**
- 可重试（超时、429、5xx）：工具层做指数退避加随机抖动，封顶 2–3 次，全程模型无感知；
- 不可重试（401、400、404）：把结构化错误连 hint 交给模型，让它决定换参数、换工具还是报告用户；
- 持续失败：上熔断，N 次失败后 fail-fast 冷却 30 秒，别让每个请求都去撞一遍。

**第三步：硬超时是必须项。** 每个 MCP 调用设超时（比如 15s），否则一个 hang 住的工具能把整个 agent loop 卡死。

**第四步：写操作加幂等键。** 客户端生成 UUID 作为 idempotency key，重试时复用。对方不支持的话，至少在工具层做本地去重记录。

**第五步：多步任务做检查点。** 长流程每完成一步就持久化中间状态，恢复时从断点续跑，而不是从头再来。

## 踩坑点

- **200 不等于成功**：不少 API 返回 200 但 body 里业务码是错的，信封层要把业务码也判掉。
- **退避不加抖动**：服务恢复瞬间，所有 agent 一起重放，刚活的接口再次被打挂。
- **重试历史灌进上下文**：三轮重试日志全给模型看，它会困惑甚至放弃。工具层内部消化，只在最终失败时给一句结论。
- **静默降级**：fallback 到缓存没问题，但必须在回复里说明"这是 X 分钟前的缓存"，否则就是制造幻觉。
- **429 别套用超时策略**：429 通常带 Retry-After，照着等，别自作主张。

## 可复用建议

- 错误信封、重试策略、熔断参数做成 per-tool 配置，别写死在代码里；
- 每次降级都发结构化日志（哪个工具、什么错、走了什么 fallback），事后才能复盘；
- 关键工具加启动时 health check，别等任务跑到一半才发现 API 早就挂了。

## 总结

Agent 的错误恢复不是 prompt 技巧，而是一层正经的工程结构：信封化错误、分层重试、熔断降级、幂等与检查点。模型只应该在"结构化的事实"面前做决策，而不是在原始异常里挣扎。把重试从上下文里拿出去，agent 会稳定得多——token 也省得多。
