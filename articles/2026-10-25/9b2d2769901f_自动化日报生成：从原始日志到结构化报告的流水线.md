## 背景

团队的每日进展散落在各种日志里：服务访问日志、定时任务输出、Agent 运行记录、CI 构建结果。日报本身不难写，难的是每天花半小时翻日志、复制粘贴，还要担心漏掉关键报错。这件事典型地"值得自动化，但不值得过度工程化"，这里记录我们搭的一条轻量流水线。

## 问题

原始日志有三个特征：量大、噪声高、格式杂。直接丢给 LLM 总结会遇到两类问题——上下文装不下；模型容易在细节上编造，比如把一条 WARN 夸成一次事故。所以核心思路是：**确定性脚本负责"算"，LLM 只负责"说"**。

## 做法

流水线分四步，用一个定时任务串起来：

1. **收集**：每天凌晨 cron 拉取前一天的日志，按来源落盘到 `logs/2025-06-01/` 目录。来源包括 nginx access log、应用 JSON 日志、Agent 任务执行记录。
2. **结构化**：一个 Python 脚本做清洗——解析时间戳、过滤 DEBUG、按错误码 / 接口 / 任务类型聚合计数，输出固定 schema 的 JSON：`{errors, top_endpoints, agent_runs: {total, failed, avg_cost}}`。这一步完全不经过 LLM。
3. **摘要**：把 JSON 喂给 Agent，通过 MCP 工具 `render_report` 生成 Markdown。prompt 只做一件事：按固定模板填槽，包括"异常摘要""与昨日对比""需人工关注事项"，每节限制不超过三行。
4. **分发与归档**：报告写入 `reports/YYYY-MM-DD.md`，推送群 webhook；中间 JSON 一并归档，便于事后核对。

整条流水线是幂等的：同一天重跑，直接覆盖同 key 的报告。

## 踩坑点

- **日期边界**：日志时间戳是 UTC，日报按本地日期切分，第一天统计少了 8 小时的量。后来统一在收集层做时区转换，再切日期。
- **格式漂移**：早期让 LLM 自由发挥，输出结构每天不一样，下游没法解析。改成严格模板 + JSON 槽位后才稳定。
- **静默失败**：cron 挂了三天没人发现。加了心跳文件——脚本成功后 touch 一个时间戳文件，另一个监控任务检查它是否超过 24 小时未更新，超时就告警。
- **采样截断**：为省 token 对错误日志做了截断，结果漏掉一个只出现在截断段的堆栈。原则改成：计数交给脚本，错误详情全量保留，但按去重后的指纹分组。

## 可复用建议

- 把"读日志""写报告"封装成 MCP 工具，而不是在 prompt 里塞路径和格式说明。Agent 的职责面收窄后，行为可预测，也更好测试。
- 中间产物（结构化 JSON）一定要落盘，它是排查"报告为什么这么写"的唯一依据。
- 先跑两周影子模式：自动报告与人工日报并行，对比差异后再切换，能提前暴露模板盲区。
- 报告按日期做 key，重跑即覆盖；不要 append，否则排障时会看到两份互相矛盾的版本。

## 总结

这条流水线代码量不到三百行，稳定运行后每天节省约半小时人工，更重要的是统计口径终于统一了。经验可以压缩成一句话：**让脚本处理确定性，让模型处理表达，让模板约束两者之间的接口。**
