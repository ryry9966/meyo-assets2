## 背景

用 OpenClaw 这类 agent 框架跑日常自动化，最常见的抱怨不是模型不够聪明，而是"它不记得我"。每个会话都是白纸：部署目标、偏好的包管理器、回复风格、常用项目路径——说过几十次的偏好，每次都得重新交代。MCP 解决了工具调用，记忆则需要自己设计。

## 问题

三个典型坑：

1. **直接把历史对话塞进 system prompt**：token 涨得快，噪音比信号多，成本和召回质量一起崩。
2. **让模型自由发挥地记**：沉淀下来的多是闲聊碎片，真正稳定的偏好反而没留住。
3. **只写不删**：三个月前的一次性上下文和今天的指令打架，agent 按旧偏好行事，用户以为是模型变笨了。

本质问题是：记忆系统要把"写入什么、怎么存、何时读、何时淘汰"当成独立的工程问题来解。

## 做法

我们在自己的 OpenClaw 插件里用了两层结构加一条流水线，跑了两个多月，够用且可控。

**第一层：结构化偏好卡。** 一张小的 key-value profile（类别、事实、置信度、时间戳、来源），控制在 2KB 内，每次会话固定注入 system prompt。只放稳定偏好：环境信息、工具习惯、风格要求。这是"必命中"的记忆，不依赖检索。

**第二层：情景记忆。** 会话级摘要片段带时间戳入库，用 embedding 做相似度检索，按语义相关度加时间衰减加权，取 top 3–5，和偏好卡共享约 800 token 的注入预算。

**写入流水线。** 会话结束后跑一次抽取，输出严格 schema 的候选记忆，置信度低于阈值直接丢弃；用户显式纠正（"我说过别用 npm"）走高优先级写入通道。存储用 SQLite + sqlite-vec 就够，不必一上来上独立向量库。

**更新与遗忘。** 新事实不覆盖旧事实，而是标记 supersede，保留版本链；偏好卡条目加 TTL，长期未命中且未确认的自动降权。同时通过 MCP 暴露 `memory_search` / `memory_write` / `memory_forget` 三个工具，让 agent 会话中能主动读写，也方便做用户可见的记忆管理面板。

**验收。** 准备 20–30 条偏好问答做回归集，改一版测一版，命中率稳定在 85% 以上再谈扩展。

## 踩坑点

- 抽取没有 schema 约束时，第一版记了一堆"用户今天心情不错"这类噪音，加了类别枚举和置信度阈值才收敛。
- 检索只看语义相似度，召回了半年前的旧部署流程；补上时间衰减和 supersede 过滤才恢复正常。
- top-k 一度给到 10，注入预算爆掉，主任务质量反而下降——记忆是配额制的，不是越多越好。
- 忘了做敏感信息过滤，密钥差点入库。现在抽取环节硬性排除凭证类内容。
- 全自动写入但没有用户入口，出问题时无法定位是记错了还是读错了。记忆必须可见、可改、可删。

## 可复用建议

1. 先分层再谈智能：必注入的小偏好卡 + 检索式情景记忆，覆盖 90% 场景。
2. 写入必须结构化、带置信度、带时间戳，宁缺毋滥。
3. 更新用 supersede，别 overwrite，保留可回溯性。
4. 给记忆设 token 配额，给用户设管理入口，这两条决定系统能否长期跑。
5. 没有回归评测集，记忆系统的一切调优都是盲调。

## 总结

记忆系统不玄学，核心是把"记住"拆成写入、存储、检索、淘汰四个可控环节，每一步可观测、可回滚。先用最朴素的分层方案把召回质量做稳，再考虑更复杂的策略。一个能被用户看见、纠正的记忆系统，比一个看起来聪明但不可控的黑盒更值得信任。
