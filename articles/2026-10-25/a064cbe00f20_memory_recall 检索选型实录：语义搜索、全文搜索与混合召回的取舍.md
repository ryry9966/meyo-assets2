## 背景

OpenClaw 这类常驻 Agent 的 memory_recall，本质是“把过去记下的东西在合适的时机找回来”。我的场景：一个长期跑的个人助理，记忆库约 800 条笔记（用户偏好、项目上下文、踩过的坑），每轮对话触发一次 recall，把 top-k 拼进上下文。检索层最初用的纯语义，后来改成混合召回，这里记录一下取舍过程，给同样在做记忆插件的兄弟省点弯路。

## 问题

纯语义检索（embedding + 向量相似度）的短板：

- **精确 token 召不回**。报错码 `ECONNRESET`、路径 `/etc/nginx/`、项目代号这类词，embedding 常被泛化成“网络错误”“配置文件”，而我要的恰恰是那个精确串。
- **小语料区分度差**。几百条记忆的向量挤在一起，top-5 经常是一堆“语义相邻但不相关”的条目。

纯全文检索（FTS）则是反过来的问题：

- **换个说法就查不到**。记的是“部署超时”，问的是“上线卡住”，零命中。

所以真正的问题不是“哪个好”，而是各自擅长什么、怎么组合。

## 做法

我的方案是 SQLite 单库 + 双通道召回 + RRF 融合：

1. **写入侧**：每条记忆一行，正文控制在 1–3 句，写完同时建 FTS5 索引和向量索引（sqlite-vec，本地 embedding 模型，768 维）。
2. **召回侧**：一次 recall 并行跑两路——FTS5 对查询分词后做 MATCH；向量路用同一模型 encode 后 KNN，各取 top-10。
3. **融合**：用 Reciprocal Rank Fusion（1/(60+rank)），只看名次不看原始分，融合后取 top-5。
4. **后处理**：按 updated_at 做轻微新近度加权（只调排序不动召回），去重后拼入 prompt。

改动量很小，recall 函数约 60 行，没有引入额外服务，嵌入本地跑，离线可用。

## 踩坑点

- **中文分词是 FTS 路的前置条件**。FTS5 默认 tokenizer 对中文基本等于整句一个 token，必须上 jieba 或 trigram，否则中文全文检索形同虚设。这是我第一次上线最痛的一课。
- **分数不要硬融**。余弦分数和 BM25 分数分布完全不同，直接加权相加会翻车；RRF 只用名次，省去归一化，效果反而稳。
- **chunk 别贪大**。早期把整篇日记切成一条记忆，召回粒度太粗，命中十条只对上半句。改成“一事一条”后明显改善。
- **top-k 不是越大越好**。从 5 加到 10 后，任务成功率没涨，token 消耗先涨了。召回质量比数量重要。
- **记忆要有失效机制**。过期排期、已被推翻的结论，不清理的话语义路会一直把它们捞回来。

## 可复用建议

- 记忆少于两三百条：先只上 FTS（把分词做好），够用。别为了“用向量”而用向量。
- 语料过千、查询措辞多变：上混合召回，FTS 管精确词，向量管改写，RRF 兜底。
- 固定一组 20 条“必须召回”的查询用例做回归测试，换模型、调参前先跑一遍，别凭感觉。
- 报错码、路径、人名这类精确标识符，写入时抽成独立字段保证 FTS 可命中，别指望 embedding 记住它们。

## 总结

语义搜索解决“换了说法还能找到”，全文搜索解决“精确的东西一定找到”。在个人助手的 recall 场景里，两者是互补而非二选一：小语料用全文起步，混合召回 + RRF 是工程上最省事的平衡点。最后一点心得了——recall 的上限由写入侧决定，怎么记比怎么搜更关键，检索器只是把已经记好的东西找出来而已。
