## 背景

在 OpenClaw 这类常驻型 Agent 环境里，自动化任务的触发源很多：cron 定时、消息指令、Webhook 回调、MCP 工具调用，以及 Agent 自身的失败重试。网络抖动、网关超时、渠道重复推送，都会让"同一次逻辑执行"在物理上跑两遍甚至多遍。你无法阻止重试发生，只能保证重复执行无害——这就是幂等性。

## 问题

非幂等操作在重复执行时副作用会叠加：

- "追加写"日志或清单 → 同一条记录出现 N 次
- "发送消息"类通知 → 群里被刷屏
- "创建"工单、文件、数据库行 → 资源膨胀
- "调用第三方 API" → 计费翻倍

典型翻车现场：定时同步任务凌晨因 cron 重叠跑了两遍，收件箱里躺着两条一模一样的日报。这类 bug 平时不出现，只在重试、重启、并发时出现，且难以复现。

## 做法

核心思路：给每次**逻辑执行**一个稳定标识，执行前后用这个标识对外部状态做判断。

1. **构造幂等键**。从稳定输入派生，例如 `任务名 + 触发源 ID + 时间桶`。不要用运行时随机数或当前时间戳，重试时必须能算出同一个键。
2. **持久化去重账本**。用一个 SQLite 表或 JSON 文件记录"已处理过的键"。执行前查询，命中则跳过；成功后写入。在 OpenClaw 插件里放一个十几行的 dedupe 模块就够用。
3. **优先 upsert，而非 create**。写文件用"内容一致则跳过，不一致则覆盖"；写数据库用 `INSERT OR REPLACE`；发通知优先"编辑原消息"而不是"再发一条"。
4. **对无幂等保证的外部 API 做客户端记账**。调用前先落账（pending），成功后更新为 done，重启后扫描 pending 对账或补偿。
5. **并发场景加锁**。cron 可能重叠时，用文件锁或数据库唯一约束兜底，把"检查—执行—记账"变成原子操作。

## 踩坑点

- **键里掺了随机性**：在任务内部生成 UUID 当幂等键，每次重试都是新键，等于没做。
- **时间桶边界**：用"当天日期"做键，重试恰好跨零点，同一逻辑被记成两天。桶的粒度要大于最大重试窗口。
- **键太粗**：只按"任务名 + 日期"去重，同一天两次合法触发被误杀。键的粒度要精确对应"一次逻辑执行"。
- **账本没持久化**：去重状态放内存里，Agent 重启后清零，重复执行照旧。
- **只在调用处去重**：副作用散落在多个插件里，没有统一账本层，漏永远补不完。

## 可复用建议

- 把"跑两遍测试"纳入验收：任何新自动化任务上线前，手动连续触发两次，对比外部状态是否一致。
- 幂等键的构造规则写进插件规范，团队统一实现，不要各写各的。
- 为无法幂等的外部操作准备补偿动作（删除、回滚、标记失效），比追求一次成功更可靠。
- 日志里打印幂等键和判定结果（skip / execute），排障时一眼看出重复发生在哪一层。

## 总结

幂等性不是锦上添花，而是常驻自动化任务的地基。重试、重叠、重复推送一定会发生，区别只在你是有准备地跳过，还是无准备地翻车。一个稳定的幂等键加一份持久化账本，成本不到五十行代码，能省掉未来无数个深夜的排查时间。
