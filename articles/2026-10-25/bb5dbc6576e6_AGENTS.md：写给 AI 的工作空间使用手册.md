## 背景

AGENTS.md 是近一年逐渐被各家 Agent 工具接受的约定：在仓库或工作区根目录放一个同名 Markdown 文件，Agent 启动会话时自动读取，作为工作区级上下文注入。OpenClaw 遵循同一约定，而且不止于人机对话——定时任务、webhook 触发的自动化、MCP 工具调用，读到的都是同一份文件。

它的定位很明确：README 写给人看，AGENTS.md 写给模型看。

## 问题

没有这份文件时，痛点很具体：

- 新会话每次都要口头交代项目结构、构建命令、代码风格，忘了说就翻车；
- Agent 在 pnpm 项目里跑 `npm install`，在 vitest 项目里跑 `jest`；
- 无人值守的自动化任务没人纠偏，第一次错，后面每次都错；
- 团队成员各自手写 system prompt，AI 行为因人而异。

本质是工作空间的隐性知识，没有被固化为机器可读的显性上下文。

## 做法

最小可用版本十分钟就能写完。在 OpenClaw 工作区根目录创建 `AGENTS.md`，按四段组织：

1. **定位**：一句话说清这个工作区是什么、不是什么；
2. **环境事实**：语言版本、包管理器、端口、测试框架——只写可验证的事实；
3. **操作守则**：常用命令、工具调用顺序、MCP server 选择偏好、插件触发约定；
4. **红线**：禁止事项，写具体动作，不写态度。

两个原则比内容本身更重要：

- **写规则，不写形容词**。“用 pnpm，禁止 npm” 有效；“请认真规范地操作” 无效。
- **关键信息放前面**。上下文有限，最重要的约束放在文件头部。

项目变大后用分层：根目录放全局约束，子目录放各自子项目的构建与测试约定，OpenClaw 进入对应目录时叠加生效。

## 踩坑点

- **写成 README**。塞满项目介绍和历史沿革，真正有用的十行规则被淹没。
- **命令过时**。构建流程改了但忘了更新文件，AI 每次按旧命令失败——比没有更糟。把“检查 AGENTS.md”放进 PR checklist。
- **多份指令文件互相打架**。与其他约定文件并存时内容冲突，模型行为摇摆。确认 OpenClaw 的读取优先级，保持单一事实源。
- **红线写模糊**。“不要动生产配置”不如“禁止修改 `infra/` 下任何文件，确需改动先停下询问”。
- **只增不减**。每次踩坑加一段，半年后三千行，约束被稀释。定期删掉模型已稳定遵守的条目。

## 可复用建议

- 每条规则写成“触发条件 + 动作”，便于模型匹配，也便于日后审计；
- 用真实失败案例回填：AI 犯一次错，就补一条针对性规则，这份文件会逐渐长成团队的运维记忆；
- 自动化任务建议在文件里约定输出格式与失败时的行为（停下、上报还是降级），无人值守场景这条最值钱；
- 把它当 CI 配置维护，而不是当文案写：有变更、有 review、有版本。

## 总结

AGENTS.md 的价值不在长短，而在于把“这个工作区该怎么干活”的共识固化下来，让每次会话、每个定时任务都站在同一份上下文上。写它的过程，本质上是在逼你把隐性经验显性化——这本身就是收益。
