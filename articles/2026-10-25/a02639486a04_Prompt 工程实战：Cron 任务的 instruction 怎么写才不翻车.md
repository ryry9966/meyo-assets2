## 背景

OpenClaw 的 cron 任务和传统 crontab 有一处本质区别：传统 cron 执行的是确定性命令，而 agent cron 调度的是一次 LLM 会话——**你的 instruction 就是程序本身**。同一条指令跑十次，可能得到十种输出。这是灵活性，也是坑。

我在社区里见过不少 cron 配置，instruction 写得像随口聊天："每天早上帮我总结一下未读消息"。这种写法上线后大概率出现：有时总结很长、有时很短；时间窗口忽大忽小；工具报错时干脆编一段摘要出来。

## 问题拆解

Cron instruction 的特殊性在于三点：

1. **没有对话上下文**。定时触发是一次冷启动，不存在"上文"，你以为的默契并不存在。
2. **时间是模糊的**。"昨天""早上"这类相对词依赖模型对当前时间的推断，凌晨触发或跨时区时容易错。
3. **输出没有即时消费者**。夜间任务跑偏了，可能几小时后才被发现，甚至悄悄发错频道。

## 我的做法

把 instruction 当规格说明书写，固定用五段结构：

1. **触发上下文**：声明这是定时任务，锚定当前时间。框架支持注入时间变量就注入，不支持就写明计算规则和时区。
2. **任务目标**：一句话说清做什么、数据来源、时间窗口。例："读取消息日志中距当前时间 24 小时以内的记录"。
3. **执行步骤**：列出 MCP 工具的调用顺序，以及某一步失败时的走向。
4. **输出模板**：给定死格式。比如固定三节——要点 / 待办 / 异常，每节最多 N 条，总长不超过 X 字，发到哪个频道、用什么消息类型。
5. **禁止事项**：明确"不要回复任何用户消息""不要发送模板之外的补充说明""工具失败时不要猜测内容，改为发送固定文案"。

写完先手动触发一次（临时改成几分钟后的时间，或用单次运行入口），看日志确认工具调用路径和输出格式，再改回正式周期。

## 踩坑点

- **相对时间翻车**：我写过"总结昨天的消息"，凌晨 0:05 触发时"昨天"被理解成了一段含混的窗口。改法是永远注入/锚定绝对时间。
- **附加礼貌回复**：指令没说死，agent 干完活还发一句"已完成，需要我做别的吗"。夜间推送场景里这就是垃圾消息。现在每条任务都带"禁止任何模板外输出"。
- **静默编造**：工具返回 403 时模型不报错，而是"合理想象"一份摘要。失败分支必须显式写出来。
- **频道错投**：多个 session 共用时输出进了默认频道。输出目标要写死，不留默认值。
- **指令过长**：把所有规范塞进一条 instruction，token 成本上去了，模型反而抓不住重点。通用规范放系统提示或工作区文件，cron instruction 只留本次任务差异化的部分。

## 可复用建议

- 把 cron instruction 存进版本库，输出不理想就改一版，像改代码一样 review。
- 上线前连续手动触发 3–5 次，观察输出方差；方差大说明指令还不够"死"。
- 高频任务（每小时）优先压缩指令长度；低频任务（每天/每周）可以容许更详细的模板。
- 失败分支的价值高于成功分支：宁可收到一条"本次汇总失败"，也别收到一份编造的日报。

## 总结

Cron 任务的 instruction，本质是"写给未来某次冷启动会话的程序"。把上下文、时间锚点、数据来源、输出模板、失败分支这五件事写清楚，定时任务就从抽奖变成了可依赖的服务。先手动验证再上线，出了问题改指令，而不是调低期望。
