## 背景

跑 Agent 自动化的人迟早会撞上这一幕：一条流水线串着五六个外部依赖——LLM 接口、MCP 工具、第三方 SaaS——凌晨其中一家返回 502，整条 run 报废。更糟的是 Agent 的"自作主张"：拿到报错后无限重试，或者干脆编一个结果交差。错误恢复不是包一层 try/except 就完事，它需要被当成一个子系统来设计。

## 问题拆开看是四类

1. **瞬时故障**：429、502、超时、连接重置。占比最高，重试即可解决。
2. **持久故障**：401 鉴权失效、404、配额耗尽。重试只会烧钱。
3. **半成功状态**：调用实际写库成功，但响应超时没拿到，重试导致重复下单、重复发消息。
4. **静默失败**：工具层吞掉异常，Agent 拿到含糊返回值，最后产出一份看起来正常、实则错误的数据。

## 做法

**第一步：错误分类前置。** 在工具封装层把错误归为 retryable / fatal 两类，别让 LLM 去猜。4xx 里的 401/403/404/422 基本是 fatal，429/5xx/timeout 是 retryable。统一返回结构化信封，例如 `{ok:false, retryable:true, code:502}`，Agent 的规划层才能做有效决策。

**第二步：有界重试 + 抖动。** 指数退避起步 1s、倍率 2、上限 3~4 次，每次加随机 jitter。重试逻辑放在代码里、设死上限，绝不要放进模型的决策循环——那是烧 token 的无底洞。

**第三步：幂等保护。** 所有写操作带幂等键（请求哈希或业务 ID），重试前先查状态。做不到幂等的操作，宁可失败后人工介入，也别自动重试。

**第四步：断路器 + 降级。** 连续 N 次失败就熔断，快速失败并走降级路径：备用 provider、缓存数据，或标记 skip 后继续后续步骤。比整条流水线卡死好得多。

**第五步：检查点续跑。** 长流水线每步落盘状态，恢复时从失败那一步继续，而不是从头再来。

## 踩坑点

- **无 jitter 的重试**：服务恢复瞬间所有客户端同步重试，把刚喘过气来的上游再打挂一次。
- **超时层级倒挂**：外层 Agent 超时 30s，内层 HTTP 超时 60s，外层先断、内层还在跑，制造大量孤儿请求。每层超时应递减。
- **把 400 当瞬时错误重试**：参数问题重试一百次还是 400，只会烧配额。
- **日志只写 "call failed"**：不记状态码、响应体、耗时，事后排查等于瞎猜。失败日志至少要有错误码 + 截断后的响应体 + attempt 次数。
- **批量操作的部分成功**：10 条写入成功 6 条，第 7 条挂了，重试是全量还是增量？没想清楚就是数据事故。

## 可复用建议

- 所有外部调用走同一个客户端封装，超时/重试/日志策略集中配置、按工具覆盖。
- 每个工具的降级策略写进配置，而不是故障时现想。
- 建一个失败任务队列（哪怕只是本地 JSON 文件），支持手动回放。
- 盯三个指标：成功率、重试率、熔断触发次数。重试率突然抬头，往往是上游故障的最早信号。

## 总结

错误恢复 = 分类 + 有界重试 + 幂等 + 降级 + 可续跑。核心原则就两条：让代码处理可预测的失败，让 Agent 只拿到机器可读的失败信息去做规划。别指望模型自己"聪明地"消化 502——把工程问题留在工程层解决，Agent 才能真正稳定地跑在无人值守的自动化里。
