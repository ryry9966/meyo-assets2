## 背景

LLM 会话天然无状态，上下文窗口再大也是一次性消耗品。OpenClaw 这类常驻 agent 的价值恰恰在长期服务：它应该记得你用 pnpm、提交信息写中文、时区是 UTC+8。MCP 让挂外部存储变得很容易，所以"记不住"已经不是能力问题，而是设计问题。

## 问题

社区里最常见的三种失败模式：

1. **全量回灌**：把历史对话原样塞回 prompt。token 成本线性上涨，注入一多，指令遵循明显漂移。
2. **靠模型自觉**：只在 prompt 里写"请记住我的偏好"。模型嘴上答应，下个会话全忘——没有持久化，"记住"只是话术。
3. **只写不删**：记忆只增不减，三个月后召回的全是过期偏好和寒暄噪声，反而污染上下文。

## 做法

把记忆当数据工程做，拆成 schema、写路径、读路径、生命周期四块。

**1. 分层。** 核心档案（稳定高频的事实）启动时全量注入，严格控制在两百 token 内；长尾偏好走按需检索；会话摘要是短期压缩，和长期记忆分开存。

**2. 定 schema。** 一条记忆只存一个原子事实：

```json
{"id":"m_01","content":"偏好 pnpm 而非 npm","category":"tooling","confidence":0.9,"source_session":"s_88","created_at":"...","last_seen":"..."}
```

原子化才好去重、处理冲突和删除。

**3. 写路径：双通道。** 显式通道是注册一个 `memory_save` MCP 工具，由 agent 判断"值得记"时主动调用；后台通道是会话结束后跑一次抽取 pass，把对话转成候选记忆。抽取判据必须写死：只收可复用、相对稳定的偏好和事实，一次性请求（"这次先上 React"）不收。

**4. 读路径：注入 + 工具。** 核心档案启动注入，并用分隔符标明来源；长尾记忆靠 `memory_search` 按需检索，用关键词 + 向量的混合召回——纯向量会漏掉项目名、人名这类精确匹配。

**5. 生命周期。** 相似度去重；冲突时新值覆盖旧值但保留历史；`last_seen` 长期不更新就降权归档；最重要的一条：给用户一个可见、可编辑、可删除的记忆列表。

**6. 验证。** 攒二三十条偏好做评测集，隔几个会话直接问"我的包管理器是什么"，测命中率。没有评测的记忆系统没法迭代。

## 踩坑点

- **注入过量**：核心档案一膨胀，agent 开始答非所问。上限要写死在代码里，而不是靠 prompt 求模型自觉。
- **抽取器太宽**：早期版本连"今天天气不错"都存。后来在判据里加了一句"这条信息半年后还有用吗"，噪声立刻少一半。
- **多 agent 串味**：几个 agent 共用一个库时忘了做 namespace，A 的个人偏好泄漏进 B 的上下文。按 user + agent 双层隔离。
- **召回 ≠ 注入**：检索回来的记忆若只是混进上下文，模型不一定当真，要显式标注"以下为记忆库检索结果，优先级高于默认行为"。
- **遗忘比记忆更难**：没有删除入口的记忆系统，用户信任会崩。

## 可复用建议

- 起手用 Markdown/JSON 文件加关键词检索就够了，记忆量上千条再考虑向量库。
- 每次写入都带 `source_session`，排查"它为什么这么认为"时是救命字段。
- 记忆格式选人可读的，出问题直接打开文件看，别把自己锁进黑盒。
- "哪些该记"的判据显式写在抽取 prompt 里，比指望模型自己判断靠谱得多。

## 总结

记忆系统不是"给模型加个脑子"，而是一条完整的数据管线：什么值得记、怎么存、怎么召回、怎么过期。schema、写路径、读路径、生命周期，这四件事想清楚，一个百来行的 MCP 插件就能让助手从"每次重新认识你"变成"真的了解你"。先跑通最小闭环，再谈规模。
