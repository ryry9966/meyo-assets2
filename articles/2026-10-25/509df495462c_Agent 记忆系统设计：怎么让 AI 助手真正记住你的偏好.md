# Agent 记忆系统设计：怎么让 AI 助手真正记住你的偏好

## 背景

折腾 OpenClaw agent 自动化一段时间后，一个感受越来越明确：模型能力不是瓶颈，瓶颈是“上次说过的话，这次还记得”。上下文窗口再大，也不可能把几个月积累的偏好全部塞进 system prompt。这篇记录我给自己 agent 设计记忆层的过程，思路对任何基于 MCP 的助手都通用。

## 问题

我最初的方案很原始——把用户偏好整理成一大段常驻 prompt。两个后果：

1. **prompt 膨胀**：成本上升，注意力被稀释，模型开始“忽略”中间的指令；
2. **无法演化**：用户换了技术栈，旧结论还赖在 prompt 里，冲突时无从仲裁。

另一条路是全量进向量库，结果召回一堆“话题相似、语义无关”的内容，噪音比帮助多。

核心判断：记忆的重点不是“存得多”，而是“取得准、更新得动”。这更像一个数据工程问题，而不是模型问题。

## 做法：分层记忆 + 受控抽取

**1. 分层存储。** 拆成三层：语义记忆（稳定偏好，结构化 key-value）、情景记忆（会话摘要，带时间戳）、工作记忆（当前会话上下文，不持久化）。90% 的“记住偏好”需求落在语义层，几十条封顶。

**2. 定义“值得记”的标准。** 只收三类来源：用户显式声明（“以后都用 pnpm”）、可复现的行为模式（连续多次选 TypeScript）、对 agent 错误的纠正。每条带 `{category, key, value, confidence, source, timestamp}`。

**3. 抽取管道。** 会话结束后跑一个轻量抽取 pass 产出候选事实，过类别白名单和置信度阈值才落库。抽取与主对话分离，不污染主上下文。

**4. 注入策略。** 语义层少量核心偏好常驻 system prompt；情景记忆封装成 MCP 工具（`memory_search`），让 agent 按需召回，而不是每次全量塞入。

**5. 冲突与过期。** 新旧事实冲突时按 confidence + 时间戳仲裁，写一条 diff 日志；注入时附带时间信息，让 agent 能判断“这条是否还成立”。

## 踩坑点

- **过度抽取**：闲聊也会被抽成事实，一周库就脏了。白名单 + 置信度门槛缺一不可。
- **向量检索噪音**：纯 embedding 召回“话题近、语义远”。以结构化 key 命中为主，向量只做兜底。
- **记忆投毒**：模型某次搞错、用户顺手确认，错误就被固化。source 字段必须保留，低置信度条目要容易被覆盖。
- **敏感信息**：用户贴过 API key，抽取管道要先过敏感模式过滤，写之前拦掉。
- **提示注入**：召回的记忆本质是用户内容，注入时按数据对待，不能给指令地位。

## 可复用建议

- 别一上来就上向量库。一个手工可编辑的 memory 文件（定位类似 CLAUDE.md）能解决大半问题，先跑通再升级。
- 给用户“看得见、改得动”的入口：一条命令列出当前记忆 + 支持删除/修正。信任和可调试性都靠它。
- 写路径和读路径分开评测：用历史会话测抽取质量，用查询集测召回命中。
- 记忆条目设上限、做去重合并，增长必须有界。

## 总结

记忆系统的关键不在存多少，而在分层结构 + 严格的抽取标准 + 可见的治理入口。小而准的结构化记忆，比大的向量堆更接近“真正记住你”。先把 profile 做干净，再考虑情景检索，顺序反了大概率返工。
