## 背景

LLM 本身无状态，每个会话开始，模型对用户一无所知，偏好和上下文全靠现场重述。对 OpenClaw 这类常驻的个人助理 Agent 来说，这是体验上最大的短板：解释过一遍的代码风格、时区、常用工具，下个会话又忘了。“加记忆”听起来简单，实际坑不少。下面是我们跑了数月、仍在用的一套最小可行方案。

## 先说三种错误姿势

1. **全塞 system prompt**：起初很爽，三个月后里面两千条“用户喜欢 X”，成本飙升且互相矛盾。
2. **依赖会话内记忆**：换个会话就清零，等于没做。
3. **聊天记录全量进向量库**：检索召回一堆闲聊噪声，关键偏好反被淹没。

本质：记忆不是存储问题，而是**写入、读取、遗忘三条路径的设计问题**。

## 做法：分层、预算、可控写入

**1. 分两层存。** 核心画像放结构化小文件（`profile.json`），只存稳定偏好——称呼、时区、语言、代码风格、禁用词，常驻 system prompt，控制在 300 token 内。情景记忆放追加式 `memory.md`，每条形如 `- [2025-06-03][偏好] 代码评审回复用中文，示例优先 Python`，带时间戳和类别，不常驻、按需检索。

**2. 控制写入。** 不要让模型随便写。稳定触发只有三类：用户显式说“记住…”；会话结束时 hook 做一次抽取，只保留事实类陈述；用户直接改文件。入库前去重并查冲突，同类新记忆覆盖旧的，旧条目归档而非删除。

**3. 读取有预算。** 核心画像常驻；情景记忆按当前任务检索，命中后按“重要性 × 新鲜度”排序，记忆段总预算硬上限 500 token，超了砍尾部。宁可少，不要杂。

**4. 做成工具而非管道。** 在 OpenClaw 里把读写封装成 MCP 工具（`memory_search` / `memory_write`），模型可主动调用，但 write 走类别白名单校验。记忆文件放在 workspace 下，用户随时能看、能改——这对信任感非常关键。

## 踩坑点

- **写入太勤**：模型会把“我今天有点累”也存进去。类别白名单 + 只收事实类陈述后，垃圾量降了一个数量级。
- **记忆打架**：用户半年后换了主力语言，新旧记忆同时被召回。时间戳 + 覆盖策略必须第一天就有，后补很痛苦。
- **检索噪声**：纯相似度会召回大量低价值条目，给记忆加来源与重要性权重，比换 embedding 模型有效得多。
- **当数据，别当指令**：记忆来自对话，可能被注入恶意内容，注入 prompt 时要明确标注为参考资料，绝不进指令位。
- **过度工程**：一上来就上图数据库。可 diff 的 markdown 够用很久，规模到了再演进。

## 可复用建议

- 记忆分两层：稳定画像常驻，情景记忆按需检索。
- 每条记忆四件套：时间戳、类别、来源、置信度。
- 写入走白名单，读取设硬预算，遗忘靠归档不靠删除。
- 记忆对用户可见、可编辑、可导出。
- 先文件，后向量，最后再考虑图谱。

## 总结

让 Agent 记住偏好，核心不是选哪个数据库，而是把写入、读取、遗忘当成三条独立路径分别设计，并始终让用户看得见自己的记忆。最小可行版本，一个 JSON 加一个 markdown 就能跑起来——先做准确，再谈聪明。
