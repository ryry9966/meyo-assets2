# 背景

Agent 跑长任务时，最不确定的因素往往不是模型，而是外部依赖。MCP 工具、第三方 HTTP API、内部微服务，任何一个都可能超时、限流或直接 503。模型本身很稳定，任务失败大多发生在工具调用这一层。

# 问题

常见的写法是工具报错后，把原始异常直接丢回模型：`ConnectionError: ...`。后果通常是：

1. 模型看到报错就开始"猜"，乱改参数重试，越改越偏；
2. Agent 循环里重试一层，工具封装里又重试一层，实际请求次数相乘放大；
3. 遇到非幂等操作（POST 建单、发消息），重试造成重复数据；
4. API 已经彻底挂了，Agent 还在循环里烧 token，几十轮后产出一份残缺结果。

# 做法：四层防线

**第一层：错误分类。** 在工具封装层把异常归一化成结构化 JSON：

```json
{
  "error_type": "rate_limit | timeout | server_error | client_error | network",
  "retryable": true,
  "attempt": 2,
  "suggested_action": "wait_and_retry"
}
```

关键区分：429 / 5xx / 超时可重试；400 / 401 / 403 不可重试——重试只会浪费额度，该改参数或换凭证。

**第二层：指数退避 + 抖动。** 可重试错误按 1s → 2s → 4s 退避，并加 0~30% 随机抖动。不带抖动的固定间隔，会在服务恢复瞬间形成请求风暴，把刚缓过来的 API 再打挂一次。

**第三层：熔断。** 同一工具连续失败 N 次（比如 5 次），标记为不健康，冷却 60 秒内不再调用，直接走降级路径。熔断要能自动半开探测恢复，否则服务好了 Agent 还在绕远路。

**第四层：降级链。** 主工具失败 → 备用 provider → 本地缓存 / 上次快照 → 明确告知用户"这一步暂时做不了"。对 LLM 侧，返回 `suggested_action` 让模型自己选择切工具还是上报，而不是硬编码死流程。

另外两件事必须做：

- **幂等键**：所有写操作带 idempotency key，重试不会重复建单、重复发消息。
- **状态持久化**：长任务每步落盘，恢复时从断点继续，而不是从头再跑。

# 踩坑点

1. **双重重试**：Agent 框架自带 retry，你的封装层又 retry，3×3=9 次请求。重试只放一层，建议放工具层，Agent 层只读 `retryable` 标志。
2. **原始报错进上下文**：几千字符的 HTML 错误页塞给模型，除了污染上下文、诱发幻觉没有任何收益。归一化后再返回，原始堆栈进日志。
3. **超时 ≠ 失败**：请求超时时，服务端可能已经执行成功。没有幂等键就盲目重试，数据就双写了。先查状态，再决定是否重放。
4. **熔断阈值拍脑袋**：太低会把正常抖动当故障，太高失去保护意义。用滑动窗口的错误率代替固定次数，更稳。
5. **冷却后不探测**：熔断打开后如果永远等人工恢复，长任务就废了。半开状态放一个探测请求，成功即恢复。

# 可复用建议

- 所有 MCP 工具调用统一过一个错误归一化中间层，固定产出 `error_type / retryable / suggested_action` 三元组；
- Agent 全局设 deadline，超出的任务标记暂停，而非无限重试；
- 重试、熔断、降级事件全部落日志，事后能复盘到底是 API 抖动还是自己代码的问题；
- 降级链里"问用户"永远是合法选项，比让模型硬编一个假结果强得多。

# 总结

外部 API 挂掉不是异常路径，而是 Agent 工程的常态。核心思路三句话：错误先分类，重试要有界，失败要能降级。把这三件事做进工具封装层，模型层只消费结构化的错误信息，Agent 才能在依赖不稳定的环境里跑得久、停得住、恢复得快。
