## 背景

跑 Agent 的日常，最常见的翻车不是模型不会解题，而是它对“这台机器”想当然：在 macOS 上敲 `apt`，把脚本写到不存在的路径，或者对着一个根本没装的 MCP 工具反复重试。AGENTS.md 这类文件解决了“这个项目怎么干活”，但“这台机器长什么样”往往无处可写，全靠 Agent 现场猜。

tools.md 就是补这个缺口的：一份由人维护、Agent 开工前必读的环境说明书。

## 问题

环境信息散落在 .env、shell rc、CI 配置和聊天记录里，至少带来三类麻烦：

1. Agent 靠试探摸环境，每换一台机器都重新交学费，浪费 token 也浪费时间；
2. 同一任务在笔记本、容器、服务器上行为不一致，排查时分不清是配置差异还是逻辑 bug；
3. 事后复盘“当时为什么能跑通”，没人说得清。

## 做法

我们的约定是：分层放置、可生成、有人认领。

**1. 分层。** 仓库里放一份 tools.md，写与本仓库相关的工具链：怎么跑测试、lint、构建；用户级再放一份全局的（如 `~/.config/openclaw/tools.md`），写机器底座：OS、shell、包管理器、Python/Node 版本、代理设置、可用 MCP server 清单。AGENTS.md 里只放一行指针，不重复内容。

**2. 只写“查不到或容易猜错”的。** `node -v` 能查到的可以不写；但“build 前要先 source 某个脚本”“GPU 任务走另一条队列”这类隐性知识必须写。经验值：单份控制在 80 行内，超了就该拆。

**3. 动态部分交给脚本。** 我保留一段人写的事实（约定、坑），另用一个小脚本输出 `tools.snapshot.md`（已装工具、版本、路径），定期刷新。人写的不漂移，机器生成的不陈旧。

**4. 环境差异用“分节”而非多副本。** 不维护 tools.linux.md / tools.macos.md 两套，而是在同一文件里按平台分节，开头写明“先确认平台，只读对应小节”。多副本必然漂移。

**5. 红线：不写密钥。** tools.md 会整份进上下文，任何 token、内网地址都用环境变量引用，例如“连接串在 `$MY_DB_URL`，不要打印原文”。

## 踩坑点

- **当第二份 AGENTS.md 用**。两边都写“怎么跑测试”，改一处忘另一处。原则：AGENTS.md 管做什么，tools.md 管在什么条件下做。
- **写死绝对路径**。换机全废，改用 `$HOME` 或相对路径，并注明默认值。
- **陈旧无人认领**。团队约定：任何改环境的行为（装工具、升版本）必须在同一 PR 里更新 tools.md，CI 跑一个 doctor 脚本抽查关键项。
- **文件太长稀释注意力**。Agent 上下文有限，300 行的环境说明不如 60 行精炼版好用，长内容放附录按需读。

## 可复用建议

- 起步模板四段就够：平台与 shell / 工具链与版本 / 标准任务命令 / 已知坑与替代方案。
- 写一个 10 行的 doctor 脚本，对比关键工具的实际版本与 tools.md 声明值，CI 定期跑。
- 每月裁剪一次：删掉一个月没被 Agent 用到的条目。文档和代码一样，不维护就是负资产。

## 总结

tools.md 的价值不在写了多少，而在 Agent 少猜了多少。分层放置、人机分工（人写约定、脚本写事实）、一份文件分节管多环境、密钥绝不落盘——做到这四点，同一个 Agent 在你的笔记本和 CI 上会一致得多。先从 40 行起步，跑两周再修。
