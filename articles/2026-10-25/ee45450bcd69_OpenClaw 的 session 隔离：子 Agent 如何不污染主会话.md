## 背景

OpenClaw 的主会话是长期滚动累积的上下文：系统提示、历史对话、工具输出全混在一起。日常问答没问题，但把“重活”也塞进主会话——批量读文件、长链路工具调用、几十轮的调研任务——上下文会被过程噪声迅速撑大，真正的决策信息反而被稀释。

社区常见的解法是派子 Agent 去干这些活。但派发不等于隔离：如果子 Agent 与主会话共享 session，污染只是换了个地方发生。

## 问题：污染长什么样

实际遇到的几种典型：

- 子 Agent 每轮工具输出（读大文件、网页抓取）直接写进主历史，几轮之后主上下文一半是过程日志；
- 失败重试的中间记录留在主会话，后续对话被“上次失败的思路”带偏；
- 临时性决策（“这版先不要”）被写进历史，隔几天又被翻出来当结论用；
- token 成本随任务数线性上涨，涨出来的部分对后续决策没有价值。

根因只有一个：**过程数据和决策数据混在同一份 transcript 里**。

## 做法：四层隔离

我们在自动化流程里把隔离拆成四层：

1. **Session 隔离**。派发时显式指定独立 session key（或让框架自动分配子 session），子 Agent 的全部轮次、工具调用、中间产物只落自己的 session 文件，主会话从头到尾看不到。
2. **返回值契约**。子 Agent 结束时只回传结构化摘要：结论、关键路径、产出文件路径、异常项。约定固定 JSON schema，父会话收到的是一条紧凑的“结果消息”，不是过程回放。
3. **预算与深度限制**。给子 Agent 单独设轮数上限和 token 预算，超限强制收敛输出；递归派发默认最多一层，防止派发树失控。
4. **工作区隔离**。子 Agent 的读写指向独立子目录，不碰主会话的状态文件和记忆文件。中间产物在结果里回传路径即可，主会话按需再取。

主会话侧还有一个动作：收到结果后用一句话“入账”（例如“调研完成，采用方案 B，明细见 xxx”），不原样引用大段返回内容。这一步保证主历史里沉淀的始终是决策，不是数据。

## 踩坑点

- **共享 session key 图省事**：最容易犯。复用主 session 跑子任务，所有隔离设计瞬间失效。key 必须在派发时显式指定。
- **返回摘要不设上限**：子 Agent 把整个文件内容当“结论”贴回来，主会话照样被撑爆。schema 里对字符串字段设长度约束，要求要点化。
- **并行子 Agent 写同一文件**：同时落同一输出路径会互相覆盖。要么各自独立目录，要么父会话串行合并。
- **系统提示继承**：子 Agent 默认继承主 Agent 的口吻，回传内容风格会串。需要时在派发 prompt 里显式覆盖。
- **子 session 不清理**：跑批一段时间磁盘上堆几百个子 session。按保留策略定期归档，重要的只留路径索引。

## 可复用建议

- 把派发模板化：固定格式的 dispatch prompt（目标、边界、返回 schema）+ 独立 session + 预算参数，做成项目标准组件，新任务只改参数。
- 定期给主会话“体检”：翻 transcript 看有没有不该出现的长工具输出，有就说明某条链路没走隔离。
- 立一条默认规则：凡是“过程可能超过三五轮”的活，默认派子 Agent，主会话只做调度和决策。

## 总结

Session 隔离的本质是分工：主会话负责调度与决策，子会话承担过程噪声。四层隔离（session、返回契约、预算、工作区）做齐之后，长任务的上下文曲线平稳很多，主会话“越用越钝”的问题基本消失。代价是多一层封装，但对任何要长期跑的自动化流程来说，这笔钱值得花。
