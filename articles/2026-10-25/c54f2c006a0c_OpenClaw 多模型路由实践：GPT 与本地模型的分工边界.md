## 背景

OpenClaw 的 agent 工作流里，各节点的任务差异很大。意图识别、槽位抽取这类轻量决策，和长上下文代码分析、多步规划这种重推理，对模型能力的要求完全不在一个量级。早期我们把所有节点都接到同一个云端模型上，跑通很快，但调用量上来后问题暴露了：账单里大量 token 花在"判断用户想查天气还是订会议室"这种事上；而内部文档类任务又因合规要求根本不能出内网。

## 问题

全走云端有三个代价：成本、延迟稳定性、数据边界；全走本地则复杂任务的规划能力明显不够。真实需求是按节点分工：简单决策下沉到本地小模型，重活留给 GPT，同时要有降级路径，保证流程不因单点故障中断。

## 做法

1. **给节点打标。** 把工作流里的 LLM 调用点枚举出来，分三类：轻决策（分类、抽取、格式转换）、中负载（单文档总结）、重推理（多步规划、跨文件分析）。路由规则挂在节点上，节点清单不清楚，后面全是白搭。
2. **配置模型池。** 在 OpenClaw 路由层给每个池定义模型、并发上限、超时，然后按节点类型绑定：轻决策走本地 7B 级模型，重推理走 GPT，中间类看预算逐步迁移。
3. **敏感内容拦截。** 加一个前置中间件，用正则加轻量分类器扫 prompt 里的内部标识、密钥特征、文档来源，命中就强制走本地。这类规则宁可误杀。
4. **降级链。** GPT 侧限流或超时，自动落到本地模型并打上 degraded 标记，下游据此决定是否复核。本地过载也可上浮到云端，但要限制频率，防止悄悄把成本打回去。
5. **观测两周再调。** 记录每个节点的模型选择、首 token 延迟、token 消耗、结构化输出失败率，拿真实数据决定哪些节点继续下沉。

## 踩坑点

- **本地模型的结构化输出是重灾区。** 同一个 JSON schema，GPT 一次过，本地模型可能有 20% 调用坏掉。必须做 schema 校验加重试，重试失败就升级云端，别硬扛。
- **路由规则别写太"聪明"。** 我们试过按 prompt 内容动态预测难度，上线后行为不可解释，排查极其痛苦。退回按节点静态绑定加手动 override 后稳定得多。
- **两个模型对 system prompt 的偏好不同。** 切模型后出现行为漂移，典型表现是工具调用参数格式变化。给每个模型池维护各自的 prompt 模板，别共用一份。
- **本地并发是隐性瓶颈。** 只有一张 GPU 时，轻决策节点的排队时间可能超过直接调云端。上线前务必压测本地池的真实吞吐。
- **成本统计别漏掉重试和降级产生的 token**，否则月度对账对不上。

## 可复用建议

先全走云端拿 baseline，再逐节点下沉，每下沉一个观察一周。给路由定"错误率预算"：某节点本地化失败率超阈值就回滚。路由配置代码化进 git，变更走 review。每个节点保留手动 override 开关，排查时能快速隔离变量。

## 总结

多模型路由不是省钱技巧，而是把任务的异质性显式建模。什么时候用 GPT、什么时候用本地，答案不在模型排行榜上，而在你自己工作流每个节点的错误率、延迟和合规约束里。先用数据画出边界，再让路由规则跟着边界走，这套东西才维护得下去。
