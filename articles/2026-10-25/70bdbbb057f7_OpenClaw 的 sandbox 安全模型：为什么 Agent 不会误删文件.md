## 背景

OpenClaw 的 Agent 自带 exec 工具，可以直接跑 shell 命令——这是它好用的原因，也是最大的风险面。第一次让 agent“帮我清理一下构建产物”时，多数人都会心里一紧：万一它把 `rm` 的路径拼错了呢？

## 问题：误操作不是小概率事件

- LLM 生成命令是概率性的，路径拼接、通配符展开、变量未定义都可能出错；
- agent 眼中的路径来自模型自己的推断，而不是操作系统的 ground truth；
- 误删不可逆（除非恰好有备份），而 agent 的默认倾向是“先干了再说”。

所以真正要解决的从来不是“模型够不够聪明”，而是：**最坏情况的爆炸半径能不能被限制住**。

## 做法：把执行环境搬进沙箱

OpenClaw 走的是纵深防御，sandbox 是第一层：

1. **文件系统隔离**。开启 sandbox 后，exec 命令在一个独立的 Docker 容器里执行，工作区以 bind mount 方式挂进去。`rm -rf /` 删的是容器自己的可写层，宿主机上除了挂载的工作区，其他路径对 agent 根本不存在。
2. **工作区收敛**。默认只挂 agent 的 workspace。它以为自己在操作“整台电脑”，实际可见的只有这一个目录——全删了，损失也止步于此。
3. **模式分级**。`sandbox.mode` 支持 `all` / `non-main` / `off`：随手折腾的会话全程沙箱，主力会话按需控制，风险高的操作配更严的隔离，不必一刀切。
4. **沙箱之外还有第二层**。工具审批（exec 执行前需确认）、工具白名单、会话隔离。sandbox 拦“删错地方”，审批拦“不该跑的命令”，两者互补，不要只开一个。
5. **可观测**。每次工具调用都有日志，事后能完整复盘它到底执行了什么。

实际效果是：agent 可以大胆试错——在沙箱里 clone、跑测试、装依赖，搞砸了重开容器即可，宿主机始终干净。

## 踩坑点

- **把宿主机家目录 bind 进沙箱**：等于把最贵的目录交给一个概率性执行者，隔离形同虚设。只挂必要的 workspace。
- **容器内路径 ≠ 宿主机路径**：排障时它报的路径是容器视角，别拿去宿主机找文件。
- **不要把 docker.sock 挂进沙箱**：等于交出宿主机 root，隔离一键被绕过。
- **别假设“开了沙箱 = 万事大吉”**：浏览器等部分工具默认不在这个隔离面里，sandbox 管的是文件系统执行面，不是全部工具。
- **首次启用卡在拉镜像**：看起来像坏了，提前预拉取镜像或用 setup 动作可避免。

## 可复用建议

1. 最小权限优先：能 `non-main` 就别 `off`，能窄挂载就别宽挂载。
2. 把“允许被删的东西”收敛到 workspace 内，宿主机重要数据再用权限和备份兜一层底。
3. 大规模重构前先快照（git 或文件快照），把不可逆变成可逆。
4. 定期翻工具调用日志——audit 比信任可靠。

## 总结

Agent 的可靠性没法靠 prompt 保证，只能靠架构兜底。OpenClaw sandbox 的价值不在于让模型更聪明，而在于把“最坏情况”关进一个可以随手丢弃的容器里。**信任执行结果，但隔离执行过程**——这是所有跑自动化 agent 的人都该内化的默认姿势。具体配置键名和默认值以你手上的版本文档为准，但思路是稳定的。
