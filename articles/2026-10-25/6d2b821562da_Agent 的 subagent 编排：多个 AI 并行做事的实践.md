## 背景

用 OpenClaw 跑长任务久了，单 agent 串行执行的瓶颈很明显：让它"调研 5 个竞品 + 各写一份摘要"，它就是一个一个来，前一个没跑完，后一个只能干等。更糟的是，所有中间产物堆在同一个上下文里，跑到后期 token 涨上去，agent 开始忘事、串台。

subagent 编排就是针对这个问题的思路：主 agent 只做拆解、派发和验收，具体的活交给多个并行子 agent，各自独立上下文，互不污染。

## 问题

串行模式有三个实际痛点：

1. **吞吐低**：涉及网络请求、构建、测试的慢工具，等待时间线性叠加。
2. **上下文污染**：A 任务的调试日志会干扰 B 任务的判断，长任务后期容易跑偏。
3. **单点卡死**：中途一步报错，整条链路停住，重试又得从头来。

## 做法

我的编排流程大致四步：

**1. 先判断可拆性。** 不是所有任务都能并行。标准很简单：子任务 B 是否需要 A 的输出才能开工？需要就是依赖关系，老实串行；不需要（比如各自调研不同站点、各自跑不同模块的测试）才进并行池。

**2. 写自包含的任务卡。** 子 agent 拿不到主 agent 的完整上下文，任务描述必须自包含：目标、输入（文件路径/URL）、输出（写到哪个文件）、约束（不准动哪些文件）。我固定了一个模板，让主 agent 照着填。

**3. 并行派发。** 通过 agent 工具在一个回合里发起多个子 agent 调用，每个指定独立的工作目录或输出文件。并发别开太高，2~4 个比较稳，多了容易撞限流，出问题也不好定位。

**4. 收口汇总。** 主 agent 不收子 agent 的全量日志，只读各自的结论文件（比如统一写到 `results/xxx.md` 的摘要），交叉验证后再决定下一步。有依赖的后续任务，开第二轮派发。

## 踩坑点

- **两个子 agent 写同一个文件**：必炸，连"追加"都会互相覆盖。给每个子 agent 划定独立输出文件，写操作坚决不共享。
- **任务卡含糊**：子 agent 会自作主张补全上下文，方向就偏了。任务卡宁可啰嗦，不要留白。
- **全量输出塞回主上下文**：并行省下的 token 又全赔进去。只收摘要，细节留在文件里，按需再读。
- **迷信"已完成"**：子 agent 报成功不等于结果可用。主 agent 要抽查关键产出，或跑一次校验脚本。
- **无脑并行**：有一轮我让 4 个子 agent 同时改同一仓库的不同模块，合并冲突修了半小时。写操作密集的任务，并行收益经常是负的。

## 可复用建议

- 用"独立性测试"过滤任务：能让 B 在不知道 A 结果的情况下开工的，才并行。
- 固定任务卡模板 + 固定输出目录结构，编排逻辑就能沉淀成可复用的 skill 或插件。
- 并发上限做成配置项，不同模型和账号配额不同，别写死。
- 给子 agent 的产出加一步机械校验（脚本、lint、diff 检查），比"看一眼"可靠。
- 失败的子任务单独重派，别整批重跑。

## 总结

subagent 编排不是"agent 越多越好"，而是把串行任务里真正独立的部分摘出来，用隔离的上下文换吞吐和稳定性。主 agent 的价值在拆解和验收，不在亲自干活。建议先从"多路调研 + 汇总"这类只读场景试起，跑顺了再碰写操作密集的并行，成本和风险都可控。
