## 背景

订阅源一直是我获取技术信息的主渠道，但 RSS 阅读器只解决了"聚合"，解决不了"筛选"。几十个源一天能攒下两三百条 item，真正值得点开的不到十分之一。这篇记录我用 OpenClaw 搭的一条自动化管线：定时抓 RSS → 清洗去重 → 两级 AI 摘要 → 推送晨报。思路不新，但细节踩踏实了能长期稳定跑。

## 问题

直接让模型读原始 feed 有三个硬伤：

1. 多数 feed 只给 summary 不给全文，摘要质量差；
2. 订阅一多 token 成本失控，大量内容根本不值得进模型；
3. 模型容易"脑补"出原文没有的结论。

## 做法

整体是"一个 skill 目录 + 一条 cron + 一个 SQLite 状态库"，不引入重型编排。

**1. 数据源。** 有 RSS 的直接用，没有的用 RSSHub 转一手。源控制在 30 个以内，宁缺毋滥。

**2. 抓取与全文。** Python 脚本用 feedparser 拉源，对只有 summary 的 item 用 readability 类工具抓正文，失败就降级为"仅摘要"并打标。每个 item 以 GUID+链接哈希作唯一键。

**3. 状态与去重。** 处理过的 item 写入本地 SQLite（hash、feed、pubDate、状态、摘要）。流程幂等，跑挂重启不会重发。跨源重复的同一事件按标题相似度粗聚，只留最早一条。

**4. 两级摘要。** 第一级用便宜快速的模型给新 item 打分：一段话概括 + 0–10 相关度，只允许基于给定文本、输出 JSON；第二级只对相关度 ≥ 7 的做 3–5 条要点的深度摘要，可换更强的模型。

**5. 调度与推送。** OpenClaw cron 每天早上触发，脚本产出 Markdown 晨报，由 OpenClaw 推到我的聊天渠道，附原文链接。摘要只用于决定"要不要点开"，不替代阅读。

## 踩坑点

- **全文抓取被 403。** 部分站点对脚本 UA 敏感，换成正常浏览器 UA 能解决大半；仍不行的老实降级，别死磕。
- **pubDate 时区混乱。** 别自己解析字符串，用 feedparser 解析后的结构化时间，统一转 UTC 再比较。
- **token 成本第一周就超预期。** 原因是全量进模型。改成启发式过滤（关键词+时效）先行、模型只看通过者，成本降了约八成。
- **幻觉。** 严格约束"只能使用输入文本中的信息"，temperature 压到 0.2 以下，基本可根治，再偶尔抽查输出能否对应到原文。
- **cron 重叠。** 抓取偶发超时导致上一轮没结束，加 lockfile，拿不到锁直接跳过本轮。
- **失败误标。** 摘要写库失败时不能把 item 标成已处理，否则永久丢条目——状态更新放在整个流程最后一步。

## 可复用建议

- 状态一律落 SQLite，别用内存或临时文件，幂等是定时任务的命根子。
- prompt 当版本化资产管理，输出留档；回看两周的摘要就知道该改哪里。
- 先用 10–20 个源跑两周再扩，源多了第一级过滤的阈值要重调。
- 有余力可以把抓取包成 MCP tool，让 agent 支持按需"拉一下今天的 RSS"，和定时推送互补。
- 第一级模型选快的，别为了质量把晨报跑成批处理作业。

## 总结

这条管线没用任何复杂组件：feedparser、SQLite、两次模型调用、OpenClaw 的 cron 和推送。它解决的不是"读"，而是"决定读什么"。跑了一个多月，每天晨报里真正点开的原文大概三到五条，筛选成本从半小时降到两分钟。自动化信息流的正确姿势，可能就是保持无聊、保持简单。
