## 背景

OpenClaw 的 agent 每次会话启动时，面对的是一个"裸"的工作空间：目录、脚本、配置都在，但它不知道哪些能碰、哪些约定要遵守。人类协作者靠 README 加口头交接，AI 协作者需要一份机器优先阅读的入口文件——这就是 AGENTS.md 的定位：放在工作空间根目录的纯 Markdown，agent 会话开始时自动读取。

它和记忆类文件（MEMORY.md 等）的分工要分清：记忆记的是个人偏好和会话沉淀，AGENTS.md 是工作空间级的公共契约——进版本库、随代码走、团队共享。

## 问题

没有它的典型症状：

- 每次会话都要重复交代"用 pnpm 别用 npm""别动 legacy 目录"；
- agent 自作主张重装依赖、全仓库格式化、删掉它认为"没用的"脚本；
- 同类任务产出风格漂移，commit message 时而中文时而英文；
- MCP 工具挂了一堆，agent 不知道什么场景用哪个，全靠现场试错。

这些本质都是"工作空间知识没有落盘"。口头交代不进版本库，换个人、换台机器就丢了。

## 做法

推荐六段式最小结构：

1. **概述**：两三句话说清项目是什么、技术栈、运行边界；
2. **常用命令**：构建/测试/lint 的确切命令，只写验证过的；
3. **目录地图**：关键目录一句话职责，明确标注禁区；
4. **约定**：命名、错误处理、commit 格式等可执行规则；
5. **安全红线**：不碰 `.env`、未经确认不执行删除类命令、破坏性操作先问；
6. **工具偏好**：什么场景用哪个 MCP 工具或插件，替代方案是什么。

写法上有一条硬约束：**全文控制在 100 行以内**。agent 每次会话都读它，长度直接消耗 token 和注意力。

再配一个迭代机制：当你在对话里第二次重复同一条指令时，就把它提升进 AGENTS.md。这文件是活的，变更跟代码一起走 PR 评审。

## 踩坑点

- **写成小说**。三百行的 AGENTS.md 会让关键红线淹没在背景介绍里，效果反而更差，删到只剩可执行规则；
- **规则冲突**。根目录说 A，子目录的 AGENTS.md 说 B，用户 prompt 又说 C。解析按就近原则覆盖，但最好主动保持一致，冲突规则会导致不可预测行为；
- **内容过期**。重构后目录变了、文件没跟着改，agent 拿着旧地图走新路。把它的更新纳入 PR 检查项；
- **写不可验证的空话**。"写出高质量代码"没有信息量，"所有对外函数必须带 JSDoc"才有；
- **放敏感信息**。文件会被完整发给模型且进版本库，密钥一律走环境变量，文件里只留变量名引用；
- **当记忆用**。"我上次让你……"这类会话上下文属于记忆文件，不属于这里。

## 可复用建议

- 单仓库直接套六段模板起步，先求有再求好；
- monorepo 用嵌套 AGENTS.md：根目录放全局约定，子项目放特化规则，就近覆盖；
- 验收方法：开一个全新会话，问 agent"这个工作空间有哪些约定和红线"，看它能否准确复述；复述不出来说明写得太长或太散；
- 每个里程碑修剪一次，删掉不再生效的规则。

## 总结

AGENTS.md 做的事，是把团队隐性知识编译成 agent 可执行的显式规则。成本几十分钟，收益是每次会话省掉重复交代和事故恢复。把它当代码一样版本化、评审、修剪，是自动化工作流里投入产出比最高的一个文件。
