## 背景

单个 Agent 包揽所有事的模式，在小任务上够用。一旦任务变成批量性质——同时审查几个代码仓库、给一批文档做摘要、跑一轮数据清洗——串行执行的短板就暴露出来：慢、上下文越滚越大、一个环节出错污染整个会话。

我们在几个基于 OpenClaw 的自动化流程里引入了 subagent 编排：主 Agent 只做拆解和汇总，子 Agent 各领一个独立子任务并行执行。跑了一段时间，把经验沉淀成这篇帖子。

## 问题

实际遇到的三类痛点：

1. **上下文污染**：工具返回的长日志、网页抓取结果全堆在主会话里，几轮之后主 Agent 开始"失忆"，指令遵循明显变差。
2. **串行延迟**：五个互不依赖的任务排成一列跑，总时长是叠加的，而它们本可以同时进行。
3. **故障扩散**：一个子任务失败后，主 Agent 的后续推理被错误信息带偏，无关任务也跟着崩。

## 做法

编排结构不复杂，分四步：

**第一步：任务拆分。** 主 Agent 先判断任务能否拆成互相独立、可幂等重跑的子任务。标准很朴素：子任务之间不共享可变状态，单个子任务重跑不产生副作用。

**第二步：定义子 Agent 规格。** 每个子 Agent 的 prompt 包含四要素：目标（一句话）、工具白名单（只挂这个任务需要的 MCP 工具/skill）、明确边界（不要做什么）、输出格式（强制 JSON，含 `status` 和摘要字段）。子 Agent 看不到主会话历史，只拿完成该任务所需的最小上下文。

**第三步：并行调度。** 并行度控制在 3~4，再高容易撞 API 限流，成本也难看。写文件类任务分配独立工作目录，避免互相覆盖。

**第四步：结果汇聚。** 主 Agent 只回收结构化摘要，不回收原始输出。原始日志落盘到本地文件，主 Agent 需要时按路径读取，而不是塞进上下文。

## 踩坑点

- **子 Agent 返回太长**。早期没限格式，五个子 Agent 各回三千字，主会话瞬间被撑爆。后来强制 JSON 摘要 + 原始内容落盘，问题解决。
- **并行写同一资源**。两个子 Agent 同时改一个配置文件，后写的覆盖先写的。现在按任务分独立目录，汇合阶段由主 Agent 统一合并。
- **子 Agent 继承太多上下文**。把完整主会话传下去，子 Agent 反而被无关信息干扰，跑题率上升。最小上下文是原则，不是优化项。
- **静默失败**。子 Agent 超时不显式返回失败状态，主 Agent 会当作"没这回事"继续走。现在 `status` 必填，失败自动重试一次，再失败降级为串行。
- **拆得太细**。把一个 10 分钟的任务拆成 20 个 30 秒的子任务，编排开销大于收益。粒度以"单任务 1~5 分钟"比较划算。

## 可复用建议

1. 子 Agent 的 prompt 做成模板（目标/工具/边界/输出四段式），换任务只改变量。
2. 输出约定固定 JSON schema，汇总逻辑不用每次重写。
3. 并行度、超时时间做成配置项，不同机器资源不一样。
4. 所有子 Agent 的输入输出落盘留档，排障时能回放完整链路。
5. 新流程先串行跑通验证逻辑，再开并行——别同时调两个变量。

## 总结

Subagent 编排不是高级技巧，本质是工程里最朴素的分治：拆得动、跑得独立、回得干净。主 Agent 保持"瘦"——只做拆解、调度和汇总；子 Agent 保持"笨"——只领一个明确任务，返回结构化结果。做到这两点，收益是实打实的：我们的批量流程总耗时降到原来的三分之一左右，单点失败也不再拖垮全局。

先串行、再并行、留日志——这是这套实践里最值钱的三句话。
