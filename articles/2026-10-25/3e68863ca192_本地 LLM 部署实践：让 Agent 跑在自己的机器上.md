## 背景

OpenClaw 这类 agent 场景有个特点：一次任务动辄几万 token 的消耗，MCP 工具来回调用、中间结果反复进出上下文，走云端 API 一天下来成本不低。另外不少自动化任务要碰本地文件、内网服务甚至个人数据，发到第三方 API 总有顾虑。本地部署解决的不是"模型更强"，而是给 agent 栈补一层私有、离线、边际成本为零的算力。

## 问题

家用电脑跑大模型，核心矛盾是三选二：模型体积、上下文长度、生成速度。而 agent 对这三项的要求都比聊天苛刻——上下文要长（工具结果很占地方）、tool call 的 JSON 要稳定、循环调用的吞吐不能太低。很多模型"聊天没问题，当 agent 大脑就翻车"，这是本地化最大的坑。

## 部署步骤

1. **算显存预算**。Q4 量化下，模型文件大小约为参数量的一半：7B 约 4.5GB，14B 约 9GB，32B 约 19GB。在此基础上再乘 1.3，给 KV cache 和运行时留余量。24G 卡可以舒适跑 32B Q4 + 8K 上下文；16G 卡选 14B；8G 显存建议 7B 起步，别硬上。
2. **选引擎**。快速上手用 Ollama，自带 OpenAI 兼容接口；要精细控制用 llama.cpp；Linux + 像样的显卡、追求吞吐上 vLLM。
3. **选模型**。agent 场景优先看 function calling 的可靠性，而不是榜单分数。Qwen 系列 14B 是比较稳的下限，7B 适合做路由、摘要这类简单任务。
4. **接入 OpenClaw**。把 base_url 指向本地端点，temperature 压到 0.1–0.3，上下文显式设够（见下面的坑）。
5. **验证**。用自己的真实 MCP 工具写 10–20 条测试用例，记录成功率和 tokens/s，达标再上生产。

## 踩坑记录

- **Ollama 默认上下文只有 2K/4K**。agent 跑到一半历史被截断，工具结果凭空消失，表现为"模型忘了刚做过什么"。必须显式设置 num_ctx。
- **7B 模型 function calling 成功率偏低**，参数填错、漏填、编造工具名，agent 会静默失败或死循环。别只看通用 benchmark，用真实工具链测。
- **显存不够时部分层回落到 CPU**，速度从 40 tok/s 掉到 5，加载日志里能看出来。宁可换小一档的模型。
- **KV cache 随上下文线性增长**，128K 上下文能把 24G 卡吃满，预算别只算权重。
- **temperature 偏高会导致工具参数 JSON 不合法**，调低温度或开启 structured output 能明显改善。

## 可复用建议

- 把"10–20 条工具调用测试集"做成固定资产，换模型、换量化档位后跑一遍，成功率 90% 以上再接入正式流程。
- 做混合路由：本地模型接隐私敏感、高频、简单的任务，复杂推理仍走云端，在 agent 入口按任务类型分流，不必二选一。
- 盯住 tokens/s：agent 循环里低于 15 tok/s 体验会明显劣化，这条比"能不能跑起来"更决定可用性。
- embedding 这类小模型本地化几乎没有代价（bge、nomic-embed 一类），检索场景收益立竿见影。

## 总结

本地部署的价值不在替代云端，而在分层：让隐私的、高频的、重复的任务沉到自己机器上，把贵而强的云端留给真正需要推理深度的环节。整个过程里，诚实的显存预算和基于真实工具链的验证，比任何"一步到位"的教程都重要。
