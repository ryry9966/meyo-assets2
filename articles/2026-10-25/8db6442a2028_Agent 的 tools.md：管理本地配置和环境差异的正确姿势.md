# 背景

OpenClaw 这类常驻 Agent 的能力边界，一半由 skill 决定，另一半由“它跑在哪台机器上”决定。同一套工作区，家里的 macOS、云上的 Ubuntu VPS、公司的内网机器，行为经常不一致：`python` 还是 `python3`、brew 还是 apt、pip 要不要走代理、路径长什么样。这些问题模型猜不出来，猜错了就是一次次失败的工具调用和无意义的重试。

工作区里的 TOOLS.md 就是为此准备的：它是注入给模型的“本机环境说明书”。但实践中它常被闲置，或者被当成垃圾桶，什么都往里塞。

# 问题

三种常见的错位：

1. **把行为规范写进 tools.md。**“回复要简洁”这类内容属于 AGENTS.md，和本机环境无关。
2. **把环境细节写死进 skill。**skill 是可迁移的“做什么”，一旦里面硬编码 `/Users/xxx/...`，换台机器就废。
3. **在对话里口头告诉 Agent。**“这台机器要挂代理”说十遍它也记不住，context 一滚动就丢。

结果就是环境差异导致的静默失败：命令不存在、路径不对、网络不通，Agent 只能瞎猜。

# 做法

把 tools.md 当作“本机事实清单”来维护，建议固定五段：

- **运行时**：python/node 版本与实际可执行路径
- **包管理器**：brew/apt/pip 的存在性与镜像源
- **网络**：代理地址、哪些工具要走代理
- **路径**：工作区、数据目录、常用脚本位置
- **限制**：无 sudo、无 GPU、磁盘配额等硬约束

示例片段：

```markdown
## 运行时
- python: /usr/bin/python3 (3.11)，无 python 别名
- node: nvm 安装，22.x

## 网络
- pip/pipx 需走 http://127.0.0.1:7890，git 不用
```

多机同步用**模板 + 本机覆盖**：仓库里只提交 `tools.md.template`，各机器用一个小探测脚本（检查命令存在性、版本、路径）生成实际文件，本机文件进 `.gitignore`。

维护节奏上建立回写闭环：Agent 每次因环境原因失败，当场把正确事实追加进 tools.md；重装系统或大版本升级后，重跑探测脚本重新生成，并人工过一遍。

# 踩坑点

- **塞密钥。**tools.md 全文进模型 context，token、密码一律不写，只写“凭据位置及环境变量引用方式”。
- **无限膨胀。**它每轮会话都占 context，控制在几十行内，过期条目及时删。
- **记录动态状态。**端口占用、临时文件这类会变的东西别写，只写稳定事实。
- **团队场景误提交。**本机文件含主机名、内网地址，务必 gitignore，只共享模板。
- **与 AGENTS.md 边界模糊。**一句话判断：换台机器还成立的是规则，不成立的是环境事实。

# 可复用建议

- 三层心智模型：**skill 管做什么，AGENTS.md 管怎么表现，tools.md 管“这台机器上什么是真的”**。
- 探测脚本 > 手写。机器写的事实比凭记忆写的可靠，每条加“最后校验日期”。
- 用定时任务让 Agent 每周自检 tools.md，逐条验证并标记失效项。
- 每条事实写成一行可验证的陈述，方便 grep，也方便 Agent 自查。

# 总结

tools.md 本质是给 Agent 看的“本机 README”。把它当基础设施配置对待：模板化、脚本生成、小而准、无密钥、定期校验。环境差异不会消失，但可以被一份安静的事实清单吸收掉——最直观的变化是，Agent 的无效重试次数会明显下降。
