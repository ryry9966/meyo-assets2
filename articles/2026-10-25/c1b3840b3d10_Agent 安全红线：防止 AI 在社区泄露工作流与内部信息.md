## 背景

社区里跑 Agent 的人越来越多，调试贴日志、发帖贴配置都是日常。但 Agent 的工作上下文和普通开发不一样：它读过你的系统提示词、MCP 工具清单、项目文件，甚至 `.env`。这些内容一旦混进你贴出的东西，泄露的不是一段代码，而是整套内部工作流——用什么工具、怎么编排、内部服务叫什么、凭证长什么样。

## 问题：三条典型泄露通道

1. **调试贴日志**。为了让别人复现，把全量配置或日志贴进社区，token、内网域名、完整 MCP 清单一并带出。
2. **Agent 代写内容**。让它写帖、回帖、做总结，它顺手引用内部路径、客户名、未发布功能名。没有恶意，只是上下文里有什么就可能写什么。
3. **权限过宽的挂载**。Agent 挂了全盘 file-read 和环境变量读取，后续任何输出环节都可能把这些内容带出去。

## 做法：四道防线

**1. 拆分 profile。** 内部调试和对外产出用两套独立配置：不同系统提示词、不同工具白名单、不同会话。对外 profile 不挂 file-read、不挂 env 类工具，只保留写作和检索必需项。这是收益最大的一步。

**2. 最小化粘贴。** 固定一个提问模板：目标、关键报错行、已尝试方案。贴日志前跑脱敏脚本，替换凭证、内网 IP 和域名。信息少一点没关系，全量一定有问题。

**3. 发布前机械审查。** 人眼不可靠，加一道脚本闸门：

```bash
patterns='(sk-[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{36}|AKIA[0-9A-Z]{16}|\.internal\.|/home/[a-z]+/)'
grep -nE "$patterns" draft.md && echo "BLOCK" || echo "OK"
```

挂成 pre-publish hook，命中即阻断。规则不只是 key，还包括内网域名、家目录路径和内部项目代号。

**4. 记住上下文只增不减。** Agent 出现过的内容不会因为你说"忘掉"就消失。红线的本质不是事后清理，而是事前不让敏感信息进入上下文。

## 踩坑点

- **截图比想象中脏**：边缘常留着浏览器标签标题、通知弹窗、IDE 文件树。发前裁剪，或只发文字。
- **`.env` 被当"项目配置"读走**，随后写进 README 草稿或脚本注释。对外 profile 直接不给读权限，比提示词约束可靠。
- **只扫 key 不扫结构**：内部代号、客户名、未发布功能名才是工作流泄露的主体。把内部代号维护成 deny-list，和 key 一起扫。
- **复用会话图省事**：调完内部问题，同一会话顺手写社区帖，上下文还热着。切换用途就开新会话。
- **过度信任提示词**："请不要输出敏感信息"只能降低概率，不能当边界。边界只能来自工具权限和机械检查。

## 可复用建议

- **双 profile 是底线**：对内对外各一套，工具、提示词、会话全隔离。
- **发布前五问**：有凭证吗？有内部路径和域名吗？有内部代号吗？截图边缘干净吗？被转载后有无风险？
- **deny-list 单一来源**：内部代号、域名、路径集中维护一份清单，各处扫描脚本引用它，避免规则漂移。
- **把上下文当只读追加日志**：默认"进去的迟早会被输出"，不想输出的就别让它进去。

## 总结

Agent 的效率和风险都是真实的。它与传统工具的区别在于：上下文进入后难以移除，输出端又没有天然权限模型。所以防线必须前移——用 profile 隔离控制"能读什么"，用工具白名单控制"能碰什么"，用发布前扫描控制"能出去什么"。三道闸门成本都不高，但少任何一道，一次普通的社区分享就可能变成内部工作流的完整外泄。
