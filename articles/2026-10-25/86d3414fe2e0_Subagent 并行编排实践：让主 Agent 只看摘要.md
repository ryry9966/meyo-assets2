## 背景

单个 Agent 啃长任务是老问题：上下文越堆越满，读文件、查日志、搜文档全是串行，等一步才能走下一步。OpenClaw 的 subagent 机制给了另一条路——主 Agent 可以派生多个子代理，每个子代理有独立上下文和受限工具集，干完只回一份摘要。用好了省上下文、省时间，用不好就是纯粹烧 token。最近把一次「故障排查 + 小重构」交给它跑，把编排方式整理如下。

## 问题

最初的跑法很朴素：让主 Agent 自己逐步读代码、翻日志。结果是主上下文塞满了中间过程，到真正要改代码时反而丢细节；大量只读操作本可以并行，却被串行拖慢。核心不是模型能力问题，是编排问题：主上下文应该只装结论，不装过程；只读任务之间互相独立，天然适合并发。

## 做法

1. **按读写拆任务**。读类任务（定位调用链、查配置、读日志、搜文档）彼此独立，进并行批次；写类任务（改文件、提交）必须串行且独占。
2. **给 subagent 立边界**。派发时写清三件事：输入范围（路径、问题）、可用工具（以只读类 MCP 工具为主）、输出格式。
3. **同一轮并行派发**。多个 subagent 任务在一次回复里同时发出，让它们并发跑，而不是等一个结束再发下一个。
4. **结构化汇总**。主 Agent 只收摘要，把各路结论合并成一张「现状清单」，再据此排写入顺序；每次写操作引用对应 subagent 给出的证据路径。
5. **兜底**。设超时和最大并发（实测 3 比较稳），失败重试一次，仍失败就标记为未解决项进入下一轮，不阻塞整体。

## 踩坑点

- **并发写冲突**：两个 subagent 同时改同一文件，后写覆盖先写。纪律只有一条：读并行、写独占。
- **摘要不设限**：subagent 回传几千字，主上下文照样爆。输出长度和格式要在派发时写死，别指望事后裁剪。
- **假独立**：看似并行的任务，B 其实依赖 A 的结论，并行只是白烧。派发前先粗画依赖，拿不准的放串行。
- **盲目重试**：工具限流时继续加并发会雪崩，正确动作是退避，不是加倍。
- **成本意识**：并行是 token 乘法。先用 2 个 subagent 验证有收益，再考虑放大。

## 可复用建议

- 把 subagent 提示词沉淀成模板/插件，按任务类型复用，不要每次现写。
- 摘要固定三段式：结论、证据（文件路径/行号）、未解决项。格式稳定后，主 Agent 的汇总质量明显提升。
- subagent 的输入输出落盘成日志，出问题时可回放复盘。
- 经验值：一次并行 2–4 个收益/成本比最好；超过 5 个后管理开销的增长比收益快。

## 总结

subagent 编排的本质是**上下文隔离 + 并发**，不是堆数量。主 Agent 的角色更像一个只看摘要的负责人：拆活、派活、收结论、排写入。守住「读并行、写串行、摘要限长」三条，长任务的上下文压力和墙钟时间都会有肉眼可见的下降。数量不是重点，纪律才是。
