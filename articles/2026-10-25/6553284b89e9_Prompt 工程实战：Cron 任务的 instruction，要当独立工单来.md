## 背景

OpenClaw 里最容易被低估的功能是 cron 定时任务。很多人第一次用，就是在 cron 里写一句"每天早上帮我看一下 GitHub 通知"，然后发现：有时输出特别长，有时什么都没发，有时干脆报一屏工具调用日志。

原因很简单：**cron 的 instruction 不是聊天消息，而是一段会被独立执行的 prompt**。它没有上下文、没有追问的机会，触发时用户大概率不在屏幕前。把它当成"给同事的留言"来写，失败是必然的。

## 问题拆解

实际跑起来，常见失败可以归为四类：

1. **语义模糊**："看一下最新动态"——最新是什么范围？看什么维度？
2. **上下文缺失**：cron 通常在独立会话执行，之前聊天里交代过的偏好，它一概不知道。
3. **输出失控**：没有格式和长度约束，agent 自由发挥，下游（推送、存储）没法稳定消费。
4. **异常无预案**：工具挂了、数据为空、网络超时，没人告诉它该沉默还是该报警。

## 做法：按写脚本的思路写 instruction

我的习惯是六段式模板，给一个可直接改的例子：

```text
【定时任务】每天 08:30（Asia/Shanghai）触发，独立会话执行。
目标：检查 X 仓库最近 24 小时的 issue 增量。
步骤：
1. 调用 <MCP 工具名>，只拉取最近 24h、状态为 open 的条目；
2. 读取 <状态文件> 中上次已处理的最大编号，做差集；
3. 有新增则按模板输出，无新增则直接结束，不发送任何消息。
输出模板：
- 新增数量：
- 关键条目（最多 5 条，一行一条）：
- 需要人工介入的：
异常：工具失败重试 1 次，仍失败则发送一行含时间戳的错误摘要。
禁止：不扩大检索范围，不调用未列出的工具，不输出原始 JSON。
```

逐段说下为什么这么写：

- **开头固定触发语境**：时间、时区、"独立会话"三个信息让模型不再靠猜。
- **输入写死参数**：范围、过滤条件全部显式，不留"最新""一些"这类词。
- **步骤编号**：明确的执行顺序比大段自然语言描述稳定得多。
- **输出给模板**：下游定时解析时不会因为格式漂移而崩。
- **静默规则是关键**：无变化就不发。这条决定用户第三天会不会关掉通知。
- **禁止清单**：把不希望它做的事直接写出来，比事后修补效果好。

## 踩坑点

- **时区错位**：调度器按服务器时区跑，instruction 里写"早上八点"可能是 UTC 八点。时区两边都要写。
- **依赖对话历史**："按我之前说的格式"——独立会话里"之前"不存在，格式必须内联。
- **一个任务干五件事**：失败时无法定位是哪一步。拆成多个小 cron，各自可验证、可重跑。
- **没写"不做什么"**：agent 很勤快，工具权限一宽就会顺手多调几个 MCP，慢且贵。
- **忘了幂等**：重复触发或重试时可能重复推送。状态文件（记录处理到的位置）比靠模型记忆可靠得多。

## 可复用建议

1. 把 instruction 当配置文件管理：进 git、写版本注释，改一次提交一次，出问题能回滚。
2. 上线前手动触发两三次，看日志确认工具调用次数和输出格式，再交给调度器。
3. 用"如果 X 则 Y，否则保持安静"的句式覆盖所有分支，不留隐式默认行为。
4. 定期回看运行日志，instruction 最大的噪音源往往是当初没料到的数据形态。

## 总结

Cron instruction 的本质是：给一个没有上下文、不能追问、定时上班的同事，留一张完全自包含的工单。触发语境、输入、步骤、输出模板、静默与异常、禁止清单——六块写齐，定时任务才会从"偶尔能用"变成"可以依赖"。
