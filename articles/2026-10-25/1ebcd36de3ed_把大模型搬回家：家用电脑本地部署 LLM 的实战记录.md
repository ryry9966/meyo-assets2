## 背景

云端 API 用久了，几个问题越来越明显：敏感数据要出境、按 token 计费长期不便宜、断网就干不了活。对 OpenClaw 这类本地 Agent 工作流来说，把模型搬回自己机器上，让 Agent、MCP 服务和推理后端待在同一个 localhost 里，是最干脆的方案。最近我在一台 32GB 内存、带 12GB 显存独显的台式机上做了完整部署，记录一下过程和结论。

## 问题

家用机器跑大模型，核心矛盾有三个：

1. 显存/内存有限，原版权重基本跑不动，只能走量化路线；
2. 量化模型“聊天”还行，但 Agent 依赖的**工具调用（function call）**能力退化明显；
3. 上下文越长，KV cache 吃的显存越多，实际可用窗口常常比标称小很多。

## 做法

1. **盘硬件**：有 8GB 以上独显优先走 GPU 推理；纯 CPU 也能跑，但生成速度会掉到个位数 token/s，只适合轻任务。
2. **选运行时**：图省事用 Ollama，一条命令拉模型，自带 OpenAI 兼容接口；追求可控性用 llama.cpp 或 vLLM，量化格式和调度参数都能手动指定。
3. **选模型**：消费级硬件建议从 7B–14B 的量化版起步，Q4_K_M 是速度与质量的常见平衡点。中文场景优先试 Qwen 系列，工具调用支持相对完整。
4. **接进 Agent 链路**：运行时暴露 `http://localhost:11434/v1` 这类兼容端点后，OpenClaw 侧只需改 base_url 和 model 名，MCP 工具照常挂载，链路不用重写。
5. **用自己的负载压测**：别看跑分。拿你真实的 Agent 任务（多轮工具调用 + 长上下文）测成功率和延迟，这才是有效指标。

## 踩坑点

- **KV cache 是隐形杀手**：14B 模型开 32k 上下文时，KV cache 可能比权重还吃显存。Agent 场景把窗口压到 8k–16k，大多数任务够用。
- **量化伤工具调用**：Q4 以下的小模型经常输出格式错误的 JSON 参数，Agent 会陷入重试循环。宁可上 14B-Q4，也别用 7B-Q2 硬扛。
- **温度和停止符**：本地推理默认参数偏“散”，工具调用场景把 temperature 降到 0.1–0.3，失败率肉眼可见地下降。
- **模型名不匹配**：OpenClaw 配置里的 model 字符串必须和运行时注册名完全一致，报 404 或空响应时先查这里。

## 可复用建议

- **模型分工**：强模型做规划和多步推理，再起一个 4B 级小模型做摘要、分类这类轻任务，同一台机器双开完全可行。
- **部署脚本化**：写成 docker-compose 或一键脚本，换机迁移就是十分钟的事，也方便重建实验环境。
- **盯显存水位**：用 `nvidia-smi` 常驻监控，给上下文增长留 20% 余量，避免长会话中途 OOM。

## 总结

本地部署不是要替代云端，而是给 Agent 工作流多一个可控、离线、零边际成本的选项。7B–14B 量化模型加一个 OpenAI 兼容端点，就足以把 OpenClaw 整条链路搬回家。建议的路径是：先跑通最小闭环，再按真实负载调量化等级和上下文窗口，最后才考虑性能优化。
