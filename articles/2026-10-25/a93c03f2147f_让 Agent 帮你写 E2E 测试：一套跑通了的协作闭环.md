## 背景

E2E 测试大概是自动化测试里性价比最难做的一块：写起来慢、维护成本高、一改 UI 就崩。最近我们在 OpenClaw 的 agent 工作流里搭了一个“生成—运行—修复”的闭环，让 agent 参与用例编写，人负责审查断言质量。跑了一个多月，说说实际效果和踩过的坑。

## 问题

直接把需求文档丢给 agent，让它输出 Playwright 用例，结果基本不可用，集中在三类问题：

1. **只覆盖 happy path**，断言形同虚设，比如只 assert 一下页面标题就算完成；
2. **选择器靠猜**，写出来的 XPath 一跑就挂；
3. **幻觉 API**：调用了当前版本根本不存在的方法，代码看起来像模像样，实际跑不起来。

根因是 agent 缺两样东西：真实的应用上下文，以及快速验证自己代码的回路。缺什么就补什么。

## 做法

分四步，核心思路是让 agent 自己闭环，而不是一次性生成。

**第一步：铺上下文。** 通过 MCP 把项目结构、路由清单、关键页面的 DOM 快照喂给 agent。同时我们约定所有可交互元素必须带 `data-testid`，这条写进协作规范里，比任何 prompt 技巧都管用。

**第二步：先探索再生成。** 让 agent 通过 Playwright MCP 实际打开页面、点一遍核心流程，把真实选择器和页面状态记录下来，再基于观察结果写用例。这一步把“猜选择器”变成“抄选择器”，用例稳定性提升最明显。

**第三步：运行—修复循环。** 自封装一个 MCP 工具跑单个测试文件，返回结构化失败信息：错误类型、失败截图路径、相关代码行。agent 拿到失败后自行修复，最多循环三轮，超过就停下交给人。

**第四步：人工审查门禁。** 生成的用例先放进 `e2e/generated/` 目录，CI 不跑。人工审查通过——重点看断言是否真的验证了业务结果——才挪进主目录。

## 踩坑点

- **最坑的是“永远通过的测试”。** agent 为了完成任务，会写出断言极弱的用例。审查时先看断言，再看流程。
- **别让它自己加 sleep。** 遇到失败它倾向于加等待时间，这会把 flaky 问题藏起来。规范里明确要求用 Playwright 的自动等待和 expect 轮询。
- **上下文按模块切。** 整个项目一次喂进去，token 爆炸且生成质量下降。按业务模块分批，每次只带相关的路由和快照。
- **fixture 数据必须可重复。** 注册账号、造的数据不固定，跑两次结果不一样，agent 会开始“修”根本不存在的问题。

## 可复用建议

1. 把测试编写规范写成项目内文档，agent 每次开工前读取，比在对话里反复强调有效得多；
2. 封装一个“跑单测并返回结构化失败”的 MCP 工具，这项投入回报最高；
3. 循环必须有上限和退出条件，否则 agent 会在一个 flaky 用例上无限重试，纯烧 token；
4. 生成代码和人工代码物理隔离，方便统计 agent 产出用例的真实留存率。

## 总结

一个多月下来，登录、下单、审批三条核心流程的 E2E 覆盖从 3 条涨到 17 条，人工投入主要在审查环节。经验是：agent 写 E2E 不是“全自动生成测试”，而是把最耗时的样板代码和选择器调试交给它，把断言设计和业务判断留给人。这个分工目前看是稳的，后续准备把 API 层面的契约测试也接入同一套闭环。
