## 背景

跑 Agent 做自动化的人迟早会遇到这个场景：同一套工具链，在笔记本上一切正常，换到台式机或 CI 容器里就翻车。Agent 幻觉式地调用一个不存在的 CLI，或者拿着错误路径去读文件，然后开始自我纠偏，越纠越偏。OpenClaw 这类框架里，MCP server、插件、shell 工具的可用性本来就是"因机器而异"的，但很多团队把这些信息散落在系统提示词、mcp 配置、wiki 和口头传承里。

tools.md 的价值，就是把这些收敛成一份 Agent 运行时能读到的"环境说明书"。

## 问题

实际用下来，tools.md 常见三个毛病：

1. **写成秘密文件**。有人把连接串、token 直接写进去，然后跟着仓库提交了。
2. **写成百科全书**。什么都往里塞，工具 schema 复制一遍、团队规范复制一遍。Agent 的注意力有限，噪声越多，越容易漏掉关键约束。
3. **写完就腐烂**。Python 升级了、venv 挪了位置、端口换了，文件没人更新——过期信息比没有信息更危险。

## 做法

我们的实践是拆成两层，当配置代码来管：

**第一层：tools.md（进仓库，团队共享）**
只放"所有机器都为真"的内容：工具清单、每个工具的调用方式与适用场景、已知坑（比如某工具在无 GPU 机器上会超时）、安全红线（哪些操作必须人工确认）。一工具一块，固定结构：是什么 / 什么时候用 / 怎么调 / 失败时什么表现。

**第二层：tools.local.md（gitignore，本地覆盖）**
放"只在这台机器为真"的内容：解释器路径、可用端口、Docker 有无、代理设置。值尽量引用环境变量名而不是字面量，比如写"连接串从 `DATABASE_URL` 读取"，而不是把值写死。Agent 加载时先读共享层，再读本地覆盖。

第三件事是**生成而不是手写本地事实**。写一个十几行的探测脚本，输出 OS、shell、已装 CLI、GPU、空闲端口到 tools.local.md 的 "environment facts" 段，带时间戳，挂一个 make target。环境变了就跑一下，避免手抄。

最后加一道**校验**：CI 里跑 lint 脚本，交叉检查 tools.md 提到的每个工具在 mcp 配置里确实存在、每个路径在目标环境确实可解析。文档和现实对不上，直接红。

## 踩坑点

- **别重复 MCP 配置**。参数 schema 在 mcp 配置里已经是单一事实源，tools.md 只补"使用注意事项"，复制一遍迟早不同步。
- **本地事实必须标时间戳**。我们吃过亏：venv 挪了位置没人重新生成，Agent 拿着旧路径反复失败。过期事实要一眼可辨。
- **平台差异显式写**。"CI 里没有 docker compose"这种事，要么写清可用性矩阵，要么靠探测脚本生成，别指望 Agent 自己发现。
- **控制篇幅**。超过一两百行就该砍，Agent 不会感激你的详细。

## 可复用建议

- 共享层进仓库走 PR 评审——它改变 Agent 行为，和改代码同级对待。
- 准备一个固定冒烟任务：每次环境变更后跑一遍，覆盖文档里的所有工具，确认描述与真实行为一致。
- 命名约定固定下来（如 `tools.local.md`），写进新成员 onboarding 清单。

## 总结

tools.md 不是文档，是 Agent 运行时接口的一部分：共享层管约定，本地层管事实，探测脚本管更新，lint 管一致性。把它当代码管，Agent 在哪台机器上都不会"睁眼瞎"。
