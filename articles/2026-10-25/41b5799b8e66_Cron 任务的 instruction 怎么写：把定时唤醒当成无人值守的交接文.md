## 背景

OpenClaw 的 cron 任务，本质是「定时唤醒 Agent 并喂一段 instruction」。它和聊天场景最大的区别是：**没有人在场**。模型不能追问、不能确认，instruction 写成什么样，它就执行成什么样。

我维护了十几个定时任务（仓库日报、巡检提醒、每周复盘），踩过不少坑，把可复用的写法整理在这里。

## 问题

几个典型翻车现场：

- instruction 写「每天早上帮我看下仓库新 issue，总结发我」——有时产出三行，有时一篇长文，结果还落在默认 session 里找半天；
- 写「拉最近的数据」——跨时区之后时间窗口直接错位；
- 工具调用失败时，模型开始自己编数据补齐输出。

共同原因：把 cron instruction 当成了聊天消息，而不是一份完整的工作契约。

## 做法：五段式结构

我的习惯是把每条 instruction 按五段写：

1. **任务目标**：一句话说清这次唤醒干什么，不复述背景；
2. **输入来源**：写死工具名和命令，比如「用 `gh` 拉取过去 24h 的 open issue」，不要写「查一下 GitHub」；
3. **处理规则**：过滤、分组、排序条件逐条列出，确定性判断尽量交给工具，不让模型推理；
4. **输出契约**：格式（Markdown 表格 / 固定模板）、条数上限、投递目标（channel 或文件路径）；
5. **兜底分支**：数据为空、工具报错时怎么办——明确「发送失败报告」，而不是「尽力而为」。

对比示例：

❌ 差的写法：

> 每天早上看看 openclaw 仓库有没有新 issue，总结一下发我

✅ 好的写法：

```text
任务：汇总 openclaw/openclaw 过去 24h 新增 issue
输入：gh issue list --state open，过滤掉 bot 创建的
规则：按 label 分组；每条提取标题、编号、一句话摘要
输出：Markdown 列表，最多 10 条，按 priority 排序
投递：发送到 #dev-daily
兜底：命令失败时发送「检查失败：<错误原文>」，禁止编造 issue
```

## 踩坑点

1. **相对时间是重灾区**。「今天」「最近」让模型猜时间窗口，时区一跨就歪。时间窗写显式的（过去 24h），触发时刻交给 cron 表达式管，别让 LLM 参与算时间。
2. **输出没写落点**。cron 场景下没有「当前对话」，不指定 channel 或文件路径，结果就掉进默认 session。
3. **逻辑塞太满**。过滤、排序这类确定性操作让脚本/工具做，instruction 只描述流程，模型负责汇总和措辞。
4. **一个任务塞多件事**。单一职责，失败了才好定位。
5. **没有兜底 = 鼓励幻觉**。写明「拿不到就报告失败」，比「想办法搞定」安全得多。
6. **改完不验证**。新 instruction 先手动触发跑两三天，对照运行日志，把模型自由发挥的部分逐步收紧。

## 可复用建议

- 心法一句话：**当成交接文档写，不是聊天消息**。值班同事读完能不能不问你就干活，是唯一验收标准。
- 每个 cron 的 instruction 独立成文件、进 git，改动可回溯、可 diff。
- 新任务先套五段式骨架，再往里填内容，比自由发挥稳。
- 高频任务注意精简 instruction——token 是按触发次数烧的。

## 总结

Cron instruction 的本质，是把有人值守的对话压缩成无人值守的契约：上下文、输入、输出、异常，全都要写死。写得越像交接文档，任务跑得越稳。下次新建定时任务时，先用五段式过一遍，能省掉大半排障时间。
