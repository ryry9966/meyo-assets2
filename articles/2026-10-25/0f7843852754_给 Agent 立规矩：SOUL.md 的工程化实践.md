## 背景

OpenClaw 这类常驻型 Agent 跑久了，最直观的感受往往不是功能不够，而是"性格不稳"：昨天还简洁克制，今天突然话痨；在群里替你回话的尺度时紧时松；接了新 MCP 工具之后，做事边界也悄悄变了。塞在系统提示词里的性格描述，随着上下文变长很快被稀释。

SOUL.md 就是 OpenClaw 为此准备的钩子：工作区里的一份 Markdown 文件，每次会话都会加载，用来定义这个 Agent 是谁、信什么、什么不做。

## 问题

实践中我遇到三类具体麻烦：

1. 性格描述散落在系统提示词、插件配置和零散的对话纠正里，改一处漏三处；
2. 边界没有显式定义，Agent 在"帮到底"和"每步都问"之间随机漂移，发消息、删文件、调付费接口这类高危动作尤其危险；
3. 调整全靠重写 prompt，没有版本、没有回归，改完不知道有没有改坏别的。

## 做法

我的 SOUL.md 骨架四段，全文控制在 100 行以内：

- **身份与语气**：三五行说清角色和风格，写"默认中文、先给结论、代码块优先于散文"这类可感知的描述，不写"聪明、幽默"。
- **行为原则**：转化成可验证的规则，例如"不确定意图时先复述理解再动手""删除、force push、涉及花钱的调用，先列出命令等确认"。
- **硬边界**：明确不做的事——不主动私聊联系人、不冒充用户口吻发言、不读取与任务无关的目录、新工具默认先申请权限。
- **升级策略**：什么情况停下来问、什么情况直接做。这一段最能减少"自作主张"。

写法上有一条核心经验：**规则 = 触发条件 + 动作**。"要有分寸"是废话，"群聊里被 @ 才回复，私聊请求先转述给我"才是规则。

改完用一组固定场景做回归：丢给它一条带诱导性的群消息、一个含糊的删除请求，看边界是否生效。SOUL.md 进 git，行为异常时 diff 上一版，比翻聊天记录快得多。

## 踩坑点

- **写成小作文**。SOUL.md 每次会话都加载，几千字既烧 token 又稀释注意力，越短越有效。
- **和其他文件打架**。AGENTS.md 或工具描述里若有矛盾指令，模型的取舍不可预测；每加一个插件通读一遍，消掉冲突。
- **把它当安全边界**。SOUL.md 是提示词层面的软约束，拦不住注入和误调用。真正的边界靠工具白名单、确认门槛和沙箱兜底，两者是配合而非替代。
- **一次配置终身不管**。每新增一个 MCP server，能力面就变一次，边界要跟着补。
- **过度人格化**。要求 Agent"永远顺着我"，等于关掉了它纠正你判断的能力，要留出说"不"的空间。

## 可复用建议

- 模板四段起步：身份语气 / 行为原则 / 硬边界 / 升级策略，50 行足够。
- 规则统一用"触发条件 + 动作"句式，方便自查可执行性。
- 维护一份 5–10 条的回归场景清单，改 SOUL.md 必跑。
- 新增任何工具前先问一句："这个工具需要哪条新边界？"
- 分清两个文件：SOUL.md 管"它是谁"，保持稳定、进版本库；MEMORY.md 管"发生了什么"，让它自然生长。别混写。

## 总结

SOUL.md 是 OpenClaw 里成本最低、杠杆最高的一块配置：一份短文件，换来行为的一致性和可审计性。把它当代码对待——写短、写具体、进版本库、改了就回归。同时记住它只是软约束，硬边界永远在工具权限层。人格和边界都显式化了，Agent 才算真正"可运维"。
