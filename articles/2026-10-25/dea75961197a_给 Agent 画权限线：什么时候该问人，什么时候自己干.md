## 背景

现在一个 Agent 挂上 MCP 和插件之后，能读文件、跑 shell、发消息、调外部 API。能力上来了，问题也跟着来：它每一步都该停下来问人，还是放手让它自己跑？

两种极端我都见过，也都踩过。一种是所有写操作全要确认——人变成审批机器，看得多了就无脑点"允许"，审批形同虚设；另一种是完全放开，直到某天它"顺手"清理了一个不该动的目录。

## 问题

核心矛盾是：模型擅长决定**怎么做**，但不擅长替你承担**做了之后的后果**。它不知道你的风险偏好，不知道一次删除的爆炸半径，也不知道哪条消息发错了收不回来。所以权限边界既不能指望模型自觉，也不能靠人肉盯梢，得在系统层显式设计。

## 做法：四级工具分层

我把所有工具按四个维度过一遍：**可逆性、影响范围、凭证级别、触发频率**，然后分成四级：

- **T0 自动执行**：只读、沙箱内、可逆。读工作区文件、搜索、本地计算。这类问人纯属打扰。
- **T1 自动执行 + 留痕**：工作区内的写操作，但必须可回滚（git 管理、写前备份）。Agent 直接干，事后可审计。
- **T2 必须确认**：不可逆或对外的操作。发真实消息、删除、部署、花钱、改工作区外的配置。每一步都要人点头。
- **T3 禁止**：改自己的权限配置、动密钥。这条写死在 harness 层，不进提示词博弈。

落地方式是把分层写进 OpenClaw 的工具策略：只读 MCP 默认放行，带写权限的 server 挂审批，高危执行走沙箱，工作区和真实用户数据物理隔离。

配套一条纪律：**确认请求必须可秒判**。Agent 发起 T2 操作时要带上"做什么、改哪个目标、有什么副作用、怎么回滚"，让人十秒内能做决定。含糊的"我可以做这个吗"只会把人训练成点击机器。

## 踩坑点

1. **审批疲劳比没有审批更危险。** 确认太频繁，人就会盲批。宁可把 T0/T1 放宽让 Agent 跑顺，把人的注意力留给 T2。
2. **工具级权限挡不住 shell 逃逸。** 你在 allowlist 里禁了网络写入，它一个 `curl` 就绕过去了。高危能力要么不装，要么进程级沙箱兜底。
3. **"临时"权限会变永久。** 调试时全开，之后忘了收。给临时放权设过期时间。
4. **Agent 会泛化你的授权。** 你批了"删这个文件"，它可能理解成"清理类似文件"。确认必须绑定到具体目标，不接受批量隐含授权。
5. **MCP server 的实际权限常常大于需要。** 按最小权限拆 server，别让一个通吃读写。

## 可复用建议

- 边界写两遍：系统提示词让模型**知道规则**，harness 配置负责**执行规则**。只写在提示词里等于没有边界。
- 一条经验法则：**出机器边界的默认问，工作区内能回滚的默认干。**
- 每周看一次自动执行的审计日志，按真实使用调分级。边界是活的配置，不是一次性决策。
- 消耗类操作加预算：设定自动执行额度，超了自动升级为人工确认。

## 总结

说到底，这不是"信不信任模型"的问题，而是系统设计问题：**让犯错的成本可控、后果可见**。可逆的、对内的、可验证的，放手让它干；不可逆的、对外的、拿不准的，停下来问人。把这条线画在配置和沙箱里，而不是祈祷模型每次都判断对。
