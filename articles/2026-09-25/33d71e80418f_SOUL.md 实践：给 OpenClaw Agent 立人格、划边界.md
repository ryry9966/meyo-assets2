## 背景

OpenClaw 的 Agent 工作区里有一组约定文件：AGENTS.md 管行为流程，TOOLS.md 管工具说明，USER.md 存用户偏好，而 SOUL.md 只负责一件事——这个 Agent 是谁。它在每次会话启动时被注入系统上下文，相当于人格声明加边界清单。很多人拿到默认模板直接跳过，先跑通再说；等 Agent 在群里语气忽冷忽热、对越权请求来者不拒时，才回头补这份文件。

## 问题

SOUL.md 缺失或写得太虚，常见三类症状：

1. **人格漂移**：会话开头克制专业，聊到后半段开始连发表情包、自称"小助手"，语气完全随模型默认状态浮动。
2. **边界模糊**：对"直接改生产配置""把聊天记录原样发出去"这类请求，模型没有稳定的拒绝姿态，全看当场发挥。
3. **风格失控**：多通道部署（CLI、Telegram、Discord）时，同一逻辑人格在不同渠道表现不一致，难排查是 prompt 问题还是渠道问题。

## 做法

我的 SOUL.md 大约 40 行，分四段：

**1. 身份与基调（5 行以内）**
只写可观测的行为，不写形容词。"回复先给结论再给理由，默认不用 emoji"是有效指令；"要聪明、友好"是无效的——模型本来就这么认为。

**2. 硬边界（最重要的一段）**
明确拒绝域和拒绝方式：

- 涉及资金操作、数据删除、对外发送信息的请求，必须先获得会话内明确确认
- 不确定时说"我不确定"，不编造
- 拒绝时保持中性语气：一句话说明原因，给出替代方案，不搞道歉三连

**3. 语气细则**
针对实际部署渠道写。机器人常驻技术群，就写"技术讨论直接给命令和参数，寒暄只回应不发起"。

**4. 冲突降级规则**
写清楚 SOUL.md 与任务指令冲突时以谁为准，比如"任务优先，人格约束只在触碰安全边界时不可让步"。否则 Agent 会在"保持简洁"和"解释完整"之间反复横跳。

改完重启会话（SOUL.md 在会话启动时加载，不重启不生效），跑一组固定探测问题：越权请求三条、模糊请求两条、日常任务一条，看回复姿态是否稳定。

## 踩坑点

- **写太长**。SOUL.md 每轮都占上下文。我见过 200 行的"人格宪法"，结果实际任务指令反而被稀释。超过一屏就该砍。
- **试图用它解锁安全限制**。底座模型的安全行为不受 SOUL.md 控制，写了也白写，还容易触发奇怪的对抗性回复。
- **多 Agent 复制粘贴不同步**。几个工作区各改各的，两周后人格就分叉了。公共部分抽出来统一维护，差异部分单独覆盖。
- **把用户偏好写进人格**。"用户习惯用 zsh"这类内容属于 USER.md，混进去后换个用户就得改人格文件。

## 可复用建议

- 把 SOUL.md 当代码管：进 git，commit message 写清"为什么改"，三个月后你会感谢自己。
- 探测问题集固化成脚本，每次改动后跑一遍，人格回归有了基线。
- 结构上"公共核心 + 部署覆盖"：核心人格全 Agent 一致，渠道差异（群聊 vs CLI）用一小段覆盖解决。
- 边界规则用"条件 + 行为"句式："当请求涉及 X 时，做 Y"，避免"要有分寸感"这种无法执行的表述。

## 总结

SOUL.md 是 Agent 配置里性价比最高的文件：十几行、零成本，直接决定每次交互的第一印象和兜底行为。它不是一次性的文学创作，而是像任何配置项一样需要版本化、测试和迭代。如果你的 Agent 还在用默认模板，建议花二十分钟写一版，观察一周——人格漂移和越权问题大概率会少一半。
