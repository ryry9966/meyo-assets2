## 背景

OpenClaw 里的自动化大多长这样：定时任务（cron）触发的 Agent 流程、Webhook/事件驱动的插件、MCP 工具调用外部服务。它们的共同点是：**触发源不可控**。

定时器可能在上一轮还没结束时又触发一轮；Webhook 服务普遍承诺"至少一次"投递；Agent 超时后会重试工具调用；用户看到没反应，手动再点一次。也就是说，同一个任务被执行两次、三次，不是异常路径，而是常态。

## 问题

很多写操作天然不幂等：

- 插件往群里发通知 → 重试后刷屏；
- `INSERT` 写数据库 → 数据翻倍；
- 调第三方 API 下单、建工单 → 重复扣款、重复建单；
- Agent 执行"追加写文件" → 内容重复。

非幂等的自动化，正确性建立在"不会重复"这个假设上——而重试机制恰恰在系统性地打破这个假设。

## 做法

核心思路一句话：**用稳定的业务幂等键，把"做一次"变成"确保做过一次"**。

1. **定义幂等键**。从业务语义取，不从执行上下文取。比如"每天同步一次 issues"的 key 是 `sync-issues-2025-06-01`，而不是 `task-<uuid>`——后者每次运行都不同，等于没做。
2. **建一张执行记录表**，对幂等键加唯一约束：`job_runs(key, status, result, updated_at)`。执行前先 upsert 一条 `running`，键冲突则读已有状态直接返回。
3. **写操作全部 upsert 化**。能靠唯一键去重的 insert 都改成 upsert，由数据库兜底，而不是只靠应用层 if 判断。
4. **外部副作用尽量走幂等接口**。不少支付、云服务 API 支持传 `Idempotency-Key` 之类的请求头，务必带上，值就是第 1 步的幂等键。
5. **不可幂等的操作加去重窗口**。比如发通知，同一 key 在 N 分钟内只发一次，用 Redis `SET key val NX EX` 就够。
6. **Agent 工具语义幂等化**。把 MCP 工具从 `create_xxx` 设计成 `ensure_xxx`：已存在则返回已有对象，不存在才创建。这样 Agent 重试、用户重发指令都不会产生脏数据。

## 踩坑点

- **幂等键里混入时间戳或随机数**：key 每次不同，幂等形同虚设。键必须由"业务对象 + 业务周期/业务事件"构成。
- **"先查后写"有竞态**：两个 worker 同时查都没查到，然后都写入。应用层检查只是优化，唯一约束才是兜底，两者都要有。
- **重试改变了 key**：比如 key 里拼了"第几次重试"，每次重试都被当成新任务。
- **半完成状态**：第一步写库成功、第二步调 API 失败，重试若从头开始，要么重复调 API，要么重复写库。把流程拆成可独立幂等的小步骤，各自记录状态，重试从断点继续。
- **定时任务重叠**：上一轮没跑完下一轮又开始。加锁之外更稳的做法是让任务本身幂等——重叠执行最多浪费一次算力，不产生副作用。

## 可复用建议

- 所有写操作过同一个 helper：自动携带幂等键、自动写执行记录，不依赖每个插件自觉。
- 验收标准很简单：**同一任务连跑三遍，最终状态和跑一遍完全一致**。拿它去测定时任务、Webhook 处理器和 Agent 工具，不达标就是没做幂等。
- 新增 MCP 工具时，把"是否可安全重试"当作与参数校验同级的默认要求。

## 总结

重试与重复触发不是 bug，是分布式系统的默认行为。幂等性不是锦上添花，而是自动化任务能"放心交给机器"的前提。先把幂等键和唯一约束立起来，再谈其他优化——顺序不能反。
