## 背景

大多数 AI 助手是纯被动的：你不发消息，它永远不动。但 OpenClaw 这类常驻 agent 天生具备主动条件——有心跳/定时任务兜底，有 MCP 工具能查状态、调接口，有插件体系可以接 webhook。我在自己的实例上把 proactive 当成一个独立模块做了一版，跑了一个多月，这里记录思路和踩过的坑。

## 问题：主动不等于多干活，而是少打扰

Proactive 的工程难点不在"能不能主动做"，而在"该不该现在说"。拆开是三件事：

1. 触发从哪来；
2. 谁来判断值不值得打断用户；
3. 主动动作的权限边界画在哪。

这三件事没想清楚就上 proactive，常见结局是一周后用户把通知静音，能力等于没做。

## 做法：触发分层 + 过滤 + 分级

**1. 事件源分三类接入。** 定时类（日报、日程预告）走 cron；事件类（CI 失败、特定关键词邮件）走 webhook 插件；状态类（服务健康、仓库动态）由低频轮询的 MCP 工具负责。所有触发统一写进一个 inbox 队列，而不是直接推到聊天频道——这是后面一切过滤的前提。

**2. 心跳时先过一道意图过滤。** agent 每次醒来先读 inbox，按"与我目标相关吗 / 过期了吗 / 重复吗"打分。规则优先：去重键、关键词、来源权重；分数不够的丢弃或攒进日报。不要一上来就上 LLM 打分，成本和延迟都不划算。

**3. 通知与动作分级。** 只读动作（查一下、汇总一下）可以直接做完，连结果一起说；写动作（替我发消息、改文件、调第三方接口）一律先进待确认列表，附上下文，等一句"确认"再执行。

**4. 降噪和反馈闭环。** 设静默时段和每类事件的每日推送上限；每条主动消息带一个"这类以后别推"的快捷回复，命中就写回过滤规则。

## 踩坑点

- **自激循环**：agent 自己发出的消息被 webhook 再次捕获，反复触发。所有 proactive 产出必须打来源标记，事件入口先过滤自己的 ID。
- **心跳太勤**：最早设 5 分钟一次，token 费用翻倍，绝大多数心跳无事可做。改成事件驱动为主、心跳 30–60 分钟兜底。
- **时区**：定时任务默认 UTC，凌晨三点推"早报"。所有时间显式带时区。
- **状态过期**：事件入队到实际处理隔了几小时，agent 拿旧快照说事。入队时把关键状态一起快照。
- **权限蠕行**：图省事逐步放宽写权限，一次误发就够喝一壶。写权限永远留人工确认。

## 可复用建议

- **先做日报，再做实时**。digest 是 proactive 里性价比最高的形态，用户耐受度高，也最容易靠它校准过滤阈值。
- **把主动消息当产品设计**：打扰成本一旦高于帮上的忙，用户就会关掉你，而且很难再打开。
- **每个主动动作落日志**：触发源、决策理由、执行结果。回溯事故、调阈值全靠它。
- **阈值宁紧勿松**：先让用户觉得"怎么不推了"再慢慢放宽，比反过来容易得多。

## 总结

Proactive 的目标不是让助手更勤奋，而是让它在对的时刻出现。触发分层、低成本过滤、动作分级、反馈闭环——这四件事做扎实，助手才算从"答录机"变成"同事"。剩下的，是长期拿日志调参的笨功夫。
