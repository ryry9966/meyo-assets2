## 背景

OpenClaw 的 Agent 默认具备 shell 执行和文件读写能力——这是它好用的重要原因，也是新手最担心的一点：模型是概率性的，一条解析错位的 `rm -rf` 难道不是随时可能发生？实际答案是：OpenClaw 不靠"在提示词里求它别删"，而是把安全性做进了执行架构的分层里。

## 问题：为什么"让模型小心"不成立

Prompt 约束无法对抗两类风险：一是**上下文注入**——Agent 读到的网页、文件、消息里可能藏着诱导执行的指令；二是**路径歧义**——相对路径、软链接、目录拼写差异，都可能让一次"清理临时文件"变成误伤。所以防线必须放在执行层，而不是对话层。

## OpenClaw 的四层防线

1. **沙箱隔离（sandbox.mode）**：非主会话（配置为 `all` 时包括全部会话）的 Agent 跑在独立容器里。容器内看到的"家目录"是挂载的 workspace 卷，不是宿主机真实文件系统。Agent 在容器里执行 `rm -rf ~`，删掉的只是容器内那份卷。
2. **工作区作用域**：文件工具的默认读写路径绑定 session workspace。越出 workspace 的访问要么被拒，要么在你显式挂载时降级为只读。
3. **审批门（exec approval）**：高危命令模式可配置为需人工确认。这是最后一道闸，覆盖"沙箱放行了、但动作本身不合理"的残存风险。
4. **工具策略（tool policy）**：MCP 工具与插件按会话/渠道做 allowlist，用不到的破坏性工具直接不下发——模型"看不见"就调不了。

## 验证：放一个金丝雀文件

配置完别凭感觉，做五分钟测试：

1. 在宿主机放一个内容唯一的哨兵文件；
2. 确认该路径没有挂进沙箱（或仅只读挂载）；
3. 在会话里让 Agent"删除这个文件"；
4. 预期结果：路径不可见或写入被拒，同时 exec 审批日志留有记录。

通过后，再把真实数据卷挂进来。

## 踩坑点

- **把整个宿主 home 挂进沙箱**：隔离形同虚设，等于换了个容器名继续裸奔。只挂任务需要的子目录。
- **图省事把 sandbox.mode 设为 off**：主 Agent 也建议保持 `non-main` 或 `all`。破坏往往发生在自动化触发的后台任务里，而不是你盯着的那次对话。
- **把 Docker socket 挂进沙箱**：容器逃逸的经典入口。沙箱内的 Agent 不需要管理 Docker。
- **权限报错就 chmod 777**：先查 volume 属主映射，不要用放开权限掩盖配置问题。
- **审批疲劳**：所有命令都设审批，人就会无脑点确认。只对高危模式（递归删除、强制写入、下载后执行）开审批，其余交给沙箱兜底。

## 可复用建议

- 最小挂载：能只读就不读写，能不挂就不挂。
- 密钥与环境变量留在沙箱外，Agent 需要时走受控注入。
- 哨兵文件测试纳入每次升级后的例行验证。
- 定期翻 exec 与工具调用日志；反复尝试越界路径这类异常模式值得追查。

## 总结

Agent 不误删文件，不是因为模型足够聪明，而是因为架构让破坏性动作"要么够不着，要么要审批，要么作用域被锁死"。沙箱兜住概率性错误，审批兜住规则盲区，策略压缩攻击面。三层各管一段，缺任何一层，都只是在赌运气。
