## 背景

用 Agent 做内容自动化，常见链条是：LLM 生成 Markdown → 人工修格式 → 复制粘贴到公众号、知乎、博客。平台一多，后两步就成了瓶颈：格式靠人肉，发布靠手贴，改一处要同步多处。这篇记录我把这段链路工程化成管线的实践。

## 问题出在哪

实际拆开是三层：

1. **AI 产出不规范**：标题跳级、列表缩进混乱、代码围栏嵌套出错、链接靠编。
2. **平台渲染差异大**：公众号不支持外链和大部分 HTML，知乎对代码块支持有限，GitHub 只认 GFM。
3. **流程不可重复**：发布产物和源文件逐渐分叉，没有单一事实来源。

## 做法：五步管线

核心原则只有一条：**确定性变换交给代码，语义判断交给模型。**

1. **归一化**。产出先过 markdownlint：标题从 h1 开始、统一 ATX 风格、修列表缩进、嵌套围栏换成四反引号。这一步纯脚本，不进模型。
2. **抽元数据**。约定 frontmatter（title / tags / date / excerpt / platforms），下游适配器只认这个结构。
3. **平台适配**。用 remark 把文档解析成 AST，按平台能力开关做变换：不支持表格的降级成列表，不支持锚点的剥掉链接只留文本。适配器写成纯函数，输入输出都是 AST。
4. **资源处理**。远端图片统一下载、校验、传图床、重写链接。AI 编造的 URL 在这步顺手做 HEAD 检查，挂的直接剔除。
5. **预览与发布**。每个平台一个本地渲染模板出预览稿，人工过目后走平台 API 或 MCP 工具发布，状态回写 frontmatter。

## 踩坑点

- 别让 LLM 直接"改格式"。它不幂等，每次跑结果都不一样，还可能引入新问题。格式问题一律交给脚本。
- 代码块里含三反引号是重灾区，生成后立刻用四反引号包裹，别等渲染炸了再查。
- frontmatter 忘剥会原样发到不支持的平台，看起来像事故现场。
- 移动端为主的平台，宽表格基本不可用，宁可提前降级成列表。
- 相对路径图片在产物里必断，资源重写必须独立成步，别指望手工替换。

## 可复用建议

- **源文件是唯一事实**。各平台产物视为缓存，永不手改，改源重跑。
- **能力矩阵配置化**，变换逻辑读配置驱动，而不是每个平台写死一套 if-else：

```yaml
wechat: { table: false, anchor: false, html: inline-only }
zhihu:  { table: true, footnote: true }
github: { table: true, footnote: true, math: true }
```

- 准备一份**全要素样例文档**（含代码、表格、图、脚注、公式），给每个适配器做快照测试，平台改版时只动 fixture。
- 人工卡点放在发布前一步：Agent 出预览和 diff，人一条命令放行。

## 总结

这套管线没有用到什么高深的东西，就是把"模型做什么、代码做什么"划清楚，再把平台差异收敛成一份配置。落地之后，新增一个发布平台通常只是新增一个适配器加几行配置。Agent 在链路里的角色是内容生成与语义裁剪，不是格式修理工——可靠性来自脚本的可重复，不是来自更好的提示词。
