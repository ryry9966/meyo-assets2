# 背景

跑过长期在线的 Agent 都会遇到同一个问题：助手"睡着"的时候，谁负责叫醒它？主流做法就两种——**轮询**（定时心跳，每 N 分钟唤醒一次检查待办）和**推送**（事件驱动，消息到达、webhook 触发才唤醒）。OpenClaw 的 heartbeat 属于前者，IM 网关的消息回调、插件和 MCP 工具的事件则属于后者。两者看似只是实现细节，实际决定了 token 成本、响应延迟和可靠性上限。

# 问题

我们最初的配置很简单：heartbeat 每 20 分钟一跳，每次唤醒走完整 agent loop。跑了一周暴露出两个问题：

1. **账单异常**。绝大多数心跳周期无事可做，但每次唤醒都过一遍模型，纯烧 token。
2. **延迟不达标**。用户从 IM 发来的指令最多等 20 分钟才有响应，不可接受。

反过来全改推送，又遇到新麻烦：本地部署没有公网入口，webhook 收不到；偶发推送丢失没有任何补救机制，任务静默消失。

# 做法与步骤

最终收敛成一个混合方案：

1. **任务分类**。交互类消息（用户即时指令）走推送，网关收到立即投递；维护类任务（整理笔记、检查订阅源、清理临时文件）走心跳。
2. **模型前加一道"廉门槛"**。心跳唤醒后先看 HEARTBEAT.md / 待办队列是否为空，为空直接结束，不进模型。空转成本降到接近零。
3. **持久化所有触发源**。推送事件不直接执行，先写入本地队列文件；心跳周期兜底扫描队列。推送丢了，下个心跳补上。
4. **自适应间隔**。工作时段 5 分钟一跳，夜间 30 分钟一跳，间隔进配置不硬编码。
5. **任务幂等**。队列条目带唯一 key，重复投递直接跳过。

# 踩坑点

- 心跳执行时恰好用户在对话，两段上下文互相污染。后来加了"会话忙则跳过本轮"的判断。
- 笔记本合盖休眠导致定时器漂移，醒来后心跳积压。需要在唤醒时做一次 reconcile。
- webhook 重试没做幂等，一次重试风暴让同一个任务跑了三遍。
- 早期空转心跳没有日志，排障无从下手。现在每次心跳记录时长和是否调用了模型。

# 可复用建议

- 默认从"轮询 + 空转门槛"起步，覆盖 80% 场景，架构最简单。
- 只有延迟真正敏感的链路才值得引入推送，且必须配队列和幂等。
- 推送和心跳不必二选一：让两者写同一个队列，心跳天然成为推送的兜底。

# 总结

轮询买的是简单和可靠，推送买的是延迟和节省 token。对个人自托管部署而言，与其追求"纯事件驱动"的优雅，不如让廉价心跳兜底、推送做加速，两者收敛到同一条任务队列。先跑起来，再按账单和延迟数据调整节奏。
