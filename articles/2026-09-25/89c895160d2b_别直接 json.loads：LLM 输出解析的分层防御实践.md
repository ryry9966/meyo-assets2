## 背景

在 OpenClaw 插件、MCP 工具封装和自动化脚本里，大量逻辑的第一步是"把 LLM 输出解析成结构化数据"。工具调用参数、批量任务的汇总结果、Agent 之间的消息传递，全都依赖这一步。解析一旦失败，下游整条链路就断，而失败往往发生在夜间无人值守的批量任务里。

## 问题

你预期模型返回纯 JSON，实际会收到各种"变体"：

1. Markdown 代码围栏包裹：```json ... ```
2. 自定义标签包裹：`<output>{...}</output>`、`<json>...</json>`
3. 围栏和标签同时出现（双重包裹）
4. 围栏前后附带解释性文字
5. 非标准 JSON：尾逗号、单引号、未加引号的键
6. `max_tokens` 截断导致的残缺 JSON
7. 中文全角引号/冒号、BOM 头

裸写 `json.loads` 的成功率可能只有七成，剩下三成就是你的告警来源。

## 做法

核心思路：**分层降级，别指望单个正则解决所有情况**。建议按顺序构建 pipeline：

1. **预处理**：去 BOM，保留原文副本
2. **剥离围栏**：正则匹配 ```` ```(json)?\s*([\s\S]*?)``` ````，取捕获组
3. **剥离标签**：匹配 `<(json|output|result|response)>([\s\S]*?)</\1>`
4. **括号配平提取**：从第一个 `{` 或 `[` 开始，用状态机扫描（记录是否处于字符串内、是否转义），找到配平的闭合位置
5. **宽松解析**：标准解析全失败后，换 json5 / json-repair 类库兜底
6. **Schema 校验**：pydantic / zod 验证字段与类型，不合法视为解析失败
7. **带错误重试**：把解析错误信息拼回 prompt 再请求一次，限 1~2 次
8. **全量留痕**：原始输出写入日志，便于离线分析和迭代 prompt

骨架大致是：

```python
def extract_json(text: str):
    candidates = [text]
    candidates += strip_fences(text)
    candidates += strip_tags(text)   # 循环剥到稳定
    candidates += brace_scan(text)   # 状态机配平
    for c in candidates:
        try:
            return json.loads(c)
        except JSONDecodeError:
            continue
    return repair_parse(text)        # 最后手段
```

## 踩坑点

- **正则贪婪问题**：`{.*}` 会吞掉两个 JSON 之间的内容，`{.*?}` 遇到多段输出只取到第一个闭合。配平扫描才是可靠解法。
- **全角替换要克制**：如果字段值本身是中文文案，盲目替换全角符号会破坏数据。先原样解析，失败再做替换。
- **截断检测**：残缺 JSON 的配平扫描永远找不到闭合，要设扫描上限，超限直接判定截断，走"重试并调大 max_tokens"分支。
- **双重包裹**：围栏套标签时要循环剥离直到输出稳定，只剥一层会漏。
- **过度修复有风险**：repair 库可能把缺失字段补成空值，让下游拿到"合法但错误"的数据。关键任务宁可失败进重试。
- **别迷信 JSON mode**：tool calling / 结构化输出能大幅减少问题，但不是所有模型和网关都支持，fallback 必须保留。

## 可复用建议

- 解析逻辑收敛到一个模块，全项目禁止散落 `json.loads`
- 失败日志必须带原始输出（注意脱敏），否则无法复盘
- 抽取类任务压低 temperature，prompt 明确"只输出 JSON，不要解释"
- prompt 格式与 parser 版本一起管理，改 prompt 时回归测试 parser
- 监控解析成功率，突降通常意味着模型或网关升级了输出风格

## 总结

LLM 输出解析不是"能不能解析"的问题，而是"多大比例能解析、失败后多快恢复"的问题。分层降级 + 配平扫描 + schema 校验 + 带错误重试 + 留痕监控，这套组合值得作为插件和自动化场景的标配。防御性编程在这里的本质只有一句话：**把模型的输出当成不可信的外部输入来对待**。
