# OpenClaw 多模型路由实战：什么时候用 GPT，什么时候用本地模型

## 背景

OpenClaw 的模型配置天然支持多 provider：云端（GPT 系列等 OpenAI 兼容端点）和本地（Ollama / LM Studio）可以挂在同一个 agent 上。但“配得上”和“用得对”是两回事。社区里常见的两种极端：要么全走云端，月底 token 账单看完沉默；要么全走本地，工具一多就开始胡言乱语。这篇记录几个跑自动化工作流的同学踩完坑后收敛出来的路由方案。

## 问题

路由本质上是在三个维度间做权衡：

1. **能力**：工具编排、多步推理、长上下文，云端强模型明显更稳；
2. **隐私**：日志、内部文档、客户数据，能不出本地就不出；
3. **成本与延迟**：定时摘要、格式转换这类高频低价值任务，用 GPT 纯属浪费。

难点在于 OpenClaw 不会替你判断“这条消息该给谁”——fallback 链只在失败时切换，不做智能分流，分流逻辑得自己搭。

## 做法

**第一步：先配 fallback，别急着上路由。** 云端和本地两个端点都声明好，主模型挂云端、本地兜底（示意，字段名以你版本文档为准）：

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-5.2",
        "fallbacks": ["ollama/qwen3:32b"]
      }
    }
  }
}
```

这保证任何一路挂掉服务不断，也是后续路由的基线。

**第二步：按任务类型分流，规则优先。** 在 agent 入口用 hooks 加一层轻量分流：

- **走本地**：定时任务、会话摘要、日志整理、格式化输出、敏感文本的预处理与脱敏；
- **走云端**：需要调用 MCP 工具链的任务、代码生成与修改、多轮复杂规划。

规则能覆盖 80% 的场景（比如“带 skill 调用的消息一律走云端”）。剩下不确定的，用一个本地小模型做分类，不要直接上大模型当路由器——那是本末倒置。

**第三步：建 20~30 条固定评测集。** 从真实会话里挑任务，包含纯文本、单工具调用、多工具链三类，每次换模型或量化版本跑一遍，记录通过率和重试次数。路由策略靠数据调，不靠感觉。

## 踩坑点

- **本地小模型的 tool call 可靠性是硬伤**：参数 JSON 格式错、漏调用、幻觉出不存在的工具。7B 级别别接复杂 MCP 工具链，32B 起步再谈。
- **同名模型不同量化表现差异巨大**：Q4 和 Q8 的 function calling 通过率可能差一截，评测必须用你实际部署的那个。
- **上下文窗口**：本地模型上下文普遍偏短，OpenClaw 会话历史越长越容易崩，要配合历史裁剪，别把长会话硬塞给本地。
- **会话内混用模型会“人格漂移”**：两个模型风格不一致，体验割裂。建议一个会话绑定一个模型，路由发生在会话入口，而不是中途切换。

## 可复用建议

- 一句话原则：**数据在本地处理，逻辑在云端推理**。
- 路由维度宁少勿多：先按“是否调工具”一刀切，跑两周再加维度。
- 敏感数据先在本地脱敏或摘要，再上行云端。
- 路由层保持无状态、可关闭：出问题时能一键回退到单模型。

## 总结

多模型路由不是越智能越好。先用规则把确定性任务分流到本地，把 GPT 这类云端模型留给真正需要推理和工具编排的部分，再用固定评测集验证效果。对大多数个人部署来说，做到这一步就够了，不需要更花哨的东西。欢迎大家把自己评测集的通过率数据发到社区，攒一份跨模型的实测对照。
