## 背景

社区运营有个现实问题：好内容靠人肉产出，节奏不稳定。我们的需求很朴素——用 OpenClaw 跑一个定时 Agent，每天从社区讨论和 issue 列表里选一个题目，产出一篇符合社区口味的帖子草稿，人工确认后发布。听起来像"调个 API"的事，实际做下来踩了不少坑，这里把架构和教训完整记录下来。

## 问题拆解

直接让 LLM"写一篇并发布"是不行的，要解决四个子问题：

1. **选题有依据**：来源必须是近期高热讨论或真实 issue，不能凭空编题。
2. **事实性**：技术帖里的命令、链接、版本号极易幻觉。
3. **去重与频率控制**：避免同一话题反复发，避免触发社区反垃圾机制。
4. **可审计**：每篇帖子为什么发、谁确认的，事后要能追溯。

## 架构与实现

最终是一个五段流水线，Agent 只负责中间两段：

```
调度器(cron) → 选题器 → Agent 草稿 → 规则校验+查重 → 人工审核队列 → 发布器 → 日志回执
```

- **调度器**：cron 每日一次，触发前查幂等键（日期 + 选题 hash），防重复触发。
- **选题器**：纯规则，不进 LLM——拉取近 7 天高回复话题与 open issue，按关键词聚类打分取 Top1，连同原始讨论一起塞进 prompt。
- **Agent 草稿**：在 OpenClaw 注册三个 MCP 工具：`fetch_context`（拉取选题相关原始材料）、`check_duplicate`（标题+正文 embedding 与历史帖比对）、`submit_draft`（写入审核队列）。注意：**没有 `publish` 工具**，发布权限不在 Agent 手里。
- **校验与审核**：规则层做硬校验（代码块语言标注、链接白名单、字数区间），通过后进人工队列，确认才调发布器。
- **发布器**：独立进程封装社区 API，带指数退避重试与本地持久化队列，发布结果写回日志表。

## 踩坑实录

**坑 1：MCP 工具粒度太粗。** 最初做了一个 `write_and_publish` 大工具，Agent 一旦决定调用就绕过了全部校验。拆成小工具、把发布挪出 Agent 权限范围后问题消失。教训：**工具边界就是权限边界**。

**坑 2：查重只看标题。** 两篇帖子标题不同但内容高度重合，标题相似度查不出来。改成标题 + 正文前 500 字的 embedding 余弦相似度，阈值 0.82，误报率可接受。

**坑 3：社区 API 限流。** 连续重试触发 429，帖子卡在中间态。加指数退避（1s/4s/16s）+ 本地队列持久化，发布器重启后可续传。

**坑 4：cron 时区不一致。** 容器与宿主机时区不同，某天重复发了两篇。幂等键按"日期+选题 hash"落库，插入冲突直接跳过。

**坑 5：prompt 膨胀。** 早期把社区规范全文塞进 prompt，token 成本翻倍且模型抓不住重点。压缩成一页 checklist 模板加 few-shot 示例，质量反而更稳。

## 可复用建议

1. 先跑通"生成 + 人工审核"的最小闭环，再考虑全自动；全自动只对低风险内容开放。
2. MCP 工具定义、prompt 模板、校验规则全部进 Git，改动可 review。
3. 发布器必须独立、幂等、可重放，不与生成逻辑耦合。
4. 每天留一份"发 / 不发"的决策日志，每周复盘一次阈值和选题质量。

## 总结

上线四周，产出 21 篇草稿，人工通过 17 篇，退回原因集中在"引用了不存在的链接"和"选题过时"。它没有替代写作者，而是把找题、凑格式、查重这些机械劳动拿走了。对想上手的同学：架构不复杂，关键是把**发布权限、幂等、查重**这三件事想清楚，剩下的都是体力活。
