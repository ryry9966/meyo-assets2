## 背景

Agent 常驻运行后，最脆弱的往往不是模型，而是它调用的外部服务：搜索 API、第三方 LLM、Home Assistant 的 webhook、各种 MCP 工具背后的上游。一个跑着定时任务和插件链的 OpenClaw 实例，一天可能发起几百次工具调用。上游偶尔挂掉不是意外，是常态。

## 问题出在哪

把工具异常原样抛给模型，通常会出三种事：

1. **盲目重试循环**。模型看到报错倾向于"再试一次"，没有上限就是在烧 token。
2. **错误级联**。链条第 3 步挂了，后面 7 步全部作废；更糟的是模型基于失败结果编造输出。
3. **静默失败**。定时任务半夜挂掉没人知道，第二天看到的是空白报告。

核心矛盾在于：模型分不清"工具坏了"和"任务做不了"，也没有重试预算的概念。这些事必须在工具适配层解决，不能靠 prompt 恳求。

## 做法：四层防护

**第一层：错误分类。** 超时、4xx、429、5xx、网络错误是五种病，不能用一个 retry 治所有。401/403 是凭证问题，重试没意义；429 该退避等待；只有 5xx 和超时值得重试。

**第二层：重试 + 熔断。** 写在 MCP 工具的包装层：指数退避加抖动（jitter），上限 3 次；连续 5 次失败后熔断，接下来 60 秒直接拒绝调用，不再打上游；冷却结束后半开探测。

**第三层：把结构化错误喂回模型。** 别返回堆栈，返回这种：

```json
{"status": "error", "type": "upstream_unavailable", "retry_after": 60, "fallback": "cache"}
```

模型拿到这个会自己决策：告知用户、走缓存、还是换工具。原始堆栈只会换来一句道歉加幻觉。

**第四层：降级链路。** 主 API → 备用 API → 本地缓存（明确标注"数据为 X 分钟前"）→ 坦诉做不了。每一步降级都要让模型知道自己在用非一手数据。

## 踩坑点

- **重试非幂等操作**。发消息、控制设备类工具重试三次就是执行三次。写操作要么带幂等键，要么失败后交还给人确认。
- **靠 prompt 限制重试**。治标不治本，换个对话轮次模型就忘。上限必须写死在代码里。
- **退避没加抖动**。上游恢复瞬间所有实例一起重试，二次打挂。
- **缓存数据不标新鲜度**。模型会把三小时前的天气当实时数据汇报。
- **单步超时太长**。60 秒超时放进 10 步链条，等于整条任务报废。建议压到 15 秒内。
- **熔断太敏感**。偶发一次超时就熔断，可用性反而下降，阈值从 5 次连续失败起步。

## 可复用建议

- 统一所有 MCP 工具的错误返回 schema，一套约定走遍全部插件。
- 重试、熔断、降级全部放适配层；prompt 只负责决策，不负责兜底。
- 定时任务单步失败不中断流水线，标记后继续，最后汇总报告。
- 主动做故障演练：写个 mock 工具固定返回 500，观察 agent 的行为，比等线上事故便宜得多。

## 总结

Agent 的可靠性等于最弱那次工具调用的可靠性。外部 API 挂掉不是需要修复的异常，而是需要设计的一等状态。把重试预算、熔断、降级链路放进适配层，把干净的错误语义留给模型，把最终解释权留给人——这套结构搭好后你会发现，多数"agent 发疯"的案例，根源都是某个没人管的上游超时。
