# USER.md 实践：把“我是谁”写成 Agent 可读的配置文件

## 背景

这一年大家把项目上下文的工程化做得很足：CLAUDE.md、AGENTS.md、各种 rules 文件，让 Agent 进仓库就知道构建命令和代码规范。但很少有人给“自己”写一份同类文件。结果是：Agent 读完了整个代码库，却不知道你是谁——你用 pnpm 还是 npm、回复要多长、哪些操作是雷区。

OpenClaw 这类常驻 Agent 把这个问题放大了。它跨会话运行、接了一堆 MCP 工具，如果你每次都要在对话里重复“用中文回、别加注释、部署只走白名单机器”，说明这些偏好应该固化成文件，而不是消耗在每一轮对话里。

## 问题

具体表现为三类：

1. **重复输入**：个人偏好散落在历史会话里，新会话全部归零。
2. **建议不贴身**：Agent 给出的方案永远“通用正确”，但不符合你的技术栈和约束。
3. **内置记忆是黑盒**：多数产品的 memory 功能不可审计、不可 diff、不可迁移。一份纯文本的 USER.md 恰好补上这个缺口：可版本化、可审查、跨工具通用。

## 做法

方案很简单：在固定路径放一个 USER.md，让 Agent 在会话启动时读取。

**步骤：**

1. 建文件，建议放在 `~/.openclaw/USER.md`（或 workspace 根目录），纳入 dotfiles 仓库用 git 管理。
2. 内容分五块，**控制在 40 行以内**：
   - 身份与角色：你是谁、主要负责什么
   - 技术栈与硬约束：语言、包管理器、部署方式、绝对不碰的东西
   - 沟通偏好：回复语言、详略程度、是否先给方案再动手
   - 当前上下文：在做的 2~3 个项目，一句话一个
   - 雷区：明确列出“不要做”的事
3. **写事实，不写愿望**。“用 pnpm，不要生成 package-lock.json”是有用的；“希望代码质量高”是废话。
4. 注入方式任选：启动脚本里 cat 进 system prompt；或包一层 MCP resource 暴露给 Agent；OpenClaw 场景直接在 bootstrap 流程加一步读取。
5. 每月 review 一次，过期条目直接删。

示例片段（节选）：

```markdown
## 技术栈
- Node + pnpm，禁止 npm install
- 部署只走 staging → prod 两步，不直连生产机

## 沟通偏好
- 中文回复，结论先行
- 改代码前先说方案，一句话能说清就不展开
```

## 踩坑点

- **写太长**。超过 60 行后关键约束被稀释，Agent 开始“选择性失忆”。篇幅以一次能扫完为准。
- **写成日记**。“上周在调试 X”这类信息两周后就是噪音，过期就删。
- **放敏感信息**。这个文件大概率会被发到模型 API，API key、客户名称、内网地址都不要写。
- **更新不生效**。有些框架缓存 system prompt，改完文件记得重开会话验证一次。
- **和项目文件打架**。定好优先级：任务级 prompt > 项目级 AGENTS.md > USER.md。个人偏好只兜底，不覆盖项目规范。

## 可复用建议

- **当代码维护**：git 管理、写 commit message、定期 review，别当随手记事本。
- **分层注入**：个人层（USER.md）、项目层（AGENTS.md）、任务层（当前 prompt），各管各的，互不越界。
- **让 Agent 帮你维护**：每月问一次“读我的 USER.md，指出过期、含糊或自相矛盾的条目”，比人工 review 快得多。
- **多工具复用**：这份文件可以同时喂给不同 Agent，一份事实源，避免偏好漂移。

## 总结

USER.md 的价值不在技术难度，而在于把“个人上下文”从对话流里抽出来，变成一份可审计、可版本化的配置。二十分钟写完初版，之后每个会话省掉几分钟的重复交代，长期看是对 Agent 协作 ROI 很高的一笔投入。建议先从五个章节的最小版本开始，跑两周再迭代。
