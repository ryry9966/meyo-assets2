## 背景

云 API 用久了有两个不爽：一是数据要出门，处理内部文档、日志、代码时总归别扭；二是成本随着 agent 循环调用线性上涨——一次自动化任务几十轮工具调用，token 烧得心疼。于是把模型搬到本地成了很多 OpenClaw 用户的自然选择：延迟稳定、无按量计费，还能和 MCP 工具链跑在同一台机器上。

## 问题

但"跑起来"和"能干活"是两回事。我最初踩的坑：模型能对话，接到 agent 里做工具调用就乱选参数；上下文一长直接 OOM；同样一张卡，别人跑 14B 很流畅，我跑 8B 都卡。后来发现核心是三件事没搞清：显存怎么算、量化怎么选、agent 场景对模型的要求和聊天完全不同。

## 做法与步骤

1. **先盘硬件，再选模型。** 显存是硬约束。经验公式：模型体积 ≈ 参数量 × 量化位宽 ÷ 8，再留 20%–30% 给 KV cache 和运行时。24G 显存跑 Q4 的 14B 很从容；12G 是 7B–8B 的甜点区；纯 CPU 也能跑，但只适合低频调用。
2. **运行时选 Ollama 或 llama.cpp。** 两者都提供 OpenAI 兼容接口，OpenClaw 侧只要把 base URL 指到 `http://localhost:11434/v1` 这类地址即可，零改造接入。需要极致吞吐再上 vLLM，但消费级卡上收益有限。
3. **量化从 Q4_K_M 起步。** 这是社区验证最多的平衡点，质量损失可感知度低。别一上来就 Q8——显存翻倍换不来对等的提升。
4. **显式配置上下文和 KV cache。** Ollama 默认 num_ctx 只有 2048，agent 场景必改；开 flash attention、KV cache 用 Q8 量化，能省下可观显存。
5. **选"会调工具"的模型。** 本地做 agent，优先选官方声明支持 function calling 的指令模型，并在自己的任务上实测，而不是看榜单。

配好后我接了两个真实场景：本地日志的敏感信息抽取，以及夜间批量的文档摘要——这两类任务对推理深度要求不高，但对数据不出机器、成本为零要求很高，正好匹配本地模型的长处。

## 踩坑点

- **显存 OOM 的元凶常常是上下文，不是权重。** 32K 上下文的 KV cache 可以轻松超过模型本身，先降 ctx 再降量化。
- **部分量化版本会破坏工具调用。** 同一模型不同 GGUF 版本行为差异很大，换模型时先跑一轮真实的工具调用回归。
- **小模型在 agent 循环里会"漂"。** 多步任务中容易忘记目标、幻觉出不存在的方法名。把单步任务拆小、在系统提示里明确列出可用工具，能明显缓解。
- **解码速度别只看 tokens/s。** prefill 速度在长系统提示的 agent 场景里才是瓶颈，命中缓存的话差距巨大。

## 可复用建议

- 用 OpenAI 兼容协议做一层抽象，本地和云端端点随时互换，做成"本地优先、云端兜底"的路由。
- 为自己的机器写一份模型卡：模型、量化、ctx、并发下的实测 tokens/s 和显存峰值。换卡换模型时对着改，不用重新踩坑。
- 评估用自己的真实任务集，10 条代表性样本远比跑分有用。

## 总结

本地部署不是替代云 API，而是给 agent 体系补一层"便宜、私密、可控"的底座。把显存账算清、选对量化、确认工具调用能力，一台普通游戏本就能承担相当一部分自动化负载。剩下的判断交给路由：高频简单的给本地，复杂推理的留给云端——这套组合在我这里跑了两周，稳定且账单为零。
