## 背景

跑过一段时间 OpenClaw agent 的同学应该有体感：一条完整的自动化链路里，LLM 调用远不止一次。规划、工具选择、结果摘要、格式化输出，每个节点都在烧 token。全走 GPT，月底账单比服务器还贵；全换本地模型（Ollama/vLLM 起 Qwen 之类），复杂任务质量塌得很快。多模型路由要解决的就是这个分配问题：哪些节点配得上 GPT，哪些节点本地模型绰绰有余。

## 问题

我们的场景是一个内部运维 agent：读取工单 → 判断类别 → 调 MCP 工具 → 汇总结果。最初两版配置都走了极端：

- **v1 全走 GPT**：单次成本可以接受，但每天几百次定时任务跑下来，八成 token 花在“这条工单是不是网络类”这种分类上，纯属浪费；敏感日志还要出公网，合规一直有意见。
- **v2 全走本地 7B**：分类没问题，但规划节点经常选错工具、生成参数缺字段，重试率上去了，端到端延迟反而比 v1 更差。

结论很直接：问题不是“选哪个模型”，而是“每个节点选哪个模型”。

## 做法

我们最终落到**三层分工 + 按节点静态路由**，没有上动态 AI 路由：

1. **给节点分层**。规划、复杂代码生成、多工具编排 → 强云端模型；分类、抽取、短文摘要、格式转换 → 本地小模型；不确定的任务 → 云端但收紧 max_tokens。
2. **在 OpenClaw 模型配置里定义 profile**，不要散落硬编码：

```yaml
profiles:
  strong: { model: gpt-4.1, temperature: 0.2 }
  fast:   { model: qwen2.5-7b, endpoint: http://127.0.0.1:11434 }
routing:
  planner: strong
  ticket_classifier: fast
  summarizer: fast
  fallback: strong
```

3. **加一条升级（escalation）路径**：fast 层输出先过 schema 校验，解析失败或置信度低，就带着原始上下文升级到 strong 层，升级次数上限 1 次。
4. **每个节点记录** token 数、首 token 延迟、升级率，跑两周后按数据调整节点归属。

## 踩坑点

- **别用 prompt 长度做路由依据**。最短的“从三个工具里选一个”恰恰最容易错，短 ≠ 简单。
- **本地模型的 JSON 遵循度是重灾区**。7B 模型偶尔在枚举值上自由发挥，schema 校验 + 一次升级是底线，别裸解析。
- **上下文按本地模型算**。云端 128k 用惯了，工具返回的大段日志直接塞给本地模型会静默截断，路由层要提前裁剪。
- **升级链路设上限**。fast 失败 → strong 失败 → 再重试，很容易写出死循环；限 1 次升级 + 总重试 2 次够用。
- **本地推理服务保活**。模型冷加载一次十几秒，定时任务场景把模型常驻并预热，否则“本地更快”不成立。
- **涉密数据钉死本地层**，不参与任何路由和升级，哪怕代价是质量略降。

## 可复用建议

- **先静态、后动态**。配置写死的按节点路由能解决 80% 的问题；让一个 LLM 当路由器，等于每次多付一次调用，早期不值得。
- **升级方向只有一个：本地 → 云端**。反向降级听起来省钱，实际把最贵的调用放在了最不确定的位置。
- **数据说话**。某节点升级率持续 < 3%，可试着下放到本地层；升级率 > 15%，说明分错了层，收回来。
- **prompt 保持模型无关**。别调教出只在某个模型上成立的写法，否则路由一改全链路返工。

## 总结

多模型路由本质是成本、质量、延迟的三角权衡，不是炫技。我们上线三层分工后，token 成本降了六成左右，P95 延迟基本持平，敏感数据全部留在内网。核心经验一句话：按节点分层，静态路由起步，用升级率和成本数据慢慢调，别急着上花哨的动态路由。
