## 背景

Agent 要真正干活，绕不开外部服务：查库存、发通知、拉工单、写数据库。在 OpenClaw 里，这条路主要有两种走法——通过 MCP 挂载现成的 server，或用插件/工具机制自己封装 HTTP 调用。这条"握手"链路看似只是配个 key 的事，实际工程里坑不少。

## 问题

社区里反复出现三类失败：

1. **工具描述与模型理解错位**。LLM 拿到的是 schema 和 description，不是你的代码。描述含糊，模型就会传错参数，或者该调的时候不调。
2. **返回值失控**。接口原样吐回 50KB 的 JSON，两三轮就把上下文撑爆；或者错误被吞掉，模型误以为操作成功。
3. **长调用与限流**。同步等一个 40 秒的导出任务，直接超时；批量请求没做退避，被 429 打死。

## 做法

我们内部接新服务时按这个顺序走：

**第 1 步：选路径。** 一次性的简单调用，写插件工具即可；服务若会被多个 agent 复用、或想跨客户端共享，包成 MCP server 更划算。别为了"新"上 MCP，也别图省事全塞插件。

**第 2 步：定义接口，而不是转述接口。** 不要把上游 OpenAPI 文档原样翻成 description。站在模型视角重写：这个工具什么时候用、参数是什么含义、什么情况该改用别的工具。参数尽量少而具体，枚举优于自由字符串。

**第 3 步：收敛返回值。** 拿到响应后做投影，只留模型需要的字段；错误统一成 `{ok, error, hint}` 结构。hint 很关键——"token 过期，请提示用户重新授权"比 401 原文有用得多。

**第 4 步：鉴权与密钥管理。** key 全部走环境变量或 secret 管理，绝不写进配置文件，更不能出现在会话历史里。token 过期在工具内部自动刷新一次，失败就返回结构化错误。

**第 5 步：超时、重试与异步化。** 每个工具设默认超时；幂等的读操作加指数退避；超过 15 秒的任务改成"提交 → 返回 job id → 轮询"模式，别让 agent 干等。

**第 6 步：最小验证。** 上线前跑两条固定用例：一次真实调用成功，一次故意失败，确认两种路径下模型的反应都符合预期。

## 踩坑点

- description 写成"查询数据"这种万能话术，模型会在该用 A 工具时选 B。每个描述写清适用边界，最好给反例。
- 直接透传上游报错堆栈，模型会去"修复"根本不该它管的东西。错误信息要面向决策，不是面向调试。
- 工具数量超过 15 个后，选择准确率明显下降。不常用的服务拆独立 agent 或动态加载。
- 忘记处理分页，模型拿第一页当全量数据用。
- 写操作没保证幂等，重试导致重复建单、重复发通知。给写操作带客户端生成的幂等键。

## 可复用建议

把下面这份 checklist 固化到你的接入流程里：

- [ ] description 面向模型重写，含使用边界和反例
- [ ] 参数最小化，枚举优先
- [ ] 返回值做投影，错误统一带 hint
- [ ] 密钥走环境变量，支持自动刷新
- [ ] 超时 + 幂等键 + 指数退避
- [ ] 长任务异步化，返回 job id
- [ ] 成功/失败两条路径都有验证用例

## 总结

对接外部服务的本质不是"调通 API"，而是给模型一份它能正确使用的契约。工具描述写给模型看，返回值服务于决策，错误信息指向下一步动作。把这三件事做扎实，OpenClaw 和外部服务之间的握手才算真正稳。
