## 背景

Agent 的价值不在于会说，而在于能做。OpenClaw 里的 agent 一旦要触碰真实世界——查内部服务、创建工单、触发构建、同步数据——就必须和外部 API 打交道。这个"握手"环节看起来只是配置问题，实际上是一次小型接口设计：你在为模型这个"手速很快、但完全按字面意思理解世界"的用户，重新封装一遍 API。

## 问题

模型不能直接发 HTTP 请求，它依赖工具层把意图转成调用。实践中常见的三类翻车：

1. **工具面太宽**：把 40 个 endpoint 全暴露出去，模型在相似 schema 之间反复选错；
2. **错误不可读**：API 返回裸 500 或一坨 JSON，模型只能瞎猜重试，甚至幻觉出"已成功"；
3. **副作用不可控**：一个 POST 被重试两次，产生两笔订单。

## 做法

我们团队内部沉淀了一条比较稳的路径，按顺序走：

**第一步：选接入方式。** 需要标准化、想跨多个 agent 复用的能力，走 MCP server；只是某个 agent 的私有动作，直接写 OpenClaw 插件（function calling 形式）更快。不要为了"先进"把所有东西都包成 MCP。

**第二步：收窄工具面。** 按"任务"而不是"资源"定义工具。比如不暴露 `update_user / patch_user / set_user_status` 三个接口，而是一个 `disable_user(user_id, reason)`。5~8 个语义清晰、互不重叠的工具，远好于 30 个 REST 镜像。

**第三步：写工具描述要像写 prompt。** 参数描述里放约束和示例："status 只能是 active/suspended，枚举之外的值会被拒绝"。描述含糊是参数幻觉的第一大来源。

**第四步：认证与密钥隔离。** token 放环境变量或 secret store，由适配器层注入请求头，绝不让它出现在工具参数或上下文里。过期刷新逻辑也在这一层做掉。

**第五步：把错误翻译成模型语言。** 适配器统一把 HTTP 错误映射成结构化返回：`{ok: false, reason: "rate_limited", retry_after_ms: 2000}`。模型读懂 reason 后能做出合理动作，而不是面对 500 干瞪眼。

**第六步：幂等与异步。** 所有写操作带幂等键；超过 10 秒的调用拆成"提交任务 + 查询状态"两个工具，避免阻塞和超时导致的假失败。

## 踩坑点

- **返回 payload 不裁剪**：一个 20KB 的 JSON 塞进上下文，几轮对话就把窗口吃光。字段过滤放在适配器层做。
- **重试不设退避**：模型在 rate limit 后立刻重试，直接雪崩。把 retry_after 写进错误返回里。
- **日志打印完整请求体**：密钥跟着进了日志系统。日志必须先脱敏。
- **工具改名或改参数不走版本化**：依赖它的 agent 流程静默坏掉，等发现时已经跑了几天。

## 可复用建议

评估一个新 API 对接是否合格，用这张清单：工具面是否收窄到任务级？错误是否结构化且可行动？写操作是否幂等？密钥是否全程隔离？返回是否限量？每次调用是否有 request_id 可追？六个都过，再考虑上线。

## 总结

Agent 与 API 的握手，本质是给模型设计一份它能理解、能纠错、不敢乱来的工程契约。工具层做得越克制，agent 的行为就越可预测。建议从一个小而完整的工具开始，先跑通错误处理和幂等，再逐步扩面——比一上来铺满 endpoint 省太多返工。如果你在 OpenClaw 里做过有意思的对接，欢迎在评论区交流具体方案。
