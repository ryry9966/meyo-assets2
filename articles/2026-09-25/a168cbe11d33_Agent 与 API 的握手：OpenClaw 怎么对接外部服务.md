## 背景

Agent 的能力边界，基本取决于它能摸到多少外部服务。查库存、发工单、读监控，都绕不开 API。OpenClaw 的思路是把"对接"收敛到两条正规路径：MCP server 和插件/技能，而不是让模型拿着一个万能 HTTP 工具到处裸调。

## 问题

动手前先做路径选择：

1. **通用 fetch 工具**：灵活，但鉴权、限流、错误处理全裸奔，出问题没法定位；
2. **自写插件**：稳，业务逻辑包死，但每接一个服务都要重写一遍；
3. **MCP server**：用标准协议把服务暴露成工具，社区主流做法。

我最近对接内部工单系统和天气服务，走的都是 MCP 路线，下面以工单系统为例。

## 做法

1. **写一个最小 MCP server**。用官方 SDK（Python/Node 均可），先只暴露两个只读工具：`list_tickets` 和 `get_ticket`。JSON Schema 要收紧，比如 `status` 限定枚举值，别给模型自由发挥的字符串。
2. **鉴权走环境变量**。token 放 `.env`，配置里只引用变量名，不落明文。先用只读 scope 的 token 跑通。
3. **在 OpenClaw 配置中注册 server**，指定启动命令和环境。重启后用一句自然语言验证："查一下最近五个未关闭的工单"，观察它选了哪个工具、传了什么参数。
4. **把工具描述当接口文档写**。模型靠 description 选工具，"什么时候用、参数含义、返回什么"写清楚，比反复调 prompt 有用得多。
5. 只读跑稳之后，再加写操作（如 `create_ticket`），并配一层确认机制。

## 踩坑点

- **描述含糊会张冠李戴**。我把 `get_ticket` 写成"查询工单"，模型拿工单号去调了 `list_tickets`。改成"按工单 ID 精确查询单条详情"立刻恢复。
- **上游 429/超时直接抛异常，模型就开始胡编**。工具层要捕获错误，返回结构化文本：错误码、原因、建议动作，让模型"读得懂失败"。
- **工具一多选择就乱**。每个服务独立一个 server，按需启用，别把二十个工具全挂上。
- **写操作必须考虑幂等与确认**。给 `create_ticket` 带上客户端生成的 request_id，重复调用不产生重复工单。

## 可复用建议

- 先只读、后写入，权限 scope 最小化；
- 每个外部服务独立 MCP server，工具面尽量小；
- 超时与重试在工具层做，别指望模型自己处理；
- 给所有工具调用留日志，排障全靠它。

## 总结

对接外部服务的本质，不是"让模型会发 HTTP 请求"，而是把每个服务的鉴权、边界、错误语义封装成模型能正确理解的小工具。MCP 提供了标准化的握手方式，剩下的工程活——收紧 schema、写好描述、守住权限——仍要自己来。跑通一个只读工具大约半天工作量，是性价比很高的起点。欢迎在评论区交流你们的对接实践。
