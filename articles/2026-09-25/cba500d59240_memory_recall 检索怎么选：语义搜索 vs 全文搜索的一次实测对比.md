## 背景

OpenClaw 的 agent 长期跑下来会积累不少 memory：用户偏好、项目上下文、历史决策。`memory_recall` 是把这些内容捞回来的入口。我们团队维护一个日常跑自动化的 agent，记忆条目 3000+ 条，中文为主，接入方式是标准 MCP 工具调用。最近发现 recall 命中质量不稳定，于是把语义搜索和全文搜索各跑了一遍数据，做了对比。

## 问题

两个核心疑问：

1. 中文场景下，语义搜索（embedding + 向量相似度）是不是天然更好？
2. 应该二选一，还是做混合？

直觉上语义搜索能理解"意思"，全文搜索只能匹配关键词。但实测之前，直觉不一定靠得住。

## 做法

搭了个小型评测集：从历史会话抽 60 条真实问题，人工标注每条对应的记忆 ID，然后分别测三路：

- **语义搜索**：embedding 模型 + 向量库，cosine 相似度，取 top-5
- **全文搜索**：SQLite FTS5 + jieba 分词，BM25 排序，取 top-5
- **混合**：两路各取 top-5，分数归一化后加权融合（0.6 / 0.4）

结果（Recall@5，语义 / 全文 / 混合）：

| 问题类型 | 语义 | 全文 | 混合 |
|---|---|---|---|
| 偏好类（"我习惯用什么部署"） | 0.72 | 0.55 | 0.80 |
| 精确类（报错串、命令、文件名） | 0.48 | 0.85 | 0.87 |
| 总体 | 0.63 | 0.68 | 0.83 |

结论很清晰：不是谁取代谁，是互补。语义赢在换说法还能召回；全文赢在专有名词、代码、报错串这类"必须字面一致"的查询。混合最好，提升主要来自两边的失败案例互相兜底。

## 踩坑点

1. **中文分词是全文搜索的命门**。FTS5 默认按空格切，中文等于没分词，必须接 jieba 或 ICU tokenizer，否则全文成绩会惨到让你误判整个方向。
2. **embedding 模型的中文能力差异很大**。同一个库换个模型，语义召回能差 15 个点。别只看榜单，用自己业务的真实 query 测。
3. **两路分数不可直接比**。cosine 和 BM25 量纲完全不同，混合前必须各自归一化（min-max 或 rank-based 都行），否则权重参数就是摆设。
4. **单条记忆太长会稀释向量**。一条 memory 塞几千字，embedding 会被泛化，排名反而下降。控制在 200 字以内效果明显更好。

## 可复用建议

- 默认上混合，权重从 0.6（语义）/ 0.4（全文）起步，再按 query 类型微调
- 先解决中文分词，这一步比选哪个向量库更重要
- 给 memory 加来源和时间戳，recall 结果按新旧做轻微衰减，避免旧记忆霸榜
- 维护一个 30–60 条的小评测集，任何检索改动都跑一遍，别凭感觉调参

## 总结

语义搜索和全文搜索不是选型题，是组合题：语义负责"换了说法也能找到"，全文负责"一字不差必须找到"。在 OpenClaw 的 `memory_recall` 里把两路都接上，成本不高（一个分词器加一次归一化），召回质量提升是实打实的。先测再选，别信直觉。
