## 背景

过去半年，我把不少自动化流程从纯云端 API 逐步迁到了本地模型。动机很朴素：数据不出门、批量任务零边际成本、断网也能干活。对 OpenClaw 用户来说，本地模型最大的价值不是替代旗舰模型，而是给 Agent 提供一个不限量、低延迟的"干活力工"——把贵的高速推理留给真正难的环节。

## 问题

家用硬件跑大模型，核心矛盾有三个：

1. **显存预算**：模型权重 + KV cache 都要吃显存，账没算好就频繁爆内存；
2. **工具调用质量**：量化到 Q4 之后，函数调用和 JSON 输出的稳定性明显下降，而 Agent 恰恰最依赖这个；
3. **上下文长度**：Agent 场景下 system prompt 加工具描述动辄上万 token，默认配置根本不够用。

## 做法与步骤

**硬件判断**：经验法则——7B Q4 模型约占 5GB 显存，14B 约 10GB，32B 需要 20GB 以上。纯 CPU 也能跑，但 Agent 多轮循环会慢到难以接受，有独显尽量 offload。

**运行时选择**：Ollama 上手最快，llama.cpp 控制粒度最细，vLLM 吞吐高但吃显存。个人建议从 Ollama 开始，跑通后再按需迁移。

**模型选择**：中文场景 Qwen 系列性价比高；14B 是单卡 12–16G 的甜点位；32B 适合双卡或 48G 显存。不要盲目追最新最大。

**部署流程**：

1. 安装 Ollama，拉取模型；
2. **关键一步**：把 `num_ctx` 设到 16k–32k，默认值太小；
3. 暴露 OpenAI 兼容接口（`OLLAMA_HOST=0.0.0.0`）；
4. 在 OpenClaw 侧把 base_url 指向本机端口；
5. 用真实工具调用任务跑一轮冒烟测试，统计成功率，而不是看感觉。

## 踩坑点

- **上下文截断**：`num_ctx` 没调大时，聊几轮工具描述就被截掉，表现为模型突然"忘了"自己有工具。排障第一嫌疑永远是它。
- **量化降级**：Q4_K_M 日常对话没问题，但结构化输出错误率上升。承担工具调用的模型建议 Q6 起步。
- **KV cache 挤占**：上下文开到 32k 后，KV cache 可能比权重还吃显存，导致 GPU offload 层数被动下降、速度暴跌。用 `ngl` 参数显式控制。
- **模型冷启动**：内存不足时 Ollama 会自动卸载模型，下一条请求要多等十几秒。设 `keep_alive` 保活。
- **并发为 1**：本地推理基本是单并发，Agent 里多个并行工具调用会被串行化，编排任务时要有心理预期。

## 可复用建议

- **自建工具调用评测集**：挑 20 个真实任务，每次换模型或量化级别跑一遍，看成功率，别迷信公开 benchmark；
- **路由分层**：格式转换、摘要、分类走本地；复杂规划、长链推理走云端。在 OpenClaw 里按任务类型配置不同模型，成本和质量的平衡点自己找；
- **记录显存账本**：权重 + KV cache + 系统占用，换配置前先算再拉，避免反复试错。

## 总结

本地模型不是用来替代旗舰 API 的，而是把 Agent 工作流里 80% 的机械劳动本地化。从 7B/14B 起步，把上下文长度和量化等级这两件事搞对，大部分家用电脑都能跑出可用的生产力。跑通第一条链路之后，再谈优化也不迟。
