## 背景

接上 MCP 之后，Agent 能干的事一下子变多了：查库、调 API、写文件、发消息、花钱。工具越多，越绕不开一个问题——哪些动作可以直接执行，哪些必须停下来等人确认。

我们最初的方案很粗糙：读操作放行，写操作全部弹确认。跑了两周，确认弹窗多到团队开始无脑点"允许"，权限控制形同虚设。

## 问题

权限边界设计里有两个常见极端：

- **全部要确认**：人变成审批机器人，产生"确认疲劳"，最后看到弹窗直接同意，风险反而更高。
- **全部放行**：靠 system prompt 里一句"谨慎操作"兜底。长上下文、多轮工具调用之后，模型对风险的判断会明显漂移。

本质上这是工程问题，不是 prompt 问题：边界要编码在工具层（MCP/插件层），而不是指望模型自己掂量。

## 做法：三级分类 + 两个闸门

**第一步，给工具分级。** 按"可逆性 × 影响半径 × 成本"三个维度，把 MCP 工具分成三档：

- **绿档**：只读、幂等、可逆。如查询、列表、dry-run、沙箱内写。默认自动执行。
- **黄档**：有外部副作用但影响有限，如测试环境写入、发内部通知。执行前生成计划摘要，等人确认。
- **红档**：不可逆或影响半径大，如删数据、动生产库、对外发送、涉及资金。禁止 Agent 直接调用，人工在原系统操作，Agent 只做准备和汇报。

**第二步，把"问人"做成一等公民工具。** 在 MCP 里实现 `request_approval`，要求 Agent 传入结构化上下文：要做什么、改哪个对象、前后 diff、失败回滚方案。人看到的是一张可判断的卡片，而不是一句"是否继续？"。

**第三步，用自动闸门替代部分人工确认。** 预算上限（单次成本、API 配额）、频率限制、影响行数阈值——超了自动降级为黄档或直接拒绝。机器能拦的，别消耗人的注意力。

**第四步，全程审计。** 每次调用记录：谁批准的、依据什么上下文、结果如何。这是后续调整边界的唯一依据。

## 踩坑点

1. **确认疲劳比误操作更危险。** 弹窗每天超过十几条，人就会机械化放行。宁可收紧绿档定义，也要把弹窗压到真正值得看的量级。
2. **只读操作未必无副作用。** 外部查询可能消耗配额、触发 webhook、写缓存。外部只读我们照样归黄档。
3. **确认粒度错了。** 逐条确认太碎，按计划一揽子确认又容易被整体放行。我们的折中：计划级确认 + 红档二次确认。
4. **审批超时没处理。** 人不在，Agent 卡在等待，会话过期后自动重跑，等于绕过了审批。超时必须显式失败并记录。
5. **让模型自评风险。** 试过让模型先自评再决定是否问人，结果复杂任务里它几乎永远自评"低风险"。分级规则放代码里，模型只负责填上下文。

## 可复用建议

- 一句话判断口径：**可逆且半径小就自己干，不可逆或外部可见就问人，红档干脆不经过 Agent。**
- diff 永远比"是否继续"有用，写操作前先给人看会改什么。
- 预算和阈值是免费的闸门，先上这个再谈人工审批。
- 边界规则版本化，每次放宽留记录、可回滚。

## 总结

权限边界不是给 Agent 上锁，而是把人的注意力花在刀刃上。核心就三件事：分级在代码层做死、确认带上下文、能用预算闸门解决的别麻烦人。跑顺之后你会发现——问人的次数越少、每次质量越高，Agent 的可用性反而越高。
