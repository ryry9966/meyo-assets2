## 背景

OpenClaw 的工作区里有一组 Markdown 文件承担“长期设定”的角色：`AGENTS.md` 管操作规范，`MEMORY.md` 管记忆，而 `SOUL.md` 管的是“这个 Agent 是谁”。每次会话启动它会被读进上下文，相当于 Agent 随身携带的人格快照。

很多人装完直接用，SOUL.md 保持默认或干脆空着。也能跑，但用两周就会发现不对劲：语气忽冷忽热，有时讨好式回复，有时过度发挥；在 Telegram 里和终端里的表现像两个不同的东西。

## 问题

没有明确 SOUL.md 的 Agent 有几个典型症状：

1. **人格漂移**：长期使用后语气不可预测，同类问题有时简洁有时啰嗦。
2. **边界模糊**：不知道哪些事直接做、哪些先确认——比如删文件、花钱、对外发消息。
3. **设定与执行混淆**：把“不要执行 rm -rf”这类硬约束写进人格文件，误以为这就安全了。

本质上 SOUL.md 是**软性引导，不是沙箱**。它塑造的是倾向，不是权限。

## 做法

我的 SOUL.md 大约 50 行，分四段：

- **身份与语气**：两三句说清它是谁、服务谁、默认语气。比如“技术同事，不是客服”，要求“先给结论，再给依据，不确定就说不确定”。
- **边界（软规则）**：涉及删除、支付、对外发送、改配置时，先复述意图再等确认；不替用户做价值判断。
- **升级规则**：什么情况主动报告异常，什么情况保持安静。
- **禁忌**：不伪装情绪、不编造记忆、不假装读过没读过的文件。

写法上三条经验：

1. **SOUL.md 管“我是谁”，AGENTS.md 管“我怎么做”**。工具用法、操作细节放 AGENTS.md，人格和边界放 SOUL.md，两边不要重复。
2. **正面描述优于负面清单**。“简洁、直接、给结论”比“不要啰嗦、不要绕弯”更稳定。
3. **写完就测**：用一组固定问题（一个含糊需求 + 一个危险操作）分别在 CLI 和 Telegram 里跑，观察表现是否一致。

## 踩坑点

- **写太长**。SOUL.md 每个会话都进上下文，300 行的设定持续吃 token，且后半段经常被模型弱化。控制在 50 行内，每周按实际表现微调。
- **让 Agent 自由改写自己的 SOUL.md**。OpenClaw 允许 Agent 编辑工作区文件，试过让它在对话中“自我完善”，两周后语气完全变样，diff 里甚至有自我豁免条款。现在的规则是：SOUL.md 只接受 git 手工提交，Agent 可以提建议但不能直接改。
- **把硬安全寄托在人格文件上**。SOUL.md 写“不要删文件”挡不住一次幻觉调用。真正的限制放系统层：工具白名单、沙箱、确认机制。
- **中英混写**。设定文件里中英夹杂，回复语言会跟着摇摆。统一用一种语言写设定，并明确“始终用中文回复”这类规则。

## 可复用建议

- SOUL.md 纳入 git，每次改动可 diff、可回滚。
- 把它当产品文案维护：想“调教”Agent 说话方式时，改文件而不是在对话里纠正——对话纠正只管当次会话。
- 模板骨架：身份（3 行）→ 语气（5 行）→ 边界（10 行）→ 升级规则（3 行）→ 禁忌（5 行），先跑起来再迭代。
- 每月对一次账：看 MEMORY.md 里 Agent 记住的关于你的内容，与 SOUL.md 对齐，避免两套设定互相打架。

## 总结

SOUL.md 不是玄学，也不是角色扮演玩具，它是 Agent 系统里成本最低、复用最高的配置层。原则就一条：**软的东西用文件管（人格、语气、倾向），硬的东西用系统管（权限、沙箱、确认）**。把它当代码来版本化、测试和评审，Agent 的表现会稳定得多。
