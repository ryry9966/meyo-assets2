## 背景

常驻型 Agent（比如 OpenClaw 这类个人助理）需要一个“自己知道该干活了”的机制。社区里最常见的两条路线：**heartbeat 定时唤醒（轮询）** 和 **webhook/事件推送**。我见过不少第一版实现走极端——要么纯轮询，token 账单难看；要么纯推送，事件静默丢失。这篇把两条路线的边界和折中讲清楚。

## 问题

- **纯轮询**：每次唤醒都要付出 prompt token 和一次推理，实际多数 tick 是空转。间隔短了烧钱，间隔长了延迟不可接受。
- **纯推送**：要求每个数据源都支持 webhook，还要解决公网暴露、签名校验、断线补发。一旦连接断了错过事件，Agent 永远不知道漏了东西。

## 做法

1. **先分类任务**：延迟敏感且数据源支持推送的（IM 消息、告警）走推送；源不支持推送、或允许分钟级延迟的（RSS、状态巡检、每日汇总）走轮询。
2. **推送链路**：外部服务 → gateway webhook → 校验签名 → 投递到 Agent 消息队列 → 触发一次处理。事件必须带去重键。
3. **轮询链路**：heartbeat 每 N 分钟唤醒，读一份很短的检查清单（OpenClaw 里就是保持 HEARTBEAT.md 精简），逐项判断“有没有事”，没事直接结束，不调用任何工具。
4. **自适应间隔**：连续 K 次空转就把间隔翻倍（设上限），有事件命中就恢复基础间隔；夜间加 quiet hours。
5. **兜底对账**：推送通道也要配一个低频轮询做对账，防止静默丢事件。

## 踩坑点

- **心跳 prompt 太肥**：唤醒时带着完整系统提示和长上下文，空转一次也烧几千 token。清单务必独立成小文件，唤醒只读它。
- **没有“无事早退”路径**：Agent 每次心跳都认真思考、调工具，等于把心跳跑成了隐形 cron 风暴。这是最常见的事故。
- **推送不幂等**：重试或重连后同一事件触发两次回复。必须用事件 ID 去重。
- **webhook 裸奔**：不校验签名，等于给公网开了一个能驱动你 Agent 的接口。
- **本机休眠**：笔记本合盖后心跳停摆，醒来瞬间补发一堆过期任务。要明确“补跑还是跳过”的策略。
- **轮询撞限流**：频率要贴着上游 API 限制设计，能用 ETag / 增量拉取就用。

## 可复用建议

- 一句话原则：**能推则推，不能推则轮询；轮询必须有廉价早退。**
- 心跳是安全网和兜底，推送是快路径——两者是分层关系，不是二选一。
- 每次心跳记一行日志：唤醒原因、命中项、耗时、是否空转。跑一周，你自然知道间隔该设多少，比任何经验公式都准。
- 去重键 + 幂等处理 + 对账轮询，是事件驱动 Agent 的三件套，缺一个都会在某个凌晨出事。

## 总结

轮询 vs 推送不是信仰问题，而是成本与可靠性的工程权衡。先用最便宜的 tick 保底，再把真正需要实时性的链路逐条升级为推送，最后用日志校准节奏。Agent 的“心跳”和人的心跳一样：平时察觉不到，但节奏乱了，整个系统都会跟着乱。
