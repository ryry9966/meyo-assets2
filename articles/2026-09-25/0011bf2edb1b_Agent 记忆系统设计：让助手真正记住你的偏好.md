## 背景

大模型本身无状态，所谓"记得你"，本质是把历史信息在合适的时机、以合适的形态重新注入上下文。常见的第一版做法是把用户偏好直接塞进 system prompt，起初够用，几个月后 prompt 膨胀到几千 token，过期信息和矛盾项开始互相打架。这篇帖记录我在 OpenClaw 插件里做记忆层的方案，供做同类功能的人参考。

## 问题

几个典型的失败形态：

1. **全量存聊天记录**：检索噪音比信号多，助手"记得太多"反而答非所问。
2. **只靠会话内记忆**：新开 session 一切归零，用户被迫反复自我介绍。
3. **偏好和事实混存**："用户在杭州"（事实）和"用户喜欢简洁回复"（偏好）生命周期完全不同，混在一起没法做更新和过期。
4. **只写不清**：错误记忆一旦写入，每次检索都在强化，用户说"我不是这个意思"也没用。

## 做法

核心是**分层 + 结构化 + 预算化注入**，分四步：

**1. 记忆分三层**

- 偏好层：稳定偏好（回复风格、默认语言、工具习惯），低频更新。
- 事实层：项目背景、环境信息，带时间戳，允许过期。
- 会话层：当前 session 的临时状态，session 结束即清理，只有被提炼的部分才下沉。

**2. 结构化存储**

每条记忆是一个结构体：`{id, type, content, tags, confidence, source, created_at, last_hit}`，不要存自由文本大段。写入走 MCP 工具 `memory_write`，由模型在对话中显式调用，而不是每轮后台静默抓取——显式调用天然带过滤，模型不确定时可以不写。

**3. 检索与注入**

每轮按 tags 匹配 + last_hit 排序，取 top-k（我限制在 5 条以内，约 300 token）。关键原则：**注入预算是硬约束**，记忆再重要也不能挤占当前任务上下文。

**4. 更新与遗忘**

- 冲突处理：新写入与旧条目 tags 高度重合时，走"覆盖 + 旧版本留档"，而不是追加。
- 提供 `memory_forget` 工具，用户说"忘掉这条"要真的能删。
- 定期跑清理任务，长期未命中且 confidence 低的条目归档。

## 踩坑点

- **向量检索未必是主路**。偏好类记忆就几十条时，tag 匹配效果更好；embedding 的语义泛化会把"喜欢 Python"匹配到"喜欢简洁代码"。量级上到几百条再考虑向量。
- **静默写入不可取**。后台每轮自动提取，token 翻倍，还会写入大量"用户今天问了 X"这类无价值条目。改成显式调用 + 写入前自查 confidence 后，垃圾写入少了八成。
- **记忆没有可视化，用户就不信任**。在面板加了记忆列表页，可查看、可手动删除，相关问题直接归零。
- **过期偏好很隐蔽**。用户三个月前说"用 TypeScript"，换了团队改用 Go，旧偏好还在悄悄生效。事实层必须带时间戳，注入时提示模型"以下信息可能过期"。

## 可复用建议

- 先做 key-value + tags 的简单版，别一上来上向量库，你的记忆量大概率撑不起它的收益。
- 写入走显式工具调用、检索做注入预算控制、遗忘提供用户入口——这三件事比选型更重要。
- 保留 `source` 字段，出问题时能回溯是哪轮对话写错的。
- 偏好和事实分开管理生命周期。

## 总结

记忆系统不是"存取模块"，而是一套有预算、有生命周期、有用户知情权的数据管理。先用最土的结构化方案跑起来，观察哪些记忆真的被命中，再决定要不要上更重的检索。能被用户看见和删除的记忆，才是值得信任的记忆。
