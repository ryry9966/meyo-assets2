## 背景

OpenClaw 的路由层允许在同一个 Agent 配置里挂多个模型。实际跑一段时间后，大多数人都会遇到同一个分叉点：全走 GPT 这类云端模型，账单和限速扛不住；全走本地模型，复杂任务的质量又明显掉线。所以路由不是"能不能配"的问题，而是"按什么维度切"的问题。

## 问题

默认配置往往是单模型跑全部环节：规划、工具调用循环、摘要、记忆压缩、格式化输出，全用同一个模型。结果是两个极端——简单任务烧 token，复杂任务换小模型后 function call 的参数开始出错。真正的大头成本通常不是对话本身，而是 Agent 循环里那些高频、低价值的机械调用。

## 做法

核心原则：**按角色切，不按个人偏好切**。我的路由表大致是这样：

1. **主规划器**：GPT-4o 级别云端模型。负责任务分解、跨工具决策、出错恢复。这类调用频次低、单次价值高，值得花钱。
2. **执行子代理**：本地 7B~14B（Ollama 跑 Qwen 级别）。负责单工具调用、格式转换、日志清理等机械环节。
3. **摘要与记忆压缩**：本地模型。长上下文压缩后写回 memory，不需要顶级推理，但要快。
4. **隐私敏感链路**：涉及内网数据、客户信息的 MCP 工具输出，强制本地。路由规则写在工具级配置里，不靠 prompt 约束。

每个模型 profile 都配 fallback 链：本地超时或校验失败，降级到云端兜底；云端限流，降级到本地重试。所有路由规则进版本库，当配置代码管理。

一个必须的细节：本地模型**必须开 JSON schema 校验 + 重试**。很多本地模型会"假装"完成 function call，参数结构是坏的，不校验就会把脏数据喂给下一个工具。

## 踩坑点

- **上下文窗口**：8k 的本地模型吃不下 MCP 工具的原始输出，会静默截断。先用本地摘要模型压缩，再进规划上下文。
- **重试吃掉收益**：本地模型 JSON 解析失败重试三次，成本反而接近直接用云端。校验失败超过阈值直接切 fallback 更划算。
- **CPU 推理别进交互循环**：批处理可以，交互式 Agent 循环里 CPU 跑 7B 的延迟会让整个流程看起来"卡死"。
- **embedding 模型一致性**：换了 memory 的 embedding 模型，旧向量库整批失效，检索质量断崖下跌。换模型必须重建索引。
- **隐私规则写在工具层**：写在 system prompt 里的"不要把数据发给云端"，在长对话中会被模型遗忘，工具级路由才可靠。

## 可复用建议

- **先量化再路由**：记录每个环节的模型、token、延迟、失败率，跑一周自己的真实流量再定路由表，不要照抄别人的。
- **从子代理卸载开始**，不要一上来动主规划器——收益最确定、风险最小。
- **每条路由都要有降级路径**，单一模型故障不应该让整个 Agent 停摆。
- **用固定任务集做回归**：换任何模型前后跑同一组任务，对比通过率再决定去留。

## 总结

多模型路由本质是三个变量的权衡：质量、成本、隐私。OpenClaw 的路由层足够灵活，但路由策略没有银弹——按角色切分、schema 校验兜底、降级链必备、数据说话。我的经验路径是：先让本地模型接走 70% 的机械调用，把账单降下来，再回头优化剩下 30% 关键环节的质量。
