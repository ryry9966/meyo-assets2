## 背景

跑过一段时间单 Agent 循环的人大概都遇到过同样的瓶颈：主循环是串行的，一次长耗时的检索或批量分析会卡住后面所有事；更麻烦的是，这类任务的中间产物（搜索结果、日志片段、代码上下文）会全部灌进主上下文，几轮下来上下文就被无关细节撑满了。Subagent 编排解决的正是这两个问题：**并行度**与**上下文隔离**。

## 哪些任务值得拆

先泼冷水：不是所有任务都需要 subagent。适合拆的特征比较明确——

- 子任务之间相互独立，不需要互相看到中间过程；
- 偏读操作：调研、代码检索、多文件审查、日志分诊；
- 产物可压缩、可验证：最终能收敛成一段结论加证据。

反过来，强依赖前序结果的任务、多个子任务要写同一批文件的任务，拆开只会增加协调成本。

## 编排做法

1. **任务切分**。主 Agent 负责拆解，每个子任务是一个"封闭命题"：明确的输入、明确的边界（允许动哪些目录/工具）、明确的交付格式。模糊的任务描述是编排失败的头号原因。
2. **子 Agent 提示词模板**。固定四段：角色与目标、工具白名单、禁止事项、返回格式。返回格式建议强制结构化，例如 `{结论, 证据/文件路径, 置信度, 遗留问题}`，字段缺一不可。
3. **并发控制**。信号量限流，从 3 开始调；每个子任务设超时；失败重试一次，仍失败就标记失败并继续，不让单个任务拖垮整批。
4. **结果回收**。主上下文只接收结构化摘要，原始输出落盘到文件或日志。这一条是上下文隔离能不能成立的关键。
5. **验证**。关键结论做抽查：文件是否真的改了、测试是否真的通过；重要判断可以让两个子 Agent 独立执行，交叉比对。

## 踩坑点

- **写冲突**：两个子 Agent 同时改一个文件，几乎必炸。写任务给每个子 Agent 单独的 git worktree 或独立工作区，由主 Agent 统一合并；或者干脆默认子 Agent 只读，写权限显式授予。
- **上下文回灌**：子 Agent 把完整过程贴回来，等于没隔离。返回摘要要有长度上限，超限截断重试。
- **假完成**：子 Agent 说"做完了"但什么都没发生。要求交付必须附带可核查的产物——文件路径、命令输出，不接受口头承诺。
- **成本**：并行度是 token 消耗的乘数。上线前后各跑一次同任务对比，确认收益为正。
- **过度编排**：三步就能做完的事套编排，协调开销大于收益。先测单 Agent 耗时，再决定拆不拆。

## 可复用建议

- 子 Agent 提示词沉淀成模板库，按任务类型（检索/审查/重构）各留一版；
- 结构化返回当成硬契约写进模板，不靠模型自觉；
- 全程落日志，出问题能回放每个子 Agent 的完整轨迹；
- 并发度、超时、重试次数做成配置项，别写死在提示词里。

## 总结

Subagent 的价值是隔离与并行，不是智能放大器。它适合读多写少、可拆分、可验证的任务；写场景要做好工作区隔离与合并。工程要点就三条：**任务封闭、返回结构化、产物可核查**。先小规模跑通再放大并发，比一开始就追求"十路并行"踏实得多。
