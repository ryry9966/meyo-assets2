## 背景

LLM 本身无状态，每次会话都从零开始。用户上个月明明说过“提交信息用中文、缩进用 4 空格”，今天助手照样再问一遍。在 OpenClaw 这类可接 MCP 工具、跑长任务的框架里，记忆不是锦上添花：记不住偏好的 Agent，每一步都在向用户重复索要上下文，自动化体验直接打折。

## 问题：三种常见的失败做法

1. **全塞进 system prompt**：偏好攒到几十条后 token 膨胀，还容易混入互相矛盾的旧记忆。
2. **全量对话入库 + 向量检索**：召回的多是闲聊噪声，“喜欢深色主题”这类短事实和当前 query 语义不重叠，根本召不回。
3. **只写不改**：记忆只增不删，一年后 Agent 还在坚持你早已放弃的技术栈。

本质问题：偏好记忆是结构化数据问题，不是“多存点文本”的问题。

## 做法：一张结构化记忆表 + 克制的写入管线

**1. 分层**

- 工作记忆：当前会话上下文，不落盘。
- 情景记忆：会话结束后的摘要，进向量库，用于“上次聊到哪”。
- 偏好记忆：结构化 KV，`scope / category / key / value / confidence / source / updated_at`，重点。
- 过程记忆：沉淀成可复用脚本或工作流，不进 prompt。

**2. 写入**

不在每轮实时抽取（写放大 + 幻觉偏好），而是在会话结束或任务完成时异步跑一次结构化抽取：LLM 按 JSON schema 输出候选偏好，并标记来源。用户纠正（“别用 tab"）是最高置信信号，直接覆盖旧值。

**3. 更新策略**

- 以 `(scope, category, key)` 为唯一键做 upsert，新值覆盖旧值，confidence 随时间衰减。
- 高影响变更（覆盖用户显式声明过的偏好）降级为提问确认。
- 个人偏好、项目约定、团队规范分开存，避免“我在 A 项目用 pytest"污染到 B 项目。

**4. 读取注入**

构建 prompt 时只注入任务命中的 top-N 情景记忆 + 高置信偏好，设 token 预算（比如 300）。偏好短事实用 KV 直查，别依赖向量检索。

在 OpenClaw 里我把读写封成三个 MCP 工具：`memory_search` / `memory_get` / `memory_write`，任何客户端都能复用，权限按 scope 收敛。

## 踩坑点

- **把“用户提过”当“用户偏好"**。用户转述别人的代码风格也会被抽取器当成偏好，`source` 字段必须有，推断类记忆置信度打折，注入前过滤。
- **嵌入检索对偏好失效**。“帮我写个爬虫”和“喜欢 Python 3.12"没有语义重叠，KV 直查才是对的。
- **记忆没有 TTL**。编辑器、常用目录这类环境偏好会过期，过期不删就是污染。
- **没有导出和删除入口**。记忆里迟早混进敏感信息，用户看不到也删不掉，这个系统就不可信。

## 可复用建议

- 先定 schema 再写代码，记忆表结构要版本化，留迁移空间。
- 宁可少记、靠置信度过滤，也不要全收。
- 建一个小评测集：二十条“换会话后能否召回偏好”的用例，改记忆逻辑前后各跑一遍，别凭感觉调。

## 总结

记忆系统不神秘，本质是一条带治理的数据管道：结构化存储、克制的写入、带作用域的读取、可解释可删除。先把偏好层做扎实（KV + upsert + 置信度），情景记忆只是加分项。Agent 的“懂你”，靠的是工程纪律，不是 prompt 魔法。
