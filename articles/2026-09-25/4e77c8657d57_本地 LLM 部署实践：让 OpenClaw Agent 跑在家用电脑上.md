## 背景

Agent 的日常是高频、碎片化的自动化任务：定时拉数据、整理笔记、调 MCP 工具。这类负载如果全走云端 API，一来成本随使用量线性增长，二来代码库、私人日记这类上下文放进第三方总归不踏实。于是花了一个周末，把本地模型接进 OpenClaw 跑真实任务，把过程和坑记录下来。

## 问题

动手前有三个核心疑问：

1. 家用硬件到底能跑多大的模型？
2. 用哪个推理框架部署最省心？
3. 7B 级别的模型，tool calling 能不能撑起 MCP 工具链？

## 做法

**1. 盘点硬件，显存优先。** 关键指标是显存而非内存：8GB VRAM 可跑 7B~8B 的 Q4 量化；12GB 能上 14B；32B 基本需要 24GB 显存，或 GPU+CPU 混合 offload。纯 CPU 能跑，但 agent 场景下速度会很折磨。

**2. 选推理框架。** Ollama 上手最快，一行命令拉模型，自带 OpenAI 兼容接口；追求极致性能用 llama.cpp 手调 GPU 层数；多并发场景再考虑 vLLM。家用单机，Ollama 够用。

**3. 选模型。** 优先验证 function calling 质量，其次再看榜单分数。中文环境下 Qwen 系列 7B/14B 的工具调用比较稳。量化从 Q4_K_M 起步——再往下压，工具调用掉点非常明显。

**4. 接入 OpenClaw。** 在模型配置里把 provider 指向本地端点（如 `http://127.0.0.1:11434/v1`），api_key 随意填非空值，模型名与本地注册名保持一致即可。

**5. 验证工具链。** 先只挂一个最简单的 MCP 工具（比如查时间），确认模型能输出合法的调用 JSON，再逐步加工具数量。

**6. 压测并记录基线。** 记下 tokens/s、显存峰值、长上下文下的掉速曲线，作为之后换模型时的对比依据。

## 踩坑点

- **num_ctx 默认太小。** Ollama 默认上下文只有 2K~4K，而 OpenClaw 的系统提示加 MCP 工具描述轻松超限，表现为模型"失忆"或输出截断。务必显式调到 8K 以上，注意 KV cache 会额外吃显存。
- **keep_alive 导致冷启动。** 默认几分钟无请求就卸载模型，定时任务每次都白等十几秒加载。显存够的话设为常驻。
- **小模型工具调用不稳。** 同时暴露超过五六个工具后，7B 模型容易选错工具或产出畸形 JSON。对策：精简并发暴露的工具数、把工具描述写得直白、日志里保留原始输出方便定位。
- **显存算得太满。** 模型占满显存会引发系统卡顿甚至 OOM，给系统和 KV cache 留 1~2GB 余量。

## 可复用建议

- 先用 7~8B Q4 打通全流程，再决定要不要上更大模型——实践中流程问题远比模型能力问题常见。
- 做混合路由：高频、固定格式、隐私敏感的任务走本地；复杂推理和长文档走云端 API。OpenClaw 里按任务配不同 provider 即可。
- 把工具调用失败率当核心指标，它对 agent 体验的影响远大于推理速度。
- 显存预算公式化：模型体积（Q4 约为参数量一半的 GB 数）+ KV cache + 系统占用，总和不超 90%。

## 总结

本地 LLM 已到"能用"的临界点，但不是"全能"。它适合高频、结构化、隐私敏感的任务；指望 7B 模型稳定驱动庞大的 MCP 工具链仍不现实。务实的路径是：本地模型处理确定性任务，云端兜底复杂推理，用日志和数据决定两者的边界。
