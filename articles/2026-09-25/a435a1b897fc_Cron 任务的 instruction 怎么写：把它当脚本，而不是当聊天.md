## 背景

OpenClaw 的 cron 任务本质上是**无人值守的单轮会话**：到点触发一个新 session，把 instruction 作为 prompt 喂给 agent，跑完即结束。它和聊天窗口里对话最大的区别是——没有历史上下文、没人回答 agent 的追问、结果不落到正确的地方就等于没跑。

很多人把聊天里用顺手的 prompt 直接粘进 cron，然后发现：要么每天输出一篇越来越长的"日报水文"，要么 agent 跑到一半停在等确认，要么干脆什么都没发生。

## 三种典型翻车

1. **输出去向不明**。instruction 只写"整理一下昨天的数据"，agent 整理完在 session 里自言自语，没人收到。
2. **时间语义模糊**。"昨天""今天早上"依赖 agent 自己推断，时区一偏就错位一天。
3. **空转无定义**。没有新数据时 agent 会硬凑内容——日报不能空着发，它就会编。

## 做法：六段式模板

我把 cron instruction 当成一个无 UI 的脚本头，固定六段：

```text
[目标] 一句话说清这次运行要产出什么
[来源] 点名要调用的工具/MCP 及取数范围
[规则] 判断标准，如"只报告错误数超过 3 次的服务"
[输出] 固定模板 + 硬性长度上限
[去向] 发到哪个 channel / 写到哪个文件路径
[兜底] 工具不可用或无数据时的行为：发固定短句或静默
```

几个关键点展开：

- **时间显式化**。开头写"以系统当前时间（Asia/Shanghai）为准，'昨天'指其日历日"。别让 agent 猜。
- **定义 no-op**。加一句"若一切正常，仅输出一行：'X 月 X 日：无异常'"。这行很关键，它把"空"变成合法输出，堵住了编造的动机。
- **给失败留出路**。"若某工具调用失败，重试一次；仍失败则在输出末尾标注 DEGRADED，不要中断。"否则一次网络抖动就让整趟任务白跑。
- **大段资料放文件**。instruction 里只留文件路径让 agent 去读。几千字说明塞进 cron 配置，既难维护，也会稀释核心指令。

## 踩坑点

- **追问陷阱**。instruction 里写"有疑问请问我"，cron 场景没人应答，agent 会停在那里。所有需要人确认的分支都应写成兜底规则，而不是提问。
- **重叠运行**。任务跑 10 分钟、间隔设 5 分钟，会出现两个 session 同时写同一个文件。要么拉长间隔，要么在 instruction 里加"开始前检查锁文件，存在则直接退出"。
- **工具调用不收敛**。"看看各渠道情况"这种写法会触发不可控的多轮调用和限流。来源段落点名到具体工具，范围才收得住。
- **日报膨胀**。没有长度上限的输出模板，两周后日报会比 commit 记录还长。上限写死，比如"正文不超过 15 行"。

## 可复用建议

- 把 cron instruction 当**版本化资产**：配置里留一行注释，写修改日期和原因，出问题能回溯。
- 新任务先**低频试运行**：每天一次观察三天再加密频率，比一步到位省很多排查时间。
- 写完自检一个问题：**这份说明书交给一个完全不了解来龙去脉的新同事，他能否不问任何问题就交付结果？** 能，才算合格。

## 总结

Cron instruction 的本质不是"提示词"，而是一份交给无人值守执行者的作业说明书。目标、来源、规则、输出、去向、兜底，六段写全；空转有定义，失败有出路，长度有上限。做到这三点，定时任务才能从"偶尔惊喜"变成"稳定基建"。
