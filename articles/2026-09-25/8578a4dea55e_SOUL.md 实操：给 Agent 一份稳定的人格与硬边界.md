## 背景

OpenClaw 的 Agent 每次会话基本是无状态的，所谓"性格"，完全取决于启动时注入 system prompt 的内容。很多人把人格指令散落各处：workspace 里写一段、插件描述里塞一句、聊天中临时补一条，结果就是行为漂移——今天话多，明天冷淡，换个模型判若两 Agent。

SOUL.md 就是为解决这个问题而存在的约定：放在 workspace 根目录（默认 `~/.openclaw/workspace/SOUL.md`），Agent 启动时读取，作为人格与价值观层的固定输入。它和 AGENTS.md 的分工很清楚：**SOUL.md 管"我是谁、什么不做"，AGENTS.md 管"活怎么干"**。

## 问题

没有 SOUL.md 的 Agent，常见三类毛病：

1. **边界缺失**。你让它"看下服务器日志"，它顺手把日志全文贴进聊天，里面的 token 一起曝光。
2. **风格漂移**。长会话后半段开始自作主张加 emoji、堆客套话，或反过来过度简短。
3. **多入口不一致**。手机、终端、网页分别聊，得到的像三个不同的助手。

共性是：行为规则没有单一事实来源。

## 做法

一份能长期维护的 SOUL.md，建议按这个骨架写：

```markdown
# 身份
你是 XX 的日常助理，工程背景，说话直接。

# 语气
- 默认简洁，先结论后细节
- 不用感叹号，不主动加 emoji

# 边界（硬性）
- 删除数据、付费、对外发送类操作，先确认再执行
- 不在聊天中贴完整密钥/日志原文，一律摘要化

# 升级规则
- 连续两次尝试失败就停下汇报，不绕路硬试
```

几个要点：

- **控制篇幅**。这份文件每次会话都进 context，压在 50 行以内。写得越满，单条规则权重越低。
- **正负向搭配**。"不主动加 emoji"比"不要过度热情"有效得多——能落到具体行为的规则才值得写。
- **入 git**。SOUL.md 改一行行为可能明显变化，提交历史就是你的 A/B 日志。
- **改动后跑探针**。固定几个问题（"帮我删掉这个目录""总结这段话"），每次修改后跑一遍对比回答。

## 踩坑点

- **把 SOUL.md 当安全边界**。它是软约束，模型可能违反。真正的边界要靠工具权限、MCP server 的 allowlist 和操作确认机制兜底。SOUL.md 是意愿声明，不是沙箱。
- **写成愿望清单**。"要聪明、要有同理心、要主动"没有可执行语义，模型只能随机演绎。删掉，换成具体行为。
- **和 AGENTS.md / 插件指令打架**。插件 prompt 里写"详细展开每个步骤"，SOUL.md 写"默认简洁"，行为就看模型心情。冲突规则要么删，要么在 SOUL.md 里写明例外场景。
- **换模型不复检**。为 A 模型调出的人格，换到 B 模型常走样，尤其是否定式指令。模型变更时，把 SOUL.md 当配置项一起回归。

## 可复用建议

- 模板三段式：身份 → 语气 → 硬边界 + 升级规则，20 行起步，够用再长。
- 每季度重读一次，删掉三个月没"触发"过的规则——不产生行为差异的规则就是纯 context 开销。
- 团队共用的 Agent，把 SOUL.md 和探针测试一起放进仓库。人格也是代码。

## 总结

SOUL.md 成本极低，就是一份 markdown，但它是 Agent 行为的单一事实来源。定位要摆正：它负责"塑造倾向"，不负责"强制执行"，硬边界交给权限系统。人格写进文件、入版本管理、定期修剪，你的 Agent 才不会越用越陌生。
