## 背景

Agent 跑起来之后，很多人会发现真正的调用大头不是主循环，而是拆出来的那些琐碎步骤：摘要、格式化、批量打标、二次改写。OpenClaw 的执行链路里，一个任务往往被拆成规划、工具调用、内容生成、结构化输出好几段，每一段对模型能力的要求其实差得很远。全用 GPT 这类云端强模型，账单和限速很快教做人；全用本地小模型，长链路任务质量又崩得很难看。

## 问题

路由的核心不是"哪个模型好"，而是：**哪些步骤值得花强模型的钱，哪些步骤本地就够了，失败时怎么兜底。** 常见的两个极端——一把梭云端、一把梭本地——都是没把模型能力当资源分配的结果。

## 做法

**1. 先给任务分层**，别急着写配置：

- 规划、复杂推理、跨工具决策 → 强模型（GPT 级）
- 工具调用密集、长上下文节点 → 强模型为主，谨慎下沉
- 摘要、改写、格式化、批量分类打标 → 本地模型（如 Qwen/Llama 系，经 vLLM/Ollama 起）
- 涉及敏感日志、内网数据不能出机器的 → 强制本地

**2. 在 OpenClaw 的 routing 配置里按节点角色绑模型**（示意）：

```yaml
routing:
  - match: role == "planner"
    use: cloud-strong
  - match: task in [summarize, format, tag]
    use: local-14b
fallback: cloud-strong   # 本地校验失败时升级
```

**3. 兜底链要带校验**：本地输出先过 schema 校验，不过再升级云端，同时打点记录升级率。

**4. 固定评测集回归**：拿 20–50 条真实任务，路由前后各跑一遍，对比成功率、端到端 P95、每任务成本。没有这组数，路由就是玄学。

## 踩坑点

- **本地模型 JSON 不稳**：裸 parse 必炸。上约束解码 + 重试 + schema 校验，三件套缺一不可。
- **function calling 差距比想象大**：tool-use 密集的节点别路由到本地，参数填错一个，后面整条链全歪。
- **本地 ≠ 低延迟**：消费级显卡跑长上下文，首 token 延迟可能比 API 还高。先测再切。
- **路由太碎会打断 prompt cache**：频繁换模型，缓存全失效，反而更贵更慢。
- **fallback 没熔断**：本地持续失败时，所有流量涌向云端，成本反向爆炸。设个升级率阈值告警。

## 可复用建议

1. 决策看三个维度：**上下文长度 × 结构化要求 × 出错代价**。出错代价高、结构化要求强的节点留云端，其余下沉。
2. 先粗后细：第一版全走云端拿 baseline，之后一次只下沉一类节点，跑评测再合入。
3. 监控三指标：每节点成本占比、格式校验通过率、端到端 P95。任一指标恶化，先回滚再分析。

## 总结

多模型路由不是省钱小技巧，而是把"模型能力"当成和 CPU、带宽一样的资源来分配的工程问题。OpenClaw 的节点化执行结构天然适合按角色绑模型，关键是：分层要有依据，下沉要带校验，决策要靠数据。先跑出 baseline，再小步下沉，比一次到位稳妥得多。
