## 背景

Agent 接上 MCP 和插件之后，能做的事从"聊天"变成了"执行"：跑 shell、写文件、调外部 API、发消息、动数据库。能力上来了，但很多人的权限模型还停留在"工具装了就能用"。通常是出了几次事故——误删文件、错发消息、付费 API 超预算——才回头补权限。

## 问题

实践里只有两种失败模式：

- **问得太多**：每步都找人确认，人变成橡皮图章，很快开始无脑点"允许"，确认机制形同虚设。
- **问得太少**：Agent 自作主张执行不可逆操作，等发现已经晚了。

核心矛盾在于："重要的事"没法用一句话定义，所以需要一个可执行的判断框架，而不是靠 prompt 里写一句"请谨慎操作"。

## 做法：按「可逆性 × 影响范围」分级

每接入一个工具，先做一次分类，**写进配置，不写在 prompt 里**：

- **L0 只读、本地**：读文件、搜索、查状态。自动执行。
- **L1 可逆写、工作区内**：编辑文件、git commit（可 reset）。自动执行，记日志。
- **L2 难逆、但影响封闭**：删文件、合并分支、重启服务。执行前生成"计划/预览"，批量给人过目；不紧急的排队到人在线时再审。
- **L3 外部副作用或不可逆**：发消息、付款、动生产库、删远端资源。必须单次人工确认。

判断顺序：先问可不可逆，再问影响是否出系统边界，最后看出错代价（丢时间 vs 丢钱/丢数据）。两个维度都高的，一律 L3。

落地方式：在 MCP 工具声明里加权限等级标签，执行层做 gate——L3 调用先暂停，把命令、影响文件列表、预估成本一起展示，人批准才放行。

## 踩坑点

1. **Prompt 管不住权限**。模型对"谨慎"的理解和你不一致，限制必须强制在工具/执行层，prompt 只负责解释规则。
2. **确认疲劳**。L2 也逐条弹窗，三天后用户就会全选"始终允许"，比不设防还危险。非紧急的 L2 攒一批审。
3. **dry-run 不等价**。本地操作能模拟，发消息没法 dry-run——外部副作用工具只能靠确认 gate。
4. **确认时上下文不足**。"我可以执行吗"不如"将执行 X，改动这 3 个文件，预计花费 Y"。人没信息，就等于没在审。
5. **工具粒度太粗**。一个 MCP 工具既能读又能写，没法分级，宁可包一层拆成两个工具。

## 可复用建议

- 新接 MCP server，先花十分钟给每个工具标级，再谈别的。
- 外部副作用类工具**默认拒绝**，显式开启才可用。
- 让 Agent 先输出"计划"再执行：计划是 L0（纯文本），执行才是 L1+，天然多出一个审视点。
- 全量审计日志，自动执行的操作也要记，出事能回放。
- 定期回顾审批记录：批准率接近 100% 说明分级过严，该降级；经常事后后悔说明过松。

## 总结

权限边界不是"信不信任模型"的问题，而是接口设计问题。可逆、封闭、代价小，就让它自己干；不可逆、出边界、代价大，就把住门。把判断标准固化在配置和执行层，而不是祈祷模型每次都和你想得一样。
