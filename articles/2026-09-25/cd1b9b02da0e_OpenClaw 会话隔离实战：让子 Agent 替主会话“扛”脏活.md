## 背景

OpenClaw 的主会话是长期运行的，主 agent 既是调度员又是执行者。日常对话、工具调用（读文件、跑命令、抓网页）的原始输出全都堆进同一个 context。短任务没什么问题，任务一长，上下文就被工具输出淹没。

## 问题

典型症状有三个：

- 主会话跑完一轮批量检索后，模型开始“忘事”，早前交代的约束被悄悄丢掉；
- compaction 频繁触发，压缩摘要把关键细节磨掉；
- token 成本随任务数量线性上涨，但真正有价值的决策只占很小一部分。

根因是把“调度”和“执行”放在了同一个 session 里。执行产生的中间产物——命令输出、网页原文、长文件内容——对后续决策几乎没用，却一直占着位置。

## 做法

OpenClaw 的子 agent 机制（spawn 出的独立 session）就是解这个问题的：子 agent 在自己的会话里干活，跑完后只把一段结果回传主会话。我的使用步骤：

1. **先判断该不该派发**。标准很简单：这个任务会不会产生大量工具输出？会，就派子 agent；纯决策、纯对话留在主会话。
2. **写清任务边界**。派发 prompt 里固定三件事：目标、期望的返回格式、返回长度上限，比如“200 字摘要 + 结论列表”。
3. **限制写权限**。给子 agent 独立工作目录，或明确禁止改动主工作区文件，避免文件层面的交叉污染。
4. **等结果再行动**。spawn 之后主 agent 要等回传摘要再继续，别提前给用户下结论。
5. **定期清理**。用 `/sessions` 查看活跃会话，僵尸任务及时结束；主会话过重时 `/new` 重置，长期约束放进 AGENTS.md 这类系统级配置，而不是指望会话记忆。

## 踩坑点

- **文件侧信道**：子 agent 和主会话共享 workspace 时，它改过的文件会“间接污染”主 agent 后续的判断。吃过一次亏后，我现在一律给子 agent 单独目录。
- **摘要比正文还长**：不限制返回长度，子 agent 会把半篇网页原文带回来，隔离等于白做。
- **并发太多**：同时派十个子 agent，回传交错，主 agent 排序混乱。现在控制在两三个，必要时串行。
- **把约束写进会话**：重要约束写在会话里，compaction 一压就没了，放系统级配置才稳。

## 可复用建议

- 把子 agent 的任务 prompt 做成模板，每次只换任务描述，减少临场发挥带来的不确定性。
- 主会话只保留“调度 + 决策”，把它当 manager 用，别当 worker 用。
- 每次长任务后看一眼主会话的 token 涨幅，如果涨得明显，说明派发粒度不够细，该拆的继续往下拆。

## 总结

session 隔离的本质不是省钱，而是保护主会话的决策质量。执行的脏活交给独立 session，主会话保持轻，模型才不会在几万 token 的命令输出里，丢掉你三天前交代的要求。这个模式本身不复杂，但它很大程度上决定了 OpenClaw 长期运行时，是一个助手，还是一个噪音发生器。
