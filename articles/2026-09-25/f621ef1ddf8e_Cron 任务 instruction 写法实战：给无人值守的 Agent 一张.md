## 背景

OpenClaw 的 cron 任务，本质是**定时唤醒 agent 并塞给它一段 instruction**。听起来和聊天没区别，工程上差异很大：聊天时用户在场，可以追问、纠偏；cron 触发时 agent 在无人值守状态下醒来，instruction 是它唯一的信息来源。社区里不少定时任务（早报、监控摘要、数据巡检）翻车，问题十有八九不在调度，而在那段 instruction 是从聊天场景直接复制来的。

## 问题

Cron instruction 最常见的三类失败：

1. **上下文缺失**：写了“按老规矩汇总”，但 agent 醒来时没有“老规矩”那段对话。
2. **时间歧义**：“今天的告警”是哪个时区？区间开还是闭？agent 会自己猜，猜错就是事故。
3. **无人兜底**：数据为空、工具失败时没有异常分支，agent 为了“完成任务”开始编数据，或者重试后在群里刷屏。

## 做法

我把它当成一份**值班交接单**来写，固定六个槽位：

```text
任务：每日 08:00 (Asia/Shanghai) 汇总 #ops 昨日告警。
数据源：仅通过 MCP 工具 log_query 读取告警记录，
       区间 [昨天 00:00, 今天 00:00)，本地时区。
步骤：拉取 → 按服务分组 → 取 Top3。
输出：发到 #ops；首行结论，再列不超过 5 条要点，总长 < 200 字。
异常：无告警则发"昨日无告警"；工具失败重试 2 次，
     仍失败私信管理员；禁止编造或估算数据。
禁止：不回复历史消息，不执行任何写操作。
```

六个槽位：**目标 / 数据源 / 时间口径 / 步骤 / 输出 / 异常**。写完先手动触发一次做 dry run，确认输出和渠道无误，再挂上 cron。

## 踩坑点

- **指代词是雷区**：“像昨天那样”“老位置”一律展开成绝对坐标（频道 ID、文件路径）。
- **相对时间必须钉死**：不写“今天”，写区间 + 时区；跨日任务注意开闭区间。
- **不指定输出渠道 = 石沉大海**：agent 的默认回复路径不一定是你看的地方。
- **没有幂等设计**：重试就会重复推送。instruction 里加一句“消息开头带日期戳，当日已发过则跳过”。
- **工具权限放开**：让 agent 自由取数，幻觉概率直线上升；只授权本轮任务需要的工具。
- **instruction 塞太长**：稳定的长流程沉淀成 workspace 文档或 skill，cron instruction 只留本次参数和差异。

## 可复用建议

- 六槽位模板直接抄，缺一项就是将来排障的盲区。
- 让 agent 结尾附一行执行摘要：读了什么、发了什么、有无异常，远端排障省一半时间。
- 短指令配短 cron；链路超过三步的任务先拆步骤再挂调度，不要指望一次唤醒全做完。
- instruction 改动按代码对待：改一句口径，可能改变整条推送的语义，值得一次 review。

## 总结

Cron instruction 的读者，不是一个正在和你聊天的助手，而是一个没有上下文、没人在场的值班同事。把上下文带全、把边界写死、把异常想好，它才能在你睡觉时可靠地干活。写完自问一句：如果我是凌晨三点被这段话叫醒的人，不问任何问题能把事办对吗？
