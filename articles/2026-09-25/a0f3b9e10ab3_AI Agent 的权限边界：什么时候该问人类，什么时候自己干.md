# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

给 Agent 接上 MCP 工具和插件之后，能力上限就不再取决于模型，而取决于你敢让它碰什么。OpenClaw 这类常驻本地的 Agent 尤其明显：shell、文件系统、浏览器、消息通道、定时任务全开着，它半夜也在干活。于是每个实践者都会撞上同一个问题——每一次工具调用，到底是放行，还是先问人？

## 问题

两个极端都不好用。全部询问：自动化直接失效，凌晨三点推送一条"是否继续执行？"没有任何意义。全部放行：一次幻觉或一次 prompt 注入就可能删错文件、往真实频道发消息、跑爆计费 API。真正需要的是一个可维护的边界，而不是凭手感临时调整。

## 做法：按"可逆性 × 影响范围"分四档

1. **只读、低影响**（读文件、搜索、查询）：默认放行，仅记日志。
2. **可逆写操作**（写工作目录内文件、本地 git commit）：放行 + 审计日志，事后可回滚。
3. **不可逆或外发**（push、发消息给真人、调用计费接口、删除数据）：强制确认。确认消息必须带上下文：打算执行什么、为什么、影响范围是什么。
4. **绝对禁止**：维护一份 deny 清单，模型说得再有道理也不放，比如递归强删、清空数据库、修改 Agent 自身配置。

落到工程上是三件事：

- 工具与参数白名单按前缀、路径、收件人收敛；
- 高频低风险操作逐步沉淀进白名单，低频高危一律走审批；
- 所有放行动作写入审计日志：时间、工具、参数摘要、结果、是否有人工介入。

## 踩坑点

- **确认疲劳**：什么都问等于什么都不问，人很快会闭眼点"允许"，边界形同虚设。宁可默认权限更紧，也别滥发确认。
- **脱离上下文的确认**：定时任务半夜问"要继续吗？"人根本无法判断。要么把该任务配进免确认的白名单路径，要么攒到早上批量审。
- **前缀通配漏洞**：允许 `git *` 就等于允许 `git push --force`。deny 规则必须先于 allow 匹配。
- **把"问人"当兜底**：模型一不确定就抛确认，制造大量垃圾审批，还掩盖了提示词和工具描述本身的问题。先修 prompt，再谈权限。
- **只拦截不记录**：没有日志就无法复盘哪次放行出了问题，边界永远调不准。

## 可复用建议

- 新工具接入先跑一周只读或 dry-run，观察它实际会传什么参数，再定权限档位。
- 每条 deny/confirm 规则写清理由，半年后的自己要能看懂。
- 每月抽一遍审计日志：被拦的和被放行的各抽样看看，误放行的收紧，不该打扰人的放宽。
- 对外发动作单独加"收件人白名单"，往往比拦命令更有效。
- 分清沙箱和权限：沙箱限制爆炸半径，权限边界决定它能不能走到危险动作，两者都要有。

## 总结

权限边界不是一次配完的安全项，而是随 Agent 能力一起增长的运营项。判断标准其实只有一条：**这个动作做错了，代价由谁承担，能不能撤销。**能撤销的，放心让它自己干；不能撤销的，必须让一个带着上下文的人来拍板。把这条想清楚，剩下的只是把它翻译成规则和日志的体力活。
