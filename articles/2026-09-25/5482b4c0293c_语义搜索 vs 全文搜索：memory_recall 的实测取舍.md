## 背景

给 Agent 做长期记忆时，`memory_recall` 是决定"它到底记不记得"的那一层。OpenClaw 生态里常见两条实现路线：向量语义检索（embedding + 近似最近邻）和全文检索（BM25 / FTS5）。社区里"语义完胜关键词"的说法很多，但我实际跑下来，结论没那么一边倒。

## 问题

我踩到的两个典型失败场景：

1. Agent 明确记录过某个部署脚本的路径和一段报错码，第二天问"那个 502 是怎么回事"，语义通道召回了一堆主题相近的旧笔记，真正那条排在第五。
2. 反过来，纯全文索引搜不到"换了说法"的问题——用户问"上次登录超时怎么解决的"，而记忆里写的是 auth timeout。

一个是精确 token 锚不住，一个是措辞泛化不了。两条路各有死穴。

## 做法

我没直接信任何一方的宣传，而是用真实数据做了小评测（约 120 条记忆、40 条从历史会话里抽的回溯类问题，人工标注应命中条目）：

1. **分块**：以"一条决策/一个事实"为粒度切块，50–200 token，保留来源和时间戳。
2. **双索引**：SQLite FTS5 做全文索引；本地中文友好的小型 embedding 模型做向量索引。
3. **分别测**：Hit@3 和 MRR。语义通道在"换说法"类问题上确实好；凡是查询含错误码、路径、命令片段的，全文通道几乎全中，语义反而引入噪声。
4. **混合**：两路各取 top-k，用 RRF（倒数排名融合）合并。整体命中明显优于单通道最好成绩。样本小，具体数字不放出来误导人，但方向明确。

## 踩坑点

- **FTS5 默认分词器不适合中文**。unicode61 对中文基本是整句切分，必须换 jieba 或 ICU tokenizer，否则中文全文检索约等于不可用。这是最常见的隐形坑。
- **小模型对标识符不敏感**。embedding 容易被高频词带偏，错误码、哈希这类 token 权重很难学到位，这正是关键词通道存在的理由。
- **记忆有强时间属性**，这是和普通 RAG 的本质区别。三个月前被推翻的旧方案与新方案并存时，要做 recency 衰减，否则 Agent 会拿过期结论作答。
- **chunk 边界切开因果**。"原因"和"结论"分到两块，只命中一半，上下文反而有误导性。切块宁可重叠。
- **不做召回日志就永远不知道 miss**。记下 query、召回结果、用户是否采纳，这是唯一能持续调优的依据。

## 可复用建议

1. 默认混合检索，不要二选一；RRF 融合够用，不必先上 reranker。
2. 查询中检测到错误码格式、路径、命令片段时，给关键词通道加权。
3. 原始记忆文本永远保留，索引只是派生物，随时可重建、可换 embedding 模型。
4. 排序加时间衰减因子。
5. 每周翻一次召回 miss 日志，比任何 benchmark 都真实。

## 总结

语义搜索和全文搜索覆盖的是两套不同的失败模式：前者锚不住精确 token，后者泛化不了措辞。memory_recall 场景下，混合检索 + 时间加权 + 可重建索引，是我目前验证过的最务实组合。别追求一个"最优检索器"，先把自己场景的 miss 日志攒起来，数据会告诉你下一步往哪调。
