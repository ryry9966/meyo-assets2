# LLM 输出解析的防御性编程：JSON 标签格式混合处理

## 背景

做 Agent / MCP 工具链时，最常见的契约是：让模型按约定输出 JSON，下游插件解析后驱动流程。理想情况下 prompt 写清楚格式就够了，但实践中同一个 prompt、同一个模型，输出的"JSON"会有多种形态：

- ` ```json ` 围栏代码块
- `<json>...</json>`、`<output>...</output>` 之类的自造标签
- 裸 JSON，前后带解释性文字
- 带尾逗号、单引号、注释的"近似 JSON"

尤其是多模型路由、模型升级、温度不为零的场景，输出形态会持续漂移。解析层必须按防御性编程来写。

## 问题

典型错误做法是 `response.split("```json")[1].split("```")[0]`，或者无脑正则取第一个 `{` 到最后一个 `}`。前者在模型某次不套围栏时直接抛异常；后者遇到字符串里含 `}` 或嵌套对象时截取错误。更隐蔽的是：单次测试通过，长跑几百轮后偶发解析失败，整条自动化链路静默中断。

## 做法：分层抽取 + 规范化 + 校验

我目前固定用一套四层管线，按序尝试，命中即停：

1. **围栏层**：匹配 ` ```json ` / ` ``` ` 代码块。用非贪婪匹配，且围栏内部可能还有嵌套反引号，按行扫描定位围栏起止比整段正则稳。
2. **标签层**：处理 `<json>`、`<answer>` 等约定标签。标签名做成可配置列表，不同模型偏好不同。
3. **括号层**：兜底方案。找第一个 `{`（或 `[`），用计数器做括号配对扫描，维护 `in_string` 状态跳过字符串字面量内部的括号（遇转义符翻状态）。这层最容易写错，别用正则。
4. **修复层**：以上都失败，换 json5 / json_repair 之类的宽容解析器，处理尾逗号、单引号、注释。

解析成功不等于结束。第三步用 pydantic（或 zod）做 schema 校验：字段齐不齐、类型对不对、枚举合法不合法。校验失败进入有界重试——把原始输出和报错回喂给模型，要求"只输出修复后的 JSON"，重试上限设 2 次。

最后，无论成败都把原始输出落盘（带模型名、prompt 版本、时间戳）。这些脏样本是后续改进抽取器和 prompt 的最好语料。

## 踩坑点

- **字符串内嵌围栏**：让模型"输出一段说明 + JSON"时，JSON 字段的值里可能包含 ` ``` `，按围栏切分会切错。按行状态机扫描更可靠。
- **零宽字符 / BOM**：部分输出开头带 U+FEFF 或零宽空格，`json.loads` 会静默失败。解析前统一清理不可见字符。
- **中文引号**：模型偶尔把 `"` 写成全角引号，肉眼难察觉，排查时在落盘日志里发现过好几次。
- **流式输出**：流式拿到的是残缺 JSON，别边流边解析，等结束后走完整管线；确需增量，用支持 partial parse 的库。
- **修复重试要加预算**：无上限重试会把偶发坏输出放大成死循环加账单。

## 可复用建议

- 抽取器写成独立纯函数，配一个"脏输出语料集"做单测：围栏、标签、裸 JSON、脏 JSON、嵌套围栏各放几条真实样本，每次换模型跑一遍回归。
- 抽取顺序"围栏 → 标签 → 括号 → 修复"是通用的，标签清单和修复策略做成配置。
- 监控解析失败率而不只看任务成功率，失败率突增往往先于模型行为变化被发现。

## 总结

LLM 的结构化输出本质上是"君子协定"，解析层要按最坏情况设计：假设格式会漂移、括号会嵌套、字符会异常。分层抽取 + schema 校验 + 有界修复 + 样本沉淀，四件事都不复杂，但能把你自动化链路里最脆的一环补结实。
