## 背景

大多数人对 Agent 的用法仍是"问答式"：你发消息，它回复，然后静默。但 OpenClaw 里的 Agent 是常驻进程，它本来就有能力在你没开口时干活。`HEARTBEAT.md` 就是这个能力的入口：Agent 每隔一段固定时间被唤醒一次，读取工作区里的 `HEARTBEAT.md`，有活就干，没活就保持安静。

## 问题

没有心跳机制的 Agent 有两个明显局限：

1. **价值依赖你的记忆力。** 日报、异常巡检、定时提醒这类事，恰恰是你最容易忘记让 Agent 做的。
2. **主动逻辑被迫外溢。** 你不得不另写 cron 脚本、单独的通知机器人，Agent 退化成"会聊天的接口"，自动化逻辑散落在两套体系里，难维护、难审计。

我们需要一个声明式、可版本管理的"常备指令"清单，让 Agent 自己周期性执行。

## 做法

**1. 建文件。** 在 Agent 工作区（默认 `~/.openclaw/workspace/`）下创建 `HEARTBEAT.md`，直接用 Markdown 写任务，检查清单风格。

**2. 配节奏。** 心跳间隔默认约 30 分钟，可通过 `HEARTBEAT_INTERVAL`（毫秒）或配置文件调整。巡检类任务 15–30 分钟足够；别贪快，每次唤醒都是一次真实的模型调用。

**3. 写任务的三条原则：**

- **条件明确**：不写"帮我看看服务"，写"调用 status 工具检查所有容器，仅在有非 running 状态时报告"。
- **安静优先**：每条任务都应包含"无事发生时不要发消息"。默认行为就是：没有值得报告的内容，Agent 只回一个心跳确认，不打扰任何频道。
- **带时间窗**：Agent 对时间没有可靠直觉，"每天早上"要写成"用时间工具确认当前在 08:00–09:00 之间，且今天尚未执行"。

**4. 用状态文件防重复。** 约定一个 `STATE.md`，要求 Agent 执行前先读、执行后写入时间戳。会话上下文可能重置，文件不会。

## 踩坑点

- **成本**：间隔太短、文件太长，每次心跳都是一次完整调用。`HEARTBEAT.md` 控制在一屏以内，做完的任务及时删掉。
- **频道轰炸**：含糊的指令（"持续关注 XX"）会让它每次都汇报。补救：加去重规则——"仅当与上次报告状态不同时才发消息"。
- **心跳不是 cron**：它只保证"至多间隔 N 分钟执行一次"，不保证整点触发。精确定时用系统 cron 给 Agent 发一条消息更可靠。
- **写操作先观察**：只读任务先跑几天，确认判断质量，再放开重启、发通知这类动作。一个判断错误的"自动修复"比没有自动化更糟。

## 可复用建议

- 把 `HEARTBEAT.md` 当 runbook-as-code：分「Daily / Watch / 静默规则」三段，纳入 git，定期评审，每条任务附一句"为什么"。
- 心跳质量的上限取决于工具面：先把需要的 MCP 工具注册好、权限收敛好，再写任务。
- 从一个低风险只读任务起步，观察两三个心跳周期，再逐步加任务。宁可清单短，不要清单噪。

## 总结

`HEARTBEAT.md` 的价值不在"自动化"这个词，而在两件事：**声明式的常备指令**，以及**克制**——无事不出声。把清单写小、写明确、保持幂等，Agent 就能从一台问答机器，变成一个安静的值班员。
