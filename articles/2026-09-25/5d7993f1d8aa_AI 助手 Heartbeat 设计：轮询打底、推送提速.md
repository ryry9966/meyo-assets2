## 背景

OpenClaw 这类常驻 Agent 绕不开一个问题：它不能只在被呼叫时才活着。定时提醒、日历触发、记忆整理、插件任务扫描，都要求它能周期性"醒来"。通用做法就两种：**轮询**（heartbeat 定时器，每隔 N 分钟自己醒一次检查状态）和**推送**（外部事件经 webhook / 消息队列直接触发一次运行）。

OpenClaw 的默认心跳是典型的轮询式：到点醒来、检查 HEARTBEAT.md 有无待办，没有就继续睡。简单可靠，但一旦任务多了、延迟要求高了，就得认真设计。

## 问题

轮询的难处在间隔：设 5 分钟，响应快，但一天几百次唤醒，token 开销和噪音都可观；设 2 小时，省钱，但"10 分钟后提醒我"直接变成废任务。

推送的难处在工程：需要公网可达的入口、可靠的投递与重试，Agent 重启期间的消息不能丢；而且推送通道一旦静默故障，没人会发现——大家都默认"有事它会叫我"。

实践中最常翻车的场景：两条链路命中同一个事件，任务被执行两次。

## 做法

我们的方案是混合式：**轮询做骨架，推送做加速**。

1. **事件分级**：分钟级（提醒、用户消息）走推送；小时级（日报、扫描）走心跳；天级（归档、整理）挂 cron 语义的心跳。
2. **心跳瘦身**：唤醒时不加载完整上下文，只带轻量任务清单和状态摘要；先用确定性代码判断有无到期任务，没有就跳过模型调用——这一步能砍掉九成以上的无效唤醒成本。
3. **推送落盘**：事件先进持久化队列再触发 Agent，进程重启后可重放，不依赖 Agent 在线。
4. **去重幂等**：事件带唯一 ID，处理器幂等，心跳与推送撞车时靠 ID 合并。
5. **心跳兼做健康检查**：每次心跳顺带探测推送通道是否健康，通道异常就临时缩短心跳间隔兜底——相当于给推送加了"死人开关"。
6. **可观测**：记录每次唤醒的来源、单次 token、事件到动作的延迟，否则无从调参。

## 踩坑点

- **唤醒 prompt 太肥**：早期心跳把完整对话历史带上，一周烧掉的 token 比正常使用还多。
- **让模型自由发挥**：心跳问模型"现在有什么要做的吗"，它真的会编任务出来。判定逻辑必须确定性，模型只负责执行已判定的事。
- **多插件各注册 timer**：六套定时器凌晨集中唤醒直接撞车。应统一到一个调度器，并加随机抖动。
- **只盯推送日志**：没报错不等于事件进来了，入队量要和触发源对账。

## 可复用建议

- 心跳是事实来源，推送只是延迟优化。删掉推送系统仍能跑（只是慢），这个架构才算稳。
- 去重和幂等从第一天就做，事后补的代价大得多。
- 盯三个指标就够：日均唤醒次数、单次唤醒 token、事件到动作 p95 延迟。
- 心跳间隔按插件独立配置，别全局一刀切。

## 总结

轮询买的是简单与可靠，推送买的是低延迟与空闲时的零成本；纯轮询贵，纯推送脆。站得住的形态是：持久化队列在下面兜底，心跳作为主干保证"最终一定会被处理"，推送作为快路径把分钟级事件做到秒级响应。先让轮询正确，再让推送变快。
