## 背景

RSS 没死，只是被算法推荐挤到了角落。对工程用户来说它依然是噪音最低的信息获取方式：格式标准、无干预、看什么完全由自己决定。问题在于信源一多，根本读不过来。

我的思路是把"收集"和"阅读"拆开：管线负责抓取、去重、摘要、打分，人只消费最后产出的每日摘要。整条管线跑在 OpenClaw 的定时任务上，LLM 调用封装成一个 MCP 工具，定时脚本和对话里的 agent 都能复用。

## 问题

直接上手会遇到三个核心问题：

1. 多数 RSS 只有标题和截断摘要，正文拿不到；
2. 信源一多，token 成本和推送噪音同时失控；
3. 同一事件被多个信源重复报道，摘要看三遍没有意义。

## 做法

管线分四段，各自独立，一段挂了不阻塞其他段：

1. **抓取**：cron 每 30 分钟拉一次 feed 列表。没有 RSS 的站点用 RSSHub 转，建议自建实例加缓存。抓到后以 guid + 规范化 URL 写入 SQLite，入库即去重。
2. **正文抽取**：feed 内容少于 200 字就标记需要全文，用 trafilatura 之类做 readability 抽取，结果本地缓存，避免重复抓。
3. **摘要与打分**：同批条目合并进一次 LLM 调用，要求输出固定 JSON：一行摘要、3 个要点、兴趣相关度 0–10、是否建议读原文。先用便宜模型全量打分，相关度 ≥ 7 的才用强模型出详细摘要——两段式是控制成本的关键。
4. **产出**：默认不实时推送。每天固定时间生成日报，按分数排序，附原文链接；只有分数 ≥ 9 的条目走即时通知。

## 踩坑点

- **正文抽取是全管线最脆弱的一环**。有的站点反爬，有的正文在 JS 里渲染，抽出来是空壳。处理方式：抽取失败就降级用 feed 自带摘要，并在摘要 prompt 里写明"信息不足时只做标题级概括，不要编造细节"。
- **合并摘要条目间会互相污染**。一批塞 20 条以上质量明显下降，实测 8–10 条一批比较稳。
- **去重不能只靠 URL**。同一篇文章会带着不同 UTM 参数被多个 feed 重复提交，先做规范化（去 query、统一 https）能解决大半，剩下的靠标题分词算相似度兜底。
- 一开始做了实时推送，两天后通知疲劳，重要信息反而被淹没。改成"日报 + 高分即时"后信噪比立刻回来。
- **务必记录每次调用的 token 消耗**。有一周某信源日更量翻倍，成本跟着翻倍，没日志根本发现不了。

## 可复用建议

- 中间数据全部落库，保留原始 feed 条目。摘要 prompt 改版后可以全量重跑，不用等新数据。
- 打分 prompt 里放一份你当前关注方向的画像（几行字即可），分数才有区分度，画像每两周更新一次。
- 先接 5–10 个信源跑一周，调好阈值再扩。一上来接 50 个 feed，只会得到一份没人看的日报。
- 摘要能力封装成 MCP 工具的额外好处：除了管线定时调用，平时在对话里也能让 agent 对任意链接按同样格式出摘要。

## 总结

这条管线没有任何黑科技，本质是 cron + 抓取脚本 + SQLite + 两次 LLM 调用。真正有价值的是两个设计决策：**收集与阅读分离**，以及**两段式的成本控制**。它不追求让你看得更多，而是保证值得看的不会被漏掉——省下来的时间，留给真正需要精读的那几篇。
