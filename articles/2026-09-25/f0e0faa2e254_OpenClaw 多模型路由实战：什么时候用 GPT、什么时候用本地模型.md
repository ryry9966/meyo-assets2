## 背景

OpenClaw 的一个 Agent 会话里往往混杂多种任务：意图识别、工具调用规划、长文总结、代码补丁、隐私数据处理。全部走云端旗舰模型，成本和延迟都吃不消，敏感数据也出不了内网；全部压到本地模型，复杂规划和结构化输出又经常翻车。多模型路由本质上是一个工程分类问题，而不是"哪个模型更强"的问题。

## 问题

我们的自动化流水线经历过两个极端：早期所有 skill 都绑云端旗舰模型，一个月 token 账单里七成花在"把 JSON 重新格式化"这类机械活上；后来为省钱整体切到本地 7B/14B，结果工具调用的参数生成错误率明显上升，MCP 工具链经常因为一个字段格式不对而中断。结论很直接：任务难度是长尾分布的，模型也应该分层。

## 做法

1. **给任务分级**。按"结构化输出要求 × 推理深度"划三档：
   - A 档：复杂规划、多步工具编排、代码生成 → 云端旗舰模型
   - B 档：摘要、翻译、文案润色 → 本地中档模型（14B~32B）
   - C 档：格式转换、字段抽取、简单分类 → 本地小模型（7B 级）
2. **档位集中声明**。skill 只声明"需要哪一档"，模型名在配置里统一映射，换模型不动业务代码。
3. **加 fallback 链**。默认方向：本地优先，校验不过升级云端；对隐私敏感数据源反过来，并在路由层加数据分级门禁，带敏感标记的内容禁止外发。
4. **结构化输出必须过 schema 校验**，失败后先重试再升级，不要裸信本地模型的 JSON。
5. **打点**。每步记录：用了哪个模型、token 消耗、校验失败次数、是否触发升级。跑两周就有调参依据。

## 踩坑点

- 本地模型 tool calling 的弱项在"参数拟合"而不是"选工具"：工具选得对，参数里日期、枚举值乱写。加 enum 约束和事后校验能挡掉大半。
- 上下文长度错觉：本地模型标称 32K，但长 prompt 的首 token 延迟明显变差，长记忆摘要场景反而比云端慢。
- fallback 风暴：本地连续失败自动升级云端，如果上游 MCP 工具本身挂了，会把故障放大成账单事故。升级要有次数上限和熔断。
- 换本地模型时别顺手换 embedding 模型，向量记忆库会整体失效，需要重建索引。
- 路由不该是静态的：同样是"总结"，输入 500 字和 50K 字该走不同档位，按输入规模二次分流很划算。

## 可复用建议

- 两档起步（云端旗舰做 planner + 本地小模型做格式化和扩展），跑通打点后再细分三档。
- 把"模型选错"当成一类可观测的故障，而不是调参玄学。
- skill 与模型解耦，档位声明收敛到一处。
- 数据分级门禁放路由层，不依赖每个 skill 自觉。

## 总结

多模型路由的价值不在省那点 token 钱，而在于让 Agent 的每一步都在合适的能力档位上执行：复杂的事交给云端，机械的事留在本地，敏感的事有门禁。先用打点数据看清任务分布，再动手分层，比拍脑袋选模型靠谱得多。
