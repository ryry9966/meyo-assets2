## 背景

我们的 OpenClaw agent 跑了三个多月，memory 目录攒了 400 多条笔记：部署记录、踩坑日志、团队偏好。`memory_recall` 这个 MCP 工具支持两种检索模式——语义搜索（走 embedding）和全文搜索（关键词匹配）。之前一直默认语义，直到有次让它回忆某个报错码的处理办法，翻遍了没召回，而那条笔记明明写在那里。

## 问题

单看任何一种检索都有盲区：

- **语义搜索**：能把“上线后接口偶发 502”和“nginx upstream timeout”关联上，但对精确 token（错误码、命令名、版本号）经常召回一堆“语义相近但不对”的笔记。
- **全文搜索**：精确匹配强，但换个说法就抓瞎——搜“记忆丢失”，召不回写着“上下文遗忘”的那条。

## 做法

写了个简单脚本做对照测试：

1. 从 agent 历史会话里挑 60 条“确实有对应笔记”的问题，人工标注目标笔记 ID。
2. 两种模式分别跑 recall，取 top5，统计命中率和平均排名。
3. 结果：语义命中 41/60，全文 33/60，**两者并集 52/60**——互补性非常明显。
4. 错例分析：语义丢的 19 条里 14 条含精确标识符；全文丢的 27 条里 21 条是换了措辞的提问。

于是把 `memory_recall` 改成混合策略：两路各取 top8，用 RRF（倒数排名融合）合并，再加时间衰减。伪配置大致是：

```yaml
recall:
  semantic: { top_k: 8, model: bge-m3 }
  fulltext: { top_k: 8, tokenizer: jieba }
  fusion: rrf_k60
  recency_decay: 0.98
```

改完重跑：命中 53/60，top3 内命中率从 61% 提到 78%。

## 踩坑点

- **中文分词**：全文检索默认分词会把“上下文遗忘”切成碎词，召回率骤降，换 jieba 后才正常。
- **短文本 embedding**：单行错误码这种笔记，向量几乎没有区分度，必须靠全文兜底。
- **RRF 后旧笔记上浮**：不处理的话三个月前的内容老被顶到前排，加时间衰减才稳定。
- **别忽视 metadata 过滤**：先按项目/时间过滤再检索，比单纯加大 top_k 有效得多。

## 可复用建议

- 查询含错误码、命令、路径、版本号 → **全文优先**。
- 描述性、换了措辞的查询 → **语义优先**。
- 拿不准就用**混合 + RRF**，成本只多一路检索，收益稳定。
- 定期用真实会话构建小评测集，改检索参数后回归一遍，别凭感觉调。

## 总结

这不是“哪个更好”的问题，而是覆盖面不同的问题：语义搜索解决“换了说法还能找到”，全文搜索解决“精确标识符必命中”。生产环境的 `memory_recall` 最好两条腿走路。评测集比直觉可靠——60 条就够了。
