## 背景

大多数时候我们用 Agent 是拉式的：想起来 → 打开会话 → 提问 → 得到答案 → 关掉。Agent 在两次对话之间是完全静止的。OpenClaw 提供了一个很轻的机制改变这一点：**心跳（heartbeat）**。Gateway 按固定间隔（默认 30 分钟）向 agent 发一条系统级触发，agent 被要求先读工作区里的 `HEARTBEAT.md`，有事就做，没事就回 `NO_REPLY` 保持沉默（这条不会转发到频道）。本质上，它是一份用自然语言写的 crontab，执行者是带工具和 MCP 的 agent。

## 问题

光靠会话式交互，有三类事天然做不了：

- **时间敏感型**：每天早上汇总日程、盯一个价格或库存变动；
- **巡检型**：磁盘水位、进程存活、日志里的 ERROR——你不问，它就永远不说；
- **粘合型**：定时轮询某个 MCP 数据源，发现差异再决定要不要通知你。

传统做法是 cron + 脚本 + 通知通道，逻辑散落各处。heartbeat 的价值在于把"什么时候查"和"查什么"收拢进一个文件，并直接复用 agent 已有的工具链。

## 做法

1. 在工作区（默认 `~/.openclaw/workspace`）创建 `HEARTBEAT.md`。文件存在心跳才生效，删掉或清空即关闭。
2. 用 checklist 风格写任务，每条尽量小、可判定：

```markdown
# Heartbeat

- 每天 8 点后第一次心跳：汇总今日日程，发到主会话。
- 检查 ~/.openclaw/logs/ 下今天是否有 ERROR，有则摘录最近一条。
- 磁盘使用超过 90% 时提醒我。
- 其余情况一律回复 NO_REPLY。
```

3. 调频率：`openclaw.json` 里 `agents.defaults.heartbeat.intervalSec` 可改间隔。巡检类 30 分钟够用，别一上来就压到分钟级。
4. 跑两三个周期后，直接在会话里问 agent"上次心跳做了什么、为什么"，根据回答修订条目。

## 踩坑点

- **token 成本**：每次心跳都是一次完整模型调用（含系统提示与工具定义）。默认 30 分钟一天 48 次，条目堆多了很烧钱。
- **条目太模糊**："帮我盯着邮件"会让 agent 每个周期全量拉邮件。改成可判定的条件："发现某发件人的未读邮件时通知"。
- **忘写 NO_REPLY 兜底**：没有兜底句，部分模型没事干时也会往频道输出闲聊，体验极差。
- **心跳里跑重活**：长工具调用会占住会话、挤占正常交互。心跳只做"发现 + 通知"，别做"发现 + 全量处理"。
- **时间感知**：agent 对当前时间不一定准，涉及"每天 X 点"的任务，让它先查系统时间再判断。

## 可复用建议

- 把 `HEARTBEAT.md` 当 crontab 对待：进 git、写注释，一次只加一条，稳定后再加下一条。
- 区分"检查类"与"动作类"：检查类放心放心跳里，动作类让 agent 产出待办交你确认，避免无人值守执行写操作。
- 有 MCP 的话，心跳是发挥它价值的最佳场景——定时拉数据源做 diff，才谈得上"主动"。
- 给心跳输出单独留一个日志文件或频道，回溯问题时不翻主会话。

## 总结

`HEARTBEAT.md` 没有任何黑魔法：定时触发 + 一份自然语言任务清单 + 一个沉默协议。它的工程价值在于用极小的配置面，把 agent 从被动应答器变成有节奏的值守进程。建议从一两条巡检任务起步，控制频率，先让它安静跑一周，再逐步加码。
