## 背景

绝大多数助手是被动的：你发消息，它回复。但真实工作流里大量任务是时间或事件驱动的——CI 挂了、会议快开始还没材料、依赖包发了新版本。OpenClaw 本身有定时任务、插件体系和 MCP 工具链，做 proactive 的硬件条件齐了，缺的不是能力，而是一套“什么时候该主动”的工程约定。

## 问题

自己动手做下来，proactive 有两个典型失败模式：一是永远不触发（规则写死、上下文缺失）；二是天天打扰你（每个心跳周期都推一条）。还有更危险的第三种：agent 自己判断“应该做”，就直接执行了写操作。所以核心问题不是“怎么让它主动”，而是“主动到什么程度、由谁授权”。

## 做法

我的方案分四步，全部落成配置，而不是散落在自由 prompt 里：

1. **事件源接入**。cron 心跳（每 15 分钟）+ webhook 插件（CI、日历、邮件）作为触发源，统一封装成一个 MCP server，对外只暴露 `list_events` 和 `get_event_detail` 两个工具。
2. **触发规则**。规则用 YAML 声明：监听什么事件、满足什么条件、组装哪些上下文。例如“main 分支 CI 失败，且最近一次 commit 是我的”→ 触发。条件判定用规则引擎做，不进大模型，省 token 且行为可预期。
3. **上下文组装**。命中规则后 agent 才开始干活：通过 MCP 拉取失败日志、相关 diff 和 issue，产出一段不超过 10 行的 brief。
4. **行动分级**。L0 只推送通知；L1 生成草稿（PR 评论、邮件回复）等你确认；L2 自动执行，仅限白名单内可逆且幂等的操作（比如重跑 flaky CI）。L2 上线前先跑两周 dry-run。

## 踩坑点

- **心跳喂全量上下文**：每个周期都把仓库状态塞给模型，一天烧的 token 比正常对话还多。改成心跳只做规则匹配，命中才组装上下文，成本降了一个量级。
- **去重 key 不稳**：一开始用时间戳做去重，同一事件每 15 分钟重复推送。换成内容 hash（repo + branch + run_id）才彻底解决。
- **时区坑**：静默时段配置和服务器时区不一致，凌晨三点被推送吵醒。现在所有时间统一存 UTC，只在展示层转换。
- **L1 越权**：agent 偶尔会把“建议”直接写进 PR 评论发出去。后来在系统提示和工具权限两层做限制，发布类工具默认不可调用，必须携带显式确认 token 才放行。

## 可复用建议

- proactive 规则当配置管理，走 code review，不要散落在对话记录里。
- 给主动行为设“预算”：每日推送上限、每类事件冷却时间，超限就并入每日摘要。
- 保留完整审计日志：什么事件、命中哪条规则、执行了什么动作、谁确认的。出问题能回放。
- 从 L0 起步，跑两周看误报率，再决定哪些规则升到 L1/L2。

## 总结

Proactive 的价值不在“做了更多事”，而在“在对的时机、以对的粒度出现”。事件驱动触发 + 规则化判定 + 分级授权 + 预算与审计，这套组合让主动变得可控。它不会让 agent 更聪明，但会让它更可靠——而可靠，才是你敢把它接进日常工作流的前提。
