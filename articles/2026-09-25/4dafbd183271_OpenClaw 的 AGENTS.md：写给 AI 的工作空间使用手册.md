## 背景

OpenClaw 的 agent 不只是"一个会聊天的模型"，它有一个自己的工作空间（workspace）。每次会话启动，OpenClaw 会把工作空间里的几个固定文件注入给模型：`SOUL.md`、`TOOLS.md`、`AGENTS.md`、`MEMORY.md` 等。其中 AGENTS.md 的角色最特殊——它不管人格，也不存记忆，而是"操作手册"：告诉 agent 这个空间怎么用、日常流程怎么走、哪些事不能做。

三者粗略分工：SOUL.md 管"我是谁"，TOOLS.md 管"我能用什么"，AGENTS.md 管"我该怎么干活"。

## 没写好会发生什么

实践里常见的几种失控：

1. Agent 把生成的文件随手扔在 workspace 根目录，几次之后目录结构不可辨认；
2. 同类任务每次执行流程都不一样，有时先备份再改，有时直接改；
3. 对"哪些目录只读"没有概念，偶尔越界动配置；
4. 团队共用一套部署，各人的 agent 行为风格完全不同，排查时无从下手。

本质是同一件事：隐性约定没有显式化。人会从 README 里猜规范，agent 不猜，它只执行被写下来的规则。

## 我的写法：五个区块

我的 AGENTS.md 目前约 150 行，固定分五块：

**1. 身份与边界**：两三句说明角色（如"个人助理，负责日记、消息、日常自动化"），加硬性边界：不改 gateway 配置、不动 `.ssh`、不在 workspace 外写文件。

**2. 工作空间地图**：逐目录说明用途和读写权限，例如 `memory/` 只追加、`projects/` 可读写、`skills/` 改前先读、`media/` 只读。

**3. 常规流程**：高频任务写成编号步骤，如"收到'记一下'：确认日期 → 写入当日 memory 文件 → 回复确认"。每条必须是可逐步照做的操作序列，不是描述性散文。

**4. 禁止项**：明确清单——不执行删除类命令、不把密钥写进任何文件、外发消息前先复述收件人。宁可写死，不要写"尽量"。

**5. 输出规范**：回复语言、格式偏好、哪些场景必须反问确认。

## 踩坑点

- **写太长**。早期塞了 400 多行，能明显感到 agent 对中段指令执行变敷衍。现在控制在 200 行内，细节下沉到 TOOLS.md 或 skills 脚本。
- **写成散文**。"希望你保持严谨"没有执行意义，改成"改配置前必须先 `cp` 一份 `.bak`"。
- **把记忆写进手册**。AGENTS.md 是稳定规则，易变事实放 MEMORY.md。混入"目前在做的项目是 XX"，一周后就是误导。
- **不进版本管理**。放 git 里，agent 行为异常时 diff 一下，经常能定位到某次改动。
- **路径模糊**。"放在合适的目录"等于没写，用 workspace 相对路径。

## 可复用建议

1. 把 AGENTS.md 当代码 review：每次改动后让 agent 实跑一遍高频任务验证；
2. 指令带可验证的完成标志，如"完成后 `ls` 确认文件存在"；
3. 三层拆分：稳定规则进 AGENTS.md，人格进 SOUL.md，工具细节进 TOOLS.md，事实进 MEMORY.md；
4. 从最小版本起步，遇到一次失控补一条规则，比一次写全更贴近真实需求。

## 总结

AGENTS.md 的价值不在写得多，而在每条都真的会被执行。它本质上是把你对 agent 的运维经验固化成文本——越贴近真实事故，agent 越稳。如果你还没维护这份文件，建议从"工作空间地图 + 三条禁止项"开始，一周后你会回来补下一条。
