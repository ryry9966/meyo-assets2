## 背景

OpenClaw 的 agent 有一个固定的工作空间（workspace），里面除了记忆文件和身份配置，还有一个核心文件：`AGENTS.md`。它在每次会话建立时被注入上下文，相当于 agent 进场前必读的操作规程。你可以把它理解成：写给 AI 的 README。

## 问题

很多人的 agent 用起来"不稳定"：同样的事有时办得妥当，有时乱来。排查下来原因往往不是模型，而是 agent 对你的环境一无所知——不知道项目在哪、测试怎么跑、哪些文件不能碰。这些信息要么靠每次对话重复交代，要么靠模型瞎猜。`AGENTS.md` 就是把这类信息一次性固化下来的地方。

## 做法：从最小骨架开始

不必一次写全，先给三节：

```markdown
# AGENTS.md

## 环境事实
- Node 20，包管理用 pnpm
- 主项目在 ~/code/my-bot，测试命令：pnpm test

## 工作流程
- 改代码前先读对应模块的 README
- 提交信息用中文，格式：模块: 变更摘要

## 硬性约束
- 不要动 .env 和任何密钥文件
- 未经确认不执行 git push --force
- 超过 200 行的改动，先列方案再动手
```

三节职责分明：**环境事实**是 agent 无法自己发现的信息；**工作流程**是你希望的做事顺序；**硬性约束**是踩坑后提炼的"不准做"清单。

后续迭代方式很简单：agent 每犯一个你不想看到第二次的错误，就把对策沉淀成一条规则。这个文件是长出来的，不是设计出来的。

两个进阶用法：
- 在里面教它维护记忆，比如"会话中出现的关键决定，追加到 MEMORY.md"；
- 工作空间里若有多个子项目，在各子目录放各自的 `AGENTS.md`，指令就近生效。

## 踩坑点

1. **写太长。** 整个文件会占上下文，几十行之后每多一行都在稀释关键约束的权重。经验上单屏能看完最好。
2. **写愿望不写规则。** "请认真负责、仔细检查"这种话模型无从执行；"改动后必须跑 pnpm test 并贴出结果"才是可验证的指令。
3. **和 SOUL.md 抢地盘。** 人格、语气归 SOUL.md，操作规范归 AGENTS.md，重叠会造成行为漂移。
4. **改完不换新会话。** 文件在会话建立时读取，改完在旧会话里测试，测的是旧版本。
5. **放敏感信息。** 密钥、token 不要写进来——它会被完整读进上下文，也可能被引用到回复里。

## 可复用建议

- 把 `AGENTS.md` 当代码对待：进版本库、走 review，每次改动写清楚为什么。
- 规则一律用祈使句 + 可验证动作，删掉所有形容词。
- 负面经验比正面经验值钱："不要做 X"比"请做好 X"有效得多。
- 定期瘦身：半年没触发过的规则，大概率可以删了。

## 总结

`AGENTS.md` 的价值不在写得漂亮，而在把你脑子里的隐性约定，变成 agent 每次开机就能读到的显性规则。最小骨架起步、错误驱动迭代、定期瘦身——把它当一份持续维护的运维文档，而不是一次性提示词。
