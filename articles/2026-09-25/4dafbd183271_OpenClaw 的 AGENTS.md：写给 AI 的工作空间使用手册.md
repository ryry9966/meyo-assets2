## 背景

OpenClaw 的 agent 每次会话启动时，都知道自己有哪些工具、接了哪些 MCP server，但它不知道你的工作空间"怎么用"：目录为什么这样分、哪个脚本能跑、哪个目录是生成物不能提交。这些信息人类靠 README 和口头传承，AI 需要一份自己的说明书——AGENTS.md。

## 问题

没有 AGENTS.md 时常见的现象：

- agent 反复猜命令，跑错测试入口；
- 每次会话都要人工重复交代"别动 .env""构建产物别提交"；
- 同类错误隔几天又犯，提示词改了这里漏了那里。

本质问题：工作空间的知识散落在人脑和零碎文档里，agent 缺一个稳定的、每次都会读的锚点。

## 做法

1. 在工作空间根目录建 `AGENTS.md`，和代码一起进 git。
2. 分层来写，建议五段：
   - **范围**：这个空间是干嘛的，agent 该做什么、不该做什么；
   - **环境事实**：运行时版本、关键路径、端口、依赖安装方式；
   - **约定**：分支命名、提交信息风格、目录职责；
   - **命令**：构建/测试/部署的确切入口，直接给可复制的命令；
   - **边界与上报**：哪些操作必须先问人（删数据、改配置、对外请求）。
3. 控制篇幅。AGENTS.md 每次会话都进上下文，目标一屏到两屏；细节用相对链接指向其他文档，但关键事实必须内联，别赌 agent 会去点开链接。
4. 用祈使句、写可验证的规则。"写高质量代码"无效；"commit message 用 `type: 描述` 格式"有效。
5. 持续迭代：agent 犯了两次的错，就补一条规则，把补规则当成修 bug。

## 踩坑点

- **写太长**：规则多了互相稀释，关键约束反而被淹没。超过两屏就该精简或外链。
- **规则冲突**：AGENTS.md 与系统提示词、子 agent 配置打架时，行为会不稳定。改规则前全局搜一遍。
- **内容过期**：重构后路径变了没更新，agent 会拿着旧地图找路。把 AGENTS.md 的变更放进 PR review，当代码看。
- **写入敏感信息**：密钥、内网地址不要写进去，AGENTS.md 会被 agent 读出、可能被日志记录。

## 可复用建议

- 把它当"给 AI 的 runbook"：每条规则都应对应一个可观察的行为，写完自问"这条被违反时我怎么发现"。
- 分层放置：全局习惯（如"所有回复用中文"）放用户级配置，项目约定放工作空间级，避免重复维护。
- 和 MCP 配合：在 AGENTS.md 里写明什么场景优先用哪个 MCP 工具、什么场景走本地脚本，减少工具选择的随机性。
- 建一个最小模板：范围/环境/约定/命令/边界五段起步，先跑起来再逐步补。

## 总结

AGENTS.md 成本极低——一个 markdown 文件，几十行——但它是工作空间里杠杆最高的一笔投入。它把"新人每来一次都要带一遍"的成本，变成一次写清、持续复用。agent 的稳定性，很大程度上取决于你给它的环境有多确定。
