## 背景

AGENTS.md 是放在 OpenClaw 工作空间根目录的一份 Markdown 文件，agent 每次进入工作空间或接到任务时会优先读取。可以把它理解为写给 AI 的 README：不是介绍项目，而是规定“在这个工作空间里干活，你得遵守什么”。

它和另外两类上下文来源分工明确：README.md 写给人，系统提示词写在配置里，而 AGENTS.md 跟着工作空间走、可以进 Git、可以分层覆盖。

## 问题

没有 AGENTS.md 时，这些场景应该很眼熟：

- 每次会话开头都要重复交代：用 pnpm 不用 npm、提交信息格式、别碰某个目录；
- agent 行为不稳定，同样的任务，这次把临时文件写进项目目录，下次写到系统 /tmp，还顺手装了两个没人要的依赖；
- 偏好散落在聊天记录里，换台机器、换个会话就丢，无法 review 也无法版本化；
- 长期记忆（memory）里混进大量“规则”，每次被当作模糊的背景噪音召回，时灵时不灵。

本质上，这是把确定性规则寄托在了概率性上下文上。AGENTS.md 的价值，就是把规则变成每次必读的确定性输入。

## 做法

我们目前的结构是两层：

1. 工作空间根目录的 `AGENTS.md`：全局约束，所有任务生效；
2. 各项目目录内的 `AGENTS.md`：项目特有约定，OpenClaw 按就近原则叠加，项目级优先。

内容上建议固定几个小节：

- **环境与命令**：构建、测试、lint 的准确命令，写到可直接复制执行；
- **目录约定**：哪里放产物、哪里放临时文件、哪些目录只读；
- **风格与格式**：回复语言、代码风格、提交信息模板；
- **禁止事项**：不主动 git push、不修改 .env、不擅自升级依赖；
- **汇报格式**：任务结束后报告改动文件列表、执行过的命令、遗留问题。

写法上有两条硬标准：每条指令可执行、可验证；用“当 X 时做 Y”的句式，给反例比给形容词有用。根文件建议控制在 100–200 行内——它每次都会被读入上下文，长度本身就是成本。

维护方式：进 Git，改动走 commit。agent 犯了不该犯的错，先判断是“不会”还是“不知道”，后者就补一条进 AGENTS.md，踩坑即沉淀。

## 踩坑点

- **写成愿望清单**。“尽量保持代码整洁”这类句子没有可操作性，agent 只会礼貌地忽略它。
- **贪多求全**。什么都塞进去，关键规则被稀释；我删掉一半条目后，遵循率反而明显上升。
- **和 memory 混用**。规则进 AGENTS.md，事实性记录才进 memory。混着写，规则就退化为玄学。
- **分层冲突**。根文件和项目文件说法不一致时，agent 的选择近乎随机；要么删掉过时条目，要么明确写清优先级。
- **夹带敏感信息**。这个文件会被完整读进上下文，还可能随仓库分发，token、内网路径别写进去。

## 可复用建议

- 从最小模板起步：环境与命令 / 目录约定 / 禁止事项 / 汇报格式，四节约 60 行即可跑起来；
- 建立“踩坑 +1”习惯：每次人工纠错后问一句“这条能不能固化成规则”，一个月后文件会自然稳定；
- 每两周 review 一次，删掉过时条目，以及已被稳定遵守到无需再说的条目；
- 团队场景把通用部分抽成模板，新成员复制后只改项目特有部分。

## 总结

AGENTS.md 把“调教 agent”从聊天记录里的口口相传，变成了可 review、可回滚、可分层的工程实践。它的价值不在于初版写得多完整，而在于每次踩坑后追加的那一条规则。一份健康的 AGENTS.md 会越来越短、越来越准——这就是它在正常工作的标志。
