## 背景

把 agent 接进 OpenClaw 工作空间后，一个现象几乎人人会遇到：agent 对环境一无所知。人类新人有 README 和 onboarding 文档，agent 每次会话却都像“第一天入职”，全靠猜——包管理器用 npm 还是 pnpm？测试命令是什么？哪些文件是生成物？猜错一次，轻则构建失败，重则改坏 lockfile、动到不该动的目录。

AGENTS.md 就是针对这件事的约定：在工作空间根目录放一个 Markdown 文件，agent 开始工作前会先读它。本质上，这是你提前写给 AI 的一页工作空间使用手册。

## 没有手册时的典型翻车

- 用错包管理器，装出一堆冗余依赖；
- 每次会话都重新“探索”目录结构，浪费 token 也浪费时间；
- 把生成代码、lockfile 当源码改，提交一堆噪音 diff；
- 团队每个人在对话里重复粘贴注意事项，还互相矛盾。

共性很明显：这些上下文本该躺在文件里，而不是每次对话里。

## 做法

**1. 定位置。** 根目录放 AGENTS.md 作为全局默认；子项目可放自己的版本做覆盖。读取时取最近一层，别让两层文件大量重复。

**2. 写六件事，各一小节：**

- **概览**：这个工作空间是干什么的，一段话即可；
- **目录结构**：每个目录一行，说明放什么、什么不能碰；
- **常用命令**：构建、测试、lint 的准确命令，以及“怎样算成功”；
- **约定**：commit 格式、分支命名、linter 管不到的风格偏好；
- **禁区**：绝不修改的文件（生成物、密钥、lockfile）和需人工确认的操作（数据库迁移、依赖大版本升级）；
- **求助路径**：卡住时看哪份日志、跑什么命令自检。

**3. 控制篇幅。** 目标 100 行以内。agent 上下文有限，一万字的手册等于没写——关键规则会被稀释。细节用链接，别整段粘贴。

**4. 当事故复盘来维护。** agent 犯错、你解释过一次之后，把结论沉淀成一行写进 AGENTS.md。同一种错犯第二次，说明文件缺了一行。

## 踩坑点

- **写成散文。**“请写出高质量代码”没有信息量；“完成前必须跑 `pnpm test`，失败不得标记 done”才是规则。
- **多处维护导致漂移。** 同一信息散在 README、docs 和 AGENTS.md 里，改一处漏两处。AGENTS.md 引用其他文档，不复制内容。
- **内容过期。** 命令改了文件没改，agent 会忠实执行错误的说明，比不写更糟。把它放进版本库、走 PR 评审，与代码同等对待。
- **管得太死。** 全是禁令，agent 会束手束脚、事事来问。区分硬规则（禁区）与偏好（默认如此，可变通）。
- **MCP 工具只装不管。** 接了 MCP 或插件，就在文件里写明优先用哪个、哪些调用危险，否则 agent 的选择接近随机。

## 可复用建议

一个够用的判断标准：**你会写进“人类实习生第一天须知”的内容，值得放进 AGENTS.md；agent 应能从代码自行推断的，不要写。** 前者是手册，后者是噪音。

模板骨架就六个标题：概览 / 目录结构 / 常用命令 / 约定 / 禁区 / 求助路径。先各写一两行，再随事故迭代。

## 总结

AGENTS.md 的成本是几十分钟，收益是每次会话少掉一轮试错。它不神秘，也不靠提示词技巧——只是把“运维文档”这件事补给了 AI 这位新同事。写好第一版、进版本库，之后 agent 每摔一跤就补一行。一个月后你会觉得它越来越“懂事”，其实只是手册越来越全。
