## 背景

Agent 接入项目后，最大的落差往往不在能力，而在上下文。OpenClaw 能读写文件、跑命令、调 MCP 工具和插件，但它不知道你的项目用 pnpm 还是 npm、哪些目录是生成物、测试怎么触发。这些信息传统上靠口头约定和 README，而 README 是写给人看的。

AGENTS.md 是一个正在被多家 agent 工具采用的开放约定：在仓库根目录放一个纯 Markdown 文件，作为 agent 进入工作空间时自动加载的"使用手册"。OpenClaw 会在会话启动时读取工作区和仓库内的 AGENTS.md，并支持子目录层级的就近覆盖。

## 问题

没有这份手册时，常见三类麻烦：

1. **行为不一致**：同一个任务，这次跑 `pnpm test`，下次跑 `npm run test:ci`。
2. **破坏约定**：改 `dist/`、手写 migration、提交信息格式随机。
3. **重复劳动**：每个同事都在提示词里粘贴一遍项目规则，换个会话就丢。

本质是：项目约定缺少一个机器可读、随代码版本化的落点。

## 做法

建议分四步搭起来：

1. **根目录先写一版最小的**。控制在 60 行以内，五块内容：项目一句话概览；常用命令（写可直接执行的命令，不要写描述）；目录地图（哪些是生成物、哪些禁止手改）；代码风格里"机器可执行"的几条；禁止事项（如"不要跳过测试提交"）。
2. **子目录分层**。monorepo 在每个包下再放一份，只写该包特有规则。OpenClaw 处理子目录任务时取就近文件，根文件继续生效。
3. **全局与仓库分治**。个人工作区的 AGENTS.md 放偏好（回复语言、提交风格），仓库里的放项目事实。冲突以仓库为准，两边尽量不重叠。
4. **当代码维护**。规则变更走 PR review；agent 同一个错犯第二次，就补一行规则；工具链换了，当天更新文件。

## 踩坑点

- **写成散文**。大段背景介绍会稀释关键约束。每条规则一行、动词开头、可判定——"运行 X"，而不是"注意测试"。
- **和 README 互相抄**。两份文档必然漂移。AGENTS.md 里链接过去，别复制。
- **塞敏感信息**。AGENTS.md 会随上下文发给模型，token、内网地址一律不写。
- **当安全边界用**。它只是引导，不是沙箱。危险命令的拦截要靠 OpenClaw 的工具权限配置，文字约束挡不住误操作。
- **只增不删**。三个月后文件越长越没人看，过期规则比没有规则更糟。

## 可复用建议

- **统一骨架**：概览 / 常用命令 / 目录说明（含禁改区）/ 风格约定 / 禁止事项，五个标题固定，团队所有仓库保持一致，agent 迁移项目时零成本。
- **定期审计**：把文件里出现的每条命令实际跑一遍，跑不通的当场修。
- **意外收益**：写得好的 AGENTS.md 同时是不错的新人上手文档——给 AI 写清楚的事，往往人也正缺这份清晰。

## 总结

AGENTS.md 的价值不在"多一个配置文件"，而在于把散落的团队约定收敛成一个版本化、机器可读的接口。经验就三条：短、准、常更新。它不会让 agent 变聪明，但能让它少猜——在自动化实践里，少猜就已经省下了大部分返工。
