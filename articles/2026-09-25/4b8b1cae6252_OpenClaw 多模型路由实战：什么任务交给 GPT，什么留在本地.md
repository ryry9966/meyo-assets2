## 背景

OpenClaw 的定位是把聊天渠道、定时任务、插件和 MCP 工具统一接到一个 agent 网关上。跑久了你会发现成本结构很畸变：80% 的调用是格式化、摘要、轮询这类杂活，20% 是规划、长上下文推理这种真正吃模型能力的活。全用 GPT，月底账单难看；全换本地小模型，agent 开始胡乱传参、忘记上下文。多模型路由要解决的就是这个分配问题。

## 我的路由原则

按任务类型分，而不是按消息分：

1. **重推理任务走云端强模型**：多步规划、跨渠道上下文整合、最终对外回复的定稿。这些错了代价高，值得花钱。
2. **高频杂活走本地**：工具调用的中间循环、批量摘要、翻译、cron 报告草稿。错了重跑就行，本地跑不心疼。
3. **隐私敏感默认本地**：涉及本地文件路径、聊天记录原文、密钥相关的任务，先本地跑，能力不够再逐项放行云端。

## 具体做法

1. 把主 agent 与子任务拆开配置：主 agent 挂强模型负责规划和最终输出；批量类子 agent（定时巡检、消息摘要）指向本地 Ollama / vLLM 的 endpoint。
2. 给每个 agent 写清楚 primary + fallback。本地为主、云端兜底；强模型那边也留一条本地退路，防止 API 限流时整个渠道哑掉。
3. 控制本地模型见到的工具数量。本地小模型 function call 稳定性差，只给它 3 个以内、参数简单的工具，通过率立刻上去。
4. 每周看一次路由日志：各模型 token 消耗、fallback 触发次数、任务失败率。数据说话，再调路由表。

## 踩坑点

- **本地模型工具调用格式不稳**：参数错乱会让 agent 循环空转，看起来像 OpenClaw 的 bug，其实是模型问题。先换强模型复测再排障。
- **上下文窗口小**：长会话"忘事"常被误判为记忆插件故障，实际是 context 溢出被截断。
- **路由粒度太细**：按单条消息切模型会导致同一会话风格漂移。以 agent 为粒度路由，稳定得多。
- **fallback 不是免费的**：触发一次就是双份 token，重试风暴时会烧钱，fallback 必须配次数上限。
- **别只看吞吐**：本地推理在高并发渠道下排队延迟反而比云端高，要看端到端响应时间。

## 可复用建议

- 路由规则全部收敛到一个配置文件，每条写注释说明"为什么这个任务用这个模型"，三个月后的你会感谢现在的自己。
- 默认本地、白名单放行云端，比反过来安全。
- 固定一个 20 条左右的小评测集，每次换模型前后跑一遍，别凭体感切换。

## 总结

多模型路由不是炫技，而是成本、延迟、隐私、稳定性四方的权衡。OpenClaw 给了足够的配置自由度，但自由度越大越需要纪律：先测数据，再定路由，以任务成功率为第一指标。钱要花在刀刃上——刀刃就是规划和定稿那 20% 的任务。
