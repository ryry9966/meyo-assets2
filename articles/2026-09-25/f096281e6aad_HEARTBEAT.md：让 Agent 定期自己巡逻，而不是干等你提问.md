## 背景

大多数 Agent 的使用模式是被动的：你提问，它回答，会话结束就沉寂。OpenClaw 在网关层有一个容易被忽略的机制——heartbeat（心跳）：默认每 30 分钟唤醒一次 Agent，让它读取工作区里的 `HEARTBEAT.md`，按文件里的指示决定要不要干活、要不要打扰你。这个文件本质上是一份「值班巡逻清单」，是让 Agent 从被动问答走向主动值守的最低成本入口。

## 问题

- 有价值的信息（RSS 更新、CI 状态、明日日程）需要你主动去问，Agent 明明有工具，却只在会话里干活；
- cron 能做定时任务，但逻辑写死，遇到「看情况判断」的场景无能为力；
- 直接让 Agent「每隔一会儿帮我看看」，结果它每 30 分钟发一条「一切正常」的废话。

## 做法

1. **定位文件**：`~/.openclaw/workspace/HEARTBEAT.md`。默认内容只有一条规则——无事可做时回复 `HEARTBEAT_OK`，网关识别后静默处理，不转发给你。这是整套机制的关键语义。
2. **写任务清单**，每条包含三要素：触发条件、动作、通知策略。例如：
   - 每次心跳检查日志目录大小，超过 500MB 时清理并告知我，否则保持沉默；
   - 工作日上午汇总今天日历和未读 GitHub issue（带 bug 标签的优先）；
   - 服务器负载连续两次心跳超阈值时立即通知。
3. **调频率**：默认 30 分钟，可在配置中调整心跳间隔；需要更灵敏的监控降到 10–15 分钟即可。
4. **守住静默规则**：明确告诉 Agent 什么情况下「没消息就是好消息」，只在越过阈值或到点汇总时发声。
5. **与工具组合**：心跳里可以调用 MCP 工具、shell、浏览器，判断逻辑交给模型，而不是写死脚本。

## 踩坑点

- **清单太长**：每次心跳都会完整执行一遍，token 成本随条目线性上涨。重活（全量备份、日报生成）交给 cron，HEARTBEAT.md 只放轻量巡逻。
- **指令模糊**：「看看有什么有意思的」会让行为不可预测。写清阈值和对应动作。
- **忘了静默语义**：没写何时闭嘴，就会每半小时收到一条健康播报，一周后你必然关掉心跳。
- **心跳跑在主会话上下文里**：长任务会占用上下文、拖慢正常响应。心跳只负责「发现并触发」，耗时动作转 cron 或子任务。
- **时间敏感任务别放心跳**：模型对「现在几点」并不总是可靠，整点类任务交给 cron 更稳。

## 可复用建议

- 把 HEARTBEAT.md 分三段管理：**每日例行 / 条件触发 / 静默规则**，结构清晰才好维护。
- 通知分级：写日志（默认）→ 汇总播报 → 立即通知，避免惊群。
- workspace 用 git 管理，巡逻清单的每次增删都可追溯、可回滚。
- 每周回顾一次心跳日志，删掉连续几周没触发过的条目——清单和代码一样需要 prune。

## 总结

HEARTBEAT.md 不是什么新范式，本质是把「值班巡检表」交给模型：轻量、可判断、可沉默。原则只有一条——心跳负责「看看有没有事」，cron 负责「到点必须干的事」，通知渠道只承载真正值得打断你的事。分工清楚之后，Agent 才像一个常驻助手，而不是一个等待提问的搜索框。
