## 背景

大多数 AI 助手的默认形态是应答机：你发消息，它回复。OpenClaw 的 agent 也一样，收到渠道消息才跑一轮。但用久了会发现，真正省时间的场景往往不是"我问它答"，而是"它先发现、先告诉我"：CI 挂了、日历冲突、磁盘快满、某个 PR 两天没人评审。

这类需求统称 proactive（主动）能力。OpenClaw 内置了两个钩子：定时任务（cron）和心跳（heartbeat）。但直接打开就用，大概率三天内你的推送渠道会变成噪音源。这篇帖记录我把自己 agent 改造成"三层触发 + 一道闸门"的过程。

## 问题：主动 ≠ 多说话

agent 每主动说一次话，都在消耗你的注意力配额。触发太少没价值，触发太多你会直接静音整个 bot，功能等于白做。所以 proactive 的工程重点，九成在"什么时候闭嘴"。

## 做法：三层触发 + 一道闸门

**第一层：定时摘要（cron）。** 低频、确定性任务。每天早上跑一次，用 MCP 工具拉取昨天的 CI 失败、未读 issue、今日日程，拼成一条 digest。这层不需要模型判断"要不要说"，到点就说。

**第二层：心跳巡检（heartbeat）。** 心跳让 agent 周期性醒来，读工作区上下文后自行决定是否发声。我在工作区放了一份巡检清单，用人话写明"什么情况才允许主动说话"，例如"只有出现新增失败或状态升级时才开口"。

**第三层：事件触发。** 监控告警回调、文件变更、新邮件等外部事件驱动。事件本身不代表要打扰用户，先进队列，交给闸门裁决。

**闸门（gate）：** 所有候选推送先过硬规则——与上次同类推送的间隔是否超过阈值？状态相对上次有无变化（去重）？严重级别是否达到"值得打断"的线？通过后才交给 LLM 生成文案。规则决定"说不说"，模型只负责"说得好"。结构示意（伪配置，以实际版本文档为准）：

```yaml
proactive:
  digest: "0 9 * * *"   # 每日摘要
  heartbeat: 30m        # 巡检间隔
  gate:
    min_interval: 6h    # 同主题最小间隔
    dedup: true         # 状态未变不推
```

## 踩坑点

- **让 LLM 直接判断"要不要说话"**：模型有幻觉式热情，一周推送量爆炸。改成硬规则前置过滤后，噪音降了约八成。
- **去重没做状态比对**："磁盘 87%"天天推。改为只对相对上次的变化推送。
- **心跳太频繁**：15 分钟一次还带全量上下文，token 消耗肉眼可见。30 分钟起步，并裁剪心跳上下文。
- **主动执行了写操作**：有次它顺手把告警"标记为已处理"。此后凡写操作一律只提示、等确认，绝不代劳。

## 可复用建议

- **push digest, pull detail**：主动推送只给一行结论加严重级别，细节等用户来问，对话天然是拉取模式。
- **分级输出**：低优写日志不推、中优进每日摘要、高优立即推送。阈值写死在配置里，不让模型临场发挥。
- 所有主动动作必须幂等、可回滚，默认只读。
- 每周人工审计一次主动日志：它说了什么、事后是否正确，据此回调闸门阈值。

## 总结

Proactive 的本质不是让 agent 更勤快，而是给它一套"值得打扰"的判断结构：cron 管确定性，heartbeat 管巡检，事件管即时性，闸门管克制。建议从每天一条摘要跑起，稳定两周再往上一层加。先让助手学会闭嘴，它开口的时候你才会听。
