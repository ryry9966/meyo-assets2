## 背景

OpenClaw 的核心模型是"每个路由一条会话"：同一个 Agent 对同一个聊天对象（比如某个 Telegram 私聊、某个群）维护一条有状态的 session，里面累积着系统提示、历史消息、工具调用与返回结果。这条主会话就是 Agent 的"长期工作记忆"。

但实践中主会话很容易被撑爆：定时任务抓了一圈网页、调试脚本灌进了几百行日志、让模型读一个大文件……这些中间产物一旦写进主会话，之后每一轮对话都要背着它们跑。

## 问题

不做隔离时通常有三个症状：

1. **上下文膨胀**：工具返回的大块内容（网页正文、日志、代码）全部留在主会话，token 成本线性上涨，最终触发 compaction，压缩又会丢细节。
2. **回答质量漂移**：几小时前的无关中间结果还挂在历史里，模型容易被带偏。
3. **线程污染**：如果子 Agent 直接往原频道回复，它的消息在用户眼里就像主 Agent 说的，对话线程被"劫持"。

## 原理：主会话和子会话是两本账

OpenClaw 的 session 按 key 隔离，形如 `agent:main:telegram:direct:12345`。spawn 出来的子 Agent、cron 的隔离运行，都持有独立的 session key 和自己的上下文，跑完只把**一个紧凑的结果**交回主会话。脏活在子会话里消化，主会话只收结论。

## 做法与步骤

1. **重活交给子 Agent**。用 `sessions_spawn`（或 cron 的隔离模式）发起子任务。注意任务 prompt 必须自包含——子会话看不到主会话历史。
2. **约定返回格式**。明确要求子 Agent 返回精简摘要（例如不超过几百字的结论 + 关键数据），而不是它的完整执行过程。
3. **控制回传路径**。默认不要让子 Agent 直接 deliver 到原频道；让它把结果交回主会话，由主 Agent 决定怎么对用户说。
4. **按域拆分 Agent**。研究、运维、代码这类重 IO 任务单独建 agent 和 workspace，路由干净，session 文件也方便审计。
5. **定期清理**。`/new` 重置主会话，`/compact` 主动压缩；批量任务跑完后看一眼 `~/.openclaw/agents/` 下的 sessions 目录，把明显不用的 jsonl 归档掉。

## 踩坑点

- **子 Agent 直接回复频道**：结果和主 Agent 的发言混在同一线程，出问题想回滚都无从下手。始终走"返回摘要 → 主会话转发"。
- **任务 prompt 写一半**：spawn 出来的子会话是白纸，别指望它继承"我们刚才聊到哪了"，需要的上下文要在 prompt 里显式给全。
- **并发过头**：一次 spawn 十个子 Agent，容易撞平台限流，也烧钱。控制并发、分批跑。
- **重置时机**：`/new` 会清掉主会话记忆，适合在一次大任务收尾后执行，别在任务中途手滑。
- **以为压缩等于隔离**：compaction 只是压缩主会话，重 IO 的中间产物该进子会话还是要进子会话。

## 可复用建议

- 把主会话当"热数据"：只放对话意图、决策和子 Agent 的结论；一切大体积中间产物走隔离会话。
- 给子 Agent 定统一的结果 schema（结论 / 证据 / 风险 / 建议下一步），主会话的后续推理会稳定很多。
- cron 任务一律用隔离会话，避免每次运行都在主会话里堆一段。
- 把这套约定写进 workspace 的说明文件里，让 Agent 在规划任务时自动优先 spawn，而不是把所有工具输出吞进主会话。

## 总结

session 隔离本质上就是"记账分离"：主会话只记该记的，脏活累活在各自的会话里消化，交回来的只有结论。这件事没有高深机制，但坚持做好之后，长对话的 token 成本、回答稳定性和多任务并行能力都会有肉眼可见的改善。如果你在多渠道场景下被上下文膨胀折磨过，建议从一个"研究型子 Agent + 固定返回格式"开始试起。
