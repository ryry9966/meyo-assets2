## 背景

做 Agent 自动化的人大多会遇到两个现实问题：一是调用频率高，云 API 账单涨得很快；二是不少本地数据（日志、文档、聊天记录）不希望出网。把模型搬到自己电脑上，是解决这两件事的直接思路。这篇帖子记录我在一台 32GB 内存的台式机上部署本地 LLM，并接入 OpenClaw 跑 MCP 工具调用的完整过程。

## 问题

"模型跑起来了"和"模型能干活"是两回事。很多人用一键安装器加载了一个 7B 模型，聊天没问题，但一接进 Agent 流程就开始翻车：工具调用格式错乱、长上下文直接爆显存、JSON 输出不合法导致解析失败。本地部署的核心难点不在安装，而在评估它到底能承担你工作流里的哪一段。

## 做法

按顺序，我的步骤是：

1. **先盘硬件，再选模型。** 显存（或统一内存）决定上限。经验公式：参数量 × 单参数量化字节数 + 2~4GB 的 KV cache。12GB 显存跑 7B Q4 很稳，14B 勉强；32GB 内存跑 14B Q4 可行但慢。
2. **选带 OpenAI 兼容接口的推理框架。** Ollama、llama.cpp server 都行，关键是暴露 `/v1/chat/completions`，这样 OpenClaw 侧只需要改 base URL 和模型名就能接入，不用改代码。
3. **量化从 Q4_K_M 起步。** 别一上来追求 Q8 或 FP16。在 Agent 任务里，量化带来的质量损失通常小于上下文长度不足带来的影响。
4. **接一个最小 Agent 流程做验收。** 不要用聊天测试，直接挂两三个 MCP 工具（文件读写、HTTP 请求），跑十轮真实任务，统计成功率。
5. **固定版本并记录基线。** 模型 + 量化等级 + 框架版本三者一起记录，升级前先跑同一套任务做对比。

## 踩坑点

- **上下文长度是显存杀手。** 标称 32K 上下文，实际塞满时 KV cache 会额外吃掉好几个 GB，直接 OOM。Agent 场景下 MCP 工具的描述会常驻 system prompt，几个工具就能占掉几千 token——工具描述务必精简。
- **小模型的结构化输出不稳。** 14B 以下的模型 function calling 失败率明显上升。建议开启框架自带的 grammar/JSON 约束，或者用提示词约束加重试兜底。
- **并发别贪。** 本地推理实际是串行排队，Agent 并发开 4 个任务，吞吐反而崩掉。把并行数设为 1，靠上游队列消化。
- **别信"一键满血"。** 同一个模型的不同量化版本差距可以很大，下载前看清楚标签，别只看参数量。

## 可复用建议

- 做**分层路由**：本地模型处理摘要、分类、简单改写这类高频低难度的活，复杂规划和多步推理仍走云端。本地承担的比例越高，省得越多。
- 建一个 20~30 条的**固定评测集**，每次换模型或量化跑一遍，用数据说话，不凭感觉换。
- 给本地端点单独配超时和重试策略，不要和云端 provider 共用参数——两者延迟分布完全不同。

## 总结

本地 LLM 的价值不在于替代云端，而在于把工作流里"高频、廉价、敏感"的那一段收回来。硬件决定下限，量化决定性价比，而真正决定它能否进 Agent 流程的，是你有没有一套可重复的验收方法。先跑通一个最小流程，再谈规模。
