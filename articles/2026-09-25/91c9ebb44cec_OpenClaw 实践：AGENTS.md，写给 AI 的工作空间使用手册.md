## 背景

AGENTS.md 是一个正在被多家 Agent 工具采纳的简单约定：在工作区根目录放一个 Markdown 文件，Agent（包括 OpenClaw）每次进入工作区时自动读取，作为该环境的操作说明。它类似 CONTRIBUTING.md——只不过读者不是人，而是模型。没有专门语法，就是纯 Markdown，随仓库一起版本管理。

## 问题

没有这份手册时，Agent 每次会话都要"重新摸索"：

- 包管理器猜错：项目用 pnpm，它跑 `npm install`，锁文件被改乱；
- 结构靠猜：建了不该存在的目录，工具函数放错位置；
- 验证缺失：改完不跑测试就宣布"完成"；
- 纠正不沉淀：上次在聊天里说清楚的规则，新会话全忘。

这不是模型能力问题，是上下文缺失。聊天里临时给指令无法沉淀、无法共享、无法跨会话生效。

## 做法

我们团队的 AGENTS.md 稳定在 80~120 行，结构大致如下：

```markdown
# 项目一句话说明
# 目录结构（只列关键目录，各配一句职责）
# 常用命令
- 安装：pnpm install
- 单测：pnpm test（改代码后必须跑）
- Lint：pnpm lint
# 约定
- 错误统一用 Result 封装，不裸抛异常
- 新接口必须带类型定义
# 禁改区
- migrations/ 只在评审通过后修改
# MCP / 插件说明
- 查数据库用 db-query 工具，不要写临时脚本直连
```

几条写法经验：

1. **命令优先于描述**。"跑 pnpm test"比"请保证代码质量"有用一百倍。
2. **只写反复用到的**。一次性的事放 issue，别塞进这里。
3. **子目录可以再放一份**。OpenClaw 处理子目录内文件时会叠加该目录的 AGENTS.md，monorepo 里适合给 `frontend/`、`server/` 分别写局部规则。
4. **迭代维护**。我们的原则：同一条规则被违反两次，就写进去。

## 踩坑点

- **写太长**。整份文件会进上下文，500 行的手册模型大概率忽略中段，还拖累每次会话的开销。信息密度比全面重要。
- **照抄 README**。README 面向"想上手的人"，AGENTS.md 面向"正在干活的 Agent"，内容交集很小，互相复制只会稀释。
- **把它当安全边界**。AGENTS.md 是引导，不是权限系统。"禁止删数据"这类硬约束要靠 OpenClaw 的工具权限/沙箱配置兜底，文字拦不住执意的工具调用。
- **让内容烂掉**。过期指令比没有更糟——Agent 会按旧命令反复失败。团队约定：改构建流程的 PR 必须同步改 AGENTS.md。

## 可复用建议

- 从 20 行起步：一段项目说明、三条命令、一条禁改区，今天就能写完；
- 用正反例代替形容词：贴一小段"正确写法 / 错误写法"，比"遵循整洁代码"有效得多；
- 把它纳入 code review：这份文件现在是你仓库行为的一部分；
- 每月扫一遍，删掉失效条目，保持文件可信。

## 总结

AGENTS.md 的价值在于把"纠正 Agent 的成本"从每次会话摊销到一次文件维护。它便宜、可版本化、随时间复利。如果还没有，先花十分钟写最简版，然后让每一次踩坑都变成文件里的一行规则。
