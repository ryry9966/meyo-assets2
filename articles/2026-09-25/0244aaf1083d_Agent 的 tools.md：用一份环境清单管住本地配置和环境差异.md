# 背景

Agent 跑起来之后，能力边界往往不在模型，而在本机环境：有没有 `jq`、Python 是 3.10 还是 3.12、`~/work` 到底存不存在、出网要不要走代理。OpenClaw 这类框架支持把 markdown 作为上下文注入 agent（和 AGENTS.md 的约定类似），tools.md 干的就是这件事——给 agent 看的本机环境说明书。

# 问题

没有这份说明书时，典型症状有三个：

1. **跨机器表现不一致**。笔记本上跑得好好的自动化，到 CI 或家里的小主机上，agent 第一步就猜错路径或缺依赖。
2. **幻觉出不存在的工具**。模型见惯了 `rg`、`docker compose`，你机器上没有，它照样调用，然后开始连环报错、自我纠错，浪费大量轮次。
3. **环境知识散落**。有的写在 system prompt，有的写在脚本注释，有的只在某人脑子里，无法版本化、无法 review。

# 做法

核心思路：把环境差异显式声明成结构化清单，分层维护，用脚本对账。

**第一步：建文件，固定格式。** 项目根放 `tools.md`，用短列表而不是散文：

```markdown
# 环境
- OS: Ubuntu 22.04, x86_64
- Python: 3.11 (/usr/bin/python3)

# 可用工具
- git, curl, jq, docker（有 root 权限）
- 不存在: rg, ffmpeg —— 不要尝试调用

# 路径约定
- 项目数据: /data/work/<project>
- 输出统一写入 ./out/

# 网络
- 出网走 http://127.0.0.1:7890 代理

# 密钥
- 不写入密钥，凭据由环境变量 TOKEN 提供
```

**第二步：分层。** 全局差异放 `~/.openclaw/tools.md`（这台机器的共性：GPU、代理、常用 CLI），项目差异放项目级文件，项目级覆盖全局，两份都注入上下文。

**第三步：脚本生成草稿。** 手写必然漂移。写个 `env-probe.sh`，用 `command -v`、`python3 -V`、`docker info` 探测后输出 markdown 片段，人工审核增删后入库。换机器重跑一遍，成本几秒。

**第四步：清单当代码。** tools.md 进 git，环境变更和对应脚本改动放同一个 commit；CI 里跑一次探测脚本做 diff，漂移直接暴露在流水线上。

# 踩坑点

- **写成小作文**。超过一屏，agent 抓不住重点还挤占上下文，只写影响决策的事实。
- **写"应该有"而不是"实际有"**。文档理想化是漂移的最大来源，探测脚本就是治这个的。
- **版本号写死**。写"Python >= 3.10"比"Python 3.11.4"更抗时间侵蚀，也避免 agent 因版本不完全匹配而犹豫。
- **敏感信息入库**。tools.md 会被注入上下文，还可能进日志，密钥只写"从哪拿"，不写值。
- **只增不删**。工具卸载了清单还留着，agent 会继续调用。diff 机制能兜底，但得有人看。

# 可复用建议

- 用三态描述工具：**可用 / 不存在 / 受限**（如"有 docker 但不能挂载 host 目录"）。"不存在"清单往往比"存在"清单更能减少幻觉。
- `env-probe.sh` 做成团队公共脚本，输出格式统一，新机器初始化十分钟搞定。
- 排障时先 diff 两台机器的 tools.md——一半的"agent 抽风"其实是环境差异。

# 总结

tools.md 的价值不在文件本身，而在于把"环境事实"变成可版本化、可 review、可对账的资产。规则很简单：清单要短、要真实、要分层、要能自动生成。做到这四点，同一套 agent 流程在笔记本、CI 和服务器上的行为差异会小得多。
