## 背景

社区里用 Agent 写技术文章的流程已经比较成熟：模型产出 Markdown 初稿，人工润色，然后发到公众号、知乎、掘金、GitHub。写一次不难，难的是"发"。各平台格式约束互不兼容，手动排版的时间往往超过写作本身。我的做法是把格式适配做成一条可复现的管线，并封装成 OpenClaw 插件，让发布变成一条指令。

## 问题

实际跑下来，痛点集中在三层：

1. **模型输出不稳定**：同样的 prompt，有时给纯 GFM，有时夹行内 HTML，有时 frontmatter 混进正文，标题层级随机。
2. **平台约束碎片化**：公众号只认内联样式 HTML、图片必须走素材库；知乎和掘金对表格、脚注、公式的支持各不相同。
3. **管线不可复现**：用 regex 修修补补，遇到嵌套代码块就崩；重跑一次，图片重复上传、草稿重复创建。

## 做法

核心原则：**只保留一份 canonical Markdown，其余全是派生物。**

**Step 1：内容契约。** 生成阶段就在 prompt 里约束：单一 H1、纯 GFM、禁行内 HTML、代码块必须带语言标注。这是第一道防线，但不能信任它。

**Step 2：归一化。** 用 remark/mdast（unified 生态）做 AST 级清洗，而不是 regex：剥掉误入的 frontmatter、HTML 节点转 Markdown、列表缩进归一、补全代码语言。每个清洗规则写成一个小插件，只做一件事。

**Step 3：平台适配器。** 每个目标平台一个 mdast transformer：公众号适配器把 AST 序列化成内联样式 HTML，代码高亮在构建期完成（直接输出带样式的 span）；不支持脚注的平台降级为文内链接；表格支持差的地方降级成列表。适配器只管"节点 → 平台表示"，不碰正文内容。

**Step 4：资产处理。** 发布前扫描 image 节点，按内容 hash 做缓存；公众号场景先把图传素材库，回填 URL 进 AST，最后才序列化。顺序不能反。

**Step 5：校验与发布。** 发布前跑 lint：节点类型白名单、图片可达性、链接有效性；先 dry-run 出预览，确认后再真正发布。整条链路封装成 MCP 工具（如 `markdown.publish(platforms=[...])`），Agent 拿到结果后自己判断是否需要重试。

## 踩坑点

- regex 改写 Markdown 在嵌套代码块（fence 里套 fence）上必然出错，一律走 AST。
- 公众号会剥掉 `<style>` 和 class，样式必须全部内联；代码高亮放构建期，别指望前端渲染。
- 防盗链：外部图床在公众号、知乎会被 referer 拦截，图必须落地重传。
- 模型对"内容契约"的执行率大约八成，lint 是必需品，不是装饰。
- CJK 文本的硬换行与软换行，个别平台会渲染出多余空行，归一化时要显式处理。
- 幂等很关键：图片上传、草稿创建都要有 hash 缓存或幂等键，否则每次重跑都是新副本。

## 可复用建议

- 把规范 Markdown 当源码，平台产物当构建产物，标记 generated，不手工编辑。
- 每个适配器配 snapshot 测试：固定输入样例，输出快照入库，升级依赖时 diff 一眼看出格式漂移。
- 适配器保持纯函数：AST 进、AST/HTML 出，不读环境、不碰网络；网络和鉴权留在发布层。
- 失败留痕：哪一步、哪个节点、哪个平台挂了，写进结构化日志，Agent 才有自我修复的依据。

## 总结

多平台发布的本质是编译问题：一份源文件、多个 target、各自的后端。用 AST 管线替代字符串拼接，用契约加 lint 替代对模型输出的盲信，用缓存和快照保证可复现，发布就从体力活变成了一条可以被 Agent 驱动的普通命令。先跑通一个平台，再横向加适配器，成本会低很多。
