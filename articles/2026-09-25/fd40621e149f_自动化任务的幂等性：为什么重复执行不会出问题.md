## 背景：自动化任务的默认语义是"至少一次"

在 OpenClaw 这类 Agent 自动化场景里，任务很难做到"恰好执行一次"。定时任务可能重叠触发；webhook 会被重复投递；Agent 调用 MCP 工具超时后往往会自行重试；网络抖动还会留下"到底执行了没有"的灰色地带。所以工程上应当默认：任何自动化任务的投递语义都是"至少一次"，幂等性就是在这个前提下保证结果正确的手段。

幂等的定义很朴素：同一操作执行 N 次，效果与执行一次相同。读操作天然幂等，真正需要设计的只有写操作。

## 问题：非幂等的写操作会累积副作用

几个社区里常见的翻车现场：

- 定时摘要任务发邮件，首次超时被重试，用户收到两封一模一样的邮件；
- Agent 通过 MCP 工具调 create_issue，超时重试后，项目管理里出现两个重复 issue；
- webhook 重投递导致同一文件被追加写入两遍，数据脏掉。

最危险的区间是"副作用已发生、确认未写回"。进程在这个窗口崩溃，重试就是一次全新的重复执行。

## 做法：一个 key，一次占位，再执行

1. **区分读写**：只对写类操作做幂等设计，读操作不用管。
2. **定义业务幂等键**：用业务含义而非随机值，比如 `daily-digest-2025-06-01`。关键在于：key 在任务实例生成时确定一次，所有重试复用同一个 key，绝不在重试路径里重新生成。也别让 LLM 临场发挥 key，把它固化进 prompt 模板或工具 schema。
3. **执行前查重**：副作用之前，先查持久化存储（SQLite、状态文件、Redis 均可）里该 key 是否存在。插件层可把这一步封装成统一中间件。
4. **原子占位**：确认不存在后，先写入一条 `running` 记录再执行副作用。查与写之间有竞态（cron 与手动触发同时到达），占位动作必须原子——数据库唯一约束、Redis SETNX、文件锁都行，不要靠"先查再写"。
5. **收尾留痕**：执行完把状态改为 `done`，key 保留一段时间，既是去重窗口也是排查依据。

重试逻辑读到 `running` 记录时，按策略跳过或恢复，而不是重新执行。

## 踩坑点

- **判断条件写错**：用"上次是否成功"做判断，正确条件是"是否已占位"。成功记录和副作用之间永远有窗口，占位在前才堵得住。
- **key 生成位置不对**：把 ID 或时间戳的生成放进重试内部，每次重试都变成"新任务"，幂等形同虚设。
- **状态放内存**：插件里用全局变量记状态，进程一重启全丢，必须落盘。
- **时区问题**：用日期做 key 时，UTC 与本地时间换算不当，"每天一次"可能跑出两个 key 或漏掉一天。
- **记录无限增长**：幂等记录要有 TTL 或定期清理，否则存储慢慢被填满。

## 可复用建议

- 给所有暴露给 Agent 的写类工具统一约定 `idempotency_key` 参数，Agent 每个任务实例只生成一次。
- 优先选天然幂等的接口形态：upsert、ensure、条件更新，能不造轮子就不造。
- 幂等状态放进 workspace 的持久化存储，并把 key 写进任务日志，排查时能对上。
- 上线前做个土办法验证：手动连跑两遍任务，数一数副作用（邮件数、issue 数、文件行数）是否只发生了一次。
- 接受"at-least-once + 去重 = 效果上恰好一次"这个现实，不必追求传输层 exactly-once，那是昂贵且多数场景用不上的目标。

## 总结

在自动化系统里，重试和重复触发不是异常，而是常态。把"每个任务都会被执行两次"当作设计前提，用一个业务 key 加一次原子占位，就能把重复执行的代价压到几乎为零。幂等性不性感，但它是自动化任务敢让你睡整觉的底气。
