## 背景

在 OpenClaw 这类 agent 工作流里，"同一个任务被跑两遍"不是异常，而是常态：cron 重叠、网络超时后重试、用户手动补跑、agent 重新规划后再次执行某个步骤。我们默认执行器一定会重试，却经常忘了问一句：**这一步重跑安全吗？**

## 问题出在哪

之前有个同步任务超时后自动重试，结果外部系统里多了三条重复工单。复盘根因很典型：这个操作是"创建"类语义（POST），第一次请求其实成功了，只是响应没返回；执行器看到超时判定失败，于是重试。失败与否的判断依据是"有没有收到成功响应"，而副作用是否发生，是另一回事。

Agent 场景会放大这个风险：LLM 输出不确定，同一意图可能被规划成两次略有差异的执行；如果幂等键是运行时临时生成的（时间戳、随机 UUID），两次执行看起来就是两个新任务，去重完全失效。

## 怎么做

我们的做法归纳为三步：

1. **定义稳定的幂等键**。从任务输入推导，比如 `hash(来源系统, 事件ID, 目标资源)`，而不是运行时生成。键必须随任务定义走，重调度、重部署都不会变。
2. **写入前先查，或直接 upsert**。优先选支持客户端幂等键的 API（Stripe 风格的 Idempotency-Key），其次是天然键 + upsert（按外部 ID 创建或更新）。数据库层面加唯一约束兜底——应用层的 check-then-insert 在并发下不可靠。
3. **记录步骤级状态**。不是记录"任务成功/失败"，而是每个步骤的结果。重试时从最后一个已完成步骤续跑，而不是从头再来。

## 踩坑记录

- 幂等键里混入了时间戳或运行时变量，重试时键变了，去重**静默失效**。这是最隐蔽的一种，日志看不出异常，只有重复数据。
- 只覆盖了写库，没覆盖通知。数据是幂等的，消息发了两条。幂等必须覆盖**最外层的副作用**。
- 超时后重试一个没有幂等键的 POST：请求可能已在服务端生效，但我们无从判断。没有键的外部写操作，重试前先查一次目标状态。
- 补偿动作本身不幂等。"清理临时文件"没问题，"补发一封致歉邮件"就不是。

## 可复用的建议

- 把每个自动化步骤都当作"**至少会执行两次**"来设计。
- 先分类：PUT、upsert、状态置位天然幂等；创建、发送、累加天然不幂等，只有后者需要额外处理。
- 幂等键放进任务定义，不放运行时状态。
- 给 MCP 工具包一层带键的 facade，并在工具描述里标注"可安全重试"，让上游规划器敢于重试。
- 在 CI/staging 里显式测一次"连跑两遍，断言无重复"。
- 监控键冲突率：重放激增往往意味着上游在抖。

## 小结

幂等性不是为了避免重试，而是为了让重试**无害**。Agent 系统里重执行是常态，把"键 + upsert + 步骤状态"做成默认习惯，才能把"祈祷别出事"变成"假设会出事也没关系"。
