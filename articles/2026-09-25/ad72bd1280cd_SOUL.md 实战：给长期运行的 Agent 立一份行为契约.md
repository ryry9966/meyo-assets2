## 背景

跑 OpenClaw 一段时间后会发现一个规律：MCP、插件、channel 接入这些工具链调通只是及格线，真正决定它"能不能长期用"的，是行为稳定性。默认配置下的模型，语气会漂、时不时过于殷勤，偶尔还自作主张。

OpenClaw 的解法是把人格外置成 workspace 里的一个 Markdown 文件：`SOUL.md`（默认在 `~/.openclaw/workspace/` 下）。每次会话注入 system prompt，随 workspace 走，可以 git 管理。

## 问题

没有 SOUL.md、或者写得太随意时，典型症状：

- 长会话、memory 压缩之后语气漂移，之前约定好的"简洁回复"没了
- 在家人群里用工程师腔，在私密 DM 里絮絮叨叨
- 越权：未经确认就给联系人发消息、执行删除或付费类操作
- 规则散落在各处配置里，改一次全靠翻代码

本质就一句话：人格和边界没有 single source of truth。

## 做法

1. **控制篇幅**。SOML.md 全文压在 50–60 行内。文件越长，每条规则分到的注意力越少。
2. **分四段写**：
   - 身份与语气：两三句，写成可观察的行为，比如"回复默认三句以内，先给结论"；
   - 硬边界（红线）：放文件最顶部。钱、隐私、代替我联系他人、不可逆操作——未经确认一律不做；
   - 冲突优先级：安全 > 用户当前指令 > 长期偏好。写明这一条能省掉大部分纠结；
   - 分渠道语气：DM 一档，群聊一档。
3. **规则要可测试**。"有分寸感"没法执行，"单笔支出超过 50 元先列计划等我确认"可以。
4. **git 管理 workspace**，把 SOUL.md 的每次修改当 code review 做，改了什么、为什么改，写进 commit message。
5. **和其他文件分层**：IDENTITY.md 管名字头像，AGENTS.md 管任务流程，USER.md 管我的偏好。SOUL.md 只管人格和边界，不重复别人的职责。

## 踩坑点

- **写成角色卡**。模型入戏太深，干活时端着。SOUL.md 是行为规格，不是同人设定。
- **负面清单太长**。一串"不要……"模型记不住，还容易互相矛盾。正面指令为主，红线只留最硬的几条。
- **把人格写进 memory 而不是 SOUL.md**。memory 会被压缩，压着压着人格就没了；SOUL.md 每次会话重新注入，这正是它存在的意义。
- **边界引用外部状态**。"我忙就别打扰我"——agent 判断不了你忙不忙，它只能猜。
- **一次改十条**。行为变了你不知道是哪条起效。一次一条，跑一周，攒 case 再迭代。

## 可复用建议

- 模板骨架固定为四段：红线区 → 语气 → 冲突优先级 → 分渠道。
- "一次事故一条规则"：每次翻车后问自己，SOUL.md 里加哪句话能拦住它？
- 接了 MCP / 插件的，把工具调用边界也写进去：哪些工具可自主调用，哪些必须先确认。shell 类默认先确认。
- 每月回看一次，删掉长期没触发的规则，保持文件短。

## 总结

SOUL.md 的价值不在于让 agent"有灵魂"，它是一个运维产物：声明式、可版本化、可回归测试的行为契约。人格只是手段，边界才是目的——你真正在定义的是"这个 agent 永远不擅自做什么"。写短、写具体、当代码维护，长期跑的 agent 才靠得住。
