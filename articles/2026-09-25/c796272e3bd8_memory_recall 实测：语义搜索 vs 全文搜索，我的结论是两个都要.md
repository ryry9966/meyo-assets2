## 背景

`memory_recall` 是 OpenClaw Agent 长期记忆的入口：从 `MEMORY.md` 和 `memory/` 目录的笔记里捞回相关片段，塞进上下文。默认走全文匹配，社区里经常有人问：要不要换成向量语义检索？我把自己跑了两个多月的对比结果整理一下。

## 问题：两种检索各有一类必挂场景

全文搜索（FTS5 / grep / BM25）逻辑是词面匹配：

- 强项：精确命中。错误码、路径、项目代号、人名这类 token 几乎不会漏。
- 弱项：换个说法就抓瞎。当时记的是“部署卡住”，三个月后问“上线失败怎么排查”，词面不重合，直接漏召。

语义搜索（embedding + 向量库）反过来：

- 强项：同义改写、概念关联都能召回。
- 弱项：对专有名词不敏感，“redis 锁超时”可能召回来一堆泛泛的“缓存问题”，真正的条目挤不进 top-5。

另外两个现实约束：每次查询有 embedding 延迟和（走 API 时的）成本；换模型要全量重建索引。

## 做法：混合检索 + RRF 融合

最终方案，也是目前最省心的：

1. **全文检索做基线**。SQLite FTS5，注意中文要换 trigram 分词器（unicode61 对中文基本没用）。
2. **加一层语义索引**。按标题/日期把记忆切块（别把整篇 MEMORY.md 糊进去），每块算 embedding，存 sqlite-vec，本地小模型就够。
3. **查询时两路各取 top-10，用 RRF 融合排序**，输出前按 token 预算截断。
4. **建 30 条左右的评测集**：从自己历史会话里挑“当时该召回却没召回”的例子，每次改检索参数后跑一遍 hit@5。

两周的对比数据（同一评测集）：纯全文 hit@5 约 55%，纯语义约 60%，混合 78% 左右。差距主要来自“换了说法”的查询；而混合方案没有丢掉任何精确命中的 case。

## 踩坑点

- **中文分词**：FTS5 默认 tokenizer 对中文几乎等于整段匹配，噪音大，务必换 trigram 或外挂分词。
- **切块粒度**：一开始按文件索引，召回一大段无关内容，白白烧 token。按条目切，一事一条。
- **embedding 模型变更**：索引元数据里一定要存模型名和版本，否则新旧向量混在一个空间，召回质量悄悄劣化，很难排查。
- **记忆本身的质量**：检索再好也救不了烂笔记。带日期、带关键词标题，召回率提升比换任何算法都明显。
- **小记忆别上向量库**：几十条笔记，grep 确定性好、零依赖、可解释，上向量库纯属过度工程。

## 可复用建议

- 全文检索是底座，永远别拆；语义检索是增量层，不是替代品。
- RRF 是无参融合，比调加权分数省心得多。
- 评测集比任何公开 bench 都真实，用你自己的失败 case。
- recall 输出的 token 预算上限，经常比排序精度更影响体验。

## 总结

语义搜索 vs 全文搜索是个假对立。全文负责“我知道关键词”，语义负责“我忘了当时怎么写的”。Agent 记忆检索的正确姿势是用 RRF 把两者缝起来，再用一套自己的评测集守住回归。先写好记忆，再优化检索，顺序别反。
