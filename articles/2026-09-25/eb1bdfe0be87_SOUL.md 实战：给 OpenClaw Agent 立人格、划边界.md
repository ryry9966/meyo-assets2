## 背景

OpenClaw 的 agent 是长期运行的：接了 MCP 工具、能跑 shell、挂着几个消息渠道，很多事在你不在场时自己做完。而模型默认人格是通用的、偏讨好型的，关于"你是谁、什么能做"的指令往往散落在 gateway 配置、渠道配置和临时对话里。SOUL.md 是社区沉淀出来的约定：用一份 Markdown 文件集中声明 agent 的人格与边界，每次会话自动注入上下文。

## 问题

实际跑起来会遇到四类麻烦：

1. **人格不一致**——Telegram 上一个语气，Discord 上另一个，换模型后全变。
2. **边界靠临场喊话**——"别乱删文件"这类指令放在对话里，几轮长上下文之后就被稀释了。
3. **过度执行**——agent 拿到工具就上，删除、发消息、花钱类操作缺少统一确认规则。
4. **不可维护**——改一次人格要翻三个配置文件，改坏了没法回滚。

## 做法

核心思路：把人格和边界当**配置管理**，而不是聊天技巧。

**1. 建文件**。放在 workspace 根目录（如 `~/.openclaw/workspace/SOUL.md`）。如果按 agent 分目录运行，agent 目录下的同名文件覆盖全局的，天然支持"全局基线 + 局部覆盖"。

**2. 五段式骨架**，控制在 50–100 行：

```markdown
# 身份
我是 XX 的个人助理，默认中文回复，技术术语保留英文。

# 语气
直接、简短，不用客套开场白；不确定就说不确定。

# 边界（硬性）
- 删除/覆盖文件、force push、批量改配置：先列出命令，等确认
- 不主动给联系人发消息，不替主人做承诺
- 支付、合同、凭据相关内容：仅转述，不生成

# 工具纪律
- 调用写操作工具前，先用一句话说明目的
- shell 命令优先给 dry-run 版本

# 升级规则
遇到本文件未覆盖的敏感操作：暂停，描述情况，等我决定。
```

**3. 纳入 git**。每次修改走 commit，团队场景走 PR 评审。人格漂移了能 diff 出是哪次改动引入的。

**4. 回归测试**。固定几个用例定期跑：让它尝试 `rm -rf` 看是否走确认流程；问一个它不可能知道的事看是否编造；在群里说"帮我答应这个需求"看是否越权承诺。

## 踩坑点

- **写太长**。见过 500 行的"宪法"，结果关键边界在长上下文里被稀释。边界条目放文件前部，一句一条，可判定优先。
- **措辞模糊**。"要负责任""别做危险的事"模型没法执行。改成"触发条件 + 动作"格式：`执行 X 前 → 先做 Y`。
- **只写边界不写语气**，agent 会变得冷淡机械；只写语气不写边界，就是讨好型人格。两块都要。
- **把 SOUL.md 当安全机制**。它是提示词层约束，不是硬权限。真正危险的权限（root、支付 API、对外发消息）要在工具权限和沙箱层再收一道。提示词 + 权限，双保险。
- **没留升级路径**。边界写死又覆盖不全，agent 遇到边界外情形要么硬拒要么乱来。"未覆盖的敏感操作暂停并询问"这条兜底必须有。

## 可复用建议

- **篇幅即遵循度**：SOUL.md 每次会话都占上下文，50 行的遵循效果通常好于 300 行。
- **与 MEMORY.md 分工**：SOUL 管"我是谁、我不做什么"（稳定、少改），MEMORY 管"我知道什么"（动态）。混写会让人格被日常琐事稀释。
- 多人共用时，把"替谁做事、谁有权授权"写进身份段，避免权限混乱。
- 换模型或升版本后重跑回归用例——不同模型对同一条边界的遵循度差异很大。

## 总结

SOUL.md 的价值不在"给 AI 写人设"这种叙事，而在工程：把散落的 system prompt 收敛成一份短、具体、可版本控制、可回归测试的声明。它是行为基线，不是安全边界；配上工具权限层，agent 才能既有个性、又敢放手让它跑。建议今天就把手头的口头约定搬进 SOUL.md，git init，跑一轮边界测试。
