## 背景

跑过一段时间 Agent 自动化的都知道，最脆弱的从来不是模型，而是工具链。MCP server 超时、第三方限流、上游 5xx，任何一环出问题，Agent 的整个 turn 就可能卡死或者跑飞。模型本身出错的概率其实不高，错误恢复做不好，大多是因为把「API 会挂」当成了异常，而不是常态。

## 问题

最常见的失败模式有三种：

1. Agent 收到报错后原地重试，参数一模一样，循环到 token 烧完；
2. 原始报错（stack trace、HTML 错误页）直接塞进上下文，模型开始「猜」API 哪里坏了，或者进入道歉式输出；
3. 没有 fallback，一个非核心工具挂掉，导致整个任务中断。

根源是同一个：重试和恢复逻辑写在了 Agent 决策层，而它本来应该下沉到工具调用层。

## 做法

我们的做法是给所有外部调用包一层统一的 tool client，Agent 永远不直接碰 HTTP：

**第一步：错误分类。** 分四类：瞬时故障（超时、502、429）、参数错误（4xx）、认证问题（401/403）、不可恢复（配额耗尽）。只有瞬时故障值得重试。

**第二步：指数退避 + 抖动。** 工具层内部重试 2~3 次，间隔 1s → 2s → 4s 加随机抖动，避免重试风暴。重试发生在 tool client 里，对模型透明。

**第三步：显式超时。** 单次工具调用超时要显著短于 Agent 整体超时，比如单次 10s、整体 60s。别让一个挂掉的 API 拖死整个调度。

**第四步：结构化报错给模型。** 重试耗尽后，返回给 LLM 的不是原始 trace，而是结构化对象：

```json
{
  "error": "upstream_timeout",
  "retryable": false,
  "hint": "try search_fallback or ask user"
}
```

`hint` 字段很关键——它告诉模型下一步有哪些选项，而不是让它自己发明。

**第五步：降级路径。** 每个核心工具预备一个 fallback：备用 provider、本地缓存，或者干脆降级成只读模式。fallback 返回的数据要标记 `stale: true`，别让模型把三天前的数据当最新的用。

**第六步：熔断。** 连续失败 5 次后把该工具标记为不可用，冷却 5 分钟。期间调用直接快速失败，不再打上游。

## 踩坑点

- **非幂等操作千万别自动重试。** POST 下单、发消息这类操作，盲目重试会导致重复执行。写操作必须带幂等键，或者只允许人工确认后重试。
- **原始报错别进上下文。** 一段 stack trace 会诱导模型进入「修复模式」，输出一堆无意义的猜测，白白消耗预算。
- **fallback 要显式告知。** 静默降级是最危险的坑——模型拿着过期数据继续推理，任务看起来「成功」了，结果是错的。
- **恢复期的惊群效应。** API 刚恢复，多个并发 Agent run 同时打过去，又把它打挂。熔断 + 抖动基本能压住。

## 可复用建议

1. 统一 tool client：重试、超时、熔断、幂等键都在这一层做，Agent 逻辑保持干净；
2. 错误对象进上下文，原始 trace 进日志，两边严格分离；
3. 每个写操作都问一句「这个操作重放两次会怎样」，答不上来就补幂等键；
4. 单独记录工具失败日志，定期复盘哪类错误最高频，优先治理。

## 总结

API 会挂是常态，错误恢复不是 Agent 的「高级功能」，而是基础设施。核心原则就三条：重试下沉到工具层、报错结构化并给 hint、降级必须显式。做到这三点，你的 Agent 就能从「一挂就瘫」变成「挂了也能把任务推进完」——这中间的差距，就是工程化。
