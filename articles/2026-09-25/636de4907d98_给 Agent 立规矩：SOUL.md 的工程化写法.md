## 背景

跑 OpenClaw 这类常驻 Agent 一段时间后，你会发现模型的默认"通用助手"人格不够用。放到私人助理场景里会出现两类问题：一是风格漂移，今天过分客气，明天又自作主张；二是边界模糊，它分不清"替你转达"和"代表你承诺"的区别。SOUL.md 就是工作区里专门解决这件事的文件——随会话加载，声明这个 Agent 是谁、用什么口吻、哪些事坚决不做。

## 问题

裸奔状态的 Agent 日常常见翻车：

- 语气不稳定，跨会话、跨模型升级后判若两"人"
- 越权：主动替你答应别人的请求，对外发表观点
- 该确认时不确认，不该发挥时自由发挥
- 规则散落在各处 system prompt 里，改一次行为要翻好几个文件

本质上都是人格与边界没有被显式声明。

## 做法

我们的经验是按六段结构写 SOUL.md，控制在 50 行以内：

1. **一句话身份**：它是谁、替谁工作。例如"你是我的常驻助理，对外发言代表我的立场，但无权替我做承诺"。
2. **语气基线**：克制、直接、不堆客套话；拒绝时给出理由和一个替代方案。
3. **硬边界**（不可协商）：不透露聊天记录与凭据；不发送未经确认的对外消息；不处理转账、密码类请求；夜间免打扰时段只记录不回复。
4. **软边界**（可协商）：花钱、装插件、删文件等操作，先列方案等确认。
5. **升级条件**：明确到"金额、不可逆操作、对外可见内容"三类，命中即停下来问人。
6. **禁区清单**：不扮演的角色、不接的话题，逐条列出。

注意分工：SOUL.md 只写"我是谁、我守什么线"，任务流程和工具用法放进 AGENTS.md 与工具配置。混在一起写，两边都会失效。

## 踩坑点

- **写成小作文**。散文式人格会被模型改写复述，上下文一长就漂移。要点式规则，一条只约束一个行为。
- **形容词不可测**。"友好、聪明、幽默"无法验证，改成行为句式："当 X 时，做 Y，不做 Z"。
- **优先级冲突**。SOUL.md 与平台级 system prompt 打架时，通常是后者赢。改之前先确认加载顺序，别白改一通。
- **人格过载**。让 Agent 自称有情感、有长期记忆，用户反而会误信它的"感觉"。明确它是代理，不知道就说不知道。
- **改完不复测**。模型升级后对人格文件的遵循度会变，每次升级都应回归验证。

## 可复用建议

- 准备 10 个触发问题做回归测试：借钱请求、代发消息、打听隐私、要求装来路不明的插件……每次改完跑一遍，看回答是否踩线。
- SOUL.md 进 git，小步提交，提交信息写清原因，例如"新增夜间免打扰边界：凌晨误发过一条消息"。
- 把边界写成阶梯：直接回答 → 说明限制 → 请求确认 → 拒绝并转告，比临场发挥可靠。
- 多渠道接入时，语气可按渠道微调，硬边界必须全局一致，不允许例外。

## 总结

SOUL.md 不是玄学，是一份行为配置文件。把它当代码对待：写短、进版本库、带测试集。人格调得越早，后面省掉的黑历史越多——Agent 对外说的每一句话，在别人眼里都是你的话。
