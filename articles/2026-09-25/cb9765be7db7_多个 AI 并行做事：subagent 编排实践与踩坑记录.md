## 背景

单 agent 串行干活有两个天然瓶颈：一是慢，抓资料、跑测试、审代码排队执行，一条任务链拖十几分钟很常见；二是上下文污染，调研过程、中间输出、报错日志全堆在一个会话里，越往后 agent 越"失焦"。

OpenClaw 的主 agent 可以把任务拆给 subagent：每个 subagent 拥有独立的上下文和工具集，干完活把结论交回来。听起来像免费的多核，但实际用下来，编排本身就是个工程问题。

## 问题

我最初把"依赖升级调研 + 代码审查 + 测试补齐"这类多线程工作一股脑并行派发，踩了三类坑：

1. **并行写冲突**：两个 subagent 同时改同一个文件，后写的覆盖先写的；
2. **结果膨胀**：subagent 各返回几千字，主 agent 汇总时上下文照样爆炸，等于把污染搬了个家；
3. **隐性依赖**：让一个 subagent 设计 API、另一个写测试，但测试依赖 API 的最终定义，并行只会产出废品。

## 做法

现在的编排原则是"读并行、写分区、层层压缩"：

**第一步，拆任务先分类。** 只读任务（调研、审查、日志分析）可以随便并行；写任务必须按目录或模块分区，一个 subagent 只碰自己的地盘，需要跨区改动就回主 agent 协调。

**第二步，写自包含的任务简报。** subagent 看不到主会话历史，简报必须包含四项：目标、边界（能碰什么、不能碰什么）、输出格式（结论 + 涉及文件路径，限 300 字内）、停止条件。简报质量直接决定产出质量。

**第三步，控制并发数。** 我稳定在 3–5 个。更多不是不行，而是限流、超时重试、结果合并的复杂度会非线性上涨，收益撑不起成本。

**第四步，结果落盘再汇总。** subagent 的完整产出写入指定文件，返回给主 agent 的只有摘要。主 agent 扮演 reviewer 而不是打字员：核对结论、抽查文件、决定下一步派发还是收尾。

## 踩坑点

- 忘了上下文隔离，简报里写"按我们刚才讨论的做"，结果它按自己的理解做；
- 没设最大重试次数，一次网络抖动让编排卡死在循环里——任何派发都要有超时和兜底；
- 把所有 subagent 输出原样贴回主上下文，token 消耗翻了三倍，汇总质量反而下降，压缩必须发生在每一层；
- 并发了不该并行的任务（如上面的 API 例子），返工成本比串行还高。

## 可复用建议

- 优先并行只读任务，其次才是分区写入，流水线式依赖传递最后再考虑；
- 简报模板固定下来：目标 / 边界 / 输出格式 / 停止条件，四项缺一不可；
- 每个 subagent 的产出留一份文件日志，排障时能回放全过程；
- 主 agent 的价值在审查和调度，不在亲自干活——它一旦开始自己改代码，编排就失控了。

## 总结

subagent 并行不是"开多开快"，而是一次上下文管理方式的重构：把隔离、压缩、冲突处理从碰运气变成显式设计。并发数克制一点、简报写清楚一点、结果压缩一层，多数编排问题就消失了大半。欢迎在评论区交流你们的分区和汇总策略。
