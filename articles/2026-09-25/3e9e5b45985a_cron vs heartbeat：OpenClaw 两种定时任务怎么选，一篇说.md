## 背景

OpenClaw 有两条让 agent「自己醒来」的路子：一是 **heartbeat**，主会话默认每 30 分钟收到一次唤醒提示，让 agent 环顾四周，没事就回一句 `HEARTBEAT_OK` 静默掉；二是 **cron**，传统调度器思路，5 段表达式决定触发时间，每次在隔离会话里跑一个独立任务。两者看起来能力重叠，实际定位差别很大。很多人两个都配了，结果是消息噪音满天飞，或者反过来全塞给心跳，token 账单一路上涨。

## 问题

实践里最常见的三个症状：

1. heartbeat 间隔被调到 5 分钟，每次醒来都跑一轮大检查，主会话上下文膨胀，响应变慢；
2. 日报类任务塞进心跳提示词里，九点发一次九点半又发一次，时间点完全不可控；
3. cron 任务依赖上一轮的结果，但隔离会话没有记忆，每轮都从零开始。

根因都是：没分清两种机制的分工。

## 做法

先给结论：**有固定时间、固定产出、需要送达某处的 → cron；「随便看看、有事才响」的 → heartbeat。**

**heartbeat：巡逻岗**

- 频率交给配置文件控制，默认 30 分钟就够，不建议压到 10 分钟以下——每次唤醒都是完整的 LLM 调用，成本与间隔成正比。
- 唤醒逻辑写进工作区的 `HEARTBEAT.md`，只做**只读检查**：有没有没处理的提醒、某个前置条件是否就绪。单次醒来的动作控制在几步以内。
- 没事就原样回复 `HEARTBEAT_OK`，只有这一句会被本地吞掉不推送；写成「今天没啥事」会当普通回复发给用户。
- 成本敏感的话，可以给心跳单独指一个更便宜的模型，主会话模型不动。

**cron：正式班次**

```bash
openclaw cron add --name "早报" \
  --cron "0 9 * * *" \
  --session isolated \
  --message "汇总昨天仓库的 issue 和 PR，十条以内" \
  --announce   # 具体参数以当前版本的 --help 为准
```

- isolated 会话一次一开，互不污染，跑完结果按配置投递到频道。
- 需要状态的任务：把本轮结论写进工作区的固定文件，下一轮先读文件再决策，状态持久化自己做，别指望会话记住。
- `cron list / run / edit / remove` 管理足够日常；一次性提醒类任务也归它，别占用心跳。

## 踩坑点

- **时区**：服务器多是 UTC，表达式照直觉写会差 8 小时，中文用户第一大坑。写之前确认系统时区，必要时在任务里显式指定。
- **HEARTBEAT_OK 必须精确**：多一个字都可能导致消息被推给用户。
- **cron 任务自我重叠**：上一轮长任务没跑完，下一轮已经触发。长任务要么收敛耗时，要么自己加文件锁跳过本轮。
- **心跳干重活**：拉仓库、跑大脚本这类事一律移去 cron 或手动，心跳只做轻量巡检。

## 可复用建议

- 一个稳定的心智模型：**一个主会话心跳 + N 个 cron 任务**，别交叉。
- 让 cron 任务本身承担「检查 + 汇报」，心跳只做兜底——这是进阶用户的常见演进路径。
- 中间结果统一落盘到工作区文件，比折腾任何记忆机制都便宜，且对两种机制通用。

## 总结

heartbeat 是「守望」，cron 是「赴约」。前者轻量、带上下文，适合环境感知；后者精确、隔离，适合确定时刻的任务。判断时问自己三个问题：有没有确定时间？有没有固定产出？需不需要跨轮状态？答案指向 cron 还是 heartbeat，基本就清楚了。
