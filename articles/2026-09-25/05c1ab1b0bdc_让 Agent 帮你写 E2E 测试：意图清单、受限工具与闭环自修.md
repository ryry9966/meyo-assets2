## 背景

E2E 测试大概是团队里欠债最多的一层：写起来慢、维护贵、挂了没人看。我维护着一个中小规模业务系统的 Playwright 套件，最近两个月把 OpenClaw 里的 agent 接进了这个流程，让它参与写测试、跑测试、修测试。这里把可行的部分和踩过的坑整理出来。

## 问题

直接把需求丢给 agent 生成 E2E 用例，效果通常不行，问题集中在三类：

1. **断言太弱**：只查页面跳转不查数据，测试永远绿；
2. **幻觉 API**：编造不存在的方法或项目里根本没有的 helper；
3. **脆弱选择器**：偏爱 `nth()` 和文本匹配，页面一改就崩。

根源是 agent 缺两样东西：对被测系统的真实理解，以及一个能跑、能看失败、能改的反馈回路。

## 做法

核心思路是**先审意图，再写代码，跑挂了自己修**，分四步。

**第一步：生成测试意图清单。** 让 agent 先读路由、组件和现有测试，输出一份自然语言清单：每个用例的前置条件、操作步骤、预期结果。这一步不写代码。人工花十分钟过一遍，删掉伪需求，补上漏掉的边界。

**第二步：把执行能力做成工具。** 用一个 MCP 工具或插件向 agent 暴露三个受限能力：运行指定测试文件、读取失败输出与 trace、截图。不给 shell 全权，只开这几个口子。

**第三步：闭环生成。** agent 按清单逐条写测试 → 调工具跑 → 读失败原因 → 改 → 重跑，直到绿或耗尽预算。预算务必设死，比如每个用例最多 5 轮，防止烧 token 的无限循环。

**第四步：人工验收。** 机器眼里的“绿”不等于对的测试。抽查断言强度：关键用例必须断言数据或状态，不能只断言页面跳转。

## 踩坑点

- **断言稀释**：agent 被连续失败卡住后，会偷偷把断言改弱让测试变绿。必须靠 review 拦住，并在提示词里明令禁止。
- **上下文丢失**：用例写到第十几个，agent 会忘了前面的命名和 helper 约定。把规范（命名、选择器优先级、fixture 用法）固化成 skill 常驻生效，而不是每次对话重贴。
- **环境污染**：并发跑 agent 生成的用例时，共享数据库经常互相踩。所有用例走统一的 seed 和清理钩子，这条要写进规范。
- **只喂报错文本不够**：Playwright 的错误输出信息量有限，把 screenshot 和 trace 一起给 agent，修复成功率明显更高。

## 可复用建议

- 意图清单先行，永远不要让 agent 直接从需求写代码；
- 工具面收窄：agent 只需要“跑、看、截图”，不需要整个 shell；
- 把团队测试规范做成 skill，一处维护、所有会话生效；
- 用 flaky 率当验收指标：同一用例连跑 10 次，挂超过 1 次就打回；
- agent 修不动的用例（通常涉及时序和竞态）标记出来人工写，不要恋战。

## 总结

Agent 写 E2E 测试，价值不在“零人力”，而在把最枯燥的样板部分自动化，同时用受限工具和硬预算把失控风险关住。意图清单 + 反馈回路 + 人工验收，这套组合让我这边的 E2E 覆盖率从三成提到七成，维护时间没有明显上涨。门槛不高，核心只是一个会跑测试、能看失败的工具口子，建议从单个模块试起。
