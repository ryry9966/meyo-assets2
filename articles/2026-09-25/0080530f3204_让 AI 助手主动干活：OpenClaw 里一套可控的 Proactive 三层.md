## 背景

大部分 AI 助手的工作模式是被动式的：你发消息，它回消息，会话结束一切归零。OpenClaw 的架构天然适合打破这个模式——agent 常驻 gateway，可以挂 cron、接 webhook、读写本地文件、调 MCP 工具。换句话说，它有条件在你不开口的时候干活。

但主动 ≠ 定时群发。见过不少配置最后退化成“每天早上八点一条无人在意的摘要”，两周后被静音。这篇帖子记录我在自己实例上跑的 proactive 方案和踩过的坑。

## 问题

动手前先想清楚三件事：

1. **什么时候说**（触发时机）
2. **说什么**（信息密度）
3. **说到哪为止**（动作边界）

最难的其实是第三条。助手主动执行有副作用的操作（发消息给别人、改文件、调用外部服务），出错成本远高于被动问答。所以方案核心是**分级**，不是全开。

## 做法：三层触发 + 一道闸门

**第一层：定时任务（cron）。** 适合需求固定的场景。我的配置：07:30 早报（日历 + 天气 + 隔夜 GitHub 通知汇总）；每周五 17:00 周报草稿。这一层没什么智能，纯粹确定性调度，prompt 只做组装。

**第二层：事件驱动。** hook 挂在具体事件上：git push 后 CI 连续失败两次才提醒、指定目录有新文件落盘时给一次归类建议。关键是**过滤在源头做**——hook 脚本先做条件判断，通过了才构造 prompt 惊动 agent，不要每个事件都触发推理。

**第三层：heartbeat 空闲巡检。** 低频（我设 6 小时一次），用便宜模型做 triage：扫一遍待办、收件箱、长任务状态，产出“候选动作列表”写入状态文件，值得打断的才进下一步。

**闸门：** 所有候选动作过同一个 gating prompt，规则就三条——只读操作可自动执行；可逆操作（发给我自己的消息、写草稿文件）执行后附带说明；不可逆或有外部影响的操作，只生成“建议 + 一键确认”，等我点头。

## 踩坑点

- **heartbeat 频率**：最初设 30 分钟，一天 token 花掉平时三倍，且大部分巡检结论是“无事发生”。降频 + triage 换便宜模型后回到正常。
- **重复打扰**：agent 会反复提醒同一件事。解决：状态文件里存上次通知的 hash 和时间，同 hash 48 小时内不重发。
- **会话污染**：proactive 触发若继承主会话完整历史，上下文迅速膨胀。做法是每次触发开干净的子会话，只注入必要的记忆片段。
- **cron 时区**：gateway 容器跑在 UTC，早报晚了八小时。最低级但最常见的坑。
- **静音设计**：没有 quiet hours 的主动助手会半夜发消息。我设 22:30–07:30 只累积不打断，早报统一带出来。

## 可复用建议

1. 给主动能力定**预算**：每天最多 N 条主动消息，写进 gating 规则，超了就排队合并。
2. 动作分级表固定下来：只读自动、可逆先斩后奏、不可逆必须确认。
3. 每次主动触发落一条日志，每月回看一次，删掉从不触发或总在触发的规则。
4. **先只用 cron 跑两周**，确认信息密度过关，再上事件和 heartbeat。顺序反了会直接劝退自己。

## 总结

Proactive 的价值不在自动化的数量，而在信息到达的时机。三层触发覆盖不同确定性级别的需求，闸门控制噪声和风险。把它当成一个**通知系统设计问题**而不是 agent 能力问题来做，产出的东西才不会在两周后被静音。
