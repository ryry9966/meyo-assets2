## 背景

单个 Agent 串行干活的问题，跑过自动化的人基本都遇到过：让它审查 20 个仓库的依赖，或者把 15 个页面的内容汇总成一份数据，它会一条条做，做一条往上下文里塞一条中间结果。跑半小时是常态，而且上下文很快被临时信息占满，后面的判断质量肉眼可见地下降。

subagent 编排就是为了解决这个：主 Agent 只做拆解和汇总，具体活儿分发给多个子 Agent 并行执行。

## 问题

实际要做对，三件事绕不开：

1. 子 Agent 不共享主 Agent 的上下文，任务描述必须自包含；
2. 并行度失控会撞 rate limit，token 消耗是串行的 N 倍；
3. 子 Agent 的返回如果不加约束，汇总时主上下文照样被塞爆。

## 做法

以 OpenClaw 里典型的并行批处理为例（我拿它跑依赖巡检和日志摘要，模式相同）：

**1. 拆任务。** 主 Agent 把总目标切成 N 个互不依赖的子任务。判据很硬：子任务之间没有数据依赖，任何一个单独失败不影响其他。

**2. 定义输出契约。** 每个子 Agent 必须返回固定结构，比如 `{ "target": "...", "status": "ok|failed", "findings": [...], "summary": "不超过 50 字" }`。这是整个编排里最重要的一条，后面汇总全靠它。

**3. 控制并行度。** 同时跑 3~5 个为宜。超过这个数，一是容易触发 API 限流，二是失败重试时排查成本陡增。用队列调度，完成一个补一个。

**4. 超时和重试。** 每个子任务单独超时（我的经验是 2~3 分钟），超时标记 failed 进重试队列，最多重试一次。不要让一个卡死的子 Agent 拖住整批。

**5. 汇总。** 主 Agent 只读各子 Agent 的结构化结果做聚合，不碰原始过程数据。

## 踩坑点

- **任务描述不自包含**：最常见的失败。写"继续刚才的分析"，子 Agent 根本不知道"刚才"是什么。每个子任务的 prompt 都要当独立请求写。
- **子 Agent 里再开子 Agent**：递归嵌套一时爽，token 烧穿天，深度超过一层后行为基本不可预测。建议硬性只允许一层。
- **返回太啰嗦**：不约束格式时，子 Agent 会返回几百字散文，十个一汇总主上下文直接爆。强制摘要字数。
- **工具挂太多**：子 Agent 一样能挂 MCP 工具和插件，但按需最小化挂载，工具越多走偏概率越大。
- **没有完成判据**："分析一下这个仓库"会跑飞。写清"列出过期依赖和建议版本，没有则返回空数组"。
- **不做用量统计**：不按子任务记录 token，优化无从谈起。

## 可复用建议

- 子任务 prompt 做成模板：目标、输入、约束、输出格式、完成判据五段式，改参数就能复用。
- 结构化输出 > 自然语言输出，永远。
- 并行度当配置项，别写死。
- 先用 2 个子 Agent 小规模验证输出契约，再放量。
- 失败任务的输入单独落盘，方便人工复查。

## 总结

subagent 并行的本质不是"多个 AI 更聪明"，而是把串行执行的两个结构性问题——慢和上下文污染——拆掉。实践中真正决定成败的不是模型能力，而是任务拆分是否独立、输出契约是否严格、并行度是否克制。把这三件事做成固定套路，这套编排可以稳定复用在巡检、批量摘要、批量审查这类场景里。
