# 背景与问题

团队每天都会积累一批原始日志：服务日志、CI 记录、告警事件、agent 会话记录。日报本应是这些信息的压缩视图，但实际操作中通常靠人工翻日志、拼数字，费时且质量不稳定。

最早的偷懒做法是把"读一下日志，写份日报"直接丢给 OpenClaw 的 agent。结果可以预料：总结泛泛而谈、数字对不上账、格式每天漂移、偶尔漏掉最重要的那条告警。根因不在模型能力，而在任务设计——没有分层，也没有约束输出。

# 做法：五层流水线

后来重构成一条五层流水线，核心思想是"确定性的归代码，措辞性的归模型"：

1. **准备层**：脚本按固定时间窗（前一天 00:00–24:00，统一时区）过滤、去重原始日志，归一化为 JSONL，每条带时间戳、来源、级别和一行摘要。纯确定性代码，不经过 LLM。
2. **统计层**：对归一化数据做聚合——错误数 Top N、新增告警、关键耗时分布，产出一个 metrics JSON。
3. **汇报层**：把 metrics 和少量代表性日志片段（不是全量）交给 agent，prompt 中给出严格的 JSON schema，并要求措辞只能引用传入的片段。
4. **校验层**：独立步骤做 schema 校验和数字回查——报告里出现的每个数字都必须能在 metrics 中找到；失败则带错误信息重试一次，再失败降级为只发 metrics 表格。
5. **投递层**：插件把最终 Markdown 写入固定路径并推送摘要到群，同日重跑覆盖而非追加，保证幂等。

schema 大致长这样：

```json
{
  "date": "string",
  "summary": "string, <=120 chars",
  "incidents": [{"name": "string", "count": "number", "evidence": "log excerpt id"}],
  "trends": ["string"]
}
```

# 踩坑点

- **时区**：日志是 UTC，读者在 UTC+8，第一版直接按字符串切日期，跨零点的错误全算错天。时区转换必须在准备层做完，不要指望 agent 判断。
- **上下文爆炸**：最初把全天日志直接塞给模型，token 成本高且总结失真。改成"统计 + 采样片段"后成本降了一个数量级，准确度反而上升。
- **数字幻觉**：让模型自己算比率几乎必错。所有数字由脚本算好，agent 只负责组织措辞。
- **格式漂移**：跑了几天后 agent 开始自创小标题和表情符号，靠 schema 加校验层兜住。
- **静默失败**：流水线挂掉后日报直接缺更，无人察觉。现在生成失败也会推送一条失败通知，缺更即是故障。

# 可复用建议

- 能写死代码的绝不交给模型，LLM 只放在"压缩措辞"这一步。
- 输出必须可校验：schema 校验 + 数字回查是底线，缺了它整条流水线不可信。
- 片段引用制：模型只能引用传入的摘录，能大幅压低幻觉概率。
- 定时任务两件套：幂等 + 失败可见，缺一不可。
- 先跑最小闭环——单一数据源、固定模板，稳定一周后再扩数据源。

# 总结

日报本身不值钱，值钱的是"每天同一时刻、同一格式、数字可信"。这条流水线没有用到任何高深的东西：脚本、MCP 工具调用、一个 schema、一个校验步骤。把结构留给代码，把措辞留给模型，半天就能搭出第一版。
