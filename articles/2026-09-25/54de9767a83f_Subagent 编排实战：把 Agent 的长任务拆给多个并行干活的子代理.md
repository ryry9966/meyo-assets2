## 背景

单 agent 跑长任务的痛点大家应该都遇到过：上下文越滚越长，工具返回的原始数据把主对话塞满，跑到一半模型开始“忘记”最初的目标。subagent（子代理）编排是目前比较务实的解法：主 agent 只负责拆解、派发和汇总，每个子代理持有独立上下文，干完活只回传压缩后的结论。

我们最近在 OpenClaw 里跑的一个真实场景：对 monorepo 的十几个模块做依赖与配置审查。单 agent 顺序执行要耗两轮长对话，中途上下文污染后结论质量明显下降；拆成并行 subagent 之后，主上下文始终干净，整体耗时也降了一半以上。

## 问题

归纳起来是三个：

1. **上下文污染**：一个工具返回 5k token 的日志，主对话基本废掉一半。
2. **串行浪费**：模块之间互相独立，顺序执行纯粹在排队。
3. **单点失败**：一个环节报错，整条链路重来。

## 做法

编排结构保持两层，不建议更深：

- **主 agent（编排者）**：拆任务、写简报、收结果、汇总，自己不碰重工具。
- **子 agent**：各领一份简报，独立上下文，通过 MCP 工具干活，回传结构化结果。

具体步骤：

1. **判断可并行性**。只拆“读多写少、模块间无共享状态”的任务。涉及写文件、发请求的操作，要么保持串行，要么按路径/资源分片，保证单写者。
2. **写任务简报**，固定五要素：目标、输入范围、输出格式（JSON，字段固定：`status` / `findings` / 产物路径）、边界（明确“不要做什么”，比如不要顺手修复）、预算（步数或超时）。
3. **限制扇出宽度**。实测 3–5 个并行是较稳的区间，再多首先涨的是 token 账单，其次才是速度。
4. **结果压缩回传**。子 agent 的执行过程留在它自己的上下文里，主 agent 只收摘要和产物路径。这一条是整个模式成立的关键。
5. **失败隔离**。单个子 agent 失败只重试它自己，主流程接受部分结果，并明确标注哪些模块没跑完。

## 踩坑点

- **子 agent 话痨**：不约束输出格式，它会把整段分析塞回来，主上下文照样爆炸。输出契约必须写死。
- **简报太模糊**：只说“审查一下安全”，子 agent 自由发挥的方向五花八门。边界条件比目标描述更重要。
- **并发写冲突**：两个子 agent 同时改同一文件，后写的覆盖先写的。写操作要么收敛给一个串行 agent，要么严格分片。
- **过度编排**：嵌套三层以上后，调试成本远超收益，目前经验是两层封顶。
- **并行 ≠ 免费**：token 消耗约为串行的 N 倍（N 为并行数），成本敏感的任务先串行验证逻辑，再开并行。

## 可复用建议

- 把任务简报沉淀成模板，五要素缺一项就不派发。
- 结果 schema 全局统一，编排者才能用同一套代码做汇总。
- 所有派发与回传落日志，能回放才能排障。
- 先串行跑通一轮，确认任务边界切对了再开并行——顺序反过来基本必返工。

## 总结

Subagent 编排的本质不是“更多 AI”，而是**上下文管理**：把脏活累活的上下文隔离在子代理里，让编排者始终保持清醒。并行只是顺带的收益，简报质量和输出契约才是决定成败的部分。建议从一个真实的批处理场景起步：两层结构、扇出 3–5、固定输出 schema，稳定跑两周之后，再考虑更复杂的拓扑。
