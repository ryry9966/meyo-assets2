# 背景

大多数人用 Agent 的方式仍然是"提问—回答"：你想起来了才去问，Agent 永远被动。OpenClaw 里有个容易被忽略的机制——心跳（heartbeat）。调度器按固定间隔（默认 30 分钟）向 agent 注入一条心跳消息，agent 收到后去读工作区里的 `HEARTBEAT.md`，按里面的指示决定做什么；文件不存在或无事可做时，它就安静返回。本质上，这个文件就是你给 agent 写的"值班手册"。

# 问题

被动应答有两个缺口：

1. 时间敏感的事没人盯。日志增长、inbox 堆积、定期汇总，靠人记得去问，迟早漏。
2. 用人工轮询替代自动化，等于把 agent 降级成高级搜索引擎。

心跳机制解决的正是"谁来触发"：触发交给调度器，"做什么"写进一个普通 Markdown 文件。

# 做法

1. 确认心跳开启。OpenClaw 默认启用，间隔可在配置里调（`agents.defaults.heartbeat.every`，以你版本的实际字段为准）。
2. 在 agent 工作区根目录创建 `HEARTBEAT.md`，用"触发条件 + 动作 + 汇报策略"的格式写任务：

```markdown
# HEARTBEAT

- 若 ~/sync/inbox 有超过 1 小时未处理的文件：归类并一句话汇报；否则保持沉默。
- 若 error.log 比上次心跳增长超过 10MB：摘录最新 3 条报错发给我。
- 心跳期间禁止修改配置文件、禁止主动对外发消息。
- 无事可做时直接返回 HEARTBEAT_OK。
```

3. 先按默认 30 分钟跑起来，观察一两天，再收紧或放宽间隔。
4. `HEARTBEAT_OK` 是关键：它告诉框架"这次心跳无事发生"，不会给你推送噪音。

# 踩坑点

- **指令太模糊**。"帮我盯着服务器"这类写法，agent 要么每次都汇报制造噪音，要么干脆不动，条件必须可判定。
- **token 成本**。心跳跑在会话里，历史越长、间隔越短，成本越高。保持文件精简，定期压缩主会话。
- **汇报噪音**。每次"一切正常"都会把人训练成忽略推送。默认沉默，有事才说。
- **无人值守的权限风险**。这是模型在你不在场时执行动作，务必用沙箱/权限限制写操作，并在文件里写明禁止事项。
- **心跳不是 cron**。"每天 8:30 整点发日报"这种精确触发，用 OpenClaw 的定时任务更可靠；心跳适合"条件满足就做"的巡逻类任务。
- **静默失效**。机器休眠、进程挂掉，心跳就停了。关键告警仍需传统监控兜底，心跳是补充而非替代。

# 可复用建议

- 每条任务三段式：**条件 + 动作 + 汇报策略**，缺一不可。
- 文件控制在 50 行以内，它每次心跳都会被读一遍。
- 先跑一周"只读"任务（检查、汇总、提醒），确认行为可信后再开放写操作。
- 把 `HEARTBEAT.md` 纳入 git。agent 有时也会自己改这个文件，得能回溯。
- 按频率分层：高频轻量检查放心跳，重活和精确定时交给 cron。

# 总结

HEARTBEAT.md 的价值不在于指令多聪明，而在于它把 agent 从"应答器"变成了"值守进程"。"什么时候该叫我"交给调度器和模型判断，但边界必须由你用一份清晰的文件框住。从一个间隔 30 分钟、只读、默认沉默的任务开始，是成本最低的起步方式。
