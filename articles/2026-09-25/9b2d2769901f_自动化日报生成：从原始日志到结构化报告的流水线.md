## 背景

我们团队维护着十来个服务与仓库，日报长期靠人肉汇总：翻 git log、看 CI 记录、翻聊天记录，再拼成一段文字。信息没大问题，但每天固定消耗 20~30 分钟，且口径因人而异。上个月我们把这件事交给 OpenClaw 的定时任务跑了一条流水线，稳定运行后基本零维护，这里把做法记录下来。

## 问题

"把原始日志直接丢给 Agent 写日报"这条路我们试过，三个硬伤：

1. 原始日志又长又杂，上下文直接爆掉，还容易被截断丢事件；
2. LLM 面对非结构化输入会"脑补"数字，昨天明明 3 个 commit，它能写成 5 个；
3. 输出格式漂移，今天有"风险"章节明天没有，没法对比归档。

结论：让 LLM 做它擅长的事（归纳、措辞），不做它不擅长的事（精确计数、解析）。

## 做法

流水线拆成五段，每段是独立脚本，中间产物落盘为 JSON：

**1. 采集**。用 YAML 配置声明数据源：git 仓库、CI、issue、服务错误日志。每源一个采集脚本（或一个小的 MCP tool），按日期拉取原始事件，输出统一 schema：`{source, ts, type, actor, summary, metrics}`。

**2. 清洗聚合**。纯确定性代码：按时间窗过滤（注意时区）、去重、敏感信息脱敏、每源截断到 top-N，产出 `events-<date>.json`。

**3. LLM 摘要**。把聚合后的 JSON 喂给 Agent，prompt 内嵌固定章节模板（今日进展 / 异常与风险 / 待办）和输出约束。Agent 只做归纳，不接触原始日志。

**4. 校验**。对比报告中的数字与源 JSON（commit 数、失败次数等），检查章节完整性。不通过就带错误信息重试一次，再不通过降级为"原始事件列表 + 机器时间戳"版本，绝不静默跳过。

**5. 分发**。渲染成 Markdown，写入 `reports/2025-xx-xx.md`，推送到 IM 机器人和邮件。文件名带日期保证幂等，重跑覆盖不重复。

## 踩坑点

- **时区与日切边界**：日志是 UTC，我们按东八区 00:00 切，凌晨的提交会跨天。最后在采集层统一转本地时区，并以 18:00 为软截止，避免"日报里没有今天下午的事"。
- **cron 静默失败**：连续两天收到的其实是同一个旧文件。现在分发前检查中间 JSON 的 mtime，超过阈值就在报告头部标注"数据过期"。
- **格式漂移**：LLM 偶尔合并章节或改标题。靠第 4 步校验兜住，比在 prompt 里反复强调"请务必保持格式"有效得多。
- **脱敏遗漏**：错误堆栈里带了内部域名和临时 token，第一次差点直接外发。脱敏规则现在按源配置，并覆盖子进程日志。

## 可复用建议

- 阶段之间用 stdin/stdout 传 JSON，任何一段都能单测、能替换（比如把 LLM 摘要临时换成纯模板渲染）。
- 中间产物按日期落盘，天然支持补跑历史某一天。
- 数据源清单配置化，新增仓库只改 YAML。
- 上线先跑两周"草稿模式"，报告只进草稿频道，人工比对无误后再全自动。

## 总结

这条流水线的核心设计就一句话：确定性的事情交给代码，模糊归纳交给模型，中间用 schema 和校验器把两边焊住。日报只是个出口，同一份事件 JSON 后来还被我们复用去做周报聚合和告警分级。经验是：当 Agent 产出"结构不稳定 + 数字不可信"时，优先怀疑是不是让它直接碰了原始数据。
