## 背景

跑 OpenClaw 一段时间后，你会发现自动化任务很少是"跑一次就结束"的：cron 定时摘要、webhook 触发、频道消息驱动的 agent、MCP 工具调用。这些链路里重试是常态：网关重启、工具调用超时、上游重复投递、人为手动补跑。如果你的任务默认只会执行一次，它迟早会在某个凌晨执行两次。

## 问题

举个常见场景：每天定时把 issue 汇总推到群里。某天模型响应慢，框架超时重试，同一条摘要发了两遍。更隐蔽的还有：日志文件被追加两次、外部系统里多了两条重复记录。这不是 OpenClaw 的 bug，而是自动化系统的固有属性——消息会重投、进程会重启、人会手抖。问题出在任务本身没有幂等性：同一操作执行一次和执行 N 次，最终效果应当一样。

## 做法

核心思路两条：识别副作用，给副作用加去重键。

1. **先分类。** 只读操作（查询、汇总、生成报告）天然幂等，不用管。需要处理的是三类副作用：发消息、写存储、调外部 API。
2. **设计幂等键。** 键要绑定业务语义，而不是执行次数。日报用 `digest-2025-06-07`（按天一个键），而不是 `run-{timestamp}`——后者每次都不同，等于没去重。
3. **用原子操作落键。** 不能"先查有没有，再执行"——cron 和手动补跑并发时，这个检查会双双通过。正确姿势是把"占坑"做成原子动作：SQLite 唯一约束 + `INSERT OR IGNORE`，或 Redis `SETNX`，或文件系统 `open(..., 'x')`。抢到键才执行副作用：

```python
def run_once(key: str, fn):
    if not db.try_insert(key):   # 原子占坑，重复执行直接返回
        return "already done"
    result = fn()
    db.mark_done(key, result)
    return result
```

4. **外部 API 能传幂等键就传。** 不少支付/消息类 API 原生支持 idempotency key，服务端帮你去重，比自己造轮子可靠。

## 踩坑点

- **别指望模型自觉。** agent 上下文重置后，LLM 不记得"昨天发过"。去重必须落在工具/脚本层，比如把"查询是否已执行"做成一个 MCP 工具，而不是 prompt 里的一句叮嘱。
- **键的粒度。** 按天一个键能防重复，但如果一天有多次合法触发，这个键就太粗了。键应该对应"一次业务事件"，而不是"一次调度"。
- **状态和操作不在一个事务里。** 先发消息再落状态，中间挂掉会重复；先落状态再发消息，挂掉会漏发。对发消息这类不可撤回的操作，推荐"至少一次投递 + 接收端按消息 ID 去重"——宁可重复，不要丢失。
- **状态会膨胀。** 幂等记录要有 TTL 或定期清理，不然半年后你的 SQLite 就成了任务坟场。

## 可复用建议

- 封装一个 `run_once(key, fn)` 放公共库，所有插件共用，别每个 cron 脚本自己发明一遍。
- 长任务分段 checkpoint，每段一个幂等键，断点续跑时自动跳过已完成段。
- 用"跑两次验证"测幂等性：上线前手动连跑两次，检查消息条数、数据库行数、文件内容是否只变化一次。这个测试比读代码更有效。

## 总结

幂等不是出错后的补丁，而是自动化系统的默认假设。写任何 OpenClaw 自动化任务之前先问一句：这个任务被调度器、网关或我自己重复触发一次，会发生什么？答案是"无事发生"，才敢放手让它无人值守地跑。
