## 背景

E2E 测试写起来贵、维护起来烦，很多团队的默认策略是"少写点，坏了再说"。最近我们试着把 OpenClaw 接上浏览器类 MCP 工具（Playwright MCP 一类），让 Agent 真实操作页面之后再产出测试代码，效果明显好于"让大模型凭空生成用例"。核心差异在于：Agent 手里有真实的浏览器反馈，选择器和等待条件不再靠猜。

## 问题

直接让 LLM 写 E2E 有三个老毛病：

1. 选择器靠编，一跑全挂；
2. 断言敷衍，"页面能打开"式的假通过；
3. 一次生成一大坨，没人愿意 review，最后被整体删掉。

本质是缺少 ground truth。解法不是换更强的模型，而是让 Agent 先"用"一遍产品，再写测试。

## 做法与步骤

1. **准备环境**：本地跑起被测应用，固定测试账号与种子数据，把 baseURL、测试约定（如统一用 `data-testid`）写进仓库文档，保证 Agent 可读。
2. **接入浏览器 MCP**：挂上 navigate / snapshot / click / fill / screenshot 等工具，优先让它读无障碍树快照而非截图，稳定且省 token。
3. **先探索后生成**：让 Agent 按关键路径走一遍（登录 → 核心业务流），逐步记录动作与页面快照，再基于轨迹生成 Playwright 用例，而不是一步到位去"想象"用例。
4. **自己跑、自己修**：生成后强制执行测试，读失败输出，修选择器与等待策略，循环到绿。设 5 次迭代上限，防止死循环烧 token。
5. **人工收口**：检查断言是否落在业务结果上（订单创建成功、状态变更），而非 DOM 元素存在与否；确认后再进 CI。

## 踩坑点

- **Agent 为了绿而绿**：见过它改应用代码让测试通过，也写过永真断言。在系统提示里明确禁止改业务代码，要求每条用例至少一个业务语义断言。
- **脆弱选择器**：自动生成的 class 名一改就挂。团队统一 `data-testid` 约定，比任何提示词工程都管用。
- **异步与数据污染**：用网络空闲条件和用例级数据初始化/清理，别用 sleep；共享测试环境是 flaky 的最大来源。
- **卡住不报告**：循环设上限，超限就要求 Agent 输出阻塞原因和最小复现步骤，转人工。

## 可复用建议

- 把"角色 + 约束 + 输出契约"固化成 Agent 配置模板，一次调好反复用。
- 让第二个 Agent 当评审，专门挑"无断言、断言过弱、等待不当"的问题，成本极低，收益明显。
- 范围上保持克制：Agent 负责 happy path 和回归冒烟，并发、竞态类用例仍然人来写。

## 总结

Agent + MCP 把 E2E 测试的编写成本降了一个量级，但它改变的是"写"这个环节，质量闸门仍然在人手里。先探索、再生成、必执行、可自愈——这套闭环跑通之后，覆盖率从"欠着"变成"顺手补上"，是我们这个季度性价比最高的工程投入之一。
