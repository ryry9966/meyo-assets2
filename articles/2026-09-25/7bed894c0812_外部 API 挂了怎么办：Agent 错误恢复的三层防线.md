## 背景

Agent 的能力边界基本由外部 API 决定：搜索、地图、消息通道、家庭设备，甚至模型本身。在 OpenClaw 这种长驻的 agent 网关里，工具调用失败不是偶发事件，而是常态——上游限流、证书过期、第三方半夜发版，都可能让一次本来很普通的任务卡死。

我们踩过一轮坑之后，把错误恢复拆成了三层：**工具层、策略层、会话层**。每层解决一个不同的问题。

## 问题：失败的三种坏姿势

1. 插件直接抛异常，整个会话中断，前面的上下文全废；
2. 把 `Error: fetch failed` 这类裸错误文本喂回模型，模型开始自由发挥，编一个看似合理的答案；
3. 没有退避的自动重试，几秒内烧光配额，甚至被上游封 key。

## 做法

### 第一层：工具层——超时 + 结构化错误

每个插件调用必须有超时（我们统一 15s）。失败时不抛异常，而是返回结构化错误给模型：

```json
{ "ok": false, "error_code": "upstream_timeout",
  "retryable": true, "hint": "上游超时，可稍后重试或使用缓存" }
```

模型看到 `retryable` 和 `hint` 才能做出合理决策，而不是对着一句报错瞎猜。MCP 工具同理：把错误码和提示放进 tool result 的文本里即可。

### 第二层：策略层——退避重试 + 降级

- 只对 429 / 5xx / 网络错误重试，4xx 直接判死，别浪费时间；
- 指数退避加抖动，最多 2–3 次；
- 准备 fallback：备用 provider，或带时间戳的最近一次成功缓存。

```ts
for (let i = 0; i < 3; i++) {
  const r = await call({ timeoutMs: 15000 });
  if (r.ok || !r.retryable) return r;
  await sleep(backoff(i) + jitter());
}
return fallbackFromCache();
```

### 第三层：会话层——熔断 + 次数上限

- 连续 N 次失败后熔断，冷却期内直接告诉模型"服务降级，用已知信息回答或询问用户"；
- 给单任务的工具调用总次数设上限，防止模型陷入重试死循环；
- 全量记录错误日志，事后能复盘是哪类故障。

## 踩坑点

- **非幂等接口重试 = 重复下单/重复发消息。** POST 类工具要么做幂等键，要么关掉自动重试。
- **双层重试相乘：** 插件层重试 3 次 × 模型自己又调 3 次 = 9 次请求。重试只放一层，另一层只做超时。
- **抖动不能省。** 多实例同时退避，恢复瞬间会形成同步风暴。
- **别把错误缓存成数据。** 缓存写入前必须校验是成功结果。
- **单进程熔断器对多实例部署无效**，跨实例至少共享一个 Redis key。

## 可复用建议

1. 把上面的错误 schema 定成团队约定，所有插件统一实现，模型侧提示词只写一次；
2. 退避、抖动、重试上限写成公共 helper，不要每个插件各抄一份；
3. 降级话术模板化："当前拿不到实时数据，以下是 X 之前的缓存结果"，比静默失败体面得多；
4. 上线前做一次简单混沌测试：手动断掉上游 API，看 agent 是优雅降级还是当场表演。

## 总结

错误恢复不是 try/catch，而是你的工具和模型之间的一套契约：超时兜住挂起，结构化错误让模型能决策，退避和熔断保护上游，降级保证会话不崩。外部 API 一定会挂，问题只是你的 agent 跟不跟着一起挂。
