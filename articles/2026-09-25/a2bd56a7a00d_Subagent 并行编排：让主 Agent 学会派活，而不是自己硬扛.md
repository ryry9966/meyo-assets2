## 背景

用 Agent 做自动化久了，都会撞到同一个瓶颈：主 Agent 串行干活。比如批量审 10 个模块的代码、同时调研 3 个技术方案、对一批日志做归因分析——它只能一件件来，中间产物还不断挤占主上下文，最后要么跑得慢，要么 context 被垃圾细节淹没，输出质量直线下降。

有了 subagent（子代理）能力之后，解法变得自然：主 Agent 负责拆解和汇总，子代理并行执行具体任务。但“能并行”和“并行得好”是两回事，这篇记录我踩过坑之后沉淀下来的一套稳定做法。

## 问题

实际用起来有三个核心问题：

1. 子代理拿不到主会话的上下文，任务描述不完整就是纯浪费 token；
2. 并发数失控会撞 rate limit，成本跟着爆炸；
3. 子代理输出格式随意，主 Agent 汇总时等于再读一遍原文，编排等于白做。

## 做法

我现在的流程分四步：

**1. 拆任务，写“完整任务书”。** 每个子代理的 prompt 必须自包含：背景一句、目标一句、输入路径/范围、输出格式。默认假设它对主会话一无所知。

**2. 限定产出格式。** 强制子代理按固定结构返回，比如：结论 / 依据 / 涉及文件 / 置信度。这样主 Agent 汇总时是结构化合并，不是自由发挥。

**3. 控制并发。** 我一般压在 3~4 个。够快，也不容易触发限流。批量任务超过这个数就分波次跑，跑完一波再派下一波。

**4. 读并行、写串行。** 子代理只做分析和读取，所有写文件、发消息、调外部服务的动作收回到主 Agent 统一执行。这是避免并行写冲突最省事的一条规则。

## 踩坑点

- **子代理自己再派子代理**，递归失控。我的做法是任务书里明确禁止，并收紧它的工具权限。
- **失败重试无上限**。有一次两个子代理超时后反复重跑，烧了不少额度。现在固定策略：单次失败重试一次，再失败就上报主 Agent 降级处理。
- **汇总 prompt 太随意**。只说“把结果整理一下”，主 Agent 会原样堆砌。改成“对比各结论，指出冲突项并给出你的判断”，质量立刻不一样。
- **子代理顺手改了文件**，和主 Agent 的写入撞车，diff 一团乱。回到“读并行写串行”后彻底消失。

## 可复用建议

- 把每个子代理的 prompt 和输出落盘到本地日志，排障时能完整回放链路，比翻聊天记录靠谱得多。
- 任务书模板化：背景 / 目标 / 输入 / 输出格式 / 禁止事项，五个字段固定，新场景只换内容。
- 并发数按预算定，不按感觉定：先估算单个子代理的平均 token 消耗，乘以并发数，对齐每日额度。
- 让任务可幂等重跑：输入只读、输出带任务标识，失败重跑不会污染已有结果。

## 总结

Subagent 编排的本质不是“开更多 AI”，而是把主 Agent 从执行者变成调度者。任务书写得越完整、输出约束得越死、写入收得越拢，并行就越稳。我的经验是：先让单个子代理在串行模式下跑对一次，再开并行——顺序反过来，你调试的就是烂摊子。
