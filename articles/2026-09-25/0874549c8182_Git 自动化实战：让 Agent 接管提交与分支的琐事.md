# 背景

日常开发里 Git 相关的机械劳动占比不小：写 commit message、按逻辑拆分暂存区、给分支命名、清理合并后的旧分支、补 PR 描述。这些事不难，但频繁、琐碎、容易糊弄。常见的团队状态是——"update"、"fix bug" 式的提交信息满天飞，远端挂着几十个早已合并却没人删的分支。

AI 助手恰好擅长这类"规则明确、上下文清晰、低创造性要求"的工作。OpenClaw 用户大多已跑通 MCP 工具接入，Git 是最适合练手的场景之一：状态可查、操作可控、结果可验证。

# 问题

直接把仓库丢给 Agent，通常会遇到四类翻车：

1. **权限失控**：Agent 拿到完整 shell 后可能执行 `reset --hard`、`push --force` 这类破坏性命令；
2. **状态幻觉**：凭记忆描述工作区，而实际文件早已变化；
3. **拆分不当**：不相关的改动塞进同一个 commit，review 没法读；
4. **规范漂移**：每次生成的 message 风格不一致，等于没规范。

# 做法

核心原则：**先只读后写入，先提议后执行。**

**第一步，收窄工具面。** 接入 MCP 的 git server（或限定目录的 shell 白名单），只放行低危命令，远端操作一律人工执行：

```
允许: status / diff / log / branch / add / commit / checkout -b
禁止: push / reset / clean / rebase / 任何 --force
```

**第二步，把规范写成文件而不是写进对话。** 在仓库根目录放一份约定（如 `AGENTS.md`），写清三件事：commit message 用 Conventional Commits，正文说明 why；分支命名 `feat/`、`fix/`、`chore/`；禁止事项清单。Agent 每次先读这份文件，规范就不会漂移。

**第三步，拆提交走固定流程。** Agent 先跑 `git status` 和 `git diff --staged --stat` 拿全貌，再逐文件看 diff，按"一个 commit 只表达一件事"分组，输出提案：文件列表 + 拟用 message。人确认后逐条执行。这个**提议 → 确认 → 执行**三段式，是所有自动化操作的基本盘。

**第四步，分支治理做成周期任务。** 让 Agent 每周执行 `git branch --merged main`，交叉比对最近提交时间，产出"建议删除清单"供人审批；每天收工前汇总未提交改动，提示哪些该拆、哪些该 stash。

**第五步，顺手生成 PR 描述。** 基于 `git log main..HEAD` 和 diff，按"改动点 / 影响面 / 测试情况"三段输出，贴进 PR 稍作编辑即可。

# 踩坑点

- **大仓库 diff 超上下文**：先看 `--stat`，再按需拉单文件，别一次全量喂。
- **多 worktree / 子模块**：Agent 容易在错误目录执行命令，任务里写死仓库绝对路径。
- **pre-commit hook**：Agent 的 commit 会触发 hook，失败就让它如实报告并修复，禁止 `--no-verify` 绕过。
- **署名策略提前定**：是否接受 AI 参与的提交、要不要在 message 里标注，先写进规范文件，避免事后扯皮。
- **提案与执行之间留时间窗**：提案后如果代码又被改过，必须让它重跑 `status` 再执行，防止拿旧状态当真。

# 可复用建议

- 权限最小化 + 命令白名单是前提，不因为"它很聪明"而放开。
- 一份仓库内的规范文件，胜过对话里的十次口头强调。
- 所有写操作走三段式，删除类操作永远保留人工确认。
- Agent 的每步操作追加写入本地日志，出问题可追溯。

# 总结

Git 自动化不是让 AI 替你写代码，而是把提交拆分、命名规范、分支清理这些**低风险、高重复**的环节交出去。用收窄的权限、书面的规范和三段式确认流程兜底，Agent 能稳定省下每天几十分钟的机械劳动——提交历史也会顺手变得可读。同一套模式可以平移到 lint 修复、依赖升级提交等场景，建议从个人仓库开始练手。
