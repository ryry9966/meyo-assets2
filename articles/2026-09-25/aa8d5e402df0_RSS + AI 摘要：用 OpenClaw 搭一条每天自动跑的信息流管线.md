## 背景

订阅信息这件事，RSS 依然是最可控的方案：格式标准、无算法干预、随时增删。但 RSS 的老问题是"只聚合不筛选"，订阅源一多，未读列表就成了压力源。这篇记录我用 OpenClaw 搭的一条信息流管线：定时抓取 → 正文提取 → 分级摘要 → 每日简报，全程无人值守，跑了两周多，成本和稳定性都在可接受范围。

## 问题

最初的想法很简单：cron 拉 feed，扔给模型总结。实际跑起来发现三个问题：

1. 很多 feed 的 description 只有前两三句，直接摘要等于摘要标题；
2. 订阅源之间互相转载，同一篇文章出现三四次，重复摘要白烧 token；
3. 一次性把几十条丢给大模型，输出又长又空，反而不如自己扫标题。

所以关键不是"接上模型"，而是把抓取、清洗、摘要、分发拆开，每层单独可控。

## 做法

整体分四层，全部落在 OpenClaw 的定时任务和 skill 里：

1. **抓取层**：一个 YAML 配置列出全部 feed 地址，cron 每六小时触发。每条以 entry 的 GUID/链接做主键写入本地 SQLite，天然去重，也方便排查"这条到底抓没抓过"。
2. **清洗层**：对新增条目做正文提取，优先读 feed 自带的 content，不行再回源抓网页跑 readability 类提取；同时按标题相似度粗去重，转载文只保留最早一条。
3. **摘要层**：两级结构。条目级用小模型，单条输入限制在 3k token 左右，输出强制为一句 40 字以内的事实性摘要；日结汇总才用大模型，把当天条目摘要合并成分主题简报，并要求每条结论标注来源编号，方便回溯。
4. **分发层**：简报生成 Markdown 存档，同时推送到常用聊天频道。摘要后附原文链接——点进去是原文，而不是 AI 二手转述。

## 踩坑点

- **正文提取是重灾区**。部分站点反爬或靠 JS 渲染，提取拿到的是空壳。对策：失败时降级用 feed 自带摘要，并在结果里标记"未取到全文"，别让模型对着空内容硬编。
- **摘要幻觉来自上下文太碎**。条目级摘要必须带原文关键句做约束；汇总层只允许基于条目摘要归纳，不允许外推。
- **GUID 并不总是唯一**，个别 feed 更新会复用同一 GUID 换内容。去重键用 GUID + 首次抓取日期更稳。
- **频率过高不划算**。前期每六小时抓一次，token 大半耗在重复内容上。先跑一天统计"新增/重复比"，再决定频率。
- **日结条目太多会漏项**。按 30 条一批先做批次摘要，再合并一次，效果稳很多。

## 可复用建议

- **配置驱动**：feed 列表、模型选择、推送渠道全放配置文件，换机器只迁一个目录。
- **成本分层**：抓取和去重不花钱，初筛用小模型，只有日结用大模型，月成本可以压到个位数人民币量级。
- **把摘要质量当回归测试**：留十几篇历史文章做样例，每次改 prompt 后跑一遍对比，避免越改越差。
- **想接 MCP 的话**：抓取和正文提取可以直接包成两个 MCP tool，agent 侧只负责调度和汇总，边界更干净。

## 总结

这条管线没有用到任何高深的东西，价值在于拆层和克制：每层只做一件事，失败可降级，成本可核算。RSS + AI 摘要不是替你读完所有内容，而是把"从 200 条里挑出 5 条值得读"这个动作自动化掉。如果你也想在 OpenClaw 里跑类似的定时任务，建议从单一 feed 的最小闭环开始跑通，再横向扩源。
