## 背景

AGENTS.md 是 OpenClaw 工作区根目录下的一个约定文件。每次会话启动，它会被整段注入到模型的上下文里，相当于 agent 每天上班前先读一遍的“员工手册”。README 写给人，AGENTS.md 写给模型——受众不同，写法也应该完全不同。

很多人装完 OpenClaw 后对默认的 AGENTS.md 看都不看一眼，结果就是 agent 行为全靠模型默认习惯兜底。其实它是整个工作区里性价比最高的一份配置：改几行 Markdown，就能改变 agent 的行为。

## 问题：没有手册时的典型症状

- **记忆乱放**：该进 MEMORY.md 的长期偏好被写进当天日记，下个会话就丢了；
- **行为漂移**：同一个问题，昨天先查文件再回答，今天直接凭空猜；
- **重复踩坑**：上周口头提醒过“别在根目录堆临时文件”，这周照犯——因为没写下来；
- **越权动作**：没确认就删文件、跑安装命令、往外部发消息。

这些不是模型“笨”，而是它缺少关于这个工作区的先验知识。每个工作区的布局、每个人的偏好都不一样，靠模型猜，不如白纸黑字写下来。

## 做法：一份够用的 AGENTS.md 长什么样

建议围绕五块内容组织，按优先级排：

1. **工作区地图**：各文件的用途和归属——MEMORY.md 放什么、每日笔记放什么、临时文件去哪。给出具体路径示例，比抽象描述有效得多。
2. **记忆策略**：什么值得记（稳定偏好、项目背景），什么不值得记（一次性任务），何时写（会话结束前）。
3. **安全边界**：明确列出需要先确认再执行的操作——删除、付款、对外发送、改系统配置。
4. **工具习惯**：先查证再回答；工具失败时重试几次、重试失败后如实报告而不是编造结果。
5. **会话流程**：开场做什么，收尾做什么（比如“把本次确定的结论写入 MEMORY.md”）。

写法上：用祈使句，一条只说一件事，每条都对应一个可观察的行为。“认真负责”是空话；“回答前先确认文件存在”才是指令。

## 踩坑点

- **写太长**。它每个会话都占上下文，300 行手册的 token 开销和维护成本往往超过收益，控制在几十行以内。
- **和其他文件打架**。SOUL.md 管人格，AGENTS.md 管规程，边界重叠时模型只能自己挑一条听，行为反而更不可预测。
- **写完不改**。它应该像代码一样迭代：agent 每犯一次错，就补一条针对性约束。三个月没动过的手册基本等于没有。
- **堆砌套话**。所有无法被验证为“做了/没做”的句子，都是在浪费上下文预算。

## 可复用建议

- **验证方法**：直接问 agent“你的工作规则有哪些”，看它复述的内容和你的预期差多少，差的部分就是没写清楚的部分。
- **纳入版本管理**：workspace 进 git，AGENTS.md 的每次修改单独提交，行为退化时能回溯到是哪条改动引起的。
- **从默认模板起步**：删掉用不到的，加上自己踩过坑的，不要从零写。
- **定期做减法**：每月通读一遍，删掉已失效或模型已经稳定内化的条目，手册越短越可靠。

## 总结

AGENTS.md 是你和模型之间最便宜、最直接的接口：不写代码、不跑流程，改几行 Markdown 就能约束 agent 的行为。它的价值不在写了多少，而在每条指令背后都有一个真实踩过的坑。把维护它当作与 agent 协作的一部分——它犯错你补一条，它稳定了你就删一条，这份手册才会一直有用。
