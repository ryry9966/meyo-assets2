## 背景

LLM 本身无状态。每次会话结束，模型对"你是谁、你偏好什么"一无所知。对 OpenClaw 这类常驻型助手来说，记忆不是加分项，而是基础设施——没有它，用户每天都在重新自我介绍。常见做法是往 context 塞历史记录，或用 RAG 检索聊天记录，但这两者都解决不了"偏好"这种需要长期沉淀、会变化、有作用域的信息。

## 问题拆解

- **偏好不等于历史。** 用户三个月前说喜欢详细解释，上周嫌啰嗦——聊天记录检索会同时命中两条，且无法判断哪条还有效。
- **偏好有作用域。** 全局（回复用中文）、项目级（这个仓库用 pnpm）、临时（今天别催我）。拍平存储必然出错。
- **写入时机难定。** 靠对话中实时抽取容易过度写入，完全不写则永远学不到。

## 做法

我按四个模块落地：

**1. 分层存储。** 工作记忆（当前会话，结束即弃）；情景记忆（按天归档的会话摘要，OpenClaw 的 daily notes 正好承担这个角色）；语义记忆（结构化偏好条目，核心层）；程序记忆（确认过的工作流，比如"每次部署前先跑 lint"）。

**2. 写入路径。** 两条触发线：显式的"记住…"直接入库，confidence 拉满；隐式的会话后抽取 pass，只保留同时满足"可复用 + 有明确宾语 + 非一次性"的条目。每条记录的 schema：`id / content / scope / source / confidence / created / last_used`。

**3. 读取路径。** 会话启动时按 scope 过滤、相关度排序，取 top-N 注入系统提示，硬性 token 预算（我设 800）。检索命中写日志，方便离线评估"该记的有没有被用上"。

**4. 更新与遗忘。** 新条目与旧条目做相似度比对，高相似且语义冲突时进冲突队列，用一次廉价模型调用裁决覆盖/并存/丢弃，不默认新压旧。加 `last_used` 衰减：长期未命中的记忆降权，90 天未用移入冷存档而非直接删。

## 踩坑点

1. **抽取太贪。** 第一版把"我今天喝了咖啡"都存了，三天 memory 文件就没法看。规则宁严勿松，漏掉的靠显式命令补。
2. **作用域拍平。** 把"项目用 pnpm"存成全局，切到别的项目就开始瞎推荐。scope 必须写入时就定，宁可写错后改，不要混存。
3. **静默记忆最难排查。** 助手行为怪异时，分不清是模型问题还是哪条老记忆作祟。做一个 recall 工具，返回"这次到底注入了哪些记忆"，排查效率完全不同。
4. **没有遗忘机制。** 半年后记忆里全是过期事实，检索层再好也救不回来。衰减和冷存档要一开始就设计进去，后补很痛。
5. **隐私明文。** 地址、密钥类要么不存，要么单独加密并标记 sensitive，且禁止自动抽取触碰这一类。

## 可复用建议

- 记忆做成显式工具（MCP tool 形态：`remember / recall / forget / list`），而不是黑盒魔法。可调试性优先于"智能感"。
- schema 里 `source` 和 `confidence` 第一天就要有，别事后迁移。
- 写入靠规则收紧、读取靠预算收紧——两个方向都要窄，context 比你想的脆弱。
- 定期抽样回放：拿历史会话跑当前记忆配置，人工看注入结果，比任何自动指标都诚实。

## 总结

记忆系统的难点不在"存"，而在"什么值得存、什么时候失效"。显式工具 + 结构化条目 + 作用域 + 衰减，这套组合不复杂，但每个环节都需要克制的规则。先保证"记住的都该记"，再追求"该记的都记住"。
