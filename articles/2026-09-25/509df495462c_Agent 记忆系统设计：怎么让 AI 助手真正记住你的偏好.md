## 背景

Agent 默认是无状态的。每次新会话，模型对"你"一无所知：时区、代码风格、常用技术栈、沟通偏好，全都要重新交代一遍。偶尔问问题无所谓，但如果你把 OpenClaw 当日常助手挂在聊天渠道上跑，重复交代偏好就成了最大的摩擦源。

记忆系统要解决的就是这件事：把"用户是谁、偏好什么"变成可持久化、可检索、可维护的数据。

## 问题：三种常见的失败形态

1. **完全没记忆**：每次重开，体验倒退回裸模型。
2. **一股脑全塞**：对话历史和偏好全堆进 system prompt，token 涨、噪音涨、矛盾也涨，最后模型被过期信息带偏。
3. **过度工程**：上来就全量向量化进库，检索噪声大、链路难调试，出了问题分不清是召回错了还是写错了。

三种我都踩过。结论是：关键不在存储介质，而在分层、写入时机和治理。

## 做法：三层记忆 + 显式写入

**第一层：静态画像（永远注入）。** 稳定事实——身份、时区、语言、核心编码偏好（比如"用 pnpm 不用 npm"、"回复尽量短"）。就是一个手写的小 Markdown 文件，卡在几百 token 内。OpenClaw 工作区里的 MEMORY.md 就是这个角色，对应 MCP 场景里每次注入的 profile。

**第二层：滚动会话记忆（按时间衰减）。** 每天或每会话一条切片，记录"最近做了什么、定了什么"。旧切片定期摘要压缩，超过 N 天自动归档。它负责近期上下文，不负责永久事实。

**第三层：按需检索的归档。** 历史决策、项目细节。不默认注入，而是给 Agent 一个 `memory_search` 工具（用 MCP 包一层即可），需要时自己查，返回条数和相似度阈值都要卡。

写入路径比读取更重要，三步：

1. **显式触发**：用户说"记住：……"时立即写；另外在会话收尾让 Agent 自查"有没有值得沉淀的偏好"。
2. **去重合并**：写入前先搜同类条目，存在就合并更新，新值覆盖旧值，带时间戳和来源。
3. **打标签**：每条记忆标 scope（global 还是某项目）和置信度，只有全局偏好才进第一层。

## 踩坑点

- **只读不写**：Agent 检索很积极，但从不动笔。靠 prompt 约束不牢，建议把写入固化成会话收尾的固定步骤。
- **矛盾堆积**："回答要简短"和三个月后的"可以详细展开"并存，模型随机听一条。合并策略要明确：last-write-wins + 保留历史可回溯。
- **第一层无限膨胀**：画像文件越长越大。我写了个 lint 脚本卡 token 预算，超了就强制整理。
- **作用域泄漏**：项目 A 用 pnpm 的偏好污染了项目 B。没有 scope 标签的记忆系统迟早出这事。
- **隐私**：记忆文件会随工作区同步。API key、密码必须用 deny 模式在写入前拦掉，别指望事后清理。

## 可复用建议

- 先用文件 + grep，别急着上向量库。等"明明记过却搜不到"真实发生再加检索，而且通常关键词召回已经够用。
- 记忆目录用 git 管理，你能 diff"Agent 认为它了解你什么"，也能回滚错误写入。
- 定期做召回抽查：直接问 Agent"列出你关于我的记忆"，人工核对。这比任何自动指标都诚实。
- 让记忆可见可编辑。用户能打开文件改掉一条错误记忆，信任感完全不一样。

## 总结

让 Agent 记住你的偏好，本质是设计一条小数据管道：分层存储（静态画像 / 滚动记忆 / 按需归档）、显式写入触发、去重合并、scope 隔离、人工可审。它不需要炫的技术，需要的是把记忆当数据治理来做——可读、可改、可回滚。先把文件层做扎实，复杂度在真的痛之前都不要加。
