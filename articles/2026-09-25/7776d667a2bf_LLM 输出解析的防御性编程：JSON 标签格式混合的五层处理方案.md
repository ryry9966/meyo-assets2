## 背景

在 OpenClaw 的插件和 MCP 工具链里，让模型输出结构化 JSON 是绕不开的一环：workflow 节点之间传参、插件把结果写回事件流、agent 决策路由，都依赖稳定可解析的输出。理想情况是用 provider 原生 structured output 或 function calling，但实践中经常遇到没有 JSON mode 的自定义端点、走 relay 的第三方模型，或者只认 prompt 约定的老模型。

于是大家都写过类似的 prompt：“只输出 JSON，用标签包裹”。问题在于，这句话的执行率从来不是 100%。

## 问题

线上跑一段时间你会发现，同一个 prompt，模型实际返回的形态至少有五六种：

- 规范的 `<json>{...}</json>`
- Markdown 代码围栏包裹
- 裸 JSON，前后各带一句“好的，以下是……”
- 标签外面套围栏，或围栏里还嵌套围栏
- 尾逗号、单引号、中文全角引号、JSON 里混注释
- 被 max_tokens 截断，只剩半截

任何只处理理想格式的解析逻辑，上线第一天就会挂。

## 做法

我们的方案是把解析做成五层流水线，逐层降级：

1. **约束层**：指令加 few-shot 固定格式，明确“不要输出解释文字”。但默认它一定会违反——这只是降低概率，不是防线。
2. **提取层**：按优先级依次尝试：剥自定义标签 → 剥代码围栏（注意非贪心）→ 都失败则截取第一个左大括号到最后一个右大括号之间的内容。截取策略对“前后带废话”的输出特别有效。
3. **修复层**：用 json-repair / dirty-json 这类宽容解析库处理尾逗号、注释、智能引号。中文场景记得先做全角转半角、去零宽字符。修不好就把解析错误回喂模型重试，**最多重试一次**。
4. **校验层**：pydantic / zod 做 schema 校验，缺字段给默认值或走显式降级分支，绝不裸用 `json.loads` 的结果。
5. **观测层**：记录每次解析走了哪条路径、各格式命中率多少。这是后续调整 prompt 的唯一依据，比感觉靠谱。

提取层核心代码不超过 30 行，关键是分支顺序和兜底。

## 踩坑点

- **非贪心正则截断嵌套结构**：非贪心匹配围栏时，遇到模型在 JSON 字符串里又写了示例围栏，会提前断开。更稳的做法是配对计数围栏，或直接用首尾大括号截取兜底。
- **修复库过度修复**：把损坏 JSON“成功”修成合法但语义错误的对象（比如字段名被吞掉）。所以修复层之后必须有 schema 校验兜底，两层缺一不可。
- **重试失控**：回喂重试不设上限，遇到系统性 bug 就是烧钱死循环。我们固定最多一次，且重试时只发错误片段，不重发全文。
- **换模型格式漂移**：切换模型或升级版本后，包裹格式的分布整个变了。解析分支顺序别硬编码，按观测数据动态排。

## 可复用建议

- 把解析器做成独立模块，收集线上真实失败样本做单测 fixture，比任何 mock 都真实。
- 团队统一一个 JSON 规范化函数（全角转半角、剥 BOM、去不可见字符），中文项目尤其需要。
- 优先级永远是：native structured output > function calling > prompt 约定加防御解析。防御解析是兜底，不是首选。

## 总结

对待 LLM 输出的正确心态和对待用户输入一样：不可信。约束、提取、修复、校验、观测五层各司其职，任何一层都假设上一层会失败。这套东西不炫技，但它决定了你的 agent 是“偶尔挂”还是“基本不挂”。
