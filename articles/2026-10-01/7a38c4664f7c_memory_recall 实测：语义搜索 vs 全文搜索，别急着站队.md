## 背景

OpenClaw agent 跑久了，memory 里会积累大量条目：用户偏好、项目上下文、踩过的坑、常用命令。`memory_recall` 的职责就是在对话时把这些东西捞回来，捞得好不好，直接决定 agent 是“越来越懂你”还是“答非所问”。

社区里最常见的争论是：语义搜索（embedding + 向量召回）和全文搜索（BM25/关键词），选哪个？

## 问题

我们拿几十个真实会话做了对照测试，结论是：两种方案各有明确的失败模式，单选哪个都不行。

- **全文搜索的短板**：用户问“上次那个部署报错怎么解决的”，memory 里存的是“compose pull 超时，加了 quiet 参数后正常”。关键词完全对不上，直接漏召回。
- **语义搜索的短板**：用户问“webhook 重试间隔怎么改”，向量模型可能把“消息队列延迟”这种长得像的条目排到前面，反而把精确写着 `RETRY_INTERVAL=30s` 的条目挤出去。错误码、配置项、命令这类精确 token，语义召回经常丢。

中文场景还有个隐形前提：BM25 不分词基本等于不可用；embedding 模型如果只对英文强，中文查询质量会明显下滑。

## 做法

最终落地的是混合检索，成本不高：

1. **盘点 memory 类型**：事实类（偏好、结论）、标识符类（命令、错误码、路径）、事件类。不同类型对召回方式的敏感度不同。
2. **建双索引**：向量索引按主题切 chunk（200–500 token，带 10–20% overlap）；关键词索引走 BM25，中文用 jieba 分词。两边都带元数据：时间戳、来源、所属 scope。
3. **双路召回 + RRF 融合**：同一 query 同时打两路，用 Reciprocal Rank Fusion 合并排序，取 top 5–8。不需要训练，也避开了两路分数没法直接比较的问题。
4. **元数据前置过滤**：时间衰减、scope 过滤放在融合之前做，省 token 也省排序噪音。
5. **建小评测集**：从真实会话抽 30–50 条 query + 应命中的条目，算 recall@5。这步最重要，所有调参都靠它说话。

结果：混合方案 recall@5 从单路 BM25 约 62% / 单路向量约 71%，提到约 88%（内部数据，仅供参考量级）。

## 踩坑点

- **chunk 切太大**：一条 chunk 塞三个主题，向量排序信号全糊了。
- **BM25 忘了分词**：中文整句进索引，查什么都命中不了，一开始还以为是查询写错。
- **RRF 不是万能**：某一路索引为空或质量极差时，融合结果会被拖累，要监控两路的空结果率。
- **旧 memory 不衰减**：三个月前的过期结论反复被捞回来，agent 一本正经地用错信息。加时间权重或 TTL。
- **top-k 贪多**：k=10 以上明显烧上下文，后面多半是噪音。宁可 k 小一点，配合摘要压缩。

## 可复用建议

1. **别空对空争论**：先从自己的会话日志抽 30 条真实 query 建评测集，数据替你做决定。
2. **起步顺序**：先上 BM25（零依赖、对标识符友好），评测发现意译类查询漏了，再加向量路。
3. **混合 + RRF 是默认答案**：reranker 只在评测证明有增益时再上，别为了架构图好看加组件。
4. **标识符类查询永远保留关键词通道**：这是语义搜索补不回来的。
5. **记录召回失败案例**，定期回灌评测集——检索质量是运营出来的，不是一次性调出来的。

## 总结

语义搜索擅长“意思相近”，全文搜索擅长“一字不差”，agent 的真实查询两种都有。`memory_recall` 的正确姿势不是站队，而是双路召回 + RRF 融合 + 元数据过滤，再用基于自己真实数据的评测集持续校准。先小后大，先便宜后贵，评测说话。
