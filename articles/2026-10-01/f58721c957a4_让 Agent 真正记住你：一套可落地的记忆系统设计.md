## 背景

LLM 本身无状态。你在 OpenClaw 里搭好的 Agent，每次新会话都得重新交代一遍：回答要短、代码注释用中文、部署目标是家里的 NUC……这些偏好散落在历史会话里，Agent 却始终"失忆"。社区常见做法有两类：把所有偏好塞进 system prompt，或依赖会话内上下文。前者随条目增长迅速膨胀，后者换个会话就清零。这里给出一套我们实践过、结构足够简单的记忆系统设计。

## 问题拆解

记忆系统实际要解决四个子问题：

1. 记什么（粒度与结构）
2. 怎么记（提取时机与写入口径）
3. 怎么想起来（召回策略）
4. 怎么纠正（冲突与遗忘）

大多数失败案例不是"没记"，而是记了错的、记了旧的，或者记了一堆噪声。

## 做法

按三层组织记忆：

- **Profile 层**：长期稳定偏好，如语言、代码风格、部署环境。KV 结构，每条带 `source`（用户明说 / 模型推断）和 `updated_at`。
- **Episode 层**：具体事实与事件，如"上周把 CI 迁到了 self-hosted runner"。用于回答"之前聊过什么"，可加 embedding 做语义召回。
- **Working 层**：当前会话状态，不入库，会话结束即弃。

提取放在会话结束后异步做：把对话喂给一个小模型，只允许输出结构化条目（key、value、confidence、source），confidence 低于阈值直接丢弃。写入走统一入口，方便审计。

召回不要全量注入：会话开始只加载 Profile 层；Episode 层按当前任务检索 top-N，相关才进 prompt。

更新规则要明确：同一 key 新值覆盖旧值，保留历史版本；超过 N 天未被命中召回的 Episode 自动降权或归档。Profile 层被覆盖前，建议让 Agent 向用户确认一次。

## 踩坑点

- **记忆噪声**：早期我们把所有推断都写入，两周后 prompt 里全是"用户可能在学 Rust"这类低置信条目，反而干扰回答。对策：推断类必须过 confidence 阈值，并定期清理。
- **旧偏好阴魂不散**：改了编辑器偏好，Agent 仍按旧的推荐插件。根因是只追加不覆盖。对策：key 唯一 + 覆盖 + 留历史版本。
- **提取粒度太粗**：让模型输出"对话摘要"当记忆，召回时几乎没用。记忆条目必须是原子化、可检索的事实。
- **敏感信息入库**：API key、家庭地址曾被写进 Episode。对策：写入前过滤敏感内容，记忆文件不出本机——这也是我们坚持本地 SQLite、不直接接云同步的原因。
- **没有评测**：改了策略不知道有没有变好。我们维护了一个 20 条的回放用例集，每条只问"Agent 是否还记得 X"。

## 可复用建议

- 把 memory_read / memory_write 做成 MCP tool，让 Agent 自主决定读写时机，比纯自动提取更可控。
- 提供"记住这个 / 忘掉这个"的显式指令通道，作为自动提取的兜底。
- 每条记忆永远带 source 和时间戳，排查问题时这是唯一线索。
- 先做 KV，再考虑向量。很多场景根本用不上 embedding。

## 总结

记忆系统不是加分项，而是 Agent 从"玩具"到"日常工具"的分水岭。核心原则就三条：结构化存储、可控写入、明确遗忘。先用最简单的 SQLite + KV 跑起来，再按需引入向量召回，比一上来堆架构有效得多。欢迎在评论区交流你们遇到的具体坑。
