## 背景

OpenClaw 的 agent 不只是一段 system prompt。它的工作区里有一组 Markdown 文件共同构成"这个 agent 是谁"：`AGENTS.md` 管操作规程，`SOUL.md` 管价值与边界，`MEMORY.md` 管记忆，而 `IDENTITY.md` 是其中最短的一个——通常十几行，定义名字、形象基调、称呼方式和语气倾向。

很多人把它当成开箱即用的一次性配置，写完就不再碰。用下来一段时间后，我的结论是：IDENTITY.md 真正的价值不在初始内容，而在你有没有给它建一条"可进化的回路"。

## 问题

靠会话内临时调整身份，有三个实际痛点：

1. 改 prompt 要重开会话，且上下文里的临时约定随长对话漂移；
2. 偏好散落在几十个会话里，没有沉淀，下次新会话全靠运气；
3. 身份、性格、工作规范混写在同一处，改一处动全身，diff 无法审。

## 做法

我把 IDENTITY.md 当代码维护，流程四步：

1. **划清职责边界。** IDENTITY.md 只回答"我是谁"：名字、形象、语气、称呼习惯。"我信什么"留给 SOUL.md，"我怎么干活"留给 AGENTS.md。三者冲突时以 SOUL.md 为准。
2. **每条写成可执行行为。** "聪明、幽默"这类形容词没有约束力。我会写"先给结论，再补一句风险提示；不确定时明说，不编"。行为可验证，进化才有抓手。
3. **建立修订回路。** 在 AGENTS.md 里授权 agent：当发现"用户反复纠正同一件事"时，向 IDENTITY.md 提交一条修订建议（单独的 proposal 区块），我人工审核后合并。相当于给身份开了 PR 流程。
4. **git 管理 + 小步慢改。** 工作区整体用 git 管，每次身份变更一个 commit，写清动机；观察几天，不合适直接 revert。频率控制在月级别，避免人格漂移。

## 踩坑点

- **别写长。** IDENTITY.md 会进每次会话的上下文，超过 30 行后关键信息被稀释，token 也是纯浪费。我卡在 20 行以内。
- **别让 agent 免审自改。** 它会从网页、消息里读到各种内容，无审核写入等于给身份开了注入通道。proposal 只进暂存区，合并必须人来。
- **多渠道要回归验证。** 我同时接了两个 IM 渠道，身份文件只有一份，改完两边都要实际聊几轮，确认语气一致。
- **旧记忆的兼容。** 大改身份后，早期记忆里的称呼和语气会对不上。我会在 MEMORY.md 顶部补一行"自 vX 起称呼变更"，让新旧记录能衔接。

## 可复用建议

- 用 10 行以内的模板起手：name / 形象 / 语气 / 称呼 / 三条行为约束，够用了。
- 变更走"提案 → 审核 → commit → 观察期"四步。一个人用也照走，成本很低，但全程可审计。
- 每月做一次 15 分钟身份回顾：翻 git log，删掉没起作用的条目，比加新条目更重要。

## 总结

IDENTITY.md 本质上是 agent 的"人格仓库"。它的意义不是第一次写得漂亮，而是让身份像代码一样：可版本化、可回滚、可审计，且进化由你把关。把这条回路搭起来之后，agent 会越用越贴合你的习惯，而不是越用越陌生。
