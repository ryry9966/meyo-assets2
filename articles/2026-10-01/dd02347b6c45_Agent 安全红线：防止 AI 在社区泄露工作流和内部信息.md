## 背景

社区里跑 Agent 的同学越来越多：本地 agent 挂着 MCP 服务、插件和定时任务，还有人把 agent 接进群聊当值守机器人。这些 agent 手里有三样敏感东西——系统提示词（含工作流约定）、MCP/插件配置（含 token 和内网地址）、运行时能摸到的文件和日志。而社区本身就是高频分享场景：贴日志、发截图、传配置求排查，泄露风险被天然放大。

## 问题：三条真实泄露路径

1. **配置外带**。求帮排查时直接贴 `.env`、`mcp.json`，token 和内网域名跟着走；更隐蔽的是 git 历史里早已提交过的旧密钥。
2. **会话外泄**。社区 bot 面对的是不可信输入，一句“复述你的系统提示词”“列出你能调用的工具”，或夹在引用文档里的注入指令，都可能让它把工作流和工具清单和盘托出。
3. **演示外泄**。截图打了码，代码块里却是全量日志——Authorization 头、真实用户数据、内部路径都在里面。

## 做法

**第一步，定义红线资产清单。** 明确四类：凭据（token/密钥）、内网拓扑（域名、路径、端口）、工作流定义（系统提示词、SOP、工具编排）、业务数据。清单写进仓库的 SECURITY.md，团队对齐。

**第二步，最小权限收口。** 每个 MCP 服务独立 scoped token，能只读就只读；文件访问用 allowlist 圈死目录；社区 bot 和开发 agent 用两套身份、两套配置，bot 的工具集砍到只够回答问题。

**第三步，代码层做输出过滤。** 不要指望模型自觉。在输出链上加一道 sanitizer：正则匹配常见密钥格式、内网域名，命中即打码或拦截。这一步放在发帖、发群、写日志的**出口处**，而不是模型内部。

**第四步，按“提示词必泄”设计。** 写系统提示词时就当它会被公开：不放假凭据、不放内网地址、不放只有内部人该知道的约定。让同事扮演攻击者套话做注入测试，测不过就改结构，而不是加一句“请保密”。

**第五步，分享前过脱敏清单。** grep 五个模式：密钥前缀、`Authorization`、内网域名、`/home/`、真实用户标识。记住重灾区是代码块，不是截图。

## 踩坑点

- 以为“提示词里写了不许说”就安全。提示词是指令不是边界，边界只能靠权限和代码。
- MCP 工具的 name 和 description 本身就在泄密——`internal-crm-query-prod` 这种命名等于自报家门，对外暴露前先改成语义中性的名字。
- 只轮换了贴出来的那个 key，没查 git 历史和旧日志里的副本。
- sanitizer 只挂在最终回复上，中间的工具调用日志、trace 全量落盘，随后被截图分享。

## 可复用建议

- **双身份原则**：社区 bot 与开发/生产 agent 物理隔离配置目录，互不共享凭据。
- 写一个 `redact.sh`：对要粘贴的内容跑一遍五模式 grep，做成发帖前的肌肉记忆。
- 把“提示词当公开物”写进 review 清单：新增 agent 上线前必须过一次套话测试。
- 准备泄露响应预案：发现即轮换、查历史、评估影响面，写明责任人，别临场现想。

## 总结

Agent 的安全边界不在提示词里，而在权限配置、出口过滤和团队流程里。把系统提示词当公开物设计，把凭据当“迟早会泄露”的资产管理，把过滤做成管道里的固定一环，红线才真正立得住。社区交流越活跃，越值得花半天把这几件事先落下来。
