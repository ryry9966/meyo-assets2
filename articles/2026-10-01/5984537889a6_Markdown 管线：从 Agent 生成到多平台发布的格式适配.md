## 背景

社区里不少人的日常工作流已经变成：让 Agent 写稿、整理文档、生成 changelog，然后手动粘到公众号、知乎、掘金和自己的博客。AI 默认输出 Markdown，但每个平台的"Markdown"并不是同一种东西——公众号只认一小撮内联样式的 HTML，掘金吃标准 Markdown 加特定 front-matter，Hugo 要自己拼元数据。人肉搬运，每次都在重复同样的格式修复。

## 问题

直接拿 Agent 输出发布，通常撞上三类问题：

1. **生成不一致**：同一个 prompt，今天 H1 开头，明天三级标题跳跃；代码块偶尔不带语言标记；链接混着相对路径。
2. **平台约束**：公众号粘贴后 `<pre>` 样式丢失、外链图片被防盗链干掉；`[^1]` 这类脚注语法部分平台不认。
3. **元数据缺位**：标题、摘要、封面、分类这些字段，让 LLM 顺手编的不可靠，又没有统一的生成时机。

## 做法

思路是把管线拆成「收敛 → 规范化 → 适配 → 人工确认」四段，核心是引入一个中间态。

**第一步：源头收敛。** 在 Agent 系统提示里约束输出形态：全文最多一个 H1、层级不跳级、代码块必带语言、链接用绝对路径、不写内联 HTML。注意这只能降低违规率，不能归零。

**第二步：AST 级规范化。** 把 Markdown 当 AST 而不是字符串处理。用 remark 解析成 mdast，跑一组确定性规则：标题层级压平、剥 HTML 节点、补代码块语言、相对链接转绝对。产出一份"规范 Markdown + 元数据"作为唯一中间态。

**第三步：平台适配器。** 每个适配器是纯函数：中间态 → 平台产物。公众号适配器把每个元素转成内联样式 HTML，图片先转存素材库再替换 URL；博客适配器负责拼 front-matter 和 slug；掘金、知乎基本透传，只处理元数据差异。

**第四步：挂进 OpenClaw。** 整条管线封装成 MCP tool，比如 `render_for_platform(platform)`，另加一个 `lint_markdown` 让 Agent 写完自查。渲染与发布分离：产物落盘、出 diff，人确认后再点发布。

## 踩坑点

- **只靠 prompt 管格式必翻车。** 格式约束要落在解析后的校验上，prompt 只是第一道滤网。
- **公众号代码高亮。** 高亮库生成的 class 会被过滤，必须输出内联 style，且 `<pre>` 要处理横向滚动，否则移动端溢出。
- **图片别赌外链。** 非素材库图片随时被干掉，转存一步不能省。
- **表格与长行**在移动端普遍难看，宽表格考虑降级成列表。
- **元数据别让模型顺手写。** front-matter 在管线里用脚本生成或人工填，正文里混入的直接剥离。
- **别在 prompt 里堆几十条格式规则**，挤上下文还不可靠；一条校验-修复循环比十条指令管用。

## 可复用建议

- 中间态思想值得抄：一次规范化，N 个适配器，适配器是纯函数，好测试好回滚。
- 把 lint 规则做成独立插件，任何产出 Markdown 的 Agent 任务都复用同一套检查。
- 保留原始生成物，适配产物放独立目录，方便 diff 和审计。
- 校验不过就走降级：先发博客，其余平台转人工，别让管线静默发出去残次品。

## 总结

多平台发布的痛点不在 Markdown 本身，而在缺少一个稳定的中间表示。规范化、校验、适配拆成独立环节后，prompt 负责降低噪声，确定性代码负责兜底，Agent 才能真正接管从生成到分发的全流程。在 OpenClaw 里，这就是一个 MCP tool 加几个纯函数的事。有同样需求的同学，建议从 lint 规则开始搭。
