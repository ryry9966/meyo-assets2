## 背景

OpenClaw 的 Agent 大部分时间是"睡着"的。要让助手具备主动性——定时汇总、监控告警、消息提醒——先要回答一个基础问题：谁来唤醒它？常见两条路：心跳轮询（heartbeat polling）和事件推送（push）。我们在自己的插件实践里两种都用过，踩了不少坑，这里做个复盘。

## 两种模式的真实差异

**轮询**：Agent 定时醒来，检查待办、消息、状态，没事就继续睡。实现简单、行为可预期，且天然兜底——即使推送链路挂了，下一次心跳也能发现遗漏。代价是每次唤醒都是一次真实的 LLM 调用，token 和延迟都真金白银，而绝大多数唤醒其实"无事可做"。

**推送**：外部事件直接触发 Agent——webhook、消息队列、cron 回调。即时性好、事件驱动精准、没有空转。代价是链路依赖多（网络、回调服务、队列可靠性），事件一旦丢失没人补发，且并发到达的事件需要排队和去重。

## 我们的做法：轮询兜底 + 推送提效

1. **保留低频心跳做兜底**：默认 30 分钟一次，免打扰时段（quiet hours）自动跳过，加随机抖动避免整点风暴。
2. **心跳定义为廉价检查，不是完整对话**：约定轻量 payload（待办计数、未读数、上次检查时间），无事直接短路返回，不进主上下文。
3. **高价值事件走推送**：消息、告警、用户显式触发，走 webhook → 事件队列 → Agent，附带去重键。
4. **失败退避与补偿**：推送失败落队列，下次心跳统一 reconcile，不留事件黑洞。

```yaml
heartbeat:
  interval_minutes: 30
  jitter_minutes: 3
  quiet_hours: "23:00-07:00"
  on_idle: silent        # 无事静默返回
push:
  source: webhook
  dedup_key: event_id
  on_failure: queue_for_reconcile
```

## 踩坑点

- **间隔太激进**：早期设 5 分钟，一天几百次调用几乎全空转。建议 30 分钟起步，按事件量调。
- **空唤醒污染上下文**：某版本心跳无事也回一句"没什么事"，会话记录被刷得很脏。务必让"无事"路径静默返回。
- **推送与心跳并发写会话**：两个入口同时改 session，出现覆盖。统一入口加锁，或事件先落盘、由心跳统一消费。
- **时区问题**：quiet hours 用了 UTC，用户半夜被唤醒。判断静默时段前必须先转用户本地时区。
- **去重缺失**：同一条 webhook 重试三次，助手认认真真回复了三遍。dedup key + 短期缓存是必备。

## 可复用建议

- 心跳是兜底不是主力，主通道尽量事件化。
- 把"唤醒"和"干活"拆开：先做廉价检查，再决定是否升级为完整 LLM 会话。
- 所有事件带幂等键，所有推送有补偿路径。
- 给心跳上指标：唤醒次数、空转率、平均处理时长。空转率超 90% 就该拉长间隔。

## 总结

轮询和推送不是二选一：轮询换来的简单与可靠值得保留，推送换来的即时与省 token 值得引入。务实的架构是**低频心跳兜底 + 高价值事件推送**，同时守住三条底线——幂等、静默返回、并发锁。让 Agent 主动，但别让它为了"主动"而空转。
