## 背景

我们团队每天站会前需要一份汇总前一日进展的日报。数据散在三处：Git 提交、CI 流水线结果、线上服务的关键日志。以前靠人肉拼贴，一份要写二十分钟，还经常漏。接了 OpenClaw 之后，我把它做成了定时流水线：cron 触发 Agent，Agent 通过 MCP 工具采集数据，脚本预处理，LLM 只负责最后的摘要，成品推到群里。跑了三个月，基本稳定。

## 问题

直接让 Agent"读日志写日报"是不行的，三个硬伤：

1. 原始日志噪音大、格式不统一，一天的量轻松超过上下文窗口；
2. LLM 面对原始文本容易幻觉——把失败的构建总结成"部分成功"这种事真实发生过；
3. 流水线本身会挂，静默失败比不出日报更糟。

## 做法

整条流水线分五步，核心原则是：确定性的活交给脚本，LLM 只做摘要。

**1. 定时采集**：OpenClaw 的 cron 任务每天 09:00 拉起一个 Agent 会话，调用三个 MCP 工具：git log（时间窗口参数化）、CI API 查询、日志文件读取。采集结果落盘为 JSON，作为中间产物保留。

**2. 脚本预处理**：一段 Python 做脏活——过滤 health check 噪音、按服务聚合错误计数、提交按仓库分组、时间戳统一到本地时区。输出是紧凑的结构化中间态，通常只有几千 token。

**3. LLM 结构化摘要**：给 Agent 一个固定的 JSON Schema（字段：昨日完成、进行中、风险、待确认），要求只输出符合 Schema 的 JSON。带校验的重试：不过就把错误信息喂回去重试，最多三次。

**4. 模板渲染**：JSON 填进 Markdown 模板，附数据来源和时间戳。纯字符串操作，不涉及模型。

**5. 投递与兜底**：插件推送到 IM webhook，带幂等键（日期 + 运行 ID），重试不发重。若任一数据源不可达，日报顶部显式标注"数据不完整"，而不是装作正常。

## 踩坑点

- **别让模型直接读原始日志**。第一版偷懒跳过预处理，token 爆掉不说，摘要还时常编造细节。预处理脚本是整条链路里最值得写的一环。
- **时区**：cron 按容器时区跑 UTC，日志却是本地时间，第一天统计的是"前天下午到昨天下午"。所有时间窗口显式传参，别依赖默认值。
- **Schema 漂移**：模型偶尔自作主张加字段或改键名。靠 JSON Schema 校验加重试兜住，目前校验失败率约 2%。
- **静默空报告**：有一次数据源 token 过期，日报照发但内容全空，没人发现。之后加了两条断言：采集条目数非负且各源可达性检查通过，否则告警而非照常投递。
- **重试导致重复推送**：webhook 超时后重试，同一天发了两份。加幂等键解决。

## 可复用建议

1. 每个阶段给独立 CLI 入口，能单独跑、单独测，调 Schema 时不用等 cron。
2. 中间产物全部落盘，出问题可回放排查，也方便审计"报告里这句话哪来的"。
3. 把流水线当生产服务对待：有自己的日志、失败告警和幂等设计，而不是一个"跑着的提示词"。
4. 摘要环节用低成本模型足够，瓶颈在预处理和投递的可靠性上。

## 总结

这条流水线的价值不在"会用 LLM 写日报"，而在边界划分：脚本管确定性，LLM 管语言，校验和断言管可靠性。OpenClaw 在这里的角色是调度器和工具总线，真正的工程质量都在流水线自身的纪律里。如果你也有定时汇总类需求，建议先画清"哪些步骤不允许模型参与"，再动手。
