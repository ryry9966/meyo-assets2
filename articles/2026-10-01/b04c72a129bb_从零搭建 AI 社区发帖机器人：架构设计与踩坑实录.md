## 背景

社区的“每周精选”过去全靠人工：翻讨论区、挑主题、写摘要、排版发帖，每期一到两小时，还经常拖更。于是用 OpenClaw 搭了个发帖机器人：定时抓取本周讨论和仓库动态，自动汇总成草稿，确认后发布。目标不是全自动无人值守，而是把人工压缩到“审一眼、点一下”。

## 问题

拆开是四件事：

1. 数据从哪来：论坛 API、GitHub Release、Issue 列表，格式各异；
2. 内容怎么生成：要稳定、可引用、不编造链接；
3. 怎么发出去：社区 API 有鉴权和频控；
4. 怎么不翻车：重复发帖、格式错乱、静默失败都得可发现。

## 整体架构

核心思路是把“生成”和“发布”拆成两段：

- **触发层**：cron 定时拉起 OpenClaw agent 任务；
- **采集层**：三个 MCP 工具（fetch_forum / fetch_repo / fetch_issues），只取数，返回结构化 JSON；
- **生成层**：agent 按 prompt 模板产出固定 schema 的草稿（标题、正文、来源 ID）；
- **发布层**：一个极薄的 MCP 工具 post_article，只做鉴权、校验、提交，不含任何“智能”；
- **状态层**：SQLite 记录内容 hash、发布状态和运行日志。

## 实施步骤

1. **先写发布工具**。用一段硬编码内容跑通鉴权与发帖，摸清社区 API 的字段要求——我们论坛的 Markdown 是方言，代码块语法和标准不同，这里就踩过坑。
2. **再写采集工具**。每个工具独立调试，用真实数据核对返回字段；抓不到的字段宁可不返回，不留空占位。
3. **写生成 prompt**。硬性约束：只允许引用采集工具返回的内容；输出强制 JSON schema；链接一律不生成。schema 校验不过就重试。
4. **接状态层**。发布前对正文取 hash，命中已发记录直接跳过。
5. **先人工确认**。草稿推到内部频道，回复确认才发布；稳定运行四周后才放开自动发布，且保留每周抽样复核。

## 踩坑实录

- **编造链接最阴险**。早期版本的摘要里出现过一条看着完全合理、实际 404 的引用链接。解法是把链接从生成层彻底拿掉：正文只写来源 ID，发布层查表替换成真实 URL。模型负责组织语言，不负责提供事实。
- **重试导致双发**。post_article 超时后 agent 自动重试，同一帖子发了两条。社区 API 不支持幂等键，只能在客户端兜底：同一 hash 在十分钟内拒绝二次提交，超时后先查询再决定是否重发。
- **token 过期静默失败**。鉴权 token 两周过期，日志只有一行 401，机器人看起来“正常跑完”但什么都没发。后来给每次运行加了结构化日志和结束摘要（抓取数、草稿数、发布数与失败原因），异常才可观测。
- **时区错位**。cron 按 UTC 跑，“本周”边界差了八小时，周五晚的讨论被漏掉。统一在采集工具里按本地时区切时间窗口，不靠 prompt 描述时间。

## 可复用建议

- 发布工具越笨越好，所有判断放在生成层和状态层；
- 外部事实一律走工具取数，模型只做组织与摘要；
- 幂等靠 hash，不指望 API；
- 新机器人先人工确认、后自动化，别一步到位；
- prompt 和 schema 进版本库，改动能 diff、能回滚。

## 总结

整个机器人不到六百行，大部分工作量花在约束和兜底上，而不是让生成更“聪明”。一句话总结：发帖机器人难的不是写出内容，而是让每一次发布都正确、可追溯、可叫停。先把失败路径设计好，才敢把自动化交给它。
