## 背景

社区运营里最耗时的不是发帖，而是攒素材、查链接、想标题。我维护的几个技术群每天沉淀一批值得讨论的链接和 issue，但手工整理成帖子，坚持不过两周就会断更。于是用 OpenClaw 搭了一个"定时采集 → 生成草稿 → 人工确认 → 定时发布"的发帖机器人。目标很克制：不追求全自动，先保证每条发出去的内容可信、不重复。

## 问题

最直接的写法是让 Agent 每天定时跑一次、直接自动发帖。试验两天就放弃了，踩到的坑：

- 模型会"凭记忆"补链接，抽查发现三成是失效甚至不存在的 URL；
- 同一主题隔几天被再讲一遍，读者敏感度比想象中高；
- 触发失败、接口限流时没有重试策略，直接漏发；
- 语气漂移：几轮迭代后帖子风格开始像营销号。

结论：发帖这种有外部副作用的动作，必须有人审、有状态、可回滚。

## 做法

最终架构分五层，全部是可替换模块：

1. **触发层**：gateway 的 cron 任务，每天两个时段各跑一次。时间统一存 UTC，渲染时再转本地时区。
2. **采集层**：自写一个 MCP server，暴露 `fetch_rss`、`list_community_issues`、`get_thread_summary` 三个工具。关键约束是 Agent 只允许引用工具返回的 URL。
3. **草稿层**：Agent 按固定模板生成草稿（摘要、链接、一句话点评），temperature 压到 0.3，prompt 里固化三篇历史范文做 few-shot。
4. **审核层**：草稿推到私人频道，回复确认发布、否决丢弃、带参数修改后发布。未过审的草稿进 24 小时暂存区，次日重新评估。
5. **发布层**：一个薄插件负责调社区 API。发布前对正文算 hash 去重、对标题做相似度比对；失败则指数退避重试三次，仍失败写入待办表等人工处理。

状态全放一个 SQLite：已发 URL、草稿、审核记录、失败任务。出问题基本靠这张表回溯。

## 踩坑点

- **链接幻觉**：光在 prompt 里写"不要编链接"没用，改成工具级约束（只有 tool result 里的 URL 可引用）后才归零。教训是约束要放进机制，不是放进语气。
- **去重粒度**：只查 URL 不够，同一篇文章换追踪参数就是两条记录。规范化 URL（去 utm、统一大小写）后大幅好转。
- **时区坑**：cron 按服务器 UTC 跑，定时帖出现时间整体偏移八小时。所有时间一律存 UTC 再显式转换。
- **重试风暴**：限流时无脑重试把配额打穿。改成指数退避加随机抖动，上限三次。
- **上下文膨胀**：原始网页全文直接喂模型，token 烧得快且质量反降。先在 MCP 工具内做正文抽取和截断，只给摘要级内容。

## 可复用建议

1. 有外部副作用的动作一律先走人工审核，跑稳一个月再谈自动化。
2. 约束放在工具和机制层（白名单、schema 校验），prompt 只是补充。
3. 每个发布动作都要幂等：同一 hash 不发第二次。
4. 失败策略宁可"不发"也不要"乱发"，fail closed。
5. prompt、草稿、审核决策全部落日志，复盘价值远超预期。

## 总结

上线六周，发帖从每天 40 分钟降到 10 分钟审核时间，漏发为零。真正的工作量不在"让 AI 写帖子"，而在状态存储、去重、重试、审核流程这些朴素的部分。下一步计划把审核反馈回流到 few-shot 样本，让语气漂移能自动收敛。代码整理后单独开帖，欢迎踩过同类坑的补充。
