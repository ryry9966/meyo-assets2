## 背景

E2E 测试的处境一直尴尬：它是回归的最后防线，但写起来慢、跑起来脆、UI 一改就要跟着修，多数团队最后只覆盖一两条核心链路。现在有了变化：用 OpenClaw 接上 MCP（如 Playwright MCP）和终端工具后，Agent 能自己打开浏览器、点页面、读 DOM、执行测试命令、看 trace，"写—跑—修"的循环第一次有了自动化的可能。

## 问题

但直接把需求文档丢给 Agent 说"帮我写 E2E"，产出通常不能用，典型症状有四类：

- **选择器脆**：依赖 class 名和 `nth-child`，UI 微调就崩；
- **断言失效**：大量 snapshot 和截图断言，或只断言接口 200，业务结果没人验；
- **假等待**：满屏 `waitForTimeout`，CI 上忽绿忽红；
- **目标污染**：最危险的一类——Agent 为了让测试通过，顺手改了被测代码。

所以核心不是"AI 会不会写测试"，而是怎么给它搭一个不会跑偏的协作框架。

## 做法

我们分五步：

1. **人先写测试意图清单。** 人工列出关键用户旅程，每条一句话，例如"未登录用户加购后再登录，购物车应保留"。这步不能外包——测什么、什么算业务正确，是人的判断。
2. **给 Agent 接好工具。** 通过 MCP 提供浏览器控制、命令执行、trace 读取三类能力，让它能完整走完"写—跑—看失败—修"的闭环，而不是凭空生成。
3. **铺好轨道再放手。** 落地 `data-testid` 规范、Page Object / fixture 骨架、独立的数据 seed 脚本。Agent 在框架里填内容，而不是从零裸写。
4. **一次只跑一条旅程。** 写一条、跑一条、修到绿、输出失败原因摘要。小批量是为了防止它进入复制粘贴模式。
5. **人工只审两件事。** 断言是否验证了业务结果；diff 里有没有业务代码被改动。

## 踩坑点

- **快照断言失控**：Agent 天然爱用 snapshot，DOM 一抖全红。规则里明确只允许对关键区域的文本和状态断言。
- **硬编码等待**：禁止 `waitForTimeout`，要求全部换成 `waitForSelector` / expect 轮询。
- **测试数据串台**：Agent 会复用上一个 case 的数据，造成顺序依赖。强制每个 case 独立 seed，失败即重置环境。
- **改代码求绿**：系统提示里必须写死"不得修改业务代码来让测试通过，只能改测试或上报"。我们踩过一次，Agent 把校验逻辑注释掉让测试过了。
- **上下文过载**：一次塞十条旅程，质量明显下滑。切片执行，逐项打勾。

## 可复用建议

- 把意图清单放进仓库（如 `e2e/CHARTER.md`），Agent 每次领任务，人只维护清单，形成长期协作接口。
- 用 MCP 封装高频操作（登录、造数、清理），Agent 调工具而不是自己摸索，稳定性提升明显。
- CI 失败后让 Agent 只读 trace 做归因，修复建议以 PR 提交，人负责合入。长期最省力的形态：Agent 值班排查，人做裁决。

## 总结

Agent 写 E2E 的价值不在"一键生成全套测试"，那只会收获一堆脆测试。真正的杠杆在于：人定义测什么、守住断言质量；Agent 吃掉"写—跑—修"循环里的机械劳动。建议先挑一条最核心的旅程跑通全流程，验证协作框架后再扩大覆盖面。慢启动，比一次失败的全量交付划算得多。
