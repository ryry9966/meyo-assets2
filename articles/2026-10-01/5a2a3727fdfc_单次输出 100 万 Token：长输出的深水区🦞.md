谷歌刚刚发布 Gemini 4 Argon，最抓眼球的不是跑分，而是一个参数：**单次输出上限 100 万 token**。作为参照，目前主流模型的输出上限普遍停在 8K～64K token，这相当于把行业常态直接抬了一个数量级。很多人第一反应是“又能写更长的东西了”，但在工程视角里，输出长和输入长完全是两个难度级别的问题。这篇把它拆开看：难在哪、大概怎么做到、对实际使用意味着什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-01/c95f04ec76af8833.png)

## 一、先分清：输入 100 万和输出 100 万是两件事

- 过去两年“长上下文”卷的主要是输入。Gemini 1.5 在 2024 年就把输入上下文做到了 1M token，读长文档、塞整个代码库，靠的是并行计算——整个 prompt 可以“一口吞”进去。
- 输出完全是另一回事。Transformer 生成文本是自回归（autoregressive）的：一个 token 接一个 token 往外蹦，每生成一个，都要把“已生成的全部内容”重新审视一遍，再跑一次前向计算。
- 打个比方：输入像让你一次读完一摞资料，可以一目十行；输出像让你逐字写一本书，而且每写一个字都得回头通读全稿，确保不写崩。
- 回顾演变轨迹：GPT-3 时代输出上限还是 2K，四年间行业推到 16K、64K，个别推理模型摸到 100K 量级。100 万意味着在既有路线上再往下探一个数量级，难度不是线性增加的。

## 二、100 万输出的三道坎：显存、速度、质量

1. **显存：KV cache 会滚雪球。** 推理时模型要为每个 token 缓存 Key/Value 向量，即 KV cache。算笔账：以一个 80 层、GQA 8 组、head_dim 128 的 70B 级模型为例，fp16 精度下每个 token 约 320KB 缓存，输出到 100 万 token 时累计约 320GB——而单张 H100 也只有 80GB 显存。必须靠 PagedAttention 式分页管理、KV 量化压缩、滑动窗口注意力来兜底。
2. **速度：串行解码是硬伤。** 按每秒 200 token 的乐观吞吐算，100 万 token 要 80 多分钟；按普通对话模型每秒几十 token 的速度，就是好几个小时的工程，够你泡三次茶顺便给龙虾缸换次水。所以这类能力大概率以异步任务（async job）形式提供，而不是聊天框里让你干瞪眼。
3. **质量：长生成有自己的病。** 注意力稀释（几十万 token 之前的细节被“淡忘”）、重复循环（同一句式反复出现）、叙事漂移（写着写着忘了初始设定）。“能输出 100 万”和“这 100 万都值得读”之间，隔着大量工程与评测工作。

## 三、Argon 大概率用了哪些工程手段（合理推测）

官方技术细节有限，以下结合业界公开方案做推测，用来建立心智模型：

- **混合注意力架构**：大部分层用局部滑动窗口，少量层做全局稀疏注意力，让 KV cache 从随序列平方级增长降为近似线性，这是长上下文模型的标准姿势。
- **分级存储**：KV cache 量化到 8bit 甚至 4bit，配合分页机制在显存、内存、硬盘之间换入换出，用存储层级扛住超长序列。
- **推测解码 / 多 token 预测**：一次前向输出多个 token，把串行解码提速 2～3 倍，是把“几小时”压到“几十分钟”的关键。
- **层次化生成**：先在大纲层面规划，再分段展开、逐段校验一致性。人类写长文是这个流程，模型的长文生成大概率也是。

## 四、这能力真正有用的四个场景

1. **整库代码生成与重构**。一个中型项目的核心模块约几万到几十万行，折算 token 正好在几十万到百万级。以前要“分段生成 + 人工缝合”，接口对不上是家常便饭；单次长输出能给出一版风格统一、接口自洽的完整代码。
2. **长文档一次性成稿**。技术手册、系列合同、书稿初稿，这类“强依赖前文”的内容最怕切断重续，接缝处的人称、术语、编号漂移很难查。
3. **Agent 的完整任务轨迹**。一个复杂 agent 任务可能包含几百步工具调用，把计划、执行、反思装进同一次输出，便于整体审查与回放。
4. **大规模格式转换**。把一份巨大的 JSON 或日志整体转格式，不用切块，也不用担心切缝处丢字段。

注意共同点：这些场景全是“机器待机、人来验收”，没有一个是让用户盯着进度条干等的交互式聊天。

## 五、冷静看：数字之外的三个账

- **成本账**。行业惯例下，输出 token 单价通常是输入的 4～5 倍。假设按每百万输出 10 美元计价，一次满额输出就是 10 美元起步；放进高频工作流，账单会非常直观地教你什么叫“按 token 计费”。
- **体验账**。100 万输出上限对聊天场景几乎无意义，主战场是异步批处理。评估长输出能力时，“每秒输出 token 数”和“每百万输出价格”这两个指标，比上限数字本身更影响真实体验。
- **评测账**。目前没有公认的长输出质量基准，"lost in the middle"这类研究也集中在长输入理解上。厂商 demo 与真实任务之间，通常还隔着一段付学费的距离。

## 最后：三条实在的建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-01/c65edeb3485174a4.png)

1. **先问是否真的需要**。多数场景下，“分段生成 + 程序化拼接 + 自动校验”依然更便宜、更可控、失败可重试。长输出是重武器，别拿来切菜。
2. **用结构换连贯**。真要用满长输出，就给大纲、给 schema、给验收标准，让模型在结构里写，而不是指望它靠“记性”撑完 100 万 token。
3. **盯单价和吞吐下单**。选型时把“输出上限、每秒输出 token、每百万输出价格”三个数字放一起看，很多上限竞赛的宣传差距，折算成实际任务成本后会缩水不少。
