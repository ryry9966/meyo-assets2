## 背景

Agent 系统的可靠性，往往不取决于模型本身，而取决于它调用的那十几个外部依赖。OpenClaw 生态里的 MCP server、插件、Webhook 自动化，本质上都是对第三方 API 的封装——对方挂了、超时了、限流了，Agent 就得面对“下一步怎么办”。这块处理不好，前面编排得再漂亮也白搭。

## 问题长什么样

实际跑起来，故障通常以三种面目出现：

1. **请求超时/连接失败**：工具调用直接报错，Agent 拿到一串异常文本。
2. **返回非预期内容**：API 返回 200 但结构变了，或返回一段 HTML 错误页，解析层先炸。
3. **部分成功**：写操作发出去了，响应丢了。Agent 以为失败，重试一次，订单或消息就重复了。

更麻烦的是 Agent 层面的连锁反应：模型拿到报错后倾向于“再试一次”，没有上限地重试；或者更糟——把空结果当成功，编一段“已完成”回复给用户。这两种都比故障本身更伤信任。

## 做法：三层防线

**第一层：连接器层，重试受控。** 不要让 LLM 决定重试策略，把重试做在工具封装里。区分错误类型：4xx 参数错误不重试；429 先读 `Retry-After` 头再等；5xx 和网络错误用指数退避加随机抖动，上限 2~3 次。超时时间单独设，别让一次调用卡死整个循环。

**第二层：Agent 层，把错误说清楚。** 工具失败时不要抛裸异常，返回结构化错误对象：错误码、是否可重试、人类可读的原因。模型看到 `"retryable": false` 会倾向于换路径或如实上报；看到裸 traceback 则容易瞎猜。这一条实现成本极低，收益最大。

**第三层：流程层，降级与断点。** 长任务先落盘状态（哪些步骤已完成），失败后从断点续跑而不是从头来。关键写操作尽量幂等——带请求 ID，让服务端能去重。连续失败达到阈值就熔断，升级给人处理，别让 Agent 在死路上反复烧 token。

## 踩坑点

- **对写操作盲目重试**。读操作重试无所谓，POST 类操作没做幂等键就是事故。超时不等于失败，可能是“成功了但响应没回来”。
- **把错误吞掉返回空结果**。模型会把空数组当真数据继续推理，产出看起来合理、实则全错的结论。
- **重试策略写进 prompt**。“失败了重试三次”这种指令不可靠，模型不一定执行，也不该由它执行。
- **退避没有抖动**。几百个实例同时重试，等于帮对方完成了一次自愈式 DDoS。
- **降级路径没测试**。缓存兜底数据过期三个月没人发现，直到用户来问。

## 可复用建议

- 做一个统一的工具错误信封（code / retryable / message / hint），所有 MCP 工具和插件都套用它。
- 重试次数、超时、熔断阈值全部配置化，别硬编码。
- 每次调用记 trace ID，日志能把“模型决策”和“底层错误”对上，排障效率完全不同。
- 给每个关键流程画一张“失败地图”：这个 API 挂了，业务上怎么办？没想清楚的流程就是裸奔。

## 总结

外部 API 的故障不是异常路径，是日常。好的错误恢复不是让 Agent 更聪明地“扛住”，而是把重试、超时、幂等、降级这些确定性逻辑从模型手里收回来，用工程手段兜底，让模型只做它擅长的那部分判断——下一步走哪条路。先把失败想清楚，再谈自动化。
