## 背景

用 OpenClaw 跑 agent 做日常开发一段时间后，一个此前不突出的问题浮上来：agent 写代码很快，但对 Git 的"卫生"普遍不在意。我们几个自动化项目跑了一个月，仓库里堆满 `update`、`fix stuff` 这类提交，分支也没人清理。人写代码慢，但提交是认真的；agent 写代码快，提交是随手的。这篇帖子记录我们把 Git 提交与分支管理交给 agent 的实践，核心是如何"可靠地放手"。

## 问题

实际踩到的四类问题：

1. **提交质量差**：agent 习惯把一次会话的所有改动打包成一个大 commit，message 空泛，review 和回滚都麻烦。
2. **分支失控**：任务完成后不删分支，两周后分支列表比代码还长。
3. **危险操作**：hooks 失败时会尝试 `--no-verify`，冲突处理失败甚至想 `reset --hard`。
4. **入口混乱**：同时挂 MCP git 工具和 shell，它有时走这头有时走那头，日志对不上，排查成本高。

## 做法

方案概括为：软规则（守则）+ 硬护栏（hooks 与权限）+ 统一入口。

**1. 统一走 MCP git 工具。** 只给 agent 挂 mcp-server-git，收掉任意 shell 权限，每条 git 操作都有结构化记录，也杜绝它临时拼命令。

**2. Git 守则写进技能文件。** 核心几条：

- 提交前先 `status` + `diff`，改动按功能分组，一组一个 commit；
- message 用 Conventional Commits 格式，正文写"为什么"，不写"改了什么"（diff 里已有）；
- 提交前确认当前分支，禁止直接提交到 main；
- 分支命名 `task/<编号>-<短描述>`，合并即清理；
- 禁止 `--no-verify`、对保护分支 force push、`reset --hard` 丢弃未推送改动。

**3. pre-commit hooks 做硬约束。** 提示词是软约束，违反了没有物理后果。hooks 里放 lint、secret 扫描和 message 校验，任何一步失败提交直接被挡。配合禁令，agent 没有绕过的通道。

**4. 低风险任务先行。** 分支清理和周报最先放手：每周让 agent 跑 `git branch --merged` 列出可删分支，人工确认后批量删；同时从 log 汇总一周变更输出给团队。跑稳两周，才把"开分支 + 提交"完全交出去。

**5. 权限最小化。** agent 用单独的细粒度 token，只有目标仓库 write 权限；每条 git 操作进审计日志，出问题可回放。

## 踩坑点

- **大 commit 顽固复发**：光写"分组提交"没用，agent 会偷懒。加了硬指标——单次改动涉及 3 个以上不相关文件必须拆分——才明显收敛。
- **hook 失败死循环**：agent 遇到 hook 报错会反复重试同一提交。改成"hook 失败先修复，重试两次就停下报告"。
- **删分支删过头**：清理分支时差点把未合并的本地分支也删了，`--merged` 过滤必须写成硬性前提。
- **守则写成命令级会错位**：MCP 工具粒度和具体命令不完全对应，第一周行为很混乱。守则应写"意图级"（如"提交前必须检查改动"），而不是绑死某条命令。

## 可复用建议

1. 提示词管意图，hooks 管底线，权限管边界——三者缺一不可，只靠提示词一定翻车。
2. 接管写操作前，先让 agent 跑两周只读任务（分支清理、日志汇总），建立信任基线。
3. Git 守则做成独立技能文件挂给 agent，跨项目复用，比每次塞系统提示省心。
4. 审计日志第一天就开，别等出事再补。

## 总结

把 Git 交给 agent，不是让它"随便提交"，而是把团队已有的工程规范翻译成它能执行、且绕不过去的形式。软规则给方向，硬护栏给底线，最小权限给边界。我们目前的分工是：agent 负责开分支、拆提交、写 message、清理和汇报；人只做 review 和 merge。提交质量比全放手时代好了一个量级，成本也比预想低——大部分工作，其实就是把守则写清楚。
