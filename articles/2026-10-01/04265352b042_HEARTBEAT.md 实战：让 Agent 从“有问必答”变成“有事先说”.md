## 背景

OpenClaw 里的绝大多数交互是拉式的：你发消息，Agent 才动。但不少真实需求是时间驱动的——盯一次部署、扫一眼磁盘、提醒你没回的消息。系统 cron 能定时跑脚本，可它没有判断力，脚本挂了它也不知道。OpenClaw 有个容易被忽略的机制：心跳（heartbeat）。Agent 会按固定间隔自己醒来一次，读取工作区根目录的 `HEARTBEAT.md`，把里面的条目当作“这次醒来该检查什么”的指令；无事发生时按约定回 `HEARTBEAT_OK`，消息不会转发给你。

## 问题

被动 Agent 的典型翻车现场：你让它“盯着 CI”，它回一句“好的”，然后就没有然后了——对话结束，没有任何机制驱动它再去看一眼。cron 又太笨：只能机械执行，做不了“结果异常才通知”这种带判断的分流。HEARTBEAT.md 补的正是中间地带：低频、轻量、需要一点判断力的主动检查。

## 做法

1. 找到工作区根目录（路径以你的实际配置为准），新建 `HEARTBEAT.md`。
2. 用“条件 + 动作”的声明式写法，不要写成流水账。示例骨架：

```markdown
# Heartbeat Checks

- 每次醒来检查 ~/logs/gateway.err 是否有新增 ERROR；
  只有出现新错误时才汇报，附最近一行日志。
  一切正常时不要说话。

- 如果日历里 2 小时内有日程，提前提醒我，附时间和标题。

- 每天首次心跳检查 git 工作区是否有未提交改动，只提醒一次。
```

3. 心跳间隔在配置文件里调（默认约 30 分钟）。日常巡检 30–60 分钟足够；别为了“更及时”压到 5 分钟，token 成本会先于收益爆炸。
4. 验证：故意制造条件（往 err 日志 echo 一行 ERROR），等下一个心跳，确认消息被主动推到你的会话；再观察无事件时它是否真的沉默。

## 踩坑点

- **每次心跳都汇报**。最常见问题：没写“正常时不要说话”，Agent 每半小时发一句“一切正常”。沉默条件必须显式写出来，这是写 HEARTBEAT.md 的第一纪律。
- **把它当垃圾桶**。塞了二十条检查项后，每次心跳都在烧 token，条目还会互相干扰。超过五六条就该分流：重活交给系统 cron，心跳只留需要判断的事。
- **任务写得太重**。心跳里的活是同步跑的，一句“重新跑全量测试”能把心跳阻塞很久。心跳只做“看一眼”，执行类动作让它先汇报、你确认后再触发。
- **忘了这是提示词注入面**。`HEARTBEAT.md` 的内容会被拼进上下文当指令——谁能写这个文件，谁就能驱动你的 Agent。别照抄网上别人的文件，自己手写、保持最小。
- **时区与静音时段**。“每天首次心跳”依赖 Agent 对时间的理解，跨时区或深夜推送很容易翻车。规则里写死你的时区，并加一条“23:00–8:00 除非紧急否则不推送”。

## 可复用建议

- 沉淀一个个人模板：稳定下来的条目放进模板仓库，新机器复制后只改路径。
- 用“只提醒一次”语义防重复轰炸：让 Agent 在 workspace 里维护一个小状态文件，记录“今天已提醒过”。
- 心跳输出统一推到一个低优先级会话，重要事项单独走直发，避免巡检噪音淹没真消息。
- 每月 review 一次：删掉整月没触发过汇报的条目——没有产出的检查项只是纯成本。

## 总结

HEARTBEAT.md 的本质，是把“主动检查什么”从对话上下文里抽出来，变成一份版本可控、可 review 的纯文本配置。它不适合替代 cron 跑重任务，也不该变成另一个通知轰炸源；它的最佳定位是：低频、轻量、带一点判断力的巡检清单。写好沉默条件、控制条目数量、守住文件安全——这三件事做到位，Agent 才会真正从“你问它才答”变成“有事它先说”。
