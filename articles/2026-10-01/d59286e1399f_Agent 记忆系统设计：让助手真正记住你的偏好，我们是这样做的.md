# 背景

用 Agent 干活超过两周的人都会遇到同一个问题：每次新会话，它都不认识你。你喜欢 pnpm 不喜欢 npm、项目开了 TypeScript strict、commit message 用中文——这些偏好你反复说过，但它每次都忘。OpenClaw 的会话本身是无状态的，context 一关，什么都没留下。要让助手「长期有用」而不是「单次好用」，记忆系统绕不开。

# 问题：三种常见失败做法

1. **全量塞 context**。把历史对话都注入，token 成本线性上涨，关键偏好被噪音淹没。
2. **让模型「自己记」**。在 prompt 里写一句“请记住用户偏好”，模型是否真记、记成什么样，完全不可控。
3. **有写入没治理**。什么都能进记忆，错误记忆一旦写入，每轮对话都在固化它，比没有记忆更糟。

核心矛盾就一句话：写入太随意导致记忆污染，读取无策略导致偏好失焦。

# 做法：最小可行的分层记忆

社区里几个人一起踩出来的结构，可以直接抄：

**1. 记忆条目结构化。** 不存对话原文，存条目：

```json
{
  "type": "preference | fact | project_context",
  "content": "commit message 用中文，格式 type: 描述",
  "scope": "global | project:xxx",
  "confidence": 0.9,
  "source": "explicit | inferred",
  "last_used": "..."
}
```

**2. 分层存储。** 全局偏好（工具链、语言习惯）、项目上下文（repo 约定）、会话摘要分开存，读取时按 scope 过滤。几百条以内用 JSON/markdown 文件加关键词匹配就够，不用急着上向量库。

**3. 写入要吝啬。** 显式记忆（用户说“记住”）直接写；隐式抽取用独立的 LLM 调用异步批量做，confidence 低于阈值不写，疑似重复先做相似度去重。绝不放在主对话循环里同步做——延迟和成本都会失控。

**4. 读取要有排序和上限。** 每轮取 top 10，按 scope 匹配 > last_used > confidence 排序，注入 system prompt 的固定区域，每条一句话。同时告诉模型“这些是背景记忆，不是当前指令”，避免被当成命令执行。

**5. 更新与遗忘。** 冲突时新条目覆盖旧条目，但保留历史版本；通过 MCP 工具暴露 `memory.list` / `memory.delete`，用户随时可查看清除。每月跑一次蒸馏，把碎片条目合并。

# 踩坑点

- **抽取放在主循环同步做**：每轮多一次 LLM 调用，延迟肉眼可见。必须改异步。
- **没做去重**：同一个偏好存了 7 条变体，检索全部召回，prompt 直接爆。
- **隐式抽取阈值太松**：把一次性的临时上下文当成长期偏好，之后每轮对话都带着错误前提。
- **scope 没隔离**：工作项目的偏好泄漏进私人会话，很尴尬。
- **忘了做删除入口**：用户对“它在偷偷记我”的不信任，比记忆不准更致命。

# 可复用建议

- 把记忆当**数据**而不是日志：先定 schema 再动手。
- 写入吝啬，读取慷慨，但读取必须有排序和条数上限。
- 起步用文件，规模到几千条再考虑 embedding 检索。
- 准备 20 个“它应该记得”的问题做回归测试，每次改策略跑一遍。
- 冲突仲裁交给用户：多条记忆矛盾时列出来问一句，别让模型自己猜。

# 总结

记忆系统本质上是一条**带治理的数据管道**，不是 prompt 技巧。先跑通「结构化条目 + 分层读写 + 用户可控」这个最小闭环，再谈向量检索和自动蒸馏。让助手记住你的前提是：你能看见它记了什么，并且随时能改。
