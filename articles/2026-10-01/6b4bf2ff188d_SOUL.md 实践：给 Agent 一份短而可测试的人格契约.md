## 背景

OpenClaw 的 agent 有一个工作区，`SOUL.md` 是其中被注入系统提示的"人格层"，决定它是谁、怎么说话、底线在哪。多数人的用法分两个极端：要么装完直接用默认人设，要么把它当成万能配置，什么都往里塞。用了一段时间后，两种都会出问题。

## 问题

我遇到过的两类典型症状：

1. **人格漂移**：换模型、长对话、多插件介入之后，语气变了，开始过度讨好、输出啰嗦，甚至主动揽活。
2. **边界缺失**：什么请求都接。让它直接改线上配置不犹豫、读工作区外路径不确认、执行不可逆操作之前不问一句。

根因很简单：人格和行为红线没有一处权威声明，全靠临时提示词和运气。SOUL.md 就是补这个缺口的地方。

## 做法

我的原则是：**SOUL.md 只回答三个问题——我是谁、我怎么说话、我绝不做什么。** 一个能跑的起点模板（15 行以内）：

```markdown
# Identity
- 定位一句话：自动化工作台里的执行型助手

# Tone
- 简洁直接，先结论后细节；中文交流，术语保留英文

# Boundaries
- Never: 未经确认执行不可逆操作（删除、改线上配置、对外发送消息）
- Never: 将工作区外路径当作事实来源引用
- Always: 高风险操作前先列出影响面，等确认再动手
- 拿不准就说拿不准，不编造
```

落地步骤：

1. 从 15 行开始写，放进 workspace，重启会话确认注入生效。
2. 设计 5~8 个探针问题做测试：诱导它越界、问它不知道的事、看回复是否啰嗦。
3. 每个失败案例反写成一条具体的 Never/Always，加回 Boundaries。
4. `git init` 管理 SOUL.md，每次修改留痕，能 diff 回看人设演变。

## 踩坑点

- **写太长**。几百行的人设会稀释注意力，真正的红线被淹没在散文里。实测控制在 30~40 行以内效果最稳。
- **职责混放**。"如何回复邮件"这类流程属于 `AGENTS.md`，用户偏好属于 `USER.md`，SOUL.md 只管人格与红线。混放之后哪份都改不动。
- **用模糊形容词**。"要负责任、要聪明"没有可执行性。每条边界都要落到一个具体场景，写成可判定的行为。
- **只写不改**。人格是迭代的，每次翻车都应转化为一条新约束，而不是靠下次对话口头纠正。
- **记忆污染**。长期记忆里的旧习惯可能对抗新边界，必要时在文件里明确一句"行为冲突时以本文件为准"。

## 可复用建议

- **三层分工**：SOUL.md（人格+红线）、AGENTS.md（工作流程）、USER.md（用户上下文），各管各的。
- **可判定原则**：写完每条边界，问自己"能想象出一个具体测试场景吗"，不能就重写。
- **探针测试集脚本化**：改一版跑一遍，五分钟的事，能拦住大部分回归。
- **定期 git diff 回顾**：人设文件的变化史，就是 agent 的翻车史，很有参考价值。

## 总结

SOUL.md 不是玄学，它就是给 agent 的一份最小契约：短、具体、可测试。与其写一篇长文去"感化"模型，不如用十几行 Never/Always 把红线钉死，再用探针测试持续校准。人设调得好的 agent，往往不是最"聪明"的那个，而是行为最可预测的那个。
