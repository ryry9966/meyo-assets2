## 背景

E2E 测试是性价比最差、但又最砍不掉的一层：写得慢、跑得慢、挂得莫名其妙。大多数团队的现状是覆盖几条核心路径就停手了。现在 agent 可以通过 MCP 直接操作浏览器（比如挂一个 Playwright MCP server），“让 AI 写测试”不再是一句口号，而是可以拆成明确步骤的工程问题。这篇记录一下我们在 OpenClaw 里跑通的做法。

## 问题

自己写 E2E 的三个老痛点：

1. **起步成本高**：搭 fixture、造测试数据、写 page object，一条有效用例的固定开销远大于用例本身；
2. **维护成本高**：前端改一次 DOM 结构，几十条用例连环红；
3. **失败分析烦**：大部分红色是时序和环境问题，真正的回归反而被淹没。

## 做法

前提：在 OpenClaw 的 MCP/插件配置里接上浏览器控制工具（navigate、click、fill、snapshot 这类）。流程分四步：

**1. 用自然语言描述业务流，不写代码。**
给 agent 一条明确的用户路径：“登录 → 新建项目 → 邀请成员 → 成员列表出现新用户”。关键约束：要求它先取可访问性快照确认真实页面结构，禁止凭记忆猜选择器。

**2. Agent 探索 + 生成。**
agent 实际打开页面，基于 snapshot 产出 Playwright 测试代码，落到 `tests/e2e/` 下。要求它复用已有 page object；没有就先建，不许内联选择器。

**3. 跑失败，喂回给 agent。**
本地或 CI 跑一遍，把截断后的失败日志和失败时刻的 snapshot 回灌，让它自己修。经验上 2~3 轮能收敛。

**4. 人工 review 后才入库。**
重点看三件事：断言是否在验证业务结果（而不是“页面没报错”）、有没有硬等待、测试数据是否会互相污染。

## 踩坑点

- Agent 非常爱写 `sleep` 硬等待，务必在提示词里直接禁掉，强制 `expect` + auto-wait；
- 放手让它发挥时，它会生成“永远绿”的弱断言，review 时优先审断言强度；
- 动态 ID、时间戳类元素是重灾区，让它走 `data-testid` 或 role + name 定位；
- 不要让它一次生成二十条用例，一次一到三条，收敛后再批量；
- 失败回灌要截断日志，全量喂进去 token 烧得快，噪音还大。

## 可复用建议

- 把定位规则、断言标准、目录结构沉淀成一份固定的系统提示词（或插件配置），团队共用，比每次口头描述稳定得多；
- CI 失败后自动触发 agent 修复，但用 CI 规则把 diff 范围锁死在测试文件内，不允许它碰业务代码；
- 已稳定的用例打上 tag，agent 修失败时优先怀疑自己的改动，而不是产品 bug——这个提示词能显著减少“越修越错”。

## 总结

Agent 写 E2E 的正确姿势，不是“一键生成测试套件”，而是把它当成一个手速很快、但完全不熟悉你系统的初级工程师：给它浏览器、给它约束、给它失败反馈，人负责断言质量和最终把关。跑通这个循环后，核心路径的 E2E 覆盖成本能降一个量级，维护工作也从“人肉修选择器”变成“review agent 的修复”——这才是这件事真正值钱的地方。
