## 背景

我们组用 Agent 做内容自动化已经跑了半年：模型生成初稿，人工审核后通过 MCP 工具分发到公众号、知乎、掘金和静态博客。链路跑通后才发现，真正耗时的不是生成，而是格式。同一段 Markdown，四个平台四种表现，人工搬运和修补占了整个流程近一半时间。于是把格式适配单独抽成一条管线，这篇记录思路和踩坑。

## 问题

各平台对 Markdown 的支持差异比想象中大：

- 公众号只接受白名单内联样式的 HTML，外链会被剥掉，图片必须走自家存储；
- 知乎保留基础语法，但表格样式和代码高亮受限；
- 掘金和静态博客接近标准 Markdown，但图片要求各自图床；
- 部分平台会把 front matter、脚注语法原样渲染出来。

另外模型本身是“方言制造机”：即使 prompt 里限制了语法，它仍会随机输出 HTML 片段、波浪线围栏、过度加粗。靠 prompt 约束不可靠，必须在代码层兜底。

## 做法

核心决策是引入 canonical Markdown 作为唯一中间表示，所有平台从它派生。管线分五步：

1. **生成约束**。把自定义“方言规范”（只允许 ATX 标题、标准表格、三反引号围栏、禁 raw HTML）写进 prompt，且与校验器共用同一份规则文件，避免两处维护。
2. **程序化校验**。输出先过一道 linter（正则 + AST 双层），命中禁用语法就自动修复或打回重生成，不靠人眼。
3. **AST 化**。用 remark/mdast 解析成语法树，后续所有转换在树上做，不再碰原始字符串。
4. **平台适配器**。每个平台一个 renderer 插件，注册进统一的发布工具（我们包成了 MCP tool）。公众号适配器负责：代码块构建期高亮并内联样式、表格定宽、外链转文末引用、图片先传自有 OSS 再替换 URL；知乎适配器负责表格降级。
5. **发布前 dry-run**。每个适配器支持 preview 模式，先产出目标平台的最终内容供 diff，确认后再提交。

## 踩坑点

- **移动端代码溢出**：桌面看着正常的代码行，公众号里必溢出。最后在 AST 阶段按 40 字符硬折行，长标识符加软断点。
- **图片防盗链**：AI 生图平台和部分图床的 URL 带防盗链，直接引用全裂。一律重传自有存储，不要信任源 URL。
- **嵌套列表被吞**：公众号对三层以上嵌套列表渲染混乱，适配器里拍平成带序号的段落更稳。
- **换行符**：CRLF 会让某些平台把段落拆碎，管线入口统一归一化成 LF。
- **幂等性**：早期重跑任务会重复传图，后来以内容 hash 做图床去重，上传前先查存在性。

## 可复用建议

- 方言规范、校验器、prompt 三者共享一份规则源，别写两遍。
- canonical 版本作为构建产物落盘，配合 golden file 做回归测试，适配器改坏了能立刻 diff 出来。
- 适配器做成可注册的插件而不是 if-else，新平台接入成本基本等于写一个 renderer。
- 表格等高危语法提前准备降级路径（转列表或转图片），别假设目标平台兼容。

## 总结

这条管线本质上是个编译器问题：canonical 是 IR，平台适配器是后端。想清楚这一点后，格式工作就从“每次手动修”变成了“改一个 renderer”。目前从生成到发布的人工介入只剩审核环节，格式相关返工基本归零。如果你也在做 Agent 的内容分发，建议先花半天把方言规范定下来，这一步收益最大。
