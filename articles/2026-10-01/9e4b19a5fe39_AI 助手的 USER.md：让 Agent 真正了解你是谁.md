## 背景

用 OpenClaw 一段时间后，最明显的感受不是它不够聪明，而是它“不认识你”。每次新会话都要重新交代一遍：时区在哪、用什么技术栈、喜欢先给结论还是先铺细节、哪些事不许碰。这些信息不属于任何一次任务，却影响每一次任务。

MEMORY.md 解决的是“发生过什么”，本质是事件流；而“你是谁、你怎么工作”是稳定的结构化事实，散落在记忆里既浪费 token 又容易丢失。这就是 USER.md 的定位：工作区里一份描述用户本人的静态档案，会话启动时随系统提示一起加载。

## 问题

没有这份档案时，常见症状包括：

- Agent 按服务器时区排定时任务，提醒总差几个小时；
- 回答风格飘忽，这次长文下次极简，你反复调教；
- 涉及你的代码习惯（缩进、命名、常用框架）每次重新说明；
- 换设备、换渠道（Telegram / 微信 / Web）后，上下文归零。

本质是同一个问题：把本该持久化的用户画像，当成临时口头传输。

## 做法

在 OpenClaw 工作区根目录建 `USER.md`，用分区结构，每节几行以内：

```markdown
# 用户档案
## 基本信息
- 时区：Asia/Shanghai，工作日 10:00-19:00
- 语言：默认中文回复，代码注释用英文
## 技术栈
- 主力：Python / FastAPI，部署用 Docker
- 代码风格：4 空格缩进，类型注解优先
## 偏好
- 回答先给结论，细节放后面
- 不确定的假设显式列出，别默默替我决定
## 边界
- 不主动操作生产环境
- 涉及花钱的动作必须先确认
```

步骤：先写最小版本（不超过 30 行），跑一两周真实任务；每次发现自己在重复交代某件事，就沉淀进对应分区；进 git 管理，改动留痕。

## 踩坑点

- **写太长。** 上百行个人经历会稀释注意力，关键约束反而被淹没。USER.md 是约束清单，不是自传。
- **信息过期。** 换了工作、换了主力语言没更新，Agent 拿旧假设推理，比没档案更糟。设一个月自查一次。
- **写入敏感信息。** 姓名+公司+地址这类组合、任何密钥，都会整段进上下文，可能随日志和模型调用外泄。写“角色”，不写“身份”。
- **结构混乱。** 大段散文提取不稳定；分节 + 短条目 + 明确措辞（“必须”“禁止”“默认”）效果好得多。
- **和 MEMORY.md 职责混淆。** 稳定事实进 USER.md，事件和临时状态进 MEMORY.md，两边重复会互相打架。

## 可复用建议

- 分区固定四块就够：基本信息 / 技术栈 / 偏好 / 边界。够用，别加戏。
- 措辞用指令语气：“默认”“必须”“不要”，而不是“我一般可能大概”。
- 让 Agent 参与维护：给它一条固定指令——“当我在对话中纠正你关于我的假设时，把修正追加到 USER.md 对应分区并告知我”。Agent 起草，人工审核。
- 团队场景拆开：USER.md 只放个人内容，团队约定走共享文档，个人偏好不进公共配置。
- 版本化之后定期 diff 复盘：哪些条目反复改，说明当初写法不够清晰。

## 总结

USER.md 不是什么高级技巧，它只是把“每次开会前的自我介绍”变成一次性的、结构化的、可版本管理的配置。对个人 Agent 而言，这种稳定性带来的体验提升，往往超过换一个更大的模型。先写 20 行，用两周，再迭代——这份档案会越用越准，而成本几乎是零。
