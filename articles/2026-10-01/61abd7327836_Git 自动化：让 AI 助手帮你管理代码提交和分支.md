## 背景

日常开发里，Git 操作占了不小的隐性时间：写 commit message、切分支、整理提交、同步远端。这些事不难，但琐碎、重复，还容易出错。OpenClaw 的 Agent 能执行 shell 命令、调用 MCP 工具，天然适合把这类流程接过去。关键不是“能不能做”，而是“怎么做才安全可控”。

## 问题

直接丢一句“帮我提交代码”，通常会翻车：

- 生成的 message 泛泛而谈（"update code"），没有信息量；
- Agent 可能顺手执行 `git reset --hard` 或 `push --force`，后果不可逆；
- diff 超出上下文窗口，模型只能“脑补”改动内容；
- 半成品文件、密钥被一起提交。

本质问题是：Agent 拿到的是不受限的 git 权限，而自动化需要的是受约束的流程。

## 做法

我的方案分三层，全部在本地仓库内完成：

**第一层：约束工具面。** 不让 Agent 裸调 git，而是封装一个薄薄的 MCP 工具（或 shell 包装脚本），只暴露白名单动作：`status`、`diff`、`add`、`commit`、`checkout -b`、`push origin <branch>`。危险命令（reset、rebase、force 类）不进工具面，Agent 想做也做不了。

**第二层：固定流程。** 约定标准序列：先 `status` 确认工作区，再 `diff --staged` 审阅变更，按 Conventional Commits 生成 message（type/scope/subject），提交前把 message 和文件清单打印出来，等我回复“确认”才执行。分支同理：按 `feat/xxx`、`fix/xxx` 规范命名，从 main 拉出，禁止直接提交 main。

**第三层：兜底检查。** 提交前强制跑 `git diff --check` 加敏感文件扫描（.env、密钥后缀），命中即中断并说明原因。全部命令和输出写入日志，出问题能回溯。

实测下来，日常提交耗时从两三分钟降到十几秒，message 质量也比手写稳定。

## 踩坑点

- **diff 过大截断**：大改动别全量塞给模型，按文件拆分，或只传 `--stat` 加关键文件 diff，否则 message 会失真。
- **工作区竞态**：Agent 分析 diff 期间你又改了文件，提交内容和 message 就对不上。解法：`add` 之后立刻快照一次 staged diff，一切以它为准。
- **hook 干扰**：仓库有 pre-commit hook 时，Agent 看到失败会反复重试。在提示词里明确“hook 失败就贴原始输出，不要自行绕过”。
- **确认环节别省**：我试过让 Agent 跳过确认来提效，结果调试用的临时文件被一起提交了。这一步只花两秒，值得保留。

## 可复用建议

1. 白名单 + 确认门是所有 Agent 自动化的通用模式，不止 Git；
2. 把 Conventional Commits 规范直接写进系统提示词或工具描述，模型遵守度很高；
3. 保持 `--dry-run` 心态：任何写操作先打印计划，再执行；
4. 日志是信任的前提，没有日志的自动化等于黑盒。

## 总结

Git 自动化的价值不在“快”本身，而在把重复决策变成可审查的流程。给 Agent 受限的工具面、固定的流程和一个人工确认点，它就能稳定承担提交与分支管理这类脏活。同样的思路可直接迁移到发版、cherry-pick 整理等场景——从最小白名单起步，逐步放权。
