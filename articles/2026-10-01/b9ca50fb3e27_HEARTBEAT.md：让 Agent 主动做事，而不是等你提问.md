## 背景：从"拉"到"推"

大多数 Agent 交互是拉模式：你提问、它回答，会话结束就沉寂。但个人助理场景里很多事不需要你先开口——收件箱值得汇总、磁盘快满、某个仓库三天没提交。这类事的特征是"条件触发 + 需要判断"：cron 只会执行，不会判断"要不要现在打扰你"；纯问答又等不到你提问。

OpenClaw 的 heartbeat 机制补的就是这一块：Agent 每隔一段时间（默认 30 分钟）被唤醒一次，读工作区里的 HEARTBEAT.md，逐条决定要不要做事。无事可做时回复 `HEARTBEAT_OK`，消息不会转发给你。它把 Agent 的主动性从会话内扩展到了会话之间。

## 问题：三种常见的失败形态

只给 Agent 一个空的 HEARTBEAT.md，很容易跑偏：

1. 条目太模糊（"帮我关注下服务器"），每次醒来自由发挥，token 烧了，产出随机；
2. 每次心跳都发消息，三天后你把它静音，主动变骚扰；
3. 把心跳当 cron 用塞长任务，跑不完又叠上下一次心跳。

## 做法：把主动性写成条目

**第一步**：HEARTBEAT.md 位于工作区根目录，Agent 首次心跳时会自动创建，也可以自己先建好。

**第二步**：按"条件 + 动作 + 默认沉默"三段式写条目：

```markdown
# HEARTBEAT

- 若 inbox/ 未读摘要超过 3 条，整理成一页清单发给我；否则回复 HEARTBEAT_OK
- 若磁盘使用率超过 85%，列出占用最大的三个目录；否则回复 HEARTBEAT_OK
- 每天首次心跳汇总昨日 git 提交数；其余心跳回复 HEARTBEAT_OK
```

每条显式写明"否则 HEARTBEAT_OK"是控制噪音的关键——不写，Agent 会倾向于汇报"我检查过了，一切正常"。

**第三步**：调间隔。默认 30 分钟对监控类够用；"每天早上一条摘要"这类需求别靠缩短间隔硬轮询，在条目里写清时间条件，让 Agent 自己判断。

**第四步**：留审计。要求 Agent 每次实际动作时往 workspace 下追加一行心跳日志（时间 + 做了什么），出问题能回溯。

## 踩坑点

- **心跳是无状态唤醒**。需要跨周期记忆的逻辑（"连续三次超阈值才报警"），把状态落盘成文件，条目里写"读某文件判断"。
- **别塞耗时任务**。心跳适合"检查 + 短动作"；跑一两分钟以上的脚本交给 cron/systemd，心跳只看结果文件决定要不要报。
- **条目控制在 5 条以内**。每条都是每次唤醒的 token 成本，文件会长胖，要像清理 crontab 一样定期清理。
- **测试期先降频**。心跳消息默认走主渠道，调试时把间隔拉长或临时禁用，避免刷屏。

## 可复用建议

- 三段式模板可以沉淀成团队模板，新人填空即可；
- 监控类（异常才说话）和摘要类（每天固定一条）分层写，节奏不同；
- 心跳条目 + MCP 工具是好组合：文件里只写意图，取数交给 MCP server，HEARTBEAT.md 保持薄；
- 把它纳入 git——"Agent 什么时候开始多管闲事"往往能定位到某次手滑编辑。

## 总结

HEARTBEAT.md 的价值不在于"AI 会主动做事"这个卖点，而在于它把主动性变成了可 review、可版本化、可审计的纯文本契约。写好它只需要回答三个问题：什么条件下做、做什么、不满足条件时如何保持沉默。这三件事写清楚了，主动性才从玄学变成工程。
