## 背景

OpenClaw 的 cron 任务，本质是「定时触发的独立 agent 会话」：到点后系统把 instruction 作为那一次会话的 prompt 交给 agent 执行。它和聊天里写 prompt 有个关键区别——**没有上下文**。没有之前的对话，没有任何你没写进 instruction 的信息。

很多第一次写 cron 的人把它当提醒事项写，比如「每天早上汇总一下新闻」。结果要么 agent 不知道汇总完发给谁，要么跑了一堆工具输出没人看，要么每天准时发一条「今天没有新动态」刷屏。

## 三个核心问题

1. **上下文缺失**：会话独立，instruction 就是全部输入；
2. **输出去向不明**：agent 默认回复在触发会话里，不指定通道大概率没人看到；
3. **失败行为未定义**：数据为空、工具报错时，agent 会自行发挥——要么硬编内容，要么礼貌地汇报「什么都没有」。

## 做法：按任务书结构写

我固定用五段式模板：

```text
任务：一句话说清目标。
数据来源：用哪个工具/MCP，取什么范围的数据。
处理步骤：筛几条、怎么排序，控制步数。
输出：发给哪个通道、什么格式、字数上限。
异常：取不到数据 / 工具失败 / 无新内容时的行为（通常是"不发消息，直接结束"）。
```

实际例子（每日资讯汇总）：

```text
任务：汇总过去 24 小时与 OpenClaw 相关的资讯。
数据来源：使用 web_search 检索，只保留过去 24 小时内的结果，时区按 Asia/Shanghai。
处理：筛出最多 3 条，按重要性排序，每条一句话概括加原文链接。
输出：将列表发送到 #daily 频道，总字数不超过 200。
异常：搜索失败或无符合条件的结果时，不发送任何消息，直接结束。
```

写完先别上正式 schedule，开发环境手动触发一次，确认输出通道、格式、静默逻辑符合预期，再设 cron 表达式。

## 踩坑点

- **时区错位**：cron 表达式按系统配置时区解析，instruction 里写「今天」可能和你差一天。要么显式写时区，要么用「过去 24 小时」这种相对描述。
- **输出通道没写**：agent 把结果回在默认会话，你在群里等了个寂寞。
- **没有空结果规则**：agent 为了「完成任务」，要么编内容，要么每天发「今天没有动态」。后者的杀伤力在于——群里的人会开始忽略这个频道，等真有重要信息时也没人看。
- **单次任务塞太多目标**：「汇总资讯 + 检查服务 + 生成周报」跑不完就截断，三件事各做一半。一个 cron 干一件事，要组合就拆任务。
- **任务间隐式依赖**：昨天失败今天照跑，产出建立在坏数据上。可在 instruction 里写明「只使用本次获取的数据」。

## 可复用建议

- 把五段式存成模板，新任务只填空。最常漏的是异常段，而它恰恰最影响观感。
- 每隔两三周翻一下 cron 的实际输出，看有没有该静默没静默、该发没发的 case，回来改 instruction。cron instruction 不是一次性的，它是持续调优的 prompt。
- 涉及推送的任务，默认「无新内容就闭嘴」。宁可少发，不要刷屏。

## 总结

Cron 任务的 instruction 不是提醒文本，而是给无状态 agent 的完整任务书：目标、来源、步骤、输出、异常，五样缺一不可。它跑得好不好，取决于你是否把「没有上下文」和「失败了怎么办」当成默认前提。写的时候多花两分钟，能省掉之后在群里解释「不是我发的」的十分钟。
