## 背景

Agent 框架本身是无状态的。每次会话开始，模型对用户一无所知：代码风格、常用技术栈、语言偏好、汇报格式，全都要重新交代一遍。OpenClaw 这类可以长期挂在终端里跑的助手，用户预期是"越用越懂你"，这就逼着我们在 Agent 外面补一层记忆系统。

## 问题：三种常见做法都有坑

1. **全塞 system prompt**：上下文膨胀，token 成本上涨，偏好之间还会互相冲突。
2. **直接 RAG 聊天记录**：检索回来的是对话碎片，不是结构化偏好，噪声大。
3. **把记忆当平铺列表**：没有生命周期，旧偏好永远留着——用户早从 Vue 换到 React 了，它还在推荐 Vue 选项。

## 我的设计：分层 + 结构化 + 有生命周期

### 1. 按变更速度分层

- **用户画像层（durable）**：语言、代码风格、命名习惯，月级不变；
- **项目上下文层（semi-durable）**：当前仓库、技术栈、团队约定；
- **会话工作层（volatile）**：本次任务的临时指令，如"这次先别加测试"。

### 2. 存结构化条目，不存原文

每条记忆是一个对象：`scope`、`content`、`source`（哪次会话产生）、`confidence`、`created/last_used`、`ttl`。存 JSON，别存聊天片段。

### 3. 写入保守

提取用"规则 + LLM 判断"双闸门：只有显式声明（"以后都用 TypeScript"）或重复出现 ≥2 次的模式才升级为持久记忆，一次性指令留在会话层。去重用 embedding 相似度 + scope 匹配，阈值宁严勿松。

### 4. 读取有预算

会话开始时按 scope 注入：用户层全量（通常就十几条），项目层按相关性取 top-k，设 token 上限。排序权重 = 相关性 × recency × frequency。工具调用前（比如写代码前）再做一次针对性检索。

### 5. 更新与遗忘

新旧记忆冲突时不追加，而是生成新版本并标记 supersede，旧版本可回滚。`last_used` 长期未命中的条目降权；用户可显式"忘掉某条"。

### 落地方式

我把记忆做成了一个 MCP server，暴露 `memory.search / memory.write / memory.update` 三个工具，Agent 按需调用；另跑一个异步管道在会话结束后做提取。用户可以 dump 全部记忆查看和修改——**记忆必须可审计**。

## 踩坑点

- **过度捕获**：早期提取阈值放太松，两周后检索全是噪声。写入端宁可漏，读取端宁可全。
- **一次性指令当偏好**："这次用中文回"被记成永久偏好，非常尴尬。scope 和条件字段必须显式。
- **相似度阈值太松**："喜欢简洁的代码"几乎能匹配一切写入，导致重复膨胀。
- **信任边界**：来源是网页内容或工具输出的信息，绝不能当用户偏好写进用户层——这是注入风险。
- **静默变更**：Agent 悄悄改记忆会摧毁信任，关键变更要回显确认。

## 可复用建议

1. 先定 schema 再写代码，`source` 和 `confidence` 从第一天就要有；
2. 从显式记忆（"记住……"）+ 少量高置信规则起步，自动提取后加；
3. 做一个 `memory dump` 命令，可视化永远值回票价；
4. 评测用回放：拿历史会话跑一遍，看行为是否符合预期，别靠感觉。

## 总结

记忆系统本质是数据工程问题，不是 prompt 问题。结构化条目 + 明确生命周期 + 可审计，比任何巧妙的提示词都管用。先做小、做对，再谈智能。
