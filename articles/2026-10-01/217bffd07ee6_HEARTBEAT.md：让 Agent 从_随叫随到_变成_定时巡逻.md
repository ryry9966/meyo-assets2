## 背景

我们用 Agent 的方式大多停留在问答模式：你不说话，它不动。但很多事并不需要人来发起——早上确认备份是否成功、repo 里有没有搁置的分支、今天日程有没有冲突。OpenClaw 提供了一个很轻的机制：Heartbeat。Agent 按配置的间隔被唤醒，去读工作区里的 `HEARTBEAT.md`；文件里有内容，就按清单逐项检查；没事可做，就保持沉默。一个 Markdown 文件，就把 Agent 变成了常驻的巡逻员。

## 问题

让 Agent 主动做事，最大的障碍不是能力，而是噪音。你跟它说"有空帮我留意一下"，它就每隔半小时冒出来汇报一句"一切正常""磁盘 62%""没有新邮件"。两天之后你一定会把它静音，这个功能等于白做。所以写 HEARTBEAT.md 的核心不是"让它做什么"，而是"什么情况下不许说话"。

## 做法

1. 在配置里开启 heartbeat，间隔先放宽到 30–60 分钟：

```yaml
agents:
  defaults:
    heartbeat:
      intervalM: 45
```

2. 在 agent 实际加载的 workspace 下创建 `HEARTBEAT.md`。注意是运行时 workspace，不是代码仓库里的任意路径——路径对不上，heartbeat 静默失效，很多人卡在这一步。
3. 文件结构：顶部一条默认规则，下面每项写清楚「检查什么 + 触发条件 + 汇报格式」：

```markdown
# Heartbeat Checklist
默认规则：所有项目正常时不发任何消息，直接回复 HEARTBEAT_OK。

- 检查今日日程，如有 2 小时内开始的会议，一行汇报。
- 检查备份目录时间戳，超过 24 小时未备份则汇报。
```

4. `HEARTBEAT_OK` 会被框架识别并丢弃，不投递给用户——这是控制打扰的关键约定，务必写进默认规则。
5. 把投递目标指向一个专门的低频频道，主动消息不要打进你的主对话。
6. 每两周审一次清单：从没触发过的删掉，触发太频繁的收紧条件。

## 踩坑点

- **Token 成本**：每次 beat 都是一次完整的模型调用。清单写得越长，成本线性上涨。建议控制在 5 项以内。
- **条件模糊**：写"留意系统状态"，Agent 会自由发挥，要么瞎找事做，要么过度汇报。条件必须可判定真假。
- **混入一次性任务**：HEARTBEAT.md 是巡逻清单，不是调度器。要精确时间触发的（比如每天 9:00 发摘要）用 cron，heartbeat 的语义是"轮到了顺手看一眼"。
- **Agent 不够沉默**：初期它爱汇报"一切正常"。先检查默认规则是否置顶、措辞是否够硬——"不要汇报"比"可以不汇报"有效得多。

## 可复用建议

- 从一项开始（比如日程前瞻），跑一周确认信噪比可接受，再逐项加。
- 把 `HEARTBEAT.md` 纳入版本管理。它本质上是这个 Agent "主动性边界"的规格说明，变更历史就是调优记录。
- 约束输出格式：每项一行，结论在前。主动消息没有读者耐心，短就是一切。
- 不加"查了也无妨"的项。每一项都会在之后的每一次 beat 里持续付租。

## 总结

HEARTBEAT.md 的价值在于用最低的成本把 Agent 从被动的问答端点变成轻量后台巡逻员。它的工程本质是信噪比管理：文件的主要职责不是告诉 Agent 做什么，而是划清"什么情况下闭嘴"。把这条规则打磨好，主动式 Agent 才能真正长期留在你的工作流里，而不是三天后被你亲手静音。
