## 背景

OpenClaw 的典型用法是 7x24 挂在消息渠道上：定时摘要、监控告警、代码审查、日常问答都走同一个 Agent。如果主模型一直设成旗舰云端模型，账单和延迟会随消息量线性上涨；反过来全切本地小模型，复杂工具链任务又经常掉链子。多模型路由要解决的就是这个分配问题：让每类任务落在成本和质量都合适的模型上。

## 问题：一刀切的两难

- 全云端：贵、慢，隐私敏感内容出域
- 全本地：复杂推理和工具调用稳定性差，长上下文容易截断

真正的解法不是选边，而是按任务特征分层。

## 做法

我目前跑了一段时间的分层方案，可以当起点：

**1. 先拆任务类型**。把 Agent 的工作流分成四类：高频轻任务（摘要、格式化、提醒确认）、常规自动化（定时任务、脚本生成）、工具密集型（MCP 多步调用、planning）、代码与复杂推理。

**2. 模型分三层**：

- Tier 0：本地 7B–14B（Ollama 起一个就行），接高频轻任务，零成本、低延迟
- Tier 1：云端中档模型，接常规自动化
- Tier 2：旗舰模型，只在 planning、代码、多步工具链时启用

**3. 在 OpenClaw 里落地**：主模型 + fallback 链（云端为主、本地兜底，或按技能反过来）；按 Agent / 会话粒度指定模型，不同技能绑不同 tier；路由判断用规则或轻量前置分类做，别让大模型自己决定走哪条路——那又是一次付费调用。

**4. 度量闭环**：记录每次调用的 token、延迟、fallback 次数，每周看一次路由命中率，再调分层。

## 踩坑点

1. **本地模型 tool call 格式差异**：部分模型对 function calling 的 schema 支持不完整，Agent 会静默失败然后进入重试死循环。上线前用固定评测集把 MCP 工具链跑一遍。
2. **上下文窗口不匹配**：长会话记忆在 8K 本地模型上被截断，表现为“失忆”而不是报错，很难排查。给本地模型配更激进的历史压缩。
3. **静默 fallback 风暴**：本地挂了自动回落到旗舰模型，一晚上账单翻倍。给 fallback 加频率告警和日预算上限。
4. **行为不一致**：两个模型的温度和风格不同，同一技能输出时好时坏，用户体感很差。关键技能固定单一模型，不做动态切换。
5. **隐私反向泄漏**：为了省钱把带敏感上下文的会话路由上云。路由规则里加渠道维度和敏感内容的硬约束，优先级高于省钱逻辑。

## 可复用建议

- 先纯云端跑一两周，攒到真实任务分布和成本基线，再决定哪些下沉本地。不要一上来就写路由规则。
- 评测集优先于路由规则：准备 10–20 个覆盖各 tier 的固定用例，每次换模型或改提示词都跑一遍。
- 本地模型先当“可用性兜底”再当主力：断网、限流、配额耗尽时保住链路，比省钱更先兑现价值。
- 路由日志单独存，别混进会话日志，否则没法复盘成本和命中率。

## 总结

多模型路由本质是成本、质量、隐私的三角权衡，OpenClaw 在模型层给了足够自由度，但默认配置不会替你省钱。路径应该是：先度量、再分层、后路由；本地模型先兜底、再上主力，是实操里最不容易翻车的顺序。
