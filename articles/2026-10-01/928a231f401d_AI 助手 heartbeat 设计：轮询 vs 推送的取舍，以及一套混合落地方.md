# 背景：Agent 为什么需要心跳

Agent 跑起来之后，核心问题不是“会不会做事”，而是“什么时候该醒来做事”。用户消息要响应、cron 到点要跑、监控报警要看，这都依赖一个唤醒机制。

OpenClaw 内置的 heartbeat 是典型的轮询思路：固定间隔（默认半小时左右）给 agent 注入一次心跳 prompt，让它自查一遍，没事就回 `HEARTBEAT_OK` 静默吞掉。另一派思路是推送：事件发生时由 webhook / MCP 通知直接唤醒 agent。两种模型各有适用场景，下面基于实际运行一段时间的经验，聊聊取舍和混合做法。

# 问题：两边各有硬伤

**轮询的痛点：**
- 延迟上限就是间隔。间隔 30 分钟，事件最多晚 30 分钟被发现
- 每次心跳都是一次带上下文的完整 LLM 调用。间隔调短，token 账单线性上涨；调长，实时性崩
- 大部分心跳是空转，但空转也有成本，还会稀释会话记录

**推送的痛点：**
- 前提是事件源会说话。IM 有 webhook，但很多内部系统、旧接口只有拉取式 API
- 推送丢了就是丢了，agent 不知道自己错过了什么，需要额外对账机制
- 事件风暴：一个源头抽风，agent 被连续唤醒几十次

# 做法：推送加速 + 轮询兜底

实际落地建议走混合模型，分四步：

1. **事件源分类**。有 webhook / MCP 通知能力的（GitHub、监控、邮件网关）走推送通道；只有拉取接口的（部分 IM、本地文件巡检、数据库轮询）归入心跳轮询。
2. **统一入口**。无论来自哪条路，事件都进同一个唤醒队列，agent 侧只认一个入口。去重在队列层做，用事件 ID 做幂等键。
3. **心跳轻量化**。心跳 prompt 用裁剪版上下文，输出收敛为三态：`HEARTBEAT_OK`（静默）、有事上报（摘要推给用户）、触发任务（丢给后台跑，不在心跳里干重活）。
4. **自适应间隔**。连续 N 次空转，间隔按 1.5 倍退避并设上限（如 2 小时）；一旦有事件或用户活跃，立刻回到短间隔。间隔加随机抖动，避免整点洪峰。

# 踩坑点

- **心跳注入了完整系统提示词和历史会话**，一天下来的 token 消耗是正常会话的好几倍。心跳上下文必须裁剪，只留当前任务清单和最近事件摘要。
- **忘了静默处理 `HEARTBEAT_OK`**，用户每半小时收到一句“一切正常”，体验灾难。
- **推送和轮询同时覆盖同一事件源却没做幂等**，同一封邮件被处理了两遍。去重必须放在队列层，不能指望模型自己分辨。
- **在心跳里跑长任务**，阻塞了主会话，用户消息排在后面干等。心跳只负责发现，执行下放给后台。
- **只开推送、关掉轮询**，某天 webhook 静默失效，三天没人发现。低频对账轮询必须保留。

# 可复用建议

- 把心跳定位成“兜底对账”，而不是主要驱动；主驱动给推送
- 间隔参数不要全局一套，按事件源活跃度分档配置
- 三态输出（静默 / 上报 / 触发）是个好约束，能显著降低空转打扰
- 监控两个指标：**心跳空转率**看成本，**事件端到端延迟**看体验，两者一起看才不会顾此失彼

# 总结

轮询简单、可靠、处处可用，但延迟和成本被间隔锁死；推送实时、省 token，但要求事件源配合，可靠性要自己兜。实践里几乎没有纯用一种能跑得舒服的场景。“推送加速、轮询兜底、队列去重、心跳轻量化”这套组合是相对稳的落点——先把心跳的静默和退避做好，再逐步把高价值事件源迁到推送，成本和实时性可以同时兼顾。
