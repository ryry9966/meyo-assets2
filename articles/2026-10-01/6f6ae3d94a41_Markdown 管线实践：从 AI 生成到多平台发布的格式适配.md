## 背景

用 Agent 生成技术帖已经是常态，但生成只解决"写"，不解决"发"。同一篇 Markdown 要投到公众号、知乎、GitHub、静态博客，各平台对语法的支持差异很大。社区里不少人卡在"每次发文手动改一遍格式"这一步。我们把它做成了流水线：规范化 → 平台适配 → 校验 → 发布，本文记录做法和坑。

## 问题

AI 直出的 Markdown 有三类典型毛病：

1. **结构噪声**：整段回答被 ```` ```markdown ```` 包裹、标题层级跳级、列表符号混用；
2. **语法越界**：用了目标平台不支持的脚注、mermaid、task list；
3. **资源失效**：相对路径图片、临时图床链接，发布即裂图。

平台侧的限制更碎：公众号会剥掉 `<style>` 标签、过滤外链图片；GitHub 收紧内联 HTML；知乎编辑器对空行和代码块的处理和标准也不一致。逐平台手改不可持续。

## 做法

核心思路：**只维护一份规范源，平台产物全部是构建产物**。

1. **定义规范格式**。以 GFM 为底，加 YAML frontmatter（title/date/tags），明确禁用项：内联 HTML 只留白名单，不写脚注。这是唯一人工可编辑的源文件。
2. **归一化**。用 remark-parse 拿到 mdast 后跑 lint：修复标题跳级、剥离外层代码围栏、统一列表标记、给缺语言标签的代码块补默认值。规则写成 remark-lint 插件，别用正则硬匹配。
3. **平台适配器**。每个平台一个纯函数：mdast → 平台字符串。公众号走 rehype 转 HTML 后用工具内联样式；GitHub 直接序列化回 GFM；静态博客补 frontmatter。适配器无副作用，可快照单测。
4. **校验门禁**。发布前跑三件事：链接可达性检查、图片转存（下载后传到目标平台素材库或自有 OSS，替换 URL）、节点白名单检查——mdast 里出现不支持节点就直接 fail。
5. **发布**。把适配器和上传接口包成 MCP tool，Agent 只负责调 `publish(platform)`。产物版本化存档，方便回滚和 diff。

## 踩坑点

- **公众号必须内联样式**，`<style>` 会被整体剥掉；嵌套列表会被压平，超过两层改用编号段落。
- **AI 会自作主张加围栏**，整篇被 ```` ``` ```` 包住很常见，归一化第一步就是剥壳。
- **图片外链是最大故障源**，只有上传到公众号素材库后的 URL 才稳定；转存必须自动化，人肉必漏。
- **frontmatter 里的中文 tags 要加引号**，部分解析器会按逗号或空格乱切。
- **锚点和标题 ID 各平台规则不同**，文内跳转链接宁可删掉，不要赌。

## 可复用建议

- 适配器写成纯函数 + 快照测试，平台改版时只改一个文件。
- 维护一张"平台能力矩阵"（各平台支持哪些节点），校验器直接读它，新平台接入只补表。
- 源和产物分开存放，永远不要直接编辑产物。
- 归一化规则宁可保守：遇到看不懂的结构就报错，不要猜。

## 总结

多平台发布的复杂度不在写，在格式收敛。一条「规范源 + mdast 中间表示 + 平台适配器 + 校验门禁」的管线，能把每次发文的边际成本压到接近零。建议先跑通一个平台的适配器，再逐步扩矩阵，比一次性搭全家桶更实际。
