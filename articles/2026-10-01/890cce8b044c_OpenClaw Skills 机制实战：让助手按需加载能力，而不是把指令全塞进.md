## 背景

用过 OpenClaw 或类似 Agent 框架的人大概有同款体验：一开始你把所有操作指南都写进常驻提示词或 AGENTS.md——部署流程、日志排查、服务器运维……一两个月后提示词膨胀到几千 token，模型每次对话都“背着”全部知识，既费上下文，又稀释注意力，真正用到的可能不到一成。

OpenClaw 的 Skills 机制就是冲着这个问题来的：把能力拆成独立的技能目录，运行时只注入“名称 + 一句话描述”，模型判断当前任务相关时，再通过 `skills_get` 把完整说明加载进上下文。本质是渐进式披露（progressive disclosure），和 MCP 按需调用工具的思路一致，只是作用对象从"外部工具"换成了"操作知识"。

## 问题

Skills 能不能真正“按需”，靠的不是框架，而是你写得怎么样。常见的失败模式：

- 描述太模糊，模型从不主动触发，技能等于没写；
- 描述太宽泛，每次对话都加载，拆了个寂寞；
- 正文写成产品文档，模型读完仍然不知道第一步做什么。

## 做法

**1. 建目录。** 技能放在 `~/.openclaw/skills/<name>/`，核心是一个 `SKILL.md`：

```markdown
---
name: home-server-logs
description: 排查家庭服务器服务异常时使用。涵盖 journalctl 查询、常见报错定位与重启顺序。
metadata:
  requires:
    bins: ["ssh"]
---

# 排查步骤
1. 先 `journalctl -u <service> --since "1 hour ago"` 看最近报错
2. ...
```

**2. 把 description 当触发条件写。** 不要写"管理服务器"，要写"在……时使用，覆盖……"。这是模型决定是否加载的唯一依据，值得反复打磨。

**3. 正文写操作，不写背景。** 祈使句、编号步骤、可直接执行的命令。细节下沉到脚本文件，SKILL.md 里用相对路径引用，正文控制在一两百行内。

**4. 用 metadata 控制可见性。** `requires.bins` 声明依赖的可执行文件，环境里没有就自动不广播，避免模型调用一个注定失败的技能。确实需要每次常驻的（比如输出规范），再考虑 `always: true`，别滥用。

**5. 验证。** 改完直接问助手"你现在有哪些技能可用？”，或者构造一个该触发的场景实测；Gateway 侧也可以用 `skills_list` / `skills_get` 确认注入内容。

## 踩坑点

- **SKILL.md 不会常驻上下文。** 正文里引用的脚本和路径必须自包含，别假设模型“记得”上一轮读过的内容。
- **和 AGENTS.md 抢地盘。** 建议划清边界：约定类（代码风格、回复格式）留在常驻提示词，流程类（怎么完成某件事）进 Skills。
- **数量失控。** 技能列表本身也占上下文，超过二三十个就该合并同类项。
- **脚本没加执行权限**，或路径写死绝对路径，换台机器就失效。

## 可复用建议

- 一个技能 = 一个可重复任务。宁可多拆，不写大杂烩。
- description 模板：*在（什么场景）下使用，用于（达成什么），涵盖（哪些步骤）*。
- 把 skills 目录纳入 git，像 review 代码一样 review 技能改动。
- Skills 和 MCP 不冲突：MCP 提供能力（接 API、控设备），Skills 教模型用好手头的工具。动手前先想清楚缺的是哪个。

## 总结

Skills 的价值不在于“多了一种配置格式”，而在于承认一个现实：助手的知识不该一次性灌满，而应像函数库一样按需链接。写好触发描述、把正文当操作手册、控制总量——做到这三点，上下文压力和触发准确率的改善通常是立竿见影的。
