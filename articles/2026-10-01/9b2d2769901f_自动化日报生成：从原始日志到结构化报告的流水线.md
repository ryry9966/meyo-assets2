## 背景

团队每天要发一份运行日报：昨日请求量、错误率、慢查询 TopN、值得关注的异常事件。之前全靠人肉——登录几台机器 grep 日志，粘进表格，再手写两段总结。每天半小时，口径还不统一。

## 问题

拆开看有三个硬伤：

1. **日志分散**：多个服务、多种格式，采集本身就是体力活。
2. **口径漂移**：同一个"错误数"，不同人 grep 条件不一样，今天的数和昨天对不上。
3. **LLM 直接读日志不可行**：几十万行日志塞给 agent，token 爆炸不说，报告里的数字还会被"圆整"，和真值对不上。

## 做法

最终落地的流水线分五段，前四段纯代码，最后一段才交给 agent：

1. **采集**：cron 触发 OpenClaw 定时任务，通过 MCP 工具拉取昨天时间窗口内的日志与 API 数据，落到本地 staging 目录。
2. **清洗**：一个确定性脚本把多源日志归一成 JSONL——统一字段名、时间戳强制转 UTC、错误码做映射表。
3. **聚合**：还是脚本。请求数、错误率、P95 延迟、新增告警数，全部由代码算出，不经过模型。
4. **异常抽样**：规则筛出疑似值得人看的事件（错误簇、延迟突增），各取代表性样本，总量控制在 2k token 以内。
5. **摘要与投递**：agent 拿到聚合 JSON + 抽样事件，按固定 JSON Schema 输出 `{summary, highlights, risks}`，校验通过后套 Markdown 模板渲染，推送群 webhook。

核心设计一句话：**模型只负责把数字翻译成人话、把散点归纳成风险；所有数字、排序、口径都在代码侧固化。**

## 踩坑点

- **让 agent 读原始日志**：第一版图省事直接喂日志，数字对不上真值。改成代码聚合后才彻底解决。
- **时区混用**：日志里本地时间和 UTC 混着来，统计窗口每天偏 8 小时。清洗层强制统一时区，解析失败的时间戳单独计数并告警。
- **Schema 漂移**：上游改了日志字段名，流水线静默产出空报告。之后加了字段覆盖率检查，低于阈值直接 fail，宁可不出报告也不出错的报告。
- **Cron 静默失败**：任务挂了没人知道，日报缺席当天才被发现。给管道加了心跳上报，日报管道自己的故障会写进下一天的日报——这个自指设计意外地有效。

## 可复用建议

- **分工原则**：确定性的事给代码，概率性的事给模型。能算出来的数字，绝不让模型生成。
- **Schema 约束输出**：校验失败自动重试一次，再失败走人工兜底，坏报告不外发。
- **保留 dry-run**：渲染结果先落盘不推送。改模板、调口径时先跑 dry-run 看 diff。
- **模板进 git**：日报格式变更要走 commit，杜绝"这周的报告怎么又变样了"。

## 总结

上线后，日报从每天半小时人肉变成无人值守，更重要的是口径唯一、全程可回溯。这条流水线的价值不在省时间，而在**统计口径的确定性**。模型擅长叙述，不擅长算数——把算数留给代码，把叙述交给 agent，这条线就能稳定跑下去。
