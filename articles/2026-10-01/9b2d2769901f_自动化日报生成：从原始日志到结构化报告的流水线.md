## 背景

每天写日报这件事，痛点不在"写"，而在"回忆"。今天改了哪些仓库、跑了哪些任务、处理了哪些告警——信息都在日志里，但散落在 git、shell 历史、定时任务输出和聊天记录里。人肉汇总十分钟的活，做了三个月就会想自动化。

用 OpenClaw 做这件事的第一直觉是：给 Agent 一句"帮我把今天的日志整理成日报"。试过就知道，这条路走不远。

## 问题

直接让 Agent 全权负责日报，有三个硬伤：

1. **幻觉不可控**。日志缺失时，Agent 会用"看起来合理"的内容补齐，日报写错一次，信任就没了。
2. **输出不稳定**。每天格式漂移，字段时有时无，没法归档对比。
3. **采集不可测**。虽然可以用 MCP 工具让 Agent 直接拉数据，但采集要可测试、可重放，一条工具调用链失败后，你分不清是采集挂了还是模型抽风。

结论：**采集和汇总必须分层**。

## 做法

流水线分四层，核心原则是确定性的事交给脚本，模糊的事交给 Agent：

**第一层：采集（脚本）**
用 OpenClaw 的 cron 定时任务在固定时间触发一个 shell 脚本，拉取当天原始数据：`git log` 按仓库聚合、系统日志按关键词过滤、任务工具导出已完成事项。每类数据各落一个 JSON 文件。

**第二层：规范化（脚本）**
把多源数据合并成一份中间产物，固定 schema：

```json
{
  "date": "2025-06-12",
  "commits": [{ "repo": "...", "count": 7 }],
  "tasks_done": ["..."],
  "incidents": [],
  "sources": [{ "name": "git", "ok": true }]
}
```

关键是 `sources` 字段：如实记录每个数据源的采集状态，缺数据就标 `ok: false`，不静默跳过。

**第三层：汇总（Agent）**
Agent 只做一件事：读入中间产物，按固定模板填空，今日完成 / 进行中 / 问题与风险 / 数据源状态。Prompt 里明确约束：只允许使用输入中的事实，禁止推断，数据缺失就写"未采集到"，不许编。

**第四层：投递与归档**
输出写入 `reports/2025-06-12.md`，同时推送摘要到常用频道。文件名带日期，天然幂等，重跑不覆盖历史。

## 踩坑点

- **时区问题**：cron 默认 UTC，第一天日报写成了"昨天"。定时任务显式指定时区，采集脚本也按本地时间边界过滤日志。
- **日志量超限**：git log 全量塞给 Agent，token 爆炸且重点被稀释。先在脚本层聚合：按仓库计数，只保留最近 N 条 commit message。
- **Prompt 漂移**：第三层的 prompt 改来改去，输出格式跟着变。后来把模板固化成独立文件，prompt 只引用模板，改动走版本控制。
- **静默失败**：早期采集脚本挂了，Agent 拿到空数据生成了"今日无事发生"的日报。现在失败的数据源会在日报末尾显式提醒。

## 可复用建议

1. **中间 schema 是流水线的合同**。采集端和汇总端各自独立演化，只要 schema 不变，加数据源不用动 Agent。
2. **保留原始快照**。中间产物按日期落盘，日报有疑问时可人工核对，也让流水线本身可回放调试。
3. **先单源后多源**。先把 git 一个数据源跑稳两周，再接第二个。一次接三个源，排障时分不清是谁的锅。
4. **Agent 是最后一公里，不是数据管道**。凡能写成确定性规则的（过滤、聚合、去重），都别交给模型。

## 总结

这套流水线跑了两个月，日报稳定生成，我再没手写过。回头看，价值不在某个精妙的 prompt，而在分层设计：脚本保证事实准确，schema 保证格式稳定，Agent 只负责它擅长的语言组织。日报只是最小场景，同样的骨架可以平移到周报、告警摘要、项目状态同步，只要记住：让确定性的事保持确定性，Agent 才能发挥真正的价值。
