## 背景

做 Agent 项目时间长了，系统提示词会不可避免地膨胀：工具说明、业务规则、输出格式、各种 SOP 全部塞在开头。OpenClaw 的 Skills 机制提供了一条更工程化的路：把能力拆成独立的"技能包"，会话启动时只注入一份极简的元数据清单，模型判断任务需要时才完整加载对应技能。

核心思路是**渐进式披露**——不是把所有说明书摊在桌上，而是先给目录，需要哪本翻哪本。

## 我们遇到的问题

- **上下文成本**：十几个能力全量前置，光描述就吃掉几千 token，长会话尤其明显。
- **注意力稀释**：无关指令越多，模型在关键步骤上的遵循度越差，这是实测能感知到的。
- **维护困难**：单体 system prompt 改一处怕碰坏全局，没人敢动。
- **复用为零**：能力绑定在某个 agent 配置里，换个项目只能复制粘贴。

## 做法：写一个能被正确触发的 Skill

OpenClaw 的 skill 本质是一个目录，入口是 `SKILL.md`：

1. **建目录**。放在 skills/ 下，比如 `skills/report-export/`。
2. **写头部元数据**：`name` 和 `description`。注意 description 是触发依据，要站在模型视角写清"什么时候用"，例如："当用户需要把对话内容整理导出为周报格式时使用。"
3. **正文只写操作要点**：步骤、约束、注意事项，控制在几十行以内。
4. **复杂细节下沉**到同目录的 `references/` 或 `scripts/`，SKILL.md 里只放引用说明。能写成确定性脚本的就别用自然语言描述，脚本比散文可靠。
5. **双向验证**：给一个相关任务确认技能被加载，再给一个不相关任务确认它没被误加载。两步都要做。

运行时链路很直接：启动时只装载所有技能的 name + description 组成的清单 → 用户请求进来 → 模型匹配到某条描述 → 通过读取工具拉取完整 SKILL.md → 按正文执行，需要时再读附属文件。已有的 MCP 工具也可以在正文里引用：技能负责"什么时候用、怎么组合"，工具负责"怎么做"。

## 踩坑点

- **description 写得太泛**（如"处理数据相关任务"）会导致永不触发或次次触发，等于白拆。
- **一个技能塞所有内容**，等于把单体 prompt 换了个目录存放，披露机制完全失效。
- **技能内文件用绝对路径**，换台机器就断，统一用相对于技能目录的路径。
- **技能数量失控**：清单本身也占上下文，三十个零散技能不如按域合并成六七个。
- **只测 happy path**：触发本质是语义匹配，边界表述一定要覆盖到。

## 可复用的经验

- description 套路：**能力 + 触发条件**，一句话说清"做什么、何时用"。
- 一个技能一个职责，宁可多拆，不要糊在一起。
- 像管依赖一样管 skills：进 git、写变更说明、附带触发用例。
- 技能正文属于"热加载"内容，同样消耗 token——保持精简，细节放二级文件。

## 总结

Skills 机制的价值不在"能加功能"，而在把能力的**声明成本**和**加载成本**解耦：清单常驻、正文按需，上下文预算从固定支出变成按使用计费。把它当成一个依赖管理问题来做——小颗粒、清晰的触发条件、版本化维护——Agent 的能力扩展才能长期保持可控。
