## 背景

跑 Agent 的同学对这种场景不陌生：任务跑到一半，某个 MCP 工具背后的第三方 API 开始返回 503，或者模型供应商突然限流。这时候 Agent 不会"体面地退出"——如果恢复逻辑没写好，它通常做三件事之一：原地死循环重试、整个流程卡死，或者更糟，对着一次失败的调用自由发挥，编一份看起来合理的答案交差。

外部依赖多，是 Agent 和普通脚本的天然区别。插件化架构里，一条任务链可能串着 LLM 调用、MCP 工具、webhook、数据库，任何一环都是故障点。错误恢复不是可选项，是基础设施。

## 三种典型翻车

1. **重试风暴**：遇到 429/5xx，模型在循环里反复调用，token 烧完，对端压力更大。
2. **无限阻塞**：工具调用没设超时，对端挂起，整个 Agent 事件循环跟着挂起。
3. **幻觉兜底**：工具返回失败，模型不承认失败，而是"推测"了一个结果继续往下走。这是最危险的，因为流程表面上是通的。

## 做法：恢复逻辑放代码层，不放模型里

核心原则一句话：**重试、熔断、超时是工程问题，用代码解决；模型只负责基于明确的信息做决策。**

**第一步：错误分类。** 分成可重试（超时、429、5xx、网络抖动）和不可重试（400、401、403、业务校验失败）。对后者重试没有意义，应直接失败并说明原因。

**第二步：代码层重试。** 指数退避加随机抖动，次数封顶（一般 2–3 次）。重试要放在工具封装层，而不是让模型在对话里"决定再试一次"——模型的 retry 策略不可控，容易走极端。

```python
result = with_retry(call_api, retries=3, backoff="exp+jitter")
if not result.ok:
    return {"ok": False, "error_code": result.code,
            "retryable": result.retryable, "hint": "..."}
```

**第三步：熔断。** 对同一端点，连续失败 N 次后进入冷却期（比如 60 秒），期间直接走降级路径，不再打对端，恢复后半开试探。粒度按端点算，不要按整个插件算。

**第四步：降级链。** 主服务 → 备份服务 → 本地缓存/上次成功结果 → 明确报错给用户。关键是必须有"降级模式"：宁可给出略旧的数据并标注来源，也不要沉默失败。

**第五步：把失败显式交给模型。** 工具返回结构化错误（错误码、是否可重试、建议动作），并在系统提示里写明：工具失败时如实报告，禁止编造结果。模型不是不能参与恢复，但它需要干净的信息。

**第六步：检查点。** 长任务在关键步骤落盘状态，故障后从断点恢复，而不是从头再来——尤其是重跑有副作用的任务。

## 踩坑点

- **非幂等操作重试**：POST 下单重试三次可能下三单。写操作必须带幂等键，或确认未生效后再重试。
- **退避不加抖动**：一堆 Agent 同时重试，等于自己对自己发起洪水攻击。
- **吞错返回空结果**：`return None` 或空字符串是幻觉的温床。失败就是失败，明确返回。
- **错误信息太模糊**："操作失败"让模型没法决策。至少带上错误码和"该重试还是该放弃"的提示。
- **超时设太长**：单线程 Agent 运行时里，一个 120 秒的超时能把整条流水线堵死。按操作类型分级设置。

## 可复用建议

1. 所有外部调用过同一个 wrapper：超时 + 重试 + 熔断 + 标准错误信封，一处修好处处生效。
2. 给每个任务设总预算：最大墙钟时间、最大重试次数、最大 token 消耗，超了就降级或上报人工。
3. 定期做故障演练：手动 kill 掉 MCP server、断网、模拟 429，验证降级路径真的能走通。没演练过的降级路径约等于不存在。

## 总结

外部 API 挂掉不是意外，是常态。恢复能力的设计目标是：失败要快、原因要明、要有退路、可以续跑。把这些做在代码层，模型层只拿到干净的结构化结果，你的 Agent 才能在依赖抖动时保持体面。欢迎在评论区贴出你们踩过的 API 故障案例和恢复方案。
