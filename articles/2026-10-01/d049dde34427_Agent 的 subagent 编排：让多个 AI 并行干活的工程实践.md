## 背景

单个 agent 串行干活有两个天花板：一是速度，十个独立任务只能一个个跑；二是上下文，长任务的中间输出会把主会话撑爆，越到后面质量越差。OpenClaw 的 subagent 机制（派生带独立上下文的子 agent）本质上是把「并行」和「隔离」两个问题一起解决。这篇记录我最近在批量信息整理和多文件重构两个场景里的编排实践。

## 问题

具体痛点有三个：

1. 一次让主 agent 读二十个网页做摘要，串行跑十几分钟，中途 context 里塞满原始网页内容，后面开始丢细节。
2. 多文件重构时，主 agent 边读边改边记，上下文互相污染，改到一半忘掉前面的约定。
3. 子 agent 并不是开起来就完事：并发多少、任务怎么传、结果怎么收、失败怎么办，都得设计。

## 做法

我的编排流程分四步：

**1. 拆任务，先判断可并行性。** 只拆「输入独立、输出独立」的任务。读十个网页分别做摘要、给十个模块分别写测试，都适合；有共享状态或顺序依赖的，老老实实串行。

**2. 写自包含的任务提示词。** 子 agent 看不到主 agent 的对话历史，任务描述必须包含全部上下文：目标、输入位置、约束、期望输出格式。我的模板固定四段：目标 + 输入 + 约束 + 输出格式（限定为两百字内摘要加关键结论列表）。

**3. 控制并发。** 实测 3~5 个并行比较稳，再多容易撞 API 限流，本机资源也吃紧。批次之间等上一批全部结束再发下一批。

**4. 结构化回收。** 要求每个子 agent 把结果写入指定文件或以固定格式返回，主 agent 只读汇总，不读过程。这一步是保住主 context 的关键。

## 踩坑点

- **多个子 agent 写同一个文件**：结果互相覆盖。改成每个子 agent 写独立文件，主 agent 统一合并。
- **返回内容太长**：有一次五个子 agent 各回传三千字，主 context 直接被塞满，汇总质量明显下降。改成子 agent 落盘完整结果、只回传摘要，主 agent 需要时再按路径取原文。
- **任务提示词不自包含**：子 agent 收到「按之前的约定改」，但它没有「之前」，只能瞎猜。所有约定必须显式写进任务里。
- **忽略失败分支**：并行任务里一个超时，整批结果就不完整。现在每批结束先核对成功数量，缺的单独重跑，不做静默降级。
- **并发上限拍脑袋**：一开始开 10 个，限流报错加重试反而更慢。降回 4 个，总耗时反而更短。

## 可复用建议

1. 把「子 agent 任务模板」沉淀成插件或 prompt 片段，四段式结构固定，每次只填空。
2. 用文件系统做子 agent 之间的交接媒介，比往提示词里塞大段文本可靠。
3. 维护一个简单台账（哪怕就是一个 md 文件），记录任务 ID、状态、结果路径，排查问题快很多。
4. 先用 2 个子 agent 验证任务描述是否自包含，跑通后再放量。
5. 成本敏感的场景，把「读」交给子 agent 并行，「写」和决策留在主 agent，避免并发写坏状态。

## 总结

subagent 编排的核心不是「多开几个 AI」，而是任务边界的划分和上下文的管理：拆得动才并行，传得全才独立，收得拢才有用。把并发数、输出格式、失败重试这三个参数调好，串行十几分钟的活压到两三分钟是常态。建议从一个低风险场景（比如批量摘要）开始跑通全流程，再逐步搬到更关键的任务上。
