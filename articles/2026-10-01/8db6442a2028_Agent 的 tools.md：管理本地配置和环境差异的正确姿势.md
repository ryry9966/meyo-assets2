## 背景

跑 Agent 的人大多不止一台机器：日常开发本、家里的宿主机、CI，偶尔还要借同事环境跑批。每换一个环境，Agent 面对的现实就变一次——脚本路径不同、Python 版本不同、某个 MCP server 只在内网可达。这些信息如果不落盘，就只能硬编码进系统提示，或者靠 Agent 每次现场摸索，白白烧 token。

tools.md 的定位很简单：一份 Agent 启动时读取的“环境说明书”，告诉它这里有哪些工具、怎么调用、有哪些前提。在 OpenClaw 里，工作区的说明文件就是它的挂载点：冷启动读一次，之后的行为都以此为基准。它是给 Agent 看的 README，不是给人看的文档。

## 问题

常见的三种翻车方式：

1. **硬编码在全局提示里**。把 `/home/zhang/scripts/backup.sh` 这类绝对路径写死，换台机器就静默失效，Agent 还会假装知道。
2. **一份配置走天下**。团队共享一份 tools.md，但 macOS 和 Linux 的路径、包管理器全不一样，后来大家干脆不看它。
3. **文档漂移**。环境改了文件没改，Agent 按过时说明操作，比没有说明更糟。

根因是同一个：把“团队共识”和“本机事实”混在一个文件里。

## 做法：两层拆分 + 脚本校验

**1. base 层：`tools.md`（入库）**
只放团队共识：工具能力边界、调用协议、输出格式约定、公共注意事项。路径一律用相对路径或环境变量占位，不出现任何机器特定信息。

**2. local 层：`tools.local.md`（gitignore）**
只放本机事实：绝对路径、本地端口、GPU 型号、内网服务的可达条件。硬规则：密钥只写“从环境变量 `DEPLOY_TOKEN` 读”，永远不写值。

**3. 固定条目 schema**
每个工具条目统一结构：名称、调用命令、前置条件、输出格式、已知问题。结构固定才能被脚本校验，Agent 也能精确检索。

**4. 写一个 doctor 脚本**
遍历 local 层逐条验证：路径存在吗？命令可执行吗？端口通吗？失败条目自动标记。脚本进 CI 或 cron，保证文件不会烂掉。

**5. 明确加载与失效规则**
Agent 启动先读 base 再读 local，同名条目 local 覆盖；工具调用失败时，第一步是核对 tools.md 是否与现实一致，而不是盲目重试。

## 踩坑点

- **别写成长文**。tools.md 全量进上下文，2000 行等于每次对话烧钱。控制在几百行，长细节拆子文件按需读。
- **别和 MCP 配置重复**。MCP 配置管“怎么连”，tools.md 管“怎么用、什么能用”，调用细节两边都写必然漂移。
- **缓存陷阱**。有的运行时会缓存启动时读入的内容，改了文件不生效。要么重启会话，要么提供显式刷新指令，并把失效规则写在文件头部。
- **local 层也会烂**。doctor 覆盖不到的条目（比如“这台机器 GPU 是 4090”）没法自动校验，建议让 Agent 在会话开头抽查一两条并主动回报。

## 可复用建议

- schema 优先于内容：先定条目结构，再填信息。
- “引用密钥而非密钥值”写进团队规范，当硬规则执行。
- doctor 输出健康报告，人工只 review 失败项。
- 把“环境变更必须同步 tools.md”纳入 code review 检查项，靠流程而不是自觉。

## 总结

tools.md 不是又一份文档，而是 Agent 与运行环境之间的契约。分 base/local 两层、固定 schema、脚本校验、明确失效规则——做到这四点，同一套配置就能在开发本、服务器和 CI 之间安静地工作，而不是每次换环境都重新吵架。
