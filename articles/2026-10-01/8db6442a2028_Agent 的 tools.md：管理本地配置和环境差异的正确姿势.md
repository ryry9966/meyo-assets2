## 背景

跑 Agent 做本地自动化，最常翻车的往往不是模型能力，而是环境假设。同一套提示词，在你的 Mac 上跑通了，到同事的 Linux 机器或家里的服务器上就找不到 `brew`、路径对不上、包管理器完全不同。很多人的应对方式是把这些差异硬塞进 system prompt，写成"如果是 macOS 就……如果是 Linux 就……"的条件分支，几轮迭代后提示词膨胀成没人敢动的泥球。

tools.md 的思路很朴素：把这些"机器事实"从提示词里拆出来，变成一份 Agent 启动时会读的文档。

## 问题

实践中反复出现四类麻烦：

1. **幻觉工具路径**：Agent 凭训练记忆猜 `node`、`ffmpeg` 装在哪，实际机器上根本没装。
2. **配置散落三处**：shell rc、`.env`、提示词片段各存一份，改了一处忘两处。
3. **团队没法同步**：每人机器不同，本地配置提交了污染别人，不提交又没法复现。
4. **密钥误提交**：本地 override 和凭据混在一个文件里，一不留神进了 git 历史。

## 做法

**1. 分层：两个文件，职责分开**

- `tools.md`：团队共享，进版本库。只写"这个项目期望什么"，不写"我机器上有什么"。
- `tools.local.md`：本地覆盖，进 `.gitignore`。写"我这台机器的实际事实"。

读取顺序固定：local 覆盖 shared，Agent 侧不需要知道分层存在。

**2. tools.md 用三段式**

- **环境事实**：OS、包管理器、代理、Python/Node 版本约束。
- **工具清单**：用表格，每行四列——工具 | 调用命令 | 版本要求 | 备注，附一条最小可用的调用示例。
- **约定**：测试怎么跑、日志在哪、哪些目录 Agent 不许碰。

**3. 关键一步：local 部分用脚本生成，别手写**

手写的 local 文件两周必过期。写一个 `doctor` 脚本，检测实际安装的工具、路径、版本，diff 后重写 `tools.local.md`，Agent 启动前跑一次，文件永远新鲜。版本不符就直接报错退出，比让 Agent 撞墙后自己排查省一个数量级的时间。

**4. 注入方式与密钥边界**

启动 hook 里让 Agent 先读这两个文件再干活。MCP 场景下把 server 名字和用途列进工具清单，但凭据只写变量名（如 `GITHUB_TOKEN` 从 `.env` 读取），tools.md 里永远不出现真实值。

## 踩坑点

- **写成大段散文**。Agent 检索表格远比检索段落准确，能用表格就用表格。
- **和 system prompt 重复**。同一事实写两处必然漂移，提示词里只留一句"先读 tools.md"。
- **过度指定流程**。写契约（"测试用 `pnpm test` 跑"）而不是步骤剧本，否则 Agent 丧失纠错空间，一出错就卡死。
- **local 文件变垃圾场**。每条记录加"verified on"日期，doctor 脚本重写时自动刷新，过期条目直接删。
- **Windows 编辑引入 BOM/CRLF**，表格解析出错。仓库里加一份 `.editorconfig` 一劳永逸。

## 可复用建议

- 一个能填的模板比一次性的完美更重要：环境事实 / 工具清单 / 约定，三段固定，新成员照着填就行。
- doctor 脚本模式可以推广：除了生成 local 文件，还能在 CI 容器里校验 `tools.md` 与真实环境的偏差，漂移在合入前就被拦住。
- 新增工具条目前先问一句："Agent 能不能一条命令调起来？"不能，就先别写进去。

## 总结

tools.md 本质上是给 Agent 写的入职文档。把它当代码对待：分层、进版本库、能用脚本生成就不手写、定期校验。环境差异永远存在，正确姿势不是消灭差异，而是把差异收敛到一份 Agent 读得懂、你也维护得起的文件里。
