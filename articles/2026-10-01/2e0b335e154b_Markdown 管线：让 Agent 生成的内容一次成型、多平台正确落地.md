## 背景

社区里不少人已经用 OpenClaw 把内容生产交给 Agent：让模型写技术文章、周报、发版说明，再分发到公众号、掘金、知乎、GitHub 和自建博客。跑起来后很快会发现，AI 输出的 Markdown 只是“看起来像 Markdown”，直接丢给各平台，一个平台一种死法。这篇记录我们把这条链路收敛成一条管线的做法。

## 问题

三个核心矛盾：

1. **平台方言差异巨大**。公众号编辑器基本只吃带内联样式的 HTML；掘金、知乎支持标准 MD 但扩展语法各不相同；GitHub 全支持，移动端预览又是另一回事。
2. **模型输出不稳定**。标题跳级、列表嵌套缩进混乱、代码块语言标签乱写，偶尔还夹带 `<br>`、`<details>` 这类 HTML 片段。
3. **图片是隐形炸弹**。外链图在公众号会被防盗链拦截，不转存必挂。

## 做法

核心原则：**单一事实源 + 标准化中间层 + 平台适配器**。

1. **约束生成端**。在 Agent 的 system prompt 里限定“MD 方言”：只用两级标题、禁用 HTML、禁用脚注和任务列表、代码块必须带语言标签。事后修复永远比事前约束贵。
2. **标准化层**。拿到输出先规范化：基于 mdast（Markdown AST）而非正则做检查——标题层级重排、缩进统一、HTML 剥离或转译。产出“规范 MD”，所有下游只认它。
3. **平台适配器**。每个目标平台一个纯函数：规范 MD → 平台格式。公众号适配器把 AST 渲染成内联样式 HTML 并处理图片转存；博客适配器基本透传。适配器注册成 MCP tool，Agent 按目标平台调用。
4. **校验**。发布前用 headless 浏览器截图渲染结果，与快照基线比对；图片上传后校验 URL 可达。失败信息回喂给 Agent 重试。

## 踩坑点

- **别用正则做全局替换**。嵌套代码块会让正则误伤，务必走 AST。
- **公众号图片接口有频控**，批量发布要加队列和重试，且注意幂等——同一张图别传两遍。
- **代码高亮**各平台对类名支持不一，干脆在服务端渲染时就内联 style，不指望平台的高亮。
- **宽表格在移动端必崩**，适配器里写死规则：超过 N 列自动降级为列表。
- 模型偶尔会输出“Markdown 套 Markdown”（代码块里再包一层），标准化层要能识别解包。

## 可复用建议

- 把“MD 方言约束”沉淀为共享 prompt 片段，所有内容类 Agent 复用。
- 适配器保持纯函数，上传、发布这类 IO 单独拆出，方便单测。
- 快照按平台分目录，平台改版时更新基线即可定位差异。
- 每个平台维护一份 quirk 清单，后人不用重新踩坑。

## 总结

这条管线没有黑科技，本质是编译器思路：方言约束（前端）、AST 标准化（中间表示）、平台适配（代码生成）、渲染校验（测试）。跑通之后，新增一个平台就是写一个适配器的事。投入一两天搭这套骨架，比每次手工改格式划算得多。
