## 背景

我们团队的服务每天产生几万行日志和若干脚本输出。日报这件事，过去一直靠人肉：早上打开监控看一眼，复制几个数字，拼一段“昨晚服务稳定”。问题在于，真正有价值的信号（一次 retry 风暴、一个磁盘水位爬升）往往被淹没在例行数字里，人肉复制还经常漏。

这篇帖子记录我们用 OpenClaw + MCP 搭的一条日报流水线：原始日志进，结构化报告出，全程无人在场。

## 问题拆解

把“写日报”拆成四件事：

1. **采集**：把散落在不同地方的日志、指标、事件收拢到一个工作目录
2. **预处理**：去噪、按时间窗切片，压缩到 Agent 能一次读下的体量
3. **分析**：让 Agent 按固定 schema 抽取异常、归类、写摘要
4. **产出**：用确定性代码（不是 Agent）渲染模板并推送

关键判断是：**分析交给 Agent，格式交给代码**。

## 做法

流水线每天 08:30 由 cron 触发一个 OpenClaw 任务，步骤如下：

**步骤 1：采集脚本先跑。** 一个 bash 脚本把昨天的 nginx error log、应用日志、监控快照查询结果落到 `daily/YYYY-MM-DD/` 目录。脚本返回非零码就中止，不进 Agent。

**步骤 2：预处理。** 用 grep/jq 过滤掉例行 INFO 噪音，只保留 WARN 以上加少量采样。这一步把 3 万行压到 500 行以内；压不下来的日子，按错误指纹聚类去重。

**步骤 3：Agent 分析。** 给 Agent 一个固定的 JSON schema：`summary`、`incidents[]`、`metrics`、`follow_ups[]`，要求只输出 JSON，不做自由发挥。通过 MCP 读本地文件，逐段抽取填空。

**步骤 4：确定性渲染。** Python 脚本用 jsonschema 校验输出，不合格走降级逻辑：报告只贴原始摘要加一句“分析失败，需人工”。合格的填进 Markdown 模板，推送群里。

整体是“脚本包着 Agent”的结构：Agent 只是中间一环，不是入口，也不是出口。

## 踩坑点

- **时区**。日志是 UTC，日报按本地时间，第一版把“昨天”算偏了 8 小时，报了一堆无关错误。统一在预处理阶段按本地时区切片。
- **输出漂移**。前两天很稳，第三天 Agent 开始在 JSON 外面包一句“好的，以下是分析结果”。解法：解析前做宽松清洗；渲染层校验失败必须降级，而不是报错崩溃。
- **上下文超限**。偶发的巨型堆栈一进来就爆 token。预处理加硬截断：单文件超 300 行先聚类再采样。
- **静默失败**。cron 跑挂了没人知道，群里的日报直接消失。兜底规则：流水线无论成败都发消息，失败时发最小摘要。

## 可复用建议

- **Schema 先行**：先定日报的 JSON 结构，再写 prompt。Agent 是填充者，不是创作者。
- **入口出口都不给 Agent**：采集和推送用确定性脚本，Agent 只做中间的结构化。
- **必须有降级路径**：任何一天分析失败，日报依然要出现，哪怕只是原始数据摘要。
- **先 dry-run 一周**：报告先发给自己不发群里，人工抽查准确率，别把幻觉固化进工作流。

## 总结

这条流水线上线一个月，日报从每天十来分钟的人肉活变成零干预。更重要的是格式稳定、可追溯：每天一个目录、一份 JSON、一份 Markdown。Agent 在这里的价值不是“会写报告”，而是在固定 schema 下做机械抽取——恰好是它最可靠的那一面。如果你也在 OpenClaw 里做类似自动化，建议从最痛的一张日报开始，把整条链路控制在“一晚能调完”的规模。
