## 背景

OpenClaw 从设计上就不绑定单一模型：主 agent、子任务、工具调用、embedding 都可以指向不同 provider。但在社区里见到的用法常走两个极端——要么全量走云端 GPT，要么在隐私焦虑驱动下全量本地化。前者费用和延迟会吃掉自动化链路的预算，后者在复杂任务上质量明显掉档。

## 问题

真正的问题不是"哪个模型更好"，而是**任务本身是异构的**：

- 复杂多步规划和高频简单分类，对推理质量的要求差几个量级；
- 聊天记录、本地文件这类上下文不适合出网；
- 本地模型在工具调用、长上下文、结构化输出上是重灾区。

所以需要的是**按任务维度路由**，而不是按信仰选边。

## 做法

**1. 先建决策表，再写配置。** 按五个维度给任务分类：复杂度、频率、隐私敏感度、延迟容忍、是否结构化输出。这一步不依赖任何框架能力。

**2. 配置层：主模型 + 规则路由 + fallback 链。** 云端和本地 provider（Ollama / LM Studio）都注册进 OpenClaw，示意如下（字段名随版本变化，看核心结构即可）：

```json
{
  "agents": { "defaults": {
    "model": { "primary": "openai/gpt-4.1",
               "fallbacks": ["ollama/qwen2.5:14b"] } } },
  "routing": { "rules": [
    { "when": { "task": ["classify", "summarize", "extract"] },
      "use": "ollama/qwen2.5:14b" },
    { "when": { "privacy": "sensitive" }, "use": "local-only" },
    { "when": { "planning": true }, "use": "cloud-only" } ] }
}
```

**3. 钩子层兜底。** 规则路由粒度不够时，写一个 router 钩子，在消息进入 agent 前根据元数据（来源渠道、token 数、是否带文件）打标签再选模型。比关键词匹配稳得多。

**4. 观测层对账。** 给路由决策打日志，按"任务成功率 / 成本 / P95 延迟"三列复盘，用固定的 20~30 个真实任务做回归集。别靠体感调路由。

## 踩坑点

- **工具调用静默失败**：本地模型的 function calling 实现差异很大，症状是不报错但工具从不被触发。先拿一个只带两三个工具的最小 agent 在目标本地模型上跑通，再上线。
- **上下文窗口不对齐**：云端 128k、本地 8k~32k，截断丢掉的往往是 system prompt 尾部的工具说明，表现为 agent"失忆"。本地路由要配独立的压缩策略。
- **本地不一定更快**：消费级显卡在长上下文下首 token 慢、并发差。只有小上下文的高频任务才真正吃到本地红利。
- **别把规划步骤给弱模型**：规划错一步，后面工具全白跑，省下的钱不够重试。
- **量化模型输出 JSON 不稳**：结构化输出任务要留校验 + 重试。

## 可复用建议

- 默认分工：规划/复杂推理→云；分类、抽取、改写、routine 确认→本地；embedding 和本地 RAG→常驻本地；云端故障→本地兜底。
- 隐私是硬约束时，在**入口**做路由（数据不出网），不要依赖模型侧的承诺。
- fallback 链必须带超时——本地模型挂起比云端报 5xx 更难察觉。
- 路由规则宁少勿多：先两条规则跑两周，有数据支撑再加。

## 总结

多模型路由的价值不在省钱本身，而在于让 OpenClaw 自动化链路的每个环节拿到"够用且稳定"的推理能力。先用最小规则集 + 日志对账跑起来，再逐步收紧，比一次性设计一套复杂路由系统靠谱得多。
