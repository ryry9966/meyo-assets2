## 背景

用 OpenClaw 做写作型 Agent 的人大多遇到过同一个场景：Agent 产出一份 Markdown，接下来要发公众号、知乎、掘金、静态博客，可能再推一份 RSS。Markdown 看起来是通用语，但"通用"只到字面为止——真正麻烦的是各平台渲染器各说各话，同一份源文件在五个渠道能长出五种样子。

## 问题

AI 生成的 Markdown 还有一层自身缺陷：标题层级跳跃（H1 直接跳 H4）、加粗滥用、嵌套列表混乱、代码块缺语言标注、偶发夹带 HTML。如果每处平台差异都靠提示词让 LLM"顺便改一下"，结果是同一份内容在不同渠道不一致，且每次重跑不可复现。格式适配需要一个确定性的环节。

## 做法

把发布拆成四段管线，LLM 只负责第一段：

1. **生成端收口**：在 Agent 的 skill/prompt 里约束方言——只用 GFM、固定 frontmatter 字段、禁 HTML、图片用占位路径。
2. **规范化**：入库前跑 markdownlint + prettier，修标题层级、补代码块语言、统一标点。纯代码执行，失败就打回重新生成，不做静默兜底。
3. **AST 变换**：用 remark/mdast 解析成中间表示（IR），平台差异全部写成小型 transformer，例如"外链转文末引用列表""表格超过 N 列转列表""图片 URL 替换为素材库地址"。
4. **平台适配器**：每个目标平台一个薄适配层。公众号用 remark-rehype + 内联 CSS，代码块预渲染成带样式的 HTML；知乎/掘金基本走原生 Markdown，只裁剪不支持的标签；静态博客注入 frontmatter 交给构建器。

发布前加校验：渲染结果做快照 diff，再跑一遍链接可达性检查。整条管线封装成 MCP tool 暴露给 Agent，Agent 只调用 `publish(platform, doc_id)`，转换逻辑全在工具内部，保证幂等——重跑不产生重复文章。

## 踩坑

- 公众号会**静默吞掉 `<a>` 外链**，表现为发布后丢链接，必须提前转文末引用，别指望平台提示。
- 图片防盗链：知乎/公众号会挂掉多数图床外链，统一转存比逐个排查便宜。
- LLM 输出的表格列数不稳定，移动端一宽就溢出，生成端设列数上限比渲染端缩放靠谱。
- 数学公式是最深的坑：KaTeX 在公众号基本不可用，要么转图片，要么在生成端直接禁用。
- 多余转义：Agent 偶尔输出 `\*` 这类字符，部分平台会原样显示，规范化时统一剥掉。

## 可复用建议

- 原则一句话：**内容归 LLM，格式归代码**。凡是能用 AST transformer 表达的规则，不要写进提示词。
- IR 是管线的核心资产，适配器保持薄，新平台接入通常一两百行。
- 沉淀一个 golden test 语料集（含表格、公式、长代码块的恶劣样本），每次改 transformer 全量回归。
- 生成端约束比渲染端修补便宜一个数量级，值得反复迭代 skill 里那几条方言规则。

## 总结

多平台发布不是渲染问题，而是"方言治理"问题。先把 AI 输出收口到受控的 Markdown 方言，再用确定性 AST 变换处理平台差异，让 LLM 退出格式适配的最后一公里。管线搭稳后，接入一个新平台的成本会稳定在一个下午的量级。
