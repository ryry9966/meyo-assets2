## 背景

Agent 本身只会"想"，真正落地的能力来自外部服务：查工单、发消息、拉数据。OpenClaw 的对接层本质上是一层工具协议——你把服务包装成结构化的工具或 MCP server，Agent 负责决定何时调用、传什么参数，剩下的事交给这层"握手"。这篇帖记录一次把内部 REST 工单接口接进 OpenClaw 的过程，以及中间踩的坑。

## 问题

直接把 API 文档丢给 Agent 是行不通的，实际会遇到三类问题：

1. Agent 编造调用结果或参数，看起来像调通了，其实没有；
2. 鉴权没有安全通道，key 要么写进 prompt 造成泄露，要么根本没传上；
3. 接口超时或报错后，Agent 陷入无意义的重试循环，烧 token 也烧对端配额。

## 做法

1. **写一个薄适配层**。别让 Agent 直接面对原始 HTTP。用几十行的插件函数包住请求：固定 base URL、注入 header、统一错误格式。
2. **定义严格的工具 schema**。参数名、类型、必填项、枚举值写清楚；description 一句话说清"什么时候该调用我"，不要复述文档。
3. **鉴权走环境变量**。token 放在插件启动时读取的环境变量里，绝不进上下文、不进日志。
4. **控制返回体**。接口返回 200 条记录时，适配层做分页裁剪和字段过滤，只把决策需要的字段送回上下文。
5. **超时与重试收口在适配层**。超时 8 秒、最多重试 2 次、指数退避；失败翻译成一句人话返回，例如"工单服务暂时不可用，已停止重试"。
6. **灰度验证**。先在测试环境跑十条真实 case，对比 Agent 实际传参和预期，再放开到日常会话。

## 踩坑点

- **description 写得太泛**。"查询数据"这种描述会让 Agent 在不该调用时调用。改成"当用户明确要求查询工单状态时调用"，选择准确率立刻上升。
- **返回原始 JSON**。一次 8KB 的响应直接把上下文撑爆，后续输出质量明显下降，裁剪是必须的。
- **吞掉错误**。适配层 catch 后返回空字符串，Agent 会以为成功并继续编。错误要显式、可读地返回。
- **工具数量膨胀**。挂到 20+ 个工具后选择准确率下降，低频工具该合并合并、该下线下线。
- **忽略限流**。对端 429 之后适配层要主动退避，否则 Agent 的重试会把配额烧光，还可能触发封禁。

## 可复用建议

- 一个工具只做一件事，复合操作拆成多个工具让 Agent 自己编排；
- 适配层返回结构统一成 `{ok, data | error}` 三段式，Agent 判断更稳；
- 每次工具调用落日志（参数、耗时、状态码），排障效率提升非常明显；
- 新服务先接只读接口，写操作一律加确认环节再执行。

## 总结

对接外部服务的核心不是"能调通"，而是把不确定性收口在适配层：鉴权、超时、限流、返回裁剪都在这一层解决，Agent 只面对干净、诚实、边界清晰的工具。握手协议做得越克制，Agent 的行为就越可预期——这也是这套对接方式能在生产里跑下去的前提。
