## 背景

Agent 的价值不在“会说”，而在“能做”。OpenClaw 作为跑在本地的 Agent 网关，落到真实场景里绕不开一个问题：怎么让它稳定地调用外部服务——查工单、发通知、拉报表、操作内部系统。LLM 的 tool call 只负责“决定调什么”，剩下的握手细节全要自己接住。

## 问题

把一个 HTTP API 裸塞给 Agent，通常在三个地方翻车：

1. **鉴权**：key 写进配置文件跟着仓库走，或者硬编码在工具描述里；
2. **返回值**：接口吐 50KB 的 JSON，直接怼进上下文，token 烧掉一半，模型还看不清重点；
3. **失败语义**：超时、429、5xx 全变成一句模糊报错，模型只能瞎猜该重试还是放弃。

## 做法

我的路径是：**通用能力用 MCP 包一层，一次性的用薄插件**。步骤：

1. **定义工具 schema**：用 zod 描述入参，description 要按模型视角写——“YYYY-MM-DD 格式的日期”远比“日期”可靠。
2. **实现 handler**：fetch 里配 timeout（10~15s）、指数退避重试（只对 GET 等幂等操作），鉴权头走环境变量。
3. **裁剪返回值**：只挑模型需要的字段，长列表截断到前 N 条并注明总数。宁可二次调用取详情，不要一次灌全量。
4. **错误结构化**：失败时返回 `{ ok: false, reason: "rate_limited", retry_after: 30 }` 这种形态，让模型能做决策，而不是抛异常把它逼进兜底话术。
5. **注册与灰度**：MCP server 挂进 OpenClaw 配置，先在单人会话跑通，再放开到群聊和定时任务。

## 踩坑点

- **写操作没做幂等**：Agent 重试导致重复建工单。给写接口加 client 生成的 idempotency key，能救命。
- **用户输入直拼 URL**：模型把用户原话塞进 path 参数，中文没 encode 直接 400。入参先校验再转义。
- **工具太“大”**：一个工具十几个可选参数，模型选不对。拆成两三个语义清晰的小工具，调用准确率明显回升。
- **忽略时区**：API 吃 UTC，用户说“今天”，Agent 传成了 UTC 的“昨天”。

## 可复用建议

- 工具描述就是给模型看的接口文档，值得花一半的工时去打磨；
- 每次调用记一行日志：工具名、入参摘要、耗时、状态码——排障基本全靠它；
- 别急着抽象：先跑通一个最小的 handler，等第三个类似需求出现再沉淀成公共 MCP 包。

## 总结

对接外部服务的本质，是把网络世界的脏活——鉴权、重试、裁剪、幂等——挡在 Agent 前面，只把干净、可决策的结果交给模型。握手握的是协议，不是运气。
