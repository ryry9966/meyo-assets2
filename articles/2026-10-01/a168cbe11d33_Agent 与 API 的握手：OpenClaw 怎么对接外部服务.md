## 背景

Agent 真正能干活，靠的不只是更强的模型，而是它能稳定调到的那些外部服务：查工单、读数据库、触发 CI、发通知。在 OpenClaw 生态里，对接外部服务基本有三条路：写一个 MCP server、做插件 skill、或者最偷懒的——在系统提示里塞一段 curl 让模型自己拼。前两条可控，最后一条迟早出事。

## 问题

我们早期把十几个内部 API 直接暴露给 agent，两周内踩完了所有坑：

- agent 传错参数，接口返回 400，它开始“猜”参数格式，越猜越偏；
- 某个列表接口返回 80KB 的 JSON，直接撑爆上下文，后面几轮对话质量明显下降；
- 一次网络抖动导致工具超时，agent 没有报错，而是自己编了一段“看起来合理”的结果写进报告；
- 最险的一次：重试机制撞上非幂等的创建接口，同一资源被建了两份。

根子是一样的：API 本来是给人写的代码用的，我们却把它当成“可以直接给模型用”的东西。

## 做法

后来我们把对接流程收敛成五步：

1. **先包一层 MCP server，再给 agent 用。** 哪怕接口再简单，也用一层薄封装把鉴权、超时、重试、日志拦在 server 端。agent 只看到工具名、参数 schema 和返回结果。
2. **鉴权只走环境变量。** API key 放 secrets，server 启动时注入。任何 key 都不进 prompt、不进配置文件、不进会话记录。
3. **server 端做裁剪。** 返回结果在 server 里过滤字段、做分页、限制最大体积。工具描述里明确写“返回什么结构、多大”，写得像给新同事交接文档一样具体。
4. **错误要写给 agent 看。** 不要只抛 `HTTP 500`，而是返回结构化错误：错在哪、可能原因、建议动作。agent 拿到“参数 date 需要 YYYY-MM-DD 格式”，就不会再瞎猜。
5. **先只读，后写入，写操作加确认。** 新服务接入先只暴露查询类工具，跑一周再放写操作；写操作在 OpenClaw 侧加一道人工确认或幂等键。

## 踩坑点

- **工具描述写“人话”没用，要写“合同”。** “查询订单”不如“输入 order_id（string，格式 ORD-xxxx），返回 status/amount/created_at 三个字段”。
- **重试默认只对 GET 安全。** 所有 POST/PUT 必须确认幂等性或带幂等键，否则重试等于重复下单。
- **不要让 agent 自己处理超时。** 降级逻辑放 server 端，返回明确的 `TIMEOUT` 错误，agent 只负责告知用户或换路径。
- **工具数量膨胀。** 一个 agent 挂 40 个工具，选对的概率反而下降。按业务域拆 MCP server，按会话场景挂载。

## 可复用建议

- 把“给 agent 的 API 封装”当一个产品做：描述、错误信息、返回体积，都按“读者是一个不会追问你的实习生”的标准写。
- 沉淀一个最小接入模板：env 注入、schema 校验、体积上限、结构化错误，四件套齐了，新服务半天接完。
- 上线前跑一组对抗性用例：错参数、空返回、超时、超大响应——重点看 agent 的行为，而不是接口的行为。

## 总结

对接外部服务的本质，不是“让 agent 能调 API”，而是“让 agent 在所有情况下都知道发生了什么”。OpenClaw 侧的能力上限，往往取决于你封装得有多细。握手握得越清楚，后面的自动化才越敢放开跑。
