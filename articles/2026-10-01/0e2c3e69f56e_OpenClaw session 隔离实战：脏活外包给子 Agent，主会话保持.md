## 背景

OpenClaw 跑久了对一件事体会越来越深：主会话的上下文窗口是最稀缺的资源。每次工具调用的输出——一次网页抓取、一次长文件读取、一轮日志排查——都会原样写进主会话历史。单次看不出问题，跑一天下来，主会话就成了一锅大杂烩：有效决策被淹没在工具输出里，轻则回复质量下降，重则上下文压缩时把关键状态丢掉。

## 问题

典型症状有三个：

1. 主会话越聊越“钝”，模型开始重复早前的错误结论；
2. 一次重 IO 操作直接吃掉大半窗口，后面十几轮都在为它买单；
3. 多任务并行时，任务 A 的中间产物串进任务 B 的判断里。

本质是同一个问题：该隔离的东西没有被隔离。

## 隔离机制怎么工作

主 agent 可以通过 spawn 类工具（如 `sessions_spawn`，具体参数以你当前版本的 tool schema 为准）拉起子 agent。关键在于：子 agent 拿到的是一个**独立的 session**——有自己的上下文、自己的工具调用记录。它在自己的会话里随便折腾，跑完只把最终结果回传主会话。主会话上下文里只多了一条 spawn 调用加一段结果摘要。

一个好用的心智模型：**主会话是寄存器，子会话是内存**。寄存器只放当前要决策的东西，重活和数据都放外面。

## 做法与步骤

1. **识别该外包的任务**。凡是“过程输出多、结论短”的活——抓网页、批量文件处理、日志排查、长文档摘要——一律 spawn，不要在主会话里直接跑。
2. **spawn 时自带上下文**。子 agent 看不到主会话历史，task 描述里要把必要事实写进去：目标、输入路径、约束、期望输出格式。它不是你的分身，是一个被派活的同事。
3. **约定回传格式**。在 task 里显式要求只回传结论、限制行数、结构化优先。示例模板：

```text
任务：抓取 <url> 定价页，提取全部套餐价格。
约束：不写任何 memory 文件；不得再 spawn 子任务。
回传：JSON（name/price/unit），总行数 ≤ 20，其余信息丢弃。
```

4. **用 label 管理子会话**。给可读的 label（如 `scrape-0415-pricing`），后续查状态、取结果、做清理不会认错。
5. **处理等待语义**。必须拿到结果才能继续的逻辑，用同步等待；可并行后台跑的，让主会话先继续、稍后汇总。混用最容易出竞态。

## 踩坑点

- **上下文给少了**：子 agent 缺历史，只能按字面理解 task，结果跑偏。宁可多贴几行事实，别让它猜。
- **回传没约束**：不写输出上限，子 agent 回传两千字，污染只是延迟发生，主会话照样爆。
- **递归 spawn**：子 agent 又开子 agent，深度失控、token 成本翻倍。约定最多一层，并在 task 里明说“不得再 spawn”。
- **工作区污染**：session 隔离 ≠ 文件隔离。子 agent 往共享 workspace 写 memory 或改配置，等于另一种污染。子 agent 提示词里显式禁止写 memory 和全局文件，重隔离场景直接上沙箱。
- **孤儿会话**：失败任务的子 session 留在后台。定期用 session 状态工具盘点、清理、reset。

## 可复用建议

- 把“重 IO 一律外包”写成 AGENTS.md 里的固定规则，让主 agent 自己形成习惯；
- 回传约定模板化：目标达成与否、关键数据、异常，三段式；
- 关键状态不要只活在会话里，落盘到 workspace 文件，主会话 reset 也能恢复；
- 每周看一眼各 session 的 token 消耗，异常膨胀的那个就是没隔离好。

## 总结

Session 隔离不是高级技巧，核心就一句：**让主会话只承载决策，把过程留给子会话**。想清楚哪些活“过程重、结论轻”，spawn 出去、约束回传、管好 label 和清理，主会话就能长时间保持清醒。做法不难，难的是把每一类重任务都坚持归位。
