## 背景

E2E 测试一直是投入产出比很尴尬的活：写起来慢、selector 脆、改一版 UI 全线飘红。多数团队的现状是核心链路覆盖几条，剩下的靠人肉回归。Agent + MCP 浏览器工具出现后，"让 AI 写 E2E"的成本曲线变了——但直接让模型生成测试代码，效果通常很差。这篇帖记录我们在 OpenClaw 里跑通的一套协作流程：Agent 出初稿，执行反馈闭环修正，人只管断言和 review。

## 问题

让 AI 写 E2E 有两个典型失败模式：

1. **凭空捏造**：模型没有真实页面上下文，selector 和断言全靠想象，跑起来必挂。
2. **一团和气**：接上浏览器工具后，Agent"看到什么写什么"，把当前 bug 的表现也断言成了正确行为。

核心矛盾是：Agent 需要真实执行反馈，但不能只信自己看到的。

## 做法

流程分四步，跑在 OpenClaw 的会话里，浏览器能力走 MCP：

1. **约束探索**。先只给 Agent 只读工具（截图、accessibility snapshot、DOM 查询），要求它针对一条用户旅程输出 Given/When/Then 格式的测试意图清单。这一步人不看代码，只看意图。
2. **生成初稿**。Agent 基于意图清单和快照生成 Playwright 测试。强制约定：只用 `data-testid`，禁止 `nth-child` 和纯文本定位，禁止 `sleep`，等待一律用语义化 waitFor。
3. **闭环执行**。跑测试，把失败信息（报错栈 + 失败步骤截图）喂回 Agent，限定最多 3 轮修正。修不完就标记"需人工"，不许它自由发挥绕过。
4. **稳定性门槛**。通过后的用例在 CI 里连跑 3 次，全绿才算数。抖动的打回重写，不允许用 `retry: 2` 掩盖问题。

## 踩坑点

- **断言是重灾区**。Agent 最爱写"页面出现了 X"这种回声式断言。我们的规矩：断言必须对应人确认过的意图清单才允许落进代码，Agent 只负责实现定位和操作。
- **上下文别贪多**。把整页 HTML 直接塞给模型，token 爆炸且噪声大。accessibility snapshot 是更好的输入，结构干净还自带语义角色。
- **测试数据要先钉死**。Agent 会自己"顺手"造数据，造出来的状态不可复现。先准备好确定性的种子数据和 reset 脚本，作为前置工具暴露给 Agent。
- **别对着生产环境跑**。探索阶段的点击不可控，一律指向沙箱环境，MCP 侧做域名白名单。

## 可复用建议

- 把"测试意图清单"做成固定产出物。人和 Agent 之间只传这份契约，代码只是它的实现。
- 维护一份 selector 规范（`data-testid` 命名约定），写进 Agent 的系统提示词，比事后修快十倍。
- 把 Agent 当初级工程师用：可以写初稿、可以跑挂自修，但不能自己 review 自己，merge 权限永远在人。
- 修正轮次要设硬上限，否则 Agent 会陷入"改一版挂一版"的循环烧 token。

## 总结

这套流程跑下来，一条中等复杂度的用户旅程从意图确认到用例进 CI 大约 20 分钟。比纯手写快，但真正省的不是写代码的时间，而是"想起来要补测试"到"测试真的在跑"之间的启动成本。一句话总结：**Agent 负责让测试跑起来，人负责保证测试测的是对的东西**。闭环执行是分水岭——没有执行反馈的 AI 生成测试，基本等于没写。
