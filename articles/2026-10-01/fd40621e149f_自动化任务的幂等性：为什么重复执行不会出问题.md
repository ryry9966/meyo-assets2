## 背景

OpenClaw 里的自动化大致有三个来源：cron 定时任务、消息或 webhook 触发的会话、agent 在循环里自己调用的 MCP 工具。它们的共同点是：**执行次数不受你控制**。网络超时会重试，用户会手动再跑一遍，宿主机重启会让 cron 补偿触发，agent 觉得"上一步好像失败了"也会再调一次工具。写自动化时默认"每条任务只执行一次"，是很多事故的起点。

## 问题

非幂等的操作在重复执行时副作用会叠加：同一条日报推送了两遍、文件被 append 两次、下游 API 创建出重复资源。更隐蔽的是"服务端已成功、本地以为失败"的场景——工具调用超时，agent 重试，实际上第一次已经写入，结果数据翻倍。这类问题平时看不见，只在重试和故障恢复时爆发，而自动化系统恰恰是重试和恢复最频繁的地方。

## 做法 / 步骤

核心思路：给每个任务一个**稳定的业务键**，用状态记录把"执行"变成"确保已执行"。

1. **定义确定性任务键。** 用业务字段拼出来，例如 `digest:${channelId}:${yyyymmdd}`。不要用随机 UUID 或当前时间戳——键必须跨重试稳定，否则形同虚设。
2. **建状态存储。** 工作区里放一个 `state.json` 或 sqlite：任务开始前置为 `pending`，成功后置 `done`；每次执行先查，`done` 直接跳过。
3. **写操作带幂等键。** 支持 `Idempotency-Key` 的 API 直接透传；自定义 MCP 工具把键放进参数，让服务端去重。
4. **优先 upsert 而非 append。** 能覆盖写的绝不追加，能"设置最终状态"的绝不"发送增量"。
5. **状态写入要原子。** 先写临时文件再 rename，避免崩溃留下半截 JSON。

```js
if (state[key] === 'done') return;
state[key] = 'pending'; saveAtomic(state);
try { await runTask(); state[key] = 'done'; }
catch { delete state[key]; } // 释放，允许重试
saveAtomic(state);
```

## 踩坑点

- **check-then-act 竞态**：两个进程同时查状态、都看到"未执行"、都执行。要么用文件锁串行化，要么让下游动作本身幂等——只靠查状态不够。
- **pending 卡死**：进程在"已置 pending、动作未完成"时崩溃，catch 不会执行，任务永久卡住。要给 pending 加超时回收。
- **键不稳定**：把 `Date.now()` 拼进键里，每次重试都是新键。键必须在进入重试循环**之前**生成。
- **去重记录无限增长**：定期清理或按日期分片，别让它变成新的故障源。
- **"读"也有代价**：agent 的一次读取可能触发昂贵的下游调用，重读取同样值得缓存。

## 可复用建议

- 把 check → pending → run → done 封装成 `withIdempotency(key, fn)`，所有定时任务和 webhook handler 统一走它，不要各写各的。
- 在 MCP 工具的 description 里写明"可安全重试 / 不可重试"，给 agent 的重试决策一个依据。
- 验收方式很朴素：**把任务连跑两遍，断言第二次是 no-op**。写进测试用例，幂等性回归就有护栏了。

## 总结

幂等不是工程洁癖，而是自动化"可以被信任地重复执行"的前提。设计任何 OpenClaw 任务时，直接假设"这一步一定会被重跑"，然后让重跑的结果与只跑一次完全一致。做到这一点，重试、故障恢复、手动补跑就从事故变成了常规操作。
