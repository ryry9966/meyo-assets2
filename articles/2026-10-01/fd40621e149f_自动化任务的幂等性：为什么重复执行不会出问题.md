# 自动化任务的幂等性：为什么重复执行不会出问题

## 背景

OpenClaw 里的自动化大多建在“不可靠地基”上：cron 触发器可能在网关重启后重放，webhook 是 at-least-once 投递，Agent 循环在工具调用超时后会重试，人也会手滑把同一条指令发两遍。这些路径中没有任何一层承诺“只执行一次”。幂等性（Idempotency）就是补上这个缺口的设计手段：**同一个任务执行一次和执行多次，最终效果一致。**

## 问题在哪

非幂等操作的典型形态：

- **追加类**：往文件/日志 append、数据库 insert、发一条消息、创建一个工单；
- **累加类**：计数器 +1、余额扣减；
- **带随机性的创建**：每次执行生成新 ID、新文件名、新时间戳。

关键在于：重试发生时，上一次调用可能已经成功——超时只代表“没收到回执”，不代表“没执行”。于是出现重复消息、重复工单、文件里同一行出现三遍。更隐蔽的是，LLM 的非确定性会让重试时的参数和上次都不一样，问题被进一步放大。

## 做法

分三步把自动化改成幂等：

**1. 给操作分类。** 把任务拆成读操作、覆写操作、创建/外部副作用三类。前两类天然幂等：读不改变状态；用固定路径写文件是覆盖而非追加；upsert 优于 insert。只有第三类需要额外处理。

**2. 用确定性幂等键。** 键由触发语义决定，而不是执行时刻：`任务ID + 逻辑时间窗 + 目标对象`，例如 `daily-report:2025-06-01:ws-a`。同一天重跑，键相同，直接命中去重。注意：键必须在调用工具**之前**生成并固化，不能让模型在重试时重新发明。

**3. 原子去重，不要先查后写。** 用带唯一约束的存储做台账：

```sql
INSERT INTO task_ledger(key) VALUES (?)
ON CONFLICT(key) DO NOTHING;
-- 影响行数为 0 说明已执行过，跳过
```

“先 SELECT 再执行”在两个触发并发到达时会同时通过检查，必须靠数据库约束或 setnx 这类原子操作兜底。写 MCP 工具时，可以在工具描述里写明幂等语义（如“接受 idempotency_key 参数，重复提交返回首次结果”），让 Agent 知道重试是安全的。

## 踩坑点

- **键里混入了执行时刻。** `任务ID + 当前时间戳` 等于没做去重，每次重试都是新键。
- **“先删后建”不是幂等。** 终态一样，但中间有破坏窗口：删完建失败比原来更糟，下游 watcher 还会被删除事件惊动。
- **批量任务只做整体去重。** 处理 100 条在第 50 条挂了，重跑要么全跳过要么全重来。幂等键应落到每一条数据上，才能断点续跑。
- **台账没有范围和过期策略。** 上月的去重记录会挡住本月合法执行；键里带时间窗通常比加 TTL 更可控。
- **重试策略与幂等脱节。** 对发送消息这类没做去重的副作用开启自动重试，等于放大问题。顺序应该是：先幂等，再重试。

## 可复用建议

- 描述任务时用**目标状态**而不是动作：“确保 report.md 内容为 X” 优于 “往 report.md 追加 X”。
- 一个自动化系统只维护**一个台账**，别在每个插件里各写一套去重。
- 验收标准很简单：在测试环境把同一个任务**连续跑两遍**，结果不一致就是没做完。
- 外部副作用（发消息、付款、建 issue）默认视为非幂等，除非对方 API 明确支持幂等键。

## 总结

分布式系统里“恰好一次执行”基本是幻觉，真正能依赖的是“至少一次投递 + 幂等效果”。给每个自动化任务想清楚“重跑一遍会发生什么”，是比调 prompt 更基础的可靠性工程。做好分类、确定性键、原子台账这三件事，重复执行就从事故变成了冗余保障。
