## 背景

跑自动化的人迟早会撞上同一个问题：任务被执行了两次。

触发源太多了。定时调度器重启后重跑上一轮；webhook 超时后对端重发；消息队列是 at-least-once 语义；Agent 调工具超时后自己决定重试一次。无论是 OpenClaw 里写的定时任务、MCP 工具调用，还是自建的插件流水线，都躲不开。人操作时看到"已经做过了"会停手，自动化不会——它只认指令。所以重复执行不是异常路径，而是常态。

## 问题在哪

幂等性（idempotency）说的是：同一个任务执行一次和执行多次，最终结果一致。

按这个定义，操作分两类：

- **覆盖型**：`set_config(key, value)`、按主键 upsert——天然幂等，跑十遍结果一样。
- **追加型**：发一条通知、插入一条流水、扣一次库存——每跑一遍就多一份副作用，重复执行就是事故。

自动化翻车几乎都出在追加型操作上：群里收到三条相同的日报、订单被创建两次、日志里同一行写了五遍。

## 怎么做

核心思路一句话：**让重复的触发收敛到同一个业务键上，并在执行前先占住这个键。**

**1. 设计幂等键。** 键从业务语义生成，而不是每次随机生成。比如日报任务用 `report:{user_id}:{date}`，库存同步用 `{source}:{batch_no}`。随机 UUID 是反面教材——每次重试都是新键，等于没做。

**2. 落一张执行记录表，用唯一约束兜底。**

```sql
CREATE TABLE task_runs (
  idem_key   TEXT PRIMARY KEY,
  status     TEXT DEFAULT 'running',
  result     TEXT,
  created_at TEXT DEFAULT (datetime('now'))
);
```

```python
try:
    db.execute("INSERT INTO task_runs(idem_key) VALUES (?)", (key,))
except IntegrityError:
    return  # 已执行或正在执行，直接收敛
do_work()
db.execute("UPDATE task_runs SET status='done' WHERE idem_key = ?", (key,))
```

先 INSERT 占位、靠主键冲突挡并发，比"先查再执行"可靠——后者在两个触发同时到达时会双双通过检查。

**3. 外部追加型动作单独处理。** 调第三方 API 优先用它官方的 idempotency key；不支持的话，本地先记 `sending` 再发，接受"状态可能停在 sending，需要对账"的代价。追加型操作不可能既不漏发也不重发，明确选一边并写进文档。

**4. Agent/MCP 工具层面。** 幂等键在任务编排层生成并透传，别让模型每次调用自己生成——LLM 两次产出的参数不一定一致。工具描述里写明幂等语义（"重复调用同一 key 安全"），模型重试时才有依据复用。

## 踩坑点

- **超时 ≠ 失败。** 请求超时时远端可能已经执行成功，"确认失败才重试"等不到确认，幂等键才是兜底。
- **状态只存内存。** 进程一重启记录全丢，定时任务重启后照跑不误。记录必须落盘。
- **幂等和重试混为一谈。** 重试策略解决"要不要再跑"，幂等解决"再跑了会不会出事"，分开设计。
- **只在成功后写记录。** 漏掉 `running` 占位，两个并发触发会各自完整跑一遍。

## 可复用的建议

- 工具默认按幂等设计：upsert 优先于 insert，按 key 删除优先于 toggle。
- 执行记录表做成自动化项目的标配：`idem_key / status / result / created_at` 四列起步。
- 定时任务用时间片做键（日期、小时），天然防重。
- 回归测试加一条：同一任务连续跑两遍，断言结果不变。

## 总结

自动化系统和人工操作的本质区别，是重试无处不在且无人盯梢。幂等不是锦上添花的健壮性优化，而是系统能长期无人值守运行的前提。先把"重复执行会怎样"想清楚，再去谈调度、并发和失败恢复，顺序不能反。
