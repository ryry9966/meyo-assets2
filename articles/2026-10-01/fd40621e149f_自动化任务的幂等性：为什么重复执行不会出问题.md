## 背景

用 OpenClaw 跑自动化一段时间后，你会发现一个规律：**任务一定会被执行不止一次**。定时任务在网关重启后补跑、webhook 被上游重投、agent 调 MCP 工具超时后自己又试了一次——这些不是异常，是常态。幂等性（idempotency）就是让"同一件事做多次"和"做一次"结果相同的性质。它不是锦上添花，而是自动化的入场券。

## 问题：非幂等操作在重试时会放大

几个常见场景：

- 每天早上把 issue 汇总发到群里。某晚容器重启，cron 补跑一次，群里出现两条一样的汇总。
- agent 调"创建周报文档"的 MCP 工具，网络超时后重试，目录下多了三份周报。
- 插件收到消息就追加一条数据库记录，上游重投，记录翻倍。

共同点：这些都是**累积型操作**——创建、追加、发送，做两次就有两份副作用。而读取、覆盖写（set/upsert）天然幂等，不用管。

## 做法

1. **先分类操作。** 写自动化前问一句：这个步骤做两次会发生什么？答案是"没影响"就跳过；是"翻倍/重复"就继续往下。
2. **定义稳定的业务键。** 幂等的核心是一把天然唯一的钥匙：日期 + 任务名、消息 id、外部单号。不要用随机 UUID——重试时生成新 UUID，等于没做幂等。
3. **落地执行记录。** SQLite 或一个 JSON 状态文件都行，关键是执行前先查、执行后写入，业务键上建唯一约束：

```sql
CREATE TABLE run_log (
  task_key   TEXT PRIMARY KEY,  -- 如 "digest-2025-06-01"
  status     TEXT,              -- running / done / failed
  updated_at INTEGER
);
```

执行前 `INSERT`，冲突就跳过。把"检查"和"占位"合成一步，避免竞态。

4. **能覆盖就不追加。** 周报固定文件名（`weekly-2025-W23.md`），重跑即覆盖；状态用 set 而不是 append。
5. **重试只给幂等步骤。** 读操作、覆盖写可以自动重试；发消息、创建资源这类非幂等步骤，失败后要么人工介入，要么先对账再补。

## 踩坑点

- **状态放内存。** 重启就丢，等于没做，必须落盘。
- **检查与执行之间有窗口。** 两次触发几乎同时到达，都通过了"还没做过"的检查。唯一约束或文件锁可解。
- **卡在 running。** 进程崩了状态停在 running，之后永远跳过。要加超时释放：超过 N 分钟的 running 视为失败。
- **指望提示词。** 在 system prompt 里写"不要重复执行"不可靠。幂等要做在工具/插件层，agent 层只管编排。
- **日期键的时区。** 用本地日期做键，跨天边界的任务可能漏跑或双跑，统一用 UTC。

## 可复用建议

- 一句话判断法：自动化里的每个副作用都问"做两次会怎样"，答不上来就先补幂等。
- 把幂等下沉到 MCP 工具和插件层，做成默认行为，而不是每个工作流单独处理一遍。
- 留一个对账入口：定期列出最近执行记录，肉眼扫一遍，比想象中更能发现问题。

## 总结

重试、重复触发、崩溃恢复不是自动化的事故，而是它的日常运行环境。幂等性解决的不是"怎么不出错"，而是"出了错之后系统仍收敛到正确状态"。下次写自动化任务时，先假设它会被执行两次——如果这个假设不成立，补上业务键和执行记录，比事后清理重复消息便宜得多。
