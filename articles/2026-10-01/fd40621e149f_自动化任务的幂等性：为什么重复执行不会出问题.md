# 自动化任务的幂等性：为什么重复执行不会出问题

## 背景

在 OpenClaw 里跑自动化任务，重试几乎是必然发生的：MCP 工具调用超时后 agent 会再试一次，调度器对失败任务按策略重跑，webhook 触发器在网络抖动时可能重复投递，再加上人工手动触发和定时任务并存。这些机制大多是 at-least-once 语义——保证至少执行一次，但不保证恰好一次。

问题在于：很多人写任务时默认“只会跑一遍”。一旦重试真的发生，结果不是报错，而是重复建了群、发了两遍通知、创建了三个重复工单。这类 bug 往往上线数周后才被发现。

## 问题出在哪

核心误解是：**超时等于失败**。实际上一次调用超时，可能请求根本没到，也可能服务端已经执行成功、只是响应没回来。客户端无法区分，只能重试；重试之后，服务端就执行了两次。

另一个来源是 agent 的自主重试。模型观察到工具调用报错后，通常会自行再调一次，且不一定带同样的参数。如果工具内部每次生成新的 ID 或时间戳，下游就会当成两个不同任务。

## 怎么做

**1. 先定幂等键。** 每个有副作用的任务，先想清楚“业务上什么能唯一标识这次执行”：外部单号、`日期 + 目标对象`、上游传入的 request_id 都可以。关键是这个键要在重试前后保持一致，由调用方生成并逐层传递，而不是每次执行时新生成。

**2. 用 upsert 替代 create。** 写入类操作优先用“存在则更新/跳过，不存在则创建”的语义，数据库层面配唯一索引兜底。

**3. 执行前查状态。** 任务启动时先读目标状态：已完成就跳过，进行到一半就从断点继续。配合一张 execution_log 表（幂等键加唯一索引，记录状态和结果摘要），重跑逻辑就退化成查表。

**4. 输入要确定性。** 同一次逻辑执行里，所有步骤用同一个 run_id、同一个快照时间，避免每步各自取 `now()` 或生成随机数。

**5. 收敛副作用出口。** 把发消息、下单这类不可逆操作集中到一个统一出口函数，在那里做幂等判断，其余步骤随便重跑。

## 踩坑记录

- **check-then-act 有竞态。** 先查“不存在”再创建，两个实例并发时都会通过检查。查询只能优化路径，唯一约束才是正确性保证。
- **返回值要区分语义。** 第二次执行返回 200 但实际什么都没做，调用方会误以为新建成功。返回体里应明确 created / skipped / deduplicated。
- **重试层级要统一。** 工具内部重试、agent 重试、调度器重跑叠加时，幂等键必须由最外层生成贯穿到底，任何一层自己造新键都会击穿整套机制。
- **补漏型任务自带反幂等。** “每天扫描失败记录并补发”如果不给记录打上已处理标记，会每天重复补发一遍。

## 可复用建议

- 把幂等键设计写进任务文档，和参数说明同等重要。
- 默认假设每个有副作用的调用都会被执行两次，按这个前提写代码。
- 沉淀一张通用 execution_log 表，任务间复用。
- 真正不可幂等的外部操作（打电话、真实扣款）不要交给自动重试，挂人工确认门槛。
- 上线前做重放验证：把同一次任务日志跑两遍，确认第二轮全部 skipped。

## 总结

幂等不是锦上添花，而是自动化任务能放心交给重试机制的前提。at-least-once 是调度器和网络层的现实，应用层的回应就是幂等设计：固定的幂等键、upsert 语义、状态表、确定性输入。这四件事做完，重复执行就从事故变成了无害的重放。
