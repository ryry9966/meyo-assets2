## 背景

我们团队日常跑着十几个定时任务和几个常驻 agent，日志散落在三处：cron 的 stdout 重定向文件、OpenClaw 会话日志，以及几个 MCP 工具自己写的 JSONL。之前日报靠人翻日志手写，每天 20 分钟起步，还经常漏掉凌晨跑挂的任务。于是搭了一条自动日报流水线，稳定跑了一个多月，把做法和坑分享一下。

## 问题

"把日志直接丢给 agent 总结"这条路我们试过，不行：

1. 原始日志一天几十 MB，塞不进上下文，截断后又丢关键信息；
2. 模型输出格式每天不一样，没法归档对比；
3. 统计类数字（任务成功率、错误计数）靠模型数，不可靠。

结论：确定性的事交给规则，表达层的事才交给模型。

## 做法

整条流水线五步，由 OpenClaw 定时任务驱动：一个预处理脚本 + 一次 agent 调用 + 一个投递插件。

**1. 归集**。每天 07:30 把三处日志拉到临时目录，统一转成 JSONL，每行强制带 `ts / source / level / message` 四个字段。格式各异的日志在这一步各写一个转换函数，之后流程只认统一 schema。

**2. 规则降噪**。先过确定性过滤：丢 DEBUG、按 message 哈希去重、按 `error / warn / task_result` 分三个桶，各桶输出计数和 Top N 样本。这步做完，几十 MB 通常剩几 KB。

**3. Agent 总结**。只把分桶摘要交给 agent，prompt 是固定模板，按 schema 输出 JSON：`abnormal`（异常与可能原因）、`done`（完成事项）、`todo`（待跟进）、`metrics`（关键数字直接引用统计结果，不让模型自己算）。

**4. 校验与重试**。用 jsonschema 校验输出，缺字段或 metrics 对不上就带错误信息重试一次；再失败走降级路径——只发规则统计部分，并标注"AI 摘要生成失败"。

**5. 投递与归档**。渲染成固定版式 markdown，经 MCP 插件推到群里，同时按 `reports/2025-06-XX.md` 归档。生成元数据（耗时、重试次数、token 消耗）单独记一份，方便调优。

## 踩坑点

- **时区**：cron 用本地时区、日志时间戳是 UTC，"昨天"的边界错了一天。现在统一 UTC 存储、展示层转本地时区。
- **敏感信息**：日志里有 token 和内网地址，进流水线前必须过脱敏正则——日报是要发群的。
- **重跑幂等**：修 bug 后手动重跑，日报发了两遍。现在用日期作幂等 key，已推送过就只更新归档不重发。
- **别迷信 prompt**：格式靠 schema 校验兜底，不靠"请务必输出 JSON"这种措辞。

## 可复用建议

- 分层原则：规则负责统计与过滤，模型只看摘要、只做表达，数字必须来自规则层。
- 模板、schema、日志路径全放配置文件，换数据源只需新增转换函数。
- 从单一数据源的小日报起步，格式稳定后再扩，别一上来接五个日志源。
- 流水线自身的运行记录也要留，排障时它就是最好的日志。

## 总结

这条流水线的价值不只是省下每天 20 分钟，更在于：格式稳定可对比、异常不会被人为遗漏、每次生成可回溯。核心思路一句话——确定性的归规则，表达性的归模型，最后用 schema 兜底，谁也别全信。适合已经在用定时任务或 MCP 插件、想往"可靠自动化"再走一步的同学参考。
