## 背景

Agent 接上 MCP 和插件之后，能做的事从"生成文本"变成了"执行动作"：写文件、调 API、发消息、跑部署脚本。工具越多，一个问题越绕不过去：哪些动作 Agent 可以直接干，哪些必须停下来等人点头？

在 OpenClaw 这类长会话、多工具、半无人值守的运行场景里，这已经不是产品哲学问题，而是工程问题——权限设计的粗糙会直接变成事故。

## 问题：两种对称的失败

实践中常见两类极端：

- **什么都问**：读个文件要确认，写个草稿也要确认。用户很快养成"闭眼点确认"的习惯，确认机制形同虚设——这才是最危险的状态。
- **什么都不问**：Agent 在一次批量清理里删掉了共享目录，或者把内部备忘发进了对外频道。复盘时发现每一步逻辑都对，错的是它根本不该有权限做那一步。

两种失败的共同根源是同一个：权限边界一刀切，没有按动作的性质分级。

## 做法：可逆性 × 影响面的四档模型

给每个工具动作打两个标签：

- **可逆性**：能不能撤销？查询可逆，发出去的消息不可逆。
- **影响面**：只影响本地沙箱，还是波及他人、生产环境、资金？

据此分四档：

1. **自动执行**：只读、本地、可逆。查资料、读代码、生成草稿。
2. **自动执行 + 审计**：可逆但留痕。往分支上提交代码、建 draft 工单。直接放行，但全量记日志。
3. **确认后执行**：不可逆或对外可见。发消息、合并 PR、花钱、删数据。必须带 diff 或预览，人确认后才跑。
4. **禁止**：无论怎么确认都不该由 Agent 发起，比如清空生产库。走独立的人工流程。

落地步骤：

1. 盘点 Agent 挂载的全部 MCP server 和插件，逐个标档位；
2. 新工具默认落第 3 档，观察一段时间再决定升降级；
3. 确认交互必须带上下文预览（改了什么、发给谁、花多少钱），不接受裸确认；
4. 所有决策进审计日志：工具名、参数、裁决结果、谁批的；
5. 每周复盘日志：频繁被确认的动作试着降档，出过事的动作升档。

## 踩坑点

- **确认疲劳**：弹窗每天超过十几次，人就开始无脑通过。要靠收窄权限减少确认次数，而不是靠人自觉。
- **裸确认**：只问"可以删除吗"却不展示将删什么，人根本无法判断，这个确认等于没做。
- **"始终允许"按钮**：会话级授权可以接受，永久授权务必谨慎，最好加过期时间。
- **子 Agent 静默继承权限**：主 Agent 有确认门槛，派生的子 Agent 却直连同一批工具，边界被绕过。子 Agent 必须显式收窄。
- **假的只读**：某些 GET 接口有副作用（触发 webhook、消耗配额），别凭 HTTP 方法名判断档位。

## 可复用建议

- 每类 Agent 角色维护一张权限矩阵，随代码一起 review；
- 区分"请求授权"和"请求信息"：缺参数该问人，但问的是信息，不是许可；
- 对自动执行的动作同样加预算与频率上限，作为兜底闸门；
- 新集成先跑 dry-run，日志观察一周再放权。

## 总结

权限边界不是一个开关，而是一条连续的滑轨，两个核心刻度是**可逆性**和**影响面**。目标不是零打扰，也不是零确认，而是让每一次打断都配得上人类的注意力——问得少，但问得值。
