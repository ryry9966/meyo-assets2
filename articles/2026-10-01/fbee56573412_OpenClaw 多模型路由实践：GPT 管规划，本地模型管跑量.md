## 背景

OpenClaw 在我们这边的典型用法是常驻网关：接几个 IM 渠道、跑定时任务、挂一堆 MCP 工具，一天几百到几千次调用。默认配置下所有会话都打向同一个云端旗舰模型，月底账单和“内部数据要不要出网”这两个问题迟早会找上门。

## 问题

把所有请求都交给 GPT 级模型，实际上是三种浪费：

1. 大量任务是摘要、分类、格式转换，小模型完全够用；
2. 涉及内部数据的任务，本来就不适合出网；
3. 定时批处理对延迟不敏感，没必要为旗舰模型的响应速度付费。

反过来全换本地模型也不行——工具编排和多步规划的失败率会明显上升，agent 变成“看起来在干活，其实一直在错”。

## 做法与步骤

**第一步，任务打标。** 把 agent 实际干的活列出来，按三个维度分类：复杂度（单轮 vs 多步工具编排）、敏感度（是否携带内部数据）、频率（每分钟 vs 每天几次）。

**第二步，准备两套模型。** 云端保留一个 GPT 级模型做主脑；本地用 Ollama 或 vLLM 跑一个 30B 上下的指令模型，显存允许的话再备一个 7B 做兜底。

**第三步，按 agent 拆分路由。** 规划、编码、复杂工具调用固定走云端；摘要、打标签、日志清洗、批量通知这类 worker 走本地。示意配置（`~/.openclaw/openclaw.json`，字段名以你手上版本为准，思路通用）：

```jsonc
{
  "models": { "primary": "openai/gpt-4.1", "fallback": ["ollama/qwen2.5:32b"] },
  "agents": {
    "planner": { "model": "openai/gpt-4.1" },
    "worker":  { "model": "ollama/qwen2.5:32b" }
  }
}
```

**第四步，加 fallback 链和日志。** 云端超时或限流时降级到本地，同时把“实际用了哪个模型、token 数、任务结果”写进日志，每周看一眼降级比例。

## 踩坑点

- **小模型的 function calling 不稳**：MCP 工具选错率高、参数格式漂移。重工具编排的 agent 别下放，这是最贵的一条教训。
- **上下文长度不一致**：本地模型窗口小，长会话中途切模型会“失忆”。要么整会话锁死模型，要么切之前先做一次摘要压缩。
- **中文质量滑坡更明显**：本地小模型在中文任务上的衰减比英文跑分显示的严重，切换前先跑一遍自己的评测集，别信榜单。
- **静默降级最危险**：质量掉了但没人发现。fallback 触发必须留痕，最好直接告警。
- **本地 GPU 并发有限**：批量任务记得排队限流，否则会把同机跑的其他服务一起拖垮。

## 可复用建议

- 路由三问：这一步需要多聪明？数据能不能出网？调用量多大？三个答案决定了模型选型。
- 先建立全云端基线，再按任务类别逐批下放到本地，每下一批跑一次回归对比。
- 维护 20~50 条真实任务样本做私有评测集，比任何通用 benchmark 都管用。
- 成本和降级率写进周报，路由策略的迭代才有依据，而不是凭感觉。

## 总结

多模型路由不是“省钱的技巧”，而是给不同任务配不同算力的工程决策。我们的实际数据：批处理和摘要类任务下放本地后成本降了约七成，核心规划任务仍留在云端，整体失败率没有上升。OpenClaw 的价值在于这套拆分是配置级的，不用改代码——先跑通全云端，再逐步收紧。
