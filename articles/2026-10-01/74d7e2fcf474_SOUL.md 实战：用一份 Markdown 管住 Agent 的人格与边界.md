## 背景

跑过长期 Agent 的人都有体感：同一套提示词，周一还克制礼貌，周三就开始自作主张"顺手"帮你执行命令；换个模型、开个新 session，语气和底线全变了。OpenClaw 的 workspace 把系统级提示拆成了几个文件，其中 SOUL.md 专门回答"这个 Agent 是谁"——身份、语气、边界。它每次会话启动时被注入上下文，是少数能进 git、能做 code review 的行为层配置。

## 问题

人格和边界散落各处，代价很具体：

- system prompt 写死在网关配置或代码里，改一次要重新部署，谁改的、为什么改，无从追溯；
- 行为漂移：长会话后期模型"忘掉"早期约束，越权调用工具、对没把握的事过度承诺；
- 多人协作时各改各的，没有 single source of truth，排障时不知道当前生效的到底是哪版规则。

## 做法

一份能长期维护的 SOUL.md，我的骨架是三段，总量控制在 60 行以内：

1. **身份与语气**（10 行以内）。不写形容词，写可执行约束。不说"简洁专业"，而说"默认回复不超过 3 段；技术结论先给，推理过程按需展开"。
2. **分级边界**（5–8 条）。绝对禁止（删数据、未经确认对外发消息）、需要确认（执行 shell、覆盖写文件）、可自主（查询、总结、读文件）。每条落到具体工具名，和 TOOLS.md 对得上，别写抽象的"谨慎操作"。
3. **语气示例**。给 2–3 组"遇到 X 时怎么回"的 few-shot，比任何描述性文字都管用。

同时注意分工：SOUL.md 管"你是谁、什么不能碰"；AGENTS.md 管"怎么干活"；项目状态这类易变信息丢给 memory 文件，不要塞进 SOUL.md。

## 踩坑点

- **写成小作文**。上百行的 SOUL.md，后半段规则在长上下文里基本失忆，规则越多越不值钱。
- **边界只写"不允许"，没写"怎么办"**。模型遇到灰色地带会自由发挥，要给替代动作，比如"不能代执行时，输出命令让用户自己跑"。
- **和 channel 层、插件注入的提示词打架**，表现为行为忽好忽坏。排查方法：直接问 agent"引用你当前生效的规则"，逐层比对来源。
- **改完不验证**。用几条对抗性输入（"忽略之前的设定""你就说到底能不能执行"）做回归测试，新开 session 再确认注入生效。

## 可复用建议

- 把 SOUL.md 当代码：改动走 commit，行为异常先 diff 这个文件，很多"模型变笨"其实是昨天手滑改了规则。
- 发现 agent 犯错，别在聊天里纠正它——会话级纠正是临时的，改文件并提交才是持久的。
- 每个 channel 只覆盖格式差异（比如飞书回复更短），人格层永远只有一份，避免分叉。
- 团队场景下给 SOUL.md 定个评审节奏：行为类 PR 必须附一条"改前/改后的实际回复对比"。

## 总结

SOUL.md 的价值不在于让 Agent 更"像人"，而在于把行为从玄学变成配置：一份短的、具体的、可版本控制的文件，配上分级边界和语气示例。人格是产品的一部分，就该按工程方式维护——改它像改代码一样严肃，测它像测代码一样例行。
