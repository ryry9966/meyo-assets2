## 背景

E2E 测试一直是自动化测试里投入产出比最难平衡的部分：写起来慢、断言容易漏、UI 一改就碎。团队里通常只有一两个人愿意维护，其他人提交 PR 时只求别挂。Agent 加上 MCP 浏览器类工具成熟之后，"让 AI 参与测试工程"从 demo 变成了能进 CI 的实践。我们在一个中等规模的前端仓库里跑了几周，把流程收敛成这篇帖子。

## 问题：一次性生成基本没用

直接把需求丢给 Agent，"帮我写 E2E 测试"，结果通常是三类：

1. **断言空洞**：测试只验证页面加载成功，`toBeVisible()` 满天飞，等于没测；
2. **选择器脆**：大量 `text=` 或按坐标点击，UI 微调就全红；
3. **幻觉 API**：编造不存在的方法，或用旧版本语法，本地跑不起来。

根因是 Agent 只拿到需求文本，没拿到应用的真实状态——它不知道你的路由结构、测试夹具和选择器规范。写作阶段从来不是瓶颈，探索和验证阶段才是。

## 做法：闭环，而不是一次生成

把 Agent 当成一个能自己跑测试的初级工程师，流程分四步：

**第一步：投喂项目上下文。** 把 `playwright.config.ts`、现有测试里两三个"金标准"样例、选择器规范（我们规定优先 `data-testid`，其次 role，禁用 CSS 路径）放进上下文。样例比长篇 prompt 有效得多。

**第二步：先逛后写。** 通过浏览器类 MCP 工具让 Agent 实际打开页面，截图、读 DOM，确认每个 `data-testid` 真实存在后再落笔。这一步能消灭大部分幻觉选择器。

**第三步：生成 + 立即执行。** 关键点是给 Agent 执行权限：写完直接跑 `npx playwright test`，失败输出原样喂回去让它自己改。我们限制每轮只允许最小 diff，禁止整文件重写。

**第四步：人工卡点。** Agent 声称"全绿"后，人只审一件事：断言是不是真的在测业务行为。合并前过一遍 diff，重点看有没有 `skip`、超时放宽、断言删减。

## 踩坑点

- **`waitForTimeout` 依赖**：Agent 特别爱用硬编码等待来"修" flaky。我们直接在 lint 里禁了这个 API，逼它改用 `expect` 的自动重试。
- **用 skip 假装修好**：连续失败两次后，Agent 会倾向给用例加 `test.skip`。在系统提示里明确禁止，并要求报告根因。
- **上下文膨胀**：全量测试套件喂进去很快爆窗口。只喂目标模块相关文件和失败用例即可。
- **环境差异**：Agent 本地跑通不代表 CI 能跑。最终验证一律放 CI 容器，本地结果只做参考。

## 可复用建议

1. 先写一份测试规范文档（选择器优先级、断言风格、禁用 API），它对 Agent 的约束力远超 prompt 里的口头要求；
2. "会跑测试的 Agent"比"会写测试的 Agent"有价值一个数量级，尽量给它执行和读日志的工具；
3. 仓库里维护 2-3 个高质量样例测试作为 few-shot 锚点，比任何提示词工程都稳；
4. 给 flaky 设预算：一个用例一周内 flaky 超过两次就降级为手动跟踪，别让 Agent 反复空转烧 token。

## 总结

Agent 写 E2E 测试的价值不在"生成代码"这个动作，而在"写—跑—修"的闭环。把项目规范固化成文档、把浏览器和执行器通过 MCP 接给 Agent、把人工审查压缩到只看断言质量——这套组合跑下来，我们的 E2E 覆盖率一个月内从 30% 提到 65%，维护成本没有明显上涨。它替代不了测试设计，但能替代大部分苦力。欢迎在评论区交流你们的卡点。
