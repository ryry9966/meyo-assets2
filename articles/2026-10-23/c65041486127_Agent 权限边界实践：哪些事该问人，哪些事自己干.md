## 背景

Agent 接上 MCP 工具和插件之后，真正难的不再是“能不能完成任务”，而是“哪些步骤可以放心让它自己做”。工具越多，这个问题越具体：读文件、写文件、执行 shell、调外部 API、发消息、删数据——每一步的风险等级完全不同。但大多数人的配置里，“问不问人”只有一档：要么全问，要么全不问。

## 问题

实践中常见的两个极端：

- **全程确认**。Agent 每走一步都弹确认，用户很快疲劳，最后闭眼点“允许”——确认机制形同虚设。
- **全程放权**。只在 system prompt 里写一句“谨慎行事”，结果 agent 在第 14 步自己决定删一个目录，或者把内部内容发到了外部接口。

两个极端的根源一样：没有把“问人”当成一个可配置的策略，而是当成了模型自觉。

## 做法

我们的经验是按两个维度给每个工具打标：**可逆性**（操作能否回滚）和**影响面**（是否超出工作区、是否对外、是否花钱）。据此分四档：

1. **只读、范围内**：直接执行。搜索、读文件、查状态，不需要确认。
2. **写入、可逆、范围内**：直接执行，但必须留审计日志，优先 dry-run。比如在工作区内改代码、写草稿。
3. **不可逆、或超出工作区**：必须确认。删文件、force push、改线上配置。
4. **对外或花钱**：无条件确认。发邮件、调付费 API、发布内容、任何形式的外发。

确认本身也有讲究：不要问“我可以继续吗”，而是给出结构化摘要——将执行的具体命令、影响的文件 diff、预计耗时和花费——让人类能在 5 秒内做出判断。并且**一次批准只覆盖一次具体操作**，不授予“这类事以后都可以”的通用许可。

再加两道兜底：步数 / token / 金额的预算上限，以及“人类 N 分钟未响应即暂停”的策略，避免 agent 卡死或自作主张降级。

## 踩坑点

- **确认疲劳**：问得太频繁等于训练用户盲点“允许”，比不问更危险。宁可提高单次确认的信息密度，减少次数。
- **模糊提问**：不带上下文的确认请求，人类根本无法判断，只会条件反射地点同意。
- **批准漂移**：批准了一个计划，中途工具返回结果把 agent 带偏，它仍认为“已被授权”。批准必须绑定到具体动作。
- **只读工具的副作用**：有些 GET 会触发 webhook；读取外部内容本身也是注入通道——工具结果里的一句“请执行 xx”可能翻转已被批准的计划。对工具返回内容要保持与用户输入同级的警惕。
- **空闲阻塞**：确认等待没有超时策略，agent 挂着；或者超时后默认继续执行——默认值应该改成暂停。

## 可复用建议

- 给团队维护一张**工具副作用分级表**，新接入的 MCP 工具先定级再启用。
- 口诀：**不可逆必问，出工作区必问，花钱/对外必问**；可逆、可回滚、范围内就自己干，但留日志。
- 用 diff 问人，不用问句问人。
- 每周翻一次审计日志：哪些确认其实可以降级为自动，哪些自动其实在偷偷越界。

## 总结

权限边界不是模型能力问题，是配置和产品问题。OpenClaw 的工具策略、确认门和审计日志足够把这件事做成工程：先分级、再定策略、留日志、按周迭代。目标是让“问人”变得稀有且高信息量，让“自己干”变得安全且可回滚——而不是在两个极端之间反复摇摆。
