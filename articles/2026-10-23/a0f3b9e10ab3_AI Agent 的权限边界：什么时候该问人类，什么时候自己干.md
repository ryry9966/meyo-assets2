## 背景

Agent 接上 MCP 和一摞插件之后，能力上限往往不再是模型，而是你敢给它多少权限。读文件、跑 shell、调第三方 API、跑定时任务……每多接一个工具，"该不该先问人"就从哲学问题变成一个真实的工程问题。

## 问题

实践里常见两个极端：

- **什么都要确认**。每写一个文件、每跑一条命令都弹窗等人。人被问烦了，开始无脑点同意，确认机制形同虚设。
- **什么都不问**。某天 agent 在"清理临时文件"的任务里顺手删了共享目录，或者把一封没润色的草稿直接发给了客户。

两个极端的根因是同一个：权限边界没有被显式定义，而是隐含在 prompt 的语气里。

## 做法：用三个维度给工具分级

判断一次工具调用是否需要人工确认，我习惯看三个量：

1. **可逆性**：能不能撤销？读操作无损，写入临时文件可逆，发消息、付款、删除通常不可逆。
2. **影响半径**：只动沙箱内的东西，还是会波及共享目录、生产环境、外部联系人？
3. **代价不对称性**：问一次人的成本（打断、延迟）vs 做错的成本。发错一条内部消息可以撤回，付错一笔钱不能。

组合起来，把工具分成三档：

- **自动执行**：只读操作、沙箱内写入。全部自动，但必须记日志。
- **执行后汇报**：可逆、影响半径小、错了能兜底的写操作。先干，事后在会话里汇报。
- **必须确认**：不可逆、外部可见（发消息/邮件/发布）、涉及钱和凭证的操作。停下来，带上上下文问人。

落地时有一个关键原则：**边界写在配置里，不写在 prompt 里**。OpenClaw 的工具策略支持 allow / ask / deny 这类分级，把每一类工具明确标注，比在 system prompt 里写一句"谨慎一点"可靠得多——prompt 会漂移，配置可以被 review、被回归测试。

## 踩坑点

- **确认疲劳**：高频弹窗会训练人类无脑同意。宁可收紧到"真正值得问的才问"，也别滥发确认。
- **批量操作逐条问**：agent 要删 200 个文件，逐个确认等于没有确认。正确做法是先生成变更预览（diff / 清单），一次确认整批。
- **把"我不确定"当成"有风险"**：模型的不自信和操作的危险性是两回事。不确定时应该让它自己多查一步，而不是把决策甩给人类。
- **确认上下文不足**：一句"是否执行 delete_files？"人类没法判断。确认请求必须带完整上下文：目标路径、影响范围、来自哪个任务。
- **超时后自作主张**：问了没人回，agent 等五分钟后"默认继续"——这是最危险的隐性策略。超时应该等于中止，不是放行。

## 可复用建议

- 新接的工具一律先以只读权限跑一段时间，再逐步放开写操作。
- 每个自主执行的动作落审计日志：时间、工具、参数、触发来源。出事时能回放。
- 确认交互按"diff 审阅"设计，而不是一个"是/否"按钮。
- 定期复盘被确认过的请求：如果人 90% 都在点同意，说明这条策略该降级为自动；如果经常拦下危险操作，说明分级是对的。

## 总结

权限边界不是一句 prompt，而是一个产品决策：可逆性和影响半径决定下限，代价不对称性决定什么时候打断人。把它做成配置、日志、确认交互三件套，agent 才能既敢干活，又不闯祸。
