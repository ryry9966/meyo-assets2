## 背景

Agent 和传统服务的关键区别：错误信息最终要经过 LLM“解读”。传统微服务里，重试、熔断、降级都是确定性代码；Agent 里模型拿到一段报错，可能把它当成数据、编出看似合理的返回值，也可能因为提示词里一句“失败了就重试”而无限循环，把 token 和配额烧光。

OpenClaw / MCP 场景下外部依赖面更广——LLM provider、tool server、第三方 SaaS、自建服务——任何一环抖动都会传导到整条任务链，错误恢复因此是 Agent 可靠性的第一道坎。

## 问题

实践中四种典型失控：

1. **幻觉兜底**：API 返回 500，模型没承认失败，编一个合理的结果继续走。
2. **无限重试**：同一工具循环调用几十次，直到烧完预算。
3. **过度中止**：一次 429 就把整个多步任务判死刑，其实等 2 秒就能恢复。
4. **静默降级**：插件吞掉异常返回空结果或过期缓存，用户毫不知情。

## 做法

核心原则一句话：**重试放代码层，决策放模型层**。

**1. 适配层做错误分类。** 可重试（429、503、超时）与不可重试（400、401、404）用代码写死，别指望模型区分 502 和 429 的语义差别。

**2. 有界重试 + 指数退避 + 抖动。** 在 MCP server 或插件适配器里做，比如最多 3 次、间隔 1s/2s/4s 加随机抖动。关键是重试永远不进入 Agent 的决策循环。

**3. 给模型返回结构化错误，而不是原始堆栈：**

```json
{
  "status": "tool_error",
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": false,
  "options": ["skip_step", "use_alternative_tool", "report_failure"]
}
```

`options` 给模型一个有限的决策集，行为会稳定得多。原始报错字符串经常被模型当成正常返回数据来“理解”，这是幻觉兜底的直接来源。

**4. 预置降级路径。** 每个关键工具想清楚挂了怎么办：替代工具？标注过期的缓存？还是停下来问用户？没有降级路径的工具就是单点故障。

**5. 长时自动化加熔断。** 同一工具连续失败 N 次就标记不可用并冷却（如 5 分钟），期间直接走降级路径。定时任务类 Agent 尤其需要。

## 踩坑点

- 对非幂等的写接口（如创建资源的 POST）自动重试，可能产生重复数据。要么带幂等键，要么写操作不自动重试。
- 退避没加抖动：多个 Agent 实例同时恢复，同一秒全部打回去，形成二次雪崩。
- 把“空结果”当“失败”：搜索类 API 返回空列表是合法答案，别触发重试。
- 超时设太长：单个工具 120 秒超时会卡死整轮任务。建议按工具特性分级设置，默认 20–30 秒。
- 只靠系统提示词约束次数：模型大概率不数数，约束必须落在代码里。

## 可复用建议

1. 分层职责不混：适配层负责重试，模型层只在有限选项里做决策。
2. 每次工具调用都要有预算：最大重试次数 + 最大墙钟时间。
3. 失败要落状态和日志，让下一轮计划能“看见”这个工具挂过，主动绕开。
4. 上线前做混沌测试：写一个 mock 工具，随机返回 500、超时、空结果，完整跑一遍你的 Agent，观察真实行为。多数人第一次跑这个测试都会被吓到。

## 总结

外部 API 挂掉是常态，不是异常。Agent 的可靠性不取决于模型多聪明，而取决于代码层替它挡掉了多少不确定性：错误分类、有界重试、结构化上报、预置降级、熔断兜底。让模型只在有限的选项里做决策——这是把它当队友的前提，别让它裸奔在原始错误信息里。
