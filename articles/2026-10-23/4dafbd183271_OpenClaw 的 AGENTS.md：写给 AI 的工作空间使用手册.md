用 OpenClaw 一段时间后你会发现一个规律：agent 翻车的原因，往往不是能力不够，而是它对你的环境一无所知。每次新会话，模型本身是失忆的，它对机器的全部认知基本来自启动时注入的工作区文件——其中排在最前面的就是 `AGENTS.md`。README 是写给 newcomer 的人看的，AGENTS.md 则是写给一个每天上线都失忆的 AI 看的使用手册。

## 问题

没有这份文件（或写得很随意）时，日常使用会反复出现几类摩擦：

- 同样的偏好每次都要口头交代：输出格式、目录习惯、部署命令；
- agent 自作主张：直接改主分支、删它认为多余的文件、把中间产物丢在项目根目录；
- 换个会话，之前的"约定"全部归零，协作成本随会话数线性增长。

本质上是上下文工程问题：与其每次对话打补丁，不如把稳定不变的部分固化成一份随工作区分发的手册。

## 做法：五段式骨架

一份实用的 AGENTS.md 不需要长，建议按五个块组织：

```markdown
# 身份与边界
- 你是这个仓库的维护助手，改动前先说明计划
# 环境事实
- macOS / Node 22 / 项目根目录 ~/projects/xxx
- 测试：npm test；部署：make deploy
# 工作流约定
- 中间产物放 /tmp，不进仓库
- 删除、推送、付费操作，先确认再执行
# 输出偏好
- 中文回复，结论先行，附命令原文
# 索引
- 详细规范见 docs/conventions.md
```

核心原则是稳定、简短、可验证。每条指令最好能被一次行为检验——它照做了或没照做，而不是"尽量聪明一点"这类无法执行的形容词。

## 踩坑点

1. **写太长。** 几百行细节会挤占真正任务的上下文，遵循率反而下降。控制在百行以内，细节外链到 `docs/`。
2. **指令互相冲突。**"回复要简洁"和"每个操作都详细解释"放在一起，模型只能随机选一个。写完通读一遍，删掉打架的条目。
3. **把它当安全边界。** AGENTS.md 是提示，不是沙箱。真正的权限控制要靠 OpenClaw 的工具白名单、审批机制和沙箱配置；文件里写"不许删库"不等于删不了。
4. **只写不维护。** 运行时升级、路径迁移后忘了更新，agent 会拿着过期地图开车。把它纳入 git，环境变更连同代码一起提交。

## 可复用建议

- 像写团队 onboarding 文档一样对待它：新会话十分钟内能正确上手，就是合格线。
- 用 agent 自测：新开会话问"这个项目怎么部署？改文件前你会做什么？"，答案与预期不符的地方，就是要补的条目。
- 分层维护：AGENTS.md 只放高频、强约束条目，低频细节拆到子文档，正文里给路径索引。
- 每次你手动纠正 agent 之后问自己：这条能不能变成文件里的一行？能就当天写进去。

## 总结

AGENTS.md 的价值不在写了多少，而在把重复出现的协作摩擦一次性固化。它和 MCP、插件解决的是不同层的问题：MCP 扩展能力，插件增加工具，AGENTS.md 约束行为。花一小时写一版短的，跑两周，把每次口头纠正都沉淀进去，这份手册会比你想象中更快变得"可用"。
