## 背景

OpenClaw 里最容易被低估的功能是 cron：配好调度，Agent 按点自己跑，结果投到指定渠道。但实际用下来，大多数"跑歪了"的任务，问题不在调度，而在那条 instruction 写得太像聊天。

交互式对话里，用户能随时补上下文、纠偏；cron 触发时往往是一个全新 session，没有历史，也没有你在场——instruction 就是 Agent 拿到的全部信息。所以它本质上不是 prompt，而是一份写给"凌晨三点独自值班、只看字面意思"的实习生的交接单。

## 问题

把聊天习惯直接搬进 cron，常见的翻车方式：

- "总结一下今天的消息"——哪个时区的今天？几点到几点？
- "接着上次的分析"——新 session 里根本没有"上次"。
- 只说做什么，不说结果放哪——Agent 自己猜渠道，或把长文灌进默认会话。
- 数据缺失时没给策略——模型为了不空手而归，开始编。

## 做法

我的习惯是按六要素拆解，再落成一条 instruction：

1. **触发上下文**：时间语义钉死——时区、覆盖哪段时间。
2. **数据来源**：写死工具名和路径，不让 Agent 自己"找找看"。
3. **处理边界**：允许什么、禁止什么，尤其是不许主动回复消息。
4. **输出格式**：规定结构、限制长度。
5. **投递目标**：明确渠道/会话，避免默认投递扰民。
6. **失败策略**：数据为空或工具失败时，跳过并说明，还是降级。

```
时区：Asia/Shanghai；范围：过去 24 小时。
数据：用 <MCP 工具名> 读取 <路径/接口>。
边界：只统计，不回复消息，不触发其他工具。
输出：结论一句 + 3 个要点 + 异常项，≤200 字。
投递：<目标渠道/会话>。
失败：数据为空则跳过，附一行原因。
```

两条低成本高收益的补充：一是幂等去重，在 instruction 里写明"先检查今天是否已投递过同样内容，重复则跳过"；二是上线前手动触发跑一次，确认输出格式和投递目标都符合预期，再交给调度，别等凌晨两点看它第一次执行。

## 踩坑点

- **时区和"今天"**：调度器的时间点和模型理解的"今天"经常对不上，跨时区部署更明显。所有时间语义都在 instruction 里钉死。
- **假设有记忆**：每次运行都是新 session。需要跨次状态就落盘到固定文件，并在 instruction 里写明读写路径。
- **输出口径太大**："给我一份完整报告"会诱导模型填充不存在的内容。宁可让它短而准，并强制附上"数据截至时间"。
- **引用不存在的工具**：instruction 里的 MCP 工具名必须真实存在且已启用，否则 Agent 会用别的方式硬凑出结果。
- **instruction 漂移**：需求改了只记在聊天里，忘了同步改 cron。建议 instruction 单独存文件、进版本控制。

## 可复用建议

- 把 cron instruction 当 runbook 写，不当 prompt 写。
- 一个任务只做一件事；想做三件事就拆成三个任务，各自独立验证。
- 频率从 daily 起步，稳定后再加密；高频任务必须控制输出长度，避免刷屏。
- 让每次输出自带"运行时间 + 数据范围 + 异常说明"三件套，方便事后回溯。

## 总结

cron 任务的核心矛盾是：无人值守、无上下文、无追问机会。好的 instruction 不是写得聪明，而是写得完备——时间、来源、边界、格式、去向、失败策略，六样给齐，Agent 才能稳定替你值班。写完之后问自己一句：如果我是凌晨三点读到这行字的实习生，能一次做对吗？
