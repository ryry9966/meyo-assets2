## 背景

OpenClaw 这类常驻网关型助理，价值不只在“你问它答”。用起来之后，用户会期待它主动做事：盯一个目录有没有新文件、到点提醒、发现 CI 挂了喊一声。这就需要 heartbeat——让 agent 在没人说话时也能“醒来”。

实现路径无非两条：**轮询**（agent 按固定间隔自醒，跑一遍检查清单）和**推送**（外部事件源通过 webhook / MCP 工具触发 agent）。两条路我们都实跑过一段时间，这篇记录取舍。

## 问题

轮询的代价很直接：每次心跳基本是一轮完整 LLM 调用。间隔 30 分钟，一天 48 次；哪怕 80% 的心跳结论是“无事发生”，token 照烧。间隔压到 5 分钟，实时性上去了，账单和上下文占用也跟着上去。更隐蔽的是心跳与主会话共池：心跳输出一旦写进共享历史，用户下午来聊天时，上下文里塞满了凌晨三点的巡检记录。

推送看起来省，但把复杂度转移到了事件侧：每个事件源都要写触发器，事件丢失没有兜底，重试没有幂等就是重复轰炸，事件风暴时 agent 会被直接打爆。

## 做法

我们的结论是**按任务性质分流，而不是二选一**：

1. **任务分类。** 周期性巡检类（磁盘、订阅更新、定时汇总）归轮询；事件驱动类（CI 失败、邮件到达、日历变更）归推送。
2. **轮询侧收敛。** 心跳要做的事收敛成一份声明式清单文件，进版本管理。心跳 prompt 只带这份清单，不带全量历史。清单为空或判定无事时走短路径，不进主模型。
3. **推送侧收敛。** 所有事件先进统一入口，落队列，由 dispatcher 做去重、聚合、限频，再唤醒 agent。禁止事件源直连会话。
4. **混合兜底。** 保留一个低频轮询（比如每小时）做对账：检查队列有没有积压、上次心跳是否成功。推送管实时，轮询管“没漏”。
5. **心跳自身可观测。** 每次心跳记录耗时、token、是否有动作；失败要有独立告警——你得监控这个“助理的助理”。

## 踩坑点

- **心跳间隔照抄默认值。** 夜间时段不拉长间隔，一晚上空转几十次，纯烧钱。
- **心跳抢主会话。** 心跳里跑重活，用户消息排队等待。后来改成心跳只“派单”，执行放独立任务队列。
- **推送事件没带幂等键。** webhook 重试一次，用户收到两条一样的告警。
- **心跳静默失败。** 连续三天心跳挂了没人发现，用户以为助理在盯，实际早死了。反向监控（心跳失联即告警）是刚需。
- **深夜推送。** 事件驱动不等于 24 小时打扰，时段策略要单独配。

## 可复用建议

- 心跳清单声明式 + 版本化，改动可 review，出问题可回滚。
- 空 session 短路是省 token 最有效的一招：先用规则或廉价判断决定要不要进主模型。
- 事件统一 schema + 幂等键 + 队列缓冲，推送侧就稳了。
- 间隔做成分时段配置：工作时间密，夜间疏。
- 个人部署的甜点区通常是混合：低频轮询兜底 + 事件推送响应，别追求纯推送的架构优雅。

## 总结

轮询买的是简单和兜底，推送买的是实时和低空转。按任务性质分配、用队列解耦、给心跳自身加监控，比纠结“哪个更先进”有用得多。心跳设计的本质不是定时器调参，而是回答一个问题：**你的助理应该在什么时候醒来，醒来后做的第一件事是什么。**
