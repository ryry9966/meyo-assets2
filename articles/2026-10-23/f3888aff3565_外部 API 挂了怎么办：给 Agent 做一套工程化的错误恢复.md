## 背景

OpenClaw 玩久了一个场景迟早会遇到：Agent 平时好好的，某天某个外部 API 突然超时，整条自动化任务停在半路——或者更糟，模型开始"编"。LLM 本身没有重试和熔断的概念，它只会顺着上下文继续推理。所以错误恢复必须由工具层兜底，指望 prompt 里一句"失败请重试"是不够的。

我维护的几个技能依赖天气、搜索、日历和几个自建服务，过去半年踩了不少坑，把可复用的做法整理如下。

## 问题：四种典型的死法

1. **幻觉补全**：工具返回报错，模型把报错当数据继续推理，编出一个看似合理的结果。
2. **重试风暴**：Agent 在循环里反复调用同一个挂掉的接口，token 和配额双烧。
3. **静默卡死**：某工具 60 秒超时，流水线阻塞，用户在聊天框干等。
4. **上下文污染**：原始堆栈被塞进对话历史，污染后续推理，严重时连密钥都带进去。

## 做法：分四层处理

**1. 工具客户端**：每个外部调用包一层标准客户端，固定三件事——超时（按工具特性设 5–20s）、重试（指数退避加抖动，最多 2–3 次，只对 5xx / 429 / 超时重试，4xx 直接走失败分支）、结构化错误。

**2. 熔断**：连续失败达到阈值（如 3 次）就把该工具标记为不可用，冷却期内直接短路返回"已知不可用"，避免每个请求都去撞一遍；恢复后先放一个探测请求（半开状态），成功再放行。

**3. 降级**：关键技能准备备选来源——缓存上次成功的数据并打时间戳、备一个镜像 API，或明确告诉模型"该工具不可用，基于已有信息回答并声明局限"。降级数据必须带陈旧标记，否则模型会把昨天的天气当今天讲。

**4. Agent 语义**：给模型的错误要短、要结构化：

```json
{"ok":false,"retryable":false,"code":"TIMEOUT","hint":"inform_user_and_skip"}
```

系统提示里写清失败时的行为准则：如实报告、不编造、给出替代方案。错误语义比错误内容更重要。

## 踩坑点

- 重试别交给模型。让 LLM 决定重试等于把节奏交给采样温度，该写死的就写死在代码里。
- 非幂等操作严禁自动重试。发消息、写数据这类调用要配幂等键，否则重试一次就是重复发送。
- 退避不加抖动，多个 Agent 同时恢复会打成节流阀。
- 超时别一刀切：搜索类 5s 够用，文件转换类给 30s 也不冤枉，按工具单独配。
- 熔断记得做半开探测，否则服务恢复了，工具还一直"挂着"。

## 可复用建议

- 把"超时 + 重试 + 结构化错误 + 日志"做成公共包装器，所有技能共用，修一处全局生效。
- 错误结构里永远带 `hint` 字段，告诉模型下一步该干什么，这是性价比最高的一行代码。
- 测试环境主动拔网线：停掉依赖 API，观察 Agent 的完整行为，比任何 prompt 优化都更能暴露问题。

## 总结

Agent 的鲁棒性不取决于 prompt 写得多细，而取决于工具层的工程质量。把重试、熔断、降级放进代码，把结构化错误交给模型，让"如实报告失败"成为默认行为——这三件事做完，外部 API 挂掉时你收到的会是一句坦诚的说明，而不是一个编出来的答案。
