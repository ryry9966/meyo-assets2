## 背景

Agent 的记忆体系跑起来之后，`memory_recall` 是决定体验的一环：它能不能在合适的时机，把三个月前那条「生产环境不要用 root 跑脚本」捞回来。OpenClaw 默认的 memory_recall 走语义检索——把 memory 目录下的 markdown 切块、embedding 进向量库，查询时按余弦相似度召回。这条路对「换个说法也能找到」很友好，但用得久了我发现它有几种相当稳定的失败模式，于是认真对比了一下两条技术路线。

## 问题

两类典型翻车场景：

- **精确标识符召回不到。** 查「上次那个 ERR_CONN_RESET 怎么解决的」，返回的全是「网络排障注意事项」，真正记录错误码的那条排不进 top-k。embedding 对错误码、路径、函数名这类低频 token 天然不敏感。
- **语义检索的短板，全文检索一样有。** 记录里写的是「部署中断复盘」，查询是「服务器挂那次」，BM25 一个词都对不上，照样丢。

也就是说，两者的失败模式几乎互补：语义赢在换说法，全文赢在精确匹配。单选任何一个，都会在特定 query 上稳定丢条目。

## 做法

我在插件侧加了一层混合召回，记忆仍然只放一个 SQLite 库：

1. **条目原子化**：一条 memory 只记一件事，带上时间、来源、类型（fact / preference / event）和 tags。长条目会让向量被稀释，关键词也难命中。
2. **双索引**：正文 + tags 建 FTS5，正文向量化进 sqlite-vec，同一张表挂两个影子索引。
3. **双路召回 + RRF 融合**：查询同时打两路，各取 top-20，倒数排名融合后按时间衰减微调，取前 5–8 条注入上下文：

```sql
-- 同一个库，两条影子索引
SELECT id FROM mem_fts WHERE mem_fts MATCH :q LIMIT 20;
SELECT id FROM mem_vec WHERE k = 20;          -- 向量近邻
-- 融合：score = 1/(60+rank_fts) + 1/(60+rank_vec)，再乘 recency 因子
```

RRF 的好处是不用调两路分数的权重，排名天然可比。

4. **建评测集**：整理 30 条真实 query → 期望命中的 memory id，改索引前后各跑一遍看命中率。没有这个，全是体感。

## 踩坑点

- **FTS5 默认的 unicode61 分词器对中文基本不可用**：连续中文会被当成一个 token，「部署」匹配不到「部署失败」。我换成了 trigram tokenizer，省事且够用。
- **换 embedding 模型等于全量重建向量**。旧向量和新查询不在同一个空间，相似度全部失真。向量表里务必存模型名和版本——我的评测集第一次跑就栽在这上面。
- **余弦相似度的绝对阈值没有跨模型意义**。0.75 在模型 A 很高，在模型 B 可能是噪音线，只看相对排序，别设绝对门槛。
- **时间衰减别开太猛**。有一次调得激进，长期偏好类记忆两周就被冲出 top-k。对用户来说，「偏好被忘了」比「召回慢半拍」伤害大得多。

## 可复用建议

- 记忆量在几千条以内，**先上全文检索 + tags 就够用**，语义检索是锦上添花，别为了架构洁癖先建向量库。
- 混合 + RRF 是省心的默认答案，两路各取所长，几乎不用调参。
- 评测集先行：30 条真实 query 的固定集子，比任何直觉都可靠。
- recall 日志里记录命中与未命中，每月人工抽查一次未命中样本，往往能提前发现新的失败模式。

## 总结

语义搜索和全文搜索不是优劣关系，而是失败模式互补。工程上的答案很无聊但有效：**两个都要，RRF 融合，评测集说话**。成本也不高——一个 SQLite，两张影子索引，一个晚上能搭完，收益是 recall 命中率实打实地上了一个台阶。
