## 背景

OpenClaw 的 agent 长期运行后，workspace 里会积累大量 memory 文件：MEMORY.md、按日期拆分的 daily notes、项目决策记录。memory_recall 的职责，就是在对话中把这些"旧上下文"捞回来。捞得准，agent 像是记得上周的事；捞不准，用户就得反复复述背景。

社区里常见两条路线：全文搜索（rg / SQLite FTS）和语义搜索（embedding + 向量近邻）。两派都有人用，但很少有人拿出可比的数据。

## 问题

我的 agent 跑了约三个月，积累 400 个 memory 文件，观察到两类典型失败：

- **全文搜索**：用户问"上次那个部署报错怎么解决的"，记录里写的是具体错误码，这次换了个说法，就捞不回来。
- **语义搜索**：问"project-x 的 webhook 密钥放哪了"，向量检索返回一堆"配置管理"的泛泛段落，精确标识符反而排不进前五。

单一方案盲区明显。真正的问题是：混合方案值不值得多出来的那点复杂度？

## 做法

我搭了一个极简评测流程，三步：

1. **攒评测集**。从近两个月的会话日志里，人工挑 30 个"确实需要回忆"的问题，标注每题应命中的 memory 文件路径。半小时的事，但这是唯一可信的标尺。
2. **跑三种检索**。a) rg 全文匹配（中文按子串命中，够用）；b) embedding 检索（memory 按 H2 标题切块，本地模型，cosine top-8）；c) 混合：两路各取 top-8，RRF 融合，再按文件日期做轻微衰减。
3. **算 hit@5**。结果大致是：全文 17/30，语义 20/30，混合 26/30。混合的收益是真实的，不是玄学。

## 踩坑点

- **切块别按固定 token 数硬切**。我最初按 512 token 切，一条决策记录被腰斩，语义检索两半都排不上去。改按 markdown 标题切后，hit@5 直接涨了 3 题。
- **语料小于两三百块时，embedding 优势基本体现不出来**，还引入模型依赖。先看自己 memory 的量级再决定。
- **中文走 SQLite FTS 默认分词基本失效**；直接用 rg 子串匹配反而稳，代价是同义词全靠 memory 写作习惯兜底。
- **不做时间衰减，半年前的过期方案会压过上周的修订版**。衰减系数要轻，重了会把老项目记忆整体埋掉。
- **top-k 别贪多**。捞 20 条塞进上下文，噪声比帮助大，agent 反而开始编。

## 可复用建议

- 别急着上向量库。全文打底 + 需要时加一路语义 + RRF 融合，几十行代码，零新增基础设施。
- memory 写作本身是检索质量的一半：文件头写清日期、项目名、状态（进行中/已废弃），比调检索参数收益更大。
- 把"recall 未命中"的 case 沉到评测集里，检索质量会随使用单调变好。

## 总结

语义 vs 全文不是二选一，而是分工：全文负责精确标识符和确定性命中，语义负责换说法的模糊回忆。在我的 30 题评测里，混合方案明显最优，但更重要的是评测集本身，没有它，所有调参都是凭感觉。建议每个跑长期 agent 的人，先攒 20 条真实 recall case 再动手。
