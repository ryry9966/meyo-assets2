## 背景

跑自动化任务的 Agent，早就不是"一次调用"了，而是把 LLM、MCP 工具、第三方 API 串成的长链路。链路越长，单点失败概率越高：按 10 个外部依赖、每个 99.9% 可用算，一次任务全绿的概率只剩九成左右。跑批和过夜任务里，失败是常态，不是意外。真正的问题是：挂了之后，Agent 表现得体面还是翻车。

## 三种典型的错误姿势

1. **直接崩**：一次 429 或超时让整个流程中断，前面跑了一半的结果全部作废。
2. **疯狂重试**：无限循环打一个已经挂掉的接口，token 和配额一起烧完。
3. **假装成功**：错误被吞掉，模型拿到空结果后开始脑补，输出看起来完整但全是编的——这是三种里最危险的。

## 做法：一套分层的恢复策略

**1. 先分类，再重试。** 把错误分成可重试（429、502、503、超时、网络抖动）和不可重试（401/403 鉴权、400 参数、404 资源不存在）。分类错了后面全白搭——对 401 重试一百次也没有意义。

**2. 退避 + 硬超时。** 可重试错误用指数退避加随机抖动（如 1s/2s/4s ±20%），最多 3~5 次；同时给单次调用设硬超时（比如 30s 封顶），绝不让一个挂死的接口阻塞整个 Agent 循环。

**3. 熔断与降级。** 连续 N 次失败后进入熔断，冷却期内直接走降级路径：读缓存、切备用 Provider、或把任务标记为 paused 等人工介入，而不是继续撞墙。

**4. 把失败结构化地喂回模型。** 工具调用失败时，不要只丢一个字符串堆栈，给模型一个结构化契约，例如 `{status, error_type, retryable, suggestion}`，模型才能正确决策：换路、跳过还是上报用户。关键是明示"失败时不要编造结果"。

**5. 幂等 + 断点续跑。** 写操作（下单、发消息、写库）必须带幂等键，重试时服务端能识别重复；长任务落 checkpoint，恢复时从断点继续，而不是从头再来。

## 踩坑点

- 对非幂等 POST 直接重试 → 重复扣款、重复发消息。先做幂等，再谈重试。
- 退避不加抖动 → 多实例同时重试，服务刚喘过气就被再次打挂。
- 把 HTTP 200 当成功 → 不少接口 200 里包着 error body，必须校验业务码。
- 超时设太长 → 一个 120s 超时的接口能把并发任务全拖死。
- 日志只写"调用失败" → 缺请求 ID、缺响应片段，事后查无可查。

## 可复用建议

- 用**统一的 tool executor** 包住所有外部调用，重试、超时、熔断、日志集中一处，别每个插件各写一套。
- 每个失败都带请求 ID 和响应片段，这是排障的最低配置。
- 长任务默认写 checkpoint：成本很低，救火时价值极高。
- 定期做故障演练：手动拔掉某个 API，看 Agent 是优雅降级还是当场翻车。

## 总结

外部 API 挂掉不是异常，是生产环境的日常。错误恢复的核心就三句话：**分类再重试、失败要结构化、状态可续跑**。做到这三点，Agent 才算得上是能放心放进生产里过夜的那种。
