## 背景：每次会话都是冷启动

OpenClaw 的 Agent 没有天然的记忆连续性。SOUL.md 定义了它是谁、怎么说话，但没有任何文件回答“对面坐的是谁”。结果是一种微妙的错位：Agent 清楚自己的角色设定，却不知道你在东八区、主力语言是 Go 还是 Python、上周正在迁移哪个服务。

聊天记录看似能补上这一点，但不可靠：记忆检索是概率性的，今天能召回的内容明天未必。而 USER.md 是确定性的——每次会话随 workspace 文件一起注入上下文，不依赖检索运气。

## 问题：隐性上下文的反复付费

没有用户档案时，三类问题会反复出现：

1. **重复交代**。时区、目录结构、命名习惯，每隔几天就要重新说一遍。
2. **错误假设**。它用你两年前弃用的框架版本写代码，或把已完成的事当作待办。
3. **风格错位**。你要结论，它给你科普；你赶时间，它按部就班。

单次成本不高，但持续发生。本质是把“我对协作的期望”这个本该一次写清的东西，摊到了无数次对话里。

## 做法：写一份够用的 USER.md

在 workspace 根目录创建 USER.md，建议四层结构：

```markdown
# USER
- 时区：Asia/Shanghai；语言：中文，技术名词保留英文
- 角色：后端工程师，主力 Go + Python，macOS
- 偏好：先给结论再展开；不确定就明说；不要复述我的提问
- 边界：不主动重构未要求的代码；不用 emoji

## 当前关注
- 消息队列从 RabbitMQ 迁移到 NATS（方案已定，进行中）
```

关键是每一条都要“可执行”。“我喜欢简洁的代码”没有信息量，“输出代码不加注释，除非我要求”才能被遵守。维护节奏以月为单位：定期 review，项目切换时更新“当前关注”。

## 踩坑点

- **写太长**。有人写成自传，三百行常驻上下文，每天白烧几千 token。控制在 50–80 行，装不下的内容下沉到 MEMORY.md。
- **混入动态信息**。会议安排、临时任务属于记忆或日程，不是身份。USER.md 的变更频率不该高于每月一次。
- **放敏感信息**。密钥、内网地址、真实客户名都不要写。这份文件会整份进入模型上下文，也可能进日志。
- **与 SOUL.md 打架**。SOUL 定义 Agent 人格，USER 描述用户事实。语气规则两处都写必然冲突，只留一处，另一处引用即可。

## 可复用建议

把 USER.md 当作“给新同事的 onboarding 一页纸”来写：一个新人读完五分钟内能和你有效协作，这份文档就合格了。三个配套习惯：

- 用 git 管理，历史 diff 就是你对协作方式认知的演化记录；
- Agent 犯了“本不该犯”的错时，先别急着在对话里纠正，想想能否落成 USER.md 的一行；
- 团队场景拆成 USER.md（个人）与 TEAM.md（团队约定），各自独立维护、独立变更。

## 总结

USER.md 的价值不在“让 AI 更懂你”这类玄学表述，而是把散落在聊天记录里的隐性约定，固化成每次会话确定注入的上下文。成本极低——一个 markdown 文件、十几行——收益是把 Agent 从“每次都要重新认识的工具”变成“记得住前提的协作者”。建议直接动手：先写十行，用一周，再改。
