## 背景

跑过自动化 Agent 的人都有体感：自己写的代码很少挂，挂的几乎全是外部依赖——LLM 供应商限流、MCP 服务超时、第三方接口 502、配额半夜耗尽。单次失败不可怕，可怕的是 Agent 对失败的"反应方式"：要么整条流水线卡死，要么更糟——模型拿到报错后自己脑补一个结果继续往下跑，等你发现时，错误已经污染了下游三步。

## 问题出在哪

传统服务的错误处理是确定性代码：catch、重试、降级，写死就行。Agent 的麻烦在于错误信号会回流进模型上下文，带来两类新故障：

1. **模型"替你"处理失败**：看到报错后自圆其说，编造数据或假装成功；
2. **重试循环失控**：把重试决策交给模型，它可能无限重试、改参数硬试，token 烧得比故障本身还贵。

结论很直接：恢复逻辑必须放在模型外面，用确定性代码做。

## 做法

**1. 先分类，再重试。** 只重试"可自愈"的错误：429、5xx、超时、连接拒绝。401/403/400 属于配置或权限问题，重试一万次也不会好，应直接终止并报警。429 记得读 `Retry-After` 头，别自己猜。

**2. 指数退避 + 抖动。** 建议 1s → 2s → 4s，上限 3 次，每次加 0~500ms 随机抖动。没有抖动的话，服务恢复瞬间所有 Agent 同时打过去，等于帮它二次宕机。

**3. 熔断按端点隔离。** 连续失败 5 次就对该工具熔断 60 秒，期间直接返回"暂时不可用"，而不是继续打超时请求拖死整个 loop。注意是 per-endpoint，别让一个挂掉的搜索接口把写库工具也连坐。

**4. 幂等是重试的前提。** 对 POST 类操作（下单、发消息、扣款）必须带幂等键，否则重试一次就是重复扣款。拿不准幂等性的接口，宁可失败上报，不要自动重试。

**5. 给模型干净的错误信号。** 工具返回不要丢原始堆栈，收敛成结构化结果：

```json
{ "status": "degraded", "reason": "upstream_timeout",
  "fallback": "cached_2h_ago", "retryable": false }
```

同时在系统提示里写清处置规则：degraded 时告知用户数据是旧的，不可重试时直接上报，禁止编造。

## 踩坑点

- 重试逻辑写进 LLM 循环里，让模型自己"再试一次"——等于把基建交给掷骰子；
- 静默降级：用了两小时前的缓存却不声明，用户拿旧数据做了决策，比直接失败更糟；
- 超时没设或设到 60s 以上，一个慢接口卡住整条工作流；
- 熔断器全局共用，一个端点抖动，全体工具躺平；
- 把上下文当垃圾桶，重试日志全量塞进去，几轮之后模型开始"道歉文学"。

## 可复用建议

- 所有外部调用走同一个带超时/重试/熔断的客户端封装，策略放配置文件，不要散落硬编码；
- 工具返回 schema 里固定一个 `status` 字段（ok / degraded / failed），提示词只需处理三种情况；
- 每次降级和熔断都落日志：错误码、重试次数、耗时，事后复盘全靠它；
- 长任务做状态持久化，恢复时从断点续跑，而不是从头来过。

## 总结

外部 API 一定会挂，这不是概率问题，是时间问题。Agent 的可靠性不取决于模型多聪明，而取决于失败发生的那几秒里，有没有一层确定性的代码在替它兜底：分类、退避、熔断、降级、幂等。把这层做扎实，模型只需要在干净的成功/失败信号上做决策——这才是提示词之外，Agent 工程里真正值钱的部分。
