## 背景

跑 Agent 自动化越久越会发现一个事实：链路里最脆的往往不是模型，而是外部依赖。LLM API、搜索、MCP 工具、第三方 SaaS……任何一环超时、限流或返回 5xx，整个任务流就会卡住。Agent 每一步都在调用外部世界，失败是常态，不是异常。

## 问题

API 挂掉本身不可怕，可怕的是它引发的连锁反应，实践中最常见的三种：

1. **盲目重试**：循环里没做退避，几秒内打几十次请求，把限流升级成封禁，还烧掉配额。
2. **假成功**：工具调用失败但异常被吞掉，LLM 拿到空结果后自己脑补一份数据继续往下走，下游全是错的。
3. **连锁堵死**：一个长超时调用阻塞了整个事件循环，后面排队的任务全部超时。

## 做法

我们的经验是把错误恢复当成 Agent 的一等公民来设计，分四步：

**1. 先给错误分类**
重试前分清“暂时性”和"永久性"：429、503、超时、网络抖动值得重试；401、404、400 参数错误重试一百次也没用。分类错了，后面的策略全是白搭。

**2. 指数退避 + 抖动**
暂时性失败用指数退避（1s → 2s → 4s…），加随机抖动避免多个 Agent 同时重试造成惊群。设最大重试次数（一般 3 次）和单次调用总超时预算，别让一次调用挂住整个循环。

**3. 熔断 + 降级**
连续失败 N 次后熔断该工具，一段时间内不再请求，转走降级路径：返回缓存、切换备用 provider、或明确跳过该步骤并打标。熔断器要有半开状态，定期探测恢复，否则工具会“假死”一整天。

**4. 把失败状态喂回模型**
这步最容易被忽略。工具失败时不要静默返回空值，而是把结构化错误（error_type、retryable、hint）传给 LLM，让它有机会换工具、改计划或如实告知用户。Agent 的“智能”应该用在应对失败上，而不是掩盖失败。

另外，所有重试必须建立在幂等基础上——带请求 ID、做去重，否则重试一个"下单"操作就是事故。

## 踩坑点

- **吞异常**：catch 所有异常然后返回空数组继续跑，是最常见的坑，问题几步之后才爆发，排查成本极高。
- **退避无抖动**：多个并发 Agent 同步重试，把刚恢复的服务又打挂。
- **重试非幂等操作**：没有去重机制的重试等于重复执行副作用。
- **熔断器永不恢复**：只熔断不探测，降级路径变成永久路径。
- **日志只有堆栈**：要记结构化事件（工具名、错误类型、耗时、重试次数），否则事后无法复盘。

## 可复用建议

- 把所有外部调用收敛到一个统一的 tool client，重试、超时、熔断逻辑写一次，处处生效。
- 定义统一的错误契约：`{ok, error_type, retryable, hint}`，让 MCP 工具和插件都遵守它。
- 本地做故障注入演练：主动 mock 超时和 503，验证降级路径真的走得通——上线前没演练过的降级逻辑，等于没有。

## 总结

外部 API 挂掉不是意外，是 Agent 工程的日常。分类错误、退避重试、熔断降级、把真实失败状态交还给模型——这套组合拳不复杂，但决定了你的自动化是“偶尔抽风后自愈”，还是“半夜把人叫起来救火”。建议从今天开始，把 Agent 里裸调的 API 全部包一层。
