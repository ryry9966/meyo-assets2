## 背景

在 OpenClaw 的自动化实践里，Agent 很少是孤立运行的：查资料要调搜索 API，读写要连数据库，MCP 工具背后几乎都挂着第三方服务。这些依赖在长周期任务里一定会挂——限流、超时、上游改接口，都是日常运维事件，不是异常。所以问题从来不是"API 会不会挂"，而是"挂的时候，Agent 的行为是否还可信"。

## 问题：挂的不是 API，是 Agent 的判断

实际跑下来，最常见的三种失控：

1. **错误正文进了上下文**。工具把 500 页面的 HTML 原样丢给模型，模型把报错信息当成资料，一本正经地硬答。
2. **无限重试烧配额**。工具层没有上限，模型又倾向于"再试一次"，几轮下来 token 和第三方配额双输。
3. **吞错返回空结果**。异常被捕获后返回 `[]`，Agent 汇报"没查到相关数据"，用户被误导。

根本原因一致：Agent 自己分不清"暂时不可用"和"没有这个数据"，除非我们在工具层替它分清。

## 做法：给失败定协议，给重试定边界

**第一步，错误分类。** 在工具层把错误分成可重试（超时、429、5xx）和不可重试（401/403、参数错误、404）。前者走退避，后者直接失败。不要把原始堆栈丢给模型。

**第二步，有界重试。** 指数退避加 jitter，最多 3 次或总耗时 10 秒封顶，且只对幂等操作重试。

**第三步，结构化失败信号。** 工具返回给 Agent 的不是错误字符串，而是协议化的状态：

```json
{ "status": "failed", "retryable": false, "hint": "try_backup_or_report" }
```

Agent 拿到的是可决策的信息：换路、问用户，还是如实汇报。

**第四步，降级链与熔断。** 顺序：主 API → 备用 API → 带时间戳的本地缓存（明确标记 stale）→ 明确告知失败。连续 N 次失败后熔断，冷却期内直接走降级路径，不再撞上游。

## 踩坑点

- **对 POST 盲目重试**：重复下单、重复发通知。非幂等调用加幂等键，或者干脆不重试。
- **退避不加 jitter**：多个 Agent 同时挂、同时恢复，形成惊群，上游刚缓过来又被打挂。
- **把错误响应缓存了**：空结果被当成有效数据。缓存必须带 TTL 和 degraded 标记。
- **只返回字符串 "error"**：模型会把这当成新的输入，自己开始循环重试。必须显式给"放弃"信号。
- **单次超时设太长**：一个 30 秒的超时能把整个 Agent 循环拖死。单步超时和任务总预算要分开设。

## 可复用建议

- 所有外部调用收口到**一个统一的 resilient client**：超时、重试、熔断、日志集中管理，插件各写一套必然出事。
- Agent 可见的状态收敛为三态：**OK / DEGRADED / FAILED**，每个状态附一个行动 hint。
- 上线前做**故障注入**：mock 一个 503 和高延迟上游，看 Agent 是体面降级还是原地转圈。
- 失败要**可见**。宁可告诉用户"该服务暂不可用"，也不要让模型基于坏上下文编一个答案。

## 总结

错误恢复的核心不是把重试次数调大，而是把"失败"翻译成 Agent 能理解、能据此选择的结构化事实。重试、熔断、降级链都只是手段；目标是让 Agent 学会体面地失败——并且让用户知道它失败了。在长期运行的自动化里，这套机制的优先级，高于任何单个功能的实现。
