## 背景

Agent 的价值不在会聊，而在能"动手"。对 OpenClaw 来说，对接外部服务——内部 RPC、第三方 SaaS、自家数据库的只读接口——是把一个聊天助手变成生产力工具的关键一步。OpenClaw 提供了两条主要通路：通过 MCP 挂载工具，或者自己写插件/skill 直接注册 tool。这篇帖子记录一次把内部工单 API 接入 OpenClaw 的完整过程，以及中间踩的坑。

## 问题

最初的做法很"直觉"：把 API 文档塞进 system prompt，让模型自己拼请求。跑了两周，问题一堆：

- 模型偶尔记错字段名，请求 400；
- 鉴权 token 出现在对话上下文里，日志中到处都是；
- 一次超时重试，同一个工单被创建了三遍；
- API 返回大 JSON，几轮对话就把上下文撑爆。

根因只有一个：我们把"协议谈判"交给了模型。模型擅长决策，不擅长精确拼接 HTTP 请求。握手这件事，应该由确定性的代码完成。

## 做法

最终收敛成三步：

**1. 先用 curl 把 API 摸清。** 明确鉴权方式、必填字段、错误码语义、是否幂等。这一步不要省，它是后面所有描述的素材来源。

**2. 写一层薄适配器（tool）。** 不管走 MCP 还是插件，原则相同：一个 tool 对应一个明确意图，比如 `create_ticket`、`query_ticket`，而不是一个万能的 `call_api`。适配器内部负责：鉴权（从环境变量读 secret）、参数校验（schema 校验）、超时（10s）、重试（只对 GET，POST 用幂等键）。返回给模型的结果做裁剪：只留 id、状态、摘要，大字段给个引用，让 agent 需要时再查。

**3. 用写文档的态度写 tool description。** 模型选不选这个工具、参数填得对不对，几乎完全取决于描述。我们的模板是：一句话说清用途；写明何时"不要"用；每个参数给一个真实示例；把常见错误码翻成人话（例如 `409 = 工单已存在，改用 query_ticket`）。

## 踩坑点

- **描述里的歧义是最大 bug 源。** "status（状态）"这种描述，模型会瞎填。改成明确枚举后，错误率基本归零。
- **写操作必须幂等。** Agent 遇到超时会重试，POST 一定要带客户端生成的幂等键。
- **secret 不能进上下文。** 鉴权只发生在适配器内部，工具入参和返回值里都不出现 token。
- **长任务别同步等。** 超过 30 秒的调用改成"提交任务 + 查询进度"两个 tool，否则模型要么一直挂着，要么超时后编造结果。
- **权限收窄。** 只读场景用只读 key，别图省事给管理员凭证。

## 可复用建议

- 一 tool 一意图，宁多勿泛；
- 返回结构化短结果，详情走二次查询；
- 上线前给 tool 加 `dry_run` 参数，灰度观察一周调用日志再放开；
- 用 trace id 把 agent 会话和 API 请求串起来，出问题能回放；
- 把 tool description 当 API 文档维护，改接口先改描述。

## 总结

Agent 与外部服务的握手，本质是"模型做决策、代码做执行"的分工。OpenClaw 的 MCP 与插件机制已经把执行层的位置留好了，我们要做的是把每一条 API 包成意图清晰、幂等安全、描述准确的工具。适配器写得越"无聊"越好——无聊意味着确定，而确定性正是 Agent 生产化最稀缺的品质。
