## 背景

Agent 的能力上限，很大程度取决于它能"够到"哪些外部服务。OpenClaw 负责调度、记忆和决策，但真正干活的是工具层：查订单、发消息、写数据库，最后都落到一次具体的 API 调用上。社区里常见的问题不是"接不上"，而是"接得乱"——每个服务一套写法，出了问题没人能复现。

## 问题

几种典型接法都埋了雷：

- 把接口文档塞进 system prompt，让模型自己"猜"怎么调；
- 在插件里硬编码 base URL 和密钥；
- 调用失败后把原始 HTML 错误页原样返回给模型。

这些做法短期都能跑，但一旦服务改版、换环境、或 agent 开始重试，就会以很诡异的方式坏掉。

## 做法

我的经验是按四步拆：

**1. 先梳理"能力"，不是"接口"。** 一个 CRM 可能有一二十个端点，agent 真正需要的往往就三件事：查客户、记跟进、查记录。工具数量控制在个位数，粒度对齐业务动作而不是 REST 资源。

**2. 写一层薄 adapter。** 每个外部服务一个插件，配置全部外置：base URL、鉴权方式、超时、重试策略走配置文件，密钥从环境变量注入。工具 schema 用 JSON Schema 声明清楚参数和返回结构，让模型知道边界在哪。

**3. 标准化错误出口。** 无论下游返回什么，adapter 出口统一成三段式：`ok / error_code / message`。message 写简短的人话，不要透传堆栈。模型拿到结构化错误，才知道该重试、该换参数，还是该告诉用户"这条路走不通"。

**4. 超时和幂等是底线。** 默认超时压在 15 秒以内；所有写操作带请求 ID 做幂等键。agent 层的重试和 adapter 层的重试要分工——4xx 参数错误不重试，5xx 用指数退避最多两次。

能走 MCP 的服务优先走 MCP：schema 和鉴权都是现成的，省掉自建 adapter 的大部分工作。剩下的内部 HTTP 服务，再按上面套路包一层。

## 踩坑点

- **粒度失控**：一口气注册三十个工具，模型选择准确率明显下降。宁可用一个 `crm_query` 带类型参数，也别拆成按字段查的十个工具。
- **GET 也有副作用**：有些服务的查询接口会顺带改状态，接之前用日志确认一遍，别默认 GET 安全。
- **返回数据不裁剪**：分页接口吐 200 条记录直接进上下文，token 烧得快，模型还抓错重点。adapter 里做字段白名单和条数上限。
- **schema 漂移**：上游加了必填字段，工具照样"成功"返回空结果。给每个工具留一个冒烟测试，CI 里定期跑。

## 可复用建议

- 先用 curl 把 API 跑通，再封装成工具，别拿 agent 当调试工具；
- 每个工具配最小用例：一个正常输入 + 一个故意触发错误的输入；
- 工具调用日志记录输入输出，但脱敏密钥和 PII——排障时这是唯一线索；
- 写操作上线前加 dry-run 开关，让 agent 先"说"它要调什么。

## 总结

对接外部服务本质上是给 agent 立规矩：能调什么、怎么调、失败了怎么办。把鉴权、超时、错误格式这些脏活收进 adapter，把干净的能力清单交给模型，OpenClaw 这套"握手"才算稳定。工具层做得越无聊，agent 层就越能发挥——这大概是对接类工作能得到的最好评价。
