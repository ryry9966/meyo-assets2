## 背景

Agent 的能力上限，基本由它能调用的外部服务决定。OpenClaw 本身不承载业务逻辑，它的价值在于把外部系统的能力翻译成 Agent 可理解、可调用的动作。MCP 让“接服务”有了标准协议，但落到真实项目里，你面对的往往是一个个普通 HTTP API，认证方式、错误格式、限流策略各不相同。握手能否成功，取决于这层翻译做得是否扎实。

## 问题

社区里反复出现几类失败模式：

- 工具接了一堆，Agent 不知道什么时候该调哪个；
- 写操作没有幂等保护，重试一次就重复建单；
- 外部 API 返回大 JSON，几轮对话后上下文被塞爆；
- 原始报错直接抛给模型，模型拿着堆栈瞎猜。

这些都不是协议问题，是工程问题。

## 做法

**1. 先定义动作语义，再写代码。** 一个工具一个职责，描述里写清用途、何时该用、何时不该用、参数约束、失败语义。工具描述是给模型看的接口文档，不是给人看的注释。我们内部用的最小模板：

```yaml
name: create_ticket
when_to_use: 用户明确要求创建工单时；纯查询不要用
failure: 返回 reason 字段，给出可行动的下一步
```

**2. 加一层薄接入层。** 不要让 Agent 直接发裸 HTTP。用插件或 MCP server 包一层，把认证、超时、重试、字段裁剪收敛在这一处。本地工具走 stdio，远程服务走 streamable HTTP，按部署形态选。

**3. 权限最小化。** 只申请用到的 scope；token 走环境变量或凭据文件，绝不出现在提示词和对话内容里。

**4. 控制返回体积。** 接入层做字段裁剪和分页，只把模型决策需要的字段传回去。返回体积失控是最常见的上下文杀手。

**5. 错误要“翻译”。** 把 429/5xx 转成模型能行动的语义，比如“已限流，建议 30 秒后重试”或“缺少参数 X，需要用户补充”。

**6. 四类用例联调。** 正常、超时、限流、鉴权失败，缺一不可。

## 踩坑点

- **幂等**：所有写操作必须带客户端生成的幂等键。Agent 重放比你想象中频繁，没有去重就会重复下单、重复建单。
- **重试叠加**：接入层重试 + Agent 层重试会指数放大请求。重试只在一层做，写操作默认不自动重试。
- **工具数量**：单服务暴露十几个以上工具，模型选择准确率明显下降，做动作合并或二级路由。
- **时间与时区**：日程、工单类 API 的经典坑，提前明确约定传 UTC 还是本地时间。
- **日志泄密**：确认接入层日志不会打出 Authorization 头和请求体里的敏感字段。

## 可复用建议

- 团队内建一个工具描述模板，字段固定，新人照填，评审有据。
- 错误码转译做成通用中间件，所有插件共享一份实现。
- 每个外部服务一个独立插件进程，故障隔离，挂一个不连累其他。
- 接入节奏固定：只读先上 → 写操作加人工确认 → 小范围灰度 → 再全量。

## 总结

握手的前提是契约：动作语义、错误语义、安全边界，三件事在接入层一次性讲清楚。协议解决“怎么连”，工程细节决定“连得稳不稳”。先只读、后写入，先小工具集、后逐步扩，是对接外部服务最不容易翻车的路径。欢迎在社区帖子里贴出你们的接入层设计，尤其是幂等和错误转译的实践。
