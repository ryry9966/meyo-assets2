## 背景

用 OpenClaw 这类 Agent 框架跑任务久了，很快会遇到同一个瓶颈：主 Agent 是串行的。比如让它"对比三个 MCP server 的能力、整理成表格"，实际执行是查 A → 记 A → 查 B → 记 B……十几分钟走完，中间产物还全堆在主对话上下文里，越跑越乱。

我们的解法是把主 Agent 变成编排者（orchestrator），把独立子任务派发给 subagent 并行执行，各自带独立上下文，跑完只回传结构化结果。

## 问题拆解

不是所有任务都值得并行。实践里适合的形态有两类：

1. **扇出型**：任务天然可拆成 N 个互不依赖的子任务（多竞品调研、多目录代码审查、多服务日志排查）。
2. **流水线型**：步骤间有依赖，但每步内部可并行（先并行收集，再合并分析）。

判断标准很简单：子任务之间会不会互相写对方的文件或状态。会，就先做隔离，或者退回串行。

## 做法

1. **主 Agent 只做拆解和汇总**。prompt 里明确角色：拆任务、派发、收结果、合并，不亲自干活。
2. **给每个 subagent 写"合同式" prompt**：输入是什么、边界在哪、必须返回什么格式。我们统一返回 JSON，带 `status` / `findings` / `files_touched` 字段。
3. **限制并发**。并发 3~5 起步，按 API 限额和成本调。在 OpenClaw 侧用插件或脚本包一层信号量，避免一次性打满配额。
4. **工作区隔离**。每个 subagent 分配独立子目录，禁止跨目录写；需要共享的中间产物由主 Agent 统一中转。
5. **失败兜底**。单个 subagent 超时或报错，主 Agent 收集部分结果继续，最后在汇总里标注哪些分支失败，而不是整体重来。

## 踩坑点

- **上下文传染**：最初我把主对话的完整历史塞给每个 subagent，结果它们继承了我的错误假设。改成只传"任务描述 + 必要背景摘要"后明显好转。
- **拆得太细**：把一个 5 分钟的任务拆成 8 个 subagent，编排开销和结果合并成本比省下的时间还多。经验阈值：单子任务预计超过 2~3 分钟才值得派发。
- **静默失败**：subagent 挂了却返回空结果，主 Agent 当成"查无信息"写进结论。必须强制 `status` 字段并在合并前校验。
- **文件冲突**：两个 subagent 同时改同一个配置文件，后写的覆盖先写的。隔离目录 + 主 Agent 统一写入能根治。

## 可复用建议

- 把 subagent 的 prompt 做成模板存进插件仓库，输入输出字段固定，团队复用成本低很多。
- 先串行跑通，再并行化。并行带来的核心价值是速度和上下文隔离，不是第一版就该上的东西。
- 每个 subagent 的执行轨迹单独落日志，排障时按分支查，别混在主对话里。
- 并发数做成配置项，不同模型、不同配额场景下差别很大。

## 总结

subagent 编排的本质是"用上下文隔离换执行速度和结果质量"。它技术上不复杂，难点在任务拆解的纪律性和结果契约的严格性。建议从一个小而独立的扇出场景开始试，把 prompt 模板和兜底逻辑沉淀下来，再逐步扩大使用范围。
