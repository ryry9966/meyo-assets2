## 背景

OpenClaw 的 `memory_recall` 是 agent 长期记忆的入口：memory 目录下的 markdown 文件被切分后，检索出 top-k 交给模型当上下文。社区里常见两种声音——一种认为必须上 embedding 做语义检索才“聪明”，另一种觉得关键词全文搜索更可控。我在自己的日常 agent 上做了一轮小规模对比，结论是：这两条路覆盖的是**不同的失败模式**，真正的问题不是二选一，而是怎么混。

## 问题：两种检索各有一种典型失败

- **语义检索丢精确 token**：让 agent 回忆某个错误码 `ERR_5021` 或某个脚本文件名，语义 top-3 里根本没有对应记忆。embedding 会把这类标识符“平均”成普通语义，区分度很低。
- **全文检索丢换说法**：当时记的是“部署流水线超时，把并发降到 4”，三个月后问“CI 老是卡住怎么办”，关键词全对不上，全文检索直接空手而归。

## 做法：20 条记忆的回归测试

1. 从 memory 目录挑 20 条真实记忆，每条写两个 query：一个换说法（同义改写），一个带精确 token（错误码 / 文件名 / 专有名词）。
2. 分别在纯语义、纯全文两种模式下跑 recall，统计 top-3、top-5 命中率。
3. 我的结果：换说法 query 上语义 16/20、全文 7/20；精确 token query 上语义 6/20、全文 17/20。两边几乎互补。
4. 落地方案是回到混合检索。OpenClaw 的 memory 本身就是语义为主、文本兜底的 hybrid，重点是把检索配置调到位：`maxResults` 放大到 6~8，让模型而不是检索层做最终筛选；`minScore` 先观察自己语料的分数分布再定，别拍脑袋设高。另外确认 fallback 真的会触发——embedding 服务异常或分数过低时能落到全文，而不是返回空结果。

## 踩坑点

- 只看 top-1 会误判。agent 能用的是 top-k 里的上下文，检索层过早截断比“排第一不够准”伤害更大。
- 换 embedding 模型后旧向量必须全量重建，否则分数体系乱了，`minScore` 完全失去参考意义。
- 中文全文检索注意分词：按字切分能兜底“流水线→流水”，但“管线”这种换词只能靠语义那一路。
- 语义检索对时间没有偏好，“上周那条”类问题要靠记忆文件本身带日期、按天/按主题分文件来补。

## 可复用建议

- 检索是基础设施：任何改动前后跑同一套 20 条测试集，用数据说话，别凭感觉。
- 写入侧比检索侧更值得投入：标题含关键词、首行写结论、精确标识符原样保留、一条记忆一个小文件。
- 记忆量小于 100 条时，纯全文其实够用；上了量或 query 方式不可控时，直接上 hybrid。

## 总结

语义和全文不是竞品，而是两块互补的召回率拼图。我的默认答案是：**混合检索 + 小回归测试集 + 写入侧规范化**，这个组合比在向量库选型上纠结的产出比高得多。
