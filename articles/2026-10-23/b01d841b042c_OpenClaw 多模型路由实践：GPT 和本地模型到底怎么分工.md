## 背景

跑过一段时间 OpenClaw agent 之后你会发现，一次任务里真正调 LLM 的地方远比想象中多：规划、工具参数生成、中间总结、格式化输出，一个工作流七八次调用很正常。全走 GPT 这类云端模型，成本和延迟都顶不住；全走本地模型，复杂任务的规划质量又明显掉。多模型路由就是为这个场景准备的——但"哪些调用给哪个模型"这件事，多数人一开始都靠拍脑袋。

## 问题

我最初的策略是"规划走 GPT，其余全本地"，结果两周后账单没降多少，本地节点还频繁出错。复盘下来问题不在模型本身，而在路由依据太粗：只按节点名称分，没考虑调用频率、上下文敏感度和失败成本。

## 做法

后来我把流程里所有 LLM 调用点列出来，按三个维度打分：

1. **推理复杂度**：是单轮结构化输出，还是多步规划、代码生成；
2. **上下文敏感度**：是否包含隐私数据、内部文档，能不能出内网；
3. **调用频率**：每天几十次，还是几万次。

结论比较清晰：

- **用 GPT**：多步规划、代码生成、模糊目标的任务拆解，以及低频但高价值的关键决策；
- **用本地模型**（我们用 vLLM 部署的 Qwen）：分类打标、信息抽取、格式化、内部敏感文档的总结——输出短、结构固定、频率高。

然后写进 OpenClaw 的路由配置：

```yaml
router:
  default: local/qwen2.5-14b
  rules:
    - match: skill in ["planner", "codegen"]
      model: gpt-4o
    - match: contains_pii == true
      model: local/qwen2.5-14b
  fallback:
    local_timeout_ms: 4000
    upgrade_to: gpt-4o-mini
```

再加两条硬规则：含 PII 的输入强制走本地；本地超时升级到云端，但每天有次数上限。

## 踩坑点

1. **只看跑分选本地模型**。通用榜单高不等于你的任务够用。我们用自己任务的 30 条样本建了个小评测集，第一版本地模型在抽取任务上差了 15 个点。
2. **本地模型调 MCP 工具时 JSON 参数不稳**，格式错误导致 agent 空转。最后把工具调用节点固定在云端，本地只做非工具节点。
3. **fallback 反噬成本**。本地偶发超时默默升级到 GPT，一周后账单翻倍才被发现。务必对升级次数设阈值和告警。
4. **上下文长度差异**。本地模型上下文短，长文档被静默截断，总结质量下降但没有任何报错。路由前先按 token 数判断，超限直接走云端。
5. **格式敏感节点换模型会导致输出风格漂移**，下游解析挂掉。这类节点锁定单一模型，不做动态切换。

## 可复用建议

- 先全用云端把流程跑通，记录每个节点的调用次数和 token 消耗，再决定哪些下放本地，不要一上来就混合；
- "能不能出内网"作为硬路由条件，其余都是软优化；
- 维护一个 30 条左右的任务级评测集，每次调整路由规则后跑一遍，比看任何榜单都靠谱；
- 路由规则保持少量、可解释。试过用小模型做自动意图路由，判断本身就不稳定，不如静态规则加 fallback。

## 总结

多模型路由的本质不是省钱技巧，而是把不同调用点的风险和质量要求分开对待：云端模型买的是推理能力和兜底，本地模型买的是频率、隐私和可控。先用日志搞清楚自己的调用分布，再动手配路由，比任何最佳实践都有效。
