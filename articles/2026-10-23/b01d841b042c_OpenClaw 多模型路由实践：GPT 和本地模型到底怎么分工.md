## 背景

OpenClaw 这类常驻 agent 的负载其实是混着来的：白天接消息、跑定时摘要、调 MCP 工具、偶尔改点代码。如果所有会话都压到 GPT 这类云端旗舰上，账单和延迟都不好看；反过来全换本地模型，复杂任务的失败率会明显上去。多模型路由就是中间那条路——按任务分模型，而不是按预算一刀切。

## 问题

难的不是"能不能路由"，而是路由粒度和判定标准。粒度太粗（全局一个模型）等于没做；太细（每次调用都动态打分）又引入新的不确定性。我的做法是：先按任务类型静态分层，跑稳之后再考虑动态调整。

## 做法

**1. 给任务分层。**
- P0：多步工具编排、代码改动、长上下文推理 → GPT（旗舰级云端模型）
- P1：常规问答、草稿撰写 → 默认走 GPT，观察后决定是否下沉
- P2：摘要、分类、格式转换、关键词抽取 → 本地模型（Ollama 跑 Qwen 8B 级别基本够用）

**2. 配置两级路由。** 默认 agent 挂主模型并配置 fallback 链（主模型超时或报错才降级）；高频轻任务做成独立 skill，在 skill 层直接固定本地模型。示意如下（字段名以你的 OpenClaw 版本为准）：

```json
{
  "agents": {
    "defaults": { "model": "gpt-4.1", "fallbacks": ["ollama/qwen3:32b"] },
    "skills": {
      "summarizer": { "model": "ollama/qwen3:8b" },
      "classifier": { "model": "ollama/qwen3:8b" }
    }
  }
}
```

**3. 路由要声明式。** 靠 prompt 里写"请用小模型"这类指令不可靠，模型选择应该落在配置里，像代码一样可审查、可回滚。

**4. 用数据收敛。** 跑两周，记录每类任务的 token 消耗、平均延迟、失败/重试次数，再决定哪些 P1 任务也能下沉到本地。

## 踩坑点

- **本地小模型跑工具调用，最常见的问题不是答错，而是 JSON 参数格式漂移、漏字段。** 排查时先看上下文是不是被截断了（8B 模型窗口小），别急着换模型。
- **fallback 链别把弱模型放太前。** 错误会被"优雅地吞掉"，表现为答非所问而不是报错，比直接失败更难查。
- **同一条任务链中途换模型（前半 GPT 规划、后半本地执行）容易上下文断裂**，风格和假设不一致。原则：一次路由，全程一致。
- **本地模型不是免费的。** 长任务会占住推理 worker，阻塞同一实例上的其他会话，并发的活别交给本地。
- **中文任务上小模型的差距比英文更明显**，尤其涉及语气、成语、长句改写。迁移前单独测，别照搬英文社区的结论。

## 可复用建议

1. 建一份 20~50 条真实任务的回归集，每次调整路由规则后跑一遍，比看单次 demo 可靠得多。
2. 先窄后宽：先只把"摘要/分类"迁到本地，稳定一个月再下沉下一类任务。
3. 给本地模型统一参数模板（温度、max tokens、停止符），减少输出格式漂移。
4. 路由规则进版本管理，改动留记录，出问题能快速回退。

## 总结

多模型路由不是省钱开关，而是把任务和模型能力对齐：GPT 花在规划、编排、代码这类"错一次代价高"的事情上；本地模型接住高频、格式稳定、错一次无所谓的活。先静态分层、用数据说话，再考虑动态路由——顺序反了，只会多出一类需要排查的新问题。
