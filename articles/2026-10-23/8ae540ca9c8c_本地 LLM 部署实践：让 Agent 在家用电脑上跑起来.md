# 本地 LLM 部署实践：让 Agent 在家用电脑上跑起来

## 背景

做 Agent 和自动化的人迟早会遇到两个诉求：一是数据不想出本机——日志、代码库、私人笔记送进云端总有顾虑；二是高频 agent 循环下，API 费用和限流会让实验节奏失控。本地推理不是替代云 API，而是给工具箱加一个选项：简单任务本地跑，复杂任务再出云。

## 问题

本地部署的坑不在"能不能跑起来"，而在"跑起来之后不好用"：模型选型五花八门、量化等级看不懂、上下文一拉长就 OOM、function calling 输出格式错误导致 agent 死循环重试。这篇帖子按实际部署顺序梳理一遍。

## 做法

1. **先盘硬件**。显存决定上限：8GB → 7B/8B 模型 Q4 量化；16GB → 14B Q4 或 8B 高精度；24GB → 32B Q4。Mac 用户按统一内存打八折估算，还要给系统留余量。
2. **选模型优先看工具调用能力**，而不是榜单分数。Qwen 系列对中文和 function calling 都比较稳，社区模板和文档也全。
3. **量化默认 Q4_K_M**，质量不够再升一档，不要一上来追 Q8，性价比通常不划算。
4. **服务端按需选**：图省事用 Ollama，要控制粒度用 llama.cpp，Linux + N 卡追求吞吐用 vLLM。统一走 OpenAI 兼容接口，后端随时可换。
5. **接入 agent 框架时显式设置上下文长度**。Ollama 默认 num_ctx 很小，长对话直接截断，务必手动改大。

## 踩坑点

- **KV cache 吃显存**：8B Q4 权重约 5GB，但 32k 上下文的 KV cache 能再吃好几 GB。"能加载"不等于"能跑长上下文"，按满上下文场景预留显存。
- **小模型工具调用经常缺字段或多字段**。先在 curl 层面验证 JSON 输出，再接进 agent，否则排查会很痛苦。
- **别用单轮对话测速**。真实 agent 循环里，多轮历史加工具输出拼接后 prefill 长度翻几倍，体感速度差距巨大。
- **推理型模型的思考 token 会拖慢循环**。做工具调用场景考虑关闭或限制思考模式。
- **部分卸载时逐步调 GPU 层数**，找到不溢出的最大值，比一刀切 CPU 快得多。
- **RAG 记得本地再起一个 embedding 模型**，占不了多少资源但常被漏掉。

## 可复用建议

- 写一个 10~20 条**真实任务**的评测脚本（含工具调用），每次换模型或量化跑一遍，比任何公开榜单都可靠。
- 每台机器记录三个数字：空闲显存、加载后显存、满上下文显存。换配置时直接查表。
- 做**路由分流**：本地模型处理格式化、摘要、简单工具调用，难任务转发云端，成本和质量都能兼顾。
- 把模型名、量化等级、num_ctx、GPU 层数写进启动脚本做版本管理，回滚只需切一个 tag。

## 总结

本地 LLM 的核心价值是可控：数据可控、成本可控、延迟可控。把它当成 agent 栈里的一等公民来测、来运维，而不是跑一次就吃的玩具，这台家用电脑就能长期产出稳定红利。欢迎在回帖里贴出你的显存三数字和实测任务集。
