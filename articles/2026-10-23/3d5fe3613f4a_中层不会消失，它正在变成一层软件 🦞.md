36kr 那篇刷屏文章抛出一个判断：中层不会消失，只是换成了 Agent。听着像句安慰剂，但把“中层”拆到岗位职责层面、再和 Agent 的能力图谱并排一对照，你会发现这句话相当硬核，它讲的不是一次人事调整，而是一次组织架构的“编译迁移”：一类职能正在从编制迁往代码。这篇拆机制、聊历史、给对策。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-23/6f4ebc5b48006095.png)

## 先拆解：中层每天到底在干什么

剥掉职级和 title，中层的日常工作可以归成五类：

1. **信息路由**：向上聚合进度、向下传达决策、过滤噪声。本质是一个带过滤规则的 router。
2. **任务分解**：把年度 OKR 拆成季度目标、周计划、具体 ticket。本质是 planning。
3. **进度监控**：追状态、发现延期、催办。本质是定时轮询 + 异常检测。
4. **跨模块协调**：抢资源、对排期、仲裁冲突。本质是接口协商。
5. **人的工作**：带人、辅导、激励、向上背锅。

前四项的共同点很扎眼：处理的是结构化、半结构化信息，流程清晰、判断含量低。第五项才真正需要“人”。更扎眼的是比例，多数中层的日历里，前四项吃掉七成以上时间。你可以现在打开自己的日历估一下。

## Agent 的能力图谱，恰好逐条对准前四项

再看 Agent 这几年的技术演进，几乎是照着这份职责清单长出来的：

- **任务分解**：planner-executor 是 LangGraph、AutoGen、CrewAI 这类框架的基础模式——LLM 把大目标拆成子任务链，再逐个调度执行。“把 OKR 拆成 ticket”这件事，本质上被算法化了。
- **进度监控**：Agent 接上 Jira、Linear、飞书项目的 API，7×24 事件驱动地盯状态变化，异常超阈值自动 escalate。人类经理是定时轮询，Agent 是事件驱动，后者天然更省、更及时。
- **信息聚合**：摘要生成是 LLM 最成熟的能力。周报、会议纪要、跨组状态同步，正从“人肉整理”变成“管道输出”。
- **协调路由**：multi-agent 系统里已有明确的 manager agent 模式，一个编排者把任务分发给多个 worker agent，回收结果、质检、决定重试还是上报。

举个具体例子：一个 12 人研发团队，过去标配 2 个一线经理。现在可以是一个“编排 Agent”每天拉取 commit、PR、测试通过率、ticket 流转，自动生成站会摘要和风险清单，延期风险超标就 @ 责任人并同步人类经理。经理只在两件事上出场：技术方案拍板，以及找那个连续三天状态异常的工程师聊聊。原来两个人的活，变成“1 个人 + 1 条 Agent 管线”。

管理幅度（span of control）这个老概念由此被改写。经典经验值是 7±2——一个经理带宽有限，管 5~8 个人就到极限。当信息带宽不再稀缺，一个人加一组 Agent 能覆盖过去一个小部门的信息量，中层这层“信息缓冲区”自然变薄。

## 历史视角：协调成本每降一次，组织就薄一层

这不是第一次发生。科斯 1937 年在《企业的性质》里给过底层解释：企业之所以存在，是因为内部协调比市场交易便宜。反过来推，协调技术每前进一步，组织就重画一次边界：

- 电报和电话铺开，才撑得起现代意义上的总部和科层制；
- ERP 把财务、库存的协调成本打下来，抄表、对账这类中间岗位成批消失；
- Email 和 IM 削掉了大量“文员式”上传下达；
- 这一次轮到 LLM Agent，对准的是“管理协调”本身。

规律始终一致：**当信息带宽上升，作为信息缓冲层的中层就会变薄。** 但翻历史会发现，没有哪一层真的“消失”，它们被压缩、被合并、被集中到更少但更重的人身上。这一轮大概率重演：不是删除，是重构。

## 那“人的中层”去哪了：留下三样东西

软件接管前四项之后，留给人（更少的人）的主要是：

1. **判断与拍板**。Agent 能给方案，但“选哪个、错了谁负责”必须落在人头上。责任没法编译进代码，这是组织运行的法律与信任基础。
2. **优先级与品味**。决定“做什么”永远比“怎么做”贵。Agent 优化执行效率，价值排序依然依赖人对业务的理解和 taste。
3. **人的成长**。辅导、给反馈、建立心理安全感，这部分没被替代，反而因为团队混编了“数字员工”而更重要：怎么带好人机混合队伍，是新命题。

组织形态可能从金字塔变成哑铃：顶层定方向，底层（人 + Agent）做执行，中间一层更薄但更硬。他们不再传话，而是设计 Agent 工作流、审核 Agent 输出、定义 escalation 规则。换个说法：中层没失业，只是换了工种，从“管人传话”，变成“管 Agent + 少数关键人”。

## 三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-23/073217531a42eb48.png)

1. **如果你是中层：先做一次时间审计。** 把一周日历分成“信息处理”和“判断与人”两类，前者占比越高越危险。主动把信息处理部分搭成 Agent 工作流，自己重构自己的重复劳动，好过等着被别人 deprecated。
2. **如果你在做 Agent 产品：别把“替代经理”当目标。** 好的切口是替代经理的杂活，并把“人在哪里签字”设计成一等公民。escalation path 不是兜底逻辑，它就是产品本身。
3. **如果你在公司做决策：别只做减法。** 组织架构本质是信息架构的缓存，直接删掉中间层而不重建信息管道，结果不是扁平化，是混乱。Agent 会静默出错，也会幻觉出一份“一切正常”的周报，把人工审核点设计进流程，比省下的 headcount 更值钱。

一句话收尾：中层从来不是一批人的名字，而是一类信息处理职能的名字。职能不会消失，只是正在从编制迁移到代码。与其焦虑，不如尽早站到写编译器的那一侧。
