## 背景

在 OpenClaw 的插件和 MCP 工具链里，LLM 输出经常被当作结构化数据消费：Agent 决策要 JSON，工具调用参数要 JSON，插件之间传状态也要 JSON。但模型不是序列化器。同一段提示词，今天输出 ```` ```json ```` 围栏代码块，明天输出裸 JSON，后天在前后各加一句说明文字，推理模型还会夹带思考段。解析逻辑不做防御，迟早会在生产里炸一次。

## 问题

最常见的写法：

```python
data = json.loads(response)
```

它在四类场景下直接抛异常：

1. **Markdown 围栏包裹**：```` ```json { ... } ``` ````；
2. **前后缀文本**：「解析结果如下：{...}，如有问题请告知」；
3. **思考段混入**：推理模型把推理过程和答案粘在一起输出；
4. **手写体 JSON**：trailing comma、单引号、字符串里未转义的换行。

这四类问题会在同一会话内随机出现——温度、上下文长度、模型版本都会影响输出格式，所以不能靠「上次没出事」来赌。

## 做法

我的处理链路分四步，从便宜到贵：

**第一步：剥离围栏。**

```python
FENCE_RE = re.compile(r"```(?:json)?\s*\n?(.*?)```", re.S)

def strip_fence(text: str) -> str:
    m = FENCE_RE.search(text)
    return m.group(1).strip() if m else text.strip()
```

**第二步：括号平衡截取。** 去围栏后扫描第一个 `{` 或 `[`，逐字符向后计数配对，截出最外层对象。这一步能处理「前缀说明 + JSON + 后缀废话」，比正则 `{.*}` 可靠——后者遇到嵌套或字符串内含大括号时会截错。注意扫描时要跳过字符串字面量内部的花括号和引号。

**第三步：宽松修复。** `json.loads` 失败后，再做字符级修复：去掉 trailing comma、替换智能引号、转义裸控制字符。逐字符状态机比全局 `replace` 安全，别急着上重型 JSON5 解析库。

**第四步：Schema 校验 + 带反馈重试。** 解析成功不等于数据可用。用 pydantic 或手写校验确认字段齐全；校验失败时，把具体错误拼回提示词重试一次，例如「你上次输出的 JSON 缺少 x 字段，请只输出修正后的 JSON」。带错误反馈的重试成功率远高于盲目重发。

## 踩坑点

- 括号平衡截取不处理字符串字面量，遇到 JSON 里带示例文本就截断错位——这是最隐蔽的一类 bug；
- 修单引号时值里的合法单引号（如 `it's`）不能动，全局替换会改坏数据；
- 重试不要超过两次。第二次还失败说明提示词本身有问题，去改 prompt，而不是堆重试次数；
- 流式输出别边收边解析，等生成结束后再走完整链路，半截 JSON 没有解析价值。

## 可复用建议

把这套逻辑抽成一个 `parse_llm_json(text, schema)` 工具函数，放进插件公共库，所有 Agent 和 MCP 工具共用，不要每个人各写一份正则。日志里保留原始输出和每一步的中间结果，出问题时能一眼定位是哪一步截错的。另外记住优先级：结构化输出接口（function calling / JSON mode）是第一选择，让模型侧约束格式；防御性解析是兜底，不是替代品。

## 总结

LLM 输出解析的本质，是对一个不确定的数据源做协议处理。围栏剥离 → 平衡截取 → 宽松修复 → 校验重试，四级防御覆盖绝大多数脏输出。它不优雅，但稳定；沉淀成公共函数之后，就是整个插件体系的地基之一。
