## 背景

团队每天需要一个"昨天发生了什么"的日报。数据散在三处：服务日志、git 提交记录、CI 与告警。以前的做法是有人翻聊天记录和后台手写一份，问题很典型：漏项、口径不一、占用人力，且隔几天换人写格式就变。

## 问题

最初的失败尝试很直接：把原始日志整个丢给 Agent，让它总结一份日报。结果两个——上下文被塞爆；重要事件被海量噪音平均掉，模型还会"脑补"没发生的事。日报对事实性要求极高，格式漂移也无法接受：今天多一个章节，明天标题换说法，下游没法对齐。

核心结论：**不要把结构化的压力交给模型，结构化应该发生在数据进入模型之前。**

## 做法

流水线拆成四层，每层独立可测、可重跑：

**1. 采集层（脚本，无模型）**
用 shell/Python 按 cron 拉取三类源：应用日志（只取关键级别）、git log（按日期过滤）、CI 结果。各自落成 JSON Lines 文件，放进固定目录 `daily/2025-06-XX/`。这一步只做抽取和过滤，不做"理解"。

**2. 归一化层（脚本）**
每个源一个小解析器，统一成相同 schema：`source / type / ts / level / summary / metrics`。做三件事：时间戳统一到一个时区、去重、按规则丢弃低价值噪音（比如重复的 health check）。产出是"当天的干净事实清单"，通常几百行以内。

**3. 生成层（OpenClaw 定时任务）**
固定时间触发 agent 会话，输入只有两样：归一化后的 JSON + workspace 里固定的输出模板（明确章节、每节条数上限、"数据之外一律写 N/A，禁止推测"）。需要补充指标时才通过 MCP 工具去查，而不是预灌一堆原始数据。temperature 调低，模型只负责措辞和归纳，不负责产生事实。

**4. 校验与分发层（脚本 + 插件）**
Agent 输出先过一遍 schema 校验（jq/Python 检查章节名、字段、日期），失败就带着错误信息重试，最多两次；仍失败则降级输出"原始清单版"，绝不静默跳过。通过后经渠道插件推到群里，同时把 markdown 落盘到一个 git 仓库留档。

## 踩坑点

- **时区**：日志是 UTC，读者按本地时间理解，"昨天"的边界会错。必须在归一化层统一时区，别指望模型算对。
- **格式漂移**：即使 prompt 写死模板，隔几天还是会变。schema 校验 + 失败重试才是兜底，prompt 只能降低概率。
- **静默失败**：cron 没跑、LLM 调用超时，日报没发出去没人发现。加一个心跳：固定时间没收到日报就告警。
- **一次接太多源**：第一版只接了 git log，跑稳两周后再逐个加日志、CI。每个源的解析器都要单独测过。

## 可复用建议

- 结构化前置：进模型前先聚合过滤，token 省一个数量级，准确率反而上升。
- 各层解耦：每层产物落盘，坏了可以单独重跑，不必重跑全链路。
- 报告进 git：历史可 diff、可回溯，比翻聊天记录靠谱得多。
- 模型定位成"翻译和排版"，事实永远来自脚本产出的数据。

## 总结

这条流水线的本质是分工：脚本负责事实，Agent 负责表达，校验负责兜底。搭建成本大概一个下午，之后每天的边际成本接近零。建议从单一数据源、最简单的模板起步，先让链路跑通，再逐步加源——稳定比丰富更重要。
