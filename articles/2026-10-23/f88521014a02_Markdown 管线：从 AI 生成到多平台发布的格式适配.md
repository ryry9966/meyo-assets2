## 背景

用 Agent 产出内容后，最大的摩擦往往不在生成端，而在发布端。同一篇 Markdown，公众号、知乎、掘金、自建博客的渲染规则各不相同：frontmatter 要不要、脚注支不支持、图片能不能外链。逐平台手工复制粘贴，慢且容易漏，还没法在 CI 里兜底。

## 问题

Markdown 看似统一，实际是“方言集合”。几个我实际踩过的坑：

- 公众号不认外部 `<a>` 链接（公众号域除外），脚注得手工挪到文末；
- 知乎会替换外站图床的图片，必须走它自己的上传通道；
- 掘金对部分行内 HTML 直接吞掉；
- 自建博客走 MDX，正文里出现 `{` 和裸 `<` 会触发 JSX 解析报错。

本质问题：AI 生成的是“理想 Markdown"，而各平台消费的是“方言子集”。中间缺一层确定性的转换。

## 做法

我把管线拆成四层，核心思想是“一次生成，多处转换"：

1. **归一化层**：所有 AI 输出先过 remark 转成统一 AST，跑 remark-lint 规则（标题层级连续、列表缩进一致、图片必有 alt）。
2. **适配层（Adapter）**：每个平台一个纯函数转换器，输入 AST，输出该平台可接受的 Markdown 或 HTML。比如公众号 adapter：剥离 frontmatter、脚注转为文末编号段落、外链降级为“链接见文末”。
3. **渲染层**：公众号走 HTML + 行内样式（编辑器不吃 class）；博客走原有静态站构建；掘金/知乎直接喂转换后的 Markdown。
4. **校验层**：dry-run 渲染成 HTML 后跑快照测试，链接全量检查，CI 失败即拦截发布。

## 踩坑点

- **图片是最痛的一环**。别指望统一图床通吃，公众号素材接口必须单独上传并回写 URL。这步要做成幂等任务，否则重跑会在素材库里堆重复图。
- 行内样式渲染建议用 shiki 输出 token 级结构，再映射成公众号能接受的 `<span style>`；直接贴 class 全部失效。
- 数学公式别硬转，按目标平台能力二选一：渲染成图片，或降级为代码块。
- MDX 的坑：归一化层加一步花括号转义，比发布后修文省心得多。
- 缓存：改了 adapter 忘了失效缓存，发出去的是旧渲染结果。renderer 配置必须纳入缓存 key。

## 可复用建议

- **单一事实源**：原始 Markdown + 元数据只存一份，所有平台产物都是派生物，可随时重建。
- 转换器保持纯函数：AST 进，AST/HTML 出，不碰网络和文件系统，单测好写。
- 每个 adapter 配一组最小样本做快照测试，平台规则变了先挂 CI 再改代码。
- 图片上传拆成独立任务队列，带内容去重。
- 把“平台能力”配置化（支持脚注？支持外链？图片白名单？），新增平台只写配置加少量转换函数。

## 总结

多平台发布的复杂度不在写作，在适配。用统一 AST 做中枢、平台 adapter 做扇出、CI 校验做兜底，AI 生成的 Markdown 就能一次成型、多处分发。这套管线代码量不大，一个下午能搭出骨架，之后省下的每一次手工排版，都是复利。
