## 背景

社区运营里最耗时的不是写作，而是"每周都得写"。版本更新、踩坑记录、精选讨论散落在 git log、issue 区和群聊里，人工汇总一遍至少两小时。我的目标是把"找素材、整理、成稿"自动化，但保留人工审校这一环——机器人负责把草稿端到桌上，发布键始终在人手里。

## 整体架构

流水线分五段，彼此解耦：

```
采集(MCP工具) → 加工(Agent起草) → 审校(人工门禁) → 发布(独立进程) → 回流(数据统计)
```

几个关键设计决策：

- 每类数据源封装成独立的薄 MCP server，只返回结构化摘要，不把原始日志丢给模型；
- 草稿环节由 OpenClaw 的 Agent 承担，落库到本地 SQLite，状态机为 `draft → approved → published / rejected`；
- 发布器是独立进程，只消费 approved 状态的记录，带速率限制和指数退避重试；
- cron 统一触发，配文件锁防重入，另有独立心跳任务上报存活。

## 实施步骤

1. **数据源收敛**：git log、issue、RSS 各写一个 MCP 工具，输出统一为 `{id, url, title, summary, date}`，summary 在工具侧生成，不进模型。
2. **约束草稿格式**：Agent 输出用 JSON Schema 硬约束，字段包括标题、正文、标签、引用来源 id 列表。解析失败直接打回重试，上限三次。
3. **去重**：发布前先算内容哈希，再算与近 30 天已发帖的 embedding 相似度，超阈值进 rejected 队列。
4. **审校入口**：一个简单 CLI 列出 draft 队列，通过 / 驳回 / 编辑三选一，编辑后回写。
5. **发布与回流**：发布成功记录 post_id，后续把阅读、回复数据拉回来，作为下一轮选题的输入。

## 踩坑实录

- **幻觉链接**。让模型自己"写"出处链接，十次里必有一次编出不存在的 URL。改法：URL 一律由工具传入，模型只负责组装和转述，正文里每个链接都必须能对应到来源 id。
- **重复发帖**。仅靠内容哈希去重没用，同一件事换个说法照样通过。补了 embedding 相似度门槛（0.85）之后才算稳住。
- **上下文爆炸**。一开始把整月 git log 全塞进上下文，token 翻倍且草稿质量下降。改为在工具侧按 commit 规模和关键词预过滤，每次只给模型 20 条以内的候选。
- **定时任务双跑**。systemd timer 和 crontab 叠加配置，同一时段触发两次，发出去两条一样的帖子。之后统一入口 + 锁文件 + 幂等键，重跑只覆盖不追加。
- **Markdown 炸版**。草稿里的嵌套代码围栏和未转义特殊字符，在社区渲染器上直接破版。生成后加一道渲染校验，失败的草稿标记格式问题退回。
- **静默失败**。最危险的坑：任务挂了两周没人发现。加心跳上报和"连续 N 次空产出"告警后才解决。

## 可复用建议

1. 先审后发，流水线稳定跑两周再考虑放开自动发布，放开也只针对低风险内容类型。
2. 事实采集与文案写作拆成两步，模型不做事实的"发现者"，只做"整理者"。
3. 机器人用独立账号、最小权限 token，出问题可随时吊销。
4. 所有环节落日志，宁可日志多，不可状态黑盒。

## 总结

这套东西代码量不大，真正的成本都在边界情况：去重、失败恢复、格式兼容。核心经验就一条——把自动化用在重复劳动上，把判断留给人。机器人负责让草稿出现在你面前，点不点头，还是你的事。
