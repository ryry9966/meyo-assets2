## 背景

社区每周要发一篇「本周动态」：整理仓库里合并的 PR、热门讨论、近期活动。这件事人工做了三个多月，流程固定但耗时，于是我用 OpenClaw 的 agent + MCP 工具链搭了个半自动发帖机器人。

先说清定位：不是全自动灌水，而是把「抓数据、整素材、排版、定时发布」这些机械环节交给机器人，人只做最后的内容把关。

## 核心问题

拆下来是四件事：

1. 数据分散在论坛 API 和 Git 记录里，需要统一成 agent 可调用的工具；
2. LLM 输出有风格漂移，格式不保证，不能全靠 prompt 约束；
3. 发布要可靠：重试不能造成重复帖，token 权限要最小化，还得躲开社区频控；
4. 链路长，出错时要能快速定位是哪一环。

## 架构：agent 只写草稿，不碰发布

链路是：定时器 → 数据采集 MCP 工具（`list_recent_topics` / `get_repo_activity`）→ agent 生成草稿 → 规则 lint → 人工审核（IM 卡片确认/驳回）→ 独立发布服务 → 状态库（SQLite 记内容 hash 和帖子 ID）。

两个关键决策：

- **生成与发布解耦。** agent 只产出 Markdown 草稿和结构化元数据，API 调用由独立小服务完成。token 不进 agent 上下文，agent 再失控也发不出请求。
- **写操作全部带幂等键。** 以「日期 + 内容 hash」为键，发布前先查当天是否已存在同 hash 的帖子。

## 落地步骤

1. 先写 MCP server，把数据源封装成两个只读工具，服务端做分页和摘要，避免撑爆上下文；
2. agent 用结构化输出套严格模板（标题字数、标签、frontmatter），不产自由文本；
3. 写几十行的 lint 脚本：校验标题长度、外链数、禁用词、论坛渲染器兼容性；
4. 审核做成 IM 卡片，确认才发布，驳回时附一句修改意见回传给 agent；
5. 发布服务统一指数退避重试，日发布上限硬编码为 1。

## 踩坑实录

- **渲染差异。** 本地预览一切正常，发到论坛后表格被 sanitizer 吃掉、代码围栏语言标签触发高亮报错。后来补了一层按论坛真实渲染器做的预渲染校验，不通过就打回。
- **重试导致重复发帖。** 首日就撞上：发布接口超时触发重试，结果第一次其实成功了，同一天出现两篇一样的帖子。加幂等键 + 发布前查重才堵住。
- **风格漂移。** 跑两周后草稿开始出现感叹号和营销腔。结论很直接：风格约束别指望 prompt 长期生效，要落到代码层 lint，命中规则直接打回重写。
- **时区与频控。** cron 默认 UTC，帖子凌晨三点发出；修完时区，重试风暴又触发社区反刷屏，给重试加随机抖动和次数上限才稳住。
- **工具返回过大。** 一次拉全量讨论记录直接把上下文撑爆，改成服务端分页、只回传摘要字段。

## 可复用建议

- 「agent 生成、普通代码发布」这条分界线，几乎所有自动化场景都适用；
- 审核从全量人工开始，跑稳后按类别逐步放宽，别一上来就全自动；
- 约束写成可执行校验，prompt 只负责生成，不负责兜底；
- 记录 agent 每一步用了什么工具、拿到什么数据，出问题能回放。

## 总结

机器人现在每周稳定出稿，人工只花几分钟审核。最大的收获不是省下的时间，而是验证了一条路径：让 agent 做它擅长的整理与起草，把确定性要求——权限、幂等、频控、格式——交给传统工程手段。发帖机器人如此，其他自动化同理。
