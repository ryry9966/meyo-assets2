最近 36kr 那句“中层不会消失，只是换成了 Agent”刷了不少人的屏。乍一听像递给焦虑管理者的安慰剂，但把组织学和技术逻辑摊开看，这句话其实相当精确：被替代的不是“中层的职能”，而是“承担职能的人肉载体”。这篇拆三件事——中层到底在生产什么、Agent 为什么恰好长在这个生态位上，以及哪些东西它接不住。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-23/18c3bf15e2070bea.png)

## 一、先搞清楚：中层到底在“生产”什么

很多人对中层的印象停留在“传话筒”和“周报主编”，但正经拆开，中层产出的核心是四类中间产物：

1. **任务分解**：把老板一句“提升留存”拆成可执行的 WBS（工作分解结构），本质是把模糊目标编译成任务树；
2. **信息压缩与翻译**：向上做摘要（30 页数据 → 3 句结论），向下做展开（一句战略 → 一季度排期），解决的是人的注意力带宽问题；
3. **进度协调**：跨部门依赖、资源冲突、优先级仲裁，天天在跑的其实是分布式系统的调度逻辑；
4. **质量监督与兜底**：review 产出、拦截风险，出事时有一个“可追责的人”。

为什么要分层？一个经典算式：n 个人两两沟通的通道数是 n(n−1)/2，10 人团队就是 45 条通道。经典管理学的管理幅度（span of control）经验值是 5~9 人，分层本质上是把沟通复杂度从 O(n²) 砍到接近 O(n·log n) 的工程手段。换句话说，中层就是组织的“中间路由层”。

## 二、为什么 Agent 恰好长在中层的生态位上

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-23/14f1e44f10b8cb14.png)

Agent 的定义不复杂：大模型 + 记忆 + 工具调用 + 自主规划循环，能多步执行任务。把它和中层职能逐项对齐，重合度高得吓人：

- **任务分解 → Planner**：主流 Agent 框架的 orchestrator-worker 模式，就是“总指挥 Agent 拆任务、多个执行 Agent 干活”，一套现成的任务树编译器；
- **信息压缩 → 总结**：LLM 的看家本领，会议纪要、周报汇总、跨团队信息拉通，是最先被吃掉的场景；
- **进度协调 → 调度**：Agent 直连 Jira、飞书等系统的 API，自动催办、检测依赖阻塞、重排优先级，7×24 不休息；
- **质量监督 → LLM-as-a-judge**：用一个 Agent review 另一个 Agent 的产出，多 Agent 互评已经是常见架构。

经济学层面还有个更底层的解释：科斯在 1937 年《企业的性质》里说，企业存在的原因是内部协调成本低于市场交易成本，而管理层级的层数，本质由协调成本决定。麦肯锡 2023 年的报告估计，用现有技术可自动化的工作活动约占员工总时长的 60%~70%，其中“信息收集、汇总、协调”首当其冲。当 Agent 把内部协调成本打到地板价，组织这棵树的中间分叉自然会被剪掉——但“协调”这个功能不会消失，它只是搬进了软件。

## 三、历史会押韵：职能不灭，只是换了载体

“中间层消失”的戏码不是第一次上演：

- **1970 年代以前**，computer 是一份人肉职业——NASA 靠一群计算员手算弹道。电子计算机出现后，“计算职能”没消失，只是从人变成了机器；
- **1990 年代**，ERP（SAP 那一代系统）把大量中层“信息中转、报表汇总”的流程固化进软件。结果中层没有集体消失，而是从“搬运数据”转向“分析例外”；
- 规律：技术消灭的是**岗位**，不是**职能**。职能总会迁移到成本更低的载体上，Agent 只是最新那个载体。

## 四、Agent 接不住的三件事

把话说全，有三件事短期内很难编译进 Agent：

1. **问责**：Agent 把排期搞错了，谁背锅？组织需要一条能追溯到“人”的信任链与责任链，这是法律和信任体系的刚需，不是技术问题；
2. **非标判断**：目标互相冲突、资源要靠关系协调、优先级需要“对人下菜”——这些依赖 face-to-face 攒下的信任存量，LLM 拿不到完整上下文；
3. **带人**：激励、辅导、招人、传文化，人对人的信息通道没法被压缩成一个 prompt。

还有一个容易被忽略的风险：Agent 在协调场景里的 hallucination 代价极高，一条编造的“对方团队已确认”可能直接污染整条决策链。所以在可预见的架构里，human-in-the-loop 不是临时方案，而是设计约束。一句工程师式总结：**Agent 是放大器，放大强流程，也放大烂流程——Garbage in, garbage out 的定律在组织里同样生效。**

## 五、给职场人的三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-23/6961c76267694062.png)

1. **把工作拆成两堆**：一堆是“可被编排的”（汇总、跟进、格式化输出），一堆是“判断与信任”（拍板、斡旋、兜底）。主动把第一堆写成清晰的流程文档或 workflow——你不写，将来 Agent 替你写的那个版本，就是你的替代说明书；
2. **学“编排思维”，不必死磕代码**：能把一个业务流程讲清楚成“节点 + 条件 + 异常分支”，比多背几个 prompt 模板值钱。这个能力在 BPMN 时代叫流程建模，在 Agent 时代叫 orchestrator 设计；
3. **攒判断力资产**：行业 know-how、跨部门信任、疑难 case 的处理记录，是 Agent 最难编译的部分。微软 2024 年《工作趋势指数》显示约三分之二的领导者不愿雇用不会用 AI 的候选人——但注意，“会用 AI”的前提是你有值得被放大的判断力。

最后回应标题：中层不会消失，消失的是“只做信息搬运”的那部分中层。职能被编译进 Agent，人则被推向链条两端——要么上去做判断，要么沉下去做执行。路由层永远是需要的，问题只是：它跑在人的脑子里，还是跑在系统里。
