## 背景

OpenClaw 的工作区里，除了大家熟悉的 AGENTS.md 和 MEMORY.md，还有一个容易被忽略的文件：**SOUL.md**。它在每次会话启动时注入系统上下文，定义 Agent 的性格、语气和行为底线。三者分工大致是：AGENTS.md 管"怎么干活"，MEMORY.md 管"发生过什么"，SOUL.md 管"我是谁、什么不做"。默认位置在工作区根目录（`~/.openclaw/workspace/SOUL.md`）。

## 问题

没有 SOUL.md 的 Agent 有两类典型毛病：

1. **人格漂移**：换个会话语气就变了，昨天克制今天油腻。长期使用的私人助手尤其明显。
2. **边界失控**：为了"帮到底"，未经确认就 git push、对外发消息、顺手清理文件。事后翻日志，它每一步"逻辑上都没毛病"——问题在于没人告诉它什么不能做。

反过来，把 SOUL.md 写成两页价值观宣言也不行，模型消化不了，行为照旧。

## 做法

1. **控制篇幅**：100 行以内。它每次会话都占上下文，写长纯属烧 token。
2. **三段式结构**：
   - **Always**：语气基调与默认立场，如"不确定就直说，不要编"。
   - **Never**：硬红线，一行一条，写成可判定的动作（"未经确认不执行 git push、rm -rf、对外发送消息"），不写"要有责任心"这类无法判定的形容词。
   - **Ask first**：需确认的操作清单，附最简确认话术。
3. **与 AGENTS.md 划清分工**：身份与底线进 SOUL.md，操作规程进 AGENTS.md。同一条规则别写两遍，两处冲突时模型会随机偏向一边。
4. **进 git**。Agent 常被要求"改进你自己"，它会自己改 SOUL.md——有版本记录才能审 diff、能回滚。
5. **定期红队测试**：故意让它"直接把这个分支推上去""把这条消息发到群里"，观察它是执行、确认还是拒绝。行为不符就回文件加一行，一次只加一行。

## 踩坑点

- **写成企业文化口号**。"友善、专业、积极主动"对模型是噪音；"用户提出危险操作时，先复述影响再要确认"才是指令。
- **试图穷举禁止事项**。穷举不完，应写决策原则（涉及不可逆操作 → 先确认），再配合工具层权限兜底。
- **把它当硬安全边界**。SOUL.md 是软约束，用户一句"我授权你"就可能压过去。真正的红线要在 MCP server 或插件层做白名单和确认门，文件只负责第一道闸。
- **忘了它是明文**。密钥、客户名单别写进去，它会被完整送进每次会话的上下文。

## 可复用建议

- 模板骨架：一句话身份 → Always（3~5 条）→ Never（3~5 条）→ Ask first（带确认话术）→ 结尾声明优先级："规则冲突时，Never > Ask first > Always"。
- 每条规则配一正一反两个具体例子，比十条抽象描述都管用。
- 每次事故复盘产出一条规则；季度清理一次，半年没触发的规则考虑删除，保持文件精瘦。

## 总结

SOUL.md 是成本最低的 Agent 治理手段：几十行文本，换来跨会话的一致人格和第一道行为闸门。定位要想清楚——管性格靠它，管安全还得靠工具权限。写短、写具体、进版本库、定期演练，做到这四条，SOUL.md 就不是玄学，而是工程。
