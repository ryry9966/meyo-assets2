## 背景

我日常用 OpenClaw 做家庭自动化：读本地文件、操作日历、调几个自建的 MCP 工具。这类任务的特点是调用频繁、上下文里全是私人数据。全走云端 API 有两个不爽：隐私上过不去；成本上，agent 一轮任务动辄几十次工具调用，账单涨得比纯聊天快得多。于是花了两个周末，把模型搬到自己桌上，这篇是过程记录。

## 问题

先泼冷水：Agent 负载和聊天负载不是一回事。聊天是一次性短上下文；agent 一轮任务要几十次调用，每次都带着工具 schema 和历史记录，对函数调用的稳定性要求极高。而家用硬件就那点余量：12GB 的 3060、24GB 的 4090，或者 Mac 的统一内存。核心问题只有一个——**在显存预算内能塞下的最大模型，它的 tool calling 靠不靠谱？**

## 做法

1. **盘点预算**：显存 ≈ 模型权重 + KV cache + 运行开销。Q4 量化的 8B 约占 5GB，32B 约占 20GB，KV cache 随上下文长度线性增长，别漏算。
2. **选运行时**：Ollama 上手最快，llama.cpp 控制粒度细，vLLM 吞吐好但显存门槛高。三者都提供 OpenAI 兼容接口，接入成本基本一样。
3. **选模型**：8-12GB 显存用 7-8B Q4；12-16GB 用 14B；24GB 或 32GB+ 的 Mac 可以上 32B Q4 或 MoE 结构（如 30B-A3B 这类激活参数小的，速度快）。
4. **接入 OpenClaw**：模型配置指向 `localhost` 的 base_url，然后用一个**真实的 MCP 工具**做冒烟测试——注意是真实工具，不是 echo。
5. **混合路由**：本地跑常规任务，复杂推理失败时回落云端。别追求全本地。

## 踩坑点

- **Ollama 默认上下文很小**（2k/4k），agent 跑几轮历史就被静默截断，表现为"模型突然失忆"。必须显式设置 `num_ctx`。
- **Q4 量化聊天没问题，多步推理会明显变笨**。8B 级别建议 Q5/Q6，或者干脆升一档模型。
- 部分模型的 function calling 依赖特定 chat template，换运行时或量化版本后可能坏掉且不报错，只会输出格式错误的参数。
- 128k 上下文在 24GB 卡上是奢侈品：KV cache 会把权重挤出去。agent 场景 16k-32k 够用就别贪。
- **别用"你好"测性能**。用你真实的 agent 循环测——多轮加工具调用的端到端延迟才是体感。

## 可复用建议

- 从自己的自动化流程里抽 10-20 个真实任务做本地评测集，换模型时跑一遍，比看榜单有用得多。
- 显存预算公式记下来：权重 + (上下文长度 × KV 系数) + 2GB 余量，买卡或选模型前先算一遍。
- Mac 统一内存被低估：64GB 的机器跑 32B 很从容，适合不想折腾的人。
- 固定一个运行时，模型用带版本的 tag 管理，别盲目追新。

## 总结

本地部署不是"替代云端"，而是一个路由问题：8B-32B 的模型能覆盖日常 agent 工作中相当大比例的常规操作，隐私数据留在家里，重活留给云。把预算算清楚、把工具调用测扎实，家用电脑跑大模型这件事，已经从玩具变成了可用的工程选项。
