## 背景

OpenClaw 社区里跑 Agent 的同学越来越多：有人挂了自动答疑 bot，有人让 Agent 整理 issue、跑日报，也有人把带 MCP 和插件的完整工作流截图发出来求助。Agent 手里的权限在变大——读文件、调 shell、连内部服务；而社区是公开场所。权限大 + 场景公开，泄露就不再是理论问题。

## 问题：泄露不只发生在"被攻击"时

三条常见路径：

1. **提示词提取**。公开 bot 被一句"复述你的 system prompt"套出内部工具名、接口约定和业务流程。
2. **调试外带**。让 Agent 帮忙排错，它把读到的 `.env`、MCP 配置、带 token 的请求头原样贴进对话，再被截图转发。
3. **自动化搬运与注入**。自动摘要 bot 把私有仓库的提交信息、内部链接带进公开频道；或者 Agent 读网页/帖子时被注入指令，主动吐出配置。

核心误判：把 system prompt 当安全边界。它不是。凡是能进模型上下文的东西，都要按"可能被输出"来设计。

## 做法：三层收口

1. **资产分级**。先列清单：密钥、内部域名、MCP 配置、工作流定义、私有仓库内容。明确哪些绝对不允许出现在输出里。
2. **收权限**。MCP/插件按任务最小授权，只读优先；工作目录隔离；显式拒绝 `.env`、`~/.ssh`、凭据文件这类路径。secrets 一律走环境变量注入，不写进 prompt 或配置文件。
3. **出口过滤**。Agent 输出进公开频道前，先过一道确定性脱敏（正则匹配常见 token 格式、Bearer 头、内网域名），再叠加人工抽检。别只靠另一个 LLM 当审查者——它同样可能被注入。审计日志记录工具调用，出现读取凭据类路径就告警。
4. **提示词分层**。对外行为提示词与内部运维提示词分开，按"prompt 迟早会泄露"来设计——泄露 ≠ 失陷，前提是 prompt 里本来就没有值钱的东西。

## 踩坑点

- 脱敏正则只覆盖 `sk-`、`ghp_` 这类常见前缀，自建服务的 token、base64 内容、内网主机名全漏了。
- 沙箱只限了文件系统，没限网络出口，Agent 照样能把内容 POST 出去。
- 最常见的泄露其实是人：求助时把整段终端日志、完整 MCP 配置直接贴群，配置里带 key 是重灾区。
- 会话记忆串台：上午在私有会话聊过内部信息，下午在公开频道 Agent 顺嘴带出来。长会话建议定期清上下文。

## 可复用建议

- 发帖前三条检查：输出里有没有 token / 内网域名 / 客户数据；截图里有没有终端路径和提示词；配置贴出前先删 secrets。
- 一条命令兜底：

  ```bash
  grep -nE '(sk-[A-Za-z0-9]{16,}|Bearer [A-Za-z0-9._-]+|\.internal|10\.[0-9]+\.)' draft.md
  ```

- 怀疑泄露立即轮换密钥。默认假设：贴出来过一次，就等于已经泄了。

## 总结

红线不在提示词里，而在权限和输出路径上。把 Agent 当成一个权限很大、但可能口无遮拦的新同事来管：先收紧它能读什么，再过滤它能说什么，最后假设任何进过上下文的内容都可能出现在公开频道。三层做到位，社区分享和自动化才跑得安心。
