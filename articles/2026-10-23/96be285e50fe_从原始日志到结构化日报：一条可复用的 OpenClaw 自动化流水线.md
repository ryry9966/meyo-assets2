## 背景

每天一封日报：服务报错多少、慢查询几条、发布了几次、遗留什么问题。数据都在——应用日志、监控导出、发布记录，散在三四处。以前靠人肉翻日志，写一封要 40 分钟还常漏。上个月我用 OpenClaw 把这件事做成流水线，现在每天早上 8:30，群里自动收到一份 Markdown 日报。本文记录做法与踩过的坑。

## 问题定义

日报生产拆开是四步：**采集**（从异构来源拉昨天时间窗的数据）、**归一化**（统一成一种中间结构）、**汇总分析**（聚合、提炼“值得注意的三件事”）、**渲染推送**（套模板发频道）。核心判断是：哪步用 Agent，哪步用确定性代码。我的原则——凡涉及数字的统计全部用代码，Agent 只负责把结构化数据翻译成人话。

## 具体做法

定时任务触发主 Agent，配合一个自建 MCP server 暴露的两个工具：

**采集（`log-fetch`）**：提供 `fetch_range(source, start, end)` 接口，对接 Nginx 日志、监控 API、发布数据库三个来源，按时间窗过滤后返回统一中间格式（JSON 数组，字段固定：time / level / source / type / detail）。

**聚合（`log-aggregate`）**：输入中间格式，输出按 type 的计数、Top 5 错误消息、慢请求分位数。纯代码实现，不过模型。

**Agent 汇总**：主 Agent 拿到的不是原始日志，而是聚合 JSON（约 2-3KB）。Prompt 明确要求只基于给定数据输出、禁止推测未提供的数字，产出固定结构：summary、highlights、anomalies、todo。

**渲染推送**：独立脚本把 JSON 塞进 Markdown 模板，经 webhook 发群。发送前做 JSON Schema 校验，失败重试一次；再失败就降级发出“原始聚合数据 + 告警”，绝不静默。

## 踩坑点

1. **让模型算数字必翻车**。早期把几万行日志直接丢给 Agent 让它统计，结果对不上账。改成代码聚合后，模型只做解读，数字永远一致。
2. **时区坑**。日志是 UTC，人的“昨天”是东八区，第一版统计窗口整体偏了 8 小时。最后约定：流水线内部全用 UTC，只在采集入口和渲染出口做转换。
3. **定时任务静默失败最伤信任**。一次 API 改了返回结构，流水线连着三天没出报告，没人发现。补了心跳机制：成功后写状态记录，超过 25 小时无心跳就在群里报警。
4. **重试导致重复推送**。Webhook 超时重试，群里出现两份日报。现在按当天 `report_key` 做推送端去重。

## 可复用建议

- **阶段之间用固定 JSON Schema 作为契约**，每段可独立运行、独立测试，换数据来源或换模型都不动骨架。
- **中间结果按日期落盘**，出问题可以离线重放渲染，不必重新采集。
- **Agent 的输入做减法**：喂聚合结果而非原始日志，token 和幻觉各降一个量级。
- **宁可发降级版日报，也不要不发**，但要带上“本次为降级输出”的标记。

## 总结

流水线跑了三周，日报耗时从 40 分钟降到 0（人工抽查约 5 分钟），数字可追溯。一句话经验：**确定性代码处理数据，Agent 处理表达，Schema 兜底双方**。MCP 的价值在于把“取数”标准化成工具——之后不管日志来源怎么换，流水线骨架都不用动。样板代码整理后准备开源到社区仓库，欢迎拍砖。
