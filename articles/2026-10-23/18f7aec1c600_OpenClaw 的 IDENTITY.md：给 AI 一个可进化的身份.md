## 背景

跑一个长期在线的 OpenClaw agent，几天后你会发现一个现象：它的"性格"是漂的。今天话多，明天高冷；上周纠正过的沟通方式，这周又犯。原因不神秘——agent 的行为由每次会话加载的上下文决定，而"我是谁"这件事如果散落在系统提示、插件说明和聊天记忆里，就注定不稳定。

IDENTITY.md 是 OpenClaw 给出的答案：把身份收敛成一个文件。

## 问题

在没有身份文件时，常见三个问题：

1. **身份无单一来源。** 名字、语气、边界分散在多个配置点，改一处漏三处。
2. **不可版本化。** 想知道"agent 的性格什么时候变的、为什么变"，无据可查。
3. **纠正不落地。** 你在对话里说"以后简洁点"，这句话进的是记忆不是身份，几轮之后就被冲淡。

## 做法

IDENTITY.md 默认位于工作区根目录（`~/.openclaw/workspace/IDENTITY.md`），每次会话启动时被加载进上下文。它就是普通 Markdown，意味着你可以像对待代码一样对待它。一个够用的骨架：

```markdown
# IDENTITY
- Name: Claw
- Creature: 寄居蟹, emoji: 🦀
- Role: 个人自动化助手，负责日程、监控和脚本巡检
- Tone: 先给结论，再给依据；默认不超过 5 句
- Boundaries: 不主动推送非告警消息；不确定的事先问
- Language: 中文
```

实践上建议四步：

1. **初始化**：文件不存在时 agent 会自己生成一版，但第一版务必由人定调，不要把定义权完全交出去。
2. **压缩**：控制在 30 行以内。身份文件每次会话都占上下文，写得越满，指令遵循越差。
3. **分工**：身份归 IDENTITY.md（我是谁），行为准则归 SOUL.md（我怎么做事），用户信息归 USER.md（我服务谁），事实与事件归 MEMORY.md。一个主题只放一处。
4. **进化**：agent 表现不合预期时，不要只在对话里纠正，把结论写回 IDENTITY.md 并 commit。文件的历史就是 agent 的性格变更日志。

## 踩坑点

- **写成小作文。** "你是一个温暖而睿智的伙伴"这类句子对模型几乎没有约束力。用可执行的行为规则替代形容词："回复不超过 5 句""先结论后论据"。
- **身份与记忆混淆。** "用户在成都出差"是 MEMORY，"永远先问清楚再动手"是 IDENTITY。把动态事实写进身份文件，会让它迅速膨胀失效。
- **多处定义同一主题。** IDENTITY.md 和 SOUL.md 都写语气规则，优先级未定义，实际表现随机。
- **放任 agent 自改。** 允许它修改自己的身份没问题，但要有 review——它会写出讨好自己的版本。git diff + 人工确认是最低成本的护栏。
- **名字不一致。** 文件里叫 A，日常叫 B，自指场景（定时任务汇报、主动消息）会混乱。定一个名字，全家统一。

## 可复用建议

- 用 git 管理工作区，IDENTITY.md 的 commit message 就是身份 changelog：`v3: 更收敛，拒绝闲聊`。
- 固定每周或每两周回顾一次，而不是出了问题才改。
- 多 agent 场景：共享一份基础身份 + 每个工作区一份差异化覆盖，避免复制粘贴导致漂移。
- 把身份规则写成可验证的条目（如"回复不超过 5 句"），方便在真实对话里抽查是否生效。

## 总结

IDENTITY.md 的价值不在"让 AI 更像人"，而在工程层面：一个短小、单一来源、可版本化的身份配置。它把"agent 性格漂移"从一个玄学问题变成一个 diff 问题。写得越克制，越有效。
