# 背景

让 Agent 具备"主动性"是自动化实践绕不开的一步：定时巡检、盯文件变化、响应外部消息，都依赖某种 heartbeat——让助手周期性或事件式"醒来"的机制。实现路径通常分两派：**轮询**（cron 定时唤醒）和**推送**（webhook / 队列 / MCP 工具触发）。两派各有拥趸，但真实系统里这不是二选一。

# 问题

纯轮询的代价很直接：假设 30 分钟一次，一天 48 次唤醒，绝大多数是空转。每次唤醒都要过一遍模型，token 在烧，"无事发生"这种噪音还会写进会话上下文，挤压真正有用的记忆。

纯推送的问题藏在故障场景里：本地跑的 agent 在 NAT 后面收不到公网 webhook；事件源挂了推送就断；agent 停机维护期间发生的事件，重启后没有任何机制补上。推送的延迟低是快路径的延迟低，不等于可靠性。

# 做法：分层，而不是二选一

我的实践是"**推送做快路径，轮询做兜底**"，分四步：

1. **事件分级**。按容忍延迟分类：消息回复、CI 失败这类要求分钟级反应的走推送；日报汇总、定期巡检这类延迟无感的走轮询。分级做不清楚，后面全白搭。
2. **轮询加抖动**。cron 触发加随机 jitter（如 ±10%），避免多实例同秒唤醒；间隔按事件分级分别设置，不要全局一个值。
3. **推送先过便宜的闸门**。事件入队时不直接唤醒模型，先跑确定性检查：文件 mtime 变没变、队列长度是否超阈值、去重键是否已存在。不通过就静默丢弃或合并，只有通过闸门的才真正唤醒 LLM。
4. **单飞与合并**。同一时刻只允许一个 heartbeat 在跑，唤醒期间到达的事件合并成一条待办，结束后一次性消费。同时解决风暴和重复劳动。

# 踩坑点

- **自触发循环**：agent 某次 heartbeat 写了状态文件，恰好触发文件监听把自己唤醒，无限循环。所有 agent 产生的事件要打来源标记，来源是自己的入队但不唤醒。
- **空 heartbeat 烧钱**：早期没闸门时，一天 48 次唤醒里 45 次是模型说"无事可做"。加闸门后降到日均 6 次，成本差近一个数量级。
- **内网收不到推送**：本地 agent 接 webhook 要么打隧道要么改拉队列。我最后选了后者——多花 30 秒延迟，换掉一整条隧道的运维。
- **停机丢事件**：推送在 agent 下线时就丢了。必须配一条低频对账轮询（如每小时核对关键状态），这本质上是承认轮询不可替代。
- **上下文污染**：heartbeat 的思考过程不要写进主会话，单独开轻量会话，结论以摘要形式回写。

# 可复用建议

- 先做轮询再上推送，轮询永远保留作对账
- 唤醒决策要便宜，执行才允许贵：LLM 之前必须有确定性检查
- 每个事件幂等，合并永远比排队安全
- 盯三个指标：唤醒次数、空转率、日均成本；空转率超三成说明闸门失效

# 总结

轮询 vs 推送不是架构品味问题，是延迟容忍度和可靠性预算的分配问题。快路径用推送，兜底与对账用轮询，中间用便宜闸门挡空转——这套分层在任何 agent 框架里都成立，在 OpenClaw 的 heartbeat 配置上加一个带去重的队列即可落地。
