## 背景

在 OpenClaw 这类常驻 Agent 架构里，`memory_recall` 是调用频率最高的工具之一。用户随口一句“我上次说的那个部署方案”，Agent 要从成百上千条记忆里捞回正确的那条。记忆库只有几十条时怎么搜都能命中；涨到几千条后，召回质量开始直接影响对话体验——答非所问、重复追问、把过期配置当成现行方案，多数都出在 recall 这一步。

## 问题

常见两条路线：

- **语义搜索**：文本过 embedding 模型存向量，查询时算余弦相似度。能理解“换个说法”，查“怎么把服务跑起来”能命中“部署流程”那条记忆；但引入模型依赖，且对精确标识符（用户 ID、文件名、错误码）经常失手。
- **全文搜索**：SQLite FTS5 / BM25，甚至 LIKE。精确匹配强、零模型依赖、结果可解释；但同义改写直接漏召回。

单用哪条都有明显短板。我们最终落地的是**混合召回**，评测集上 recall@5 比单用任一种高出约 15 个百分点。

## 做法

1. **存储层不二选一**。每条记忆保留原文 + 结构化字段（时间、来源、重要度），embedding 只作为派生缓存列，模型升级可全量重建。
2. **双路并行召回**。查询同时打 FTS5（BM25 排序）和向量检索（各取 top 20），用 RRF（倒数排名融合）合并，再按时间衰减微调。别把余弦分数和 BM25 分数直接加权相加——量纲不同，调参是无底洞。
3. **分数和来源一起返回给模型**。不只吐文本，把 score、命中方式（semantic/keyword）、时间戳一并给 LLM，让它自己判断置信度。
4. **先建小评测集**。人工整理 30~50 条“问题 → 期望命中的记忆 ID”，每次改动跑一遍 recall@5 / MRR。没有这个，所有优化都是凭感觉。

## 踩坑点

- **中文分词是 FTS 的隐形坑**。FTS5 默认 unicode61 对中文基本无效，整句成一个 token。要么换 jieba 分词器，要么用 trigram。我们一开始忘了这个，所谓“精确匹配”其实从未工作过。
- **embedding 模型版本漂移**。索引和查询用了不同版本，相似度整体下滑但不报错，极难察觉。存记忆时把模型名写进去，不一致就触发重建。
- **记忆条目太长**。一整段对话切成一条记忆，embedding 信号被稀释。按“一件事一条”切，单条控制在 200 字以内效果好很多。
- **小语料别上向量**。几百条记忆时 FTS 足够，向量检索反而因近邻区分度低引入噪声。

## 可复用建议

- 默认起点：SQLite + FTS5 + 本地 embedding 模型，单机够用，别一上来就上独立向量数据库。
- 混合是终局，但顺序是先用 FTS 跑通评测，再按评测缺口决定要不要加向量。
- 把 recall 未命中的 query 记日志，每周看一次，比任何理论分析都有用。
- 重要记忆加 pinned 字段，绕过排序直接注入上下文。

## 总结

语义搜索和全文搜索不是二选一，而是分工：向量管“换了说法”，FTS 管“一字不差”。正确的工程顺序是先建评测集，再让数据决定混合比例。memory_recall 的上限不取决于算法多先进，而取决于你有没有认真看过它每一次到底漏了什么。
