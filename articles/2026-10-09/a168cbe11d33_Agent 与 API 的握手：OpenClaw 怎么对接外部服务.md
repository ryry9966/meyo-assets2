## 背景

OpenClaw 这类 agent 的能力上限，往往不取决于模型本身，而取决于它能"摸到"哪些外部服务。查工单、发通知、拉数据、调内部 RPC——都绕不开 API 对接。社区里常见两种极端：一种直接让 agent `curl` 一把梭，另一种一上来就写全套 MCP server。两种都有适用场景，多数人踩坑不是因为选错，而是没想清楚边界。

## 问题

实际对接中反复出现三类问题：

1. **参数幻觉**：agent 调 API 时编造字段名、漏传必填项，收到 400 后进入"改一下再试"的死循环。
2. **上下文污染**：API 返回几万 token 的 JSON 被原样塞进对话，垃圾数据挤占上下文，后续推理质量明显下降。
3. **凭据安全**：key 写死在配置里、打进日志里，甚至被 agent 复述进对话历史。

## 做法与步骤

我们的实践按优先级排：**先 MCP，再插件，最后才考虑裸调用**。

**第一步：圈定接口面。** 列出真正需要的能力，一般控制在 5 个以内。不要把整个 OpenAPI spec 丢给 agent——工具越多，选错率越高。

**第二步：写薄封装的 MCP server。** 每个工具只暴露一个业务动作，入参用严格 JSON Schema，描述里写清"什么场景该用我"。返回值做裁剪：只回关键字段和分页游标，原始大 payload 落盘或进缓存，给 agent 一个引用 ID 即可。

**第三步：管好凭据。** key 走环境变量或系统密钥链，MCP server 启动时注入；出参在 server 层统一脱敏，确保 token、手机号之类不会进入对话历史。

**第四步：区分读写。** 读操作可以给 agent 自动化权限；写操作强制二次确认，或做成 dry-run——先返回"将要执行的操作摘要"，确认后再真调。

**第五步：补齐韧性。** 超时设短（10-30 秒）、指数退避、重试上限 2-3 次。长任务改异步：提交后返回 job ID，agent 轮询或等回调，别让一次调用挂死整个会话。

## 踩坑点

- **工具描述含糊是参数幻觉的根源。** "发送消息"这种描述不够，要写明平台、频率限制、字段格式。工具描述就是给模型看的 API 文档，值得认真写。
- **别在 agent 层做重试。** agent 对"失败"的判断不稳定，容易重试出重复订单。重试逻辑下沉到 server，写操作必须带幂等键。
- **stderr 污染协议。** MCP server 里随手 `print` 调试信息会破坏通信，日志一律走文件。
- **一次接太多服务。** 先在一个业务域跑通，把模板沉淀下来再复制，比同时铺开五个服务划算得多。

## 可复用建议

- 按**业务域**拆 MCP server，而非一个大而全网关：认证方式、限流策略不同的服务天然该分开。
- 每个写接口都留 dry-run 开关，联调期全程开着。
- 统一错误结构：`{ok, error_code, hint}`，让 agent 能基于 hint 自修正，而不是靠猜。
- 记录每次工具调用的请求摘要与耗时，排障时比翻对话历史快得多。

## 总结

Agent 对接外部服务的本质，是把"不稳定的自然语言意图"翻译成"稳定的结构化调用"。核心工作量不在模型，而在封装层：窄接口、严格 Schema、凭据隔离、幂等与确认。把这几件事做扎实，agent 的可靠性会有肉眼可见的提升。接口面收敛、封装保持薄，剩下的留给社区一起迭代。
