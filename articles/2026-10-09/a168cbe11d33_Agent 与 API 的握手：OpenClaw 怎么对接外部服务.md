## 背景

Agent 的价值在于"能动手"，而动手的前提是能对接外部服务：查数据、读写数据库、触发内部系统。在 OpenClaw 里，这条链路主要有两种形态：**MCP server**（标准工具协议，配置在 `openclaw.json` 的 `mcpServers` 下）和**本地插件/skill**（自己封装的轻量工具）。看起来只是"配个 key、调个 API"，实际跑起来坑不少——大多数问题不在模型，而在我们给模型准备的那层"握手协议"。

## 常见问题

实践中反复出现三类故障：

1. 模型不调工具，或参数乱填——根因多半是工具描述写得不行；
2. 调用失败后陷入重试死循环——错误信息模型读不懂，只能瞎猜；
3. key 泄露或权限过大——图省事直接把管理员凭证塞进配置。

## 做法与步骤

**第一步：先用 curl 跑通 API。** 别上来就写插件。先确认鉴权方式（header 还是 query）、参数格式、限流策略。这一步能排除 80% 的"以为是 Agent 的问题"。

**第二步：选对接形态。** 已有现成 MCP server 的服务（文件系统、数据库、代码仓库等）直接配置复用；没有 server 的内部 API，写个轻量插件。经验判断：工具少于 5 个、逻辑简单用插件；需要跨会话复用、有资源或流式需求，再考虑 MCP。

**第三步：key 走环境变量。** 配置文件里只留 `${VAR_NAME}` 引用，真实凭证放 `.env` 或系统环境变量，日志注意脱敏。

**第四步：认真写工具描述。** description 不是注释，是 prompt 的一部分。写清楚四件事：工具干什么、什么时候**不该**用它、参数的单位与格式、返回结构。模型选工具基本全靠这段话。

**第五步：结构化错误返回。** 失败时返回 JSON：错误码 + 一句模型能执行的处置建议，例如"date 参数格式应为 YYYY-MM-DD，请修正后重试"，而不是抛异常或返回空串。

## 踩坑点

- **描述含糊**：写"获取数据"，模型不知道是订单还是用户，开始随机猜参数。描述里要写清边界和反例。
- **没设超时**：外部 API 挂了，agent 卡死整个会话。HTTP 调用统一加 timeout（10–15s）和有限次重试。
- **schema 与实际不符**：声明 required 的参数实际可省略，导致模型每次都向用户追问。以 API 真实行为为准。
- **工具挂太多**：一次性加载 20+ 工具，上下文膨胀、选择准确率下降。按场景拆分，按需启用。
- **危险操作无闸门**：删除、支付类工具要有 dry-run 或人工确认环节。

## 可复用建议

- 插件保持"薄"：只做参数校验、鉴权、错误包装，业务逻辑放独立脚本，便于单独测试。
- 给每个写操作配一个只读"预览"版本，先查后写。
- 把"curl 验证 → 封装 → 接 agent"固化成团队 checklist。
- pin 住 MCP server 版本，升级前在测试会话里 diff 一遍工具列表。

## 总结

对接外部服务的本质不是"接上"，而是"让模型可靠地接上"：鉴权收口、描述精确、错误可读、危险可控。把每个 API 当成一位讲道理但脾气固定的同事——先用 curl 摸清它的习惯，再给 agent 写一份它能看懂的说明书。握手才算完成。
