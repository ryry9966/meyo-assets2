## 背景

OpenClaw 的 `memory_recall` 是 agent 回忆历史信息的核心工具：从 `~/.openclaw/workspace/memory/` 下的 Markdown 记忆文件中检索相关条目，注入当前上下文。默认走 SQLite FTS5 全文索引，开启 embedding 后可以叠加语义检索。社区里常见一个默认假设：“语义搜索更聪明，开了肯定更好。”我用自己的记忆库跑了一轮小评测，结论没那么简单。

## 问题

语义检索的卖点是“理解意图”，但个人记忆库有三个特殊条件：语料小（几百条）、查询里大量专有名词（项目名、路径、设备型号、报错码）、时间敏感。这三个条件对两种检索方式的影响方向完全相反，不能照搬 RAG 大语料场景的经验。

## 做法：用真实查询做一次小评测

1. 从最近两周的会话里挑 30 条确实触发过回忆的查询，人工标注每条的正确命中记忆。
2. 同一批查询跑三种模式：纯 FTS、纯语义、混合（两路召回后按 0.6/0.4 加权重排）。
3. 统计 hit@5。我的结果：FTS 21/30，语义 17/30，混合 25/30。

语义输在专有名词上——查询写的是具体报错码或设备型号，向量相似度反而被“话题相近但条目不对”的结果稀释。全文搜索输在换说法：比如“那个总掉线的摄像头”匹配不上记忆里的“camera 断连排查记录”。

配置层面：embedding 用本地 `bge-small-zh-v1.5` 走 Ollama；混合权重 0.6 全文 + 0.4 语义起步，再拿评测集微调。

## 踩坑点

- FTS5 默认的 unicode61 分词器基本不切中文，整句会被当成一个 token，中文全文搜索形同虚设。要么改用 trigram，要么入库前先 jieba 分词。中文用户测出“全文搜索不行”，很可能是分词问题，不是方案问题。
- 换 embedding 模型必须全量重建索引，维度和语义空间都不兼容，只改配置文件没用。
- 云端 embedding API 会把记忆原文整条发出去。含密钥、内网路径的记忆，建议强制走本地模型。
- 不加时间衰减的话，三个月前的旧配置记录会和新记录混排，正确的条目被过时版本压在后面。

## 可复用建议

- 检索参数的收益远小于记忆文件本身的写法：日期、项目名、关键报错码放进标题或首行，命中率提升比调权重明显得多。
- 顺序应该是先全文、后语义：只有当你实际观察到“换了说法就搜不到”时再开语义，而不是一上来就全量上 embedding。
- 评测集别跑完就扔，存成脚本每周让 agent 自己跑一遍，改模型、改权重之后防退化。
- 混合是稳态，但权重没有万能值，必须用自己的查询分布调。

## 总结

这不是二选一的题。个人记忆库场景下，全文搜索解决精确匹配，语义搜索解决换说法，两者叠加再补一个 recency 加权，才是可靠的组合。这次最大的教训其实和检索算法无关：先建评测集，再动手调参——否则所有“感觉变好了”都不可信。
