## 背景

在 OpenClaw 这类常驻运行的 Agent 环境里，工具调用是整条链路中最不可控的一环。天气、搜索、支付、自家内部服务，多半走 HTTP API，再套上 MCP 之后故障面更大：上游超时、限流 429、网关 502、密钥过期、字段悄悄变更。模型本身很稳定，挂的通常是边界上的第三方。很多自动化流程第一次跑通后就没人管了，某天 API 一抖，整条任务链就断了——甚至更糟：模型在拿不到数据时自己编了一个。

## 问题

观察下来，故障现场的 Agent 通常有三种坏行为：

1. **盲目重试**：同一条指令循环调用，token 烧完，还把上游限流雪上加霜。
2. **沉默失败**：工具抛出异常，原始堆栈混进上下文，模型接着编一个"看起来合理"的答案。
3. **长时间挂起**：没设超时，一次慢请求把整个会话堵死。

根因往往只有一个：把重试策略写进了 prompt，指望模型自己临场判断。这类确定性逻辑应该放在代码里。

## 做法

我们的做法是在插件层包一层统一的调用适配器，Agent 只看到规整后的结果：

1. **错误分类**。把异常归为可重试（超时、429、502/503/504）和不可重试（400、401、422）。401 是密钥问题，重试一百次也没用。
2. **限时 + 退避重试**。每次调用设硬超时；可重试错误做指数退避加随机抖动，最多 3 次。抖动必须有，否则服务恢复的瞬间会被集中请求打第二次。
3. **熔断**。连续失败达到阈值后把该工具标记为不健康，冷却窗口内直接短路返回，不发起真实请求。
4. **结构化错误上抛**。最终失败时不把堆栈丢给模型，而是返回 `{ok, error_code, retryable, hint}` 这样的错误包，hint 写人话："上游搜索服务暂不可用，请告知用户稍后再试"。
5. **幂等保护**。写操作（下单、发消息）重试必须带幂等键，否则重试本身就是事故。
6. **诚实降级**。系统提示里明确规则：工具最终失败时如实告知用户，禁止用旧数据或编造内容顶替。

## 踩坑点

- **让模型自己数重试次数**：它数不准，还容易进循环。重试、退避、熔断全部下沉到代码。
- **把 429 当普通 5xx 立刻重试**：应读取 `Retry-After`，按上游要求等。
- **熔断打开后永不恢复**：要留半开探测，否则服务恢复了 Agent 还在报错。
- **幂等键每次重试重新生成**：等于没做。
- **超时一刀切**：搜索类接口 5 秒够，报表类可能要 30 秒，按工具分别配置。
- **健康检查放进主链路**：探测应异步进行，别让每次调用都多一跳延迟。

## 可复用建议

- 所有外部调用收敛到一个适配层，错误包格式全站统一，新插件直接复用，不必各自造轮子。
- 每次工具调用记录耗时、结果码、重试次数——排障时这就是你的行车记录仪。
- 开发环境故意把 mock API 关掉，演练一遍故障路径，确认 Agent 的表现是"告知并等待"，而不是"编造"。

## 总结

外部 API 挂掉不是异常，是常态。要做的不是把 prompt 写得更恳切，而是把确定性逻辑——超时、分类、退避、熔断、幂等——沉到调用边界里，让模型只在拿到结构化结论后做决策。边界稳了，Agent 才谈得上可靠。
