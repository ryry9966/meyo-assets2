## 背景

OpenClaw 的主 agent 默认是一条会话一条线：调工具、等结果、继续推理。任务一多就暴露两个问题：一是纯串行等待，二是主会话上下文被大量中间输出污染，越往后模型越“记不住重点”。

subagent 提供了另一种结构：主 agent 只做拆解、分发、汇总，执行下放给各自独立会话的子 agent。在 OpenClaw 里，子 agent 通过 spawn 类工具（如 `sessions_spawn`）创建，跑在独立 session 中，有自己的上下文和工具权限；如果配了 MCP，子 agent 也能挂自己的工具面。

## 问题

典型场景：批量扫描多个代码仓库找隐患、同时从多个数据源收集调研资料、对一批文档做抽取归类。这些任务的共同点：子任务相互独立、以读为主、单块产出往往很啰嗦。放在主 agent 里串行做，耗时长、上下文爆炸，一步失败全链路卡住。

## 做法

1. **先判断能不能并行**：任务独立、读多写少、边界清晰。涉及共享文件写入的，写入阶段必须串行。
2. **写自包含的任务描述**。子 agent 看不到主会话上下文，task 里要带全信息。我的模板是：目标 + 背景（具体路径、已知信息）+ 约束（不要改动文件 / 只输出结论）+ 输出格式（如 markdown，限 N 行内）。
3. **控制并发**。一次 spawn 3~5 个比较稳。更多会撞 API 限流，结果你也看不过来。
4. **要求子 agent 返回摘要而非全量**。比如“只返回命中列表和一句话理由”。聚合的活留给主 agent。
5. **收口**。主 agent 收集结果，做去重、冲突检查、最终聚合；失败的子任务记录下来，决定重试还是降级。

## 踩坑点

- **任务描述偷懒**：写一句“帮我看看这个仓库”，子 agent 全靠猜。上下文不共享是 subagent 的第一原则，需要什么就写进 task。
- **并发开太猛**：限流报错、超时，总耗时可能比串行还慢。
- **子 agent 直接写文件**：两个 agent 同时改一个文件，后写的覆盖先写的。原则是读并行、写串行。
- **返回内容不设限**：子 agent 把整段日志贴回来，主会话上下文照样爆。
- **没有失败处理**：一个子 agent 卡住，聚合阶段无限等待。task 里明确超时预期和“拿不到就说明原因返回”。

## 可复用建议

- 子 agent 适合“宽”的活（搜索、批量审查、抽取）；主 agent 保留“深”的活（决策、架构判断、需要全局视角的部分）。
- 把任务描述模板固化进你的 agent 配置或系统提示里，让主 agent 自己 spawn 时也遵守同一套格式。
- 给每类并行任务定一个固定输出 schema（哪怕是三行 markdown），汇总阶段会省很多事。
- 先拿 2~3 个子任务小批量试，验证任务描述质量，再放大并发。

## 总结

subagent 编排的本质不是“更多 AI”，而是把串行长任务改造成并行的有界子任务：主 agent 负责拆解与汇总，子 agent 负责隔离执行。收益最大的场景是批量读类工作；决定成败的是任务描述质量和并发控制。先用小规模验证，再逐步放大，别一上来就开十个。
