## 背景

大模型本身无状态，每次会话从零开始。OpenClaw 这类常驻 Agent 提供了天然的记忆载体：workspace 里的 `MEMORY.md`、`memory/` 目录下的每日笔记，以及可以自行接入的向量库。但“有地方存”和“记得对、取得准”是两回事。最近我把自己的记忆链路重写了一遍，记录一下设计取舍。

## 问题：三个真实痛点

1. **记不住该记的**。明确说过“回复用中文、尽量简短”，十几轮后 Agent 又恢复长篇输出。
2. **记得太杂**。每轮对话都往记忆里写，几周后 MEMORY.md 膨胀，一半是过期信息。
3. **取得不准**。检索回的记忆与当前任务无关，反而污染上下文。

核心矛盾在于：偏好写入是**低频高价值事件**，而对话是**高频低信息密度事件**。把对话流直接灌进记忆，两头不讨好。

## 做法：三层结构 + 一条写入流水线

**第一层：静态偏好档案（必进上下文）**
单独维护 `preferences.md`，只放稳定偏好——语言、代码风格、常用工具链、时区，每条带来源和更新时间。会话启动时全量注入，控制在 500 token 以内。

**第二层：情景记忆（按需检索）**
`memory/` 按天记事，只记“发生了什么、做了什么决定”，原始对话不落盘。检索用语义搜索取 top-3，低于分数阈值直接丢弃。

**第三层：写入流水线（关键）**
不是每轮都写，触发条件限定三种：

- 用户显式说“记住这个 / 以后都这样”；
- 用户纠正了 Agent 的行为（价值最高的信号）；
- 同一偏好在七天内的对话里出现三次以上。

触发后用 LLM 抽取成结构化条目 `{key, value, confidence, evidence, ts}`，先进候选区，定时审核后合并进 preferences.md。冲突时新的覆盖旧的，被覆盖条目进 changelog。

**反馈闭环**：Agent 命中某条偏好时累计 hit 计数，九十天零命中的条目自动归档。

## 踩坑点

- **嵌入模型与中文不匹配**。第一版用英文为主的嵌入模型，中文偏好句召回很差，换多语言模型后 top-1 命中率明显改善。
- **抽取太激进**。早期每轮都抽取，产生大量“用户偏好简洁排版”这类模糊废条目。写入必须有门槛。
- **没有冲突处理**。新旧两条“测试框架”偏好同时被召回，Agent 行为随机。条目必须带时间戳和覆盖逻辑。
- **top-k 给太多**。从 5 降到 3 并配合分数阈值，上下文噪音显著下降。
- **没有评测集**。攒了三十条“在某偏好下 Agent 应有表现”的用例，每次改版跑一遍，否则调参全靠感觉。

## 可复用建议

- **先用 Markdown + grep，再考虑向量库**。几百条以内的规模，关键词检索够用，且全程可读可调试。
- **记忆条目必须带元数据**：时间、来源、置信度、命中数，否则无法维护。
- **用户纠正优先于一切自动抽取**。
- **隐私红线**：偏好档案不存凭据类信息；向量库若上云要明确告知用户。

## 总结

记忆系统本质是一个带写入策略的数据库问题：什么该写（触发条件）、怎么存（结构化 + 元数据）、怎么取（检索 + 阈值）、怎么废（TTL 与冲突覆盖）。OpenClaw 的 workspace 机制是很好的底座，剩下的都是工程纪律。建议先跑通“偏好档案 + 纠正触发写入 + 命中计数”这个最小闭环，再逐步引入语义检索，比一上来就搭 RAG 管线稳得多。欢迎在评论区交流各自的记忆目录结构。
