## 背景

用 Agent 做日常自动化的人大多遇到过同一个尴尬：昨天明明说过“部署只用 pnpm”，今天它又开始建议 npm。上下文一清，一切归零。模型本身没有跨会话状态，所谓“记忆”必须在外围系统自己解决。OpenClaw 生态里这件事尤其突出——插件和 MCP 工具接得越多，用户偏好如果不持久化，每次对话都得重新交代一遍。

## 问题

最常见的三种失败做法：

1. **全塞 system prompt**。偏好一多，token 预算爆掉，且无法动态增删。
2. **有存储没检索**。存了一堆 JSON，注入时要么全量灌入要么干脆不查，等于没存。
3. **只写不更新**。偏好变了旧记忆还在，新旧冲突时模型随机采信，输出不稳定。

## 做法

社区实践目前大致收敛成一个四层结构：

**1. 采集层。** 两条通道：显式指令（“记住 XXX”）直接落盘；隐式信号由模型在任务结束后自评——用户本次纠正过什么、重复表达过什么倾向。隐式采集要设阈值，比如同一纠正出现两次才写入，避免噪声入库。

**2. 存储层。** 每条记忆不是一句话，而是一条结构化记录：`{category, content, confidence, source, created_at, hit_count}`。分类粗分即可：工具链、代码风格、沟通偏好、项目上下文。粒度太细检索不准，太粗复用性差。

**3. 检索层。** 混合检索：向量相似度保语义，keyword 匹配兜底，叠加 recency 权重。每次注入只取 top-k（默认 5 条），并设注入预算——记忆区 300~500 token 足够，超了会挤压任务上下文，反而降低表现。

**4. 更新层。** 新记忆与旧记忆相似度超阈值时走合并而非追加：置信度高的覆盖低的，时间新的覆盖时间旧的。被合并的记录保留 audit 链，用户随时可查可删。这一条对信任度影响很大。

用 MCP 实现的话，暴露两个 tool 就够：`memory_search`（agent 主动查）加 `memory_write`（强制带 category 和 confidence 参数）。不要给 agent 无限写权限，写入动作记日志。

## 踩坑点

- **写入过滥**：早期让 agent 每轮自评，结果“用户今天用了感叹号”都存进去了。后来收敛为只允许三类触发：显式指令、纠正行为、重复模式。
- **记忆污染**：一次性的临时需求（“这次先别加测试”）被当成永久偏好。加 `source` 字段区分 one-off 和 standing，one-off 默认 7 天过期。
- **检索时机错误**：只在会话开始注入一次，用户中途切了话题就失效。改成每次工具调用前按当前任务重新检索，多一跳查询，但命中率提升明显。
- **没有清理入口**：记忆系统一旦不可审查，用户宁可整个关掉。哪怕只做一个 CLI 命令列出全部记忆，也比黑箱强。

## 可复用建议

- 先做最小闭环：一张 SQLite 表 + 向量列 + 两个 MCP tool，一天能跑通，再谈优化。
- 注入永远限量，宁缺勿滥——错记忆比没记忆危害大。
- 所有写入带 confidence 和 source，这是后续一切治理的基础。
- 记忆带版本号或时间戳，回滚才有抓手。

## 总结

记忆系统本质是数据治理问题，不是提示词问题。采集要克制、存储要结构化、检索要限额、更新要可追溯。先把闭环跑通、把审计入口留好，精度问题可以靠数据慢慢磨。社区已有几个插件在做类似的 schema，欢迎在回复里贴你们的字段设计，一起对齐。
