## 背景

跑 Agent 的都知道，日常自动化里大部分调用是“低难度高频次”：解析一条消息、格式化一段文本、调一次 MCP 工具、走一轮固定流程。这类活交给云端旗舰模型，贵且没必要；而涉及家庭照片、日程、聊天记录的私有数据，过第三方 API 也不安心。所以在台式机上常驻一个本地模型专干这些脏活，云端只处理真正需要推理的任务，是我几个月验证下来比较经济的组合。

## 问题

家用硬件跑本地模型，难点不是“能不能跑起来”，而是三件事：显存装得下模型还不够，长上下文的 KV cache 会再吃一块；小模型对 function calling 的支持参差不齐，工具调用格式一错整个 Agent 循环就卡死；推理框架默认上下文很短，接上 OpenClaw 这种带长系统提示和一堆 MCP 工具 schema 的场景，不显式调参数，模型会“看不见”自己的工具。

## 做法

1. **盘点硬件。** 经验值：Q4_K_M 量化下，7B≈4.5GB、14B≈9GB、32B≈20GB，另留 2–6GB 给 KV cache。16GB 内存老老实实跑 7–8B；24GB 显存可舒服跑 14B 甚至 32B MoE。
2. **选运行时。** 图省事用 Ollama，自带 OpenAI 兼容端点（`http://127.0.0.1:11434/v1`）；要精细控制用 llama.cpp 的 llama-server，`-ngl` 控制上卡的层数。
3. **选模型。** 重点看两点：原生支持 tool calling、中文能力够用。Qwen 系列目前是稳妥选择；MoE 结构（如 30B-A3B）激活参数少，家用 CPU+GPU 混跑速度也能接受。
4. **接 OpenClaw。** 模型后端的 base_url 指到本地端点，API key 随便填；显式设上下文长度（Ollama 里是 `num_ctx`），建议 ≥16k——系统提示加工具 schema 每轮都要占。
5. **真实任务压测。** 别跑通用 benchmark，直接拿日常 Agent 流程跑一小时，统计工具调用成功率和 tokens/s。

## 踩坑点

- **上下文静默截断最阴险。** Ollama 默认上下文很短，Agent 不报错，只是模型“忘了”自己有哪些工具，表现为凭空编造参数。先查 `num_ctx`。
- **小模型吐的 tool call JSON 偶尔不合法。** 把 temperature 压到 0.2–0.6，选官方标注支持 function calling 的模型，避开民间魔改 quant 版。
- **并发排队。** OpenClaw 并发调工具时，本地推理服务默认单队列。要么把并发设为 1，要么 llama-server 开并行 slot。
- **部分层上卡是假省。** `-ngl` 不拉满时 PCIe 搬运成为瓶颈，速度可能不如全 CPU；上不了全量就换小一档模型。
- **别碰 Q2 以下量化。** 省的显存换来的能力损失，在 Agent 任务里就是幻觉率翻倍。

## 可复用的建议

- 做**路由**而不是**替代**：本地接住高频低难度调用，复杂规划仍走云端，成本和体验都有保底。
- 推理服务独立进程跑（systemd/守护），OpenClaw 重启不陪着重载模型。
- 给每次工具调用记日志——本地模型的问题几乎都藏在失败的 JSON 里。
- 模型版本固定后再接生产流，升级前重跑一遍压测脚本。

## 总结

本地模型替代不了旗舰模型的推理能力，但作为 Agent 的常驻执行层——解析、格式化、调工具、跑流程——在 16GB 内存的家用机上就已可用，24GB 显存则相当宽裕。先小后大、先跑通再调优，盯住上下文长度和工具调用质量这两个变量，本地化这条路比想象中平缓。
