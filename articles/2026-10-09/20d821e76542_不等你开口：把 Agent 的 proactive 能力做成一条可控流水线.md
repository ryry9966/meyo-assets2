## 背景

大多数 Agent 的工作模式是被动式的：你提问，它回答，会话结束就沉寂。但日常里大量有价值的事情属于"可预测的时间敏感事件"——CI 红了、日历要撞车、证书两周后过期、监控指标越线。这些不需要你去问，需要有人盯着。

所谓 proactive 能力，本质上就是给 Agent 补上一条自己的触发回路。在 OpenClaw 生态里，插件负责调度与事件监听，MCP server 负责把各类数据源标准化暴露，拼出这条回路并不难，难的是拼出来之后不翻车。

## 问题

最常见的失败路径：给 Agent 挂一个 cron，每半小时唤醒做全量检查。结果三选一——刷屏、长期沉默、token 账单失控。更隐蔽的是没有状态设计，同一个故障连报三遍，用户第一周就把通知关了。

根因是三层都缺约束：触发没有节流，判断没有门槛，行动没有分层。

## 做法

我们最终收敛成一条四段流水线：

1. **事件接入**。数据源用 MCP server 封装（CI 状态、日历、指标、工单），能 webhook 就别轮询；事件里带上 `origin` 和 `fingerprint` 字段，后面每一步都要用。
2. **确定性预筛**。阈值、关键词、diff 规模这类规则先行，九成事件在这里被挡掉，LLM 只看候选。这一步直接决定成本曲线。
3. **判断层**。用便宜的小模型跑一遍"值不值得打扰"的分类，rubric 写死三个维度：影响面、时效性、是否与已报 fingerprint 重复。输出必须是结构化的 L0–L3 分级。
4. **分层执行**：

```yaml
L0: log            # 静默记录，进决策日志
L1: daily_digest   # 汇总进日报，不实时打扰
L2: notify         # 即时通知，附下一步动作建议
L3: act            # 白名单内低风险写操作，带每日配额
```

配套两件基础设施：状态存储做 dedup（同一 fingerprint 24 小时内只报一次）和 quiet hours；所有主动决策连同理由写日志，供回放调参。

## 踩坑点

- **自触发回环**。Agent 自己发的 L2 通知又进了事件流，把自己再次唤醒，几分钟内打满配额。解法：事件带 origin 标记，来源为本 Agent 的一律忽略。
- **预筛校准方向搞反**。上线时怕吵到人，阈值设得极严，连续两周零输出，还以为管道坏了。正确做法是先宽松，靠日志回放逐步收紧。
- **上下文断档**。定时唤醒的是全新 session，Agent 不知道上周和用户约定过什么。需要按事件主题检索相关记忆片段注入 prompt，否则判断会脱离用户偏好。
- **权限蠕化**。图省事给了常驻写权限，一次误操作后改成 L3 仅白名单 + 配额，才算睡得着觉。

## 可复用建议

- 从一个低风险场景起步（比如 CI 失败聚合日报），把触发→预筛→分级→执行全链路跑通，再接第二个源。
- 主动消息固定三段式：发生了什么 / 为什么与你有关 / 我可以接着做什么。第三段给可执行选项，用户按一下就能推进。
- 把"采纳率 / 忽略率"当核心指标，忽略率连续走高就该收阈值；策略放版本化配置，别埋在 system prompt 里。

## 总结

Proactive 不是把 Agent 调得更聪明，而是给它套上触发、过滤、授权三道闸。先守住误报率和成本，主动性才有存在感——用户信任的是"它开口就有事"，而不是"它随时会开口"。
