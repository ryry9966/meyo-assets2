## 背景

做 Agent 自动化久了，痛点往往不在 prompt，而在后端：API 限流、账单随调用量线性上涨、涉及个人笔记和本地文件的流程不敢直接上云。我的方案是把日常高频、隐私敏感的那部分推理搬回家：一台普通台式机跑本地 LLM，OpenClaw 的 Agent 和 MCP 工具链全部指向本地端点。跑了两周，记录一下可复制的路径和踩过的坑。

## 问题

实际要解决三件事：

1. **硬件上限**：显存/内存决定能跑多大的模型；
2. **小模型可靠性**：本地能跑的模型普遍不大，function calling 的稳定性直接决定 Agent 能不能用；
3. **长期运行**：并发、超时、散热这些“跑一次没问题、跑一周出事”的问题。

## 硬件盘点与模型选择

粗略估算规则：Q4 量化的模型权重约占显存 `参数量 × 0.6GB`，再加 KV cache。

- 7B Q4 ≈ 5GB，14B Q4 ≈ 9GB，32B Q4 ≈ 20GB；
- 16GB 显存：14B Q4 很舒服，32B 需要部分 offload 到内存，速度掉一个档次；
- 纯 CPU + 大内存：走 llama.cpp 的 GGUF，能跑但慢，适合离线批处理而非实时 Agent。

结论：16GB 显存是 Agent 场景的实用分水岭，8GB 只够 7B，勉强可用但工具调用质量明显下降。

## 部署步骤

1. **Ollama 起步**：一条命令拉模型，自带 OpenAI 兼容端点，Agent 侧只改 `base_url` 和模型名，五分钟跑通；
2. **改上下文窗口**：Ollama 默认 `num_ctx` 很小，Agent 多轮对话会被静默截断——这是我踩的第一个大坑。显存允许的话直接拉到 16k 以上；
3. **进阶换 llama.cpp / LM Studio**：量化档位可选余地大，支持连续批处理，并发场景明显更好；
4. **压测**：模拟 Agent 连续 20 轮工具调用，记录 tokens/s 和显存曲线，确认不 OOM 再上真实任务。

## MCP / 工具调用的坑

- **量化太狠会坏 JSON**：Q4 以下生成工具参数时字段名拼错、引号错位概率明显上升。工具密集的任务至少用 Q5，最好 Q6；
- **小模型判断错“要不要调用”**：加一层规则路由，格式固定、低风险的操作直接模板化，不进模型；
- **流式输出 + 工具解析**在部分推理框架上有兼容问题，排查时先关流式，确认是解析问题还是生成问题；
- system prompt 里的工具 schema 要瘦身，冗余描述既耗上下文又增加小模型误读的概率。

## 稳定性

- 本地推理单轮 10 秒以上很常见，Agent 侧超时放宽到 120s 并加重试；
- 温墙降频是隐形杀手：机箱风道改善带来的收益，往往比换一个更小的模型更实在；
- 在日志里记每轮 tokens 和耗时，推理速度退化（比如显存泄漏、温度上墙）能第一时间发现。

## 可复用建议

- **大小模型组合**：7B 做摘要、分类、路由，14B 以上做主推理，延迟和资源都更均衡；
- **本地 + 云混合**：日常读文件、总结走本地，复杂多步推理走云，不必追求 100% 本地化；
- **配置固化**：用 docker-compose 或 systemd 管理推理服务，开机自启、崩溃自动拉起，别靠手动敲命令；
- 省下来的每一千 token 上下文，都是实打实的显存。

## 总结

本地部署不是要替代云端，而是把“高频、低复杂度、隐私敏感”的流量收回来。一台 16GB 显存的家用机，就能让 Agent 的大部分日常任务脱离 API 账单和限流。建议路径：先 Ollama 跑通，再逐步精细化量化档位和推理框架，不要一上来就折腾多卡集群——先把单机跑稳，价值已经够大。
