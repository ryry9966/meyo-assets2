## 背景

单 agent 串行干活有个天然瓶颈：任务一多，上下文越拉越长，又慢又贵。比如让主 agent "读完 8 个仓库的 README 并各自总结"，它只能一个个来，中间还容易丢细节。OpenClaw 的 subagent 机制给了另一条路：主 agent 把任务拆出去，每个 subagent 在独立 session 里跑，互不污染上下文，跑完把结果交回来。

## 问题

听起来简单，实际并行化后踩的坑比收益先到：subagent 不知道主对话里聊过什么；并行写同一批文件直接冲突；一轮下来 token 花费是串行的三倍；某个 subagent 卡死，整批任务被拖住。编排本身变成了新的工程问题。

## 做法

我的通用流程分四步：

1. **拆任务**：先判断任务是否"天然可并行"——每份子任务输入独立、输出独立、互不依赖。批量阅读、多源调研、逐文件审查是典型场景；需要共享状态或与用户来回确认的任务不要拆。
2. **写自包含 prompt**：subagent 看不到主对话，spawn 时必须把仓库路径、文件清单、输出格式、禁止事项全部写进 prompt。我的模板大致是：

```
任务：总结 <repo_path> 下的 README 与 docs/
输出：写入 /tmp/notes/<name>.md，返回"文件路径 + 一句话结论"
边界：只读，不修改任何文件；遇到歧义在结论里标注，不要猜
```

3. **控并发**：一次 spawn 3~5 个为宜。subagent 把结果落盘而不是塞进返回值，主 agent 只收路径和摘要，聚合阶段再按需读文件。
4. **收口**：主 agent 等全部完成后统一聚合；失败的单独特重试或降级为串行，不让一个失败拖死整批。

## 踩坑点

- **上下文隔离**：最大认知误区。subagent 不是"分身"，是新人，prompt 不自包含就会瞎猜。
- **写冲突**：两个 subagent 同时改同一个文件基本必炸。按模块/目录切分工作区，或者干脆先只让 subagent 做只读任务。
- **成本放大**：并行 N 个就是 N 份上下文在烧。小任务（3 个以内、单个几分钟能跑完）串行反而更省。
- **孤儿任务**：主 session 被打断时 subagent 可能还在跑，收口前先确认状态，别假设结果一定到齐。
- **返回值截断**：大结果别走返回值，落盘 + 传路径是更稳的约定。

## 可复用建议

- 先用只读类任务（调研、审查、总结）练手，验证流程后再放开写操作。
- 给每个 subagent 明确"禁止事项"，往往比写清"要做什么"更能防事故。
- 结果统一落盘到约定目录，天然形成可回溯的产物，出问题能复盘。
- 并发上限固化成自己的编排习惯，不要临时起意开 10 个。

## 总结

subagent 编排的本质不是"让 AI 更快"，而是用工程手段把可并行的独立子任务从主上下文里剥离出去：拆得干净、prompt 自包含、结果落盘、并发可控。做到这四点，多 agent 并行才从演示变成日常生产力；做不到，它就只是更贵、更乱的串行。
