技术圈每隔一段时间就会重演同一出戏：有人甩出一个惊人的倍数，社区先欢呼，再考古，最后翻车。这次的主角是 Rails 之父 DHH，据 36kr 等媒体报道，他分享了一份用 Rust 重写 Ruby 代码的 benchmark，宣称快了约 150 倍，随后被开发者逐行翻代码，评论区一度变成大型"挑刺"现场。今天不聊谁的面子，聊三个更有用的问题：这 150 倍可能怎么来的？Rust 到底快在哪？以及，普通人该怎么读"快 N 倍"这种数字。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/a785dddda82d524b.png)

## 一、事件速览：一条 benchmark 引发的代码考古

- 剧本很经典：DHH 给出同一任务的 Ruby 版与 Rust 版实现，晒出运行时间对比，结论指向"Rust 快约 150 倍"。
- 第一波评论是转发与赞叹；第二波画风突变，有人真的把代码 clone 下来逐行读。
- 从 Hacker News、Reddit 等社区的讨论看，质疑点集中在三处：
  1. **两边不完全等价**：数据结构、并发方式、I/O 策略并不一致，测的严格说不是同一个东西；
  2. **基线太朴素**：Ruby 侧接近"课本写法"，没开 YJIT，也没做批处理和热点优化；
  3. **归因错位**：加速主要来自算法与实现策略，却被叙事成"语言红利"。
- 所以群嘲的炮口其实不是 Rust，而是一个不严谨的对比，被包装成了科学结论。

## 二、"快 N 倍"是怎么翻车的：benchmark 四大经典坑

1. **Apples vs Oranges（不等价对比）**。一个版本逐行读文件加正则匹配，另一个 mmap 整块读入加 memchr 加查表；一个单线程，另一个多线程并行。150 倍里可能 100 倍来自算法，30 倍来自并行，真正属于语言本身的可能只剩零头。
2. **基线不调优**。对照组用最省事的写法跑一遍就上场。Ruby 3.x 开启 YJIT 后，Rails 类负载普遍有两位数百分比的正向提升；不开 YJIT 就开跑，相当于让对手穿钉鞋、自己穿拖鞋。
3. **没有预热与统计**。JIT 需要 warm-up，单次测量受 CPU 频率、缓存状态、后台进程影响。合格的 benchmark 是多次采样，报告中位数和方差，而不是跑一次截图了事。
4. **忽视 Amdahl 定律**。若 90% 的耗时集中在某段热点，把这段优化到无限快，整个程序上限也只有 10 倍。反过来，一个"只有"3 倍但覆盖面广的优化，端到端收益可能更实在。

一句话总结：跑一次就下结论的 benchmark，跟量一次体重就宣布减肥成功，是同一种科学精神。

## 三、Rust 为什么真的快：不是玄学，是设计取舍

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/323a4cc12d83ef3b.png)

先把话说公平：Rust 确实快，而且快得有清晰的工程理由。

- **没有 GC**。Rust 用所有权（ownership）和借用检查（borrow checker）在编译期确定每块内存的生命周期，运行时没有垃圾回收停顿。Ruby 一切皆对象、GC 全程护航，灵活和安全的代价就是这层运行时开销。
- **零成本抽象（zero-cost abstraction）**。迭代器、泛型经过编译期单态化，基本摊平成手写循环；没有动态派发税，也没有反射税。
- **内存布局编译期定死**。数据结构紧凑、缓存友好；Ruby 的每个值都是携带元信息的对象指针，内存访问模式天然吃亏。
- **并发模型**。Rust 的类型系统在编译期就拦截数据竞争，多线程可以放心铺开；Ruby（MRI）有 GVL，CPU 密集任务的多线程基本等于排队单线程，传统上靠多进程绕开。
- 但"快"不等于"更好的工程"。Ruby 换来的是开发速度、可读性和 Rails 这套成熟的业务生态，37signals 全家桶就是这套哲学最大的广告位。

## 四、大家笑的不是"快"，是"归因"

- DHH 本人也谈不上"反 Rust"。他一贯的选型逻辑是：业务层用开发效率最高的语言，等热路径真成了瓶颈，再针对性重写那一小块。Python 配 C 扩展、Node 配 Rust addon，走的都是同款思路。
- 翻车的点在叙事：把"我换了算法、换了并发策略"的收益讲成"语言快 150 倍"，相当于换了套新轮胎之后宣布"我这个人变快了"。
- 换个角度看，"翻代码"恰恰是开源社区最好的传统：结论必须能被第三方复现，数字必须经得起逐行审。这就是科学方法里"可复现性"的微缩版，审代码的对事不对人（好吧，多少有点对人，但主要还是对事）。

## 五、下次看到"快 N 倍"，先过这五道闸

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/1d4c2fe392e65f70.png)

1. **对比等价吗？** 两版的输入规模、算法、并发、I/O 是否一致？有没有一边偷偷加了额外优化？
2. **基线调优了吗？** 对照组开没开 JIT、编译优化（release build / -O3）？默认写法和用心写法差一个数量级很正常。
3. **测的是热点还是全链路？** micro-benchmark 的倍数，换算到端到端往往要大打折扣，因为语言本身可能只占整条链路耗时的一小部分。
4. **样本和方差在哪？** 跑了几次？给了中位数和误差吗？还是只截了最好看的一次？
5. **换到你的场景还剩多少？** 别人的 150 倍乘以你的热点占比，可能等于整体 1.3 倍。为这 1.3 倍值不值得重写、维护成本谁来背，才是真正的工程决策。

## 冷思考：三条带回家

1. **数字不构成证据，可复现的实验才构成。** 以后看到任何倍数，先找代码、环境和测试方法；找不到这三样的"快 N 倍"，默认当成广告处理。
2. **性能问题先 profiling，后换语言。** 真实系统里的大头通常是算法复杂度、I/O、N+1 查询和锁竞争。先用 profiler 找热点，多数时候根本不需要动语言。
3. **语言之争本质是取舍之争。** Rust 拿编译期复杂度换运行时性能，Ruby 拿运行时开销换开发敏捷；成熟团队的做法是组合拳——热路径换快工具，业务层保持好维护。真正值得群嘲的从来不是某门语言，而是不严谨的论证方式。
