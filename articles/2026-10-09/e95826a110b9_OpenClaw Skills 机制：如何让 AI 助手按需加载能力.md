## 背景

接了一堆 MCP server 和插件之后，最直观的变化是系统提示词变厚了。十几个工具定义常驻上下文，每个几十到上百 token，不管这次任务用不用得上，全都占着位置。副作用有两个：一是成本随能力数量线性上涨，二是工具选择准确率下降——可选项一多，模型挑错工具的概率明显上升。

## 问题

本质是"常驻加载"和"按需使用"之间的错配。某个能力可能一周只触发两三次，但它的完整说明、参数约定、注意事项却 100% 的时间都泡在上下文里。理想状态是：平时只留一行索引，真用到的时候再展开细节。

OpenClaw 的 Skills 机制就是围绕这个思路设计的：把能力封装成带元数据的目录，运行时按三级渐进加载。

## 做法

**1. 目录结构。** 一个 skill 就是一个文件夹，入口是带 frontmatter 的 `SKILL.md`：

```
skills/
  pdf-report/
    SKILL.md
    scripts/merge.py
  db-audit/
    SKILL.md
```

**2. 元数据先行。** frontmatter 里只写 `name` 和 `description`，启动时注入上下文的只有这两行，几十个 skill 合计也就几百 token：

```markdown
---
name: pdf-report
description: 当用户要求合并多份 PDF 并生成周报时使用。输入为文件路径列表，输出为合并后的报告文件。
---
```

**3. 正文按需读取。** 模型判断当前任务命中某个 skill 的 description 后，才会去读正文（步骤、约束、示例），这时才产生完整说明的 token 开销。

**4. 脚本最后加载。** 正文里引用的脚本、模板等资源，在真正执行那一步才运行。整体是三级结构：索引常驻 → 正文命中才载 → 资源执行才跑。

## 踩坑点

- **description 写得太泛或太窄。**"处理文档"这种描述什么都命中不了；只写一个极端场景又永远触发不到。建议写成函数签名的风格：触发动词 + 输入 + 输出。
- **把 skill 写成大而全的 prompt 文件。** 正文超过两三百行就该拆，把稳定流程沉淀成脚本，正文只留"什么时候调、怎么调"。
- **脚本依赖没声明。** skill 里调 Python 脚本，运行环境缺包直接报错。依赖和调用方式要写进正文，不要假设环境现成。
- **多个 skill 边界重叠。** 两个 skill 都会被"导出数据"触发，模型会犹豫甚至乱选。要么合并，要么在 description 里把边界词划清。
- **改了 skill 没验证。** 长会话里可能还是旧索引，改完建议开新会话，用真实任务回放一遍触发链路。

## 可复用建议

1. 一个 skill 只做一件事，命名用动词短语（`pdf-report`、`db-audit`），别起抽象名词。
2. description 当 API 文档写：什么时候用、吃什么、吐什么。
3. 上线前用 5–10 条历史真实任务回放，统计触发率和误触发率，比肉眼审 description 靠谱得多。
4. 高频 skill 正文控制在百行内；低频 skill 可以写细，反正只有触发才产生开销。
5. 和 MCP 工具分工：确定性接口走 MCP，流程性经验走 skill，别用 skill 把工具列表重新包装一遍。

## 总结

Skills 的核心价值，是把能力的上下文成本从"常驻"变成"按需"：索引常驻、正文命中才载、资源执行才跑。对 agent 来说，这意味着几十个能力可以共存而不撑爆上下文，同时每个能力的说明还能写得足够详细——两头的好处都拿到了。建议从把现有某个多步骤 SOP 改造成第一个 skill 开始，跑通三级加载链路，再逐步迁移其余能力。
