## 背景

OpenClaw 的 cron 任务本质是“定时唤醒的无人值守执行”：到点后 agent 拿着一段 instruction 独立跑完，全程没有用户在场。我最初把日常对话里效果不错的 prompt 直接搬进 cron，结果三天两头翻车——输出没人收到、“今天”算错日期、数据源空了它自己编一份。这篇记录踩坑后沉淀下来的写法。

## 问题：cron instruction 和聊天 prompt 是两种东西

对话里的 prompt 有三样隐性兜底：上下文记忆、随时追问、人肉纠错。cron 全都没有：

1. 没有会话上下文，“按老规矩处理”这类引用直接失效；
2. 没法澄清，instruction 有歧义，agent 就按自己的理解执行；
3. 没人看过程，失败是静默的，可能错一周才被发现。

所以核心认知是：**cron instruction 不是聊天消息，是交接文档**。执行者相当于一个每次醒来都失忆、还不许提问的新同事。

## 做法：五段式模板

我现在的 instruction 都按固定结构写，以一个日报任务为例：

```text
[时间] 执行时取系统当前日期，处理其前一天全天（UTC+8）数据
[取数] 用 xxx MCP 的 query 工具查昨天 00:00–24:00 的告警记录
[处理] 按 severity 分组统计，列出 Top 3
[输出] 在指定频道发 ≤10 行 Markdown 列表，首行给结论
[异常] 结果为空→发"昨日无数据"，禁止编造；工具失败→重试 1 次后报告失败
```

逐段说明：

- **时间锚点**：不写“今天”，写清相对哪个基准、哪个时区。服务器时区和你不一致是高频事故源。
- **数据来源与工具**：点名用哪个 MCP 工具/命令取数。“查一下最近的日志”这种写法等于把决定权交给模型。
- **处理步骤**：两三步说清，每步一个动作，别写成散文。
- **输出契约**：写到哪、什么格式、多长。没有目的地，agent 有时会“自言自语”然后直接结束。
- **异常分支**：最容易漏的一段。给模型一条明确的失败出口，比让它自由发挥好得多。

## 踩坑点

- **相对时间漂移**：23:50 调度的“日报”和 00:05 调度的“日报”，数据窗口差一整天。先想清楚调度时刻和数据窗口的关系。
- **编造数据**：数据源空了，模型倾向“凑一份像样的报告”。异常分支必须显式禁止。
- **重复执行**：cron 补跑或重跑时，推送类任务会重复发消息。要么在 instruction 里写幂等要求，要么把任务设计成先查后写的可重入形式。
- **一次塞太多**：一个 cron 干五件事，出问题都不知道哪步挂的。拆成多个小任务，各自可独立验证。

## 可复用建议

1. **先手动跑一遍再挂调度**：把 instruction 原样手动执行，确认输出符合预期再上 cron，头几天提高观察频率。
2. **指令带版本注释**：改了什么记一笔，方便回溯“上周为什么突然不对”。
3. **可观测类任务宁可多报不可静默**：“无数据”是有效输出，静默才是事故。
4. **频率克制**：不是所有事都要每小时跑，token 成本和频道噪音都会累积。

## 总结

写 cron instruction 的心智模型一句话：**假设执行者失忆、无法提问、结果直接交付**。时间锚死、来源写死、格式约定好、失败给出口——做到这四点，大多数“cron 跑着跑着就不对劲”的问题都能在上线前消灭。
