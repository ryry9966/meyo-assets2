## 背景

现在大多数 agent 仍是"问答式"的：你不发消息，它就永远静止。但 OpenClaw 这类常驻型助手，本质上是一个带工具调用能力的常驻进程，天然具备做 proactive 的基础——定时调度、MCP 工具、持久 memory 都是现成的。所以"主动办事"不是玄学，是一个可以拆解的工程问题：**事件从哪来、要不要做、做完怎么反馈**。

## 问题

纯被动的代价是上下文切换成本：你得记得去问它。但如果简单粗暴地加"主动性"，常见的翻车方式是通知骚扰、误操作、token 成本失控。核心矛盾在于：模型不知道哪些事"应该主动做"，这层判断必须由我们自己工程化地定义。

## 做法

**1. 先铺事件源**，三类就够用：

- 时间触发：cron/scheduler，比如每天早上汇总日历 + 待办；
- 外部事件：webhook、文件变更、邮件到达，通过 MCP tool 接入；
- 心跳：固定间隔（如每小时）跑一次轻量自检任务。

**2. 触发与决策分离**。事件只是触发器，模型收到的是精简上下文 + 明确任务描述。不要把全部历史对话塞进去。

**3. 建分级策略（policy）**：

- L0 只观察：汇总信息，发一条消息；
- L1 半自动：生成草稿/预案，等你确认；
- L2 自动执行：仅限白名单内的低风险操作。

**4. 执行要幂等**：每次主动任务带唯一 task_id，执行前查重，结果落盘。否则 cron 重复触发会导致重复发消息、重复下单。

**5. 反馈闭环**：主动做的事写进 memory，下次心跳知道上次干了什么，避免重复汇报。

## 踩坑点

- **心跳带全量上下文**：一天跑 24 次，token 直接爆。心跳必须用独立的精简 prompt。
- **让模型在定时任务里"自由发挥"**：它会扩大解释任务范围。任务描述要写成验收式——做什么、不做什么、输出什么格式。
- **时区错位**：cron 按服务器时区跑，你的日程按本地时区，汇总时间对不上。
- **通知不聚合**：一天 20 条消息，用户第一反应是把它关掉。
- **权限过大**：主动任务的 MCP tool 只给只读 + 白名单写权限，别复用交互会话的权限。

## 可复用建议

- 把"主动"做成三层模板：**trigger（事件）→ policy（分级）→ executor（幂等执行 + 通知聚合）**，每个新需求只填空。
- 新增主动行为先跑一周 L0 观察模式，统计误报率，再逐步升 L1/L2。
- 每条主动消息带来源标签（哪条规则触发的），排障和临时关停都靠它。
- 新触发器先 dry-run：只打印"本来会做什么"，不真执行。

## 总结

Proactive 不是让模型猜你想什么，而是把事件、策略、执行拆开，用分级授权和幂等控制风险。先小范围观察，再逐步放开权限——这样助手的"主动"才是帮你减负，而不是给你添乱。
