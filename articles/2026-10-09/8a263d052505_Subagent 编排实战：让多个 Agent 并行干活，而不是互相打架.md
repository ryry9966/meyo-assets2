## 背景

用 Agent 做自动化跑得久了，最明显的瓶颈往往不是模型能力，而是"一条线串行"的执行方式。比如让它审查 20 个模块、调研 5 个候选库、给一批文件补测试——主 Agent 只能一个个来，所有中间细节还会塞满主上下文，跑到后半程它对最初的目标已经"记不清"了。

Subagent 编排就是针对这个问题的：主 Agent 负责拆任务和汇总，每个子任务交给一个拥有独立上下文的 subagent，多个 subagent 并行执行，只把精炼后的结果交回来。

## 问题

不是所有任务都能并行。能拆给 subagent 的任务要满足两个条件：一是子任务之间相互独立，没有共享的可变状态；二是每个子任务的信息是自足的——subagent 看不到主对话，prompt 里必须把目标、输入、约束全部说清。

## 做法

以"给仓库里 15 个模块做依赖梳理"为例，我的流程：

1. **主 Agent 先拆解**：列出 15 个模块，按目录划成 4 组，每组互不重叠。
2. **给每个 subagent 写自足的 prompt**，固定结构：目标 / 输入（具体路径）/ 输出格式（JSON，字段固定，总长不超过 30 行）/ 禁止事项（不改文件、不越出目录）。
3. **控制并发**。同一时刻最多跑 3-4 个，避免触发限流，也方便看日志。
4. **主 Agent 收结果**：去重、交叉比对，冲突项单独拎出来人工确认，最后合成一份总表。

如果是写类任务（批量改文件），原则是 subagent 只产出 diff 或建议，落盘动作由主 Agent 串行执行——写操作不并行，是底线。

## 踩坑点

- **并发写同一批文件**。两个 subagent 同时编辑相邻文件，冲突几乎必然发生。按目录硬分区，或者干脆让 subagent 只读。
- **结果回灌爆上下文**。早期我让 subagent 返回"完整分析"，4 个结果回来主 Agent 就开始丢信息。后来强制规定返回格式和行数上限，问题消失。
- **隐性依赖**。拆任务时以为独立，实际模块 A 的结论影响模块 B 的判断，并行跑完发现要重做一半。拆之前先理依赖，有依赖的串成一串再并行。
- **subagent 幻觉没人查**。子结果错了，主 Agent 汇总时照单全收。汇总阶段加一道抽检或交叉验证，比事后排查省得多。

## 可复用建议

1. 先并行"读"，再考虑并行"写"。调研、审查、检索类任务收益最大、风险最低。
2. 把 subagent prompt 当接口来设计：输入、输出 schema、约束三段固定，写成模板复用。
3. 并发数从 2-3 起步，观察限流和成本再往上加。并行不免费，token 消耗基本按并发数翻倍。
4. 每个 subagent 的输入输出都落日志，排障时能直接回放是哪个分支出了问题。
5. 写任务保证幂等：同一 subagent 重跑两次结果应一致，否则重试机制会放大错误。

## 总结

Subagent 编排的核心不是"多个 AI 显得很强"，而是两件朴素的事：用独立上下文隔离中间噪音，用并行换扇出类任务的耗时。它对任务拆解和输出契约的要求，比单 Agent 对话高得多——拆得干净、契约清楚，并行才有意义；拆不干净，并行只是把混乱加速了。建议从只读类任务试起，先把 prompt 模板和日志建好，再逐步扩大到写场景。
