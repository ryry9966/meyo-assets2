## 背景

我们社区（几十人规模）每周有一类固定内容：整理本周的 issue、热门讨论和合并记录，发一篇周报帖。人工做，每次 40 分钟上下，还容易漏。于是决定用 OpenClaw 搭一个发帖机器人，目标不是“全自动运营”，而是把这 40 分钟压到 5 分钟的审核。

## 问题

最初的方案很直觉：一个 cron + 一个脚本，抓数据、丢给模型写、直接 POST 到社区 API。跑了一周暴露三类问题：

1. 模型会编造引用——链接指向不存在的 issue 号；
2. 任务重复触发——cron 间隔短于任务耗时，同一篇周报发了两次；
3. 失败不可见——某天抓取源挂了，脚本静默空转，没人发现。

根因是同一个：没有把“生成”和“发布”当作两个有边界的环节，也没有持久化状态。

## 做法

最终架构分四层，工具全部通过 MCP 接入 OpenClaw：

```
数据源（GitHub / 论坛 API / RSS）
        │  fetcher（MCP，只读）
        ▼
SQLite 状态库（content_hash + 状态机：drafted / reviewed / published / failed）
        │  OpenClaw Agent（仅产出草稿和结构化字段，不做任何写操作）
        ▼
规则校验 + 抽检门禁
        │  publisher（MCP，唯一持有写 token）
        ▼
社区发帖 API → 回写状态，失败告警
```

三个关键决策：

1. **写权限收敛到 publisher 一个工具。** Agent 提示词明确禁止生成 URL、禁止调用发布；正文里的所有链接由脚本从结构化字段回填，模型只负责“选哪些条目”。
2. **状态落库 + 幂等。** 每篇草稿按 `content_hash + 目标版块` 建唯一索引，发布前查重；调度侧加文件锁，防止重叠触发。
3. **灰度门禁。** 前两周所有草稿进人工队列，确认后才发；稳定后切自动发布，保留每日抽检和失败通知。

## 踩坑点

- **幻觉链接**：让模型“附上来源”，它编了个格式完全合理的 issue 号。修法如上——链接不经过模型的手。
- **重复发帖**：查重只是兜底，更根本的是把任务本身做成幂等：同样的输入，第二次运行不会产生第二个帖子。
- **429 风暴**：早期裸重试，一分钟打了 API 几十次。改成指数退避 + 单日配额上限。
- **输出格式漂移**：模型偶尔把 JSON 包进 markdown 代码块，下游解析崩。用 JSON Schema 校验，不通过就带着错误信息重生成，两次失败进人工队列，而不是静默丢弃。
- **密钥泄漏**：早期把 token 写在 MCP 配置文件里提交了仓库。轮换密钥、改环境变量注入，publisher 的配置单独存放。

## 可复用建议

1. 读写分离：只读工具随便给，写工具只留一个，且独立持有凭证。
2. 一切任务先设计幂等，再谈调度。
3. 把模型输出当不可信输入：强 Schema 校验，失败必须有兜底路径。
4. Prompt 进版本库、改动走 review——发帖机器人的“事故”多半是 prompt 改坏的。
5. 监控先行：宁可先做失败告警，再加新功能。

## 总结

机器人上线两个月，周报零漏发，人工介入总共三次（两次格式漂移、一次上游 API 变更）。回头看，价值最大的不是“AI 写得多好”，而是工具边界和状态设计让整个流程可控、可回滚。OpenClaw + MCP 适合这类场景的前提是：先想清楚哪些环节允许模型自由发挥、哪些必须收敛，再动手写 prompt。
