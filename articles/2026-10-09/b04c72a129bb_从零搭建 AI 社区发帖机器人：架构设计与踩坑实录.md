## 背景

OpenClaw-CN 社区的内容供给一直靠几个管理员手动维护：每周翻仓库更新、整理群内讨论、写成周报。结果就是断更常态化——大家都有正职，谁也没法保证稳定产出。上个月我们决定做一个发帖机器人：自动收集社区相关动态，生成符合社区文风的草稿，人工确认后发布。本文记录架构决策和实际踩过的坑。

## 核心问题：为什么不直接全自动？

第一版方案就是全自动定时发帖，写完自己先否掉了。三个硬伤：

1. **链接幻觉**：LLM 会"补全"看起来合理的仓库地址，实测十次能错三次；
2. **内容重复**：没有外部去重，同一话题换个措辞反复发；
3. **文风漂移**：跑几天后草稿越来越像通用营销号。

所以架构上做了一个关键取舍：**模型只负责草拟，事实必须来自工具抓取，发布前强制人工确认**。

## 架构与实现步骤

整体链路：`cron 调度 → Agent → MCP 工具抓取 → 草拟 → 人工审核 → 发布插件 → 状态落库`

**1. 调度层**：系统 cron 触发 OpenClaw agent，配合文件锁保证单实例运行。

**2. 工具层（MCP server）**：写了三个只读工具——RSS 抓取、GitHub releases 查询、站内搜索。全部返回结构化 JSON，每条数据附带原始 URL 和时间戳。

**3. 草拟层**：prompt 里固定文风模板 + 两三篇历史帖子做 few-shot。硬性要求每条事实都带来源 URL，且 URL 只能引用工具返回值。

**4. 审核层**：草稿推送到管理员 IM，回复"通过"或修改意见，通过后触发发布。

**5. 发布层**：调用论坛 API，以草稿内容 hash 作为幂等键，失败指数退避重试，状态写入 SQLite。

**6. 观测**：每次工具调用和发布结果都落日志，失败推送告警。

## 踩坑实录

**坑 1：链接幻觉防不住单靠 prompt。** 初期靠提示词约束，仍有漏网。最终解法是三重防线：prompt 约束 + 发布前 URL 域名白名单校验 + 只允许工具返回的原始 URL 进入正文。上线后再没出过坏链。

**坑 2：hash 去重形同虚设。** 标题被模型改写后 hash 完全对不上。改成"关键词集合 + 标题相似度"双重去重，历史记录全量入库，重复率降到接近零。

**坑 3：cron 重复触发。** 一次服务重启导致同一条内容发了两帖。加了文件锁还不够，最终靠幂等键兜底：同一个 key 只允许发布一次。

**坑 4：文风漂移是慢性的。** 两周后草稿质量明显下滑。把风格规则从"建议"改成"硬性模板"，few-shot 样本每月人工更新一次，才稳定下来。

**坑 5：MCP server 静默挂掉。** 工具挂了返回空结果，agent 拿到空数据照样"编"了一份草稿。现在的规则是：工具失败即流程失败，直接终止并告警，禁止模型自由发挥降级。

**坑 6：重试导致覆盖。** 发布失败重试时误用 create 接口造成重复帖，改成先查幂等键再决定 create 还是 patch。

## 可复用建议

- **先 human-in-the-loop，跑稳一个月再谈全自动**。审核成本远低于事故成本；
- **一切事实来自工具调用**，模型只做组织和转述；
- **所有写操作带幂等键**，这一条能挡住大部分重复发布事故；
- **状态放数据库，不要放对话上下文里**，上下文会被压缩和截断；
- **工具失败即终止**，宁可少发一期，不发错的内容。

## 总结

机器人上线六周，发布 30+ 帖，单帖人工审核耗时从约 40 分钟降到 5 分钟，第三周之后零幻觉链接事故。最大的收获不是省时间，而是把"内容质量"从主观判断变成了可工程化约束的对象。下一步计划把审核意见回流成 few-shot 样本，持续提升草稿一次通过率。欢迎在社区交流你们Agent 自动化实践中的类似问题。
