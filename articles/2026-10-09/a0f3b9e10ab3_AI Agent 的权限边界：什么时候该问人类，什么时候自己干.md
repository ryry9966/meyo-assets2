## 背景

Agent 接上 MCP 之后，能力面就从"聊天"扩展到了"读写文件、跑 shell、调外部 API"。自动化收益确实大，但代价是：每一次工具调用，都在消耗你对它的信任额度。权限边界不是可选项，而是第一周就该设计的东西。

## 问题

实践中常见两种翻车方式：

1. **全自动型**：agent 顺手 `rm -rf`、往生产库写数据、给客户群发邮件。模型不缺执行力，缺的是"这件事该不该由我决定"的意识。
2. **全请示型**：每一步都弹审批，人退化成"点击确定机器"。审批疲劳之后开始无脑全批，边界形同虚设。

本质问题只有一个：没有按**可逆性 × 影响面**做分级，而是把所有操作一锅端。

## 做法

**第一步：盘点工具，两个维度打标。**
- 可逆性：能否一条命令回滚？
- 影响面：只影响本机 / 影响项目 / 影响外部世界（别人的收件箱、生产环境、账单）。

**第二步：分三档。**
- **T0 自动执行**：只读、本地、可逆。如 grep、读配置、跑测试。
- **T1 自动但留痕**：写本地文件、开分支提 PR。动作前先展示 diff，写完可一键回滚。
- **T2 必须审批**：删除、发消息/邮件、花钱、部署生产、任何跨出本机边界的调用。

**第三步：把审批做得便宜且信息充分。** 审批界面给的是一条命令、一个 diff、一个目标地址，而不是整屏日志。人 3 秒能判断，才不会疲劳。

**第四步：沉淀为权限清单，跟着仓库版本化。** 每个 MCP 工具标上 T0/T1/T2，新人接手一眼能看懂边界在哪，改边界走 review。

**第五步：定期升降级。** 出事故就降级，稳定跑一个季度可以试点升级。权限清单是活的，不是定完就归档。

## 踩坑点

1. **审批疲劳**：T2 设太多，人开始机械点"允许"。宁可少设几个真正关键的闸门。
2. **打包审批**：agent 一次性申请"执行整个计划"。必须逐项确认——打包批准等于把决定权交了回去。
3. **凭证范围过大**：直接挂主账号 token。应该给 agent 单独的最小权限凭证，出事可单独吊销。
4. **假可逆**：移进回收站不等于删除；外部 API 一旦调用就回不去了。凡是过了本机边界，一律按不可逆处理。
5. **审批上下文不足**：只问"可以吗"却不给 diff 和影响面，人的判断质量反而低于 agent，问了个寂寞。

## 可复用建议

- 一句话判断法：**一条命令回滚不了的事，先问。**
- 三个必问词：**花钱、对外、删除**。命中任意一个，走 T2。
- 频率高 + 风险低的操作进 allowlist，别让 agent 反复请示同一件事。
- 所有工具调用落日志，审批记录单独存：事后要能复盘"当时谁批的、基于什么信息"。

## 总结

权限边界不是信任问题，是接口设计问题。好的边界让 agent 在 90% 的日常操作里完全自主，在剩下 10% 的不可逆操作前，把决策权干净地交还给人——给足上下文，然后等一个明确的是/否。做到这一点，自动化才敢放心放量。
