## 背景

跑过一段时间 Agent + MCP 的团队都有类似体感：权限给少了，Agent 是个每三步来问一次的实习生；权限给多了，它半夜把测试环境的表清了，还会一本正经地写一份“自查报告”解释为什么这么做。“什么时候该问人”看起来像哲学问题，实际上必须落成配置和代码。

## 问题

多数团队的回答是“重要的事要问”。但“重要”没法写进策略引擎。真正能落地判断的是两个可度量的维度：

- **可逆性**：操作能否撤销？`git revert` 能撤，没备份的 `DELETE` 撤不了。
- **影响面**：波及的是一个文件、一个分支，还是生产数据、真实资金、对外关系？

## 做法与步骤

按这两个维度把工具分成四档，策略跟着档位走：

1. **档 0（只读、可逆）**：搜索、读文件、查 schema。直接放行，不要问。
2. **档 1（可逆写、影响面小）**：改分支、写草稿、动测试环境。自动执行 + 全量日志，事后可审计、可回滚。
3. **档 2（不可逆或影响面大）**：删数据、合主干、花真钱、对外发消息。必须问人。
4. **档 3（凭证与权限变更）**：永远不自动做，人来执行或逐步确认。

具体落地几条：

- 把“问人”做成**带 schema 的工具**，而不是自由文本。要求 Agent 给出：要做什么、影响哪些资源、备选方案、默认选项，人回一个编号即可。
- 校验放在**工具层（MCP 网关或插件宿主）**，不要只写在 system prompt 里。prompt 会被注入，网关不会。
- 每个工具设额度：单位时间调用上限、金额上限、diff 行数上限，超限自动升级为“问人”。
- 高危操作先 **dry-run**，展示将要执行的命令或 diff，确认后才真跑。

## 踩坑点

- **问得太多等于没问**。人被问十次后会无脑点“允许”，确认疲劳比不问更危险。宁可收紧档 0/1 的范围，也要保住弹确认框时的严肃性。
- **开放式提问没有意义**。“我可以继续吗？”人无法评估；展示 diff 和选项才有意义。
- **幂等没做好，可逆也会变不可逆**：重试逻辑把“创建一条记录”跑成三条，回滚就不再是回滚。
- **审批不留痕**：谁在何时批了什么必须落库，否则出事没法复盘。
- **环境没有在配置层隔离**：Agent 拿同一个 profile 两边跑，测试的授权泄漏到生产。

## 可复用建议

新接一个 MCP 工具时先做分类：它读还是写？动了什么资源？出错最坏损失是什么？按答案放进档位，再决定要不要确认钩子。上线顺序永远是：只读 → 可逆写 → 高危，每一步观察一两周日志再放开。把“问人”当产品功能打磨：问题短、选项清、默认对。

## 总结

权限边界的本质不是信任问题，而是把“哪些自动做、哪些必须有人签字”变成配置和代码。可逆且影响面小的自动跑，不可逆或影响面大的必须问；问的方式要结构化，审批要留痕。Agent 的自主性是逐步放宽出来的，不是一次设计出来的——每一次调大权限，都应该对应一段你亲自 review 过的日志。
