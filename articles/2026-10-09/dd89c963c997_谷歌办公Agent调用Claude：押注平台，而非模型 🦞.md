大家原本都在等 Gemini 4，结果谷歌先交出的答卷是另一份：一套面向企业办公场景的 Agent 产品，并且明确支持接入第三方模型——包括 Anthropic 的 Claude。谷歌的产品调用竞争对手的模型，表面上有点微妙，拆开看却是一条清晰的产业信号：企业级 AI 的竞争重心，正在从“谁的模型更强”上移到“谁的编排层更好用”。这篇文章把新闻事实、技术原理和选型建议一次讲透。

## 一、先对齐事实：这次到底发布了什么

- **产品形态**：一套面向企业办公的 Agent 平台，定位是“员工的数字同事”——读企业文档、调内部系统、跑审批和流程自动化，而不是又一个聊天窗口。
- **关键能力**：平台支持多模型接入。除了自家的 Gemini，也能把特定子任务交给 Claude 等第三方模型完成。
- **并非急转弯**：Google Cloud 的 Vertex AI Model Garden 很早就上架了 Claude；今年发布的 Agent Development Kit（ADK）明确宣称 model-agnostic；A2A（Agent2Agent）协议也是为了让不同框架的 Agent 互联互通。这次更像是把“平台不绑定单一模型”从开发者能力产品化成了前台卖点。
- **别过度解读**：Gemini 依然是默认主力，Claude 是“特定任务下的可选项”，不是替代关系。

## 二、技术上，“Agent 调用 Claude”是怎么发生的

一个企业 Agent 的典型分层长这样：

1. **感知层**：接邮件、日历、文档、IM 消息——Workspace 生态的主场；
2. **大脑（LLM）**：负责理解、规划、生成，这是“可插拔”的部分；
3. **工具层（tool use / function calling）**：查数据库、写表格、发起审批、调内部 API；
4. **编排层（orchestrator）**：决定哪个子任务交给哪个模型和工具，处理重试、超时与 fallback。

所谓“调用 Claude”，本质是编排层在模型抽象上做了统一接口（很多团队直接采用 OpenAI-compatible 格式作为事实标准）：请求携带 prompt、上下文和工具定义，发往不同 provider 的 endpoint（Vertex API、Bedrock、Anthropic API），再以统一的 tool call 格式返回。对上层业务来说，大脑换型号，手脚和记忆不动。

为什么要多模型？一个典型的路由策略：

- 代码生成、长文档精修、复杂指令跟随 → Claude（业界公认的强项是 coding 和 instruction following）；
- 多模态理解、超长上下文、与 Workspace 数据深度整合、大批量低成本任务 → Gemini；
- 某家限流或服务抖动 → 自动切到备用模型。

不同模型每百万 token 的价格差可达数倍，路由本身就是省钱手段。这和后端架构里配多级缓存、降级策略是同一个思路——没有哪个工程师会把全部流量押在一个上游上。

## 三、商业逻辑：谷歌为什么敢把对手的模型装进自家产品

这步棋在云计算行业早有先例，一点都不新鲜：

- **卖水的不挑水种**：AWS 一边卖 Nvidia GPU，一边推自研芯片；Azure 上 OpenAI 模型和第三方模型并排卖。客户不会因为“能用竞品”而走，反而因为“什么都有”而留下。
- **企业买的不只是模型**：权限体系、数据不出域、审计日志、SLA、与现有 OA/CRM 的集成，才是企业客户真正付费的部分。模型是推理引擎，数据和工作流才是资产。
- **分发即护城河**：Workspace 背后是数以十亿计的用户账号和海量企业文档。Agent 一旦长在权限和文档体系之上，迁移成本极高。
- **内部竞争倒逼进步**：平台上跑着 Claude，Gemini 团队的基准压力是实打实的，对产品端是好事。

打个比方：这像五星级酒店允许你自带主厨，但灶台、供应链和账单都归酒店管。谷歌不是认怂，而是把竞争上移到平台层——模型你随便选，租约签在我这里。

## 四、对企业用户：把新闻变成一张选型清单

如果你正在给公司挑 Agent 平台，这条新闻提供了一个很实用的检验维度：**模型可替换性**。建议按下面几条过一遍：

1. 模型层是否可插拔：换模型要不要改业务代码？有没有统一的 gateway 抽象？
2. 路由是否可控：能不能按任务类型、成本预算、延迟要求配置“谁干谁的活”？
3. 评测体系是否开放：平台能不能跑你自己的 eval set，而不是只看厂商发布会上的 benchmark？
4. 数据与权限边界：prompt 和企业文档会不会出域？审计粒度够不够细？
5. 协议与生态：是否支持 MCP（Model Context Protocol）、能否对接 A2A 这类开放标准，避免被单一框架锁死？

一个常见的坑必须提醒：**prompt 在不同模型之间不能无损迁移**。同一段 system prompt，在 A 模型上 90 分，换到 B 模型可能只剩 70 分。多模型不等于免费随便换，每次切换都需要重新调优和评测。

## 五、冷思考：这条新闻没说的部分

- **“支持调用”不等于“默认好用”**。路由策略做得差，多模型只是多一份账单。体验的胜负手在编排细节：上下文怎么切、工具怎么注册、失败怎么兜底。
- **模型差距在缩小，平台差距在拉开**。头部模型在同一档任务上的能力差，已经小于工具链、数据接入和流程整合上的差。
- **对开发者的直接启示**：从今天起把 LLM 调用收进抽象层，别让业务代码直接依赖某一家的 SDK。未来换模型应该像换电池，而不是换发动机。

## 收尾：三条可以马上执行的建议

1. **加一层 model gateway**：统一收口 prompt 管理、计费、限流和 fallback，业务代码只认接口、不认厂商；
2. **建一套任务级评测集**：用真实业务样本决定路由策略，别拿发布会 PPT 当选型依据；
3. **把工具和数据接入沉淀为资产**：MCP server、内部 API 封装、知识库索引，这些跨模型通用的东西，才是长期回报最高的投入。

模型会一直迭代，平台会一直卷，但“把企业自己的数据和流程接进 AI”这件事的价值，只会越来越贵。
