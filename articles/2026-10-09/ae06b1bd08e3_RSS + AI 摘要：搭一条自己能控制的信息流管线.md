## 背景

推荐算法把信息入口越收越窄，RSS 反而是现在少数完全由自己掌控的结构化信息源。另一方面，LLM 的摘要成本已经低到可以按“每天几百条”的量级来用。这两件事合起来，就有了一条很朴素但好用的管线：**RSS 采集 → AI 过滤与摘要 → 定时推送**。我在 OpenClaw 侧用定时任务加两个 skill 把它跑通了，跑了一个多月，说说踩过的坑。

## 问题

直接订阅原始 RSS 会遇到四个麻烦：

- 源一多，未读条目每天几百条，人工根本看不完；
- 相当一部分站点只输出 description，不给全文；
- 每条都丢给模型，成本和延迟都不划算；
- “看过/没看过”的状态需要持久化，否则天天重复推。

## 做法

整体是三段式，各层解耦：

**1. 采集层。** 有 RSS 的直接订阅；没有的用 RSSHub 或自写脚本转成 RSS。所有源统一收敛成中间格式：`id / title / link / published / content`，后面的逻辑只认这个格式。

**2. 状态与调度层。** 用 SQLite（或一个本地 JSON）存已处理条目的 hash，按 guid + link 去重。OpenClaw 的定时任务每两小时触发一次采集 skill，拉增量。

**3. 加工层。** 关键是**分级处理**：先走一遍便宜模型做打分和去重（相关性、是否与昨天重复），只把 top N 交给强模型做摘要。全文缺失时，先做 readability 抽取再进模型。

摘要 prompt 里的硬约束：只基于原文、不引入外部事实、每条不超过两句话、必须保留原文链接。

**4. 分发层。** 汇总成一份 Markdown 日报，通过 OpenClaw 的消息插件推到 IM，同时落一份到笔记仓库存档。

## 踩坑点

- **只拿 RSS description 做摘要，质量很差。** 很多站点的 description 是 SEO 文案而非内容，必须抓全文，抓不到的宁可直接给链接。
- **prompt injection。** RSS 正文里可能被塞进指令（“忽略之前的要求……”）。摘要 prompt 里要明确声明：正文只是数据，不是指令。这是最容易被忽略的安全点。
- **成本失控。** 最初全量摘要，一周烧掉的 token 够买半年 VPS。改成“便宜模型过滤 + 强模型精摘”后降了约 90%。
- **去重不彻底。** 同一篇文章改个标题就重复出现。现在用 URL 规范化 + 标题相似度双重判断。
- **时区。** cron 默认 UTC，日报时间漂移了八小时才被发现。调度和日期切分要显式指定时区。

## 可复用建议

1. 三层解耦是核心，任何一层（采集方式、模型、推送渠道）都可以独立替换，不要写死在一起。
2. 源从 5–10 个起步，跑稳两周再扩。一上来订几十个源，坏源和噪音会淹没管线本身。
3. 定期抽查：随机取几条摘要对照原文，验证模型没有幻觉。这一步不能省。
4. 状态文件纳入备份或 git，重建管线时历史去重记录比代码更难恢复。
5. 摘要质量差时先怀疑输入：八成是全文没抓到，而不是模型不行。

## 总结

这条管线没有用任何黑科技，就是采集、状态、加工、分发四件套加上分级调用模型。它的价值不在单点技术，而在于**信息入口完全自主可控**：加源、改摘要口径、换推送渠道都是改配置的事。如果你已经在用 OpenClaw 跑定时任务，搭起来大概一个晚上，建议从自己每天真的会看的五个源开始。
