## 背景

Agent 每次会话都是冷启动。系统提示词决定了它“是谁”，但它不知道“你是谁”。在 OpenClaw 的 workspace 里，`SOUL.md` 定义人格，`AGENTS.md` 约束行为，而 `USER.md` 是留给“用户是谁”的位置——很多人装完框架后这一栏是空的。结果是每开一个新会话都要自我介绍一遍：我用什么语言、代码什么风格、手上在做什么项目。

## 问题

没有 USER.md 的直接代价有三个：

1. **重复输入上下文**：同样的自我介绍贴几十遍，token 浪费且容易遗漏关键信息。
2. **建议不贴身**：Agent 默认推荐它最熟悉的方案，而不是你技术栈里的方案。你用 PostgreSQL，它给你 MySQL 的建表语句。
3. **风格漂移**：昨天明确要求结论先行，今天新会话又开始长篇铺垫。

## 做法

在 workspace 根目录建 `USER.md`（`~/.openclaw/workspace/USER.md`），每次会话自动注入上下文。关键原则是**结构化写，不写散文**：

```markdown
# User Profile
## 身份
- 称呼：老周
- 时区/工作时段：UTC+8，晚间活跃
## 环境
- OS / Shell：macOS / zsh
- 主力语言：Python 3.12, Go 1.22
- 数据库：PostgreSQL，不用 ORM
## 偏好
- 回答风格：结论先行，代码优先于解释
- 代码风格：4 空格缩进，函数不超过 40 行
## 边界
- 不要主动重构我未要求改动的代码
## 当前项目（易过期，定期清理）
- xxx 数据管道重构，预计 6 月结束
```

两个分层原则：**稳定事实**（身份、环境、长期偏好）进 USER.md；**易变状态**（项目进度、临时决定）放 `MEMORY.md` 或日报，别混在一起。另外把它纳入 git 管理，改动有据可查。

## 踩坑点

1. **写太长**。300 行的 USER.md 每次会话全量注入，稀释关键信息还烧 token。控制在一屏以内，60 行是合理上限。
2. **放敏感信息**。密钥、密码、内网地址绝不写进去——它会被注入每一次会话上下文，任何能读 workspace 的工具链都可能触达。
3. **信息过期**。换了技术栈没更新，Agent 会一直按旧栈回答。设个每月提醒审一遍，过期的“当前项目”直接删。
4. **多处定义互相打架**。偏好只写一处，USER.md 和 AGENTS.md 各管各的，出现“一边要求简洁、一边要求详尽”的矛盾时，Agent 的行为不可预测。
5. **写主观评价而非事实**。“我是新手”不如“熟悉 Python 基础，未用过 asyncio”，后者才是可执行的上下文。

## 可复用建议

- 把 USER.md 当作**自己的 README** 来维护：像 review 代码一样 review 它，删掉不再成立的条目比新增更重要。
- 团队内共享一份空模板，每人填自己的，降低上手成本。
- 让 Agent 参与维护：定期在会话里让它 diff 最近对话中暴露的新信息（新装的依赖、明确的否决偏好），提议更新条目，你确认后写入。写权限留在人手上，Agent 只做提案。
- 每次排障发现“Agent 答非所问”时，先检查是不是 USER.md 缺了对应的背景条目——十次里有六次是上下文问题，不是模型问题。

## 总结

USER.md 是成本最低、收益最直接的 Agent 调优手段之一：十几行 Markdown，换来每次会话零自我介绍、回答贴着真实环境走。Agent 的上限往往不取决于模型，而取决于你喂给它的上下文质量。先把这十行写满，再谈别的优化。
