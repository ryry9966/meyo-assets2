## 背景

Agent 自动化跑了一段时间后，你会发现问题的大头不在模型：任务真正挂掉，多数时候是外部依赖——LLM 供应商限流、MCP 工具背后的第三方 API 超时、某个 SaaS 接口半夜开始 5xx。传统服务里这是运维问题，但在 Agent 场景里，错误会进入推理循环，处理不好会被放大成重试风暴、token 白烧，甚至模型编造结果硬撑。

## 三种常见翻车方式

1. **异常裸抛给模型**：工具层直接把报错丢进上下文，模型自己决定重试。每轮重试都烧一次 LLM 调用，还容易陷入"换个说法再试一次"的死循环。
2. **无脑代码重试**：没有退避和抖动，下游刚恢复就被并发请求二次打死。
3. **把 200 当成功**：不少 API 挂的时候返回 200 + 错误 JSON 或截断数据，Agent 拿着垃圾继续推理，错得更远。

## 建议的分层做法

**第一步：工具层做错误分类。** 分三类——可重试（429 / 502 / 503 / 超时）、不可重试（401 / 403 / 参数错误）、语义可疑（200 但 schema 校验失败）。在 MCP 插件里包一层统一 client，别让裸异常透出。

**第二步：重试下沉到代码层。** 指数退避 + 随机抖动，上限 3 次左右，并设总预算（比如单次调用总耗时不超过 30s）。重试是便宜操作，不该花模型的钱。

**第三步：给 Agent 返回结构化错误。** 不要丢堆栈，返回类似 `{error_type, retryable, retry_after, hint}` 的结构。只有 `retryable=false` 时，模型才会正确地跳过或换路径，而不是反复撞墙。

**第四步：熔断与降级。** 连续 N 次失败后熔断，走降级路径：备用供应商、缓存快照，或明确告知"这一步失败，任务跳过该部分继续"。降级输出要打标，不能假装是正常结果。

**第五步：检查点续跑。** 长任务在关键工具调用后落盘状态，恢复时从断点继续，而不是从头再来一遍。

## 踩坑点

- 把重试策略写进 system prompt 让模型自己处理：实测几乎必然循环，模型对"放弃"这事非常抗拒。
- 只有熔断没有半开探测：熔断之后永不恢复，得留少量探测流量试活。
- 401 直接重试：token 过期应先刷新再试，否则三次重试全是浪费。
- 超时二选一陷阱：单调用超时太长拖死整个 loop，太短杀掉慢但正常的请求；deadline 要沿调用链传递，别每层各设各的。
- 日志只记"调用失败"：不记错误类别和耗时，事后排障基本靠猜。

## 可复用建议

- 所有外部调用走同一个封装：timeout + retry(3, exp+jitter) + 熔断 + 结构化错误，写一次到处用。
- 给关键工具维护降级预案：备用 API、缓存策略、显式跳过，三选一，别出事时临时想。
- 在 staging 做故障演练：直接干掉依赖接口，看 Agent 是优雅降级还是原地爆炸。
- 区分两种重试：传输层重试（便宜，代码里做）和任务层重试（贵，Agent 决策、对用户可见）。

## 总结

外部 API 挂掉不是异常，是常态。恢复能力的主体应该在工具层用代码解决，Agent 层只负责接收诚实的结构化信号，做"值不值得继续"的经济判断。把重试、熔断、降级做成基础设施，Agent 的可靠性才能从看运气变成看设计。
