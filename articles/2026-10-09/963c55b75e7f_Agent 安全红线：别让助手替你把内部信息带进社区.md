## 背景

最近社区里用 OpenClaw + MCP 搭自动化流程的人明显多了。Agent 能读本地文件、调工具、带着长上下文回答问题，效率确实高。但随之而来一个不太显眼的风险：我们在向社区求助、分享配置或导出"技能包"时，Agent 的上下文和产物里可能夹带了不该出去的东西——API key、内网域名、客户名、内部工作流细节。这类泄露不像越权攻击那样有戏剧性，往往就是你随手贴的一段日志。

## 问题：三条典型泄露路径

1. **求助时贴上下文。** 让 Agent"总结一下报错原因，我去社区问问"，输出里带着 Authorization 头、内部服务的绝对路径、真实的业务参数。
2. **分享配置和技能。** MCP 配置、skill 文件、memory 摘要里常有内网 hostname、真实路径和示例 payload——而这些 payload 往往来自真实流量。
3. **读到的内容被复述。** Agent 工作区里有 `.env`、SSH config、内部笔记，你问一个宽泛问题，它会把相关内容组织进答案；之后这段答案被你复制到公开频道。

## 做法：四步收紧

**1. 先做资产盘点。** 列出 Agent 能碰到的一切：workspace 目录、MCP server 清单、每个 server 开了哪些 tool、memory 文件位置。不确定的权限等于敞开的门。

**2. 最小化可达面。** 给 Agent 独立工作目录；秘密全部走环境变量注入，而不是躺在工作区文件里；MCP 只开必需的 tool，文件读取限制在项目子目录。内部笔记、运维文档移出可达范围。

**3. 建立分享前的脱敏闸门。** 任何要出社区的东西——日志、配置、skill、截图——先过一遍固定检查：搜 `sk-`、`Bearer`、`token`、内网域名后缀、真实客户名。更省事的办法是维护一个"演示工作区"专门用来复现问题，里面只有合成数据。

**4. 内外上下文分离。** 内部开发用的 Agent profile 和帮社区排查用的 profile 分开，不共用 memory 和 skill 包。内部那个读过敏感文件，它的记忆摘要就不该被二次分发。

## 踩坑点

- **日志是最常见的泄露源。** 堆栈和请求头里的内网信息，比配置文件里的更隐蔽。
- **分享的 skill 里嵌着"真实示例"。** 写示例时务必用合成数据，别图省事直接贴生产报文。
- **反向风险：** 直接导入社区里别人分享的 MCP 配置或 skill，等于接受对方的权限申请和指令内容。先审再用。
- **上下文摘要会"翻旧账"。** 新会话里 Agent 可能引用早期记忆中的内部信息，对外输出前自己扫一眼。

## 可复用建议

- 把 Agent 产物当代码评审对待：分享前跑 checklist，就像 PR 前跑 lint。
- 给出站动作加确认门槛：凡涉及 webhook、POST、上传类 tool，一律人工确认，顺带缓解一部分 prompt injection 风险。
- 定期轮换演示环境的密钥，防止历史数据沉底后被翻出来。

## 总结

Agent 没有权限意识，它只会忠实组织它能看到的东西。红线不在模型侧，而在两处：我们给它的可达面，和我们分享前的那个检查动作。盘点、最小化、脱敏、分离——四个词，实施成本很低，但能挡住绝大多数"顺手泄密"。欢迎大家补充自己踩过的坑。
