## 背景

大多数人用 Agent 的方式是问答式：你发消息，它回复，然后沉寂。OpenClaw 里有个常被忽略的机制——heartbeat（心跳）。Agent 会按固定间隔自动醒来，读取工作区根目录下的 `HEARTBEAT.md`，判断有没有该做的事，做完再睡回去。这个文件就是让 Agent 从「被动应答」转向「主动巡逻」的入口。

## 问题

纯被动模式有三个实际痛点：

1. **周期性任务全靠人记**。检查收件箱、盯服务报错、整理每日摘要，每次都要手动触发一遍。
2. **上下文断裂**。昨天让它「关注某个服务的异常」，今天它已经忘了。
3. **Agent 大部分时间空转**，实例跑着，利用率却很低。

## 做法

核心三步：

**1. 在工作区根目录建 HEARTBEAT.md**

用 checklist 形式写任务，关键是把触发条件写死，不留模糊空间：

```markdown
# HEARTBEAT

## Every beat
- 检查收件箱，只报告需要我决策的邮件，其余跳过

## Daily（09:00 前后一次）
- 汇总昨日 git 提交与未关闭 issue，发到 #daily-digest

## Only when asked
- 不想让它自动执行的敏感操作写在这里
```

**2. 配置心跳间隔**

默认间隔偏保守，可通过 `HEARTBEAT_INTERVAL` 调整。建议从 30 分钟起步，观察一周再调。

**3. 赋予「沉默权」**

在文件里明确写：没有值得报告的事，直接静默结束，不要发消息。这一条直接决定体验好坏。

## 踩坑点

- **任务写得太模糊**。「帮我关注下服务器」这种写法，Agent 每次心跳都要花 token 纠结要不要报告，最后要么乱报要么不报。改成可判定条件：错误日志超过 3 条且持续 10 分钟才通知。
- **没有专属汇报出口**。默认它往主对话发心跳消息，很快刷屏。单开一个低优先级频道，重要事项再升级到主会话。
- **常驻任务堆太多**。每次心跳是一次完整推理调用，10 个任务意味着每天几百次 LLM 调用。先跑 2-3 个，验证价值再加。
- **把精确调度塞进心跳**。需要「每天 8:55 准时」的任务应该用 cron 触发；心跳适合「每小时看一眼」这类模糊周期任务，两者别混用。
- **改完文件以为立即生效**。要等下一个心跳周期才会读到，调试时手动触发一次验证最省事。

## 可复用建议

- 把 `HEARTBEAT.md` 纳入 git，任务变更可追溯、可回滚。
- 用三段式结构管理优先级：Every beat / Daily / Only when asked，语义清晰，Agent 也容易遵守。
- 心跳例行检查如果支持单独配模型，用便宜的小模型跑，需要深思考再切主模型。
- 新任务先设成「只记日志不通知」，观察几天输出质量，再放开汇报权限。

## 总结

`HEARTBEAT.md` 本质是一份写给 Agent 的值班手册：它不增加智能，只是把「什么时候醒、醒来看什么、看完怎么办」写清楚。主动性上限完全取决于任务质量——条件越可判定，行为越稳定。建议从一个任务开始，比如每天早上整理一次待办，跑顺了再扩展。让 Agent 真正省时间的，从来不是它答得多快，而是它开始在你开口之前把事做了。
