## 背景

AGENTS.md 是一个逐渐成为事实标准的约定：用一份 Markdown 文件，向在这个目录里干活的 AI agent 说明“这里怎么运作”。README 写给人看，AGENTS.md 写给模型看。在 OpenClaw 里，工作空间根目录（默认 `~/.openclaw/workspace`）下的 AGENTS.md 会在每次会话启动时注入系统上下文，相当于 agent 开工前必读的操作规程。

## 问题

大部分人第一次部署 OpenClaw 时，AGENTS.md 基本是模板原样，甚至只有几句口号。典型症状：

- 每次会话行为不一致，同一件事今天这样做明天那样做；
- 往 MEMORY.md 里塞流水账，真正重要的事实被淹没；
- 定时任务失败时反复打扰你，或者反过来，该汇报的时候沉默；
- 在群聊和私聊里用同一套回复风格；
- 你已经纠正过十次的问题，它继续犯。

这些大多不是模型能力问题，而是缺一份明确的“岗位说明书”。

## 做法

我的 AGENTS.md 按这个骨架维护（精简示例）：

```markdown
# 工作空间约定

## 会话规则
- 每次会话先读 MEMORY.md 和当日 daily note，再决定是否提问

## 记忆纪律
- 长期事实写 MEMORY.md，带日期；过程性内容不写

## 渠道行为
- Telegram：默认简短，技术问题可展开
- 定时任务：失败只记录，连续 3 次失败才提醒

## 安全边界
- 不主动执行删除类 shell 命令；涉及支付和对外发送一律先确认
```

写作顺序建议：先让 agent “裸奔”跑一两周，把它反复让你不爽的行为逐条记下来，再固化成规则。AGENTS.md 本质是行为补丁的累积，不是一次性设计出来的。

## 踩坑点

1. **写太长。** 整个文件进上下文，300 行规则模型反而抓不住重点。控制在 100 行以内，每条必须可执行。
2. **规则打架。** 比如 SOUL.md 写“语气轻松”，AGENTS.md 又要求“输出严谨”，模型只能随机选边。跨文件的约定要明确优先级。
3. **写成给人看的 README。** 项目架构、安装步骤对 agent 无意义，它要的是“遇到 X 情况执行 Y”。
4. **只增不删。** 每次出问题加一条，半年后互相矛盾。建议每月清理一次，删掉已内化为默认行为的条目。

## 可复用建议

- 每条规则用“条件 + 动作”句式，触发条件可判定，避免“尽量”“适当”这类形容词。
- 和 MEMORY.md 分工：AGENTS.md 管“怎么干活”，MEMORY.md 管“知道什么”。
- 放进 git 管理，规则变更留提交记录，方便回溯“哪次改动导致行为变化”。
- 接入 MCP 工具后，把使用偏好也写进去：同类工具哪个优先、哪些禁止调用。
- 规则改完后，在同一会话里让 agent 复述一遍它的理解，歧义当场暴露。

## 总结

AGENTS.md 的价值不在模板，而在于把人与 agent 的磨合过程显式化、可版本化。它是一份活文档，随使用持续演化。写得克制、具体、可验证，agent 行为的稳定性会有肉眼可见的提升——这比换模型或调参数便宜得多，也常被低估。
