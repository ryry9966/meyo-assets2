## 背景

OpenClaw 的长期记忆本质上是一堆 Markdown 文件：MEMORY.md 做索引，memory/ 目录下是日记式笔记。`memory_recall` 工具负责在对话时按查询捞出相关片段、塞回上下文。检索质量直接决定 agent 是"记得你上个月说过的话"，还是"每次都现编"。

默认检索是全文匹配。社区里反复有人问：要不要上向量检索？我把过去半年沉淀的约 400 条记忆笔记拿来实测了一次。

## 问题

全文搜索有两类典型失败：

1. **换说法找不到。** 当时记的是"用户偏好深色主题"，三个月后 agent 查"界面配色习惯"，关键词零命中。
2. **中英混杂。** 记忆里写的是 "MCP server 超时重试"，查询却是"工具调用失败怎么办"，同样搜不到。

但语义搜索不是免费午餐：多一个 embedding 依赖、索引要维护、小语料下优势未必明显。值不值得换？用数据回答。

## 做法

**第一步，建评测集。** 从历史会话挑 40 个"当时确实有对应记忆"的查询，人工标注源笔记。指标用 hit@3（前 3 条结果里有没有正确片段）。

**第二步，实现三条检索路径：**

- 全文：SQLite FTS5，trigram 分词；
- 语义：bge-small-zh-v1.5 本地 embedding，按标题/空行切块，向量存 sqlite-vec，余弦相似度；
- 混合：两路各取 top 10，RRF（倒数排名融合）合并。

**第三步，跑分。** 结果如下（我的语料，仅供参考）：

| 方案 | hit@3 | 备注 |
|---|---|---|
| FTS5 trigram | 55% | 关键词命中时极准 |
| 语义 | 72% | 换说法场景明显更好 |
| 混合 RRF | 84% | 互补效应显著 |

一个反直觉的发现：纯术语型查询（如 "cron job 重叠"）全文反而赢——用户提问时往往原样复现术语。

## 踩坑点

1. **FTS5 中文分词**：默认 unicode61 把整句中文当一个 token，等于搜不到，必须换 trigram 或外挂 jieba。高频坑。
2. **切块粒度**：按固定 token 数切会把一条记忆拦腰斩断，按 Markdown 标题/空行切块后召回明显更稳。
3. **索引失效**：手改了 memory/*.md 但向量库没更新，agent 一直召回旧内容。用 mtime+hash 做增量比对，启动时跑一次即可。
4. **语义分数没有统一阈值**：不同查询的相似度分布差异很大，硬编码 0.75 之类的阈值时灵时不灵。混合方案靠相对排名绕开了这个问题。

## 可复用建议

- 语料少于 200 条时先别上向量。FTS5 + 记忆文件规范写 front matter（日期、标签），够用。
- 给记忆定格式约定：一行一个事实、保留原始术语。这会**同时**提升两种检索的命中率。
- 混合检索是当前性价比最高的落点，RRF 十几行代码，无需调参。
- 把每次 memory_recall 的查询与命中结果落日志，定期扫一遍未命中的查询——它们就是你下一批评测集，闭环就这么建立。

## 总结

这不是二选一的问题：中文语料 + 换说法查询多，语义收益真实存在；术语型查询，全文更准；生产环境，直接上混合。动手前先建 30~50 条的评测集——记忆检索的体感差异很容易被"看起来更智能"带偏，数据比直觉可靠。
