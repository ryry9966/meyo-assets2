# 自动化日报生成：从原始日志到结构化报告的流水线

## 背景

我手上跑着十几个服务，日志散在文件、journald 和 docker logs 里。每天早上花二十分钟翻日志写日报，重复且容易漏。于是用 OpenClaw 的 cron 调度加 Agent，配一个 webhook 插件，搭了一条“日志进、日报出”的流水线，跑了两周，稳定可用。

## 问题

直接让 Agent 读日志写日报，会撞上三个硬问题：

1. **量大**：一天日志几十 MB，塞不进上下文，模型也只能“选择性失明”；
2. **噪声高**：同一个错误每分钟打几十条，真正的信号被淹没；
3. **格式漂移**：模型每次输出的段落结构不一样，没法归档对比，也没法做下游解析。

结论：模型只适合做摘要这一步，流水线的主体必须是确定性的工程。

## 做法

分四步，前三步是脚本，最后一步才交给模型：

**1. 收集裁剪（脚本）**。cron 每天 07:30 拉取过去 24 小时日志，按 level 过滤（保留 ERROR/WARN 和关键路径 INFO），再按 `(级别, 关键词)` 去重聚合计数。几十 MB 压成 3~5 KB 的原料，比如“DB timeout 出现 4217 次，首次 03:12，末次 06:40”。

**2. 组装 prompt（脚本）**。摘要原料 + 运行时注入的日期 + 固定输出 schema，交给 OpenClaw Agent。schema 钉死四段：异常、变更、容量指标、待办。

**3. 校验重试（脚本）**。返回结果先解析校验，字段缺失就带报错重试一次；再失败就降级——把摘要原料原文发出去，附一句“自动摘要失败”。

**4. 分发归档（插件）**。报告推到群频道，同时写一份带日期的 markdown 进归档目录，供检索和逐日对比。

整条链路以日期为 key 做幂等，同一天重跑不会发重复消息。

## 踩坑点

- **别把原始日志直接喂给模型**。token 爆炸是小事，更糟的是模型会“礼貌地”把噪声也总结进来，甚至补出日志里不存在的原因。先做确定性裁剪，永远值得。
- **去重要在喂模型之前**。聚合计数后把“出现 N 次”作为事实交给它，而不是让它自己数。
- **输出格式要在 prompt 里钉死**。要求纯 JSON、不要包裹代码块标记，解析失败时回传报错重试。实测一次重试能解决九成格式问题。
- **时区与切日点**。cron 时区、“过去 24 小时”还是“自然日”，要和团队日报习惯对齐，否则跨天任务会被算错日子。我们最后用“昨天 00:00–23:59”的自然日口径。
- **静默失败最危险**。流水线挂掉比不出日报更糟，没人会主动发现。失败分支也要推送，哪怕是降级内容。
- **日期不要写死在 prompt 模板里**，运行时注入，否则模板复用必出错。

## 可复用建议

- 记住一个比例：**九分工程，一分模型**。裁剪、去重、校验、分发都是普通代码，模型只负责最后一段自然语言摘要。
- 把输出 schema 当接口设计，日报结构改动只动 prompt 模板，不动流水线代码。
- 日志源做成小 adapter（文件 / docker / journald 各一个几十行的脚本），新机器接入只是加一个 adapter。
- 归档的 markdown 别偷懒，它是后面做周报和月度趋势的原料。

## 总结

整条流水线代码不到两百行，难点不在模型，而在边角的工程细节：裁剪策略、失败降级、幂等和时区。跑顺之后，每天早上的日报是稳定、可比对的，我从“翻日志的人”变成了“看日报的人”。如果你也在用 OpenClaw 做自动化，建议先拿单一日志源跑通全链路，再逐步扩源——先让它可靠，再让它丰富。
