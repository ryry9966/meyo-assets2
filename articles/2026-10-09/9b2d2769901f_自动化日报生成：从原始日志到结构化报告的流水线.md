## 背景

我在一台家用服务器上长期跑着 OpenClaw，日常有几类日志散落各处：gateway 的运行日志、定时任务的执行记录、几个自写小工具的输出。以前每晚花十几分钟翻日志写日报，坚持两周就放弃了。后来干脆交给流水线：定时触发 agent，产出固定格式的日报，推到我的聊天频道。跑了一个多月基本稳定，把方案整理出来。

## 问题

最初的想法很简单：把当天日志全塞给模型，让它"总结一下"。实际跑起来有三个致命问题：

1. **上下文装不下**。一天的 debug 级日志轻松几十万行，直接喂要么截断要么爆上下文，成本也难看。
2. **输出不稳定**。今天是 bullet list，明天写成小作文，关键数字有时凭空出现——让模型自己去数日志行数，基本等于编。
3. **噪音淹没信号**。下游服务抖一下，重试风暴刷出几千行同质错误，真正的那条配置变更反而被淹没。

结论：不能让 LLM 直接面对原始日志，中间必须有一层确定性处理。

## 做法

整条流水线拆成五步，原则是**代码管数据，模型管语言**：

1. **采集**。crontab 每天固定时间触发一次 agent 会话（也可以用 OpenClaw 的定时任务能力），脚本先把各来源日志按时间窗口切好，落到工作目录。
2. **预处理**。这一步全部用脚本，不经过模型：按级别过滤、按错误指纹去重并计数、只保留 Top N 异常和关键指标的变化量。产出一个紧凑的 JSON 摘要，通常能压到几百行以内。
3. **结构化提取**。把摘要交给 agent，prompt 里强制按预定义 JSON schema 输出（字段固定：异常事件、指标、待办、风险提示）。外面包一层校验，schema 不通过就带错误信息重试一次。
4. **渲染**。模板填充。数字、日期、计数全部由上一步的结构化数据注入，模型不参与任何计算，产出固定章节顺序的 Markdown。
5. **投递与归档**。报告推送到指定频道，同时按日期归档成 markdown 文件。历史报告本身就是可检索数据，之后随时可以问 agent "上周三报过什么"。

后来把这套东西封装成了一个 skill，既被定时触发，也能随时手动喊一句"来今天的日报"，复用同一条链路。

## 踩坑点

- **时区切割**。日志是 UTC，我的"一天"是本地时区，最早的版本总把前一天晚上的事件算进当天。解决：采集入口统一转时区，窗口显式定义为 [00:00, 24:00)。
- **去重不能只看字符串**。同一条错误的堆栈里时间戳每行都不同。按"错误模板 + 来源"做指纹，保留计数。
- **静默失败**。cron 挂了的表现是"今天没收到日报"，很容易被当成"今天没事"。加了兜底：流水线任何阶段失败都发一条明确的失败消息，而不是什么都不发。
- **格式漂移**。让模型"直接输出 Markdown 日报"坚持不了三天，章节顺序就开始漂。拆成"输出 JSON"和"渲染"两步之后就稳了。

## 可复用建议

- **中间产物全部落盘**。每个阶段都有文件可查，排障时能一眼定位问题出在采集、摘要还是渲染。
- **schema 先行**。日报的 JSON schema 定义一次，周报、月报只是渲染模板不同。
- **别让模型算数**。所有数字在脚本侧算好注入，模型只负责把结构化数据写成人话。
- **先跑通一个日志源一个模板再扩**。我第一版只接了 gateway 日志，能稳定出报告之后才加别的来源。

## 总结

这个项目的价值不在"AI 写日报"这个噱头，而在流水线本身：LLM 只是其中负责"把结构化数据翻译成可读文本"的一环。确定性的部分越厚，整条链路越稳。如果你也有散落的日志和一个每天要手动写的总结，建议从"脚本预处理 + schema 约束输出 + 模板渲染"这三件套起步，一天就能搭出第一版。
