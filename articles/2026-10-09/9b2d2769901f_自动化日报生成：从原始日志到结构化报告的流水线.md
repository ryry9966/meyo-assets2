## 背景

我们团队每天要出一份日报：线上异常、CI 失败、主要仓库的提交动态、值班工单。以前是值班同学手动翻日志、看面板、复制粘贴，拼成一段话发到群里。问题不在“写”，而在“凑料”——每天花 20 到 40 分钟，格式全凭个人习惯，隔几天根本没法对比。

## 问题

拆开看，日报其实是两件事：

1. **数据工作**：从多个异构来源（服务日志、CI 结果、git log、工单系统）提取当天的事实；
2. **叙述工作**：把事实组织成人能读的报告。

痛点在第一部分纯属重复劳动。而常见的错误做法是让 LLM 直接吞原始日志“帮我总结”——日志量大、噪音多、token 成本高，模型还会把没把握的数字写得煞有介事。

## 做法

核心原则一句话：**数字由代码算，Agent 只负责叙述**。流水线分四步，整体跑在 OpenClaw 的定时任务里：

**1. 采集与归一化。** 各来源接独立采集脚本（部分通过 MCP server 暴露成工具），统一输出为带 schema 的 JSON：时间戳、来源、级别、类别、原文摘要。上游格式各异没关系，归一化层兜底。

**2. 聚合与统计。** 纯代码逻辑：按服务/错误类型分组计数，与昨日、上周同日做差值，标出新增告警。产出一份“事实清单”，是报告的唯一数据源。

**3. Agent 生成叙述。** 把事实清单喂给 Agent，套一份固定模板（概览 / 异常明细 / 趋势对比 / 待跟进）填充解读文字。Prompt 里明确：不得引入清单之外的数字，无话可说的段落直接省略。

**4. 投递与归档。** 报告经 webhook 推送到群，中间产物（归一化 JSON + 最终 Markdown）按日期归档入库，便于回溯和 diff。

## 踩坑点

- **日志格式漂移**：上游改了一行格式，解析器静默失败，日报连续三天“一切正常”。后来加校验：解析成功率低于阈值就先告警，报告里显式标注“数据不完整”，绝不静默降级。
- **时区**：统计窗口起初用了 UTC，跨天事件被切进两份报告。统一固定时区，并把窗口起止写进报告元数据。
- **Agent 编数字**：早期版本让模型“参考日志补充细节”，出现过错报的接口名。收紧为只允许引用事实清单后消失。
- **重复投递**：调度重试导致日报发两遍。给每次运行生成 run_id，投递前查重，任务改为幂等。
- **无事可报**：空报告比没报告更困惑。定义了“静默日”输出：一句话说明无异常，附关键指标基线。

## 可复用建议

- **中间产物落盘**：归一化 JSON 是最有价值的资产，排障、回填、换模板都靠它。
- **解析率也是指标**：要监控流水线本身，别只监控业务。
- **模板数据驱动**：报告结构写成配置而非写死在 prompt 里，改版不动代码。
- **先跑通再接 Agent**：先用纯脚本验证两周，确认数据可信，再让 Agent 介入叙述层。

## 总结

流水线跑了一个多月，日报从“每天人工 30 分钟”变成“早上八点半自动出现在群里”，更重要的变化是格式稳定、可对比、可回溯。经验可压缩成一句：确定性的事交给代码，不确定性的叙述交给 Agent，并用 schema 把两者隔开。Agent 在这类场景的正确位置，是最后一公里的写作者，而不是全程的数据处理者。
