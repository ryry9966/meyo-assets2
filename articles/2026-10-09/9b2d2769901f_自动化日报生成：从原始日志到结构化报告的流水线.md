## 背景

团队里总有几类"每天必须有人写"的日报：服务运行摘要、告警汇总、任务进度。以前的做法是人肉翻日志、抄数字、贴群里，费时且口径不一。最近我把这件事改造成一条跑在 OpenClaw 上的自动化流水线，核心思路只有一句：**数字让脚本算，话让模型说**。

## 问题

把原始日志直接喂给 Agent 有三个硬伤：

1. **体量**。一天的 access log 加应用日志动辄几十万行，远超上下文，截断后模型看到的只是碎片。
2. **幻觉**。让 LLM 自己从日志里"数"错误次数、算成功率，数字基本不可信。
3. **口径**。每个人手写日报时对"异常"的定义不同，模型自由发挥只会放大这个问题。

## 做法

流水线分四段，Agent 只参与第三段：

**1. 采集层（cron + 采集脚本）**
系统 cron 每天 00:30 触发，拉取前一天自然日 00:00–24:00 的日志切片落盘。调度不依赖 Agent——采集必须是纯脚本，可独立重跑。

**2. 聚合层（脚本，无模型参与）**
用 jq/grep/awk 把原始日志压成一份结构化 JSON：请求总量、错误码分布、Top 慢接口、告警条目、部署记录。这份 JSON 是唯一的"事实源"，字段固定并做 schema 校验。百万行日志在这一层被压成 2KB。

**3. 报告层（OpenClaw Agent + MCP 工具）**
系统提示绑定固定模板（概览 / 异常 / 变更 / 待办），Agent 通过 MCP 工具读取聚合 JSON。提示里明确要求：所有数字必须原样引用 JSON 字段，禁止推算、禁止补全，缺数据就写"数据缺失"。temperature 设 0。

**4. 分发层（webhook 插件）**
渲染成 Markdown 推到群 webhook，按 `report-YYYY-MM-DD` 的 key 归档。推送前做幂等检查，当天已有记录就跳过。

## 踩坑点

- **别用"当前时间往前 24h"做窗口**。凌晨跑批天然错位，老老实实用自然日边界，并在脚本里固化时区，服务器是 UTC 就显式转东八区。
- **迟到的日志**。写入有延迟，00:10 采集会漏尾巴。我们把时间推迟到 00:30，报告末尾标注"统计截至时刻"。
- **静默失败最危险**。流水线挂了没人发现，因为"今天没日报"看起来像正常。加了一条反向告警：00:35 归档文件还不存在就推送故障通知。
- **模型自作主张补数字**。第一版提示词太宽松，模型把"错误率上升"脑补成了具体百分比。改成"数字只能引用 JSON，禁止计算"后才干净。

## 可复用建议

- 把"聚合"和"叙述"彻底分开：LLM 永远不接触原始日志，只接触聚合产物。
- 模板即合同：schema 定字段，模板定小节，模型只有填空的自由度。
- 定时流水线必须有"缺席告警"，它比成功通知更重要。
- 归档用带日期的幂等 key，方便重跑和追溯。

## 总结

整条流水线花了一个下午，其中聚合脚本占七成工作量。模型在这里的价值不是"分析日志"，而是把结构化数据翻译成人愿意读的段落——边界划清楚，日报就稳了。上线后连续两周，产出没再需要人工修正。
