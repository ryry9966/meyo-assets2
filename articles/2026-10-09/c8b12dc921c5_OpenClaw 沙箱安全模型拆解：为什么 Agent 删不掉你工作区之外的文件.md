## 背景

OpenClaw 的 Agent 默认握着一整套工具：exec、文件读写、浏览器、各类 MCP 服务。模型一旦误解指令——“帮我清理一下项目”被理解成 `rm -rf`，甚至执行了从网页里读来的一条命令——没有隔离的话，就是宿主机事故。OpenClaw 的设计前提很朴素：**模型迟早会错，问题只在于错误发生时的爆炸半径有多大。**

## 问题

跑长任务自动化时，最怕的不是模型答错，而是它“答错还动手”。典型场景：让 Agent 重构目录结构，它把备份文件夹当垃圾清了；或者它在自主浏览时复制了一条危险命令直接执行。宿主机 shell 没有撤销键，事后能做的只剩恢复备份——前提是备份没被它一起删掉。

## 做法

1. **分层沙箱。** `sandbox.mode` 设为 `"all"`（保守场景至少 `"non-main"`），非主会话的所有工具调用都在一次性 Docker 容器里执行。容器内是一个最小镜像环境，不是你的系统。
2. **挂载收敛。** 默认只把 workspace 以读写方式挂进容器，宿主机其它路径对 Agent 不存在。参考资料目录用只读挂载。别图省事挂 `$HOME`。
3. **工具门控。** 对 exec 这类高危工具在 tool policy 里设 `ask`/`deny`；需要落回宿主机执行的操作走 elevated 通道，默认人工确认，并配 allowlist 限制触发来源。
4. **网络与资源限制。** 容器不开 privileged，限制内存/CPU，出网走代理并配域名白名单，避免沙箱里的进程拿着 env 里的 key 乱访问。
5. **工作区可回滚。** workspace 放 git，任务前自动 commit。沙箱挡住“外面”，git 挡住“里面”——Agent 在工作区内删文件，也只是可恢复的工作树变更。

## 踩坑点

- `"non-main"` 模式下**主会话仍在宿主机上跑**，别误以为全隔离；高价值机器直接上 `"all"`。
- 把 `/var/run/docker.sock` 挂进容器，等于把宿主机 root 交出去——这是“配了沙箱但白配”的最常见原因。
- 为了修网络问题随手关沙箱，之后忘了开。出网不通先查 DNS 和代理配置。
- workspace 是最后一层爆炸半径，密钥、`.env`、备份别放在里面。
- 第三方 MCP server 的进程边界要单独审视：它跑在哪个命名空间、拿到什么凭证，沙箱不会自动替你想清楚。

## 可复用建议

- 按“模型必然犯错”做设计，而不是按“这次应该没事”。
- 每接入一个新工具或 MCP，问三个问题：它能碰到哪些路径？能出网到哪里？操作失败能不能回滚？
- 高危操作宁可多一次人工确认，也别追求全程无人值守的顺滑。
- 沙箱策略会随功能迭代漂移，定期审计 tool policy 和挂载配置，当作例行维护。

## 总结

OpenClaw 不靠“相信模型会小心”来保证安全，而是靠边界：容器隔离进程、挂载收敛可见范围、工具门控拦下高危动作、git 兜底可逆性。沙箱的价值不是让 Agent 不犯错，而是**让错误发生时你还有得选**。这才是它敢把 Agent 接进真实文件系统的底气。
