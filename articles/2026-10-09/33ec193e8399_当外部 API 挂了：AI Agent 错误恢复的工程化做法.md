## 背景

做 Agent 自动化的人迟早会撞上同一件事：模型本身没坏，但它调用的外部 API 挂了。LLM 供应商限流、MCP 工具超时、第三方服务 5xx——这类故障不是异常，是日常。本地脚本挂了大不了重跑，但 Agent 挂在长任务中间时状态是碎的：有的步骤已完成，有的执行了一半，直接重跑可能出事。

## 问题在哪

实践中最常见的三种翻车方式：

1. **重试引发副作用重复**。写操作（下单、发通知、写库）没有幂等保护，超时后重试，同一件事做了两遍。
2. **不可重试错误进了重试循环**。401、参数错误这类致命错误被当成临时故障，Agent 反复重试直到烧完 token。
3. **错误被吞掉**。工具层捕获异常后返回空字符串，模型以为操作成功了，带着错误状态继续往下走，产出整体不可信。

## 怎么做

一套可以直接落地的分层做法：

**第一步：错误分类。** 所有工具调用异常先归为两类——可重试（429、503、超时、网络抖动）和致命（401/403、400、业务规则拒绝）。分类标准写死在工具层，不要交给模型现场判断。

**第二步：有限退避重试。** 指数退避加随机抖动，同时设总时长预算。关键是“有限”二字：

```yaml
retry:
  max_attempts: 4
  backoff: exponential   # 1s 2s 4s 8s + jitter
  timeout_per_call: 20s
  fatal_status: [400, 401, 403]
  idempotency_key: required_for_write
```

**第三步：幂等键。** 所有写操作带唯一请求键，服务端去重或本地记录已完成操作 ID。这是自动重试写操作的安全前提，没这个就不要自动重试。

**第四步：熔断与降级。** 连续失败超过阈值就熔断该工具，走降级阶梯：备用 API → 缓存结果 → 跳过可选步骤 → 升级人工。降级产物必须打上标记，不能假装是正常结果。

**第五步：断点恢复。** 长任务把每步状态持久化（checkpoint），故障恢复时从最后成功的步骤继续，而不是从零重跑。

**第六步：结构化错误回传。** 把 `{error_type, retryable, attempts}` 这类结构化信息返回给模型，允许它重规划，但重规划次数也要有硬预算——模型自己同样会陷入“再试一次”的循环。

## 踩坑点

- **超时设太长**：单次调用 120s 超时会卡死整个循环，工具级超时建议 10~30s，靠重试覆盖长尾。
- **对限流 API 高频重试**：同参数打过去只会让配额更紧张，收到 429 必须读 Retry-After。
- **分不清“API 挂了”还是“我的 prompt 把它搞挂了”**：先手动 curl 验证服务端是否正常，再排查 Agent 侧。
- **降级静默**：备用路径的输出如果不标注来源，事后根本查不清数据为什么不对。

## 可复用建议

1. 给所有工具调用套统一错误信封：`{ok, error_type, retryable, attempts, latency_ms}`，上层逻辑只看这个结构。
2. 每个 tool 一份独立的重试策略配置（次数、退避、超时），不搞全局一刀切。
3. 留存失败样本：原始请求、响应、时间戳，保证能离线回放。
4. 批量任务前先做一次轻量健康检查调用，别让 500 个子任务死在同一个故障上。

## 总结

Agent 的错误恢复本质上不是写 try/catch，而是预算管理：时间预算、次数预算、成本预算，每一层都花在刀刃上。核心顺序是——先分类、再有限重试、写操作必须幂等、挂了就降级、状态可恢复。做到这五点，外部 API 挂掉时你的 Agent 才是“减速”，而不是“翻车”。
