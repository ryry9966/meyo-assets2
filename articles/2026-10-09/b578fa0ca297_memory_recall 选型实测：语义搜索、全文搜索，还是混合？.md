## 背景

OpenClaw 的 memory_recall 是助手"回看过去"的关键工具：会话里出现"我们之前怎么处理的"，agent 就会调用它从 memory 目录捞相关片段。我的 memory 是几百条按日期组织的 markdown 笔记，量不大，但检索方案的坑踩了不少。这篇记录一次认真的对比：语义搜索（embedding + 向量召回）vs 全文搜索（SQLite FTS5）。

## 问题

两条路各有明显短板：

- **全文搜索**对精确标识符很稳——错误码、路径、服务名，一搜一个准；但换了说法就抓瞎：记忆里写的是"发版失败后回滚"，agent 查的是"上次部署出问题怎么办"，直接搜不到。
- **语义搜索**反之，换了说法能兜住，但会被"字面相似、语义无关"的结果干扰，对标识符类内容的召回也经常不准。

真正的问题不是二选一，而是：在我的数据分布下，各自错在哪、混合方案值不值得多维护一条 embedding 管线。

## 做法

1. **先固定评测集。** 从日志里挑了 58 条真实 recall 查询，人工标注每条应命中的片段。判定标准是"召回后 agent 是否真的用上了"，不是"看起来相关"。
2. **跑 FTS5 基线。** 零依赖、离线、毫秒级响应。
3. **加语义链路。** 记忆按标题切块（300–500 token，标题进 metadata），本地模型出向量，查询取 top-8 余弦召回。
4. **混合排序。** 两路各取 top-8，用 RRF（reciprocal rank fusion）合并，再叠一个 recency 加权——三个月前的记录和昨天的，权重不该一样。
5. 对比三组：FTS / 纯语义 / 混合，看 top-5 命中率。

结果（我的数据，仅供参考）：FTS 基线约 61%，纯语义约 68%，混合约 84%。提升主要来自那批"换说法 + 带错误码"并存的查询——恰好是日常最常见的一类。

## 踩坑点

- **FTS5 默认 tokenizer 对中文基本不可用**，整句会被切成一个 token，换 unicode61 也没用。要么用 trigram，要么入库前先分词，否则中文全文搜索等于摆设。
- **agent 发起的查询往往又长又啰嗦**，对 FTS 很不友好。在 memory_recall 的 tool description 里明确要求"查询用 3–8 个关键词"，命中率肉眼可见地提升，零代码改动。
- **切块切在话题中间，两路检索一起遭殃。** 宁可块大一点，也别硬按固定长度切。
- **本地小模型对中英混合记忆的向量质量波动大。** 评测集留下，否则每次换模型都是盲调。

## 可复用建议

- 别从向量开始。FTS + 好的切块 + 查询改写，很多时候就够了，先有基线再谈升级。
- memory 保持纯 markdown 存储，向量只作为索引。这样检索引擎随时可换，数据不被绑死。
- 混合检索用 RRF 就够，不必上重型 reranker；recency 权重比想象中重要。
- 评测集是唯一可信的东西。没有它，每次调参都是凭感觉。

## 总结

语义 vs 全文不是站队问题。标识符密集、查询偏关键词的 memory，FTS 是性价比之王；查询措辞多变的场景，语义兜底明显；两路用 RRF 合并，几乎总是优于单路。更重要的结论是：先把评测集建起来，再决定要不要为十几个百分点的提升多维护一条 embedding 管线。
