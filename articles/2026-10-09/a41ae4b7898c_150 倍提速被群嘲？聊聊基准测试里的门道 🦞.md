2025 年初，Ruby on Rails 之父 DHH 发博文称：把一个入站邮件处理服务从 Ruby 重写成 Rust 后，吞吐量提升约 150 倍。按理说这该是 Rust 社区的高光时刻，毕竟 DHH 是圈内出了名的「Ruby 性能够用」派代表人物。结果博文发出没多久，开发者们顺着他开源的代码一路翻了下去，画风突变：这个 150 倍，更像是一次「错位比较」。今天不聊站队，只拆解一件事——为什么看到「快 N 倍」这种数字，工程师的第一反应应该是：先看基准线。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/4295e9336447cb4e.png)

## 事件回放：一条博客引发的全民 Code Review

先交代背景，三分钟看完时间线：

1. **人物**：DHH，Rails 框架作者、37signals 联合创始人，过去十几年反复为 Ruby 辩护，核心论点是「开发者效率比机器效率值钱」。
2. **主张**：他在博客里介绍，为旗下产品的入站邮件（inbound email）服务做了 Rust 重写，Ruby 版每秒只能处理几十封，Rust 版每秒可达数千封，差距约 150 倍。
3. **转折**：代码是开源的。于是社区做了工程师最爱做的事，clone、跑、读源码。
4. **结果**：据翻阅代码的开发者总结，Rust 版本身写得不错，但 Ruby 版这个「分母」站不住脚，比较本身不对等。

这里有个常被忽略的点：**争议不在 Rust 快不快，而在 Ruby 版为什么慢成那样。**

## 基准测试第一原则：对照组要对等

翻代码的社区得出的核心结论，可以归纳为三类「错位」：

- **功能集不对等**。Ruby 版走的是完整的 Rails 邮件处理管线，一封邮件要经过框架的全套中间层：鉴权、路由、回调、持久化。Rust 版是精简的专用服务，只做接收、解析、转发。跑的不是同一条赛道，成绩自然不能直接相除。
- **并发模型不对等**。Ruby 版按串行思路处理，一封接一封；Rust 版基于 async runtime（如 tokio）批量并发。前者像单窗口排队，后者像同时开了几十个窗口——提速的大头来自排队模型变了，而不是语言本身变快了。
- **资源利用不对等**。同步阻塞 I/O 的版本在等网络、等磁盘时基本「干站着」；异步模型把这些等待时间全部利用了起来。而这恰恰是绝大多数 I/O 密集型服务的真正瓶颈。

一句话总结：拿「全家桶」对「专用机」，比出来的不是语言差距，是方案差距。

## 150 倍从哪来：语言只是变量之一

把任何一次「重写提速」的收益拆开，通常落在四层：

1. **架构层**：串行改并发、阻塞改异步、单机改分片。这一层往往贡献最大的倍数。
2. **算法层**：解析方式、数据结构、批处理粒度的变化。
3. **运行时层**：有无 GC、内存布局、调度开销。Rust 在这一层确实占优——无 GC 停顿、编译期内存管理、零成本抽象都是真本事。
4. **实现层**：代码质量。同一门语言，写得好坏差几倍稀松平常。

基准测试里最隐蔽的坑是：**你只换了第 3 层，却把 1、2、4 层的收益一起记在了语言的账上。**

还有一个 1967 年就被讲透的物理常识——阿姆达尔定律（Amdahl's Law）：整体加速比受限于「优化不掉的部分」的占比。邮件处理是典型的 I/O 密集任务，如果一封邮件 90% 的耗时在网络传输和磁盘写入，那 CPU 快 100 倍，端到端也快不了 10 倍。所以遇到「换语言快 150 倍」的叙事，先问一句：瓶颈真的在语言上吗？

## Ruby 和 Rust：各自该待的位置

这场风波里最冤的其实是 Rust——它是好工具，只是被抬上了不合适的领奖台。冷静看两者的定位：

**Ruby/Rails 的强项：**
- 开发速度快，约定优于配置，适合业务快速迭代
- 生态成熟，ORM、迁移、后台任务一站式齐活
- 人才池大，招人和长期维护成本友好

**Rust 的强项：**
- 性能可预测，延迟尾部（p99）稳定，没有 GC 停顿
- 内存安全由编译器保证，适合长期运行的核心服务
- 并发模型严谨，数据竞争在编译期就能拦下

**业界成熟做法**是混合架构：主体业务用 Ruby/Python/Go 保住迭代速度，把 profiler 测出的热点路径（解析、压缩、加解密）单独抽成 Rust 服务或模块。Discord 的 Read States、Dropbox 的同步引擎、Cloudflare 的 Pingora 都是类似实践。也就是说，「Rails + Rust 热点」是正常的架构演进，「Rails 慢所以全换 Rust」才是需要警惕的叙事。

## 三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/00610bf3224dfa0c.png)

1. **看到「N 倍快」，先问三个问题**：分母是什么？两边跑了相同的功能吗？瓶颈在 CPU 还是 I/O？三问之后，大多数漂亮数字会自动降级。
2. **基准测试要可复现、要公开**：硬件配置、数据集、运行参数缺一不可。这次事件唯一的好消息是代码开源了，所以才存在「翻代码」这回事。不公开的 benchmark，性质上更接近广告文案。
3. **先量测，再动手**：用 profiler 找热点，而不是凭直觉重写。重写系统的隐性成本（人力、bug、迁移风险）通常远超收益；真要换语言，从边界清晰的小服务开始试。

最后说句实在的：DHH 敢把代码放出来挨审，这份开放本身值得尊重；社区用源码而不是口水来纠错，也是开源世界运转良好的证明。技术圈从不缺性能数字，缺的是把数字放回上下文里的耐心。虾友们做技术选型时记住一条铁律就够用：**数字会撒谎，但诚实的基准线不会。**
