## 背景

OpenClaw 这类常驻 Agent 和一次性对话不同：它有 workspace、有记忆、接了 MCP 工具和插件，可能在群聊里主动发言，也可能定时跑任务。当行为约束散落在各处配置里，Agent 的表现就会随时间漂移。SOUL.md 是 OpenClaw 约定的工作区文件（默认在工作区根目录），每次会话启动时注入上下文，用来集中回答三个问题：这个 Agent 是谁、说话什么风格、哪些事不做。

## 问题

我们实际撞到过三个典型现象：

1. **人设漂移**：长会话开头克制、后面话痨，表情符号越用越多，语气越来越随意；
2. **边界不清**：凌晨被 @ 就回，收到含糊指令也硬执行，甚至替用户做了本该先确认的操作；
3. **多实例不一致**：主号和分身行为对不上，排查半天才发现两份提示词早已分叉。

这些都是“人格没有单一样板、边界没有可执行条款”的症状。

## 做法

SOUL.md 建议控制在 60 行以内，分四段写：

**1. 身份与语气**：两三句说清角色定位。写行为而不是形容词——“回复不超过三句，先给结论”比“简洁专业”可靠得多。

**2. 硬边界**：写成可判定的规则。例如：不执行删除、支付类操作，先列出影响并等待确认；私聊可以闲聊，群聊只回应被 @ 或明确求助；不确定时说“我不确定，需要你确认”，禁止编造。

**3. 升级路径**：什么情况必须转人工、什么情况直接拒绝、什么情况记入 memory 留待复盘。

**4. 三个示例**：给一个标准回复、一个拒绝回复、一个请求确认的回复原文。示例对模型的约束力远高于抽象描述。

写完重启会话验证，之后纳入 git 管理。行为不合预期时，修条款而不是现场哄。

## 踩坑点

- **写成了许愿池**：二十条“要友好、要聪明、要有趣”，模型记不住，等于没写。规则越少越硬越好。
- **和 AGENTS.md、插件提示词打架**：插件注入的指令可能与 SOUL.md 冲突。先用最简配置排除干扰，再逐个启用定位冲突源。
- **当成安全边界**：SOUL.md 是行为引导，不是沙箱。真正的权限控制要靠工具白名单、系统权限和 MCP 侧审批，提示词挡不住提示注入。
- **写入敏感信息**：SOUL.md 全文进上下文，密钥、地址别放。
- **忘了它何时生效**：会话启动时加载，改完不重开 session，会误以为没生效。

## 可复用建议

- 用四段式模板：身份 / 边界 / 升级 / 示例，先抄后改；
- 边界条款统一用“如果 X，则 Y”句式，可判定优先；
- 每条规则配一个反例测试（诱导它执行危险命令、在群里抢话），过了才算数；
- 人格和权限分离：语气可以随场景软，边界必须全场景硬；
- 每月跑一遍红队问题清单，把行为漂移当 bug 修。

## 总结

SOUL.md 的价值不在“人设多有趣”，而在把散落的隐性约束收敛成一份可版本管理、可测试的行为契约。对常驻 Agent 来说，清晰且少量的硬边界，比丰富但模糊的性格描述有用得多。先立规矩，再谈性格。
