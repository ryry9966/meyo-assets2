## 背景

写自动化的第一周，你通常只考虑“跑一次”的情况；第三周，你会遇到同一次任务被执行了两次。原因很朴素：网络超时后重试、调度器误判任务失败、Agent 规划循环里重复调用同一个工具、消息队列的 at-least-once 投递。在分布式和 Agent 场景里，“恰好执行一次”几乎做不到，能承诺的只有“至少一次”或“至多一次”。幂等性就是让“至少一次”变得安全的手段：**同一操作执行一次和执行多次，最终状态一致。**

## 问题

非幂等任务在重复执行时的典型翻车现场：

- 定时摘要任务因重试，往群里发了两条一模一样的消息；
- webhook 插件重复消费同一条事件，创建了两张重复工单；
- Agent 工具调用超时后重试，目标文件被追加了两段相同内容；
- 部署脚本重跑，把增量操作又执行了一遍，环境状态被污染。

这些问题不出在“第一次执行”，而出在“第二次”。很多自动化在演示里一切正常，上线后第一批告警全是重复副作用。

## 做法

1. **用稳定的业务键，而不是随机 ID。** 任务每次运行都生成新 UUID，去重就无从谈起。改用“日期 + 数据源 + 动作”这类确定性键，比如 `daily-report-20240601-channel-a`，重试时键不变。
2. **把判重交给存储层，别只靠 if。** 数据库唯一索引 / upsert 是最可靠的防线；内存里的“已执行”标记在多实例下不可信。
3. **外部调用带幂等键。** 支持 Idempotency-Key 的 API 一定用上；不支持的，先查再调，并把调用结果落库。
4. **优先“收敛式”而不是“增量式”。** “确保文件包含这段配置”（重复执行结果不变）远比“往文件追加这段配置”安全。能用 PUT 语义就不用 POST。
5. **每一步独立幂等。** 五步任务在第三步失败，重试会重走前两步——只有整体幂等没用，每个副作用都要能安全重放。
6. **记录执行账本。** 一张简单的 runs 表：task_id、状态、结果。判重时看状态而不只是看存在，避免“上次失败了却被当成已完成”。

## 踩坑点

- **check-then-act 竞态**：两个 worker 同时通过“是否已存在”检查，然后都执行。要靠唯一索引兜底，捕获冲突异常处理，别相信检查和执行之间没有别人。
- **键粒度不当**：按秒级时间戳做键，重试间隔超过一秒就失效；按天做键，当天合法的第二次执行又被拦掉。键的粒度要等于业务的重复语义。
- **同键不同参数**：重试时 Agent 重新规划，参数变了。要提前定策略：拒绝、覆盖，还是记录告警。
- **部分成功的假象**：把“没报错”当成功，实际第三步没跑完。状态要记到步骤级。

## 可复用建议

- 任何自动化上线前问一句：**现在手动再跑一遍，会发生什么？** 答不上来就别上线。
- 在测试环境故意连续执行两次，断言副作用只有一份——把它写成回归测试。
- 设计 MCP 工具时明确声明幂等语义：哪些调用可安全重放、哪些会重复产生副作用，让上层 Agent 敢于重试。
- 日志里始终带 task_id 和 attempt 序号，排障时你都用得上。

## 总结

幂等性不是锦上添花的优化，而是重试机制的前置条件。既然“至少执行一次”是自动化的常态，就把每个任务设计成“再跑一遍也无害”。这比任何精巧的防重调度都可靠，也让你的 Agent 和插件在故障面前从容得多。
