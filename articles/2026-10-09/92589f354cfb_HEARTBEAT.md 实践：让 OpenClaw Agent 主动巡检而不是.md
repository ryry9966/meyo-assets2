## 背景：为什么 Agent 需要"心跳"

大多数 Agent 的默认形态是应答机：你不发消息，它永远安静。这对聊天够用，但对"个人自动化助手"不够——监控磁盘、早上汇总提交、发现没 push 的分支提醒一声，这些事你不会想起来问，但它应该主动做。

OpenClaw 的心跳机制就是为此设计的：网关每隔一段时间（默认 30 分钟）自动发起一次模型调用，把工作区里的 `HEARTBEAT.md` 全文注入上下文。Agent 自己判断这一轮有没有值得做的事：有就调用工具执行，必要时通过消息渠道通知你；没有就回复 `HEARTBEAT_OK`，网关识别到这个标记后不会向用户转发任何内容。

换句话说，HEARTBEAT.md 是一份常驻的、低频轮询的任务说明书。

## 问题：三种典型误用

1. **当成 TODO 堆放处。** 塞几十条长期任务，每次心跳全文注入，token 白烧，注意力也被稀释。
2. **没写沉默规则。** 模型天然有"表现有用"的倾向，不明确"什么时候闭嘴"，它会每个心跳都汇报一句"一切正常"，三天后你就把它禁用了。
3. **忽略调用成本。** 心跳是真实的模型调用，30 分钟一次就是每天 48 次，模型选错或文件太长，月底账单会教育你。

## 做法：从零写一份能用的 HEARTBEAT.md

**第一步**，确认位置：默认在 agent 工作区根目录 `~/.openclaw/workspace/HEARTBEAT.md`，没有就新建。

**第二步**，配置间隔。在 `openclaw.json` 的 `agents` 段下设置 `heartbeat.every`（如 `"30m"`），设为 `0m` 可整体关闭。调试期先调到 1–5 分钟。

**第三步**，按"例行 / 条件 / 沉默"三层结构写：

```markdown
# Heartbeat

## 例行
- 每天 08:00 后的第一次心跳：汇总各仓库昨日提交与未读邮件数，发给用户
- 其余时间不执行例行项

## 条件检查
- 磁盘使用率 > 85%：发警告，附 df 关键输出
- ~/projects 下存在超过 3 天未 push 的分支：提醒一次

## 沉默规则
- 无条件命中时只回复 HEARTBEAT_OK，不要汇报"一切正常"
- 同一事项 24 小时内最多提醒 1 次
```

**第四步**，观察 1–2 天：看消息噪音、token 消耗、动作日志，再定正式间隔。

## 踩坑点

- **心跳跑在主会话里。** 让它执行重任务会污染主上下文。正确分工：心跳只做"检查 + 判断 + 触发"，重活交给 cron 任务或子 agent。
- **弱模型不守 HEARTBEAT_OK 约定。** 有的模型会自作主张输出解释。对策：把沉默规则放文件第一行，或给心跳单独配一个更守指令的模型。
- **时区。** 容器里常见 UTC，"每天 08:00"会错位。先在运行环境跑 `date` 确认，或条目里写明时区。
- **通知风暴。** 漏写"24 小时内最多一次"这类去重约束，Agent 会在每个心跳重复催你。
- **文件膨胀。** 每次心跳全文注入，几百行的文件等于持续放血。控制在几十行内，长文档放别处，让它在需要时自己读。

## 可复用建议

- **心跳与 cron 分工**：确定性时间点的事（日报、定时备份）用 cron；"顺便看一眼再决定说不说"的事用心跳。心跳的核心能力是判断，不是定时。
- **留动作日志**：让 Agent 把每次主动执行的动作追加写入工作区日志文件，方便事后审计它替你做了什么。
- **每条提醒类条目必须带频率上限**，这是长期共存的前提。
- **上线节奏**：短间隔观察一天 → 定正式间隔 → 每月修剪一次文件，删掉从未触发的条目。

## 总结

心跳机制的价值不在"自动执行"，而在"自主判断说不说"。一份好的 HEARTBEAT.md，一半篇幅其实在定义沉默。把"什么时候闭嘴"当成一等公民来设计，它才是一个能长期共事的巡检员，而不是刷存在感的实习生。
