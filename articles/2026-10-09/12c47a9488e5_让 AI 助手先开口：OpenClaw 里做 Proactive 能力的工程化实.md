## 背景：从"你问我答"到"它先开口"

大多数 Agent 的默认形态是被动应答：用户发消息，助手处理，结束。但真实使用中有一类需求天然是反向的——CI 半夜挂了、磁盘快满了、日历上两个会议撞车了。这些事等到你开口去问，往往已经晚了。

OpenClaw 这类框架配上 MCP 工具和定时触发能力后，做 proactive 在技术上并不难：定时任务、webhook、文件监听都能把事件喂给 Agent。真正难的是工程问题——**怎么让它主动得恰到好处，而不是变成一个半夜给你推消息的骚扰源**。

## 问题的本质：不是"会不会做"，是"该不该说"

被动模式里，用户开口本身就是一次过滤——能被问出来的事都值得处理。Proactive 模式把这道过滤拆掉了，Agent 必须自己回答三个问题：

1. 这件事**值不值得打扰用户**？
2. 值得的话，是**通知**还是**直接动手**？
3. 动手的话，**权限边界**在哪？

这三个问题没想清楚，做出来的 proactive 功能基本活不过一周。

## 做法：一条最小可用的 proactive 管线

我在自己的 OpenClaw 实例里跑了一套简化的管线，核心是**事件分级 + 确定性门槛 + 分级响应**：

**第一步：事件入口收敛。** 所有触发源（cron、webhook、文件 watcher）统一写进一个"待处理事件"列表，带时间戳、来源和去重 key。不要让每个触发器各自直接调模型。

**第二步：确定性规则先行。** 大部分事件用纯规则就能分流——磁盘超 85%、CI 红了、日历冲突，这些判断根本不需要 LLM。规则能拦掉的就不进模型，这一步直接决定了成本和稳定性。

**第三步：LLM 只做"值得说吗"的判断。** 剩下的模糊事件（比如"某依赖连着两天有更新"）才交给模型，让它按分级输出：忽略 / 记录 / 进摘要 / 立即通知 / 建议行动。

**第四步：按分级走不同通道。** 忽略和记录只是写日志；摘要类攒到固定时间合并推一条；立即通知走 IM；只有写操作进入"建议 + 等确认"队列——主动但不越权。

## 踩坑点

- **事件风暴没去重。** webhook 重试 + cron 重叠，同一故障能触发十几次。去重 key 和防抖窗口必须在一开始就设计好。
- **太早让 LLM 看所有事件。** 一开始我把所有事件都丢给模型判断，一天烧掉的 token 是现在的五倍，结论还不比规则好。
- **proactive 运行没有会话上下文。** 定时触发的会话是空白的，聊天历史帮不上忙。状态必须外置——配置、阈值、上次检查时间都落盘，别依赖对话记忆。
- **通知疲劳。** 前两周我觉得每条都很重要，用户（就是我自己）三天后开始无视一切推送。加了静默时段和摘要合并才恢复。
- **凭证权限过大。** 主动 Agent 拿着全量写权限的 token，等于定时炸弹。给 proactive 通道单独发最小权限凭证。

## 可复用建议

- **先做只读，再挣权限。** 前两周只让它"说"，日志里人工复盘它的判断，准确率上来了再放开低风险写操作。
- **每条 proactive 规则都要有开关和归属。** 出问题时能一键关掉单条规则，而不是整个功能下线。
- **门槛写进配置，不写进 prompt。** 阈值放在配置文件里可调可审计，别埋在系统提示词里靠改 prompt 调优。
- **定期审计主动行为日志。** 每周扫一遍它"替你做了什么决定"，这是唯一能发现判断漂移的手段。

## 总结

Proactive 能力的价值不在"多做了多少事"，而在**替用户省掉多少次不必要的开口**。工程上的关键结论就一条：把"发生什么"和"是否值得说"拆开，前者交给触发器和规则，后者才交给模型。管线搭对了，主动的 AI 助手是杠杆；搭错了，它只是一个更吵的通知栏。
