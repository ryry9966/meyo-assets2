## 背景

OpenClaw 里的 agent 平时是“被动”的：有消息进来才跑一轮。要让助手具备主动性行为——定时摘要、盯 CI、跟进待办——就得靠 heartbeat，让 agent 周期性醒来检查一次。最朴素的实现是轮询：定时唤醒，agent 读一份 HEARTBEAT.md 清单，决定“做事还是继续睡”。但社区里常见两种极端：有人把间隔调到 5 分钟然后抱怨 token 烧得飞快；也有人直接上 webhook 推送，被重试和事件风暴教做人。这篇把两条路线的取舍讲清楚。

## 问题

轮询和推送本质上是两种延迟/成本结构：

- **轮询**：实现成本≈0，延迟上限=间隔。代价是每次唤醒都要加载完整上下文，即使 99% 的唤醒什么都没发生。30 分钟一次、每次几千 token，一天固定烧掉不少。
- **推送**（webhook / MCP 通知注入会话）：延迟低、空闲零成本，但要自己解决幂等、去重、事件聚合、失败重试，还多维护一个可达的 HTTP 入口。

## 做法：分层，而不是二选一

我目前的方案分三步：

1. **先给任务分类**。时间驱动的（每天早报）用 cron 精确触发；事件驱动的（新消息、CI 失败、指标越阈值）走推送；状态巡检类的（“看看磁盘空间”）才留给 heartbeat 轮询。
2. **heartbeat 保持低频兜底**。30–60 分钟一次，HEARTBEAT.md 写成判断清单，并明确写上“无事可做就静默结束”。它的角色是兜住推送丢失和状态漂移，不是主力。
3. **推送走会话注入**。webhook 收到事件后组装成一条系统消息塞进对应 session，带上去重 key 和时间戳；MCP 侧则是工具执行完主动发 notification。

## 踩坑点

- **唤醒太频繁**：每次 heartbeat 都是一次完整推理。没事件的日子里 5 分钟间隔纯属烧钱，从 30 分钟起步，根据日志里的空转率再调。
- **推送没做幂等**：webhook 超时重试 → 同一事件触发两轮 agent → 助手重复回复。去重 key 必须落在事件源头，不能靠 agent 自己判断。
- **事件风暴**：CI 连挂 20 次，20 条推送排队打进同一个 session。要聚合——同源事件在时间窗口内合并成一条再注入。
- **heartbeat 幻觉任务**：不写清楚“允许什么都不做”，agent 会为了显得有用而编造提醒。HEARTBEAT.md 里 no-op 要写成合法输出。
- **静默时段**：凌晨三点的主动消息很讨嫌，心跳和推送都要过一遍 quiet hours 判断。
- **停机补偿**：gateway 重启后错过的心跳怎么办？记录 last_run 时间戳，醒来先补算错过的窗口。

## 可复用建议

- 决策依据一句话：**延迟要求小于一分钟且事件源可控 → 推送；其余先用轮询**。不要为“偶尔想快点”提前上基础设施。
- 每次心跳的决策（做了什么/为什么跳过）落日志，跑一周就能算出合理间隔。
- HEARTBEAT.md 当配置而不是代码：条目化、可注释、进 git 管理。
- 推送入口必须有认证和限流，裸奔的 webhook 迟早被扫到。

## 总结

轮询买的是简单和可靠，推送买的是延迟和空闲成本。对个人 assistant 场景，“cron 管时间、推送管事件、低频心跳兜底”的混合结构是实践里最省心的形态。先跑一周空转日志，再决定要不要为那几秒延迟多维护一套推送链路——多数情况下，答案是不用。
