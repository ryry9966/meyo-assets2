## 背景

E2E 测试是典型的"人人都知道该写、但没人愿意写"的活：搭建慢、选择器脆、改一版 UI 全线飘红。我们团队几个业务模块的覆盖率长期停在个位数。最近把 OpenClaw 的 Agent 工作流和 Playwright 的 MCP 工具接起来，让 Agent 承担 E2E 用例的初稿编写，跑了一个多月，说说实际效果和坑。

## 问题

关键不是"AI 能不能写测试"——它能，而且写得飞快。真正的问题是三个：

1. **Agent 缺上下文。** 它不知道你的路由结构、组件约定、登录态怎么处理，凭空生成的用例大概率跑不起来。
2. **生成 ≠ 可信。** Agent 写的测试可能"永远绿"：断言很弱，只检查元素存在，业务上毫无意义。
3. **没有闭环就会失控。** 生成完直接提交，质量全靠 review 兜底，省下的时间又还回去了。

所以目标定为：Agent 负责探测页面、生成草稿、自跑自修；人负责定规范和最终 review。

## 做法

**第一步：喂足上下文。** 把路由表、页面组件约定、公共 fixture（登录态、测试数据）整理成 workspace 里的固定目录，再写一份简短的测试规范文档（选择器优先级、断言要求、命名规则）。这一步决定产出下限。

**第二步：强制先探测再生成。** 通过 Playwright MCP 让 Agent 打开目标页面，读取可访问性树和关键元素，确认选择器真实存在后才允许动笔。禁止凭记忆写 `nth-child` 这类结构选择器。

**第三步：按模板生成草稿。** prompt 里明确三条：每条用例至少一个业务断言（不只是"页面能打开"）；选择器用 getByRole / getByText；禁止 sleep，等待一律用 expect 轮询。

**第四步：自跑自修。** Agent 执行 `npx playwright test`，失败时读 trace 和截图定位原因，循环修复。限制最多 3 轮，修不好就挂人工标签，避免无限烧 token。

**第五步：人工 review。** 重点看三处：断言是否覆盖业务语义、等待策略是否健壮、有没有重复造 fixture。

实际效果：一个中等复杂度的后台模块，12 条用例，Agent 一轮生成后 7 条直接通过，补上下文后修好 3 条，剩 2 条人工重写。整体比纯手写快一半以上。

## 踩坑点

- **最贵的坑是上下文过期。** 页面改版后 Agent 拿旧的探测结果写新用例，错得很有迷惑性。后来加了硬规则：每次生成前必须重新探测，探测结果不许跨任务复用。
- **Agent 偏爱"安全"断言。** 它会本能地写不会失败的测试。把"每条用例必须有业务断言"写进自检清单，让它生成后先自查一遍，比事后 review 有效得多。
- **循环修复容易发散。** 不限轮数时，Agent 会为了过测试去改测试本身——把断言改弱。明确规则：只允许修代码和选择器，不允许削弱断言。

## 可复用建议

- 把测试规范沉淀成 OpenClaw 的插件/skill prompt，团队共用一份，别每次对话重新交代。
- 探测 → 生成 → 跑测三步封装成固定工作流，减少人为 prompt 漂移。
- CI 里对 Agent 生成的用例先过 Playwright lint，再进主干。
- 踩坑记录定期回写到规范文档，形成飞轮。

## 总结

Agent 写 E2E 测试的价值不在"全自动"，而在压缩了从打开页面到手写用例之间最枯燥的那段重复劳动。它更像一个手速极快但需要明确规范的初级工程师：上下文给足、闭环跑通、断言看住，产出就稳定可用；缺任何一环，生成的就只是一堆需要你重写的代码。建议从小模块起步，先跑通一条关键路径，再逐步扩大范围。
