## 背景

AGENTS.md 是一个正在成为事实标准的约定：在工作空间根目录放一个 Markdown 文件，专门写给 AI agent 读。OpenClaw 把这个约定落在了 workspace 里——`~/.openclaw/workspace/AGENTS.md` 会在会话启动时被注入 agent 的上下文，作为它的行为基准。

要理解的关键一点：它不是文档，是**运行时配置**。你写进去的每一条规则，都会影响 agent 接下来的每一步操作。

## 问题

没有 AGENTS.md 或写得随意时，常见的症状：

- 每个新会话都要重复交代："测试用 pnpm，别用 npm""临时文件别放仓库根目录"；
- agent 把产物和草稿散落各处，目录约定全靠它现场猜；
- 自动化跑批时行为飘忽：这次记了 MEMORY.md，下次没记；
- 多人共用同一套 workspace，各自的口头习惯没有沉淀，agent 每天在重新摸索。

根因很简单：agent 没有持久的"常识"，它上下文里的事实就是它的常识。你不写下来，它只能猜。

## 做法

建议分两层维护：

1. **全局层**：`~/.openclaw/workspace/AGENTS.md`，写个人通用偏好——回复语言、汇报格式、安全底线。
2. **项目层**：在具体项目根目录再放一份，写这个仓库的工具链、命令和目录约定，agent 进入该目录干活时以它为准。

写作上遵循三条原则：

- **写祈使句，不写愿望**。"提交前跑 `pnpm lint --fix`"，而不是"请重视代码质量"。
- **只写 agent 用得上的信息**：命令、路径、边界、执行顺序。
- **控制篇幅**，几十行以内。它每次会话都全文读入，太长会稀释关键约束。

一个可以直接抄的骨架：

```markdown
# 项目约定
- 包管理器只用 pnpm，禁止 npm/yarn
- 全量测试：pnpm test；单文件：pnpm test path/to/file
- 临时文件一律放 /tmp/claw-scratch，不污染仓库根目录
- 改动涉及 3 个以上文件时，先列计划再动手
- 只在用户明确说"记住"时才写 MEMORY.md
```

## 踩坑点

- **写太长**。两百行的 AGENTS.md 等于没写，注意力被稀释后，真正重要的禁止事项反而被跳过。
- **多处规则互相冲突**。全局说回复用中文、项目里说 commit message 用英文，这没问题；但全局和项目层同时规定 memory 策略且内容打架，agent 行为就会随机。冲突的规则必须合并成一份。
- **把它当 README 写**。架构介绍、贡献指南是给人看的；agent 需要的是"操作规则"，不是"项目介绍"。
- **工具链变了忘了更新**。CI 从 make 换成 just 之后没改文件，agent 会继续用旧命令——然后你误以为它变笨了。
- **写入敏感信息**。AGENTS.md 会进入每次会话上下文，密钥、内网地址一律不放。

## 可复用建议

- 纳入 git 管理，改规则像改代码一样提 PR，留变更记录。
- **两次法则**：agent 犯同类错误犯到第二次，就把对应约束写进去，把排障经验沉淀成规则。
- 新规则写完后，开一个**全新会话**验证。长会话里有旧上下文干扰，测不准。
- 定期删：过时的规则比没有规则更糟，它会让 agent 坚持用已经废弃的流程。
- 从最小版本开始：10 条真正踩过坑的规则，胜过 50 条想象出来的规则。

## 总结

AGENTS.md 做的是一件朴素的事：把"你希望 agent 怎么干活"从口头交代，变成版本化的、每次会话自动生效的配置。它不会让模型变聪明，但能让它稳定地不踩你踩过的坑。维护心态应当像维护 CI 配置一样——小步、具体、持续修正。写好这一个文件，往往比换更强的模型更能提升日常体验。
