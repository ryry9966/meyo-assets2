## 背景

OpenClaw 每次新会话启动时，会从工作空间（默认 `~/.openclaw/workspace/`）加载一组引导文件：`SOUL.md` 管人设，`TOOLS.md` 管工具说明，而 `AGENTS.md` 管的是最实际的一层——**在这个工作空间里干活要遵守什么规矩**。可以把它理解成写给 AI 的 CONTRIBUTING.md：读者不是人，而是每次冷启动、没有历史记忆的 agent。

## 问题

不写 AGENTS.md 的工作空间，通常会遇到这些情况：

- 输出风格漂移：这周要求报告写成清单，下周又变回大段文字；
- 临时文件乱放，工作空间根目录被截图、日志、草稿塞满；
- 有副作用的操作（删除、覆盖、对外发消息）不经确认直接执行；
- 同一个问题在对话里纠正过多次，换个会话又犯。

这些不是模型能力问题，而是缺一份固定、可版本化的操作规范。只靠聊天记录里的"上次说过"，是留不下来的。

## 做法

1. **建文件**：在工作空间根目录创建 `AGENTS.md`，用 git 管起来。
2. **分层写**，建议四个板块：
   - 环境事实：时区、交流语言、关键路径；
   - 文件规范：临时文件去哪、产物放哪、命名习惯；
   - 执行规则：哪些操作先复述计划再动手，长任务怎么放后台；
   - 禁忌清单：明确"不要做"的事。
3. **控制篇幅**：这份文件每次会话都会注入上下文，建议 100 行以内，最重要的规则放最前面。
4. **示例骨架**：

```markdown
# AGENTS.md
## 环境
- 时区 Asia/Shanghai，交流用中文
- 临时文件放 tmp/，产物放 outputs/
## 执行
- 删除、覆盖、对外发送前，先复述操作计划
- 长命令放后台执行，记录 PID 与日志路径
## 输出
- 对话回复保持精简，长报告写入文件并附路径
```

5. **迭代**：这是真正的重点。发现 agent 第二次犯同一个错，就把它固化成一条规则，而不是在对话里再纠正一遍。

## 踩坑点

- **和 SOUL.md 职责混写**：语气、性格归 SOUL.md，操作规范归 AGENTS.md。混在一起，改人设时容易误伤规则。
- **规则无作用域**："回复要精简"和"报告要详尽"并列就会冲突，agent 会随机选一个。每条规则写清适用场景。
- **改完不验证**：旧会话的上下文已经固定，必须开新会话确认新规则真的生效。
- **硬编码绝对路径**：换台机器就集体失效，能用相对路径就用相对路径。
- **写入敏感信息**：AGENTS.md 会进入模型上下文，token、密码一律放环境变量，不要写进文件。

## 可复用建议

- 建立"错误 → 规则"的映射习惯：规则应来自真实事故，而不是凭空设想。
- 像 review 代码一样 review 规则变更，每次改动走 git commit，留得住、回得去。
- 定期清理：环境变了、规则过期就删，别让文件越长越钝。
- 多 agent 场景：公共规范维护一份模板，再按各 agent 的职责做差异化增量。

## 总结

AGENTS.md 的价值不在写了多少，而在把"重复纠正"变成"一次性约束"。它的成本极低——一个 markdown 文件；收益是行为可预期、工作空间不失控。写它的过程本身也是在梳理自己的工作流：如果你自己都说不清规矩，agent 就更说不清了。
