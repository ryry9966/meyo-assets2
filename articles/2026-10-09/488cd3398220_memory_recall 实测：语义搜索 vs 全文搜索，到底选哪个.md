## 背景

OpenClaw 用了半年，memory 目录攒了 400 多条笔记：部署记录、插件配置、踩坑备忘。Agent 回答前通过 memory_recall 检索这些内容，检索质量直接决定它"记不记得住"。memory 检索有两条路线：全文（关键词匹配）和语义（embedding 相似度），配置里可切换。我之前一直用默认值，直到发现它反复想不起明确记过的事，才认真对比了这两种方案。

## 问题

把失败案例归类后主要是两种：

- **换说法搜不到**：笔记里记的是"frp 内网穿透掉线"，我问"远程访问不稳定怎么办"，全文检索直接空手而归。
- **精确词搜偏**：语义检索"nginx"时，返回一堆内容相近但无关的笔记，真正的配置记录反而排在后面。

直觉上语义更"智能"，但两边各有死穴。

## 做法

搭了个 20 题的小评测集：

1. 从 memory 里挑 20 条已知笔记，每条写一句"我实际会怎么问"，其中 10 句刻意换说法、换用词；
2. 分别在全文、语义模式下调用 memory_recall，人工判断 top-3 是否命中正确笔记；
3. 记录命中率、单次延迟、语义模式的 embedding 开销。

结果（样本小，仅供参考）：全文 13/20，语义 15/20，两路召回后用 RRF 合并的混合方案 17/20。延迟全文 50ms 以内，语义 200–400ms，主要耗在 embedding 调用上。

## 踩坑点

1. **中文分词是全文模式第一道坎**。默认切分对"nginx证书续期"这类串很粗，建议笔记里主动写关键词行，或换分词器。
2. **通用 embedding 模型对中文专名不敏感**。插件名、端口、报错码在向量空间区分度不够，是语义搜偏的主因。
3. **索引时效坑最深**：改了 memory 文件没触发重建，语义检索一直命中旧内容。把 reindex 挂在文件变更事件上。
4. **长文条目向量被稀释**。一条 memory 写成几百字，所有条目相似度趋同，拆成原子化短条目。
5. **语义检索必须设相似度下限**，否则永远"能搜出点什么"，Agent 会拿着无关结果硬编答案。

## 可复用建议

- memory 条目开头一行写清专有名词和关键词，对两种检索都友好，这是收益最大的动作；
- 语料几百条以内，先用全文：零依赖、零成本、低延迟，别过度设计；
- 出现"换说法搜不到"再上语义，且优先配混合检索，比单押一边稳；
- 评测集保持 10–20 题，任何配置改动都跑一遍，比看别人的 benchmark 可靠。

## 总结

这场对比没有普适赢家：语义赢在换说法，全文赢在精确词、成本和延迟。个人助理场景的合理路径是**全文起步、评测驱动、混合兜底**。另外最大的体会是：memory 怎么写，比用什么检索算法影响更大——写得烂的笔记，换什么搜索都救不回来。
