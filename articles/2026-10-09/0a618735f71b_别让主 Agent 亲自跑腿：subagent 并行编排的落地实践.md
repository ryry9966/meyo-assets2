## 背景

单个 Agent 串行处理长任务链，两个问题迟早会撞上：一是上下文被工具输出塞满——比如抓取 20 个页面之后，主 Agent 已经“忘了”最初的目标；二是串行太慢，任何一步卡住，整条链都停摆。

OpenClaw 的 subagent 机制给了一个工程化解法：主 Agent 只做规划和汇总，把“跑腿”交给若干个拥有独立上下文的子代理并行执行。本质上是**上下文隔离 + 受控并行**。

## 问题

举个实际场景：对 12 个内部服务做健康巡检并生成汇总报告。串行做法下，12 次 HTTP 检查的原始输出全部涌入主上下文，到第 8 个服务之后主 Agent 开始漏项、混淆结果，单轮耗时也难以接受。这不是提示词写得好不好的问题，是结构问题。

## 做法

1. **判断是否值得拆。** 满足三个条件再拆：子任务相互独立、以读取/检索为主、结果能压缩成短摘要。强顺序依赖的任务拆了反而更乱。
2. **定义子任务接口。** 给每个 subagent 一段窄提示词：明确目标、工具白名单、输出格式（结论一行 + 关键数据 + 风险，超过五行视为不合格）。工具面要收敛：只挂载该任务需要的 MCP server，巡检类只留网络请求工具。
3. **控制并发与预算。** 并发上限 3–4；每个子代理设超时和 token 预算，超限直接终止并返回失败摘要。
4. **汇总阶段隔离。** 父代理只接收结构化摘要，不接触原始工具输出。发现异常服务，再派一个针对性子代理深挖，而不是自己在主上下文里翻原始日志。
5. **留痕。** 每个子代理的完整 transcript 落盘，出问题时可以回放。

## 踩坑

- **子代理的上下文同样会爆。** 一个子代理只领一个服务，别把 12 个打包塞给它，隔离粒度宁小勿大。
- **摘要太简导致父代理瞎猜。** 强制要求带上证据：路径、状态码、耗时，缺证据的结论按无效处理。
- **并发打满触发上游限流。** 加退避重试，宁可慢一点，不要整批失败重来。
- **权限跟着任务走。** 只读巡检的子代理绝不给写权限，写入类任务单独派发。
- **失败必须显式上抛。** 禁止子代理“静默返回空”，空结果和失败要在摘要里区分开。
- **并行写同一文件必冲突。** 各自写独立路径，由父代理统一合并。

## 可复用建议

- 把“分-做-合”沉淀成模板：spawn 提示词、输出 schema、并发参数固化为插件默认值，新场景只改任务描述。
- 先在只读任务上跑通全流程，再逐步放开写入类子代理。
- 复盘时只看父上下文 + 子代理摘要，比翻全量日志高效得多。

## 总结

subagent 编排的价值不在“多开了几个 Agent”，而在让主 Agent 的角色从“干活的人”变成“派活的经理”。四条原则记牢：接口窄、输出结构化、失败响亮、权限最小。做到这些，多 Agent 并行才不是炫技，而是稳定可维护的工程手段。
