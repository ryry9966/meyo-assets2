## 背景

做一个能干活的 Agent，绕不开"调工具"：读文件、查数据库、调内部 API、发消息。2024 年以前，这件事没有标准做法——各家模型有自己的 function calling 格式，每个宿主（IDE、聊天客户端、Agent 框架）都要自己写一套工具接入层。

MCP（Model Context Protocol）是 Anthropic 在 2024 年 11 月开源的协议，一句话概括：**给"模型应用"和"外部工具/数据源"之间定一个统一的通信标准**。可以理解成 AI 生态的 USB-C：工具只出一个口，宿主只认一个口。

## 问题：M×N 的适配地狱

没有 MCP 时，接工具是典型的 M×N 问题：

- M 个宿主应用（你的 Agent、各种客户端、IDE 插件）
- N 个工具/数据源（GitHub、Postgres、内部服务……）

最坏情况要写 M×N 份胶水代码，而且每份都在重复解决同一批问题：工具怎么发现、参数 schema 怎么描述、鉴权怎么做、连接怎么保活。对插件和自动化用户来说，最直观的痛是：同一套工具逻辑，在 A 框架里写一遍，换到 B 框架再写一遍。

## MCP 怎么解决

它把 M×N 拆成 M+N：

- **宿主侧**只实现一次 MCP 客户端逻辑；
- **工具侧**把能力包装成 MCP Server，只写一次；
- 两边用统一协议通信。协议本体基于 JSON-RPC 2.0，定义三类核心原语：**Tools**（模型可调用的操作）、**Resources**（可读取的上下文数据）、**Prompts**（预置提示模板）。传输层常用两种：本地进程走 stdio，远程服务走 Streamable HTTP。

一次对接，到处可用——这是它真正的价值主张。

## 上手步骤

1. 选官方 SDK（Python/TypeScript 等），起一个最小 Server，暴露 1–2 个 tool，写清 name、description、JSON Schema 参数；
2. 本地用 stdio 跑通，用官方 Inspector 确认工具能被列举、能被调用；
3. 在宿主（如 OpenClaw 或其他支持 MCP 的 Agent 框架）里注册该 Server 的启动命令或 URL；
4. 观察模型实际如何选择和调用工具，迭代 description 和参数设计；
5. 稳定后再迁到 Streamable HTTP，接鉴权与多用户。

## 踩坑点

- **description 决定命中率**：模型靠描述选工具。写得含糊，要么选错，要么不用。description 是 prompt，不是注释。
- **工具数量爆炸**：单个 Server 塞 50 个工具，选择准确率明显下降。按域拆分，单 Server 暴露 5–15 个工具比较稳。
- **stdio 的路径与环境**：宿主拉起子进程时的 cwd、虚拟环境、PATH 可能和你终端里不一样，"我本地能跑"多半栽在这。启动命令用绝对路径。
- **长任务与超时**：同步等长任务的 tool call 容易超时，考虑异步任务 + 轮询或资源订阅。
- **动态工具列表**：运行中增删工具，部分宿主不会自动刷新，需要重连或显式拉取变更。

## 可复用建议

- 先 stdio 后 HTTP：本地先验证协议语义，再考虑部署；
- 复用官方 SDK，别手写 JSON-RPC；
- 把原始 JSON-RPC 流打进日志，排障效率高一个量级；
- 工具粒度宁粗勿细：让模型调 `create_issue`，而不是拆成五步原语；
- 鉴权放传输层（OAuth/Token），别让模型经手明文密钥。

## 总结

MCP 没有让工具变得更强，它解决的是工程问题：把 M×N 的重复适配收敛成 M+N，让工具生态和宿主生态解耦。判断标准很简单——工具只在一个宿主用一次，直接写 function calling 可能更快；工具要复用、要跨客户端迁移、要给别人用，MCP 就值得现在接。协议本身不复杂，复杂的是工具设计，而这部分功夫无论用不用 MCP 都省不掉。
