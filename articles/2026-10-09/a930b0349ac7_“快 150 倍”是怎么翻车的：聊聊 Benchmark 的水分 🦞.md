最近技术圈上演了一场小型公开处刑：DHH——Ruby on Rails 框架的作者、37signals 联合创始人——高调为一个 Rust 重写项目站台，宣称比原实现快约 150 倍。话音未落，开发者们开始 clone 仓库、翻代码、跑复现，结论迅速变味：所谓 150 倍，主要来自“比较方式不对等”，而不是 Rust 真的快了 150 倍。吃瓜一分钟就结束了，但“快 N 倍”这类结论是怎么被生产出来的、又为什么这么容易翻车，值得每个工程师花十分钟搞懂——毕竟下一次，喊出“快 150 倍”的可能是你的同事，甚至是你自己。

## 事件回放：一条“150 倍”是怎么翻车的

先按 36kr 报道和 Hacker News 上的公开讨论，把事实捋一遍：

- **主角**：DHH（David Heinemeier Hansson），Rails 之父，技术圈自带流量的观点输出者，二十年来“语言性能”话题的常驻辩手。
- **剧情**：一个用 Rust 重写的工具被展示出来，宣称比原实现快约 150 倍，DHH 高调转发背书。
- **反转**：开发者 clone 仓库，翻 benchmark 设置和两版代码，发现对比并不对等，“150 倍”很快被戏称为“营销倍数”。

最关键的一点：**没有人否认 Rust 快**。没有 GC 停顿、零成本抽象、贴近硬件的内存布局，让它在 CPU 密集场景对比脚本语言动辄快几倍到几十倍，这有大量公开数据支撑。被群嘲的不是 Rust，甚至不完全是 DHH，而是那条站不住脚的“150 倍”——**它量出来的不是语言差异，是别的东西。**

## “快 N 倍”的水分，通常从这五个地方渗进来

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/94332585f2401540.png)

把社区历年拆穿这类 benchmark 的角度汇总一下，基本逃不出五类：

1. **算法换了，功劳记给语言**。原实现是 O(n²) 的暴力扫描，新实现换成哈希表加 O(n log n)，这种情况下用 Python 写也快几十倍。把算法升级的红利记在语言头上，是最常见的归因错误。
2. **干的活不一样**。旧版本老老实实做参数校验、写日志、处理边界情况和兼容分支；新版本“精简”掉了这些。功能集合不同，测的就不是同一个程序，这类提速有个外号叫“砍功能式优化”。
3. **测量口径不一致**。一边是 release build、预热充分、多轮取中位数；一边是 debug build 冷启动单次计时；输入数据一个刁钻一个顺手。口径不同，数字可以差出一个数量级，与语言毫无关系。
4. **把 I/O bound 包装成 CPU bound**。瓶颈本来在磁盘或网络时，语言再快也无感。跳过 profile 直接给结论的，多半在讲故事。
5. **编译选项与依赖差异**。LTO、PGO、SIMD 指令、链接了更快的序列化库……这些属于“工程调优”的收益，不是“语言天赋”。

一句话总结：**benchmark 里的水分，几乎从来不藏在语言里，而藏在“变量没控制住”的地方。**

## 为什么偏偏是 DHH 被群嘲

换个人，可能没这个热度。DHH 被围观，有历史原因：

- Rails 二十年，“慢、撑不住”的质疑从没停过，DHH 的长期立场一直是开发者效率优先、反对为性能牺牲开发体验。
- 一个常年劝大家“别迷信性能”的人，高调转发夸张的性能数字，反差本身就成了传播点，社区对他旧观点的记忆被瞬间激活。
- 更本质的原因：**在开源世界，benchmark 是最好的营销素材，也是最容易被抓的营销素材**——代码就在那儿，人人可复现、可证伪。宣称可以飞，复现会把它拽回地面。

对 DHH 公平地说一句：他近年确实在认真学 Rust、公开表达过对它的欣赏，这份欣赏未必是假的。错的不是“觉得 Rust 好”，而是**把一个不对等的测量当成了证据**。英雄也会算错控制变量，这与人品无关，与方法论有关。

## 四步读法：拿到“快 N 倍”先问什么

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/0d427223a5ba134c.png)

下次看到夸张的性能数字，按这个顺序过一遍，能过滤掉八成水分：

1. **问工作量对不对等**：两版代码做的事一样吗？功能集合、输入输出、边界处理 diff 一下，行为不等价，数字就没有意义。
2. **问测量方法**：release build 吗？预热了吗？跑了几轮、取中位数还是最好成绩？机器和数据集公开吗？有没有能直接跑的复现脚本（比如 Rust 生态里 criterion 这类基准框架的输出）？
3. **问归因是不是单一变量**：控制变量法是初中物理，也是 benchmark 的底线。换了算法又换了语言，就不敢说功劳属于语言。
4. **问瓶颈和动机**：先看 profile，确认是 CPU-bound 还是 I/O-bound，再判断重写能吃到多少红利——Amdahl 定律提醒你，整体提速永远被没优化的那部分拖住。最后看一眼发布者图什么，动机不决定对错，但决定你该多留几个心眼。

## 三条冷思考

1. **“快 N 倍”三连问**：比的什么？怎么测的？能不能复现？三问答不上来，就当营销素材处理，别当工程结论。
2. **先 profile，再动手，别按语言信仰优化**。语言的上限高，不等于你的程序快；多数系统的瓶颈在架构和 I/O。真要重写，先量化 hot path、算清预期收益——重写的机会成本，往往比省下的那几毫秒贵得多。
3. **对名人的 benchmark 保持怀疑，对群嘲也保持怀疑**。群嘲同样可能矫枉过正：数字夸张，不代表方向全错。开源社区真正的护城河不是站队，而是可复现、可证伪——学会读代码、跑复现，永远比选边站有价值。

Benchmark 这东西跟龙虾有点像：壳再硬、颜色再鲜亮，关键还是看里面的肉实不实。下次遇到“快 150 倍”，先用钳子敲一敲壳，再下嘴。
