## 背景

OpenClaw 里的 cron 任务和系统 crontab 不是一回事。到点触发时，你写的 instruction 会作为一条用户消息投递给 agent，由 agent 结合自己的工具、记忆和会话上下文去执行。换句话说，**cron 调度的是时间，决定成败的是 instruction 的质量**——它本质上是一份每次运行都会原样重放的 prompt。

我目前维护着十来个定时任务：每日摘要、证书到期巡检、备份校验。早期翻过不少车，这里把经验沉淀一下。

## 问题：一条“看起来没问题”的指令

我最早写的版本大概是：

```
每天早上 9 点总结我的 GitHub 通知，发到群里。
```

跑了一周，出现三种情况：有时总结的是全部仓库而不是我关心的几个；有时“发到群里”发进了主会话；有一次 GitHub API 超时，agent 编了一份“看起来很合理”的通知列表。三个问题指向同一件事：instruction 里没写清楚的规则，agent 会自己补——补出来的不一定是你想要的。

## 做法：六要素模板

现在所有 cron 任务我都用固定结构写 instruction：

1. **目标**：一句话说清做什么；
2. **数据源**：点名具体工具和范围，不写“查一下”；
3. **范围与过滤**：明确只处理什么、跳过什么；
4. **输出**：固定模板 + 条数上限，格式可预测；
5. **去向**：写清发到哪个 session/channel，禁止落进主会话；
6. **异常语义**：失败时明确报告、禁止编造。

改写后：

```
任务：每日 PR/issue 摘要
数据：用 github 工具拉取 org/{ORG} 过去 24h 的 open PR 和新 issue
过滤：只保留 p0/p1 标签；没有匹配项就跳过本次
输出：四列「仓库/标题/链接/状态」，最多 10 条，按更新时间排序
去向：发到 session {CHANNEL_ID}，不要发到主会话
异常：API 失败重试 1 次；仍失败只发"数据源不可用"，不要编造内容
```

同一个任务，输出从此稳定，排障也从“猜它为什么这么干”变成“对照指令看哪条没被执行”。

## 踩坑点

- **时区**。服务器默认 UTC，“每天 9 点”实际是下午 5 点。建任务时显式指定时区，别依赖主机配置。
- **调度与执行分离**。触发时间归 cron 表达式管，instruction 里别再重复“每天 9 点”，两处不一致时 agent 会困惑。
- **时间窗口用可计算表达**。“昨天”对 agent 是模糊词，写“过去 24 小时”；“上周”写“过去 7 天”。
- **假设每次执行独立**。任务可能在重启后补跑，不要依赖上一次的会话状态；需要跨次状态就落盘到文件，并在指令里写明路径。
- **别把逻辑塞进指令**。复杂处理放到脚本或 MCP 工具里，instruction 只负责编排和约束输出。它是提示词，不是程序。
- **session 隔离**。定时任务跑在主会话会污染上下文、白白烧 token，单独开 session。
- **输出漂移**。LLM 不会天然稳定复现格式，模板里放一个填好的示例行，比十句描述都管用。

## 可复用建议

- 新任务先用 5 分钟间隔跑测试版，确认输出符合预期再改成正式周期；
- 成功时保持安静（一行甚至不发），失败时详细——告警疲劳比故障更危险；
- instruction 里永远不要出现明文密钥，凭据走环境变量或凭据管理；
- 每月 review 一次所有任务的近期输出，数据源变了指令要跟着改。

## 总结

Cron 任务的 instruction 是一份会被反复重放的 prompt：把目标、数据源、过滤、输出、去向、异常语义写全，用可计算的时间表达，失败时显式报告。写清楚一次，比事后排查十次划算。
