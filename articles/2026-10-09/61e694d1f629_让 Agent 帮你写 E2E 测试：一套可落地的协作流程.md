## 背景

E2E 测试是回归体系里最脆的一层：写起来慢、selector 频繁失效、覆盖率靠人肉盘点。我们团队的现状是核心链路有测试，长尾功能基本裸奔。尝试让 Agent 参与后，长尾覆盖的补齐成本明显下降——但前提是流程要设计好。直接把需求扔给模型说"写个测试"，产物基本不可用。

## 问题

先说为什么直接生成不行：

1. **幻觉 selector**：模型没看过页面，编出来的 class 名一写就挂。
2. **断言失去语义**：AI 倾向于"按当前行为写断言"，bug 会被固化成测试。
3. **上下文不足**：不清楚项目里 Page Object 的写法、测试数据从哪来，产出代码风格割裂。

结论：Agent 不能只当生成器，要让它**看得见页面、跑得了测试**。这正是 Agent + MCP 工具链的用武之地。

## 做法

流程分四步，全程在 OpenClaw 里编排：

**1. 准备输入。** 给 Agent 三样东西：用户故事描述、项目的测试规范文件（目录结构、Page Object 约定、常用 fixture）、浏览器操作类 MCP 工具（navigate / click / snapshot / screenshot）加上测试执行工具。

**2. 探索而非生成。** 第一步不是写代码。让 Agent 用浏览器工具实际走一遍流程，每一步落一份 DOM snapshot，确认关键元素的稳定定位方式（优先 `data-testid`，其次语义 role）。这一步的产出是带真实 selector 的操作轨迹。

**3. 生成与执行闭环。** 基于轨迹生成测试代码，调用测试运行器执行。失败时把报错和截图回喂给 Agent，限定最多 3 轮修复循环，每轮要求说明"改了什么、为什么"。

**4. 人工确认断言。** 评审生成的 PR 时只重点看断言：每个断言必须标注"是需求要求的，还是现状描述"。现状描述类断言由人判断是否其实是 bug。

## 踩坑点

- **不让 Agent 真开浏览器，产出全是幻觉。** 工具调用必须强制，prompt 里明确"未 snapshot 过的元素禁止定位"。
- **等待逻辑。** Agent 很爱写硬编码 sleep。我们在规范文件里禁掉 sleep，只允许 expect 型轮询断言。
- **测试数据。** 不提供 fixture 时它会编造账号和接口。把造数方法封装成工具挂给 Agent。
- **循环失控。** 不设轮次上限时，Agent 会沿着"改测试迁就错误"的方向狂奔。3 轮修不好就转人工。
- **触发时机。** 流程变了但没人想起来补测试。建议挂在 PR 流程上：改动涉及核心链路时自动发起生成任务。

## 可复用建议

- 把"测试规范文件"当成项目资产沉淀，喂给任何 Agent 都能对齐风格，换模型也不怕。
- 探索阶段产出的 DOM snapshot 和截图随 PR 提交，评审时对照着看，效率翻倍。
- 长期统计两个指标：Agent 产出测试的**首轮通过率**（衡量生成质量）和**三个月后的 selector 存活率**（衡量定位策略是否可靠）。

## 总结

Agent 写 E2E 测试，价值不在"替代人写代码"，而在把"走一遍流程、抄 selector、套模板"这类机械劳动接过去。生成质量完全取决于你给它什么工具和约束：看得见页面、跑得了测试、断言有人把关——三者齐了，这件事才算真正成立。
