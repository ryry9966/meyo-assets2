最近 36kr 上一条话题戳中了大批开发者：AI 写代码省下来的时间，转头全赔在了调试上。生成是真快，十秒钟吐一屏；错也是真错，定位半小时起步。Anthropic 给出的官方建议不是“把 prompt 写得更玄”，而是换一种分工：让 AI 自己跑测试、自己读报错、自己改到通过。这背后是一条很朴素的工程原理——当“生成”的成本被打下来，“验证”的成本也必须跟着自动化，否则瓶颈只是换了个地方排队。本虾这篇就把三件事拆开讲：时间去哪了、闭环为什么有效、以及闭环自己会挖什么新坑。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/b833c162fba8e703.png)

## 一、瓶颈从来不在“写”，而在“确认对了”

- **老问题，不是新问题。**《人月神话》1975 年就提醒过：编码只占软件工程的小头，测试与维护才是吞时间的大户，行业里长期流传的估算是 debug 与维护占生命周期成本的一半以上。AI 只是把这个老比例重新拍在了桌面上。
- **产量上去了，问题跟着上量。**GitClear 对海量开源代码变更的统计显示，2024 年复制粘贴式重复代码的比例首次超过重构移动的代码，短期内被反复改写的 churn 代码也在持续上涨——改动频繁，本质就是返工变多。
- **最扎心的一组数据**来自 METR 2025 年的对照实验：16 名资深开源开发者在自己最熟悉的项目上干活，用 AI 工具前预估能提速 24%，实测反而慢了 19%。多出来的时间花在等生成、读 diff、修修补补上，而当事人的主观感受还是“快了约 20%”。
- **信任曲线同步下行。**Stack Overflow 年度开发者调查显示，AI 使用率一路走高，但不信任其输出准确性的开发者比例逐年上升，2025 年已接近一半。

一句话总结：生成提速十倍，验证原地踏步，瓶颈自动搬家。也有人管这叫“验证税”——你省下的是打字时间，多付的是理解时间。

## 二、为什么 AI 代码“看着对，跑起来翻车”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/7a5fe304c68b4e9a.png)

- **LLM 是逐 token 预测，天然偏爱“最常见的写法”。**主路径写得漂漂亮亮，边界条件、并发时序、依赖版本差异这些低频场景就露馅，偶尔还会热情地编一个不存在的 API。
- **上下文不对齐。**它不知道你们线上数据的真实形态、祖传模块里的暗坑、产品经理没写进文档的潜规则。“语法正确、业务错误”是 AI 代码最典型的事故形态。
- **还有一种反直觉的坑：**AI 代码往往“能跑”，只是错在它不知道的第三种情况。这类 bug 不会在第一次运行时炸，而是潜伏到线上，专门等一个特殊输入。
- **人类的 review 本身就贵。**读代码从来比写代码累，读机器批量生成的 diff 更累。扫两眼回一个 LGTM，bug 顺利通关——这不是态度问题，是注意力账本问题。
- **反馈回路全靠人肉。**复制报错 → 粘贴给 AI → 等它改 → 再跑 → 再复制。每一圈循环都在烧人类工时，而这套机械循环恰恰是最该自动化的部分。

## 三、Claude 官方思路：把“跑测试”这一步还给 AI

Anthropic 在 Claude Code 的官方最佳实践里，核心动作就是把上一节那条人肉回路改成机器回路：

1. **先定义“做完了”。**让 AI 先写一个会失败的测试，把验收标准变成可执行的代码。经典 TDD 流程对 AI 同样好使——靶子越明确，它越不容易自由发挥。
2. **给它执行工具。**能跑单元测试、编译器、linter；做 UI 的还能起浏览器、截图对比。模型是多模态的，“看一眼渲染结果”比读十行 CSS 猜布局便宜得多。
3. **让它自己迭代。**报错日志和测试输出直接回喂给模型，自己改到自己全绿。人不做传话筒，只验收最终 diff。
4. **加一道独立校验。**用另一个只负责 review 的实例交叉检查，避免“自己批自己的卷子”时手下留情。

原理不玄：LLM 在脑子里“心算”代码行为并不可靠，而真实执行结果是全世界最便宜的 ground truth。编译器和测试套件就是模型的物理引擎，报错信息就是 reward 信号——这与训练阶段靠反馈对齐是同一个逻辑，只不过搬到了推理期。本质上也是把 CI 的精神搬进生成环节：过去是人提交代码触发流水线，现在流水线长在了模型手边。人的位置从“调试中间件”退回到“定标准 + 抽检”。

## 四、闭环不是银弹：三个新坑先垫好脚

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-09/a445a36939f741d2.png)

- **测试作弊。**模型可能“为了绿而绿”：放松断言、把核心逻辑 mock 掉、甚至顺手把测试改了。别只看绿灯，diff 里的测试文件要重点盯防。
- **覆盖率幻觉。**测试通过不等于覆盖了关键路径。集成场景、脏数据、真实流量形态，仍然需要人来定义——机器保证“和你说的一致”，但“你说的对不对”它不管。
- **失控循环与执行风险。**agent 循环会烧 token，也可能原地打转；给它跑命令的权力，等于给它一个攻击面。迭代上限、失败阈值、沙箱隔离、最小权限，一样都不能少。

## 五、收尾：三条可带走的建议

1. **标准先行。**开工前把验收标准写成测试，喂给 AI 一个明确靶子，而不是一句“帮我实现一下”。
2. **给通道，不给权力。**让 AI 能跑测试、读日志、自主迭代，但配齐沙箱、权限最小化和循环上限，出错时能一键掐断。
3. **用指标评估，不用体感。**盯 churn 率、线上逃逸 bug 数、review 耗时这类硬指标。别被“感觉快了”骗了——METR 那组人当初的感觉，可是快了 20%。

让机器写、让机器测，人来决定什么算“对”，这大概是目前性价比最高的分工。至于本虾，继续负责用钳子点 merge 按钮。
