## 背景

Agent 拿到工具之后，第一件事不是调 prompt，而是划权限。在 OpenClaw 这类场景里，一个挂了 shell、文件系统和若干 MCP 工具的 agent，和只读问答机器人是两种东西：前者每一步都在对真实环境做变更。

实践里最常见的两个极端：

- **全自动**：agent 直接跑，出错靠人兜底；
- **全请示**：每个动作都弹确认，人变成橡皮图章。

两个都会失败。全自动的失败是事故，全请示的失败是确认疲劳——人看多了"是否继续？"就会无脑点允许，权限系统名存实亡。

## 问题

判断该不该问人，核心其实只有两个维度：

1. **可逆性**：这个动作错了能不能撤？
2. **爆炸半径**：错了影响多大？

再加一个实际维度：**失败成本**。删临时目录和删生产库都是"删除"，但决策级别完全不同。

## 做法

按这三个维度把工具分三档：

**T1 只读类：自己干**
读文件、查询、list、dry-run。错了只是浪费时间。这档不需要确认，但所有调用必须记日志。

**T2 可逆写操作：自己干 + 事后审计**
新建文件、本地 commit、重启测试容器、发草稿。前提是可回滚、影响限于工作区、无外部副作用。落地方式：在配置里给这类工具开白名单，同时跑在可整体回滚的上下文里（分支、快照、沙箱）。

**T3 不可逆或外部可见：必须问人**
删数据、push 远端、发消息邮件、调计费接口、改生产配置。这档的正确做法不是"弹个窗"，而是把确认做成结构化闸门：

1. agent 先给出执行计划：具体命令、diff、目标对象、影响范围；
2. 人确认后，授权精确到这一次调用，而非整个会话；
3. 拒绝时必须回报原因，agent 据此修正计划，而不是换个姿势再试。

在 OpenClaw 里可以用一个 approve 型 MCP 工具实现：T3 工具默认 deny，拿到审批结果才放行。

## 踩坑点

- **问得太频繁等于没问。** T3 划太宽（比如所有写操作都要确认），一周后人就开始盲批。宁可 T2 稍放宽，也要保住 T3 确认的注意力价值。
- **让人回答没法回答的问题。**"我可以继续吗？"是坏问题，人没有上下文。要把命令、diff、影响对象摆出来，让人看事实而不是意图。
- **被拒后绕路重试。** agent 被拒后换一个工具达成同一目的，是真实发生过的事故模式。拒绝原因要写进上下文，且 T3 白名单本身不允许 agent 修改。
- **审批丢上下文。** 长任务中途等人确认，恢复后容易丢状态。审批环节要携带任务快照，确认后能接着原计划走。

## 可复用建议

- 权限分级在配置期做死，不要让 agent 运行时自评风险；
- 所有工具调用记日志，T2 靠审计兜底；
- 审批内容 = 命令 + diff + 影响范围，拒绝必须带原因；
- 新接入的 MCP 工具默认进 T3，观察一周再降级；
- 无人值守场景（定时任务、CI 里的 agent）只允许 T1/T2，T3 直接跳过并留待处理记录。

## 总结

权限边界不是安全插件，而是 agent 能否被长期使用的前提。原则一句话：**可逆的自己干，不可逆的问人，问人时要给人能判断的信息。** 把分级做进配置、把审批做成闸门，agent 才能从演示玩具变成可以挂进生产流程的东西。
