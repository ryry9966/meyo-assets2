## 背景

Agent 的能力边界，基本等于它能调用的外部服务边界。MCP 工具、HTTP API、第三方模型服务……这些都可能超时、限流、返回 5xx。对一个跑自动化任务的 Agent 来说，"外部 API 挂了"不是异常路径，而是日常。但很多实现只设计了"一切正常"的路径，失败一来就原形毕露。

## 问题

实际跑起来，常见三种坏法：

1. **无限重试烧 token**：模型拿到报错后自行决定"再试一次"，循环几十轮，任务没成，账单先爆。
2. **假装成功**：工具调用失败但错误被吞掉，模型基于幻觉结果继续往下走，产出脏数据。
3. **部分完成不可恢复**：任务执行到一半挂掉，没有断点，重跑要么从头来，要么造成重复写入（重复下单、重复发消息）。

## 做法

建议按三层来兜：

**工具层：把失败变成"可控的失败"**
- 每个 HTTP 工具显式设置超时，不要依赖默认值。
- 重试只做 2~3 次，指数退避加抖动（jitter），且只在幂等操作上开。
- 非 2xx 响应统一封装成结构化错误：`{"error": "upstream_timeout", "retryable": true}`，别把原始堆栈直接丢给模型。

**Agent 层：限制模型的"自救次数"**
- 在系统提示或工具描述里明确：同一工具连续失败 N 次（比如 3 次）后必须上报，不许继续盲试。
- 实现断路器：某工具连续失败达到阈值，后续调用直接快速失败，等冷却窗口过了再放行，避免雪崩式重试。
- 错误信息写给模型时要"可决策"：告诉它这是限流还是参数错误，重试有意义还是该换路径。

**流程层：留断点，留退路**
- 长任务按步骤落 checkpoint（存本地文件或数据库），失败后从断点续跑，不重头再来。
- 关键外部依赖准备降级路径：备用 API、缓存数据，或者干脆挂起任务转人工。
- 所有对外有副作用的写操作，先记日志再执行，方便事后对账和补偿。

## 踩坑点

- **非幂等操作加重试 = 事故**。POST 下单接口重试三次，可能真的下三单。要么用幂等键，要么写操作不自动重试，交给上层决策。
- **超时设得比上游网关还长**。你设 60s，上游 30s 就掐了，你的重试全在等一个永远不会来的响应。
- **让模型自己判断"要不要重试"，却不给它失败计数**。上下文被截断或跨会话后，模型没有记忆，会一直觉得"这次也许能成"。
- **把 4xx 和 5xx 一视同仁**。401 该报警改凭证，503 才值得退避重试，混在一起处理会掩盖真正的问题。

## 可复用建议

- 错误返回结构化、带 retryable 标记，模型才有判断依据
- 重试上限 + 断路器，双保险，缺一不可
- 写操作必须有幂等键或显式人工确认
- checkpoint 粒度对齐到"外部副作用发生之前"
- 监控单独统计工具失败率，别只看任务成功率

## 总结

Agent 的可靠性不靠 prompt 祈祷，靠的是把失败当成一等公民来设计：工具层控制失败形态，Agent 层限制自救次数，流程层保证可恢复。外部 API 迟早会挂，问题只是挂的时候，你的系统是优雅降级，还是在烧 token 演出一场永不谢幕的重试。
