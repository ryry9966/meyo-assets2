## 背景

日常自动化里最常见的工作流是这样的：主 Agent 接到一批任务——汇总十几个信息源、给多个模块跑检查并修复、批量整理文件。单 Agent 的做法是逐个执行，痛点很典型：

- 中间过程全部堆进主会话上下文，跑两轮之后上下文就脏了，后续决策质量明显下降；
- 串行耗时，一个 20 分钟的任务卡住后面所有事；
- 单点失败，第一步挂了整条流水线停摆。

OpenClaw 的 subagent 机制正好针对这个问题：主 Agent 可以派生子 Agent，每个子 Agent 拥有独立上下文，执行完毕把摘要交回主 Agent。

## 问题

具体到我的场景：每周自动产出一份技术周报，需要读多个来源、分别提炼、再汇总。改造前全流程 30 分钟以上，中途任何一步出错都要人工重跑整条链路。

## 做法

1. **先做任务切分，确认独立性。** 并行的前提是子任务之间没有共享读写目标。我把“读来源”拆成 N 个互不相干的子任务，汇总单独留给主 Agent。
2. **定义输出契约。** 在给主 Agent 的指令里明确：每个 subagent 只做一件事，详细产出写入工作区指定文件（如 `digest/<来源名>.md`），返回给主 Agent 的只有三行——状态、产物路径、一句话摘要。
3. **fan-out / fan-in。** 主 Agent 一次性派发 N 个 subagent 并行执行，收拢后读取产物文件做汇总。主 Agent 自己不做重活，只做调度和聚合。
4. **控制并发。** 实测并发 3~4 是性价比拐点，再多收益递减、token 消耗陡增。指令里写明“最多同时 4 个”。
5. **失败显式上报。** 契约里约定失败也要返回 status: failed 和原因，主 Agent 对失败子任务重试一次，仍失败则标记跳过，不阻塞整体。

## 踩坑点

- **共享文件冲突。** 两个 subagent 同时改一个文件会互相覆盖。解法是按目录切分工作区，或用 git worktree 隔离后再合并。
- **子 Agent 输出倒灌主上下文。** 早期没限定返回长度，subagent 把全文塞回来，主上下文照样爆。必须在指令里硬性限制返回摘要的字数。
- **隐式依赖被并行化。** 有一次任务 B 依赖任务 A 的产物，派发时没识别出来，并行后 B 读到空文件。经验：派发前逐对检查读写关系，有依赖就老实串行。
- **静默失败。** subagent 超时或报错如果不上报，主 Agent 会误判任务成功。失败路径必须和成功路径一样有明确约定。

## 可复用建议

- 输出契约模板固定下来：`status / 产物路径 / ≤50 字摘要`，所有编排场景直接复用；
- 主 Agent 只做调度、聚合、异常处理，重活全部下沉给 subagent；
- 并发上限 3~4，单任务设超时，失败重试一次后跳过并记录；
- 产物走文件、不走对话：文件是稳定的 fan-in 接口，对话不是。

## 总结

subagent 编排的价值不是“Agent 多所以快”，而是三件事：上下文隔离、失败隔离、把主 Agent 从执行者变成调度者。这套 fan-out/fan-in 加文件交接的模板，已经在周报生成、批量检查、素材整理三类场景复用。改造成本主要在任务切分和输出契约上，建议先在一个小场景跑通，再逐步推广。
