## 背景

OpenClaw 的 Agent 默认带 exec 能力，理论上它可以执行 `rm`。社区里被问得最多的不是"能不能做到"，而是"为什么默认配置下很少出事"。答案不是某个单一开关，而是一组叠加的防御层。这篇帖把这四层拆开讲一遍，附上我自己验证过的配置思路。

## 问题：把模型当普通用户授权

一句话概括风险模型：**模型输出是建议，执行层必须假设它会犯错**。误删文件的典型路径有三条：

1. 相对路径歧义：Agent 在错误的 cwd 下执行 `rm -rf ./build`；
2. 通配符过宽：`rm -rf *`，或变量为空时的 `rm -rf "$DIR/"`；
3. 越界操作：目标路径写错，落在 workspace 之外。

任何单层防御都挡不住这三种情况同时出问题，所以 OpenClaw 的思路是把多层叠起来，让单一失误不至于变成事故。

## 做法：四层叠加

**1. workspace 锚定。** exec 默认以 workspace 为根启动，Agent 语义里的"相对路径"被约束在这个目录内。这是最便宜的一层，先把大部分误操作圈住。

**2. 容器 sandbox。** 开启 sandbox 后，exec 在独立容器里运行，workspace 以挂载方式进入容器，宿主机其余文件系统根本不在它的视图里。就算它真的跑了 `rm -rf /`，删的也是容器层。挂载进容器的宿主路径用 allowlist 控制，宁少勿多。

**3. 工具策略。** 每个 Agent 可对工具按 allow / ask / deny 配置。我的实践是：写文件 allow，exec 设为 ask，网络类工具按需开。ask 会打断自动化，但对删除类动作，这个打断值得。

**4. 快照兜底。** 会话开始前对 workspace 做快照，出问题可回滚。它不阻止事故，但把恢复成本压到分钟级。

## 踩坑点

- **开了 sandbox 不等于安全**：如果 allowlist 里挂了整个 HOME，容器隔离形同虚设，挂载粒度务必按目录走。
- 配置完要**实测**：故意让 Agent 执行一条越界 `rm`，确认它会被询问或拦截，而不是只看配置文件以为生效了。
- **审批疲劳本身就是漏洞**：ask 配太多工具，人会被频繁打断，最后开始无脑点确认。只对高风险动作保留 ask。
- 容器**网络出口要收紧**，删除之外，数据外带同样要防。
- 迁移 workspace 后快照路径容易失效，**快照目录要显式固定**，否则回滚时找不到。

## 可复用建议

- 分层原则记住四个词：**锚定、隔离、审批、可回滚**。缺任何一层，都挡不住一个"自信的模型"。
- 三个最小先于一切高级配置：最小挂载、最小工具集、最小网络。
- 定期跑一次"红队脚本"：故意让 Agent 越界删除，验证整条链路行为符合预期，这应该进 CI 或至少进月度检查。
- 这套策略写进仓库里的 agent 配置文件，跟着版本走，别靠手工改。

## 总结

Agent 不会误删文件，不是因为模型变聪明了，而是因为执行层假设它会犯错。OpenClaw sandbox 模型的本质，是把"信任"从模型身上移走，交还给一层层可验证的工程约束。配置成本半小时，换来的底线是：**单点失误永远到不了你的原始数据**。
