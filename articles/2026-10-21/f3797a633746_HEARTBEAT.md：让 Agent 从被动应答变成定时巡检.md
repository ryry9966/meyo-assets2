# HEARTBEAT.md：让 Agent 从被动应答变成定时巡检

## 背景

大多数 Agent 的交互是"你问它答"：不发消息，它就静默停着。但真正跑起来后你会发现，很多事是"到了时机该看一眼"的：仓库有没有脏状态、日报草稿该不该生成、本地服务的日志有没有异常。这类事不适合每次都靠你想起来手动触发。

OpenClaw 提供了一个很轻的机制：心跳（Heartbeat）。系统默认约每 30 分钟给主 Agent 发一个极简提示词，让它读工作区里的 `HEARTBEAT.md`，判断这次"醒来"有没有事可做。没事就回复 `HEARTBEAT_OK`，这条回复默认不会转发到聊天渠道——不打扰你，但会有少量 token 消耗。

## 问题

机制本身简单，难点在于：怎么写 HEARTBEAT.md 才能既"该说的时候说"，又"不该说的时候闭嘴"。写得含糊，Agent 要么每次心跳都来汇报刷屏，要么永远沉默，形同虚设。

## 做法

1. **在工作区创建文件**。默认路径 `~/.openclaw/workspace/HEARTBEAT.md`，每条任务写清三件事：触发条件、执行动作、沉默条件。例如：

```markdown
- 检查 ~/projects/api 的 git 状态；仅当存在超过 1 天的未提交变更时，
  摘要发到 #dev-alerts，否则保持沉默
- 上午 9 点后的第一次心跳，汇总本地 RSS 未读，发到 #daily-digest
```

2. **用 `#频道名` 做定向投递**。心跳输出默认不进主聊天；指定频道后，告警和日常摘要就分开了，不会互相淹没。

3. **调整频率**。`HEARTBEAT_INTERVAL_SECS` 默认 1800 秒，巡检类任务够用；想更灵敏可以缩到 5-10 分钟，但要接受 token 成本近似线性上升。调试期用 `HEARTBEAT_DISABLED=1` 关掉，避免心跳干扰你测试。

4. **复杂逻辑下沉到 skill**。心跳每次都会把 HEARTBEAT.md 全文带入上下文，所以文件本身要短——判断逻辑写进脚本或 skill，条目里只留"何时调用它、结果发给谁"。

## 踩坑点

- **别把它当 cron**。心跳没有精确时刻语义，"9 点整跑批"应该用系统定时任务，心跳适合"周期性看一眼有没有事"。
- **沉默条件比触发条件更重要**。我们第一条规则只写了"检查 git 状态"，结果一晚上收到十几条正常状态报告。改成"仅当满足 X 才报告"才安静下来。
- **心跳跑在主会话里**。巡检产生的大量工具调用会占用主 Agent 的上下文，也会和你正在进行的对话抢会话。重活丢给后台脚本，心跳只做"读结果、做判断"。
- **留审计痕迹**。让它每次行动时往 `heartbeat-log.md` 追加一行。没有这个日志，你很难复盘"它昨晚为什么给我发那条消息"。

## 可复用建议

- 每条任务固定为「条件 → 动作 → 频道 → 沉默规则」四段式，全文控制在 15 行以内。
- 把任务分成"静默巡检"（只在异常时出声）和"定期汇报"（固定频道定期输出）两类，混写很容易乱。
- 每月清理一次：从没触发过的删掉，频繁误报的收紧条件。HEARTBEAT.md 是活配置，不是一次性文档。

## 总结

HEARTBEAT.md 的价值不在机制本身——一个定时器加一个约定文件——而在于它强迫你把"Agent 应该主动关心什么"写成明确、可判定的条件。写好"何时沉默"，比写好"何时行动"更决定体验。建议从一个低风险任务起步（比如 git 脏状态巡检），跑一周看日志，再逐步加码。
