## 背景

用 OpenClaw 这类 agent 框架跑日常任务，最大的体验断层不在模型能力，而在"每次会话都是陌生人"。session 是无状态的：你上礼拜刚纠正过"commit message 用中文、遵循 conventional commits"，这周它又开始输出英文。这类偏好级信息重复出现两三次之后，大多数人都会想同一个问题：能不能让它自己记住。

## 问题

我们第一版做法很朴素：把历史会话摘要全塞进 system prompt。跑了两周暴露三个问题：

1. token 成本线性上涨，注入内容约 80% 和当前任务无关；
2. 偏好淹没在对话流水里，模型该忽略的还是忽略；
3. 存进去的"记忆"没法改、没法删，用户完全不透明。

结论：记忆不是"存得多"的问题，是"存什么、何时取、如何过期"的数据工程问题。

## 做法

现在跑的方案分五步，全部可以用 OpenClaw 的插件 / MCP 机制落地：

**1. 分层。** 只做三层：session 内的 working memory（框架自带，不用管）、用户偏好层（长期稳定的事实）、事件层（"上周三我部署过 X"，可选）。精力集中在偏好层。

**2. 写入靠筛选，不靠全量。** 在 session 结束的 hook 里跑一个轻量抽取 prompt，只提取满足条件的陈述：带"以后 / 总是 / 默认 / 不要再"这类稳定信号，或用户明确纠错模型行为。每条记忆带四个字段：`content`、`scope`（全局 / 某项目）、`confidence`、`updated_at`。隐式推断的记忆 confidence 打低分，供后续合并。

**3. 存储 SQLite 就够。** 字段化存储优先于向量库。偏好总共几十上百条，scope 过滤加关键词匹配已经足够准。等记忆过千条、自然语言查询需求真出现，再上 embedding 不迟。

**4. 注入要限量。** session 启动时按 `scope 匹配 > confidence > updated_at` 排序取 top-K，硬性控制在 300–500 token 预算内。同时把 memory 做成 MCP 工具（`memory_search` / `memory_write`），让 agent 在任务中按需查写，而不是只靠开局注入。

**5. 更新与遗忘。** 新旧记忆冲突时保留新值、旧值进历史表（别直接删，调试要用）。连续 N 个 session 未命中且 confidence 低的记忆降权。给用户一条命令直接查看和清除全部记忆——透明度决定用户敢不敢让它记东西。

## 踩坑记录

- **把一次性内容当偏好存。** 早期版本存进了"用户下周要去东京"，一个月后它还在推荐东京餐厅。解决：抽取 prompt 明确只收"跨会话有效"的陈述，带时间范围的一律拒收。
- **冲突不处理，行为飘忽。** 同一偏好的新旧版本同时注入，模型随机听哪个。必须有 merge 逻辑，宁可信最新的。
- **注入无日志。** 记忆改变 agent 行为是隐性的，排查"它为什么突然这么做"时两眼一抹黑。现在每次注入都写 debug 日志，标明命中了哪几条。
- **明文存敏感信息。** 记忆文件里出现过 API key 相关内容。现在抽取阶段加正则过滤，记忆默认只存本地、不随配置同步。

## 可复用建议

- 先用"一个 JSON / SQLite 文件 + session 启动时加载"跑起来，够用很久，别一上来上向量库。
- 记忆单元是"带 scope、confidence、时间戳的事实"，不是散文段落。
- 读写都做成工具而非纯 prompt 注入，agent 的自主性会明显提升。
- 永远给用户保留"看和删"的入口。

## 总结

记忆系统的本质是数据治理：小而准、有冲突处理、会过期、可审计，比一个大而全的向量 dump 有用得多。偏好记忆做对之后，体感提升非常直接——它终于像一个用过一个月的助手，而不是每天重逢的陌生人。
