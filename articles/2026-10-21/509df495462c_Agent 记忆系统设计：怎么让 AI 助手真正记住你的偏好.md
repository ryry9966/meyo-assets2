# Agent 记忆系统设计：怎么让 AI 助手真正记住你的偏好

## 背景

模型本身无状态，每次新会话都是陌生人。上下文窗口再大，也解决不了跨会话的问题。对 OpenClaw 这类常驻 Agent 来说，记忆不是锦上添花，而是能不能“长期用下去”的分水岭。我们给社区的自动化 Agent 加了一套记忆系统，跑了几个月，踩了不少坑，把经验整理出来。

## 问题

三种常见的失败模式：

1. **全塞上下文**：token 爆炸，关键偏好被噪声淹没，成本和效果双输。
2. **指望模型自己记住**：换个会话就清零，还偶发“幻觉出假记忆”。
3. **只存不治**：记忆越攒越多，过时、互相矛盾，检索回来的一半是错的。

核心矛盾在于：**写什么、怎么存、何时取、如何纠错**——这四件事没有一件是靠调 prompt 能解决的。

## 做法

**1. 分层定义记忆。** 三层就够：

- `profile`：稳定偏好（语言、代码风格、常用路径），每次会话常驻注入；
- `episodic`：会话中产生的事实（项目背景、某次踩坑结论），按需检索；
- `procedural`：被用户纠正过的行为（“commit message 别加 emoji”），冲突时优先级最高。

**2. 存储做成独立 MCP server。** 工具面收窄到四个：`memory_search` / `memory_put` / `memory_delete` / `memory_list`。SQLite 起步完全够用，别一上来就上向量库。

**3. 写入走显式提炼，不做全文摘抄。** 会话结束时跑一次抽取，每条记忆只放一个原子事实。schema 固定：`{type, content, confidence, source_session, created_at, last_hit_at}`。

**4. 读取分两路。** system prompt 常驻 profile 层（控制在几百 token 内）；episodic 层按当前任务做 top-K 检索注入。关键词检索先跑通，条目过万再考虑 embedding。

**5. 纠错通道必须有。** 用户说“不对，我不用 pnpm 了”时，不是新增一条，而是 supersede 旧条目并打时间戳；`memory_list` 让用户随时审计、删除。

## 踩坑点

- **记忆污染最难治**。一条错误偏好被反复检索，会不断被模型复述、强化，用户越用越烦。对策：confidence 随“被反驳次数”衰减，低于阈值自动归档。
- **抽取太勤 = 噪声**。早期我们每轮对话都写，两周攒了几百条“用户今天问了 X”。改成会话结束批处理 + 重要性阈值后，条目数量降了一个数量级。
- **冲突别合并**。新旧偏好直接 merge 会得到四不像，永远用 supersede + 时间戳。
- **条目别写长句**。检索命中率最高的都是 15 字以内的短条目，长叙述拆成多条。
- **隐私边界**：memory server 单独设权限 scope，密钥、凭证类内容在抽取层直接拒绝写入。

## 可复用建议

- 记忆是**数据工程问题**，不是 prompt 问题。先定 schema 和生命周期，再谈检索算法。
- 让用户**看得见、删得掉**。一个 `memory_list` 命令带来的信任，比任何“聪明”的检索都值钱。
- 留一组**固定评测题**：跨会话问 10 个偏好相关的问题，数命中个数，每次改动跑一遍，防止越改越差。
- 从 SQLite + 关键词开始，容量和延迟真逼你升级了再换工具。

## 总结

让 Agent 记住偏好，本质是搭一条“提炼 → 存储 → 检索 → 纠错”的数据管线，模型只负责其中抽取和理解的环节。做对的关键不在算法炫技，而在三件朴素的事：**原子化条目、显式生命周期、用户可审计**。先把这三件做扎实，你的 Agent 才算真正“认识”你。
