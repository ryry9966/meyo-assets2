最近，OpenAI Codex 团队的产品负责人 Alexander Embiricos、agent 工程负责人 Ben Chess 等核心成员接连做了几场复盘访谈，36kr 以《编程顶流是如何诞生的》为题编译后刷了屏。这个项目最有意思的地方在于：它不是一路顺风的天才故事——第一代 Codex 在 2021 年诞生、2023 年被官方亲手弃用，2025 年又以 agent 形态翻红，几个月内成为开发者日常工具。复盘里最值钱的不是故事，而是一套被验证过的工程方法论。本文按「历史—技术—产品—团队」四层拆给你看。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-21/096d91276b660d0d.png)

## 一、先补背景：一个名字，两代 Codex

- **第一代（2021）**：基于 GPT-3 做代码微调，是 GitHub Copilot 背后的引擎，定义了「IDE 里逐行自动补全」的范式。Copilot 的成功证明了代码辅助有真实需求，但当时没人相信模型能独立干完一个任务。
- **退场（2023）**：GPT-3.5 / GPT-4 综合能力更强，第一代 Codex API 官方下线，多数人以为这页翻过去了。
- **重启（2025）**：o 系列推理模型 + 强化学习成熟后团队卷土重来——4 月开源 Codex CLI，上线后 star 数迅速破万；5 月发布云端编码 agent，底层模型 codex-1 官宣在 SWE-bench Verified 上拿到 72.1%；9 月 GPT-5-Codex 把成绩推到约 74.5%。
- **关键差别**：第一代是「预测下一行」，新一代是「自主完成一个任务」。同名重启不是情怀，是底层能力换了血。

## 二、核心机制：为什么 RL 偏偏在代码上跑通了

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-21/4a8d624e16bf88d9.png)

访谈里被反复强调的一点：代码是极少数天然适配强化学习（RL）的领域。以前 RL 难做，是奖励难定义；代码领域恰好自带裁判。

1. **可验证奖励（verifiable reward）**：一个 bug 修没修好，跑一遍测试就知道。奖励客观、自动、可大规模生成，不依赖人工标注偏好——这在对话、写作类任务里很难做到。
2. **RL 环境（environments）**：团队搭了一套基础设施，从真实仓库生成数以万计的训练任务（修 bug、实现 feature），每个任务自带测试套件和独立沙盒容器，可以大规模并行训练。
3. **长时程迭代**：模型学会「改代码 → 跑测试 → 读报错 → 再改」的循环，能自主连续工作几十分钟。训练里常见这样的轨迹：先跑测试复现问题，定位到某个解析函数，修改后重跑，全绿才算交卷。
4. **顺带学出工程习惯**：训练目标里明确要求「只做最小改动、遵守代码风格、测试不过不收工」，这些约束被 RL 固化进模型行为。
5. **数据飞轮**：Codex 被用来开发 Codex——它帮团队写评估、修基础设施、产出新的训练任务，越用越强。

## 三、产品转向：从「打字机」到「异步队友」

- **旧范式**：你打字、它补全，人盯着屏幕，秒级反馈，模型潜力被交互锁死。
- **新范式**：云端 agent。每个任务跑在预装好仓库的独立容器里，几分钟到几十分钟后回来一份 diff / PR。
- **关键判断**：当模型能自主思考分钟级，硬塞进 IDE 补全的壳里就是浪费。异步并行才是对的容器——早上把「给登录模块加限流」和「修一个 flaky test」两个任务派出去，开完会回来，两份 PR 已经在等你 review。
- **人的角色变了**：从「打字员」变成「审稿人 + 调度员」。复盘里说得很直白：读 diff、做评审的能力，比打字速度值钱得多。交互形态必须配得上模型能力，这是一条可以外推的产品教训。

## 四、团队打法：复盘里最值得抄的五条

1. **小团队、全栈、快出活**：Codex CLI 最初是几个工程师几周内做出来的开源工具；研究员直接写产品代码，不做「研究做完交产品」的接力。
2. **Evals 先行**：评估体系被当成核心资产。没有好的 eval，迭代方向全靠感觉；有 eval，每周的模型升级才有裁判。
3. **模型与产品共同设计**：产品形态反哺训练目标。因为要做异步 agent，训练时就强调长时程任务、最小 diff、自我验证。
4. **内部 dogfood 走在发布前面**：员工大规模日常使用，问题先在自己身上暴露，再面向外部。
5. **发布即迭代**：不憋大招——CLI 先开源收反馈，agent 随后跟进，几个月内连续升级。

## 五、三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-21/d730fc3fd8db6fa5.png)

1. **把「可验证」当设计杠杆**。无论做产品、带团队还是给 agent 派活，尽量让任务有明确的通过标准（测试、指标、验收口径）。可验证性决定了一个任务能不能被安全地委派出去——这是 agent 时代最实际的分水岭。
2. **先修工作流，再换工具**。异步委派 + 代码评审的流程，往往比换一个更贵的模型提升更大；小步提交、把 issue 描述写清楚，就是对 agent 最好的「提示词工程」。
3. **生成 ≠ 正确**。测试通过不代表语义正确，依赖审计、安全边界仍需人来兜底。把 AI 当成一个打字飞快、极度自信、偶尔闯祸的实习生——它交的东西，你要签字负责。

顶流的诞生不靠玄学：可验证的奖励、能自转的飞轮、敢砍敢重启的决策。这三样东西，放进任何一个工程团队都成立。
