# 背景

在 OpenClaw 的插件和自动化流水线里，让 LLM 返回结构化结果是常态：工具调用决策、参数抽取、分类打标。我们惯用的约定是在系统提示里要求模型「用 `<json>` 标签包裹输出」，或者输出带 ```` ```json ```` 围栏的代码块。但约定只是约定——换个模型、调高温度、提示词改动一行，输出格式就开始漂移。

# 问题

整理了近两个月插件日志里的解析失败样本，混合格式主要有四种形态：

1. 有时带 `<json></json>` 标签，有时标签被丢掉只剩裸 JSON；
2. 标签和围栏叠加：`<json>` 内部又套了一层 ```` ```json ```` 围栏；
3. JSON 前后带寒暄文本（「好的，以下是结果：」），字符串值里混着中文引号、全角冒号；
4. 一次输出里出现两个 JSON 块，贪婪正则把两个拼成了一个。

单一策略都有盲区：只做 `json.loads` 挂在 2/3，只剥围栏挂在 1/3，只匹配标签挂在 2/4。

# 做法

核心思路：把解析器做成一条**分层管线**，按成本从低到高逐层尝试，任一层成功即返回，全部失败则带着原始输出进入重试。

1. **直接 `json.loads`**：开了 JSON mode / 函数调用时命中率最高，零成本，放最前；
2. **标签提取**：对自定义标签用非贪婪正则取内部内容，标签缺失则跳过；
3. **围栏剥离**：匹配 ```` ```json ... ``` ````，用非贪婪模式，并容忍围栏不闭合；
4. **括号平衡截取**：从第一个 `{` 用计数器扫到配对的 `}`，天然免疫贪婪匹配问题；
5. **宽松修复**：去 BOM/零宽字符、全角标点转半角、去尾逗号，再试一次 loads；
6. **失败兜底**：把解析错误和原始输出回传模型重试一次，仍失败就抛异常并落盘原始报文。

```python
def extract_json(text: str) -> dict:
    for fn in (loads_direct, tag_extract, fence_strip,
               brace_balance, lenient_fix):
        try:
            return validate_schema(fn(text))
        except Exception:
            continue
    raise ParseError(raw=text)
```

注意：每一层成功后还要过 schema 校验（pydantic/jsonschema）——**解析成功不等于语义正确**。

# 踩坑点

- 括号平衡扫描要跳过引号内的 `{}`，否则字符串值里有花括号就会截断错位；
- 字符串值里出现 ` ``` ` 会破坏围栏剥离的正则；实测括号平衡这层比剥围栏更稳，可以提前或两层都试；
- Python 的 `json.loads` 默认接受 `NaN/Infinity`，这是非标准 JSON，下游序列化会炸，校验层要拦；
- 修复层别太激进：修不动的就失败，静默「修好」的数据比失败更难排查；
- 中文场景下全角引号/冒号出现频率远比想象高，值得单独一层处理。

# 可复用建议

- 全项目只留一个 `extract_json` 入口，禁止各插件自写正则；
- 失败时把原始输出、各层尝试结果写进 trace，支持离线回放；
- 用**真实失败样本**建语料库做单元测试，比拍脑袋造的 case 有价值得多；
- 运行时支持结构化输出（JSON mode / tool schema）就优先用，标签解析只做兜底，不当主路径。

# 总结

LLM 输出格式漂移不是异常，而是常态。防御性解析的价值不在某个聪明的正则，而在「分层降级 + 显式失败 + 可回放」这套结构。把混合格式处理收敛成一个经过真实语料测试的工具函数，比在每个插件里各自打补丁省心得多。
