## 背景

OpenClaw 里的 agent 默认是被动响应：有人发消息才干活。但做自动化迟早会遇到"没人说话也要干活"的场景，平台给了两条路：

- **cron**：经典定时任务，用 cron 表达式定义"到点执行"，到点把预设 prompt 投递给 agent；
- **heartbeat**：心跳循环，每隔固定间隔（默认 30 分钟，可配置）唤醒 agent 一次，由 agent 自己判断有没有事要做，没事就回 `HEARTBEAT_OK` 保持沉默。

两者都能让 agent 定期醒来，但语义完全不同。

## 问题：什么时候该用哪个

典型误用有两种。一是用 heartbeat 做"每天 9:00 发日报"——心跳是 tick 不是闹钟，它可能在 8:47 刚醒过，9:00 的精度不可控。二是用 cron 做"每 5 分钟看一眼收件箱有没有新邮件"——你得拆成几十条任务，而 cron 每次触发都是一次完整的模型调用，纯空转检查既贵又吵。

本质区别一句话：**cron 表达的是"时刻"，heartbeat 表达的是"状态巡检"**。

## 做法

**选 cron：**
1. 触发条件能写成确定时刻（每天 9:00、每周一整点），就用 cron；
2. 写 cron 表达式 + 投递 prompt，把"做什么、输出到哪、要不要 @ 谁"写全——cron 触发的调用与主会话是隔离的，别指望它记得聊天上下文；
3. 一次性任务加上一次性标记，用完即焚，避免僵尸任务堆积。

**选 heartbeat：**
1. 触发条件是"看一眼状态再说"，就用 heartbeat；
2. 间隔先调粗（30 分钟起步），跑几天再收紧；
3. 心跳 prompt 是关键：写清楚检查哪些项、什么条件算"有事"、什么情况必须回 `HEARTBEAT_OK` 跳过。不写跳过规则，agent 每个周期都会输出内容，消息刷屏、token 翻倍。

## 踩坑点

- **时区**：cron 表达式按 agent 运行环境的时区解析，容器里 `TZ` 没设对，"9 点"就是 UTC 9 点。部署后先跑一条一分钟间隔的测试任务验证；
- **心跳成本**：heartbeat 每个周期都是一次真实调用，哪怕只回 `HEARTBEAT_OK`。间隔 5 分钟的长驻 agent，月底账单会让你重新评估这个数字；
- **cron 的会话隔离**：投递的 prompt 默认拿不到主聊天上下文，需要历史信息时要在 prompt 里显式指定读哪个 session，或让它调用工具去取；
- **心跳里跑长任务**：重活会拖慢周期甚至叠跑。正确姿势是心跳只负责"发现并派发"——记一条状态、触发一个独立任务，自己别下场干重活；
- **静默失败**：cron 任务挂了（表达式错、session 不存在）往往不报错，只是不执行。上线后定期用 `cron list` 核对下次触发时间。

## 可复用建议

- 决策口诀：**通知类、时刻明确的用 cron；看护类、状态驱动的用 heartbeat**；
- 两者可以组合：heartbeat 巡检和派发，cron 负责精确定时通知，心跳里顺带核对 cron 任务是否按预期执行；
- 心跳 prompt 当配置对待，进版本管理，每次改间隔或检查项都留 diff；
- 接新需求先问一句："这件事需不需要知道'现在是几点'？"需要，cron；只需要"每隔一段时间看一眼"，heartbeat。

## 总结

cron 和 heartbeat 不是竞品，是两种触发语义：一个是闹钟，一个是脉搏。把"时刻驱动"交给 cron，把"状态驱动"交给 heartbeat，再用 `HEARTBEAT_OK` 和合理的间隔把心跳成本摁住，OpenClaw 里的定时自动化就少了一大半玄学问题。
