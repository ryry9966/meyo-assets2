## 背景

跑 Agent 一段时间后你会发现：LLM 本身很少出问题，真正把流程打断的，大多是外部依赖——搜索 API 限流、模型供应商超时、某个插件背后的第三方服务 503。OpenClaw 这类常驻型 Agent 尤其明显：它 7x24 挂着，任何一次外部抖动都可能发生在你不在场的时候。MCP 工具、自建插件、第三方 skill，本质上都逃不开这个问题。

## 问题在哪

把失败的工具调用原始报错直接抛回给 LLM，通常出现三种糟糕结局：

1. **无限重试**。模型看到报错就"再试一次"，没有退避策略，几分钟烧掉大量 token。
2. **幻觉兜底**。模型编一个看起来合理的结果继续往下走，你事后才发现数据是假的。
3. **整条链路卡死**。一个非关键步骤失败，任务整个中断。

核心原因：Agent 分不清"暂时性错误"和"永久性错误"，而我们把重试决策完全交给了它。

## 我的做法

分三层处理，思路是"能在代码里决定的，别让模型决定"。

**第一层：工具层统一错误信封。** 所有插件调用外面套一层 wrapper，不管内部怎么挂，返回给模型的结构固定为 `{ok, error_type, retryable, retry_after, hint}`。error_type 区分 transient（超时/429/5xx）和 permanent（401/404/参数错误）。模型拿到的不是原始堆栈，而是一句人话提示。

**第二层：代码里做退避和熔断。** transient 错误在 wrapper 内部先做 2–3 次指数退避重试（带 jitter，尊重 Retry-After），失败才上抛。每个工具维护失败计数，连续失败 5 次进入熔断，冷却期内调用直接返回"工具暂不可用，请走降级路径"，不再真正发请求。

**第三层：告诉模型退路。** 在每个工具的 description 里写清失败策略，比如"若 retryable=true，等待后重试，最多 3 次；若 permanent，直接告知用户，不要编造结果"。重点写上"不要编造结果"——实测它确实能压住大部分幻觉兜底。

降级策略按工具重要性区分：搜索类挂了，让 Agent 说明"该来源暂不可用"并继续；写库、支付这类关键操作宁可硬失败，让任务停在安全点。

## 踩过的坑

- **重试非幂等操作**。一次网络超时 + 自动重试，重复创建了两条记录。现在所有写操作强制带 idempotency key。
- **熔断太敏感**。一次短暂限流把工具熔断 10 分钟，误伤正常请求。后来把 429 和 5xx 分开计数，阈值和冷却时间分开调。
- **把错误响应缓存了**。缓存层不分成败，一个 503 的响应被缓存了几分钟。
- **system prompt 只写"遇到错误自动重试"，没写次数上限**。模型真的会一直试。

## 可复用的建议

- 错误信封结构定下来就别动，所有插件对齐，Agent 行为才会稳定。
- "不要编造结果"写进工具描述，而不是 system prompt——模型对工具描述的注意力更高。
- 每次工具失败打日志，带 request id，事后排查全靠它。
- 先只做错误分类 + 退避重试这两件事，熔断和降级等真被故障痛过再加，不要一步到位堆架构。

## 总结

Agent 的错误恢复不是一个模块，而是一组约束：代码管重试和熔断，模型管选择退路，prompt 管住幻觉。外部 API 一定会挂，目标不是让它不挂，而是挂的时候 Agent 能体面地降级，而不是烧着 token 编数据。
