## 背景

OpenClaw 的 agent 配置里挂多个 model profile 是常规操作：一个云端强模型（GPT 系列），一个本地推理服务（Ollama / vLLM 跑 Qwen 或同级开源模型）。但实践中容易走两个极端：要么全走云端，月底账单难看；要么全走本地，agent 在复杂任务上频繁翻车。路由不是配置问题，而是成本、质量、隐私三者之间的工程权衡。

## 问题

我的自动化工作流大致三类负载：规划和工具编排（多步推理、function calling）、批量文本处理（摘要、清洗、格式转换）、涉及内部文档的处理。第一类用本地模型经常参数幻觉、流程中断；第三类直接扔云端又有合规顾虑。混着用但没有规则，等于每次都在赌。

## 做法

1. **按出错代价给任务分级**，而不是按任务类型。A 类：出错会导致流程中断或错误操作的（规划、工具编排、写库），走云端强模型；B 类：出错可被下游校验兜住的（摘要、翻译、打标签），走本地；C 类：embedding、意图识别这类高频小请求，固定用小模型，本地优先。
2. **在 agent 配置里显式绑定**：主 agent 的规划环节指定云端 profile，子任务和插件各自指定本地 profile，MCP 工具调用保持云端（原因见踩坑）。
3. **加一层输出校验**：本地模型输出一律过 JSON Schema 校验，失败自动 fallback 到云端重试一次。这一层是整套方案能稳定运行的前提。
4. **记录路由决策**：每次请求记下 route 来源、token 消耗、延迟、是否触发 fallback。跑两周再调规则，不要拍脑袋。

## 踩坑点

- 本地模型的 tool calling 可靠性远低于跑分表现，函数参数幻觉在 Q4 量化模型上尤其明显。别信 benchmark，拿自己的 20 条真实用例测。
- 上下文长度差异是静默炸弹：本地 8k、云端 128k，超限后行为各不相同。给本地模型的任务要主动裁剪 MCP 工具描述，否则光工具清单就吃掉一半窗口。
- fallback 链没有预算上限会变成计费漏洞：本地抖动一晚上，云端 fallback 能跑掉一周额度。务必加每日 token 预算和熔断。
- 关键词匹配做路由起步可以，但别让它长期承担意图判断。误路由比贵更伤：错任务进了弱模型，错误会顺着流程向下游传播。

## 可复用建议

- 路由粒度做到子任务/工具级，不要整个 agent 一个模型。
- 含敏感信息的数据默认走本地路径，确需上云先脱敏，把这条写成 agent 的硬规则，而不是口头约定。
- 摘要、改写类请求重复率很高，加缓存，收益立竿见影。
- 维护一份 30~50 条的私有评测集，每次调整路由规则后跑回归，防止“优化了成本、劣化了质量”。

## 总结

多模型路由的本质是按出错代价分配算力：贵且强的模型只花在错误传播不可逆的环节，其余交给可校验、可重试的本地路径。先规则、后分类器，先观测、后优化——这条路径在 OpenClaw 里成本最低，也最容易回滚。
