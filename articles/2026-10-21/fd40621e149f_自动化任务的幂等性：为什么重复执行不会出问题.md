## 背景

在 OpenClaw 的自动化场景里，任务被重复触发几乎是常态：定时器重叠、webhook 重试、Agent 判断失误后再次调用同一个 MCP 工具、消息队列 at-least-once 投递、失败后的手动重跑。写一次性脚本能跑通很容易，难的是它在第二遍、第三遍执行时仍然产出正确结果。这就是幂等性要解决的问题：**同一操作执行一次和执行多次，最终状态一致**。

## 问题

反例很常见：每天定时往频道发一条摘要，某天进程卡死后重试，频道里出现两条一模一样的消息；或者一个“创建工单”的插件被 Agent 连调两次，凭空多出一张重复工单。更隐蔽的坑是：很多人在任务开始时用 `Date.now()` 或随机 UUID 生成任务 ID，本意是做去重，结果每次执行都生成新键，去重逻辑形同虚设。幂等性坏掉的成本不是立刻显现的，而是以脏数据、重复通知、重复计费的形式慢慢累积。

## 做法

我的实践可以拆成四步：

1. **构造确定性任务键。** 键来自任务语义而非执行时刻，例如 `hash(任务名 + 业务日期 + 关键参数)`。同一个逻辑任务，无论重跑多少次，键不变。
2. **维护执行台账。** 用 SQLite 或一个本地文件记录 `task_key → 状态 + 结果指针`。执行前先查台账，键已存在且状态为 done 就直接跳过。
3. **写操作天然幂等化。** 能 upsert 就不 insert，能 `delete by key` 就不追加，数据库层面用唯一索引 + `ON CONFLICT` 兜底。这是最后一道防线，不依赖应用逻辑正确。
4. **对外部副作用显式传键。** 调用支持幂等键的 API 时带上 `idempotency_key`；自己写的 MCP 工具/插件接口也应预留这个参数，在服务端做去重。

## 踩坑点

- **随机键是伪装的幂等。** 每次运行生成新 UUID，台账永远查不到重复，等于没做。
- **“检查再执行”有并发窗口。** 两个重叠的调度实例可能同时通过检查。要么靠唯一约束硬拦，要么加文件锁。
- **不要追“恰好一次”。** 在“先标记后执行”和“先执行后标记”之间崩溃，都会出现中间态。现实的目标是 **at-least-once 执行 + 幂等的效果**，对 stale 的 running 状态写恢复逻辑。
- **超时不等于失败。** 请求超时后服务端可能已处理成功，盲目重试又没有幂等键，副作用就重复了。
- **台账覆盖不到的地方才是重灾区。** 自己库里的数据去重了，发消息、第三方调用这些外部副作用没传键，照样重复。

## 可复用建议

- 把每个定时任务当作“至少会跑两次”来设计，这是最省心的心智模型。
- 团队内统一的插件规范里加入可选 `idempotency_key` 参数，默认由调用方生成。
- 在 CI 里放一个重放用例：同一任务连跑两遍，断言外部效果数量为 1。幂等性是可以测试的。
- 日志里始终带上任务键，排障时能串起多次执行。

## 总结

幂等性不是装一个库就能获得的特性，而是设计出来的属性。确定性任务键 + 持久化台账 + 唯一约束兜底，三件套成本不高，却能把重试从“事故源”变成“安全网”。自动化系统越是无人值守，这套机制越早加上越好。
