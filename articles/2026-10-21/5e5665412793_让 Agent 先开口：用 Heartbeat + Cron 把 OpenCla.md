## 背景

大多数 AI 助手的交互模型是「你问它答」：不动手就什么都不发生。但真正称得上助理的东西应该反过来——磁盘快满了、CI 挂了、某个 deadline 明天到期，它应该先于你注意到。

OpenClaw 在架构上给了三块积木：**heartbeat**（周期性自唤醒）、**cron**（定时触发）、**skills + MCP**（检查与执行能力），再加上已有的消息 channel 可以反向推送。理论上拼起来就是主动式助手；实际能不能用，取决于你怎么控制噪声和成本。

## 问题

主动化有两个天然坑：

1. **噪声**：agent 每次醒来都想"汇报点什么"，否则显得没干活，结果是一堆"一切正常"的废话推送。
2. **越权**：主动的 agent 发现问题后顺手"修"了——重命名文件、回复消息、删东西。没人授权它这么干。

所以核心工程问题不是"怎么让它动起来"，而是：**在什么条件下、以什么方式，允许它打断你**。

## 做法

我的配置分四步，跑了一个多月，比较稳：

**1. 把 HEARTBEAT.md 当 SLO 文档写。** 工作区里的 HEARTBEAT.md 是每次唤醒的检查清单，关键不是列什么任务，而是每项都写清"什么算异常"。比如：检查 `logs/error.log` 当天新增行数，超过 50 行视为异常；根分区使用率超过 85% 视为异常；无异常则保持沉默，不输出任何消息。明确"沉默 = 健康"，这一条能把推送量砍掉 90%。

**2. 时间性任务走 cron，别塞进 heartbeat。** 每日早报、每周汇总这类固定时间的事用 cron 精确触发，和 heartbeat 的"巡检"分开。注意时区：gateway 跑在服务器上时 cron 用的是机器时区，先和你的作息对齐。

**3. 检查能力用 MCP 挂载，保持只读。** 文件系统、git 仓库、监控接口用 MCP server 接进来。heartbeat 阶段我只给只读工具，写操作全部收敛到需要确认的 skill 里。这样主动性的上限就是"发现问题并通知"，不会自己动手造成二次事故。

**4. 按严重度分流 channel。** 异常推送走单独的通知渠道，日报走另一个。混在同一个会话里，重要告警必然被淹没。

## 踩坑点

- **唤醒间隔太短 = 烧钱**。每次 heartbeat 都是一次完整推理，哪怕啥也没查出来。30 分钟起步，低于 10 分钟的场景要能说清理由。
- **清单写得太模糊**。"看看项目有没有问题"这种条目，agent 会自己脑补标准，隔三差五编个问题出来。每项检查必须可判定。
- **输出格式不钉死**。LLM 每次醒来的措辞和详细度都会漂。钉一个固定模板（状态 / 异常项 / 建议动作），方便肉眼扫，也方便后续做统计。
- **心跳会话上下文膨胀**。长期运行的 heartbeat session 会积累历史，token 越滚越大。定期重置，只留结论不留过程。
- **触发源互相打架**。cron 任务改了 heartbeat 正在检查的文件，形成循环。触发源保持单一。

## 可复用建议

- 主动消息设每日上限（比如 5 条），超了就合并成摘要，防止失控。
- 每条主动触发留日志：时间、触发源、判定结果。两周回看一次，删掉从未命中的检查项。
- 先只读跑两周，确认误报率可接受，再逐项放开写操作，且每项写操作单独确认。
- 把"观察类 skill"和"执行类 skill"分成两组，heartbeat 只允许引用前者。

## 总结

主动性不是开关，是噪声控制问题。主动助手的净价值 = 抓住的问题数 − 打断你的注意力税。先用「沉默即健康 + 每日限额 + 只读巡检」把税压住，再谈覆盖面。跑顺之后你会发现，最好的主动推送频率其实很低——一天一两条，每条都值得看。
