## 背景

在 OpenClaw 上跑起常驻 Agent 之后，我们最先交给它的不是写代码，而是那些"谁都不想做但又不能不做"的 Git 杂活：写提交信息、按规范切分支、清理合并完的远端分支。跑了两个月，这套流程已经比较稳定，把实践记录一下。

## 问题

人工维护 Git 的痛点很具体：

- 提交信息全看当时心情，半年后 `git log` 基本无法回溯；
- 分支命名混乱，`feat/`、`fix/`、`hotfix/` 随手起名；
- 合并完的分支没人删，远端堆了 40 多个 stale branch；
- 改动跨多个文件时习惯一把 `git add .`，提交粒度失控。

这些事的共同特征是：规则明确、重复度高、判断含量低——正适合交给 Agent。

## 做法

1. **工具层**：给 Agent 接入 MCP Git server（或白名单化的 git shell），初始只开只读命令：`status` / `diff` / `log` / `branch -a`。
2. **约定层**：仓库根目录放一份规则文件（如 `AGENTS.md`），写清 Conventional Commits 格式、分支命名规范（`feat/xxx`、`fix/xxx`）、哪些目录不允许单独成提交。
3. **提交流程**：Agent 读完 diff 后产出提交信息和分文件 `add` 方案，人工确认后才执行 `commit`。push 一律不自动。
4. **分支流程**：从 issue 建分支交给 Agent；每周定时任务跑一遍已合入 main 的分支清单，输出报告，确认后批量删除。
5. **审计**：Agent 执行的每条 git 命令落日志，出问题可以回放。

## 踩坑点

- **状态幻觉**：Agent 会把上一轮的 `git status` 记在"脑子里"，而仓库实际早已变化。必须要求每次操作前重新执行 `status`/`diff`，禁止复用上下文里的旧结果。
- **交互式命令失效**：`git add -i`、`rebase -i` 在非交互 shell 下直接挂。改用 `GIT_SEQUENCE_EDITOR=true` 的方式，或干脆让 Agent 只做指定文件 `add` 加普通提交。
- **pager 卡住**：`git log`/`diff` 在无 TTY 环境下仍可能触发 pager 导致挂起，统一 `GIT_PAGER=cat` 或加 `--no-pager`。
- **凭证泄漏**：不要把 token 写进提示词。走系统 credential helper，Agent 只调用、不感知。
- **误提交敏感文件**：在规则里加一条硬校验——提交前检查 staged 文件里有没有 `.env`、密钥类文件。
- **权限兜底**：别指望提示词挡住一切。保护分支的限制要在服务端（分支保护规则）配好，Agent 被提示词"说服"了也推不上去。

## 可复用建议

- **确定性的事用脚本，判断性的事用提示词**。分支清理写成脚本让 Agent 调用，比让它每次现场拼 git 命令可靠得多。
- **从只读权限起步**，稳定运行两周再逐步放开 commit、branch 操作；push 和 merge 始终保留人工。
- **规则文件随仓库走**，换机器、换 Agent 实例，约定不丢。
- 提交信息必须**基于 diff 生成**而不是基于任务描述，否则会出现描述正确但内容空洞的 commit message。

## 总结

这套流程的本质是把 Git 操作拆成三层：机械执行交给 Agent，规则校验交给脚本和 hooks，最终决策（push / merge / 删远端分支）保留在人手里。两个月下来，`git log` 可读性明显提升，stale branch 从 40+ 降到个位数。它没有让开发本身快多少，但让仓库变干净了——对多人协作的项目来说，这本身就值回配置成本。
