## 背景

起因很简单：我们维护的技术社区需要稳定的内容节奏，人工排班成本高，摘要和转载类工作重复度也高。于是做了个发帖机器人，跑在 OpenClaw agent 上，通过 MCP 接入搜索、社区 API 和数据库。目标是每天产出 1–2 条有信息量的帖子，而不是刷量。

## 问题

真正的难点不是“发出去”，而是三个约束：

- 内容不能重复，不能编造链接和引用；
- 发布行为必须可审计、可回滚；
- 出错时宁可少发，不能发错。

## 架构与步骤

整体是五段流水线：

1. **采集**：定时任务拉取 RSS、仓库 release、社区热帖，写入候选池，附带来源与抓取时间。
2. **生成**：OpenClaw agent 读取候选，调用 MCP 搜索工具补充上下文，产出草稿和引用列表。提示词里明确禁止无来源陈述。
3. **校验**：独立校验模块做三件事——embedding 相似度去重（阈值 0.88）、链接可达性检查、引用与原文比对。
4. **审核**：校验通过的进草稿队列。前两周全部人工确认，稳定后才对低风险类别（纯资讯摘要）开放自动发布；教程、观点类永远走人工。
5. **发布与归档**：发布带幂等键（来源 URL 哈希），回执落库，失败进重试队列，指数退避。

## 踩坑点

1. **去重先用了关键词**，“LLM Agent 评测方法”和“Agent 评测 LLM 方法”重复发了。换 embedding 相似度后才干净。
2. **模型会一本正经编 URL**。解法是把“引用必须来自工具返回结果”写成硬约束，校验阶段逐条验证，无引用的段落直接删除而不是放行。
3. **幂等坑最深**：一次发布成功但回调超时，重试队列又发了一遍。现在发布前先用幂等键占位（`INSERT ... ON CONFLICT`），占位失败即跳过。
4. **频控**：连续整点发帖触发平台风控，加了 0–40 分钟随机 jitter 和每日上限后消失。
5. **质量漂移**：换模型版本后语气突然营销化，是靠一条“语气检查”校验规则拦回来的。校验规则是持续维护的工程，不是一次性配置。

## 可复用建议

- 把“是否可发布”做成独立策略模块，与生成、发布解耦，方便灰度和回退。
- 自动发布的默认状态应该是“草稿”，人工确认是常态而非例外。
- 结构化日志记录每次决策依据：选了哪条候选、相似度分数、失败原因。排障时这是唯一救命的东西。
- 给 LLM 调用设每日预算，防止采集源异常时循环重试烧钱。

## 总结

这个项目代码量不大，复杂度都在流程约束上。机器人真正的价值不是省了几十分钟排版，而是把“发什么、凭什么发、发错了怎么办”变成了显式规则。建议想动手的同学先跑通“草稿 + 人工确认”闭环，再逐步放开自动发布。
