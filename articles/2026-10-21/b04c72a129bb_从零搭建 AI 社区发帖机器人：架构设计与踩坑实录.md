## 背景

社区日常有几类固定内容要发：每周版本摘要、新教程推荐、值得关注的 issue 精选。以前靠人工整理粘贴，重复劳动还容易漏。于是我用 OpenClaw 搭了一个发帖机器人，目标流程是：定时抓取信息源 → Agent 起草 → 人工确认 → 调 API 发布。跑了一个多月，这里记录架构和踩过的坑。

## 问题：直接让 Agent 发帖为什么不行

最初方案很粗暴：一个 prompt，"每天九点去抓这些源，写成帖子发出去"。跑了三天就暴露三个问题：

1. **幻觉**：模型会把没发生的事写成 changelog；
2. **重复**：信息源改了一个字的标题，机器人当成新内容又发一遍；
3. **自激循环**：机器人订阅了自己发帖所在的频道，开始评论自己的帖子。

结论：不能把"判断发什么"和"执行发布"都交给模型自由发挥，必须有外部状态和闸门。

## 做法：三层架构 + 人工闸门

最终架构分三层：

- **触发层**：cron 调 OpenClaw agent，传入本次任务 ID（日期 + 源标识），任务 ID 同时作为幂等键。
- **Agent 层**：Agent 只负责"取材 + 起草 + 自检"。发布动作封装成独立的 MCP 工具 `publish_post`，分 `dry_run` 和 `confirm` 两种模式，默认 dry_run，只输出草稿和结构化摘要。
- **状态层**：SQLite 存三张表——已处理的源条目（source_id + 内容哈希）、已发布任务、发布回执。Agent 每次启动先读状态，而不是依赖自己的记忆。

人工闸门放在发布前：草稿生成后推送到审核渠道，人确认后带上 task_id 调 confirm 才真正调社区 API。头两周全量人审，稳定后只对高风险内容（含版本号、外链的段落）做人工复核。

## 踩坑点

1. **幂等键选错**。最初用标题哈希去重，标题一改就判重失败。改成"源条目 ID 为主键 + 正文相似度兜底"才解决。
2. **让 Agent 自己生成 task_id**。模型拼的日期字符串时区一错就重复发。改成触发层生成、只读传入。
3. **MCP 工具返回太大**。抓网页原文直接塞进上下文，一次十几万 token。后来在工具内做 HTML 清洗和截断，只回传正文前 2000 字加元信息。
4. **Markdown 转义不一致**。社区 API 对代码块和反斜杠的处理和标准 Markdown 有差异，草稿看着对，发出来全乱。写了一个格式 lint 的 MCP 工具，发布前强制过一遍。
5. **失败重试没有回执**。API 超时后 Agent 以为没发出去，重发导致双帖。规定 publish 工具重试前必须先查回执，状态层记录 request_id。

## 可复用建议

- 状态放库不放上下文，模型不该负责"记住发过什么"；
- 发布动作做成独立、可 dry-run 的 MCP 工具，和取材起草物理隔离；
- 定时任务一律用外部生成的幂等键，模型只消费；
- 先全量人审，再按风险分级放开，别一上来就全自动；
- 发布工具必须带回执和 request_id，重试前必查。

## 总结

这个机器人真正省时间的不是"自动写作"，而是自动取材、格式校验和去重这些确定性环节；模型擅长的是起草和组织语言。把确定性的事交给工具和状态层，把判断权留给人，才能长期稳定运行。目前它每周稳定产出 2-3 篇摘要帖，误发率为零——代价是前期把闸门设计做扎实。这套分层结构不依赖具体社区，换一套发布 API 也能直接复用。
