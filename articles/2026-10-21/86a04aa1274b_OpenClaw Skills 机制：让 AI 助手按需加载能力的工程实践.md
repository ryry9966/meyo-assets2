## 背景

接的 MCP server 和插件多起来之后，最直观的感受是会话变"重"了：每个工具的描述、参数 schema 都要塞进上下文，几十个工具下来，光描述就占掉数万 token。更麻烦的是，模型面对一长串工具列表时，选错工具的概率明显上升——不是能力不够，而是注意力被稀释了。OpenClaw 的 Skills 机制就是针对这个问题：把能力拆成独立技能包，平时上下文里只放一个轻量索引，命中时才加载完整内容。

## 问题

传统"全量注入"有三个代价：

1. token 成本随工具数量线性增长，长会话尤其明显；
2. 无关工具的描述持续干扰模型决策，调用错误率升高；
3. 能力更新要改主配置，和 agent 本体强耦合。

Skills 的解法是**渐进式披露**：索引常驻、正文按需、辅助文件再按需，三层各管各的。

## 做法

**1. 搭目录结构。** 每个技能一个目录，核心是 `SKILL.md`：

```
skills/
├── pdf-report/
│   ├── SKILL.md        # 只有 frontmatter 里的 description 常驻上下文
│   ├── template.html   # 触发后才被按需读取
│   └── render.py
└── data-cleanup/
    └── SKILL.md
```

**2. 写好 description。** 这是唯一的触发器。用一两句话说明"这个技能做什么 + 什么场景用"，把用户可能说出的关键词明确写进去。写得含糊，它就永远不会被触发。

**3. 控制正文体量。** SKILL.md 主体建议几百行以内，放工作流程、约束和示例；大文档、模板、脚本拆成同目录下的引用文件，模型只在需要时才去读。

**4. 确定性工作下沉到脚本。** 能用脚本跑的就别让模型用自然语言推理，SKILL.md 里写清"执行某脚本、传什么参数"即可，稳定性和幂等性都会好很多。

**5. 验证触发。** 用几组真实口吻的 prompt 测试命中率：不触发就补关键词，误触发就收窄描述。

## 踩坑点

- **description 太泛**：写"处理文件相关任务"等于没写，几乎每次都会误触发；太窄又永远命中不了。要具体、可枚举。
- **把所有内容塞进 SKILL.md**：见过有人写几千行全放正文，结果一触发上下文就爆，完全违背按需加载的初衷。拆文件。
- **相对路径失效**：技能里引用脚本要用相对技能根目录的路径，否则换个工作目录就找不到。
- **误以为模型会读所有文件**：它只读打开的文件。关键约束必须写在 SKILL.md 正文里，不能只藏在引用文件中。
- **技能数量失控**：几十个技能后索引本身也变长，要定期合并低频技能。

## 可复用建议

- 一个技能只做一件事，宁多勿大；
- 把触发词当搜索关键词来写，覆盖真实说法而非术语；
- 技能放进 git 仓库，走 PR review，改动可追溯、可回滚；
- 上线前后对比 token 消耗和工具调用错误率，用数据验证收益，而不是凭感觉。

## 总结

Skills 机制的本质是把"能力发现"和"能力执行"解耦：索引负责被发现，正文负责被执行，两者分层、按需加载。对长期跑自动化任务的用户来说，这不只是省 token，更是把 agent 从"工具越多越乱"拉回"能力清晰、行为可控"的工程轨道。先从拆一两个最占上下文的工具开始，收益很快能看出来。
