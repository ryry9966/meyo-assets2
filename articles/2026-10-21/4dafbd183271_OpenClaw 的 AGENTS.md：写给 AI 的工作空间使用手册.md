## 背景

OpenClaw 的 agent 不是无状态的问答机。它有一个常驻的工作空间（workspace），里面放着记忆文件、技能、脚本和你让它维护的各种数据。但 agent 每次会话冷启动时，并不"天生"知道这个空间里有什么、哪些目录不能碰、对外回复该用什么口吻——这些上下文需要一个固定入口。

这个入口就是 AGENTS.md。可以把它理解成 README 的镜像：README 写给人类开发者，AGENTS.md 写给每次启动的 agent。OpenClaw 建立会话时会把它和 SOUL.md、TOOLS.md 等文件一起注入上下文，作为这个工作空间的操作规程。

## 问题

没有 AGENTS.md 时，典型症状：

- 每个会话都要重新解释"配置在 `config/` 不在根目录""`archive/` 里的旧脚本别动"；
- agent 自作主张在根目录新建文件，或使用你没约定的命名规则；
- 不同入口（Telegram、CLI、定时任务）行为不一致，像三个人在值班；
- 上周踩过的坑（误删文件、重复触发 cron）过两周又犯一遍。

本质是同一个问题：工作空间缺少一份 agent 每次都能稳定读到的约定。

## 做法

我的 AGENTS.md 控制在 60 行以内，分四块：

1. **空间地图**：列出目录结构和用途，明确读写权限。例如 `memory/` 由 agent 自行维护，`scripts/` 修改前先说明意图。
2. **工具与技能约定**：本工作空间启用了哪些 MCP 工具和插件、优先级如何、哪些操作必须先确认再执行。
3. **行为边界**：回复语言与风格、长任务的处理方式（先告知预估耗时再动手）、失败时的上报路径。
4. **已知坑**：踩过的坑写成禁止项，例如"22:00–8:00 不触发群消息""删除操作一律先移入 trash/"。

写完放进工作空间根目录，开新会话即生效。建议纳入 git：agent 行为不符合预期时，先修文档，再考虑改提示词。

## 踩坑点

- **写成人类文档**：大段架构介绍、外链、贡献指南，agent 不需要这些，它需要可执行的规则。
- **太长**：注入上下文有成本，几百行的 AGENTS.md 会稀释关键指令，重要规则放文件前部。
- **与 SOUL.md 冲突**：两个文件对同一行为给出不同规定时，agent 表现会不可预测。边界类规则只写一处，SOUL.md 管人格，AGENTS.md 管操作。
- **写入敏感信息**：token、内网地址不要放这里，它会随上下文进入模型。
- **当场改不生效**：进行中的会话通常不会重读 AGENTS.md，改完务必开新会话验证。

## 可复用建议

- 把它当**合同**而不是说明书：每一条都应该是 agent 会照做的指令，不是背景铺垫。
- 用失败日志反哺：agent 出错时先问"这条规则写进 AGENTS.md 了吗"，比反复口头纠正有效得多。
- 多 agent 各写各的：不同工作空间不共享、不交叉引用，宁可少量重复。
- 定期裁剪：已稳定执行、不再需要提醒的条目果断删除，保持短小。

## 总结

AGENTS.md 的价值不在"多写了一份文档"，而在于把对 agent 的隐性要求显性化、版本化。它就是你和工作空间里那个 agent 之间的接口定义——接口稳定了，自动化才谈得上可靠。建议每个 OpenClaw 用户至少维护一份 30–60 行的 AGENTS.md，从"空间地图 + 三条禁止项"起步，随踩坑逐步增补。
