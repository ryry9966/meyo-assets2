## 背景：agent 每次开机都要读的"员工手册"

OpenClaw 的 agent 没有常驻记忆，每次会话启动时，它做的第一件事是读取工作空间里的一组 markdown 文件：SOUL.md 定人格，USER.md 定用户画像，MEMORY.md 存长期记忆，而 AGENTS.md 负责"怎么干活"——目录约定、操作流程、工具边界。你可以把它理解成新员工入职第一天拿到的操作手册：写得清楚，agent 就省心；写得含糊，它就靠猜。

## 问题：手册形同虚设的几种典型症状

我在自己的 OpenClaw 实例上踩的坑，大多能追溯到 AGENTS.md 没写好：

- **行为漂移**：同一个整理任务，这周把脚本放 `/scripts`，下周放 `/tmp`，因为它每次都在自己发明约定。
- **越权操作**：清理文件时顺手删了还在用的配置，因为手册里没写"哪些东西不能动"。
- **指令膨胀但没用**：文件堆到几百行，关键规则淹没在散文里，该犯的错照犯。

根因只有一个：把它当成了随手记的便签，而不是一份每次会话都会被完整消费的上下文文档。

## 做法：按写 runbook 的方式写 AGENTS.md

**1. 先划清文件分工。** AGENTS.md 只写操作规程；语气、称呼、价值观放 SOUL.md；某个工具的特殊用法放 TOOLS.md。重复是冲突之源。

**2. 按固定骨架分节。** 我的版本只有四节：

- 工作空间布局：每个目录的用途、临时文件放哪、命名规则；
- 会话流程：开工先看什么、改动前要不要确认、收尾要不要写 MEMORY.md；
- 工具与命令：哪些可以直接执行，哪些必须先汇报；
- 禁止事项：明确的红线清单。

**3. 用具体规则替代形容词。** "保持工作区整洁"等于没写；"临时脚本一律放 `workspace/tmp/`，会话结束前删除"才是规则。

**4. 控制长度。** 一到两屏为宜。上下文里每一行都在分摊注意力，规则越多，单条权重越低。

**5. 像运维文档一样迭代。** agent 犯一个新错，就补一条针对性规则；每两周清理一次过时条目。手册是养出来的，不是一次写完的。

**6. 进 git。** workspace 目录直接版本化，行为一旦退化，diff 一下就知道是哪次改动引入的。

## 踩坑点

- **与记忆打架**：MEMORY.md 里的旧习惯会和手册新规则冲突，agent 表现随机。要在手册里写明优先级："本文件与记忆冲突时，以本文件为准。"
- **模糊措辞**："尽量""酌情""适当"出现在规则里，基本等于没写。
- **改完不测**：手册改动后要跑几个典型任务做回归，规则互相矛盾只有跑起来才会暴露。
- **把 SOUL.md 的内容抄进来**：两处都管语气，结果 agent 一会儿正式一会儿卖萌。

## 可复用建议

- 把 AGENTS.md 当成写给"能力很强但完全不了解你环境的新同事"的 onboarding 文档：它聪明，但需要你的约定。
- 加一条元规则兜底："遇到本手册未覆盖的情况，先停下询问，不要自行裁决。"这一条帮我拦掉了大半越权操作。
- 规则尽量写成可判定的条件句：有明确触发条件和明确动作，agent 才能稳定执行。

## 总结

AGENTS.md 本质上是在做一件工程化的事：把对 agent 的隐性期望显式化、条目化、版本化。它不需要文采，需要 runbook 式的纪律——分工清晰、规则可判定、持续迭代。写好这一份文件，往往比换模型、调参数对日常体验的提升更直接。建议还没认真写过 AGENTS.md 的朋友，今天就从"目录布局 + 禁止事项"这两节开始。
