## 背景

用 OpenClaw 跑内容类工作流后，常见形态是：Agent 负责调研和写作，产出 Markdown，之后要发到公众号、知乎、掘金、静态站等多个渠道。问题在于 LLM 的产出只解决"写"，不解决"发"——各平台格式约束差异很大，手工适配不可持续，让 LLM 直接输出各平台格式又会翻车。

## 问题

实测下来主要是三类：

1. **LLM 输出不规范**：混入内联 HTML、标题层级跳级、代码围栏语言标记随意、表格和脚注使用 GFM 扩展语法；
2. **平台约束不同**：公众号只接受内联样式的 HTML 白名单子集，知乎会剥离大量标签，掘金支持 GFM，静态站又要完整 HTML；
3. **图片链路**：本地路径、图床、平台素材库三者不一致，直发必挂。

## 做法

核心原则：**内容只生成一次，格式转换交给确定性代码，不让 LLM 做转换。**

管线分四层：

1. **规范化层**。对 LLM 原始输出先做一遍清洗：标题层级重排到统一基准、剥离内联 HTML、统一代码围栏、公式转成平台可接受的形态。这一步用 remark / markdown-it 的 AST 操作实现，几十行代码，比在 prompt 里加约束可靠得多。
2. **单一事实源**。规范化后的 Markdown 加 frontmatter（标题、标签、各平台特有配置）作为唯一源文件，进 git。
3. **适配器层**。每个目标平台一个纯函数：canonical MD → 平台格式。比如公众号走 markdown-it 渲染后用 juice 做样式内联，再上传图片到素材库并重写链接；知乎直接用清洗后的 MD；静态站走完整渲染。适配器无状态、可单测。
4. **校验与发布层**。发布前跑 markdownlint（自定义规则集）+ 平台格式断言（如"不得含 class 属性"），再走 API 发布，记录返回 URL 实现幂等。

在 OpenClaw 里的接法：Agent 产出到工作区后，把整条管线封装成一个 skill / MCP tool，Agent 只调用 `publish(platform)`，转换过程对它黑盒。

## 踩坑点

- 让 LLM"输出公众号 HTML"是坑的开始：它会编造样式、混用标签，且每次输出不稳定。样式内联必须在构建期做。
- markdown-it 默认会转义部分特殊字符，从别处复制来的内容常出现多余反斜杠，规范化层要先处理一遍。
- 图片重写要幂等：重复发布会传两次图床，用内容 hash 做缓存键。
- 长表格在移动端必炸。规范化层加规则：列数超限就转列表，宁可损失一点表达。
- 知乎等平台剥离标签是**静默失败**，发布后要抓一次回显做 diff 校验，而不是只看 API 返回 200。

## 可复用建议

- 把 canonical Markdown 当契约，适配器全设计成纯函数，新增平台 = 新增一个文件。
- lint 规则跟着各平台白名单走，规则文件进版本库，平台改版改规则即可。
- 所有发布动作记录三元组 `(内容 hash, 平台, 返回 URL)`，重跑不重复发。
- 预览优先：本地先渲染各平台近似效果，人工过目再触发真实发布。

## 总结

这类管线的价值不在某个具体转换，而在边界划分：LLM 管内容，代码管格式。转换是确定性需求，就该用确定性代码；LLM 的不确定性只留给写作本身。管线搭好之后，接入一个新平台通常半天够了，剩下时间才是真正省下来的。
