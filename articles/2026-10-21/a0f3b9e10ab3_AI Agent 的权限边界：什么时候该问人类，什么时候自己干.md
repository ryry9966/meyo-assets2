## 背景

现在跑 OpenClaw 这类 Agent，接上 MCP 工具后能干的事越来越多：读写文件、调 API、发消息、改配置。工具一多，核心问题就冒出来了——哪些动作 Agent 可以直接执行，哪些必须停下来等人确认。

## 问题

两个极端都不行。每步都问，人会被确认请求淹没，最后无脑点"允许"，比不问还危险；完全不问，一次误操作（删错目录、发错群、重复扣费）就够喝一壶。真正要做的是把"问不问"从临场判断变成一条工程化规则，而不是指望模型每次自己拿捏分寸。

## 做法

我的做法是按**可逆性 + 影响范围**把工具分四档，落到 Agent 配置里：

- **T0 只读**：查询、搜索、读文件。直接放行，只记日志。
- **T1 可逆写**：限定目录内写文件、建草稿、本地提交。自动执行，但变更必须走版本控制或快照，保证能回滚。
- **T2 不可逆 / 对外可见**：删除、对外发消息、计费接口、生产部署。强制人工确认，且确认时必须附带完整参数、影响对象、回滚方案。没有回滚方案的 T2 动作，一律拒绝而不是降级为自动。
- **T3 模糊地带**：Agent 置信度低，或同一动作短时间重复触发，主动转人工。

落地靠三个机制：

1. **审批门**：在工具调用层用代码拦截，而不是靠 prompt 约定。prompt 会被长上下文稀释，代码层不会。
2. **干跑模式**：T2 动作先输出"将要做什么"的计划，人确认后才真正执行。
3. **预算限制**：单任务最多 N 次确认请求、M 次外部调用，超了就停，防止死循环刷审批。

## 踩坑点

- **确认疲劳**：问得太勤，人会变成自动点确认的机器。宁可把更多动作降到 T1 但加强回滚，也不要高频弹窗。
- **"可逆"是分场景的**：本地写文件可逆，但内容一旦推到公开渠道，"撤回"救不回已经被看到的事实。分类要按最坏情况算。
- **确认信息不够**：只弹一句"是否允许执行？"等于没问。人得看懂参数和后果才能判断，否则确认就是个仪式。
- **调用链会稀释权限**：主 Agent 有审批，但 MCP 工具内部又包了子流程，检查容易在中间层丢掉。审批门要覆盖整条调用链。

## 可复用建议

接入任何新工具前过一遍 checklist：

- 这个动作能回滚吗？成本多少？
- 出错时影响的是一个文件、一台机器，还是外部用户？
- 有没有干跑 / 预览能力？
- 审批时人能看到完整上下文吗？
- 日志里能事后还原"谁在何时批准了什么"吗？

五个问题里有两个答不上来，就先归入 T2。

## 总结

权限边界不是"信任模型多少"的问题，而是把不可逆操作的暴露面压到最小。原则一句话：**可逆的尽量自动化并留好回滚，不可逆的必须让人在看到完整上下文后亲手放行**。这套分档不完美，但它把"问不问"从每次的临场赌博，变成了可以评审、可以迭代的配置。
