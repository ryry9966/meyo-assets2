## 背景

跑 Agent（OpenClaw workspace、MCP、各类插件）久了会发现一个规律：提示词写得再好，环境对不上照样翻车。同一个任务在你机器上能跑通，换台机器或丢给同事的 gateway 就开始报错——包管理器不同、路径不同、代理不同、有没有 GPU 也不同。

Agent 每次会话都是冷的，没有"这台机器长什么样"的长期记忆。AGENTS.md 解决的是"行为规范"，但"环境事实"没有归宿，最后往往被硬编码进提示词，一换环境就失效。

## 问题

常见的三类翻车：

1. Agent 自作主张用了 npm，而项目约定是 pnpm；
2. 提示词里写死 `/Users/xxx/...` 路径，Linux 上直接找不到；
3. 本地 / CI / 服务器三套环境，Agent 分不清自己在哪套里，用错凭据或端口。

根因是环境事实散落在提示词、shell rc、口头约定里，Agent 看不到全貌，也看不到差异。

## 做法

核心思路：把"这台机器/这个工作区的事实"收敛成一个 `tools.md`，放 workspace 根目录，并在 AGENTS.md 里引用。

1. **建基线文件** `tools.md`（入库共享）：只写事实，不写愿望，每条一行、格式统一：
   - 包管理：`pnpm@9，禁止 npm/yarn`
   - 运行时：`node 22，用 nvm 切换`
   - 网络：`出网走 127.0.0.1:7890，内网服务直连`
   - 平台：`macOS arm64，Homebrew 在 /opt/homebrew`

2. **机器差异下沉**：建 `tools.local.md`（gitignore），覆盖本机特有内容：本地模型路径、GPU、特殊端口。约定读取顺序：基线在前，local 覆盖在后。

3. **接入 Agent 上下文**：AGENTS.md 里加一条："执行任何安装/构建/联网操作前，先读 tools.md 与 tools.local.md，冲突时以 local 为准并向我确认。"如果你的网关支持 workspace 文件自动注入，直接挂载即可。

4. **加一个预检脚本**：`check-env.sh` 把 tools.md 里的关键断言跑一遍（命令是否存在、版本是否匹配、代理是否可达），失败输出差异。会话开始先跑它，比事后排障便宜得多。

## 踩坑点

- **写太多**：tools.md 不是文档，是断言清单。超过一屏，Agent 会跳读，人也懒得维护。
- **过期信息比没有更糟**：Agent 会把写的当真。改环境不同步改 tools.md，等于给 Agent 埋雷。环境变更走 PR，和代码一起 review。
- **别放密钥**：`.env` 归 `.env`，tools.md 只写"凭据在哪个文件、怎么加载"。
- **别和 AGENTS.md 抢活**：AGENTS.md 管"怎么做"，tools.md 管"有什么"。混着写两边都会漂移。
- **跨平台细节**：路径分隔符、shell 方言、brew 安装位置，这些正是 local 文件最该覆盖的。

## 可复用建议

- 一行一条、可被脚本验证的格式最耐久；无法验证的描述尽量删掉。
- 把 check-env 的输出直接粘回给 Agent，让它基于事实修 tools.md，比手写快。
- 多机排障时，先 diff 两份 local 文件，往往就能定位"为什么在你那能跑"。

## 总结

tools.md 的价值不在文件本身，而在把环境差异从隐式口令变成显式契约：**基线共享、差异本地化、断言可验证**。做到这三点，Agent 跨机器的稳定性会有肉眼可见的提升，排障也从"猜"变成"查"。
