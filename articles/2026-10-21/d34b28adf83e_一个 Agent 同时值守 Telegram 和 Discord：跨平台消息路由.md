## 背景

我们组的 Agent 最早只挂在 Telegram 上，干两件事：值班应答和日报推送。后来团队协作迁到了 Discord，问题就变成了：再养一个 Agent，还是让同一个 Agent 同时接两条管道？

答案是后者。记忆文件、工具集、MCP 配置只有一份，维护成本最低，两边看到的行为也一致。真正的工作量不在"接上"，而在下面这三件事。

## 问题

多通道接入不等于多填一个 token。核心难点是：

1. **会话路由**：哪条消息进入哪个 session；
2. **上下文隔离**：Discord 频道里的讨论，要不要漏进 Telegram 的私聊上下文；
3. **输出适配**：两家平台的 Markdown 方言、消息长度限制、媒体处理机制完全不同。

## 做法：四步搭起来

**第一步，通道层最小配置。** 在 `openclaw.json` 的 `channels` 里同时启用 telegram 和 discord，各填各的 bot token，先跑通最朴素的收发，不要一上来就加路由规则。

**第二步，明确 session 策略。** OpenClaw 默认按通道 + 会话 ID 隔离 session，这正好是想要的。用 `bindings` 把具体目标（TG 群 A、Discord 频道 #dev）绑到同一个 agent，但 session key 各自独立。确实需要跨平台共享上下文的场景，走一个显式命名的共享项目 session，而不是把私聊 session 混进去。

**第三步，平台感知提示。** 在系统提示里注入当前平台标识，让模型知道自己在哪、面对谁。但格式适配不要指望模型自觉——长度限制（Telegram 4096 字符、Discord 2000 字符）、表格和代码块的渲染差异，统一放在输出适配层处理：超长分段、表格降级为列表、分段时保护代码块完整性。

**第四步，安全策略。** 两个平台都开 pairing/allowlist，私聊只响应白名单用户，群聊只响应被 @ 的消息。这一步在公开的 Discord 服务器里尤其重要。

## 踩坑点

- **Telegram 的 MarkdownV2 转义是重灾区**。模型输出的下划线、括号动不动触发 400。后来整体切到 HTML parse mode 才稳定下来。
- **Discord 的 rate limit** 会让批量通知翻车。主动分批、批次之间加间隔，别把节流寄希望于重试。
- **同一个人在两个平台是两个身份**，记忆系统会当成两个人。我们选择接受这个现实：重要事实手动归并进 MEMORY.md，不做自动 identity merge——自动归并错一次，清理成本远高于手动维护。
- **回声循环**。测试时两个通道互相桥接，A 的消息到 B、B 的回复又回到 A，无限套娃。规则很简单：Agent 不回复来自 bot 的消息，这条要写死在适配层。
- **长代码块跨平台分段后语法高亮全坏**。最后的约定是：超过阈值的内容落成附件或链接，不硬塞进消息体。

## 可复用建议

- **一个 Agent、N 个通道、session 默认隔离**；共享必须是显式动作，不要默认打通。
- **平台差异做成独立的输出适配层**，别写进 prompt 让模型每次自己猜，更别在 prompt 里塞平台规则表。
- **路由配置进版本库**，改动走 PR。路由改错时的影响面很大，能回滚很重要。
- **先用测试 bot 把两条管道各跑一周**（含群聊、私聊、长消息、附件），再换生产 token。

## 总结

跨平台消息路由的难点不在接入，而在会话边界和输出适配。把隔离做成默认、共享做成显式、适配做成独立的一层，一个 Agent 服务两个平台就从玄学变成了常规工程问题。目前这套结构跑了两个月，除了 Telegram 转义偶尔冒头，整体稳定，供有同样需求的兄弟参考。
