## 背景：为什么 Agent 玩家要关心本地模型

玩 OpenClaw、MCP 和自动化流程一段时间后，会撞到一个现实问题：Agent 每一步都要调模型，token 成本和隐私顾虑随流程复杂度线性上涨。摘要、分类、格式抽取这类高频低难度任务，没必要每次都打到云端。把一部分负载下沉到本地，是自动化玩家迟早要走的一步。

## 问题：家用机器跑模型，卡在哪

真正的瓶颈不是"能不能跑起来"，而是三件事：

1. **显存/内存预算**：权重和 KV cache 要一起算，长上下文下 KV cache 会悄悄吃掉好几个 GB。
2. **工具调用质量**：小参数量本地模型的 function calling 可靠性参差不齐，参数幻觉（编造字段名、JSON 格式错）会直接打断 Agent 循环。
3. **吞吐**：Agent 一轮任务要几十次模型调用，短对话流畅不等于长 prompt 下速度可接受。

## 做法：一条可复现的路径

**第一步：盘点硬件。** 记下显存（或 Mac 统一内存）、内存和磁盘。经验值：7B Q4 量化约 4–5GB，14B 约 9GB，32B 约 20GB，统一要给 KV cache 留 20–30% 余量。

**第二步：选运行时。** 没有特殊需求直接上 Ollama：一条命令拉模型，原生暴露 OpenAI 兼容接口，Agent 框架或 MCP 桥接层把 provider 指向本地端点即可。显存充裕、需要并发再考虑 vLLM。

**第三步：选模型，优先验证工具调用。** 别只看聊天评测。挑两三个明确支持 tool use 的同量级模型，写个最小脚本：给它一个带 schema 的假工具，跑 20 次调用，统计参数合法率。这个指标比跑分真实得多。

**第四步：接入 Agent 并加护栏。** temperature 压到 0.1–0.3，限制上下文长度，工具调用一律过 schema 校验，失败自动重试一次再降级到云端模型。

**第五步：用真实任务压测。** 拿日常 Agent 流程跑端到端，记录 tokens/sec、首 token 延迟和工具调用成功率，而不是靠聊天窗口的手感做判断。

## 踩坑点

- **只看权重显存**：32k 上下文的 KV cache 能再吃好几个 GB，OOM 往往发生在长任务中途，而不是启动时。
- **部分层卸载的假象**：显存不够把一半层放 CPU，速度可能掉到不可用，不如诚实地换小一档的模型。
- **MoE 模型的内存陷阱**：激活参数少、推理快，但全部权重都要驻留内存，按激活参数估显存会翻车。
- **并发排队**：本地推理默认单请求串行，Agent 里并行发起的多个工具调用会排队，耗时要按串行估算。
- **用短 prompt 测速**：Agent 的 system prompt 加工具定义动辄几千 token，预填充阶段才是延迟大头。

## 可复用建议

- **分层模型策略**：本地小模型接高频简单任务（摘要、抽取、路由），困难推理留给云端，按任务路由，不做二选一。
- **选型固化进配置**：模型 tag、量化版本、上下文长度写进配置文件锁定，避免运行时升级导致行为漂移。
- **保留一个真实任务基准脚本**：换模型、换量化、换运行时时跑一遍，三分钟出对比结论。
- **所有工具调用过 schema 校验**：这是本地小模型进 Agent 链路的安全带。

## 总结

本地部署的价值不在于替代云端，而在于给自动化流程一个可控、低成本、可离线的兜底层。先想清楚哪些任务值得下沉，用工具调用成功率和真实任务延迟做验收标准，再把配置固化下来。硬件不够就降一档模型，比硬塞大模型然后天天 OOM 划算得多。
