## 背景

单 agent 跑长任务的老问题：上下文越滚越脏，串行耗时线性增长。当任务能拆成互相独立的小块——比如给 10 个模块补单测、对 5 个数据源各写一份抓取脚本——串行就是在浪费。主流 agent 框架基本都支持派生 subagent：主 agent 发一个任务描述，subagent 拿到独立上下文和工具集，跑完只把摘要交回来。听起来美好，实际编排起来坑不少。这篇记录我们在自动化流水线里跑并行 subagent 的做法。

## 问题

核心是三件事：

1. **怎么拆**——拆错了根本并行不起来；
2. **怎么合**——结果回收不能把主 agent 的上下文撑爆；
3. **怎么不打架**——多个 subagent 同时写文件、同时调同一个 MCP server。

## 做法

按步骤来：

1. **先做独立性判断。** 把任务列出来问一句：A 的产出是不是 B 的输入？凡是需要互相看中间结果的，一律不并行。适合并行的典型场景：多文件同构改动、多数据源独立抓取、多候选方案各自生成再对比。

2. **给 subagent 定死接口。** 任务描述包含四段：目标、边界（允许动哪些路径）、输出格式（我们统一要求返回 JSON：`status` / `changed_files` / `summary` / `risks`）、禁止事项（不要 commit、不要动公共配置）。描述越模糊，subagent 越自由发挥。

3. **工作区隔离。** 代码类任务用 git worktree，每个 subagent 一个分支一个目录；纯分析类任务给独立临时目录。绝不允许多个 subagent 写同一批文件。

4. **并发控制。** 起一个信号量，初期并发 2~3。并发数不是越大越好：模型侧有速率限制，很多 MCP server 也不是为并发设计的（比如共享同一个浏览器实例或本地索引）。

5. **结果回收只收摘要。** subagent 的产出细节落盘（patch 文件、报告文件），主 agent 只读 JSON 摘要和文件路径，需要时再按路径取。这是保住主上下文干净的关键。

6. **失败处理。** 每个 subagent 设超时；失败的先记录、不阻塞其他任务；全部收完后由主 agent 统一决定重试还是降级串行。

## 踩坑点

- **摘要超标**：不限制输出长度，subagent 会把整个推理过程塞回来。给 `summary` 设上限，比如 200 字。
- **MCP 并发瓶颈**：有的 server 内部是单队列，并发调用反而排队。观察工具耗时分布，必要时给不同 subagent 分配不同 server 实例。
- **文件冲突**：两个 subagent 都"顺手"改了公共 util，合并时对不上。靠边界声明 + worktree 缓解，最终合并前跑一遍 diff 审查。
- **嵌套失控**：subagent 又派生 subagent，任务树越长越大。我们直接禁止二层派生。
- **成本**：并行不免费，token 消耗近似翻倍。低价值任务不值得开并发。

## 可复用建议

- 把任务描述模板沉淀成插件或脚本：填四个字段自动生成标准任务，减少人为遗漏。
- 用文件系统当交换区，别用上下文传大块数据。
- 新流程先串行跑通，再开并行；并发从 2 起步，观察后再加。
- 每次编排留档：任务描述、结果 JSON、耗时、token 数。没有留档，复盘全靠猜。

## 总结

并行 subagent 的收益来自任务拆分质量，不来自并发数本身。接口定死、工作区隔离、摘要回收——这三件事做好，主 agent 的上下文才干净，编排才可持续。其余的（并发调优、失败重试）都是在骨架上做增量。建议先把一条串行流程改造并行跑起来，再逐步沉淀自己的编排模板。
