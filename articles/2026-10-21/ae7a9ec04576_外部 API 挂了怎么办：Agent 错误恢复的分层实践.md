## 背景

Agent 的能力边界，很大程度上取决于它能调多少外部 API：搜索、数据库、支付、第三方模型……OpenClaw 的插件和 MCP 工具链也是同样模式。问题在于，这些依赖的可用性不受我们控制。演示时一切正常，凌晨三点第三方接口 502，Agent 该怎么办？多数人第一次认真面对这个问题，是在生产环境里。

## 问题：三种典型的翻车姿势

1. **静默幻觉**：工具调用失败后，模型不想"交白卷"，直接编一个看似合理的返回值。这是最危险的，因为下游完全无感知。
2. **重试风暴**：不区分错误类型，429 也重试、500 也立刻重试，指数级放大故障，顺带烧光自己的配额。
3. **无限挂起**：没设超时，对端 hang 住，整个 Agent 循环卡死，任务队列堆积。

## 做法：把恢复逻辑下沉到工具层

核心原则一句话：**确定性的事交给代码，判断性的事交给模型。**

**第一步：统一客户端封装。** 每个外部调用都过同一层：连接超时 + 读超时（建议整体 10–30s，按接口特性调）、结构化日志、错误分类。这层放在 MCP server 或插件公共库里最合适，Agent 主循环不用感知细节。

**第二步：分类重试。** 只有两类错误值得重试：网络抖动和 5xx/429。429 必须读 `Retry-After`；指数退避加随机抖动（jitter），上限 3 次。非幂等操作（下单、发消息）一律不自动重试，改用幂等键让上层显式决定。

**第三步：熔断与降级。** 连续 N 次失败后打开熔断器，冷却期内快速失败，半开状态试探恢复。降级路径要提前想好：读缓存、切备用供应商，或者明确标记"该步骤跳过"。

**第四步：把错误翻译给模型。** 返回给 LLM 的不是堆栈，而是结构化信息：

```json
{"status": "error", "code": "UPSTREAM_TIMEOUT", "retryable": false, "hint": "搜索服务暂不可用，可基于已有资料继续或告知用户"}
```

同时在系统提示里明确要求：工具失败时如实上报，禁止编造结果。模型擅长的是在"降级方案 A/B/C"里做选择，不是从堆栈里猜原因。

## 踩坑点

- **catch-all 吞异常**：Agent 拿着残缺数据继续跑，比直接失败更难排查。
- **空结果 ≠ 失败**：搜索返回 0 条是合法状态，别当成错误去重试。
- **熔断器没有半开态**：一旦熔断永不恢复，故障从"间歇"变成"永久"。
- **重试无抖动**：多个并发任务同步退避，依赖恢复瞬间打出流量尖峰。
- **超时拍脑袋**：太短误伤慢接口，太长拖死整个循环，按 P99 实测数据定。

## 可复用建议

- 封装一个标准的 `resilient_call(timeout, retries, breaker, idempotency_key)`，所有插件强制复用。
- 给每个任务设"失败预算"：总重试次数和总耗时封顶，防止死依赖烧穿配额。
- 在预发环境做混沌测试：手动断掉依赖，观察 Agent 是优雅降级还是原地崩溃。
- 每次故障后复盘日志，把人工判断的恢复动作固化进策略。

## 总结

外部 API 挂掉不是异常路径，而是 Agent 日常的一部分。好的错误恢复不靠模型"聪明地应对"，而靠工具层的确定性设计：超时、分类重试、熔断、降级、结构化上报，层层兜底之后，模型只需要做它擅长的判断。先把这个封装写好，你的 Agent 才算真正能上生产。
