# 背景

团队每天要交一份服务运行日报。过去的做法是值班同学早上翻日志、截图、手拼数据，平均花 30–40 分钟，且格式因人而异。后来我们用 OpenClaw 搭了一条流水线：定时触发 → 脚本预处理 → Agent 摘要 → 模板渲染 → 推送。上线两个月，日报生成稳定在 2 分钟内，人工介入只剩抽查。

# 问题

最初的偷懒方案是"把原始日志直接丢给 LLM，让它写日报"，很快暴露三个问题：

1. **上下文爆炸**：一天的 INFO 日志轻松上百万行，根本塞不进去；
2. **数字不可信**：模型会在长上下文里数错错误次数、漏掉某时段的峰值；
3. **格式漂移**：每天报告的小标题、统计口径都不一样，无法横向对比。

结论：LLM 适合做归因和叙述，不适合做统计和排版。

# 做法

流水线分四层，核心原则是"脚本管数字，Agent 管叙述，模板管格式"：

1. **采集层**：cron 定时触发一个插件任务，按水位线（上次处理到的时间戳，落库保存）增量拉取日志源，统一成 `{ts, level, source, msg}` 的中间格式，用 run_id 保证重跑幂等。
2. **预处理层**：纯脚本完成——过滤健康检查和 DEBUG 噪声、按错误特征聚类去重、统计每小时错误分布。输出一份 200 行以内的结构化 JSON：错误 Top5、耗时分布、异常事件时间线、关键指标。
3. **摘要层**：Agent 拿到的不是原始日志，而是这份 JSON。通过 MCP 工具调用两个能力：查询历史日报做环比、检索相关告警上下文。Prompt 只要求输出固定 schema 的分析 JSON（根因猜测、需人工跟进项），temperature 设 0。
4. **渲染层**：Jinja2 模板把数据 JSON + 分析 JSON 渲染成固定格式 Markdown，推送到 IM 机器人和邮件。输入快照与渲染产物都落盘，任何一份日报都可回放复现。

# 踩坑点

- **时区坑**：日志源是 UTC，报告口径是本地时间，第一天直接漏了 8 小时数据。所有时间戳在采集层就统一转成带时区的 ISO 格式。
- **重跑重复推送**：任务失败重试导致同一份日报发了三遍。用 `run_id + 日期` 做推送去重键。
- **静默失败**：某天日志源挂了，流水线正常跑完，产出一份"零错误"的日报——比失败更危险。后来加了自检：输入数据量低于历史均值 30% 时，报告头部强制标注"数据可能不完整"。
- **JSON 偶发解析失败**：渲染层做 schema 校验兜底，校验不过就降级走"纯数据版"模板，保证日报至少能发出去。

# 可复用建议

1. **先定义中间 schema 再写代码**。新增日志源只需写一个采集适配器，后三层完全不动。
2. **统计永远用代码，不用模型**。报告里的每个数字都应能在数据 JSON 中找到出处。
3. **报告要可复现**：留存输入快照和渲染产物，出问题能回放定位。
4. **降级路径先于完美路径设计**：LLM 不可用、数据缺失时，数据版日报也要照发。
5. 从一个日志源、三个指标起步，跑稳两周再扩。

# 总结

这条流水线的核心不是"用 AI 写报告"，而是把统计、归因、排版三类职责拆开，各交给最合适的工具。Agent 的价值在于把散落的信号连成一段有判断的叙述，而不是替你数数。拆干净之后，整条链路才真正可控、可复现、可扩展。
