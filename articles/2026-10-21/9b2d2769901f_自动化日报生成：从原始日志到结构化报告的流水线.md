## 背景

团队里总有几类信息散落在不同地方：git 提交、CI/CD 结果、服务器日志、告警渠道、工单系统。每天早上写日报，靠人肉去各处翻，费时且口径不一。我们基于 OpenClaw 的定时任务 + MCP 工具，搭了一条从原始日志到结构化日报的流水线，跑了一个多月基本稳定。这篇把设计和踩过的坑整理出来。

## 问题

第一反应通常是"把日志全丢给 Agent 总结"，实际做会发现三个问题：

1. 原始日志动辄几十万行，token 成本高，还经常被截断；
2. Agent 对噪音敏感，容易把重试日志当成故障，产生幻觉；
3. 输出格式不稳定，今天字段叫"结论"，明天叫"summary"，下游解析和归档全乱。

核心结论先说：**Agent 只做它擅长的那一步（归纳措辞），其余全部交给确定性脚本。**

## 做法

流水线分五层，每层独立可测：

1. **触发层**：OpenClaw 的 cron 定时任务，每天 08:30 拉起一个 session，注入固定的 system prompt。
2. **采集层**：一组小脚本（也可以封装成 MCP tool），分别拉取 git log、CI 运行记录、告警导出、关键服务日志，统一输出 JSON Lines 落盘。
3. **预处理层**：纯脚本。过滤 debug/heartbeat 噪音，按服务分组，做计数聚合（错误数、成功率、提交数），每个服务压成不超过 30 行的结构化摘要。
4. **汇总层**：Agent 只接收预处理后的摘要，按固定 JSON schema 输出：每日变更、异常事件、风险项、待跟进。输出后做 schema 校验，失败自动重试一次，再失败就降级为"原始摘要拼接版"并显式标注。
5. **渲染投递层**：模板渲染成 Markdown 推送到频道，同时把结构化 JSON 归档，供后续周报、月报二次聚合。

## 踩坑点

- **别跳过预处理层**。第一版直接喂日志原文，一天跑三次，两次编造了不存在的故障。加上预处理后归零。
- **时区问题**：CI 平台返回 UTC，日报按东八区切"昨天"，第一周每天漏掉凌晨的提交。采集层统一转成带时区的 ISO 时间。
- **输出不稳定**：LLM 小概率漏字段或多冒出一个 key，下游解析直接崩。加 schema 校验 + 重试 + 降级兜底，才敢说"稳定"。
- **静默失败最危险**：cron 挂了没人发现，连续三天没日报才有人问。改成无论成败都发消息——失败时发"今日数据采集失败，原因：xxx"，远好于沉默。
- **脱敏要在采集层做掉**，不要指望 Agent 自己识别 token 和内网 IP。

## 可复用建议

- **分层原则**：确定性的事（采集、过滤、统计）给脚本，模糊归纳给 Agent，边界越清晰越好维护。
- **schema 是流水线的合同**：改格式先改 schema，再动渲染模板，顺序别反。
- **中间产物落盘**：每层输出保留在工作目录，出问题能定位到具体一层，也方便回放调试。
- **增量上线**：先只接一个数据源跑通全链路，再逐个加，别一次全上。

## 总结

这条流水线的本质不是"用 AI 写日报"，而是把日报拆成确定性与非确定性两部分，各用合适的工具：Agent 负责最后 10% 的归纳表达，前 90% 的可靠性由脚本保证。骨架跑稳之后，只改采集层就能复用做周报、值班交接报告，边际成本很低。
