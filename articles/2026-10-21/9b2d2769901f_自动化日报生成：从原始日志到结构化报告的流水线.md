## 背景

团队日报是个高频但低价值的活：数据散落在 git 提交记录、CI 运行日志、工单系统和服务器日志里，每天有人花 20–30 分钟手工汇总，格式还经常不统一。我们的目标很朴素——把这件事做成无人值守的流水线，产出一份**数字可溯源**的结构化日报。

## 问题

拆开看有三个核心难点：

1. **数据源异构**：JSON 日志、纯文本、API 返回混杂，字段命名各搞各的。
2. **确定性要求高**：日报里的失败率、请求数不能错，也不允许"编"。
3. **需要可追溯**：出了问题要能回答"这个数字哪来的"。

## 做法

用 OpenClaw 搭了一条四层流水线，每层职责单一：

**1. 采集层**：定时任务触发，每个数据源封装成独立的 MCP tool 或 collector 脚本，各自拉取后落盘为中间 JSON。采集和后续步骤完全解耦。

**2. 规范化层**：统一 schema——时间戳转 UTC、日志级别映射、字段改名。这一步全部用纯代码实现，**不要交给 LLM**。

**3. 聚合与摘要层**：这是关键设计。代码先算好所有确定性指标（请求数、失败率、新增工单数），再把结构化摘要喂给 agent，只让它做自然语言解读。Prompt 里明确约束：只允许引用输入数据中出现的数字。

**4. 渲染与投递层**：Markdown 模板渲染，投递到群频道，同时归档一份到对象存储。

## 踩坑点

- **时区边界**：日志里 UTC 和本地时间混用，"昨天"的范围算错过一次，漏掉了晚上 8 点后的告警。对策：全链路统一 UTC，只在渲染层转本地时区。
- **日志格式漂移**：上游改了个字段名，流水线静默产出空值，连续三天日报数据缺失才被发现。对策：加 schema 校验，不合规直接 fail loud，并在日报里显式标注"该数据源异常"。
- **LLM 幻觉数字**：早期直接把原始日志丢给模型总结，它编过一个不存在的错误码。改成"代码算数、LLM 叙事"后才彻底解决。
- **重复投递**：任务手动重跑导致日报发两遍。对策：投递前检查幂等键（日期 + 版本号）。
- **Token 超限**：日志量大了塞不进上下文。对策：先聚合再喂，控制输入在几千 token 以内。

## 可复用建议

- **采集与生成分离**：中间产物落盘，任何一层都可以单独重跑，调试时不用全链路过一遍。
- **数字与叙事分离**：确定性计算归代码，模糊概括才归 LLM。这是整条流水线可信度的基础。
- **日报要自监控**：日报本身包含"数据源健康度"一节，采集挂了当天就能看见。
- **模板版本化**：日报模板放 git，改格式走 review，避免悄悄改坏。

## 总结

上线后日报从每天 20–30 分钟人工参与降到零，可信度反而上升——因为每个数字都能溯源到中间产物文件。核心经验一句话：**让 agent 做它擅长的语言组织，把确定性的事留给代码**。OpenClaw 的插件与 MCP 机制很适合把各数据源封装成独立 tool，而流水线本身保持足够薄，后续接新数据源只是加一个 collector 的事。
