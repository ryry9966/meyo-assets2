## 背景

每天要写日报的人大概都经历过同样的流程：翻服务器日志、翻 git 提交、翻群聊记录，再凭记忆拼一份"今日进展"。这件事不难，但每天 20 分钟的重复劳动，加上遗漏和口径不一致，性价比一直很低。

我的思路是把"看日志"和"写报告"拆开：采集和清洗用脚本做死，理解与组织语言交给 OpenClaw 的 agent。AI 只做它真正擅长的那一段。

## 问题

直接丢给 agent 一句"读日志写日报"是跑不通的，主要三个障碍：

1. **噪音大**：一天下来 debug 行、心跳行动辄几十万条，塞进上下文既贵又没用。
2. **数字不可信**：让模型自己从日志里数部署次数、统计错误率，偶尔会"编"一个看起来合理的数。
3. **失败不可见**：定时任务半夜挂了，第二天没人发现，日报悄悄断更。

## 做法

最终跑起来的流水线分三段，每段独立、可单独重跑：

**第一段：采集与规整（纯脚本）**
- 定时拉取当日数据：应用日志、`git log`、CI 记录、工单状态。
- 统一清洗成 JSONL，每条带 `ts / source / type / message` 四个字段，按日期落盘，如 `logs/2025-06-12.jsonl`。
- 这一层做减法：过滤 debug 级、关键词白名单、单源条数上限（超出先预聚合）。

**第二段：提炼（agent 会话）**
- 定时任务触发 agent，读入规整后的 JSONL。
- 提示词锁死输出模板：今日完成 / 异常与处理 / 风险 / 明日计划，四段固定，Markdown 输出。
- 关键约束：模型只做归类和措辞，所有数字由脚本预计算后作为事实注入，模型禁止自己算。

**第三段：分发与归档**
- 报告写入 `reports/YYYY-MM-DD.md`，摘要推送到频道。
- 原始 JSONL 保留 30 天，报告每节标注数据来源文件，随时可回查。

## 踩坑点

- **噪音控制必须前置**。一开始把过滤放在提示词里（"忽略无关日志"），token 直接爆掉。过滤要在进模型之前完成，提示词管不了体量。
- **格式漂移**。模型偶尔把四段写成三段，或换个标题。后来把模板做成校验脚本，输出不合 schema 就带着错误信息重试一次，基本稳定了。
- **时区坑**。CI 用 UTC、日志用本地时间，第一天的日报里"今日"和"昨日"混在一起。统一在采集段转成同一时区再落盘。
- **静默失败**。加了一条心跳检查：超过 09:00 没生成报告，单独推一条告警，和日报本身分开。

## 可复用建议

1. **模板即代码**：报告结构写在校验脚本里，而不是只写在提示词里。模型负责填内容，不负责定格式。
2. **每段幂等**：任何一段失败都能带着当日数据单独重跑，不产生重复推送。
3. **先接一个源**：只接应用日志跑稳两周，再逐个加 git、CI。一次加一个，出问题好定位。
4. **保留原始数据**：日报是给人看的摘要，排障靠的还是原始 JSONL，两者都要留。

## 总结

跑通之后回头看，核心工作量其实在第一段脚本和第三段的可靠性上，agent 在中间承担的是"理解非结构化内容并按规范输出"——恰恰是脚本最难写、人最烦的部分。经验就一句：能用代码确定的不要交给模型，模型只处理真正模糊的部分。日报本身只是产物，稳定的数据链路才是这条流水线真正的价值。
