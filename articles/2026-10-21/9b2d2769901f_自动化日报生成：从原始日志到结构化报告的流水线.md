## 背景

我们团队的服务和 Agent 任务散落在十几个地方：cron 脚本输出、OpenClaw 会话日志、CI 结果、几个服务的 access log。每天的日报靠人翻日志拼凑，格式时好时坏，还经常漏掉关键异常。这篇帖子记录我把这件事做成流水线的过程，思路不绑定具体业务，可以直接搬走复用。

## 问题

直接让 Agent「读日志写日报」会踩三个坑：

1. 原始日志噪音大，一天的量几十万行，塞给模型又贵又容易漏；
2. 模型自由发挥，今天和昨天的日报结构对不上，没法横向比较；
3. 汇总数字靠模型口算，错了没法追溯。

所以核心设计原则只有一条：**确定性的活交给脚本，模型只做它擅长的那一层。**

## 做法

流水线分四段，每段独立可跑：

**1. 采集（cron，每天 00:05）**：脚本把当天各来源日志抓到 `staging/YYYY-MM-DD/`，统一转成 JSONL，每行至少含 `ts / source / level / summary / raw_excerpt` 五个字段。原始文件保留不删，staging 只是标准化副本。

**2. 预聚合（纯脚本）**：按来源分组，产出确定性统计——各来源条目数、error/warn 计数、Top 异常指纹（message 归一化后去重）。这一步不过模型，数字绝对可靠。

**3. 摘要（Agent + MCP）**：OpenClaw 定时任务在预聚合完成后触发。关键点：给 Agent 的不是原始日志，而是预聚合 JSON + 每类异常抽样 20 行。要求它输出固定 JSON schema（`highlights / incidents / to_watch / empty_ok` 四个数组），通过 MCP 挂载的校验工具做 schema 校验，失败自动重试一次。

**4. 渲染与投递（纯脚本）**：极简模板把 JSON 渲染成 Markdown，写入 `reports/` 后经 webhook 推送到群。同一天重跑即覆盖，天然幂等。

## 踩坑点

- **时区**：日志源头 UTC 和本地时间混用，第一版统计窗口错位一小时。采集层统一转成带偏移量的时间戳，聚合窗口按本地自然日切。
- **格式漂移**：最初让 Agent 直接输出 Markdown，三天后格式就飘了。改成「模型只填 JSON、模板管格式」后彻底解决。
- **Token 失控**：有一次直接投喂全天日志，单次跑掉几十万 token 还超时。大多数场景预聚合已经把量压下来了，真不够再上分片 map-reduce。
- **敏感信息**：日志里有裸 token 和内网地址，采集层加了一道正则脱敏，宁误杀不放过。
- **静默失败**：cron 挂了没人知道。给流水线自己加心跳日志，日报里固定一行「流水线健康度」，哪个来源缺采会显式标出。

## 可复用建议

1. **JSON schema 是 Agent 和渲染层之间的契约**，比在 prompt 里写「保持格式一致」管用得多。
2. **能脚本算的别让模型算**：模型负责归类、措辞、判断轻重，数字一律来自脚本。
3. **先接一个来源跑通全链路**，再横向扩展，别一上来接五个。
4. **staging 目录保留标准化原始数据**，日报有争议可回溯，也方便补跑历史。
5. 这套结构稍改就能做周报：聚合窗口从一天改七天，其余不动。

## 总结

整条流水线脚本约 200 行，Agent 侧只有一段系统提示词加一个 MCP 校验工具。上线一个月，没再漏过 P1 级异常，早上拼日报的时间归零。经验浓缩成一句：日报自动化的难点不在模型，在于先把日志变成「敢让模型看」的形状。
