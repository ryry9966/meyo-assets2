## 背景

Agent 自动化流程里，外部依赖越来越多：模型供应商、MCP 工具、第三方 SaaS、搜索、通知渠道。跑一次长任务可能串起七八个外部调用，任何一个挂了，整条链路都可能停摆。和传统服务相比，Agent 还多一层 LLM：错误信息怎么喂回给模型，直接决定它下一步是重试、换路，还是编一个“看起来成功”的结果。

## 问题

常见的失败模式有三种：

1. **无限重试**：429/超时后模型在循环里“再试一次”，烧 token、拖时间，任务永远不结束。
2. **静默失败**：工具返回空值或异常，Agent 没识别出来，拿半截数据继续往下走。
3. **幻觉成功**：最危险的一种——工具调用明明失败，模型却在总结里说“已完成”，下游的人信了。

根因是同一个：重试和错误分类没有被当成系统设计，而是丢给了模型临场发挥。

## 做法

把恢复逻辑分两层：**客户端层管“怎么重试”，Agent 层管“下一步做什么”**。

**客户端层（工具 / MCP 封装）：**

- 错误先分类：429、503、超时、网络抖动是可重试；401、403、400、配额耗尽不可重试，重试只会更糟。
- 指数退避加抖动（jitter），重试上限 2–3 次。没有 jitter，服务恢复瞬间所有实例一起打过去，等于二次故障。
- 每个调用都设连接超时和读超时，没有超时的调用是定时炸弹。
- 非幂等操作（下单、建工单、发消息）带幂等键。注意：**超时不等于失败**——请求可能在服务端已经生效，盲目重试会产生重复副作用。
- 熔断：连续失败 N 次后进入冷却期，快速失败，别再打上游。

**Agent 层：**

- 工具返回结构化错误，而不是抛完异常让模型猜。例如统一成：

```json
{ "ok": false, "error_code": "UPSTREAM_TIMEOUT",
  "retryable": true, "hint": "稍后重试或跳过此步骤" }
```

- 系统提示里写清失败语义：可重试错误怎么办、不可重试错误怎么办、什么时候升级给人。
- 校验工具返回的 schema，结构和预期不符一律按失败处理——这一条能拦住大部分“幻觉成功”。
- 长流程做检查点，失败后从断点恢复，而不是从头重跑。
- 可选步骤降级：摘要生成挂了就跳过；核心动作挂了才中断并通知人。

## 踩坑点

- **不要让模型负责重试。** 重试放在客户端层，便宜且可控；让 LLM“再试一次”，每次都是真实的 token 和延迟。
- 超时后的结果是不确定的，不是失败的。先查询状态，再决定是否重做。
- 熔断阈值拍脑袋：设太低，一次抖动就把流程打挂；设太高形同虚设。按依赖的 SLA 定，留观测数据再调。
- cron 触发的自动化任务，故障期间任务会堆积。加并发上限和去重锁。
- 降级路径也要测。很多人写了 fallback，上线后从来没真正走到过。

## 可复用建议

- 所有外部调用套同一个客户端封装：超时、重试、错误分类、日志一处搞定。
- 在 MCP 工具层约定统一的错误 schema，Agent 侧只认结构，不猜语义。
- 定期做故障注入演练：把 mock API 挂掉、加延迟，看 Agent 是按预期恢复还是乱来。
- 永远保留人工介入的出口，尤其是涉及钱和外部世界写入的动作。

## 总结

错误恢复不是 prompt 问题，是系统设计问题。把“怎么重试”下沉到客户端层，把“下一步做什么”交给拿着结构化错误信息的 Agent，再用 schema 校验兜住幻觉——多数 API 故障就能从“整条链路停摆”，变成一次可观测、可恢复的降级。
