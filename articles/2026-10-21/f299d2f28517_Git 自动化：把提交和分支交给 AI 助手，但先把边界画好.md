## 背景

用 OpenClaw 这类 agent 写代码之后，开发节奏会明显变碎：一个下午改七八个小功能点，每一处都值得单独成一次提交。手动维护 commit message 和分支很快就会崩——要么攒一大坨 "update" 一把梭，要么分支越开越乱没人收。

我的做法是把「建分支 → 暂存 → 提交 → 汇报」这条流水线交给 agent，人只保留 review 和 push。跑了一个多月，把配置和踩过的坑整理如下。

## 问题在哪

直接给 agent 一个裸 shell 是最省事也最危险的方案，实际会遇到：

- `git add -A` 一把梭，把 `.env`、构建产物顺带提交；
- commit message 空洞，甚至编造不存在的 issue 编号；
- 在 `main` 上直接动手，或嫌 pre-commit 麻烦偷偷加 `--no-verify`；
- 遇到冲突自作主张 `reset --hard`，丢工作区。

结论：不能给裸 shell，要给一份带边界的 git 能力。

## 具体做法

**1. 权限收敛到白名单。** 无论走 MCP git server 还是 OpenClaw 的命令白名单，只放行读状态和本地写操作：

```text
allow: git status / diff / log / branch / switch / stash
       git add <明确路径> / commit
deny:  push --force / reset --hard / clean -fd
       commit --no-verify / rebase / checkout -- .
```

push 默认人工触发。个人仓库可以放宽，团队仓库这条别省。

**2. 写一份 git 约定文档放进仓库**（比如 `GIT_CONVENTIONS.md`），session 开始时让 agent 先读。核心条目：

- 分支名统一 `feat/xxx`、`fix/xxx`；
- 遵循 Conventional Commits，没有明确 issue 引用就不要写编号；
- 只 add 与当前任务相关的文件，禁止 `-A`；
- 禁止在 `main` 上直接提交，禁止改写历史。

**3. 把流程固化成任务模板。** 每个任务开头固定三句：先 `git status` 确认工作区干净 → 从最新 `main` 切新分支 → 干完活分块 stage、逐块提交，最后输出一份变更摘要，等我确认再 push。

**4. 用 hooks 兜底。** commitlint 校验格式、CI 跑 secret 扫描。agent 被 hook 挡住时，明确要求它读错误信息去修，而不是绕过。

## 踩坑点

- **长会话忘分支。** agent 连续跑十几个任务后，会把 A 任务的提交落到 B 分支上。解法是在约定里加一条：每次 commit 前必须 `git status` 核对当前分支名。
- **detached HEAD 乱处理。** agent 不理解这个状态时会乱切乱 reset。约定里写死：遇到不熟悉的 git 状态，停下来问人。
- **`add -A` 复发。** 白名单拦不住 `git add .` 这类变体，最终靠 secret 扫描 + 约定双保险。
- **message 质量漂移。** 会话越长写得越糊。模板里强制每次提交后附「本次改动一句话摘要」，等于让它自检。

## 可复用建议

1. 约定放仓库里，别放全局 prompt——跟着代码走，团队都能复用。
2. 每次提交后输出固定格式摘要，方便人工快速审计。
3. 定期 `git log` 回看 agent 的提交质量，发现的问题反哺约定文档，这个文档是活的。
4. 权限宁紧勿松：加权限容易，出事回滚难。

## 总结

这套东西没有黑科技，本质是三件事：**白名单限权、书面约定、人工 push 门禁**。agent 负责重复劳动，人守住边界。跑顺之后，提交历史反而比手写时更整洁——因为规则被它一字不差地执行了。
