## 背景

在 Agent、MCP 工具调用和插件自动化里，我们经常要求模型输出结构化 JSON。提示词里明明写了“只输出 JSON”，但实测中模型会用各种方式“包装”结果：```json 围栏、`<json>` 或 `<result>` 自定义标签、裸 JSON，甚至说明文字里夹着两段代码块。换模型、升版本、拉长上下文、调高温度时，格式漂移尤其明显。把 LLM 输出当可信输入直接解析，是自动化流程里最常见的一类隐性故障源。

## 问题

几个我真实踩过的坑：

- 围栏语言标记不统一：```json、```JSON、```json5，甚至光秃秃一个 ```；
- 模型不用围栏，改用 `<output>...</output>` 这类标签交差；
- 一次回复先给一个示例 JSON，再给正式结果（两段围栏）；
- JSON 的字符串字段里嵌了 markdown 代码块，简单正则截断在半路；
- 中文语境下混进全角引号、全角冒号、尾逗号、行内注释。

只适配一种格式的解析器，上线后一定会周期性挂掉。

## 做法

我的方案是把解析做成一条分层管线，逻辑收敛在一个模块里：

1. **归一化**：去 BOM、零宽字符，strip 首尾空白；
2. **多策略提取**（按优先级）：
   - 自定义标签优先：正则取 `<result>…</result>`，自己定义的标签最可控；
   - 围栏块：按行扫描 ``` 边界，收集**所有**候选块，不是只取第一个；
   - 括号配平扫描：定位首个 `{` 或 `[`，用带字符串/转义状态的扫描器找配对括号，兜住裸 JSON；
3. **分级解析**：先 `json.loads` 严格解析；失败再做受限修复（去尾逗号、剥字符串外注释、替换全角标点），或上 json-repair / json5 这类库；
4. **Schema 校验**：用 pydantic / jsonschema 验证结构与字段。解析成功 ≠ 语义正确；
5. **受限重试**：校验失败时把报错信息附回给模型自我修正，上限 1–2 次，且永远落盘原始输出。

候选块有多个时，取第一个通过 schema 的；全部失败才走重试。

## 踩坑点

- 围栏正则用 `.*?` 非贪婪匹配，遇到字段值里嵌套围栏会提前截断，按行状态机更稳；
- 无脑取第一个围栏块，拿到的往往是模型给的“示例”而非答案；
- 修复要克制：单引号转双引号可能破坏含撇号的英文字符串，只在严格解析失败后做，修完必须重新校验；
- 全角标点只能替换字符串外的部分，全局粗暴替换会改坏字段值本身；
- 自修复重试不设上限，故障时会烧掉大量 token；
- 温度 0 也不保证格式恒定，模型一升级输出分布就变，解析器要按“一定会变”来设计。

## 可复用建议

- 解析逻辑收敛到单一模块，策略链做成可插拔；
- 平时收集解析失败的原始样本，攒成本地回归测试集，比凭空写的单测值钱得多；
- 把解析失败率当指标监控，突变往往意味着上游模型被更新了；
- 提示词里用自定义标签做输出契约，比指望围栏格式稳定更可靠。

## 总结

LLM 输出应视为不可信的外部输入：归一化 → 多策略提取 → 分级解析修复 → schema 校验 → 受限重试。五层里任何一层单独存在都不够，叠起来之后，解析失败从“日常故障”变成“偶发事件”，而且每次失败都有原始样本可复盘。防御性编程在这里不是过度设计，是自动化流程能长期无人值守运行的前提。
