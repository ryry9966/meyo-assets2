## 背景：多数 Agent 是"被动的"

平时用 OpenClaw，交互模型基本是 pull：你发消息，它回话，不问不动。但一个称职的个人助理应该是 push 的——到期该做的事、异常该报的警，不应该等你想起来去问。

OpenClaw 的 heartbeat 机制就是为此设计的：Gateway 周期性唤醒 agent（默认约 30 分钟，可配置），唤醒时 agent 读一遍工作区根目录（默认 `~/clawd/workspace`）里的 HEARTBEAT.md，有活干活，没活就返回一个简短确认（默认不下发到聊天里）。HEARTBEAT.md 本质上是你和 agent 之间的一份"定时值守合同"。

## 问题

没有心跳机制时有三个痛点：

1. **你得记住该问什么。** 上下文里提过一次的需求，三天后大概率沉底。
2. **cron 解决不了需要判断的事。** "检查收件箱里有没有值得马上看的邮件"这种任务，shell 脚本写不了，agent 一句话的事。
3. **被动 Agent 无法闭环。** 你让它盯一个目录、盯一次构建，它盯完那一次就结束了。

## 做法：四步跑起来

1. **建文件。** 在工作区根目录新建 `HEARTBEAT.md`。
2. **写条目。** 每行一个任务，格式固定为：触发条件 → 动作 → 输出位置。例如：
   - 每天 09:00 前后，汇总 `~/notes/inbox` 下新增文件，写摘要到 `daily.md`
   - 若 `~/deploy/status.json` 中 `build=failed` 且未上报过，整理最近 50 行错误日志发到当前会话
   - 无事可做时，保持沉默
3. **调频率。** 先把 heartbeat 间隔临时调到 1–2 分钟，观察日志确认行为符合预期，再改回 15–30 分钟。
4. **接入工具。** 条目里可以点名调用 MCP 工具或插件，比如定时跑一次仓库巡检、查日历冲突。心跳是"调度判断"的入口，重活交给工具。

## 踩坑点

- **写成散文。** HEARTBEAT.md 是每次唤醒都要读的 prompt，大段落会让 agent 犹豫、浪费 token。用清单，一行一事，条件明确。
- **指令太模糊。** "帮我看看有什么重要的"会得到不可预测的行为。写清楚看哪个路径、什么算"重要"、结果输出到哪。
- **每次心跳都说话。** 必须显式写"无事则沉默"，否则聊天频道会被例行汇报刷屏。
- **在心跳里跑长任务。** 心跳占用当前会话，重任务让它转交 cron 或后台脚本，心跳只负责判断和触发。
- **频率太高。** 心跳是真实的模型调用，30 分钟一次和 2 分钟一次成本差一个量级，先低频验证再加密。
- **权限边界。** 心跳是无人值守执行，别让它带全量工具权限做不可逆操作。给条目加"先 dry-run、输出方案、等人确认"之类的护栏。

## 可复用建议

- 把 HEARTBEAT.md 当 crontab 管理：进 git，改动写 commit message，每月回顾删掉失效条目。
- 条目控制在 20 行以内——它每次唤醒都被完整读一遍，长度直接乘以成本。
- 三层分工：心跳管"要不要做"，cron 管"准点做"，MCP 管"怎么做"。
- 让心跳产物落到固定文件（`daily.md`、`alerts.md`），方便你审阅，也方便后续会话引用。

## 总结

HEARTBEAT.md 只有几行字，但它把交互模型从"你拉"改成了"它推"。工程价值在于：把"需要判断力的定时任务"从 shell 脚本手里接了过来。建议从一两个低风险任务开始——比如每日摘要或构建告警——跑稳了再往外扩。
