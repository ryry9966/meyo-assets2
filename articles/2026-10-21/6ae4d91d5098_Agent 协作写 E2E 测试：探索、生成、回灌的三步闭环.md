## 背景

E2E 测试是大多数团队"知道该写但一直欠债"的部分。单测好写，E2E 麻烦：要搭环境、造数据、维护选择器，UI 一改一片红。而 Agent + 浏览器类 MCP（如 Playwright MCP）恰好擅长"打开浏览器、点一点、看结果"这类事。这篇记录我们在内部项目里让 Agent 参与 E2E 编写与维护的实践，重点讲流程和坑。

## 问题

直接让 AI"帮我写个 E2E 测试"，效果通常很差，集中在三类问题：

1. **幻觉选择器**：模型没看过真实 DOM，编出来的 `data-testid` 和 class 全靠猜；
2. **断言太弱**：生成十几个"能跑过"的用例，实际只验证了页面能打开；
3. **维护脱节**：代码改了测试不知道，红灯全靠人肉排查。

本质是：Agent 缺少对应用运行时状态的真实感知，也没有失败反馈闭环。

## 做法

我们把 Agent 从"生成器"改成"带眼睛的协作者"，分三步：

**第一步：探索优先于生成。** 不让它直接写代码，先通过浏览器 MCP 打开目标页面，抓取 accessibility snapshot，在真实 DOM 上确认角色、标签和可交互元素，产出一页"页面结构笔记"。

**第二步：按约定生成草稿。** 把团队测试约定（目录结构、fixture 用法、选择器规范：优先 role + name，禁止脆弱 CSS 路径）写成一份 markdown，随 prompt 一起喂给 Agent。断言必须锚定第一步的真实快照，不允许凭记忆写。

**第三步：跑挂了就回灌。** 生成的用例直接进 CI，失败输出（报错 diff、trace、截图路径）结构化回传给 Agent 修复。这个"运行—失败—修复"循环通常 2~3 轮收敛。

人在环里只做两件事：**审断言、定边界**。哪些是 bug、哪些是预期，Agent 不该替你决定。

## 踩坑点

- **别信没跑过的测试**。Agent 很擅长生成"看起来对"的代码，未执行的用例价值存疑，一律进 CI。
- **快照很贵**。整页 DOM snapshot 动辄上万 token，按组件/区域截取，或先让 Agent 列候选元素再精确抓取。
- **auto-wait 掩盖问题**。自动等待会让"慢但有 bug"的页面蒙混过关，关键路径要显式断言网络与状态，而非仅元素可见。
- **测试数据污染**。Agent 不了解你的隔离策略，容易写出依赖执行顺序的用例；造数与清理逻辑提前固化成 fixture。
- **别让它顺手重构**。修测试时它很爱"顺便优化"业务代码，prompt 里明确：只改测试。

## 可复用建议

- 把测试约定沉淀为一份静态文档，每次生成都带上，比反复调 prompt 稳定得多；
- 选择器统一 `getByRole` / `getByLabel`，对 Agent 和人都更抗 UI 改动；
- 失败回灌的结构化程度决定修复效率：带截图、trace、断言 diff，别只贴一段报错；
- 维护场景比从零生成更值钱：UI 改动后让 Agent 对照新快照批量修复旧用例。

## 总结

Agent 写 E2E 的价值不在"一键生成"，而在把**探索、生成、运行、修复**连成闭环。生成只是开始，跑通并守住断言质量才算数。我们的经验：Agent 能覆盖七成左右的常规 CRUD 页面用例，复杂交互和边界场景仍需人主导。把它当成一个不知疲倦、偶尔犯错的初级测试工程师来用，预期就对了。
