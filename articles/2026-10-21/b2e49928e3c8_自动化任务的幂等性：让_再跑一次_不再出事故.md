## 背景

在 OpenClaw 这类自动化体系里，任务很少只跑一次：定时调度超时会重试，webhook 源头可能重复推送，Agent 在自检纠错时会重新调用工具，MCP 工具层也可能因网络抖动重发请求。更隐蔽的一种是"成功了但响应丢了"——执行方认为没跑，触发方认为失败，于是再触发一次。

## 问题

一旦操作本身不幂等，重复执行就变成事故：重复建单、重复发消息、文件被追加两次、数据库里出现两行"同一件事"。很多人的第一反应是"加个去重"，但去重加在哪一层、用什么做依据，决定了它是护栏还是摆设。

## 做法

核心一句话：**给每次逻辑操作一个稳定的业务标识，执行前先查，执行时有兜底。**

1. **定义幂等键**。不要用运行时随机生成的 UUID，要从业务语义派生：外部单号、`source_id + 日期`、内容的规范化哈希。标准是"同一任务两次触发，得到同一个键"。
2. **先记录意图再执行**。调外部 API 之前，先落一条 `{key, status: pending}`；成功后更新为 done。重跑时见 done 就跳过，见 pending 且超时则走对账。
3. **用"确保"语义替代"创建"语义**。`mkdir -p` 比 `mkdir` 安全，`INSERT ... ON CONFLICT DO NOTHING` 比裸 insert 安全，写文件用临时文件 + 原子重命名。
4. **把唯一约束当最后防线**。应用层判重存在并发窗口，数据库唯一索引才兜得住，冲突后按"已存在"处理即可。
5. **在插件/工具包装层做透明去重**。对 `(tool_name, 规范化参数哈希)` 做短期缓存，命中直接返回上次结果。注意"规范化"：先剔掉时间戳、随机数字段再哈希，否则缓存永远不命中。

伪代码大致是：

```text
key = derive_from_business(payload)
if state(key) == done: return last_result(key)
try: insert(key, pending)          # 唯一索引兜底
except Conflict: return wait_or_verify(key)
result = do_action()
update(key, done, result)
```

## 踩坑点

- **幂等键生成在重试循环内部**：每次重试都 new 一个键，等于没设防。
- **先查后写没有原子性**：两个并发实例同时查到"不存在"，然后都执行。要么靠唯一约束，要么加锁。
- **键的作用域失衡**：带秒级时间戳，重试晚一秒键就变了；粒度太粗，又会吞掉合法的新任务。
- **外部系统最终一致**：执行完立刻反查状态，对方还没更新，误判"没执行"导致二次发送。重要动作给状态检查留缓冲窗。
- **只处理失败重试，不处理"成功但响应丢失"**：这类重跑靠查证而非重放，先调查询接口确认结果，再决定是否补执行。

## 可复用建议

- 写每个定时任务、webhook、Agent 步骤时，先回答一个问题：**这段代码被执行两次，会发生什么？** 答不上来就是隐患。
- 分层设防：业务幂等键 → 唯一约束 → 工具层缓存 → 重复发生时告警。任何一层失效，下一层兜住。
- 日志带上幂等键，出问题能追溯"这次为什么被放行/拦截"。
- 把工具设计成 `ensure_xxx` 而不是 `create_xxx`，让调用方天然可重入。
- 在 staging 把整条流水线连续跑两遍，断言副作用数量不变——这是最便宜的幂等性测试。

## 总结

幂等性不是锦上添花的优化，而是自动化系统敢开重试、敢开调度、敢让 Agent 自主重跑的前提。重试策略只解决"愿不愿意再跑一次"，幂等性才解决"再跑一次会不会出事"。把"可重复执行"当成设计目标而不是运气，自动化才真正可以托付给别人管。
