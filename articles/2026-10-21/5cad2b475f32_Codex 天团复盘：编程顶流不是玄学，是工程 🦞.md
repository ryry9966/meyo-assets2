36kr 那篇「Codex 天团深度复盘」上了热搜，把一个老牌名字的二次创业讲得挺透。Codex 不是新词，2021 年它就是 GitHub Copilot 背后的模型，2023 年 API 下线，一度像被时代翻篇；2025 年它以 coding agent 的身份满血归来，成了 OpenAI 增长最快的开发者产品线之一。今天不聊八卦聊机制：一个编程模型从「能用」到「顶流」，中间到底隔着哪几道坎？老规矩，开拆。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-21/57fb32e46a1a7898.png)

## 先补课：Codex 的前传与重生

- **2021 年**，OpenAI 发布 Codex：在 GPT-3 上用海量公开代码 fine-tune 的专用模型，GitHub Copilot 的早期能力就来自它。当时的产品形态是「补全」——你在 IDE 里打字，它续写下一行。
- **2023 年 3 月**，Codex API 正式下线，团队火力转向 GPT-4。对外看像弃子，实际是把代码能力并入通用基座模型。
- **2025 年**，Codex 以全新身份回归：4 月开源了 Codex CLI（跑在终端里的本地 agent），5 月推出云端 agent 版本，底层是 codex-1，基于 o3 用强化学习在真实软件工程任务上训练；随后 GPT-5-Codex 等迭代持续跟进。
- **形态彻底变了**：从「你打字它补全」的同步工具，变成「你派活它交付」的异步 agent，任务丢进云端沙箱，它自己读仓库、改代码、跑测试、开 PR，多个任务可并行，单个任务经常持续几分钟到半小时。

第一个启示就在这段历史里：顶流不是一口气炼成的，是「模型能力曲线」和「产品形态」恰好对上了时机。补全时代模型不够强，agent 时代刚好够用。

## 核心机制：为什么编程是 RL 的天选之地

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-21/d448177a5cb52056.png)

这波模型进步的引擎是 RL（强化学习），而 RL 最怕两件事：环境建不起来、奖励算不出来。编程恰好两头都占便宜：

1. **可验证奖励（verifiable reward）**。数学和代码是少数「有标准答案」的领域：代码要么编译通过、要么不通过，单测要么全绿、要么不红。测试套件、类型检查、CI 天然就是一台自动判分机，让 RLVR（用可验证奖励做强化学习）能规模化跑起来。对比之下，「文案写得好不好」这种主观任务的奖励信号就模糊得多。
2. **环境可构造**。训练 agent 需要海量真实感任务环境。代码领域可以把真实仓库的历史 issue 和 PR 快照成任务：给模型一个带 bug 的 checkout，让它修到测试通过为止。环境可以无限生成、自动校验，成本远低于人工标注。
3. **执行反馈闭环**。codex-1 的训练目标是「像一个靠谱同事那样干活」：跑测试到通过为止、遵循仓库现有风格、产出能被 review 的 diff。官方公布的 SWE-bench Verified 成绩约 72%，且是不借助测试脚手架、单次尝试的结果——放在 2025 年属于第一梯队。

一句话总结：编程领域把 RL 最难的两件事（环境、奖励）从科研问题变成了工程问题。这是「编程 agent 第一个跑出来」的根本原因，不是玄学。

## 组织打法：小团队、高授权、模型和产品同锅炒

复盘里另一个值得细看的维度是组织：

- **团队小而密**。Codex 核心团队早期只有十几个人，但成员横跨 post-training（RL 训练）、产品和基础设施。决策链路短，改一个 eval 到看到模型行为变化，中间可能只隔一顿饭。
- **自家狗粮管够**。团队自己就是重度用户：日常开发、修内部 bug 都交给 Codex 跑，定期复盘「agent 哪里让人失望」，这些真实挫败直接变成下一轮 evals 和训练数据。OpenAI 内部后来甚至有「多数新代码由 AI 参与生成」的说法，dogfooding 的密度决定打磨速度。
- **模型和产品一起迭代**。多数公司是「模型组交付 API，产品组接需求」，Codex 是反过来的：产品形态（异步、并行、沙箱）反哺训练目标（长任务、自我验证、少打扰人）。沙箱里能并行跑几十个任务，前提是模型被训练成「能独处半小时不闯祸」。
- **敢砍敢重启**。前传里那段 API 下线不是失败，是止损：与其在补全形态上挤牙膏，不如把代码能力并进基座模型，等 agent 范式成熟再杀回来。判断「什么时候放弃一个形态」，本身就是顶流团队的核心能力。

## 容易被忽略的工程细节：沙箱、复现与无聊的美德

- **沙箱与安全**。云端 agent 的每个任务跑在隔离容器里：无外网、受控依赖，防止「顺手装个带毒的包」这类供应链风险。这不是炫技，是 agent 能被企业采用的前提。
- **环境可复现**。agent 接到任务的第一步是「把项目跑起来」。setup 脚本、依赖锁定、环境变量管理这些无聊活，直接决定成功率。很多团队 agent 用不好，卡点不在模型，在仓库本身的「可启动性」。
- **反馈回路的质量**。与其抱怨模型笨，不如先给够「判分器」：更全的测试、更快的 CI、更清晰的 lint 规则。模型会朝着你能量化的方向优化，这既是机会也是风险——你只测了什么，它就只对什么负责。

## 三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-21/86e2d62f14b98ce9.png)

1. **选战场先看可验证性**。个人或团队挑 AI 落地方向时，优先挑「对错能自动判定」的环节：代码、数据清洗、规则审核。反馈信号越清晰，自动化收益越大；纯主观创意环节，短期内别指望 agent 顶上。
2. **用杠杆重新定义团队规模**。Codex 的故事说明：小团队 + 高杠杆工具 + 短反馈回路，可以打大仗。与其急着扩人头，不如先问自己：evals 建好了吗？反馈回路多快？「一个人带十个 agent」的产能公式已经成立，岗位设计要跟着变。
3. **别把 demo 分数当护城河**。跑分是入场券，不是终点。真实仓库上的通过率、返工率、人类 review 成本，才是产品力。反过来说，如果你的业务数据、环境和工作流沉淀得足够好，这恰恰是通用大模型短期内拿不走的那部分价值。

每一次「顶流诞生」，拆开看都是老三样：清晰的奖励信号、快速的反馈回路、克制的组织。代码只是恰好三条全占的第一个战场，大概率不会是最后一个。
