# Agent 与 API 的握手：OpenClaw 怎么对接外部服务

## 背景

Agent 的规划能力再强，真正"落地"的还是那几次 API 调用。OpenClaw 的设计思路是让模型专注编排，把取数、写库、触发外部动作交给工具层。这一层做不好，前面跑得再顺也是空转。

## 问题

模型不会天然使用 HTTP：它不知道你的接口参数、鉴权方式、错误语义。实际项目里的翻车集中在三类：

- 工具 schema 与实际接口不一致，模型拼参数基本靠猜；
- 超时与重试没有设计，POST 被重放，产生重复下单；
- 返回体太大，一次调用吃掉半个上下文窗口。

## 做法

1. **选对接路径**：优先 MCP server，把外部服务封装成独立进程，OpenClaw 通过标准协议做工具发现和调用；内部简单场景用插件直接注册 tool 更省事。
2. **一个工具一个意图**：`create_order` 就只下单，别做成万能 `do_action`。参数字段名与业务接口保持一致，description 写清单位、枚举值和边界条件。
3. **鉴权集中管理**：凭证放环境变量或密钥服务，工具运行时注入；绝不让 token 出现在 prompt、日志或工具返回值里。
4. **超时与重试**：默认 10–30 秒超时；只对幂等的 GET 自动重试，POST 一律带幂等键（Idempotency-Key），失败与否交给上层决策。
5. **裁剪返回体**：接口一次返回 1000 条列表时，工具层先分页、截断、只留关键字段再回给模型，必要时返回一个"取下一页"的游标。
6. **可观测性**：每次工具调用记录参数摘要、耗时、状态码，agent 跑偏时才有得复盘。

## 踩坑点

- description 写得太省，模型会把返回值里的 `status: "ok"` 当成参数传回来；
- 长任务在工具里同步轮询，把 agent 整个卡死——改成提交任务返回 `job_id`，再单独提供一个查状态的 tool；
- 忽略限流，agent 高频自动重试直接触发 429，形成重试风暴；
- 错误信息直接透传原始堆栈，模型会自由发挥编故事，应转成结构化的简短错误描述。

## 可复用建议

- 工具命名统一"动词 + 宾语"，返回值统一 `{ok, data, error}` 结构，模型学得快、出错率低；
- 为每个外部依赖加一层薄适配器，上游接口升级时只改适配器，工具层不动；
- 上线前做一轮工具冒烟：正确参数、缺参、错误参数各跑一次，确认三种路径的返回都"模型可读"。

## 总结

对接外部服务不是"把 API 塞给模型"，而是替模型做一次减法：接口要窄、语义要明、失败要可控。工具层越安静，agent 越可靠。建议从一个最小的 MCP server 起步，先跑通一条端到端链路，再横向铺开——比一次性注册十几个工具然后调 schema 要划算得多。
