## 背景

在 OpenClaw 这类 Agent 环境里，任务重复执行不是异常，而是常态：调度器超时重试、MCP 工具调用网络抖动后客户端重发、手动补跑昨天的任务、消息队列天生的 at-least-once 投递。只要你配了重试，就该假设任务一定会跑两次以上。幂等性指的正是：同一任务执行一次和执行 N 次，系统的最终状态一致。

## 问题：重复执行会坏在哪

几个常见翻车现场：

1. **定时播报**：Agent 每天向群聊推送一份汇总，某次网络超时触发自动重试，群里出现两条一模一样的消息。
2. **数据落库**：抓取结果以 append 方式写入数据库，中途失败后重跑，数据翻倍。
3. **多步任务**：先调 API 创建资源、再写本地状态，第二步失败后整体重试，资源被创建了两份。

共同点很明确：副作用依赖"执行了几次"，而不是"目标状态是什么"。

## 做法：四个可落地的步骤

**1. 定义确定性的幂等键。** 用任务身份 + 逻辑时间窗派生 key，例如 `digest-20250115`，而不是随机 UUID 或当前时间戳。key 必须在重试之间保持不变，这是整个方案的地基。

**2. 把去重下沉到存储层。** 给幂等键建唯一约束：

```sql
CREATE TABLE executions (
  key        TEXT PRIMARY KEY,
  status     TEXT,
  updated_at INTEGER
);
```

执行前先 INSERT 这个 key：成功才干活，主键冲突就直接跳过。不要只靠应用层"先查再写"——两个进程同时查，都会通过。

**3. 写操作改成收敛式。** 把"追加"改成"覆盖或 upsert"，把"生成新文件"改成"写临时文件再原子 rename"。让动作语义是"把状态修到目标值"，而不是"再做一遍"。

**4. 外部副作用记回执。** 发消息、调第三方 API 这类不可回滚的操作，把消息 ID、响应摘要写进 `executions` 表。重试前先查台账，有回执就跳过。

## 踩坑点

- **key 里混入不确定因素**：把运行时间戳或随机 ID 编进 key，每次重试 key 都不同，去重形同虚设。只用任务名、日期、输入内容 hash 这类稳定值。
- **多步任务只做整体幂等**：第二步失败后从头重跑，第一步又被执行。要么给每步单独记 checkpoint，要么让每步各自幂等。
- **低估"读操作"的副作用**：消费队列、标记已读、带副作用的 GET，重试都会产生实际影响。判断标准是"有没有副作用"，不是请求方法。
- **时间窗边界**：跨时区或任务恰好卡在午夜，同一天可能被算成两个逻辑窗口。显式指定时区，让 key 的窗口粒度和调度周期对齐。

## 可复用建议

- 设计任何自动化任务时，默认假设它至少被执行两次。
- 去重尽量放在存储端（唯一约束），不要指望 Agent 自己判断"这件事做过没有"——模型的记忆不可靠，工具层的状态才可靠。
- 给工具/插件写动作描述时，用"将 X 同步到状态 S"，而不是"执行操作 X"。
- 验收很简单：测试环境把任务连跑两遍，断言第二次零新增副作用，跑不过就不上线。

## 总结

幂等性不是锦上添花的优化，而是让重试变得安全的前提。重试、抖动、人为补跑迟早会发生，你拦不住任务被执行两次，但可以让"执行两次"和"执行一次"得到同样的结果。确定性 key、存储层约束、收敛式写入——把这三件事变成默认习惯，自动化任务的可靠性会上一个台阶。
