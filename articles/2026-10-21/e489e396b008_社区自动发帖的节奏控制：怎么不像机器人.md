## 背景

用 OpenClaw 挂一个定时任务，让 Agent 通过 MCP 工具往社区自动发内容，是很常见的玩法：日报、新版本摘要、FAQ 整理。跑起来不难，难的是跑得"像个人"。我们最早的实现很朴素：cron 整点触发，Agent 生成后直接发。三天后就有群友问"你们是不是接了个机器人"，第五天被管理员私聊了。

## 问题

不像人的发帖节奏，通常有这几个特征：

1. **时间点过于规律**：整点触发、固定间隔，时间戳一看就是脚本；
2. **突发连发**：多个任务同时命中，一分钟内连发三条；
3. **内容模板化**：开头、结构、表情组合高度一致，节奏对了也能一眼认出；
4. **无上下文感知**：凌晨频道没人说话，机器人准时开讲；或频道正在激烈讨论时硬插一条日报；
5. **失败重试无节制**：接口报错后每分钟重试一次，像攻击行为。

本质上这是一个限流器（rate limiter）设计问题，只是约束从"保护下游"变成了"贴合人类活跃规律"。

## 做法

最终收敛出的结构，核心原则只有一条：**生成与发布分离**。

### 1. 生成入队，发布单独控制

Agent 生成的内容先写入 draft 队列（SQLite 足够），由独立的 publisher 进程决定"何时发、发不发"。解耦之后，节奏控制才有抓手。

### 2. 带约束的随机调度

不做固定间隔，也不做纯 `random.uniform`——后者照样可能背靠背连发。用基础间隔 + 抖动 + 最小间隔兜底：

```python
import random

def next_delay(base_s, jitter_ratio=0.35, min_gap_s=5400):
    d = base_s * random.uniform(1 - jitter_ratio, 1 + jitter_ratio)
    return max(d, min_gap_s)
```

同时把发布窗口约束在活跃时段（如 9:00–23:00），按社区在线人数加权抽样，而不是均匀分布。

### 3. 日配额与滚动窗口

每天上限 3–4 条，任意 3 小时滚动窗口内最多 2 条。publisher 取任务前先查计数器，超了就顺延到下一窗口。

### 4. 上下文检查再放行

发布前做轻量检查：频道最近 30 分钟有无新消息、是否正在讨论事故或敏感话题。静默期推迟，热点期只放行高优先级内容。

### 5. 内容层去模板化

节奏对了，内容露馅也白搭。要求 Agent 每次变换开头句式、长短交替（短动态和长帖混排）、是否带列表；签名和固定 emoji 组合一律去掉。

### 6. 失败处理与幂等

重试用指数退避 + 抖动，每次发布携带幂等键，避免重试风暴造成重复发帖。

## 踩坑点

- **时区**：服务器是 UTC，社区是本地时间，最初"活跃窗口"整体错位，排查一晚日志才发现；
- **过度随机**：抖动太狠会出现凌晨 4:17 发帖，比整点更像机器人。随机必须被活跃时段约束；
- **队列堆积**：draft 队列不设 TTL，积压两天后发出的"今日资讯"已是旧闻，观感比不发还差。现在超过 24 小时的任务直接丢弃；
- **周模式重复**：单次随机没问题，但每周分布长得一样（周一密、周末无）也会被看出规律，后来把 base_interval 按周内日期再扰动一层；
- **只调时间不调内容**：内容去模板化带来的观感改善，不比调度策略小。

## 可复用建议

- 节奏参数全部配置化：`active_hours`、`base_interval`、`jitter_ratio`、`daily_cap`、`min_gap`，别写死在代码里；
- 只让一个 publisher 拥有"发"的权限，生成侧再多 Agent 也只是入队；
- 上线前跑两周 dry-run：所有决策只写日志不发布，人工复核节奏分布再切换；
- publisher 每次决策（发/延/弃）都记录原因，方便回溯"为什么那几天没发"。

## 总结

节奏控制不是把自动化藏得更深，而是把发帖当成对社区带宽的占用，按限流器的思路做设计：解耦生成与发布、带约束的随机、配额与窗口、上下文感知、内容去模板化。验收标准很简单——把发布时间戳列出来给自己看，如果不觉得突兀，社区成员大概率也不会。
