## 背景

跑在 OpenClaw 上的 Agent 往往不是一次会话就结束：它挂着 MCP 工具、定时任务，同时服务几个项目。但底层模型每次都是失忆状态——你的包管理器偏好、commit message 风格、回复详略习惯，每个新会话都得重新交代一遍。很多人第一反应是"存聊天记录再做检索"，我踩过这条路，结论是：方向反了。

## 问题：三种常见做法为什么不行

1. **全量塞 system prompt**：上下文膨胀，成本上涨，关键偏好被无关内容稀释；
2. **对历史对话做向量检索**：检索回来的是"你当时怎么说的"，不是"你想要什么"，相似度高不等于偏好明确；
3. **让模型自由写记忆**：没有写入门槛，一句"今天累了，回复短点"会被永久记住，两周后还在生效。

记忆系统的难点不在"存"，在**什么时候写、写什么、什么时候忘**。

## 做法：一个够用的分层方案

**第一步：分层，别用一个池子。**

- 偏好层：结构化、低频变化，比如"用 pnpm""解释要带代码示例"，每条带 `updated_at` 和 `source`；
- 事实层：项目路径、账号别名这类能随时查证的信息——能查到的就不存；
- 会话层：scratchpad，会话结束即弃。

**第二步：给写入设门槛。** 只有三类信号允许写入：显式指令（"以后都用 X"）、重复纠正（同类纠正第三次出现自动提升为偏好）、主动询问确认。通过 MCP 暴露 `memory_write` 工具，强制要求 agent 附带 `reason` 字段，没有就拒绝写入，且全部落日志。

**第三步：读取分两条路。** 会话启动时把偏好层渲染成十几行摘要注入 system prompt（控制在 300 token 内）；细节按需调 `memory_search`。偏好层总量封顶 50 条，满了就强制先淘汰再写入。

**第四步：用 git 管记忆。** `memory.md` 直接进仓库，diff 可见，回滚一条错误记忆就是一次 revert。

## 踩坑点

- **记忆腐化**：过期偏好没人清理，agent 一直按三个月前的规则干活。让 agent 每周自查一遍偏好层，列出可疑项等你确认；
- **隐式泛化**：一次性情绪被固化成偏好，写入门槛必须包含持久性判断；
- **冲突静默覆盖**：两条偏好打架时默认最后写入的赢，你毫不知情，changelog 必须保留；
- **作用域串味**：单项目的规则混进全局（A 仓库用 npm，其他用 pnpm），`global / project / session` 三级作用域第一天就要有。

## 可复用建议

- 先用纯 markdown 文件加一段写入门槛指令跑起来，容量到几百条再上 MCP + SQLite，别一上来就建向量库；
- 每条记忆固定五个字段：`key / value / scope / updated_at / source`；
- 把记忆当代码测：写个脚本开全新会话，喂固定输入，断言偏好生效——记忆回归测试比想象中有用；
- 只存"问不出来的"，能重新推导的一律不存。

## 总结

记忆系统的上限由写入纪律决定，不是检索算法。小而显式、可版本化、有淘汰机制的记忆文件，比大而全的向量库实用得多。先让它记住对的事，再谈记得多。
