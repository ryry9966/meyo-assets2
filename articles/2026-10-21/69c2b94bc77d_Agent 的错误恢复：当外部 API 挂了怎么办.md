## 背景

在 OpenClaw 的 Agent 场景里，一次任务往往串着七八个外部依赖：模型推理、搜索、MCP 工具、自家业务 API。任何一个环节 429、超时或者 502，整个任务流就可能停摆。我跑一个自动化日报 Agent 时，搜索 API 连续限流，Agent 重试了十几次后把上下文撑爆，最后输出了一段编造的"搜索结果"。从那以后我把错误恢复当成一等公民来设计。

## 问题拆开看

外部 API 挂掉时，朴素写法通常有三种死法：

1. **直接崩**：异常没兜住，任务中断，前面的工作全部作废。
2. **死循环重试**：没有退避策略，越重试越触发限流，烧 token 也烧钱。
3. **幻觉兜底**：错误信息被塞进上下文，模型"脑补"一个结果继续往下走——这是最危险的。

## 我的做法：分层兜底

**第一步：错误分类。** 把工具调用的错误归为两类：可重试（429、5xx、超时、网络抖动）和不可重试（400、401、403、404、参数校验失败）。逻辑很简单，但决定了后面所有策略。

**第二步：重试加退避和抖动。** 可重试错误用指数退避（1s → 2s → 4s…封顶 30s），并加随机抖动。固定间隔重试会让多个实例在同一时刻一起撞限流。

**第三步：熔断与降级。** 连续失败超过阈值（比如 5 次）就熔断，冷却期内直接走降级路径。降级选项按优先级排：备用 API → 本地缓存 → 明确告知"该数据暂不可用"。注意熔断要按工具粒度设，别让一个坏掉的 API 拖死整个 Agent。

**第四步：幂等和断点。** 有副作用的操作（下单、发消息、写库）必须带幂等键。超时不等于失败——请求可能已经成功，盲重试就是重复执行。长任务每步落一次状态检查点，恢复时从断点续跑，而不是从头再来。

**第五步：把错误诚实地交给模型。** 给模型的是结构化摘要：工具名、错误类型、已重试次数、建议动作（换工具 / 跳过 / 上报）。不要喂原始堆栈，也不要为了让流程"看起来正常"而隐藏失败。

## 踩过的坑

- **对 POST 盲目重试**，导致重复推送了三条通知。非幂等操作先补幂等键，再谈重试。
- **退避没加抖动**，多任务并行时重试请求同步共振，限流雪上加霜。
- **熔断设成了全局**，一个天气 API 挂掉把整个 Agent 停了，其实其他工具都正常。
- **超时后直接当失败**，实际服务端已执行成功，靠幂等键 + 状态查询接口才兜回来。
- **重试没有硬上限**，一个死循环任务一晚上烧掉不少 token。任何重试必须有封顶。

## 可复用的建议

1. 所有工具调用收口到统一的执行器：超时、重试、熔断、日志在一处配置，别散落在各插件里。
2. 结构化记录每次失败：工具名、错误类别、耗时、第几次尝试。事后复盘全靠它。
3. 降级答案宁可"少而诚实"，也不要"多而虚构"。
4. 定期做故障演练：用代理人为注入 500 和超时，验证恢复路径真的能走通。没被演练过的降级逻辑，等于没有。

## 总结

错误恢复不是一个 try/except，而是一条链路：**分类 → 退避重试 → 熔断降级 → 幂等断点 → 如实上报**。核心原则只有一条：让 Agent 在依赖不可靠的世界里，输出可信、可解释的行为——哪怕是失败，也要是诚实的失败。
