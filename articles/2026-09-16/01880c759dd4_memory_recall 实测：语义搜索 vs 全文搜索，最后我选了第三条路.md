## 背景

OpenClaw 里 `memory_recall` 是 agent 回看历史的入口：会话摘要、踩坑笔记、用户偏好都躺在工作区的 markdown 里，模型靠这个工具把它们捞回来。用得久了会发现一个朴素的规律——捞不捞得回，直接决定助手"像不像记得你"。

## 问题

检索基本就两条路：

- **语义搜索**：向量化 + 相似度，能兜住换说法的查询（"上次部署炸了" ↔ "deploy failure 排查记录"）；
- **全文搜索**：BM25 / FTS，精确命中错误码、函数名、项目代号这类硬 token。

各自单用盲区都很明显：语义检索会漏掉精确标识符，全文检索对改写无能为力。实际该选哪个？

## 做法

1. **自建评测集**：从真实使用记录里抽 30–50 条查询 + 应命中的记忆条目。不要用想象出来的 query，合成样本会严重高估语义检索。
2. **跑双基线**：FTS5（BM25）一路，中文友好的 embedding（bge 系即可）一路，记录 hit@10 和延迟。
3. **看互补性**：我的结果是语义赢在改写类查询，全文赢在标识符类查询，几乎没有重叠——这基本决定了要混合。
4. **上混合检索**：两路各取 top20，用 RRF（倒数排名融合）合并。别直接加权两路分数，量纲不同，调不好。
5. **调 chunk 粒度**：记忆条目按"一条一事"切，标题和日期放条目开头，别把整个 session 塞进一个向量。

## 踩坑点

- SQLite FTS5 默认分词器对中文基本失效，整句会被当成一个 token，必须换 trigram 或外部分词后入库。
- 换 embedding 模型必须全量重建索引，向量记录里务必存模型版本号，否则新旧向量混搜结果不可信。
- 语义检索对时间一视同仁："半年前的旧结论"会压过"上周的修正"，需要加时间衰减或日期加权。
- 本地 CPU 跑 embedding，单次延迟可能从几毫秒涨到几百毫秒，交互场景要权衡。
- 融合权重不是拍脑袋定的，RRF 里的 k 也要在自己评测集上扫一遍。

## 可复用建议

- **默认上混合 + RRF**，这是性价比最高的终点，不是优化到最后一刻才考虑的选项。
- **检索质量一半由写入侧决定**：短条目、带标签、日期在前，比任何检索算法调优都划算。
- 把每次 recall miss 记进评测集，检索是长期维护项，不是一次性配置。
- 如果记忆总量只有几百条、查询以标识符为主，纯 FTS 够用，别为了架构而架构。

## 总结

这不是二选一的问题。语义和全文解决的是两类不同的失败模式，在自己的真实数据上跑一遍评测，大概率会落到混合方案。比选型更重要的两件事：用真实查询持续评测，以及在写入端把记忆组织好。
