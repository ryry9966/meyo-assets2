## 背景

OpenClaw 的 memory 机制，核心是一个很朴素的问题：助手干活时，怎么把该想起来的记忆想起来。`memory_recall` 就是这条链路——消息进来，先召回若干条历史记忆，再拼进上下文。

我的记忆库大约 3000 条：会话摘要、踩坑笔记、服务器信息、个人偏好。此前一直走语义检索，最近发现部分查询明显召不回，于是把全文搜索拉进来做了轮对比。

## 问题：两种检索各有一类盲区

- **语义搜索**（embedding + 向量近邻）：对“换个说法”很稳。问“上个月数据库为什么变慢”，能召回当时记的“Postgres 慢查询排查”。但对精确标识符很差——查 `srv-jp-02`、错误码、某条命令，向量相似度经常排不进前列。
- **全文搜索**（FTS/BM25）：精确词命中极强，标识符一查一个准。但中文分词和同义改写是硬伤，“机器人连不上”搜不到记成“gateway 掉线”的条目。

结论先行：这不是二选一，是分工问题。

## 做法

1. 构建 30 条金标准查询，每条标注期望命中的记忆 ID，覆盖标识符类、语义改写类、时间类三种。
2. 全文侧用 SQLite FTS5，中文内容用 jieba 分词后入库。
3. 语义侧用 sqlite-vec，条目向量化，查询时实时 embed。
4. 两路各取 top-k，用 RRF（倒数排名融合）合并，取前 5 条进上下文。
5. 用 recall@5 对比单路与混合。

结果：语义单路 recall@5 约 0.71，全文单路约 0.63，混合后到 0.87。提升主要来自标识符类查询——这类查询在语义路线下基本全军覆没。

## 踩坑点

- FTS5 默认的 unicode61 分词器对中文基本无效，整句会被当成一个 token，必须先分词或改用 trigram。
- 换 embedding 模型要全量重建索引，务必在元数据里记录模型版本，否则新旧向量混在一个空间，排序全是噪声。
- 记忆条目太长会稀释向量语义，单条建议只讲一个主题，标题和标签抽成独立字段供全文检索。
- 语料只有几百条时，语义检索的评测波动很大，别靠一两次体感下结论。

## 可复用建议

- 默认上混合检索，RRF 融合实现简单，不用调融合权重。
- 精确信息（ID、路径、命令）落库时抽成结构化字段，走 metadata 过滤比硬搜更可靠。
- 维护 20~30 条金标准查询集，改检索策略前后各跑一遍，比体感靠谱得多。
- embedding 模型版本写进记忆元数据，为将来换模型留后路。

## 总结

语义和全文不是竞品，是互补的两只手：语义管“意思相近”，全文管“一模一样”。`memory_recall` 的质量上限，往往不取决于检索算法多先进，而取决于记忆本身写得干不干净。先把条目写短、写结构化，再谈检索优化。
