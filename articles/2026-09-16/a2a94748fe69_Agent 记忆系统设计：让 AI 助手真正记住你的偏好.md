## 背景

LLM 本身无状态。今天你告诉助手"我的时区是 UTC+8，代码注释用中文"，明天开新会话它照样再问一遍。上下文窗口再大也解决不了跨会话问题——用户偏好属于长期知识，不该靠往 system prompt 里硬塞。MCP 的出现让"外挂记忆"有了标准做法：一个提供 memory 工具的 server，任何支持 MCP 的 agent 都能接上。

## 问题：三种典型失败

动手之前，先把常见跑偏的记忆系统归个类：

1. **什么都不记**：体验最差，用户被迫每次重复交代。
2. **什么都记**：把每轮对话原文往库里塞，两周后检索结果全是噪声，真正的偏好被闲聊淹没。
3. **记了但不对**：用户三个月前说要简洁回复，现在口味变了，旧记录照样生效——没有更新和失效机制。

核心矛盾不在"存"，在"该存什么、怎么取、何时失效"。

## 做法：分层存储 + 结构化写入 + 混合检索

**第一步，分层。** 只做两层：会话内的工作记忆（本来就在上下文里），跨会话的事实库。第三层"历史会话摘要"可选，优先级放低。

**第二步，定 schema。** 每条记忆至少包含：`scope`（偏好/事实/项目上下文）、`content`、`confidence`、`updated_at`、`source`。存结构化记录而不是对话原文，这是后面一切的地基。

**第三步，写入手册。** 抽取逻辑放到会话结束或每 N 轮批量执行，不要每轮都跑。抽取时做去重合并：同 scope 新条目默认覆盖旧条目，带时间戳留痕。用户显式说"记住 XX"的优先级最高，直接写入。

**第四步，检索策略。** 向量检索负责语义相似，关键词检索兜底精确匹配（时区、ID、文件路径这类东西向量经常丢）。结果按 scope 过滤、按 `updated_at` 加权，取 top-k 注入 system prompt。

**第五步，MCP 化。** 把 `memory_write` / `memory_search` / `memory_delete` 做成 MCP 工具，再在 system prompt 里加一句"涉及用户既有偏好时先检索记忆库"，agent 就有了稳定统一的读写入口。

## 踩坑点

- **每轮抽取**：token 成本直接翻倍，边聊边改库还容易写脏数据。务必批量、延后抽取。
- **纯向量检索**：问"我时区哪年设置的"，向量召回一堆时区讨论，就是没有那条事实。混合检索不是可选项。
- **记忆黑箱**：用户不知道 agent 记了什么，错了也没法删。至少提供一个 `/memory` 查看命令，能看能删。
- **沉默失效**：偏好不会自己过期。简单做法是覆盖时保留新旧两个字段，检索时新记录压旧记录。

## 可复用建议

- 从显式记忆做起：用户主动要求"记住 XX"的先支持好，隐式抽取后加——它容易做砸，也难评估。
- 宁少勿滥：单日写入条数设上限，写入前先问一句"半年后这条还有用吗"。
- 可导出、可删除是底线，别把用户记忆锁死在自己的库里。
- 准备一个 10 条偏好的回归测试集，每次改抽取或检索逻辑就跑一遍，比肉眼比对靠谱。

## 总结

记忆系统不是"存得越多越好"，而是一条"抽取 → 结构化 → 混合检索 → 可管理"的流水线。先用 MCP 把读写口标准化，再逐步打磨策略，比一上来就堆向量库踏实得多。真正的好记忆是安静的：用户不说，它从不多话；用户需要时，它一定在。
