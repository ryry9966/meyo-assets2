## 背景

过去几个月，我们把不少自动化流程从“一次性 prompt”迁到了 OpenClaw 的 Skills 机制上。动机很直接：上下文预算。早期做法是把操作手册、内部 API 约定、部署流程全塞进 system prompt，结果会话还没干活，光指令就吃掉大半窗口，模型对无关内容的注意力也被稀释。

Skills 的核心思路是渐进式披露（progressive disclosure）：每个技能是一个目录，含一份 SKILL.md 加可选的脚本和参考资料。会话启动时只注入技能的名称和描述这两行元数据；任务匹配时才加载完整正文；正文引用的文件，只在需要时才读取或执行。三层结构，越靠近常驻层越便宜。

## 问题

具体痛点有三个：

1. **上下文膨胀**：全量指令常驻，token 成本高，信噪比低。
2. **触发不可控**：靠用户手动“召唤”某个流程，容易忘、容易错。
3. **经验难沉淀**：同事的流程知识散落在文档和聊天记录里，agent 用不上。

## 做法

一个最小可用的技能目录长这样：

```
skills/deploy-check/
├── SKILL.md
├── scripts/preflight.sh
└── references/runbook.md
```

1. **写好 frontmatter 的 name 和 description**。description 是关键——它是模型常驻可见的唯一线索，要写成“做什么 + 何时用”，例如“发布前检查：当用户提到上线、发版、部署验证时使用”。
2. **正文控制在五百词以内**，只放工作流、判断分支和文件指引，别写成百科。
3. **确定性逻辑下沉到 scripts/**，让 agent 用 bash 执行脚本拿结论，而不是把长文档读进上下文。preflight.sh 跑完直接返回“通过/失败 + 原因”，比让模型逐行理解 runbook 省一个数量级的 token。
4. **验证触发**：构造一个应触发的任务和一个不该触发的任务，各跑一遍，看日志里技能是否按预期加载。

## 踩坑点

- **description 写得太泛**（比如“帮助你完成各种任务”），结果是永远不触发，或者乱触发。按“动词 + 场景”来写。
- **把细节全堆进 SKILL.md**，渐进式披露名存实亡。正文超了就拆到 references/，让模型按需再读。
- **脚本写死绝对路径和内网地址**，换个环境就断。用相对路径和环境变量。
- **技能职责重叠会导致选错**。我们遇到过“部署检查”和“发布回滚”互相抢触发，最后按生命周期阶段拆开、在名字里写清边界才解决。
- **别在技能里放凭证**，技能内容会被注入上下文，等于明文暴露。

## 可复用建议

- 把 description 当成技能的 API 来维护，这里花的功夫占一半以上收益。
- 一个技能只解决一类任务，宁可多建，不做大杂烩。
- 信息组织优先级：跑脚本拿结果 > 读短文档 > 读长文档。
- 维护一份团队技能清单，定期审一遍重叠项和失效项；技能改了要记得新会话才生效。

## 总结

Skills 没有什么黑魔法，本质是“索引常驻、正文按需、执行外置”的上下文工程。它和 MCP 是互补关系：MCP 提供能力接口，Skills 教 agent 何时、如何组合使用这些能力。把团队重复性流程沉淀成技能，是我们目前性价比最高的 agent 工程实践，建议从一个最痛的流程开始试。
