## 背景

给 agent 接多了 MCP server 之后，一个老问题会重新出现：启动时全量挂载几十个工具定义，系统提示轻松破万 token。后果不只是贵——模型面对长工具列表时选择准确率明显下降，调错工具、漏传参数的情况变多。Skills 机制解的就是这个问题，核心思路是**渐进式披露**：平时上下文里只保留一张"能力目录"，真正命中需求时，才把完整说明、脚本和参考资料加载进来。

## 问题

我自己的场景：一个内部自动化助手同时接了文档检索、代码仓操作、CI 流水线三组 MCP 工具，30 多个工具定义常驻上下文。典型故障是让它"查一下最近一次发布的变更"时，模型调了代码检索工具而不是发布记录接口，只能在系统提示里反复打补丁。工具越多，补丁越多，进入负循环。

## 做法

Skills 的加载是三层递进的：

1. **目录层**。每个 skill 一个目录，入口是 SKILL.md。agent 常驻上下文里只有每个 skill 的 name 和 description，各占一行。
2. **入口层**。命中后加载 SKILL.md 正文：操作步骤、注意事项、脚本调用方式，控制在一两百行内。
3. **资源层**。SKILL.md 引用的脚本和长文档放 `references/`，执行到对应步骤再读。

```
skills/
  release-check/
    SKILL.md               # 描述 + 步骤入口
    scripts/precheck.sh
    references/runbook.md
```

description 是关键，建议用"何时使用"句式，把触发词写具体。Skills 与 MCP 不是替代关系：工具定义仍由 MCP 提供，skill 承担的是"使用说明书"——什么场景用哪个工具、前置检查做什么、失败怎么兜底。改完后用一组固定测试句跑回归，验证"应触发"和"不应触发"都符合预期。

## 踩坑点

- **description 写得模糊**。"处理部署相关问题"基本等于没写，模型要么不触发要么乱触发。改成"用户要求发布/回滚服务，或流水线失败需要定位原因时使用"，命中率立刻不一样。
- **单个 skill 体积失控**。SKILL.md 超过两三百行就该拆，长 runbook 挪进 references，入口文件只留主干。
- **职责重叠**。两个 skill 都覆盖"日志排查"，选择就近乎随机。边界不清时，在各自 description 里显式互斥。
- **脚本依赖不声明**。skill 里调用的脚本要写清运行环境：解释器版本、必需环境变量、工作目录。换个机器跑不起来是最常见的翻车点。
- **更新不生效**。改了 skill 但 agent 还在用旧目录索引，先确认重载机制，再排查别的。

## 可复用建议

- **粒度对齐用户意图**：一个 skill 对应一类任务，而不是一个系统。按系统拆会造出大量永远不被选中的 skill。
- **能脚本化的别写成散文**：让模型背步骤，不如给它一个可执行脚本，确定性完全不同。
- **维护触发回归集**：10～20 条典型请求，覆盖应触发与不应触发两类，每次改 description 后跑一遍。
- **把 skills 目录当文档用**：新人扫一眼目录结构，就知道这个助手实际"会什么"，比任何 README 都准。

## 总结

Skills 的价值不在于多加了一层抽象，而在于重新分配上下文预算：把"知道有哪些能力"的成本压到每项一行，把"怎么把事做对"的细节延迟到命中之后再加载。实践下来，工具选择准确率和单次会话成本都有可感知的改善。如果你也在被膨胀的工具列表折磨，建议从拆一个最高频的流程开始，先让它稳定触发，再逐步铺开。
