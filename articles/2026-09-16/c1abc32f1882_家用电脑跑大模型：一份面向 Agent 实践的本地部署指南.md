## 背景

过去半年，我把 agent 的日常推理逐步从云端 API 迁到了家里的台式机。动机很实际：自动化任务 7×24 跑，token 费用积少成多；而且很多任务涉及本地文件、剪贴板、家庭照片库，走云端总归不放心。对 OpenClaw 这类靠 MCP 插件串联本地能力的玩法来说，"模型在本地、工具在本地"的闭环其实更自然。

## 问题

本地部署的难点不是"跑起来"，而是跑得**可用**：

- 显存/内存有限，模型选型稍大就爆；
- agent 高度依赖工具调用，而小参数量模型在 function calling 上表现参差；
- 上下文一长，显存占用远超"模型权重多大就占多少"的直觉预估。

## 做法

我的环境：RTX 3060 12GB + 32GB 内存，供参考。

1. **选运行时**。命令行党直接 Ollama 或 llama.cpp；两者都提供 OpenAI 兼容接口，方便接 agent 框架。有 N 卡且追求吞吐可以考虑 vLLM。
2. **选模型与量化**。Q4_K_M 量化起步，中文场景优先 Qwen 系列的 7B/14B 级别，工具调用支持相对扎实。7B-Q4 大约占 5GB 显存，14B 就得考虑部分层 offload 到内存。
3. **暴露 OpenAI 兼容端点**。Ollama 默认 11434，llama.cpp 起 server 后同样是 /v1/chat/completions 风格。OpenClaw 侧只需改 base_url 和 model 名。
4. **接进 agent 链路**。MCP server 全部跑本机，模型端点指向 localhost；先砍掉冗长的 system prompt，用小上下文验证工具调用是否稳定。
5. **压测**。用自己真实的 agent 任务测 tokens/s 和工具调用成功率，而不是看跑分榜。

## 踩坑点

- **上下文吃显存比想象狠**：8K 上下文时 KV cache 能再吃掉 1-2GB，"刚好塞下"的模型一开长对话就 OOM。预留 20-30% 余量。
- **工具调用格式差异**：不同运行时对 function calling 的解析实现不同，换运行时后务必重测；小模型还容易编造参数名，建议在插件侧做严格 schema 校验并兜底。
- **笔记本别乐观**：散热撑不住持续推理，温度一高频率掉一半，批量任务反而不如小模型稳定。
- **流式超时**：本地首 token 延迟偏高，部分 agent 框架对慢流式响应有默认超时，需要显式调大。
- **Embedding 是另一回事**：RAG 场景单独跑一个小 embedding 模型，别指望主模型兼任。

## 可复用建议

- **分层用模型**：7B 快速档做路由、分类、简单工具调用；14B 慢速档做复杂推理。agent 里按任务难度分发，吞吐和质量的平衡最好。
- **配置代码化**：模型名、量化版本、端点写进 repo，一键拉起，换机器可复现。
- **加健康检查与降级**：给本地端点做探活，模型挂了自动切回云端 API，保住自动化任务的可用性。

## 总结

本地 LLM 不是替代云端，而是给 agent 体系补一块"可控、免费、离线"的推理层。量力选型、实测工具调用、留足显存余量，家用电脑完全能承担日常自动化任务的推理负载。先把 7B 跑通，再谈 14B 和长上下文——别一上来就追最大的模型。
