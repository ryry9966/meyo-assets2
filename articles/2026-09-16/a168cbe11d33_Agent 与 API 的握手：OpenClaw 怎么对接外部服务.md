## 背景

Agent 的价值在"能动手"。模型再强，接不上外部服务就只是一个会聊天的盒子。在 OpenClaw 里对接外部服务主要有三条路：直接写工具函数包一层 API、接现成的 MCP Server 做标准化接入、或者做成社区插件。这篇帖子过一遍我们最近对接几个典型 REST 服务时的做法，给后来的人省点时间。

## 问题

直接把 API 塞给 Agent，通常会撞到四件事：

1. **认证**：密钥放哪、token 过期谁来刷新，不能指望模型自己处理；
2. **返回值**：真实 API 一口气回几十 KB 的 JSON，全量进上下文，几轮对话就撑爆；
3. **错误语义**：HTTP 429/5xx 对模型没意义，它不知道该等、该重试还是该放弃；
4. **副作用**：POST 类操作被模型"顺手"重试，重复建单、重复下单。

## 做法

以对接一个工单类 REST API 为例：

**第一步，圈定工具边界。** 不要按 API 文档一比一映射出几十个工具。按用户意图归并，通常 3~5 个就够：查单、建单、改状态、加备注。工具越多，模型选错的概率越高。

**第二步，写清楚工具描述。** 参数说明里写明格式（日期是 ISO8601 还是时间戳）、单位、必填与可选。这一步花的时间比写代码多，但回报最高——调用准确率基本取决于描述质量。

**第三步，认证收敛到一个 client。** 密钥从环境变量或密钥管理服务读取，不落盘、不进日志；token 过期在 client 内自动刷新，对上层工具透明。

**第四步，做返回值裁剪和错误翻译。** 成功时只返回模型需要的字段；失败时把 HTTP 错误映射成结构化提示，比如"rate_limited，建议 30 秒后重试"或"invalid_param：priority 取值应为 low/medium/high"。模型拿到这种信息才能自我修正。

**第五步，超时、重试、幂等。** 所有请求带超时；GET 幂等可自动重试，写操作必须由工具层显式决策，并带幂等键。OpenClaw 的工具注册处可以统一挂中间件，别在单个工具里散着写。

如果目标服务已有官方或社区维护的 MCP Server，优先接 MCP——schema、鉴权、错误形态都是别人踩过坑的版本，你只需要管好配置和密钥注入。

## 踩坑点

- **裸 JSON 直接返回**：上下文膨胀极快，几轮后模型开始"忘事"。裁剪到必要字段，大结果落文件、只给路径。
- **描述里写模糊话**："id 是工单的 id"是废话。要写"是 ORD- 前缀的外部单号，不是系统自增 id"。
- **长任务同步等待**：超过 30 秒的调用改成异步加轮询，别让会话干等。
- **日志打印请求头**：调试时顺手把 headers 打进日志，密钥就泄了。日志落盘前先脱敏。
- **工具粒度太细**：按端点映射出的十几个工具，模型经常把查询和更新的参数混着填。

## 可复用建议

- 一个服务域一个 MCP Server / 插件，别做成大杂烩；
- 错误返回统一结构：`{status, retryable, hint}` 三件套；
- 写操作上线前先加 dry-run 参数，跑通再放开；
- 每次工具调用记录工具名、参数摘要、耗时、结果状态，排障全靠它。

## 总结

对接外部服务的本质不是"能调通"，而是把 API 的工程约束翻译成 Agent 能理解、能自纠的接口。工具定义写得像给人看的说明书，返回值裁剪得像给模型看的摘要，错误翻译得像给同事留的备注——这三件事做到位，OpenClaw 里对接新服务的边际成本会越来越低。欢迎在评论区贴你踩过的坑。
