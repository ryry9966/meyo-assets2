## 背景

Agent 的价值不在于能说，而在于能做。一个只有模型没有工具的 OpenClaw 实例，本质上是个聊天窗口；一旦接上数据库、工单系统、消息通道，它才真正成为自动化链路的一环。但"接上"这件事比看上去琐碎：每个外部服务的鉴权方式、返回格式、限流策略都不一样，如果不加约束地逐个硬写，一个月后你会收获一堆无法维护的胶水代码。

## 问题

社区里反复出现三类翻车：

1. **工具定义随缘**。函数名随便起，描述一句话带过，模型在多个相似工具之间反复选错。
2. **返回值直灌上下文**。一个接口返回 50KB 的 JSON 原样塞给模型，两三轮对话后 token 就爆了。
3. **凭证管理裸奔**。API key 写进配置文件提交到 Git，或者出现在工具调用的调试日志里。

根源是同一个：没有把"Agent 与 API 的握手"当成一个协议来设计。

## 做法

建议把对接拆成四步，每步都有明确产出物。

**第一步：选对接层。** 优先用 MCP Server，尤其目标服务已有现成 MCP 实现时——它顺便解决了发现、schema 和进程隔离。没有现成的，再写 OpenClaw 原生插件。把裸 HTTP 请求直接包成工具是最后手段，只适合一两个简单的只读接口。

**第二步：定义握手契约。** 每个工具三个要素必须写清楚：

```yaml
tool: search_orders
description: 按时间范围和状态查询订单，返回摘要列表（非明细）
params:
  status: { type: string, enum: [pending, shipped, refunded] }
  since:  { type: string, description: ISO 日期 }
returns: 最多 20 条，仅含订单号 / 金额 / 状态
```

描述里写清"返回什么、不返回什么"，比堆形容词有用得多。

**第三步：收敛鉴权与错误。** 凭证统一走环境变量或 secret 存储，工具内部读取。所有外部调用强制 timeout（10 秒起步），对 429/5xx 做指数退避重试，上限 3 次。失败时返回结构化错误而不是抛异常——模型需要可读的错误信息来决定下一步是重试、换参数还是放弃。

**第四步：控制返回体积。** 在工具层做裁剪：只挑必要字段、列表截断并暴露分页参数、大文本给摘要。工具是 Agent 的感官，感官不需要把整个世界塞进大脑。

## 踩坑点

- **写操作没有幂等保护**。网络重试导致重复下单是真实发生过的。凡写操作，要么带幂等键，要么默认 dry-run、由人确认后执行。
- **工具数量膨胀**。挂载超过 15 个工具后，模型选错率明显上升。按场景拆 profile，一个会话只挂当前需要的子集。
- **日志泄密**。调试时把完整请求打进日志，key 跟着进去了。在日志层统一做脱敏，改一次就够。
- **忽略 schema 漂移**。外部 API 改字段名不会通知你。给关键工具写 fixture 测试，放进 CI 定期跑。

## 可复用建议

1. 一个工具只做一件事，组合逻辑留给 Agent 或上层编排。
2. 错误信息是写给模型看的，不是写给人看的——说清"哪里错了、可以怎么改"。
3. 工具命名带命名空间前缀（如 `github_create_issue`），降低跨服务歧义。
4. 新工具先挂 shadow 模式跑一周，只记录不执行，观察参数分布再放开。

## 总结

对接外部服务不是"能调通就行"，而是一次小型协议设计：契约清晰、边界明确、失败可预期。OpenClaw 提供了挂载点，但握手质量取决于你对工具定义、鉴权和返回体积的克制程度。把上面四步固化成团队模板，之后每接一个新服务，边际成本都会显著下降。
