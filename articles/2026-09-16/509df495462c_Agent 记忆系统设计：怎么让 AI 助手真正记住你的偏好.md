## 背景

LLM 本身无状态。OpenClaw 里跑的 agent 每次会话都是"失忆"的——你上周说过"项目用 pnpm 不用 npm"、"回复别用 emoji"，这周它照样忘。用户对 agent 的期待早已从"能答对"变成"越用越懂我"，中间差的不是模型能力，而是一套工程化的记忆系统。

## 问题：三种常见做法为什么不行

1. **全塞 system prompt**：token 成本线性膨胀，冲突记忆互相打架，改一条要动全局。
2. **对聊天记录做 RAG**：检索回来的是"聊过什么"，不是"用户偏好什么"，噪声大、召回不稳定。
3. **只存会话摘要**：细粒度偏好（代码风格、时区、称呼习惯）在摘要压缩时被抹掉。

核心矛盾：记忆的"写入"和"使用"是两个独立问题，混在一起做必然两头塌。

## 做法：结构化条目 + 读写分离

我的实现是一个 MCP memory server，暴露三个工具：`memory_search` / `memory_write` / `memory_delete`，分五步：

**1. 定义结构化 schema，不存裸文本：**

```json
{ "key": "code.package_manager", "value": "pnpm",
  "source": "explicit", "confidence": 0.9,
  "scope": "global", "updated_at": "..." }
```

`source` 区分"用户明说"和"模型推断"：明说的高置信，推断的默认降权待复核。

**2. 会话后异步抽取。** 会话结束跑一次抽取调用（temperature 0 + JSON schema 约束输出），只提取"可复用、跨会话有效"的条目，一次性任务细节不进长期记忆。

**3. 去重与冲突消解。** 写入前先查同 key 旧条目：值相同→跳过；值不同→比较 `updated_at` 和 `confidence`，新值覆盖，旧值留历史便于回滚。

**4. 检索注入。** 请求进来时按 scope 过滤 + embedding 相似度排序，取 top-k（我设 8 条），拼进 system prompt 并设 500 token 硬预算。记忆是"上下文乘客"，不能喧宾夺主。

**5. 反馈闭环。** 用户纠正 agent（"我说过别用 emoji"）时，agent 调 `memory_write` 更新该条目置信度，下次检索权重更高。用户可随时列出、编辑、删除记忆——这不是可选项，是信任底线。

## 踩坑点

- **过度抽取**：早期版本什么都存，两周后记忆库全是垃圾。后来加硬规则：抽取时判断"这条 30 天后还有用吗"，答不上来就不存。
- **偏好过期**：用户换了语言栈但没明说，旧记忆一直生效。解法：推断类条目加 TTL，过期降权而非删除。
- **上下文错配**：A 项目的记忆被注入 B 项目会话，用户觉得"你怎么知道这个"。scope 必须在检索时强制过滤。
- **敏感信息入库**：抽取阶段做正则 + LLM 双重过滤，密钥、密码、证件号一律拦截。
- **抽取不稳定**：同一会话两次抽取结果不同。改结构化输出 + 低温度后基本稳定，但务必对写入记 diff 日志，出问题能定位是哪次抽取写坏的。

## 可复用建议

- 用 SQLite 起步，单表 + 一列 embedding 足够，别一上来搭"记忆框架"。
- 每次 `memory_search` 和 `memory_write` 都记日志，90% 的"它怎么记错了"靠日志五分钟定位。
- 写入必须是显式工具调用，不要让模型隐式改记忆。
- 攒一个 20 条左右的小评测集（"agent 是否应用了该偏好"），每次改检索策略跑一遍，比感觉靠谱。

## 总结

记忆系统本质是"抽取 → 存储 → 检索 → 反馈"的闭环工程问题，不是一段 prompt 能解决的。先把 schema 定小、把写入做成显式动作、把删除权交给用户——这三件事做对，agent 的"懂你"才可持续。
