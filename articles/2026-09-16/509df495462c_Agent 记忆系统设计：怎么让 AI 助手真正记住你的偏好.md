## 背景

大模型的上下文是无状态的。今天告诉助手“我偏好 pnpm、部署走灰度、回复用中文”，明天新会话它照样一问三不知。上下文窗口再大也不等于记忆——它是工作台，不是档案柜。对用 OpenClaw 搭 Agent、接 MCP 工具的人来说，让助手跨会话记住偏好，是体验上收益最大的一块基建。

## 问题

常见三种做法都不太行：

1. **全塞 system prompt**：偏好和一次性信息混在一起，token 成本线性上涨，还会互相污染；
2. **重放历史会话**：噪声远大于信号，召回回来的大多是废话；
3. **微调**：迭代慢、成本高，偏好变了没法即时生效。

真正的难点不是“存”，而是四个决策：**记什么、怎么存、何时取、如何更新与遗忘**。

## 做法

我在自己的 OpenClaw 实例里跑了一版极简记忆层，核心四步：

1. **分层定义**。只存两类：偏好（稳定项，如代码风格、语言、时区）和事件笔记（项目决策、环境细节）。闲聊不进库。
2. **结构化抽取**。会话结束后跑一次抽取 pass，用 JSON schema 约束输出：内容、类型、置信度、来源时间。置信度低于阈值直接丢弃——用户随口一句不算偏好。
3. **存储与检索**。SQLite 存原文 + 向量做语义召回就够用。封装成 MCP 工具：`memory_write` / `memory_search`，让 Agent 自己决定何时写入、按需检索。
4. **注入与更新**。新会话启动时按相关性取 top-k，硬性限制在 500 token 预算内注入；同 key 冲突时新条目覆盖旧条目，保留时间戳可回溯。同时给用户一个可见、可删的记忆列表。

## 踩坑点

- **什么都记等于什么都不记**。没有置信度过滤，一句“今天有点累”也会进库，检索质量迅速劣化。
- **召回不设上限**。top-50 全注进去，信号被稀释，模型反而开始瞎联想。
- **只追加不覆盖**。“偏好 tabs”和后来的“偏好 spaces”同时存在，行为就随机了。冲突必须走更新而非追加。
- **记忆没有来源**。不记“这条偏好来自哪次会话”，出问题无法排查，用户也无法确认。
- **没做评测**。建议先攒 20 条“偏好回忆”测试问答，改一版跑一次，否则调优全靠感觉。

## 可复用建议

- 先做显式记忆（“记住：我用 pnpm”），再上自动抽取，稳定性完全不同；
- schema 先行，写路径和读路径分开演进，互不阻塞；
- 记忆永远是数据、不是指令，注入时带上来源标注，降低被当成系统指令的权重；
- 全部本地存储，把查看/删除入口留给用户，这是信任底线。

## 总结

记忆系统的本质不是“更大的上下文”，而是一条带过滤、带版本、可审计的偏好流水线。先解决记什么和怎么删，再优化怎么取。大约半个周末的工作量，换来的是助手不再每次都问“你的部署流程是什么”——这个投入很值。
