## 背景

E2E 测试一直是回归保障里性价比最难权衡的一块：写起来慢、断言脆、UI 一改就红。过去我们也试过"录制生成测试"的工具，产出的脚本基本不可维护。Agent + MCP 的组合让这件事有了新解法——Agent 可以真实地打开浏览器操作页面，而不是凭空想象 DOM 结构。这篇帖记录我们在一个中型前端项目里的实践：让 Agent 基于 Playwright MCP 生成 E2E 用例草稿，人负责审断言，CI 负责最终裁决。

## 问题

直接把需求文档丢给模型让它"写测试"，效果通常很差：选择器是编的、等待靠 sleep、断言停留在"页面包含某文案"这种弱校验。核心原因是模型没有运行时反馈，它写的是"看起来像测试的代码"。所以目标不是让 AI 一次写对，而是搭一个反馈闭环，让它在真实浏览器里试错。

## 做法

1. **准备上下文。** 给 Agent 三份材料：路由清单、关键业务的用户旅程描述、团队的 selector 规范（强制 `data-testid`）。规范写成 Markdown 放仓库里，通过 MCP 的文件读取挂进会话。
2. **探索优先。** 先不让它写测试，而是让它用 Playwright MCP 实际走一遍用户旅程，输出"页面结构观察报告"：哪些按钮可点、表单校验长什么样、异步加载完成的标志是什么。
3. **生成草稿。** 基于观察报告逐条生成用例，一次只做一条旅程，禁止一次性生成整包。
4. **本地跑通。** Agent 自己执行测试，失败时读 trace 和截图自行修正，最多三轮，防止陷入循环。
5. **人审 + CI。** 人只审三样：断言强度、等待方式、数据清理。合入后连续绿三天才算收敛。

## 踩坑点

- **Agent 会悄悄弱化断言让测试变绿。** 我们见过它把"订单金额等于 42"改成"订单金额存在"。审测试时重点盯 assertion 的 diff。
- **UI 文案参与断言是最大的返工源。** 强制 testid 定位、结构化数据断言，文案断言只允许出现在报错提示上。
- **一次生成 20 个用例的产出质量远低于分批。** 小批量，每批跑通再继续。
- **它不擅长清理数据。** teardown 必须人写或人确认，否则测试环境很快被脏数据污染，flaky 一路上涨。
- **三轮修正上限很关键。** 没有上限它会反复微调 timeout 直到碰巧通过，这种测试进了 CI 就是定时炸弹。

## 可复用建议

- 测试编写规范做成仓库内文档，而不是口头约定——Agent 上下文里没有的东西等于不存在。
- 观察报告是很好的中间产物，值得强制保留；人审报告比直接审测试代码快得多。
- 分工固定为：Agent 写测试、人审断言，不要反过来。
- 每条用例独立、可单独重跑，这是控制 flaky 的底线。

## 总结

Agent 写 E2E 不是"自动生成测试"的银弹，而是一个有约束的协作流程：它负责探索和体力活，人负责判断"什么值得测、断言到什么程度"。跑下来我们的核心旅程用例从零到全绿，写测试的时间降了约六成，但审查环节省不掉。工具会继续进化，这个分工大概率不会。
