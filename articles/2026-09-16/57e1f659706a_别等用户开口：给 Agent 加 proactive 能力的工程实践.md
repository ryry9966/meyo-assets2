## 背景

大多数 agent 的交互模型是"你问我答"——用户发消息，agent 响应。但真正省时间的是另一类场景：任务在合适的时机自己发生。比如每天早上把昨夜的 CI 失败、日历冲突、待合并 PR 汇总成一条简报；或者只在磁盘水位超过阈值时才提醒你。这就是 proactive 能力：由触发器驱动，而不是由对话驱动。

## 问题

直接给 agent 加个定时器，会撞上三类问题：

1. **噪音**：什么都汇报，三天后用户开始忽略它，主动能力形同虚设。
2. **上下文腐化**：触发时刻的系统状态和用户上次对话可能差很远，agent 拿旧记忆办事。
3. **风险失控**：主动执行写操作（发消息、改文件、调外部 API），触发条件一旦写错，就是无人值守的事故。

## 做法

我在 OpenClaw 里跑了一个分层结构，核心是"触发、评估、行动、反馈"四段：

**1. 触发层。** 只用三种来源：cron 定时、webhook 事件、状态轮询（带最小间隔）。每个触发器独立开关，写在一份 YAML 配置里。例如每天 08:45 的"晨间简报"触发器，挂载 calendar、github、ci 三个 MCP 工具。

**2. 评估层。** 触发后不直接执行，先跑一次"值不值得打扰"的判断：收集事实 → 按预设规则打分 → 低于阈值的进摘要池，攒着合并成一条 digest；超阈值或高危事件才即时推送。这一步把噪音砍掉了大头。

**3. 行动层。** 按风险分级：只读操作直接执行；写操作和外部副作用强制走确认队列——agent 把"我打算做什么"写成一条待确认消息，用户回复后才放行。所有动作走同一个网关记录日志，方便回溯。

**4. 反馈层。** 用户对推送的忽略 / 已读 / 确认都记入触发器台账，每周统计一次，把长期没人看的触发器自动降频或关闭。

## 踩坑点

- **自触发循环**：agent 发出的消息又触发了自己的 webhook，半小时刷了几百次。解决：给每个动作打来源标记，来源是自己的一律丢弃。
- **时区**：cron 用了容器默认的 UTC，简报凌晨送达。现在触发器配置里显式声明时区。
- **轮询成本**：1 分钟一次的状态轮询，一天烧掉的 token 比 20 次对话还多。改成事件驱动 + 5 分钟兜底轮询。
- **幂等**：确认队列重试导致同一动作执行了两次。现在每个待执行动作带唯一 ID，网关侧去重。

## 可复用建议

1. 第一个 proactive 任务一定做成只读的，跑两周看噪音率，再考虑加写能力。
2. 宁可合并延迟，也不要即时轰炸：digest 是主动能力的保底形态。
3. 触发器台账比触发器本身重要——没有数据，你不知道该砍掉哪一个。
4. 每个触发器独立可开关、可降频，不要只做全局开关。

## 总结

Proactive 不是让 agent 变得更聪明，而是把"何时行动"从对话里拆出来，变成一个可配置、可观测、可回滚的工程问题。触发器负责时机，评估层负责克制，风险分级负责安全。把这三件事做扎实，主动推送才会从骚扰变成真正的杠杆。
