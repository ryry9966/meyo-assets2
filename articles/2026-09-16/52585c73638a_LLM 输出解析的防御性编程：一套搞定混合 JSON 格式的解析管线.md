## 背景

在 OpenClaw 插件和 MCP 工具开发里，让模型按约定输出 JSON 是高频需求：Agent 编排要读结构化决策，自动化流水线要拿字段做后续调用。提示词里写清"只输出 JSON"之后，多数时候确实能拿到可解析的结果——但"多数时候"在自动化场景里不够用。跑一百次的任务失败五次，就是五次人工排障。

## 问题：模型并不总是守约

实际采到的输出至少有这么几种形态：

1. 纯 JSON，理想情况；
2. 包在 ` ```json ... ``` ` 围栏代码块里；
3. 前后带说明文字，JSON 夹在中间；
4. 用 `<json>...</json>` 之类的自造标签包裹；
5. 带尾逗号、全角引号，或字符串值里还嵌着围栏符号。

如果解析器只按理想情况写 `json.loads(raw)`，上面所有变体都会变成线上故障。

## 做法：分层解析管线

不要指望单条正则解决所有情况，按"成本从低到高"依次尝试：

**第一步：直接解析。** `raw.strip()` 后 `loads`，覆盖理想情况，开销最小。

**第二步：按标记提取。** 依次匹配围栏块和自造标签，把候选片段逐个尝试解析。围栏正则必须非贪婪；由于嵌套围栏会把内容截断，标签格式的候选优先级可以放更高。

**第三步：平衡扫描兜底。** 全文找第一个 `{` 或 `[`，用"字符串感知"的括号配对扫描截取完整结构再解析，这是最稳的一层。

**第四步：轻度修复。** 仍失败时去尾逗号、替换全角引号再试。修不好就抛错，不要硬造结果。

```python
import json, re

FENCE = re.compile(r"```(?:json)?\s*(.*?)```", re.DOTALL)
TAG = re.compile(r"<(?:json|answer|result)>(.*?)</(?:json|answer|result)>",
                 re.DOTALL | re.IGNORECASE)

def balanced_seg(text: str, i: int) -> str | None:
    """从 text[i] 的 { 或 [ 出发，字符串感知地截取配对片段。"""
    o, c = text[i], {"{": "}", "[": "]"}[text[i]]
    depth, in_str, esc = 0, False, False
    for j in range(i, len(text)):
        ch = text[j]
        if in_str:
            if esc: esc = False
            elif ch == "\\": esc = True
            elif ch == '"': in_str = False
        elif ch == '"': in_str = True
        elif ch == o: depth += 1
        elif ch == c:
            depth -= 1
            if depth == 0: return text[i:j + 1]
    return None

def extract_json(raw: str):
    cands = [raw.strip()]
    cands += TAG.findall(raw) + [m.strip() for m in FENCE.findall(raw)]
    for s in cands:
        try: return json.loads(s)
        except json.JSONDecodeError: pass
    for i, ch in enumerate(raw):
        if ch in "{[":
            seg = balanced_seg(raw, i)
            if seg:
                seg = re.sub(r",\s*([}\]])", r"\1", seg)  # 尾逗号修复
                try: return json.loads(seg)
                except json.JSONDecodeError: continue
    raise ValueError("no parsable JSON")
```

解析成功后过一层 pydantic / jsonschema 校验。**解析成功不等于语义正确**，字段缺失、类型漂移要在这层拦住。

## 踩坑点

- **贪婪正则跨块吞并。** `re.DOTALL` 下 `\{.*\}` 会把两个独立 JSON 块连同中间文字一起匹配，必须非贪婪或改用平衡扫描。
- **括号计数不感知字符串。** 值里出现 `"note": "use { carefully"` 会让朴素深度计数错乱，扫描器必须处理引号与转义状态。
- **别用 `ast.literal_eval` 兜底。** 它解析的是 Python 字面量，`true/false/null` 直接报错，语义也不等价于 JSON。
- **流式场景不要边收边 parse。** 半截 JSON 必然失败，等终止符或做增量解析。
- **MCP 工具参数的双重编码。** 有时 arguments 拿到的是"字符串化的 JSON"，需要 `isinstance(args, str)` 判断后二次 `loads`。
- **自纠重试要有上限。** 把报错信息和原始输出喂回去让模型修，最多两三次，失败就进错误状态，别让成本失控。

## 可复用建议

- 把 `extract_json` 收敛成一份公共实现放进插件脚手架，别每个工具各写一版，坏一处修一处。
- 沉淀"坏输出样本库"当 pytest fixtures，换模型版本就跑回归。
- 记录解析失败时的原始输出、模型版本、prompt 指纹，线上问题基本靠这个定位。
- 优先级永远是：结构化输出 / 工具调用 > 标签格式 + 容错解析 > 裸文本约定。
- 结构化任务把 temperature 压低，能显著减少格式漂移。

## 总结

对 LLM 输出的解析，本质上是对一个"不守约的数据源"做容错。提示词约束负责降低出错率，分层解析负责兜住剩余变体，schema 校验负责最后的语义闸门。三层各管一段，自动化链路的可靠性就从"碰运气"变成了可度量的工程指标。
