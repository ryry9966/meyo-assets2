## 背景

我们早就习惯了给项目写上下文文件：CLAUDE.md、AGENTS.md、workspace rules，把架构约定和代码规范喂给 Agent。但有个更基础的问题经常被忽略——**Agent 不知道你是谁**。

每个新会话都要重新自我介绍：我主力语言是 Go 不是 Python，我在 UTC+8，这台机器上我没有 sudo 权限，回复请直接给结论、别铺垫。这些信息高度稳定，却在每轮对话里重复消耗。

## 问题

项目上下文回答的是“这个代码库怎么干活”，用户上下文回答的是“给谁干活”。缺了后者，典型症状包括：

- 换设备、开新会话，就得重复交代一遍偏好；
- Agent 做出错误默认假设：包管理器猜错、部署目标猜错、时区算错；
- 同一个人在不同环境里，Agent 行为不一致；
- 团队里每个成员都在为同样的沟通成本买单。

解法很朴素：一份 `USER.md`，让 Agent 在会话启动时读取。

## 做法

**位置与加载**

- 全局：`~/.openclaw/USER.md`，跟随 dotfiles 同步；
- 项目级：repo 根目录放一份 `USER.md`，覆盖全局偏好；
- 加载方式：会话启动时注入系统提示，或者封装成 MCP resource 按需暴露。后者更省 token，适合内容偏长的场景。

**模板：六段结构，控制在 100 行以内**

1. **身份与角色**：职位、主力技术栈、职责边界；
2. **运行环境**：OS、shell、包管理器、时区、网络限制；
3. **沟通偏好**：语言、详略程度、代码注释语言；
4. **硬约束**：明确不许做的事，比如“不要自动 push"、"不要动 git stash"；
5. **常用工作流**：测试命令、部署习惯、看日志的方式；
6. **当前焦点**：本周在做什么。这段最容易过时，放最后。

**维护节奏**

- 用 git 管理，纳入 dotfiles 仓库；
- 每月让 Agent 自己审计一次：“对比最近会话，指出 USER.md 里过时或缺失的条目”。Agent 是最好的维护者。

## 踩坑点

1. **别写密钥和内网地址**。USER.md 会进模型上下文，贴日志、发截图时也可能带出去。保持“事实可公开”这条底线。
2. **控制篇幅**。超过 1k token 就变成第二个系统提示，会和项目规范打架。通用事实放全局，项目特例放项目文件。
3. **优先级要显式声明**。写明“项目级规范优先于本文档”，否则你的全局格式偏好会污染协作项目。
4. **事实和指令分开**。混写会导致 Agent 有时复述、有时执行。用小节标题区分“我是谁”和“你要怎么做”。
5. **它会过时**。换机器、换栈之后，错误的旧信息比没有信息更糟。审计习惯比模板本身更重要。

## 可复用建议

- 把 USER.md 当**稳定事实层**，和 Agent 的滚动 memory 分层：身份与环境写死，任务状态交给 memory；
- 会话初始化脚本里加一行校验：文件不存在就提示创建，避免静默降级；
- 团队可以共享一份脱敏模板，新人 clone 后改三行就能用；
- 写给 Agent 的过程，其实也是给自己整理工作习惯的过程，别浪费这次梳理。

## 总结

USER.md 不是什么新协议，就是一份被 Agent 持续读取的 Markdown。它的价值不在格式，而在于把“每次重新解释自己”的成本压缩到一次。检验标准也很简单：新会话的第一轮对话，Agent 的默认假设就基本正确——做到这一点，这份文件就值了。
