## 背景

RSS 没死，只是被塞进了角落。对我这种要跟踪几十个博客、GitHub Release、项目公告页的人来说，它仍是最可控的信息源：没有推荐算法、没有广告、格式统一。问题不在获取，在于读不过来。市面上托管式 AI 阅读器要么按订阅收费，要么是黑盒——摘要质量没法审计，数据也不在自己手里，更没法接进自己的 agent 工作流。

## 问题

我的痛点很具体：

- 订阅 60+ 源，每天新增 200+ 条，逐篇读不现实；
- 多数 RSS 只给摘要段，点进去才知道有没有干货；
- 同一事件常被 3-4 个源重复报道；
- 已有方案摘要不可控，无法定制格式与推送渠道。

目标是：每天早上收到一份推送，只含「值得看的 10-20 条 + 每条三句以内摘要」，全程本地可审计、可重跑。

## 做法

管线分四段，跑在 OpenClaw 的 cron 任务里，脚本加 MCP 工具组合：

1. **抓取**：解析 OPML 拿订阅列表，feedparser 拉全量条目，按 `guid/link` 哈希做一级去重，新条目原样落 SQLite（正文用 trafilatura 提取，失败就存 RSS 自带 summary）。
2. **粗筛**：不把所有条目丢给 LLM。先用规则过滤——关键词命中、来源权重、标题长度——把量从 200 压到 30-50。
3. **摘要**：批量调 LLM，prompt 强制结构化输出：`一句话结论 / 关键点 / 相关度评分`，并明确「仅基于给定原文，原文没有的信息不要写」。评分低于阈值直接丢弃。
4. **聚合推送**：按主题合并同一事件的多个来源为一条，生成日报，推到 Telegram。

## 踩坑点

- **摘要幻觉**：最初 prompt 没限定来源，模型会自行补充背景知识。加上「仅基于原文」后稳了很多，但仍需人工抽查。
- **去重不彻底**：标题相似度判重会漏掉改写过的转载，换 embedding 算余弦相似度（阈值 0.85 左右）才基本干净，代价是多一步向量计算。
- **正文抓取被反爬**：少数站对无 UA 的请求直接 403。带上正常 UA、控制 1 秒间隔，比上代理池省事得多。
- **任务不幂等**：第一次跑挂了一半，重跑把已推送的又推了一遍。后来把「已处理」「已推送」状态分开落库，重跑只补漏。
- **token 成本失控**：全量摘要一天烧掉不少。粗筛加评分丢弃后，成本降到原来的约三分之一；每次运行顺手记录 token 用量，超阈值告警。

## 可复用建议

- **先落库，再处理**。原始条目是资产，摘要只是视图，换模型可以随时重跑。
- **粗筛用规则，精读用模型**，把贵的调用留给值得的内容。
- **结构化输出优于自由文本**，后续接笔记、agent 工具等消费端都省事。
- **选源比算法重要**。管线再好，源低质量就是垃圾进垃圾出，定期审计订阅列表。
- 失败是常态：抓取、LLM 调用、推送都要有独立的重试与记录。

## 总结

这条管线跑了一个多月，每天早上五分钟扫完日报，终于在「信息不遗漏」和「不被淹没」之间拿到平衡。没有黑科技，就是把抓取、筛选、摘要、推送拆开，每一段可测、可重跑、可替换。如果你已经在用 OpenClaw 做 agent 自动化，加一个 RSS 源管理 skill 和一个摘要 workflow，一个下午能跑通第一版。真正的门槛不在代码，而在持续维护源列表与摘要质量的耐心。
