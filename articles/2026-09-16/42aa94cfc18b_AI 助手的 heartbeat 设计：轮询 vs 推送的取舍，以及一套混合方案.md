## 背景

OpenClaw 这类常驻 Agent 有个绕不开的问题：怎么让它"醒来"。定时提醒、MCP 资源变更、外部消息，都需要一个 heartbeat 机制把 Agent 从待机状态拉起来干活。常见两条路：**轮询**（定时唤醒，自己去看有没有事）和**推送**（外部事件主动唤醒）。两种我都跑过一段时间，这里把取舍和最终方案记录一下。

## 问题

纯轮询的代价很直接：间隔设长，事件延迟不可接受；间隔设短，token 成本和 API 调用量线性上涨。更隐蔽的是，很多实现里每次心跳都会加载完整上下文，成本被进一步放大。

纯推送看起来优雅，但工程上问题不少：需要一个可达的入口（webhook 或消息队列），本地跑的 Agent 还要面对 NAT 和内网穿透；事件丢失、重复、乱序全要自己兜底；而且推送失效时往往是静默的，排障比轮询难得多。

核心矛盾在于：**不同任务的时间敏感度不同，单一模式必然顾此失彼。**

## 做法

我的方案是"轮询打底 + 推送加速"，步骤如下：

1. **任务分类**：硬时限任务（定时提醒）、事件驱动任务（日历变更、消息到达）、可延后任务（巡检、摘要），三类分开对待。
2. **轻量心跳**：固定间隔（15–30 分钟）加随机抖动，心跳上下文只带压缩后的状态摘要，不加载全量历史。
3. **敏感事件走推送**：MCP server 或外部服务产生事件时写入队列并唤醒 Agent，事件负载里显式带上 `wake_reason` 和 `event_id`：

```json
{ "wake_reason": "event", "event_id": "a1b2", "source": "mcp:calendar", "deadline_hint": "5m" }
```

4. **合并层**：队列按 `event_id` 去重，短窗口内的多个事件合并成一次唤醒；推送通道失败时自动退回轮询兜底。
5. **埋点**：记录心跳次数、单次心跳 token 消耗、实际动作率（醒来后真的干了活的比例）。

## 踩坑

- **心跳加载全量上下文**是最大的坑，token 消耗直接爆炸。解法是心跳走独立会话或压缩状态。
- **定时器漂移**：笔记本休眠、容器被回收后，Agent 醒来时不能假设"上次心跳刚刚发生"，要先做 catch-up，补查错过的窗口。
- **Webhook 重试不幂等**，同一事件触发两次动作。`event_id` 加已处理集合是底线。
- **推送静默失败最危险**：没收到事件不等于没出事，必须保留一条哪怕很稀疏的兜底轮询。
- 本地环境收 webhook，签名校验和重放保护别省，内网穿透链路本身就不可靠。

## 可复用建议

- 判断标准一句话：**能容忍 N 分钟延迟的用轮询，不能的用推送。**
- 把 `wake_reason` 枚举化（scheduled / event / escalation / manual），Agent 醒来先判断"为什么醒"，再决定做什么，行为会稳定很多。
- 无动作的心跳也要记日志，沉默的心跳比报错更难查。
- 从纯轮询起步先跑通，再按延迟需求把任务逐个迁到推送，不要一上来就全量事件化。

## 总结

heartbeat 本质是个系统设计问题，不是加个定时器就完事。轮询买到的是简单和存活保证，推送到手的是及时和低成本。对大多数 Agent 来说，"轮询打底、推送加速"的混合结构，配上队列、幂等和指标，才能既省 token 又不漏事。
