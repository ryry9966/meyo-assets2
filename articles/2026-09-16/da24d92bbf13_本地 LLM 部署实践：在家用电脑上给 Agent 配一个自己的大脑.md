## 背景

做 Agent / MCP / 自动化实践的人，大概都绕不开两个现实问题：调试用的对话里带着私有数据，走云端 API 不放心；或者批量跑自动化任务，一个月 token 费用比电费还高。本地部署大模型不是新鲜事，但对写插件、接工具链的人来说，它的价值不只是"能跑"，而是提供一个**成本恒定、数据不出门、可以随便折腾**的推理环境。

## 问题

真正要解决的有三件事：

1. **硬件预算和模型规模的匹配。** 很多人高估了需求，更多人低估了显存——尤其是上下文拉长之后 KV cache 的开销。
2. **本地模型的工具调用质量参差不齐。** 跑分好看不等于能稳定走完一个 Agent 循环。
3. **服务栈选型混乱。** Ollama、llama.cpp、各种一键包，接口行为不一致，出问题很难定位。

## 做法

我的路径比较朴素：

**1. 先定硬件基线。** 8GB 显存跑 7B/8B 的 Q4 量化，12GB 跑 14B，24GB 跑 32B。纯 CPU 跑 7B 也可以，但每秒几个 token 的速度做 Agent 循环基本不可用。

**2. 固定服务栈。** 我最终在 Ollama（省心）和 llama.cpp 的 `llama-server`（参数可控）之间二选一。两者都提供 OpenAI 兼容接口，Agent 框架只需改 `base_url`：

```bash
# llama.cpp 示例
./llama-server -m qwen2.5-14b-instruct-q4_k_m.gguf \
  --n-gpu-layers 999 --ctx-size 8192 --port 8080
```

**3. 量化从 Q4_K_M 起步。** 效果明显不够再上 Q6/Q8。别一上来追满血精度，先让链路跑通。

**4. 接入 Agent/MCP 时控制工具数量。** 工具 schema 注入 system prompt 后，本地小模型的上下文压力陡增，建议工具控制在 10 个以内，描述写短写准。

**5. 建一个 20~30 条的私有工具调用测试集**，就用你真实的业务任务。每次换模型、换量化、换服务栈，跑一遍再决定。

## 踩坑点

- **上下文长度是隐形杀手。** MCP 工具 schema + 多轮对话很快吃满 4K 上下文，表现为 Agent 循环莫名中断。请显式把 `ctx-size` 拉到 8K 以上，同时注意 KV cache 也占显存。
- **优先用服务栈的原生 tool calling**，别靠 prompt 模拟 JSON——同一个 7B 模型在不同服务栈上的解析行为可能不同。
- **`max_tokens` 设太小**会导致工具参数 JSON 被截断，报错看起来像"模型不会调工具"，其实是被截断了。
- 笔记本 GPU 有散热墙，长时间 Agent 循环掉速是正常的，别误判成显存不足。

## 可复用建议

- 把 OpenAI 兼容接口当作唯一接入层，后端随便换，改一行配置的事。
- "快模型做粗活，强模型做决策"在本地同样成立：7B 做意图分类和格式化，14B 以上做工具编排。
- 不要信公共榜单，信你自己的测试集。
- RAG 场景给嵌入模型单独留一份小显存，别和主模型抢。

## 总结

本地部署的核心价值是把实验成本压到接近零。它不会在能力上取代云端旗舰模型，但对于工具调用验证、私有数据自动化、离线场景，一台 12GB 显存的机器加一个 Q4 量化的 14B 模型，已经够支撑大部分日常实践。先跑通链路再逐步加码，比一次到位更省钱，也更省心。
