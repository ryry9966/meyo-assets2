## 背景

OpenClaw 的 cron 任务本质是一个**定时唤醒的无人值守会话**：到点触发，agent 拿着你写的 instruction 独立跑一遍，跑完即结束。它和聊天场景最大的区别是——没有上下文、没有追问机会、结果默认没人看。

不少人的第一版定时任务就是把聊天 prompt 直接搬进去，跑两周后得出结论"定时任务不可靠"。实际多数情况下不可靠的不是调度，而是 instruction 没按"作业规范"来写。

## 问题：聊天式写法在 cron 里的四个典型翻车点

- **自言自语**：没指定交付渠道，结果留在一次性会话里，跑得再对也没人收到。
- **没定义静默条件**："有重要的告诉我"——什么算重要没说，agent 要么每天硬凑一条，要么永远沉默。
- **无状态**：不知道上次看过哪条，要么重复推送，要么漏推。
- **失败静默**：源站 404、凭据过期，任务表面"正常运行"，实际什么都没查到。

## 做法：把 instruction 当作业规范写

我现在的模板固定五段，按顺序填：

1. **目标与范围**：做什么、查哪些源、时间基准（时区、窗口期）。cron 是机器触发，别指望它理解"早上"。
2. **输出契约**：发到哪个渠道、什么格式、几条合并成一条。这是最常被省略、也最致命的一段。
3. **静默条件**：明确写出"什么情况下什么都不做"。没有这段，agent 会倾向于"来都来了，总得说点什么"。
4. **状态与幂等**：用本地文件记录上次进度（如已见 tag），运行结束写回；任务重试时靠它去重。
5. **失败处理**：报错如何呈现、连续失败是否只提醒一次，避免故障时被轰炸。

一个 release 监控的实例：

```text
目标：每天 09:00（Asia/Shanghai）检查 A、B 两个仓库过去 24h 的新 release。
状态：读取 release-watch.json 中的已见 tag，文件不存在则视为首次运行。
输出契约：仅当出现新 tag 时发一条消息，格式「仓库 版本 一句话变更」。
静默条件：无新 release 时不发送任何内容。
失败处理：单仓库请求失败在消息末尾附一行说明；同一仓库连续失败不重复提醒。
收尾：将最新 tag 写回 release-watch.json。
```

## 踩坑点

- instruction 里写"如前所述 / 上次说过"——cron 会话没有这些记忆，一切前提必须内联。
- 高频调度 + 长指令：每 5 分钟全量扫一遍，token 和限流都会教育你。先低频验证，再提频。
- 手动触发成功一次就上线：务必让静默分支也跑一遍，确认"无事发生"时真的无输出。
- 指令里硬编码 URL 和路径：源一变任务就废。我把数据源清单拆到单独文件，instruction 只管流程。

## 可复用建议

- 用"给零记忆实习生写工单"的标准自检：他只看这张工单，能否独立完成并正确交差。
- 运行结果顺手落一份日志文件，排障时比翻会话记录快得多。
- 指令模板放 git 里管版本，改 prompt 和改代码一样走 diff。

## 总结

Cron 的 instruction 不是聊天消息，而是一份带 I/O 契约的作业说明：目标、输出、静默、状态、失败，五段写全，定时任务才能从"薛定谔的运行"变成可靠自动化。经验上，先写清楚"什么时候什么都不做"，往往比写清楚要做什么更重要。
