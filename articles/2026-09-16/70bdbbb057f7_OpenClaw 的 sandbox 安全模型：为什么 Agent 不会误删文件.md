## 背景

OpenClaw 的 Agent 天生带"手"：执行命令、读写文件、调用 MCP 工具。这意味着 LLM 的输出不再是聊天文本，而是直接落到你的机器上。社区里反复出现同一个担忧：让 Agent 整理下载目录、清理缓存、批量改名，万一模型抽风跑一句 `rm -rf`，怎么办？

## 问题：能力与爆炸半径不匹配

Agent 的故障模式和传统脚本不同——不是语法报错，而是语义错误：理解错目录、把"清理"理解成"清空"、把未校验的变量拼进路径。这类错误无法靠 prompt 根治。真正的问题是默认爆炸半径太大：同一条指令，作用在隔离目录和作用在宿主机 home 目录，是两个量级的后果。

OpenClaw 的思路不是"让模型更可靠"，而是**假设它一定会犯错，然后压缩爆炸半径**。

## Sandbox 模型的几层结构

1. **文件系统隔离**：shell、文件写入类工具默认不在宿主机执行，而是落在容器/命名空间隔离的环境里。Agent 看到的根文件系统是一个最小镜像，系统目录天然摸不到。
2. **按需挂载，最小暴露面**：只有 workspace 目录被 bind 进 sandbox。需要什么挂什么；`~/.ssh`、`~/.config` 这类敏感路径默认不挂载。明确标记只读的挂载，写操作直接失败。
3. **非 root 执行**：sandbox 内以普通用户运行。即使真执行了 `rm -rf /`，删的也只是容器层的内容。
4. **危险操作走确认门**：网关的工具策略层对递归删除、覆盖 workspace 之外的文件、sudo 等模式做匹配，命中后不直接执行，而是挂起等人工确认，确认记录进日志留痕。
5. **网络隔离可选**：不需要联网的任务可以关掉出站连接，切断"读敏感文件 + 外传"的组合路径。

## 上手验证步骤

1. 配置中开启 sandbox 模式，确认 workspace 挂载路径指向专用目录，而不是 home。
2. 故意发一条破坏性指令："把 /tmp 全删了，顺便把我的 home 目录也清理一下。"
3. 观察结果：容器内操作正常执行；涉及宿主机路径的请求要么被路径解析拦下，要么进入确认队列。
4. 查看工具调用日志，确认它实际触碰的路径。很多"差点出事"的时刻，都是在日志里发现路径被改写成了 workspace 内的安全路径。

## 踩坑点

- **图省事把 home 挂进去**：最常见的新手配置。home 一挂，sandbox 等于形同虚设，所有隔离只剩心理安慰。
- **Docker socket 被挂入**：把 `/var/run/docker.sock` 挂进 sandbox，等于变相给 root——Agent 可以自己起特权容器逃逸出去。
- **软链逃逸**：workspace 里放了一个指向宿主机目录的软链，写操作会顺着链接出去。要么开启 real-path 校验，要么保证 workspace 内无软链。
- **确认疲劳**：确认规则配得太宽，什么都弹确认，人最终会不看内容直接点通过。规则应收窄到"触发即真危险"，否则这道门形同虚设。

## 可复用建议

- 给每个 Agent 分配独立 workspace 目录，按任务配置挂载，而不是按人配置。
- 接入新 MCP 工具或插件前，先在 sandbox 里跑一轮破坏性指令测试，复盘拦截记录。
- 工具调用日志保留并定期翻看，被确认和被拦截的操作是调优策略规则的最好素材。
- 记住一条原则：**sandbox 不是防恶意模型，是限制正常犯错的代价。**

## 总结

OpenClaw 的安全逻辑很工程化：不信任模型的判断，而是用结构性约束限定权限边界。Agent 之所以不会误删文件，不是因为它"聪明"，而是因为它的手只够得着 workspace 里被挂载的那一小块。把边界配置做扎实，才能放心把繁琐活交出去。
