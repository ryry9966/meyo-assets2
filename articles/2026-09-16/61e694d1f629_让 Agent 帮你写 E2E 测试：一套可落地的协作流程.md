## 背景

E2E 测试一直是"人人都知道该写、但没人愿意写"的那类工作。原因不复杂：用例写起来慢、坏得快，维护成本随页面迭代线性上涨，于是回归全靠人肉点一遍的团队不在少数。

Agent + MCP 工具链（比如让 Agent 直接操作浏览器）改变的是成本结构：探索页面、生成用例、跑失败、自己修，这些环节 Agent 都能承担。但它不会自动替你解决"测什么、断言什么、怎么保证稳定"这些本质问题。

## 问题

直接丢一句"给这个站点写 E2E 测试"，通常得到三类结果：

1. 看起来很像测试的脚本，断言形同虚设——只检查元素存在，不验证业务结果；
2. 选择器依赖自动生成的 class 名，一次构建就碎；
3. 用固定 `sleep` 蒙混等待，本地绿、CI 红。

问题不在模型能力，而在于你没给它约束和反馈回路。

## 做法

我的流程分四步，核心思路是把 Agent 当成一个需要 onboarding 的新同事：

**第一步：给它工具和边界。** 通过 MCP 接入浏览器控制能力，明确它能访问的环境——只用 staging，绝不碰生产。测试框架、目录结构、命名规范提前定好。

**第二步：先探索、再生成。** 让 Agent 自由走查核心路径（登录 → 下单 → 回调），先输出它理解的业务流程描述，人工确认后再生成代码。这步很关键：Agent 对业务的理解错了，后面全白写。

**第三步：跑失败、喂日志、修。** 用例进 CI，失败时把结构化错误日志、截图、失败步骤喂回给 Agent 让它自己修，但修复有边界：不许通过削弱断言让测试变绿。

**第四步：人工 review，当正式 PR 对待。** 标准 and 人写的一样：断言是否验证业务结果、选择器是否语义化、有没有数据耦合。

## 踩坑点

- **假绿测试**：Agent 很容易生成"跑通但没测到东西"的用例。review 时优先看断言数量和强度，一个用例至少一个业务级断言。
- **wait 陷阱**：在规范里直接禁用固定 sleep，强制 wait-for-condition 类 API，违例走 lint 拦截。
- **选择器漂移**：要求 Agent 只用语义化选择器（role、label、test-id），同时给前端一份补 data-testid 的清单，一次沟通解决一半稳定性问题。
- **上下文浪费**：失败反馈别只丢截图，结构化日志加对应的测试代码片段，修复成功率差距非常大。

## 可复用建议

- 把规范沉淀成仓库内的规则文件（如 AGENTS.md），写清禁用项、选择器策略、断言标准、目录约定，Agent 每次生成都读它。
- 生成的用例统一放 draft 目录或打 label，跑稳两周再合入主干，避免 flaky 用例污染 CI 的信任度。
- 失败自愈循环可以放 CI 里自动跑，但修复 PR 必须人工 approve。

## 总结

Agent 把写 E2E 的边际成本压到了接近忽略的程度，但测试的工程价值仍由断言质量和稳定性决定。经验归结为四点：约束先行、探索先行、断言人工把关、修复有边界。做到这四点，Agent 生成的用例可以直接进代码库；做不到，它只是帮你更快地生产一堆假测试。
