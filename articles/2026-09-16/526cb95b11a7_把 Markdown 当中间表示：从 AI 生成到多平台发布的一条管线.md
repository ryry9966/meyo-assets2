## 背景

在 OpenClaw 的自动化流程里，Agent 产出 Markdown 已经是默认动作：技术周报、发布说明、教程草稿。但真正的麻烦不在生成，而在发布——同一篇内容要进公众号、静态站、GitHub、RSS，各平台的 Markdown 方言和渲染限制完全不同。是把格式适配当一次性的复制粘贴来糊弄，还是当编译问题来解决，直接决定这条自动化的可持续性。

## 问题

实际踩过的坑归为三类：

1. **方言差异**：GFM 表格、脚注、Mermaid、行内 HTML 在不同平台存活率不一样。公众号编辑器剥掉大部分样式和部分标签；静态站全支持；RSS 只认最保守的子集。
2. **AI 输出不稳定**：模型有时从 `###` 起步写标题、列表缩进混用、段落里夹 HTML 块，直接投喂会放大噪声。
3. **资产问题**：外链图片在公众号端大概率裂图，必须转存；Mermaid 不渲染，得预渲染成图。

## 做法

我们的思路是：**Markdown 即中间表示（IR），平台适配器即编译后端**。

- **归一化层**：入库前跑 lint/fix——统一标题层级（补 `##` 起步）、修列表缩进、剥离非法 HTML。用 remark/mdast 在 AST 层面操作，不要用正则硬匹配。
- **适配器层**：每个目标平台一个纯函数 `adapt(mdast, platform) -> artifact`。公众号后端负责代码块转行内样式 HTML、图片下载转存并回填 URL；静态站后端几乎透传，只补 frontmatter。
- **校验层**：发布前跑三个检查——链接可达性、禁用片段（外部域名/平台敏感词）、渲染冒烟测试（本地渲染一遍，HTML 结构不塌）。
- **执行**：做成 OpenClaw skill，输入草稿路径和平台列表，输出各平台产物目录加预览链接，人只做最后确认。

## 踩坑点

- 公众号不支持 `<details>` 和自定义 class，代码高亮必须转成行内 style，否则粘贴进去是纯文本。
- Mermaid 在公众号和 RSS 都活不下来：要么预渲染 SVG，要么在归一化层降级为代码块并标注。
- 图片转存要按内容 hash 去重加缓存，否则重复上传触发频控。
- 适配器必须幂等：同一份 mdast 跑两次，产物逐字节一致。否则快照测试写不了，diff 也没法审。
- 适配器不要改内容语义。删段落、改文案是归一化层和人的事，后端只管格式。

## 可复用建议

- Frontmatter 保持最小 schema：`title / tags / platforms`，其余进正文，降低解析成本。
- 每个适配器配快照测试，换模型、升级依赖后跑一遍就知道哪里坏了。
- 记录 `源文件 hash → 产物 hash` 映射日志，排障时快速定位变化来自哪一层。
- 预览环节不要省。自动化可以生成，发布按钮留在人手里。

## 总结

多平台发布的本质不是排版问题，是编译问题：Markdown 定语法，AST 定语义，适配器定目标产物。把适配器写成幂等纯函数、把校验做在发布前，这条管线就能在换模型、换平台时保持稳定。剩下的，交给 review。
