## 背景

给 Agent 接上 MCP 工具和插件之后，第一周很爽，第二周开始纠结：我让它清理构建产物，它顺手把两个没跟踪的日志目录也删了；而另一些时候，它复制一个文件都要先跟我确认半天。两个极端背后是同一个问题没想清楚：权限边界到底画在哪。

## 问题

多数人默认用两种朴素策略：要么"全部先问我"，要么"全都自己干"。前者很快把人训练成无脑点确认的机器——确认疲劳之后，确认环节形同虚设；后者则是把生产环境、外部通信、不可逆操作全押在模型当下的判断力上。更关键的一点：**确认不是安全边界，执行层才是**。写在 system prompt 里的"请先征求我的同意"属于君子协定，模型状态不好或被注入时它就是纸。

## 做法

我们把动作按三个维度分级：**可逆性**（能不能撤销）、**爆炸半径**（影响本地草稿，还是共享状态/外部世界）、**意图对齐**（是用户指令的直接推论，还是模型自己推断出来的）。落到三档策略：

- **T1 自动执行**：只读操作、本地可逆写操作（git 管理下的文件编辑、生成草稿）。不问，但全部记审计日志。
- **T2 会话内确认**：不可逆但范围可控——删文件、调用付费 API、写共享文档。第一次询问，批准后本会话内同模式放行，会话结束授权作废。
- **T3 硬门槛**：外部通信、部署、schema 变更、批量删除。逐次确认，且确认的是参数级 diff，不是"我要执行 XX 工具"这种一句话。

实现上就一件事：在工具分发层加一个策略网关。每个 MCP 工具或插件注册时带上风险等级标签，网关按策略决定放行、拦截或转入待批准队列。注意按**调用**分级而不是按工具名——同一个 `bash` 工具，`ls` 和 `rm -rf` 是两回事，命令串需要模式匹配加危险模式黑名单兜底。

再往上叠一层"计划确认"：批量任务先让 Agent 输出步骤清单，人批一次计划，网关校验每一步实际调用是否落在批准范围内，超出即重新询问。这能把确认次数从 N 次压到 1 次。

## 踩坑点

- **确认疲劳是最大的坑**。一天弹二十次确认，用户会条件反射地点同意，比没有网关更危险。宁可默认收紧，也别让确认变成噪音。
- **按工具名分级不够**。同一工具的两次调用风险完全不同，必须看参数。
- **命令串模式匹配是易碎的**。base64 编码、管道拼接、`&&` 链都能绕过简单正则，黑名单只能兜底不能当主防线。最稳的办法是收窄工具面：不给通用 shell，只给封装过的具体能力。
- **授权要有时效**。昨天点的"同意"不该覆盖今天语境完全不同的操作。
- **后台任务要单独设计**。人不在时长任务跑着，T2/T3 调用应进待批准队列，而不是静默放行或直接失败。

## 可复用建议

1. 从"离开本机的操作默认拒绝"起步，拿审计日志说话，再逐步放宽。
2. 确认时展示参数 diff，不是工具名——人只能对具体内容做判断。
3. 审计日志是底线配置，没有日志的权限系统等于没做。
4. 每周回看一次拦截和放行记录，按误报率调整分级。

## 总结

权限边界不是"问不问"的二选一，而是按可逆性、爆炸半径、意图对齐拉出来的连续光谱。两条工程原则：确认要稀缺、具体、会过期；强制要在代码层做，而不是靠提示词自觉。Agent 的自主性和可控性并不冲突——冲突的是没想清楚就想两全的配置。
