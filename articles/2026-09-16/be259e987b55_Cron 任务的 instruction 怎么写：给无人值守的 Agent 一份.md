## 背景

OpenClaw 的 cron 任务本质上是**无人值守的 prompt**：到点唤醒一个冷启动的 agent，跑完即退出。它和聊天里写的 prompt 有三个关键区别——没有人在场追问、没有对话上下文、输出没有即时反馈。很多在交互模式下表现正常的指令，直接搬进 cron 就开始自由发挥。

## 问题

常见症状：

- instruction 里写了「有需要随时问我」，结果任务卡在等待确认，永远等不到；
- 每次跑完都往群里发一大段消息，或者反过来——跑完了但谁也没看到输出；
- 「继续昨天没做完的部分」这种指令，冷启动的 agent 根本不知道「昨天」指什么；
- 工具调用失败后，agent 自行编造一个看起来合理的结果。

根因是同一个：交互 prompt 依赖人在环上兜底，而 cron 没有这个兜底。

## 做法

把 cron instruction 当成一份 mini SOP 写，推荐固定五段结构：

1. **目标与时间基准**：一句话说清做什么；「昨日 / 上周」等相对时间，明确以系统当前日期计算。
2. **输入与工具**：写死数据来源、路径、工具名，不要用「最近的文件」这类模糊指代。
3. **执行步骤**：编号列出，每步一个动作，避免长散文。
4. **输出契约**：cron 特有的一段，说清三件事——正常情况发不发消息、发到哪里、什么格式；以及「无事可报」时怎么办（通常明确写：无异常则保持安静）。
5. **失败与边界**：失败重试几次、失败后记录到哪里；明确禁止事项（不写入、不追问、不扩散范围）。

一个能直接改的示例：

```text
目标：每日 08:30 汇总昨日 RSS 抓取结果。
时间基准：以系统当前日期计算"昨日"。
数据源：用 fetch 工具读取 /data/rss/daily.json。
步骤：1) 读取文件并统计新增条目数；2) 筛选关键词命中，最多 10 条；
3) 写入 /data/reports/YYYY-MM-DD.md。
输出：命中 ≥1 条时向 #daily 发一条消息，格式"昨日命中 N 条 + 标题列表"；
否则不发任何消息。
失败：文件不存在重试 1 次，仍失败写入 /data/logs/cron-error.log 后结束。
禁止：不要追问，不要执行以上列表之外的操作。
```

最后一个流程原则：**先在聊天里手动跑一遍同样的 instruction**，确认全程无追问、输出符合预期，再挂上 cron。聊天是 staging，cron 是 production。

## 踩坑点

- **留了追问口子**：cron 无法追问，agent 要么卡住要么瞎猜。改成决策规则，例如「缺失数据超过 3 条则跳过本次并记日志」。
- **时间语义含糊**：「每天早上」和 cron 表达式对不上；相对时间必须注明时区基准。
- **一个 cron 干多件事**：排查失败时无法定位，拆成单一职责的多个任务。
- **忽略幂等性**：任务重跑会产生重复消息、重复文件。instruction 里写清「若今日结果已存在则跳过」。
- **没有输出上限**：让它「总结全部」，一次跑掉几万 token。限制条数和长度。

## 可复用建议

- 把五段结构存成**模板**，新建 cron 只填空，不从头写；
- 消息分级：**告警才推送，常规报告落盘**，避免渠道刷屏；
- **每月回看一次实际输出**。instruction 是会腐化的，上游数据结构变了它不会主动告诉你；
- 复杂业务逻辑放脚本或代码里，instruction 只负责编排和简单判断，不要用自然语言描述复杂规则。

## 总结

给交互场景写 prompt 是在对话，给 cron 写 instruction 是在写岗位说明书。默认执行者是冷启动、没人监督、跑完就走的一个进程——把决策规则、输出契约、失败行为全部写死，它才能稳定值班。
