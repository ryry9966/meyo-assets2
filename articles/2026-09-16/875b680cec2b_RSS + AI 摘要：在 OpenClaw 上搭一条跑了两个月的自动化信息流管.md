## 背景

信息源越订越多，真正读完的比例越来越低。RSS 依然是拿到非算法化信息流的最稳方式，但原始 feed 有两个老问题：噪音大、长文耗时。我的解法是在 OpenClaw 上把「抓取 → 清洗 → 摘要 → 推送」整条链路自动化，每天两次把汇总摘要推到 IM。目前稳定运行两个月，把做法和坑分享一下。

## 问题定义

- 订阅源分散，部分站点不输出全文，拿到的是摘要残片
- 正文直接丢给 LLM，token 成本不可控
- 同一事件多个源重复报道，推送里全是冗余
- 需要可靠调度和失败告警，不能依赖手动跑脚本

## 做法

整体是四段式管线，每段独立、可单独替换：

1. **抓取层**：用 Miniflux 做集中订阅管理，自带去重和抓取间隔控制；没有全文输出的源用 RSSHub 补规则。
2. **清洗层**：写了一个轻量插件，定时从 Miniflux API 拉未读条目，正文过一遍 readability 提取，剥掉导航和广告残留。这一步实测能砍掉 60% 以上的无效 token。
3. **摘要层**：清洗后的条目按源分组喂给 Agent。Prompt 固定三段式：一句话结论、关键事实列表、原文链接。单条超过 3000 字只取前半加结尾，信息损失很小。
4. **推送层**：摘要合并成日报格式，经 MCP 消息通道推到群组。条目落库存 hash，作为下一轮去重依据。

调度用 cron，每天 8 点和 20 点各跑一次，错峰避开源站更新高峰。

## 踩坑点

- **不要跳过 readability**。很多 feed 的 content 字段混着 HTML 片段和推荐位文案，直接喂模型，摘要会一本正经地引用广告语。
- **去重要在内容层面做**，不能只看链接。同一篇文章 URL 带 utm 参数就会重复，先归一化 URL、再 hash 标题才可靠。
- **批次上限要硬编码**。有一次某个源积压 80 条未读，一批喂进去直接超上下文。之后加了单批条目上限，超出部分顺延到下一轮。
- **失败必须可观测**。早期抓取静默失败，三天没收到推送才发现问题。现在每个环节写状态日志，连续两轮失败就单独推一条告警。
- **摘要 prompt 别追求花哨**。试过「风格化转写」，产出忽好忽坏；退回三段式后基本不再需要人工修正。

## 可复用建议

- 管线分层解耦：抓取/清洗/摘要/推送各自可替换，比如换摘要模型不影响其他环节
- 原始条目一定落库：摘要可以随时重算，原始数据丢了没法回溯
- 成本控制前置：清洗比换便宜模型更有效，先减量、再谈模型
- 新源先进观察队列一周，确认输出质量再进正式列表，低质量源及时砍

## 总结

这套管线没有用任何复杂技术，核心是每步只做一件事、失败路径提前想清楚。上线后每天阅读时间从零散一小时压到十五分钟以内，重要信息没有漏过。如果你已经在用 OpenClaw 的插件和 MCP 能力，搭完这条管线大约一个下午的工作量，性价比很高，推荐直接抄作业。
