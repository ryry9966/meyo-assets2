## 背景

跑过一段时间的 Agent 都有体感：大多数线上故障不是模型本身的问题，而是外部依赖——LLM 供应商限流、MCP 工具背后的第三方 API 超时、Webhook 掉线、Token 过期。Agent 的特点是调用链长，一个任务串起七八个工具，任何一环抖动，整个任务就废了。

## 问题：失败不可怕，可怕的是两种反应

1. **直接崩掉或静默失败**：任务中断，用户只看到沉默。
2. **更糟的**：把原始报错丢回给模型，让它"自己想办法"。常见结局是模型在循环里疯狂重试烧 token，或者干脆编一个结果交差。

核心矛盾在于：重试与放弃是工程决策，但我们经常把它交给了概率模型。

## 做法：四层防线

**第 1 层：错误分类（写在代码里，不在提示词里）**
- 可重试：429、5xx、超时、网络抖动
- 不可重试：400、401、404、业务校验失败

分类逻辑放在工具封装或 MCP 中间层，模型只拿到结论。

**第 2 层：指数退避 + 抖动**
封装层重试 2–3 次，backoff 从 1s 起指数增长，加随机 jitter，遇到 429 尊重 `Retry-After`。重试永远不要放在 agent loop 里。

**第 3 层：熔断**
连续 N 次失败后把该工具标记为 degraded，冷却期内直接返回"服务暂不可用"，避免每次调用都等满超时。多 agent 场景建议共享熔断状态。

**第 4 层：降级**
- 切备用数据源，或返回过期缓存（必须带时间戳声明）
- 跳过该步骤，任务部分完成并如实上报

原则：宁可说"我没做到"，不说一个假结果。

另外，返回给模型的错误信息要结构化：错误码、是否可重试、建议等待时长。模型拿到 `rate_limited, retry_after=30s` 会选择等待或告知用户；拿到一坨 stack trace 只会不停道歉。

## 踩坑点

1. **让模型自己重试**：token 烧穿，且失败模式不可预测。重试属于代码层。
2. **重试非幂等操作**：发消息、下单类工具超时时，可能"已成功但没收到响应"，盲目重试就是重复执行。用幂等键。
3. **所有错误一视同仁**：对带着 Retry-After 的 429 还 1 秒重试三次，只会被拉黑更久。
4. **无 jitter 的定时重试**：多个定时任务同一秒一起打过去，自制造流量尖峰。
5. **静默降级**：用了缓存却不声明，用户拿到的是昨天的天气。降级必须对用户可见。
6. **只有单次调用超时，没有任务级预算**：每步都"差不多能过"，整个任务挂十分钟。给整个任务设总时长上限。

## 可复用建议

- 做一个统一的 resilient client / MCP 包装层：超时、重试、熔断、降级全部配置化，所有插件复用，不要每个插件自己造一套。
- 在工具 schema 和描述里写清楚副作用属性（幂等与否），恢复策略才有依据。
- 维护一张"错误码 → 模型可见消息"的映射表，保证返回给模型的信息短、结构化、可执行。
- 日志里把重试次数、熔断触发、降级来源记成结构化字段，事后排查才查得动。

## 总结

外部 API 一定会挂，这不是 if，是 when。Agent 错误恢复的本质，是把"重试还是放弃"的决策从模型手里拿回代码层，让模型只面对清晰的结论和选项：等、换、跳、如实报告。做好分类、退避、熔断、降级四层，再补上幂等性和任务预算，你的 agent 就能在依赖抖动时体面地失败——而不是崩溃，或者撒谎。
