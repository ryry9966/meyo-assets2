## 背景

OpenClaw 常驻跑起来之后，任务谱系比想象中宽：主循环里的规划、代码改动、跨工具编排是一头；heartbeat 定时巡检、消息分类、日志归整、字段抽取是另一头。前者吃模型能力上限，后者只要求“稳定够用”。全走云端旗舰，账单和 p95 延迟都难看；全走本地小模型，规划层一崩，执行层全是无效重试。

多模型路由解决的就是这个分配问题：把不同层级的任务，交给性价比最合适的模型。

## 怎么做

### 1. 先给任务分层

- **L1 重推理**：任务规划、多步工具编排、代码重构 → 云端旗舰（GPT-4o 一档）
- **L2 中等**：带明确 schema 的工具调用、结构化抽取、中等长度摘要 → 本地 14B~32B 或云端小杯
- **L3 轻量**：分类、打标、格式转换、去重 → 本地 7B 一档，能规则解决的用规则

### 2. 路由规则写成配置，不写成代码

三个维度基本够用：

- **按 skill 绑定**：每个 skill 声明自己用哪档模型，互不干扰；
- **按触发路径**：交互会话走云端，定时/自动化任务走本地；
- **按敏感度**：上下文触及本地文件路径、密钥相关内容的，强制本地执行，数据不出机。

再配一条 fallback 链：云端限流降级到本地；本地连续解析失败升级回云端。别让单点故障拖死整条链路。

### 3. 给本地模型“修路”

本地模型能不能用，很大程度取决于你喂给它什么：精简 system prompt、MCP 工具结果先裁剪再入上下文、输出走严格 JSON schema 加一次自动修复重试、温度压到 0.2 以下。路修好了，L2/L3 层的可用性才谈得上。

## 踩坑点

1. **本地模型的 function calling 不可全信**。有的模型 JSON 外面套 markdown 围栏，有的参数名自己发挥。没有 schema 校验和降级策略，重试烧掉的钱比省下的还多。
2. **上下文窗口陷阱**。本地 8K 窗口，塞了 MCP 工具定义和会话历史就爆，外在表现是“突然变笨”，很难第一时间联想到是路由问题。
3. **别把 planner 路由到本地**。规划层省 5% 成本，执行层多出 30% 无效重试，净亏。
4. **用自己的任务集测，别看榜单**。中文指令遵循和 tokenizer 效率，榜单成绩和真实 agent 场景差距不小。
5. **长输出别给本地**。慢，且自动化链路对延迟敏感，卡在最后一步最伤。

## 可复用建议

- 从“云端默认 + 本地接管 3 类任务”起步，跑一周有数据再扩，别一步到位全路由；
- 每层记三个数：任务成功率、p95 延迟、单任务成本，没有指标就没有路由；
- 路由表放配置里，支持灰度和一键回退；
- 每月回看一次路由表，本地模型和云端都在快速更新，半年前的结论会过期。

## 总结

多模型路由不是省钱小技巧，而是把“模型能力”当资源来分配的工程问题。一句话原则：不可重试、影响全局的任务给最强模型；可校验、可重试、高频的任务给便宜模型；敏感数据不离开本机。先分层、再路由、用指标说话，路会越调越准。
