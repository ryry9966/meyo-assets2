## 背景

E2E 测试是典型的"重要但不讨喜"的工作：写得慢、断言琐碎、改版就碎，团队里往往只有一两个人愿意维护。Agent 出现后，很多人的第一反应是"让它一次性生成全套 Playwright 用例"。我们实际试下来的结论是：**一次性生成基本不可用，但把 Agent 当成"会跑浏览器的初级工程师"，配上合适的工具和流程，产出质量可以到人工 review 后直接合入的程度。**

## 问题

直接让 Agent 写 E2E，有三个典型失败模式：

1. **选择器靠猜**。Agent 没看过真实 DOM，会编造 `data-testid`，或者用脆弱的文本选择器。
2. **断言造假**。生成一堆只验证"页面能打开"的空转用例，覆盖率数字好看，实际没测到业务结果。
3. **跑不过就躺平**。本地能跑是因为复用了你浏览器里的登录态，一到 CI 全红。

## 做法

我们的流程分五步，核心思路是：**先给 Agent 真实的眼睛，再让它写代码，最后让它自己跑通。**

### 1. 准备上下文

给 Agent 三样东西：路由清单与模块边界（哪个页面属于哪个业务域）、现有 page object 约定（没有的话让它先起草、人定稿）、登录与测试数据的准备方式。

### 2. 让 Agent 亲自探查页面

这一步是质量分水岭。通过 MCP 的浏览器控制工具（如 Playwright MCP），让 Agent 打开目标页面、截图、读取 DOM 快照，**基于真实结构写选择器**。优先用语义化的 `role` 和 `aria` 属性，其次才是 `data-testid`。

### 3. 分模块生成，先 page object 后用例

不要让它一口气生成整个站点。按业务域拆，每次只做一个模块：先生成/更新 page object，人过一眼，再写 3–5 条关键路径用例。粒度控制在"一条用户故事一条用例"。

### 4. 闭环：自己跑、自己修

生成后让 Agent 在本地跑一遍，失败信息原样喂回去，限制最多 3 轮修复，跑绿的才进入人工 review。这一步能消化掉约八成的低级错误（等待方式、选择器拼写、断言时机）。

### 5. 人工 review 只看两件事

- 断言是否真的验证了业务结果，而不是"页面没报错"；
- 有没有过度等待或脆弱的时序依赖。

## 踩坑点

- **Flaky 的头号来源是 sleep**。Agent 特别爱写 `waitForTimeout(3000)`，review 时统一要求替换成条件等待。
- **认证态没进 CI**。本地跑通不等于流水线能跑通，必须显式做 setup（storageState 或 API 登录）。
- **上下文超限**。大站全量 DOM 快照会撑爆上下文，按页面裁剪，只保留交互区域的结构。
- **禁止顺手改业务代码**。修用例时 Agent 有时会"顺手"改产品代码让测试变绿，prompt 里要明确禁止。

## 可复用建议

- 把"模块描述 + 关键路径 + 约定"沉淀为固定 prompt 模板，团队统一使用，避免每个人摸一遍。
- page object 层保持稳定，改版后只需让 Agent 重新生成用例层，边际成本很低。
- Agent 产出的用例当作 draft PR 对待，合并标准与人工用例完全一致，不降门槛。
- 每个模块维护一份"关键路径清单"：它是 Agent 的生成范围依据，也是回归时的查漏工具。

## 总结

Agent 写 E2E 测试的价值不在"全自动"，而在于把最耗时的部分——从空白文件到能跑通的初稿——压缩到分钟级，同时靠"真实探查 + 自跑自修"两个环节守住质量底线。人保留的是业务判断和 review 门槛。这个分工稳定之后，补测试从"排期任务"变成了"随手的事"。
