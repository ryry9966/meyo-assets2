## 背景

OpenClaw 上的 agent 跑久了，对话要点、用户偏好、环境事实都会落到本地记忆库。`memory_recall` 是每轮对话前把相关记忆捞回来的那一步——捞错或漏捞，助手就会"失忆"或答非所问。检索方案无非两条路：基于 embedding 的语义搜索，和基于 BM25 的全文搜索（比如 SQLite FTS5）。

## 问题

两条路线的失败模式完全不同，我们都在生产里撞过：

- **语义搜索对精确标识符很弱**：错误码、文件路径、配置键、项目代号，在 embedding 空间里这些词经常召回一堆"看起来像"但不相关的条目。
- **全文搜索对改写无能为力**：用户说"上次那个部署翻车的事"，记忆里存的是"deploy 失败排查记录"，关键词一个都对不上。
- 中文场景还有额外变量：embedding 模型对中文口语 query 的编码质量参差不齐，选错模型，语义通道基本白搭。

## 做法

我们的落地路径，建议照这个顺序来：

1. **先建 FTS 基线**。SQLite FTS5 + trigram tokenizer（或外挂 jieba 分词），memory 表挂 FTS 虚表，查询取 top-10。成本几乎为零，先跑起来。
2. **加语义通道**。选一个中文表现靠谱的 embedding 模型，条目写入时算向量存同库，查询时 cosine 取 top-10。
3. **混合融合**。两路结果用 RRF 合并：`score = Σ 1/(60 + rank)`，取融合后 top-5 注入上下文。
4. **建评测集**。手写 50–100 条 query，覆盖改写型、精确标识符型、时间型三类，每次改动跑一遍 recall@5 做回归。

## 踩坑点

- FTS5 默认的 unicode61 分词器按空白切词，中文整段会被当成一个 token，全文索引直接报废。这是最常见的翻车点。
- BM25 分数无上界，cosine 在 0–1 之间，两路分数直接加权归一化基本必翻车，用 RRF 绕开可比性问题。
- 换 embedding 模型等于全量重建向量索引，向量表里务必存 model 版本号。
- 记忆条目必须带时间戳，召回后按 recency 做轻度加权，否则三个月前的老记忆永远霸榜。
- 条目粒度按"单条事实 / 单次事件"切。整段对话塞成一条，召回时噪声会淹没有效信息。

## 可复用建议

- 不要一上来就堆向量库。先跑 FTS 基线 + 评测集，量出真实缺口；如果缺口集中在改写类 query 上，再补语义通道。
- 混合检索 + RRF 是默认答案，单通道只在数据形态极其单一时够用。
- 把每轮真实命中的 recall 结果落日志，评测集会自己长大——这比任何前期设计都值钱。

## 总结

语义搜索和全文搜索没有普适赢家：精确标识符靠全文，模糊改写靠语义，中文场景两者都要先解决分词和编码质量。工程上的稳定解是**混合检索 + RRF 融合 + recency 加权**，配一个持续生长的评测集。先测量，再优化，别凭感觉选型。
