## 背景

给 Agent 接上 MCP server 和插件之后，它就不再只是生成文本，而是开始执行：写文件、调 shell、发 HTTP 请求、动数据库。权限边界的问题从这一刻起就不是理论问题了——你交给它的每一把钥匙，都是它可以在无人监督时使用的东西。

## 问题

实践中常见两个极端。一种是什么都放行，结果 Agent 跑飞：误删工作区、往客户群发了消息、把 API 额度一晚烧完。另一种是每步都问，人退化成点击机器，点了三十次之后开始条件反射地全选"允许"，防护形同虚设。

真正要做的是把"问不问"从现场拍脑袋，变成一份可维护、可审计的策略。

## 判定框架：三个维度

给每个工具（或工具+参数组合）按三个维度打标：

- **可逆性**：能否用 git revert、软删除、重新执行恢复？
- **爆炸半径**：影响单个文件，还是共享状态、生产数据、外部用户？
- **外部可见性**：结果是否离开你的机器——发消息、调第三方接口、花钱？

由此分四档：

| 档位 | 特征 | 策略 |
|---|---|---|
| L0 | 只读、无外部副作用 | 自动执行 |
| L1 | 可写但可逆（工作区内、git 管辖） | 自动执行 + 审计日志 |
| L2 | 影响共享状态但可拦截（开 PR、staging 部署、幂等外部调用） | 首次确认，确认后按 scope 加白名单 |
| L3 | 不可逆 / 花钱 / 对外通信 / 动凭据 | 每次必问，人来确认 |

## 落地步骤

1. **盘点工具清单**。把每个 MCP server、每个插件的 capability 列成一张表。第一次做的人通常会发现工具数远超预期。
2. **打标分级**。按三维度标 L0–L3，拿不准的一律先按高一级处理。
3. **写进配置**。用 MCP 的 allowlist/denylist 加确认钩子实现。注意 L2 白名单的粒度应是"工具+参数前缀"，而不是整个工具名放行。
4. **确认时给上下文**。弹出的不应是"是否允许？"，而是 diff、目标路径、请求参数、预计费用。没有上下文的确认按钮，只会训练人无脑点允许。
5. **审计 + 回路**。所有执行落日志，每周扫一遍：出过事的降级，长期顺畅的再讨论升级。

## 踩坑点

- **按工具名分级不够细**。同一个 `write_file`，写 `./notes.md` 和写 `~/.ssh/` 是两回事。分级必须落到参数层面。
- **确认疲劳**。问得太频繁，人会条件反射点允许，比不问更危险。宁可减少提问次数，提高每次提问的信息量。
- **逐次安全 ≠ 整体安全**。Agent 循环调 50 次"安全"的接口，合计可能超预算或触发对方风控。需要调用频率和费用上限这类断路器。
- **只读不等于无害**。读到密钥再拼进后续外部请求，就是泄漏。敏感路径的读操作也应归入 L2 以上。
- **异步任务里人不在**。确认请求超时的默认行为必须是拒绝，不能是放行。
- **别完全信任工具描述**。MCP server 换版本、换实现后语义可能变，分级清单要跟着版本走。

## 可复用建议

- 新工具默认 L3 或至少 L2，观察一段时间再降级——和生产权限管理同一个思路：默认拒绝，逐步放行。
- 每个 Agent 使用独立凭据、独立 scope，不共享管理员 token，出事时可精确吊销。
- 把权限清单当代码维护：进版本库、有 review、有变更记录。
- 确认交互坚持"意图 + 参数 + diff"三件套，缺一项就不允许加入白名单。

## 总结

权限边界不是一个开关，而是一张持续维护的分级表。判断标准始终是三问：能不能撤回、出事影响多大、结果给谁看。把这三个答案编码进配置和流程，Agent 在"自己干"和"问人"之间，才有一条讲得清楚、也改得动的线。
