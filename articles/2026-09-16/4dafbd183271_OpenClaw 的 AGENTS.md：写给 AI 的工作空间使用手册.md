## 背景：Agent 需要“入职文档”

把 OpenClaw 接入一个真实工作空间后，最先遇到的不是能力问题，而是上下文问题。模型并不知道你的项目用什么命令构建、哪些目录不能动、多个 MCP 工具该优先调哪个。README 是写给人看的，而 Agent 需要一份写给它的说明书——AGENTS.md 就是这个角色：放在工作空间根目录的纯 Markdown 文件，OpenClaw 在会话初始化时自动读取，作为持久化的行为约束注入上下文。

## 问题：没有它，每次会话都在重蹈覆辙

没有 AGENTS.md 时常见三种损耗：

1. **命令靠猜**。Agent 可能用 `npm test` 去跑一个实际用 `pnpm test` 的项目，失败后自行折腾，烧掉大量 token 和时间。
2. **约定靠提醒**。代码风格、提交格式、目录归属，每个新会话都要重复交代一遍。
3. **边界靠运气**。哪些文件只读、哪些操作要先确认，不说清楚就是风险。

本质上是同一类问题：把本该确定性的信息，寄希望于模型的记忆和推理。

## 做法：写一份能落地的 AGENTS.md

我的文件大致分四段，供参考：

```markdown
# 构建与验证
- 包管理器：pnpm，不要用 npm/yarn
- 测试：pnpm test，单文件用 pnpm test path/to/file

# 结构约定
- src/agents/ 下按"一个能力一个目录"组织
- 产物一律放 dist/，不要提交

# 边界
- infra/ 目录只读，改动需人工确认
- 禁止执行 rm -rf 或任何生产环境命令

# 工具偏好
- 查文档优先走 docs MCP，其次再搜索
- 批量改文件前先列出修改计划
```

落地步骤建议：先写 20 行以内 → 用一个真实任务跑一轮 → 哪里出错就补哪条规则 → 提交版本库，随代码一起 review。

## 踩坑点

- **写成愿景文档**。“写出高质量代码”这类话没有信息量，Agent 无法执行。要写可验证的事实：具体命令、具体路径、具体禁令。
- **贪多求全**。两三百行的文件会稀释关键指令的权重。守则是一行一个事实，超过一屏就该拆到子目录的 AGENTS.md，OpenClaw 按就近原则叠加生效。
- **过期不维护**。重构后命令变了文件没跟上，Agent 会拿着旧规则反复失败。把它当代码依赖对待：改了构建方式就顺手改它。
- **根目录与子目录冲突**。层级文件叠加后规则打架，Agent 行为会变得不可预测，需定期检查一致性。

## 可复用建议

- 放进 git，在 PR 里 review 对 Agent 行为的修改，与 review 代码同等对待
- 每次排障后问一句：这条教训能否变成文件里的一行？这是最有效的沉淀路径
- 密钥、内网地址绝不写入，它会进入模型上下文
- 团队协作场景下，它是对“AI 协作规范”最好的载体，比口头约定可靠得多

## 总结

AGENTS.md 的价值不在文件本身，而在于把“与 Agent 协作的经验”从聊天记录搬进版本库，变成可积累、可 review、可迁移的工程资产。建议每个 OpenClaw 工作空间都从一份 20 行的最小版本开始，让它随踩坑慢慢长大。
