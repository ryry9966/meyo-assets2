## 背景

玩 OpenClaw 自动化一段时间后，你会发现一个反直觉的事实：**"只执行一次"在工程上几乎不可能保证**。定时任务可能因调度器重启被补跑；webhook 通常是 at-least-once 投递；agent 调工具超时后框架会自动重试；更别提你自己手动"再跑一遍"的场景。

所以真正的问题不是"怎么保证只跑一次"，而是"跑多次也没关系"。这就是幂等性。

## 问题

幂等指的是：同一操作执行一次和执行多次，最终结果一致。

而自动化里最常用的几类操作恰好都不幂等：往文件追加一行、往群里发一条通知、创建一张工单、git commit 一次。两个真实场景：

- 每日摘要 cron 发 IM 消息，网络超时但消息其实已发出，重试后群里出现两条一样的摘要；
- agent 的"创建 issue"工具调用超时，agent 判定失败并重试，仓库里出现两个重复 issue。

超时 ≠ 失败，但副作用已经发生。这就是为什么幂等必须做在"产生副作用的那一端"，不能指望上层判断兜底。

## 做法

一个可落地的流程：

1. **盘点步骤**：把任务拆开，逐个标注幂等（覆盖写、upsert、纯读）或非幂等（create、append、send）。
2. **定义幂等键**：为每个"逻辑任务"生成稳定键，比如 `digest-<日期>`、`sync-<仓库>-<commit>`。注意在重试循环**外**生成，整个重试期间复用同一个键。
3. **先查后做**：执行前查键，命中则直接返回上次的结果，不再执行副作用。
4. **改写非幂等操作**：append 改为覆盖写固定路径；create 改为 upsert 或依赖唯一约束的 find-or-create；发消息前先落"已发送"记录，发送与记录尽量原子完成。
5. **按步骤推进重试**：用状态机记录已完成步骤，失败重跑从断点继续，而不是整个任务从头来。
6. **对齐 TTL**：幂等键的存储有效期要大于最大重试窗口，否则隔天补跑时键已过期，去重失效。

## 踩坑点

- **check-then-act 不是原子的**：两个并发触发同时通过"查键"，然后各自执行。正确姿势是靠唯一约束、`SETNX` 这类原子操作抢占，而不是先查再做。
- **键里掺了时间戳或随机数**：每次重试生成新键，等于没做。
- **键太粗**：所有日报共用一个键，第二天的任务被误吞。
- **去重命中返回了错误**：上游看到失败又触发新一轮重试。命中时应返回原始成功结果。
- **"看似只读"的操作有隐性副作用**：LLM 调用按 token 计费、自动创建的监控项和定时器，重跑都是成本。

## 可复用建议

- 新接自动化时先问一句："这个任务被触发两次会怎样？"——把这个问题写进你的任务模板。
- 优先选带 overwrite/upsert 语义的工具和 API；自己写 MCP 工具时，主动接受调用方传入幂等键。
- 定期做"跑两遍"测试：同一输入连跑两次，diff 产出。多出一份文件、多出一条消息就是红灯。
- 幂等和重试是一对搭档：有了幂等才敢放心开重试；没有幂等，重试只是副作用的放大器。

## 总结

分布式世界里 at-least-once 是默认现实，幂等才是让"重复执行"变得安全的设计。把它当成自动化的默认选项而不是事后补丁，你的 cron、webhook 和 agent 流程才敢于失败、敢于重来。
