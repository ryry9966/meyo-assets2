## 背景

绝大多数 Agent 的使用方式还是“你问、它答”：打开会话，输入指令，等结果。这在 demo 里没问题，但在日常使用里有个明显缺口——很多事不需要你问，它应该自己知道该办了。CI 挂了、磁盘快满了、仓库里来了新 issue、一个跑了两小时的任务结束了，这些都是明确的信号源。

在 OpenClaw 这类 gateway + agent runtime + MCP 工具 + 消息通道的架构里，做 proactive 的零件其实都齐了：定时任务、webhook 入口、工具调用、推送通道。缺的不是能力，是一条把“事件”变成“主动动作”的工程链路。

## 问题

两个我自己的真实场景：

1. 每天早上要手动问一句“昨晚 CI 有没有挂”，其实事件早就发生了；
2. 收到告警只有一条原始报错，还是得自己登机器跑命令定位。

Proactive 要解决的不是“更早通知你”，而是“带着上下文、在正确的时机出现”。理想状态是：告警来了，它先自己跑几个只读诊断，然后把“现象 + 初步归因 + 待确认的修复方案”一起推给你。

但直接把 agent 挂到事件源上会很快失控：噪音刷屏、误执行写操作、token 成本爆炸。这三个坑决定了它必须分层做。

## 做法：触发、过滤、决策三层

**第一层，触发层。** cron 定时器、webhook 监听、文件 watcher（写个薄插件接进来即可），统一产出同一种事件格式：`source / type / id / timestamp / payload`，写入队列。层与层之间用队列解耦，任何一段挂了都能重放。

**第二层，过滤层。** 纯规则，不花一分钱 token：去重 key（同一告警源 5 分钟内只放行一条）、静默时段、每日事件上限、按来源打优先级。实测 90% 以上的事件在这层就该被杀掉，这是整条链路里最重要的一段。

**第三层，决策层。** agent 只见过筛后的事件，用固定 schema 输出四选一：`ignore / log / notify / act`。`act` 只允许调用白名单内的只读 MCP 工具；任何写操作一律先生成 dry-run 结果和 diff，推给你等确认。输出通道也分级：紧急走即时推送，其余进每日 digest。

以告警场景跑一遍：webhook 收到错误率突增 → 过滤层确认该服务近一小时无同类事件 → agent 拉最近日志和指标，归因到两小时前的一次发版 → 推送“错误率上升，疑似 v1.8.2 引入，回滚方案已备好，回复确认即执行”。这才叫 proactive，而不是把原始告警换个渠道再发一遍。

## 踩坑点

- **噪音失控**：一个服务抖动，一晚上推了 200 条。解法是聚合窗口 + 同 key 抑制 + 每日打断上限，超限自动降级进 digest。
- **权限过大**：proactive 等于无人监督执行。有过一次它“顺手”重启了容器的经历，之后所有写操作强制确认，白名单之外一律 dry-run。
- **成本压不住**：别让原始事件直接进大模型。规则先杀，剩下的用小模型做初筛分类，大模型只处理需要归因的。
- **决策发散**：不固定输出 schema 时，模型总想“顺便”多做一步。降 temperature，schema 校验不通过就丢弃重试一次。
- **幂等**：webhook 平台重发过一次事件，同一动作执行了两遍。所有 act 必须带幂等 key。
- **静默期**：被半夜的消息吵醒一次之后，时区和 quiet hours 配置就再也没漏过。

## 可复用建议

1. 先只做“只读 + 通知”，稳定跑两周、误报率可接受后，再逐步放权给写操作。
2. 把“打扰政策”显式写进 system prompt：什么值得打断你、什么进 digest，别靠模型自己悟。
3. 事件 id 全链路透传，审计日志按 id 串起来，排障基本靠它。
4. 决策层保持无状态、可重放：拿历史事件回放调 prompt 和阈值，别等线上再翻车。

## 总结

Proactive 不是一个 prompt 能解决的事，而是触发、过滤、决策、执行四段工程。真正的门槛不在模型聪不聪明，而在过滤层敢不敢杀、执行层守不守得住。一个好用的主动助手，特征恰恰是克制：它少说话，但每句话都有用，你才会放心把“主动权”交给它。
