## 背景

用 OpenClaw 一段时间后，MCP、插件接了一圈，但交互模型仍然是拉模式：你不开口，它不动。其实 OpenClaw 内置了一个常被忽略的机制——heartbeat（心跳）：Gateway 按固定间隔（默认 30 分钟）唤醒一次 agent，把 workspace 里的 `HEARTBEAT.md` 注入当次上下文，让模型自己判断“有没有值得主动做的事”。这个文件就是主动行为的全部契约。

## 问题

常见两种失败方式。一是从没写过这个文件，心跳空转，白白烧 token；二是写成了愿望清单，agent 每半小时发一条“一切正常”式的问候，一周后你开始无视它。主动性的工程难点不是“能不能做”，而是“什么时候该闭嘴”。

## 做法

1. **在 workspace 根目录建 `HEARTBEAT.md`**。它会被注入每次心跳 prompt，所以先立规矩：控制在 30 行以内。
2. **每条任务写成三段式：触发条件 / 动作 / 静默条件**。例如：

```markdown
# Heartbeat checklist
- 检查 workspace/inbox.md 是否有新增未处理条目；
  有则整理成摘要发到当前会话；无则保持沉默。
- 检查日历未来 2 小时内的事件，仅当事件含 [prep] 标签时才给出准备建议。
- 若所有检查均无需动作，返回 HEARTBEAT_OK，不要发送任何寒暄。
```

`HEARTBEAT_OK` 是约定俗成的哨兵值：返回它表示无事发生，不落消息。

3. **间隔按任务性质定**：提醒类 15–30 分钟足够，巡检类放到小时级。在 agents 配置里调整心跳间隔，或对单个 agent 单独覆盖。
4. **动作必须幂等**：动作前先查状态（“今天是否已提醒过”），否则会重复轰炸。心跳默认跑在独立会话，不污染主聊天上下文；需要跨心跳记忆时，让 agent 把状态写回一个小文件（如 `sent-log.md`），下次读它判重。
5. **重活别放心跳**：心跳会话有超时和上下文上限。批量任务交给 cron 事件或独立脚本，心跳只做“看一眼、决定要不要叫人”。

## 踩坑点

- **文件写太长**。30 行变 300 行，token 成本按心跳次数相乘，且注意力被稀释后反而漏检。
- **没写静默条款**。默认行为是“有 prompt 就要回复”，不明确授权沉默，它就会硬找话说。
- **非幂等动作**导致同一件事提醒三遍。
- **心跳和 cron 职责混淆**：精确到点的定时任务用 cron（到点触发），模糊的周期检查用 heartbeat（轮询 + 自行判断）。
- **模型选型**：如果部署支持给心跳会话单独配模型，用便宜够用的——判断“要不要叫人”不需要旗舰模型。

## 可复用建议

- 把 `HEARTBEAT.md` 当**值班手册（runbook）**写，而不是愿望清单。每周复盘一次：删掉从未触发的条目，补上“希望它当时能发现”的条目，并纳入 git 版本化。
- 主动消息要“挣得”发送权：每条主动消息都应能回答“如果它没发，我会错过什么”。
- 先从一条规则起步跑一周，观察触发频率和误报率，再逐步加。 宁可少而准，不要多而噪。

## 总结

heartbeat 的价值不是让 AI 包办一切，而是用很低的成本让它盯住你明确授权的几件事。写好这个文件的核心约束只有一条：**事无必要，保持沉默**。主动性越克制的 agent，长期越可用。
