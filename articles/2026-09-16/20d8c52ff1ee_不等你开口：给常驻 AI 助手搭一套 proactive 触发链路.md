## 背景

现在大部分“AI 助手”本质还是问答机：用户发消息，助手回消息，会话结束就沉寂。真正意义上的 proactive，是助手自己感知状态变化，在没人开口的前提下把事情推到面前——磁盘快满了先告警，日报到点自动汇总，PR 有新评论顺手摘出来。OpenClaw 这类常驻网关型助手天然适合做这件事：有稳定进程、常驻会话和工具调用能力，缺的只是一套触发与降噪机制。

## 问题

把 proactive 做砸很容易，核心是三个矛盾：

1. **触发靠什么？** 硬编码轮询太死，全靠模型自由发挥又不可控。
2. **打扰成本。** 推多了用户直接静音，信任一次性花光。
3. **无人值守的权限边界。** 定时任务半夜跑，高危工具谁来批准？

## 做法

我目前的落地结构分四层，可以直接照抄：

1. **事件源。** 三类够用：cron 定时巡检（每日 8:30 日报）、webhook 接外部事件（GitHub、监控告警）、文件/状态探针（磁盘、证书过期）。
2. **触发判定。** 事件不直接推给用户，先进入一个“值班的” agent session，系统提示只干一件事：对照规则判断 `should_notify`，输出结构化 JSON 并附 reason。判定阈值写死在提示里，比如“磁盘 >85% 必报；CPU 瞬时峰值不报；同一问题 24h 内不重复报”。
3. **动作执行。** 判定为真才把摘要推到用户常用的消息渠道；进一步可以授权直接执行低危动作（重试、清理临时文件），高危动作只推“建议 + 一键确认”。
4. **会话隔离。** 每个 proactive 任务独立 session、独立系统提示、独立历史保留策略，避免巡检的中间过程污染用户主动对话的上下文。

## 踩坑点

- **自触发循环**：助手把告警发到群里，自己又监听群消息，把告警当成新事件再处理一遍。事件入口必须带来源标记，自己发出的消息直接丢弃。
- **上下文膨胀**：巡检 session 不清历史，一周后 token 账单很难看。巡检类任务建议滚动保留最近 N 条即可。
- **幂等性**：webhook 重试导致同一 PR 通知三次。事件侧做去重键，处理侧记录已处理 ID。
- **静默时段**：夜间告警堆到早上统一 digest，比实时轰炸体验好得多。
- **权限**：无人值守会话默认禁用写类工具，白名单逐个放行，别图省事全开。

## 可复用建议

- **先只读，后写入。** 汇总、提醒这类只读 proactive 先跑两周，观察误报率，再逐步放开低危写操作。
- **判定用结构化输出，别让模型直接发消息。** 中间隔一层 JSON，阈值就能在代码里调，不用反复改提示词。
- **所有主动行为落日志**（时间、触发源、是否推送、reason），一周后回看，阈值怎么调一目了然。
- **频率上限比智能判定更管用**：单任务每小时最多推 1 条，全局每天设上限，简单粗暴但保命。

## 总结

Proactive 的本质不是让模型更聪明，而是工程问题：触发源、判定层、降噪、权限。把这四件事做扎实，助手才会从“你问它答的工具”变成“不等你开口的同事”。建议从一个日报类任务开始跑通全链路，再逐步扩展——千万别一上来就让它替你干写操作。
