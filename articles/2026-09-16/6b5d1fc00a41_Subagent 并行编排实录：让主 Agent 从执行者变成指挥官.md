### 背景

用 OpenClaw 做了一段时间自动化后，最明显的瓶颈不是模型能力，而是主会话：查资料、改代码、写文档，所有任务都挤在一个上下文里排队执行。任务一多，主上下文迅速膨胀，响应变慢，而且任何一个环节卡住，后面全部阻塞。

OpenClaw 的 subagent 机制提供了另一个思路：主 agent 只负责拆任务、发任务、收结果，每个 subagent 有自己独立的会话和上下文窗口，互不污染。这篇帖子记录一次把周报流水线改成并行编排的完整过程。

### 问题

具体场景：每周固定任务——跟踪十几个仓库的更新日志，逐个总结，汇成一份 Markdown 报告。原来的做法是主 agent 一个接一个跑，实际体验：

- 串行跑完全程约 40 分钟；
- 中间产物（每个仓库的原始摘要）全部堆在主上下文里，跑两三轮后回答质量明显劣化；
- 第 8 个仓库请求失败时，流程直接中断，需要人工介入续跑。

### 做法

改成 subagent 编排后，流程固定为四步：

1. **拆分**：主 agent 把任务拆成 N 个自包含子任务，一个仓库一个 subagent，交付物写到独立文件（如 `notes/repo-xxx.md`）。
2. **写简报**：给每个 subagent 的任务简报必须自包含——输入路径、输出路径、格式模板、约束条件，全部写死。不要假设它能“看到”主会话。
3. **并发控制**：同时最多 3~4 个 subagent，剩余排队。简单的信号量就够，不必上复杂调度。
4. **验收合并**：全部落盘后，主 agent 只检查文件是否存在、格式是否符合模板，抽查一两份内容，然后合并成报告。中间产物始终不进主上下文。

改造后同样任务 12 分钟左右跑完，主会话上下文几乎不增长。

### 踩坑点

- **subagent 没有主会话记忆**。第一版简报没给格式模板，每个 subagent 自由发挥，合并时格式五花八门。简报里必须显式给模板路径。
- **并发写同一个文件必炸**。早期让所有 subagent 直接 append 同一份报告，内容交错损坏。规则：一个任务一个文件，最后统一合并。
- **并发数不是越大越好**。试过 6 路并发，直接触发限流，重试风暴让情况更糟。3~4 路是经验上的甜点区。
- **子任务会卡死**。有一次某个 subagent 挂了 20 分钟，主 agent 一直在等。后来加了超时：超时任务标记失败，先合并已完成部分，失败的单独重跑。
- **成本乘以并发数**。简报啰嗦，每个 subagent 都在烧 token。简报要像配置文件一样精炼。

### 可复用建议

- 一个 subagent 只交付一件事，交付物落盘为文件；
- 简报自包含：输入、输出路径、模板、约束，一样不缺；
- 主会话只接收路径和一句话摘要，不接收全文；
- 并发 3~5 起步，确认无限流再逐步加；
- 失败任务单独重试，不要整体重来；
- 主 agent 定位为拆分器 + 验收器 + 合并器，尽量不亲自执行。

### 总结

subagent 编排的收益，与其说是“快”，不如说是“隔离”：上下文隔离让主会话保持干净，任务隔离让失败可以局部重试。真正难的不是并发本身，而是把任务简报写清楚、把交付物定义清楚。建议从自己手上一个真实的周期性任务开始，先跑 2~3 个 subagent 的并行，把简报模板迭代两三轮，再考虑扩大规模。
