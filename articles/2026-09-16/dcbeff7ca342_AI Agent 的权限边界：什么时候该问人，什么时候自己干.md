# AI Agent 的权限边界：什么时候该问人，什么时候自己干

## 背景

Agent 早就不是"只会聊天"的东西了。接上 MCP、插件和 shell 工具之后，模型能直接产生真实副作用：写文件、调 API、发消息、改配置。OpenClaw 这类常驻框架更是把"自动执行"变成了默认状态——你不在屏幕前，它也在干活。

于是问题从"能不能做"变成了"该不该自己做"。

## 问题

实践中就两种典型翻车：

1. **什么都不问**。一次"顺手清理"删掉整个目录，一段"优化后"的配置直接覆盖了线上文件。事后回看日志，每一步模型都"有理由"。
2. **什么都问**。每读一个文件、每写一行代码都弹确认。人很快变成橡皮图章，无脑点"允许"，真正的危险操作反而淹没在确认流里。

本质是一样的：权限边界没有按**风险**设计，而是按"写起来方便"设计。

## 做法：按可逆性 × 影响范围分级

把每个工具动作丢进四象限：

- **可逆 + 低影响**：自动执行，全量记录。读文件、查数据、沙箱内写入都归这类。
- **可逆 + 高影响**：可以自动执行，但必须有回滚手段（git、备份、幂等接口），事后通知。
- **不可逆 + 低影响**：给个小额度免确认，比如单次发一条消息，超了就问。
- **不可逆 + 高影响**：必须人工确认，且确认内容要人能判断。

落地步骤：

1. 盘点接入的 MCP 工具和插件，逐个打标：只读 / 可逆写 / 不可逆。
2. 只读和沙箱内可逆写默认放行，tool call 全量留日志。
3. 不可逆 + 高影响动作加确认门。确认请求必须包含四件事：**要执行什么、目标对象、影响范围、怎么回滚**。
4. 批量操作合并为一次确认（"将删除 37 个文件，清单如下"），而不是弹 37 次。
5. 确认设超时策略：超时默认拒绝（fail closed）。宁可重跑一次，不要赌。
6. 定期回看日志：从没被拒绝过的低风险确认，降级为自动执行；被拒绝过的，升级管控。

## 踩坑点

- **确认疲劳**：问得太碎，人就不再思考。确认是稀缺资源，宁少问、问到位。
- **确认上下文不足**："是否继续？"这种问题人没法判断。确认请求本身要信息完整，最好带 diff。
- **组合逃逸**：单个工具安全，组合起来越权。比如"可写任意路径 + 可执行脚本"，等于绕过所有限制。路径白名单必须落在工具网关/配置层，不能指望 prompt 约束——模型会被长上下文带偏。
- **静默降级**：人不在，agent 等超时后"先干了再说"。确认失败必须终止任务，绝不能 fail open。

## 可复用建议

- 每接一个新工具先问三句：动什么？能不能撤销？最坏影响多大？
- 默认拒绝，逐项放行；放行用白名单，不用黑名单。
- 所有副作用操作留日志：谁、何时、改了什么。
- 高危确认模板固定化，永远包含 diff 和回滚方案。
- 每月按实际拒绝记录审一次权限表，动态调级。

## 总结

权限边界不是"问不问人"的二选一，而是按可逆性和影响范围做分级路由。目标既不是让 agent 更听话，也不是让人更省事，而是让每一次人工介入都花在真正需要判断的地方。别把确认弹窗用成橡皮图章——等你真的需要人把关时，它才关得住。
