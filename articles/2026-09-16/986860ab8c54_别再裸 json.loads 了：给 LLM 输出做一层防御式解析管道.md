## 背景

在 OpenClaw 插件、MCP 工具和自动化脚本的开发里，让模型返回结构化结果是高频需求：工具参数填充、意图路由、信息抽取，都依赖 JSON。提示词里通常写一句"只输出 JSON"，开发者就 `json.loads` 了事。跑得通，直到某天批量任务集体失败。

## 问题：JSON 很少"纯净"地到达你的代码

实际跑下来，输出污染形态大致有五种：

1. 被 markdown 围栏（```json ... ```）包裹；
2. 前后带解释性文字，"好的，以下是结果：{...}";
3. 推理模型的 `<think>` 标签残留在正文里；
4. 语法瑕疵：尾逗号、单引号、中文全角引号；
5. 流式消费时拿到半截 JSON。

任何一种都会让裸解析直接抛异常，整条自动化链路中断。

## 做法：分层解析管道

原则是**先无损、后有损；先结构、后修复**，逐层降级：

```python
import json, re

def parse_llm_json(raw: str):
    candidates = [raw]
    m = re.search(r"```(?:json)?\s*(.*?)```", raw, re.S)
    if m:
        candidates.append(m.group(1))
    cleaned = re.sub(r"<think>.*?</think>", "", raw, flags=re.S)
    candidates.append(cleaned)
    candidates.extend(extract_balanced_objects(cleaned))
    for c in candidates:
        try:
            return json.loads(c)
        except json.JSONDecodeError:
            continue
    return json.loads(light_repair(cleaned))
```

关键在 `extract_balanced_objects`：扫描文本中的花括号，维护深度计数，遇到引号就进入"字符串跳过模式"直到闭合——否则字符串值里的 `{}` 会把计数搞乱。它能从混合文本里截出第一个语法完整的 JSON 对象。

`light_repair` 只做低风险修复：去尾逗号、替换全角引号。解析成功后还要过一遍 pydantic/JSON Schema 校验；校验失败就把错误信息回喂给模型重试，上限两次。

## 踩坑点

- **贪心正则**：`\{.*\}` 会把两段 JSON 之间的说明文字一起吞进来，`\{.*?\}` 又会在嵌套对象处提前截断。别用正则做截取，用括号平衡扫描。
- **字符串里的括号**：不带跳过模式的括号计数器是重灾区，`"pattern": "{a}"` 就能击穿它。
- **修复层过猛**：把模型真正答错的内容"修"成了合法但错误的数据，比解析失败更危险。所以修完必须过 schema 校验。
- **流式场景**：别攒完整文本再解析，等括号深度归零即可切分增量处理。
- **不留现场**：解析失败时务必把原始输出写日志，否则无法归因是提示词问题还是解析器 bug。

## 可复用建议

- 解析逻辑收敛到一个共享模块，全项目走同一条管道，别每个插件各写一套。
- 能用 provider 的结构化输出或工具调用约束时优先用，防御式解析只是兜底，不是替代。
- 把"解析失败率"当成一个指标记录，突增往往意味着模型版本或提示词被改动了。
- 修复规则按风险排序：格式类（剥围栏、去空白）> 语法类（尾逗号）> 语义类（尽量避免自动改写）。

## 总结

防御式解析不是让代码去"猜"模型想说什么，而是承认一个工程事实：LLM 输出天然不可控。用确定性的分层管道把这份不确定性收敛掉，上层业务代码才能保持简单。这套管道在 OpenClaw 的工具调用场景里可以直接复用，改造成本很低。
