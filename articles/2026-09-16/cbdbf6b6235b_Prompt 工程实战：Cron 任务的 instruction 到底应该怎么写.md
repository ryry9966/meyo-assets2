## 背景

OpenClaw 的 cron 能力，本质上是"到点唤醒一个 agent，把 instruction 当 prompt 执行"。很多人把 instruction 写成聊天消息——"早上帮我看看 inbox 有什么新的"。聊天里这么说没问题，因为有上下文兜底；但 cron 是无人值守执行，调度器不会替你补上下文。instruction 写得好不好，直接决定任务是"工程"还是"许愿"。

## 问题

我自己踩过、也在群里见过几类典型失败：

- 任务到点执行了，但推了五百字长文到频道，噪音大到想关掉；
- instruction 里写"今天"，agent 拿不准日期/时区基准，输出错位一天；
- 引用了上次会话里的某个文件，但 cron 跑在隔离会话里，路径失效；
- 工具调用失败后，agent 编了一个"看起来成功"的结果，无人察觉。

共同根因只有一个：把 cron instruction 当成了对话，而它其实是一次**无状态的任务声明**。

## 做法

我现在的写法，是把每条 instruction 当一个微型 system prompt，固定五段：

1. **时间基准**：开头一句"执行前先读取当前系统时间与日期"。把"今天/昨晚"换成"过去 24 小时"这类可计算的表述，容器时区是 UTC 时尤其关键。
2. **任务与边界**：做什么、不做什么。例如"只检查 `~/notes/inbox` 下 24h 内新增的文件"，范围写死。
3. **工具与顺序**：点名用哪个工具/MCP，失败怎么办。例如"调用 fetch 工具；若失败，回复'数据源不可用'并结束，不要编造数据"。
4. **输出契约**：格式、长度、去向。比如"不超过 3 条要点，每条一行，发送到 #daily；若无新增内容，只回复'无事'"。
5. **幂等约束**：动作前先检查。"发送前确认今日未推送过相同摘要，已推送则跳过。"

一个实际例子：

```text
先读取当前系统时间。
任务：汇总 ~/.openclaw/workspace/inbox 中过去24小时新增的 md 文件。
步骤：1) 列出文件；2) 逐个读取，每个提炼1条要点。
若无新增文件：仅回复"无更新"，不要调用发送工具。
输出：3条以内，每条一行，发送到 channel #daily。
失败处理：单个文件读取失败则跳过并在末尾注明，不要中断整体。
```

## 踩坑点

- **相对时间词漂移**："昨天""本周"必须换成可计算的表述，否则换个时区就错位；
- **依赖会话记忆**：cron 常在隔离会话执行，引用文件一律绝对路径；需要的历史信息，让它先读固定文件或 memory，不要假设"它记得"；
- **没有"无事可做"分支**：不写"若无更新只回一句"，agent 会硬凑内容交差；
- **指令过长且互相矛盾**：超过十几行的 instruction 优先级会打架。复杂逻辑应沉淀成脚本，instruction 只负责调度、摘要与异常汇报；
- **直接上线**：一定先手动触发跑一次，看真实输出再挂表达式。模拟和真实执行差得比你想象的多。

## 可复用建议

- 建一个自己的五段模板（时间基准/任务/步骤/输出/失败处理），新任务复制改，别从零写；
- cron 配置纳入 git，改 prompt 走 commit，出问题能回溯"是哪次改动让任务变坏"；
- 任务命名带频率与目的，如 `daily-inbox-digest`，排查时不用猜；
- 原则一句话：**逻辑下沉到脚本，instruction 保持薄**，agent 只做调度、摘要和异常上报。

## 总结

Cron instruction 不是"跟 agent 说话"，而是给一个无状态执行者写任务规格。时间基准、边界、输出契约、失败分支、幂等——这五样写清楚，定时任务才从碰运气变成可依赖的基础设施。
