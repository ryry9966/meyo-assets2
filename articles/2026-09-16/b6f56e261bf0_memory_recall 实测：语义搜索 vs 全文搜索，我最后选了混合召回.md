## 背景

OpenClaw 这类常驻 Agent 的记忆层大同小异：助手把值得记住的事实（用户偏好、项目约定、排障结论）写成一条条小笔记存进本地库，对话时通过 memory_recall 按当前话题捞回最相关的几条注入上下文。捞得准不准，直接决定助手是"贴心"还是"复读机"。

捞回手段基本两派：全文搜索（SQLite FTS5、BM25 这类关键词匹配）和语义搜索（embedding 向量 + 余弦相似度）。我最近在自己的实例上实测过一轮，结论记录如下。

## 问题：两派各自会在哪里翻车

全文搜索的强项是精确 token：错误码、文件路径、函数名、配置项。问 "ECONNRESET 那次怎么解决的"，一击即中。弱点是换个说法就抓瞎——搜"部署脚本报错"，找不到当时记下的"CI 流水线超时"。

语义搜索正好相反：同义改写、中英混述都能命中，但遇到纯技术标识符经常失灵——embedding 把 `kubectl rollout undo` 和其他 K8s 笔记都算得很像，却不保证这条具体命令排前面。另外它要求维护 embedding 模型和向量存储，多一份基础设施。

本质问题是：memory_recall 是召回问题，两种方法各有系统性盲区，单选哪边都会在特定 query 上稳定失败。

## 做法：先基线，再融合

1. **建黄金集。** 从历史会话挑 30~50 组"query → 应召回哪条记忆"的样本。没有它，选型就是玄学。
2. **先上全文基线。** SQLite FTS5 一张表加索引，半小时搞定，跑黄金集记 recall@5。记忆只有几百条时，全文 + 时间衰减可能已经够用，可到此为止。
3. **补语义通道。** 记忆切块后过 embedding（中英混存必须选多语言模型），向量存本地，同一黄金集再跑一遍，单独记录两路命中情况。
4. **混合召回。** 两路各取 top-20，用 RRF（Reciprocal Rank Fusion）合并——只看排名不看原始分数，天然回避两边分数量纲不可比的问题。融合后取 top-3~5 注入上下文。
5. **加精确通道。** query 里出现错误码、路径样式的 token 时，强制走一次 LIKE/正则匹配，命中直接置顶。

改完后黄金集 recall@5 从全文单路的 68% 提到 89%，提升几乎全部来自改写类 query——这正是语义层该干的活。

## 踩坑点

- **中文分词。** FTS5 默认按空格切词，中文整段被当成一个超长 token，等于不可用。要么上 trigram tokenizer，要么入库前先分词。我第一版就栽在这，看似"跑通"其实全靠英文 token 撑着。
- **embedding 版本漂移。** 换模型后旧向量全部作废，但不报错，只会悄悄劣化。向量旁必须存模型名和版本，不一致就全量重建。
- **绝对阈值不可靠。** 不同模型的余弦分布差异很大，0.75 在 A 模型是高相关、在 B 模型是噪声。用相对排名（RRF、top-k）远比调阈值稳。
- **陈旧记忆霸榜。** 冗长的老笔记在两路检索都容易排前。给召回分加时间衰减，或入库时控制粒度：一条记忆只说一件事。
- **召回过多反而变笨。** 灌 10 条进上下文，模型会被带偏。3~5 条，宁缺毋滥。

## 可复用建议

- 数据卫生 > 检索算法：条目短、原子化、带 tag 和时间戳，对召回质量的贡献比换算法大。
- 记忆库几百条以内别急着上向量，全文 + recency 往往是最优性价比。
- recall 命中/未命中打日志，定期拿真实 query 补充黄金集，这个反馈回路比任何一次选型都值钱。
- 精确标识符永远保留独立通道，这是语义搜索的结构性短板，别指望换模型解决。

## 总结

语义搜索和全文搜索不是二选一，而是互补的召回通道：一个覆盖"换了说法"，一个覆盖"精确标识"。正确的工程顺序是先建评测集、先跑便宜的基线，确认盲区后再加语义层并用 RRF 融合。memory_recall 的上限从来不是检索算法，而是你存进去的记忆本身有多干净。
