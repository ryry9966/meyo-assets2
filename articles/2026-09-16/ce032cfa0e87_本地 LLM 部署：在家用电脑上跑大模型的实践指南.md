## 背景

给 agent 体系配一个本地模型，动机通常很实际：数据不出门、没有按 token 计费、断网也能跑。自动化场景里 agent 调用频繁，一个 7B 量级的本地模型当常驻后端，成本几乎可以忽略。这篇帖子记录我在家用机上把本地模型接入 OpenClaw agent 链路的完整过程，重点不是"怎么跑起来"，而是"怎么稳定地给 agent 用"。

## 问题

家用硬件和数据中心的差距是硬约束：显存有限、吞吐有限，而 agent 场景对模型的要求比纯聊天苛刻得多——工具调用格式必须可靠、多轮上下文不能崩、长时间挂机不能悄悄掉线。跑通 demo 一小时就够，调到能日常值守是另一回事。

## 做法与步骤

**1. 先盘硬件，显存决定一切。** 8GB 显存可跑 7B Q4 量化；12–16GB 上 14B Q4 比较从容；24GB 可以摸 32B Q4 或 14B 高精度量化。纯 CPU 也能跑 7B，但 agent 多轮调用延迟会明显拖工作流。

**2. 选推理运行时。** 建议先用 Ollama 验证链路：自带 OpenAI 兼容接口、一条命令拉模型，出错概率最低。追求吞吐再迁移到 llama.cpp 或 vLLM。

```bash
ollama pull qwen2.5:7b-instruct-q4_K_M
OLLAMA_KEEP_ALIVE=-1 ollama serve
```

**3. 选模型时盯死工具调用能力。** 优先选官方支持 function calling 且经过工具调用微调的版本，社区魔改版质量参差，宁可参数小一点也要格式稳定。

**4. 接入 OpenClaw。** 把模型配置里的 base_url 指向 `http://localhost:11434/v1`，模型名填 Ollama 的 tag。接入顺序很重要：先跑纯对话验证连通，再逐个挂 MCP 工具，最后上完整工作流。

**5. 用真实任务压测。** 拿你日常的 agent 工作流连续跑 20 轮，记录工具调用成功率、首 token 延迟、显存峰值。这三个数字就是你后续换模型、调参数的基线。

## 踩坑点

- **上下文长度吃显存。** KV cache 随 ctx 线性增长，8k 上下文安然无恙，拉到 32k 直接 OOM。给 agent 设上下文窗口时务必留余量，工具返回的长文本也会进上下文。
- **工具调用格式不匹配。** 部分模型走 XML 或自定义格式，OpenAI 兼容层解析不了，agent 拿到的是空参数——症状是"模型答应了但什么都没做"。换模型前先单测一次 tool call。
- **冷启动陷阱。** Ollama 默认几分钟不活动就卸载模型，凌晨定时任务触发时首次调用冷启动 30 秒起步。设 `KEEP_ALIVE=-1` 常驻，或任务前预热一次。
- **温度没降。** function calling 场景把 temperature 压到 0.1–0.3，JSON 合法率提升非常明显。
- **别迷信参数量。** 一个通用 14B 未必稳赢专为 agent 微调的 7B，一切以自己任务的成功率实测为准。

## 可复用建议

1. **做一张显存预算表**：显存 → 量化等级 → 参数量，换机器时直接查表决策，不重头试。
2. **本地 + 云端双路由**：本地模型打头阵，低置信度或超长上下文任务回落云端，可靠性跳档。
3. **文件统一管理**：模型文件放独立大盘，用软链接挂到运行时目录，回滚换版本只需切链接。
4. **把压测脚本留下来**，每次换模型跑一遍，数据说话。

## 总结

本地部署的技术门槛这几年降得很快，真正的工程量在接入 agent 体系之后的稳定性调优——上下文预算、工具调用格式、常驻策略，这三件事比选哪个模型更值得花时间。建议路径：小模型跑通全链路 → 真实任务压测建基线 → 按显存余量逐步上探。一步到位不如每一步可验证。
