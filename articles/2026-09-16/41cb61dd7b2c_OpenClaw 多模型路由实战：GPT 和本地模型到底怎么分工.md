## 背景

OpenClaw 的模型接入不限定单一 provider，同一个 agent 可以声明多个模型：云端 GPT 走 API，本地模型走 Ollama / vLLM / LM Studio。跑了一段时间混合架构后，我最大的感受是：收益不主要是省钱，而是把任务分层——不同层级的任务配不同档位的模型。

## 问题

实践中最常见的两种极端：

- **全打 GPT**：日常摘要、格式转换这类杂活也用旗舰模型，账单涨得快，还把敏感上下文（日志、内部文档）送出了内网。
- **全换本地**：规划、多工具编排这类长链路任务质量明显下滑，agent 表现为"看得懂指令但做不对事"。

## 做法

我按三个维度划分路由：任务类型、上下文长度、敏感度。

| 任务 | 路由 |
|---|---|
| 规划 / 拆解 / 多工具编排 | GPT |
| 摘要 / 改写 / 分类 / 抽取 | 本地 7B–14B |
| 含敏感日志或私有数据 | 强制本地 |
| JSON 修复、格式化 | 本地 + 校验重试 |
| 兜底 | GPT（mini 档） |

配置示意（字段名以你的版本为准）：

```yaml
models:
  planner: gpt-4.1
  worker:  ollama/qwen2.5:14b
  fallback: gpt-4.1-mini

routing:
  sensitive: force_worker     # 标记敏感的任务强制本地
  context_over: 24000        # 超长上下文走 GPT
```

核心思路：把模型当成**可分配的资源**，在路由层决策，而不是靠提示词去"劝"。

## 踩坑点

1. **本地模型 function calling 质量参差**。Qwen 系还行，一些小模型在三层以上工具链会漏参数、幻觉调用名。上线前先跑 20 条固定用例。
2. **上下文窗口差异是静默失败**。本地模型塞不下时不会报错，可能触发截断或压缩，表现为"失忆"。长对话任务要在路由层就分流。
3. **采样参数别共享**。GPT 习惯的 temperature=0.7 放到本地小模型会放大跑偏，本地任务建议 0.2 以下。
4. **fallback 别做成回环**。本地失败→GPT→再回本地，很容易烧 token。给 fallback 加次数上限，并落日志。

## 可复用建议

- 每条请求记录 `model / 耗时 / token / 是否 fallback`，一周后你会发现 80% 的流量其实在做杂活——这就是下沉空间。
- 建 20–50 条黄金用例做回归集，每次换本地模型版本跑一遍，别凭感觉升级。
- 敏感路由做成**硬规则**而非提示词约束：提示词是劝，路由是断。
- 本地模型优先选对工具调用友好的（Qwen、Llama 3.x 及其微调），别只看跑分。

## 总结

多模型路由的本质不是省钱，而是把推理强度当作可以按任务分配的资源。规则不必复杂：**规划上云、杂活下沉、敏感强制本地、永远留兜底**。先把每条请求的模型和结果记录下来，再谈优化——没有数据的路由策略都只是猜测。
