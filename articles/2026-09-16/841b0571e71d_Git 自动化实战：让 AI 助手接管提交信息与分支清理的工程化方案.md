# 背景

用 OpenClaw 或任意 Agent 框架跑过一段日常开发后，会发现最容易被自动化的不是写代码，而是 Git 的机械操作：写 commit message、整理分支、生成变更摘要。这些活规律性强、容错率低、占时间——正好适合交给 agent。

# 问题

直接丢一句「帮我把代码提交了」，通常会撞上三个典型问题：

1. commit message 质量不稳定，不符合团队的 conventional commits 规范；
2. agent 拿到 shell 权限后什么命令都敢跑，`push --force`、`reset --hard` 一旦误执行就是事故；
3. 分支只增不减，三个月后仓库里躺着几十个已合并的 stale branch。

核心矛盾是：Git 的破坏性操作太多，而 agent 执行得太快。自动化必须先划边界。

# 做法

**第一步：收窄工具面。** 不要把裸 shell 交给 agent。用 MCP git server，或自己封装一层白名单脚本，只暴露 `status / diff / log / add / commit / branch / checkout -b` 这类低危命令；`push` 只允许普通推送，`reset --hard`、`clean -fd`、`push --force` 直接在封装层拒绝。

**第二步：注入仓库规范。** 在项目说明或 agent 的 system prompt 里写清楚：message 格式（如 `feat: xxx`）、分支命名（`feat/`、`fix/` 前缀）、哪些文件永不入库。规范写进配置，比指望 agent 每次自己悟靠谱得多。

**第三步：限定写操作范围。** agent 只做本地操作：暂存、提交、建分支、生成摘要。push 由人触发或走 PR 流程。这样即使出错，损失上限是本地一个 commit，`revert` 就能救回来。

**第四步：让 message 基于 diff 生成。** 流程固定为：`git diff --staged` → agent 阅读 diff → 输出 message → 人确认 → commit。禁止跳过看 diff 直接编 message，这是幻觉重灾区。

**第五步：分支清理做成周期任务。** 让 agent 每周跑一次：列出所有已合并到 main 的本地分支、超过 N 天无提交的分支，输出清理清单。删除动作必须人工确认，agent 只负责「发现」。

# 踩坑点

- **`add -A` 是最大的坑。** agent 图省事一把梭，把 `.env`、密钥、构建产物全提交了。对策：要求 agent 先列出待暂存文件清单，确认后再执行。
- **message 写了 diff 里没有的内容。** 我见过 agent 在 message 里「展望」了根本没实现的功能。要求每条 message 都能对应到 diff 中的具体变更，review 时对照检查。
- **冲突处理不能交给 agent。** rebase、merge 遇到冲突，agent 容易陷入反复尝试的死循环，甚至乱改代码迁就测试。规则写死：遇到冲突立即停止，转人工。
- **工作目录校验。** 多仓库场景下 agent 可能在错误目录执行 git 命令。封装层里每次操作前先 `git rev-parse --show-toplevel` 校验路径。

# 可复用建议

把上面的约束沉淀成三样东西随仓库走：一份工具白名单配置、一份规范 prompt 模板、一份命令审计日志（agent 执行的每条 git 命令落盘）。换 agent 框架、换 MCP 实现时，这三样可以直接迁移。另外建议给封装层加 dry-run 模式：agent 先输出执行计划，人点头再真跑。

# 总结

AI 助手管 Git 的正确姿势不是「放开手让它跑」，而是「机械活给它，破坏性操作锁死，远端操作留给人」。规范靠配置注入而不是 prompt 祈祷，风险靠工具面收窄而不是事后追责。按这套边界跑下来，commit message 质量明显稳定，分支也不再堆积——这才是 agent 在工程链路里该待的位置。
