## 背景

信息源越来越分散，算法推荐不可控，RSS 仍然是少数能自己说了算的订阅方式。但现实是：多数目标站点没有原生 feed，且每天几十上百条更新根本读不完。这篇记录我搭的一条管线：**定时抓取订阅源 → 结构化 AI 摘要 → 推送 IM + 归档**，全程可回溯。

## 问题

三个核心痛点：

1. **源不稳定**：一半站点没有 RSS，第三方转换路由经常静默失效；
2. **阅读成本高**：人只能筛，不能全读；
3. **直接丢给 LLM 不行**：token 账单和幻觉问题都很现实。

## 做法

分五个阶段，每阶段独立脚本，中间产物全部落 SQLite：

1. **源聚合**：原生 RSS 直接收；没有的用自建 RSSHub 实例转；订阅统一用 OPML 管理。
2. **定时抓取**：cron 每 30 分钟一轮，带 ETag / If-Modified-Since，返回 304 直接跳过；feed 只有摘要的页面，用 readability 做二次全文抓取。
3. **入库去重**：guid/link 归一化后取 hash 做主键，天然去重；跨源重复选题靠标题+摘要的 embedding 相似度（阈值 0.92）合并。
4. **两级摘要**：第一级用本地小模型给每条打重要度分（0–10）+ 一句话摘要，低于阈值的不进第二级；第二级用强模型按源分组生成日报，强制 JSON Schema 输出 `{title, one_liner, bullets[], tags[], score, source_url}`，校验失败重试一次。
5. **推送归档**：webhook 推到 Telegram/飞书，同时落一份 Markdown 日报到静态页。

如果接进 OpenClaw 的 agent 工作流，把第 2–4 步封装成 MCP tool，agent 就能按需"查一下今天关于某个主题的更新"，定时推送和主动查询两条路都通。

## 踩坑点

- **全文抽取比想象中难**：正文页有反爬和懒加载，readability 经常抽出评论区或推荐位。加长度下限检查（如 <200 字符就标记降级，只保留原文链接）。
- **摘要幻觉**：prompt 里明确"只能基于给定文本，原文没有的信息输出 unknown"，temperature 压到 0.2 以下，定期抽样人工核对。
- **重复选题**：按 URL 去重没用，不同源报同一件事很常见；但相似度阈值别调太低，0.9 以下会误伤系列文章。
- **RSSHub 路由静默失效**：表现是 item 数骤降而不是报错。加监控：每个 feed 记录近 7 天 item 数，跌幅超 50% 告警。
- **cron 重叠**：长摘要任务撞上下轮抓取，加文件锁或改用带超时的任务队列。
- **成本失控**：全量送大模型一个月账单很难看。两级过滤 + 本地小模型跑第一级，成本基本可以压到忽略不计。

## 可复用建议

- 每步中间产物落库，出问题可以单独重放某一步，不用整条管线重跑；
- 摘要 prompt 当代码管理，版本号写进库里，方便对比改版效果；
- 先订 5–10 个真会看的源跑两周再扩量，一上来导入 200 个源是新手最常见翻车点；
- 输出永远保留 `source_url`，摘要只是索引，深读仍回原文。

## 总结

这条管线没有用到任何高深的东西：RSS 标准化 + 定时抓取 + 两级模型 + 结构化输出 + webhook 推送，一个晚上能跑通 MVP。真正的价值在于**可控**：源自己选、阈值自己调、数据自己留。对做 agent 的同学来说，它同时还是一个现成的 MCP 数据源工具——信息获取这件事，自己搭一次，比依赖任何托管服务都踏实。
