## 背景

Agent 自动化真正跑起来之后，你会发现大部分线上故障不是模型出了问题，而是外部依赖出了问题。OpenClaw 插件调用的 LLM API、MCP 工具背后的搜索服务、数据库、第三方业务接口——任何一个 429、超时或 503，都可能打断整条任务链。测试时一切正常，长跑时必挂，这是常态而不是意外。错误恢复能力，某种程度上比单次任务的成功率更能决定一套自动化能不能上生产。

## 问题：三种典型的坏行为

1. **无脑重试循环**：收到报错后模型决定"再试一次"，重试策略由 LLM 自由发挥，容易陷入死循环，烧 token 也烧钱。
2. **幻觉式兜底**：工具返回错误，模型却编造一个"看起来合理"的结果继续往下走。这比直接失败危险得多——错误会沿着流水线传播。
3. **级联阻塞**：某个慢接口的超时设了 120 秒，整条流水线被一次挂起卡死，后续任务全部排队。

## 做法

**1. 错误分类先行。** 把错误分成可重试（429、503、超时、网络错误）和不可重试（400、401、404、配额耗尽）。后者重试没有意义，应直接走失败分支。

**2. 重试策略写进代码，不交给模型。** 指数退避 + 随机抖动，尊重 `Retry-After` 响应头，设最大重试次数（比如 3 次）和总时间预算。重试是确定性逻辑，LLM 不该做这个决定。

**3. 熔断与降级。** 连续失败 N 次后熔断，后续调用直接 fail fast，不再等超时。同时准备降级路径：备用 provider、可接受的过期缓存、跳过可选步骤、写入队列延后处理。

**4. 把失败诚实地暴露给 agent。** 工具报错时返回结构化信息：`error_type`、`retryable`、`suggested_action`，并在系统提示里明确"工具不可用时你可以跳过此步骤或询问用户，禁止编造数据"。

**5. 幂等与断点。** 在有副作用的边界（下单、发消息、写库）做 checkpoint 和幂等键，恢复时从断点继续，而不是从头重跑。

## 踩坑点

- **对非幂等操作盲目重试** → 重复下单、重复发消息。先保证幂等，再谈重试。
- **退避不加抖动** → 多个任务同时到期恢复，形成惊群效应，把刚缓过来的 API 再次打挂。
- **让 LLM 决定重试次数** → 它要么放弃太快，要么无限循环，两个方向都不对。
- **错误被 catch 后静默吞掉** → 下游拿着残缺数据继续跑，最终结果错得莫名其妙，排查成本极高。
- **熔断粒度太粗** → 一个接口挂了把所有依赖一起熔断，应该按 endpoint 隔离。

## 可复用建议

- 所有工具调用收敛到统一的 invocation 层：超时、重试、熔断、日志集中处理，各插件只写业务逻辑。
- 定义统一的错误契约，作为 MCP 工具返回值的一部分，长期保持稳定。
- 记录每个工具的错误率、延迟、重试次数，错误率突增时触发告警，别等用户来报障。
- 定期做故障注入：手动关掉某个依赖，看 agent 是优雅降级还是原地崩溃。

## 总结

错误恢复本质上是系统工程，不是 prompt 工程。原则一句话：**确定性策略放代码，创造性决策给模型，错误信息要诚实。** API 迟早会挂，好的 agent 不是不遇到故障，而是挂了之后清楚知道自己该重试、该降级、还是该停下来问人。
