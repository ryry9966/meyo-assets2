## 背景

社区里每周都有固定内容要发：版本更新摘要、精选 issue 汇总、新插件介绍。这些内容格式固定、来源明确，但手工整理很耗时间。于是我基于 OpenClaw 搭了一个发帖机器人，跑了四周，稳定发布 20+ 篇。这篇记录整体设计和真实踩过的坑，供想动手的同学参考。

## 问题定义

先明确边界：机器人只做三件事——**采集结构化素材、生成草稿、发布到论坛**。不做创意写作，不做自动回复，不追热点。边界越窄，系统越可控。

## 架构设计

整体分四层：

1. **采集层**：定时拉取 Git release、issue 流、插件仓库更新，输出结构化 JSON（版本号、变更列表、链接）。不经过 LLM。
2. **Agent 层**：OpenClaw 运行时，挂载三个 MCP 工具——`get_pending_material`（取素材）、`submit_draft`（提交草稿）、`publish_post`（发布）。System prompt 严格限定只能引用素材字段。
3. **调度层**：cron 插件触发，任务状态存 SQLite，不存内存。
4. **审核层**：草稿先进待审队列，我在移动端点确认后才真正发布。

设计原则只有一条：**LLM 只负责组织语言，不负责生产事实**。

## 踩坑实录

**坑一：重复发帖。** 第一周 cron 偶发双触发，同一内容发了两遍。修复：发帖前对正文做内容 hash，与最近 7 天发布记录比对；同时在 `publish_post` 里引入幂等键（素材 ID + 日期）。

**坑二：模型幻觉。** 初版 prompt 写得宽松，模型会把"修复了若干问题"扩写成不存在的功能描述。修复：prompt 明确禁止补全素材外信息，且 `submit_draft` 工具校验草稿中出现的版本号必须存在于素材 JSON，不匹配直接打回。

**坑三：MCP 工具重试导致重复提交。** 网络抖动时客户端重试，论坛端收到两次请求。修复：`publish_post` 返回论坛帖子 ID，客户端超时后先查询再决定是否重发，而不是盲目重试。

**坑四：论坛 API 限流。** 批量补发历史内容时连续 429。修复：加了简单的令牌桶 + 指数退避，频控逻辑放在工具层而不是 Agent 层——让模型自己控制频率是不可靠的。

**坑五：全自动质量下滑。** 试过跳过人审全自动发布，两周后明显感觉到内容模板化。结论：草稿生成全自动，发布保留人工确认。这一个按钮的成本，换来的可控性非常值。

## 可复用建议

- 先自动化"生成草稿"，再考虑自动化"发布"，分两步走。
- 所有跨进程状态落 SQLite 或等价存储，重启不丢任务。
- 每个写操作工具都设计幂等键，重试是常态而非异常。
- 日志完整记录 prompt、工具入参出参，排障时能精确回放。
- 频控、校验这类确定性逻辑放工具层，不要指望模型自觉。

## 总结

这套架构的核心不是让模型更聪明，而是把不可控的部分（生成）圈在最小范围，把可控的部分（校验、频控、幂等）做成确定性代码。四周下来，每周节省约两小时整理时间，误发率为零。代码量不大，核心逻辑几百行，有兴趣的同学可以按这个分层自己搭一版，踩坑欢迎回来补充。
