## 背景

现在的 AI 助手大多是“应答机”：用户发消息、模型回复、会话结束。但在 OpenClaw 这类可以挂 MCP 工具、跑常驻进程的框架里，Agent 完全有能力“自己醒过来”——定时巡检 CI 状态、监听日志关键词、到点提醒待办。我们最近给团队的运维助手加了一层 proactive 触发机制，跑了三周，这里把设计和踩过的坑记下来。

## 问题：主动 ≠ 勤快

让 Agent 主动做事，难点不在“怎么调模型”，而在三个工程问题：

1. **触发**：Agent 默认是被请求唤醒的，谁来唤醒它？
2. **决策**：醒来之后，怎么判断“这件事值得打扰用户”？
3. **行动**：判定要做之后，怎么安全执行并留痕？

## 做法：触发 → 决策门 → 执行

我们的链路分三层：

1. **触发源接入**。cron 定时任务和 webhook 事件统一投递到同一个队列，事件只带最小上下文（类型、来源、时间戳），外加一个 dedup key。
2. **上下文组装**。Agent 被唤醒后，先通过 MCP 工具实时拉取当前状态（查最新 CI 结果、读指标），而不是信任事件携带的信息——事件可能滞后。
3. **决策门**。用一段轻量 prompt 让模型先输出结构化判断 `{should_notify, reason, severity}`，只有 `should_notify` 为 true 才继续。severity 决定渠道：低的进每日摘要，高的立即推送。
4. **执行与留痕**。动作走 MCP 工具完成，每次「触发→决策→动作」写一条结构化日志，方便回溯误报。

## 踩坑点

- **误报轰炸**：第一天 CI 失败直接推给所有人，一下午十几条，群里集体屏蔽。加 severity 分级 + 15 分钟静默窗口后才恢复。
- **上下文过期**：cron 唤醒时拿缓存状态做判断，告警的是两小时前的旧问题。教训：决策前必须实时拉取。
- **幂等缺失**：webhook 重试导致同一事件触发两次、发两条通知。dedup key 是刚需，不是优化项。
- **成本失控**：日志监听最初每分钟跑一次，token 消耗是预期的十倍。改成“关键词命中才唤醒”，而不是“每次都让模型看一遍”。
- **权限越界**：曾允许 Agent 自动重启服务，某次误判后重启了发布中的实例。现在所有不可逆操作必须人工确认。

## 可复用建议

- 从低风险高频场景起步：日报、摘要、监控告警，先建立信任再谈自动执行。
- 感知、决策、执行三层分离，决策层保持无状态、可重放。
- 给每个触发源独立的频率预算和静默配置，别共享一个全局开关。
- 把“用户是否忽略/点击通知”作为反馈信号回收，持续校准 severity 阈值。
- 不可逆动作一律 human-in-the-loop，没有例外。

## 总结

Proactive 能力的价值不在“模型多聪明”，而在触发-决策-执行这条链路的工程质量。误报和成本控制住了，用户的主动才不会被当成骚扰。先让 Agent 学会“什么时候该闭嘴”，它主动做事的资格才算拿到。
