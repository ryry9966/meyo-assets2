## 背景

我们团队每天要交一份日报，内容散落在 git 提交、CI 运行记录、工单系统和服务器日志里。过去的流程是：下班前半小时，几个人各自翻记录、拼段落、发群里。重复了两周之后我受不了了，决定用 OpenClaw 搭一条流水线，让日报在每天固定时间自动生成。

## 问题

直接把原始日志丢给 Agent 说"写个日报"，听起来简单，实际有三个坑：

1. 日志总量大，动辄几十万行，直接进上下文既贵又不稳定；
2. LLM 对数字不老实，完成率、耗时这类指标一旦让它自己"算"，就可能编；
3. 没有固定结构，昨天一份格式今天一份格式，没法归档和对比。

所以核心设计原则定为：**数字由脚本算，文字由模型写，结构由 schema 定。**

## 做法

整条流水线分四步，由一个定时任务串联：

**第一步：采集。** Python 脚本按时间窗口（前一天 00:00–24:00，统一 UTC+8）拉取各来源数据：git log、CI API、工单导出 CSV。这一步只做过滤和截断，不做解读。

**第二步：结构化。** 脚本输出一个中间 JSON，字段固定：`date`、`commits`、`ci_runs`、`failed_jobs`、`open_tickets`。所有数字在这一步敲定，来源可追溯。

**第三步：摘要。** 把 JSON 喂给 OpenClaw 的 Agent，prompt 里明确要求"只基于给定数据，不得推断未提供的数字"，让它生成"今日进展 / 风险与阻塞 / 明日计划"三段。MCP 侧只暴露一个只读的 `get_daily_stats` 工具，不给写权限。

**第四步：投递与归档。** 报告写成 Markdown 按日期归档，同时通过 webhook 推到群。生成失败走独立的告警通道，绝不静默。

## 踩坑点

- **时区**：日志时间戳是 UTC，日报窗口按本地时间，第一天就把两天的提交混在了一起。现在采集脚本里显式做时区转换，不再依赖系统默认值。
- **格式漂移**：CI API 升级后字段改名，流水线没报错，但 `failed_jobs` 一直是 0。补了一个字段存在性断言：缺字段直接失败，而不是输出空值。
- **重跑幂等**：手动补跑某天任务时生成了两份报告。后来统一用 `reports/YYYY-MM-DD.md` 命名，覆盖写。
- **上下文膨胀**：有一次把 commit message 全量塞进 prompt，token 直接超限。现在中间 JSON 里 commit 只保留 hash 和首行。

## 可复用建议

1. 先定 schema 再写 prompt，报告结构稳定比措辞漂亮重要得多；
2. LLM 之前必须有确定性预处理器，模型只做它擅长的归纳，不做算术；
3. 保留中间 JSON，日报内容有争议时能回溯到原始数据；
4. 给流水线本身加监控——日报系统的失败方式，往往就是"今天没有日报"这种最安静的失败。

## 总结

这条流水线跑了一个多月，日报从每天约 30 分钟的人工活，变成每天检查一眼的自动产物。真正的价值不只是省时间：格式统一后，周报和月度回顾可以直接基于归档的 JSON 聚合，整条数据链是通的。下一步打算把失败任务的关键日志片段也结构化进来，让"风险与阻塞"一节更有据可查。
