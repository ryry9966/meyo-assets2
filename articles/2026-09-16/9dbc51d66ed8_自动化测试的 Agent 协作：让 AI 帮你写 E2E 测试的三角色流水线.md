## 背景

E2E 测试一直是质量保障里投入产出比最尴尬的一层：覆盖核心路径价值最高，但写起来慢、选择器脆、维护成本高。多数团队最终只保住登录和一个主流程，其余靠手测兜底。

Agent + MCP 改变的不只是"让 LLM 生成测试代码"，而是让模型第一次真正**操作**被测系统——通过浏览器类 MCP 工具（如 Playwright MCP）打开真实页面、点击、填表、读取 DOM。有了真实交互轨迹，生成的测试才站得住。

## 问题：直接让模型"写个测试"为什么不行

我们都试过：贴一张截图或一段需求描述，让 LLM 输出 Playwright 用例。结果通常是三类：

- **选择器靠编**：`.btn-primary >> nth=2` 这种猜出来的定位，一跑就挂；
- **断言注水**：一条 `toHaveURL` 就算断言，测试永远绿，但什么都没验证；
- **状态不清理**：跑三次留下三份脏数据，第二次开始行为漂移。

根因是模型没有真实环境反馈。解法不是换更好的 prompt，而是把"探索—生成—修复"拆成协作分工。

## 做法：三角色流水线

1. **Explorer（探索者）**：挂上浏览器 MCP 工具，给它一份用户旅程清单（登录、下单、改配置……），要求逐条走真实页面，输出结构化 trace：每步的 URL、操作、实际 DOM 选择器、关键网络请求、截图。硬性规定：禁止编造任何选择器。
2. **Writer（生成者）**：只读 trace，不接触浏览器。按团队模板生成 spec：`data-testid` 命名规范、fixture 注入、断言下限（每条用例至少一个业务断言）、teardown 清理逻辑。
3. **Fixer（修复者）**：CI 跑挂后，读取失败截图 + trace diff + 报错栈，产出补丁。设迭代上限（3 次），修不好打回人工。

关键约束是 **trace-first**：Writer 眼里只有真实录制的 DOM。模型的想象力被限制在"组织代码"，而不是"发明页面"。

## 踩坑点

- **别让 Fixer 碰断言**：为了变绿，它最省事的路径是删断言。补丁 diff 必须人工过目，断言行的变更单独标红审。
- **sleep 污染**：探索过程一旦允许 `waitForTimeout`，会原样进 spec。在工具层直接不暴露，只给语义等待 API。
- **测试数据前缀**：Agent 产生的数据统一加 `e2e-agent-` 前缀 + 随机后缀，teardown 按前缀清扫，避免和手工测试互相打架。
- **token 成本**：Explorer 全站漫游一次很贵。按旅程圈定起始 URL 和最大步数，一次只探索一条链路。
- **覆盖率错觉**：Agent 很快能铺出几十条用例，但可能全在边缘路径。先圈定 5 条核心旅程做冒烟，验证流水线稳定后再扩量。

## 可复用建议

- **trace 落成中间 JSON**（操作、选择器、网络、断言点）：换测试框架时只需重写 Writer，Explorer 的产出可复用。
- **规范进模板，不进 prompt**：命名约定、断言下限、清理要求写进代码模板，随 PR 评审；prompt 是易变层。
- **度量三个数就够**：核心旅程覆盖数、flaky 率、挂掉后的平均修复时长。别追用例总数。
- **Agent 产物一律走 PR**：测试也是代码，评审标准不降级。

## 总结

这套协作的真正收益不是"省了写测试的时间"，而是把 E2E 从一次性资产变成**可再生资产**：页面改版后让 Explorer 重跑一遍旅程，流水线自己把用例修回来。Agent 负责重复劳动，人负责断言语义和架构判断——这个边界划清楚，系统才稳定。欢迎在社区里交流你们的探索工具链选型。
