## 背景

大部分 Agent 的交互模型是“你问它答”：会话结束，能力归零。但在真实自动化场景里，很多事本来不需要人发起——夜间 CI 挂了、某个 issue 停滞三天、监控指标越过阈值。这些“该被处理”的信号一直存在，缺的是让 Agent 在正确时机被唤醒的机制。

## 问题

把 reactive Agent 改成 proactive，常见的三种翻车：

1. 直接让 LLM 循环轮询——成本爆炸，且绝大多数轮次无事可做；
2. 触发太密——通知疲劳，一周后用户直接关掉；
3. 醒来时没有上下文——Agent 靠猜行事，一次错误动作就把信任烧光。

核心矛盾是：**触发必须是确定性的，而判断和执行是概率性的**。工程上要做的，是把两者解耦。

## 做法

以我给团队搭的“值班助手”为例（夜间盯 CI 与 issue，早晨产出待办草稿），分四步：

**1. 触发层用纯代码，不用模型。** 三类触发器：cron（定时）、webhook（事件）、阈值检查（状态）。全部是普通脚本加 MCP 工具调用，条件命中才唤醒 Agent，其余时间零开销。

**2. 唤醒时注入 wake context。** Agent 醒来拿到的不是空会话，而是结构化快照：什么触发了、相关状态、本次允许的动作白名单。上下文持久化在本地状态文件里，不指望模型“记得”。

**3. 动作分三级策略。** 低置信 → 只写日志；中置信 → 生成草稿等一键确认；高置信且可逆且在白名单内 → 直接执行。值班助手里，“起草 issue 跟进话术”是草稿级，“合并标记 ready 的 PR”是执行级。

**4. 限流与防环。** 每类触发器设冷却时间和每日动作预算；过滤 Agent 自己产生的下游事件，避免“它发的消息又触发 webhook”造成自循环。

上线节奏：前两周只开草稿模式，第三周才放开自动执行。

## 踩坑点

- 没处理时区和静默时段，凌晨三点被推送叫醒过一次——从此所有触发器强制带静默窗口；
- Agent 的一次回复再次触发同一个 webhook，一小时内自循环四十多轮——触发器必须携带来源标记；
- 最初把“是否值得唤醒”也交给 LLM 判断，它开始过度解读日志来凑结论，改回代码判断后才稳定。

## 可复用建议

- 记住一句话：**触发是代码，Agent 是被调用的函数**；
- 每次主动动作落一条记录（触发源、上下文、决策、结果），既是审计凭据，也是调阈值的依据；
- Proactive ≠ 高频，一条有用的晨间摘要胜过十条即时提醒；
- 从只读动作起步，逐步放宽写权限，每放宽一档观察一周。

## 总结

Proactive 能力不是模型问题，而是工程问题：确定性的触发、充分的唤醒上下文、分级的动作策略、可审计的日志。这四件事做扎实，Agent 才能从“等你开口”变成“把事办好再汇报”——而且不会让你想把它关掉。
