## 背景

OpenClaw 的 agent 默认是被动模式：你有消息它才动。但日常运维里有大量"周期性、低价值密度、需要有人盯"的事——磁盘水位、依赖落后、收件箱汇总、定时巡检。OpenClaw 为此内置了心跳机制：gateway 按固定间隔唤醒 agent，agent 先读工作区根目录的 `HEARTBEAT.md`，有任务就执行；文件为空则直接跳过这一轮，不调模型、零成本。

## 问题

大多数人把这个文件当成备忘录，塞一堆任务进去，结果通常是三种：token 账单暴涨、agent 每轮心跳都来频道里说"一切正常"、或者一个长任务跑到超时。根因在于误解了机制——心跳是**定时触发的一轮对话**，不是后台定时任务。

## 做法

1. **建文件**：在 workspace 根目录（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`。
2. **写任务条目**，每条按"触发条件 + 动作 + 汇报策略"三段式：

```markdown
- 若 ~/monitor/inbox 有新文件：逐个总结，追加写入 daily-notes.md
- 每次心跳运行 git -C ~/proj fetch；本地落后超过 3 个提交才播报，否则保持沉默
```

3. **配间隔与出口**：间隔建议 30m 起步（`agents.defaults.heartbeat.every`），并用 `HEARTBEAT_TARGET` 把心跳输出路由到一个专门的静默频道，别污染主会话。
4. **验证**：先设 2 分钟短间隔观察两轮日志里的 heartbeat 记录，确认行为后再调回。
5. **长任务外包**：心跳只负责"看结果、发通知"，重活交给脚本或系统 cron。

## 踩坑点

- **任务越堆越多**：文件里有 N 条任务，每轮都可能全跑一遍。上限控制在 3~5 条，没产生过价值的条目及时删。
- **无事也说话**：agent 会倾向于汇报"一切正常"。文件里必须显式写"仅异常时播报"，否则频道会被 ack 刷屏。
- **定时精度**：心跳的定时精度就是间隔本身。"每天 9 点"实际是"9 点后的下一次心跳"。要准点就上系统 cron 触发，心跳只做摘要。
- **别写秘钥**：`HEARTBEAT.md` 每轮注入上下文，写进去的 secret 等于反复发给模型，且是明文存储。
- **会话膨胀**：心跳轮次持续累积上下文，注意 session 裁剪/重置配置，否则跑一周后响应质量下降。

## 可复用建议

- **任务行模板**：`条件 / 动作 / 汇报策略`。汇报策略三选一：仅异常播报、每轮汇总一条、凑够 N 条再报。
- **分层原则**：确定性检查（端口、磁盘、fetch）交给 shell 脚本和 cron；心跳只做编排与判断。`HEARTBEAT.md` 写"盯什么"，不写"怎么做"。
- **版本化**：文件纳入 git，与 workspace 一起管理，改任务有迹可循。
- **降级即免费**：暂时不用就把文件清空，心跳自动跳过，不产生任何开销。

## 总结

`HEARTBEAT.md` 的价值不在于"定时执行"——这件事 cron 更便宜。它真正把"盯什么、何时开口"的判断交给了模型，让 agent 从问答终端变成一个带待办清单的常驻进程。工程纪律三句话：**文件要小、默认沉默、重活外包**。
