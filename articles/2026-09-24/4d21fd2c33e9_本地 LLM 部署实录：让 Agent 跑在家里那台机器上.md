## 背景

做 Agent 自动化的人迟早会遇到三件事：API 账单随调用频率线性上涨、本地文件和聊天记录不方便交给云端、内网环境干脆出不去。本地部署 LLM 的定位不是替代前沿模型，而是给 Agent 体系补一层「高频、低价、数据不出门」的执行层。我最近把家里一台 32GB 内存 + RTX 4060 Ti 16GB 的机器改造成常驻推理节点，跑通了从选型到接入 MCP 工具链的全流程，记录如下。

## 先想清楚的两个问题

一是「内存够就能跑」：量化后的权重确实塞得下，但 KV cache、运行时开销、系统占用都要算进去，塞得下和跑得快是两回事。二是「跑起来就能接 Agent」：本地模型真正的难点在上下文长度和工具调用质量，而不是能不能生成文本。

## 部署步骤

1. **算内存预算**。经验公式：Q4 量化下每 B 参数约 0.55–0.6 GB，另留 25%–35% 给 KV cache 和运行时。14B 模型 Q4 约 9GB 权重，实际占用 12–13GB；32B 约 20GB，需要 26GB 以上空间。Mac 统一内存可以更激进，但要给系统留 8GB 以上。
2. **选运行时**。省事用 Ollama，自带 OpenAI 兼容接口；要细粒度控制用 llama.cpp；显存充裕且要并发可以上 vLLM。家用场景我选 Ollama。
3. **选模型**。中文场景优先看 Qwen 系列的 7B/14B/32B，工具调用支持相对成熟。务必确认模型卡明确支持 function calling，别只看跑分。
4. **定量化档位**。Q4_K_M 是性价比起点；显存有余再上 Q5/Q6，收益通常不如把上下文开大。
5. **接入 Agent**。base_url 指向 `http://localhost:11434/v1`，先用最小脚本验证：调一次天气查询之类的工具，确认模型能正确产出参数 JSON，再接入完整工作流和 MCP 工具链。
6. **调关键参数**。`num_ctx` 显式设到 8192 以上；`keep_alive` 设为足够长或 `-1`。

## 踩坑记录

- **默认上下文太小**。Ollama 默认上下文只有 2K–4K，系统提示词和工具 schema 会被静默截断，Agent 表现为「莫名其妙忘了规则」。这是我排查时间最长的一个坑。
- **KV cache 比预期凶**。长会话加大 ctx，14B 也能 OOM，而 Agent 的多轮循环恰恰制造长会话。
- **小模型工具调用不稳**。同一个 7B 模型，参数抽取成功率随 schema 复杂度明显下降。上工作流前先跑测试集。
- **加载延迟**。keep_alive 过短时，Agent 循环间隔一长就触发重新加载，单次延迟从秒级跳到分钟级，还容易被误判为「模型变笨了」。

## 可复用建议

- 做路由分层：本地模型接高频低风险子任务（摘要、分类、格式转换），规划和高风险操作仍走云端强模型。
- 固定一套 10–20 条工具调用测试用例，每次换模型先跑一遍，数据说话。
- 用模型 digest 锁版本，避免静默升级导致行为漂移。
- 给本地调用设超时和降级路径，本机服务挂了不能阻塞整条工作流。

## 总结

本地 LLM 的价值在于把 Agent 的「手脚」留在自己机器上，而不是和云端比脑子。建议从 7B–14B 起步验证链路，确认场景真的吃得到本地化收益，再决定是否为 32B 加硬件。先跑通，再加重。
