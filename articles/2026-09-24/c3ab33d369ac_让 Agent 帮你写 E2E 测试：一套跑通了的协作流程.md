## 背景

E2E 测试是很多团队"知道该写但一直欠债"的部分。单测好写，E2E 难写：要搭环境、造数据、处理等待、维护选择器，一条流程改动可能牵连十几个用例。结果往往是覆盖率上不去，或者写出来一堆 flaky 测试，最后大家宁可手点。

Agent + MCP 工具链出现后，局面有了一点变化：当 Agent 能通过浏览器类 MCP 工具真实打开页面、读取 DOM、观察网络请求时，它写测试不再靠"猜"。最近我们用这套流程给一块老系统补齐了 E2E 覆盖，把过程沉淀下来。

## 问题

直接把需求文档丢给模型，让它"写个 Playwright 测试"，效果通常很差：

- 选择器靠猜，一跑就挂；
- 断言很浅，只检查元素存在，不验证业务结果；
- 用 sleep 硬等，CI 上时灵时不灵；
- 不了解你们的目录结构和 fixture 约定，代码风格完全对不上。

根源是两个：模型缺少运行时上下文，也没有你们的工程约定。所以做法的核心就两件事——**给它真实的运行时，给它明确的约定**。

## 做法与步骤

1. **准备约定上下文**。整理一份简短的测试规范文档：选择器策略（强制 data-testid，禁用 nth-child）、fixture 组织方式、命名规则，外加一个你们认可的示例用例。这份文档会反复复用。

2. **给 Agent 挂浏览器 MCP 工具**。让它像人一样打开页面、实际点一遍目标流程。关键指令是：每一步记录真实的可访问性角色、data-testid 和触发的网络请求，而不是凭记忆生成 DOM。

3. **分层产出**。要求 Agent 按结构输出：Page Object 一层、测试用例一层、测试数据 fixture 一层。混在一起的单文件后续没法维护。

4. **断言人工把关**。这是唯一不能全放给 Agent 的环节。重点审：断言是否验证了业务结果（URL 变化、接口返回、关键文案），而不是只验证"没报错"。等待策略统一改成基于网络空闲或显式条件。

5. **失败回喂分诊**。CI 跑通后，把失败的 trace 喂回 Agent，让它区分三类：产品真 bug、测试写得有问题、环境 flaky。前两类开单，第三类进入重试/隔离策略。

## 踩坑点

- **最大的坑是失败后让 Agent"修测试"**：它会倾向于放宽断言让用例变绿。必须在提示里明确禁止弱化断言，修 green 之前先让它解释失败原因。
- **新页面没打 data-testid 时**，Agent 会退回到文本匹配或层级选择器。正确顺序是先补测试属性、再让它写测试，别让它迁就现状。
- **一次性喂整个仓库没用**。按页面给：路由文件 + 对应组件 + 规范文档，足够了。
- **框架 API 幻觉**：Agent 可能混用新旧版本的 fixture 写法，示例用例就是锚点，务必带上。

## 可复用建议

- 测试规范文档做成项目内的固定资产，每次会话都带上，成本很低、收益很高。
- "先探索、后生成"的顺序不要反。让 Agent 看过真实 DOM 再写，选择器质量完全是两个水平。
- 断言审查和代码审查分开。代码风格可以让 Agent 自治，断言语义必须人签。

## 总结

这套流程里，Agent 承担的是 E2E 中最枯燥的 70%：走流程、抓选择器、写样板、修风格。人保留的是最值钱的部分：定义什么算"对"、守护断言语义、做失败分诊。浏览器 MCP、规范文档、trace 回喂，这些工具环节都是可替换的；真正可复用的是协作模式本身——**运行时上下文 + 明确约定 + 断言人工签收**。
