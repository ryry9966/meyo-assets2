前阵子一条新闻在开发者圈刷屏：新一代 GPT 模型的缓存输入（cached input）价格最低降到常规输入的一折。评论区一片“推理成本坍塌”的欢呼，结果月底一拉 API 账单，很多人发现：省是真省了，但账单离“一折”差得远。问题不出在厂商定价不诚实，而是大多数人没搞清楚——这一折，到底折在哪一笔钱上。这篇把 prompt caching 的原理、账单结构和命中率问题一次讲透。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-24/86b10cca0c474a06.png)

## 一折折扣，折的是哪一栏？

- LLM API 按 token 计费，一次请求的账单通常拆成三栏：**未命中缓存的输入、命中缓存的输入、输出**。
- 以新一代 GPT 系公开价目为例（媒体口径，具体以官网为准）：输入 $1.25 / 百万 token，缓存输入 $0.125 / 百万，输出 $10 / 百万。缓存输入确实只有常规输入的 10%，数学上没毛病。
- 但打折的只有“输入”这一栏。输出单价纹丝不动，而且是输入的 8 倍。
- 顺便一提，各家力度并不一样：OpenAI 的缓存折扣随模型从五折到一折不等；Anthropic 缓存读取同样约一折，但写入缓存要加价 25%；Gemini 隐式缓存大约七五折。“最高省九成”是单价上限，不是普适默认值。

## 缓存到底缓存了什么：prefill 与 decode

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-24/1adf3ff24ec7a6c6.png)

- Transformer 推理分两段。**prefill**：把整个 prompt 一口气读进去，为每个 token 算好注意力所需的 Key/Value 中间结果（KV cache），相当于“读题”；**decode**：一个 token 一个 token 往外蹦，每蹦一个都要对全部上下文做一次前向计算，相当于“答题”。
- Prompt 前缀不变时，prefill 算出的 KV cache 可以直接复用——读题不用重读，省的就是这部分算力。厂商敢打一折，是因为这块成本确实省了，属于让利而非补贴。
- 但 decode 无法复用缓存：每一次生成都要重新跑，而且解码阶段的显存带宽压力更大。这就是为什么输出单价通常是输入的 4~8 倍——账单的大头，恰恰长在折扣够不着的地方。
- 几个技术细节：缓存按**前缀**匹配，最少 1024 token 起缓，之后按 128 token 粒度命中；缓存有 TTL，通常几分钟到几十分钟，超时或显存紧张就被清掉；多机负载均衡还可能把请求路由到没有缓存的那台机器——命中是概率事件，不是承诺。

## 一笔账算给你看：为什么不是一折

- 设一个典型 Agent 请求：system prompt + 检索上下文共 10 万 token，其中 9 万命中缓存、1 万是本次变动的新增内容，模型输出 8000 token。按上面单价：
  - 未命中输入：1 万 × $1.25/M = $0.0125
  - 缓存输入：9 万 × $0.125/M = $0.01125
  - 输出：8000 × $10/M = $0.08
  - 合计约 $0.104，其中**输出一项占 77%**。
- 对照完全不命中的情况：10 万 × $1.25 + $0.08 ≈ $0.205。缓存帮你省了约 49%——账单接近对折，但离一折很远。
- 把输出加大到 2 万 token（比如生成代码），输出占比逼近九成，缓存再猛也撬不动总账单。结论很简单：输入侧打一折，对总账单的杠杆天然有限——输出单价高、占比大，且一分不打折。

## 命中率才是命门：存了不等于省了

- **前缀匹配是严格的**：从第一个 token 开始逐段比对，中间任何一个字变了，从那里往后全部作废。把时间戳、随机数、用户 ID 拼在 system prompt 开头，是缓存命中率杀手榜的常年第一名。
- **多轮对话是追加式结构**：第 N 轮能吃到前 N-1 轮的缓存，但每轮新增内容和输出照原价。对话越长，缓存的相对收益越明显，绝对支出却也在滚雪球。
- **TTL 是隐形的坑**：用户隔了一小时再问一句，缓存早没了，全部按原价重算。低峰期缓存可能活得久一点，但没人能拿它做容量规划。
- **1024 token 的门槛**意味着：短 prompt 场景（大多数字客服、短问答）从头到尾与缓存无缘。

## 谁赚麻了，谁基本无感

受益最明显的画像：

- 长 system prompt 的 Agent：几千上万 token 的角色设定 + 工具说明，每步调用都重复，命中一次省一次；
- 共享固定前缀的批量任务：同一份长文档前缀跑批量抽取、翻译、审核；
- IDE 代码补全：同一文件前缀被反复读取，天然高命中；
- few-shot 长示例、长规则约束的固定框架 prompt。

基本无感的画像：

- prompt 短于 1024 token 的轻量应用；
- 请求开头就变的动态场景（个性化开场白、把检索结果拼在了前缀位置）；
- 输出远大于输入的生成型任务（写作、代码生成）——账单大头在输出侧，缓存折扣鞭长莫及。

## 三条实用建议与一点冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-24/c35f0d8f9d32bd58.png)

1. **结构化 prompt，盯住命中率。** 静态内容前置、动态内容后置，把时间戳这类易变信息挪到 prompt 末尾；各家 API 响应里都有 cached_tokens 字段，把它接进监控面板。命中率上不去，先查前缀稳定性，再查调用间隔是否超过 TTL。
2. **先做账单归因，再谈优化。** 把账单拆成输入 / 缓存输入 / 输出三栏看占比。很多应用的大头根本是输出——要求模型简洁作答、用结构化输出、简单步骤路由给小模型、收紧 max_tokens，这些手段对总账单的杀伤力往往比死磕缓存大得多。
3. **冷思考：折扣改变的是边际成本，不是总成本。** 单价降了，上下文会越塞越长、Agent 步数越跑越多、以前做不起的用法被解锁——总账单完全可能不降反升（杰文斯悖论的 LLM 版本）。把缓存折扣理解为“能多做事”的信号，而不是“同样的活自动变便宜”的承诺，你对成本的判断会清醒很多。
