## 背景

给 Agent 接上长期记忆后，真正决定体验的往往不是存储，而是 `memory_recall` 这一步：用户问"上次那个部署脚本的问题最后怎么解决的"，你能不能把三个月前那条记忆捞回来。常见两条路线：语义搜索（embedding + 向量相似度）和全文搜索（关键词 / BM25，比如 SQLite FTS5）。社区里经常吵"哪个好"，我的结论是：单挑都不够，混合才是起点。

## 问题

两条路线的失效模式几乎互补：

- **语义搜索**擅长"换了个说法也能找到"。但遇到精确标识符就拉胯：错误码 `ERR_CONN_REFUSED`、配置键 `database.pool_size`、函数名、工单号——embedding 会把它们模糊化，常常排不进 top5。
- **全文搜索**擅长精确命中。但用户的说法和记忆原文经常没有词面重叠，中英混排更糟：问的是"数据库连接老断"，记忆里写的是 "PostgreSQL connection pool timeout"，一个词都对不上。

我在本地 50 组"查询 → 应命中的记忆"的小评测集上分别测了两条链路：语义 recall@5 约 0.65，纯 FTS 约 0.55，但两边未命中的集合重叠度很低——这基本宣告了该做融合。

## 做法

1. **先建评测集，再动手。** 从历史会话挑 30–50 对"查询 → 目标记忆"，人工核对。没有这个，后面所有调参都是玄学。
2. **两路并行召回。** 语义路：给每条记忆算 embedding（选对中文友好的模型），存向量库；全文路：SQLite FTS5 + jieba 分词建索引。每路取 top 20 候选，别只取 5。
3. **RRF 融合，别手调权重。** 两份候选列表用 Reciprocal Rank Fusion 合并：`score = Σ 1/(k + rank)`，k 取 60。它只看排名不看分数，天然避开"cosine 在 0~1 而 BM25 无上界怎么归一化"这个经典大坑。
4. **后置过滤放在融合之后。** 时间衰减（30 天前的记忆打小折扣）、项目/会话范围过滤、去重。这些是元数据逻辑，别混进排序器。
5. （可选）top 8 再过一遍 rerank，或直接塞给模型自己挑。实测前四步已解决大部分问题，rerank 收益递减。

改完后同一评测集 recall@5 到 0.85 左右，改善最明显的是错误码、路径、命令这类精确查询，以及中英互查。

## 踩坑点

- **中文 FTS 不加分词等于没用。** FTS5 默认按空格切词，中文整句变成一个 token，几乎查不中。jieba 或 ngram 必须上。
- **embedding 模型对代码标识符不敏感。** 通用模型把 `ERR_CONN_REFUSED` 当普通词。这类查询占比高的话，考虑加第三路兜底：对原文做 LIKE / 精确匹配。
- **每路候选太少，RRF 无米下锅。** 两路各取 5 再融合，常常不如单路——候选池先放大再收敛。
- **记忆条目粒度太粗。** 整段对话当一条记忆存，向量会被稀释。按"原子事实"切：一条记忆一件事，带时间戳。
- **换 embedding 模型要全量重算，且新旧向量不可比。** 给向量带版本号，迁移期间双路并存。

## 可复用建议

- 默认就上混合，别先押注单边。RRF 零调参、成本近零，覆盖 80% 场景。
- 评测集进 CI：每次动检索链路（换模型、改分词、调 k）跑一遍 recall@5 / MRR，防退化。
- 定期看"没召回上来"的 case，它们暴露的多半是写入侧问题：该存的没存、存了没去重、表述太烂。
- 时间新旧和重要性当后置信号用，不要烘进向量里。

## 总结

语义搜索和全文搜索不是对手，是两条互补的召回通道：前者管"换说法"，后者管"精确串"。工程上最划算的组合是 FTS + 向量双路召回、RRF 融合、元数据后置过滤。但比检索更值得投入的是记忆写入的规范——原子化、去重、带上下文。检索做得再好，也捞不回一条没写好的记忆。
