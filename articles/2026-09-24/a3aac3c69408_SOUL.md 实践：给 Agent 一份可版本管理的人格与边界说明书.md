## 背景

在 OpenClaw 的 workspace 里，除了大家熟悉的 AGENTS.md 和 TOOLS.md，还有一个经常被忽略的 SOUL.md。它会在每次会话（包括 heartbeat 唤醒）时注入上下文，决定 agent “是谁、怎么说话、什么不做”。

听起来有点玄学，本质上是 prompt 工程：把人格和行为约束从散落的系统提示词里拆出来，变成一个可编辑、可 diff、可 review 的文件。既然是文件，就该按工程方式管理。

## 问题

没有明确 SOUL.md 时，常见三种症状：

1. **语气漂移**。同一个任务，今天啰嗦明天敷衍；长会话越聊越“讨好”，什么都答应。
2. **边界缺失**。agent 对 `rm -rf`、强制推送、批量外发邮件这类操作不做确认，直接执行。
3. **约束散落**。人格要求一半在系统 prompt、一半在插件描述里，改一处漏三处，出问题无法定位。

## 做法

**1. 三段式最小结构。** 身份与语气（3~5 条）、行为准则（做什么）、硬边界（绝不做什么）。每条一句话，不要展开叙事。

**2. 边界写成可判定条件。** “保持谨慎”没法验证；“凡涉及删除、支付、外发的操作，先复述关键参数并等待确认”可以验证。规则统一为：触发条件 + 要求动作。

**3. 与其他文件分层。** SOUL.md 只管人格与红线；工作流程放 AGENTS.md，工具说明放 TOOLS.md 或 MCP 配置。避免同一规则写两遍导致互相打架。

**4. 把拒绝话术也写进去。** 说明原因 + 给替代方案。否则 agent 拒绝时容易生硬，甚至为了“好心办事”绕过边界。

**5. 当代码管理。** SOUL.md 进 git，改动走 PR；准备 10 条固定测试问题（含边界试探类），每次改完跑一遍，对比回答是否漂移。

## 踩坑点

- **写成人物小作文**：几百字 backstory 占上下文，还稀释关键规则。规则密度比“人味”重要。
- **全是形容词**：“专业、友好、克制”这类词模型无法稳定执行，落到条件和示例才有用。
- **被工具描述覆盖**：某些 MCP/插件在自己的 description 里塞了语气要求，优先级抢在 SOUL.md 前面。行为异常时先查工具层。
- **边界过死卡住自动化**：所有写操作都要求人工确认，heartbeat 任务直接瘫痪。按“可逆 / 不可逆”分级，只对不可逆操作设卡。
- **以为生效了实际没加载**：文件放错路径或没被注入，改了半天白改。先用一个只有 agent 该知道的问题验证注入。

## 可复用建议

- 三段式模板 + “不可逆操作白名单”，可直接迁移到任何 agent 项目，不限于 OpenClaw。
- 人格回归测试题库放仓库里，和 SOUL.md 一起版本化。
- 多 agent 场景：一份基础 SOUL.md + 每个 agent 一小段 delta，避免复制粘贴后各改各的。
- 每次遇到“agent 行为不符合预期”，先问一句：这条约束写在哪个文件里？写清楚了吗？——大部分时候答案是没写。

## 总结

SOUL.md 的价值不在于“给 AI 一个灵魂”，而在于把行为约束从一次性 prompt 变成工程资产：可 review、可回滚、可回归测试。人格是产品参数，边界是安全机制，都值得像代码一样认真对待。
