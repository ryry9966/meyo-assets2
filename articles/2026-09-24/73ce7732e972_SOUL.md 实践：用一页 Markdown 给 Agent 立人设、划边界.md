## 背景

跑一个长期在线的个人 Agent（OpenClaw + MCP 工具链）一段时间后，普遍会遇到两个问题：一是**人格漂移**——今天话痨、明天惜字如金，换个会话语气就变；二是**边界模糊**——它会在你未确认的情况下直接发消息、调工具、改文件。这些行为约定散落在系统提示词、skill 文件、工具描述里，改一处漏三处。

SOUL.md 的思路很朴素：把"它是谁、它怎么说话、它什么不能做"收敛成一个文件，放在 Agent 工作区根部，每次会话加载进上下文。它不是魔法，本质是一段稳定的系统级提示词，但"单文件 + 版本化"带来的可维护性是实打实的。

## 做法

我的 SOUL.md 大致四段，全文控制在一页内：

1. **身份与角色**：两三句话。它是谁、服务于谁、口吻基调。避免形容词堆砌，写具体行为，比如"默认中文回复，先给结论再给细节，单次回复不超过 200 字，除非我要求展开"。
2. **边界（硬规则）**：绝不做什么。例如：发送消息、花钱、删除文件前必须确认；不主动联系通讯录里的人；不把内部笔记内容外发。
3. **升级规则**：什么时候必须来问我。场景模糊时宁可多问一句。
4. **交互约定**：格式偏好、称呼、何时用列表何时用段落。

配套两件事：SOUL.md 只管"软边界"，真正的风险控制放在 MCP 工具权限和审批门槛上——写操作走确认，支付类工具默认禁用。**提示词会被绕过，权限不会。**

## 踩坑点

- **写成小作文**。早期我写了 2000 字，结果模型抓不住重点，还吃 token。砍到 400 字后反而稳了。规则要少而硬。
- **只有负面清单**。光写"不许 X"效果一般，给替代路径更好："不直接发送，而是先起草并等我确认"。
- **和 skill/工具描述打架**。某个 skill 的提示词里也写了人格相关内容，两边冲突时行为很随机。原则：人格和边界只在 SOUL.md 一处定义，skill 只管怎么做。
- **写完就不管**。每周把翻车的对话捞出来，判断"这条要不要进 SOUL.md"，攒几条再统一改，别天天动。

## 可复用建议

- **模板**：身份（3 句）→ 硬边界（5–8 条）→ 升级规则（3 条）→ 交互约定（3 条）。超出这个规模，说明该拆到权限层了。
- 每条规则配一个**具体例子**，比十条抽象形容词管用。
- SOUL.md 进 git，每次调整打 tag，行为出问题能 diff 回滚。
- 改完用固定的三五个**探测问题**跑一遍（比如故意让它"直接帮我发条消息"），确认边界生效再上线。

## 总结

SOUL.md 解决的不是"让 Agent 更聪明"，而是让它的行为**可预期**。人格是产品体验，边界是安全兜底：前者用提示词写清楚，后者必须落在权限和审批上。一页 Markdown、一个 git 仓库、一个每周回顾的习惯，比任何复杂的提示工程框架都耐用。
