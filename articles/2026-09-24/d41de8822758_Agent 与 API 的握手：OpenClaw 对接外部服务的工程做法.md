## 背景

Agent 的能力上限，基本等于它能安全触达的服务集合。模型本身只会"说"，真正"做"事靠工具调用。OpenClaw 里这条链路通常三段：模型决定调用 → 工具层（插件 / MCP Server）翻译成 HTTP 请求 → 外部服务返回结果。本文记录我们对接几个内部与第三方 API 的做法，供复用。

## 问题

跑通 demo 容易，稳定跑难。失败集中在五类：

1. 鉴权配置散落，密钥出现在日志甚至模型上下文里；
2. 工具描述模糊，模型传参靠猜，成功率低；
3. 没设超时，网络一抖 agent 卡死一整轮会话；
4. 写操作重试造成重复下单、重复建单；
5. API 返回大 JSON 直接塞上下文，token 爆掉。

## 做法

**第一步：先定工具边界，再写代码。** 每个外部服务拆成粒度均匀的工具，一个工具一个动词（`create_issue`、`query_order`），不做"万能接口"。参数用 JSON Schema 写清类型、必填项和枚举值，这段描述就是模型的"说明书"，值得花时间打磨。

**第二步：薄适配层封装 HTTP。** 用 MCP Server 或插件把 REST 包一层：鉴权、限流、超时、重试全部收在适配层，不让模型感知细节。密钥放环境变量或本地配置，适配层负责注入，绝不把 key 拼进模型可见的参数。

**第三步：超时与重试策略。** 读操作默认 10–15 秒超时，指数退避重试 2–3 次；写操作要么不自动重试，要么带幂等键（比如用请求内容哈希做 `Idempotency-Key`），避免重复副作用。

**第四步：错误信息面向模型设计。** 返回给模型的错误要"可行动"：`400: date format should be YYYY-MM-DD` 远好于 `request failed`。模型拿到可读错误才能自我修正，这是调用成功率的关键变量。

**第五步：裁剪返回值。** 适配层做字段筛选和分页截断，只传模型决策需要的字段；大响应先落盘或摘要，给个引用 ID 让模型按需查询。

**第六步：分层验证。** 先用 curl 验证 API 本身，再对适配层做单测，最后才挂到 agent 上小流量联调。哪层出问题，一眼定位。

## 踩坑点

- 工具描述写"查询信息"这种模糊话，模型必然乱传参，每个参数都要给语义和示例。
- 非幂等接口别无脑重试，我们重复建过工单，靠幂等键才堵住。
- 长任务（如导出报表）改异步：提交后返回任务 ID，另配一个 `check_status` 工具轮询，别让一次调用干等。
- 日志脱敏要覆盖 URL query 和 header，密钥最容易从这两处漏。

## 可复用建议

- 一个外部服务 = 一个薄适配层，职责单一，坏了单独替换。
- 每个写操作工具提供 dry-run 模式，联调期全开。
- 维护一份工具清单文档：用途、参数、副作用、限流额度，团队共用。

## 总结

对接外部服务的本质是"翻译 + 约束"：把 API 翻译成模型能理解的工具，把鉴权、超时、幂等等约束收进适配层。OpenClaw 侧做好 schema 描述与错误设计，大部分稳定性问题能在联调期暴露。先想清楚边界，再动手写代码。
