最近一波中文用户集体破防：Claude 网页版的额度掉得莫名其妙，同样强度的使用，英文对话还能再战三百回合，中文对话聊没几轮就提示用量见底、等待重置。36kr 的标题把话说得很直白——“只因回复里有汉字”。这句略带戏剧性的总结，其实歪打正着地指向了一个真实的技术问题：不是 Claude 在“针对”中文，而是汉字在它的计量体系里，天生就更“占秤”。这篇我们把 token 的账本翻开，看看这笔钱到底是怎么多出来的。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-24/c0da02935d39cc81.png)

## 一、先说结论：不是“封中文”，是计量口径问题

- **现象层面**：大量 Pro / Max 订阅用户在 V2EX、Reddit 等社区反馈，中文会话的额度消耗明显更快。有用户做了对照：同一类问题，英文提问能撑很多轮，换成中文，几轮就触发滚动窗口限制。
- **机制层面**：Anthropic 官方帮助文档对网页版限额的解释一直是“按 token 消耗量计算”，会话越长、附件越大、开启的推理思考越多，消耗越快。文档里没有任何一条规则提到语言。
- 换句话说，限额系统眼里根本没有“汉字”，只有一串串 token。中文被切成了**更多** token，于是在同一块水表下“跑”得更快。
- 打个比方：两辆车跑同一段路，一辆按里程跳表，另一辆的计价器对同样的路况加倍跳字。问题出在计价器，不在司机，也不在路。

## 二、原理：模型不认识汉字，只认识 token

- LLM 的输入和输出，最小单位都不是字符，而是 token。负责切分的是 tokenizer（分词器），它决定一段文字最终变成多少个 token。
- 主流方案是 BPE：从海量语料里统计高频字节片段，逐步合并成词表词条。英文语料通常占大头，所以英文很省——OpenAI 官方口径是 1 token ≈ 4 个英文字符，约 0.75 个单词。
- 中文吃亏主要在三个环节：
  1. **词表覆盖不足**：没被收进词表的汉字，会按 UTF-8 退化成字节处理，1 个汉字 = 3 字节 = 最多 3 个 token，这就是所谓的 byte fallback；
  2. **合并质量不高**：即使字在词表里，如果训练语料中中文占比低，常见词组的合并规则没学好，一个字也可能被拆成 1~2 个 token；
  3. **计费场景叠加**：多轮对话每一轮都要把历史重新算一遍 token，模型的输出、以及 extended thinking 的思考过程，全都计入消耗。
- 举个量级示意：英文 "Explain how attention works" 大约 5~6 个 token；中文“解释一下注意力机制的原理”十个字，在中文友好的分词器里约 8~10 个 token，到了压缩较弱的分词器上，翻倍并不稀奇。

## 三、三层放大：为什么体感差异这么大

单看一句话，差几枚 token 好像无所谓，但实际使用中，开销是逐层放大的：

1. **编码层放大**：byte fallback 让生僻字、特殊符号直接三倍起步，混在正文里像一台隐藏的“碎钞机”。
2. **会话层放大**：无状态的 API 每一轮都重发全部历史，对话越长，token 消耗越接近平方级增长。中文的额外开销，每一轮都被复利一次。
3. **输出层放大**：模型按 token 自回归地一个一个往外蹦，生成速度基本恒定在若干 token/秒。中文一个字要消耗 2 个 token，意味着屏幕上“每秒蹦出的汉字”直接减半——体感更慢、额度更薄，双重暴击。
- 社区实测（不同文本差异很大，仅作量级参考）：同样一段中文，Claude 的 token 数常见是 GPT-4o 的 1.5~2 倍上下；而 Qwen、DeepSeek 这类把中文语料喂足的模型，普遍能做到 1 token ≈ 1 个甚至更多汉字。
- 结论很朴素：同一份订阅费，中文用户买到的“有效字数”打了折。

## 四、历史包袱：分词器的欠账不是一天欠下的

- GPT-2 时代，中文才是真的惨，常见一字 2~3 个 token；GPT-3.5 / GPT-4 的 cl100k 词表大幅补充了 CJK 词条，情况明显好转；到 GPT-4o 的 o200k，不少常用中文词已能合并成单个 token。
- 国内模型从一开始就把中文压缩率当核心指标调优，tokenizer 在中文上普遍更省，这是训练数据配比决定的，不是玄学。
- Anthropic 长期主打英文编程和 Agent 场景，中文语料在训练配比里优先级不高，而且它的 tokenizer 并未公开，社区只能靠 token 计数接口反推实测。
- 商业视角看，这不只是体验问题：API 按 token 计费，中文内容的实际单价更高；“128K 上下文”装中文的有效容量同样缩水。当各家模型能力逐渐接近，分词效率正在变成一项隐性的产品竞争力。

## 五、实用建议：把每一枚 token 花在刀刃上

1. **语言混搭**：指令、技术名词用英文写（比如结尾加一句 "answer concisely in Chinese"），必须中文的内容再贴原文，两头省。
2. **控制历史长度**：长对话定期开新会话，避免几十轮历史反复重发；超长文档先让模型做摘要，再基于摘要续聊。
3. **压缩输出**：明确要求要点式作答、不复述问题、不写客套铺垫；不需要深度推理的任务，关掉 extended thinking。
4. **大批量中文任务**：优先选对中文 tokenizer 友好的模型，或先用 API 的 token 计数功能实测成本，再决定放哪儿跑。
5. **心态放平**：这是工程问题，不是立场问题。与其把“额度焦虑”升级成语言对立，不如带着实测数据走官方反馈渠道——后者真的有用。

## 收尾：三条冷思考

1. **Token ≠ 文字**。所有按 token 定价或限额的产品，都在向非英语用户收取一笔“隐性汇率”。多语言公平，是整个行业共同的欠账，谁先还上，谁就多一分好感。
2. **分词效率会走到台前**。当模型能力咬得很紧时，同样的预算能处理多少有效信息，就是性价比本身。
3. **对开发者多说一句**：任何多语言 LLM 应用的成本模型，必须按真实 token 实测，不能拿字符数拍脑袋估算——否则上线第一天的账单，会替市场好好教育你。
