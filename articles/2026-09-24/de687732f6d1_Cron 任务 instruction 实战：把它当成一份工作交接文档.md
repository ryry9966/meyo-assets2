## 背景

OpenClaw 的 cron 任务本质上是**无人值守的 agent 调用**：到点触发，agent 读一段 instruction，执行完把结果推到指定渠道，然后结束。它和对话式使用最大的区别是——没有上下文铺垫，没有追问机会，跑错了也没人当场发现。

我目前在用 cron 做三件事：每天的仓库巡检摘要、每周的兴趣资讯整理、不定时的备份校验。跑了两个多月，instruction 改了十几版，踩的坑基本都出在“写法”上，和 cron 本身无关。

## 问题

最初我把 instruction 写得像一条聊天消息：

> 帮我看看仓库最近有什么动态，整理一下发出来。

结果很不稳定：每次整理的维度都不一样，有时漏掉关键 issue，有时输出一大段没法读的长文，还有一次它自作主张去翻了不相关的仓库。核心原因是：**对话里用户可以实时纠偏，cron 里没有这个环节**，instruction 必须一次性把话说死。

## 做法

现在我每条 cron instruction 都按固定五段结构写：

1. **角色与目标**：一句话说清这次要干什么，只干一件事。
2. **输入**：数据从哪来。写具体的工具名、路径或命令，比如“用 MCP 的 `github_list_issues` 拉取 X 仓库过去 24 小时的 open issue"，而不是“看看仓库”。
3. **步骤**：编号列出执行顺序，每步一个动作。实测 agent 对编号清单的遵循度远高于一段流水文字。
4. **输出契约**：发到哪个渠道、什么格式、限制多少条。我通常直接内嵌一个输出样例。
5. **异常分支**：显式写“如果 X 拿不到 / 为空 / 超时，就做什么”。这是最容易被忽略的一段。

另外两个习惯：硬约束（禁止事项、格式要求）单独成段、放在靠前位置；时间基准写死，比如“以系统时间，Asia/Shanghai 为准，汇总过去 24h"——凌晨跑的任务里，“今天/昨天”的歧义值得用一句话消掉。

## 踩坑点

- **时区与相对时间**：cron 表达式按服务器时区触发，instruction 里写“早上九点”没有意义，写“每天 09:00（Asia/Shanghai）触发”才有意义。
- **幂等性**：失败重试后可能重复推送。后来我在输出前加了一步“检查今天是否已发送过摘要”，用状态文件判断。
- **指令膨胀**：每次出问题就往 instruction 追加一句，两个月后变成 40 行大杂烩，关键约束被淹没。定期整体重写比打补丁有效。
- **权限过宽**：无人值守的任务不应有写操作权限。巡检类任务我只给只读，需要变更的操作走人工确认流程。
- **自然语言输出**：早期让 agent"写一段总结”，下游脚本没法解析。改成固定字段的清单后稳定多了。

## 可复用建议

- 把 instruction 当代码管理：放 git，改一版提交一次，出问题能回滚对比。
- 新任务先**手动触发**跑三五次、看日志，再挂 cron，不要写完直接上线。
- 异常分支的篇幅不该少于主流程——无人值守场景下，失败路径才是常态路径。
- 输出契约里写明“宁缺毋滥”：数据不足时宁可发“今天没有值得报告的内容”，也不要让 agent 编。

## 总结

Cron instruction 的本质，是给一个**没有上下文、不能追问、跑完就走**的新同事写工作交接文档。输入、步骤、输出、异常四个要素齐全，任务就稳；缺哪块，哪块就是下次的故障点。写好它靠的不是 prompt 技巧，而是把你脑子里所有默认假设显式写出来。
