## 背景

用 OpenClaw 跑自动化任务时，最常见的瓶颈不是模型能力，而是串行执行。比如让 agent 审查 20 个插件目录、给 15 个 MCP 工具补测试、跨三个仓库找一处 API 变更的引用——这些任务彼此独立，但主 agent 只能一个个做，上下文还被中间产物塞满，越跑越慢、越跑越糊。

subagent 机制就是为这种场景准备的：主 agent 派生子 agent，每个子 agent 有独立上下文窗口，干完活把结论交回来。听起来简单，实际编排有几条值得提前想清楚的线。

## 问题

直接上手通常会遇到三件事：

1. 主 agent 把「怎么干」和「干什么」混在一段 prompt 里，子 agent 拿到的指令缺上下文，输出没法用；
2. 子 agent 返回的结果原样堆进主对话，几轮下来主上下文反而爆得更快；
3. 多个子 agent 同时写文件，互相覆盖。

## 做法

我目前的编排模式比较固定，分三步：

**第一步，任务分诊。** 先判断能不能并行：只读的分析、检索、代码走读可以并行；有写入的、有依赖关系的必须串行。这一步省下的时间比后面任何优化都多。

**第二步，派发。** 给每个 subagent 一段自包含的 prompt，固定三要素：

- **目标**：只说一件事，例如「读 plugins/foo 下的 MCP 定义，列出与 schema 不符的字段」；
- **边界**：明确可读的路径范围，禁止写操作，禁止派生新 agent；
- **输出格式**：约定返回结构化摘要（结论 + 证据路径 + 置信度），并限制篇幅。

**第三步，聚合。** 主 agent 不记流水账，只收各子 agent 的摘要，冲突结论自己复核。所有写入动作统一收口到主 agent 串行执行。

## 踩坑点

- **子 agent 数量别贪多。** 实测 4–6 个并发是比较稳的区间，再多会撞 API 速率限制，失败重试反而拖慢整体，token 成本也线性上涨。
- **prompt 必须自包含。** 子 agent 看不到主对话历史，引用「刚才那个问题」必然翻车。
- **禁止子 agent 嵌套派生**，除非能控制递归深度，否则一棵树展开后基本无法排障。
- **写冲突要靠分工避免，不是靠锁。** 按目录/模块切分任务，比事后合并省事得多。
- **失败的子 agent 要有兜底**：超时或返回为空时，主 agent 补一条串行执行路径，别让整体卡死。

## 可复用建议

- 把「分诊 → 派发 → 聚合」固化成 prompt 模板，每次只改目标和路径；
- 聚合时强制 schema（如 `{"verdict": ..., "evidence": [...], "risk": ...}`），方便主 agent 机械比对；
- 记录每次编排的子 agent 数、耗时、token 消耗，几轮下来你会得到自己的并发上限经验值；
- 「能并行」的本质是**只读 + 无依赖**，守住这条线，编排就不会出大事。

## 总结

subagent 编排不是堆并发，而是把「读」和「写」分开：读并行拿信息，写串行保一致。在 OpenClaw 这套机制下，主 agent 退化成一个调度器和最终决策者，系统反而更稳。先把模板和边界定好，再谈并发数量。
