## 背景

算法推荐流越来越吵，RSS 反而是唯一你能完全掌控的信息协议：来源自选、时间线干净、没有插手排序。但订阅源一多，未读数本身就成了压力。我的思路是让 OpenClaw 接管中间层：定时拉取 RSS，用 LLM 做过滤和摘要，最终每天只在固定时间收到一份"值得看"的清单。

## 问题

最直觉的做法——每条 entry 直接丢给模型总结——实际跑起来有三个坑：

1. **成本失控**：每天上百条、单条正文几千 token，很快烧不动；
2. **单条摘要信息密度低**：脱离上下文的碎片总结，看完还是不知道"今天整体在发生什么"；
3. **状态不可靠**：guid 不稳定、重复推送、任务中断后断点丢失。

## 做法

架构四段：**拉取 → 清洗去重 → 分级摘要 → 推送**，状态全部落 SQLite。

1. **订阅源配置化**：`feeds.yaml` 按"必读 / 可批量 / 仅存档"分三级，不同级别走不同处理强度；
2. **拉取**：OpenClaw cron 每 30 分钟触发一次 skill，请求带 ETag / Last-Modified，无更新直接退出；
3. **清洗**：RSS 里只有 description 的源，用 readability 抓正文；对正文算 content hash，和库里已存 hash 比对去重；
4. **摘要分两层**：先用小模型对"标题 + 首段"打分（0–10），低于阈值的直接归档；过阈值的条目按主题聚类，一次请求批量精读摘要，输出强制走 JSON schema；
5. **推送**：每晚定时生成 digest 推到聊天渠道，单条高分消息即时提醒，模板里保留原文链接。

## 踩坑点

- **guid 不可信**：有的源 guid 会变，有的干脆没有。用"link 归一化 + content hash"双键去重才稳；
- **反爬**：部分站点 RSS 只给摘要，抓正文直接 403。对这类源降级为"仅标题进 digest"，别硬刚；
- **摘要幻觉**：prompt 里强制"只转述原文出现的事实，不确定就写'原文未明确'"，并要求附一句原文引用做锚点；
- **cron 重叠**：拉取慢时下一轮又启动了。加文件锁，拿不到锁就跳过本轮；
- **JSON 输出不稳定**：别用正则抠字段，直接走 structured output，解析失败进重试队列，重试三次进死信。

## 可复用建议

1. **状态与逻辑分离**：SQLite 只存 hash、时间戳、分数，管线本身幂等，挂了重跑不会产生重复推送；
2. **模型分级是成本关键**：初筛用便宜模型，精读才上主力模型，成本差距是 10 倍级的；
3. **摘要指令写清"为谁摘要"**：个人技术 digest 和团队周报的 prompt 模板应该分开维护；
4. **把"不想看"做成闭环**：推送消息里支持回复指令，标记某源降级或拉黑，写回 `feeds.yaml`，订阅清单随使用习惯自动收敛。

## 总结

这条管线里，LLM 只占 20% 的工作量，另外 80% 是去重、状态管理、失败重试这些脏活——但正是那 80% 决定了你收到的是"稳定的日报"还是"时灵时不灵的玩具"。建议先把去重和状态做扎实，再逐步叠加摘要分级和推送策略。
