## 背景

OpenClaw 这类常驻 Agent 的记忆层基本长一个样：会话结束后把值得留的信息写进记忆库，下次任务开始时通过 `memory_recall` 拉回相关条目拼进上下文。检索实现通常两条路：**语义搜索**（embedding + 向量相似度）和**全文搜索**（FTS5/BM25 关键词匹配）。

我的 Agent 此前一直用纯语义检索，直到几次明显翻车，才认真把两条路都跑了一遍。

## 两种检索各会在哪里翻车

语义搜索的优势是“换种说法也能找到”：用户上次说“部署老是超时”，这次问“发布卡住怎么办”，向量检索能召回。但它在两类查询上表现很差：

1. **精确标识符**。错误码、主机名、文件路径、版本号这类 token，embedding 模型并不理解其内部结构，`ERR_CONN_2043` 和一堆无关文本的相似度可能差不多。
2. **冷门术语**。领域专有名词如果不在 embedding 模型的语料分布里，它在语义空间里的位置基本是随机的。

全文搜索正相反：精确命中极稳，抓 ID 一抓一个准；但同义改写、跨语言（中文问英文记）基本失明。

实测结论很朴素：**语义赢在召回的泛化，全文赢在命中的精确，而 Agent 的真实查询里两种需求都存在。**

## 做法：混合检索的最小落地

我的落地顺序，供参考：

1. **先建全文基线**。记忆存 SQLite，开 FTS5 做关键词检索，零额外依赖，很快能跑。全文结果还可以当作评估语义检索的对照组。
2. **再加语义层**。条目写入时算 embedding 存向量列，查询时对 query 向量化取 top-k。
3. **两路结果用 RRF 融合**。Reciprocal Rank Fusion 按 `1/(k+rank)` 加总，不用调和向量分数与 BM25 分数的量纲，二十行代码的事。
4. **后置过滤**。时间衰减加权 + 去重 + 截断 top-k，最后才拼进上下文。

## 踩坑点

- **中文分词**：FTS5 默认 tokenizer 对中文按整句切，基本搜不到东西。换 jieba 或 trigram tokenizer 才可用，这是中文场景最容易忽略的一坑。
- **query 太长**：Agent 生成的检索 query 经常是一整段话，直接算 embedding 会稀释信号。我让 Agent 先抽 2-3 个关键词再走 FTS 通道。
- **老记忆霸榜**：不加时间衰减时，三个月前的琐碎条目反复被召回，加 recency 权重后明显改善。
- **没有评估集就别调参**：我攒了 30 组“query → 应召回的记忆 ID”做回归测试，每次改权重跑一遍。没有这个，融合系数纯靠玄学。
- **换 embedding 模型 = 全量重建索引**，迁移成本要提前算进去。

## 可复用建议

- 记忆条目里凡含 ID、路径、命令的，确保全文通道能覆盖，别指望向量。
- 元数据（时间、来源、标签）入库时存好，检索后过滤比检索时加权便宜。
- top-k 宁小勿大：脏记忆比没记忆更伤，它会污染上下文并诱导模型编造关联。
- 把 recall miss 的 case 记下来，这是迭代检索策略最值钱的数据。

## 总结

“语义 vs 全文”是个伪选择题，真正的决定因素是你的记忆内容（精确标识符多不多）和查询习惯（改写多不多）。**全文基线 + 语义补充 + RRF 融合**是工程上最稳的默认解；而一套 30 条的评估集，比任何一篇选型文章都管用。
