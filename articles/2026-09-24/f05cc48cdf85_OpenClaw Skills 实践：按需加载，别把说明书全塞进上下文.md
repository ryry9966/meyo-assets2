## 背景

用 OpenClaw 搭常驻 agent 一段时间后，几乎所有容器都会遇到同一个天花板：能力越挂越多，system prompt 越来越肥。浏览器操作、邮件、cron、各种 CLI 封装……如果全部能力常驻上下文，token 开销是一方面，更麻烦的是模型开始在不相关的工具之间犹豫、误选。

Skills 的设计思路是**渐进式披露（progressive disclosure）**：平时只向模型注入每个技能的一行描述；当用户请求命中触发条件时，才把完整的技能说明读进上下文。能力可以无限挂载，但上下文始终只装"当前用得上的那份"。

## 我遇到的问题

之前我在 gateway 上挂了十几个能力，全量注入后 system prompt 接近一万 token，简单任务也慢，且偶发选错工具。另一个痛点是团队协作：同一段操作 prompt（比如"发周报的标准格式"）在群机器人里被反复粘贴，没人沉淀、没人维护。

## 做法

1. **建目录**：技能放在 `workspace/skills/<技能名>/SKILL.md`，跨项目通用的放用户级目录，两者会被合并加载。
2. **写 frontmatter**：核心是 `name` 和 `description`。`description` 是路由的钥匙——它决定模型会不会在合适的时机想起这个技能。具体可用字段以当前版本文档为准。
3. **写正文**：步骤化指令、硬性约束、一个最小可运行示例，最好带可验证的完成标准（"执行后应看到 X"）。
4. **挂资源**：脚本、模板放同目录，正文里写清楚相对路径和调用方式，别让模型猜。
5. **验证**：reload 之后，先问一句该技能领域的问题，看它是否被触发；再看日志，确认平时只有描述被注入、触发时才读全文。

## 踩坑点

- **description 写成产品简介**。"这是一个用来发周报的技能"基本不会触发。改成条件句："当用户要求整理或发送周报、提供会议记录时使用"。
- **单技能太肥**。触发一次吃几千 token，等于没省。正文超过两三屏就该拆分，或把细节挪进附带资源文件。
- **脚本写死绝对路径**。换机器、换容器立刻断，一律用相对 workspace 的路径。
- **技能互相引用形成依赖网**。排查"为什么没触发"时非常痛苦，尽量让每个技能自包含。
- **执行类技能忘了授权**。gateway 对 exec 有审批/白名单机制，触发成功但跑不动是常见现象。
- **命名过泛**。`utils`、`helper` 这类名字要么被误触发，要么永远不被想起。

## 可复用建议

- 把 skill 当**说明书**而不是插件：它是指令 + 资源包，不追求代码级热插拔，胜在改起来快、可版本化。
- description 模板：*当用户要求 X / 出现信号 Y 时使用；用于完成 Z。*
- 收益最大的场景：把群里反复粘贴的固定操作流程沉淀成技能。
- skills 目录进 git。code review 时，值得花时间的是 description，而不是正文。
- 每个技能单一职责，正文里永远放一个最小示例。

## 总结

Skills 机制的价值不在"能挂多少能力"，而在"只在需要时展开"。它把 prompt 工程从"一次写对所有"变成"写对触发条件 + 写清操作步骤"。对我们团队来说，最直接的变化是上下文成本降了一个量级，以及那些原本散落在聊天记录里的操作经验，终于有了归属地。

建议从一个小而高频的流程开始写第一个技能，验证触发链路，再逐步迁移。
