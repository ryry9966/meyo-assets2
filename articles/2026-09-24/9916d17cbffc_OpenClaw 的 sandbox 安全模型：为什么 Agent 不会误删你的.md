# OpenClaw 的 sandbox 安全模型：为什么 Agent 不会误删你的文件

## 背景

让 Agent 直接操作 shell，最怕的不是它写错代码，而是执行一条不可逆的命令。OpenClaw 的设计前提很朴素：不“相信模型”，而是假设它一定会犯错，然后把破坏面收进沙箱。这套机制平时不显眼，但值得每个跑自动化任务的人搞清楚。

## 问题：误删到底怎么发生

实际观察下来，误删基本走三条路径：

1. **语义歧义**：用户说“清理一下项目”，模型执行 `rm -rf node_modules`，但 cwd 已经不对了；
2. **路径幻觉**：模型自己拼出一个似是而非的绝对路径，直接作用在系统目录上；
3. **提示注入**：被读取的文件或网页内容里夹带指令，诱导 Agent 执行删除。

只靠系统提示词里写“请不要删除文件”是不可靠的，必须在执行层兜底。

## 做法：四层同心圆

OpenClaw 的 sandbox 不是单一开关，而是分层结构：

**第一层：工作区边界。** exec 和文件工具默认以 workspace root 为唯一可写根。所有传入路径先做 canonicalize（解析 `..` 和 symlink），解析结果落到根外即拒绝。读可以放宽，写只在工作区内。

**第二层：命令网关。** shell 命令先过拦截器，匹配高危模式（`rm -rf` 作用于 `/` 或工作区外、`mkfs`、`dd`、`git clean -fdx`、`find -delete` 等），命中即 block 或转人工审批。审批界面展示的是**解析后的最终路径**，不是模型给的原始字符串——这一点很关键。

**第三层：容器隔离。** 开启 sandbox 后，exec 在容器内运行：独立低权用户、宿主根目录只读挂载、仅 workspace 可写、网络可关。即使前两层被绕过，最坏情况也只是丢弃一个一次性容器。

**第四层：审计。** 每条命令记录来源（哪个会话、哪条用户消息触发）、原始命令、网关判定结果，出事后可完整回放。

## 最小可用配置

1. 显式设置 workspace root，不要用家目录；
2. 打开 sandbox 开关（容器模式），确认进程以非 root 运行；
3. 审批策略设为“工作区外写操作 + 破坏性命令必须确认”；
4. 跑一次真实任务，对照审计日志检查路径解析结果，重点确认 symlink 场景被正确拦截。

## 踩坑点

- workspace 设成 `/root`，或包含 `.ssh`、`.aws` 的目录，隔离等于摆设；
- `rm -rf "$VAR"` 这种变量拼接，静态匹配容易漏，容器层才是真兜底；
- 往容器里挂载目录时忘了设只读，实际隔离范围比你以为的大得多；
- 复用同一个容器跑多次任务，“一次性”失效，被删的东西就真没了；
- 为了省事关掉审批——模型第一次“自作主张”往往发生在你最贵的目录上。

## 可复用建议

- 永远不让 Agent 以 root 运行，这是成本最低、收益最高的一条；
- 把 workspace 当可丢弃目录：重要数据物理放在外面，配合定期快照；
- 审批时坚持看 canonicalize 之后的路径，不看模型复述的路径；
- 拦截规则只当兜底，主防线永远是边界 + 容器；
- 定期做红队测试：故意下达“清理一下项目”这类模糊指令，观察它到底碰了什么。

## 总结

OpenClaw 防误删不靠模型自觉，而靠四层同心圆：路径边界决定它够得着哪，命令网关决定哪条命令能过，容器决定最坏情况有多坏，审计决定事后能不能查清。给 Agent 权限的正确姿势，是先给最小集，再按真实需要逐条放开——而不是先给全量，再指望它懂事。
