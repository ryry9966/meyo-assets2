## 背景

在 OpenClaw 的插件与自动化实践里，让模型吐 JSON 几乎是标配：MCP 工具的中间结果、Agent 步骤间的结构化传递、插件入参……提示词里明明写了"只输出 JSON"，实际拿到的却是五花八门的形态。本文记录我们处理这类问题的一套防御性做法，不求优雅，求不断。

## 问题

跑得多了，输出基本处于"混合态"：

- ```json 代码围栏包裹；
- 裸 JSON，前后带一句"以下是结果："；
- 自定义标签 `<result>{...}</result>`；
- 中文引号、尾逗号、字符串里夹换行；
- 偶尔一次返回两个 JSON 块。

按单一格式写解析，线上早晚挂。一次 parse 失败，整条自动化流程就断了。

## 做法：把解析做成多级 fallback 管线

核心思路：不赌格式，按命中率排一串策略，逐级尝试，并记录每级的命中情况。

```python
def extract_json(text: str):
    # 1. 直接解析（模型最乖的情况）
    # 2. 剥代码围栏：```json ... ```
    # 3. 标签提取：<result>...</result>
    # 4. 括号配平扫描：从第一个 { 找到配平的 }
    # 5. 轻量修复后重走 1-4：中文引号→英文、去尾逗号、清控制字符
    # 6. 全失败 → 抛结构化错误，由上层决定是否重试
```

几个实现细节：

- 剥围栏用非贪婪正则 `r"```(?:json)?\s*(.+?)\s*```"` 加 DOTALL，并留意嵌套围栏的极端情况；
- 括号配平要处理字符串内的 `{ }`（维护引号状态机），否则会被内容里的花括号骗到；
- 每个策略命中时带上 strategy 名落日志，一周后你就知道该优化哪一级。

解析和校验要分开：解析只保证"是合法 JSON"，结构对不对交给 pydantic / jsonschema。两种失败的处理路径完全不同——解析失败可以修或重试；结构不符通常是提示词问题，改 prompt 而不是改解析器。

## 踩坑点

1. **贪婪正则**：`json(.*)` 遇到字符串里的反引号会直接吃穿；
2. **json.loads 的宽容**：默认接受 `NaN` / `Infinity`，这并不是合法 JSON，下游序列化会炸，建议用 `parse_constant` 拦一下；
3. **多 JSON 块**：模型有时把"解释 + 结果"写成两个对象，取最后一个通常更稳；
4. **修复别无底线**：修复规则越加越多，失败率归零的同时可能掩盖提示词退化。给修复策略设配额和监控，失败率突增说明该改 prompt 了；
5. **别用 `str.strip('`')`** 这类省事手法，边界一多全是雷。

## 可复用建议

- 解析收敛到一个公共模块，全项目只此一处，别让每个插件各写一套；
- 把线上解析失败的原始输出攒成 fixture，解析器每次改动跑回归——这类样本比任何手写测试用例都真实；
- 运行时支持结构化输出 / JSON mode 就优先用，约束解码能消掉大半问题；但 fallback 管线照留，换模型、换供应商时不至于裸奔；
- 提示词里给一个精确的输出示例，并明确"除此之外不要任何字符"，比十句"请规范输出"管用。

## 总结

LLM 输出解析没有银弹，格式混合是常态而非异常。防御性做法归结为三件事：分级 fallback、解析与校验分离、失败可观测。做到这三点，解析失败率通常能压到千分之一以下，而且每一次失败你都知道它死在哪一级。
