## 背景

单 agent 干长任务的老问题：让它梳理一个仓库的依赖、查升级方案、写报告，几十轮工具调用下来，context 里塞满了中间结果，agent 开始遗忘、重复搜索、跑偏。而其中很多步骤其实互不依赖——串行执行纯属浪费时间和 token。

subagent 编排就是针对这个问题的：主 agent 负责拆任务和汇总，子代理各自持有独立 context，只回传结构化结果。听起来简单，实际用起来有不少细节要处理。

## 做法

我最近做的一次实践是跨仓库依赖升级评估，拆分和执行流程如下：

1. **任务拆分**。先让主 agent 列出子任务清单，明确标注依赖关系。有依赖的串行，独立的进并行队列。
2. **定义契约**。每个 subagent 的 prompt 自包含：输入是什么、只做什么、输出格式（强制 JSON 或固定结构）。不假设它能读到主 agent 的上下文。
3. **读写分离**。只读任务（扫描、检索、跑基线测试）放心并行；写任务默认串行，或按文件/目录分区。
4. **扇出执行**。三个并行 subagent：A 扫描仓库出依赖清单，B 查各依赖新版本的 breaking changes，C 跑现有测试建立基线。三者互不接触。
5. **汇总验证**。主 agent 只消费结构化摘要生成升级方案，对关键结论抽查复核，最后派一个独立的写 subagent 改配置。

并发上限先设 3，稳定后再加。

## 踩坑点

- **上下文不共享**。subagent 看不到主 agent 的对话，prompt 里漏一句背景，它就"自由发挥"。我踩过最贵的坑就是 subagent 自行修改了任务范围。
- **并行写冲突**。两个 subagent 同时改同一文件，后者静默覆盖前者。写操作必须串行或分区，没有例外。
- **扇出放大成本**。每个 subagent 都是完整的 agent，token 消耗是乘法不是加法。琐碎任务不值得拆。
- **失败要隔离**。单个 subagent 失败走"重试一次→标记失败→继续"的降级路径，别让整个编排卡死在一个分支上。
- **汇总失真**。subagent 返回的摘要格式太随意，主 agent 会基于残缺信息做决策。输出格式必须强制校验。

## 可复用建议

- **一句话检验拆分**：这个子任务能否在不看主 agent 聊天记录的情况下完成，并给出可验证输出？不能就再拆或合并。
- **只读并行、写串行**是默认策略，偏离它要有明确理由。
- **给每个 subagent 编号并记录日志**，出问题时能回放定位是哪个分支的锅。
- **并发从 2-3 起步**，观察配额和下游服务的承受能力再加。
- 超过 5 个 subagent 时考虑两层编排（fan-out/fan-in），但结构能简单就不要复杂。

## 总结

subagent 编排的核心不是"更多 AI"，而是**上下文隔离 + 依赖管理**：把独立、只读、可验证的部分并行出去，把有状态、有冲突、需要全局判断的部分留给主 agent。先用小规模任务验证拆分方式，再逐步放大，比一上来就搭复杂编排框架划算得多。
