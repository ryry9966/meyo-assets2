## 背景

Agent 和自动化脚本有一个共同特点：它们比你想象的更容易重复执行。网络超时后的重试、cron 任务的重叠触发、用户手动补跑、MCP 工具调用失败后的兜底重跑——在 OpenClaw 的日常实践里，一个"看起来只跑一次"的任务，真实生命周期里往往被执行了两三次。

幂等性（Idempotency）就是让重复执行不出问题的设计前提：**同一操作执行一次和执行 N 次，系统的最终状态一致。**

## 问题

不幂等的自动化任务，故障模式很典型：

- 通知类任务重试后，群里收到两条一模一样的告警；
- 建资源的任务重跑后，产生两个重复的工单/文件/记录；
- 更麻烦的是"部分成功"：任务跑了一半失败，重跑时前半段的副作用又来一遍。

根源是同一个：任务把"执行动作"当成了唯一事件，而不是把"达成某个状态"当目标。

## 做法

**1. 先给操作分类。** 只读操作天然幂等，不用管；带固定键的写入（upsert）天然幂等，优先用；纯追加式操作（发消息、insert）才需要额外设计。

**2. 用稳定的幂等键。** 键必须跨重试保持一致，推荐由业务语义派生：`hash(任务ID + 关键参数 + 时间窗口)`，而不是每次运行现生成的随机 UUID。比如"同步昨天的数据"，键里带解析后的日期，重跑三次也是同一个键。

**3. 先落状态，再执行副作用。** 执行前先写入一条带幂等键的执行记录（或直接依赖数据库唯一约束），成功后更新状态。重跑时先查记录：已成功就跳过，进行中就告警，失败才继续。

**4. 分步任务记录检查点。** 长任务拆成步骤，每步完成即记录进度，重跑从检查点继续，而不是从头再跑。

**5. 善用外部系统的幂等支持。** 不少支付、消息类 API 支持幂等键参数，把自己的键透传过去，比在应用层自己兜底更可靠。

## 踩坑点

- **随机 UUID 当幂等键**：每次重试生成新 UUID，等于没做幂等，这是最常见的错误。
- **时间键跨边界**："按当天日期生成键"的任务在 23:59 失败、00:01 重试，键变了，照样重复执行。
- **先查后写的竞态**：两个并发实例都查到"不存在"，然后都插入。应用层检查挡不住并发，要靠唯一索引或分布式锁。
- **高估外部 API**：默认所有 POST 都可能重复生效，除非文档明确说幂等。
- **状态记录清理太激进**：保留期短于重试窗口，等于亲手拆掉去重能力。

## 可复用建议

- 给常用的工具调用写一层薄封装：自动计算幂等键、查历史、缓存结果，Agent 侧无感知。
- 编排时尽量描述"期望状态"而非"执行动作"："确保这个文件存在且内容为 X"比"写这个文件"天然更幂等。
- CI 里加一条断言：同一任务连跑两次，第二次执行后的状态指纹不变。
- 在 Agent 的系统提示里明确要求：创建任何资源前先查询是否已存在。

## 总结

幂等不是事后补的补丁，而是自动化任务与生俱来的设计属性。一个可用的检验标准：**把你的每个任务假设成"至少会跑两次"来设计**——键稳定、状态先行、检查点完备、并发有约束。做到这四点，重试就从风险变成了普通的容错手段。
