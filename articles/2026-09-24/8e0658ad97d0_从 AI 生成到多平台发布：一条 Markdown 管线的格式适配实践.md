## 背景

用 OpenClaw 这类 Agent 做内容生产，最终产物基本都是 Markdown。但问题出在下游：同一篇文档要发公众号、掘金、知乎、静态博客，各平台渲染规则差异极大。手动复制粘贴再逐处修格式，每篇要花 20–30 分钟，还容易漏。我的做法是把这一步做成一条确定的转换管线，跑在发布之前。

## 问题

- 公众号不支持外链（a 标签会被剥掉）、不支持任意 HTML、图片必须走自家图床
- 知乎对表格、代码高亮的支持有限
- Mermaid、脚注、任务列表只在部分平台可用
- frontmatter 粘进去就是一段脏文本
- 各平台重写标题锚点规则不同，文内跳转几乎必断

核心矛盾在于：Markdown 的“约定”大于“标准”，而 Agent 生成内容时毫无顾忌地用上全部语法。所以需要可测试的转换管线，而不是每次靠人肉判断。

## 做法

1. **规范化**：Agent 输出先过 remark-lint + Prettier，统一标题层级、空行、代码块围栏。此后人工修改一律回到源仓库。
2. **中间表示**：不做正则字符串替换，用 unified/remark 解析成 AST，每个平台适配器都是 AST → AST 的纯函数。
3. **平台适配器**：每个平台一个插件。例：公众号适配器把外链转成「标题 + 脚注 URL」；图片先传自己的 OSS 再替换 URL；Mermaid 在构建期渲染成图后栅格化为 PNG（公众号不支持 SVG）。
4. **能力矩阵驱动降级**：用一份 YAML 声明各平台支持哪些特性，管线按矩阵决定“转换 / 丢弃 / 降级”，不把规则散写进插件。
5. **验证与 dry-run**：`--dry-run` 输出转换后 HTML 到本地预览；准备几组 fixture 做快照测试；每次转换输出 diff 报告（链接数、图片数、表格数前后对比）。
6. **发布**：有 API 的走 API，没有的走浏览器自动化，或生成可直接粘贴进编辑器的内联样式 HTML。

## 踩坑点

- **别在字符串层做替换**。正则处理嵌套列表必翻车，代码块里的示例内容也会被误伤。
- **图片防盗链**：外站图床 URL 粘进公众号会被拦，且平台转存后可能压缩到糊，重要图片要提前控制尺寸。
- **标题锚点**：文内目录链接跨平台基本失效，稳妥做法是转换期整体降级为纯文本。
- **粘贴版 HTML**：公众号编辑器对行内 style 有白名单，用 juice 之类做样式内联再过白名单过滤，比手工调 CSS 可靠。
- **幂等性**：同一篇跑两次结果必须一致，否则你无法信任任何一次发布产物。

## 可复用建议

- 单一事实源：所有平台产物视为 build 产物，只读，改动回到源仓库。
- 适配器纯函数化 + fixture 快照测试；平台规则变了只改适配器，正文不动。
- 能力矩阵 YAML 比代码里的 if/else 好维护得多，接入新平台先填矩阵。
- 锁住 remark 版本，这类库 minor 升级经常改变 AST 行为。

## 总结

这条管线的本质是把“格式适配”从发布动作里剥离，变成有测试、可审计的构建步骤。投入一两天，换来的是每次发布从半小时降到一条命令。Agent 负责生成内容，管线负责确定性格式，两者解耦之后，新增一个平台只是多写一个适配器插件的事。
