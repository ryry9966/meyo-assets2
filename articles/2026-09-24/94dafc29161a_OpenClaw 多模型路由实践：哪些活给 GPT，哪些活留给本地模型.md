# 背景

OpenClaw 的 Agent 跑起来之后，token 账单和响应延迟往往是最先失控的两件事。我们自动化流水线里的请求，大部分其实是格式转换、字段抽取、简单改写这类“低认知密度”任务，真正需要 GPT 级推理的只占两三成。全走云端贵，全走本地又不稳，多模型路由就是为了把这个配比调出来。

# 问题

两种极端我们都试过：

- **全走 GPT**：日均成本高，批处理任务排队等限流，本地 14B 明明能干的活也在烧钱；
- **全走本地**（Ollama 混部 Qwen/Llama）：多步规划和工具调用经常崩，agent 循环里一步错步步错，重试反而更费时间。

本质问题是：路由决策不该靠人手动切，也不该靠“猜哪个模型行”，而应该按任务特征分流。

# 做法

1. **先打标签，再谈路由。** 把 OpenClaw 里的任务类型枚举化：`extract`（抽取）、`rewrite`（改写）、`plan`（规划）、`tool-call`（工具调用）、`chat`（对话）。这一步比任何“智能路由”都重要。
2. **静态规则先行：**

```yaml
routing:
  rules:
    - match: { task: [extract, rewrite] }
      model: local/qwen2.5-14b
    - match: { task: [plan, tool-call] }
      model: gpt-4.1
      fallback: local/qwen2.5-32b
    - default: gpt-4o-mini
```

3. **复杂度兜底。** 静态规则覆盖不了的长尾，用本地小模型做一次廉价打分（0–10），超阈值升级到 GPT。打分 prompt 控制在 100 token 以内。
4. **落路由日志。** 每次请求记录：任务类型、命中规则、实际模型、耗时、token 数。跑一周再调规则，不要拍脑袋。
5. **失败降级链。** 本地模型工具调用格式错误两次，直接切云端，别恋战。

# 踩坑点

- **本地模型的 function calling 是重灾区。** 同一段 JSON schema，GPT 一次过，14B 可能三次都格式不合法。凡要精确调 MCP 工具的，别省这个钱。
- **上下文长度差异会静默截断。** 本地模型 32k 上下文，超长的 MCP 返回结果塞进去直接丢尾部，且不报错。路由层要做长度预检。
- **分类器自身有成本。** 用云端模型做路由分类等于每次请求多一跳，简单任务延迟反而上升。小任务走静态规则，别过分类器。
- **降级要有熔断。** 否则本地服务一抖动，云端配额瞬间被打爆。

# 可复用建议

- 起步只用静态规则 + 一个 default，别上来就搞智能路由；
- 按“任务类型”路由，不要按 prompt 内容路由——前者可测试、可回滚；
- 每周看一次路由日志的成本分布，规则靠数据收敛；
- 高频模板化任务加缓存，命中率往往比换模型省得多。

# 总结

多模型路由不是炫技，是算账的手艺。我们的结论：规划和工具调用交给 GPT，抽取改写留给本地，中间地带用日志数据慢慢收。上线六周后，整体成本降到全 GPT 方案的 35% 左右，p95 延迟基本持平。先能算清账，再谈优化。
