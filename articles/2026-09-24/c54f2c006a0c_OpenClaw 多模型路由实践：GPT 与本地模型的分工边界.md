## 背景

我们的 OpenClaw 实例跑着十几条自动化流：定时巡检、群消息摘要、MCP 工具调用、代码评审预检。接上 GPT 级别的云模型后，月账单一路涨；换成跑在本地 vLLM 上的 Qwen 之后，工具调用失败率又肉眼可见地上升。最后发现真正的问题不是"哪个模型更好"，而是没回答清楚：哪些任务值得花云模型的钱。

## 问题

多模型路由最常见的错误是按"心情"切模型：白天图快全走云，月底心疼钱全走本地。结果是要么账单失控，要么 agent 在关键时刻拿不出可靠的 function calling。路由应该是配置驱动的规则，而不是临时手动切换。

## 做法

**第一步：给任务分类，而不是给模型打分。** 把自己 agent 的调用按四类盘点：

- 结构化提取、分类、打标 → 本地 7B~14B 足够
- 多步规划、复杂工具调用 → 云模型
- 长上下文摘要 → 看上下文窗口，通常云
- 涉及私密数据（聊天记录、内部文档）→ 强制本地

**第二步：把规则落到 OpenClaw 的路由配置里。** 思路是按子代理名和任务标签匹配（字段名以你版本的实际 schema 为准）：

```yaml
routes:
  - match: { agent: "summarizer", tokens: "<2000" }
    model: local/qwen2.5-14b
  - match: { task: "tool-planning" }
    model: gpt-4.1
    fallback: local/qwen2.5-32b
  - match: { tag: "private" }
    model: local/*
    allow_cloud: false
```

**第三步：配置 fallback 链。** 云模型限流或超时时落到本地，保证自动化流不中断；本地搞不定的复杂任务也可以反向升级到云。关键是 fallback 要设次数上限，避免重试风暴。

**第四步：按路由打日志。** 在调用日志里带上 route 字段，每周看一眼每条路由的耗时、失败率和 token 成本，规则才有迭代依据。

## 踩坑点

- **本地模型的 function calling 格式漂移**：同一个工具 schema，云模型稳定，小模型偶尔多字段、漏字段。MCP 工具端要做宽松解析和校验。
- **上下文窗口不一致**：给 128k 窗口设计的摘要插件接到 8k 的本地模型上直接截断。路由规则里要加长度判断。
- **换 embedding 模型会废掉向量记忆**：本地推理和云 embedding 混用时固定一个，别随手换。
- **GPU 被占**：本地推理和别的服务抢显存，表现为超时而不是报错。超时阈值调小并触发 fallback。
- **JSON mode 不是万能的**：本地模型开了 JSON mode 仍可能产出解析失败的内容，重试一次后直接升级到云模型更省心。

## 可复用建议

1. 高频低难度的活永远给本地小模型——这部分往往占调用量六成以上，省钱效果最明显。
2. 工具调用链路里，"决策节点"用云模型，"执行节点"的简单转换用本地。
3. 路由配置进版本库，改动走 PR，回滚有据可查。
4. 新规则先灰度 10% 流量跑两天，看日志再全量。
5. 别拿"响应慢"当切模型的理由，先分清是推理慢还是网络慢。

## 总结

多模型路由的本质，是成本、能力、隐私三者在任务级上的权衡。OpenClaw 提供了配置化的路由能力，但规则本身要靠对自己自动化流的盘点和日志数据来打磨。先分类、再落规则、配好 fallback、按路由看日志——这套流程跑顺之后，云和本地的边界自然会清晰起来。
