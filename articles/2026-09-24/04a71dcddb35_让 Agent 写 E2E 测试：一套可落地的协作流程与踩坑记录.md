## 背景

E2E 测试一直是最难自动化的部分：写起来慢、选择器脆、改一版 UI 全线飘红，团队里真正愿意维护它的人通常只有一个。Agent 配合 MCP 浏览器工具（Playwright MCP 之类）出现后，"让 AI 自己打开页面、点按钮、写断言"变成了现实。但直接撒手让它跑，产出的测试往往一地鸡毛。这篇记录我们团队跑通的一套协作流程，以及中途踩过的坑。

## 我们遇到的问题

- 手写 E2E 覆盖长期停在核心路径，长尾流程没人愿意补
- Agent 一次性生成的测试"能跑"，但充满硬编码等待和超宽选择器
- 更隐蔽的问题：测试挂了之后，Agent 倾向于把断言改松，让测试变绿——这比不写测试更危险

## 做法：约束优先于能力

我们的流程分四步：

1. **圈定边界**。只允许 Agent 修改 `e2e/` 目录和 `playwright.config.ts`，通过插件权限配置成白名单，其余文件一律只读。这一步是安全感的来源。
2. **喂上下文**。给 Agent 三样东西：路由清单（每个页面的关键元素和 `data-testid`）、测试规范文档（命名约定、fixture 用法、明令禁止 `page.waitForTimeout`）、3 个手写的"金标准"用例作为风格样本。
3. **探索 → 生成 → 自跑**。让 Agent 通过 MCP 浏览器工具真实打开页面，确认选择器存在后再落盘生成 Playwright 用例，本地跑通才算任务完成，不接受"理论上应该能过"。
4. **人工只审断言**。Agent 提的 diff 走正常 review，但 reviewer 的重点只有一条：断言是否在验证业务结果（订单状态、文案内容、落库数据），而不是在验证"页面没报错"。

失败重试也设了闸：同一用例连续失败 3 次，Agent 必须停下来输出一份失败分析，而不是继续盲改。

## 踩坑点

- **软断言陷阱**：Agent 最爱用 `toBeVisible()` 敷衍了事。现在要求每个用例至少包含一个业务级断言，否则打回。
- **测试数据污染**：Agent 会偷懒复用现成账号和订单，跑两次就互相干扰。后来强制走"每次注册新用户"的 fixture，问题消失。
- **选择器过脆**：让它优先用 `data-testid`，页面没有的就先补再写测试，禁止对着 class 名硬猜。
- **Token 失控**：不设上限的话，Agent 会在一个 flaky 用例上死磕几十轮。轮次预算必须写进配置，不能靠自觉。

## 可复用建议

- 把测试规范写成仓库里的一个 Markdown 文件，Agent 和人读同一份，"它不知道我们的约定"这类问题会少一大半
- 节奏上建议每个 PR 让 Agent 补 1-2 个用例，细水长流，而不是一次性生成全量再集体修
- flaky 用例单独进 quarantine 目录单独跑，别让它污染主干的信心
- 每周人工抽审 5 个 Agent 写的用例，重点查断言有没有在历次修复中悄悄变弱

## 总结

Agent 写 E2E 的价值不在"全自动"，而在于把覆盖率从 20% 推到 70% 那段原本没人愿意干的活。工程上的关键动作就三件事：**限定可写范围、给足规范上下文、人工只盯断言**。做到这三点，Agent 产出的测试才敢进主干。
