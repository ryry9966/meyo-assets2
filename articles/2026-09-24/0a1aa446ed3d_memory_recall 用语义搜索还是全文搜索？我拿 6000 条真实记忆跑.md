## 背景

OpenClaw 这类长期运行的 Agent，跨会话记忆会从几十条很快涨到几千条。`memory_recall` 的职责是在用户发起新请求时，把相关的旧记忆捞回来塞进上下文，检索质量直接决定 Agent 是“记得住事”还是“答非所问”。目前社区两种主流方案：向量语义搜索（embedding + ANN）和全文搜索（FTS/BM25）。很多新手的默认假设是“语义搜索更先进”，但实测未必。

## 问题

我拿一个约 6000 条记忆的真实库做了对比，查询样本来自近一个月的真实 recall 日志。两个典型失败场景：

- **语义搜索翻车**：查询“怎么修 ECONNRESET"，命中的全是泛泛的网络排障笔记，而精确包含该错误码的那条记忆排到十名开外；
- **全文搜索翻车**：查询“之前那个部署卡住的事”，明明有对应记录，但记录里写的是"CI hang"，一字不中。

结论很直观：精确标识符场景关键词赢，换说法场景语义赢。这不是二选一，是配比问题。

## 做法

1. 从 recall 日志抽样 120 条真实查询，人工标注期望命中的记忆 ID，做成小型评测集；
2. 两套索引跑在同一份数据上：SQLite FTS5 + `bge-small-zh` 向量 + sqlite-vec；
3. 统一指标：recall@5、P95 延迟、建索引耗时；
4. 补一组混合方案：两路各取 top10，用 RRF（倒数排名融合）合并。

结果（供参考，非普适结论）：单路 FTS5 recall@5 约 68%，单路向量约 74%，RRF 混合 88%。混合方案 P95 延迟只增加不到 40ms——这个规模根本不需要独立向量库。

## 踩坑点

- FTS5 默认分词器对中文几乎失效（整句当一个 token），必须换 trigram tokenizer 或先 jieba 分词再入库，否则中文召回直接归零；
- embedding 模型换版本后向量不兼容，全库重建，评测集务必留着做回归；
- 记忆切块粒度对结果的影响比检索算法更大：按“一条记忆”整块索引最省心，别过度切分；
- 不加时间衰减，三个月前的旧结论会反复盖过新结论，建议按 `updated_at` 加权；
- 混合排序别用分数直接相加，两路分数量纲不同，RRF 是稳妥默认。

## 可复用建议

- 冷启动直接 FTS5 + trigram，零成本覆盖大部分精确查询；
- 等评测集显示“换说法类查询”recall 不达标，再叠加向量层，别一步到位；
- 万条以下记忆用 sqlite-vec 足够，无需引入独立向量数据库；
- 评测集是资产，每次换模型、改切块策略都重跑一遍；
- recall 结果带上来源和置信度标记，方便下游 Agent 自己决定信多少。

## 总结

语义搜索 vs 全文搜索，答案不是“哪个好”，而是“各管一段”：精确标识符靠关键词，意图改写靠向量，混合 + 时间衰减是记忆召回的务实默认。先用日志建评测集，再让数据决定要不要加复杂度——这比追逐“更先进的检索”重要得多。
