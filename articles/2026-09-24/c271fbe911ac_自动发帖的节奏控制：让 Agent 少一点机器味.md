## 背景

社区里跑自动发帖的人越来越多：OpenClaw agent 定时把插件更新、日报、汇总发到论坛或群频道。技术链路不难——生成、格式化、调 API 发出去，一晚上就能跑通。真正难的是后面两周：帖子开始被折叠、收到负反馈、被老用户屏蔽，甚至账号被限流。

复盘下来，问题大多不在内容，而在节奏。

## 问题：机器味从哪来

把被限流账号的发布时间拉出来看，特征非常明显：

- 间隔精确固定，每 30 分钟一条，秒级误差都没有；
- 内容批量生成后倾泻式发布，一分钟三条然后沉寂四小时；
- 凌晨三点照发不误，时区明显不对；
- 版式、长度、标题结构几乎逐字复刻。

人能看出来，风控规则自然也能看出来。更隐蔽的一种：发布完全不看社区状态——频道里正讨论得热闹，一条长日报硬插进去，观感极差。

## 做法

我们最后收敛成五步，核心是“生成与发布解耦”：

1. **队列化**。agent 只负责生成并产出入队，由一个独立的 scheduler 插件负责出队发布。这是后续所有控制的前提。
2. **加抖动**。目标间隔叠加 ±25% 随机偏移，避开整点和半点。不要用均匀随机——那只是“过于整齐的乱”。更好的做法是按社区历史活跃时段拟合分布，从中采样。
3. **设静默时段和日配额**。凌晨 1–8 点不发布，单日总量封顶，超了顺延。时区以社区所在时区为准，不是服务器为准。
4. **感知上下文再发**。出队时先拉目标频道最近消息：正在活跃讨论就延迟半小时；上一条自己的帖子没人理，主动降频。
5. **退避与审计**。收到限流信号或删帖反馈，指数退避并下调日配额；每次调度决策（为何提前、延迟、丢弃）写日志，出问题能回放。

## 踩坑点

- **重试制造突发**：发布失败立即重试三次，等于自己给自己造一波连发。重试同样要加抖动和退避。
- **多实例各自抖动**：三个 agent 实例独立随机，整体上仍然扎堆。抖动要在共享的 scheduler 层做，不要散在实例里。
- **积压补偿**：服务重启后把积压消息一口气补发，是最典型的翻车现场。追赶速率必须有硬上限。
- **只随机时间不随机内容**：时间打散了，两条帖子版式一字不差，照样一眼假。
- **UTC 陷阱**：cron 按服务器时区跑，国内社区在本地凌晨收到“早安日报”。

## 可复用建议

- 把节奏参数当配置而不是代码：活跃窗口、最小/最大间隔、日配额、静默时段全部外置，改行为不动逻辑。
- 调度器做成通用插件，所有发帖型 agent 共用一份节流实现，别各写各的。
- 新账号、新板块先按日常配额的 1/3 灰度跑两周，看负反馈再放开。
- 重要或低置信度的内容走人审队列，human-in-the-loop 不丢人。

## 总结

机器味不是自动化的必然产物，而是“任务完成即发布”这种偷懒架构的产物。把发布当成一个有独立策略的服务——有抖动、有配额、会看上下文、能听反馈——agent 的发言才能自然融入社区节奏。如果只做一件事：先加抖动和静默时段，这一步就能消掉八成显眼的问题。
