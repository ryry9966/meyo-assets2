## 背景

跑 OpenClaw 或任何带工具调用的 Agent，一段时间后都会撞上同一个问题：它该自己干，还是停下来问我？问多了，读个文件都要确认，基本不可用；问少了，删错数据、消息发错群、替你下单，都是真疼。多数人的第一反应是在 system prompt 里写一句"危险操作先问我"——跑两周就会发现这不靠谱。

## 问题

根源在于：用提示词划边界，等于把安全约束放进概率模型里，换个模型、调个温度、上下文一挤就漂移。正确姿势是把"问不问人"当成工程问题：定义边界、在工具层强制执行、靠日志复盘。判断依据是两条轴——**可逆性**（能不能撤销）和**影响半径**（出错时波及谁：只有你，还是外部的人、系统、资金）。

## 做法：一个可落地的五步模型

1. **先列事故清单。** 写下你的 Agent 最坏能干出的五件事（对外发消息、删数据、支付、动凭证、群发），直接进"必问"名单。这一步比任何方法论都值钱。
2. **按两条轴分级：**
   - 可逆 + 只影响本地（读文件、检索、写草稿）：默认放行，不问。
   - 可逆但对外可见（往测试频道发消息）：放行 + 全量日志。
   - 不可逆 / 涉钱 / 对外不可撤回（发送、删除、部署）：硬性中断，交还给人。
3. **闸门做在工具层，不做在提示词里。** 把危险工具包一层 wrapper 或 MCP 中间件：命中确认名单就返回 `needs_confirmation`，由外层发起审批流，人批准后才真正执行。记住，模型说"我会问用户"不等于问了。
4. **高危操作走 plan → approve → execute。** Agent 先产出操作清单（哪些路径、发到哪、金额多少），人批一次计划，再一次性执行，避免 50 个文件确认 50 次。
5. **加预算和停止条件。** 单次运行的资金上限、消息条数上限、时长上限，触线就停下汇报，而不是中途问"要不要继续"。

## 踩坑点

- **审批疲劳**：必问名单太长，人会变成无脑点"允许"，闸门形同虚设。名单要短而狠。
- **批准没有作用域和时效**：上周批的"可以清理临时目录"不该覆盖今天的删除。批准默认一次性或带短 TTL，并绑定精确参数。
- **收件人不校验**："发给团队"这种指令，Agent 选错频道的概率远超想象。对外发送必须把目标对象写进审批内容。
- **参数错填**：工具被批准了，参数却是模型自由发挥的。按 schema 校验，路径、金额做白名单和上限。
- **只在提示词里约束**：凡是出事会疼的规则，必须落在代码层。

## 可复用建议

- 新工具先跑 shadow mode：只读跑一周，翻日志，再逐步放开写权限。
- 默认策略：钱、删、外发、凭证一律默认拒绝；其余默认放行 + 日志。日志是你以后敢放松的依据。
- 出一次事故收紧一个点，平时别凭感觉加限制，否则系统会慢慢变得不可用。
- 审批数据是产品反馈：某类操作被频繁批准，就降级为自动；被频繁拒绝，就从能力清单里移出去。

## 总结

权限边界不是一句 prompt，而是一层工程控制：用"可逆性 × 影响半径"定分级，在工具层做硬闸门，批准带作用域和时效，配预算和日志。让 Agent 在便宜的错误上自由，在贵的错误上停下来——这比"全自动"和"步步都问"都更接近能长期运行的状态。
