## 背景

跑 OpenClaw 或任何本地 Agent 一段时间后，你会发现失败大头往往不是模型能力，而是环境错配：Agent 执行 shell、调 MCP 工具、跑插件，全靠对这台机器的"假设"。一旦你有 MacBook + Linux 服务器 + 容器多套环境，这些假设就开始批量失效。

tools.md 是个很朴素的约定：把机器上真实可用的事实写进一个 Markdown，会话启动时随 workspace 带给 Agent。不是新技术，但比事后排障便宜得多。

## 问题

典型的错配场景：

- Agent 默认 `ffmpeg` 在 PATH 里，服务器上根本没装；
- 本机是 `brew`，服务器是 `apt`，命令混着来；
- 笔记本走了代理，服务器直连外网超时；
- 容器重建后 Python/Node 版本变了，旧脚本直接挂。

这些不是 bug，是"事实与假设的差值"。与其让 Agent 报错 → 探测 → 重试，不如启动时就把事实递过去。

## 做法

1. **分层**。机器级放 `~/.openclaw/workspace/TOOLS.md`：OS、包管理器、常用二进制及版本、代理、特殊限制；项目级放仓库根目录的 `TOOLS.md`：项目脚本、虚拟环境路径、端口、测试命令。同名条目项目级优先。
2. **只写事实，不写指令**。写"python3.11 在 /usr/local/bin，系统另有 3.9"，不写"请用 3.11"。指令归 AGENTS.md 管，混在一起两边都难维护。
3. **脚本生成，人工补充**。写一个 detect 脚本探测存在的二进制、版本、`HTTP_PROXY`、docker 可用性，输出 Markdown；生成后人工追加几句"机器备注"（比如显卡驱动太旧，勿动）。
4. **控制篇幅**。一屏以内。它每次进上下文，多一行就多一份 token 成本，也多一分注意力稀释。

## 踩坑点

- **绝不写密钥**。token 属于 `.env`，tools.md 只写"密钥在 .env，用 dotenv 读"这一句。
- **生成脚本要有降级标记**。探测不到的命令要明确标"不可用"，否则容易留下一段文档虚构——比不写更糟。
- **别和 MCP 重复**。MCP 工具能自描述，让 Agent 运行时发现即可；tools.md 只写"配置在哪个文件"这类稳定事实。
- **更新时机要固定**。容器重建、系统升级后必跑；把生成命令挂进装机脚本或 dotfiles 安装流程，别靠记忆。

## 可复用建议

- 用 diff 思维写：只记录与默认假设不同的部分，标准环境不用提，文件越薄越好维护。
- 定期让 Agent 自己审计：让它对照 tools.md 与实际环境跑一轮，输出差异清单，比人手动核对勤快。
- 换机迁移时，带走生成脚本而不是文件——文件是环境的快照，脚本才是事实的来源。

## 总结

tools.md 的价值在于把"猜环境"变成"读环境"。它不酷，但把最容易碎的一层——本地事实——固化成了可版本化、可审查的文本。记住四条：分层、只写事实、脚本生成、定期对账。环境这一层稳了，Agent 的下限自然就抬上去了。
