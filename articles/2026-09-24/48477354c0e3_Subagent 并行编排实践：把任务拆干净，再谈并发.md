## 背景

用 OpenClaw 做自动化一段时间后，最常见的瓶颈不是模型能力，而是串行执行。比如"巡检 12 个 MCP 插件的版本与配置漂移"，主 agent 一个个跑，慢是一方面，更难受的是中途产生的大量中间输出会把主会话上下文撑满。subagent 机制正好针对这个问题：主 agent 可以派生多个独立会话，各自带上下文跑任务，跑完只把结论交回来。

## 什么任务适合并行

两类场景收益明显：

- **同构批量任务**：对象多、流程一致、彼此无依赖，比如批量巡检、批量摘要、批量格式转换。
- **中间过程嘈杂的任务**：子任务会产生大量阅读和推理，但你只要结论。隔离到 subagent，主上下文只收摘要。

反过来，任务之间有顺序依赖、或者要写同一个文件/同一份状态的，不要强行并行。

## 做法与步骤

1. **拆分与独立性检查**。把任务清单写成互相独立的一行描述，逐条问：这个子任务只靠给定输入能否完成？有没有共享写目标？两条都过才进并行池。
2. **写自包含的 subagent prompt**。每份四段：目标、输入（材料直接内联或给明确文件路径）、返回格式、禁区（不允许改全局配置、不允许反向追问）。subagent 看不到主会话，prompt 必须能独立执行。
3. **控制并发**。同时 3–4 个为宜，更多并不线性提速，还容易撞 API 速率限制。
4. **约定返回格式**。要求结构化短摘要：结论一行、关键数据、异常项列表，并硬性限制总长度，禁止返回完整过程记录。
5. **主 agent 汇总落盘**。收齐后统一聚合出最终报告，子任务明细各自存独立文件备查。

以 12 个插件巡检为例：串行半小时起步，拆成 4 路并行后几分钟出结论，主会话只多出十几行汇总。

## 踩坑点

- **共享写目标冲突**：多个 subagent 同时写同一工作区文件，互相覆盖。解法是每个子任务分派独立输出文件，合并交给主 agent。
- **结果被截断**：subagent 返回太长，只剩半截。解法是 prompt 里硬性限长，并明确"只返回结论"。
- **输入塞太多**：把整个项目文档丢给每个 subagent，token 成本随并发数放大。按子任务裁剪输入，大数据走文件引用而非内联。
- **假并行**：拆完才发现子任务有依赖，跑完返工。拆分阶段的独立性检查不能省。
- **成本失控**：并行等于成本乘数。新任务类型先拿 2–3 个样本试跑，估算单任务消耗再放量。

## 可复用建议

- 一条判断标准：任务清单能写成互相独立的一行描述，就值得并行；写不出来就别拆。
- 并发上限 3–4；给每个 subagent 设预算（轮数、返回字数）。
- prompt 模板化沉淀：目标 / 输入 / 返回格式 / 禁区 四段结构，新任务只换内容。
- 结果落盘习惯：子任务结论进独立文件，主 agent 只读汇总，方便事后审计与重跑。

## 总结

subagent 并行的核心价值不是"快"，而是上下文隔离和结构化分工：脏活和中间过程留在子会话，主 agent 只做拆分、派发、聚合。先把任务拆干净、把返回格式约定死，再调并发数。顺序反了，并行只会更快地制造混乱。
