## 背景

最近在 OpenClaw 里跑自动化任务，遇到一类典型工作：给老项目批量补测试、对几十个 MCP 数据源做巡检、同时生成多份文档。这些任务共同点是步骤重复、彼此独立，但总量大。让单个 Agent 顺序处理，跑一次要四十多分钟，中途还经常因为上下文塞满而"失忆"，后半个任务的质量明显不如前半个。

## 问题

单 Agent 串行模式有三个硬伤：

1. **上下文挤爆**：大量中间结果占满窗口，后期步骤质量下降；
2. **任务互相污染**：一个子任务出错，错误信息混进上下文，影响后续判断；
3. **纯串行太慢**：时间成本随任务数线性增长。

## 做法

我的编排思路很简单：**主 Agent 只负责拆解、调度、汇总，执行全部下放给 subagent**。

1. **拆解**：主 Agent 把任务切成独立子任务清单，每个子任务写清输入、期望输出、可用的 MCP 工具白名单；
2. **并发控制**：队列限制同时跑 3~4 个 subagent。并发再高，token 消耗和 API 限流会把收益吃光；
3. **工作区隔离**：每个 subagent 分到独立目录（或 git worktree），避免并行写同一批文件；
4. **返回契约**：subagent 只返回结构化摘要——状态、改动文件路径、关键结论、错误信息，不返回完整过程；
5. **汇总**：主 Agent 收齐结果统一合并，失败子任务进入重试队列。

## 踩坑点

- 第一版让 subagent 返回全部日志，主 Agent 上下文照样爆炸。改成"摘要 + 落盘路径"后解决，日志写文件按需读取；
- 并行写同一仓库出现过文件互相覆盖，后严格用 worktree 隔离，最后由主 Agent 统一合并分支；
- 粒度踩过两次坑：拆太细，调度开销比执行还贵；拆太粗，失败重试代价高。目前经验是单个子任务控制在 5~15 分钟工作量；
- 有个 subagent 挂着全量权限的工具，顺手改了不该改的配置。现在每个 subagent 只挂必需工具，权限最小化。

## 可复用建议

- 子任务清单做成 YAML，编排脚本读清单起并发池，任务定义和执行逻辑解耦；
- 固定 subagent 返回的 JSON schema，汇总阶段就能自动化处理；
- 中间产物全部落盘并带上子任务 ID，出问题能复盘到具体分支；
- 编排脚本先拿 2~3 个任务小规模试跑，确认合并逻辑无误再放量。

## 总结

subagent 编排的本质不是"多用几个模型"，而是**把编排和执行分层**：主 Agent 管上下文和决策，subagent 管隔离执行。做完这套改造，原来四十多分钟的批处理稳定在十分钟左右，失败可重试、过程可复盘。它不复杂，难点在返回契约和隔离边界——这两件事设计好，并行才真正省心。
