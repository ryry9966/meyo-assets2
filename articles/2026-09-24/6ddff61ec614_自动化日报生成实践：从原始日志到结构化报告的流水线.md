## 背景

团队每天的进展汇总——昨天跑了多少任务、出了哪些报错、部署了什么——长期靠人肉翻日志拼凑。数据散在应用日志、网关访问日志和部署记录里，格式各异。写日报的人每天要花二十到三十分钟，口径还经常对不齐。我们的思路是：把这件事做成一条定时流水线，**代码负责算数，Agent 负责说话**。

## 问题拆解

最初尝试直接把原始日志丢给模型总结，实践下来有三个硬伤：

1. **上下文装不下**：一天的访问日志轻松几十万行；
2. **数字不可信**：让模型"数一下错误次数"，每次结果都不一样；
3. **格式漂移**：报告结构随机，没法做日环比和沉淀。

由此得出核心结论：LLM 不该当会计，只该当撰稿人。统计口径全部由代码完成，模型只消费一份干净的结构化中间产物。

## 流水线做法

整条链路分五步，由 OpenClaw 的定时任务驱动：

1. **采集**：凌晨拉取昨日时间窗口数据——应用日志、网关日志、部署记录、git log。每类来源一个独立采集插件，输出统一格式的中间 JSON。
2. **清洗归一**：用结构化解析把日志行转成事件对象（时间、级别、模块、消息）。解析失败的行进"死信桶"，不阻塞主流程。
3. **聚合统计**：纯代码计算——错误总数与分布、Top N 慢接口、部署清单、异常关键词命中，产出符合预定义 schema 的 `daily_facts.json`。
4. **Agent 撰稿**：通过 MCP 把 `daily_facts.json` 喂给 Agent。prompt 只做两件事：按固定章节模板组织语言、对超阈值指标给出提示性描述。明确禁止编造数字，所有数值直接引用输入字段。
5. **投递归档**：渲染为 Markdown 推送到群机器人，同时按日期落盘，供月末汇总复用。

关键设计：中间产物是强 schema 的 JSON，日报只是它的一个视图。想换周报、换口径，改聚合层即可，撰稿逻辑不动。

## 踩坑点

- **时区**：第一版用 UTC 算"昨天"，凌晨的报错全被划到前一天。后来在聚合层显式传时区，并在中间产物里记录窗口起止时间。
- **日志格式悄悄变了**：上游改了字段名，解析器静默失败，日报连续几天错误数为 0。教训是给解析失败率设阈值告警，而不是等"看起来不对"。
- **重复投递**：任务重跑会发两份日报。改为输出文件以日期为键、先检查后写入，天然幂等。
- **prompt 不进版本库**：早期 prompt 散在配置里，改一次风格报告就变样。现在 prompt 与 schema 一起进 git，改动有 diff 可查。

## 可复用建议

- 先定中间产物的 schema，再写采集和撰稿。schema 是整条流水线的契约。
- 模型只做组织语言，不做统计计算；数字必须来自代码算好的字段。
- 一切以日期为键：采集窗口、输出文件、归档路径，保证幂等可重跑。
- 保留 dry-run 模式，只产出中间 JSON 不投递，调试聚合逻辑时非常有用。
- 给流水线自己也记日志：生成耗时、解析失败率、token 消耗。流水线坏了比报告错了更隐蔽。

## 总结

流水线上线后，日报从每天半小时的人肉工作变成早上自动出现在群里的一条消息，数字口径稳定，历史可回溯。真正花时间的不是接模型，而是把日志清洗和统计口径这两个"无聊"的部分做扎实。把 Agent 的角色刻意收窄——不做它不擅长的事，整条链路才可靠。欢迎在社区帖子里交流你们的日报/周报自动化实践。
