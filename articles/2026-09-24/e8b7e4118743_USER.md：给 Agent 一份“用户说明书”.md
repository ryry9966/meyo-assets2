## 背景

OpenClaw 这类常驻 Agent 和一次性对话机器人最大的区别，在于它有一个持久化的工作区。每次会话启动时，工作区里的一组 Markdown 文件会被注入上下文：SOUL.md 定义 Agent 的性格，TOOLS.md 说明能力边界，而 USER.md 描述的是"你是谁"。

多数人的 USER.md 要么是空的，要么还留着初始模板。结果就是：模型知道世界上的一切，唯独不知道你的任何事。

## 问题

没有像样的 USER.md，日常使用会遇到三类反复出现的摩擦：

1. **重复自我介绍**。"我的服务器是 ARM 架构""我们用 pnpm 不用 npm""回复用中文"，这些话每周都要说一遍。
2. **错误的默认假设**。Agent 给出 apt 命令而你用 brew，生成的 CI 配置默认 x86，时间安排忽略你的时区。
3. **风格不匹配**。你想要简短直接的结论，它给你面面俱到的长文。

这些都不是模型能力问题，是上下文缺失问题。

## 做法

**第一步：想清楚定位。** USER.md 是手工维护的静态画像，不是任务状态。动态内容（项目进展、临时待办）放 MEMORY.md 或任务文件里，两者混写必然冲突。

**第二步：只写"会影响决策的事实"。** 一个可用的四段结构：

```markdown
# 环境
- 主力机 macOS (Apple Silicon)，服务器 Ubuntu ARM
- 时区 UTC+8，工作语言中文

# 技术栈
- 包管理一律 pnpm，不要建议 npm install
- 部署走 Docker + 自建 VPS

# 偏好
- 回答先给结论，细节放最后
- 代码示例直接可运行，不要伪代码

# 禁止
- 不要主动升级依赖大版本
- 不碰 prod 分支
```

判断标准很简单：删掉这条，Agent 的输出会变差吗？不会就删。

**第三步：初始化可以偷懒。** 让 Agent 对你做一次访谈："请问我 10 个问题，帮我生成 USER.md 草稿"，然后自己删改，比从零写快得多。

**第四步：当配置管理。** 放进 dotfiles 仓库做版本控制，多台机器同步，每月扫一遍删掉失效条目。

## 踩坑点

- **写成简历**。"五年后端经验"对 Agent 没有操作意义，"后端只用 TypeScript"才有。
- **塞敏感信息**。USER.md 会随上下文进入每次会话，还可能被工具调用带出。密钥、密码、详细住址一概不写。
- **太长**。每次会话都消耗 token，控制在一屏能读完的量级。条目越多，单条权重越低。
- **写完不维护**。换了机器、换了栈没更新，Agent 会拿着半年前的假设一本正经地犯错。
- **语言不一致**。用中文写，Agent 的默认回复语言通常会跟随，这本身是个 feature。

## 可复用建议

- 检验方法：新开一个会话，问"我现在该用什么命令装依赖"，看它是否引用了你的约定。
- 负面约束单列一段。禁止事项比正面描述更不容易被忽略。
- 结合 MCP 场景：如果你的 MCP server 区分 dev/prod 环境，把环境约定写进 USER.md，能明显减少误操作。

## 总结

USER.md 是投入产出比最高的 Agent 定制手段：十几行文本，换来的是每次会话少说十句话。把它当配置而不是文档来对待——短、具体、可验证、进版本库。写它的过程本身也有价值：你会被迫想清楚，自己真正的工作约定到底是什么。
