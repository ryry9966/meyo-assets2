## 背景

OpenClaw 的 cron 任务让 agent 具备无人值守能力：每日早报、定时巡检仓库、周期性告警汇总。社区里一个常见现象是：同一个需求，手动聊一次效果不错，挂上 cron 之后输出时好时坏。排查下来，问题大多不在调度配置，而在 instruction 本身——大家习惯用「聊天的方式」写定时任务。

## 问题：cron 不是聊天

交互式对话里用户在场：agent 理解偏了可以追问，输出不对可以纠正。cron 任务执行时没有人在场，instruction 是唯一的上下文。判断标准因此很直接：**这条指令能否被一个完全不了解背景的执行者独立完成？**

失败的典型写法：

> 每天早上 8 点帮我总结一下昨天的工作。

总结什么数据、发到哪里、拿不到数据怎么办，全都没有答案。agent 只能自由发挥，而自由发挥在无人监督时就是事故来源。

## 做法：六段式模板

我目前固定用这个结构写 cron instruction：

1. **目标**：一句话说清任务产出什么。
2. **数据源与工具**：明确从哪取数（哪个 MCP 工具、哪个文件路径），不要假设 agent 记得任何历史会话。
3. **步骤**：3–5 步以内的执行顺序，工具调用间的依赖写清楚。
4. **输出契约**：发到哪个频道或文件、格式是什么、长度上限（如「不超过 15 行」）。
5. **失败处理**：显式授权失败——「若工具不可用，发送失败说明并注明原因，不要编造数据」。这条最重要。
6. **时间锚点**：写明时区和统计窗口，如「统计 UTC+8 昨天 00:00 至 24:00」。

改写后的例子：

> 每日 08:00（UTC+8）执行。调用 github 工具拉取 org/repo 过去 24 小时的 closed issues，按「已完成 / 阻塞」两类各列不超过 5 条，单条一行，发送到 #daily 频道。若工具调用失败，发送「数据源异常：<原因>」，不要推测内容。

## 踩坑点

- **假设 agent 有记忆**。多数框架下 cron 是冷启动会话，历史对话不可用，上下文必须全部内联。
- **相对时间不锚定**。「昨天」依赖执行时刻，跨时区或调度延迟会让统计窗口漂移，务必显式写时区。
- **没有失败出口**。工具挂掉时模型倾向编一个「看起来合理」的结果，比失败本身更糟。
- **输出没有落点**。生成一大段但没说发到哪，任务显示成功，人却什么都没收到。
- **一个任务塞所有需求**。日报和 15 分钟一次的告警，频率与容错要求完全不同，拆开写；高频任务的指令要更短。
- **没有成本预算**。「详细分析」配上高频调度，账单会很诚实。给输出长度设上限，等于给 token 设上限。

## 可复用建议

- 上线前手动触发 2–3 次验证输出；上线后回看执行日志，而不是只看有没有报错。
- instruction 纳入版本管理，改动留 diff，出问题可回滚。
- 每月审查一次：没人看的输出就是噪音，直接删任务。
- 从高频短任务起步，跑稳之后再叠加复杂度。

## 总结

cron instruction 本质是无人值守场景下的接口设计：输入、处理、输出、异常路径都要显式定义。写得像 runbook，任务就可复现；写得像聊天，就是在赌运气。
