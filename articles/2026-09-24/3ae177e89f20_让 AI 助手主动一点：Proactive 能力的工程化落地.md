## 背景

多数人的 AI 助手仍停留在纯被动模式：你发消息，它回话，会话结束就"断电"。但真正省时间的场景往往是反过来的——磁盘快满了它先发现、日程冲突它先提醒、PR 卡了两天它先去催。OpenClaw 这类常驻 agent 框架天然具备做 proactive 的条件：有心跳、有工具、有消息通道。缺的不是触发机制，而是判断和克制。

## 问题

把 proactive 做砸的方式高度一致：助手每五分钟汇报一次"没什么新情况"，一周后你把它静音。核心难题不是"怎么让它动起来"，而是"什么时候它应该闭嘴"。一个主动的 agent 本质上是在替你做注意力分配，做错了比不做更糟。

## 做法

我们的实现分三层，按风险递进：

1. **定时层（cron / heartbeat）**：最便宜、最可控。给 agent 挂周期任务，每两小时跑一次巡检 prompt，输入是固定清单：磁盘、日历、CI 状态。确定性高，适合纯读取类任务。
2. **事件层（webhook / 文件监听 / 消息钩子）**：由 MCP server 或插件把外部事件推进来。事件层必须做去重和节流，同一个 key 在冷却窗口内只触发一次。
3. **判断层**：前两层只负责"有事发生"，要不要打扰用户由这层决定。把触发上下文加一份评分规则交给模型，强制三选一：直接办（低风险）、进日报（中等）、立即提醒（紧急）。规则里写死：任何写操作默认不允许"直接办"。

配套的几个关键件：

- **静默时段**：晚十点到早八点只累积不提醒，早八点合并成一条 digest。
- **行动白名单**：读文件、查状态可自动执行；发消息、删东西、提交代码必须确认或走白名单。
- **全量日志**：每次主动动作记录触发源、判断理由、执行结果，这是后面调规则的唯一依据。

## 踩坑点

- **心跳太密**：最初设 15 分钟，token 成本翻了几倍，产出几乎为零。改成 2 小时加事件驱动兜底后，成本降八成，效果没变差。
- **自循环**：agent 发出的通知被自己的消息监听器捕获，触发新一轮判断，十分钟刷了三十条日志。解法：给自家发出的消息打标记，监听层直接丢弃。
- **去重键设计错误**：按事件 ID 去重，结果同一个 PR 的多次 webhook 各有各的 ID，提醒连发。改成按"业务实体 + 动作类型"去重才稳定。
- **判断层永远选"立即提醒"**：模型天然倾向多报告。在 prompt 里塞正反例，并加一条硬规则——"如果这件事晚 6 小时说也没损失，必须进日报"——才压下来。

## 可复用建议

- 三档响应（静默执行 / 日报合并 / 立即打断）比二档（做/不做）好用得多，值得直接抄。
- 先只做只读监控，跑两周、看日志，再放开第一个写操作。别一上来就让它代发消息。
- 每周花十分钟回看主动动作日志，删掉"你从没点开过的提醒"，这个反馈循环决定系统能不能长期留下。
- 把判断理由也存下来，排查误报时，理由比结果有用。

## 总结

Proactive 不是加个定时器就完事。它是一个三件套：触发系统负责发现问题，判断系统决定要不要说，克制系统保证说了有人听。触发只占工作量的两成，剩下八成在去重、静默、白名单和日志这些不起眼的地方。一句话：让助手主动不难，难的是让它学会闭嘴——而这恰恰是它能不能长期留在你桌面的决定因素。
