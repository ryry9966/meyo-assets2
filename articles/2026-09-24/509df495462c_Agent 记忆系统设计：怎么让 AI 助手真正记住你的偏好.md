## 背景

LLM 本身无状态，关掉会话就什么都没了。Agent 框架（OpenClaw 这类）解决了单次会话内的上下文管理，但跨会话的用户偏好——“回复要简洁”“部署脚本用 bash 不要 fish”“周三别安排会议”——依然要自己设计一套记忆层。这事儿听起来简单，做起来最容易翻车。

## 问题

两个常见极端：

1. **全塞系统提示**：把历史对话总结全部塞进 system prompt，一两周后上下文爆掉，正式任务反而被挤掉。
2. **逢句必存**：每条消息都向量化入库，召回时全是“用户上次问了天气”这种噪音，检索质量崩塌。

核心难点不在“存”，而在三个问题：**写什么、读多少、怎么处理冲突**。

## 做法

我把记忆分四层，前三层是数据，第四层是策略：

**1. 会话内记忆**：框架自带，不展开。

**2. 工作记忆**：当前任务的状态、中间产物，放 scratchpad。任务结束即清理，严禁流入长期层。

**3. 长期偏好记忆**：结构化条目，建议 schema：

```json
{
  "id": "mem_8f2a",
  "content": "代码解释时先给结论再展开",
  "category": "reply_style",
  "confidence": 0.9,
  "source": "explicit",
  "created_at": "...",
  "last_used_at": "...",
  "superseded_by": null
}
```

**4. 写入与召回策略**：

- **写入**：两条触发规则。用户显式表达（“以后记住…”“我喜欢…”），或同类行为重复出现 2-3 次再由 LLM 抽取入库。写入前让模型自问一句：这条信息三个月后还有用吗？
- **召回**：混合检索——embedding 相似度 + 关键词 + category 过滤，再加硬预算：top 5 条、token 上限 500。预算是红线，不是建议。
- **冲突**：新偏好与旧条目 category + 主语相同时，**不覆盖**，追加新版本并把旧条目标记 `superseded_by`，召回只取最新链。

## 踩坑点

- **相似度陷阱**：“我喜欢简洁的回复”和“这段代码可以更简洁”向量距离极近，但一个是偏好一个是临时指令。没做 category 过滤时我踩过，召回了一堆无关记忆。
- **记忆污染**：任务过程细节被当成偏好存进去。判断标准只有一条：跨场景可复用才进长期层。
- **静默记忆**：召回后不告诉用户就直接用了，用户会觉得“你怎么知道？”，信任感崩塌。回复里标一句“根据你之前的偏好…”成本低效果好。
- **偏好过期**：口味会变。`last_used_at` 超过 30 天的条目降权，60 天进 consolidation 队列待清理。

## 可复用建议

1. 记忆读写做成独立 MCP 工具，带 schema 校验，不要让 Agent 直接改存储。
2. 每周跑一次 consolidation 任务：合并重复条目、跑一遍冲突链、清理过期项。用 Agent 自己干这活就行。
3. 冷启动别硬等：前几次对话显式问用户 2-3 个偏好问题，答案直接结构化入库，比静默观察快得多。
4. 给记忆条目留 `source` 字段，显式来源和推断来源分开管理，出问题时好回溯。

## 总结

Agent 记忆系统 = 克制的写入策略 + 结构化存储 + 受预算的召回 + 冲突与过期治理。写的时候多问一句“这值得记吗”，读的时候守住 token 预算，冲突时不覆盖只追加。做到这三点，助手就真的“记得你”，而不是背着一坨聊天记录假装记得。
