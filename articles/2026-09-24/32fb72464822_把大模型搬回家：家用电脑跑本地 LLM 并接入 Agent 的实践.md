## 背景

过去半年，我把大部分 Agent 任务的推理从云 API 迁到了家里一台 32GB 内存 + RTX 4060Ti 16G 的主机上。动机很朴素：自动化脚本一天跑几千次工具调用，API 账单不可控；部分任务涉及本地文件和隐私数据，走云端不踏实。这篇帖子记录从选型到接入 OpenClaw 的完整路径，供有同样需求的人参考。

## 问题

本地部署不是“装个 Ollama 就完事”，真正的问题有三个：

1. **硬件边界**：显存/内存决定能跑什么规模的模型，选错直接 OOM 或慢到没法用；
2. **Agent 可用性**：模型聊天流畅不代表能可靠地做 function calling，这是本地模型最常见的坑；
3. **上下文预算**：系统提示 + MCP 工具 schema 轻松吃掉几千 token，本地运行时默认上下文往往不够。

## 做法

**第一步：盘硬件。** 经验估算：Q4_K_M 量化约每 1B 参数占 0.6GB，即 7B 约 4.5GB、14B 约 9GB、32B 约 20GB，另预留 20%~40% 给 KV cache。纯 CPU 也能跑，优先选激活参数小的 MoE 型号（如 Qwen3-30B-A3B 这类），吞吐远好于同规模稠密模型。

**第二步：选运行时。** Ollama 上手最快，OpenAI 兼容接口开箱即用；llama.cpp（llama-server）控制粒度最细；显存 24G+ 且有并发需求再考虑 vLLM。家用场景我最终用 Ollama，够用省心。

**第三步：选模型。** 我的标准是“工具调用优先于聊天质量”：16G 显存跑 14B 级别的 Q4 量化比较稳；同级别里只选官方声明支持 tools 的型号，别信评论区“感觉能调用”。

**第四步：接入。** 把 OpenClaw 的模型端点指向 `http://localhost:11434/v1`，API key 随便填，模型名对上即可。MCP 工具照常挂载，本地模型与云端模型的接入方式完全一致。

**第五步：用真实任务验收。** 别用“写首诗”测模型。我准备了一组包含 3~5 次工具调用的固定任务（读文件→检索→写入→汇总），跑 20 轮统计成功率和平均耗时，这个数字才是部署质量的真话。

## 踩坑点

- **Ollama 默认上下文很小（2k~4k，看版本）**，Agent 一挂 MCP 工具就静默截断，表现为“忘了系统提示”或乱编参数。务必显式设置 `num_ctx`，并注意上下文越大 KV cache 显存占用越高。
- **量化太狠会坏工具调用**。Q4_K_M 是下限；Q2 档聊天看着正常，function calling 成功率明显下降，且掉得没有规律。
- **别用首 token 延迟做指标**。Agent 循环里吞吐（token/s）才是体感，单次生成 500 token 的任务，20 tok/s 和 60 tok/s 体感差距巨大。
- **采样参数别照抄云端默认值**。部分模型工具调用对 temperature 敏感，在 0.2~0.6 之间实测再定。
- **Embedding 别和主模型混用**。RAG 用独立的小 embedding 模型，CPU 跑即可，主模型专注生成。

## 可复用建议

1. 建一份本地“模型卡”笔记：模型名、量化版本、num_ctx、显存占用、任务成功率。版本一换就更新，避免“上次怎么配的”式考古。
2. 配置即代码：启动脚本、模型参数进 git，重装系统十分钟恢复。
3. 保留云端逃生通道：路由层留一个 fallback，本地任务失败率超标时自动降级，别让自动化流水线陪本地模型殉葬。

## 总结

本地 LLM 的定位不是替代云端，而是承接“高频、低难度、含隐私”的 Agent 任务。一台中端主机跑 14B 级别 Q4 模型，配合 OpenClaw 和 MCP 工具链，完全能覆盖日常自动化的主力负载。核心心法一句话：**按工具调用成功率选模型，按真实任务耗时定配置**。
