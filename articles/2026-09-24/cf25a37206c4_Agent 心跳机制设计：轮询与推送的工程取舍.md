## 背景

长期运行的 Agent 大部分时间是"睡着"的，但定时任务、状态巡检、待办提醒又需要它周期性醒来。OpenClaw 的 heartbeat 就是干这个的：网关按固定间隔唤醒 agent，检查 HEARTBEAT.md 和任务队列，有事干活，没事快速返回。问题在于怎么触发——定时轮询，还是事件推送叫醒？两种方式我都跑过一段时间，记录一下取舍。

## 两种方式的天然矛盾

**轮询**：agent 每隔 N 分钟醒来查一次。简单、可靠、对网络环境零要求——设备休眠、断网恢复后下一轮自然接上；代价是空闲时也在烧 token，事件响应延迟最长等于一个周期。

**推送**：事件发生时由 webhook / 消息总线唤醒 agent，响应及时、空闲零成本。但前提是链路常通：需要可达入口、维持长连接，而且推送丢了没人知道——你以为任务会触发，消息其实死在了半路。

核心矛盾一句话：轮询用确定性换成本和延迟，推送用及时性换链路复杂度和可靠性风险。

## 做法：轮询兜底，推送提速

1. **固定轮询作底线**：默认 30 分钟一次 heartbeat，读任务队列和 HEARTBEAT.md。这是可靠性地板，其他层挂了它还在。
2. **自适应间隔**：连续空转就把间隔拉长（30min → 2h），有新任务入队立刻恢复短间隔，夜间时段降频。
3. **推送只给紧急事件**：告警、用户消息这类延迟敏感的走 webhook 唤醒，唤醒后第一件事是写幂等标记，避免和下轮轮询重复执行。
4. **统一任务状态源**：两种触发最终都收敛到同一个队列，执行前原子地改状态位，谁抢到谁干。
5. **心跳可观测**：每次记录触发源、耗时、token 消耗、是否空转，这是后面调间隔的唯一依据。

## 踩坑点

- **空转烧钱**：早期固定 10 分钟一跳，空闲时也走一遍完整上下文，月度 token 直接翻倍。教训：给"无事发生"设计最短路径，空转心跳用最小提示词、短上下文。
- **重复执行**：推送刚做完，下轮轮询又捞到同一条，消息发了两遍。解法朴素：执行前原子改状态位，宁可漏一次靠下轮补，不要重复。
- **推送链路静默死亡**：路由器重启后 webhook 入口失效，推送全丢，而 agent 看起来一切正常。这就是轮询不能删的原因——它同时是死链探测器，超过两个周期没心跳日志就报警。
- **推送风暴**：一次批量告警触发十几个并发 run，直接打到模型 API 限流。推送入口先进队列，由单例 worker 串行消费。
- **长任务堵心跳**：某次心跳里跑了个 20 分钟的任务，期间推送全在排队。长任务异步化，心跳只负责发现和派发。

## 可复用建议

- 默认轮询起步，推送只留给真正秒级敏感的事件，多数场景轮询就够了。
- 空转路径的 token 成本应该压到个位数级别。
- 幂等是两种触发共存的前提：任务 ID + 状态位 + 原子写入。
- 把心跳日志当 SLA 看：触发源、间隔、空转率、成本，四个指标齐了再谈调优。

## 总结

轮询 vs 推送不是二选一：轮询是可靠性地板，推送是延迟优化，heartbeat 的本质是 agent 的调度时钟加死链探测器。先用便宜的心跳保证系统活着，再用推送缩短关键路径的响应时间——顺序反了，你会先为一堆打不通的 webhook 付学费。
