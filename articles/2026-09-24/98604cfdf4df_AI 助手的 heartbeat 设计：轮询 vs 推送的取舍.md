### 背景

OpenClaw 的 agent 是常驻进程，但"常驻"不等于"时刻在思考"。要让 agent 主动做事——巡检、日报、盯任务——得先回答一个老问题：**它怎么知道自己该醒了？**

主流就两条路：轮询（heartbeat 定时唤醒）和推送（事件驱动触发）。OpenClaw 默认走前者：每隔 N 分钟唤醒 agent，读取 HEARTBEAT.md 里的检查清单，有事处理，没事返回 `HEARTBEAT_OK` 静默。这个设计朴素，但用深了会撞上不少取舍。

### 问题

轮询的三个代价：

1. **空转成本**：大部分唤醒其实无事可做，但每次唤醒都是真实的 LLM 调用，token 和延迟都在烧。
2. **响应延迟**：事件落在两次心跳之间，最坏要等一整个周期。30 分钟的心跳，在用户眼里就是"反应慢半拍"。
3. **噪音风险**：如果 agent 醒了总想说点什么，心跳就变成定时骚扰。

推送的代价同样存在：事件源本身要建设（webhook、监听、cron 接入）；事件丢了没人知道；突发流量会把 agent 打爆。

### 做法：轮询兜底 + 推送驱动

我目前的方案是混合式，分四步：

**第一步，拆任务来源。** 把需求列成两栏：周期性的（每日摘要、定时巡检、清理）和事件性的（收到新消息、仓库有新 PR、监控告警）。前者留给 heartbeat，后者走推送。

**第二步，把 heartbeat 调成"看门狗"。** 间隔放大到 30–60 分钟；HEARTBEAT.md 只写最关键的检查项，并明确硬约束：无事必须返回 `HEARTBEAT_OK`、不发消息。心跳的价值从"干活"降级为"兜底"——即使推送链路全挂，任务最迟一个周期内还会被扫到。

**第三步，事件侧做即时唤醒。** 外部系统通过 webhook 或脚本触发：调用 agent 的触发入口、落一个事件文件、或直接投递到消息通道，agent 收到即处理，不等心跳。

**第四步，幂等与状态。** 推送会重复、会乱序。我用本地 sqlite 记每个事件的 key 和处理时间，agent 处理前先查重，同 key 直接跳过。

### 踩坑点

- **心跳间隔拍脑袋定 5 分钟**：一天光空转就几百次调用，某天集中跑任务直接触发限流。后来改用"控制清单长度"而不是"压频率"来降成本。
- **静默约定没写成硬规则**：agent 每次醒来都汇报一句"一切正常"，第二天我就把它关了。静默必须是约束，不是建议。
- **只做推送不做轮询**：某天 webhook 服务重启漏了 3 小时事件，没有补偿机制，任务无声丢失。教训：推送再可靠，也要留一条轮询底线。
- **事件风暴**：一次批量操作触发几十条 webhook，排队堆积。简单解法是在事件侧合并去重，同源事件在 60 秒窗口内只投递一次。

### 可复用建议

- 判断标准一句话：**"每次醒来都检查同一件事"用轮询，"发生了才需要做"用推送。**
- 关键任务永远双通道：推送保证快，轮询保证不丢。
- 心跳成本 ≈ 唤醒频率 × 每次上下文大小，调这两个旋钮都比"换模型"便宜。
- 每类事件都要定义 key 和去重窗口，这是推送方案能长期跑的前提。

### 总结

轮询和推送不是二选一。heartbeat 的正确姿势是低频兜底的看门狗，而不是主力执行通道；实时性交给事件推送，可靠性交给状态记录与去重。先用最小的心跳跑起来，让真实负载告诉你哪边该加码——比一开始就搭复杂事件系统划算得多。
