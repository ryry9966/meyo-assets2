## 背景

Agent 跑过一段时间，大都会遇到同一个需求：助手不能只在被喊的时候干活，得有"自己醒来"的能力。OpenClaw 里的典型做法是 heartbeat——按固定间隔唤醒一次 agent，检查 HEARTBEAT.md 里的任务清单，有活就干，没活就继续睡。另一条路是推送：外部事件（webhook、channel 消息、MCP 工具回调）直接触发 agent。

两条路都能跑通，但选错场景会付出真实代价：要么延迟高、token 烧得快，要么事件丢了没人知道。这篇聊一下取舍依据。

## 问题：两种机制各自的失效模式

轮询的本质是"我猜可能有事，所以定期看一眼"，失效模式很直观：

- 间隔短 → 大量空转唤醒，每次都是一次完整 LLM 调用，成本和时间配额在陪跑
- 间隔长 → 感知延迟不可接受，用户问"那个任务好了吗"，助手还不知道任务开始了

推送的本质是"有事你会被通知"，失效模式更隐蔽：

- 事件源不可靠：webhook 超时、网络抖动，丢一次就永远丢了
- 重复投递：同一条事件触发两次 agent，产生重复副作用
- 时机冲突：推送到达时 agent 正在处理别的会话，事件要么排队要么被吞

单独依赖任何一种都会踩坑。

## 做法：分层判断 + 混合兜底

我在几个插件里收敛出三步：

**1. 先问事件源的能力。** 外部系统有可靠回调能力（GitHub webhook、监控告警回调），推送做主通道；数据源是"哑"的（网页、IMAP 邮箱、没有 webhook 的内部 API），只能轮询。

**2. 把 heartbeat 从"唤醒 agent"降级为"廉价预检"。** 到点后不要直接跑完整推理，先做零成本检查：读状态文件 diff、比对上次快照、看队列是否非空。没变化就直接结束，不消耗 LLM 调用；有变化才真正唤醒。这一步能压掉 90% 以上的空转成本。

**3. 推送做幂等，heartbeat 做对账。** 每条推送事件带 idempotency key，agent 侧去重；同时保留一个较慢的兜底轮询（15–30 分钟一次），专门修复推送丢失造成的状态漂移。推送负责快，轮询负责准。

## 踩坑点

- **间隔拍脑袋定**。早期我设过 2 分钟，一天几千次空转唤醒。后来按任务实际时效倒推：日级任务 30 分钟起步，要求分钟级的任务说明本该用推送。
- **推送 payload 直接塞上下文**。一次 webhook 把整个变更集推进来，上下文瞬间爆掉。改法是推送只带事件引用（ID + 类型），细节由 agent 用 MCP 工具按需拉取。
- **没有 jitter**。多个插件都配了整点轮询，同一秒并发唤醒触发限流。给每个 heartbeat 加随机偏移。
- **幂等只做了一半**。去重表放内存里，agent 重启后清零，重放旧事件又触发一遍。去重状态必须落盘并带过期时间。

## 可复用建议

- 决策看三个量：可接受的感知延迟、事件源是否有回调能力、单位时间 token 预算。前两个定架构，第三个定参数。
- HEARTBEAT.md（或任意等价状态文件）是最好的廉价信号载体：diff 一个文件比调一次 LLM 便宜几个数量级。
- "推送为主 + 慢轮询对账"是大多数自动化场景的稳态，不是二选一。
- 静默时段值得做：夜里没人看，heartbeat 拉长或直接跳过。

## 总结

heartbeat 设计没有银弹。轮询贵在可控、稳在兜底；推送快在即时、险在丢失。工程上的答案通常是混合：用最便宜的信号做预检，用最可靠的事件做触发，再留一条慢速轮询做一致性修复。先想清楚失效模式再选机制，参数永远可以后调。
