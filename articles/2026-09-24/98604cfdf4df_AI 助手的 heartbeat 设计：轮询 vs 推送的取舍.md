## 背景

让 Agent 主动干活——定时提醒、盯群消息、检查 CI、汇总日报——前提是它能"被唤醒"。唤醒机制基本就两条路：固定间隔的心跳轮询，和事件源的推送。在 OpenClaw 这种常驻网关 + MCP 工具的架构里，这个选择直接决定了成本、延迟和可靠性，而且很容易在早期做错。

## 问题

- **纯轮询**：绝大多数 tick 无事可做。如果每次 tick 都把上下文塞给模型，token 成本和响应延迟都难看：间隔短就贵，间隔长就不准点。
- **纯推送**：延迟最低，但前提是事件源都支持 webhook，而且你的网关得有可达入口——内网机器、合盖休眠的笔记本都做不到，还要自己处理签名验证、重试和重复投递。
- **混合不当**：推送和轮询同时开，同一事件被处理两次，用户收到重复回复。

## 做法

1. **先给事件源分类**。能可靠 webhook 的（git、CI、日历）走推送；只能拉的（部分 API、RSS、邮件）走心跳。分类决定通道，不要一刀切。
2. **心跳本身不进模型**。tick 只做一次廉价预检：比对本地水位线（上次处理位点）、未完成队列、脏标记，预检命中才构造 prompt 调模型。健康的系统里 90% 以上的 tick 应该在预检层终止。
3. **间隔加抖动 + 自适应**。基础 5–15 分钟，随机 ±20% 避免整点齐发；夜间静默时段拉长，有活跃任务时临时缩短。
4. **幂等与去重**。每个触发（不管来自推送还是心跳）都带事件 ID 和位点，动作执行前先落"已处理"标记；推送通道按 at-least-once 设计。
5. **补偿扫描兜底**。网关重启、机器唤醒、推送通道断开超过 N 个心跳周期时，跑一次 catch-up 扫描。一句话记住分工：**心跳是底座，推送是加速器**。

## 踩坑点

- **预检写进了 prompt**：让模型自己判断"有没有事做"，一个空转 tick 也烧几千 token。预检必须是普通代码，模型只处理确认有活儿的情况。
- **没有 jitter**：多个 Agent 和定时任务整点同时醒，齐刷刷撞上游限流。
- **推送只顾收**：不验签、不去重，上游重试一次就重复发消息、重复执行动作。
- **本地网关休眠**：macOS 合盖后 `setInterval` 不走，醒来一堆"错过的心跳"。要的是 wake 后补偿，不是一屏报错堆栈。
- **心跳静默失败**：异常被吞，表面活着实际死了。暴露 `last_success_at`，配 watchdog 告警。
- **每次心跳重建全量上下文**：把"上次干到哪"持久化成一条简短的 handoff note，比每次全量恢复便宜得多。

## 可复用建议

- 判断标准就两条："源能不能推、你能不能收"，同时成立才用推送，否则老老实实轮询。
- 把模型移出热路径：空转 tick 的成本应该是毫秒级，不是 token 级。
- 一切触发器默认幂等：假设每条推送至少到达一次，心跳可能重复。
- 可观测性前置：interval、last_success、队列深度放进 status 页，排障不用翻日志。

## 总结

轮询和推送不是二选一。工程上更稳的形态是：心跳负责兜底和补偿，推送负责低延迟，中间用预检、幂等和水位线把两者缝起来。先让空转变得便宜，再谈响应速度——顺序反了，成本曲线会先给你上一课。
