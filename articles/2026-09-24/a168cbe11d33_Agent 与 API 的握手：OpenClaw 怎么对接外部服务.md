## 背景

OpenClaw 的 Agent 跑起来之后，社区里被问得最多的不是“模型聪不聪明”，而是“它能不能真的去干活”。干活意味着调外部服务：查工单、发消息、写数据库、触发流水线。模型本身只会输出文本和工具调用，真正完成握手的是贴在 Agent 外面那一层——MCP server、插件或 skill。这层的工程质量，直接决定 Agent 是可靠助手还是定时炸弹。

## 问题

三种常见失败模式：

1. **把 API 文档原文塞进 system prompt，让 Agent 自己看着调。** 结果是参数编造、路径记错、重试语义全靠模型即兴发挥。
2. **一个工具对应一个接口，几十个工具铺开。** Agent 选择困难，调用错误率随工具数量上升。
3. **返回值原样透传。** 上游几 KB 的 JSON 直接灌进上下文，几轮对话后 token 爆掉，模型还被无关字段带偏。

## 做法

我们的经验是分四步：

**1. 先画边界，再写代码。** 列出允许 Agent 执行的动作清单：哪些只读、哪些可写、哪些必须人工确认。写操作默认拒绝。这份清单比任何精心打磨的 prompt 都管用。

**2. 面向意图封装工具，而不是面向接口。** 不要暴露 `PATCH /tickets/:id`，暴露 `update_ticket_status(ticket_id, new_status)`。工具名和参数名用 Agent 能从任务描述里“猜中”的词，描述里写清前置条件和副作用。一类业务通常 10 个以内的工具就够了。

**3. 鉴权收在服务层。** 密钥放环境变量或 OpenClaw 的配置里，Agent 上下文中永远不出现。token 刷新、限流、重试都在工具内部处理——这些细节不该让模型操心，它也操不了。

**4. 裁剪返回值 + 结构化错误。** 只返回决策需要的最小字段集；失败时返回“发生了什么 + 下一步建议”的短文本，而不是原始堆栈。模型对这种错误信息的利用率远高于一坨裸 JSON。

## 踩坑点

- **工具描述含糊。** 只写“获取数据”，Agent 会在该用 A 工具时用 B。描述里写明“何时用 / 何时不用”，比堆 few-shot 例子便宜得多。
- **写操作没有幂等键。** 网络重试导致重复建单，这个坑只有在生产里才踩得到。
- **超时不设上限。** 上游卡住，Agent 要么干等要么反复重试，把整个会话拖死。
- **日志里打完整请求头。** 密钥跟着进了日志系统，脱敏要从第一天做起。
- **在 channel 消息里直接执行写操作、没有二次确认。** 用户一句口误，数据就没了。

## 可复用建议

- 每个外部服务封装成独立的小 MCP server，进程隔离，崩了不连累 Agent 主循环。
- 工具变更当作 API 变更管理：描述改一个词就可能改变 Agent 行为，必须走 review。
- 上线前用一组固定的评测任务做回归：同样的任务集跑一遍，对比工具选择和参数是否漂移。
- 给每个工具调用记结构化日志（工具名、参数摘要、耗时、结果状态），排障时就是命脉。

## 总结

Agent 对接外部服务，本质不是“让模型学会调 API”，而是把鉴权、边界、幂等、可观测性这些传统工程问题重新封装一遍，让模型只做它擅长的事：理解意图、选择工具、组织参数。握手的另一半，始终是人的工程。
