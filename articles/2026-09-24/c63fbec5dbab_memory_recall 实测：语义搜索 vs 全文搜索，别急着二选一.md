## 背景

给 agent 挂上长期记忆之后，真正决定体验的往往是 `memory_recall` 这个工具：每轮对话把"当前要干什么"变成查询，从记忆库里捞相关条目塞回上下文。社区里常见两套实现——基于向量的语义搜索（sqlite-vec / pgvector），和基于关键词的全文搜索（SQLite FTS5 / Meilisearch）。论坛上经常吵哪个更好，我们拿两个月的真实使用日志跑了一轮对比。

## 问题：两种方案各自翻车的场景

- **语义搜索赢的地方**：换说法能命中。用户说"上次那个部署老失败的事"，能召回正文为"CI 部署流水线报错排查"的记忆。
- **语义搜索翻车的地方**：精确标识符。错误码、文件名、版本号、人名，embedding 之后混在一堆普通词里，排名经常不如预期；另外有 embedding 调用成本和延迟。
- **全文搜索赢的地方**：精确词一查就中，快，零模型依赖，且可解释——能说清命中了哪个词。
- **全文搜索翻车的地方**：同义改写、口语化提问、跨语言，基本召回不了。

结论先说：不是二选一，是混合。但混合怎么做才不糊，有讲究。

## 做法：混合召回的落地步骤

以自建的 MCP memory server 为例：

1. **条目结构**：每条记忆带 metadata（时间戳、来源会话、项目标签），正文 200–400 字，一条只写一个事实。
2. **双索引**：FTS5 建关键词索引，sqlite-vec 建向量索引，写路径一次写两份。
3. **召回路径**：同一查询分别查两路，各取 top 10，用 RRF 合并（score = Σ 1/(60 + rank)），再乘时间衰减（半衰期 14 天），取 top 5 进上下文。
4. **评估**：从日志抽 50 条真实"该召回没召回 / 召回错"的 case，算 hit@5。我们自己的数据仅供参考：纯语义 72%，纯全文 61%，RRF 混合 86%。

## 踩坑点

1. **FTS5 默认 unicode61 分词器对中文基本不可用**，整句会被当成一个 token，属于最典型的 silent fail。要么换 trigram，要么外挂中文分词器。
2. **两路分数直接加权求和不行**，量纲不同：语义相似度常年 0.8+，BM25 分数浮动大。用 rank 融合（RRF），不要用分数融合。
3. **时间衰减别漏**。纯语义相似会把三个月前的旧话题顶上来，agent 拿过期信息当现状用，比召回不到更危险。
4. **换 embedding 模型 = 全量重建索引**。metadata 里存模型版本号，方便灰度迁移。
5. **召回不是越多越好**。top 5 以上再往上下文塞，实测任务完成率反而下降，模型还容易串味。

## 可复用建议

- 冷启动先只上 FTS5（配好中文分词），跑两周看日志里"改写型 miss"的占比，超过两成再加向量路。
- 评估集从真实日志里来，不要手造——手造的查询太干净，测不出真实差距。
- RRF + 时间衰减是性价比最高的默认解，先跑通再调权重。
- 给 `memory_recall` 加 debug 开关，返回每条命中的来源路（semantic / fulltext）和分数，排障能省一半时间。

## 总结

语义搜索解决"换了说法还记得"，全文搜索解决"精确的东西一查就中"——长期记忆系统两种需求都会遇到。别在选型上做二选一，先用最便宜的全文搜索跑起来，让真实日志决定要不要加第二路。召回质量的上限不在模型，而在条目切分、metadata 设计和评估集这几个朴素环节。
