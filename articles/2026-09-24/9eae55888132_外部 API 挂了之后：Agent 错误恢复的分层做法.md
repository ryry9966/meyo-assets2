## 背景

Agent 系统的可靠性下限，往往不取决于模型，而取决于它调用的外部 API。LLM provider、搜索、支付、公司内部服务——任何一个都可能超时、限流、返回 5xx。普通服务挂了就是报错，Agent 挂了会“表演”：无限重试、编造数据，或者拿着错误字符串继续往下推理。这篇整理一套在 OpenClaw 插件和 MCP 工具封装里都适用的分层恢复做法。

## 问题：Agent 会放大故障

- **重试循环**：模型看到报错后倾向于“再试一次”，且没有任何退避，几秒内烧掉大量 token。
- **幻觉填充**：工具返回错误信息时，模型有时把它当部分数据处理，输出看似合理实则编造的结果。
- **级联阻塞**：一个死掉的依赖卡住整个计划，后续步骤全部等待。
- **静默降级**：没拿到数据就“凭经验”回答，用户完全不知道数据缺失。

## 做法：五层处理

**1. 先分类，再谈重试。** 429 / 502 / 503 / 超时是可重试的；400 / 401 / 403 / 404 重试一万次也没用，直接失败。429 记得读 `Retry-After` 头。

**2. 退避和熔断放在代码里，不要交给模型。** 工具封装层做有界重试：3 次，1s→2s→4s 加抖动；连续失败 N 次后熔断 60 秒，快速失败。模型永远不应该面对“原始报错 + 自由决定重试”。

**3. 给模型结构化的错误。** 工具返回统一信封：

```json
{"ok": false, "error": "UPSTREAM_TIMEOUT", "retryable": false, "hint": "跳过此步骤，并在总结中说明"}
```

同时在工具 description 里写清失败时的预期行为。模型拿到结构化信息，决策质量明显好于拿到一段堆栈。

**4. 降级要显式。** 三个选项按优先级：缓存的 last-known-good（必须带“数据截至 X 时间”标记）、备用数据源、或者直接问用户。绝对不要让模型默默补全空缺。

**5. 计划层的熔断和预算。** Agent 循环里维护连续失败计数，某工具连续挂掉就从本轮可用工具里摘除并重新规划。同时设全局预算：最大重试次数、最长运行时间、最大 token 消耗，超了就带着已有结果退出。

## 踩坑点

- **重试没做幂等。** POST 下单接口重试导致重复下单。写操作带 idempotency key。
- **超时太长。** 60s 超时 × 3 次重试 = 用户面对 3 分钟无响应。超时要激进，长任务给进度反馈。
- **降级缓存不标新鲜度。** Agent 自信满满地返回三天前的数据，比直接报错更糟。
- **熔断器每个 worker 各一份。** 多实例部署时各自为政，死掉的 API 还是会被打死。尽量共享熔断状态。
- **异常字符串直接进上下文。** 堆栈既浪费 token，又诱导模型误读。

## 可复用建议

- 所有工具过统一的错误信封封装，别每个插件各写一套。
- 每个工具的重试策略放配置里（次数、退避、超时、熔断阈值），不同上游的容忍度差异很大。
- 长流程在关键步骤前做 preflight 健康检查，早失败比晚失败便宜。
- 主动做故障演练：把某个工具指向一个必挂的 endpoint，观察 Agent 是优雅降级还是当场表演——这一步暴露的问题最多。

## 总结

错误恢复不是一个“重试次数”参数，而是一条链：分类 → 代码层有界退避 → 结构化错误交给模型 → 计划层降级与熔断 → 全程可观测。目标不是永不失败，而是失败时可见、便宜、可恢复。如果只做两件事，先做第 2 层和第 3 层，投入产出比最高。
