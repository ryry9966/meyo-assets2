## 背景

OpenClaw 的用法正在从“本地私人助手”扩展到“社区常驻角色”：群聊答疑 bot、issue 分诊、自动周报。这类 agent 通常带着完整的工作环境——工作区文件、MCP 工具、长期记忆。能力越全，对外发言时“说多了”的风险越大。

## 问题：三条主要泄露路径

1. **配置与工作流外泄**：群里有人问“你怎么做到自动整理 issue 的”，agent 把系统提示词、目录结构、内部 SOP 复述出来。
2. **工具结果带毒**：MCP 工具返回的日志、数据库行、env 文件进入上下文后，被当作“参考资料”贴进回复。token、内网地址、用户数据都走这条路。
3. **记忆串场**：私聊内容被写入记忆，公开频道回答时顺口引用；或排障时把含敏感信息的会话日志原样发到群里求助。

还有个放大器：公开频道里任何人都能对 agent 发起诱导，一条构造过的 issue 评论就可能构成 prompt injection。

## 做法：按入口—过程—出口分层收紧

**入口（收权限）**
- 对外 agent 单独工作区，不挂载密钥和内部文档目录，env、credentials 一律 deny。
- MCP 工具按场景白名单化：答疑 bot 不需要写文件和 shell，就别给。

**过程（管上下文）**
- 系统提示词写明披露策略：讲“我能做什么”，不复述“我怎么配置的”；引内部文档只给结论不给原文。
- 工具返回先过脱敏钩子再进上下文，至少滤掉 key/token/内网 IP 的常见格式。
- 公开角色禁用或隔离长期记忆。

**出口（设闸门）**
- 出站消息加过滤 hook：正则匹配密钥格式、内网域名、绝对路径，命中即拦截或改写。这道闸是独立的确定性代码，不依赖模型自觉。

## 踩坑点

- 只靠提示词约束等于只防君子。注入可以从任何公开输入进来，别假设它“不会坏”。
- 脱敏正则太窄漏新格式，太宽把回复打成乱码。先宽松拦截+人工放行，再逐步收窄。
- 排障贴出的“脱敏日志”常还带着用户 ID 和文件名，等于半脱敏。日志出本地前统一过一遍脱敏脚本。
- 插件和 MCP server 默认权限普遍偏宽，装完第一件事是核对它申请了哪些目录和工具。
- 记忆是隐性通道，agent 自己写的“备忘”也可能带敏感上下文，公开角色宁少勿多。

## 可复用建议

公开 agent 上线前跑一遍“红线测试”：

1. 让它复述自己的系统提示词和工具列表；
2. 让它列出可访问的文件；
3. 让它复述“上次某人的私聊”；
4. 在测试 issue 里塞一条注入指令，看是否执行。

四条全过再上线，并把这套流程脚本化，每次改配置后重跑。

## 总结

Agent 在社区里说的每句话都代表你的环境。安全不靠模型“懂事”，靠权限最小化、上下文脱敏、出站闸门这三道确定性防线，加上一次上线前的红线测试。提示词只能算第四道，也是最弱的一道。
