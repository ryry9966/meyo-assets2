## 背景

OpenClaw 的主会话（比如 Telegram/WhatsApp 通道对应的 main session）是长期滚动累积的：用户指令、工具输出、心跳、定时任务全都挤在同一个上下文里。上下文一满就触发裁剪，早期定下的约定和偏好容易被悄悄挤掉，表现为“它怎么忘了我上次说过的规范”。

子 Agent 机制本来就是为了解决这个问题：把重活放进独立 session（独立的 session key、独立上下文）里跑，只把结论带回主会话。但实际用下来，隔离是否生效，很大程度取决于你怎么用它。

## 问题

最容易翻车的三种情况：

1. **任务描述太含糊**。子 Agent 反复跑偏，主 Agent 只好亲自下场，工具输出照样灌进主会话，隔离了个寂寞；
2. **返回值不带预算**。子 Agent 把整个文件或网页内容当“结果”返回，污染只是换了个入口；
3. **工具继承失控**。子 Agent 拿到消息类工具后直接回复用户，主会话完全不知情，出现两个“人格”同时说话。

## 做法

以我日常的批量代码梳理为例，现在的固定流程：

1. **先判断任务量**：预计超过 5–10 次工具调用的（全库检索、多文件重构、长网页抓取），一律 spawn 子 Agent，不在主会话直接干；
2. **任务提示词写死四要素**：目标、输入（精确路径/链接，不传对话历史）、约束（不许发消息、不许改配置文件）、交付格式（“返回 ≤200 字摘要 + 关键文件清单”）；
3. **确认隔离生效**：spawn 后用 `/sessions` 查一下，子 Agent 应该挂在独立 key 上（形如 `subagent:xxx`），它的所有工具输出留在自己的上下文里；
4. **只回流结论**：主会话拿到摘要后再决定是否汇总回复用户，原始输出永远不进 main。

## 踩坑点

- **摘要不设上限等于没隔离**。我吃过亏：子 Agent 返回了两千字的“简要说明”。现在提示词里明确“超 200 字自行压缩为要点”；
- **工具白名单要显式给**。某次子 Agent 自作主张给测试群发了进度汇报，就是继承了默认工具集导致的，之后统一在 spawn 参数里收权；
- **定时任务别挂 main**。曾经每小时一次的日志巡检跑在主会话里，把当天的对话冲得七零八落，改成 isolated session 后才正常；
- **注意读写时序**。子 Agent 改完文件、主会话立刻去读，偶发读到旧状态。现在约定：子 Agent 返回摘要之后再动文件，或摘要里带上变更时间戳。

## 可复用建议

- 把“目标 / 输入 / 约束 / 交付”四段式任务提示词存成模板，spawn 时填空，避免每次临场发挥；
- 摘要预算固定写进提示词，超出让子 Agent 自己压缩，而不是事后让它再总结一遍（多一轮调用、多一份 token）；
- 定期 `/sessions` 清理孤儿 session，子 Agent 上下文同样是真金白银的成本；
- 心跳、cron 这类系统触发任务，一律隔离运行，绝不进 main。

## 总结

会话隔离的本质不是“多开一个 session”，而是**控制信息回流的方向和体积**：脏活在子会话里消化，主会话只进结论。把任务模板化和工具白名单固化下来之后，我这边主会话的上下文存活时间明显变长，裁剪导致的“失忆”问题也基本消失了。如果你也在被主会话膨胀困扰，建议先从“给子 Agent 的返回值设预算”这一条改起，收益最直接。
