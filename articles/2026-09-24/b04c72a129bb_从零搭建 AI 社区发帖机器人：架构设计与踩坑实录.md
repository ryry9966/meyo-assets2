# 背景

社区内容运营里最耗时间的不是写，而是“定期整理并发出”。每周精选、新版本速递、FAQ 汇总，模板固定但来源分散。我们的解法是让一个跑在 OpenClaw 上的 agent 接手“收集—起草—发布”主流程，人只负责终审。

# 问题定义

发帖机器人听起来就是“调一次模型”，实际要先回答四个问题：

1. 素材从哪来，怎么去重；
2. 文风怎么保持稳定，不会越写越油；
3. 定时触发后如何保证不重发、不漏发；
4. 出错了怎么知道、怎么兜底。

# 架构与实现

整体是一条单向流水线，OpenClaw agent 挂载 MCP 工具，关键环节全部落库：

- **采集层**：RSS、仓库 Releases、论坛新帖，统一格式化后写入 SQLite，每条素材以 URL 作为天然主键；
- **粗筛层**：小模型打分过滤，只把过线素材交给主模型，控制成本；
- **起草层**：agent 按插件（skill）里的固定模板加三篇人工挑选的历史好帖 few-shot 起草，链接和数字只允许引用素材库字段；
- **审核层**：草稿进入 `pending` 状态，通过 webhook 推给管理员确认；
- **发布层**：调用论坛 API，成功后写回状态并归档，幂等键 = 期号 + 素材 URL。

调度用系统 cron 触发 OpenClaw 的 heartbeat，agent 拿到任务后按状态机推进：`draft → pending → published / rejected`。

# 踩坑实录

1. **幻觉链接**。第一版让模型“自由整理”，结果编了两个不存在的帖子标题。修复：起草后加校验器，逐条核对 URL 是否存在于素材库，不存在即打回。
2. **重复发帖**。有一次发布成功后进程崩溃，状态没写回，第二天原样又发了一遍。修复：先写 `publishing` 再调 API，发布后写 `published`；启动时扫描卡在中间态的记录做补偿查询。
3. **风格漂移**。跑了两周，标题越来越像营销号。修复：few-shot 样例库锁死，禁止 agent 自行扩样例，每季度人工复检一次。
4. **成本失控**。起初把原始网页全文塞进上下文，一天的 token 够跑一周。修复：先摘要再起草，全文仅在需要补充时按条拉取。
5. **时区**。cron 按 UTC 跑，早八点变成了下午四点。问题低级，但日志里排查了半小时，值得写进文档。

# 可复用建议

- 凡是“模型写、系统发”的场景，把内容当数据看：状态机 + 幂等键是底线；
- 让模型引用数据，而不是回忆数据，引用内容先落库；
- 上线前至少两周保持人工终审，审核通过率稳定后再放开全自动；
- 给机器人配一条私有回执通道，每日成败计数发给你自己，挂了第一时间知道。

# 总结

这套东西真正难的不是 agent 本身，而是周边工程：幂等、补偿、校验、观测。agent 只占两成工作量，其余八成是“笨功夫”。但做完之后，每周稳定省下两三个小时，且从未再漏过一期。如果你也在维护一个内容节奏固定的社区，这条流水线可以直接照搬。
