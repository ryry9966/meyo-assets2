## 背景

我维护一个技术社区，每周需要固定产出 3~5 条内容摘要帖：收集素材、筛选、去重、排版、发布，纯手工做下来每期大概要花两小时。于是我用 OpenClaw 搭了一个发帖机器人。先明确定位：它不是无人值守的自动发帖机，而是「自动化生成 + 人工审核放行」的半自动流水线。这个定位后来被证明是对的。

## 问题

拆开看，真正要解决的是四件事：

1. 素材从哪来，怎么过滤低质量内容；
2. 如何避免重复发帖（标题相似、语义相近都算）；
3. 草稿质量如何稳定，来源链接是否真实；
4. 发布动作如何幂等，崩溃重试不能重复发。

## 架构与步骤

整体分四层：**调度器 + Agent 运行时 + MCP 工具层 + 状态库**。

- **调度器**：cron 每天触发一次，加 ±10 分钟随机抖动，避免请求过于规律；
- **Agent 运行时**：OpenClaw 拉起一次会话，加载系统提示词和工具清单，跑完即退出；
- **MCP 工具层**：五个小工具——`fetch_sources`（抓 RSS/频道）、`similarity_check`（标题哈希 + embedding 余弦相似度）、`draft_post`（生成草稿并携带结构化来源）、`queue_review`（写入审核队列）、`publish`（人审通过后发布）；
- **状态库**：SQLite 存已发内容 hash、来源、时间戳和发布状态。

流程：抓取 → 过滤 → 去重 → 草稿 → 自检（核对链接、字数、是否有夸大表述）→ 审核队列 → 人工放行 → 发布 → 落库。

两个关键设计：Agent 本身不存状态，所有状态在 SQLite；`publish` 用内容 hash 做幂等键，发布前先查库。

## 踩坑点

1. **幻觉链接**：模型早期会「补全」出根本不存在的文章 URL。解法是把链接来源收归工具——草稿只能引用 `fetch_sources` 返回的结构化数据，禁止自由生成 URL。
2. **去重失效**：只靠标题哈希，同一事件换个表述就漏网。补了 embedding 相似度（阈值从 0.85 起调），误杀和漏杀目前仍靠人审兜底。
3. **重复发布**：一次进程崩溃后重试，同一草稿发了两遍，原因是 publish 没做幂等。修复后改为「发布前先写 pending 记录，成功后更新状态，重试先查状态」。
4. **触发风控**：最初每小时跑一次，被社区接口限流。改成每天一次 + 抖动 + 冷却时间后才稳定。
5. **模型版本漂移**：升级模型后文风突然变花哨。现在固定模型版本，留了 10 条历史好帖做回归样例，换版本必跑一遍。

## 可复用建议

- MCP 工具尽量小而幂等，一个工具只做一件事；
- 状态外置，Agent 无状态化，进程崩溃可恢复；
- 一定留 dry-run 模式，我们前两周只产草稿不发布，白捡了一批质量反馈；
- 每次工具调用记录入参、出参、耗时，排障基本全靠这份日志；
- 人审闸门别急着拆，先让机器人用数据证明自己，再逐步放权。

## 总结

这个项目代码量不大，难度全在边界处理：去重、幂等、限流、质量回归。我的核心体会是：Agent 适合做生成与编排，但「发布」这类不可逆动作，永远值得留一道人工闸门。下一步计划把审核队列接入移动端通知，把人审响应时间从小时级压到分钟级。欢迎在评论区交流你们的自动化流水线设计。
