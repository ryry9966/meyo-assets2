## 背景

社区内容运营有个老问题：好素材散落在 RSS、GitHub Release、群聊纪要里，靠人手动搬运发帖，节奏不稳定，还容易漏。我的目标是做一个跑在 OpenClaw 上的发帖机器人：定时抓信源，Agent 生成草稿，审核后自动发布。听起来简单，实际做了两周，踩的坑比预期多，这篇把架构和坑都摊开讲。

## 整体架构

核心思路是把「决策」和「执行」分开，Agent 只负责生成内容，不直接碰发布权限：

1. **调度层**：系统 cron 每 2 小时触发一次 `openclaw run`，传固定任务 ID；
2. **采集层**：自写一个 MCP tool（`fetch_source`），拉 RSS/API，返回前做截断和字段裁剪；
3. **生成层**：Agent 按模板 prompt 产出 Markdown 草稿，附带信源链接与自评置信度；
4. **审核层**：草稿落盘，前 20 篇强制人工 review，通过后标记 approve；
5. **发布层**：独立插件进程读取 approved 队列调用社区 API，带幂等 key；
6. **观测层**：每次 run 追加一行 JSONL 日志，记录耗时、token、结果。

```
sources/    抓取缓存
drafts/     待审草稿
approved/   审核通过
logs/run.jsonl
```

关键原则：Agent 的工具权限最小化。它只有 fetch 和 draft 两个工具，publish 是独立进程，两边通过文件队列解耦。

## 踩坑实录

**坑一：重复发帖。** 第一版把生成和发布放在同一个会话里，重试一次就发两帖。后来把幂等 key 定义为 `hash(信源URL + 日期)`，发布前先查重，才算堵住。

**坑二：MCP 返回撑爆上下文。** RSS 全量带正文，几轮下来 token 飞涨。解决：tool 内部先摘要到 500 字以内，正文只给链接，Agent 需要细节再按需取。

**坑三：cron 假设任务 5 分钟结束。** Agent 偶尔卡在重试里，拖垮整个调度。改成异步 job + 超时熔断，超时放弃本轮并在日志标记，下一轮自然补救。

**坑四：prompt 漂移。** 改了一版模板，输出从 Markdown 混进了 HTML，插件解析直接挂。之后 prompt 入 git，每次改动跑 10 条历史样本做回归。

## 可复用建议

- 先 dry-run 一周：所有「发布」动作先写成文件，人看过再放行；
- 幂等 key 前置到生成层，不要等到发布层才补救；
- 工具返回值永远裁剪，宁可多调一次，别一次灌满上下文；
- 每个环节独立可重放：抓取、草稿、发布各有目录，出问题能定位到具体一环；
- 权限最小化，Agent 永远不该持有删除类接口的凭据。

## 总结

机器人现在每天稳定发 2-3 篇 digest，人工只做审核。最大的收获不是自动化本身，而是学会「把 Agent 当不可靠的初级同事来设计系统」：给它窄权限、给它检查点、给它回滚路径。代码结构很简单，难的是边界设计。欢迎在评论区聊聊你们的审核策略和去重方案。
