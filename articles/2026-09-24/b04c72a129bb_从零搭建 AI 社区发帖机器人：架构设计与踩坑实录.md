## 背景

社区内容运营有个现实问题：好素材散落在 issue 讨论、群聊和成员笔记里，没人有精力定期整理成帖。我们的目标很克制——不是“全自动内容工厂”，而是一个定时把候选素材整理成草稿、经人工确认后发布的机器人。技术栈很朴素：OpenClaw Agent + 自定义 MCP 工具 + SQLite 状态库 + Discourse API。

## 问题

第一版按最直觉的做法跑：cron 定时唤醒 Agent，让模型自由发挥写一篇帖子直接 POST。三天内暴露了所有典型问题：

- 模型会“编造”引用链接，404 率接近三成；
- 连续两天发布主题高度雷同的帖子；
- 一次网络抖动触发重试，同一篇帖子发了三遍；
- Markdown 代码块的缩进被社区渲染器吃掉。

结论：问题不在模型，在架构。发帖机器人本质上是一个带 LLM 节点的状态机，不是一次性 prompt。

## 做法

最终架构分五段，每段独立可测：

1. **素材采集**：自定义 MCP 工具 `fetch_sources`，从 issue 列表、RSS、群聊纪要拉原始素材落库；
2. **草稿生成**：Agent 读取素材 + 版本化管理的 prompt 模板 + 最近 20 篇已发帖标题（防重复），产出结构化草稿；
3. **规则闸门**：不依赖模型的脚本检查——URL 全部 HEAD 验证、与历史帖的相似度阈值、字数下限、代码块语法校验；
4. **人工确认**：草稿进待审队列，推送到私聊通道，回复确认才放行；
5. **发布与记账**：发布适配器带幂等键（内容 hash），成败都写状态表，失败走指数退避。

关键取舍是：生成和发布之间强制隔一层状态。任何环节崩了，重启后从状态表续跑，不会重复发布。

## 踩坑点

- **幻觉链接**：在 prompt 里写“不要编造链接”基本没用。解法是限制模型只能引用 `fetch_sources` 返回的 URL，闸门再补一次 HEAD 校验，双保险。
- **cron 重叠**：Agent 跑得慢时会和下次调度撞车。加文件锁 + 状态机（pending → drafting → reviewing → publishing），非 pending 状态直接跳过本轮。
- **查重交给模型不可靠**：让模型自己判断“是否和之前的帖子重复”，它总觉得自己写的是新的。改用 embedding 余弦相似度做硬阈值。
- **MCP 工具粒度**：最初把“发帖”做成一个大工具，模型频繁传错参数。拆成 `create_draft` / `submit_post` 两个小工具后，参数错误基本消失。
- **密钥管理**：第一版把 API key 写进配置文件提交了仓库。全部改成环境变量并轮换密钥。

## 可复用建议

- 外部副作用一律收敛到 MCP 工具，并强制带幂等键；
- prompt 模板进版本库，改动走 commit，方便回溯质量波动对应哪次修改；
- 先跑一到两周“人工确认”模式，积累坏例后再逐步放开自动化；
- 每次工具调用记结构化日志，出问题时能定位到素材、生成、发布哪个环节。

## 总结

这个项目最大的收获不是“用 Agent 发帖”，而是验证了一个模式：把 LLM 当作流水线中可测试的一个节点，配上确定性的闸门和状态管理，自动化才敢上生产。目前机器人每天稳定产出 1–2 篇经确认的技术帖，坏例率从最初的 30% 降到 5% 以下。整体代码量不大，复刻成本低，建议从素材采集这一个 MCP 工具写起，跑通一段再加下一段。
