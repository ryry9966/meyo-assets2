## 背景

OpenClaw 的自动化场景（定时任务、MCP 工具链、常驻 Agent）天然适合本地模型：不联网、不按 token 计费、数据不出门。我的动机很朴素——有一批涉及个人笔记和本地文件的操作，交给云端 API 不放心，而任务本身不复杂，7B~32B 级别的模型足够应付。

## 问题

真正上手后发现，"能跑起来"和"能干 Agent 的活"是两回事：

1. **显存账算不准**：模型权重只是一部分，长上下文的 KV cache 同样吃显存；
2. **工具调用不稳**：聊天评测不错的模型，跑 function calling 循环时经常输出残缺 JSON；
3. **吞吐跟不上节奏**：一次自动化任务动辄十几轮工具调用，token 生成速度直接决定任务能否在可接受时间内完成。

## 做法与步骤

**第一步：算显存账。** 粗略经验：Q4 量化下每 1B 参数约 0.6GB，再留 20%~40% 给 KV cache 和运行时开销。8GB 显存跑 7B/8B 很从容，14B 勉强；24GB（3090/4090）可以碰 32B 的 Q4，但要压上下文。

**第二步：选运行时。** Ollama 起步最快，OpenAI 兼容接口开箱即用；llama.cpp / LM Studio 适合精细调参；需要并发（主 Agent 调子 Agent）时上 vLLM。三者都暴露 `localhost:port/v1` 风格的接口。

**第三步：选模型。** Agent 场景优先看工具调用质量，不是榜单分数。Qwen 系列的 7B/14B/32B instruct 版本在工具调用上表现稳定，选明确支持 function calling 的版本。

**第四步：接 OpenClaw。** 模型 provider 指向本地 endpoint（如 `http://127.0.0.1:11434/v1`），API key 填任意非空值；上下文长度显式指定（本地默认值经常偏小），超时放宽到 120 秒以上。

**第五步：用真实负载压测。** 拿一段自己实际的 Agent 任务轨迹回放，记录每轮延迟和工具调用成功率——这比任何 benchmark 都有说服力。

## 踩坑点

- **上下文长度是显存刺客**：32B 模型从 8k 开到 32k 上下文，多吃好几个 GB，直接 OOM。自动化场景主动压上下文，用摘要代替全量历史。
- **工具调用格式**：部分模型在 Ollama 里需要确认带 tools 支持标签，否则 function calling 静默失效，表现为模型用自然语言"描述"想调的工具而不是发起调用。
- **并发瓶颈**：Ollama 默认串行排队，主 Agent 调子 Agent 时会互相等。vLLM，或调大 `OLLAMA_NUM_PARALLEL`，能明显缓解。
- **别迷信参数量**：14B 工具调优模型在 Agent 任务里经常打赢 70B 通用模型，还快 4~5 倍。
- **长任务漂移**：本地小模型跑长流程容易重复或跑偏，temperature 建议 0~0.3，并在关键步骤加程序化校验。

## 可复用建议

1. **分层路由**：常规任务走本地，复杂推理留给云端模型，OpenClaw 的模型路由配置天然支持这种混搭；
2. **固定一套压测脚本**：三五个典型任务轨迹，每次换模型、改量化都跑一遍，数据说话；
3. **显存监控常开**：`nvidia-smi -l 1` 挂个终端，OOM 前总有权征兆；
4. **KV cache 量化**：显存紧张时开 Q8 KV cache，质量损失很小，能省 30% 左右显存。

## 总结

本地 LLM 的价值不在"替代云端"，而在于把中等复杂度、高频、涉隐私的自动化任务收回来。正确路径是：按显存选模型 → 按 Agent 负载选运行时 → 用真实任务轨迹验收。当你的 Agent 一天要跑几百次工具调用时，本地模型的边际成本趋近于零，这份确定性值得投入一个周末。
