## 背景

Agent 跑久了，memory 目录里会积累几十上百条 markdown 笔记——部署偏好、踩坑记录、项目上下文。`memory_recall` 的职责就是在对话中把这些东西捞回来，捞得准不准，直接决定 agent 是"记得你的习惯"，还是每次都要重问一遍。

社区里常被问到：memory_recall 底下该接语义搜索还是全文搜索？两种方案我们都在自己的实例上跑过一段时间，分享一下实测结论。

## 问题：两边都有明显短板

**全文搜索**（FTS5/BM25）胜在零依赖、精确命中。查 `sqlite-vec`、`502 报错` 这类含专有名词和错误码的查询几乎不漏，但它不理解改写：你记的是"偏好简短回复"，三个月后问"我的说话风格要求"，一条都召不回。

**语义搜索**（embedding + 向量库）正好相反，改写、口语化、跨语言的查询都能命中，但遇到精确 token 就拉胯——查函数名或错误码时，一堆"大概相关"的笔记排在前面，真正命中反而沉底，还引入了 embedding 模型依赖和索引重建成本。

先说结论：单选哪个都有翻车场景，我们最终落到混合检索。

## 做法：四步搭一个混合 memory_recall

1. **先建全文基线。** SQLite FTS5 直接对 memory 目录的 markdown 建索引，改动小、结果可解释。
2. **加语义层。** 按 300–500 token 分块，每块带上来源文件和标题作 metadata，embedding 存进 sqlite-vec，不需要单独起向量服务。
3. **两路召回，RRF 融合。** 每路各取 top-8，用 Reciprocal Rank Fusion 合并取 top-5。注意不要把 BM25 分数和余弦相似度直接相加——量纲完全不同，必须按排名融合。
4. **建一个小评测集。** 从自己的对话日志里挑 20–30 条真实问题（一半精确查询、一半改写查询），每次调参后跑一遍看命中率。没有这个集子，调参全靠感觉。

## 踩坑点

- **中文分词是第一个坑。** FTS5 默认 tokenizer 按空格切词，中文会被切成整段，召回率惨不忍睹。要么接 jieba 分词，要么换 trigram tokenizer，二选一。
- **分数不可比，排名才可比。** 我们一开始给两路分数加权，调了两天不如 RRF 一行公式效果好。
- **embedding 模型一换，全部重索引。** 维度一变旧向量全废，选型要谨慎，别频繁追新。
- **记忆量小于一两百条时别上语义。** 全文搜索足够，embedding 只是增加维护面。
- **别丢时间戳。** 记忆有时效性，"上周的部署方式"和"三个月前的"权重应该不同，融合后可以加一个简单的 recency 调整。

## 可复用建议

- 默认从全文搜索起步，够用就别加复杂度；
- 当评测集里改写类查询开始漏召回时，再引入语义层，按 RRF 融合；
- 每次改检索逻辑，先跑评测集再上线；
- metadata 至少保留三样：来源文件、标题、时间戳。

## 总结

这不是"语义 vs 全文"的二选一题，而是"你的 memory 查询长什么样"的问题：精确 token 多，全文为主；改写多，语义补位；拿不准，就混合检索加小评测集，用数据说话。memory_recall 的价值不在检索算法多先进，而在 agent 能不能稳定地想起该想起的事。
