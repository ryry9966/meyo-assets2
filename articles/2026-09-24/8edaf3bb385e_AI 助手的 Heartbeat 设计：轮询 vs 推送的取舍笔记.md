## 背景

OpenClaw 的 agent 默认是被动应答的：有人说话才跑。但一旦把它接到监控告警、日报生成、收件箱巡检这类自动化场景，就绕不开一个问题——agent 什么时候该“自己醒过来”。常见两条路：一是 heartbeat 轮询，让 agent 按固定间隔自检；二是推送，由外部事件（webhook、插件回调）直接触发。两条路我们都踩过，这里把取舍记录一下。

## 问题

轮询的问题不在“能不能跑”，而在成本曲线：不管有没有事，每次心跳都是一次真实的模型调用。间隔设小了，token 消耗和消息噪音都翻倍；设大了，又失去时效性。推送刚好相反：延迟和成本几乎理想，但覆盖率完全依赖上游——事件源不发 webhook、或者网关重启期间丢了事件，agent 就永久失明，而且你很难察觉。

## 我们的分工方式

第一步是给任务分类，看三个维度：

1. 事件源是否原生支持回调（CI 失败、PR 提及、新邮件——支持）；
2. 延迟敏感度（告警类敏感，日报类不敏感）；
3. 状态是否可随时主动查询（这是轮询成立的前提）。

结论落到三类：

- **推送为主**：上游有 webhook、延迟敏感的场景。在插件层加签名校验，收到事件直接触发 agent run。
- **心跳为主**：没有事件 API、但状态可查的场景，比如“检查某个目录或接口有没有变化”。`HEARTBEAT_INTERVAL` 放到 30–60 分钟量级。
- **混合**：推送负责即时处理，心跳降频做对账——每次心跳只对比“上次已知状态 vs 当前状态”，补上推送丢失的窗口。这是实测里最稳的形态。

## 心跳本身的三个工程细节

1. **心跳 prompt 要极简**。idle 时让它回一个固定的短标记并直接丢弃，不要把完整人设和长上下文塞进每次心跳。我们见过心跳 prompt 写了四十行检查清单的配置，一天空转几百次全是白烧的 token。
2. **间隔加抖动**。固定间隔在多 agent 场景下会自然对齐到同一秒（尤其是都从整点启动），集中触发限流。加 ±10%–20% 的随机偏移即可。
3. **心跳用独立会话**。别让心跳往主对话历史里堆记录，否则一周后主会话上下文里全是“无事发生”。独立会话 + 紧凑 prompt，只在有事时把结论转发出来。

## 踩坑点

- **只做推送**：某次网关重启吞掉了两小时的事件，agent 全程无感。之后所有推送链路都强制配一条低频心跳兜底。
- **心跳重叠**：上一轮还没跑完，下一轮又触发，任务互相踩。加个简单的运行锁（文件锁或内存标记）就够用。
- **webhook 裸奔**：推送接口不加鉴权，等于任何人都能唤醒你的 agent 消耗额度。至少做共享密钥校验。

## 可复用建议

- 默认原则：**推送解决时效，心跳兜底可靠性**，两者不是二选一。
- 心跳成本 ≈ 频率 × 单次 prompt 大小，两个都往小压。
- 把每次心跳的决策（idle / 有事 / 出错）落到日志，否则“agent 到底有没有在正常巡检”完全不可观测。
- 间隔宁可先设大，再按日志里的空转占比逐步往下调。

## 总结

Heartbeat 不是免费的自愈能力，它是用 token 换覆盖率；推送是用接入成本换延迟。多数自动化场景的最优解是混合：推送走主路，心跳做低频对账。先把任务按“事件源能力 + 延迟敏感度”分好类，再决定谁当主角，比纠结间隔的具体数字更有价值。
