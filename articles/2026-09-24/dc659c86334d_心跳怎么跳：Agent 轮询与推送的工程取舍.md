## 背景

OpenClaw 这类常驻式 Agent 有个绕不开的问题：它大部分时间应该"睡着"，但又要及时响应外部变化。heartbeat（心跳）就是解决这个矛盾的机制——每隔一段时间把 Agent 唤醒一次，检查有没有该做的事：到期的 cron、未读的收件箱、被修改的文件、需要跟进的对话。

默认实现通常是纯轮询：固定间隔（比如 30 分钟）唤醒一次，把上下文塞给模型，问一句"有什么要做的吗"。

## 问题

跑一段时间就会发现两个矛盾：

1. **成本**：每次心跳都是一次完整的 LLM 调用，哪怕 95% 的心跳结论是"没事"。账单和功耗直接与心跳频率挂钩。
2. **延迟**：事件发生后，最坏要等一整个周期才被处理。调小间隔能降延迟，但成本线性上涨。

推送看起来是正解：事件发生时主动通知 Agent，零空转。但推送通道有自己的问题——webhook 丢失、长连接断开、上游抖动引发事件风暴。推送一旦失败，任务就静默滞留，比慢更糟的是"以为做了"。

## 做法

我们最终采用"预检 + 兜底轮询 + 事件加速"的混合结构：

1. **先量化再优化**。给心跳加日志：触发源、耗时、token 消耗、是否产生实际动作。跑一周，得到"有效动作率"，这是所有后续决策的依据。
2. **心跳前做无 LLM 预检**。写一个便宜的系统级检查：文件 mtime、队列长度、日历最近变更时间。信号全无变化就直接跳过本次唤醒，不进模型。这一步通常能砍掉 70% 以上的无效心跳。
3. **分层心跳**。轻心跳只带最小上下文，让模型判断"是否值得展开"；重心跳每天固定一两次，做全量巡检和清理。
4. **事件走推送，轮询做兜底**。能拿到 webhook 的上游（CI、邮件、Git）接推送通道，事件到达后写入待处理队列，下一次唤醒立即消费；同时保留一个较长的兜底轮询（比如 60 分钟），推送丢了也不会静默失败。
5. **设静默窗口与退避**。夜间只保留兜底轮询；连续空转时按指数退避拉长间隔，有事件时重置。

## 踩坑点

- **心跳 prompt 带全量上下文**：一开始把记忆和会话历史全塞进去，单次心跳成本是正常对话的 3 倍。心跳上下文应该是独立裁剪的精简版。
- **一次唤醒做太多事**：任务堆进心跳批量执行，超时中断后下次心跳重复执行。心跳任务必须幂等、可重入，最好一次只处理一个队列头。
- **推送通道没有回执**：只发不确认，丢了就丢。至少要有"收到即标记 + 兜底轮询清账"的闭环。
- **忘了时区和静默时段**：半夜被心跳唤醒给用户发消息，属于典型的"技术正确、体验灾难"。

## 可复用建议

- 轮询和推送不是二选一：**轮询是正确性兜底，推送是延迟优化**。
- 把心跳当预算管理：设定每日最大唤醒次数，超了就合并任务。
- 所有心跳动作写日志，没有数据就没有优化。
- 评价标准不是"心跳多快"，而是"这次唤醒值不值"。

## 总结

heartbeat 设计的本质不是选轮询还是推送，而是回答"什么信号值得花一次 LLM 调用"。先用便宜的非模型预检过滤噪音，用推送压缩关键事件的延迟，再用低频轮询兜住推送的不可靠——这三层叠起来，成本和实时性才能同时成立。先跑一周日志，再动手改架构，顺序别反。
