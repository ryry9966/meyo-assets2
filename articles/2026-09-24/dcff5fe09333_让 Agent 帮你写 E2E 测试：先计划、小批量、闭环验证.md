## 背景

E2E 测试的处境一直尴尬：价值公认，但写起来枯燥、维护成本高，多数团队只覆盖关键路径就收手。Agent + MCP 工具链成熟后，情况有变化——模型不仅能写测试代码，还能通过浏览器自动化插件实际"操作"被测系统，看得到运行时行为。这改变了 E2E 用例的生成方式，但也带来一类新问题：**AI 生成的用例表面跑得通，实际可能什么都没验证**。

## 问题

常见的失败模式有三种：

1. **只看代码不看运行时**。让模型直接读前端源码写用例，selector 全靠猜，一遇动态 class 就挂。
2. **断言空洞**。只断言 URL 跳转或元素存在，业务逻辑错了一样绿灯。
3. **一次生成几十条**。review 不动，坏用例混进 CI，反而抬高维护成本。

## 做法

我们的流水线分四步，核心是把"探索、规划、生成、验证"拆开，不让 agent 一步到位。

**第一步：给 agent 装"眼睛"。** 在 OpenClaw 工作区接入浏览器自动化类 MCP 工具（如 Playwright MCP），让 agent 在真实跑起来的 dev 环境里走一遍核心流程：登录、下单、提交表单。它顺手就能拿到真实 DOM 结构和稳定 selector，比读源码猜靠谱得多。

**第二步：先出测试计划，再写代码。** 让 agent 输出一份用例清单：用户旅程、每步操作、预期断言、优先级。人先审这份清单——成本最低，也最容易拦住"测了个寂寞"的用例。

**第三步：小批量生成 + 立即执行。** 每次只生成 3~5 条，跑完把失败上下文（截图、trace、错误栈）原样喂回给 agent 修复，循环到通过。不要一次生成 30 条再统一跑，失败了定位不了。

**第四步：PR 门禁。** 每条用例过一遍 checklist：有业务断言、测试数据独立、优先 data-testid、等待方式合理。人工 review 只看这些，不再逐行看代码。

## 踩坑点

- **别让 agent 靠加 timeout 消灭 flaky**。它会用最省事的方式让测试变绿。正确做法是回喂失败上下文，追问根因。
- **测试数据要显式构造**。agent 很爱硬编码 `test_user_1`，换个环境就挂。在任务描述里明确要求走 fixture/seed。
- **警惕过度 mock**。agent 倾向拦截大量网络请求换取稳定，结果把被测逻辑也拦掉了。mock 边界必须由人划定。
- **断言语义必须人审**。agent 能保证"测试能跑"，保证不了"断言测对了东西"。

## 可复用建议

- selector 规范（data-testid 优先）写进项目约定，agent 生成质量立刻提升一档。
- 失败时回喂日志，而不是让它凭记忆重写，收敛速度快很多。
- 测试计划单独成文件进仓库，后续维护时 agent 可对照原计划判断"该修用例还是该修 bug"。

## 总结

Agent 负责 coverage 和样板代码，人负责断言语义和 flaky 策略——这条分工线划清楚，E2E 测试的维护成本才能真正降下来。工具会一直变，但"先计划、小批量、闭环验证"这套流程，今天就可以搬到你的项目里。
