## 背景

我用 OpenClaw 跑了一个多月的常驻 agent，记忆主要来自三处：MEMORY.md 里的长期结论、每日笔记、会话结束时的摘要。`memory_recall` 是 agent 查记忆的入口，检索质量直接决定它"记不记得住事"。

## 问题

最初方案很朴素：把记忆全量塞进 system prompt。记忆涨到几万 token 后，成本上去了，注意力被稀释，agent 反而开始张冠李戴。于是改成按需检索，问题就变成：检索用语义搜索还是全文搜索？

## 做法

**1. 先跑全文基线。** 用 SQLite FTS5（BM25）对记忆条目建索引。实际查询大多是“上次那个报错的修法”“某项目的部署脚本在哪”，关键词重合度高，BM25 直接命中，零成本、可解释、毫秒级返回。

**2. 补语义层。** 把记忆切块（约 300 token，带 50 token 重叠），本地 embedding 模型向量化，用 sqlite-vec 存向量，余弦相似度取 top-k。它解决的是“换个说法就找不到”：问“怎么让它安静点”，也能召回“日志降噪配置”那条。

**3. 混合召回。** 两路各取 top-8，用 RRF（倒数排名融合）合并取前 5，再按时间衰减给近期记忆轻微加分。两路并行执行，总延迟几乎没变。

评测别凭感觉。我攒了 30 条“确实希望它能想起来”的查询当金标集，每次改动跑一遍。结论很明确：纯全文对措辞漂移的查询漏召回严重；纯语义对精确标识符（函数名、错误码、端口号）反而不如 BM25 稳。

## 踩坑点

- **切块尺寸**：超过 800 token，相似度被稀释，top-1 常是一整篇“泛相关”；太小则上下文断裂，召回的单条没法用。
- **embedding 模型的语言匹配**：我一开始用了纯英文优化的模型，中文查询召回明显偏，换多语言模型后才正常。
- **语义结果互相重复**：top-k 看着都像，白烧 token。加了简单去重（相似度 > 0.92 只留一条）。
- **索引不同步**：已删除的结论还在被召回。向量索引的更新必须挂在记忆写入路径上，不能靠事后手动重建。
- **别急着上独立向量库**：几千条记忆的量级，SQLite + sqlite-vec 完全够用，少一份运维负担。

## 可复用建议

1. 先全文、后语义：全文免费且可解释，跑不通的查询类型再让语义补位。
2. 混合 + RRF 是性价比最高的落点，纯语义很少是最终答案。
3. 记召回日志：查询、命中条目、agent 最终是否引用。没有这个，调优全靠玄学。
4. top-k 控制在 3~5，检索是为了省 token，不是为了多塞。
5. 记忆本身要治理：过期结论及时删、重复条目合并。检索器救不了脏数据。

## 总结

语义搜索和全文搜索不是二选一。全文负责确定性命中，语义负责措辞漂移，混合融合加一个轻量评测闭环，比任何单一方案都稳。先建金标集、再动检索，是我这轮最大的收获。
