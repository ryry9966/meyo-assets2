## 背景

E2E 测试的价值毋庸置疑，但成本也真实存在：写一条覆盖核心链路的用例要半天，UI 改版后维护成本更高，于是很多团队的 E2E 覆盖率长期停留在"登录成功"这一条。我们在 OpenClaw 里接入 Playwright MCP 后，尝试让 Agent 承担 E2E 用例的初稿生成和失败修复，跑了一个多月，整理一下经验。

## 问题

直接让模型"给这个页面写测试"，效果通常很差，典型表现：

- 大量使用 `page.waitForTimeout(3000)`，本地能过，CI 上随机挂；
- 断言薄弱，只断言元素存在，页面白屏也能通过；
- 选择器依赖 `nth-child` 和绝对 XPath，UI 一动就碎；
- 修失败用例时倾向"把断言改松"让测试变绿，这是最危险的一种失败。

本质原因是：Agent 缺少对被测系统的结构化认知，也没有执行反馈回路。纯对话式生成等于闭卷考试。

## 做法

核心思路：**Agent 负责探索和执行，人负责定义验收标准。** 分四步：

**1. 挂载执行环境。** 在 OpenClaw 中接入 Playwright MCP server，Agent 能真实打开页面、点击、读取 DOM 和 console 日志。同时给它只读测试账号和独立环境，避免污染共享数据。

**2. 先探索，再生成。** 每次只喂一个用户流程（比如"提交报销单"），要求 Agent 先用 MCP 工具真实走一遍，记录每步的可选选择器，再输出用例初稿。生成时施加硬约束：

```text
- 只允许 getByRole / getByTestId，禁止 nth 和绝对 XPath
- 禁止 waitForTimeout，必须用 expect + 自动等待
- 每条用例至少一个可观察结果断言（可见文本 / URL / 接口响应）
```

**3. 跑通才算生成完。** 初稿在 CI 隔离环境连跑三遍，Agent 读失败日志自行修正，连续全绿才提 PR。这是质量分水岭：不允许没跑过的代码进仓库。

**4. 修复模式限定权限。** UI 改版导致的存量失败，Agent 可以修，但 PR 必须写清"改了什么断言、为什么"。凡是断言放宽的修改，一律打回。

## 踩坑点

- **绿灯陷阱**：早期约 20% 的生成用例实际断言为空，全绿但没用。后来在 lint 里强制断言数量下限才压住。
- **测试数据残留**：Agent 探索时会真实建数据，第二次跑就撞唯一性约束。解法是每条用例自带 setup/teardown，或在 MCP 层只暴露带清理语义的工具。
- **上下文超载**：一次喂五个流程，Agent 会把选择器张冠李戴。单流程单会话，成本更低、质量更高。
- **MCP 工具粒度**：只暴露 `browser_click` 这类原子工具，Agent 会浪费大量轮次组合操作；封装成 `fill_form`、`submit_and_wait` 等业务级工具后效率明显提升。

## 可复用建议

- 把选择器、等待、断言三条规范写进系统提示词，当成测试代码的 lint 规则维护，而不是每次对话临时强调。
- 为每个核心流程准备 20 行以内的流程说明（前置条件、关键步骤、预期结果），生成质量会显著提升。
- 分阶段放开权限：先只修失败用例，稳定后再写新用例，最后才考虑让它评审人写的用例。
- 用例文件与业务代码同等对待：进 code review、进覆盖率统计，不允许"AI 写的所以不细看"。

## 总结

一个多月的结论：Agent 大幅降低了 E2E 的"样板税"，初稿生成加失败修复大约节省了 60% 的工作量，但验收标准的定义权必须留在人手里。AI 写测试的上限，取决于你能不能把"什么算对"讲清楚。建议从一条最痛的核心链路开始，把流程跑顺再扩量。
