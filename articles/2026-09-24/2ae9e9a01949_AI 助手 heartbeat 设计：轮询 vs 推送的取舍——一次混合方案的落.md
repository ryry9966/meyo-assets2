## 背景

OpenClaw 的 agent 默认是被动的：你不发消息，它不跑。要让助手"主动做事"，目前有两条路：

- **heartbeat（轮询）**：gateway 定时器周期性向主 session 注入一条心跳提示，agent 读取 `HEARTBEAT.md` 里的任务清单，没事就回 `HEARTBEAT_OK`；
- **事件推送**：webhook / cron / MCP 工具回调把外部事件直接注入 session。

我的场景是家用小主机上跑 gateway，让助手做三件事：每天早上汇总 GitHub 通知、盯 CI 失败并提醒、定时清理下载目录。

## 问题

两条路的核心取舍其实是"谁付账"：

- 轮询的成本是**确定性**的：interval 越短 token 花得越多，大部分心跳是空转，但延迟上限就是 interval；
- 推送的成本是**事件驱动**的：平时几乎为零、延迟低，但端点暴露、去重、重试、幂等都要自己扛，出问题往往在半夜。

所以问题变成：哪些任务值得为低延迟付基础设施的钱？

## 做法

我最终落地为混合方案：

1. **先全用 heartbeat 验证价值**。interval 30 分钟，`HEARTBEAT.md` 只写三行任务，跑一周看日志：哪些任务真的产生过动作。
2. **分类**。检查型任务（通知汇总、目录清理）留在 heartbeat；触发型任务（CI 失败、告警）改推送。
3. **推送侧加一层极薄的 relay**：几十行的小服务收 webhook，做去重（事件 key + 5 分钟静默窗口），再调用 gateway 接口把消息注入对应 session。
4. **heartbeat 降频到 60 分钟作兜底**，专门兜"推送通道挂了"的情况——CI 状态每 60 分钟对账一次。

## 踩坑点

- **心跳提示每次都进上下文**。interval 15 分钟跑了一天，session 膨胀明显——`HEARTBEAT_OK` 本身也是 token。降频加精简任务清单后恢复。
- **推送没做幂等**。webhook 重试导致同一次 CI 失败发了三条提醒。去重必须在 relay 层做，不能指望 LLM 自己判断"这是不是重复事件"。
- **心跳会静默死亡**。笔记本合盖、网络抖动时 heartbeat 停了且无报错。后来加外部监控：超过两个周期没见到心跳就在别的渠道报警。
- **把重活塞进心跳**。一次全量日志分析直接把当次心跳变成几万 token 的会话。心跳只做"要不要处理"的判断，重活由它触发的独立任务执行。

## 可复用建议

- 选型就三条：时效要求（分钟级 → 推送）、事件粒度（高频低值 → 轮询聚合）、运维预算（不想维护端点 → 轮询）。
- 心跳任务写成幂等可跳过的：每个任务一句话，判断标准明确，能回 `HEARTBEAT_OK` 就回。
- 推送必须过 relay：去重、聚合、限流都在这层做，agent 只应看到"值得处理的事件"。
- 监控心跳本身——它可能是你系统里唯一没有失败报错的组件。

## 总结

heartbeat 便宜可靠，但延迟和成本与频率线性挂钩；推送精确低延迟，但要自己扛可靠性。合理路径是：先用轮询验证每个主动任务是否真有价值，再只对少数高价值事件上推送。对多数个人部署，30–60 分钟的心跳加一两个 webhook relay，就足够了。
