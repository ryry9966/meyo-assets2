## 背景

在 OpenClaw-CN，求助和分享是社区的基本盘：贴一段 config、一张终端截图、一份日志，或者干脆让 Agent 帮忙“写个帖子说明我的工作流”。问题在于，Agent 的工作区什么都看得见——SOUL/AGENTS 指令、memory、工具输出、环境变量、内部文档。它没有“内部/外部”的概念，只有“相关性”。你问它怎么排障，它会把最相关的内容全写出来，包括不该出去的那部分。

## 三条典型泄漏路径

1. **人肉贴日志**。日志和错误堆栈里常带 Authorization 头、内网地址、客户名，人眼扫一遍就发，是最常见的泄漏方式。
2. **让 Agent 代写对外内容**。“帮我整理个帖子发社区”，它会忠实贴出完整插件清单、真实路径、内部流程的时序描述——工具组合本身就是工作流的一部分。
3. **Agent 常驻社区频道**。给社区群挂了个 bot，背后连着全套 MCP 工具。群里有人一句“你们那边是怎么处理的”，它就去内部系统拉数据回帖。

第三条最容易被低估：密钥有特征可以扫，但“什么算内部信息”没有特征，Agent 自己判断不了。

## 做法：四道闸门

1. **分离工作配置与展示配置**。维护一份脱敏的 share snapshot，对外分享只从这份出。写个简单脚本做字段清洗和 diff，别靠手删。
2. **在指令里写死输出红线**。SOUL/AGENTS 中明确：生成任何对外内容时，禁止包含密钥、内网地址、真实路径、客户名；拿不准的字段一律替换为占位符并标注，等人确认。
3. **工具最小化**。常驻公开频道的 Agent 实例只挂只读、白名单工具；内部系统的 MCP 不进这个实例。用两套 workspace 物理分开，配置不共享。
4. **人审兜底**。凡对外发布——尤其是 cron 或 hook 触发的自动发帖——走人工确认队列，不给社区频道账号免审直发权限。

## 踩坑点

- 只删了 apiKey 字段，但 memory 和对话 history 里还留着当时带完整 header 的报错。
- 截图比文本更容易漏：终端滚动缓冲区里的历史命令、浏览器标签页标题。
- 脱敏后的 prompt 仍能反推流程：工具名组合、调用时序就是 SOP 本身，删密钥不等于删工作流。
- 信任惯性最危险：“它很聪明，不会乱说”。生成质量高和边界判断正确是两回事。
- 打包分享 workspace 快照时，memory、skills、.env 一起被带走了。

## 可复用建议

- 建一份 30 秒 pre-share checklist：有无密钥、有无内网/客户信息、有无可反推的流程细节、是否走了脱敏副本。
- 发布前用 gitleaks 之类的扫描器过一遍要贴的文本，成本低、回报高。
- 定期做一次“红队演练”：起一个干净实例，让它尝试总结你的内部信息，检验红线指令是否真的生效。
- 对外/对内实例分开后，把这条写进自己的部署文档，别依赖记忆。

## 总结

Agent 没有“内外之别”，这条边界只能由人来定义、由流程来执行。把脱敏做成脚本和 checklist，而不是每次靠自觉——这是目前唯一能 scale 的做法。在社区里，分享得越多越有价值，前提是每次发出去的，都是你确认过可以公开的那份。
