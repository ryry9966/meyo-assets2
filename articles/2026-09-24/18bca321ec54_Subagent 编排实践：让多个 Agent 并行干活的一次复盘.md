## 背景

用 OpenClaw 做自动化一段时间后，最常见的瓶颈不是模型能力，而是串行执行。主 agent 接到"调研这三个 MCP server 的接入方式、分别给出建议"这类任务时，默认是一个一个做：读一个、总结、再读下一个。半小时过去了，主会话的上下文里塞满了中间产物，真正要输出的报告反而没空间写了。

## 问题

串行的代价主要有三个：

1. **慢**：彼此独立的子任务本可以同时跑，却只能排队。
2. **上下文污染**：子任务的中间过程全部堆在主会话里，注意力被稀释，后面的判断质量下降。
3. **阻塞**：一个长任务卡住，后面所有事都得等。

subagent 的价值就在这里：把独立子任务分出去，各自有独立会话，主 agent 只收结果。

## 做法

以"同时调研三个 MCP server 的接入方案"为例，我的常用流程：

**1. 先判断可并行性。** 只拆"彼此不共享可变状态"的任务。三个库的调研互不依赖，可以拆；"先定方案再写代码"有依赖，不能拆。

**2. 给每个 subagent 明确的产出契约。** 关键不是"你去看看 X"，而是"调研 X 的安装方式和鉴权配置，把结论写入 `notes/x.md`，分三节：安装、配置、风险"。subagent 看不到主会话上下文，提示词必须自包含。

**3. 用文件系统做交接。** 让 subagent 把详细结果写到文件，完成后只 announce 一段简短摘要（结论 + 文件路径）。细节留在文件里，不占主上下文。

**4. 主 agent 汇总。** 三个结果都回来后，我读三份笔记，做交叉对比和最终决策。subagent 负责"收集事实"，主 agent 负责"判断"，职责不混。

**5. 收尾。** 后台任务结束有通知，我会核对摘要是否符合预期，不合格的直接追加指令重跑，不影响其他分支。

## 踩坑点

- **并行写同一目录冲突。** 两个 subagent 同时改一个文件，互相覆盖。需要写文件的任务，用 git worktree 或干脆分目录。
- **产出契约太模糊。** 早期我写过"帮我调研一下"，回来的是一段没法用的泛泛而谈。改成固定模板后质量立刻稳定。
- **并行度开太高。** 一口气开六七个，token 消耗飞快，还容易触发限流。现在控制在 2-4 个。
- **忘了约定交付方式。** subagent 干完了但没 announce 也没写文件，结果等于丢了。现在"交付到哪、以什么格式"是提示词必填项。
- **什么都想并行。** 有依赖关系的任务硬拆，只会多一轮返工。先画依赖，再决定拆不拆。

## 可复用建议

- 把 subagent 当"无状态的外包工"：提示词自包含、产出落文件、摘要回主会话。
- 文件系统就是消息总线，比在对话里传大段内容可靠得多。
- 每个 subagent 的交付物要可验证：文件存在、格式符合模板、必要的测试通过。
- 并行上限宁少勿多，先跑通一条完整链路，再扩大规模。

## 总结

subagent 编排的核心不是"开更多 agent"，而是任务拆解的纪律：独立性判断、产出契约、文件交接、主 agent 只做汇总与判断。把这四件事做扎实，并行带来的提速是实打实的，主会话也干净得多。如果你也在跑长链路的自动化任务，建议从一个"三路并行调研 + 文件汇总"的最小场景开始试。
