## 背景

OpenClaw 的自动化流程里，Agent 对外部依赖的暴露面比传统服务大得多：MCP 工具、第三方搜索、内部数据库、各类 SaaS API。这些依赖的可用性从来不是 100%，而 Agent 和普通客户端的区别在于——它是一个会"理解"错误的决策者。API 报错后，错误信息会进入上下文，模型会基于它继续推理。如果错误没有被良好定义，模型就会自行其是。

## 三种典型的失败表现

1. **重试风暴**：工具返回超时，模型出于"完成任务的执念"反复调用同一接口。见过一次 run 里对同一个挂掉的搜索 API 连调 14 次的案例，token 直接烧穿预算。
2. **幻觉补位**：工具返回空结果或报错，模型不承认失败，编一份数据交差。这比崩溃更糟，因为输出看起来是成功的。
3. **级联阻塞**：一个同步调用卡 30 秒，后续步骤排队超时，整条 workflow 报废。

## 做法：把失败变成被定义过的状态

**第一步：在工具层兜底，不要让模型兜底。** 每个 MCP 工具外面包一层 wrapper：超时 10s，最多重试 2 次，指数退避加抖动（1s → 2s ± 0.5s）。只对幂等操作重试，写操作必须带幂等键。

**第二步：给模型结构化的错误，而不是裸异常。**

```json
{
  "ok": false,
  "error": "UPSTREAM_TIMEOUT",
  "retryable": false,
  "hint": "上游服务暂时不可用，请勿重试，告知用户稍后再试"
}
```

`retryable: false` 是关键——这是你在对模型说"别再试了"。

**第三步：熔断。** wrapper 里统计连续失败次数，超过阈值（比如 5 次）后短路：一段时间内的调用不再发请求，直接返回 `CIRCUIT_OPEN`。给上游留恢复时间，也给自己省 token。

**第四步：降级路径。** 缓存 last-known-good 结果（必须带时间戳），或接备用数据源。都没有，就明确降级：让 Agent 告诉用户"该能力暂时不可用"，而不是硬答。

**第五步：运行预算。** 限制单次 run 的工具调用总数（比如 20 次）和总耗时，超限即终止，输出已有结论。这是防死循环的最后保险丝。

## 踩坑点

- **双重重试**：工具层在重试，模型也在重试，失败被指数放大。解决办法就是上面那个 `retryable` 字段。
- **对非幂等接口重试**：重复下单、重复发消息，都是这么来的。
- **错误信息太"圆滑"**：比如返回 `{"status": "degraded", "data": []}`，模型会理解成部分成功然后开始编。失败就要明说失败。
- **降级数据没标时间**：模型把三天前的缓存当实时数据输出，用户不会知道。
- **熔断太灵敏 + 恢复探测打爆上游**：半开状态的探测请求要限流，一次只放一两个。

## 可复用建议

- 把这套逻辑做成统一的 tool wrapper 或 MCP 中间件，一次实现，所有工具受益，不要每个工具各写一遍。
- 团队内统一错误 schema，字段名和语义保持一致。
- 埋点统计 fallback 命中率、熔断触发次数，这是衡量 Agent 韧性的核心指标。
- 定期演练：把某个依赖临时指向一个恒定返回 503 的端点，验证降级路径真的走得通，而不是只在代码里"看起来能走通"。

## 总结

Agent 的错误恢复，核心不是"更聪明地重试"，而是把失败定义成一种有边界的状态：谁负责重试、重试几次、失败后模型应该说什么、不应该做什么。模型只负责在清晰边界内做决策，韧性是基础设施的事。
