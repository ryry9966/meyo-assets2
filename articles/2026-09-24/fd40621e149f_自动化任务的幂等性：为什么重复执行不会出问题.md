## 背景

自动化系统里，“同一条指令执行了不止一次”不是异常，而是常态。定时任务重叠触发、Agent 判定失败后重试、MCP 工具调用超时后客户端重发、上游 webhook 重新投递——这些场景每天都在发生。一次性脚本跑通就行，但长期运行的自动化链路必须回答一个问题：**这条任务再跑一遍，结果会不会坏掉？**

这就是幂等性：同一操作执行一次和执行 N 次，对外效果相同。

## 问题

不幂等的自动化，故障形态往往很隐蔽：

- 定时任务重复触发，日报在群里发了两遍；
- Agent 重试时把同一批数据插入数据库两次；
- 工具调用超时，实际已成功但客户端以为失败，重试导致文件被追加两次；
- 状态被部分更新，重跑后走进了错误分支。

共同点只有一个：**副作用已经发生，但系统不知道它发生过。**

## 做法

以常见链路（调度器 → Agent → MCP 工具）为例，落地幂等可以分四步：

1. **盘点副作用操作。** 列出所有“会改变外部世界”的动作：写库、发消息、调第三方 API、写文件。只读操作天然幂等，不用管。
2. **给每个任务发幂等键。** 用“任务类型 + 业务对象 + 时间窗口”生成稳定 key，例如 `daily_report:user123:20250106`。key 必须由确定信息派生，不能让模型临时编一个随机串。
3. **执行前先查重。** 用一张去重表（key、状态、时间戳）做前置检查：key 存在且状态为成功则直接跳过。写库类操作优先用 upsert，或靠唯一约束兜底，别依赖“先查后插”。
4. **状态与动作同事务，或可补偿。** 标记“已执行”与实际执行要么在同一事务里，要么设计成失败可重放：成功了但没标记，重跑时先核实副作用是否存在，再补标记。

## 踩坑点

- **幂等键不稳定。** 让 LLM 参与 key 生成，每次措辞不同，等于没有幂等。key 必须来自代码侧的确定性字段。
- **check-then-act 竞态。** 查重和写入之间有时间窗，并发下仍会重复。要么数据库唯一索引硬兜底，要么加锁。
- **重试层层叠加。** 调度层 × Agent 层 × 工具层各重试三次就是九次。明确每层策略，幂等保证只做在最靠近副作用的那一层。
- **时间敏感任务。** “发今天的日报”重复执行时，窗口判断要用业务日期而不是执行时刻，否则跨零点会发两份。

## 可复用建议

- 默认假设任何任务都会被重复触发，把“重跑安全”作为验收标准之一；
- 发送类操作先落“待发送”记录，成功后更新状态，重跑只补发缺的；
- 第三方 API 优先选原生支持 idempotency key 的接口，没有就在自己侧包一层去重；
- 定期做“手动触发两次”的演练，主动验证幂等，比线上出事再补救便宜得多。

## 总结

幂等性不是性能优化，而是自动化系统的地基。它决定的不是“跑得快不快”，而是“敢不敢放手让它自己跑”。给任务一个稳定的幂等键，把去重做在副作用旁边，重试和调度就不再是风险，只是普通的容错手段。对长期运行的 Agent 自动化来说，这是最值得先补的一块短板。
