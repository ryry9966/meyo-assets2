## 背景

写一次性脚本时，我们默认"这段代码只会跑一次"。但在 OpenClaw 这类 agent 环境里，这个假设不成立：工具调用超时后 agent 会重试；插件和系统 crontab 同时部署可能双重触发；用户看任务"卡住了"会手动再点一次；某些框架层甚至可能重放 MCP 调用。**重复执行是常态而不是异常**，幂等性因此成了自动化任务的底线设计。

## 问题

两个真实场景。其一，"每日摘要"插件向群内推送并追加写入汇总文件，网络超时后 agent 自动重试，群里出现两条相同摘要。其二，数据同步任务向 SQLite 插入记录，服务重启后被再次调度，统计口径直接翻倍。

共同点：操作是"追加式"的——每执行一次就多一份副作用，重复即事故。

## 做法

1. **给任务一个稳定键**。ID 不能是运行时随机生成的 UUID，要从业务语义派生：`hash(任务类型 + 数据源 + 时间窗)`。比如摘要任务的 key = `hash("digest" + 当天日期)`，重试和手动重跑天然命中同一个 key。
2. **原子占位，而非先查后做**。用 `INSERT ... ON CONFLICT DO NOTHING`、Redis `SETNX`、`open(O_CREAT|O_EXCL)` 这类原子操作"抢资格"。先查询再执行有竞态：两个 worker 可能同时通过检查。
3. **收敛状态，而非追加动作**。把同步类任务写成 Terraform 的思路：先算"期望状态"与"当前状态"的差集，只执行差异部分。"确保文件内容为 X"天然幂等，"往文件追加一行 X"不是。
4. **记 journal**。关键步骤执行前先落一条 `task_key + step + status`。重试时先查日志：已完成的跳过；对"已提交但结果未知"的状态，凭幂等键去对端查询，而不是盲目重发。
5. **状态文件原子写入**：先写临时文件再 rename，避免进程崩溃留下半份状态。

## 踩坑点

- 拿随机 UUID 当幂等键：每次重试都换新键，等于没设。
- 时间窗跨边界：重试恰好跨天，两个窗口各执行一次。窗口起点要截断到整数周期（如按天对齐）。
- 号称只读、实则有副作用的 MCP 工具：dry-run 参数没实现、列表接口里夹带测试发送。工具描述和实现要一起审。
- 重试整条流水线而不是从日志续跑：浪费执行是小事，重复执行副作用步骤才是大事。

## 可复用建议

- 把每个工具/插件接口按 PUT 设计，而不是 POST：语义是"确保状态达到 X"，不是"执行一次 X"。
- journal 统一放一张 SQLite 表：`task_key, step, status, result_ref, updated_at`，够用很久。
- 幂等性进 CI：同一任务连跑两次，断言第二次为 no-op 或 diff 为空。
- 设计评审只问一句话："这个操作被执行两次会发生什么？"答不上来就别上线。

## 总结

幂等性不是高级优化，而是自动化任务的入场券。有了它，重试才安全、调度才允许重叠、agent 才敢在失败后自行重试。落到工程上就三件事：**稳定的任务键、原子的占位、收敛的状态**。下次写插件时，先回答"执行两次会怎样"，再动手。
