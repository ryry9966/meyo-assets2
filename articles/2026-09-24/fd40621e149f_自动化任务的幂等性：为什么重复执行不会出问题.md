## 背景

自动化跑久了会发现一个事实：任务失败重试、定时器重复触发、Agent 把同一个工具调用发起两次、人工说一句"再跑一遍"——重复执行不是异常，而是常态。调度框架通常只能保证 at-least-once（至少执行一次），没人能承诺"恰好一次"。

OpenClaw 这类常驻 Agent 尤其明显：cron 插件到点触发、消息通道 webhook 重投、LLM 解析失败后工具层自动重试、进程崩溃后 watchdog 拉起重放队列。这些路径叠加起来，同一段逻辑被执行两次的概率远比想象中高。

## 问题

幂等性的定义很朴素：同一操作执行一次和执行 N 次，最终状态一致。而我们写的很多任务天然不满足：

- "发送一条通知"——重试后发两条；
- "INSERT 一条记录"——产生重复数据；
- "把计数 +1"——多加一次；
- "往文件追加一行"——出现重复行。

单看都是小事，叠加成日报双发、告警轰炸、下游统计翻倍后，排障成本会迅速失控。

## 做法

我的习惯是四步，按改造成本从低到高：

1. **先盘点副作用**。把任务分三类：只读、天然幂等（如"确保配置文件包含某行"这类收敛式写入）、非幂等（发送、插入、累加）。前两类基本免费：把"追加/累加"改写成"覆盖/对齐目标状态"，比如用 upsert 代替 insert。

2. **给非幂等任务定一个稳定的幂等键**。关键是"稳定"：不能每次执行随机生成，要从业务身份推导，例如 `task_name + 执行日期 + 目标对象`。日报用"当天日期"，不要用"当前时间戳"——重试时时间戳变了，键就废了。

3. **用原子操作做去重**。一张 SQLite 表加唯一约束就够：

```sql
CREATE TABLE task_runs (
  idem_key TEXT PRIMARY KEY,
  status   TEXT,
  updated_at INTEGER
);
```

执行前先 INSERT（拿唯一约束当锁），成功后置 `status='done'`。INSERT 冲突说明已跑完或正在跑，直接退出。Redis 场景用 SETNX 同理。

4. **能借外部幂等能力就借**。不少工单、支付类 API 支持幂等键（如 `Idempotency-Key` 请求头），把第 2 步生成的键透传过去，重复请求会被服务端合并，比自己造轮子可靠。

## 踩坑点

- **先查后做的竞态**：两个并发实例都查到"不存在"，然后都创建。检查和写入必须原子（唯一约束 / SETNX），不能拆成两步。
- **先做事后记账**：副作用成功了，但记录状态前进程崩了，重试照样重复。应先写入 in_progress 再执行，重启时看到 in_progress 就先核对真实下游状态，再决定是否重做。
- **键里混入执行时信息**：随机 UUID、毫秒时间戳、自增序号，都会让每次重试拿到不同键，去重形同虚设。
- **去重记录过期太早**：TTL 设一小时，结果三小时后人工补跑，重复了。记录至少保留一周。
- **MCP 工具的隐藏副作用**：`get_or_create` 和 `create` 语义完全不同。给 Agent 用的工具，描述里最好注明"可安全重试"或"不可重试"——LLM 发起重试时是不看后果的。

## 可复用建议

- 把幂等包装做成公共插件：`withIdempotency(key, fn)`，所有定时任务默认套上，而不是每个任务手写一遍。
- 任务定义里写清幂等键的构成，人工补跑时复用同一个键。
- 验收标准加一条：连跑三次、中途 kill 一次，最终状态与跑一次完全一致。
- 能用"收敛到期望状态"就不要用"追加动作"，这是成本最低的幂等化。

## 总结

重复执行是自动化的常态而非事故，设计时就该按"至少执行一次"做假设。一句口诀：副作用收敛化，幂等键业务化，去重判断原子化。做到这三点，重试、补跑、双触发都只是普通日志里的一行，而不是凌晨三点的告警。
