## 背景

我们团队每天要在群里发日报，覆盖服务运行状态、异常事件、agent 任务执行情况和代码变更。过去的流程是值班同学手动翻日志、拼数字、写段落。坚持了三个月后发现两个规律：一是格式漂移严重，每个人写出来的日报结构都不一样；二是数字经常抄错，事后对账很痛苦。于是我把这件事做成了流水线，核心原则只有一句：**数字由代码算，叙述由模型写**。

## 问题

最直接的方案是让 LLM 读原始日志写日报，我们试过，不可靠：

- 原始日志量大且格式混杂，远超上下文，token 成本高；
- 模型生成的统计数字时对时错，无法审计；
- 输出格式不稳定，想聚合周报时根本没法解析。

## 做法与步骤

整条流水线分五层，用 cron 定时串联：

1. **采集**：定时拉取各来源数据——服务日志、git 提交记录、告警事件、agent 任务运行记录——统一转成 JSONL 落盘，每行一个事件，带统一时间戳。
2. **归一化**：纯脚本处理，不经过模型。做字段抽取、级别分类（error/warn/info）、按指标聚合：调用量、失败率、P95 耗时、变更条数。产出的结构化摘要控制在几千 token 以内。
3. **生成**：把结构化摘要交给 agent，提示词里明确“只解读给定数字，不允许引入摘要之外的信息”。需要细节时通过 MCP 工具回查原始日志，而不是把全部日志塞进上下文。要求输出固定 schema 的 JSON。
4. **校验**：schema 校验器检查字段完整性；关键统计数字与第 2 层输出逐一比对，不一致就带着错误信息重试，三次后降级为纯模板报告并告警。
5. **投递**：渲染成 Markdown 推到群 webhook，失败重试，同时把 JSON 归档。周报、月报直接从归档数据聚合，不再重新解析日志。

## 踩坑点

- 早期图省事把整段日志直接喂模型，一次跑掉几十万 token，还产出幻觉数字。改成“先聚合再解读”后成本降了一个数量级。
- 模型偶尔改字段名或漏字段，没有 schema 校验时下游直接崩，加了校验加重试才稳定。
- 时区问题踩过一次：统计窗口混用 UTC 和本地时间，日报里“昨天”的边界和实际告警对不上。现在统一按固定时区计算，并在配置里显式声明。
- 流水线失败过一次静默，靠群里没人发日报才发现。补了两条规则：任务失败必告警，连续产出为空也告警。
- 日志里偶有 token、内网地址，投递前加了一层脱敏。

## 可复用建议

- **数字永远由代码计算**，模型只负责把数字组织成人话，这是可靠性的根基。
- 每层独立可测：采集层可重放，归一化层是纯函数，生成层可离线跑样例。
- 固定 schema、校验、重试、降级，四件套缺一不可。
- 报告归档成结构化数据而非纯文本，周报、月报、趋势图都是免费的。
- 从单一来源跑通最小闭环，再逐个接入新数据源，别一上来铺满。

## 总结

流水线上线后，日报格式稳定、数字可审计，值班同学从每天半小时的拼凑工作中解放出来。它没有用到什么复杂技术，关键就一条：把“算数”和“说话”分开，让代码负责事实，让模型负责表达。需要稳定性，就把模型关进 schema 的笼子里。
