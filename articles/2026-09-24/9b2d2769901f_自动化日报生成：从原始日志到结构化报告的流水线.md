## 背景

团队每天要发日报，信息散落在服务日志、Agent 执行记录、Git 提交和工单系统里。之前的做法是值日同学手动翻日志、复制粘贴，再让大模型"润色"一遍。结果是格式不稳定、低频但关键的事件容易漏报、跨天任务算重或算漏。这篇帖子记录我们把这条链路改成自动化流水线的过程，核心思路一句话：**让确定性代码做采集和结构化，让模型只做最后的汇总生成。**

## 问题

把原始日志直接丢给 Agent 总结，实测会遇到三个问题：

1. 日志格式不统一，模型理解成本高，重要但低频的事件容易被忽略；
2. 缺少校验环节，幻觉和遗漏没人兜底；
3. 报告结构每次都变，读的人要反复适应。

根因是没有中间层——采集、结构化、生成三个职责被揉进了一次 LLM 调用里。

## 做法

拆成三段，中间用固定的 JSON schema 作为契约。

**第一段：采集。** 用 OpenClaw 的定时任务在每天固定时间触发：日志按行读取，git 按时间窗口取 log，工单通过 MCP 工具拉取。每条记录转成统一结构：

```json
{
  "entry_id": "唯一键",
  "source": "git | log | ticket",
  "ts": "报告时区的 ISO8601 时间戳",
  "type": "deploy | incident | feature | chore",
  "summary": "一句话描述",
  "status": "done | in_progress | blocked"
}
```

**第二段：校验与归并。** 脚本负责去重（按 entry_id）、按报告日切分、统计空字段比例。空字段率超过阈值就告警中断，宁可不发，不发残缺报告。

**第三段：生成。** 把结构化 JSON 喂给 Agent，prompt 只要求两件事：按固定章节（昨日完成 / 进行中 / 风险）组织语言；对缺失字段显式标注"数据缺失"，禁止补写。输出 Markdown 推送到频道。

## 踩坑点

- **时区**：日志是 UTC，日报按本地时区切日，凌晨前后的任务常被划错天。统一在采集层就把时间戳转换好，不要留给后面。
- **重复执行**：定时任务重跑会插入重复条目。靠 entry_id 幂等写入：同 id 覆盖不追加。
- **格式漂移**：上游日志改了格式，脚本不报错但字段全空。空字段率监控不是可选项，是必须项。
- **模型补写**：早期 prompt 写"整理成报告"，模型会把缺失部分"合理脑补"。改成显式指令"缺失即标注，不得推断"后才稳定。
- **先跑通再扩展**：第一版只接了 git 一个源，稳定两周后才加日志和工单，排障范围小很多。

## 可复用建议

1. 抽取层尽量用确定性手段（正则、jq、API 字段映射），LLM 只出现在最后的汇总层；
2. schema 是三段之间的接口协议，改动要带版本号，方便历史报告回溯；
3. 每天归档原始快照，报告随时可以重新生成；
4. 上线前加 dry-run 模式，人工抽查一周样本再放开自动推送；
5. 每个数据源做成独立插件，新增数据源不改主流程。

## 总结

日报自动化的难点不在"让模型写报告"，而在前面 80% 的采集与结构化。把确定的交给代码，把不确定的交给模型，中间用 schema 和校验兜底——这条流水线搭好之后，基本不会再半夜把你叫起来改 prompt。
