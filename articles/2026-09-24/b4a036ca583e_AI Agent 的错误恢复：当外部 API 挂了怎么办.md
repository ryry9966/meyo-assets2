## 背景

跑过长时间自动化任务的人都会遇到：Agent 前半程一切正常，突然某个 MCP 工具背后的第三方 API 开始 429、502，或者干脆超时。本地脚本挂了可以重启，但 Agent 的麻烦在于——它有状态、有上下文、有半成品输出。错误处理不好，结局往往不是干脆地崩溃，而是"看起来还在跑，实际上已经歪了"。

## 问题：三种典型死法

1. **无限重试**：模型收到报错后自己决定"再试一次"，循环十几次，烧 token 也烧调用配额。
2. **幻觉成功**：API 超时返回空响应，模型把空结果脑补成有效数据继续往下走。
3. **半途烂尾**：前两步写了数据库、发了消息，第三步挂了，没人知道任务停在哪。

## 做法

**1. 把重试从模型手里拿走。** 重试是工程决策，不该由 LLM 的"判断力"承担。在工具封装层（MCP server 或 client wrapper）统一处理：收到 429/5xx/超时 → 指数退避 + 抖动重试，尊重 Retry-After 头，上限 3~5 次并加总时间预算。除 429 外的 4xx 直接判失败，不重试。

**2. 区分幂等与非幂等操作。** 幂等的（查询、PUT）可以放心重试；非幂等的（下单、发通知）重试前必须先查状态，或携带幂等键。这一条是踩坑重灾区。

**3. 熔断与降级。** 连续 N 次失败后短路该工具，冷却期内不再打它；Agent 侧准备好降级路径：备用 provider、缓存结果，或者干脆输出结构化的 blocked 状态，把任务交回编排层或人工，而不是硬编。

**4. 检查点续跑。** 每完成一步持久化状态，恢复时从断点继续，而不是从头执行导致重复副作用。

**5. 喂给模型的错误要"翻译"过。** 别把原始堆栈塞进上下文。封装层把错误归一化成结构化信息：错误类型、是否可重试、已重试几次、建议动作。模型只需要决定"换路走还是上报"，不需要理解 HTTP 细节。

## 踩坑点

- **退避不加抖动**：定时任务里跑着一群 Agent，API 恢复瞬间全体同时重试，雪崩二次触发。务必加随机抖动。
- **200 里藏着错误**：不少老 API 返回 200 + 错误 JSON。封装层必须校验响应 schema，别只看状态码。
- **超时一刀切**：连接超时和读超时要分开；LLM 类接口读超时给长一点（60s 不夸张），普通 REST 给短一点，否则一个慢调用卡死整条流水线。
- **把错误日志喂给模型**：既浪费上下文，又可能泄漏 key、内网地址。日志进日志系统，上下文里只放摘要。
- **部分写入无补偿**：多步操作要有回滚或补偿动作，至少在状态里明确记录"第几步失败、哪些副作用已发生"。

## 可复用建议

- 每个工具声明两个元数据：`retry_policy` 和 `idempotent`，封装层据此自动处理，不依赖每个调用点记得写。
- 全局错误分三类就够：可重试 / 不可重试 / 不确定（超时）。"不确定"按最坏情况对待——先查询核实再重试。
- 每个任务带重试预算和墙钟预算，超了就上报，别硬扛。
- 上线前专门测故障路径：staging 里把依赖 API 停掉，看 Agent 是优雅降级还是原地抽搐。这比测 happy path 有价值得多。

## 总结

API 挂掉不是异常路径，是日常。错误恢复的核心原则就一条：**让代码管恢复，让模型管决策**。分类、退避、降级、检查点，这四件事做扎实，你的 Agent 才配叫"自动化"，而不是"自动化翻车记录仪"。
