## 背景

OpenClaw 的 agent 跑久了，记忆库会积累几百上千条记录：踩过的坑、配置片段、用户的偏好。`memory_recall` 的职责就是在对话中把"相关的那几条"捞回来塞进上下文。捞得准，agent 显得有记性；捞不准，要么答非所问，要么被无关记忆带偏。

我最初的实现很朴素：记忆存 SQLite，用 FTS5 做全文检索。后来看社区不少人在讨论上向量库做语义搜索，索性两条路都跑了一遍，记录下对比结论。

## 问题

两条路线的失效模式完全不同：

- **全文检索**靠关键词命中。用户问"上次部署脚本那个坑"，但记忆里写的是"CI 流水线超时"，一个词都对不上，直接漏召回。
- **语义搜索**靠向量相似度，对改写、同义、跨语言友好，但对错误码、路径、API 名这类高熵字符串几乎无感——`ERR_CONN_RESET` 嵌在一段话里，embedding 之后区分度被稀释，最关键的那条反而挤不进 top-k。

所以问题不是"哪个好"，而是各管一段：全文管精确的东西，语义管模糊的意图。

## 做法

现在的 recall 流程是两路召回加融合：

1. **写入端先做减法**：每条记忆一个原子条目，带时间戳、来源、标签，正文存摘要而非日志原文，长度控制在两三句以内。
2. **全文路**：SQLite FTS5，tokenizer 换成 trigram（中文场景必须换，见下文）。负责精确命中错误码、命令、文件名。
3. **语义路**：本地跑 bge-small-zh 出向量，余弦相似度取 top-k。负责"换了说法也能找到"。
4. **融合**：两路结果用 RRF（倒数排名融合）合并去重，按时间做轻度衰减，最后截断到 token 预算内（我设 800）。

## 踩坑点

- FTS5 默认的 unicode61 tokenizer 对中文基本失效：整句被当成一个 token，搜什么都搜不到。中文必须换 trigram 或外挂分词器，这一步不做，全文检索等于没做。
- 语义路 top-k 给太宽（我一开始给 20），无关记忆灌满上下文，agent 反而被带偏。收窄到 5 条以内效果明显更好。
- 换 embedding 模型必须全量重嵌入，且要把模型版本写进元数据。否则新旧向量混在一个空间里，相似度数值是错的。
- 评估不能靠感觉。我留了 20 条固定的 query → 期望命中记忆做回归集，每次调参跑一遍，避免"这次好像好一点"式的自欺。

## 可复用建议

- 不要一上来就上向量库。先跑纯全文检索一两周，确认存在"改写说法就召回不到"的真实案例，再加语义路。
- 召回质量的上限在写入端。写入时不清洗，召回端怎么调参都救不回来。
- 混合召回 + RRF 是性价比最高的终态：两路各覆盖一类失效，工程量可控，不引入重型依赖。
- token 预算本身也是检索参数：召回条数、截断长度都应该进回归测试。

## 总结

语义搜索和全文搜索不是二选一，而是互补。`memory_recall` 属于每次对话都可能调用的热路径，宁可先简单可靠，再按真实失败案例逐步加复杂度——这也是给所有 agent 记忆类插件的建议。
