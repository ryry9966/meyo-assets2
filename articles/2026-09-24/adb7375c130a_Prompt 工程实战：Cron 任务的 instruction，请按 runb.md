## 背景

OpenClaw 的 cron 能力本质是"无人值守的定时触发"：到点拉起一次会话，把 instruction 交给 agent，跑完即走，不留上下文。很多人顺手把日常聊天的 prompt 抄过来，写成"帮我每天早上整理下群里的讨论"，结果要么 agent 反问没人接，要么每次输出都不一样。

## 问题在哪

和交互式会话相比，cron 少了三样东西：上下文、纠错者、即时反馈。用户不在场，instruction 就是 agent 的全部世界。验收标准因此很明确——把这段文字交给一个不了解背景的执行者，能不能在无人指导的情况下一次做对。

## 写法：按 runbook 的五段结构

1. **触发声明**：开头写明"这是一次定时触发，无用户在线，禁止反问，不要等待确认"。这一句能消掉大部分"卡住等输入"。
2. **目标与数据源**：做什么、从哪取数。工具名写全，"查一下"这种模糊动词不要出现。
3. **时间窗**：相对时间必须锚定，"过去24小时"应写成"以本次运行为基准，取前24小时"，并注明时区。
4. **输出契约**：输出到哪个频道或文件、什么格式、长度上限。给一个固定模板让 agent 填空，稳定性远高于自由发挥。
5. **异常与边界**：数据为空怎么办、工具失败怎么办、允许哪些副作用。宁可发空报告，也不要让 agent 补内容。

## 踩坑点

- **非幂等**：重试或重叠触发导致报告发两遍。让 agent 先检查上次运行标记（文件时间戳、已发送消息 ID）再决定是否执行。
- **一个 cron 塞多个活**：日报、备份、提醒混在一个指令里，输出纠缠、难以排查。一个 cron 只做一件事。
- **指令过长或过短**：背景故事堆太多会稀释注意力，一句话又全靠即兴。实测 300–800 字的结构化指令最稳。
- **时间歧义**："今天""最新"在不同时区、不同触发时刻含义不同，务必显式锚定。
- **静默失败**：工具挂了 agent 自己"想办法"补数据。必须写明失败路径：跳过、记录、通知谁。

## 可复用建议

- 上线前手动触发一次，看完整运行日志，再挂 cron。
- instruction 存文件、进版本库，改动可回溯。
- 每个任务带运行标记，幂等和调试都靠它。
- 定期扫一遍任务日志，输出劣化通常是数据源或指令漂移的信号。

## 总结

Cron instruction 的本质，是给一个没有记忆、没有在线同事的执行者写交接文档：自包含、可判定、幂等，输出路径和失败路径都写死。验收只问一个问题："它会不会自作主张？"答案是不会，这条指令就算合格。
