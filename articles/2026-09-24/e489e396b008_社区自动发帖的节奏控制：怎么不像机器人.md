# 背景

我们在社区里跑着几个自动化角色：每日 issue 摘要、新插件速报、CI 失败通报。早期方案很直接：cron 定时触发 agent，走 MCP 工具直接发帖。功能上没问题，但跑了两周，群里的反馈很一致——“这 bot 一到整点就刷屏，一看就是脚本。”

# 问题

自动发帖的问题往往不在内容，而在节奏：

- 精确整点发布，分秒不差，特征极其明显；
- 事件驱动没有上限，构建连环失败就十连发；
- 模板句式固定，每条开头结尾都一样；
- 只发不回，零交互，像广播不像参与；
- 重试没有幂等，故障恢复后补发积压，重复刷屏。

这些不影响功能，但严重影响观感，最后往往以 bot 被禁言收场。

# 做法

1. **抖动调度**：cron 只定大致窗口，实际发布时间加 0–20 分钟随机偏移，避开整点整分，且每天偏移量不同。
2. **静默时段**：22:00–08:00 不发，事件先进队列，次日早高峰后合并输出；周末整体降频。
3. **聚合优先**：同类事件攒批。单条构建失败不单独发，攒够 3 条或到下一个窗口合成一条摘要。能用日报解决的绝不用单发。
4. **质量门槛**：发帖前跑规则检查——与上一条做相似度去重；没有新增信息就不发。“保持沉默”也是一种合法策略。
5. **幂等与预算**：每条消息带幂等键（业务事件 ID + 日期），重试不重复发布；同时设每日配额，超限直接丢弃最低优先级的消息。
6. **透明标注**：帖子带 [bot] 标记，并在帖内说明如何退订。实践中发现，明确标注自动化之后，社区对节奏瑕疵的容忍度反而更高——大家反感的是伪装成人的刷屏，不是自动化本身。

# 踩坑点

- 抖动的随机数用了固定 seed，一周后被人发现“随机”周期完全一致。种子必须按天更换。
- 最初把聚合逻辑写进 agent prompt，模型偶尔“忘记”合并。后来把节流下沉到 MCP 工具层硬编码，prompt 只负责内容生成，立刻稳定了。
- 幂等键一开始用时间戳，重试时时间戳变了，等于没做。必须用业务事件 ID。
- 配额超限时选了“延后”而非“丢弃”，结果积压在下一个窗口集中爆发，比不节流还难看。
- 静默时段按服务器时区配置，但社区成员分布在多个时区，后来改成按目标频道的主要活跃时区来定。

# 可复用建议

- **节流放代码层，不要放 prompt 层**。确定性规则交给工具层，模型只管内容。
- 给每个自动化建一张极简指标表：发帖数、重复率、被负反馈次数，每周看一眼。
- 新自动化上线前先跑**影子模式**：只记录不发布，人工审一周输出再放开。
- 节奏问题的本质是优先级问题。先想清楚哪些消息值得打扰别人，再谈怎么发。

# 总结

自动发帖“不像机器人”，核心不是伪装成人，而是克制：抖动、聚合、配额、幂等、透明。让每次发布都有信息增量，让频率匹配内容密度，比任何拟人化技巧都有效。社区对一个自动化的接受度，最终取决于它是否尊重大家的注意力。
