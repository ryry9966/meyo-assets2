## 背景

OpenClaw 这类常驻 agent 跑久了，memory 里积累的不只是聊天摘要——还有报错信息、命令行片段、配置路径、项目代号。memory_recall 的职责是在新任务到来时，把这些东西按相关度捞出来塞进上下文。检索方式选什么，直接决定助手"记不记得住事"。

## 问题

常见两种实现：语义搜索（embedding + 向量相似度）和全文搜索（SQLite FTS5 / BM25）。社区经常问"哪个好"，但实际用下来，两者的失败模式几乎不重叠：

- **语义搜索**擅长"换了说法也能找到"：上次记的是"部署脚本超时"，这次问"发布卡住了"，能召回。但对精确 token 很不可靠——错误码 `ECONNRESET`、路径 `/etc/openclaw/`、一个 UUID，在向量空间里和一堆"意思差不多"的内容挤在一起，还容易被相似但错误的条目淹没。
- **全文搜索**精确匹配稳，但同义改写、错别字、中英混写一出现就抓瞎。

## 做法

结论先行：**混合检索，两路都跑，用 RRF（倒数排名融合）合并**。步骤：

1. **存储层**：每条 memory 记录保留原文 + 元数据（时间、来源、标签）。embedding 是派生数据，永远别只存向量丢原文。
2. **全文索引**：SQLite FTS5。中文注意 tokenizer，`unicode61` 会把整句中文当奇异 token 处理，改用 `trigram`，或写入前先 jieba 分词。
3. **向量索引**：切块 200~400 字，本地跑个 bge-small-zh 级别的小模型就够起步，别一上来就调大模型 API。
4. **查询时**：两路各取 top-20，RRF 融合（k=60 起步），叠加时间衰减权重，最终取 top-5 进上下文。
5. **建评测集**：手工写 20~30 条"应该被召回"的查询，每次改参数跑一遍 hit@5，别凭感觉调。

## 踩坑点

- **中文分词是第一大坑**：FTS5 默认配置下症状是"英文能搜到、中文永远空"，先查 tokenizer 再怀疑模型。
- **精确标识符必须走全文**：错误码、文件路径、人名，语义检索会返回"语义相近但不是那条"的结果，而且很难察觉。
- **块切太大**（>800 字）会稀释相似度，切太小丢上下文，300 字加 50 字重叠是稳妥起点。
- **索引不新鲜**：条目被编辑后没重嵌，召回的是旧版本。给记录加版本号，变更即重建。
- **RRF 别混原始分数**：它只吃排名。两路分数分布差异大时，想加权就先各自归一化。

## 可复用建议

- 先用全文搜索跑通，等出现"换个说法就搜不到"的真实案例，再补语义那一路，不要一步到位全向量化。
- 黄金查询集做回归测试，检索质量不可测就等于没有。
- 上下文预算紧张时，优先保全文命中的精确条目，语义结果做补充。
- embedding 调用加缓存，同一查询 10 分钟内直接复用结果，延迟立刻降一档。

## 总结

"语义 vs 全文"是个伪选择题。全文搜索管精确性，语义搜索管泛化性，RRF 把两者拼起来，成本增量只有一次 embedding 调用，可靠性提升立竿见影。先跑评测集，再谈优化——检索这件事，测不了就调不好。
