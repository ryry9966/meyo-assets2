## 背景

OpenClaw 里 agent 的行为主要由几层配置决定：AGENTS.md 管操作规范，TOOLS.md 管工具使用习惯，而 SOUL.md 管的是"这个 agent 是谁"——语气、价值取向、做事风格、不做什么。它会被注入 system prompt，随每次会话生效。

很多团队的精力都在工具链和 skill 上，SOUL.md 要么空着，要么只有一句"你是一个有用的助手"。结果是 agent 在长会话里人格漂移：上午严谨、下午话痨，遇到边界问题全靠模型默认值兜底。

## 问题

我们实际踩到三类典型情况：

1. **风格漂移**：多轮对话后 agent 越来越迎合用户，该质疑的地方也跟着走。
2. **边界缺失**：涉及删除数据、对外发消息、花钱的自动化任务，没有明确的"先确认再执行"规则。一次误触发的排查成本，远高于写几行规则的成本。
3. **职责混淆**：把 cron 该不该跑、MCP 工具的调用偏好这类操作规则写进 SOUL.md，导致改流程时动到人格文件，diff 混乱、回滚困难。

## 做法

我们的 SOUL.md 稳定在四个区块，一页以内：

```markdown
# 身份
一句话说明你是谁、服务于谁、长期角色是什么。

# 风格
默认语气、详略程度、中英文偏好、代码注释习惯。

# 边界
明确不做的事：不替用户执行不可逆操作；涉及删除/支付/对外
发送时，先复述计划等确认；不确定时说不确定，不编造。

# 升级路径
什么情况停下来问人，什么情况可以自主推进。
```

写的时候遵循三条原则：

- **正向表述优先**："回复控制在三段以内"比"不要啰嗦"更容易被稳定执行。
- **边界写具体触发条件**，不写抽象美德。"涉及数据库写操作时，先列出将执行的语句等确认"比"谨慎行事"有用得多。
- **和 AGENTS.md 严格分工**。判断标准：这条规则换一个 agent 还成立吗？成立就放 SOUL.md，不成立放操作文件。

## 踩坑点

- **写太长**。超过一页后，中间条款在长会话里经常被稀释，模型只稳定记住开头和结尾。我们砍到 400 字以内后，执行一致性反而上升。
- **规则互相冲突**。一边要求"简洁"，一边要求"所有操作前复述完整计划"，模型会随机选边。写完自己通读一遍，冲突的合并或删掉。
- **当成法律文书写**。堆满"应当""不得"的长句不如口语化短句——这是给模型看的，不是合规审查。
- **从不迭代**。agent 行为不符预期时，先问：是 SOUL.md 没覆盖，还是规则本身有问题？把真实对话里的 badcase 沉淀回文件，比一次性憋完美版本更现实。

## 可复用建议

- 用 git 管 SOUL.md，与 workspace 配置同仓库，每次行为调整都是一次可回滚的 diff。
- 按用途分模板：个人助理、值班运维 bot、代码评审 bot 的边界区块差异很大，别共用一份。
- 测试方法很朴素：准备 5–10 个真实场景（含一个边界场景），每次改完跑一遍，看语气是否稳定、确认机制是否触发。
- 团队场景让所有使用者都能提 PR，人格定义应该像代码一样有 review。

## 总结

SOUL.md 不是玄学，它就是把团队对 agent 的期望显式化、版本化的一个文件。投入不大，但决定了 agent 是"能跑的工具"还是"可信赖的协作者"。建议每个 OpenClaw 用户至少花半小时写一版：四个区块、一页以内、边界写触发条件，然后用真实对话持续迭代。行为异常时先查它，往往是收益最高的排查起点。
