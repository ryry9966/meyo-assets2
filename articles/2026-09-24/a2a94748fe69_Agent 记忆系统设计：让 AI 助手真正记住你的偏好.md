## 背景

LLM 本身无状态，上下文一关，模型对"你是谁"一无所知。做 OpenClaw 插件和 MCP 工具时最常见的诉求就是：助手能记住我习惯用 pnpm、注释写中文、部署只走 staging。这类偏好记忆不是把聊天记录存下来那么简单，它是一个独立的工程问题。

## 问题：三个容易走偏的方向

1. **全量塞上下文**：历史对话都灌进 prompt，token 成本线性上涨，噪声还会稀释真正重要的偏好。
2. **只存不选**：什么都记，检索时召回一堆无关条目，模型反而被带偏。
3. **黑盒记忆**：用户不知道助手记了什么、也没法改，信任很快崩掉。

核心矛盾是：写太多污染检索，写太少没法个性化，"该记什么"只能靠策略约束。

## 做法：分层记忆 + 生命周期管理

**1. 分层**
- 工作记忆：当前会话上下文，不落盘。
- 偏好库（长期）：一条 = 一个原子事实，如"包管理器：pnpm"。
- 事件记忆（可选）：阶段性结论，如"3 月做过一次 K8s 迁移"。

**2. 结构化存储**
SQLite 起步就够了，字段建议：`id / user_id / content / type / confidence / source / created_at / last_used / hit_count / superseded_by`。向量库不是第一步，等关键词 + 标签检索不够用再加。

**3. 写入要有门槛**
- 会话结束后用便宜模型跑一次抽取，只收显式声明（"以后都用 X"）和高频模式（同一行为出现 ≥3 次）。
- 单次提及不记，或打低 confidence。
- 新旧冲突不做覆盖，而是 supersede：旧条目标记被取代，保留时间线。

**4. 检索与注入**
- 先按标签/关键词精确过滤，语义召回兜底，混合排序。
- 注入预算设硬顶：单次最多 8–10 条，按 confidence × 最近使用排序。
- 同时暴露为 MCP 工具（memory.search / memory.write），让 Agent 自己决定要不要查，比无脑全量注入省得多。

## 踩坑点

- **逐字存对话**：要存结论不存原文，条目原子化，一条不超过一句话。
- **没有遗忘机制**：加 TTL，90 天未命中且低 confidence 的归档淘汰。
- **冲突不处理**：用户从 npm 迁到 pnpm 后旧偏好还在，必须按时间戳取代，不能简单去重。
- **纯向量检索**："不要用递归"这类否定式指令，向量召回经常丢，关键词通道必须保留。
- **记忆不可见**：给用户一个 `/memory` 命令列出全部条目并支持删除。这一条比召回多准都重要。

## 可复用建议

1. 第一版只做：SQLite + 关键词标签 + 8 条注入上限，一天能跑通。
2. 记录 hit_count 和 last_used，两周后回看哪些条目从未被命中，那才是真正的噪声。
3. 评测用回放：拿旧会话构造问题，验证新系统能否召回正确偏好，比拍脑袋调 prompt 靠谱。
4. 抽取 prompt 里明确写"不确定就不输出"，能挡掉大部分幻觉偏好。

## 总结

记忆系统的难点不在存储，而在**选择和生命周期**：记什么、什么时候忘、冲突怎么办。从小结构起步，把记忆做成用户可见可改的东西，再按检索命中数据迭代。先让它可被信任，再谈更聪明。
