## 背景

OpenClaw 的 cron 任务本质是一次无人值守的 agent 会话：到点唤醒、执行 instruction、把结果发出去、结束。它和聊天里"你一句我一句"的交互完全不同——模型醒来时没有任何历史上下文，你写的 instruction 就是它唯一的输入。很多定时任务"偶尔好偶尔坏"，问题往往不在模型，而在 instruction 被当成了聊天消息来写。

## 问题

我踩过几类典型失败：

- 指令里写"按上次的格式整理"，而 cron 会话没有历史记录，模型只能自由发挥，输出每次都不一样；
- 写"汇总今天的动态"，模型对"今天"的理解和你的时区、预期对不上；
- 没写失败分支，数据源挂了之后要么彻底静默（你误以为没数据），要么每次运行报错刷屏；
- 没限定工具边界，agent 在无人监督时调用了带写权限的工具，动了不该动的东西。

## 做法

现在我的 cron instruction 都按固定骨架写，六段：

```text
【任务】每天 08:30 汇总过去 24 小时 xxx 仓库的 issue 动态。
【数据源】只用 GitHub MCP 工具，不要访问其他网站。
【时间】以系统时间为准，时区 Asia/Shanghai；
"过去 24 小时" = now-24h 至 now。
【输出】不超过 10 条，每条含标题、链接、一句话说明；
无更新时只回复"今日无更新"。
【失败】工具调用失败重试 1 次，仍失败则发送
"数据源异常：<原因>"，禁止编造内容。
【边界】本次运行只读，不创建、不修改任何 issue 和配置。
```

几个要点：

1. **自包含**。假装读者刚睡醒且失忆，任务背景、服务对象全部写明。凡是"上次""老样子"这类指代，一律展开成显式规则。
2. **钉死时间与数据源**。时区、时间窗口怎么算写清楚；工具限定到具体的 skill/MCP，不给"自由检索"的空间。
3. **输出给锚点**。条数上限、字段、空结果文案都定死。模型有随机性，跑几十次格式必漂移，模板就是防漂移的锚。
4. **失败行为是第一公民**。失败时说什么、发到哪、重试几次，写进指令，而不是指望运行时救场。
5. **写权限最小化**。无人值守默认只读；确需写操作，列白名单动作。

## 踩坑点

- **指令膨胀**。执行成本 ≈ 指令长度 × 频率。跑两周后回看运行日志，把模型从没用到的话删掉。
- **静默失败最难发现**。宁要一条"数据源异常"，不要一声不吭。
- **高频任务别用重模型**。15 分钟一次的轻量检查，小模型 + 低温度足够，而且更稳定。
- **回复目标要独立**。cron 结果发到专用 channel 或文件，别混进主对话，否则上下文被定时任务污染。

## 可复用建议

- 新任务先手动触发一次（立即执行），确认输出和路由符合预期，再挂调度；
- instruction 放进 git 管理，改动走 commit，出问题能 diff、能回滚；
- 用 review 交接文档的标准审视每条 instruction：一个不了解背景的人，只看这段话能不能把活干完整。

## 总结

写 cron instruction 的心智模型很简单：你不是在聊天，而是在给一位没有记忆、无人监督的值班同事写交接文档。自包含、有边界、有失败预案——守住这三条，定时任务的稳定性会上一个台阶。
