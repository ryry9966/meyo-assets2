## 背景

OpenClaw 初始化工作区时会生成一份 `IDENTITY.md`，官方模板只有几个字段：Name、Creature、Vibe、Emoji、Avatar。多数人的用法是填个名字、配个头像，然后再也不打开它。

跑了一段时间 Agent 之后你会发现，真正的问题不在"它叫什么"，而在行为随时间漂移：今天啰嗦明天简洁，你在聊天里纠正过的偏好，下个会话原样复发。身份如果不沉淀，就只能反复口头教育。

## 问题

没有把身份当作受管理的文件时，常见的三个坑：

- **行为不可复现**：偏好只存在于对话记忆里，会话一清就丢。
- **职责散落**：人设写在 system prompt，语气要求散在工具描述里，改一处漏三处。
- **不可回滚**：prompt 改坏了，没人记得上一版长什么样。

## 做法

我的实践是把 IDENTITY.md 从"名片"升级成"身份 + 行为约束"的单一事实源：

```markdown
# IDENTITY.md

## Name
Ops 助手

## Creature
终端里的运维协作 Agent

## Vibe
直接、克制，先结论后细节

## Emoji
🛠

## 边界（社区扩展段）
- 删除类操作必须先确认
- 查不到的配置值直接说查不到，不猜

## 风格（社区扩展段）
- 报错时先复述错误，再给修复步骤
- 命令一律带行内注释

## 演进记录
- 2025-06-01：新增删除确认规则（起因：一次误删）
```

落地步骤：

1. 填好官方五字段，保证基础人格一致。
2. 追加"边界 / 风格"两段，条目控制在十条以内。
3. 纳入 git：每次改动一条 commit，能回滚、能 review。
4. 聊天里纠正过 Agent 的话，事后写回文件——"纠正即落盘"是整套机制能否转起来的关键。
5. 每两周复盘一次：删掉从未触发的条目，合并重复项。

## 踩坑点

- **和 SOUL.md 抢活**。OpenClaw 的分工大致是：IDENTITY.md 管"你是谁"，SOUL.md 管"你怎么行事"。把价值观、行为准则全塞进 IDENTITY.md，两处规则冲突时行为会摇摆。
- **写太长**。超过一两页注意力就被稀释，核心规则反而失灵。
- **写愿望不写行为**。"保持专业"没有信息量；"报错先复述再给步骤"才可执行、可验收。
- **频繁重写**。身份应该缓慢演化，今天改明天改，说明你在拿它当草稿纸。
- **写敏感信息**。这个文件会被完整注入上下文，密钥和内网地址绝不能出现。
- **多 Agent 共用一份**。职责不同的 Agent 各自维护，共享的只是风格基调。

## 可复用建议

- 把它当代码对待：改动有 commit message，重要变更拉同事 review。
- 文件内部分两层：上面是稳定核心，下面是"实验区"，条目验证有效再上移。
- 官方字段保持极简，扩展段落宁缺毋滥——每一条都应该能回答"它阻止过什么事故"。
- 排查行为异常时，先 diff 这份文件的历史，再怀疑模型或工具。

## 总结

IDENTITY.md 的价值不在于让 Agent"有个性"，而在于把行为从对话里的临时变量，变成版本化、可 review、可回滚的配置。一页短小、诚实、持续维护的身份文件，比一段精心雕琢却从不更新的长 prompt 有用得多。建议每个跑在 OpenClaw 上的 Agent 都从一页开始，让它跟着实际使用慢慢长。
