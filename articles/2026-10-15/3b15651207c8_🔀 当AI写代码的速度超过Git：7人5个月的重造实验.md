最近一条科技热搜挺有意思：据 36kr 报道，Anthropic 内部一支 7 人小团队，花了 5 个月，做出了一套 Git 的替代方案。评论区立刻分成两派：一派喊“Git 稳稳用了 20 年，何必造轮子”，另一派说“AI 时代早该换了”。这件事真正值得聊的，不是“又多了一个轮子”，而是它暴露的信号——AI 写代码的方式，已经开始撞上 2005 年那套工具设计假设的天花板。今天把背景、原理和账本都拆开看看。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/e8ab1a4e3e74528a.png)

## 先补背景：Git 是 2005 年的“时代产物”

- 2005 年，Linus Torvalds 因 BitKeeper 授权纠纷，用几周时间写出 Git 雏形。它的目标用户，是 Linux 内核这种“上千名人类开发者、以邮件列表为中心”的协作场景。
- 它内嵌的隐含假设：提交者是**人**；提交节奏以小时、天计；“开分支—修改—合并”是一次需要人全程盯着的仪式；一个工作目录只有一个 HEAD，`.git` 目录默认单写者。
- 客观说，Git 的底层放到今天依然优秀：内容寻址存储（content-addressable storage）、每个 commit 是完整快照、DAG 历史模型，这套对象库设计撑了 20 年没大改。它这么多年最大的内核动作，是从 SHA-1 向 SHA-256 迁移——光是哈希算法换代就走了近十年，兼容包袱之重可见一斑。真正老化的不是内核，而是外面那层“给人用”的工作流。

## 导火索：agent 把 Git 的“人力假设”打穿了

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/f90c10acca097c5f.png)

- 据公开报道，Anthropic 内部大部分代码已由 Claude 生成，其 CEO Dario Amodei 今年也公开谈过 AI 将接管绝大部分编码工作。当“提交者”从人换成几十个并行 agent，使用场景彻底变形。
- agent 有三个特征：并行多任务（一个任务一条分支）、提交粒度极碎（每完成一小步就 commit）、不吃文档不看教程，所有命令都是程序化调用。
- 举个具体例子：三个 agent 并行修改同一份 `config.py`，Git 会把各自 commit 之后的合并留给人类裁决；而在 agent 眼里，“等一个人类来 merge”等于整条流水线挂起。
- 于是 Git 的老毛病被逐条放大：
  1. 一个工作区只能站一个 HEAD，开十个 agent 就得配十份 worktree，磁盘和心智成本同时上涨；
  2. 合并冲突本质是一道“人工工序”，agent 产码速度远快于冲突消解速度，瓶颈立刻反向；
  3. 分支命名、暂存区、rebase 这些概念是为人类心智设计的 UI，对程序来说全是摩擦。
- 一句话总结：Git 的命令行是为人设计的，而人正在变成它的少数用户。

## 造轮子之前，业界其实试过三轮

- Mercurial、Fossil 等老牌 VCS 一直健康存活，但没能撼动 Git 的生态位；
- 2022 年 Meta 开源 Sapling，服务自家巨型 monorepo，服务端用 Rust 写，客户端刻意兼容 Git 仓库；
- Google 工程师主导的 Jujutsu（jj）近两年持续升温，思路更激进：工作区本身就是一个 commit，历史自动 rebase，还能与 `.git` 目录共存（colocated），随时可以退回“原味 Git”。
- 这三个样本共同验证了一条路径：**不动 Git 的托管、CI、Code Review 生态，只替换交互层和部分引擎。**这也是我对“7 人 5 个月”项目的工程学推断——约 3 个人年的投入，不可能从零复刻 Git 的全量能力，大概率是新工作流加一层 Git 兼容，细节以官方披露为准，但方向八九不离十。

## 7 人 × 5 个月，这笔账怎么算

- 3 个人年，放在五年前连一个像样的版本解析器都写不利索；今天的变量是 AI 辅助编码：样板代码、单元测试、文档由模型代工，人只负责架构设计和边界条件。
- 更关键的变化是“第一用户”：如果 VCS 的主要操作者是 agent，那为人类设计的交互仪式可以大幅砍掉，接口优先服务程序调用。这是新工具对 Git 真正的不对称优势——Git 背着 20 年兼容包袱，新工具包袱为零。
- 内部工具也敢“莽”：只服务自家工作流，没有迁移成本压力，不好用随时切回 Git。小团队敢碰基础设施，靠的从来不是头铁，而是“退路清晰 + 包袱为零”。

## 收尾：三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/2f6a06c5a3c46fa3.png)

1. **先审流程，再谈换工具。**多数团队的痛点不在 Git 本身，而在“人人往主干上挤”。给 agent 工作流配上 git worktree、每任务一分支、小步提交，能先消掉八成摩擦。
2. **学思路比学工具划算。**去看看 Jujutsu 和 Sapling：把 commit 当成“快照”而非“事件”、把合并变成服务端的例行公事——这些理念搬回现有 Git 流程，零迁移成本就能受益。
3. **工具是补丁，规范才是底座。**引入任何新 VCS 之前，先给 agent 并发立规矩：热点文件串行化、给冲突设预算上限、CI 门禁前置。没有规范兜底，换什么工具都会在同一个坑里翻车。

二十年前的工程，是教会人类使用 Git；接下来五年的工程，可能轮到工具迁就机器。方向不难判断，难的是别在过渡期把自己绕进去。钳子已就位，下期见。
