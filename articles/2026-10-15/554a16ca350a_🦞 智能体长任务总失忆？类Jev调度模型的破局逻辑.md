让 Agent 重构一个中型代码库：前 20 分钟思路清晰，40 分钟后开始反复读同一批文件，一小时后最初的需求已经忘了一半——做过长程任务的开发者对这一幕都不陌生。最近“国产开源、类 Jev 调度模型接管 Agent 编排”冲上热搜，核心主张一句话：别再让一个大模型既当思考者又当记账员，把记忆管理和任务调度交给一个专门训练的小模型。这篇文章拆开讲三件事：Agent 为什么失忆、现有方案卡在哪、调度模型到底在调度什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/74015b34aab7ff41.png)

## 一、长任务为什么总“失忆”

1. **上下文窗口是物理上限。** 窗口从 2K 涨到 200K 再到百万级，涨了几百倍，但一次多小时任务里累积的网页抓取、代码读写、工具返回值照样写爆窗口。一旦触发截断，早期约束就永久丢失。
2. **Lost in the Middle。** 斯坦福 2023 年的实验测出，LLM 对上下文开头和结尾的信息召回最好，中段明显拉胯，准确率呈 U 形曲线。窗口越长“雾区”越大，那条关键的业务约束一旦掉进中段，模型就可能视而不见。
3. **Context rot 与成本。** Chroma 团队的测试显示，无关信息堆积会让同一个模型连简单问题都答错；同时每轮重放全部历史，token 费用与首字延迟线性上涨——KV cache 命中率正是 Manus 等产品公开分享的头号优化指标。

一句话总结：失忆不是模型“笨”，而是把工作记忆、长期记忆、任务状态全塞进一个窗口硬扛，架构上就不成立。LLM 的注意力像一块会议室白板——写满了就得擦，擦哪块基本靠运气。

## 二、现有“续命”方案，各管一段

- **压缩摘要（compaction）**：窗口快满时把旧对话压成摘要，Claude Code、Manus 都在用。省 token，但丢什么不可控——摘要里漏掉的那行配置，可能就是后面 debug 两小时的原因。
- **外部记忆（RAG / 向量库）**：历史步骤切块入库、按需检索。存得下，但“何时检索什么”全靠主模型自觉，该查没查是常态。
- **文件系统当记事本**：任务清单、中间产物落盘，要用再读。可靠，但读写时机同样没有统一裁决者。
- **Plan-and-Execute 分层**：规划器拆任务、执行器干活。结构清晰，但计划一旦过时，缺少中立角色触发重规划。

这些方案并不互斥，真正的缺口是：**谁来决定“何时压缩、何时检索、何时落盘、何时重规划”？** 目前大多写死在框架的 if-else 和 prompt 里，改一处崩全身。

## 三、类 Jev 调度模型：把编排变成可训练的技能

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/9805dc98406f67e3.png)

拿操作系统类比最直观：CPU 调度器决定哪个进程上核心、什么时候换页；类 Jev 这类模型决定哪段上下文进窗口、哪个子任务派给谁、何时打 checkpoint。这条思路并不新——2023 年 MemGPT 论文就把操作系统换页思想搬进了 LLM 记忆管理，类 Jev 的关键差异在于：把“何时换页”的决策从固定规则升级为可训练的策略模型。典型工作流四步：

1. **任务编译**：把用户目标拆成带依赖关系的任务图（DAG），每个节点标明输入、产出和预算；
2. **上下文供给**：节点执行前只检索最小必要信息，组装“刚好够用”的上下文，不做全量重放；
3. **状态巡检**：节点完成后核对产出与计划的一致性，发现偏差就触发重规划，不让错误滚雪球；
4. **换页与落盘**：窗口吃紧时决定压缩谁、丢弃谁、归档谁——优先级是训练出来的策略，而非手写规则。

为什么用小模型而不是再堆一个大模型？三个理由：

- **延迟与成本**：调度决策高频发生，7B 级小模型比每步调用旗舰大模型便宜一两个数量级；
- **可专门训练**：用海量长程任务轨迹做 SFT / RL，直接优化“调度正确率”，比靠 prompt 苦口婆心劝大模型“记得整理记忆”靠谱得多；
- **职责分离**：思考归思考、记账归记账，出问题好定位——和微服务拆分是同一套工程哲学。

## 四、开源的意义与现实的坑

- **意义**：可私有化部署（数据不出内网）、可针对自家业务微调调度策略、可与 LangGraph 等主流框架对接，调度逻辑从黑盒 prompt 变成可审计的模型权重。
- **坑也要看清**：调度模型自己也会犯错——该压缩时不压缩、误删关键状态都会发生；长程任务的评测集稀缺，demo 顺滑不等于生产可用；它解决的是编排层，单步推理的上限仍取决于主模型本身。

## 五、冷思考：给开发者的三条建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/69493eefd9515e45.png)

1. **先做上下文工程，再谈调度模型。** 把任务状态结构化：to-do 清单、状态文件、统一的工具返回格式，日志留全。调度模型是放大器，喂给它一团乱的上下文，只会放大得更乱。
2. **长任务先拆 DAG，别指望一个 prompt 撑到底。** 能手动拆清楚的任务先手动拆，调度模型的价值在“拆不清楚时兜底”和“跑起来后自动纠偏”，而不是替代你思考。
3. **自建长程评测集再上线。** 挑 20 个真实的多步任务，记录完成率、token 成本、回滚次数，任何优化前后各跑一遍。没有数字支撑的 agent 优化，本质上都是在给 demo 化妆。

长任务的终点不是更大的窗口，而是更聪明的记账员。窗口还会继续变大，但“注意力是稀缺资源”这件事不会变——把调度从玄学变成工程，Agent 才算真正有了打工的体格。
