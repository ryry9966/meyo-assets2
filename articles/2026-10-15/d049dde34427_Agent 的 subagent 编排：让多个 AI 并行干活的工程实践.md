# 背景

用 OpenClaw 这类 agent 框架久了，主 agent 单线程干活会遇到两个典型瓶颈：一是上下文越塞越满，工具返回的大段输出把真正重要的指令稀释掉；二是串行执行慢——比如“把这十个仓库的 README 各翻译一遍并跑一遍 lint”，一个 agent 排队做，耗时就是十倍。

subagent 编排就是解决这类问题的：主 agent 负责拆任务、派任务、收结果，子 agent 各自带独立上下文去执行。配合 MCP 工具和插件，子 agent 能真正“动手”改文件、调服务，而不只是生成文本。

# 问题

实际用下来，直接让主 agent“开 N 个子任务并行跑”基本不可靠。常见的翻车方式：

- 子 agent 互相覆盖同一批文件；
- 主 agent 把全部背景塞给每个子 agent，上下文爆炸且各自跑偏；
- 子 agent 报告“完成”，实际工具调用失败了一半；
- 并发一高触发 API 限流，整批任务半途而废。

核心矛盾是：并行带来隔离需求，而聚合又要求结果可校验。这两头都得显式设计。

# 做法 / 步骤

我目前稳定使用的模式可以概括为“文件交接 + 主 agent 验收”：

1. **拆任务**。主 agent 先把工作拆成互不共享写文件的独立单元。每个任务写清楚：输入在哪、输出写到哪个路径、完成标准是什么。
2. **定契约**。给每个 subagent 的 prompt 只包含它需要的最小上下文加输出契约，例如：“把结果写入 `work/03.report.md`，格式为三条要点，不要读取其他文件。”
3. **并行派发**。用 subagent 机制一次发起多个子会话，给每个子 agent 独立的工作目录，或至少独立的输出文件。并发上限先压到 3–4，观察限流情况再调。
4. **聚合与验收**。主 agent 不信任子 agent 的口头汇报，逐个读输出文件做校验：格式对不对、关键内容在不在。失败的单独重派一次，而不是整批重来。

# 踩坑点

- **写冲突最阴险**。两个子 agent 各自“读—改—写”同一个文件，谁后写谁赢，还不报错。拆任务时按文件边界拆，或强制每个子 agent 只写自己的文件。
- **子 agent 上下文不是越多越好**。我试过把整份需求文档塞给每个子 agent，结果翻译类任务跑去“顺便优化代码”。最小上下文加明确指令效果更好。
- **“完成”不等于“做对”**。子 agent 的自我汇报必须当作待验证声明，验收环节不能省。
- **没有超时的并行等于挂死的并行**。给每次派发设时限，超时的子 agent 直接放弃、单独重派。
- **日志按子任务分文件**。出问题时全混在一个会话日志里，根本没法定位是哪个子 agent 干的。

# 可复用建议

- 把“任务契约”做成固定模板：输入路径 / 输出路径 / 完成标准 / 禁止事项，四行写死。
- 主 agent 的角色定位是“项目经理加质检”，不是打工人。它自己动手越少，编排越稳。
- 结果用文件交接而不是靠对话回传，天然可追溯、可重跑。
- 先串行跑通一个子任务，再放开并行。能串行跑对是并行跑对的前提。

# 总结

subagent 编排不是“多用几个 AI”这么简单，本质是工程问题：隔离写路径、最小上下文、显式契约、独立验收。把主 agent 当调度器、把文件当消息总线、把子 agent 的汇报当不可信输入——这套模式在我们的批量翻译、批量审查、多源信息汇总里已经稳定跑了一段时间，故障率明显低于让单个 agent 硬扛。并行带来的提速是副产品，可靠性才是主产品。
