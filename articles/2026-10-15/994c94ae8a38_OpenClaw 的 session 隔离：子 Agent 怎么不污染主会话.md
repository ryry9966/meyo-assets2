## 背景

OpenClaw 的主会话是长期运行的：聊天记录、工具调用结果、记忆读写全都堆在同一个 context 里。跑得越久，主会话越“重”。子 Agent（通过 `sessions_spawn` 拉起的独立会话）是官方给的解法之一，但不少人用了一段时间还是疑惑：子 Agent 到底隔离了什么？为什么它“看不到”之前的对话？这篇把我现在的工作方式整理一下。

## 问题：不隔离会怎样

如果子任务直接跑在主会话里，典型后果有三个：

1. **Context 膨胀**：一轮批量文件处理、一次全网调研的中间输出，能把主会话的有效上下文顶掉一大截，之后的对话质量肉眼可见地下降。
2. **干扰决策**：大量过程性工具输出留在上下文里，主模型容易被无关细节带偏。
3. **副作用扩散**：子任务里的报错、重试、临时路径全留在主会话记忆里，回头翻记录全是噪音。

## 隔离机制：进什么、出什么

OpenClaw 的子 Agent 会话，本质是“独立 session + 受限工具 + 一次性生命周期”：

- **独立上下文**：子 Agent 看不到主会话历史，只能拿到 spawn 时传入的任务 prompt。这是特性，不是 bug。
- **结果单向回流**：子 Agent 干完活，主会话收到的只是它的最终回复（结论/摘要），不是全程 transcript。
- **生命周期短**：子会话记录单独存放、用完即可清理，不要把它当持久存储用。

## 实操：我现在的做法

1. **任务 prompt 自包含**。按固定结构写：目标 / 输入（绝对路径、参数）/ 约束（只读、工作目录、不许动 git）/ 输出格式（一段不超过 200 字的总结 + 关键数据）。
2. **一次 spawn 一个明确任务**。要并行就在同一条消息里 spawn 多个，每个职责单一。
3. **调研类任务加只读约束**；写文件类任务给独立的 scratch 目录，避免和主会话、其他子 Agent 抢同一批文件。
4. **要求“结论先行”的输出**。主会话只消费摘要，需要细节时让子 Agent 指到具体文件路径，而不是把全文塞回来。
5. **排查直接看子 Agent 的 session 日志**，不要靠主会话的“回忆”去还原它干了什么。

## 踩坑点

- **以为子 Agent 能看见上下文**：结果它反问“哪个文件？”，或者自作主张猜路径。我遇到的子 Agent 翻车，九成是 prompt 不自包含。
- **反向踩坑**：spawn prompt 里把整段历史原样贴进去，隔离等于白做。传的是提炼后的任务说明，不是原始上下文。
- **并行写冲突**：多个子 Agent 同时改同一目录或同一 git 仓库，merge 冲突比省下的时间贵。并行前先做文件级切分。
- **递归 spawn**：默认子 Agent 不能再生子 Agent，别为了“更智能”打开这个口子，失控后上下文和费用都不好看。
- **最终回复啰嗦**：主会话收到的就是那段话，它写 800 字废话，污染只是换了个地方发生。

## 可复用建议

- 把主会话当**编排者**：只做决策、汇总、对外沟通，重活全部下沉。
- 固化一个 spawn 模板（目标/输入/约束/输出），每次微调而不是重写。
- 子 Agent 数量宁少勿多：3 个职责清晰的，好过 8 个互相踩脚的。

## 总结

Session 隔离不是魔法，而是一份契约：**prompt 进、摘要出**。spawn 时多花两分钟写清任务边界，换来的是主会话长期干净、成本可控、行为可预测。社区里跑长任务的同学，最后基本都收敛到这套模式。有更好的模板欢迎贴出来一起迭代。
