让 AI Agent 跑一个 20 步以上的长任务——比如"调研某行业并产出报告""把一个仓库的代码重构一遍"——你大概率见过这样的场面：前几步它精神抖擞，到十几步开始重复提问、忘记约束、把已经改过的文件再改一遍。社区戏称这是"金鱼记忆"。最近 36kr 报道的"类Jev模型接管 Agent 调度"，指向的正是这个问题：与其让大模型自己硬扛记忆，不如请一个专职的调度模型来管。这篇文章把"失忆"的原理、现有补丁的短板、这条新路线的逻辑与边界一次讲清（下文按报道口径，把这类专职调度模型统称"类Jev"）。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/e98b31a42e4c581b.png)

## 一、失忆的根源：不是模型笨，是架构有三道坎

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/6cc49d33623d4a45.png)

1. **上下文窗口有限且昂贵**。主流模型窗口已到 128K 甚至 1M token，但 Agent 每走一步都要把历史重新塞进 prompt。粗算一下：循环里每步重发全部历史，n 步任务的累计 token 消耗是 O(n²) 量级——50 步任务的累计开销约为 10 步任务的 25 倍。
2. **注意力会"稀释"**。斯坦福 2023 年的"Lost in the Middle"研究给过结论：模型对上下文开头和结尾的信息召回最好，中间部分明显掉链子，部分设置下掉 20 个百分点以上。窗口再大，塞在中间的细节照样"看得见、想不起"。
3. **错误会滚雪球**。长任务是串行依赖：第 7 步一个错的文件路径，第 15 步可能演变成整条分支跑偏。没有外部纠错机制时，错误率随步数近似复合增长——这是很多 Agent 演示"前半段封神、后半段崩盘"的直接原因。

工程侧还有个隐藏成本：推理时 KV cache 随上下文线性膨胀。以 7B 级模型、典型 MHA 结构、fp16 精度估算，32K 上下文的 KV cache 就能吃掉十几 GB 显存。所以记忆问题不只是"装不下"，还是"养不起"。

## 二、现有补丁为什么不够用

- **滑动窗口**：只保留最近 N 步。简单有效，但等于主动遗忘中段的关键决策。
- **摘要压缩**：把旧历史压成 summary。省 token，但压缩必然有损——约束条件、中间结论容易被压没。
- **RAG 外挂记忆**：历史切片进向量库，用时检索。难点在于"检索什么"——Agent 往往不知道自己忘了什么。
- **MemGPT 式分层记忆**：借鉴操作系统分页，把记忆分"核内/核外"。思路是对的，但"什么时候换页"这个决策本身很难：规则写不全，让大模型自己判断又贵又不稳定。

这些方案的共同点是：记忆管理仍然寄生在主模型身上。类Jev 路线的核心变化就一句话——**把调度权从主模型里剥离出来，交给一个专职小模型**。

## 三、类Jev思路：给 Agent 配一个"操作系统内核"

把主 LLM 类比为 CPU——算力强但不该管杂务；调度模型就是 OS kernel——专职决定资源怎么分配。分工大致是这样的：

1. **压缩与写入**：监控任务流，判断哪些中间结论该固化为长期记忆，哪些草稿可以丢弃。
2. **检索与换页**：任务进入新阶段时，主动把相关记忆换入工作区、无关内容换出，保住主模型的注意力质量。
3. **任务重排与断点续传**：长任务被切成带检查点的子任务，某步失败就从最近检查点恢复，而不是从头再来。
4. **异常拦截**：发现 Agent 循环重复、或输出与约束冲突时，提前纠偏或上报。

为什么用小模型反而可行？因为调度是**决策密度高、但单步推理浅**的任务——判断"该压缩了""该检索了"不需要千亿参数，几个 B 的模型靠蒸馏加强化学习就能胜任，奖励信号直接绑定下游任务成功率。总账算下来：小模型高频调用（便宜）+ 主模型只在关键步骤全功率输出（贵但少），比"每一步都让大模型背着全部历史硬算"划算得多。

开源的意义也在这里：调度策略可以被复现、被微调、被私有化部署。对要在内网跑 Agent 的团队来说，这比闭源记忆中间件现实得多。

## 四、冷静看待：它不是银弹

- **任务可分解性是前提**。调度模型擅长管理结构清晰的长流程；对高度依赖灵感跳跃的开放型任务，收益有限。
- **多一层系统，就多一类 bug**。调度器如果把关键记忆错误淘汰，这种故障比主模型的幻觉更隐蔽、更难排查。
- **评测要跟上**。看这类方案别只看 demo，重点看长任务基准（多步工具调用、长程软件工程类任务）上"步数—成功率"曲线的斜率有没有真实改善。

## 五、给你的三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/03a33981a72caf7a.png)

1. **先画失忆曲线，再决定动手**。给自己的 Agent 记录"步数—成功率"数据，找到断崖点在哪一步，再选择滑动窗口、摘要还是调度模型。多数团队的实际问题，还到不了需要专职调度模型的规模。
2. **上下文工程优先于记忆系统**。结构化状态文件、检查点机制、机器可读的显式约束清单（而不是埋在自然语言里），这三个低成本手段能解决一半以上的"伪失忆"。
3. **小规模验证调度模型的迁移成本**。开源调度模型值得持续跟，但先拿一两个典型长任务做 A/B：对比成功率、token 开销、失败恢复时间，数字说话再决定是否引入。

Agent 的记忆问题，本质上是"注意力是稀缺资源"这个老问题在新架构上的重演。操作系统当年靠分层与调度解决了内存稀缺，Agent 大概率也会走同一条路——只不过这次的"内核"，是团队亲手训出来的模型。
