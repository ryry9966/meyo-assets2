## 背景

单个 Agent 处理主线任务没问题，但遇到"面广活浅"的工作——比如一次性审查 10 个文件、交叉核对 3 个 MCP 数据源、给整个项目做健康巡检——它只能串行推进。结果是慢，而且中间产物把主上下文塞得满满当当，等真正要写结论时，主 Agent 已经被过程信息淹没了。

## 问题

三个具体痛点：

1. 主 Agent 上下文被长任务的中间过程污染，注意力被稀释；
2. 串行执行浪费墙钟时间，本可并行的独立子任务排队等彼此；
3. 高风险操作（跑脚本、改文件、外部调用）混在主流程里，一个出错全盘连坐。

## 做法

思路是把主 Agent 定位为"调度员"，subagent 是"工人"。我们落地的五个步骤：

1. **任务拆解**：主 Agent 先把大任务切成 N 个彼此独立的子任务。判断标准很硬：子任务间数据依赖趋近于零。有先后依赖的，不要强行并行。
2. **写任务卡**：每个 subagent 的 prompt 必须自包含——目标、必要输入（直接贴进去，它看不到主对话）、可用工具白名单、输出格式、停止条件。缺一项，它就会自由发挥。
3. **并行派发**：同时拉起 3~4 个 subagent，各自隔离上下文，工具集按最小权限给。
4. **受控执行**：设最大轮数和超时。大体积产出先写文件，返回消息里只带摘要，实践中我们强制"返回不超过几百字的 JSON，细节落盘"。
5. **聚合收口**：主 Agent 收各路结构化结果，合并、消歧、出最终结论。冲突的部分单独标记，不静默合并。

## 踩坑点

- **默认 subagent 能"看到"主上下文**。这是最常见的错。subagent 没有记忆，任务卡里没写的等于不存在。
- **工具冲突**：两个 subagent 同时改同一个文件、同时跑 git、占同一个端口。派发前做资源分区，或者把操作设计成幂等的，重试才安全。
- **Token 消耗翻倍**：4 路并行就是 4 倍成本，没有轮数上限就是无底洞。上限加超时，双保险。
- **静默失败**：某一路挂了不能拖死全局。超时兜底，失败也要返回明确的错误结构，别让主 Agent 干等或误判成功。
- **返回不设限**：subagent 话痨一点，主上下文立刻爆炸。格式约束要写死在任务卡里。

## 可复用建议

- 把任务卡做成模板：目标 / 输入 / 工具白名单 / 输出格式 / 约束，每次复制微调；
- 信息传递优先走共享文件系统："过程进文件，结论进消息"；
- 先跑 2 路并行验证拆解质量，再逐步加并发，不要一上来就拉满；
- 每个 subagent 的 transcript 单独留档，排障时能对上账；
- 流水线式的依赖链任务不适合并行，只有依赖图上的叶子节点才值得派 subagent。

## 总结

Subagent 编排本质上是工程化的项目管理：任务边界清晰、资源相互隔离、返回受到约束。Agent 的智能决定拆解质量，这些工程约束决定并行是提效还是灾难。不建议追求大规模并发，先把 2~3 路跑稳、把任务卡模板打磨好，收益就已经很明显了。
