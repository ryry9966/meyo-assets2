## 背景

做 Agent / MCP / 自动化的同学，大多数时候依赖云端 API。但有几类场景本地模型确实更合适：数据不想出本机、频繁调试不想烧 token、断网或内网环境、以及想深度定制模型行为。这篇帖子记录我在一台消费级显卡的家用机上部署本地 LLM、并接入 Agent 工具链的完整过程，重点放在工具调用相关的实践上。

## 问题

先把要解决的问题列清楚：

1. 显存有限（12GB），跑多大参数、什么精度的模型是第一道选择题；
2. Agent 场景对 tool calling 依赖很重——不少模型本地对话没问题，函数调用却一塌糊涂；
3. 长上下文 + KV cache 的显存开销容易被低估，context 一拉长就 OOM；
4. 推理框架众多（Ollama、llama.cpp、vLLM……），选型成本高。

## 做法与步骤

**第一步：盘点硬件。** 显存是硬约束。12GB 显存跑 7B–14B 的 Q4/Q5 量化模型比较稳；纯 CPU 也能跑，但 Agent 多轮循环里延迟会被逐轮放大。

**第二步：选推理框架。** 我用 Ollama 起步（模型管理省心，OpenAI 兼容接口开箱即用），对吞吐有要求后再换 llama.cpp server 或 vLLM。关键是它们都提供 OpenAI 兼容 API，Agent 侧代码几乎不用改。

**第三步：选模型。** 优先看三点：工具调用能力、中文能力、上下文长度。建议用自己真实的 Agent 任务做小规模评测（20–30 条带工具调用的样本），不要只看榜单分数。

**第四步：定量化档位。** Q4_K_M 是性价比起点。Q8 精度提升有限但显存接近翻倍；低于 Q4 后工具调用格式错误率会明显上升。

**第五步：接入 Agent。** base_url 指向本地服务、模型名对上即可。MCP 工具的 schema 会随系统提示注入，务必确认本地模型能稳定输出合法的调用格式。

**第六步：压测真实负载。** 模拟 Agent 的多轮循环：系统提示 + 工具 schema + 若干轮调用，观察 tokens/s、首 token 延迟、显存峰值。

## 踩坑点

1. **context 默认值坑**：不少框架默认 context 只有 2K/4K，Agent 的系统提示加工具描述动辄就占满，模型开始"失忆"。要显式设置 context，并为 KV cache 预留显存。
2. **工具调用格式**：同一模型在不同框架下的 tool calling 模板不同，切换框架后必须重测；部分模型需要配套 prompt 模板才能触发可靠的函数调用。
3. **并发即显存**：KV cache 随并发数线性增长，并行参数开大直接 OOM。家用机按 1–2 并发设计即可。
4. **采样参数**：小模型在 Agent 循环里容易复读，适当调低 temperature、加一点 repeat penalty。
5. **历史膨胀拖慢循环**：每轮都要重新处理全部上下文，轮数越多越慢。控制历史长度，必要时做摘要截断。

## 可复用建议

- 建 20–30 条自己的评测集（必须含工具调用），换模型、换框架、改参数都跑一遍，五分钟出结论；
- 显存预算粗略记：权重 + KV cache + 激活，KV cache 与 context 长度 × 并发数成正比；
- 先用 Q4_K_M 的 7B/14B 把流程跑通，再考虑更大的模型；
- 把本地服务和云端 API 做成可切换的配置，Agent 层不感知差异，方便对比与兜底。

## 总结

本地部署的技术门槛在降低，真正的难点在于它能否撑起 Agent 的工具调用循环。实测结论：12GB 级家用机可以稳定承载 7B–14B 量化模型跑轻量 Agent 任务；重度多工具、长上下文的场景，仍建议云端 + 本地混合。先小规模验证，再逐步放大，是最省时间的路径。
