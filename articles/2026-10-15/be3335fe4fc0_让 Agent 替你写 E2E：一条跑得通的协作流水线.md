## 背景

E2E 测试的处境一直尴尬：价值高（覆盖真实用户路径），成本也高（选择器易碎、环境难伺候、改一版 UI 回归一片），团队里愿意写的人少，写完愿意维护的人更少。现在 Agent 能通过 MCP 直接驱动真实浏览器（比如 Playwright MCP 这类工具），“让 AI 顺手把 E2E 补上”从口号变成了可验证的工程实践。我们在内部项目上跑了两三周，把做法和坑记录一下。

## 问题

先划清边界：不是让 AI“凭空想象”测试用例——纯靠 LLM 生成测试代码，产出的是语法正确但断言空洞的摆设。要解决的是这条链路：**操作一遍真实应用 → 记录交互 → 产出可跑的测试草稿 → 人只做审查**。

## 做法

1. **备好环境**。在 OpenClaw 里给 agent 挂上浏览器类 MCP 工具，指向本地 dev 环境；数据库只灌种子数据，邮件短信用本地 fake。工具权限收敛为四类：导航、点击、填表、读 DOM。
2. **一次只喂一个流程**。用自然语言描述用户路径和验收标准，例如“新用户注册后创建第一个项目，应看到引导页”。范围越窄，产出越可用。
3. **让 Agent 真走一遍**。它在浏览器里实际操作，读取 DOM 和可访问性树，而不是看截图猜。走完输出一份 Playwright 测试草稿。
4. **人审两件事**：选择器策略（是否优先 data-testid / role），断言深度（是否断言了业务数据，而不是只 `expect visible`）。
5. **进 CI 后跑修复循环**。UI 变更导致测试挂掉时，让 Agent 看失败原因、重新打开页面、改选择器或改断言，输出 diff 给人确认后合入。

## 踩坑点

- **选择器腐烂**：Agent 很爱抓构建生成的 class 名，第二天构建就挂。规范里必须写死只用 data-testid / role / 可见文本。
- **同义反复断言**：不约束的话，它写出的测试永远绿。我们在 skill 模板里要求每条用例至少断言一个业务字段值。
- **显式 sleep 满天飞**：Agent 模仿了老式测试写法，全靠硬等待。要求统一用 `expect` 的自动轮询。
- **修复循环掩盖真 bug**：UI 没变、测试却“被修好”了，大概率是功能回归。修复 diff 必须人签字，不能自动合。
- **权限不收敛**：删库、支付这类高危流程不要交给 Agent 探索，用固定脚本兜底，MCP 工具只开白名单。

## 可复用建议

- 把测试规范沉淀成一份 skill / prompt 模板：命名、选择器、断言深度、文件位置，Agent 每次生成前先读。
- 仓库里维护一份关键流程清单（每条一段话），既是 Agent 的上下文输入，也顺手当了覆盖率地图。
- 指标只看两个：关键流程覆盖数、flaky 率。别统计生成了多少行代码，那是虚荣指标。
- 心态上把 Agent 当“起草人”：它负责样板代码和维护性劳动，人负责决定测什么、信不信。

## 总结

这套流程跑下来，E2E 从“没人愿意碰”变成了“有草稿、有人审、有 CI”。收益最大的是样板生成和变更后的测试修复；最不该外包的判断是“该测什么”。Agent + 真实浏览器 + 收敛的权限，是这套做法成立的三个前提。缺任何一个，产出都会从“省时间”滑向“添乱”。
