## 背景

日常开发里，git 相关的操作大多是高频低难度的：写 commit message、按规范开分支、合并后清理本地分支。这些事不难，但很打断注意力。OpenClaw 的 agent 本身就能通过 shell 工具操作本地环境，天然适合把这类流程收编进自动化。问题是：怎么让 AI 碰 git，又不至于哪天给你来一个 `push -f`。

## 问题

直接把 git 权限丢给 agent，常见风险有四类：

- 误提交敏感文件（`.env`、日志、构建产物）；
- 自作主张执行破坏性命令（force push、`reset --hard`）；
- commit message 风格飘忽，和团队规范对不上；
- 在错误的分支或 worktree 里操作，改完才发现。

所以重点不是"能不能做"，而是"怎么设护栏"。

## 做法

我目前的配置分五步，从最低风险场景逐步放开：

**1. 限定命令白名单。** 给 agent 的 git 能力只开放只读和低风险命令：`status / diff / log / add / commit / branch / switch`。明确禁掉 `push -f`、`reset --hard`、`clean -fd`。推送操作保留在人工手里。

**2. 把规范写成文件。** 在仓库里放一份说明，约定 Conventional Commits 格式、分支命名（`feat/xxx`、`fix/xxx`）、标题不超过 50 字符。agent 每次先读这份文件，而不是靠我每次口头叮嘱。

**3. 提交流程固定化。** 要求 agent 严格按顺序执行：先 `git status` 和 `git diff --staged`，自己总结改动生成 message，**逐文件 add**（禁止 `-A`），提交后回显"改动摘要 + 提交哈希"让我一眼确认。

**4. 分支生命周期托管。** 开任务前让它基于 main 最新提交建分支；任务合并后，用 `git branch --merged` 列出可清理分支，逐个向我确认后删除。

**5. 保留原有兜底。** pre-commit hook 照常生效，agent 的提交一样会被 lint 和 secret 扫描拦住。新流程先在个人仓库试跑一周，再放到工作项目。

## 踩坑点

- **大 diff 会让总结失真。** agent 面对 500 行的 diff 生成的 message 经常抓错重点。解法是约束提交粒度：一个逻辑改动一个 commit，别攒着。
- **agent 偶尔无视"逐文件 add"的要求。** 后来我在说明文件里写死"add -A 视为违规操作"，加上提交前回显 staged 文件列表，才稳定下来。
- **detached HEAD 状态下它照样干活。** 现在强制它每次动手前先输出当前分支和工作目录路径。
- **别让它做冲突决策。** rebase / merge 遇到冲突，它选的"保留哪边"看起来合理，但可能丢逻辑。冲突一律停下来交给人。

## 可复用建议

1. 规则沉淀成仓库内文件，别依赖对话记忆——换会话就丢。
2. 按"生成 message → 建分支 → 清理分支"的顺序逐级授权，每级观察几天。
3. 固定一个回报格式（摘要 + 分支 + 提交记录），review 成本会降到几秒钟。
4. 白名单宁可一开始给少了再加，反过来收权很难。

## 总结

AI 管 git 的价值不在替代你理解 git，而是把高频、低风险、强规范的操作自动化掉，人保留对推送、合并、冲突的最终决定权。护栏先行、小步授权，这套流程跑顺之后，"提交代码"这件事的注意力开销基本可以忽略。
