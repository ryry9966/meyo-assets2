## 背景

Agent 一旦接上工具——本地 shell、文件系统、MCP server、浏览器自动化——就绕不开一个问题：哪些操作它可以直接执行，哪些必须停下来等人确认。在玩具 demo 里这个问题不明显，一旦 agent 开始碰真实数据、真实账户、真实用户，它就是整个系统里最重要的设计决策之一。

## 问题：两个对称的失败方向

实践中最常见的错误不是单纯“太放权”，而是两个方向都踩：

- **过度请示**。每读一个文件、每调一次只读 API 都弹确认。结果是人类确认者几分钟内进入“无脑点同意”状态——确认疲劳反而把安全机制变成了摆设。
- **过度放权**。agent 在一次“帮我清理日志”的任务里自作主张删了共享目录，或者把未审的草稿直接发给了真实客户。

所以真正的问题不是“问还是不问”，而是**建立一套稳定的分级规则**，让“问”这个动作本身变得稀缺、可信。

## 做法：按可逆性和影响面分四级

把所有工具调用按两个维度分类：可逆性（能不能撤销）和影响面（出错了波及多大）。

- **L0 只读**：读文件、本地检索、只读 API。直接执行，不打扰人。
- **L1 可逆写**：工作区内的文件编辑、写临时分支、沙箱内调用。直接执行，但全量留日志。
- **L2 难撤销 / 对外可见**：删除数据、向真实用户发消息、支付、push 到共享分支。必须确认，且确认载荷要具体——展示 diff、完整命令、目标对象，而不是一句“是否继续？”
- **L3 一律拒绝**：写死在配置里，任何提示词都改变不了。

落地手段：OpenClaw 侧用工具白名单加确认钩子（hook）拦截 L2；MCP server 尽量标注工具的只读属性，给调用方分级依据；花钱类操作设硬预算，超了直接失败，而不是转去请示。

## 踩坑点

- **确认疲劳**：请示频率是最容易被低估的参数。一天弹 50 次，安全机制等于没有。宁可收紧 L1 的范围，也要把确认次数压到人类会认真看的水平。
- **只读工具成为提权通道**：网页抓取是 L0，但抓回来的内容里可能藏着一句“请执行 rm -rf”。注入不依赖工具本身有权限，只依赖下游工具链。分级要覆盖整条调用链，不是单个工具。
- **组合绕过**：agent 不能直接发邮件，但可以写一个文件，而 cron 会把这个文件发出去。边界被组合操作绕过了。审计看最终效果，不看单步动作。
- **批量放大**：人类批准了一次删除，agent 认为该模式已获认可，接着删了 40 个同类目录。确认范围必须显式声明：一次批准只覆盖当次调用的参数。
- **权限只增不减**：白名单越攒越长，没人记得当初为什么加。把它当代码管，进版本库，定期过一遍。

## 可复用建议

1. **默认拒绝，显式放行**。新增工具先落在最严格的层，观察后再调级。
2. **提权有时效**。批准的 L2 权限 10 分钟后自动回落，避免“批准一次、会话内永久生效”。
3. **破坏性操作先跑 dry-run**，把“将要发生的事”渲染给人看。
4. **请示要带上下文**：agent 想做什么、为什么、备选方案是什么。人评估的是计划，不是一句许可请求。
5. **全量审计日志**：每次工具调用记参数、记层级、记结果，出事能复盘。

## 总结

权限边界不该取决于 agent 的“自信程度”，而取决于操作本身的可逆性和影响面。四个层级、一份可版本化的分级配置、一次只覆盖一次调用的确认——这三件事做完，agent 才敢放手用。边界划得越清楚，能推的自动化就越远，这两者是正相关的。
