## 背景

多数 Agent 的使用模式是“你问一句、它答一句”。但当 Agent 常驻在你自己的机器上（比如 OpenClaw 这种接入个人聊天渠道的助理框架），被动应答就浪费了它的存在——你半夜不会去问“服务器挂没挂”，但它明明有能力自己查。

OpenClaw 用一个很小的机制解决这个问题：HEARTBEAT.md + 周期性心跳。它让 Agent 按固定节奏自己醒来、读一份任务清单、判断要不要做事。

## 问题：主动性 vs 噪音

让 Agent 主动做事，核心矛盾有两个：

1. **成本**。每次“主动”都是一次完整的模型调用，如果每分钟醒一次，跑一天账单会很感人。
2. **打扰**。一个没有节制的 Agent 会不停给你发“我检查过了，一切正常”，两天你就会把它静音。

所以这个机制必须回答三个问题：什么时候醒、醒来干什么、没事的时候怎么闭嘴。

## 机制与做法

原理很简单，三个约定：

- 运行时按配置的间隔（默认 30 分钟，也支持 cron 表达式）唤醒 Agent，注入一条固定提示：“读 HEARTBEAT.md 并执行”。
- HEARTBEAT.md 放在工作区根目录，用自然语言写任务清单。
- 无事可做时，Agent 回复字面量 `HEARTBEAT_OK`，运行时拦截这条回复、不投递给你——这就是静默协议。

我的 HEARTBEAT.md 大致长这样：

```markdown
## 巡检
- 检查 ~/logs/app/error.log，出现新的 FATAL 级日志时报告，附时间戳
- 检查 main 分支 CI 状态，失败超过 24 小时未处理才提醒

## 纪律
- 只在异常首次出现时通知，重复出现不要刷屏
- 无事可做时只回复 HEARTBEAT_OK，不要附加任何文字
```

配置上：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "30m" }
    }
  }
}
```

调试期建议把间隔调成 5 分钟，观察两三个完整周期的行为再调回去。

## 踩坑点

- **清单越长越贵**：每次心跳都会把 HEARTBEAT.md 塞进上下文，控制在 20 行以内。高频巡检可以考虑给心跳单独配一个便宜模型。
- **HEARTBEAT_OK 不严格**：模型多写一句“本次巡检完成”，运行时就不认为是静默信号，照样推送。所以“纪律”段必须写，且每次改完清单都回归测一轮。
- **任务写得太含糊**：“帮我留意一下消息”这种条目会让 Agent 天天找借口汇报。每条任务都要有明确的触发条件和通知阈值。
- **注入风险**：心跳会读工作区文件，别把不可信来源（网页原文、陌生文档）留在工作区里，否则等于给定时任务开了任意指令入口。
- **任务堆积**：间隔短、单次任务重（比如让它跑十分钟脚本）时，下一个心跳可能撞上未完成的上一轮，注意工具超时与并发。

## 可复用建议

- 把 HEARTBEAT.md 当 runbook 写：条件、动作、通知策略三段式，别写成散文。
- 只读巡检放心交给心跳；写操作（重启服务、往别人的群发消息）一律要求先问你。
- 心跳适合“需要判断力”的事；硬性定时（每天 9 点日报）用 cron 更可靠，两者搭配使用。
- HEARTBEAT.md 进 git，每加一条任务就是一个 commit，出问题能回溯。

## 总结

HEARTBEAT.md 的本质是一个低成本循环加一条静默协议：`周期唤醒 → 读清单 → 做事或 HEARTBEAT_OK`。机制本身十分钟就能配好，真正的差异在清单质量——写得像 runbook，它就是个靠谱的值班员；写得像愿望清单，它就是个定时骚扰器。建议从一两条高价值巡检起步，跑稳了再加。
