最近 36kr 一条热搜把「人机配比」这件事顶了上来：Claude Code 原本是个住在终端里的命令行工具，被社区一通暴改——套上桌面壳、接上任务看板、接好 git 隔离，硬生生变成一个人的「AI 军团作战室」。一个人拆任务、派活、验收，底下七八个 agent 同时开写。这事看着像炫技，其实是软件工程分工方式正在换挡的信号。今天把它拆开：改的是什么、为什么能改、军团化之后坑在哪。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/aa38fe7dede94fc0.png)

## Claude Code 本体：住在终端里的那只钳子

- 2025 年 2 月，Anthropic 发布 Claude Code，形态是 CLI agent：给它一个代码仓库，它自己读文件、改代码、跑测试、提 commit，在终端里完成整个 agentic loop。
- 设计上处处是「可组合」：CLAUDE.md 充当项目记忆，hooks 允许在生命周期节点插入自定义脚本，MCP（Model Context Protocol，2024 年底开源）把浏览器、数据库、CI 等外部工具标准化地接到 agent 手上——业内常把它比作「AI 应用的 USB-C」。
- headless 模式（`claude -p`）让它能像普通程序一样被脚本调用、吐 JSON 流。这一条是所有「暴改」的地基：既然能被程序调用，就能被程序**批量**调用。
- 官方后来补了 IDE 插件和网页端，但社区走得更快：给 CLI 套 GUI、加看板、加 diff 审阅面板，把单兵工具升级成指挥系统。

## 暴改的三个技术支点：进程、隔离、看板

社区方案五花八门，骨架基本是三块积木：

1. **进程级并行**。用 headless 模式或 Agent SDK，从桌面壳里一次性 spawn N 个 Claude Code 实例，每个实例独立会话、独立上下文。Claudia、Claude Squad、Vibe Kanban 这类开源项目，本质上都是这个思路的不同 UI 包装。
2. **工作区隔离**。git worktree 让同一个仓库派生多个独立工作目录，每个 agent 在自己的目录、自己的分支上干活，互不踩脚。没有这一步，五个 agent 改同一个文件就是灾难片。
3. **编排与验收界面**。看板管理任务队列，每个格子绑一个 agent；改动以 diff 呈现，人只在关键节点点「允许」或「打回」。hooks 在这里当门禁：测试不过，不许提交。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/82e5109fb75c0701.png)

一句话概括这套架构：**人负责「什么算做完了」，agent 负责「怎么做完」**。指挥官的工作从敲代码变成写规格、切任务、审 diff——这也是为什么有人说，AI 时代最稀缺的工程技能之一是「把活儿拆清楚」。

## 分工换位：从写代码的人，到验收代码的人

- 节奏完全不同了。以前：接 ticket → 写码 → 自测 → 提 PR，一天两三个封顶。军团模式：早上花一小时，把五个 ticket 拆成带验收标准的规格（输入、边界条件、必须通过的测试），然后派发、巡检、review、merge，人的一天在「审」而不在「写」。
- Anthropic 团队公开分享过，Claude Code 自身的代码有相当大比例（给过约九成的说法）由模型产出；但规格设计与验收始终由人把守。这基本就是军团模式的成熟形态预览。
- 代价是瓶颈转移。人的产出速度不再限制项目速度，但人的**审阅带宽**成了新瓶颈：单线程的人类面对多线程的 agent，review 队列只会越排越长。

## 军团不是越大越好：并行的三笔账

- **冲突账**。N 个 agent 共享一个代码库，改到同一批模块的概率随 N 上升，merge 冲突与返工大致按组合数增长。经验法则：每个 agent 只领「横切面小」的任务，公共模块串行改。
- **成本账**。token 消耗随并行数线性上涨，重度并行场景下 API 账单一天烧掉几百美元很正常，订阅制则有速率限制兜底。开八个 agent 跑一整天，可能只产出三个能 merge 的 PR——先算「单位有效产出的成本」，再决定军团规模。
- **质量账**。agent 之间没有共享的情境感知，会重复造轮子、调用不存在的 API、在过时认知上盖楼。2025 年 METR 那项研究值得贴在墙上：资深开源开发者用上 AI 工具后，自认为快了 20%，实测慢了 19%。感觉提速和实际提速之间，隔着一条叫「返工率」的河。

## 上车前的三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/6fdf42e85bd17e07.png)

1. **先把任务拆清楚，再谈并行。** 不能被测试验证的任务派给 agent，等于开了一台随机代码发生器。规格里写清输入输出、边界条件、必须通过的测试——验收标准越硬，军团越靠谱。
2. **隔离要彻底，信任要渐进。** worktree / 容器沙箱是底线；默认关掉 auto-approve，让每次写操作、每条 shell 命令都过闸；分支保护 + CI 绿灯才允许 merge。权限给出去容易，收回来难。
3. **用数据校准体感。** 给每个 agent 记三笔账：返工率、token 成本、测试通过率。体感说「快多了」不算数，METR 的 -19% 就是前车之鉴。军团化不是信仰问题，是一道算术题。

工具在换挡，工程能力的定义也在换挡：从「能写出代码」，变成「能指挥一个会写代码的系统」。钳子多了，活儿好不好，还是看掌舵的那只钳。
