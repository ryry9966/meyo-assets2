最近技术圈有条消息值得细品：据 36kr 等媒体转述，Anthropic 只用了 7 名工程师、5 个月时间，就在内部造出一套版本控制系统，替代了服役近二十年的 Git 工作流。一家手握顶级 AI 编程工具、最没理由“重复造轮子”的公司，为什么偏要自己动手？答案不叫炫技，而是一个更根本的变化：写代码的，不再只有人了。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/cee6ff3a64d8ace4.png)

## 先补课：Git 是为“人”设计的系统

- 2005 年，Linus Torvalds 因 BitKeeper 授权破裂，花十几天写出 Git 雏形，目标很明确：让上千名人类开发者高效协作 Linux 内核。
- 它的核心设计几乎全是围绕“人”展开：
  1. 分布式：每人 clone 完整仓库，离线也能干活，历史不可篡改；
  2. 分支即任务单元：feature branch、Pull Request、code review，本质是给人看的协作仪式；
  3. 冲突靠人解：三方合并按文本行比对，机器搞不定的部分，留给人类的脑子和键盘。
- 底层上，Git 用哈希寻址存快照、分支只是指针，轻快灵活；2008 年 GitHub 上线后，把这套分布式能力包装成社交化协作，"branch–commit–PR–merge"从此成了全球程序员的肌肉记忆。

这套设计太成功，二十年没人动过地基。直到它的服务对象变了。

## 瓶颈在哪：当 agent 成为提交主力

Anthropic 是这轮变化的极端样本。据其管理层公开分享，内部绝大多数代码已由 Claude 完成，比例一度被提到九成上下。于是 Git 的几条“人类假设”逐条失效：

- 分支仪式变成噪音：人一天开两三个分支是常态，agent 一天能跑出成百上千个并行会话，每个都走 branch→PR→review，人类评审通道瞬间堵死；
- 完整 clone 是浪费：agent 通常跑在一次性容器里，为改几百行代码拉全量仓库，时间和存储都是纯开销；monorepo 一大，clone 和切分支的等待对人类尚可忍，对高频启停的 agent 是灾难；
- 文本合并不够用：agent 不怕冲突，怕的是等人。文本级合并解不了就挂起，而挂起正是并行度最大的敌人；
- Review 重心变了：逐行审机器代码性价比极低，真正把关的是测试、CI 和任务目标是否达成。

一句话概括：Git 管理的是“人类的提交历史”，而 Anthropic 需要的是“agent 的协作调度系统”。

## 他们怎么改：把版本控制从“给人用”改成“给 agent 用”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/5fe737187203946e.png)

从公开分享看，新系统的思路是围绕 agent 重排优先级，共识大致有四条：

- 服务端为中心：仓库常驻服务端，agent 领取轻量工作区、按需同步，不再人人 clone 全库；
- 快照代替分支仪式：高频自动快照加一键回滚，agent 崩了、跑偏了，直接回到上一个检查点，不开新分支、不留烂尾 PR；
- 合并尽量自动化：冲突先由系统检测，能自动合的合掉，解不了的交给 AI 做语义级调和，再用测试结果当最终裁判；
- 审计与回滚优先：所有改动留痕，人类 review 从逐行细读，升级为按变更集和执行结果抽查。

为什么 7 个人 5 个月干得动？一是范围收敛，只服务内部已知工作流，不做通用产品；二是站在 Git 二十年的概念积累上，该借的照借；三是最有意思的一点——用 Claude 写 Claude 要用的工具，AI 加速了“解决 AI 瓶颈”的工程本身，dogfooding 闭环比加班管用。

## “Git 已死”？先把墓志铭收起来

- 生态位不同：Anthropic 是“agent 写九成代码 + 内部 monorepo”的极端场景。多数团队的现实仍是人写人审为主，Git + PR 依旧是性价比最高的默认解。
- 自研并非孤例：Google 为超大规模 monorepo 造过 Piper，Meta 用 Sapling 重塑过 Mercurial 工作流。共同点都是——规模或工作方式超出了原有假设。
- 历史节奏：版本控制大约十年来一次范式迁移，CVS/SVN（集中式）到 Git（分布式）花了近十年，新范式通常从内部与垂直场景起步。
- 更可能的走向是分层而非替换：Git 的对象模型和存储层继续服役，上层交互——分支、评审、合并这套“工作流”——被 agent 原生工具重塑。就像 GitHub 当年没换掉 Git，却重新发明了协作方式。

但信号是实的：当工作方式变了，“不可撼动的基础设施”也会变成可讨论的选项。

## 冷思考：三条带回去能用

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/5eb40b656741c29a.png)

1. 先量化瓶颈，再谈换工具。拉出团队的 PR 平均流转时长、冲突率、评审排队时间。大头卡在人，换什么系统都没用；卡在流程拥堵，优先试合并队列（merge queue）、trunk-based 这类轻改法。
2. 把测试当第一审稿人。agent 时代，自动化验证的质量直接决定机器产出能多快安全合入。测试薄弱还猛上自动化，等于给没刹车的车踩油门。
3. 小团队 + AI 正在重画基础设施的门槛线。7 人 5 个月做出 VCS 级系统，说明基础软件的护城河正从“造不出来”转向“生态与信任”。对个人来说，保值的是判断该不该造、怎么造的能力，而不是对某个工具的肌肉记忆。

工具会老，工作流的演化不会停。盯住“谁在写代码”这个变量，比死守任何一款工具都更管用。
