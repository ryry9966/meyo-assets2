# 自动化任务的幂等性：为什么重复执行不会出问题

## 背景

跑过一段时间 Agent 自动化的人，几乎都遇到过同一个场景：任务明明执行完了，几天后却发现它被执行了两次。原因不外乎几种——LLM 网关超时后客户端重试、MCP 工具调用中途断连、调度器误判失败重新拉起、用户在界面上点了"再跑一次"。重试本身不是 bug，恰恰是自动化可靠性的来源；问题在于任务是否经得起重试。这就是幂等性：同一任务执行一次和执行多次，最终结果一致。

## 问题

非幂等的操作在重试下会放大副作用，典型症状：

- 通知类工具发出两条一模一样的消息；
- "创建工单/记录"类操作写入重复数据；
- 对文件 append 的步骤，重跑后内容翻倍；
- 计数、累加类接口被多加或少加一次。

这些操作有一个共同点：它们描述的是"做一次动作"，而不是"达到某个状态"。重试场景下，前者必然出问题。

## 做法

我在自己的 OpenClaw 工作流里按四步收敛这个问题：

1. **给操作分类。** 把工作流里所有写操作过一遍，标出天然幂等的（把状态设为 X、按固定 key 做 upsert）和非幂等的（append、create、increment）。后者才是改造对象。
2. **造出确定性的任务键。** 用触发源 + 目标 + 时间窗口拼一个 key，比如 `daily-report:2024-06-01:channel-a`。同一次逻辑任务的 key 稳定，重试才能被识别。
3. **加一层执行台账。** 用 SQLite 或 Redis 存 `(task_key, status, result_hash, updated_at)`。工具执行前先查台账：已完成就直接返回上次结果，不重复触发副作用。注意用唯一约束或 `SETNX` 这类原子操作做"占位"，而不是先查后写。
4. **把语义从"做动作"改成"确保状态"。** 这是收益最大的一条：工具接口不要叫 `send_message`，而是 `ensure_notified(user, event_key)`。底层先查重再发送，重试自然安全。

## 踩坑点

- **先查后写有竞态。** 两个并发实例同时查"不存在"，然后各自创建。必须靠数据库唯一索引或原子命令兜底，不能只靠应用层判断。
- **key 粒度失衡。** 太粗会把用户手动触发的合法重跑也吞掉；太细（精确到毫秒）等于没去重。建议按"逻辑任务"而非"物理执行"来定义。
- **响应丢失比请求失败更麻烦。** 请求实际成功但响应超时，客户端看不到结果只能重试——所以去重必须做在服务端/工具层，客户端检查不可靠。
- **台账别放内存。** 进程重启去重状态就没了，等于裸奔。另外记得给台账设过期或归档策略，不然它自己会变成新的问题。

## 可复用建议

- 幂等性要固化在 MCP 工具/插件层，而不是靠提示词让模型"记住做过没有"。模型上下文不可靠，台账才可靠。
- 把"跑两遍"纳入验收：任何新自动化任务上线前，手动连续触发两次，确认副作用只发生一次。
- 接受"至少一次 + 去重"的现实。真正的"恰好一次"在分布式场景里成本极高，通常不值得追求。

## 总结

自动化系统的可靠性不来自"永远不重试"，而来自"重试也无害"。把副作用收敛到确定性的任务键和一份持久化台账上，让重试变成安全的日常操作，你的 Agent 工作流才敢真正放到无人值守的环境里跑。
