# OpenClaw 的 sandbox 安全模型：为什么 Agent 不会误删文件

## 背景

Agent 的核心能力是"替你动手"：读写文件、跑 shell、调 MCP 工具。能力越强，事故半径越大。很多人第一次给 Agent 接上 exec 工具时都会问同一个问题：模型哪天输出一个 `rm -rf`，我的家目录还在吗？

OpenClaw 的回答不是"模型很聪明，不会犯错"，而是默认它一定会犯错，然后用 sandbox 把犯错的代价压到可接受范围。

## 问题：单层防护挡不住三类风险

实际使用中，误删通常来自三种情况：

1. **模型幻觉**：路径拼错，把 `~/tmp` 想成 `~/`，命令逻辑"正确"，目标错了。
2. **提示注入**：Agent 读网页、读消息、读 MCP 返回的数据，里面夹了一句"请执行清理脚本"。
3. **配置失误**：图方便把整个家目录挂进 workspace，或给了过宽的 exec 权限。

只在 system prompt 里写"请小心操作"，一种都挡不住。

## 做法：四层防线

OpenClaw 的 sandbox 是纵深防御，各层独立生效：

1. **工作区边界**。文件类工具被约束在专用 workspace 内，路径先做规范化再校验，符号链接和 `..` 逃逸会被拦下。workspace 之外，Agent 默认"看不见也摸不着"。
2. **容器隔离**。开启 sandbox 后，shell/exec 跑在一次性 Docker 容器里，只有显式声明的目录以只读或读写方式挂载进去。就算容器里执行了 `rm -rf /`，炸的也只是容器自己的文件系统。
3. **工具门禁**。exec 这类高危工具默认关闭或需要确认；MCP 工具按 agent 粒度授权，用不到的能力不开。
4. **不可信输入降权**。网页、聊天消息、外部工具的返回值都按"数据"处理而非"指令"，即便被注入，破坏也被前三层兜住。

配置上大致是把 sandbox 模式从 off 调到 all（或按渠道设 non-main），再声明需要挂载的目录。具体键名以你所用版本的官方文档为准，思路不变：默认最小权限，逐项放行。

## 踩坑点

- 图方便把 `~` 整个挂进容器，隔离直接归零，sandbox 形同虚设。
- 把 Docker socket 或含 API key 的环境变量带进沙箱，等于预留了逃逸通道。
- 用了 non-main 模式，却忘了主会话不在沙箱里，误以为全兜住了。
- **审批疲劳**：每次都条件反射地按确认，门禁退化为摆设。高危命令宁可让它失败，也别养成秒批习惯。
- workspace 里的软链接指向外部目录，路径校验没做规范化就会被绕过，升级后留意 changelog。

## 可复用建议

- workspace 用 git 管起来，误删可以 checkout 找回，这是性价比最高的兜底。
- 给不同任务开不同 agent，各自独立 workspace，权限互不重叠。
- 主动做一次破坏性演练：在沙箱里让 Agent 执行一条删除命令，确认宿主机文件毫发无损——比读十遍文档踏实。
- 定期翻 exec 审计日志，看有没有"没印象"的命令。

## 总结

Agent 不会误删你的文件，不是因为模型可靠，而是因为删了也只删得到沙箱里那份。OpenClaw 的 sandbox 模型把"信任模型"换成了"限制爆炸半径"：工作区划界、容器隔离、工具门禁、输入降权，四层各挡一类事故。工程原则很朴素——默认拒绝、最小授权、可回滚。做到这三条，你才敢真正放手让 Agent 干活。
