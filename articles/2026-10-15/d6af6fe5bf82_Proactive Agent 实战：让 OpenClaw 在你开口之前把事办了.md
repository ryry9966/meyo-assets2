# 背景

大多数 Agent 的默认形态是被动应答：你发消息，它处理。但真正省时间的场景往往是反过来的——构建挂了它先报，日历冲突了它先调，依赖出了 CVE 它先查影响面。OpenClaw 的 heartbeat/cron 机制加上 MCP 工具链，其实已经具备做 proactive 的全部零件，缺的不是能力，而是一套克制的设计。

# 问题

最直觉的做法是：定时任务每半小时唤醒一次模型，“看看有没有什么事”。跑起来立刻会遇到三个问题：

1. **成本**：绝大多数唤醒一无所获，token 纯烧；
2. **骚扰**：主动消息一旦频繁，用户会关通知，整个机制等于作废；
3. **误报**：模型天然倾向于“找点事汇报”，会放大甚至编造问题。

所以 proactive 的核心不是“多做”，而是**什么时候配做**。

# 做法

我目前跑的流水线分五步：

1. **数据接入**：用 MCP server 拉事件源——Git 仓库、监控告警、日历、依赖扫描结果，全部只读。
2. **规则预筛**：cron 拉到数据先过一道便宜的正则/阈值过滤，命中才进模型。这一步的命中率直接体现在账单上。
3. **模型裁决**：给 agent 一个模板化的判断 prompt，三条硬条件——事件**可行动**、**有明确截止时间**、**属于用户明确圈定的关注域**。任一不满足，写入待办池，不通知。
4. **动作分级**：
   - L0：只记录，不发声；
   - L1：通知 + 附建议；
   - L2：通知 + 给出可一键确认的执行方案；
   - L3：直接执行，仅限白名单内幂等、可回滚的操作（重启无状态服务、清理临时资源这类）。
5. **反馈闭环**：每次主动行为记录“被回复 / 被忽略”，每周复盘一次，据此调阈值和分级。

# 踩坑点

- **心跳频率别贪高**。我一开始设 10 分钟一跳，两天烧掉的 token 抵得上一个月正常对话；降频加预筛后降到原来的 1/8。
- **主动消息必须带证据**。强制要求附原始日志链接或 diff，否则 agent 偶尔会“总结出”不存在的问题。
- **去重要做在状态层**。同一个 CVE、同一次构建失败只提醒一次，dedup key 落库，别指望模型记得。
- **静默时段和每日上限是硬约束**，写在网关层而不是 prompt 里——prompt 里的规则模型会“偶尔忘记”。
- **主动会话和主会话隔离**，否则主动上下文很快污染你日常对话的记忆。

# 可复用建议

- 先只开 L1 跑两周，攒够反馈再逐步放开 L2/L3。**写权限的开放速度应该明显慢于你信心的增长速度**。
- 判断条件全部模板化进 prompt，别散落在代码里；条件变了只改模板，不碰逻辑。
- 给每个主动行为打标签（来源、等级、结果），这是你唯一能拿来做阈值调优的数据，没有它复盘全靠感觉。

# 总结

Proactive 不是把 cron 挂上模型就完事，它的本质是替用户做“是否值得打扰”的判断。用规则挡量、用模板定标准、用分级控风险、用反馈调参数——四件事做扎实，Agent 才会从“你得盯着它”变成“它盯着事”。克制，是这个功能唯一的正确打开方式。
