## 背景

团队日报大多靠人肉：翻 git 提交、看 CI 结果、回忆昨天做了什么，再拼成一段文字。低价值，但每天都要做。我们的思路是让 Agent 承担取数与成文，人只做最后审核。跑了一段时间后，把这套流水线的设计与踩坑整理如下。

## 问题：为什么一个 Prompt 解决不了

最初的做法很直接：把当天所有日志丢给模型，让它"写一份日报"。实际效果不稳定：

1. 日志噪音大，debug 行淹没关键事件；
2. 多数据源（git、CI、告警、工单）格式不一，模型经常漏项；
3. 数字类结论（构建次数、失败率）模型会算错甚至编造；
4. 输出格式随 prompt 波动，没法直接归档。

结论：LLM 适合"成文"，不适合"取数与计算"，这两层必须拆开。

## 做法：五段式流水线

**1. 采集层**。每个数据源封装成独立的 MCP tool：`git.daily_commits`、`ci.runs`、`alert.summary`。工具内部用代码做时间窗口过滤（昨天 00:00–24:00，明确时区），返回统一 schema 的 JSON。

**2. 清洗层**。降噪放在工具侧而不是 prompt 侧：按级别和关键字过滤日志、去重、截断超长字段、脱敏（抹掉 token 和内网 IP），保证进入模型的数据控制在几千 token 内。

**3. 计算层**。所有统计由代码完成：构建成功次数、失败用例数、新增/关闭工单数，结果作为结构化字段随数据输出。模型只引用，不复算。

**4. 成文层**。按日报模板分段调用：先让模型对每个数据源写一小节，再合并成全文，约束输出为固定 Markdown 结构（进展 / 风险 / 待办），数字一律取自输入字段。

**5. 投递层**。cron 触发整条链路，产出先写进草稿区并附原始数据链接，人工确认后再推送。失败时单独发告警，避免"静默不出报"。

## 踩坑点

- **时区**：CI 平台返回 UTC，本地按东八区切窗口，第一天就把凌晨任务算丢了。所有时间统一转成带时区的 ISO 字符串再处理。
- **上下文超限**：告警高峰日的原始日志几十万行，必须在清洗层截断并保留 top-N，别指望模型自己扛。
- **格式漂移**：模型偶尔把"待办"写成散文。后来要求先输出 JSON 再渲染 Markdown，格式基本稳住。
- **静默失败**：定时任务挂过一次没人发现。补了失败通知，并加了一条"日报为空也算异常"的检查。
- **脱敏遗漏**：日志里的临时凭证被原样带进模型上下文。清洗层加了正则黑名单，宁可误杀。

## 可复用建议

- 数据与成文分离：工具负责"真"，模型负责"顺"。
- 每个数据源独立成 tool，新增来源不动主流程。
- 原始结构化数据落盘缓存，改 prompt 后可离线重跑成文层，不必重新采集。
- 模板和 prompt 进版本库，改动能 review、能回滚。
- 先用一个数据源跑通全链路，再逐步加，不要一次铺开。

## 总结

日报自动化的关键不在 prompt 多花哨，而在流水线分层：采集、清洗、计算交给代码，模型只做它擅长的归纳与表达，人保留最后一道审核。这套结构稍作调整，就能迁移到周报、值班交接、发布纪要等场景。
