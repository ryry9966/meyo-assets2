## 背景

我们团队用 OpenClaw 跑了不少定时任务：数据同步、爬虫巡检、日志清理，另外还有 agent 运行日志和 MCP 工具调用记录。此前每天早上的日报靠人肉：翻昨天的运行记录、数错误、写几行结论，耗时且口径不统一。于是花了一个周末搭了一条「原始日志 → 结构化日报」的流水线，跑了近一个月，稳定后基本零维护。

## 问题

- 日志分散在多处：agent 运行输出、git 提交记录、MCP 调用记录，格式各异；
- 直接把原始日志丢给模型总结，token 消耗大，且模型经常在数字上出错（成功率、次数算错）；
- 日报格式漂移：谁值班谁写法，无法横向对比。

## 做法

流水线分四段，核心原则是：**LLM 只负责归纳措辞，不负责产出精确数据**。

1. **采集**：一个 collector 脚本（注册成 OpenClaw 的定时任务）读取昨天的日志文件、git log 和 MCP 调用记录，统一输出为事件 JSON：`{source, type, ts, level, summary, metrics, evidence_id}`。
2. **归一化**：统一时区为本地时区、映射日志级别、按 `(type, message哈希)` 去重错误堆栈并保留计数、做敏感信息清洗（token、内网域名打码）。
3. **汇总**：把压缩后的事件 JSON 喂给模型，附带固定 schema，要求输出：整体状态、Top 3 问题（必须引用 evidence_id）、显著变更、次日建议。temperature 设 0。
4. **渲染推送**：Markdown 模板渲染，推送到群 webhook 和邮件，同时归档 JSON。

模型产出的每个结论都能通过 evidence_id 回溯到原始日志，抽查成本很低。

## 踩坑点

- **日期边界**：日志是 UTC 时间戳，「昨天」按本地 00:00 切割。第一版切错边界，漏掉了凌晨的错误，直到有人发现日报和告警对不上。
- **多行堆栈**：按行解析会把异常堆栈撕碎，去重完全失效。改为按记录分隔符解析，多行作为一条事件。
- **上下文超限**：某天故障产生 4 万 token 的事件，直接把汇总打爆。加了按来源的条数上限和截断标记（`truncated: n more`），并按严重度排序决定谁存活。
- **模型编数字**：早期让模型自己算成功率，结果它在没有数据的地方也能「算」出一个数。改为所有计数由归一化层预计算，模型只能引用。
- **流水线静默失败**：最坑的一次——流水线自己挂了三天，没人发现，因为「没收到日报」不触发任何告警。补了一条自监控：09:00 前没有产出报告，就走第二个渠道推送告警。

## 可复用建议

- **中间层 JSON 是核心资产**。换模型、改 prompt、调整模板，都不影响历史数据，后续做趋势分析几乎零成本。
- **渲染层与汇总层解耦**：schema 固定 + 字段校验，模型输出不合法直接重试，不让脏数据进模板。
- **prompt 版本化**：报告末尾带上 prompt 版本号，复盘时能对齐当时的行为。
- **渐进上线**：先跑一个「只有数据表格和标题」的裸版本，稳定一周后再让模型写结论，团队信任度会高很多。

## 总结

这条流水线的价值不在于「AI 写日报」，而在于把结构化提取从模型手里拿走。模型擅长归纳和措辞，不擅长数数。能用确定性代码解决的部分全部用代码，模型只放在最后一公里。全部实现大约 100 行脚本加一个 prompt，之后只在数据源变更时维护。对于已经在用 OpenClaw 定时任务和 MCP 的同学，这套结构可以直接复用。
