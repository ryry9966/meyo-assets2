## 背景

我们团队每天要出一份日报，覆盖服务运行状态、Agent 任务执行情况、异常与告警。数据来源有三处：应用日志、Agent 会话记录、定时任务执行记录。以前靠人翻日志拼报告，一次约 40 分钟，而且口径经常对不上——谁整理的，报告就长谁的样子。

## 问题

最初的做法很偷懒：把原始日志直接丢给 Agent 生成日报。试了一周就放弃：

1. 单日日志几十万行，远超上下文；
2. 模型会“编数字”，错误次数统计和真实值对不上；
3. 输出结构每天漂移，有时少一节，有时格式变；
4. 定时任务静默失败，第二天才发现没报。

## 做法

核心原则一句话：**结构化靠代码，摘要靠模型**。流水线分四层：

1. **采集与预处理**：cron 定时按天拉日志，先本地去重、过滤 debug 级别、剔除健康检查等噪声，只留有价值事件。
2. **结构化**：一段 Python 脚本用规则把每行日志抽成统一 JSON schema：`{time, module, level, event_type, count, extra}`。这步完全不过模型，保证数字准确。
3. **分块摘要**：结构化 JSON 按 module 分块，Agent 用固定 prompt 只负责归纳现象、点出异常模式，被明确禁止改写任何数字。
4. **汇总与校验**：按版本化的 Markdown 模板合并各模块摘要，跑一遍规则校验（各模块错误数之和是否等于总数），通过后推送；失败重试一次，仍失败则发告警。

## 踩坑点

- **时间窗切分**：日志有延迟写入，0 点前几分钟的事件可能落到第二天。加了 10 分钟缓冲，按 watermark 收敛切窗，日报里注明统计窗口。
- **输出格式漂移**：早期 prompt 太自由，模型偶尔自由发挥。改成强制 JSON 输出 + schema 校验，不合法就带错误信息重试，temperature 设 0。
- **幂等性**：同一天重跑必须结果一致。中间产物按“日期+模块”落盘，重跑直接复用，不重复拉原始日志。
- **静默失败**：加了兜底——某天报告缺失，第二天自动补一条“昨日报告生成失败”的占位通知。宁可难看，不可沉默。

## 可复用建议

- 模板和 schema 都带版本号，字段变更走小版本，方便回溯历史日报。
- 统计一律用代码算完再喂进去，Agent 只做归纳与措辞。
- 采集与统计逻辑封装成独立的脚本或 MCP 工具，Agent 按需调用，绝不让它直接翻原始日志文件。
- 保留结构化中间产物，出问题时能快速定位是采集、结构化还是摘要环节的锅。
- 上线初期保留人工 review 一周，口径稳定后再放开。

## 总结

这套流水线把 40 分钟的人工整理压到 3 分钟以内，更重要的收益是口径统一、过程可回溯。经验浓缩成一句：别让模型做它不擅长的事——算数交给代码，归纳才交给 Agent。
