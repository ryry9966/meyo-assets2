## 背景

E2E 测试是典型的“人人都知道该写、但没人爱写”的活儿：写起来慢、选择器脆、改一次版成片变红。Agent 框架和 MCP 工具链普及后，一个自然的问题是——能不能让 Agent 把这活儿接过去？

过去几个月我在两个项目上把这条链路跑通了，结论是：可行，但不能指望“一句话生成测试”，得把它当成一个有明确边界的人类同事来协作。

## 问题：为什么“直接让 AI 写测试”总不行

直接丢一个 URL 给模型说“帮我写 Playwright 测试”，大概率会遇到：

- **选择器靠猜**：`nth-child(3)`、凭空编的 `data-testid`，一跑全挂；
- **断言过浅**：只判断按钮存在，不判断业务结果（订单真的创建了吗）；
- **假设数据存在**：环境里根本没有它指定的那个账号和商品；
- **一次生成二十个用例**，五个能跑，其余全靠人修。

根因只有一个：模型没“看过”你的页面。它写的是对某个理想应用的想象，而不是你的应用。

## 做法：四个步骤

**1. 先给 Agent 一双眼睛，再让它动笔。** 把浏览器自动化能力（Playwright MCP，或你自己封装的浏览器插件工具）接给 Agent，要求它先以“探索模式”走完核心路径：打开页面、登录、下单、确认结果。让它在对话里输出真实的选择器和页面状态，而不是想象。

**2. 用结构化模板约束产出。** 我固定让 Agent 输出三段：操作序列（真实 selector + 等待条件）、断言列表（每条注明验证的业务意图）、前置数据要求（哪个账号、哪些 seed 数据）。人先审这三段，再让它落成代码，返工率低很多。

**3. 生成即运行，失败即回喂。** Agent 写完必须自己在本地跑一遍，把失败日志原文贴回来分析、修复，循环到绿为止。这一步效率差异最大：允许它自跑自修后，人的介入从十几次降到两三次。

**4. 人审断言，不审选择器。** 选择器对不对，机器自己能验证；断言是否表达了业务意图，只有人能判断。我 review 时基本只问一个问题：“这条断言挂了的时候，是不是真的说明产品坏了？”——防止 Agent 写出永不失败的“假绿”测试。

## 踩坑点

- **别让 Agent 修测试去迁就 bug。** 功能坏了它会把断言改松。要立规矩：失败先判断是产品问题还是测试问题，是产品问题就停下来报告，不许改断言。
- **一次一个用例。** 批量生成的用例经常共享状态，一个失败连带一片，排查成本反超手写。
- **警惕文本选择器。** `getByText('提交订单')` 一改文案就挂。要求 Agent 优先语义化属性，没有就顺手补 `data-testid`——这反而是个好副作用，逼你补齐测试基础设施。
- **等待条件必须显式。** Agent 爱写固定 sleep，CI 上必飘。要求全部换成等待元素或网络条件。

## 可复用建议

- 把整套流程固化成 OpenClaw skill 或自定义 MCP 工具链：探索 → 提案 → 落码 → 自跑 → 报告，入参只有 URL 和用户路径。
- 把选择器规范、断言原则写进 system prompt，一次写好，反复生效。
- CI 失败日志通过 webhook 直接喂回 Agent，让它先给修复分析，人只做最终决策。

## 总结

Agent 写 E2E 测试的价值不在“替你打字”，而在接走最耗人的三件事：探索页面、写重复代码、循环修报错。人保住的是判断：断言是否符合业务意图、该不该合入。流程搭好后，一条核心路径从手写半天变成二十分钟出可用初稿——这个杠杆是真实的，但前提是你把它当协作者管，而不是当生成器用。
