# AI 助手的 USER.md：让 Agent 真正了解你是谁

## 背景

用 OpenClaw 这类常驻 Agent 跑一段时间后，你会发现一个不对称：项目侧的上下文——`AGENTS.md`、MCP 工具说明、仓库文档——越攒越全；而你自己的信息：时区、技术栈、沟通习惯、不能踩的红线，全靠模型从对话里"猜"。结果就是每次冷启动，都像给新实习生重新做一遍入职培训。

## 问题

没有 USER.md 时的典型症状：

- 反复确认已知信息：时区、部署环境、用什么包管理器；
- 默认值错位：你在 Linux 上，它给 macOS 路径；你想中文回复，它切回英文；
- 风格不匹配：你要结论，它先铺三屏背景；
- 同一个错误重复犯：上次明明说过"别自动 commit"，这次又来了。

关键区别在于：会话记忆的召回是**概率性**的，落盘文件的注入是**确定性**的。凡是说过两遍以上的偏好，都该变成文件。

## 做法

1. 在 workspace 根目录建 `USER.md`，它会随每轮对话进入上下文。
2. 用固定结构写，控制在 60 行以内：

```markdown
# USER
## 硬性约束（最高优先级）
- 不自动 git commit / push
- 消息发往群组前必须经我确认
## 基本事实
- 时区 Asia/Shanghai；中文回复，术语保留英文
- 环境：Arch Linux，zsh，pnpm
## 沟通偏好
- 先结论后推理，不要客套铺垫
- 出错直接说，不用"建议"包装
## 当前工作（每月更新）
- 主力项目：xxx 网关重构
```

3. 明确分工：`AGENTS.md` 管"这个仓库怎么干活"，`USER.md` 管"跟谁干活"，`MEMORY.md` 管过程性记忆。三者内容重叠是行为混乱的常见根源。
4. 把 workspace 纳入 git，偏好变更留下 diff，随时可回溯。

## 踩坑点

- **写太长**。它每轮都占 token，超过 100 行后注意力被稀释，模型反而抓不住重点。1–2KB 是合理预算。
- **放易变信息**。进行中的任务清单、临时排期放进去很快过期，Agent 会拿着旧状态自作主张——这些归 MEMORY 或任务系统。
- **放敏感信息**。明文 token、内网地址、客户名单不要写。它会进入日志和上下文，泄露面远比直觉大。
- **与系统提示词冲突**。全局配置里说过"简洁回复"，USER.md 又写"详细解释"，行为就会变得随机。一个事实只在一处定义。
- **写完不维护**。过期的偏好比没有偏好更糟。

## 可复用建议

- 把 USER.md 当"给新同事的入职文档"来写：他第一天上班你需要交代什么，就写什么。
- 硬约束放文件最顶部——长上下文中开头位置的权重最稳。
- 养成回写习惯：同一条纠正说到第二次，就写进 USER.md，而不是只留在聊天记录里。
- 团队共用工作助手时，把模板抽出来共享，每人只填事实段，避免格式各自漂移。

## 总结

USER.md 是投入产出比最高的一类配置：十几分钟的写作，换掉的是无数次重复交代和重复犯错。Agent 协作质量的上限取决于模型，下限取决于共享上下文的质量——项目侧你已经做了，"人"这一侧同样值得一份落盘的文档。
