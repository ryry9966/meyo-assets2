## 背景

给 Agent 配定时任务后，一个很快会撞上的事实是：cron 运行和交互对话是两种完全不同的东西。交互时用户在场，Agent 可以追问、可以试错；而 cron 任务是**无人值守运行**——没有上下文、没有人回复、产出直接进渠道（消息、文件、日志）。很多平时用得很好的 prompt，套到 cron 上就翻车，原因往往不在模型，而在 instruction 的写法没切换场景。

## 常见问题

我这段时间观察到的典型翻车：

- 每次运行都发一条"今天没有需要处理的事项"，渠道被无意义输出刷屏；
- 同一件事重复报告，因为 Agent 不记得上次跑过；
- "每天早八点"实际在漂移，因为没写时区；
- instruction 里写"有重要的事就汇报"，结果它认为什么都重要；
- 工具调用失败后 Agent 自己编了个结果，任务静默出错一整周。

共同点：instruction 只写了"要做什么"，没写"什么时候不做"和"出错了怎么办"。

## 我的做法：六段式模板

现在每条 cron instruction 我都按这个骨架写：

1. **角色与边界**：一句话说明这是谁、只负责什么。防止任务范围漂移。
2. **数据来源**：明确用哪个工具/MCP/文件路径获取输入，不写"查一下相关资料"这种模糊表述。
3. **执行步骤**：按顺序列出动作，关键动作写明先读什么状态（比如先读 `state.json`，对比上次已处理的位置）。
4. **输出契约**：格式模板、长度上限、发到哪个渠道。宁可给一个空模板让它填。
5. **中止条件**：最重要的一段。明确写"如果本次没有符合条件的新内容，直接结束，不发任何消息"。这里的条件要可判定，比如"仅报告创建时间晚于上次运行时间戳的条目"。
6. **异常处理**：工具调用失败时重试几次、失败后写日志还是发一次告警，写清楚，不留给它即兴发挥。

写完先**手动触发一次做 dry run**，确认输出格式和渠道都对，再交给调度。

## 踩坑记录

- **默认 Agent 记得上次**：每次 cron 运行都是全新上下文，任何跨运行的状态必须落盘成文件，instruction 里写明读写路径。这是新手坑第一名。
- **静默退出没写死**：哪怕写了"无事可报时可以不发"，模型仍倾向于输出点什么证明自己干活了。要写成硬性规则。
- **prompt rot**：遇到一次漏报就往 instruction 里补一句，三个月后变成谁也不敢删的长文。建议 instruction 单独放一个 markdown 文件，进版本管理，改动走提交。
- **一个任务干多件事**：日报、告警、清理堆在同一条 instruction 里，任何一段出问题都会污染整条任务。一个 cron 只干一件事。

## 可复用建议

- 把 instruction 当**岗位说明书 + 行为契约**写，而不是对话开场白；
- 上线策略：先高频静默运行（只写日志），观察几天确认稳定，再放开通知；
- 每条 instruction 里最值钱的一行，是"什么时候什么都不做"。

## 总结

Cron 的 prompt 工程核心不是让 Agent 更聪明，而是给它一个信息完备、边界清晰、可自我判断是否需要行动的工作契约。把中止条件、状态落盘和异常路径写进 instruction，定时任务才能长期无人值守地跑下去。
