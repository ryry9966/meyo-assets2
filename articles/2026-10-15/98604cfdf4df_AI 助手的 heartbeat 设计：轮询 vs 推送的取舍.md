## 背景

OpenClaw 里的 agent 默认是被动的：用户发消息，事件进来，agent 醒一次，干活，睡回去。但真实使用中总有些事不需要你开口——早报、监控告警、队列里没发出去的草稿。heartbeat 就是给 agent 加一个"自己会醒"的闹钟：每隔 N 分钟注入一条系统消息，让 agent 自检一轮。

于是问题来了：什么时候该靠心跳轮询，什么时候该靠推送？

## 问题

两种唤醒各有代价：

- **轮询（heartbeat）**：实现简单、不依赖公网入口，但每次心跳都是一次完整的模型调用，context 是整条会话——哪怕无事发生，token 照烧。间隔短了烧钱，间隔长了"心跳"变成"年检"。
- **推送（webhook/事件）**：准时、按需触发，理论零浪费，但要求公网可达的入口、鉴权、重试和幂等；而且很多数据源根本没有 webhook，只有"你来查"的接口。

纯推架构在回调丢失时会静默漏事件；纯轮询架构在任务密集时成本失控。这是取舍，不是二选一。

## 做法

我的实践是"推送为主、心跳兜底"的三层结构：

1. **消息类事件走推送。** 聊天渠道本身就有事件回调，不需要心跳参与。
2. **时间确定的任务走 cron。** 早报、定时提醒这类"知道几点干"的事交给 cron job，别让心跳猜。
3. **心跳只做扫尾和兜底。** 心跳 prompt 明确写三件事：检查未投递的队列、检查 cron 是否漏跑、检查有没有挂起待跟进的任务。无事则返回一行简短确认。

配置上：心跳间隔 30 分钟起步，设置 active hours（比如 8:00–23:00），深夜不跑；心跳 prompt 单独写，要求"最小动作"，避免 agent 每次醒来重读全量历史还长篇大论。

## 踩坑点

- **心跳刷屏**：最初版 agent 每次心跳都在群里说"一切正常"。解法是给心跳定义静默模式——无事时返回特定简短标记，由 gateway 丢弃，不进聊天渠道。
- **成本误判**：以为心跳 prompt 短就便宜，结果 context 是整条主会话，单次心跳和普通对话同价。后来把心跳路由到独立会话，只带最小状态摘要。
- **推送与心跳双触发**：webhook 已处理的事件，心跳又扫到一次，重复执行。所有可触发动作都加了幂等键（事件 ID 去重 + 状态标记）。
- **长任务阻塞**：一次心跳触发的抓取任务跑了 8 分钟，下一拍直接跳过。给心跳任务设超时，超时转后台或 cron。
- **兜底失效的错觉**：以为有心跳就不会丢事件，结果心跳自己挂了两天才发现。加了"上次心跳时间"自监控，超时告警推给自己。

## 可复用建议

- 能推送的不要轮询，能 cron 的不要心跳；心跳是安全网，不是主引擎。
- 心跳会话与主会话隔离，携带状态摘要而非全量历史。
- 一切可触发动作幂等：去重键 + 状态位，推送和心跳可以共存而不冲突。
- 记三个指标：心跳次数、实际动作次数、token 消耗。动作/心跳比长期低于 5%，就该拉长间隔或收紧 prompt。
- 心跳本身要可观测——"心跳死了"比"没有心跳"更危险。

## 总结

轮询和推送不是对立选项，而是成本模型不同的两种唤醒方式：推送买准时，心跳买简单和兜底。在 OpenClaw 这种自托管场景里，入口能力参差不齐、外部依赖随时失联，一个便宜、安静、有超时的心跳，往往是整条自动化链路里最不起眼但最保命的一层。
