## 背景

OpenClaw 的 cron 任务，本质是“定时新开会话 + 注入 instruction + agent 自主执行”。它和你在聊天窗口里发的那句话，最大的区别有三点：没有上下文、没人盯着、结果直接进通知渠道。

我把三个长期跑的定时任务（晨报汇总、仓库 issue 巡检、价格监控）的 instruction 重写了一遍之后，误报率和 token 消耗都降了一个量级。这里把方法沉淀一下。

## 问题：cron instruction 的四种典型死法

1. **当聊天 prompt 写**。“帮我看看有没有新 issue”，“看看”是什么动作？“新”以什么时间为界？agent 只能猜，而且每次猜得还不一样。
2. **假设它记得上一次**。cron 每次都是全新会话，“和昨天对比一下”在它听来是凭空的。
3. **没有输出约束**。结果格式随机，有时一句话有时一大篇，通知渠道很快被刷屏。
4. **没有边界**。工具一报错就开始自由发挥、连环重试，单次任务烧掉平时十倍的 token。

## 做法：六段式 instruction 模板

我现在的写法固定成六段，直接填在 cron 任务的 instruction 字段里：

1. **场景声明**：一句话说明“这是定时任务，当前时间 {now}，时区 Asia/Shanghai”。时间必须显式注入，别让它自己算。
2. **目标**：只有一个。一个 cron 任务只做一件事，想做两件就拆成两个任务。
3. **数据源与工具**：写明用哪个插件取数、时间窗口多大。例如“调用 github 插件，查询过去 24 小时内 label 为 bug 的 open issue”。
4. **判断标准**：把“看看有没有异常”翻译成可执行的布尔条件。模糊描述是 cron 任务最大的敌人。
5. **输出契约**：固定模板，比如三行以内、包含结论/依据/建议；并写明“仅当满足条件 X 时发送消息，否则本次静默结束”。
6. **边界与异常**：最多调用几次工具、失败不重试只记录、禁做写入类操作。无人值守的任务，约束比能力重要。

## 踩坑点

- **时区错位**：cron 表达式按系统时区跑，instruction 里又写“今天”，两边理解不一致就会错峰。时区和“今天”的定义都要在 instruction 里显式声明。
- **插件未启用**：cron 执行上下文里插件的可用性要单独确认。引用了一个没启用的工具，任务会稳定失败且无人发现，上线前务必手动触发一次。
- **幂等缺失**：10 分钟一次的监控任务，必须写清“如何判断这条告警已经发过”，否则同一个问题会反复轰炸通知渠道。
- **静默不等于失败**：建议在输出里带一行执行摘要（做了什么、耗时/token），发到日志渠道而非通知渠道，方便事后回溯。

## 可复用建议

- 把六段式做成模板，新任务从模板复制，不要每次从零写。
- instruction 里加版本号（如 v1.3），改过什么有据可查。
- 新任务先按低频（每天一次）灰度跑三天，看日志再提频。
- 输出保持结构化，方便统计误报率——它是评价 cron instruction 唯一诚实的指标。

## 总结

Cron 任务的 instruction 不是一条 prompt，而是一份写给“没有记忆、没人监督的新员工”的交接文档：目标单一、数据源明确、判断可执行、输出有契约、边界写死，任务才能长期稳定地无人值守。你写得越像文档，它跑得越像服务。
