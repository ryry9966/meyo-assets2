## 背景

对 OpenClaw 用户来说，本地跑模型的价值不在“替代云端”，而在三件具体的事：隐私敏感的自动化流程不想把数据交给第三方 API；家里那台闲置显卡可以 24 小时挂一个随时可用的 Agent 后端；以及给 API 账单做个兜底。这篇帖记录我在一台 16GB 显存的主机上部署本地模型并接入 OpenClaw 的完整过程。

## 问题

先说一个反直觉的判断：**Agent 负载比聊天难得多**。聊天场景 2K 上下文就够，但 Agent 一轮要塞进系统提示、工具定义、历史消息和工具返回结果，上下文轻松破 8K。很多人第一次跑本地模型“感觉还行”，一接上 Agent 就崩，崩因通常是三个：上下文被静默截断、工具调用格式不稳、显存被 KV cache 吃爆。

## 做法

1. **先摸清硬件边界**。经验值：8GB 显存跑 7-8B 的 Q4 量化；16GB 跑 14B Q4 或 8B Q6；24GB 可以碰 32B Q4。Mac 统一内存另算，32GB 能跑 14B 左右。低于 Q4 的量化不建议用于 Agent——工具调用的 JSON 输出会明显劣化。
2. **推理引擎选型**：不想折腾用 Ollama；要精细控制上下文和量化用 llama.cpp；Linux + 大显存追求吞吐上 vLLM。我用 Ollama 起服务，够用。
3. **两个必改参数**：`num_ctx` 至少拉到 8192（默认值对 Agent 太小）；GPU offload 层数按显存上限调，用 `nvidia-smi` 盯着，宁可少放几层也别溢出到内存。
4. **接入 OpenClaw** 走 OpenAI 兼容端点（Ollama 是 `http://127.0.0.1:11434/v1`），模型名填本地 tag。建议给本地模型单独建一个 provider 配置，方便和云端随时切换。
5. **用真实任务验收**：准备 3-5 个日常真实会跑的 Agent 任务（比如“读文件 → 调 MCP 工具 → 写结果”），对比 Q4/Q6 两个量化的表现，而不是拿“你好”测。

## 踩坑点

- **静默截断**：Ollama 默认 2K/4K 上下文不报错，只悄悄丢内容，症状是 Agent “忘了”前面定义的工具。改 `num_ctx` 后消失。
- **KV cache 显存常被低估**：8B 模型 + 16K 上下文，KV cache 能吃掉 2-4GB。容量规划公式是：显存 = 权重 + KV cache + 余量。
- **不是所有模型都会好好输出工具 JSON**。挑官方声明支持 function calling 的模型（Qwen 系列、Llama 3.1+ 这类），别拿纯基座模型硬上。
- **生成速度卡显存带宽而不是算力**。部分 offload 时 token 速度断崖式下跌，实测低于 10 tok/s 的 Agent 体验基本不可用。
- **别追求“全本地”**。复杂推理该走 API 就走 API，本地模型干隐私敏感和轻量重复的活。

## 可复用建议

- **分层路由**：按任务类型分流——敏感数据、格式化输出、简单摘要走本地；规划和多步推理走云端。
- 把验收用的 3-5 个任务**脚本化**，每次换模型或量化跑一遍，十分钟出结论。
- **固定模型版本号**，量化文件与配置一起存档，避免“上次好好的这次不行”。
- 记录每个配置的 tok/s 和显存峰值，一张表胜过记忆。

## 总结

本地部署本质上是一次容量规划工程，而不是玄学调参。把它当成给 Agent 链路加一个“本地档位”，而不是云端平替，预期就对了。8B Q4 + 8K 上下文是一个务实的起点，跑顺了再往上加。
