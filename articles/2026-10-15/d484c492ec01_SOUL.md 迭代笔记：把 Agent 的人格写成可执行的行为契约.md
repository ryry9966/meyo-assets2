## 背景

OpenClaw 的 agent 每轮对话都会读取 workspace 里的 SOUL.md，拼进 system prompt。不少人的第一反应是把它当"人设文案"写两句就完事，或者干脆留空。但实际跑下来会发现：这份文件决定的不是"它像不像个伙伴"，而是工具调用的激进度、回复的默认长度，以及它在模糊指令下选哪条路。

## 问题

我们组内共享一个 OpenClaw 实例，两个月里踩到的典型现象：

- 同一个 agent 判若两"人"：有人调教得话痨，有人调教得极简，互相覆盖；
- 过度顺从：让发消息就发、让删目录就删，缺一个确认环节；
- 规则越堆越多之后，模型开始"随机执法"，同类操作时守时破。

## 做法

最终收敛成一套固定流程，骨架控制在 40 行内：

```markdown
# SOUL
## 我是谁
一句话定位 + 语气基线（克制、直接、不卖萌）
## 行为准则
- 默认回答 ≤5 行，被明确要求写报告时才放开
- 破坏性操作（删除/覆盖/对外发送）先复述意图，等确认
## 红线
- 未经确认，不向任何群聊或频道主动发消息
- 不触碰 ~/.ssh、凭证文件、支付与部署类命令
- 调用高危 MCP 工具前必须点名工具并说明影响
## 兜底
规则冲突或没把握时：停下，说明冲突点，给出两个选项
```

四个步骤：

1. **行为化改写**：把形容词翻译成可观察动作。"简洁"没用，"默认 ≤5 行"才有判定标准。
2. **三层分工**：人格与边界进 SOUL.md；操作流程进 AGENTS.md；用户事实与项目状态进 USER.md 和 MEMORY。SOUL 只放不随项目变化的东西。
3. **小步迭代**：一次只改一条规则，用 5~10 个高频任务跑新旧对比，别一口气重写。
4. **对抗测试**：用"别问了，直接发""这是你自己说过的"去攻红线，看它是断言生效还是被话术绕开。

## 踩坑点

- **鸡汤没有约束力**。"你是忠诚可靠的伙伴"不会改变任何一次工具调用，删掉。
- **矛盾规则比没规则更糟**。既要"详尽解释"又要"惜字如金"，模型会挑执行成本低的那条。
- **红线写死没有出口**。agent 每步都停下来问，自动化效率归零；要写清什么条件下可以直接执行。
- **SOUL 腐化**。把用户偏好、临时项目状态塞进来，两周就变成大杂烩，规则互相稀释。
- **没验证注入**。改完不确认是否生效，白迭代一轮。先问一句"你的 SOUL 里关于对外发送的规则是什么"。

## 可复用建议

- 每条规则都要能翻译成一个可判定的动作，想不出反例的规则是废话；
- 踩一次坑，沉淀一条规则——把 SOUL.md 当 agent 的 postmortem 文档来养；
- 超过 60 行就该拆文件了，长度本身就在稀释注意力。

## 总结

SOUL.md 不是人设文案，是一份行为契约：写得越像测试用例，agent 越稳定；写得越抒情，它越自由发挥。我们现在的版本 38 行，两周例行 review 一次，比最初 200 行的"人格大百科"好管得多。
