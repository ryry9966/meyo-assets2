## 背景

过去几个月我用 OpenClaw 承担了不少重复性工作：批量代码审查、多仓库依赖梳理、定时情报汇总。单 agent 模式跑了一段时间后，两个问题越来越明显：一是上下文被塞满后，工具调用质量明显下滑，模型开始"忘事"；二是所有任务严格串行，一个要跑十分钟的分析会阻塞后面所有排队的活。

## 问题

具体拆开是三件事：

1. **上下文污染**：长任务把对话历史撑爆，早期的关键约束被挤出窗口。
2. **串行瓶颈**：任务之间明明没有依赖，却只能排队等。
3. **故障传导**：一个任务的异常输出混进上下文，影响后续所有判断。

## 做法

我的编排方式可以概括为 fan-out / fan-in：

**第一步，划定子任务边界。** 只把"读多写少、彼此独立、结果可结构化"的任务下放给 subagent。比如审查 8 个模块，就拆成 8 个子任务，每个只看自己的模块。

**第二步，写任务契约。** 每个 subagent 的 prompt 必须自包含：目标、输入路径、产出格式、禁止事项。子 agent 看不到父会话历史，别指望它"接上文"。

**第三步，控制并发。** 并发从 2~3 起步，观察限流和成本再往上调。父 agent 维护一张简单的任务表，记录每个子任务的状态。

**第四步，结构化回传。** 要求每个子 agent 返回固定格式的摘要（结论 + 证据文件路径 + 置信度），长度限制在几百字内。父 agent 只读摘要，需要细节再按路径去取。

**第五步，失败兜底。** 每个子任务设超时；失败重试一次，仍失败就标记跳过，不让单个子任务拖垮整批。产物要做存在性校验，防止"嘴上说完成"。

## 踩坑点

- **共享工作区冲突**：多个子 agent 同时写同一个 git 工作树，几乎必出冲突。解法是要么写操作串行化，要么各用独立分支/目录，最后统一合并。
- **汇总爆炸**：10 个子 agent 各回传 2000 字，父 agent 的上下文照样爆。回传必须限长，细节落盘到文件。
- **静默失败**：子 agent 返回"已完成"但产物不存在或为空。回传格式里强制带产物路径，由父 agent 校验。
- **成本翻倍**：并行意味着 token 消耗同步翻倍。跑批前先估算，给单批任务设预算上限。
- **拆分过细**：把一个内聚任务拆成十几个微任务，编排开销反而超过收益。两三个内聚块好过十个碎片。

## 可复用建议

- 先写任务契约，再写编排逻辑；契约说不清就不要下放。
- 用文件（而非对话）作为子 agent 之间的交接介质，天然幂等、可重放。
- 并发数保守起步，压测后再加。
- 全程留日志：每个子任务的起止时间、token 消耗、产物路径，复盘时能快速定位哪个环节拖后腿。
- cron 触发的定时批量任务是最适合先落地的场景：失败成本低、结果可核对，适合用来验证整套编排。

## 总结

Subagent 编排解决的不是"模型不够聪明"，而是工程上的三件事：上下文隔离、并行吞吐、故障隔离。它有明确的适用边界——独立、可结构化、可校验的任务才值得下放。我的经验是：先从一个小场景（比如批量审查）跑通全链路，把契约、回传、兜底固化成模板，再逐步推广到其他自动化流程。并行不是目的，可控地提速才是。
