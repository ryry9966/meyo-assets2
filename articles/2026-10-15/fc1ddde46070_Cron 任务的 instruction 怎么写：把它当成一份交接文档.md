# 背景

OpenClaw 的 cron 任务本质上是“到点执行一段 instruction"。很多人把 instruction 写得像平时聊天——“帮我看看今天的日程，有重要的就提醒我”。手动在会话里这么说没问题，因为 agent 有上下文、能追问。但 cron 触发时是一次无人值守的运行：没有你上一句话的语境，也没有机会澄清。写不好，轻则输出格式每次都飘，重则任务静默失败。

# 问题

我自己踩过的三类典型问题：

1. **上下文缺失**：instruction 里写“继续昨天那件事”，但 cron 运行时根本没有“昨天”。
2. **输出无主**：没写结果发到哪，agent 自己挑了个默认渠道，或者只在日志里嘟囔一句。
3. **条件逻辑过多**：写了大量“如果 A 就 X，否则 Y"，实际执行时 agent 跳过分支，只做了主线。

# 做法：按交接文档的结构写

我的模板分六段，按需裁剪：

```text
【目标】一句话说明这次任务要产出什么
【数据来源】允许用哪些工具/文件/API（含 MCP 工具），禁止臆造
【步骤】3-5 步以内，线性执行，不写嵌套条件
【输出】格式（列表/表格/篇幅）+ 投递渠道（发给谁/写到哪个文件）
【异常】数据拿不到、工具失败时：降级还是跳过
【静默规则】没有值得报告的内容时，不发消息，只写日志
```

一个真实例子（每日摘要任务）：

```text
【目标】汇总过去 24 小时 ~/inbox/ 下新增的 md 文件
【数据来源】只读本地 ~/inbox/，不要联网
【步骤】1) 列出 24h 内修改的文件；2) 每个文件提取一句话摘要；3) 按修改时间排序
【输出】Markdown 列表，投递到 Telegram 的"日报"会话
【异常】目录为空则不发消息
【静默规则】文件数超过 20 时，只报总数和前 10 条
```

# 踩坑点

- **时区**：服务器多为 UTC，“每天早上 8 点”先确认 cron 表达式的时区基准，或在 instruction 里写死日期计算口径。
- **高频 + 重工具**：每 15 分钟跑一次带浏览器抓取的任务，很快遇到限流和成本问题。重任务降到小时级，或改成事件触发。
- **让 agent“自行判断”**：凡是没写死的判断标准，每次执行结果都可能不同。“重要的提醒我”不如“deadline 在 48 小时内的事项必须提醒”。
- **改一处重写全篇**：每次微调都把 instruction 整段重写，容易引入回归。建议只改对应段落。

# 可复用建议

1. **先手动后定时**：把 instruction 直接发给 agent 跑一遍，确认输出符合预期，再挂上 cron。
2. **一个任务一件事**：复杂的晨报拆成“取数、汇总、投递”三个任务，各自可单独验证、单独重跑。
3. **落盘优先于通知**：结果先写文件再发消息，方便回溯和排障。
4. **instruction 进 git**：定时任务的 prompt 和代码一样需要版本管理，改坏了能回滚、能 diff。
5. **必加静默规则**：几乎所有定时任务的噪音，都来自“没事也报平安”。

# 总结

Cron 任务的 instruction 不是聊天，而是一份写给未来某个无人值守时刻的交接文档。把目标、来源、步骤、输出、异常、静默规则写清楚，任务成功率会从“看运气”变成“可预期”。核心原则只有一条：**假设执行那一刻没有任何上下文，然后把所有必要信息写进 instruction 里。**
