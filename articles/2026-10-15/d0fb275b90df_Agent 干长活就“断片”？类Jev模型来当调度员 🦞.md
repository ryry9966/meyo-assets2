Agent 的演示视频里个个身手矫健：订机票、写报告、跑数据分析一气呵成。可一到真实的长任务，几十步工具调用、跨天推进的项目，它们就开始“金鱼化”：忘记初始约束、重复踩坑、第四十步悄悄跑偏。36kr 近日报道了国产开源的“类Jev模型”，打法很明确：让一个专职模型接管 Agent 的调度。这篇拆三件事：失忆的病根在哪、调度模型的药理是什么、哪些冷水值得提前泼。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/4586eda7199c0673.png)

## 一、病灶：失忆不是玄学，是结构性缺陷

- **上下文窗口 ≠ 有效记忆**。2023 年斯坦福的 "Lost in the Middle" 研究发现，LLM 对长文本的注意力呈 U 形：开头和结尾记得牢，中间大段信息像被静音。塞 100 页文档，第 50 页的关键约束它就是看不见。
- **标称 128K，好用可能只有 32K**。RULER 这类长上下文基准反复验证：不少模型在远小于标称长度的位置就开始掉点。“能塞进去”和“用得动”是两回事。
- **错误是按复利算的**。假设单步工具调用成功率 95%，50 步任务的端到端成功率只有 0.95^50 ≈ 7.7%。长任务比拼的不是“每步都准”，而是“别让小错误滚雪球”。
- **成本也不友好**。attention 对序列长度是平方级开销，KV cache 随对话线性膨胀。让主力大模型全程在线盯梢，又贵，又容易注意力涣散。

典型场景：让 Agent 从零搭一个数据看板，第 5 步定下“SQL 只能查只读库”，到第 30 步这条约束早已在长上下文里被稀释——不是模型蠢，是信息浓度掉了。

## 二、老药方为什么不够：RAG 是“记性好”，不是“会记账”

- **RAG / 向量记忆**解决“存”和“取”，但更难的问题是“何时该存什么、何时该忘什么”。检索是被动等 query，调度是主动管流程。
- **MemGPT 式分页记忆**思路接近操作系统虚拟内存，把历史压到外存按需换入。可“何时换页”这个决策本身还得靠 LLM 自己判断，让失忆的病人自己管吃药时间，逻辑上就别扭。
- **纯堆长上下文**：窗口越长越贵，注意力越稀；让模型边干活边自我总结，总结质量还会随位置衰减。
- 历史也报过警：2023 年 AutoGPT 火过一轮，大量项目烂尾，复盘时最高频的抱怨正是“跑着跑着忘了目标”。

一句话总结：**记忆是存储问题，调度是决策问题**。缺的是一个不亲自干活、只负责管事的稳定控制器。

## 三、类Jev模型的药理：把“调度”从大模型手里拿走

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/7e035f6bc866ed16.png)

从报道的架构描述看，这类模型走的是 JEPA（联合嵌入预测架构）一脉的思路：不逐字生成文本，而是学习“任务状态如何演化”，在紧凑的表示空间里做预测和决策。落到 Agent 场景，它干四件事：

1. **状态追踪**：把几十步的任务维护成一张紧凑任务图（已完成/进行中/阻塞），每步只把相关片段喂给执行 Agent，上下文恒定在几 K token。
2. **记忆压缩裁决**：什么升级为长期记忆、什么降级成摘要、什么直接丢弃，由它统一拍板。龙虾蜕壳前会把旧壳里的有用物质回收一遍，Agent 的记忆也该这么管。
3. **子任务派发**：决定下一步派哪个子 Agent、带哪些工具、给多少预算，像调车场里扳道岔的调度员，让每列车只拉属于自己的货。
4. **止损与回滚**：检测到 Agent 原地打转（连续相似动作、指标不收敛），强制回滚到最近 checkpoint 换路径。

为什么用小模型干这个？三个工程理由：

- **便宜且高频**：调度是每步都要调用的环节，用大模型等于每步交一次“管理费”，预算会烧穿；小模型可以铺在每一个决策点上。
- **窄域可靠**：只做状态判断和路由，微调数据可以构造得很干净，行为远比通用大模型稳定。
- **可本地部署**：开源权重意味着调度层不依赖外部 API，延迟和隐私都可控。

本质是**分工而非换模型**：执行层继续用最强的大模型，控制层交给专职、便宜、稳定的小模型——就像操作系统里内核调度器管进程，而不是让每个进程自己抢 CPU。

## 四、训练与验证：过程奖励比结果奖励更对症

长任务训练的经典难点是奖励稀疏：跑满 50 步才知道成败，信号像沙漠里找水。类Jev 这类调度模型的常见组合拳：

- 先从成功轨迹做模仿学习打底；
- 再用**过程奖励模型**（Process Reward Model）对每一步的状态判断打分，而非只看最终结果。OpenAI 2023 年的 "Let's Verify Step by Step" 已在数学推理上验证：过程监督显著优于结果监督；
- 评测重点看两个指标是否**同时**改善：端到端完成率 + token 成本。只涨完成率但 token 翻倍，属于伪进步。

报道称在长程规划、多步工具调用类任务上“完成率与开销同步改善”。具体数字建议等论文和第三方基准复现，别急着信发布会口径。

## 五、冷水与建议：三件事值得记下

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/a9e836ef3528eaf2.png)

1. **先加“步数预算 + checkpoint”，再谈换架构**。很多所谓失忆，本质是无上限循环加无状态快照。给每个子任务设最大步数，每 N 步强制把状态摘要落盘，一周就能救活一半跑不完的 Agent，成本接近零。
2. **用复利视角做评估**。单步成功率从 95% 提到 97%，50 步任务的端到端成功率就从 7.7% 涨到约 22%——调度器的价值，就是把“每步可靠性”提上去、把“无效步数”压下来，两头一起动。
3. **专职调度不是银弹**。它缩小了出错面，但调度模型自身的状态预测偏差同样会在长程累积；各家接口也未必互通，可能重演 Agent 框架混战。稳妥姿势是影子模式：让调度模型在旁路并行跑，与现有主流程对拍一周，数据说话再切换。

Agent 的进化路径越来越像软件工程本身：不是造一个全知全能的大脑，而是先造一个不犯低级错误的内核。把流程交给专职的，把聪明留给干活的，这条分工铁律，操作系统验证过四十年，现在轮到 Agent 补课了。
