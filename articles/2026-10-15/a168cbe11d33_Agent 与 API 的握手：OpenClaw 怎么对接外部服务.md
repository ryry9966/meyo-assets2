## 背景

Agent 本身只会"想"，真正落地靠的是它能调到的工具。在 OpenClaw 里，无论是 MCP server 还是插件暴露的 function，本质都是同一件事：把一个 HTTP API 翻译成模型能理解的工具描述。所以"对接外部服务"的难点从来不是调通一次请求，而是让 Agent 在真实任务里**稳定、安全、可回溯地反复调用**。这篇帖记录我们内部对接几个第三方 API 时的做法和代价。

## 问题：三类典型翻车

1. **凭据进上下文**。API key 被写进系统提示，或者工具返回值里带着敏感字段，最后散落在会话日志的各个角落。
2. **工具描述模糊**。模型不知道什么时候该调、参数怎么填，开始瞎猜参数，越猜越偏。
3. **错误处理缺位**。上游返回 429/500，工具把原始报错直接抛给模型，模型基于错误信息开始自由发挥。

## 做法：六步握手

1. **先划边界再写代码**。列出服务提供的全部操作，一个工具只做一件事，读写分离。清单之外的不暴露。
2. **写薄封装层**。工具内部不写业务逻辑，只做五件事：参数校验、认证注入、超时控制、重试、错误归一化。
3. **认证走环境变量或密钥管理**，工具运行时读取，返回值统一脱敏，不透传任何 header。
4. **错误信息写给模型看**。把 HTTP 错误翻译成可行动的描述，比如"速率受限，建议 60 秒后重试"，而不是甩一段 stack trace 让模型猜。
5. **先只读后写入**。用 dry-run 和只读模式跑通主流程，确认工具行为符合预期，再放开写操作。
6. **观测要留痕**。记录每次调用的工具名、参数摘要、耗时、结果状态，但不落完整 payload。

## 踩坑点

- **optional 参数别多给**。schema 里可选项一多，模型每次都热情地填一堆没用的，token 翻倍还容易触发误操作。
- **分页接口模型不会自己翻**。要么在工具内聚合并限制条数，要么显式提供 page 参数并在描述里写清语义。
- **写操作必须幂等**。模型侧的重试策略不可控，没有幂等键就是等着数据翻倍。
- **超时要自己管**。工具层超时设得比上游 P99 略长即可，不要无限等待，更不要依赖模型"自己意识到卡了"。
- **工具数量要克制**。单个 MCP server 挂几十个工具后，选错工具的概率明显上升，按业务场景拆分比堆在一起好。

## 可复用建议

- 沉淀一个内部的"API → 工具"适配模板，固定包含校验、超时、重试、错误归一化、脱敏五个槽位，新服务接入只填空。
- 上线前准备一组固定评测用例：正常路径、边界值、错误路径各几条，跑通再放开。
- 工具返回值要结构化且精简，长文本给摘要加引用，别把 50KB 的 JSON 原样灌进上下文——那是所有幻觉的温床。

## 总结

对接外部服务，本质是给 API 写一个**面向模型的客户端**：认证、错误、边界情况都在工具层消化掉，让模型面对的永远是干净、语义明确的接口。握手协议定清楚了，Agent 才不会在真实任务里掉链子。有问题欢迎在评论区交流具体场景。
