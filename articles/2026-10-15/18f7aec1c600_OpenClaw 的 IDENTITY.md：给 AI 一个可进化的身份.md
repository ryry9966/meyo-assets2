# 背景

OpenClaw 不是“每次请求从零开始”的 API，而是跑在自己机器上的常驻 agent：常驻进程、接入 IM、有记忆、会主动干活。它的工作区里有一组 Markdown 文件充当“操作系统”：`AGENTS.md` 管行为规范，`SOUL.md` 管性格与价值观，而 `IDENTITY.md` 管“我是谁”——名字、形象、emoji、语气、头像。

多数教程对这个文件一笔带过：填个名字就完事。但跑了一段时间后我发现，它的维护质量直接决定 agent 在长期使用中的稳定性。

# 问题

两种常见失败模式：

1. **空白式**：只写名字和 emoji。结果多渠道表现不一致——Telegram 里自称 A，CLI 里自称“助手”，语气随模型当天的心情漂移，用户搞不清在和谁说话。
2. **小说式**：塞几百字人设。agent 每次自我介绍都复读台词，还挤占上下文里任务指令和工具调用的注意力。

本质问题：身份没有结构、没有版本、没有反馈闭环，改人设全凭手感。

# 做法

我的分工原则：价值观和边界放 `SOUL.md`，`IDENTITY.md` 只保留“可感知的外壳”，控制在 15 行以内：

```markdown
- **Name:** 小钳
- **Creature:** 机械寄居蟹
- **Emoji:** 🦀
- **Vibe:** 简短直接，先给结论；没把握就明说，不编造；被纠正后复述一次确认
- **Avatar:** avatars/claw.png
```

几个要点：

- **vibe 写可观察的行为**，不写形容词堆砌。“幽默风趣”没用，“开头不寒暄、结尾不复读”才有用。
- **版本化**：workspace 整个进 git，每次改 IDENTITY 单独 commit，message 写清楚“哪个场景翻车了”。
- **进化闭环**：每两周复盘一次对话记录，把重复出现的吐槽（太啰嗦、太卑微、称呼不对）转成一行 vibe 修改，小步提交。先在测试渠道跑两天，再推到主渠道。
- **回归验收**：准备一组固定问题（“你是谁”“怎么称呼我”“没把握的事怎么办”），每次改动前后各问一遍，对比输出是否漂移。

# 踩坑点

- **跨文件冲突**：IDENTITY 写“爱开玩笑”，AGENTS 写“严格事实”，agent 会在中间摇摆。规则口径必须一致，别赌模型的自行仲裁。
- **Avatar 路径失效**：文件挪位置后部分渠道静默回落默认图，很难第一时间发现，改动后记得在各渠道各发一条消息确认。
- **拿旧会话测试**：改完文件，旧会话不会自动刷新。务必新开会话验证，否则会误判“没生效”。
- **大改人设**：频繁重写会让老用户明显感到“换人了”。进化要小步，一次改一两条。

# 可复用建议

- 把 IDENTITY.md 当**产品 UI 文案**维护，不当角色扮演小说。
- 每条 vibe 必须能映射到一个可验证的行为，映射不出来就删。
- git commit message 就是身份的 changelog，不必在文件里再堆历史。
- 身份回归问题清单 + 每次改动走 diff 评审，和个人代码库同等待遇。

# 总结

IDENTITY.md 的价值不在“给人设”，而在把散落各处的隐性约定，收敛成一个可 diff、可回滚、可评审的文件。配合 git 和定期复盘，agent 的性格就能像代码一样小步迭代——用久了它会像一个磨合过的同事，而不是每次都在换人的客服。
