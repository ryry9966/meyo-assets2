## 背景

OpenClaw 的工作区里有一组约定文件：AGENTS.md 管行为规范，SOUL.md 管价值观和语气，USER.md 记录用户偏好，而 IDENTITY.md 回答的是一个更基本的问题——"我是谁"。文件里通常只有几行：名字、形象设定（creature/vibe）、emoji、头像路径。很多新人把它当成装饰，填完就忘。

用了一段时间后，我的看法变了：IDENTITY.md 不是人设玩具，而是一个**每次会话都会注入 system prompt 的配置项**。它便宜、高频、影响面大，值得像代码一样对待。

## 问题

没有认真维护 IDENTITY.md 的环境，通常会遇到三类麻烦：

1. **行为漂移。** 换模型、升级版本、清空会话之后，语气和称呼方式变来变去，日常使用感知很明显。
2. **多 agent 混淆。** 一个实例跑自动化，另一个跑日常对话，两个都叫"助手"，日志和群聊里分不清谁干的。
3. **身份知识散落。** 真正起作用的"人格"藏在某次调试时改过的 prompt 片段里，没有沉淀，人走了就丢。

## 做法

我的实践是把它当成一份小型的、可版本化的接口文档：

**第一步：写一个最小版本。** 名字、形象、emoji、头像，再加 3-5 条可观察的行为特征。注意写行为而不是形容词——"收到模糊指令时先复述再执行"，比"严谨"有用得多。

**第二步：和 SOUL.md 划清边界。** IDENTITY.md 回答"我是谁"，SOUL.md 回答"我相信什么"。同一条规则不要出现在两个文件里，否则模型在冲突时随机站队，表现不稳定。

**第三步：纳入 git 管理。** 每次调整都提交，附一句改动动机；改名、改语气基线这类重大变更单独 commit，方便回溯和回滚。

**第四步：定期验证。** 开一个全新会话，问它"你是谁、做事边界是什么"，对照文件检查是否生效；再用几个边界 case（模糊指令、越权请求）跑一遍，确认特征不是摆设。

## 踩坑点

- **写太长。** 见过 60 多行的版本，每条都在争抢注意力，结果哪条都没被执行。10 行以内足够。
- **和 AGENTS.md 冲突。** 比如身份里写"永远先道歉"，行为规范里写"不做无意义道歉"，模型会摇摆。冲突规则宁可删掉。
- **过度人格化。** 人设太强，agent 会开始"出戏"式拒答："这不符合我的性格"。工作型 agent 的身份应该服务于任务，而不是反过来。
- **改了不记。** 换名字或形象不写说明，团队其他人的脚本和习惯全被打乱。

## 可复用建议

- 特征统一写成"输入 → 行为"的格式，天然可测试。
- 给每个 agent 一行"绝不做什么"，比十行"应该做什么"更有约束力。
- 身份变更走 PR review——哪怕团队只有你一个人，一个月后的你就是别人。
- 记忆文件会随时间累积，定期检查是否有和当前身份矛盾的旧条目。

## 总结

IDENTITY.md 的价值不在于让 agent 可爱，而在于把"这个 agent 应该怎么表现"从口头约定，变成一份被每次会话读取、被 git 追踪、可验证的配置。**身份即接口，接口就该演进。** 今天花十分钟写好它，省掉的是之后无数次"它怎么又变了"的排障时间。
