最近 36kr 报道了一条让不少工程师坐直了的消息：Anthropic 内部 7 名工程师，花了 5 个月，造出了一个 Git 的替代品。评论区迅速分成两派——一派惊呼“连 Anthropic 都受不了 Git 了”，另一派嘲讽“又一家大厂瞎造轮子”。把情绪摘掉，这条新闻其实串起两个更值得聊的问题：一是服役二十年的 Git，为什么在 AI 大规模写代码的时代开始吃力；二是“7 个人、5 个月”这组数字本身——基础设施工程的成本结构，正在被 AI 改写。下面把两条线都捋清楚。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/31304f25cc39a4e1.png)

## Git 的二十岁：它当年为什么是革命

- 2005 年，Linus Torvalds 因为 BitKeeper 的授权纠纷，几天之内写出 Git 第一版，目标非常单纯：管好 Linux 内核的源码。
- 三个核心设计至今仍是它的骨架：
  1. **内容寻址对象库**：文件内容、目录、提交全部按哈希存储，天然防篡改、内容去重；
  2. **快照而非补丁**：每个 commit 记录整棵目录树的快照，分支因此只是一个可移动的指针，创建成本趋近于零；
  3. **分布式**：每人本地都有完整仓库与完整历史，离线也能提交，服务器只负责交换对象。
- 在 2005 年的假设下，这套设计近乎完美：代码由人手写，一人一天提交几次；几十万行就算大项目；历史以“年”为单位缓慢增长。
- 二十年过去，工作负载翻了几百倍，但架构骨架没法换——这正是故事的起点。

## AI 写代码之后，Git 撞上三道性能悬崖

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/5cffdc3f5707402c.png)

- **提交频率从“人速”变“机速”**。人类工程师一天几个 commit；AI agent 一个会话就能产出几十上百个 commit，还会开大量分支做实验再丢弃。分支与标签引用（refs）爆炸后，引用查找、垃圾回收（GC）都开始变慢。
- **仓库体积拖慢日常操作**。Git 的本地性是用“完整历史”换来的：clone 要拉全量。仓库变大后，新成员入职等半天，`git status`、`git log` 在百万级文件的 monorepo 里明显卡顿。
- **快照模型的维护成本**。快照靠 packfile 压缩和周期性 GC 维持体面，仓库越大，GC 停顿与 merge-base 计算越昂贵。
- Anthropic 是放大版受害者：monorepo、海量 Claude 生成的代码、大量 agent 并行工作流，让 Git 的痛点从“偶尔卡”变成“每天疼”。
- 历史上这不是头一回。Google 2016 年发表论文介绍自研的 Piper，管理数十亿行代码、每天数万次提交；Meta 把 Mercurial 改造成 Sapling，2022 年开源；微软 2017 年为 Windows 巨型仓库做了 VFS for Git。规律很一致：规模一旦越过 Git 的设计假设，大厂就会动手。Anthropic 特殊的从来不是“做了”，而是“多少人、多久做完”。

## 7 个人、5 个月，才是这条新闻真正的爆点

- 对照历史：Piper 和 Sapling 都是专职基础设施团队以“年”为单位的工程。为什么 Anthropic 能压缩到 7 人 5 个月？拆开看有三个原因：
  1. **最难的 20% 已被前人铺路**。内容寻址存储、提交 DAG、写时复制这些核心机制在学术界与开源界早已成熟（Sapling、Jujutsu 都已开源），知道路怎么走之后，剩下的主要是工程执行；
  2. **AI 把“写代码”环节的成本打了下来**。据报道团队把 Claude 深度嵌入开发流程：生成测试用例、迁移脚本、胶水代码，工程师把精力留给架构设计与边界条件。个体产出从“写了多少行”变成“能并行开多少条探索线”；
  3. **需求范围收窄**。内部工具不必兼容二十年历史、不必服务所有语言与平台，只服务自己的 monorepo 和 agent 工作流。砍掉通用性，复杂度指数级下降。
- 三点合并成一个模式：**AI 并没有让“造一个 VCS”变简单，而是让“验证一个设计”变便宜了**。以前一个想法要养一个团队试一年，现在小团队几个月就能跑出真结论。

## 大多数团队要不要跟进？大概率不要

- 结论先行：这不是“Git 要死了”的信号。对 99% 的团队，Git 仍是期望收益最高的选择：
  1. **生态锁定**：GitHub/GitLab、CI、Code Review、IDE 插件全部围绕 Git 构建，迁移的隐性成本远超显性成本；
  2. **多数“Git 变慢”不需要换工具**：partial clone（`--filter=blob:none`）、sparse-checkout、commit-graph、`git maintenance`、LFS 管理大文件，能解决绝大多数案例。先调优，再谈替代；
  3. **若确实需要更现代的模型，开源已有现成选项**：Meta 的 Sapling、Google 工程师主导的 Jujutsu（可直接兼容 Git 仓库），成本比自研低几个数量级。
- 自研的账要算全：不止 5 个月开发，还有持续维护、数据迁移、团队培训、新人上手摩擦。Anthropic 敢做，是因为它几乎是全球 AI 代码产出密度最高的公司之一，规模红利能覆盖成本——这个前提，多数团队并不成立。

## 写在最后：3 条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-15/a572a8f5b93d6a5d.png)

1. **先量化，再归因**。团队抱怨“Git 慢”时，先拉数据：慢在 clone、status、CI 排队还是网络？瓶颈往往不在版本控制本身，配置级的调优常常就能解决。
2. **把 AI 当杠杆，别当许愿机**。这个案例里 AI 压缩的是写代码、写测试的时间；架构决策、迁移策略、边界条件依然靠人。正确姿势是让人上移到设计层，把执行层尽量交给 agent。
3. **定期检查工具的“出厂假设”**。每个工具都带着诞生年代的假设——Git 假设代码由人写、仓库按年缓慢增长。当你的负载明显违背这些假设，不必急着自研，但值得小范围试点 Sapling、Jujutsu 这类新工具。工具换代从来不是在新闻发布那天完成的，而是在团队提前一两年开始准备的那天就注定了。
