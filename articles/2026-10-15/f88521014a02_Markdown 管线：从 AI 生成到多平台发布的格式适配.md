## 背景

Agent 产出长文越来越常见：技术总结、教程、周报。写完只是第一步，真正的摩擦在发布——同一份 Markdown 要进 GitHub、静态站点、公众号、掘金、知乎，各家渲染规则不同。手动复制粘贴改格式，一次两次还行，常态化就是纯体力活还容易出错。这篇分享一条我在用的管线：把 AI 输出规范化为统一中间格式，再按平台分发。

## 问题在哪

直接把模型输出发出去，会遇到三类问题：

1. **生成端不稳定**：同样的 prompt，模型有时吐裸 HTML，有时代码块缺语言标签，列表缩进时对时错，标题从 `#` 还是 `##` 开头随缘。
2. **平台口径不一**：公众号限制最严——外链被剥掉、代码高亮要靠内联样式、图片必须传到自家 CDN；掘金和知乎接近 GFM 但各有裁剪；静态站点则取决于你的 SSG 配置。
3. **嵌套围栏**：模型爱把全文再包一层 ` ```markdown `，二次解析时很容易把代码块截断。

## 做法

核心原则：**AST 是唯一事实源，平台只是渲染目标**。用 unified/remark 把 Markdown 解析成 mdast，所有转换都在 AST 上做，不碰正则。管线分四层：

**1. 规范层。** system prompt 里硬约束：只输出 GFM、禁 HTML、标题从 `##` 起、代码块必须带语言。约束不能只靠 prompt，后接 remark-lint 自定义规则兜底。

**2. 校验层。** 检查非法节点（raw HTML、不支持的扩展）、图片链接可达性、表格内管道符转义。关键设计：校验结果输出结构化错误，喂回 agent 工具循环自我修正，而不是直接 fail。

**3. 适配层。** 每个平台一个 mdast 转换插件，纯函数：

- 公众号：外链转文末引用列表、代码块降级为带内联样式的 `pre`、图片走上传 API 后回填 URL
- 知乎：`$$` 公式转 `\(...\)`、删除 HTML 节点
- 站点：保留 frontmatter，其余平台统一 strip

**4. 发布层。** 每个平台一个 MCP tool，接收适配后的产物。必须支持 dry-run 和幂等——用内容 hash 作外部 ID，重跑不重发。

校验规则示意：

```js
visit(ast, 'html', (node) => {
  errors.push({ type: 'raw_html', line: node.position.start.line });
});
```

## 踩坑点

1. **正则改 Markdown 必挂**。嵌套围栏、表格里的管道符、转义字符，正则全处理不了。哪怕只写一个转换，也走 AST。
2. **公众号图片防盗链**。外站图片预览时能看，群发后全裂。适配层里就做图片搬运，别指望发布时自动处理。
3. **行尾两个空格**。AI 生成常带行尾双空格，部分平台渲染成 `<br>`，部分清洗掉。规范层统一成一种（我选直接合并段落）。
4. **幂等靠 hash 不靠标题**。标题改一个字重发就是两篇，用正文 hash 才稳。
5. **dry-run 必须带 diff 预览**。纯日志看不出格式问题，渲染成 HTML 后对比一眼就能发现。

## 可复用建议

- 把"规范格式"写成一份 prompt 片段 + 一组 lint 规则，放进 agent 工具循环，让模型自己修，修不过再报给人。
- 每个平台留一份 golden file 样例文档，转换逻辑进 CI，平台规则一变第一时间知道。
- 转换函数保持纯函数、无副作用，方便单测和按平台组合。

## 总结

这条管线的本质，是把"格式适配"从发布时的手工劳动，前移成生成后的确定性变换。投入大概两天，换来的是发一篇内容到五个平台的边际成本接近零。建议从最疼的那个平台开始做适配，别一上来追求大而全。
