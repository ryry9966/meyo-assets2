## 背景

团队每天需要一份"昨天发生了什么"的日报：接口报错、任务失败、发布记录、关键指标。过去靠人肉翻日志拼凑，20 分钟起步还经常漏项。这篇帖子记录我把这条链路跑通的过程：**采集 → 清洗聚合 → 结构化摘要 → Agent 叙述 → 推送**，全程可复现，核心代码不到 200 行。

## 问题

原始日志有三个特征，决定了不能直接丢给模型：

1. **量大且噪**：健康检查、重试、心跳占 80% 以上，直接塞进上下文既贵又稀释重点；
2. **格式不统一**：应用、网关、CI 日志格式各异，时间戳还有 UTC 与本地混用；
3. **数字不能靠模型算**：让 LLM 数错误次数，十次有两次会编。

所以核心思路是：**统计和过滤用确定性代码做，LLM 只负责它擅长的部分——把结构化事实转译成人话。**

## 做法

流水线分五段，每段一个独立脚本，cron 串联：

**① 采集**：定时拉取前一天三个来源的日志，统一转 JSONL 落临时目录。关键是按业务时区切窗口，而不是 UTC 自然日。

**② 清洗聚合**：规则过滤噪声（探活、重试成功），按错误码分组计数、算 P95/P99 延迟、抽部署事件，输出固定 schema 的 JSON，我管它叫 daily digest。

**③ 摘要落盘**：digest 带版本号（`schema_version: 3`），原始日志归档 7 天，方便回溯重跑。

**④ Agent 叙述**：digest 通过 MCP 自定义 tool 喂给 agent，prompt 明确三条约束：只基于 digest 写、数字原样引用禁止推算、输出固定 JSON（conclusion / anomalies / suggestions）。外层加 JSON Schema 校验，不过就重试。

**⑤ 渲染推送**：确定性代码把 JSON 渲染成 Markdown，webhook 推群，同时落一份到 wiki。

## 踩坑点

- **时区切窗**：第一版用 UTC 自然日，早上 8 点的报错被切到"两天"，排查半天。所有时间在采集层统一转业务时区。
- **噪声打爆输入**：某服务调试期刷了几万行 DEBUG，digest 直接超限。加了"单来源 top-N 截断 + 溢出标记"，溢出时明写"该来源已截断"。
- **输出不稳定**：模型偶尔在 JSON 外面包一层解释。除了校验，把"只输出 JSON"写进 system prompt，重试上限 2 次。
- **静默失败最危险**：流水线挂了没人发日报，大家反而以为"没事"。现在失败也发降级消息："今日数据缺失，原因 XXX"。

## 可复用建议

1. **Schema 先行**：先定 digest 的 JSON Schema，再写采集与聚合，Agent 那段反而最简单；
2. **每段幂等**：日期作为显式输入参数，任何一步可单独重跑；
3. **金样本测试**：存三份历史 digest 与期望输出，prompt 改动后跑 diff，防止叙述质量悄悄劣化；
4. **数字与叙述分离**：这是整条流水线的底线，模型碰数字必出事。

## 总结

跑了一个多月，日报从"人肉 20 分钟"变成"全自动 + 偶尔抽查"。最大的收益其实不是省时间，而是**口径稳定**——同样的指标每天以同样方式统计和呈现，趋势才有可比性。Agent 在链路里的角色很克制：不碰数、不推测、只转译。这种"确定性代码为主、模型为辅"的分界，比全托管式自动化靠谱得多。欢迎在社区交流你们日报流水线的 schema 设计。
