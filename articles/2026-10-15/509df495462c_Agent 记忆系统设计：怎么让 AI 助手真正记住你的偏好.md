## 背景

LLM 本身无状态。你在 OpenClaw 里跑一个常驻 agent，每次会话都得重新自我介绍：“我用 pnpm 不用 npm"、“周五别给我排发布”、“commit message 不要加 emoji”。说一次两次还行，三个月后没人受得了。这篇文章记录我给自己助手做偏好记忆的方案——不追求“大而全的长期记忆”，只解决一件事：让 agent 稳定记住并正确应用你的偏好。

## 问题：三种常见做法都有坑

1. **全量塞 system prompt**：偏好一多，token 成本上升，长上下文里指令遵循还会被稀释。
2. **每轮都写入记忆**：重复、矛盾条目堆积，两周后记忆文件没法看。
3. **只靠对话历史召回**：检索噪声大，历史里一句玩笑也会被当成“事实”存下来。

## 做法：分层存储 + 读写分离

核心思路是三条：记忆分层、写入走抽取、人可读可改。

**存储层**
- 每个用户一个 `memory.md`（或 JSON），条目结构化：`{类别, 内容, 置信度, 来源, updated_at}`。
- 类别先只做三种：技术偏好、沟通偏好、项目上下文。别一上来建十几个分类。
- 文件放进 Git 仓库，diff 可见，改坏了能回滚。

**写入路径**
- 不做逐轮写入。会话结束（或每 N 轮）让模型做一次抽取：“这轮对话里有哪些值得长期记住的偏好或事实？"
- 抽取结果与现有条目做相似度比对（本地 embedding 就够），超过阈值就**合并更新**，而不是追加。
- 同时暴露 `remember` / `forget` 两个 MCP 工具给 agent，支持用户显式说“记住：xxx"。

**读取路径**
- 会话开始时按当前任务相关性检索 top-K 条目（我限制在 10 条、500 token 以内），拼进 system prompt。
- **当前指令优先级永远高于记忆**：用户本轮明确说的，覆盖记忆里的旧偏好。
- 所有读写打日志，排查“agent 为什么这么回”时能定位到具体条目。

## 踩坑点

1. **去重阈值太松**：“用 pnpm"和“包管理器用 pnpm”变成两条，逐渐膨胀。我把合并阈值调到 cosine 0.92 左右才稳定。
2. **偏好会过期**：“最近改用 Bun 了”是真实场景。加了 updated_at 和置信度衰减，90 天未被命中或确认的条目降级，主动提醒用户复核。
3. **敏感信息被抽进去**：一开始 API key 也被存了。现在写入前有敏感模式过滤（key/token/password），且只存用户可见的明文，保证随时能审查。
4. **多渠道共用一份记忆**：群里说的话污染了私聊行为。按 user + channel 做命名空间隔离。

## 可复用建议

- **先用 markdown/JSON 文件，别急着上向量数据库**。几百条以内，全文匹配 + embedding 召回完全够用，而且可读、可审计、可 diff。
- **对用户透明是信任前提**：提供 `/memory` 命令让用户查看、编辑、删除，比任何“智能”都重要。
- **建一个 10–20 条的回归问题集**（“我爱用什么包管理器？"），每次改动后跑一遍，防止改崩。
- **宁可少记，不可错记**。一条错误记忆对 agent 行为的破坏，远大于十条缺失的偏好。

## 总结

记忆系统本质是个工程问题：写入要抽取 + 去重，读取要限量 + 相关，更新要有时间戳和衰减，全程可观察、可人工干预。从 50 行脚本开始就够了，先跑起来，再根据真实使用中的误判逐步收紧。别把它做成黑盒——能被用户看懂和改动的记忆，才是好记忆。
