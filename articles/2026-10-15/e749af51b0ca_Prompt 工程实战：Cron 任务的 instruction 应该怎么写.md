## 背景

OpenClaw 的 cron 调度大概是除消息触发外用得最多的入口：定时摘要、巡检、日报推送、备份提醒。但它和交互式会话有本质区别——**每次触发都是一次独立运行，没有上文，也没有追问的机会**。你在聊天里说"帮我看看服务器状态"，agent 还能反问"哪台？"；cron 里它不会问，只会按自己的理解执行。

所以 cron 的 instruction 不是"提醒便签"，而是一份交接文档：假设执行者失忆、不能提问、做完就走。

## 一个真实的问题

我最早写的 cron 长这样：

> 每天早上九点整理一下服务器状态发给我

跑了一周，问题全暴露了：

- 输出格式每次不一样，有时是表格有时是大段文字；
- "发给我"被理解成默认会话，有一次差点发去别的频道；
- 某天监控接口超时，agent 没报错，而是"合理地编了一份状态"——这是最危险的一次；
- 手动补跑，文件和消息重复生成了一份。

## 做法：五段式模板

后来我把所有 cron instruction 重写成固定结构：

1. **目标**：一句话说清做什么、给谁看。
2. **输入**：数据源写死。路径、命令、URL 直接写全，不写"昨天的数据"这类相对词；时间统一要求 agent 运行时先执行 `date` 确认，避免时区歧义。
3. **边界**：只读还是可写，允许用哪些工具，禁止哪些动作（比如"不主动发消息到群组，只写入指定频道"）。
4. **输出**：格式、投递目标、长度上限全部写实，不留"发给我"这种指代。
5. **异常**：数据源不可用时怎么办——我的写法是"对应字段填 UNKNOWN 并单独一行说明原因，禁止用推测补全"。

改完后的核心部分：

> 每天运行一次。先执行 `date` 确认当前时间，然后读取三台主机的最新监控快照（路径见配置）。输出 Markdown 表格：主机 / CPU / 内存 / 磁盘 / 状态，缺失字段填 UNKNOWN 并附原因。只写入 #ops-daily 频道，不 @ 任何人。写入失败则重试一次后停止并报错。

## 踩坑点

- **相对时间词**是第一大坑。"今天""昨天"依赖 agent 对时区的猜测，固定写"运行时先取系统时间"。
- **静默失败**比失败更糟。必须让异常也产出消息，否则 cron 挂了三天你都不知道。
- **幂等性**。会重复执行的任务，instruction 里要写"先检查目标文件/消息是否已存在，存在则跳过"。
- **一个 job 一件事**。把日报、巡检、清理塞进同一条 instruction，任何一段出问题都难定位，拆开。
- **敏感信息**不要写进 instruction，走环境变量或配置引用；指令模板放仓库里改，走评审。

## 可复用建议

- 写完后先在交互会话里手动跑一遍等价 prompt，确认行为符合预期再固化到 cron，能省掉大部分试错。
- 上线后留一周观察期，收集 agent 跑偏的输出，针对性收紧措辞——instruction 是调出来的，不是一次写对的。
- 指令改版进版本管理，出问题能回滚。

## 总结

Cron instruction 的本质，是把会话里靠上下文兜底的"默契"，翻译成纸面上可执行的"契约"。自包含、边界清晰、失败可见——做到这三点，定时任务才真的能放手让它跑。
