## 背景

团队里几乎都有这种日常：到点打开几个终端、几份日志，人工拼一份"昨日发生了什么"。事情不难，但每天都做、每次都可能漏。我把这条流程搬到了 OpenClaw 上做成自动化流水线：定时拉日志、规则结构化、交给 Agent 归纳、校验后推送。稳定跑了几周，基本不再需要人碰。

## 问题

"把原始日志直接丢给模型写日报"是第一个想到的方案，也是最先失败的：

- 原始日志噪声大，一天几十万行，token 和模型注意力都撑不住；
- 关键事件（报错、阈值告警）容易淹没在 INFO 级别里；
- 模型每次输出的格式、详略都不一样，下游没法稳定消费；
- 任务失败是静默的，没人发现今天的日报其实没发出来。

所以核心思路定为：**规则先做结构化，模型只做归纳，输出必须过校验**。

## 做法

流水线分五步，每步是独立脚本，中间产物落盘：

1. **采集**：定时任务拉取各来源日志（文件、API、数据库），统一转成带时区的标准时间戳，存为原始 JSONL。拉取失败自动重试两次。
2. **结构化**：这一步纯规则——用正则和字段映射把日志解析成固定 schema 的 JSON：事件类型、级别、次数、涉及模块、耗时。过滤 DEBUG 和心跳类噪声，聚合后的数据量通常只有原始日志的 1%~5%。
3. **归纳**：把聚合 JSON 通过 MCP 工具喂给 Agent，prompt 里只有两条硬要求：按固定模板写、数字只能引用输入不许编造。模型负责"异常集中在哪个模块、与前日相比有什么变化"这类叙述。
4. **校验**：输出用 JSON Schema 校验，再加两条断言：各模块事件数总和是否等于输入总数、报告日期是否正确。校验不过重试一次，再失败就降级成纯模板报告——宁可朴素，不能缺席。
5. **投递**：推送到群 webhook，同时把最终报告和中间 JSON 按日期归档，方便回溯。

## 踩坑点

- **时区**：第一天就踩了。采集端用本地时间、统计端用 UTC，跨天边界的事件对不上账。现在统一 UTC 存储、本地时区展示。
- **幂等**：定时任务重跑会出两份日报。给每次执行加 `日期+版本号` 的幂等键，重跑只覆盖不追加。
- **格式漂移**：模型偶尔在 JSON 外面加一句"好的，以下是报告"。Schema 校验直接拒绝，重试一次基本能过。
- **告警静默**：日报失败和日报内容走不同通道。流水线挂了必须有单独的失败通知，否则"今天没收到日报"本身就是最晚的告警。

## 可复用建议

- **规则能做的不交给模型**。解析、过滤、聚合是确定性工作，便宜且稳定；模型的价值在归纳和措辞。
- **中间产物落盘**。结构化 JSON 存档后，日报只是其中一个视图，周报、月报、临时排查都复用同一份数据。
- **模板即契约**。字段固定下来，下游（人或其他 Agent）才敢依赖。
- **每一步可独立重跑**。排障时不用整条链路从头来。

## 总结

这条流水线没有炫技的部分：规则解析 + 受限的模型归纳 + 硬校验 + 静默失败兜底，总代码量不到两百行，却把一份每天要人肉维护的日报变成了不烦人的后台任务。经验一句话：**别让模型干规则的活，别让自己的流程静默失败**。
