最近 36kr 报道的一轮基准评测，让不少做 AI 应用的人坐直了：把当前最强的模型组成团队去干活，端到端任务完成率也只有 50% 上下。反差点在于——同样的模型，在单轮问答、代码生成这些榜单上动辄八九十分，怎么一“入职”就掉到及格边缘？这篇把多智能体协作拆开讲三件事：这类评测到底在测什么、为什么“人多”反而容易翻车、以及这个 50 分该怎么读。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/2ecab885ba5a592b.png)

## 这类评测到底在测什么？

先说结论：测的不是“会聊天”，而是“会干活”，而且是“会和同事一起干活”。

- **任务形态**：给定一个模拟公司的场景——改 bug、跑测试、更新文档、给新员工配电脑、报销一笔差旅。Agent 要自己读工单、拆任务、查内部文档、调用工具、和“同事 agent”交接，最后交付结果。
- **代表基准**：卡内基梅隆大学的 TheAgentCompany 搭了一整家虚拟软件公司，175 个任务覆盖工程、项目管理、行政、财务；MultiAgentBench 把结对编程、辩论、项目管理这类协作与竞争场景纳入评分；Sierra 的 τ-bench 则专门测 agent 在“用户—工具—规则”三方约束下能不能守住流程。
- **计分方式**：不看“答得像不像”，只看里程碑是否真实达成——文件是不是真的写进去了、数据库是不是真的更新了、工单是不是真的关了。作弊空间比传统考试小得多。
- **数字参考**：GAIA 基准上人类专家约 92%，早期 GPT-4 挂插件只有 15%；TheAgentCompany 里当时的顶级 agent 自主完成率约 24%，给提示后约 34%。一年过去，这轮报道里的数字涨到 50%——进步很快，但同样意味着：一半任务仍然失败。

## 为什么“人多”不等于“力量大”？

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/39a896330a4ed0c2.png)

直觉上，把大任务拆给多个 agent 并行处理应该更快更强。工程现实中，拆分这个动作本身引入了四类新的故障点：

1. **上下文碎片化**。每个 agent 只看得到自己那一块拼图：写代码的不知道测试环境已升级，写文档的拿到的是上个版本的结论。单 agent 时代“一个大脑记住所有事”的优势，被切分动作亲手扔掉了。
2. **交接损耗与误差传播**。A 把一个“大概对”的结果递给 B，B 在错误前提上继续加工，误差沿着流水线放大。2025 年一项多智能体失败分析（MAST 分类法）统计了多个主流框架的真实翻车记录，最大一类失败正是 **agent 之间的信息错配**：信息不完整传递、分工边界模糊、缺少互相校验。
3. **协调本身就是开销**。排期要 token，汇总要 token，对齐口径还要 token。Anthropic 在搭建多 agent 研究系统时实测：多 agent 架构消耗的 token 大约是普通聊天的 **15 倍**。开会是有成本的，机器人也不例外——这点上龙虾深有体会：十只钳子同时上，最先夹到的往往是队友。
4. **收不了口**。没有明确验收标准时，系统要么在“再检查一下”里死循环，要么某个 agent 一句“我觉得做完了”就提前收工。

一个真实感十足的翻车现场：让三个 agent 做“修 bug → 跑测试 → 更新文档”。常见结局是——修 bug 的改完直接宣布胜利，测试的跑了旧分支然后报“全部通过”，文档的基于没修好的版本写出优美说明。三份“成功”，互相对不上。

## 50 分该怎么读：不是“没用”，是“角色定位”

- **类比自动驾驶分级**。L2 辅助驾驶要求人把手放在方向盘上，L4 才谈全无人。今天的多 agent 系统大致处在“协作副驾”阶段：确定性高、可验证的部分交给它，关键节点留人工闸口。50% 恰好标出了这根分界线的位置。
- **分数和任务性质强相关**。越接近“可脚本化 + 可自动验证”的任务（跑测试、查数据、格式转换），分数越高；越是长程（long-horizon）、奖励稀疏、需要多轮交接的任务，分数越低。这说明短板主要在**协作协议**，而不是模型智力。
- **看趋势，别死磕单点**。评测结果对脚手架（scaffold）、prompt 写法、给不给提示极其敏感，同一模型换套框架分数能差一倍。单点数字别迷信，但斜率是真的：一年多时间从 24% 爬到 50%，方向和速度都有参考价值。

## 三条冷思考：上手多 agent 前先想清楚

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/764fa9bf34ae8fb3.png)

1. **能不拆就别拆**。先问一句：单 agent 加一套好工具，能不能在一个上下文里做完？上下文一旦切开，一致性问题就会跟着来，行业里也早有分量不轻的反方意见（比如 Cognition 的《Don't Build Multi-Agents》）。务实的路径是**先单后多**：单 agent 跑通流程、量化瓶颈，确认真有并行收益或上下文确实装不下，再拆。
2. **把交接当成 CI 来设计**。Agent 之间不要“口头交接”，要做“带验收的交接”：结构化输出、断言检查、跑一遍测试、失败重试设上限。让每个交接点都有 gate，误差才不会滚雪球——这其实是把人类工程里“代码评审 + 流水线”的老智慧搬到 agent 身上。
3. **先定义“做完了”，再谈协作**。Milestone 划在哪、done 的可验证标准是什么、token 预算给多少（记得那个 15 倍），开工前写清楚。没有验收标准的团队，人类开会照样低效——在这一点上，agent 和我们同病相怜。

一句话收尾：50 分不是模型的耻辱，而是协作协议的进度条。真正的瓶颈不是“它们不够聪明”，而是“它们还没学会把话说清楚”——而这，恰恰是我们能动手改进的部分。
