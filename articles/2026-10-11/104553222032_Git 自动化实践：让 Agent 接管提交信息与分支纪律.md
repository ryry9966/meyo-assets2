## 背景

在 OpenClaw 的使用场景里，Agent 通常已经具备 shell 执行能力，能跑测试、改代码。但很多工作流止步于此：git 操作仍靠人手工完成。结果是提交历史一团糟——`fix`、`update`、`临时改一下`满天飞，实验性改动直接堆在 main 上，回溯成本极高。

我们最近把 git 的日常操作交给 Agent 管理，跑了大概一个月，把流程和踩的坑整理如下。

## 三个真实痛点

1. **提交信息质量差**：人赶进度时写的 message 基本不可读，`git log` 等于废掉。
2. **分支纪律形同虚设**：想到什么改什么，改完才发现忘了切分支。
3. **误提交敏感文件**：`.env`、本地配置差点进远程仓库，靠手快才拦下来。

这三个问题的共性是：它们是**纪律问题**，不是技术问题。而 Agent 恰好擅长执行纪律。

## 落地方案

核心思路是**权限分层 + 规范固化 + 人工闸门**，我们没有让 Agent 裸敲 shell，而是封装成一个 skill（用 MCP git server 也可以，原理相同）：

```yaml
# skill: git-guard（节选）
allow:  git status, git diff, git log,
        git add -p, git commit, git switch -c
confirm: git push, git reset --hard, git rebase
deny:   git push --force, git filter-branch
rules:
  - 提交前必须跑 git status --porcelain，
    发现 .env / 密钥类未跟踪文件即中止
  - message 遵循 conventional commits，
    标题 <= 72 字符，body 说明动机
  - 分支命名 <type>/<短横线slug>，建前先校验
  - 远程已存在的分支禁止 amend / rebase
```

固定的执行流程是：`status → diff → 生成 message → 给人确认 → 执行`。关键是**人只在两处介入**：确认 commit message，确认远程写操作。其余全部自动化，一个月下来 `git log` 终于像样了。

## 踩坑记录

- **`git add -A` 是最大风险点**。Agent 图省事会全量暂存，把 `.env` 一起带进去。规则里强制先跑 `status --porcelain` 做敏感文件检查，另外补了个 pre-commit 钩子兜底。双保险是必要的。
- **Agent 对已推送提交执行 amend**。它觉得 message 写得不完美就改，结果远程冲突。规则必须显式写死：远程已有分支只允许追加提交。
- **大 diff 一次提交，message 质量骤降**。改动跨五个文件时，Agent 生成的 summary 开始说车轱辘话。后来要求按文件拆分提交，质量立刻回升。
- **detached HEAD 陷阱**。Agent checkout 到旧 commit 上开始改代码，提交悬空丢失。解法是每次操作前重读 `status`，绝不依赖上下文记忆里的仓库状态。
- **失败重试循环**。push 被拒时它会反复重试，最危险的一次差点尝试 force push。现在限制：同类命令最多重试两次，失败直接上报等人。

## 可复用的建议

1. **规则写成配置，不要写成散文提示词**。白名单/确认/拒绝三层清单，Agent 执行得比自然语言规则稳定得多。
2. **所有 git 写操作落审计日志**：时间、命令、产生的 commit hash。出问题时能复盘。
3. **支持 dry-run**：先输出将要执行的命令清单，人确认后再真跑。
4. **远程凭证最小化**：给 Agent 的 token 只开必要仓库的写权限，别拿个人主账号凭证喂给它。

## 总结

Git 自动化的价值不在于省几秒钟敲命令的时间，而在于让提交历史变成**可审计、可回溯的记录**。实践下来我们的分工很清晰：Agent 负责执行和守住规范，人负责守住闸门。规则进配置、敏感操作进确认队列——这套模式不依赖特定工具，换成任何有 shell 能力的 Agent 都成立。

欢迎在社区里交流你们对 Agent git 权限边界的划分方式。
