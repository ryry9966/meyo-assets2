## 背景

团队里总有几种"日报"：个人工作记录、服务运行摘要、项目进展同步。写的人烦，看的人更烦。我们这边的情况是：数据其实都在——git 提交、CI 流水线、服务器日志、任务清单——但散落在各个系统里，没人愿意每天手工汇总。

OpenClaw 的定时任务加 MCP 工具恰好适合干这件事：调度是现成的，取数有工具，归纳交给模型。于是花了一个周末把日报流水线搭了起来，稳定跑了几周，这篇做个复盘。

## 问题

最初的想法很直接：写个 cron，把当天所有日志一股脑塞给模型，让它"总结成日报"。跑了一天就放弃了：

- 一天的原始日志动辄几十万行，直接进上下文既贵又容易被截断；
- 模型会"补细节"——日志里没有的事，报告里写得有模有样；
- 输出格式每天不一样，有时是 markdown，有时是散文；
- 失败是静默的：有一次采集脚本挂了，当天日报凭空消失，没人发现。

本质问题是：把"结构化"整个丢给模型，既不可靠也不可控。

## 做法

现在的流水线分五段，原则是**采集靠脚本、降噪靠规则、归纳靠模型、兜底靠校验**：

1. **采集（脚本）**：每个数据源一个独立小脚本——git log 按仓库聚合、CI 取失败用例、任务清单拉状态变更。各脚本输出统一 schema 的小块 JSON，互相不依赖。
2. **降噪（规则）**：进模型前先砍量——去掉心跳与探活日志、按关键词去重、单源超限只保留聚合摘要。这一步通常能砍掉 90% 以上体积。
3. **归纳（模型）**：一次 Agent 调用，temperature 设 0，prompt 里给死 JSON schema：每条事件包含「来源、事件、影响、状态、建议跟进」，并要求"输入为空就输出空列表"，不许编造。
4. **校验（兜底）**：输出过 JSON schema 校验；失败则带报错重试一次；再失败就降级——把原始摘要直接附在报告末尾，宁可糙也不能空。
5. **投递（模板）**：固定模板渲染成 Markdown，推到群频道，同时在本地归档一份带日期的原始文件，方便回溯"报告为什么这么写"。

调度上用 OpenClaw 的 cron 在每天固定时间触发，整条链路是幂等的，重跑不会产生重复报告。

## 踩坑点

- **时间戳不统一**：不同系统时区不一致，模型自己换算时算错过一次。所有时间在采集阶段就归一到同一时区，别指望模型。
- **空输入诱发幻觉**：日志为空的日子，模型倾向于"合理想象"。必须在 prompt 里显式允许空结果，并在校验时核对每条事件能在输入里找到出处。
- **静默失败最伤**：流水线自己也要有"日报"——加了个心跳检查，连续两轮没产出就告警。
- **prompt 要进代码库**：改 prompt 不留版本，出了问题根本不知道是数据变了还是指令变了。

## 可复用建议

- 先接一个数据源（比如 git）跑通全链路，再逐个加源，不要一次铺开。
- 每个采集脚本做成独立工具/插件，坏了只降级一个源，不拖垮整条流水线。
- 对输入内容做哈希，内容没变就跳过模型调用，省钱也省心。
- 报告模板和 schema 一起版本化，格式变更提前在群里知会。

## 总结

这套东西单看每一步都很朴素，价值在于分工清楚：确定性的工作交给脚本，模糊的归纳交给模型，质量交给校验，可靠性交给兜底。跑了几周的体感是，日报终于从"人伺候流程"变成了"流程伺候人"。下一步打算把周报和异常专项也接到同一条流水线上，大部分环节可以直接复用。
