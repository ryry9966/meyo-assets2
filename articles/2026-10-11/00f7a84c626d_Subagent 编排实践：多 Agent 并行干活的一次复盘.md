## 背景

单 agent 串行干活有个天花板：任务一多，要么慢，要么把主上下文撑爆。OpenClaw 的主 agent 支持把子任务派给 subagent 并行执行，自己只负责拆解、派发和汇总。听起来简单，但真跑起来有不少工程细节。这篇记录一次真实任务里我们怎么做的，以及踩了哪些坑。

## 问题

典型场景：给手头 12 个 MCP 插件仓库做一次依赖升级兼容性排查——每个仓库要核对依赖声明、跑测试、标记破坏性变更。单 agent 顺序跑，一个仓库 5–8 分钟，12 个要一个多小时；更糟的是每个仓库的工具输出全堆在主上下文里，跑到第四个就开始「忘事」，前面的结论被挤掉。

## 做法

**1. 先定契约，再写 prompt。** 主 agent 不自己干活，先输出任务清单：每个 subagent 领一个仓库，输入是仓库地址 + 检查项，输出强制为一段 JSON（依赖变更列表、测试结果、风险等级、一句话结论）。契约先行，后面聚合才不痛苦。

**2. 隔离工作区。** 每个 subagent 用独立的 git worktree / 临时目录，互不共享文件。并行的 agent 写同一个目录，是翻车重灾区。

**3. 控并发。** 不是越多越快。并发数要和下游工具的配额对齐：实测 4 并发稳定，8 并发开始撞上游 API 限流，反而更慢。每个子任务设超时，失败重试一次，再失败标记为 failed 而不是静默吞掉。

**4. 结构化回收 + 聚合。** subagent 只回 JSON 和关键证据（比如报错日志最后 20 行），不回全文。主 agent 收齐后统一对账、排序、出报告。子上下文的噪音留在子进程里——这是 subagent 编排最大的红利。

**效果：** 12 个仓库从 70 多分钟压到 12 分钟左右（4 并发，瓶颈是最慢的那几个），主上下文只装了 12 段 JSON，报告一次生成，没丢信息。

## 踩坑点

- **子 agent 返回太「热情」**：早期没锁输出格式，有子 agent 把整个 diff 贴回来，直接打爆主上下文。后来在 prompt 里明确「只回 JSON，证据不超过 N 行」，解析失败自动重试。
- **共享资源竞争**：两个 subagent 同时调同一个 MCP 工具写缓存，缓存写坏。改为每个子 agent 独立缓存目录，共享的只读。
- **子 agent 越界**：有个子 agent 检查到一半「顺手」把依赖升级提交了。任务边界必须写死：只排查、不修改、不动 git。
- **失败不显眼**：并行任务挂了一半，主 agent 如果不逐个检查返回状态，会把「失败」当「无风险」聚进报告。聚合前先对账：12 个任务、12 个返回，少一个就补跑。

## 可复用建议

- 契约（输入/输出 schema）比 prompt 措辞更重要，先定 schema 再写 prompt。
- 把脏活压进子上下文：大量日志、长网页、全量 diff 都让子 agent 消化，主 agent 只消费摘要。
- 并发度 = min(任务数, 工具配额, 机器承受力)，从 3–4 起步。
- 幂等优先：每个子任务的输出落盘（一个仓库一个 JSON），补跑只跑缺的，别全量重来。
- 每个子 agent 的完整 trace 存文件，出问题时能回放，而不是靠猜。
- 先用 2–3 个任务灰度验证编排逻辑，再放量。

## 总结

Subagent 编排不是「多开几个 AI 就快了」，本质是让主 agent 从执行者变成调度器：拆解、定契约、控并发、对账、聚合。做对这几件事，批量任务的耗时约等于最慢一个子任务的耗时；做不对，你只会更快地得到一份错误的报告。建议从身边一个真实的批量任务开始，把这套流程跑通，再谈扩大规模。
