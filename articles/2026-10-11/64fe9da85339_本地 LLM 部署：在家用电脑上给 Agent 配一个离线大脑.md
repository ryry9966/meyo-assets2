## 背景

玩 Agent 自动化之后，我很快遇到一个现实问题：手头的自动化流程要读聊天记录、本地文件、家庭网络的设备状态，全走云端 API，一是费用随调用量线性上涨，二是隐私上不太舒服。于是尝试把一部分任务切到本地模型上跑，让 OpenClaw 的 Agent 在断网时也能完成基础的工具调用。折腾了两周，把过程和结论整理一下。

## 真正的问题是什么

本地部署的门槛早就不是"能不能跑起来"，`ollama run` 一条命令就完事。真正的问题是：**模型能否稳定完成 Agent 循环**——准确发起 tool call、输出可解析的 JSON、在多轮上下文里不丢指令。很多教程在"模型能聊天"就停了，到接 Agent 这一步才发现完全不是一回事。

## 做法

1. **摸清硬件上限**。粗略估算：Q4 量化的 7B/8B 模型约占 5~6GB 显存，14B 约 9~10GB，32B 需要 20GB 左右，还要给 KV cache 留余量。我的 12GB 显存卡最终稳定跑 14B。
2. **选运行时**。Ollama 或 llama.cpp 都行，关键是暴露 OpenAI 兼容接口，这样 Agent 侧配置统一，换模型只改模型名。
3. **选模型**。优先选原生支持 function calling 的模型，中文场景下 Qwen 系列表现较稳。从 7B/8B 起步验证链路，再往上加参数。
4. **接入 Agent**。`base_url` 指向 `localhost:11434/v1`，显式设置上下文窗口，每次任务只挂载必要的 MCP 工具。
5. **最小化验证**。先跑"单工具 + 单任务"的最简循环，统计 JSON 解析成功率，再逐步加复杂度。

## 踩坑点

- **上下文长度是隐形杀手**。默认 `num_ctx` 往往只有 2048/4096，Agent 的系统提示词加工具 schema 很快就撑爆，症状是模型"失忆"、工具参数乱填。务必显式调大。
- **不是所有模型都会真的调工具**。有的模型只是输出"长得像调用"的文本。换模型前先单独测一轮 tool call。
- **KV cache 吃显存超出预期**。权重装得下不代表 16k 上下文装得下，8GB 卡跑长上下文容易 OOM，可以量化 KV cache 或压缩上下文。
- **速度预期要现实**。消费级设备上 5~15 tok/s 很常见，一个 10 步的 Agent 循环可能要跑几分钟，任务设计要粗粒度。
- **别迷信参数量**。一个稳定调用工具的 14B，好过一个总幻觉参数的 32B。

## 可复用建议

- 写一个固定的基准脚本，记录每个模型的 tok/s、峰值显存、tool call 成功率，换模型前先跑一遍，别凭感觉。
- 控制工具数量，本地模型挂太多 MCP 工具会明显退化，按任务注册最小集合。
- 做混合路由：敏感或简单任务走本地，复杂任务走云端，把模型配置做成 OpenClaw 里按任务可选的参数，而不是全局常量。
- 提示词尽量短，few-shot 例子挪进工具描述里，给上下文省空间。

## 总结

本地 LLM 用于 Agent 自动化已经完全可行，但工程重心不在"跑起来"，而在**稳定结构化输出和上下文管理**。建议路径：小模型打通链路 → 建立量化基准 → 按任务灰度切流。慢一点没关系，可复现才重要。
