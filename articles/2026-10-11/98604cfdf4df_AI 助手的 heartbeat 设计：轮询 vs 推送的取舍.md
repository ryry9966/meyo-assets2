## 背景

Agent 平时是被动的：用户不说话，它不动。但自动化场景里总有一些"没人说话也要干"的活——每天早上汇总一次 CI 状态、盯一个目录的变化、定时巡检 MCP 工具的可用性。这些需求最终都会落到同一个设计问题上：agent 的心跳怎么打。

主流做法就两种：轮询（agent 按固定间隔醒来检查）和推送（外部事件主动唤醒 agent）。两者都不是新东西，但在 agent 语境下成本模型变了：每次心跳往往意味着一次真实的模型调用，token 是真金白银。

## 问题

纯轮询的痛点很直接：绝大多数心跳是空转。我把间隔压到 5 分钟试过一天，日志里 95% 以上的唤醒最后什么都没做，token 账单和上下文膨胀倒是实打实的。

纯推送看起来更优雅，但工程上有两个坑：一是事件源到 agent 之间要打通链路（webhook → 网关 → 会话注入），任何一环挂了事件就丢了，而 agent 自己不知道；二是很多事件源根本没有推送能力，只有"来查一下"的接口。

## 做法

我的结论是混合架构：**推送做主通道，心跳做兜底和对账**。具体步骤：

1. **先列心跳清单**。heartbeat 文件里只写"必须周期性确认的事"，比如巡检项、待办超时检查。清单要短，5 条以内。
2. **间隔按容忍度倒推**。任务能容忍多久延迟，间隔就设多少，宁可长不可短。我目前 30 分钟起步，再加随机抖动避免整点共振。
3. **推送走独立通道**。事件源通过 webhook 打到网关，网关把事件作为一条消息注入 agent 会话，带上事件 ID。
4. **心跳只做对账**。心跳唤醒时先读状态文件，比对"应该发生的事"和"已发生的事"（事件 ID 是否处理过、巡检项是否异常），有差异才真正调模型处理，没有就直接结束。
5. **所有动作幂等**。不管唤醒来自心跳还是推送，处理前先查状态，处理后原子更新状态文件。

## 踩坑点

- **心跳触发全量对话**：最初每次心跳都带着完整会话历史调模型，上下文越滚越大。后来把心跳单独开轻量会话，只带清单和状态摘要。
- **推送丢了没人知道**：网关重启丢过一批 webhook。心跳对账就是为这个准备的——推送可能丢，但状态差异会在下一次心跳被发现。
- **心跳和推送并发撞车**：同一个事件既被推送处理了，又被心跳扫到。加了一层基于事件 ID 的去重才解决。
- **安静时段没做**：半夜心跳照样跑，白烧 token。加了 quiet hours，跳过的检查在下个窗口补上。

## 可复用建议

- 心跳频率是成本旋钮，先用最长间隔跑，出现真实延迟问题再缩短。
- 每次唤醒记录"唤醒原因 + 结果"，一周后回看日志，空转比例会告诉你间隔该怎么调。
- 判断标准就一条：**延迟敏感的事件用推送，一致性敏感的状态用心跳对账**，别让任何一个通道独自扛全部职责。

## 总结

轮询和推送不是二选一。轮询便宜但迟钝、空转多；推送及时但链路脆弱。用推送换及时性，用心跳换确定性，中间靠一份幂等的状态文件缝合——这是我在 OpenClaw 自动化实践里跑得最稳的组合。先让兜底可靠，再去优化及时性，顺序别反。
