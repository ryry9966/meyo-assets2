## 背景

跑 Agent 和自动化任务久了会发现一个规律：**重试不是异常，而是常态**。MCP 工具调用超时后调度器会重试；webhook 可能被上游重复投递；cron 补跑、用户手动"再执行一次"、插件重启后恢复队列——都会让同一条指令进入执行路径不止一次。消息队列的常见保证是 at-least-once：保证至少送达一次，不保证恰好一次。

## 问题

于是关键问题从"怎么保证只执行一次"变成"重复执行时怎么不出事"。非幂等操作的典型事故：通知发两遍、订单重复创建、日志文件同一行被追加 N 次、状态机被二次推进跳到非法状态。这类 bug 在测试环境几乎复现不出来，因为测试时没人手动重试。

## 做法

我们的约定很简单：**每个会改变状态的任务，必须有稳定的任务键**。

1. **定义任务键**：用业务 ID + 意图描述生成，例如 `order:{id}:ship`。绝对不要用时间戳或随机 UUID 当键——那样每次重试都算"新任务"，幂等形同虚设。
2. **唯一约束兜底**：任务键写入数据库唯一索引，插入冲突即视为已执行，直接返回上次结果。不要只靠代码里的 if 检查，并发重试时两个实例可能同时通过检查（check-then-act 竞态）。
3. **先记后做，同事务**：幂等记录和业务变更放同一事务提交。做不到同库，就退化为"先抢锁、再执行、完成后标记"。
4. **外部 API 带幂等键**：调第三方接口时透传 `Idempotency-Key`，支付、消息类 API 大多支持。
5. **Shell 与文件操作改写成幂等形式**：`mkdir -p`、覆盖写代替追加、先写临时文件再原子 rename、`rsync` 代替 `cp`。
6. **无法幂等的外呼单独处理**：比如发邮件这类没有幂等键的第三方，用去重表 + 时间窗，同键在窗口内只放行一次。

## 踩坑点

- **假成功**：幂等记录写了，业务操作却失败了，之后所有重试都被跳过，任务永远"已完成"。所以记录和操作必须同事务，或配对账/超时回收机制。
- **半完成状态**：任务执行到一半崩溃，重试要么从头再来（要求每个步骤本身幂等），要么断点续跑（要求步骤化记录进度）。二选一，别混着来。
- **重复挂载**：插件热重载后旧 handler 没注销，同一事件被消费两次。这种"框架层的重复"最隐蔽，靠任务键一样能兜住。
- **读操作别过度设计**：查询、列表类操作天然幂等，强行加键只会增加复杂度。

## 可复用建议

- 把幂等做成框架层中间件：任务键 → 唯一约束 → 执行 → 完成标记。插件只声明业务键，不各自造轮子。
- 工具接口显式声明是否幂等，非幂等工具强制走去重通道。
- 日志里永远带上任务键，排障时一眼分清"这次是重试还是新任务"。
- 上线前做一次演练：手动把同一条消息投递三遍，观察系统行为是否符合预期。

## 总结

在自动化系统里，重复执行是必然事件，不是小概率故障。正确的思路是把"恰好一次"拆成"至少一次投递 + 幂等执行"：投递层交给重试机制，执行层用稳定的任务键和唯一约束兜底。当重复变得无害，重试、补跑、故障恢复这些机制才真正敢放开手脚。
