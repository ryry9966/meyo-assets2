## 背景

OpenClaw 这类常驻 Agent 和一次性对话不同：它跑在你自己的机器上，挂着 WhatsApp / Telegram 等通道，能调 MCP 工具、执行命令、替你发消息。人格如果写死在系统提示词里，改一次要动配置重启，还会和业务配置搅在一起。SOUL.md 的定位是把「我是谁、我怎么说话、我绝不做什么」抽成工作区里的一个普通文件，随上下文注入，Agent 自己也能读、能改。相当于把人格从代码层挪到配置层。

## 问题

没有这份文件时，常见三类麻烦：

1. **语气漂移**。今天正式明天贫嘴，跨会话、跨通道不一致，用户感知割裂。
2. **没有边界**。你说"帮我删了那个目录"它就删；群里陌生人让它查隐私它也照办。
3. **约束散落**。一部分写死在配置里，一部分靠你事后纠正，无法版本化、无法回归测试。

## 做法

工作区里通常有 SOUL.md、AGENTS.md、USER.md、MEMORY.md，分工先划清：SOUL.md 只放身份、语气、价值观、硬边界和升级规则；操作规程放 AGENTS.md；个人偏好放 USER.md。

我现在的 SOUL.md 骨架四段，全文控制在一百行内：

- **身份**：两三句，说清角色定位和与"我"的关系；
- **语气**：具体到"先给结论再给解释""不堆 emoji"；
- **硬边界**：祈使句、可判定。例如"执行删除、转账类操作必须先复述命令并等我确认""不在公开群转述私聊内容""不冒充我对外承诺"；
- **升级规则**：拿不准就停下来问，列出哪些情况必须问。

两条配套做法：

1. **用 git 管它**。人格修改走小步提交，出问题能 diff 回溯。我做过一次大改后助手语气突变，靠 git 半小时定位到某一条措辞。
2. **换会话验证**。新开会话问它"你会做什么、不会做什么"，再跑几条对抗测试——比如让它冒充我朋友要转账。边界写得好不好，测了才算数。

## 踩坑点

- **写成空话**。"你是一个乐于助人的助手"没有信息量，模型默认就这样，不如删掉。
- **越长越好是错觉**。几百行的人格文件吃上下文，还会自相矛盾，运行时模型随机取一边。
- **把 SOUL.md 当安全边界**。它只是上下文，不是沙箱。提示注入、恶意 MCP 工具描述都可能绕过它。真正的强制层在工具权限：openclaw.json 里的工具白名单、审批门、通道隔离。软约束靠 SOUL.md，硬约束靠配置，两层都得有。
- **边界没有对应动作**。写了"不许碰生产环境"，但 gateway 还是挂载了那台机器的 shell，这条边界等于没写。
- **只测正常路径**。边界的价值恰恰在异常请求上，正常对话测不出什么。

## 可复用建议

- 每条边界都应该能改写成一条测试用例，写不出来说明它太模糊。
- 一次提交只改一个意图，别攒着批量改人格。
- 换模型时重读一遍 SOUL.md：对 A 模型有效的措辞，对 B 模型未必生效。
- 团队场景可以按通道做轻量覆盖，但底层身份保持一致。

## 总结

SOUL.md 成本极低、杠杆很高。把它当配置即代码来管：短、具体、可测试、有版本。人格负责"像谁"，工具权限负责"能做什么"，两层对齐，常驻 Agent 才敢真正放手用。
