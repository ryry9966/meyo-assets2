## 背景

OpenClaw 的主会话承担两件事：和用户的持续对话上下文，以及长期记忆（MEMORY 读写）。它的价值在"连续"。而日常自动化里大量任务是重 IO 的：全库检索、批量抓网页、跑测试、整理文件。这些活适合丢给子 Agent——主 Agent 通过 spawn 类工具（如 `sessions_spawn`）拉起一个子 Agent，它拥有独立的 session：独立的上下文窗口、独立的本地 transcript，干完活把最终结果交回主会话后即结束。

隔离机制是现成的。但实践中"隔离"不等于"不污染"，污染往往是用法喂出来的。

## 问题

我们踩过三类典型污染：

1. **内联跑重工具。** 在主会话里直接执行一条输出几千行日志的命令，stdout 整段进主 transcript。几轮对话后上下文被工具输出填满，模型开始"失忆"，且每轮都在为这些垃圾 token 付费。
2. **子 Agent 返回值不设限。** spawn 时不说明要什么，子 Agent 会把全部过程性发现（比如十几个页面的原文摘录）塞进 final message，主会话瞬间膨胀。
3. **共享写路径。** 子 Agent 图省事直接改 MEMORY.md 或工作区共享笔记，把中间结论当"事实"写进长期记忆，之后每次对话都被这段污染误导。

## 做法

以 cron 自动化和 Telegram 通道上的日常使用为例，我们固化了几条约定：

1. **重活必 spawn，不在主会话内联跑。** 凡预期输出超过几十行的命令，一律交给子 Agent，主会话只接收结论。
2. **spawn 时写明返回契约。** 任务描述里显式要求："只返回不超过 N 行的结论 + 关键文件路径，不要贴原文。"契约前置比事后裁剪省得多。
3. **给子 Agent 独立工作目录。** 临时产物写到 `/tmp` 或任务专属子目录；长期记忆对子 Agent 默认只读（用 agent 配置和工具白名单约束），写 MEMORY 只留给主 Agent。
4. **控制子 Agent 寿命。** 设轮数/超时上限，失败就带着错误信息退出，由主会话决定是否重试，不让子 Agent 自己无限挣扎。
5. **调试用独立 session key。** 手动验证子 Agent 逻辑时用单独的会话跑，别在主会话上调试——否则测试输出会永久留在主 transcript 里。

## 踩坑点

- 子 Agent 默认继承主 Agent 的系统提示和工具集，起点就很重。给它精简提示 + 最小工具集，更快也更稳。
- 并行 spawn 多个子 Agent 写同一个文件，后写覆盖先写。要么各写各的分片文件，要么串行。
- 返回契约不写进任务描述，模型默认倾向给详尽结果，"要摘要"必须显式。
- 定期看主 session 的 transcript 体积，持续增长基本意味着有内联重工具或未约束的返回值，回溯找污染源。

## 可复用建议

把上面这套约定做成团队的 spawn 模板：任务描述 + 返回契约 + 工作目录 + 超时上限。每次拉子 Agent 复制模板改参数，隔离行为就一致了，主会话能长期保持"轻"。

## 总结

session 隔离是 OpenClaw 的默认能力，但污染主会话的方式有一百种。核心原则一句话：**主会话只消费结论，过程留在子 Agent 的生命周期里。**把返回契约和写权限约束固化成模板，隔离才算真正可靠。
