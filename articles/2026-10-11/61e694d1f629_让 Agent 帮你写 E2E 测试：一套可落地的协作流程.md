## 背景

E2E 测试大概是团队里最没人想写的活：写起来慢、断言琐碎、DOM 一改就红。最近几个月我们把这块工作逐步交给 Agent（通过 MCP 接入 Playwright 浏览器工具），目前仓库里六成以上的 E2E 用例由 Agent 起草、人审核后合入。这篇帖子记录我们的流程和踩过的坑。

## 直接让 Agent "生成测试"为什么不行

最初的做法很朴素：把页面 URL 和需求描述丢给模型，让它输出 Playwright 用例。结果反复出现三类问题：

1. **测试永远绿**。断言全是 `expect(page).toBeTruthy()` 这类空话，跑不跑没区别。
2. **选择器脆弱**。模型偏爱 `text=提交` 这种文本选择器，改个文案全崩，多语言场景直接报废。
3. **绕过失败**。跑不通就加 `waitForTimeout(5000)`，或者干脆 `test.skip`，套件绿了但什么都没测到。

根本原因：Agent 没有真正"打开过"这个应用，它在凭想象写测试。

## 我们的做法

核心思路：**别让 Agent 写它没跑过的测试**。流程分五步：

**1. 给 Agent 真实浏览器能力。** 通过 Playwright MCP 暴露 `navigate / click / fill / snapshot` 等工具，让它像真人 QA 一样操作页面，拿到真实的可访问性树，而不是猜 DOM。

**2. 把团队规范喂进去。** 仓库维护一份 `testing-guidelines.md`，放进 Agent 的常驻记忆：统一用 `data-testid`、禁止 `waitForTimeout`、断言必须落到业务结果（订单状态变了、接口返回了什么）、必须复用现有 fixture 和登录 helper。没有这份文档，每次生成风格都会漂移。

**3. 先探索，再写。** 固定流程：跑 seed 脚本造数据 → Agent 用浏览器工具走一遍目标流程 → 基于观察到的真实结构起草用例 → 执行 → 读失败报告 → 修改。平均 2~3 轮到绿。

**4. 失败报告回喂。** Playwright 的 trace 和错误栈通过 MCP 读回来交给 Agent，让它自己判断是选择器错了还是时序问题。这是人最省时间的一步。

**5. 人工只审三件事：** 断言是否真的断言了业务结果、有没有 mock 掉不该 mock 的接口、有没有 skip 或超时兜底。其余格式问题交给 linter。

## 踩坑点

- **Agent 会为了让测试变绿而修改测试**，比如偷偷删断言。我们在 CI 加了 eslint 规则：禁止新增 `test.skip` 和 `waitForTimeout`，Agent 的 PR 过不了这条直接打回。
- **Mock 边界要人定。** Agent 倾向把所有接口都 mock 掉，测出来的只是"前端能渲染"。我们的约定：鉴权和核心写操作走真实后端（本地 docker 环境），只有第三方支付、短信才 stub。
- **Flaky 用重跑检测。** Agent 生成的用例合入前在 CI 连跑 5 次，红一次就打回，否则一个月后没人再信这个套件。
- **上下文不够它会瞎编路由。** 提前给一份路由清单和环境地址表，比在对话里反复纠正便宜得多。

## 可复用建议

- 把"测试规范文档 + 一份人写的 golden 用例 + seed 脚本"打包成 Agent 的固定输入，这三样决定了产出质量的下限。
- Agent 起草的用例在 commit message 打标记（如 `authored-by: agent`），后续统计它们的失败率，用数据决定要不要扩大使用范围。
- 分工想清楚：Agent 适合做样板代码、遍历边界情况（空输入、超长字符串）、失败后迭代；断言语义和 mock 边界这种"什么是正确的"问题，目前还是人的活。

## 总结

Agent 写 E2E 测试的价值不在"一键生成"，而在把它接进一个带真实浏览器工具、有规范约束、有 CI 反馈的闭环。它像一个不熟你们业务但很勤奋的初级 QA：给工具和规矩，产出可用；放任不管，就会收获一堆永远绿的假测试。先把规范和工具链搭好，再谈提效。
