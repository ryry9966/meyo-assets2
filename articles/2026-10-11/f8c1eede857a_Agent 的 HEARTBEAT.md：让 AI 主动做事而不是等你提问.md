## 背景：拉模式的局限

大多数 Agent 的交互是“拉”的：你提问，它回答，会话结束。所有需要被盯的东西——收件箱、磁盘水位、CI 状态、某个仓库有没有新提交——都依赖你先想起来去问。OpenClaw 提供了一个很轻的机制补这块：HEARTBEAT.md。本质上是给 Agent 一份“值班手册”：网关按固定间隔唤醒 Agent，Agent 读一遍手册，有事就处理并上报，没事就静默。

## 问题：被动 Agent 的三个代价

1. **状态漂移**：两次会话之间发生的事，没有任何人处理。
2. **提问负担在你**：你得记住“该问什么”。
3. **上手 cron 又偏重**：很多巡检不需要精确到分钟，只需要“定期看一眼，有异常再说”。

## 做法：三步跑起来

1. 在工作区根目录建 `HEARTBEAT.md`（默认 `~/clawd/workspace/HEARTBEAT.md`）。文件不存在时心跳直接跳过、不烧 token，所以建这个文件本身就是开关。
2. 写常驻指令。每条一个任务，祈使句，包含三要素：**检查条件 + 阈值 + 动作**。例如：
   - 检查 `~/logs/` 下是否有超过 2GB 的文件，有则压缩并告知我。
   - 每 4 小时左右扫一眼 GitHub 通知，只把和我 repo 相关的发给我，其余忽略。
3. 配置间隔。`agents.defaults.heartbeat.intervalMins` 控制唤醒频率（默认约 30 分钟）。Agent 处理完若只回 `HEARTBEAT_OK`，网关不会打扰你；只有产生实际内容才会推送。

注意边界：心跳是**条件驱动的巡逻**，不是定时器。“每天 9:00 准时发日报”这种精确调度请用 cron 任务，别塞进 HEARTBEAT.md。

## 踩坑点

- **间隔太短 = 持续烧钱**。每次唤醒都是一次真实的模型调用，5 分钟一轮一晚上能烧掉不少 token。从 30 分钟起步。
- **指令模糊 = 要么噪音要么沉默**。“帮我盯一下服务器”这种写法，Agent 要么频繁误报，要么直接忽略。必须写成可判定的条件。
- **`HEARTBEAT_OK` 必须是唯一内容才静默**。多带一句“顺便检查了一下……”就会推到你手机上。
- **紧急告警别放心跳**。30 分钟级的检测延迟不适合作 paging，真正的告警走 cron 或直接调用。
- **模型选型**：心跳负载很轻，可以在配置里给心跳单独指定便宜的小模型（`agents.defaults.heartbeat.model`），省钱效果确定。

## 可复用建议

- 用三段式模板：`CHECK <什么> / THRESHOLD <多少> / ACTION <做什么>`，比自然语言段落稳定得多。
- 冷启动只放 2–3 条，跑一周，观察哪些从未触发（条件多半写错了）、哪些频繁触发（阈值太松），再迭代。
- 文件保持一屏以内：条目越多，每次心跳的上下文越贵，误触发也越多。
- 心跳 + cron 混用，职责分清：**cron 管时间点，心跳管状态面**，噪音会小很多。
- 把“我每天手动问 AI 的重复问题”列个清单，能改写成判定条件的逐条迁进去——这是收益最高的一步。

## 总结

HEARTBEAT.md 的价值不在于自动化多炫，而在于把 Agent 从问答工具变成一个低噪音的值班进程。工程上关键就三点：条件写得可判定、间隔配得克制、紧急的事不放这里。先小步跑起来，再按触发数据迭代条目，比一次写满整页有效得多。
