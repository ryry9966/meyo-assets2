## 背景

大多数人用 Agent 的姿势仍是"你问一句、它答一句"。但 OpenClaw 的 agent 是常驻在工作区（workspace）里的，它有一个更值得挖掘的能力：**心跳（heartbeat）**。默认每 30 分钟，agent 会被唤醒一次，读一遍工作区根目录的 `HEARTBEAT.md`，决定这一轮要不要做事、要不要出声。这个文件本质上是写给 agent 自己看的值班日志。

## 问题

没有心跳机制时，周期性任务只有两条路：一是人肉记得去问，二是写死脚本用 cron 推消息。前者会忘，后者没有判断力——脚本不知道"今天没异常就别吭声"，于是一天几十条一模一样的巡检消息，很快没人看了。我们真正需要的是"**有判断力的定时器**"：到点醒一次，看一眼清单，有值得说的才说。

## 做法

1. **建清单**：在工作区根目录创建 `HEARTBEAT.md`，用 checklist 写法列任务。每条尽量写成"条件 + 动作"，例如："检查 NAS 磁盘占用，超过 85% 才报告，否则回复 NO_REPLY"。
2. **开心跳**：在配置里设置间隔与投递目标（如 `agents.defaults.heartbeat.every: "30m"`，字段名以你安装版本的文档为准），把输出 target 指到常用的 IM 渠道。
3. **跑一轮的逻辑**：agent 读清单 → 调用工具（MCP / 插件 / shell）→ 逐条判断。无事发生时回复 `NO_REPLY`，消息就不会发出去；清单为空时，较新版本会直接跳过模型调用，不产生费用。
4. **维护文件**：完成或失效的条目及时删掉、打勾，agent 也会自己更新这份文件。

我目前的真实清单（巡检类为主）：

```markdown
- 检查 NAS 磁盘与内存，异常阈值才报
- 每天早上汇总一次昨天的 git 提交与 CI 失败情况
- 盯某个仓库，有新 release 再说
```

## 踩坑点

- **最大的坑：写成无条件任务**。写"汇报服务器状态"而不是"异常才汇报"，等于每 30 分钟轰炸一次群。所有条目都要带触发条件。
- **心跳不免费**。每次唤醒都是一次模型调用，清单越长开销越大。重活交给工具：让 MCP/脚本一次性返回结构化结果，agent 只做判断，不要让它逐步探索。
- **模型对绝对时间并不可靠**。"每天早上八点"会受时区和间隔累计误差影响而漂移。真正卡点的任务，用系统 cron 触发一条"现在去做 X"的消息更稳；`HEARTBEAT.md` 适合"每天一次""有变化再说"这类模糊周期。
- **别让心跳跑长任务**。心跳占的是 agent 的会话上下文，长任务会和你正在进行的对话互相干扰。心跳任务要短平快，跑不完的活让它把进度写到文件，下轮接着干。
- **状态要落盘**。重启后对话记忆可能丢，但 `HEARTBEAT.md` 和它写的状态文件还在，不要依赖"它记得上次做到哪"。
- 清单是明文文件，**别写敏感信息**。

## 可复用建议

- 清单按三类写：**巡检类**（异常才报）、**日报类**（一天一次）、**盯梢类**（事件发生才报）。总数控制在 5 条以内，每条一句话、可验证。
- **心跳 + MCP 是标配**：`HEARTBEAT.md` 只写"何时调用什么工具、什么条件出声"，执行细节全在工具侧。
- 心跳默认克制（无事即静默），某条任务必须穿透静默强提醒的，查一下你版本是否支持强制投递的告警写法。
- 每月 review 一次：连续几周零输出的条目删掉；跑得稳定的条目，考虑固化成插件或脚本，让它从清单里"退役"。

## 总结

`HEARTBEAT.md` 的价值不在于"定时执行"——cron 早就能做——而在于把"**要不要出声**"的判断交给了模型。写好它的诀窍是克制：条件写清楚、重活给工具、清单保持短。做到这三点，agent 就从一问一答的问答机，变成一个安静但靠得住的值班员。
