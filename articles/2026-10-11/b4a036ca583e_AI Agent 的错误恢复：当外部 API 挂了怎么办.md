## 背景

OpenClaw agent 跑了一段时间后会发现一个规律：把自动化搞挂的往往不是模型，而是外部依赖。天气、搜索、行情、自建服务、各家 LLM API——任务链上挂了工具，就一定会遇到“今天那个 API 又不行了”。交互式聊天里失败顶多重问一次；但在定时任务和多步流程里，一次未处理的失败会让链路静默中断，或者更糟：模型基于错误信息编一个看起来合理的结论。

## 问题

外部 API 故障大致三类：瞬时故障（超时、429、502/503，几秒后恢复）、持续宕机（分钟到小时级）、劣化（能响应但极慢）。真正的问题不在故障本身，而在 agent 的反应：

- **无限重试**：模型收到报错的第一反应是“再试一次”，没有节奏控制，几秒内打满限流，把小故障放大成封禁级故障。
- **幻觉兜底**：报错信息太模糊时，模型倾向于脑补一个结果继续往下走。
- **半途而废**：链路走到一半断掉，既没报错也没产出，cron 看起来“跑成功了”。

## 做法

核心原则一句话：**恢复策略放在工具层（插件 / MCP server）的代码里，不要交给模型用 prompt 现场发挥。**

1. **错误分类**：插件返回统一的结构化错误，如 `{ok:false, retryable:true, code:"TIMEOUT", hint:"上游搜索服务超时"}`。可重试的（超时、429、5xx）和不可重试的（401、403、404）必须分开，别把 stack trace 原样喂给模型。
2. **有界重试**：在工具包装层做指数退避 + 抖动，比如 3 次、基数 1s、因子 2、加 0–500ms 随机；429 优先读 `Retry-After`。不要让模型自己决定重试几次。
3. **熔断**：同一工具连续失败 N 次后进入冷却期（如 60s），期间所有调用快速失败并明确返回“服务暂不可用”，让 agent 走降级路径，而不是每次调用都干等超时。
4. **降级与止损**：按优先级准备——带时间标注的缓存数据、备用 provider、部分结果（明确说明哪一步失败）。同时给 agent 一个显式的“放弃并汇报”出口：任务失败预算用完（比如累计 5 次工具失败）就停止执行，输出已完成步骤和失败原因。
5. **观测**：日志记录工具级结果码，而不只是 agent 的最终回答；熔断打开时打告警。

## 踩坑点

- **重试非幂等操作**：POST 建单接口重试三次 = 三个重复工单。写操作要么带幂等键，要么不自动重试。
- **超时不一致**：agent 框架的等待时间比 HTTP client 超时还长等于白等；反过来会出现“上层已放弃、下层还在重试”。
- **降级缓存不标新鲜度**：agent 会把昨天的数据当今天的，一本正经地汇报。
- **熔断恢复太急**：多个 agent 共用一个工具时，冷却结束瞬间流量全部涌回去，需要半开探测、分批放行。
- **错误信息走极端**：太详细（模型被 stack trace 带偏）或太模糊（只有一句 "error"，模型开始编原因）。

## 可复用建议

1. 定义一套通用的 ToolError schema，社区插件对齐后，system prompt 里只需解释一次错误语义。
2. 重试 / 退避 / 熔断做成共享中间件或包装函数，新插件一行接入，不要各写一套。
3. CI 里加一个“模拟死掉的 API”的测试用例，专门验证失败路径，像验证成功路径一样认真。
4. 每个任务设失败预算，超预算即止损上报——留给人看的那份“做到哪一步、哪里挂了”的摘要，就是最好的人机交接物。

## 总结

Agent 的可靠性不是 prompt 问题，是系统设计问题。用户感知到的“agent 不稳”，多半是某个工具包装层没写失败路径。下次给 OpenClaw 加插件时，建议先写错误处理再写正常逻辑——毕竟外部 API 挂掉不是异常，是日常。
