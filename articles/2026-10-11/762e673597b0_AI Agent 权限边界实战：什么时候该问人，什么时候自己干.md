## 背景

跑过一段时间 OpenClaw + MCP 工具链的人，迟早会撞上同一个分叉路口：Agent 到底该有多大的自主权。我在自己的自动化流水线里先后踩了两轮坑——一轮是 Agent 事事请示，一轮是 Agent 胆子太大——最后沉淀出一套按「可逆性 × 影响面」分级的做法，记录在这里。

## 问题：两个失败方向

**方向一：事事确认。** Agent 每调一个工具都弹一句「是否继续？」。头两天你还会认真看，第三天开始无脑点确定。确认机制退化成橡皮图章，人不再提供信息增量，只提供一次点击。

**方向二：完全放权。**「清理这批过期文件」「给全部客户群发提醒」「把本月预算投到 A/B 测试」——每一步单看都合理，连起来看就是事故。不可逆动作一旦没有闸门，事后补救的成本远高于事前确认的成本。

本质是：权限边界不该由「模型此刻有多自信」决定，而该由**动作本身的属性**决定。

## 做法：按可逆性 × 影响面分级

我现在的分级矩阵：

- **可逆 + 低影响**：直接执行。读文件、查库、草稿态写入，记日志即可。
- **可逆 + 高影响**：先 dry-run。批量改名、批量打标签这类操作，先输出「将影响 342 条记录」的预览，再自动执行，附带速率限制和回滚脚本。
- **不可逆 + 低影响**：规则内自动，规则外拦截。站内可撤回的消息可以自动发；对外的、发给真实用户的，一律按不可逆处理。
- **不可逆 + 高影响**：必须人工确认。删数据、花钱、对外发布、改权限改配置，都归这类。

落地时抓住三件事：

1. **工具层打标，而不是在提示词里求它。** 在 MCP 工具定义上给每个 action 标注风险等级，调用层在执行前检查标签。提示词约束会漂移，代码闸门不会。
2. **结构化确认。** 不要让 Agent 自由发挥地写「确认吗？」，用模板生成：做了什么、为什么、影响范围、怎么回滚。人审批的是一张卡片，不是一段聊天。
3. **独立硬护栏。** 每日花费上限、每小时外发消息上限、域名和频道白名单，全部独立于模型决策，超限直接熔断。

## 踩坑点

- **确认疲劳可以量化**：审批通过率接近 100%，说明问得太多，该降一档；频繁被驳回，说明分级错了。
- **别让 LLM 自己措辞确认请求**。它会（往往是无意识地）把问题写得偏向「同意」。确认内容必须由系统从工具参数生成。
- **人不在时怎么办要提前定**。我的策略是默认拒绝、状态挂起、人回来后可续。默认继续是事故放大器。
- **批谁就执行谁**。确认通过后要执行「被批准的那件事」，不是「一件类似的事」。审批快照和执行动作要绑定。
- **自动执行也要全量日志**。否则事后审计无从谈起，「自动」就等于「黑箱」。

## 可复用建议

- **先严后松**。上线时全走确认，攒两三周日志后，把「从未被驳回」的动作降级为自动。反过来先松后紧，代价高得多。
- **权限策略写成配置文件**，进版本库，像 review 代码一样 review 它。
- **每周花十分钟翻自动执行日志**，这是整套体系里性价比最高的动作。

## 总结

权限边界不是「信不信任模型」的态度问题，而是系统工程问题：用可逆性和影响面给动作分级，把闸门放进代码而不是提示词，让确认请求结构化、且足够少。确认机制的价值在于稀缺——问得越少，每一次「问」才越有分量。
