## 背景

在 OpenClaw 的 agent 链路里，模型调用是成本和延迟的最大变量。云端大模型（GPT-4o / GPT-4.1 这类）推理强、上下文长，但按 token 计费、有延迟和限流；本地模型（Ollama / vLLM 跑 Qwen、Llama 系列）近乎免费、数据不出门，但长链路工具调用容易掉链子。多模型路由的意义不是炫技，而是把贵的算力花在刀刃上。

## 问题

我们有一个跑消息摘要 + 定时任务的常驻 agent，全量走 GPT 时月度 token 账单难以接受；全换本地小模型后，复杂任务的 MCP 工具调用成功率明显下滑。核心矛盾在于：同一个 agent 的不同环节，智力需求差异很大，用单一模型必然是“要么浪费、要么不够”。

## 做法与步骤

1. **主模型定调**：规划、长上下文、多步工具链交给云端模型，配置在 `agents.defaults.model.primary`。
2. **子任务下沉**：摘要、分类、改写、模板化输出这类高频低难度任务，通过子 agent 或工具级 model 覆盖指到本地模型（如 `qwen2.5:14b`）。
3. **fallback 兜底**：fallback 链按需排序（先本地后云端，或反过来），避免主模型限流时任务整体挂掉。
4. **用 eval 验证**：准备 20~50 条真实任务样本，跑路由前后的成功率对比，用数据决定切分边界，而不是拍脑袋。

示意配置（字段名以所用版本为准）：

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4.1",
        "fallbacks": ["ollama/qwen2.5:14b"]
      }
    }
  }
}
```

## 踩坑点

- **上下文窗口错配**：本地模型窗口小，长对话被 truncate 后丢关键约束，表现为“重复提问”或“忘记输出格式”。路由前先确认任务的实际 token 长度。
- **工具调用格式差异**：部分本地模型的 function call 输出不稳，OpenClaw 解析失败会静默重试，日志里要盯 `tool_call_failed`，别只看最终回复。
- **fallback 循环**：主备模型互相踢皮球会打满重试次数，务必显式设置 max retries，并对 fallback 触发加告警。
- **风格跳变**：不同模型 tokenizer 和温度敏感度不同，路由切换后输出风格变化用户可感知。摘要类任务建议统一锁定 temperature。

## 可复用建议

一句话判据：**要“想”的给 GPT，要“跑”的给本地。** 具体切分：

- 云端：任务规划、代码生成、跨文件检索、模糊指令理解；
- 本地：摘要、分类、翻译、固定模板生成、隐私敏感内容预处理。

另外两条经验：路由规则宁少勿多，先二分（云/本地）再细分，规则一多排查成本指数级上涨；每次调整路由都重跑一遍 eval 集，没有对比数据就不要上线。

## 总结

多模型路由本质是在成本-质量曲线上人工选点。建议路径：先跑通单一模型基线，量化成本和成功率，再按任务类型切分，边测量边收敛。不要一上来堆一堆路由规则——规则越少，系统越可解释，出问题时也越快定位。
