## 背景

社区里用 Agent + MCP 做内容自动化的同学越来越多了。典型流程是：LLM 生成一篇 Markdown 技术稿，然后发到公众号、知乎、掘金、GitHub。听起来是"写一次发多处"，真做起来会发现，Markdown 只是看起来通用——各平台渲染器的方言差异比想象中大得多。

## 问题在哪

三个层面：

1. **平台侧**。公众号编辑器不认 Markdown，只接受带内联样式的 HTML，还会过滤部分标签和属性；知乎、掘金的支持各有限制；`<details>`、脚注、数学公式，没有一个平台全收。
2. **生成侧**。LLM 输出不稳定：标题层级随手写、表格单元格里塞管道符、代码块里嵌套反引号，这些都会让下游解析翻车。
3. **资产侧**。图片是重灾区。AI 给的多是占位符或外链，而多数平台要求图片上传到自家素材库。

## 做法

我们的管线分五步，核心原则是**所有处理基于 AST，不碰正则**：

**1. 生成端立契约。** 在 system prompt 里明确：只输出 GFM；全文唯一一级标题；禁止裸 HTML 和脚注；图片一律写占位符 `![img-1](placeholder://img-1)`。契约越死板，下游越省心。

**2. 统一中间表示。** 用 unified/remark 把 Markdown 解析成 mdast，后续所有变换都在这棵树上做。它是整个管线的单一事实来源。

**3. 平台适配器。** 每个目标平台一个 transform 插件。公众号走 remark-rehype 再注入内联样式（doocs/md 的思路可参考）；掘金、知乎主要做裁剪降级，比如把不支持的节点替换成引用块；GitHub 近乎原样输出。

**4. 资产同步。** 遍历 image 节点：下载 → 通过 MCP 工具上传到平台素材库 → 回填真实 URL。上传失败时保留原路径并打标记，绝不静默丢图。

**5. 校验与 dry-run。** markdownlint 管通用结构，自写规则管平台约束（比如"公众号版本不允许出现 details 节点"），最后渲染 HTML 预览，人工确认后再发。

## 踩坑记录

- 最早用正则替换图片链接，结果代码块里的示例 URL 也被改了。切到 AST 后按节点类型处理才干净。
- 公众号会吞部分 CSS 属性，`position` 直接消失；表格样式必须内联到每个 `td`，写 class 无效。
- 模型偶尔在代码块里用四个反引号嵌套三个反引号，解析直接乱套。契约里要写死"代码块只用三个反引号"。
- front matter 忘了剥离，原样进了公众号，变成正文开头一段 `---` 神秘文本。
- 知乎没有稳定的公开文章 API，只能走浏览器自动化。这里别追求全自动，保留一步人工确认。

## 可复用建议

- 把"发布契约"做成 prompt 模板，和适配器一起版本化管理，改契约必须过回归测试。
- 平台差异沉淀成一张 quirks 表，接新平台先补表再写代码。
- MCP 工具粒度拆细：上传图片、提交草稿分开，agent 失败时才能精准重试。
- dry-run 产物永远落盘，出问题直接 diff 定位。

## 总结

这套管线的价值不在于"一键分发"，而在于把格式的不确定性收敛到一个 AST 层：生成端用契约压住模型的随意性，中间层用适配器隔离平台方言，发布端保留人工确认。自动化的边界想清楚，管线才跑得稳。
