# 背景

OpenClaw 的 agent 不是常驻等消息的进程，而是被事件唤醒的：用户消息、定时心跳（heartbeat）、插件回调。heartbeat 本质是「每 N 分钟醒一次，看看 HEARTBEAT.md 里有没有要办的事」。听起来像 cron，区别在于唤醒时带着完整会话上下文，可以读文件、调工具、自主判断做不做。

做自动化很快会撞到同一个问题：哪些事靠心跳轮询，哪些事改成推送？

# 两种机制的边界

**轮询（heartbeat）**：实现最简单，不需要公网入口，天然有兜底语义。代价是延迟和成本的权衡——间隔短，token 和调用次数涨得很快，且大多数唤醒是空转；间隔长，事件延迟不可控。

**推送（webhook / 插件回调）**：延迟低、按需唤醒，token 只花在真事件上。但要求一个可达且可信的入口，鉴权、payload 校验、防重放都得自己做；上游没有回调能力时，这条路直接不通。

# 我的做法

1. **先给事件源分类**。CI 结果、git、监控告警这类有回调能力的走推送；网页状态、无回调的第三方 API、本地文件变化走轮询。
2. **心跳间隔保持保守**（默认 30 分钟），把它当兜底而不是主通道。高频需求用外部 cron 或 webhook 精确唤醒，而不是缩短全局心跳。
3. **HEARTBEAT.md 只放「需要主动检查的清单」**，其余进常驻记忆。清单为空时 agent 直接跳过，一次空心跳成本接近零。
4. **推送入口做三件事**：签名鉴权、幂等键去重、限流。payload 只发事件指纹（类型 + ID + 时间戳），细节让 agent 自己拉，避免大 JSON 白占上下文。
5. **记录每次唤醒的触发源和 token 消耗**，每周看一次空转率。

# 踩坑点

- **在心跳里干重活**。单次心跳跑十分钟，下一次触发被排队或超时。重活应落成任务交给后台执行，心跳只负责发现和分派。
- **推送风暴**。上游一次抖动推来几十条 webhook，没去重直接把当日 token 打穿。幂等键是必须项，不是可选项。
- **轮询太勤快**。每次心跳全量拉数据，实际九成轮次状态没变。先查一个便宜的状态位（文件 mtime、版本号），有变化再拉详情。
- **别假设心跳等间隔**。设备休眠、容器调度都会让心跳漂移，依赖「精确每 5 分钟」的逻辑迟早翻车。

# 可复用的判断标准

- 事件延迟容忍 > 心跳间隔：轮询足够，别过度设计。
- 需要秒级响应：上推送，入口做好鉴权和去重。
- 混合场景（大多数真实情况）：推送触发 + 心跳兜底，两层都留着。
- 无论哪种：盯住空转率和单次唤醒成本，这两个数字会告诉你设计是否合理。

# 总结

轮询和推送不是二选一，而是分层：心跳负责「我不会漏」，推送负责「我来得快」。先用最粗的心跳跑起来，等空转率或延迟真的成为问题，再针对具体事件源加推送通道。先测量再优化，比一上来就搭完整事件系统便宜得多。
