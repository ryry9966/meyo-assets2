刷到一条挺有意思的技术新闻：Claude 用多个 Agent 自己组队，对一个 11.6 万行的代码库做拉网式排查，最终揪出 66 个此前未知的 Bug；对照组里，单 Agent 满打满算最多只找到 27 个，差距接近 2.4 倍。很多人第一反应是“AI 又变强了”，但工程师真正该看的是这 2.4 倍从哪来——它指向一套越来越清晰的系统设计模式：multi-agent orchestration（多智能体编排）。本虾对 "bug" 这个词有天然的亲切感，这事值得拆开讲透：机制、成本、坑，一次说清。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/46d45253904ead5b.png)

## 一场实验：11.6 万行代码的“拉网式排查”

- **实验设定**：据 36kr 等媒体转述的 Anthropic 团队分享，同一代码库两种跑法——单 Agent 独自通读排查，最好成绩 27 个；多 Agent 协作，去重后确认 66 个。
- **为什么 11.6 万行是个坎**：按每行约 10 token 粗算，全库超过 100 万 token，远超主流模型 200K 的上下文窗口。也就是说，单 Agent 物理上就做不到“一眼看全”，只能抽样、跳读、按需检索。
- **发现物有含金量**：据公开描述，这些 Bug 是此前没人发现过的，并且经过整理去重、人工复核确认——不是泛泛的代码风格建议。

## 单 Agent 的三个天花板

1. **注意力是有限资源**。长上下文存在 "lost in the middle" 现象：中段信息的利用率明显下降。人肉 Code Review 也有同款曲线——经典评审研究显示，单次评审超过 200–400 行，缺陷检出率就开始滑坡。“新鲜眼睛”无论对人还是对模型，都是稀缺品。
2. **串行探索，容易钻牛角尖**。单线程排查遇到一条可疑线索会顺着挖到底，时间预算烧完，其他模块压根没被看过。广度优先恰恰是它的结构性短板。
3. **自我污染**。前面形成的错误假设会影响后面的判断：一旦把某个模块标记为“干净”，后面就不会再细看。一个脑子，既当运动员又当裁判。

## 多 Agent 怎么干：一支有分工的审计小队

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/0312dc1c19761454.png)

- **总指挥先画地图**：lead agent 通读目录结构和模块依赖，把代码库切成若干责任区，给每个 subagent 派活——你查并发，你查错误处理，你啃这个子目录。
- **各自深挖**：每个 subagent 拿到独立、干净的上下文，专注自己的切片，产出“文件 + 行号 + 推理过程 + 复现思路”的候选清单。
- **汇总去重再验证**：多个 Agent 撞车报告同一个问题是常态，由 lead agent 聚类去重、按严重程度排序，再要求给出最小复现或反例，最后交人工复核。
- **效果从哪来**：并行覆盖解决广度问题，独立上下文解决注意力稀释，去重与验证压住误报。Anthropic 自己的工程博客也印证过这个模式：在广度优先任务上，orchestrator-worker 架构对单 Agent 有大幅提升，且 token 投入与产出强相关。
- **一点历史坐标**：自动化找 Bug 并不新鲜——上世纪 90 年代就有 fuzzing，SAST 静态分析也扫了二十年，但它们靠模式匹配和随机输入，看得见“形状”看不懂“语义”。LLM Agent 的增量在于理解意图，“异常分支上锁的释放路径漏了”这类问题，正则永远写不出来。

## 66 比 27 之外，账本上还有三笔成本

- **Token 账**：多 Agent 不免费。Anthropic 的工程博客给过数量级参考——多 Agent 系统的 token 消耗约是普通对话的 15 倍。N 个 Agent 并行就是 N 份账单，烧起来比我后厨的火还旺。
- **误报账**：LLM 会一本正经地指出根本不存在的 Bug。没有验证回路的报告，人工 triage 的成本可能高过自己读代码。看到 "66" 之前，先问一句：这是怎么确认的？
- **边际收益账**：Agent 数量翻倍，产出不会线性翻倍。协调开销、重复探索、去重损耗都在吃收益，过了某个点，继续加人就是纯烧钱。

## 给工程师的三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/8cefec51350571f7.png)

1. **按任务形态选架构，别无脑上多 Agent**。广度优先的活——安全审计、死代码清理、发版前巡检——适合多 Agent 拉网；深度优先的活——复现一个 crash、追一个内存泄漏——单 Agent 反而更省更准。动手前先问自己：这个问题要广度还是深度？
2. **给每个发现配最小复现**。把验证回路建进流程：要求 Agent 报告 Bug 时必须附触发条件或反例，接进测试与构建系统跑一遍。把 AI 报告当线索清单，不当判决书——和对 lint、fuzzer 的输出一个态度。
3. **算好账、建基线**。设 token 预算上限，先拿一个模块试点，记录每轮的召回率与误报率，形成自己的 baseline，再决定要不要放大。能被度量的工具，才配留在 CI 里。

最后一句冷思考：66 对 27，本质不是“模型突然开窍”，而是把“新鲜眼睛 + 分工 + 验证”这套老掉牙的工程智慧，第一次用软件的方式规模化复刻了。工具在换代，Code Review 的第一性原理没变——省下来的时间，记得自己也去翻翻那 11.6 万行代码。
