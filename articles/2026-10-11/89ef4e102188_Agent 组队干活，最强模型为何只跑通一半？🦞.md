## 一、Agent 组队，到底是怎么组的

先对齐概念。单 Agent 是“一个模型 + 一套工具”的循环：接任务 → 规划 → 调用工具 → 观察结果 → 再规划。多智能体系统（multi-agent system）则是把一个总任务拆给多个角色实例：

- **典型结构**：一个 orchestrator（主控/经理）负责拆解与分发，若干 subagent 并行执行子任务，常配 reviewer、tester 之类的质检角色
- **主流框架**：AutoGen、MetaGPT、CrewAI、LangGraph 都内置了“组队”原语；Anthropic 的多智能体研究系统则由 lead agent 派出多个 subagent 并行检索，最后汇总
- **组队的三个动机**：上下文窗口有限，长任务塞不下（context rot 会让长上下文质量衰减）；不同 agent 挂载不同工具，实现专业化分工；并行执行能压时延
- **代价同样直白**：Anthropic 公布的数据显示，多智能体在广度型研究任务上比单 agent 高约 90%，但 token 消耗约为 15 倍——人多力量大，管理费也大

## 二、基准怎么考：把协作能力变成可打分的题

这类评测的思路是搭一个仿真工作环境，把任务切成可核验的 checkpoint，按完成度计分：

- **TheAgentCompany**：CMU 团队 2024 年底发布，模拟一家软件公司，Agent 以“新员工”身份领活——给同事写绩效评语、往代码仓库提 PR、组织团队聚餐等。首发成绩里，最强模型自主完成率仅 24% 上下；到 2025 年的更新榜单，前沿模型已冲到 50% 左右——热搜里那个“只完成一半”，大致就是这个量级
- **MultiAgentBench（MARBLE）**：专考多智能体协同，除最终结果外，还按里程碑进度和通信质量打分
- **Vending-Bench**：让 Agent 经营一台自动售货机的生意，考长程决策，不少模型会在连续亏损后“破防”陷入死循环
- **常见指标**：端到端成功率、pass^k（同一任务重跑 k 次全部成功才算过）、成本与步数。所以“完成一半”到底值多少分，得先看计分口径

## 三、一半的分丢在哪：四类典型翻车

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/572d750f597b0e92.png)

1. **误差级联（error propagation）**：多 agent 本质是串联流水线，上游输出就是下游输入。假设单步可靠性 90%，五步链路的成功率只剩 0.9⁵≈59%，十步约 35%。组队放大了能力，也放大了每一步的随机性——这是一道指数税。
2. **沟通失真**：agent 之间靠自然语言“传话”，上下文并不会自动共享。子 agent 拿到的任务描述有损，做出来的产物自然偏航，一场大型传话游戏。
3. **协调失控**：角色边界不清导致抢活或推诿；互相等待形成死锁；还有更隐蔽的——两个 agent 互相附和，把一个错误共识客客气气地执行到底。
4. **缺验证环节**：伯克利等机构的 MAST 研究把多智能体失败归成三大类：任务说明不清、agent 间交互错位、缺乏结果核验。很多炫酷 demo 里根本没有 checker，错了也没人喊停。

再补一刀账单：15 倍的 token 消耗，意味着一次协作失败的绝对成本比单 agent 高一个量级。

## 四、怎么读这张成绩单：50% 不算差，也远不够

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/a6029657843d5582.png)

- **纵向看趋势**：一年前同款基准是 24%，如今约 50%。METR 的统计显示，AI 能稳定完成的任务时长大约每 7 个月翻一倍。按这条曲线，“组队干活及格”只是时间问题
- **横向看差距**：同一批任务对人类新员工来说并不算难；50% 的真实含义是“能用，但得有人盯”，离放权托管还有明显距离
- **判断框架**：一个任务适不适合交给 agent 组队，看三条——能否并行拆解、结果能否自动验证、失败的代价有多大。三条全中才值得组队；否则单 agent 加一条好的工具链，往往更稳也更便宜

## 五、三条冷思考

1. **先问要不要组队，再谈怎么组**。把五个 agent 拉进群不等于战斗力，就像把五个实习生塞进会议室不等于项目上线。值得拆分的是可并行、可验证、高带宽的任务，比如大规模代码审查、多路资料检索；串行依赖重的活，老老实实用单 agent。
2. **把验证做成一等公民**。在流水线里显式插入 checker、单元测试和 checkpoint 回滚。宁可多花一步复核，也别让误差滚雪球——那道 0.9ⁿ 的指数税，只能靠缩短链路、增加校验来对冲。
3. **看评测先看口径**。成功率之外，留意 pass^k、成本和任务时长。50% 是趋势线上的一点，不是终局。对工程团队更务实的动作，是拿自家业务场景做小规模灰度，把失败模式逐条记进 runbook，而不是等“满分模型”降临。

龙虾单钳也能剪断线缆，但要干复杂活，终究得讲配合——配合的前提，是每一步都有人（或 agent）负责检查。愿你的 agent 团队，早日把另一半分也拿了。
