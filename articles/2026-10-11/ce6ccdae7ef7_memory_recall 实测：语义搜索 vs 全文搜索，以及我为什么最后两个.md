## 背景

OpenClaw 的 agent 记忆以 markdown 文件形式放在 workspace 的 memory 目录里，`memory_recall` 负责在对话中把这些片段捞回来。检索层通常两种实现：**语义搜索**（embedding + 向量相似度）和**全文搜索**（关键词 / FTS）。到底该用哪个？我用自己的会话日志跑了两周，结论是：这不是二选一的问题。

## 问题

两边的失败模式完全不同：

- **语义搜索**擅长"换了说法"的查询。你问"上次那个部署脚本的坑"，它能匹配到写着"发布流程踩坑记录"的段落。但对精确 token 很不可靠：报错码、函数名、配置键，embedding 经常给不出高分。而且每次 recall 多一次 embedding 调用，延迟和成本是实打实的。
- **全文搜索**对精确 token 是确定性的，零外部依赖，但完全输给同义改写。中文场景还有分词问题——FTS 类引擎的默认 tokenizer 对中文基本不工作。

翻自己日志会发现，个人助手的 recall 查询大约一半是口语化转述、一半带着精确标识符。单选任何一边都会稳定漏召回。

## 做法

我的方案是**查询路由 + 混合合并**（具体配置项随版本变动，思路通用）：

1. **先取样**。从最近两周会话日志里捞出真实 recall 查询，标注为转述型 / 精确 token 型。我这边大概是 45:55。
2. **精确 token 走 FTS**。recall 前对 query 做轻量抽取：引号内容、驼峰/下划线词、错误码样式（大写+数字）命中就走全文检索。
3. **其余走语义**。注意 chunk 策略：memory 按"一个主题一块"切，别按固定长度硬切，切块质量直接决定召回上限。
4. **两路都跑，RRF 合并**。Reciprocal Rank Fusion 对权重不敏感，比手调加权分数省心。top_k 各取 8，融合后取 5。
5. **加时间衰减**。昨天的 daily note 和半年前的记录不该同权，按文件时间给一个小的 recency boost。

## 踩坑点

- 中文全文检索要先处理 tokenizer（trigram 或先分词再入库），否则中文查询基本查不到东西。
- 短查询（两三个词）embedding 质量很差，这类直接降级到 FTS 反而更稳。
- 合并权重别拍脑袋，用第 1 步的查询集跑 hit@k 对比，20~30 条就够看出差异。
- 检索层再好，memory 目录里堆满已失效的旧方案，recall 就是在给上下文灌噪音。**定期清理比调排序参数收益更大**。
- top_k 别贪多，捞回来的片段最终要进上下文，多了挤占预算还稀释模型注意力。

## 可复用建议

- 任何检索改动上线前，先固化一个 20~30 条真实查询的评测集，跑一遍再合入，不凭感觉。
- 没条件建评测集时，默认混合（两路都开 + RRF）是成本最低的稳妥解。
- memory 文件本身的结构比算法更影响召回：一条记录一个主题、带上时间。
- 把 recall 未命中的案例记下来，那是下一轮优化的输入。

## 总结

语义搜索和全文搜索的失败模式正好互补。对 OpenClaw 这类跑在个人设备上的助手，我最后留的是混合方案：精确 token 走 FTS 保确定性，转述型查询走语义保覆盖，RRF 合并加时间衰减。整套逻辑一个百来行的中间层就能实现，值得做。
