## 背景

做 Agent 开发有个现实的痛点：调试循环烧 API 费用，涉及本地数据不敢上云，自动化任务半夜跑还得看限流。本地部署大模型的价值不是和云端旗舰比智力，而是给自己的链路一个免费、可离线、数据不出门的常驻推理节点。这篇记录我把本地模型接进 OpenClaw 工作流的完整过程。

## 问题

动手前先想清楚三个问题：

1. 你这台机器到底能跑多大的模型？
2. 用哪个推理框架，怎么暴露成标准 API？
3. 本地模型能否稳定支撑 Agent 的工具调用（function calling）？

## 做法与步骤

**第一步：摸清硬件。** NVIDIA 显卡看显存：8GB 可跑 7B/8B 的 Q4 量化；12GB 能上 14B；24GB 可以试 32B Q4。Mac M 系列靠统一内存，32GB 跑 14B 很从容。纯 CPU 也能跑，但 token 速度只够做文本处理，撑不起多轮 Agent。

**第二步：选运行时。** 推荐路径是先用 Ollama 跑通——一条命令拉模型，自带 OpenAI 兼容 API。遇到吞吐瓶颈再考虑 vLLM（需要大显存，胜在并发），或 llama.cpp（可控性最强）。

**第三步：选模型。** 中文 + 工具调用综合表现比较稳的是 Qwen 系列，7B 起步，14B 起明显可用。量化优先 Q4_K_M，这是体积和质量的平衡点，别追 Q2，工具调用的 JSON 输出会明显劣化。

**第四步：接入 OpenClaw。** Ollama 默认监听 11434，容器里的 Agent 要访问它，记得把 `OLLAMA_HOST` 设为 `0.0.0.0`，然后把模型配置的 base_url 指向 `http://<host>:11434/v1`。接好后先跑最小闭环：建一个只挂 1–2 个 MCP 工具的 Agent，验证模型能否正确生成工具调用参数，通过了再加复杂度。

## 踩坑点

1. **上下文静默截断。** Ollama 默认上下文很短，Agent 的系统提示加工具描述很容易超限，表现为“模型忘了自己有工具"。务必手动设 `num_ctx`。
2. **小模型的工具调用很脆。** 7B 以下模型在多工具场景常输出不合法 JSON 或编造参数名。工具描述写短写精确，必要时减少并行挂载的工具数量。
3. **KV cache 比模型参数更吃显存。** 长上下文配大 `num_ctx` 会直接 OOM，且报错信息不明显。显存紧张时先砍上下文，再考虑换小模型。
4. **并发默认排队。** 多个 Agent 同时打本地端点会互相阻塞，调高 Ollama 并行参数或迁移 vLLM 才能缓解。

## 可复用建议

- **用真实任务做基准。** 同一个 Agent 任务在云端和本地各跑十次，统计工具调用成功率，别信通用榜单。
- **混合路由最划算。** 文本整理、分类、摘要走本地，关键规划和复杂工具调用走云端，OpenClaw 里按任务配不同模型即可。
- **固定模型版本号。** 量化模型一更新行为就可能漂移，prompt 要跟着重测。

## 总结

本地部署不是替代云端，而是给自动化链路加一个不花钱、可离线的兜底节点。从一台 8GB 显存的机器加一个 8B Q4 模型开始，先跑通最小 Agent 闭环，再逐步放大。把「稳定复现的工具调用」当作唯一验收标准，就不会跑偏。
