## 背景

OpenClaw 的 Agent 本身只会"想"，真正能"做"依赖外部工具：调 HTTP API、查数据库、触发自动化。社区里最常见的落地形态，是给 Agent 挂一个 MCP server 或自定义插件，把某个外部服务的几个端点包装成可调用的工具。听起来简单，但"能调通"和"稳定可用"之间差着不少工程活。

## 问题

我们对接内部工单系统和两个公开 API 时踩过一轮，典型症状：

1. 工具描述写得太模糊，模型在该传 ID 的地方传了名字；
2. 上游超时后 Agent 盲目重试，非幂等接口产生了重复提交；
3. 把上游几千行 JSON 原样塞回上下文，几轮对话就把 token 烧光；
4. 密钥写在插件配置文件里，一次截图分享差点泄露。

本质是：Agent 层和 API 层之间缺一个"握手协议"——谁负责鉴权、谁负责重试、错误怎么翻译成模型能理解的语言。

## 做法与步骤

后来我们沉淀出一套薄适配层模式：

1. **收敛工具面**。不要把整个 API 透传给 Agent，只暴露 3~5 个语义清晰的高频操作，每个工具配一句动词短语级的 description，参数格式写进描述里。
2. **写薄适配器**。用 MCP server 或插件包一层，负责注入鉴权头（密钥走环境变量）、设置 8~15 秒超时、统一重试策略。
3. **裁剪响应**。适配器只返回模型决策需要的字段（状态、关键 ID、错误码），大 payload 落到文件或缓存，给 Agent 一个引用路径即可。
4. **翻译错误**。401/429/5xx 分别映射为明确语义："凭证失效，请重新配置" / "限流，稍后再试" / "服务异常，已停止重试"。模型拿到结构化错误才不会瞎猜。
5. **幂等保护**。所有写操作带客户端生成的请求 ID，重试时复用同一个 ID，让上游去重。
6. **夹具测试**。用录制好的响应做离线回归，改 prompt 或换模型版本后跑一遍，确认工具调用行为没漂移。

OpenClaw 侧只需在 agent 配置里声明 MCP server 入口，密钥用环境变量注入，不进配置文件、不进日志。

## 踩坑点

- **HTTP 200 ≠ 成功**。不少服务把业务错误藏在 body 的 code 字段里，适配器必须先解包再返回，否则 Agent 会把失败当成功继续往下走。
- **重试只对幂等接口开**。读操作可以指数退避，写操作宁可把错误抛回给模型，让它去问用户。
- **分页别让模型循环翻页**，适配器里一次聚合完再返回摘要，省 token 也省轮次。
- **参数校验放适配器里做**，报错信息写清"期望什么格式"，模型的自我纠错能力比想象中好。

## 可复用建议

- 工具数量控制在 5 个以内，description 里带一个调用示例；
- 密钥全部走环境变量，日志对 header 脱敏；
- 统一超时 + 退避，写操作带幂等键；
- 返回给模型的响应裁到 1KB 以内；
- 错误三分类：可重试 / 需换参数 / 需人工；
- 有离线夹具测试，升级模型后回归一遍。

## 总结

对接外部服务的关键不是"接上"，而是把鉴权、重试、错误语义、响应裁剪这些脏活挡在适配层里，让 Agent 只面对一个干净、诚实、小而美的工具面。适配层越薄、约定越明确，Agent 的行为就越可预测。这套模式我们在两个场景跑了一个多月，故障基本收敛在"上游真挂了"这一类，而不是 Agent 自己折腾出来的。
