# Agent 与 API 的握手：OpenClaw 怎么对接外部服务

## 背景

Agent 本身只会推理，真正“能做事”靠的是工具调用。在 OpenClaw 的体系里，对接外部服务主要有两条路：走 MCP 接现成的 server，或者自己写插件注册工具。无论哪条路，本质都是同一件事——把一个不稳定、有状态、有权限边界的外部 HTTP 世界，包装成 Agent 可以安全、确定地调用的接口。这个“握手”做得好不好，直接决定 Agent 的上限。

## 问题

实践里最常见的翻车，大多不在模型，而在工具层：

1. **鉴权与密钥**：API key 写进提示词或配置被日志带出，甚至被模型原样复述到输出里。
2. **契约不一致**：工具描述含糊，Agent 按自己的理解编参数，请求发出去了，结果和预期完全对不上。
3. **失败处理缺位**：超时、限流、部分成功被当成成功，重试非幂等接口造成重复下单、重复发消息。

## 做法

我们在内部项目里沉淀了一套五步流程：

**第一步，划边界。** 一个工具对应一个明确动作。宁可选 `list_orders` + `get_order_detail` 拆开，也不要一个 `do_everything`。粒度粗了模型容易乱用，细了上下文会被无意义的工具列表撑爆。

**第二步，把 schema 当合同写。** 注册工具时参数类型、必填项、枚举值、边界条件写全。工具描述要像 API 文档，不要像宣传语——描述越准，模型编造越少。

**第三步，凭证不下放。** 密钥只放在工具进程的环境变量里，Agent 拿到的永远是调用结果，不接触原始凭证。

**第四步，出口统一。** 超时、重试（只对幂等操作）、限流、错误码归一化，全部在工具层收口，不要指望模型自己判断“该不该再试一次”。

**第五步，返回值裁剪。** 结构化返回关键数据，截断超长内容。把第三方接口 500 报错的整页 HTML 回灌给模型，既浪费 token，也是注入入口。

## 踩坑点

- **重试了不该重试的接口。** 下单类接口自动重试三次，客户收到三单。现在所有写操作默认不自动重试，改为显式确认。
- **API 响应原文直接回灌。** 第三方返回的文本里可能夹带指令式内容，属于典型的间接注入。响应先过一层清洗和结构化再进上下文。
- **只测了 happy path。** 上线前用错误 key、断网、超长响应各跑一遍，比任何 prompt 调优都更能暴露问题。
- **工具描述写得太“强”。** 模型会高估能力，在不适用的场景硬调用。描述克制一点，失败率反而下降。

## 可复用建议

- 每个外部服务一个独立工具进程或沙箱，权限最小化，单点故障不拖垮全局。
- 日志记录调用参数与状态码，密钥一律脱敏。
- 写、删、支付类敏感操作，加 dry-run 参数或人工确认钩子。
- 工具层维护一份变更记录，上游 API 改字段时能快速定位影响面。

## 总结

Agent 对接外部服务，做的是“翻译”工作：把不可控的外部世界，翻译成可控的确定性接口。模型负责决策，工具层负责兜底。OpenClaw 生态里 MCP 和插件机制给了足够的扩展空间，但可靠性这件事，八成取决于工具层做得严不严。先把手握牢，再谈放手让 Agent 跑。
