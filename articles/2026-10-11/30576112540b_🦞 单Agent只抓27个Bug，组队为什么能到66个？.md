最近技术圈刷屏一条新闻：Anthropic 让一群 Claude Agent 自己“组队”做安全审计，扫了约 11.6 万行代码，揪出 66 个此前未知的 Bug；而对照组里，单个 Agent 硬着头皮单干，最好成绩是 27 个。同一批模型，组织方式一换，战绩直接翻倍。这不是“AI 又变强了”的故事，而是一个很经典的工程命题：当单个节点的能力撞上天花板，系统架构怎么救场。今天把这件事拆开看。

## 一场 11.6 万行代码的“团战”是怎么回事

先把事实层面摆清楚（细节以官方博客与公开报道为准）：

- **审计对象**：多个真实代码库，合计约 11.6 万行，规模相当于一个中型工程项目
- **结果**：多 Agent 系统累计报出 66 个此前未知的缺陷，其中包含若干有实际利用价值的安全漏洞，交由人工复核与修复
- **对照实验**：同样的模型做单 Agent 审计，最好成绩 27 个，约为多 Agent 的四成
- **验证流程**：Agent 的发现还要经过去重、压误报的验证环节，最后才落到人类工程师桌上

两个容易忽略的细节值得划重点：其一，对比用的是同一个模型，唯一变量是“组织方式”；其二，这不是营销演示，而是一次控制变量的对照实验。所以真正值得讨论的问题不是“Claude 多厉害”，而是“多 Agent 组织到底解决了什么”。

## 单 Agent 的天花板：不是不聪明，是“拿不动”

让一个单 Agent 查 11.6 万行代码，会同时撞上三堵墙：

1. **上下文窗口装不下**。按代码平均每行 8~12 个 token 粗算，11.6 万行就是一百多万 token，而很多主力模型的上下文仍在 20 万 token 量级（少数支持百万级）。也就是说，单 Agent 物理上无法把代码库“整体拿在手里”，只能抽样式地翻，翻到哪算哪。
2. **注意力被稀释**。长上下文存在著名的 "lost in the middle" 现象：模型对开头和结尾的内容记得牢，中段容易被忽略。找一个藏在代码中段的 off-by-one 错误，对单 Agent 来说是逆风局。
3. **探索是串行的**。单 Agent 同一时刻只能追一条假设线索：查内存泄漏就顾不上竞态条件，追输入校验就得放下权限逻辑。串行探索的麻烦在于——你不知道漏掉的那条线，是不是正好藏着大鱼。

打个比方：让一个人通读整座图书馆找错别字。他不是不认真，是根本读不完。

## 组队之后：一个编排者，一群侦察兵

多 Agent 方案的骨架，工程师会觉得很眼熟——本质是把 map-reduce 搬进了 LLM 世界：

- **侦察**：编排者 Agent（lead agent）先通读项目结构，画出“地图”：有哪些模块、哪些依赖、哪些历史高危区
- **分工（map）**：把代码库切成若干片区，每个子 Agent 领一份限定任务，比如“只查这个模块的内存安全问题”。任务边界越清晰，单点的搜索密度越高
- **汇总（reduce）**：子 Agent 返回压缩后的结构化报告，编排者负责去重、合并、按严重程度排序
- **验证**：独立的 Agent 对每条疑似发现做复现与交叉质证，尝试构造可触发的复现路径，压掉误报后再交给人

这套思路并不新。1986 年 Minsky 在《社会的心智》（Society of Mind）里就提出，智能可以由大量简单单元协作涌现；亚当·斯密的制针厂分工理论更是两百年前的事。变化在于：以前的“单元”是人写的启发式规则，现在是能自主调用工具的模型实例。

补一个数据点：Anthropic 早前发布的“How we built our multi-agent research system”报告中，编排者+子 Agent 架构在内部评测上比单 Agent 高出 90.2%，且分析发现 token 消耗量能解释约 80% 的性能差异——多 Agent 系统的 token 开销约为普通对话的 15 倍。换句话说，相当一部分收益来自“把更多算力组织到了刀刃上”，组织本身放大了算力的有效利用率。

## 66 对 27 的冷账本：收益翻倍，账单也翻倍

泼一盆必要的冷水，多 Agent 至少有三笔账要算：

1. **成本账**。并行跑 N 个 Agent，token 开销近似乘 N。安全审计这种低频高价值任务烧得起；换成日常高频任务，账单可能先于 Bug 把你击穿。
2. **重复与误报账**。探测器越多，独立发现重叠的概率越高，误报总量也会上涨。验证环节不是可选项，而是多 Agent 架构的必要组件——没有验证层的多 Agent，等于把噪音放大器接上了功放。
3. **边际递减账**。Agent 数量翻倍，不等于 Bug 数量翻倍。各 Agent 的搜索范围有重叠，覆盖率提升走的是“并集”逻辑，越往后越贵。

那什么时候值得组队？经验判据大致是：**任务可拆、可并行、单个发现的验证成本可控**——审计、测试、技术调研都属于此类；反过来，需要单一连贯上下文输出的任务（比如写一篇逻辑严密的长文），组队反而会把上下文拆散，得不偿失。

一句稍显扎心的总结：模型没有变聪明，是系统变聪明了。而“系统怎么组织”，恰好是工程师能动手优化的那部分。

## 写在最后：三条可操作的建议

给想把这套思路搬进自己工作流的开发者：

1. **先拆任务，再上模型**。无论你用 Claude Code 的 subagent、LangGraph 还是手搓脚本，价值最大的动作是提前想清楚：这个任务能不能切成互相独立的子任务？每个子任务的边界和产出格式是什么？拆不清楚的任务，加多少 Agent 都是空转。
2. **先算 token 账，再谈架构**。多 Agent 的默认代价是十几倍 token。动手前问一句：这个任务的验证成本多高？值不值得为召回率多付十几倍账单？小任务用单 Agent 配好工具链，往往更划算。
3. **自动化产出，一律人工终审**。66 个发现里照样有误报和重复。健康的分工是：AI 负责召回（尽量不漏），人负责精度（决定哪些是真的、哪些要修）。把终审权交给自动化系统，等于把质检环节外包给了生产车间。

Bug 还是那些 Bug，变的是搜索的组织方式。这大概是这波新闻里最“不 AI”、也最工程的一课。
