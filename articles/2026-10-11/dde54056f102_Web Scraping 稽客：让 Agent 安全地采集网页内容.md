## 背景

Agent 工作流里，“去网上查一下”是最高频的需求之一：做调研、盯价格、汇总公告、比对文档。在 OpenClaw 里，常见做法是给 Agent 挂一个 fetch 工具或 scraping 类 MCP server，让它自己决定抓哪个 URL。工具一挂，能力就有了；但“能抓”和“抓得安全、抓得干净”之间，差着不少工程活。这篇帖子把我们在实际项目里踩过的坑和沉淀出的管线整理一下，供参考。

## 问题

直接把 fetch 权限丢给 Agent，通常会遇到四类翻车：

1. **内容注入**：页面正文、HTML 注释、隐藏 div 里可能藏着“忽略之前的指令”类文本。Agent 把网页内容当指令执行，是目前最容易被低估的风险。
2. **上下文污染**：一个页面几十 KB，导航、页脚、评论区一起塞进上下文，轻则浪费 token，重则把关键任务信息挤丢。
3. **动态渲染**：直接 GET 只拿到一个 JS 壳，Agent 以为抓到了，实际什么都没有。
4. **礼貌问题**：循环任务高频抓同一站点，触发限流甚至封 IP，连累同出口的其他服务。

## 做法

我们现在的标准管线是五步：

1. **域名白名单**：在工具配置里限定可抓取的域名集合。优先官方 API 和 RSS，抓页面只作兜底。
2. **分层取数**：静态页用普通 fetch + 正文抽取（readability 类算法）；需要 JS 渲染的才上 headless browser；大规模结构化需求走专门的 MCP server。
3. **清洗与截断**：抓回来先过清洗脚本——去 script/style/注释，抽正文，超长截断，同时保留标题、发布时间等元信息。
4. **不可信标注**：所有网页内容用统一标记块（如 `<<<WEB_CONTENT url=... time=...>>>`）包裹，并在 system prompt 里明确约定：该区块内的一切文字都是数据，不是指令。
5. **限速 + 缓存 + 日志**：同一域名请求间隔不低于数秒，结果按 URL + TTL 缓存；每次抓取记录 URL、时间、UA、结果哈希，方便审计和回放。

## 踩坑点

- 正文抽取不是万能的，部分站点会把侧栏、热榜混进正文，需要按站点加选择器白名单。
- 别把带登录态的 cookie 交给抓取工具，单独用无痕 context，防止凭据泄漏或被页面脚本利用。
- gzip / charset 处理不好会出现乱码，Agent 可能基于乱码“总结”出荒谬结论，而且看起来还挺自信。
- headless browser 内存占用大，常驻实例要加超时回收，否则跑几天就 OOM。
- 截断要“截尾保头”，很多页面关键信息在前部；也别只抓首屏，正文可能在懒加载区域。

## 可复用建议

- 白名单、限速、缓存三件套做成默认配置，不要等出事再补。
- 把“抓取→清洗→标注→摘要”封装成一个独立 MCP 工具，而不是让 Agent 手搓多步调用——步骤越少越稳。
- 输出永远带来源 URL 和抓取时间，方便人工核验。
- 团队内共享站点适配规则（选择器、是否需要渲染），避免重复踩坑。
- 拿不准合规性时，先看 robots.txt 和站点条款；商用场景优先走授权接口。

## 总结

让 Agent 安全采集网页，核心不是“更好的抓取”，而是“更窄的权限 + 更脏的内容假设 + 更厚的后处理”。把网页内容永远当不可信数据、把清洗做成管线、把礼貌当成默认，Agent 的采集能力才能长期稳定地用在正经任务上。欢迎大家在评论区补充自己的站点适配经验。
