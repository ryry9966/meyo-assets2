## 背景

E2E 测试难写难养：用例逻辑不复杂，难在选择器要稳、数据要可重置、异步要等对。这些重复劳动恰好适合交给 Agent。我们团队现在的模式是 OpenClaw agent 接上 Playwright MCP，让它"看着"真实页面写测试，而不是凭空想象 DOM。跑了两个多月，从纯手写变成 Agent 出初稿、人来审，新增用例的成本降了一半左右。

## 问题：直接让 AI 写为什么不行

最初的做法是把需求文档丢给模型，说"帮我写个 Playwright 用例"，结果反复出现三类问题：

1. **选择器靠猜。** 生成的 `getByText('提交')` 文案一改就挂，或者匹配不到异步渲染出来的元素。
2. **等待靠 sleep。** 满屏 `waitForTimeout(3000)`，CI 上时快时慢。
3. **幻觉 API。** 用了当前版本不存在或不推荐的写法，本地碰巧能跑，CI 直接红。

根因只有一个：模型既没有页面上下文，也没有项目的测试约定，只能按"最常见的写法"盲生成。

## 做法：让 Agent 摸到真实页面

1. **先写约定文档。** 把规范固化成 `TESTING.md`：强制 `getByRole` / `getByTestId`、禁止 `waitForTimeout`、测试数据用固定 seed、一条用例只验证一条用户路径。文档随系统提示注入 agent。
2. **挂 Playwright MCP。** Agent 能实际打开页面、点击、读 DOM。要求它写用例前先手动走一遍流程，基于观察结果生成代码。
3. **本地跑通才交付。** 失败信息直接回喂给它自己修，一般两三轮能收敛。
4. **人工审查盯三处：** 断言是否验证业务结果而非 DOM 细节、数据清理是否完整、有没有把操作路径写死。

## 踩坑点

- **别让它顺着自己的点击路径写断言。** 它记录了什么就断言什么，页面一改版全崩。断言语义必须人工核对到"这条流程成功在业务上意味着什么"。
- **CI 与本地环境差异。** viewport、时区、字体渲染都可能导致本地绿、CI 红。`playwright.config` 由人统一管理，agent 无权改动。
- **一次只写一个 journey。** 批量丢十个用例过去，会得到高度雷同的 fixture，坏一处全坏。小步提交，每个 PR 一条用户路径。
- **固定模型版本。** 换模型后生成风格和 selector 习惯会漂移，规范文档要写得比模型默认习惯更强。

## 可复用建议

- 测试规范比更强的模型收益大，尤其是反例：贴一个 flaky 用例和修复后的版本，比十条规则都管用。
- 加一条 lint 规则禁掉裸 CSS 选择器和 `waitForTimeout`，机器守门比口头约定可靠。
- 维护一个 flake 率看板：一条用例一周内 flake 两次以上就标记回炉，不带侥幸进主干。
- Agent 适合写"新增"，不适合改"存量"——老用例里隐含的历史决策太多，动之前先让人读一遍。

## 总结

这件事的瓶颈不在模型能力，而在你能否把项目约定和真实页面上下文喂给它。OpenClaw + MCP 的组合让 Agent 从"文本生成器"变成"能动手操作的协作者"，这是体验上变化最大的部分。定位上建议把它当高级初级工程师用：初稿它写，断言语义和边界你来把关。
