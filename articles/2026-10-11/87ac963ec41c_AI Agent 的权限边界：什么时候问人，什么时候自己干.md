## 背景

OpenClaw 这类 agent 框架的日常形态已经变成：一个模型 + 一组 MCP 工具 + shell + 文件系统。工具越接越多，"这一步要不要问人"就不再是细节问题，而是架构问题。问得太少，一次事故就够写一篇复盘；问得太多，人会对确认框脱敏，最后变成无脑点"允许"，确认机制名存实亡。

## 问题

实践中最常见的两个失败模式：

1. **确认疲劳**：agent 每步都问，到第 20 次之后人类开始机械批准。此时确认框只提供仪式感，不提供安全性。
2. **静默越权**：prompt 里写了"危险操作请确认"，模型某天临场判断"这应该不算危险"，直接执行了 200 条 delete。

根因是同一个：把权限边界寄托在模型的临场判断上。模型判断是 best-effort 的，边界必须落在工具层和 harness 层，才能被强制执行。

## 做法

我们的经验是把每个工具调用放到两个维度上评估：**可逆性**和**影响面**。

- 可逆 + 影响小（读文件、查询、写沙箱草稿）：直接执行，只留日志。
- 可逆 + 影响大（批量改文件、改配置）：自动执行，但先做快照或 git commit，保证一条命令能回滚。
- 不可逆 + 影响小（发一条内部消息）：自动执行，事后可审计。
- 不可逆 + 影响大（删数据、对外发布、花钱、动生产）：必须问人，且没有绕过路径。

落地步骤：

1. **工具分级**。给每个 MCP 工具标注 read / write / destructive 三档，harness 按档位走不同策略，而不是靠模型自觉。
2. **危险工具强制提供 dry-run**。没有 dry-run 的 destructive 工具，先补齐再接入。
3. **预算约束**。金额上限、调用次数上限、影响行数上限，超限自动升级为人工确认——让"问人"可以被规则触发，而不是靠模型心情。
4. **把"问"设计成可决策的形式**。展示 diff、展示影响范围、附带回滚命令。禁止问"可以继续吗"这种没有信息量的问题。

## 踩坑点

- **高频确认等于没有确认**。一天弹 50 次确认，说明策略本身有问题，先收敛自动档的范围。
- **批处理藏雷**。一个"整理文件"的循环里藏着 200 次 delete，每步单独看都"可逆"，整体不可逆。影响面要按任务算，不按单次调用算。
- **权限只增不减**。prompt 里的许可条款越积越多，最后等于全放行。权限配置要进版本库，改动走 review。
- **把"不太会出错"当成"出事也不严重"**。概率和后果是两个轴，别合并成一个模糊的"信任度"。

## 可复用建议

- 默认拒绝写入，白名单放行，而不是默认全开再打补丁。
- 会话级授权：临时放行附带范围和过期时间，任务结束自动收回。
- 所有自主执行的动作记录"为什么这么做"，事后审计才有上下文。
- 每次事故复盘只问一个问题：这个动作当时应该在哪一档？

## 总结

权限边界不是"信任模型多少"的问题，而是把人类注意力当稀缺资源来分配的问题。可逆的事让 agent 跑快一点，不可逆的事把人拉回决策环里，并让"问人"这件事本身足够廉价、足够有信息量。做到这两点，自动化才能长期跑得下去。
