热搜上挂着一条消息：在评测多智能体协作能力的新基准里，最强模型带着一队 Agent 干活，任务完成率只有 50% 上下。这和大众直觉正好相反——单个大模型已经能写代码、做报表、订机票，为什么一群“聪明 AI”组队，反而连一半的活都干不利索？这篇把“Agent 组队”拆开讲：协作能力是怎么被测出来的，分丢在哪一步，以及 50% 这个数字到底该怎么读。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/d5bfd325a8f7b8e5.png)

## 先对齐概念：什么叫“Agent 组队”

- 一个单体 Agent = LLM + 工具调用 + 记忆 + 规划循环。它不是聊天机器人，而是能自己决定“下一步调哪个工具”的执行体。
- 多智能体系统（Multi-Agent System）常见三种组织形态：
  1. 指挥官–工人：一个“项目经理”Agent 拆解任务，分发给子 Agent 并行执行，最后汇总，Anthropic 的多 Agent 研究系统就是这个架构；
  2. 角色流水线：PM、程序员、测试各司其职，MetaGPT、CrewAI 的经典玩法；
  3. 互查互辩：多个 Agent 互为审稿人，用来压幻觉。
- 组队的理论收益很诱人：分工降低单份上下文负担、并行提速、交叉纠错。听起来 1+1>2，但评测分数讲的是另一个故事。

## 基准怎么把“协作能力”变成分数

- **TheAgentCompany**（CMU 团队，2024 年底发布）：在一间模拟软件公司里布置了 175 个真实工作任务——写代码、查数据、做表格、处理行政流程——按 0 / 0.5 / 1 打分，人类新人被假定为 100 分。结果：最强模型完整完成率约 24%，超过四成任务颗粒无收；在它最擅长的软件类任务上完成率约 54%，正是“一半”的水位。有趣的是，允许向人类要一次提示后能涨到 34%——很多失败不是“不会做”，而是“不会问”。
- **τ-bench**（Sierra）：让 Agent 对接一个模拟客户和一套数据库，考察能不能把事办成且不出错。它最有名的指标是 pass^k：同一任务独立重跑 k 次、全部成功的概率。以单次通过率 60% 计算，重跑 8 次全过的概率只剩 0.6^8 ≈ 1.7%。
- **MultiAgentBench 等协作专项**：除了看结果，还给协作过程设里程碑——分工是否合理、是否达成共识、中间交付质量如何，拼出一张“团队作战”成绩单。
- 三类基准的共同点：测的都是端到端“把事办成”，而不是单步答对。这正是协作的硬门槛。

## 50% 之后，任务都死在哪一步

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/61be9935203bda57.png)

- **误差级联**：Agent 的活是长链条——理解任务、拆解、检索、调用工具、汇总、验证。假设每一步可靠性 90%，10 步串下来只剩 0.9^10 ≈ 35%。多智能体的链条比单体更长，每多一次交接，就多一次翻车机会。
- **上下文交接损耗**：多 Agent 靠消息传递协作，本质是“传话游戏”。A 查到三条候选方案，压缩成一句话转给 B，B 再转述给 C——信息在每一轮压缩里失真。各 Agent 的上下文窗口互不相通，你以为它们共享了全局信息，其实只共享了一句摘要，像三个人共用一块屏幕却不知道对方改了哪行代码。
- **目标与协议对齐失败**：研究者提出的 MAST 失败分类法（Why Do Multi-Agent LLM Systems Fail?）把真实失败案例归类后发现，近八成失败与“模型不够聪明”无关，而是流程与协作问题：任务说明含糊却没人追问、Agent 不承认自己不知道、中间产出缺一个验证者、出错后互相甩锅、甚至编造不存在的 API。
- 还有一笔经济账：Anthropic 的工程团队自己承认，多 Agent 系统的 token 消耗约是单轮对话的 15 倍。50% 的完成率，是花 15 倍成本买来的。

## 50% 该怎么读：不是天花板，是“半自动水位”

1. **纵向看趋势**：两年前同类基准里，GPT-4 加插件在 GAIA 上只有 30% 出头，而人类是 92%；如今前沿模型在多个 Agent 基准上翻倍再翻倍。50% 是陡峭曲线上的一个点，不是终点。
2. **横向看场景**：50% 在“可校验 + 可重试”的场景里已经可用——代码有测试兜底，写坏了重跑即可；文案草稿有人把关，50 分的初稿也是生产力。但在“不可校验 + 一次定成败”的场景（直接操作生产数据库、对接真实客户），单次 60% 的通过率乘上 8 层链路就是灾难。
3. **对照看基准**：分数依赖评分法（0 / 0.5 / 1 本身就是设计选择）、依赖 scaffolding 和提示策略。换个 Agent 框架、加一个人工检查点，同一个模型能涨一大截。读基准时要问“它替我模拟了什么样的工作环境”，别只记一个数字。

## 三条冷思考：组队这件事少交学费

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-11/c0468f7a0261429c.png)

1. **先把单体做到位，再谈组队。** 很多“多 Agent”需求，本质是“单 Agent + 合理的子任务拆解 + 可验证的检查点”。组队的 token 成本是 15 倍量级，只有子任务彼此独立、可并行、可校验时才划算；否则它只是把一个错误放大成 N 个错误的站会。
2. **给系统配“验证者”，而不是只配“干活的”。** MAST 的数据说明，大多数失败缺的不是能力，是关卡：让每个里程碑都有机器可查的产物——测试用例、diff、引用来源、结构化输出——把人的注意力从“盯全程”里省出来，只审检查点。
3. **用 pass^k 思维做预期管理。** 评估任何 Agent 产品，别看演示跑通的那一次（pass^1），要问独立重跑 10 次能成几次；给工作流留出重试预算和人工兜底，再决定放不放手。

组队的上限，从来不是队里最聪明的那个成员，而是成员之间那几步交接。这条规律对 AI 成立，对人类团队同样成立。
