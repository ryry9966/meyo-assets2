## 背景

OpenClaw 跑一段时间后，大多数人会撞上同一个分岔口：全部走云端大模型，账单和延迟都难看；全部换成本地小模型，复杂任务的规划质量又肉眼可见地掉。OpenClaw 本身支持同时挂多个 provider（云端 API 和 Ollama 之类的本地推理都行），所以问题从来不是"二选一"，而是"谁干什么活"。

## 问题

我自己的工作流里，agent 每天要处理三类请求：多步规划、高频小任务（摘要、分类、工具入参整理）、以及涉及私人数据的处理。用一个模型扛全部，要么浪费，要么降智。核心矛盾在于路由标准不清晰，配置一多就变成玄学。

## 做法与步骤

1. **先做任务分型，再动配置。** 花半天把 agent 近期实际执行的任务拉出来分三类：强推理类（多步规划、跨工具编排、报错排查）；高频轻量类（会话摘要、意图分类、MCP 入参格式化）；敏感数据类（本地文件、私人上下文）。
2. **按 agent 分配模型，而不是按请求猜。** 在 config 里给主 agent 指定云端模型做 primary（字段名以你当前版本为准），负责规划和复杂编排；另起一个子 agent 跑本地小模型，专门接高频轻量任务。OpenClaw 的多 agent 结构天然适合"大脑 + 手脚"这种分工。
3. **配 fallback 链，但要有上限。** 本地模型做云端故障兜底没问题，但建议加次数/成本上限，避免故障时静默降级、输出质量掉了你都不知道。
4. **敏感数据走本地。** 涉及本地文件和私人上下文的任务固定路由到本地模型，这条是硬规则，不参与动态判断。
5. **记观测数据。** 按路由维度记录 token 用量、延迟、失败率，跑一两周再调。没有数据，路由策略就是拍脑袋。

## 踩坑点

- **本地模型的工具调用格式是最大的坑。** 小模型的 function calling 稳定性明显弱于 GPT 系，调 MCP 插件时入参偶尔缺字段或类型错。我的做法是：要调工具的任务一律留在云端模型，本地模型只做纯文本处理。
- **上下文长度别想当然。** 本地小模型窗口小，长会话塞进去会被截断，表现为"越聊越忘"。给本地路由加一个 prompt 长度阈值，超了就回流云端或先做压缩。
- **fallback 会掩盖故障。** 云端挂了、本地悄悄顶上，日志里只有一条 fallback 记录。把 fallback 事件当告警级别处理，别当正常日志。
- **升级即漂移。** 本地模型一升级行为可能变，调好的 prompt 未必成立。本地模型版本固定，别追新。

## 可复用建议

一条决策线，可以直接抄：

- 多步规划、跨插件编排、报错排查 → 云端强模型；
- 摘要、分类、格式整理、定时例行任务 → 本地模型；
- 涉及私人数据 → 本地，无例外；
- 不确定放哪边 → 先放云端，观测两周，确认质量不掉再下沉到本地。

## 总结

多模型路由的价值不在省了多少钱，而在于让每个任务的执行路径变成显式决策。先分型、按 agent 分配，守住工具调用和隐私两条硬边界，再用观测数据迭代。路由策略本身也应该是版本化配置：改一次，记一笔。
