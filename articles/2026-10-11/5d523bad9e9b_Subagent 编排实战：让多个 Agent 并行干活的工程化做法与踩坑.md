## 背景

我们团队用 OpenClaw 做日常自动化有一段时间了。单 agent 跑小任务没问题，但一遇到"调研三个数据源 + 整理结果 + 出报告"这类复合任务，短板就暴露：主 agent 的 context 越滚越大，串行执行慢，工具调用之间还互相污染。后来把任务拆给 subagent 并行跑，整体耗时从四十多分钟压到十分钟出头。这里把做法和踩过的坑整理一下。

## 问题

直接让主 agent 自己拆任务自己干，有三个硬伤：

1. 所有中间结果堆在主 context 里，几轮之后开始丢细节；
2. 明明子任务之间没有依赖，却在串行等待；
3. 主 agent 既当调度员又当工人，prompt 越写越臃肿。

## 做法

我们的编排结构很简单，分三层：

1. **主 agent 只做拆解和裁决**。读需求、拆成互不依赖的子任务、控制并行度、最后汇总，自己不做具体工作。
2. **每个 subagent 一个职责、一个独立工作区**。调研类任务各自走各自的 MCP 数据源，写文件类任务各自操作独立子目录，避免互相覆盖。
3. **结构化回传**。subagent 必须按固定 schema 返回：状态、产出路径、关键结论、异常。不要让它自由发挥写散文，否则主 agent 汇总时没有抓手。
4. **并行度收敛**。实测稳定在 3~4 路并发收益最好，再高边际递减，token 成本倒是线性涨。

## 踩坑点

- **并行写冲突**：最初两个 subagent 同时改一个配置文件，后写的覆盖先写的。解法是"只读并行、写入串行"——调研阶段全并行，落盘阶段由主 agent 串行执行或按文件分片。
- **context 传递过宽**：图省事把主 agent 全量上下文塞给 subagent，结果它被无关信息带偏。改为每个子任务只注入最小必要上下文。
- **单点阻塞**：一个子任务超时卡住整批。给每个 subagent 设硬超时，失败的单独重试一次，还不行就降级为"标注缺失、继续汇总"。
- **拆得太细**：一个子任务只有两步操作，spawn 开销比干活还贵。经验值：预期消耗低于主 agent 单轮调用量级的任务，不值得拆出去。

## 可复用建议

- 从"只读任务并行 + 写操作单点"这个最稳的模式起步，跑通再加复杂度。
- 把 subagent 的 prompt 当接口设计：输入、输出 schema、边界条件写死，固化成插件或模板。
- 先串行验证任务拆分是否合理，再并行化，不要一步到位。
- 汇总阶段保留人工 diff 审查，尤其是涉及写文件的任务。

## 总结

Subagent 编排本质是工程问题，不是 prompt 玄学：拆分粒度、并发控制、结构化回传、失败降级，这四件事做扎实了，多 agent 并行的收益是稳定可复现的。建议先把一类高频复合任务固化成模板跑顺，再逐步推广到其他场景。
