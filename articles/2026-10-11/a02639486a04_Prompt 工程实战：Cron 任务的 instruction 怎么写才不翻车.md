## 背景：cron 任务本质是一条无人值守的 prompt

在 OpenClaw 里，cron 任务的核心机制很朴素：到点之后，把 instruction 里的内容当作一条消息交给 agent，由它自己调工具、干完活、把结果送出去。它和交互式对话最大的区别是“没人盯着”——agent 不会回头问你“要 A 还是 B”。所以 instruction 的质量，直接决定这个任务是稳定交付，还是每天产出玄学。

## 问题：意图式指令的翻车现场

我最早写的 cron 指令全是意图式的：“每天早上帮我看下 GitHub 通知和今天的日程，汇总发我。”跑了两周，问题接连出现：有时漏掉日历；有时把通知原文整段贴过来刷屏；工具超时就干脆没消息；有一次它还“好心”替我把通知标成了已读。回头看，问题不在模型，而在于我没把 cron 当成无人值守作业来写需求。

## 做法：五段式 instruction

现在我的 cron 指令固定为五段：上下文、目标、工具与数据源、输出契约、失败兜底。以晨报任务为例：

```text
这是每日晨报任务，只读不写。
1. 调用 GitHub MCP 的通知工具，读取过去 24 小时的未读通知；
2. 调用日历插件，读取今天 09:00–19:00 的日程；
3. 汇总为一条消息：日程在前，通知按仓库分组、每仓库最多 3 条，全文不超过 300 字；
4. 结果发送到 Telegram 的「工作」会话；
5. 任一数据源为空或调用失败，不要编造内容，在消息末尾注明「XX 未取到」。
禁止任何写操作：不回复、不标记已读、不修改日程。
```

几段关键用意：

- **工具与数据源**：点名用哪个 MCP 工具或插件，别让它自己猜，也别假设服务一定在线；
- **输出契约**：发到哪、什么格式、多长。这是最容易被省略又最该写的一段，没有它就会出现“刷屏或沉默”两个极端；
- **兜底**：agent 在工具返回空结果时非常倾向编数据，“宁缺毋假”必须显式写出；写操作的边界同理。

## 踩坑点

1. **隔离会话没有记忆。** cron 可以跑在隔离会话里，agent 不记得上次干了什么。需要状态的任务，要么把状态落到固定文件让它读，要么每次现查，千万别写“和昨天一样”。
2. **意图不等于步骤。** “盯一下服务”这种指令，十次能跑出十个版本。
3. **时间窗要绝对化。** “每天早上”不如“每天 08:00 后的第一次运行”，跨时区设备尤其如此。
4. **高频配长任务会叠。** 5 分钟一次的抓取配上 10 分钟才能跑完的链路，前后任务互相干扰。要么拉长周期，要么把重活下沉成脚本，cron 只负责触发和汇报。

## 可复用建议

- **先手动验证**：把 instruction 直接当普通消息发给 agent 跑一遍，链路通了再挂 cron，能省掉大半排障时间；
- **一件事一个任务**：晨报是晨报，巡检是巡检，别让一条 instruction 承载三条业务线；
- **结果落盘**：让任务把每次输出追加到本地文件或固定频道，失败率一眼可见；
- **定期回写**：每月看一次失败案例，把新的报错模式补进兜底段。instruction 是长期维护的对象，不是一次性配置。

## 总结

把 cron instruction 理解成“给一位失忆同事的交接班说明”就够了：它每次都是新人，不知道历史，只照字面执行。做什么、用什么工具、产出什么、失败了怎么办——四件事写全，定时任务就从玄学变成工程。
