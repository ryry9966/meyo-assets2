## 背景

用 OpenClaw 做内容自动化的团队基本都会遇到同一个局面：Agent 产出天然是 Markdown，但下游发布目标五花八门——静态博客吃 frontmatter，公众号只认内联样式的 HTML，知乎、掘金是各自"魔改"的 Markdown 方言，图片还得换到各家的对象存储。一稿多发，真正的成本不在写，而在格式适配。

## 问题

最早的偷懒做法是让 LLM 直接"改写成公众号版"。跑了两周就暴露问题：

1. 模型每次重写，正文都会漂移，同一个事实三篇文章三个说法；
2. 正则替换在嵌套代码块、表格上频繁翻车；
3. 图片相对链接在不同平台表现不一致，发布后才发现挂图。

结论很明确：**内容生成和格式适配必须分开**。格式适配是确定性工作，交给代码，不交给模型。

## 做法

我们现在的管线分四层：

1. **规范化层**：Agent 产出后先过 markdownlint 加 frontmatter schema 校验（title/tags/date 必填，标题层级从 `h1` 起）。不合格直接打回重生成，这一步在发布前拦掉了八成问题。
2. **转换层**：基于 unified/remark 写 mdast 变换，不碰正则。每个平台一份 profile（YAML 配置），声明允许的节点类型、样式映射、图片宿主。转换时按 profile 裁剪 AST：公众号目标把代码块转成内联样式 HTML 片段；博客目标改写图片路径；不支持表格的平台降级为列表。
3. **资源层**：图片上传封装成 MCP tool，入参是内容 hash。发布前预扫 AST 收集全部图片，逐个上传、用返回 URL 替换节点。hash 作幂等键，管线重跑不会重复传图。
4. **编排层**：OpenClaw Agent 只负责调度：generate → lint → transform → dry-run 出预览 → 人工确认 → publish。发布目标各自封成 MCP tool，Agent 不碰转换细节。

## 踩坑点

- **别用正则做转换**。嵌套代码块、转义字符、表格里的竖线，正则迟早翻车；mdast 变换一次写对，长期受益。
- **公众号净化规则要实测**。文档声称支持的标签和实际保留的差异不小，部分 style 属性会被剥离，伪类全失效。我们维护了一份实测允许清单，放进 profile。
- **LLM 改写引入漂移**。踩过最大的坑：图省事让模型直接出"平台版"，结果数字和结论都变了。适配必须是纯函数，同样的输入永远得到同样的输出。
- **幂等**。发布步骤不幂等，一次重试就是一次重复发文。所有写操作以内容 hash 去重。
- **标题层级**。很多模型爱从 `##` 开头，直接转换会导致部分平台目录错乱，lint 里强制归一。

## 可复用建议

- Canonical markdown 是唯一事实源，进版本库；各平台产物视为构建产物，不进版本库。
- 平台差异全部收敛进 profile，新增平台只写一份配置加少量 transform 插件。
- 转换函数保持纯函数、可单测，每个 profile 配 golden file 回归测试。
- dry-run 预览、人工确认、正式发布三步不要合并，省下的时间不够填一次翻车的坑。

## 总结

管线跑通后，新增一个发布目标的工作量从"改一天脚本"降到"写一份 profile"。核心原则就两条：内容归模型，格式归代码；所有外部副作用（上传、发布）必须幂等。平台 API 被 MCP 封装成工具之后，Agent 的角色也干净了——只做编排和决策，不做格式手术。
