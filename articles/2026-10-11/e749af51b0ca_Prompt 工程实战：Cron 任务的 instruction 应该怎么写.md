## 背景

OpenClaw 的 cron 本质很简单：到点把你的 instruction 作为一条用户消息喂给 agent，跑完把结果投递出去。它和交互式聊天最大的区别是——**没有上下文、没有你在场纠偏、结果直接进频道**。这让 cron instruction 更像一次无人值守的接口调用，而不是一句随手的聊天。

社区里看到的定时任务翻车，九成不是调度配置问题，而是 instruction 写法问题。

## 典型问题

- 输出格式每天不一样，有时三百字有时三千字；
- "今天"算错，或者指令里写死了日期；
- isolated session（独立会话）里写"接着上次说的"，直接失效；
- 数据源挂了，任务要么沉默失败，要么每隔几分钟刷一条报错；
- 顺手执行了指令没让做的操作。

## 做法：把 instruction 当接口契约写

推荐五段式骨架，逐段填空：

1. **目标与范围**：一句话说清做什么、不做什么；
2. **数据来源与工具**：用哪个工具/MCP，取哪些字段；
3. **输出契约**：格式、长度上限、无数据时输出什么；
4. **投递规则**：发到哪，什么条件下不发；
5. **异常策略**：失败重试几次，失败时发什么。

一个每日巡检的例子：

```
任务：每日服务器巡检摘要，以本次触发时刻为"今天"。
1) 用 ssh 工具检查三台主机的磁盘与内存占用（阈值：磁盘 85%、内存 90%）。
2) 输出 Markdown，只列超阈值项；全部正常时只输出一行"全部正常"。
3) 结果投递到 #ops；无异常时不发送。
4) 单台主机连接失败：最多重试 2 次，仍失败则发送一行故障说明。
不要执行巡检以外的任何操作。
```

上线前用 cron 的手动触发跑两三次，对照日志确认每段约束都真的生效了。

## 踩坑点

- **依赖上下文**：isolated session 每次冷启动，没有历史。"上文""刚才""上次"一律不能出现，所有前提都要在指令里自包含。
- **时间基准**：cron 表达式按调度器时区触发，指令里不要写死日期，统一用"以触发时刻为准"。
- **想做增量对比**："和上次不一样才发"需要状态，而 isolated session 无记忆。要么让 agent 把上次结果落到文件再读回比对，要么干脆简化成条件触发（有异常才发）——后者更稳。
- **失败策略缺失**：不定义重试上限和失败通知粒度，结果不是沉默就是轰炸。
- **任务贪多**：一个任务塞三件事，容易超时且难排查。一个 cron 只做一件事，要组合就再建一个任务。
- **假设工具存在**：指令里引用的工具必须在该 agent 配置里真实可用，否则模型会现场编造一个像模像样的结果。

## 可复用建议

- 心态转变：cron instruction 是 contract，不是聊天。你默认的"常识"——今天几号、发到哪、失败了怎么办——都要显式写进去。
- 默认组合：isolated session + 显式投递目标 + 条件发送。
- 输出一定给长度上限，并写明无数据时的占位行为。
- 每次改完指令先手动触发验证，再上正式排期；改指令 = 改代码，要有回归意识。

## 总结

定时任务没有你在场，instruction 就是你留下的值班手册。把写接口契约的严谨度用在它身上，任务才能从"碰运气"变成"可依赖"。
