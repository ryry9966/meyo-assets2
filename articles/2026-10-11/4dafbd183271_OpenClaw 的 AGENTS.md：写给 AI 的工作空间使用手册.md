## 背景：README 之后，AI 还缺一份手册

传统仓库的上手指引写在 README 和 CONTRIBUTING 里，读者是人。而在 OpenClaw 这类 agent 工作流里，第一个读文档、跑命令、改代码的往往不是人，而是模型。人遇到疑问会问同事，agent 只能按它对同类项目的先验去猜：猜错包管理器、猜错测试入口、把产物放进会被提交的目录。AGENTS.md 就是补这个缺位的社区约定：一份纯 Markdown，放在工作区根目录，OpenClaw 在会话启动时自动读取，agent 先读它再动手。它不替代系统提示词，定位是"这个工作区的事实清单"。

## 问题：没有手册，成本摊在每一次会话上

没有 AGENTS.md 的典型场景：每个新会话都要在对话里重复"用 pnpm 别用 npm；测试只跑 tests/；dist 目录别提交"。这些纠正散落在聊天记录里，换个会话就清零，团队里每个人还要各自纠正一遍。更糟的是 agent 半对半错地完成任务，等你 review 才发现它绕开了全部约定——事后纠错的成本，远高于事前写几十行文档。

## 做法：五步写一份够用的 AGENTS.md

1. **根目录主文件，控制在 150 行以内。** 核心段落：项目一句话说明、环境准备、常用命令（build/test/lint 直接给可复制的命令行）、目录结构地图、代码风格硬约束、"不要动"清单（生成目录、锁文件、迁移脚本等）。
2. **写清权限与工具边界。** 明确允许写入的路径范围、哪些 MCP 工具和插件在本工作区可用、有副作用的操作是否需先确认。OpenClaw 的工具调用来自插件和 MCP server，在文件里声明"什么工具用在什么任务上"，比事后在对话里拦截可靠。
3. **子目录放局部文件。** monorepo 里在 packages/xxx 下写更具体的规则，就近覆盖根文件；并在根文件注明"子目录文件优先"，消除歧义。
4. **当代码维护。** 进版本库、走 PR。谁改了构建流程，同一提交里顺手更新 AGENTS.md，review 时按接口变更对待。
5. **持续"提升"对话纠错。** 发现自己第二次向 agent 纠正同一个错误，就把这条写进文件，然后从对话里删掉。这是文件长期有效的关键习惯。

## 踩坑点

- **写太长。** 超过两三百行，模型对中后段规则的遵循度明显下降；少而硬的条目优于多而软的建议。
- **过期比缺失更糟。** agent 会信任文件内容，过期的命令会被一直执行；命令或流程变更必须同步更新。
- **与系统提示词或插件默认行为冲突。** 同一件事两处描述不一致，agent 行为会不稳定。文件只写工作区事实，不重复框架通用规则。
- **写空话。** "写出高质量代码"没有约束力，要写成可执行、可验证的条目。
- **塞绝对路径和密钥。** 路径用相对工作区根的写法，密钥走环境变量。
- **关键规则藏在链接后。** agent 不一定读外链，重点直接写在正文。

## 可复用建议

- 一句话判断标准：同样的话对 agent 说第二遍，就该进 AGENTS.md。
- 依赖升级或 CI 变更后做"冷启动测试"：开全新会话，让 agent 只凭文件跑通 build + test，数一数你纠正了几次——这个数字就是文件质量的度量。
- 给"已知坑"留独立小节并注明日期，例如"某依赖 3.x 在 Node 20 下构建失败，锁 2.x"。
- README 给人看，AGENTS.md 给模型看，受众不同，别合并成一个文件。

## 总结

AGENTS.md 是典型的低成本、高杠杆实践：用几十行 Markdown 把团队隐性约定显性化，把 agent 的试错成本从"每次会话"摊销到"一次维护"。它不需要额外工具，需要的是像对待接口文档一样的持续维护。从工作区里第一份 50 行的版本开始，比等一份完美手册更有价值。
