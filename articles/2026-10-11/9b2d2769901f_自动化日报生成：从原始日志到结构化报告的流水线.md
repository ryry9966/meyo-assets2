## 背景

服务多了之后，日报变成一种体力活：从十几个服务的日志里捞数据，汇总成一份格式统一的报告。人肉做一遍半小时起步，还经常漏项。我们的思路是把它做成一条流水线：**确定性的部分交给代码，叙述性的部分交给 Agent**，中间用固定 schema 隔开。

## 问题

直接把原始日志丢给大模型“帮我总结一份日报”，会遇到三个硬伤：

1. **数字不可信**。模型算数不稳，错误率、QPS 这类关键指标一旦算错，日报反而制造事故。
2. **结构不稳定**。今天三段式，明天变散文，下游归档和比对全部失效。
3. **成本失控**。原始日志动辄几十万 token，一天跑几次谁都扛不住。

## 做法

流水线分四层，OpenClaw 承担调度和生成两块：

**1. 采集与归一化（代码）**：脚本拉取各服务日志，统一转 JSONL，字段固定为 `timestamp / level / service / event / metrics`。解析失败的行进死信文件，不硬塞给下游。

**2. 统计预处理（代码）**：错误数、环比变化、Top 事件、延迟分位数全部用确定性代码算好，输出几 KB 的聚合结果。这一步是整条流水线的信任基座——**模型不碰原始日志，只读聚合结果**。

**3. 生成层（OpenClaw Agent + MCP）**：写了一个 MCP 工具 `get_daily_aggregate` 返回聚合数据。系统提示里明确约束：所有数字必须来自工具返回，异常只能基于数据中已有的标记描述，不允许自行推断。输出走固定 Markdown 模板，段落与字段一一对应。

**4. 触发与校验**：用 cron（或 OpenClaw 调度插件）定时触发，生成后先过 schema 校验——段落数、字段完整性、关键数字与聚合结果抽查比对——通过才推送到 IM webhook，失败重试一次并告警。

## 踩坑点

- **时区**。日志是 UTC，报告窗口按本地时区切，第一版每天漏统计 8 小时数据。现在归一化阶段统一转时区，并在报告里写明统计窗口。
- **日志格式漂移**。某服务改了埋点，解析器静默退化，日报连续三天数据偏少才被发现。后来加了归一化成功率自检，低于阈值直接报警而不是硬生成。
- **只靠 prompt 约束结构不可靠**。模型偶尔省略字段，schema 校验加自动重试基本解决。
- **流水线自身的静默失败**。任何一层挂了，日报就“消失”而不是报错。加了心跳通知：没收到日报和收到失败日报，都算异常。

## 可复用建议

- **分层原则**：事实归代码，措辞归模型。能提前算的都不要让 LLM 算。
- **MCP 工具返回小而结构化的载荷**，别把整段日志当上下文塞进去。
- **校验前置于分发**：宁可晚十分钟，不发一份错的。
- **把流水线当服务运维**：每层留运行日志，失败必须可观测。

## 总结

这条流水线上线后，日报从每天半小时的手工活变成零干预的定时产物，准确率反而更高——因为所有数字都出自同一段代码。经验浓缩成一句话：**不要让 Agent 当计算器，让它当作者**。把结构、数字、校验做扎实，生成模型才能真正发挥叙述的价值。
