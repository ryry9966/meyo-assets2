## 背景

团队日报的素材散落在好几个地方：git 提交记录、CI 流水结果、工单系统变更、还有群聊里零散的讨论。之前每天由人肉汇总，大概花 30 分钟，漏项和口径不一致是常态。这篇帖子记录我用 OpenClaw 搭的一条日报流水线，跑了三周，基本稳定，把过程和踩的坑整理出来。

## 问题

从"原始日志"到"能直接发的日报"，中间有几段脏活：

- 数据源分散、格式各异，时间窗口容易对不齐；
- 直接把日志丢给模型总结，数字经常被"脑补"，重点也会漂移；
- 模型每次输出的结构不一样，下游没法自动化；
- 定时任务失败是静默的，第二天才发现日报没发。

## 做法

整条流水线由 agent 的 cron 触发，分五段：

1. **采集**：三个 MCP 工具分别拉 git log、CI 记录、工单变更，只取时间窗口内的增量，不做全量。
2. **清洗**：脚本先跑一遍去重和噪音过滤（merge commit、心跳日志、机器人消息），原则是让模型看聚合后的条目，不看原始流。
3. **结构化**：prompt 里锁死一个 JSON schema，固定五个字段——变更条目、异常、风险、数据指标、明日计划，每条必须带来源引用。模型只做归类和一句话概括，所有数字从结构化数据读取，不允许它自己计算。
4. **渲染**：JSON 套固定的 Markdown 模板，输出格式永远一致。
5. **投递兜底**：发到群里并落盘存档；失败重试一次，仍失败就发告警，绝不静默。

## 踩坑点

- **时区**：cron 按 UTC 跑，数据窗口却按本地日期取，第一天漏了一半昨天的提交。后来统一用带时区的日期边界，采集和触发共用同一套。
- **原始日志直接进模型**：几千行塞进去，模型开始合理脑补。改成脚本先聚合，幻觉基本消失，token 开销也降了一个量级。
- **schema 漂移**：模型偶尔多加字段或改字段名，渲染直接挂。现在输出先过 schema 校验，不合格就带着报错信息重试一次，基本一次能过。
- **重复推送**：任务重跑导致同一份日报发两遍。加了个按"日期 + 版本号"的幂等键，发送前先查。

## 可复用建议

- **schema 先行**：先定输出结构，再写 prompt，最后接数据源，顺序反了必返工。
- **数字不进模型**：统计全部在代码层算好，模型只负责叙述。
- **保留 dry-run 模式**：加个参数只生成不发送，调 prompt 时先跑 dry-run 做新旧对比。
- **原始日志是事实源**：日报只是视图，存档时把来源引用一起落盘，方便回溯和审计。

## 总结

这条流水线的核心思路不是"让 AI 写日报"，而是把采集、清洗、统计这些确定性环节交给代码，把归类和措辞交给模型，再用固定模板收敛输出格式。上线后人工时间从每天半小时降到偶尔抽查几分钟，格式再也没被人吐槽过。如果团队还在人肉拼日报，花一个下午搭一条类似的，性价比很高。
