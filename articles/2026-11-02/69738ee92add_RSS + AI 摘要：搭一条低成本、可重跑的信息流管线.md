## 背景

订阅源越攒越多，真正读进去的越来越少。RSS 本身没问题——稳定、开放、格式统一，问题在于人的阅读带宽。最近我把阅读流改造成一条「RSS 抓取 → AI 摘要 → 定时推送」的管线，每天早上收到几百字摘要，信源一个没删，焦虑感明显下降。把做法和坑记录一下。

## 问题

直接让 Agent「帮我读 RSS」听起来很美，实际会撞上三件事：

1. **成本失控**：几十个源每天上百条更新，逐条丢给 LLM，token 消耗很可观。
2. **去重困难**：同一篇文章常以不同 URL 出现（utm 参数、摘要页与全文页），不去重就会重复摘要。
3. **摘要质量**：RSS 的 description 往往只有一两句，模型没东西可总结时就开始编。

## 做法

刻意没上复杂编排，四个阶段、各自独立的脚本：

**1. 抓取层**：cron 每 2 小时跑一次 fetch，拉所有 feed，只存 `guid`、规范化后的 `link`、`title`、`published` 和原始 content 字段进 SQLite。抓取与摘要分离是整条管线最重要的设计：摘要挂了随时重跑，不丢数据。

**2. 去重层**：link 去掉跟踪参数后取哈希作主键，title 再做一次模糊去重（编辑距离 / 前缀匹配）。纯代码，不用模型。

**3. 摘要层**：不是逐条摘要，而是**按源分组、批量请求**，要求输出 JSON——每条一句话结论 + 值不值得深读（是/否/存疑）。只对「值得深读」的少数条目做全文抓取和细摘要。两段式下来，token 用量约为逐条方案的 1/5。

**4. 输出层**：摘要写回 SQLite，同时生成一份 Markdown 日报推到 Telegram bot；再暴露一个只读 MCP 工具，让 Agent 随时能查「今天有什么值得看的」。第二个是后来加的，价值意外地高——Agent 有了新鲜、结构化、可信的信息入口。

## 踩坑点

- **正文抽取比想象中脏**：很多 feed 只有摘要，需要 fallback 到 readability 类抓取，且必须设超时，别让管线卡死在一个慢站点上。
- **模型会硬编**：content 为空务必在代码层先判空跳过，别指望 prompt 兜底。
- **RSSHub 实例不稳定**：自建实例 + 失败重试队列，别相信某次抓取一定成功。
- **时区**：published 格式五花八门，统一转 UTC 存储、展示时转本地，否则日报会混进昨天的条目。

## 可复用建议

- **能脚本解决的就别上 Agent 编排**：这条管线没有自主决策，确定性流程用确定性代码，Agent 只在「查询摘要」一步通过 MCP 工具出现。
- **中间产物全部落盘**（SQLite 就够），每个阶段幂等，任何一步坏了都能单独重跑。
- **记录每次摘要的 token 消耗**，跑一周再优化，比凭感觉调 prompt 有效。
- **判断与摘要分离**：先做廉价的分类判断，再对入选内容做贵的深加工。

## 总结

这条管线没有任何新概念：RSS、SQLite、cron、一次 LLM 调用，加一个 MCP 工具出口。它解决的不是「信息不够」，而是「信息触达成本太高」。如果你也有攒了几十个源却从不打开的阅读器，建议从一个源、一个 cron 脚本开始，先跑通，再谈智能。
