## 背景

大多数人用 Agent 的方式还是"一问一答"：你想起来了，去问它，它回答，然后就此沉默。OpenClaw 有一个不太显眼但会改变使用模式的机制——心跳（heartbeat）。网关按固定间隔（默认约 30 分钟）唤醒一次 Agent，让它读取工作区里的 HEARTBEAT.md，逐条判断哪些事项此刻该执行。相当于你有了一块 Agent 每次醒来都会主动查看的"值班记录板"。

## 问题：被动响应的天花板

一问一答能覆盖大量场景，但有三类事它天生做不了：

1. **周期性任务**：每天早上汇总收件箱、每周盘点磁盘空间；
2. **条件触发类**："CI 红了就告诉我"、"书签里躺了两周没读的文章提醒我"；
3. **长期跟进**："上周让我查的那个问题有结论了吗"。

这些事以前只能靠系统 cron + 脚本解决，但脚本没有上下文、不会写自然语言总结，维护成本高。心跳机制的价值在于：把"触发"交给网关，把"判断和执行"交还给带着完整上下文的 Agent。

## 做法：三步跑起来

**第一步，建文件。** 在工作区根目录创建 `HEARTBEAT.md`，纯 Markdown，随手可编辑。

**第二步，写条目。** 每条按"条件 + 动作 + 汇报策略"来写，例如：

- 每天 09:00 后的第一个心跳：检查收件箱，只在我有需要回复的邮件时通知我，其他情况静默。
- 每次心跳：磁盘占用超过 85% 时清理缓存，并汇报释放了多少空间。
- 每周五心跳：把本周未完成的 TODO 追加到日志文件，不单独打扰我。

关键是**汇报策略必须显式写出来**。没有这条，Agent 要么每次心跳都来刷存在感，要么什么都不说。

**第三步，调节奏。** 在网关配置里调整心跳间隔。观察类任务 30 分钟够用；告警类可以缩短，但要先评估 token 成本。

## 踩坑点

1. **间隔太短 = 纯烧钱。** 每次心跳都是真实的模型调用，5 分钟一次跑一晚上，账单会教你做人。先用默认值跑一周再调。
2. **条目太模糊。** "帮我留意一下邮件"这种写法，Agent 每次解读都不一样，产出不稳定。要写成可判定、可执行的动作。
3. **静默失败。** 心跳依赖 MCP/插件的工具（日历、邮件），凭证过期后心跳照常执行但什么都做不成，而你毫不知情。让 Agent 把每次执行结果追加到日志文件，定期扫一眼。
4. **重活别放心跳。** 心跳有超时限制，长任务会被直接掐断。重计算、长抓取交给主会话或脚本。
5. **通知疲劳。** 一周后你会开始无视聊天窗里的心跳推送。大部分条目应该是"无事静默，有事才说话"。

## 可复用建议

- 按用途分三段维护：**监控类**（条件告警）、**汇总类**（日报周报）、**清理类**（磁盘、TODO、过期提醒）。
- 像 code review 一样对待它：放进 git，条目变更有记录，出问题能回滚。
- 从 1~2 个条目起步，观察一周误报率和漏报率，再逐步加。
- 汇报去重：同类告警 24 小时内只报一次，避免同一个问题反复轰炸。
- 和 MCP 工具组合是甜点区：心跳负责"什么时候看"，工具负责"看到什么"，Agent 负责"判断和转述"。

## 总结

HEARTBEAT.md 本质上是把 Agent 从"问答机器"推成"值班助理"。它的核心不是让模型更聪明，而是提供了一个可靠的唤醒节奏，加一块人类可读、可维护的任务清单。实践下来最重要的经验只有一条：**写清楚"什么情况下才需要告诉我"**。做到静默为主、告警为辅，心跳才真正省心，而不是添乱。
