## 背景

我大部分 Agent 使用是被动式的：我提问，它回答，会话结束，Agent 就"死"了。但一个私人助理的真正价值往往在对话间隙——磁盘快满了、某个 PR 卡了两天、日历出现冲突。这些事要么你自己轮询，要么反复在聊天里敲"帮我看看 XX"。

OpenClaw 的 HEARTBEAT.md 就是冲着这个问题来的：Agent 按固定间隔醒来，读取工作区根目录的 HEARTBEAT.md。文件里有可执行的任务，它就用现有的工具（shell、浏览器、MCP、消息通道）去规划和执行；没有任务就保持沉默，不会硬凑一句回复。

## 问题

常见的两种替代方案都有短板：

1. **Cron + 脚本调模型 API**：时间精确，但没有上下文——没记忆、没工具、没消息通道，每个 job 都是一个孤立脚本。
2. **在聊天里反复催**：可靠但繁琐，而且人会忘。

HEARTBEAT.md 走中间路线：任务用自然语言声明，执行时享有一个完整 Agent 运行时。定时精度交给间隔配置，"该不该做、怎么做"的判断留给模型。

## 我的做法

1. 在工作区根目录建 HEARTBEAT.md，每个任务写清三要素：**触发条件 + 动作 + 通知渠道 + 明确的"不满足就沉默"规则**。
2. 任务示例：
   - "检查主机磁盘占用，若超过 85%，通过 Telegram 发告警并列出占用前三的目录；低于阈值不要发任何消息。"
3. 间隔用默认（约 30 分钟）即可。调试期可临时调成 5 分钟，观察一两个完整周期再改回去。
4. "发生了变化"类任务必须让 Agent 把上一次的状态落到快照文件（比如 `disk_usage.json`），每次心跳做对比。否则它分不清"新变化"和"上次已经报过"。
5. 跑一周后做减法：从没触发过的、或者让你烦的，删掉或收紧条件。

## 踩坑点

- **Token 成本**：每次心跳是一轮完整的模型调用，即使什么都不做。别设 1 分钟级间隔；文件保持精简，我个人上限 5 条任务。
- **模糊任务制造垃圾消息**："看看有没有什么有意思的事"这类任务会让 Agent 频繁打扰你。每个任务必须写清楚什么情况算"不需要报告"。
- **跨心跳无状态**：Agent 默认不记得"这条我已经告警过"，状态必须落文件。重复告警多半是这个原因。
- **别放交互式任务**：需要验证码、二次确认、人工授权的操作会反复失败或卡住。心跳任务应该是只读的检查和推送。

## 可复用建议

- 任务三要素模板可以直接抄：条件 / 动作 / 沉默规则，缺一不可。
- 状态进文件，别指望模型记忆：快照、日志都比"它应该记得"可靠。
- 和 cron 分工：精确调度、重计算交给 cron；"需要判断"的巡检交给心跳。心跳甚至可以反过来巡检 cron 任务的输出日志。
- 配合 MCP server 使用，心跳就变成通用看门狗：站点健康、证书到期、价格监控都能做。但一次只加一类任务，观察一周再加下一类。

## 总结

HEARTBEAT.md 的价值不在于"AI 变聪明了"，而在于把主动性变成一个可声明、可审查、成本可控的机制。它奖励克制：任务少、触发条件清晰、沉默规则明确，才能长期稳定运行。建议从一条任务开始，跑一周，你会很快知道它适不适合自己的工作流。
