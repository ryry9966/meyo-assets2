## 背景

OpenClaw 的 agent 行为，很大程度上由 workspace 里的几个 Markdown 文件决定。`SOUL.md` 是其中最容易被忽略的一个：它在会话启动时被注入上下文，定义"这个助手是谁、怎么说话、什么不做"。很多人的 workspace 里它还是模板默认内容，结果同一份配置，早上像个严谨的运维，晚上像个陪聊的。

## 问题

没认真写过 SOUL.md 的 agent，常见三类毛病：

1. **人设漂移**：跨会话、跨渠道语气不一致，用户感知割裂；
2. **边界模糊**：该问的不问（直接替你做决定），不该揽的照揽（删除、对外发消息、花钱类操作未经确认就执行）；
3. **指令冲突**：人格描述和 `AGENTS.md` 里的任务规范互相打架，模型行为变得随机。

## 做法

我的写法分四段，总长控制在 40 行以内：

- **身份**：两三句话。服务对象、能力范围、定位。不写形容词，写事实。
- **语气**：给可执行规则。比如"回复默认三段以内；不确定时直接说不确定，不编造"。
- **边界**：明确禁止项和升级路径。例如"涉及删除文件、对外发送、支付的操作，先列计划等我确认"。
- **分工**：SOUL.md 只放稳定人格，用户偏好放 `USER.md`，任务规范放 `AGENTS.md`，同一条规则只出现一次。

改完用一组固定的测试问题过一遍——让它总结一篇文章、拒绝一个越权请求——像跑回归测试。SOUL.md 进 git，每次调整有 diff 可查。

## 踩坑点

- **形容词没用**。"聪明、友好"模型翻译不成行为，"先复述我的问题再回答"才会被遵守；
- **写太长会稀释注意力**。我踩过 200 行 SOUL.md 导致工具调用明显变笨的坑，它还会挤占 TOOLS.md 和任务指令的权重；
- **别把它当安全边界**。SOUL.md 是提示词不是沙箱，模型仍可能被诱导复述内容，真正的防线在工具权限和 MCP 白名单上；
- **改了不生效**。它在会话启动时读取，编辑后需要重开会话，或让 agent 显式重读文件。

## 可复用建议

- 每条规则用"当 X 时，做 Y"的条件句，可测试、可回归；
- 维护 10 条左右的回归 prompt 集，随版本一起跑；
- 边界本质是产品决策：想清楚哪些事 agent 可自主、哪些必须停下来问人，写进升级路径；
- 多 agent 场景下，公共人格抽成一份，按 agent 覆盖差异部分，避免多处维护。

## 总结

SOUL.md 是成本最低、杠杆最高的一份配置。把它当代码写：短、具体、可测试、有版本。人格不是玄学，是一组能跑回归的行为约束。
