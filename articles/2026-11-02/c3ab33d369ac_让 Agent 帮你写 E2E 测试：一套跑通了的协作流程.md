# 背景

E2E 测试是回归保障里投入产出比最难平衡的一环：写起来慢、断言容易弱、UI 一改选择器全崩。团队里往往只有一两个人愿意维护测试目录，覆盖率长期停滞。最近几个月我们尝试把 Agent 接入 E2E 流程，让它承担「初稿生成」和「失败修复」这两块最耗人力的工作，人只负责定规范、审 PR。跑了一段时间，分享一些实测经验。

# 问题

- 写一条覆盖完整用户路径的用例，熟手半小时起步，新人常卡在环境和 fixture 上；
- UI 改版后测试批量变红，修复是纯体力活；
- 直接让 Agent「看代码写测试」效果很差：它不知道页面真实长什么样，选择器和等待逻辑基本靠猜。

# 做法

核心思路：不给 Agent 静态代码，给它一套浏览器工具，让它像 QA 一样先「操作」再「落笔」。

1. **接工具**：通过 MCP 把浏览器能力（导航、截图、点击、读取 DOM）和测试运行器（跑单条用例、读报告）暴露给 Agent，本地环境用一次性容器拉起。
2. **给规范**：准备一页测试约定文档——目录结构、Page Object 写法、强制 `data-testid`、断言基线——作为项目上下文注入，而不是每次对话临时纠正。
3. **走流程**：人只描述一条业务路径（如「游客加购到支付取消」），Agent 打开本地环境实际走一遍，边操作边记录关键状态，最后产出 spec 草稿和 Page Object 改动，提 PR。
4. **闭环**：CI 挂上 trace 和截图产物。用例挂了，把 trace 和报错喂回 Agent，让它判断是产品 bug、环境问题还是选择器失效，并给出修复 diff。

# 踩坑点

- **弱断言**：Agent 倾向「走到哪断言到哪」，比如只断言元素存在。约定里必须明确：断言业务结果（订单状态、金额、跳转 URL），不是 UI 痕迹。
- **脆弱选择器**：哪怕写了 data-testid 规范，Agent 偶尔仍用文本定位。我们在 CI 加了 lint，关键路径禁用文本匹配，违规直接打回。
- **幻觉 API**：Agent 会编造不存在的方法或用旧版语法。所以生成后必须先跑通再提 PR，跑不通的草稿没有评审价值。
- **Flaky**：Agent 对异步等待理解不可靠，爱写 `sleep`。约定里统一禁掉，只允许 auto-wait 和 expect 轮询。
- **环境安全**：Agent 只能指向本地或一次性环境，账号用测试号，权限上直接切断预发和生产。

# 可复用建议

- 把测试约定写成一页文档随仓库维护，比在对话里反复纠正省力得多；
- Agent 产出按「草稿 PR」对待，评审标准与人工代码完全一致；
- 每个任务只让 Agent 做一件事：要么新增用例，要么修复一批失败，不要混合；
- trace 和录屏是 Agent 排障效率最高的输入，比只贴报错文本有效；
- 修选择器这类高频低价值工作可以放心交出去；核心链路的断言设计，仍然应该由人拍板。

# 总结

Agent 写 E2E 的正确姿势不是「一键生成测试」，而是把人从选择器维护和用例补齐中解放出来，把判断力留在断言设计和验收标准上。工具接入一天就能搞定，真正决定效果的是约定文档和「跑失败→喂 trace→修」的反馈闭环。建议先挑一条高频回归路径试跑，稳定了再横向铺开。
