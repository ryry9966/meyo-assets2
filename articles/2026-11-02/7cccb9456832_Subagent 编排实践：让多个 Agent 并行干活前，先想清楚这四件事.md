## 背景

单个 Agent 跑长任务的老问题大家都遇到过：上下文越滚越长，模型开始“忘事”；工具调用串行排队，一个搜索卡住，后面全等；中间结果全堆在主对话里，几轮之后质量明显下滑。OpenClaw 的 subagent 机制（通过 MCP 工具或插件把子任务派给独立 Agent）让“拆任务、并行跑、只回传结果”变成可行方案。最近我把一批批处理任务（多文件同类修改、批量信息搜集）迁移到 subagent 编排，把过程和坑记录一下。

## 问题

具体痛点有三个：

1. **串行瓶颈**：30 个文件的同类处理，主 Agent 一个个跑，耗时和上下文双重爆炸。
2. **上下文污染**：所有中间输出都进主对话，信噪比越来越差，主 Agent 后期开始偏离初始指令。
3. **错误传播**：某一步失败，整条链路报废，重跑代价大。

## 做法

**第一步：判断任务可拆性。** 不是所有任务都能并行。标准很朴素：子任务之间无共享写资源、无顺序依赖、单个子任务的上下文独立可完成。三条缺一条，就别硬拆。

**第二步：定义子任务契约。** 每个 subagent 的输入输出固定成结构化格式：

```yaml
task: refactor_module
input:  { file_path, style_guide_ref }
output: { status, changed_files, notes }
```

契约的意义在于：主 Agent 汇总时只读结构化结果，不去读子 Agent 的完整过程。上下文污染从根上被切断。

**第三步：资源隔离。** 每个 subagent 用独立工作目录，涉及代码修改的用 git worktree 各自分出，避免并行写冲突。

**第四步：控制并发度。** 不是越多越好。API 限流、机器负载、结果合并复杂度都随并发数上涨。实测 3~5 路并发是性价比比较稳的区间。

**第五步：汇总与失败处理。** 主 Agent 只做两件事：收集结果、对失败任务决定重试或降级。失败任务的错误信息原样带回，不要让主 Agent 猜着补。

## 踩坑点

- **子 Agent 之间互相“以为”对方知道。** 每个 subagent 是独立上下文，看不到主对话历史。它需要的信息必须显式写进 input，一点都不能省。
- **过度拆分。** 本来就小的任务拆成 5 个 subagent，调度开销超过收益。经验法则：单子任务预计超过 3~4 轮工具调用才值得拆。
- **共享资源竞争。** 两个 subagent 同时改同一个文件或同一张表，结果不可预测。写操作要么隔离，要么排队。
- **Token 成本失控。** 并行意味着成本乘以并发数。给每个 subagent 设轮数/预算上限，超限直接判失败，别让它空转。
- **合并质量劣化。** 子 Agent 输出风格不一，主 Agent 合并时容易“再创作”。强制按 output schema 返回，主 Agent 做机械合并而非重新生成。

## 可复用建议

1. **契约模板化**：input/output schema 做成固定模板，新任务只填字段，降低每次编排的心智成本。
2. **幂等优先**：每个子任务设计成可重跑，失败重试不需要清场。
3. **主 Agent 保持“薄”**：只做调度和汇总，不碰具体工作，上下文才不会爆。
4. **先串行验证再放量**：新类型任务先单线程跑通一个样本，确认契约没问题，再开并行。

## 总结

Subagent 编排不是“多开几个 AI”这么简单，本质是工程问题：任务怎么拆、契约怎么定、资源怎么隔离、失败怎么兜底。这四件事想清楚了，并行的收益才真正落得下来。反过来说，如果一个任务拆不出清晰的契约，那它大概率不适合并行——老老实实串行，反而更省心。
