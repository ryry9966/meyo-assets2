## 背景

大多数人对 Agent 的用法是"应答机"：你提问，它回答，会话结束就静止。OpenClaw 里有一个容易被忽略的机制——heartbeat（心跳）：Agent 会按固定间隔自动醒来一次，读取工作区里的 `HEARTBEAT.md`，判断有没有值得做的事。这个文件就是把 Agent 从被动应答切到主动值班的开关。

## 问题

没有心跳时，时间敏感的事全靠你自己记：磁盘快满了、某个仓库来了新 issue、日志开始刷 ERROR、答应别人的事到点了没跟进。你可以自己写 cron 和脚本，但逻辑散落在系统各处，Agent 反而成了摆设。理想状态是：巡检逻辑写在 Agent 能理解的地方，由 Agent 自己执行。

## 做法

1. 在工作区（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`，用清单体写，每条 = 触发条件 + 动作 + 输出去向：

```markdown
# 心跳任务
- 检查日志有无 ERROR，有则汇总最近 3 条发给我
- GitHub 通知按仓库归类，只列需要我决策的
- 磁盘占用 > 85% 时提醒，平时不说
- 没事做就回复 HEARTBEAT_OK
```

2. 在配置里开心跳并控制输出（键名以你的版本文档为准）：

```json
"heartbeat": { "every": "30m", "target": "none" }
```

`every` 控制间隔，`target` 控制结果发到哪：`none` 表示静默执行（适合只做记录类任务），也可以固定指定某个聊天渠道。

3. 直接改文件即可，下个 tick 生效，不用重启。空转时让模型回 `HEARTBEAT_OK`，并配置不把这种短确认推送到聊天里，省 token 也省通知。

4. 观察一两天：看会话日志里心跳触发的频率和 token 消耗，再决定加条目还是减。

## 踩坑点

- **写成散文**。心跳每个 tick 都会把文件塞进上下文，文件越长越烧钱，长篇描述还会让行为漂移。保持短、可执行。
- **把 heartbeat 当 cron**。`every: 30m` 的语义是"至少隔这么久"，不是准点触发。要精确到某时某分的事，交给系统级调度或让心跳去调调度工具，心跳适合轮询式巡检。
- **target 用 last 的串台问题**。结果可能发到你最后活跃的渠道，半夜一条巡检汇报突然出现在工作群里。要么 `none`，要么固定一个专用渠道。
- **共享主会话**。心跳和你聊天走同一个会话上下文，长任务会占场子。心跳任务要幂等、可中断、避免删除类副作用。
- **没有输出上限**。"有异常就发消息"这种条目，一定补上触发条件和频率上限，否则坏一次能轰炸你一整天。

## 可复用建议

- 条目模板：**条件 → 动作 → 输出去向 → 频率上限**，四项缺一不可。
- 分层：高频轻量巡检放心跳；重活（跑构建、长分析）留给显式指令或 cron，别让心跳背着跑。
- 把 workspace 纳入 git，`HEARTBEAT.md` 每次改动可回溯，出问题能 diff。
- 每周复盘心跳日志：从不触发的条目删掉，频繁触发的考虑固化成正式脚本。

## 总结

HEARTBEAT.md 不是什么智能涌现，它只是一份按 tick 重复注入的清单——但这恰好是最工程化的主动方式：成本可算（每 tick 的 token），行为可审（文件在 git 里），边界可写（条件和上限都在条目里）。建议从一个真实痛点起步，写两三条，跑一周，再决定要不要养大它。
