## 背景

大多数 Agent 的交互模型是"一问一答"：你不说话，它就静止。但想让 agent 真正融入日常工作，关键在于它能定期自己醒来，检查该做的事。OpenClaw 的 heartbeat 机制就是为这个设计的：agent 每隔一段时间自动触发一次心跳（默认 30 分钟量级，可配置），如果 workspace 里存在 `HEARTBEAT.md`，其内容会作为本次心跳的上下文注入，agent 读完自行决定"做点什么"还是"无事可做"。

## 问题

定时任务交给 cron 也可以，但 cron 只适合精确时刻触发的确定性任务。实际使用中有一类需求介于两者之间："有空就看一眼，有事就办，没事别烦我"——比如 downloads 目录有新文件需要归档、某个长期任务是否停滞、MCP 工具是否还连得上。这类事的触发条件模糊且依赖上下文，写成脚本很痛苦，写成 HEARTBEAT.md 里的一条自然语言检查项却很自然。

## 做法

1. 在 agent workspace 根目录创建 `HEARTBEAT.md`。
2. 每条任务写成"条件 + 动作 + 兜底"三段式，例如：
   - 若 downloads 有超过一天的 PDF，整理进 archive 并简短告知我；否则跳过。
   - 每次心跳检查 filesystem MCP 工具连通性；失败时写入状态文件，不重复告警。
3. 间隔先用默认值，观察几天实际触发频率再调。
4. 无事可做时让 agent 回复 `HEARTBEAT_OK`，框架会静默吞掉这次心跳，不打扰你。

## 踩坑点

- **成本**：心跳无论有没有事都消耗一次模型调用。文件越长、任务越重，每次心跳越贵，保持一屏以内。
- **模糊条件导致骚扰**：任务没写清"什么情况下跳过"，agent 会倾向于做事并给你发消息。每条都要有明确的 skip 条件。
- **心跳不是 cron**：它是间隔触发，不是精确时刻。"每天 9 点执行"这种需求请用 cron job，别硬塞进来。
- **幂等性**：同一任务每个心跳都可能被重新评估。要么动作本身幂等，要么让 agent 先查外部状态文件再决定动不动手。
- **别放敏感信息**：HEARTBEAT.md 是作为 prompt 注入的，写进去的任何内容都会进模型上下文。

## 可复用建议

- 把 HEARTBEAT.md 当代码维护：进 git、写注释、每次改动有明确理由，回溯时你会感谢自己。
- 任务分层：巡检类（便宜、高频）放心放；重活（批量整理、生成报告）写清触发阈值，或改走 cron / 手动触发。
- 主动权可收放：想临时静默，把文件改名或清空即可，无需改配置重启。
- 用 1-2 条任务起步，跑几天看心跳日志（误报率、单次成本），再逐步加条目。

## 总结

HEARTBEAT.md 的本质，是把"你想起来的事"迁移成"agent 定期自己想起来的事"。它不替代 cron，也不替代 MCP 定时工具，而是补上了"低精度、上下文敏感的主动性"这一层。写好它的核心纪律就三条：每条任务可验证、有兜底、默认静默。控制住成本和噪音之后，它大概是让 agent 真正"住"进你系统里成本最低的方式。
