## 背景

团队每天要交一份运行日报：服务异常、定时任务成败、Agent 任务的执行情况。过去一直是人工摘录——翻几个日志文件、挑关键行、贴进模板。这活不难，但有两个隐性代价：一是口径漂移，今天看 A 文件、明天看 B 文件，数字对不上；二是不可复现，出了争议没人能说清"昨天那个数怎么来的"。

## 问题拆解

落地前把痛点列了一下：

- 数据源分散：服务日志、cron 输出、Agent 运行记录在不同位置，格式各异；
- LLM 直接"读日志写日报"会编数字，实测失败次数能差出一截；
- 日志量波动大，全量塞上下文又贵又容易截断；
- 日报是给人对账的，格式必须稳定，不能每次一个样。

## 做法：四段式流水线

**1. 采集层。** 调度器每天固定时间触发，通过一个自写的 MCP tool 拉取各数据源，落成中间 JSONL。原始日志只存路径和行号引用，不进正文。

**2. 归一化层。** 统一 schema：`ts / source / event_type / level / metrics / raw_ref`。这一步是纯代码，不涉及模型。时区在这里统一转掉，并显式记录本次日报的统计窗口。

**3. 汇总层。** 先用脚本算确定性的聚合指标：成功/失败数、Top 错误、耗时分位数。LLM 只做两件事：把指标翻译成一段人话；对异常条目给出归因猜测，且必须标注"待人工确认"。提示词模板版本进 Git，改模板等于改代码。

**4. 输出层。** 按固定模板渲染 Markdown，推送到群 webhook，同时归档到仓库。schema 校验不过就走降级模板——宁可发一张纯表格，也不发空报告或错报告。

## 踩坑点

1. **别让模型算数。** 第一版直接丢日志让模型统计，数字对不上账。改成脚本算好、模型只叙述后，问题消失。
2. **时区边界。** 日志是 UTC，日报按本地日切，跨零点的任务会被算错天。必须在采集层统一转换，而不是渲染时补救。
3. **幂等。** 手动重跑会产出第二份日报。按日期做幂等键，重跑即覆盖。
4. **流水线自己会挂。** 加了心跳上报，连续两天没产出就在群里报警。自动化任务没有监控，等于没做。

## 可复用建议

- Schema 先行：报告格式是和数据源之间的契约，先定 schema 再写逻辑；
- 中间产物落盘：排查问题时能回放，补数时能重算；
- 留 dry-run 模式：改模板、改 prompt 后先跑一遍不推送，肉眼确认再上线；
- prompt 和模板当代码管理，不要散落在脚本字符串里。

## 总结

一句话原则：**确定性代码负责事实，LLM 负责叙述。** 这条流水线跑稳定后，每天省下的不只是十几分钟人工，更重要的是口径一致、结果可追溯——日报从"一个人的记忆"变成了"一个可复现的产物"。后续如果接入更多 Agent 任务源，只需要在采集层和 schema 上扩展，下游不用动。
