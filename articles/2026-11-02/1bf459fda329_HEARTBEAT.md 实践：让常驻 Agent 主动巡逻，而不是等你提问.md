## 背景

大多数 Agent 交互是被动式的：你提问，它回答，会话结束就归档。但如果你跑的是一个常驻的 OpenClaw 网关（接在 Telegram / 终端上的 24 小时 agent），它其实具备"自己醒着"的条件。OpenClaw 的 heartbeat 机制就是为此设计的：网关每隔一段时间（默认约 30 分钟，可在配置中调整）唤醒 agent 一次，agent 醒来后读取工作区里的 `HEARTBEAT.md`，自行判断有没有值得做的事。无事就静默结束这一轮，有事就执行并汇报。这个文件，本质上是你交给 agent 的值班日志。

## 问题

被动模式有两个代价：一是"要问什么"得靠你自己记——看看 CI 过没过、磁盘还剩多少，提问的负担全在人这边；二是响应滞后，等你发现问题时往往已经晚了。但直接放开让 agent "主动干活"也不行，实践中立刻会遇到三个坑：空转（每次心跳都是一轮完整上下文调用，token 照烧）、打扰（动不动发"一切正常"）、幻觉式巡逻（没事找事，编造问题来显得有产出）。所以 HEARTBEAT.md 的核心工程问题只有一个：**如何把主动性约束成低噪声、可预期、可审计。**

## 做法

1. **建文件，定结构。** 在 agent 工作区根目录建 `HEARTBEAT.md`，每个条目按固定结构写：检查什么 → 判定阈值 → 触发后做什么 → 什么情况下才汇报：

```markdown
总则：无异常不发言；每天最后一次心跳发一条当日汇总。

- [ ] 磁盘：检查 /data 使用率，> 85% 才告警，附 du 排名前三的子目录
- [ ] 夜间任务：读 ~/logs/nightly.status，出现 failed 才汇报
```

2. **条目要少。** 初期 2~3 条即可。心跳是完整 agent 轮次，清单越长成本越高，注意力也被稀释。
3. **只放轻检查。** 读文件、跑一条命令、比对状态这类秒级操作适合放心跳；重活交给 cron 或脚本，脚本把结果写进状态文件，心跳只负责读和判断。
4. **写明静默规则。** 文件开头的总则比任何条目都重要："没有异常不要发消息"必须白纸黑字。
5. **用 git 管理它。** 这是你对 agent 的指令集，改了什么、何时改的，值得留痕。

## 踩坑点

- **模糊条目是噪声之源。**"帮我盯着项目"这种写法会让 agent 每次心跳都纠结要不要汇报，最后要么疯狂打扰、要么彻底沉默。路径、阈值、命令必须具体。
- **一次性提醒别放这里。** 心跳是周期性的，"周三下午提醒我开会"放进去会每周触发，一次性事项应走专门的定时/提醒功能。
- **别在心跳里放大操作。** 会写文件、会调外部重接口的内容容易形成自触发循环，成本失控。
- **别依赖 agent 的时间感。** 它对"现在几点"的感知不可靠，用文件 mtime、cron 产物的时间戳这类外部证据代替。

## 可复用建议

把 `HEARTBEAT.md` 当"巡检配置"维护，可以沉淀一个模板：头部写汇报风格（走什么渠道、什么算紧急），正文每条一个 check，尾部设"临时观察区"并注明移除条件，比如"观察 v2 部署，稳定一周后删除此条"。这套模式不限于 OpenClaw——任何具备定时唤醒或 webhook 触发入口的 agent 框架，同样的清单结构都能直接套用。

## 总结

HEARTBEAT.md 的价值不是"让 AI 更主动"，而是给主动性一个受控接口：**清单短、阈值明、默认静默、变更留痕**。做到这四点，agent 才能从你问到才动，变成有事它先说、没事不打扰的值班员。
