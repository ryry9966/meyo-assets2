## 背景

LLM 本身无状态。每次会话开始，Agent 对用户的了解归零——上周你说过"回复用中文、示例用 TypeScript、别加表情"，这周它照样给一堆英文长答案。在 OpenClaw 这类常驻场景（连接 MCP 工具、跑自动化任务）里问题更突出：助手越常用，重复交代偏好的成本越烦人。

## 问题：三种常见做法为什么不够

1. **全塞 system prompt**：最简单，但偏好一多 prompt 膨胀，注意力被稀释，模型反而开始忽略关键约束，token 成本也线性涨。
2. **全量聊天记录做 RAG**：能召回"上周聊了什么"，但偏好不是普通事实。"用 pnpm"是原话，"他偏好 pnpm"是归纳结论，向量检索很难区分两者。
3. **只写不改**：很多实现把记忆当 append-only 日志，三个月后"用户在 A 公司"和"用户在 B 公司"并存，Agent 随机采信，行为飘忽。

本质问题：写入、存储、检索、更新没有被当成一个系统工程来设计。

## 做法：分层存储 + 独立写路径

**存储分两层**

- **L1 用户画像（结构化）**：SQLite 一张表，只放偏好类条目，常驻注入 system prompt，硬上限 800 token 左右。
- **L2 情节记忆（向量库）**：项目背景、历史任务结论，按需检索，不常驻。

**写路径是关键**。不要让主 Agent 在对话中随手写记忆，加一步独立抽取：把对话片段交给小模型或一个 MCP memory 工具，输出结构化候选条目：

```json
{"key":"package_manager","value":"pnpm","type":"preference",
 "confidence":0.9,"source_session":"s_0412"}
```

写入信号分两类：显式（"记住我用 pnpm"）直接高置信写入；隐式（用户纠正、重复选择）累积到阈值再写，避免一次性事件污染画像。

**更新与冲突**：同 key 新条目做 supersede（替换）而非追加，旧条目保留 source 便于回溯；加时间衰减，长期未命中的低置信条目定期降权归档。

**读路径**：画像整体注入（小、稳定、可缓存）；情节记忆暴露成 MCP 工具 `memory_search`，由 Agent 主动调用。记忆条目一律按不可信输入处理，检索结果过一遍注入防护，别让记忆库变成 prompt 注入的暗门。

**让人能看、能改**：提供 `/memory` 命令列出当前画像条目，允许删除与修正，用户主动修正的条目置信度拉满。这一步对信任度的提升超过任何算法优化。

## 踩坑点

- **偏好和事实混存**：一次性任务细节（"周三要交报表"）写进画像，两周后画像全是垃圾。入库前先分类，`type=preference` 才进 L1。
- **缺 provenance**：每条记忆必须带 source_session 和 updated_at，否则 Agent 行为异常时你答不上"它为什么会这样"。
- **敏感信息直接入库**：先过 redaction，密钥、token 类内容用规则拦截。记忆库是长期持有的，泄露面比单条聊天记录大得多。
- **画像无限膨胀**：常驻注入必须设上限，超了就强制合并条目或降级到 L2。
- **检索每轮必调**：情节检索有延迟和成本，做成主动工具调用，别每轮自动触发。

## 可复用建议

1. 条目 schema 固定下来：key/value/type/confidence/source/updated_at，别用自由文本存记忆。
2. 读写分离：写走抽取管道，读走注入 + 工具，主对话模型不承担记忆维护职责。
3. 写回归脚本：回放历史会话，断言"偏好 X 是否被遵守"。记忆系统没有测试，等于没有。
4. 先做小：L1 结构化画像贡献八成收益，向量库可以晚点加。

## 总结

让 Agent"记住你"，靠的不是更大的 context，而是一条有分类、有更新、有来源、可被用户审计的记忆管道。借 OpenClaw 插件体系和 MCP 工具，落地这套东西不需要多深的基建——一张 SQLite 表、一个抽取调用、一个检索工具，就是可用版本。先让画像小而准，再谈长期记忆。
