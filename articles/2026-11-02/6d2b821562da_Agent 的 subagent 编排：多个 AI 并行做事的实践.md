## 背景

单个 Agent 串行干活的问题，用过的人都有体感：让它排查一个跨多模块的 bug，它要读十几个文件、翻日志、查文档，一条线跑到底。结果就是两点：慢，以及主上下文被大量中间输出塞满，越到后面越“失忆”。

OpenClaw 的 subagent 机制给了另一个思路：主 Agent 把独立子任务分给多个 subagent 并行执行，每个 subagent 有自己的上下文，跑完只回传一份压缩后的结论。

## 一个具体问题

上周的真实场景：排查“插件加载后 MCP 工具注册失败”。串行模式下主 Agent 花了大量 token 读完插件目录、MCP 配置、日志，上下文很快被撑爆，后面开始瞎猜。

拆解后发现这个任务天然可并行：

- 分支 A：静态梳理插件目录结构和加载入口
- 分支 B：读 MCP 配置与工具注册链路
- 分支 C：扫描日志里的报错模式

三个分支互不依赖，且全部只读。

## 做法

1. **划定边界**：只把“只读、独立、可验证”的任务交给 subagent。写操作一律留在主 Agent。
2. **写窄 prompt**：每个 subagent 只给一个目标、一个范围、一个输出格式。比如分支 C 的要求是“只看最近 24h 日志，输出 3 条以内报错模式，每条附文件路径和行号”。
3. **限制并发**：同时最多 3–4 个 subagent。太多会撞 API 限流，结果质量也会掉。
4. **约定返回格式**：结论一句话 + 证据（文件：行号）+ 存疑点。禁止把原始文件内容整段搬回来。
5. **主 Agent 汇总与抽查**：合并三个分支的结论，对关键结论做一次抽查（比如真的打开那个文件看一眼），再决定下一步。

这一轮下来，原本十几分钟的串行排查压缩到三四分钟，主上下文里只剩三份各几百 token 的摘要，干净得多。

## 踩坑点

- **subagent 拿到写权限**：有一次手滑给了全量工具，两个 subagent 同时改同一个配置文件，直接互相覆盖。教训：subagent 默认只读。
- **返回内容不压缩**：早期让 subagent“把找到的都贴回来”，结果三份原始输出照样把主上下文撑爆，并行变成了并行的污染。必须强制“结论式”返回。
- **跑飞**：没有范围约束时，subagent 会顺手去“修”它发现的问题，越界改代码。prompt 里要明确“只调查，不修改”。
- **递归 spawn**：subagent 又开 subagent，层级失控。要设深度上限，我们目前硬编码为 1。
- **成本翻倍**：并行是拿 token 换时间，任务拆得越碎越贵。小任务不值得拆。

## 可复用建议

- 并行化的判断标准就一条：任务之间是否**只读且互不依赖**。不满足就老老实实串行。
- 把 subagent 返回格式固化成模板：结论 / 证据路径 / 存疑点。可验证性比信息量重要。
- 并发 3–4、深度 1、subagent 只读，这三个限制先固定下来，跑稳了再逐步放开。
- 每次编排记录各 subagent 的 prompt 和返回，方便复盘哪条分支在浪费钱。

## 总结

subagent 编排的核心价值不是“快”，而是**上下文的隔离与压缩**——并行只是副产品。真正的工程量在定义任务边界和返回契约上：边界划清了，多 Agent 并行很稳；划不清，并行只会更快地制造混乱。建议从一次真实排查任务起步：三个只读分支、固定返回模板、并发上限 3，先把这条最小链路跑通，再谈更复杂的编排。
