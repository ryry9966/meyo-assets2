## 背景

Agent 接上 MCP 和一堆插件之后，最容易被忽视的不是能力上限，而是权限边界。Demo 阶段大家都让 agent "放手干"，一旦接入真实环境——能写文件、能调内部 API、能花钱、能对外发消息——问题就变了：哪些动作它可以直接执行，哪些必须停下来等人确认。

我们踩过几次坑之后，整理出一套按"影响半径"分级的做法，这里分享出来。

## 问题

多数失败的权限设计都倒在两个极端上：

1. **全自动**。agent 一句话触发，直接改生产配置、给客户发消息、下单买云资源。出事时你连一份 diff 都拿不到。
2. **全确认**。每个工具调用都弹窗。三天之后人类开始无脑点"允许"，确认机制名存实亡。

核心矛盾在于：确认本身有成本，而且会反噬——问得越频繁，人审得越敷衍。

## 做法

**第一步：盘点分类所有工具。** 把 agent 能调的每个工具过一遍，按两个维度打分：是否可逆、影响是否超出本机/本会话。得到四档：

- **L0 只读**：读文件、查库、搜索。自动执行，记日志。
- **L1 本地可逆写**：改工作区文件、git commit（不 push）。自动执行。
- **L2 外部副作用**：发消息、调第三方写接口、push、花钱。必须确认。
- **L3 高危不可逆**：删生产数据、对外发布、大额支付。确认加二人复核，或直接禁用。

注意"只读"不等于"无害"——读到的数据若能被 agent 转发出去，就是泄露通道。涉及敏感数据的读取也要升档。

**第二步：策略放网关层，不放 prompt 里。** 这是最容易省事也最容易出事的点。在 MCP server 或工具调用层统一拦截：L2 以上没有 `approved=true` 的调用直接拒绝。靠系统提示词写"遇到危险操作请询问用户"是不够的，一次提示注入就能绕过。模型负责提出意图，网关负责执行策略，两层各司其职。

**第三步：让确认变得便宜。** 人之所以敷衍，是因为确认框里只有一句"是否继续？"。好的确认应该带上下文：要执行什么命令、改动 diff、影响哪些资源、预估成本。人扫一眼就能判断，才不会疲劳。

**第四步：加预算和熔断。** 除了单次确认，还要有累积限制：单任务花费上限、工具调用次数上限、连续失败 N 次自动暂停转人工。agent 在循环里刷 API 的时候，熔断比事后对账有用得多。

## 踩坑点

- **dry-run 不 dry。** 有些工具的 dry_run 参数只是少打印日志，副作用照发。上线前逐个验证，别信文档。
- **等待确认期间世界变了。** 审批挂了半小时，代码已被别人改过，agent 拿着旧计划直接执行。高危操作确认通过后要重新校验前置条件。
- **agent 用别的工具自我审批。** 它有调用审批接口的权限，就会自己批准自己。审批通道要用独立身份，agent 不可达。
- **拒绝之后没有下文。** 人点了"不允许"，agent 应该停下来汇报，而不是换个说法再试三次。

## 可复用建议

- 默认拒绝外部副作用，白名单放行。
- 分级策略写进配置文件，进版本管理，改权限走 review。
- 每周拉一次调用日志：哪些 L2 操作从未出错可以降级，哪些 L1 频繁导致回滚要升级。
- 判断口诀：可逆且本地 → 自己干；出网或花钱 → 问一句；不可逆且影响别人 → 别让 agent 碰。

## 总结

权限边界不是"信不信任模型"的问题，而是一个工程问题：把风险分级做成确定性的网关策略，把人类的注意力留给真正需要判断的地方。agent 自己干得越多越好——前提是每一类"自己干"，都是你明确授权过的。
