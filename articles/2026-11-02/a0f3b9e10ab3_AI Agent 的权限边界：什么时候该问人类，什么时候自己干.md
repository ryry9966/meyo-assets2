## 背景

OpenClaw 这类 agent 框架跑起来之后，最常见的问题不是"不会干活"，而是"不知道哪一步该停"。工具一多——MCP 服务、插件、shell、消息通道——agent 手里就有一份很长的可执行动作清单。哪些动作它可以自己做，哪些必须回头问人，这个边界如果靠感觉拍，结果只有两种：要么每步都弹确认，你退化成人肉按钮；要么它自作主张删文件、发消息、调付费 API，你事后救火。

## 问题

失败模式就两类：

- **保守失败**：权限收得太紧，agent 无法自主完成任务，自动化变成"每步点确认的遥控器"。
- **激进失败**：权限放得太开，一个写操作在错误上下文里执行，代价不可逆。

关键在于两类错误的代价不对称：多确认几次只是烦，放错一次可能回不来。所以边界设计应偏向保守，但要用工程手段压低单次确认的成本，而不是靠堆确认次数。

## 做法

1. **按"可逆性 + 影响半径"给工具分三级**：
   - 只读类（搜索、读文件、查状态）：直接放行；
   - 可逆写类（走 git 的本地修改、写草稿）：自动执行，但强制留审计日志和 diff；
   - 不可逆/外溢类（删数据、对外发消息、花钱调 API、动生产配置）：必须人工确认。
2. **确认必须带上下文**：执行什么、影响哪些资源、怎么回滚。只弹一句"是否执行"的确认毫无意义，人会条件反射按 yes。
3. **默认拒绝**：确认请求超时无人响应，agent 应该停下，而不是猜一个动作继续跑。
4. **预算兜底**：给高危工具设调用频率和金额上限，即使判断错了，损失也有天花板。
5. **定期复盘日志**：总是被秒批的确认，说明分级过严，可以降级为自动；让你心惊的自动动作，就升级为确认。

## 踩坑点

- **确认疲劳**：弹得太频繁，人就会无脑通过，机制名存实亡。宁可提高单次确认的信息密度，也不增加次数。
- **确认嵌进循环**：批处理 50 个文件逐个问，任务直接卡死。循环里应汇总成一次批量确认。
- **粒度太粗**：把整个 shell 当一个"高危工具"统一确认，等于没分级。应按命令模式拆分，只读命令白名单放行。
- **只有拦截没有记录**：拦下的和放出的动作都要落日志，否则事后没法区分是权限设计问题还是模型判断问题。
- **插件权限继承**：新装的 MCP/插件默认继承宽松权限是常见坑，新工具应默认进"需确认"档。

## 可复用建议

- 判断依据只用三个词：**可逆吗、影响谁、错一次多少钱**。
- 确认的价值在信息量，不在次数。
- 权限分级是活的配置，随日志复盘迭代，不要一次定死。

## 总结

权限边界不是一道墙，而是一个带审计的闸门系统。让 agent 真正干活，同时敢让它长期替你干活，前提是你在设计层面回答清楚"哪一步必须停下来问你"。把分级写进配置、把上下文带进确认、把日志留作迭代依据——这三件事做好，"自己干"和"问人类"就不再是二选一，而是一条清晰可维护的工程界线。
