## 背景

社区每周都有固定动作：整理本周值得看的帖子和资源，发一篇汇总。做了一段时间后发现，真正耗时的不是写，而是收集素材、查重、排版、按时发出去这些机械环节。于是用 OpenClaw 的 agent 调度加自写 MCP 工具，搭了一套"自动起草 + 人审 + 定时发布"的管线。注意目标不是全自动灌水，第一版红线就是：**发布前必须过人审**。

## 问题

真正要解决的就三件事：

1. 模型产出的内容质量和格式不稳定；
2. 素材和成品帖都可能重复；
3. 失败恢复：一重试就可能重复发布。

## 做法

整体流程如下：

```
cron 触发 → OpenClaw agent → 素材收集(MCP tool)
  → URL 归一化去重(SQLite) → 草稿生成 → 人审消息
  → community.publish(带幂等键) → 状态落库
```

**1. 发布动作封装成 MCP tool。** 不让模型直接拼 HTTP 请求。写了一个 `community.publish` 工具，入参只有 title、body、idempotency_key，鉴权、频率限制、错误码重试全部在工具层处理。模型只负责产出结构化字段。

**2. 素材管线。** RSS 与抓取结果先做 URL 归一化（去 utm 参数、统一协议），哈希后存 SQLite 查重，再生成摘要进草稿模板。去重状态全部落库，不依赖会话记忆。

**3. 幂等与状态机。** 发布记录三态：`pending → published / failed`。先落库 pending 再调 API，成功后更新；重启后扫描超时的 pending 条目转人工确认，绝不盲目自动重试。

**4. 降级模式。** 前两周只跑 draft-only，草稿进审稿频道，人点确认才发。观察误判率和格式问题后，才放开定时发布。

## 踩坑点

- **直接让模型输出整篇 Markdown**，社区渲染器不认其中一部分语法，多次翻车。改成模板渲染 + 结构化字段后稳定。
- **cron 和手动触发撞车**导致同一天双发。加了幂等键和进程内锁才堵住。
- **去重只比标题不够**，同一篇文章换个标题就漏网。改成 URL 归一化 + 标题相似度双闸。
- **模型会幻觉出"看起来很像真的"的链接**。现在发布前对全部 URL 做 HEAD 校验，404 直接打回草稿。
- **把重试逻辑写进提示词**（"失败请再试一次"）是错的。重试必须收敛在工具层，模型不该控制写操作的重试次数。
- **凭据安全**：用单独的小权限账号，token 走环境变量，不进代码库。

## 可复用建议

1. 所有写操作一律工具化 + 幂等键，这是底线，没有例外。
2. 状态外部化到 SQLite 或文件，别指望对话上下文帮你记住"昨天发过什么"。
3. 节奏固定为：draft-only → 半自动（人审后定时发）→ 再考虑全自动。跳步的代价就是删帖和道歉。
4. prompt 和草稿模板纳入版本管理，出了问题能回溯到具体版本。
5. 日志记录每次发布的输入、输出和完整工具调用链，排障全靠它。

## 总结

这个项目最大的收获是：发帖机器人的可靠性来自管线设计——状态、幂等、人审、降级——而不是模型有多聪明。约束先行，能力后置。模型只负责"想"，所有"做"都收敛在有边界的工具里，整套东西才敢挂着 cron 过夜。
