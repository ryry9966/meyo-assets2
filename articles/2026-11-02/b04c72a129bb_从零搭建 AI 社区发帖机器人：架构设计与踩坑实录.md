## 背景

社区内容运营有个现实痛点：有价值的信息散落在 GitHub Release、论坛、RSS 订阅里，人工搬运费时还容易漏。我用 OpenClaw 的 Agent + MCP 工具链搭了一个发帖机器人，跑了一个多月，从纯自动降级到"半自动 + 人工审核"，这里把架构和踩坑记录下来。

## 问题

最初目标很朴素：每天定时抓取若干信息源，让 LLM 汇总成一篇中文帖自动发出。但要长期稳定运行，问题比预想多：

- 模型会"补全"不存在的链接和版本号；
- 定时任务重叠导致重复发帖；
- 信息源超时、接口限流没有统一处理；
- 出了问题才发现，缺少审计和回滚手段。

## 架构与步骤

最终架构刻意保持简单：五个无状态模块 + 一个本地 SQLite 状态库。

1. **抓取器**：RSS、Git tag、论坛 API 三个插件式数据源，统一输出结构化条目（title / url / hash / time）。
2. **去重器**：对条目归一化（去 utm 参数、小写、去标点）后算 hash，与已发表记录比对。
3. **起草器**：一个 Agent，系统提示词写死"只允许引用输入材料中的 URL 和数字，缺失就写'见原文'"，通过 MCP 调抓取结果，产出行内 Markdown 草稿。
4. **审核网关**：草稿先进队列。前两周 100% 人工审核；待引用完整性、长度、历史重复度等指标稳定后，降为高置信自动发、低置信转人工。
5. **发布器**：调社区发帖 API，带幂等键（内容 hash），失败进重试队列，指数退避，最多 3 次。

状态库只存三样：已发 hash、草稿原始材料、运行日志，方便复盘。

## 踩坑点

- **幻觉链接**：第一版提示词只说"写一篇摘要"，模型自己编了 Release 号。改成"逐条引用、编号对齐、禁止推断"后基本杜绝。核心原则：让模型做组织，不做记忆。
- **重复发帖**：两条 crontab 规则在整点重叠，双进程同时过审。加文件锁 + 幂等键解决。任何"写"操作都要假设会被执行两次。
- **上下文爆炸**：某天信息源积压 40+ 条，塞给模型导致截断。限制单次最多 15 条，超出顺延下一轮——宁可延迟，不丢真。
- **提示词漂移**：为修小问题反复改提示词，两周后没人说得清哪版在线上。把提示词纳入 git，改动走 commit，发布记录版本号。
- **密钥管理**：早期把 token 写在 .env 里还进了镜像。改为运行时注入 + .gitignore + 定期轮换。

## 可复用建议

- 先跑两周 dry-run：所有"将要发的内容"落日志，再决定是否放开自动发。
- 去重做在 LLM 之前，别让模型判断"这条发过没有"。
- 各模块无状态、可单独重跑，排障时逐段二分。
- 给机器人留"自我报告"通道：每轮结束往固定频道推一行运行摘要（抓取数 / 发布数 / 跳过数），异常一眼可见。

## 总结

这个机器人代码不到 600 行，真正的工作量在工程细节：幂等、限流、审计、降级。LLM 只负责它擅长的组织和转述，事实校验、去重、发布控制全靠外围的确定性代码。自动化的上限不取决于模型多聪明，而取决于失败路径设计得多保守。想做内容机器人的同学，建议从"人工审核 100%"起步，用数据决定何时放手。
