## 背景

我维护的社区每周要发一条「本周技术动态」，素材来自内部笔记和几个 RSS 源。手工整理三个月后决定自动化：基于 OpenClaw 的 Agent 循环加自定义 MCP 工具，让机器人每天定时抓素材、生成草稿，人工确认后发帖。目标不是全自动，而是把人工参与压缩到「看一眼、点确认」。

## 总体架构

三个模块，独立进程，通过本地文件和 SQLite 状态库衔接：

1. **采集器**：cron 触发，用 MCP 的 fetch 工具拉 RSS 和 wiki 导出 JSON，落盘到 `sources/` 目录，按内容 hash 去重后登记状态库。
2. **草稿生成器**：Agent 读素材清单，按提示词模板产出结构化草稿（标题、摘要、链接），写入 `drafts/`，状态置 `pending`。
3. **发布器**：轮询 `pending` 草稿；`REVIEW_MODE=1` 时先推送人工确认频道，确认后才调用社区 API，写回 post_id。

关键决策是生成与发布完全解耦，任何一步失败都能重跑，状态库保证幂等。

## 踩坑实录

**1. LLM 会编造链接。** 第一版让模型「引用素材链接」，上线第一天就发出一条不存在的 URL。修复：提示词禁止模型输出任何 URL，链接由脚本从素材 JSON 原样拼入，模型只写文字。

**2. 精确匹配去重不够。** 同一篇内容换措辞就被当成新素材。改用标题+摘要的 Jaccard 相似度，加 7 天时间窗过滤，误判降到可接受。

**3. 时区坑。** cron 写死 UTC，第一条帖子北京时间凌晨 4 点就发出去了。现在统一存 UTC，展示层转 Asia/Shanghai，调度配置显式写时区。

**4. 静默失败最危险。** 社区 API 限流返回 429，发布器没记日志直接跳过，三天没人发现。修复：所有失败必须写状态库并打 error 日志，连续失败 3 次触发告警。

**5. 提示词要进版本管理。** 早期提示词散在代码字符串里，改一次效果回退一次。挪进独立 YAML 后，每次调优都有 diff 可回溯。

## 可复用建议

- 先跑 `--dry-run`：所有写操作只打印不落库，稳定运行一周再开真发。
- 幂等优先：以「素材 hash + 目标板块」为唯一键，重跑不会重复发帖。
- 人工确认环节别急着砍，它是发现提示词漏洞的唯一抓手。
- 模块间无共享内存，坏了单独重跑，不互相拖累。

## 总结

上线一个月稳定发出 20+ 条帖子，人工时间从每周 2 小时降到 10 分钟。最大体会：AI 部分只占三成工作量，剩下七成是状态管理、去重、失败处理这些「无聊」的工程活。把无趣的部分做扎实，才敢放心让 Agent 替你发帖。代码整理后计划开源到社区仓库，欢迎在评论区交流提示词模板的写法。
