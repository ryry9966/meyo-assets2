## 背景

大多数 agent 的默认形态是"你问我答"：不发消息，它就是一块石头。但真正省时间的场景往往反过来——日历冲突早半天提醒、依赖仓库出了新 issue 先汇总、磁盘快满先报数。OpenClaw 这类常驻 agent 天然适合干这个：有稳定的运行时、工具权限和消息通道，缺的只是"什么时候主动说话"的纪律。

## 问题

我最初的做法很粗糙：起一个每小时跑的 cron，把所有事件塞给模型，"有事就说"。三天后我把它关了：重复推送、凌晨两点的"摘要"，还有一次它自作主张回了一条群消息。问题不在"主动"本身，而在于没把**触发—判断—执行—通知**拆开，所有决策糊在同一个 prompt 里。

## 做法

现在的结构是四层：

1. **触发层**。三类来源：cron 定时（晨报、周报）、事件 webhook（GitHub issue、CI 失败、监控告警）、heartbeat 轮询（每 30 分钟自检一次待办）。每个触发只携带最小上下文。
2. **判断层**。单独一个判定 prompt，输入事件摘要，输出结构化 JSON：`{action: "silent" | "notify" | "act", reason, urgency}`。核心规则一条：**沉默是默认值**。凑不齐"与用户相关 + 有新信息 + 有可执行建议"三条，就走 silent，只落库。
3. **执行层**。MCP 工具按只读优先接入：读仓库、查日历、抓日志随便用；任何写操作（发消息、建 issue、提交代码）只生成草稿，等确认。
4. **通知层**。推送固定格式：一行结论 + 证据链接 + 建议动作。用户回个"做"，才真正执行。

## 踩坑点

- **heartbeat 频率**。30 分钟一次看似不高，但每轮都拉工具、读上下文，一周烧掉的 token 比日常对话还多。后来改成 heartbeat 只做轻量检查，重活留给 cron 和事件触发。
- **会话污染**。最初心跳和主对话共用 session，模型记了一堆"上次巡检"的噪声，正常问答质量肉眼可见地下降。现在每个主动任务一个独立 session，结束后只回写结论摘要。
- **静默失败**。主动任务挂了没人知道，因为用户本来就不盯着它。给调度器本身加上报：连续两轮没跑，才允许它打破沉默，报告自己的故障。
- **去重与冷却**。同一个 issue 被三个 webhook 同时命中，推了三条。现在按事件 key 做 6 小时冷却窗。
- **时区**。cron 默认 UTC，晨报下午三点才到。调度时间统一显式写时区。

## 可复用建议

- 三档动作模型（silent / notify / act）直接抄，比自己调"语气"管用。
- 判定 prompt 与执行 prompt 分开写；判定输出必须结构化，方便统计和调阈值。
- 先只读，后写操作；写操作永远带人工确认。
- 每次主动推送记日志（触发源、判定结果、用户是否回应），两周后你会需要这份数据来降噪。
- 冷却、去重、静默默认——这三样是主动能力不变成骚扰的三根支柱。

## 总结

proactive 的价值不在"它主动了"，而在"它在该闭嘴的时候闭嘴"。分层之后，我的助手一天大约主动说两三句话，每一句我都愿意看——这个比例比每天十条晨报有用得多。建议从单一场景起步（比如 CI 失败通知），跑稳了再往外扩。
