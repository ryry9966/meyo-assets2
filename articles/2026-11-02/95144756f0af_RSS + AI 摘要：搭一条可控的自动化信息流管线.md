## 背景

信息源越订越多，真正读的时间越来越少。RSS 依然是可控性最好的聚合方式——结构稳定、没有算法干预、天然适合机器处理。我的做法是把 RSS 当作管线的输入端，交给一个定时运行的 Agent 做筛选和摘要，最后推送到自己的阅读渠道。整条管线跑在一台常驻的小服务器上，每天早上产出一份五分钟能读完的日报。

## 问题

最初的版本很朴素：cron 拉取 RSS → 全文丢给 LLM → 输出摘要。跑了两天就暴露三个问题：

1. 同一条新闻在多个源重复出现，日报里同一件事出现三遍；
2. 不分轻重全部摘要，token 消耗大，产出却全是水话；
3. 部分 RSS 只有摘要没有全文，模型只能基于标题硬编，出现幻觉。

## 做法

现在的管线分四层：

**抓取层**：用标准 RSS 解析库拉订阅源，RSS/Atom 都支持。对只有摘要的源，用 headless 浏览器补抓正文，带随机延迟和 UA。

**去重与存储**：SQLite 一张表，主键用 guid + 源 ID 的哈希。注意有些源的 guid 不稳定，所以用「标题归一化 + 发布时间窗口」做二次去重，48 小时内的相似条目视为重复。

**处理层**：这是 Agent 的部分。按源分组做 map 阶段摘要，再做一次 reduce 归并，按主题聚类输出。粗筛用便宜的小模型打分（0–5），低于阈值直接丢弃，3 分以上才进入精摘。Agent 通过 MCP 挂了两个工具：`fetch_url`（抓原文）和 `save_digest`（写日报），模型在上下文不够时可以自己补抓原文，而不是硬编。

**分发层**：日报生成后推到 Telegram，同时落一份本地 Markdown 存档。失败重试三次，仍失败则跳过并记日志，不阻塞当天任务。

## 踩坑点

- **guid 不可信**：至少两个源会更新已发布文章的 guid，导致重复推送。靠发布时间窗口兜底才压住。
- **全文抓取被反爬**：某技术社区对无头浏览器返回验证页，抓回来的是一段 JS。后来发现它自带全文输出的 RSS 变体，直接换源，省事得多。
- **摘要幻觉**：早期让模型直接总结标题列表，编造了不少“细节”。改成强制先抓原文、引用段落再总结，幻觉率明显下降。宁可输出“信息不足”也不要硬写。
- **调度重叠**：某次源响应慢，上一轮 cron 还没跑完，两轮任务并发写库。加了文件锁解决，简单但必须做。

## 可复用建议

1. 两阶段摘要（map-reduce）比一次性长上下文更省 token，也更容易定位问题；
2. 粗筛和精摘分开，粗筛用便宜模型，成本能降一个量级；
3. 每条摘要必须带原文链接，摘要只是索引，不是替代；
4. 提示词里明确「无新增信息就只输出原文要点，不要润色」，水话会明显减少；
5. 把「抓不到全文」当作正常路径处理，而不是异常。

## 总结

这条管线每周维护成本大概十分钟，主要是增删订阅源和抽查摘要质量。没有用到任何复杂技术，价值在于把「读信息」从被动刷变成主动收。对 OpenClaw 用户来说，RSS 是成本最低的结构化输入源，配合 MCP 工具链，一个下午就能跑起来。建议先接两三个源验证质量，再逐步扩容——信息管线和代码一样，先跑通，再优化。
