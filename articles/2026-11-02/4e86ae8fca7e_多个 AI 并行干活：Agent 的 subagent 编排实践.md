## 背景

单 Agent 串行干活有几个明显瓶颈：上下文越堆越长导致质量下滑；互相独立的任务（跑测试、查依赖、审文档）只能排队等；一次长任务中途挂掉就得全部重来。把部分工作拆给 subagent 后，这些问题都有缓解。这里记录我们在 OpenClaw 场景下跑了一段时间的编排实践。

## 问题

最初的用法很朴素：主 Agent 在一条消息里列完所有子任务，等结果回来继续。实际跑起来暴露了三件事：

1. 子任务结果全文回灌，主 Agent 上下文迅速膨胀，后面几轮推理质量明显下降；
2. 两个 subagent 同时改同一个文件，后写的覆盖先写的；
3. 某个 subagent 静默失败，主 Agent 拿着空结果继续推理，产出看起来"完整"，实则缺了一块。

## 做法

我们的编排原则很简单：主 Agent 只做拆解、派发与汇总，不碰具体执行。

- **任务拆分先行**。派发前先显式判断依赖：无依赖的（代码审查、依赖审计、文档检查）一次性并行派发；有依赖的（先测后修）强制串行。
- **一职一事**。每个 subagent 只绑定一组 MCP 工具，职责窄化。比如"测试员"只准跑测试并返回通过/失败摘要，不准顺手改代码。
- **返回值做减法**。约定 subagent 只回结构化摘要（结论 + 关键文件路径 + 状态码），完整日志落盘到共享工作区，主 Agent 需要时按路径去读。
- **文件所有权分区**。并行写文件的场景，提前按目录或文件划分归属；确实要动同一文件的任务，降级为串行。
- **失败显式化**。返回体必须带状态字段，主 Agent 对失败要么重试要么终止汇报，不允许"当没看见"。

## 踩坑点

- **摘要丢信息**。早期只说"总结一下"，关键报错被总结没了。后来把返回格式固化成模板，必填字段写死。
- **并行 ≠ 提速**。三个子任务如果抢同一个工具的配额，并行反而互相等待。先看资源依赖，再定并行度。
- **subagent 会幻想自己的权限**。不给明确边界时，"测试员"会自己改代码去"修问题"。工具白名单和提示词约束缺一不可。
- **上下文不自动继承**。主 Agent 以为 subagent 知道刚才的对话，实际对方什么都不知道。派发消息里把必要背景写全，宁可冗余。

## 可复用建议

1. 把 subagent 当成一个有输入输出契约的函数来设计：输入、返回格式、失败语义都要明确。
2. 用共享工作区（文件系统）做通信介质，比往 prompt 里塞内容可靠得多。
3. 并行度从 2 开始试，跑稳了再往上加，别一上来开满。
4. 每次 subagent 运行留日志，出问题时能回放定位。

## 总结

subagent 编排的本质不是"更多 AI"，而是更清晰的职责边界和更严格的接口约定。并行带来的收益，只有在任务拆分干净、返回值克制、冲突被预先设计掉的前提下才成立。建议从一个高频低风险的场景（比如并行的代码检查）起步，把契约打磨稳定，再逐步扩大编排范围。
