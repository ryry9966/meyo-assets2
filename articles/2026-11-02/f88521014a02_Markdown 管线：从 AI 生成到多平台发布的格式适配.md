## 背景

Agent 工作流里，AI 产出的初稿几乎都是 Markdown。但真正的麻烦不在生成，而在发布：公众号、掘金、GitHub、RSS、Notion，各家对 Markdown 的支持差异很大。我们的做法是把格式适配从人工搬运改成一条管线——Agent 只负责产出规范的中间格式，发布交给适配器。

## 问题

直接把 AI 输出丢给各平台，会遇到三类问题：

1. **生成质量不稳定**：标题层级跳跃（h1 直接跳 h4）、代码块不带语言标注、滥用表格和加粗、夹带原生 HTML。
2. **方言差异**：GFM 的表格、任务列表、脚注，在公众号里要么不渲染要么变乱码；微博类平台干脆没有 Markdown。
3. **资源问题**：相对路径图片、外链防盗链、frontmatter 需要剥离。

## 做法

整条管线分四段，核心原则是**单一事实源 + 纯函数适配器**：

**1. 规范化。** 选定 GFM 作为中间表示（IR），用 unified/remark 生态解析成 AST 后跑 lint：标题从 h2 起步且不跳级、代码围栏必须带语言、禁用行内 HTML、链接转绝对路径。注意是操作 AST，不要用正则改文本。

**2. 资源处理。** 遍历 AST 中的 image 节点：远程图片下载、压缩、转存到自己的图床，统一替换为持久 URL。这步做完，后续平台适配不用再碰图片。

**3. 平台适配。** 每个目标平台一个纯函数：canonical AST → 平台载荷。

- GFM 系（GitHub、掘金）：lint 通过后基本直出，frontmatter 按目标格式改写；
- 公众号：markdown-it 渲染成 HTML 后样式全部内联，只保留白名单标签；
- 纯文本系（微博、社群）：表格降级为列表，标题降级为符号行，剥离强调标记；
- 图片卡片系：分页渲染成 PNG 卡片。

**4. 校验。** 每个平台维护一份 golden snapshot，适配结果 diff 不通过就拦截。发布动作封装成 MCP tool 暴露给 Agent，参数只有平台 ID，调用前必须先过 lint。

## 踩坑点

- **用正则预处理 Markdown 是最大的坑**。代码块里的 `#` 和链接会被误改，永远走 AST。
- 公众号会剥掉 class 和大部分属性，样式必须内联；但内联过头的 HTML 又会被部分 RSS 阅读器拒绝，两条链路要分开维护。
- 任务列表 `- [ ]` 在不支持的平台显示为字面量 `[ ]`，适配器里要主动降级成普通列表。
- 表格转纯文本时列宽溢出比想象中常见，长单元格先摘要再降级。
- AI 很爱写"总结"段和高频加粗，lint 里加一个加粗密度阈值，实测有效。
- 微信图片有 referrer 防盗链，热链外站图全挂，必须转存。

## 可复用建议

- lint 规则当代码维护、进 CI，别散落在 prompt 里；prompt 中可以写规则让模型遵守，但事后必须用 linter 兜底。
- 适配器保持无状态、可单测，新增平台只写一个函数。
- golden snapshot 是多平台渲染回归的最低成本方案。
- 发布工具做成 MCP server，Agent 侧只感知"平台 ID"这个抽象，方言细节全部下沉。

## 总结

这条管线没有黑科技，价值在于把"AI 会写什么"和"平台能收什么"解耦：上游保证 AST 干净，下游每个平台一个小函数。跑通之后，新增一个发布渠道的成本从半天人工搬运降到写一个适配器加跑一遍 snapshot。对做自动化内容工作流的团队，建议先从 lint 和图片转存这两段做起，收益最直接。
