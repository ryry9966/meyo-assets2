## 背景

在 OpenClaw 的自动化流程里，让 Agent 产出 Markdown 已不是难点，难的是“一份内容发到 N 个平台还能保持体面”。公众号要内联样式的富文本，知乎会剥掉大部分 HTML，掘金原生吃 Markdown 但代码高亮规则不同，RSS 要求合法 XML。不少自动化工作流就死在这一步：不是内容不行，是格式适配没做成工程。

## 问题

典型症状有三个。其一，Agent 输出的是“方言”Markdown：标题层级跳跃、代码块语言标记随意（sh/bash/zsh 混用）、表格与脚注用法不统一。其二，适配逻辑散落在字符串替换里，`replace` 一路 replace 到发布前，改一处崩一处。其三，链接和图片不可控——幻觉外链、过期图床、被平台拦截的第三方图，都到发布后才暴露。

## 做法

核心思路是**单一事实源 + AST 优先**，分五步：

1. **约束生成端。** 在 Agent 的系统提示里明确一份受限 Markdown 子集（可称为“发布方言”）：只用 GFM 核心语法，标题从 H2 开始且不跳级，代码块必须带语言标记，禁用内联 HTML。生成后先过 remark-lint，不合规直接打回重写——这比在下游兜底便宜得多。
2. **解析成 AST。** 用 remark/mdast（或 markdown-it 的 token 流）把文档变成树。之后所有操作都在节点层面进行，彻底告别正则替换。
3. **按平台写 transformer。** 每个平台一个纯函数：输入 AST + 平台配置，输出目标格式。公众号 renderer 在构建期完成代码高亮（highlight.js 产出内联样式的 span），整体转成全内联 CSS 的 HTML；知乎走它接受的 Markdown 子集；掘金基本透传，只做语言标记映射；Dev.to 注入 front matter。平台差异抽成一份 YAML 能力矩阵（是否支持表格、脚注、数学公式），transformer 读配置降级——不支持表格就转列表。
4. **发布前校验门。** 跑三个检查：链接可达性（顺手拦掉幻觉链接）、图片资源（外链图先传平台图床，回填节点 URL 后再渲染）、长度与标签数量上限。
5. **Dry-run 与快照。** 每次发布前渲染各平台预览，HTML 做快照测试。管线保持幂等：同样输入必出同样输出，别在渲染时引入随机 class 名。

## 踩坑点

- 公众号会剥 class 属性，所有样式必须在构建期内联，代码高亮别指望运行时 JS。
- 图片替换要在 AST 节点上改 `url`，对源文本做字符串替换会漏掉转义和重复出现的情况。
- RSS 的 XML 转义：正文里的 `&`、`<` 不处理，整条 feed 直接挂。
- AI 爱写四级以上标题，部分平台渲染成正文大小，视觉上“塌”掉——方言里直接禁掉。
- front matter 忘了在某平台剥离，元数据被当正文发出去，这种事故一次就够。

## 可复用建议

- 把“发布方言”写成规范文档，放进提示词或 MCP 资源，让所有生成任务共享同一套约束。
- transformer 保持无状态、可单测；平台差异只出现在配置和 renderer 两处。
- 能力矩阵是数据不是代码，接新平台先填表再写函数。
- 快照测试至少覆盖三个恶劣样例：长代码块、嵌套表格、含特殊字符的段落。

## 总结

多平台发布的本质不是“多写几个转换脚本”，而是把格式适配收进一条可测试的管线：生成端收敛方言，中间层一切基于 AST，平台差异配置化，出口有校验。Agent 负责内容，管线负责体面，职责分清之后，接入一个新平台通常就是半天的事。
