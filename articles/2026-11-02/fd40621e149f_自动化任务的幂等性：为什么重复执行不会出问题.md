## 背景

在 OpenClaw 这类自动化体系里，任务被触发两次几乎是常态：cron 重叠、webhook 重投、Agent 超时后重试、人工手动补跑。网络抖动和调度层重试不是异常，而是设计前提。

## 问题

一个典型场景：每日定时任务让 Agent 汇总 Issue 并写入看板。某天执行超时，调度器自动重试，结果两条重复记录入库，通知也发两遍。排查时日志"看起来都成功了"，很难定位。根本原因不是重试机制有 bug，而是任务本身不幂等——同样的输入执行两次，产生了多余的副作用。

## 做法

1. **给任务一个确定性 ID**。不要用随机 UUID 或当前时间戳，而是从触发语义推导：`digest-20250612-issue-sync`。同一天重跑，ID 相同，天然可去重。
2. **执行前查状态**。用一张简单的本地表（SQLite 就够）记录"这个 ID 是否已完成/进行中"。已存在则跳过或覆盖，而不是再执行一遍。
3. **写操作尽量用 upsert 而非 append**。文件用固定文件名覆盖，数据库用 `INSERT ... ON CONFLICT` 或先删后写。"收敛到目标状态"的操作天然幂等。
4. **外部调用带幂等键**。支持 `Idempotency-Key` 的 API 直接传确定性 ID；不支持的，在调用前落一条 pending 记录，拿到响应再更新为 done。
5. **先记意图，再执行副作用**。如果崩溃发生在"发通知"和"写完成标记"之间，重试方能看到 pending 状态，据此决定跳过还是补偿。

## 踩坑点

- **check-then-act 的竞态**：两个并发实例同时查到"未执行"，然后都执行。解决：数据库唯一约束、文件锁，或把状态写入和执行声明做成原子操作。
- **时间桶 ID 的时区问题**：按天聚合时，服务器是 UTC 还是本地时区，会导致跨午夜任务 ID 漂移。明确固定时区。
- **补偿动作不幂等**：失败回滚时再删一次、再退一次，比不回滚更糟。补偿逻辑也要过同样的幂等检查。
- **状态存储被清掉**：去重记录本身要有保留策略，别在清理脚本里顺手删了。

## 可复用建议

- 一条经验法则：**任何可能被触发两次的任务，一定会被触发两次**。
- 上线前自测两个问题：现在立刻连续跑两遍会怎样？跑到一半中断会怎样？答不上来就还不算完成。
- 能用"声明目标状态"（Terraform/Ansible 那种思路）就不要用"执行一连串动作"，前者天然幂等。

## 总结

幂等性不是额外的工程负担，而是让你敢于开启重试、敢于手动补跑、敢于让 Agent 自主执行的前提。确定性 ID + 状态记录 + upsert 式写入，三件事覆盖 80% 的场景，剩下的并发问题用唯一约束兜底即可。
