## 背景

自动化跑起来之后，重复执行几乎是必然的：cron 到点重叠、webhook 被上游重发、MCP 工具调用超时后 Agent 自动重试、插件被手动再触发一次。分布式环境里，“请求失败”往往意味着“结果未知”——你不知道服务端到底执行了没有。幂等性就是解决这个问题的：同一个操作执行一次和执行 N 次，最终状态一致。

## 问题

一个典型的失败链路：定时任务每小时抓数据写入表格，写入函数先查重再插入。某天网络抖动，请求超时但实际已写入，重试后再插一条——出现重复数据。Agent 场景更隐蔽：模型输出不稳定导致“发送通知”这个工具被调了两次，用户收到两条一模一样的消息。根源相同：写操作不是幂等的，而执行层无法保证“恰好一次”。

## 做法

核心思路：不追求恰好一次，追求“至少一次 + 幂等”，这是更现实的组合。

1. **给每个逻辑任务定一个稳定键**。用任务内容哈希、`(来源, 日期, 动作)` 拼接等，保证重试时键不变。不要用随机 UUID——每次重试生成新键，去重就白做了。
2. **执行前查键，执行后记键**。存哪都行：SQLite 一张表、Redis `SET key value NX EX 86400`，甚至一个文件锁目录。键存在就跳过，或直接返回上次结果。
3. **检查与写入必须原子**。“先查再写”两步之间有竞态，两个并发实例可能同时通过检查。用 `SETNX`、`INSERT ... ON CONFLICT DO NOTHING` 或唯一索引兜底，让存储层替你拒绝第二次。
4. **优先改造操作本身**。能 upsert 就不要裸 insert；按唯一键删除天然幂等；状态更新用 `UPDATE ... WHERE status = 'pending'` 条件式推进，而不是无条件 set。
5. **外部副作用单独去重**。发邮件、发消息这类不可回滚的动作，把幂等键透传给下游（不少通知类 API 支持），或调用前查一次本地记录。

## 踩坑点

- **键在重试循环内生成**：每次重试都是新键，去重形同虚设。键必须派生自稳定输入。
- **Agent 重规划导致键漂移**：二次规划时任务措辞变了，内容哈希就变了。Agent 任务的键应来自触发源（消息 ID、定时槽位），不是任务文本本身。
- **只做时间窗口去重**：“5 分钟内不重复”挡不住 6 分钟后的重试，也会误伤真正的下一个周期。按逻辑任务去重，不按时间去重。
- **忽略“已存在”的返回**：查到键后应返回上次结果或明确状态，否则上层把“跳过”当失败，又触发一层重试。
- **记录没有清理机制**：键里带日期的长期任务，记得让过期记录可回收。

## 可复用建议

把这套逻辑收敛成一个十几行的包装函数：`run_once(key, fn)`——查键、原子占位、执行、记录结果。所有定时任务和 Agent 工具调用统一走它。再配一条验证：CI 或沙箱里把关键任务连跑两遍，第二遍必须零新增副作用。写这条测试，远比事后排查重复数据便宜。

## 总结

自动化系统的可靠性，不是靠“保证不重复触发”，而是靠“重复触发也无害”。给任务一个稳定键，让存储层做原子裁判，把外部副作用纳入同一个去重体系——做到这三点，重试就从风险变成了常态。
