## 背景

自动化系统里，“同一段逻辑被跑两次”几乎是常态而不是异常：定时器在边界时刻可能触发两次；网络超时后重试机制会把请求再发一遍；你自己看任务好像没跑，手动补了一次；Agent 的自愈循环更是如此——执行、检查、发现没达预期、再执行。调度和重试属于基础设施，它们默认一件事：**重复执行是安全的**。这个默认成立的前提，就是幂等性。

## 问题

反例大家多少都见过：

- 定时摘要推送到群里，同一条内容发了两遍；
- “给新用户发欢迎语”的任务重跑后，老用户又收到一次；
- Agent 调用写文件的工具，一次超时后重试，文件被追加了两份内容。

最麻烦的是超时场景：你根本不知道上一次执行有没有生效。不重试，可能丢任务；重试，可能重复执行。非幂等操作让“失败恢复”变成赌博。

## 做法

我会先把任务里的操作分类：只读操作天然幂等，不用管；有副作用的写操作，按下面几步处理。

1. **给任务一个稳定的业务 ID。** 注意是“业务级”的，比如 `daily-summary-2024-06-01`，而不是每次尝试新生成的 UUID。重试时 ID 不变，才有去重依据。
2. **写操作优先用 upsert / 集合语义。** 数据库用唯一键加 `ON CONFLICT DO NOTHING`；配置修改写成“把状态设为 X”，而不是“把 X 追加进去”；文件写入用临时文件加原子改名，重复执行结果一致。
3. **不可幂等的外部动作加一层本地台账。** 发通知、调第三方这类动作没法安全重放，那就先在本地记录“准备做 X（key=K）”，执行完标记完成；重试时先查台账，已做就跳过。
4. **用“回读验证”代替“信任返回值”。** 任务末尾读一次最终状态确认结果，Agent 的自愈循环据此判断要不要重跑，而不是凭一次报错盲目重试。

落到 MCP 工具和插件设计上同理：它们会被 Agent 以不可预测的次数调用，`upsert_record`、`ensure_dir` 这类是安全的；`append_log` 这类就要在实现内部自己处理去重。

## 踩坑点

- **先查后做有竞态。** “检查存在→不存在则创建”在两次并发执行时会双双通过检查。去重要靠原子原语（唯一约束、文件锁、SETNX），不能靠两次独立调用。
- **幂等键漂移。** Agent 重试时如果重新规划，请求体变了，键也跟着变，去重形同虚设。键要锚定在原始任务上，贯穿整个重试链。
- **标记时序。** 先标完成再执行，失败会丢任务；先执行再标记，标记那步失败下次就重复。常见折中是“先记意图、再执行、后标完成”，配合台账查询兜底。
- **清理类任务藏得最深。** “删掉最旧的一个备份”跑两遍就删两个，改成“只保留最近 N 个”就安全了。

## 可复用建议

- 写操作必须携带稳定任务 ID，这是一切去重的前提；
- 能用 upsert 就不用 insert，能用“设为”就不用“追加”；
- 外部副作用一律过台账，不做裸调用；
- 最实用的一条：**在 CI 里把每个任务跑两遍**，断言第二遍执行后状态与第一遍完全一致。这一条测试能抓住绝大多数幂等漏洞。

## 总结

幂等性不是锦上添花的优化，而是重试、调度、Agent 自愈这些机制能安全工作的前置条件。把“再跑一遍一定安全”当成自动化任务的验收标准，你才有资格放心地加调度、加重试、加循环。
