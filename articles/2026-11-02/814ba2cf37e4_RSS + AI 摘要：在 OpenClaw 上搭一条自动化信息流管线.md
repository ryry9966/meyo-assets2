## 背景

信息获取这块，RSS 其实没死，只是被算法推荐挤到了角落。它的优势很明确：源是自己选的，格式是标准的，拉取是可控的。问题只剩一个——读不过来。OpenClaw 这类常驻 Agent 网关正好补上这一环：有 cron、有插件和 MCP 工具、有现成的消息通道，把它变成一条"定时拉取 → 摘要 → 推送"的管线，成本很低。

## 问题

直接把 RSS 原文丢给模型，会遇到三个现实问题：

1. **噪声大**。几十个源一天出几百条，全量摘要既费 token 也看不过来；
2. **幻觉**。模型拿着标题加截断的描述去扩写，很容易编出正文里没有的结论；
3. **重复推送**。各 feed 的更新策略不一致，处理不好同一篇文章会推三次。

所以这条管线的目标不是"让 AI 多写"，而是让它在固定时间给我一份能看完、可信、不重复的摘要。

## 做法

**1. 订阅治理先行。** 订阅收敛到 30 个以内，按主题分三档：必读、可选、观察。没有 feed 的站点用 RSSHub 补。清单放一份 YAML 配置里，增删就是改配置。

**2. 拉取与去重。** cron 定时触发 skill，拉取所有 feed，清洗 HTML 后按 guid 写入本地 SQLite；推送前再查一次库，只取增量。这一步全在模型外面做，纯代码，不要交给 Agent 判断。

**3. 摘要策略，分两级：**

- 条目级：每条一句话加标签（值得深读 / 一般 / 跳过），批量送入，单次控制在 20 条左右；
- 日报级：把"值得深读"的正文节选（每篇限 1500 字符）给模型，产出 3-5 条要点。

Prompt 里强制约束：只基于给定内容总结，信息不足就标注"不确定"，禁止补充外部知识。输出走固定 JSON 结构，渲染层只管排版。

**4. 推送与反馈。** 摘要渲染成 Markdown 推到常用频道，早晚各一份。另留一条关键词实时告警：命中即单推，不进日报。

## 踩坑点

- **guid 不是万能的**。个别源的 guid 会变，改成 guid + 链接双键去重后才稳定；
- **先清洗再进模型**。好几个 feed 的 content 里全是内联样式，直接塞进去 token 翻三倍；
- **cron 时区**。网关默认 UTC，日报第一次下午四点才到，记得显式指定时区；
- **RSSHub 限流**。并发拉几个源会 429，改成错峰调度，且单源失败不阻塞整轮；
- **模型"热心补全"**。摘要里出现源里没有的数据，加上约束、把 temperature 降到 0.2 以下才收敛。

## 可复用建议

- 订阅清单、摘要模板、推送时间全部做成配置，管线代码保持稳定；
- 去重、清洗、调度这类确定性逻辑放代码，模型只负责理解与归纳；
- 输出走固定 schema，方便换模型做 A/B 对比；
- 摘要质量不达标时，先优化订阅和过滤，再考虑换模型——大多数问题出在前者。

## 总结

这条管线跑了一个月，日报打开率大约七成，几个观察源因为连续两周"全跳过"被我退订了。整体感受是：没有什么魔法，就是老老实实的管道工程加一个克制的摘要 prompt。AI 在这里的价值不是替你读，而是把"值得你读"的那部分筛出来。
