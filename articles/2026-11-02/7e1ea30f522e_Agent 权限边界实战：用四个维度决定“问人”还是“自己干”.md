## 背景

Agent 接上 MCP 和插件后，能力从“聊天”变成“动手”：读文件、写仓库、调内部 API、发消息、花钱。社区里两个极端都常见——一种事事请示，改个注释也要确认，人成了昂贵的按钮；另一种几乎不问，直到某天它“顺手”清掉一个不该动的目录。权限边界不是产品功能，是工程问题。

## 问题

矛盾在于：问得少，风险失控；问得多，人会疲劳，之后所有确认都变成无脑点“允许”。所以要设计的不是“问不问”，而是**哪些动作必须到达人类，其余的如何安全地自动跑完**。

## 做法：按四个维度给动作分级

给每个工具调用打标，再定策略：

1. **可逆性**：能否撤销？读文件、工作区内写入可逆；删远端分支、发出去的消息不可逆。
2. **影响半径**：只影响本地沙箱，还是波及共享资源（生产库、团队仓库、外部用户）？
3. **成本**：是否触发计费、消耗配额、批量执行。
4. **歧义度**：指令和现状对不对得上？需求模糊时，执行得越准，偏得越远。

映射成四档：

- **L0 自动执行**：只读操作、沙箱内读写。不确认，但记日志。
- **L1 自动执行 + 留痕**：工作区内可逆写入（新建文件、本地 commit），存下 diff 供事后审计。
- **L2 执行前必确认**：不可逆、出沙箱、花钱、对外发送（发邮件、提 PR、部署生产、删数据）。
- **L3 默认拒绝**：改凭证、删备份、修改权限配置本身。除非当次明确指令，不做。

## 落地：写进配置，而不是 prompt

只在系统提示里写“危险操作先问我”，模型一定会漏。更可靠的是在 MCP 工具注册层做能力声明：每个工具标注 `readonly` / `destructive` / `external` / `cost`，框架按标注路由到“自动放行”或“人审队列”。新接入的工具默认落 L2，观察两周再降级。

## 踩坑点

- **确认疲劳**：一天弹 30 次确认，人只会全点允许。宁可收紧 L1 的定义，也要把弹窗压到每天个位数。
- **无效提问**：只问“可以继续吗”，不给出将执行的命令、影响范围和回滚方式——这种确认等于没问。
- **会话授权不回收**：“本次允许”要绑定任务，任务结束或超时自动失效。
- **转述吞掉风险**：Agent 说“做点小清理”，实际是 rm。L2 确认必须展示原始命令和 diff，不接受转述。
- **分级标错**：我们曾把一个“写配置”工具标成只读，它顺手重启了服务。分级要核对真实副作用，不能看工具名猜。

## 可复用建议

1. 新工具默认 L2，看两周日志再降档；升权容易，收权难。
2. 所有自动执行的动作落审计日志（时间、参数、结果），每周扫一次，重点看 L1 里混没混进“像 L2 的”。
3. 支持 dry-run：先输出执行计划，一次确认覆盖一批动作，避免循环弹窗。
4. 分级表进版本管理，跟插件一起维护——权限策略是代码的一部分。

## 总结

权限边界的本质，是把人类注意力当作最稀缺的资源来分配：只有**不可逆、出边界、花钱、含糊**这四类动作才配占用一次确认，其余靠沙箱、日志和可回滚性兜底。先用最严格的配置跑起来，根据事故而非感觉去放宽——顺序反过来，就是大多数翻车现场的开始。
