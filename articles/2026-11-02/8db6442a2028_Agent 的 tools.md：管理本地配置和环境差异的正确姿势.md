## 背景

跑 Agent 做自动化的人大多遇到过这种场景：同一套 prompt，在办公电脑上跑得好好的，换到家里服务器或 CI 容器里就翻车——Agent 幻觉出一个不存在的路径，或者用错了包管理器。原因很简单：Agent 对"这台机器长什么样"一无所知，只能靠猜，或者靠反复执行 `which`、`--version` 去试探，既浪费 token 又不可靠。

## 问题

环境信息散落在各处：shell rc 文件、README、口头约定，Agent 每次会话都要重新摸索一遍。团队里每个人的本地环境还不一样：macOS 和 Linux 的命令差异、Python 版本、代理设置、某个自研 CLI 其实是个 wrapper 脚本。这些差异如果没有一个 Agent 可读的载体，就会持续变成翻车点。

## 做法

核心思路：把环境事实沉淀成一份 Agent 可读的 markdown 文件，约定为 `tools.md`。

1. **分层放置。** 用户级 `~/.config/openclaw/tools.md` 记录个人全局环境（OS、默认 Python、代理）；项目级 `tools.md` 跟仓库走，记录项目专属工具链；机器级差异放 `tools.local.md` 并加进 `.gitignore`。优先级明确：项目 > 用户 > 默认。
2. **只记"猜不出来"的东西。** `which node` 这类可探测的事实不用写，要写的是探测不出来的：某命令其实是 wrapper、某工具在沙箱里不可用、Windows 下要走 WSL、内网需要特定代理。
3. **结构固定。** 每个工具一小节：路径、版本约束、调用示例、坑。开头放一段环境总览。整体控制在 100 行以内，超出部分链接到详细文档。
4. **用脚本生成骨架。** 写一个 probe 脚本跑一遍环境探测，填模板生成初稿，人工审一遍再提交。CI 或容器场景在镜像构建 / entrypoint 时自动生成，保证永远准确。
5. **允许 Agent 反写。** 在系统提示里约定：发现环境与 tools.md 不符时，先按实际情况执行，再把差异追加到"待确认"小节，由人工合并。

## 踩坑点

- **别放密钥。** tools.md 会被读进上下文、可能被提交。token 一律走环境变量，文件里只写变量名。
- **别让它烂掉。** 过期信息比没有信息更糟。定期重跑生成脚本，或要求改工具链的 PR 顺手更新这份文件。
- **别写成说明书。** tools.md 记事实，不记流程和规范，那是 AGENTS.md 的职责。混在一起两边都难维护。
- **分层冲突要显式。** 项目里装了不同版本的解释器时，写清楚哪个覆盖哪个，别指望 Agent 自己排序。

## 可复用建议

- 把 tools.md 当代码：走 review、走 diff，环境变更可追溯。
- 模板 + 生成脚本一起进仓库，新人入职第一件事就是跑一遍，生成自己的用户级文件。
- 保持配额心态：这份文件每次会话都会进上下文，每多一行都是成本。宁可短而准，不要全而杂。

## 总结

tools.md 本质上是"环境即文档"：把原本靠猜、靠试探、靠口口相传的机器差异，变成一份可 diff、可 review、Agent 直接可读的事实清单。它不解决所有问题，但在多机、多人的 Agent 工作流里，是投入产出比最高的一个约定。
