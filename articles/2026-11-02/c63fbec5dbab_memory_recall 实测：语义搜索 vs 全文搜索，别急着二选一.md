## 背景

OpenClaw 的 agent 跑久了，memory 里会积累大量笔记：用户偏好、部署细节、踩过的坑。`memory_recall` 是把这些东西捞回来的唯一入口，它的检索质量直接决定 agent 是"记得住"还是"一本正经地胡说"。社区里经常有人问：记忆检索到底该用语义搜索（embedding 向量相似度）还是全文搜索（FTS/BM25）？我在这两个月里把两种方案都在自己的实例上跑了一遍，记录一下实测结论。

## 问题

单独用任何一种，都会在真实对话里翻车：

- **只用语义搜索**：查询"上次那个部署脚本为什么超时"，能召回语义相近的笔记，但查某个具体的报错码、文件路径、服务名时经常漏掉——向量对精确标识符不敏感。
- **只用全文搜索**：查"`nginx worker_connections` 怎么调"很准，但用户换个说法（"上次并发一多就 502 那个事"）就完全召回失败。

一句话：语义搜索管"换了说法也能找到"，全文搜索管"精确词必须命中"。真实使用两种情况都存在。

## 做法

我最终用的是**双路并行 + 合并排序**，步骤如下：

1. **盘点记忆库**。先确认记忆的写入结构：每条 memory 带自然语言摘要 + 原始路径 + 时间戳。这一步决定后面所有检索的上限。
2. **双路召回**。`memory_recall` 调用时拆成两次查询：原始问句走 embedding 相似度；同时从问句里抽取关键词（报错码、路径、专有名词）走全文索引。
3. **合并去重**。两路结果用 RRF（reciprocal rank fusion）合并，同一来源文件只保留得分最高的分块，取 top 5~8。
4. **时效加权**。语义相似但时间久远的笔记容易压住新笔记，合并时给近 7 天的记录一个小的加分项。
5. **建立评测集**。写了 25 个真实召回问题（一半含精确标识符，一半是口语化描述），每次调整检索策略后跑一遍，看 hit@5。

## 踩坑点

- **中文分词是全文搜索最大的坑**。SQLite FTS5 默认 tokenizer 对中文基本无效，整句会被当成一个 token。要么换 trigram，要么写入时先做分词，否则中文查询召回率惨不忍睹。
- **embedding 模型别混用**。中途换模型意味着全库重新向量化，维度不一致还会静默报错。换之前先把模型名和维度记在配置里。
- **小记忆库别过度设计**。记忆条目少于几百条时，语义搜索的优势很小，全文搜索加上好的笔记结构完全够用，先跑起来再优化。
- **k 值别贪大**。一次召回 20 条塞进上下文，agent 反而容易被旧信息带偏，5~8 条足够。

## 可复用建议

- **检索策略是可以测的，不要凭感觉选**。20 个评测问题的成本很低，但能避免每次拍脑袋改方案。
- **记忆的写入方式比检索方式更重要**。每条笔记开头放一行含关键词的摘要，两种检索的命中率都会明显提升。
- 精确标识符（ID、路径、错误码）永远走关键词路；口语化回忆走语义路，不要指望某一路通吃。

## 总结

这个问题的答案不是"哪个好"，而是"各管一半"。双路并行 + RRF 合并是目前性价比最高的方案，但它建立在记忆本身结构化、可测量的前提上。先整理写入，再优化检索，顺序别反了。
