## 背景

Agent 跑久了，memory 目录会积累大量笔记：部署命令、踩坑记录、环境约定、用户偏好。笔记少的时候随便怎么取都能命中，但超过几百条之后，「能不能想起来」就变成了一个纯检索问题。我们社区的 memory_recall 默认走的是语义检索（embedding + 向量相似度），最近在真实使用里开始出现「明明记过，就是想不起来」的情况，于是做了一轮对比测试。

## 问题：两种检索，两种死法

**语义检索的死法：丢精确 token。** 我问「那个 0x8 的报错怎么处理」，库里有一条笔记明确写着 `ECONNRESET 0x8`，但向量检索返回的全是不相关的部署记录。原因是罕见 token（错误码、文件名、路径）在整段 embedding 里被语义稀释了。

**全文检索的死法：丢改写。** 笔记原文是「ws 掉线自动重连」，我查「websocket 断连重试策略」，BM25 直接零命中。同义词、中英混写、口语化改写，全文检索全无招架之力。

结论很清楚：单独用哪个都会漏，问题不是选型，是融合。

## 做法

1. **先盘点规模。** 当前约 1200 条 memory，平均 200 字。经验值：低于 500 条，全文检索 + 时间排序就够了，别上向量。
2. **搭全文通路。** SQLite FTS5。第一个坑就在这：默认 tokenizer 对中文基本失效，整句变成一个长 token，必须换 trigram 或用 jieba 预分词后存影子列。
3. **搭语义通路。** 本地跑 bge-small-zh，CPU 即可。关键是在**写入时**算 embedding 存进 sqlite-vec，而不是召回时现算。一条 memory 就是一个 chunk，不要细切。
4. **RRF 融合。** 两路各取 top 20，Reciprocal Rank Fusion（k=60）合并出 top 8，再叠加时间衰减（半衰期约 14 天），最终只注入 5 条进上下文。
5. **建评测集。** 手写了 30 条查询 + 对应应命中的笔记，测 recall@5。结果：纯 FTS 61%，纯向量 74%，混合 89%。数字不算漂亮，但方向明确。

## 踩坑点

- **中文分词是 FTS 的第一坑**，不做处理等于没建索引。
- **召回时现算 embedding 是浪费**，延迟和资源都白花，务必写入时算好。
- **top_k 贪多必失**。超过 8 条笔记塞进上下文，回答质量反而下降。
- **过期笔记不会自己死**。旧的配置类记忆会被混合检索「自信地」召回，需要定期清理或加墓碑标记。
- **中英混写 token（如「K8s 滚动更新」）要单独验证**，不少多语言 embedding 模型会把这类词糊掉。

## 可复用建议

- 语料过几百条就上混合检索，RRF 便宜、对排序算法无假设，别自己发明融合公式。
- 保留精确匹配逃生通道：查询里出现引号包裹的字符串、十六进制码、文件路径时，FTS 结果直通，不参与融合。
- **记录召回失败**。用户换个说法重问第二次，就是一次检索失败，攒起来喂评测集，这是最便宜的质量迭代。
- 配置类、事实类记忆时间权重应该高于相似度；操作类、流程类相反。如果笔记有类型标签，值得按类型分别调权。

## 总结

语义 vs 全文不是站队题：语义管改写和同义，全文管错误码和精确标识。混合检索 + 时间衰减 + 一个 30 条的评测集，比纠结换哪个 embedding 模型的收益大得多。memory_recall 的上限不在模型，在检索工程的基本功。
