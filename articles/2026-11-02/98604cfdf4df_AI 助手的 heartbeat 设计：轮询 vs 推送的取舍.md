## 背景

OpenClaw 这类常驻 agent 网关都带一个朴素机制：heartbeat。agent 每隔一段时间（默认 30 分钟）自唤醒一次，读一眼待办文件（HEARTBEAT.md），有活干活，没活歇着。很多人第一反应是"这也太原始了"，但真到设计触发链路时你会发现，heartbeat 背后是一个绕不开的架构问题：**agent 的工作到底由谁触发——轮询还是推送？**

## 问题

两种方式的差异不在"能不能实现"，而在三个工程指标上：

- **延迟**：轮询的延迟上限等于间隔；推送近乎实时。
- **空转成本**：每次 heartbeat 如果走 LLM，就是真实的 token 开销；推送天然零空转。
- **可靠性**：推送丢了是静默失败，你根本不知道；轮询错过最多等一个周期，行为可预期。

轮询的隐性坑：本地笔记本休眠时定时器不触发，容器重启后周期重置。推送的隐性坑：自托管 agent 多半在 NAT 后面，公网事件根本进不来；一旦接了 webhook，鉴权、重试、幂等全得自己补。

## 做法

1. **先按延迟需求给事件分类**。用户在等的事（消息回复、提醒）走推送；没人盯的事（日报汇总、仓库巡检、记忆整理）留给 heartbeat。
2. **让 heartbeat 保持便宜**。第一拍只做廉价判断：读待办文件，空则直接 no-op，不要每拍都把大段上下文喂给模型，重活由条件触发。
3. **按部署形态选推送通道**。有公网入口就 webhook；纯本地环境用 MQTT 或长轮询挂一个轻量 broker，插件收到事件后写入会话队列，别直接抢会话。
4. **幂等与去重**。每条事件带 event id，处理前查去重表；heartbeat 兜底扫描走同一套逻辑。
5. **把 heartbeat 定义成对账器**。推送是快路径，heartbeat 负责扫漏，两条路径最终收敛到同一状态。

## 踩坑点

- 每拍 heartbeat 都带全量上下文，一天下来 token 账单很难看。先判断，再升级。
- 推送没有重试等于静默丢事件，broker 至少要 at-least-once。
- 推送和 heartbeat 同时命中同一任务，没有幂等键就会重复执行——重复给用户发消息是最常见的翻车现场。
- 事件突发没有合并，推送风暴会打爆会话队列，加 debounce 或合并窗口。
- 上线前务必测一次"休眠后唤醒"和"重启后追赶"路径，定时器不讲道理。

## 可复用建议

- **默认架构是 heartbeat 打底 + 推送加速**，不是二选一。
- **触发与执行分离**：heartbeat 只决定"要不要干活"，不承担全部干活。
- **只度量两个数**：P95 事件延迟、每次空转 wakeup 的 token 成本。有了这两个数，间隔怎么定、要不要上推送，都不用争论。
- 间隔从事件的真实容忍延迟倒推，别拍脑袋。

## 总结

轮询买的是简单和确定性，推送买的是延迟和效率。自托管 agent 场景里，几乎总是混合方案赢：推送管用户在等的事，heartbeat 管没人盯的事。先把事件按延迟需求分好类，再决定通道，比先选框架再填坑省力得多。
