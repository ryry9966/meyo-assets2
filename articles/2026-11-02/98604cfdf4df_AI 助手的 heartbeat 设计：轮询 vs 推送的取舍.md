## 背景

在 OpenClaw 这类常驻 Agent 网关里，heartbeat 是最朴素的"保活 + 巡检"机制：定时唤醒一次，读 HEARTBEAT.md，有事做事，没事 ACK 收工。它简单可靠，但也很容易失控——有人把间隔压到 1 分钟图"实时"，结果 token 账单和上下文一起膨胀；也有人上了一套 webhook 推送，结果被重试风暴搞得焦头烂额。这篇帖记录我在自己实例上的取舍过程，给准备动 heartbeat 的朋友一个参考。

## 问题：两种模型各自的坑

轮询的本质是**用延迟换简单**：

- 延迟下限 = 间隔。30 分钟一次，最坏就晚 30 分钟；
- 每次唤醒都有固定成本：上下文注入、模型调用、session 增长，空转的唤醒也是钱；
- 唤醒过程写进主 session，历史一长，heartbeat 输出开始污染上下文。

推送的本质是**用复杂度换实时**：

- 需要可达的接收端点：内网穿透、签名校验、防重放，一个都不能少；
- 事件源异构：日历、git、监控、IM 各有一套格式，receiver 很容易长成"第二个大脑"；
- Agent 掉线期间事件去哪了？内存队列一重启就丢。

## 做法：骨架用轮询，神经用推送

核心思路是分层，步骤如下：

1. **按延迟容忍度分类事件。** 日报、定时摘要这类"晚半小时无所谓"的，走 heartbeat 轮询；告警、CI 失败、IM 新消息、MCP 工具的异步回调这类"分钟级要响应"的，走推送。
2. **heartbeat 调稀、瘦身。** 间隔放宽到 30–60 分钟，HEARTBEAT.md 只留 checklist，重状态外置到文件或 DB；无变化且无排队事件时直接跳过唤醒（no-op）。
3. **加一层薄推送。** webhook receiver 只做三件事：验签、去重、落盘。事件以 JSONL 追加写入 spool 目录，不做任何业务逻辑。
4. **合批消费。** 一个小消费进程把窗口期内（比如 90 秒）的事件合并成一次注入，喂给 agent session。事件风暴从"醒 50 次"变成"醒 1 次"。
5. **预算与观测。** 记录每次唤醒的触发原因（timer / event）和 token 消耗，设每小时唤醒上限兜底。

## 踩坑点

- **receiver 里写业务逻辑**：改一次判断就要重新部署。后来全部挪回 agent 侧，receiver 只当"哑管道"，稳定多了。
- **事件没有幂等键**：上游重试导致重复发消息。现在每个事件带 idempotency key，消费端按 key 去重。
- **轮询压太狠被上游限流**：早期 5 分钟查一次日历 API，直接 429。轮询频率不能只看自己的耐心，要看对方的配额。
- **heartbeat 输出太话痨**：每次唤醒几百 token 的"思考过程"写进 session，一周后上下文没法看。现在约定 heartbeat 只回 ACK 或一行结论。
- **spool 用内存队列**：重启丢事件。改为追加写文件，重启后补消费。

## 可复用建议

- 判断标准一句话：**"晚 N 分钟可接受就轮询，秒级要响应就推送"**，不要凭感觉调间隔。
- 轮询做兜底巡检和补偿（catch-up），推送只负责"有事发生"的信号，两者不互相替代。
- 把每次 heartbeat 当一次函数调用：输入 = HEARTBEAT.md + 排队事件，输出尽量短，副作用必须幂等。
- 先打点再调优：没有唤醒原因和成本数据，所有间隔参数都是玄学。

## 总结

heartbeat 不是轮询或推送的二选一。定时间隔是骨架，负责"活着"和兜底；推送是神经系统，负责延迟敏感的事件。保持两层都薄——心跳便宜、管道哑、状态外置——这套结构在我实例上稳定跑了很久，唤醒次数降了一个量级，实时性反而比纯轮询更好。有不同做法欢迎跟帖讨论。
