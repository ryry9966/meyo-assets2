## 背景

Agent 本身只会"想"，真正能"做"，靠的是工具调用。OpenClaw 里无论你走 MCP server 还是自定义插件，本质上都在做同一件事：把一个外部服务的 HTTP 接口，翻译成模型能理解、能正确填参、能读懂报错的工具。这个过程，就是 Agent 与 API 的握手。

## 问题

社区里最常见的不是"连不上"，而是"连上了但用不好"：

1. 模型选错工具或填错参数——工具描述写得像给人看的注释，而不是给模型的指令；
2. 调用成功但结果没用——返回一个两千行的 JSON，直接把上下文撑爆；
3. 看似跑通，一上生产就出事——重试导致重复建单，密钥进了日志。

## 做法：四步接上一个服务

以对接一个内部工单 API 为例：

**第一步：选接入路径。** 只读查询、逻辑简单，用 OpenClaw 的 HTTP 工具直接配；需要 OAuth 刷新、多接口编排，就写一个薄薄的 MCP server。原则是能薄不厚，别在插件里堆业务逻辑。

**第二步：把 schema 当 prompt 写。** 每个工具的 description 说清三件事：干什么、什么时候用、什么时候**不要**用。参数用 JSON Schema 给出类型和枚举，别让模型猜 `status` 是字符串还是数字。一个工具一个动词，拒绝用 `mode` 参数切换行为的"万能工具"。

**第三步：约定错误契约。** 不要把堆栈原样抛给模型。统一返回结构化错误：错误码、人类可读原因、建议动作（重试 / 修改参数 / 放弃）。模型拿到这个，才能自己走下一步。

**第四步：加安全垫。** 写操作加 `dry_run` 参数，默认先让模型确认再执行；超时设短，遇 429 按指数退避重试；密钥只从环境变量或密钥管理读，永远不进工具返回值。

## 踩坑点

- **大响应撑爆上下文**：分页和字段裁剪在工具层做完，别指望模型自己"挑重点"。
- **非幂等写操作被重试**：给请求加幂等键，或把"创建"改成"查询不存在再创建"。
- **长任务同步等待**：超过十秒的调用改成异步——提交后返回 job id，另给一个查状态的轮询工具。
- **工具太多**：超过十五个，模型开始乱选。按场景拆 MCP server，会话里只挂当前需要的。
- **描述与实现漂移**：接口改了、description 没改，模型按旧文档填参，排查半天才发现。

## 可复用建议

1. 工具描述当 prompt 的一部分来 review，而不是当 API 文档来写；
2. 所有调用记录 request id 和脱敏后的入参摘要，排障效率完全不同；
3. 先用 mock server 跑通全链路，再切真实凭证；
4. MCP server 打版本号，schema 变更走灰度。

## 总结

握手能不能成，不取决于模型多聪明，而取决于 schema、鉴权、错误契约这三件事定义得多清楚。工具面收窄、错误结构化、密钥走旁路——守住这三条，OpenClaw 对接外部服务就是体力活，而不是玄学。
