## 背景

OpenClaw agent 真正产生价值的地方不在对话本身，而在它能不能替你调用外部服务：查工单、发通知、拉数据。接口对接看起来只是"发个 HTTP 请求"，但从 agent 视角看，这是一次双向握手——agent 要理解服务的能力边界，服务也要能承受 agent 不按常理出牌的调用方式。

## 问题

我们团队最初对接几个内部服务时，踩的坑集中在三件事：

1. **鉴权信息散落**：有的写在 prompt 里，有的写在配置文件，一次日志泄漏排查花了半天。
2. **agent 传参不可控**：工具描述写得含糊，agent 会自己"脑补"参数格式，调用成功率忽高忽低。
3. **失败处理粗糙**：超时一重试，非幂等接口直接重复下单。

## 做法

我们把对接收敛成三层：

**1. 服务接入层**：优先用 MCP 封装。每个服务一个 MCP server，只暴露少量、语义清晰的 tool，别把 REST 全量接口一股脑塞进去。如果只是一次性的简单调用，直接注册一个 HTTP tool 也够用；但凡涉及状态维护、鉴权刷新或多个相关接口，就值得包成 MCP server。tool 的 description 按"给新同事的接口文档"标准写：什么时候用、参数含义、返回结构、失败时的表现。

**2. 鉴权与配置层**：密钥只走环境变量或 secret 管理，代码和配置里只留引用。OpenClaw 侧在启动时统一注入，工具实现里不做任何硬编码。

**3. 容错层**：
- 只读接口：5s 超时，失败重试 2 次，指数退避；
- 写操作：先判断是否幂等。不幂等的不自动重试，把错误原样返回给 agent，让上层决策；
- 大响应：分页或截断，别让一次调用把上下文窗口撑爆。

## 踩坑点

- **tool description 太短**。写"查询订单"不如写"按订单号查询单个订单详情，不接受模糊搜索，参数 order_id 为 32 位字符串"。描述精确度直接决定调用成功率。
- **重试把写接口打了两遍**。现在所有写操作默认不重试，除非显式声明幂等。
- **返回整页 JSON**。agent 不需要 200 条记录，截断到前 N 条再加一个 total 字段，省 token 也更稳。
- **错误只返回 HTTP 状态码**。agent 拿到 "500" 只会反复重试；改成返回带 reason 的结构化错误后，它能自己调整参数换路径。

## 可复用建议

- 新服务先只读接入，跑一周观察调用日志，再放开写权限。
- 每个服务包一层薄 adapter，把业务错误翻译成 agent 可读的结构，方便日后换底层实现。
- 日志对 token/密钥做脱敏，别让 debug 日志变成泄密渠道。
- 给每个 tool 加调用次数和耗时统计，异常的调用模式往往先于故障出现。

## 总结

对接外部服务不是"能不能调通"的问题，而是让 agent 与服务建立一份双方都遵守的契约：清晰的工具描述、受控的鉴权、明确的容错边界。做到这三点，这次握手才算真正握稳。
