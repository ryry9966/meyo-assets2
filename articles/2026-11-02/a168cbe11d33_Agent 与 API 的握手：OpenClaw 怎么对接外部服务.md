## 背景

OpenClaw 的 Agent 本身不产生业务价值，价值来自它能调用的外部服务：查数据库、发消息、触发 CI、读写内部系统。MCP 成为工具暴露的事实标准之后，“接一个服务”从写胶水代码变成了写一个 MCP server 或者一份插件描述。但**接得上**和**接得好**是两回事，我们团队最近半年接了十来个内外部服务，把经验沉淀成这篇。

## 问题

实际对接中反复出现三类故障：

1. **Agent 调错工具、传错参数**——工具描述含糊，模型只能靠猜，猜错就连环重试。
2. **响应把上下文撑爆**——一个接口返回几万 token 的 JSON，三轮对话后 agent 开始“失忆”，忘记最初任务。
3. **认证与密钥管理混乱**——key 写死在配置里，日志里全是明文。

## 做法：固定成五步

1. **选接入路径。** 只读查询走 MCP server，复杂有状态的逻辑走插件，临时脚本直接 HTTP tool。不要为了“架构统一”强行归一。
2. **收窄工具面。** 每个业务域一个 server，只暴露 3–8 个工具。宁要两个语义清晰的窄工具，不要一个大而全的万能调用。
3. **写“给模型看”的描述。** 参数说明要写清约束：格式、取值范围、何时该用、何时不该用。描述本身就是 prompt 的一部分，不是注释。
4. **统一错误结构与响应裁剪。** 返回体设固定预算（比如 2KB），超出就分页或摘要；错误统一成 `{ok, code, message, hint}` 结构，agent 能据此自纠而不是原样复述给用户。
5. **加工程护栏。** 超时、指数退避重试、写操作带幂等键、每次工具调用落日志。

一个合格的工具描述大概长这样：

```yaml
name: query_order_status
description: 按手机号查询订单状态，返回最近 5 条。
parameters:
  phone: 11 位字符串，必填
notes: 仅支持已实名账号；不要用于批量导出。
```

## 踩坑点

- **描述写成“查询用户数据”这种废话。** Agent 会把所有工具挨个试一遍。要写“按手机号查订单状态，返回最近 5 条”这种可执行的精度。
- **长任务同步等待。** 一个跑 90 秒的导出接口会让 agent 空转到超时。拆成“提交任务”+“轮询结果”两个工具。
- **把原始 stack trace 抛给模型。** 它不会 debug，只会把报错朗读给用户听。在工具层吞掉异常，翻译成带 hint 的结构化错误。
- **写操作没做幂等。** Agent 重试一次，订单创建了两条。所有写接口必须带幂等键。
- **密钥管理偷懒。** 密钥放环境变量或密钥服务，配置文件只留引用；日志脱敏要在工具层做，别指望模型自己不 leak。

## 可复用建议

- 把每个工具当成一个产品来设计：**Agent 是一个没有耐心、但完全按字面执行的用户。**
- 建内部 tool 模板仓：超时、重试、日志、错误结构全部预置，新对接只剩填参数和写描述，半天能上线。
- 上线前做回放测试：固定一批工具调用样本，改了描述或参数定义后跑一遍，防止 agent 行为漂移。

## 总结

对接外部服务的难点从来不在 HTTP 调用本身，而在于把一个为人设计的 API，翻译成 agent 能稳定理解、安全使用的工具面。**描述、裁剪、幂等、密钥**——这四件事做扎实了，agent 和 API 的这次握手才算真正握上。欢迎在评论区交流你们对接时的坑。
