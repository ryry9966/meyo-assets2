# USER.md：别让你的 Agent 每个会话都重新认识你

## 背景

用 OpenClaw 一段时间后，大多数人会认真打磨 Agent 那一半的配置：SOUL.md 定性格，AGENTS.md 定规矩，工具和 MCP 越挂越多。但很少有人写另外一半——**关于用户自己的那份文件**。

结果就是：Agent 对自己是谁了如指掌，对你却一无所知。每个新会话都是冷启动。

## 问题

没有 USER.md 时，典型症状：

- 每次都要自我介绍一遍：技术栈、偏好语言、时区、机器环境；
- Agent 自作主张：给 macOS 用户出 `apt` 命令，给只写 Python 的人推 Node 方案；
- 反复确认你已经回答过的问题（“要直接给结论还是详细解释？”）；
- 不同会话行为不一致，像换了个人。

这些问题不致命，但持续消耗信任。Agent 缺的不是能力，是你这个人的**事实**。

## 做法

在我的 workspace 里，USER.md 与 SOUL.md 平级，全文控制在 40 行左右：

```markdown
# USER

## 环境
- 主力机：Arch Linux + zsh；容器用 podman，不用 docker
- 常用栈：Python / Go；编辑器 Neovim

## 偏好
- 默认中文回复，技术名词保留英文
- 先给结论，再给依据；不要客套铺垫
- 代码示例直接可运行，不要省略 import

## 边界（硬约束）
- 不要自动 git push
- 生产环境命令必须先展示再执行
- 不主动联系通讯录里的人

## 当前上下文
- 正在做日志采集的 side project（2025-06 起）
```

加载方式上，OpenClaw 会读取 workspace 的引导文件，把 USER.md 纳入即可；如果你的版本不自动加载，就在 AGENTS.md 里加一行指向它。原则是**一个事实只写在一处**，避免两份规则打架。

## 踩坑点

1. **写成了愿望清单。**"希望你能更高效地帮我”这类话没有信息量。只写可验证的事实和可执行的规则。
2. **太长。**超过一屏，token 成本上升，关键信息被稀释。控制在 50 行内，细节交给项目级文件。
3. **放了敏感信息。**真实姓名、住址、密钥、内网地址都别写——这份文件会随上下文发给模型服务端，用角色代称即可。
4. **过期信息堆积。**半年前的项目上下文会误导 Agent。给易变小节加日期，每月扫一遍。
5. **越界。**某个仓库的构建命令属于那个仓库自己的 AGENTS.md。USER.md 只放"跟着你走"的内容。

## 可复用建议

- 骨架就四块：**环境、偏好、边界、当前上下文**。边界用硬措辞（“必须”“不要”），偏好用默认值（“默认……”）。
- 像对待接口契约一样对待它：改一次提交一次，git 历史能看出你的协作偏好如何演化。
- 验证方法很朴素：开个全新会话问“我的主力机是什么系统？”“哪些事你不该擅自做？"答不上来，说明没加载或者写了废话。
- 团队场景可做脱敏模板，新人克隆后十分钟就能跑起来。

## 总结

USER.md 的本质，是把“你希望别人怎么配合你”从口头默契变成可版本化的配置。写它的过程本身就是一次梳理——很多偏好你自己都没意识到。半小时投入，换每个会话省掉的开场白和纠错。值得做。
