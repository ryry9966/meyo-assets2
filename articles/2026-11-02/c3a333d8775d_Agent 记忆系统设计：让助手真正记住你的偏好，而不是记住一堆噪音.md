## 背景

LLM 本身是无状态的。每次开新会话都得重新交代一遍：回复用中文、commit message 用英文、部署只走 docker compose、别碰那个老分支。context window 再大，也不该拿来当硬盘用。对 OpenClaw 这类常驻助手来说，"越用越懂你"是核心卖点，但它不会自动发生——记忆层要自己设计。

## 问题

常见的三条歧路：

- **全塞 system prompt**：记忆越积越多，token 烧钱，内容互相矛盾还没法维护；
- **只靠会话历史**：换个会话、换个入口，全丢；
- **一步到位上向量库**：基础设施先行，闭环没跑通就变成没人敢动的黑盒。

真正的难点不在"存起来"，而在写入时机、存储结构、检索策略三者构成闭环。缺一环，"记住"就变成"记乱"。

## 做法

我的方案是三层存储加两条链路。

**存储分层：**

1. 会话内上下文：框架自带，不用管；
2. 结构化偏好库：起步阶段就是工作区里一份 YAML/markdown，字段带 `key / value / scope / source / confidence / use_count / last_used`，成熟后迁 SQLite；
3. 语义记忆（可选）：会话摘要和项目事实片段，做嵌入检索。

**写入链路：**

- 显式指令（"记住我部署只用 docker compose"）直接 `memory_write`，confidence=1.0；
- 隐式提取走会话结束钩子或每晚 cron：跑一次提取 prompt，候选偏好先落 staging，再次命中或置信度过阈值才转正；
- 更新一律按 key 做 upsert，旧值进 history，绝不 append。

**读取链路：**

- 会话启动注入结构化偏好全量（控制在 500 token 以内），语义记忆按当前任务取 top 3~5；
- scope 按工作区/项目隔离，公司项目和个人项目互不可见；
- 检索先走精确 key，再走向量——"部署方式"这类短词，嵌入经常不灵。

**治理：**

- 记忆操作全部走 MCP 工具（`memory_write / memory_list / memory_delete`），留调用日志，可审计；
- 用 `use_count` 和 `last_used` 做衰减，长期未用且低置信的归档；
- 定期把过期的会话摘要压缩合并。

## 踩坑点

1. **记忆污染**。用户随口一句"今天别用 TS"被记成永久偏好。解法：记 source 和上下文，区分一次性指令和稳定偏好，拿不准的一律进 staging。
2. **自相矛盾**。append-only 的库三个月后既写着"用 pnpm"又写着"禁用 pnpm"。必须 upsert 加冲突检测。
3. **注入过量**。两百条记忆全塞进 prompt，注意力被稀释，模型反而开始编造。给记忆区设 token 预算，超了按分数截断。
4. **黑盒不透明**。用户看不到助手记了什么，就不敢让它记。`memory_list` 是信任的最低保障，删不掉的记忆没人敢让它留。
5. **跨项目串味**。"回复用英文"从公司项目漏进个人项目。scope 从第一天就要做，后补很痛。

## 可复用建议

- **先文件后数据库**：进 git 的结构化文件可 diff、可回滚，闭环跑通了再谈向量库；
- **每条记忆必带元数据**：没有时间戳和使用次数，衰减和清理无从谈起；
- **preference / fact / episode 分开放**：三者生命周期完全不同，混在一个池子里迟早出事；
- **写入保守，读取慷慨**：宁少记不错记——错误的记忆比没有记忆更贵。

## 总结

记忆系统不是存储问题，而是"什么时候写、写什么、怎么取、怎么忘"的闭环。最小可用版本就是一份支持 upsert 的 KV 文件，加一条会话结束的提取链路，一个下午能搭完。先让它记对 20 条偏好，再考虑规模化。
