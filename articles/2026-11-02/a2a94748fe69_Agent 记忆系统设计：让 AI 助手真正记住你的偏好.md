## 背景

用 Agent 做日常开发自动化的人都有同感：每次新会话都要重新交代一遍偏好——"commit message 用中文""别自动 push""测试用 pnpm 跑"。模型本身无状态，会话一断，一切归零。OpenClaw 生态里 Agent 通常通过 MCP 与外部系统交互，把“记忆”做成一个独立的 MCP 服务是很自然的切入点。本文记录我给自己 Agent 搭记忆系统的一轮迭代，聚焦“偏好记忆”这个最小可行子集。

## 问题：三种常见做法为什么不成立

1. **全量塞 system prompt**：偏好少时能用，几十条之后注入的噪音比信息多，模型反而开始忽略关键约束。
2. **依赖会话历史检索**：token 成本高，而且偏好往往埋在闲聊里，检索命中率低。
3. **只写不删**：三个月后记忆里全是过期信息，“上个项目的构建命令”会污染当前任务。

核心矛盾：记忆系统的价值不在“存得多”，而在**在对的时候，给对的那几条**。

## 做法：分层 + 结构化 + 可遗忘

**1. 分层。** 工作记忆（当前会话上下文）不持久化；情景记忆在会话结束时用固定 schema 总结一条（做了什么、用户的反应）存 SQLite；重点做**偏好记忆**，即结构化 key-value。

**2. 记录结构。** 每条偏好带元数据：

```json
{
  "scope": "global | project:xxx",
  "key": "commit_language",
  "value": "中文",
  "source": "explicit | inferred",
  "confidence": 0.9,
  "last_used_at": "...",
  "superseded_by": null
}
```

`source` 和 `confidence` 很关键：用户明说的直接高置信写入；模型从行为推断的标低置信，复现两次才转正。

**3. 写入。** 不在对话中途抢工具调用（容易打断流程，还容易造成调用循环），而是在会话结束或空闲时跑一次提取 pass：模型输出候选偏好列表，key 相同则 merge / supersede，再落库。

**4. 读取。** 任务开始时检索：scope 过滤（当前项目优先）→ key 精确 + 关键词匹配 → 只取 top-k（我限制 10 条、400 token 内）注入。**控制注入量比提升召回更重要。**

**5. 遗忘。** 用户改主意时旧记录不删，标 `superseded_by`；低置信且长期未使用的记录进入清理队列，定期让用户确认。

## 踩坑点

- **一次性事件被当成永久偏好。** “这次用 npm 装吧”被存成永久规则。解决：提取时区分一次性指令与持续偏好，前者只进情景记忆。
- **矛盾记忆打架。** 新旧偏好冲突时模型行为随机。必须有 supersede 逻辑，注入时只给生效版本。
- **检索噪音。** 上 embedding 后召回变“宽”，无关记忆被塞进 prompt，模型开始胡乱套用。改回“scope 过滤 + 精确/关键词匹配为主，embedding 兜底”后稳多了。
- **隐私泄漏。** 提取 pass 曾把 API key 抓进记忆。加了敏感信息正则过滤和值长度上限。
- **记忆不可见导致不信任。** 做了 `memory_list` / `memory_forget` 两个 MCP 工具，让用户能看、能删、能改。

## 可复用建议

- 先做结构化 KV + 关键词检索，真不够用再上向量库。
- 记忆必须带元数据（来源、置信、时间），否则无法清理。
- 写入求准（宁可漏不要错），读取求稳（宁缺勿滥），两条链路分开调优。
- 让记忆对用户透明可编辑，这比任何算法优化都更能建立信任。
- 攒一批真实会话做回放测试，改了提取逻辑就回放一遍，对比记忆库 diff。

## 总结

偏好记忆本质上是个数据生命周期问题：结构化的写、克制的读、有依据的删。第一版只需要一张 SQLite 表加两个 pass，难点在字段设计和更新语义。如果你也在 MCP 侧做类似的东西，建议从“用户明说的偏好”这个最小集合开始，跑稳了再扩到行为推断。
