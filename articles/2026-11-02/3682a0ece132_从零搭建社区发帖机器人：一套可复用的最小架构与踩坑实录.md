## 背景

社区每周的精选摘要帖一直靠人肉整理：翻 issue、看群聊记录、汇总成帖。坚持两个月后明显掉链子——不是没素材，是没时间。于是做了个发帖机器人，目标很克制：每天自动生成一篇草稿，人工审核后发布。跑了一个多月，稳定出帖 40+ 篇，这里把架构和踩坑记录下来。

## 整体架构

刻意保持简单，五个模块：

1. **触发器**：cron 定时任务，每天早八点拉起。不搞事件驱动，素材频率根本不需要。
2. **素材采集**：Agent 通过 MCP 工具拉三个源——GitHub 的新 issue/release、RSS 订阅、论坛高赞未读帖。每个源一个独立 MCP tool，输出统一成 JSON。
3. **生成**：Agent 基于素材列表产出 Markdown 草稿，system prompt 里塞了 5 篇历史精选帖做风格锚定。
4. **审核**：草稿落库（SQLite），状态置 `pending`，推通知到群。人工确认后才进发布队列。
5. **发布与记账**：发布器从队列取任务，调论坛 API，写回 post_id 和状态；每次 LLM 调用记录 token 消耗。

关键决策：**Agent 本身无状态，所有状态进 SQLite**。生成和发布拆成两个进程，挂了互不牵连。

## 踩坑实录

**1. 去重不能只看 URL。** 第一周就发了两篇高度雷同的帖——素材源不同但主题重叠。后来加了双层去重：URL 精确匹配 + 标题 embedding 余弦相似度阈值 0.85，落库前查最近 14 天历史。

**2. 重试导致重复发帖。** 论坛 API 超时后重试，服务端其实已经收到，出现双帖。解法：发布前生成幂等键（日期 + 内容哈希），发布器先查库，同键记录存在就跳过。这是整个系统里最值钱的十行代码。

**3. 风格漂移。** 模型偶尔把标题写成营销号风格。两招压住：few-shot 锚定 + 发布前规则自检（标题长度、感叹号数量、禁用词表），不过关就打回重生成。

**4. 发布频率触发风控。** 补发积压任务时连续快速调 API，吃了 429。加令牌桶 + 2~8 秒随机抖动，问题消失。

**5. 没有日志等于没有机器人。** 第一次排查“今天为什么没发帖”，翻了半小时 shell 历史。之后强制：生成、审核、发布全写结构化日志，失败时 webhook 通知到群。

## 可复用建议

- 先做“每日批量 + 人工审核”，别上来就追实时全自动。审核环节是质量下限，也是观察模型行为最好的窗口。
- MCP tool 按源拆分，别写大而全的抓取工具——单源挂掉时你希望能单独降级。
- 幂等键、去重、限流，在写第一行生成代码之前就该设计好。它们和 LLM 无关，但决定机器人能不能活过第一周。
- token 消耗从第一天记账，成本失控往往从“反正一次没多少钱”开始。

## 总结

这个项目里真正花时间的不是 prompt，而是去重、幂等和可观测性这些“无聊”的部分。Agent 负责让内容生成变便宜，工程负责让这件事可信。架构和清单都在上面，欢迎直接抄作业，也欢迎评论区聊聊你们的风控策略。
