## 背景

OpenClaw 每次新会话启动时，agent 都会先读取工作空间里的几个固定文件，`AGENTS.md` 是其中最核心的一个。它不是给人看的文档，而是给模型看的指令：这个工作空间怎么用、哪些工具优先、哪些事不许做。`AGENTS.md` 本身是一个跨工具的社区约定（Codex、Cursor 等也认），OpenClaw 延续了这个约定，把它放在工作空间根目录，随会话自动注入上下文。

## 问题

没有 AGENTS.md 或写法不对时，常见症状：

- agent 每次用不同方式做同一件事，行为不可预测；
- 明明装了某个 MCP 工具，它还是绕路用内置方案；
- 上周纠正过的错误这周再犯；
- cron 触发的自动化任务输出格式漂移，无人值守时容易翻车。

原因很朴素：LLM 没有跨会话记忆，环境里"显而易见"的约定对它来说并不存在。

## 做法

1. 新建工作空间时 OpenClaw 会生成一份默认模板，别留空也别推倒重来，在模板上改。
2. 内容分四层写：目录结构 → 工具偏好 → 硬性约束 → 输出格式。
3. 用祈使句，每条可执行、可验证；不写背景故事。
4. 跑几个典型任务，观察偏差，把人工纠正的过程沉淀成新条目。
5. 定期修剪，删掉从未触发的规则。

一份能用的最小版本大概长这样：

```markdown
# Workspace conventions

## Structure
- notes/ 放长期笔记；tmp/ 放一次性产物，可随时清理

## Tools
- 网页抓取优先走 browser MCP，不要用 fetch 拼 HTML
- 图表用 chart 插件生成，输出到 tmp/

## Hard rules
- 禁止 git push --force
- 改配置前先备份到 backup/
- 超过 2 分钟的任务转后台执行并汇报进度

## Output
- 默认中文回复，代码注释用中文
```

## 踩坑点

1. **写太长**。它每个会话都占上下文，几百行会稀释注意力，关键规则反而被忽略。经验值是单屏以内，超过 100 行就该拆分。
2. **写成文档而非指令**。"本项目采用 X 架构"没有行为约束力，要改成"改动 X 前必须先做 Y"。
3. **规则互相冲突**。工具节说"优先用 A"，安全节又说"禁止 A"，agent 会随机选边。写新规则前先全文搜一遍旧规则。
4. **把敏感信息写进去**。它会被注入每次会话，还容易随工作空间同步外泄，密钥和内网地址不要放。
5. **只写不改**。它是配置不是文章：agent 犯一次错，就考虑是不是缺了一条规则。

## 可复用建议

- **分层管理**：通用偏好放全局层，项目特有规则放各自工作空间，一份文件别管所有场景。
- **规则带半句"为什么"**：比如"禁止 force push，避免覆盖他人提交"，agent 在边界情况下泛化得更准。
- **职责分开**：SOUL.md 管人格语气，USER.md 管个人偏好，AGENTS.md 只管操作规程，混写会互相干扰。
- **自动化任务的输出要求显式写进去**：cron 和插件触发的任务没有你在旁边纠偏，格式约定写在文件里最稳。
- **纳入版本控制**：效果退化时能 diff 回退，也能看清自己的运维经验是怎么积累的。

## 总结

AGENTS.md 的本质，是把你的运维经验编译成 agent 可执行的上下文。它不值得一次写完，值得每次出错后加一行、每周冗余后删一行。等你的 agent 表现稳定下来，回头再看这份文件，它就是你这个工作空间真实的运维手册。
