## 背景

OpenClaw 的 cron 任务本质是一次"无人值守的会话"：到点触发，agent 在一个全新的上下文里执行你写的那段 instruction，跑完把结果发到指定渠道。听起来简单，但很多人把 instruction 写成了聊天口气——"帮我看看最近的消息，总结一下"——然后发现凌晨跑出来的东西要么答非所问，要么根本没送到手里。

问题不在调度，在 prompt。定时任务里没有人陪你多轮对话，instruction 必须自己撑起全部上下文。

## 核心问题：执行时刻没有上下文

写聊天 prompt 时你默认了三件事：对方知道你是谁、知道"刚才"指什么、回复会回到当前对话。cron 触发时这三件事全不成立：

- 全新会话，没有历史消息；
- "今天""早上"这类相对时间没有锚点，服务器时区常常是 UTC，和你的本地时间对不上；
- 没人回答反问。agent 如果停下来"请问你想……"，任务就静默失败了。

## 我目前的写法：四段式

一个 cron instruction 我固定拆成四块，直接写进 instruction：

1. **身份与场景**：一句话说明这是什么。"这是每日 08:00（Asia/Shanghai）的定时简报任务，日期以系统时间为准，执行前先自报当前时间。"这一句同时解决了时区漂移。
2. **任务与数据源**：明确输入从哪来。"读取 `~/notes/inbox` 下过去 24 小时新增的文件"，而不是"看看最近有什么"。数据源不明确等于让模型自由发挥。
3. **输出格式与去向**：结果长什么样、发到哪。"输出不超过 10 条 bullet，通过 WhatsApp 发送给 +86xxx"。不写去向，结果就烂在会话里。
4. **失败与兜底**："如果 inbox 为空，发送'今日无新内容'；不要编造条目。"这一段最容易被省略，也是幻觉的主要来源。

## 踩坑点

- **相对时间**：instruction 里写"昨天"，模型推算时可能基于错误时区。显式写时区，日期让 agent 用系统时间算。
- **让 agent 提问**：cron 里没有第二个人。所有"如果要 A 就问我"的分支，都改成"如果 A 就默认做 B"。
- **依赖上次运行的状态**：每次运行是独立会话。真需要状态（比如"上次推过的不再推"），就落盘：让任务把已处理 ID 写进文件，下次先读文件再过滤。
- **一个任务塞多件事**：简报 + 周报 + 监控挤在一段 instruction 里，哪部分失败都说不清。拆成多个 job，频率和兜底各自独立。
- **写完就上线**：先手动触发跑三五次，确认输出格式和投递去向稳定，再挂正式时间；上线后第一周每天抽查一次。

## 可复用建议

把四段式存成模板，新任务只填空：场景 + 数据源 + 输出格式与渠道 + 兜底。原则一句话：**假设执行时刻你不在场、agent 失忆、数据源可能为空**——instruction 写到这个假设下还能正确产出，才算合格。

## 总结

Cron 任务的质量上限不取决于调度器，取决于那段 instruction 是否自足：时间有锚点、输入有出处、输出有去向、失败有交代。按四段式来写，手动验证后再上调度，大部分"定时任务不靠谱"的问题会自然消失。
