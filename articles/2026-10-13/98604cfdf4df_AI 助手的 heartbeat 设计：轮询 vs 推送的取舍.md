## 背景

OpenClaw 这类常驻 agent 网关里，heartbeat 是最容易被低估的机制：agent 按固定间隔醒来，扫一眼 HEARTBEAT.md 和环境状态，决定要不要做事。很多人跑通之后的第一反应是把间隔从 30 分钟调到 5 分钟，觉得"更及时"。然后 token 账单和上下文噪音会先教会你做人。

## 问题

本质上 heartbeat 要解决的是"agent 如何知道该干活了"，只有两条路：

- **轮询（polling）**：agent 定时自查。简单、可控、无外部依赖，但响应延迟 ≈ 间隔时长，成本 = 每次唤醒的 token + 工具调用。
- **推送（push）**：事件源主动通知（webhook、MCP 事件、消息平台回调）。延迟低、空闲时零成本，但丢事件、重复事件、服务重启窗口都得自己兜。

没有银弹，只有按事件源特性做分配。

## 做法

我的分层策略，三步：

1. **盘点事件源，按"能否主动通知"分类。** GitHub、邮件、消息平台有 webhook → 走推送；网页价格、本地文件、没有 API 的内部系统 → 只能轮询。
2. **推送为主，心跳兜底。** 推送只做"通知"，不当"状态源"：事件先落本地队列做幂等去重，agent 被叫醒后拉取处理。推送链路挂了，最多延迟到下一次心跳补上——此时心跳退化为低频对账（reconcile），30–60 分钟一次足够。
3. **心跳提示词写"判据"，不写"清单"。** HEARTBEAT.md 里明确：什么条件才算需要叫醒、醒来后只做 diff 比对不直接执行、无事可做就静默返回。判据越窄，误唤醒越少。

## 踩坑点

- **心跳提示词太宽。** 早期我写过"检查有没有新东西"，结果每次唤醒都触发动作，一轮几千 token 还污染会话上下文。改成"仅当 X 条件满足才输出动作"后，触发率降到 5% 以下。
- **纯推送没有兜底。** 网关重启的 30 秒里 webhook 打过来就丢了，而且你不知道丢了。任何推送链路都必须能被下一次心跳的重放覆盖。
- **自适应间隔没加抖动。** 多个 agent 用同一条退避曲线，会在同一时刻集体醒来，打满 API 限流。间隔乘个 0.8–1.2 的随机系数即可。
- **心跳里干重活。** 醒来后同步跑十分钟爬虫，主循环全堵住。心跳只做检查和入队，执行交给正常任务流。

## 可复用建议

- 心跳 = 检查 + 对账，不执行；执行走正常任务队列。
- 推送 = 通知，不是状态源；可重放的对账才是最终一致性的来源。
- 心跳间隔宁长勿短，先跑一周观察触发率，再逐步收紧。
- "该不该醒"的判据写成明确可判断的条件，不要靠模型自由发挥。

## 总结

轮询换确定性，推送换及时性，成熟的方案几乎都是推送打头、心跳兜底的混合结构。heartbeat 的价值不在"醒得勤"，而在每一次醒来都能廉价、准确、可预期地回答同一个问题：现在有没有必须由我做的事。
