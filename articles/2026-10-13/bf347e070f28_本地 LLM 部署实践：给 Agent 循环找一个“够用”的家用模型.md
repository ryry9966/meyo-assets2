## 背景

做 Agent / MCP 自动化的同学大多依赖云端 API，但有两类场景会逼你考虑本地模型：一是涉及隐私数据的自动化流（日志、聊天记录、内部文档），不希望出网；二是高频调用的小任务（路由、摘要、格式化），API 费用累积得比想象快。这篇帖记录我在一台 16GB 显存的 Windows 主机和一台 32GB 统一内存的 Mac 上的部署过程——重点不是跑分，而是让模型在 Agent 循环里“够用”。

## 问题

本地部署的真正难点不是“能跑起来”，而是三个工程问题：

1. **显存预算**：权重 + KV cache 都吃显存，长上下文场景下后者经常被忽略。
2. **工具调用质量**：聊天表现不错的小模型，在多轮工具调用循环里可能连 JSON schema 都吐不稳。
3. **生成速度**：一次 Agent 任务可能触发 20+ 次模型调用，10 tok/s 和 60 tok/s 就是不可用和可用的区别。

## 做法与步骤

**1. 摸清硬件预算。** 显存是硬约束。经验值：Q4 量化的 7-8B 模型约需 6GB，14B 约 10-12GB，32B 至少 20GB+。Mac 统一内存按 60-70% 折算，给系统留余量。

**2. 选运行时。** 个人使用直接上 Ollama 或 LM Studio，都提供 OpenAI 兼容端点，接入 OpenClaw 只需改 base_url 和模型名。Linux + N 卡追求吞吐可上 vLLM，家用场景收益不大。

**3. 选模型。** Agent 场景优先验证工具调用能力，而不是榜单排名。中文环境下 Qwen 系列 7B/14B 是稳妥起点；14B 是目前家用硬件上能力与速度的甜点位。

**4. 量化选 Q4_K_M。** 社区验证过的平衡点。低于 Q3 的量化在工具调用场景下 JSON 输出容易崩，省下的显存不值得。

**5. 接进 Agent 循环实测。** 写一个冒烟脚本：固定系统提示词 + 3-5 个真实 MCP 工具调用，跑完整循环，记录每轮耗时和调用成功率。每次换模型就重跑一遍，数据比感觉可靠。

## 踩坑点

- **KV cache 占用被低估**：上下文开到 32k 后，内存占用远超权重本身。llama.cpp 系运行时默认上下文可能只有 4k，而 Agent 的系统提示词加 MCP 工具定义就可能吃掉大几千 token，务必显式设对。
- **聊天没问题 ≠ 工具调用没问题**：多轮循环后小模型容易漏参数、编造工具名。用真实 MCP 工具测，别用“帮我写首诗”验证。
- **重复惩罚别开太高**：会破坏 JSON 结构，导致下游解析失败。
- **推理型模型拖慢循环**：思考链输出在路由、分类这类场景是纯开销，跑工具调用时关掉 thinking 模式。
- **Mac 别把统一内存全给 GPU**：系统内存压力一大，推理速度反而崩。

## 可复用建议

1. 建一条混合链路：本地小模型做路由、脱敏、格式化，云端大模型做硬推理。本地模型是组件，不是替代品。
2. 维护自己的“硬件-模型-量化”三列表格，记下显存占用和 tok/s，比看任何评测都准。
3. 冒烟脚本做版本管理，每次换模型或量化跑一遍，五分钟避免线上翻车。
4. 个人使用并发为 1 就够，不要过度工程化。

## 总结

家用硬件跑本地模型，在 7B-14B 区间已经完全可用，前提是把“够用”定义清楚：工具调用稳定、速度可接受、显存有余量。把它当成 Agent 技术栈里一个需要认真测试的依赖服务，而不是一个玩具，本地 LLM 就能实实在在地替你省钱、保隐私。
