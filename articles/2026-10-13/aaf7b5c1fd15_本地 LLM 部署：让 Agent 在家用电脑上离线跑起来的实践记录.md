## 背景

做 Agent 自动化绕不开一个现实问题：MCP 工具链会碰到大量私人数据——本地文件、剪贴板、浏览器记录、日程。把这套东西全托给云端 API，心理负担和长期成本都不小。我的动机很简单：让一条「读文件 → 调工具 → 写结果」的自动化流程，在一台没有外网的家庭机上稳定跑通。

硬件基准：RTX 3060 12G 显存 + 32GB 内存，典型的中端家用配置。以下经验都基于这套环境验证。

## 问题

动手前真正的不确定点有三个：

1. 12G 显存能塞下多大的模型，量化怎么选；
2. 小模型的 function calling 是否稳到能撑起多轮工具调用——这是 Agent 场景和纯聊天的本质区别；
3. MCP 的工具 schema 本身就吃几千 token，上下文预算怎么留。

## 做法

**第一步，估算显存预算。** 经验公式：Q4_K_M 量化的模型，权重约占参数量 × 0.6 GB，再加上 KV cache。7B 约占 5G，14B 约占 9~10G，12G 显存跑 14B Q4 是舒适上限。

**第二步，选运行时。** 我用 Ollama 起步：一条命令拉模型，自带 OpenAI 兼容端点（`http://localhost:11434/v1`）。追求极限性能再换 llama.cpp，显存充裕且在 Linux 上可上 vLLM。对 Agent 场景而言，OpenAI 兼容接口是唯一重要的契约。

**第三步，选模型。** Qwen 系列 7B/14B Instruct 对中文和工具调用支持较好，Q4_K_M 起步够用。别追最新最大的，先跑通链路。

**第四步，接 Agent 和 MCP。** `base_url` 指向本地端点，`api_key` 随意填。关键验证点：把 MCP 工具定义转成 function calling 格式后，模型能否稳定输出合法 JSON 参数。这一步建议单独写个 20 轮的循环脚本压测。

**第五步，调参数。** context 显式设到 8k~16k（Ollama 里是 `num_ctx`），给工具定义留足空间；temperature 压到 0.2~0.4，长循环下低温明显更稳。

## 踩坑点

- **Ollama 默认上下文只有 2048/4096**，MCP 工具定义会被静默截断，表现为模型「忘了」某些工具。必须显式设大。
- **显存不够时运行时静默 CPU offload**，速度从 40 tok/s 掉到 5 tok/s。模型能跑不等于跑得对，看日志确认层数分配。
- **7B Q4 的工具调用成功率大约七成**，长循环必出错。对策：上 14B，或在 Agent 侧加 JSON schema 校验 + 失败重试，工程手段比换模型便宜。
- **KV cache 是显存大户**，context 开太大反而把权重挤去内存。
- **嵌入模型单独跑**，用 bge-m3 这类小模型，别让主 LLM 顺手做 embedding。
- Windows 下睡眠唤醒后显存不释放，重启运行时即可。

## 可复用建议

- 先用 7B Q4 验证全链路，再逐级升模型，顺序不能反；
- 用自己的真实 Agent loop 做基准：测「20 轮工具调用成功率」，公开跑分参考价值有限；
- 保留云端降级开关，本地失败自动切换，不追求 100% 离线；
- 持续记录 tok/s、显存占用和失败样例，这份日志是后续换模型的唯一可靠依据。

## 总结

2025 年在家用电脑上跑本地 LLM 做 Agent 自动化是务实的：12G 显存就能覆盖 7B~14B 的完整链路。真正的瓶颈不是速度，而是小模型工具调用的可靠性——围绕它做校验、重试和降级，比纠结选哪个模型收益大得多。从小模型开始，用真实负载度量，逐步加码。
