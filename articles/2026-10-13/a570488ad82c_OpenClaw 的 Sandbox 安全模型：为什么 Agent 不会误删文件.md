## 背景

OpenClaw 的核心使用方式，是让 Agent 拿到一整套本地工具：读写文件、跑 shell、调 MCP 服务。第一次跑通"帮我清理这个目录"的人，几乎都会冒出同一个念头：它要是路径搞错，把我家目录删了怎么办？

这个担心是合理的。LLM 会幻觉路径、拼错相对路径、在重试循环里把删除范围越扩越大。沙箱模型的职责，就是把这些"概率性错误"挡在确定性边界之外。

## 问题拆解

实际出事的路通常是这几条：

1. Agent 调文件工具时传了错误的绝对路径；
2. Agent 在 shell 里执行 `rm` + 通配符，范围比预期大；
3. workspace 里有 symlink 指向外部，操作"顺藤摸瓜"逃出去；
4. Agent 自己写了个清理脚本再执行，绕过上层工具的权限判断。

对应四个层面：路径解析、进程边界、链接逃逸、权限绕过。OpenClaw 的沙箱不是单点开关，而是四层叠加。

## 具体机制与配置步骤

**第一层：文件工具的路径边界。** 文件工具以 workspace 为根做路径解析——所有传入路径先 resolve 成绝对路径，再校验必须落在 workspace 前缀之下，越界直接拒绝。注意是"解析后校验"，不是字符串 `startsWith`，否则 `../` 这类变形都能绕。

**第二层：进程级隔离。** shell 工具默认跑在容器/沙箱进程里，只挂载 workspace 目录，且默认非 root。宿主机的 `.ssh`、`.env`、生产配置根本不在它的文件系统视图里——看不见的东西删不掉。

**第三层：破坏性操作的权限门。** 读默认放行，写限 workspace，删除、移动、批量覆盖走单独的确认通道，或要求调用里显式携带确认参数。确认记录和操作本身一起写进审计日志，事后可回放。

**第四层：链接逃逸防护。** resolve 之后再校验前缀，天然挡住 workspace 内 symlink 指向外部的场景；更稳的做法是挂载时加 nofollow 类选项，或在沙箱镜像里禁止创建指向挂载区外的软链。

## 踩坑点

- **最常见的破防**：为了"方便"把整个 HOME 甚至 `/` 挂进沙箱。挂载粒度一大，第二层形同虚设，只剩权限弹窗在撑。
- **允许执行任意 shell 后**，Agent 自己 `rm` 是不经过文件工具权限门的。这就是为什么 shell 必须关在容器里——工具层的检查可以被绕过，OS 层的边界不能。
- **权限提示疲劳**。把确认弹窗当"一路允许"点下去，第三层就没了。宁可把默认策略收紧，也不要靠人肉把关兜底。
- **相对路径 + Agent 自己 `cd`** 的组合，容易让"我以为在这个目录"变成真实事故。让工具统一收 workspace 相对路径，由框架负责解析。

## 可复用建议

- 给 workspace 单独建 git 仓库，任何误操作都能 `git status` + 回滚，是成本最低的兜底。
- 自动化上线前做一次演练：建一个诱饵目录结构，故意让 Agent 执行"全盘清理"，验证它实际能触达的路径范围。
- MCP 工具按需暴露，只给当前任务需要的工具，压缩权限面。
- 审计日志单独落盘、只追加，不要和 workspace 放在一起。

## 总结

"Agent 不会误删文件"，不是因为它够聪明，而是因为最坏情况下它也只够到一个被裁剪过的文件系统视图：路径解析挡越界，进程隔离挡看不见的文件，权限门拖住破坏性操作，git 和审计日志负责最后一公里。四层单独看都不完美，叠起来才是工程上说得过去的答案。别把安全寄托在"模型不犯错"上——它一定会犯，关键是犯错时能碰到什么。
