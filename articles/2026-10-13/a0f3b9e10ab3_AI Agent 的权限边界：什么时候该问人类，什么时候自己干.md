## 背景

跑过一段时间 OpenClaw / MCP 工具链的人，都会撞上同一个问题：agent 到底该有多大的自主权。权限给少了，每一步都弹确认，人沦为点击机器，自动化名存实亡；给多了，一条歧义指令就可能让它删文件、发消息、调付费接口。这不是玄学问题，是工程问题，可以拆成风险模型和落地策略。

## 问题：两类失败模式

**过度请示。** 所有工具都挂确认，前三天还认真看，之后开始无脑点"允许"，确认机制退化成仪式。这比没有确认更危险——它制造了安全的错觉。

**过度自主。** 模型对模糊指令自作主张。典型场景：让它"清理一下测试环境"，它顺手把生产配置也改了。模型没有恶意，它只是没有边界概念。

## 做法：按风险分级，而不是按工具类型

核心是别问"这个工具危不危险"，而问"这次调用失败后能不能撤销"。三个维度：

- **可逆性**：读文件可逆，发消息、付款不可逆；
- **影响半径**：只碰本地 workspace，还是会触达外部世界（邮件、群消息、第三方 API）；
- **资源消耗**：是否花钱、耗配额、写脏数据。

据此分三档策略：

**第一档：自动执行。** 只读操作、限定在 workspace 内的读写、幂等且可回滚的动作。比如列目录、查文档、跑本地测试。这类不确认，跑了也不心疼。

**第二档：确认后执行。** 不可逆、对外发送、涉及资金的动作：发消息、提交 PR、删文件、调付费接口。确认弹窗必须带足上下文——目标、参数、后果，让人 3 秒能做判断，而不是只给一个工具名。

**第三档：默认拒绝。** 不在白名单里的能力一律拒绝，需要时显式加白。宁可麻烦一次，不要静默放行。

落地步骤：

1. 盘点 agent 能触达的所有工具（MCP server、插件、shell）；
2. 逐个打标签：可逆性 / 影响半径 / 成本；
3. 配置成白名单 + 分级确认，默认拒绝；
4. 高危写操作先 dry-run：让 agent 输出将要执行的命令或内容，人审完再放行；
5. 全量审计日志，事后能复盘"它当时为什么这么干"；
6. 给自主执行设预算上限（次数、金额、时长），超限自动降级为确认模式。

## 踩坑点

- **确认疲劳**：弹得越多越没人看。宁可第一档放得宽一点，也要保住第二档确认的严肃性。
- **"只读"不等于安全**：一个 GET 接口可能触发对方业务流程，shell 里的"读"也可能间接改状态。
- **复合任务是重灾区**："整理收件箱并回复"中间藏着几十次不可逆发送。要先让 agent 给出执行计划，批计划，而不是批每一步。
- **插件权限会叠加**：单个插件无害，组合起来可能绕过边界——能读文件 + 能发 HTTP，就等于数据外传。要按组合评估。
- **模型会试探边界**：提示词里的限制不是硬约束，"请不要删除文件"挡不住任何事，真正的兜底是工具层白名单和沙箱。

## 可复用建议

- 默认拒绝，白名单放行；
- 按"可逆性 × 影响半径"分级，不按工具名分级；
- 确认弹窗给足上下文，3 秒可判断；
- 高危操作先出计划、dry-run、再执行；
- 审计日志 + 预算上限是底线配置；
- 每月回顾一次日志，调整分级——边界是长出来的，不是一次定死的。

## 总结

权限边界不是信任问题，是接口设计问题。好的边界让"自动执行"的部分跑得安心，让"需要确认"的部分真正被人看住。当你发现自己开始无脑点"允许"，或者 agent 替你做了一次你不想要的"主"，就是该回来调整分级的信号。
