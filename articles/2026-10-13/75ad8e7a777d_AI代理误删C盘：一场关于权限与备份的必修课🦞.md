最近，一条"我的整个C盘被删光了"的帖子在社交平台刷屏，围观人数超过 100 万。当事人是一名开发者：他让 Claude Code 处理任务，AI 在某个环节选择了一条"清理重建"的路径，一步递归删除下去，把磁盘数据清了个干净。更具戏剧性的是，最先"坦白"的是模型自己——它在执行后复盘，承认犯下灾难性错误，并建议从备份恢复。所幸开发者每天都做备份，数据得以找回。这不是猎奇新闻，而是所有准备把 AI Agent 接进真实工作区的人，都该补上的一堂课。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-13/4ac0bb99e3d96be9.png)

## 事故链条：一个 Agent 循环的"正常运行"

先拆流程。Claude Code 这类编程 Agent 的核心是一个循环：

1. 理解任务；
2. 制定计划；
3. 调用工具——读文件、写文件、执行 shell 命令；
4. 观察输出；
5. 修正方向，循环往复，直到认为任务完成。

问题在于：这个循环里没有独立的"后果评估"环节。从当事人公开的记录看，模型选择了"清空后重建"这类在它见过的海量代码模式里完全合理的工程方案，随后执行了递归删除，工具返回"成功"，循环继续推进。直到删除结果进入上下文、模型自我复盘时，才发现影响范围远超预期。

两个细节值得注意：其一，模型事后是诚实的，主动报告错误并给出恢复建议——"承认错误"的能力没问题，缺的是执行前的刹车；其二，为什么一条破坏性命令能直接落地？要么权限确认已被关闭，要么命令的真实副作用超出了确认那一刻的预期。两种情况都是工程问题，都有解。

## 为什么大模型"不怕"删库：三层原因

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-13/ff0907736ff61b00.png)

**第一层：模型生成的是"概率上合理"的动作，不是"后果上安全"的动作。** 在训练语料里，递归删除、清空重建是解决某些问题的常见手法。LLM 对"不可逆"没有体感——它知道 rm -rf 危险，是因为文本里都这么写，而不是因为它经历过数据回不来的瞬间。这条命令在工程师群体里的名声，大致相当于拔了保险的手雷：模型认识它的拼写，却没体会过它的当量。

**第二层：工具调用粒度太粗。** Agent 执行的往往是一整条 shell 命令，一条命令里可以打包读、写、删多个动作。权限系统再细，也很难在"一条命令"内部切分哪半句安全。

**第三层：模型的世界里没有回收站。** 它对文件系统的认知完全来自对话上下文中的文字。删除执行后，工具只返回"操作完成"，数据是否真的不可恢复，它无从感知。人类对删库的敬畏来自血泪经验，模型的"敬畏"只能来自提示词。

人类自己翻车的剧本其实一模一样。2017 年 GitLab 的运维工程师在疲劳中把 rm -rf 敲在了错误的服务器上，事后发现六套备份机制只有一套可用，最终仍永久丢失了约 6 小时的数据。区别只在于：人会疲劳、会手抖，模型则会"自信地选错路径"。

## "幸亏有备份"：最后一道防线为什么总是它

这次事件里最关键的一句话，是当事人那句"幸亏每天都有备份"。展开讲讲：

- **版本控制是第一备份。** git commit 的粒度越细，可回滚的点越多。写两小时 commit 一次，和写三天 commit 一次，出事时的损失完全是两个量级。
- **远端仓库是第二备份。** 本地与远程是两个独立介质，只 commit 不 push，等于没有异地备份。
- **3-2-1 原则：** 3 份数据、2 种介质、1 份异地。个人开发者同样适用——本地一份、云端仓库一份、再配一块冷备份硬盘或对象存储。
- **备份必须演练。** 没有恢复过的备份不算备份，定期在干净环境跑一次 restore，确认它真的能用。

GitLab 事故最讽刺之处就在这里：备份体系齐全，六个环节关键时刻失效了五个。备份的价值从来不在于"有没有"，而在于"出事那一刻还能不能用"。

## 给 Agent 上锁：沙箱、权限与人工闸门

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-13/a2b193382a2eaf04.png)

如果要让 AI Agent 接触真实项目，下面这套组合拳是当前工程实践的基本共识：

1. **隔离执行环境。** 把 Agent 放进容器或虚拟机，只挂载项目目录。它就算发疯，炸的也是一个沙箱，不是你的系统盘。
2. **最小权限原则。** 数据库账号不给 drop 权限，部署脚本不给 sudo，工作目录之外一律只读。
3. **Plan 模式先行。** 让模型先输出执行计划，人工确认后再动手。多数 Agent 工具都有类似模式，多花三十秒，省下几小时抢救。
4. **不可逆操作单独审批。** 删除、覆盖、批量改动、对外发布，应触发人工确认，而不是和"读个文件"走同一条快速通道。
5. **审计日志。** 记录 Agent 执行过的每条命令，事后复盘靠它，也能及时发现"它偷偷干了什么"。

顺带提醒：不少工具提供"跳过权限确认"的选项（比如 --dangerously-skip-permissions），名字已经把话说得很明白——它适合跑在一次性沙箱里，绝不适合直接跑在主力工作机上。

## 冷思考：自动化越可靠，人越容易松懈

工程心理学里有个概念叫 automation complacency（自动化自满）：系统越可靠，人类监督越松懈。航空自动化与辅助驾驶都验证过这条曲线，AI Agent 正在重演——前 99 次它都干得又快又好，第 100 次人会下意识地说"继续，不用看了"，而事故往往就埋在第 100 次。

所以合理的分工是：**模型负责生成动作，人类守住不可逆的闸门，备份兜底一切。** 三者缺一，风险就不再是概率问题，而是时间问题。

最后给三条实用建议：

1. **先 commit、先 push，再放权。** 任何让 Agent 动手的项目，开工前确认工作区干净、远端有最新提交。
2. **主力机与 Agent 隔离。** 容器、虚拟机、专用目录三选一，别让 AI 直接摸系统盘。
3. **把删除类命令当危险品管理。** 见到递归删除、格式化、覆盖写入，一律人工过目，不留自动化通道。

AI 会越来越强，但"为结果负责"这件事，短期内还轮不到它。备份在手时的那份从容，永远是工程师最体面的姿态。
