## 背景

OpenClaw 默认给 Agent 挂一个模型跑到底。但实际使用中，单一模型很难同时满足三件事：复杂任务的推理质量、高频自动化任务的 token 成本、以及私有数据不外发的约束。OpenClaw 本身支持多 provider 接入（云端 API、Ollama 等本地推理），配置里也有 primary/fallback 链和按 Agent 覆盖模型的能力——所以真正的问题早就不是"能不能接多个模型"，而是路由策略怎么定。

## 问题

我最初的用法很粗：主 Agent 全程旗舰云模型。一个月下来发现，大约八成 token 花在摘要、格式转换、定时汇报这类小模型就能干的活上；反过来，本地笔记、未公开代码这些内容又不适合发云端。两头亏：贵的算力用在了简单事上，敏感的数据还不得不上云。

## 做法

**第一步：给任务分类。** 翻一周的会话日志（OpenClaw 的会话和 token 记录都在本地），按四类打标：

| 任务类型 | 路由目标 |
| --- | --- |
| 规划、复杂工具链、长上下文推理 | 云端旗舰 |
| 高频轻任务：摘要、打标、格式化、定时汇报 | 本地 7B–14B |
| 隐私敏感：本地笔记、私有代码 | 本地 |
| 多模态：截图理解、OCR | 云端 |

**第二步：配 fallback 链 + 按 Agent 覆盖。** 主 Agent 旗舰起步，兜底链落到次旗舰再到本地，限流或断网时对话不断；跑定时任务的子 Agent 直接锁本地模型：

```jsonc
// ~/.openclaw/openclaw.json 节选，字段名随版本略有出入
"agents": {
  "defaults": {
    "model": {
      "primary": "anthropic/claude-opus-4-5",
      "fallbacks": ["openai/gpt-4.1", "ollama/qwen3:14b"]
    }
  }
}
```

**第三步：按失败升级，不按内容猜难度。** 轻任务先走本地，检测到工具调用失败或产出质量差，再换云端重试一次，比一开始就猜"这题难不难"稳定得多。

**第四步：记录每轮实际用的模型、tokens、耗时。** 用 `openclaw models status` 和日志对账，一周后回头调路由表。聊天里也可以用 `/model` 临时切换验证。

## 踩坑点

1. **本地小模型工具调用严格性差。** function call 参数经常缺字段，Agent 会陷入"调错→重试"循环。解法：给本地 Agent 只挂当前任务需要的 MCP 工具，别全量注入。
2. **MCP 工具 schema 吃上下文。** 十几个插件的工具描述轻松吃掉几万 token，8k 窗口的本地模型直接截断，表现为莫名"失忆"。走本地就要瘦身 system prompt 和工具列表。
3. **fallback 静默降级。** 主模型限流后悄悄落到本地，质量下滑但你没察觉。日志必须记"这一轮实际是谁在答"。
4. **量化太狠的版本别做编排。** Q4 量化的模型工具调用成功率明显下降，当摘要器可以，当编排者不行。
5. **云端重试放大成本。** 路由到旗舰后的失败重试、上下文重发会让账单翻倍，重试上限和超时要显式配置。

## 可复用建议

- 真正"必须旗舰"的任务通常不到 20%，先量化再路由，别凭感觉。
- 把本地模型当过滤器而不是主力：做预处理、摘要、去噪，把干净的上下文交给旗舰。
- 模型选择要可观测：没有 per-turn 的模型日志，路由就是玄学。

## 总结

多模型路由不是省钱小技巧，而是把算力和任务对齐的架构问题。OpenClaw 已经把"接多个模型"的门槛降到配置层面，剩下的才是工程师的活：分类你的任务、测你自己的数据、让每次降级可见。别追榜单，追你自己日志里的失败率和账单。
