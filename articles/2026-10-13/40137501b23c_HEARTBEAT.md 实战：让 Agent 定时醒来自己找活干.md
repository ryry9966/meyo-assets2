## 背景

OpenClaw 里的 agent 默认是纯被动的：你不发消息，它就一动不动。但很多事其实不需要人盯着触发——日历快到点、磁盘快满了、某个 RSS 出了新文章。OpenClaw 为此给了一个很小的机制：heartbeat。gateway 按固定间隔（默认 30 分钟）唤醒 agent，agent 读一遍 workspace 下的 HEARTBEAT.md，按清单决定要不要干活、要不要打扰你。

## 问题

常见的两种错误用法：

- **装完不写**：文件保持默认的 `HEARTBEAT_CHECKLIST: none`，agent 每半小时醒来发现无事可做，白白多一轮调度。
- **一次写满**：把二十条"帮我盯着 XX"塞进清单，每小时跑一遍，月底看 token 账单很难受，还会高频误报。

核心矛盾是：主动做事的代价（token、噪音）必须压得住，否则你迟早亲手把它关掉。

## 做法

1. **先定频率**。监控类任务 30–60 分钟一次足够，`HEARTBEAT_INTERVAL_SECS` 可调，改完重启 gateway 生效。
2. **编辑 HEARTBEAT.md**。每条任务写成三段式：看什么 + 判定条件 + 做什么。例如：

   > 检查 `~/logs/error.log` 末尾 50 行；若出现新的 ERROR，汇总 3 条以内关键信息发到 Telegram；否则只回 OK。

3. **利用静默路径**。无事发生时 agent 回 OK，不会转发到聊天渠道、不产生通知——这是控制噪音的关键开关，务必在清单里明确写上"无事则只回 OK"。
4. **分流输出**。需要人看的事发 IM，例行记录写本地状态文件，别全走通知。

## 踩坑点

- **清单长度失控**：每轮心跳整个文件都进上下文，建议 ≤5 条，宁少勿多。
- **判定条件模糊**："盯着服务器"没法执行，必须给阈值（"磁盘 >85%"）和动作（"发到哪个渠道"）。
- **间隔太短**：5 分钟一跳，大部分周期无事，纯烧钱。
- **塞重任务**：心跳适合"看一眼、判断、汇报"，10 分钟的批处理交给 cron 或专用任务，别堵在心跳里。
- **状态不复位**：报警后没有记录，下一轮又报一遍，IM 被刷屏。

## 可复用建议

- **给报警加状态文件**：发现异常时写入 `alerts.md` 并附时间戳，下轮心跳先读它，同类告警 24 小时内只报一次。
- **按场景维护注释块**（运维 / 个人助理 / 内容监控），用注释切换启用，避免文件越写越乱。
- **先低调上线**：先接本地 CLI 渠道观察一两天噪音水平，再接正式 IM。

## 总结

HEARTBEAT.md 本质是最小化的"cron + LLM 判断力"：定时触发是现成的，价值全部取决于你能不能把需求收敛成低频、条件明确、动作具体的指令。写好它的标准很朴素——绝大多数心跳便宜地返回 OK，偶尔一条心跳带来的消息，值得你被打断一次。
