## 背景

OpenClaw 默认接一个大模型跑所有事情，稳定运行一段时间后，最先撞上的两堵墙是账单和延迟。简单任务（整理通知、提炼消息、格式转换）和复杂任务（多步规划、代码生成、跨工具编排）对模型能力的要求差距很大，用同一个模型处理两头，要么浪费，要么不够用。

## 问题

全走 GPT：高频小任务把 token 费用顶上去，简单请求还要排队、等首 token。全走本地模型：MCP 工具一多、system prompt 一长，小模型的工具调用质量明显下滑，规划类任务经常中途断链。核心问题不是“哪个模型更好”，而是怎么按任务分流。

## 做法

我的分工原则是：**按任务类型路由，而不是按会话路由**。

1. 先给任务分类。本地模型适合：分类打标、短摘要、格式化、固定模板的草稿生成。GPT/云模型适合：多步规划、涉及工具调用的编排、长上下文、代码生成。
2. 在 OpenClaw 配置里把主模型设为云模型，负责 agent 主循环；再单独起一个轻量会话或插件，走 Ollama 之类的 OpenAI 兼容端点跑本地模型，处理高频低风险任务。
3. 配 fallback 链：本地模型输出校验失败（JSON 解析不过、工具调用为空）时，降级到云模型重试一次，并打日志留痕。
4. 控制发给本地模型的上下文：只带任务所需片段，不要把完整的 agent system prompt 塞进去。

路由判断先用规则（任务来源、prompt 长度、是否挂工具），规则不够再上小模型做分类器——但分类器自身也要有降级路径。

## 踩坑点

- **工具调用格式差异**：不同 provider 的 function calling 行为不一致，本地模型可能“看起来调用了”但参数是错的。建议对所有本地模型输出做 schema 校验。
- **上下文窗口**：8k 的本地模型接上完整 system prompt 加 MCP 工具列表后，实际可用空间很小，表现为答非所问。先查窗口占用，再怀疑模型能力。
- **fallback 死循环**：降级链配错会出现本地失败→云端失败→重试本地的循环，费用翻倍，务必加重试上限。
- **缓存不共享**：同一个 prompt 换个模型就重新计费，别指望跨模型命中缓存。
- **采样参数不同步**：两边温度不一致会导致输出风格漂移，下游解析莫名失败。

## 可复用建议

- 从两级路由（云 + 本地）起步，不要一上来搭三级路由矩阵。
- 先跑一周日志，统计 token 分布和失败率，用数据决定哪些任务迁到本地。
- 发往本地模型的工具 schema 尽量精简，能不带就不带。
- 所有降级路径必须可观测：哪个任务、哪一级失败、最终用了哪个模型，三个字段缺一不可。

## 总结

多模型路由的价值不在省钱本身，而在让每个任务匹配到合适的能力档位。OpenClaw 的会话和插件机制足以把这些拆开做：先用最简单的两级结构跑起来，剩下的交给日志和迭代。
