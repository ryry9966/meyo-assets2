## 背景

技术信息源越来越散：博客、GitHub Release、邮件列表、播客。我最后还是回到 RSS——它是少数格式稳定、可以完全自持的订阅协议。但 RSS 只解决"聚合"，不解决"读得过来"。这篇记录我用 OpenClaw + MCP 搭的一条摘要管线，跑了一个多月，稳定且成本可控。

## 问题

直接把几十条全文塞给模型总结，有三个明显问题：

1. token 成本不可控，长文一多费用翻倍；
2. 噪音大，软文和重复报道混在里面，摘要质量被拉低；
3. 输出格式不稳定，没法程序化渲染成日报。

所以管线的核心不是"调一次 LLM"，而是抓取、过滤、摘要、分发四段解耦。

## 做法

**1. 数据层。** 源用 RSSHub 自建实例 + 各站原生 feed。写了个 80 行左右的拉取脚本，cron 每 30 分钟跑一次，入 SQLite。表结构极简：guid、链接、标题、正文、来源、抓取时间。去重优先用 guid，缺失时 fallback 到链接 hash。

**2. 过滤层。** 纯规则：关键词黑名单、标题相似度去重、来源权重。这一层能砍掉六到七成条目，是成本大头。

**3. 摘要层。** 注册两个 MCP tool 给 agent：`fetch_pending_entries(limit, source)` 和 `save_digest(entry_id, summary, tags, quality)`。system prompt 里明确：每条输出两句以内摘要 + 3 个标签 + 质量评级，评级为"低"时允许直接存一个 skip 标记。超长正文先做抽取式截断再进模型。

**4. 分发层。** 定时触发 agent 汇总当日 digest，渲染成 Markdown，推 webhook 到 IM 和一个静态页。原文链接永远保留，摘要只是索引。

## 踩坑点

- **正文抽取**：很多 feed 只有 summary，需要抓原页。务必用 readability 类工具抽正文——我一开始把整个 HTML 塞进去，模型把侧栏导航当新闻写进了摘要。
- **guid 不稳定**：少数源每次刷新 guid 都变，导致重复入库，链接 hash 兜底必须做。
- **摘要漂移**：营销软文会被一本正经地总结。加质量评级 + 允许跳过后明显好转。
- **定时任务并发**：cron 和手动触发撞车会产生重复日报，加文件锁才解决。
- **时区**：feed 里的日期五花八门，"今日"一律以本地抓取时间戳计算，别信源里的时间。

## 可复用建议

- 四段之间用数据库衔接，任何一段挂了可单独重跑，不级联失败。
- 摘要输出强制结构化（JSON），下游渲染和统计都省事。
- 记录每次调用的 token 消耗，一周后你就知道哪个源最贵、值不值得继续订。
- 模型只做"压缩"和"评级"，别让它做"决策"——源的增删自己来。

## 总结

跑下来，每天早上一份 20 条左右的日报替代了我两小时的刷信息时间。这套东西的价值不在 AI 多聪明，而在可控：源是自己选的，节奏是自己定的，数据在自己库里。下一步打算把质量评级做成历史信号，自动降权低产出的源。代码不长，核心就是一张表 + 两个 MCP tool + 两个 cron，有兴趣的可以照着拆一遍，欢迎在评论区交流各自的过滤策略。
