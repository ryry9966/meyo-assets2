## 背景

OpenClaw 的 cron 任务本质是「定时唤醒的 agent 会话」：到点后，系统把你写的 instruction 作为 prompt 交给模型执行，跑完即止。它不是 crontab 那种确定性脚本——同一份 instruction，两次执行结果可能不同，因为背后是模型加工具调用的组合。

很多人把它当备注写，一句话完事，跑起来才发现各种不对劲。这篇记录我踩过的坑，以及现在在用的模板。

## 问题

我最初的写法是：**「每天早上 9 点汇报一下服务器状态。」**

结果出现过三种事故：一次因时区问题在错误的时间跑了；一次模型自己挑了个监控接口，缺数据时直接编了数；一次消息发到了默认会话而不是值班群。归纳下来是三个根因：

1. **cron 会话是全新的**，它不知道你之前聊过什么，「之前的任务」「上次说的那个」统统无效；
2. **instruction 是 prompt，不是配置**，写得模糊，模型就会自己发挥——自己选工具、自己定格式、自己补数据；
3. **没人盯着**，手动对话出错能立刻纠正，cron 跑错要等你翻消息才发现，往往已经晚了几个小时。

## 做法：六段式模板

现在我的每条 cron instruction 都按固定结构写：

```text
【任务】每天生成一次服务状态摘要。
【时间约定】一律使用 Asia/Shanghai 时区，先确认今天的日期再执行。
【数据来源】只允许调用 monitor MCP 的 get_metrics 工具，
禁止使用其他来源，禁止凭记忆推断。
【输出格式】## 摘要 / ## 异常项（无则写"无"）/ ## 建议，
合计不超过 200 字。
【发送目标】发到会话 ops-daily，不要发到其他会话。
【兜底】工具调用失败时回复"数据源不可用，本次跳过"，
不编造数值，重试不超过 1 次。
```

四个关键点：

- **时间与时区写进 prompt**。cron 表达式按服务器时区触发，模型对「今天是几号」也可能出错，开头就约定时区，并让它先确认日期；
- **工具白名单**。「查一下状态」会被解释成任何可能的路径，「只允许调用 X 工具」把自由度收回来；
- **输出模板化**。固定结构无论人看，还是给下游 agent 消费，都稳定；
- **兜底必须显式**。最重要的一条：不说「拿不到就说拿不到」，模型倾向于编一个看起来合理的数。

写完先手动触发一次，确认输出结构和发送渠道无误，再启用定时。

## 踩坑点

- **时区**：cron 触发时间按服务器时区算，服务器跑 UTC 时尤其要留心，prompt 里再强调一次；
- **任务间依赖**：任务 A 失败，任务 B 照跑，产出级联错误。宁可重复取数，不要假设前序成功；
- **明文敏感信息**：token、内网地址写进 instruction，会随会话记录落盘，改用环境变量或 MCP 配置承载；
- **让 cron 干长活**：轮询等待、批量处理几千条数据，超时风险高。cron 适合短平快，重活拆分或改成手动触发；
- **僵尸任务**：需求变了 instruction 没改，任务每天发没人看的通知，建议每月清理一次。

## 可复用建议

1. 一条 cron 只干一件事，组合逻辑放在 instruction 之外；
2. 状态外置：需要跨次记忆的任务，让 agent 把状态写到 workspace 里的文件，下次先读文件，别依赖会话记忆；
3. 先用便宜模型验证流程，多数定时摘要任务不需要顶级模型，稳定后再评估是否升级；
4. 轻量周期巡检交给 heartbeat，cron 留给「有明确产出物和发送目标」的任务，别混用；
5. 把 instruction 当代码 review：每次改动都跑一次真实验证，而不是「看起来没问题」。

## 总结

写 cron instruction 的正确心态，是给一个**没有记忆、没人监督的同事写交接文档**：它几点上班、该用什么工具、产出长什么样、出了问题怎么办，全部白纸黑字。写得越像 prompt、越不像备注，任务就越可靠。六段式模板（任务 / 时间 / 数据源 / 输出 / 渠道 / 兜底）不复杂，但足以把定时任务从「偶尔靠谱」变成「默认靠谱」。
