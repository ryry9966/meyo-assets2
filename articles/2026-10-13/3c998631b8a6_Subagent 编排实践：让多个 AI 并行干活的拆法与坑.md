## 背景

我平时用 OpenClaw 做日常自动化：每天早上汇总几个仓库的 issue 和 CI 状态，生成简报推到群里。一开始全靠主 agent 一把梭——采集、分析、写报告，全在一个上下文里顺序执行。结果是两个：**慢**，十分钟起步；**脏**，工具返回的大段 JSON 塞满上下文，写到报告时模型已经开始遗忘前面的要求。

后来我把流程改成 subagent 编排：主 agent 只做拆解和汇总，具体活交给并行的 subagent。改完整体耗时降到原来的三分之一，主上下文也干净了。这里把做法和踩的坑整理一下。

## 问题：什么时候值得拆

不是所有任务都该拆，我看两个信号：

1. **任务天然独立**：查多个仓库、跑不同检查、读多份日志，彼此不依赖，顺序执行纯属浪费。
2. **中间产物很大**：工具输出动辄几千 token，但最终只要结论。让 subagent 在自己的上下文里消化，只交回摘要。

反过来，每一步都依赖上一步完整输出的任务，硬拆并行只会增加协调成本。

## 做法

我的编排结构是"拆解—分派—回收"三段：

1. **父 agent 做拆解**：要求输出结构化任务清单，每个子任务带目标、输入、验收标准，并明确一句"只做这一件事"的约束。
2. **并行分派**：独立子任务并发跑，并发上限压在 3~4 个——再高容易撞模型速率限制，失败重试的代价反而更高。有依赖的步骤保持串行。
3. **约定返回格式**：每个 subagent 固定返回三样：状态（成功/失败/部分完成）、核心结论、异常信息。父 agent 按模板拼装，不自由发挥。
4. **失败处理**：单个 subagent 失败不中断整体，汇总里明确标注缺口，供人工补齐或单独重试。

## 踩坑点

- **写冲突**：两个 subagent 同时改同一个文件，后写的覆盖先写的。现在拆解阶段就按文件/目录划清写边界，或者把写操作串行化。
- **上下文传递过度**：一开始把父 agent 的完整历史塞给每个 subagent，token 成本翻倍，效果没变好。改成只传任务说明和必要的输入引用。
- **静默失败**：subagent 挂了，父 agent 拿到空结果当成功。返回格式里的"状态"字段就是为这个加的，缺字段直接判失败。
- **拆太碎**：拆过八个子任务，每个只干一两分钟的活，协调开销比省下的时间还多。现在要求单个 subagent 的工作量至少撑得起一份独立上下文。

## 可复用建议

1. 每个 subagent 绑定单一交付物，验收标准写进任务描述，不靠事后猜。
2. 并发保守起步（3 个），观察速率限制和成本再加。
3. 让任务幂等：重跑无副作用，写操作先落临时区再提交。
4. 给每次 subagent 运行留独立日志，排障时按子任务切片看。
5. 先用干跑模式验证拆解合理性，再真跑。

## 总结

subagent 编排本质是工程问题，不是模型问题：拆得准、边界清、返回格式统一，多 AI 并行就能稳定提效；拆得随意，只是把一个慢任务变成几个贵任务。建议从"采集类"任务开始并行化，风险最低，收益立竿见影。
