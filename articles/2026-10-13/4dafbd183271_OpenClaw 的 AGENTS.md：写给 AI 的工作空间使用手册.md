## 背景

AGENTS.md 是近年逐渐形成的社区约定：在仓库或工作区根目录放一个 Markdown 文件，专门写给会进入这个环境的 AI agent 读——README 给人看，AGENTS.md 给 agent 看。OpenClaw 把这个约定做成了工作区的默认组件：workspace 根目录下的 AGENTS.md 会在每次会话启动时加载进上下文，相当于系统提示词之外的一份“驻场操作手册”。你在里面写下的每条规则，都会成为 agent 在你机器上行动的默认约束。

## 没有它时的典型问题

- 每个新会话都要口头交代一遍：笔记在哪、用什么语言回复、哪些目录不能碰；
- agent 拿到 shell 和消息工具后行为不可预期：在错误的目录跑命令、把回复发到不该发的渠道；
- 约定散落在聊天记录里，换模型、换机器就丢，也无法 review；
- memory 越积越多，agent 不知道什么该读、什么该写、什么时候写。

这些本质是同一个问题：工作区缺一份显式、可版本化的操作契约。

## 我的做法

先看骨架（节选自我的 workspace）：

```markdown
# AGENTS.md

## 工作区结构
- notes/：会议与灵感笔记
- memory/：长期记忆，按月一个文件
- scripts/：可执行脚本，改动前先通读

## 沟通
- 中文回复，术语保留英文
- 不确定的事直说不确定，不要编造路径

## 工具
- rm、git push --force 等破坏性命令必须先确认
- 发消息前核对目标渠道

## 记忆
- 会话结束前把值得保留的事实写入 memory/
- MEMORY.md 只做索引，不堆正文
```

写法上五条经验：

1. **从最小集开始**：结构、沟通、安全三节就够，后面按需加；
2. **用祈使句**：写可执行的行为规则，不写背景故事和动机；
3. **每条规则对应一个真实踩过的坑**：写不出对应场景的规则，先删掉；
4. **进 git**：改动像改代码一样走 commit，能 diff 才能回滚；
5. **分层**：跨项目的个人习惯放全局 workspace，项目特有规则放项目内自己的 AGENTS.md，避免全局文件无限膨胀。

## 踩坑点

- **写太长**。我第一版写了近两百行，结果关键规则（删文件前先确认）反而没被执行。压到六十行以内后遵循率明显改善——这一段是和系统提示词、记忆一起竞争注意力的，短即是强。
- **写成 README**。给人的文档要解释 why，给 agent 的文档只需说清 what 和边界，铺垫越多越糊。
- **塞敏感信息**。AGENTS.md 会被完整注入上下文，API key、内网地址不要写，交给环境变量和凭证机制。
- **规则互相冲突**。“所有命令先确认”和心跳巡检要自动执行任务就会打架，冲突场景要显式写清优先级。
- **写完就忘**。它是 living doc：agent 犯一次错，就补一条能防住它的规则，流程等同修 bug。

## 可复用建议

- 建立“错误 → 规则”回路：每次 agent 行为不符预期，问自己“加一条什么规则能防住”，补进对应小节；
- 关键流程用 checklist 收尾，比成段散文有效得多；
- 每季度做一次减法，删掉长期没触发的规则；
- 验证方法很简单：新开会话，一个字不说，看 agent 的第一个动作是否符合预期。

## 总结

AGENTS.md 的价值不在文件本身，而在于它把“调教 agent”从聊天里的即兴发挥，变成了可 review、可回滚、可迁移的工程资产。它是你和 agent 之间的接口协议——接口越清晰，系统行为越可预期。建议今天就把自己口头交代过的约定搬进去，跑一周再迭代，比一次写完美更有用。
