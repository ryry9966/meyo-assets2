## 背景

让 OpenClaw agent 写技术稿很顺手：skills 里挂一个写作模板，输出就是标准 Markdown。真正麻烦的是发布环节——公众号、掘金、知乎、静态站，每家编辑器对 Markdown 的"方言"理解都不一样。手工贴一次还行，三个渠道每天发，就变成纯体力活，而且每次贴完都要重排一遍格式。

## 问题

实践中问题集中在三层：

1. **生成端不稳定**：模型有时用加粗当标题、代码块不写语言标签、把 frontmatter 混进正文。
2. **平台端有方言**：公众号要求全内联样式、外链图片有防盗链；掘金标准 Markdown 但窄屏表格会挤爆；知乎不认脚注。
3. **中间没有契约**：同一篇稿子发三个平台等于做三次人工转换，出错率和维护成本都很高。

## 做法

核心思路：**把 Markdown 当 AST 处理，而不是当字符串处理**。管线分四段：

**Step 1 生成约束。** 在 agent 系统提示里固定输出契约：单一 H1、frontmatter 声明 `title/tags/platforms`、代码块必须带语言、禁用裸 HTML。生成后先过 lint（标题层级、链接格式），不合规就带着报错回炉重写一次。

**Step 2 规范化。** 用 unified/remark 把 Markdown 解析成 mdast，做一轮通用清洗：展平过深嵌套列表、给无语言代码块补默认标签、相对链接转绝对链接。产出一份"标准中间格式"，所有平台都从它出发。

**Step 3 平台适配。** 每个平台一个 adapter（纯函数：mdast → 目标格式）。公众号 adapter 把标题降一级、给节点注入内联样式、图片先传素材库再替换 URL；静态站 adapter 只补 frontmatter 和 slug；掘金基本透传。adapter 之间互不感知。

**Step 4 校验发布。** 渲染前跑两个检查：图片是否全部换成目标平台可达 URL、有无未转义 HTML 泄漏。通过后才落盘或调发布接口。在 OpenClaw 里可以封装成一个 skill 或 MCP tool，由 cron 触发，agent 只负责写稿这一段。

## 踩坑点

- **别指望提示词解决所有问题。** 生成约束只能降低违规率，lint + 一次重写的兜底是必须的。
- **表格是重灾区。** 窄屏下宽表格必炸，超过 4 列建议直接转图片或降级成列表。
- **图片防盗链是最常见的隐性失败**：本地渲染正常，发布后图片全挂。素材上传要做成管线里的显式步骤，不能指望平台兜底。
- 脚注、公式、任务列表，先确认目标平台支不支持，再决定要不要在规范化阶段降级替换。
- adapter 改动必须补 golden file 测试：固定输入 mdast，比对输出快照，否则一次样式微调很容易把某个平台悄悄改坏。

## 可复用建议

- 元数据进 frontmatter，正文保持纯净；adapter 读元数据，不猜内容。
- adapter 保持纯函数、无副作用；上传图片、调接口等副作用全部收口到独立的发布步骤。
- 新增平台时先写"透传 adapter"验证中间格式够不够用，再逐步加转换规则——如果透传就失败，说明规范化没做干净。

## 总结

这条管线的关键不是某个具体工具，而是两个决定：把 Markdown 当 AST 而非文本，把平台差异收敛到独立 adapter。落地之后，写稿和格式适配彻底解耦，新增一个发布渠道的工作量从"每次手工重排"变成"写一个百行左右的转换函数"。
