## 背景

主 agent 单线程干活有两个老问题：一是上下文越滚越长，工具输出（日志、网页抓取、长文档）很快把窗口吃满，后面的事情开始“失忆”；二是批量任务串行跑太慢。subagent 的思路很朴素——主脑分活，工人干活：主 agent 保持轻上下文，只负责拆解、派发、汇总，脏活累活丢给一批短生命周期、上下文干净的 subagent。

## 问题：什么时候该拆

不是所有任务都值得编排。我总结两个信号：

- 子任务的中间产物**不需要进入主对话**，比如“读十个文件各写一份摘要”；
- 子任务之间**彼此独立、可并行**。

反过来，强依赖共享状态、或需要多轮用户确认的任务，硬拆只会更乱。先判断适不适合，再谈怎么拆。

## 做法：一套可跑的流程

以 OpenClaw 的 subagent 机制配合 MCP 工具为例：

1. **拆任务**：主 agent 先产出任务清单，每个条目包含目标、输入（路径/URL）、产出格式、验收标准。清单落盘成 JSON 或 Markdown 文件，不要只存在于上下文里。
2. **派发**：每个条目起一个 subagent，prompt 用固定模板：角色 + 单一目标 + 输出 schema。subagent 上下文从零开始，只带它需要的那部分输入。
3. **并发控制**：别一次全开。实践中 2–4 路并发比较稳——模型端有速率限制，工具端（浏览器实例、git 工作区）也可能互斥。用一个简单队列按批次派发即可。
4. **收口**：subagent 只回结构化结果（status、summary、artifact 路径），不回大段散文。主 agent 统一汇总汇报，失败条目记录原因，按需重试。

## 踩坑点

- **上下文想当然**：subagent 看不到主对话，别假设它“知道你在干嘛”。路径、约定、版本号都要显式写进 prompt。
- **工具冲突**：两个 subagent 同时操作同一个 git 工作区或浏览器实例，几乎必炸。要么按资源分片，要么对共享资源串行化。
- **结果格式漂移**：不约束输出 schema，汇总阶段就靠模型“猜”，错误会被放大。宁可 prompt 里贴一个空模板让它填。
- **过度并行**：任务数一多，派发与汇总自身的成本和失败率上升，收益反而为负。先串行跑通，再拆并行。
- **错误传播**：单个 subagent 卡死别拖垮整批，每个子任务都要有超时和降级路径。

## 可复用建议

- 任务清单和结果**落盘**，编排状态不依赖任何 agent 的记忆，中断后可续跑。
- subagent prompt 当代码维护：模板化、进版本库、改动走 review。
- 先用 2 个 subagent 的小扇出验证拆分方式，跑顺了再扩规模。
- **幂等优先**：让每个子任务可重跑、产出可覆盖，重试才是安全的。

## 总结

subagent 编排的本质不是“堆更多 AI"，而是更清晰的接口设计：拆解有清单、派发有模板、回传有 schema、失败有降级。把主 agent 从“什么都干”变成“只管派活和验收”，主上下文干净了，并行收益自然出来。建议从批量阅读、批量代码审查这类低耦合场景小规模试起，验证拆分粒度后再谈规模化。
