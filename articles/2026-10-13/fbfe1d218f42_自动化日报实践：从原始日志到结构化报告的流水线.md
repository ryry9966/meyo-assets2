## 背景

我们的执行记录散落在几处：Agent 的运行日志、服务端的应用日志、仓库的 commit 记录。日报原本靠人手动拼，格式不一，还经常漏掉当天真正的异常。这篇帖子记录用 OpenClaw 搭的一条日报流水线，思路很朴素：确定性代码处理数据，模型只做最后一公里的归纳。

## 问题

直接把原始日志丢给 Agent 有三个明显问题：

1. 日志体量远超上下文，模型只能看到片段，摘要漏掉关键错误；
2. 输出格式随缘，有时 JSON 有时散文，没法归档对比；
3. 数据缺失时模型会"好心补全"，编出看似合理的数字。

## 做法

**1. 定时触发。** OpenClaw 的定时任务每天固定时间拉起一次会话，作为流水线入口。入口只负责取数，不做总结。

**2. 采集与规整。** 通过 MCP 工具拉取各来源：文件读取、git log、HTTP 接口。所有时间戳先统一到本地时区，输出统一字段：时间、来源、级别、内容摘要。这一步是纯脚本，可单测。

**3. 确定性清洗。** 不要让模型读原始日志。先用脚本聚合：按级别计数、抽取 ERROR/WARN 行、按服务分组，压成几百行的中间 JSON，超长堆栈只留首尾。模型拿到的永远是"素材"，不是"全量"。

**4. 模型归纳。** Agent 收到中间 JSON 和固定模板的提示词，输出固定结构的 Markdown：今日完成、异常与原因、待办、风险。提示词明确允许写"数据缺失"，禁止推测数字。temperature 调低，输出先过 schema 校验，失败带着报错重试一次。

**5. 投递与归档。** 插件把成品推进频道，同时按日期归档三层产物：原始快照、中间 JSON、最终报告，路径形如 `reports/2025-06-07/`，重跑天然幂等。

## 踩坑点

- **时区。** 跑批机器是 UTC，cron 在本地八点触发实际是十六点，报告少了半天数据。后来 cron 和解析层都显式钉死时区。
- **上下文爆炸。** 第一版把当天日志全量塞进去，直接超限。改成先聚合再给模型，输入体积降了一个数量级。
- **输出漂移。** 模型偶尔自由发挥加章节。schema 校验加重试解决了大半，剩下的靠提示词里给一个完整输出样例。
- **静默失败。** 最危险的不是写错，而是根本没产出。加了个看门狗：触发后 30 分钟内归档目录没有新报告，就往频道发告警。
- **重复投递。** 手动重跑导致同一份日报发两遍。用日期路径 + 幂等写解决。

## 可复用建议

- 确定性的事交给脚本，模型只做归纳和措辞，这是整条流水线稳定的关键。
- 报告要可 diff：固定结构、固定字段，才能做周环比和趋势。
- 三层归档别省，出问题时能从最终报告一路回溯到原始日志。
- 提示词模板当代码管，改动走 review。
- 先接一个数据源跑两周，再扩第二个。一次接四个源，排障成本会淹没收益。

## 总结

这条流水线没有用到什么高级技巧，价值来自"分层 + 固定结构 + 兜底告警"三件朴素的事。模型只承担其中一小步，而这一步稳定的前提是前面全是确定性代码。建议从最小闭环开始：一个源、一个模板、一条告警，先让它连续两周不断线，再谈扩展。
