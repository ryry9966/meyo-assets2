## 背景

现在很多内容生产的起点是 AI：让 Agent 写技术笔记、产品说明、周报，产出几乎都是 Markdown。但终点往往不是一个文件，而是多个渠道——公众号、知乎、掘金、GitHub README、静态博客。Markdown 本身不是问题，问题在于**每个平台对 Markdown 的理解都不一样**。

我在 OpenClaw 里跑了一条内容发布管线，把 AI 产出归一化后分发到三个渠道，稳定运行了几周，本文记录设计思路和踩坑。

## 问题

差异集中在四类：

1. **渲染能力**：公众号编辑器只吃内联样式的 HTML，`<style>` 标签会被剥掉；知乎只支持 Markdown 子集，表格和脚注表现不稳。
2. **AI 产出不规范**：标题层级跳跃（H1 直接跳 H4）、代码块语言标签混乱（js / javascript 混用）、偶尔在 Markdown 里夹带内联 HTML。
3. **资源路径**：AI 引用的图片要么是本地路径要么是幻觉 URL，直接发布必挂。
4. **特性降级**：Mermaid 图、数学公式、任务列表，在部分平台要么不渲染要么渲染错。

## 做法

管线分四段，核心原则是**单一事实源 + 纯函数适配器**：

**1. 归一化（normalize）**
用 unified / remark 做第一道处理：标题层级收敛（全文一个 H2 起头，内部用 H3）、代码块语言标签按映射表统一、AI 夹带的 HTML 按白名单剥除。这一步输出"规范 Markdown"，与平台无关。

**2. 资源处理（assets）**
图片统一上传图床，回填绝对 URL；本地 Mermaid 和公式在转换前预渲染成 SVG/PNG。资源处理必须在格式转换之前——公众号的图片域名限制要在上传阶段解决，事后补不了。

**3. 平台适配（adapters）**
每个适配器是一个纯函数：规范 Markdown 进，平台载荷出。
- 公众号：remark → rehype → juice 内联样式，表格包横向滚动容器，代码块在服务端高亮后注入带内联样式的 span。
- 知乎：先 lint 检查是否踩到不支持语法，表格降级为列表。
- 博客 / README：直出 GFM，基本不用动。

**4. 预览与发布（dispatch）**
适配产物先落一个 HTML 预览页，人工确认后，OpenClaw agent 再通过对应 MCP 工具推送。不建议全自动直发，格式事故的代价远高于省下的十秒。

## 踩坑点

- juice 内联化后体积膨胀明显，长文会被公众号截断，先剔除无用样式再内联。
- 代码高亮别指望客户端：公众号会剥掉所有 class，必须服务端转成内联 style。
- 语言标签映射表要人工维护，`shell`/`bash`/`console` 归一错一个，高亮就花。
- 表格在移动端必然超宽，适配器里统一包滚动容器，比逐个修省事。
- Mermaid 转图片要放在管线里做，本地转完再传会出现版本不一致。

## 可复用建议

- 归一化规则单独成库，配 golden file 快照测试；适配器只吃归一化输出，不碰原始 AI 文本。
- 维护一份"平台能力矩阵"配置（是否支持表格、脚注、高亮方式），适配器读配置决定降级策略，而不是散落 if-else。
- lint 先于 transform，格式问题在归一化阶段就报出来，别等发布失败再排查。
- 少写正则，用 remark 插件做 AST 操作，写起来慢但崩溃率低一个量级。

## 总结

这条管线没有用到高深技术：unified 生态 + 几个适配器 + 一个人工确认环节。真正的收益在于把"格式适配"从每次发布的临时劳动，变成可测试、可复用的代码。AI 负责生成，管线负责让它落到任何平台都不走样——这才是自动化该有的样子。
