## 背景

在 OpenClaw 里搭自动化，定时任务几乎绕不开：每天早上推一份 AI 领域摘要、定期巡检一台服务器、每周整理一次订阅源。配置层面只有两样东西：一条 cron 表达式，加一段 instruction。前者决定“什么时候跑”，后者决定“跑成什么样”。

实际用下来，任务翻车的原因九成不在调度，而在那段被随手写掉的 instruction。

## 问题：Cron 会话是冷启动

很多人把聊天里随手打的 prompt 直接搬进 cron，效果立刻打折。根本原因是上下文差异：

聊天时 agent 有历史——聊过格式偏好、随时可以补充一句。而 cron 触发的是一个（近乎）全新的会话：没有记忆、没有历史，更关键的是，**没有人在场**。

正确心态是：你在凌晨三点给一个刚入职、没看过任何聊天记录、也无法向你提问的新同事派工单。写得含糊，它只能猜，而猜测的失败方式非常固定：

- **输出跑偏**：领域、条数、格式全靠临场发挥，一周七个样；
- **任务挂起**：数据缺失时它回复“请问您想要哪个来源？”，然后永远等不到回答；
- **内容编造**：检索失败时不忍心交白卷，给你编一份像模像样的日报。

## 做法：把 instruction 当工单写

一套经过验证的结构是六要素：

1. **任务一句话**：动词开头，只做一件事。“汇总过去 24 小时 HN 前端相关的高分讨论，生成日报。”
2. **数据来源**：点名要用哪个技能或 MCP 工具，别让它即兴选。
3. **时间窗口**：显式声明时区与区间，“以 Asia/Shanghai 为准，覆盖运行时刻往前 24 小时”，不依赖模型对“今天”的理解。
4. **输出格式**：固定模板加长度上限，“markdown，不超过 300 字，至多 5 条，每条标题+链接+一句点评”。
5. **投递目标**：写明结果发到哪。cron 的默认回复路径不一定是你想要的会话。
6. **失败与兜底**：失败时发简短错误说明、禁止编造；明确“不要提问”；与上期重复时如何标注。

对比一个例子：

```text
# 改前
每天早上给我整理一下昨天 AI 圈的新闻。

# 改后
以 Asia/Shanghai 时区计算，"昨天"为运行日前一天的 00:00–24:00。
使用 web_search 技能检索 AI 领域新闻，筛选至多 5 条，每条一行：
标题 + 链接 + 一句话点评，markdown 输出，全文不超过 300 字。
若检索失败或结果为空，只发送"今日检索失败：<原因>"，禁止编造。
不要向我提问，直接输出结果。
```

改前那句在聊天里没问题——你可以随时纠偏。在 cron 里，它是一张注定返工的工单。

## 踩坑点

- **默认它“记得”**。任何“按我们上次说好的格式”都是赌博，自包含是底线。
- **提问即挂起**。凡是可能触发追问的设计都是死路，“不要提问”必须显式写出来。
- **三个时间没对齐**：调度时区、instruction 里的时间词、数据源返回的时间戳。日报少一段或多八小时，基本都是这里的问题。
- **工具可用性**。聊天里可用的 MCP 工具，不代表 cron 会话默认加载。instruction 里点名它，上线前手动触发验证一次。
- **范围蔓延**。“顺便再把天气带上”——一个 cron 一件事，要加就开新任务，别让单条 instruction 长成小说。

## 可复用建议

- 把六要素存成骨架模板，新任务复制改参数：

```text
# 任务：<一句话，动词开头>
# 数据来源：<使用 <技能/工具名>，筛选条件>
# 时间窗口：<时区 + 区间>
# 输出格式：<结构 + 长度上限>
# 投递：<发到哪个会话/频道>
# 兜底：<失败行为> / 不要提问 / 重复处理
```

- instruction 当代码管理：存文件、进 git，改了什么有据可查。
- 新任务先手动触发跑三五次，确认输出稳定再挂正式频率。
- 让任务在输出末尾附一行运行信息（数据条数、耗时），回溯问题时非常有用。
- 结果给下游程序消费时，严格规定 JSON 结构并禁止代码块包裹，格式漂移是自动化管道最常见的断点。

## 总结

Cron instruction 不是聊天 prompt，而是给一个没有记忆、不能提问、但会准时出现的实习生的工单。做到四件事——自包含、显式时间窗、固定输出格式、写清失败路径——定时任务就能从“玄学”变成普通工程问题：可预期、可回溯、可修。
