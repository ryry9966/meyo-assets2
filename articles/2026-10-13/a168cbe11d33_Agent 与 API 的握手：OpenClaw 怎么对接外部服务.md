## 背景

Agent 真正产生价值的地方不是聊天，而是"动手"：查工单、发通知、拉数据、触发流水线。OpenClaw 里的 Agent 默认只有推理能力，所有对外动作都要通过工具调用完成。对接外部服务的路径大致有三条：直接注册 HTTP 工具、接入 MCP server、写插件。三条路都能走通，但工程量和可维护性差别很大。

## 问题

我们最早的做法很粗糙：把 API 文档贴进 system prompt，让模型自己拼 curl。演示时像模像样，问题很快暴露：

- 凭证直接写进 prompt，日志一开就是泄漏现场；
- 模型会"脑补"文档里不存在的参数，调用偶发失败且难复现；
- 没有统一超时，下游服务一慢，整个 agent 会话挂死；
- 错误响应被模型自由解读，用户看到的是幻觉式的"成功"。

根因是：我们把"协议协商"交给了模型，而这本该是确定性的工程问题。

## 做法与步骤

现在团队的标准动作是五步：

1. **先分类再动手。** 把要对接的接口按只读/写入、内部/外部分成四象限。只读接口可以直接暴露给模型；写操作必须加确认层或 dry-run 开关。
2. **显式定义工具 schema。** 参数名、类型、必填项、返回结构、错误码全写进 tool definition。模型不需要"理解"这个 API，只需要"填表"。
3. **凭证走环境变量。** 适配器在运行时注入 token，prompt 和日志里永远只有占位符。OpenClaw 插件配置支持 secret 引用，直接用即可。
4. **用 MCP 收敛接口面。** 服务多于三四个之后，逐个手写工具函数会失控。把它们包成一个 MCP server，Agent 看到的是一组语义清晰、粒度一致的 tool，鉴权和限流在一处收口。
5. **超时、重试、幂等三件套。** 每个工具默认 10s 超时；可安全重试的 GET 加指数退避；写操作带幂等键，防止模型重试导致重复下单、重复发消息。

## 踩坑点

- **错误要结构化返回。** 把 HTTP 500 原文丢给模型，它会道歉然后瞎猜。改成返回 `{code, retryable, hint}`，模型下一步的决策明显更稳。
- **rate limit 会引发风暴。** 模型遇到 429 会立刻重试，没有退避就是自我 DDoS。退避逻辑必须写在适配器里，不能指望模型"克制"。
- **schema 别贪多。** 参数越多，模型填错的概率越高。一个"查询订单"拆成两个窄工具，比一个带八个可选参数的宽工具好用。
- **写操作必须留痕。** 每次写入记一条 trace（谁、何时、调了什么、参数是什么），出问题能回放，事后也能作为给模型的上下文素材。

## 可复用建议

- 给每个外部服务写一个薄适配器：鉴权、超时、重试、错误归一化都收在这一层，工具函数只做参数翻译。
- 新接口先灰度：让 agent 在 dry-run 模式跑一周，收集误调用案例，再放开真实写入。
- 工具命名用动宾结构（`get_ticket`、`create_issue`），模型选对工具的概率显著高于名词式命名。

## 总结

Agent 对接外部服务，本质是把一次不确定的"模型即兴发挥"压缩成确定性的工程契约：schema 是契约文本，适配器是执行者，MCP 是标准化信封。模型只负责决定"调什么"，其余都应由代码兜底。把这条边界划清楚，agent 才敢真正被放进生产环境。
