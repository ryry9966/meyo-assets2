热搜挂了条消息：GPT-6.1 Sol 一夜之间扩容到 500k，而且完全免费。评论区立刻分成两拨，一拨已经冲进去薅，另一拨在问"长上下文不是最烧钱的活儿吗，凭什么白给"。这两个问题其实是同一个问题——把 50 万 token 的上下文窗口一口气拉满还不收钱，背后必然同时发生了两件事：推理成本被压下来了，以及有人愿意暂时不赚这笔钱。模型名和具体参数以官方文档为准，这篇拆的是它背后的通用原理：500k 从哪来，成本怎么打下来，免费又是谁在买单。

## 一、500k 是什么概念：八年涨了五百倍

先对齐单位。token 是大模型处理文本的最小单位，一个汉字通常对应 1 个左右的 token，英文大约 1 个 token 对应 0.75 个单词。上下文窗口（context window）就是模型一次能"读进去并一起思考"的 token 上限。

这个数字的历史大致是：

- 2019 年 GPT-2：1024 token，约两页纸
- 2020 年 GPT-3：2048 token
- 2023 年初 GPT-4：8k / 32k 两档，按档收费
- 2023 年中 Claude 把窗口拉到 100k，年底主流旗舰普遍到 128k
- 2024 年 Gemini 1.5 冲到 1M，长上下文军备竞赛正式开打

500k token 粗略相当于 30 万～50 万汉字，大约五本《哈利·波特与魔法石》，或一个中型代码仓库的大部分源码。实际意义在于：整本合同可以一次塞进去逐条对质；一个项目的全部代码可以整体喂给模型排查 bug；一整天的会议转写加往来邮件可以放进同一个窗口做交叉分析。这些事在 2k 时代得靠人先把材料切碎、摘要，模型只负责"复读"。

## 二、为什么长上下文贵：O(n²) 和那条线性膨胀的 KV cache

长上下文贵，贵在两个数学事实。

1. **注意力计算是平方级的。** Transformer 的 self-attention 要让序列里每个 token 都看一遍其他所有 token，两两配对。长度翻倍，计算量约变四倍。从 512 token 到 512k token，不是一千倍的差距，而是一百万倍的差距。
2. **KV cache 线性膨胀。** 推理时每生成一个 token，都要缓存之前所有 token 的 Key/Value 中间结果。按 70B 量级模型的原始结构粗算，fp16 下每 token 的 KV cache 约 2.5MB，128k 上下文就要 300GB 上下的显存——单卡放不下，500k 更是天方夜谭。

所以 2023 年之前，长窗口基本等于"把更多显卡排队上前线"，按长度定价自然陡峭。要让 500k 变得可服务，得先把这两笔账改写。

## 三、"一夜扩容"的工程底牌：四板斧

所谓一夜，通常是几个月的软件优化攒够后集中上线。这和所有"一夜爆火"的系统一样：你看到的只是一次 git push，看不到的是底下几千个 commit。业界做长上下文的通用套路：

1. **改注意力本身。** FlashAttention 重排显存读写，数学结果不变，速度和显存占用大幅优化；GQA/MQA 让多个查询头共享一组 KV 头，KV cache 直接砍到 1/8 甚至更少；滑窗注意力只保留局部窗口，配合 attention sink 保住远处关键信息。
2. **位置编码外推。** 基于 RoPE 做位置插值、NTK-aware 缩放、YaRN，让短序列训练出的模型获得长序列推理能力，"短训长推"，省下天价的长文本训练成本。
3. **显存工程。** vLLM 的 PagedAttention 像操作系统分页内存一样管理 KV cache，碎片大幅减少；KV cache 再做 INT8/INT4 量化又降一档；投机解码用小模型起草、大模型验证，把解码吞吐再抬一截。
4. **架构层面换打法。** MoE 每次只激活部分参数，稀疏化推理开销；线性注意力、Mamba 这类 SSM 结构把平方项摊平，混合架构已是不少长上下文模型的标准配置。

四板斧叠起来，同样的显卡能同时服务的长上下文请求数翻几倍是正常幅度。成本曲线压下来，才有资格谈"免费"。

## 四、完全免费的账本：谁在替你付钱

推理永远有边际成本——电费、显卡折旧、带宽一样不少。所以免费不是成本归零，而是有人在补贴，补贴通常换四样东西：

- **默认入口。** 用户习惯一旦养成，迁移成本极高。邮箱时代 Gmail 用 1GB 空间碾压对手的几 MB，抢的就是"默认打开"这个位置。
- **数据飞轮。** 真实使用中的提问、纠错、追问，是改进模型最值钱的燃料，比任何合成评测集都真实。
- **生态锁定。** API 接口、工具链、插件体系一旦围绕你搭起来，换一家就不是换个网页那么简单。
- **价格战心智。** 当各家能力趋同，价格本身就是产品。先免费占住心智，再用规模把单位成本继续摊薄。

对应的"隐形账单"也真实存在：限速、排队、高峰期降级到小模型、对话数据可能被用于改进服务。这些一般都写在服务条款里，只是很少有人读。免费额度用起来没问题，但要清楚自己在哪条泳道。

## 五、500k 的窗口 ≠ 500k 都读懂了

这是最容易被发布会数字带偏的地方。

- **大海捞针测试有局限。** 早期"在长文里埋一句话再提问"的测试很多模型能通过，但它只考了"检索"，没考"理解"。更严格的 RULER 基准显示，不少模型的有效长度明显低于标称长度。
- **Lost in the middle。** 2023 年斯坦福的研究发现，关键信息放在长文开头和结尾时召回率高，埋在中段明显下降。窗口大，不等于注意力均匀。
- **长上下文和 RAG 不是替代关系。** 通读型任务（整份合同、整个代码库的一次性分析）适合长窗口；常驻知识库、成本敏感、需要实时更新的场景，检索增强（RAG）仍然更划算。实践中两者混用是常态。

## 写在最后：三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-13/39755238e895a4bb.png)

1. **把长窗口当工作内存，别当硬盘。** 关键指令和核心事实放开头或结尾，并主动复述一遍；低价值背景材料放中间。重要任务拆开跑，别一次会话贪多。
2. **免费额度当开发环境，生产环境留后手。** 读清 rate limit、数据使用条款和模型降级策略；关键业务不要单点依赖任何一个免费池——昨天免费的东西，不承诺明天还在。
3. **自测有效长度再上生产。** 在你自己的长文档中间埋一条只有你知道的事实，然后提问。这个五分钟的土办法，比任何发布会数字都诚实。
