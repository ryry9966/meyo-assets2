## 背景

在 OpenClaw 插件和 MCP 工具链里，让模型输出结构化 JSON 是常态：工具参数填充、子任务路由、配置生成，全靠 `json.loads` 接下一跳。提示词里写明“只输出 JSON，不要任何解释”，但实际跑起来模型并不总是配合——中文指令、长上下文、低能力模型场景尤其明显。

## 问题

我们一条自动化流水线曾出现约 8% 的解析失败，把失败样本拉出来归因，大致五类：

1. **Markdown 代码围栏**：模型用三反引号包住 JSON，语言标识还常写错（json/JSON/无标识混用）；
2. **XML 风格标签包裹**：`<json>{...}</json>`、`<output>...</output>`，偶尔带属性；
3. **围栏 + 前后解说文字混合**出现；
4. **“类 JSON"**：全角标点、单引号、尾逗号、字符串内裸换行；
5. **一次回复多个代码块**，只有一个是有效 JSON。

直接 `json.loads` 对五类全军覆没；单一正则剥围栏只能救第 1 类。这类失败间歇出现，单测全绿、线上偶发，最难排查。

## 做法：分层解析管道

核心思路：把模型输出当**不可信输入**，逐层降级解析，而不是一个大正则一把梭。

```
Layer 0  直接 json.loads（快路径）
Layer 1  剥 Markdown 围栏：finditer 收集所有代码块，逐块尝试
Layer 2  提取 XML 标签内容（json/output/自定义标签），逐个候选尝试
Layer 3  括号配平扫描：定位首个 {，在字符串态/转义态感知下配平
Layer 4  修复层：去尾逗号、单引号转双、全角标点归一、去 // 注释
Layer 5  兜底：返回失败 + 原文，由调用方决定是否带原文重试
```

几个实现要点：

- **不要 raise，返回结构化结果**。统一返回 `ParseResult(ok, data, strategy, raw)`，`strategy` 记录命中哪一层。
- **括号配平必须跟踪字符串状态**。维护 `in_string` 和 `escape` 两个标志，否则字符串里的 `}` 会让配平提前截断——我们第一版的 bug 就出在这。
- **解析成功 ≠ 语义正确**。最后一道门是 schema 校验（pydantic 或 jsonschema），字段缺失、类型不对，同样触发重试。
- **重试用“修复提示词”**：把原始输出原样贴回去让模型自己改错，比换着花样重新问省 token。

## 踩坑点

1. **贪婪正则抓错块**：多代码块时 `.*?` 会匹配错位，改用 `finditer` 全收集再逐个尝试。
2. **别用 eval / ast.literal_eval 兜底**：前者是安全洞，后者不认 `true/false/null`，且都会被“类 JSON”文本骗出看似成功的结果。
3. **全角字符**：`，：""` 混入很常见，归一化集中在修复层统一做，别散落各处。
4. **流式输出别中途修复**：半截 JSON 修出来必然是错的，攒完再解析，或换增量解析方案。
5. **修复别太激进**：我们曾自动纠正疑似字段名的拼写，结果解析“成功”了、数据是错的。修复层只做语法级操作，语义问题交给 schema 校验把关。

## 可复用建议

- **抽成独立小模块**（我们叫 `llm_json.py`），插件、MCP handler、workflow 共用一份，别各写各的正则。
- **上报 `strategy` 命中分布**。如果围栏层占比高，说明该改提示词而不是继续加固代码——解析数据最终要反哺提示词侧。
- **结构化任务用低温度**；provider 有 JSON mode / structured output 就开，但兜底管道照样保留，厂商行为会变。
- **永远留存原始输出**。解析器升级后可以离线重放历史数据，修复当时的断点。

## 总结

LLM 输出解析的防御性编程，本质是把“模型会以任意格式表达正确答案”当作默认假设：分层解析管语法容错，schema 校验管语义把关，strategy 埋点负责把问题推回提示词侧。三层齐备，流水线才从“能跑”变成“敢挂着无人值守跑”。
