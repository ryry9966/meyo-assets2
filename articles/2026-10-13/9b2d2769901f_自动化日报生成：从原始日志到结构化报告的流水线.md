## 背景

我们团队每天要发一份日报，覆盖服务运行状况、构建部署记录、Agent 任务执行结果。之前是人工从各处捞日志、拼 Markdown，每天固定花 20-30 分钟，还经常漏项。这篇帖子记录把这件事做成全自动流水线的过程，思路不复杂，但有几个坑值得提前知道。

## 问题

原始日志有三个特点：散、杂、不可信。

- **散**：数据源至少四个——服务器日志、CI/CD 构建输出、OpenClaw 的 Agent 会话记录、监控告警 webhook。
- **杂**：格式不统一，有 JSON 行、有纯文本、有第三方平台的私有格式。
- **不可信**：如果直接把原始日志丢给 LLM 让它"写日报"，它会编数字、编结论。日报一旦失真，比没有日报更糟。

所以核心设计原则是：**数字和事实由代码产出，LLM 只负责组织语言**。

## 做法

流水线分四层，每层独立可测试：

**1. 采集层**：cron 每天固定时间拉取当日原始日志，落到 `raw/YYYY-MM-DD/` 目录，按来源命名。拉取失败记录 offset，下次补拉。

**2. 结构化层**：为每种来源写一个解析器，输出统一 JSON Schema：`{source, event_type, timestamp, entity, metric, raw_ref}`。能用正则和字段映射解决的绝不用 LLM。只有自由文本类内容（比如 Agent 会话里的一段结论）才过一遍 LLM 做字段抽取，要求 JSON 输出并做 Schema 校验，校验失败进人工队列。

**3. 聚合层**：按 event_type 分组，算错误数、部署次数、耗时分布、Agent 任务成功率。全部是确定性脚本，产出一份中间 JSON——这是整条流水线的"事实底座"，必须持久化。

**4. 渲染层**：中间 JSON + Markdown 模板 → 报告。LLM 在这一步只做两件事：把分组数据转成两三句小结、给"需关注"条目写一句备注。Prompt 里明确禁止引入模板和数据之外的信息。最终报告由 OpenClaw 定时任务推送到群里，同时归档一份。

## 踩坑点

1. **LLM 编造数字**：最早图省事把原始日志直接丢给模型，报告里的错误数和真实值对不上。改成代码算数、模型写字之后才稳定。
2. **时区问题**：日志里 UTC 和本地时间混用，第一版把"昨天"的数据算进了"今天"。现在所有时间戳在结构化层统一转成带时区的 ISO 格式。
3. **重复生成**：cron 偶尔重复触发，同一份报告发了两遍且内容略有出入。加了幂等键（日期 + 版本号），重跑只覆盖不追加。
4. **上下文超限**：高峰期日志量大，全量塞给模型直接爆。解法是聚合层先算好 top N，渲染层只拿摘要级数据。

## 可复用建议

- **中间产物必须落盘**：既能回放调试，也能在渲染层失败时单独重跑，不用重新采集。
- **每层一个脚本，各自可单测**：出问题时能快速定位是哪一层坏了。
- **对 LLM 输出做 Schema 校验**：不过就走降级路径（模板直接渲染数据，不要模型小结），日报永远能发出去。
- **保留 raw_ref 字段**：报告里每条结论都能溯源到原始日志，有人质疑数据时秒级定位。
- **分层可以顺手暴露成 MCP 工具**：把聚合层的查询能力包成一个小 MCP 工具，Agent 被问到日报细节时能自己查数，不用改动流水线本身。

## 总结

这套东西没有用到什么高深技术，核心就一句话：把"事实计算"和"语言组织"拆开，中间用一个持久化的结构化层隔开。OpenClaw 在这里承担调度和推送，真正的可靠性来自每层的确定性代码和校验。目前跑了三周，日报零漏发，人工介入次数为零。如果你的场景更复杂（多项目、多团队），建议先把 Schema 设计好，解析器可以慢慢补。
