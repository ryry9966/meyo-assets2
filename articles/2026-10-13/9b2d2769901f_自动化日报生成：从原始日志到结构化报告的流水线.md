每天收工前翻日志写日报，这件事不难，难在坚持和一致。我的 OpenClaw 实例每天跑着若干定时任务、插件调用和会话交互，日志散在多个文件里。最早我直接在晚间问 agent"总结一下今天的运行情况"，结果格式每天不一样，数字靠猜，日志一大就截断。后来改成一条固定流水线，跑了一个多月基本稳定，把做法和坑记下来。

## 问题出在哪

直接让 agent 面对原始日志有三个硬伤：

1. **上下文放不下**。一天的工具调用和调试记录轻松上百 KB，要么截断要么爆窗。
2. **数字不可信**。让模型数"今天失败几次"，它给你的是近似值。统计必须由代码算。
3. **格式漂移**。没有固定模板，日报没法横向对比。

## 流水线四个阶段

核心思路一句话：**确定性的事交给脚本，归纳判断的事交给 agent，两者之间用固定 schema 交接。**

**阶段一：收集与归一化。** 独立脚本由 cron 在 23:50 触发，从各日志源拉当天记录，统一成 JSON Lines，字段固定：`ts / source / type / duration / status / summary`。这一步纯代码，不经过模型。

**阶段二：分段预摘要。** 归一化数据按小时切块，每块单独喂给 agent，要求输出符合固定 JSON schema 的摘要：事件计数、错误列表、值得注意的异常。单次输入控制在几 KB，token 成本可控。schema 校验失败的块带错误信息重试一次，仍失败就标记缺失，不硬编。

**阶段三：聚合出稿。** 把全部分块摘要（此时总量通常只有几 KB）连同显式日期区间交给 agent，套一个版本化的 Markdown 模板生成日报。所有数字来自阶段二的统计字段，模板只留一处"人工观察"给 agent 自由发挥。

**阶段四：投递与留档。** 日报写入 `reports/2025-06/`，同时推送消息渠道；JSON 摘要作为 sidecar 存档，供日后做趋势统计或回溯某天的判断依据。

## 踩坑点

- **prompt 里别写"今天""昨天"**。agent 对日期的感知不可靠，要显式传 `2025-06-12 00:00 至 23:59` 这样的区间，时区换算由脚本负责——我的日志是 UTC、日报按本地时区切天，最初漏了这层，日报里的"昨天"实际是前天。
- **中间产物不设 schema 必翻车**。早期分块摘要偶尔输出散文，聚合阶段直接解析失败，加校验加重试后才算闭环。
- **cron 静默失败最难防**。流水线凌晨挂了没人知道，第二天还以为"没生成是因为没日志"。补了心跳检查：超时未产出文件就向消息渠道告警。
- **脱敏要在进模型之前**。日志里混着 token 和内网地址，归一化阶段统一打码，别指望模型替你保密。

## 可复用建议

1. 分层原则可推广到所有日志类自动化：采集与统计用代码，摘要与异常识别用 agent。
2. 中间 JSON schema 是流水线的契约，改字段要同步改校验和模板，建议连模板一起打版本号。
3. 原始日志永远只读，流水线可对任意历史日期重跑，排查"上周三到底发生了什么"就很轻松。
4. 先接一个日志源跑通全链路，再横向扩展，不要一上来铺四个来源。

## 总结

这套东西的价值不在于"AI 替我写了日报"，而在于把报告生产拆成了可校验的阶段：数字由代码保证，文字由模板约束，agent 只做最后一步归纳。成本从每天几千 token 的"猜"，降到几百 token 的"整理"，且任何一环出问题都有明确的失败点可查。
