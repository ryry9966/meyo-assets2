## 背景

OpenClaw 的主会话是长期存在的：指令历史、工具调用记录、持久化 memory 都挂在上面。任务一复杂，我们习惯派子 Agent 去干重活——批量读文件、跑检索、调 MCP 工具做探索。但一个现实问题随之而来：如果子 Agent 的每一步都写回主会话，上下文很快被中间产物填满，主 Agent 的注意力被稀释，后续推理质量肉眼可见地下降。

## 问题：污染具体是什么

实际踩到的污染有三种：

1. **上下文污染**：子 Agent 的工具原始输出、报错栈、长文档片段进入主会话历史；
2. **记忆污染**：子 Agent 把探索过程中的临时结论写进共享 memory，下个会话被当成事实召回；
3. **状态污染**：子 Agent 改了工作区文件或 MCP server 的全局状态，主流程拿到的是被动过的环境。

## 做法

OpenClaw 的隔离模型核心一句话：**子 Agent 有独立 session，只把最终结果回传主会话。**

落地四步：

1. **派发时划边界**：任务目标、允许使用的工具、输出格式写清楚。子 Agent 启动后拥有自己的 session 文件，工具调用和中间输出都记在那边，不进主会话历史。
2. **约定返回物**：只回传一段有长度上限的结构化摘要（结论 + 关键路径 + 异常），而不是逐条工具日志。
3. **大数据走文件交接**：子 Agent 把完整结果写到工作区约定路径，主会话只拿路径和摘要，需要时再按需读片段。
4. **验证隔离**：跑一个会大量调工具的子任务，然后让主会话模型复述"刚才发生了什么"。它应该只知道摘要，说不出工具日志细节——说得出，说明隔离没生效。

## 踩坑点

- **摘要太长等于没隔离**。给返回物设硬上限，超了让子 Agent 自己先压缩一轮再交。
- **子 Agent 写 memory 要收权**。探索型任务建议禁写，或写到隔离 namespace，人工确认后再合并进主 memory。
- **MCP server 是进程级的**。多个 Agent 共享连接时状态互相可见，有副作用的工具（写库、发消息）要在派发阶段就收走。
- **别让子 Agent 继承完整主会话历史当输入**。那等于把污染反向做了一遍，按需注入最小上下文即可。

## 可复用建议

把子 Agent 当**纯函数**设计：输入是任务描述 + 最小上下文，输出是约定格式的摘要 + 明确列出的文件产物，副作用全部显式化。这样隔离就不只是框架给的机制，也是你任务结构自带的质量。

## 总结

session 隔离不是一个开关，而是"独立 session + 受限返回 + 文件交接 + 显式副作用"的组合。框架保证机制，任务设计保证效果。跑通一次验证流程后，就能放心把脏活累活丢给子 Agent，主会话保持干净轻量。
