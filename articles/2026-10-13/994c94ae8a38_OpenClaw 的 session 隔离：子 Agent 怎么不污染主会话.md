## 背景

OpenClaw 里每个 agent 的会话是一条持续追加的 JSONL：系统提示、频道消息、工具调用和结果全部堆在同一个上下文里。主会话是"长期记忆 + 当前对话"的混合体，越用越重。子 Agent 的定位是干脏活——批量检索、跑测试、整理文件，这类任务工具输出大、中间状态多，天然不适合和主对话混在一起。

## 问题

不做隔离时，典型症状有三个：

1. **上下文膨胀**。子任务的工具结果直接灌进主会话，很快触发 compaction，关键指令和用户偏好被挤掉。
2. **交错污染**。两个任务并行时，A 任务的中间产物混进 B 任务的推理，agent 自己都分不清哪句话属于哪件事。
3. **残留干扰**。任务结束后，那些只对当时有用的上下文永远留在会话里，后续对话一直背着包袱。

## 做法

核心机制是 `sessions_spawn`：派生一个拥有独立 sessionId 的子会话，主 agent 只拿回一条摘要。实际用下来，我把它整理成几条约束：

1. **窄进**。taskPrompt 必须自带完成任务所需的一切：文件路径、约束条件、期望的输出格式。子 Agent 看不到主会话历史，别指望它"自己去找"。
2. **窄出**。要求子 Agent 回传结构化摘要：结论、产物路径、遗留问题三段式。原始工具输出不要回传，让它落到文件里。
3. **交接靠文件系统，不靠会话消息**。给每个子任务划独立目录（如 `runs/<taskId>/`），主 Agent 需要细节时按路径去读，而不是让子 Agent 把全部内容贴回来。
4. **投递目标收口**。明确子 Agent 不要直接向频道发消息，结果统一回主 Agent，由主会话决定要不要、怎么呈现给用户，否则容易出现重复回复。
5. **异步心智**。spawn 返回是"已受理"，不是"已完成"。把它当任务编排，等回传消息再继续，别在 spawn 之后立刻假设结果可用。

## 踩坑点

- 任务描述写太简，子 Agent 无历史可查，只能瞎猜路径，产出一堆废件。
- 子 Agent 和主会话同时写同一个文件，谁后写谁生效，竞争没有任何告警。约定"路径所有权"能避免大半问题。
- 回传摘要里塞大段原文，主会话照样膨胀——隔离的意义就没了。
- 长期跑下来 `~/.openclaw/agents/<id>/sessions/` 下子会话文件持续堆积，建议偶尔用 `sessions_list` 审计清理，别等磁盘报警。

## 可复用建议

- 把"上下文边界"当接口设计：spawn 的输入输出就是接口契约，字段写清楚。
- 需要用户实时介入的任务留在主会话，子 Agent 只接能独立闭环的事。
- 养成习惯：每个子任务 = 一个目录 + 一份摘要 + 一次清理。
- 主会话定期 `/new`，长期记忆放 AGENTS.md 和记忆文件，不放对话流。

## 总结

session 隔离不是开个 spawn 就完事，本质是三件事：**主会话保持轻、子会话用完即弃、交接靠摘要加文件**。把这三条守住，多任务并行的 OpenClaw 才不会越用越糊。
