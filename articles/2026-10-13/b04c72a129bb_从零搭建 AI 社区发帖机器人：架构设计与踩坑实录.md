## 背景

我们社区需要每天发一条「今日精选」：从 issue 和讨论区里挑出高价值内容，整理成一条帖子。人肉做了一周，问题很明显——选材靠记忆、格式靠手感、经常忘记发。于是决定用 OpenClaw 搭一个发帖机器人，但目标很克制：**不是全自动营销号**，而是"机器起草、人审核、定时发布"的半自动流水线。

## 架构

核心分四层：

1. **触发层**：gateway 的 cron 任务，每天 09:00 触发一次。
2. **Agent 层**：单 agent，system prompt 里写死选题边界（只覆盖指定话题、语气克制、禁止营销话术）。
3. **工具层**：三个 MCP tool——`fetch_sources`（拉 RSS/API 源）、`save_draft`（写本地 JSON）、`publish_post`（调社区发帖 API）。
4. **状态层**：SQLite 一张表，存内容 hash、发布状态、时间戳，用于去重和幂等。

发布前有一道**人工审核门**：草稿先推到我的 Telegram，回复 `ok` 才真正调用 `publish_post`，2 小时未确认自动丢弃。

## 步骤（可复现的最小路径）

1. 先跑通只读链路：cron → fetch_sources → 输出到日志，确认素材质量。
2. 加草稿生成，强制结构化输出（title/body/tags），落盘到 `drafts/`。
3. 接审核门：草稿推送 + 命令解析。
4. 最后才接 `publish_post`，并携带幂等 key（内容 hash）。

顺序很重要：**先只读、再落盘、后写外部**，每一步稳定一两天再进下一步。

## 踩坑实录

- **cron 时区**：gateway 默认 UTC，第一天帖子 17:00 才发出去。显式配置时区后解决。
- **会话污染**：最初复用同一个 agent session，跑一周后上下文里堆满历史素材，输出质量明显下滑。改成每次 cron 新开 session，问题消失。
- **结构化输出不稳**：模型偶尔在 JSON 前后夹解释文字。改用 tool call 的结构化参数，而不是在 prompt 里"请输出 JSON"，稳定得多。
- **重复发布**：网络超时后重试，帖子发了两条——第一次其实成功了。加入内容 hash 幂等 key，发布前先查库。
- **审核门死锁**：命令解析最初匹配太宽松，一句"不太行，但标题可以"被当成通过。改成只认单独的 `ok`。
- **限流**：社区 API 连续调用触发 429，加了指数退避和每日调用上限。

## 可复用建议

- 状态必须外置（SQLite/文件），别指望 agent 记住自己发过什么。
- 所有外部写操作都设计成幂等的，超时重试是常态不是异常。
- 权限分离：草稿 agent 可以读一切，`publish_post` 单独授权，最好做成独立 skill 按需启用。
- 全程落日志，出问题靠日志回放，不靠猜。
- 先人工审核跑两周，误报率稳定后再考虑逐步放权。

## 总结

这个机器人没用任何"高级技巧"，架构核心就是：**cron 触发、工具收窄、状态外置、人审兜底**。上线三周发了 20 条，零事故、零重复。体会最深的一点：自动化的坑往往不在模型能力，而在状态管理和边界设计——把这两块做扎实，剩下的都是体力活。
