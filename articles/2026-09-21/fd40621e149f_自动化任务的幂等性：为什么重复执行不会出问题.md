## 背景

在 OpenClaw 里跑自动化任务的人，迟早会遇到这些场景：定时任务被触发了两次、Webhook 被上游重发、Agent 调用工具超时后框架自动重试、进程执行到一半崩溃重启。这些都不是异常，而是常态。网络抖动、LLM 响应慢、宿主机重启，任何一环都可能导致同一段逻辑被执行不止一次。

## 问题

如果任务本身不幂等，重复执行就是事故：

- 向群里发了两条一模一样的日报；
- 同一个 issue 被创建了两遍；
- 文件被 append 了两份相同内容；
- 调用付费 API 被扣了两次钱。

最典型的链路是：Agent 调一个"发送消息"的工具，请求实际已到达但响应超时，上层重试，消息就发了两次。第一次执行其实成功了，只是 Agent 不知道。

幂等性的定义很朴素：**同一个操作执行一次和执行 N 次，最终结果一致。** 在自动化系统里重试无法避免，所以真正的问题不是"如何避免重复执行"，而是"如何让重复执行无害"。

## 做法

1. **先区分操作类型**。"把状态设置为 X"（set / upsert）天然幂等；"追加一条记录""计数加一""发送消息"天然不幂等。动手前先归类，能改语义的就改语义。
2. **用确定性 ID，不要用随机 UUID**。幂等键必须从触发源派生，而不是在执行时现场生成。比如定时日报用 `daily-report-20250601` 这种"任务名 + 时间片"的格式，重试多少次键都相同；在任务体内 `uuid4()` 等于没做。
3. **落一个执行台账**。一张 SQLite 表或一个 JSON 文件就够：记录 key → 状态/结果。执行前查，成功后写。更稳的是"占位"模式：向带唯一约束的表 INSERT，键冲突就直接跳过，原子性由数据库保证。
4. **先确认，再补执行**。对"超时但可能已到达"的调用，先查询目标侧的实际状态再决定是否重发，而不是盲目重试。这是处理"请求成功但响应丢失"的唯一干净办法。
5. **工具与插件层面**。给 OpenClaw 写工具时，把"是否幂等"写进工具描述，Agent 才能据此决定重试策略；外部 API 若支持幂等键（如支付类接口的 key header），务必透传。

## 踩坑点

- **在任务体内生成 ID**：每次重试都是新键，台账形同虚设。键的生命周期必须覆盖所有可能的重复触发。
- **先记状态、后做副作用**：先写 watermark 再调 API，中间一崩溃，这个任务就永远不会再跑。顺序必须是"执行 → 确认 → 记录"，并且想清楚你接受"至少一次"还是"至多一次"的失败模式。
- **多层各自重试**：框架层重试一次、工具层再退避重试一次，乘起来就是重试风暴。重试策略只保留一层。
- **Agent 重试时重新生成参数**：LLM 可能微调参数导致键变化。键要从稳定输入（触发时间、任务定义）计算，不能依赖 LLM 的输出。
- **时间片键忽略时区**：本地时区和 UTC 差八小时，日报键错位，任务要么漏跑要么双跑。统一用 UTC 生成时间片。

## 可复用建议

- 定时 / Webhook 任务三件套：**确定性 ID + 持久化台账 + 执行前检查**。
- 工具语义尽量设计成 upsert / set，而不是 insert / append。
- 验收方式很简单：手动把同一个任务连跑两遍，断言副作用没有翻倍。过不了这一关，重试真正来临时一定出事。

## 总结

幂等性不是防止重复执行，而是让重复执行变得安全。在 Agent 自动化场景里，重试是确定会发生的，区别只在于你有没有提前设计。一个确定性 ID 加一张台账表，成本很低，却能把"偶发重复"从线上事故降级为日志里的一行 skip 记录。下一次写定时任务时，先问自己一句：这段逻辑跑三次，结果和跑一次一样吗？
