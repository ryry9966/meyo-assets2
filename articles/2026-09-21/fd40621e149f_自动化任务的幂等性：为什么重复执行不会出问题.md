## 背景

写自动化流程的人迟早会撞上一个反直觉的事实：**"只执行一次"是保证不了的**。

在 OpenClaw 这类 Agent / 自动化体系里，重复执行几乎是常态：

- Webhook、消息队列普遍是 at-least-once 语义，网络抖动就会重投递；
- cron 定时任务在上一轮没跑完时可能重叠触发；
- Agent 自己也会重试：模型对某次工具调用结果不确定、调用超时、框架层自动重试，都会让同一个操作被再次执行。

所以问题从来不是"怎么保证只跑一次"，而是"跑两次、三次，结果会不会坏"。这就是幂等性（idempotency）：同一操作执行多次，最终效果与执行一次相同。

## 问题

举一个最常见的翻车场景：一个"读新邮件 → 建工单 → 发回执"的自动化流程，在建完工单、还没标记邮件已处理时崩了。下一轮重跑，同一封邮件又建了一张工单。如果流程中间还有"发通知"这类外部副作用，就是重复骚扰用户。

类似的还有重复扣款、重复写库、重复创建文件、重复触发下游流水线。共同点是：**操作带有不可重复的外部副作用，且没有防重机制**。

## 做法

实践中我按这几层来做，成本从低到高：

1. **先定幂等键（最重要）**。从业务实体里找天然唯一标识，比如"邮件 ID + 动作类型"、"订单号 + 操作名"。幂等键必须来自业务数据，不能来自执行上下文——时间戳、随机数在重试时会变，等于没做。
2. **数据库层兜底**。给幂等键建唯一索引，写入用 `INSERT ... ON CONFLICT DO NOTHING` 或 upsert。这是最后防线，不依赖应用逻辑正确性。
3. **状态机 + 条件更新**。状态流转写成 `UPDATE tasks SET status='done' WHERE id=? AND status='processing'`，检查受影响行数；为 0 说明已被处理，直接返回上次结果。
4. **外部副作用带幂等键**。调支付、通知类 API 优先用官方的 Idempotency-Key 参数；对方不支持时，本地维护一张"操作记录表"：执行前查 key，已存在就返回上次结果。
5. **工具设计层面**。给 MCP 工具 / 插件统一约定：写操作接受调用方传入的 `dedupe_key`，由 workflow 层生成——而不是工具内部自己生成（Agent 重试时内部生成的 key 必然不同）。
6. **写重放测试**。同一输入事件连续跑两遍，断言第二次不产生新副作用、最终状态一致，放进 CI。

## 踩坑点

- **幂等键选错**：用时间戳或随机 UUID 当 key，每次重试都是新 key，防线形同虚设。
- **check-then-act 竞态**：先查"不存在"再写入，两个并发实例同时查到不存在，双双写入。应用层 if 判断挡不住并发，必须靠唯一约束。
- **把"内容相同"当"幂等"**：重发两条一模一样的通知，内容相同但用户收到两次，副作用翻倍。幂等看的是效果，不是内容。
- **内存态去重**：在进程内存里记"已执行"，重试发生在另一个会话 / 进程时完全失效，去重状态必须落库。
- **粒度不清**：三步 workflow 第二步失败，重试时第一步又跑了一遍。要么整条 workflow 幂等，要么每一步各自幂等，设计时明确选一种。

## 可复用建议

- 设计任何自动化步骤前自问一句：**"这个操作再来一次会怎样？"** 答不上来就是隐患。
- 给所有写操作工具统一加 `dedupe_key` 参数，形成团队约定。
- 记录并监控"重复被拦截"的次数——拦截数突然升高，往往说明上游在异常重试。
- 读操作天然幂等，可以放心重试；把不可重试的范围压缩到最小的写路径上。

## 总结

可靠性不来自"保证只执行一次"——分布式环境下这基本做不到——而来自"执行多次也安全"。幂等不是高级技巧，更像是自动化系统的基本卫生习惯：定好幂等键、数据库兜底、副作用带 key、重放测试进 CI。把这四件事做成默认动作，你的 Agent 和自动化流程就能坦然面对重试、超时和重复投递，而不是每次都靠运气。
