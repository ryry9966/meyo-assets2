## 背景

OpenClaw 的 cron 任务本质上是：定时唤醒一个 agent，按 instruction 干活，把结果投递到指定会话。听起来简单，但我最早写的几个定时任务，十次里有三次要么空转（agent 反过来问我要上下文），要么每天的输出格式都对不上。踩了几轮坑才意识到：**给 cron 写 instruction 和在聊天窗口里写 prompt，是两回事**。

## 问题的根源：cron 会话没有上下文

三个执行环境上的关键差异：

1. **隔离会话**：cron 默认在全新会话里跑，看不到你们之前聊过什么，写“按之前说的格式整理”只会换来沉默或瞎猜。
2. **无人值守**：任务跑的时候你多半不在屏幕前，agent 遇到歧义没法追问，只能自行决策。
3. **结果即投递**：输出直接发进聊天渠道，格式失控就是每天一条的消息轰炸。

所以设计目标只有一个：**把所有决策在写指令时就做完，不留需要 agent 临场发挥的空隙**。

## 我的做法：五段式模板

现在每个 cron instruction 都固定包含五块，以一个 HN 日报任务为例：

```
【目标】每天 08:00（Asia/Shanghai）汇总一次 HN 热点。
【来源】用 web_fetch 抓取 HN 官方 API 的 top stories 接口。
【规则】只保留 AI / LLM / Agent 相关条目，最多 5 条，按热度排序。
【输出】每条一行：中文标题 + 一句话摘要（≤40 字）+ 原文链接。
       全文控制在 800 字符以内。
【异常】抓取失败或无符合条目时，只回复"今日抓取失败：<原因>"，
       不要编造内容，不要发旧数据。
```

五个要点展开：

- **时间写死时区**。别依赖服务器默认时区，直接声明 Asia/Shanghai。
- **来源给到具体工具名和接口**，而不是“上网查一下”。工具名写错，第一次试跑就能暴露。
- **规则限定数量和排序**，输出才可对比。“关注行业动态”这种开放式目标，每天产出都不一样。
- **输出给硬约束**。尤其投递到 Telegram 这类有长度限制的渠道，超长会被截断。
- **异常分支必须显式写**。这条最重要：不告诉它“失败时不要编”，它真会编一份看起来很像样的日报发给你。

## 踩坑记录

- **“如上所述”是定时任务的毒药**。cron 会话里没有“如上”。凡是引用过往约定的，全部内联进 instruction。
- **相对时间不可靠**。“昨天的数据”里的“昨天”要 agent 自己算，容易错。改成“过去 24 小时内发布”这类可计算表述。
- **凭证问题导致静默失败**。有一次任务用了需要登录态的抓取工具，交互会话里能用，cron 隔离会话里没凭证，连续三天没产出我才注意到。涉及鉴权的工具，先确认 cron 会话里可用。
- **上线前手动干跑一遍**。把 instruction 原样贴进会话执行一次，能提前暴露工具缺失、格式跑偏的问题。

## 可复用建议

1. 把五段式模板存成 snippet，新任务只填空。
2. 新任务先用 10~15 分钟间隔试跑两三次，确认稳定后再改正式周期。
3. 输出尽量结构化（固定字段顺序），方便后续再写个任务对前一天结果做 diff。
4. 每月审一遍在跑的任务：数据源还有效吗？输出还有人看吗？没人看的定时任务就是噪音制造机。

## 总结

Cron instruction 的本质是**把一次性的对话约定，压缩成一份无人值守时也能独立执行的工单**：上下文自带、时间写死、来源具体、格式限定、异常兜底。五样齐了，定时任务才能从“偶尔灵”变成“天天稳”。
