## 背景

LLM 是无状态的，每次会话都从零开始。做过 Agent 自动化的人都有体会：你明明告诉过它“提交信息不要带 emoji”，三天后它又带上了。上下文窗口再大也只是工作台，不是档案柜。在 OpenClaw 这类长期运行、跨会话服务本地用户的场景里，记忆是绕不开的基础设施，值得认真做一次设计。

## 问题：三种常见做法都不太行

1. **全量塞 system prompt**：把历史对话和偏好全量注入。token 成本线性上涨，且互相矛盾的旧偏好会打架，模型随机听哪个。
2. **简单 RAG**：把聊天记录向量化，检索 top-k。但“语义相似”不等于“与当前任务相关”，召回的大多是噪音。
3. **把记忆当黑盒**：让模型“自己记住”，没有显式写入路径。无法审计，错了删不掉，出问题无从排查。

本质上，记忆是一个**数据建模 + 生命周期管理**问题，不是一个“聪明的检索”问题。

## 做法：三层结构 + 四个环节

**分层：**

- **L1 核心画像**：结构化偏好（语言、时区、代码风格、禁用词），控制在 1~2KB，每次会话必注入。来源明确、数量少。
- **L2 情景/事实库**：一条记忆 = 一个原子事实，本地存文件（JSON/Markdown，每条一个），字段包括 `content`、`type`、`confidence`、`source`、`created_at`、`last_used`、`ttl`。
- **L3 工作记忆**：会话内 scratchpad，会话结束清空或压缩归档。

**落地四步：**

1. **写入**：把记忆做成 MCP 工具（`memory_write` / `memory_search`），由模型显式调用，而不是后台悄悄抓取。写入带来源（哪轮对话、哪次工具输出），高影响条目要求用户确认。
2. **整理**：定期合并去重。冲突不追加、要覆盖——新偏好带时间戳压过旧的，旧版本留档可回滚；长期未用的打衰减标记。
3. **检索**：L1 无条件注入；L2 按相似度 × 时间衰减 × 使用频率打分。几千条以内，本地 BM25 或小型 embedding 模型足够，不必急着上向量库。
4. **遗忘**：TTL 和 `last_used` 驱动清理；提供 `memory ls` / `memory rm` 这类 CLI 入口，让用户能看、能删。

## 踩坑点

- **只存不删**：记忆库变垃圾场，检索精度崩掉。存蒸馏后的事实，别存原始对话。
- **过度自信写入**：用户随口一句玩笑被固化成永久偏好。用 `confidence` 字段兜底，高影响写入必须确认。
- **追加式冲突**：新旧偏好并存导致行为不稳定，必须显式覆盖。
- **记忆回音壁**：注入的记忆影响输出，输出又被提取成相似记忆，自我强化。对“复述已有记忆”的候选去重，不重复计分。
- **记忆投毒**：工具输出里夹带的指令被当成事实写入。记忆内容一律视为不可信输入，用户消息和工具消息分开置信级。
- **静默改写**：让模型直接改画像文件，出问题无从排查。只允许经工具写入，落审计日志。

## 可复用建议

- 先做 L1 纯文件画像，别急着上向量检索。一个 Markdown 文件覆盖 80% 场景，git 可管、肉眼可查，放进 OpenClaw 工作目录即可版本化。
- 记忆单元越小越好，合并、覆盖、删除都简单。
- 写入路径必须显式且可审计，宁可漏记，不可记错。
- 度量两个数：检索命中后**实际被采纳的比例**（反映精度），记忆条目**月增长率**（提醒你该清理了）。

## 总结

好的记忆系统不是“记得多”，而是**记得准、改得动、删得掉**。分层存储、显式写入、有衰减、可审计——把它当普通数据工程做，而不是玄学。建议从今天起把 Agent 的记忆从 system prompt 里搬出来，先建一个画像文件试试，你大概率会发现：不需要多复杂的模型，需要的只是克制的设计。
