## 背景

我们社区有几条自动化流水线：每周精选摘要、Release 通知、RSS 聚合转发，全部由 OpenClaw agent 挂定时任务，通过一个 MCP posting 工具发到论坛和群。技术上很稳，跑了几个月没宕过。但社区反馈很一致：“内容还行，但一看就是机器人。”

拆开看，问题不在内容，在节奏。

## 机器味的四个典型症状

1. **分秒不差**：每天 09:00:00 准时出现，连续三周秒级一致。
2. **突发连发**：任务积压后队列一起放行，两分钟内五条帖子刷掉整个版面。
3. **不看现场**：社区正在热聊一个技术话题，摘要贴硬挤进来；凌晨三点照样发。
4. **零反馈**：某类帖子连续四周零回复零点赞，下周照发。

这些行为不会立刻出事，但会慢慢把频道变成垃圾场，成员折叠、屏蔽，运营价值归零。

## 做法：把节奏做成一层独立策略

核心思路：**所有自动发帖必须经过同一个出口队列，节奏控制做在队列上，而不是各任务自己管**。

1. **统一出口**。写一个 posting MCP tool，内部单线程队列。任何自动化只负责“投递内容 + 优先级”，不直接发。这是后续所有控制的前提。
2. **抖动（jitter）**。目标时间 09:30，实际发送在 ±40 分钟内随机。注意 jitter 要在出队时算，不是调度时算——否则多任务共享同一基准时间，抖完还是扎堆。
3. **硬性最小间隔**。任意两条自动帖之间至少 20~30 分钟，每日总量设上限。这是硬约束，抖动只是软偏好，两者不能混用。
4. **活跃时段**。不要用你自己的时区。从社区消息量热力图反推成员活跃窗口，发送限制在窗口内，深夜直接禁发。
5. **让行与退避**。发送前检查最近 feed：正有高热度讨论、或几分钟内刚有人发帖，就顺延。用优先级队列兜底——安全公告 P0 可以插队，周报 P2 可以等。
6. **反馈闭环**。按内容类别统计互动率，连续 3~4 次（别用 2，容易误杀季节性内容）低于阈值，自动暂停该类别并通知人，而不是无限照发。

## 踩坑点

- **时区**：服务器 UTC，社区 UTC+8，“早九点”实际发在下午五点。社区时区要显式写进配置，不要继承系统时区。
- **补发风暴**：停机恢复后积压队列一次放行，一小时三十条，直接触发平台限流。恢复后要么慢速排水，要么丢弃过期条目，旧摘要补发了也没人看。
- **随机没约束**：纯随机偶尔会两条间隔一分钟。随机必须夹在最小间隔之内。
- **去重失效**：RSS 源轻微改写标题就绕过了 hash 去重，改用归一化标题加相似度阈值。
- **换了模板没换签名**：结构在变，页脚永远一样。机器人身份应该公开透明，我们要消除的是“行为上的机械”，不是身份本身。

## 可复用建议

- **策略配置化**：窗口、上限、静默时段、优先级全放 YAML，代码里不出现任何具体时间。
- **先跑一周 dry-run**：只记录“本应何时发什么”，人工 review 节奏曲线再放开。
- **决策可观测**：为什么延迟、为什么丢弃，全部落日志。节奏问题只能靠审计发现，靠感觉调不好。

## 总结

“不像机器人”不是把随机数调大，而是三件事：**一个统一出口 + 一份反映社区作息的节奏策略 + 一个会停下来的反馈闭环**。自动化做得好不好，成员不一定说得出原因，但他们一定会用折叠和屏蔽投票。
