## 背景

OpenClaw 的 cron 任务，本质是"定时触发的隔离 agent 会话"：到点执行你写的那段 instruction，跑完把结果投递出去。它和交互式对话最大的区别是——**没有上下文、没有追问机会、没人盯着**。很多人把平时聊天的写法直接粘进 cron，配置时看着正常，跑偏了要等到第二天早上才发现。

## 问题

我最早踩的三个坑，大概率你也会遇到：

1. instruction 里写"按之前讨论的格式整理"——但 cron 会话是隔离的，agent 根本看不到"之前"。
2. 写"每天早上 9 点发日报"，没注意服务器时区，实际在下午触发。
3. 让 agent"查一下最新动态然后发给我"，没限定来源和时间窗，有一次它"补"了几条并不存在的新闻。

## 做法

后来我把 cron instruction 固化成一个结构，稳定性明显提升：

1. **祈使句 + 单一任务**。一条 instruction 只做一件事，删掉所有"顺便再看看"。
2. **自包含上下文**。目标、范围、关键词全部写进 instruction 本身，不引用任何历史对话。
3. **显式时间与窗口**。不写"今天""最近"，写"过去 24 小时（Asia/Shanghai）"。
4. **指定数据来源与工具**。明确用哪个 skill / MCP 工具取数，不留"自行判断"的空间。
5. **定义输出格式**。给模板或字段清单，限定长度；要投递到 IM 的，要求先压缩成几行。
6. **写失败分支**。明确"如果获取失败或结果为空，如实说明原因，禁止编造"。这条对无人值守任务最重要。
7. **投递单一出口**。结果送到哪，用 cron 自身的投递配置；instruction 里不要再让 agent"发消息"，否则容易双发。

我实际在用的骨架：

```
任务：<一句话目标>
时间窗：<过去 N 小时，时区>
数据来源：<工具/skill，取不到怎么办>
输出：<字段模板，长度上限>
失败处理：<为空或出错时的行为>
```

## 踩坑点

- 要求输出 JSON 却没给字段清单和示例，下游脚本隔三差五解析失败。
- 任务耗时变长后与下一次触发重叠，产生重复通知；要么拉长间隔，要么在 instruction 里要求幂等（同一窗口内数据不重复提交）。
- instruction 塞了太多"可能用到"的工具说明，反而稀释主任务。改动频繁的参数（关键词、频道名）放最上面，方便维护。
- 新任务先手动触发一次验证，再启用定时。别让它的第一次执行发生在凌晨三点。

## 可复用建议

- 把 cron instruction 当配置代码：进仓库、留变更记录，出问题能 diff。
- 上线前过一遍 checklist：自包含？时区明确？来源指定？格式固定？失败分支写了？投递只有一个出口？
- 定期 review 长期任务。数据源和上游接口会变，instruction 不会自己变。

## 总结

Cron 的 instruction 不是聊天，是一份写给无人值守执行者的任务说明书，必须被一次读懂。自包含、显式时间、明确格式、定义失败——四点做到位，定时任务的可靠性会上一个台阶。剩下的，交给时间（和时间窗）去验证。
