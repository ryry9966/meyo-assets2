# 背景

Agent 跑在本地时，最大的不确定往往不是模型，而是环境。同一份指令，在公司台式机和家里笔记本上表现完全不同：包管理器不一样、路径不一样、有的机器装了 Docker 有的没有。社区里常见的做法是把这些信息塞进系统提示词，或者写死在自动化脚本里——时间一长，就是一场缓慢的灾难。

# 问题

具体表现大家都遇到过：

- Agent 猜路径，猜错了就自己 `mkdir`，工作区里多出一堆垃圾目录；
- 换一台机器，提示词里的 `~/go/bin` 立刻失效；
- 团队共享的 Agent 配置里全是个人路径，别人拉下来跑不通；
- MCP server 配置和实际安装的工具对不上，启动即报错。

本质只有一个：**环境知识没有独立载体**，散落在提示词、脚本、README 和人的脑子里。

# 做法

我们的方案是在项目根目录维护一个 `tools.md`，核心原则：**只描述事实，不下指令**。

建议分六节，不用花哨：

- **runtime**：node/python/go 版本、包管理器（这台机器用 pnpm，不是 npm）；
- **paths**：工作区、数据目录、日志位置；
- **tools**：docker、ffmpeg、本地脚本及调用方式；
- **mcp**：当前启用的 server、启动命令、已知报错；
- **platform**：Windows 下用哪个 shell、哪些命令不可用；
- **notes**：杂项与例外。

分层管理是关键：

- `tools.md`（入库）：团队共性、项目约定；
- `tools.local.md`（gitignore）：个人路径与偏好；
- Agent 启动时先读前者，local 存在则覆盖合并。

写法上，一行一条事实，例如「本机 python 由 pyenv 管理，用 `pyenv which python` 确认」——指向验证方式，而非绝对断言。全文控制在 50 行以内，因为它要进 context。

再加一条自愈机制：指令里写明「若发现 tools.md 与现实不符，修正对应行并在末尾注明日期」。让文档跟着机器一起活着。

# 踩坑点

1. **把 secret 写进 tools.md**。它会被读进上下文、可能进日志。只写「token 存在 keychain，用某命令读取」。
2. **文档腐烂**。过期的 tools.md 比没有更糟，因为 Agent 会信。环境一变就顺手改一行。
3. **覆盖规则不明**。local 与 shared 冲突时 Agent 会自己挑一个听，优先级必须写死。
4. **写成操作手册**。tools.md 是地图不是教程，长篇大论浪费 context 还稀释关键信息。
5. **替代运行时验证**。路径存不存在，`ls` 一下就知道，文档只是加速器，不是真相源。

# 可复用建议

- 固定六节模板，新机器 10 分钟能填完，别追求一次完美；
- 配一个 `check-tools` 脚本，核对文档中的路径与版本是否仍有效，CI 里可选执行；
- Agent 每犯一次环境相关的错，问一句：这个信息能否落进 tools.md？能就落，同类错误不犯第二次；
- 团队内 tools.md 的 diff review 与代码同等对待。

# 总结

tools.md 解决的不是技术问题，而是知识归属问题：把「这台机器的事实」从提示词和人脑里拿出来，变成版本化、可合并、可自愈的一等公民。成本极低，收益是 Agent 在任何一台机器上都能少猜几次、少错几次。先从一个只有五行的文件开始，比设计一个完美的方案更重要。
