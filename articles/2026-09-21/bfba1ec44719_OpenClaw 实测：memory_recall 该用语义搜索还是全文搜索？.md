# 背景

OpenClaw 的记忆层本质上就是一堆 Markdown：`MEMORY.md` 放长期事实，`memory/*.md` 放每日流水。agent 每轮对话不可能把全部记忆塞进上下文，只能靠 `memory_recall` 按查询捞出最相关的几条。捞得准不准，直接决定 agent 是"记得住事的同事"，还是每次都要你重新交代的实习生。

# 问题

`memory_recall` 底层有两条路线：全文检索（关键词/BM25/FTS）和语义检索（embedding 向量 + 相似度），配好 embedding provider 后还能开混合。我的记忆库一半是中文口语笔记，一半是命令行片段（报错码、参数、路径）。默认单引擎时经常两类翻车：查"上次证书过期怎么处理的"没结果，但记忆里明明写过；查 `rsync -avz` 这种精确串倒是能命中。于是决定做次小规模实测，而不是猜。

# 做法

1. 从近三个月的会话日志里挑 15 个真实 recall 问题组成评测集：一半中文口语描述，一半含精确标识符。
2. 先切全文模式，逐条跑评测，人工核对 top-5 是否包含期望条目，算命中率。
3. 切换到语义模式（同一套 embedding 配置），重跑同一份评测集。
4. 开混合模式再跑一次，观察融合结果是否稳定优于单引擎。
5. 结论落到配置：默认混合，评测集留在仓库里，以后改配置就重跑。

结果：口语化中文提问，语义命中率明显更高；精确标识符（报错码、命令参数）全文接近全中，语义反而因"长得不像"而漏。混合模式是唯一在两个子集上都不翻车的选项。

# 踩坑点

- **中文分词**：全文索引对无空格的中文不友好，长句查询可能整句零命中、单关键词反而正常。遇到"明明写过了却搜不到"，先怀疑分词。
- **索引滞后**：agent 写完 memory 文件后索引没刷新，会出现"刚记完就想不起来"。要么写后触发重建，要么定时任务兜底。
- **换 embedding 模型必须重建索引**：维度不一致会静默退化成无效检索，而不是报错，很难第一时间发现。
- **混合不是万能**：如果其中一路（比如分词坏了）在产出噪声，融合分数会被拖累。先单独验证两路都健康，再开混合。
- **top-k 别贪多**：5 条左右够用，捞太多等于把垃圾塞回上下文。

# 可复用建议

- 别凭感觉选引擎。15 条真实问题的小评测集，半小时能建，长期受用。
- 写记忆时兼顾两种检索：同一条目里既保留精确的命令串/错误码，也补一句大白话描述。
- 每日笔记控制粒度，一条一个主题，标题即摘要，对两种引擎都友好。
- agent 说"我不记得"时先分诊：记忆文件里到底有没有（写入问题），还是有但搜不到（检索问题），修法完全不同。

# 总结

语义 vs 全文不是二选一：概念类问题靠语义，标识符靠全文，工程上的务实答案基本是**混合检索 + 一个可重跑的评测集**。这套东西值得花半小时搭，因为 agent 的可靠性瓶颈往往不在模型，而在它能不能在正确的时候想起正确的事。
