## 背景

日常开发里不少 git 操作是纯机械的：写提交信息、建分支切分支、合并后删分支、偶尔 cherry-pick。这些事不费脑子，但容易做得潦草——message 语焉不详、忘了自己在哪个分支、合并后留一堆没清理的分支。在 OpenClaw 的 agent 拿到 shell 和 MCP 工具调用能力之后，我试着把这部分交给 AI 助手，跑了几周，稳定下来一套做法，分享给同样在折腾自动化的朋友。

## 问题

直接“让 AI 跑 git”有三个典型风险：

1. 一把梭 `git add -A`，把 `.env`、密钥文件一起提进去；
2. 提交信息写得漂亮，但和实际 diff 对不上；
3. 碰到 main 这类共享分支，或者 force push，翻车后很难恢复。

所以方案的核心不是“AI 能做多少”，而是“它被允许做什么”要先画清楚。

## 做法

**第一步：工具层收权。** 不给 agent 裸 shell，用 MCP git 工具或包装脚本，只注册白名单子命令：`status / diff / log / branch / add / commit / stash`。`push --force`、`reset --hard`、`rebase`、`clean` 这类干脆不暴露成工具——物理上做不到，比 prompt 里写一百遍“禁止”都可靠。

**第二步：规则放进仓库。** 仓库根目录放一个约定文件（比如 `AGENT_RULES.md`），内容大致是：只在当前工作分支操作；提交前必须先列出待暂存文件和 diff 摘要；提交信息遵循 Conventional Commits；main 分支只读。agent 的系统提示词只需一句“先读取并遵守 AGENT_RULES.md”。好处是规则随仓库版本化，换一个 agent 实例行为也一致。

**第三步：流程三段式。**

- **查状态**：每次操作前强制跑 `git status`，确认当前分支、脏文件；
- **先提案后执行**：agent 给出“准备提交哪些文件 + message 依据了 diff 里哪些改动”，我确认后才执行；
- **收尾**：合并后让它列出已合并分支、提议删除清单，我点头再删。

决策权始终在我，agent 只负责起草。

## 踩坑点

- **`.env` 差点进库。** 早期它确实试图 `add -A`。后来加了两道保险：规则要求逐文件列出暂存清单，命中敏感模式的文件直接进拒绝列表；pre-commit hook 里再做一次本地扫描兜底。
- **message 和 diff 两张皮。** AI 有时会根据任务描述而非实际改动写出“正确的废话”。现在的规则是：message 必须能从 diff 里指出至少一处对应改动，指不出来就不许提交。
- **detached HEAD 的假正常。** 它曾在 detached 状态下“一切看起来正常”，幸好提交被规则拦住。工具层拦不住的话，至少在提交前做一次当前分支名校验。
- **上下文长了状态会过期。** 聊了很多轮之后，agent 记忆里的 repo 状态是旧的。“每次操作前重新跑 status”这条必须硬性强制，比任何提示词技巧都管用。

## 可复用建议

1. **权限分三档**：默认只读、写操作逐项确认、危险操作不注册工具；
2. **规则文件放仓库里**，跟着仓库走，不跟着会话走；
3. **留审计日志**：把 agent 执行过的每条 git 命令追加到本地文件，出问题回溯不抓瞎；
4. **先 dry-run**：想尝试更激进的工作流（比如自动 rebase），先让它只输出计划执行的命令序列，人审后再放行。

## 总结

AI 管 git 的正确姿势不是全自动，而是“AI 起草、人类签收”。用工具白名单守住底线，用仓库级约定统一行为，剩下的机械操作确实能每天省下十几分钟。更重要的是：这套围栏搭好之后，你才敢让 agent 往更深的自动化里走——否则第一次误删分支就会让你把所有权限收回来。先画围栏，再谈效率。
