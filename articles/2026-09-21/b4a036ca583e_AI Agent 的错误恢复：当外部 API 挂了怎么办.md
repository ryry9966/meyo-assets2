# 背景

跑自动化 Agent 的人迟早会撞上这一幕：流程白天好好的，凌晨三点的定时任务里，某个外部 API 突然 503，整条链路中断——或者更糟，LLM 编了个像模像样的结果继续往下跑。

和人在环的对话场景不同，自动化 Agent 失败时往往没人看着。聊天挂了用户会重试，定时任务挂了只会安静地留一条没人看的日志。所以错误恢复不是锦上添花，而是自动化能否交付的基本盘。

# 问题：三种失败模式

按危害排序：

1. **显式中断**：工具调用抛错，任务终止。烦人，但诚实。
2. **静默劣化**：插件把异常吞掉返回空结果，下游照常执行，产出半残数据。
3. **幻觉补位**：LLM 拿到失败的调用结果后，凭"常识"编了一个合理答案继续走。这是最危险的，因为它看起来完全正常。

第三种在 LLM 驱动的 Agent 里尤其常见，值得单独设防。

# 做法：分层恢复

**第一步，先分类再行动。** 429、5xx、超时、网络抖动属于可重试；401/403、配额耗尽、参数错误属于重试无意义，直接走告警或人审。分类逻辑写进统一的客户端封装，不要散落在各工具里靠 LLM 自行判断。

**第二步，指数退避 + 抖动重试。** 3~5 次封顶，间隔 1s→2s→4s 加随机抖动。抖动很重要：多个定时任务同点触发时，同步重试会形成重试风暴，把刚缓过来的 API 再次打挂。

**第三步，熔断。** 连续失败 N 次后标记该工具"暂时不可用"，冷却期内不再调用，并把这一状态注入 Agent 上下文，让模型明确知道"这条路现在不通"，而不是反复撞墙烧 token。

**第四步，降级要有排序。** 常用顺序：备用数据源 → 带时间戳的陈旧缓存（明确标注数据截至时点）→ 跳过该步骤但把任务标记为"部分完成" → 暂停并通知人。降级可以，但劣化必须可见。

**第五步，把失败显式喂给模型。** 工具失败时返回结构化错误（类型、原因、建议动作），并在系统提示里写死一条：工具调用失败时如实报告，禁止用推测补齐缺失数据。这条提示成本极低，收益极高。

**第六步，写操作先确认幂等。** 超时的 POST 到底成没成功？盲目重试可能重复下单、重复发消息。写操作要么带幂等键，要么重试前先查询状态。

# 踩坑点

- **HTTP 200 不等于成功**：不少 API 用 200 包错误体或空结果，务必做响应 schema 校验，别只看状态码。
- **无限重试烧钱**：每次重试都消耗 LLM token，Agent 陷入"再试一次"循环时，成本比故障本身还高。重试上限和熔断必须硬编码。
- **异常吞没**：插件层一个大 `except: return None`，把可恢复错误变成静默劣化。捕获可以，但要向上传递结构化错误。
- **超时错配**：客户端超时短于 API 的 P99，会把慢请求误判为失败；反过来框架默认超时过长，又会让整条工作流卡死。按上游实际延迟定超时。

# 可复用建议

- 做一个统一的弹性封装层（超时 + 重试 + 熔断 + 日志），MCP 工具和插件都走它，别各写各的 try/except。
- 长任务做检查点，恢复时续跑而不是从头再来。
- 给单次运行设"失败预算"：降级步骤超过阈值就整体中止并标记人工介入，别交付一份半坏的结果。
- 在测试环境里故意杀掉 mock API，验证 Agent 的降级路径真的能走通——失败路径不测，等于没做。

# 总结

错误恢复的目标不是消灭故障，而是让故障的形态**可判定、有边界、可感知**：先分类，再退避重试，触发熔断，诚实地降级，最后绝不给 LLM 用想象力填坑的机会。做到这几点，凌晨三点的定时任务才敢放心让它自己跑。
