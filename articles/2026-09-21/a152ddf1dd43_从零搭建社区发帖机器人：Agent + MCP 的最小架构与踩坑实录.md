## 背景

社区每天产生大量讨论帖，人工整理日报越来越难坚持。我的目标很朴素：让一个机器人每天定时抓取新话题和版本发布信息，生成摘要，发布到指定版块。项目跑了一个多月，期间翻过几次车，这篇把架构取舍和踩坑过程记录下来，供有类似需求的社区成员参考。

## 问题

最初想得简单：写个脚本让 LLM 直接调论坛 API 发帖。实际跑起来暴露三个核心问题：

1. Agent 会"创造性发挥"——编造不存在的链接、拼错话题 ID；
2. 失败重试叠加定时触发，导致一晚上发出三条重复日报；
3. 权限失控：把 token 写进系统提示词后，任何提示注入都可能泄露它。

## 做法

最终收敛为五层最小架构：

1. **触发层**：cron 定时 + webhook 手动触发，任务先写入队列表，避免并发执行。
2. **采集层**：三个 MCP 工具——`fetch_topics`（拉取新话题，返回结构化 JSON）、`fetch_releases`（拉取 git tag）、`search_history`（查历史日报防重）。
3. **编排层**：Agent 只负责汇总与排版，系统提示明确禁止生成 URL，链接一律从工具返回值透传。
4. **审核层**：规则前置（长度限制、黑名单词、链接白名单）+ dry-run 模式。上线前两周所有产出只发测试版块，人工确认后才真实发布。
5. **发布层**：`create_post` 是全链路唯一的副作用工具，幂等键为"日期 + 版块"哈希，服务端遇重复键直接返回已有帖子 ID。

状态全部落 SQLite：任务表、发布记录表、工具调用日志表，三张表够用。发布失败走指数退避，最多三次，超限即告警到群。

## 踩坑点

- **幻觉链接**：让模型自由输出 URL 必出事。改为工具只返回 `topic_id`，模板渲染阶段才拼完整链接，问题归零。
- **重复发布**：不是幂等逻辑的 bug，而是 cron 与手动触发同时跑。之后所有触发先在 SQLite 事务里抢锁再执行。
- **凭据放错位置**：起初鉴权信息写在 Agent 提示里，重构后移到 MCP server 进程的环境变量。原则是：Agent 只见工具，不见凭据。
- **内容跑飞**：有一次上下文混入了群聊闲聊记录，日报里冒出一句不该有的话。解法是采集层做输入隔离，让无关数据根本不进上下文，而不是指望模型自己把关。
- **循环失控**：早期没限制迭代次数，一次工具报错后 Agent 反复重试了 40 轮。现在硬编码 max_iterations = 5。

## 可复用建议

1. 副作用工具越少越好，最好只有一个，且全部走幂等键；
2. 所有"发布"动作先 dry-run 落库可审，真人放行，稳定两周后再放开；
3. 凭据永远留在工具服务端，绝不进提示词；
4. 模型只做生成，不做事实——ID、URL、时间戳一律由代码注入；
5. SQLite 足够，别一上来就上消息队列和容器编排。

## 总结

整个项目代码不到 500 行，Agent 的真正价值只体现在"汇总与排版"这一层，其余可靠性全部来自工程约束。结论朴素但有效：把模型当成不可靠的生成器来设计系统，而不是当成可靠的执行者。下一步计划把审核层从全量人工改为规则 + 抽检，进一步降低维护成本。欢迎在评论区交流你们的自动化实践。
