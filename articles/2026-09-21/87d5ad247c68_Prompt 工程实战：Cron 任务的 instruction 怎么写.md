## 背景

OpenClaw 的 cron 任务本质上是「无人值守的对话」：到点之后，gateway 把 instruction 作为一条消息喂给 agent，agent 执行完把结果发到指定 channel。它和交互式聊天最大的区别是——**用户不在场**。没有追问的机会，也没有上下文补全，instruction 写得好不好，直接决定这条自动化是省心还是惊吓。

## 问题

我最早的几条 job 都是这么写的：「每天早上帮我总结一下 GitHub 通知」。一周内踩遍了所有坑：

- agent 反问「你想看哪个仓库？」，凌晨七点在频道里等我回复；
- 数据源为空时，它硬编了几条「通知」凑数；
- 输出长度不稳定，有时三行，有时刷屏一整页；
- 「昨天」到底是哪天，它和我的理解不一致。

这些问题最后都在 instruction 层面修掉了，没动一行代码。

## 做法

核心思路一句话：**把 cron instruction 当成交接文档来写，而不是聊天消息。** 想象接班的是一位刚睡醒、失忆但很能干的同事，你要在几句话里让他把事办对。建议每条 job 按五段式骨架写：

1. **背景一句**：任务是干什么的、发给谁看，帮 agent 校准语气和详略；
2. **输入来源**：明确指定用哪个 skill/工具、读哪个文件，不写「看看最近的情况」这类模糊指代；
3. **执行步骤**：有顺序依赖就编号列出；需要落盘的状态（如「追加到 log.md」）在这里写明；
4. **输出契约**：发到哪个 channel、几条要点、是否带日期标题、上限几行；
5. **失败分支**：工具报错或数据为空时怎么办——发一句简短说明即可，禁止编造补位。

一个可复制的最小模板：

```
任务：每日站会摘要，发送到 #dev 频道。
输入：用 github 工具拉取过去 24 小时的 PR 与 issue；
     时间基准从系统时间获取。
步骤：拉取 → 按仓库分组 → 每仓库最多 2 条要点。
输出：以"YYYY-MM-DD 日报"开头，总计不超过 10 行。
失败：若无数据或工具报错，仅发送"今日无更新/<原因>"，
     不要推测或编造任何条目。
禁止：不要提问，不要等待确认，一次运行内完成。
```

## 踩坑点

- **对话式措辞**：「帮我看看…」「你觉得…」会诱发反问。cron 场景一律用祈使句，并显式写「禁止提问」；
- **相对时间没锚点**：agent 每次都是冷启动，「昨天」没用，必须让它从系统时间换算，或直接注入日期；
- **没写失败分支**：agent 有很强的「把空结果圆过去」倾向，不禁止编造就一定会编造；
- **状态依赖记忆**：想让 job 知道「上次跑到哪」，必须落盘成文件并在输入段指明读取，session 记忆不可靠；
- **高频 job 忽略成本**：15 分钟一次的任务，instruction 里每个废字都会乘以 96，高频任务要更克制。

## 可复用建议

- 新建 job 先手动触发一次，验证输出契约符合预期，再挂时间表；
- 把五段式存成 snippet，所有 cron job 从模板改起，不要从零写；
- 输出契约越死板越好——「稳定且无聊」是无人值守输出的最高评价。

## 总结

Cron instruction 的质量上限，取决于你把它当「给同事的交接文档」还是「给助手的随口一提」。用户不在场时，prompt 就是全部上下文：写清输入、锁死输出、备好失败分支，自动化才算真的自动。
