## 背景

Agent 拿到 shell 和文件工具后，最怕的不是它写错代码，而是它"自信地"执行了一条破坏性命令。模型对路径的理解是概率性的：相对路径、符号链接、`~` 展开，任何一环都可能被它搞混。社区早期出现过 Agent 把递归删除的目标写到工作区之外的案例，这也是 OpenClaw 后来把 sandbox 做成默认开启、而不是可选插件的原因。

## 问题：单层拦截为什么不够

只靠 prompt 约束（"请不要删除文件"）靠不住；只在 shell 层拦 `rm` 也会被绕过——`find -delete`、`mv` 到回收路径、脚本间接调用，都能绕开关键词匹配。OpenClaw 的思路是把安全从"拦命令"前移到"管路径"，再做多层兜底。

## OpenClaw 的四层做法

1. **工作区边界**：所有文件工具调用前，路径先做规范化（解析 symlink、折叠 `..`），再校验是否落在 `workspace_root` 内。越界直接拒绝，不进入模型重试循环。
2. **工具级权限**：read 默认放行；write/move/delete 在 sandbox 配置里单独声明。delete 实际执行的是"移入 workspace 内 `.trash/` 并记录元数据"，保留期可恢复。
3. **shell 命令分析**：对即将执行的命令做解析，识别破坏性模式——递归删除、批量移动、重定向覆盖、管道进 `sh`。命中即阻断或升级为人工确认，而不是只做关键词黑名单。
4. **确认与审计**：越界或高危操作触发 confirm 事件，默认在终端/IM 里等待人工批复；所有拦截记录写入审计日志。

配置示例：

```yaml
sandbox:
  workspace_root: ~/projects/demo
  confirm:
    - shell:destructive
    - fs:delete_outside_trash
  trash:
    retain_days: 7
```

## 踩坑点

- **把 workspace_root 设成 `~` 或 `/`**：等于没设边界。根目录越小越安全，建议一个项目一个 workspace。
- **符号链接逃逸**：workspace 内指向外部的软链会在规范化后被判定越界，这是特性不是 bug；确需共享目录，用 `allowed_paths` 显式声明。
- **Agent 用 `cd` + 相对路径**：命令本身无害，但工作目录漂移后路径校验的语义就变了。确保执行器在固定 cwd 下起子进程，而不是继承 Agent 的"心理目录"。
- **`git clean -fd` 这类命令**：合法、不带 `rm` 字样，早期版本会放行，现在已归入 destructive 确认项。自建插件时别忘把它加进自己的确认清单。
- **别为了一个报错放宽白名单**：先看审计日志里到底拦了什么，多数"误拦"其实是路径配置问题。

## 可复用建议

- 沙箱按"默认拒绝 + 显式放行"配置，不要按"默认放行 + 拉黑"。
- 删除永远走 trash + 元数据，恢复成本远低于从备份重建。
- 在 CI/自动化里开 dry-run，把本会触发的确认事件先打出来人工过一遍。
- 审计日志接通知渠道，拦截事件当天看，别攒着。

## 总结

OpenClaw 之所以少见"Agent 误删文件"，不是因为模型变聪明了，而是因为最坏情况被工程手段限制在了 `.trash/` 里。路径边界、工具权限、命令分析、人工确认，四层各管一段，任何一层失守都有下一层兜底。对做 Agent 自动化的人来说，这套分层思路比任何单个开关都值得复用。
