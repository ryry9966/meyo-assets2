## 背景

在 OpenClaw 里，cron 任务的本质是：到点把一个 agent 从零唤醒，塞给它一段 instruction，让它自己跑完再睡回去。它没有你白天聊天攒下的上下文，输出大概率也没人盯着。所以 cron instruction 的写法，和随手写一条日常 prompt 完全是两回事。

我的经验是：把它当成给夜班同事的交接文档来写，而不是给自己看的备忘录。

## 问题：几种典型的失败

早期我写过的指令大概长这样：

> 每天早上看一下 GitHub 通知，整理好发给我。

跑起来之后依次遇到了这些问题：

- agent 不确定“看一下”该用哪个工具、哪个数据源，于是自由发挥；
- 没有新通知时，它硬凑了几条旧内容发过来；
- 半夜排程跑挂了，没有任何报错，我两天后才发现；
- 它顺手“帮忙”标记了已读，导致我真正想看的通知被吞掉。

## 做法：instruction 里写死五件事

现在每个 cron instruction 固定包含五段：

```text
每天 08:30（Asia/Shanghai）执行一次：
1. 目标：汇总我 GitHub 账号的未读通知。
2. 来源：只通过 GitHub MCP 的 notifications 接口读取。
3. 边界：只读，不标记已读、不回复 issue、不发评论。
4. 输出：按 repo 分组、过滤机器人账号，压缩成不超过 10 条
   的摘要，发到我的 Telegram 会话。
5. 异常：unread 为 0 时直接结束，不发消息；接口报错时发一条
   一句话的失败通知，重试不超过 1 次。
```

对比旧版本，差别在于把所有“隐式共识”显式化——定时任务没有共识可依赖，没写的部分就是随机行为。

## 踩坑点

- **相对时间词慎用。**“昨天”在 00:10 和 23:50 跑出来不是一回事。建议写“过去 24 小时”或明确日期边界，并写死时区。
- **空结果分支必须写。**不写“没有新内容就静默结束”，agent 倾向于产出点什么来“完成”任务，这是最常见的输出污染来源。
- **频率先低后高。**每次唤醒都带完整的 system prompt 和工具定义，5 分钟一次的任务先算算 token 账，从日频观察一周再加密。
- **一个任务一件事。**“汇总通知并顺手检查 CI”这类杂烩指令往往两件都做不好，拆成两个 cron 也更好排障。
- **改完指令先手动触发一次。**OpenClaw 支持对任务立即执行，先跑一遍看日志，别让第一次验证发生在凌晨三点的真实排程上。

## 可复用建议

- 把五段结构（目标 / 来源 / 边界 / 输出 / 异常）存成模板，新建任务照着填空；
- 涉及发送动作的任务，默认在指令里收紧为只读，稳定运行后再逐步放权；
- 给每个任务写一句人话描述，保证一个月后回来你能看懂它在干嘛；
- 周期性回头审计：跑了两周没出过问题的任务，通常也值得精简一遍指令。

## 总结

Cron instruction 的质量不取决于文采，取决于你是否把冷启动的 agent 当成一个不知情的值班员来交接：目标、来源、边界、输出去向、异常分支，一件都不能少。写完之后问自己一句——如果半夜三点一个陌生人只拿到这段话，他会做错吗？不会，这个任务就算写合格了。
