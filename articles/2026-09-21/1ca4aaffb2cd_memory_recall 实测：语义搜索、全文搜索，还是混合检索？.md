## 背景

OpenClaw 的 memory_recall 负责在每轮对话前把相关历史记忆捞回来塞进上下文。它好不好用，直接决定 agent 是「记得上周排查过这个问题」，还是每次都从零开始。我给自己的工作助手配了记忆库（会话摘要 + 手动笔记，约 3000 条），最初只开了语义检索，用了一个月后召回质量忽好忽坏，于是做了一次对比实验。

## 问题

只开语义检索时暴露了两类失败：

1. **精确标识符查不到。** 想找回当时处理 `ECONNRESET` 重试策略的记录，语义搜索返回的全是「网络异常的一般讨论」——错误码这类 token 在 embedding 空间里几乎没有区分度。
2. **相似但不对。** 查「上次部署超时怎么解决的」，召回的却是两条不相关的发布记录，只是措辞像。

反过来，纯全文搜索（FTS5 / BM25）能精准命中 `ECONNRESET`，但换个说法就丢：「部署卡住了」搜不到写着「部署超时」的条目。

## 做法

三步走：

**1. 建评测集。** 从真实会话里挑 30 条查询，人工标注期望命中的记忆条目 ID。别用编造的用例，编的你测不出问题。

**2. 分别跑基线。** 同一批查询分别过向量余弦（本地 bge-small-zh）和 FTS5 BM25，记录 hit@5。结果：语义 21/30，全文 17/30，但两者命中的条目重合只有约六成——失败案例几乎互补，这基本宣告了该上混合。

**3. RRF 融合。** 两路各取 top10，用倒数排名融合：`score = Σ 1/(60 + rank)`，取融合后 top5。不需要做分数归一化——余弦分和 BM25 分数量纲完全不同，硬加权归一反而难调。改造后 hit@5 到 27/30。

另外在融合前先按元数据过滤：时间窗（默认近 90 天，可显式放宽）、来源标签（笔记 / 会话 / 工单）。

## 踩坑点

- **中文分词。** FTS5 默认的 unicode61 分词器把中文按整段处理，等于只能整句匹配。解法是换 trigram tokenizer，或者入库前先 jieba 分词存一列，二选一，后者可控性更好。
- **召回 ≠ 被使用。** 评测不能只看检索分数，要打日志记录「召回的 chunk 是否真的被模型引用」。我一度因为某次调参检索分涨了很开心，后来发现 agent 根本没用那几条，属于自欺。
- **旧记忆刷屏。** 不加时间衰减，老条目会反复霸榜；加一个随时间递减的权重因子后明显改善。
- **换模型必须重跑评测。** embedding 模型一换，全库向量要重建，评测结果整体漂移。30 条用例重跑只要几分钟，值得。

## 可复用建议

- 默认上混合检索。记忆库以对话型内容为主，语义那路权重可以高些；如果代码、ID、错误码占比高，FTS 那路别省。
- RRF 是工程上最省心的融合方式，先别碰学习型排序，调参成本不匹配收益。
- 评测集跟着记忆库一起养，每两周补几条新查询，防止指标老化。

## 总结

语义搜索和全文搜索不是二选一，而是失败模式互补的两路信号。对 memory_recall 这种「错一次就浪费一轮对话」的环节，混合检索 + 元数据过滤 + 持续评测，是我目前测下来投入产出比最高的组合。欢迎大家贴自己的召回失败案例，一起攒评测集。
