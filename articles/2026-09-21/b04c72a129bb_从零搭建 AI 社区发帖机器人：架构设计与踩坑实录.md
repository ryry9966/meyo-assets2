## 背景

社区运营里有类活儿重复度极高：每周整理精华帖、跟踪值得关注的 issue、把信息源更新压缩成一条摘要帖。这类工作不适合人肉，也不适合让 agent 完全自由发挥。我的目标是做一个发帖机器人：定时抓取信息源，生成草稿，经我确认后自动发布到社区。

技术栈就建在 OpenClaw 上：gateway 常驻，agent 负责内容生成，MCP 工具负责发布，cron 负责调度。

## 架构设计

整体分四层，每层职责独立，出问题好定位：

1. **触发层**：OpenClaw cron job，每天固定两次。
2. **内容层**：agent 调用 MCP fetch 工具拉信息源，清洗、去重，生成结构化草稿（JSON，含 title / body / tags）。
3. **审核层**：草稿先落到本地 SQLite，附带去重指纹；我在聊天客户端回复确认，才进入发布队列。
4. **发布层**：一个薄薄的 MCP 插件，只做一件事——把已批准的草稿 POST 到社区 API，记录返回的帖子 ID。

核心原则：**agent 只产草稿，不碰发布按钮；发布工具无逻辑，只执行。**

## 踩坑实录

**坑一：自由文本输出不可靠。** 最初让 agent 直接输出 Markdown 正文，格式时好时坏，社区 API 偶尔 400。改成强制 JSON Schema 输出，发布前本地再校验一遍，问题消失。

**坑二：重试导致重复发帖。** 一次 API 超时，agent 判定失败重跑，结果发了两条一样的帖。解法是幂等键：草稿入库时生成指纹（信息源 ID + 日期哈希），发布前先查库，存在即跳过。现在"宁可不发，不可重发"写死在工具逻辑里。

**坑三：限流。** 发布频率上来后连续吃 429。加了两层防护：全局发送间隔 + 429 时指数退避，退避状态存 SQLite，重启不丢。

**坑四：长帖摘要爆上下文。** 源帖几百层楼，直接塞 prompt 又贵又差。改为 fetch 工具先做楼层截断和关键回复抽取，agent 只看压缩后的文本。

**坑五：时区。** cron 默认 UTC，我想要的"早上八点"实际落在下午。OpenClaw 的 cron 支持指定时区，配置里显式写上，别靠猜。

## 可复用建议

- 发布工具越薄越好，所有判断放在内容层；
- 默认 dry-run，审核通过才真发，上线头两周人工兜底；
- 所有发布动作记日志（入参、返回、时间戳），排障全靠它；
- 幂等键 + 状态持久化，比"提醒自己小心"可靠得多；
- agent 输出一律结构化，自由文本只给人看。

## 总结

机器人跑了一个多月，发了四十多帖，手动撤回 3 次，零事故。最大的体会：工程价值不在 agent 有多聪明，而在流程里那些"无聊"的设计——审核门、幂等、退避、日志。发帖是低容错场景，宁可慢一点，也要每一步可确认、可回滚。代码不复杂，复杂的是把"让它发"变成"让它稳当地发"。欢迎在评论区交流你的自动化实践。
