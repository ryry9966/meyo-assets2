## 背景

社区每天都会产生值得沉淀的内容：新版本发布、高频问题、不错的实践帖。人工整理精华和写周报，一周大概要花三四个小时。于是我基于 OpenClaw 搭了一个发帖机器人，目标很明确：不是全自动刷帖，而是「每天生成若干候选草稿，人工花三十秒审核后发布」。跑了一个多月，把架构和踩的坑记录一下。

## 问题

拆开看，这个需求有四个硬约束：

1. **有副作用**：帖子发出去删改都有成本，不能让模型自由发挥；
2. **要持续**：素材每天变，prompt 会漂移，文风必须稳；
3. **有纪律**：频率、去重、内容安全都需要硬性闸门；
4. **可回放**：出了问题要能定位是哪次生成、哪个 prompt 版本干的。

## 架构设计

最终落地成一条五层流水线：

- **触发层**：cron 每天上午跑一次，抓取素材（release notes、社区热帖、issue 列表），结果落盘缓存；
- **生成层**：agent 读取素材 + 版本化的 prompt 模板 + 3~5 篇精选历史帖做 few-shot，产出草稿；
- **状态层**：SQLite 维护状态机 `draft → pending_review → published / rejected`，每条草稿有唯一 id；
- **审核层**：极简审核脚本列出待审草稿，人工通过才写入发布队列；
- **发布层**：独立小脚本消费队列，封装社区 API，带幂等键和限流。

最关键的一条设计原则：**生成与发布严格分离**。agent 的 MCP 工具里只有「读素材」和「写草稿」，根本没有「发布」这个能力——发布权在人工审核之后的独立脚本手里。

## 踩坑实录

**1. 重试导致重复发帖。** 第一版网络超时后直接重试，同一篇帖子发了两遍。解法：发布请求带唯一幂等键，发布前按内容 hash 查重，状态机里 `published` 是终态，不可重入。

**2. Prompt 漂移。** 两周后草稿越来越「营销腔」。解法：把几篇公认质量好的帖子固化成 few-shot 文件纳入版本管理，改 prompt 走 PR，日志里记录当次使用的版本号。

**3. 定时任务重叠。** 容器里 cron 走 UTC，发帖时间整体漂了八小时；还有一次长任务没跑完，下一轮 cron 又启动，草稿写重。解法：显式设置时区，任务加文件锁。

**4. Token 成本失控。** 最初把最近两百条社区讨论整个塞进上下文，单次生成开销很高。解法：先做粗召回（关键词 + 相似度取 top 10），素材抓取结果缓存复用。

**5. 换个说法重复发帖。** 同一话题上周刚发过，机器人改写后又发一遍。解法：发布前对候选标题和正文做 embedding，与已发帖比对相似度，超阈值一律打回人工。

## 可复用建议

- 上线前先跑一周 shadow 模式：只生成不发布，草稿导出来人工过目；
- 发布做成幂等状态机，任何一步可重入、可回放；
- 权限最小化：不给 agent 删帖、改帖的工具，出事也只是草稿级别；
- 结构化日志：draft_id、prompt 版本、模型、耗时、token 数都记下来；
- 频率上限写死在配置文件里，别让模型自己决定「今天多发几条」。

## 总结

发帖机器人本身不难，难的是把它当成一个有副作用的生产系统对待。幂等、限流、审核门、可观测，缺哪一个都会在某个深夜找上门。目前这条流水线稳定运行六周，人工审核通过率从早期的六成升到九成。下一步计划把审核门降级为「低风险自动发布、高风险人工兜底」，但前提是去重和内容安全的阈值再磨得足够准。
