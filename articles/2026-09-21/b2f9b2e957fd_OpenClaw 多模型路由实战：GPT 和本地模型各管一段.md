## 背景

OpenClaw 的 agent 循环——理解意图、拆解任务、调用 MCP 工具、汇总回复——对模型能力的要求其实并不均匀。规划复杂任务、多轮工具调用需要强模型撑着；而消息分类、日志摘要、定时批量处理这类高频小任务，本地模型完全够用。

很多人装完 OpenClaw 的默认姿势是全部流量走 GPT 这类云端模型。跑两周一看，token 账单不难看，隐私敏感的本地文件内容也全部出了网。反过来全切本地模型，agent 主循环很快就开始翻车。多模型路由要解决的就是这个分配问题。

## 问题

单一模型配置的两个极端各有代价：

- **全走云端**：成本随消息量线性上涨；日记、邮件、本地代码等隐私数据全量上传；高峰期限流时 agent 直接停摆。
- **全走本地**：函数调用格式不稳定，MCP 工具参数乱填；上下文窗口小，长会话历史被截断；agent 卡在重试循环里出不来。

## 做法

核心思路：**按任务类型分层，而不是按"哪个模型最新"来选。**

**第一步：主模型给强云端模型，负责 agent 主循环。** 规划、工具调用、长上下文都交给它。在 `openclaw.json` 里配置（示意，字段以你当前版本文档为准）：

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-5.2",
        "fallbacks": ["anthropic/claude-opus-4-5"],
        "image": "openai/gpt-image-1"
      }
    }
  }
}
```

**第二步：配 fallback 兜底。** 主模型限流或超时自动降级到备用云端模型，保证 agent 不断线。这一步是稳定性下限，别省。

**第三步：本地模型承接外围任务。** 通过 Ollama 或 LM Studio 的 OpenAI 兼容接口把本地模型接入，单独建一个子 agent 绑定它。适合的任务：会话摘要、消息分类打标、翻译、定时报告的初稿生成。这类任务失败成本低、调用量大，是省钱的主战场。

**第四步：给隐私敏感任务单独路由。** 处理本地文件、私人笔记的 agent 固定绑本地模型，数据不出机器，即使能力弱一点也值得。

## 踩坑点

- **本地模型的 function calling 是重灾区。** 不少本地模型工具调用格式时对时错，MCP 工具一多参数就填飞。先只挂一个工具跑通，再逐步加。
- **上下文窗口差距比想象中大。** 本地 32k 和云端 200k 不是一回事，长会话历史别硬塞给本地模型，先做摘要压缩。
- **fallback 会掩盖故障。** 主模型悄悄挂了三天、流量一直走 fallback，账单翻倍才发现。定期看 `openclaw` 日志里的模型命中分布，最好加个简单告警。
- **"本地=快"不成立。** 消费级显卡跑 30B 级模型，延迟可能比云端 API 还高，高频任务先测再切。
- **参数默认值漂移。** 不同模型的温度、默认 system prompt 处理不同，切换后行为可能微妙变化，换完要回归测一遍。

## 可复用建议

1. **先测量再分流。** 抓一周日志，按任务类型统计 token 消耗和成功率，用数据划分界线，别凭感觉。
2. **维护一个 20 条左右的小评测集**，覆盖你最高频的 5 类任务，每次换模型前跑一遍，5 分钟换一个安心。
3. **省钱的优化放在外围，主循环默认用强模型。** agent 循环里本地模型省下的钱，往往抵不上一次工具调用失败的返工成本。
4. **本地模型优先选工具调用支持好的系列**（如 Qwen），纯对话模型不要硬上 agent 场景。

## 总结

多模型路由的价值不在于"同时用了几个模型"，而在于让每类任务落在成本、能力、隐私三者的合理交点上。一个务实的起点：主循环用 GPT 级云端模型加 fallback 兜底，摘要和分类这类高频任务交给本地模型，隐私敏感的任务强制本地。跑稳之后，再用日志数据持续微调分界线。路由是调出来的，不是一次配出来的。
