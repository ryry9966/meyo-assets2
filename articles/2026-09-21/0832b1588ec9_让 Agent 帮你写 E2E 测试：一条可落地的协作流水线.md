## 背景

E2E 测试大概是自动化测试里"性价比最难看"的一层：一条完整用户路径的用例写下来动辄半天，UI 稍微改版，断言就大面积崩。最近两个迭代，我们在内部项目里让 Agent 深度参与了 E2E 用例的**起草**环节，流程跑通后写用例的时间压缩到原来的三分之一左右。这篇帖子记录具体做法和踩过的坑。

## 问题：直接"贴页面要测试"为什么不行

多数人第一次尝试都是同一个姿势：把需求文档丢给模型，让它输出 Playwright 用例。结果通常有三类：

- **选择器靠猜**：模型没见过真实 DOM，生成的 `locator` 一半不存在；
- **用例"看起来对"**：语法正确、结构工整，一跑就红，红得莫名其妙；
- **覆盖不到真实边界**：优惠码过期、重复提交这类业务边界，模型不知道你的系统里有。

根因是同一个：Agent 缺少对真实运行系统的观测能力。

## 做法：观测 → 起草 → 回灌

**第一步，给 Agent 接浏览器。** 通过 Playwright MCP 之类的浏览器工具，让 Agent 真正打开页面、点击、读取 DOM。这是整个流程的分水岭——Agent 从"猜页面"变成"读页面"后，生成用例的有效率从三成左右提升到八成以上。

**第二步，人给意图，Agent 起草。** 不要让它直接写最终用例，先描述用户旅程：

> "用户登录 → 加购两件商品 → 应用满减券 → 支付失败 → 重试成功"

让 Agent 在浏览器里实际走一遍流程，边走边输出用例骨架和断言，人再对着骨架补业务边界。

**第三步，失败回灌，但设上限。** 跑挂的用例把报错、截图、当时的 DOM 片段喂回给 Agent 修复。关键约束：**修复轮次不超过 3 轮**，第三轮还红就转人工。没有这个上限，Agent 会在 flaky 用例上无限"碰运气式重试"。

## 踩坑点

1. **别让 Agent 同时改测试和被测代码。** 它会为了测试通过去"迁就"业务代码，产出假绿。职责必须分开：测试归 Agent 起草，业务代码归人改。
2. **先约定 data-testid，再放 Agent 进来。** Agent 默认爱抓 class 名和 `nth-child`，UI 一改版全军覆没。选择器规范要写进给 Agent 的系统提示里。
3. **测试数据必须隔离。** Agent 起草的用例经常共享同一个测试账号，串数据后表现为"时好时坏"的诡异 flaky，排查成本极高。每个用例独立造数据，跑完清理。
4. **只读流程先行。** 先让 Agent 覆盖浏览、搜索这类只读路径来验证流程可靠性，再放它碰下单、支付等写操作——错误断言在写路径上的代价大得多。

## 可复用建议

- 把 Agent 当"动手快的初级工程师"，自己当 reviewer：体力活它干，边界判断归你；
- 把项目内的选择器规范、常用 fixture 写法沉淀成一份文档，作为 Agent 上下文的一部分，比每次对话临时解释稳定得多；
- 用例文件顶部保留一段结构化的"意图注释"（用户旅程原文），下次 UI 改版让 Agent 基于意图重新生成，比基于旧代码修补效果好。

## 总结

AI 写 E2E 测试不是"一键生成"，而是一条流水线：真实浏览器观测 → 意图驱动起草 → 有限轮次的失败回灌 → 人工验收。收益是把写用例从半天级压到小时级，但维护质量的上限取决于你的选择器规范和评审纪律——工具改变的是速度，不是标准。
