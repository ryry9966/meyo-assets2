## 背景

OpenClaw 里 `memory_recall` 决定 agent 能不能"想起该想起的东西"。多数部署的默认路径是全文检索——对 `MEMORY.md` 和 `memory/` 目录直接跑 SQLite FTS5 或 grep；也有人一步到位上向量库。用生产数据跑了几个月后，我的结论是：两条路单独用都有明显短板，混合召回才是性价比答案。

## 问题：各自翻车的真实场景

- **全文检索的坑**：用户问"上次 token 验证失败那次怎么解决的"，记忆里存的却是"签名校验报错排查记录"。关键词完全对不上，检索空手而归。同义改写是自然语言查询的常态。
- **语义检索的坑**：排查 `ERR_22023`、找 `~/.openclaw/workspace/agent.json` 这类精确标识符时，向量召回经常混进一堆形近不相关的片段，偶尔还漏掉原文。
- 此外，中文在 FTS5 默认 tokenizer 下基本不可搜，而嵌入有成本和延迟。

## 做法：一套可落地的混合召回

1. **统一入库**：`MEMORY.md`、`memory/*.md`、会话摘要全部结构化，每条带 `source`、`created_at`、`tags`。
2. **双通道索引**：FTS5 走一路（CJK 用 trigram 或外接 jieba tokenizer），嵌入走另一路（中文选多语模型如 bge-m3，私有数据务必本地跑）。
3. **召回管道**：query 轻量清洗 → 两路各取 top-20 → RRF 融合 → 叠加时间衰减与 tag 命中加分 → 截 top-5 注入上下文。RRF 只看排名不看分数，天然绕开量纲问题。
4. **评测集**：从真实会话攒 30~50 条 query 和期望命中的记忆条目，每周回归一次 top-5 命中率。没有这个，调参全靠感觉。

## 踩坑点

- **分数加权是陷阱**：余弦相似度（0~1）和 BM25（无上限）直接相加，必然一边压倒另一边。用 RRF，稳且省心。
- **trigram 有代价**：中文能搜了，但索引体积约涨三倍、写入变慢，记忆量大时先评估。
- **分块按标题切**：300~500 字一块，切完把父级标题拼进块首，否则跨章节内容召回出来缺上下文。
- **换嵌入模型 = 全量重建索引**：索引里记得存模型版本，否则新旧向量混在一个空间，相似度直接失真。
- **时间衰减别拍脑袋**：半衰期参数用评测集调；重大结论类记忆加 pinned 标记绕过衰减。

## 可复用建议

- 混合召回设为默认；纯向量只在"小语料 + 自然语言问句"场景够用。
- 错误码、路径、ID 这类精确查询旁路直走全文检索，别进向量。
- recall 的命中/未命中写日志，检索质量不评测就是玄学。
- 优先本地嵌入模型，隐私和延迟都更可控。

## 总结

语义搜索解决"换个说法也能找到"，全文搜索解决"精确命中"——前者贵在理解，后者贵在确定。对 OpenClaw 这类常驻自动化 agent 来说，双通道 + RRF 融合 + 小评测集，是成本、延迟、命中率三者平衡最好的方案。先跑通混合，再谈优化。
