## 背景

OpenClaw 的 cron 任务本质上是"无人值守的 agent 会话"：到点唤醒，agent 拿着你写的 instruction 独立执行，再把结果投递到指定渠道。它和聊天里随口说一句"帮我总结下今天的消息"完全是两回事——聊天时有上下文、能随时纠偏，cron 里 instruction 就是 agent 拿到的全部信息。

社区里不少定时任务跑几次就哑了，排查下来问题大多不在调度配置，而在 instruction 被写成了"对话语气"。

## 典型问题

- **时间指代模糊**："今天的新闻"——是自然日、过去 24 小时，还是上次运行以来的增量？agent 只能猜。
- **没有空结果分支**：没有新数据时，agent 为了"完成任务"会硬凑内容，这是定时幻觉的主要来源。
- **输出没有落点**：不说发到哪，结果散落在默认会话里或直接丢失。
- **一个任务塞太多事**：抓取、分析、写文件、发通知串成一条链，中间一步失败，整条链路哑掉。
- **引用不存在的上下文**："按我们上次讨论的口径"——cron 会话每次都是全新的，没有"上次"。

## 做法：六段式模板

我现在的 cron instruction 基本都按这个骨架写：

```text
【任务】每天 08:30（Asia/Shanghai）执行。
【数据源】只用 <工具/MCP 名> 和本地目录 /path/to/notes，禁止联网搜索。
【时间窗】统计过去 24 小时的新增内容。
【输出】Markdown，不超过 300 字，按"要点 / 风险 / 建议"三段组织。
【投递】结果发送到 <目标渠道>，同时写入 /path/to/daily.md。
【兜底】若无新增内容，只回复一行"过去 24h 无更新"，不要扩展、不要猜测。
【禁止】不执行数据源之外的操作，不主动调用其他工具。
```

几个关键段的用意：

- **数据源收窄**：agent 挂了多个 MCP 时，直接点名工具，避免它自由发挥选错。
- **时间窗显式化**：把"今天"翻译成"过去 24 小时"这类可计算的描述，并写明时区——容器里的系统时区经常不是你以为的那个。
- **兜底分支**：明确"没数据时做什么"，以及更重要的——"没数据时不要做什么"。

## 踩坑点

1. **先手动触发，再挂调度**。每个 cron 都先用"立即运行"验证两三次，确认输出格式和投递落点都对，再上时间。
2. **一个 cron 只干一件事**。需要链式操作就拆成多个任务，用文件作为中间产物交接，失败了也好定位。
3. **给输出设上限**。不限定字数，模型会越写越长，token 成本和阅读成本一起涨。
4. **少写提醒式废话**。"请务必认真仔细"没有约束力，把要求写成可判定的规则才有用。

## 可复用建议

- 把 instruction 当**交接文档**写，验收标准是：一位凌晨三点被叫醒、没有任何上下文的同事，照着它能否一次跑对。
- **版本化**：把所有 cron instruction 存进 repo，改动留痕，方便回滚和 diff。
- **每月 review 一次**：需求变了 instruction 没变，是定时任务静默跑偏的开始。

## 总结

Cron instruction 的本质是一份微型任务规格书：任务、数据源、时间窗、输出格式、投递落点、兜底行为，缺一个就留一个坑。写完问自己一句：agent 醒来时手里只有这一段话，它能不带歧义地执行、并交出我预期的东西吗？能，再挂调度。
