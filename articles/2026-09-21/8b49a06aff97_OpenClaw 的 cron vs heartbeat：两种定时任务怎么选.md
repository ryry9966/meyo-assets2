# 背景

OpenClaw 网关层内置了两种“让 agent 定时干活”的机制：**cron job** 和 **heartbeat**。新手常把两者混用，结果要么 cron 列表膨胀成一堆脆弱的定时脚本，要么心跳把主会话上下文搅得一团糟。这篇帖子把两者的适用边界讲清楚，给出一个可复用的判断流程。

# 本质区别

**Cron：时间驱动。** 到点执行，执行内容在配置时就固定了——绑定的 prompt、目标会话、投递渠道都写死。语义是“X 点 Y 分，做 Z”。支持 cron 表达式、一次性任务、显式时区。

**Heartbeat：状态驱动。** 网关按固定间隔（默认约 30 分钟）向主 agent 发一个心跳 prompt，agent 结合当前上下文自行判断“有没有需要处理的事”。语义是“每隔 N 分钟看一眼，有事就办，没事别吭声”。当 agent 判断无事可做时返回约定标记，网关会抑制这条回复，不打扰用户。

关键差异：cron 的“做什么”是预先确定的，精确、可预测；heartbeat 的“做什么”由模型运行时决定，灵活，但消耗 token 且有不确定性。

# 怎么选：三步判断

1. **有明确时间点吗？** 早报 8 点推送、每周日备份提醒、某个具体时刻的会议提醒 → 用 cron。
2. **是周期性巡检吗？** 盯一个长跑训练是否结束、巡检收件箱、观察部署状态 → 用 heartbeat。
3. **是“条件满足后在某时刻行动”吗？** 比如“训练结束后 10 分钟通知我” → heartbeat 负责探测条件，命中后由 agent 动态注册一个一次性 cron 精确跟进。**这个组合是实践中最好用的模式。**

# 踩坑点

- **时区**：跑在服务器上的网关默认按 UTC 解析 cron，“早上 8 点”变成下午。要么显式指定任务时区，要么对齐宿主机 `TZ`。
- **心跳太吵**：interval 调太短、prompt 里又没写“没事别说话”，结果每半小时收到一条没营养的消息，token 账单同步上涨。务必在心跳 prompt 里明确“无事则直接返回无事标记，不要打扰用户”。
- **上下文污染**：heartbeat 跑在主会话里，巡检过程的中间输出会留在上下文中，挤占正常对话空间。重活交给 cron + 独立会话，心跳只做判断。
- **重叠执行**：上一轮任务没跑完，下一轮又触发了。任务要幂等；长任务用“心跳查状态”，而不是“cron 直接跑任务”。
- **投递目标**：cron 结果发群还是私聊，直接决定噪音大小。结果类建议走私聊或低优先级渠道。

# 可复用建议

- 命名带作用域和频率，如 `daily-report-0800`，半年后你还会感谢自己。
- 心跳 prompt 保持精简，只写“检查什么、什么算异常、无事怎么办”。
- 观测先行：统计心跳触发次数与“无事返回”占比，超过九成无事就该拉长 interval。
- 把“heartbeat 探测 → 动态注册一次性 cron”沉淀成模板，是这套机制里性价比最高的用法。

# 总结

一句话：**确定时间用 cron，周期巡检用 heartbeat，条件触发的精确动作用两者组合。** 把“何时触发”和“何时行动”分开考虑，定时任务就不会失控。
