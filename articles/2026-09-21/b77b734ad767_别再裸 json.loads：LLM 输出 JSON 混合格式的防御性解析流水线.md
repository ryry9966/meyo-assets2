## 背景

在 OpenClaw 插件和 MCP 工具链里，让 LLM 返回 JSON 是最常见的集成方式。但实际跑起来会发现：同一个 prompt，在不同模型、不同温度、不同上下文长度下，输出格式并不稳定——有时是裸 JSON，有时包着 ```` ```json ```` 代码块，有时前后带一句解释性散文，有时还夹着 `<json>`、`<tool_call>` 这类自定义标签。解析层如果不做防御，整条链路就在"偶尔失败"和"必然失败"之间反复横跳。

## 问题

归纳下来，失败模式有四类：

1. **包裹类**：markdown 代码围栏、前后缀散文、XML 风格标签；
2. **畸形类**：尾逗号、单引号、未加引号的键、行内注释；
3. **截断类**：`max_tokens` 打断，JSON 不完整；
4. **多块类**：一段输出里出现两个以上 JSON，朴素正则抓错位置。

演示时一切正常的 `json.loads`，上线后失败率随模型和 prompt 漂移而上升，而且失败常发生在夜间批处理，排查成本很高。

## 做法

我的方案是把解析做成一条**分层降级流水线**，逐层兜底：

```text
raw → 归一化 → 直接解析 → 去围栏 → 标签提取 → 平衡扫描 → 修复 → schema 校验 → 失败重试
```

1. **归一化**：去 BOM、统一换行、strip；
2. **直接解析**：能过就过，这是最快路径；
3. **去围栏**：剥离 ```` ```json ```` 代码块外壳；
4. **标签提取**：识别 `<json>`、`<tool_call>` 等约定标签；
5. **平衡扫描**：用带字符串感知的花括号计数器，从第一个 `{` 或 `[` 起提取完整对象。必须跳过字符串内部的引号和转义，不能用朴素计数；
6. **修复**：仍失败时用 json_repair 之类的库处理尾逗号、单引号等；**修复必须打日志**，因为它可能悄悄改变语义；
7. **校验**：用 pydantic / jsonschema 按 schema 校验字段类型与枚举，校验通过才算成功；
8. **重试**：把具体解析错误回喂给模型重试一轮，通常一次就够。

## 踩坑点

- 正则用贪婪匹配 `.*` 抓 JSON，遇到多段输出会抓穿到错误位置；要么平衡扫描，要么非贪婪加边界约束；
- 花括号计数不考虑字符串时，JSON 值里带 `{` 的文本会让解析断在半截；
- 截断输出别急着修复，先看 `finish_reason`——截断的 JSON 修出来也是错的，直接重试更便宜；
- 修复工具不是中立的：单引号转双引号可能改写值内容，所以修复层要留痕（log + 命中计数）；
- 不要因为开了 JSON mode / function calling 就删掉解析层，它只是降低失败率，不是归零。

## 可复用建议

- 把流水线封装成 `safe_extract_json(text, schema)` 一个工具函数，插件和 MCP 工具统一引用，别各写各的；
- 优先在 API 层用结构化输出 / 工具调用，解析层作为降级兜底，两层叠加最稳；
- 沉淀一个"脏输出语料库"：线上每次解析失败，把原文（脱敏后）存下来做回归用例，比任何手写的单元测试都真实；
- 记录各层命中率。如果"修复层"命中持续偏高，说明该改 prompt，而不是把解析器写得更复杂。

## 总结

LLM 输出解析的本质，是对不确定性的工程化收编。格式混合无法彻底消除，但可以用分层降级，把失败变成可观测、可重试、可收敛的常规路径。核心原则就三条：**永远不要裸解析、修复必须留痕、schema 校验才是真相**。把这套流水线做成社区共享工具，远比每个插件各修各的 bug 划算。
