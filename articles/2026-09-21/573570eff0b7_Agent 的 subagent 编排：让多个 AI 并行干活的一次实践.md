## 背景

用 OpenClaw 做自动化一段时间后，最明显的瓶颈不是模型能力，而是串行执行。比如"把 8 个数据源的摘要整理成周报""对三个仓库分别跑依赖检查"，主 agent 一个个做，一个任务卡住后面全排队。而这些子任务其实互相独立，完全可以并行。subagent 编排就是解决这个问题的：主 agent 拆任务、派生多个子 agent 并发执行、最后汇总。

## 问题

真上手会发现，并行不是"多开几个会话"就完事，难点在三处：

1. 子 agent 拿不到主 agent 的对话上下文，提示词必须自包含；
2. 多个子 agent 同时改同一批文件，必然冲突；
3. 汇总阶段怎么判断谁成功谁失败，失败了要不要重试。

## 做法

我目前稳定的流程分五步：

1. **拆任务**。主 agent 先把工作拆成互相独立的子任务，判断标准很简单：子任务之间有无读写依赖。有依赖的留在主线上，没依赖的才丢出去并行。
2. **定契约**。每个子 agent 的提示词固定三件事：输入（具体路径或明确指令）、输出（写到哪个文件、什么格式）、状态（完成后在结果文件头部写 ok 或 failed）。子 agent 不在对话里回长篇大论，只落盘。
3. **限流并行**。同时最多 3~4 个子 agent。再往上，先是 API 限流，然后本机的 exec、浏览器工具开始互相抢资源，收益反而变负。
4. **汇总**。主 agent 等待或轮询各结果文件，读状态和内容，合并成最终输出。
5. **兜底**。failed 或超时的子任务单独重跑一次，仍失败就降级——周报里那一节标"数据缺失"，而不是让整个任务挂掉。

效果：一次 8 数据源的汇总任务，串行约 12 分钟，并行后 4 分钟左右。token 成本略升（每个子 agent 都带一份提示词开销），在可接受范围。

## 踩坑点

- **提示词不自包含**是最常见的翻车点。子 agent 会自然地"猜"上下文，猜错就白跑。现在我每个子任务都写全路径、全格式要求，不省这几个 token。
- **让子 agent 直接改共享文件**。吃过亏：两个子 agent 同时编辑同一份草稿，后写的覆盖先写的。现在规定每个子 agent 只写自己名下的文件，汇总阶段才合并。
- **输出太啰嗦**。早期子 agent 把全部中间过程写回对话，主 agent 上下文直接爆炸。改成只回状态加文件路径后干净多了。
- **没设超时**。一个卡死的子 agent 会把汇总无限期挂起，超时按失败处理是必须的。
- **伪并行**。看着独立、实际共享浏览器登录态或同一个分支的任务，并行只会制造冲突，不如老实串行。

## 可复用建议

- 把"拆分 → 契约 → 限流并行 → 汇总 → 兜底"固化成提示词模板，每次只换任务描述。
- 用文件做子 agent 之间的通信介质，不要靠对话上下文传结果。
- 记录每个子 agent 的耗时和 token 消耗，算清并行到底省没省——有些任务的调度开销比收益还大。
- 先从 2~3 路并行起步，跑顺了再加大并发。

## 总结

subagent 编排的价值在于把"独立的等待"变成"并行的执行"，但它考验的是任务拆分和契约设计，而不是 agent 数量。任务独立性越好、单任务越是 I/O 密集，收益越明显；反之就串行。用 OpenClaw 还是别的框架不重要，重要的是这套纪律。
