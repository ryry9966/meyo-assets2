## 背景

在 OpenClaw 这类 Agent / MCP 工作流里，LLM 的输出很少是终点，而是下一个环节的输入：插件要读它，工具要消费它，自动化脚本要基于它继续编排。我们通常在 system prompt 里写一句"只输出 JSON"，然后 `json.loads` 一把梭。测试时相安无事，上了长上下文、真实数据、多插件输出拼接之后，就开始随机崩。

## 问题

同一类任务跑下来，输出格式至少有五六种变体：

- 直接裸 JSON；
- 包在 ```json 围栏里；
- 前面带一段"好的，结果如下："的客套话，尾部再补一句解释；
- 混入 `<think>...</think>` 推理段（开了推理模式的模型尤其常见）；
- 中文全角引号、尾逗号、`True/False/None` 这类 Python 字面量；
- 极端情况：JSON 字符串值里本身含 `{`、`}` 甚至反引号。

用一条正则去"剥围栏"，注定按住葫芦起了瓢。解析是整条自动化链路里最没有存在感、却最先挂掉的环节。

## 做法

核心思路：**不猜格式，枚举候选，逐个尝试，失败可观测**。

1. **预清理**：去 BOM、零宽字符，删掉 `<think>` 块。
2. **候选提取**：不做围栏正则，直接做**括号配平扫描**——遍历字符串维护一个栈，处于字符串内部（含转义）时跳过，遇到最外层闭合时切出一个候选子串。围栏、客套话、思考段被自然忽略，还天然支持多 JSON 块。
3. **逐候选解析**：先尝试原文；失败做**最小修复**（去尾逗号、全角引号转半角）；仍失败再交给 `json-repair` 这类兜底库（记得锁版本）。
4. **Schema 校验**：解析成功 ≠ 结构正确，用 pydantic / jsonschema 再验一遍，错误落到具体字段。
5. **失败处理**：截断记录原始输出（注意脱敏），带错误信息重试一次，不行就走降级路径。禁止 `except: pass`。

```python
import json, re

def _candidates(s: str):
    out, stack, in_str, esc = [], [], False, False
    for i, c in enumerate(s):
        if in_str:
            if esc: esc = False
            elif c == "\\": esc = True
            elif c == '"': in_str = False
        elif c == '"': in_str = True
        elif c in "{[": stack.append((c, i))
        elif c in "}]" and stack:
            o, j = stack.pop()
            if not stack and (o, c) in (("{", "}"), ("[", "]")):
                out.append(s[j:i + 1])
    return out

def parse_llm_json(text: str):
    s = re.sub(r"<think>.*?</think>", "", text, flags=re.S)
    s = s.replace("\ufeff", "").replace("\u200b", "")
    for raw in _candidates(s):
        t = re.sub(r",\s*([}\]])", r"\1", raw)               # 尾逗号
        t = t.replace("\u201c", '"').replace("\u201d", '"')  # 全角引号
        try:
            return json.loads(t)
        except json.JSONDecodeError:
            continue
    raise ValueError("no parsable JSON found")
```

（示例为简化版，生产环境建议给候选加长度上限和数量上限。）

## 踩坑点

- **括号计数必须处理字符串状态**。裸数花括号数量，遇到值里含 `{}` 就崩，这是最常见的翻车点。
- **别全局替换单引号**。"it's" 一替换就烂。全角引号可以放心转，ASCII 单引号和 Python 字面量替换同理，只能放最后兜底。
- **多候选要有确定性优先级**（比如取第一个能解析的），否则同一段输出两个插件解析出不同结果，问题更难查。
- **静默兜底会掩盖格式漂移**。换模型、改 prompt 后输出悄悄变了，失败率不埋点你根本发现不了。
- **json-repair 很好用，但它"太宽容"**：没有引号的 key 也照收。这是策略问题不是 bug，先想清楚你要不要这种宽容。

## 可复用建议

- 把 `parse_llm_json` 沉淀成公共模块，所有插件、MCP 工具共用一份，别各写各的。
- 收集真实坏输出建一个 golden 测试集，每次换模型 / 改 prompt 跑回归。
- 埋一个解析失败率指标，超阈值告警——它是 prompt 漂移最灵敏的探测器。
- 能用 JSON mode / function calling / 结构化输出参数就优先用，字符串解析永远是最后防线。

## 总结

对 LLM 输出的正确预期是"大概率守约，偶尔越轨"。防御性解析不是把 prompt 写得更凶，而是在解析层承认格式会漂移：候选枚举 + 最小修复 + schema 校验 + 可观测兜底，把不确定性收敛成确定的行为。这套东西半天能写完，省下的是往后每一次"怎么又解析失败了"的深夜排查。
