## 背景

Agent 跑起来之后，调用量会失控。一次看起来很简单的任务，拆进工具调用循环里，往往就是二三十次 LLM 请求。全走 GPT，账单和延迟都顶不住；全走本地模型，复杂任务的成功率又明显掉下来。OpenClaw 的多模型路由解决的正是这个问题：同一个 Agent 里，不同步骤绑定不同的模型档案，按规则分发。

## 问题

实际项目里通常有三个约束同时存在：

1. **成本**：GPT 单次调用不贵，乘上 Agent 的调用次数就很贵；
2. **隐私**：日志、内部文档、客户数据不允许出网，这部分必须本地处理；
3. **质量**：本地 7B~14B 模型做摘要、改写没问题，做多步规划和严格 JSON 输出经常翻车。

单一模型无法同时满足三条。所以问题从来不是"选哪个模型"，而是"每一步该路由到哪个模型"。

## 做法

我们的经验是按"认知密度"给任务分层：

| 层级 | 典型任务 | 默认路由 |
|---|---|---|
| L0 | 格式转换、简单摘要、翻译 | 本地小模型 |
| L1 | 单跳工具调用、结构化抽取 | 本地 14B 或云端轻量模型 |
| L2 | 多步规划、代码修改、失败决策 | GPT |
| L3 | 兜底升级 | 更强的云端模型 |

落地分四步：

1. **配置模型档案**：在 OpenClaw 里定义 `fast-local` / `deep-cloud` 两个 profile，各自写清超时、并发上限和降级链；
2. **静态绑定**：工具循环里的中间步骤固定走本地，最终总结和规划节点固定走 GPT——这一条能拿到大部分收益，成本先降一半以上；
3. **动态规则**：按数据源打标签（内网数据强制本地）、按输入 token 长度路由（超过本地上下文直接走云端）、失败两次自动升级到 GPT；
4. **加观测**：每条路由记录命中率、失败率和端到端耗时，跑一周再回来调规则。

## 踩坑点

- **路由判断别用 LLM**。用一个 GPT 调用去决定"要不要省一个 GPT 调用"，账算不过来。规则或轻量分类器就够。
- **本地模型的 JSON 输出不稳**。上 schema/grammar 约束，温度压到 0.2 以下；还不行就改成"本地出草稿、云端校验"的两段式。
- **上下文长度对不齐**。本地 8k、GPT 128k，中途切换会截断历史。路由前先做 token 预算检查，超了就整段走云端。
- **显存并发是隐性瓶颈**。本地模型并发一高就排队，批处理场景反而比云端慢，务必给 profile 设并发上限。
- **换模型会带来输出风格漂移**，长对话里下游解析会抖，输出 schema 必须跨模型统一。

## 可复用建议

- **先测量再路由**：把历史日志跑一遍，统计哪些步骤小模型也能通过，用数据定分层，别拍脑袋；
- **草稿-审核模式收益最大**：本地生成初稿，GPT 只做校验和改写，实测能省六七成成本；
- **路由规则全部写进配置**，不要硬编码，方便灰度和回滚；
- **维护一个 20~50 条的迷你评测集**，每次改规则跑一遍，防止"省了钱、坏了活"。

## 总结

多模型路由不是省钱技巧，而是成本、质量、隐私三者之间的工程权衡。核心就三件事：任务分层、失败升级、全程可观测。先把中间步骤和隐私数据切到本地，拿到主要收益，再用数据慢慢收紧规则——这比一开始就追求精细路由靠谱得多。
