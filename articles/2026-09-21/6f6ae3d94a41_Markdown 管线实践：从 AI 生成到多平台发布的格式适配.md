## 背景

跑过内容类 Agent 的人大概都遇到过同一个尴尬：模型产出的 Markdown 单看很工整，但往公众号、知乎、VitePress 站点、GitHub 各发一份，要么样式崩掉，要么代码块变纯文本，要么图片全裂。问题不在生成端，而在中间缺一条稳定的格式适配管线。这篇记录我们在社区项目里落地的一条管线，思路是"一次生成、方言收敛、多端适配"。

## 问题

各平台对 Markdown 的支持差异比想象中大：

- 公众号编辑器不认 Markdown，需要 HTML + 内联样式，且会剥掉 class 属性；
- 知乎、掘金对表格、脚注、任务列表支持残缺；
- 静态站点认 front matter 和相对路径图片，第三方平台只认外链；
- AI 生成内容还夹带私货：`<br>` 标签、HTML 注释、LaTeX 混进代码块、对齐语法不规范的表格。

不收敛的话，每个平台都得人肉修一遍，自动化就失去了意义。

## 做法

管线分四步，核心工具是 unified/remark 这套 AST 生态：

```
生成 → lint/normalize → remark AST → adapter(公众号|站点|知乎) → 图床重写 → publish
```

**1. 生成端约束。** 在 Agent 的系统提示里限定输出为 GFM 子集：禁用脚注和行内 HTML，图片一律写占位符 `![alt](IMG_xxx)`。源头约束比下游兜底便宜得多。

**2. 规范化。** 输出先过 markdownlint 加自定义规则，修掉缩进列表、多余空行、异常表格，再用 remark-parse 生成统一 AST。后续所有操作都在 AST 上做，不要用正则改 Markdown——这是这条管线最重要的纪律。

**3. 平台适配器。** 每个平台一个 adapter，输入同一棵 AST：

- 公众号：remark-rehype 转 HTML 后做样式内联（juice 或自己遍历注入），复杂表格降级为列表；
- 静态站点：保留 front matter，图片走本地相对路径；
- 知乎/掘金：剥离不支持的节点，脚注转为文末"参考"段落。

**4. 资源与校验。** 图片占位符在发布前统一上传图床并重写 URL；发布后跑链接检查和渲染快照对比。

这套管线我们封装成了 MCP tools（normalize / adapt / publish），挂成 post-generation hook 后，Agent 生成完自己链式调用，人工只做最后审核。

## 踩坑点

- 别指望提示词能完全锁死方言。LLM 对 GFM 边界语法（嵌套列表里的代码块、表格内换行）把握不稳，解析阶段必须容错；
- 公众号样式内联后体积暴涨，长文会被编辑器截断，注入前要压缩 CSS；
- 图床重写必须幂等，管线重跑不能二次上传；
- 渲染快照对比要注意平台自身改版，diff 噪音需要设白名单。

## 可复用建议

- 维护一张"方言矩阵"表，记录每个平台支持的语法，既是 adapter 的实现依据，也是测试用例来源；
- 用 golden file 做回归：每个平台存一份转换后的期望输出，改管线就跑 snapshot 测试；
- 适配器只做降级、不做增强，宁可丢样式，不可丢语义。

## 总结

多平台发布的本质是方言问题，解法和一般工程问题一样：先收敛输入（约束生成），再统一中间表示（AST），最后按端分发（adapter）。AI 负责内容，管线负责格式，边界划清楚，自动化才立得住。欢迎大家在自己的 Agent 里复用这套思路，也欢迎补充各平台新踩的坑。
