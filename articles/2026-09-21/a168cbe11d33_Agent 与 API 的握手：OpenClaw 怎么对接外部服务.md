## 背景

OpenClaw 这类 Agent 框架的价值，最终落在"能动手"上：查日历、读工单、触发构建、改配置，背后全是对外部 API 的调用。对接得顺，Agent 是自动化助手；对接得糙，就是每天给你制造事故的实习生。这篇记录一下我们内部对接几个业务 API 时沉淀的做法。

## 问题

实际对接里反复出现三类问题：

1. **契约不清**：工具描述模糊，模型开始猜参数，猜错返回 400，它换个姿势再猜，进入死循环。
2. **安全裸奔**：API key 明文放在配置里被工具读到，或写操作没有确认机制，一次重试就是三笔重复订单。
3. **返回失控**：上游一口气回 200KB 的 JSON，直接塞进上下文，两轮对话就把窗口吃满。

## 做法与步骤

以"给 Agent 一个查询 + 修改订单状态的能力"为例，四步走：

**1. 选对接形态。** OpenClaw 侧优先走 MCP server：标准化、可复用、权限好收口。简单场景在 skill 里包一层 HTTP 调用也够。别一上来就写大而全的插件。

**2. 把工具定义当契约写。** 参数能收窄就收窄：用 enum 就别用 string，数值加范围，时间统一格式。description 里写清楚"什么场景该用、什么场景不该用"，这比参数说明更能决定调用准确率。

**3. 在 wrapper 层干脏活：**

- 鉴权走环境变量或密钥管理，运行时注入，模型只见引用不见明文；
- 统一超时（10s 量级）+ 指数退避重试，且只重试幂等请求；
- 响应裁剪：只返回模型需要的字段和条数，原始数据落日志；
- 错误结构化：返回 `{ok, error_code, hint}`，hint 明确告诉模型下一步怎么办。

**4. 写操作加确认。** 破坏性工具先跑 dry-run，返回变更 diff 给 Agent，由 Agent 转述给用户，确认后才真正执行。

## 踩坑点

- **"万能 call_api" 是反模式。** 一个工具包打天下，模型传错参数的概率飙升。拆成多个小而明确的工具，准确率立刻上来。
- **重试不等于幂等。** POST 下单重试三次就是三笔订单。要么上游支持幂等键，要么 wrapper 里生成请求 ID 做去重。
- **429 必须显式处理。** 限流后 Agent 若继续重试只会更糟。错误 hint 里要写明"等待后重试"，而不是让它硬刚到账号被封。
- **错误信息是给模型看的提示词。** 只返回 "failed"，模型会用同样的参数无限重试；写清原因和建议动作，它才能自我修正。

## 可复用建议

- 先只读，后写入，权限逐级放开，跑稳一周再升级；
- 每次工具调用记日志（参数 + 截断响应），排障全靠它；
- adapter 层保持薄，上游改字段只动这一层，不碰 prompt；
- 工具总数控制在十几个以内，超出就按场景分组或动态加载。

## 总结

Agent 与 API 的握手，本质是设计一份**模型能读懂、系统扛得住**的契约：schema 是合同，wrapper 是安全垫，日志是黑匣子。这三件事做扎实，OpenClaw 对接外部服务就从"碰运气"变成"可交付"。有别的对接姿势欢迎在评论区交流。
