## 背景

E2E 测试一直是投入产出比最尴尬的一层：用例少覆盖不住核心链路，用例多又难维护。过去半年，我们把 E2E 维护工作的一部分交给 OpenClaw 的 Agent（通过自建 MCP 工具接入 Playwright），跑出了一条还算稳的协作流程，记录一下做法和边界。

## 问题

直接让 AI"帮我写测试"基本不可用，踩过三类典型失败：

1. **断言过弱**：生成的大多是 `toBeVisible()`，页面能打开就绿，业务逻辑错了照样通过。
2. **镜像实现**：Agent 看了源码后写的选择器全是 class 名和内部组件结构，一次重构全挂。
3. **脆弱等待**：靠 sleep 和重试掩盖时序问题，偶发挂掉比没有测试更消耗信任。

根因是 Agent 缺两样东西：业务链路的知识，和可稳定观测的页面结构。

## 做法

流程拆成四个环节，Agent 负责体力活，人负责语义：

**1. 链路梳理（Agent 草拟 + 人审核）**
输入是 PRD 摘要和路由表（通过 MCP 工具 `get_routes` 暴露），Agent 产出"关键用户旅程清单"——登录、下单、退款这类。人工筛掉约三成伪链路，这份清单作为后续的唯一事实来源。

**2. 用例生成（Agent）**
刻意不让它看实现代码，只给 a11y 树快照和页面约定。要求全部基于 `data-testid` 和可访问性角色定位，产出 Page Object + 用例骨架。这步产出很快，但断言一律标记为"待人工确认"。

**3. 执行与修复循环（Agent + CI）**
测试跑在隔离环境，失败时修复 Agent 拿到 trace 文件、网络日志和失败截图，输出修复 PR。硬性约束：不允许它通过加 retry/timeout 让测试变绿，修复 PR 必须说明根因。

**4. 人工门禁**
评审只看一件事：每条断言验证的是业务结果（订单状态、金额、DB 落库），还是仅仅是"页面出现了"。后者一律打回。

## 踩坑点

- **先给行为规格，再给代码**：顺序反了，用例就会在测试实现而不是测试行为。
- **MCP 工具宁窄勿宽**：早期给过一个"操作浏览器"的万能工具，Agent 经常偏离任务乱点。拆成 `get_routes`、`get_page_snapshot`、`run_test` 三个窄工具后稳定很多。
- **测试数据要隔离**：Agent 生成的数据撞过库里的既有记录，现在强制走带前缀的 fixture 命名空间。
- **用注入 bug 验证覆盖**：手动在代码里埋几个缺陷（改金额、跳过校验），看用例能不能抓到。抓不到的"绿"是假绿。

## 可复用建议

- 团队先统一 `data-testid` 规范，并做成一个 MCP 校验工具，缺 testID 的页面在 CI 直接报错——这是 Agent 定位稳定的前提。
- 从 3~5 条冒烟链路开始，别一上来全站铺开。
- 把 AI 生成的用例当实习生 PR 评审：重点看断言质量，不看能不能跑过。

## 总结

Agent 在 E2E 上的价值不在"替你决定测什么"，而在把 Page Object、等待策略、fixture 这些体力活消化掉，并承担失败后的第一轮修复；场景选择和断言语义仍然是人的活。这条流水线跑了三个月，用例维护耗时降了一半左右，假绿率明显下降。数字不算惊艳，但路径可复制，适合正在被 E2E 维护成本拖着走的团队试一试。
