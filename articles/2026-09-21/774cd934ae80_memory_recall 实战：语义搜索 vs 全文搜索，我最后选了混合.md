## 背景

OpenClaw 助手跑了几个月后，记忆库里攒了几百条条目：用户的部署偏好、某项目的架构决策、踩过的依赖坑。`memory_recall` 的职责是在每轮对话前，把这些条目里最相关的几条捞出来注入上下文。捞得准，助手显得"记性好"；捞不准，要么答非所问，要么上下文被无关记忆塞满。

## 问题

我最开始只上全文检索（SQLite FTS5）。用户问"上次那个部署报错怎么解决的"，召回为空——记忆里存的是具体错误码和命令行，和 query 字面上完全不重叠。换成 embedding 语义检索后，问题反过来了：查"ERR_CONN_RESET 的处理记录"，返回一堆语义相近但毫无关系的"网络问题笔记"，精确标识符被稀释。

结论很清楚：语义搜索管"意思相近"，全文搜索管"字面精确"，单靠任何一路都有系统性盲区。

## 做法

我的方案是混合召回，步骤如下：

1. **记忆条目原子化**。写入时不存整段对话，拆成"一条记忆 = 一个事实"，附上 `timestamp`、`tags`、`project` 字段。这是后面一切检索质量的地基。
2. **双索引**。FTS5 负责 BM25（中文记得换 trigram 或 jieba 分词器），sqlite-vec 或 pgvector 存 embedding。条目量在几千条以内，SQLite 单文件够用，不必上独立向量库。
3. **两路并行 + RRF 融合**。同一 query 同时打给两路，用 Reciprocal Rank Fusion 合并：`score = Σ 1/(60 + rank)`。只看排名不看原始分数，天然回避两套分数量纲不一致的问题。
4. **时间衰减**。融合分乘一个按 `timestamp` 计算的 recency 权重，近期记忆略微优先。
5. **取 top 5~8 条**注入上下文，超过 8 条开始挤占有效空间。

## 踩坑点

- **中文分词**。FTS5 默认 tokenizer 对中文基本失效，整句会变成一个 token，等于不可用。这是最容易被忽略的一步。
- **别手工加权融合分数**。BM25 无上界，余弦相似度在 [-1,1]，直接 `0.6*bm25 + 0.4*cos` 等于让 BM25 独裁。要么先归一化，要么直接用 RRF。
- **旧记忆不会自动失效**。同主题出现新决策时，要给旧条目打 superseded 标记并在召回时过滤，否则新旧矛盾记忆一起进上下文。
- **没有评测集就是玄学**。攒 30~50 条 "query → 期望命中的记忆 id" 的测试对，每次调权重、换 embedding 模型前跑一遍，看 recall@5 就够。

## 可复用建议

- 起步阶段只上关键词检索，出现"换个说法就找不到"的实际案例后，再补语义路，避免过早优化。
- 混合 + RRF 是默认起点，不要在没有评测集的情况下精调融合权重。
- 检索是下游，质量在上游：写入时的 tags 和原子化程度，比召回算法本身影响更大。
- 把每次召回的 miss 打进日志，定期人工筛一遍回灌评测集，形成闭环。

## 总结

语义搜索和全文搜索不是二选一，而是互补的两路信号。原子化条目 + 双索引 + RRF 融合 + 时间衰减，是我目前在 OpenClaw 上跑得最稳的 memory_recall 组合：改动少、依赖轻、结果可解释。先搭评测集，再谈优化——这个顺序比任何算法选型都重要。
