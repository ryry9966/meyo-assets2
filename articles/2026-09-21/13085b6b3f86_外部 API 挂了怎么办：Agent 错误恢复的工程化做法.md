## 背景

跑过一段时间 Agent 自动化的人多半遇到过：流程白天好好的，凌晨三点 LLM 供应商限流、搜索接口超时、某个 MCP 工具静默失败。Agent 本身没有"依赖掉线"的概念——它只会不停重试、编造结果，或者干脆卡死。韧性不是模型层的职责，是编排层的事，得自己建。

## 问题

外部依赖故障大致分四类：

1. **可重试错误**：429、5xx、网络抖动，重试通常能过；
2. **不可重试错误**：401/403、配额耗尽、参数非法，重试只烧 token；
3. **伪成功**：HTTP 200 但 body 里嵌着 error 字段，或返回结构变了导致解析失败；
4. **慢而非死**：接口响应 40 秒，不设超时就拖垮整个循环。

不区分这些情况的典型后果：重试风暴烧光配额、非幂等写操作被执行两次、Agent 在工具失败后"脑补"一个结果继续往下跑。

## 做法

原则只有一条：所有外呼收敛到统一调用层，错误以结构化形式交回给 Agent 决策。

1. **错误分类先行**。把异常归一化成信封：`{error_type, retryable, suggestion}`。retryable 按状态码和错误码白名单判断，不要靠模型猜。
2. **指数退避 + 抖动重试**。1s 起倍增，封顶 30s，加随机抖动避免同步重试；上限 3–5 次，超了就放弃本次调用。
3. **每层独立超时**。HTTP 请求、单次工具调用、整个 step 各设超时，且必须小于上层剩余预算。宁可快速失败，不要挂死。
4. **熔断 + 半开探测**。同一依赖连续失败 N 次即熔断，冷却期内直接走降级；冷却结束放一个探测请求，成功才恢复。没有半开探测的熔断器可能永远起不来。
5. **降级路径提前写好**。备选供应商、缓存结果、或跳过该步并在输出中标注"该部分基于降级数据"——三选一，都比让模型自由发挥强。
6. **幂等键**。所有写操作（下单、发消息、写库）带幂等键，重试才安全。
7. **检查点**。长流程每步落盘中间状态，故障后从断点恢复，而不是从头再跑一遍。

## 踩坑点

- 只看状态码不看 body，把伪成功当真成功，污染下游数据；
- 重试不加抖动，多个并发任务同时打过去，把半死的服务彻底打死；
- 超时设 120s 这类大值，一个慢接口卡住整个并行批次；
- 把原始堆栈直接塞回给模型，它开始"解释"错误而不是换路径——给它的应该是上面那个三字段信封；
- 熔断冷却时间写死：高峰期恢复太慢，低谷期又探测过频。

## 可复用建议

- retry / timeout / breaker 做成配置项，每个工具独立策略，不要全局一套；
- 批任务启动前对关键依赖做一次预检（preflight），失败就延迟启动；
- 给错误分类打点：哪类错误、重试几次、最终是否降级——这些指标比笼统的"成功率"更能预警；
- 写一页 runbook：某依赖挂了，人工介入的第一步是什么。

## 总结

Agent 的可靠性不取决于模型多聪明，而取决于编排层如何对待失败。分类、退避、超时、熔断、降级、幂等、检查点——七件事单看都不复杂，但缺任何一件，故障都会以你没想到的方式放大。先让失败**可见、可控、可恢复**，再谈自动化率。
