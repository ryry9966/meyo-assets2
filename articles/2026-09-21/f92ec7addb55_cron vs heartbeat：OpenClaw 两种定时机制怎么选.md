## 背景

用 OpenClaw 搭个人自动化跑了一段时间，被问得最多的问题之一是：周期性的事到底交给 cron 还是 heartbeat？两者都能"定期叫醒 agent"，但设计意图完全不同。选错了轻则浪费 token，重则渠道被消息轰炸。

## 两者差在哪

- **heartbeat（心跳）**：挂在主会话上的固定节拍，默认约 30 分钟一次。每次把一段极简 prompt 发给 agent，agent 读 `HEARTBEAT.md` 里的清单，判断"有没有需要做的事"；没事就回 HEARTBEAT_OK，不投递到任何渠道。
- **cron**：独立调度器。每个任务有自己的 cron 表达式（或 one-shot 时间点）、专属 prompt、隔离会话、超时与 jitter，跑完后按配置 announce 到指定渠道。

一句话概括：心跳是"到点了，看看有没有事"；cron 是"到点了，去干这件事"。

## 怎么选：先分清触发条件

关键不是间隔长短，而是触发条件属于"时间"还是"状态"：

- **时间确定 → cron**。每天 9 点发日报、周五下午提醒周报、一次性的"明早 8 点叫我"，时间一到就执行，不需要 agent 参与判断。
- **状态不确定 → 心跳**。"有重要新邮件才打断我"、"磁盘超 80% 才通知"、"今晚有安排就提前一小时提醒"——做不做取决于 agent 对状态的判断。

## 做法

1. 列出所有周期性需求，逐条标注：时间是固定的，还是"满足条件才做"。
2. 固定时间的进 cron：写 cron 表达式，**显式指定时区**，prompt 里写清输入来源（读哪个文件、调哪个工具）和投递目标；一次性事项用 one-shot。
3. 条件触发的进心跳：把 `HEARTBEAT.md` 当 checklist 写，每条都要有可判定的条件和动作，比如"若 GitHub 有未读 mention，则汇总标题投递到 TG"。没写进清单的事，不该指望 agent 自作主张。
4. 心跳间隔从默认值起步，观察几天再调。

## 踩坑点

- **心跳与主会话共用**：主会话正在跑任务时，心跳会被跳过，别拿它做高实时性监控。
- **清单写太宽泛**（"帮我盯着邮件"）会频繁误触发。每条必须可判定：什么条件、什么动作、投到哪。
- **成本**：心跳每次都带完整 system prompt，间隔调到分钟级后 token 消耗会很可观。建议统计 HEARTBEAT_OK 占比，命中率低就拉长间隔。
- **时区**：cron 不显式指定时区时默认跟主机走，容器里常是 UTC，会差 8 小时。
- **上下文隔离**：cron 是独立会话，看不到主会话内容；需要的信息要么写进 prompt，要么让它去读文件。
- **投递目标没配好**：任务其实跑完了，结果只躺在会话日志里，你会误以为没执行。

## 可复用建议

- 口诀：**时间触发选 cron，状态触发选心跳**。拿不准时先用心跳观察一段时间，发现规律后固化成 cron。
- 心跳做薄、cron 做厚：心跳只做判断和轻量动作，重活拆成独立 cron 任务并配专属 prompt，出错也好定位。
- cron 调度密集时加 jitter，避免整点齐射打爆渠道。
- 定期翻会话日志复盘：心跳空转多不多、cron 结果有没有人看，用数据调间隔和投递策略。

## 总结

两者不是竞争关系，而是分工：cron 负责"什么时候做"的确定性，心跳负责"要不要做"的判断力。把固定节奏交给 cron，把模糊状态交给心跳，再用心跳命中率的数据反过来收敛心跳清单——这套组合跑顺之后，agent 的主动性才真正可控。
