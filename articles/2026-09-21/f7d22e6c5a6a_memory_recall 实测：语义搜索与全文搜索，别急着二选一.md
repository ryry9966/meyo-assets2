## 背景

OpenClaw 的“记忆”本质上是一堆 markdown 文件：`MEMORY.md` 加上 `memory/` 目录下的日记式笔记。`memory_recall` 默认走全文匹配（grep 类），装了向量检索插件后可以切到 embedding 语义搜索。社区里经常有人问“要不要把全文换成语义”，我拿自己的实例跑了两个月，结论是：这不是二选一的问题。

## 问题

两条路线各有明显的失效场景：

- **全文搜索**：对“当时那个权限报错是怎么解决的”这类模糊提问基本无能为力，因为查询词和原文措辞对不上。中文同义词尤其致命，搜“重启”找不到“重新启动”。
- **语义搜索**：反过来，对精确 token 会翻车。报错码、路径、项目代号这类高区分度的词，embedding 反而会稀释，top-k 里混进一堆“语义相近但完全无关”的旧笔记。

只留一个，必然丢召回。

## 做法

1. **先做基线。** 确认默认 recall 的匹配范围和行为，从聊天记录里翻出 20~30 条真实历史问题，记录 hit@3。没有这个数字，后面一切调优都是玄学。
2. **加语义层，而不是替换。** 在 memory 写入时做分块 + 本地 embedding，存进 SQLite 向量库，块上带日期、文件路径、所属小节。分块按日记条目或标题切，别用固定 token 窗口。
3. **合并策略。** recall 时先跑全文；命中数不足、或查询是自然语言问句时，叠加语义检索结果，按文件+行号去重，top-k 控制在 5 左右，设最低相似度阈值。
4. **索引新鲜度。** 挂在 memory 写入事件上做增量更新，别只在启动时全量构建。
5. **跑一周再看数。** 对比 hit@3，按“命中走的是哪条路”的分布调阈值。

## 踩坑点

- **索引滞后**：白天记的笔记晚上搜不到，排查半天发现是只在会话启动时建索引。改成写入即更新才稳定。
- **分块切碎上下文**：固定窗口把一条记忆切成两半，命中了后半段、丢了日期和主体。改成条目级分块基本解决。
- **语义假阳性**：阈值太低时返回“看起来相关”的旧记忆，agent 还会一本正经地引用它。把相似度分数打进日志，排障时能省很多时间。
- **中文全文匹配噪声**：查询先归一化（去标点、统一大小写），长查询考虑拆词。
- **云端 embedding**：recall 是高频调用，延迟和费用不可控。记忆就几 MB，本地小模型绰绰有余。

## 可复用建议

- 记忆总量在几百 KB 以内时，别上向量，grep 就够了，复杂度换不来收益。
- 混合检索是默认答案：全文保底精确匹配，语义补模糊召回。语义是叠加项，不是替代品。
- 与其调检索器，不如让记忆条目自包含：一行开头带日期 + 主题关键词 + 常用别名（“重启/重新启动”写在一起），两种检索同时受益。
- 评测集必须是你自己的真实查询，通用 benchmark 和你的使用模式大概率不一致。

## 总结

memory_recall 的选型不是“语义 vs 全文”的信仰之争，而是“什么查询走哪条路”的工程问题。先量化自己的查询分布：精确 token 多就守住全文，模糊提问多再补语义层。我目前的配置是两者合并 + 严格去重 + top-k=5，hit@3 从约 0.4 提到 0.75。数字不一定可迁移，方法可以——先测，再改。
