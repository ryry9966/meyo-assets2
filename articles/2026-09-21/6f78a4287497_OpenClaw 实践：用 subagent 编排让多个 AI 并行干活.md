## 背景

OpenClaw 用久了会发现主 agent 的一个天然瓶颈：单会话、单上下文、串行执行。比如让它「把 20 个仓库的 README 各读一遍，总结 3 条要点」，它只能逐个 fetch、逐个总结，跑十几分钟，而且所有工具输出全堆在主上下文里，跑到一半 token 开始膨胀，输出质量肉眼可见地下滑。

## 问题

这类任务其实天然可并行、可隔离：每个子任务互不依赖，中间产物也不需要主 agent 亲自看。让主 agent 串行干，既慢，又用大量原始材料污染了它本该用来做决策的上下文。

## 做法

OpenClaw 内置的 subagents 工具就是为这个场景准备的：主 agent 可以 spawn 出带独立上下文的子 agent，把活包出去，自己只负责拆分、分发和汇总。我总结成一个三段式：

1. **拆分**：主 agent 先明确任务边界，列出 N 个互不依赖的子任务；
2. **分发**：并行 spawn 多个 subagent，每个的 prompt 写死五件事：

```text
【目标】读取仓库 X 的 README，提炼 3 条要点
【输入】仓库地址 + 分支
【工具】仅允许 web_fetch / read
【输出】不超过 200 字的摘要，最后一行给结论
【禁止】不写文件，不 spawn 子任务
```

3. **汇总**：子 agent 回传精简结果，主 agent 合并成最终产出，必要时再派一个收尾 agent 做去重和排版。

并发别拉满，我压在 3~5 个，够快，也不容易触发 API 限流。

## 踩坑点

- **子 agent 上下文是隔离的**。主 agent「以为它知道」的东西它一概不知道。prompt 里漏了路径、地址或参数，它就开始瞎猜或原地反问。
- **并发写同一个文件必炸**。两个 subagent 同时改一个文件，后写的覆盖先写的。要么分文件写，要么只让子 agent 返回文本，由主 agent 统一落盘。
- **成本是乘法**。5 个并行子 agent 各自都在烧 token，无上限并发一次能跑掉平时一天的量，先算好预算。
- **返回太长会反噬主上下文**。必须在 prompt 里强制摘要输出，原始材料留在子 agent 里用完即弃。
- **递归 spawn 失控**。放任子 agent 再 spawn 子 agent，任务树会爆炸式展开。上面模板里的【禁止】段就是为这个准备的。

## 可复用建议

- 那个五段式模板（目标/输入/工具/输出/禁止）可以固化下来，每次填空，比每次现想 prompt 稳定得多。
- 让 subagent 只做读和算，写操作收敛到主 agent，天然避开写冲突。
- 失败要隔离：单个子 agent 失败就让它返回错误摘要，不要中断整体，主 agent 最后统一决定重试哪些。
- 上不上 subagent 的判断标准很简单：**子任务无数据依赖、单个产出不超过几百字、能接受各自失败重试**。三条都满足就并行，否则老实串行——编排本身也有开销。

## 总结

subagent 编排不是玄学，本质就是三件事：上下文隔离、并行执行、结果收敛。OpenClaw 把机制做成了开箱即用的工具，真正的工作量在于任务拆分和 prompt 约束。建议从读多写少的批处理任务试起——批量总结、批量巡检、批量抓取——跑顺了再往复杂流程上推。
