## 背景

大多数人用 Agent 仍是问答式：想起一件事，去问，得到回答，然后彼此下线。OpenClaw 的 agent 常驻在网关里，除了被动响应消息，还有一个容易被忽略的机制——heartbeat（心跳）。网关按固定间隔（默认约 30 分钟）唤醒一次 agent，agent 醒来后第一件事是读工作区里的 `HEARTBEAT.md`，决定这次醒来要不要干活。

`HEARTBEAT.md` 就是个普通 Markdown 文件，但语义是“常备指令”：不用你每次提问，agent 每次心跳都会对照它检查一遍。

## 问题

纯被动模式有几个实际痛点：

- 监控类需求落不了地。“看看部署完没有”“留意下磁盘”，每次都得你自己发起。
- 用 cron 裸调 LLM 能做定时任务，但编排逻辑散落在外部脚本里，agent 的工具、记忆、会话上下文全用不上。
- 脑子里那些“以后再说”的小事，没地方托付。

## 做法

1. 在 agent 工作区建 `HEARTBEAT.md`（默认在 `~/.openclaw/workspace` 下）。
2. 用清单格式写任务，每条尽量满足：明确的检查条件 + 明确的动作 + 明确的汇报标准。
3. 明确告诉 agent：无事可做时返回 `HEARTBEAT_OK`。这是社区约定，agent 以此跳过回复、避免刷屏。
4. 间隔在配置里调（`agents.defaults.heartbeat.every`），夜间可用 `activeHours` 静默。

示例：

```markdown
# HEARTBEAT

- 检查 ~/deploy/status.lock：存在且标记为 done，则摘要通知我，然后删除该文件
- 跑 `df -h /`：使用率超过 85% 才提醒，否则安静
- 看 inbox.md 有没有新增条目，有就处理并勾掉
- 没有任何事可做：返回 HEARTBEAT_OK，不要发消息
```

## 踩坑点

- **文件写太长。** 每次心跳都是一次真实的模型调用，任务一多 token 成本上来，agent 还容易“脑补”出不存在的任务。控制在 20 行以内，只放真正需要周期检查的事。
- **忘写 `HEARTBEAT_OK` 兜底。** 结果就是每半小时收到一句“一切正常”，三天后你会把整个机制关掉。
- **心跳 ≠ cron。** 心跳适合“条件满足才动作”的巡检；固定时间推送（每天早报）用 OpenClaw 自带的 cron 任务更准，别用心跳硬凑整点。
- **重活别同步放在心跳里。** 心跳会话有时间预算，长任务应让 agent 触发脚本或 MCP 工具异步跑，心跳只负责看结果。
- 另外有些版本在你正和 agent 对话时会自动跳过心跳，这是正常行为，不是丢了任务。

## 可复用建议

- 任务分三类写：**状态检查类**（lock 文件、磁盘、进程）、**收件箱类**（inbox.md、待读列表）、**汇总类**（只在有增量时汇报）。每类一节，互不纠缠。
- 汇报分级很重要：在文件里写清楚哪些发现“值得打扰我”，哪些只追加到日志文件，否则 agent 会把鸡毛蒜皮都推给你。
- 与 `MEMORY.md` 配合：心跳是手脚，记忆是脑子。巡检得到的结论写进记忆，避免每次重新判断。
- 把工作区放进 git。心跳驱动的 agent 是会自己改文件的，出问题时你能 diff 出它到底干了什么。
- 从 1~2 条任务起步，观察一周心跳日志，再决定加不加。

## 总结

`HEARTBEAT.md` 本质上就是“周期唤醒 + 一份 agent 每次都会读的清单”，技术上毫无神秘可言。但它把交互模型从“你拉”变成了“它巡”，给那些介于“值得写脚本”和“不值得记在脑子里”之间的小事提供了一个安放位置。写短一点、写具体一点、让它学会安静，这个机制就能长期跑下去。
