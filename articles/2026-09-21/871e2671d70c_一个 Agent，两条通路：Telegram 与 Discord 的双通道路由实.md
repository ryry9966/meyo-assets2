## 背景

我们的 Agent 最初只挂在 Telegram 上，服务个人和小群。后来团队希望在 Discord 服务器里也能用。第一反应是再起一个实例，但很快暴露问题：两份配置、两套记忆、两个工具环境，同一个人在两边的上下文完全对不上。于是改成单实例、多通道路由，稳定跑了一段时间，把过程记录下来。

## 问题

多通道不是"多接一个 token"那么简单，核心是四件事：

1. **会话归属**：Telegram 私聊和 Discord 频道共用还是隔离 session？
2. **身份统一**：同一个人在两边 ID 不同，记忆会分裂成两个人格。
3. **格式差异**：两边 Markdown 方言不同，代码块和加粗经常渲染错。
4. **回环与限流**：两边群如果被桥接，消息可能进 Agent 后又流回另一端形成循环；Discord 高频 @ 会触发 429。

## 做法

OpenClaw 的网关本身支持一个进程挂多个 channel 插件，思路是把所有平台差异压在插件层，Agent 只面对规范化后的消息。

1. 配置里同时启用 `channels.telegram` 与 `channels.discord`，指向同一个默认 Agent；网关单进程同时维持 Telegram 长轮询和 Discord gateway 连接。
2. Session key 采用 `channel:chatId`，**默认隔离**；确需共享的群单独显式声明合并。
3. 入站消息附带 channel 元数据，系统提示词要求 Agent 平台自适应：Discord 侧控制长度、多用分节；Telegram 侧可以更口语。
4. 出站统一用中性 Markdown，由各 channel 插件转成对应方言，Agent 不输出平台特化语法。
5. 在 workspace 放一张身份映射表（telegram id ↔ discord id ↔ 别名），Agent 检索后按"同一个人"处理记忆。
6. 每个通道独立计数与重试，掉线只重启对应插件。

## 踩坑点

- **回环最隐蔽**：有人用桥接机器人把两边群打通，Agent 的回复被桥回另一端再次进 Agent，开始自言自语。解法是过滤所有 bot 来源消息，并给自己的出站消息打来源标记。
- 调试期手动跑了一个脚本 poll 同一个 Telegram token，导致网关收不到消息（getUpdates 409 冲突）。**同一个 token 只允许一个消费者。**
- 共享 session 试了一周就回滚：Telegram 里的私人上下文被引用到 Discord 公开频道，越权感很强。默认隔离是对的。
- 身份映射不全时，Agent 会在 Discord 里重新"认识"一个 Telegram 老用户，语气突变。映射表需要人工核对一次。

## 可复用建议

- 把平台差异封装在通道层，Agent 永远只见统一消息模型——之后加 Slack 或其他平台基本零成本。
- Session 隔离做默认，共享做例外并显式配置。
- 上线前先在测试群跑影子模式，只观察不回复，验证路由和格式转换。
- 通道级监控与独立重启比全局重启重要：Discord 断线不应影响 Telegram。

## 总结

单实例多通道的难点不在"连通"，而在会话语义、身份一致性和格式收口。把差异下沉到插件、把映射显式化、把隔离设为默认——这套结构后来接入新平台时，基本只改配置。
