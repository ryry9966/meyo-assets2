## 背景

OpenClaw 的 agent 长驻运行之后，第一个真实需求往往不是对话，而是"自己动起来"：早上发一份日报、半小时巡检一次目录、到点提醒待办。平台为此提供了两条路径——**cron（定时任务）**和 **heartbeat（心跳轮询）**。两者都能让 agent 周期性醒来，但设计意图完全不同，选错了轻则空转烧 token，重则时间漂移、重复执行。

## 问题

社区里最常见的两类误用：

- 用 heartbeat 做"每天 9 点发日报"，结果时间漂移，主会话被无用唤醒塞满；
- 用 cron 做"看看有没有未处理的事"，每 5 分钟空跑一轮，什么也没干，token 账单翻倍。

本质区别一句话：**cron 是时间驱动，heartbeat 是状态驱动**。

## 做法与步骤

**cron：明确"几点干、干什么"**

1. 任务里写标准 cron 表达式，如 `30 8 * * *`；
2. payload 写清本次执行的动作或发给 agent 的指令；
3. 执行跑在独立会话里，不污染主对话上下文；
4. 适合：日报、周报、定时提醒、固定时刻的数据拉取。

**heartbeat：写清"什么条件算有事"**

1. 在心跳配置（如 HEARTBEAT.md）里写条件-动作规则，不要写抒情式描述；
2. agent 按固定间隔醒来，读规则、自查状态、决定干不干活；
3. 无事时静默返回，不产出回复；
4. 适合：未读消息巡检、磁盘/进程监控，一切"有活才干"类判断。

简单判断法：把需求念出来，如果出现"每天 X 点 / 每周一"，用 cron；如果是"每隔一会儿看一眼，有事再动"，用 heartbeat。

## 踩坑点

1. **时区**。容器里默认 UTC，cron 任务集体错位 8 小时。配置里显式指定时区，别赌系统默认值。
2. **心跳频率**。每次唤醒都是一轮完整的模型调用。从 30 分钟起步往下调，不要从 1 分钟开始往上压；高频采样交给脚本或工具，心跳只做决策。
3. **心跳指令太模糊**。写"看看有没有异常"，agent 每次都会长篇输出。规则要落成：条件 + 动作 + 无事静默。
4. **cron 失败静默**。任务挂了没人知道。关键任务接一条失败通知（消息通道或日志告警），比事后翻日志省太多时间。
5. **重复执行**。同一个动作既挂了 cron 又写进心跳，两头都触发。一个动作只挂一处，必须幂等的地方加去重键。

## 可复用建议

- 选型口诀：**时间驱动用 cron，条件驱动用 heartbeat**；
- 心跳规则模板：`当<条件成立>时执行<动作>；否则保持静默`；
- 心跳间隔宁长勿短，先保证账单可预期，再按需加密；
- 固定时刻的任务永远优先 cron，它比心跳更准、也更便宜；
- 排查定时问题时，先看执行日志里"触发时间"和"实际执行时间"的差值，能快速定位时区或频率问题。

## 总结

cron 和 heartbeat 不是二选一的竞品，而是分工明确的两种触发器：一个对表，一个对状态。把"几点干"交给 cron，把"要不要干"交给 heartbeat，定时自动化就能同时做到准点、省钱、可排查。
