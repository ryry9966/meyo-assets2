## 背景

在 OpenClaw 的自动化流程里，Agent 产出 Markdown 几乎是默认能力：日报、技术笔记、发布草稿都由模型直接生成。但"生成出来"和"发得出去"之间隔着一段被低估的工作——各平台的格式方言差异很大，同一段 Markdown 发到不同渠道，效果经常面目全非。

## 问题

我们实际碰到的问题集中在四类：

- **结构不稳定**：模型输出的标题层级有时从 h1 起步、有时从 h3 起步，frontmatter 时有时无、字段随意。
- **平台方言**：公众号编辑器只认内联样式，class 全被剥掉；知乎对 footnote 和部分 HTML 支持有限；静态站要 frontmatter/MDX；掘金吃 GFM 但嵌套列表渲染有出入。
- **图片链接最脆**：Agent 常引用外链或临时 URL，发布后失效。
- **正则替换必翻车**：在嵌套列表和表格上做字符串替换，迟早出事。

## 做法

整体思路是**一次归一化，多端适配**，管线分五步：

1. **归一化**：用 remark 生态把任意来源的 Markdown 解析成 mdast，先用 remark-lint 加自定义规则统一标题层级、列表缩进、代码块语言标注，并校验/补齐 frontmatter。这一步的输出就是管线的标准中间格式。
2. **AST 转换**：所有变换写成 mdast transformer（纯函数，输入 AST 输出新 AST）。例如把 footnote 节点降级为尾注段落，把 HTML 注释指令解析成元数据后删除节点。
3. **平台适配器**：每个目标平台一个小模块——公众号走 mdast → 全内联样式 HTML；知乎/掘金走 mdast → 裁剪版 Markdown（不支持的节点显式降级）；静态站生成带 frontmatter 的 MDX。适配器只做格式映射，不做业务判断。
4. **资源处理**：图片统一先下载、再按目标平台要求传图床、替换 AST 中的 URL；失败就报错终止，绝不带着死链发布。
5. **校验与发布**：发布前对输出跑一次目标平台的渲染 dry-run（至少 lint 一遍），diff 展示给人确认后才调发布接口。在 OpenClaw 里我们把整条管线包成一个 MCP tool，Agent 只负责产草稿，归一化和校验对它透明。

## 踩坑点

- 正则处理嵌套结构必翻车，所有变换坚持在 AST 上做。
- 公众号的粘贴链路会丢样式，必须生成全内联 style 的 HTML；测试别只看剪贴板方案，用编辑器实际粘贴或接口验证。
- 模型爱在 frontmatter 里加自由字段，schema 校验要 fail loudly——静默容忍会让下游取值出错。
- footnote、任务列表、数学公式是平台不支持的重灾区，适配器里给每个节点类型定义明确策略：降级、转换或拒绝发布。
- HTML 注释当私有指令很方便，但部分平台会原样渲染注释，输出前务必删干净。

## 可复用建议

- 建一个"金样例"语料库：几十篇覆盖表格、脚注、代码块、图片的文章，每次改管线跑一遍快照测试。
- 适配器保持纯函数并配单元测试，不要在适配器里发请求。
- 未支持的节点宁可让发布失败，也不要静默丢内容。
- 给管线配置加版本号，排查"上个月能发这个月不行"时先 diff 配置。

## 总结

这条管线的核心不是某个具体的库，而是三件事：**标准中间格式、纯函数适配器、发布前人工卡点**。AI 把内容生产成本压到接近零之后，格式适配和发布可靠性反而成了瓶颈。把这段管线固化下来，Agent 的产出才能真正稳定地进入发布环节。
