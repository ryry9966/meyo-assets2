## 背景

Agent 产出的内容几乎清一色是 Markdown，但落地端五花八门：公众号只接受内联样式的 HTML，掘金和知乎吃 Markdown 但语法子集不同，静态站点支持完整 GFM，邮件客户端对表格和代码块的处理又自成一派。第一篇内容往往手工搬一下就发了，到第三篇、第五篇，重复劳动和格式事故开始堆积，这时候就该把“格式适配”沉淀成管线了。

## 问题

实际做下来，难处是三层不确定性叠加：

1. LLM 输出本身不稳定：代码围栏不闭合、Markdown 里混 HTML、标题层级跳跃、该转义的字符不转义；
2. 平台方言差异：表格、脚注、外链、代码高亮的支持度各不相同；
3. 资源路径不同：图片在各平台的托管和防盗链策略完全不一样。

很多人的第一反应是正则加字符串替换，做两个平台之后嵌套代码块一出现就会误伤，这类脚本基本不可维护。

## 做法：四层管线

我的做法是分层，每层职责单一：

1. **规范化层**。把 LLM 输出当不可信输入处理：用 unified/remark 解析成 mdast，先修复再收紧——闭合围栏、拍平标题层级、剥离内联 HTML、统一列表缩进，最终收敛成一份内部“规范 Markdown”：frontmatter 约定元数据，语法走白名单子集（禁脚注、表格受限、图片一律用占位符）。
2. **AST 转换层**。所有平台差异都写成 mdast 上的纯函数 transformer。比如公众号适配器把 code 节点在构建期预渲染成带内联 style 的 span 序列；不支持表格的端把 table 节点降级成有序列表。
3. **资源层**。图片先落图床拿稳定 URL，需要的话再走平台素材接口二次上传换回平台链接，URL 替换仍然在 AST 里完成。
4. **校验与回写**。发布前跑一个 lint 工具（封装成 MCP tool），检查死链、超长段落、平台禁用语法；错误清单回传给 Agent，让它带着错误自修一轮再走发布节点。

在 OpenClaw 里这段可以编成一个 workflow：生成 → 规范化 → 按平台并行的适配 → lint → 发布。适配器全是无状态纯函数，Agent 只负责编排、重试和失败兜底。

## 踩坑记录

- 正则替换是最贵的坑，嵌套围栏和转义字符必炸，坚持 AST 操作一次到位。
- 公众号会剥掉 class 和外部 CSS，代码高亮必须在构建期烧成内联样式，运行时补是补不上的。
- 脚注语法各家实现不一致，与其做兼容不如在规范层直接禁用。
- 图片外链在不少平台是防盗链 403，别假设“贴个 URL 就能看”，一律走素材上传。
- frontmatter 不要裸奔，有些渲染器会把 `---` 当分隔线渲染出来。

## 可复用建议

- 把内部规范 Markdown 当接口文档写下来，同时贴进 Agent 的 system prompt，从源头减少脏输出。
- 每个适配器配 3~5 篇金样本（golden file），CI 里跑快照测试，平台改版时第一时间能发现。
- 适配器保持无状态、可单测；有状态的部分（重试、人工确认）才交给编排层。

## 总结

多平台发布的核心不是“写转换脚本”，而是先定义一个收敛的内部标准，再把平台差异隔离在薄薄的适配层里。管线每个环节可测、可回滚，Agent 的价值才能体现在编排和自愈上，而不是替你维护一堆越改越长的正则。
