## 背景

信息源越加越多，真正读完的比例越来越低。RSS 是目前少数结构稳定、无算法干预、可自托管的输入渠道；而 OpenClaw 的 cron 调度和 skill 机制，恰好适合把「定时拉取 → 清洗 → 摘要 → 推送」串成一条无人值守的管线。这篇记录我这套管线的实际做法，供想动手的参考。

## 问题

最直觉的做法是把 RSS 条目整段扔给模型。跑了一周就暴露出四个问题：

- **噪声大**：不少源只有 summary，里面嵌着 HTML 和推广文案；
- **重复多**：同一篇技术新闻会从三四个源进来；
- **成本高**：全部塞全文，一天轻松几十万 token；
- **产出不稳**：模型偶尔补出原文没有的结论，甚至编造链接。

所以管线的关键不是「接上模型」，而是把降噪和约束做在模型之前。

## 做法

分层结构，每层独立可替换：

1. **采集层**：自托管 Miniflux 聚合订阅源（部分站点用 RSSHub 转换），OPML 按主题分组。
2. **调度层**：写一个 `rss-digest` skill，cron 每 2 小时触发，只拉上次水位之后的新条目。
3. **清洗层**：对 summary-only 的源做全文抓取（readability 提取正文），HTML 转纯文本；`guid + 标题 hash` 双重去重后写入 SQLite。
4. **摘要层**：两级漏斗。第一级只用标题和原生摘要打分粗筛；第二级对入选条目（每天上限 30 篇）做全文摘要，输出固定 JSON：要点、为什么值得读、原文链接。
5. **分发层**：按主题合并成日报，推送到 Telegram；原始条目和摘要都落库存档。

## 踩坑点

- summary 里藏 HTML 和广告，直接喂模型效果很差，清洗层不能省。
- 跨源重复靠 guid 挡不住，加了一条标题相似度去重才干净。
- cron 偶发重叠导致重复推送，在 skill 入口加了幂等标记（当天已生成则跳过）。
- 模型编链接：prompt 强约束「只允许引用输入中出现的 URL」，代码层再校验链接是否在本次输入集合里，不在就丢弃该字段。
- token 靠「先便宜后贵」：粗筛用小模型，全文摘要才上大模型，并对全文长度截断。

## 可复用建议

- 管线做成配置驱动：feed 列表、打分阈值、推送目标都放配置文件，skill 代码不动。
- 原始条目一定要落库，摘要翻车时能回溯是源的问题还是 prompt 的问题。
- 攒一组固定的 20 条样本做回归：改 prompt 后跑一遍对比，避免修一处坏一处。
- prompt 里允许模型写「该文信息量不足」，宁可日报少一条，不要硬凑。

## 总结

这条管线没有单点黑科技，价值在分层：RSS 保证输入稳定，规则和去重负责降噪，模型只做它擅长的压缩。出问题时每一层都能单独排查和替换。如果你已经用 OpenClaw 跑过定时任务，加一个 skill 就能复用这套思路——建议从 5 个源开始小规模验证，再逐步扩。
