## 背景

过去一年本地推理的门槛明显降了：Ollama、llama.cpp 这类运行时已经成熟，7B~14B 级别的量化模型在消费级硬件上能跑到可用的速度。对我们这类跑 Agent、接 MCP 工具、写自动化脚本的用户来说，本地模型的价值不在"替代云端大模型"，而在三件事：高频调用不烧钱、数据不出门、断网也能跑。

## 问题：Agent 场景比聊天苛刻得多

很多人踩的第一个坑，是用"聊天体验"来评估本地模型。跑 Agent 完全是另一回事：

- 工具调用要稳定，模型得可靠地输出结构化参数；
- 上下文要长，MCP 工具描述加多轮中间结果，几万 token 很容易吃掉；
- 无人值守，自动化循环里一次格式错误就可能让整条流水线挂掉。

所以本地部署的核心矛盾不是"模型聪不聪明"，而是"在受限显存里，工具调用可靠性、上下文长度、速度三者如何取舍"。

## 做法

**1. 先算显存账。** 经验值：7B/8B 的 Q4 量化约需 6GB 显存，14B 约 10GB，32B 要 20GB 往上。注意这只是权重开销，KV cache 随上下文线性增长，32k 上下文可能额外吃掉好几 GB。Apple Silicon 用户按统一内存估算，给系统留一半。

**2. 选运行时。** Ollama 上手最快，自带 OpenAI 兼容接口；llama.cpp 控制粒度细，适合调参；vLLM 吞吐高但基本要求 Linux 加独显，适合当"家庭推理服务器"。个人建议从 Ollama 起步，遇到瓶颈再换。

**3. 选模型与量化。** Agent 场景优先看工具调用能力，Q4_K_M 是速度与质量较均衡的档位。中文环境下 Qwen 系列的小尺寸模型在函数调用上表现稳定，作为首选比较省心。

**4. 接入 OpenClaw。** 把模型配置指向本地 OpenAI 兼容端点（如 `http://localhost:11434/v1`）即可。先接一个最简单的 MCP server（比如 filesystem），手动跑通"模型 → 工具调用 → 结果回填"这条闭环，再上真实任务。

**5. 建最小验证集。** 从自己的 Agent 日志里挑 20 个真实场景（含工具调用、长上下文、边界 case），每次换模型、换量化、改参数都回归一遍。10 分钟得出的结论，比任何 benchmark 都可信。

## 踩坑点

- **默认上下文过短**：部分 Ollama 版本默认上下文很小，Agent 对话被静默截断，症状是"模型忘了系统提示"。务必显式设置上下文长度。
- **MCP 工具挂太多**：工具超过十几个，小模型的工具选择错误率明显上升。只挂载当前任务需要的工具，描述写短。
- **思考 token 失控**：推理型模型的思考过程会大量消耗上下文，自动化循环里要么关掉，要么设预算。
- **采样参数错配**：聊天常用的参数放到无人值守循环里容易复读，建议压低 temperature 并加重复惩罚。
- **磁盘与驱动**：几份量化就是几十上百 GB，注意缓存目录；WSL2 下 GPU 直通偶发异常，报错先查驱动。

## 可复用的建议

- **分层路由**：高频低难度任务（分类、摘要、格式化）走本地小模型，难步骤回退云端大模型，成本和可靠性都拿到。
- **锁定模型版本**：本地模型文件会随更新悄悄变化，自动化环境里固定 tag，升级走灰度。
- **长跑监控**：连续 Agent 任务跑几小时后留意显存/内存曲线，某些运行时在高频请求下有泄漏。
- **把换模型当成一次小型发布**：验证集回归 + 观察一天，而不是直接替换。

## 总结

家用电脑跑 7B~14B 本地模型，如今已是成熟的工程选项。瓶颈早已不是"能不能跑"，而是工具调用可靠性与上下文管理。把它当作容量规划问题来对待——算显存、建验证集、做分层路由——本地模型就能在 Agent 与自动化链路里，稳稳承担起属于它的那部分负载。
