## 背景

Agent 能调工具之后，真正的问题不再是"它能不能做到"，而是"它该不该自己做"。在 OpenClaw 这类框架里，插件和 MCP 工具一多，模型面对的就不只是一个对话接口，而是一排能直接改文件、发消息、动数据的开关。权限边界没设计好，出事只是时间问题。

## 问题：两个极端都不对

常见的翻车姿势有两种：

1. **全都要人确认。** 每一步都弹"是否继续？"。头两天你还认真看，第三天开始无脑点确认。Agent 变成一个更慢的 shell，人变成橡皮图章。
2. **全都自己干。** 直到某天它为了"清理临时文件"删了你没备份的目录，或者把草稿直接发进了客户群。

这两种其实是同一个病：把权限当成一个开关，而不是一套分级体系。

## 做法：三个维度定分级

我会用三个问题给每个工具动作定级：

- **可逆吗？** git 能 revert 的、有回收站的，算可逆；`rm`、`DELETE`、发出去的消息，不可逆。
- **半径多大？** 只动自己工作目录，半径小；动共享仓库、生产配置、别人能看到的内容，半径大。
- **有外部承诺吗？** 花钱、发消息、调第三方付费接口、任何"代表你"对外说的话，都算。

由此得出四档：

| 档位 | 动作类型 | 策略 |
|---|---|---|
| A | 只读（list / read / search） | 全自动，记日志 |
| B | 可逆、小半径写（工作区文件、草稿） | 自动执行，事后可查 |
| C | 不可逆或中半径写（删文件、push 主干） | 执行前问一次，必须带上下文 |
| D | 外部承诺（发消息、花钱、动生产） | 必须问，且展示"做什么、影响谁、花多少" |

落地步骤：

1. **在 MCP / 插件层配置白名单和参数约束**，而不是只写在 system prompt 里。prompt 是建议，运行时校验才是边界。
2. 给高危工具加 **dry-run 或两段式调用**：先返回 diff 和影响面，确认后再提交。
3. 加**批量阈值**：删 3 个文件自动放行，超过 10 个必须确认，防止 agent 把大操作拆成一百次小调用绕过闸门。
4. 确认时给人**足够信息**：影响范围、涉及条数、预估成本。只有一句"是否继续？"的确认等于没有。
5. 所有调用落日志，每周翻一次，按实际表现调整档位。

## 踩坑点

- **确认疲劳**：问得越多，人越不看。宁可少问，问就要值得看。
- **只靠 prompt 设边界**：换模型、长对话后边界会"漂"，模型可以被后续指令说服。硬约束必须落在工具层。
- **假只读**：有些接口 GET 一次就触发 webhook 或计费。接新工具前先验证副作用。
- **dry-run 不 dry**：我见过"预览"阶段已经把通知发出去的。两段式要保证第一阶段零副作用。
- **问得太晚**：活干了一半才来问，人没有上下文，只能瞎批。该问的节点要放在动手之前。

## 可复用建议

一句话版本：**读的自动，写的看半径，钱和对外必问，不可逆一律问。**

再补三条：

- 权限配置当代码管，进版本库，改档位要有 commit 记录。
- 新插件接入先按 B 档观察两周，再决定升档还是降档。
- 给每个工具写一行"副作用说明"，比任何长 prompt 都管用。

## 总结

权限边界不是限制 Agent 的能力，而是让它敢于在安全区里全自动跑。分好档、把约束放到运行时、确认时给足信息之后，你会发现真正需要人出手的场景其实很少，而且每一次出手，你都知道为什么。
