## 背景

团队里的"日报"大多靠人肉：翻 git 记录、翻运维群里的事件、回忆昨天 agent 跑了哪些任务，最后拼成一段格式随机的文字。写的人痛苦，看的人更痛苦——格式不固定，没法归档对比，也回答不了"上周三到底出了什么问题"。

我的思路是：日报不应该是"写"出来的，而应该是从既有数据里"编译"出来的。LLM 只负责最后一公里的措辞，而不是从原始日志里裸读。

## 问题

直接让 agent 读日志写日报，会遇到三个硬问题：

1. **日志量远超上下文**。一天的 journal 加 agent 会话记录轻松几十万行，塞不进去；塞进去了，关键事件也被心跳和健康检查淹没。
2. **输出格式漂移**。模型每次生成的结构都不一样，今天多一段"温馨提示"，明天少一个字段，没法 diff 和归档。
3. **事实性风险**。模型会把"重试 3 次后成功"脑补成"服务波动"，报告反而制造焦虑。

## 做法

核心原则：**规则能做的事不交给模型**。整条流水线分四段：

**① 采集**。在 OpenClaw 侧配一个定时任务，每天 07:30 触发。各采集源独立脚本：git log、journalctl 时间窗切片、agent 会话日志、MCP 工具调用记录，统一输出 JSON Lines（ISO 时间戳 + source 字段）。某个源挂了不影响其他源，缺源时在报告里标注"数据缺失"，而不是静默跳过。

**② 清洗与聚合**。这一步全是确定性脚本：按关键词剔除噪声（heartbeat、healthcheck、状态码 200 的访问日志），错误按类型聚合计数，长堆栈只留首帧和指纹。实测能把数据量砍掉 90% 以上，也是整条流水线里最值得花时间的地方。

**③ 模型摘要**。把清洗后的 JSON 喂给 agent，配一个固定的 JSON Schema 输出：`completed / incidents / risks / today_plan` 四个数组，每个条目带 severity 和 evidence 字段（引用清洗后数据的行号，方便回查）。temperature 压到 0.2 以下。

**④ 校验与落盘**。Schema 校验失败重试一次，再失败就降级为纯模板填充——宁可日报丑，不可日报错。产物是按日期命名的 markdown，写入归档目录，同时 webhook 推送到群里。

## 踩坑点

- **时区**。日志是 UTC，读者看 UTC+8，跨天边界的事件会归错日期。所有时间戳在清洗阶段统一转本地时区，再进模型。
- **脱敏必须放在进模型之前**。日志里的 token、内网 IP、客户名，靠 prompt 里写"请注意保密"是靠不住的，只能脚本正则替换。
- **幂等**。重跑任务时按日期覆盖旧报告，而不是追加，否则归档目录很快变成灾难现场。
- **控制篇幅**。异常前置、正常项折叠，超过一屏的日报等于没写。

## 可复用建议

- 固定的 JSON 中间 Schema 是整条流水线的解耦点：换模型、换模板、换推送渠道，上游一行不改。
- 清洗后的中间产物落盘保留一周，出错时可以离线重放，不用等第二天。
- 人工修正过的报告别浪费：diff 人工版和机器版，把高频修正点沉淀成清洗规则或 few-shot 示例——这是报告质量持续变好的主要来源。

## 总结

这套流水线跑下来，最深的体会是：日报自动化的质量上限不取决于模型多聪明，而取决于"原始日志 → 结构化数据"这一步做得多扎实。LLM 是流水线的最后一环，不是第一环。先把数据和 schema 立起来，模型的活儿其实很轻。
