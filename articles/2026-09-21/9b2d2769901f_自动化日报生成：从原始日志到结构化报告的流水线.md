## 背景

我们小组的日报一直是人肉流程：下班前翻 git 提交、CI 记录、值班群消息，拼成一段 Markdown 发出去。事情不大，但每天耗 20 分钟，还经常漏项。这篇记录我用 OpenClaw 搭的自动化流水线：从各处原始日志到结构化日报，已稳定运行一个多月。

## 问题

一开始试过"把日志直接丢给 Agent 写日报"，效果不行：

- 各来源格式不同（git log、CI JSON、聊天导出），模型大量 token 花在理解格式上；
- 一天的完整日志塞不进上下文，模型倾向于编造细节补空；
- 输出版式每次都不一样，没法归档和横向对比。

结论：LLM 只适合做"归纳"，不适合做采集、清洗和排版。

## 做法

流水线分五步，每步独立落盘，可单独调试重跑：

1. **采集**：用 OpenClaw 的 cron 调度，每天 07:30 通过 MCP 工具和 webhook 拉取前一日数据，原始文件写到 `daily/raw/YYYY-MM-DD/`。
2. **结构化（纯脚本）**：Python 脚本把各来源统一成 JSONL，字段固定 `time / source / actor / action / status / ref`，顺带做脱敏和时区归一。这一步全部是确定性代码，不经过模型。
3. **归纳（Agent）**：Agent 只接收 JSONL，prompt 里三条硬规则——只允许引用 entry id；无证据写"无记录"；输出限定为固定 JSON（今日变更 / 异常 / 待跟进）。数据多就分段 map 再 reduce。
4. **渲染**：日报版式由 Jinja2 模板锁死，Agent 的 JSON 只负责填空，格式从此稳定。
5. **投递与归档**：渲染成 Markdown，webhook 推送到群，同时 commit 到内部仓库；原始 JSONL 保留 30 天备查。

## 踩坑点

- **"今天"的边界**：跨时区服务和本地 cron 对不上，日报漏过昨晚 23 点后的提交。统一用 UTC 存储，按业务时区切时间窗口。
- **重复噪音**：CI 重试、告警反复触发会把归纳带偏。结构化阶段按 `ref` 去重，同 ref 只保留最终状态。
- **上下文溢出**：某天发大版本，日志量翻倍直接超限。改成按来源分组分片后解决，归纳质量反而更高。
- **幻觉**：早期没要求引用 id，日报出现过"修复了某问题"而日志里根本没有。加引用校验后，渲染前脚本检查 id 是否存在，不存在就拒绝发布。
- **静默失败**：流水线挂了没人发现，群里断更两天才被提。现在失败走独立告警通道，投递前校验产物非空。

## 可复用建议

- 阶段分离是核心：采集、清洗、归纳、排版各自留产物，任何一步都能重跑和回归。
- 把 prompt 当代码管理：进仓库、写注释，改动后用固定一天的真实数据做 fixture，跑完看 diff。
- 宁可日报"薄而准"，不要"全而虚"。结构化阶段多下功夫，归纳阶段的 token 和错误率都会明显下降。
- 从单一来源起步跑通全链路，再逐步加源，别一上来接五个系统。

## 总结

这套流水线没有黑魔法：90% 的工作是脚本和模板，LLM 只负责中间那层归纳。上线后日报从每天 20 分钟变成零操作，且因为引用可查，可信度比手写更高。Agent 适合做流水线上的"归纳工位"，而不是整条流水线本身。
