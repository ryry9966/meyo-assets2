## 背景

社区里做 Agent 的同学，精力大多花在工具调用和任务规划上，记忆往往是一个 `MEMORY.md` 往 context 里一塞就完事。短会话没问题，但助手一旦要用几周，就会发现它"好了伤疤忘了疼"：上周明明说过构建用 pnpm，这周又开始建议 npm。这不是模型问题，是工程问题。

## 问题

"记不住"通常出在三个环节：

1. **写入无门槛**：模型每轮自由决定记什么，要么什么都不记，要么把一次性任务上下文当成偏好存下来。
2. **读取无预算**：启动时把全部记忆塞进 system prompt，token 爆炸，新旧记忆矛盾时模型随机站队。
3. **没有遗忘与覆盖机制**：偏好会漂移，两年前的记录和昨天的记录权重相同。

## 做法：三层结构 + 受控读写

**第 1 层：结构化偏好档案（必做）**
一个 JSON/YAML 文件，只存稳定偏好：语言、代码风格、常用技术栈、回复语气。每条记录带 `key / value / confidence / source / updated_at`。会话启动时无条件注入，通常几百 token 就够。文件进版本库，可 diff、可回滚。

**第 2 层：情景记忆 + 定期蒸馏**
完整会话日志另存。跑一个离线任务（cron 或会话结束钩子），用固定 prompt 提取"候选偏好"，要求附带对话原文作证据，并区分"显式声明"（用户直说）和"推断"（观察多次）。候选写入第 1 层前先做 key 归一化去重；冲突时新时间戳覆盖旧值，旧值留历史。

**第 3 层：向量检索（可选）**
档案规模变大、出现大量项目级长尾上下文时再上 embedding。查询按相关度 + 时间衰减取 top-k，硬性限预算（比如 500 token），绝不全量注入。

**读写接口化**
把记忆做成 MCP 工具（`memory.get / memory.put / memory.delete / memory.search`），而不是让模型自由编辑文件。写入走 schema 校验；删除必须对用户可见。用户随时能说"忘掉 X"，且真的删掉。

## 踩坑点

- **记忆污染**：不约束"证据原文"，蒸馏步骤会把模型的猜测当事实存进去，之后每轮被强化。强制 `source` 字段能挡掉大半。
- **一次观察就下结论**：用户用了一次 vim 不代表偏好 vim。推断类记忆要求至少 2–3 次观察，confidence 初始给低。
- **key 不归一**："代码风格"和 `coding_style` 存成两条，检索时各取一半。先定义枚举 key 集合，新增 key 走显式合并。
- **蒸馏任务自己产生幻觉**：蒸馏模型与主 agent 分开，temperature 调低，输出只允许结构化 JSON，解析失败直接丢弃，不要重试硬塞。
- **没有删除入口**：记忆不可见、不可删，用户会直接失去信任，内部工具也一样。

## 可复用建议

- 先用单文件 + 手动确认跑两周，观察哪类偏好高频出现，再决定是否上向量库。多数个人助手场景，第 1 层就够了。
- 每条记忆是数据不是代码：带时间戳、置信度、来源；冲突策略写死在代码里，别靠 prompt 描述。
- 做回归测试：回放历史会话，断言助手在关键偏好上行为一致。记忆系统没有测试等于裸奔。
- 写入默认保守：用户显式说的话，永远优先于模型推断。

## 总结

让 Agent"记住你"，核心不是更大的 context，而是受控的写入门槛、带预算的读取策略、可审计可删除的数据结构。先用最土的文件方案把这三件事做对，再谈向量库和更花哨的检索。
