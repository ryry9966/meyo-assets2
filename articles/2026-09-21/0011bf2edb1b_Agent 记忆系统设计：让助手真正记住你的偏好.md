## 背景

Agent 的单轮能力已经不差，真正拉开体验差距的是跨会话记忆。你明明告诉过它"回答用中文、缩进用两空格、包管理用 pnpm"，下次新会话它照样从头问一遍。这不是模型问题，是工程问题：记忆没有被系统化地提取、更新和注入。

## 问题

三种常见做法都有坑：

1. **全量历史塞上下文**：token 成本线性上涨，噪声把真正的偏好淹没，长会话还容易被截断。
2. **写死在 system prompt**：撑得住十几条，撑不住上百条，且无法按用户和场景区分。
3. **一把梭向量检索**：所有记忆都走 RAG，召回一堆"语义相似但当前无用"的片段。更麻烦的是偏好类记忆在 embedding 空间里彼此是邻居——"喜欢简洁"和"喜欢详细"距离很近，检索反而制造冲突。

核心认知：**记忆 ≠ 历史记录**。记忆是从历史里蒸馏出来的、可结构化更新和遗忘的状态。

## 做法

一套跑通过的最小架构，五步：

**1. 分层存储**
- 偏好层：低频更新、强结构，KV 形式，如 `code_style.indent = 2`
- 事实层：会话中沉淀的具体信息，带时间戳，可过期
- 摘要层：滚动压缩的会话摘要

**2. 固定 Schema**
每条记忆统一为 `{key, value, confidence, occurrences, source, updated_at}`。key 必须是稳定的规范化命名，不要让模型自由发挥——这是后面去重的地基。

**3. 低频蒸馏，而非实时提取**
每轮都调提取，又贵又抖。实际做法是会话结束或每 N 轮触发一次蒸馏调用（用便宜的小模型足够），输入近期对话，输出结构化的记忆变更列表。

**4. 冲突用覆盖，不用追加**
新偏好与旧偏好冲突时，按 `confidence` + `occurrences` 决策：次数多、置信高的覆盖旧的，保留 `updated_at` 便于追溯。一次性请求（"这次输出长一点"）不进偏好层，靠 occurrences 计数自然过滤。

**5. 注入分层**
偏好层走**确定性注入**：会话启动时按 key 拉取，拼进 system prompt 或通过 MCP resource 提供，并设条数上限（比如 20 条）。只有事实层才走向量检索。

另外两个必备件：**遗忘机制**（TTL + 引用计数，长期未命中且低置信的降权归档）和**用户可见可编辑**（给一个 memory 列表视图，能删能改，封装成一个小型 MCP server 或插件暴露即可）。

## 踩坑点

- key 设计太随意，"缩进偏好"存出五种表述，事后去重的成本远高于一开始定 schema
- 模型把临时指令当长期偏好提取，`occurrences` 字段别省
- 偏好走了向量检索，语义邻居互相打架——偏好必须确定性注入
- 注入条数不设上限，50 条记忆进去，指令遵循明显劣化
- 多会话并发写同一 key，简单方案是按 `updated_at` 后写优先 + 单写者队列
- 无差别提取把密钥、密码也存进去了：提取 prompt 里加敏感信息过滤规则，写入前再过一遍正则

## 可复用建议

- 先做偏好 KV + 确定性注入，一两周能跑通，收益最直接；向量层后加
- 蒸馏用小模型，成本可以压到忽略不计
- 记忆导出/清除做成一等能力，既是信任问题也是合规需要
- key 命名空间化：`code_style.*`、`comm.*`、`env.*`，便于批量管理

## 总结

Agent 记忆的本质是**有纪律的状态管理**，不是把数据攒起来。键值偏好层能解决 80% 的"记住我"问题，剩下的再按需引入检索和遗忘。先跑通最小闭环，再谈智能。
