## 背景

我的信息源长期散落在各处：技术博客、GitHub Release、几个邮件列表。RSS 是其中唯一长期稳定、无算法干预的分发方式，问题只在"刷不过来"。这次的目标很克制：不做通用阅读助手，只做一条每天定时跑的管线——聚合、过滤、摘要，最后产出一份日报推送到群里。

## 问题

动手前列了几个明确的失败模式：

1. 相当一部分 feed 只输出截断的 summary，直接喂给模型等于让它复述半篇文章；
2. 同一篇文章常被多个源重复收录，去重必须放在摘要之前，否则纯烧 token；
3. 全量摘要不现实，两三百条/天，成本和延迟都不可接受；
4. 模型偶尔会"补写"原文没有的结论或链接，这类幻觉在日报场景里杀伤力最大。

## 做法

管线分四段，各自独立：

- **拉取层**：自托管 Miniflux 做 feed 聚合，它本身处理了大量 feed 兼容性问题；OpenClaw 侧定时通过 REST API 拉未读条目。
- **清洗层**：readability 提取正文；URL 去掉 utm 参数后规范化，取 hash 存 SQLite，主键冲突即跳过。正文抓取失败的条目记日志后丢弃。
- **过滤层**：两段式。第一段纯规则——关键词、来源权重、发布时间，打粗分；第二段用便宜模型对粗分通过的条目打分排序，只有头部条目进入摘要。
- **摘要与输出**：把 `fetch_unread`、`summarize_batch`、`push_digest` 封装成 MCP tools，agent 只负责编排。日报按得分排序生成 Markdown，webhook 推送。

把逻辑收敛到 MCP 工具层有个附带好处：cron 脚本和日常对话里 agent 复用同一套工具，不用维护两份逻辑。

## 踩坑点

- **summary-only feed 是最大的坑**。不做正文抓取，摘要质量直接塌方。个别站点反爬严，抓不到就丢弃并记录，不要让模型硬编。
- **去重必须先规范化 URL**，否则带不同追踪参数的同一篇会被当成两条。
- **摘要 prompt 必须显式约束**："只基于给定文本归纳，禁止输出原文没有的链接和数据"。早期版本出过模型自己编摘要链接的事故。
- **限流**：批处理 + 指数退避。日报是异步任务，慢十分钟无所谓，稳定优先。
- **feed 本身是脏的**：CDATA、非法实体、编码错误都遇到过，用宽容解析器，解析失败的源单独监控。

## 可复用建议

1. 各阶段做成幂等，SQLite append-only 存原始内容和摘要，管线挂了可以无损重放；
2. 成本控制的核心是"先规则后模型"，不要一上来就全量调 LLM；
3. 工具逻辑放 MCP 层，编排层（cron / 对话）随时可换；
4. prompt 带版本号，和输出一起落库，调优时有据可查。

## 总结

这条管线代码量不大，真正的时间花在去重、成本和防幻觉这些工程细节上。RSS 这种老协议配 agent 的压缩归纳能力依然好用，前提是想清楚分工：抓取、清洗、存储交给确定性代码，模型只做它擅长且可校验的部分。
