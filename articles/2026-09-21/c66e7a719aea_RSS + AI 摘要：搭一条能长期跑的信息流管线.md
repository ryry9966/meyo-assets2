## 背景

做技术的人大多有信息焦虑。RSS 看起来过时，但它依然是控制感最强的订阅方式：源自己选、格式标准化、没有算法插手。问题从来不在 RSS，而在"订阅了没时间读"。

我过去几个月在 OpenClaw 里搭了一条 RSS + LLM 摘要的自动化管线，每天早上产出一份按相关性排序的摘要日报，平时也能让 Agent 按需查询。思路不新鲜，但有些工程细节值得记录。

## 问题

直接"抓 RSS → 扔给 LLM → 输出摘要"能跑，但会遇到几个现实问题：

1. 很多站点不提供全文 feed，LLM 拿到的信息本身残缺；
2. 订阅源一多，token 成本和摘要长度都会失控；
3. 通用摘要模板产出的内容"什么都对，但没什么用"，无法帮你做取舍；
4. 网页正文里可能藏 prompt 注入，摘要任务容易被带偏。

## 做法

管线拆成四个独立阶段，中间用 SQLite 落盘，任何一步坏了可以单独重跑：

**抓取**：cron 定时拉 feed，不提供 RSS 的站点用 RSSHub 兜底。按 GUID/链接去重，原始内容永远先存库——摘要是可丢弃的，原文不能丢。

**预处理**：对只有摘要的 feed 回抓原文正文（Readability 类提取），截断到固定长度，代码块优先保留。这一步决定摘要的质量上限。

**摘要**：两级模型策略。便宜模型先做分类打分（是否命中我的关注列表，0–10 分），低于阈值直接丢弃；过线的再用强模型产出结构化 JSON：一句话结论、关键变化、与已有认知的差异、原文链接。提示词里明确"只基于给定文本，信息不足就标记 incomplete"，并用分隔符包裹正文，声明它是数据不是指令。

**投递**：每天固定时间汇总成 Markdown 日报推送；同时把"查询近 N 天摘要"封装成一个 MCP tool，Agent 在对话里可以直接回答"今天有什么值得看的"。

## 踩坑点

- **去重不能只看标题**：同一篇博客常被多个源转载，链接才是主键，标题相似度做辅助。
- **feed 的时间字段很脏**：时区缺失、日期在未来都有，落库时统一转 UTC，抓取窗口放宽到 48 小时，靠去重兜底。
- **抓取别太猛**：有些站会封高频请求的 UA，加随机间隔和合理的 User-Agent，比事后处理封禁便宜得多。
- **成本失控通常源于不筛就摘要**：先把打分做便宜，强模型只服务少数过线内容，日成本才能基本恒定。
- **注入比想象中常见**：技术文章里贴一段"ignore previous instructions"并不罕见，分隔符 + 明确角色声明是底线。
- **日报长了就没人看**：硬性上限 10 条，按分数排序，剩下的入库备查。

## 可复用建议

- 阶段之间用数据库解耦，每层幂等可重放，这是管线能长期跑的前提。
- 从 10–20 个源开始，跑两周再扩。信源质量决定上限，管线只决定下限。
- 结构化输出（JSON）比自由文本好用得多，后续的过滤、排序、统计都靠它。
- 记录哪些条目被自己点开过，定期清理从不产生价值的源——这是唯一需要的反馈回路。

## 总结

这条管线没有用到任何新东西：RSS、cron、SQLite、两次 LLM 调用。它的价值在于把"信息获取"从每天的主观消耗，变成一次配置好的基础设施——你只需要维护信源列表和提示词，其余交给管线。工程上最大的心得是：先保证原文落盘和阶段解耦，摘要质量可以慢慢迭代，架构返工才是最贵的。
