## 背景

跑过常驻 agent 的都知道一个前置问题：模型本身不会"挂机等待"，每次干活都需要一次触发。工程上触发源只有两类——**定时轮询（heartbeat）**和**事件推送**。OpenClaw 这类网关默认给的是前者：按固定间隔唤醒 agent，读一份任务清单，决定做事还是沉默。但什么时候该从轮询升级到推送、还是干脆混合，社区里问的人不少，实际踩过的坑更多。

## 问题

我在自己的部署里做过统计：30 分钟一次 heartbeat，一天 48 次唤醒，其中 **80% 以上是空转**——唤醒、读清单、无事可做、结束。每次空转照样烧 token 和上下文。但如果把间隔拉长到 2 小时，提醒类任务的延迟又不可接受。

反过来，纯推送也有代价：需要公网可达的入口、签名鉴权、离线时丢事件的处理。Git push 可以 webhook，但"每天早上八点给我日报"这种时钟驱动的事，推送根本覆盖不了。

结论先行：**这不是二选一，而是分层**。

## 做法

1. **先分类触发源。** 拿张纸列出 agent 要响应的所有事情，分成两栏：时间驱动（日报、定时提醒、周期巡检）和事件驱动（新邮件、CI 失败、消息到达）。事件驱动里再按延迟敏感度分级——秒级需要的和容忍几分钟的是两回事。

2. **heartbeat 做基线。** 固定间隔（个人场景 30 分钟足够），唤醒后读任务清单文件，每条带过期时间和优先级，无事则直接静默。关键约束：heartbeat 用独立的轻量上下文，不要复用主会话，否则每半小时污染一次主对话。

3. **推送补延迟敏感场景。** Webhook 接收器收到事件后**先落盘**（文件或 SQLite 都行），再触发即时唤醒。注意顺序：先持久化再唤醒，唤醒失败事件不丢。

4. **heartbeat 兼任对账。** 每次唤醒顺带扫描队列里未消费的事件，作为推送失败时的兜底。这套"推送保及时、轮询保可靠"的结构，跑了一个多月没丢过事件。

## 踩坑点

- **唤醒即烧钱。** 早期我把 heartbeat 挂在主会话上，一周下来上下文膨胀、响应质量明显下降。拆分会话后立竿见影。
- **清单文件腐化。** 没加过期时间的任务条目堆积到 40 多条，agent 开始对过期任务"认真执行"。条目必须带 TTL。
- **推送丢失。** 第一版队列放内存，网关重启全丢。任何 push 都按 at-least-once 设计，靠 heartbeat 对账兜底。
- **公网入口裸奔。** Webhook 没做签名校验，被扫到了就是别人免费使唤你的 agent。签名 + 时间戳防重放，五分钟能写完，必须写。
- **间隔抖动。** 跑了多个 agent 实例后，整点唤醒撞在一起，API 限流。间隔加随机偏移即可。

## 可复用建议

- 默认方案就选 **30 分钟 heartbeat + 带过期时间的文件清单**，覆盖个人自动化的 80% 场景，不要一上来就搞推送。
- 只有延迟要求在分钟级以内的事件才值得接推送，每个推送源单独评估接入成本。
- 盯三个指标：**空转率**（过高说明该降频或清理清单）、**单次 heartbeat token 成本**、**连续失败次数**（连续 3 次失败要报警，可能清单格式坏了或网关异常）。
- 队列持久化 + heartbeat 对账，是这套设计里唯一不能省的部分。

## 总结

heartbeat 是底座，推送是优化。轮询解决"可靠且简单"，推送解决"及时"，而工程上的正确答案通常是：推送负责快，轮询负责稳，中间用持久化队列和定期对账把两者缝起来。先跑通最朴素的轮询，等真实延迟痛点出现了再逐个接推送源——这个顺序反过来做，大概率会为用不上的及时性付出不该付的复杂度。
