## 背景

跑 Agent 做自动化时，有两个场景让我认真考虑本地模型：一是定时任务高频调用，API 费用累积不低；二是涉及本地文件、剪贴板、私人数据的 MCP 工具调用，数据不想出网。于是花了两周，在一台家用机上做了完整验证，这篇是记录。

## 硬件与软件基线

- 32GB 内存的笔记本（无独显）+ 一台 12GB 显存的台式机
- 推理框架用 Ollama（省事）和 llama.cpp（可控），对外统一暴露 OpenAI 兼容接口
- 模型跑了 Qwen2.5-14B-Instruct Q4_K_M 和 7B 版本各一轮

结论先行：Agent 场景下，14B Q4 是"能用"的下限，7B 只适合分类、摘要这类单轮任务。

## 部署步骤

1. 安装 Ollama，`ollama pull` 拉模型，确认 `curl localhost:11434/v1/models` 能列出模型
2. Agent 配置里把 base_url 指向本地端点，模型名对应上
3. 先跑不带工具的对话冒烟测试，再挂一个最简单的 MCP 工具（读本地文件）验证 tool calling
4. 观察 prefill/decode 速度和首 token 延迟，llama.cpp 加 `--verbose` 看日志
5. 稳定后再接入正式自动化流程

## 踩坑点

- **KV cache 吃内存超预期**。14B Q4 权重约 9GB，但 32k 上下文的 KV cache 还要再吃几个 GB，不够时会静默降级或 OOM。上下文按实际需要给，别无脑拉满。
- **小模型的 tool calling 很脆**。7B 经常漏参数、编造参数名，或输出混入自然语言导致 JSON 解析失败。解法：工具描述写严格、限制工具数量、Agent 层加 schema 校验和一次重试。
- **Ollama 默认 keep_alive 会卸载模型**，隔几分钟再调用要重新加载，首 token 从 1 秒变 20 秒。显存够就设 `OLLAMA_KEEP_ALIVE=-1`。
- **并发约等于没有**。本地推理是串行的，别在 Agent 里设计并行调用同一模型的分支，老老实实排队。
- **量化差异真实存在**。同型号不同量化在工具调用成功率上差异明显，Q4 以下别指望稳定的 function calling。

## 可复用建议

- **按任务难度分层路由**：简单任务走 7B，工具调用走 14B，复杂规划走云端 API，成本和延迟都能打下来。
- **统一用 OpenAI 兼容格式暴露端点**，Agent 侧只改 base_url，切换成本最低。
- **建一个 20 条左右的工具调用测试集**，每次换模型或量化跑一遍，成功率低于 90% 就换。
- **显存/内存预算公式**：权重 + KV cache + 系统占用，再留 20% 余量。

## 总结

本地 LLM 不是替代云端，而是给 Agent 体系补一层"便宜、离线、私有"的执行层。14B 量化模型 + OpenAI 兼容端点 + 严格的工具校验，就能撑起大部分日常自动化。别追求在本地跑最大的模型——把小模型在明确边界内用稳，比什么都重要。
