## 背景

OpenClaw 的 agent 自带 heartbeat：每隔一段时间被唤醒一次，检查 HEARTBEAT.md 里的待办、核对定时任务的产出。这是一个典型的轮询模型——简单、可预期，但用久了大家都会冒出同一个念头：能不能改成事件驱动，有事才醒，没事别吵？

## 问题

两种机制的代价都很真实：

**轮询**：每次唤醒就是一次完整的模型调用。默认 30 分钟一跳问题不大，但有人为了“及时”调成 1 分钟一跳，token 开销直接上一个数量级，且绝大多数唤醒是无事发生的空转。

**推送**：及时、空闲时零消耗，但前提是事件源“够得着”你的 agent——要么暴露 webhook 入口，要么中间加转发层。链路一长，丢事件、重复投递、重试风暴这些分布式老问题全回来了。

先回答一个前置问题：你的事件到底需要多快的响应？多数自动化场景并不需要秒级，想清楚这一点，选择就少了一大半。

## 做法

我的方案是混合式，一句话：**push 触发，poll 兜底**。

1. **先给事件分类。** 用户消息这类强实时输入，本来就由渠道适配器推给 agent，不用动。剩下的多是软实时——邮件汇总、仓库巡检、日程核对——轮询完全够。
2. **让心跳保持便宜。** 心跳间隔按实际需求配（我用 30 分钟）；HEARTBEAT.md 写成短清单，只放真正需要周期核对的事；无事发生就静默返回，不产出内容。
3. **确需及时性的走推送。** 例如 GitHub webhook → 一个几十行的转发脚本 → 经 Gateway 把事件摘要投递给 agent，秒级到达。
4. **轮询负责对账。** 在 HEARTBEAT.md 里加一条“核对最近的推送是否都已处理”，相当于 dead-man's switch。推送丢了，下一轮轮询能捡回来。

## 踩坑点

- **HEARTBEAT.md 会膨胀。** 什么都往里塞，agent 每次唤醒都要读一大坨上下文。定期清理，超过一屏就拆走。
- **上了推送就砍轮询。** 有人配好 webhook 就把心跳间隔拉到几小时，转发脚本崩了半天没人发现。推送可靠性没验证之前，轮询是保险，别拆。
- **重试 + 对账 = 重复执行。** webhook 重试一次，轮询又补一次，agent 把同一件事干两遍。凡是 agent 要执行的动作，务必带幂等键，最简单的做法是按事件 ID 去重。
- **心跳污染主会话。** 唤醒与用户对话共享 session，空转记录多了会稀释上下文。心跳指令保持定向，禁止它闲聊。
- **时区。** 定时任务显式写时区，夏令时切换那一周重点盯一次。

## 可复用建议

- 延迟要求落在轮询间隔可接受范围内 → 用轮询；超出才引入推送。
- 改间隔前先跑几天唤醒日志，看每次唤醒的实际决策，用数据说话。
- 幂等是底线：事件带 ID，执行前查重。
- 心跳文件是清单，不是日记。

## 总结

轮询和推送不是二选一，工程上稳的形态是分工：推送管“快”，心跳轮询管“不丢”。前者负责及时触发，后者负责对账兜底。把事件的延迟要求和可靠性预算想清楚，这个取舍其实并不难。
