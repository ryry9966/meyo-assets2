## 背景

个人项目和小团队仓库里，Git 日常操作其实很机械：写提交信息、切分支、清理合并后的旧分支。单次耗时不长，但频繁打断心流。Agent 框架成熟后（本地助手 + MCP git 工具或自定义 skill），把这部分交出去是顺理成章的事。过去半年我在三个个人仓库上跑了一套方案，这里记录做法和教训。

## 问题

手工维护的痛点集中在四处：

1. 提交信息质量不稳定，回看 history 全是 "fix"、"update"；
2. 忘记开分支，顺手就在 main 上改；
3. 合并完的分支堆积，几个月后不敢删；
4. 让 agent 直接跑 shell 执行 git，风险不可控（force push、`reset --hard`）。

## 做法

**1. 收敛工具面，不给裸 shell。** 用 MCP git server 或自己包一层插件，只暴露 `status` / `diff` / `add` / `commit` / `branch` / `log` 这类白名单命令。这是整个方案的安全底座。

**2. 用配置固化提交规范。** 在 skill 指令文件里写清 Conventional Commits 格式、scope 列表、语言要求，并强制 agent 基于当前 staged diff 生成信息；diff 超过 300 行时先输出摘要，用户确认后再提交。

**3. 分支策略写成规则。** 动手前先查工作区，发现停在默认分支就自动 `git switch -c feature/xxx`；合并后由 agent 列出 `--merged` 分支，经确认再删。删除永远走人工确认。

**4. 写操作走单入口。** 插件里一个 `git_exec()` 统一做三件事：白名单校验、参数黑名单（`--force`、`reset --hard`、`clean -fd`、`branch -D`）、写审计日志。本地 commit 可以全自动，push 一律推到聊天渠道等用户确认。

**5. 挂一道密钥扫描。** commit 入口前跑 gitleaks，命中即中止。agent 不一定知道 `.env` 不该进仓库，这层要外部兜底。

## 踩坑点

- **用旧 diff 写提交信息。** agent 拿到的是几分钟前的上下文，期间文件又改了，信息就对不上。解法：commit 前强制重取 diff，禁止模型"回忆"。
- **index.lock 冲突。** 定时任务和交互会话同时跑 git 会撞锁，后来改成单队列串行执行才稳定。
- **自动 rebase 共享分支。** 有一次 agent 自作主张 rebase 了已推送的分支，协作者拉代码直接冲突。规则改为：已推送分支只允许 merge，rebase 需显式授权。
- **大仓库 diff 爆上下文。** 按 `--stat` 分级，先看概览，需要细节再分文件取。

## 可复用建议

- 策略放配置文件（白名单、保护分支、命名规范）并纳入版本管理，别散落在提示词里；
- 先只读（状态汇报、log 摘要）跑一周，再逐步放开写权限；
- 自动化分级：本地 commit 全自动、push 半自动、删除和 rebase 全人工；
- 所有 agent 触发的 git 操作留审计日志，出问题能回放。

## 总结

Git 自动化不适合"一步到位"，适合"逐步放权"。工具面收窄、策略进配置、写操作过单入口、高危动作留人工，做到这四点，agent 管提交和分支是稳的。收益不是省几秒钟，而是提交历史终于可读、分支列表终于敢清理——这类"还债式"收益会持续累积。
