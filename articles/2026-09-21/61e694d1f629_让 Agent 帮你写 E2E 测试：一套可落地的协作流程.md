## 背景

E2E 测试长期处于"重要但没人爱写"的位置：选择器脆、跑得慢、维护成本高，业务一改版就成片变红。过去靠人肉补用例，投入产出比太低。现在有了带浏览器控制能力的 MCP 工具和能读代码库的 Agent，这笔工程账终于算得过来了——但前提是把 Agent 当协作方，而不是一键生成器。

## 问题

我们团队先踩的坑，就是直接让 AI"根据页面生成完整 E2E 测试"。三类问题集中爆发：

1. 代码看着像，跑不起来：调用不存在的组件方法、凭空捏造路由；
2. 选择器全靠 CSS 类名和元素位置，页面一抖就 flaky；
3. 断言极弱，只验证"页面没报错"，业务结果对不对完全不管。

结论很直接：缺上下文、缺约定、缺验证闭环，Agent 产出的测试就是负资产。

## 做法

把流程拆成五步，Agent 和人各管一段：

**第一步，人定范围。** 从业务里挑 3~5 条核心用户旅程（登录-下单-支付这种），写清前置条件、操作步骤、预期结果。这步不交给 AI，范围错了后面全错。

**第二步，喂上下文。** 把路由表、组件库约定、现有测试规范整理成仓库内的约定文档（比如 AGENTS.md），让 Agent 按需读取，而不是把整个 repo 灌进去。

**第三步，Agent 探路径。** 通过浏览器类 MCP 工具让 Agent 实际走一遍操作流程，输出结构化的操作序列（页面-动作-元素-等待条件）。人先审这个中间产物，成本低、纠错快。

**第四步，生成代码。** 让 Agent 基于操作序列生成 Page Object 和用例，约定写死：交互元素必须用 `data-testid`，断言必须落到业务结果（订单状态、落库数据、接口返回），禁止 sleep 轮询。

**第五步，闭环验证。** 本地跑一遍，红了就把失败截图和 trace 文件喂回 Agent 做 triage，区分产品 bug 和测试腐化。CI 接入后，失败用例的初步归因也复用同一套流程。

## 踩坑点

- **幻觉代码必须跑过才算数。** 一次都没执行过的生成用例，不要进主干。
- **弱断言是隐形债。** review 时专盯断言部分，"页面可见"级别的直接打回。
- **别让 Agent 自己加重试掩盖 flaky。** 加重试要人批，先查清是环境问题还是选择器问题。
- **测试数据要显式约定。** Agent 不知道你的 seed 和 fixture，不提前写进约定文档，它就会现场造数据污染环境。
- **上下文按需给。** 一次塞太多，Agent 会混淆组件来源；按页面/模块切分投喂效果明显更好。

## 可复用建议

- 测试规范固化成仓库文档，Agent 每次读、团队新人也能读，一份投入两份收益。
- 拆成两个子 Agent：一个负责从操作序列生成用例，一个负责跑测试、读 trace、修失败，职责单一效果稳定。
- 中间产物（操作序列 JSON）单独保存，页面改版时只重新生成代码层，路径层可以复用。
- 人始终 review 两样东西：**测试范围**和**断言**，其余可以放手。

## 总结

Agent 写 E2E 的价值不在"零人力"，而在把最烦的部分——探路径、生成模板、失败初筛——自动化掉，让人集中在定范围和审断言上。先从一条用户旅程试点，流程跑顺再扩，比一次性全量生成靠谱得多。
