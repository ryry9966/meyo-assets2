## 背景

单一 Agent 串行干活的瓶颈很明显：任务一长，上下文被中间产物塞满，工具调用一个接一个排队，批量任务跑下来动辄半小时起步。OpenClaw 的 agent 体系支持主 agent 派生 subagent，这让我们可以把"能拆的任务"真正并行起来，而不是让一个 agent 从头憋到尾。

## 我们遇到的问题

一个典型场景：让 agent 一次性调研 5 个 MCP 服务的接口并生成接入代码。串行跑有两个毛病——主 agent 的上下文被 5 份中间笔记占满，后半程开始遗忘前面的约束；总耗时也是 5 段叠加。我们尝试用 subagent 并行化，过程有些坑值得记录。

## 做法与步骤

1. **拆任务**：主 agent 先把目标切成若干"自包含"的子任务。每个子任务的 prompt 必须写清目标、输入、约束、输出格式，不假设 subagent 能看到父级上下文。
2. **并行派发**：同时 spawn 3–5 个 subagent，每个绑定独立工作目录（如 `workspace/task-01/`），从源头避免写冲突。
3. **限制回传体积**：要求 subagent 只返回结构化摘要（JSON：结论 + 关键文件路径 + 遗留问题），不回传完整过程。
4. **聚合与验收**：主 agent 收齐结果后统一校验，跑一遍集成测试，失败项单独起一个修复 subagent，而不是原地返工。
5. **兜底**：每个 subagent 设超时与重试上限，单个失败不阻塞整批。

## 踩坑点

- **共享文件冲突**：最初所有 subagent 写同一目录，git index 频繁锁死。改成每任务独立目录后彻底消失。
- **上下文反噬**：5 个 subagent 各回传 3k token，主 agent 立刻臃肿。强制"摘要 ≤ 500 token"是关键约束。
- **隐式上下文假设**：subagent 不知道项目约定，代码风格、目录结构必须在 prompt 里显式带上，宁可重复。
- **并发配额**：并行 8 个时触发了模型端速率限制，后来固定在 3–5 个，收益已经够高。
- **部分失败**：要有"3/5 成功也先聚合"的策略，别让一个失败废掉整轮。

## 可复用建议

- 沉淀一个 subagent prompt 模板：目标 / 输入 / 约束 / 输出格式 / 完成标准，五段式，每次派发只改参数。
- 优先并行化"读多写少"的任务（调研、评审、批量生成）；有共享状态的写任务放最后串行做。
- 每次派发记录 task id 和 prompt 快照，出问题时能复盘到底是拆分问题还是执行问题。
- 从 2–3 个并发起步，压测稳定后再加，不要一上来拉满。

## 总结

subagent 编排不是"多开几个 AI"这么简单，本质是工程上的任务拆分 + 上下文隔离 + 结果收敛三件事。把拆分粒度、回传协议、失败兜底定义清楚，并行收益才真正落得到地上。我们这批接入任务的总耗时从 40 分钟左右压到 12 分钟，而且主 agent 的上下文干净了很多，后续多轮迭代的稳定性也明显变好。建议大家在跑长任务前先问一句：这活儿拆得开吗？拆得开就别串行。
