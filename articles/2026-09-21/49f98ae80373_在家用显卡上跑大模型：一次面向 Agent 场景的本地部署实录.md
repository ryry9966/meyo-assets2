# 背景与动机

跑 Agent 的都知道，LLM 调用是最大的变动成本。MCP 工具链一挂，一个自动化流程动辄几十次调用：任务拆解、规划、每次工具往返都要过一遍模型。云端 API 用着省心，但两个问题一直没解决：一是隐私——日志、截图、本地文件路径全都要喂出去；二是频率——调试插件时反复跑流程，限流和账单都难受。

所以我花了个周末，把一台 16GB 显存的家用机改造成本地推理节点，让 OpenClaw 的部分调用走 localhost。这篇记录过程和踩坑，供同好参考。

# 硬件与选型：从显存倒推

结论先行：显存决定一切。

- **8GB**：7B 模型 Q4 量化，可用，但 tool calling 稳定性一般
- **12–16GB**：14B Q4_K_M 是甜点位，权重约 9GB，还能留出上下文空间
- **24GB+**：可以碰 32B，或者 14B 跑长上下文
- **Mac 统一内存**：按可用内存的 60% 做预算

模型我选了 Qwen 系列的 14B Instruct，理由很直接：中文场景下的工具调用格式遵循明显好于同档位的其他开源模型，这对 Agent 是硬指标。

# 部署步骤

1. **选运行时**。Ollama 省心，llama.cpp 可控（能精确调 KV cache），vLLM 吞吐高但吃显存。家用单机从 Ollama 起步即可。
2. **拉模型、起服务**。`ollama pull` 后自带 OpenAI 兼容端点（`localhost:11434/v1`）。
3. **改 Agent 配置**。把 base_url 指到本地，API key 填占位符即可。关键是 `num_ctx` 要显式调大，后面讲为什么。
4. **先 curl 验证 tool calling**。别直接上 Agent，先发一条带 `tools` 参数的请求，确认模型能返回合法的 function call。这一步能提前过滤 80% 的问题。
5. **接 MCP，跑最小闭环**。挂一两个只读工具（比如文件列表），跑通「规划 → 调用 → 观察 → 再规划」一整圈，再逐步加工具。

# 踩坑实录

- **上下文是隐形杀手**。默认上下文只有 4K，Agent 循环几轮就静默截断——不报错，模型只是开始「失忆」。把 `num_ctx` 拉到 16K/32K 后，KV cache 显存占用成倍增长，16GB 卡跑 14B 会直接 OOM。我的平衡点是 14B + 16K，刚好卡进显存。
- **小模型的工具参数幻觉**。14B 偶尔会编造文件路径、填错枚举值。解法不是换更大的模型，而是在工具层加 schema 校验加一次重试，把报错喂回去让它自己修。实测成功率从约 85% 拉到 97% 以上。
- **并发即串行**。单卡基本一次只跑一个请求，Agent 里并行开子任务，本地模型会排队，整体延迟反而不如串行编排。自动化流程要按「本地单并发」来设计。
- **温度与格式漂移**。temperature 超过 0.7，工具调用的 JSON 偶尔崩。Agent 场景建议压到 0.2 以下。
- **keep_alive**。默认几分钟不用就卸载模型，下次调用冷启动十几秒。长驻自动化记得设 `keep_alive: -1`。

# 可复用的建议

1. **混合路由比全本地更务实**。本地跑高频低敏任务（格式化、摘要、简单工具链），规划类重任务仍走云端。按任务分档，不要非此即彼。
2. **建一个 15 条左右的 tool-calling 评测集**。每次换模型或量化版本先跑一遍，五分钟就知道该不该升级。没有这个，升级全靠玄学。
3. **显存预算心里有数**：权重体积 + KV cache（经验值：14B/16K 约 3–4GB），再留 20% 余量给系统。
4. **配置固化成脚本**。环境变量加启动脚本，不依赖 GUI 手点，换机或重装十分钟复原。

# 总结

本地 LLM 不是要替代云端，而是给 Agent 体系补一层「离线可用的兜底」。投入一个周末，换来的是调试不限流、隐私不出门、断网也能跑流程。对玩 MCP 和自动化的同学来说，这个本地推理节点大概率会成为你基础设施里性价比最高的一块。
