## 背景

OpenClaw 工作区里有一组约定文件，`TOOLS.md` 是最容易被敷衍的一份——很多人复制个模板了事。结果是 Agent 在一台机器上干活利落，换到 VPS 或第二台机器就开始瞎猜路径、乱装依赖。问题不在模型，而在于环境知识没有落盘：它们只存在于之前的对话里，换个会话就没了。

## 问题

环境差异比想象中多：

- **多机不同构**：家里是 macOS + brew，VPS 是 Ubuntu + apt，公司笔记本的 Python 版本又不一样；
- **工具存疑**：ffmpeg 装没装、Docker 能不能用、node 是哪个版本；
- **隐性约定**：脚本放哪、密钥从哪读、哪些目录绝对不能碰。

拿不到这些事实时，Agent 的默认行为是试探：找不到就 `apt install`，猜一个路径写进脚本。同一条指令，两台机器两种结果，还可能污染环境。

## 做法

把 `TOOLS.md` 当“这台机器的环境清单”写，而不是工具教程。建议三段式：

**1. 本机有什么。** 系统版本、包管理器、关键工具的绝对路径和版本，例如 `ffmpeg: /opt/homebrew/bin/ffmpeg (7.x)`。写事实，别写“应该有”。

**2. 东西在哪。** 工作目录约定（脚本放 `~/scripts`，产物放 `/data/agent-out`）、凭据的读取位置（如 `~/.config/xxx/token`——只写位置，不写内容）、代理或网络限制。

**3. 有什么禁忌。** 不要全局 pip install、不要动 `/etc` 下的配置、某服务在跑不要重启。

多机场景的关键原则：**每台机器一份，跟着工作区走**。不要追求“通用版”，通用版等于没有。可以维护一个共享模板，每台机器只 diff 出差异段。

再加一条让它活起来：Agent 试探成功后（比如自己摸到了某个工具的实际路径），要求它把结论写回 `TOOLS.md`。这份文件应该越用越准。

## 踩坑点

- **写成愿望清单**：写了“建议安装 xxx”但实际没装，Agent 会当真并直接调用，比不写还糟；
- **密钥入文**：`TOOLS.md` 会随工作区同步、进上下文，任何凭据都只写“从哪读”，绝不写值；
- **太长**：Agent 的上下文预算有限，几百行描述会稀释关键信息。控制在一屏内，关键行放前面；
- **版本漂移**：系统升级后没更新文件，Agent 按“确信的旧事实”行动，是比瞎猜更危险的事故来源；
- **职责混淆**：行为规则放 `AGENTS.md`，环境事实放 `TOOLS.md`，两边重复迟早出现不一致。

## 可复用建议

1. 用一行命令生成底稿再人工裁剪：把 `uname -a`、`which ffmpeg python3 node`、`python3 --version` 的输出整理进文件，保证起点即真实；
2. 换机或升级后跑一遍校验，把它当配置文件来 review，而不是当文档；
3. 约定“不确定就删”：一条信息如果不确定还成不成立，宁可删掉，让 Agent 现场确认并回写。

## 总结

`TOOLS.md` 的价值不在写得漂亮，而在于把环境事实从对话记忆搬到一个 Agent 每次都会读、且随机器同步的地方。它本质上是你给 Agent 的一张机器快照：少一次试探，就少一次事故。写五分钟，省掉的是之后每个会话里重复解释和排错的时间。
