2 月底的五天里，DeepSeek 连续放出五个硬核代码仓库——从 FlashMLA 到 3FS，几乎把推理系统里最核心的几块"发动机零件"拆开给人看。戏剧性的是，开源周落幕没几天，SGLang 和 vLLM 两大推理框架就宣布完成适配，SGLang 官方口径的解码吞吐提升一度到 6 倍量级。一场推理速度竞赛就此开卷：开源的不是模型本身，而是"怎么把模型跑得更快"的图纸。这篇文章拆三件事：竞赛在比什么、提速从哪来、开发者怎么从中捞到实际好处。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-27/a257726c00ff35f8.png)

## 先对齐概念：推理速度到底在比什么

- LLM 推理分两段：**prefill**（一次性读完 prompt，算力密集）和 **decode**（一个 token 一个 token 往外吐，显存带宽密集）。两段瓶颈完全不同，优化手段也不同。
- 常用指标有三个：TTFT（首 token 延迟，决定"响应快不快"）、TPOT（相邻 token 出字间隔，决定"读起来流不流畅"）、吞吐（每秒总 token 数，决定单位成本）。
- 为什么值得卷：推理是模型商业化的大头支出。同一张卡吞吐翻倍，API 成本理论上就能砍半——速度直接换算成钱。
- 所以所谓"性能反超"，本质是**单位算力产出 token 的效率**之争。

## DeepSeek 开源周：不止给代码，还附赠说明书

- **FlashMLA**：MLA（Multi-head Latent Attention）的高性能内核，官方数据在 H800 上显存吞吐约 3000 GB/s、算力约 580 TFLOPS。MLA 的价值在于把 KV cache 压缩一个数量级，给大并发腾出显存。
- **DeepEP**：官方称首个开源的专家并行（EP）通信库，专治 MoE 模型 all-to-all 通信这个老大难——DeepSeek-V3 总参数 671B、每 token 只激活 37B，几百个专家在多机之间频繁互传数据，通信就是命门。
- **DeepGEMM**：FP8 矩阵乘内核，H800 上做到 1350+ TFLOPS，覆盖 MoE 场景的分组乘法。
- **DualPipe / EPLB**：双向流水线并行与专家负载均衡，用软件把 GPU 的"摸鱼时间"压到最低。
- **3FS / smallpond**：面向 AI 数据管线的高性能并行文件系统与处理框架。
- 彩蛋是最后附赠的推理系统 **profiling 数据**：decode 阶段算力与访存比约 1:14、KV cache 的设计取舍，甚至推算了理论上 545% 的成本利润率。等于把生产级系统的工程账本摊在了显微镜下。

这份材料的真正意义不是"能抄作业"，而是公开了"为什么这么写"。社区第一次能对着真实生产系统的剖析数据做优化，而不是凭感觉调参。

## vLLM / SGLang 是怎么"连夜"消化的

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-27/8a8b21e76638de7a.png)

- SGLang 的路径最典型：先接入 FlashMLA 内核，再叠加 DP attention、DeepGEMM，配合自家的 RadixAttention 前缀缓存与 TBO 双批次流水，官方口径解码吞吐最高提升约 6 倍。
- vLLM 则把 PagedAttention 与 continuous batching 的看家本领打磨得更细，逐步完善对 DeepSeek MLA/MoE 结构的原生支持。
- 提速原理可以浓缩成一条链：**KV cache 更小 → 同样显存塞进更大 batch → 显存带宽利用率拉满 → 吞吐上涨**。
- 另一半收益来自"消灭空闲"：借鉴 DualPipe 思路让通信与计算重叠，GPU 等数据时也算着别的活。
- 再叠加 MTP 投机解码（一次多猜几个 token 再验证），decode 的出字速度还能再抬一截。

值得注意的细节：适配是以"天"为单位发生的，内核开源当周就有 PR 合入主干。说明社区早就把架构论文吃透了，缺的只是官方内核这块最后拼图。

## 开源飞轮：为什么开源了反而更快

- 直觉上，把核心技术送出去是帮对手。但在推理引擎这个生态里逻辑恰好相反：透明度越高，可复现性越强，下场卷的人越多，整体水位涨得越快。
- 闭源栈是单点试错，开源社区是并行试错——几百个工程师同时在 H800/H100/H200 上找瓶颈，一周的迭代量可能抵闭门造车半年。
- 竞争还附带免费的"质检服务"：框架之间互相打脸式优化，跑分注水很快会被同行当众指出，数字越卷越真实。
- 当然别神化：开源内核只是半成品弹药，能不能打出去，取决于你的团队会不会集成、调参、压测。这也是为什么不少团队"抄了作业"依然跑不出官方数字。

## 看懂跑分：数字里的水分在哪

- **看测试条件**：吞吐跑分通常在高并发、长上下文下最漂亮，与你的真实流量形态可能天差地别。
- **分清 prefill 与 decode**：有些"提速 10 倍"只在其中一段成立，混合统计容易误导。
- **分清瓶颈类型**：decode 阶段多数时候卡的是显存带宽而不是算力，换更强的卡未必有用，压缩 KV cache 才是正解。
- **警惕理论峰值**：GB/s、TFLOPS 是天花板，工程实现能拿到六七成就算优秀。
- 最稳的做法是用自己业务的 prompt 分布建一套固定基准，定期回归测试。

## 三条实用建议与冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-27/5560b035c8905694.png)

1. **选型先看负载形态，再看跑分**：长文档场景 prefill 权重高，高并发对话场景 decode 和前缀缓存权重高，先测自己的流量再选框架。
2. **优先榨 KV cache 的价值**：RadixAttention 式前缀缓存、并发结构设计带来的收益常常比换内核更大，把缓存命中率当成核心监控指标。
3. **把 profiling 数据当教材，别只当新闻**：读懂"瓶颈在算力、带宽还是通信"这个分析框架，比追任何一个新框架都保值。

这场竞赛最健康的地方在于：赢家不是某一家公司，而是所有使用推理服务的人。速度的上限还在被继续推高——而且这一次，图纸是公开的。
