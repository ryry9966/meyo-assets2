## 背景

最近在 OpenClaw 里跑自动化任务，最明显的瓶颈不是模型能力，而是单 agent 的串行结构：所有工具输出、文件内容、报错堆在同一个上下文里，任务一大就上下文吃紧、墙钟时间爆炸。把「补测试、迁移依赖、批量重构」这类可拆任务交给 subagent 并行做，实测能把 40 分钟的串行流程压到 15 分钟左右。

## 问题

单 agent 干大任务有三个典型病灶：

1. **上下文污染**：模块 A 的调试日志把模块 B 的规划细节挤出去，后面开始凭记忆瞎写；
2. **串行等待**：每步工具调用都阻塞下一步，大部分时间在空等；
3. **单点卡死**：一步陷入循环，整条链路报废。

## 做法

以「给三个独立模块补单元测试」为例，流程如下：

**1. 拆任务，写清契约。** 主 agent 先做静态分析，产出任务清单，每项包含：输入文件、允许改动的范围、产出物、验收标准（如「新增测试全部通过，且不修改 `src/` 下其他文件」）。契约必须机器可校验，不写「尽量做好」这种模糊话。

**2. 起子 agent，隔离上下文。** 每个 subagent 只携带任务描述 + 相关文件路径，**不带主对话历史**。这既是省 token 的关键，也是避免污染的关键。

**3. 控并发。** 用信号量把并发压在 3 左右，按文件粒度划分写入边界，避免两个子 agent 改同一个文件。

**4. 结构化回收。** 子 agent 返回固定格式摘要：状态、diff 路径、关键日志路径。主 agent 只吃摘要，原始输出落盘。

伪代码示意：

```text
tasks = planner.split(repo)
results = pool.map(run_subagent, tasks, max_workers=3)
report = verifier.check(results)   # 统一跑测试入口
retry(report.failed)               # 失败者重派，或降级串行
```

## 踩坑点

- **子 agent 继承父上下文**：一旦把主对话整个塞进去，token 成本直接 ×N，务必显式构造子 prompt；
- **并发写冲突**：Git 同分支并发 commit 会互相顶掉，要么按文件划分边界，要么让子 agent 只产出 patch、主 agent 统一应用；
- **幻觉式「已完成」**：子 agent 会理直气壮地报告成功，验收必须可执行（跑测试、跑 lint），不能靠自述；
- **限流**：4 个并发就可能触发 429，重试要加指数退避，别裸 retry；
- **失败传播**：默认单任务失败不影响其他任务，最后统一汇总，别一失败就 cancel 全部。

## 可复用建议

1. 把任务契约固化成 JSON schema，主 agent 生成、校验通过后再派发；
2. 子 agent 权限最小化：只读任务挂载的 MCP 工具集合里不要混入写操作；
3. 并发从 2 起步，观察限流与冲突情况再逐步上调；
4. 所有子 agent 输出落盘，主上下文只存指针，方便事后排查。

## 总结

subagent 编排的本质是**上下文隔离 + 结构化交接**，并行只是收益之一。实践中别急着拉高并发，先把拆分粒度和验收标准做扎实，稳定性自然就上来了。欢迎在评论区交流各自的调度策略和翻车案例。
