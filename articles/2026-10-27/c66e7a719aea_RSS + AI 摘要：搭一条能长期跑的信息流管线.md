## 背景

订阅源越攒越多，真正读完的比例越来越低。RSS 依然是控制感最强的信息源：格式标准化、无算法干预、数据可以自己留存。缺的只是一层"压缩"——把每天上百条 item 压成十几条值得点开的摘要。这篇记录我用 OpenClaw 的 cron 触发加 MCP 工具搭的一条管线，稳定跑了一段时间，把踩过的坑整理出来。

## 问题

直接"拉 feed → 喂给模型"会遇到三个现实问题：

1. 很多 feed 只有摘要没有全文，模型对残缺文本做总结，容易脑补；
2. 同一篇文在多个源重复出现，摘要重复推送；
3. token 成本不可控，源一多，每天的账单很难看。

## 做法

管线分四段，各段解耦：

1. **抓取**：cron 定时触发 agent，调用 fetch MCP 工具拉取 feed 列表，解析出 item（guid、link、title、published）写入 SQLite。没有 RSS 的站点用自托管 RSSHub 补源。
2. **清洗去重**：link 去掉 utm_* 等追踪参数后再算 hash；guid 缺失时用规范化 URL 兜底。正文用 readability 类工具抽取，截断到固定长度。
3. **摘要**：分批喂给模型，prompt 强制输出结构化 JSON——一句话摘要、三个要点、相关度评分。先用小模型按评分过滤，过阈值的条目才用大模型精摘，这一步把成本降了一个量级。
4. **推送**：汇总成每日 digest，推到 Telegram 和一份 Markdown 文件；原文链接永远保留，摘要只是索引。

关键约束写进 prompt：只允许基于给定文本总结，文本里没有的信息一律输出 unknown，禁止猜测。

## 踩坑点

- **URL 去重失效**：同一篇文章带不同 utm 参数被算成两条。规范化 query 参数后解决。
- **截断引发幻觉**：截断点刚好落在结论段，模型"补全"了结论。截断策略改成保头保尾，并在 prompt 里声明文本可能不完整。
- **摘要的摘要**：早期把日报再丢给模型生成周报，信息失真明显。改成周报直接聚合七天的高分摘要原文，不再过模型。
- **公共 RSSHub 限流**：源一多就 429。自托管加缓存后才稳定。
- **时区问题**：digest 的"今天"按 UTC 算，早上收到的日报缺了昨晚的内容。固定为本地时区零点截断。

## 可复用建议

- **原始与派生分离**：item 表只存抓取原文，摘要是可重建的派生产物，prompt 改了随时全量重跑。
- **两阶段分工**：便宜模型做过滤打分，贵模型做精摘，比一刀切省钱且质量不降。
- **schema 先行**：摘要输出强制 JSON schema，下游推送代码不用猜格式，出问题容易定位到具体段落。
- **记 token 账**：每次调用记录用量，加一个源成本涨多少，心里要有数。

## 总结

这条管线没用任何复杂技术，价值在于把抓取、清洗、摘要、推送拆开，每段可单独替换和重跑。AI 摘要的可信度上限取决于喂进去的全文质量，所以清洗段花的心思比 prompt 还多。下一步打算加反馈回路：记录点了哪些链接、停留多久，用来反哺相关度过滤阈值。
