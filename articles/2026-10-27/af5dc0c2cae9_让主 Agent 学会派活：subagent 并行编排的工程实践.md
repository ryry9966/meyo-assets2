## 背景

单个 Agent 跑长任务时有个很现实的瓶颈：上下文。读十几个文件、跑几轮测试之后，主对话里塞满中间产物，模型开始“忘事”，工具调用也越来越绕。另一类问题更直接——比如“给 8 个模块补单测”“调研 5 个候选方案”，本质是互相独立的子任务，串行做纯粹浪费时间。

subagent 编排就是针对这两点：主 Agent 只做拆解、派发和验收，子代理各自开独立上下文干活，能并行的就并行。

## 问题

直接开干会遇到四个坑：

1. **上下文污染**：子代理原样回传过程日志，主 Agent 的上下文瞬间被冲爆，编排本身变成负担。
2. **写冲突**：多个子代理并发改同一个目录，轻则互相覆盖，重则 git 状态彻底乱掉。
3. **错误传染**：一个子代理卡死或失败，整批任务跟着挂起。
4. **验收缺失**：并行跑完直接合并，等于把质检环节删了。

## 做法

我目前跑得比较稳的流程分四步，以“批量补测试”为例：

**第一步：主 Agent 只拆任务，不写代码。** 输出任务清单，每项包含目标文件、要覆盖的行为、完成标准。拆分原则是任务之间没有共享写入目标——这是能否并行的前提。

**第二步：给每个子代理隔离环境。** 用 git worktree 开独立工作副本，或至少独立子目录。同时做工具白名单：只允许跑测试和写指定文件，不碰网络、不碰全局配置。

**第三步：控制并发，跑批。** 并发数压在 3~4。子代理的 prompt 必须自包含：项目约定、路径、测试命令、“完成定义”全写进去，别指望子代理自己来问。每个子代理设超时（比如 10 分钟），超时标记失败，不阻塞其他任务。

**第四步：结构化回传 + 统一验收。** 子代理只回传固定结构：结论、改动文件列表、测试是否通过、遗留问题。主 Agent 汇总后统一跑 lint 和全量测试，通过的分支按序合并，失败的进重试队列，重试一次仍失败就隔离出来人工看。

同样 8 个模块的补测试任务，串行约 40 分钟，这套流程压到 12 分钟左右，且主对话上下文始终干净。

## 踩坑点

- **子代理回传了完整日志**。第一次没限制输出格式，主上下文直接膨胀，后续推理质量明显下降。务必写死“只返回摘要，不超过 N 行”。
- **并发开到 8**，触发 API 限流，成本线性上涨，实际吞吐反而不如 4 并发稳定。
- **prompt 不自包含**。子代理不知道目录规范，文件放错位置，合并阶段全部返工。自包含 prompt 是整条链路里性价比最高的投入。
- **没设超时**。一个子代理陷入工具调用死循环，整批白等。超时加失败隔离要作为默认配置。

## 可复用建议

- 子代理 prompt 做成四段模板：目标 / 边界 / 交付物 / 禁止事项。
- 回传统一 JSON 结构，让主 Agent 程序化汇总，而不是靠自然语言“理解”。
- 并发数、超时、重试次数做成配置项，不同任务类型用不同档位。
- 新场景先用 2 个子代理验证链路，确认验收闸门有效再扩量。
- 保证子代理幂等：重跑不产生副作用，重试才有意义。

## 总结

subagent 编排的核心不是“多开几个 AI”，而是把规划、执行、验收三种角色分开：主 Agent 负责拆解和把关，子代理在隔离环境里做可并行、可丢弃、可重试的执行单元。收益来自并行与上下文隔离，风险几乎都来自共享状态和缺失的验收闸门。建议从小规模批处理任务入手，把流程模板固化后，再推广到调研、重构这类更大的场景。
