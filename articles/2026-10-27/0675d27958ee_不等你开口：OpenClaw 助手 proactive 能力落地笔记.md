## 背景

大多数助手是"拉"式交互：你不发消息，它永远不动。接上 IM 通道、跑在自己服务器上之后，会暴露一类天然属于"推"的需求——CI 挂了、磁盘快满、监控越阈值、日历上的会需要提前准备。这类事的特点是：等你开口问，往往已经晚了。

OpenClaw 的架构适合做这件事：常驻网关，会话、工具、消息通道在同一层。难点从来不是"能不能主动"，而是"主动到什么程度才不烦人"。

## 问题

从 reactive 改到 proactive，本质要解决三件事：

1. **触发源**：事件从哪来。没有事件源，主动就是定时瞎猜。
2. **决策**：醒来后是行动、记一笔，还是继续睡。多数失败不是没触发，而是每次触发都硬要说点什么。
3. **状态**：agent 大部分时间"睡着"，每次醒来上下文是空的；不解决这个，它就是个失忆的定时任务。

## 做法

我的落地结构是三层：感知 → 判断 → 行动。

**感知：三种入口。** Webhook 收外部推送（GitHub、监控告警、任何能发 HTTP 的设备），统一写进观察日志；Cron 定时拉没有 webhook 的源（日历、天气）；Heartbeat 兜底，每 30 分钟唤醒 agent 自查。

**状态外置。** 不上花哨的记忆系统，一个 markdown 观察日志就够，三列：时间、观察到什么、做了什么决定。每次唤醒先读日志再决策。

**判断：三选一，默认沉默。** 心跳 prompt 显式给出 `notify`（发消息）、`log`（只写日志）、`silent`（什么都不做）三个动作，并写明"不确定选 silent，宁漏勿扰"。notify 条件要具体：越过阈值、重复出现 N 次、有明确截止时间。

**行动收敛。** 主动消息固定格式：一句结论 + 关键证据 + "需要我处理吗"。主动场景默认只通知不执行，写操作走确认或白名单。

## 踩坑点

- **心跳太密**：起初设 5 分钟，一晚烧掉不少 token，还产出一堆"没事发生"。30 分钟起步，能事件驱动的别靠心跳兜。
- **没给沉默选项**：早期 prompt 只写"检查并汇报"，agent 每次都汇报，信噪比直接崩。沉默必须是显式合法动作。
- **主动消息缺锚点**：冷不丁一句"磁盘 91%"让人一头雾水，必须带上"因为我持续观察到……"。
- **观察日志膨胀**：一个月后日志比上下文窗口还长。现在每次唤醒顺手做摘要压缩，只留未决事项。
- **Webhook 直通执行**：告警曾直接触发一次重启，结果没事，但这条路不该开——主动通道只写日志，执行永远人在环。

## 可复用建议

- 感知/判断/行动三层解耦：事件源挂了不影响决策逻辑，改规则不用动接入。
- 朴素观察日志比向量记忆方案实用得多，先跑三个月再谈升级。
- "什么情况可以打扰我"做成配置：阈值、白名单、免打扰时段，别写死在 prompt 里。
- 上线前跑影子模式：只写日志不发消息，观察一周它"想"说什么，再放开 notify。

## 总结

Proactive 不是让 agent 更聪明，而是三个工程问题：事件怎么进来、状态怎么保住、打扰怎么克制。最难的是第三个——默认沉默、宁漏勿扰，是这套东西能长期开着的唯一原因。先让它在日志里想，再让它对你说话，最后才是替你动手。
