## 背景

接了 MCP 之后，Agent 的能力上限一下子打开了：读文件、调 API、执行脚本、发消息，都是一轮 tool call 的事。但多数团队把精力放在"能不能干成"，很少放在"该不该自己干"。结果往往是两个极端：要么每一步都弹确认，人变成了 Agent 的人肉回车键；要么全自动跑，直到某天它把测试库当生产库删了。

## 问题

"问不问人"不是语气词问题，是策略问题。我踩过的两类典型失败：

- **确认疲劳**：高频低危操作也要求确认，两周后所有人条件反射式点"允许"，高危操作混在里面反而没人细看。
- **静默越权**：权限只写在 system prompt 里（"请不要删除文件"），工具层没有任何拦截，模型一跑偏就直接执行了。

其实判断维度只有四个：**可逆性、影响半径、成本、意图清晰度**。所有策略都应该从这四项推导出来。

## 做法

我把所有工具调用分成三级，落到配置层而不是 prompt 里：

1. **auto（自动执行）**：只读操作、沙箱内可回滚的写操作。照常执行，但必须留审计日志。
2. **confirm（需确认）**：不可逆、对外可见、花钱的操作——给真实用户发消息、删生产数据、支付类调用。确认请求必须带五件事：做什么、对哪个目标、diff、回滚方案、不做的后果。不许只问一句"可以继续吗？"。
3. **deny（禁止）**：明确划走的红线，比如直接接触生产凭据、访问范围外域名。

配套三个工程手段：

- 写操作默认 dry-run，先出 diff，人看完再 apply；
- 用预算做硬限制：单次运行花费上限、tool call 次数上限、时间窗口，超了自动停，而不是继续弹窗；
- 确认与执行全量落日志，每周复盘一次来调整分级——哪些 confirm 从没被拒过，可以降级成 auto。

## 踩坑点

- **确认请求不带上下文**。Agent 问"我可以继续吗"，人不知道它在问什么，只能盲点。确认 payload 必须结构化。
- **分级粒度太粗**。要按"操作"分而不是按"工具"分：同一个 GitHub 工具，读 issue 是 auto，close issue 就该是 confirm。
- **忘了子 Agent**。主 Agent 有边界，派生出去的子任务继承了全部工具却没继承策略，这是最常见的事故来源。
- **混淆两类"问"**。因为不确定而问，应该随着经验收敛；因为策略而问，永远不该自动放行。

## 可复用建议

- 默认拒绝外部副作用，白名单放行，顺序不要反。
- 权限边界做在网关/工具层，prompt 里写的只是给人看的说明。
- 确认可以攒批：低危确认排队、定时批量处理，别让人被碎片化打断。
- 边界不是一次定死的，用审计数据每两周迭代一次。

## 总结

权限边界本质上是产品决策，不是 prompt 技巧。判断标准永远是那四个维度：能不能撤销、影响多少人、花多少钱、意图明不明确。先保守、再依据日志逐步放宽，比先放开再收权成本低得多。
