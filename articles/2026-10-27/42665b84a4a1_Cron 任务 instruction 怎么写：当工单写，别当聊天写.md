## 背景

OpenClaw 的 cron 功能本质上是"定时触发的 prompt"：到点后，调度器把你的 instruction 交给 agent 独立执行。很多人踩的第一个坑，是把它当成日常对话来写——反正都是跟 agent 说话。但交互式对话有大量隐性支撑：你在场、有上下文、可以追问。定时任务把这三样全拿掉了，instruction 就得自己把这些支撑补回来。

## 问题

无人值守改变了 prompt 的约束条件：

- 执行时没有当下对话上下文，"刚才说的那个"无从谈起；
- agent 不能向你确认，遇到模糊处只能猜；
- 结果如果没有明确的投递路径，跑完了也无人知晓。

我见过不少"任务明明在跑，效果却时好时坏"的案例，根源几乎都在 instruction 本身，而不是调度配置。

## 做法：按五段式工单来写

我现在的模板是：**目标 / 数据源 / 动作 / 输出 / 异常处理**。以一个每日待办播报任务为例：

```text
每天 08:30（时刻由调度器固定，无需自行判断日期）：
1. 读取 ~/notes/inbox.md 中未标记 [done] 的条目
2. 按优先级排序，最多取 5 条
3. 通过 Telegram 发给我，每条一行，前缀序号
4. 若文件不存在或为空，发"今日无待办"，不要自行补充内容
5. 不执行任何写操作，不要追问
```

拆开看每部分的用意：

1. **目标一句话说死**：不写"帮我看看待办"，写清楚取什么、怎么排、取几条。
2. **数据源给绝对路径**：不给 agent"找找看"的发挥空间。
3. **输出写死通道和格式**：发到哪、什么格式、几条，逐项明确。
4. **异常处理必须有**：数据缺失时输出什么、禁止做什么，防止它编内容补位。
5. **显式禁止追问**：一句话省掉无人值守时卡死的可能。

## 踩坑记录

- **时间指代**：instruction 里写"昨天的日志"，时区和锚点全靠模型猜。现在我只在调度器里定时刻，instruction 一律用"本次运行"表述。
- **输出通道没写**：任务正常跑完，结果躺在 session 里，手机上什么都没收到。教训：每条 instruction 都写"通过 XX 发给我"。
- **工具边界没收紧**：一次让 agent"整理笔记目录"，它把几个旧文件做了归档移动，动作完全超出预期。现在权限一律白名单式写明，只列允许的动作。
- **周期与耗时错配**：一个 15 分钟周期的任务实际要跑 20 分钟，执行堆叠。新任务先手动跑一遍测耗时，再定周期。

## 可复用建议

1. 新 cron 任务先以 10 分钟间隔试跑 2–3 轮，观察执行路径是否稳定，再改正式周期。
2. instruction 放进版本管理：改坏了能回滚，也能对比出哪次改动导致行为漂移。
3. 定期翻执行 session，看 agent 实际调了哪些工具、走了哪条分支——它比你想象中更常"抄近路"。
4. 相似任务合并成模板，改参数不改结构，出问题时排查面小很多。

## 总结

一条 cron instruction 的质量，等于一份工单的质量。写完之后做个思想实验：设想凌晨三点，一个没有对话上下文、无法被追问的执行者拿到这句话，能否独立完成并交付结果。能，这条 instruction 才算合格。
