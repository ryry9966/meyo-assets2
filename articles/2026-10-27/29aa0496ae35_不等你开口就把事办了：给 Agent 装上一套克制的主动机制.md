## 背景

绝大多数 AI 助手是纯响应式的：你问，它答。这在问答场景够用，但在自动化实践里很快就不够了——磁盘快满了、CI 红了、日历上有冲突，等你想起来去问，往往已经晚了。OpenClaw 提供了 heartbeat、cron 和事件触发这些底座，但"能主动"和"该主动"之间差着一整套工程设计。最近我把自己的 agent 从纯响应式改成半主动式，记录一下思路。

## 问题：主动 ≠ 骚扰

最直觉的做法是让 agent 定时检查所有东西，发现异常就说话。跑了一天我就关掉了：它一小时推七八条"一切正常"，信噪比低到用户必然 mute。主动能力的核心矛盾在于：触发太勤是噪音，触发太懒不如没有。所以真正要设计的不是"怎么让 agent 开口"，而是"怎么让它在多数时候闭嘴"。

## 做法

1. **先把触发源列清楚。** 我只留三类：cron（每天早上扫一次日历和待办）、heartbeat（默认 30 分钟检查一次规则文件）、webhook（GitHub、监控系统的外部事件）。其余一律不接，避免"什么都听一点"。
2. **规则写成文件，不靠模型自觉。** 所有主动行为定义在一个 markdown 里（类似 HEARTBEAT.md 的机制），每条规则必须包含：可判定的触发阈值、动作、静默窗口。比如"磁盘 >90% 才提醒，同一事项 6 小时内不重复"。并且显式写明：所有条件都不满足时，静默结束，不发任何消息。
3. **分级响应。** 输出分三档：写日志（完全静默）、进日报摘要（每天一条汇总）、立即提醒（真正紧急）。实践里 90% 的检查结果落在第一档，日报兜住剩下的大多数，立即提醒一周也就两三次。
4. **防自激。** agent 自己发出的消息不再作为触发事件；动作执行后写状态文件记录时间戳，抑制逻辑读这个文件做去重。

## 踩坑点

- heartbeat 间隔设 5 分钟试过，token 烧得心疼且毫无收益，30 分钟起步足够；
- 早期规则写得模糊（"有重要邮件就告诉我"），模型每次都在自行"判断重要性"，结果就是乱报——规则必须可判定，阈值必须写死；
- 时区坑：cron 默认 UTC，半夜被日报叫醒过一次，务必显式指定时区；
- 有一次 agent 主动"帮忙"清理了临时目录。从此主动模式下所有写操作走 allowlist，只读操作默认放开。

## 可复用建议

- 从一条确定性规则起步，别一上来就做"智能判断"；
- 把静默当作默认成功状态，说出去的每句话都要有明确理由；
- 给主动行为留审计日志，每周回看一次，删掉从未触发或触发过频的规则；
- 评估指标只有一个：用户有没有 mute 它。

## 总结

proactive 能力不是模型能力的延伸，而是触发器、阈值、抑制窗口这三件套的工程问题。模型只负责最后一步"判断 + 执行"，前 90% 的工作是让它在正确的时候什么都不做。把沉默当默认值，主动才不会被用户当成 bug 关掉。
