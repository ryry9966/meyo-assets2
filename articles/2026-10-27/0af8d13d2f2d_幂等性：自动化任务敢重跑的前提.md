## 背景

在 OpenClaw 这类自动化环境里，"同一件事被执行多次"不是异常，而是常态：

- 定时任务到点就跑，上一次卡住了，这一次照常触发；
- 网络抖动、工具调用超时，框架自动重试；
- Agent 判断失误，把同一个工具调用发了两遍；
- 人工补跑昨天的失败任务。

写过脚本做数据同步的人都有体会：跑一次没问题的逻辑，跑十次就出事，迟早出事。

## 问题

举个典型场景：一个 agent 每天把工单系统的新记录同步到表格，追加写入。某天网络超时任务失败，人工重跑——表格里多了两份重复数据。更隐蔽的是消息推送类任务：重试导致同一条告警发了三遍，值班的人开始无视告警，真正的事故反而被淹没。

这些问题的共同点：**副作用和执行次数相关**。而分布式系统保证不了"恰好执行一次"（exactly-once），只能保证"至少一次"（at-least-once）。幂等性就是在两者之间搭桥：让操作执行一次和执行 N 次，最终状态一致。

## 做法

1. **选对幂等键。** 用业务上的天然唯一标识（日期 + 来源 + 记录 ID），不要用时间戳、UUID 或模型生成的随机串。幂等键选错，后面全是白做。
2. **追加改为覆盖。** 数据写入用 upsert（按主键插入或更新），文件按固定路径整体覆盖，配置按声明式模板渲染。目标状态不变，执行次数就无关紧要。
3. **外部副作用加去重层。** 调用不支持幂等头的 API 前，先在自己的存储里落一条"意图记录"（含幂等键，建唯一索引），调用成功后更新状态。重试时先查这张表：已成功就跳过，已失败才重发。顺序是先写记录再调用——宁可多查一次，不可多发一条。
4. **用存储层约束兜底。** "先查后写"有竞态：两个实例同时查到"不存在"，然后都写入。唯一索引和主键冲突才是最终防线，代码里的 if 判断只是优化。
5. **中断可续跑。** 记录处理进度（上次成功的 offset 或游标），重跑从断点继续；或者把整个任务包进事务/原子操作。

## 踩坑点

- **删除操作未必幂等。** 按 ID 删除是幂等的，"删掉最新一条"不是——重跑会连环删。
- **并发场景想当然。** 单机测试一切正常，两个调度实例同时触发就穿帮。幂等设计要按并发假设来做。
- **让 agent 自己编幂等键。** 模型输出不稳定，同一意图两次可能生成不同 ID。幂等键必须在代码/工具层生成，只把业务参数交给模型。
- **部分失败被忽略。** 批量写 500 条，第 300 条挂了。没有进度记录，重跑要么从头来（幂等能兜住但浪费），要么跳过前 300 条（需要可靠的进度标记）。

## 可复用建议

写任何自动化任务前，先自问三个问题：

1. 重跑一次会怎样？
2. 重跑十次会怎样？
3. 跑到一半挂掉再跑，会怎样？

三个问题都答不出"没问题"，就还不到能上线的程度。可以按任务类型套模板：同步类用 upsert，通知类用去重表，部署类用版本对齐（目标版本已就位就跳过）。最后把"是否幂等"写进任务描述，作为 review 的固定检查项。

## 总结

幂等性不是高级架构技巧，而是自动化敢交付的底线。重试、重跑、并发触发都是日常，与其祈祷它们不发生，不如让它们发生时毫无影响。下次写 agent 工具或插件时，先想清楚幂等键是什么——这个习惯比任何重试策略都省钱。
