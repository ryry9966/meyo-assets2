## 背景

OpenClaw 支持同时配置多个模型来源：云端 API 和本地服务（Ollama、LM Studio、vLLM 起的推理服务都能接）。大多数人的第一版配置是"一个模型走天下"——全走云端，月底账单难看；全走本地，工具调用三天两头失败。多模型路由的意义不在炫技，而是让每一类任务落在性价比最合适的那一档。

## 问题：先看清你的负载

把我的 agent 跑了两周的日志拉出来看，负载大致四类：

1. 意图识别、闲聊兜底——简单，频率极高；
2. 工具调用与 MCP/插件编排——要求严格的函数调用和 JSON 稳定性；
3. 记忆压缩、长文档摘要——token 量大，难度低；
4. 复杂规划、代码生成——难度高，频率低。

单一模型的矛盾就在这里：第 3 类用云端纯属烧钱，第 2、4 类用小本地模型纯属翻车。

## 做法：四步落地

**1. 先分类任务，再选模型。** 不要从"哪个模型最强"出发，要从自己的任务分布出发。路由规则是为任务写的，不是为模型写的。

**2. 配 fallback 链。** primary 放云端主力，fallbacks 前置本地模型——方向别搞反，本地挂掉时云端兜底，比反过来安全：

```json
"agents": { "defaults": { "model": {
  "primary": "openai/gpt-4.1",
  "fallbacks": ["ollama/qwen2.5:32b", "openai/gpt-4.1-mini"]
}}}
```

**3. 按 agent 粒度覆盖。** 主循环 agent 用云端强模型管规划和工具编排；memory 压缩、heartbeat、定时摘要这类后台杂活，在对应 agent 配置里把 model 覆盖成本地模型。涉及私人文件、密钥读取的任务，直接锁本地。

**4. 验证与观测。** 会话里用 `/model status` 看命中情况，日志里统计各模型的工具调用成功率和 token 花费，每周扫一遍。

## 踩坑点

- **小模型函数调用不稳。** 缺字段、参数幻觉，重试三次的墙钟时间比直接走云端还长。上线前用固定的 20 条工具调用用例跑一遍，成功率低于九成就别让它碰工具。
- **上下文窗口不匹配。** 本地 8k、云端 200k，长会话一旦路由到本地会被静默截断，表现是"它突然失忆"。路由条件里务必带上 token 数。
- **fallback 链太宽容。** 本地一超时全落到云端，账单悄无声息翻倍。给按天用量设个告警，哪怕只是推送到自己的群。
- **embedding 别混用。** 记忆检索的索引和查询必须用同一个 embedding 模型，换供应商要重建索引，否则召回质量会莫名其妙下降。

## 可复用建议

- 从两个模型起步：一个云端、一个本地，跑顺了再加第三档。配置复杂度是真实的税。
- 分工口诀：本地干杂活和敏感活，云端干攻坚活和兜底。
- 路由规则用固定评测集迭代，凭感觉调参数没有意义。
- 记录每次路由决策（任务类型、token 数、命中模型），这是你下一轮优化的全部依据。

## 总结

多模型路由不是一次性配置，而是持续的运维工作：先分类任务，再配链，然后用日志数据回头修规则。做到位之后，成本曲线和稳定性都会给你正反馈——这两件事在日志里都看得见，不用猜。
