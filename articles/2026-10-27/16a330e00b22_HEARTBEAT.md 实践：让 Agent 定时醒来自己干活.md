## 背景

大多数 Agent 的默认形态是“问答机”：你不说话，它永远安静。但真实使用里，很多需求天生是主动型的——早间日程摘要、仓库 issue 轮询、磁盘巡检、订阅源定时整理。

## 问题

这类事过去只有两条路：要么每天手动问一遍 Agent，要么自己写 crontab 加脚本。前者是重复劳动，后者脱离了 Agent 的上下文和工具链，等于另起炉灶。OpenClaw 用一个很小的机制把这条路接通：**HEARTBEAT.md**——让 Agent 周期性醒来，读一眼工作区里的这个文件，有事就做，没事继续睡。不引入新协议、新服务，就是“定时触发 + 一份常驻指令文件”。

## 心跳是怎么跑的

流程很短：定时器到点 → Agent 被注入一条心跳检查 prompt → 读 HEARTBEAT.md → 判断有没有该做的事 → 有则执行并把结果推到目标会话，没有则回复 HEARTBEAT_OK，本次静默结束。

三个关键配置：

- `agents.defaults.heartbeat.every`：唤醒间隔，默认约 30 分钟；
- `agents.defaults.heartbeat.target`：结果推给谁，`last` 表示上次活跃会话；
- `agents.defaults.heartbeat.model`：心跳检查用的模型，可与主模型分开。

## 实操步骤

1. 在 workspace 根目录新建 HEARTBEAT.md。文件为空或不存在时，心跳会被低成本跳过，不产生开销。
2. 条目化描述任务，每条包含：触发条件、动作、输出位置、静默规则。例如“每天 09:00 前汇总昨日 CI 失败项；若无失败则不发消息”。
3. 把间隔调到实际需要的粒度：监控类 15–30 分钟够用，日报类没必要高频。
4. 给心跳配一个便宜模型做“有没有事”的判断，重任务留给主会话的主力模型。这一步能砍掉大部分心跳成本。
5. 跑一两天，观察推送频率，再回来修剪文件。

## 踩坑点

- **写成大段散文**。模糊指令下“该不该动”的判断很不稳定，要么每次全量执行，要么干脆不动。用短条目 + 明确条件。
- **任务没有完成判定**。“关注一下仓库动态”会导致每次心跳重复汇报同一件事。让 Agent 把状态写入本地状态文件，下次心跳先比对再决定是否推送。
- **target 用 `last` 但你换了聊天窗口**，结果推到了工作群。心跳输出建议固定到专用会话。
- **间隔设太短**。心跳每次都是真实的模型调用，5 分钟一次加大模型，等于账单惊喜。
- **往心跳里塞长任务**。心跳周期内跑不完的构建、爬虫会拖住节奏，这类活交给 cron 触发、Agent 接手处理。
- **把它当 AGENTS.md 用**。HEARTBEAT.md 只管周期性任务，人格和全局规则该放哪放哪，混写会让每次心跳的判断更重。

## 可复用建议

一个沉淀下来的条目模板：

```markdown
- [任务名] 触发：<时间/条件>
  动作：<做什么>
  输出：<推到哪>
  静默：<什么情况下不发消息>
```

配套两个原则：一是**默认静默**——没有值得打扰用户的信息就不发，这是心跳类 Agent 体验好坏的分水岭；二是**状态外置**——去重靠文件不靠模型记忆，重启也不丢。

## 总结

HEARTBEAT.md 本身只是一个 Markdown 文件，但它把 Agent 从“被动应答”变成“定时自查”，改变的是使用姿态。上手成本接近零，真正需要打磨的是任务条目的写法和推送纪律。建议从一件低风险的日报类任务开始，跑稳了再往巡检、监控方向加。
