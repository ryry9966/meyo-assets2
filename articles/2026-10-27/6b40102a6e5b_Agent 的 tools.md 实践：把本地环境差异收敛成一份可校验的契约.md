## 背景

跑 Agent 做本地自动化时，最不稳的往往不是模型，而是它脚下的那台机器。同一份任务，在 A 机器上 ffmpeg 在 `/usr/local/bin`，B 机器上由 nvm 接管 node，CI 容器里某些工具干脆不存在。Agent 每次会话都要重新"摸索"环境，或按训练数据里的常识猜路径——猜对是运气，猜错就是一串无意义的报错排查。

tools.md 的思路很简单：在项目根目录放一个约定文件，OpenClaw 这类会把工作区指令文件注入上下文的 Agent 启动时先读它，把"这台机器有什么工具、怎么调、有什么坑"一次性声明清楚。它不是文档，是机器与 Agent 之间的契约。

## 问题

没有这份契约时，典型症状有三个：

1. **Prompt 里硬编码路径**：换台机器就失效，且 prompt 越写越长。
2. **自行探测浪费上下文**：反复执行 `which`、`--version`，一个会话烧掉几千 token 只为确认 python 在哪。
3. **环境漂移无声发生**：本地 jq 1.6、容器里 1.7，不报错但结果不对，排查成本极高。

## 做法

**第一步，定结构。** 每个工具一条，只写 Agent 需要的三件事：怎么调、依赖什么、有什么限制。

```markdown
## ffmpeg
- 调用: ffmpeg（已在 PATH）
- 版本: >= 6.0，当前 6.1
- 注意: 无 libx264，转码改用硬件编码器

## 数据库
- 连接: `psql $LOCAL_DB_URL`（URL 从 .env 读，勿写入本文件）
```

**第二步，区分"机器事实"和"人的约定"。** 路径、版本这类机器事实用探测脚本生成；参数偏好、禁用行为这类约定手写维护。生成的部分不进 git，模板和手写部分进 git。

**第三步，按环境分片。** 以 tools.md 为主文件，tools.darwin.md / tools.linux.md 做增量补丁，Agent 按当前平台合并读取，避免单文件里堆满 if-else 式叙述。

**第四步，加校验。** 写一个 probe 脚本，在 CI 里逐条执行 tools.md 中的命令，失败即阻断。文件烂没烂，机器说了算，不靠自觉。

## 踩坑点

- **写成散文**。Agent 需要可直接执行的命令，不是使用手册；超过一屏的描述基本不会被完整读。
- **塞密钥**。tools.md 会进上下文、可能进日志，只写环境变量名，绝不写值。
- **与 MCP 配置重复**。MCP server 的工具能力已在 server 配置里声明，tools.md 再描述一遍必然漂移。正确姿势是只写"这个 server 在本机怎么启动、端口是什么"。
- **绝对路径写死**。尽量用 PATH 或包装脚本收敛；实在要写，注明获取方式。

## 可复用建议

- 把 tools.md 的变更纳入 code review，当代码对待——它直接决定 Agent 行为。
- 团队维护一套"探测脚本 + 模板"组合，新人跑一条命令即可生成自己机器的底稿。
- 会话开头让 Agent 复述关键工具版本并写进执行计划，出现偏差时立刻能对质。

## 总结

tools.md 解决的不是"Agent 聪不聪明"，而是"环境可不可预期"。把机器事实声明化、生成化、校验化，Agent 的执行稳定性会立竿见影地改善。它成本低——一个 markdown 加一个脚本——收益却在每次会话里持续兑现。建议从小项目试起：先写三条工具，跑一周，再决定要不要推广到团队。
