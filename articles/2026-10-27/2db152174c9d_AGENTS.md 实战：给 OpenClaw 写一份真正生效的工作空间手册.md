## 背景

OpenClaw 的 agent 每次新会话启动时，都会先读工作区根目录下的 `AGENTS.md`。可以把它理解成"写给模型的 onboarding 文档"：工作区长什么样、哪些文件是它的记忆、临时产物放哪、什么操作要先确认。代码仓库的 README 是写给人看的，`AGENTS.md` 的读者是模型。

## 问题

默认模板只有几行泛泛的说明，实际跑起来常见三类失控：

1. **行为漂移**：临时脚本随手丢在根目录，记忆文件格式每次会话都不一样；
2. **指令不生效**：写了一大段，模型抓不住重点，或几条规则互相冲突；
3. **边界模糊**：发消息、跑 shell 这类敏感操作没有明确的确认流程。

本质原因是大家把它当"配置"随手写，但它其实是一份需要设计的工作空间契约。

## 做法

我重写自己工作区的 `AGENTS.md` 时用了四步：

1. **先盘点再动笔**。列出 agent 实际会碰到的文件和操作：MEMORY.md、日志目录、skills、MCP 工具清单，再决定每一项的使用规则。
2. **分层组织**。最前面放硬性规则，每条一句话、祈使句、可验证，比如"临时脚本一律写到 workspace/tmp，用完即删"；中间放目录结构说明；最后放习惯性约定（如记忆条目的格式建议）。
3. **收缩职责**。`AGENTS.md` 只回答"什么时候用什么"，调用参数和工具细节交给 skills 与 MCP 工具描述。这个文件的读者是每次重启都"失忆"的模型，越短越可靠。
4. **版本化验证**。放进 git，每次只改一小块，跑几轮真实会话观察行为变化，再决定保留或回滚。

## 踩坑点

- **散文式写法**。几百字的"你是一个乐于助人的助手"，不如十行明确规则。模型对"祈使句 + 具体路径"的服从度明显更高。
- **规则冲突**。"所有外发消息先问我"和"心跳任务自动执行"放在一起，模型会自己挑一个解释。冲突的规则宁可删掉，也别指望它自己权衡。
- **硬编码环境信息**。绝对路径、端口、机器名写进去，换台机器立刻失效。环境相关的东西交给环境变量或启动配置。
- **高估服从性**。`AGENTS.md` 是强倾向，不是硬约束。真正不能出事的操作（删除、外发），要在工具层和权限层兜底，别只靠提示词。
- **改太勤**。每轮会话都重写一遍，行为会抖动。把它当代码 review，小步提交。

## 可复用建议

- **模板三段式**：硬规则区（10 行以内）→ 结构区（目录与文件职责）→ 习惯区（格式建议）。总长度控制在 100 行以内，它是要常驻上下文的。
- **和 MEMORY.md 划清边界**：`AGENTS.md` 是"法规"，稳定、低频变更；MEMORY.md 是"日记"，高频追加。混在一起，两边都会失效。
- **定期做审计会话**：丢一个混合任务给它，逐条核对规则是否被遵守，把违反的条目改成更具体的表述。
- **每条规则带可判定条件**：能回答"这条到底遵守没有"的规则，才值得写进去。

## 总结

`AGENTS.md` 是 OpenClaw 工作区里杠杆最高的一个文件：改十行，可能比装三个插件更能改变 agent 的日常表现。把它当成一份正式的、需要 review 和版本管理的契约来维护，而不是初始化之后再看一眼的模板。手册写清楚了，agent 才算真正"入职"。
