## 背景

我们用 OpenClaw 跑日常自动化已经有一段时间。最近遇到一类典型任务：一份“竞品功能梳理 + 本地代码适配方案”的活儿，既要查资料、读代码库、跑测试，又要写报告。以前都是丢给单个 agent 串行处理，结果是上下文越滚越长，做到后半段模型开始忘掉前半段的约定，报告前后矛盾。这次我改成 subagent 编排的思路，让主 agent 只当“带队的人”，效果明显，把踩过的坑记录一下。

## 问题

单 agent 串行模式有三个硬伤：

1. **上下文污染**：调研的原始网页、代码中间输出、测试日志全堆在一个会话里，真正关键的约束反而被稀释。
2. **速度慢**：子任务之间明明没有依赖，却只能排队。
3. **失败传染**：一个环节卡死，整条链报废，只能从头再来。

## 做法

我的编排流程分五步：

**第一步，拆任务。** 只拆“无数据依赖”的子任务。比如三个模块的代码调研互相独立，可以并行；而“汇总成报告”必须等它们全部完成。判断标准很简单：子任务只共享输入和最终产物，中间不读对方的工作区。

**第二步，定返回契约。** 给每个 subagent 规定结构化返回格式（固定字段：结论、产物路径、风险点），禁止自由发挥。主 agent 聚合时只依赖契约，不猜语义。

**第三步，主 agent 只编排不干活。** 我在主 agent 的系统提示里明确写了角色定位：负责拆解、派发、等待、聚合、校验，子任务的任何细节都交给 subagent 自己消化。

**第四步，限流和超时。** 并发上限设 3~4 个，每个子任务带超时；失败时不自动重试，而是把失败原因回传给主 agent，由它决定重派、降级还是放弃。

**第五步，产物落盘。** 每个 subagent 把完整产出写进自己独立的工作目录，回传的只有摘要和路径，主 agent 需要细节时再按需读取。

## 踩坑点

- **上下文继承没裁剪**。最初 subagent 默认继承了主会话的完整历史，token 直接翻倍，还互相干扰。改成只注入任务描述加必要约束后明显改善。
- **并发写冲突**。两个 subagent 同时改同一个配置文件，后写的覆盖先写的。现在按子任务划分独立工作区，最后由主 agent 统一合并。
- **聚合即爆炸**。主 agent 把四个子任务的全量输出一次性读进来，上下文瞬间撑爆。解法是强制 subagent 先做自我摘要，全量只落盘。
- **重试风暴**。子 agent 内部无限重试叠加 API 限流，直接雪崩。重试决策必须收归主 agent 一层。

## 可复用建议

- 把“管理者不执行”写进主 agent 的系统提示，这是最省力也最有效的一条。
- 返回契约做成模板，新任务直接复用。
- 每个子任务保持幂等，重派不产生副作用。
- 记录每次 spawn 的耗时和 token 消耗，事后评估并行是否真的比串行划算——不是所有任务都值得拆。
- 有严格顺序依赖的任务别硬并行，编排复杂度会吃掉收益。

## 总结

Subagent 编排的价值不在“多开几个 agent”，而在于三件事：上下文隔离、真并行、失败隔离。建议先拿两个子任务的小场景验证返回契约和落盘机制，跑顺了再扩大规模，比一上来就搭大编排稳妥得多。
