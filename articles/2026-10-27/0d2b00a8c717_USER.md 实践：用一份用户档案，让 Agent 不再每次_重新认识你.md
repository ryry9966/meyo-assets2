## 背景

Agent 的会话本质上是无状态的。哪怕你跑的是常驻的 OpenClaw，每次心跳唤醒、每轮新对话，上下文都要重新拼装一遍：系统提示词定义了"它是谁"（AGENTS.md、SOUL.md 管这个），却没有任何文件定义"你是谁"。结果就是，你得在会话里反复交代：我的时区、我用的 shell、项目目录结构、喜欢简短回答还是详细论证。

## 问题

没有用户档案时的典型症状：

- Agent 反复问你已经回答过的问题（时区、路径、语言偏好）；
- 回复风格漂移，有时过度啰嗦，有时直接替你做决定；
- 换会话、换设备，之前交代的环境信息全部丢失；
- 在 prompt 里写一大段自我介绍，每条消息都带上，浪费 token 且不可维护。

共同根源：缺少一份稳定的、随上下文自动注入的用户画像文件。

## 做法

在工作区根目录建一个 `USER.md`，建议固定五个分节：

1. **基本身份**：怎么称呼你、默认语言、时区、活跃时段；
2. **环境事实**：操作系统、常用 shell、项目根目录、包管理器偏好；
3. **沟通偏好**：回复长度、先给方案还是直接动手、不确定时是否先问；
4. **当前上下文**：进行中的项目、近期优先级、不想被打扰的方向；
5. **边界**：哪些操作永远需要确认（发消息、删文件、花钱）。

配套的工程约定：

- 用标题分节 + 短句列表，方便模型定位和摘要，别写成散文；
- 长度控制在 1–2k token 以内，因为每轮上下文都会注入它；
- 职责分离：稳定事实放 USER.md，动态笔记放 MEMORY.md，行为规则放 AGENTS.md，三者不互相渗透；
- 用 git 管理，每次改动顺手提交，出问题能 diff 回滚。

## 踩坑点

- **当日记写**。大段叙事会稀释关键信息，结构化条目越靠前权重越高，散文式表达检索效果最差。
- **存敏感信息**。API key、家庭住址写进去，等于每个会话外发一遍，还会进日志。凭据走环境变量或密钥管理。
- **信息腐化**。三个月前的项目列表会让 Agent 基于错误假设干活。设个两周一次的 review 提醒，删过期条目比补新条目更重要。
- **放任 Agent 自己改**。允许它追加"学到的偏好"可以，但要有确认机制，否则一次错误推断会被固化成事实。

## 可复用建议

- 做一个五节固定结构的模板（身份 / 环境 / 偏好 / 上下文 / 边界），起手只填内容不改结构；
- 团队场景拆成两层："共享约定"进仓库，"个人档案"本地保留，避免互相污染；
- 定期做冷启动测试：开全新会话，只靠 USER.md 问 Agent 三个你最常问的问题，回答不达标就回去补条目。

## 总结

USER.md 本质上是一份给 Agent 读的用户配置文件。它解决的不是模型能力问题，而是上下文工程问题：把"你是谁"从每次会话的口头交代，变成一份版本化、结构化、可审计的静态资产。写好它大概半小时，之后每一次会话都在还你时间。
