## 背景

跑 OpenClaw / Agent 一段时间后，多数人会经历同一个循环：agent 想跑个测试，先猜 node 在哪、用 npm 还是 pnpm、项目根目录是哪个；猜错了就报错，你再口头纠正一次。更麻烦的是家里 NAS、公司电脑、VPS 三台机器环境各不相同，同一个 agent 换个宿主机，行为就开始漂移。

这些问题的共性只有一条：环境事实没有被固化成 agent 可读的持久知识，只散落在你的聊天记录里。

## 问题：环境信息没有落点

常见的三种错误姿势：

1. **全塞进 AGENTS.md**——行为规范和环境事实混在一起，文件膨胀，重点被稀释；
2. **靠 system prompt 现场喊话**——每次会话重复一遍，忘了一次就翻车一次；
3. **什么都不写，指望 agent 自己探测**——探测成本高且会猜错，差异越大的机器翻得越狠。

OpenClaw 的 workspace 里专门留了 tools.md 这个位置：它是写给 agent 看的工具与环境笔记，会进上下文，agent 也有权限维护它。定位摆对，它就是成本最低的环境管理方案。

## 做法：四个区块，固定结构

把 tools.md 当成一份精简的“机器说明书”来写：

**1. 环境事实（只写稳定项）**
OS 与包管理器（macOS 用 brew，VPS 用 apt）；runtime 管理方式（node/python 由 mise 管理，shell 需先激活）；项目根路径与常用脚本入口（`make test`、`pnpm dev`）；代理端口等网络形态。

**2. 检查命令（先探测，再动手）**
比如“跑任何 node 命令前先 `mise which node` 确认”。用一条命令代替一段描述，agent 执行起来最可靠。

**3. 禁止事项**
不全局 pip install、不动 `~/.ssh`、不在根目录执行清理类命令。这一段收益最高，防的是不可逆事故。

**4. 已知坑**
踩过的坑修完后追加一行结论，例如“Podman 下 bind mount 要加 `:Z`”。一句话即可，不写过程。

篇幅控制在 30–60 行。tools.md 是常驻上下文的，每多一行都是持久成本。

## 踩坑点

- **写成流水账。** 把对话结论原样粘贴进去，几百行之后 agent 反而抓不住重点。定期删旧条目，只留仍然成立的规则。
- **记录易变状态。** 当前分支、临时 IP、实验性配置写进去，一周后就是误导源。易变的东西让 agent 现场跑命令确认，文件里只留稳定事实。
- **和 AGENTS.md 重复。** 两处都写“测试用 pnpm”，改了一处忘另一处。分工要清：AGENTS.md 管行为与偏好，tools.md 管工具与环境。
- **写入敏感信息。** token、内网密码进了 tools.md，等于进了模型上下文和编辑历史。用环境变量，文件里只写“凭据从环境变量读取”。
- **多机共用一份。** 宿主机事实互相矛盾时 agent 无所适从，可以按机器分节，或每台机器的 workspace 各维护一份。

## 可复用建议

- 建一个自己的四区块模板（事实 / 探测 / 禁止 / 已知坑），新机器初始化时先填事实和禁止两项；
- 养成“修完坑回写一行”的习惯：每次口头纠正 agent 后，让它把结论追加进 tools.md，成本一行，收益是同类问题不再发生；
- 月度审计一次：凡是一条命令能探测出来的信息，删掉描述，换成探测命令；
- 团队场景把 tools.md 纳入 dotfiles 或仓库版本管理，敏感机器单独维护。

## 总结

tools.md 不是配置文件，而是写给 agent 的环境 runbook。原则就两条：只记稳定事实和不可协商的禁令，其余交给现场探测。把“你脑子里的机器差异”翻译成 agent 每次都能读到的几十行笔记，多机漂移和重复踩坑这两类问题，会消掉大半。
