## 背景

大多数助手的默认形态是“应答器”：你不发消息，它就安静待着。但跑在 OpenClaw 上的 agent 其实具备先开口的条件——gateway 常驻、channel 已接通、cron/heartbeat 能定时把一段 prompt 注入 session，MCP 工具又能让它读到外部状态。缺的不是能力，而是一套“什么时候该说话”的规则。

## 问题

把被动改主动，工程上会撞到三个问题：

1. 触发从哪来——定时、事件还是状态变化；
2. 决策谁做——写死的规则，还是让模型自己判断值不值得打扰；
3. 动作边界在哪——只汇报，还是直接执行。

这三件事不想清楚，做出来大概率是消息轰炸机。

## 做法

我的落地路径，四步：

**1. 场景盘点。** 只挑两类：我每天固定会问的（早间日程 + 关键指标），以及事后才发现、其实希望立刻知道的（CI 挂了、磁盘超阈值）。其他一律不做。

**2. 分层触发。**
- 时间驱动：cron 触发，agent 醒来自查任务清单、汇总一份摘要；
- 事件驱动：webhook / MCP 事件把结构化 payload 推进 session，由 agent 决定是否转述；
- 状态驱动：轮询只读接口，变化超过阈值才注入。

**3. 决策收敛。** 触发后先跑一段固定的“值机 prompt”：让 agent 按新信息量、时效性、上次互动间隔打分，低于阈值只写日志、不发消息。这一步是整套方案里性价比最高的。

**4. 动作分级。** L0 只记录；L1 汇总后通知；L2 通知并附建议命令；L3 直接执行——仅限白名单动作，事后必须带回执。新场景一律从 L1 起步。

## 踩坑点

- heartbeat 最初设了 15 分钟，一晚上刷了三十条“没有值得汇报的事”。改成 6 小时起步、加上抑制器才安静下来。
- 主动触发的 session 没有对话上下文，模型容易自己脑补。解决办法是触发时注入结构化摘要（来源、证据、时间），不指望它记得。
- webhook 重试导致同一告警推送两次。加了事件 ID 去重才解决——幂等必须做在触发层。
- L3 试运行时它“顺手”改了 staging 配置：没违反指令，但超出预期边界。白名单从“动作类型”细化到了“目标对象 + 参数范围”。
- 多通道降级：Telegram 能带图，纯文本通道就得另备短模板。

## 可复用建议

- proactive = 触发器 + 抑制器 + 分级动作。先做抑制器，再做触发器。
- “要不要打扰”必须是显式判断，可解释、可回看；每次主动触达都落审计日志，被忽略的动作下次自动降一级。
- L3 上线前先跑两周 L1/L2，用人肉复盘替代信任。
- 触发源注入的上下文统一 schema，以后换模型不换逻辑。

## 总结

proactive 的本质不是让 agent 更聪明，而是给它一套守规矩的调度：触发源工程化、打扰决策可解释、动作可回滚。这三件事做扎实，它先开口才是帮你省事，而不是制造新的待办。
