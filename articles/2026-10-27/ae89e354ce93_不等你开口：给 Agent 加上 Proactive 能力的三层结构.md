## 背景

绝大多数 agent 的使用模式是"你问它答"。即便接了 MCP、挂了一堆工具，本质上仍是个更聪明的查询接口。真正省时间的场景往往是反过来的：CI 挂了它先去看日志，早晨它把昨晚的 PR 和日程冲突汇总好推给你。这类 proactive 能力在 OpenClaw 这类可自托管的架构里完全可做，核心是把"触发"从用户输入中解耦出来。

## 问题

把 reactive agent 改造成 proactive，会撞上三个工程问题：

1. **触发从哪来**：模型不会自己醒来，必须有外部时钟或事件源。
2. **何时该开口**：不是每件事都值得打扰用户，推多了被静音，等于白做。
3. **权限边界**：主动不等于自主，带副作用的动作不能无人把关。

## 做法

我目前的结构分四层：

**1. 触发层**。两类来源：定时触发用 cron（如工作日 9:00 的晨报任务）；事件触发用 webhook（监控告警、git push、邮件到达）。每个触发带一个 source 标记，后面防自循环要用。

**2. 任务队列**。触发不直接跑 agent，先入队。好处是削峰、可去重、失败可重试，也方便统计每个触发源的实际价值。

**3. 决策门**。入队后先过一个廉价判断（规则或小模型）：这件事值不值得打断用户？我按三个维度打分——时效性、与用户的相关性、是否处于免打扰时段。低价值触发在这里直接丢弃，不进主模型，省 token。

**4. 执行与反馈**。只读动作（汇总、检查、报告）执行后直接推送；写动作（给其他人发消息、改配置）生成草稿等确认。每次主动行为连同触发来源写进日志和记忆，跑两周后回头统计哪些触发根本没人看，下掉。

## 踩坑点

- **自循环**：agent 自己提交代码触发 CI webhook，又去"调查"自己的 commit，差点无限循环。解法就是触发层的 source 标记：凡是 agent 自己动作引发的事件，默认降级或吞掉。
- **通知疲劳**：最初晨报塞了十几个板块，第三天我自己都开始跳着看。现在固定不超过三条要点，细节留给追问。
- **陈旧上下文**：定时任务跑起来时，agent 拿到的还是昨天的缓存工具结果。触发的每次执行都要强制拉新数据。
- **成本失控**：一个高频 webhook 一天能烧掉几十次完整 agent run。过滤必须放在触发层和决策门，不能指望模型自己"少说点"。

## 可复用建议

- 先做只读类主动任务，观察两周再放开写权限。
- 主动策略（时段、频率、渠道、阈值）收敛到一个配置文件，别散在各个触发器里。
- 决策门独立于主 agent，用最便宜的方案实现——它的调用频率远高于主流程。
- 每条主动推送带来源标记，用户回一句"这类以后别推"就能直接降权。

## 总结

Proactive 不是"更多自动化"，而是"自动化 + 什么时候该说话的判断"。触发层解决醒来的问题，决策门解决打扰的问题，反馈环解决越用越准的问题。三层都做薄、各自独立，出问题也好排查。建议从每天一次的定时晨报起步：风险最低，体感最强，一周内就能验证这套结构是否适合你的工作流。
