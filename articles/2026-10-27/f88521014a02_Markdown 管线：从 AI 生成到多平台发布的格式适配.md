## 背景

在 OpenClaw / Agent 工作流里，产出物基本是 Markdown。但下游平台——静态博客、公众号、知乎、掘金、团队 Wiki——对 Markdown 的支持各不相同：有的吃完整 GFM，有的剥离内联 HTML，有的连脚注和任务列表都不认。我们的做法是把「AI 生成」和「平台适配」拆成两段，中间用一条确定性转换管线连接。

## 问题

直接把模型输出粘贴到各平台，会遇到三类麻烦：

1. 模型输出不稳定：标题层级忽高忽低，偶尔夹带内联 HTML 或多余表情；
2. 方言差异：代码块渲染、表格转义、图片外链规则各平台不一致；
3. 人工修补不可持续：每发一篇手动改一遍，等于没有管线。

## 做法

核心原则：**一份 canonical Markdown 作为唯一事实源，所有平台版本都是构建产物。**

1. **规范化**：AI 产出先过 mdast（remark / mistune 均可），统一标题层级、剥离内联 HTML、合并多余空行，输出 canonical.md 加 frontmatter（标题、标签、目标平台列表）。
2. **方言档案（profile）**：为每个目标平台声明「支持哪些节点、不支持哪些节点、如何降级」。比如公众号 profile：外链转脚注、代码块降级为内联样式的 HTML 片段。
3. **AST 级转换**：适配逻辑全部写成 mdast 上的纯函数，禁止对原文做正则替换。图片节点统一走「先传图床、再回写 URL」的插件。
4. **校验门禁**：构建时跑 lint——链接可达、图片存在、代码块有语言标注、profile 内无不支持节点。任一失败即构建失败。
5. **幂等发布**：以 canonical 内容哈希加 profile 版本号做缓存键，内容没变就不重发。

整条管线封装成一个构建命令或 MCP tool，Agent 侧只需一次调用，拿到各平台产物路径即可。

## 踩坑点

- 正则处理 Markdown 一定会在嵌套代码块上翻车：正文里的三反引号围栏会吞掉后续内容，这是我们最早转向 AST 的直接原因。
- YAML frontmatter 里含冒号的标题必须加引号，否则解析静默失败。
- 表格单元格内的竖线要转义成 `\|`，模型经常漏。
- 同一篇文档多平台发布时脚注 ID 会冲突，转换阶段要按 profile 前缀重编号。
- 图床回写 URL 注意幂等：重复构建不能重复上传，用图片内容哈希做去重键。

## 可复用建议

- 每个 profile 配一套 fixture：准备 3~5 篇覆盖表格、代码块、脚注、图片的样例文档，profile 一改就全量跑对比。
- 校验规则宁严勿松：遇到不支持节点直接报错，而不是静默丢弃——线上丢内容极难发现。
- canonical 文档永远不手改；要改就改生成它的 prompt 或后处理规则，重跑管线。

## 总结

这套管线的本质是把「格式适配」从人工经验变成声明式配置：canonical 源 + profile + AST 转换 + 门禁校验。接入新平台只需新增一个 profile 和两三个转换函数，而不是再造一遍流程。对 Agent 场景尤其友好——模型只负责产出高质量 canonical，格式确定性全部交给下游工程。
