## 背景

项目一多，Git 里的机械劳动就显眼：写提交信息、切分支前检查工作区、清理已合并的旧分支。这些事不难，但打断心流。OpenClaw 的 agent 自带 shell 执行能力，而 Git 本地、可回滚、行为可预期，很适合作为第一个自动化目标——前提是别把权限裸交给它。

## 问题

直接说“帮我 commit”会踩几个雷：

- agent 为了“完成任务”倾向 `git add -A`，把 `.env`、临时文件一起带上；
- 提交信息靠模型猜，和 diff 实际内容对不上；
- `reset --hard`、`push --force` 这类命令一旦被授权，误操作成本极高。

所以核心思路是：**读操作全自动，写操作半自动**。

## 做法

我用一个独立的 git skill 加一层包装脚本实现，四个要点：

**1. 命令白名单。** 允许 `status`、`diff`、`log`、`add`（限路径）、`commit`、`branch`；脚本里硬性拒绝 `push --force`、`reset --hard`、`clean`。护栏写在脚本和 skill 文本里，不靠对话记忆。

**2. 提交信息只准引用 diff。** 固定流程：先 `git diff --cached --stat` 概览，再按变更文件取 `--unified=2` 的 diff 喂给模型，要求按 Conventional Commits 模板输出，禁止出现 diff 里没有的文件名。生成后进入 dry-run：列出待提交文件和信息，确认后才真正执行。

**3. 分支清理只报告不动手。** 用 cron 每天跑一次：`git branch --merged` 找已合并分支，配合 `for-each-ref` 找 14 天无提交的旧分支，输出一份清单到会话。删不删我手动决定，skill 里明确禁止 `-D`。

**4. 全量审计日志。** 包装脚本把 agent 执行的每条 git 命令带时间戳 append 到日志文件，出问题回看，比翻会话记录靠谱。

## 踩坑点

- **diff 超长撑爆上下文。** 大重构几百行改动直接喂会截断，先 `--stat` 概览，再挑重点文件取细节。
- **模型脑补提交信息。** 只给变更摘要时它会编造“修复了 xx 问题”，必须喂真实 diff，并在 skill 里写死“只描述 diff 中可见的变更”。
- **pre-commit 钩子改文件导致循环。** 格式化钩子改了文件，agent 看到 dirty 又想提交。约定：commit 后最多重查一次 status，仍有变化就停下来报告。
- **amend 已推送分支。** 加一条规则：分支存在 upstream 时禁止 `--amend` 和 rebase。
- **提交信息风格漂移。** 模板里固定格式，避免中英混排忽左忽右。

## 可复用的建议

- 把“AI 提议、人确认”做成 skill 的默认姿态；全自动只留给 `status`/`diff`/`log` 这类只读操作。
- 护栏放代码里（包装脚本、白名单），不要只写在 prompt 里——prompt 会被长对话稀释。
- 先在个人仓库跑两周，每周看一次审计日志，再考虑推广到团队仓库。
- 凭证最小化：push 用受限的 SSH key，别把 token 明文交给 agent。

## 总结

Git 自动化的价值不在于让 agent “会用 git”，而在于把它的动作空间收窄到安全子集。白名单 + dry-run + 只报告的清理任务 + 审计日志，四件套搭好后，日常提交和分支琐事基本可以放心交出去，出错也有据可查。
