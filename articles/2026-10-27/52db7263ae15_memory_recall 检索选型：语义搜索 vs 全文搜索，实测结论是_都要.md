## 背景

Agent 跑久了，memory 里会积累大量历史会话摘录、用户偏好、项目约定。`memory_recall` 的职责就是在对话中把这些"该想起来的东西"捞回来。检索方案无非两条路：基于嵌入的语义搜索，或者 SQLite FTS5 这类全文搜索。两条路各有明显短板，单选一个迟早翻车。

## 问题

我们最初用纯语义搜索，遇到两类典型事故：

1. 用户问"上次那个部署脚本改到哪了"，召回了一堆聊过 Docker 的泛泛片段，真正含 `deploy.sh` 路径的那条排不进 top-5；
2. 换成全文搜索后，用户一改述就失灵，"之前说的那个端口冲突的事"直接查无结果。

精确命中和改述容错，恰好是两种检索各自的天赋和盲区。

## 做法

现在线上跑的是混合检索，结构不复杂：

1. **存储分两份**：memory 条目按"一条一个事实"写入，同时建 FTS5 虚拟表和向量列（sqlite-vec，嵌入用本地小模型，离线可用）。
2. **双路召回**：查询先抽关键词走 FTS5 MATCH，再算嵌入走 KNN，各取 top-10。
3. **RRF 合并**：两路排名用倒数排名融合，不调权重分数，实现省心且稳。
4. **时间衰减 + 截断**：融合分数乘一个按天数衰减的系数，最终只取 5~8 条进上下文。

## 踩坑点

- **FTS5 默认分词器基本不认中文**。整句中文存进去怎么都查不中，必须换 trigram 或接 jieba 分词后再建索引，这是最大的坑，没有之一。
- **语义搜索"什么都像"**。余弦相似度阈值卡太松（>0.6 就收），top-10 全是平庸相关。后来改成双阈值 + 至少一路强命中才采纳，噪声明显下降。
- **精确标识符别指望向量**。订单号、报错码、文件路径在嵌入空间里几乎没有区分度，这类查询必须靠全文路兜底。
- **衰减别过头**。系数调太狠，三个月前但很关键的架构决定就永远召不回了。最终用对数衰减，给老记忆保留底分。

## 可复用建议

- 中文场景优先把 FTS5 分词搞对，这是零成本、收益最大的一步；
- 向量索引不是必需品，查询里大量出现改述和代词指代时再加不迟；
- 检索质量的上限其实在写入侧：一条 memory 一个事实、写入时去重，比换任何检索算法都有效；
- 只想跑单路的话：偏技术向的 memory（路径、命令、配置）选全文，偏对话偏好的选语义。

## 总结

"语义还是全文"是个伪选择题，真正的答案是"怎么组合"。全文负责确定性命中，语义负责改述容错，RRF 缝合后加时间衰减，四十行以内的代码就能把 `memory_recall` 的可用性拉高一截。执行顺序建议是：先修分词，再上向量，最后回头治理写入质量——顺序别反了。
