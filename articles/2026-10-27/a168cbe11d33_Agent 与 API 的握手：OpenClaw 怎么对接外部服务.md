## 背景

Agent 的价值不在于会聊天，而在于能动手。在 OpenClaw 这类框架里，Agent 真正干活的路径几乎只有一条：调用外部服务——查数据、发请求、触发流程。MCP 和插件体系把这件事标准化了，但"能调通"和"调得稳"之间，差着不少工程细节。

## 问题

最常见的做法是把 API 文档塞进 system prompt，让模型自己拼 HTTP 请求。跑 demo 没问题，一上真实业务就崩：

- **参数幻觉**：模型编造字段名、日期格式，请求打出去才发现不对；
- **鉴权混乱**：token 写死在 prompt 里，轮换一次要改一片；
- **错误不可读**：agent 拿到 500 的原始堆栈，开始自由发挥；
- **上下文爆炸**：一个接口返回 20KB JSON，几轮对话就把窗口吃光。

根因是：把"协议适配"的活交给了概率模型。这件事应该由确定性代码来做。

## 做法：三层握手

我们的实践是把对接拆成三层，Agent 只见最上层。

**1. 工具层（Agent 可见）**

每个外部服务封装成 MCP tool 或 skill，描述写清三件事：什么时候用、参数含义、副作用（只读还是写入）。参数用 JSON Schema 收紧，能枚举的别开放成自由字符串。工具粒度宁小勿大——`查询订单`和`取消订单`分开，别做成一个`订单操作`大杂烩。

**2. 适配层（确定性代码）**

- 鉴权放环境变量或配置中心，工具启动时加载，token 过期在代码里自动刷新；
- 统一超时（比如 10s）、限流、指数退避重试；遇到 429 别傻重试，读 Retry-After；
- 返回值做投影：只吐 agent 需要的字段，分页数据给摘要加游标，别整包甩。

**3. 错误翻译层**

把 HTTP 错误映射成 agent 能行动的消息。`404` 不能只说 "not found"，而是"订单号 X 不存在，请确认后重试"。错误结构固定为 `{ok, error_type, hint}`，agent 才能稳定地走分支。

## 踩坑点

- **写操作没闸门**：对接第三方发送类 API，agent 理解错参数直接发出去了。所有非幂等操作加确认环节或 dry-run 参数；
- **重试风暴**：下游抖动时，agent 和工具层双重重试，请求量放大十倍。重试只做一层，其余向上抛；
- **密钥进日志**：debug 日志打了完整请求头，token 落盘。日志先脱敏再写；
- **时区与日期格式**：本地测试全过，一接真实数据就对不上。入参统一 ISO8601，在适配层转换；
- **工具描述偷懒**：一句"调用 XX 接口"，模型用错场景。描述里要写清适用条件和不适用条件。

## 可复用建议

1. 工具层与 LLM 解耦测试：写契约测试直接调工具函数，不跑模型，快且稳定；
2. 所有工具调用留结构化日志（工具名、参数摘要、耗时、错误类型），排查问题基本靠它；
3. 新接一个服务先做只读工具，观察一两周再决定是否放开写操作；
4. 描述模板固定下来：用途 + 参数 + 副作用 + 失败时的建议动作，团队内统一执行。

## 总结

Agent 对接外部服务，本质是一次"握手"：模型负责决策，工程层负责可靠。把协议、鉴权、错误翻译从 prompt 里挪进确定性代码，agent 的输出质量会立刻上一个台阶。OpenClaw 的 MCP/插件机制已经提供了足够的挂载点，剩下的就是老老实实的接口工程——少一点聪明，多一点纪律。
