## 背景

Agent 接上 MCP 和插件之后，能力从"回答问题"变成了"执行动作"：写文件、调 API、发消息、跑 shell、花预算。OpenClaw 这类框架把工具调用的门槛降得很低，低到配置几行就能让 agent 摸到生产环境。能力上去了，问题跟着来：它到底该自己干，还是停下来问人？

## 问题

实践中常见两种翻车，方向相反：

- **问太多**：每一步都弹确认，人变成盖章机器。几天之后所有人都会被训练成无脑点"允许"，确认机制形同虚设——这叫确认疲劳。
- **问太少**：agent 自作主张删了分支、把通知发进了大群、在错误的目录跑了清理脚本。事后复盘发现，工具权限配置里根本没设拦截。

核心矛盾在于：确认的价值依赖"人真的在看"，而人的注意力是稀缺资源。所以真正的问题不是"要不要问"，而是**在哪些操作上问，问的时候给什么信息**。

## 做法：三个维度定档位

判断一次工具调用要不要人工确认，看三个维度：

1. **可逆性**：能不能撤销？写 workspace 文件可逆；发消息、付款、删数据基本不可逆。
2. **影响半径**：只影响本机沙箱，还是会波及外部系统、其他人、生产环境。
3. **意图明确度**：用户原始指令是否直接覆盖了这个操作，还是 agent 自己引申出来的。

组合起来分四档：

| 档位 | 条件 | 策略 |
|---|---|---|
| A | 可逆 + 低影响 + 意图明确 | 自动执行，记日志 |
| B | 可逆但影响不明 | 自动执行，事后汇报 |
| C | 不可逆或外部副作用 | 必须确认 |
| D | 不可逆 + 高影响 | 确认 + 展示计划，必要时二次确认 |

落地步骤：

1. 给每个 MCP 工具/插件标注档位，写进权限清单。只读工具一律 A 档。
2. 在配置层做门禁：C、D 档工具调用前强制拦截，agent 无权绕过。
3. 确认时必须带上下文：做什么、目标是什么、改动 diff、怎么回滚。只弹一句"是否继续？"等于没问。
4. 高频 C 档操作改用"先出计划"模式：agent 产出一份执行方案，人批准的是 plan，不是逐条调用。这是对抗确认疲劳最有效的一招。
5. 硬护栏独立于判断逻辑：预算上限、调用频率、目录白名单，超线自动停机。这些不需要问，直接停。

## 踩坑点

- **无上下文确认**：弹窗里只有"允许/拒绝"，人只能瞎点。信息量决定确认质量。
- **MCP 配置一把梭**：为了省事把 shell 和全量文件系统权限给一个只需要读配置的 agent，档位直接失控。
- **授权存活太久**："本会话记住选择"一旦开启，几小时前的批准会掩护几小时后的误操作。授权应该有时间盒，最好绑定到具体目标。
- **审批时机错位**：agent 已经把状态改了一半才来问，此时确认毫无意义。要么先问后做，要么把确认点放在事务边界之前。

## 可复用建议

- 新 agent 默认只读跑一周，翻日志再逐级放档，不要一步到位。
- 每个插件维护一份权限清单：能调什么、副作用是什么、回滚命令是什么。
- 用环境隔离代替复杂判断：沙箱全放开，生产全确认。规则简单才守得住。
- 每周回看一次自动执行日志，发现误判就调档——档位是活的，不是一次配置定终身。
- 确认交互设计成批准/修改/拒绝三选，而不是二元开关。很多时候人想说的是"方向对，但改一下参数"。

## 总结

权限边界不是开关，是旋钮。原则可以压缩成三句：**可逆的小事自己干并留痕；不可逆或出了边界的事先问；问的时候把计划和回滚方案一起端上来。** Autonomy 的前提是 reviewability——所有自动执行必须可审计。信任建立很慢，清零只要一次事故。
