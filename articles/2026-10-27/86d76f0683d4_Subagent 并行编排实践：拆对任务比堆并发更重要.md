## 背景

我们团队在 OpenClaw 上跑的自动化流程，早期都是一个主 Agent 从头干到尾：拉需求、查 MCP 数据源、翻代码库、写报告，全程串行。功能上没毛病，但稍复杂的任务动辄十几分钟，而且主 Agent 的上下文被中间过程塞满，后半段输出质量明显下滑。引入 subagent 编排后，同类任务耗时降到原来的三分之一左右，这篇把做法和坑整理一下。

## 问题

串行单 Agent 有三个硬伤：

1. **慢**：相互独立的子任务（同时查三个 MCP 工具、审五个模块）被排成一列；
2. **上下文污染**：子任务的中间输出全堆在主对话里，真正的结论被稀释；
3. **单点失败**：一步跑偏，后面全歪。

## 做法

我们目前的编排方式分五步：

1. **先判断任务能不能拆**。只有满足"子任务相互独立、无共享写入、结果可汇总"才并行。只读类任务（检索、审查、扫描）最适合；有写入的操作要么隔离工作区，要么收敛回主 Agent 串行做。
2. **给 subagent 定契约**。每个 subagent 的 prompt 固定四段：目标、边界（明确不许做什么）、可用工具白名单、输出 JSON schema。主 Agent 拿到的是结构化结论，不是流水账。
3. **控制并发**。并行度压在 3~5。再高容易撞 MCP 服务的限流，排查难度也会陡增。
4. **失败显式化**。subagent 超时或报错时返回带错误码的结构，由主 Agent 决定重试还是降级，不静默吞掉。
5. **有依赖就分波次**。真存在先后关系的任务，拆成两波：第一波并行跑完，主 Agent 汇总后再发起第二波，而不是强行塞进同一次并行里。

## 踩坑点

- **prompt 太模糊**：subagent 返回一堆没法用的泛泛之谈。宁可写得啰嗦，也要把范围和输出格式钉死。
- **并行写冲突**：多个 subagent 同时写同一个文件，直接互相覆盖。我们的规则是并行任务只读，写操作统一回收。
- **返回内容失控**：subagent 输出太长，主 Agent 上下文反而爆得更快。强制摘要 + 结构化字段，并限制单条返回长度。
- **隐式依赖**：subagent B 其实需要 A 的结果，并行后 B 只能瞎猜。这类依赖必须在拆任务阶段识别出来。
- **成本翻倍**：每个 subagent 都是独立上下文。先在小任务上对比过耗时和 token 消耗，再决定是否值得并行。

## 可复用建议

- 把 subagent prompt 做成模板放进插件里，四个字段填空即可，别每次手写；
- 先串行跑通、验证结果正确，再加并行——并行只是加速手段，不是正确性手段；
- 每个 subagent 的调用留独立 trace 日志，出问题能单独回放，不用重跑整条链路；
- 对外部系统的写操作尽量做成幂等，subagent 重试才安全。

## 总结

subagent 编排的价值不在"多个 AI 很酷"，而在任务形状：独立的、只读的、可汇总的工作适合并行；有状态、有依赖、有写入的部分老实串行。契约严格、并发克制、失败显式，是这套东西能长期稳定跑下去的三个前提。
