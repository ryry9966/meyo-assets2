## 背景

OpenClaw 的长期记忆基本靠 `memory_recall` 这一个入口：Agent 每次要“翻旧账”——上周的部署参数、某个用户的偏好、某次事故的复盘结论——都是拿当前 query 去记忆库检索 top_k 条，塞回上下文。检索质量直接决定 Agent 是“想起来了”，还是一本正经地编。

记忆后端通常有两类可选：

- **全文搜索（FTS/BM25）**：按词面匹配，SQLite FTS5 一类实现，零额外依赖；
- **语义搜索（embedding + 向量索引）**：按“意思”匹配，需要嵌入模型和向量库。

## 问题

两者的失败模式都很典型，我各踩过一次：

1. **语义找不到精确标识符**。记忆里存的是 `err_code=0x8007`、`deploy-cluster-b3` 这类 token。问“上次那个 0x8007 怎么解决的”，向量检索返回了几条泛泛的“部署问题”记录，真正的条目排第 9，被 top_k=5 截掉。
2. **全文扛不住换说法**。记忆写的是“用户偏好浅色主题”，问句是“他喜欢什么界面风格”，BM25 一个词都对不上，空手而归。

所以真正的问题不是“哪个好”，而是：**各自的失败边界在哪，怎么组合。**

## 做法：40 条真实查询的小型评测

步骤很朴素，但比拍脑袋选型靠谱：

1. 导出记忆库确认规模（我的场景约 1200 条，单条 100–400 字）。
2. 从近两周会话日志里挑 40 条真实触发过 `memory_recall` 的 query，人工标注期望命中的记忆 ID。
3. 分别跑 FTS、语义、混合（RRF 融合两路排名）三种配置，统一 top_k=5。
4. 记录 hit@5 和“错误命中”数——语义相近但无关的记忆，最容易把 Agent 带偏。

我的结果（仅供参考）：

| 后端 | hit@5 | 备注 |
|---|---|---|
| 语义 | ~78% | 换说法类强，标识符类 6 条全挂 |
| FTS | ~62% | 标识符 8/8 全中，换说法类几乎全挂 |
| 混合（RRF） | ~90% | 标识符靠 FTS 兜底，错误命中降到 2 条 |

结论在这个场景里很清晰：**语义当主力，全文做兜底。**

## 踩坑点

- **中文分词决定 FTS 成败**。默认 tokenizer 对中文基本不可用，“浅色主题”可能整句匹配不到。要么前置 jieba 一类分词，要么启用 ngram 配置。
- **嵌入模型要在自己语料上抽查**。通用榜单分数高，不代表它在你的记忆库上区分度好。
- **chunk 别贪大**。单条记忆超 500 字后语义召回明显被稀释。我按“一个事实一条记忆”重新切分后 hit 提了约 8 个点。
- **top_k 别抠太紧**。截掉关键记忆的代价远大于多塞两条的 token 成本，混合检索下我固定 8。
- **记忆要带时间戳并做衰减**，否则一年前的旧方案会以高相似度挤掉上周的新结论。

## 可复用建议

1. **优先 hybrid，别二选一**。RRF 融合十几行代码就能实现，收益最大。
2. **入库保留原文**，别只存摘要——精确匹配靠原文，语义匹配靠全文或摘要嵌入都行。
3. **加结构化字段**（时间、项目、类型），检索前先过滤，同时降低错误命中和索引压力。
4. **维护 20–50 条真实 query 评测集**，每次换模型或调参跑一遍，避免“感觉变好了”。
5. **记录未命中和命中错的 case**，它们就是下一批评测集。

## 总结

语义搜索解决“说法不同但意思相同”，全文搜索解决“一字不差但很关键”，单用任何一个都会在另一侧翻车。工程上的答案不性感：hybrid + 真实评测集 + 持续看未命中日志。`memory_recall` 的上限不取决于检索算法多先进，而取决于你是否清楚自己记忆库里的 query 长什么样。
