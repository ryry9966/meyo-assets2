## 背景

跑 Agent 自动化时，把请求全交给云端模型有三个现实问题：隐私（MCP 工具会把本地上下文带出去）、成本（agent 循环的 token 消耗远超单轮聊天）、可用性（断网或限流时自动化直接停摆）。所以我花了两周末，在家用机（RTX 4070 Super 12GB + 一台 32GB 内存的 Mac）上做了本地化验证，目标是让 OpenClaw 的日常任务至少一半能落在本地模型上。

## 问题

本地部署本身不难，难的是"能跑"和"能干 agent 的活"是两回事。聊天场景 7B 模型就够，但 agent 循环里有长 system prompt、十几个 MCP 工具的 schema、多轮中间结果，对上下文长度和 function calling 可靠性的要求高得多。

## 做法

1. **盘点硬件**。显存是硬约束：12GB 显存实际能稳跑 14B 的 Q4_K_M 量化；Mac 统一内存 32GB 可以碰 30B 级别，但速度打折。先算账再选模型。
2. **选运行时**。要求只有两条：OpenAI 兼容接口 + 稳定。我用 Ollama 做日常，llama.cpp 做需要精细控制量化参数的场景。接口统一到 `/v1/chat/completions`，之后换模型不动代码。
3. **选模型和量化**。Q4_K_M 是默认起点，质量损失小、显存省一半。工具调用优先选对 function calling 友好的模型（Qwen 系列实测较稳）；R1 蒸馏版推理强，但输出带思考段，接 agent 前要先处理。
4. **接入 OpenClaw**。provider 指向本地 endpoint，显式设置上下文长度（千万别用默认值），温度调低。做一层环境变量级的配置切换，本地/云端一键换。
5. **用真实任务压测**。拿三个日常任务（日志摘要、文件整理、带两个 MCP 工具的信息查询）各跑十轮，记录成功率和 tok/s，用数据说话。

## 踩坑点

- **上下文静默截断是最阴的坑**。Ollama 默认上下文很小，超了不报错，表现是模型"忘了"系统提示、乱调工具。必须显式把 `num_ctx` / context length 设够。
- **显存预算不止模型权重**。KV cache 随上下文线性增长，14B + 32k 上下文能直接 OOM。要么砍上下文，要么配置 offload。
- **量化伤工具调用比伤聊天明显**。低量化模型生成 function call JSON 时格式错误率上升。工具挂得多就上 Q5/Q6，或开结构化输出约束兜底。
- **别用跑分选模型**。本地模型做多步规划确实不如云端旗舰，承认这一点，把复杂任务路由回云端，本地只接确定性高的活。
- **笔记本注意散热降频**，长 agent 循环下 tok/s 会掉近一半。

## 可复用建议

- 按任务定规格：摘要/改写 7-8B 够用；带 MCP 工具的 agent 建议 14B 起步；tok/s 低于 15 的多步任务体验很差，把它当底线。
- 工具 schema 是上下文的大头，agent 里只挂必要工具，能省一半 token。
- 把验证过的「运行时版本 + 模型 + 量化」组合记下来，升级前先在副本上重跑一遍压测脚本。
- 本地/云端混合路由是务实解：本地兜隐私和可用性，云端兜复杂度。

## 总结

家用机跑本地模型如今已不是玩具，但要把它当**容量规划问题**来做：显存预算、上下文预算、工具调用可靠性，三个数字先算清楚再谈选型。我的结论是 12GB 显存 + 14B Q4 是目前 agent 场景的甜点配置，配合路由策略能覆盖约六成日常任务。剩下的留给云端，不硬撑。
