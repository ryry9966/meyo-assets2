## 背景

用 Agent 久了会遇到一个天花板：它再聪明，本质上还是被动的。你不发消息，它就永远沉默。OpenClaw 提供了一个朴素但容易被忽略的机制——heartbeat：Agent 按固定间隔被自动唤醒，读取工作区里的 `HEARTBEAT.md`，按其中的指令自主决定要不要干活、要不要打扰你。这个文件写得好不好，直接决定了 Agent 是"定时值班员"还是"定时烧 token 机"。

## 问题

多数人装好 OpenClaw 后只把它当聊天窗口用，`HEARTBEAT.md` 要么不存在，要么写成一堆"帮我盯着 XX"的模糊指令。结果两种：要么 Agent 每轮唤醒无事可做、白耗 token；要么它自作主张推送一堆无效消息，最后你干脆把 heartbeat 关掉，机制等于没配。

## 做法

我的 `HEARTBEAT.md` 现在固定为三个部分：

1. **执行规则（放最前面）**。明确告诉 Agent：每项任务先判断状态是否有变化，无变化直接回复 `HEARTBEAT_OK` 静默；只有状态变更或到期提醒才推送给用户。这一段是防骚扰的关键。
2. **任务清单（checklist 格式）**。每条写清"检查什么、判断条件、具体动作"。例如：
   - 每日 9 点：汇总未读 RSS，超过 3 条才发摘要，否则跳过
   - 每轮：检查 `~/sync/flag` 是否存在，存在则调用 MCP 工具处理后删除该文件
3. **状态落盘约定**。任务产出写进文件（如 `brief-2025-06-01.md`），而不是只留在对话里。Agent 下一轮醒来靠文件判断"上次做到哪了"，不依赖上下文记忆。

唤醒间隔从 30 分钟起步（配置里可调），低频任务用文件里的时间戳条件过滤，而不是一味调短 interval。

## 踩坑点

- **没写静默规则**：早期我没写"无事勿扰"，Agent 每轮都回"一切正常"，一天几十条消息。heartbeat 机制本身支持用 `HEARTBEAT_OK` 抑制投递，但一定要在文件开头重申，否则模型经常"忘了"。
- **指令太模糊**："帮我盯一下服务器"这种写法，Agent 只能靠猜。改成"curl 返回码非 200 且连续两次才告警"，行为立刻可预期。
- **清单堆积**：任务超过十几条后，每轮唤醒的 token 成本明显上升，且 Agent 开始漏项。我的原则是超过 8 条就砍或合并。
- **依赖记忆**：指望 Agent "记住上次汇报过什么"基本不可靠，跨会话状态一律用文件或 MCP 存。

## 可复用建议

把 `HEARTBEAT.md` 当成 cron + runbook 来写，而不是愿望清单：每条任务 = 触发条件 + 判断标准 + 具体动作 + 静默条件。先从一两个高频、低风险的任务跑两周，观察它实际推送的内容，再决定是否扩展。别急着塞花活，"每天一条有用的日报"远胜于"十件半吊子的自动化"。

## 总结

heartbeat 机制本身很轻，价值全在文件怎么写。写好了，Agent 才真正从"你问它答"变成"它巡检、有事才报"。这是我目前用 OpenClaw 性价比最高的一个配置，推荐每个跑长期 Agent 的人花半小时把这份文件认真改一遍。
