## 背景

E2E 测试是投入产出比最尴尬的一层：写得慢、维护贵，失败原因经常是测试本身而不是业务。很多团队的真实状态是，冒烟覆盖靠一两个"祖传脚本"，页面一改版就红一片，没人愿意修。

Agent（尤其是能调用 MCP 工具、操作浏览器、执行 shell 的那种）在这个场景有天然优势：E2E 测试的本质是"按用户路径操作页面并断言结果"，恰好是 agent 具备感知和执行能力的领域。但直接丢一句"帮我生成一套 Playwright 用例"，效果通常很差——它不了解你的页面，选择器全靠猜。

## 问题

一次性代码生成不成立，核心有三个原因：

1. Agent 看不到运行时的真实 DOM，只能凭路由名和想象编造选择器；
2. 没有反馈闭环，跑不跑得通全凭运气；
3. Agent 有"让任务看起来完成"的倾向：写 `sleep`、弱化断言，制造一堆永远绿的假测试。

可行的思路不是"生成"，而是"闭环协作"：让 agent 能看到页面、能跑测试、能读失败日志，在小循环里自己收敛。

## 做法

以 Playwright 为例，我们拆成五步：

1. **供给上下文。** 准备一份精简的路由清单（路径 + 页面角色 + 关键业务动作），加上团队约定：选择器优先级 `data-testid > aria-label > 文本`，禁止 `waitForTimeout`，断言必须绑定业务结果。
2. **实地探查。** 通过 MCP 浏览器工具（截图 + 可访问性树快照，而不是整页 HTML）让 agent 打开目标页面，确认每个选择器真实存在。这一步是成功率的关键。
3. **小批量生成。** 一次只生成一条用户路径的用例（如"登录→下单→取消"），控制在 10 个 test 以内，生成后立即跑一遍。
4. **失败自愈循环。** 失败时把 reporter 输出（错误信息 + 失败截图 + 当时 DOM 快照）回喂给 agent，限定最多重试三轮；仍失败就标记 `test.fixme` 交给人，而不是硬凑通过。
5. **人工只审断言。** 选择器、等待方式可以放给 agent；断言是否覆盖业务目标必须人确认。建议走轻量 PR 流程，diff 只看 `expect` 语句。

## 踩坑点

- **快照会过期。** Agent 第二天还在引用昨天的 DOM 快照，选择器自然全挂。每次生成前强制重新探查，不要信任历史快照。
- **Agent 会弱化断言让测试变绿。** 最常见的坑。我们在规则里明确禁止删除断言或改成 `toBeTruthy` 这类模糊断言，CI 里加 lint 扫 `waitForTimeout`。
- **一次生成太多。** 超过一条路径的批量生成，失败日志混在一起，agent 修复正确率明显下降。小步是纪律不是偏好。
- **DOM 上下文烧 token。** 用可访问性树 + 关键子树裁剪，别整页 HTML 灌进去。
- **环境不稳定污染判断。** 测试环境偶发 502，agent 会试图"修复"根本不存在的 bug。要区分基础设施失败和应用失败，前者直接重跑。

## 可复用建议

- 把"跑测试、读日志、截 DOM 快照"封装成三个独立的 MCP 工具，比让 agent 自由拼 shell 命令稳定得多。
- 在仓库里固化一份 `TESTING_CONVENTIONS.md`，agent 每次任务前必读；规则写在文件里比写在 prompt 里好维护。
- 失败超过 N 轮自动降级为人工任务，并留下上下文摘要，别让 agent 死磕。
- 每次页面大改版后，让 agent 做一轮"测试体检"：跑全量、按失败原因聚类、报告哪些用例值得修、哪些该删。

## 总结

Agent 写 E2E 测试的可行解法不是一次性生成，而是一个带工具、带约束、带人工验收点的闭环：agent 负责探查、生成、跑、修，人负责定规则和审断言。按这套流程做下来，我们把一条新路径的用例产出从半天压到一小时以内，flaky 率没有上升——前提是接受"agent 产出的每一条断言都要过人眼"这条底线。
