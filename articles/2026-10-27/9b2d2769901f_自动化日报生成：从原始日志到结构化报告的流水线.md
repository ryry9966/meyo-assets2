## 背景

团队每天要出一份"昨天发生了什么"的日报：服务报错数、定时任务成败、Agent 运行记录、代码变更。人肉整理的痛点不是难，而是重复、易漏、口径不稳。既然 OpenClaw 侧已经跑着一批定时 Agent，顺手把日报也做成一条流水线，是最自然的切入点。

## 问题

原始日志有三个特征：**分散**（服务日志、cron 输出、git 提交、监控告警各在一处）、**噪声大**（DEBUG 级别和重复堆栈占了九成）、**无人直接阅读**。日报的本质不是搬运日志，而是回答三个问题：有没有异常、趋势是否平稳、今天该关注什么。

## 做法

流水线分四段，核心原则是：**确定性的事情交给脚本，叙述性的事情交给模型。**

1. **采集**：收集脚本把各来源日志拉到本地 staging 目录，按日期命名，如 `logs/2025-06-01/`。服务日志走 tail 导出，git 用 `log --since` 拉取，告警走 API。
2. **预处理**：这步全部用代码，不碰模型。过滤 DEBUG、按错误指纹去重聚合、统计每类错误次数与首末时间、算接口 P95 延迟。产出一个字段固定的中间 JSON：`error_summary`、`job_results`、`deploy_events`、`metrics`。
3. **模型归纳**：把中间 JSON 喂给 Agent，prompt 里明确要求：只允许引用 JSON 中出现的数字，禁止推测；输出也必须是固定 schema 的 JSON，含 `highlights`、`risks`、`todo_suggestions` 三个数组。
4. **渲染与投递**：Jinja2 模板把两段 JSON 拼成 Markdown 日报，先落盘归档，再由 Agent 通过 MCP 工具推送到群 webhook。cron 每天早上触发整条链路。

## 踩坑点

- **别让模型算数**。第一版让它直接读原始日志写结论，错误次数被数错过两次。改为脚本算数、模型只写叙述后，这类幻觉归零。
- **日志太大塞不下上下文**。预处理阶段就做截断和 Top-N 聚合，进模型的永远只有中间 JSON，成本可控。
- **时区与日切边界**。服务日志是 UTC，人的日报是本地时间，第一周两者相差八小时。统一在采集层转本地时间并固定日切点。
- **流水线本身会静默失败**。日报没发出来没人发现，比日报难看更糟。加了个 watchdog：超过 09:30 未产出当日文件就告警。
- **schema 漂移**。模型偶尔在输出 JSON 里加字段或改键名，渲染直接崩。加一层 JSON Schema 校验，不合法就带着原始输出重试一次。

## 可复用建议

- 把中间 JSON 当作"契约"：预处理和渲染各自独立，中间产物按日期归档，任何一天都可以离线重跑和回溯。
- 报告幂等：同一天重复执行覆盖同一文件，避免补跑时群里出现重复消息。
- prompt 与 schema 放仓库里版本化，日报格式变更走 review，和代码同等对待。

## 总结

这条流水线的价值不在"省了十分钟"，而在口径稳定：数字永远来自脚本，模型只负责把人话写好。跑稳之后，同样的骨架换个采集脚本，就能复用到周报、Agent 运行周检等场景。
