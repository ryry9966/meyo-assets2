## 背景

OpenClaw 的 workspace 里有一组约定文件：`AGENTS.md` 管操作流程，`USER.md` 记用户偏好，`MEMORY.md` 存长期记忆，而 `SOUL.md` 负责最上面那一层——这个助手是谁、说话什么腔调、什么不做。它会在会话启动时注入 system prompt。很多人装完直接跑，agent 能干活，但"性格"是随机的：今天极简，明天话痨，遇到敏感请求一口答应。

## 问题

把人格直接写进 gateway 的 system prompt 也能用，但有三个工程上的麻烦：

1. 改一次要重载，迭代慢；
2. 人格、操作规范、用户上下文混在一起，改语气容易误伤流程规则；
3. 无法版本化，出问题回溯不了"当时它是被怎么定义的"。

## 做法

我的 `SOUL.md`（`~/.openclaw/workspace/` 下）约 60 行，分四段：

**1. 身份与语气：写可观察行为，不写形容词**
不要写"友善、专业"，写"回复先给结论，再给两条理由；不确定时明说，不编"。形容词模型各自理解，行为描述才能验收。

**2. 价值观排序**
例如：隐私 > 准确性 > 效率，并明确"宁可多问一句，不猜"。

**3. 边界（最关键的一节）**
- 不做：支付操作、批量删除文件、代我向联系人发消息；
- 需确认：一切对外发送和不可逆操作；
- 给一句固定的拒绝话术模板，避免每次拒绝风格漂移。

**4. 与其他文件分工**
SOUL.md 只管"是什么样的人"，"怎么调工具、怎么写 cron"放 AGENTS.md。判断标准：这条规则换个任务还成立吗？成立进 SOUL，不成立进 AGENTS。

改完 `git commit`——它就是个文件，天然支持 diff 和回滚。

## 踩坑点

- **写太长**：超过 150 行，中段规则在长上下文里常被稀释，控制在 80 行内；
- **把边界当硬过滤**：SOUL.md 是软约束，模型偶尔越线。高风险操作要靠工具层兜底——MCP 工具加确认参数、目录白名单，别指望 prompt 一个字顶住；
- **多 agent 共用一份**：主助手和 cron 定时播报员用同一份人格，会输出不合场景的客套话，按 agent 拆文件；
- **只写一次**：接了新插件、换了模型，人格和边界要复审，否则规则和现实脱节。

## 可复用建议

- 用行为清单代替形容词，每条都能设计测试用例验证；
- 边界分三层：禁止 / 需确认 / 放行，配合 MCP 工具权限做双保险；
- 每次表现不对劲，先改 SOUL.md 再 commit，积累出自己的调教史；
- 每月跑一组对抗性提问（诱导、越权、含糊指令），确认边界仍生效。

## 总结

SOUL.md 不是玄学，它把"我希望助手是什么样"从脑内默认值变成一份可评审、可版本化、可回归测试的配置。写它的过程本身就有价值——多数人写完才发现，自己从没认真想过 agent 的边界在哪。先从 20 行开始，跑两周，再迭代。
