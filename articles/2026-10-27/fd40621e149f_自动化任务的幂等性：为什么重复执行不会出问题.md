## 背景

跑过一段时间 OpenClaw 定时任务的人，大概率遇到过这种场景：同一个 cron 任务明明只配了一次，群里却收到两条一模一样的日报；或者一个 webhook 触发的 agent 流程，因为上游重试，同一件事被执行了两遍。

这不是概率意义上的 bug，而是自动化的固有属性：网络超时会重试、调度器可能重复投递、人也会手滑多点一次。手动操作时你盯着屏幕，重复了当场能发现；自动化任务没人盯着，**重复执行必须被当作默认输入来设计**。这就是幂等性要解决的问题：同一个任务执行一次和执行多次，最终状态一致。

## 问题

翻车点几乎都集中在"写"操作上：

- agent 调 MCP 工具往 issue tracker 建单，超时后框架重试，第一次其实已经成功，结果出现两张重复工单；
- 日报脚本重跑，通知渠道被刷屏；
- 数据同步插件用 insert 语义写库，重试后出现重复行。

根源在于这些操作的语义是"追加"，而不是"确保存在"。读操作天然幂等，写操作默认不幂等，而自动化场景里恰好全是写。

## 做法

原则很简单：**把幂等落在工具层，不指望模型层**。agent 的输出有随机性，去重逻辑不能依赖它。

1. **定义稳定的幂等键。** 用业务标识而不是随机值：日报的键就是日期，同步任务的键是源记录 ID，webhook 处理用事件 ID。键必须在多次重试之间保持一致——所以应由调度器/调用方传入参数，而不是让 agent 每次现编一个 UUID。
2. **写之前先查，或直接 upsert。** 比如"确保 label 为 `daily-2024-06-01` 的 issue 存在，存在则更新正文"，而不是无条件创建。数据库层用 `INSERT ... ON CONFLICT` 配合唯一索引兜底。
3. **原子化副作用。** 文件写入用临时文件 + rename；建目录用 `mkdir -p` 语义；外部 API 若支持幂等键头（支付、消息类常见），一律带上。
4. **大任务拆成各自幂等的小步骤。** 三步串行任务挂在第二步，重试时不应重做第一步——用状态记录推进到哪一步了，从断点续跑。

## 踩坑点

- **check-then-act 的竞态。** 先查再建并不保险：两个实例并发执行，都查到"不存在"，然后各建一份。真正可靠的兜底是存储层唯一约束，应用层判断只是优化。
- **键不稳定。** 拿时间戳或随机数当幂等键，等于每次都是新任务，重试照样重复。最常见的错误是让 LLM 自己生成 ID。
- **伪幂等。** "先删光再重建"看起来结果一致，但下游的 webhook、通知、外键引用全被殃及。判断幂等要看全局副作用，不是只看自己那张表。
- **部分成功无记录。** 任务做了三步挂第二步，又没有任何状态留存，重试只能从头来，前面所有非幂等步骤全部重放。

## 可复用建议

- 默认假设任何任务都会被执行至少两次，第二次可能在五秒后，也可能在三天后。
- 幂等键 = 稳定业务标识，由调度器传参，不让模型生成。
- 工具接口尽量设计成"确保达到目标状态"（upsert、`mkdir -p` 式语义），而不是"追加一次"。
- 兜底交给唯一约束和原子操作，应用层 if 判断只算锦上添花。
- 保留执行日志，出问题时你能回答"到底跑了几次、跑到哪一步"。

## 总结

幂等性不是自动化做完之后的优化项，而是入场券。手动的世界里，重复靠人眼兜底；自动化的世界里，只能靠设计兜底。把"这个东西会被重复调用"写进每个工具和插件的默认假设，你的 cron、webhook 和 agent 才敢真的放手让它跑。
