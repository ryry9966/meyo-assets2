## 背景

LLM 会话本身无状态。每次新会话，助手都从零开始：你上次明确说过“回复尽量简短、代码要带注释、时区按 UTC+8 处理”，这次它照样忘。一次性问答无所谓，但如果你在用 OpenClaw 搭长期运行的 Agent——日报生成、代码审查、自动化运维——记忆缺失会直接体现在输出质量上。MCP 和插件生态解决的是“能力”问题，记忆系统解决的是“上下文”问题，两者互补，不可替代。

## 问题

两种朴素做法都会失败：

1. **全量塞 system prompt**：几轮之后 prompt 膨胀、成本上升，旧指令和新指令互相打架；
2. **全量聊天记录做 RAG**：检索回来大多是无关注水，关键偏好反而被淹没。

根因在于：记忆不是“存”的问题，而是**写入过滤 + 分层检索 + 冲突处理**的工程闭环。

## 做法

**1. 分层。** 至少三层：工作记忆（当前会话）、偏好记忆（稳定的用户约定，如风格、习惯、环境）、事件记忆（带时间戳的历史事实，如“上周部署过 v2.3”）。偏好常驻，事件按需检索。

**2. 结构化写入。** 会话结束后跑一次抽取：用便宜模型把候选记忆抽成记录——`{type, content, source_quote, confidence, created_at}`。关键约束：content 必须附对话原文引用，防止模型“替用户发明偏好”。

**3. 写入过滤。** 入库前两道闸：embedding 相似度 > 0.9 的去重合并；新旧冲突（“喜欢简短” vs “这次要详细报告”）走一次 LLM 裁决，带时间戳，新覆盖旧并保留版本。

**4. 分层检索。** 偏好记忆分两档：核心档（10 条以内）每次会话注入 system prompt；长尾档走向量检索按需取 top-k。别把所有记忆都塞进去。

**5. 出口与反馈。** 提供可见入口（一个 MCP 工具或 `/memory` 命令）让用户查看、编辑、删除。显式指令“记住 XX”直接写入；用户对话中的纠正（“不是这个意思，我是说……”）作为高置信信号触发抽取。

## 踩坑点

- **抽取幻觉**：模型会把推测写成事实。强制 `source_quote` 字段，无引用不入库。
- **过期偏好霸榜**：加 `last_hit` 字段和衰减权重，长期未命中的自动降级或归档。
- **记忆投毒**：工具返回的不可信内容里混入“指令”被当成偏好存下。只从用户消息抽取，工具输出仅作参考。
- **敏感信息**：写入前过滤密钥、token 类内容，本地存储加密。
- **注入过量导致行为漂移**：核心档满了先做淘汰，不是扩容。

## 可复用建议

- 先用 JSON 文件 + embedding 起步，几千条以内完全够用，别一上来上重型向量库。
- Schema 固定五个字段起步：`type / content / source_quote / confidence / created_at`，够调试也够演进。
- 把写入过滤做成独立模块，方便单独评测：回放一批历史会话，人工抽查 20 条入库结果，比任何指标都直观。
- 记忆查看界面（哪怕只是个列表）不是锦上添花，是排障刚需。

## 总结

记忆系统的难点不在存储与检索本身，而在写入质量和更新策略。一个小而闭合的循环——结构化抽取、去重裁决、分层注入、可查可删——比套大框架有效得多。先让 10 条核心偏好 100% 生效，再考虑规模化。
