2025 年 2 月底，DeepSeek 搞了个“开源周”：五天连发五个仓库——FlashMLA、DeepEP、DeepGEMM、DualPipe、3FS，节奏紧凑得像在清库存，但清的全是压箱底的原厂件。几个小时内，SGLang 宣布完成 FlashMLA 集成并跑通测试，vLLM 次日跟进合并，社区跑分随后一路刷新。热搜标题写“连夜性能反超”，多少有点戏剧化，但这场“模型厂放零件、框架厂连夜装车”的接力赛，确实是观察大模型推理生态运作机制的最佳切片。下面拆开讲：放了什么招、为什么接得住、速度到底在卷什么，以及普通开发者能带走什么。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-27/dd74cbcac23eb3aa.png)

## 开源周放了什么：五个仓库，五块硬骨头

先把清单过一遍，每一样都对应推理/训练链路上的一个具体瓶颈：

- **FlashMLA**：面向 Hopper 架构（H800）优化的 MLA kernel。MLA 是 DeepSeek-V2/V3 采用的注意力结构，核心卖点是把 KV cache 压得极小。FlashMLA 把它跑到显存带宽约 3000 GB/s、算力约 580 TFLOPS 的量级——decode 阶段是 memory-bound，带宽就是生命线。
- **DeepEP**：MoE（Mixture of Experts）专家并行的 all-to-all 通信库，提供两套 kernel：高通量模式（NVLink+RDMA）服务 prefill，纯 RDMA 低延迟模式服务 decode 的稀疏 dispatch。
- **DeepGEMM**：FP8 GEMM 库，支持细粒度 tile-wise scaling，H800 上峰值 1350+ TFLOPS，靠 JIT 编译适配任意矩阵形状。
- **DualPipe & EPLB**：双向流水线调度，让计算与通信互相重叠，附赠专家并行的负载均衡策略。
- **3FS + smallpond**：面向训练数据管道的分布式文件系统，180 节点集群压测出约 6.6 TiB/s 的聚合读取吞吐。

一句话总结：没有 demo，没有 PPT，全是生产线上拆下来的原厂件，而且都是 MIT 协议，随便用。

## 为什么框架能“连夜”接住：接口早留好了，只换零件

这件事快得反常识，其实前置条件早已铺好：

1. **生态位早已卡住**。V3/R1 发布时，SGLang 和 vLLM 就做了 Day 0 支持。SGLang 此前靠一系列 MLA 优化把 V3 的吞吐拉高过数倍，vLLM 的 PagedAttention 也是 KV cache 管理的老牌方案。框架对这两个模型的内部结构早就熟门熟路。
2. **零件是模块化的**。开源周放出的是 PyTorch extension 风格的 kernel 和通信原语，不是一整套 serving 系统。框架要做的只是把旧算子替换成更快的新算子，改动面可控。SGLang 团队当晚就合并支持、跑通精度测试，vLLM 次日跟进。
3. **分工天然清晰**。模型团队最懂算法结构——MLA 压缩了什么、MoE 的访存模式是什么；框架团队最懂 serving——batch 调度、KV cache 管理、CUDA graph。零件厂和整车厂各干各的强项。

所以“反超”的真相并不神秘：不是哪个框架被一夜颠覆，而是框架第一时间把更优的算子拼进整车，端到端跑分自然上台阶。工程上这叫“吃到了 kernel 红利”，而不是“底层被换血”。

## 卷速度到底在卷什么：两个阶段、两个指标

推理速度不是单一数字，至少拆成两段看：

- **prefill（读 prompt）**：compute-bound，把整个 prompt 一次性编码，堆算力、拉 GPU 利用率，决定 TTFT（首 token 延迟）。
- **decode（吐 token）**：memory-bound，每生成一个 token 都要把权重和 KV cache 在显存带宽上过一遍。这就是 FlashMLA 那个 3000 GB/s 重要的原因——带宽几乎直接决定出字速度。
- 对应的指标：TTFT 管“响应快不快”，TPOT/吞吐管“单位时间产出多不多”。对话场景看前者，离线批处理看后者；两者在调度上还互相拉扯——batch 打得越大吞吐越高，单条延迟往往越差。
- 系统级手段还包括：PD 分离（prefill 与 decode 拆到不同机器）、continuous batching、KV cache 分页与前缀复用（RadixAttention 的思路）。

举个直观的例子：同样是 671B 的 MoE 模型，喂一个 32K 长文档做摘要，prefill 阶段的通信效率和 GEMM 精度决定用户是“秒回”还是“转圈”；而逐字输出的流畅度，几乎全看 decode 阶段的带宽利用率。

## 互利循环：开源怎么变成基础设施

这轮接力赛真正值得记一笔的，是它跑通了生态飞轮：

- **模型厂视角**：把部署门槛打下来，等于让 V3/R1 长进各家框架和各家机房。生态位比闭源 API 更稳——大家天天在你的底座上跑，迁移成本本身就是护城河。
- **框架视角**：谁能最快集成、并在生产负载下稳定运行，谁就赢得用户。跑分是获客手段，稳定性才是留存手段。
- **飞轮闭环**：模型厂开源算子 → 框架快速集成 → 社区压测反馈真实负载数据 → 下一轮优化有了明确靶子。有点像当年 Linux 内核与各发行版的关系：内核给能力，发行版给体验，互相成就。
- **开发者视角**：单位 token 的推理成本在快速下探。今天还觉得贵的长上下文应用，过几个月可能就落进成本舒适区——这也是今年各家 API 敢打价格战的底层原因。

## 三条实用建议与一点冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-27/73d2806c12277d5c.png)

1. **别拿单一跑分选框架**。先画清楚自己的负载画像：高并发短请求看吞吐，长上下文对话看 TTFT，跑 MoE 模型重点看专家并行与通信效率。用真实流量压测，公开跑分只当参考线。
2. **升级 kernel 前先锁环境**。这类底层库对 CUDA 版本、GPU 架构（Hopper 还是 Ada）、驱动版本都有硬性要求。建议灰度小流量验证精度与稳定性，再全量上线——别在周五晚上直接推。
3. **分清 op-level 与端到端**。单个 kernel 快 50%，端到端可能只挪 5%～10%，取决于它占总耗时的比例。看 benchmark 先看测试条件：模型、并发数、序列长度、精度，缺一项都可能是“特定条件下的胜利”。

**冷思考**：这轮接力赛最值钱的不是某个具体数字，而是它示范了一种分工——模型厂把独家优化变成公共基建，框架厂在组合与调度上竞争。当底层能力被开源，竞争焦点就从“谁能造出来”变成“谁组合得更好”。对整个行业来说，这是把内卷用对了地方。
