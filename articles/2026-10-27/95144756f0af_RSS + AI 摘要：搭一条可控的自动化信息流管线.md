## 背景

时间线类产品的推荐算法决定你能看到什么，而 RSS 虽然老，但来源完全可控。问题在于订阅源一多，人工阅读就不现实了——这正是 LLM 摘要有价值的地方：先压缩，再阅读。本文记录我搭的一条「RSS → 清洗 → AI 摘要 → 定时推送」管线，以及在 OpenClaw 里落地的具体做法。

## 问题

「把 RSS 直接喂给模型」看似一行 prompt 的事，实际有三个坑：

1. 很多源只输出 summary 不给全文，摘出来全是车轱辘话；
2. 源的更新频率差异极大，逐条过强模型，token 成本和延迟都难看；
3. 同一事件多源重复，日报里一半是重复项。

## 做法：四层管线

**1. 采集层**：系统 cron 定时抓取 OPML 里的源，没有 RSS 的站点走自建 RSSHub 生成。抓到后写入 sqlite 的 entries 表，用 URL + guid 做幂等标记。

**2. 预处理层**：全文抽取（trafilatura）→ URL 归一化去重 → 按关键词和来源权重打分粗筛，只有过阈值的条目才进摘要。这一层决定了 80% 的成本，宁可 here 粗一点，也别把垃圾送进模型。

**3. 摘要层**：两段式。map 阶段用便宜模型给每条生成 1~2 句要点加标签；reduce 阶段按主题聚合，用更强的模型合成日报，并给死 token 预算上限。

**4. 分发层**：日报落成 markdown 归档，同时推送到 OpenClaw 配置的消息渠道。

OpenClaw 侧的分工：采集和预处理是纯脚本，不占 agent 资源；理解环节交给 OpenClaw 的定时任务——cron 触发一个会话，agent 从 sqlite 读待处理条目，调 LLM 生成日报再经渠道发出。把「读库 + 生成」封成一个 skill，prompt 里只管输出格式和预算。

## 踩坑点

- **全文抽取失效**：懒加载和反爬站点抽出来是空的，这类条目要降级为「仅标题」，并在 prompt 里明确告知信息不完整，否则模型会编。
- **去重不能只靠 URL**：转载会换链接，标题归一化后再做相似度兜底。
- **日期与时区**：不少源的 published 是 UTC 或格式混乱，必须统一解析，否则「今天的日报」里混着昨天的。
- **任务重叠**：上一轮没跑完下一轮又触发，加文件锁。
- **推送疲劳**：我一开始每 2 小时推一次，三天后把机器人静音了。改成每天早晚各一次固定摘要后，实际打开率高得多。
- **公共 RSSHub 实例不稳定**，重要源自建或直接用站点官方 feed。

## 可复用建议

- 分层解耦，每层可独立重跑：采集挂了不影响摘要，摘要挂了不影响采集。
- 所有状态进 sqlite，管线本身无状态；OPML、阈值、prompt 与代码分离成配置。
- 每次运行记录条目数和 token 消耗，跑两周后按数据调阈值，而不是拍脑袋。
- 摘要永远是索引不是替代，保留原文链接，重要内容点进去读原文。

## 总结

这条管线没有用到任何新技术，价值全在组合与克制：RSS 保证来源可控，预处理控制成本，两段式摘要保证质量，固定节奏推送控制打扰。在 OpenClaw 里，采集交给脚本、理解交给 agent、状态交给数据库，各干各的活。核心代码不到 300 行，但调参花的时间远多于写代码——这大概是所有信息管线的共同宿命。
