## 背景

给 Agent 接记忆系统时，`memory_recall` 是最容易被低估的一环。我们的做法是把助手运行中沉淀的事实（用户偏好、项目约定、踩过的坑）拆成一条条短条目存进 SQLite，对话时按需捞回。最初只上了向量检索，默认"语义搜索更聪明"，结果两周内被用户反复质疑"我明明告诉过你"，才开始正经做选型对比。

## 问题

把 badcase 拉出来复盘，分成三类：

1. **精确 token 召回失败**：项目代号、错误码、用户名这类词，向量检索经常匹配到"语义相近但不是它"的条目。查 `ERR_40213`，返回的是关于支付超时的泛化笔记，而不是当初记录的具体错误。
2. **换说法召回失败**：全文检索搜"部署脚本"找不到"上线那条 pipeline 的笔记"。
3. **静默失败**：top-k 返回空或全是噪声时，模型不承认没查到，直接编。

单用任何一种检索，至少踩中两类。

## 做法

最终落地是混合检索，流水线很朴素：

1. **条目原子化**：一条记忆只写一个事实，200 字以内，带时间戳、来源、scope 标签。这是后面所有效果的地基。
2. **双索引**：SQLite FTS5 建 BM25 索引，sqlite-vec 建向量索引。embedding 用多语言小模型即可，几千条记忆不需要重模型。
3. **召回融合**：查询抽取关键 token 走 FTS，同时算 embedding 取 top-8，两路结果用 RRF（倒数排名融合）合并。RRF 只看排名不看分数，绕开了两路分数量纲不可比的问题。
4. **后过滤**：按 scope 和时间衰减排序，重排后只给模型 top-3~5。
5. **留痕**：每次 recall 把 query、命中条目、是否被模型引用写日志，攒成评测集。

用攒下的 60 多条评测 query 跑 recall@5：混合方案比纯向量高约 15 个点，比纯 FTS 高约 25 个点，收益主要来自上面第 1、2 类 case。

## 踩坑点

- **中文分词**：FTS5 默认 unicode61 分词器会把整句中文当一个 token，全文检索等于直接失效。要么上 trigram，要么用 jieba 分词后再入库，这个坑耗了我们半天。
- **过期记忆**：语义检索对"曾经对、现在错"的条目毫无抵抗力，相似度照样很高。必须做时间衰减 + 显式失效标记，否则助手会坚持旧结论。
- **换 embedding 模型**：换一次就要全量重建向量索引，索引必须带模型版本号，别裸存。
- **top-k 贪多**：k=10 时噪声明显挤占上下文，模型反而开始忽略命中的条目，宁缺毋滥。

## 可复用建议

- 记忆量几千条以内，先只上 FTS（记得解决分词），不够再补向量，别一上来就堆架构。
- 条目写得越结构化，关键词检索越可靠；语义检索是兜底，不是主力。
- 检索质量别靠感觉调，先攒 30 条评测 query 再动手改。
- 召回为空时明确返回"未命中"，让模型选择追问，而不是硬答。

## 总结

memory_recall 的瓶颈通常不在"选哪个搜索引擎"，而在记忆条目本身的质量和失效机制。语义搜索和全文搜索各解决一半问题，混合检索 + RRF 是目前性价比最高的组合。先把数据和评测做扎实，再考虑换更大的 embedding 模型也不迟。
