## 背景：一问一答的天花板

绝大多数 Agent 的默认交互模型是问答式：你不发消息，它就永远安静。OpenClaw 有一个不起眼但很关键的机制——心跳循环：Agent 按固定间隔自行醒来，读取 workspace 下的 `HEARTBEAT.md`，根据文件内容判断"这次醒来要不要做事”。本质上，它是把一段持续生效的指令从会话里挪到了一个可版本化的文件里。

## 问题：主动性要么没有，要么失控

不用心跳，重复性巡检任务（盯日志、看磁盘水位、检查待办）只能靠 cron + 脚本，或靠自己记得来问。脚本僵硬、缺上下文；人脑提醒不可靠。

而配了心跳的人又常遇到另一个极端：`HEARTBEAT.md` 写得笼统，Agent 每次醒来要么空转烧 token，要么每小时汇报一次“一切正常”，把你轰炸到静音。

## 做法：四步跑起来

**1. 确认心跳启用并设置间隔**（`HEARTBEAT_INTERVAL_SECS`，默认约 30 分钟）。巡检类任务 15–60 分钟比较合理。

**2. 按四要素写每条任务：条件 + 动作 + 冷却 + 沉默规则：**

```markdown
## 磁盘水位巡检
- 条件：任一挂载点使用率 ≥ 85%
- 动作：发消息给我，附 df -h 的相关行
- 冷却：同一挂载点 6 小时内不重复提醒
- 否则：保持沉默，不要汇报"一切正常"

## 日志错误扫描
- 条件：~/logs/app.log 最近 1 小时新增 ERROR ≥ 5 条
- 动作：汇总去重后的错误摘要发给我
- 冷却：2 小时
```

**3. 关键是“否则”分支。** 明确告诉 Agent 无事发生时沉默。OpenClaw 在文件为空或只有占位内容时会直接跳过本次心跳、不调用模型——这是省 token 的关键设计，写满了反而丢掉这个优化。

**4. 让 Agent 自维护状态。** 允许它在 workspace 写一个小文件记录“上次提醒时间”，冷却逻辑靠它实现。跑 3–5 个心跳周期，把误报案例作为反例直接补进文件，迭代措辞。

## 踩坑点

- **心跳不是 cron。** 间隔只是唤醒，做不做、做多少由 Agent 判断，措辞含糊就会漏做或过做。
- **成本随任务数线性涨。** 每次心跳是一次模型调用，把 HEARTBEAT.md 当备忘录塞满，月末账单会教你做人。
- **时间感知不稳。** 模型对"每小时"的理解会漂，让它读系统时间，并在文件里写明时区。
- **消息风暴。** 多个任务同时触发、又没写冷却，就是连环轰炸。
- **权限复用。** 心跳执行用的是同一套工具权限，别安排需要人工确认的敏感操作——它要么卡住，要么自作主张。
- **重启丢状态。** workspace 清理后冷却记录丢失，可能重复提醒一次，属于已知代价。

## 可复用建议

- 把 HEARTBEAT.md 当**巡检 runbook**，不是愿望清单。四要素缺一不可。
- 从 1–2 个低风险只读任务起步（日志、磁盘），跑稳了再上有副作用的。
- 用 git 管它。Agent 行为异常时 diff 一下，多半能定位到哪次改动引入的。
- 提醒类任务合并汇报、设免打扰时段——写进文件即可，Agent 能遵守。

## 总结

HEARTBEAT.md 的价值在于把"主动性”从玄学变成文本配置：可版本化、可评审、可回滚。写好它的核心不是多写，而是写清“何时不做”。先让它安静地做对一两件小事，再逐步扩展——主动的 Agent 好用，聒噪的 Agent 只会被静音。
