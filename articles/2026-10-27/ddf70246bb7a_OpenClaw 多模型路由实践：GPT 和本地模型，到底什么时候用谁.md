## 背景

用 OpenClaw 跑了一段自动化之后，大家基本都会撞上同一个分叉口：任务五花八门——批量摘要、日志清洗、MCP 工具编排、长上下文规划——成本和可靠性要求完全不一样。全走 GPT 账单难受，敏感数据还要出网；全走本地模型，复杂任务的工具调用失败率又会明显抬头。多模型路由要解决的就是这个分配问题。

## 问题

没有路由策略时，团队往往是“哪个顺眼用哪个”，结果两个极端都踩过：

- 高频轻任务（比如每小时跑一次的摘要）走了旗舰模型，token 费用占了大头；
- 关键的多步 agent 任务走了本地小模型，漏参数、输出不合法，重试成本反而超过省下的钱。

路由的本质是用明确的规则换成本和稳定性，规则本身必须可观测。

## 做法

**1. 先给任务分三档。** 高频轻任务（摘要、改写、分类）→ 本地 7B/14B；标准任务（常规 tool call、代码补全）→ 中档模型；难任务（多步规划、长上下文、严格 JSON schema）→ 旗舰模型。

**2. 按能力路由，不按模型名路由。** 在路由配置里声明任务的能力需求，由路由器去匹配候选池，换模型时只改池子不改规则：

```yaml
routes:
  - match: { task: summarize, max_tokens: 2000 }
    prefer: local-14b
    fallback: [gpt-4o-mini]
  - match: { requires: [strict_json, tool_call], ctx_gt: 32k }
    prefer: gpt-4o
```

**3. fallback 链要显式、单向。** 本地优先 → 超时/校验失败/低置信 → 云端，且失败必须打标记录，不允许“再试一次本地”。

**4. 写路由决策日志。** 每次请求记下：命中哪条规则、用了哪个模型、耗时、token 数。没有这份日志，阈值调优全靠猜。

## 踩坑点

- **本地模型 tool call 格式不稳。** 小模型经常漏参数或输出包裹错误，对“强 schema 任务”建议直接在路由规则里强制走云端，或至少限定为带 function calling 微调的模型。
- **上下文长度别靠预估。** MCP 工具返回一大段结果就把 prompt 顶爆了，路由前应做 token 实测，超限直接升级到长上下文模型。
- **fallback 死循环。** 本地失败 → 云端失败 → 又回本地，重试放大三倍成本。链里要有“不再回头”的终止标记和全局重试上限。
- **量化模型长上下文质量骤降。** 本地模型超过某个长度后，检索型任务的召回明显变差。建议用固定测试集压测出这个阈值，写死进路由规则。

## 可复用建议

- 维护 30~50 条金标准任务集，每次换模型或调阈值后完整回放一遍，看通过率和成本变化。
- 路由决策按**能力、成本、延迟**三个维度打分，只看成本会把可靠性做塌。
- 留一个“逃生舱”：任何任务允许手动指定模型，路由只是默认值，不是铁律。

## 总结

多模型路由不是“本地便宜就全本地、GPT 强就全 GPT”，而是把任务按能力需求和代价分级，让规则替你做重复决策。OpenClaw 这套机制的关键在于：规则显式、失败可观测、阈值可回放验证。先把路由日志跑起来，再谈优化，顺序别反。
