## 背景

接上 MCP 和一批插件之后，Agent 的能力上限不再是"会说"，而是"能做"：读文件、跑 shell、调内部 API、发消息、花钱。能力越大，"它自己干还是先问我"就越是一个工程问题，不是在 system prompt 里写一句"请谨慎操作"能解决的。

## 问题

实践中常见的两个失败方向：

- **什么都问**。"我要读取这个文件，可以吗？""我要跑一下测试，可以吗？"三天之后你就开始无脑点确认——确认机制退化成橡皮图章，等于没有。
- **什么都不问**。某次模型理解偏了，删了分支、把测试通知发给了全组，或者对着生产库跑了条 UPDATE。一次事故就把之前省下的时间全部赔进去。

这两个方向本质是同一个问题：**确认的价值被稀释了**。好的边界不是"问得少"，而是"每次问都值得看"。

## 做法

我们内部用一套简单的分级，落到每个工具（甚至工具参数）上：

- **L0 可逆且只影响工作区**：读文件、写草稿、本地 diff。自动执行，事后汇报。
- **L1 可逆但有可见痕迹**：建 PR 草稿、写 issue、调测试环境。自动执行，留结构化日志。
- **L2 难撤销或影响他人**：push、发消息、部署 staging、任何花钱的调用。必须确认。
- **L3 不可逆 / 生产 / 凭证类**：删数据、动生产、输出密钥。确认之外，再加双人复核或环境隔离。

落地步骤：

1. **盘点工具，做一张风险清单**。给每个 MCP 工具标注风险级别，直接写进配置，跟着代码一起 review，而不是散落在各处 prompt 里。
2. **破坏性操作两段式**。先输出计划 / diff / 影响面，再申请执行。很多工具天然支持 dry-run，没用上的先补上。
3. **风险 = 工具 × 范围 × 参数**。同一个 git，push 到 feature 分支和 force push 到 main 不是一个风险级。边界至少做到子命令级，不要整个工具一刀切。
4. **给"自动"设预算**。单位时间的调用次数、花费上限、影响对象数量，低于阈值自动放行，超了升级为询问。
5. **每次询问带上下文**。必须附上：要做什么、为什么、备选方案、diff。一句干巴巴的"是否继续？"是在训练人类点 yes。
6. **记录每一次决策**。哪些自动放行了、哪些问了、人怎么答的。这份日志既是审计材料，也是后续调阈值的依据。

## 踩坑点

- **确认疲劳**：问得越勤，确认越不值钱。宁可 L0/L1 全自动，也要保住 L2 询问的信噪比。
- **只按工具名控权**：白名单了 `git`，等于白名单了它的全部子命令。
- **"只读"也有副作用**：某个 GET 会触发 webhook，爬虫把对方服务打挂了。别假设读等于无害。
- **事后确认**：Agent 先干了再问"这样可以吗"，等于没问。两段式必须卡在执行之前。
- **注入风险**：Agent 读回来的网页、issue 评论里可能藏着指令。权限边界同时是安全边界，L2/L3 的入口不能被外部内容间接驱动。
- **阈值定了就不看**：没有日志回顾，分级很快会和现实脱节。

## 可复用建议

- **默认从严，两周后按日志放松**。误报多就降级，零事故才考虑放宽。
- **凭证分级隔离**：Agent 拿 staging 的 token 干所有事，生产凭证根本不出现在它的环境里。这比任何 prompt 约束都可靠。
- **把边界策略写成配置文件**，进版本库，像 review 代码一样 review 权限变更。
- **真正的 L3 用"两把钥匙"**：Agent 确认之外，还需要人输一次口令或在控制台点一次。

## 总结

权限边界不是一个开关，而是关于**可逆性 × 影响半径 × 频率**的函数。目标不是减少询问，而是让每一次询问都携带足够的信息、值得人类认真看一遍。先从严、留日志、按数据放松——这套流程跑顺之后，"问不问"就不再靠感觉，而是靠配置。
