## 背景

玩 Agent 的人迟早会算一笔账：一个带工具调用的 agent loop，跑一轮动辄几万 token，反复调试时云 API 账单涨得比预期快。另外，MCP 工具读的往往是本地文件、数据库、浏览器记录——这些数据交给云端总有点别扭。于是我把一台旧主机改成了本地推理节点，跑了两三周，把过程和坑记录下来。

## 问题

真实的问题有三个，和营销话术里的"人人都能跑 70B"不是一回事：

1. **硬件错配**：显存/内存决定上限，但网上教程很少讲 KV cache 的额外开销；
2. **量化迷雾**：Q4、Q5、GGUF、AWQ 一堆术语，选错档位 agent 直接不可用；
3. **集成断层**：本地模型跑通聊天容易，但 agent 需要的是**稳定的工具调用和结构化输出**，这才是真正的门槛。

## 做法：五步走

**1. 摸清硬件底数。** 经验法则：8GB 显存跑 7B-8B 的 Q4 量化；12GB 上 14B；24GB 才够 32B 的 Q4。Mac 统一内存的机器，模型文件大小控制在内存的 70% 以内。

**2. 选运行时。** 图省事用 Ollama，要精细控制用 llama.cpp，想点 GUI 用 LM Studio。关键要求只有一个：暴露 OpenAI 兼容接口。vLLM 除非你有数据中心级显卡，否则别碰。

**3. 量化档位从 Q4_K_M 起步。** Agent 场景不要低于 Q4——工具调用的 JSON 输出对量化损耗很敏感，Q3 经常生成残缺参数。

**4. 接入 OpenClaw。** 把模型提供方指向本地的 OpenAI 兼容端点（如 `http://localhost:11434/v1`），**显式设置上下文窗口**，别依赖默认值。MCP 工具照常挂载，先用一个"列出目录再读某个文件"的简单任务验证工具调用链路。

**5. 留一条云端回退路由。** 本地模型接高频低难度的活（路由、摘要、分类），复杂推理走云。这是混合架构，不是替代。

## 踩坑记录

- **KV cache 吃显存超预期**：8B 模型开 32k 上下文，显存占用几乎翻倍。8GB 卡上把上下文压到 8k-16k 更稳。
- **小模型的工具调用很脆**：7B 及以下会编造不存在的工具、填错参数。缓解手段：精简暴露的工具数量、把工具描述写清楚、temperature 压到 0.2-0.3。
- **长上下文的首 token 延迟**：消费级显卡的 prefill 很慢，2 万 token 的 prompt 可能要等几十秒才开始吐字。Agent 每轮都带全量历史的写法在本地会很难受，需要做历史裁剪。
- **模型切换的冷启动**：按请求切换模型时，每次加载要 10-30 秒。固定住常用模型，别让 agent 频繁换脑子。
- **并发会排队**：本地推理默认近似单流，agent 并行执行多个工具步骤时会串行阻塞，实测要调并行参数并降低预期。
- **别信排行榜**：跑一个自己的 20 条任务评测集，覆盖工具调用、摘要、代码三种场景，用数据说话。

## 可复用建议

- **升级路径自下而上**：7B Q4 起步，质量不够再往上换；反过来先上大模型再降级，大概率浪费时间。
- **角色拆分**：小本地模型做路由和 embedding（顺手把 RAG 的向量化也本地化，隐私闭环），重的生成任务按成本路由到云端。
- **端点保持 OpenAI 兼容**：换模型、换运行时都只是改配置，不动 agent 代码。
- **持续记录两项指标**：吞吐（token/s）和首 token 延迟，按任务类型归档，扩容决策靠数据不靠感觉。

## 总结

本地 LLM 在 7B-32B 这个区间已经足够实用，尤其适合 agent 里的高频轻任务。它不是云 API 的替代品，而是让整个自动化体系多了一个"边际成本近乎为零"的层级。硬件决定下限，量化档位和上下文配置决定可用性，而工具调用的稳定性——才是本地模型能不能当好 Agent 大脑的真正分水岭。
