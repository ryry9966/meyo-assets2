# 为什么 OpenClaw Agent 不会误删你的文件：拆解 sandbox 的四层防线

## 背景

OpenClaw 的核心能力之一，是让 Agent 真正动手：跑 shell 命令、读写文件、装依赖。这等于把一台"能执行任意指令"的终端交给模型输出。而模型输出本质上不可控——一次误判的上下文、一条幻觉出来的"清理"命令，`rm -rf` 就可能落在不该落的地方。所以问题从来不是"模型聪不聪明"，而是"边界设在哪里"。

## 问题：既要能干活，又不能交出宿主机

限制太死，Agent 只剩聊天；放得太开，等于把家目录交给概率。OpenClaw sandbox 的设计目标是在两者之间给出工程解：**默认安全，按需放行，且每次放行都有明确范围。**

## 四层防线是怎么拦住 rm 的

1. **执行层隔离（Docker 沙箱）。** `exec` 工具默认不在宿主机 shell 里跑，而是在容器内执行。Agent 看到的"根目录"是容器文件系统，不是你的机器。
2. **文件系统收口（workspace 挂载）。** 只有工作区（workspace）和显式配置的目录会挂进容器，可加只读标志。挂载之外的世界对容器内进程根本不存在——不是"没权限删"，是"看不见"。
3. **文件工具路径校验。** 内置文件读写工具以 workspace 为根做路径约束，越界路径直接拒绝，不依赖模型"自觉"。
4. **工具策略网关。** 工具按 allow / ask / deny 分级；高危操作（如 exec）可设为人工审批。就算前三层被配置失误削弱，仍有一道确认兜底。

这就是纵深防御的价值：任何一层被误配，后面的层还在工作。

## 动手验证一次

信任要靠演练建立，不要靠读配置注释：

- 确认沙箱已启用（sandbox 跑在 Docker 模式，而非 off）；
- 让 Agent 执行 `ls /`，对比宿主机根目录，看到的应是容器内视图；
- 在 workspace 放一个 canary 文件，让 Agent 删它——应成功（这是授权区）；
- 再让它删挂载区之外的路径——应报不存在或无权限；
- 用 `docker inspect` 核对实际挂载清单，确认没有多余目录混进去。

## 踩坑点

- **挂载过宽。** 图省事把 `/home` 整个挂进去，沙箱立刻退化成"带审批的宿主机直连"。最小挂载原则不可妥协。
- **Docker socket 泄漏。** 把 `/var/run/docker.sock` 挂进容器，等于给 Agent 宿主机 root，常见于"方便起子容器"的配置。
- **关闭沙箱跑裸机模式。** 只剩审批和文件权限兜底，风险量级完全不同，仅限隔离环境调试。
- **审批疲劳。** 把 exec 一律设成"总是允许"，审批层等于不存在，策略要按操作风险分级。
- **把沙箱当备份。** 授权区内的文件删了就是删了，sandbox 不替代备份，workspace 必须进 git 或定期快照。

## 可复用建议

- **授权区最小化：** 只挂当前任务需要的目录，历史资料用只读挂载。
- **定期 canary 演练：** 用测试文件验证删除边界，而不是相信文档。
- **workspace 进 git：** 删除类操作随时可回滚，成本几乎为零。
- **策略分级：** 低风险操作自动放行，跨出 workspace 的高危动作一律 ask。

## 总结

Agent 不会误删文件，靠的不是系统提示词里写一句"请小心"，而是执行环境本身的边界。OpenClaw 的 sandbox 是典型的纵深防御：容器隔离、挂载白名单、路径校验、策略审批，四层各挡一部分，互相兜底。工程上有一条朴素的规律：**机制保证的可靠性，永远比模型保证的可靠性便宜。** 与其祈祷模型这次不犯傻，不如把边界画清楚。
