## 背景

OpenClaw 的 cron 任务本质上是一个「定时触发的独立会话」：到点后系统把 instruction 作为 prompt 交给 agent，agent 调工具、产出结果、按配置投递。很多人把 instruction 当聊天消息随手写，跑起来才发现各种跑偏。

## 问题

我最早写的 instruction 是这样的：「每天早上帮我看看 GitHub 通知，有重要的就总结一下」。跑了三天，问题全暴露：

- 「重要」没有定义，agent 自己发挥，每天标准都不一样；
- 没写输出格式和投递目的地，结果发到默认会话根本没人看；
- 某天 API 超时，agent 自己重试了五次，最后输出了一堆中间过程；
- 它甚至不确定「今天」是哪天——cron 会话是全新的，模型拿不准日期，差点把昨天的通知当新的发出来。

## 做法

后来我把每条 instruction 都按「函数契约」重写，固定六段：

1. **目标**：一句话，说明这个任务做什么、给谁看。
2. **数据源与范围**：明确工具和边界，例如「调用 github 工具读取过去 24 小时的未读通知，只看 mention 和 review request」。
3. **步骤**：编号列出，先取数、再过滤、再汇总，不允许自由探索。
4. **输出格式**：给死模板，比如「最多 5 条，每条一行：仓库 / 事件类型 / 一句话摘要；没有新内容就输出『今日无新通知』」。
5. **投递**：写清楚发给谁。「通过 message 工具发送到 Telegram 的 xx 会话；超过 400 字先压缩再发」。
6. **失败与幂等**：「取数失败重试最多 2 次，仍失败则发一条一行错误通知，不要贴堆栈；发送前检查缓存文件里的日期标记，同一天不重复发送」。

改完之后稳定性明显上升：输出格式一致、失败可预期、没有重复打扰。

## 踩坑点

- **会话隔离**：cron 会话没有主会话的上下文，别写「接着上次说的」。需要的上下文提前落到 workspace 文件，instruction 里让 agent 去读。
- **日期歧义**：涉及「今天/昨天」的，让 agent 先跑 `date` 拿系统时间再计算，别信模型自己推。
- **非交互约束**：cron 里没人点确认。凡是需要确认的工具调用，要么在配置里放开，要么不要出现在任务里，否则任务会卡住或被拒。
- **重复副作用**：定时任务可能因网关重启补跑一次。凡「发通知」这类有副作用的动作，都要有去重依据（落盘标记、去重键）。
- **范围失控**：「顺便也看看 XXX」这种附赠需求不要写。一个 cron 只干一件事，成本和排障都可控。

## 可复用建议

- 写完先手动触发一次，确认输出和投递正确，再挂定时。
- instruction 存进 git，当脚本对待：改一次提交一次，出问题能 diff 回滚。
- 高频任务把输出做得更「哑」：有增量才说话，没增量保持沉默。
- 把六段模板固化下来，新任务从模板复制，一段不少。

## 总结

Cron 的 instruction 不是提示词技巧问题，是工程问题：把它当成一个无人值守函数的接口文档来写——输入、边界、格式、投递、失败路径、幂等，全部显式声明。写得越「无聊」，跑得越稳。
