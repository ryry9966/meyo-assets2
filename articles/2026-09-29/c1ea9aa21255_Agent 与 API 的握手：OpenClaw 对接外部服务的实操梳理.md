## 背景

OpenClaw 的 agent 本体再强，不接外部服务就只是个会聊天的沙盘。真实价值几乎都来自那一步：读工单、查监控、触发 CI、往内部系统写数据。我们把这叫"握手"——agent 决定调用、翻译参数、通过认证、拿到结果、处理失败。这条链路任何一环松了，表现都是同一个症状："agent 行为不稳定"。最近两周我们给 OpenClaw 接入了三个内部服务（工单、监控查询、对象存储），把过程沉淀成这篇。

## 问题

一开始的做法很直接：把 OpenAPI 文档转成 MCP tool 描述，塞一个 key 进去。跑起来问题一堆：

- agent 自己编参数（幻觉字段、单位写错）；
- 遇到 401 它在对话层反复重试，烧 token 还解决不了；
- 一个 500 让它直接放弃，而那其实是可重试错误；
- 建单接口重试后出现重复工单——没有幂等键。

根因只有一个：我们让模型承担了它不该承担的工程职责。

## 做法

最终收敛成一个约定：**agent 只负责决策，adapter 负责一切工程细节**。

1. **划边界**。给每个服务标注读写属性，第一轮只接只读接口，写操作放第二轮。
2. **一层 adapter**。每个服务一个 MCP server / 插件，内部只做四件事：认证与 token 刷新、参数校验、错误翻译、超时重试。不放业务逻辑。
3. **凭证不下沉**。API key 放环境变量或 secret 存储，工具参数里永远不出现凭证字段。
4. **工具描述当接口文档写**。每个 tool 描述包含：参数含义与单位、副作用（读/写）、是否幂等、典型返回示例；写操作统一加 `dry_run` 参数。
5. **错误返回三要素**。adapter 把 HTTP 状态翻译成结构化结果：`retryable`（能否重试）、`reason`（原因）、`hint`（建议动作，如"刷新凭证"或"降低频率"）。agent 只需要读懂这三个字段。
6. **灰度与观测**。每次 tool call 记录入参、出参、耗时、重试次数，先在测试环境跑一周再上生产。

## 踩坑点

- **别把整份 API 文档丢进上下文**。token 消耗巨大，agent 反而更容易选错工具。一个服务暴露 5–8 个高内聚的 tool 就够。
- **重试必须带幂等键**。写操作由 adapter 自动生成并复用 idempotency key，重试窗口内同 key 直接返回第一次结果。
- **长任务别让 agent 轮询**。返回任务 ID 加一个独立的查询工具，而不是让它每 30 秒打一次状态接口——上下文会被塞满。
- **统一时间与单位**。三个服务的时间戳格式各不相同，最后在 adapter 层强制转 UTC ISO8601，省掉大量纠错。

## 可复用建议

- 命名规范：`服务_动作_资源`，例如 `tickets_create_issue`，agent 的工具选择准确率明显提升。
- 写 adapter 之前，先用 curl 手动把关键接口走一遍，包括失败路径。文档与真实行为的差距，手动调一次全暴露。
- 工具超过 20 个时按场景拆 MCP server，按任务动态挂载，别全量注入。
- 把 `retryable / reason / hint` 这个错误契约固化下来，新服务接入直接套用。

## 总结

对接外部服务的本质不是"把 API 给模型"，而是设计好一套握手协议：认证、描述、错误、幂等，这四件事在 adapter 层做扎实，agent 层保持薄。做到这一步，"agent 不稳定"的问题基本消失——剩下的问题，才是真正需要交给模型能力去解决的。
