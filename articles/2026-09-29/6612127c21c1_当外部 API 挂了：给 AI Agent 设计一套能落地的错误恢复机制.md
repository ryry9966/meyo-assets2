## 背景

Agent 的可靠性上限，往往不取决于模型，而取决于它调用的那堆外部服务。LLM API、搜索、数据库、第三方 MCP 工具——任何一环抖动，整个自动化流程就会停在半路。我们在社区自动化任务里观察到的失败，八成不是模型推理出错，而是外部调用失败后 Agent 的反应不对：要么死循环重试烧 token，要么干脆编一个"看起来合理"的结果继续往下跑。

## 问题：失败不可怕，可怕的是三种错误反应

1. **无脑重试**：遇到 429 或超时就立刻原样重发，既触发更严的限流，又浪费配额。
2. **静默降级成幻觉**：工具调用报错，Agent 却基于"它以为会返回的数据"继续推理，产出看似完整实则错误的结果。
3. **全局崩溃**：一个非核心依赖挂掉，整条 pipeline 报废，已完成的中间成果全部作废。

## 做法：把错误恢复拆成四层

**第一步，先分类。** 错误分成可重试（429、5xx、超时、网络抖动）和不可重试（400、401、403、404）。前者值得再试，后者重试多少次都没用，直接走失败分支。

**第二步，指数退避 + 抖动。** 重试间隔从 1s 起步按倍数增长，加随机抖动，避免多个 Agent 实例同时恢复造成二次雪崩。重试上限建议 3 次，到顶就认输。

**第三步，优雅降级。** 每个外部依赖准备一个 Plan B：备用 provider、本地缓存，或者干脆输出"本次结果基于 X 小时前的缓存"这样的显式标注。关键是降级要可见，不能悄悄用旧数据冒充新数据。

**第四步，断点续跑。** 长流程里每个成功的外部调用结果落盘（checkpoint），重试时从断点继续，而不是从头再来。这一条在跑批任务里尤其值钱。

两个容易忽略的工程细节：HTTP 客户端超时要显式设置（库默认值往往过长）；对非幂等操作（如下单类 POST），重试前必须先查询确认，防止重复执行。

## 踩坑点

- **200 不等于成功。** 不少 API 返回 200 但 body 里是业务错误码，必须解析 body 再判定，否则错误会一路穿透到下游。
- **嵌套重试。** 重试逻辑在插件层和 Agent 层各写了一份，3×3=9 次请求，等待时间指数放大。重试应收敛到一处。
- **超时 ≠ 失败。** 服务端可能已经执行成功，只是响应慢。对写操作，超时后先查状态再决定是否重发。
- **降级数据不标注。** 缓存兜底没问题，但不告诉下游"这是旧数据"，比直接报错危害更大。

## 可复用建议

- 把所有外部调用统一包一层 resilience 中间件（分类、退避、熔断、日志），不要每个工具各写一套。
- 结构化记录每次失败：错误类型、状态码、耗时、第几次尝试。没有这些数据，谈不上优化。
- 熔断器值得做：连续 N 次失败后短路一段时间，省下的不只是 token，还有用户的等待。
- 主动做故障演练：手动把依赖关掉跑一遍流程，比线上事故便宜得多。

## 总结

外部 API 挂掉是常态，不是异常。一套合格的错误恢复机制，验收标准很简单：可重试的有节制地重试，不可重试的尽快放弃，降级时诚实标注，崩溃时保住已完成的部分。模型能力决定上限，错误处理决定下限——而自动化场景里，用户首先感受到的是下限。
