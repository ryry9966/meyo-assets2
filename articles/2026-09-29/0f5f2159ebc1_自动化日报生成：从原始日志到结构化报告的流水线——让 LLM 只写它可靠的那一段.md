## 背景

我们这里的日常自动化比较杂：几个 cron 定时脚本、多个常驻 agent 会话、若干 MCP 工具调用，每天产生的日志分散在不同目录和进程输出里。日报长期以来靠人肉：早上翻日志、挑重点、贴数据，十分钟起步，还经常漏掉夜里跑挂的任务。

## 问题

归纳下来是三个：

1. **格式不统一**：时间戳、字段命名各异，想批量分析先得花时间清洗；
2. **汇总靠人**：口径随写日报的人漂移，上周和本周的“成功率”定义都不一样；
3. **直接丢日志给 LLM 不可靠**：试过“帮我把今天的日志总结一下”，数字经常编，日志一多还会截断。

## 做法：四段流水线，每段独立可跑

**1. 采集归一。** 所有任务输出统一追加到 `logs/YYYY-MM-DD.jsonl`，固定六个字段：`ts`、`source`、`event`、`level`、`metrics`、`detail`。写一层薄适配器，老脚本只改输出那一行。

**2. 结构化。** 每天 07:30 的 cron 跑解析器：正则和规则优先，能解析的绝不进模型；确实无结构的 `detail` 字段才批量送模型打标签。产物是当天快照 `snapshot.json`：错误 Top-N、各任务耗时分布、异常事件列表。

**3. 聚合。** 所有数字由脚本算完：成功率、环比、失败清单。这一步输出的是给叙述层用的“事实卡”，不是日志原文。

**4. 叙述与分发。** 把事实卡塞进固定模板 prompt，让 agent 只负责把数字组织成人话，prompt 里写死“只能引用输入中的数字，不得补充事实”。渲染成 Markdown，经插件推送到群，同时归档到 `docs/reports/`。

## 踩坑点

- **时区**：容器 UTC、宿主机 CST，差 8 小时导致“昨天”的窗口跨天错位。所有 `ts` 存 ISO 格式带时区，聚合层统一换算。
- **数字幻觉**：第一版让 LLM 直接读日志算成功率，误差能到 3%。改成脚本算完再喂，才稳定。
- **重复推送**：cron 重跑导致群里出现两份日报。给任务加幂等键（日期 + 版本号），已存在则跳过。
- **日志量爆炸**：某天一个任务的 debug 日志把快照撑爆了上下文。采集层加了 level 过滤和采样，铁律：原始日志永远不直接进模型。
- **静默失败**：流水线自己挂了没人知道，“没日报”和“没异常”分不清。加心跳：跑完必发一条含状态行的消息，失败即告警。

## 可复用建议

- **中间产物落盘**：`snapshot.json` 让每段可单独重跑、可回放，排障不用从头来。
- **模板版本化**：报表模板和 prompt 当文件管理，改动可 diff、可回滚。
- **进模型前先做减法**：过滤、采样、聚合，模型只做最后的文字组织。
- **“无数据”也要成文**：宁可发“今日无异常”，也不要不发——沉默应该永远代表失败。

## 总结

这套流水线的核心不是“让 LLM 写日报”，而是划清边界：**所有事实由确定性代码生产，LLM 只负责它可靠的部分——语言组织**。归一 → 结构化 → 聚合 → 叙述，四段式加中间产物落盘，迁移到周报、告警复盘等场景基本只换解析器和模板。上线一个月，日报制作时间从每天十分钟降到零，唯一一次漏报由心跳捕获，五分钟内修复。
