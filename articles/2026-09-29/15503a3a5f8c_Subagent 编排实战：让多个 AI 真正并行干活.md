## 背景

单个 agent 的执行循环是串行的：工具调用一个接一个，任务排队处理。事情少时没问题，但遇到"对 6 个仓库做依赖升级调研""按服务分头排查 10 份日志"这类天然可切分的工作，串行意味着耗时线性增长，而且所有中间结果堆在同一个上下文里，跑到后半程模型开始丢细节。

OpenClaw 的 subagent 机制（如通过 `sessions_spawn` 派生子会话）提供了另一条路：主 agent 只负责拆任务和收结果，每个子 agent 拿着干净的上下文、单一目标和受限的工具集独立干活。

## 问题

实际用下来，把"能并行"做成"真的并行且结果可用"，中间有三个坎：

1. **拆分不当**：子任务之间有隐性依赖，并行后互相踩；
2. **结果不可控**：子 agent 返回自由文本，主 agent 聚合时解析失败；
3. **失败被吞**：某个子 agent 半路挂掉返回空结果，主 agent 当成正常数据继续汇总，产出错误结论。

## 做法

以多仓库依赖升级调研为例，我们把编排固定成五步：

1. **判独立性**。先列出任务清单，确认两两之间没有数据依赖。有依赖的串成一个子任务，不要硬拆。
2. **定契约**。每个子 agent 的 prompt 模板包含四件事：单一目标、工具白名单（只给 MCP 里它用得到的那几个）、输出 JSON schema、轮数与预算上限。
3. **派发**。主 agent 并发 spawn，子 agent 各自把结果写入独立文件（如 `result/repo-a.json`），不共享状态。
4. **校验与重试**。逐个校验 JSON 合法性和必填字段，失败的只重试一次，再失败标记 partial，不阻塞整体。
5. **聚合落盘**。主 agent 读取全部结果文件做汇总，原始结果保留，便于事后审计。

编排参数示意（伪配置）：

```yaml
orchestration:
  concurrency: 4
  subagent:
    output: json_schema
    retry: 1
  on_failure: mark_partial
```

## 踩坑点

- **伪并行**：几个子 agent 往同一个文件写，后写的覆盖先写的。每个子任务必须有独立工作区或输出路径。
- **工具给太多**：一开始图省事把全部 MCP 工具都开放给子 agent，结果它去干了不相干的事。收窄白名单后明显稳定。
- **并发打满**：一口气开 10 个子 agent，上游 MCP 限流，全部超时。并发压到 3–5 并配预算上限。
- **主 agent 抢活**：主 agent 觉得"我自己查更快"就开始自己调工具，编排退化回串行。prompt 里明确它只做拆分、派发、聚合。
- **聚合时超窗**：子 agent 返回全文，六份结果塞回主 agent 直接爆上下文。让子 agent 返回前先做压缩摘要，全文只落盘不回传。

## 可复用建议

- 先串行跑通再并行化，契约没定稳之前，并行只会放大错误；
- 子 agent prompt 模板化，与输出 schema 放在一起维护；
- 失败也要结构化上报（error 字段 + 原因），不要靠"返回为空"暗示失败；
- 编排逻辑写成脚本或插件，别指望模型每次即兴拆得一样；
- 所有中间结果落盘，排障时能复盘每个子 agent 做过什么。

## 总结

Subagent 编排的收益不来自"多个 AI"本身，而来自任务分解的独立性：拆得干净，并行才成立；契约定得清楚，聚合才可靠。先用两个子 agent 把链路跑通，再谈扩并发，是代价最小的路径。
