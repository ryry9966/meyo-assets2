## 背景

OpenClaw 的 cron 本质是“定时把一条 instruction 当作用户消息发给 agent"。写得好，它是个无人值守的自动化员工；写得差，它就是每天定时制造噪音的随机源。最近我把早报摘要、磁盘巡检、RSS 精选三个日常任务迁到 cron 上，跑了一个多月，把 instruction 从“聊天体”重构成“工单体”，才真正稳定下来。

## 问题：它和普通 prompt 的区别

核心差异只有一条：**执行时没有人在场**。

- 没法追问：agent 遇到歧义只能猜，猜错就静默错下去；
- 没有上下文：定时任务通常跑在独立会话里，“按之前说的”“和上次一样”这类指代全部失效；
- 失败延迟暴露：凌晨跑挂的任务，早上才被发现，而且看到的可能还是 agent 编的圆场话。

所以目标不是“写得像人话”，而是让一个没有上下文的执行者在一次调用内跑对。

## 做法：一个可以直接抄的模板

六段式，顺序固定：

```text
【触发】定时任务，无人值守，禁止向用户提问。
【时间】以系统时间为准，统计过去 24 小时（起止日期由调度侧注入）。
【边界】只使用 xxx 工具，只读取 ~/notes/，禁止访问其他目录。
【步骤】1. 拉取数据 2. 按规则过滤 3. 汇总。
【输出】发到 Telegram，不超过 10 行；无新增时只回复"无更新"。
【兜底】拉取失败时回复"数据源异常：<原因>"，禁止编造数据补位。
```

几个关键取舍：

1. **显式声明无人值守、禁止提问**。不写这句，agent 有概率走交互式 skill，然后卡到超时。
2. **时间范围由调度侧注入**，别让 agent 自己算“今天”，时区问题也在这里一并解决。
3. **工具和数据源写白名单**。无人值守任务默认只读、低风险。
4. **输出契约定死**：发到哪、多长、空结果怎么办。空结果不写清，agent 要么发一条空洞的“今日汇报”，要么自己找点东西凑数。

## 踩坑点

- **聊天体 instruction**：“帮我看下昨天的消息”——哪个时区的昨天？看哪些渠道？看完干嘛？每个空隙 agent 都在填自己的猜测。
- **时区错位**：cron 表达式走 gateway 所在机器的时区，instruction 里的“今天”走 agent 的推断，两边不一致就会在奇怪的时间做奇怪的事。
- **会话污染**：定时任务结果写进主会话，几周后日常对话的上下文里全是任务中间输出。单独开 session，或至少加固定前缀。
- **没有兜底分支**：源站改版、token 过期之后，agent 不会报错，而是基于空数据“正常”输出。务必写明失败时的表现。
- **一个任务干三件事**：出问题时分不清哪段挂了，宁可拆成两个 cron。

## 可复用建议

- instruction 当代码管：进 git、改版留痕，行为异常时可以 diff。
- 上线前用同一条 instruction 手动触发一次，确认输出契约成立；初期用 10 分钟一次的高频观察几轮，再调回正常频率。
- 每次出错，把教训回写进【兜底】段，让任务越跑越健壮。
- 涉及写操作的定时任务，第一版只跑 dry run：只输出它打算做什么，不发不写，人工确认一周再放权。

## 总结

Cron instruction 的本质是一份**给无上下文执行者的单次工单**：触发说明、时间范围、边界、输出契约、失败兜底，五样缺一就容易静默出错。它不靠花哨的 prompt 技巧，靠的是把“人会在场补全的信息”全部显式写下来。写完自检一句：这条消息如果发给一位完全失忆的同事，他能一次跑对吗？
