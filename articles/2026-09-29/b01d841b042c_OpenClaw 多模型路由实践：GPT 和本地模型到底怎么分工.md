## 背景

OpenClaw 用久了，第一个感知是账单，第二个感知是有些任务压根用不上旗舰模型。一个跑着主对话、定时摘要、记忆检索和若干消息通道的实例，如果全走 GPT 这一档的云端模型，成本和延迟都撑不住；反过来全换成本地模型，多步工具链和长上下文推理又会明显变笨。多模型路由要解决的就是"哪个任务配哪个模型"的分配问题。

## 问题

路由难的不是配置，是策略。OpenClaw 支持多个 provider、支持按 agent 覆盖模型，但策略定错，表象通常是两种：要么"agent 突然变傻"，要么"账单没降多少还多了排障成本"。我的结论是：先按任务类型做静态路由，跑稳了再考虑动态。

## 做法

1. **先给任务分维度**：是否多步工具链、上下文多长、隐私等级、延迟容忍度。四个问题问完，路由表基本就出来了。
2. **静态路由起步**：
   - 主对话 agent（多步推理、复杂工具链）→ 云端旗舰模型；
   - 定时摘要、日报、标签、翻译这类单轮任务 → 拆成独立 agent，绑本地 7B–14B；
   - 隐私敏感内容（私人日志、家庭数据）→ 强制本地，不给 fallback。
3. **配降级链**：主模型限流或失败时降级到本地，但只降一级，防止来回横跳。
4. **看一周日志**再决定要不要上动态路由，多数场景静态就够了。

示意配置（字段名以你版本的实际 schema 为准）：

```jsonc
{
  "agents": {
    "defaults": {
      "model": { "primary": "openai/gpt-4.1", "fallbacks": ["ollama/qwen2.5:14b"] }
    },
    "list": [
      { "id": "daily-digest", "model": { "primary": "ollama/qwen2.5:14b" } }
    ]
  }
}
```

## 踩坑点

- **本地模型工具调用不稳**。小模型在多步循环里漏参数、编造工具名，表现为"看起来在跑，工具其实没执行"。对策：本地只接单轮或弱工具任务，并收窄它的可用工具集。
- **上下文静默截断**。会话滚长之后本地模型开始"失忆"，还不报错。长会话要么做摘要压缩，要么直接路由云端。
- **延迟错觉**。消费级显卡跑 14B，一次推理几十秒，比 API 还慢。路由前先测真实 P95 延迟，别只看参数量。
- **fallback 风暴**。云端限流→降本地→本地超时→再切回来，工具被重复执行。降级只走一次，工具调用尽量做幂等。
- **embedding 换型**。切到本地 embedding 后旧向量索引召回明显变差，换模型就要重建索引，别偷懒。

## 可复用建议

- 路由表单独维护成文档，一行一个 agent：用途、主模型、fallback、选型理由。
- 日志里固定记录每次调用的 model 字段，月底才能算清"到底是哪个模型在花钱"。
- 攒 20–30 条典型任务的回归集，每次换模型跑一遍，比肉眼感觉可靠。
- 隐私规则优先于成本规则：先圈出必须本地的任务，剩下的再谈省钱。

## 总结

多模型路由不是炫技，是成本、质量、隐私三者的显式取舍。OpenClaw 的按 agent 覆盖模型加 fallback 机制刚好够用，关键是把任务分类做扎实、静态路由先落地、用日志验证效果，最后才谈动态调度。我自己的实例现在云端流量降了六成左右，主对话质量没有可感知的下降——这个数字不通用，但方法可以直接搬走。欢迎在评论区贴你们的路由表，互相抄作业比各自动脑快。
