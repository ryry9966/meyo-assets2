## 背景

大多数 Agent 的使用模式是“你问它答”：不发消息，它就不动。但很多真实需求是反过来的——盯着某个仓库有没有新提交、每天固定时间汇总一次、发现异常才说话。这类任务靠人肉轮询很浪费，靠写死脚本又脱离了 Agent 的上下文和工具能力。

OpenClaw 有一个容易被忽略的机制：**heartbeat（心跳）**。Agent 每隔一段时间被自动唤醒一个 turn，读取工作区根目录下的 `HEARTBEAT.md`，判断有没有该做的事。这个文件本质是一份常驻任务清单。写得好的话，Agent 会从“被动应答”变成“定期巡逻”；默认情况下它是空的，所以大多数人从来没体验过这个能力。

## 做法

1. **建文件**：在 Agent 工作区根目录创建 `HEARTBEAT.md`（如 `~/clawd/workspace/HEARTBEAT.md`）。
2. **写任务**：每条任务按三段式写——触发条件、动作、沉默条件。
3. **配间隔**：默认 30 分钟唤醒一次，通过 heartbeat 配置（`intervalMinutes`）调整。心跳检查建议挂便宜模型，主会话保持高质量模型。
4. **验证**：先把间隔调到 5 分钟，观察两三个周期日志，再调回生产值。

示例：

```markdown
- 每次心跳检查 ~/repos/api 的 git status：
  有新提交就摘要发我；无变化则 NO_REPLY。
- 每天晚上 23 点后第一次心跳：
  汇总 heartbeat.log 当日记录，发到默认目标会话。
```

关键认知：每次心跳 Agent 都会**真实跑一个 turn**。无事可做时它返回 `NO_REPLY`、不给你发消息，但 token 照花。`HEARTBEAT.md` 的长度 ≈ 每个周期的固定上下文成本。

## 踩坑点

- **任务写太模糊**。“帮我盯着仓库”这种写法，Agent 会每周期都发一条“一切正常”。沉默条件必须显式写出来，这是防骚扰的核心。
- **当成 cron 用**。心跳是固定间隔轮询，不是定时调度。“每天 9 点”只能靠“检查当前时间 + 日志里记上次执行时间”自己实现，且存在漂移。
- **文件越写越长**。做完的任务及时删，建议控制在 10 行以内。
- **与活跃会话冲突**。有正在进行的对话时，心跳可能被跳过或排队，别指望它做秒级响应。
- **没留审计**。主动行为出了问题，你甚至不知道它做过什么。让每个动作追加写一行到 `heartbeat.log`。

## 可复用建议

- **三段式模板**：条件 / 动作 / 沉默条件，套用即可。
- **心跳只做轻检查**：发现问题先发消息让你确认，而不是直接执行重动作；把心跳当哨兵，不当执行者。
- **独立便宜模型跑心跳**，成本能降一个量级。
- **灰度上线**：短间隔观察日志两三天，确认没噪音再投生产。

## 总结

`HEARTBEAT.md` 的价值不在文件本身，而在于它把“Agent 什么时候该工作”的控制权，从你的输入框移到了一个可版本化、可审计、可回滚的文件里。写清沉默条件、控制清单长度、留好执行日志，主动式 Agent 才不会从帮手退化成噪音源。
