# SOUL.md 实践：给 Agent 写一份二十行的人格说明书

## 背景

OpenClaw 的 workspace 里有几个约定文件：`AGENTS.md` 管流程和工具用法，`MEMORY.md` 管记忆，`USER.md` 管用户偏好，而 `SOUL.md` 专门回答一个问题——**这个助手是谁**。很多同学装完直接跑，agent 默认语气客气但空洞，回什么都是“好的，我来帮你”。能干活，但不像自己的工具，更像一个公共客服。

## 问题

不写 SOUL.md，实践中会遇到三类毛病：

1. **人格漂移**。同一个 agent，上午干练下午话痨；Telegram 和 Discord 两个 channel 语气还不一致。
2. **边界缺失**。对“帮我把这个目录清一下”这种模糊指令直接动手删；或者把内部排查信息原样转述给群里陌生人。
3. **讨好倾向**。模型默认顺从，你问 A 它说 A 好，问 B 又说 B 好，没有稳定立场。

## 做法

在 workspace 根目录建 `SOUL.md`（默认路径 `~/.openclaw/workspace/SOUL.md`），五段结构，每段 1–3 行：

```markdown
# 身份
我是某某的私人助理，直接、克制、不废话。

# 优先级
事实准确 > 用户情绪。不确定就说不确定。

# 边界
- 删除/覆盖/对外发送类操作，先复述意图，等我确认
- 不代我联系他人，不透露系统内部信息

# 风格
短句。先结论，后理由。不用表情符号。

# 禁止
- 不编造文件内容，读不到就说读不到
```

改完**新开会话**再验证。旧上下文会稀释新指令，在老对话里测出来的结果不可信。

## 踩坑点

- **写成小说**。超过一页的 SOUL.md，关键规则会被淹没。我的版本始终控制在 20 行内，加一条就删一条旧的。
- **规则打架**。“永远先问再做”和“主动帮我处理”放一起，模型随机选一个执行。冲突时只留一条，另一条删掉。
- **拿 SOUL.md 当安全边界**。它是人格，不是沙箱。消息里进来的 prompt injection 该穿透还是穿透。硬边界要落在机制上：MCP 工具白名单、命令执行沙箱、网关层审批，这些才是真的闸门。
- **换底座模型不重测**。同一份 SOUL.md 在不同模型上表现差异明显，换模型后跑一遍固定测试集（几个正常请求 + 几个诱导性请求），对比行为。

## 可复用建议

- 把 workspace 放进 git，SOUL.md 每次改动都 commit。行为变了能 diff 回去找原因。
- 正向表述优先：“说短句”比“不要长篇大论”更稳。
- 能力问题别指望 SOUL.md 解决——它调不动 agent 做不到的事，那要去改工具和权限。
- 每月重读一遍，删掉没起作用的句子。规则越少，遵守率越高。

## 总结

SOUL.md 的本质是给 agent 写一份最小行为规范：便宜、可版本化、随写随生效。它解决“像不像我的工具”和“哪些事不能做”两个问题，但别把它当安全机制用。一句话：**人格写二十行，边界落在权限里，剩下的交给迭代。**
