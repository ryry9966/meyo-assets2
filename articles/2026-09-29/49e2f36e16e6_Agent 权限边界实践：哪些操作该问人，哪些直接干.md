## 背景

接上 MCP 和插件之后，Agent 手里的能力从"聊天"变成了"办事"：写文件、调内部 API、发消息、跑脚本。能力上来了，一个老问题变成了新问题——每一步都停下来问人，自动化就没了意义；全放权，凌晨三点一条删除命令就能让你后悔。

我们的场景是 OpenClaw 挂了若干 MCP 工具和自定义插件，日常跑文件整理、数据拉取、定时报告。这里把近几个月摸索出的权限分层做法整理一下，供参考。

## 问题

实际失败模式只有两种：

1. **问得太多**。人类变成橡皮图章，看到弹窗就按确认，确认环节名存实亡。
2. **问得太少**。一次不可逆操作（删除、外发、生产变更）直接执行，事后无法回滚。

更麻烦的是两者会互相转化：问得太多导致确认疲劳，确认疲劳导致盲目放行——本质上等于不问。

## 做法：按两个维度分层，而不是一刀切

给每个工具操作打两个标签：

- **可逆性**：能不能撤销？git 管得住的改动可逆；删库、外发消息、调第三方付费 API 基本不可逆。
- **爆炸半径**：影响的是一个工作区内的文件，还是跨系统、对外的？

据此分四档：

| 档位 | 典型操作 | 策略 |
|---|---|---|
| L0 | 只读、dry-run、沙箱内执行 | 直接干，记日志 |
| L1 | 工作区内可逆写 | 直接干，全量记录参数供审计 |
| L2 | 低频但敏感（首次向某渠道发消息、首次调某外部 API） | 首次确认，放行后写入 allowlist |
| L3 | 不可逆 / 对外 / 跨系统 / 涉凭证 | 每次确认，且确认内容必须可判断 |

两个关键实现点：

1. **拦截放在执行层，不放在提示词里。** 提示词里写"危险操作请先询问"是不可靠的，模型会漏。我们在工具调用链上加了一层 policy 检查，按"工具名 + 参数模式"匹配，命中 L3 直接挂起等确认。
2. **确认请求要带上下文。** 不是"是否继续？(y/n)"，而是带上 diff、目标地址、影响范围。人判断的是具体这一次操作，不是抽象的"要不要允许 bash"。

## 踩坑点

- **allowlist 粒度太粗。** 早期按工具名放行，等于把 `bash` 整个放开。后来改成按命令/参数前缀匹配。
- **确认疲劳要当指标看。** 统计每天的 ask 次数，超过阈值（比如 20 次）说明分层不合理，回来调 policy，而不是训练用户手速。
- **拆分绕过。** Agent 会把一个大操作拆成 20 个"可放行"的小操作。加了聚合限制：同类操作短时间超过 N 次自动升级为需确认。
- **跨会话记忆错位。** approve 记忆太短会重复问，太长会一次放行变永久放行。L2 的 allowlist 现在带过期时间，默认 7 天。
- **长任务里的确认会阻塞。** 定时任务跑到 L3 挂起等不到人，超时策略要提前定好：丢弃、降级还是排队，别让任务悄悄死掉。

## 可复用建议

1. 给自己的工具清单做一张风险表，半小时能填完，每季度复查。
2. 所有 L0/L1 自动放行的操作，参数全量落日志，出事时你会感谢这条。
3. 默认拒绝边界外的一切：工作区目录之外的写、未知域名的外呼，先挡再说。
4. 把"ask 率"当成和 token 消耗同级的指标监控，它直接反映权限策略的健康度。
5. 人在回路的价值在于判断，不在点击。确认内容设计得让人能判断；做不到，不如砍掉换成更严的默认拒绝。

## 总结

权限边界不是"问 or 不问"的单选，而是按**可逆性 × 爆炸半径**分层的策略，必须由执行层强制、由日志兜底。目标不是零打扰，也不是全自动，而是把人类注意力花在真正值得判断的那几次操作上。如果一周下来你按确认的次数明显下降、事故也为零，说明这套边界划对了。
