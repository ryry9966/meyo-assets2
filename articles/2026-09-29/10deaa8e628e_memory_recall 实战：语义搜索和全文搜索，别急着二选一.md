## 背景

Agent 记忆做起来不像 demo 里那么玄。OpenClaw 的 `memory_recall` 本质是个检索问题：助手平时把决策、偏好、踩坑记录写进 memory，下次对话时召回几条注入 context。检索方案无非两条路——全文搜索（SQLite FTS5 / LIKE / BM25）和语义搜索（embedding + 向量相似度）。

## 问题

我最初只上了语义搜索（bge-m3 + sqlite-vec），一周就翻车了，两个典型 case：

- 用户问“那个 502 的事怎么解决的”，memory 里有完整记录，向量召回排到第 8，低于截断阈值直接漏掉——因为笔记里当时写的是“网关超时排查”，措辞不同。
- 更致命的是精确匹配：笔记里有 `OPENCLAW_TIMEOUT=30000` 这种配置项，用户问“超时设了多少”，embedding 对数字和配置键几乎无感，召回回来的是三条不相关的偏好记录。

反过来，纯全文搜索也有硬伤：同义改写、中英混排（用户说“部署”，笔记存的是 "deploy"），关键词命中不了。结论很清楚：两者的失效模式是互补的，单选哪条路都有明显盲区。

## 做法

现在的方案是混合召回，四步：

1. **双路检索**：FTS5 走 BM25（中文换 trigram 分词，jieba 也行）；语义路用 bge-m3 出向量，sqlite-vec 存储，余弦相似度。
2. **RRF 融合**：两路各自排序后用 Reciprocal Rank Fusion 合并，比手工调权重分数省心得多。
3. **简单路由**：查询里出现配置键、路径、错误码、纯数字时给全文路加权，反之语义路权重略高。一个正则就够，别过度设计。
4. **截断与预算**：融合后取 top-5，注入 context 的 memory 总量控制在 500 token 以内，超出直接丢。

## 踩坑点

- **FTS5 默认分词器对中文基本不可用**，unicode 切出来是一整串，必须换 trigram 或 jieba，否则中文查询命中率约等于零。
- **阈值宁紧勿松**：相似度阈值放宽后，噪声条目混进 context 会把 agent 带偏，比漏召回更糟。我们从 0.35 起步，宁可漏了再人工补。
- **过期记忆是隐性炸弹**：笔记写着“服务部署在 A 机”，后来迁到 B，向量检索会非常自信地把旧条目排在前面。每条 memory 必须带时间戳，注入前做时效衰减。
- **长文本稀释 embedding**：单条笔记超过 300 字就切分，核心语义会被冲淡，召回质量肉眼可见地下滑。

## 可复用建议

- 别一步到位上向量库。先 FTS + 时间衰减跑两周，看召回 miss 日志；miss 集中在改写型查询，再上语义路。
- 记忆条目写短、写自包含，一条一个事实，带日期。检索质量的上限取决于写入质量，不取决于检索算法。
- 留 20 条典型查询做手工 hit@5 评测，换模型、调阈值前后各跑一遍，十分钟的投入比任何直觉可靠。

## 总结

语义搜索和全文搜索不是竞争关系，是分工：精确标识符靠全文，模糊意图靠语义，RRF 把两者缝起来。真正拉开效果的不是算法选型，而是分词、阈值、时效性和写入质量这些工程细节。用日志驱动决策，别被 demo 带节奏。
