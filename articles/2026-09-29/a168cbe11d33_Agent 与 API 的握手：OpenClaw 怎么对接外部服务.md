## 背景

Agent 只会聊天价值有限，真正干活靠的是触达外部世界：查订单、发消息、写数据库、调第三方接口。在 OpenClaw 里，对接外部服务主要有三条路：原生 tool/插件、MCP server、通用 HTTP 调用封装。这篇帖记录我最近把一个内部工单系统和一个第三方查询 API 接进 OpenClaw 的过程，重点谈契约设计，不展开具体服务的配置细节。

## 问题

最开始我偷懒，直接把服务的 REST 文档丢给模型，让它"照着文档调用"。结果三连：选错工具、编造参数、返回体塞爆上下文。复盘后意识到，API 文档是写给程序看的，模型需要的是另一层更收敛的契约。握手失败，不是服务的问题，是中间那层没设计好。

## 做法

1. **选对接路径**：高频调用、需要鉴权、参数复杂的，写成 MCP server 或原生 tool；低频只读的，用通用 HTTP 工具加 endpoint 白名单就够了，别为一次性需求写插件。
2. **写 schema**：工具名用"动词+宾语"，参数尽量带枚举和默认值。description 是写给模型的用法说明，不是接口文档——它决定调用准确率。一个工具只做一件事。
3. **鉴权与配置**：key 走环境变量或 secret 文件，在工具运行层注入，绝不写进系统提示词，也绝不落日志。
4. **容错下沉到工具层**：超时、重试、限流都在代码里做，指数退避；写操作必须带幂等键，Agent 是会重试的，别指望它克制。
5. **返回裁剪**：只返回模型需要的字段，大结果做分页或摘要。错误统一成 `{ok, error, hint}` 结构，hint 里写清"下一步建议做什么"，而不是抛原始堆栈。

## 踩坑点

- 两个工具 description 写得含糊，职责有重叠，模型来回选错。改成互斥的职责描述后才稳定。
- 第三方接口偶尔返回整页 HTML 而不是 JSON，直接把上下文打爆。教训：先手动 curl 看真实返回，再在工具层做类型校验和裁剪。
- 重试没加幂等键，测试环境重复创建了十几条工单，还好不是生产。
- 把异常堆栈原样返回给模型，它开始"脑补修复"，输出一套看似合理的错误操作。改成一句人话加建议动作后恢复正常。

## 可复用建议

- **工具薄、服务厚**：业务逻辑放服务端或脚本里，工具只做转发、鉴权和裁剪。
- 错误信息面向模型写，不是面向人——人能看懂的堆栈，模型只会编故事。
- 每个工具配一个 smoke test，进 CI，schema 改动立刻能暴露。
- 上线前把模型关掉，纯手工按 schema 调一遍工具，确认契约自洽再交给 Agent。

## 总结

Agent 与 API 的握手，本质是两层契约：schema 是给模型看的，鉴权、超时、幂等、裁剪是给系统做的。这两层分开设计、各自收敛，握手才算稳。工具层写得越克制，Agent 的行为就越可预测——这是这次对接最大的收获。
