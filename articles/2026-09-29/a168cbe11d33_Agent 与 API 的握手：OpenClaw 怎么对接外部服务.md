## 背景

Agent 的价值不在"会聊天"，而在能替你干活。干活就意味着要碰外部世界：查工单、调内部系统、触发部署、读写数据库。在 OpenClaw 的实践里，这条路径基本收敛为一个固定模式：**工具层（tool / MCP server）包住外部 API**，Agent 只面对结构化的工具描述，不直接碰 HTTP。

这篇帖子把我们最近对接几个内部服务的过程整理一下，重点讲握手时的工程细节，不讲"怎么装 MCP"这种一句话能查到的事。

## 问题

直接让 Agent 调 API，通常死在三件事上：

1. **鉴权放错位置**：把 token 写进系统提示词或工具描述，日志一落盘就是泄露。
2. **错误语义断裂**：API 返回 4xx/5xx 甚至一段 HTML 错误页，Agent 拿到后开始自由发挥，编出一个"看起来合理"的结论。
3. **Schema 与现实不符**：工具描述写 `query: string`，实际服务要求分页参数、特定时间格式，Agent 只能瞎猜。

## 做法

我们的做法是把对接拆成四步，每步都有明确产出：

**第一步：封装而非透传。** 不把 REST 端点原样暴露成工具。一个领域一个 MCP server，比如"工单服务"只暴露 `search_tickets`、`get_ticket`、`add_comment` 三个工具。工具数量压到最少，Agent 选错工具的概率显著下降。

**第二步：Schema 按调用方写，不照抄服务端文档。** 服务端文档是给人类看的。给 Agent 的参数描述要写清格式约束（"ISO 8601 日期"、"最多返回 20 条，更多请带 cursor 翻页"），枚举值全部列出来。

**第三步：鉴权收敛在传输层。** token 放环境变量，MCP server 启动时注入。工具描述里只写"需要授权"这个事实，不出现任何凭据，轮换密钥只改一处。

**第四步：把 API 错误翻译成 Agent 语言。** 统一错误结构：`{ok: false, error: "rate_limited", hint: "60s 后重试"}`。Agent 读得懂 hint，就不会在 429 上反复硬试。写操作一律加幂等键，重试不产生脏数据。

## 踩坑点

- **返回值塞满上下文**：一个列表接口返回 50 条完整记录，两三轮对话就把窗口吃光。我们在 MCP server 里做了裁剪，默认只回摘要字段 + 总数，要详情再调单条接口。
- **长任务阻塞**：有个触发部署的工具要跑 5 分钟，同步调用直接超时。改成提交任务返回 task_id，另加一个 `check_status` 轮询工具。
- **工具描述歧义**："查订单"和"查工单"描述写得太像，Agent 高频选错。后来在描述里显式写明各自关键词和典型问法，误选率基本归零。
- **没留观测**：起初工具调用不落日志，出问题只能靠猜。现在每次调用记录入参摘要、耗时、错误码，排障从半小时缩到两分钟。

## 可复用建议

1. 工具按"领域"分，不按"端点"分；单个 Agent 挂载的工具控制在 10 个以内。
2. 所有写操作默认带 dry-run 参数，让 Agent 先预演一遍。
3. 结果裁剪和错误翻译放进 MCP server，别指望模型自己消化原始响应。
4. 日志记输入摘要而非全文，兼顾排障效率与敏感信息。

## 总结

对接外部服务，难点从来不是"能调通"，而是让 Agent 在异常路径上依然行为可预期。封装、收窄、翻译、留痕——这四个词是我们踩完坑之后的全部结论。工具层做得越"无聊"，上层 Agent 就越好写。欢迎在评论区聊聊你们对接时的错误翻译策略。
