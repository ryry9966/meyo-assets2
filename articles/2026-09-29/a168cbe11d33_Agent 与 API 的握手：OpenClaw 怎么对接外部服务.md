## 背景

Agent 真正能干活，靠的不是提示词写得多花哨，而是能不能稳定地把外部服务接进来。在 OpenClaw 这套体系里，对接外部服务主要有三条路：MCP Server、插件（plugin）、以及最朴素的 HTTP 工具封装。三条路各有适用场景，但工程核心是同一个问题：让模型清楚「能调什么、怎么调、调错了怎么办」。

## 问题

把一条 curl 命令直接丢给 Agent，演示阶段看起来很美，落地立刻出问题：

- 模型不知道参数边界，字段全靠猜；
- 凭证怎么给？写进 system prompt 等于裸奔；
- 接口返回 20KB 的 JSON，几轮对话就把上下文吃光；
- 网络抖动、限流、超时，Agent 不会自己兜底。

所以「握手」不是调通一次请求，而是建立一套稳定契约。

## 做法

以最典型的 MCP 方式为例，步骤如下：

1. **一个服务一个 MCP Server**。不要做万能网关。把某个服务的 API 收敛成 3~5 个职责单一的工具，比如 `query_order`、`create_ticket`，命名让人和模型都看得懂。
2. **认真写工具描述**。描述就是给模型看的接口文档。参数含义、单位、必填/可选、典型示例写清楚，能省掉 80% 的误调用。
3. **凭证走环境变量，不进上下文**。OpenClaw 侧通过配置注入 token，工具内部使用，返回结果里绝不回显。
4. **错误要翻译成人话**。把 HTTP 409 映射成「订单已存在，订单号 xxx」，而不是把原始堆栈丢给模型。结构化的错误信息，模型才能据此做下一步决策。
5. **超时与重试放在工具层**。工具内部做指数退避、限流退让，Agent 只拿最终结果，避免模型自己发起连环重试。
6. **上线前跑干跑清单**：正常路径、参数缺失、服务 500、返回超大响应，各验证一遍。

## 踩坑点

- **描述含糊**：写「查询数据」这种描述，模型会自由发挥。见过一个工具因为没写清时间戳单位，模型一直把秒当毫秒传。
- **返回体不裁剪**：列表接口一页 200 条全量返回，两轮对话上下文就爆了。要么分页，要么做字段白名单。
- **长任务同步等**：导出报表要 90 秒，Agent 等不住。改成提交任务返回 `job_id`，再给一个 `check_status` 工具轮询。
- **写操作没做幂等**：一次重试导致重复建单。写类工具务必带幂等键。
- **日志泄密**：工具日志打印了完整请求头，token 直接落盘。日志必须脱敏。

## 可复用建议

- 给每个 MCP Server 配一个 `ping` / `health_check` 工具，排障先验通路，再查逻辑。
- 返回结果控制在几百字节内，大对象给摘要加引用 ID，需要细节再用第二个工具取。
- 工具命名带版本或来源，比如 `crm_v2_query_customer`，升级不打架。
- 把上述步骤沉淀成团队模板，新服务接入从「写代码」变成「填空」。

## 总结

Agent 与 API 的握手，本质是契约设计：模型看懂工具描述、凭证安全传递、错误结构化回传、失败有兜底。OpenClaw 提供了 MCP 和插件两条正规通道，剩下的活是工程细节。把每个外部服务当成一个需要精心设计的小产品来做，Agent 的能力上限才会真正打开。
