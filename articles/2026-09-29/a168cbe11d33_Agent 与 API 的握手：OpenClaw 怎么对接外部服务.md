## 背景

Agent 的价值不在"会聊天"，而在"能动手"。一个 Agent 能否可靠地查数据库、发消息、调内部系统，取决于它和外部服务之间的那次"握手"是否规范。在 OpenClaw 里对接外部服务主要有两条路：走 MCP，把服务封装成标准 tool server；或在插件里写适配层直连 API。两条路的核心问题一样——怎么让模型准确知道"有什么工具、什么时候用、结果怎么消化"。

## 问题

实际落地时最常见的四类翻车：

1. 工具描述含糊，模型选错工具或编造参数；
2. 认证管理混乱，密钥被拼进 prompt，甚至写死在配置里提交进仓库；
3. 没有超时、重试、限流边界，一个慢接口拖死整个任务循环；
4. 返回体不做裁剪，一个大 JSON 直接撑爆上下文窗口。

## 做法

以接入一个内部订单查询服务为例，我的标准流程：

**第一步，选接入方式。** 服务会被多个 Agent 复用 → 用 MCP server 封装一次；只有一个 Agent 用、且需要定制鉴权或缓存逻辑 → 插件内直连更省事。

**第二步，写清楚工具契约。** 工具名用动宾结构（如 `query_order_status`），参数注明类型与必填性，描述里额外写两句：什么场景该调用、什么场景不该调用。这一步的收益远大于后面任何调参。

**第三步，认证走环境注入。** 密钥放环境变量或 secret 管理，运行时注入进程，绝不进模型上下文。

**第四步，加边界。** 每次调用设显式超时（比如 10s）；重试只用于幂等操作，带指数退避；有配额的服务加客户端限流。

**第五步，裁剪返回值。** 只回传模型需要的字段，错误统一转成结构化短文本（错误码 + 一句人话），别把堆栈喂给模型。

**第六步，留观测。** 记录每次 tool call 的入参、耗时和结果摘要，出问题能回放定位，而不是靠猜。

## 踩坑点

- **描述歧义**：早年用过 `get_data` 这种名字，模型在两个数据源之间反复摇摆，改名后选择准确率立刻回来。
- **重试非幂等接口**：下单接口超时后重试，结果重复扣款。非幂等操作要么不重试，要么强制带幂等键。
- **MCP server 静默挂掉**：进程崩了，Agent 还对着空气报"工具未找到"，排查半天。务必加启动探活和调用失败计数告警。
- **字段漂移**：外部 API 升级改了字段名，适配层直接报错。适配器里对未知字段容错，关键字段做断言，坏了要坏得响亮。

## 可复用建议

1. 永远在模型和外部服务之间放一层适配器，不直连——限流、裁剪、mock 全在这层做；
2. 工具描述当"提示词"写，写清正反例，而不是当接口文档写；
3. 每接一个新服务，先跑一组金丝雀问题，人工核对工具选择是否正确，再放开上线；
4. 错误信息是给模型看的输入，不是给运维看的日志——短、结构化、可行动。

## 总结

对接外部服务，本质是给 Agent 立"交通规则"：契约清晰、边界明确、失败可解释。OpenClaw 提供了 MCP 和插件两条通道，但握手质量取决于工程细节——描述怎么写、密钥怎么管、失败怎么兜。把这些做扎实，Agent 才能从"能调 API"进化到"可靠地调 API"。
