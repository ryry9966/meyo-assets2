## 背景

RSS 没有死。技术博客、开源项目的 Release Notes、不少论坛的转换网关，高质量信息仍然以 RSS 形式存在。问题在量：我订阅了 60 多个源，工作日每天新增 200+ 条，逐条读不现实，全部跳过又怕漏。稍后读工具本质上是把筛选压力从"现在"挪到"以后"，攒起来更不想看。于是决定把筛选这一步交给自动化管线：RSS 供给，规则初筛，LLM 摘要打分，最后产出一份每天十条以内的日报。

## 问题

核心矛盾有三个：

1. **信息量大但相关度低**。200 条里可能只有 5 条与我当前工作相关。
2. **判断成本高**。判断"这条值不值得读"本身就要先读一遍，这个动作恰好适合丢给模型。
3. **输出不能反向制造噪音**。如果 AI 摘要产出的是另一份 200 条的列表，等于没解决问题。

## 做法

管线分五步，每步独立可重跑：

1. **抓取**：定时任务每小时跑一次，读 YAML 维护的源列表。SQLite 记录条目 GUID 与内容 hash，天然完成增量。
2. **去重归一化**：同一篇文章常被多个聚合源转载。先做 URL 规范化（去 utm 参数、统一协议），再用标题分词 Jaccard 相似度合并。
3. **规则初筛**：关键词命中、来源权重、发布时间窗口，三条规则能把量砍到 20–30 条。这一步很便宜但很关键——直接决定 LLM 的调用量和成本。
4. **摘要打分**：对初筛后的条目抓正文（feed 只有摘要的就去原文提取），限长后喂模型。Prompt 强制结构化输出：一句话概括、三个要点、相关度评分 1–5，原文没有的信息一律不写。低于 3 分直接丢弃。
5. **汇总推送**：按评分排序取 Top 10，渲染成 Markdown 日报，通过 webhook 推到 IM，同时归档一份到笔记目录备查。

## 踩坑点

- **正文提取比想象中脏**。不少站点正文混着代码块和广告节点，摘要容易跑偏。加了降级逻辑：提取结果过短或链接密度过高，就退回只用 feed 自带的 description。
- **模型会补内容**。即使 prompt 里写了"不要编造"，偶尔还是会把常识塞进要点。改为要求每个要点标注对应原文的段落序号，标不出来的丢弃，基本解决。
- **长文撑爆上下文还稀释摘要质量**。改成两段式：先分块摘，再对块摘要做一次汇总，稳定很多。
- **成本没设防**。某天一个源抽风吐了几百条，token 直接翻了一天的量。后来在初筛层加了"单源单日上限 20 条"的硬闸。
- **源会静默死掉**。每两周扫一次全部源，连续失败三次的自动标灰并在日报末尾提示，避免管线无声退化。

## 可复用建议

- **中间产物全部落盘**。抓取、初筛、摘要结果分开存，任何一步坏了可以单独重跑，不用从头来。
- **LLM 调用封成独立一层**。文本进、结构化 JSON 出，换模型只改一处；要接 Agent 或 MCP 工具形态，这一层可以直接包成 tool。
- **日报上限宁少勿多**。10 条是心理阈值，超了就没人看了，宁可让评分门槛"错杀"。
- **先小规模验证一周**。用 10 个源跑通全链路、确认摘要质量可接受，再扩到几十上百个源。反过来做会很痛苦。

## 总结

这套东西没有用到什么高深的技术：定时任务 + SQLite + 一个 LLM 调用层，几百行代码。它的价值不在单点，而在于把"筛选"这件事拆成了规则能做的和模型该做的两层，各自干各自便宜的活。跑了一个多月，日报打开率稳定，确实省下了每天刷 reader 的四十分钟。如果你也在用 RSS 但已经被未读数劝退，值得照这个思路搭一版自己的。
