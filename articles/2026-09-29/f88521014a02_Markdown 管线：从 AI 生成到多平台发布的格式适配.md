## 背景

做 Agent 和自动化内容的朋友大概率绕不开同一个场景：让 LLM 写东西，然后发到不止一个地方——静态站、公众号、知乎、GitHub 仓库。AI 输出的是 Markdown，但"Markdown"只是各平台的最小公约数，渲染器和内容策略差异很大。这篇帖记录我们内部跑了一段时间的格式适配管线，重点是思路和踩坑。

## 问题

直接把 LLM 输出贴到各平台，会遇到四类问题：

1. **语法子集不统一**：脚注、数学公式、任务列表、内嵌 HTML，这些扩展语法在 GFM 没问题，到公众号编辑器基本全丢。
2. **样式与内容约束不同**：公众号只认内联样式且不支持正文外链；知乎吃富文本剪贴板；静态站需要 front-matter。
3. **AI 输出不稳定**：偶尔整篇被代码围栏包住、表格里混入 HTML、代码块内出现 ``` 导致提前闭合。
4. **资源问题**：外链图床防盗链、代码高亮各家实现不一。

## 做法

核心原则一句话：**收紧源头，AST 中转，按目标渲染。**

**第一步：约束源格式。** 不要指望"万能 Markdown"。在系统提示里明确允许的子集：标题、列表、表格、围栏代码块、引用；禁用原生 HTML、脚注、数学公式，需要时用占位符后置处理。同时要求输出用固定哨兵包裹（首行 front-matter 或起止标记），方便截取正文、排除模型的解释性文字。

**第二步：parse 成 AST，别做字符串替换。** 用 unified/remark 把 Markdown 解析成 mdast，所有适配逻辑写成对 AST 的 transform：任务列表降级为普通列表加前缀、图片节点抽出来批量处理、表格包一层横向滚动容器。AST 中转的好处是规则可测试、可组合，字符串正则迟早被嵌套结构反噬。

**第三步：平台适配器。** 每个目标平台一个 adapter，输入同一份 AST：

- 静态站：注入 front-matter（slug、摘要、标签），保留原生 GFM，几乎零成本；
- 公众号：渲染成 HTML 后用 shiki 输出内联样式高亮，全部 CSS 内联，外链转成文末参考列表，图片转存后回写 URL。写入编辑器走剪贴板富文本，比模拟 DOM 注入稳；
- 知乎/掘金：重点是把扩展语法降级。

**第四步：发布前 lint。** 把"允许的子集"做成规则跑在管线上：H1 唯一、代码块有语言标注、图片必有 alt、链接可达、表格列数一致。Agent 场景下把这一步包成一个 MCP 工具，让模型在"发布"动作前必须调用校验，不通过就自己修。

## 踩坑点

- **代码围栏嵌套**：正文示例里出现 ``` 会让 parse 断裂。要求模型对含围栏的代码块一律用四反引号，lint 兜底。
- **公众号外链被吞**：统一转"文内序号 + 文末参考列表"，AST 里一个 transform 搞定。
- **图片重复上传**：转存要在适配阶段一次性完成并缓存 URL 映射，别每次发布重复传。
- **`&nbsp;` 等实体混入**：从网页抓的内容带实体，粘贴后显示异常空格，lint 直接报错。
- **宽表格移动端溢出**：别指望平台自己处理，统一包滚动容器。

## 可复用建议

1. 先只打通两个平台（建议静态站 + 公众号），模式定了之后加平台是体力活不是设计活。
2. 子集规范文档和 lint 规则放同一个仓库，并喂给模型，保证约束与校验一致。
3. adapter 返回统一的 `PublishResult`（url、失败原因、截图），Agent 才能可靠地重试和汇报。
4. mdast 解析结果按内容 hash 缓存，多平台适配只 parse 一次。

## 总结

多平台发布表面是"格式转换"，实际是"源头收紧 + AST 中转 + 目标渲染"的三段式工程。把不确定性消灭在输出约束和 lint 这一层，后面的 adapter 都会简单很多。管线跑顺之后，接入新平台的成本基本只剩写一个 adapter。
