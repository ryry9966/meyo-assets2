## 背景

用 Agent 写技术帖效率很高，但产出之后才是麻烦的开始：同一篇 Markdown，发静态博客要 front-matter，贴公众号要内联样式，知乎编辑器会吞 HTML，掘金只认 GFM。手动改一遍十分钟，三四个平台改下来，比写稿还累。这篇记录一下我把「AI 生成 → 多平台发布」做成自动化管线的实践。

## 问题

三个具体痛点：

1. **AI 输出不稳定。** 同一个 prompt，模型有时二级标题起手，有时用加粗当标题，列表符号混用 `-` 和 `*`，代码块偶尔退化成四空格缩进。
2. **平台方言差异大。** 公众号几乎剥掉全部 HTML 属性；知乎对表格和代码高亮支持有限；静态站又要求 YAML 头。
3. **手动适配不可复现。** 每次粘贴都是一次新的格式事故来源。

## 做法

核心原则：维护一份**规范源**（canonical Markdown），所有平台版本都是它的纯变换产物。管线分四步：

**1. 归一化。** AI 产出先过归一化脚本：标题层级重排（从 `##` 开始、不跳级）、统一列表符号、四空格代码块转 fenced、去掉加粗伪标题。用 remark 的 AST 遍历实现，不写正则。

**2. 校验。** markdownlint 加自定义规则：图片是否有本地副本、链接可达性、表格列数一致。不过 lint 不进入发布阶段。

**3. 按目标变换。** 每个平台一个 transformer：

- 博客：注入 front-matter，图片改相对路径
- 公众号：md → HTML，再用样式内联工具（如 juice）把 CSS 压进 style 属性，代码高亮预处理成行内 span
- 知乎：表格降级为列表或缩进引用

各平台能力清单（支持表格？支持 HTML？图片外链？）写成声明式 config，加平台就是加一条规则。

**4. 接入 OpenClaw。** 管线包成单个 CLI 脚本，注册为 MCP tool。让 Agent 生成完规范源后调用工具，而不是让它逐平台改写输出。

## 踩坑点

- **别用正则处理 Markdown。** 嵌套列表和代码块内的文本会骗过所有正则，mdast 遍历啰嗦但可靠。
- **公众号内联样式有体积上限。** 全量 CSS 转 inline 后部分客户端渲染异常，需要提前做样式瘦身。
- **下划线转义。** `snake_case_name` 这类变量名在部分渲染器里被斜体化，归一化阶段统一处理。
- **front-matter 污染。** 模型有时把 `---` 当分隔线用，整段正文被解析成元数据。校验里加了一条：正文首行必须是标题。
- **图片热链失效。** 外链图重新上传到目标平台，alt 文本在变换时容易丢，AST 变换里显式保留。

## 可复用建议

- 平台能力做 config 驱动，transformer 读 config 自动降级，不写 if-else 硬编码
- 用 golden file 做快照测试：一份规范源 + 各平台预期输出，改管线跑一遍即回归
- 职责边界划清：模型负责生成内容、调用工具；格式变换永远交给确定性代码

## 总结

管线跑通后，「发一篇稿」从一小时手工活变成一次脚本调用。最重要的经验是：不要让模型做确定性的事。模型只产出规范源，归一化、校验、多目标变换全部走 AST 级确定性代码——Agent 管内容，管线管格式，各司其职，出问题时也容易定位。
