## 背景

用 Agent 产出内容后，发布端往往不止一个：博客吃标准 Markdown，知乎、公众号要 HTML，掘金对扩展语法的支持也参差。很多人的第一反应是让模型按平台分别输出，但很快会被维护成本拖垮——每加一个平台就要改一遍 Prompt，且输出永远在漂。我们最后的做法是：**模型只产出一个"规范 Markdown"，格式适配交给独立的管线层**。

## 问题

实际跑下来，AI 生成的 Markdown 大致有这几类脏数据：

- 标题层级不稳定：缺 H1、H2 直接开头、标题里混粗体；
- 代码块语言标记五花八门，部分平台高亮器不认识；
- 脚注 `[^1]`、Mermaid、数学公式，各平台支持度差异大；
- 图片是 Agent 工作区的相对路径，发布后全部裂图；
- frontmatter、思考过程片段偶尔漏进正文。

## 做法

管线分四步，全部要求幂等，可重复执行：

```
agent-output.md → normalize → sanitize → adapter(公众号|知乎|博客) → validate → publish
```

1. **规范化**：统一 H1 唯一、修正列表嵌套、代码围栏语言走映射表（`shell`→`bash`）；frontmatter 摘出来转元数据。
2. **净化**：相对链接转绝对 URL；图片先上传对象存储再替换；HTML 白名单过滤，清理 `&nbsp;` 之类实体。
3. **平台适配**：每个平台一个转换器。公众号转内联样式 HTML；知乎把脚注改写成尾注文本；博客保留 Mermaid，不支持的平台显式降级为代码块。适配器只做"减法和翻译"，不重写内容。
4. **校验**：发布前跑链接检查 + 渲染快照对比，防止某次模型输出格式漂移没被发现。

如果走 MCP，可以把 normalize/sanitize/adapter 注册成独立 tool，让 Agent 只调用 `publish(platform)`，适配细节对它透明。

## 踩坑点

- **别让模型输出各平台格式**。Prompt 写得再严也会漂，转换放代码里才是确定的。
- 正则处理嵌套结构迟早出事，列表、表格务必走 AST（mdast）级变换。
- 降级要显式：Mermaid 渲不出就替换为代码块加截图，不要静默丢内容。
- 幂等很关键：同一份生成物重复跑管线，结果必须一致，否则排查问题会怀疑人生。
- 图片同步上传会阻塞管线，我们改成生成阶段先落本地缓存，发布阶段并行上传。

## 可复用建议

- 单一事实源 + 适配器模式，新增平台只加一个 adapter；
- 把"平台语法差异表"当配置维护，而不是散落在各转换器里；
- 快照测试存渲染后的 HTML，模型升级或改 Prompt 后，diff 一眼看出格式漂移；
- 适配器与内容解耦，任何时刻都能从原始 Markdown 重新出全平台版本。

## 总结

这套管线的核心不是"格式转换"，而是**把确定性从模型端挪到代码端**：模型负责内容，管线负责格式。跑通之后，新增平台基本是一小时级的活，Agent 的输出也因此有了稳定的发布契约。
