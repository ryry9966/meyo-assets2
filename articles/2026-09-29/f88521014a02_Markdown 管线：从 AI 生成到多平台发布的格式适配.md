## 背景

用 OpenClaw agent 写技术内容是常见用法：让它产出初稿、补代码示例、按模板整理结构。但生成只是第一步——同一篇稿子往往要发到博客（Hugo/VitePress）、GitHub、公众号、知乎等多个渠道。Markdown 天然适合做中间格式，问题在于各平台支持差异极大：公众号只认富文本且外链会被删，知乎会剥离一部分 HTML，静态站需要 frontmatter，掘金的代码高亮规则又不一样。

## 问题

如果指望 agent 一次性生成“能直接发布”的内容，实践中做不到。反复出现的事故集中在几类：

- 模型混排 HTML 标签，部分平台正常渲染、部分平台原样转义；
- frontmatter 忘记剥离，元数据直接出现在正文里；
- 外链图片在公众号端加载失败，外部超链接被静默删除；
- 正文里写了 H1，和平台的标题字段重复。

逐平台手工修补不可复现，也不适合交给自动化。核心结论是：**AI 只负责产出一份受约束的规范 Markdown，所有平台差异后置到适配层。**

## 做法

管线分五步。我在 agent 侧做成一个 skill，也可以包成 MCP 工具：

1. **约束生成端**。在 agent 的系统规则里限定白名单语法：只允许标题（从 H2 起）、段落、列表、围栏代码块、引用、图片、表格；禁止内联 HTML 和行内样式；frontmatter 不让模型写，由工具按模板补全。
2. **规范化**。用 remark 在 MDAST 层做收敛：统一列表符号、补全代码块语言标注、剔除白名单外的节点。
3. **资产本地化**。扫描图片引用，下载到本地再按目标平台上传（公众号走素材接口），改写为最终 URL。不要赌外部图床的可用性。
4. **平台适配器**。每个目标渠道一个纯函数 adapter：公众号把代码块转高亮 HTML、外链改写为文末引用；静态站注入 frontmatter；知乎降级复杂表格为列表。
5. **校验与 dry-run**。发布前跑两项检查：违禁元素扫描（内联样式、裸外链、残留 frontmatter）和渲染截图 diff。确认无误才调平台 API 发布，并在 manifest 里记录源文件到各平台 URL 的映射。

## 踩坑点

- **事后清洗不如事前约束**。LLM 会模仿训练语料里的 HTML 混排习惯，靠正则修复永远补不全，白名单要写进生成规则。
- **别用 regex 改 Markdown**。列表里嵌代码块这类结构一碰就碎，坚持走 AST。
- **公众号的外链是静默失败**，不报错直接删，必须主动转成文末引用列表。
- **宽表格在移动端必崩**，适配层降级成列表比强行缩放可靠。
- **frontmatter 泄漏是最高频事故**，把它放进发布前校验的第一条。

## 可复用建议

- 白名单收敛在生成端，平台差异收敛在 adapter，中间永远只有一份规范 Markdown。
- adapter 保持纯函数，每平台一份 profile 配置；新增渠道只需新增一个文件。
- 全流程幂等：源文件只读，产物可随时重建，出问题直接重跑。
- dry-run 加截图 diff 作为发布门禁，比肉眼检查省事得多。

## 总结

这套管线的价值不在单个脚本，而在职责划分：生成端管“内容对”，适配层管“格式对”，校验层管“发布前兜底”。三层拆开后，接入新平台是加一个 adapter 的事，agent 的写稿规则也不用反复改。建议从两三个渠道开始搭，跑顺了再扩。
