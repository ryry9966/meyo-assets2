## 背景

现在很多内容的起点是 AI 生成的 Markdown：技术帖、周报、文档、笔记。写完只是第一步，真正花时间的是发布——公众号不认 Markdown，知乎的支持是语法子集，掘金要求 GFM，静态博客要 frontmatter。同一份稿子贴三四个平台，手动调整的时间往往超过写作本身。

## 问题

归纳下来是三类：

1. **源不干净**：AI 产出经常混入 HTML 标签、标题层级跳跃、错误的代码围栏语言标记、编造的图片链接。
2. **目标方言多**：各平台对表格、脚注、任务列表的支持差异很大，没有一份通吃的语法。
3. **资源依赖**：本地图片、图床失效、锚点断裂，都是发布之后才暴露的问题。

## 做法

我的管线分五步，核心原则是「一份正典 Markdown，多个适配器」：

1. **归一化**：用 remark/mdast 解析成 AST，统一标题层级、剥掉幻觉出来的 HTML、补齐代码块语言标记。所有处理基于 AST 而非正则，嵌套列表和表格才不会被改坏。
2. **校验**：跑一遍 lint——死链检查、图片可访问性、frontmatter 字段完整性。这一步能在本地拦住八成发布事故。
3. **按目标转换**：每个平台一个适配器。公众号走 md→HTML 再内联 CSS（它不认 `<style>`，样式必须全内联）；掘金/知乎主要做语法裁剪；博客目标补 frontmatter 和 slug。适配器是纯函数：输入 AST，输出目标格式，可以单独测试。
4. **资源处理**：发布前把本地图片统一传图床并回填链接。这一步适合交给挂了 MCP 工具的 Agent——上传、重试、URL 回填都是工具调用，让 Agent 处理异常分支比写死脚本省事；但纯格式转换别交给模型，确定性代码更稳。
5. **发布与留档**：有 API 的平台直接推，没有的降级为「复制到剪贴板 + 打开编辑页」。每次发布的产物按 `日期-平台` 落盘，出问题能 diff。

## 踩坑点

- **别用正则改 Markdown**。嵌套引用里的列表、代码块里的 `#` 注释都会误伤，AST 是唯一靠谱路径。
- **公众号的内联样式有白名单**，部分 CSS 属性会被吞，转换器要维护一份属性映射，通用工具很难一次到位。
- **AI 生成的图片链接经常是编的**，校验不能省；失效链接建议在管线里替换成占位并标记，而不是让读者看到裂图。
- **发布产物必须落盘**。平台侧内容被误改时，你有 diff 可查，而不是凭记忆重排。

## 可复用建议

- 把归一化和校验做成独立命令，任何来源的 Markdown 都先过一遍再谈发布。
- 适配器写成纯函数 + 快照测试，平台改版时只改一个文件。
- 管线支持 dry-run：只产出各平台最终稿不入库，人工扫一眼再推。

## 总结

多平台发布的成本不在写作，在格式适配。把它固化成「归一化 → 校验 → 适配 → 资源 → 发布」的管线，每一步可测试、可回滚，AI 生成的提速才能真正落到发布环节。管线本身不复杂，难的是坚持让所有内容都走同一条路。
