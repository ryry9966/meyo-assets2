## 背景

E2E 测试是前端工程里性价比最难权衡的一块：价值明确，但编写和维护成本高。最近我把 OpenClaw 接上浏览器自动化工具（Playwright MCP），让 Agent 参与写 E2E，工作流从“完全手写”变成“Agent 起草 + 人工把关”。跑了两个项目、一百多条用例后，把经验沉淀成这篇。

## 问题

直接让 AI“帮我写一个登录的 E2E 测试”，效果通常很差：选择器靠猜、断言形同虚设、跑起来全红——或者更糟，全绿但什么都没测到。根本原因是 Agent 没有页面的真实上下文，它在凭想象写代码。

## 做法

核心思路一句话：**不让 Agent 编，让它看。**

1. **接入浏览器工具。** 在 OpenClaw 里配置 Playwright MCP（或自带浏览器插件），让 Agent 能打开页面、截图、抓 accessibility snapshot。
2. **先走一遍流程。** 让 Agent 以用户视角实际操作：打开首页 → 点按钮 → 填表单 → 提交，每一步保存 DOM 快照。这是整条链路的地基。
3. **基于快照生成测试计划。** 要求 Agent 先输出结构化的测试点列表（路径、前置条件、断言），人工确认后再写代码。别跳过这步，直接生成代码的返工率会翻倍。
4. **生成 spec 并运行。** 用快照里的真实角色、文本、测试 ID 生成 Playwright spec，本地 headless 跑。
5. **失败回喂。** 用例红了，把 trace 文件和截图路径丢回给 Agent，让它定位是选择器问题、时序问题还是产品 bug。设一个修复上限（比如 3 轮），超过就转人工。

## 踩坑点

- **凭记忆写选择器必翻车。** 哪怕 Agent 声称“我知道这个页面”，也要强制先 snapshot。幻觉选择器是我返工的最大来源。
- **警惕假绿。** Agent 倾向写弱断言（比如只断言 URL 变化）。审核时重点看断言是否验证了业务结果，而不是“页面没报错”。
- **等待策略要显式约束。** 不加约束时它爱用 `waitForTimeout`，这种用例上 CI 必 flaky。直接在提示词里禁止，要求用 `expect(...).toBeVisible()` 这类条件等待。
- **测试数据要隔离。** Agent 写用例时不会主动考虑数据清理，第二轮跑就互相污染。每个用例走独立账号/独立 schema，或统一用工厂函数造数。
- **自我修复循环要封顶。** 不设上限的话，Agent 会反复微调选择器直到“变绿”，而绿的原因可能只是断言被它改弱了。

## 可复用建议

- 把第 2、3 步固化成一个 skill 或自定义指令：“先遍历、再计划、后编码”，三条规则写进系统提示，产出稳定性提升非常明显。
- 团队先落 `data-testid` 规范，Agent 生成选择器的准确率会从“碰运气”变成“基本可用”。
- 评审用例时只盯两处：**断言强度**和**清理逻辑**，其余放手，别逐行抠代码。

## 总结

Agent 写 E2E 的正确姿势不是“一句话生成测试”，而是给它眼睛（浏览器快照）、给它流程约束（先计划后编码）、给它刹车（修复上限 + 人工审断言）。这三件事做对，起草效率的提升是实打实的；但断言质量的最终判断，目前仍然只能靠人。
