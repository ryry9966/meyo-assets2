## 背景

E2E 测试的老问题：写起来慢，维护起来更慢。登录流程改个按钮文案，三条测试一起挂，团队里没人愿意认领，最后覆盖率停在“能跑通主流程”。

Agent 有了工具调用能力之后，这件事的性质变了。它不再只是生成代码，而是可以：读代码库、开浏览器实际操作页面、跑测试、看失败日志、改完再跑。OpenClaw 的 MCP 插件机制正好把这些能力串起来。过去半年我在两个项目里跑通了这套流程，E2E 覆盖从零到稳定维护，分享具体做法。

## 问题

直接让 AI“帮我写个 Playwright 测试”，产出通常不可用：

1. **选择器脆弱**——AI 拿不到真实 DOM，只能猜一条 CSS 路径，页面一改就挂；
2. **API 幻觉**——生成不存在的断言方法，跑都跑不起来；
3. **同义反复**——测试断言的是“代码现在怎么做”，而不是“产品应该怎么做”，全绿但没有价值。

根本原因：写 E2E 测试的难点不在代码，在于理解应用的真实行为、定义验收标准。前者 Agent 可以自己解决，后者必须由人提供。

## 做法

流程拆五步，核心原则是**先探索、后写码**：

**① 给上下文。** 挂上 filesystem MCP，让 Agent 读路由定义、组件目录和现有测试规范。不要整仓喂给它，按页面/路由圈定范围。

**② 让 Agent 探索应用。** 用 Playwright MCP（或等价的浏览器控制插件）实际打开页面、走一遍用户流程、记录真实选择器和行为，产出一份“行为清单”：每条写清入口、操作、预期结果。这份清单是后续所有测试的唯一依据。

**③ 人审行为清单。** 这是唯一必须人工把关的环节——确认每条预期是“应该如此”而非“恰好如此”，改掉错误预期，补边界情况。

**④ 生成并运行。** 按仓库既有规范生成 Playwright 测试，硬约束写进规则文件：只用 getByRole / data-testid、禁止 sleep、测试数据走 fixture。shell MCP 跑测试，失败日志直接喂回 Agent 迭代；设 3 轮迭代上限，超限转人工。

**⑤ 接入 CI。** PR 触发时让 Agent 分析 UI 变更影响的测试并给出修改建议，人来合入。

## 踩坑点

- **不要跳过第②步。** 我们第一次偷懒直接生成，选择器命中率不到一半，返工成本比手写还高。
- **迭代上限必须设。** 否则 Agent 修不动时会往测试里塞 waitForTimeout“糊”过去，留下一堆慢而不稳的用例。
- **每条测试保留一行意图注释。** 这是给未来维护者（无论人还是 Agent）的锚点，没有它，三个月后没人知道这条测试为什么存在。
- **幻觉靠运行来消灭。** 任何没跑过的 Agent 产出只当草稿，测试执行结果是唯一事实。

## 可复用建议

把这套东西沉淀成仓库资产，而不是每次现写 prompt：

1. 规则文件（AGENTS.md 或等价物）固化选择器规范、fixture 约定、迭代上限；
2. 行为清单放 `docs/e2e-specs/` 进版本控制，测试改动必须能对应到清单条目；
3. 按“初级工程师的 PR”标准 review Agent 产出：重点看断言质量，不纠结代码风格。

## 总结

Agent 写 E2E 测试，价值不在省打字的时间，而在把“理解应用行为”这件最枯燥的事自动化了。人保留判断（什么是对的），Agent 承担执行（怎么验证对）。整个流程里最关键的一步不是生成代码，而是那份经过人工确认的行为清单——它是 AI 产出与人判断之间唯一可靠的接口。
