## 背景

在 OpenClaw 的 workspace 里，大多数人熟悉 `AGENTS.md` 和 `TOOLS.md`，但真正决定 agent "行为手感"的往往是 `SOUL.md`。它会被注入系统提示词，定义这个 agent 是谁、用什么语气说话、哪些事绝对不做。很多人把它当成一段"人设文案"随手写几句，结果跑了两周就发现 agent 越来越不像当初想要的样子。

## 问题

SOUL.md 缺失或写得随意时，典型症状有四类：

1. **人格漂移**：同一个 agent，在聊天渠道里话痨卖萌，在 CLI 里冷漠简短，跨会话风格不稳定；
2. **讨好倾向**：用户说什么都对，明明方案有问题也顺着执行；
3. **越界执行**：删文件、外发消息、调用付费接口这类高风险动作没有刹车；
4. **越改越乱**：每次出 badcase 就口头"教育"一下 agent，下次会话全部忘记。

本质上，人格和边界都是运行时约束，不写进文件就不存在。

## 做法

我现在的写法按这个顺序：

**1. 先定边界，再定人格。** 列出高风险动作清单（删除、支付、对外发送、修改系统配置），逐条写成硬约束。人格可以慢慢调，红线第一天就要有。

**2. 用第一人称、现在时。** SOUL.md 是注入 prompt 的，"我会先确认再执行"比"该助手应当……"在行为上更稳定。

**3. 控制在 30–60 行。** 超过一屏，重点就被稀释了，宁可少而硬。

**4. 固定分区**：身份与语气 / 优先级 / 红线 / 风格示例。优先级是关键，比如明确写"安全 > 隐私 > 任务完成 > 语气友好"，否则"幽默"和"精简"冲突时模型会随机二选一。

**5. 用示例代替形容词。** "简短直接"没有约束力，贴一段理想回复的示范，模型会照着模仿。

**6. 和 AGENTS.md 分工。** SOUL.md 管人格与红线，AGENTS.md 管流程与工具规范，重复写两边会互相打架。

**7. Git 版本化，像维护 runbook 一样迭代。** 每次行为跑偏，就把对应约束补进去，等同于写 postmortem 的 action item。

## 踩坑点

- **写成营销文案**："你是最强的助手"这类句子对行为零约束，还烧 token；
- **红线太模糊**："尊重隐私"不如"不读取用户未提及目录的文件内容"，约束必须可判定；
- **人设与边界冲突**：一边要"热情主动"，一边要"少说话"，不排优先级必然翻车；
- **一次写完不再改**：SOUL.md 的价值一半来自持续修订，三个月不动的版本基本等于没写；
- **过度膨胀**：它和 MEMORY.md、工具说明共享上下文，写太长反而降低遵守率。

## 可复用建议

直接套这个骨架：

```
# 身份
# 语气
# 优先级（冲突时按此排序）
# 红线（不可协商）
# 风格示例（给 1–2 段示范回复）
```

配套两个习惯：每两周固定 review 一次，把当期 badcase 转成具体条款；每次改动只加不改太多，方便 diff 回溯。

## 总结

SOUL.md 不是玄学，是一份需要测试和维护的行为契约。人格部分决定 agent "像不像你想要的"，靠示例和优先级支撑；边界部分决定它"敢不敢乱来"，靠硬约束和持续迭代支撑。花一个下午认真写一版，再用两周的 badcase 打磨，收益远高于反复在对话里口头纠正。
