## 背景

我们团队跑着十几个常驻 Agent 任务（定时抓取、数据同步、工具调用代理），每天产生的运行日志散落在多台机器上。之前的日报流程是：早上有人登录机器、grep 昨天的日志、肉眼挑错误、往群里贴一段总结。整个过程二十分钟起步，且经常漏报。

这篇帖子记录我们把它改造成全自动流水线的过程，核心思路一句话：**确定性统计交给代码，模糊归因交给模型。**

## 问题拆解

原始日志有三个特征，导致 LLM 没法直接吃：

1. **量大**：单日日志数百万行，远超上下文；
2. **噪**：健康检查、心跳、debug 级输出占九成以上；
3. **散**：格式不统一，有的 JSONL，有的纯文本。

直接把日志扔给 Agent 总结，结果是贵、慢、数字靠编——模型数数不可靠，这一点试过一次就够了。

## 流水线做法

整体分四步：

**1. 归集与粗滤（纯脚本）**

各机器按天落盘 JSONL，凌晨用 cron 汇总到中心目录。用 jq 做第一层过滤，只保留五个字段：时间戳、任务 ID、工具名、耗时、状态。日志体积缩到原来的 3% 左右。

**2. 统计聚合（纯代码，不走模型）**

写了一个 MCP 工具 `log_stats`，输入过滤后的日志路径，输出固定结构的 JSON：总调用数、失败数、失败率、P50/P95 耗时、Top 5 错误类型及次数。这部分是确定性计算，结果可复现，模型不参与。

**3. 异常切片 + 归因（模型登场）**

失败样本按错误类型分组，每类最多取 3 条，截取堆栈首行和关键帧，拼成小上下文交给 Agent。Prompt 只要求两件事：归纳同类错误的可能原因、标注是否需要人工跟进。输出强制走 JSON Schema 校验，字段不符重试一次。

**4. 模板渲染与推送**

报告固定为 Markdown 三段：总量概览（直接填统计 JSON）、异常清单（模型产出）、待跟进事项。渲染后写入固定路径并推送群机器人。cron 在生成窗口结束后做存在性检查，缺失则单独告警——**日报静默失败比日报有错更糟**。

## 踩坑点

- **时区跨天**：日志是 UTC，报告按本地时区切“昨天”，第一版切分错位导致两个时段数据重叠。统一在聚合层先转本地时区再切窗。
- **重跑去重**：上游任务偶发重试，同一任务 ID 出现两次，失败率虚高。聚合时按任务 ID 去重，保留最后一次。
- **错误摘要截断**：最初直接截前 200 字符，恰好把异常类型那行截掉了。改成先正则提取异常类名 + 首行，再截断。
- **模板漂移**：早期没锁 Schema，Agent 有时把“异常清单”写成散文，下游解析崩。加 Schema 校验 + 失败重试后稳定。

## 可复用建议

1. **能算的不问模型**：计数、分位、去重这类活，十行脚本比一段 Prompt 可靠得多；
2. **中间产物落盘**：粗滤日志、统计 JSON、归因结果都存文件，任何一步挂了可单独重跑，不用从头来；
3. **模板当代码管**：报告模板和 Schema 进版本库，改动走 review，避免“今天的报告格式又变了”；
4. **先跑最小闭环**：先接一个数据源、一个指标、一个推送渠道，链路稳了再横向扩。我们第一版只有一个服务的失败率，跑稳两周后才扩到现在的规模。

## 总结

整条流水线的分工很清楚：脚本负责压缩和算数，MCP 工具负责确定性统计，Agent 只做它擅长的事——把零散的错误样本归因成几句人话。现在日报每天早上八点自动到群，人只需要看“待跟进”那一栏。省下的不只是那二十分钟，更是“今天有没有漏报”这个心理负担。
