## 背景

团队日常信息散落在多路来源：服务器日志、Git 提交、CI 流水线结果、群里的运维记录。以前日报靠人肉拼，经常漏项、格式漂移。最近把这件事交给 OpenClaw 的定时任务加一个汇总 Agent，跑了两周，基本稳定，把方案沉淀一下。

## 问题

人肉日报有三个痛点：收集耗时、口径不统一、容易漏。而"直接让 agent 去看日志写个日报"也不可行——日志量波动大，token 成本不可控，模型还容易把没发生的事写进去。所以核心问题不是"能不能让模型写报告"，而是怎么把它塞进一条可控的流水线里。

## 做法

流水线分四段，关键设计是**收集与生成解耦**：

1. **收集层（cron 脚本）**：三个小脚本分别拉取昨天的日志切片、git log、CI 结果，各自清洗后统一写成一份 JSONL，按日期命名落盘，如 `reports/raw/2024-06-07.jsonl`。这一步纯脚本，不过模型。
2. **预处理**：按关键词和行数上限裁剪。error/warn 全保留，info 抽样，同类事件超过 50 条只留计数加首尾样例。
3. **汇总层（Agent）**：定时任务触发一次 agent run，输入是当天 JSONL 加一个固定模板 prompt。模板写死报告结构：概况 / 异常事件 / 变更记录 / 待跟进，并要求输出 JSON，每条事件必须带 source 行号引用。
4. **校验与投递**：用 JSON schema 校验输出，数字字段回查原始 JSONL，对不上就重试一次；通过后渲染成 Markdown，推送到群 webhook，同时归档到 `reports/daily/`。

## 踩坑点

- **时区边界**：cron 默认 UTC，"昨天"的统计窗口错位 8 小时。所有脚本和 prompt 里显式指定时区，日期由脚本传入，不让模型自己算。
- **日志量尖峰**：某天 CI 重跑三百次，原始输入直接超限。预处理必须做去重和计数折叠，agent 只看摘要层。
- **幻觉**：第一版日报出现过"已修复某问题"——实际日志里只是提到了它。对策是强制 source 引用加数字回查，凡引用不到的条目直接丢弃。
- **静默失败**：最坑的是流水线挂了没人发现。加了一个心跳检查：到点没收到报告，单独发一条告警——"没有日报"本身也是要报警的信号。

## 可复用建议

- 原始 JSONL 保留 30 天，报告随时可重放、可追溯。
- Schema 一旦稳定不要轻易改字段，后续周报、月报的聚合都依赖它。
- 做 LLM 降级：模型不可用时，脚本直接发一版纯统计的极简日报，保证信息不断流。
- 模板放仓库走版本管理，报告格式的变更和代码变更一样可以 review。

## 总结

整套东西代码量不大，核心思路三条：**结构前置**（schema 和模板先定死）、**校验兜底**（引用回查加 schema 校验）、**收集与生成解耦**（agent 只做最难的语义压缩那一环）。模型在流水线里是环节之一，而不是全部——想清楚这一点，日报这类任务就能从"偶尔惊艳的 demo"变成"可以托付的基础设施"。
