## 背景

在 OpenClaw 里跑自动化任务，执行环境比想象中"脏"：定时触发可能重叠、Agent 调 MCP 工具超时后重试、插件在网络抖动后再次投递、排查问题时人工手动补跑一次。只要跑得够久，每个任务迟早会被执行第二次。这时候决定系统是否出事的，不是任务写得多优雅，而是它是否幂等——执行一次和执行多次，最终结果一致。

## 问题

非幂等任务的典型翻车现场：

- 通知类任务重跑，同一份日报在群里发了三遍
- "往配置文件追加一行"的任务，重试后配置重复，下游解析报错
- 调外部 API 创建资源的任务，超时但实际已成功，重试后创建了两份

本质都一样：副作用是**增量式**的，执行次数参与进了最终结果。

## 做法

1. **改写任务语义，把"追加"改成"收敛"。** 把"append X"改成"确保内容等于 Y"，把"发一条通知"改成"确保今天的日报已发出"。状态型操作（set / put / upsert）天然幂等，增量型（add / append / create）不是。
2. **给任务一个确定性 ID。** 用 `任务名 + 执行窗口（如当天日期）+ 关键输入的 hash`，不要用时间戳或随机数。同一窗口内无论重跑几次，ID 不变。
3. **维护一条已处理记录。** 轻量场景一个本地 SQLite 或 JSON journal 就够：执行前查 ID 是否存在，存在则直接跳过。
4. **外部调用优先用平台自带的幂等能力。** 不少 API 支持幂等键，把第 2 步的 ID 直接传过去。
5. **兜底方案：** 对无法幂等的外部操作包一层"先查后做"——先查询资源是否已存在，再决定是否创建。

## 踩坑点

- **标记的写入时机。** "先写标记再做事"：做事失败后任务永远不会再跑（at-most-once）；"先做事再写标记"：崩溃窗口内重跑会重复（at-least-once）。通知丢失比重复更糟就选后者，反之选前者。明确你要哪种失败模式，别默认。
- **用精确时间戳做去重键。** 重跑时时间变了，去重直接失效。键要基于业务窗口，不是执行时刻。
- **两层各重试一次。** MCP 工具内部重试 + Agent 外层再重试，等于放大执行次数。去重逻辑要放在最外层统一收口。
- **LLM 输出不可复现。** 不要拿"两次输出是否相同"判断是否重复执行过，去重要在任务和输入层面做。

## 可复用建议

- 把"**敢不敢直接再跑一遍**"作为自动化任务的验收标准，写完故意连跑两次验证。
- 定时任务统一走一个带 journal 的执行壳：查 ID → 执行 → 记录，插件只写业务逻辑。
- 倾向写"对账式"任务：每次运行先读当前状态、计算差异、只补齐缺失部分。这类任务重跑永远安全。

## 总结

幂等不是加了重试才需要考虑的事，而是自动化的默认前提。假设每个任务都会被执行两次，把语义改写成收敛式的，配上确定性 ID 和一条本地 journal，你会发现重试、补跑、触发重叠这些原本吓人的场景，都变成了无感操作。
