## 背景

跑自动化之后你会发现一个反直觉的事实：任何任务都注定会被执行不止一次。定时任务重叠触发、Webhook 因为对方没收到 ack 而重发、Agent 循环里某一步超时后自动重试、MCP 工具调用在网络抖动后被上层重新发起——这些都是日常。分布式系统里这叫 at-least-once 投递：**重复是常态，不是异常**。

## 问题

问题在于我们写任务时默认它只跑一次。典型的不幂等操作：往文件 append、调用"创建"接口、发一条通知、给计数器加一。最坑的场景是超时重试：第一次调用其实成功了，只是响应没及时回来，Agent 判定失败后重跑，于是同一份数据写了两遍、同一条消息发了两次。这类 bug 平时不发作，一发作就是在生产数据上。

## 做法

我的习惯是把幂等当默认设计，分四步：

1. **定义稳定的幂等键。** 从业务语义推导，比如 `hash(任务类型 + 关键参数 + 时间窗口)`。键里不要带时间戳或随机数，否则每次重试键都不同，去重就失效了。周期任务可以用"日期 + 任务名"做键。
2. **执行前先查账。** 用 SQLite 或一个 JSON 文件维护执行记录，键已存在就直接返回上次结果。如果你在写 OpenClaw 插件或 MCP 工具，可以在工具层接收一个 request_id 并缓存响应，让上层怎么重试都安全。
3. **优先用覆盖语义。** 能 upsert 就不要 insert，能写固定文件名就不要带时间戳的文件名，能"确保状态为 X"就不要"再执行一次动作"。声明式（把系统收敛到目标状态）天然比命令式（追加一个动作）抗重复。
4. **保证单步原子性。** 先写临时文件再 rename，数据库操作放事务里。幂等解决"重复执行"，原子性解决"执行一半"，缺一不可——半完成状态是幂等检查最大的干扰源。

## 踩坑点

- **检查和执行之间有竞态。** 两个进程同时查账都发现"没做过"，然后都执行。低频场景可以接受偶尔重复；高频场景用文件锁或 SQLite 事务把"查 + 记"做成原子。
- **超时被当成失败。** 重试逻辑必须假设"上一次可能已经成功"，而不是"上一次肯定失败了"。
- **缓存命中但参数不同。** 只按 request_id 返回缓存、不校验载荷，会把 A 任务的结果还给 B。键和参数要一起校验。
- **多步任务只做整体幂等。** 第 3 步失败后重跑，前两步必须能被跳过，否则要给每一步单独记账，或用状态机记录进度。
- **幂等键粒度取错。** 只用任务名做键，不同输入会互相误伤；只用输入做键，周期任务每天都被判成重复。键的粒度要和业务语义对齐。

## 可复用建议

- 写任何自动化任务前先回答一个问题：**这个任务连续跑两次，世界会发生什么变化？** 答案必须是"没有变化"。
- 把幂等检查做成中间件或装饰器，而不是在每个任务里手写一遍。
- 在 CI 里加一条用例：同一任务连跑两遍，断言第二次执行后的状态与第一次一致。
- 排查历史故障时，优先怀疑重复投递——它比代码 bug 常见得多。

## 总结

幂等不是锦上添花的健壮性优化，而是自动化系统的入场券。重试、重发、重跑一定会发生，你要做的不是祈祷它们别来，而是让每一次重复执行都变成无害操作。判断标准只有一条：同样的任务执行 N 次，结果和执行一次完全相同。
