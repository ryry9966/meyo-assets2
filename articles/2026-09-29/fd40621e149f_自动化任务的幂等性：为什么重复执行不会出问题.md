## 背景

跑过一段时间自动化的人几乎都遇到过同一个场景：定时任务因网络超时重试了一次，结果消息发了两条、记录插了两行；或者 Agent 在工具调用超时后重新规划，把同一个操作又执行了一遍。

原因不复杂：自动化和分布式环境里，**至少一次（at-least-once）是常态**。重试、重放、补跑都不可怕，可怕的是操作本身不支持重复执行。幂等性解决的就是这件事：同一个逻辑任务执行一次和执行多次，最终效果一致。

## 问题

在 OpenClaw / MCP 的实践中，非幂等的写操作主要有几类：

- **追加类写入**：append 文件、insert 记录、发消息，重复执行就重复生效；
- **有副作用的 API 调用**：创建工单、下单，重放会产生第二份；
- **状态机推进**：重复触发会把状态推过头。

而触发重复的路径很多：调度器重试、Agent 超时重试、人工补跑、上游消息重复投递。你没法消灭这些路径，只能在副作用端兜住。

## 做法

核心原则：**去重逻辑放在产生副作用的那一层**（通常是 MCP 工具服务端），而不是调用方。

1. **定义稳定的业务键**。键必须跨重试保持一致，比如 `任务ID + 时间窗口`，而不是每次执行随机生成的 UUID，重试时带着同一个键。
2. **存储层强约束**。用唯一索引让数据库兜底，而不是先查后插：

```sql
INSERT INTO task_runs (run_key, status)
VALUES ($1, 'running')
ON CONFLICT (run_key) DO NOTHING;
```

影响行数为 0 就是重复触发，直接返回上次结果。

3. **写操作尽量改成 upsert / 设定状态**。"把配置置为 X" 天然幂等；"往列表里追加一条" 就不是。能改的都往幂等方向改。
4. **外部调用记意图日志**。执行前写一条 `running` 记录，成功后更新为 `done`。重试时发现 `running` 且未超时，等待或跳过；确实超时才允许带 force 重跑。
5. **读操作不用管**。查询、列资源天然幂等，精力花在写路径上。

## 踩坑点

- **每次重试生成新 UUID 当去重键**——等于没去重，键的稳定性是第一原则。
- **先查再插的竞态**。两次并发都查到"不存在"，然后都插入。唯一索引才是可靠兜底，应用层判断只能当优化。
- **TTL 设太短**。用 Redis 记去重键时，TTL 必须大于最大重试窗口，否则晚到的重试就穿透了。
- **只在上层去重**。Agent 层做了去重，但 MCP 工具服务内部对 HTTP 超时的重试没管，副作用照样翻倍。
- **把"卡在 running"当成功缓存**。意图日志要记状态，失败要能显式重跑，别让去重层把失败一并吞掉。

## 可复用建议

自动化任务上线前过一遍清单：

- 列出所有写路径，标注哪些非幂等；
- 每个非幂等操作定义稳定的业务键；
- 存储层加唯一约束，不依赖应用层判断；
- 去重记录保留时间 > 最大重试时间；
- 提供 dry-run 和 force 参数，留人工兜底口子；
- 上线前故意连跑两遍，验证第二遍无副作用。

最后一条最实用：幂等性不是推出来的，是跑两遍测出来的。

## 总结

自动化系统里重复执行不是异常，是日常。把"至多一次"的期望换成"至少一次执行 + 幂等副作用"，任务才能放心地重试、补跑、并行。核心就三件事：稳定键、存储层约束、贴着副作用去重。做完这些，定时任务和 Agent 工作流才真正敢无人值守。
