## 背景

在 OpenClaw 这类 Agent 环境里，任务被重复执行是常态而不是异常：模型对结果不确定会重试、调度器超时会重发、用户没看到反馈会手动再跑一遍。调度和重试本身是可靠性机制，但如果每次执行都产生副作用，这套机制就变成了事故放大器。

## 问题

几个典型场景：

- Webhook 处理器被重试三次，工单系统里出现三条重复记录；
- Agent 调 MCP 工具写数据库，请求超时但服务端实际已成功，重试后表里出现两份"唯一"数据；
- 通知插件因网络抖动重发，用户收 到五条一样的消息。

根因都一样：**操作不幂等**。幂等的定义很朴素——同一操作执行一次和执行 N 次，最终状态一致。自动化系统里，凡是没按这个标准设计的写操作，迟早会还债。

## 做法

1. **先区分读写**。读操作天然幂等，不用管；所有写操作默认"它会被调用两次以上"来设计。
2. **用确定性的幂等键**。键必须跨重试稳定：内容哈希、`(源, 目标, 时间窗口)` 组合键都可以。随机 UUID 和时间戳是常见错误——重试时它们会变，等于没设。
3. **把 create 语义改成 ensure/upsert**。工具接口定义为"保证目标状态"而不是"执行一次动作"。`ensure_subscribed` 天然抗重试，`create_subscription` 不是。
4. **数据库层兜底唯一约束**。"先查再插"在并发下有竞态，唯一索引才是最后防线；冲突时捕获异常，视为"已存在即成功"。
5. **状态机 + 条件转移**。操作定义为状态转移，只有合法转移才执行。重复请求落在已达状态上，直接返回当前结果。
6. **不确定时先查询再重试**。超时不等于失败——请求可能已经成功。重试前先查结果，能省掉一半的重复副作用。

## 踩坑点

- **幂等键生成位置错了**：放在每次调用的入口重新生成，重试时键已经变了；
- **接口幂等 ≠ 编排幂等**：三个工具各自幂等，但整条 workflow 被重复触发，依然产生两轮完整副作用；
- **外部副作用难回滚**：发消息、调第三方付费接口，这类操作至少要落一条"已发送凭证"，发送前先查；
- **缓存干扰判断**：查到过期状态，误判"还没执行"，于是又执行了一遍；
- **Agent 重试策略与工具层没对齐**：系统提示里鼓励重试，工具却不支持幂等，等于把风险推给模型。

## 可复用建议

- 工具命名约定：写操作统一用 `ensure_` / `get_or_create_` 前缀，读心术不如命名规范；
- 工具 schema 里把 `idempotency_key` 设为写操作的必填字段，缺了直接报参数错误；
- 维护一张执行日志表 `(key, result, timestamp)`，重试前先查；
- 验收标准就一条：**同一任务连续跑三遍，终态一致，副作用只有一份**。CI 里完全可以自动化这条测试。

## 总结

幂等不是锦上添花的优化，而是自动化敢于重试的前提。Agent 编排越复杂，重试越多，幂等设计的回报就越高。与其在事故后人工清数据，不如在写第一个工具时就想清楚：这个操作被调用两次，世界会不会变样？答案应该是"不会"。
