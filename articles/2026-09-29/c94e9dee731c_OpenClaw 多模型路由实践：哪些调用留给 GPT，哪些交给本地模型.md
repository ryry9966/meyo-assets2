## 背景

OpenClaw 里一个典型的 agent 任务不是一次调用，而是拆解、检索、工具调用、汇总的十几步链路。每一步都打 GPT 级云端模型，账单和延迟会快速失控；全切本地模型（vLLM/Ollama 跑 Qwen、Llama 系列）又会遇到工具调用失败率上升、结构化输出不稳定的问题。OpenClaw 支持按节点和技能配置模型路由，配置本身不难，难的是"怎么分"。

## 问题

我们在实际跑批中撞到的三个矛盾：

1. **成本**：单任务几十次调用，云端长上下文一跑就是几毛到几块，乘上并发很难看。
2. **数据**：日志摘要、内部文档问答这类任务，数据不想出内网。
3. **质量**：规划、多工具编排对模型能力敏感，小模型错一次参数，整条链路报废。

## 做法

1. **先审计再路由**。把一周的任务调用日志按环节打标：规划/编排、代码生成、结构化抽取、摘要改写、向量化。多数团队会发现 60%–80% 的调用其实是抽取、分类和摘要——这部分才是路由的收益空间。
2. **定一条保守的分界线**：
   - 规划、多工具编排、复杂代码生成 → 云端旗舰模型
   - 字段抽取、格式转换、摘要、分类、embedding → 本地模型
   - 涉及内部敏感数据且不要求强推理 → 一律本地
3. **按节点配模型，不要按 agent 配**。编排 agent 用云模型，各 worker 节点按技能类型在 OpenClaw 的模型注册表里指定不同的本地模型，避免一个 agent 内所有步骤共用同一个模型。
4. **配 fallback 链**：本地失败 → 校验不过 → 升级云端。注意触发条件是"校验失败后升级"，不是"本地报错后升级"，后者会把质量问题静默吞掉。
5. **记录四项指标**：每类任务的调用量、平均 token、失败率、人工修正率。跑两周回头看数据，再调整边界。

## 踩坑点

- **本地模型的 JSON 输出别信 schema 兼容声明**。实际会遇到多余逗号、字段名漂移。加一层严格校验加一次重试，仍失败再升级云端。
- **别只按 prompt 长度路由**。长输入不等于简单任务，一段长日志里判断"是否发生故障"同样需要强推理。
- **本地模型冷启动延迟**。vLLM/Ollama 空闲卸载后首次请求可能超过 10 秒，批量任务前先预热。
- **工具调用参数幻觉是静默失败**。不报错但参数是编的，工具层必须自己做参数合法性校验，别指望模型自律。
- **本地模型版本锁死**。升级一次小版本，抽取格式全变，下游解析直接崩。

## 可复用建议

- 用"错一次的代价"划分，而不是"任务难度"：错一次需要人工兜底或影响下游的，上云端；错了能被校验层拦住的，留本地。
- 校验层做成独立中间件，别散在各 agent 里，路由策略调整时只改一处。
- 留一个全局开关支持一键全切云端，排查问题时用来隔离变量。

## 总结

多模型路由不是省钱技巧，而是把"模型能力"当作和缓存、重试一样的工程资源来分配。先用数据找到链路里真正吃能力的那 20% 调用，把剩下 80% 交给可控的本地模型，再用校验和 fallback 兜住边界。OpenClaw 的节点级路由足以支撑这套做法，关键在于：先量化、再划线、持续回看数据。
