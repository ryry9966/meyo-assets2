## 背景

OpenClaw 的 cron 任务本质上是一次“无人值守的对话”：到点后 agent 醒来，手里只有你写的那条 instruction——没有聊天记录，没有文件上下文的默认注入，更没有追问的机会。日常对话里缺上下文可以补问，cron 里没人应答。所以 instruction 的信息完备度，几乎直接决定任务成败。

## 问题

模糊的定时指令通常有三种结局：

1. **跑偏**：agent 理解空间太大，做了不该做的事，比如顺手把结果发到了不该发的会话；
2. **沉默**：agent 不确定“要不要打扰人”，犹豫之后什么都没发；
3. **编造**：数据为空时，agent 自己补了一个“看起来合理”的结果。

这三种都不是模型能力问题，而是 instruction 没把话说死。

## 做法：五段式模板

把 instruction 当成一份极简任务说明书，按五段写：

1. **触发上下文**：一句话说明这是定时任务、要做什么；
2. **数据来源**：精确到文件路径、命令或工具名，不让 agent 猜；
3. **执行步骤**：用可验证的动作词（读取、对比、计算、追加），避免“帮我看看”“总结一下”这类开放式动词；
4. **输出路由**：结果去哪、什么格式、发消息还是写文件、追加还是覆盖，逐条写死；
5. **异常分支**：数据为空、文件不存在、命令失败时怎么办。最稳的写法是“无数据则不发消息，仅在日志文件追加一行”——把沉默变成合法结果。

一份我在用的日报模板：

```text
这是每日 09:00 的定时任务。读取 /root/notes/todo.md，
与昨天归档文件对比，找出新增未完成项。
若无新增：仅在 /root/notes/cron.log 追加一行日期后结束。
若有新增：按 [日期][条目] 格式逐条发到消息渠道，
条数不超过 5 条，不足 5 条按实际数量发送。
```

## 踩坑点

- **依赖会话记忆**：对话里说过的路径、约定、格式偏好，cron 里一概不知，必须原样重写进 instruction；
- **相对时间词**：“今天”“最近”取决于 agent 对时区的理解，建议写成“过去 24 小时（UTC+8）”这种可计算的表达；
- **一个 cron 塞多个任务**：失败时无法定位是哪一步出问题，前一步的异常还会污染后一步的输入；
- **缺空结果处理**：这是编造问题的高发区，“为空时怎么办”必须显式写；
- **任务本身需要判断**：凡是“视情况而定”的逻辑，要么拆成明确规则，要么别放进 cron——需要澄清的任务不适合定时执行；
- **上线前不手动触发**：先强制跑一次，看 agent 实际输出再定稿，比反复调 cron 表达式有用得多。

## 可复用建议

- 写完自检三问：agent 知道**去哪拿数据**吗？知道**结果发给谁**吗？知道**数据为空时该干嘛**吗？三个都答“是”再保存；
- 长任务拆成多个 cron，中间用文件交接，而不是在一条 instruction 里堆步骤；
- 输出格式定死：固定字段、条数上限，下游好消费，agent 也不容易发散。

## 总结

cron 任务的质量上限，就是那条 instruction 的信息完备度。核心思路是把日常对话里的“追问机会”提前补齐：数据来源、输出路由、异常分支三样写清楚，定时任务就能从“偶尔靠谱”变成“默认靠谱”。
