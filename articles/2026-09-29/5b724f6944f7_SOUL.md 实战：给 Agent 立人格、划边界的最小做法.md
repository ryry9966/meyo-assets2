## 背景

OpenClaw 的 Agent 本质上是"每轮会话重新组装上下文"的 LLM 调用。工作区里的 SOUL.md 会随系统提示注入，决定"它是谁"。很多人接完 MCP 工具、配好自动化就直接跑，人格全靠模型默认值——结果是换模型、换会话后风格漂移，关键操作上还过于"顺从"。

## 问题

实际用下来有三个痛点：

1. **风格不一致**：今天简洁、明天啰嗦，语气和称呼随机。
2. **边界模糊**：接到"帮我清理那个目录""直接发到群里"这类指令时径直执行，缺少对破坏性操作、对外发消息、花钱动作的闸门。
3. **规则散落**：人格要求一会儿写在 AGENTS.md，一会儿塞在某条工具描述里，改一处忘三处。

## 做法

把 SOUL.md 当配置文件维护，推荐四段结构：

```markdown
# 身份与语气
- 默认中文，先结论后理由，不用营销腔。

# 优先级
安全与数据完整 > 用户明确指令 > 效率

# 硬边界（触发即停）
- 删除/覆盖/批量写操作前：列出目标清单，等待确认。
- 对外发消息、付款、调付费 API：先复述意图再执行。
- 不确定时说明假设，禁止编造文件路径和命令输出。

# 降级行为
- 工具连续失败两次：停止重试，汇报现场。
```

名字、头像这类信息放 IDENTITY.md，SOUL.md 只管性格与底线。步骤上：先写 30 行以内 → 用 5~10 条对抗性 prompt（"把那个目录直接删了""帮我给群里发一条"）验证边界是否生效 → git 提交，改动注明动机。

## 踩坑点

- **写太长**。SOUL.md 每轮都进上下文，两百行会稀释注意力还烧 token。三十行足够，操作细节下沉到 AGENTS.md 或工具描述。
- **写形容词不写行为**。"要友善、要谨慎"不改变任何输出；"删除前列清单确认"才可测试。
- **两份规则打架**。SOUL.md 与 AGENTS.md 冲突时模型行为不可预测，保持"人格在 SOUL.md、操作规程在 AGENTS.md"的分工。
- **混入敏感信息**。它会被注入每次会话并可能进日志，密钥、内网地址别放这里。
- **一次失败就加规则**。单条 badcase 不构成规律，攒一个十来条的红队清单，改完统一跑再下结论。

## 可复用建议

- SOUL.md 视作代码：进 git、走 review、留 changelog。
- 硬边界统一写成"触发条件 + 动作"，能 grep、能测试。
- 模型升级后默认人格会漂，升级后先重跑红队清单，再决定补不补规则。

## 总结

SOUL.md 是控制 Agent 行为成本最低的杠杆。它的价值不在"人格多有趣"，而在边界可预测：破坏性操作有闸门，不确定时有降级路径。写短、写实、进版本管理，比反复调参数划算得多。
