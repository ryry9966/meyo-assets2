## 背景

我们社区每周都有值得沉淀的讨论，人工整理发周报坚持了三周就断了。于是用 OpenClaw 搭了一个发帖机器人：定时汇总近七天热门讨论，生成草稿，校验后自动发帖。跑了两个月、发了 40+ 帖，中途踩了不少坑，记录如下。

## 问题定义

真正要解决的不是“能不能生成文本”，而是四个工程问题：

1. **内容可信**：引用必须来自真实帖子，不能让模型编
2. **不重复**：同一主题不反复发
3. **失败可控**：API 挂了、被限流了怎么办
4. **质量不漂移**：模板跑久了内容同质化

## 架构与做法

整体分五层，生成与发布严格解耦：

```
调度(cron) → 数据采集 → Agent生成 → 校验/审核 → 发布插件 → 回执落库
```

1. **调度层**：cron 每周五触发，同时保留手动触发命令——前两周主要靠手动跑。
2. **数据层**：通过 MCP 工具拉取近 7 天讨论列表、回复数、点赞数，落 SQLite，按帖子 ID 去重。
3. **生成层**：OpenClaw agent 持有检索工具，prompt 模板进 git 带版本号。要求模型只能引用工具返回的帖子 ID 和标题，URL 由代码根据 ID 拼接，不走模型输出。
4. **校验层**：规则先行——链接可达性、长度区间、禁用词、与历史帖标题相似度（简单 TF-IDF 够用）。规则通过后进人工抽审队列。
5. **发布层**：独立插件调社区 API，带幂等键 `sha256(周号 + 主题hash)`，发布前先查；失败进重试队列，指数退避。
6. **回执层**：发布结果、阅读/回复数回流数据库，作为下周选题输入。

## 踩坑实录

- **模型编造引用**。第一版让模型自己带链接，三条里一条是幻觉 URL。改成“模型只给 ID、代码拼 URL”后归零。教训：事实性字段不要让 LLM 直出。
- **重复发布**。某次重试导致同一帖发了两遍，根因是幂等键只用了日期。幂等键必须第一天就设计好，覆盖“同一周期同一主题只发一次”。
- **Token 成本失控**。把全部讨论原文塞进上下文，一次跑掉大量额度。改为工具侧先做摘要排序，只把 top 10 的标题+摘要给模型，成本降了约 80%。
- **API 限流**。重试没加退避，直接被社区 API 封了一小时。上令牌桶 + 指数退避，别信“偶尔一次没事”。
- **失败静默**。有一次任务跑了但没发出来，三天后才发现。任何一步失败都必须打告警（webhook 到群），静默失败比失败更糟。
- **内容同质化**。模板跑了五周，帖子越来越像。解决：每周向模板注入真实统计（本周最热话题、新成员提问 top3），让数据驱动结构，而不是让模型自由发挥。

## 可复用建议

1. 发布做成独立插件，生成和发布分离，随时可切回人工
2. 事实性字段（URL、ID、数字）一律由代码生成或校验
3. 幂等键、重试、告警是三件套，缺一个都会在某个凌晨坑你
4. prompt 模板进 git 带版本号，出问题能回滚
5. 前两周保留人工审核，观察够了再放开

## 总结

这个项目里模型只占两成工作量，剩下八成是幂等、重试、校验、告警这些“不性感”的工程。建议先跑通最小闭环——单帖、手动触发、人工点发布——再逐步自动化。机器人放大的是流程的质量：流程本身烂，它只会更快地生产烂内容。欢迎在评论区交流你们的自动化实践。
