## 背景

社区内容运营有个老问题：优质素材散落在各处——GitHub Release、群聊讨论、成员博客，需要有人整理后搬到社区论坛。人工搬运重复枯燥，还容易漏。于是我用 OpenClaw Agent 加 MCP 工具搭了一个发帖机器人，跑了一个多月，发布 40 余篇，这里把架构和踩的坑记录下来。

## 问题定义

这件事不是“让 LLM 写帖子”这么简单，真正的约束有三条：

1. 内容必须可溯源，机器人不能编造；
2. 发帖必须幂等，重试不能发出重复帖；
3. 质量必须可控，不能让营销腔污染社区。

## 架构与步骤

整体分四层：

- **触发层**：cron 定时（每天早九点）+ webhook 手动触发。
- **采集层**：三个 MCP 工具——GitHub Release 读取、RSS 拉取、社区 API 查询近期热帖。
- **生成层**：Agent 拿到原始素材后做摘要归类，按社区模板生成草稿。关键设计是草稿不直接发布，先写入本地 SQLite 的 drafts 表。
- **发布层**：独立脚本从 drafts 表读取已审核草稿，调用社区发帖 API。幂等键 = 内容 hash + 日期。

## 踩坑实录

**坑一：Agent 重试导致重复发帖。** 最初把发布动作也交给 Agent，网络超时后 Agent 自动重试，同一内容发了三遍。解法：把写操作从 Agent 循环里剥离，Agent 只生成草稿，发布由确定性脚本完成，幂等键兜底。

**坑二：MCP 工具超时传染。** 某个 RSS 源偶尔很慢，单工具 30 秒超时拖死整个任务。解法：给每个 MCP 工具设独立超时加降级策略——跳过该源、记日志、下轮补偿。

**坑三：LLM 语气失控。** 模型默认爱写“重磅！”“必看！”，社区观感很差。解法：语气约束写进 system prompt，附三篇社区高赞帖做 few-shot，再加硬规则：禁止感叹号连用、禁止素材支撑不了的形容词。

**坑四：时区。** cron 按 UTC 跑，帖子早上七点就发出去了。容器里显式设置 TZ，草稿里记录本地时间戳。

**坑五：格式漂移。** 社区 Markdown 渲染器不支持脚注等语法，生成时看着正常，发出来是乱的。解法：发布层加一道渲染白名单校验，不支持的语法直接替换。

## 可复用建议

- 生成与发布分离：Agent 产草稿，脚本管发布，用 draft → approved → published 状态机流转；
- 一切写操作带幂等键；
- 先跑两周 dry-run，人工逐篇审核再放行，收集完 prompt 问题后逐步放开；
- 每篇帖子附素材来源链接，方便社区回溯。

## 总结

这个项目最大的收获不是省了多少时间，而是验证了一个模式：Agent 适合做“理解与生成”，不适合做“执行与写入”。把确定性操作留给传统代码，把模糊任务交给 Agent，稳定性会好很多。MCP 工具配置已放进社区仓库，欢迎复用和改进。
