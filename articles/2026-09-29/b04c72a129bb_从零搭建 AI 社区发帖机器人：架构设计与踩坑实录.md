## 背景

我们社区每周都有值得沉淀的内容：issue 讨论、插件更新、群里的零散技术问答。人工整理发帖坚持了两个月，节奏就断了。于是想做一个发帖机器人：定时拉取素材，让 Agent 起草帖子，经人工确认后发到社区板块。目标很克制——不是全自动营销号，而是一条"自动起草、人工把关"的辅助流水线。

## 问题

最初原型把"生成 + 发布"塞进同一个 Agent 循环里，跑了一周暴露三个问题：模型会编造不存在的 issue 链接；同一主题隔两天发两遍；有一次代码块没闭合，整页排版崩了。本质原因是：把 LLM 当成了可信的发布者，而不是一个需要约束的起草者。

## 架构与步骤

最终架构拆成四层，所有动作走 MCP 工具，行为可审计：

1. **素材层**：三个只读 MCP 工具——查 git log、查 issue 列表、读社区精华帖，以插件形式挂在同一个 server 上。模型只能引用工具返回的真实 ID 和链接，禁止自己拼 URL。
2. **起草层**：Agent 基于素材生成草稿，写入 SQLite 草稿队列，草稿带内容哈希用于查重。
3. **审核层**：草稿进入 staging 状态，我在终端用一条命令确认（approve / reject / edit）。发布凭证单独发放，且只接受 staging 里的草稿 ID，防止模型绕过审核直接调用。
4. **发布层**：带幂等键的发布工具 + 频率限制（每天上限 2 帖，失败指数退避重试）。

调度用 cron 触发，Agent 循环设置了最大迭代次数（8 次）和超时，避免工具调用死循环。

## 踩坑实录

- **幻觉链接**：最有效的治理不是在 prompt 里求它别编，而是发布前用校验工具逐条核对引用 ID 是否存在于素材层返回结果中，对不上就打回。
- **重复发帖**：只做内容哈希不够——改几个词哈希就变了。补了一层标题相似度检查（简单编辑距离即可），再对照发帖历史表。
- **频率风险**：调试第一天连续发了 5 帖测试帖，差点被当成 spam。后来把测试发布指向私有测试板块，主板块凭证平时不出现在环境变量里。
- **排版崩坏**：发布前加 Markdown lint 步骤：代码块闭合、标题层级、链接格式，任一失败退回草稿。
- **时区与漏跑**：cron 机器人和本地时区不一致，错过两次发送。改为调度器落库记录"上次运行时间"，启动时补偿执行。

## 可复用建议

- v1 一定要留人工审核门，先让机器人证明草稿质量，再谈自动化程度。
- 发布凭证最小权限、独立管理，模型永远不直接持有。
- 每次工具调用的输入输出都落日志，排障时是救命稻草。
- 幂等、限流、查重三件套，应该在写第一行生成代码之前就设计好。

## 总结

这个项目做下来，模型相关代码大概占两成，剩下八成都是工程护栏：校验、幂等、限流、审计。AI 发帖机器人的核心竞争力不在"会不会写"，而在"会不会在正确的时候写正确的东西，并且出错时能被拦住"。建议想做同样事情的同学，从人机协同的半自动版本起步，护栏先行。
