# LLM 输出解析的防御性编程：JSON 标签混合格式处理实践

## 背景

在 OpenClaw 的 Agent 工作流和 MCP 工具链里，我们常用一种简单约定拿结构化数据：要求模型把结果包在 `<json>...</json>` 标签中，插件侧截取后 `json.loads`。约定本身没问题，问题在于模型不总是守约——长上下文、中文语境、换模型版本，任何一种都可能让输出漂移。

## 问题

同一个 prompt，实测输出会漂成好几种形态：

- 围栏混入：```` ```<json>{...}</json>``` ````，或标签内再嵌围栏
- 标签漂移：`<JSON>`、`<output>`、`<result>` 混用
- 前后缀文字："以下是解析结果：…" 出现在标签外
- 全角字符：`<ｊｓｏｎ＞`、中文引号，中文输出里尤其常见
- JSON 本身不干净：尾逗号、被 max_tokens 截断

如果解析只写了"找 `<json>` 标签"这一条路径，任何一种漂移都会断掉整条 pipeline，而且自动化场景里往往要等下游任务空转了才发现。

## 做法：分层防御

核心思路是把**抽取 → 清洗 → 校验 → 重试**拆开，每层独立兜底。

**1. 抽取层：匹配链代替单一正则**

```python
PATTERNS = [
    r"<json>\s*(.*?)\s*</json>",               # 精确匹配
    r"<(json|output|result)>\s*(.*?)\s*</\1>", # 别名放宽，配 IGNORECASE
    r"```(?:json)?\s*(.*?)```",                # 裸围栏兜底
]
# 依次 re.search(..., re.DOTALL)，全部失败再做平衡花括号扫描
```

平衡花括号扫描就是逐字符计数取第一个完整的 `{...}` 块，十几行搞定，是最后一道保险。

**2. 清洗层**：抽出来别急着 loads。去掉围栏残留、BOM、零宽字符；只在引号和标签位置做全角→半角转换，别转全文，否则会破坏数据里的中文标点；移除 `}`/`]` 前的尾逗号。

**3. 校验层**：loads 成功不等于能用。用 pydantic 或 JSON Schema 校验字段和类型，失败时把原始输出连同异常一起记日志。

**4. 重试与降级**：解析失败不要裸抛。把报错回传给模型做一次自我修正（上限 1~2 次），仍失败则降级走宽松模式，并把 raw 输出落盘，方便事后回放。

## 踩坑点

1. `.*` 贪婪匹配在多标签输出时会吞掉中间内容，务必非贪婪 + `re.DOTALL`
2. 全角字符肉眼极难发现，`json.loads` 报的行列号会把排查引向错误位置
3. 花括号扫描不跳过字符串字面量的话，遇到值里含 `{` 的 JSON 直接截错
4. 重试不设上限等于烧 token 的死循环
5. 只记异常不记 raw 输出，等于放弃回放定位的能力

## 可复用建议

- 把这套流程封装成公共解析工具，所有插件和 MCP 工具共用一份，别各写各的
- prompt 里给一个 few-shot 输出示例，比强调十遍"请严格按格式输出"有效
- 准备一组漂移样例（围栏、全角、别名、截断）做成单测，换模型或升级版本后跑回归
- 把解析失败率当监控指标：突然升高，大概率是模型行为变了，不是你的代码变了

## 总结

防御性解析的前提是承认"约定会失效"。抽取宽容、清洗克制、校验严格、重试有界，再配上原始输出留档和漂移率监控，这套组合拳比 prompt 里任何一句"请务必"都可靠。花半天把公共工具做好，之后每个新 Agent 都在吃这份红利。
