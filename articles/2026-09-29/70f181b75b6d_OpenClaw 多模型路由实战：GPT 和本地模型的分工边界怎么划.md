## 背景

OpenClaw 的 agent 循环里，模型调用其实分好几类：规划与工具编排、正文生成、结构化抽取、高频小调用。很多团队起步时要么全挂 GPT，要么全挂本地模型——前者一周跑下来账单难看，后者工具调用成功率惨不忍睹。我们目前的做法是把两类模型显式分工，跑了一个多月，把经验和坑记录下来。

## 问题

核心痛点是判断标准不清晰。两类典型事故：

- 让本地 14B 模型做多步 function calling，第二步就开始编造工具参数，agent 循环直接死锁；
- 把纯摘要、打标这类任务也发给 GPT，一天几千次调用，成本占大头，但质量收益几乎为零。

## 做法

先把任务按三个维度分类：**是否涉及工具调用、是否接触私有数据、调用频次**。然后按这个路由表分配：

| 任务类型 | 模型 | 理由 |
|---|---|---|
| 规划、多步工具编排 | GPT | tool-call 稳定，容错好 |
| 摘要、改写、翻译、打标 | 本地模型 | 高频、无状态、成本低 |
| 私有数据粗筛 | 本地模型 | 数据不出机 |
| schema 校验失败的兜底重试 | GPT | 一次性纠错，量很小 |

落地步骤：

1. 在 OpenClaw 的 agent 配置里声明两个 provider，主模型（agent loop 用的那个）固定为工具调用强的云端模型，**不要在会话中途切换模型**，上下文风格不一致会导致行为漂移。
2. 高频、无状态的任务走本地模型，用 Ollama 或 vLLM 起 Qwen 系列或同级模型就够了，不必追最大参数量。
3. 在插件层加一道 schema 校验：本地模型输出不合法时，升级用 GPT 重试一次。这是整套路由里收益最大的一个闸门，失败率肉眼可见地降下来。
4. 记录每个模型的调用次数、失败率、token 花费，跑一周，边界自然就浮出来了，比拍脑袋准。

## 踩坑点

- 本地模型**标称支持 tools 不等于真能用**，务必拿你真实的 MCP 工具清单跑一轮回归测试，尤其是多工具、多参数的场景。
- 上下文长度：OpenClaw 的 system prompt 加上 MCP 工具描述轻松超过一万 token，本地模型 context 配到 32k 以下会静默截断工具定义，而且不报错，非常隐蔽。
- 别只看延迟数字：本地 7B 生成 2000 token 长文的总耗时，在消费级显卡上往往比 API 还慢，"本地=快"是错觉。
- 两个模型的 JSON mode 行为不一致，解析器要按最严格的那个写，不要假设两边输出完全同构。

## 可复用建议

- 路由配置进版本库，改动走 review，和代码同权重。路由规则本质是工程决策，不该藏在运行时手动改。
- "本地优先、GPT 兜底"比"GPT 优先、本地省钱"更容易落地——前者只损失钱，后者损失可用性，而可用性是 agent 的生命线。
- 用失败率而不是成本做第一指标，成本是失败率稳定之后的副产品。

## 总结

多模型路由不是省钱技巧，而是把"任务-模型"的匹配关系显式化。先保证 agent loop 的工具调用稳定，再把可降级的任务逐步迁去本地，用 schema 校验做闸门，用一周的真实数据决定边界。做到这四步，这套路由基本不需要再频繁调整。
