## 背景

在 OpenClaw-CN 排障互助是日常：贴一段日志、贴一份 agent 配置、贴 system prompt，或者干脆让 agent 自己生成"问题摘要"发到群里。动作很快，但很多人没意识到，求助的过程本身就在把内部工作流和敏感信息推向公网。尤其当你的 agent 接了 MCP、插件和自动化任务，泄露面比传统应用大得多。

## 三条主要泄露路径

1. **人为粘贴**：日志里带 token、session ID、内部域名和绝对路径；system prompt 里藏着你的私有规则、客户名和业务约束。
2. **Agent 自主输出**：digest 机器人或自动总结 agent 读取了 memory 和 workspace，把私人笔记、未公开项目一起写进公开帖。
3. **权限过宽**：demo 和生产共用一把 MCP key，agent 有整盘读写权限，发帖内容未经审查，等于直接开门。

## 做法

1. **建"展示用"工作区**：单独 profile，独立空 memory，专用 key 只给最小只读权限，路径和端口与真实环境错开。
2. **粘贴前脱敏三件事**：密钥换成占位符（如 `sk-XXXX`）；内部域名、IP、绝对路径统一替换为 `example.com`、`/path/to/...`；客户和项目名改成代称。
3. **system prompt 只贴相关片段**：与问题无关的身份设定、私有规则整段删掉再贴。
4. **Agent 产出当不可信内容**：机器人生成的摘要、周报、issue 内容，发出前必须人工过一道，重点查是否引用了 memory 里的私密条目。
5. **给自动化 bot 划白名单**：digest 类 agent 只允许读指定目录，workspace 其他部分和 memory 文件默认拒绝。

## 踩坑点

- **折叠的日志才是雷区**：贴出来时只看了前几行，展开后底下埋着完整请求头。
- **截图比文本更难脱敏**：小字、侧边栏、文件树都可能带路径和人名。
- **删帖不等于失效**：泄露的 key 一旦进过公网，唯一正确动作是轮换，删帖只是止损。
- **bot "顺手"读了不该读的**：权限给了就收不回那一次读取，事后补救意义有限。

## 可复用建议

- 发布前 checklist 四问：有没有 key？有没有内部域名？有没有真实路径？agent 是否参与了生成？
- demo 资源统一 `demo-` 前缀命名，方便识别和回收。
- 养成占位符习惯，配置模板里永远不放真值。
- 每季度轮换一次演示用 key，弃用即时作废。

## 总结

Agent 时代的安全红线不是"少用自动化"，而是把"给社区看的系统"和"真正干活的系统"物理隔离。凡是贴出去的，一律假设它已被截图保存；凡是 agent 要发出去的，一律假设它会读到你不想公开的东西。隔离加审查，成本很低，但对个人和小团队来说，这两步能挡住九成事故。
