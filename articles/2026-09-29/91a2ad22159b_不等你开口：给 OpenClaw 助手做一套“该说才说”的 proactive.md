## 背景

大多数人对 AI 助手的用法还是“你问它答”。但日常里真正省时间的往往是另一类事：证书快过期提前三天告诉你、监控指标突破阈值时把上下文捋成一封信、每天早上把待办汇总成日报。这类事没人愿意手动触发，天然适合让助手主动来。

OpenClaw 在架构上给了两个 proactive 底座：**heartbeat（心跳唤醒）** 和 **cron（定时任务）**。这篇讲怎么把两者组合成一套“该说才说”的主动通知机制，以及我踩过的坑。

## 问题

朴素的 proactive 很容易做成骚扰源：

- 心跳半小时醒一次，模型没东西说也硬找话说，一天几十条废话，第二天你就把它静音了；
- 检查项写成“帮我盯着重要的事”，模型自行发挥，产生幻觉提醒；
- 同一件事反复报，没有去重和状态。

所以工程问题其实是：怎么让“主动”**便宜、可判定、有状态、有出口**。

## 做法

1. **心跳 = 轻量巡检，不是聊天。** 在 workspace 放一个 `HEARTBEAT.md`，只写两样东西：检查项清单，和“什么情况才值得打扰用户”的判定标准。每轮心跳模型读文件逐项对照，没有可报的就返回固定确认（HEARTBEAT_OK），这轮不会投递到任何渠道。把“沉默是默认值”写成明确指令，效果立竿见影。

2. **确定性任务交给 cron。** 固定时间的日报、周报、缴费提醒，不要指望心跳“碰巧”在早上触发，直接配 cron 表达式投递到指定 channel。心跳管“条件触发”，cron 管“时间触发”，别混。

3. **状态外置。** 用 `MEMORY.md` 或独立 JSON 记录：上次检查时间、上次读到的值、已提醒未确认的事项。每轮做 diff，变化超过阈值才说话——这是去重的关键。

4. **通知分级。** 在 HEARTBEAT.md 里定义 P0（立即发：服务挂了、额度见底）、P1（攒进日报）、P2（只记录不吭声）。分级写清楚，模型执行就稳定。

5. **session 隔离。** cron 巡检用独立 session 跑，别把中间过程污染进主对话上下文。

## 踩坑点

- **心跳别调太快。** 分钟级间隔 token 账单很难看，且多数轮次是空转。低频 + 收敛检查项才是正解。
- **检查项必须可判定。** “证书是否 7 天内过期”可以，“有没有异常”不行。可判定 = 模型不用猜。
- **去重做在状态里，不靠模型记忆。** 跨 session 它什么都不记得，已提醒事项必须落盘，用户确认前不再报。
- **时区。** cron 跟宿主机走，容器里是 UTC 就会晚八小时提醒，部署完先确认。
- **权限收紧。** 能主动发消息意味着 agent 可随时触达你的聊天渠道，给它最小渠道权限，别让它读全量历史。
- **发送失败没有自动重试。** 渠道挂了那条提醒就丢了，重要通知至少落一个待发文件，下轮心跳补发。

## 可复用建议

把每个 proactive 行为拆成四要素再动手：**触发器**（心跳/cron）+ **判定条件**（可 diff 的规则）+ **状态**（落盘的 diff 与去重）+ **出口**（渠道与分级）。四要素写不清晰的任务，说明还不该自动化。

另一个验证技巧：新检查项先让它只写日志、不发消息，跑一周看误报率，再开放投递，省得调试期轰炸自己。

## 总结

Proactive 的价值不在“主动”，在“准”。它本质是个降噪问题：便宜的巡检、严格的判定、有状态的去重。OpenClaw 把 heartbeat、cron、渠道投递这些底座给齐了，剩下的事是把你自己的判断标准写成模型能执行的文件——没有捷径，但写完之后，“不等你开口就把事情办了”才真正成立。
