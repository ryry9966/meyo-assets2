## 背景

E2E 测试是团队里最“该做但总被推迟”的事：写起来慢、选择器脆、维护成本高。我们自己的 Playwright 套件，核心链路覆盖率长期停在 40% 左右——不是不想补，是补测试的时间永远排不上优先级。

最近我们尝试把这件事交给 OpenClaw 的 Agent，思路不是“让 AI 生成测试代码”，而是把 Agent 当成一个有浏览器、有规范文档、有反馈回路的新同事。跑了两周，新增 60 多个用例，稳定通过率 92%。把踩过的坑整理如下。

## 问题：裸生成不可用

最早的做法是把页面截图丢给模型，让它直接输出测试文件。结果几乎不可用：

- 选择器靠猜，`.css-1a2b3c` 这类样式名满篇都是，页面一改全挂；
- 断言形同虚设，很多用例只 assert 元素存在，跑过等于没测；
- 到处是 `sleep(3000)`，本地能过，CI 里随机挂。

结论很明确：Agent 没有真正“打开过页面”，写出来的就是想象中的测试。

## 做法：给 Agent 一个 QA 的工作环境

我们把流程改成了四步：

1. **准备上下文包**。仓库里放一份 `testing-guide.md`：路由清单、选择器约定（只允许 getByRole / getByTestId）、命名规范、数据清理要求。Agent 每次写测试前先读它。
2. **接入浏览器工具**。通过 Playwright 的 MCP 工具，让 Agent 能真实启动浏览器、访问页面、导出可访问性树。它写的每个选择器都必须来自实际探测到的 role 或 testid，而不是脑补。
3. **生成—运行—修复循环**。Agent 产出用例后在沙箱里自己跑，读失败输出、自行修复。循环上限设 3 次，3 次跑不过就打上标记丢给人工，避免无限重试烧 token。
4. **人工审查门槛**。产出统一进独立分支，审查时重点看断言：是否验证了业务结果（订单状态、跳转后的数据），而不是元素存在。

## 踩坑点

- **登录态**：Agent 一开始每个用例都完整登录一遍，套件跑 20 分钟。改用 `storageState` fixture 复用会话后降到 4 分钟。
- **测试数据污染**：它会建测试订单但不知道删。现在强制要求 teardown，或使用带唯一后缀的测试账号。
- **隐性 flaky**：Agent 修失败的方式经常是加长等待。我们在 lint 里直接禁了 `waitForTimeout`，逼它改用条件断言。
- **覆盖假象**：它很乐意一口气生成 10 个相似用例。后来改成每次只喂一个“黄金流程”（下单、退款、改地址），宁缺毋滥。

## 可复用建议

- 把测试规范写成仓库内文档而不是塞进 prompt，Agent 按需读取，规范迭代不用改提示词。
- 选择器约定 + lint 规则是这套流程的地基，先于一切 Agent 配置。
- 循环必须设上限，产出必须走独立分支——把它当成“产出很快但需要 review 的初级 QA”来管理。

## 总结

Agent 写 E2E 测试，真正需要的不是更强的模型，而是和人类 QA 相同的工作条件：能打开页面、能跑测试、能看到失败、有明确规范。做到这四点，它就是一个不知疲倦的测试补位；做不到，它只是把“脆的测试”生产得更快。
