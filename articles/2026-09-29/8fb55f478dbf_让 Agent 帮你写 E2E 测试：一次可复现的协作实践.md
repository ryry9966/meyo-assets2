## 背景

E2E 测试长期处于"重要但不讨喜"的位置：写起来慢、选择器脆、维护成本高，团队里往往只有一两个人愿意碰。最近我把 OpenClaw 的 agent 接上浏览器类 MCP 工具（Playwright 那一套），让它参与 E2E 用例的编写和调试，跑了两周。整体判断：初期能省一半以上工作量，但前提是你要先给它立好规矩。

## 问题

具体痛点有三个：

1. 从零写一条用例，要翻路由、翻组件、猜接口返回，半小时起步；
2. UI 一改，断言和选择器成片失效，没人愿意修；
3. 新功能上线前想补回归用例，排期永远排不上。

这三件事恰好是 agent 擅长的：读代码、爬页面、跑命令、看报错、循环修。

## 做法

流程分五步：

1. **固定技术底座**：Playwright 做执行器，agent 通过 MCP 的 browser 工具（导航、截图、点击、读 DOM）实际操作页面，而不是只靠读代码猜行为。
2. **先立约定再写代码**：把团队规范写成一份可复用的 skill 文档喂给 agent——统一用 `data-testid`、禁用硬等待、每个用例自带数据准备和清理、断言必须校验业务结果而非仅元素存在。
3. **小批量生成**：一次只写一个页面的 2~3 条核心路径用例，生成后立刻跑，红的自己看 trace 修，修不动就停下汇报。
4. **自跑自修循环**：`生成 → 执行 → 读失败报告 → 改 → 重跑`，限定最多 5 轮，防止它在一个 flaky 用例上空转。
5. **人工门禁**：agent 的产出一律走 PR review，重点看断言强度和清理逻辑——这两个地方它最容易糊弄。

## 踩坑点

- **"永远绿"的用例**：agent 最常见的偷懒是只断言元素可见。后来约定里明确：review 时把断言删掉，用例必须变红，否则打回。
- **硬等待泛滥**：它很爱写 `waitForTimeout(3000)`。约定里直接禁止，只允许 `expect(...).toBeVisible()` 这类自动重试断言。
- **假设数据库状态**：它默认环境里有测试账号和干净数据。解法是把 seed/reset 脚本封装成 MCP 工具，用例 setup 阶段强制调用。
- **上下文膨胀**：整份 Playwright trace 喂回去，token 烧得快还抓不住重点。只喂失败步骤附近的截图和报错片段，效果好得多。
- **一次生成太多**：一口气写十个用例，错误会滚雪球。控制在个位数，红一条修一条。

## 可复用建议

- 测试规范做成 skill 文档，换项目只需替换路由表和示例页面，流程本身不用动；
- 让 agent 按统一格式输出 PR 描述（覆盖路径、断言列表、数据准备方式），review 成本会明显下降；
- 给它一个"放弃通道"：跑满轮数或连续两次同因失败就停下等人，比它自己瞎改强；
- 已有稳定用例库的项目，先让它做"补断言、修选择器"这类维护活，收益比从零生成更稳。

## 总结

Agent 写 E2E 测试，本质是把"翻页面、写样板、追报错"这类机械劳动外包出去，而约定、数据治理和断言质量仍要人来兜底。它不是替代测试工程师，而是把那条"没人想写但都得写"的用例流水线跑了起来。如果你已有 agent + MCP 的基础环境，建议从一个小页面的三条用例开始试，别一上来就全量铺开。
