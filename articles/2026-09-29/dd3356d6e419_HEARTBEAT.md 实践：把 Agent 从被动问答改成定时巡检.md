## 背景

OpenClaw 的 Agent 默认是被动式的：你发一条消息，它响应一次。但运维和自动化场景里，真正值钱的是"没人问的时候它也在看"——CI 是不是红了、磁盘还剩多少、RSS 有没有值得读的更新。OpenClaw 为此内置了心跳机制：调度器按固定间隔（默认 30 分钟）唤醒 Agent，Agent 醒来后读取工作区根目录的 `HEARTBEAT.md`，按里面的指令决定做什么。文件为空或写着 `NO_REPLY` 时保持沉默，否则执行任务，必要时还能主动给你发消息。

## 问题

这文件有两种常见的"死法"。一种是干脆不写，心跳照常触发，token 白烧；另一种是堆满"每天帮我总结一下 XX"，Agent 每次醒来都汇报一遍，第三天你就开始烦它，最后整个机制被关掉。本质问题是：大家把它当成了待办清单，而它其实应该是一份巡检手册（runbook）。

## 做法

1. **写条件，不要只写动作。** 差的写法："每天检查一下 CI"。好的写法："检查 CI 状态；全部通过则回复 NO_REPLY；有失败才通知我，并附失败的 job 名。"让 Agent 每次醒来先做判断，大部分时候沉默。
2. **用 NO_REPLY 控制噪音。** 这是心跳机制的约定：这轮没什么值得说的，就让 Agent 显式输出 `NO_REPLY`，它不会打扰你。把"默认沉默、异常才报"写进文件开头，当作总原则。
3. **用状态文件去重。** 让心跳任务读写一个小 JSON 或日志（记录上次通知的时间和内容），用来判断"这件事是不是已经报过了"。没有状态，Agent 很容易每个周期把同一件事推给你。
4. **控制间隔和权限。** 分钟级的高频任务别靠心跳，交给系统 cron 或外部触发器，心跳只做低频巡检。另外注意：心跳是无人监督执行的，给它挂的 MCP 工具和插件要收窄权限，避免破坏性操作。

## 踩坑点

- **token 成本被低估。** 每次心跳都是一次真实的模型调用，清单越长烧得越快。保持 3–5 条以内，能用脚本先判断的就先跑脚本，Agent 只看结论。
- **重复执行。** 没有状态文件时，"发现即通知"会退化成"每次心跳都通知"。
- **重任务阻塞。** 心跳跑在主会话里，别让它当场抓几百个网页。让后台脚本先干活，心跳只读摘要、做判断。
- **时间感知不可靠。** "每天早上报一次"这类指令，最好让 Agent 先查系统时间再决定，或干脆把定时逻辑外置到 cron。

## 可复用建议

把 `HEARTBEAT.md` 当成一份持续演进的 runbook 来维护：每条任务 = 触发条件 + 判定逻辑 + 升级路径（沉默 → 记日志 → 通知）。文件纳入 git，改坏了能回滚。再留一条"心跳自检"：让 Agent 偶尔确认自己的工具可用、状态文件没写坏——值班员也得确认自己没睡着。

## 总结

HEARTBEAT.md 的价值不在"让 Agent 更勤快"，而在让它学会克制：低频醒来、快速判断、多数沉默、异常才出声。管住这四点，它才是一个安静的值班员，而不是一个每小时骚扰你的群发机器人。
