## 背景

OpenClaw 的主会话本质是一条持续追加的上下文流：用户指令、模型回复、每一次工具调用的输出，默认都进同一个 session。日常问答没问题，但任务一旦变“重”——批量抓网页、跑长脚本、反复试错调试——上下文就会被中间产物迅速填满。

## 问题

一个典型场景：让主 agent 依次抓 20 个页面做汇总。每页正文动辄几千 token，全部落在主会话里，结果是上下文成本暴涨、模型被无关细节干扰、很快触发压缩（compaction），早期的重要指令反而被压掉。调试场景同理，试错留下的垃圾信息会一直跟着主会话走。

核心矛盾一句话：主会话的上下文预算是稀缺资源，而重任务的中间产物天然是“脏”的。

## 做法

OpenClaw 提供了会话级隔离：通过 `sessions_spawn` 派生子 agent，它拥有自己独立的 session 文件和上下文窗口。实践中我把它拆成五步：

1. **写自包含任务书**。spawn 时把目标、输入、约束、输出格式一次性写进 prompt。子 agent 不需要、也不应该回头找主会话要信息。
2. **脏活全在子会话**。抓取、重试、报错、中间笔记，全部留在子 agent 自己的 session 里，主会话完全看不到这些过程。
3. **只回传结论**。任务书里明确要求“只返回 200 字以内摘要，或结构化 JSON”，主会话拿到的就是干净结果。
4. **明细落盘**。让子 agent 把完整明细写到文件，主会话只持有路径，需要时再读。本质是用磁盘换上下文。
5. **生命周期管理**。`sessions_list` 查看在跑的会话，需要续聊用 `sessions_send`，收尾用 `sessions_kill` 清掉。

## 踩坑点

- **任务书不自包含**：子 agent 缺上下文，反复向主会话追问——污染没有消失，只是换了方向。
- **子 agent 回传全文**：隔离形同虚设，膨胀的上下文从另一个入口进来了。回传格式必须在 spawn 时就锁死。
- **并发不设限**：一口气 spawn 十个子 agent，容易撞 rate limit，gateway 压力也大。重任务建议串行，或限制在 2~3 个并发。
- **长任务的子会话自己也会膨胀**：超长任务让子 agent 分段工作、每段及时收口，别指望一个子会话扛到底。
- **误把隔离当沙箱**：子 agent 继承主 agent 的工具与权限配置，隔离的是上下文，不是安全边界。危险操作照样要在工具配置里管住。

## 可复用建议

- 沉淀一份 spawn 任务书模板：目标 / 输入 / 约束 / 输出格式 / 停止条件，五要素齐了再派发。
- 团队内形成约定：一切“重上下文”的探索性任务，默认进子会话，不进主会话。
- 产出物优先落盘，主会话只持引用，把上下文留给决策。
- 定期 `sessions_list` 清理僵尸会话；审计需求用 `sessions_history` 抽查子会话，而不是让主会话亲历全程。

## 总结

Session 隔离的本质是上下文预算管理：主会话留给决策、状态和用户对话，探索成本交给子 agent 消化。让脏活有地方脏，让干净的东西保持干净——长任务的稳定性、成本和可控性都会明显改善。
