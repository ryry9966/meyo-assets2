## 背景

Agent 平时是被动响应的，但自动化场景要求它"自己醒"：定时汇总、跟进任务、监控变化。OpenClaw 的 heartbeat 就是为此设计的周期性自唤醒机制——到点给 agent 一个轻量 prompt，由它判断这次要不要干活。听起来简单，但"多久醒一次、醒来干什么"决定了整套自动化的成本和时效。

## 问题

两条路线各有硬伤：

- **轮询（定时 heartbeat）**：实现零成本，不依赖任何外部设施。但间隔难定——5 分钟一次，一天 288 次唤醒，绝大多数是空转，token 白烧；拉到 1 小时一次，时效又跟不上。
- **推送（事件驱动）**：webhook 或消息队列在事件发生时直接触发 agent，时效好、无空转。但你要自己维护接收端，还要处理重试、幂等、乱序，本地环境还可能根本收不到。

单一方案都不理想，纠结间隔参数是死路。

## 做法：轮询兜底 + 推送加速

1. **给 heartbeat 重新定位**：它是兜底巡检，不是主通道。间隔 15–30 分钟起步，加 ±10% jitter，避免多实例同拍。
2. **heartbeat 保持极轻**：prompt 只让它检查待办标记，输出"做/不做"，不做完整任务。空转成本要低到可以忽略。
3. **时效敏感的事件走推送**：webhook 收到 → 写队列 → 触发 agent。用 MCP 工具包一层接收器即可，不必改内核。
4. **推送只发信号**：不带完整上下文，agent 醒来后自己拉详情，避免 payload 膨胀和注入面扩大。
5. **幂等兜底**：每个事件带 `event_id`，agent 侧持久化记录已处理 ID，at-least-once 投递下防重复执行。
6. **静默时段**：夜间 heartbeat 降频，低优先级推送攒到下个窗口统一处理。

## 踩坑点

- **heartbeat 里塞重任务**：一次巡检跑 5 分钟、烧掉大量 token，还要防重入。heartbeat 只做判断，任务主体单独执行并带超时。
- **伪推送**：内网部署收不到 webhook，没有公网可达的接收端（或内网穿透），推送通道等于不存在。
- **重复执行**：队列重试叠加 agent 重启，同一事件跑了两遍。去重必须落在持久层，放内存迟早出事。
- **心跳风暴**：多 agent、多渠道各配各的间隔，叠加后唤醒频率失控。间隔和 jitter 统一在配置层管。

## 可复用建议

- **选型判据**：延迟容忍大于一个心跳周期 → 轮询足够；秒级时效 → 必须推送；两者兼有 → 混合，别犹豫。
- **成本公式**：heartbeat 成本 ≈ 频率 × 单次空转成本。把单次空转压到最低，比反复调频率划算得多。
- **留决策日志**：每次唤醒记录"醒/没醒/为什么"，调间隔时全靠它说话，不靠感觉。

## 总结

轮询买到的是简单可靠，推送买到的是时效和成本，heartbeat 的角色是兜底而非主力。先用最便宜的 heartbeat 跑起来，等真实事件源出现，再逐个加推送通道——这是这个问题的性价比最优路径。
