## 背景

OpenClaw 的 agent 有一套基于工作区文件的 memory 体系：`memory/YYYY-MM-DD.md` 记日常笔记，`memory_recall` 负责在历史记忆里检索，默认实现是全文搜索（ripgrep 风格的关键词匹配）。社区里隔三差五有人问：要不要上 embedding 做语义检索？我在自己的真实记忆库上把两条路都跑了一遍，记录如下。

## 问题

全文搜索的短板很明显：你问“上次数据库超时怎么解决的”，记忆里写的是“PostgreSQL 连接池耗尽，调大 max_connections”——关键词对不上，直接 miss。语义搜索理论上能兜住这种措辞差异，但代价是 embedding 模型、向量索引、重索引维护一整套复杂度。值不值，得看数据。

## 做法

1. **固定评测集**：从记忆库里挑 30 条真实问题（都是当时确实问过 agent 的），人工标注对应的文件和行号。
2. **基线**：默认全文搜索，top-5。命中 17/30（57%），miss 的几乎全是“口语描述 vs 书面记录”的措辞差异。
3. **语义版**：bge-m3 本地 embedding + sqlite-vec，按段落切块、保留日期路径，top-5。命中 23/30（77%）。
4. **关键一步**：给全文搜索加“查询改写”——让 agent 调用 recall 前先把问题拆成 3~5 组关键词变体（同义词、英文术语、项目代号），逐个搜索后合并。命中 27/30（90%），反超纯语义。
5. **混合**：全文 + 语义用 RRF（排名融合）合并，30/30，但只比改写版多 1 条。

## 踩坑点

- **语义搜索的“相关”很廉价**：它经常返回一堆看起来相关、实际没用的段落，白白占用上下文窗口，agent 反而被带偏。全文命中虽少，但条条有用。
- **切块会毁掉上下文**：daily note 的一段话脱离日期就没意义，chunk 元数据里必须带文件路径和日期。
- **中文 embedding 模型差异大**：随手拿英文模型跑，中文查询效果崩掉，多语模型（如 bge-m3）是底线。
- **索引会过期**：记忆文件每天在追加，向量库要监听文件变化重建索引，漏了这步就会出现“明明记过却搜不到”。
- **两套分数不可直接比**：做融合时别比较 score，用排名（RRF）。

## 可复用建议

- 记忆库在几百条以内：老实用**全文搜索 + agent 查询改写**。零依赖、行为可控、命中精准——LLM 本身就是最好的语义层。
- 记忆库变大、或中英混杂严重：上**混合检索**（全文 + 向量 + RRF），语义当兜底，别当主力。
- 无论哪种方案，返回结果务必带**文件路径和行号**，让 agent 能用 read 工具读原文，而不是只喂 chunk。
- 上线前先造 20~30 条自己的评测集，别信 demo 和别人的结论。

## 总结

语义搜索不是银弹，全文搜索也不是古董。在 agent 场景里，模型自己会改写查询，这让“笨”的关键词匹配效率大增；语义检索更适合在措辞差异大、跨语言时兜底。我的选择：默认全文 + 改写，记忆库规模上来后再混入向量。工具要服务于 agent 的工作流，而不是反过来。
