## 背景

大部分 Agent 的使用模式还是问答式：你提问，它回答。但对个人自动化场景来说，真正省时间的往往是反过来的——你还没开口，它已经把该查的查了、该提醒的提醒了。OpenClaw 生态里其实已经有做这件事的骨架：heartbeat 提供周期性检查点，cron 承担固定时刻任务，MCP 让 Agent 能实时读到外部状态。缺的不是能力，而是一套克制的工程方案。

## 问题

最容易踩的坑，是把"主动"理解成"每五分钟把所有东西查一遍再汇报"。跑两周通常是三种结局：通知噪音让人直接静音、token 账单翻倍、或者一次未经确认的自动操作惹麻烦。核心难点不在"执行"，而在"决定什么时候值得打扰你"。

## 做法

我把主动能力拆成三层，每层单独可测：

**1. 感知层：分清触发源类型**

- 定时触发：固定节奏的检查走 cron，比如每天早上汇总日历和天气；
- 状态变更触发：靠外部事件推送（webhook 转发、MCP 工具返回 diff），比如监控指标越线、仓库有新 PR；
- 阈值触发：数值类判断尽量在工具侧先算好，只把结论给模型。

**2. 决策层：把 policy 写进 HEARTBEAT.md**

心跳里不放"帮我看看有什么事"，而是放明确的检查清单，每条包含三要素：数据来源（用哪个 MCP 工具）、判断条件、命中后的动作等级。间隔建议拉长到 30 分钟以上，高频检查交给事件推送，心跳只做兜底扫描。

**3. 执行层：动作分级**

- P0：立即推送 IM（服务挂了、账单异常）；
- P1：进每日摘要，不打扰；
- P2：只写本地日志，周报复盘；
- 一切会改变外部状态的动作（替你发消息、删文件、下单），一律先进确认队列，拿到人工批准再执行。

## 踩坑点

- **通知疲劳**：同一事件反复报。加去重窗口：同一 key 在 N 小时内只报一次，后续合并进摘要。
- **心跳 token 爆炸**：心跳每次带着全量上下文跑。清单保持极简，判断类工作用便宜模型做 triage，只有命中才升级到主模型。
- **幻觉状态**：模型凭上次对话记忆判断"应该没问题"。policy 里要写死：判断前必须实际调用工具取实时数据，拿不到就按"未知"上报，不许猜。
- **自触发循环**：Agent 自己发出的消息回到频道，又触发自己处理。在事件入口按来源过滤掉自己产生的消息。
- **时区问题**：cron 跑在服务器上默认 UTC，"每天早上九点"发成了下午五点。任务里显式写时区。

## 可复用建议

1. **把"观察"和"打扰"分开**。99% 的观察结果应该进摘要和日志，只有真正的异常才值得一条即时消息。
2. **规则小而独立**。每条主动规则像一段代码：单一职责、可单独禁用、数据来源写清楚。别写一条"什么都查"的大规则。
3. **留审计日志**。每次主动动作记录触发源、判断依据、执行结果，每周复盘误报率，误报多的规则降级或下线。
4. **默认只读**。新接入的 MCP 数据源先跑两周纯观察模式，确认判断准确后再放开执行权限。

## 总结

Proactive 不是让 Agent 更"聪明"，而是给它一套关于"什么时候值得说话"的纪律。触发源分层、policy 写成清单、动作分级加确认门、误报率纳入复盘——这四件事做完，主动式助手才可能长期开着而不被你自己静音。建议从一个最小场景起步：每天早上一条日程摘要，加上服务异常立即报警，跑稳了再往外扩。
