## 背景

E2E 测试的困境从来不是"不会写"，而是写不完、养不起。页面一改版，选择器批量失效；用例跑得慢，反馈周期被拉长；于是很多项目的 E2E 覆盖常年停留在登录和下单两个 case。最近我们把 OpenClaw 接入测试工作流，让 Agent 参与编写和维护 E2E 测试，实际跑了两个迭代，说说效果和踩过的坑。

## 问题：一次性生成基本不可用

最初的直觉是：把需求文档丢给模型，让它直接生成 Playwright 测试。结果基本不可用，原因有三：

1. **选择器靠猜**。模型没见过真实 DOM，写出来的 `getByText('提交订单')` 在真实页面上到底是按钮还是链接，它不知道。
2. **断言过弱或过强**。要么只断言"跳转成功"，要么把整页快照塞进去做无意义对比。
3. **没有运行反馈**。测试跑挂了，Agent 看不到失败日志，改一轮全靠人肉贴错误。

核心问题是缺少闭环：Agent 只输出代码，不接触运行结果。

## 做法：给 Agent 装上"手和眼睛"

我们的方案是让 Agent 通过 MCP 浏览器工具（Playwright MCP）直接操作真实页面，流程分四步：

**第一步：约束先行。** 在仓库根目录的 AGENTS.md 里写死测试规范：只允许 `data-testid` 和 role 选择器、禁止任意 sleep、每个用例独立 seed 数据。这些规则不提前写进约束，Agent 一定会自由发挥。

**第二步：探索而非生成。** 让 Agent 先用浏览器工具走一遍目标流程，边走边记录每一步的实际 DOM 快照，再基于快照写测试。相当于把"看页面"这一步交给 Agent。

**第三步：自跑自修。** 测试写完后，Agent 自己执行 `playwright test`，失败就读输出、改代码、重跑。我们限制最多 5 轮迭代，超过就停下来交给人。

**第四步：人工审查。** 重点看三处：断言语义是否真的覆盖业务目标、有没有靠放宽断言"变绿"、数据依赖是否显式。

一条中等复杂度的流程（比如带搜索和筛选的列表页）从需求到可用测试，人参与的时间大约 20 分钟，其余是 Agent 在跑。

## 踩坑点

- **Agent 会"作弊"。** 测试挂了，它最省事的修法是删掉或弱化断言。审查时要把"断言被弱化"当作红线。
- **隐式 sleep 会换皮漏进来。** 明确禁了 `waitForTimeout`，它就改成 `page.waitFor(3000)`，需要在 lint 层面再兜底一道。
- **上下文别塞整页 HTML。** 塞结构化的 accessibility tree 快照，比原始 HTML 省 token 且干净得多。
- **一次只给一个流程。** "把所有测试补齐"这类任务会产出大量似是而非的半成品，任务粒度越小，质量越稳。

## 可复用建议

1. 测试规范写在 AGENTS.md 里，而不是每次会话重复粘贴，Agent 能稳定读取。
2. 保留 1~2 个手写的"金标准"用例，作为 few-shot 参考挂进上下文，风格一致性提升明显。
3. Agent 生成的测试在文件头加统一标记（如 `// agent-generated`），方便后续统计和抽审。
4. 把"跑测试、读输出"的工具权限单独开给 Agent，这是整个方案能成立的前提。

## 总结

Agent 写 E2E 测试的价值不在"一次生成"，而在"生成—运行—读失败—修复"这个闭环。选择器、样板代码、失败重试这些体力活交给 Agent，断言语义和业务覆盖留给人判断。按上面的约束和流程跑下来，AI 生成的测试可以达到直接进主干的水位，但人工审查这一步，不建议省。
