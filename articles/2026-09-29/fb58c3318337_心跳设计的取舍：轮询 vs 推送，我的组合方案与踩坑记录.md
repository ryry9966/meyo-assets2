## 背景

OpenClaw 的 agent 默认是“被动应答”的：有人说话才干活。但自动化场景里，我们往往需要 agent “常驻”——定期检查待办、盯监控、清理临时文件。这就引入了 heartbeat（心跳）机制：让 agent 每隔一段时间自己醒一次。

实现“常驻”有两条路：**轮询**（agent 定时醒来扫一遍状态）和**推送**（外部事件主动叫醒 agent）。两条路我都跑过一段时间，把取舍记录下来。

## 问题

轮询的痛点很直接：

- 间隔太短，token 消耗和打扰明显上升——大部分心跳其实无事可做
- 间隔太长，实时性崩掉，“几分钟内响应”变成“平均十几分钟”

推送看起来更优雅，但工程上坑不少：

- 事件源不稳定：webhook 服务重启、SSE/WebSocket 断线，推送会静默失效
- agent 正忙时事件到达，要么丢、要么需要排队
- 插件/MCP 生态里并非所有能力都支持主动通知

## 我的做法

最终我采用**“推送为主、轮询兜底”**的组合：

1. **心跳只做检查，不做执行。** HEARTBEAT.md 保持极简，心跳醒来只判断“有没有活儿”，有才派发正式任务。心跳上下文压到最小，无事时输出尽量短。
2. **间隔分级。** 默认 30 分钟一次兜底扫描；对实时性有要求的任务（如监控告警）单独走推送或 cron，不混在统一心跳里。
3. **推送信号落盘。** 事件到达时先写入队列文件（带时间戳和去重键），由心跳或空闲钩子消费。事件不直接触发长任务，避免 agent 重入。
4. **断线自愈靠心跳。** 推送通道挂了，最坏情况是任务延迟到下一次心跳被扫到——这就是兜底的意义。

## 踩坑点

- 心跳 prompt 一开始塞了完整系统提示，每次醒来都是全量上下文，一天下来 token 翻了几倍。后来拆出心跳专用的轻量上下文才压下来。
- 推送去重没做，同一条告警在重试时触发了三次任务。现在所有事件带幂等键，处理结果落盘。
- 笔记本休眠后心跳堆积，醒来瞬间连跑多次。加了“错过的周期直接跳过、只跑最新一次”的逻辑。
- WebSocket 断线没有检测，以为推送在用，实际死了两天，最后靠心跳兜底才发现。

## 可复用建议

- 心跳间隔从 15–30 分钟起步，别一上来就 1 分钟
- 心跳的“无事成本”要趋近于零：轻上下文、短输出
- 推送和心跳不是二选一：推送管实时性，心跳管可靠性
- 事件必须幂等 + 可重放，落盘优先于内存队列
- 给推送通道加健康检查，心跳顺便探活

## 总结

心跳设计的本质不是“轮询 vs 推送”的二选一，而是分层：**推送解决“快”，轮询解决“稳”**。把心跳做便宜、做兜底，把推送做精确、做幂等，agent 的常驻能力才扛得住真实环境的抖动。
