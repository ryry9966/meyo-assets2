用 Claude Code 干活的人，大概率经历过这个名场面：重构进行到第 7 个文件，屏幕上突然弹出 usage limit，正在写入的 diff 停在一半，函数少个右括号，测试全线飘红——你只能眼睁睁看着任务“失血而亡”。最近 36kr 一条热搜把这口恶气出了：Claude Code 更新后，额度耗尽不再在代码中间硬切断，而是先把手头的活干完，再优雅停下。这不只是修了个小 bug，背后是所有 Agent 工具在资源调度上的一堂必修课。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-29/77e445e0ba5cdee6.png)

## 一、先搞清楚：代码是被谁“砍断”的

- Claude Code 的本质是“本地 CLI + 远端模型”组成的 agent loop：规划 → 读文件 → 改代码 → 跑测试 → 提交，每一步都是一次模型调用 + 工具调用（tool call）。
- 每次调用都在实时消耗 token，服务端限流系统同步扣减。当余额触零，API 返回限流错误，CLI 的执行循环立刻 halt——这就是“切断”的技术本质，跟模型“偷懒”没关系。
- Chat 场景被切断无所谓，重发一遍就行；但 agent 的一次任务动辄几十次工具调用、横跨十几分钟到几小时，中断点落在哪全凭运气。
- 举例：跨 14 个文件重命名一个变量，跑到第 7 个文件被切，留下语法不一致的中间态，git diff 一半新一半旧，CI 红到发紫。
- 根因一句话：限流系统和长任务之间，缺一个“事务边界”。

## 二、为什么额度这么不经用：Agentic 时代的算力账本

- Agent 模式对 token 的消耗是数量级放大的：每一步工具调用都要把上下文——系统提示、文件内容、历史操作——重新喂给模型。一句“帮我修个 bug”，实际消耗可能是普通聊天的几十倍。
- 额度有多紧？Anthropic 在 2025 年给订阅加上了“5 小时滚动窗口 + 每周上限”双重限制：Pro 约 40–80 小时 Sonnet/周，Max 5x 约 140–280 小时，Max 20x 约 240–480 小时，更强的 Opus 额度还要再打折。看着挺多，agent 跑起来跟漏斗似的。
- 为什么要限：GPU 推理是实打实的电力和硅片成本。订阅制按“平均用量”定价，而 agent 把重度用户的 p99 用量直接拉爆——总有人拿 200 刀的套餐跑 24 小时自动化农场，成本模型瞬间失真，限流是必然。
- 5 小时窗口的逻辑类似景区限流：从你第一条消息开始计时、滚动重置，防止有人把一周额度压缩到一晚烧完。

## 三、这次到底改了什么：从“硬切断”到“软着陆”

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-29/a246482cbd8302ca.png)

据官方 changelog 和社区反馈，这次更新的关键改动可以概括为“软着陆”四件套：

1. **原子操作保护**：到达限额时，先完成当前正在写入的文件和 edit，把 diff 落完整再停，不再留下半截代码。本质上是把“一次文件写入”当数据库事务（transaction）来做——all or nothing，要么完整落盘，要么不写。
2. **提前预警**：用量到达 50%、90% 等阈值时就开始提示，把“最后一刻背刺”改成“前方施工，请绕行”。
3. **用量可视化**：`/usage` 命令直接查看窗口余量和周额度，告别黑盒猜额度。
4. **停在安全点**：配合 checkpoint 与会话恢复机制，额度恢复后能接着上次继续干，而不是从零开始复述需求。

为什么以前做不到？优雅降级（graceful degradation）需要客户端和服务端协同：计费/限流服务要在硬停止前返回“最后警告”状态，CLI 才知道“写完这个文件再停”。这是纯工程细节，却是那种最容易被产品排期扔到 P2 的活——直到用户骂声盖过新功能，才被捞回 P0。

## 四、不止 Claude Code：所有 Agent 工具的资源调度题

- 同样的矛盾在 Cursor、Copilot 和各家 coding agent 身上都存在：订阅制 vs 按量付费（pay-as-you-go），天然存在“重度用户吃垮成本”的张力。
- 可以预见的设计趋势有三个：
  1. **任务前预算检查**：动手前先估算“这个任务大约要 X token，余额够不够”，不够就提示拆分或换模型。
  2. **自动降级**：临近限额切换到更小更便宜的模型，保住“能干活”，牺牲一点质量——类似流量用尽后的降速不限量。
  3. **Checkpoint & Resume**：长任务持久化中间状态、中断后可续跑，这才是 agent 时代的“断点续传”。
- 一个判断工具成熟度的野路子：别只看 benchmark 跑分，看它怎么对待“没电”这件事。

## 五、3 条实用建议

1. **小步提交，任务原子化**：让 agent 每完成一个小步骤就跑测试 + git commit。任何时刻被切断，你都能 reset 回最近的安全点，损失从“半小时白干”降到“一步重跑”。
2. **看着油表开车**：`/usage` 的 50%、90% 预警别无视；大规模重构这类重活，放在窗口刚重置时启动，别在剩 3% 电量时点“开始”。
3. **订阅 + API 双保险**：deadline 前的关键任务走按量付费 API，日常探索用订阅额度。选工具时，把“限额是否透明、中断是否优雅”列为和模型能力同级的评估项。

冷思考一句：限流本质是算力稀缺下的排队问题，工具能做的只是把“排队”变得体面；真正的解法，永远在你自己拆解任务的能力上。
