## 背景

OpenClaw 的 agent 跑久了，memory 里会积累大量会话摘要、用户偏好、项目笔记。`memory_recall` 的职责就是在每轮新对话中把相关记忆捞出来塞进上下文。捞得好，助手像真的记得你；捞得差，要么答非所问，要么上下文被低质量记忆占满。

我们的场景：一个长期运行的个人助手，memory 约 2 万条记录，单条 50–500 字，中文为主，混不少代码片段和命令。

## 问题

检索层常见两条路线：

- **语义搜索**：embedding + 向量库，靠相似度召回
- **全文搜索**：BM25 / SQLite FTS5，靠关键词匹配

社区里谁也说服不了谁，我干脆做了组对照实验。

## 做法

三套 recall 实现，同一评测集（50 个真实问题 + 人工标注的相关记忆）：

1. **纯语义**：bge-small-zh 向量化，余弦相似度取 top-8
2. **纯全文**：FTS5 + jieba 分词预处理，BM25 取 top-8
3. **混合**：两路各取 top-8，RRF 融合后取 top-6

结果（召回率@8 / 平均延迟）：

| 方案 | 召回率@8 | 平均延迟 |
|---|---|---|
| 纯语义 | 0.74 | 35ms |
| 纯全文 | 0.61 | 12ms |
| 混合 + RRF | 0.86 | 48ms |

几个典型 case 很说明问题：问“上次那个部署脚本怎么写的”，记忆里存的是 `deploy.sh`、`systemctl`，全文搜索关键词对得上，反而比语义好；而“之前聊过的那个类似提醒功能的思路”这种表述模糊的，只有语义能召回。

## 踩坑点

1. **中文分词是全文搜索的命门。** FTS5 默认 tokenizer 对中文基本失效，接上 jieba 后，全文方案召回率才从 0.4 出头拉到 0.61。换分词器要重建索引，别等数据量大了再做。
2. **embedding 模型别贪大。** small 和 large 在评测集上召回率只差 0.03，延迟却差 3 倍。memory_recall 是每轮都调的高频路径，延迟敏感。
3. **混合排序别用简单加权。** 两路分数量纲不同，0.5/0.5 直接加权会互相污染，RRF（倒数排名融合）稳定得多。
4. **记忆要带时间戳参与排序。** 半年前的过时偏好和昨天的决定撞车时，纯相似度分不出先后。
5. **查询本身也要清洗。** 用户一句“帮我看看那个事”，embedding 出来就是一团噪声；加一步 query 改写（让模型先补全指代）效果明显。

## 可复用建议

- 记忆条数 < 1000：别上向量库，FTS5 + 分词足够，简单可靠
- 记忆里专有名词、代码、命令占比高：把全文权重调高
- 用户表述口语化、指代多：语义权重调高，或前置 query 改写
- 拿不准就上混合 + RRF，这是鲁棒性最好的默认解
- 一定要建自己的小评测集，20 条人工标注的问答对比，就能看出方案差异

## 总结

语义和全文不是二选一，而是互补：语义解决“换个说法也能找到”，全文解决“精确词一击命中”。对 memory_recall 这种高频、低延迟要求的组件，混合检索 + 时间衰减 + 自建评测集，是我目前最推荐的组合。先跑通最小混合方案，再按自己数据的分布调权重，比纠结“哪个更好”有价值得多。
