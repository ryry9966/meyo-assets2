## 背景

OpenClaw 每次会话启动时，会把工作区（workspace）里的一组文件注入 agent 上下文，`AGENTS.md` 排在最前面。它长得像 README，但读者不是人，是模型。可以把它理解为入职手册：新同事第一天要读的那份"我们这怎么干活"的文档——目录在哪、常用命令是什么、什么事要问过才能做。

## 问题

没有这份手册时，常见三类症状：

1. **每次会话都靠猜**：路径猜错、启动命令用错、把项目结构重新探索一遍，时间和 token 双重浪费；
2. **行为不稳定**：上一轮口头定下的规矩（回复用中文、提交信息格式、哪些文件别动），下一轮就丢；
3. **边界不清**：agent 分不清哪些可以自动执行、哪些必须先确认，要么过度保守，要么越权操作。

很多人的第一反应是换模型、或把 prompt 写得更长。更便宜的做法，是把稳定的知识落盘到 AGENTS.md。

## 做法

建议按五段写，控制在一屏以内：

```markdown
# 工作区说明
## 目录结构
- notes/   观察记录，随时可写
- scripts/ 运维脚本，改动需说明原因
- archive/ 只读，不要修改

## 常用操作
- 重启网关：openclaw gateway restart
- 查日志：~/.openclaw/logs/

## 约定
- 回复使用中文；代码注释与提交信息用英文
- 写文件前先复述目标路径

## 边界
- 不要改动 config 目录和凭证文件
- 删除操作、对外发送内容，先向我确认

## 升级判断
- 信息不足时列出缺失项再问，不要自行假设
```

写完用一个冷启动会话验证：让 agent 复述"你会怎么完成 X"，看它是否按手册走，而不是按习惯走。

## 踩坑点

- **写成小说**。手册每次会话都注入，150 行以内为宜；规则越密集，单条权重越低。
- **形容词化指令**。"严谨一点""注意安全"没有可执行性，改成具体动作和禁止项。
- **和其他文件打架**。SOUL.md 管人格，MEMORY.md 管状态，AGENTS.md 只管规则与流程。同一件事写在两处且不一致，行为必然漂移。
- **把它当文档库**。插件参数、API 用法应链接到具体文件，手册里只留"去哪查"。
- **写死会过期的内容**。目录改名后手册没跟上，agent 会沿着错误地图走。把 AGENTS.md 纳入 git，改工作区结构时顺手改它。
- **放敏感信息**。密钥、内网地址不落盘。

## 可复用建议

维护节奏建议"事件驱动"：初始只写 20 行骨架，之后 agent 每犯一次值得避免的错，就沉淀为一条规则。三个月后它自然长成贴合你工作流的手册，而不是一份抄来的模板。MCP 和插件同理：在手册里写清"什么场景用哪个工具、失败时回退到什么方案"，比在插件配置里堆注释有效得多。验证手段也固定下来——定期开冷启动会话做抽查，手册 drift 会在第一时间暴露。

## 总结

AGENTS.md 本质是 prompt 形态的配置：小、具体、可版本化、随错误迭代。它不提升模型上限，但能稳定托住下限。对一个每天跑自动化的工作区来说，下限往往比上限更值钱。
