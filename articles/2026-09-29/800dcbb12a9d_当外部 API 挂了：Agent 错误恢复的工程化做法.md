## 背景

跑长任务的 Agent 几乎都绑着一堆外部依赖：LLM 推理接口、搜索、数据库、各类 MCP 工具。链路一长，"某次调用失败"就不再是异常，而是日常。真正的分水岭不在于会不会出错，而在于出错之后 Agent 是恢复、降级，还是原地幻觉一个结果交差。

## 问题：三类典型故障

1. **瞬时故障**：429、503、网关超时，重试通常能好。
2. **持久故障**：key 失效、配额耗尽、接口下线，重试只会浪费 token 和时间。
3. **部分成功**：写操作实际已执行但响应丢失，Agent 误判失败后重复执行。

更隐蔽的是 Agent 层面的反应：拿到原始异常后，模型可能编造"任务已完成"，或者陷入自己发明的重试循环，一晚上烧掉半个月额度。

## 做法

**第一步：错误分类前置到代码层。** 不要把异常原文丢给模型。在工具封装里按状态码分类：429/5xx/超时标记为可重试，401/403/404/422 标记为不可重试，并归一化成结构化返回：

```json
{"ok": false, "error": "upstream_timeout", "retryable": true, "hint": "已自动重试3次"}
```

**第二步：退避重试放在代码里，不放 Agent 循环里。** 指数退避加抖动（jitter），上限 3–5 次，尊重 `Retry-After`。让 LLM 自己"决定重试几次"，等于把稳定性交给采样随机性。

**第三步：加熔断。** 同一工具连续失败 N 次后进入冷却期（如 60 秒），期间直接返回"该工具暂不可用"。熔断粒度按工具划分，不要全局一刀切。

**第四步：给 Agent 诚实的失败信号和降级路径。** 系统 prompt 里明确三选一策略：跳过可选步骤并标注、切换备用源或缓存数据、或携带已有进度询问用户。关键是让它"如实汇报断在哪一步"，而不是笼统报错。

**第五步：断点续跑。** 长任务落盘中间状态（已完成步骤、中间产物），恢复时从断点继续。所有写操作带幂等键，重放不会产生重复副作用。

## 踩坑点

- **对非幂等接口裸重试**：下单、发消息类操作被重复执行。幂等键必须做在客户端。
- **退避无抖动**：多个定时 Agent 同时重试，打到上游形成二次雪崩。
- **工具超时设太长**：一次 120 秒的挂起会卡死整个 Agent 循环，建议 10–30 秒快速失败，再走重试。
- **分不清"服务挂了"和"我的配额用完了"**：前者重试，后者该告警换 key。
- **吞掉错误让模型自己猜**：这是幻觉式成功的最大来源。

## 可复用建议

- 所有 MCP 工具调用走统一的客户端封装：超时、重试、熔断、错误归一化一处搞定。
- 错误 schema 固定四字段：`ok / error_code / retryable / hint`，Agent 的处理逻辑才有章可循。
- 系统 prompt 里加一段固定的失败处理约定，比事后修补稳定得多。
- 对关键依赖做启动前健康检查，失败则降级启动，而不是整个任务直接失败。

## 总结

错误恢复没有魔法，就是分类、退避、熔断、降级、断点这五件朴素的事。重试引擎放在代码层，Agent 层只负责接收诚实信号并做路由决策。把"失败"当成一等公民来设计，Agent 才敢被放进无人值守的场景里跑。
