## 背景

跑过稍长一点的自动化任务的人都有体感：Agent 的大部分失败，不是模型不行，而是外部依赖抖了。LLM 网关限流、MCP 工具背后的第三方 API 超时、Webhook 目标服务 502——这些在高峰期几乎是必然事件。如果错误恢复只靠"让模型再试一次"，任务成功率会很难看，token 账单也会很难看。这篇帖子整理一套实践中沉淀的分层恢复方案，核心思路：把恢复逻辑尽量下沉到工具层，让 Agent 只做少量、有信息支撑的决策。

## 问题：挂法不同，处理不该相同

外部 API 的失败至少分四类，正确动作各不相同：

- **暂时性错误**：429、502/503/504、网络超时，等一等大概率就好；
- **确定性错误**：400、401、404，重试只是浪费配额，需要修参数或换凭证；
- **部分成功**：调用可能已到达对方并产生副作用，只是响应丢了，盲目重试会重复下单、重复发消息；
- **持续不可用**：上游挂几分钟甚至更久，继续重试是给自己挖坑。

Agent 原生行为还有个隐患：LLM 拿到原始报错后，要么死循环重试烧 token，要么自作主张"假装成功"继续往下走——后者比失败更危险。

## 做法：五层防线

**1. 先分类，再重试。** 在工具封装层统一解析状态码和异常类型，打上 `retryable` / `fatal` / `ambiguous` 标签，只有明确可重试的才进重试路径。

**2. 指数退避 + 抖动 + 硬上限。** 退避基数 1s 起、逐次翻倍，加随机抖动避免重试风暴；最多 3~5 次；对方返回 `Retry-After` 时优先遵循它。

**3. 熔断与降级。** 滑动窗口内错误率超阈值就熔断，快速失败，期间切备用供应商或返回缓存的降级结果，并用低频探测请求试探恢复。熔断状态要全局共享，否则并行的多个 Agent run 会各自撞一遍墙。

**4. 幂等与断点。** 所有有副作用的调用带幂等键（业务唯一 ID）；长任务在每个工具调用前落 checkpoint，崩溃后从断点续跑，而不是从头来。

**5. 把错误"翻译"给模型。** 不要把堆栈原样丢给 LLM，给结构化摘要：错误类型、已重试次数、剩余预算、可选动作。同时给 Agent 很小的重试预算（比如 1 次），超出就走暂停任务或人工升级，不让它自由发挥。

## 踩坑点

- **对非幂等操作裸重试**是最贵的坑，重复扣款、重复通知都源于此。先补幂等键，再谈重试。
- **超时两头堵**：太长卡死整个 agent 循环，太短误杀慢但健康的请求。按工具的 P99 延迟定，不要拍脑袋。
- **把"API 错误"和"任务失败"混为一谈**，导致一遇错就放弃整个任务。绝大多数 API 错误只影响单步。
- **失败日志不结构化**，复盘只能靠 grep 猜。每次失败记录：时间、目标、错误码、第几次尝试、最终动作。

## 可复用建议

- 写一个统一的 `resilient_call` 包装器，收敛重试、熔断、超时、幂等逻辑，所有插件工具走它，参数化配置（`max_retries`、`backoff_base`、`timeout_ms`、`breaker_threshold`）。
- 失败路径和成功路径同等对待：失败也要有明确终态（成功 / 降级 / 暂停待人工），不留"悬挂中"。
- 长任务优先设计成"暂停可恢复"，而不是"失败即终止"。

## 总结

错误恢复是系统工程问题，不是提示词问题。核心原则两条：恢复逻辑下沉到工具层，用代码保证确定性；Agent 只拿到精炼后的错误信息和有限决策权。做到这两点，外部 API 挂掉就只是一次普通的延迟，而不是一次任务事故。
