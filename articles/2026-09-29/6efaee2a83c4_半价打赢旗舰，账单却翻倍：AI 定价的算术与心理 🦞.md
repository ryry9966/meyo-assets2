上周深夜，Anthropic 没开发布会、没有预热海报，直接在模型文档里挂出了 Claude Sonnet 5.5：定价约为 Opus 的一半，官方给出的基准成绩却在多项开发者最关心的评测上反超自家旗舰。一觉醒来，Hacker News 和 X 上的工程师分成两派：一派惊叹"性价比怪物来了"，另一派默默晒出本周 API 账单，单价降了，总花费反而涨了。三件事放在一起，恰好是一堂完整的 AI 经济学课：发布节奏、能力下沉、成本反弹。

## 一、"深夜空降"：大模型发布正在变成游戏式更新

- **没有发布会的发布。** 过去旗舰模型登场要有 keynote、有 demo 视频、有媒体通稿；现在越来越多是"凌晨改文档、changelog 一行、社区自己测"。节奏更像游戏热更新，而不是软件大版本。
- **为什么变快了。** 模型迭代周期从"年"压缩到"月"，训练—评测—上线的 pipeline 高度自动化。对目标用户（开发者）来说，发布会营销的边际价值在下降，他们只看两样东西：公开 benchmark 和自己业务数据上跑出来的 eval。
- **Drop 文化的来源。** 这个打法借鉴了音乐行业的"surprise drop"：不预告、直接上，靠社区自传播制造讨论度。OpenAI 的 o 系列小版本、Google 的 Gemini 中间版本都出现过类似节奏。
- **对工程师的实际含义：** 模型会越来越像"可替换的依赖"。今天写死 `model = "claude-opus-4"`，明天深夜就有人换成了更快更便宜的那个。代码里的模型名，最好当成配置而不是常量。

## 二、"一半价格击败 Opus"：能力下沉是怎么发生的

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-29/472e6c47cc2478f9.png)

大厂的产品分层一直很清楚：**旗舰（Opus 系）**负责最难的任务，**中杯（Sonnet 系）**是干活的工作马，**小杯（Haiku 系）**处理高频轻任务。中杯反超旗舰，听起来违反直觉，其实有三条成熟路径：

1. **训练配方下放。** 旗舰先验证过的 RL 训练管线、合成数据配方、后训练策略，会在下个周期搬进中杯。旗舰不只是产品，还是整条产线的试验田。
2. **推理端优化。** 蒸馏、量化、投机解码这些工程手段，能让"相同参数量"打出更多有效算力。中杯模型晚发布几个月，天然吃到这批优化红利。
3. **评测针对性优化。** SWE-bench、agentic 工具调用这类开发者最关注的评测，恰好是中杯模型的优化重点。评测分数上涨，一部分是能力提升，一部分是"考前刷题"。

冷静看，"击败"通常指特定评测集上的平均分或 pass@1。在长上下文稳定性、极端复杂推理、罕见指令遵循这些维度上，旗舰一般仍有余量。榜单分数是"平均海拔"，你的任务是"具体山峰"——海拔高，不代表每一座峰都好爬。

## 三、账单为什么暴涨：Jevons 悖论 × Agent 的乘法效应

单价腰斩、总账单翻倍，这不是玄学，是 160 年前就有人描述过的现象。

- **Jevons 悖论。** 1865 年，经济学家 William Stanley Jevons 在《煤炭问题》里发现：蒸汽机效率提高后，煤的总消耗不降反升，因为效率提升让更多场景"用得起"了。Token 是同一种商品：单价降一半，原本"不敢让模型干"的活全涌进来。
- **算一笔简化账。** 假设输入价格从 $6/M tokens 降到 $3/M：
  1. 原来人工做的代码审查、文档总结全交给模型，调用次数 ×3；
  2. Agent 工作流上线：一次编码任务要走"规划 → 读文件 → 改代码 → 跑测试 → 修 bug"的循环，20+ 次调用，每次都携带完整上下文，单次 token 消耗 ×2；
  3. 结果：总 token 消耗 ×6，总账单 = 6 × 0.5 = **3 倍于之前**。
- **Agent 是天然的 token 放大器。** 循环里每一步都在重读上下文；开启 extended thinking 后，那些"看不见的思考 token"也按输出计费。单价降得越狠，大家越敢开循环，放大效应越明显。
- **这不是新故事。** 云计算按小时计费比物理机便宜，结果是总 IT 开支上涨；流量资费下降，结果是人均月流量从几百 MB 涨到几十 GB。价格弹性一直都在。

## 四、把账单管住：三个立刻能做的工程动作

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-29/c9d78bbfbfb5879b.png)

1. **模型路由（Model Routing）。** 按任务难度分流：分类、抽取、格式转换交给小杯；日常编码和总结交给中杯；架构设计、疑难 bug 才动用旗舰。实现可以很朴素，一个按任务类型分流的 router 函数，或者"先便宜模型试、置信度低再升级"的级联策略。
2. **用满 caching 和 batch。** Prompt caching 对固定的 system prompt、长文档前缀极其有效，缓存命中可省 50%~90% 的输入费用；Batch API 用一半价格换几小时延迟，离线批处理首选。这两个开关不打开，等于白送钱。
3. **建立成本观测。** 给每个 feature 打 tag，按"每任务 token 与成本"记账，而不是只看月度总账单；Agent 循环加 max steps / max tokens 护栏；预算触线告警。没有观测就没有优化，账单端的 SRE 和服务端的 SRE 同等重要。

## 冷思考：三条带走

1. **榜单看个位数差距就当"打平"。** 真正该投入的是用自己业务数据建的 eval 集——在你的数据上测出来的排名，才决定你的选型。
2. **单价下降 ≠ 总成本下降。** 把"每任务成本"提升到与延迟、准确率同级的优化指标，写进监控面板，而不是月底看到账单才发现。
3. **把模型名做成配置。** 深夜空降的下一个模型，可能两周后就到；能不能一小时完成切换，取决于你今天是否把模型从代码常量里抽出来。

模型可以打五折，你的 token 永远原价。
