## 背景

单个 Agent 处理复杂任务有个天然瓶颈：所有工具调用、中间结果、报错信息都堆在同一个上下文里。跑上半小时，上下文塞满日志和半成品输出，模型开始"失忆"，决策质量肉眼可见地下降。更糟的是所有步骤串行执行，明明三个独立的调研任务，还得排队跑。

subagent 编排就是针对这两个问题的：主 Agent 只负责拆解和汇总，脏活分给若干带独立上下文的子 Agent 并行处理。

## 什么样的任务适合拆

不是所有任务都该并行，实践中我总结了三个判断标准：

1. **子任务之间无共享写目标**。三个子 Agent 同时改同一个文件，等于给自己埋雷。只读调研、分别生成不同模块、批量处理不同数据源，这些才是安全区。
2. **单步耗时长**。比如调用外部 MCP 工具做抓取、跑代码测试，并行收益才明显。
3. **结果可以压缩汇总**。子 Agent 干了 50 步，最终只需回传 200 字结论。

## 具体做法

以常见的 fan-out / fan-in 模式为例：

**第一步：主 Agent 拆任务。** 每个子 Agent 的任务描述必须自包含——它看不到主 Agent 的上下文。我的模板是：目标、输入（具体路径/URL/参数）、允许使用的工具范围、输出格式（写到哪里、什么结构）、超时和失败时的行为。

**第二步：限制并发数。** 别一口气开十几个，API 限流、MCP server 连接数、机器负载都会先爆。经验值是 3-5 个并发，稳定后再调。

**第三步：结果落盘，不靠回传。** 让每个子 Agent 把产出写到约定路径（如 `workspace/results/task-01.md`），回传只带一行状态和文件路径，主 Agent 最后统一读取汇总。这一条是控制上下文膨胀的关键。

**第四步：容错收口。** 单个子 Agent 失败不该拖垮整批。汇总时逐个检查状态，失败的单独重试或降级，而不是整批重来。

## 踩坑记录

- **任务描述不够自包含**。子 Agent 上来就问"那个文件在哪"，一轮交互浪费两次调用。派发前把必要的上下文细节手动搬进去。
- **共享文件写入冲突**。两个子 Agent 同时 append 同一个文件，内容交错。解法：各自独立输出，汇总阶段再合并。
- **子 Agent 输出过长**。让它"详细报告"就是灾难，回传轻松吃掉几千 token。明确要求"结论 + 路径"格式。
- **隐藏依赖没拆出来**。"调研 A 和 B 然后对比"，A、B 可以并行，但"对比"必须等两者完成。拆之前先画依赖关系，别想当然全并行。
- **忘了设超时**。一个子 Agent 卡在无限重试的 MCP 调用上，整个批次干等。每个任务都要带超时和最大重试次数。

## 可复用建议

- 把任务描述做成模板沉淀下来，比每次现写稳定得多。
- 给子 Agent 的工具权限做减法：只读任务就别给写权限，能少一半事故。
- 记录每次编排的并发数、耗时、token 消耗，这是调参依据，凭感觉不靠谱。
- 先用两个子 Agent 验证流程，跑通再扩并发。

## 总结

subagent 编排的本质不是"多开几个 AI"，而是把上下文隔离、任务边界、结果汇总这三件事做扎实。并行只是手段，可控才是目的。从小的 fan-out 开始，把任务模板和落盘规范沉淀下来，这套模式在调研、批量处理、多模块生成这类场景里，收益非常稳定。
