## 背景

用 Agent 做自动化跑久之后会遇到两个瓶颈：一是主会话上下文越滚越大，塞满了工具输出和中间结果，模型开始“失忆”；二是任务天然串行，调研五个候选方案就得等五轮。OpenClaw 的 subagent 机制正好对准这两个问题：主 Agent 通过 `sessions_spawn` 起一个隔离会话，给一段自包含的任务描述，子会话独立跑完后把结果送回来，主会话的上下文基本不受污染。

## 什么时候值得拆

实践中我总结三条判断标准，全满足才拆：

- **任务可独立**：比如并行调研多个库、批量处理一批文件、对多个数据源分别做摘要；
- **读多写少**：以检索、分析、生成草稿为主；
- **结果可压缩**：最终能收敛成一段短摘要或一个产物文件。

强顺序依赖、需要和用户反复确认的任务，不要拆，拆了反而增加协调成本。

## 具体做法

1. **单一目标 prompt**：给 subagent 的任务描述必须自包含——目标、输入位置、输出格式、边界条件，一条不落。它看不到主对话，你以为它知道的它都不知道。
2. **收窄工具面**：在 agents 配置里限制 subagent 可用工具，只读任务就只给读取类工具，不给写权限。
3. **控制并发**：2~4 个起步，观察限流和机器负载再加。每个 subagent 都是一个完整会话，token 消耗是实打实的。
4. **硬约束回传格式**：要求返回不超过 200 字的结论加产物路径，否则子会话的长输出只是把污染搬了个地方。
5. **主 Agent 只做汇总和决策**：比较各路结果、挑方案、决定下一步，不做具体执行。

## 踩坑点

- **并行写同一文件必冲突**。我们的规矩是：读可以并行，写要么串行，要么启动前按文件明确分区。
- **回传太长**。第一版没限制格式，三个 subagent 各回传几千字，主会话上下文直接爆炸，得不偿失。
- **失败静默**。subagent 中途出错但返回了半截结果，主 Agent 当成正常结论用了。现在强制要求显式返回失败原因，主 Agent 汇总前做校验。
- **递归 spawn**。subagent 又去开 subagent，任务树失控。直接禁止，编排权只留在主会话。
- **并发开太高**。一次开了 8 个，撞上 API 限流，全员重试，比串行还慢。

## 可复用建议

- **一个 subagent 一个交付物**，目标模糊的任务宁可不拆；
- **先串行跑通再并行**，先把单任务 prompt 调稳，再复制成多路；
- **spawn prompt 模板化**，把验证过好用的任务描述存成模板，随取随用；
- **留痕**，记录每次 spawn 的 prompt 和回传结果，出问题时能复盘是拆分错了还是执行错了。

## 总结

Subagent 编排的价值不在“多个 AI 很酷”，而在上下文管理和失败隔离：主会话保持干净，单路失败不影响全局。并发数克制、回传格式硬约束、写操作谨慎，这三条守住，并行编排才会真正提效而不是制造新问题。
