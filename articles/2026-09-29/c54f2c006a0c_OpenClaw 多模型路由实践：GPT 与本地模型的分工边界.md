## 背景

跑 OpenClaw 一段时间后会发现，一个看似简单的 agent 任务背后其实是几十次模型调用：任务拆解、工具参数生成、MCP 结果摘要、异常重试……全部压在一个模型上，要么账单难看，要么本地小模型在关键步骤掉链子。多模型路由要解决的就是“每一步该用哪个模型”。

## 问题

两种常见极端：

- **全走云端强模型（GPT 这一档）**：质量稳，但一次长任务几百次调用，成本和延迟都受不了，而且代码片段、内部文档这类敏感上下文全出了网。
- **全走本地模型**：隐私和成本好，但规划、跨工具编排这类步骤错误率明显上升，而 agent 链路里的错误会被下游放大。

## 做法

我目前实测比较稳的分层策略：

1. **按步骤类型分层**，而不是按“信不信得过本地模型”拍脑袋：
   - 规划、多工具编排、模糊指令理解 → 云端强模型
   - 结构化输出（工具参数 JSON）、文本抽取、摘要、格式转换、简单 RAG 问答 → 本地模型
2. **在路由配置里给每个 agent 声明 primary / fallback 链**：本地为主、云端兜底，触发条件写死，例如“schema 校验连续失败 2 次”或“步骤类型标记为 planning”。
3. **把结构化校验当路由闸门**：本地模型吐出的 JSON 先过 schema 校验加轻量修复，失败自动升级到云端，不要靠人肉盯日志发现。

## 踩坑点

- **本地模型对 prompt 格式敏感得多**。GPT 能容忍的冗长工具定义，本地 7B/14B 直接输出跑偏。给本地模型的 prompt 要单独裁剪：工具描述砍半，few-shot 只留一个最典型的。
- **升级时上下文超限**。两边 tokenizer 和窗口大小不同，把本地失败时的完整上下文原样扔给云端，长会话会炸，升级前先裁剪。
- **重试风暴**。路由写成“失败→换模型→重试”但没上限，一次 MCP 工具故障能把云端配额打穿。每个任务的升级次数必须是硬限制。
- **别只看最终结果评估路由**。中间步骤用错模型但结果碰巧对了，问题会被掩盖。日志里记下每步的模型选择和耗时，定期回放。

## 可复用建议

- 路由维度用“任务类型 + 输出是否结构化”，比对着能力榜单选模型好维护得多。
- 敏感上下文（代码、内部文档）默认绑本地，这是硬约束，不是优化项。
- 用自己的 trace 做评测，公开榜单分数和你的实际工作负载相关性很低。
- 先两档跑起来，规则数量控制住；三层以上没有日志数据支撑就是自找麻烦。

## 总结

多模型路由不是省钱技巧，而是把 agent 的不确定性按步骤拆开管理。先用最粗的两层——云端负责规划、本地负责执行——把校验闸门和升级预算做扎实，再基于自己的调用日志逐步收紧规则。OpenClaw 这类框架的价值就在于让这些决策显式化：路由规则写得越清楚，agent 的行为就越可预测。
