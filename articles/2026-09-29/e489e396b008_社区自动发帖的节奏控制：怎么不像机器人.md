# 背景

用 OpenClaw 挂一个常驻 Agent，配合 MCP 工具定时往社区发摘要、周报、精华整理，是很常见的自动化玩法。跑起来不难，难的是跑得"像个人"。第一版几乎都长一个样：cron 每小时整点触发，内容模板固定，凌晨三点照发不误。结果要么被频道管理员当垃圾信息处理，要么被用户直接静音。

# 问题

先说清楚目标：所谓"不像机器人"，不是伪装身份——发帖身份该声明还是要声明——而是**不制造打扰**。机器人感的来源其实很具体：

- 整点触发，间隔恒定 60 分钟
- 活跃低谷期（深夜）照常发帖
- 每次措辞、排版完全一致
- 停机恢复后把积压内容一口气全发出去

# 做法

我把节奏控制拆成四层，每层独立可关：

1. **决策层（要不要发）**：先判断内容价值。没有新内容的周期直接跳过，这一步能砍掉大部分无效发帖。
2. **排期层（什么时候发）**：从社区历史消息量统计出一条活跃曲线，按分布采样发帖时刻，而不是取固定时间点，再叠加 ±10~30 分钟抖动。
3. **闸门层（允许不允许）**：安静时段（按社区本地时区）、每日上限、最小间隔、近 20 条内容哈希去重，任一命中就丢弃并记日志。
4. **执行层**：失败不立刻重试，走指数退避，当天最多重试 2 次。

状态全部落盘到一个 JSON 文件：上次发帖时间、当日计数、近期内容哈希。进程重启不丢上下文。核心配置大致长这样：

```yaml
quiet_hours: "00:00-08:00"
daily_cap: 4
min_gap_min: 50
jitter_min: [10, 30]
schedule: sample_from_activity_histogram
shadow_mode: true
```

# 踩坑点

- **抖动用了均匀分布**：一周日志拉出来，发帖时刻在窗口里呈现明显的"平顶"，人眼都能看出规律。改成从活跃直方图采样后自然多了。
- **时区**：服务器是 UTC，社区在东八区，第一版的安静时段等于形同虚设。所有时间判断统一转成社区本地时区。
- **崩溃恢复**：积压队列千万别补发。超过一定年龄的内容直接丢弃——人类不会发六小时前的"新闻"。
- **随机种子写死在配置里**：每天抖动模式一样，等于没抖。
- **重试没设上限**：webhook 报错触发循环，两分钟发了十几条，这是我们最像机器人的一次事故。

# 可复用建议

- 先跑 **shadow 模式**一到两周：所有"将发内容"只写日志不真发，人工 review 节奏和内容后再放开。
- 每条决策都记录 skip 原因，每周复盘一次 skip 率；比例异常说明闸门太紧，或内容源本身有问题。
- 留一个手动 pause 开关，出事故能一键停。
- 内容端也做变体：开头句式、段落组织准备 3~5 套轮换。但别追求"骗过检测"，目标是读者体验——**如果一个人类会在那个时间点发那条内容，才发**。
- 最有效的"不像机器人"是少发。信号密度低的周期，跳过就是最优解。

# 总结

节奏控制本质是四件事：要不要发（决策）、什么时候发（排期）、多久发一次（节流）、每次长什么样（变化）。调度交给代码，内容判断保留人的 review，身份保持透明。做到这几点，自动化发帖就能长期安静地跑下去，而不是三天后被管理员请出去。
