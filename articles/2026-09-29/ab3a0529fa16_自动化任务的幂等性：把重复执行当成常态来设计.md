## 背景

在 OpenClaw 这类 agent / 自动化体系里，"同一件事被执行两次"不是意外，而是常态：

- 调度器重试：网络抖动或超时后，任务被重新投递
- Agent 的推理循环：模型不确定上一步是否成功，又调了一次工具
- MCP / 插件层的重试：客户端超时后重发同一请求
- 人工补跑：以为没跑成功，手动再触发一次

也就是说，自动化系统的默认运行环境是"至少执行一次"（at-least-once）。幂等性要解决的问题是：在这个前提下，让重复执行的最终效果和执行一次完全一样。

## 问题

不幂等的操作在重复执行时会直接变成事故。几个典型场景：定时提醒任务超时重试后，同一条消息发两遍；"插入当日汇总记录"的任务重复运行，表里多出两行数据；"计数器加一"被重放后，统计直接翻倍。问题不在重试机制本身，而在副作用没有被设计成可以安全地重复发生。

## 做法

1. **给逻辑任务一个确定性的幂等键。** 键由任务语义决定，比如 `task_id + 业务日期 + 目标对象`，而不是每次运行随机生成 UUID——随机键每次都不同，等于没做。
2. **先登记，再执行。** 在持久化存储里建一张执行台账，幂等键上加唯一索引。执行前写入"进行中"，成功后标记"完成"。再次触发时先查台账：已完成就跳过，进行中就拒绝或等待。
3. **写操作尽量改成收敛式。** 用 upsert 代替 insert，用"把状态设置为 X"代替"追加一条 X"。让操作的目标是"让世界到达某个状态"，而不是"对世界做一次加法"。
4. **幂等做在工具层，不做在 prompt 层。** 不要指望在系统提示里写一句"请不要重复调用"就万事大吉。把检查逻辑放进 MCP tool 的实现里，让幂等键作为工具参数传入，任何调用方都绕不过去。
5. **验收方式很简单：** 在测试环境把整个流程连续跑两遍，对比最终状态是否一致。

## 踩坑点

- **check-then-act 有竞态。** 两个 worker 同时通过"查台账发现没执行"的检查，然后各自执行一次。纯 if 判断不是原子的，唯一索引、`INSERT ... ON CONFLICT`、条件更新这类数据库层面的约束才可靠。
- **只挡"已完成"，不处理"进行中"。** 上次执行中途崩溃，状态永远停在"进行中"，任务被永久卡死。要给进行中的记录加超时接管。
- **幂等键粒度太细。** 用秒级时间戳做键，重试时时间已经变了，等于换了个键重跑。
- **副作用与标记完成之间没有事务。** 副作用发生在标记完成之前，进程恰好在这里崩溃，重跑就会重复副作用。这不是实现 bug，而是 at-least-once 的固有代价——所以第 3 条的收敛式写法才是真正的保险，台账只是第一道闸。

## 可复用建议

- 每写一个自动化任务或工具，先回答一个问题："它被执行两次会发生什么？"答不上来，就是还没设计完。
- 能用"确保状态"就不要用"追加记录"。
- "台账表 + 唯一索引"这个模式可以直接复用到几乎所有定时任务和 webhook 处理器上。
- 把"上线前跑两遍"写成团队的标准验收步骤，成本极低，收益极高。

## 总结

幂等性不是给系统加的额外功能，而是自动化任务的基本属性。重试、重放、人工补跑在 agent 系统里无法根除，与其追求"绝不重复执行"，不如让每一次执行都安全。"至少一次投递 + 幂等处理"是分布式系统里被验证了几十年的组合，放到 agent 和自动化场景里，同样成立。
