## 背景

刚上手 OpenClaw 的人大多是被动用法：有问题才发消息，agent 答完就安静。但一个常驻在网关里的 agent，完全可以反过来主动找你。OpenClaw 为此留了个不起眼但很实用的口子：heartbeat（心跳）。只要 agent workspace 根目录存在 `HEARTBEAT.md`，网关就会按固定间隔（默认 30 分钟）把文件内容连同当前时间注入提示词，跑一次完整的 agent 循环。无事发生时 agent 回复 `HEARTBEAT_OK`，这次运行的结果被静默吞掉；有事时，它就像你自己发了条消息一样主动推送。默认模板里只有一条"检查有没有没回的消息"，真正的价值要靠你自己写进去。

## 问题

没有心跳机制时的典型痛点：周期性检查（日志、磁盘、待办）靠人脑记，最后都变成"想起来才做"；cron + webhook 能做定时任务，但那是硬编码自动化，缺少判断力——它不会根据上下文决定"这次要不要报、报多少"。心跳补的就是这一环：定时触发，由模型判断做还是沉默。

## 做法

1. 在 workspace 根目录建 `HEARTBEAT.md`，写成机器可判定的检查清单。每条规则三段式：条件 + 动作 + 沉默条件。比如"读 `~/logs/app.log` 末尾 100 行，出现 ERROR 则汇总成一条消息发到 Telegram，否则回复 HEARTBEAT_OK"。
2. 在 `~/.openclaw/openclaw.json` 里调参：

```json
"agents": { "defaults": { "heartbeat": {
  "every": "30m",
  "model": "<便宜模型>",
  "activeHours": { "start": "09:00", "end": "23:00" }
}}}
```

3. 用 `openclaw heartbeat status` 确认在跑，盯紧前几次的运行日志。
4. 每条规则先收紧沉默条件，验证没问题再放开。

## 踩坑点

- **规则太模糊**（"帮我盯着项目"）→ 模型次次 HEARTBEAT_OK，等于没开。检查项必须落到具体路径、命令、文件。
- **规则太宽**（"每小时汇报一次状态"）→ 被 24 小时轰炸。沉默条件和触发条件同等重要。
- **上下文污染**：心跳默认跑在主 session，每次运行的轨迹会进入会话历史。高频心跳 + 长会话会把 context 吃掉，务必配便宜模型并控制频率。
- **成本**：30 分钟一次约 1440 次/月，`activeHours` 能直接砍掉夜间空转。
- **别把 HEARTBEAT.md 当 MEMORY.md 用**。前者是循环指令，后者是长期记忆，混着写会让每次心跳变慢变贵。
- **写操作要克制**：凌晨三点没人盯着，危险动作（重启、删除）只做"提醒"，不做"执行"。

## 可复用建议

- 条目模板：触发条件（可执行检查）+ 输出目标（渠道与格式）+ 沉默条件，三者缺一不可。
- 从 2~3 条规则起步，跑一周再加，别一上来堆十个检查项。
- 多条规则的输出尽量合并成一条消息，别一条规则轰炸一条。
- 调试期把间隔临时调到 2m 观察行为，稳定后调回。
- 想让心跳摘要走独立频道，就单独配 heartbeat 的 `target`；保持默认投递则是"有事才打扰"。
- 排查问题时用 `/heartbeat stop` 暂停、再恢复，能快速判断"是不是心跳干的"。

## 总结

HEARTBEAT.md 的本质是把"定时器 + 判断"交给 agent，而不是写死的 cron。它的价值不在自动化执行——那有很多工具能干——而在自动化决定"要不要做"。写好它的关键不是堆任务，而是替模型把沉默条件想清楚：什么时候该闭嘴，往往比什么时候该说话更难定义。建议从一条日志检查起步，跑通"检查—判断—沉默/上报"这个闭环，再逐步扩大。
