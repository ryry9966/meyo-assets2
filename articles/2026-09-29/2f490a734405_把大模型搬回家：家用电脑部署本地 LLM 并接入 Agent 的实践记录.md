## 背景

玩 Agent 和 MCP 的人迟早会遇到这个场景：任务里全是本地文件、内网服务、家庭自动化设备，每一步都要把上下文送出去调云端 API——隐私、费用、断网可用性都是隐患。于是“在家用电脑上跑一个模型”从玩具需求变成了工程需求。这篇记录我从零到跑通一次真实 Agent 任务链的过程。

## 问题

真正要回答的是三个：

1. 我的机器到底跑得动多大的模型；
2. 小模型的工具调用（function calling）质量够不够撑起一个 Agent 循环；
3. 长循环下延迟和成功率是否可接受。

## 做法

**第一步，摸硬件底线。** 经验值：Q4 量化的 7~8B 模型约需 6GB 显存，14B 约 10~12GB，32B 基本要 24GB 显存或部分卸载到内存。没有独显的机器靠纯 CPU + 内存也能跑 8B，但速度只适合做后台批处理。

**第二步，选运行时。** Ollama 上手最快，llama.cpp 控制粒度最细，LM Studio 适合桌面党。无论选哪个，确认它暴露 OpenAI 兼容接口，这是接 Agent 的前提。

**第三步，选模型。** 优先选原生支持工具调用的指令模型。8B 级别从 Q4_K_M 量化起步，显存富余再上 Q5/Q6，别一开始就盯着最大的参数量。

**第四步，改上下文配置。** 很多运行时默认上下文只有 2~4K，MCP 工具定义加返回结果很容易撑爆。显式把上下文设到 16K~32K，同时确认 KV cache 的显存占用——长上下文会让显存翻倍，这是最常见的“明明放得下却 OOM”的原因。

**第五步，接进 Agent 验收。** 把 base_url 指向 localhost，跑真实的任务链：读本地文件 → 调 MCP 工具 → 汇总输出。别看通用跑分，只记录两个数：单次推理 tokens/s，整条任务链的成功率。

## 踩坑点

- **模型声称支持工具调用，但运行时的聊天模板不匹配**，表现为 Agent 从不触发工具。换运行时或更新模板通常能解决。
- **采样温度过高导致 JSON 参数畸形**，工具调用场景建议 temperature ≤ 0.3，或直接开结构化输出。
- **把部分层卸载到 CPU 后速度掉一个量级**。Agent 循环一次任务要调几十次模型，单次慢 5 秒就是灾难——宁可换小模型。
- **量化低于 Q4 后结构化输出开始崩**，别为了塞进显存无脑压缩。

## 可复用建议

- 先用 8B Q4 打通全链路，再考虑升级模型，顺序别反。
- 本地 + 云端混合路由：简单分类、摘要、格式化交给本地小模型，复杂推理走 API，成本能降一个数量级。
- 锁定模型版本，把模型文件的 hash 记下来，工具调用行为对版本相当敏感。
- 给 Agent 加工具调用日志，出问题时这是唯一的排查依据。

## 总结

家用电脑跑本地模型已经完全可用，但要按工程问题对待：硬件算清楚、上下文配对、用真实任务验收。对 Agent 用户来说，本地模型不是替代云端，而是给整个体系补上“私有、离线、廉价”的那一块。先跑通，再优化，别在选型上过度纠结。
