## 背景

Agent 能调的工具越来越多：MCP server、shell、HTTP、消息推送。能力上去之后，真正难的不是"能不能做"，而是"该不该自己做完"。我自己的 agent 跑了小半年，踩过两类极端：一类是什么都要确认，执行一个三步任务被打断三次，最后我变成无脑点"允许"的橡皮图章；另一类是什么都自己干，某次把测试环境的清理脚本跑到了生产库上。这篇帖把当时梳理权限边界的思路整理出来，供大家参考。

## 问题

权限设计有两个失败方向：

- **问太多**：确认疲劳，人类不再真的审内容，防线形同虚设；
- **干太多**：一次参数幻觉、一条被注入的网页指令，就可能造成不可逆的对外副作用。

核心矛盾在于：确认的价值取决于人是否真的在看，而"看"的成本必须压到足够低。

## 做法：按"可逆性 × 影响范围"分四档

先盘点 agent 能触达的每个工具，按两个维度分类：能不能回滚、出错波及多大。然后落到四档默认策略：

1. **T0 自动执行**：只读操作、沙箱内写文件、dry-run。不问，直接做。
2. **T1 自动 + 留痕**：工作区内的可逆写操作，比如建分支提交、生成草稿。做，但全量记日志，事后可审计。
3. **T2 确认执行**：任何对外副作用——发消息、调第三方 API、删数据、花钱超阈值。必须人工确认。
4. **T3 禁区**：凭据管理、生产数据删除、支付。agent 只生成方案，不执行。

落地时有三个动作，比分类本身更重要：

- **确认内容要"可审"**。不要让 agent 问"我可以继续吗"，而是把将执行的命令、diff、收件人直接摆出来。人审的是内容，不是心情。
- **先产出、后确认**，而不是先确认、后执行。让 agent 把完整计划或补丁生成好，人批一次，再批量执行。
- **确认按单条动作拆分**，拒绝打包。一个批次里混着 T1 和 T3 操作时，必须拆开。

## 踩坑点

- **确认疲劳是最真实的坑**。我曾把一个中风险工具也设成必确认，一周后我开始无脑点允许——防线反而退化了。对策：稳定跑 20 次后降档，出一次事故立即升档。
- **子 agent 和插件会静默继承父级权限**。在插件配置里显式声明自己的工具等级，别默认信任继承链。
- **环境漂移**：开发沙箱的宽松策略被原样带进生产配置。用显式的环境维度字段隔离，不靠约定。
- **提示注入**：agent 读了网页或邮件后"被建议"去调危险工具。分档策略是最后一道闸，注入内容再有说服力也不能跨档。

## 可复用建议

- 一句话原则：**不可逆 + 对外 → 问人；可逆 + 局部 → 自己干**。
- 涉及钱的工具，无论金额多少单独建档，阈值独立配置。
- 允许清单每季度人工过一遍，删掉半年没用过的工具授权。
- 日志里除了"做了什么"，还要记"当时为什么没问"，方便复盘。

## 总结

权限边界不是"要不要人审"的开关，而是一张按可逆性和影响范围划出来的分档表。工程上关键只有三件事：让确认内容真的可审、让自动化真的在跑、让升降档有数据依据。Agent 的自主性应该是挣来的，不是配出来的。
