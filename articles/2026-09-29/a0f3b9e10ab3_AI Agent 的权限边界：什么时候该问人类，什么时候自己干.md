## 背景

OpenClaw 接上 MCP 和插件之后，Agent 能做的事从“聊天”扩展到“动手”：读写文件、跑 shell、调第三方 API、对外发消息，甚至花钱。实践里最常见的两个极端：要么每个动作都停下来问，自动化价值归零；要么全放行，直到某天它改了生产配置、把消息发错了群。

先说结论：这不是“信不信任模型”的问题，而是一个工程问题。

## 问题在哪

很多同学一开始用 prompt 约束行为——“谨慎操作”“重要的事先问我”。这种约束在工具少、任务简单时勉强够用，一旦工具多了、任务链长了就失效：模型对“重要”的判断和你不一致，而且 prompt 约束没有任何强制力。

真正的边界必须落在工具和权限层，而不是提示词层。

## 一个可落地的分级做法

判断标准只有两个维度：**这个动作能不能撤销？出错时波及谁？** 按这两个维度可以分成四级：

- **L0 自动执行**：只读操作。读文件、查询、沙箱里跑 dry-run。这类不用管。
- **L1 自动执行 + 留痕**：工作区内的可逆写。分支上的 git 提交、临时文件、能 revert 的改动。放行，但必须留 diff 和日志。
- **L2 首次确认、模式放行**：装依赖、改配置、连新的外部 endpoint。第一次人工确认，之后同模式自动放行，并定期复查清单。
- **L3 永远问人**：对外发消息、支付、批量删除、动生产环境、碰凭证。没有例外，且提问必须带上下文——改什么、影响谁、怎么回滚，而不是一句“我可以继续吗”。

落地时对应到配置层：MCP 工具按白名单注册，L3 类默认 deny；shell 工具限制在允许的命令模式内；cron 触发的自动化任务比交互式会话再收紧一档，因为没人盯着。

## 踩坑点

1. **确认疲劳**。问得太频繁，人会不读内容直接点确认，这比不设门槛更危险。如果你发现自己在无脑点 yes，说明分级划错了，该把 L2 往 L1 降一档。
2. **批量授权**。一次确认放行 50 个删除操作等于没确认。批量动作要么逐批确认，要么先给完整清单再整体放行。
3. **模糊提问**。Agent 问“是否继续”但不给 diff，人只能靠猜。必须要求它附上计划、影响面、回滚方式。
4. **新工具默认放行**。接入一个新的 MCP server 等于引入第三方代码，默认 deny，审过再加白名单。
5. **混淆“要权限”和“要信息”**。Agent 缺参数时直接问是便宜且应该的，别为了少打扰让它瞎猜默认值。

## 可复用建议

- 从收紧开始，用无事故记录逐步放宽，不要反过来。放宽的依据是执行日志，不是感觉。
- 一切不可逆动作前，先产出可审查的产物：dry-run 输出、diff、预览。没有产物，就没有确认按钮。
- 每周扫一遍自动执行日志，重点看 L1 里有没有“当时觉得可逆、其实并不想要”的动作。
- 提问本身要结构化：动作、对象、影响、回滚四项，缺一项就不该问人。

## 总结

权限边界 = 可逆性 × 影响范围，落点在工具层。该自己干的是只读和可逆的小动作，该问人的是对外、花钱、删数据、动生产。边界会随使用变化，所以要有日志、有复查、有升降档机制。划好这条线，你才真正敢放手用 Agent。
