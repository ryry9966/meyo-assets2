## 背景

大多数人对 AI 助手的使用还停留在“你问我答”：开一个会话，丢一段需求，等结果。但回想真人助理的价值——好助理不是响应快，而是会在你开口之前把事办了：日历冲突提前提醒、CI 挂了主动通知、关键邮件进了及时喊你。

OpenClaw 这类常驻型 agent 框架其实已经把 proactive 的地基打好了：heartbeat 心跳机制、cron 定时任务、webhook/插件事件触发，再配上多渠道推送。问题不在能力，而在于怎么把它用得不烦人。

## 问题

直接把“主动性”打开，通常死在三个地方：

1. **噪音**。agent 每次心跳都汇报点啥，一周后你把它静音，proactive 等于白做。
2. **成本**。心跳间隔设短了，token 消耗线性上涨，大部分 run 是空转。
3. **越权**。主动模式下 agent 自己决定“发消息”“改文件”，一次误操作就把信任花光了。

核心矛盾一句话：**怎么让 agent 有事说事，没事闭嘴。**

## 做法

我把主动能力拆成四层，逐层加：

**1. 心跳层：定时巡检。** 开启 heartbeat，间隔先设 1 小时（活跃时段即可）。把巡检事项写进 HEARTBEAT.md，每条必须是可判定的条件，比如“24 小时内日历有两个冲突会议”“CI 主干连续两次失败”。模糊指令如“帮我盯着点”是禁忌。

**2. 判断层：值不值得打断你。** 在心跳指令里显式写一个 checklist：什么情况允许发通知（临近 deadline、错误率超阈值、外部来信待回复），什么情况只写日志不吭声。明确告诉它“no news is good news，静默是合法输出”。

**3. 执行层：隔离 + 白名单。** 主动 run 用独立 session，不污染主会话上下文。只读检查（查邮件、看 CI、读日志）直接放行；写操作（代你回消息、提交代码、部署）先进确认队列，等你在场时批量批。

**4. 事件层：时效性强的事不走心跳。** git push、监控告警这类能拿到 webhook 的事件，用插件直接触发一次 agent run，别等下一个心跳。原则很简单：**心跳管周期巡检，事件管突发。**

## 踩坑点

- **心跳间隔拍脑袋。** 我从 10 分钟起步，两天后 token 账单教我做人。1 小时起步，观察空转率再调。
- **检查项写得不可判定。** “关注一下仓库动态”这种条目，agent 每次都能编出点汇报内容。每条必须带阈值或明确条件。
- **主动会话污染主上下文。** 早期我把心跳和日常对话跑在同一个 session，很快上下文里全是巡检垃圾。必须隔离，只把结论注入通知渠道。
- **静默策略没写清楚。** 不明确说“可以不汇报”，agent 会出于“展示工作量”的本能硬找话说。
- **不可逆操作没有闸门。** 主动发消息翻车一次，你要花十倍精力重建信任。

## 可复用建议

1. 把“值得打断用户”的 checklist 当代码维护：版本化、定期 review、删掉连续两周没触发过的条目。
2. 新任务先跑两周“只读+只汇报”灰度，攒够信任再放写权限。
3. 通知分级：低优先级攒成每日两次的 digest，高优先级才实时推送。
4. 每个 proactive run 记录“触发源 → 判断依据 → 执行动作”三段日志，出问题能回溯，也能帮你发现哪些巡检纯属浪费。

## 总结

Proactive 的本质不是“更勤快”，而是“更会判断什么时候值得出现”。心跳 + 事件覆盖时效光谱，显式 checklist 管住判断，session 隔离和写权限闸门兜底。先把“什么时候闭嘴”想清楚，“主动办事”才有价值。
