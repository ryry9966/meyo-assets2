## 背景

我订阅了三十多个 RSS 源：技术博客、项目 Release 公告、几个期刊的目录。全部读不现实，漏读又焦虑。AI 摘要看起来是显然的解法，但"抓 feed → 塞给模型 → 发给自己"的玩具管线，我见过的大多撑不过两周：token 账单失控、内容重复、摘要不可信、静默失败。这篇记录我在 OpenClaw 上重搭的一条管线，重点是工程决策，不是 prompt 模板分享。

## 问题

直接方案有三个通病：

1. **成本不可控**：所有条目无差别过模型，一天轻松几十万 token，其中大半是垃圾；
2. **摘要不可信**：模型会把标题党写得像干货，对只有两行摘要的 feed 硬编内容；
3. **静默失败**：某个源改版或路由挂了，管线不报错，只是产出悄悄变少，两周后你才发现少了一个信息源。

## 做法

拆成四个独立阶段，各自可单独跑、单独测：

**1. 采集**：脚本拉全部 feed，解析出 entry（link、title、pubDate、content），原样落 SQLite。唯一键用 link hash，天然去重。OpenClaw 的定时任务每天触发两次，没做成插件——纯定时批处理，脚本比 MCP server 更直接，MCP 更适合需要 Agent 交互式调用的场景。

**2. 预过滤（零 token）**：时间窗口过滤（只看上次运行之后新增的）、关键词黑名单、跨 feed 标题相似度去重（同一篇被多源转载很常见）。经验上这一层能砍掉 60–70% 的条目。

**3. 摘要**：剩余条目按 feed 分批，每批一次调用。prompt 硬性要求三条：输出固定 JSON（title / summary / verdict）；summary 只能基于给定原文；verdict 为 skip 时直接丢弃。设每日 token 上限，超了留到下一轮——反正原始数据在库里，不会丢。

**4. 投递**：keep 条目渲染成 Markdown 日报，通过 OpenClaw 的消息通道推送。写回数据库标记已处理，保证幂等，手动重跑不会重复推。

## 踩坑点

- **全文 vs 摘要 feed**：很多源只给前两行，直接摘要等于让模型看标题编故事。加了 readability 抽取兜底：正文过短就抓原页面，抓不到就标记 skip，不硬摘。
- **pubDate 不可信**：见过时区错乱导致"未来发布"和"十年前"的条目。改用抓取时间 + 首见时间去重后问题消失。
- **RSSHub 路由不稳定**：路由挂了不代表源没了。按 feed 记录健康度，连续 N 天零产出就在日报末尾显式提示，而不是默默吞掉。
- **模型对无信息量内容过于宽容**：初期 keep 比例高达 80%，日报成了复读机。在 prompt 里加入硬标准（"这条不发给我，我会损失什么？"）并给每个 feed 设单轮 keep 上限，才压到合理水平。
- **一批塞太多条**：超过 10 条后，排在后面的条目明显被敷衍。按 5–8 条切批。

## 可复用建议

- 先落库再处理，所有阶段幂等，任何一步都可以重放；
- 预过滤的收益远大于调 prompt，优先砍量再谈质量；
- 摘要输出用结构化 JSON，渲染层与模型解耦，换模型不动下游；
- 每个 feed 建健康记录，"产出变少"必须可见；
- 成本上限做成硬限制，不要事后看账单才发现。

## 总结

整条管线没有编排框架：一个脚本 + SQLite + OpenClaw 的定时与推送，两百行左右。核心体会是：这类系统的价值不在于"AI 能总结"，而在于管线能持续告诉你**哪些东西不值得看**。让丢弃可见、让失败可见、让成本可见，比任何精致的 prompt 都重要。
