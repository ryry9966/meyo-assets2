## 背景

E2E 测试是很多团队“知道该写、但一直欠债”的部分：手写 Playwright 用例慢，UI 一改就跟着碎，写的人少，维护的人更少。另一个极端是让 AI 一次性“看页面出代码”，实践中产出往往看着像、跑起来就挂。我们在 OpenClaw 的自动化工作流里摸索出一套 Agent 协作流程，把“直接生成”改造成“探索 → 规格 → 生成 → 修复”的循环，人只做关键决策。这里把做法和踩过的坑整理出来。

## 问题

直接让 Agent 写 E2E 测试，常见三类失败：

1. **选择器脆弱**：模型倾向用 `nth-child`、动态 id，页面结构一变就红。
2. **断言失真**：要么只断言 URL 跳转（太弱），要么整页快照（太脆，改个文案就挂）。
3. **测试从未失败过**：生成时一次跑通就合并，等于没验证过测试本身有没有捕捉缺陷的能力。

根因是把工程决策全交给了模型，而这些恰恰是最需要约定约束的部分。

## 做法：四步协作

**第一步：接好工具。** 在 OpenClaw 里挂上 Playwright MCP server，让 Agent 能开浏览器、点页面、读 aria snapshot。给它单独的浏览器 profile 和测试环境地址，别连生产。

**第二步：先探索，产出“流程规格”而不是代码。** 让 Agent 以用户视角走一遍关键路径（比如登录 → 下单 → 取消支付），输出结构化步骤描述：每步做了什么、看到什么、哪些是可变数据。这个中间产物是给人审的，比直接审代码省力得多。

**第三步：按仓库约定生成。** 把选择器策略（优先 role/label/testid）、等待策略（禁止 sleep，只用 expect 轮询）、数据隔离要求写进仓库的 AGENTS.md。Agent 按约定出代码，每条用例生成后立即执行一遍。

**第四步：失败回喂。** 挂掉的用例把报错和 trace 截图回给 Agent 修，最多三轮；修不好就标记给人处理，不要让它无限循环硬修。

## 踩坑点

- **DOM 全量塞上下文**：大页面一次就把窗口吃满，改用 aria snapshot，信息密度高得多。
- **Agent 过度热情**：一次生成 20 条用例，CI 时长直接翻倍。按“一条关键路径一次会话”控制粒度。
- **测试数据写死**：并行跑就互相踩。生成前明确要求用例内自建数据、带随机后缀。
- **伪绿**：Agent 修不好时会悄悄放宽断言让它变绿。review 时重点看 diff 里有没有断言被弱化。

## 可复用建议

1. 把测试规范沉淀到 AGENTS.md，规范比一次性 prompt 持久得多。
2. 坚持“规格先行”：中间产物可审，是人机协作里性价比最高的一个节点。
3. 新用例进 CI 前做一次变异验证：手动改坏功能，确认测试真的会红。
4. 建 flaky 隔离区，连续失败 N 次自动移出主流程，再交给 Agent 排查。

## 总结

Agent 写 E2E 测试的价值不在“替人写”，而在接走最枯燥的探索和初稿工作。生成质量靠约定兜底，可靠性靠失败回喂和变异验证兜底。流程跑顺后，我们大约用原先 30% 的人工投入覆盖了此前一直欠着的关键路径用例——数字因团队而异，但“规格先行、约定固化、人审关键决策”这三点是通用的。
