## 背景

OpenClaw 这类常驻 Agent 和"一次性问答"最大的区别，是它有一个固定的工作区。工作区里的几个约定文件各司其职：`SOUL.md` 定义 Agent 的性格，`MEMORY.md` 记录事件流水，而 `USER.md` 只回答一个问题——**坐在对面的人是谁**。

很多人装完环境直接开聊，这份文件一直是空的。Agent 照样能用，但你会反复付出同样的成本：自我介绍、纠正偏好、解释环境。

## 问题

没有 USER.md 的 Agent，像一个礼貌但失忆的实习生：不知道你主力写 Python 还是 Go，不知道你的服务器在哪个时区，不知道你 23 点后不想被推送。每次新会话都是冷启动。

随手写一大段塞进去也不行。实践中常见三种翻车：上下文被无用信息挤占、内容过时导致 Agent 拿旧事实给出错误建议、敏感信息被反复读入每次会话。

## 做法

我的原则：把 USER.md 当**配置文件**写，而不是当自我介绍写。四步：

1. **结构化**：小标题加要点，每个事实独立成行。Agent 提取要点远比提取散文段落可靠。
2. **分层**：只放稳定事实（身份、环境、偏好、禁区），有时效的状态（当前项目、deadline）留给 MEMORY.md。
3. **控篇幅**：60 行以内。它是每次会话的固定开销，写越长，留给真正工作的上下文越少。
4. **可验证**：改完新开会话，问三个事实性问题（时区、主力语言、禁区），答错就说明写得不可提取。

参考模板：

```markdown
# USER.md
## 身份
- 称呼：老周（中文，直呼其名）
- 角色：后端工程师，兼管一台家用服务器的运维
## 环境
- 主力机：macOS + Homebrew；服务器：Ubuntu 22.04
- 技术栈：Python / FastAPI / PostgreSQL，在学 Go
## 偏好
- 时区 UTC+8，23:00 后非紧急事项不推送
- 先给结论再给依据；代码示例必须可直接运行
## 禁区
- 不要动 /etc/nginx，任何改动先展示 diff
- 不处理公司业务数据，哪怕只是"顺便看看"
```

## 踩坑点

- **写成简历**。大段生平描述提取率极低，Agent 只能抓住零星几个词。
- **敏感信息入库**。USER.md 每次会话都进上下文，还可能被文件类 MCP 工具间接读走。API key、密码、内网地址一律不写，用环境变量引用。
- **职责混淆**。把"昨天会议结论"塞进 USER.md，一周后上下文全是废料。性格归 SOUL.md，事实归 USER.md，流水归 MEMORY.md。
- **放任 Agent 自改**。允许它补充事实，但必须先展示 diff、确认后写入，否则它会自己越写越长。

## 可复用建议

- USER.md 纳入 git 管理，改动走 commit，能 diff 能回滚。
- 设季度提醒做 review：换机器、换技术栈、换团队后尤其要改——内容腐烂比空白更糟。
- 多项目场景复制一份改成 PROJECT.md，让 Agent 知道"这个项目是谁"，与 USER.md 搭配。
- 优先写禁区字段，"不要动什么"比偏好字段的价值更高。

## 总结

USER.md 本质上是一份写给 Agent 的用户手册：写得好，每次会话都是热启动；写得差，它就是上下文里的负资产。按配置文件的标准对待它——结构化、分层、版本化、定期 review——Agent 对你的了解才会从"猜"变成"查"。
