## 背景

写 Agent 的人迟早会撞上同一个问题：模型本身不会干活，它需要被接上文件系统、数据库、内部 API、浏览器。早期做法是各家框架自己定义 function calling 格式，工具提供方再为每个框架适配一遍。M 个客户端 × N 个工具，就是 M×N 份胶水代码，且没有统一的权限和上下文规范。

MCP（Model Context Protocol）做的事，本质上是把这个 M×N 问题压成 M+N：工具方按协议实现一次 server，任何支持 MCP 的客户端都能直接用。

## 它实际解决的三件事

1. **统一的工具发现与调用格式**。MCP 基于 JSON-RPC，客户端连接 server 后可以列出它提供的 tools / resources / prompts，按统一 schema 调用，不再各说各话。
2. **进程边界与权限收口**。工具跑在独立的 server 进程里，客户端只暴露你显式启用的那几个，出问题好定位、好回收。
3. **上下文注入的标准化**。资源类数据（文件、配置、查询结果）通过协议进入上下文，而不是靠手写 prompt 拼接。

## 最小上手步骤（以 OpenClaw 场景为例）

1. **先用现成 server 验证链路**。比如官方的 filesystem server，只暴露一个指定目录。
2. **在 OpenClaw 的 MCP 配置中注册**。stdio 模式最简单，配好 command、args、env 三项即可。
3. **重启会话确认工具列表已加载**，让模型执行一个只读操作（比如列出目录），验证"模型 → 客户端 → server → 返回"整条链路。
4. **链路通了再自建 server**。用官方 SDK，先声明一两个工具，description 写清楚什么时候该调用、每个参数的含义，返回紧凑的 JSON。

## 踩坑点

- **stdio 模式下日志污染**：server 往 stdout 打调试日志，会混进协议消息导致解析失败。日志一律走 stderr，这是新手最常见的事故。
- **路径与环境继承**：server 继承客户端的 cwd 和环境变量，相对路径经常找不到文件，直接用绝对路径。
- **返回内容撑爆上下文**：一次性读几百 KB 的文件，会话质量立刻劣化。要么分页，要么返回摘要加句柄，按需再取。
- **description 写得含糊**：模型要么不调，要么乱调。description 就是给模型看的接口文档，值得花时间写。
- **工具装太多**：几十个 server 全挂上，模型选择工具的准确率明显下降，按项目裁剪启用列表。

## 可复用建议

- 一个 server 只做一件事，按领域拆分，别做全能网关。
- 先跑稳只读工具，再开放写操作；写操作做好二次确认和回滚路径。
- 参数 schema 收紧：枚举、范围、必填都标上，模型传参出错率会明显下降。
- 返回结构化、小体积的数据；大内容给路径或引用，而不是全文。

## 总结

MCP 不会让模型更聪明，它解决的是工程问题：让"接工具"有了通用插座——一次实现、多处复用、边界清晰、权限可控。对 OpenClaw 用户来说，务实的路径是先用现成 server 打通链路、建立体感，再逐步把内部高频操作沉淀成自己的 MCP server，把原本散落各处的胶水代码收敛到协议层。这件事没有捷径，但每一步都是可复用的资产。
