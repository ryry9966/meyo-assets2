## 背景

模型本身无状态，会话结束上下文就清零。对 OpenClaw 这类常驻 Agent 来说，"记住用户"不是锦上添花，而是体验的及格线：你的代码风格、常用技术栈、时区、明确说过"别做"的事，第二十次对话时助手应该已经知道，而不是每次重新自我介绍。

## 问题

大多数实现卡在两个极端：

- **什么都不存**，全靠手写 system prompt——记忆不可积累；
- **什么都存**，把每轮对话原文塞进向量库——检索噪声大、token 爆炸、新旧偏好互相打架。

核心矛盾是：写入太勤则脏，写入太懒则忘。需要一个明确的读写策略，而不是"先存了再说"。

## 做法

**1. 分三层，别用一个大池子。**

- **偏好卡**：结构化、小体量、每次必注入。语言、代码风格、常用工具、禁区，控制在 200 token 内；
- **事实层**：从对话中抽取的可泛化偏好（如"部署偏好 Docker 而非 K8s"），带 embedding 供检索；
- **情节层**：会话摘要与事件记录，只按需检索，不默认注入。

**2. 写入走异步、走低频。** 会话结束后用便宜模型跑一次抽取 pass，prompt 里明确"只提取持久偏好，忽略一次性上下文"。新事实先与现有库做相似度比对：>0.85 视为重复，走合并/更新；语义相反则把旧条目标记 `superseded`，保留审计记录，不要直接删。

**3. 读取带预算、带出处。** 每轮组装记忆块：偏好卡全量注入，事实层用当前消息做向量检索取 top-5，总预算 800 token。注入 prompt 时明确标注"以下是历史偏好，可能过期，与用户当前指令冲突时以后者为准"——否则模型会把旧记忆当实时事实。

**4. 把记忆做成 MCP 工具暴露给 Agent。** `memory_search` / `memory_write` / `memory_forget` 三个工具，用户说"以后别用那个库了"，Agent 能当场修正，而不是等后台批处理。

**5. 每条记忆带元数据：** `source`（显式/推断）、`confidence`、`created_at`、`last_hit_at`。长期未命中的走衰减，进入待清理队列。

## 踩坑点

- **隐式推断过猛。** 用户随口一句"今天不想吃辣"被记成永久偏好，之后每次翻车。`source=推断` 且 confidence 低时，要么不写，要么命中时找机会与用户确认。
- **检索没带 scope 过滤。** 多用户/多项目场景，`user_id` 不进过滤条件就是串台事故——这是安全问题，不是优化项。
- **只写不删。** 三个月后库里几千条陈年事实，命中率反而不如一张偏好卡。`last_hit` 统计必须从第一天就有。
- **记忆块无出处。** 模型拿三个月前的偏好，回应"我改主意了"的当下指令，体验极差。

## 可复用建议

先别上向量库。一张半自动维护的结构化偏好卡能解决六成问题，且完全可控、可审计、可编辑；规模上来后再补事实层检索。另外强烈建议做**回放测试**：拿历史对话集重放，验证该想起的偏好是否想起——记忆系统这才算有了回归测试。

## 总结

记忆系统本质是数据工程问题：分层、带元数据、有写入门槛、有衰减机制、对用户透明。让用户看得到、删得掉记了什么，比多记十条更影响信任。从偏好卡起步，逐步加检索，别追求"全知"，追求"记得准"。
