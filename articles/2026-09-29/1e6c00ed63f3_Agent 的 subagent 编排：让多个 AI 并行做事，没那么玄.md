## 背景

单个 Agent 跑长任务的老问题：上下文越滚越长，工具调用只能串行。一个任务要读三十个文件、跑测试、再写报告，全塞进主循环，既慢，context 也迟早撑爆。subagent 编排的价值其实就两点：**上下文隔离**和**并行**。每个 subagent 有独立 context，干完活只把结论带回主循环，原始过程留在子任务里。

## 问题

举个具体场景：让主 agent 做一次代码库体检——扫描模块依赖、跑测试、汇总风险点。串行做法下，主 agent 的 context 里堆满中间输出，到第三步就开始丢前面的信息，总耗时还是各步骤之和。这不是模型能力问题，是结构问题。

## 做法

1. **拆任务**：主 agent 先做拆解，产出 N 个自包含的子任务描述。关键是“自包含”——subagent 看不到主对话历史，prompt 里必须写全路径、约束和期望输出格式，当成给新同事的完整工单来写。
2. **并行派发**：通过编排层同时拉起 N 个 subagent，每个子任务声明超时和重试次数。
3. **收结构化结果**：约定 subagent 只返回固定结构（status + 结论 + 证据路径），禁止把原始日志整段带回。
4. **聚合**：主 agent 拿到 N 份小结果再汇总，聚合输入被压到几 KB，context 压力骤降。
5. **失败兜底**：超时或报错的 subagent 返回 partial 标记，主 agent 决定重试还是降级为串行单步。

实测同一个体检任务，3 个 subagent 并行比主循环串行快 2 倍以上，主 context 占用降了一个数量级。

## 踩坑点

- **prompt 不自包含**是最常见的坑。给 subagent 一句“继续刚才的分析”，它只能靠猜，产出全是幻觉。
- **并行写同一文件必炸**。两个 subagent 同时改一个模块，后写的覆盖先写的。并行只给只读任务或互不重叠的写分片，写操作收敛到主 agent。
- **结果不限长**，聚合时 context 又爆了。给返回加硬性长度约束。
- **无脑拉满并发**。N 太大撞限流，费用也失控。经验值是 3–5 个并发，超出排队。
- **过度编排**。两步能做完的事别拆三层，拆解质量和聚合损耗本身就是成本。

## 可复用建议

- 先串行跑通，再对确认的瓶颈步骤并行化，别一上来就上编排。
- 子任务契约三要素：输入路径、约束、输出格式，直接做成模板。
- 所有 subagent 的输入输出落盘留痕，排障时能完整回放。
- 只有幂等、可独立验证的任务适合并行；有严格顺序依赖的，老实串行。

## 总结

subagent 编排不是“更多智能”，而是一个工程手段：用隔离换 context 卫生，用并行换耗时。收益确实大，但前提是任务拆得干净、契约写得清楚、失败有兜底。把它当成进程池来管理，而不是当成一群会聊天的同事，基本就不会踩大坑。
