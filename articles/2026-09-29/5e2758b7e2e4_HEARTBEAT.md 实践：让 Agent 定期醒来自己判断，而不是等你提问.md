# 背景

OpenClaw 里的 agent 默认是被动的：你不发消息，它不动。但有些事不适合"想起来才问"——磁盘水位、证书到期、关注的仓库发了新版本、日志里连续报错。OpenClaw 提供了一个很轻的机制：Heartbeat（心跳）。它按固定间隔唤醒一次 agent，agent 先读工作区里的 `HEARTBEAT.md`，逐条判断"这条要不要现在处理"；没事就静默 ack，有事才真正推送给你。

# 问题

我的起点很原始：提醒全靠 cron 推消息，维护类的小事靠想起来再问。三个痛点：

1. cron 只会定时执行，不会判断——服务正常时也吵，条件写死了还容易漏报；
2. "我长期关注什么"散落在 crontab、备忘录里，agent 并不知道；
3. 想让 agent 主动做点巡检、整理类小活，没有入口。

`HEARTBEAT.md` 本质上是把"长期关注清单"放进 agent 的工作区，判断逻辑交给模型，而不是硬编码在脚本里。

# 做法与步骤

**1. 在工作区（默认 `~/.openclaw/workspace/`）创建 HEARTBEAT.md**，每行一条，写成"条件 + 动作 + 静默条件"三段式：

```markdown
- 检查今天 logs 中的 error 数；超过 20 条才汇总给我，否则静默。
- 用 MCP 工具查主域名证书剩余天数；低于 14 天才提醒，其余不说话。
- 09:00–21:00 之外：全部静默，不做任何检查。
```

**2. 在 `~/.openclaw/openclaw.json` 调间隔**（默认 30 分钟）：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "intervalMins": 45 }
    }
  }
}
```

**3. 验证**：把间隔临时改成 1 分钟，看日志确认心跳会话确实读到了清单；观察一轮"无事静默、有事推送"都符合预期后再调回。改完文件无需重启，下个间隔生效。

**4. 持续维护**：每周回顾一次心跳触发记录，删掉从未触发的条目，给频繁触发的加阈值。想临时停用，在文件里写 `HEARTBEAT: OFF` 即可。

# 踩坑点

- **条件写太虚**。"帮我盯着服务器"这种条目，模型要么每次都报，要么直接忽略。每条必须可执行、可判定真假。
- **它不是 cron**。心跳是"固定间隔醒来 + 读清单 + 自行判断"，没有精确到分钟的调度语义。要 09:30 准时发日报，请用 cron 或定时插件；心跳只管状态巡检。
- **静默失效**。频繁收到"没事也在说话"的消息，多半是模型没遵守 ack 约定。把"否则静默"写进每一条，并在文件头部加一句总则，会明显好转。
- **不幂等**。心跳会重复执行，"一次性任务"（比如整理某段笔记）放进去会被反复做。这类直接发给 agent，别进清单。
- **成本**。每个间隔都是一次真实调用。重的 MCP 查询要设前置条件，整份文件控制在 10 条以内。

# 可复用建议

- 统一模板：`当 <可判定条件> 成立，<动作>；否则静默。`
- 分层：便宜的本地检查放前面，贵的远程调用写明触发前提。
- 心跳管"状态巡检"，cron 管"定时动作"，分工不互相替代。
- 把升级策略写进条目：连续 N 次异常才提醒，避免单次抖动骚扰。

# 总结

HEARTBEAT.md 的价值不在"定时"，而在把判断权交给 agent：边界由你定义，触发与否由模型根据当下状态决定。用下来最大的体会是——主动性不是让 AI 疯狂输出，而是让它在该说话时说话，其余时候安静。清单要短、条件要硬、阈值要明确，这个机制才能真正省心而不是添乱。
