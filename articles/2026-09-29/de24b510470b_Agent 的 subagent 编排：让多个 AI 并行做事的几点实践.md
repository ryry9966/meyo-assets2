## 背景

单个 agent 处理复合任务时有两个常见瓶颈：一是上下文被中间过程塞满，越到后面越"失忆"；二是工具调用串行，一次全库检索加跑测试可能要等好几分钟。subagent 编排就是针对这两点：主 agent 只做拆解、派发和汇总，具体执行交给若干上下文隔离的子 agent，能并行的就并行。

## 问题

上周做一个代码库迁移评估：要摸清模块结构、依赖关系、测试覆盖，最后写结论。串行做，主会话上下文很快被目录树和 grep 输出占满，最终报告质量明显下降；总耗时接近二十分钟，期间主 agent 完全阻塞，别的消息也回不了。

## 做法

1. **先分清"可并行"和"有依赖"。** 只读型调研（扫描、检索、统计）天然可并行；写文件、跑有副作用的命令，默认串行。
2. **给每个 subagent 定契约。** 输入只带它需要的材料（比如只给目标目录和关注点），输出固定结构，例如 `{status, findings, risks, evidence}`。字段写进任务卡 prompt，别靠它自觉。
3. **隔离上下文。** 子 agent 不继承主会话历史，只拿任务卡。这既是省 token 的关键，也是避免子任务间互相污染的关键。
4. **控制并发与超时。** 并发 3~4 个基本是收益拐点；每个子任务设超时和一次重试，失败必须显式返回 `status: failed`，不许静默给空结果。
5. **主 agent 汇总仲裁。** 对互相冲突的结论，要求子 agent 附证据（文件路径、行号），主 agent 抽查后再落笔。

同样的评估任务，并行版 6 分钟左右出报告，主会话上下文占用只有串行版的四分之一左右。

## 踩坑点

- **子 agent 返回太长。** 一开始让它"写详细报告"，三份报告直接把主会话撑爆。后来限制 findings 条数和每条长度才稳住。
- **共享资源冲突。** 两个子 agent 同时写同一份缓存，结果互相覆盖。只读并行、写操作排队，这条要当铁律。
- **递归失控。** 子 agent 又派子 agent，任务树越滚越大。限制层级为一层：子 agent 只许用工具，不许再拆。
- **失败被当成成功。** 子 agent 超时返回空数组，主 agent 当作"没有风险"。契约里必须强制 status 字段，汇总时先看状态再看内容。
- **限流。** 并发 4 个子 agent 各自调工具，429 很快出现。并发数要结合配额定，别拍脑欰开 8 个。

## 可复用建议

- 把 subagent 任务卡做成模板：目标、输入、输出 schema、禁止事项四段固定，换任务只改前两段。
- 返回一律结构化 + 限量，宁少勿长；主 agent 需要细节，可以针对指定子 agent 二次追问。
- 并行只用于只读；涉及写的一切串行并加锁。
- 留 trace：把每个子任务的 prompt、耗时、返回存档，出问题能复盘，也能统计哪类任务真正受益于并行。
- 不是所有任务都值得拆。两步以内能做完的事，编排开销大于收益，直接单 agent 干完更省心。

## 总结

subagent 编排的核心不是"多开几个 AI"，而是**上下文预算的再分配**：把脏活累活的中间产物隔离在子上下文里，主会话只保留结论和证据。模式比 API 重要，无论所用框架是否原生支持 subagent，把"拆解、隔离、限流、结构化回收"这四件事做到位，多数复合任务都能做到既快又稳。欢迎大家把自己那套任务卡模板贴出来对照改进。
