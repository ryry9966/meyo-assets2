## 背景

OpenClaw 的助手默认是被动的：你发消息，它响应。但很多场景需要它“自己醒过来”——定时汇报、监控巡检、跟进待办。OpenClaw 内置的 heartbeat 机制就是为此设计的：按 `HEARTBEAT_INTERVAL` 定时唤醒 agent，读取 `HEARTBEAT.md` 里的检查清单，有事处理，没事回复 `HEARTBEAT_OK` 直接结束。另一条路线是推送：外部事件通过 webhook 直接注入会话。两条路线各有代价，选错方向，要么 token 账单失控，要么事件延迟不可接受。

## 问题

- 轮询间隔怎么定？太短，每次唤醒都是一次真实的模型调用，哪怕无事可做也在烧钱；太长，反应延迟扛不住。
- 推送需要自建接收端：鉴权、去重、排队、重试，基础设施复杂度陡增，而且事件丢了就是丢了。
- 混用时，heartbeat 唤醒和推送消息可能撞进同一个会话，时序混乱。

## 做法

**第一步，按延迟容忍度给事件分类。** 秒级敏感的（CI 失败告警、用户消息到达）走推送；分钟到小时级可接受的（邮件巡检、每日汇总）走 heartbeat；纯批量的（日报）用 cron 触发一次会话即可。

**第二步，heartbeat 侧保持克制。** `HEARTBEAT.md` 只放稳定的低频检查项，间隔 30–60 分钟起步，观察一两周真实唤醒日志后再收紧。每项写成“检查什么、什么条件才需要回复”，让 agent 能快速判定 no-op。

**第三步，推送侧做减法。** 用一个小 webhook 桥接服务（或包成 MCP tool）把事件转成一条注入消息，桥接层只做三件事：验签、幂等键去重、指数退避重试。复杂逻辑不要放在这里。

**第四步，让 heartbeat 兜底。** 推送是 at-least-once 的，终会漏；在 `HEARTBEAT.md` 里放一个“对账式”检查项，定期核对上游状态，补上漏掉的事件。

## 踩坑点

- **无差别唤醒最烧钱**：早期把 8 个检查项全塞进 heartbeat、5 分钟一醒，一天近 2000 次调用，95% 是 no-op。正确顺序是先拉长间隔，再逐项加回。
- **清单膨胀**：HEARTBEAT.md 容易变成垃圾桶，每次唤醒都要读完整个清单，上下文成本随行数线性涨。细节挪到独立文件，清单只留索引。
- **推送撞车**：多个 webhook 在夜间批量到达，会话被冲垮。桥接层要做合并（coalesce）和静默时段排队。
- **时区问题**：heartbeat 是全局间隔，记得按助手所在时区跳过深夜唤醒，否则半夜收到一堆汇报。

## 可复用建议

- 用“延迟容忍度”做决策依据，默认取业务可接受的最长间隔。
- 轮询管对账和低频任务，推送管延迟敏感事件，混合方案几乎总是对的。
- 所有推送事件带幂等键，agent 侧做去重；所有 heartbeat 唤醒记日志（时长、token 消耗），用数据说话。
- 清单最小化并进版本库，改动走 review。

## 总结

heartbeat 的成本随频率线性增长，好处是零额外设施、天然兜底；推送延迟好、单次成本低，代价是基础设施和故障面。对多数 OpenClaw 用户，我的建议是：从 heartbeat 起步，等出现真实无法忍受的延迟时，再为那一类事件单独接推送——而不是一开始就搭一套事件总线。
