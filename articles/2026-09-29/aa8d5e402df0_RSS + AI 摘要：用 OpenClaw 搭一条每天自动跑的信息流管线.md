## 背景

我的信息源很分散：技术博客、GitHub Release、几个论文板块和少量论坛。RSS 阅读器用了很多年，问题始终是“收藏从未减少”——订阅源一多，每天真正点开的比例越来越低。与其把人挂在阅读器上，不如把“筛选 + 压缩”这一步交给跑在本地的 OpenClaw agent，人只看每天一份摘要。

## 问题

直接让模型读 RSS 输出摘要，实践下来有三个坑：

1. **原始 feed 内容脏**：全文 feed 里混着 HTML、CDATA、跟踪参数，直接塞给模型既费 token 又带噪声；
2. **摘要不可控**：模型自由发挥时会补细节、给评价，摘出来的东西没法当“事实”用；
3. **增量困难**：feed 会突发式更新，重复条目和漏条目都很常见。

所以这条管线的关键不是“接个模型”，而是把抓取、清洗、去重、摘要、推送拆成可独立验证的步骤。

## 做法

用 OpenClaw 的定时任务做调度，整条管线每 6 小时跑一次：

1. **抓取**：通过 MCP 的 fetch 工具拉 feed 原始 XML，失败重试一次，连续失败记日志但不阻断整体流程。
2. **清洗**：脚本层剥掉 HTML 标签、截断超长正文（保留前 2000 字符足够判断价值），只保留 title / link / guid / published 四个字段。
3. **去重**：本地 SQLite 存 seen 状态，键用 `hash(guid or link)`。这步必须持久化，内存态一重启就全量重复推送。
4. **摘要**：批量喂给模型，prompt 严格约束——只基于给定内容、每条固定输出“一句话事实 + 涉及的技术点 + 值不值得点进去”，禁止评价和推测，温度设 0。
5. **聚合推送**：按重要度排序拼成 Markdown 日报，经 OpenClaw 的消息通道推到我的私聊，同时落一份 `.md` 存档方便回溯。

跑了两周，日报从 40+ 条收敛到每天 10 条左右，点开率明显回升。

## 踩坑点

- **guid 不等于唯一键**：部分源的 guid 会变，最好用 `hash(guid)` 和 `hash(link)` 双键去重。
- **实体转义**：`&amp;`、内嵌 `<code>` 不清干净，摘要里会带出奇怪断句，清洗这步别省。
- **token 成本失控**：源一多，map-reduce 式两级摘要（先单条压缩、再合并）比一次塞入便宜且稳定。
- **时区**：cron 默认 UTC，日报变成下午推送；显式指定时区后才对齐“每天早上”。
- **摘要幻觉**：约束 prompt + 温度 0 只能缓解，日报里保留原文链接是最后的兜底，复核时随时跳回源头。

## 可复用建议

- 每步中间产物落盘（raw / cleaned / digest 三个目录），出错可以单步重放，不用整条重跑。
- prompt 当代码管理，改版留版本号，摘要风格漂移时能定位是哪次改动引入的。
- 先接 3-5 个高频源跑稳再扩；一上来接几十个源，坏的是你对整条管线的信任。
- 给管线本身加失败通知：连续两轮抓取失败时让 agent 主动私聊提醒，而不是默默空转。

## 总结

RSS 的价值从来没消失，消失的是“人肉消化”的耐心。把抓取、清洗、去重这些确定性环节交给脚本，把压缩和排序交给模型，OpenClaw 负责调度和推送——分层之后每个环节都可测、可回放。这套东西没有技术难度，难在克制：摘要只做压缩不做观点，日报只做入口不做替代，源头还是要点进去自己读。
