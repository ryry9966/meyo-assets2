## 背景

跑长任务或托管式 Agent 时，“让助手定时醒来看一眼”是最直觉的保活方式——OpenClaw 的 heartbeat 就属于这类机制。但随着接入 MCP 事件、webhook、消息通道，很多人开始纠结：到底该靠定时轮询，还是改成事件推送？

## 问题

两者各有代价。轮询简单可靠：不需要公网入口，能穿透 NAT，故障面小，周期内必然醒来一次。坏处是延迟上限等于间隔，而且每次醒来如果都走一遍模型，空闲时也在烧 token。推送延迟低、按需触发，但要求可达的入口（webhook、长连接、MCP 通知），多一层基础设施，还引入丢事件、重复投递这类新故障模式。单独选任何一个，迟早会变成事故。

## 做法：分层混合

我的结论是：heartbeat 当兜底，推送走快路径。

1. **事件分类。** 延迟敏感的（用户消息、告警、CI 失败）走推送；容忍分钟级的（日报汇总、清理任务、仓库巡检）留给 heartbeat。
2. **给心跳加便宜的前置闸门。** 唤醒后先跑本地脚本判断值不值得进模型：查任务文件 mtime、队列长度、git 有没有新提交。没变化就直接睡回去。这一步能省掉九成空转。
3. **推送通道做落盘与去重。** webhook 进来先写一条本地事件（带幂等 ID），Agent 处理完再 ack，网关重启重放也不怕重复。
4. **合并队列。** 心跳和推送汇入同一个待办队列，Agent 醒来只消费队列，唤醒逻辑里不写业务。
5. **间隔加抖动和静默时段。** interval 别取整（30min、1h），加 ±10% jitter 避免所有 Agent 同时醒来撞限流；深夜设 quiet hours，只累积不执行。
6. **记录每次心跳结果**：fired / skipped / triggered 和耗时，跑一两周再用数据调间隔。

## 踩坑点

- **最贵的坑是心跳无条件进模型。** 哪怕只是“看一眼没新消息”，一次几万 token，一天下来很可观。前置闸门必须先行。
- **推送只做 at-most-once 会丢事件。** 网关重启、隧道断连我都遇到过。至少做到落盘重放加幂等 ID 去重。
- **心跳里干重活会堵住下个周期。** 心跳只做判断和入队，重活交给独立的定时任务。
- **webhook 依赖内网穿透或反代，这条链路本身是单点。** 有心跳兜底，它挂了只是变慢，不是失联——这正是混合的价值。

## 可复用建议

- 心跳是保险，推送是快路，别二选一。
- 闸门逻辑用脚本写在 Agent 外部，别让模型自己决定要不要跳过——它总会想找点事做。
- interval、jitter、quiet hours 做成配置而非代码，不同 Agent 用不同档位。
- 所有事件带幂等键、消费端统一去重，这条纪律比架构选型更重要。

## 总结

heartbeat 和推送不是对立选项，而是两个不同 SLO 的通道：延迟敏感交给推送，“活着”本身交给心跳，中间用便宜的前置检查控制成本，再用日志回头调参。先跑起来让数据收敛，比一开始就设计一套复杂调度系统划算得多。
