最近开发者圈在传一个梗：Opus 5.5 “干一半就开溜”。有人让它写八百行的模块，写到四百行戛然而止；有人让它做数据清洗，三轮工具调用后突然“收工致谢”。官方跟进排查后给出的结论相当反直觉：绝大多数情况下，模型并没有“想跑”，是你的程序在它活还没干完的时候，提前替它打了下班卡。这条热搜看似段子，实际上掀开了大模型工程里最容易被忽略的一层——**一次生成到底什么时候停，从来不是模型一个人的决定。**

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-29/d9006d2ae2720cb1.png)

## 一、“停下来”这件事，到底是谁说了算

先补一点原理。LLM 的输出本质上是一个 while 循环：模型每一步只做一件事——预测下一个 token，把新 token 拼回去，再预测下一个。这个循环什么时候退出，由一组“停止条件”决定，谁先命中谁生效：

- **模型自己收工**：输出终止 token（API 里对应 `stop_reason: end_turn`），意思是“我认为任务说完了”；
- **max_tokens 预算**：生成数量达到上限，硬切；
- **stop_sequences**：输出撞上你预设的停止串，立刻断；
- **客户端超时**：网关、SDK 或你自己写的 timeout 先到了；
- **上下文窗口耗尽**：输入加输出把窗口塞满，循环被迫终止。

关键在这：每次 API 响应里都带着 `stop_reason`（Anthropic 系）或 `finish_reason`（OpenAI 系）字段，这是生成过程唯一的“考勤记录”。`end_turn` 才是模型自己下班；`max_tokens` 意味着被预算裁员；其余大多是外部干预。很多人骂模型之前，压根没看过这个字段。

## 二、“替它打下班卡”的，通常是这几张卡

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-09-29/6f5fc87a8c739fb8.png)

把官方口径翻译成工程语言，最常见的“误杀”有这几类：

1. **max_tokens 用了框架默认值**。不少脚手架默认给 4096。八百行代码轻松上万 token，写到一半必然被硬切——表面看是“模型不干了”，实际是预算见底。
2. **上下文窗口塞满**。200K token 听起来很大，但 agent 跑几十轮工具调用，网页正文、文件内容、报错日志全往里堆，最早的系统指令被挤出去后，模型等于“失忆”，只好草草收尾。
3. **超时掐断流式输出**。自建网关常见 60 秒 timeout，长任务写到第 50 秒连接被掐，前端看到的就是一句没说完的话。
4. **agent loop 自身的 bug**。tool call 的 JSON 被截断、解析失败、重试策略把整轮结果吞掉，症状同样表现为“模型放弃了”。
5. **系统提示词的反向作用**。为了日常对话体验写了“回答务必简洁”，结果长任务里模型也学乖了，提前总结收工。

注意一个细节：这些场景里模型的运行逻辑完全正常——它在既定停止条件下老实工作。锅在管线，不在脑子。

## 三、为什么大家第一反应是怪模型？

因为归因偏差在起作用：黑盒系统出问题，人总倾向怀疑里面“最像人的那个组件”。模型会说话、会道歉、看起来有性格，天然适合背锅。

但要公平地说，“模型偷懒”并不是冤案。2024 年底 Claude 3.5 Sonnet 就被大规模吐槽 lazy coding，Anthropic 自己也发过说明，承认模型行为存在波动，甚至提到一个玄学现象：任务被打断后先跟模型打个招呼，输出质量会变好。所以两类问题都真实存在，关键是分清责任：

- **模型行为问题**：`stop_reason` 是 `end_turn` 但质量不行 → 调提示词、拆解任务、换版本；
- **harness 问题**：`max_tokens`、timeout、异常中断 → 改代码。

这次官方的数据口径很明确：多数中断来自客户端配置。诊断顺序应该是先看日志，再看模型——先怀疑自己的配置，这是工程师的基本美德。

## 四、三分钟自查：一条一条排除

1. **先看 `stop_reason` / `finish_reason`**，这一步能直接排除一半可能性；
2. **max_tokens 拉到模型允许的上限**，别信任何框架的默认值；
3. **算 token 账**：输入 + 输出 + 工具返回 vs 窗口大小，长任务要配上自动摘要或历史压缩；
4. **对齐全链路 timeout**：SDK、网关、负载均衡各设了多久，最小的那个说了算；
5. **agent 框架打印每一轮的原始返回**，别只盯着最终结果排障；
6. **系统提示词区分场景**：对话简洁和任务完整是两回事，别用一条规则管两边。

## 写在最后：三条冷思考

1. **长任务的可靠性是个乘法**：模型能力 × harness 稳定性 × 预算管理，取最小值。换新模型解决不了配置问题，就像换旗舰显卡治不好网线接触不良。
2. **`stop_reason` 是全行业最便宜的排障工具**，却被大量应用无视。认真做 agent 的话，把它当一等公民记进监控和告警。
3. **校准一下期待**：模型没有“任务进度感”，它不会自己摸鱼，但你的程序随时可能替它下班。把 agent 当成一个随时会被上游掐断的 worker 来设计——幂等、可断点续跑、预算快耗尽时主动上报，才是正经的相处方式。
