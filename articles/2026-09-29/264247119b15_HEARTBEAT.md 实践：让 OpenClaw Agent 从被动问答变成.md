## 背景

大多数 Agent 的使用模式是"你问它答"：打开对话框，提需求，等结果。OpenClaw 里有一个容易被忽略的机制——heartbeat（心跳）。网关按固定间隔唤醒一次 Agent，塞给它一段系统提示，让它去读工作区里的 `HEARTBEAT.md`，再由它决定"要不要做事、做什么事"。这个文件是 Agent 主动行为的唯一入口：写得好，它是个定时巡检的值班员；写得差，它要么装死，要么凌晨三点给你发消息。

## 问题

实践中 heartbeat 有两种典型失败。一是**空转**：`HEARTBEAT.md` 是空的，或只有一句"帮我盯着点服务器"，Agent 每次醒来无事可做，但每次唤醒仍是一次真实的模型调用。二是**轰炸**：没告诉它何时该沉默，它每个周期都回复"目前没有异常"，聊天窗口被无用消息刷屏。本质问题是把心跳当成了"定时聊天"，而不是一个低成本的巡检循环。

## 做法

**1. 建文件。** 在 workspace（默认 `~/openclaw/workspace`）下创建 `HEARTBEAT.md`。

**2. 写任务。** 每行一个可验证的任务，格式尽量统一：条件 + 动作 + 去向。

```markdown
# HEARTBEAT
- 检查 ~/inbox 是否有新文件，有则摘要后发到 #daily
- 本地仓库未推送提交 > 3 个时，提醒我
- 每天 09:00 后的第一次心跳：汇报服务器磁盘和内存
- 无事发生时：回复 HEARTBEAT_OK
```

最后一行是关键。`HEARTBEAT_OK` 的约定含义是"无事发生，保持沉默"，Agent 看到它就不产生回复，省 token 也不打扰人。

**3. 配节奏。** 在 `openclaw.json` 里调整心跳间隔（默认 30 分钟，轻量巡检建议 30–60 分钟起步），并设置 target（主动消息发到哪个渠道）和 activeHours（如 09:00–22:00），避免夜里被吵醒。

**4. 观察。** 跑两三个周期，再决定加任务还是调间隔，不要一次写满二十条。

## 踩坑点

- **间隔太短 + 任务太泛。** 每次心跳都花输入 token，哪怕最终沉默。15 分钟一次的"看着点"纯属烧钱。
- **任务写成愿望而非指令。** "帮我盯服务器"没法执行；"磁盘使用率 > 85% 时发消息"才可以。
- **心跳里跑重活。** 心跳回合应当轻量；重任务交给 cron 或脚本跑，心跳只负责看结果文件并转述。
- **忘了 activeHours。** 默认全天候，第一次半夜收到消息你就会回来加这一行。
- **心跳输出污染主会话。** 心跳与主会话共享上下文，长篇汇报会稀释后续对话质量，明确要求"汇报不超过三行"。

## 可复用建议

- 把 `HEARTBEAT.md` 当 SRE runbook 写：每行都有触发条件、动作、去向。写不出来，说明这条任务还不成立。
- 分层频率：便宜检查（文件有无、git 状态）30 分钟级；贵的汇总（日报、全量扫描）用日期条件压到每天一两次。
- 文件控制在 20 行内，做完的任务及时删，避免 checklist 腐化。
- 心跳负责"判断要不要说"，脚本负责"干活"，职责分开后两边都好维护。
- 让 Agent 把主动动作追加写进一个 log 文件，方便事后审计它到底自作主张干了什么。

## 总结

heartbeat 的价值在于把 Agent 从被动问答变成低频、有纪律的主动巡检。全部工程要点可以压缩成三句话：**任务要可验证，节奏要克制，默认要沉默**。写好 `HEARTBEAT_OK`，比写十条任务更重要。
