## 背景

LLM 本身无状态。你今天告诉助手"部署一律用 Docker Compose，别给我上 K8s"，下周新开会话，它照样给你生成一整套 Helm chart。上下文窗口越来越大，但"把历史聊天全塞进去"既贵又吵——真正的解法不是更长的上下文，而是一个设计得当的记忆层。在 OpenClaw 这类常驻型助手场景里（workspace 记忆、MCP 工具、定时任务），这件事尤其重要：助手越自动化，凭空"失忆"的代价越高。

## 三种典型失败

1. **无记忆**：每个会话重新自我介绍，偏好全靠人肉重复。
2. **全量堆砌**：聊天记录原文灌进 system prompt，token 成本飙升，关键偏好淹没在噪声里。
3. **只写不改**：偏好只增不删，半年前的旧习惯和新偏好同时召回，助手精神分裂。

## 做法：分层、结构化、有预算

**1. 分层。** 至少分两层：会话内的工作记忆（本来就是上下文），和跨会话的长期偏好库。情景日志（今天干了什么）可选，别一上来就做复杂架构。

**2. 结构化存储。** 每条记忆是一条记录，不是一句自然语言：

```json
{"type":"preference","content":"部署用 Docker Compose","scope":"global","confidence":0.9,"updated_at":"2025-06-01"}
```

关键字段是 `scope`（global / project / channel）和 `updated_at`。存储先用本地文件——Markdown 或 JSONL，能 grep、能 diff、能手改，比一上来上向量库靠谱得多。

**3. 保守写入。** 会话结束跑一次提取 pass，提取器只输出"明确、可执行、会复用"的偏好。寒暄和一次性任务不配进记忆库；重复出现的偏好做合并，confidence 上调。

**4. 有序召回。** 读取路径分三步：先按 scope 过滤，再按关键词/标签匹配（硬规则必须走这条路），向量检索只做兜底。最后按 confidence × 时间衰减排序，**注入 token 设硬上限**（比如 500），超了就截断。

**5. 可修正。** 用户说"以后别这么干了"时，更新原记录而不是追加新记录，旧值进 history 字段。给用户一个直通记忆文件的入口，随时能看、能删。

## 踩坑点

- **提取器太热情**：把"今天有点累"写成"用户状态消极"，污染召回。提取 prompt 里要写明负面清单。
- **只靠向量检索**："代码里别写分号"这类硬规则，embedding 召回很不稳定，标签匹配才是主力。
- **scope 没隔离**：工作偏好泄漏到私人频道，或反过来，是信任杀手。
- **没有时间戳**：新旧偏好冲突时无法裁决，时间衰减也就无从谈起。
- **注入无预算**：记忆越攒越多，把 system prompt 撑爆，精度和成本双输。

## 可复用建议

一句话原则：**保守写入、宽泛召回、严格排序、可审计**。落地时：

- 先文件后数据库，记忆格式必须人类可读；
- 每条记录必带 `scope` 和 `updated_at`，没有例外；
- 排序和截断逻辑写在检索层，别指望模型自己挑；
- 定期人工 review 记忆文件，把它当配置文件而不是黑盒。

## 总结

记忆系统不是模型能力问题，是工程问题：写什么、存哪、怎么取、怎么改，四个决策做对，一个本地文件方案就能覆盖 80% 的需求。先用一个 Markdown 文件加一个提取 prompt 跑起来，等记录真的多了，再谈 embedding 和数据库也不迟。
