## 背景

OpenClaw 的 Agent 是长期驻留的：跑在你自己的机器上，接多条消息渠道，带持久记忆。`SOUL.md` 放在 workspace 根目录，每轮对话都会注入 system prompt，是少数跨会话稳定生效的人格层配置。它和 `AGENTS.md`（怎么干活）、`TOOLS.md`（有什么工具）分工不同——SOUL.md 回答的是"我是谁、我不做什么"。

## 问题

大多数人的 SOUL.md 有两种典型失败形态：

1. **空着不写**。Agent 人格随模型默认值漂移，今天话痨明天高冷，群聊里过度插嘴。
2. **写成散文**。"你是一个温暖、专业、乐于助人的助手"——全是形容词，没有一条可执行，模型读了等于没读。

更隐蔽的是边界缺失：Agent 会顺手执行 `rm -rf`、在群里复述用户私聊内容、替你把邮件发出去。人格是体验问题，边界是事故问题，后者才是 SOUL.md 真正的工程价值。

## 做法

我的模板分四段，控制在 30 行以内：

1. **身份与语气**：名字、默认语言、回复长度上限。写行为不写形容词，比如"默认不超过三段，先给结论"。
2. **硬边界**：不可逆操作（删除、`git push --force`、支付、对外发送消息/邮件）必须复述命令并等确认；不在群聊引用私聊内容；不把本地文件内容带进第三方 API 调用。
3. **升级规则**：信息不足时先问再做；工具连续报错两次就停下汇报，而不是自由发挥绕过去。
4. **渠道差异**：私聊可以口语化；群聊少说话，被 @ 才回。

写完纳入 git 管理。Agent 每出一次格，就补一条回归规则——和修 bug 一样对待。

## 踩坑点

- **写太长**。SOUL.md 进 system prompt，我见过 2000 字的版本，重点被稀释后模型开始选择性遵守。压到 40 行内，遵守率明显回升。
- **与 AGENTS.md 冲突**。两处都定义"如何回复"，规则不一致时模型随机站队。人格归 SOUL.md，流程归 AGENTS.md，宁可互相引用，不要重复定义。
- **把它当安全机制**。SOUL.md 是指引，不是沙箱。高危操作要靠工具白名单、权限最小化、MCP 侧审批兜底，prompt 层只做体验上的确认闸门。
- **一次写完不再迭代**。上线一个月没出事不代表规则没用，更可能是没触发。要定期用刁钻 prompt 主动打一打边界。

## 可复用建议

- **确认清单模式**：任何不可逆动作前，让 Agent 复述"将执行什么、影响哪些对象"，等用户回复确认再动。
- **每条规则附触发案例**：一行注释说明这条规则源自哪次事故，半年后你才知道它为什么存在。
- **季度 prune**：删掉从未触发的规则。SOUL.md 的信噪比就是它的执行力。
- **建对抗测试集**：10 条左右（诱导删库、套隐私、越权发消息），每次改完 SOUL.md 跑一遍。

## 总结

SOUL.md 不是人设小作文，而是一份行为规格说明：短、可执行、分层、进版本库。人格决定 Agent 好不好用，边界决定你敢不敢放手让它用。先写边界，再谈性格。
