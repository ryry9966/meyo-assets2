## 背景

现在大多数 Agent 还是“问答机”：用户发消息 → 模型响应 → 结束。但工程里的活儿大多有时间轴和事件源：每天早上的简报、CI 变红、新 Issue 进来、磁盘快满了。这些事等你开口已经晚了。Proactive 能力的本质不是让模型变聪明，而是在 Agent 外面套一层可靠的触发系统。

## 问题

自己搭 proactive 触发，常见的三种翻车：

1. **打扰过度**：一天推 20 条“您有一条新动态”，用户两周内关掉所有通知；
2. **循环触发**：Agent 写了文件，文件 watcher 又触发 Agent，死循环烧 token；
3. **越权执行**：半夜自动删了“看起来没用”的分支，第二天没人能还原决策依据。

核心矛盾是**主动性 × 控制权**。下面是过去几个月在几个内部项目里跑通的一套做法。

## 做法：四步

**1. 先盘事件源，再谈智能。** 把可监听的源列清楚：cron 定时、webhook（GitHub/CI/工单）、文件系统 watch、邮件/IM 收件、数据库阈值。80% 的 proactive 场景不需要模型实时判断，先问一句：“这事用 if-else 能不能触发？”

**2. 触发与执行分离。** 触发层保持“笨”：不跑 LLM，只做条件判断、去重、限频，命中后才调用 Agent，并把结构化上下文（事件 payload + 相关文件摘要）塞进 prompt。这样 token 成本可控，触发逻辑也能独立单测。

**3. 给动作分级。** 只读动作（汇总、检索、归因分析）→ 静默执行直接给结果；可逆写操作（写草稿、建 issue、打标签）→ 生成后一句话确认，或直接执行但留完整 diff；不可逆操作（删除、外发）→ 只出建议等确认，绝不自动跑。权限上给 proactive 任务单独的 scoped credential，MCP 工具的授权范围和交互会话分开。

**4. 降噪三件套。** 去重键（同一事件 ID 只处理一次）、冷却时间（同类通知 N 小时内合并）、免打扰时段（夜间只累积，早晨发 digest）。

一个落地组合：每天 08:30 拉 calendar + 收件箱 + 昨晚 CI 结果生成晨报（cron 触发，纯只读）；CI 红了由 webhook 触发 Agent 做失败日志归因，结果写进草稿区；新 Issue 进来自动打标——全程没有一步需要用户先开口。

## 踩坑点

- **Watcher 别监听 Agent 自己的输出目录**，输出走 out-of-band 路径，或加标记位过滤；
- **Webhook 都会重试**，任务必须有幂等键，否则一次事件跑两遍；
- **每次触发全量拉上下文，账单会很难看**，上下文做增量更新 + 摘要缓存；
- **时区**：cron 用 UTC 还是本地时间，先统一，血泪教训；
- **先灰度**：挑一两个用户跑两周，统计“主动通知被点开率”，低于 30% 就砍触发器，而不是加通知。

## 可复用建议

- 触发器保持无状态、可独立单测，别把逻辑写进插件深处；
- 每个 proactive 动作落审计日志：触发原因、用了哪些上下文、做了什么；
- 给用户一个总开关 + 按触发器的分开关，随时可调频、可暂停；
- 宁可少触发，不要错触发——信任是 proactive 系统唯一的货币。

## 总结

Proactive 不是让模型“猜你想”，而是一个工程问题：可靠的触发层 + 分级的动作权限 + 克制的通知策略。先让 10% 的高价值事件可靠地主动化，比让 100% 的事件都“聪明”有用得多。欢迎在社区里贴出你的触发器配置和命中率数据。
