## 背景

多数 Agent 是"被动应答机"：你不发消息，它永远安静。真正省心的助手应该反过来——盯着你关心的事，在合适时机主动找你。OpenClaw 其实已经内置了两块地基：heartbeat/cron 定时唤醒，加上 MCP 工具与插件体系。缺的不是能力，而是让"主动"不变成"骚扰"的工程约束。

## 问题

直接在系统提示词里写一句"你可以主动找我"，跑两天你就会想关掉它。实测会撞上三个问题：

1. 不知道何时开口：同一件事反复提醒，凌晨三点推消息；
2. 开口没信息量："一切正常"式心跳汇报和噪音无异；
3. 开口之后做不了事：要么只敢报告，要么擅自执行了写操作。

核心是缺一层门控，而不是缺一个更聪明的模型。

## 做法

四步，全部用 OpenClaw 现有能力即可搭出来：

**1. 接入事件源。** 默认 heartbeat 设为每 30 分钟；再挂两个 webhook，分别接监控告警与日历/仓库变更推送。事件统一写入本地状态文件（SQLite 即可），带 `dedupe_key` 和 `created_at`。

**2. 设计心跳任务。** 心跳 prompt 保持极短，只做一件事：读未处理事件，按三档分类——需要行动 / 合并进日报 / 直接丢弃。分类必须引用工具返回的原始证据，不允许模型凭空判定"紧急"。

**3. 写死门控规则。** 进系统提示词的硬规则：

- 同一 `dedupe_key` 4 小时内只提醒一次；
- 23:00–08:00 只累积不推送（白名单除外）；
- 低优先级事件攒成每日一条摘要；
- 涉及写操作的任务只产出草稿卡片，等用户一次点击确认。

**4. 分级执行 + 闭环日志。** 只读操作（查询、汇总、巡检）直接自动跑；写操作降级为草稿；删除、支付类永远不自动。每次主动行为的触发源、证据、动作、结果全部落日志，每周用一次心跳专门回顾日志、调阈值。

## 踩坑点

- **自己触发自己**：Agent 主动发出的消息也会进事件流，不加 loop guard，它会在消息渠道里和自己聊一整晚。过滤 `sender == self` 是第一课。
- **幂等没做在写入前**：webhook 重试导致同一事件处理两次、提醒发两次。`dedupe_key` 必须在写入状态文件时查重，而不是处理完再标记。
- **心跳上下文膨胀**：把完整聊天历史塞进心跳 prompt，两天后单次 token 翻了十倍。心跳只传增量 diff 与状态摘要。
- **时区**：cron 默认 UTC，静默期要按本地时间算，否则静默窗口整体漂移八小时。

## 可复用建议

- 顺序不能反：先跑一周"只读 + 只提醒"，看日志后再放开草稿确认，最后才考虑任何自动写操作。
- 三档分类别让模型自由发挥，把档位定义与阈值写成提示词里的枚举，输出固定为结构化字段。
- 主动能力的信任是一锤子买卖：一次误报的代价远大于十次沉默，阈值宁紧勿松。
- 冷却时间、静默期、摘要频率这些参数收进配置文件，别散落在 prompt 里。

## 总结

Proactive 不是让模型更聪明，而是给它套上"事件驱动调度 + 门控 + 分级执行"的骨架。OpenClaw 的 heartbeat、MCP 与插件机制提供了全部原料，你需要补的是纪律：什么时候开口、开口说什么、说完了能不能做。把这三件事写死成规则，主动的助手才不会变成深夜轰炸你的机器人。
