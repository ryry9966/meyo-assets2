## 背景

RSS 常被说"过时"，但对做自动化和 Agent 的用户来说，它恰恰是最省心的信源协议：格式标准化、不依赖第三方 SDK、还能用 RSSHub 自建补齐没有官方 feed 的站点。这篇文章记录我搭的一条"采集 → 去重 → 过滤 → AI 摘要 → 日报"管线，已经稳定跑了两个多月，说说做法和踩过的坑。

## 问题

直接把 feed 全量丢给大模型，有三个问题：

1. **成本失控**：订阅源一多，每天几百条目，逐条摘要的 token 消耗很可观；
2. **信噪比低**：多数条目和自己的关注面无关，模型再好也只是在产出垃圾摘要；
3. **管线脆弱**：feed 挂掉、编码异常、API 限流，任何一处没兜底，"无人值守"就变成"每天手动救火"。

## 做法

整条管线五层，每层独立可替换：

- **采集层**：官方 RSS 优先，缺的用 RSSHub 补齐。OpenClaw 的定时任务每 2 小时拉一轮，原始 XML 直接落盘；
- **去重层**：用 `GUID + link + title hash` 三级判重，命中任一即跳过，状态存 SQLite。纯本地逻辑，零成本；
- **过滤层**：两步走。先规则粗筛（关键词黑名单、来源权重），再用便宜的小模型给剩余条目打相关性分，低于阈值直接丢弃。实测这一层砍掉约 70% 条目；
- **摘要层**：按主题分批，每批 8–10 条一次调用，prompt 强制输出固定 JSON：一句话摘要 + 2–3 个关键点 + 是否值得深读，温度压到 0.2 以下；
- **投递层**：汇总成当日 markdown 日报，推送到 IM，同时归档本地目录。

## 踩坑点

- **只有 description 没有全文的 feed 很多**。直接摘要等于"摘要的摘要"，关键信息早没了。要加正文抓取兜底，抓不到就老实标注"仅标题摘要"，别硬编；
- **条目会被更新**。有的站 pubDate 变但 GUID 不变，纯判重会漏掉内容修订，对高价值源要保留旧摘要做 diff；
- **一批塞太多条目，模型会悄悄漏条**。10 条以内是稳定上限，别贪；
- **截断文本容易诱发编造**。prompt 里必须写明"信息不足则标注，不得推测"，这比调参管用；
- **重试要有退避和死信队列**。失败条目存下来次日重跑，别让单点失败阻塞整条管线。

## 可复用建议

1. **两段式结构是成本核心**：规则 + 小模型先过滤，贵模型只处理留下的 30%，整体成本能降一个量级；
2. **原始数据永远落盘**，摘要只是视图。以后模型升级，拿旧数据重新生成即可，不必重新采集；
3. **prompt 和模型配置进版本管理**，摘要质量回退时能定位到具体改动；
4. **输出结构用 schema 约束**，别指望自然语言描述格式模型就能稳定遵守。

## 总结

这条管线的价值不在"接了 AI"，而在信息分层：采集保证覆盖，去重保证不重复劳动，过滤保证成本，摘要保证可读。每层是独立模块，出问题能快速定位到层，替换某一层也不牵连其他部分。信息流工具最怕"新鲜三天就弃养"，分层架构加上稳定的去重存储，才是它能长期跑下去的根本原因。
