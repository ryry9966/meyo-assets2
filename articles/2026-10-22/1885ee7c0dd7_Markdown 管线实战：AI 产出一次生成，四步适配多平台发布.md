## 背景

社区里跑 Agent 自动化的同学大多遇到过同一个场景：让模型产出内容，格式定成 Markdown——语法宽松、结构清晰，是 AI 与人之间理想的交接格式。但真正的难题在「最后一公里」：同一份 Markdown 要发到公众号、知乎、博客和内部 Wiki，每家渲染规则都不同。手动复制粘贴改格式偶尔可以，流水线跑起来就不可持续。

## 问题

踩过的坑归纳为三类：

1. **AI 产出的 Markdown 本身不规范**：同一任务跑十次，标题层级可能从 H2 起也可能从 H1 起；偶尔混入内联 HTML、幻觉出来的图片链接；代码块语言标注时有时无。
2. **平台方言差异大**：公众号不吃原生 Markdown，外部 CSS 类名会被剥离，只剩内联 style；知乎对表格和任务列表支持有限；博客最自由但要处理 frontmatter。
3. **资源链接不可移植**：相对路径图片发出去就是裂图，图床上传和链接重写必须独立成环节。

## 做法

我们把它拆成四步，做成 OpenClaw 工作流里的原子节点，每个节点同时封装为独立 MCP 工具：Agent 可以编排调用，出错时只重跑单步。

**1. 规范化**：AI 输出先过 linter——强制单一 H1、剥离内联 HTML、补代码块语言标注。基于 remark 的 MDAST 写规则，几段遍历逻辑就够，比正则可靠得多。

**2. 资源落位**：扫描图片引用，先校验 URL 可达（AI 幻觉图片在这步被拦下），本地图片自动传图床，所有引用重写成永久链接。

**3. 按平台渲染**：每个目标平台一个渲染器插件，输入统一的 MDAST，输出平台能吃的内容。公众号渲染器把块级元素全部转成内联样式的 HTML；知乎渲染器降级表格、去掉任务列表；博客渲染器基本透传，只处理 frontmatter。渲染器是纯函数，测试友好。

**4. 发布前校验**：按各平台已知限制做最后 lint——公众号检查是否残留 class 属性，知乎检查表格单元格长度，任一项不过就阻断发布，并向工作流回传错误信息。

## 踩坑点

- **别用正则做规范化**。代码块里一行 `# comment` 就能被误改成标题语义，嵌套列表更是重灾区。直接操作 AST，代码量多不了多少，稳定性差一个量级。
- **公众号代码高亮要预渲染**。它不支持客户端高亮，要么把 token 展开成带内联颜色的 span（shiki 的 transformer 可以直接产出），要么整块转图片。我们选了前者。
- **frontmatter 泄漏**。有次渲染器忘了剥 frontmatter，`---` 和字段原文直接上了线。之后校验步骤加了一条「发布内容不得包含 `---` 起始块」。
- **裸下划线标识符被解析成斜体**。`get_user_id` 没包反引号就会出事。与其在文本层做转义替换，不如在生成 prompt 里就要求所有标识符必须用行内代码包裹，规范化阶段对裸下划线单词打 warning。

## 可复用建议

- 把「平台语法白名单」做成配置而非硬编码，新平台接入只需要一份配置加一个渲染器。
- 渲染器上快照测试：固定输入 MDAST，比对输出字符串，平台规则一变，diff 一眼可见。
- 图床和链接重写单独成步，渲染器只关心格式，不碰网络。
- 在生成端就约束格式（单一 H1、代码块带语言标注、标识符包反引号），能省掉一半规范化规则。

## 总结

核心思路一句话：**Markdown 只在一处定义，适配在边缘完成**。规范化、资源处理、平台渲染、发布校验各自独立，AI 产出波动时管线能兜底，平台规则变化时只改一个插件。对跑自动化发布的团队来说，这比「一个大函数转格式」好维护得多。AST 处理逻辑和渲染器插件模板我们整理后会同步到社区仓库，欢迎一起补平台配置。
