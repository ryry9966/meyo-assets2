## 背景

让 Agent 接入 shell 和文件工具之后，社区里被问得最多的一句就是：它会不会哪天手滑把我的目录删了？这不是杞人忧天。LLM 会产生幻觉路径，会误解析相对路径和通配符，也可能在多轮对话里被上下文带偏。一旦 `rm` 类操作执行出去，是不可逆的。所以 OpenClaw 在设计上没有把"模型够聪明"当作安全边界，而是默认它会犯错。

## 问题本质

误删的根因通常不是单一环节失效，而是三层同时失守：

1. **路径层**：Agent 拿到的路径没有规范化解析，`..` 穿越或 symlink 把操作引到了工作区之外；
2. **命令层**：只靠字符串匹配拦 `rm -rf`，但 Agent 可以用 Python、Node 脚本甚至 `find -delete` 达到同样效果；
3. **权限层**：删除和写入同级放行，没有任何确认或回滚手段。

只堵其中一层，都会被绕过。

## OpenClaw 的分层做法

OpenClaw 的 sandbox 是纵深防御，每一层独立兜底：

- **文件系统命名空间隔离**：Agent 的工具调用被限制在专用 workspace 根目录内。文件操作的根就是 workspace 本身，最坏情况只影响这个目录，碰不到宿主 home 和系统路径。
- **路径规范化**：所有文件工具在执行前做 realpath 解析，拒绝解析后越界的路径，包括 symlink 指向工作区外的情况。
- **命令策略层**：`exec` 工具对命令做危险模式识别，命中后要么直接拒绝，要么升级为需要人工确认的操作。
- **工具权限分级**：读、写、删除不是一个级别。删除类操作默认走确认或被策略禁用，可以按项目粒度配置放行。
- **删除走回收站**：即使放行，删除也优先落到 trash 目录而非直接 unlink，配合快照可以回滚。
- **审计日志**：每一次文件操作记录原始请求、解析后的路径和最终结果，出问题能复盘。

示意配置（字段名以实际版本为准）：

```json
{
  "sandbox": {
    "root": "~/openclaw-workspace",
    "deletePolicy": "trash",
    "dangerousOps": "confirm"
  }
}
```

## 踩坑点

- **Symlink 逃逸**：有人在 workspace 里放了个指向 home 的软链接图方便，路径规范化之外，最好也不要把敏感目录链进来。
- **bind mount 范围过大**：用容器跑 sandbox 时把 `/home` 整个挂进去，隔离形同虚设。挂最小集合。
- **误信"拦住了 rm 就安全"**：真正的兜底是文件系统层（workspace 根 + realpath），命令字符串匹配只是第一道滤网。
- **确认弹窗被滥用**：如果 Agent 每个操作都弹确认，人会形成惯性点"允许"，prompt injection 就有可乘之机。确认应该只留给真正高危且低频的操作。
- **本地直跑模式**：关掉 sandbox 直接跑工具时，以上所有防护都会退化。调试可以，长期挂机不行。

## 可复用建议

1. 给每个 Agent 分配独立 workspace，宁可目录多，不要共用根；
2. 权限默认 deny，按需放行，放行记录进日志；
3. 一切删除操作强制走 trash + 快照，把"不可逆"从系统里消除；
4. 定期回放审计日志，重点看 symlink 解析结果和被拒操作的模式，它们能提前暴露策略漏洞；
5. 新工具接入时先在只读模式下跑一周，确认它请求的路径范围再放开写权限。

## 总结

OpenClaw 防误删不靠提示词，也不靠模型自觉，而是靠"命名空间隔离 + 路径规范化 + 权限分级 + 可回滚"四层结构，让最坏情况被限制在一个可接受的爆炸半径内。安全模型的正确心智是：假设 Agent 一定会犯错，然后保证犯错时损失可控。这套思路不限于 OpenClaw，任何让 Agent 拿到文件系统权限的场景都适用。
