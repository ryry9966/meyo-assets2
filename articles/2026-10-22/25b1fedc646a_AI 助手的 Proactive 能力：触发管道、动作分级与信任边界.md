## 背景

现在大多数 Agent 的交互模型仍是一问一答：用户发起，模型响应。但很多真实价值发生在"没人说话"的时间段——CI 挂了、日历冲突、错误率上涨、依赖出了新版本。信号一直都在，缺的是一条把它们送到 Agent 面前的管道。MCP 和插件生态让 Agent 有了"手"，proactive 要补的是"闹钟"，以及判断什么时候该伸手的分寸。

## 问题

直接把 Agent 挂上定时任务和 webhook，通常一周内就翻车，集中在三件事：

- **打扰**：低价值事件也唤醒模型，产出没人看的推送；
- **风险**：主动执行写操作，用户事后才知道；
- **成本**：每个事件都过一遍大模型，token 消耗随事件量线性增长。

本质上，proactive 不是模型能力问题，而是触发管道、动作策略和信任边界的工程问题。

## 做法：五步搭一条主动管道

1. **枚举触发源**。定时、webhook、文件变更、MCP resource 订阅都行，先挑真实有价值的 3~5 个信号，宁少勿多。
2. **廉价预筛**。用确定性规则（阈值、关键词、去重键）挡掉九成事件，只有过筛的才唤醒模型。不要让 LLM 做第一道判断。
3. **动作分级**：
   - L0 静默记录：只写日志，不打扰人；
   - L1 自动准备：草稿、摘要、待审清单——产出但不执行；
   - L2 需确认：发消息、调写接口、花钱，一律生成待确认项，用户点头才走。
4. **预算与静默期**。每天最大唤醒次数、单次 token 上限、免打扰时段、同主题冷却窗口（同一错误 2 小时只报一次）。
5. **审计闭环**。每次主动行为记录触发源、依据、动作和消耗，落盘可查。

我们的落地示例：早八点定时任务拉 CI 状态和 issue 增量，规则预筛后只把"主分支失败"和"P0 issue"送进 Agent，产出晨报草稿和三条修复建议，全部停在 L1。跑了两周才放开第一条 L2（往群里发晨报），再两周才允许它自动打 issue 标签。

## 踩坑点

- **自触发循环**：Agent 的写操作又产生事件把自己唤醒，必须过滤自身身份产生的事件。
- **旧上下文**：主动唤醒时应重新拉取状态，别信缓存里的旧世界。
- **权限扩散**：给 proactive runner 单独发最小权限凭证，不要复用主会话的。
- **时区**：定时任务跟着服务器时区跑，用户在另一个时区，晨报变午报。
- **难测试**：把历史事件录下来做回放，比等线上触发靠谱得多。

## 可复用建议

- 默认"给草稿不给动作"（draft, don't execute），这是建立信任的起点。
- 每个触发事件都带元数据：来源、置信度、去重键，下游策略全靠它。
- 先只读跑两周，再谈写权限。
- 唤醒决策要便宜且确定，模型只负责"醒了之后干什么"。

## 总结

Proactive 的价值不在"更聪明"，而在该出手时出手、出手前有分寸。把触发管道做薄、动作分级做严、审计做全，主动助手才不会从效率工具退化成噪音源。建议从一条只读的定时摘要任务起步，两周后再逐步放权。
