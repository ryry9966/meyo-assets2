## 背景

跑了一段时间 OpenClaw 的 agent 工作流后会发现，“一个 agent 配一个模型”其实是个假象。一次任务里混着多种性质的活：多步规划、MCP 工具编排、结构化字段抽取、日志归类、长文本摘要、最终回复润色。全走 GPT 级云端模型，token 账单和首 token 延迟都扛不住；全换本地模型，复杂推理和工具调用成功率又明显下滑。多模型路由要解决的不是“哪个模型更强”，而是把不同性质的子任务分给合适的那一侧。

## 问题

OpenClaw 支持在 agent / 插件层给每个角色指定模型和 fallback 链，能力是现成的，难点在切分标准：按 agent 身份切太粗，按单条消息切又太碎，还会出现同一会话前后风格割裂的问题。

## 做法

1. **先摸底再分流。** 把一周的路由日志和 token 用量拉出来，按任务类型分成四类：规划决策 / 工具编排 / 结构化抽取 / 长文本摘要，标出每类的平均 token、耗时和失败率。没有这个分布，后面全是拍脑袋。
2. **定分工基线。** 本地模型（vLLM/Ollama 跑 7B–14B 级别）接高频、格式固定、上下文短的任务：批量抽取、日志归类、PII 预脱敏、工具参数预校验；云端模型接多步规划、长上下文推理、跨工具的复杂编排和最终输出。
3. **显式配置 + 单跳 fallback。** 每个 agent 明确写 primary 模型，不依赖全局默认；关键链路配一跳兜底：本地失败直接升云端，不要本地→小云端→大云端层层降级。
4. **固定回归集。** 准备 20–30 条典型 case，每次改路由规则前后各跑一遍，对比工具调用成功率和 JSON 合法率，达标再上线。

## 踩坑点

- **小模型 function calling 格式漂移**：同一份工具 schema，本地 7B 偶尔多字段、漏 required 字段。必须在路由层做 schema 校验加一次重试，别把坏参数直接喂给 MCP 工具。
- **上下文窗口静默截断**：云端 128k 无感，本地 8k/32k 超限后表现是“答非所问”而不是报错。路由前先算 token 数，超限直接走云端，不要硬塞。
- **fallback 链过长**：层层降级导致延迟叠加，体验比直接失败更糟，只留一跳。
- **本地模型升级小版本后输出格式变化**：抽取字段突然变了格式，回归评测集就是拦这个的。
- **共享 system prompt 的差异**：两个模型对指令跟随和温度的敏感度不同，切换时会显出风格断层，重要 prompt 要在两个模型上分别验证过。

## 可复用建议

- 按“难度信号”路由比按身份路由省心：先让本地模型接，检测到多轮纠错或低置信度再升级云端。
- 路由决策必须打日志：选了哪个模型、为什么、耗时多少。没有日志的路由没法优化。
- 敏感数据先本地脱敏再上云，是成本和合规之间务实的折中。
- 确定性子任务的结果直接缓存，通常比换更便宜的模型省得多。

## 总结

多模型路由的价值不只是省钱，而是把延迟、隐私、成本放进同一张表里权衡。务实的路径是：日志摸底 → 小步分流 → 回归评测 → 持续调优。别指望一步配出“最优路由”，它是跟着你自己的任务分布演化出来的。
