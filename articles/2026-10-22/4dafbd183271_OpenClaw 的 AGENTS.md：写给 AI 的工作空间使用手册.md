## 背景

如果你同时维护几个项目，又频繁让 OpenClaw 的 agent 进来做事，大概率遇到过这种情况：每次新会话，agent 都要重新"摸底"——用错包管理器、跑一个不存在的测试命令、把生成目录里的文件当源码改了。这些不是模型能力问题，而是它缺少一份稳定的上下文。

AGENTS.md 补的就是这块：一个放在工作区根目录的纯 Markdown 文件，agent 进入工作区时会自动读取。可以这么理解——README 是写给人的，AGENTS.md 是写给 AI 的。它不是某个工具的私有格式，而是逐渐被各家 agent 工具接受的开放约定，所以写一份，换工具也能继续用。

## 问题

没有 AGENTS.md 时，团队约定只存在于两个地方：老成员的脑子里，和聊天记录里。前者 agent 读不到，后者会话结束就丢了。于是每个新会话都在重复交学费：

- monorepo 里三个包分别用 npm / pnpm / uv，agent 一律 `npm install`；
- `dist/`、`generated/` 是构建产物，agent 拿来就改；
- 测试需要先起本地依赖服务，agent 直接跑，红一片；
- 有 lint 规则，但没人告诉它提交前要过一遍。

这些都是确定性信息，完全可以一次性写下来。

## 做法

建议从小开始，只写"不写就会错"的内容：

1. **根目录 AGENTS.md 先写三段**：项目一句话概述；安装、构建、测试、启动的确切命令；环境要求（Node 版本、必需的环境变量、本地依赖服务）。
2. **记录非显性约束**。包管理器用 pnpm 而非 npm、哪些目录是生成物不要手改、改某个文件必须同步更新哪里。这类信息 README 里通常没有，恰恰是 agent 最需要的。
3. **monorepo 分层**。根目录放全局约定，各子包放自己的 AGENTS.md，agent 按所在目录就近读取。层级之间不要写互相矛盾的规则。
4. **细节外链，不复制**。代码风格、发布流程这类长文档独立维护，AGENTS.md 里只放路径引用，避免两处内容逐渐漂移。
5. **迭代维护**。每次手动纠正 agent 之后问一句：这条能不能变成 AGENTS.md 里的一行？能就加进去。

长度建议控制在 100 行以内。agent 的上下文不便宜，写它用不上的内容是纯浪费。

## 踩坑点

- **写成大部头**。几百行的文件，关键规则会被淹没，实测效果反而不如三十行精华。
- **和 README 抢内容**。README 更新了、AGENTS.md 忘了更，agent 拿着过期信息行事，比没有更糟。
- **写不可执行的口号**。"请写出高质量代码"没有信息量，要写"提交前运行 `pnpm lint`，修复所有 error"。
- **硬编码易变信息**。版本号、临时路径写进去，下个迭代就过期。写"以 package.json 为准"比写死版本号安全。
- **写完不验证**。开一个干净会话，让 agent 跑一遍测试或加个小功能，看它是否按约定走。没验证过的 AGENTS.md 不能算写完。

## 可复用建议

- 把"一次纠错，沉淀一条规则"当成习惯，AGENTS.md 会自然长成团队经验的索引。
- 像 review 代码一样 review 它：约定变了，改 AGENTS.md 的 PR 与改 CI 配置的 PR 同等优先级。
- 模板可以精简到四节起步：概述、命令、约束、文档索引。够用很久。

## 总结

AGENTS.md 的本质，是把"你希望 agent 怎么在这个工作区干活"从口头约定变成版本化管理的工作区配置。成本很低——一次半小时，之后每次会话都在回本。对经常和 agent 协作的人来说，这可能是性价比最高的一类文件。
