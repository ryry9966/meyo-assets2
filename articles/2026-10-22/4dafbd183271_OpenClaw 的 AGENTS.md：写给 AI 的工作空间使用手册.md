## 背景

AGENTS.md 原本是编码 agent 圈的一个约定：在工作区根目录放一个 markdown 文件，agent 启动时读取，用来了解项目结构和规矩。OpenClaw 沿用了这个约定，并把它放到了更核心的位置——workspace 里的 AGENTS.md 是每次会话冷启动时最先加载的指令文件。可以这么分工：SOUL.md 决定"它是谁"，MEMORY.md 记录"发生过什么"，而 AGENTS.md 规定"在这个工作区里怎么干活"。

## 问题

常见的两种极端。一种是空着不写，或只有几句自我介绍，结果 agent 每次凭通用习惯干活：命名随性、乱调用不上的 MCP 工具、改动前不确认。另一种是反过来，把想到的规则全塞进去，两千多行，后半段指令基本被稀释，模型各处只挑着听。还有个高频误会：把它当成写给人的 README，满是叙述性段落，真正可执行的约束反而没几句。

## 做法

我的 AGENTS.md 现在稳定在 120 行左右，结构固定：

```markdown
# 工作区约定
## 环境事实
- Debian 12，Python 3.12，包管理用 uv
- 代码在 ~/projects，产出统一放 ~/workspace/out
## 工具偏好
- 文件搜索优先 ripgrep，不要 ls 翻目录
- browser 工具只用于外部网页，本地文档别走浏览器
- MCP 某服务连续失败两次就换方案，不要死磕
## 行为边界
- 删除、覆盖文件前必须复述目标路径并等我确认
- 一次改动超过三个文件，先列计划再动手
## 汇报格式
- 完成后用三行以内说明：改了什么、在哪、怎么验证
```

写作原则：每条都是祈使句，一条只说一件事，写"做什么"而不是"注意质量"。环境事实只放不常变的；经常变的交给 MEMORY.md 或现场查。如果某些项目放在独立 workspace，就各放一份，不必追求一份管所有。

## 踩坑点

- **规则打架**。我早期同时写过"总是先跑测试"和"未确认不要执行命令"——测试也是执行命令，模型随机选边。修法是把优先级本身写进去：确认类规则永远压过效率类规则。
- **易变信息写死**。端口、容器 ID、当天日程，写进去第二天就错。两周内可能过期的，都别放。
- **别放密钥**。AGENTS.md 会随上下文发给模型和工具链，token、内网地址一律不写，走环境变量。
- **改完不生效**。它是会话启动时加载的，编辑后要新开会话（或 /new）才读得到。不少人以为规则"没被遵守"，其实是"没被加载"，白调试半天。
- **心跳任务也在读它**。OpenClaw 的定时/心跳任务同样受它约束，所以"别主动打扰我"这类规则要考虑无人值守场景，别写出只有你在场才成立的假设。

## 可复用建议

1. 建"错误晋升"循环：同一个错犯第二次，就升级成 AGENTS.md 里的一条规则，下次会话验证。这个文件的价值不在初稿，在迭代。
2. 每接一个新 MCP server 或插件，在"工具偏好"下加两三行：什么时候用、什么时候别用、失败怎么办。
3. 放进 git 跟工作区一起版本化，规则变更可回溯。
4. 定期做减法：我每月扫一遍，删掉已被模型稳定执行的条目。

## 总结

AGENTS.md 是少数"投入一小时，之后每次会话都省时间"的配置。它不玄，就是一份写给 AI 的岗位说明书：短、具体、无冲突、随错误持续修订。写好它，agent 的下限就稳了。
