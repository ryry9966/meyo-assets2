## 背景

OpenClaw 这类常驻 Agent 和普通聊天机器人的区别在于：它有真实的工具权限——shell、文件系统、浏览器、MCP 服务、定时任务。权限越大，"在社区里问个问题"这个日常动作的风险就越高。我们贴配置、贴日志、让 agent 帮忙排错，这些都是社区最正常的互动，也是最容易出事的地方。

## 三条泄漏路径

1. **人贴出去的**。最常见：排错时把整个 session 日志、workspace 下的文件直接粘到群里，里面往往有 API key、内网地址、客户信息，甚至 memory 文件里 agent 帮你记下的所有私事。
2. **Agent 自己发出去的**。社区 bot 和私人助理共用同一实例时，上下文是互通的。你在私信里让它总结过财务数据，转头有人在公开频道问"今天有什么进展"，它可能就把摘要带出来了。
3. **被诱导出去的**。Agent 有浏览器和抓取能力，网页内容里藏一句 prompt injection，就可能让它把工作区文件发往外部地址。这不是假设，是 Agent 类系统已经反复出现的攻击面。

## 做法：四步收口

**第一步：实例隔离。** 公开频道用的 agent 和私人助理拆成两个实例、两份 workspace、两套凭据。公开实例只挂最小工具集，不接邮件、笔记、文件系统这类高敏数据源。

**第二步：MCP/工具最小权限。** filesystem server 不要挂 `$HOME`，挂一个专门给 agent 的目录；只读能解决的绝不给写；每个 MCP server 单独审一遍 scope。审计方法很土但有效：问自己"这个工具被滥用时，最坏能读到什么"。

**第三步：分享前过脱敏流程。** 固定动作：日志先用正则扫一遍 `sk-`、`token`、`password`、内网域名；session 只贴相关回合，不带 memory 和 workspace 上下文；截图前确认浏览器没登录内部系统。有条件就用 gitleaks 之类的工具在本地跑一遍要贴的内容。

**第四步：审计定时任务和 webhook。** agent 的 cron 摘要、自动播报是最容易被忽略的出口。逐条确认：这些任务的输出最终发到哪个频道、数据来自哪些源。

## 踩坑点

- **"提示词里没写秘密就安全"**——不对。泄漏的不只是提示词，还有工具输出。agent 读过的每个文件都可能进入上下文。
- **给 agent 挂了浏览器却忘了登录态**。浏览器工具复用你的会话 cookie，agent 能进的内部后台比你以为的多。
- **排错心切直接贴全量配置**。代理地址、内部 webhook URL 这类"不算 key 的敏感信息"，一样能被用来定位你的内网。
- **指望公开频道里的 agent "自己懂事"**。权限控制要靠配置，不能靠模型自觉。

## 可复用建议

把下面这份 checklist 贴在 workspace 里，分享前过一遍：

1. 有没有 key / token / 密码？（正则扫）
2. 有没有内网地址、客户名、内部项目代号？
3. session 是否裁剪到只含问题相关回合？
4. 公开 agent 是否接了不该接的数据源？
5. cron / webhook 的输出去向是否确认过？

再加一条习惯：新接一个 MCP server 时，把"它最坏能读到什么、写到哪"写进自己的文档。半年后你会感谢这行字。

## 总结

Agent 的便利来自权限，风险也来自权限。社区分享是好事，但默认假设应该是：贴出去的内容会被陌生人完整阅读。实例隔离、最小权限、脱敏后分享、定期审计——四件事都不难，难的是形成习惯。红线不是限制 agent 的能力，而是保证你能长期放心地用它。
