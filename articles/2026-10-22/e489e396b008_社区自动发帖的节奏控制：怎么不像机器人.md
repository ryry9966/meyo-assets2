## 背景

我们在社区里用 OpenClaw agent 挂了几个 MCP 插件，做周报摘要、changelog 通知和部分答疑回复。第一版很直接：cron 定时触发 + 固定 prompt 模板，跑得很稳。结果两周内一个频道的 bot 被静音了三次。

复盘后发现，问题不在内容质量，而在节奏。成员和平台的反垃圾机制识别"机器人感"，很大程度上看的不是单条内容，而是时间序列特征。

## 问题

典型的机器人指纹有这么几类：

- **固定间隔**：每小时整点发一条，方差为零；
- **错峰发布**：服务器跑 UTC，社区在 UTC+8，凌晨三点准时出现；
- **结构雷同**：同样的问候语、同样的 bullet 数量、同样的结尾提问，temperature 调高也救不了模板；
- **突发倾泻**：服务重启后把积压队列一次性灌出去；
- **秒回**：用户提问后 5 秒给出完整答案，人类做不到。

Agent 默认优化的是"发帖成功"，不是"被人读到"。

## 做法

**1. 发帖时间从定时改为采样。** 拉取两周的社区历史消息时间戳，按小时统计权重分布，发帖时刻从这个分布里采样，再叠加 ±10 分钟抖动。社区活跃它就活跃，社区安静它就闭嘴。

**2. 给发帖设预算。** 用 token bucket 做限流：全局日上限、单频道上限、bot 发帖数占频道总消息数的比例阈值（我们压在 5% 以下）。超预算就合并或丢弃，排队不等于都要发。

**3. 内容去重。** 发帖前和自己的最近 N 条、频道近期消息做 embedding 相似度检查，超阈值就搁置或并入已有帖子。跨频道分发时也要变体，不要复制粘贴同一段。

**4. 风格抖动放进配置。** 维护几套"voice profile"（长短、语气、是否带列表），每次发帖随机选一套，禁用固定问候和固定结尾。有时一条摘要就该只有两句话。

**5. 回复节流。** 被 mention 后进队列，延迟 2–10 分钟再回，低相关性的 mention 直接跳过。回复率设上限，比如不超过被提及数的 30%。

**6. 失败退避。** 发布失败走指数退避 + 最大重试次数，超限就报警给人，绝不重试风暴。

## 踩坑点

- **均匀随机仍然可被识别**。±20 分钟的均匀抖动看起来"随机"，但人类一眼能看出每小时一条的骨架。必须用真实活跃分布采样。
- **时区是最常见的翻车点**。cron 写死在服务器时区，上线前先跑一周 shadow 模式核对实际落点。
- **temperature 治标不治本**。模板 prompt 固定了结构和措辞，采样再随机，输出还是那个味儿。要改的是 prompt 的变量维度，不是温度。
- **积压恢复后的倾泻**。断线重连、队列重放都会造成突发，窗口内必须有硬上限。
- **周末和节假日**。活跃分布是按周统计的，记得区分工作日和周末，不然周六照常"上班"。

## 可复用建议

- 把发帖当成一种**配额资源**管理：`quiet_hours`、`daily_cap`、`per_channel_cap`、`max_reply_ratio` 做成配置项，而不是散在代码里。
- 先影子运行两周：所有帖子进人工审核队列，顺便收集真实的时间分布数据，再放开自动。
- 建观测指标：回复率、负面反应数、被静音/拉黑次数。这些是比"发送成功"诚实得多的信号。
- 每周回头审一遍自己发的内容，问一句"这条有必要吗"。合并永远优于拆分。

## 总结

节奏控制的目的不是伪装成人，而是让 agent 遵守社区已有的运行规律。一个发得少、发得准时的 bot，比一个高频整齐的 bot 更容易被当作成员而不是噪音。自动化发行的 KPI 从来不是产量，是被读到的比例。
