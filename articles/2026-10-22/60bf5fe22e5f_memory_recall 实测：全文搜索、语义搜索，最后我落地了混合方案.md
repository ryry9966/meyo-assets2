## 背景

Agent 跑久了会积累大量记忆片段：用户偏好、项目约定、踩过的坑。`memory_recall` 负责在新对话里把这些捞回来。检索策略选得对不对，直接决定 agent 是"记得住重点"，还是"胡乱联想污染上下文"。最近我把自己的 assistant 记忆检索重构了一遍，把两种路线的取舍记录如下。

## 问题

两条路线各有明显短板：

- **全文搜索（SQLite FTS5 / BM25）**：查 `ERR_CONN_REFUSED`、`postgres-15` 这类精确 token 非常准，检索零成本、结果确定。但换个说法就抓瞎——用户说"上次那个部署脚本"，关键词根本对不上。
- **语义搜索（embedding + 向量检索）**：换说法能召回，但精确 token 反而弱。查"redis 连接池上限"，可能召回一堆只聊过 redis 的闲聊。
- **隐性成本**：embedding 调用的延迟和费用，以及不相关记忆挤占上下文窗口——这是最容易被忽略的代价。

## 做法

最终落地的是"全文为主、语义兜底"的两段式：

1. **写入侧**：不存原始对话，存原子事实，每条不超过 100 字，带 tag 和时间戳。写入质量决定召回上限。
2. **双索引**：FTS5 建关键词索引；每条记忆算一个 embedding 向量存同库，按内容 hash 缓存，避免重复计费。
3. **召回流程**：先从 query 抽关键词走全文，top1 分数过阈值就直接返回；不达标再走向量检索，两路结果用 RRF 融合，叠加时间衰减，取 top 3~5。
4. **评估**：攒了 30 条「query → 期望记忆 id」的测试集，每次调参跑一遍 hit@5，不靠感觉。

## 踩坑点

- **FTS5 默认分词器不切中文**："部署脚本"整串成一个 token，搜"脚本"搜不到。换 trigram tokenizer 解决，代价是索引体积明显变大。
- **向量阈值设太松**（0.7 以下全放行）：不相关记忆灌进上下文，token 消耗翻倍，agent 还被带偏。收严到 0.82 以上后重新跑评估集才敢上线。
- **没做写入去重**：同一条偏好被写了五遍，五遍全召回。现在写入时对近邻向量查一次相似度，>0.9 直接合并。
- **老记忆永生**：加了时间衰减系数，被再次命中的记忆刷新时间戳，形成自然淘汰， pinned 的除外。

## 可复用建议

- **先全文后语义**：别一上来就堆向量库，很多场景 trigram + 好的写入规范就够了，语义是兜底不是默认。
- **召回条数宁少勿多**：3~5 条封顶，上下文是稀缺资源。
- **评估集是唯一可信依据**：20~50 条手工标注的 query 就够起步，比任何直觉都可靠。
- **写入时多花十秒**：整理成原子事实、打好 tag，比召回端任何算法优化都管用。

## 总结

语义 vs 全文不是二选一：精确 token 走全文，模糊意图走语义，两段式 + 融合排名 + 小评估集，是我实测最稳的组合。基于自己的 30 条测试集，召回率从约 60% 提到 85% 以上，仅供参考——你的数据分布不同，结论请以自己的评估集为准。工程上最重要的从来不是算法，是写入质量和持续评估。
