# 背景

用 OpenClaw 跑自动化任务一段时间后，大概率会遇到同一个瓶颈：单 Agent 串行干活。比如"审查这三个模块、各出一份重构建议"，在主循环里一个个来，上下文越堆越长，前面的结论开始干扰后面的判断，速度也慢。subagent 编排就是针对这个问题的：父 Agent 负责拆任务和汇总，子 Agent 各自带独立上下文并行执行。

# 问题

但直接上并行会踩三类坑：

1. 子 Agent 拿不到父对话的上下文，任务描述不全它就自己脑补；
2. 多个子 Agent 并行写同一批文件，互相覆盖；
3. 汇总时子结果太大，父 Agent 的上下文反而先爆。

所以核心工程量不在"并行"本身，而在接口设计：怎么派活、怎么收活。

# 做法

以"三个模块的代码审查"为例，我们的流程是：

1. **拆任务**。父 Agent 先读一遍仓库结构，把工作切成互不重叠的三份。每份任务书写成自包含 brief：目标、涉及的文件范围、约束（只读不改）、输出格式（每个文件最多 5 条问题 + 严重级别）、完成标准。
2. **派发**。主 Agent 调 subagent 工具同时发起三个子 Agent，各自独立会话；需要的话给子 Agent 挂 MCP 工具，但按需给，只读任务不给写权限。
3. **控并发**。默认并发 3。别一上来开十几个——API 限流和 token 消耗会先于收益到来。
4. **收结果**。要求子 Agent 只返回结构化摘要，不贴原始日志，父 Agent 负责合并成一份报告。
5. **失败处理**。每个子任务设超时；失败的单独重试一次，仍失败就标记降级，不让一个子任务卡死整批。

# 踩坑点

- **brief 不自包含是最常见的失败原因**。子 Agent 不知道"我们之前讨论过什么"，任务书里必须写全。前几次跑建议人工过一遍 brief 再放行。
- **文件所有权要划清**。并行写代码时按目录/文件分片，一个文件只归一个子 Agent，否则合并时打架。
- **返回内容要设上限**。我们约定"diff + 3 行结论"。否则三个子 Agent 各返回两千 token，父 Agent 上下文直接被冲垮。
- **有隐性依赖的任务别并行**。比如"先改 schema 再写迁移脚本"，这类保持串行。
- **触碰外部系统的动作要幂等**。发消息、部署这类操作，重试时不能产生重复副作用。
- **给每个子 Agent 打 trace ID**，日志按 ID 分组，否则并行排障是灾难。

# 可复用建议

- 任务书模板固定成五段式：目标 / 范围 / 约束 / 输出格式 / 完成标准。
- 返回契约（结构 + 长度上限）和任务书同样重要，前者决定汇总质量。
- 并发从 3 起步，跑稳了再加。
- 优先把**读多写少**的扇出类任务交给 subagent：调研、多模块 review、资料汇总。写密集且耦合高的改动，并行收益低、风险高。
- 从 2 个子 Agent 开始验证流程，确认汇总质量后再扩规模。

# 总结

subagent 编排的本质是两件事：**上下文隔离 + 并行吞吐**。并行程本身很简单，难点全在接口——自包含的任务书和克制的返回契约。把这两个文档习惯建立起来，多 Agent 并行才会从"演示"变成日常工具。
