## 背景

大模型本身无状态。每次新会话都得重新交代：语言习惯、代码风格、部署偏好。上下文窗口再大，历史里九成是流水，真正值得长期记住的偏好往往就几十条。

在 OpenClaw 这类支持 MCP 的框架里，我的结论是：记忆不要做成 RAG 外挂，而是做成独立的 MCP server，让 Agent 通过 `memory_save / memory_search / memory_forget` 三个工具自己管理。以下是我们迭代过两版、跑了几个月的方案。

## 问题：三种常见失败模式

1. **全塞 system prompt**：token 持续膨胀，旧偏好挤占新指令的信噪比。
2. **对聊天记录直接做 RAG**：检索回来的是对话片段，不是"用户偏好 TypeScript"这种可泛化陈述。
3. **让模型自由发挥写记忆**：格式漂移、无法更新、冲突越积越多，三个月后没人敢用。

## 做法：分层建模 + 读写分离

**数据模型**：一张扁平表（JSONL 或 SQLite 都行）：

```json
{ "id": "...", "type": "preference|fact|event|procedure",
  "content": "...", "tags": [], "confidence": 0.9,
  "source_session": "...", "updated_at": "...", "status": "active" }
```

关键是 `type` 和 `status`：preference/fact 长期保留，event 默认三个月衰减归档，`archived` 不参与检索。

**写入路径**：不在对话中途写——既拖延迟，又打断主任务。会话结束或空闲时，用一次独立的 LLM 调用提取候选记忆，过滤规则只有一条：只留可泛化的陈述（"我偏好 pnpm"留，"我今天吃了什么"不留）。入库前与现有记忆去重（tags 精确匹配 + 向量相似度），语义冲突时走显式确认覆盖，旧版本置 `superseded` 而非删除。

**读取路径**：每轮按 `score = 相关度 + 时间衰减 + 使用频次` 取 top 5~8 条注入 system prompt，硬预算控制在上下文的 10% 以内。超了就砍频次权重最低的，绝不为记忆挤占工具结果的空间。

## 踩坑点

- **中文短查询向量误召回**：embedding 对"部署方式"这类三四字查询基本失效。tags 关键词匹配做过滤，向量分只参与排序。
- **提取阈值太松**：第一版把聊天流水几乎全收进库，两周后检索质量崩掉。收紧到"能推断未来行为"才收。
- **偏好变更只增不改**：用户从 Vim 换到 VS Code，库里两条都在，模型随机听一条。冲突确认这步不能省。
- **注入预算失控**：条数上限必须写死在代码里，不能靠写在 prompt 里让模型自觉。
- **多用户隔离**：namespace 按 user_id 分；敏感信息只允许显式写入，禁止模型隐式提取。

## 可复用建议

1. 起步用一个 JSONL 文件 + 显式确认就够了，先跑通写入和删除，再谈检索排序。
2. 记忆必须人可读、可审计、可导出、可删除——用户要能直接打开文件看 Agent 记了什么。
3. 把"遗忘"做成一等公民：`memory_forget` 和衰减归档缺一不可。
4. 留一套对话回放集做回归：改提取 prompt 或排序权重后重放，diff 记忆库的变化。

## 总结

Agent 记忆的本质不是"要不要上向量库"，而是三件事：**写入策略**（提取什么、如何去重与冲突处理）、**读取策略**（注入多少、如何排序）、**生命周期**（衰减、遗忘、可审计）。先用最笨的方式跑通全链路，再按真实痛点逐层加东西——记忆系统和小步迭代的工程习惯，本来就是一回事。
