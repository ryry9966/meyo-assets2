## 背景

过去半年，我把一部分 Agent 调用从云端 API 迁到了本地。起因很实际：高频的文件整理、消息摘要、MCP 工具试跑，账单积累得比想象快；同时聊天记录和本地文件也不希望反复出网。先把定位说清楚——本地模型不是用来替代云端旗舰的，它接的是“高频、轻量、私密”的那一层调用。

## 问题

动手之前，有三个绕不开的问题：

1. **硬件够不够**。显存是硬约束，不是“电脑还行”就行。
2. **小模型工具调用可靠吗**。Agent 场景要求模型稳定输出可解析的 tool call，这比单纯聊天难得多。
3. **链路碎**。推理后端、API 格式、Agent 侧配置三方要对齐，任何一处的默认值不对，表现都会莫名其妙。

## 做法

**第一步：摸硬件底。** 我的经验表（按 Q4 量化估算）：

- 8GB 显存：7B–8B 模型，链路验证够用
- 12–16GB：14B 模型，或 Qwen3-30B-A3B 这类 MoE（激活参数少、速度快，性价比突出）
- 24GB：32B 模型，本地能上到的实用上限
- Mac 统一内存：按可用量的 60–70% 估算

**第二步：选推理后端。** 别纠结，先用 Ollama：一条命令拉模型，自带 OpenAI 兼容接口。等确认有吞吐需求（并发、批量任务）再换 vLLM 或 llama.cpp server。

**第三步：裸验证。** 接 Agent 之前先 curl 一下 `/v1/chat/completions`，确认基础对话和流式输出正常。这一步能省掉之后一半的排查时间。

**第四步：接入 OpenClaw 并测工具调用。** 新增一个本地 provider，baseUrl 指向 `http://127.0.0.1:11434/v1`。然后做关键动作：准备 5–6 个真实工具（读文件、查天气、跑一个 MCP server），让 agent 连续执行 20 轮任务，人工统计 tool call 成功率。低于 90% 就降模型档位或直接换模型，不要硬调 prompt。

**第五步：调参。** context 开到 16K 以上、生成超时放宽到 120s、temperature 压到 0.3 以下。这三个默认值最容易拖垮 agent 体验。

## 踩坑点

- **工具调用 JSON 破损**：7B 档位高发。优先选 tool calling 友好的模型家族，并在后端开 structured output / grammar 约束，比改 prompt 有效得多。
- **context 默认值陷阱**：不少后端默认 4K 上下文，长对话被悄悄截断，agent 表现“变笨”。排障先查这个，再怀疑模型本身。
- **显存只算模型不算 KV cache**：长上下文的 KV cache 能再吃掉 2–4GB，OOM 之前务必留余量，别把显存顶满。
- **量化不是免费的**：Q4 是我的底线，再往下指令遵循明显劣化，工具调用首当其冲。
- **别用通用跑分选型**：跑分高不代表会调工具。用自己的真实任务建 10 条用例的小评测集，比看榜单靠谱。

## 可复用建议

1. **先通链路再上大模型**：用最小模型把“部署 → 接口 → 工具调用”全流程跑通，之后升级只是换个模型名。
2. **本地 + 云端双路由**：日常高频走本地，复杂规划走云端，本地失败自动 fallback。这是目前我最推荐的架构。
3. **建立模型档案**：把每个模型的量化版本、ctx、超时、模板写进配置注释里，三个月后的你会感谢现在这行注释。
4. **固定冒烟测试**：3–5 个固定任务，每次升级前后各跑一遍，回归成本一分钟。

## 总结

本地部署的价值不在跑分，而在**可控**：数据不出门、调用不计费、实验不怕炸。路径其实很简单——定硬件预算，选对后端，用真实 agent 任务验收。链路一旦打通，换模型就是分钟级的事，剩下的只是持续挑一个更适合你任务的小模型。
