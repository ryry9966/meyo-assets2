## 背景

E2E 测试是大多数团队“知道该写但写不动”的那类资产：写一条要几十分钟，改一次 UI 就得跟着修，最后大家宁愿手点回归。我们在一个中等规模的前端项目里试了一种做法——不追求“AI 一键生成测试”，而是把跑在 OpenClaw 里的 agent（通过 MCP 接入工具）放进测试开发的日常工作流，让它承担“初稿生成 → 跑测试 → 读报错 → 自修”这段机械劳动。

## 问题

直接让模型“给我写个登录的 E2E”效果很差，主要有三类问题：

1. **选择器靠编**。模型没看过真实页面，`data-testid` 全是猜的，第一轮通过率接近零。
2. **断言空洞**。写出一堆 `toBeVisible()`，测试绿了但什么都没验证。
3. **只写 happy path**。错误分支和边界条件它不会主动覆盖。

根本原因是：一次生成是开环的。E2E 的难点恰恰在于“跑起来才知道对不对”。

## 做法

核心思路是把 agent 放进闭环，步骤如下：

1. **准备上下文**：把路由清单、现有测试的命名与结构规范、Playwright 配置放进 agent 工作目录。有条件的话导出一份页面 accessibility tree 快照，选择器命中率会明显提升。
2. **封装 MCP 工具**：写一个薄薄的 MCP server，只暴露两个工具——`run_spec`（执行 `npx playwright test --reporter=json`，返回结构化结果）和 `read_trace`（返回失败用例的 trace 摘要）。这比让 agent 自己拼 shell 命令可靠得多。
3. **单条生成循环**：一次只让 agent 生成一条 spec → 运行 → 失败就把报错和 trace 喂回去 → 修复重跑。设定最大迭代次数（我们用 5 次），防止循环失控烧 token。
4. **人工把关断言**：agent 修到全绿后，diff review 是必须的。重点看两件事：断言是否真的验证了业务语义、有没有为了变绿而删断言。这条红线要写进系统提示。
5. **入库归档**：通过的进主干；反复修不好的标记原因（环境数据缺失、组件未加 testid 等）转人工，形成 backlog。

## 踩坑点

- **选择器编造**：agent 会虚构不存在的 testid。给它页面快照，或在提示里强制“只用 `getByRole`”，能大幅缓解。
- **假修复**：最常见的“修复”是弱化断言或加大 `timeout`。review 时 diff 必看。
- **测试数据**：agent 不知道 seeding 逻辑，常写出依赖随机数据的用例。把 fixture 约定放进上下文。
- **上下文膨胀**：多轮失败报错堆在一起，agent 会开始胡修。每轮只保留最新一次报错。
- **flaky 被掩盖**：偶发失败建议让 agent 直接上报，而不是重试到绿。

## 可复用建议

- “能跑测试 + 能读结果”封装成 MCP 工具，是整套流程里性价比最高的一步。
- 为测试单独写一份规范文件放在 repo 里，让 agent 每次都读，比在提示词里反复强调有效。
- 先让 agent 列出“要覆盖的用户路径”，人确认后再生成，能省掉大量无效循环。
- 把 agent 的产出定位成“待 review 的初稿”，而不是成品。

## 总结

这套流程跑下来，一条 E2E 从手写约 40 分钟降到 10 分钟左右（含 review），覆盖的分支也更多。但价值不来自“全自动”，而来自把生成、运行、排错这个循环交出去，让人只做机器做不了的事：判断测试到底测没测到该测的东西。目前 agent 还不适合接管断言语义和 flaky 判定，这两块保持人工是底线。
