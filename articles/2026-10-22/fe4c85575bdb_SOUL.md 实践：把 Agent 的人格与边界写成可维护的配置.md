# 背景

OpenClaw 的工作区里，SOUL.md 是每次会话都会注入上下文的常驻文件，定位是“这个 Agent 是谁”。它和聊天时临时写的 system prompt 不一样：长期存在、跨会话生效、能进 git。既然是常驻配置，就该按配置的工程标准来维护，而不是当成随手写的心情文字。

# 问题

没认真写 SOUL.md 的 Agent，常见三种漂移：

1. **人格漂移**：Telegram 上简洁克制，换个渠道突然热情，同一周内语气都不稳定；
2. **边界漂移**：明明约定“发送前先确认”，过两天它自己就把消息发出去了；
3. **职责混叠**：人格、操作规程、临时记忆堆在一个文件里，行为异常时根本定位不了是哪段在起作用。

# 做法

我的 SOUL.md 稳定在 60 行左右，分五段：

1. **身份（3–5 行）**：一句话说清它是谁、服务谁。写“语气像资深同事：直接、克制、不堆形容词”，比写“聪明友善”有效得多——可执行的描述才有约束力。
2. **语气示例**：给一段符合预期的示例回复。模型对 example 的遵循度远高于对形容词的遵循度。
3. **红线（绝不做）**：逐条硬性列出，如“不主动给联系人发消息”“不执行删除类命令”。
4. **灰色地带（先问再做）**：如“单笔支出超阈值先确认”“新装 MCP 工具先报备”。
5. **渠道差异**：群聊少说话、私聊可展开；深夜请求的处理方式。

配套原则：SOUL.md 只放稳定的人格与边界；操作规程放 AGENTS.md；会变的事实（待办、项目状态）放 MEMORY.md。三层各管各的，出问题才能定位。

# 踩坑点

- **写太长**。300 行的 SOUL.md 会让关键边界被稀释，越靠后的规则越容易被忽略，控制在 100 行内。
- **规则冲突**。“凡事先确认”和“日常事务自主处理”并存，模型会随机挑一条执行。要么合并，要么按条件拆清楚。
- **把它当安全边界**。Prompt 层约束是软的，注入、长对话稀释都可能绕过。真正的硬限制落在权限层：敏感凭证不给、MCP server 侧做 allowlist、危险目录在配置里禁掉。人格文件是第一道，不是唯一一道。
- **只测正常路径**。我维护了约 10 条边界测试集（诱导乱花钱、代发情绪化消息、深夜做重大决定），每次改完跑一遍再提交。
- **留意自修改**。Agent 默认有工作区写权限，偶尔会顺手“优化”自己的 SOUL.md，git diff 一眼就能看到。

# 可复用建议

- SOUL.md 纳入 git，改动走 diff review，人格回退有据可查。
- 每条规则写完自问：我怎么验证 Agent 遵守了？答不上来的重写。
- 五段式骨架（身份 / 语气 / 红线 / 先问再做 / 渠道差异）可直接套用。

# 总结

SOUL.md 是工作区里成本最低、杠杆最高的一份配置。把它当代码对待：短、具体、可验证、有版本。人格靠示例立起来，边界靠 prompt 层加权限层双保险。写好它，Agent 行为的可预期性会上一个台阶。
