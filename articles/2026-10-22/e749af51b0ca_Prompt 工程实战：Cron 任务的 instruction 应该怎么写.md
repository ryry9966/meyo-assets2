## 背景

OpenClaw 的 cron / 定时任务用起来很简单：设一个触发时间，附一段 instruction，到点 agent 带着这段话冷启动一个会话去干活。听起来像聊天，写起来却不能像聊天。我陆续把日报、仓库巡检、监控摘要迁到了 cron 上，踩的坑几乎都出在 instruction 本身。

## 问题：cron 指令不是聊天消息

交互式对话里，用户可以随时纠偏；cron 是无人值守的，instruction 就是 agent 醒来时拿到的**全部上下文**。常见翻车方式：

- "帮我看看仓库有什么新情况" —— 没有数据源边界，agent 自由发挥扩大范围；
- 没写输出去向 —— 结果留在当次会话里，等于白跑；
- "今天 / 昨天"靠模型猜时区 —— 跨天后全错；
- 工具调用失败时模型脑补数据 —— 编一份看起来合理的假报告；
- 每天全量输出 —— 没人看，通知疲劳。

## 做法：六段式模板

我把 cron instruction 固定成六段，缺哪段补哪段：

1. **目标**：一句话说清任务为什么存在；
2. **数据源与边界**：点名用哪个 MCP 工具、查哪个仓库/路径，明确"只做这些"；
3. **时间锚点**：写死时区，相对时间以运行时刻为基准；
4. **步骤与决策规则**：按顺序列步骤，分支写成 if/then；
5. **输出契约**：写到哪个文件、发到哪个渠道、最多几行、什么格式；
6. **异常与静默**：失败重试几次、失败时说什么、无事发生时是否沉默。

对比示例——

改前：

> 每天早上帮我看看 my-org/my-repo 有什么新 issue，重要的告诉我。

改后：

```text
目标：汇总 my-org/my-repo 过去 24 小时新增的 open issue。
数据源：仅使用 github MCP 的 issue 列表接口，不做其他操作。
时间：以 Asia/Shanghai 为准，"过去 24 小时"从本次运行时刻往前推。
步骤：
1) 拉取 created > 昨天此刻的 issue；
2) 按 bug / feature / question 分桶；
3) 每条一行：编号、标题、标签、是否已有回复。
输出：明细写入 ~/reports/issues-<日期>.md；群里发不超过 10 行摘要；
bug 超过 3 条时摘要首行加 ⚠️。
异常：工具失败重试 1 次，仍失败只发一句"数据源不可用"，禁止编造数据。
静默：过去 24 小时无新 issue，则不发任何消息。
```

同样一个任务，改后第一次跑就稳定了。

## 踩坑点

- **写成对话语气**。"帮我看下"没有边界，模型会把"看看"扩成全量巡检；
- **没有静默条件**。没事也天天发，两周后你把通知静音，真出事反而没人看；
- **一个 cron 塞多个任务**。日报 + 巡检 + 提醒挤在一条指令里，输出契约就写不清，拆开；
- **指令里预设结果**。比如写"把 bug 数量报给我"，工具没跑通时模型会顺着预期编数字，必须显式写"禁止编造"；
- **上线即定型**。instruction 改一版要观察至少一周再调，cron 的坏样本是按天积累的。

## 可复用建议

- 把 cron instruction 当**交接单**而不是消息：接手的同事失忆、无人监督、按点上班，你写的东西要能让他独立完成并留下记录；
- 输出契约优先于一切措辞技巧：**去哪、什么格式、多长、失败说什么**，这四项写清楚，任务就成功了一半；
- "不做什么"和"做什么"同样重要：限定工具、限定范围、限定重试次数；
- 挂 cron 之前，先在交互会话里手动把同一段 instruction 完整跑一遍，确认工具可达、路径可写、输出格式符合预期。

## 总结

cron instruction 的质量，决定自动化是省心还是添乱。核心就一句：别把它当聊天，把它当成给一个没有上下文的新同事写的工作说明书——目标、边界、时间锚、步骤、输出契约、异常处理，六段写全，剩下的交给时间验证。
