## 背景

信息源越加越多，真正读进去的越来越少。我订阅的 30 多个技术博客和期刊源，每天产出 150+ 条目，大部分只扫一眼标题。RSS 本身依然是最好的订阅协议——开放、可自托管、没有算法插手——缺的只是有人替你先把水拧干。于是用 OpenClaw 的定时任务加一个摘要 Agent，搭了一条管线，每天早上固定时间推一份日报。

## 问题

直接把 RSS 原文喂给模型有三个痛点：一是全文太长，30 个源全量摘要成本撑不住；二是同一新闻常被多个源转载，重复严重；三是不少源只给摘要前两行，全文要单独抓。所以管线不能只是"RSS → LLM"，中间必须有清洗层。

## 做法

整体分四层：

1. **抓取**：OpenClaw cron 每 2 小时拉一次 feed，源列表放 YAML 配置里。原始条目入库（SQLite 就够），存 URL hash、发布时间、标题。
2. **清洗**：全文抓取直接复用现成的 fetch MCP server（自己写个小插件也行），用 readability 类解析抽正文，失败就降级用 RSS 自带摘要；URL hash 精确去重，标题再做相似度聚类，同组只留最早一条。
3. **摘要与排序**：每天 7 点触发汇总任务。先按源权重和关键词给条目打分，取 top 15 走 LLM 细摘要，要求结构化 JSON 输出（一句话要点 + 三条关键信息 + 值不值得点开），其余只进标题清单。全文放进 prompt，并明确要求"仅基于给定材料，不确定就标注无法确认"。
4. **分发**：渲染成 Markdown 日报，经 webhook 推到 Telegram。每条摘要都附原文链接——AI 是索引，不是替代。

Prompt 模板和 feed 配置都走配置文件，改源、改口味不动代码。

## 踩坑点

- **全文抓取被反爬**：并发拉 30 个源，第二天好几个站返回 403。加 UA、并发限到 2、同一域名间隔 3 秒，再配一层磁盘缓存，问题解决。
- **模型幻觉**：早期让它"总结这篇博客"，它会脑补结论。改成结构化输出 + 明确要求标注不确定项 + 温度 0.2 后基本稳定。
- **重复条目**：只做 URL 去重不够，转载文章 URL 不同。标题相似度超 0.8 就合并，宁可误杀。
- **cron 任务重叠**：一次抓取超时没退出，下一次又启动，重复入库。加了文件锁和单实例互斥。
- **编码坑**：个别老 feed 是 GBK 或带 HTML 实体，入库前统一转 UTF-8 并解码实体，否则乱码会传染到摘要输出。

## 可复用建议

- 先跑最小闭环：5 个源、每天一条日报，验证 prompt 和推送链路，再扩规模。
- 摘要质量要留痕：记录每次的 token 消耗、耗时、条目数，成本异常能第一时间发现。
- 每周复盘一次 feed：信噪比低的源果断退订，管线再好，垃圾进垃圾出。
- 分层处理比全量摘要便宜一个量级：打分过滤在前，LLM 在后。

## 总结

这条管线本质上是"抓取 → 清洗 → 压缩 → 分发"，LLM 只占最后一环。实际跑下来，数据清洗占了我 70% 的调试时间——决定下限的是工程，prompt 只决定上限。现在每天 15 条高质量摘要，10 分钟读完，比刷时间线踏实得多。配置文件和 prompt 模板整理好之后，后续会在社区发出来。
