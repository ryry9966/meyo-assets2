## 背景

我们社区每天都有几个固定动作：整理上游项目的 release notes、汇总群里反复出现的高频问题、转发值得一看的技术帖。这些活重复、机械，谁来干都觉得烦，拖更是常态。于是我用 OpenClaw 搭了一个发帖机器人，稳定跑了一个多月，本文记录架构取舍和踩过的坑。

## 问题

难点从来不是"能不能发出去"。调通一个 API 只需要十分钟，真正的问题是：

- 生成的内容准不准，尤其是版本号、链接这类硬信息；
- 会不会重复发帖、刷屏，变成社区公敌；
- 流水线半夜挂了，谁第一时间知道；
- 从"全自动"到"敢全自动"之间，怎么安全过渡。

## 做法

整体分五层，核心原则是**采集、生成、发布完全解耦**，靠数据库状态流转，不靠一个长函数串到底。

1. **采集层**：RSS + 站内 webhook 收集素材，落到 SQLite，每条带 `source_url` 和内容 hash，采集时就去重。
2. **生成层**：OpenClaw Agent 读取 pending 素材，按固定模板产出草稿（标题、摘要、标签），写入 drafts 表。
3. **发布层**：用 MCP 工具封装社区发帖 API，只做一件事：把指定 draft 发出去，返回 post_id。
4. **调度层**：cron 每 30 分钟跑一次采集，每天两个固定时间点触发生成 + 发布。
5. **审核层**：前期全部人工点通过；稳定后仅对高风险类型（含版本号、外链的）保留人工，其余自动放行。

## 踩坑点

**1. 第一天全自动就翻车。** 模型把版本号写错了。教训：凡是数字、链接、专名，必须从素材透传，绝不让模型凭"记忆"生成。改成模板占位符注入后，此类事故归零。

**2. 重试导致重复发帖。** 网络超时后重发，出现两条一模一样的帖子。解法是以 `draft_id` 为幂等键，发帖前先查 post_id 是否已存在，发布工具做成"先查后发"。

**3. MCP 调用没有超时。** 一个请求挂住，整条流水线卡死一晚。给所有 MCP 工具调用加 timeout，失败降级为跳过本轮并记日志，而不是无限重试。

**4. 内容同质化。** 跑两周后帖子越来越像一个模子。对策：固定 system prompt + 3 个少样本示例控制语气，每周人工抽样 10 条做质量回归。

**5. cron 时区坑。** 服务器是 UTC，本地晚八点发成了早上。调度统一用 UTC 存储，展示层再转本地时间。

## 可复用建议

- **幂等优先**：任何对外写操作都必须有幂等键，重试是必然发生的。
- **灰度上线**：全自动之前至少一周人工审核，并保留一键停用开关。
- **可观测**：失败时直接往群 webhook 推一条消息，比翻日志及时得多。
- **状态机驱动**：draft 走 `pending → approved → published / failed`，不要把状态存在内存里。

## 总结

机器人本体不难，难的是把"发帖"变成一个可控的工程问题：幂等、审核梯度、失败通知，三件事做扎实就稳了。一个月下来自动发布 200+ 帖，人工介入 3 次，全部是版本号类内容。下一步打算加素材打分，让低价值素材直接跳过生成，省 token 也省审核精力。代码不复杂，欢迎在社区里交流实现细节。
