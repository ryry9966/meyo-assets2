## 背景

我们的 Agent 最早只挂在 Telegram 群里，核心逻辑在 OpenClaw 侧，工具走 MCP，跑得很稳。后来另一个社区在 Discord 提了同样的需求。第一反应是再起一个实例，但很快意识到问题：两份 system prompt、两份记忆、两份工具配置，改一处漏一处，不到一个月两边行为就分叉了。于是改成消息路由：一个 Agent 核心，多个渠道适配器。

## 问题

拆开看是三件事：

1. **入站统一**：两个平台的消息结构、ID 体系、线程语义完全不同；
2. **会话归属**：同一个人在两边是两个身份，上下文要不要共享？
3. **出站适配**：长度上限、Markdown 方言、限流规则都不一样，直接把核心输出吐出去必然翻车。

## 做法

核心原则一句话：**渠道只做翻译，不做逻辑。**

**第一步，定义规范信封。** 所有入站消息归一化成统一结构：

```yaml
platform: telegram | discord
chat_id: "..."
user_id: "..."
thread_id: "..."   # Discord 线程 / Telegram 话题，可空
text: "..."
attachments: []
```

**第二步，薄适配器。** Telegram 用长轮询（内网部署省掉 webhook 配置），Discord 走 gateway。适配器只负责收消息 → 填信封 → 交给路由层，以及把出站内容渲染回平台格式。适配器里不允许出现业务判断。

**第三步，会话键隔离。** 默认用 `platform:chat_id` 做会话键，各群/频道独立上下文。没做跨平台身份合并——理论上可行，但需要可信的绑定流程，早期不值得投入。

**第四步，出站渲染器 + 队列。** 核心输出统一为标准 Markdown，渲染器按平台转换；每个平台独立出站队列，限流各自管理。

## 踩坑点

- **Telegram 的 MarkdownV2 转义是重灾区**，下划线、点、感叹号全要转。我们放弃 MarkdownV2，让核心输出受限 Markdown、渲染器生成 HTML，稳定得多。
- **分片切错位置**：Discord 上限 2000 字符，Telegram 4096。按长度硬切会把代码块拦腰斩断，改成优先按段落边界切，跨片手动闭合代码围栏。
- **限流是两套体系**：Discord 按频道有短窗口限制，Telegram 每聊天约 1 条/秒。没队列时，长回复连发几段立刻被限流，重试还会重复发送。出站队列 + 幂等 ID 是必须的。
- **交互组件不可移植**：inline keyboard 和 Discord 组件是两套东西，约定核心不产出组件，确认类操作用"回复 y 继续"顶替，丑但可靠。
- **媒体路径**：图片要分别走 Telegram 的 sendPhoto 和 Discord 的 attachment 上传，别假设一个 URL 两边都能拉到。
- **别拿正式群测试**：我们踩过一次，测试对话污染了长期记忆。之后严格用测试群 + 独立会话键。

## 可复用建议

1. **规范信封 + 平台编解码器**是通用模式。后来接第三个渠道时只写了一个适配器，核心零改动。
2. 把平台能力差异（长度、格式、是否支持组件）做成**配置表而不是 if-else**，渲染器读表工作。
3. 日志带上 `platform + chat_id + trace_id`，能从一条消息追到完整路由链路。
4. 每个适配器独立健康检查，单渠道故障单独重启，不要一个进程挂掉拖垮全部。

## 总结

结论很简单：Agent 核心保持平台无关，路由本质是适配器工程。前期多花一天定义信封和出站队列，换来每加一个渠道的成本趋近线性。这套结构跑了两个月，两边共享同一份记忆和工具集，行为一致，维护点只剩适配器目录。如果你也在多个 IM 上养同一个 Agent，建议从"信封 + 渲染器 + 队列"三件套起步，而不是先做身份打通这类高成本的事。
