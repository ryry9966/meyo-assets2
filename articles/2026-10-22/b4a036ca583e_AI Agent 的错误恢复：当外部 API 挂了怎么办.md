## 背景

Agent 系统的可靠性上限，往往不在模型本身，而在它调用的那些外部依赖：LLM 供应商限流、MCP 工具超时、第三方接口 5xx、网络抖动。传统后端容错有一整套成熟打法，但 Agent 场景多了一层麻烦——**失败信息会进入模型上下文**，模型可能把报错当数据去"解释"，甚至编造一个结果来兜底。这让简单的 API 故障演变成更难排查的行为异常。

## 问题：三类典型翻车现场

1. 工具返回原始堆栈 → 模型进入"道歉循环"，或直接臆造工具返回值，用户拿到假数据。
2. 收到 429 后立即重试 → 撞得更狠，配额烧光，任务彻底卡死。
3. 长流程跑到第 7 步依赖挂了 → 状态全丢，重启后从第 1 步重来。

## 做法：按层设防

**1. 超时先行。** 所有 HTTP / MCP 调用显式设置 connect 和 read timeout，禁止任何默认无限等待。一个挂起的 API 能拖死整个 Agent 主循环。

**2. 分类重试。** 先区分错误类型：429 / 5xx / 超时 / 网络错误可重试；400 / 401 / 403 / 404 不可重试，重试纯属浪费。可重试的用指数退避 + 随机抖动，尊重 `Retry-After`，设最大尝试次数。

**3. 错误结构化。** 不要把原始报错丢给模型。在工具层把失败翻译成结构化结果：

```json
{
  "ok": false,
  "kind": "rate_limited",
  "retryable": true,
  "retry_after_s": 30,
  "hint": "上游限流，建议稍后重试"
}
```

模型拿到的是**决策信息**，不是报错噪音。这一步对行为稳定性的提升最明显。

**4. 降级与兜底。** 关键工具准备 plan B：备用供应商、返回缓存旧数据（明确标注"数据可能过期"）、或把任务写入队列延后执行。注意兜底供应商的响应 schema 可能不一致，切换前先对齐字段。

**5. 熔断与断点续跑。** 连续 N 次失败后短路该工具一段时间，避免重试风暴；熔断状态放共享存储，多 worker 才不会各自为战。长流程按步骤持久化检查点，恢复时从断点继续。

**6. 诚实上报。** 系统提示词里写明：工具失败时如实告知用户当前状态和已尝试的动作，禁止编造结果。模型负责沟通，工程负责扛抖动，别让模型兼职容错。

## 踩坑点

- **在模型循环里重试**而不是在工具代码里：烧 token、行为不可复现。重试逻辑必须下沉到工具层。
- **一刀切重试**：对 401 重试五次，只会把锁定账号变成封号。
- **无抖动的固定退避**：多个 Agent 实例会形成同步重试风暴。
- **兜底切换是静默的**：下游解析悄悄坏掉，排查半天才发现数据来自备份源。
- **没有整体预算**：单任务应设 wall-clock 和 token 上限，防止"重试到天荒地老"。

## 可复用建议

- 给每个外部依赖包一层标准 client：超时 + 分类重试 + 结构化错误 + 指标埋点，Agent 代码只面向这个抽象。
- 上线前做故障演练：测试环境直接 kill 掉依赖，观察 Agent 的真实行为。
- 日志里带 correlation ID，重试链路才查得动。
- 把降级模式写进文档：哪些功能在依赖挂掉时仍可用，运维和用户都该知道。

## 总结

Agent 的错误恢复，核心思路不是"让模型聪明地处理失败"，而是**在工程层消化掉 90% 的故障**，剩下必须暴露给模型的，用结构化、可决策的形式呈现。超时、分类重试、结构化错误、熔断、检查点——这套组合拳不新，但在 Agent 场景里每一层都值得重新做一遍。依赖一定会挂，区别只是挂的时候你的 Agent 是在优雅降级，还是在编故事。
