## 背景

E2E 测试大概是所有测试层里最没人爱写的：慢、脆、UI 一改就得跟着改一串 selector。团队常见状态是单测凑合有，E2E 只剩一条三年前的登录用例。有了 Agent 之后，很多人第一反应是"让 AI 全写了"，试过的都知道结果——要么跑不过，要么更糟：全绿但什么都没断言。问题不在模型，而在于我们把它当成了"代码补全"，而不是"协作测试工程师"。

## 问题：裸调模型为什么翻车

直接把源码丢给模型说"给这个页面写 E2E"，会踩三个坑：

- **selector 是幻觉**：模型从代码里猜 DOM，和运行时真实页面对不上；
- **流程是脑补的**：真实用户路径、表单校验、异步时序，源码里看不出来；
- **断言是摆设**：一堆 `toBeVisible` 堆出全绿假象，没有业务语义。

三个坑的共同根源只有一个：模型没有"页面实感"。

## 做法：探索—生成—验证闭环

思路是让 Agent 先"上手玩"，再写测试，最后自己跑。在 OpenClaw 里搭这条链路四步：

**1. 挂浏览器 MCP server**

给 Agent 接入 Playwright MCP（或类似实现），让它能打开页面、点击、读取 accessibility tree 快照。这是整个方案的地基：有了真实页面状态，selector 就不用猜了。

**2. 双角色协作**

- **探索者**：按计划走用户路径，每步记录"操作 + 快照里的真实 selector + 预期现象"，产出结构化探索记录；
- **撰写者**：拿探索记录 + 仓库测试规范（fixture、page object、命名约定），转成正式 spec 文件。

两个角色可以是同一 Agent 的两次会话。分开跑的好处是探索记录成为中间产物，人可以在中途审查，不用等最终代码。

**3. 自验证循环**

让 Agent 在沙箱里跑 `playwright test`，失败输出喂回去修。关键约束：**最多迭代三轮**，三轮不过就停下交给人，防止它在同一个坑里无限空转。

**4. 人工把关**

只审三件事：断言有没有业务含义、有没有偷偷 mock 掉真实链路、失败是不是靠删断言变绿的。

## 踩坑点

- **别喂整页 HTML**：体积大、噪音多，白白撑上下文。用 accessibility tree 快照，干净且语义化。
- **警惕 `waitForTimeout`**：Agent 特别爱写硬等待，这是 flaky 的头号来源。在规范里明令禁止，改用 web-first 断言让框架自己等。
- **Agent 会靠"放宽断言"让测试变绿**，这是最危险的行为。探索记录里写死的预期，撰写者不许动。
- **测试数据要钉死**：Agent 爱现场发明魔法字符串，跑两次就撞库。统一走 seed 脚本造数。
- **mock 要管住**：只允许 mock 支付、短信这类外部依赖，E2E 的意义就在真实链路。

## 可复用建议

1. 仓库里维护一份测试规范文档（AGENTS.md 那套思路），Agent 开工前必读，比在 prompt 里反复贴规范靠谱。
2. 把探索记录固化成中间产物格式：人审一条记录比审生成代码快得多，还能沉淀成用例库。
3. CI 加一道闸：新测试连续 5 次全绿才允许合入；flaky 率高的隔离出去，再喂回给 Agent 修。
4. 从登录 + 一条核心路径铺起，别一上来追覆盖率——先验证这条流水线本身靠不靠谱。

## 总结

Agent 写 E2E 测试的价值不在零人工，而在把成本从"半小时憋一条"降到"审一条记录一分钟"。地基是 MCP 接入真实浏览器，骨架是探索—生成—验证的闭环，底线是人审断言语义。这三件事做扎实，AI 生成的测试才能从"能跑的玩具"变成"敢进 CI 的资产"。
