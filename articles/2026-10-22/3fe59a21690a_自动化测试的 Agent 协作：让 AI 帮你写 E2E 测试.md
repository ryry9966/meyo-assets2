## 背景

E2E 测试大概是每个团队“都知道该写、但一直欠着”的那类活：要搭环境、造数据、处理登录态，写完还得跟着 UI 改版持续维护。我们组最近把 OpenClaw 的 agent 编排和 Playwright MCP 接起来，让 AI 参与 E2E 用例生成。跑了几个月，覆盖率上来了，坑也踩了不少，这里做个记录。

## 问题：一次性生成为什么不行

最直觉的做法是把页面 URL 扔给模型：“帮我写这个流程的 E2E。”产物看着像样，直接跑基本过不了，就算过了也不敢信。常见问题三类：

- 选择器全是脆弱的 CSS 路径，一次改版全红；
- 断言很弱，只 assert 元素可见，等于没测业务；
- 不知道项目的 fixture、登录态和数据约定，自己发明一套。

根源是 agent 缺上下文、缺反馈回路。所以方案核心不是“换更强的模型”，而是补上这两块。

## 做法：三个角色的协作环

**1. 探索 agent。** 通过 Playwright MCP 走一遍目标流程，输出结构化的“流程笔记”：每步的动作、当时的可观察状态、可用的稳定定位（role、文本、data-testid）。关键是用 accessibility snapshot，不用截图——后面细说。

**2. 编写 agent。** 输入 = 流程笔记 + 仓库里的测试规范文件，输出 Playwright 用例草稿。一次只生成一个流程，别让它一口气写整个 suite。

**3. 执行-修复环。** 跑测试，失败信息回传给编写 agent，迭代上限 3 轮。旁边挂一个审查 agent，专查两件事：断言强度（有没有验证业务结果，而不只是“元素出现了”）和规范符合度。

**4. 人工把关。** 产物走正常 PR 流程，人主要审断言语义——这个测试到底在验证什么。这是 agent 替代不了的部分。

整体流程：探索 → 笔记 → 生成 → 执行 → 失败回传 → 修复 → 审查 → 人工 review。

## 踩坑点

- **截图驱动是大坑。** 又烧 token 又容易幻觉（按钮名都能编错），accessibility tree 又小又稳，优先级永远给 snapshot。
- **agent 会“改测试让它过”。** 修复环里如果给业务代码写权限，它倾向放宽断言而不是暴露 bug。我们的规矩：环内只许改测试文件，业务代码变更一律人来定。
- **登录态别让 agent 现场解决。** 提供 storageState fixture，否则每个用例都会长出一段各自发明的登录代码，又慢又脆。
- **规范文件里明令禁止 sleep 和固定等待**，用 auto-wait 和网络断言，否则 flaky 会慢慢积累。
- **迭代必须设上限。** 不设上限的修复环会把 token 烧穿，而且第 4 轮之后基本是在原地打转。

## 可复用建议

1. 把选择器策略（role > testid > 文本，禁 CSS 路径）和断言标准写进仓库内的 agent 规范文件，跟代码一起 review、一起演进。
2. 一次一个流程，小步生成，跑通再要下一个。
3. agent 产物不搞特殊通道，走同一套 PR / CI / 覆盖率统计。
4. 建一个“失败日记”：反复出现的 flaky 模式（时序、异步弹层、动画）沉淀回规范文件，让环越跑越准。

## 总结

跑下来的体会：agent 没有取代“理解测试”这件事，它取代的是打字。流程笔记补上下文，执行-修复环保真实性，规范文件保一致性；人的角色从写测试变成审断言。E2E 该有的工程纪律一样没少，只是产能换了个来源。
