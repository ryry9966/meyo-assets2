## 背景

Agent 的价值不在“会说”，而在“能做”。OpenClaw 的定位是把模型的规划能力接到真实系统上：查工单、发消息、触发部署。这中间的桥，就是工具调用（tool calling）和 MCP 这类协议。但真正对接过几个外部服务的人都知道，桥不好搭——能调通只是起点。

## 问题

常见的失控现场：

- 每接一个服务就复制粘贴一段胶水代码，鉴权、重试、日志各写一套；
- 模型传参全靠猜，同一个工具十次调用八次格式不对；
- 网络抖动重试三次，“下单”也跟着发了三遍；
- 一次返回 50KB 的 JSON，上下文直接被撑爆。

本质是：API 是给程序用的，Agent 调 API 时中间多了一层“会误解的自然语言”。对接设计必须同时服务两边。

## 做法

**1. 先选对接形态。** 服务有现成 MCP server 就优先复用；只有简单 REST 端点的，直接在 OpenClaw 插件里写 tool 更省事；需要跨多个 Agent 复用或维护会话状态的，才值得自己包一层 MCP server。别为了协议而协议。

**2. Schema 当合同写。** 参数描述是写给模型看的，不是写给编译器看的。能用枚举就不用自由字符串，必填/可选分清，返回值固定成 `success / data / error` 三段结构，下游解析才有据可依。

**3. 鉴权不进上下文。** key 放环境变量或 secret 管理，插件启动时读取。任何把 token 当工具参数传给模型的设计，都是在赌日志不外泄。

**4. 超时、重试、幂等三件套。** 超时按服务特性定（10–30 秒起步）；只对 429、5xx、网络错误重试，指数退避；一切写操作带幂等键，重试才不会变成重复发货。

**5. 响应裁剪。** 工具层做字段过滤和分页，把 50KB 压到模型真正需要的几百字节。宁可让 Agent 多调一次“翻页”工具，也别一次喂全量。

**6. 错误信息是写给模型的提示词。** 别抛堆栈，返回 `{"error": "rate_limited", "retry_after": 30}` 这种模型能理解并自行决策的结构化信息。

**7. 留观测埋点。** 每次调用记录工具名、入参摘要、耗时、状态码。出问题时，这是唯一能救你的东西。

## 踩坑点

- 工具描述含糊（比如只写“查询数据”）→ 模型乱传参。每个参数写清语义和示例值。
- 长任务同步等待 → 阻塞主循环。拆成“提交任务 + 查询状态”两个工具。
- 时区问题：让模型输出 ISO 8601 + 显式时区，插件层统一转换。
- 先接写操作再接读操作：顺序反了，调试成本翻倍。

## 可复用建议

- 一个工具只做一件事，粒度对齐“一次 API 调用”，而不是“一个业务流程”；
- 写操作提供 `dry_run` 参数，上线前先空跑；
- 工具命名带版本（如 `crm_query_v2`），schema 变更不静默；
- 把“重试 + 幂等 + 裁剪 + 结构化错误”抽成插件基类，新服务只填业务逻辑。

## 总结

对接外部服务的核心不是“能调通”，而是把不确定性封死在工具层：鉴权、重试、裁剪、错误格式都在插件里解决，暴露给模型的是一套语义清晰、行为可预期的最小接口。接口越“像人话”，行为越“像程序”，Agent 与 API 的握手就越稳。
