## 背景

Agent 的价值不在对话本身，而在它能不能替你动手：查工单、发消息、拉数据、触发部署。OpenClaw 的工具体系（内置工具 + MCP + 插件）给了它"动手"的能力，但对接外部服务这件事，不少人的第一版都写得比较随意——把 API 文档塞进系统提示词，或者让模型直接拼 HTTP 请求。跑起来看着能用，出了问题就很难查。

## 问题

让模型裸调 API，有几个结构性风险：

1. **密钥暴露**：key 放在提示词或会话上下文里，等于随日志和 transcript 一起泄漏；
2. **参数幻觉**：模型对字段名、枚举值的记忆不可靠，错一个参数就是一次线上事故；
3. **错误不可读**：接口返回一大坨 JSON error，模型要么忽略要么误判；
4. **权限失控**：模型能碰到删改接口，一次自动重试就可能造成重复写入。

## 做法

推荐加一层薄封装：**用 MCP server 把外部 API 包成少量、语义明确的工具**，OpenClaw 只面对工具，不面对原始 API。

1. **盘点操作面**：列出 Agent 真正需要的动作，比如"查订单状态""创建退款单"，通常 3～8 个就够，不要把整个 REST 面暴露出去；
2. **写薄封装**：Node 或 Python 起一个 MCP server，一个工具一个函数：入参用 JSON Schema 收窄，鉴权在函数内部从环境变量读取，出参做裁剪——只返回模型判断所需的字段；
3. **在 OpenClaw 侧注册**：配置挂载该 MCP server，重启会话确认工具列表加载成功。工具描述是写给模型看的，要讲清楚"什么时候用我、入参含义、失败代表什么"；
4. **灰度验证**：先只开只读工具，从会话日志观察模型的实际调用（参数对不对、频率高不高），再逐步放开写操作，写操作建议加人工确认；
5. **兜底**：每个工具设超时和重试上限，错误返回改成一句话摘要 + 错误码，别把原始堆栈丢给模型。

## 踩坑点

- **工具描述太敷衍**："调用某接口"这种描述会直接导致选错工具或乱填参数。描述本身就是提示词工程的一部分，值得反复打磨；
- **写操作没做幂等**：模型超时后会重试，POST 重复提交是真实发生过的。要么接口侧支持幂等键，要么封装层自己生成请求 ID；
- **工具数量爆炸**：十几个工具挂上去，选择准确率明显下降。按业务域拆多个 MCP server，按需挂载；
- **把原始密钥交给模型**：所有 secret 应止步于封装层，模型最多拿到"操作成功/失败"。

## 可复用建议

- 一个业务域一个 MCP server，工具命名用动词短语，语义自解释；
- 默认只读，写操作单独授权 + 确认；
- 封装层留好结构化日志（工具名、入参、耗时、结果码），排障全靠它；
- 加一个 `health_check` 类的只读工具，上线前先验证链路。

## 总结

对接外部服务的核心不是"让模型会调 API"，而是把 API 翻译成模型能稳定理解、且权限可控的工具面。OpenClaw + MCP 这套组合的价值就在于这层握手协议：鉴权、裁剪、幂等、限流都在封装层解决，模型只负责决策。先把这层做薄、做稳，Agent 的自动化才敢往生产推。
