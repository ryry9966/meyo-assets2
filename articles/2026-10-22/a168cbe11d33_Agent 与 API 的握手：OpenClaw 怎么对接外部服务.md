## 背景

Agent 在本地跑通任务之后，下一步几乎一定是"够到外部世界"：查工单、拉订单、写数据库、触发流水线。OpenClaw 里的 Agent 本身不直接碰网络，所有外部交互都要经过工具层——MCP server 或插件注册的 tool。这层握手做得好，Agent 像个靠谱的运维；做得差，它就是个会编造成功状态的随机数生成器。

## 问题

实际对接中反复出现四类坑：

1. 模型拿着模糊的 tool description 猜参数，调用成功率看运气；
2. API key 散落在脚本和对话里，一不小心就进日志；
3. 对方返回 429/500 时，Agent 拿到原始报错就开始脑补"操作成功"，或者无限重试；
4. 接口返回的大 JSON 直接塞进上下文，几轮对话就把窗口吃满，推理质量直线下降。

## 做法与步骤

**第一步：收敛入口。** 不要让 Agent 直接持有 HTTP 客户端。每个外部服务封装成一个 MCP server 或插件工具，一个工具对应一个语义动作（`create_ticket`、`query_order`），而不是留一个万能的 `http_request` 让模型自己拼 URL。语义化工具的 description 本质上就是给模型的 prompt，参数含义、单位、取值边界都要写清。

**第二步：统一鉴权。** 密钥走环境变量或 OpenClaw 的配置层，注入发生在 wrapper 内部。模型全程接触不到凭据，自然也不会把它复述出来。

**第三步：结构化错误。** 工具返回统一 schema：`{ok, code, message, retryable}`。重试逻辑放在 wrapper 里做指数退避，而不是让模型看到报错后自己决定"再试一次"——后者是事故的常见起点。

**第四步：裁剪响应。** wrapper 里做分页、字段过滤、超限截断，给模型的是提炼后的结果而非原始 payload。顺手加超时，别让一次卡死的请求拖住整个会话。

**第五步：给写操作上闸。** 涉及 POST/DELETE 的工具加 dry-run 参数和确认门槛。先只读，再放开幂等写，最后才给危险写，灰度上线。

## 踩坑点

- description 里写不写清楚"日期格式是 ISO8601""token 上限 512 字"，排错时间能差一倍。模糊描述是错误调用的头号来源。
- 让模型自己解读原始 HTTP 状态码，它会真诚地恭喜你"任务完成"。错误必须结构化后再交给模型。
- 重试没加退避，几轮就把对方限流甚至封禁。
- 调试日志记得脱敏，Authorization 头是最容易被顺手打出来的东西。

## 可复用建议

- 新接一个服务，按"只读 → 幂等写 → 危险写"三档逐步放权，每档稳定运行一段时间再升级。
- 上线前过一遍清单：超时？重试退避？错误 schema？响应裁剪？密钥隔离？dry-run？
- 可以留一个通用 HTTP 工具做兜底，但主力交互走语义化工具——两者的可测试性和安全性完全不在一个量级。

## 总结

Agent 与 API 的握手，难点从来不是"能不能调通"，而是把鉴权、错误、重试、裁剪这些工程细节从模型手里接过来，封进工具层。模型只负责决策，wrapper 负责可靠性。把这层做扎实，OpenClaw 的 Agent 才真正敢放进生产流程。
