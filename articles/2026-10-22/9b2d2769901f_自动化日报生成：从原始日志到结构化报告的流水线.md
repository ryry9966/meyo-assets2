## 背景

我们维护着十几个自托管服务和一批定时任务，日志散落在容器、裸机和网关层。此前日报是人工产出：一个人每天花三四十分钟 grep 日志、拼结论，质量还依赖当天状态。这个帖子的目标很朴素：**把"看日志"变成一条定时执行的流水线**，每天固定时间把结构化日报推到群里，人只负责复核。

## 问题

动手前明确了三个核心难点：

1. **原始日志噪声大**：多行堆栈、重复告警、格式不统一，直接喂给 LLM 既超上下文也浪费 token。
2. **LLM 不可信**：让它直接总结日志，数字经常被"脑补"，输出格式每次都漂移。
3. **日报要的是结论加证据**，不是流水账——纯摘要工具满足不了这个需求。

## 做法

流水线分五段，LLM 只占其中一段：

```
采集(cron/插件) → 清洗归一化 → 聚合去重 → Agent 摘要 → 校验 → 渲染推送
```

**1. 采集与归一化**。每个日志源写一个轻量 parser 插件，统一输出 JSON Line：`ts / source / level / event / metric`。多行堆栈在 parser 内折叠成一条，时区一律转 UTC 存储。

**2. 聚合去重**。相同 `event+level` 在时间窗口内聚合计数，只有 Top N 进入摘要；错误堆栈按首行指纹去重。这一步把几十万行压成几百条统计记录。

**3. Agent 摘要**。模型拿到的是聚合后的统计表加每类的代表样本，而不是原始日志。输出强制走 JSON schema：`summary / incidents[{title, level, count, evidence_ids}] / metrics / todo`。模型只负责归纳和表述，不负责计数。

**4. 校验层**。脚本核对模型输出里的每个数字是否与聚合结果一致（count、错误率），不一致就重试，重试两次仍失败则降级为纯模板报告。这一层是整条流水线可信度的底线，不能省。

**5. 渲染与推送**。schema 渲染成 Markdown 卡片，附原始日志的可回溯链接，webhook 推群，同时 JSON 归档到对象存储。

## 踩坑点

- **时区对不齐**：日志源混杂本地时间和 UTC，"昨天"的窗口切错了两天才发现。入口统一转 UTC，渲染时再转业务时区。
- **模型编数字**：即使给了数据，它也会"补充"没出现过的指标。schema 约束加"只允许引用 evidence_ids"双管齐下。
- **格式漂移**：偶尔漏字段或改字段名。JSON schema 强约束 + 解析失败自动重试，temperature 压到 0.2 以下。
- **日志洪峰**：某天错误暴涨百倍，摘要输入直接爆炸。聚合层限流 Top N，超限的统一标注为"异常规模事件"。
- **幂等**：任务重跑会重复推送。用日期加数据快照 hash 做幂等键，重跑只覆盖不重复发。

## 可复用建议

- 把流水线抽象成"归一化 → 聚合 → 摘要 → 校验 → 渲染"五段，每段独立可测。日报只是第一个应用，周报和告警复盘换个聚合窗口就能跑。
- MCP 工具设计的通用原则：**让模型接触聚合后的中间产物，而不是原始数据**。这同时解决成本和幻觉两个问题。
- 中间结果落盘。出问题时可以离线重放摘要环节，不必重跑采集。
- 校验层哪怕只做数字一致性检查，也能拦住大部分低级错误。

## 总结

这条流水线跑下来，核心体会是：**难点不在 LLM，而在它前后的工程**。分工要清晰——parser 管格式，聚合管规模，LLM 管语言，校验管可信。总投入大概几个晚上，每天省下半小时，更重要的是日报从"某个人的手工产物"变成了可审计、可重放、格式稳定的基础设施。这比省时间本身更有价值。
