## 背景

我维护着几台服务器和十来个仓库，日报长期靠人肉拼凑：翻 git log、翻告警群、翻部署记录，最后写出来的东西要么遗漏要么掺水。这周把这件事彻底交给了 OpenClaw 的定时任务加 MCP 工具链，跑了一周基本稳定，把整条流水线拆开记录一下。

## 问题

原始信息有三个特点：**散**（日志在 journald、git、CI 里各自为政）、**脏**（混着堆栈、心跳、重复告警）、**时序敏感**（必须严格框定"昨天 00:00 到今天 00:00"）。直接把原始日志塞给模型总结，会出现三类失败：上下文爆掉、模型对着噪音编故事、输出格式天天变。

所以核心思路是：**不要让模型碰原始日志，中间加一层确定性的归一化。**

## 做法

流水线分四步，前三步是纯脚本，只有第三步用到模型：

1. **触发。** 在 OpenClaw 配置里加一个每天 08:30 的 cron 任务，指向一个 shell 入口脚本。失败自动重试两次，仍失败就推一条裸告警，而不是沉默。
2. **采集与归一化。** 脚本并行拉取各数据源：按仓库聚合的 git log、CI 失败 job 列表、journald 里的 ERROR 条目、MCP 服务器返回的指标快照。全部压成同一种中间格式——带 `source`、`level`、`timestamp`、`summary` 字段的 JSONL，按天落盘，如 `data/2025-06-12.jsonl`。
3. **摘要与结构化。** Agent 只读这个 JSONL。prompt 是固定模板：今日完成 / 异常与风险 / 明日计划，并明确要求"数据里没有的不要写，每条结论后括号标注来源行号"。输出前自检四个一级标题是否齐全。
4. **投递与归档。** 产出写入 workspace 的 `reports/` 目录，按日期命名，同日重跑直接覆盖（幂等）；通过 webhook 推到群里，同时附文件路径方便回查。

## 踩坑点

- **时区坑：** 脚本里 UTC 和本地时区必须钉死。我第一版按 UTC 取日志，日报里的"昨天"实际是前天。
- **模型编造：** 早期 prompt 没写"无数据不写"，它把一条 INFO 心跳渲染成了"服务出现异常波动"。加上来源标注后编造基本绝迹，抽查也方便。
- **噪音淹没信号：** 告警按 `(source, message前80字符)` 聚合去重，重复一百次只留一条加计数，否则 token 全花在重复条目上。
- **敏感信息：** 日志里偶尔有 token，采集阶段用正则先脱敏，别指望模型帮你保密。
- **格式漂移：** 只靠 prompt 约束格式迟早漂。落盘前用一个十行的校验脚本检查标题结构，不合格就带着错误信息重试一次。

## 可复用建议

- **采集与摘要必须分离，中间产物落盘。** 出问题时先看 JSONL，就能判断是数据问题还是模型问题，比盯着 prompt 调参省时间得多。
- **先接一个数据源跑通全链路，再横向扩展。** 我第一版只有 git log，跑顺了才加日志和指标。
- **日报模板当契约维护。** 模板和 prompt 的改动进 git，享受和代码同等的评审待遇。
- **定时任务的可观测性比任务本身重要：** 跑没跑、跑了多久、产出了什么，都要有痕迹可查。

## 总结

这件事的关键不在于模型写得多好，而在于把"不确定的模型"圈在"确定的数据"之上：脚本负责采集、过滤、归一化和校验，模型只做它擅长的那一段压缩与措辞。整条流水线约 150 行脚本加一个模板 prompt，一晚上搭完，之后每天早上我只需要决定要不要转发。
