## 背景

我们团队每天要发一份研发日报：昨天做了什么、CI 挂了几次、线上有哪些告警、今天计划。内容本身不难，难的是"每天都要凑齐"。信息散在 git log、CI 平台、告警群和各个 Agent 的任务日志里，人工拼一份至少 20 分钟，还经常漏。

## 问题

第一版方案很直接：把所有原始日志丢给 LLM，让它"总结成日报"。跑了一周就暴露出三个问题：

1. **数字不可信**。commit 数、告警数经常被编造或四舍五入；
2. **格式漂移**。每天段落结构都不一样，收报告的人要重新适应；
3. **静默失败**。某天日志源挂了，报告照样"看起来很完整"，没人发现少了内容。

结论：不能把事实生产交给 LLM，它只适合做最后一步的语言组织。

## 做法

现在的流水线分五段，事实和语言严格分离：

1. **采集**。每个数据源一个独立的小脚本（或 MCP tool）：git 提交、CI 运行结果、告警记录、Agent 任务完成状态。各自输出统一的事件结构：`{type, source, ts, summary, link}`。
2. **归一化**。纯代码处理：统一时区、按 link 去重、过滤 merge commit 和 bot 提交。这步没有 LLM，输出是确定性的。
3. **汇总**。把结构化事件按类型分组，交给 LLM 做的只有两件事：给每组写一句人话摘要、把异常项排前面。温度设 0，输入输出都限定结构。
4. **渲染**。用固定 Markdown 模板拼装，段落标题写死，数字全部来自第 2 步的统计结果，不允许 LLM 生成任何数字。
5. **投递与校验**。用 OpenClaw 的 cron 定时触发，产出先过一遍 schema 校验（必填段落非空、数字字段存在），通过后推送到群；校验失败则降级为"原始事件附录 + 失败原因"，宁可难看也不能假完整。

## 踩坑点

- **时区**。日志源有 UTC 有本地时间，第一版日报里"昨天"和"今天"混在一起。所有时间戳在归一化层统一转换，别信上游。
- **忙天的 token 爆炸**。某天 CI 挂了 80 次，原始事件直接超上下文。改成按来源分块摘要、再合并，超长事件只保留计数和首尾两条。
- **"零数据"不等于"没跑"**。某天采集脚本权限过期，产出了一份全空报告。后来加了硬校验：任何数据源返回空都单独标注，而不是显示为 0。
- **报告越长越没人看**。模板收敛到正文 30 行以内，细节全部放链接，日报只回答"有没有异常、进展到哪"。

## 可复用建议

- 把日报当 schema 设计，而不是当文档写。事件结构稳定了，下游随便换。
- 事实归代码，语言归模型。LLM 在流水线里出现的位置越靠后越安全。
- 每个采集器保持幂等、可单独重跑，失败只影响自己的分组。
- 模板改动留版本，出问题时至少能对比"上周的报告长什么样"。

## 总结

这套东西没有用任何高级技巧，核心就一条：让确定性代码负责"真"，让 LLM 负责"顺"。日报从每天 20 分钟降到 0，更重要的是它可信了——收报告的人开始真的读它，而不是默认它是凑数。同样的模式可以直接套到周报、值班交接、发布说明上。
