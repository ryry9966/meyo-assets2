## 背景

OpenClaw 的 heartbeat 本质是定时轮询：每隔固定间隔，框架给 Agent 发一条轻量 check-in 提示，Agent 读完任务清单（比如 `HEARTBEAT.md`）后自行决定"动手"还是"沉默"。这套机制简单可靠，但跑一段时间后常见两种抱怨：要么 token 花在大量空转上，要么真正的事件（监控告警、邮件到达、CI 失败）要等十几分钟才被处理。这时候就该认真聊聊轮询和推送的取舍了。

## 问题：两种唤醒方式，各有隐性成本

**轮询的隐性成本是"空转"**：绝大多数心跳周期里没有事可做，但每次唤醒都有固定开销——上下文注入、模型推理、日志写入。间隔调小，费用线性上涨；间隔调大，响应延迟不可控。

**推送的隐性成本是"基建"**：你需要一个能被外部系统够到的入口（webhook、消息通道、常驻进程），还要处理鉴权、重试、并发。事件没来时它几乎零成本，但每接一种新事件源，就要多接一根线。

一句话概括：轮询买的是"最终一定会被处理"，推送买的是"此刻立刻被处理"。

## 做法：按任务性质分流

**第一步，把任务分类。** "巡检类"任务（每天检查订阅、整理摘要、确认证书到期）适合心跳；"反应类"任务（告警触发、有人 @ 你、文件上传完成）适合推送。分类错了，后面怎么调参都难受。

**第二步，把心跳做薄。** 三件事：间隔按任务容忍度设置，巡检类 30–60 分钟足够，别默认开 5 分钟；心跳携带的指令保持极短，详细清单放在文件里让 Agent 按需读，而不是塞进每次心跳的 prompt；要求 Agent 无事时只回一个固定短标记，方便统计空转率。

**第三步，让事件自己叫醒 Agent。** 优先复用现有通道：webhook 插件、精确到分钟的 cron、或者一个十几行的中转脚本——事件到达时直接调用 Agent 的 CLI/接口注入一条消息。关键是中转层要做幂等：带上事件 ID，重试不会导致重复执行。

**第四步，混合兜底。** 生产上最稳的形态是"推送为主、心跳兜底"：推送负责实时性，心跳每隔较长时间做一次对账——有没有漏掉的事件、有没有卡住的任务。

## 踩坑点

- 心跳间隔设得过猛：一天几千次空转唤醒，账单先告诉你错了。
- 心跳 prompt 里塞完整任务清单：每次唤醒都背着大上下文跑，成本翻倍。
- webhook 直接打进 Agent 会话：并发事件叠加导致会话竞争，轻则消息乱序，重则任务互相覆盖，中间必须加队列或锁。
- 推送重试没有幂等键：一次告警触发三次执行，同一件事被做了三遍。
- 心跳和长任务撞车：Agent 正在跑 20 分钟的长活，心跳又排队注入新指令，越积越多。

## 可复用建议

1. 先跑一周"记录模式"：每次心跳只记录"做了/没做"，根据空转率反推合理间隔。
2. 一切推送入口默认幂等，事件 ID 是底线。
3. 心跳负责发现异常，发现后转为推送通知自己——别让心跳本身承担实时性预期。
4. 新事件源先走中转脚本验证，跑稳了再固化成插件。

## 总结

轮询和推送不是二选一，而是两种不同的支付方式：轮询用固定成本买确定性，推送用建设成本买即时性。把任务按性质分流，心跳做薄、推送做稳、再加一层兜底对账，大部分个人自动化场景就能在成本和响应速度之间拿到一个舒服的平衡。
