## 背景

OpenClaw 的 agent 是常驻进程，但不会一直"醒着"。任务来源基本分两类：定时巡检类（每小时看一眼日历、每天清一次收件箱），和事件触发类（git push 了、监控报警了、有人 @ 了机器人）。heartbeat 是内置的轮询机制：agent 按固定间隔醒来，读一遍 HEARTBEAT.md，决定要不要干活，默认半小时一跳，间隔可调。

常见的问题是两个极端：有人把所有任务都塞给 heartbeat，也有人全走 webhook 推送，两种做法都要付代价。

## 问题

选错机制的典型症状：

- **轮询当推送用**：把"磁盘满了要立刻通知我"写进 HEARTBEAT.md，最坏要等一个完整间隔才被发现，事故窗口就是间隔本身。
- **推送当轮询用**：为"每天巡检一次"搭一整套 webhook + 定时器 + 消息队列，链路比任务本身还复杂，事件丢了还没兜底。
- **隐性成本**：heartbeat 每次醒来都触发一次 LLM 调用，15 分钟间隔的 agent 一天就是近百次调用，大部分在回答"无事可做"。

## 做法

我的原则是**推送为主、心跳兜底**，分四步落地：

1. **任务分类**。按两个维度盘点半自动化任务：对延迟是否敏感（秒级 vs 小时级）、事件源是否可控（自己写的脚本/服务 vs 外部系统）。延迟敏感且源可控 → 推送；纯状态巡检 → 轮询。
2. **轮询侧做减法**。HEARTBEAT.md 保持极简，只放真正需要周期检查的事；巡检类任务写清判断条件，让 agent 能快速判定"无事可做"。间隔按任务容忍度设，别一刀切。
3. **推送侧做幂等**。用 cron、自动化工具或自建 webhook 把事件作为消息投进会话，每条事件带唯一键（commit hash、告警 ID），agent 侧按键去重。
4. **心跳做对账**。保留一个低频 heartbeat（如每小时），职责只有两个：确认推送通道还活着、补漏掉的事件。这就是 reconciliation 思路。

## 踩坑点

- **心跳烧 token**：HEARTBEAT.md 堆了几十条待办，agent 每次醒来都认真读一遍。解法：内容瘦身，能确定性判断的（文件是否存在、时间是否到）交给外部脚本预处理。
- **推送无确认**：webhook 发出去就不管，网关重启期间的事件直接丢。至少本地落盘，再用心跳对账兜底。
- **双通道重复触发**：推送和心跳同时命中同一任务，agent 干两遍。所有任务必须有幂等键，这是底线。
- **心跳污染上下文**：心跳输出全量写进主会话历史，几轮下来全是"无事可做"。心跳日志单独存放，只把需要行动的结果写回。

## 可复用建议

- 一句话判断：**事件找得到源头就用推送，找不到源头或只是状态检查就用轮询，丢了会出事的任务两个都要**。
- 心跳间隔 = 任务能容忍的最大延迟，不是越小越好。
- 任何任务进入 agent 前，先定幂等键，再选触发方式。

## 总结

轮询和推送不是二选一，而是分工：推送负责时效，心跳负责兜底。heartbeat 的价值不在"万能触发器"，而在于它是唯一不依赖外部条件、一定会醒来的机制——把最关键的对账交给它，其余交给更合适的通道。
