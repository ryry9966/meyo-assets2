## 背景

OpenClaw 跑起来的 Agent 任务其实很杂：规划拆解、工具调用、长文摘要、结构化抽取、日志巡检……早期我们图省事，所有任务都打到同一个云端强模型上，一个月 token 账单很难看；后来一刀切全换本地模型，又在复杂规划任务上翻车。多模型路由不是省钱技巧，而是把「任务难度—模型能力—成本/隐私」对齐的工程问题。

## 问题

单一模型路由有三个典型矛盾：

1. 云端强模型贵，而且内部日志、含敏感字段的上下文都被送了出去；
2. 本地小模型便宜、数据不出机器，但多步规划和复杂工具调用的成功率明显下降；
3. 失败重试不区分来源，本地模型失败后拿云端模型兜底，延迟翻倍，还把路由问题掩盖了。

## 做法

我们的路由层分四步落地：

**1. 先盘点任务。** 给 Agent 里每类调用打标：`planning / tool-call / extract / summarize / classify`，写进任务 metadata，路由规则才有挂靠点。

**2. 按类分配模型档位。** 原则是「能力下限对齐任务难度」：

- 规划、多步工具编排、代码生成 → 云端强模型；
- 抽取、分类、摘要、格式转换 → 本地 7B~14B（我们用 Ollama 起的 Qwen 系）；
- 含用户隐私或内部数据的上下文 → 一律本地，哪怕质量略降。

**3. fallback 显式声明**，不靠全局重试：

```yaml
routes:
  - match: { task: extract }
    primary: local/qwen2.5-14b
    fallback: cloud/gpt-4o-mini   # 明确写出，可审计
  - match: { task: planning }
    primary: cloud/gpt-4o
    fallback: null                # 规划失败直接报错，不静默降级
```

**4. 每次 routing 决策写日志**：任务类型、命中规则、实际模型、耗时、是否触发 fallback。跑一周后回看日志，规则基本就稳了。

## 踩坑点

- **别信本地模型的 schema 遵循率。** 复杂 JSON Schema 的 function calling，本地小模型经常漏字段、加字段。我们的做法是让它输出宽松 JSON，后接一层校验修复，再把修复率纳入监控。
- **上下文窗口对不齐。** 云端 128k、本地只开到 16k，长会话路由到本地会静默截断，表现为「模型突然变笨」。路由层要做长度预检，超限直接改道。
- **fallback 别配成环，也别对 planning 类任务静默降级。** 规划被小模型接手后，后面每一步都在放大错误，宁可报错让人介入。
- **采样参数要跟着模型走。** 照抄云端的 temperature 到本地模型，输出发散，抽取任务错误率肉眼可见地涨。

## 可复用建议

- 经验法则：面向用户的第一跳、不可逆操作前的决策用强模型；后台批量、可校验、有重试余地的任务用本地模型。
- 路由规则要可审计：所有 fallback 显式写出来，拒绝隐式降级。
- 用「任务级成功率」而不是「模型级 benchmark」评估档位——同一个抽取任务让候选模型各跑一周再定。
- 配置里模型用引用不写死，换模型不动规则，给本地模型留升级位。

## 总结

多模型路由的价值不在「省了多少 token」，而在于让每类任务有清晰的成本、延迟和隐私边界。先打标、再分档、显式 fallback、持续看日志——这套流程不绑定任何具体模型，模型换代时规则可以原样沿用。
