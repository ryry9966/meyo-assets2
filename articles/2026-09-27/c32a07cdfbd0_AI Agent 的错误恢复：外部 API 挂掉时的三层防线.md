## 背景

Agent 的可靠性瓶颈往往不在模型，而在外部依赖。一条典型的自动化链路里，LLM 调用、MCP 工具、第三方 SaaS API 串在一起，任何一环抖动都会传导到最终结果。传统后端有成熟的重试和熔断方案，但 Agent 场景多了一层麻烦：**失败会被模型"消化"掉，变成一段看似合理的幻觉输出**。

## 三个典型问题

1. **静默失败**。工具抛错后返回空字符串或裸异常文本，模型把它当普通上下文，编一个答案继续跑，用户拿到的是错的。
2. **重试风暴**。遇到 429/503 立即重试，Agent 循环本身就是放大器，一次任务能打出几十个请求，配额瞬间烧完。
3. **部分成功不可恢复**。长流程跑到第 5 步挂掉，整体重跑既浪费，还可能重复执行写操作。

## 做法：三层防线

**第一层：封装内做传输级重试。** 在 MCP 工具 / 插件代码里做指数退避加抖动（如 1s/2s/4s ± 20%），只重试 429、500、502、503、504 和超时；有 `Retry-After` 头就听它的。4xx 参数错误重试没有意义，直接上抛。重试逻辑放在封装层，不要写进 system prompt——让模型自己决定"重试几次"是最不可控的方案。

**第二层：返回结构化错误契约。** 所有工具统一格式：

```json
{
  "ok": false,
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "hint": "上游检索服务超时，可稍后重试或改用备用检索工具"
}
```

关键是 `retryable` 和 `hint`：模型据此区分"该等"还是"该换路线"，而不是去解析一段堆栈。错误描述控制在一两句话，避免污染上下文窗口。

**第三层：规划层做降级与断点。**

- **降级路径**：主 API 挂了切备用 provider，或返回缓存数据并显式标注 `stale: true`，别让模型和用户以为拿到了新数据。
- **断点续跑**：每个完成步骤落盘 checkpoint，写操作带幂等键（任务 ID + 步骤号），恢复时跳过已完成步骤。
- **熔断**：同一 API 连续失败 N 次后标记不健康，冷却 60 秒内不再调用，直接走降级。

## 踩坑点

- 非幂等的 POST 别盲目重试，先补幂等键，否则可能重复下单、重复发送。
- 重试预算按"任务"设（如整任务上限 6 次），不要按单次调用设，长链任务的成本会失控。
- 别把完整 traceback 喂给模型，截取关键错误即可，堆栈越长幻觉概率越高。
- 上线前专门测失败路径：在 dev 环境故意停掉依赖 API，看 Agent 是走降级还是开始编故事。

## 可复用建议

- 给所有工具定一套统一错误 schema，写进团队的插件开发规范。
- "哪些错可重试、重试几次"固化在封装层，prompt 只描述策略意图。
- 把依赖健康状态暴露给规划层，让 Agent 在任务开始前就能避开已知故障的服务。

## 总结

外部 API 挂掉不是异常分支，而是 Agent 的常态输入。核心原则一条：**把失败做成结构化的、模型可理解的一等输出**——重试交给封装层，降级决策交给规划层，状态恢复靠 checkpoint 和幂等键。做到这三件事，Agent 才能从"一碰就碎"变成"坏了能绕"。
