## 背景

Agent 本身只会"想"，真正干活靠外部服务：查数据库、发消息、调第三方 REST 接口。在 OpenClaw 里这条链路主要有三种接法：MCP server、原生插件，以及最朴素的 HTTP 工具。选哪种，取决于服务的形态和你愿意维护多少胶水代码。

## 问题

实际对接时，大部分失败不在"能不能调通"，而在工程细节：

- 鉴权散落在配置甚至提示词里，泄漏风险高；
- 没有超时和重试策略，一个慢接口拖死整轮对话；
- 返回体太大，把上下文窗口吃穿；
- 接口偶发 429/5xx，Agent 拿到错误后开始瞎编。

## 做法

以对接一个内部 REST 服务为例，我一般按四步走：

**1. 先用 MCP 跑通最小闭环。** 社区已有现成的 MCP server（fetch、postgres 之类），先本地起一个，在 OpenClaw 的配置里注册，验证鉴权与参数格式：

```json
{
  "mcpServers": {
    "internal-api": {
      "command": "npx",
      "args": ["-y", "@internal/mcp-wrapper"],
      "env": { "API_KEY": "${INTERNAL_API_KEY}" }
    }
  }
}
```

MCP 的价值在于工具描述、输入 schema、返回结构都有协议约定，Agent 的调用成功率明显高于裸 prompt 猜接口。

**2. 收敛工具面。** 不要把服务的 30 个端点全暴露，只留 Agent 真正需要的 3~5 个，每个工具的 description 写清楚"什么时候该用我"。工具越少，选错率越低。

**3. 包一层薄适配。** 用一个小函数包住真实调用：注入鉴权头、强制 timeout（比如 10s）、对 429 做一两次退避重试、把大响应裁剪或摘要后再返回。这层是整条链路里性价比最高的代码。

**4. 稳定后沉到插件里。** MCP 适合探索期和跨项目复用；形态确定后写成 OpenClaw 插件，把配置、权限、日志统一管理。

## 踩坑点

- **API key 出现在模型可见的地方。** 用环境变量或 secret 引用，别写进提示词、全局配置或工具返回值。
- **description 太模糊。** "查询数据"不如"按工单 ID 查询售后工单状态，返回状态和更新时间"。
- **忽略幂等性。** 重试 + 非幂等接口 = 重复下单。写操作要么带幂等键，要么关闭自动重试。
- **返回值直接塞 JSON 原文。** 先裁字段、再限条数，超长给摘要，上下文是稀缺资源。
- **没有熔断。** 外部服务挂了会拖垮整个 agent loop，连续失败 N 次后短时间内直接拒调，比反复撞墙好。

## 可复用建议

- 每个外部服务维护一份"工具卡片"：用途、鉴权方式、超时、限流、已知坑，交接和迁移时省一半时间。
- 鉴权、超时、重试、截断四件事统一在一层处理，不要散落在各工具里各写一遍。
- 上线前用固定的几条测试 prompt 回归一遍：Agent 是否选对了工具、参数是否拼对。

## 总结

对接外部服务的本质，是给 Agent 一份诚实、边界清晰的工具说明书。MCP 解决协议层，插件解决工程层，而真正决定稳定性的，往往是那层不起眼的适配代码。
