## 背景

我们社区每周要发一期「本周动态」：汇总仓库更新、精选讨论、活动预告。此前靠人工整理，耗时且经常延期。于是我基于 OpenClaw 搭了一个发帖机器人：定时拉数据、生成草稿、人工确认后自动发布。跑了两个月，发帖准时率从约 60% 提到基本 100%。这里记录架构设计和踩过的坑。

## 整体架构

分三层：

1. **调度层**：cron 触发 OpenClaw 定时任务（每周一 09:00），只传任务 ID，不直接执行逻辑，方便手动补跑。
2. **执行层（Agent + MCP）**：Agent 调用一组 MCP 工具——`fetch_github_releases`、`fetch_rss`、`fetch_forum_hot_topics`——拿到结构化数据后按模板生成 Markdown 草稿，写入草稿存储。
3. **发布层**：独立小脚本轮询草稿队列，草稿被标记为 approved 后调用社区 API 发帖，回写 post_id。

关键取舍是**生成与发布解耦**：Agent 只产出草稿，不直接发帖。发布动作由无 LLM 参与的确定性脚本完成，保证可回滚、可审计。

## 实施步骤

1. 写三个 MCP tool，输入输出全部用 JSON schema 约束，工具内部做分页和截断。
2. 在 OpenClaw 中定义 agent 系统提示：角色、输出模板、禁止编造（每个条目必须附来源链接，拿不到来源就丢弃）。
3. 草稿落库（SQLite 足够），字段包含 `content_hash`、`status`、`generated_at`。
4. 发布脚本校验 hash 未重复、status=approved 才调 API；失败重试三次并告警。
5. 接一个简易审核命令：预览草稿，一键 approve / reject。

## 踩坑点

- **跑通当天就放开自动发布，结果同一期发了两遍。** 原因是 cron 重试叠加。修复：以「期号 + 内容 hash」做幂等键，发布前查重。
- **MCP 工具把 release notes 原文整段塞进上下文，token 爆了，模型开始自由发挥。** 修复：工具层先做摘要和字段裁剪，只把「标题 + 变更类型 + 链接」交给模型。原则：**返回给模型的信息要为下游任务裁剪过**，不要透传原始数据。
- **格式漂移**：提示词里写「按社区格式」，两周后输出开始混入客套话。修复：格式硬编码为代码模板，模型只填充变量，不决定结构。
- **凭证静默过期**：社区 API token 两周失效，机器人无声失败。修复：发布脚本对 401 显式告警，不吞异常。
- **幻觉链接**：即便要求附来源，偶尔仍编造 URL。修复：发布前校验所有链接可访问且在域名白名单内，失败条目自动剔除并在草稿顶部标注。

## 可复用建议

- 凡是「AI 产出 → 对外发布」，中间加一道人审闸门，成本极低，收益极高。
- 幂等键 + 内容 hash 是定时任务的保命符，先做这个再加自动化。
- 上下文是稀缺资源：裁剪放在工具层，不要靠提示词求模型「长话短说」。
- LLM 只负责生成，不做状态变更；发布、删除等副作用交给确定性代码。
- 日志记下 agent 的中间输出（工具调用参数、草稿 diff），排障时比看最终帖子有用得多。

## 总结

机器人本身不复杂，复杂的是把 LLM 放进「会对外产生后果」的流程时所需的工程约束：幂等、审核、校验、可观测。OpenClaw + MCP 让接入新数据源变成写一个 tool 的事，但工具边界和权限设计仍要自己把关。下一步计划把审核从命令行挪到社区私信，用对话式确认替代脚本命令。
