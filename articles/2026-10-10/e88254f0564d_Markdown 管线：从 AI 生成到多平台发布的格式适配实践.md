## 背景

在 OpenClaw 的工作流里，让 Agent 产出技术稿件已经很常见：调研、写作、改稿都能交给模型跑。但真正卡住“最后一公里”的往往不是内容质量，而是格式——同一份 Markdown，发到不同平台，呈现效果各不相同，手工排版又费时间。

## 问题

- 公众号不认 Markdown，只收带内联样式的 HTML；知乎、掘金等平台对 Markdown 子集的支持也不一致。
- AI 生成的 Markdown 本身就不规范：标题跳级、嵌套列表缩进错乱、代码块语言标记缺失。
- 图片链接是重灾区：Agent 引用的临时 URL 会过期，各平台对外链图片的防盗链、转存策略也不同。
- 表格、脚注、任务列表、数学公式这些扩展语法，各平台支持度参差不齐。

## 做法：单源 + 适配器

思路很简单：AI 只负责产出一份**规范化的源 Markdown**，格式适配交给管线，不写进 prompt。

**1. 规范化。** Agent 输出先过一遍 lint（挑十几条 markdownlint 规则即可），强制标题不跳级、列表缩进统一、frontmatter 剥离成元数据。这一步用 remark 在 AST 层处理，比正则可靠得多。

**2. 资产处理。** 管线把所有图片下载到本地缓存，按内容 hash 命名，再按目标平台上传到对应图床或平台存储，回写 URL。链接重写同样在 AST 层做。

**3. 按平台变换。** 维护一份平台能力矩阵配置（是否支持表格/公式/脚注/HTML），管线据此启用或禁用变换插件。不支持的部分降级：过宽表格转图片、公式服务端渲染成 SVG、脚注改成文末列表。需要内联样式的目标（如公众号），用 markdown-it 出 HTML 后注入内联 CSS，代码高亮直接烘焙成 style 属性。

**4. 校验与发布。** 变换后做两个检查：渲染快照对比（防止变换破坏结构）和图片可达性探测。发布动作封装成 MCP tool 或插件，Agent 可以调用，但默认 dry-run，人审 diff 后才真正推送。

## 踩坑点

- **别用正则做结构变换。** 嵌套列表、表格这类结构用正则迟早出事，remark/rehype 的 AST 变换是底线。
- **AI 爱混排 HTML**（`<br>`、`<b>` 之类），会在下游渲染器里炸出意外行为，规范化阶段要统一剥离或转写。
- 公众号对代码块里的 `<`、`>`、引号转义非常敏感，烘焙内联样式时必须逐字符处理。
- hash 命名方便图床去重，但同图多平台上传有时间差，回写前先比对平台返回的 URL。
- 降级策略别全自动：表格转图片这类有损变换，至少留一个确认点。

## 可复用建议

- 平台能力矩阵做成配置而非硬编码，新平台只加一份配置 + 一个适配器。
- 源 Markdown 是唯一事实来源，任何平台特有的写法都放进适配器，不污染源文件。
- 每步产物落盘（`normalize.md` / `assets.json` / `wechat.html`），出错可从任意一步重放。
- 发布类 MCP tool 必须有 dry-run 和人工闸门：Agent 负责“备好”，人负责“按下发送”。

## 总结

格式适配本质上是一个编译问题：源语言是规范化的 Markdown，目标平台是不同方言，管线就是编译器。把适配逻辑从 prompt 里挪出来，交给确定性的代码，Agent 输出质量和发布稳定性都会上一个台阶。这套管线在我这边跑了几十篇稿件，最大的收益是：改样式只改适配器，内容一行不动。欢迎交流你们的目标平台配置。
