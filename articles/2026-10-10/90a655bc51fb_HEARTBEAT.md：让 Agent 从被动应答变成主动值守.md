## 背景

大多数 Agent 的交互模式是「你问它答」。但部署在常驻环境里的 Agent（比如挂在服务器上的 OpenClaw 网关）其实能做更多：定时醒来、看一眼待办清单、自己判断要不要打扰你。HEARTBEAT.md 就是这个机制的载体——一张放在工作区的常驻清单，心跳调度器按固定间隔唤醒 Agent，Agent 读完清单后决定执行动作还是继续沉默。

## 问题

没有心跳机制时的典型尴尬：你让 Agent「帮我盯着磁盘空间」，它回复好的，然后就没有然后了——因为它只在被提问时才思考。反过来，靠人肉定时去问，又会带来消息轰炸和无意义的 token 消耗。核心矛盾是：**如何让 Agent 在正确时机主动出手，其余时间闭嘴。**

## 做法

1. **确认心跳已启用。** 检查配置中的心跳间隔（默认 30 分钟，可通过 `HEARTBEAT_INTERVAL_SECS` 或 `agents.defaults.heartbeat.every` 调整）。
2. **在工作区根目录创建 `HEARTBEAT.md`**，例如 `~/.openclaw/workspace/HEARTBEAT.md`。
3. **用「条件 → 动作 → 沉默规则」三段式写清单项**，每项一行：

```markdown
- 磁盘：检查根分区使用率，超过 85% 时通知我，否则 HEARTBEAT_OK
- 邮件：有白名单发件人的未读邮件时给摘要，否则 HEARTBEAT_OK
- 证书：检查 example.com 剩余有效期，少于 14 天时提醒，否则 HEARTBEAT_OK
```

4. **调试期把间隔临时调到 60 秒**，看日志确认每拍行为和误报率，可接受后再调回默认值。

关键约定：Agent 判断无事可做时输出 `HEARTBEAT_OK`，这一拍的结果不会推送给你——这是整个机制不沦为骚扰源的前提。

## 踩坑点

- **清单写太长**：整个文件每拍都会注入上下文，控制在 30 行以内比较稳，重任务挪去 cron。
- **条件模糊**：「帮我看看有什么新东西」这种写法会导致每次心跳都汇报一遍。条件必须可判定、带明确阈值。
- **漏写沉默规则**：不写 `HEARTBEAT_OK` 兜底，Agent 可能每拍都礼貌性回话，频道瞬间变聊天室。
- **用心跳做定时任务**：心跳的语义是「有空看一眼」，不是闹钟。每天 9 点的日报请用 cron/session 定时，心跳只负责状态型巡检。
- **间隔压太小**：分钟级心跳先算 token 成本，30 分钟是合理起点。

## 可复用建议

- 把 `HEARTBEAT.md` 纳入 git 管理，改动可回溯、可评审。
- 三类高价值场景：**状态巡检**（磁盘/证书/进程）、**消息聚合**（邮件/PR/issue 摘要）、**轻量提醒**（基于状态而非时刻）。
- 每一项都坚持「触发条件 + 动作 + 否则沉默」格式，团队里任何人接手都能看懂。
- 心跳管「模糊时机的轻判断」，cron 管「精确时刻的重任务」——两者搭配使用，而不是互相替代。

## 总结

HEARTBEAT.md 的价值不在技术复杂度，而在交互模式的转变：Agent 从「问答机」变成「值班员」。写好它的诀窍恰恰是克制——条件明确、动作轻量、默认沉默。清单维护得当，主动性才会是助力而不是噪音。
