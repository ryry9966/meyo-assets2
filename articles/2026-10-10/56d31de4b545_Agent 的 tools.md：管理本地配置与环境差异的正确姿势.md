## 背景

OpenClaw 这类常驻 Agent 的上下文，是靠工作区里的几个 Markdown 文件拼出来的：`AGENTS.md` 管行为约束，`USER.md` 管个人偏好，`TOOLS.md` 管"这台机器怎么操作"。定位本该很清晰，但我帮朋友重装工作区时发现，多数人的 `TOOLS.md` 是个垃圾桶：路径、端口、部署命令、甚至"回复要简短"这种风格设定全塞在里面。换台机器，上下文直接错乱。

## 问题在哪

三个典型场景：

1. **多机复用**：同一份全局配置想在笔记本、家里小主机、VPS 上通用，但三台机器的服务名、路径、硬件、代理各不相同；
2. **重复探索**：不写清楚，Agent 每次干活都要现场 `ls`、`which`、试错，token 烧得快，结果还不稳定；
3. **误提交**：把内网地址、部署方式写进可同步的全局文件，推到仓库等于变相泄漏。

## 我的做法

**先分层。** 与机器无关的规则进 `AGENTS.md`，可以提交、可以多机同步；`TOOLS.md` 只放本机事实，默认不进版本库。跨机复用靠一个脱敏的 `tools.template.md` 模板，每台机器领走自己填。

**首次生成，Agent 盘点、人来审。** 让 Agent 扫描常驻服务、常用路径、部署脚本，起草初稿，然后逐条人工验证。这步不能省——Agent 写的东西"看起来很对"，但端口、服务名经常记岔。

**条目三要素。** 一条 = 一个任务 + 一条可执行命令 + 一个验证方式：

```markdown
## 常驻服务
- homebridge: `sudo systemctl restart homebridge`
  验证: `curl -s localhost:8581/status` 返回 ok

## 密钥索引
- DEPLOY_TOKEN: 用 `op read` 从 1Password 取，值不落盘
```

**维护闭环。** 命令失败且修复是持久性的，当场回写；每隔一阵让 Agent 逐条跑"验证"命令，失效条目直接删。把它当缓存对待：可重建、可失效，不是唯一真相源——真相源是这台机器本身。

## 踩坑点

- **密钥进上下文**：`TOOLS.md` 每轮都会注入上下文，可能被日志和缓存记录。只写"去哪取"，绝不写值本身。
- **过期条目**：Agent 对文件内容近乎盲信，端口换了文件没改，它会反复撞同一堵墙。每条带验证命令能大幅缓解。
- **职责混用**：性格和回复风格是 `AGENTS.md` 的事；`TOOLS.md` 只写环境事实。混了之后两边都难维护。
- **一份通吃多机**：不要。一台一份，哪怕内容重叠 70%，分节共用只会增加误读概率。
- **Agent 自改**：工作区默认可写，Agent 可能顺手"优化"掉你写的条目。建议在 `AGENTS.md` 里加一句"修改 `TOOLS.md` 前先征得确认"，或者干脆把工作区纳入 git，至少有回滚。

## 可复用建议

- 固定五节：workspace、常驻服务、常用命令、本机怪癖、密钥索引；
- 总量控制在 80 行内，高频上下文越长，指令遵循越稀释；
- 每条目保持"祈使句 + 一条命令 + 一个验证动作"的最小结构；
- 模板进仓库，真身留本地，跨机差异只体现在填充值上。

## 总结

`TOOLS.md` 的本质是给 Agent 的一页"本机说明书"。分层让它不背跨机包袱，条目化让它可验证，当缓存对待让它始终新鲜。做好这三件事，同一个 Agent 在笔记本和服务器上都能可靠干活，而不是每次都要重新认识一遍你的机器。
