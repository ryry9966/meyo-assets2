## 背景

Agent 跑了几个月后，OpenClaw 的 memory 目录会越积越多：对话结论、踩坑笔记、命令片段、各种 ID。`memory_recall` 是让助手"想起来"的关键工具。很多默认配置走语义检索——记忆切块、算 embedding、按余弦相似度召回。看起来很现代，用久了会撞上两类很典型的翻车。

## 问题

**翻车一：精确标识符搜不到。** 问"上次那个超时的订单号是多少"，向量库返回一堆"语义相近"的段落，唯独没有那串 ID——embedding 把数字和代号都抹平了。

**翻车二：全文搜索换个说法就哑火。** 当时记的是"pod crashloop"，三个月后搜"容器反复重启"，一条都出不来。

本质：语义搜索匹配**意思**，全文搜索匹配**字面**。而记忆里两类内容各占一半——结论、偏好是意思型的；ID、命令、报错原文、时间是字面型的。单选任何一路，必有一半场景瘸腿。

## 做法

两路召回 + 融合，步骤如下：

1. **入库**：记忆照旧写 markdown；写库时同步做两件事——切块后算 embedding 存向量索引；原文（含 ID、命令）写入 SQLite FTS5 表。
2. **查询**：`memory_recall` 收到 query 后并行跑两路，各取 top 20。
3. **融合**：用 RRF（Reciprocal Rank Fusion），`score = Σ 1/(60+rank)`。不用调权重，对两路分数量纲差异不敏感，几乎零成本。
4. **过滤**：旧记忆按时间衰减降权（不删除）；同一 memory 文件只保留最高分块，去重。
5. **回填**：最终 top 5–8 条连同**来源文件路径**一起给 LLM。路径很重要，agent 拿不准时可以自己去读原文。

这套东西做成一个小 MCP 工具或 workspace 脚本都行，量级不大，一个下午能落地。

## 踩坑点

- **FTS5 默认分词器对中文基本无效**：unicode61 按空格切，整段中文变成一个 token。可选 trigram 或 jieba 分词后入库，我们最后用 trigram——省事，且对"搜子串"场景友好。
- **切块粒度**：太碎丢上下文，太大稀释相似度。300–500 字 + 50 字 overlap 是个能跑的起点。
- **换 embedding 模型 = 全量重建索引**，维度和向量空间都变了。选型想在前面，别在线上换。
- **语义检索对"它觉得很像"的错误毫无自知**：专有名词、项目代号上经常自信地召回错的东西。这正是必须保留全文那一路的根本原因。
- **召回条数别贪多**：top-k 超过 15 条，上下文很快被记忆灌满，agent 反而开始编。5–8 条 + 来源路径，不够让它自己再调一次 recall。

## 可复用建议

- 默认就上 hybrid，别等翻车再改。RRF 融合的代码量大约二十行。
- 小规模（几千条记忆）用 SQLite FTS5 + 本地 embedding 足够，不必一上来就上向量数据库全家桶。
- recall 工具的入参设计成 `mode: auto / semantic / keyword`，让 agent 在"我要那串 ID"时能显式走 keyword。
- 建一个 20–30 条的评估集：一半意思型问题、一半字面型问题。每次改检索参数跑一遍，避免拍脑袋调优。

## 总结

语义搜索和全文搜索不是对手，是两路互补的信号。记忆里"意思"和"字面"各占一半，`memory_recall` 的工程目标不是选边站，而是：两条路都通、融合得便宜、单路挂了能回退。三句话，够你少踩一半的坑。
