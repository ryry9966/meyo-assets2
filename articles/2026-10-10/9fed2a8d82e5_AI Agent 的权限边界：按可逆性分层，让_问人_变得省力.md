## 背景

跑过一段时间 Agent 自动化的人都会遇到同一个问题：权限给少了，每一步都要人工确认，自动化退化成"人肉流水线"；权限给多了，一条错误的 shell 命令、一封发错的邮件，代价可能很高。OpenClaw 这类能挂 MCP 工具、插件和定时任务的 Agent，本质上是在替你"出手"，出手前要不要回头看你一眼，得有明确规则，不能靠感觉。

## 问题

常见做法是二元的：要么全放（信任模型），要么全问（每次工具调用弹一次确认）。两者都不对。真正需要的是一条连续的边界，而且这条边界不能靠模型"自己判断"——模型在长上下文里会被注入、会漂移，权限闸门必须是确定性的代码。

## 做法

我们按两个维度给动作分层：**可逆性**和**影响范围**。

- **L0 只读**：读文件、查询、搜索。直接放行。
- **L1 可逆写入**：工作区内的文件编辑、本地脚本产出。放行 + 全量审计日志。
- **L2 难撤销或出边界**：超出回收站语义的删除、对外发消息/邮件、花钱、调用有副作用的第三方 API。先出执行计划（dry-run），人工批准后执行，批准记录绑定计划哈希。
- **L3 高危**：生产凭证、批量删除、支付。默认拒绝，需要时白名单临时开启，并设定过期时间。

落地步骤：

1. 盘点所有调用面（内置工具 + MCP server + 插件），逐个打上 L0–L3 标签。
2. 在 harness 层实现闸门：模型输出"计划"，代码校验计划是否落在当前层级允许的范围内，不合法直接拒绝执行。
3. 设计省力的确认协议：展示 diff、计划、回滚方式，人工回复"批准 / 改 / 拒绝"三选一，而不是让人读一段自由文本再猜意图。
4. 每周翻一次审计日志：某工具连续两周零事故就降一级，出一次事故就升一级。

一条经验法则：**数据不出机器、动作可回滚 → 自己干；涉及钱、外部世界、不可逆 → 问人。**

## 踩坑点

- **确认疲劳**：问得太频繁，人会变成无脑点"批准"，这比不设闸门更危险。宁可合并成一次计划审批。
- **"只读"不等于无害**：读了密钥再放进一封外发邮件，就是泄漏。数据敏感度要单独作为一维，不能只看动作类型。
- **批准 ≠ 永久授权**：批准的是那份计划，不是这类操作。执行时要重新校验实际参数，防止批准后漂移。
- **工具描述会骗人**：MCP 工具返回的内容可能携带注入指令，闸门必须放代码里，模型的意见只能参考。
- **授权要过期**：临时开的高危权限忘了关，是最常见的事故来源。

## 可复用建议

- 默认拒绝一切花钱和出网有副作用的调用，再按需放行。
- 把"问人"设计得足够便宜：结构化计划 + 一键批准，人才会认真看。
- 优先做 dry-run 模式，而不是给每个工具加确认弹窗。
- 提升可逆性本身就是扩权：快照、回收站、先建分支再改，都等于把 L2 降成 L1。
- 授权记录带时间戳和过期时间，高危权限默认 24 小时失效。

## 总结

权限边界不是一个 prompt 技巧，而是一套工程决策：用可逆性和影响范围给动作分层，把闸门做进 harness 的确定性代码里，把"问人"设计成人愿意认真对待的低成本动作。Agent 的自主性不是配置出来的，是在干净的审计和可回滚的前提下，逐步挣出来的。
