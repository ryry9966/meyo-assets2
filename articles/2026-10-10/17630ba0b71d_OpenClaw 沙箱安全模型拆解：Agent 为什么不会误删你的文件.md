## 背景

让 Agent 干活，本质上是递给它一把 shell。OpenClaw 的 exec 和文件读写工具一旦接上，模型就具备了实际改动你磁盘的能力。社区里被问得最多的一句是：“让它整理下载目录，会不会把我照片删了？”这个问题值得认真回答，因为答案不在模型本身，而在沙箱的分层设计。

## 问题

LLM 的输出是非确定性的。哪怕 99% 的时候表现正常，一条被误解析的路径、一段被污染的上下文指令，都可能触发不可逆操作。常见的思路是“在提示词里叮嘱它小心”，但这只是行为约束，不是安全边界。工程上的结论只有一条：**安全靠架构，不靠自觉。**

## 做法：四层防线

**第一层：容器隔离。** OpenClaw 默认把 agent 的执行环境放进 Docker 容器，工具调用在容器内落地。宿主机文件系统对它默认不可见——不是“不敢删”，是“看不见”。

**第二层：最小挂载。** 只有显式配置的 workspace 会被 bind-mount 进容器，且可指定 `:ro` 只读。参考资料目录只读挂载，工作目录读写挂载，边界写在配置里，而不是指望模型自己理解。

**第三层：工具策略网关。** exec 类调用经过策略层过滤：deny list 拦截高危命令模式（`rm -rf`、`mkfs`、`dd` 等），写操作超出 workspace 范围时触发确认门，需人工放行。批量删除可以先 dry-run 输出计划，确认后再执行。

**第四层：快照兜底。** 批量文件操作前对 workspace 做快照，配合审计日志记录每次工具调用。就算前三层都失手，也能回滚。

## 踩坑点

1. **把 `$HOME` 整个挂进容器。** 图省事挂全目录，沙箱直接退化成装饰品。
2. **容器里挂了 Docker socket。** 拿到 docker.sock 等于把宿主机 root 递过去，一句 `-v /:/host` 就穿透了。
3. **只做命令正则匹配。** `rm -rf` 拦住了，但 `python -c "shutil.rmtree(...)"` 绕过去了。deny list 必须配合“workspace 外写操作需确认”这类路径级策略，不能只靠模式匹配。
4. **忽略符号链接。** workspace 里一个指向外部的软链，工具跟着 realpath 走就出去了，挂载前要清理或在策略层做路径归一化校验。
5. **分不清执行位置。** gateway 跑宿主机、agent 跑容器，部分插件工具默认在 gateway 侧执行，配置时要逐个确认落地环境。

## 可复用建议

- workspace 给“够用的最小目录”，而不是最大目录；
- 参考资料一律只读挂载；
- 每个会话独立 workspace，避免交叉污染；
- 上自动化流程前放一个金丝雀文件：故意诱导 agent 执行一条危险指令，确认被策略层拦住再信任它；
- 审计日志保留下来，出问题能复盘到具体某次工具调用。

## 总结

“Agent 不会误删文件”不是一个承诺，而是一组可验证的机制：容器隔离让它看不见，最小挂载让它够不着，策略网关让它动不了，快照让它可恢复。提示词约束只是锦上添花，边界一定要落在架构上。建议每个跑自动化的用户按这四层检查一遍自己的配置——十分钟的事，远比事后恢复数据便宜。
