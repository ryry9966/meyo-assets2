## 背景

Agent 的可靠性上限往往不取决于模型本身，而取决于它调用的那几个外部 API：搜索、支付、行情、自建 MCP 工具——任何一个挂掉，整条自动化链路就可能停摆。更麻烦的是，LLM 面对工具报错时的默认行为并不可靠：要么无限重试烧 token，要么干脆编一份结果继续往下走。下面整理一套可以直接落地的错误恢复做法。

## 三种典型故障模式

1. **重试风暴**：Agent 自己决定重试且没有上限，一次任务跑出几十次调用。
2. **幻觉兜底**：上游返回 500，模型“不想让用户失望”，虚构一份看似合理的数据。
3. **级联失败**：链路上某个非核心工具超时，整个 workflow 卡死或整体作废。

## 做法：四层防线

**第一层：重试放在工具封装层，不要交给 Agent。**
在 MCP server 或工具 wrapper 里做指数退避加抖动（如 1s/2s/4s，附随机偏移），上限 3 次。区分错误类型：429 尊重 `Retry-After`；5xx 和网络错误可重试；4xx 参数错误重试没有意义，直接失败。Agent 层只看最终结果——把重试决策交给 LLM 是最容易踩的坑。

**第二层：给模型返回结构化错误，而不是原始堆栈。**

```json
{"ok": false, "error": "UPSTREAM_TIMEOUT", "retryable": false, "hint": "搜索服务超时，可改用备选工具或跳过本步骤"}
```

`hint` 字段很关键：明确告诉模型“可以降级、跳过或换工具”，它就不会卡在原地，也不会瞎编。

**第三层：准备降级路径，并强制 Agent 显式声明。**
每个关键工具备好一档降级：备选 API、标注“非实时”的过期缓存、或跳过并在最终输出里说明“该步骤未完成”。系统提示里写死一条规则：任何降级必须在回复中告知用户，禁止静默兜底。

**第四层：写操作幂等，状态可恢复。**
下单、发消息这类写操作，重试前先带幂等键；长任务做检查点，恢复时从断点继续，而不是从头重跑。

## 踩坑点

- **对非幂等接口重试**：一次支付回调重试两遍，钱扣了两次。
- **降级 API 的 schema 不一致**：换了数据源但字段含义有差异，脏数据静默流入下游。
- **把失败响应写进缓存**：缓存层没区分错误和数据，故障期间所有请求都命中“错误缓存”。
- **超时设太长**：单工具 120 秒超时会阻塞主循环；快速失败、立刻进降级分支反而更稳。

## 可复用建议

- 所有工具统一错误信封格式，`retryable` 字段必填，Agent 的重试判断只依赖它。
- 每个工具独立配置重试策略（次数、超时、退避），别全局一套参数。
- 加一个轻量熔断：某工具连续失败 N 次后，本次运行内直接走降级，不再请求。
- 重试与降级全部落日志并带 trace id，事后复盘全靠它。
- 关键任务开跑前做一次 preflight 健康检查，几十毫秒换整场任务的确定性。

## 总结

Agent 的错误恢复本质是工程问题，不是提示词问题：重试、降级、幂等这些经典模式放进工具层，LLM 只需要在结构化错误面前做“继续、降级还是上报”的有限选择。把不确定性关进笼子，Agent 才敢上生产。
