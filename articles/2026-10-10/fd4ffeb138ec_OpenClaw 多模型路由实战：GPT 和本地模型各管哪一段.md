## 背景

OpenClaw 的一次典型 agent run 并不是一次调用，而是拆成几十个步骤：任务规划、工具选择、MCP 调用、结果摘要、代码改写。很多团队默认全走同一个旗舰 API 模型，账单和延迟都难看；也有团队为了省成本全切本地小模型，结果在多步工具编排上频繁翻车。多模型路由要解决的不是"选一个更好的模型"，而是"给每类步骤配一个够用的模型"。

## 问题

我们把一个日常数据处理 agent 拆开统计：约 70% 的 token 花在摘要、改写、格式校验这类低难度步骤上，真正需要推理能力的规划和跨文件代码生成只占 30%。全走 GPT 是浪费；全走本地 7B，工具调用格式错误率明显上升，重试反而更贵。另外部分步骤涉及内部数据，走云端需要额外的合规评估。

## 做法

1. **先做步骤分级**。按四个维度给 skill 打标：任务类型（规划 / 代码 / 摘要 / 分类）、上下文长度、是否含敏感数据、延迟要求。
2. **搭本地推理服务**。用 vLLM 或 Ollama 起 OpenAI 兼容 endpoint，OpenClaw 里作为独立 provider 配置，和云端模型共用一套调用链路。
3. **写路由规则**。我们的初始矩阵是：
   - 规划、多步工具编排、跨文件重构 → 云端旗舰模型；
   - 单函数改写、摘要、实体抽取、格式转换 → 本地模型；
   - 含内部数据的预处理步骤 → 强制本地。
4. **加 fallback 链**。本地输出连续两次校验失败自动回退云端，并把回退事件写日志，回头用来修路由表。

## 踩坑点

- **小模型的结构化输出不可信**。7B 级别调 MCP 工具时 JSON 常缺字段或类型错，必须在中间加一层 schema 校验加一次修复重试，否则错误会传导到下游。
- **上下文截断是隐形杀手**。本地模型 32k 上下文听着够用，但长会话里工具返回被静默截断后，agent 会基于残缺信息继续跑，这种错从日志里很难一眼看出。
- **本地不等于快**。显存不足触发 swap 时响应比 API 还慢，路由前先压测。
- **别忽略日志侧信道**。敏感步骤留在本地了，但 prompt 调试日志和缓存如果同步到云端存储，等于白路由。

## 可复用建议

- 维护一份"路由矩阵"文档：每类步骤用哪个模型、为什么，团队评审，不要个人拍脑袋。
- 打开按步骤的 token / 成本统计，用固定 task set 跑成功率和耗时对比，数据支撑切换决策。
- 把模型版本 pin 死。云端 API 曾静默更新，agent 的工具调用风格随之变化导致成功率下降，pin 版本能避免这类"无改动回归"。
- fallback 触发频率本身是信号：某类步骤频繁回退，说明它本来就不该路由给本地模型。

## 总结

多模型路由的价值不在省钱本身，而在于让每个步骤的可靠性和成本都可预期。先用数据把步骤分级，再配路由和校验兜底，最后靠观测持续修表。OpenClaw 的 provider 抽象足以支撑这套做法，缺的往往只是工程化的耐心。
