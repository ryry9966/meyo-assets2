## 背景

Agent 跑在本机时，真正决定它行为的不只是模型和提示词，还有本地环境：ffmpeg 装没装、Python 是 3.10 还是 3.12、docker compose 是插件还是独立二进制、某条构建链只在特定机器上可用。MCP 和插件解决了“工具怎么调用”，但“这台机器上有什么、怎么用、哪些不能用”目前没有统一的落点。我们的做法是用一个 tools.md 把这些信息显式声明出来，让 Agent 启动时读取，而不是靠模型猜。

## 问题

没有 tools.md 时常见三类事故：

1. Agent 假设工具存在，张口就是 `brew install`，那台机器其实是 Ubuntu；
2. 同一份提示词在本地和 CI 表现不一致，排查半天发现是 PATH 和 shell 差异；
3. 每换一台机器就在系统提示词里手工粘贴环境信息，越粘越长，还容易夹带密钥。

本质上，环境知识需要像代码一样版本化、分层、可审查，而不是散落在对话历史里。

## 做法

推荐三层结构，加载时合并，优先级为机器层 > 项目层 > 全局层：

- **全局层** `~/.config/openclaw/tools.md`：跨项目通用的机器事实，如包管理器、默认 shell、常用路径；
- **项目层** `tools.md`（进仓库）：项目依赖的工具链、启动命令、版本约束，走 PR 审查；
- **机器层** `tools.local.md`（gitignore）：本机覆盖项，比如“这台机器用 fnm 管理 Node，不要用 nvm”。

每个工具条目用统一 schema：用途、首选调用命令、版本或变体备注、禁止事项（如“不要加 sudo”）。写完做一次冒烟验证：让 Agent 复述它读到的工具清单，与 `which` 和实际版本对照，确认注入链路没有断。

## 踩坑点

1. **不要写任何密钥。** tools.md 会被整体送进模型上下文，写进去等于公开。只写环境变量名，值留在本机。
2. **写成事实，不要写成散文。** “我们一般用 pnpm”不如“包管理器：pnpm；禁止 npm install”。Agent 需要可执行陈述。
3. **条目腐化。** 工具卸载了文件没更新，Agent 会反复尝试失败调用。清理工具链后顺手核对，或写个脚本比对声明与实况。
4. **优先级没写清。** 两台机器行为不一致却无从排查，多半是层级冲突规则没定义。把优先级写进文件头部。
5. **贪多。** 超过两三百行就是提示词垃圾。只声明有歧义、易错、受限的内容，显然存在的不必写。

## 可复用建议

- 把 tools.md 当代码：进版本库、走 review，改工具链的 PR 必须同步改它；
- 文件末尾加一段“自检清单”，列出 Agent 可自行执行的验证命令，让它开机自检，而不是运行中途才发现环境不对；
- 团队内统一条目格式，解析稳定性会明显提升；
- CI 机器的 tools.md 用流水线探测环境后生成，保证与真实执行环境一致，不要手写。

## 总结

tools.md 解决的不是新问题，而是老问题的落点：环境差异应该被声明，而不是被模型猜。三层分层加统一 schema，搭建成本在一小时以内，换来的是 Agent 在任何一台机器上的行为可预期。它不优雅，但可靠——在这个阶段，可靠比优雅重要。
