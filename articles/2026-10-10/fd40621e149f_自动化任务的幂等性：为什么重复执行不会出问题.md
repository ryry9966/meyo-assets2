## 背景

在 OpenClaw 这类自动化体系里，“同一段逻辑被执行多次”不是异常，而是常态：网络超时后客户端重试、cron 到点时上一轮还没跑完、用户对结果不满意手动点重跑、Agent 在规划回路里对同一个工具连续调用两次。MCP 工具、插件、定时任务，都逃不开重复触发。

很多人的第一反应是“尽量避免重复”。但工程上更靠谱的假设是：**重复不可避免，要做的是让重复无害**。这就是幂等性——同一操作执行一次和执行 N 次，最终结果一致。

## 问题

不幂等的自动化任务，故障模式很固定：

- **追加型写入**：日志被 append 两遍，报表里出现重复行
- **创建型操作**：同一个 webhook 重投，创建了两个一模一样的工单
- **通知类副作用**：重试导致同一批用户收到两条消息
- **状态覆盖**：上一轮跑到一半，新一轮把中间态数据洗掉

Agent 场景还会放大这个问题：模型并不“记得”上一轮做过什么（上下文被压缩、会话重启），它看到任务未完成，就会理直气壮地再做一遍。指望 LLM 自己记住“我已经做过了”，是最不可靠的防线。

## 做法

按四层加固，从便宜到贵：

1. **区分读写**。只读操作天然幂等，不用管；把精力全部花在写操作上：创建、发送、修改、删除。
2. **给写操作加业务唯一键**。落库用 upsert 而不是 insert；对“日期+来源+目标”这类天然键加唯一约束。重复请求撞上约束，要么被吞掉，要么转为更新。
3. **用稳定的幂等键做前置去重**。在工具封装层（比如包一层的 MCP middleware）生成 key：任务 ID + 目标对象 + 时间窗口，执行前先查状态存储（一个 SQLite 表或 state 文件就够），已存在则直接返回上次结果。注意 key 必须在多次重试间稳定，不能每次执行重新生成。
4. **把副作用设计成声明式**。把“发送一条消息”改成“确保消息已发送”：先查目标状态，不存在才执行。配合状态机（pending → done），执行前先原子地占位或落标记，再执行副作用。

文件操作同理：写临时文件 + 原子 rename，整体覆盖而不是逐行 append。

## 踩坑点

- **check-then-act 竞态**：两个并发实例同时查到“未执行”，然后都执行。去重判断和状态写入必须原子，或用唯一约束兜底。
- **幂等键不稳定**：把时间戳或随机数编进 key，重试时 key 变了，去重形同虚设。key 的粒度要和你对“同一次任务”的定义严格一致。
- **多层重试叠加**：Agent 层重试一次、HTTP client 重试两次、队列又重投一次。要在最靠近副作用的那一层做去重，而不是只在最外层。
- **部分失败**：DB 写成功但通知失败，或反过来。把副作用拆开、各自保证幂等，别指望一个大事务罩住所有外部调用——罩不住的。
- **依赖第三方 API 的“隐含幂等”**：调用前先确认对方是否支持幂等键（很多支付/消息 API 支持），不支持就在自己这边先落凭证。

## 可复用建议

- 给所有写类 MCP 工具统一包一层幂等 middleware，key 规则全项目一致
- 工具设计优先提供 `ensure` / `create_if_not_exists` 语义，而不是裸的 create
- 每次副作用记一条日志：幂等键、时间、结果，出问题能对账
- 测试加一条硬性用例：所有定时任务在预发环境**连跑两遍**，对比结果 diff
- 状态存储宁可简陋（一个 SQLite），也要存在——别放在模型上下文里

## 总结

幂等性不是防止重复，而是承认重复必然发生之后，把系统设计成“重复也不出错”。做到这一步，“再跑一次”就从危险动作变成了最安全的恢复手段。对长期无人值守运行的自动化任务来说，这比任何花哨的重试策略都更值钱。
