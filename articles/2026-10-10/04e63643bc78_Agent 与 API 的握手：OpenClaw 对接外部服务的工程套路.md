# 背景

Agent 的能力上限，往往不取决于模型本身，而取决于它能触达哪些外部服务。查数据、发工单、调内部系统，本质都是同一件事：让模型把「意图」翻译成一次可靠的 API 调用，再把结果翻译回模型能理解的结构化数据。OpenClaw 里这条链路通常由工具调用或 MCP server 承担，但「能调通」和「能稳定跑」之间，差着好几层工程。

# 问题

我最近给 OpenClaw 对接几个外部服务时遇到的典型状况：

1. 模型生成的参数和 API 实际 schema 对不上，尤其是枚举值和日期格式；
2. 上游偶发超时、限流，Agent 收到一坨错误文本后开始自由发挥，甚至编造结果；
3. 密钥管理混乱——最初直接把 token 写进工具描述，日志里到处都是；
4. 重试没有幂等保障，一次「创建工单」的重试造出了三张单。

# 做法

后来我把对接流程收敛成固定五步：

**第一步，给每个 API 做薄封装，不把原始接口直接暴露给模型。** 封装层做三件事：参数校验（JSON Schema 或 pydantic）、错误归一化（把 4xx/5xx/超时统一转成 `{ok, error_code, message}`）、日志脱敏。

**第二步，工具描述既写给人看，也写给模型看。** description 里明确参数格式、单位、约束，比如「日期必须为 YYYY-MM-DD，UTC 时区」。枚举值直接列进 schema，比在描述里写一句「支持多种类型」可靠得多。

**第三步，认证统一走环境变量或密钥管理，由封装层读取。** 永远不通过工具入参传密钥——入参会进对话历史。

**第四步，超时与重试写死在封装层。** 读操作重试 2~3 次加指数退避；写操作要么服务端幂等（带 idempotency key），要么不自动重试，把失败原样返回、由上层决策。

**第五步，用 MCP 时把 server 当独立进程对待。** 每个工具有清晰的错误边界，server 崩溃要能被拉起，工具列表变更后记得让客户端刷新。

# 踩坑点

- **返回值太大**：把整个 JSON 丢回模型，几轮就把上下文撑爆。裁剪字段、只回关键结果，原始数据落盘给个引用。
- **工具太多**：十几个平铺工具，模型选择准确率明显下降。按场景分组、合并成少量粗粒度工具更稳。
- **错误信息太「友好」**：「请求失败，请稍后再试」对模型毫无帮助。把状态码、限流剩余额度、可行动建议塞进错误返回，模型才有自我纠正的余地。
- **只测 happy path**：专门构造 401、429、500、超时的 mock 用例，Agent 的降级行为才有保证。

# 可复用建议

- 封装层接口保持稳定，API 升级不动工具 schema；
- 每个工具带 `dry_run` 参数，接入期先观察不落库；
- 关键写操作记审计日志：谁、何时、什么参数、什么结果；
- 把错误返回当作「写给模型读的文档」来打磨。

# 总结

Agent 对接外部服务，核心不是「调通 API」，而是把不确定性封在封装层里：schema 校验挡住幻觉参数，归一化错误让模型可决策，幂等与重试策略保证副作用安全。这套套路做扎实之后，新接一个服务基本就是复制模板的事。有不同打法的欢迎在评论区交流。
