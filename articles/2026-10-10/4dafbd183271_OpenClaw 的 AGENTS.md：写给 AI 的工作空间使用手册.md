## 背景

OpenClaw 的 agent 每次会话开始都会读取工作区根目录下的 `AGENTS.md`，并把它注入系统上下文。这是你少数能稳定控制的“常驻指令位”——不是记忆检索，不是临时对话，是每次必读。

但很多人的 AGENTS.md 是从项目 README 改出来的，写完之后 agent 行为没有任何变化，于是得出“这文件没用”的结论。问题通常不在文件本身，而在写法。

## 问题

实际用下来，失效集中在三类：

1. **写成介绍文档**：讲愿景、讲架构，没有一条指令式规则。agent 读完只知道“这是个什么项目”，不知道“我该做什么不同的事”。
2. **写得太满**：三百行全塞进去，关键规则被稀释，上下文预算被低频信息吃掉。
3. **规则不可验证**：“保持简洁”“注意质量”这类表述，agent 执行起来等于没说。

## 做法

我的工作区模板分三段，总量控制在 60 行以内：

**第一段：身份与边界。** 用三档动词标注优先级：必须 / 禁止 / 先问。例如“对外发消息必须先给我看草稿”“禁止主动 git push”“批量删除文件前先问”。

**第二段：环境事实。** 写成可直接执行的命令，而不是描述：

```
测试：pytest tests/ -x
本地起服务：make dev（端口 7788）
```

**第三段：流程约定。** 回复语言、commit 规范、长任务先给计划再动手。

每条规则尽量写成“条件 → 动作”，例如：“改完 Python 代码后运行 pytest，有失败就不要提交”。

写完做两步验证：先让 agent 复述 AGENTS.md 要点，确认注入生效；再跑一次典型任务，确认行为真的变了。

## 踩坑点

- **把密钥写进去**。AGENTS.md 是常驻上下文，任何能读工作区的工具都可能把它带出去。密钥放环境变量，文件里只写“密钥用环境变量 X”。
- **和 SOUL.md / TOOLS.md 职责重叠**。身份描述进 SOUL.md，工具用法进 TOOLS.md，AGENTS.md 只放行为规则，否则两边改着改着就不一致。
- **绝对路径写死**。agent 换机器或换容器就崩，优先写相对路径和 make 目标。
- **改了不回归**。每次修改后都做“复述 + 典型任务”两步验证，否则你不知道改动的实际效果。
- **规则从不触发或总被违反**。前者直接删掉，后者要么改写法让它更具体，要么承认当前 agent 能力做不到——硬写只会浪费上下文。

## 可复用建议

- 三段式模板（边界 / 环境事实 / 流程约定）直接 fork 到新项目，10 分钟起步。
- 用行为数据审计手册：agent 经常问到、且 AGENTS.md 里能答上的条目保留；从来没被触发的条目删除。
- 低频细节下沉到 MEMORY.md 或按需读取的文件，AGENTS.md 只留高频、关键规则。
- 每条规则不超过一行，能用命令表达的不要用形容词。

## 总结

AGENTS.md 不是文档，是配置。像对待代码一样对待它：小、可验证、有回归、进版本控制。写它花的一小时，换的是之后每次会话省下的纠正成本——这是 agent 工作区里性价比最高的一个文件。
