## 背景

我们团队之前每天早上要花 20-30 分钟拼日报：翻 git 提交、看 CI 记录、扫一遍错误日志，再手动写成固定格式发群里。内容重复、格式漂移，关键异常还经常被噪音淹没。这个月我们把这件事交给 OpenClaw 的定时任务 + Agent 跑了，稳定运行两周多，这篇帖记录一下这条流水线的设计和踩过的坑。

## 问题

日报本身不难，难的是三点：

1. **数据源分散**：git log、CI 结果、服务错误日志各在一处，格式互不相同；
2. **汇总靠人肉判断**：哪些该报、哪些是重复报错、哪些值得 @人，全凭经验；
3. **输出必须稳定**：日报是每天要发的东西，格式乱、漏报、迟报都是事故。

直接把原始日志丢给大模型"帮我写个日报"看似可行，实际跑过就知道：上下文塞爆、费用高、每天输出结构还不一样。所以核心思路是——**确定性的工作交给代码，LLM 只做最后一步归纳**。

## 流水线设计

整条链路分四段，每段独立可测：

```
定时触发 → 采集 → 结构化 → Agent 汇总 → 校验 & 推送
```

**1. 触发与采集（代码）**。用 OpenClaw 的 cron 能力每天固定时间拉起一个会话，会话里只执行 shell 脚本：`git log --since=...`、CI API 拉取、`grep ERROR` 前一天的日志片段，结果落地成本地 JSON。如果数据源有现成 MCP 工具，这一段可以直接换成 MCP 调用，后面不变。

**2. 结构化（代码，不用 LLM）**。脚本把原始日志压成统一 schema：

```json
{ "source": "ci", "ts": "...", "level": "fail", "job": "build-api", "msg_hash": "a1b2c3" }
```

这里做两件事：按 `msg_hash` 去重并计数，丢弃 debug 级别。一天几千行日志压缩后通常只剩几十条。

**3. Agent 汇总（LLM）**。Agent 读入压缩后的 JSON，按提示词模板填固定字段：昨日概要、失败任务 TOP3、新增错误、待跟进项。提示词里明确要求"只基于输入数据，不推测"，输出必须是指定 JSON 结构。

**4. 校验与推送（代码）**。推送前用 JSON Schema 校验 LLM 输出，失败自动重试一次，仍失败就降级为纯数据表格推送，保证群里每天一定有东西。最后通过 webhook 发出，同时归档一份 Markdown 到仓库。

## 踩坑点

- **时区**：cron 默认 UTC，第一次跑出来的"昨日"其实是前天。给采集脚本显式传时区，并在报告里带上数据窗口起止时间。
- **LLM 输出漂移**：偶尔会在 JSON 里夹解释文字。加 schema 校验 + 重试后基本绝迹；重试的提示词要更"凶"，直接贴出校验错误。
- **静默失败**：最阴险的一种——报告正常发出，但数据源当天挂了，Agent 拿到空数据照样写了一篇"平稳运行"。后来加了新鲜度检查：采集到的最后一条时间戳距当前超过阈值，就在报告头部打警告。
- **敏感信息**：错误日志里偶现 token 和内网地址，推送前加了一道正则脱敏。

## 可复用建议

- 各阶段解耦，中间产物（结构化 JSON）落盘保存，报告可以随时离线重生成，不用重跑采集；
- 报告结构写死在模板里，LLM 只填值、不发明结构；
- 先单数据源跑一周、发给自己看，再扩多源、再发群；
- 去重和计数这类事永远在代码层做，LLM 数不准数。

## 总结

这套东西没有用到什么高深技术，价值在于**把人的判断固化成流水线，把 LLM 用在它擅长的归纳环节**。跑稳定之后，日报从每天 25 分钟降到每天看一眼。下一步计划把周报聚合接在同一条结构化数据上——中间产物存下来了，这是顺路的事。
