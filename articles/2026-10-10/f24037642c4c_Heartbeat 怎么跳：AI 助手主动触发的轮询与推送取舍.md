## 背景

Agent 做事分两种：用户开口才做（被动响应），以及没人说话也得做（主动触发）。后者就是 heartbeat 的领地——定时醒来，扫一眼任务清单，有事处理，没事继续睡。OpenClaw 的 heartbeat 属于这类：gateway 按间隔唤醒 agent，读 HEARTBEAT.md，没活儿就静默返回。

另一条路线是推送：外部事件（webhook、消息队列、cron 回调）直接把任务塞给 agent。两条路线各有拥趸，但真实项目里很少是非此即彼的。

## 问题

我在一个个人自动化项目里踩过三种典型情况：

1. **纯轮询的成本幻觉。** 5 分钟一次 heartbeat，每次唤醒都是一次完整 LLM 调用。一个月 wake 数千次，其中真正需要行动的不到 5%，token 账单比正常对话还高。
2. **纯推送的静默失效。** webhook 服务挂了或被限流，agent 就永远沉默——而你的告警链路本身也依赖推送，故障是自指的，没人知道出事了。
3. **心跳噪音。** agent 醒来后明明没事，还是回了句“一切正常”，把聊天窗口刷屏。

所以问题不是“选哪个”，而是怎么分层组合。

## 做法

我现在的结构是三层：

1. **预门禁（无 LLM）。** gateway 在真正唤醒 agent 前，先跑一段本地脚本：检查 HEARTBEAT.md 里各项的触发条件（文件 mtime、API 状态码、时间窗）。全部不满足就直接跳过本轮，零 token 消耗。
2. **推送通道（低延迟事件）。** 对延迟敏感的事——告警、新消息提醒——走 webhook 直接触发 agent，事件带幂等键防重复。
3. **低频兜底心跳（看门狗）。** 把心跳间隔从 5 分钟放宽到 30–60 分钟，只在预门禁通过、或到达“最小心跳周期”时才真正调用 LLM。它不再负责时效，只负责证明链路活着。

配套的一个关键细节：heartbeat 的唤醒提示词要压到最小——一份 checklist 加一条“无事则返回空”的约定，不要每次唤醒都塞完整对话上下文。

## 踩坑点

- **心跳与活跃会话冲突**：用户正在和 agent 对话时心跳插进来，抢上下文。要加“活跃会话抑制”，会话进行中延后心跳。
- **长任务重叠**：上一轮心跳任务没跑完，下一轮又醒了。必须加锁或跳过标记，否则状态文件会被并发写坏。
- **时区问题**：cron 和免打扰时段都按 UTC 配的，本想 23 点静默，实际是早上 7 点吵醒全家。上线前务必人工验证一次本地时间触发。
- **推送重试风暴**：发送端失败重试 3 次，agent 重复处理同一事件。幂等键必须落在 agent 侧持久化，不能只靠发送方自觉。

## 可复用建议

- **按事件分级决策**：秒级时效 → 推送；小时级 digest → 轮询；其余 → 兜底心跳。
- **监控一个比值**：wake 次数 / 有效动作次数。长期低于 10% 就该拉长间隔或收紧预门禁条件。
- **心跳本身就是健康指标**：记录 last_heartbeat_at 并做超时告警，哪怕推送链路全挂，它也能告诉你系统还活着。
- **HEARTBEAT.md 当配置用，别当日志用**：每次唤醒都要读它，写崩了会引发连锁失败，改动走版本控制。

## 总结

心跳是地板，推送是油门。先用最便宜的轮询把可靠性兜住，再对真正在乎延迟的事件加推送，中间用无 LLM 的预门禁把成本压下来。别追求一次到位的“完美调度”——先让心跳跳得安静、可观测、可关停，再谈智能化。
