## 背景

跑过一段时间 OpenClaw 的人都会遇到同一个问题：agent 大部分时间是"睡着的"。你不在场时它不会自己干活，除非有人叫醒它。叫醒方式无非两种：

- **轮询（heartbeat）**：按固定间隔唤醒，agent 醒来检查一遍待办，有事处理，没事继续睡。OpenClaw 里就是一个可配置的 interval，配合一份检查清单。
- **推送（push）**：外部事件直接打进来——GitHub webhook、监控告警、CI 回调、频道消息——事件到了才唤醒。

## 问题

两种方式单用都不舒服：

- **纯轮询**：延迟上限就是间隔。30 分钟的心跳，意味着最坏情况你晚知道半小时；而且每次醒来都要跑一遍 session，哪怕无事发生，token 照烧。间隔调小，成本和"没事也来烦你"的消息噪音同步上升。
- **纯推送**：延迟低、成本省，但前提是事件源都支持 webhook，且你的网关能被公网打到。家庭网络/NAT 后面还得架隧道；隧道断了、token 过期了，事件就静默丢了——你不会收到"我错过了什么"的通知。

## 做法

我的方案是混合：**能推的推，推不了的轮询，心跳做对账兜底**。

1. **先盘事件源**。支持 webhook 的（GitHub、监控、CI）全部走推送；只给轮询接口的（部分内网 API、RSS、本地文件变化）留给心跳。
2. **推送侧加去重和 TTL**。同一个事件 key（来源 + 事件 ID）进网关先查重，避免上游重试导致 agent 跑两遍、给用户发两条消息。推送带 TTL，过期事件直接丢，由心跳兜底补上。
3. **心跳降级为"对账"角色**。默认间隔放宽到 30–60 分钟，唤醒后先跑一段廉价预检脚本：比对上次处理的位点/时间戳，没新东西就直接结束，不进 LLM。有差异才拉起完整 session 补漏。
4. **心跳清单文件化**。要检查什么写进一份 markdown 清单，agent 醒来读它。清单进 git，行为可审计、可回滚。

## 踩坑点

- **空转心跳烧 token**：最早期每次心跳都起完整 session，一天下来成本明显高于推送事件本身。加了预检短路径后才降下来。
- **webhook 没做幂等**：上游重试一次，agent 重复执行、消息重复推送，用户体感是"它疯了"。去重 key 是必须的。
- **推送静默失败**：隧道断了一下午，没有任何报错。后来靠心跳对账 + 一条"距上次成功投递超过 N 分钟"的自检才兜住。
- **心跳任务没加锁**：某次检查跑得久，下一个 tick 又进来了，两个 session 并发改同一份状态。加互斥锁 + 超时强杀解决。
- **消息噪音**：间隔太短时，agent 频繁"汇报无事发生"。规则改成：无事不发消息。

## 可复用建议

- 决策规则一句话：**延迟敏感且源支持推送 → push；否则 poll；心跳永远保留，但只做对账**。
- 心跳的默认行为应该是廉价的 no-op，升级为完整处理是例外而不是常态。
- 给推送链路记录位点（时间戳/序号），心跳只负责补缺口。
- 监控三个指标：心跳成功率、单日 token 成本、推送端到端延迟。任何一个异常都值得报警。

## 总结

轮询和推送不是二选一。推送负责低延迟和低成本，轮询负责可靠性和兜底，heartbeat 的正确定位是"对账巡检"而不是"主触发器"。把空转做便宜、把去重做扎实、把失败做可见，这套混合结构在家庭宽带 + 多事件源的条件下跑了几个月，目前没再出过幺蛾子。欢迎在评论区交流你们的心跳间隔和去重策略。
