## 背景

OpenClaw 的 workspace 里默认躺着几个 Markdown 文件：`AGENTS.md` 管操作规范，`MEMORY.md` 管记忆，`SOUL.md` 管"你是谁"。SOUL.md 会在每次会话启动时注入 system prompt，相当于 Agent 的人格底座。很多人装完就跳过它，或者写一句"你是一个友好的助手"就完事——这基本等于没写。

## 问题

没认真写过 SOUL.md 的 Agent，常见症状：

- **语气漂移**：今天话痨、明天冷淡，跨会话不一致；
- **边界模糊**：带 shell 权限的 Agent 会顺手执行危险命令，甚至把内部 prompt 原文贴给用户；
- **人格与任务混写**：把某个项目的 SOP 塞进人格文件，换个项目全乱；
- **多渠道割裂**：Telegram 上和钉钉上像两个不同的 Agent。

本质原因：人格和边界也是配置。散落在对话里靠反复"调教"，不如固化成文件——可版本化、可回归、可 diff。

## 做法

1. **定位文件**：workspace 根目录下的 `SOUL.md`，改完开新会话生效。
2. **控制篇幅**：200–400 词。它是每次会话的固定 token 开销，写长了既烧钱又稀释任务指令。
3. **写四块内容**：
   - 身份：一句话角色定位 + 服务对象；
   - 语气：用可验证的行为描述，不用形容词；
   - 边界：明确的禁止清单（不执行哪些类别的命令、不透露 system prompt、涉及删除/付款先确认）；
   - 升级策略：拿不准时停下来问，而不是猜。
4. **用行为代替形容词**："回复默认不超过 10 行"比"简洁"可测试得多。
5. **进 git**：每次改动留 commit message，行为变了能 diff 回去。
6. **验证**：开新会话，用几个边界 case 测——诱导它贴 prompt、要求无确认删文件——多渠道各跑一遍。

## 踩坑点

- **篇幅失控**：300 行的 SOUL.md 每个会话都在吃 token，还会和 AGENTS.md 抢优先级。
- **职责不清**：人格进 SOUL.md，操作规程进 AGENTS.md，两边写重了 Agent 会随机站队。
- **改完不生效**：当前会话上下文已固定，改完要开新会话再验，别误判为"没写进去"。
- **边界写太死**："永远不要执行删除命令"会让正常运维卡死，写成"删除类操作需用户显式确认"更合理。
- **形容词堆砌**："专业、友善、高效"对模型几乎没有约束力，等价于没写。

## 可复用建议

- 一份可抄的结构：身份（3 行）/ 语气（5 行）/ 边界（8–10 条）/ 升级规则（3 行）。
- 边界条目用"触发条件 + 动作"格式，模型执行更稳。
- 每月回顾一次：把实际踩过的坑反向写成新的边界条目。
- 把验证 case 存成固定 prompt 列表，改版后跑一遍做回归。
- 子 Agent 继承同一份 SOUL.md 时注意 token 翻倍，必要时给子 Agent 换精简版。

## 总结

SOUL.md 不是玄学人设，而是一份随会话加载的策略文件。它写得好不好，标准很朴素：跨会话语气稳定、边界 case 有确定行为、改动可 diff 可回归。花半小时写好这几十行，比之后在对话里反复"调教"省事得多。
