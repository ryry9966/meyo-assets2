# 背景

做 Agent 自动化的人大多经历过同一个阶段：先让模型直接输出 JSON 去调函数，再手写一层胶水代码对接自家 API、数据库、文件系统。接第三个工具时开始抽象，接第五个时发现抽象开始漏水。更麻烦的是换宿主：同一套工具，在这个 Agent 框架里是一套插件格式，换到另一个客户端又得重写注册、鉴权和 schema 描述。

2024 年底 Anthropic 开源了 Model Context Protocol（MCP），把它定位成“AI 应用的 USB-C 口”。一年多下来，主流宿主和大量工具服务都已支持，值得每个做 Agent 的人花半小时理解一遍。

# 问题：M×N 的集成税

MCP 解决的核心问题是集成成本随组合爆炸：

- M 个宿主（Agent 客户端）各自实现一套工具调用格式；
- N 个数据源/工具（数据库、SaaS、本地脚本）各自适配每个宿主；
- 结果是 M×N 个适配器，鉴权、错误处理、schema 全都重复实现。

MCP 把它压成 **M+N**：宿主实现一次 MCP Client，工具实现一次 MCP Server，中间用统一的 JSON-RPC 消息和标准传输层通信。

# 做法：三步接入

1. **分清角色**。Host 是跑模型的 Agent 应用；Server 是暴露能力的一端。Server 对外提供三类原语：Tools（模型可调用的函数）、Resources（应用可读取的数据）、Prompts（可复用的提示模板）。绝大多数自动化场景只用 Tools 起步就够。

2. **选传输方式**。本地工具用 stdio——宿主把 Server 当子进程拉起，零网络暴露，适合 git、本地脚本这类能力；远程服务用 Streamable HTTP，走标准 HTTP 语义，适合团队共享的内部 API。OpenClaw 这类框架通常两种都支持，配置里声明启动命令或 URL 即可。

3. **写“给模型看”的工具定义**。MCP Server 的核心不是代码而是 schema：工具名、一句话描述、参数说明。模型是靠这些文字决定调不调、怎么调的。

写完先用 Inspector 或最小客户端脚本单独验证，再挂进 Agent。

# 踩坑点

- **描述敷衍，调用必歪**。“query_data：查询数据”这种描述会让模型在多个相似工具间乱选。写清楚什么时候用、参数单位是什么、失败返回什么。
- **工具越挂越多，上下文越拖越重**。每个 Server 的 schema 都要吃 token，二十个工具之后选择准确率明显下降。按项目启用/禁用，别全量常驻。
- **stdio 的环境继承**。子进程继承宿主的环境变量和 cwd，Windows 下还有编码与路径分隔符问题；密钥写进配置的，记得别提交进 git。
- **阻塞调用卡死主循环**。长任务必须设计超时和进度上报，否则 Agent 整个 loop 挂住。
- **信任边界**。第三方 MCP Server 就是任意代码，装之前过一遍源码；有写操作的工具加人工确认，尤其是删除、转账、发消息类。
- **同名冲突**。多个 Server 暴露同名工具时，确认框架是否支持命名空间前缀。

# 可复用建议

- **先只读后写入**：只读工具随便挂，写工具必须过确认闸门。
- **别重写，包装**：把团队已有的 CLI 脚本套一层 MCP Server，半天就能让所有宿主复用。
- **维护一份团队 Server 注册表**：用途、维护人、版本、风险备注。
- **定期看工具调用的 token 开销**：精简 schema 的收益常常大于换模型。

# 总结

MCP 不会让模型变聪明，它只是把“接入”这件事标准化了：M×N 变 M+N，集成成本从每一对宿主-工具组合，降为每个端点一次。对个人，是少写胶水代码；对团队，是工具资产可以在不同 Agent 宿主之间平移。如果你已经在 OpenClaw 里手写过两个以上的工具适配器，现在就是迁移的时机。
