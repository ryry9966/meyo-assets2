## 背景

在 OpenClaw 里做编排是常态：主会话负责拆解任务，把代码审查、批量重构、文档生成这类活派给子 Agent，子 Agent 再挂一两个 MCP server 干活。听起来很干净，但我们团队跑了一段时间后发现，主会话越来越"脏"——上下文持续膨胀，模型开始引用子任务的中间细节，甚至自作主张去调用本不该它碰的工具。

## 问题出在哪

默认配置下，子 Agent 并不是完全独立的：

- 子 Agent 继承主会话历史，主会话的噪音全带过去了；
- 子 Agent 跑完后，完整 transcript（工具原始输出、读过的文件内容）回写主会话；
- MCP 工具调用记录挂在主会话名下。

后果很典型：一次批量重构跑完，主会话上下文直接翻倍；下一轮对话模型还在纠结子任务里某个早已解决的报错；token 成本和延迟肉眼可见地涨。这就是"污染"。

## 我们的隔离做法

1. **子 Agent 用独立 session**。spawn 时显式指定隔离模式（不同版本叫法略有差异，认准"新建独立 session id"这个行为）。子 Agent 只收到一份紧凑的任务描述，不带主会话历史。
2. **定义输入/输出契约**。输入：任务字符串 + 少量文件路径 + 必要的约定摘要；输出：强制结构化 JSON，例如 `{"status": "...", "files_changed": [...], "notes": "..."}`。回写主会话的只有这个 JSON。
3. **MCP 配置跟随子 Agent**。工具授权和 server 配置挂到子会话上，主会话不加载这批工具，调用记录自然留在子会话里。
4. **工作区隔离**。子 Agent 在 scratch 目录干活，改完由主流程 review 后再合入，避免直接动主仓。

跑下来效果：主会话上下文基本恒定；子任务的中间产物（报错、日志、大文件内容）全沉在子会话里，需要排障时单独翻子会话文件即可。

## 踩坑点

- **隔离过头**：子 Agent 完全不知道项目约定，产出风格跑偏。解法是传一份压缩过的规范摘要，而不是放开全部历史。
- **假成功**：子 Agent 内部失败却返回"完成"。务必校验结构化结果里的 status 字段，别只看退出码。
- **并发写冲突**：多个子 Agent 同时改同一个文件。按文件给子任务划边界，或写操作串行化。
- **递归 spawn 没上限**：子 Agent 再 spawn 子 Agent，深度失控。显式设置 max depth。
- **主会话"好心"传太多**：把整个任务背景塞给子 Agent，隔离形同虚设。克制，只传契约里定的字段。

## 可复用建议

把子 Agent 当纯函数看待：有类型的输入、有类型的输出、不碰调用方的状态。沉淀一份团队通用的契约模板（输入字段、输出 schema、status 枚举），新任务照抄即可。子会话文件单独留存并记录 session id，排障时比翻主日志快得多。另外注意：隔离省的是主会话的上下文，不是总 token 开销，子任务量大时考虑合并批量派发。

## 总结

session 隔离不是高级魔法，核心就一句：**边界要显式**。子 Agent 拿什么、还什么、在哪儿干活，全部写进契约；主会话只接收摘要。做到这几点，编排复杂度上去了，主会话依然能长期保持干净。
