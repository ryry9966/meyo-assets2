## 背景

OpenClaw 的 agent 跑久了，记忆库会积累几百上千条会话摘要、配置决定、用户偏好。`memory_recall` 是 agent 主动查记忆的入口，它的召回质量直接决定 agent 是“记得你说过的话”，还是“一本正经地现编”。社区里做 memory 插件（不管是原生插件还是通过 MCP 挂载的 memory server）基本两条路线：**语义搜索**（embedding 向量检索）和**全文搜索**（关键词/BM25）。争论很多，实测很少。

## 问题

我自己的 agent 记忆库约 600 条，两类典型失败：

- 走语义搜索时，问“上次那个定时任务的 cron 表达式”，召回回来一堆“任务调度策略讨论”，真正含 `0 3 * * *` 的那条排不进 top-5；
- 走全文搜索时，问“之前怎么处理上传超时的”，库里明明有一条“分块上传 + 断点续传”，但“上传超时”在原文中没有连续出现，直接零召回。

一个偏精确、一个偏模糊，单用哪边短板都很明显。

## 做法

我没急着换方案，先搭了个 30 条查询的评测集，分四类：专有名词（命令/路径/ID）、同义改写、数字与时间、模糊意图。两条 pipeline 分别跑 top-5 命中率：

- 全文：SQLite FTS5，中文先分词再入库；
- 语义：本地 bge-small-zh-v1.5（512 维），cosine 相似度。

结果：专有名词类全文 9/10、语义 4/10；同义改写类语义 8/10、全文 3/10。和预期一致——但数字摆出来，做决定才有底气。

于是上**混合检索**，步骤如下：

1. 入库时每条记忆拆成 `text`（原文）、`summary`（一句话摘要）、`tags`、`timestamp` 四个字段；
2. 全文索引建在 text + tags 上，向量索引建在 summary 上（摘要比原文更聚焦，向量不容易被稀释）；
3. 查询时两路各取 top-10，用 RRF 融合：`score = Σ 1/(60 + rank)`；
4. 融合后按时间做轻度衰减（半衰期 30 天），再截 top-5 给 agent。

改造后评测集平均命中率从 6.5/10 提到 8.5/10，改动量不大，两个索引都是现成组件。

## 踩坑点

- **FTS5 默认 tokenizer 对中文几乎无效**，整句被当成一个 token。全文路线看起来“完全不行”，很多时候是配置问题，先确认分词；
- embedding 对短查询（人名、报错码）很不可靠，会把不同实体的相似句混在一起，别指望语义搜索兜底精确匹配；
- 记忆原文太长，向量会被稀释。摘要入库比原文入库召回稳得多；
- 时间衰减一开始设太狠，一个月前的关键决定全沉底，agent 表现得像“失忆”；改成轻度衰减 + tags 保底才恢复；
- 试过把 top-k 从 5 放到 10，上下文变长后 agent 反而更容易引用无关记忆。召回宁少勿多。

## 可复用建议

- **先建评测集再动手**。20~30 条真实查询就够，凭感觉选型大概率返工；
- 命令、路径、ID、人名这类 token，永远保留精确/全文通道；
- 混合 + RRF 是性价比最高的起点，不需要 reranker 就能到 80 分，有精力再上重排；
- 检索质量一半取决于入库质量：摘要、tags、时间戳在写入时就结构化好，比事后调检索参数有用得多。

## 总结

语义搜索和全文搜索不是二选一，而是分工：全文负责“说出来的词必须对得上”，语义负责“换个说法也能找到”。`memory_recall` 这种高频小工具，简单可靠的混合方案比堆模型更务实。这次最有价值的产出其实是那个 30 条的评测集——建议每个做 memory 插件的人先写它，再写检索。
