## 背景

做 Agent 自动化的人早晚会遇到同一个问题：MCP 插件要读本地文件、操作浏览器、跑定时任务，这些上下文里全是隐私数据。全走云端 API，一是费用随调用量线性涨，二是敏感信息出网不放心。开源模型这一年进步很快，Qwen3、DeepSeek 蒸馏版在工具调用上已经基本可用，本地部署从“玩具”变成了“可选方案”。

## 问题

难点不是“能不能跑起来”——llama.cpp 一条命令就能起服务。真正的门槛是：**能不能当一个合格的 Agent 大脑**。拆开是三件事：工具调用格式是否稳定；MCP 场景下动辄 10k+ tokens 的工具描述，长上下文显存扛不扛得住；批量自动化任务时吞吐够不够。这三点决定方案怎么选。

## 做法

按显存分三档：

- **8GB**：Qwen3 8B/14B 的 Q4 量化，Ollama 起服务，日常对话和简单工具调用够用；
- **16GB**：重点看 Qwen3 30B-A3B 这类 MoE 模型——激活参数少、推理快，工具调用能力明显高于同级稠密模型，是我目前的主力推荐；
- **24GB+**：可上 32B 级 Q4–Q5，或留足余量给长上下文。

步骤上我固定走这条路径：

1. 装 Ollama（省心）或 llama.cpp server（可控性强），关键是拿到 OpenAI 兼容端点；
2. **显式设置上下文长度**，MCP 场景下默认值严重不够：

```bash
# Ollama 默认 num_ctx 只有 4k，建议拉到 16k–32k
OLLAMA_CONTEXT_LENGTH=32768 ollama serve
```

3. 在 OpenClaw 的模型配置里加一个自定义 provider，baseURL 指向 `http://127.0.0.1:11434/v1`，key 随便填；
4. 拿真实自动化任务做回归测试——不是聊天测试，而是让 Agent 连续调十几次工具完成一件事。

## 踩坑点

- **工具调用格式**：不是所有量化版都完整保留了 tool calling 模板，同一个模型，官方 GGUF 和第三方裁剪版行为可能不同，优先用官方发布；
- **KV cache 吃显存**：显存占用随上下文线性增长，32k 上下文在 14B 模型上能额外吃掉几个 GB。“能装下”和“装下且能跑长任务”是两回事；
- **思考模式**：Qwen3 这类模型默认输出思考段，部分客户端处理不好会污染工具参数，部署时先确认开关行为；
- **并发**：本地服务默认串行处理，Agent 循环里若并行调用工具，排队延迟会很明显，要么限制并发，要么接受等待；
- **温度参数**：别沿用聊天习惯的 0.7，工具调用场景建议 0.1–0.3，稳定性差异肉眼可见。

## 可复用建议

- **大脑和工人分开**：本地大模型只做规划与决策，摘要、分类这类高频轻活交给小模型甚至规则，能显著延长本地方案的可用寿命；
- **永远留云端 fallback**：本地服务挂了，Agent 不至于瘫痪；
- **建固定测试集**：用自己的典型任务列十几条用例，每次换模型/换量化版本跑一遍，别靠体感判断。

## 总结

本地 LLM 当前的核心价值是隐私和成本可控，代价是你得理解显存、上下文和工具调用这些细节。以工具调用为主的 Agent 工作负载，16GB 显存 + MoE 模型 + 显式上下文配置，是当下性价比最好的组合。先小规模跑通再扩，别一步到位。
