## 背景

Agent 的能力边界，基本等于它能调用的工具边界。在 OpenClaw 的典型用法里，一次自动化任务往往串着多个外部依赖：搜索 API、行情/天气数据源、自建服务的 MCP 工具、第三方插件的 HTTP 端点。跑批和定时任务一多，"某个 API 挂了"就不是偶发事故，而是每周都会遇到的常态。多数教程只讲怎么接工具，很少讲工具挂掉之后怎么办——而后者才决定 Agent 能不能上生产。

## 问题：挂掉之后的三种坏结局

1. **盲目重试**。Agent 收到 429/503 后立刻原样再调，几秒内把限流打得更死，token 也烧掉了。
2. **静默编造**。更危险的情况：工具把报错原文丢给模型，模型"理解"之后自己补了一个看起来合理的值。用户拿到的是幻觉数据，任务却显示成功。
3. **整单阻塞**。多步任务里一个非关键依赖失败，导致整条链路中断，前面已完成的步骤全部作废。

## 做法：把错误处理下沉到工具层

核心原则一句话：**重试和降级不要指望模型在提示词里"自觉"，要在工具包装层用代码兜住。**

**第一步，错误分类。** 在工具执行器里把错误分成两类：可重试（超时、429、5xx）与不可重试（400、401、404、参数校验失败）。只有前者进重试队列。

**第二步，有上限的退避重试。** 指数退避加随机抖动，比如 1s/2s/4s，最多 3 次。上限写死在代码里，不留给模型决定。

**第三步，熔断。** 同一工具连续失败 N 次后熔断 60 秒，期间直接快速失败，避免每个 Agent 实例都去试探一遍。

**第四步，降级路径。** 每个关键工具准备一条退路：返回带 `stale: true` 标记的上次成功缓存、切换备用数据源，或者明确返回"此步骤跳过"。

**第五步，给模型结构化错误，而不是堆栈。** 工具返回 `{ "ok": false, "error_code": "UPSTREAM_TIMEOUT", "retryable": true, "attempt": 2 }` 这类契约，并在系统提示里只保留一条规则：重试由外层处理，耗尽后如实报告失败，禁止编造数据。

## 踩坑点

- **重试非幂等接口**。POST 建单类操作一重试就出重复资源，要么上游支持幂等键，要么这类调用禁用自动重试。
- **缓存不带新鲜度标记**。Agent 把旧数据当新数据用，比直接失败更糟。
- **把原始异常抛给模型**。一段 Java 堆栈只会换来一段一本正经的错误解读。
- **熔断粒度太粗**。按工具熔断而不是按调用方/实例隔离，一个慢接口会拖垮所有无关任务。

## 可复用建议

- 写一个统一的工具执行器（重试 + 熔断 + 超时 + 结构化错误），所有 MCP 工具和插件调用都走它，不要每个工具各写一套。
- 长任务启动前先对各依赖做一轮健康检查，挂掉的提前走降级分支。
- 工具失败日志带 trace_id，事后能回答"那次任务到底为什么失败"。
- 提示词只负责一件事：失败要如实说。其余策略全部进代码。

## 总结

外部 API 一定会挂，问题只是什么时候。Agent 的可靠性不来自更长的系统提示，而来自工具层那几十行不起眼的重试、熔断与降级代码。把错误当成一等公民设计进工具契约，模型才有机会做到"诚实失败"——这是 Agent 从演示走向生产，最短的那条路。
