## 背景

用 Agent 这么久，最大的别扭不是它答不好，而是它从不主动。所有能力都堵在一个入口后面——你得先开口。而时间敏感的事（盯 CI、看磁盘、早上发日报）靠人肉触发，意义就丢了一半。

OpenClaw 提供了一个很小的原语来解决这个问题：**心跳（heartbeat）**。Gateway 每隔一段时间唤醒主会话，注入一条极简提示，让 Agent 去读工作区里的 `HEARTBEAT.md`，按需执行。文件即常备指令，Agent 即值班员。

## 问题

- 反应式交互天然覆盖不了"时间维度"的任务；
- 外部 cron + 脚本能做轮询，但一旦需要**判断**——这封邮件算不算紧急？这次构建失败要不要叫人？——脚本就写不动了；
- 心跳的价值在于三件事的组合：**定时唤醒 + 会话上下文 + 工具链（MCP/插件）**。判断留给模型，执行交给工具。

## 做法

1. 配置 gateway 周期性心跳，默认 30 分钟一次，测试期可调短，设 `0m` 关闭；
2. 在工作区根目录建 `HEARTBEAT.md`，按条件和动作写，像写 runbook：

```markdown
- 08:00 之后首次心跳且今日日报未发：汇总昨晚 CI 失败项，推送到构建频道
- 检查数据盘占用，超过 85% 才提醒
- 无事可做时，只回复 HEARTBEAT_CHECK_OK
```

3. 无事时让 Agent 回复 `HEARTBEAT_CHECK_OK`，gateway 会吞掉这条回复，不推送到消息渠道，不打扰你；
4. 只放"需要判断"的任务进来，纯定时任务继续交给 cron 和脚本；
5. 状态去重：让 Agent 往一个小文件里写"上次已发时间"，每次心跳先读再判断，避免重复推送。

## 踩坑点

1. **Token 成本 = 心跳频率 × 主会话上下文**。HEARTBEAT.md 写二十条，等于每半小时全量跑一遍。控制在 5 条以内，重活转给子 agent 或降低频率；
2. **心跳不是 cron**，间隔会漂移、重启会重置。别写"8:00 整发"，要写"8:00 之后首次心跳且今天没发过"；
3. **长任务会占住主会话**，后续心跳只能排队。心跳里只做检查和触发，大体量动作丢给后台会话或脚本；
4. **忘写 OK 抑制**，Agent 每次都"汇报无事"，半天下来你的聊天渠道全是噪音；
5. **模型档位**：心跳多数时候只是"看一眼"，如果版本支持，给心跳单独配便宜的小模型，命中任务再升级到大模型。

## 可复用建议

- 把 HEARTBEAT.md 当 SOP 维护，每条任务写全四要素：**触发条件、动作、频率、去重方式**；
- 入 git 管理，改动有 diff，踩坑可回滚；
- 与 MCP 工具复用同一套：心跳里调用的就是平时对话里那批工具，不需要额外接线；
- 先以 30 分钟低频跑一周，观察 token 账单和渠道噪音，再决定往上加任务。

## 总结

HEARTBEAT.md 本质上只是一个 Markdown 文件加一个定时唤醒，但它把 Agent 的交互模型从 pull 改成了 push。工程上真正要管理的从来不是"能不能主动"，而是**主动的频率、成本和噪音**。文件小、任务少、去重严，它就是个省心的值班员；写膨胀了，它就是个烧钱的定时炸弹。
