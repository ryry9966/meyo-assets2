## 背景

在 OpenClaw 插件和 MCP 工具开发里，让 LLM 返回结构化结果是常态：路由决策、参数抽取、批量标注，最终都要落到 JSON 上。但模型输出本质是文本，你要求它"只输出 JSON"，它未必照办。我们的经验是：解析层必须假设输入是脏的，这是防御性编程的第一课。

## 问题

同一套 prompt，模型返回的 JSON 载体至少有五种形态：

1. 裸 JSON，理想情况；
2. Markdown 代码围栏包裹（三个反引号 + `json` 标注）；
3. 自造 XML 标签包裹：`<json>`、`<result>`、`<output>`；
4. 前后带说明文字："解析结果如下：……"；
5. 混合形态——围栏套标签、标签套围栏，或 JSON 字符串里嵌了含反引号的代码片段。

直接 `json.loads`，前三种全挂。更麻烦的是输出格式会随模型版本、温度、上下文长度漂移，今天能跑的解析器明天就崩。

## 做法

我们把解析收敛成一个五层漏斗，逐层降级，命中即返回：

**第一层：直接解析。** strip 空白后 `json.loads`，接住理想输出。

**第二层：剥围栏。** 用正则匹配围栏块（三个反引号 + 可选语言标注），非贪婪提取内部内容再解析。注意语言标注可能缺失。

**第三层：剥标签。** 对 `<json>`、`<result>`、`<output>` 等常见标签做提取。建议把标签列表做成配置项，不同插件可扩展。

**第四层：平衡截取。** 找到第一个 `{`，向后做括号计数扫描（跳过字符串字面量内的括号和转义），取到配平的 `}` 为止。不要用 `\{.*\}` 这种贪婪正则，多对象场景会从第一个 `{` 一路吃到最后一个 `}`。

**第五层：语法修复。** 处理尾逗号、智能引号（`""`→`"`）、Python 风格的 `True/False/None`。可以直接用 json-repair 这类库，也可以维护一个 20 行的最小修复器。

解析成功后还有第六道关：**schema 校验**。用 pydantic / zod 定义字段和类型——解析对不等于语义对。校验失败时，把错误信息和原始输出一起喂回模型重试一次，通常一轮就能修正。

## 踩坑点

- **贪婪正则**：`\{.*\}` 在输出含两个 JSON 时会匹配整段，解析必挂，务必用平衡计数。
- **嵌套围栏**：JSON 字符串里含三个反引号时，简单围栏正则会提前截断，需要靠第四层兜底。
- **few-shot 示例反噬**：示例若带围栏，模型就会学舌。示例请用裸 JSON，同时明确要求"不要输出代码围栏"——但解析层照样做兜底，两条腿走路。
- **修复别过度**：只修语法不修语义。缺字段、类型错交给 schema 校验和重试，静默补默认值会把 bug 藏到下游。
- **务必记录原始输出**：解析失败时把 raw text 落日志，否则线上问题无法复盘。

## 可复用建议

- 把漏斗封装成单一工具函数（如 `parse_llm_json`），配 10 条以上坏输出测试用例作为回归集，跨项目复用；
- 优先用模型侧的结构化输出或 function calling，防御层作为降级路径而非主路径；
- 维护一个"脏输出语料库"，每次线上解析失败都往里加一条，测试集会越来越贴近真实分布；
- 流式场景下按增量累积解析，别在半截 JSON 上提前报错。

## 总结

LLM 的输出格式不是契约，是概率。防御性解析的核心思路：分层降级、语法修复与语义校验分离、失败可观测。一次把漏斗写好，后面每个插件都受益。
