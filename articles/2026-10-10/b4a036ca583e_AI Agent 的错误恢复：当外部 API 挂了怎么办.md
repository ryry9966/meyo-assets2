## 背景

现在一个典型的 Agent 工作流里，模型本身往往不是最先挂的那个。真正高频出故障的是它周围的东西：LLM 供应商限流、MCP 工具背后的第三方 API 超时、搜索或数据库插件抖动。传统后端服务挂了会抛异常、触发告警；Agent 挂了的表现要隐蔽得多——它会继续“说话”。

## 问题：静默失败比崩溃更贵

外部 API 出错时，如果原始错误被直接塞回上下文，常见三种恶化路径：

1. 模型把报错当任务输入，开始道歉，最后编一个“看起来合理”的结果；
2. 无限重试，token 消耗翻倍，任务永远不收敛；
3. 非幂等操作被重复执行，比如重复下单、重复发通知。

工程上的目标不是“让 API 不挂”，而是：挂了之后，Agent 能在有限成本内做出正确决策——重试、降级、换路，或者停下来问人。

## 做法：三层兜底

**第一层：工具/插件层。** 每个 API 调用都要有显式超时（别依赖默认值）、指数退避加抖动的重试、尊重 `Retry-After` 头、幂等键。这一层解决瞬时抖动，和模型无关。

**第二层：Agent 决策层。** 不要把原始堆栈喂给模型，给它结构化错误摘要：

```json
{ "status": "rate_limited", "retryable": true, "retry_after_s": 30, "detail": "供应商限流，第2次" }
```

配合系统提示词明确策略：可重试错误最多 N 次；不可重试错误立即降级；连续失败则暂停并向用户报告。关键是把“重试几次”做成硬预算（max_attempts / max_cost / max_wall_time），不交给模型自由发挥。

**第三层：编排层。** 熔断与降级：连续失败达到阈值后直接切备用供应商或读缓存，并给结果打上“降级来源”标记；任务做 checkpoint，恢复后从断点续跑，而不是从头来过。

## 踩坑点

- **只重试不分类**：配额耗尽重试一百次也没用。错误分三类——瞬时（可重试）、永久（快速失败）、配额/鉴权（暂停并告警）。
- **无抖动的固定间隔重试**：对端刚恢复就被一波请求打挂，形成重试风暴。
- **非幂等操作裸重试**：先加幂等键，再谈重试。
- **降级数据无标记**：用户拿到两小时前的缓存还以为是实时数据。
- **让模型看完整 traceback**：上下文被污染，后续行为不可预测。

## 可复用建议

- 给所有工具做统一的错误信封（status / retryable / retry_after / detail），Agent 层只认这个格式，换供应商不改上层逻辑。
- 重试、降级、熔断的参数写进配置，不要散落在 prompt 里靠“说”。
- 结构化记录每次失败（工具名、错误类别、耗时、重试次数），事后能回放定位。
- 定期做混沌测试：故意把某个工具指向必挂的端点，观察 Agent 是停、是降级、还是烧 token——这比线上事故便宜得多。

## 总结

外部 API 挂掉不是异常路径，是 Agent 的日常。好的错误恢复不靠模型“聪明地想办法”，而靠工程上把决策空间设计好：工具层消化瞬时抖动，Agent 层在硬预算内做重试/降级决策，编排层兜住系统性故障。先用预算防住最坏情况，再逐步优化恢复策略——顺序别反了。
