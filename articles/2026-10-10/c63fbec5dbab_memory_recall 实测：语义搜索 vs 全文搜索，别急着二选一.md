## 背景

OpenClaw 的 agent 跑久了会在 workspace 里积累大量记忆文件：MEMORY.md、memory/ 下的日期笔记。`memory_recall` 是 agent 主动"翻旧账"的入口——它搜得准不准，直接决定"我记得你上次说过"是真是假。目前可选的检索路径主要是两条：语义搜索（embedding 向量召回）和全文搜索（关键词匹配，FTS/grep 式）。

## 问题

语义搜索听起来更"智能"，但我们实测发现它不是万能的：

- 查"上次那个 502 部署故障"，语义检索能召回当时的复盘笔记，全文检索因为分词问题可能漏；
- 查一个精确的报错码或函数名，全文检索一击必中，语义检索反而可能被"相似但不对"的条目挤占 topK。

两条路各有明确的失效区间，而默认配置往往只走其中一条。

## 做法

我们的做法是先跑一轮确定性评测，再定配置：

1. 从记忆库挑 20 条真实笔记，手工设计 20 个 query：一半转述型（换说法问），一半精确型（报错码、命令、人名）。
2. 分别用语义和全文模式跑 recall，记录命中/未命中。
3. 结果：转述型 query 语义命中率约 8 成，全文只有 4 成；精确型 query 完全反过来。
4. 最终方案：语义为主路，配好 embedding provider；全文作为回退和混合通道，两路结果合并去重，精确 token 类查询直接信任全文结果。

## 踩坑点

- **中文分词是全文检索的暗坑**：按空格切词的 FTS 对中文几乎失效，"部署故障"整串匹配不上"部署 出问题"。要么保证 embedding 常开，要么选对 CJK 分词友好的实现。
- **embedding 不是免费的**：每次 recall 都是一次 API 调用，agent 高频自检时延迟和费用都会涨。本地 embedding 模型是可选项，但质量必须重新评测。
- **索引要跟上记忆的更新**：追加完记忆没重建索引，会出现"我明明写了但 recall 不到"的灵异问题。
- **语义检索的假阳性**：召回的笔记看起来相关，实际是另一个项目的同名概念。topK 别开太大，宁可让 agent 二次确认。

## 可复用建议

- 记忆语料小（几百条以内）时，全文检索 + 规范的关键词前缀（日期、标签）已经够用，语义检索收益有限。
- 给记忆文件固定 frontmatter 结构（日期、主题、关键词），能同时喂饱两种检索。
- 评测集固定下来，换 embedding 模型或调参后重跑，别凭感觉。
- 打开 recall 日志，观察 agent 实际采用了哪些召回结果——这比离线评测更接近真实。

## 总结

语义 vs 全文不是二选一，而是失效区间互补：转述靠语义，精确靠全文；中文场景下，分词决定了全文检索的下限。先用一个 20 条的评测集量出基线，再决定主路和回退——半小时的投入，换 agent"记性"的确定性提升。
