## 背景

Agent 接上 MCP 和插件之后，能做的事从"读文件、跑测试"扩展到"改配置、推分支、调外部 API、花钱"，而权限策略常常还停留在两级：要么全放，要么每个动作都弹确认。OpenClaw 这类可扩展框架把工具暴露得很细，恰恰更需要一张明确的边界表。

## 问题：两个对称的失败方向

- **全自作主张**：一次误删、一条发错渠道的消息、一笔不该花的 API 费用，就足以毁掉信任。
- **全问人**：人会疲劳，然后开始无脑点"允许"，确认机制形同虚设，Agent 退化成一个昂贵的回车键。

所以真正要设计的不是"问不问"，而是一套分级策略。

## 做法：三个维度定级

每接入一个工具（尤其是新 MCP server），先按三个维度打分：

1. **可逆性**：能不能撤销？`git revert` 可以，删库、给客户发消息不行。
2. **影响半径**：只碰工作区/沙箱，还是会触及共享仓库、生产环境、外部人群？
3. **成本**：钱、额度，以及批量操作对前两者的放大效应。

然后落到三档：

- **绿档（自动执行）**：可逆、半径限定在工作区、语义上被指令明确覆盖。读文件、跑测试、建分支、生成草稿。
- **黄档（一次确认，批量问）**：改共享状态但可逆。推 feature 分支、装依赖、改共享配置。把相关动作攒成一批，一次展示完整 diff 和目标，而不是逐条打断。
- **红档（永远问人，必须给预览）**：不可逆、对外、涉及钱。删数据、对外发送、支付、生产部署、改动认证与权限本身。

## 落地要点

- **管控放工具层，不放 prompt 层**。系统提示里写"请谨慎"是建议；工具的 allowlist/denylist、路径白名单、高危命令拦截才是约束。
- **确认弹窗要有信息量**：展示真实命令、diff、目标地址，而不是"是否允许调用某工具"——后者只会训练人条件反射点允许。
- **全量审计日志，含自动放行的动作**。没有数据就没法调边界。

## 踩坑点

1. **确认疲劳**：如果连续一周都在无脑点允许，说明黄档太宽——收窄它，或降级为绿档+审计。
2. **能力组合升级**：单独看都安全的工具，组合起来可能等价任意执行（能写文件 + 能跑 shell）。评估权限要算传递闭包，不能只看单个工具。
3. **凭证不随沙箱隔离**：Agent 在沙箱里跑，但 MCP 凭证是全局的，照样能打到生产 API。沙箱隔离的是文件系统，不是权限。
4. **只靠 prompt 收紧**：换个模型、换个会话，约束就没了。

## 可复用建议

- 新工具接入时填一张三行表（可逆？半径？成本？），定档写进**版本化的权限配置**，变更走 review。
- **"草稿不发送"**：Agent 产出内容，最后的发送/部署动作留给人，这是黄红档之间最省心的缓冲带。
- 边界是活的：出过事故的档位收紧；连续一个月零告警的可考虑放宽。初期每周过一次审计日志。

## 总结

权限边界不是"信不信任模型"的态度问题，而是把自主权与可逆性、影响半径对齐的工程问题。绿档足够宽，自动化才有价值；红档足够硬，信任才守得住。先用保守配置上线，再靠审计数据慢慢放宽。
