## 背景

跑过长期自动化任务的人都知道：Agent 的大部分故障不是模型不行，而是外部依赖挂了。LLM 供应商限流、搜索接口超时、MCP 工具背后的数据库断连——这些在凌晨三点的定时任务里几乎是必然事件。模型本身很稳定，不稳定的是它周围那一圈 HTTP 调用。

## 问题

多数框架的默认行为是把原始报错字符串直接塞回上下文，让模型"自己想办法"。结果通常是三种：模型陷入无脑重试循环直到 token 烧完；模型把报错当成工具的正常输出，幻觉出"调用成功"；或者干脆放弃整个任务。本质上，错误恢复被当成了推理问题，而它其实是工程问题。

## 做法：四层处理链路

**1. 错误分类。** 在工具封装层把异常转成结构化结果：`429 / 5xx / 超时`标记为可重试，`401 / 400 / 404`标记为致命。返回 `{code, retryable, retry_after}` 而不是一段堆栈。这一步决定了后面所有行为。

**2. 受控重试。** 可重试错误走指数退避加随机抖动，设置最大尝试次数和总时间预算。只对幂等操作重试；非幂等的 POST 必须带幂等键，否则一次网络抖动就是两封邮件、两笔订单。

**3. 熔断与降级。** 连续失败达到阈值就打开熔断器，后续请求快速失败，既不打爆对方，也节省自己的配额。同时准备降级路径：备用供应商、本地缓存、或跳过该步骤并在结果里注明。

**4. 断点续跑。** 每次外部调用前落一次检查点（已完成步骤、中间产物）。恢复后从检查点继续，而不是从头执行整个 workflow——这对长任务尤其关键。

分层的意义在于：重试、熔断、降级都发生在编排层，模型只在真正需要决策时才看到错误，比如"主通道和备用通道都失败了，是否改用离线数据"。

## 踩坑点

- **非幂等操作裸重试**。最常见的生产事故来源，没有之一。
- **把 HTML 错误页或完整堆栈喂给模型**。上下文被污染后，模型后续的判断基本不可信。
- **重试没有总预算**。每次退避翻倍，二十次就是天文数字的等待，任务本身也超时了。
- **timeout 设得太宽**。一个卡死的调用能拖住整个并发池。
- **降级成功但没标注**。下游把旧缓存数据当实时数据用，比直接失败更危险。

## 可复用建议

1. 所有外部调用走统一封装（装饰器或中间件），错误处理逻辑一处维护，不要散落在各个插件里。
2. 错误码枚举固定下来，并在 agent 的系统提示里写清每种码的含义和预期应对。
3. 任何降级都要在最终输出里标注数据来源和时效。
4. 把失败率、平均重试次数、熔断触发次数纳入监控——它们是 Agent 健康度最诚实的指标。

## 总结

外部 API 挂掉不是异常，是常态。可靠的 Agent 不是不遇到错误的 Agent，而是错误被分类、被限流、被降级、可续跑的 Agent。核心原则只有一条：能在编排层用确定性逻辑解决的，就不要交给模型去"想"。
