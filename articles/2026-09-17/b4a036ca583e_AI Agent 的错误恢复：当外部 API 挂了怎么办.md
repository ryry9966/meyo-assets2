## 背景

Agent 自动化跑得越久，越会撞上同一个问题：某个外部 API 突然不可用。搜索接口限流、地图服务超时、第三方模型网关 502……在 MCP 和插件生态里，一次任务往往串联五六个外部调用，任何一环挂掉，Agent 就停在半路。失败不是异常路径，而是常态输入，值得当成正经工程问题来设计。

## 问题：两类最糟糕的反应

1. **直接崩溃或静默吞错。** 崩溃丢掉已有进度；吞错后返回空字符串，模型会把"没拿到"当"没有"，开始编造数据。
2. **让 LLM 自己重试。** 模型不懂退避，往往连续猛发请求（加剧限流），或者把错误转述一遍后丢失状态码，在死路上反复打转烧 token。

核心矛盾：重试是工程决策，不该交给概率采样；但"接下来怎么办"（换路、降级、放弃）需要语境判断，适合交给模型。

## 做法：分层错误恢复

**第一层：适配器内处理瞬时错误。** 每个外部工具包一层薄适配器，统一做超时、重试和错误归一化。规则：429/5xx/网络超时可重试，指数退避加随机抖动（如 1s/2s/4s ±30%），上限 3~5 次；401/403/404/参数错误不重试，直接上抛。重试逻辑全在代码里，模型无感。

**第二层：结构化错误交给 Agent。** 重试耗尽后，不要把堆栈丢给模型，而是返回固定结构：错误码、一句话原因、可选的恢复建议（"服务限流中，预计 60 秒恢复"/"配额已耗尽，请改用备用源"）。模型拿到的是决策信息，不是日志。

**第三层：降级与断路。** 关键数据源准备 fallback：本地缓存（标注数据时间戳）、备用 provider，或明确的"此信息暂不可用"。同一工具在时间窗口内连续失败 N 次就熔断，之后工具直接返回"已熔断"，省掉无效等待，也让 Agent 提前改道。

**第四层：状态持久化与幂等。** 长任务每完成一步就落盘（checkpoint），恢复时从断点续跑。对有副作用的调用（下单、发消息、写库）强制幂等键，重试才不会变成重复扣款。

## 踩坑点

- **退避没加抖动**：API 恢复瞬间所有实例同时重发，二次压垮对方。
- **200 当成功**：有些 API 把错误包在 200 响应体里，必须校验业务码，否则 Agent 拿着错误 payload 继续推理。
- **非幂等操作裸重试**：POST 类请求不加幂等键，一次网络抖动变成两次写入。
- **备用源 schema 不一致**：降级后字段含义变了，Agent 静默产出错误结论。降级路径要过同一层适配器归一化。
- **重试上限太松**：token 预算和任务时限也要算进重试成本，重试不是免费的。
- **熔断状态不共享**：多实例部署时各自熔断等于没熔断，至少共享一个标记文件或 redis key。

## 可复用建议

1. 给每个外部工具加"故障模拟"开关，能返回 429/500/超时，把失败路径纳入日常测试。
2. 建中心化的 per-tool 配置：timeout、重试次数、退避基数、是否可降级，别散落在各插件里。
3. 失败事件打结构化日志（工具名、错误码、耗时、重试次数），事后能统计哪个源最不稳定。
4. 长任务跑之前先做一次 preflight 探活，成本极低，能省掉跑到 80% 才发现源挂了的浪费。

## 总结

外部 API 挂掉不是意外，是 Agent 工程的必答题。原则一句话：瞬时错误在代码层退避重试，持久错误结构化交给模型重新规划，副作用操作保证幂等，长任务随时可从断点恢复。让重试归代码、决策归模型，这条边界画清楚，Agent 的鲁棒性会上一个台阶。
