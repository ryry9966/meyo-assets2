## 背景

RSS 依然是我认为最可控的信息源：协议开放、无算法干预、随时可退订。问题不在获取，而在消化——我订阅了 40 多个源，每天产出上百条，真正值得读的不到十条。

与其每天人肉刷 reader，不如把这件事交给 agent。目标很朴素：OpenClaw 定时抓取订阅源，LLM 做一轮筛选和摘要，把一份简短日报推到我的聊天窗口。

## 问题

动手前明确三个痛点：

1. **噪点大**。逐条让 LLM 判断既贵又慢，token 消耗和条数成正比。
2. **全文缺失**。不少源只给 summary 甚至只有标题，直接摘会把"标题党"当成本体。
3. **重复与死链**。同一篇文章被多个源转载，去重做不好，日报里全是复读。

## 做法

整体是一条四段管线：

```
cron 触发 → 抓取 + 全文抽取 → 去重入库 → 分批摘要 → 推送
```

**1. 抓取与全文抽取。** 用一个轻量 RSS skill 每 30 分钟拉一次。feed 里只有摘要的条目，补一次 readability 抽正文，截断到前 2000 字符——够摘要用，不浪费 token。

**2. 去重入库。** 所有条目先进 SQLite，去重键用 `norm(link) + feed_id`，而不是单纯依赖 guid（后面踩坑会讲）。同时记 `seen_at`，方便排查。

**3. 分批摘要。** 攒到固定时间点（每晚 21:00）统一处理，每批 15–20 条，prompt 要求输出结构化 JSON：

```json
{
  "title": "...",
  "one_liner": "一句话摘要",
  "why_it_matters": "为什么值得看",
  "score": 3,
  "tags": ["agent"]
}
```

score ≤ 2 的直接丢弃，不进日报。

**4. 推送。** 摘要结果渲染成卡片，走 OpenClaw 已配置的 channel 发出去。原始条目保留在库里，日报只是"视图"，想回溯随时查。

## 踩坑点

- **guid 不可信。** 部分源每次抓取 guid 都变，纯 guid 去重会漏。用归一化链接 + 源 ID 做复合键，稳定得多。
- **全文截断太狠，摘要会退化。** 一开始统一截 500 字符，摘要基本在复述标题。后来按 feed 分级：重点源给 4000 字符预算，一般源 1000。
- **单次塞太多条。** 超过 25 条一批，模型开始混淆条目边界，输出串条。分批是硬要求。
- **cron 时区。** 容器默认 UTC，日报早上九点才到。显式声明时区，别赌宿主机配置。
- **静默失败。** 某个 feed 挂了不该让整条管线无声死掉。现在任何阶段抛错都会推送一行错误——宁可吵，不可哑。
- **HTML 转义。** 标题常见 `&#39;`、`&amp;`，渲染前统一 decode 一次。

## 可复用建议

- **先攒后摘，不要逐条调用。** 定时批量处理砍掉大部分 token 成本，也方便统一控制输出格式。
- **原始数据落库，摘要只是视图。** prompt 迭代错了可以重跑，这是管线最重要的保险。
- **抓取层不必造轮子。** 社区有现成的 RSS MCP server 可以直接挂上用；但去重和存储建议留在自己的脚本里，这部分和你的数据强绑定。
- **重要性打分前置。** 让模型摘要的同时打分，低分即弃，比"先全摘再筛"省得多。
- **强制结构化输出。** 自由文本没法稳定渲染成卡片，JSON 输出让下游零解析成本。

## 总结

这条管线跑了两周多，日均 token 成本很低。每天早上花三分钟扫一遍日报，比过去刷半小时 reader 效率高不少。它没有任何黑科技，核心就一句话：把"看什么"和"怎么看"分开——抓取、去重、存储交给确定性代码，判断和压缩交给模型。架构越简单，坏得越少，也越敢改。
