## 背景

Agent 一旦接上外网，第一件想干的事就是“去网页上看看”。但直接把 fetch 工具丢给模型，跑起来往往两种结局：要么整页 HTML 把上下文撑爆，要么 Agent 为了拿到数据开始自作主张——换 UA、加并发、绕限制。这篇帖讲一套实践中反复验证过的做法：把爬取封装成一个克制、可稽核的工具，让 Agent 只负责“读”，不负责“闯”。“稽客”取“稽查”之意——每一次采集，都应有据可查。

## 核心问题

1. **上下文成本**：一个普通商品页 HTML 轻松 200KB+，直接塞给模型又慢又贵，信噪比极低。
2. **合规边界**：robots.txt、ToS、目标站的反爬策略，模型自己不会遵守，除非在工具层强制。
3. **注入风险**：网页正文里可能埋着“忽略之前的指令”这类文本，未经清洗就进上下文等于开门揖盗。
4. **行为漂移**：被 403 之后，Agent 会尝试“更聪明”的绕过方式，这类自主升级必须被拦截。

## 做法

思路是 **MCP 工具收窄 + 管道分层**：

1. **定义窄接口**。工具只暴露 `url` 和 `extractor` 两个参数，`extractor` 限定为 article / product / table 几种预置模式。不给 Agent 裸 HTML 出口，也不给自定义选择器入口——那是人的活。
2. **采集前检查**。工具内部先查 robots.txt，命中 Disallow 直接返回明确错误，而不是让 Agent 看到页面。UA 里带上可联系的标识。
3. **提取而非下载**。headless 浏览器渲染后走 readability 类算法抽正文，转 Markdown，剥离 script/style/注释，默认截断到 8KB 并附截断标记。
4. **清洗与脱敏**。正则过滤疑似指令句式（"ignore previous" 等），按需跑一遍 PII 脱敏，再入上下文。
5. **缓存与限速**。同 URL 结果缓存 1 小时，工具级全局限速（如 1 req/s）、并发上限 2。目标站是数据源，不是对手。
6. **结构化输出**。要求模型按 JSON schema 返回，字段校验失败直接打回重试，避免 Agent 即兴发挥字段名。

## 踩坑点

- **只做 readability 不够**：电商列表页、表格页抽出来是碎的。提前为这几种 extractor 写死规则，收益远大于反复调 prompt。
- **别让 Agent“多抓几页”**：分页逻辑由人固化在工具里，翻页参数不暴露给模型，否则它会自己拼 `page=2`、`page=3` 打到天亮。
- **缓存键要包含 extractor 名**，否则换抽取模式命中旧缓存，排查半天才发现。
- **403/429 返回给模型时附人话解释**（“目标站限流，请稍后再试”），不带解释它会立刻重试三连。
- **请求日志落本地文件**，出问题能回放“Agent 当时到底抓了什么”，这是排查纠纷和误抓的最后一道保险。

## 可复用建议

- 工具越窄越好：能不给的参数就不给，采集策略固化在代码里。
- 模型只读清洗后的 Markdown，永远不接触原始 HTML。
- 一切自主重试、换头、加并发都视为越权，在工具层直接拒绝。
- 错误信息写给“人”看，Agent 只需要知道下一步该做什么。

## 总结

Agent 抓网页的难点从来不是“能不能抓到”，而是抓取行为是否**可控、可查、可复现**。把爬取做成规则先行、接口收窄的工具，模型只承担理解与抽取，边界留在代码里——这套“稽客”式设计，迁移到其他外部数据源（RSS、公开 API）同样成立。欢迎在社区帖下贴出你自己的工具 schema，一起把边界设计打磨得更细。
