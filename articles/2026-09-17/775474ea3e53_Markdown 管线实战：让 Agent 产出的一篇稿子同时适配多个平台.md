## 背景

用 OpenClaw 跑内容类 Agent，LLM 的输出天然是 Markdown。但真正发布时，各平台各说各话：公众号编辑器只吃白名单 HTML，掘金支持完整 GFM，知乎对内联标签很挑剔，静态站生成器还有自己的扩展语法。一篇稿子手动改三遍，是很多人的现状。这篇记录我把它收敛成管线的过程。

## 问题

实际踩过的差异集中在几处：

- task list、脚注、数学公式，只有部分平台渲染；
- 表格在移动端必崩，宽表尤其严重；
- Agent 生成的图片常是本地路径或临时外链，直接发布就是裂图；
- 代码块里也有 `#`、`|`，用正则做全局替换必然误伤。

逐平台堆脚本会越积越乱，最后没人敢动。根因是缺一个 canonical 中间层。

## 做法

管线分四层，全部基于 mdast 操作，用 unified/remark 实现：

1. **规范化层**。不管输入来自哪个模型，先统一换行符、标题层级、图片引用格式，产出 canonical Markdown，作为唯一事实源。
2. **校验层**。remark-lint 加自定义规则：未闭合代码块、空链接、超宽表格直接拦截，错误信息回喂给 Agent 重写，而不是带病往下走。LLM 偶尔会漏闭合 ``` 围栏，越晚发现越难定位，这一步必须前置。
3. **适配层**。每个目标平台一个 transform 插件：公众号把 task list 降级为带前缀的普通列表、脚注转文末段落、HTML 过白名单；知乎 strip 不支持的标签、表格转列表；掘金和静态站基本直通，只处理图片。
4. **资源层**。挂一个上传工具，本地图片推图床后回写 URL，按文件 hash 幂等，不重复上传。

OpenClaw 侧封装成一个 skill / MCP tool：入参是 canonical 文件加目标平台列表，出参是各平台产物；提供 dry-run 模式，只输出 diff 供人工确认。

## 踩坑点

- **永远别用正则直接改 Markdown**。我的第一版用正则替换表格，把代码块里的示例表格也改了。AST 之下无例外。
- 公众号粘贴 HTML 时样式必须内联，类名会被剥掉，用现成的内联化工具比自己拼 CSS 稳。
- 图片外链有防盗链，本地渲染正常不代表发布正常，务必在目标平台实际预览。
- 适配规则写成 platform profile 配置，不要写死在代码里——平台规则半年一变。
- 派生产物不回写 canonical，改稿只改源文件，重新跑管线。

## 可复用建议

- 「AST transform + 平台 profile」是核心抽象，换 markdown-it 实现同样成立。
- 把「Agent 输出是否合法」当输入质量问题处理，lint 前置比发布端兜底便宜得多。
- 每个平台维护一份 golden sample，CI 跑快照测试，平台规则变化时第一时间感知。

## 总结

这套管线没有黑科技：把格式差异从发布时刻挪进管线，用 AST 统一处理，用配置描述平台。上线后单篇三平台发布从手动改稿约 40 分钟降到机器跑一遍加人工扫一眼。真正花时间的是维护 profile，建议从小处起步——先解决图片和代码块这两个最高频问题，再逐步铺开。
