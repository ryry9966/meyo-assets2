## 背景

Agent 的价值不在于会聊天，而在于能落地干活——查工单、发通知、拉数据、改配置。OpenClaw 作为 agent 网关，外部服务对接是绕不开的一环。目前主流路径有两条：写插件直接封装 HTTP 调用，或者挂一个 MCP server 把工具标准化暴露给模型。两条路我都踩过，这篇把流程和坑摊开讲。

## 问题

对接外部服务，真正的难点往往不是"调通一个 API"，而是：

- 凭证放哪，怎么不泄到日志和对话上下文里；
- 模型传参不可控，工具描述写得含糊就开始乱来；
- 超时、限流、重试叠加后，产生重复的写副作用；
- 返回体太大，几个来回就把上下文撑爆。

## 做法

以"对接一个内部工单系统"为例，我的流程是：

**1. 先盘接口，再定边界。** 列出真正需要的端点，通常三五个足够（查单、建单、回复、关单）。只读和可写拆成独立工具，不要一个万能接口包打天下。

**2. 选封装方式。** 接口稳定、想跨多个 agent 复用，就起一个 MCP server（本地 stdio 或远程 SSE）；只是 OpenClaw 自己用、逻辑简单，直接写插件更轻。我倾向 MCP，工具清单和权限可以独立演进。

**3. 凭证只走环境变量或 secret 存储。** API key 不写进配置文件，更不能出现在工具返回值里。OpenClaw 侧做 allowlist，明确哪些工具对哪个 agent 开放。

**4. 工具 schema 要替模型着想。** 参数名用业务语言（`ticket_id` 而不是 `id`），description 写清格式、单位、必填项，最好给一个参数示例。写操作工具加确认参数或二级确认，防误触发。

**5. 响应裁剪。** 在封装层做字段过滤和分页截断，只把模型需要的核心字段吐回去，原始大 JSON 留在服务端日志里查。

**6. 验证闭环。** 先只读 dry run，再放开写权限；全程打 trace 日志，出问题能回放。

## 踩坑点

- **重试 × 非幂等 = 重复建单。** 写接口必须带幂等键（客户端生成的唯一 ID），否则网络抖动一次重试就是两条工单。
- **工具描述太随意。** 我写过一条 description 只有一句"创建工单"，模型把标题塞进了 priority 字段。补上参数示例后，传参准确率立竿见影。
- **超时设太长。** 默认 30 秒超时遇上上游卡死，agent 会一直干等。按接口 P99 设，配合熔断。
- **密钥进了上下文。** 有次调试把原始请求头打进日志，随后被召回进对话。日志脱敏必须在封装层统一做，别指望人肉小心。

## 可复用建议

1. **每个外部服务封一层 thin adapter**：鉴权、重试、裁剪、脱敏收敛在这一层，工具定义保持干净。
2. **错误语义统一**：把上游错误翻译成模型能理解的短句加建议（"令牌过期，请重新授权"），而不是抛原始堆栈。
3. **权限最小化**：只读工具默认开放，写工具逐个审批。
4. **观测先行**：trace id 串起 agent 决策与 API 调用，排障时能对上账。

## 总结

对接外部服务的本质是"给模型立规矩"：接口收敛、权限分级、副作用可控。MCP 解决的是标准化问题，但幂等、脱敏、响应裁剪这些工程细节仍要自己补齐。先把一层干净的 adapter 写好，Agent 才能稳稳伸出手，和 API 完成一次可靠的握手。欢迎在社区里交流你们对接时的 schema 设计和权限方案。
