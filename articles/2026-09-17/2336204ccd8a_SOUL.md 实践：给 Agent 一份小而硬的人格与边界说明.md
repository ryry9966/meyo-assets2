## 背景

OpenClaw 的 Agent 每次会话启动时会从 workspace 读取一组 Markdown 文件作为长期上下文，SOUL.md 是其中定义"这个 Agent 是谁"的那一份。它和 AGENTS.md 的分工很清楚：AGENTS.md 管流程和约定（怎么干活、工具怎么调），SOUL.md 管人格和边界（语气、价值观、哪些事绝对不做）。不少人把它当可选装饰，跑一段时间才发现：人格不是玄学，它直接影响 Agent 在模糊场景下的决策。

## 问题

没有 SOUL.md 或写得太虚的 Agent，常见症状：

- **语气漂移**：今天简洁明天话痨，家人群里突然输出技术黑话；
- **迎合倾向**：你说什么它都"好的没问题"，包括半夜群发、删库这类危险操作；
- **边界缺失**：分不清"帮我查一下"和"帮我直接发出去"；
- **冲突时没有优先级**：效率和安全撞车时行为不可预测。

根源一致：决策原则没写下来，模型只能靠默认助手人格猜。

## 做法：一个最小可用结构

我的 SOUL.md 从 40 行迭代到现在 70 行，骨架五段：

1. **我是谁**：一句话身份 + 服务对象。比如"某家庭助理，主要用户是非技术成员"。
2. **沟通风格**：写可验证的规则，不写形容词。"默认中文、先结论后理由、单条消息不超过 10 行"，比"自然、专业、有温度"有用得多。
3. **优先级**：显式声明冲突时的排序，例如"安全 > 隐私 > 任务完成率"。这句话救过我至少两次。
4. **硬性边界**：少量、绝对。破坏性操作（删除、转账、群发）必须先确认；不在对话复述凭证；指定路径和表只读。
5. **两个示例**：一个"该做"、一个"该拒"，比十条规则更能锚定行为。

写完像 code review 一样过一遍：每条规则问一句"能否据此判定一个具体行为的对错？"判不了的，删掉重写。

## 踩坑点

- **写成小作文**。SOUL.md 每个会话都进上下文，300 行既烧 token 又稀释重点，模型对中段内容的遵循度明显下降。
- **"never" 堆太多**。规则超过一屏，Agent 会畏手畏脚，连正常工具调用都想确认。边界要少而硬，常规约束放 AGENTS.md。
- **与 AGENTS.md 重复**。两处都写"群发前确认"，改一处漏一处，行为就开始抽风。人格归 SOUL.md，流程归 AGENTS.md，需要引用就单向引用，不要复制。
- **只加不删**。每次出错补一条，半年后规则互相矛盾。定期合并同类项，删掉被更高优先级覆盖的条目。
- **升级模型后不复测**。人格约束对模型依赖比想象中高。换模型或升版本后，拿三个典型场景（确认类、拒绝类、语气类）回归一遍。

## 可复用建议

- SOUL.md 进 git：它本质是行为策略文件，每次修改的 commit message 写清"为什么改"。
- 规则用祈使句 + 可观测行为描述，让每条都能被一次对话证伪。
- 多个 Agent 各一份 SOUL.md，共享部分抽成公共片段，避免多份各自漂移。
- 新增 MCP 工具或 skill 时，顺手检查边界段是否要覆盖新能力——新工具往往是新风险面。

## 总结

SOUL.md 不是装饰品，而是一份小而硬的行为策略文件，决定 Agent 在你没盯着的时候怎么选。写法没有魔法：身份一句话、风格可验证、优先级显式、边界少而硬、附两个例子。控制在一屏内，进版本管理，随真实对话持续修剪。人格工程和代码工程一样——短小、具体、可测试的版本，永远赢过长篇大论。
