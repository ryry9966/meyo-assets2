## 背景

OpenClaw 这类 Agent 网关里，cron 任务是最容易被低估的功能：配一个表达式，写一句话 instruction，看起来五分钟就能跑起来。但它的运行模式和对话完全不同——**无人值守、无上下文、无人工确认**。你在聊天里随手写"每天帮我看一下 GitHub 通知"，模型可以靠追问补全；放到 cron 里这样写，跑三次之后你会发现它要么沉默，要么开始瞎编。

## 核心问题

定时任务的 instruction 本质上是**用自然语言写的无人值守程序**。它天然缺三样东西：触发时的上下文、失败时的反馈回路、明确的输出去向。写 instruction 的工作，就是把这三样补齐。

## 我的写法：五段式模板

迭代几轮后，我固定用这个结构：

1. **目标**：一句话说清本次运行产出什么。"整理一下"不算目标，"输出过去 24 小时新增 issue 的标题与链接列表"才算。
2. **数据来源**：写明用哪个工具/MCP 取数，工具名用全称，不要留给模型猜。
3. **步骤**：3–5 步封顶。步骤越多，跳步概率越高。复杂逻辑拆成多个任务或下沉到脚本，Agent 只做编排和总结。
4. **输出**：发到哪个会话/频道、什么格式、长度上限。越具体越好，例如"发到 daily 频道，纯文本 10 行以内；无变化时只发一行 no update"。
5. **异常路径**：明确数据源取不到或为空时怎么办。我会固定写一句：**取不到数据时如实报告原因并跳过，禁止编造或用旧数据顶替**。这大概是性价比最高的一句 prompt。

两个容易漏的细节：

- **时间**：别假设模型知道"现在几点"。要么在 instruction 里注入触发时间，要么让它显式查系统时间再算窗口。
- **变更上报**：日报类任务把"每天汇报"改成"与上次结果对比，仅在变化时输出"。否则一周后没人看那个频道，真正的告警会被淹没。

## 踩坑点

- **用聊天语气写任务**。"帮我看下""顺便整理一下"，在无人值守场景几乎等于没有需求定义。
- **没跑过就启用调度**。我的习惯是：任何 cron 先手动触发一次，确认输出落点、格式、异常路径都对，再开 schedule。
- **时区错位**。cron 表达式的时区和 instruction 里"今天"的时区可能不是一回事，跨时区部署尤其要检查。
- **静默失败**。任务挂了一周没人发现，是因为没人知道它什么时候该出声。加一条：连续失败时向指定频道主动报错。
- **一个 instruction 塞整条流水线**。抓取、清洗、分析、推送全靠一段话，出问题无法定位。拆开，每段可单独测试。

## 可复用建议

- instruction 当代码管理：进 git，改动留说明，每月像 code review 一样过一遍。
- 先手动、后定时；先窄、后宽。宁可任务粒度小，也不要一个定时巨型提示词。
- 团队内统一五段式模板，谁接手都能读懂。

## 总结

Cron instruction 的质量不取决于文笔，而取决于你是否把它当成一个没人盯着的后台程序来对待：上下文自包含、输出可预期、失败会喊人。做到这三点，定时任务才能长期跑着不闹鬼。
