## 背景

单个 Agent 串行跑长任务队列的问题，做过的人都有体感：给主 agent 一批待办任务（比如批量整理文档、给十几个插件跑配置审查），串行执行要一个多小时；上下文越塞越长，后半段质量明显下滑；中途一个任务报错，整条队列卡住。

subagent 编排的思路很朴素：**主 agent 只做拆解、分发、汇总，具体执行交给多个上下文隔离的 subagent 并行完成。**

## 做法

以我们实际跑过的一个场景为例：批量审查 15 个插件的配置文件并输出修订建议。

1. **拆任务**。主 agent 把任务清单落成一组独立任务文件，每个文件包含：输入路径、期望产出路径、验收标准。任务之间不共享可写文件。
2. **限定上下文**。每个 subagent 只拿到任务文件内容 + 按需授予的 MCP 工具权限，不给全局权限。切忌把主 agent 的完整对话历史塞给它——这是最常见的浪费。
3. **限流并行**。并发数默认开 3，用简单队列调度。开太高会撞 API 限流，账单也难看。
4. **文件即总线**。subagent 把结构化结果写到指定路径，返回值只带状态（done / failed / partial）。主 agent 收摘要和文件指针，不收大段文本。
5. **汇总校验**。主 agent 逐个检查产出文件是否存在、结构是否合规，failed 的任务重新入队，最多重试 2 次。

代码层面就是一个标准的 fan-out / fan-in：

```text
tasks   = split(manifest)
results = pool.map(run_subagent, tasks, workers=3)
report  = aggregate(verify(results))
```

## 踩坑点

- **两个 subagent 改同一个文件**。第一版没做写路径隔离，两个 agent 同时编辑一份共享配置，后写覆盖先写。解法：任务粒度按“不可再分的写目标”切，或各写独立副本由主 agent 合并。
- **subagent 谎报完成**。它声称做完了，产出文件却是空的。后来立了规矩：状态声明一律不采信，只认文件证据，没有产出即视为 failed。
- **重试不幂等**。失败重试导致同一插件生成两份修订建议。给每个任务固定 ID，产出文件名带 ID，重试前先清理旧产物。
- **拆得太细**。有次把一个任务拆成 20 个 subagent，调度和汇总的开销比串行还大。经验值：单任务耗时低于 30 秒的不值得拆。

## 可复用建议

- 用文件系统做 subagent 间通信总线，天然可审计、可断点续跑。
- 每个 subagent 的工具权限收窄到“刚好够用”，MCP 工具按任务白名单授予。
- 并发从 3 起步，观察限流与错误率再调。
- 主 agent 上下文只放任务清单、状态摘要、失败原因；细节永远在文件里，不进上下文。
- 每次 subagent 的输入输出落盘，出问题能回放，不靠猜。

## 总结

subagent 编排不神秘，本质是工程里早就有的 fan-out/fan-in，只是执行单元从线程换成了带上下文的 agent。真正决定成败的不是并行本身，而是任务边界的划分、结果的校验方式，以及“只认文件证据”这条纪律。那批插件审查任务，我们从串行 70 分钟压到并行 18 分钟，且失败可单独重跑。如果你的 agent 也经常在长任务队列里越跑越糊涂，值得试一次。
