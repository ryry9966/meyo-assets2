## 背景

我们团队有十来个服务，日志分散在几台主机和 CI 系统里。以前日报靠值班同学手动汇总：翻日志、数报错、抄指标，每天花 20-40 分钟，质量还看人。于是我用 OpenClaw 搭了一条全自动日报流水线，跑了近两个月，基本稳定。

## 问题

直接"把日志丢给 Agent 写日报"有三个硬伤：

1. 原始日志量大，动辄几十万行，远超模型上下文；
2. 数字类内容（错误次数、耗时分位数）交给模型算，必然出现幻觉；
3. 失败没有兜底，一次 Agent 调用挂了，当天就没日报。

核心思路因此很明确：确定性的活交给脚本，模型只负责它擅长的归纳与叙述。

## 做法

流水线分四步，每天 08:00 由 OpenClaw 定时任务触发：

**1. 采集与聚合（纯脚本）**。Python 脚本拉取前一天的服务日志、Git 提交、CI 记录，按统一 schema 聚合成 JSON：错误按类型去重计数、耗时算 P95、部署列 commit 清单。这一步不涉及模型。

**2. 结构化数据进 Agent**。聚合后的 JSON 通常只有几十 KB，通过 MCP 资源挂给 OpenClaw Agent。Prompt 里明确约束：只允许引用 JSON 里出现的数字，禁止自行推断；输出必须套固定模板（总体状态 / 异常与归因 / 变更记录 / 明日关注）。

**3. 确定性校验**。模型输出后，脚本做一层回验：报告里的数字逐项与聚合 JSON 比对，不一致就打回重生成（最多 2 次），仍失败则降级为纯数据版报告。

**4. 分发与归档**。校验通过后推 webhook 到群，同时把聚合 JSON 和最终 Markdown 归档，便于事后追溯。

## 踩坑点

- **让模型算数字是最大的坑**。第一版我偷懒让它直接读原始日志，错误计数差了 30% 多。改成脚本统计后，数字问题彻底消失。
- **时区**。三台机器日志时区不一致，日报把"昨天"算错了一半。统一在聚合脚本里转 UTC+8，并在 JSON 里显式带日期字段。
- **幂等**。手动补跑一次，群里出现两份日报。现在每次运行前按日期做幂等键，已存在则覆盖。
- **上下文超限**。某天一次故障打了 8 万条重复堆栈，聚合 JSON 暴涨。去重 + TopN 截断这步不能省。
- **降级路径要真测过**。模拟 Agent 超时时才发现，降级报告模板没写完，推出去的是空报告。

## 可复用建议

- 模板与数据分离：模板存版本库，数据永远来自聚合 JSON，别让模型"创作"结构。
- 数字经过两次落地：脚本算一次，校验脚本对一次。
- 灰度上线：前两周只发草稿到私有频道，人工确认后再转正式推送。
- 给流水线自身加心跳：连续两日没产出就告警——日报系统自己没日报，才是最尴尬的故障。

## 总结

这条流水线的价值不在于"用了 Agent"，而在于把责任切干净：数据正确性归脚本，表达质量归模型，流程可靠性归幂等与降级。Agent 做的是最后 10% 的润色，却让整个流程看起来"智能"。有类似需求的，建议从"脚本聚合 + 模型叙述 + 确定性校验"这个最小结构起步，别一开始就把原始日志直接塞给模型。
