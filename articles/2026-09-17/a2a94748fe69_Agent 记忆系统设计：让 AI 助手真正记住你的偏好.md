## 背景

Agent 的一个老问题：它是无状态的。上周你说过"项目统一用 pnpm"，这周它又开始生成 npm 命令；你调好的代码风格偏好，下次会话全部归零。上下文窗口再大也解决不了这件事——窗口是临时工作台，不是档案柜。对做自动化和工作流的用户来说感受更深：一个每天跑的 Agent，如果记不住部署习惯、命名规范、常用路径，就只能靠一段手写 system prompt 硬编码，改一处就要重发一遍。

## 三种常见的错误做法

1. **全塞进 system prompt**：偏好一多，提示词膨胀到几千 token，关键信息反而被淹没，成本也上去了。
2. **存整段聊天记录再检索塞回**：历史对话噪声极大，一段无关闲聊就能把关键偏好挤出 top-k。
3. **只做会话内摘要**：会话结束即失效，跨会话等于没做。

## 我们的分层设计

实践里比较稳的结构是三层：

- **工作记忆**：当前会话上下文，不落盘，交给框架。
- **偏好记忆（核心）**：结构化 KV 存储，每条记录至少含 `key / value / scope / confidence / source / updated_at`。例如 `{key: "包管理器", value: "pnpm", scope: "全局", confidence: 0.9, source: "用户显式指令"}`。
- **情景记忆**：会话结束后的压缩摘要，用于回答"上次聊到哪了"，与偏好记忆分开存。

**写入策略比存储结构更重要。**我们的规则：只有两类信号才写入——用户显式表达（"以后都用…""别再…"），或小模型抽取出的高置信度重复模式。写入走独立的 MCP 工具 `memory_write`，读取走 `memory_search`，Agent 可主动调用；同时每次会话开始时系统自动检索 top 5–8 条高置信度偏好注入 prompt。

读取时做三件事：按 scope 过滤（项目级优先于全局）、按 updated_at 裁决冲突（新覆盖旧）、按 confidence 排序后截断。

## 踩坑点

- **记忆污染**：一句临时的"今天先用 yarn"被永久固化。对策：confidence 按来源分级——显式指令给高值，模式推断给低值，低置信度条目超过 N 天未复现就降权。
- **偏好冲突**：新旧记忆打架时不要简单去重，保留版本，用 updated_at 裁决，冲突条目标记出来下次主动向用户确认。
- **注入风险**：记忆内容会进 prompt，等于把历史输入变成了持久化攻击面。source 字段必须保留，来源不可信的内容只作参考文本，绝不当作指令拼接。
- **检索贪多**：top-k 拉到 20 条，关键偏好反而被稀释，宁少勿多。
- **缺少用户可见性**：必须提供"列出 / 删除我的记忆"的入口，这既是隐私合规要求，也是排查记忆污染的唯一手段。

## 可复用的建议

1. **先别上向量库**。偏好记忆是结构化数据，SQLite + 字段过滤能覆盖 80% 场景；只有情景摘要才需要嵌入检索。
2. **schema 先行**：source、confidence、updated_at 三个字段第一天就要有，后补成本极高。
3. **建一个小评测集**：20 条已知偏好 + 10 条干扰对话，定期跑召回率和误注入率。记忆系统没有指标就是玄学。
4. **写操作可审计**：记录每次写入的触发消息 ID，出现污染能定位、能回滚。

## 总结

记忆系统的难点不在存储，而在写入门槛和冲突治理。先用最简单的结构化 KV + 严格写入规则跑起来，再逐步加检索和衰减机制。一条原则送给大家：**一条错误记忆比十条缺失记忆伤害更大**——宁可让 Agent 少记住，也别让它记错。欢迎在社区里贴出你们的 memory schema 和误注入案例，一起迭代。
