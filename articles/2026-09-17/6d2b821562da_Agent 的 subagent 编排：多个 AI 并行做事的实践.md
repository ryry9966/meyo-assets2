## 背景

大多数 agent 框架默认是单会话串行循环：主 agent 拿到任务 → 调工具 → 等结果 → 继续。做“帮我查个东西”这种事没问题，但任务一旦变成“同时看三个数据源、各自整理、最后汇总”，串行就成了瓶颈——不是模型不够聪明，而是时间都花在排队上。

还有一个更隐蔽的问题：所有中间过程都堆在同一个上下文里。跑上二三十分钟，主上下文被工具调用的原始输出塞满，模型开始“遗忘”最初的指令。OpenClaw 的 subagent 机制正好针对这两点：主 agent 可以把子任务派生（spawn）到独立会话，子会话有自己的上下文和工具权限，跑完只把摘要交回主会话。

## 问题

我的典型场景是定时巡检多个数据源并整理成日报。串行跑要十几分钟，而且巡检过程的原始输出会污染主会话，影响后续交互。目标很朴素：**并行、隔离、结果可聚合**。

## 做法

1. **先定任务粒度。** 一个 subagent 的任务应该是“能在几分钟内独立完成、不依赖其他子任务结果”的事。拆太细（一次工具调用拆一个）调度开销超过收益；拆太粗（整份报告丢给一个子 agent）等于没拆。
2. **主 agent 只做三件事：拆任务、派发、聚合。** 派发时给每个子任务带明确的输入、期望的输出格式、超时时间。
3. **上下文隔离。** 子 agent 的 prompt 显式写清“你只做 X，结果以约定格式返回”，不要把主会话历史整段带过去。
4. **聚合阶段做减法。** 主 agent 只读摘要字段，原始长输出落盘成文件，需要时再按需读取，避免聚合时又把主上下文撑爆。
5. **控制并发度。** 同时 3~5 个比较稳，具体看下游 API 的限流。

伪代码骨架大致是：

```text
plan    -> 拆成 N 个独立子任务（各自有输入/输出契约）
spawn   -> 每个子任务派一个 subagent，带 timeout
collect -> 收摘要，超时/失败记为显式错误项
merge   -> 汇总成最终结果，原始输出写文件
```

## 踩坑点

- **递归失控**：子 agent 又派子 agent。要硬性限制深度，我们设 1 层，够用。
- **竞态写入**：多个子 agent 写同一个文件。改成每个子 agent 写自己的输出文件，聚合时统一合并。
- **摘要丢信息**：不约定输出格式，子 agent 会自由发挥，聚合时字段对不上。输出契约必须先行。
- **没有超时兜底**：子 agent 卡死比失败更麻烦。务必设 timeout，失败时返回明确的错误结构，而不是静默。
- **成本**：并行 5 个 agent 各自跑满上下文，token 消耗是串行的数倍。低价值任务不值得拆。

## 可复用建议

- **判断要不要拆**：任务里有没有“可并行的独立读操作”。有就拆，纯串行逻辑别硬拆。
- **契约先行**：先定义子 agent 返回的结构（字段名、类型），再写 prompt。
- **把子 agent 当无状态函数**：输入明确、输出明确、不碰主会话状态。
- **留账**：每次派发记录任务 ID、耗时、token 消耗，事后好算成本。

## 总结

Subagent 编排不是让 AI 变聪明，而是让工程结构变合理——**并行省时间，隔离保上下文，契约保证可聚合**。它适合“多源独立子任务 + 最终汇总”这种形状的问题，不适合强依赖、强状态的流程。建议先挑一个两路并行的真实任务试起，把契约和超时跑通，再逐步扩展并发度。
