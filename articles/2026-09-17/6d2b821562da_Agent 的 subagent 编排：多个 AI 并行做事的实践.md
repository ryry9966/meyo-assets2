## 背景

单 agent 串行干活的痛点大家应该都遇到过：让它"调研三个竞品的定价策略再汇总成表"，它会一个接一个地搜、读、总结，上下文越堆越长，中途一次工具调用失败就全盘重来。上下文窗口是硬约束，而这类任务里的子任务本质上互相独立，完全可以并行。

我们团队把一部分长流程任务改成了 subagent 编排：主 agent 负责拆解、派发、汇总，子 agent 各自在独立上下文里干活。跑了几个月，有些经验值得沉淀下来。

## 问题

直接让主 agent 一个人扛，主要有三类问题：

1. **上下文污染**：调研 A 的中间网页内容会干扰后续对 B 的判断；
2. **串行耗时**：五个独立任务排队执行，总时长是求和而不是取最大值；
3. **失败放大**：中间某一步超时，整条链路挂掉，重跑又从头来。

## 做法

我们的编排模式比较朴素，分四步：

**第一步：判断可并行性。** 只把满足三个条件的子任务拆出去：输入自包含（不依赖其他子任务的中间结果）、操作以只读为主（搜索、抓取、分析、审查）、产出可结构化。有依赖链的任务老老实实留在主流程里串行。

**第二步：为每个 subagent 写窄提示词。** 这是收益最大的一步。子 agent 看不到主 agent 的对话历史，所以 prompt 必须给足：明确的任务边界、必要背景、统一的返回格式（我们固定为 JSON：结论、依据、置信度、失败原因），外加一句"拿不到就说拿不到"。子 agent 的 system prompt 单独维护，每个不超过十几行，别复用主 agent 那套冗长人设。

**第三步：并发派发，限制并发度。** 通过并行工具调用（或 MCP 侧的批量任务方式）同时发出。并发度我们压在 3–5，再高会撞 API 限流，成本也会失控。

**第四步：主 agent 汇总与裁剪。** 子 agent 返回后不做原样拼接，先压缩：只保留结论和关键依据，剔除原始网页摘录，汇总上下文才不会爆炸。

## 踩坑点

- **写操作别盲目并行。** 三个子 agent 同时往同一个配置文件写入，谁后写谁赢，而且不报错。我们的原则：只读任务随意并行；写任务按资源分片（每个子 agent 只写自己的文件或分区），否则串行加锁。
- **子 agent 静默失败。** 有的子 agent 拿不到数据时会编一个看起来合理的答案。所以返回格式里强制带 `confidence` 和 `sources` 字段，主 agent 汇总时校验，低于阈值标记"待人工确认"。
- **限流与超时要显式处理。** 有次开了 8 个并发，触发限流后子 agent 全部超时，主 agent 却以为任务完成了。重试和熔断必须写在编排层，不能指望子 agent 自己优雅退出。
- **不是所有任务都值得并行。** 拆分和汇总本身有开销，子任务太碎反而更慢。

## 可复用建议

1. 把"拆解—派发—校验—汇总"抽成固定模板，子 agent 的 prompt 和返回 schema 做成配置而非硬编码；
2. 先在只读场景（调研、代码审查、日志排查）落地，验证收益后再碰写场景；
3. 记录每次编排的子任务耗时和失败率，两周数据就能告诉你哪些任务值得并行、哪些是伪需求；
4. 汇总环节永远做压缩，别让子 agent 的原始输出直接进主上下文。

## 总结

subagent 编排不是银弹，它只是把"一个很累的 agent"换成"一个会派活的 agent 加几个很窄的 agent"。核心纪律三条：任务可拆才拆、写操作要么分片要么串行、结果必须结构化且校验。做到这三条，我们这边长流程任务的耗时普遍压到了原来的三分之一左右——更重要的是，单点失败不再意味着全部重来。欢迎在社区里交流你们的编排结构。
