## 背景

用 OpenClaw / Agent 做日常开发时，最容易被"顺手自动化"的就是 Git：写 commit message、按规范建分支、整理提交历史。这些操作重复度高、规则明确，很适合交给助手。但 Git 又是出事成本最高的地方之一——一次误操作的 push 或 reset，比十次糟糕的提交更难收拾。这篇记录我们落地的做法和踩过的坑。

## 问题

直接给 agent 开 Git 权限，典型问题有四个：

1. **提交质量不稳定**：模型自由发挥，message 时而精细时而敷衍，团队风格无法统一。
2. **越权操作**：agent 理解偏差时会自作主张 `push`、`reset --hard`、改历史。
3. **上下文膨胀**：大 diff 直接塞进上下文，token 爆炸还抓不住重点。
4. **分支失控**：随手建分支、命名混乱，两周后没人记得哪条分支是干嘛的。

## 做法

核心原则：**读操作放开，写操作收口，危险操作人工确认**。

**第一步：只读工具先行。** 通过 MCP git server 或带白名单的 shell 工具，只暴露 `status`、`diff`、`log`、`branch -a` 这类只读命令。先让 agent"看懂"仓库，再谈操作。

**第二步：约定大于自由。** 把 commit 规范（Conventional Commits + 团队 scope 列表）和分支命名规则（如 `feat/issue-123-short-desc`）写进系统提示或插件配置，再配两三条团队真实提交做 few-shot 示例，效果远好于只描述规则。

**第三步：两段式提交。** 我们的工作流是：

- agent 读取 staged diff，产出 message 草稿 + 变更摘要；
- 人类在终端确认（或走交互确认工具）；
- 确认后才执行 `git commit`。

**第四步：分支自动化，但划清边界。** 从 issue 建 `feat/issue-xxx` 分支、收尾时列出可清理分支，这类任务可以完全托管；`push`、`merge`、`rebase` 一律要求显式人工指令。

## 踩坑点

- **pre-commit hook 会改文件**：格式化 hook 动过文件后，agent 容易陷入"为什么有未暂存变更"的循环。要求它 commit 后重跑一次 `status` 再下判断。
- **大仓库 diff 溢出**：先给 `diff --stat`，让 agent 决定看哪些文件，再拉具体 diff。
- **agent"顺手"修无关文件**：提示里必须明确"只操作已 staged 内容，禁止自行 add 未提及的文件"。
- **凭证暴露**：agent 有时会把含 token 的 remote URL 原样输出到日志，工具层要做脱敏。

## 可复用建议

1. **白名单而非黑名单**：明确列出允许的 git 子命令，其余一律拒绝。
2. **审计日志**：agent 执行的每条 git 命令都落盘，出问题能回放。
3. **模板化工作流**："提交草稿 → 人工确认 → 执行"做成可复用模板，PR 描述生成同理。
4. **危险操作永不全自动**：push / merge / rebase / clean 永远走人工确认，不要为省一步拆掉保险。

## 总结

Git 自动化的价值不在"全自动"，而在把重复判断（message 怎么写、分支怎么命名）交给模型，把不可逆决策留给人。读放开、写收口、审计留痕——这套模式跑了月余，提交规范执行率明显上升，误操作为零，关键是那道人工确认一直没拆。
