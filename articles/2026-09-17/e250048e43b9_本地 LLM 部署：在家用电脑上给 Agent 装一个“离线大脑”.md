## 背景

跑 Agent 做自动化这两年，我一直混用云端 API 和本地模型。把一部分推理搬回家的原因很朴素：一是敏感数据（日志、私人文档、家庭照片索引）不想出网；二是批量跑任务时 API 费用累积得比想象快；三是断网时自动化链路直接瘫痪。本地模型不是替代云端，而是给 Agent 体系补一个常驻的、便宜的、可控的底层。

## 问题

家用电脑跑大模型，核心矛盾是资源：

- 显存/内存有限，模型体积和上下文长度互相挤压；
- Agent 场景对 tool calling 的格式稳定性要求高，而小模型恰恰在这点上弱；
- 网上教程大多停在“跑通 demo”，没人告诉你接进 Agent 框架之后会发生什么。

我的硬件参考：一台 32GB 内存的 Mac，一台 12GB 显存的 Windows 台式机，以下经验在两台机器上都验证过。

## 做法与步骤

**1. 先盘硬件，再谈模型。** 粗略估算：Q4 量化的 7B 模型约占 5GB，14B 约 9GB，还要留 KV cache 的余量。8GB 显存老老实实跑 7B；16GB 可以摸到 14B；Mac 统一内存可以分一半给模型。

**2. 推理框架选型。** 只求快速跑通用 Ollama；要精细控制采样参数和量化格式用 llama.cpp；需要并发吞吐且显存充裕再上 vLLM。家用场景我 90% 的时间用 Ollama，维护成本最低。

**3. 模型选择。** 中文 + tool calling 场景，我固定用 Qwen 系列的 Q4_K_M 量化版，能力损失可接受，体积砍到三分之一。别碰 Q2 量化，小模型的推理能力塌得很快。

**4. 暴露 OpenAI 兼容接口。** Ollama 自带 `/v1` 端点，Agent 框架基本能直接接。三件事必须手动设：`num_ctx` 拉到 8192 以上（默认值对 Agent 长上下文远远不够）、`keep_alive` 设长一点、`base_url` 指向本机端口。

**5. 接入 OpenClaw 验证。** 本地跑一个最简单的 MCP server（只做文件读写），让模型完成“读目录 → 总结 → 写文件”的链路，连续跑十次看成功率。这一步是试金石。

## 踩坑点

- **context 默认值陷阱**：不显式设 `num_ctx`，长对话会中途“失忆”，且没有任何报错，我排查了一晚上才定位。
- **小模型 tool calling 不稳**：7B 在参数复杂时会把 JSON 拼错。解法是在系统提示里给严格输出模板，Agent 侧加一层 JSON 校验 + 重试。
- **显存溢出静默降速**：不够时部分框架会把层卸到 CPU，速度从 30 token/s 掉到 3，没有报错只有变慢。跑之前先盯一眼显存占用。
- **模型反复冷启动**：两次调用间隔超过 `keep_alive` 默认值，模型就重新加载，一次 20 秒起步，Agent 循环里尤其致命。

## 可复用建议

- **分层路由**：简单任务（分类、抽取、格式转换）走本地，复杂推理和长文写作走云端。Agent 配置里准备两套 model profile 即可切换。
- **本地模型当隐私过滤器**：敏感原始数据先由本地模型脱敏摘要，再交给云端处理。
- **写个健康检查脚本**：定时探测端口、显存和一次最小推理，异常就推通知。本地服务挂了没人提醒，是最容易被忽略的运维点。

## 总结

家用电脑跑本地 LLM，以前是玩具，现在已经是能进生产自动化的实用件。我的结论：7B–14B 量化模型 + Ollama + 严格的输出校验，足以承担 Agent 体系里三成的日常调用量。它不会取代云端大模型，但让整条自动化链路在断网、限流、隐私敏感这几个场景下多了一条退路。先跑通一条最小链路，比纠结跑多大的模型更有价值。
