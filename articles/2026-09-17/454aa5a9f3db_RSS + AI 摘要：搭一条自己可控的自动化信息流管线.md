## 背景

订阅源一多，Read it later 就变成了 never read。RSS 虽然老，但它是少数不被算法干预、完全由自己掌控的分发协议。真正的问题是：源可以自动化，读不能。于是我把"读"这一步也交给模型，人只看摘要，再决定要不要点进去。

## 问题

实际要解决三件事：

1. 源更新频率极不均匀，有的日更几十条，有的周更一条，人工扫标题成本太高；
2. 直接把全文塞给 LLM，token 成本爆炸，而且大部分条目根本不值得细读；
3. 管线一旦不稳定（feed 挂了、编码错了、模型抽风），人就不信它了，整套东西形同虚设。

## 做法

分层搭，抓取与摘要解耦：

**数据层**：用 Miniflux/FreshRSS 或直接拉 RSSHub 聚合源，OPML 管订阅。自建的关键是原始条目留档，模型升级后可以重跑。

**抓取层**：定时任务（cron 或 OpenClaw 的定时技能）每 2~4 小时拉一次，按 guid/link hash 去重后落 SQLite，带上 ETag/Last-Modified，对源礼貌一点。

**摘要层**：每天固定时间触发批处理。分两段——先用便宜模型按标题+简介粗筛打分，过线的才进正式摘要。Prompt 要求结构化输出：一句话结论、三个要点、原文链接、置信度，强制 JSON，方便下游渲染。

**输出层**：日报落 Markdown 到笔记目录，同时推一份到 IM。标题和链接永远保留——摘要是入口，不是替代品。

如果按 MCP 思路做，fetch、dedup、summarize、notify 各封装成独立 tool，由 Agent 调度串联，失败可以单点重试，不用整条管线重来。

## 踩坑点

- 很多 feed 只有 summary 字段且被截断到两三百字，摘出来全是废话。要么抓全文做 readability 提取，要么在 prompt 里允许模型标注"信息不足"；
- 同一篇文章常出现在多个源，去重要做在标题归一化之后（去空格、全半角、utm 参数）；
- 列表类内容（周报、changelog）让模型"总结"容易编细节，改成逐条抽取效果稳定得多；
- 定时任务重叠执行会重复推送，加文件锁或状态检查；
- 单条超长文本会撑爆上下文，先截断到固定长度再入队，别指望 prompt 里写一句"请忽略多余内容"。

## 可复用建议

- 原始条目永远落库，摘要只是视图，可重算；
- 粗筛 + 精摘两级结构，比一级直摘省 70% 以上 token；
- Prompt 里显式给出输出 schema，不要靠模型自觉；
- 给每个源加"静默开关"：连续失败 N 次自动停用并提醒，避免日报里全是报错。

## 总结

这套管线的核心不是"AI 帮你读"，而是把信息获取拆成抓取、过滤、摘要、分发四个可独立替换的环节，模型只是其中一环，随时可升可降。跑通之后，每天的信息消费从"刷"变成"过一遍日报、挑两篇精读"。建议先接 3~5 个源跑两周，观察误杀和漏报，再逐步扩量。
