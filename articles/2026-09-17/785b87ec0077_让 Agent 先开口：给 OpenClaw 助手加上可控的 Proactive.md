## 背景

用 Agent 这么久，绝大多数交互还是"你问它答"。但自动化真正的价值往往出现在没人盯着的时候：CI 挂了、仓库有新 issue、监控越过阈值。所谓 proactive，就是让助手基于外部信号——时间、事件、状态变化——主动发起任务，而不是干等你输入。听起来很美好，实际落地时坑比想象多。

## 问题

直接给 agent 挂个定时任务就算"主动"了吗？实践里会撞上三个矛盾：

1. **触发容易，收敛难**：按分钟轮询，token 烧得飞快，产出大多是噪音。
2. **主动执行有风险**：写操作没人确认，出问题就是事故。
3. **噪音反噬信任**：推送三次没用的消息之后，用户会直接关掉整个通知通道——proactive 当场死亡。

所以核心工程问题不是"怎么触发"，而是"什么时候值得触发，触发之后敢做多大的动作"。

## 做法

我的方案分三层，全部用 OpenClaw 现有机制拼出来，没写额外框架。

**1. 感知层：事件进，而不是 LLM 轮询**

- 定时类：cron 触发，最小间隔 30 分钟起步，别按分钟跑。
- 事件类：Webhook 或 MCP 工具回调（git push、新邮件、文件变更、告警）。
- 关键点：感知层是普通脚本，不经过 LLM。先用代码做条件过滤（比如"只有失败的 CI 才往下游发"），模型只处理值得处理的事件。

**2. 决策层：把"要做的事"和"能做的事"分开**

Agent 被唤醒后的产出不是直接执行，而是一份结构化提议（动作、目标、理由、风险等级），然后过一道 gate：

- 只读操作：直接执行；
- 低风险写（建草稿、写自己的笔记）：执行后通知；
- 高风险操作（对外发消息、删改数据、花钱）：只生成提议，等人确认。

**3. 执行层：统一通知 + 审计**

所有主动动作走同一个通知通道，附提议内容；每次执行落日志（时间、触发源、动作、结果）。排障时这是唯一的救命稻草。

## 踩坑点

1. **去重没做，一夜 40 条消息**：同一告警源反复触发。解法：按触发源 key + 时间窗去重，窗口内重复事件只更新状态，不重新唤醒。
2. **唤醒时塞全量上下文**：每次主动运行都带完整记忆，成本翻几倍。改成只注入"相关摘要 + 本次事件数据"。
3. **权限复用太宽**：调试时给过一次全权限 profile 忘了换回，proactive 任务半夜跑了写操作。主动任务应单独 profile，最小权限。
4. **静默时段没设**：凌晨三点推消息很败好感。加 quiet hours，非紧急事件进队列，早晨合并成一条摘要。
5. **提议格式不稳定**：早期让 agent 自由发挥，gate 解析不了。后来强制 JSON schema，解析失败一律降级为人工确认。

## 可复用建议

- 从只读 proactive 起步，跑两周确认信噪比，再放开低风险写。
- 每个主动任务必须有 kill switch：一个配置项或一条命令能整体停掉。
- 频控三件套：最小触发间隔 + 时间窗去重 + 每日配额。
- 用"打扰成本"评估规则是否值得上：一周主动找你几次？每次是否真省了事？超过两次且偶尔没用，先撤。
- 确认交互要一键化：确认 / 拒绝 / 忽略三个按钮，别让人打字。

## 总结

Proactive 不是让 agent 更"聪明"，而是给系统加上一套"什么时候值得出声、出声后能做多大动作"的纪律：感知用普通代码收敛信号，决策用结构化提议控风险，执行用统一通道保审计。先把只读场景跑稳再谈自动化——信任是 proactive 的前提，噪音毁掉的信任，比它省下的时间难补得多。
