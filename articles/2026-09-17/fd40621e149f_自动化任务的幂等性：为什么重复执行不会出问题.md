# 背景

在 OpenClaw 这类常驻 Agent 环境里，自动化无处不在：cron 定时摘要、消息回调驱动的工具调用、插件同步任务、MCP 写入操作。它们的共同点是：你没法保证"只执行一次"。

超时重试、调度重叠、平台消息重投、用户手动补跑，甚至模型自己判断"上一步好像失败了"再调一次工具——重复执行是常态，不是异常。

# 问题

幂等性指同一操作执行一次和执行 N 次，最终状态一致。多数写入型操作天然不满足：create 产生重复记录，send 刷屏，append 污染数据文件。

最麻烦的是"请求生效但响应丢失"：任务已经执行成功，程序却没收到确认，于是重试。这不是 bug，而是分布式环境的默认行为。问题不在重试本身，而在重试不安全。

# 做法

以"每天推送群摘要"为例，一个可复制的最小方案：

1. **定义确定性任务键**。不要用随机 UUID，用逻辑键如 `digest:2025-06-01:group_a`。同一逻辑任务无论触发几次，键不变。
2. **执行前查重、成功后落库**。本地建一张 `run_log(run_key, status, ts)` 表（SQLite 足够），键已存在则直接跳过。
3. **优先用收敛型写法**。upsert 代替 create，set 状态代替 append，配合唯一索引和 `ON CONFLICT DO NOTHING` 兜底。重复执行只是覆盖成同样的结果。
4. **防调度重叠**。长任务用锁文件或 advisory lock，拿不到锁立即退出，避免两份实例并行。
5. **主动验证**。测试时故意连跑两次，确认没有重复消息、没有重复记录。这一步比任何推理都可靠。

# 踩坑点

- **随机数当幂等键**：每次重试生成新键，等于没做。键必须由任务逻辑推导。
- **时区不一致**：同一逻辑运行在不同机器上算出不同日期、不同键。统一用 UTC。
- **只查内存不落盘**：进程重启后记录丢失，防了个寂寞。唯一约束要建在存储层，不能只靠内存判断。
- **先执行后记录的崩溃窗口**：发送成功、记录前崩溃，下次仍会重复。彻底消除需要事务或预写意图，多数场景接受这个小概率窗口，但要心里有数。
- **指望模型"别调两次"**：Agent 的重试决策不可靠，幂等必须做在工具/插件层，而不是提示词里。
- **查重表无限增长**：加保留策略，定期清理。

# 可复用建议

- 审查自动化任务时默认问一句：这步是读还是写？读天然安全，写必须收敛。
- 封装 `ensure_*` 风格的工具：`ensure_ticket`、`send_once`，让上层调用可以无脑重试。
- 幂等做对了，才敢放开重试策略——调度器和 Agent 的自动重试、故障续跑，都是靠它托底的。
- 新任务上线检查项：连跑两次无副作用、崩溃后重跑能续上、并发触发不双写。

# 总结

幂等性不是阻止重复执行，而是让重复执行变得无害。在 Agent 自动化里，重试无法避免，也不该避免——要做的是让每一次重试都收敛到同一个结果。把幂等做进工具层，上层的一切重试、补跑、并发，就从风险变成了常规操作。
