## 背景

写自动化脚本、给 Agent 挂定时任务时，最初的假设往往是"一个任务只跑一次"。但真实运行环境里触发源不可控：Cron 任务可能重叠，Webhook 会被上游重发，MCP 客户端超时后重试，用户手动再点一次，Agent 规划失败后重新执行。**重复触发是常态，不是异常。**

## 问题

幂等性说的是：同一个任务执行一次和执行多次，最终结果一致。

不满足时的问题很具体：消息发两遍、文件被追加两次、数据库出现重复记录、第三方接口被重复调用。Agent 场景里更隐蔽——LLM 输出不确定，同一条指令重放时参数可能漂移，你以为没重复，副作用其实已经叠加了。

## 做法

给任务加幂等保护，核心是三步：

1. **定义幂等键。** 用一个稳定标识代表"这件事"，比如 `hash(触发源 + 业务参数 + 业务日期)`。键必须来自原始触发数据，不要让模型生成——模型输出不稳定。
2. **先登记，后执行。** 执行前在持久化存储（SQLite、Redis 均可）里查这个键：存在且成功就跳过；不存在就原子写入"执行中"再跑。最简单的兜底是数据库唯一索引。
3. **副作用写成状态收敛。** 优先用 `INSERT ... ON CONFLICT DO UPDATE`、upsert、"SET 到目标状态"这类确保型写法，而不是"创建 X"这种动作式写法。调外部 API 时尽量传幂等键（多数支付/云服务支持），不支持就先查后建。

## 踩坑点

- **check-then-act 竞态**：两个 worker 同时查到"不存在"，然后都执行。查询本身不解决问题，必须原子抢占——Redis `SET NX EX`，或靠唯一索引让第二个插入直接失败。
- **键里混入时间戳或随机数**：每次都不同，幂等形同虚设。
- **超时但实际成功**：状态卡在"执行中"，重试又跑一遍。给运行状态设 TTL，或执行后补一次对账确认真实结果。
- **以为读操作天然安全**：读本身幂等，但"读了再写"整条链路就不幂等了，边界要算到副作用为止。
- **执行记录无限增长**：给执行表加清理策略，比如只保留 30 天。

## 可复用建议

- 把幂等逻辑抽成统一的 task wrapper：调用方传入幂等键，内部负责查重、抢占、记录结果，业务 handler 只写纯逻辑。改一处，所有任务受益。
- 在 MCP 工具层就做幂等设计。Agent 重试是常态，工具不幂等，上层怎么兜都兜不住。
- 定期演练：手动重放一次已完成任务，确认行为是"跳过"而不是"重做"。这比任何文档都可信。

## 总结

幂等不是高级特性，而是自动化系统的默认要求。凡是会被触发的任务，都应默认"它可能被触发第二次"。稳定的幂等键 + 原子登记 + 状态收敛式副作用，能让重复执行从风险变成安全网——重试可以放心开，故障恢复只需重放。可靠性不是靠"保证不重复"实现的，而是靠"重复了也无害"实现的。
