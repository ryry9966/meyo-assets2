## 背景

用 OpenClaw 跑自动化一段时间后会发现：重试不是异常，而是常态。cron 定时任务遇到网络抖动重跑、Agent 调 MCP 工具超时后被框架重试、手动补跑昨天漏掉的任务、渠道消息重复投递。同一个任务被执行两次甚至多次，几乎无法避免。

## 问题

麻烦不在重复执行本身，而在副作用被重复执行。常见翻车场景：

- 日报任务重跑一次，群里收到两条一模一样的推送；
- 文件同步插件重试后，同一批文件多出一份带后缀的副本；
- Agent 调工具在远端创建记录，超时后重试，远端其实已成功，于是出现两条。

读操作天然幂等，危险的全是写操作：推送、落库、调外部 API、改外部状态。Agent 场景还有个特殊难点：重试路径不确定，第二次可能走了不同工具，"上次做没做过"没法靠翻日志或问模型自己判断。

## 做法

我的原则：把每个自动化任务写成"让状态收敛到期望值"，而不是"执行一次动作"。拆成五步：

1. **盘点副作用**。列出任务里所有写操作——推送、写文件、远端调用、标记已读都算，纯读部分不用管。
2. **构造确定性任务键**。键从业务上下文派生，比如 `digest:{channel}:{日期}`、`sync:{源目录指纹}:{目标}`；定时任务把时间窗锚进键里，不要用运行时刻的时间戳。
3. **先记账，后执行**。副作用前先把任务键写入去重存储（SQLite 一张表或带 TTL 的 KV 足够），存在即跳过；不存在则落 pending 再执行。写入用 upsert / `ON CONFLICT DO NOTHING` 兜底。注意：去重状态必须放在 Agent 之外的持久存储里，上下文会被压缩、会话会更新，模型"记得做过"不可靠。
4. **边界处去重**。调外部 API 前先查账；下游支持幂等键就透传任务键，不支持就只靠自己这层挡。
5. **校验终态**。完成后校验结果（条数、标记、哈希），而不是相信返回值；校验失败就报警，让重试有依据。

## 踩坑点

- **键里混入随机量或 `now()`**：重试时键变了，去重直接失效，这是最高频的坑。
- **时区漂移**：不同执行环境对"今天"理解不一致，键对不上。
- **部分成功**：先发推送后记账，中间崩掉，重试必双发。顺序必须先记账再副作用，崩溃恢复时 pending 记录走对账。
- **并发重叠**：上一轮没跑完下一轮又触发，要么加执行锁，要么靠 upsert 语义保证并发安全。
- **"只读"不纯**：读完邮件顺手标已读、归档就是副作用，重试会把还没摘要的邮件归档掉。
- **去重存储没设 TTL**：无限增长；TTL 太短又会让迟到重试穿透。

## 可复用建议

- 做一个通用任务包装器：键派生 + 去重存储 + 终态校验三件套，定时任务和触发式任务统一套用，别每个插件自己造。
- 验收方法很朴素：手动连跑两遍，diff 两次副作用，第二遍应该什么都没发生。
- 日志始终带任务键和阶段（pending / done / failed），排查重复问题时这是唯一可靠线索。

## 总结

幂等不是靠运气让重试无害，而是把"执行一次"和"执行 N 次"设计成等价。在 Agent 与自动化场景里重试是默认事件，把幂等做成结构而不是补丁，定时任务才敢长期挂着跑。
