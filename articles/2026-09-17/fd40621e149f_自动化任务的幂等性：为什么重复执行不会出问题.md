## 背景

自动化任务很少只跑一次。定时器重叠触发、队列 redelivery、网络超时后的重试、人工手动补跑——在 Agent / MCP 这类多环节链路里，重复执行是常态而非异常。很多消息投递语义本身就是 at-least-once：只保证不丢，不保证不重。所以问题从来不是"会不会重复执行"，而是"重复执行之后会发生什么"。

## 问题

非幂等操作在重复执行时会放大副作用：

- 计数器重复累加，报表数据翻倍；
- 向下游重复发通知、重复建工单；
- Agent 调用工具超时后重试，但上一次实际已成功，产生两份结果。

根因只有一个：**操作结果依赖于执行了多少次**。跑两次和跑一次结果不同，系统迟早会在某次重试里出错。

## 做法

核心思路是让"执行 N 次"和"执行 1 次"产生相同结果。几个可落地的手段：

1. **业务键 + upsert。** 同步类任务不要盲目 INSERT，用天然唯一键（外部 ID、日期+来源）做 `INSERT ... ON CONFLICT DO UPDATE`，重复跑只会覆盖同一行。
2. **幂等键去重。** 调用不支持天然键的 API 时，为每个业务动作生成稳定 key（任务 ID + 目标对象），写入发送记录表，配合唯一索引兜底。
3. **条件更新代替"先查后做"。** 状态流转用 `UPDATE ... WHERE status='pending'`，靠 affected rows 判断是否抢到，天然防并发重复。
4. **用"设置"代替"累加"。** 能整份覆盖的状态不要增量拼接，重跑等于重新收敛到目标状态。

## 踩坑点

- **先查后做有竞态：** 两个并行 run 同时查到"未发送"，然后都发。检查只能优化路径，唯一约束才是兜底。
- **超时 ≠ 失败：** 请求超时但服务端可能已成功。这就是为什么幂等键最好在 API 层支持——客户端无法自行判断上一次到底成没成功。
- **幂等键不稳定：** 用时间戳或随机数当键等于放弃去重。键必须来自业务语义，且重试时保持不变。
- **LLM 输出非确定：** Agent 每次生成的内容不同，如果生成的文件名或 ID 参与去重键，同一任务会被判成不同操作。
- **定时任务重叠：** 上一次没跑完下一次又触发。锁和幂等要同时有：前者降低撞车概率，后者保证撞车也不出错。

## 可复用建议

- 写任何自动化前先回答一个问题：**"这个任务连续跑两次，会发生什么？"** 答不上来就是没设计完。
- 设计工具 / MCP 接口时，尽量暴露幂等变体：接受调用方传入的 run_id 或业务 key，而不是接口内部自增。
- 执行记录落库（任务 ID、幂等键、结果、时间），既是去重依据，也是审计和补跑的素材。
- 重试务必带退避。幂等保证正确性，退避保护下游。

## 总结

幂等性不是锦上添花，而是自动化可靠性的底线。投递会重复、重试会越界、并发会撞车，这些都是工程事实。把每个任务都按"一定会被重复执行"来设计，用业务键、upsert、条件更新把重复执行收敛成无害操作，自动化才敢放进无人值守的场景。
