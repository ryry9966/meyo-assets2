## 背景

作为常年折腾 Agent 和自动化流程的用户，我对本地模型的诉求从来不是"替代云端旗舰"，而是三件很具体的事：隐私数据不出门、高频调用不烧钱、断网也能跑定时任务。当你的自动化脚本每天要调几百次模型做分类、摘要、路由时，一个本地小模型的价值就体现出来了。

## 问题

真正的问题不是"能不能跑起来"，而是：

1. 我的硬件到底能跑多大的模型？
2. 跑起来之后，工具调用的可靠性够不够 Agent 用？
3. 上下文长度和显存怎么取舍？

## 做法

**第一步：盘硬件。** 关键指标是显存/统一内存，不是算力峰值。经验公式：模型权重大小 × 1.2，再预留 KV cache 空间。16GB 显存跑 14B Q4 比较稳；32B Q4 需要 24GB 显存或 32GB 统一内存；纯 CPU 跑 7B 可行，但吞吐只够批处理，不适合交互式 Agent。

**第二步：选运行时。** Ollama 上手最快，自带 OpenAI 兼容接口；llama.cpp 控制粒度细，适合调参；有独立显卡且追求并发就上 vLLM。我的选择是 Ollama 加显式参数配置，省心且够用。

**第三步：选模型。** 别只看聊天榜单，去查该模型的工具调用评测。在 7B~14B 里挑明确支持 function calling 的型号，量化从 Q4_K_M 起步。

**第四步：接入 Agent。** 关键一坑：Ollama 默认上下文只有 2048/4096，必须显式把 `num_ctx` 拉到需要的长度，否则系统提示词加工具定义会直接挤爆上下文，模型表现为"忘记工具格式"。

**第五步：建小评测集。** 拿真实的 10~20 个任务场景（含工具调用、多轮对话、失败重试）做成固定测试集，每次换模型或量化级别都回归跑一遍。这比看任何榜单都有用。

## 踩坑点

- **KV cache 吃显存超预期**：上下文从 4k 拉到 32k，显存占用可能翻倍，OOM 往往发生在长对话中途而不是启动时。
- **小模型的工具调用很挑接口**：同一模型在原生接口和 OpenAI 兼容接口下，工具调用成功率可能不同，接 Agent 前务必实测。
- **量化不是无损**：Q4 以下，JSON 格式输出错误率明显上升。对 Agent 场景，宁可换小一号模型用 Q8，也别硬上大模型 Q3。
- **统一内存带宽是瓶颈**：Mac 上生成速度尚可，但长输出任务的整体耗时容易被低估，给自动化流程的超时阈值留足余量。
- **别迷信"能跑"**：能出 token 和能稳定完成多步工具调用，是两回事。

## 可复用建议

- 评测集版本化管理，换模型即回归，选型有据可依。
- 分层路由：本地模型处理高频低难度任务（分类、格式化、简单摘要），难任务回落云端大模型，成本与可靠性兼顾。
- 用 systemd/launchd 守护模型服务，配合健康检查接口，自动化流程才敢真正依赖它。
- 记录每次部署的参数快照（模型 hash、量化级别、上下文长度），出问题时可快速回滚。

## 总结

本地部署的价值在于把"高频、低风险、格式化"的模型调用收归自有，而不是追求单点智能上限。先明确 Agent 场景对工具调用可靠性的真实要求，再用固定评测集驱动选型——硬件决定下限，工程化程度才决定你能不能把它真正用起来。
