## 背景

在 OpenClaw 的 skill 和插件里，凡是需要模型返回结构化结果的场景——子 agent 汇总、MCP 工具入参、定时抽取任务——最省事的约定就是在提示词里写一句"只输出 JSON"。demo 阶段它工作得很好，真实跑起来就开始变形：围栏、自创标签、前后废话、残缺输出，全都可能出现。

## 问题

实际日志里见过的输出形态，经常混在一起出现：

- ` ```json ` 围栏包裹；
- 无语言标注的 ` ``` ` 围栏；
- 模型自创 `<json>`、`<result>` 之类的标签；
- JSON 前后各带一句"以下是结果"；
- 尾逗号、单引号、全角引号；
- 数组被 max_tokens 截断。

任何一处解析失败，整条自动化链路就断在中间。防御性解析要解决的不是"怎么让模型听话"，而是"当它不听话时，链路怎么活下来"。

## 做法：解析阶梯（parse ladder）

核心思路是把所有清理动作收敛到一个入口函数，按成本从低到高依次尝试，任一步成功即停：

```python
def parse_llm_json(raw: str):
    steps = [strip_bom, strip_fence, extract_tags,
             balanced_slice, lenient_repair]
    for step in steps:
        cand, ok = step(raw)
        if ok:
            return cand, step.__name__
    raise ParseError(raw_head(raw))
```

1. **归一化**：去 BOM、统一换行。全角字符不要在这一步全局替换（原因见踩坑）。
2. **剥围栏**：非贪心匹配 ` ```(?:json)?\n?([\s\S]*?)``` `；遇到嵌套围栏匹配失败就跳过，交给下一步。
3. **标签提取**：识别 `<json>`、`<result>` 等常见自创标签，取第一个匹配块。
4. **平衡扫描**：定位第一个 `{` 或 `[`，用栈扫描到配对结束，期间跳过字符串字面量和转义符。这一步能把前后说明文字干净地切掉。
5. **宽松修复**：尾逗号、单引号这类问题交给 JSON5/宽松 parser，不要自己堆正则。
6. **Schema 校验**：parse 成功不等于数据正确。过一遍 pydantic/zod，失败时把校验错误拼进重试提示词，只重试一次。

## 踩坑点

- **平衡扫描漏了字符串内的括号**。`{"a": "}"}` 会被切早，必须跳过引号内内容并处理 `\"` 转义。
- **流式场景提前 parse**。边流边解析很容易拿到半截 JSON，等终止标记或流结束再走阶梯。
- **多对象连发**。切出第一个平衡块后，检查剩余内容是否只剩空白，否则宁可判失败。
- **过度修复**。修复让非法输入变合法，也可能变成"合法但错误"。Schema 校验是最后一道闸，不能省。
- **全角替换一刀切**。全局替换全角引号会破坏正文内容，只对结构字符做受控替换。

## 可复用建议

- 所有 skill 复用同一个解析模块，返回 `{ok, data, repairs, raw_head}`，让修复路径可观测。
- 统计各阶梯的命中分布：某类修复高频出现，说明提示词该改了——兜底是补丁，不是长期方案。
- 优先用模型侧原生的 structured output / JSON mode，解析阶梯作为跨模型的统一兜底。
- 日志保留原始输出片段（截断即可），只存异常栈没法定位问题。

## 总结

LLM 输出解析的稳定性，不靠一次写对的提示词，靠三层设计：有序的清理阶梯、严格的 schema 校验、可观测的修复记录。把模型的"不守规矩"当作正常输入的一部分来设计，自动化链路才跑得长。
