# OpenClaw 的 AGENTS.md：写给 AI 的工作空间使用手册

## 背景：agent 的行为不止取决于模型

用 OpenClaw 一段时间后会发现，同一个 agent 在不同会话里的表现并不稳定：文件命名风格变来变去、定时任务写歪、把临时文件堆在根目录。模型能力没变，变的是它对"这个工作空间该怎么用"的理解。

OpenClaw 的工作空间里有一组约定俗成的 .md 文件，AGENTS.md 是其中最工程化的一个：它不是给用户看的使用说明，而是写给 agent 自己的操作手册，随工作空间一起加载，成为系统提示的一部分。

## 问题：口头约定无法沉淀

没有 AGENTS.md 时，使用规范只能靠两种方式传递：每次在聊天里重复交代，或者吃几次亏之后口头发火。前者浪费上下文，后者不可复现。换一个消息渠道、重置会话之后，之前教过的东西全部归零。

## 做法：把规范写成机器可读的事实

我的 AGENTS.md 大约 60 行，结构如下：

1. **工作空间地图**：每个目录的用途，一句话一个。`drafts/` 放草稿，`archive/` 按年月归档，临时文件一律进 `tmp/`。
2. **硬性约束**：不主动给联系人发消息、不碰凭据相关文件、删除操作必须先确认。用祈使句，一行一条。
3. **工具偏好**：同类 MCP 工具里优先用哪个，什么场景走脚本而不是手搓。
4. **输出习惯**：日报的固定格式、代码改动的汇报粒度。
5. **已知错误清单**：agent 犯过且重复过的错，写进来，附一句正确做法。

写完不代表结束。每次 agent 出问题，先问自己：这是模型能力问题，还是我没写清楚？多数情况是后者，那就补一条规则。

## 踩坑点

- **写太长**。超过一两百行后，关键规则会被稀释。我砍掉过一半"感觉有用"的内容，效果反而变好。
- **形容词多于动作**。"小心处理文件"没用，"删除前必须列出文件清单并等待确认"才有用。
- **和聊天指令冲突**。SOUL.md 管人格，聊天上下文管当下，AGENTS.md 管长期规范。三者一旦打架，行为会变得不可预测，改 AGENTS.md 时顺手检查另两处。
- **放了敏感信息**。AGENTS.md 会被读进上下文，token、密钥、内网地址都别写。
- **忘了它的加载时机**。改完文件不重置会话，可能还在跑旧规则，容易误判成"改了没用"。

## 可复用建议

- 把 AGENTS.md 当代码管理：进 git，改动写清楚为什么。三个月后你会感谢那条带注释的规则。
- 每条规则尽量可验证：能写出"违反了会怎样"的规则才值得写。
- 保持最小核心 + 引用其他文档，让 agent 按需去读细节，而不是把所有细节塞进常驻上下文。
- 验证方式很朴素：重置会话，丢一个日常任务过去，看它是否按新规范执行。

## 总结

AGENTS.md 的价值不在"配置技巧"，而在把人对 agent 的隐性期望显性化。它成本极低——一个 markdown 文件——但把调试 agent 的过程从"每次重新教"变成"维护一份文档"。对长期跑自动化任务的 OpenClaw 实例来说，这份手册值得认真写。
