## 背景

AGENTS.md 是一个正在被各家 agent 工具采纳的简单约定：在工作区（仓库）根目录放一个纯文本 Markdown 文件，agent 进入工作区、启动会话时会自动读取。它之于 agent，相当于 README 之于人——只是 README 写给"第一次接触项目的人类"，AGENTS.md 写给"第一次接触项目的模型"。OpenClaw 的 agent 在挂载工作区时同样遵循这一约定，但约定本身不保证效果，写得好坏差异非常大。

## 问题

没有 AGENTS.md 的日常大概是这样的：

- 让 agent 跑测试，它自己猜命令，猜出一个不存在的脚本；
- pnpm 项目被它用 npm 装出一堆多余的 lock 文件；
- 改完代码不跑 lint，CI 红了再来回折腾；
- 每个新会话都要重新解释一遍项目结构，解释完上下文已经烧掉不少 token。

反过来，写了但写砸的也不少见：把 README 复制过来当 AGENTS.md，通篇是项目愿景和架构介绍，唯独没有"该执行什么命令"；或者写了几百行，关键规则淹没在里面；或者三个月没更新，命令早就变了。对 agent 来说，一份错误的手册比没有手册更糟。

## 做法

我们的实践可以概括为"最小可用 + 持续追加"：

1. **先写最小版本（20 行以内）**。只回答四个问题：这个工作区是什么；构建命令是什么；测试命令是什么；有哪些硬性约束（包管理器、格式化工具、禁止动作）。
2. **用祈使句，不用描述句**。写 `运行测试：pnpm test --filter core`，不要写"本项目使用 pnpm 管理依赖"。agent 需要的是可执行指令，不是背景介绍。
3. **明确"不要做"清单**。比如"不要手动修改 generated/ 目录""不要升级依赖版本"。负向约束往往比正向指引更省上下文。
4. **Monorepo 分层**。根目录放全局规则，每个子包放自己的 AGENTS.md，只写该包特有的命令和约定。
5. **把踩坑变成条目**。agent 在对话里犯过的错，如果你口头纠正过两次，就沉淀一行进 AGENTS.md。这个文件应该是长期演化出来的，不是一次性写完的。

## 踩坑点

- **写成了 README**：介绍性内容对 agent 几乎无用，还会稀释关键指令。介绍留给 README，AGENTS.md 只留操作指令。
- **过长**：超过一屏（约 100 行）就要警惕。塞得越满，单条规则的执行率越低。
- **与事实漂移**：构建脚本改名后忘了同步。建议规矩：凡是改构建/测试流程的 PR，必须顺手检查 AGENTS.md，把它当代码 review。
- **与 README/CI 矛盾**：agent 遇到冲突指令时行为不可预测。宁可只留一处权威来源，其他地方用链接引用。
- **写入敏感信息**：AGENTS.md 会进入模型上下文，token、内网地址不要写。
- **只写不测**：改完在干净会话里问一句"如何跑这个项目的测试"，看它是否直接给出正确答案，这是最简单的验收方式。

## 可复用建议

一个可以直接抄的骨架：

```markdown
# AGENTS.md

## 项目概览
（1-2 句即可）

## 常用命令
- 构建：
- 测试：
- Lint：

## 硬性约束
- 包管理器：pnpm，勿用 npm
- 不要修改：generated/ 目录

## 提交规范
- ……
```

经验法则：**同一件事在对话里解释到第二遍，就写进 AGENTS.md**。它不是文档，是给 agent 的接口约定，值得像代码一样被版本化和维护。

## 总结

AGENTS.md 的价值不在格式，而在"把团队默会知识显式化"这个过程。写得越克制、越像操作手册，agent 的表现越稳定。从 20 行开始，让每次踩坑都变成一行规则，几周后你会得到一份真正属于这个工作区的、AI 能读懂的使用手册。
