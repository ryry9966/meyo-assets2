## 背景

接了不少 MCP 工具之后，agent 从"问答助手"变成了"能动手的执行器"：能查数据库、调 API、发消息、改文件。能力上去之后，新问题也来了——哪些动作它可以直接做，哪些必须停下来问人？边界划得太松，一次误操作可能就是删表、发错邮件、扣错款；划得太紧，人就退化成确认按钮，自动化名存实亡。

## 问题本质：副作用，而不是"能力"

实践中我们发现，判断标准不该是"模型聪不聪明"，而是工具的副作用形态。大致分四类：

1. **只读**：查数据、搜文档、列文件。风险是信息泄露，不是破坏。
2. **可逆写**：写草稿、建分支、写临时目录。错了能撤。
3. **不可逆外部副作用**：发邮件、调支付、删资源、向第三方推数据。错了撤不回。
4. **高敏操作**：改权限、动生产配置、读个人信息。哪怕可逆也敏感。

第 1、2 类基本可以自动执行；第 3 类要么确认后执行，要么先 dry-run；第 4 类无论多确定都该停下来问。

## 落地做法

关键点：权限做在 MCP 工具层，而不是 prompt 里。

- 给每个工具打标签：`readonly / reversible / external / sensitive`，配置在工具注册处。
- 写一个统一的工具网关（wrapper），执行前按标签和上下文路由：直接放行、执行后通知、执行前要人确认、直接拒绝。
- 确认请求必须带决策材料：完整参数、参数 diff（比如"把配额从 10 改成 100"）、影响范围、回滚方式。让人 10 秒内能做判断，而不是丢一句"我要执行 xx，可以吗"。
- 显式定义确认超时策略：默认不执行、通知升级、还是降级为 dry-run。
- 所有放行和拦截进审计日志，事后能回放整条决策链。

## 踩坑点

- **靠 system prompt 约束"高危先询问"，实测会漂移。** 模型状态好时守规矩，上下文一长就自作主张。权限必须是代码层硬约束，prompt 只是补充。
- **确认疲劳。** 一天弹 30 次确认，人会上来就点同意，确认机制等于失效。宁可收紧阈值，把确认次数压到每天个位数。
- **"只读"不等于无害。** 有的 GET 会触发 webhook、消耗配额、写审计表。接新工具时真的要读文档，别按方法名猜。
- **确认后的重试要幂等。** 用户点了确认，执行超时，重试时如果网关状态丢了，要么重复执行，要么重复打扰用户。确认请求要有唯一 ID 和有效期。
- **别忘了"执行后通知"这一档。** 很多中等风险操作，事前确认是浪费，事后不通知又失控，执行完发一条消息是不错的折中。

## 可复用建议

- 新接一个 MCP 工具，先花五分钟填一张四行权限表：副作用类型、单次影响上限（金额/条数/范围）、自动执行条件、确认方式。填不出来就默认按 `external` 处理。
- 危险工具默认 dry-run 上线，跑一周看参数分布，再逐步放开自动执行。
- 权限矩阵放配置文件里，随代码走版本管理，别散落在各处逻辑里。

## 总结

权限边界不是"问还是不问"的单选题，而是一套按副作用分级、由代码强制执行、有人类兜底的路由系统。原则很简单：**可逆的放手，不可逆的设闸，高敏的必问。** 把判断标准从模型手里收回到工程手里，自动化才敢真正往前跑。
