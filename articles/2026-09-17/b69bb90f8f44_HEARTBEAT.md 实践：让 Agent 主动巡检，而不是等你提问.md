## 背景

OpenClaw 里的 Agent 默认是被动模式：你不发消息，它就不动。但很多人实际拿它当值班助手用——定时看邮件、盯 CI、检查仓库更新、提醒日程。这类需求靠"人记得去问"是不靠谱的。

OpenClaw 为此提供了心跳机制：每隔一个可配置的周期，运行时会向 Agent 注入一条心跳 prompt，Agent 据此读取工作区根目录的 `HEARTBEAT.md` 决定做什么。关键设计是：**文件为空（只有 `# HEARTBEAT`）时，Agent 回一个静默心跳（HEARTBEAT_ACK），不产生实际输出**；文件里有任务，才真正执行。

## 问题

被动 Agent 有三个工程上的痛点：

1. **遗忘成本**：任务依赖用户主动发起，忘问 = 漏办；
2. **逻辑割裂**：用外部 cron 调 API 能定时，但任务逻辑散落在脚本里，和 Agent 的工具、会话记忆脱节；
3. **成本失控**：如果每个周期都跑一轮完整回复，token 消耗很可观。

HEARTBEAT.md 的价值就是把"定时触发 + 任务定义 + 静默降级"收进一个文件。

## 做法

1. **先验证链路**。在 workspace 根目录建 `HEARTBEAT.md`，内容只写 `# HEARTBEAT`，观察日志确认心跳在跑且是静默 ACK。
2. **配置间隔**。`openclaw.json`：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "interval": "30m" }
    }
  }
}
```

3. **用 checklist 语法写任务**，每条都写成"触发条件 + 动作 + 汇报方式"：

```markdown
# HEARTBEAT
- [ ] 每天 09:00 汇总未读邮件，仅当有新邮件时推送摘要
- [ ] 检查 ~/proj 的 git remote，有新 commit 则给出一句话摘要
- [ ] 磁盘占用超过 85% 时告警，否则静默
```

4. **任务多了做两级结构**：HEARTBEAT.md 只放索引，具体 SOP 写到独立文件让 Agent 按需读取，避免单文件膨胀。

## 踩坑点

- **任务写太模糊**。"关注一下服务器状态"会让模型自由发挥、产生噪音。必须写成可判定的条件句：什么算异常、异常了做什么。
- **间隔太短**。1 分钟一轮会让上下文频繁膨胀、成本上升，建议 30 分钟起步，按需求收紧。
- **单轮塞太多任务**。一次心跳全跑会拉长耗时，控制在 2~3 条，其余排下一轮。
- **副作用不设闸**。模型可能"顺手"执行发消息、删文件等操作，敏感动作前强制"先汇报、确认后再执行"。
- **路径放错**。心跳读的是 workspace 根目录的文件，别放到子目录里然后怀疑机制坏了。

## 可复用建议

- 把 HEARTBEAT.md 当 **SOP 而不是 TODO**：写"何时、查什么、什么条件才响"，不写流水账。
- 遵循"**默认静默、异常才响**"：没有变化就 ACK，有变化才打扰人，这是控制成本和噪音的核心。
- 多 Agent 场景按角色分文件，每个 Agent 维护自己的心跳表。
- 配合 MCP 工具（邮件、日历、git、监控）扩展心跳能查询的数据源，心跳只负责"何时查、怎么报"。

## 总结

HEARTBEAT.md 本质上是给 Agent 一个极轻量的常驻调度入口：**文件即配置，静默即健康**。它不替代复杂的 workflow 编排，但"定时 + 可判定 + 默认静默"这三条，足以让大部分个人自动化从"你问它才动"变成"它该动就动"。建议从一条只读、无副作用的巡检任务开始跑通，再逐步加码。
