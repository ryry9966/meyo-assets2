## 背景

最近半年，社区里用 Agent 干活的身影明显多了：有人让它整理 issue 摘要，有人挂了 MCP 让它直接读本地仓库，还有人搭了自动化流水线，让 Agent 定时往公开频道发周报。效率确实上去了，但一个容易被忽略的问题也随之浮现：**Agent 并不天然区分“能发到社区的内容”和“只能留在内网的内容”。**

## 问题出在哪

泄露几乎从来不是模型“故意”的，而是边界没划。常见三条路径：

1. **工具越权读取。** 社区答疑用的 Agent 挂着全量文件系统访问，它为了“回答得更准确”，顺手读了你本地的部署配置、内网域名设置，然后原样贴进回复。
2. **上下文污染。** 你让它“帮我把这份内部方案改写得更通顺”，改写完它记住了。几天后另一个会话里有人问类似问题，它把方案细节用自己的话复述出来——你看不出是复述，但它知道。
3. **自动化管道直发。** 定时任务抓取日志和告警，Agent 生成摘要后直接发频道。摘要里混进 stack trace、内部主机名、半截 token，没人审核就出去了。

## 我们的做法

把这件事当边界问题而不是提示词问题，分四层处理：

**第一层：实例隔离。** 面向社区的 Agent 和内部开发用的 Agent 是两个实例、两套配置。社区实例的工作目录是干净沙箱，内部仓库对它不可见。

**第二层：工具白名单。** 社区实例只保留只读检索、网页抓取这几类工具；shell、大范围文件读写、内部系统的 MCP server 一律不挂。临时要挂，用完即拆，写进团队约定。

**第三层：出站过滤。** 加一个出站钩子，所有准备发到公开频道的内容先过一遍规则：密钥格式、内网域名段、IP 段、客户名。命中即拦截转人工。规则不复杂，但能兜住大部分“手滑”。

**第四层：人工闸门。** Agent 生成的社区内容，要么标注来源并走一遍人工审核，要么先发内部频道二次确认。全自动直发公开频道的管道，目前一条都没留。

## 踩过的坑

- **正则过滤给人虚假的安全感。** Base64 编码过的 token、拼接出来的内部 URL，规则抓不到。过滤层定位是“减速带”，不是“墙”。
- **子代理继承上下文。** 多 Agent 编排时，主代理的会话历史会带进子代理，隔离必须显式做，别默认它干净。
- **“就挂五分钟”的 MCP。** 为排查一个问题临时挂上的宽权限工具，修完忘了拆，两周后才在授权审计里发现。
- **截图和会话文件本身也是泄露面。** 分享排障截图、同步 session 记录前，先确认里面没有其他会话的残留。

## 可复用的建议

一个朴素但有效的判断标准：**你不敢直接截图发社区的东西，就不要让面向社区的 Agent 碰它。** 落成三个习惯：

1. 发布前问一句：这段内容的“源头”是什么？Agent 过程中读了哪些文件、调了哪些工具？
2. 给社区 Agent 的系统提示写明红线清单（内部域名、凭据格式、未公开方案），并定期做一次“诱导泄露”演练，看它守不守得住。
3. 每季度过一遍所有在线 Agent 的工具授权清单，砍掉用不上的。

## 总结

Agent 的默认行为是“尽力帮忙”，不是“替你守密”。防泄露的核心不是一句“不要泄露内部信息”的提示词，而是用实例隔离、工具最小授权、出站过滤、人工闸门四层结构，把信任边界显式画出来。提示词可以是最后一道提醒，但不能是第一道防线。欢迎在评论区交流你们的边界方案和演练经验。
