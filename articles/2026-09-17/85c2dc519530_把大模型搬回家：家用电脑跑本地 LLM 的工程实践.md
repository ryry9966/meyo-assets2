## 背景

做 Agent 自动化的人迟早会撞上两个现实：API 费用随调用次数线性上涨，以及敏感数据不方便出网。在 OpenClaw 这类框架里，一个稍复杂的任务跑下来，agent 循环加上 MCP 工具调用，轻松消耗几十万 token。把模型搬到本地，是很自然的下一步——但难点从来不在"能不能跑起来"，而在工程细节。

## 问题

家用硬件跑本地模型，核心是三个约束：

1. **硬件预算**：显存/内存直接决定模型上限；
2. **Agent 兼容性**：本地模型必须稳定输出 tool calling 的结构化参数，否则 MCP 工具全部失效；
3. **长上下文**：agent 循环 token 累积极快，上下文窗口和 KV cache 的内存开销经常被低估。

## 做法

**Step 1：盘点硬件。** 有 8GB 以上显存（RTX 3060 12G / 4060Ti 16G 这类），可上 7B–14B 量化模型；纯 CPU 加 32G 内存的机器，7B Q4 也能跑，速度约 10–20 token/s，够用但不快。

**Step 2：选运行时。** 推荐 Ollama 起步，安装简单且自带 OpenAI 兼容 API（`localhost:11434`），后续追求性能再换 llama.cpp 自行编译。

**Step 3：选模型。** Agent 场景首选 Qwen 系列 8B/14B 的 Q4_K_M 量化，tool calling 支持成熟。别盲目追参数量，14B 挤爆显存不如 8B 稳定输出。

**Step 4：接入 OpenClaw。** 把 agent 配置里的 base_url 指向本地 API、模型名对上即可。关键是先做最小验证：让模型调用一个最简单的 MCP 工具（比如查时间），确认 JSON 参数格式没跑偏，再上真实任务。

**Step 5：调上下文。** Ollama 默认 `num_ctx` 很小，agent 场景手动调到 16K 起步；同时设置 `keep_alive`，避免每次调用重新加载模型。

## 踩坑点

- `num_ctx` 没调，agent 跑到一半突然"失忆"、工具参数开始编造——是上下文被静默截断了；
- 同一模型不同量化版本，tool calling 表现可能不同，换量化后必须重测一遍工具调用；
- 温度高于 0.7 时，小模型输出的 JSON 容易格式漂移导致解析失败，agent 场景建议压到 0.2–0.4；
- 默认并发请求会排队，多个 agent 同时跑会互相等待，需要调 `OLLAMA_NUM_PARALLEL`。

## 可复用建议

- 显存估算经验公式：**模型文件体积 × 1.3 ≈ 实际占用**（含 KV cache）；
- 混合路由更划算：本地小模型做意图分类、格式化、简单工具调用，复杂推理留给云端，成本能降一个量级；
- 建一份记录：模型名、量化版本、`num_ctx`、温度、实测 token/s，团队复现零成本。

## 总结

本地 LLM 不是要替代云 API，而是给自动化系统加一层可控、便宜、离线可用的基座。正确路径是：先用最小闭环验证 tool calling 的稳定性，再逐步把高频低难度的任务迁到本地。家用硬件跑 8B 级模型支撑一条 agent 工作流，如今已是成熟方案——缺的不是能力，是把这些工程细节沉淀成文档。
