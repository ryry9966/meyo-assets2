## 背景

OpenClaw 的 memory_recall 依赖工作区里的记忆文件（MEMORY.md 和 memory/ 下的 markdown），Agent 每次需要历史上下文时从中检索。检索质量直接决定"助手到底记不记得事"。我最初只上全文搜索，后来补了向量层，中间踩了不少坑，记录一下决策过程。

## 问题

两种检索各有明确的失效场景：

- **全文搜索（FTS/BM25）** 对精确标识符无敌：函数名、错误码、配置键、节点 ID，一查一个准。但同义改写直接失效——搜"上次部署卡住"，召不回写着"docker build 阶段 hang 住"的那条记忆。
- **语义搜索（embedding + 余弦）** 擅长改写和跨语言，但遇到具体 token 会漂移：搜"kafka 消费超时配置"，召回一堆"消息队列性能优化"的泛泛内容，唯独漏掉写着 `max.poll.interval.ms` 的那条。

单选任何一个，都能构造出可复现的召回失败。

## 做法

结论是混合检索，成本可控：

1. 记忆保持纯 markdown，一文件一主题，人可以直接编辑。这是唯一事实源，不要引入第二套格式。
2. 全文索引用 SQLite FTS5。中文必须换 jieba 或 trigram 分词器，默认 unicode61 会把整句中文当一个 token，检索基本靠运气。
3. 向量层按需加：按标题切块（300–500 token 一块），本地 embedding 模型或 API 均可，向量存 sqlite-vec 就够，不必上独立向量库。
4. memory_recall 流程：query 同时走 FTS top-20 和向量 top-20 → RRF（倒数排名融合）合并 → 取前 8 条，附文件路径和时间戳注入上下文。
5. 维护一个 20 条真实查询的小评测集，每周跑一次 recall@5，用数据决定下一步。

## 踩坑点

- 中文 FTS 分词是第一坑，症状是"中文检索时灵时不灵"，换分词器后立刻解决。
- 手动编辑记忆文件后向量索引不会自动更新。用 mtime + 内容 hash 做脏检查，启动时增量重建。
- 记忆总量在几百条以内时，语义检索纯属浪费——FTS + 时间衰减权重能覆盖九成场景。我是记忆过千条、评测集集中出现改写类 miss 后才加的向量。
- 语义召回的"相似但没用"：设相似度阈值，结果按源文件去重，否则前 8 条可能是同一段记忆的 5 个相邻块。
- 注入上下文时务必带来源路径和日期，否则模型会把三个月前的旧结论当作当前事实。

## 可复用建议

- 顺序是：先全文 → 后向量 → 再考虑 rerank，每一步都要有评测数据支撑，不要一步堆满架构。
- 记忆写入时就原子化：一条记忆一个事实 + 日期标签，检索粒度自然就对了。
- RRF 是默认答案，不需要调权重；加权融合的权重基本调不出稳定收益。
- query embedding 可以做短 TTL 缓存，高频重复查询能省一半延迟。

## 总结

语义 vs 全文不是二选一，而是失效模式互补：精确标识符靠全文，同义改写靠语义。我的路径是 FTS5 起步 → 评测暴露改写类 miss → 加向量 + RRF，全程没有引入重型依赖，单进程 SQLite 搞定。检索工程里，可控和可评测，比模型的先进性重要得多。
