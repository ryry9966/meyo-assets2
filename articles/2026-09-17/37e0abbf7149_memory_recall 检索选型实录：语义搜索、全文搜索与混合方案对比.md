## 背景

在 OpenClaw 里跑一个长期 Agent，memory 会越积越多：会话纪要、用户偏好、踩过的坑、环境配置。`memory_recall` 的职责就是在回复前从这堆记忆里捞出最相关的几条，塞进有限的上下文窗口。捞得准不准，直接决定 Agent 是"记得你说过的话"，还是"答非所问地引用旧笔记"。

## 问题

默认走语义检索（embedding 向量召回），我用了一段时间发现两类明显翻车：

1. 查询里带精确标识符时（文件名、错误码、命令参数、端口号），语义检索经常返回"主题相近但内容无关"的记忆；
2. 反过来，用户换个说法问同一件事（"上次那个部署问题"），纯全文搜索又完全找不到。

于是想搞清楚：语义 vs 全文，到底该选哪个？

## 做法

四步验证流程：

1. **先记录，再对比。** 给 `memory_recall` 包一层日志：查询原文、召回的 chunk、以及这条 chunk 最终有没有出现在模型回复里（用"是否被实际使用"近似当作"有用"标签）。跑一周攒了 40 多条真实查询。
2. **搭对照。** 同一批记忆文件建两套索引：SQLite FTS5（中文需自己处理分词）+ bge-small-zh 本地 embedding 存 sqlite-vec，查询时各取 top-8。
3. **算指标。** 用 Recall@5 和"有用率"（召回中被实际使用的比例）做粗评估，不追求严格，能分出量级差即可。
4. **上混合。** 两路结果用 RRF（倒数排名融合）合并，取 top-5 进上下文。

结果：纯语义在"换说法"类查询上明显赢；纯全文在标识符类查询上几乎全胜；混合方案两类都不垫底，有用率最高。

## 踩坑点

- **FTS5 默认分词器对中文基本没用**，unicode61 会把整句当一个 token。要么先用 jieba 分好词再入库，要么用 trigram，否则全文索引形同虚设。
- **embedding 模型与语料不匹配。** 通用中文模型对代码、命令、标识符的向量区分度很差，这是语义检索在技术场景翻车的主因。
- **高相似度 ≠ 有用。** 语义检索最迷惑的地方是返回相似度 0.85+ 却没被用到的 chunk，不看使用日志根本发现不了。
- **k 别贪大。** top-8 开始明显挤占上下文预算，实测 top-5 混合召回收益已经饱和。
- **记忆更新后要重建向量索引**，否则持续召回旧版本内容，而且这类问题很难归因。

## 可复用建议

- 混合检索（RRF）当默认方案，全文那一路留着兜底精确匹配，别二选一。
- 使用日志是所有优化的前提。没有"被用过没有"这个信号，调参就是玄学。
- embedding 用本地小模型（bge-small 级别）就够，隐私和延迟都友好。
- chunk 控制在 300–500 字，带 50 字左右 overlap。

## 总结

这不是"谁更好"的问题，而是两类失败模式互补：语义管改写，全文管精确。混合召回 + 使用日志 + 一个 40 条的手工评测集，成本一个晚上，换来的是长期 Agent 记忆召回确定性的明显提升。建议每个长期跑的 Agent 都做一次。
