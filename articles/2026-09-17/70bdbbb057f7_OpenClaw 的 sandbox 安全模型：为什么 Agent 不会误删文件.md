## 背景

让 Agent 直接操作本机文件是自动化的刚需，也是最大的风险来源。LLM 并不可靠：一次幻觉、一条藏在网页内容里的提示注入，都可能让模型生成 `rm -rf` 这类不可逆命令。OpenClaw 的设计前提不是"信任模型"，而是假设模型一定会犯错，然后在架构上把错误的爆炸半径限制住。

## 问题：能力与风险的错配

核心矛盾很直接：Agent 必须有写文件、跑命令的能力才有用，而这两样能力天然可以破坏系统。所以"要不要给权限"是个伪问题，真正要回答的是：**权限的边界画在哪里，越界时谁来兜底。**

## OpenClaw 的做法：四层防线

**1. 工作区路径硬边界。** 所有文件工具（读/写/移动/删除）在执行前先对目标路径做 realpath 归一化，落点必须在 workspace 根目录之内。`../../` 这类相对路径穿越、软链接逃逸，都在这一层被拦下，返回的是正常的工具错误，模型会收到反馈并自行修正，而不是抛异常。

**2. 执行沙箱。** exec 类工具默认进 Docker 容器运行，只挂载 workspace，网络按需关闭。容器内的 root 与宿主机无关——即使模型真的执行了破坏性命令，它能碰到的也只有这份工作目录，宿主系统对它不可见。

**3. 高危命令审批。** 在默认拒绝之上配白名单，叠加高危模式匹配（`rm -rf`、`dd`、`mkfs` 等），命中即挂起等待人工确认。所有执行过的命令落审计日志，事后能还原"谁在什么时候跑了什么"。

**4. 快照兜底。** workspace 定期快照，删除类操作执行前自动留档。即便前三层都被绕过，误删也能回滚。

## 踩坑点

- **符号链接逃逸**：workspace 里建了个软链指向 `~/Documents`，早期如果校验发生在解析真实路径之前，越界写入就拦不住。教训：路径校验必须统一放在 realpath 解析之后。
- **挂载图省事**：把整个 home 目录 bind mount 进沙箱，隔离等于没有。挂载粒度只到 workspace。
- **黑名单不完备**：`find -delete`、`git clean -fdx` 都能批量删文件，靠枚举永远列不全。正确姿势是默认拒绝 + 显式白名单，黑名单只做最后一道模式匹配。
- **审批疲劳**：如果所有命令都弹审批，用户一周后就会变成无脑点 yes。审批项要少而准，只留真正高危的。
- **密钥挂进沙箱**：模型读不到 ≠ 沙箱里的进程读不到。exec 起的子进程能看到环境变量，密钥不要注入沙箱环境。

## 可复用建议

1. 默认拒绝，能力按需逐项开启；
2. 所有路径校验收敛到同一个 realpath 入口，不要各工具各写一套；
3. 沙箱挂载最小化，只挂 workspace，不挂 dotfiles；
4. 删除类操作强制前置快照；
5. 审计日志只追加、落盘保存；
6. 定期做对抗演练：故意让 Agent 执行 `rm -rf /`，观察是哪一层拦住的——四层全穿透才叫事故。

## 总结

"Agent 不会误删文件"，不是因为模型足够聪明，而是因为最坏情况真的发生时，它删掉的只是容器里一份带快照的工作区。这类安全模型的价值在兜底层，不在模型层。给 Agent 放权之前，先问自己：最后一道防线是什么，它被穿透过吗？
