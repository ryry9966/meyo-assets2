## 背景

大模型本身是无状态的。你在 OpenClaw 里搭好的 Agent，今天调好的习惯、说过的偏好，明天开新会话就全部归零。上下文窗口再大，也不可能把三个月的对话全塞进去——成本、噪声、注意力稀释都会反噬。所以"记忆"必须当成一个独立的系统设计问题，而不是"把 context 拉长"就能解决的。

配合 MCP 之后，记忆完全可以做成一个独立的 server，Agent 通过工具调用读写。下面是我迭代了几个版本后沉淀下来的一套做法。

## 问题：三类典型失败

1. **全量塞 context**：把历史对话摘要全部注入，token 消耗暴涨，关键偏好反而被噪声淹没。
2. **裸向量检索**：所有记忆丢进向量库靠相似度召回，结果"用户喜欢喝美式"召回了大量含"咖啡"字样的无关片段，污染上下文。
3. **一次发言永久生效**：用户说了一句"今天不吃辣"，从此 Agent 认定用户忌辣，三个月后还在推荐粤菜。

根因一致：没有区分记忆的类型、作用域和时效。

## 做法：分层存储 + 显式写入

**第一步，分三层存。**

- **工作记忆**：仅当前会话，不落盘；
- **偏好档案**：结构化长期偏好，形如 `{type: "preference", key: "咖啡口味", value: "美式少冰", scope: "长期", confidence: 0.9, updated_at}`，每次会话启动整份注入，控制在 500 token 以内；
- **情节记忆**：具体事件，落 SQLite，只在需要时通过 `memory_search` 工具按需检索，不主动注入。

**第二步，写入走显式工具调用，而不是自动抓取。** 给 Agent 暴露 `memory_write` / `memory_search` 两个 MCP 工具，并在 system prompt 里约定：只有用户表达稳定偏好时才写，且必须带 scope 字段区分"长期偏好"与"临时状态"。

**第三步，更新与冲突处理。** 同一 key 重复写入时做 merge：新值覆盖旧值，同时保留 `previous_value` 便于回滚；低置信度、长期未命中的记忆定期清理，防止膨胀。

**第四步，让用户可纠正。** Agent 引用某条记忆时附上来源；用户说"不对"，立即触发更新。这个反馈回路比任何算法调优都有效。

## 踩坑点

- **向量库不是第一选择。** 我一开始就上了向量库，检索噪声比信息还多。先写死一份 JSON 档案，撑了两个月才真正需要检索。
- **提取阈值要高。** 让 LLM 自动提取记忆，它倾向于什么都记。一段对话提取超过 2 条，基本就是过度提取。
- **记忆内容是不可信输入。** 网页里的指令性文字一旦被存入记忆，后续会话就成了持久化的 prompt injection。存入前过滤，注入时当数据处理。
- **没有评测就没有记忆质量。** 攒 30 条历史会话做回放，检查 Agent 能否答对偏好类问题，每次改策略都跑一遍。

## 可复用建议

- 从扁平 JSON 档案起步，别过早引入向量库；
- schema 里必须有 scope 和 updated_at，否则迟早出脏数据；
- 常驻注入的档案控制体积，其余记忆一律按需检索；
- 记忆变更保留审计日志，出错能定位到具体一次写入；
- 用回放集做回归测试，记忆策略改动必须可验证。

## 总结

记忆系统的本质不是"存得多"，而是"该在场的信息恰好在场"。分层存储、显式写入、用户可纠正——这三个原则比任何具体选型都重要。先用最朴素的方案跑起来，让真实使用暴露问题，再决定要不要上检索。这条路径在 Agent 工程里几乎不会错。
