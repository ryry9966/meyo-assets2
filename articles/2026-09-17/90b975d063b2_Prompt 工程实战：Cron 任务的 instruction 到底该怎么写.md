## 背景

OpenClaw 的 cron 任务本质上是**无人值守的会话**：到点触发，agent 拿着你写的那段 instruction 独立执行——没有上下文、没有追问机会、没有人盯着。很多人把它当普通聊天来写，比如“每天早上帮我看看昨晚的报错”。交互式场景下模型会追问、会补全，cron 场景下这些兜底全没了。

## 问题

社区里常见的翻车大致三类：

1. **指令太模糊**。模型自由发挥，今天跑 A 明天跑 B，行为漂移。
2. **输出没有落点**。agent 干完了活，结果留在一次性的会话里，没人看见，等于没干。
3. **没有失败约定**。数据源挂了、工具超时，模型开始硬编，产出看起来正常，实则错误。

根因是同一个：cron instruction 的写作标准应该是“交接文档”，不是“聊天消息”。

## 做法

我现在的模板固定五段，实测稳定很多：

1. **输入**：写死数据来源和工具。“调用 search_logs 工具”，不要写“你自己找一下相关数据”。
2. **动作与边界**：一次只做一件事，划清不做什么。“只统计，不给修复建议。”
3. **输出落点与格式**：写到哪（文件 / MCP 通道 / 通知）、格式什么样，给样例。没有落点的任务不要挂 cron。
4. **失败行为**：明确“拿不到数据时，输出一句话说明原因并结束，禁止推测”。这一句能挡掉大部分幻觉。
5. **幂等约束**：如果会发通知、写文件，加一句“已存在当天记录则跳过”，防止重跑时重复轰炸。

对比一下：

- 反例：`每天早上总结一下昨天的告警。`
- 正例：

```
每天 09:00（Asia/Shanghai）执行：
1. 输入：调用 search_logs，拉取昨天 00:00–24:00 的 ERROR 日志。
2. 动作：按服务名分组统计数量，只统计、不输出修复建议。
3. 输出：按固定模板写入 daily-report.md，字段：服务名/次数/典型报错一条。
4. 失败：拉取失败时在文件末尾追加失败说明并结束，不要编造数据。
5. 幂等：若文件已含昨天日期，直接结束。
```

## 踩坑点

- **时区**：cron 调度和 instruction 里都要写明时区，我吃过 8 小时偏移的亏。
- **塞历史**：把上周结论粘进 instruction 当上下文，两周后就成了过期信息污染输出。历史结论放外部文件，让任务运行时自己读。
- **一个任务干三件事**：抓数据 + 分析 + 通知，链路越长越脆。拆成多个 cron 串行，单点失败好定位。
- **先手动跑再上调度**：挂 cron 前手动触发两三次，确认输出落点真实可见，再交给调度器。

## 可复用建议

- 把每条 cron instruction 当代码 review：改动留备注，记原因和日期。
- 每月回看一次输出文件，行为漂移几乎都是从 instruction 被“宽松解读”开始的。
- 能用工具拿到的信息不要写死在 instruction 里——instruction 只描述流程，不承载数据。

## 总结

Cron instruction 的核心心智模型：假设执行者是个能力很强、但完全不了解背景、也不会向你提问的新同事。把输入、边界、输出、失败行为、幂等这五件事写清楚，无人值守任务就能从“碰运气”变成“可预期”。
