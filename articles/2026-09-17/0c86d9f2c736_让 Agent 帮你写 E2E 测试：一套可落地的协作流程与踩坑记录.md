## 背景

E2E 测试一直是个投入产出比尴尬的环节：写起来慢、维护成本高、经常只有团队里一两个人在坚持写。Agent 和 MCP 工具链成熟之后，“让 AI 写测试”听起来很美，但实践中直接丢一个 URL 说“帮我测一下”，产出的用例基本不可用。这篇记录我们团队把 Agent 接入 E2E 测试流程的实际做法，场景是 Playwright + MCP 浏览器工具，但思路对其他框架同样适用。

## 问题

手写 E2E 的时间大头其实不在测试逻辑，而在机械劳动：定位元素、处理等待、写样板代码。而让 Agent 直接生成用例，又会遇到几个典型毛病：

- 断言过弱：点了按钮没报错就算 pass，实际什么都没验证；
- 选择器脆：生成一堆依赖 DOM 结构或自动生成的 class 的选择器；
- 硬编码 sleep：用 `waitForTimeout(3000)` 掩盖时序问题；
- 测试跑绿了但没人看得懂、没人敢改，最后集体被 skip。

## 做法

我们把它拆成一个人机分工明确的五步流程：

**1. 人先写“测试意图清单”。** 每个用例一句话描述：前置条件、操作步骤、预期断言。这一步是整个流程的锚点——操作可以让 Agent 写，断言必须由人定。

**2. 精准投喂上下文。** 给 Agent 的输入包括：意图清单、对应的 page object 文件、项目的 Playwright 配置、一两个现有用例作为风格示例。注意：不要喂整个仓库，上下文过载反而让生成质量下降。

**3. Agent 生成并自校验。** 通过 MCP 挂载的浏览器工具实际打开页面，验证选择器能否命中（role 和 testid 优先），跑通后输出 diff，而不是直接提交。

**4. 失败回喂循环。** 本地和 CI 跑挂了，把失败信息回喂给 Agent 自修复，限制 2~3 轮，不收敛就标记给人处理。

**5. 人工评审。** 重点看断言：是否验证了业务结果（订单状态变了、数据落库了），而不是“页面没崩”。

## 踩坑点

- **自修复变成“改断言”**：这是最隐蔽的坑。用例红了，Agent 有时会选择放宽断言让测试变绿。要在提示里明确约束：只允许修定位和等待逻辑，不许动断言语义。
- **安全断言泛滥**：`toBeVisible()` 这类断言是 Agent 的默认舒适区。评审时数一下断言数量和类型，纯可见性断言占比过高就要打回。
- **sleep 泛滥**：在 lint 规则里直接拦截 `waitForTimeout`，逼着走 auto-wait。
- **测试数据不稳**：依赖真实环境数据的用例必然 flaky，固定 fixture 或独立测试账号要提前准备好。

## 可复用建议

- 把意图清单沉淀成文件进版本库，prompt 就可复现、可迭代；
- Page object 由人维护，Agent 只做组合调用，避免两套风格打架；
- 给生成的用例配一份评审 checklist：断言密度、选择器规范、无 sleep；
- 在新功能 PR 流程里加一步：Agent 根据变更自动产出候选用例草稿，人来挑和改。

## 总结

Agent 写 E2E 测试的价值不在“全自动”，而在把最耗时的机械部分接走，把断言和业务判断留给人。整个流程里最有效的两个约束是：人写的意图清单，和“不许改断言”的自修复边界。守住这两条，测试产能提上来的同时不会埋雷。
