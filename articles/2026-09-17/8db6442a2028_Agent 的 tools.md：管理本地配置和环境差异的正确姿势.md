## 背景

用 OpenClaw 这类 Agent 干活时，我常遇到一个尴尬场景：同一套指令，在台式机上跑得好好的，换到笔记本或服务器上，Agent 就开始瞎猜路径、用错版本的 Python、调用根本不存在的命令。问题不在模型能力，而在于它不知道"这台机器长什么样"。

tools.md 的思路很简单：在 Agent 的工作区放一个约定文件，把本机工具链、路径、调用方式和已知坑写清楚，Agent 启动时先读它再干活。相当于把环境差异从"模型猜"变成"文档说"。

## 问题在哪

没有 tools.md 时，这些信息散落在三处：系统提示词（写死了，换机器即失效）、对话历史（每个新会话口头交代一遍）、模型先验（大概率猜错，比如默认你用 bash 而实际是 fish）。结果是反复调教，团队成员之间的环境差异更是没法同步。

## 做法与步骤

我的实践是三层结构，优先级从低到高：

1. **全局层** `~/.openclaw/tools.md`：跨项目通用的事实——解释器版本、默认 shell、编辑器、代理设置。
2. **项目层** `repo/tools.md`：进版本库，写构建命令、依赖管理方式、端口约定、禁止操作（比如"不要直接跑 migration"）。
3. **机器层** `tools.local.md`：写进 gitignore，放绝对路径、本机特有的 CUDA 版本、容器挂载点这类不可移植的信息。

合并规则要明确：项目层覆盖全局层，机器层只做补充，永不提交。

内容上坚持三条原则：

- 只写事实，不写散文。"Node 20.11 / pnpm 9"，而不是"我们用了比较新的 Node"。
- 关键工具附一句验证命令（如 `python3 --version`），让 Agent 先验证再信任。
- 单文件控制在 60 行以内，超了就该拆分或精简。

## 踩坑点

- **别放密钥。** tools.md 会进上下文和日志，token、密码一律走环境变量，文件里只写"XX 通过 env 提供"。
- **信息会过期。** 机器升级后文件没同步，Agent 反而被误导。现在我的习惯是让 Agent 执行关键命令前先跑验证行，不一致就提示更新文件，而不是盲信文档。
- **层级重复。** 全局层和项目层描述了同一件事，冲突时 Agent 行为随机。解法是划清归属：通用的进全局，项目特有的下沉到项目层。
- **跨平台路径。** Windows 同事提交了 `C:\Users\...`，macOS 直接懵。可移植的用相对路径或变量占位，绝对路径只允许出现在 tools.local.md。

## 可复用建议

新机器初始化时，可以直接让 Agent 探测环境起草一份 tools.md（一句"检查本机并起草"即可），人工审一遍再定稿，比从零手写快很多。团队场景下，把项目层 tools.md 纳入 code review，环境变更和代码变更一起进 PR。还有个隐性收益：如果某条验证命令频繁失败，说明文档和现实已经脱节——这本身就是个值得处理的信号。

## 总结

tools.md 本质是"环境即文档"的实践：把不可移植的事实显式化、分层化、可版本化。它不解决所有问题，但能显著降低 Agent 在多机环境下的翻车率，成本只是每台机器十几分钟的整理时间。对经常多设备切换、或带团队用 Agent 协作的人来说，这笔投入很划算。
