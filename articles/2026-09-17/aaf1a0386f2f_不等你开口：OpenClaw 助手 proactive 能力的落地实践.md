## 背景

绝大多数 AI 助手的使用是拉式的：你提问，它回答。但更像“助理”的形态是推式的——它盯着你关心的事，在对的时机主动开口。OpenClaw 的底子其实齐了：gateway 常驻、支持 cron 与 webhook 触发、agent 可挂工具，事件源还能用自定义 MCP server 包装内部系统状态。缺的从来不是执行能力，而是一套“什么时候该说话”的判断机制。

## 问题

把 agent 直接接上定时任务，一周内就会撞上三件事：

1. **噪音**：CI 一挂就推送轰炸，用户第一反应是关通知；
2. **成本**：每个事件都丢给大模型判断，token 烧得毫无必要；
3. **越权**：proactive 意味着无人确认就执行，一次误操作比十次漏报更毁信任。

所以核心工程问题是三个：事件从哪来、谁决定打扰你、它能自主做到哪一步。

## 做法：触发 → 判断 → 执行，三层拆开

**1. 触发层：只负责产事件**

- cron：早八点半拉一次日历、未读 PR、服务器磁盘水位；
- webhook：CI 失败、监控告警直接 POST 到 gateway。

每条事件带幂等 key（如 `ci_failed:repo-x:run-1234`），供下游去重。

**2. 判断层：规则兜底，模型加分**

先过纯代码的硬门卫：幂等去重、静默时段（注意服务器时区）、每日推送上限（比如 5 条）。过门的才进模型，且 prompt 里不问“这件事重要吗”，而是给可枚举维度：是否影响我负责的资产、是否有时效、是否需要我做决定。要求结构化输出：

```json
{
  "decision": "notify_now | batch | ignore",
  "reason": "...",
  "draft": "给用户看的一句话"
}
```

只有 `notify_now` 立即推送，`batch` 进队列等固定摘要时间一起发。

**3. 执行层：权限分档**

- 只读调查（查日志、看 diff）：自动执行；
- 写文件、给他人发消息：只生成草稿，附在通知里等你确认；
- 不可逆操作（删数据、对外发送）：禁止自主执行。

## 踩坑点

- **让模型当第一道门卫**：又贵又不稳定。规则能挡掉八成噪音，模型只处理模糊地带。
- **没做幂等**：同一次 CI 失败每 5 分钟推一遍，一周后整个渠道被静音。
- **时区**：cron 按服务器 UTC 跑，静默时段形同虚设，凌晨三点的推送很难被原谅。
- **webhook 静默失败**：事件源断了你不会知道。加心跳任务，每天核对预期事件量，落差超阈值就自我告警。
- **权限想当然**：agent 有次主动“帮忙”回复了同事消息，措辞还不对。此后对外发送一律只出草稿。

## 可复用建议

- 三层各自可测：触发层测事件完整性，判断层拿历史事件回放测误报率，执行层测权限边界；
- 判断维度写成 checklist 注入 prompt，别让模型自由发挥“重要性”；
- 每条通知带反馈入口（“这类别推了”/“这类必须推”），写回配置，阈值随使用进化；
- 上线后留决策日志，一周回看一次：误报率高于两成就收紧规则，而不是调 prompt 措辞；
- 先只做一个场景（比如 CI），稳定两周再复制到日历和监控。

## 总结

proactive 的难点不在“自动执行”——cron 和 webhook 谁都会配——而在“何时打扰你”的判断工程。我的经验浓缩成十六个字：规则兜底、模型加分、权限分层、反馈闭环。做扎实这四件事，agent 才能从一个等你提问的工具，变成一个会在对的时间敲你一下的同事。而“对的时间”，是设计出来的，不是模型自己悟出来的。
