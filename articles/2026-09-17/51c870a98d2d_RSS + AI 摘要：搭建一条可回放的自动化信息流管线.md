## 背景

RSS 看起来"过时"，但它仍是目前唯一完全由你控制的订阅协议：没有算法排序，没有推荐干预，数据结构稳定。配合 OpenClaw 的定时任务和 Agent 能力，可以把它做成一条低噪音的信息管线，而不是又一个新的信息过载源。

## 问题

直接订阅 RSS 有两个痛点：

1. 源多了看不完，源少了覆盖不够；
2. 大部分条目是标题党或跨源重复，真正值得深读的可能不到 10%。

目标很明确：每天固定时间收到一份推送，条目按主题归组、保留原文链接，且 token 成本可控。

## 做法

我现在的管线分四段，全部跑在一台小机器上：

**1. 采集（cron，每 2 小时）**
- 维护一个 feeds 列表，约 15 个源（技术博客为主，少量新闻源）
- 脚本用 etag / last-modified 做增量拉取，条目按 link hash 去重后写入本地 SQLite

**2. 过滤（纯规则，不花 token）**
- 丢弃超过 72 小时的旧条目
- 关键词黑名单 + 来源权重分，低于阈值直接丢
- 这一步能砍掉 60% 以上的流量

**3. 摘要（每天 2 次）**
- 攒下的条目按来源分批喂给模型，prompt 里强制：只用给定材料、每条摘要必须附原链接、输出固定 JSON 结构
- 两段式：便宜模型先做"值不值得进日报"的二分类，通过的再用较强的模型出摘要

**4. 推送**
- 定时任务把生成的 markdown 日报推到聊天频道，早 8 点晚 8 点各一次

## 踩坑点

- **摘要源太短**：很多 feed 只给前 200 字的 summary，摘要质量很差。对策是对进入第三段的条目再抓一次全文。
- **去重不彻底**：同一事件不同源的标题完全不同。最后用 URL 归一化 + 标题分词重合度做二次合并，解决大部分情况。
- **输出格式漂移**：模型偶尔不按 JSON 出。改成结构化输出 / 严格 schema 后基本稳定。
- **幻觉**：早期日报里出现过"模型脑补的结论"。prompt 里加"禁止出现材料之外的信息"，并且摘要和原文链接并排展示，方便抽查。
- **时区**：cron 默认 UTC，第一次推送时间全错，记得显式指定时区。

## 可复用建议

- **采集和消化分离**：采集高频、摘要低频，避免每次拉取都烧 token
- **全程落盘**：原始条目进 SQLite，日报存 markdown，出问题随时回放排查
- **先小后大**：3~5 个源跑一周，确认摘要质量再扩量，否则调参无从下手
- **记录你的行为**：把"你点开过哪些链接"记下来，隔周回顾一次，用来调来源权重——这是整条管线里唯一需要人工投入的环节，也是回报最高的

## 总结

这条管线的价值不在 AI 摘要本身，而在于每个环节都可观测、可回放、可调整。RSS 提供稳定数据源，规则过滤砍掉噪音，LLM 只做最后一公里的压缩。跑了一个多月，最大的体会是：与其追求更聪明的模型，不如先把过滤和去重做扎实。
