# 背景

单 agent 干活的瓶颈很典型：一个会话里塞进搜索、抓取、解析、写入，上下文很快被工具返回的原始数据污染，模型开始忘事、串味，后面的步骤质量明显下滑。我们的解法是把"调度"和"执行"拆开——主 agent 只做拆解和汇总，具体的脏活交给 subagent，并且尽量并行。

# 问题

以一个真实任务为例：给一个文档站做 weekly 摘要，需要抓 20 个页面、提取变更点、按主题归类、生成报告。串行跑下来 15 分钟起步，而且第 10 个页面之后，提取质量肉眼可见地下降——上下文里堆满了原始 HTML 片段，模型开始漏抓、张冠李戴。

# 做法

编排结构三层，刻意保持简单：

1. **主 agent（dispatcher）**：接收任务，拆成可独立执行的子任务清单，为每个 subagent 写清输入路径、输出路径和完成标准。
2. **subagent 池**：每个 subagent 一个独立会话，只挂载它需要的 MCP 工具。抓取类任务只给只读 fetch，不给写权限。
3. **文件总线**：所有 subagent 把结构化结果写到约定目录（JSON + schema），主 agent 在全部完成后统一读文件聚合，而不是靠 subagent 在对话里"口头汇报"。

并行度用队列控制，初始设 4，观察 token 消耗和失败率再调。失败任务单独重试，不阻塞整体。

# 踩坑点

- **共享文件冲突**：早期两个 subagent 同时写一个汇总文件，互相覆盖。改成每个 subagent 只写自己的分片，聚合由主 agent 独占完成。
- **上下文传递想当然**：subagent 看不到主 agent 的对话历史。第一版默认它会"自然知道"任务背景，结果输出完全跑偏。现在每个子任务 prompt 自带完整上下文，不依赖任何隐式状态。
- **无界并行**：一次性放出 20 个 subagent，MCP 服务端限流直接打爆，一半超时任务还触发了重试风暴。并发上限 + 指数退避是必备项。
- **错误被吞掉**：subagent 失败后返回了一段礼貌的失败说明，主 agent 却当成正常结果聚合进报告。之后统一要求输出文件带 `status` 字段，聚合前先校验。
- **成本失控**：并行是 token 放大器。给每个 subagent 设了工具调用轮次上限，超限即中止并标记，不让它无限自我纠错。

# 可复用建议

- 子任务必须**幂等且无共享写**，否则并行只会放大混乱。
- subagent 之间不要直接对话，**用文件交换数据**，主 agent 做唯一聚合点，出错时可回放、可断点续跑。
- 给 subagent **最小工具集**：能只读就别给写，能限定目录就别给全盘。
- 输出必须**结构化 + 带 status**，聚合前做 schema 校验，把"礼貌的失败"拦在报告之外。
- 并行度从 4 开始试；并发上限、重试策略、轮次上限写进配置，不要散落在 prompt 里靠模型自觉。

# 总结

subagent 编排的本质不是"多开几个 AI"，而是工程上的关注点分离：主 agent 管拆解、聚合和容错，subagent 只把自己那一小块做干净。文件总线加结构化输出是最朴素的方案，但可调试性和可控性远好于让 agent 们在对话里自由协作。这套结构后来在批量巡检、多源数据比对类任务上直接复用，改造时主要换工具挂载和输出 schema，编排骨架没动过。
