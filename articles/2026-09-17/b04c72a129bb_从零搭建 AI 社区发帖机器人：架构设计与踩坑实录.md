## 背景

社区运营里有个固定负担：周期性的摘要帖——每周更新整理、精华汇总、新资源收录。人工做，重复且容易忘，断了节奏还影响社区活跃度。我的目标是：用 OpenClaw 搭一个发帖机器人，定时从信息源采集内容，agent 生成草稿，审核后自动发布到社区。跑了两周多，基本稳定，这篇记录架构取舍和踩过的坑。

## 问题

最初版本很天真：cron 触发 → LLM 直接生成 → 调社区 API 发帖。三天内出了三次事故：一次任务重试导致同一内容连发两遍；一次 agent 编造了一个不存在的链接；还有一次帖子在凌晨三点发出（时区问题）。这些事故说明，难点不在"能不能发出去"，而在**确定性、幂等性和内容可信度**——这三件事 LLM 本身一件都解决不了。

## 架构与做法

我把系统拆成四层，每层独立失败、独立重试：

1. **采集层**：通过 MCP 工具接 RSS、GitHub Releases 和论坛 API，只做抓取和结构化，不做任何生成。产出写入本地 SQLite，带 source_id 和抓取时间。
2. **生成层**：OpenClaw 的定时任务唤醒 agent，prompt 中明确要求只允许引用采集表中存在的条目，禁止自行补充链接和数据。产出标记为 draft。
3. **审核层**：规则校验（字数、格式、链接域白名单、与近 30 天已发内容的相似度），可选加一道人工确认。通过的进入发帖队列。
4. **发布层**：独立插件消费队列，带令牌桶限流、指数退避和幂等键（source_id + 周期哈希），发布前强制查重。

所有状态落盘（SQLite + 文件日志），进程重启不丢任务。生成与发布彻底解耦，中间永远隔着一条可审核的队列。

## 踩坑点

- **幂等**：cron 重试没有幂等键，直接导致重复发帖。修复：内容哈希查重 + 发布记录表，发布前必查。
- **时区**：调度默认按 UTC 跑，发布时间全错。统一在任务里显式声明时区，发布层再校验一次"本地时间是否在允许窗口"。
- **格式**：agent 偶尔输出嵌套列表和表格，社区渲染器不支持。解决：prompt 给死格式模板 + 发布前做格式 lint，不合格打回重写。
- **幻觉链接**：最危险的一类。对策是收权——agent 只能从采集层给的候选池里引用，链接做域名校验，白名单外直接拒绝。
- **限流**：社区 API 批量发帖触发 429。加了令牌桶和退避，把发布改成队列慢消费。
- **会话污染**：agent 复用 session 时被历史上下文带偏，风格漂移。后来每次任务开新会话，只注入本次采集结果。

## 可复用建议

- 生成与发布必须解耦，中间放一层可审核、可回滚的队列。
- 任何外部写操作（发帖、评论）都要有幂等键。
- 压缩 agent 的自由发挥面：只允许引用结构化数据，链接走白名单。
- 状态落盘，别放内存。
- 保留每一版草稿和发布日志，出问题能回溯到具体是哪一层错了。

## 总结

这个项目里真正的工作量不在"接个 LLM"，而在确定性工程：幂等、限流、格式校验、内容溯源。OpenClaw 在这里的角色是把定时调度、MCP 工具调用和插件机制串起来，让你能把精力放在这些边界条件上。上线后没再出过重复帖和坏链，人工审核也从每篇必看降级为抽查——这才是自动化该有的样子。
