## 背景

社区运营里有一类重复劳动：整理上周的 issue 精华、同步版本更新、把论坛里值得讨论的帖子做二次分发。这类事情规则清晰、频率固定，很适合交给机器人。我花了两周做了一个 AI 发帖机器人，跑了一个多月，期间踩了不少坑。这篇帖子把架构和踩坑过程整理出来，供有同样需求的同学参考。

## 目标与约束

- 定时从指定数据源（issue 列表、精华帖、RSS）抓取内容，生成摘要帖并发布
- 全流程可审计：每条帖子发布前后都有状态记录，能追溯
- 内容必须过一道审核门，不允许 LLM 直接发布
- 频率受控，避免刷屏

## 架构设计

核心思路是**生成与发布解耦**，整体分五层：

1. **调度器**：cron 触发，负责任务编排和失败重试，本身不做任何业务逻辑。
2. **采集层**：拉取原始数据，标准化成统一的中间格式（标题、链接、时间戳、来源）。
3. **生成层**：一个 Agent 节点，通过 MCP 调用本地工具（去重查询、历史风格检索、摘要模板），产出草稿和元信息。
4. **审核门**：草稿落库后进入 `pending` 状态。规则校验（链接可达、长度、敏感词）通过后进入人工确认队列，确认才置为 `approved`。
5. **发布层**：发布适配器只认 `approved` 状态的记录，带幂等键调用社区 API，写回结果。

状态机很关键：`draft → pending → approved → published / rejected / failed`，所有流转都写日志。发布失败可以重试，但幂等键保证不会重复发帖。

## 实现步骤

1. 先手写三天"应该发什么"的样例帖，提炼出内容模板和风格约束，写进系统提示词
2. 搭状态表和调度骨架，发布层用假适配器先跑通全流程
3. 接 LLM 生成，加去重查询（基于标题相似度 + 链接哈希）
4. 接真实发布 API，加限流和退避重试
5. 灰度：先发到测试板块一周，再切正式板块

## 踩坑实录

**1. LLM 编造链接**。早期提示词里没强制"只允许使用上下文中的 URL"，模型会自己补一个看起来合理的链接。后来在审核门加了硬校验：草稿中所有链接必须能在采集层的原始数据里找到，否则直接打回。

**2. 相似内容重复发**。去重最初只比对 URL，但同一 issue 被人改标题重开后就是新链接。补充了标题 embedding 相似度阈值（0.85 以上拦截），误杀率可接受。

**3. 发布接口的隐性限流**。社区 API 没写明限流策略，连续发布第三条开始报错。改成队列串行发布，间隔 5 分钟以上，配合指数退避，问题消失。

**4. cron 与实际执行漂移**。任务耗时波动导致高峰期两个实例同时触发。调度器加了分布式锁（一行 Redis SETNX 的事），顺手解决了。

**5. 风格漂移**。跑了两周后帖子风格越来越"营销腔"。原因是历史帖子被当作 few-shot 喂回去，正反馈放大。修复方式：few-shot 只取人工确认过的精选样本，且每周固定，不滚动更新。

## 可复用建议

- **永远不要让 Agent 直接持有发布权限**，发布层做成唯一的、幂等的出口
- **状态机 + 幂等键**是最小可靠的自动化底座，比复杂的编排框架更耐折腾
- 审核门先做规则校验再做人工抽检，灰度期抽检比例可以逐步降低但不能降到零
- 提示词里出现的所有事实性内容（链接、数字、日期）都应该来自结构化输入，而不是让模型生成

## 总结

这个项目技术上不复杂，难点全在"让自动化可控"：解耦、幂等、可审计、有人工兜底。AI 负责内容和判断，传统工程负责流程和边界——这个分工想清楚了，后面接新的数据源、新的目标板块，基本就是加一个适配器的事。欢迎在评论区交流你们的自动化实践。
