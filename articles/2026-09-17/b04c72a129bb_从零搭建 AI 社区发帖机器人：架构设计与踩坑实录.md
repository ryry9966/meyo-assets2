## 背景

社区日常运营里有不少重复劳动：每周精华帖整理、活动预告、外部 RSS 摘要搬运。我用 OpenClaw 搭了一个发帖机器人，目标不是"全自动无人值守"，而是 **AI 起草 + 人工确认 + 定时发布** 的半自动流水线。跑了一个多月，稳定发出 40+ 帖，这里记录架构和踩过的坑。

## 最初的问题

第一版很天真：一个 cron 任务加一句 prompt，让 Agent 直接生成内容并调用发帖插件。三天翻车两次：

- 生成的"上周精华帖"里一半链接是编造的（幻觉）；
- 同一个任务被 cron 和手动触发各跑一次，重复发帖；
- 有一条帖子语气过于营销，被社区成员吐槽。

问题本质：把"生成"和"发布"耦合在一起，缺少事实校验和幂等控制。

## 现在的架构

拆成四层，各自独立：

1. **采集层**：RSS / API 拉取源数据，写入 SQLite，带 `source_id` 唯一约束。素材必须有出处，不让 LLM 凭空写。
2. **起草层**：Agent 读素材库，按模板生成草稿，输出结构化 JSON（标题、正文、引用源列表），只写草稿表，不触发任何发布动作。
3. **审核层**：两道闸门——脚本校验（链接可达性、字数、敏感词、与已发帖的相似度）+ 人工在终端确认，通过后才进发布队列。
4. **发布层**：独立 worker 消费队列，调用 MCP 发帖工具，成功后把 `post_id` 回写状态表。

关键决策：**Agent 全程不直接接触发布接口，发布权收在 worker 手里**。这一条解决了 80% 的事故。

## 踩坑实录

**坑 1：重复发帖。** cron 每天跑，手动补跑一次就双发。解法：任务带幂等键（如 `digest-2025-W23`），发帖前查状态表，已完成直接跳过。幂等键必须由内容决定，不能靠"今天跑没跑过"。

**坑 2：链接幻觉。** 即使给了素材，模型偶尔还是自己补链接。解法：草稿中的 URL 一律从素材库字段渲染，禁止模型生成 URL 字符串；脚本再对每个链接做 HEAD 请求验证。

**坑 3：时区。** 服务器是 UTC，我按北京时间想当然设了 9 点，帖子凌晨 1 点发了出去。cron 配置显式写 `TZ=Asia/Shanghai`，worker 里再校验一次当前小时。

**坑 4：会话状态膨胀。** 早期把历史草稿全塞进上下文，第二周 token 消耗翻倍、质量下降。解法：上下文只带最近 5 条已发帖标题做避重参考，其余靠相似度脚本兜底。

**坑 5：429 限流。** 发布层最初串行无重试，接口抖动导致队列堆积雪崩。加了指数退避和单日发布上限：队列最多积压 3 条，超出就报警等人工。

## 可复用建议

- 生成与发布物理隔离，Agent 永远只产出草稿；
- 幂等键跟着内容走，不跟着时间走；
- 链接、数据等外部资源由代码注入，不让模型"背书"；
- 先 dry-run 一周，所有发出内容人工过目，再逐步放开自动度；
- 状态存 SQLite 就够，别急着上消息队列。

## 总结

这个项目技术难度不高，真正的工作量在"约束 Agent"：让它只在有依据的地方发言，让发布动作可审计、可回滚。半自动（AI 起草 + 人工确认）是目前性价比最高的形态，等审核脚本准确率稳定后，再考虑对低风险类别放开全自动。实现核心就是三张表：素材、草稿、发布状态。欢迎在社区交流各自的闸门策略。
