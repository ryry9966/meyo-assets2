## 背景

LLM 本身无状态。每次新会话，模型对"你喜欢简洁回复、代码要带注释、部署用 docker compose 而不是 k8s"这些事实一无所知。Context window 再长也只是工作台，不是档案柜——塞满历史对话既贵，又会稀释模型注意力。要让助手跨会话"记得你"，必须自己设计一层记忆系统。我在自己的 OpenClaw 工作流里落地了一套方案，分享出来。

## 问题

实践里最常见的三种失败：

1. **记不住**：每个会话重新交代一遍偏好；
2. **记太多**：什么都存，检索时噪音盖过信号；
3. **记错不更新**：半年前的旧偏好和新偏好同时命中，模型随机挑一个。

## 做法

核心思路：把记忆当成一个**有 schema 的小型数据系统**，而不是一坨自由文本。

### 1. 分层

- 工作记忆：当前会话上下文，不用管；
- 情景记忆：会话结束后的摘要、关键决策，按时间组织；
- 偏好/语义记忆：蒸馏后的稳定事实，本方案的重点。

### 2. 结构化存储

每条记忆是一条结构化记录：

```json
{
  "id": "pref_response_style",
  "type": "preference",
  "content": "回复先结论后细节",
  "scope": "global",
  "confidence": 0.9,
  "source": "user_explicit",
  "updated_at": "2025-01-10"
}
```

`source` 区分"用户明说"和"模型推断"，推断类初始 confidence 给低，避免模型脑补的错误偏好被长期固化。

### 3. 写入路径（优先级从高到低）

- **显式指令**："记住我不用 vim" → 直接写入，confidence 1.0；
- **会话蒸馏**：会话结束跑一个抽取 pass，只存"会重复出现的模式"，单次性的不存；
- **工具反馈**：任务失败原因等工程事实（如"该环境无 GPU"）。

### 4. 通过 MCP 暴露成工具

把记忆封装成一个 MCP server，提供 `memory_write` / `memory_search` / `memory_forget` 三个 tool。**forget 必须是一等公民**——用户说"别再这样了"时，改写或删除旧记录，而不是追加一条矛盾的。

检索用关键词 + 向量混合，按 scope（global / project / session）过滤，top-k 控制在 3–5 条，注入 system prompt 尾部。

### 5. 更新与衰减

- 冲突裁决：显式来源 > 推断来源，时间新 > 时间旧；旧条目标记 superseded，不立刻删；
- 推断类记忆长期未被命中则 confidence 衰减，低于阈值归档。

## 踩坑点

1. **全量存储对话**。早期我把历史全部向量化，检索出来的全是上下文碎片。后来严格限定"只存蒸馏后的记录"才解决。
2. **无 schema 的自由文本记忆**。无法去重、无法改写、无法统计，模型写的东西自己都解析不了。结构化是底线。
3. **top-k 给太大**。塞 20 条进 prompt，注意力被稀释反而开始忽略。3–5 条 + scope 过滤效果好得多。
4. **没有验证闭环**。记忆系统上线后你不知道它是否生效。我加了简单日志：记录每次注入了哪些记忆、回复是否遵守，抽查几周就能清理"死条目"。
5. **隐私**。蒸馏时过滤敏感字段（密钥、地址），长期存储只允许白名单类别。

## 可复用建议

- 从最小版本开始：一张表 + 显式指令写入 + 关键词检索，够用再迭代，别一上来上图数据库；
- 记录必带 `source` / `confidence` / `updated_at`，否则后期没法治理；
- 会话蒸馏用低成本小模型跑即可，不占主模型额度。

## 总结

记忆系统的本质不是"存得多"，而是"检索时给对的那几条"。把它当成有 schema、有生命周期、有验证闭环的数据系统来设计，比指望模型自己"会记"可靠得多。最小可行版本一个下午能搭出来：建议先只开显式指令路径跑两周，确认命中质量后，再决定要不要加蒸馏和衰减。
