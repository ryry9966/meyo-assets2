## 背景

我们的 Agent 跑了半年，memory 里积累了两千多条记录：部署事故复盘、配置变更、踩过的坑、用户偏好。`memory_recall` 是这些记忆的唯一检索入口，它的召回质量直接决定 Agent 是"靠谱同事"还是"失忆实习生"。

最初我们用的是纯 embedding 语义检索，一直觉得够用，直到线上连续出现几次答非所问，才认真做了一轮对比。

## 问题

两类典型失败，分别打在两种方案脸上：

**语义检索的坑：搜不到精确标识符。** 用户问"ERR_52003 那个错误怎么处理"，语义检索返回一堆泛泛的"错误处理心得"，而真正记录了这个错误码的那条排不进 top5。embedding 模型对低频 token、数字串、下划线命名的敏感度普遍很差。

**全文检索的坑：搜不到换了说法的内容。** "上次部署卡住那事"搜不到标题为"CI 流水线超时排查"的记录。同义改写、口语化提问是常态。

结论很清楚：单用哪个都有硬伤。

## 做法

改成双路召回 + 融合：

```yaml
recall:
  fts:    { engine: sqlite_fts5, tokenizer: trigram, top_k: 10 }
  vector: { model: bge-m3, metric: cosine, top_k: 10 }
  fusion: { method: rrf, k: 60 }
  final:  top 5, 创建时间做 tie-breaker
```

全文路用 SQLite FTS5 的 BM25，负责精确匹配；语义路用向量召回，负责语义泛化；两路各取 10 条，用 RRF（倒数排名融合）合并后取 5 条喂给模型。

评测方式：人工攒了 40 组"提问 → 应命中的记忆"对，跑 recall@5。结果大致是：纯语义 0.72，纯全文 0.65，混合 0.9 以上。提升主要来自标识符类查询，这正是语义检索最弱的部分。

## 踩坑点

1. **中文全文检索默认是坏的。** FTS5 默认 unicode61 分词器按空格切，中文整段成一个 token，等于搜不到。要么换 trigram 分词器，要么入库前先做分词。这个坑能浪费一整天。
2. **换 embedding 模型必须全量重建向量库。** 新旧向量混存的相似度完全是噪音。我们后来在每条向量上挂了模型版本字段，启动时校验。
3. **单条记忆太长会稀释召回。** 500 字以上的长记忆语义匹配"擦边"严重，按主题切成 100–200 字的小段后明显改善。
4. **时间因素不能丢。** 半年前的旧记录经常霸榜，融合后加创建时间做同分排序，效果好于硬砍旧数据。
5. **别只看 top1。** demo 里 top1 命中很漂亮，但线上模型完全有能力从 5 条候选里自己挑，评测口径要用 recall@5。

## 可复用建议

- **记忆量 1k 以内，先全文就够了**，别为了架构先进性上向量库。
- **混合是默认答案，但权重别拍脑袋。** 两路各 10 条 + RRF 基本免调参，比手动调加权系数靠谱。
- **原文永远留底。** 索引、向量、分词方案都可能换，原始文本是唯一可以随时重建的东西。
- **把 recall 未命中的 case 记下来。** 攒够 20 条就是下一轮评测集，检索质量是迭代出来的，不是选型一次定终身的。

## 总结

一句话：语义搜索解决"说法不一样"，全文搜索解决"符号要精确"。对 memory_recall 这种高频、低延迟、查询五花八门的入口，混合检索 + RRF 是目前性价比最高的组合。但比选型更重要的是有自己的评测集——别信任何人的默认参数，包括这篇里的。
