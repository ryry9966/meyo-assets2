## 背景

OpenClaw 的 memory_recall 是 agent 长期记忆能否真正"用起来"的关键：会话中被写入的记忆片段，靠 recall 环节在后续对话里捞回来。社区常见两条实现路线：语义搜索（embedding + 向量检索，如 sqlite-vec、Qdrant）和全文搜索（SQLite FTS5、Meilisearch 这类 BM25 实现）。不少插件默认堆语义搜索，理由是"更智能"，但智能不等于召回准。

## 问题

我们在实际使用中撞上两类相反的故障：

- 用户问"上次那个 ECONNREFUSED 怎么解决的"，语义搜索召回一堆泛泛的网络错误讨论，偏偏漏掉那条精确记录了错误码和修复步骤的记忆，罕见 token 在向量里被稀释了。
- 反过来问"之前聊过的部署思路"，措辞和原记忆完全不同，全文搜索一个词对不上，直接空手而归。

单押一路检索，总有一类 query 会翻车。真正的问题不是选哪个，而是各自的失效边界在哪。

## 做法

最有效的办法是拿真实数据自己测：

1. 从历史会话整理约 40 条真实 query，每条标注期望召回的记忆 ID，作为固定评测集；
2. 全文搜索：SQLite FTS5，中文先用 jieba 分词再入库，查询侧同样分词；
3. 语义搜索：bge-m3 出向量 + sqlite-vec，取 top-5；
4. 混合：两路各取 top-5，用 RRF（倒数排名融合）合并；
5. 跑 Recall@5 和平均延迟，之后每次换模型、改参数都重跑同一评测集。

我们的结果：含精确 token（错误码、函数名、日期、版本号）的 query，全文搜索命中率明显更高；口语化改写的 query 语义搜索更稳；混合方案整体最优，平均 Recall@5 比单路高出约 15 个百分点，延迟只多一次轻量查询。

## 踩坑点

- FTS5 默认 unicode61 tokenizer 基本不切中文，必须先分词再写入，否则退化成整句匹配，几乎是必踩的第一个坑；
- embedding 对哈希值、ID、版本号极不敏感，别指望语义搜索兜底精确匹配；
- top-k 别设太小，但要配相似度阈值，低于阈值宁可不召回，避免低质结果污染上下文；
- 评测集必须来自真实会话，自造 query 会天然偏向你设想的措辞，结论不可信。

## 可复用建议

- 入库时原文和向量都存，索引只是视图，原文永远是兜底；
- 直接上混合检索，RRF 融合实现不到二十行，无额外模型依赖，收益确定；
- 给记忆加元数据（时间、来源、会话 ID）并在 recall 时过滤，很多"检索不准"本质是没过滤；
- 把评测集当回归测试，任何索引层改动后重跑一遍再上线。

## 总结

语义搜索 vs 全文搜索不是二选一：精确 token 靠全文，改写泛化靠语义，混合 + 元数据过滤是当前性价比最高的组合。比选数据库更重要的是先建一套真实 query 的评测集——没有度量，所有检索优化都是玄学。
