## 背景

在 OpenClaw 的插件和 Agent 流程里，LLM 输出经常被当作结构化数据消费：MCP 工具参数、节点间传递的中间结果、自动化任务的下一步动作。Prompt 里写了"请只输出 JSON"，模型大多数时候也确实配合。但"大多数时候"在自动化链路里不够用——一天几百次调用，只要有一次输出裹了层代码围栏，整条流水线就停了。

## 问题

从实际收集的脏输出看，大致三类：

1. **包裹型**：JSON 外面套了 Markdown 代码围栏，或前后带"好的，以下是结果："之类的客套话；
2. **语法瑕疵型**：尾逗号、单引号、注释、`True/None` 这类 Python 字面量；
3. **截断型**：`max_tokens` 打满，JSON 只写到一半。

三类的处理策略完全不同，混在一起用正则硬修，是 bug 的主要来源。

## 做法

我们的思路是**分层解析，先廉价后昂贵，每层命中即返回**：

1. **严格解析**：先直接 `json.loads`，不命中再进下一层；
2. **剥离围栏与散文**：去掉代码围栏，按第一个 `{` 或 `[` 到最后一个 `}` 或 `]` 切片；
3. **平衡提取**：不做贪心切片，而是逐字符扫描，跟踪花括号深度并跳过字符串字面量内部的花括号，取出第一个语法完整的对象；
4. **容错修复**：交给 json5 / json-repair 类库处理尾逗号、单引号、注释；
5. **截断检测**：解析失败且输出长度接近 token 上限时，不要硬修，直接把报错信息拼回对话重试一次，让模型自己补全。

每层命中都记日志：命中层级 + 原始输出哈希。解析成功后再过一遍 pydantic / jsonschema 校验——**合法 JSON 不等于结构正确**。

## 踩坑点

- **正则提取嵌套 JSON 会翻车**：`{.*?}` 遇到字符串里的 `}` 或嵌套对象就断在半路，必须用括号深度扫描；
- **截断的 JSON 别修**：修复库能把半截 JSON 补"合法"，但补出来的字段值是猜的，下游当真数据用更危险；
- **多个 JSON 块**：模型有时输出"说明 + JSON + 解释"三段，取第几个块要规则固定，并用测试锁死；
- **Python 的 `json.loads` 接受 `NaN/Infinity`**，这不是合法 JSON，校验层要拦；
- **别静默吞异常**：解析失败务必保留原始输出（至少哈希加落盘），否则没法离线复盘、没法补测试用例。

## 可复用建议

- 解析逻辑收敛到一个模块、一个入口函数，别让每个插件各写各的；
- 把线上真实失败样本固化成单元测试，**测试集比解析器本身更值钱**；
- 监控两个指标：一次解析成功率、容错层命中分布——容错命中率突然升高，往往意味着模型或 prompt 被改动了；
- 有 function calling / 结构化输出能力优先用，但它不是免死金牌，兜底层照样要有。

## 总结

对 LLM 输出的正确心态是"默认它会脏"。防御性解析不是堆更多正则，而是把失败模式分类，按处理成本从低到高排队，截断这种无法本地修复的情况果断重试。解析器本身只有百来行，真正的资产是持续积累的失败样本和命中统计。
