## 背景

Agent 一旦接上真实工具——shell、文件系统、MCP server、各类 HTTP API——每次调用都有副作用。设计问题就从“它能做什么”变成“哪些动作可以自主做，哪些必须停下来问人”。这条线划不好，要么自动化形同虚设，要么半夜悄悄删了共享目录。

## 问题：两种失败模式

- **过度询问**：每一步都等人点头，自动化沦为“人肉确认器”。更糟的是，问得太多，人会不假思索地全部批准——这比不问还危险。
- **过度自主**：花钱调用付费 API、给真实用户发消息、`rm -rf`、push 到 main。
- 还有隐性失败：**问的时机和方式不对**。问的是开放性问题（“我可以继续吗？"），人没有低成本做决策的材料。

## 做法：按“影响半径 × 可逆性”分三层

| 层级 | 策略 | 典型动作 |
|---|---|---|
| Tier 0 | 直接干 | 只读、检索、工作区内写文件、生成草稿 |
| Tier 1 | 干了留痕 | push 到功能分支（非 main）、发到测试频道、存邮件草稿 |
| Tier 2 | 必须问 | 花钱、对外发消息、删共享数据、改生产、授予权限 |

落地五步：

1. **盘点工具清单**。列出 Agent 可触达的所有动作（包括 MCP server 里的每个 tool），逐个标注影响半径和可逆性。按实际效果分类，不按工具名。
2. **配置默认策略**。三层各自的默认动作，加上预算限制（次数/金额/频率）和熔断条件。
3. **把“问”设计成结构化决策**。展示 diff、后果、备选方案、默认动作（通常是中止）、超时策略。永远不问开放性问题。
4. **边界沿调用链传播**。子 Agent、插件、被调用的 MCP server 继承同一套权限，不允许绕过。
5. **全量留痕，周期复盘**。每周看一次审批日志和自动执行日志，有证据再放宽边界。

## 踩坑点

- **确认疲劳**：问太勤 → 人盲批，整道防线失效。
- **按工具名而非效果分类**：一个叫 `fetch_page` 的工具内部照样可以 POST。
- **dry-run 失真**：预演环境和真实环境配置不一致，“演练通过”不代表能上。
- **问晚了**：问了“要不要部署”，但 merge 在提问前已经发生。确认点必须在不可逆动作**之前**。
- **超时语义没定义**：人两小时没回，Agent 是等、中止还是继续？必须显式写死，默认中止。

## 可复用建议

- 起步从严，用日志证据逐步放宽，不要反过来。
- 与其靠问，不如把工具切得更细：读 / 预览 / 提交拆成三个独立工具，把确认点固化进工具协议本身。
- 问人时永远附默认选项；无人响应即执行默认（中止）。
- 每接入一个新工具或插件，重过一遍分层表。
- 审计日志当一等公民输出，别散落在 stdout 里。

## 总结

权限边界不是一次性配置，而是随工具面扩大持续校准的过程。核心判断只有两个维度：**这步是否可逆，出错影响多大**。可逆且影响小就让它自己干并留痕；不可逆或涉及外部世界就停下来问——而且要让“问”本身可以被低成本回答。边界清晰了，自动化才敢真的放开跑。
