## 背景

大多数 agent 的交互模式是"你问它答"：会话一结束，agent 就静止了。但在 OpenClaw 的架构里，agent 常驻在你的机器或网关上，本身具备定时触发能力。HEARTBEAT.md 就是把这种能力工程化的一份约定文件：agent 每隔固定间隔自动醒来一次，读取工作区根目录的 HEARTBEAT.md，判断"这次有没有该干的事"——有就执行并汇报，没有就静默返回。

它解决的不是模型能力问题，而是调度问题：主动性不再依赖你记得去问。

## 问题

只开心跳、不写清单，会出现两种典型失败：

- **空转**：agent 每次醒来回复一句"没有需要处理的事项"，token 白烧；
- **乱动**：任务边界模糊，agent 凭理解自由发挥，做出不可逆操作，或者频繁推送打扰。

所以核心问题是：如何把"我想让它主动做的事"，写成一份**可判定、低噪音、有护栏**的清单。

## 做法

1. **建 HEARTBEAT.md**：每条任务写三要素——判定条件、动作、输出渠道。
2. **约定静默协议**：无事可做时回复 `HEARTBEAT_OK`，不推送给用户；只有真正需要人知道的事才发消息。这是降噪的关键。
3. **配置心跳间隔**：建议从 30 分钟起步，并让心跳判断走便宜的小模型。
4. **任务分三层**：
   - 观察类：读日志/目录/接口，只在异常时发声；
   - 行动类：调用 MCP 工具或插件，比如抓数据写入本地文件；
   - 汇报类：定时摘要（日报、待办），推送到 IM。
5. **状态落盘**：用 `heartbeat-state.json` 记录上次执行时间、已处理条目 ID，避免重复执行。

一个可参考的片段：

```markdown
- 每天 08:00 后的首次心跳：汇总今天日历与未读邮件，发一条摘要到 Telegram。
- 每次心跳：检查 ~/downloads 下 24h 内新增的 pdf，重命名并归档，无需通知。
- 每次心跳：curl 本机 MCP server 健康接口，非 200 时告警。
- 以上都不满足：回复 HEARTBEAT_OK。
```

## 踩坑点

- **间隔拍脑袋定**：5 分钟一次的心跳，成本远超预期。先 30 分钟，观察一周再调。
- **任务写得太模糊**："帮我盯一下服务器"这种描述，模型每次理解不一致。必须写成可判定的 if-then。
- **忘了静默协议**：每次心跳都推送，用户第三天就会关掉整个功能。
- **心跳里塞不可逆操作**：删文件、代发邮件这类动作，务必加白名单或人工确认环节。
- **"每天一次"靠次数估算**：会随运行漂移，让 agent 读系统时间判定日期边界。
- **状态不落盘**：agent 记不住"上次做到哪"，同一批文件会重复处理。幂等性要自己保证。

## 可复用建议

- 把 HEARTBEAT.md 当"值班手册"写，而不是愿望清单：一条 = 一个判定 + 一个动作 + 一个输出。
- 心跳是调度层，MCP/插件是执行层，保持分离。任务清单里只写"调用什么工具"，不写实现细节。
- 观察类任务先行，跑稳一两周，再逐步放开行动类。
- 心跳判断用小模型即可，便宜且够用，把大模型留给真正的任务执行。

## 总结

HEARTBEAT.md 的价值不在于"AI 变聪明了"，而在于把主动性从概率事件变成工程约定：固定间隔、可判定条件、静默协议、状态落盘。这四件事凑齐，agent 才能真的在你不开口的时候，把该做的事做完，且不打扰你。建议从两条观察类任务起步，一周后再评估要不要扩清单。
