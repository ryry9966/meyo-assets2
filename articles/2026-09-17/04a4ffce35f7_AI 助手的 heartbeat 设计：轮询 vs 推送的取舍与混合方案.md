## 背景

OpenClaw 这类常驻 Agent 有个绕不开的问题：它大部分时间在"睡觉"，但必须能被及时唤醒——处理新消息、跑定时任务、清队列。唤醒机制基本两条路：轮询（heartbeat，Agent 每隔 N 分钟主动看一眼）和推送（事件源主动打过来，webhook、长连接、消息队列）。两种我们都在生产环境跑过，记录一下取舍。

## 问题

轮询的问题不是"能不能用"，而是成本结构：每次心跳如果不加控制，都会组装上下文、甚至触发一次 LLM 调用。设 5 分钟一次，一天 288 次唤醒，其中九成是空转——你为空转付 token、付配额、付日志存储。拉长间隔又牺牲实时性，用户消息等十分钟才被回，体验不可接受。

推送反过来：延迟低、不浪费，但它要求 Agent 侧可达。NAT 后的家庭机器收不到 webhook；推送链路还要处理认证、重试、去重、风暴抑制——复杂度不会消失，只是从"等"变成了"接"。

## 做法

我们的结论是混合方案，按事件的延迟要求分流：

1. **事件分级**。实时类（用户消息、告警）走推送；延迟容忍类（摘要、清理、巡检）走心跳。梳理后会发现，绝大多数事件其实属于第二类。
2. **两段式心跳**。心跳第一段是廉价探测：用本地脚本或 MCP 工具查队列长度、消息表有无新行、标志文件的 mtime。只有探测命中才进入第二段，真正唤醒 LLM。这一步把空转成本压到接近零，是整个设计里性价比最高的改动。
3. **推送侧加固**。本地起网关（或走内网穿透/云中继），事件先落盘 spool 再触发 Agent；每条事件带幂等键，重试不重放。Agent 掉线时事件堆在 spool，上线后批量回放并合并，避免重连风暴。
4. **心跳参数**。基础间隔加随机抖动，避免多实例共振；连续空转后指数退避；设每小时唤醒上限做熔断。
5. **可观测**。记录每次唤醒的 reason，统计空唤醒率和"唤醒到动作"延迟。空唤醒率突然升高，通常是探测条件写错了。

## 踩坑点

- **心跳直接喂 LLM**。最早的版本每次心跳都组装完整上下文发给模型，一天烧掉的 token 里九成是"没什么事"。改成两段式后成本降了一个数量级。
- **推送没有幂等键**。网关超时重试导致同一条指令执行两遍，文件被删了两次。任何推送都必须假设它会重试。
- **笔记本休眠**。心跳依赖定时器，机器睡了定时器就停。唤醒后要做补偿：比对上次心跳时间，超时任务补跑一次而不是静默跳过。
- **双通道去重**。推送和心跳同时在线时，同一事件可能被两条路各触发一次。事件层要有全局去重（幂等键 + 已处理表）。
- **固定间隔踩整点**。所有实例都在整分钟唤醒，撞上游 API 限流。加抖动。

## 可复用建议

- 判断规则一句话：延迟要求秒级且事件源能主动找到你 → 推送；否则轮询，但必须加廉价探测前置。
- 唤醒要便宜，动作才敢频繁。把"要不要醒"和"醒来干什么"拆成两个阶段。
- 事件永远先落盘，唤醒消费端保持无状态，崩了重放即可。
- 心跳不是越密越好，用空唤醒率反推合理间隔。

## 总结

轮询和推送不是二选一。工程上更稳的形态是：推送管实时性，心跳兜底并承担后台任务，中间用两段式探测控制成本，用幂等和落盘保证两条通道合并时不重复。先测量空唤醒率，再调参数——这个顺序别反了。
