## 背景

玩 Agent 这段时间，最明显的感受是"每次都在重新自我介绍"。系统提示词定义了 Agent 的人格和能力边界，AGENTS.md 描述了项目规则，但没有一个地方告诉它：我是谁，我的机器长什么样，我习惯怎么协作。

OpenClaw 这类常驻 Agent 理论上可以靠对话记忆慢慢积累用户画像，但实际体验是：记忆是无结构的，重要信息和不重要的一起堆，还会漂移。上周纠正过的偏好，这周它又犯。

## 问题

没有用户上下文时，典型症状：

- 每次重复说明技术栈（"我用 Arch + fish，别给我 bash 命令"）
- Agent 给出的方案不符合你的工程习惯
- 时区、命名风格、代码风格反复出错
- 依赖厂商的记忆功能，不可导出、不可审查，换工具就丢

核心问题是：用户上下文需要一个明确、可版本化、可审查的载体，而不是散落在聊天记录里。

## 做法

我的方案是在工作区根目录放一个 `USER.md`，作为每次会话注入的用户上下文：

```markdown
# USER.md

## 环境
- OS: Arch Linux, fish shell
- 编辑器: Neovim

## 偏好
- 中文交流，代码注释和 commit message 用英文
- 先给结论，再给推理；不要客套
- 类型标注齐全，优先标准库

## 禁区
- 不要主动 git push
- 不要执行任何 sudo 命令

## 项目速览
- 主力项目: xxx（技术栈、部署方式各一句话）
```

三步接入：

1. 写 USER.md，控制在 60 行以内；
2. 在 AGENTS.md 或系统提示词里显式引用：`用户上下文见 USER.md，优先级高于对话记忆`；
3. 进 git 仓库，用 dotfiles 同步到多台机器。

另外和 Agent 约定一个动作：它学到新东西时只提议 diff，由你确认后写入。这样记忆变成"有审核的写入"，而不是黑盒。

## 踩坑点

- **写太长**。USER.md 每个会话都吃上下文预算，超过一屏就开始稀释关键信息，控制在 50–80 行。
- **写成散文**。大段自述 Agent 提取不到重点。短句、列表、可判定的规则才有效。
- **放敏感信息**。USER.md 会被完整读入上下文并随请求发出，真实姓名、密钥、内网地址不要放。
- **硬编码易变事实**。IP、端口、临时路径写进去，两周后就是污染源。写"去哪里查"，而不是"值是多少"。
- **与 AGENTS.md 冲突**。两边规则打架时行为不稳定。明确层级：项目规则 > 用户偏好 > 对话记忆。

## 可复用建议

- 模板固定五段：环境 / 偏好 / 禁区 / 项目 / 更新记录
- 更新记录带日期，方便回滚和 review
- 分层管理：全局 USER.md 放稳定偏好，项目级放该仓库特定上下文
- 每月像 review 代码一样 review 一次，删掉过期条目
- 多个 Agent 工具共用同一份文件——这是它相比闭源记忆功能最大的优势

## 总结

USER.md 本质上是你和 Agent 之间的一份契约：把"你应该知道我什么"从玄学变成显式文件。它便宜、可审查、可迁移，比黑盒记忆可控得多。先写 20 行，用两周，你自然知道该往里加什么。
