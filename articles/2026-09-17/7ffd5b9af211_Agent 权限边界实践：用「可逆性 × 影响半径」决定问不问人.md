## 背景

Agent 接上 MCP、插件和一堆自动化工具之后，能力上限往往不再由模型决定，而是由我们愿意交出多大的操作空间决定。回看社区里翻车的案例，多数不是模型"变笨"，而是把只读查询和删库级别的工具放在了同一个自动执行域里。权限边界这个话题不性感，但它决定了你敢不敢让 agent 挂着跑。

## 问题

什么时候该问人，什么时候自己干？这个问题没有标准答案，但拍脑袋决定一定出事。我的经验是：判断维度收敛到两个就够了——**可逆性**和**影响半径**，频率可以作为调节项。

## 做法：四级工具分级 + 一个审批门

**第一步，在 MCP / 插件配置层给每个工具打标：**

- **L0 只读**（搜索、读文件、查状态）：自动执行
- **L1 可逆写**（写工作区文件、改本地草稿）：自动执行 + 审计日志
- **L2 对外可见但可撤回**（提 PR 不合并、发草稿邮件、建 issue）：规则内自动，超规则问人
- **L3 不可逆或高影响**（删数据、付款、发正式消息、动生产配置、批量外发）：必须人工确认

**第二步，给自动执行设预算。** L1/L2 按会话设上限：次数、金额、时间窗。超预算自动降级为"问人"，而不是静默继续。

**第三步，认真设计"问"这个动作本身。** 这是最容易被忽略的部分：

- 一次问清楚：把计划、diff、影响面、回滚方式放在同一次确认里，别拆成十次
- 超时默认拒绝，不是默认通过
- 让拒绝便宜（一键否决），让补救容易（动作前保留快照）

**第四步，定期回看决策日志。** 哪些"问了人"的案例其实人只是无脑点同意？哪些"自动执行"的案例事后被回滚了？这两个信号分别告诉你该升权还是该收权。

## 踩坑点

1. **确认疲劳。** 问得太频繁，人会变成无脑点"同意"的橡皮图章——这比不问更危险，因为它制造了虚假的安全感。
2. **缺上下文的确认。** "要继续吗？"没人判断得了。确认请求必须自带 diff、目标和回滚方式，否则问等于没问。
3. **异步审批悬挂。** 人不在场时 agent 反复等待重试，导致审批通过后重复执行。超时语义必须显式定义。
4. **权限蠕变。** 每出一次事故就加一条黑名单，半年后规则库没人看得懂。黑名单要定期回收，靠分级而不是堆例外。
5. **用"问人"逃避设计责任。** 把所有模糊情况都抛给人，本质是把系统复杂度转嫁给操作者。

## 可复用建议

- **先收敛后放开**：新工具一律按 L3 跑一两周，看日志再降级，比事后收权成本低得多
- **三件套底线**：每个自动动作必须可解释（为什么做）、可回滚（做错了怎么办）、可关停（一键 kill switch）
- **口诀**：不可逆就问，可逆就干但留痕；影响出工作区就问，影响在沙箱内就干

## 总结

权限边界不是一份写死的安全策略，而是随信任数据持续演化的配置。目标既不是"问得最少"，也不是"问得最多"，而是让每一次人工介入都发生在人真正具备信息优势的地方。把确认预算花在不可逆的操作上，其余的交给规则、日志和回滚。
