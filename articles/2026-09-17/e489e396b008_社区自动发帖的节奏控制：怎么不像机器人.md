## 背景

用 OpenClaw 做内容自动化的人，大多走过同一条路：先接一个 MCP 工具把帖子发出去，验证通路没问题；然后挂上定时任务，每天固定几个点发。通路验证完，真正的问题才开始——账号开始"看起来像机器人"。

## 问题

定时任务的本质是时钟驱动：到点就发，不管社区现在的状态。这会暴露出几个典型特征：

- 间隔过于规律，标准差接近零；
- 发布时间与社区活跃时段错位（服务器是 UTC，社区在东八区）；
- 内容结构雷同，标题模板一眼可辨；
- 故障重试时突发连发。

管理员的肉眼和论坛的反垃圾规则，识别的就是这些统计特征，而不是"内容是不是 AI 写的"。

## 做法

我把节奏控制拆成四层，按优先级排：

**1. 事件驱动优先于时钟驱动。** 定时器只负责"唤醒 Agent 去判断"，不负责"直接发布"。发布前先判断：社区是否冷清、同类话题是否刚有人发过、上一条帖子是否还没有回应——不满足条件就跳过本次。

**2. 活跃窗口 + 宽区间抖动。** 发布限制在社区本地时间的活跃时段，间隔在一个宽区间内随机，而不是整点 ±5 分钟：

```python
def next_slot(now, window=(8, 23), lo=90, hi=260):
    delay = random.uniform(lo, hi) * 60
    slot = now + timedelta(seconds=delay)
    if not window[0] <= slot.hour < window[1]:
        slot = slot.replace(hour=random.randint(*window),
                            minute=random.randint(0, 59))
    return slot
```

**3. 日配额 + 令牌桶限速。** 每天硬上限（比如 4 条），防止重试和积压补发造成突发。宕机恢复后，积压任务只补发最新一条，其余作废。

**4. 内容层面的节奏。** 长短交替、话题分散、开头方式轮换。不要用同义词替换制造"随机性"——那只会让文本更假。

## 踩坑点

- **随机种子写死**：重启后随机序列重复，等于没抖动，用系统熵源初始化。
- **抖动区间太窄**：±3 分钟的抖动在间隔分布图上仍是一条直线。
- **失败立刻补发**：重试退避至少 30 分钟起步，否则故障时段会连发一串。
- **多身份共用一个调度器**：多个账号被同一个 tick 同步共振，间隔高度相关，要分调度、分参数。
- **忽略周末和节假日**：周末活跃窗口和工作日差异明显，准备两套窗口参数。

## 可复用建议

- 节奏参数全部抽成配置：活跃窗口、间隔上下界、日配额、退避曲线，别硬编码。
- 上线前先 dry-run 两周：只记录不发，画出计划时间与实际间隔的分布。间隔的变异系数（CV）低于 0.3，说明还是太规律。
- 每条帖子落库：计划时间、实际时间、跳过原因。跳过率本身是有价值指标——一个从不跳过的调度器，多半没接事件判断。
- 保留每周一次人工抽检：机器管节奏，人管口味。

## 总结

"不像机器人"的核心不是加随机数，而是让发布行为对外部世界有响应：社区安静就降速，有话才说。时钟驱动加抖动只是及格线，事件驱动、配额、退避、可观测性叠起来，节奏才会自然。先 dry-run、看分布、再上线，比任何精心调的随机函数都管用。
