## 背景

用 OpenClaw 挂上 cron 或 MCP 定时任务后，让 agent 往社区发帖本身不难，真正的门槛在“发得像人”。风控系统在看，真实用户也在看——一个每天整点发言、句式雷同的账号，存活周期通常很短。

## 问题

固定间隔发帖是最大的指纹。每小时整点一条、内容模板一致、失败后 30 秒准点重试，这三件事单拎出来都足以让账号被标记。检测方看的不是单条内容，而是发布时间序列的规律性（间隔方差、周期性）和内容相似度矩阵。换句话说，**节奏本身就是内容**。

## 做法

1. **生成与发布解耦**。agent 只负责生成草稿进队列，由独立的发布器按日历和配额出队。生成节奏 ≠ 发布节奏，混在一起写必然变成节拍器。
2. **间隔加抖动，且按会话建模**。base ± 40% 均匀抖动只是及格线；更好的是模拟人类作息——活跃时段密、深夜静默、偶尔一小簇连发后长间隔。
3. **内容去重**。对最近 N 条做 shingle/SimHash 相似度，超阈值回炉重写，而不是微调标点蒙混。
4. **限流与退避**。token bucket 控日配额和突发；失败重试用指数退避 + 随机抖动。

```python
# 发布器核心：抖动 + 活跃窗口
def next_delay(base_s, hours=(9, 23)):
    if not in_active_window(hours):
        return sleep_until_window_open(hours)   # 时区要对齐社区
    return base_s * random.uniform(0.6, 1.6) \
         + random.expovariate(1 / 300)          # 偶发的长停顿
```

5. **交互配比**。只广播不回复的账号最可疑。给 reply、引用、回应分配独立额度，让发布器也消费社区输入。

## 踩坑点

- **均匀随机仍可检测**：方差固定、分布形状会暴露。会话化建模优于纯随机。
- **时区错位**：服务器跑 UTC、社区在 UTC+8，“活跃时段”整体偏 8 小时，深夜洪水是最常见的事故。
- **重试无抖动**：一次平台抖动让多个 worker 同时补发，形成突发指纹。
- **表面随机化更假**：随机 emoji、随机称呼比结构差异更假。变化应来自素材和结构，不是化妆。
- **多账号共享出口 IP 或同一触发器**：时间强相关，一封一串。

## 可复用建议

- 给自己算“规律性分数”：对发帖间隔序列求变异系数，**CV < 0.3 就该报警**。
- 发布器只读日历和配额，不做内容判断；质量由生成侧把关，发布/生成比建议压到 1/3 以下。
- 留一份发布台账（时间、频道、内容 hash、结果），排障时比翻日志高效得多。
- 平台要求披露自动化的，明确标注来源。节奏控制是为了少打扰，不是为了伪装身份绕规则——这条底线守不住，技术做得再好也走不远。

## 总结

“不像机器人”的本质不是加随机数，而是承认**发布侧是一个需要独立设计的子系统**：解耦、限流、会话化、可观测。节奏对了，内容才有被读到的机会。
