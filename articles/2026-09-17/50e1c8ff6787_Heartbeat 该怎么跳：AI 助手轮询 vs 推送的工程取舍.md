## 背景

OpenClaw 这类常驻型 agent 网关，模型调用其实是按需发生的——agent 平时并不"在线思考"。于是有个绕不开的问题：**谁来决定 agent 什么时候醒来？** 目前主流就两种机制：

- **轮询（heartbeat）**：网关按固定间隔注入一条心跳 prompt，agent 检查任务清单（如 `HEARTBEAT.md`），有事做事，无事静默。
- **推送**：外部事件（webhook、精确 cron、MCP 通知、文件变更）直接触发一次 agent 调用。

## 问题

单用哪个都有毛病。纯轮询的时延上限就是心跳间隔——30 分钟一次的心跳，意味着最坏情况事件要等 30 分钟才被处理；为压时延把间隔调到 5 分钟，token 成本线性上涨，因为**每次心跳都是一次带上下文的完整调用**。纯推送则脆弱：webhook 丢了就是丢了，没有兜底；本地部署还要额外解决公网可达的问题。

## 我的做法：分层，各干各的活

1. **推送负责"触发"**。时效敏感的事件全部走推送：仓库 webhook、日历提醒用精确 cron、IM 消息走消费者回调。每个事件带幂等键，失败进重试队列。
2. **heartbeat 负责"对账 + 兜底"**。保持低频（30–60 分钟），心跳 prompt 里写明协议：对照 `HEARTBEAT.md` 检查推送是否漏单、状态是否漂移；无事可做就返回空操作，不产生用户可见消息。
3. 两者共享会话上下文，但给心跳轮次单独打标记，方便事后审计心跳到底烧了多少 token。

## 踩坑点

- **静默协议没写好**。早期没约定"无事时返回什么"，agent 每次心跳都礼貌性汇报一句，一天刷几十条。在心跳 prompt 里加明确的静默条件后才治好。
- **上下文膨胀**。心跳与业务对话共用会话，几十轮心跳历史把上下文撑满，质量和成本双恶化。要定期归档、对心跳轮次做摘要压缩。
- **推送无对账**。服务端超时重发 + 我这边没幂等，同一事件被执行两次。幂等键 + 去重记录解决。
- **机器睡眠**。笔记本合盖后心跳停摆，恢复后不会补跑。要么接受"错过就错过"，要么在心跳里做时间窗对账。
- **间隔叠加 LLM 延迟**，任务串行堆积，外部看起来像"卡死"。

## 可复用建议

- 原则一句话：**推送做触发，轮询做对账。**
- 心跳必须便宜且安静：低频 + 静默协议 + 独立成本统计。
- 推送必须可靠：幂等、重试、死信记录，并且永远假设推送会丢。
- 心跳间隔不是越短越好。先测单次心跳的平均 token 成本，再反推预算能承受的频率。

## 总结

heartbeat 的价值不是"实时"，而是"最终一致"。把实时性交给推送，把可靠性交给轮询，agent 才能既灵敏又省钱。别让心跳变成每 5 分钟一次的昂贵问候。
