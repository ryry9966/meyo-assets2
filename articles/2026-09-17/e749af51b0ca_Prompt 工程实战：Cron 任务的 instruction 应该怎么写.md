## 背景

OpenClaw 的 cron 任务和系统 crontab 看起来很像：定个时间，到点执行。区别在于执行的不是一个脚本，而是一次完整的 agent 会话——你写的 instruction 就是这次会话的全部输入。agent 每次被唤醒，都是一个没有上下文的新员工。instruction 写成什么样，自动化就稳定成什么样。

## 问题

我见过（自己也写过）几类典型的失败 cron：

- instruction 只有一句话，比如"每天早上总结一下行业动态"。跑三天，输出格式换了三次，发送位置也不固定。
- 数据源挂了，agent 没被告知怎么处理，于是开始编造内容，定时任务变成了定时造谣。
- 写了"接着上次没做完的继续"，但 cron 会话不继承历史，agent 只能瞎猜。
- 一条 instruction 塞了四件事，跑到一半超时，前面做的全部作废。

共同根源：把 instruction 当成了备忘录，而不是运行手册。

## 做法：五段式 instruction 模板

写 cron instruction 时，我固定用五个段落，缺一段后期一定补课：

1. **触发语境**：开头一句"你正在执行定时任务 XX，无人值守，无历史上下文"。能有效抑制 agent 等待确认、试图翻记忆的行为。
2. **任务目标**：一句话说清做什么。一个 cron 一个职责，多件事拆成多个任务。
3. **输入与工具**：明确数据来源（文件路径、MCP 工具名、API），需要参数的直接写死，不要让 agent 自由选工具。
4. **输出契约**：发到哪里、什么格式、篇幅上限。格式给固定模板，下游才好消费。
5. **异常分支**：源不可用怎么办、结果为空怎么办、允不允许重试。我通常写"失败时发送一条一句话错误说明，不要静默，不要自行补救"。

节选一个我在跑的日报任务的 instruction：

> 你正在执行定时任务 daily-report，无人值守。用 fetch 工具读取指定 URL 的最新列表，筛选 24 小时内的新条目，按"标题 / 一句话摘要 / 链接"三行格式整理，发送到指定 Telegram 群，全文不超过 300 字。如果抓取失败或列表为空，发送"今日无更新或抓取失败：原因"，不要尝试其他数据源。

## 踩坑点

- **别用相对时间**。"每早"让 agent 自己算时区很容易出错。调度交给 cron 表达式和时区配置，instruction 里不要做时间推理。
- **别给多余的写权限**。定时任务意外改了配置文件，排查起来非常痛苦。
- **别省异常分支**。宁可每天多收一条"失败了"，也不要静默——你不会知道它静默了多久。
- **别追求一次跑完大任务**。高频小任务远比低频大任务可控，token 消耗也更好预估。

## 可复用建议

- 写完先手动触发一次再上线。把 cron 当成"会在凌晨三点独自运行的代码"来 review。
- 所有 cron instruction 存进一个文件做版本管理，改版留痕。
- 定期翻 cron 会话记录，像看日志一样。格式漂移大多在第一周就能发现。

## 总结

cron 任务的可靠性工程，本质是 instruction 的确定性工程。它多久跑一次，就值得你花多少时间打磨——一条每天执行的 instruction，值得花半小时写成运行手册，而不是十秒钟写完，再花几个凌晨去救火。
