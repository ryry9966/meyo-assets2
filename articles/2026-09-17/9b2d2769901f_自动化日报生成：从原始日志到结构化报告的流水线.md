## 背景

我们维护着十来个服务，日志散落在容器 stdout、Nginx access log 和几个业务库表里。此前日报靠值班同学手动整理：翻日志、数报错、写摘要，平均耗时要 40 分钟，而且每个人写出来的格式都不一样，出了偏差也没法追溯。这篇文章记录我们把它改造成一条自动化流水线的过程，以及在 OpenClaw 里落地的具体做法。

## 问题拆解

看似简单的"生成日报"，实际是三个独立问题：

1. **数据从哪来**：多来源、多格式、时区不统一；
2. **谁来摘要**：数字必须准确，叙述必须可读——这两件事的可靠性要求完全不同；
3. **怎么交付**：定时推送到 IM 群，不能重复、不能截断、不能在数据不完整时硬发。

## 流水线设计

五个阶段，每段都可独立运行和测试：

1. **采集**：定时任务拉取前一自然日的日志，按约定目录落盘，采集时统一时间戳到东八区，每个来源一个文件；
2. **规整**：纯脚本把原始日志解析成固定 JSON schema——日期、服务名、错误计数、关键事件列表等字段。这一步**不用模型**，全部确定性代码；
3. **汇总**：把结构化 JSON 喂给 Agent，只要求生成叙述性摘要。数字一律来自 JSON，模型不做任何计算，只负责措辞；
4. **渲染**：Markdown 模板 + 数字 + 摘要，产出完整日报文件；
5. **推送**：发送到 IM 群，同时记录幂等键（日期 + 流水线版本号）。

在 OpenClaw 里的分工：阶段 3-4 由 Agent 完成，通过 MCP 工具读写中间文件和调用推送接口；阶段 1-2 是普通脚本，由 cron 触发。核心原则一句话：**代码管数字，模型管措辞**。

## 踩坑点

- **时区边界错误**：日志是 UTC，报告按本地日期取数，第一版把"昨天"取错了 8 小时的量。修复：采集阶段统一时区，且报告日期显式传入，不要依赖运行时的"今天"；
- **模型算数不可靠**：早期让模型根据计数算错误率，出现过个位数级别的偏差。修复：所有指标由脚本算好，并加了一道校验——从生成的报告里反向抽取数字，与源 JSON diff，不一致就拒绝发布；
- **日志格式漂移**：某服务升级后日志格式变了，解析器静默产出空统计。修复：每个阶段加覆盖率检查，解析率低于阈值直接中止并告警。宁可不出报告，不出错报告；
- **重复推送**：推送超时重试导致群里出现两份日报。修复：推送前先按幂等键查重；
- **长报告截断**：IM 消息有长度上限。修复：群里只发摘要段，完整报告以文件形式附带。

## 可复用建议

- 用固定 JSON schema 作为阶段间契约，schema 变更走 review，别让上下游默契漂移；
- 不要写成一个巨型脚本，阶段隔离后，哪段坏了修哪段；
- 保留原始日志快照和中间产物，出问题时能回溯到"报告里的这个数字来自哪条日志"；
- 健康检查前置：数据覆盖率不足就熔断，这条比任何功能都重要；
- 日报本身也归档，积累一段时间后天然可用于趋势对比和复盘。

## 总结

这条流水线的价值不在于"AI 写日报"，而在于把一个手工、易错、不可审计的日常仪式，拆成了可验证的阶段化流程。LLM 只是其中一段，且只做它擅长的事。整个搭建花了两个晚上左右的业余时间，之后日常维护成本接近零——偶尔出问题，因为阶段隔离，定位基本在十分钟以内。如果你也有类似的手工汇报负担，建议从"先把数字算准"开始，再考虑让模型接管叙述。
