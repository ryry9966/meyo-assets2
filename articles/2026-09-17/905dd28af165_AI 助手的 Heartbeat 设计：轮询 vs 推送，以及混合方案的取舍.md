# 背景

在 OpenClaw 这类常驻 Agent 框架里，heartbeat（心跳）承担两件事：一是证明 agent 还活着，二是周期性唤醒它检查待办。最常见的实现是定时轮询——每 N 分钟醒一次，读一遍心跳清单（比如 `HEARTBEAT.md`），没事就回个轻量确认。但随着接入的技能、监控源、提醒越来越多，纯轮询会暴露出问题，很多人于是转向推送（webhook / 事件注入）。这篇文章记录我在这两种模式之间的取舍过程。

# 问题

两种模式各有硬伤：

- **轮询**：延迟上界就是轮询间隔。想要分钟级响应就得缩短间隔，token 成本线性上涨——哪怕 90% 的唤醒最后什么都没做。
- **推送**：每个事件源都要写接入（webhook 鉴权、payload 转换、注入到哪个 session），而且“没收到推送”无法区分“没事发生”和“管道挂了”。

本质上是两个问题被耦合在一起：**活性检测**（我还活着吗）和**事件分发**（有事发生时唤醒我）。混在一起设计，两头都做不好。

# 做法

我的方案是分层混合：

1. **先给事件分类**。按“能容忍多大延迟”划分：日历提醒、定时巡检这类容忍 15–30 分钟，走轮询；CI 失败、指定联系人的消息、传感器触发，要求秒级，走推送。
2. **轮询侧做减法**。心跳清单控制在 10 行以内，只放“看一眼就知道要不要做”的条目；重检查（跑脚本、调 API）外包给外部 cron，结果写回文件，heartbeat 只读结论。无事时返回固定短确认，避免每次都完整回复烧 token。
3. **推送侧收口到一个入口**。所有 webhook 打到网关层，统一鉴权、去重、格式化，再注入对应 session，别让事件源直连 agent。
4. **轮询兜底推送**。保留一个长间隔（如 1 小时）的低频心跳，专查“距上次收到推送多久了”，超时就告警。
5. **记录 wake reason**。每次唤醒记下触发原因，月底看各类唤醒的占比和 token 花销，再决定调间隔还是砍清单。

# 踩坑点

- **心跳清单膨胀**：从 5 行涨到 40 行，每次唤醒成本翻了数倍。清单要像代码一样过 review，改之前先问“这条能不能外部化”。
- **固定间隔踩点**：整点轮询会和系统 cron、备份任务挤在一起。加随机抖动（±10%）。
- **webhook 裸奔**：没有鉴权的推送端点等于任何人都能向你的 agent 注入指令，至少上 HMAC 签名。
- **静默失败**：推送队列挂了一周没人发现，因为“没消息”看起来像“没事”。必须有超时告警，别依赖人肉感知。
- **session 污染**：高频心跳把琐碎记录刷进主会话上下文，挤占有效窗口。心跳单独开 session，结论再同步过去。

# 可复用建议

- 决策规则一句话：**要求的响应延迟低于你能接受的轮询间隔，就上推送；否则轮询**。
- 轮询间隔取“最大可接受延迟”，不是“越短越好”。
- 心跳本身也要被监控——它是你的看门狗，看门狗不能没人看。
- 推送管道的健壮性上限，就是 agent 主动性的上限；管道挂了，agent 就退化成纯被动应答。

# 总结

不要一上来就追求全事件驱动。先用轮询把 heartbeat 跑起来，成本可控、行为可预测；只为真正延迟敏感的少数路径加推送，并始终保留轮询兜底。heartbeat 设计到最后是个预算问题：你愿意为“主动性”支付多少 token、多少复杂度。想清楚这一点，取舍自然清晰。
