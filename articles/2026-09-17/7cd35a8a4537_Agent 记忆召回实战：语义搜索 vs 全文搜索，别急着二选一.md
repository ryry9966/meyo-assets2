## 背景

长期运行的 Agent 都会撞上同一个问题：记忆越攒越多，`memory_recall` 的质量直接决定它"像不像记得你"。OpenClaw 场景里，记忆通常是一堆 Markdown 片段——用户偏好、项目决策、踩坑记录、会话摘要。召回层一般两条路线：**语义搜索**（embedding + 向量检索）和**全文搜索**（BM25 / SQLite FTS5 这类）。社区里经常争论哪个更好，实际答案是：各有明确的失效场景，单选哪个都会翻车。

## 问题

两条路我们都在真实项目里翻过车：

- **语义搜索对"意思相近"很强，对精确 token 很弱。** 用户问 "AUTH-2147 那个 bug 后来怎么解决的"，向量检索返回一堆"权限相关讨论"，唯独没有那条带编号的记录——embedding 把标识符模糊掉了。
- **全文搜索相反，换个说法就全军覆没。** "上次那个数据库超时"查不到记成 "DB connection pool 耗尽" 的条目，中英文混存的记忆库里尤其严重。

## 做法与步骤

结论先给：默认上混合检索。四步：

1. **双索引。** embedding 索引负责语义，FTS5/BM25 负责精确匹配。写入时同时更新，不要事后补索引，否则召回结果会有诡异的"时间断层"。
2. **RRF 融合。** 两路结果用 Reciprocal Rank Fusion 合并。比调加权分数稳得多——两边分数量纲根本不一样，权重基本是玄学。
3. **元数据过滤前置。** 时间衰减、项目/标签过滤放在融合之前做，先把三个月前的过期决策和别的项目的记忆剔掉，再谈排序。
4. **建一个 30~50 条的评测集。** 把真实踩过"召回不准"的「问题 → 目标记忆」对记下来，每次改参数跑一遍命中率。没有这个，所有调参都是体感。

## 踩坑点

- **分块太大。** 整篇会话摘要塞一个 chunk，召回时上下文爆炸，Agent 反而被无关细节带偏。200~500 字 + 标题元数据比较稳。
- **embedding 模型与主语言不匹配。** 英文模型处理中文记忆，召回质量肉眼可见地下滑。选型前务必用自己的语料测，别信榜单。
- **只写不清。** 过时决策（"暂时用 A 方案"）留在库里反复被召回，Agent 会一直引用已废弃的结论。需要定期合并、降权或打上"已失效"标记。
- **评测集闭门造车。** 自己编的问题风格太规整，指标虚高。尽量从真实会话里捞。

## 可复用建议

- 新项目别纠结选型，直接 hybrid + RRF，代价只是多维护一个索引。
- 标识符类内容（错误码、文件路径、commit hash）在写入时额外抽出来做精确映射表，召回命中直接置顶，绕过排序。
- 记忆写入时打齐**时间、项目、类型**三个标签。经验上，召回层 80% 的问题靠过滤就能解决，剩下的才轮到算法。

## 总结

语义搜索解决"换个说法也能找到"，全文搜索解决"精确的东西必须找到"——Agent 的记忆两种需求都有，所以这不是二选一的题。而且实践中真正决定召回质量的，往往不是检索算法本身，而是分块策略、元数据质量，和那个不起眼的小评测集。先让评测集存在，再谈优化。
