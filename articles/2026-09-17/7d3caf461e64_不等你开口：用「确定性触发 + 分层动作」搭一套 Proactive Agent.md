## 背景

多数 AI 助手的使用模型是「你问它答」。但当 Agent 接上 MCP 工具、文件监听和定时任务后，它完全有能力在你不开口时就干活：早上把日程、CI 状态、未读消息汇总成一条简报；PR 连续两次挂 CI 时主动拉日志给出初步诊断；新文件落盘后自动归档并生成摘要。

问题不在于「能不能做」，而在于「怎么做才不会被用户关掉」。

## 问题

我见过几类失败的 proactive 尝试：

- **无差别推送**：助手每半小时汇报一次「一切正常」，第三天被静音；
- **让 LLM 自由决定「何时行动」**：行为随机，同一条件有时触发有时不触发，无法复盘；
- **定时任务空转**：没有任何变化也全量调用工具链，token 费用翻倍；
- **越权动作**：自动替用户发了消息、改了配置，翻车一次信任就没了。

核心矛盾：主动性是有成本的（注意力 + 费用 + 信任），缺省设计往往把这个成本直接转嫁给用户。

## 做法：触发确定性，判断概率化

一条踩坑后固定下来的原则：**什么时候行动由确定性机制决定，说什么、做什么才交给 LLM**。

**1. 选触发源（不用 LLM 判断时机）**
- 定时：cron 驱动的晨间简报、周报汇总；
- 事件：webhook、文件监听、git hook、日历变更；
- 阈值：通过 MCP 工具轮询监控指标，超阈值才触发。

**2. 动作分层**
- Tier 0 静默后台：整理文件、预热缓存，不打扰；
- Tier 1 汇总：并入每日简报，不单独推送；
- Tier 2 主动提醒：确需注意才单独推送，并设每日上限（比如 3 条）；
- Tier 3 执行动作：可逆、低风险且在 allowlist 内的才自动执行；不可逆操作一律生成草稿等确认。

**3. 最小例子：PR 诊断助手**

CI webhook 触发 → 脚本检查该 PR 是否连续失败两次（确定性）→ Agent 通过 MCP 拉日志、比对上次失败原因 → 相同原因且已提醒过则去重跳过 → 否则产出「失败摘要 + 疑似原因 + 建议命令」发到频道。整条链路里 LLM 只负责归纳，不负责决定「要不要管」。

## 踩坑点

- **去重靠外部状态**：每次主动运行应是无状态会话，用状态文件记录「上次提醒内容的 hash + 时间戳」，否则同一问题反复提醒；
- **冷却期必须有**：同一触发源设 cooldown，避免事件风暴下连环推送；
- **先只读后写入**：前两周只开读类工具，观察误报率，再逐步放开写权限；
- **安静时段**：夜间只入队不推送，早上合并成一条；
- **留决策日志**：每次「触发 / 不触发 / 说了什么」都落盘，调阈值全靠它，不靠感觉。

## 可复用建议

1. 把 proactive 拆成三件事：**触发器、判断层、权限边界**，分开演进，别糅在一个 prompt 里；
2. 提醒预算制：每天主动消息设硬上限，宁可漏报，不可轰炸；
3. 变化检测前置：用 hash/diff 判断「有没有变化」，没变化就不进 LLM，省钱省心；
4. 先静默运行两周校准阈值，再正式交给用户。

## 总结

Proactive 不是让 Agent「做更多」，而是让它在正确的时机、以最小的噪音做对的事。工程上就是三件朴素的事：确定性的触发、受限的判断、可审计的权限。先把只读场景跑稳，再谈自动执行，这套东西才立得住。欢迎在社区里晒你的触发规则和误报率数据，这类经验比 demo 更有价值。
