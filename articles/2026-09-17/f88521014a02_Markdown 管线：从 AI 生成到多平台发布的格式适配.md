## 背景

在 agent 工作流里，写作环节基本已经交给模型：调研、成稿、修订都能在 Markdown 里闭环。但成稿之后才是麻烦的开始——公众号只接受内联样式的 HTML，掘金和 GitHub 直接吃 Markdown，知乎介于两者之间，邮件还要求表格布局。同一次生成，三个平台三种待遇，手工适配既慢，又容易在复制粘贴中引入新错误。

## 问题

我们最初的方案是“每个平台一个脚本”，结果三个脚本各自解析、各自渲染，修一个 bug 要改三处。更麻烦的是 AI 输出本身不稳定：标题层级从 `##` 起步、偶尔把整篇包进一个代码围栏、生成不存在的链接、frontmatter 里的冒号不带引号导致解析直接失败。管线要同时解决两件事：清洗 AI 输出，以及一份源稿到多平台的确定性转换。

## 做法

核心原则只有一条：**规范源稿保持纯净 Markdown，平台差异全部收进转换层。**

1. **规范化**：对 AI 输出先做一轮清洗——剥掉误包的代码围栏、把标题层级重排到 `#` 起步、校验外链可达性、修复 frontmatter。这步不做，脏数据会被后面所有渲染器继承。
2. **统一 AST**：选一套解析器生态（我们用 remark/mdast），所有转换写成 AST 插件，而不是字符串替换。字符串替换在嵌套结构里必然出错。
3. **平台渲染器**：每个平台一个 renderer，输入同一棵 AST。公众号 renderer 用 highlight.js 离线预高亮成内联样式 HTML，不依赖平台端 JS；掘金 renderer 基本直出；邮件 renderer 走表格布局。Markdown 表格在小屏上不可控，公众号版直接降级为卡片式分段。
4. **Lint 关卡**：渲染前跑一遍检查——图片域名白名单、禁用标签清单、代码块语言合法性、中英文标点混用。规则全部配置化，加规则不改代码。
5. **产物隔离**：源稿放 `src/`，产物放 `dist/<platform>/`，源稿永远只读。转换必须幂等，跑几遍结果一致。

最后把管线包成一个 MCP tool 暴露给 agent：agent 交稿后自己跑 lint、看转换 diff 报告，确认无违禁项再走发布，格式问题在发布前暴露，而不是发布后被读者发现。

## 踩坑点

- **公众号的 sanitizer 很激进**：class 属性会被剥掉，必须全量内联样式；table 标签部分场景直接丢失，宁可提前降级，别赌平台的容忍度。
- **图片是重灾区**：外链图床会被防盗链拦截，`![]()` 的 alt 在粘贴后经常丢。我们在管线内先按平台要求归一化图片（转存、重命名、改写引用），不依赖平台编辑器的行为。
- **源稿里坚决不写内联 HTML**：一旦混入，“纯净源稿”的前提就破了，之后每个渲染器都得加特判，特判会指数繁殖。
- **快照测试省命**：每个 renderer 维护一份 golden file，改插件后 diff 一眼看出哪个平台的产物变了、变得对不对。

## 可复用建议

- 差异下沉到转换层，源稿保持只读——这一条决定管线能活多久。
- Lint 规则配置化，让“平台禁什么”成为数据而不是代码。
- 给 agent 一个自检入口，把格式约束变成工作流里的硬关卡。
- 转换必须幂等，产物不可手改；要改就改源稿重新构建。

## 总结

这套管线没有用任何新东西，就是 remark 插件、几个 renderer、一份 lint 配置。价值在于把“平台怪癖”从人的记忆挪进了代码：AI 负责生产内容，管线负责确定性地适配格式，人只审最终 diff。多平台发布从手工活变成了一条可测试的构建流程，这才是自动化该有的样子。
