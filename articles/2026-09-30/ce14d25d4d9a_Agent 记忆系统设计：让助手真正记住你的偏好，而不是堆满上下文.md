## 背景

LLM 本身无状态。OpenClaw 这类常驻助手，一旦跨会话，你昨天说过的「用 pnpm」「时区 UTC+8」「commit 不带 emoji」就全丢了。很多人的第一反应是往 system prompt 里堆上下文，堆到三四千 token 之后，真正要办的事反而被淹没。记忆系统要解决的不是「存得多」，而是写、查、删三件事都可控。

## 问题

拆开看是三个问题：

1. **记什么**：偏好（稳定）、事实（项目相关）、过程（上次会话的决策）混在一起，检索必然互相干扰。
2. **怎么写**：什么时候触发写入？用户随口一句「下次别这样」要不要记？
3. **怎么读**：每次会话注入多少？注入错了比不注入更糟。

## 做法

OpenClaw 默认用工作区的 `MEMORY.md` 和 `memory/` 目录做持久化，会话启动时注入。在这个基础上建议按四步工程化：

1. **分层**。拆成三层：Profile（用户偏好，稳定、量小）、Episodic（按天的会话摘要与决策）、Facts（项目事实，按需检索）。Profile 常驻注入，上限 500 token；后两层走检索，合计不超过 1000 token。
2. **写入分级**。显式指令（「以后都用 pnpm」）直接写；同一行为重复 ≥3 次才由提取逻辑落盘；单次推断不写。写入前先做语义去重——与已有条目相似度超阈值就走更新而非新增，同时刷新 `updated_at` 和 `confidence`。
3. **混合检索**。关键词命中（偏好类条目往往有明确触发词）+ 向量相似度，再乘以 recency 衰减和 `hit_count` 权重，取 Top-N。别只用向量，精确匹配场景（比如「pnpm」）纯相似度会漏。
4. **生命周期**。每个条目带 `last_used` 和 `confidence`，长期未命中自动降权；用户纠正（「不是这个意思」）触发覆写而不是追加；提供 `/memory list`、`/memory forget` 这类命令，让用户能看、能删——透明度决定信任度。

如果想走 MCP 扩展，可以把读写封成一个 memory server：`upsert(query, content, type)` 和 `search(query, top_k, filters)` 两个接口就够。提取逻辑放 Agent 侧的 skill 里，存储和检索留在服务侧，职责干净。

## 踩坑点

- **全记**：见什么都存，两周后检索全是噪声。只收高信号条目。
- **重复条目**：同一偏好处存五个措辞变体，注入时 token 翻倍且互相矛盾。去重必须做在写入时，事后清理成本高得多。
- **写入时机错误**：会话中途提取，把用户还没确定的方案存成事实。统一在会话结束或显式指令时写。
- **密钥入库**：token、密码被提取逻辑当成「重要信息」存下来。写入前过一遍敏感信息过滤。
- **注入过量**：记忆吃掉一半上下文，当前任务反而变笨。每层设死 token 上限，超了就按权重截断。
- **只用向量**：精确偏好匹配失败，退化成模糊推荐。混合检索是底线。

## 可复用建议

- 条目 schema 最小集：`id`、`type`、`content`、`source`、`confidence`、`created_at`、`last_used`、`hit_count`。先用 SQLite，别上来就上向量库。
- 可信度排序：显式指令 > 重复行为 > 推断，写入策略跟着走。
- 每次写入记录 `source`（哪个会话、哪句原话），出问题能回溯。
- 评估别省：准备 10 个历史会话做回放，检查偏好是否被正确应用，比肉眼聊天可靠。

## 总结

记忆系统的核心不是攒数据，而是**写得克制、查得准、舍得删**：分层控制注入预算，写入分级加去重，混合检索兜底，再配上用户可见可删的出口。先跑通这套最小闭环，再考虑向量库和知识图谱——大多数个人助手的场景，前者已经够用。
