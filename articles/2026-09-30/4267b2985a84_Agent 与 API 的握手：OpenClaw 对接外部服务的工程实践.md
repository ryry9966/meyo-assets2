## 背景

OpenClaw 里的 Agent 本身只会"想"，不会"做"。它能不能查库存、发工单、拉报表，完全取决于你给它接了哪些外部服务。社区里目前主流的对接方式有两条路：写一个 MCP Server 把 API 包装成工具，或者在插件里直接注册 tool。两条路本质相同——都是把 HTTP 调用翻译成 Agent 能理解、能调用的工具接口。这篇帖子里，我把最近对接一个内部工单系统的经验整理出来。

## 问题

"能跑通"和"稳定可用"之间差得很远。常见的症状：

- Agent 调工具时参数乱填，或者该调的时候不调；
- API 返回 5KB 的 JSON，两三轮对话就把上下文吃满；
- 接口报错后，Agent 只拿到一句 "error"，开始盲目重试；
- 写操作没有确认环节，一条指令直接改了线上数据。

这些都不是模型能力问题，而是握手协议没设计好。

## 做法

我的实际流程分六步：

1. **先定工具边界，再写代码。** 一个工具只做一件事。`create_ticket`、`query_ticket`、`close_ticket` 分开，不要做一个带 action 参数的大工具。工具名和 description 是写给模型看的，参数含义、单位、必填项要写清楚。

2. **认证收敛到环境变量。** Token 只从环境变量或 secret 文件读取，配置文件里不留明文，日志里不打印完整凭证。

3. **把 API 响应翻译成模型友好格式。** 只返回模型需要的字段，超长列表截断并提示用分页参数；错误信息写成模型能据此行动的话，比如"日期格式应为 YYYY-MM-DD，请修正后重试"，而不是透传堆栈。

4. **超时与重试在工具层兜底。** 内部设 5–10 秒超时，只对幂等的 GET 自动重试，POST 交给 Agent 决策。失败时返回结构化错误：错误码加一句人话描述。

5. **写操作加确认门。** 涉及创建、修改、删除的工具，先返回预览——"将创建工单：标题 X，指派 Y，确认？"——用户确认后再真正执行。

6. **先测工具，再测 Agent。** 用 mock 响应验证 schema 和解析逻辑，确认无误后再让 Agent 真实调用，观察它是否用对参数。

## 踩坑点

- **description 太简略。** "查询工单"这种描述，Agent 分不清是查自己的还是查全组的，默认范围和过滤条件要写明。
- **透传原始响应。** 分页接口一次回 200 条，直接塞给模型既费 token 又降准确率，工具层必须做裁剪。
- **忽略幂等性。** Agent 偶尔会重复调用同一个写工具，POST 侧要么做幂等键，要么在工具层加短时间去重。
- **时区与日期格式。** API 要 UTC、用户说"明天"，工具层必须显式转换一次，差八小时的坑迟早踩。
- **错误被吞。** try/except 之后返回 None，Agent 会以为调用成功了。失败必须显式返回。

## 可复用建议

- 工具设计三原则：小而正交、描述精确、错误可行动。
- 每次工具调用记录 request id、参数摘要、耗时，出问题能回放。
- 读和写分离：读工具可以放开自动调用，写工具默认走确认流程。
- 给工具加版本号，schema 变更时旧配置不至于静默失效。

## 总结

对接外部服务，不是"调通 HTTP"就结束，而是设计一套 Agent 能稳定使用的握手协议：边界清晰的工具、模型友好的返回、可控的失败路径、必要的确认机制。把这四件事做扎实，Agent 才能从"能演示"走到"敢上线"。欢迎在评论区交流你们踩过的坑。
