## 背景

单 agent 的瓶颈通常不是“不够聪明”，而是两件事：上下文被工具输出灌满，以及独立子任务只能串行跑。比如一次代码库调研要读 20 个文件，或一批数据校验脚本各跑各的，全塞进主对话，结果就是上下文爆炸、响应变慢、注意力被稀释。

OpenClaw 的 subagent 机制针对的就是这个问题：主 agent 负责拆任务和汇总结论，子 agent 各自在独立会话里干活，只把结果回传。

## 问题

我们当时的真实需求：对一个 8 万行的旧项目做架构梳理，同时批量生成接口文档。单个 agent 跑了几分钟还在翻文件，主对话堆了上百条工具调用记录，到生成文档阶段已经开始“忘事”，前面读过的结论后面引不出来。

## 做法

我们的编排结构比较朴素，四步：

1. **主 agent 只做拆解和裁决。** 先把任务拆成互不依赖的子任务清单，每个子任务写清楚：输入是什么、产出写到哪个文件、什么算完成。
2. **子 agent 靠文件系统交接，不靠对话。** 每个子任务约定独立输出目录（如 `out/04_api_docs/`），子 agent 把结果写成结构化 Markdown 或 JSON。主 agent 之后只读这些文件，不读子 agent 的过程记录。
3. **限制并发，分批派发。** 一次最多 3 个子 agent。IO 等待多的搜索类任务可以放到 4-5，跑本地重脚本的压到 2。宁可多一轮，不要一次全压上去。
4. **主 agent 验收和聚合。** 每批回来只做三件事：检查产出文件是否存在且格式合法、抽查结论是否自洽、把通过的结果合并成最终交付物。不合格的单独重派，不带历史。

## 踩坑点

- **多个子 agent 写同一个文件。** 最早让所有子 agent 追加写一份汇总文档，并发时互相覆盖。改成“一人一目录，主 agent 统一合并”后才稳定。
- **拆得太细。** 有一次拆出 17 个子任务，派发和验收的开销超过干活本身。经验值：一个子 agent 应该能在一个上下文窗口内独立完成，拆不动再细分。
- **指令模糊。** “帮我看看这个模块”派下去，回来的东西基本不能用。派发前要把验收标准写进任务描述，等价于给同事写需求单。
- **失败静默。** 子 agent 中途失败但没写产出，只检查“有没有返回”就会漏掉。约定：失败也要写一个带 error 字段的结果文件，验收时一并检查。
- **成本失控。** 并行 4 个子 agent 就是 4 份 token 同时烧。给每类任务定了预算上限，超了自动降并发。

## 可复用建议

- 任务描述模板化：目标 / 输入路径 / 输出路径 / 完成标准 / 禁止事项，五项写全再派发。
- 产出用固定 schema 的 JSON 或 Markdown 段落，方便程序化校验，而不是“读一眼感觉对”。
- 并发数按任务类型分组设置，不要全局一个数。
- 主 agent 保持“瘦”：只读摘要和产出文件，不读子 agent 的原始过程。这是长任务编排能不能撑住的关键。

## 总结

subagent 编排不是“多开几个 AI 就更快”，本质是一次工程化重构：把上下文管理和任务调度从主对话里剥离出去。我们的体感收益是长任务完成率明显上升、主对话不再膨胀，代价是要提前想清楚任务边界和交接格式。建议从 2-3 个子 agent 的小规模编排起步，把交接协议跑顺了再加并发。
