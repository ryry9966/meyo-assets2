## 背景

单 agent 串行处理是大多数人的起点：一个会话里让模型读文件、跑命令、写总结。任务一多，问题就暴露出来——上下文越来越长，响应越来越慢，一个长任务卡住，后面全部排队。我们在批量场景（比如一次审计十几个仓库的依赖、给一批 PR 做初筛）实测，串行跑一轮一小时起步，中间任何一步失败都得重来。

于是把 subagent 编排提上日程：主 agent 负责拆任务、发任务、收结果，子 agent 各干各的，互不污染上下文。

## 问题

串行模式有三个具体痛点：

1. **上下文膨胀**：所有中间结果堆在一个会话里，后期模型"记不住"早期结论；
2. **延迟线性叠加**：十个独立子任务串行跑，耗时就是单个的十倍；
3. **失败耦合**：第 7 步挂了，前 6 步的成果很难复用。

## 做法

以"批量审查多个仓库的依赖风险"为例，我们的编排流程：

**第一步：任务分解。** 主 agent 把总目标拆成 N 个独立子任务，每个子任务一个仓库、一条明确指令、一个强制输出格式（JSON schema：`{repo, findings[], severity}`）。

**第二步：隔离工作区。** 每个子 agent 分配独立目录，git 场景直接用 worktree，从根上避免写冲突。

**第三步：并发控制。** 并发数压在 3~5。不是越高越好，API 限流和结果聚合的复杂度都会跟着上来。

**第四步：结果聚合。** 主 agent 只做两件事：校验子结果的 schema，把合格结果合并成报告。子 agent 的中间过程（读了哪些文件、跑了哪些命令）不回传主会话，只回传结论。

**第五步：失败兜底。** 单个子任务失败不影响整批，聚合阶段标记 failed 项，支持断点重跑。

工具侧配合 MCP：给子 agent 只挂它需要的最小工具集——审查依赖的就不给 shell 写权限，按需分配。

## 踩坑点

- **上下文继承太多**：最初子 agent 继承主会话全部历史，token 翻倍还互相干扰。改成"只传任务描述 + 必要背景"后效果反而更好。
- **输出格式漂移**：模型偶尔在 JSON 外包一层解释文字。聚合前统一做解析清洗，解析失败直接判失败重试，别靠正则硬抠。
- **共享资源竞争**：两个子 agent 同时写同一个缓存目录导致文件损坏。共享写操作要么每子任务独立路径，要么加文件锁。
- **并发打满限流**：第一版没限并发，15 个子任务同时起，直接被 rate limit 打回。重试要指数退避，不能傻等固定秒数。
- **成本失控**：并行意味着 token 消耗是并发的倍数。加单批预算上限，超了自动降级为串行。

## 可复用建议

1. 子任务设计原则：**窄、独立、无共享状态**。判断标准是"不看其他子任务能不能独立完成"。
2. 主 agent 保持"薄"：只做拆分、分发、校验、聚合，别自己下场干重活。
3. 输出永远是结构化的，宁可多一次 schema 校验。
4. 并发数做成配置项，不要写死。
5. 一切幂等：任何子任务重跑都不应产生副作用。

## 总结

subagent 编排不是炫技，核心收益就两点：延迟从串行叠加变成并行取最大值，上下文从一锅粥变成各管各的。真正的门槛不在"能不能起多个 agent"，而在任务拆分是否干净、结果契约是否稳定、失败路径是否想清楚。把这三件事做扎实，并行编排就是稳定的工程手段，而不是玄学。
