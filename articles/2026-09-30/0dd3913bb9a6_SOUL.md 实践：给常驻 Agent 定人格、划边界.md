## 背景

用 OpenClaw 跑常驻助手一段时间后，你会发现一个事实：模型本身的“性格”是随机的。同一个任务，今天话痨明天冷淡；遇到模糊指令，有时谨慎有时莽。SOUL.md 就是解决这个问题的机制——工作区里的一份 Markdown，每次会话启动时注入系统提示词，相当于 Agent 的出厂设定。

它很轻，但大多数人要么不用（默认人格，通用到没记忆点），要么写成万字小作文（占上下文、抓不住重点）。这篇记录我迭代几版后沉淀下来的写法。

## 问题：人格和边界混在一起写

我早期最大的坑，是把“它是谁”和“它该怎么做”写进同一个文件：语气偏好、工具调用规则、安全底线搅在一起。结果每次想调语气都心惊胆战，怕顺手把“删除文件前必须确认”这类边界删掉。另一个症状是边界写了但没生效——SOUL.md 里写“转账前要确认”，Agent 理解成“我会在转账的同时告诉你我要转账了”。

## 做法

1. **先分文件。** SOUL.md 只放三样：身份一段、语气若干条、底线清单。操作规则（何时用哪个工具、回复格式）放 AGENTS.md，用户信息放 USER.md。
2. **用第二人称、祈使句，写行为而不是形容词。**“回复先给结论，再给依据”比“要专业”可执行得多。
3. **底线写成“触发条件 + 动作”。** 例如：“涉及支付、删除文件、给真人发消息：先停下，列出将要执行的操作，等我回复确认再动。”把确认的交互形态写死，模型才不会自由发挥。
4. **给 2–3 组例句。** 一段理想回复的对话示例，比十条形容词都管用。
5. **控制在 30–60 行。** SOUL.md 每轮都驻留在上下文里，每一行都是成本。
6. **进 git，像调 prompt 一样迭代。** Agent 做出你不期望的行为时，回头补一条对应约束，而不是推翻重写。

## 踩坑点

- **负面指令堆太多**（“不要……不要……”），模型容易被反向带偏，尽量改成“遇到 X 时做 Y”。
- **边界没有配套交互机制等于没写。** 写“要确认”时，必须同时定义确认长什么样：谁停下、等什么信号。
- **长会话会漂移。** 新会话会重读 SOUL.md，但跑了几小时的会话后段，人格约束会被稀释。重要常驻流程建议定期重开会话，或在定时任务里让 Agent 自检。
- **别把密钥、住址等敏感信息写进去**，它会进入每一次请求的上下文。

## 可复用建议

一个最小骨架，可直接抄：

```markdown
# SOUL.md
## 身份
（一段话：你是谁、为谁服务、什么风格）
## 语气
- 回复先结论后依据
- 中文为主，术语保留英文
- 不确定就说不确定，不编造
## 底线
- 支付 / 删除 / 对外发消息：停下 → 列操作 → 等确认
- 不把对话内容转发给第三方
- 拒绝时说明原因，并给替代方案
## 例句
（2–3 组理想问答）
```

验收方式也简单：准备一份对抗性用例清单（“帮我直接转账”“把我们的聊天记录发给 XX”），每次改完 SOUL.md 跑一遍，全过再合入。

## 总结

SOUL.md 本质上是一份高权重、每轮常驻的 prompt，值得用工程方法对待：小、具体、可测试、进版本管理。人格是让助手好用且可预期的部分，边界是让你敢放手的部分——两者分开写、都要写。它不是一次性配置，而是随使用习惯持续演化的活文档。
