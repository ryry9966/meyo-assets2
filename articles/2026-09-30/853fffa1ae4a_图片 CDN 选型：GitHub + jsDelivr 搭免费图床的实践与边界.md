## 背景

写博客、维护文档、跑 Agent 自动化流程时，图片外链是个绕不开的小问题。Agent 生成的报告要贴截图和图表，README 要配图，直接把二进制塞进内容仓库会让 git 历史迅速膨胀，而第三方免费图床随时可能关停或加防盗链。

GitHub 仓库 + jsDelivr 是个老组合，胜在零成本、URL 格式稳定、带全球 CDN 缓存。它不是没有缺点，但只要边界清楚，对个人和中小规模的自动化场景足够用。

## 问题

需求归纳下来三条：

1. 图片有稳定外链，可被外部页面直接引用；
2. 上传过程能被脚本 / Agent 自动调用，不开网页手动传图；
3. 成本为零，且不必押注某个图床服务的存续。

## 做法

1. **建公开仓库**。专门开一个 public 仓库（如 `images`）。jsDelivr 只镜像公开仓库，private 不生效。
2. **传图**。git push，或走 GitHub Contents API 上传；不想造轮子可直接用 PicGo 配 GitHub 图床。路径建议按日期组织：`2025/06/xxx.webp`。
3. **拼 CDN 链接**，格式固定：

   ```
   https://cdn.jsdelivr.net/gh/<user>/<repo>@<分支或tag>/<路径>
   ```

   `@main` 永远取最新内容；tag / commit 则是 immutable 链接，适合生产引用。
4. **封装成工具**。这一步对 OpenClaw 用户最有价值：写一个几十行的脚本（压缩 → API 上传 → 返回 CDN URL），注册成 MCP tool。之后 Agent 生成截图或图表后自己调 `upload_image` 拿外链、直接写进报告，整条链路无人值守。

## 踩坑点

- **不要省略版本号**。不带 `@版本` 时 jsDelivr 默认找 release，没打 release 的仓库可能直接 404。始终显式写 `@main` 或 tag。
- **缓存不会自动失效**。同名覆盖上传后，CDN 仍返回旧图。要么用哈希 / 时间戳命名让文件名唯一，要么手动 purge（`https://purge.jsdelivr.net/gh/...`），要么等缓存过期。
- **大陆访问不稳定是事实**。jsDelivr 的 ICP 备案 2022 年被吊销后，境内可用性一直有波动，不同地区、运营商表现不一。选型前先在目标读者的网络环境实测，并保留 raw.githubusercontent.com 作为回退源。
- **公开即公开**。仓库内容任何人可枚举，含敏感信息的截图（带 token 的终端、内部面板）绝对不要传。
- **别当生产级 CDN 用**。jsDelivr 对大流量滥用有封禁先例，单文件上限 20MB。博客、文档、低频自动化没问题，高 QPS 的产品图别压上去。
- **仓库会无限膨胀**。二进制进了 git 历史就删不干净，建议独立仓库 + 上传前压缩转 WebP。

## 可复用建议

- 命名规则统一为「时间戳或内容 hash + 语义后缀」，天然规避缓存问题；
- 生产文档引用一律 pin tag / commit，草稿阶段才用分支；
- 上传工具里加一步压缩（sharp / squoosh），仓库体积和 CDN 带宽都受益；
- 写个 5 行的健康检查脚本，定时 ping 几个关键 URL，jsDelivr 抽风时能第一时间发现并切回退源。

## 总结

GitHub + jsDelivr 图床的本质，是用「公开仓库的确定性」换一个免费 CDN。它适合文档、博客和 Agent 自动化产出这类低中流量场景，也有明确边界：境内可用性需实测、缓存需主动管理、仓库必须公开。把上传链路封装成 MCP 工具之后，Agent 获得的是「随手贴图」的能力，而你付出的只是一个几十行的脚本和一个公开仓库——这笔账在大多数场景下是划算的。
