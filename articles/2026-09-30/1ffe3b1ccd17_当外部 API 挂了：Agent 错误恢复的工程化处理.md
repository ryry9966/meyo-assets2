## 背景

在 OpenClaw 的自动化流程里，Agent 很少只靠本地能力干活——查数据、发消息、调第三方服务，几乎每一步都压在某个外部 API 上。本地代码出问题你能看日志，但远端接口返回 503 或直接超时时，Agent 往往正处在任务中间态：前两步已执行、副作用已产生、第三步没落地。怎么处理这一刻，决定了你的自动化是"偶发抖动"还是"半夜起来人工救火"。

## 问题

常见的三种翻车方式：

1. **不设超时**。工具调用没有 deadline，API 挂起时整个 Agent 卡死，队列里的任务全部堆积。
2. **让模型自己重试**。异常被丢进上下文，模型在循环里反复重调，几十次重试烧光 token，上下文塞满报错后开始幻觉出"已成功"。
3. **吞掉错误**。catch 之后返回空字符串给模型，模型以为操作成功了，后续步骤在错误前提上继续跑。

## 做法

核心原则：**错误处理发生在工具层，不发生在模型的推理循环里**。模型只做决策，不做重试。

1. **先分类，再处理**。瞬时故障（超时、5xx）→ 可重试；限流（429）→ 按服务端节奏退避；业务错误（参数、权限）→ 重试无意义，直接上抛。
2. **超时 + 退避重试**。每个工具调用强制设超时；重试用指数退避加抖动（1s/2s/4s 加随机偏移），最多 3 次，且只对幂等调用生效。
3. **熔断**。同一工具连续失败 N 次后短路一段时间，期间直接走降级，不打远端。否则 API 恢复瞬间会被重试洪峰再次打挂。
4. **降级路径**。读类接口返回过期缓存，并打上"数据可能过期"标记；写类接口改为入队延后执行，或跳过并在结果里显式标注"部分完成"。
5. **状态可恢复**。多步任务执行前把状态落盘（已完成步骤、中间结果），恢复时从断点续跑而不是从头再来——对有副作用的流程尤其关键。
6. **结构化地交给模型**。重试穷尽后，给模型一段错误摘要和可选动作（跳过 / 换方案 / 求助人工），让它决策，而不是让它在黑暗里盲试。

在 OpenClaw 里，这套东西通常收口在工具封装层（MCP server 或插件的自定义 tool wrapper），伪代码大概是：

```python
@tool(retry=Retry(max=3, backoff="exp", jitter=True),
      timeout=10, breaker=CircuitBreaker(fail=5, cooldown=60),
      fallback=return_stale_cache)
def fetch_customer(id: str): ...
```

## 踩坑点

- **非幂等接口不要自动重试**。下单、发消息类 API 重试一次就是重复扣款/重复通知，必须带幂等键，或只允许人工触发。
- **429 和 5xx 别一视同仁**。前者按 Retry-After 退避，后者才适合快速重试。
- **重试不加抖动**。API 恢复瞬间所有实例一起重发，等于帮它二次挂掉。
- **原始异常直接进上下文**。堆栈和原始 JSON 会污染上下文，先在工具层摘要成一两句。
- **熔断没有半开探测**。短路后要放少量请求试探恢复情况，否则永远缓不过来。

## 可复用建议

- 四件套做成装饰器统一收口：超时、退避重试、熔断、降级，别在每个工具里手写。
- "多步 + 有副作用"的流程必须可断点续跑，状态落盘先行。
- 给模型看的错误永远是"摘要 + 选项"，不是原始异常。
- 定期演练：故意把下游 API 停掉，看 Agent 是优雅降级还是原地爆炸。

## 总结

外部 API 挂掉不是异常情况，是常态。好的 Agent 不是从不失败，而是失败后行为可预期：该重试的重试、该降级的降级、该停就停下来找人或换路子。把重试逻辑从模型的上下文挪到工具层，你会发现 token 账单和半夜告警会一起降下来。
