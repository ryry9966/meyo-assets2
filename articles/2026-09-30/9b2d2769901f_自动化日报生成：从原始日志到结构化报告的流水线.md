## 背景

团队和个人的日报大多是"人肉 ETL"：翻 git log、翻 Agent 会话记录、翻 CI 和告警，再凭记忆拼一段话。在 OpenClaw 的日常使用里，Agent 每天会产生大量会话与工具调用记录，这些其实是最真实的工作流数据。问题不在于没有数据，而在于没有一条稳定的转换管道。

## 问题

我最初试过"最省事"的方案：cron 定时把当天所有日志 cat 进一个 prompt，让 Agent 直接写日报。跑了一周暴露出四个问题：

1. 上下文爆掉，长日志被截断，截掉的部分往往是关键错误；
2. 输出格式每天不一样，下游程序没法解析；
3. 模型会"脑补"没有发生的变更，而且语气很确定；
4. 管道本身会静默失败——某天采集脚本挂了，日报照常发出，内容却是昨天的。

结论：LLM 只适合做管道的最后一层，前面的采集、清洗、聚合必须用确定性代码完成。

## 做法

整体分四层，我用一个 OpenClaw 定时任务加几个自写插件搭起来：

**1. 采集层。** 每天固定时间（如 23:40）触发，拉取时间窗口内（左闭右开，明确 UTC+8）的几类源：git 提交、CI 运行结果、Agent 会话摘要、告警事件。每个源一个 collector，统一输出 JSONL，字段包括 `source`、`ts`、`level`、`module`、`summary`、`raw_ref`。

**2. 清洗聚合层。** 纯脚本完成：按 `source+module` 去重合并（心跳类日志一天几百条只留计数）、按 level 过滤、超长字段截断、对 token 和内网路径做脱敏。产出一份聚合中间产物，通常压到几千 token 以内。

**3. 汇总层。** 把中间产物交给 Agent，用 map-reduce：先按 source 分别小结，再合并成日报。Prompt 里硬性约束——只允许引用输入中的字段，缺失就写"无数据"，禁止推断原因。输出走固定 markdown 模板：概览 / 变更清单 / 异常与处理 / 明日关注，同时附一份 JSON 版本供程序消费。

**4. 输出与校验层。** JSON 先过 schema 校验，不通过就带错误信息重试一次；渲染 markdown 后推送到群 webhook，并把原始快照和成稿按日期归档。

## 踩坑点

- **时间窗口错位**：cron 在 23:40 跑，采集却用了"当天 00:00–24:00"，漏掉了最后 20 分钟。改成"昨天 00:00 到今天 00:00"并写进配置，不要散落在代码里。
- **格式漂移**：模型偶尔把"变更清单"写成散文。schema 校验加失败重试解决了大部分 case，剩下的其实是模板字段本身有歧义——改模板比改 prompt 有效。
- **静默失败**：生成脚本挂了没人知道。后来定了一条规则：日报本身就是 healthcheck——管道异常时必须发"生成失败 + 原因"，而不是什么都不发。
- **脱敏做晚了**：第一版把 access token 原样送进了模型上下文。脱敏必须放在采集层出口，不要指望汇总层兜底。

## 可复用建议

- 把日报当成"ETL + 一次受限的 LLM 调用"：LLM 的输入越小、约束越硬，输出越稳。
- 模板即契约：先定 JSON schema 再写 prompt，模板变更走版本号。
- collector 保持单一职责，新增数据源只是加一个插件，不动主干。
- 永远归档原始快照，日报只是视图，回溯时靠原始数据。

## 总结

这条管道上线一个月，日报从"每天 20 分钟手写"变成"每天扫一眼"。真正的收益不是省时间，而是格式稳定、可回溯、出了问题能定位到管道的哪一层。对 OpenClaw 用户来说，Agent 的价值不在于替你写报告，而在于接在一个足够干净的数据管道后面，做那一步它真正擅长的事。
