## 背景

我们团队的服务分散在几台机器上，每天的运行信息散落在应用日志、调度器输出和 agent 任务记录里。之前日报靠人肉：早上开三个终端、grep 几轮、把数字抄进模板。耗时且不稳定，漏看是常事。于是花两天搭了一条定时流水线，把"原始日志 → 结构化日报"全程自动化，跑了三周效果稳定，这里记录一下思路和坑。

## 问题

拆开看，日报自动化有三个核心难点：

1. **日志异构**。不同服务的格式、时区、级别定义都不一致，直接解析必然出错。
2. **噪音太多**。原始日志里 debug 和心跳占 90% 以上，整段丢给 LLM 总结，既超 token 又容易幻觉。
3. **日报要可信**。数字必须能对上，纯靠模型自由发挥的报告没法用。

## 做法

流水线分四层，每层独立幂等：

**1. 采集切片。** cron 每天 08:30 触发，按服务把前一天（00:00–24:00，UTC+8）的日志切到工作目录，每个服务一个文件，文件名带日期，天然幂等。

**2. 预处理聚合。** 用 Python 脚本归一化：时间戳统一转 UTC、过滤 debug 级、按`服务名+错误码+关键词`分组聚合，输出中间 JSON。这一步纯规则，不涉及模型。

**3. 结构化总结。** 通过 MCP 工具把聚合 JSON 交给 agent，指令是"填模板"而不是"写报告"：章节字段固定（概况、异常 Top5、耗时分布、待跟进），模型只负责把数字组织成可读的句子，数字本身必须从 JSON 引用。

**4. 校验投递。** 发布前跑校验脚本：日报里出现的所有数字与聚合 JSON 逐一比对，不一致直接拦截。通过后生成 Markdown 发群里，JSON 落盘存档。

## 踩坑点

- **时区边界**：第一版用 UTC 切"昨天"，早高峰的错误全落在了前一天窗口外，数字对不上人工感知。后来统一按 UTC+8 切片，聚合时再转 UTC。
- **去重过头**：按错误码聚合时，把一个首次出现的新错误并进了旧分组，第二天才被发现。现在每个分组保留 `first_seen` 和 `count`，新关键词单独成组。
- **模型改动数字**：即使指令写了"只引用不编造"，模型偶尔还是会"约等于"。所以校验必须做在投递前，不能只靠提示词兜底。
- **静默失败**：流水线挂过一次没人发现，因为"没日报"不触发任何告警。加了一条规则：08:45 前日报未产出，直接告警到群。

## 可复用建议

- **中间 JSON 落盘**。日报生成失败可以重放，改模板也能基于同一份数据重新生成，方便对比效果。
- **先跑影子模式**。上线前并行跑一周，人工对照手写日报，确认统计口径一致再切换。
- **模板与数据分离**。模板是独立文件，改格式不动代码。
- **规则做统计，模型做叙述**。这条边界划清楚，流水线的可信度就有了底线。

## 总结

这条流水线没有用到多复杂的技术：cron、一个聚合脚本、一个带模板约束的 agent、一个校验器。真正让日报可用的是"确定性"设计——统计交给规则，叙述交给模型，中间用结构化数据衔接，最后用校验兜底。自动化日报的难点从来不在生成，而在让结果值得信任。
