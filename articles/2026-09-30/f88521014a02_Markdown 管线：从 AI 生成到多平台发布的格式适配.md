## 背景

在 Agent 生态里，Markdown 是事实标准：模型输出、skills 文档、MCP 工具返回、知识库条目，几乎全是它。但"生成"和"发布"是两回事：公众号编辑器只认内联样式的 HTML，知乎对表格和脚注支持残缺，掘金和 GitHub 原生吃 GFM，静态站还要 frontmatter。AI 一次生成，发布端却是碎片化的格式矩阵，多数人仍在手工逐平台粘贴调格式，慢且不可复现。

## 问题在哪

实际踩过一轮后，痛点集中在三层：

1. **语法超集不一致**：GFM 表格、脚注、任务列表、数学公式，各平台支持差异很大，转换必然有损；
2. **AI 产出自带缺陷**：嵌套代码块只用三个反引号、段内硬换行、相对路径图片、一本正经的假脚注编号；
3. **渲染端黑盒**：公众号会剥离 class、折叠空白，本地预览和线上效果对不上。

## 我的管线做法

核心原则：**Agent 只产出标准 Markdown，格式转换交给确定性代码。**

1. **归一化**：所有来源（Agent 会话、webhook、手动投稿）统一过 normalize——换行符、frontmatter 补齐、嵌套围栏升级为四反引号、相对图片路径打标。用 remark/mdast 做中间表示，不直接改字符串。
2. **Lint 卡点**：自定义规则检查占位符残留、外链域名白名单、空表格、超长段落。这一步能拦住 AI 大部分格式事故。
3. **平台适配器**：每个目标一个 adapter，输入 mdast，输出目标 payload——公众号走 HTML 样式内联；知乎把表格降级为图片或列表、脚注改为文末小节；掘金/GitHub 接近透传，只处理图片。
4. **图片资产**：按内容 hash 上传图床并重写 URL，记录映射表，这是幂等的关键。
5. **预览与发布**：渲染截图 diff，人工确认后走 API 发布，平台 URL 回写 frontmatter。

在 OpenClaw 里落地时，我把每一步包成独立的 skill / MCP tool，Agent 只负责**编排**——发哪些平台、何时发、失败重试；cron 触发定时汇总。adapter 做成插件，新增平台只需注册新插件，不动核心逻辑。

## 踩坑点

- 公众号对 `<table>` 支持很差，colspan 基本不可用，宽表提前截图最省事；
- 样式内联后 `calc()` 和 CSS 变量全部失效，构建阶段必须静态求值；
- AI 爱在段内硬换行：公众号渲染成 `<br>`，GitHub 不换，归一化阶段统一掉；
- 四反引号在部分平台仍按三反引号解析，发布前要对目标平台做一次降级；
- 图片重传不幂等，重跑管线会在图床堆一堆重复文件，务必 hash 命名。

## 可复用建议

- **单一事实源**：只维护标准 Markdown，各平台产物视为构建工件，不手工编辑；
- **快照测试**：每平台固定一两篇样例文章做 golden file，改转换逻辑后 diff 一下就知道有没有回归；
- **支持矩阵数据化**：各平台"什么语法支持、什么不支持"写成 YAML，lint 和 adapter 读它，别硬编码在代码里；
- **幂等 + dry-run**：发布类步骤必须支持干跑，失败可从断点续跑。

## 总结

多平台发布的格式适配，本质是把 Agent 的自由发挥收窄成管线里的确定性环节。Agent 擅长生成内容、判断时机，但排版这种要求 100% 可预期的事，交给测试过的代码更稳。这套管线搭好之后，从生成到三平台发布基本零手工，调整格式规则也只需要改 adapter 一处。
