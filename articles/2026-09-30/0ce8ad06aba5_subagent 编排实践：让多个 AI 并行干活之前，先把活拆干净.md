## 背景

OpenClaw 的主 agent 默认是串行干活：读上下文、调工具、再决策。任务一多问题就暴露——让它在同一次会话里"审查代码 + 跑测试 + 补文档"，三个任务的中间输出互相挤占上下文，一个卡住全都得等。

subagent 编排的思路很朴素：主 agent 只负责拆解、调度和收口，具体执行交给多个各自带独立上下文的 subagent，能并行的并行。

## 问题

实际遇到的痛点有三类：

1. **上下文污染**：任务 A 的过程输出稀释了任务 B 需要的注意力，主 agent 决策质量下降；
2. **串行延迟**：三个本可以并行的任务排队跑，总时长是相加而不是取最大值；
3. **失败放大**：一个任务的报错把整个会话状态搅乱，排查成本陡增。

## 做法

以"给一个仓库做模块化改造"为例，我们的拆法分五步：

1. **拆任务**：把主目标切成边界清晰的子任务，比如"迁移模块 A"、"迁移模块 B"、"补测试"。判断标准很实在：两个任务不读写同一批文件，就可以并行。
2. **发任务简报**：每个 subagent 拿到的不是父会话的全部上下文，而是一份压缩过的简报：目标、相关文件路径、约束（不许动哪些目录）、输出格式。
3. **隔离执行**：每个 subagent 用独立的工作目录（或 git worktree），工具按需分配——写代码的给编辑工具，跑测试的给终端，别把整套 MCP 工具塞给所有人。
4. **文件作为交接介质**：subagent 把结果写到约定路径，返回时只报"改了哪些文件 + 一段摘要"，不把完整 diff 贴回来。
5. **主 agent 收口**：汇总各路结果、处理冲突、做最终合并和验证。主 agent 保持"薄"，只做调度和裁决。

## 踩坑点

- **隐式依赖**：看似独立的任务 B 其实要读任务 A 的产出。并行前先画一下数据流，有依赖的排成流水线，别硬塞进 fan-out。
- **结果回传爆炸**：subagent 把完整输出贴回主会话，上下文照样爆。强制约定"摘要 + 文件路径"的返回格式，交接走文件。
- **并发写冲突**：两个 subagent 同时改一个文件，后写的覆盖先写的。要么拆目录，要么在简报里明确圈出"只允许动这些文件"。
- **MCP 限流**：并行的 subagent 打同一个 MCP server，容易被 rate limit 打懵。共享工具的服务要么加队列，要么错峰触发。
- **超时与悬挂**：必须给 subagent 设超时，并约定"失败时返回已完成的部分"，否则一个卡死拖垮整批。
- **别过度并行**：任务本身 30 秒能跑完，编排开销比收益还大。经验上，单任务超过几分钟且确实无依赖，才值得拆。

## 可复用建议

- **沉淀任务简报模板**：目标 / 输入路径 / 禁区 / 输出格式 / 完成标准，五项写全，subagent 跑偏率明显下降。
- **从 2~3 个 subagent 起步**：先观察失败模式再加并发，别一上来开十个。
- **每路独立留痕**：日志和返回摘要按 subagent 分开存，出问题时能定位到具体哪一路，而不是面对一团混合上下文。
- **合并留给人看一眼**：尤其是涉及写操作的汇总阶段，自动合并省下的时间可能不够还账。

## 总结

subagent 编排的核心不是"多开几个 AI"，而是**隔离 + 收口**：隔离让每个执行者上下文干净、工具最小化；收口让主 agent 只做调度、裁决和合并。并行是良好任务拆解的自然结果，而不是目标本身——先拆清楚，再谈并发。
