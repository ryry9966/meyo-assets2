## 背景

AGENTS.md 是放在工作空间根目录的说明文件，OpenClaw 每次启动会话都会读取它并注入 agent 上下文。可以理解为"写给 AI 的新人手册"：项目是什么、目录怎么摆、命令怎么跑、哪些地方不能碰。它不是什么复杂机制——一个 Markdown 文件，不需要写插件、不需要接 MCP，却是目前性价比最高的 agent 配置手段。

## 问题

没有 AGENTS.md 的工作空间，agent 每次会话都在冷启动：拿不准构建命令，猜一个 `npm test`，实际用的是 `pnpm test:unit`；分不清生成目录和源码目录，把产物提交进了版本库；每个人本机的坑它不知道，反复踩；团队约定靠口述，换个人用 agent 又得重讲一遍。这是把人类工程里的 onboarding 问题原样搬给了 agent：你不写，它就猜；它猜错，你收拾。

## 做法

建议按以下顺序搭一份可维护的 AGENTS.md：

1. **写最小骨架**：五个固定小节——概览（两三句话）、目录结构（只写 agent 会碰的）、常用命令（逐条验证过）、约定（命名/提交风格）、禁区（不能动的路径和操作）。
2. **控制长度**：目标 100 行以内。上下文是共享资源，手册塞太满，任务本身的材料反而放不下。
3. **逐条验证命令**：每条命令在干净环境跑一遍，跑不通的命令比不写更糟，agent 会在报错里绕圈。
4. **子目录下沉**：monorepo 场景在子模块放第二份 AGENTS.md，只写该模块特有规则，避免根文件膨胀。
5. **错误回写**：agent 犯了错，别只手动改结果，把这条规则写回文件——这是它最主要的增长方式。
6. **写清工具偏好**：接了多个 MCP 或插件时注明优先级，例如"搜代码优先用本地索引，不要全量 grep"。

## 踩坑点

- **写成 README**：项目介绍、架构展望对 agent 是噪音，它只关心"现在该做什么"。
- **规则漂移**：依赖升级后命令变了、文档没跟上，agent 会忠实执行错误命令并陷入重试循环。命令变更和文档变更要放同一个 PR。
- **禁区太含糊**："不要随便改配置"不可执行。要写具体：`不修改 config/*.yaml，改动需人工确认`。
- **塞敏感信息**：密钥、内网地址写进去等于随上下文外发。手册只写"去哪找"，不写值本身。
- **当记忆用**：会话日志、临时结论不要堆进来，这是手册，不是聊天记录。

## 可复用建议

- 纳入版本控制，对它的改动走和代码一样的 review 流程。
- 新写规则前先问：这个问题会再出现吗？一次性的问题不值得进手册。
- 验收方式很简单：开一个全新会话，丢一个中等复杂度的常规任务进去，观察偏离约定的地方，逐条补规则。
- 个人偏好（回答语言、解释详略）放全局配置，工作空间文件只放与项目强相关的内容。

一个可以直接抄的最小模板：

```markdown
# 概览
本工作空间是 XX 服务的 monorepo，包管理用 pnpm。

# 常用命令
- 构建：pnpm build
- 单测：pnpm test:unit（需先启动本地 mock，见 scripts/mock.md）

# 约定
- 提交信息用 conventional commits
- 生成代码一律放 src/generated，勿手动编辑

# 禁区
- 不修改 config/*.yaml
- 不执行任何 force push
```

## 总结

AGENTS.md 是 agent 工作空间里成本最低、杠杆最高的一份文件。它的价值不在写得多全，而在能否随项目演化持续维护——像 runbook 一样，谁踩坑谁回写，团队共享。认真迭代两周，agent 输出的稳定性会有肉眼可见的差别。
