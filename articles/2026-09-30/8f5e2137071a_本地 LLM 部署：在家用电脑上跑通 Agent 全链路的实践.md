## 背景

做 Agent 和 MCP 自动化久了，会反复撞到三件事：调试要花钱、敏感数据不敢喂、API 限流打断压测。云端 API 依然是能力上限，但工程实践中很需要一层"随便折腾不心疼"的基础算力。把模型搬到本地的价值不在追平旗舰模型，而在于迭代速度和数据主权：改 prompt、压测插件、重放失败 case，都不用看账单。

## 问题

家用电脑跑本地模型，聊天很容易，真正的分水岭是**工具调用**。三个现实约束：

1. **显存/内存墙**：装得下和跑得舒服是两回事，上下文一长，KV cache 就吃掉剩余显存；
2. **量化损失**：低比特量化对能力的影响在聊天里不明显，在多步 Agent 任务里会被放大；
3. **小模型 function calling 可靠性参差**：坏一个 JSON，整条自动化链路就断。

## 做法

1. **选运行时**：Ollama 或 llama.cpp 均可。OpenClaw 侧走 OpenAI 兼容接口，把 `base_url` 指到本地端点，Agent 配置几乎零改动。
2. **按显存定档**：8GB 显存（或 16GB 统一内存）从 7B/8B 的 Q4_K_M 起步；24GB 可上 14B 甚至低量化 32B。中文 + 函数调用场景优先 Qwen 系。
3. **三个必改参数**：`num_ctx` 拉到 8k 以上（system prompt 加 MCP 工具定义轻松吃掉几千 token）；`keep_alive` 设长，避免反复冷加载；`temperature` 压到 0~0.3。
4. **先写冒烟测试再接 Agent**：做一个假的 `get_weather` 工具，让模型连续调用 20 次，统计 JSON 解析成功率，低于 90% 就换模型或调参。这个测试比任何跑分榜单都贴近真实。
5. **MCP server 留在本地**：模型、编排、工具全链路离线，才能真正复现"断网也能跑"。很多时序类 bug 只有在这种环境下才暴露得出来。

## 踩坑点

- `num_ctx` 默认只有 2048，多轮对话后工具定义被截断，表现是模型"忘了工具"，实际是上下文被切了；
- 量化别低于 Q4，Q3 以下的小模型输出的工具参数 JSON 会频繁坏格式；
- 同时挂载的 MCP 工具控制在 10 个以内，用 OpenClaw 的插件分组按需启用——工具太多对本地小模型是负优化；
- macOS 走统一内存，瓶颈常在内存带宽；NVIDIA 卡注意 CUDA 与驱动版本匹配；
- 首次请求卡几秒通常是模型冷加载，不是网络故障，别急着去查代理。

## 可复用建议

- **分层路由**：格式化、摘要、简单分类交给本地模型，复杂推理留给云端。OpenClaw 里配两个 provider，按任务标签路由，成本和隐私兼顾；
- 把工具调用冒烟测试纳入插件变更流程：换模型、改 prompt，都先过测试再上线；
- 记录一份 tokens/s 和显存占用基线，后续任何性能劣化都能第一时间归因。

## 总结

本地 LLM 不是云端的替代品，而是 Agent 工程师的可控试验场。门槛从来不在"跑起来"，而在工具调用稳定性和上下文管理。建议路径：小模型打通全链路 → 冒烟测试建立基线 → 再逐步升档。链路通了，换模型只是改一行配置的事。欢迎在社区里贴出你的冒烟测试数据和踩坑记录，这类一手信息比测评文有用得多。
