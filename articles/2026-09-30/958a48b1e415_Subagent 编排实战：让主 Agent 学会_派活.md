## 背景

用 Agent 做自动化久了，总会撞到同一类场景：巡检 6 个 MCP 服务的状态、批量读 10 篇文档各出一句话摘要、对 4 个插件仓库分别跑依赖检查。这类任务彼此独立，但默认的单 Agent 循环是串行的——工具调用一个接一个，墙钟时间是所有任务之和，中间结果还不断挤占主上下文，跑到后面质量明显下降。

Subagent 编排就是针对这个问题的：主 Agent 不亲自干活，而是把任务拆给多个并行的 subagent，每个 subagent 拥有独立上下文，干完只回传一份紧凑结果。

## 问题

拆解前先明确串行模式的三个具体痛点：

1. **慢**：任务耗时线性叠加，8 个 30 秒的检查就是 4 分钟起步。
2. **上下文污染**：中间的工具输出全堆在主会话里，真正需要决策的信息反而被稀释。
3. **职责混杂**：一个巨型 prompt 既当调度又当执行，某一步失败后很难定位和恢复。

## 做法

**第一步：判断任务独立性。** 并行的前提是任务之间没有共享可写状态、没有顺序依赖。批量读取、检查、摘要类任务是好候选；"构建→测试→部署"这种链式任务不要硬拆。

**第二步：定义输出契约。** 每个 subagent 的 prompt 要足够窄：明确目标、允许使用的工具、以及严格的返回格式（比如固定字段的 JSON，限制条目数）。主 Agent 只看契约结果就能汇总，不应该需要读原始日志。

**第三步：控制并发与超时。** 并发从 3 起步，最多 5，避免触发限流。每个 subagent 必须带超时（比如 120 秒），失败要返回显式的失败状态，而不是静默超时。

**第四步：汇总落盘。** 主 Agent 只保留结构化摘要，原始输出写到文件里备查，主上下文始终保持清爽。

在 OpenClaw 里落地很直接：把 subagent 做成独立 session 的 agent，通过工具调用触发，在主 agent 的工具描述里把契约写清楚即可。

## 踩坑点

- **共享状态竞争**：两个 subagent 同时写同一个文件必出事。subagent 尽量只读，写操作统一收回主 Agent。
- **递归派生**：subagent 自己再开 subagent，很快失控。把派生深度限制为 1。
- **结果超长**：不限返回长度，上下文和账单一起爆炸。契约里写死上限。
- **静默失败**：subagent 超时后主 Agent 顺着"编"一个结果补上——这是最危险的坑，必须要求返回带 status 字段。
- **限流**：并发一上去就撞 API 限额，做好并发闸门和指数退避重试。

## 可复用建议

- **先串行后并行**：先串行跑通，确认各步真的独立，再并行化。
- **契约先行**：输出 schema 是任务定义的一部分，不是事后补丁。
- **只读优先**：subagent 越接近"纯函数"越安全，可重试性也越好。
- **可观测**：记录每个 subagent 的工具调用与耗时，没法排查的 subagent 是负资产。

## 总结

并行编排的价值不在"Agent 多"，而在任务拆得对：独立、只读、带严格输出契约的任务，并行才有真实收益；主上下文因此保持干净，排查也更容易。满足不了这三个条件，老老实实串行反而更稳。建议从两个 subagent 的小规模试点开始，跑顺了再扩。
