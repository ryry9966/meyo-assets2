## 一、背景

我平时把学习笔记放在本地一个 Git 仓库里，格式统一是 Markdown。问题是：写完就沉底，很少整理成帖子发到社区。手动搬运要改标题、写摘要、贴代码块、调格式，一篇十分钟，坚持不下来。

于是花了一个周末，用 OpenClaw Agent 搭了一个发帖机器人。定位先说清楚：**不是全自动水帖**，而是"机器生成草稿 → 规则校验 → 定时发布"的半自动流水线。跑了三周，稳定发出 40+ 帖，这里把架构和踩过的坑记录下来。

## 二、问题定义

拆开看其实是三个问题：

1. **内容从哪来**：选题不能靠模型瞎编，必须有真实素材；
2. **质量怎么控**：LLM 会润色、会幻觉，发出去的是社区信誉；
3. **怎么安全发出去**：API 鉴权、频控、失败重试、不能重复发。

## 三、架构与实现

整体分四层：

```
内容源 → Agent 层 → 审核层 → 发布层
```

**1. 内容源**：仓库笔记 + RSS 订阅，通过 MCP 的 filesystem 和 fetch 工具读取。这一层只负责"给原料"，不做加工。

**2. Agent 层**：OpenClaw 定时任务每天触发一次，读取未处理的笔记，生成"标题 + 三句话摘要 + 正文草稿"。Prompt 里硬性要求：只能基于原文，结论必须能在原文找到对应段落。

**3. 审核层**：先走 dry-run——草稿落盘成本地 Markdown，同时跑一遍规则校验：正文长度下限、代码块是否闭合、是否命中已发内容（相似度粗筛）。

**4. 发布层**：插件调用社区 API。关键是两个设计：

- 用正文 hash 做幂等键，发布前先查重；
- 重试上限 3 次，指数退避，另有每日配额兜底。

每次运行的输入输出写成结构化日志，发布状态回写到一个 JSON 文件，作为下次运行的去重依据。

## 四、踩坑实录

**坑 1：重复发帖。** 头两天定时任务和手动触发撞车，同一篇连发两次。解法：内容 hash 幂等键 + 文件锁，两道闸。

**坑 2：幻觉标题。** 模型会给笔记"加戏"，总结出原文没有的结论，被社区朋友指出来很尴尬。解法：prompt 强制"禁止输出原文之外的结论"，摘要要求标注来源段落，校验时抽查。

**坑 3：转义问题。** 代码块里的 `<T>` 被 API 当成 HTML 标签吞掉，帖子排版全乱。解法：发布前按社区渲染器的白名单做一遍转义，别信默认行为。

**坑 4：重试风暴。** 一次社区接口 5xx，机器人按固定间隔疯狂重试，触发频控，token 被临时限制。解法：指数退避 + 每日配额。宁可当天少发，不能把账号搭进去。

**坑 5：时区。** cron 按 UTC 跑，帖子全在凌晨发出。解法：调度和日志里显式声明时区，别依赖默认值。

**坑 6：凭证泄露。** 第一版把 token 写进配置文件，差点提交。解法：全部走环境变量，`.gitignore` 兜底，然后立刻轮换了 key。

## 五、可复用建议

1. **先 dry-run 一周**，人工看过至少 20 篇输出，再放开自动发布；
2. **生成与发布解耦**，中间必须落盘，出问题可以回放；
3. **幂等键、锁、配额**三件套缺一不可，这是所有"自动对外动作"的底线；
4. **日志结构化**，出事靠 grep 复盘，别靠回忆；
5. **保留人工开关**，一键暂停永远要有。

## 六、总结

机器人本身不难，OpenClaw + MCP 让工具接入变得很轻，一个周末能跑通。真正花时间的是防御性设计：把"发帖"当成一个有状态、可能失败、会被重试的分布式操作来对待。自动化省下的时间，一部分要还给出错排查——但只要护栏够稳，这笔账是划算的。
