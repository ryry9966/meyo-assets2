## 背景

社区的内容运营长期靠人肉：每周整理精华帖、搬运 GitHub Release、发周报。问题不在于写，而在于**准时、稳定、格式统一**——这三件事恰恰是人最不擅长长期坚持的。于是决定把这条链路交给机器人：定时抓取信息源 → Agent 生成草稿 → 审核后发帖。本文记录这套系统的架构取舍和两周内踩过的坑。

## 问题

最初设想的"一个 prompt + 定时任务"很快暴露问题：

- **重复发帖**：任务重试时没有幂等，同一帖连发三遍
- **幻觉链接**：模型编造不存在的 PR 号和 issue 链接
- **语气漂移**：同一模板不同次生成，风格差异肉眼可见
- **权限失控**：bot token 出现在了 prompt 上下文里

## 架构与做法

核心原则：把发帖机器人当成一条**数据流水线**，而不是一个聊天对象。架构分五层：

1. **采集层**：cron 定时拉取 RSS / GitHub Release / 社区精华帖，产出结构化原料
2. **生成层**：Agent + prompt 模板，只负责把原料转成草稿
3. **校验层**：规则检查（链接可达、长度、敏感词）+ 双重查重
4. **发布层**：把社区 API 封装成 MCP tool，Agent 通过工具调用发帖
5. **观测层**：每次执行记录 run_id、原料、草稿、结果，落 SQLite

几个关键决策：

- **生成与发布解耦**：草稿先落库，审核通过后由独立进程发布，模型永远拿不到直接的发布权限
- **查重用内容 hash + 标题相似度双保险**，靠单一手段都会漏
- **dry-run 模式**：全链路跑通但只写日志不发帖，上线前跑了一周

## 踩坑实录

**1. 重试导致重复发帖。** 网络超时后任务重试，帖子发了三遍。修复：发布前先写"待发布"记录并携带幂等键，社区侧做 upsert。

**2. 模型幻觉链接。** 让模型"补充相关阅读"，它开始编造 PR 号。修复：**禁止模型生成链接**，链接只允许从采集层透传。

**3. 时区问题。** cron 按 UTC 跑，帖子总在本地凌晨发出。修复：调度统一存 UTC，配置里显式声明时区，展示层再转换。

**4. MCP tool 粒度太粗。** 最初只封装了一个"发帖"大工具，模型偶尔传错参数。拆成 `create_draft` / `publish_draft` / `upload_image` 三个小工具、收紧参数 schema 后稳定很多。

**5. token 成本失控。** 每次全量带历史帖做风格参考，单次跑掉 2 万 token。改成检索 3 篇近期高赞帖做 few-shot，成本降了一个数量级。

**6. 日志泄密。** 一次 debug 把完整请求 dump 进日志，token 一起进去了。修复：统一脱敏中间件，秘钥只走环境变量。

## 可复用建议

- **先人工审核，再逐步放开自动发布**，放开阈值用误报率数据说话，不拍脑袋
- **模型只做转换，不做事实**：链接、数字、ID 等事实性内容全部来自上游结构化数据
- 工具拆小、schema 收紧，宁可模型多调几次
- 每一步可单独重放，run_id 贯穿全链路，排障靠回放不靠猜
- 失败要有兜底：发不出去就进死信队列并通知人，而不是静默重试到天荒地老

## 总结

两周下来，机器人稳定覆盖了周报和 Release 速递两类内容，单篇人工介入从 30 分钟降到 5 分钟审核。最大的收获不是省时间，而是把"内容生产"变成了**可观测、可回滚的工程流程**。复盘代码量：AI 相关只占两成，剩下八成全是查重、幂等、重试这些朴素但必要的活。想抄作业的同学，建议从 dry-run 模式和幂等键做起——这两个坑不填，其他都白搭。
