# 背景

OpenClaw-CN 社区每周都有值得沉淀的内容：新插件、MCP 实践、各种踩坑讨论。我过去手动整理《本周精选》，费时且容易漏。于是用 OpenClaw 搭了一个发帖机器人，目标是：自动汇总素材、按社区文风生成草稿、经确认后定时发帖。核心约束只有一条——宁可少发，不能发水帖。

# 整体架构

四个分层加一个台账：

1. **触发层**：OpenClaw 的 cron 任务，每周日晚上定时触发；
2. **采集层**：社区 RSS 拿新增话题，GitHub API 拿最近合并的 PR / Release，统一输出素材 JSON；
3. **生成层**：一个专职 agent，读素材 + 文风模板（内嵌 3 篇历史精选做 few-shot），产出 markdown 草稿；
4. **发布层**：自定义 MCP 工具 `create_topic` 封装论坛 API，只暴露这一个能力；
5. **台账**：SQLite 记录素材指纹（来源 URL + 内容哈希）、发布状态、草稿版本，去重和故障恢复全靠它。

生成与发布是两个独立步骤，中间留人工确认口。

# 踩坑实录

1. **重试导致重复发帖**。首次上线遇到网络超时重试，同一天发了两篇一样的。修复：发布前先写 intent 记录（含内容指纹），成功后再置为 done；启动时先扫台账，pending 状态进人工复核而非直接重发。

2. **cron 时区差 8 小时**。容器默认 UTC，21:00 变成了次日早上。所有调度显式声明 `Asia/Shanghai`，日志同时打本地时间。

3. **文风漂移**。默认输出很“营销号”，满屏惊叹号。解法是负向约束 + few-shot：prompt 里明确“不用感叹号、不堆形容词、不写‘重磅/颠覆’”，再塞几篇社区高赞帖作参照，合格率明显回升。

4. **Markdown 方言不兼容**。嵌套列表和代码块在论坛端渲染错乱，@提及还会误触发通知。现在生成时限定：最多两级列表、代码块只用三反引号、禁止 @ 任何人。

5. **API Key 暴露面过大**。最初把论坛 Key 放在 agent 工作区文件里，后来意识到任何能读工作区的注入都可能带走它。改为环境变量注入 MCP 进程，agent 全程接触不到明文。

6. **素材本身是攻击面**。抓回来的网页正文里如果混入“忽略之前指令”之类的文本，agent 可能被带偏。素材先做纯文本化 + 截断再进 prompt，且发布工具强制要求人工审批才可调用。

7. **限流被警告过一次**。加两道闸：最小发帖间隔 24 小时、每日上限 1 篇，请求间加随机抖动。机器人账号在签名里注明身份，既是礼貌也是自保。

# 可复用建议

- **先跑 dry-run**：把“发帖”换成“写本地文件”跑两周，人工验收草稿质量后再接真实 API；
- **工具面最小化**：只给 agent 一个窄接口，不给通用 HTTP 能力，出问题的概率会指数级下降；
- **生成与发布解耦**，中间必留人工闸门——自动化负责省时间，不替你负内容责任；
- **prompt、模型输出、HTTP 响应全部落盘**，九成线上问题靠翻日志定位，不靠猜。

# 总结

机器人稳定运行一个多月，每周省下约两小时，未漏发过一次，也没发过不合格的帖子。最大的体会是：发帖机器人的难点不在“让 AI 写出帖子”，而在幂等、限流、权限这些不起眼的工程细节。先把它当成一个普通的定时发布系统来设计，LLM 只是其中一个可替换的生成环节——带着这个心态去做，返工会少很多。
