## 背景

社区每周都有几类重复劳动：新教程汇总、插件更新整理、常见问题归档。人工做太耗时间，质量还不稳定。我用自己部署的 OpenClaw agent，加上两个自写的 MCP 工具，搭了一个发帖机器人，跑了一个多月，现在稳定产出周报和文档转帖。这篇记录架构取舍和踩过的坑，给有同样需求的人参考。

## 问题：第一版为什么不行

第一版的思路很朴素：一个大 prompt 全干——抓取、总结、排版、发布一条龙。跑了三天就暴露问题：输出格式不稳定、同一内容重复发帖、发错板块、甚至出现编造的来源链接。

根因是把“生成内容”和“执行动作”混在一个不可控的调用里，中间没有校验层，本地也没有状态。改版的核心就一句话：生成和动作分离，动作之前必须过机器可判定的检查。

## 现在的做法

架构一句话：OpenClaw agent 做编排，两个 MCP 工具做采集和发布，本地 SQLite 存状态，cron 定时调度。

- **采集与发布分离**：`fetch_sources` 只读；`create_post` 只能往指定板块发帖，用独立 bot 账号，权限收窄到单一动作。
- **结构化输出**：生成阶段强制 JSON Schema（标题、板块、标签、正文、来源链接），校验失败带着报错重试一次，再失败丢弃并记录。
- **发布前三道闸**：内容指纹去重（本地状态库比对）、来源链接白名单校验（链接必须出现在本轮采集结果里）、每日发帖上限。
- **灰度上线**：先 dry-run 落到测试板块，人工看两周才切正式板块；前期每帖人工确认，稳定后改为抽样复查。

## 踩坑实录

1. **权限过大**。最初图省事用了管理员 token，一次 prompt 注入测试让 agent 尝试修改社区配置，惊出一身冷汗。现在发布凭证只保留“指定板块发帖”一个权限。
2. **重复发帖**。接口超时重试导致同一内容发了两次——发布动作本身不幂等。改成发布前先生成内容指纹，查本地状态，确认成功才落库，重试只针对“未确认”记录。
3. **格式漂移**。模型偶尔在 JSON 外面再包一层 markdown 代码块，解析直接挂。处理：剥离代码块 + Schema 校验 + 带报错重试。
4. **幻觉链接**。模型会“补全”不存在的 URL。规则改成：正文引用的链接只能从本轮采集结果里选，校验不过整篇打回。
5. **触发限流**。调试期连续发帖触发了论坛反垃圾机制。现在固定发布间隔、每天上限 3 帖，重试用指数退避。
6. **文风太"AI"**。加了两条硬约束：每帖必须引用至少一条真实来源；禁用模板化开场句。自动打标签仍不理想，保留了人工改标签的习惯。

## 可复用建议

- 生成与动作分离，动作前必须有机器可判定的校验层。
- 对外动作一律按幂等设计：先查状态、再执行、结果落库。
- 凭证最小化：读、写分开，写权限只给到单一板块。
- 自动化发布先过测试板块，人审环节不能省。
- 日志记全：每次运行的输入摘要、校验结果、发布结果，排障基本全靠它。

## 总结

这个项目里最难的，不是让模型写出一篇像样的帖子，而是权限、幂等、校验、可观测这些不性感的工程问题。Agent 负责内容，工程负责兜底，边界划清楚，机器人才敢长期无人值守地跑。下一步计划把人工确认环节换成规则打分、低置信度才进人审，跑通后再来分享。
