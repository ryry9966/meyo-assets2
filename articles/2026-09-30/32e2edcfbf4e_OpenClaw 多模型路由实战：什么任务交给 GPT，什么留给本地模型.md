## 背景

OpenClaw 的典型玩法是主 agent 常驻做编排：消息进来先判断意图，再决定自己处理、派子 agent，还是调 MCP 工具。很多人默认只挂一个旗舰云端模型，跑一周看 token 账单就发现问题：大量消耗花在"把这段话总结一下""这条消息要不要提醒用户"这类低难度任务上。另一部分人反过来全上本地模型，结果多步工具调用频繁断链。多模型路由要解决的就是这个中间地带。

## 问题

路由不是"贵的模型一定好"，实际要同时平衡三件事：

1. **成本**：高频低价值任务往往吃掉 70% 以上的 token；
2. **延迟**：简单回复走云端，网络往返加排队，可能比本地推理还慢；
3. **隐私与可用性**：聊天记录、日程这类私人数据未必都想出网；断网时 agent 最好还能响应。

## 做法

我们采用的分层原则：**按"失败的代价"分配模型，而不是只按调用频率。**

- **第一层：意图分类与消息预处理 → 本地小模型。** 7B 级别（Qwen、Llama 蒸馏版）足够做分类、摘要、关键词提取和"是否打扰用户"的判断。跑在 Ollama / llama.cpp 上，量化到 Q4，资源占用可控。
- **第二层：主 agent 编排 → 云端旗舰。** 规划、跨工具决策、代码生成对工具调用格式稳定性要求高，交给 GPT/Claude 级别，失败重试成本最低。
- **第三层：长文处理、批量任务 → 云端中档。** 总结长文档时中档模型和旗舰差距很小，价格差数倍。

配置上利用 OpenClaw 按 agent 覆盖模型的能力，再配一条 fallback 链：云端超时或限流时降级到本地保底，保证 agent 永远有响应。

落地步骤：

1. 先跑一周全云端配置，从日志统计任务类型分布，别拍脑袋定比例；
2. 把任务归成三类桶：分类/摘要、编排/生成、批量处理；
3. 在配置里为每类任务指定模型和 fallback 顺序；
4. 给本地模型加 keep-alive，避免每次请求冷启动；
5. 观察两周 token 消耗、首 token 延迟、工具调用成功率，再调边界。

## 踩坑点

- **本地小模型的 function call 格式经常不规范**，工具调用成功率明显低于旗舰模型。这是最多人栽的坑：别用本地模型做编排。
- **上下文窗口**：本地 8K 上下文塞一段长对话就爆，做摘要前先做截断或分块。
- **量化有代价**：Q4 以下 JSON 输出开始不稳定，本地模型需要吐结构化数据时至少 Q6 或换更大参数。
- **fallback 风暴**：云端限流后重试全部压到本地，把机器打满。降级路径里务必加退避和熔断。
- **别只看总延迟**：首 token 延迟决定"agent 活着"的手感，本地模型在这一点上有天然优势，值得单独统计。

## 可复用建议

- 路由表做成配置而不是写死在代码里，换模型只改配置不动逻辑；
- 维护一个 20~30 条的固定测试集，每次调整路由跑一遍，防止"优化了成本、劣化了质量"；
- 敏感数据（聊天记录、凭证相关）默认路由本地，除非用户明确允许出网；
- 监控按"任务类型 × 模型"两个维度拆分，否则根本看不出路由是否真的生效。

## 总结

多模型路由的本质是把 agent 的任务按风险和难度切开：低风险、高频的交给本地省成本、保隐私；高风险、低频的交给云端保质量。先测量、再分层、最后用数据收边界——这比任何"最优模型推荐清单"都可靠。
