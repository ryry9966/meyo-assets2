# 背景

OpenClaw 的默认用法是“一个主模型走天下”：Agent 主循环、定时任务、MCP 工具调用全压在同一个云端模型上。跑起来没问题，但账单和隐私边界很快会逼你重新分配流量。好在 OpenClaw 支持把任意 OpenAI 兼容端点（Ollama、LM Studio、vLLM）注册为 provider，再通过 primary / fallbacks / agent 级覆盖来做路由，这给了分层的空间。

# 问题

实际使用中会遇到三类诉求：

1. **成本**：心跳检查、摘要、日志整理这类高频低价值任务，用旗舰模型纯属浪费；
2. **隐私**：本地文件批处理、家庭数据整理，不想让内容出网；
3. **可用性**：云端限流或断网时，整条自动化链路直接瘫掉。

反方向的问题同样存在：复杂推理、多工具串联、长上下文对话，本地 7B/14B 模型明显撑不住，尤其是 function calling 的稳定性。

# 做法

我的分工原则是：**按任务类别路由，不按模型品牌路由**。

**第一步，给任务分类。** 把一周里 OpenClaw 实际干的活列出来，按“复杂度 × 敏感度 × 频率”分桶：Agent 主循环和 MCP 编排归云端强模型；定时摘要、分类打标、格式转换归本地小模型；涉私数据一律本地。

**第二步，配置路由。** `agents.defaults.model.primary` 指向云端模型承担默认流量；需要本地处理的场景单独起一个 agent（比如 digest、file-janitor），在 agent 配置里覆盖 model 指向本地端点。云端再配一条 fallbacks 链兜底断网场景。

**第三步，验证工具调用。** 本地模型上线前，先手动跑一遍它要用的 MCP 工具，确认能稳定产出合法的工具调用 JSON，再接入自动化。

**第四步，加观测。** 日志里记录实际命中的 model id，每周扫一遍 fallback 触发率、本地任务超时率、token 消耗分布。路由策略靠数据调，不靠感觉。

# 踩坑点

- **本地模型的 function calling 是最大的坑**。同一个工具，云端一次过，本地小模型经常漏参数甚至编造参数，Agent 循环直接卡死。结论：工具调用重的路径不要路由到本地。
- **上下文长度**。本地部署常见 8k~32k，长会话或 MCP 返回大段 schema 时会被静默截断，表现为“模型变笨”，极难排查。
- **量化损失**。Q4 量化在闲聊上没差别，在代码和结构化输出上差异明显，评测必须用你自己的真实任务跑。
- **fallback 不是质量降级开关**。它只在报错时触发，不会因为“本地效果差”自动回退云端，质量回归只能靠评测和日志发现。
- **单卡并发**。本地模型同时喂多个定时任务会排队，低优先级任务记得错峰或限流。

# 可复用建议

- 路由粒度做到 agent 级别，不要全局切换，保持一条稳定的云端主线；
- 每个任务类别维护一个 10~20 条的私有评测集，换模型、改量化、升版本前先跑一遍；
- fallback 链保持在两跳以内：云端主模型 → 云端备选 → 本地兜底，链条太长时故障行为难以预测；
- 涉私任务宁可牺牲一点效果也走本地，这条边界一旦松动就收不回来。

# 总结

多模型路由的本质是成本、隐私、能力三者的分配。OpenClaw 提供了 provider 注册和 agent 级覆盖的机制，剩下的工作是把任务分类做扎实、把工具调用路径留给云端、把高频低价值任务交给本地，然后用日志和评测持续校准。建议先小范围试运行两周，看数据再决定本地模型的承担面，别一上来就全量切换。
