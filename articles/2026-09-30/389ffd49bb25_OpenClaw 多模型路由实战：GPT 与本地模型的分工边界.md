## 背景

OpenClaw 的典型自动化链路里，模型调用高度分层：消息去重、记忆打标、定时摘要这类高频小任务占了大头，而多步工具调用、代码生成、跨插件编排才是真正吃推理能力的部分。早期我们全链路走 GPT，账单和延迟都难看；全换本地模型后，agent 又经常在工具调用环节掉链子。多模型路由要解决的就是这个分工问题。

## 问题

单模型策略的两个极端都不成立：

- **全走云模型**：80% 的流量是低价值任务，成本结构不合理，高峰期还受速率配额限制。
- **全走本地模型**：小参数模型在 function calling 上格式漂移严重，重试率高，复杂任务成功率明显下降，排障成本反而更高。

## 做法

核心思路是**按任务分层，把路由规则显式写进 agent 配置**，而不是散落在业务代码里：

1. **分层**
   - Tier 0（分类、打标、去重、记忆抽取）：本地 7B-8B 级模型
   - Tier 1（摘要、常规文案、单工具调用）：本地中档模型或云上低价档
   - Tier 2（多步规划、代码生成、跨工具编排）：GPT 旗舰档
2. **配置主备链路**：每层配 primary + fallback，Tier 0/1 校验失败时自动升级到云模型。
3. **埋点观测**：每次调用记录 route 标签、token 数、延迟、重试次数，按周复盘分层阈值。

配置大致长这样：

```yaml
routing:
  tier0:
    primary: local/qwen2.5-7b
    fallback: cloud/gpt-4o-mini
  tier2:
    primary: cloud/gpt-4o
```

## 踩坑点

- **结构化输出不稳**：本地模型 function calling 的 JSON 格式漂移常见，必须加 schema 校验 + 有限次重试，别裸奔上线。
- **上下文窗口**：本地模型普遍 8k-32k，长会话摘要链路会被静默截断，先用自己的真实对话压测。
- **fallback 风暴**：本地一挂全部升级到云，省的钱全吐回去。加熔断：如 5 分钟内失败率超 30% 就告警转人工。
- **延迟不止 tokens/s**：本地模型冷启动和 KV cache 重建经常是延迟大头，常驻进程通常比按需拉起划算。
- **embedding 别随意换**：换了必须重建向量库，否则检索质量会悄悄劣化，且很难第一时间发现。

## 可复用建议

- **先按 80/20 切**：把明确低价值的 80% 流量迁到本地，剩下 20% 留在云端，不追求一步到位。
- **所有调用打 route 标签**：没有标签的路由等于黑盒，后期没法归因。
- **保留逃生通道**：任何校验失败自动升级云模型，守住成功率底线。
- **模型版本当依赖管理**：换版本等于一次迁移，要有回归用例再切换。

## 总结

多模型路由不是炫技，是成本、延迟、成功率之间的三角权衡。OpenClaw 的价值在于把这些策略变成显式配置和可观测数据，而不是隐式逻辑。建议从任务分层和日志埋点入手，小步迁移，用自己链路上的数据说话——别人的 benchmark 只能当参考，不能当地图。
