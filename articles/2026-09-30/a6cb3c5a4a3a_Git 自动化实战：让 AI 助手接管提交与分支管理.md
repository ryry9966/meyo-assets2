## 背景

日常开发里，Git 操作占了不成比例的时间：写 commit message、按规范开分支、清理合并后的残留分支、整理发版日志。这些事不难，但琐碎且容易走样。自从给 Agent 接上 shell / MCP 工具后，我发现这部分工作是可以部分交出去的——前提是把边界画清楚，而不是一句"帮我管 Git"就完事。

## 问题

直接放手让 AI 管 Git，会撞上三类问题：

1. **质量不稳定**：自由发挥的 commit message 时而详细时而敷衍，分支命名五花八门，两周后自己都看不懂。
2. **安全风险**：`reset --hard`、`push --force`、`clean -fd` 这类破坏性命令，Agent 在"好心帮你清理"时可能直接执行。
3. **上下文不足**：Agent 看不到完整 diff 就开始猜改动内容，写出的提交说明是文采很好的幻觉。

## 做法

我在自己的工作流里分四步落地：

**第一步：只读先行。** 只开放 `status` / `diff` / `log` / `branch -v` 这类只读命令的 allowlist，先跑一周，观察它的判断质量再谈写操作。

**第二步：提交走"提议—确认"流程。** 固定循环：`git status` → `git diff`（大 diff 先 `--stat` 再分文件看）→ 生成符合 Conventional Commits 的 message → 输出给我确认 → 确认后才执行 `git add`（指定文件，禁用 `-A`）和 `git commit`。

**第三步：分支规则编码进 skill。** 命名格式（如 `feat/issue-123-xxx`）、从哪个基线切、合并后何时删，全部写成可复用的 skill 模板，而不是每次口头交代一遍。

**第四步：危险命令硬拒绝。** denylist 直接拦 `push --force`、`reset --hard`、`clean`、`checkout -- .`；push 默认需要显式确认，且只允许 `--force-with-lease`。

## 踩坑点

- **别让 Agent 凭记忆写提交信息**：必须把真实 diff 喂给它，否则就是包装精美的编造。
- **非交互 shell 跑不了 `rebase -i`**：需要交互的场景要么拆成单步操作，要么人工接手。
- **切分支前强制查状态**：Agent 有时忽略工作区有未提交改动就 checkout，把 `status` 写成流程前置步骤能省很多事故。
- **大仓库 diff 会撑爆上下文**：先 stat 再按文件取，比一把梭强得多。
- **密钥泄露**：Agent 不会主动识别 `.env` 这类文件，我在 commit 前加了一步密钥扫描，命中即中止。

## 可复用建议

- 把"读 diff → 提议 message → 确认 → 提交"固化成一个 skill，团队所有人复用同一套标准，而不是各调各的 prompt。
- allowlist / denylist 跟仓库一起版本化，进 code review，规则变更可追溯。
- Agent 执行的每条命令落审计日志，出问题能回放。
- 本地操作先放开，网络操作（push、PR 创建）永远留人工闸门。

## 总结

AI 管 Git 的价值不在于"全自动"，而在于把格式、命名、流程这些确定性的事情标准化，把人从琐事里解放出来。渐进放权、硬性护栏、全程可审计——这三条做到位，这套工作流就能长期稳定跑下去。
