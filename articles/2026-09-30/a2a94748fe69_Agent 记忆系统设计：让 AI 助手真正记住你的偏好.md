## 背景

LLM 本身无状态，每次会话都是白纸。OpenClaw 这类常驻助手的价值恰恰在"越用越懂你"：时区、称呼、代码注释习惯、回复语言，这些偏好散落在对话里，没有记忆机制就得每次重说。上下文窗口再大，把历史全塞进去既贵又会稀释注意力——记忆系统的本质，是把"发生过的事"压缩成"可检索的事实"。

## 问题

三种常见做法都不理想：

1. **全量历史入上下文**：成本线性涨，关键偏好被闲聊淹没；
2. **一大段"记忆总结"**：不可更新、互相矛盾、越滚越长；
3. **纯 embedding 召回**：中文短句相似度不稳，容易召回一堆无关记忆。

核心矛盾：写太多污染记忆，写太少记不住；读太多干扰模型，读太少等于没做。

## 做法与步骤

我在自己的 OpenClaw 实例里用的是**三层结构 + 独立读写循环**：

**分层存储**

- 稳定层：结构化偏好档案（语言、时区、沟通风格、常用工具），一条事实一条记录，字段含内容、分类、来源、`created_at`、`updated_at`、置信度。会话开始时全量注入，体积可控；
- 情节层：每次会话结束生成摘要 + 关键实体，按相似度 + 时间衰减召回；
- 工作层：会话内 scratchpad，不落盘。

**写路径**：在会话结束的插件钩子里跑一次抽取 prompt，输出 JSON 候选：

```json
{
  "category": "style",
  "content": "代码注释用中文，回复避免 emoji",
  "source": "session-0612",
  "confidence": 0.9
}
```

先过规则过滤（只收稳定、可复用的事实），再与现有记录做相似度去重，冲突时新覆盖旧并保留来源。也可以挂一个 MCP memory server，`memory_search` / `memory_write` / `memory_forget` 三个工具就够起步（钩子命名以你所用版本的插件文档为准）。

**读路径**：稳定层固定注入；情节层 hybrid 检索（embedding + 标签兜底），top-3~5、带时间衰减分数，渲染成明确标注的"参考资料"块，避免模型当成指令执行。

**维护**：每周跑一次 consolidation：合并重复、归档矛盾、对长期未命中且非核心的记忆降权。

## 踩坑点

- **抽取过宽**：连"好的"都存下来。务必在 prompt 里限定只抽稳定事实，并加分类白名单；
- **冲突不处理**：模型会"精神分裂"。冲突解决策略要显式写进代码，别指望模型自己判断；
- **注入过多**：top-k 超过 10 条，回答明显变啰嗦、注意力涣散，3~5 条是甜点区；
- **中英混合查询**的 embedding 召回偏差大，标签/关键词兜底很必要；
- **异步写入静默失败**：留一个 debug 命令 dump 当前记忆，排查全靠它；
- **隐私**：敏感信息打 tag，给用户可见可删的记忆列表，这是信任底线。

## 可复用建议

- 先做稳定层 + 显式指令（"记住/忘掉 XX"），够用后再上语义召回，不要一步到位；
- 记录保持原子化：一条一个事实，别写段落；
- 注入块显式标注来源和时间，模型引用会更准；
- 记录召回命中日志，用数据决定要不要加层，而不是凭感觉。

## 总结

记忆系统不是玄学，就是一个**写—读—维护的闭环工程**。先用最土的结构化档案解决 80% 的偏好问题，再按需叠加语义召回。检验标准很简单：助手是否在你没有重复的前提下，做对了一件上周提过的小事。
