## 背景

在 OpenClaw-CN 写实践帖、维护插件文档时，截图和架构图是刚需。可选方案其实不多：第三方免费图床随时可能跑路，对象存储要绑域名备案，本地路径贴出去别人也看不到。团队内部沉淀文档时，同样需要一个"贴图即得外链"的方案。

## 问题

我的需求很朴素：

- 免费、长期稳定，链接不突然失效
- 国内访问速度可接受
- 支持脚本化上传，最好能让 Agent 自动完成"截图 → 上传 → 贴链接"
- 图片有版本管理，改图不污染旧文档

试了几家免费图床后，最后落在 GitHub 仓库 + jsDelivr CDN 这个组合上。

## 做法

1. **建仓库**：新建公开仓库如 `assets`，按日期或主题分目录，比如 `2025/01/`。
2. **上传并打 tag**：jsDelivr 能直接代理 GitHub 仓库文件，推荐用 release 固定版本，URL 形如：

```text
https://cdn.jsdelivr.net/gh/<user>/assets@1.0.0/2025/01/cover.png
```

开发期可以先 `@main`，定稿后打 tag 替换，链接即不可变。

3. **脚本化**：核心就一步——调用 GitHub Contents API 写入文件，十几行 Python 够用。文件名建议用内容 hash，防重名覆盖，返回时直接拼好 CDN 链接。
4. **接入 Agent**：我把它封成了 MCP 工具 `upload_image`，入参是本地路径或剪贴板，出参是 CDN URL。写帖时让 Agent 截图、调工具、替换 Markdown 里的本地路径，全链路无需手动。

## 踩坑点

- **国内可达性波动**：jsDelivr 在大陆的可达性历史上反复过，重要文档发布前先实测，或准备 Cloudflare Pages/R2 兜底镜像。别把它当 SLA 级依赖。
- **`@main` 缓存**：边缘缓存很凶，同名覆盖后 CDN 可能长期不更新。要么换文件名，要么去 purge.jsdelivr.net 手动刷新。结论：把文件当"只追加"的。
- **体积限制**：单文件建议小于 20MB，仓库控制在 1GB 内；截图先压一遍，pngquant 足够。别放视频，被封是迟早的事。
- **隐私**：公开仓库人人可见，含 token、内网地址、客户数据的截图千万别传。上传脚本里加一层关键词扫描更稳。
- **链接生命周期绑仓库**：仓库转私有或删除，外链全灭。它是"慢存储镜像"，不是唯一真源。

## 可复用建议

- 封装成 MCP 工具是这套方案价值最大的一步：Agent 自动贴图和手动贴图完全是两个量级的体验。
- 命名用 `日期/主题/hash.png`，天然防冲突、好清理。
- 文档引用固定 tag，升级图片时新文档用新 tag，旧文档不动。
- 仓库本身即备份（git 历史 + 本地 clone），比无主图床多一层保险。

## 总结

GitHub + jsDelivr 适合社区帖子、博客、插件文档这类中低频、可容忍偶发波动的场景，成本为零且全链路可脚本化。但它不是生产级 CDN，可达性和配额都要留后手。把上传逻辑沉淀成 Agent 可调用的工具，才是这个组合在自动化工作流里真正的杠杆。
