## 背景

大多数 Agent 会话仍是"一问一答"：你不发消息，它就永远安静。但真正省时间的场景往往是反过来的——CI 红了、日历冲突了、某个文件三天没动而 deadline 就在明天。这类事不需要人去"问"，只需要有人（或某个 Agent）先注意到。本文记录我在 OpenClaw 上给个人助手加 proactive 能力的实践：一条"触发 → 判断 → 行动 → 汇报"的最小链路，以及如何让它不变成骚扰源。

## 问题

最直接的做法很诱人：给 Agent 挂个定时任务，每小时把所有状态拉出来"自己看着办"。跑两天你会遇到三个问题：

1. **打扰噪音**：推送 20 条，值得看的只有 2 条；
2. **成本失控**：每次"看一眼"都是一轮完整推理；
3. **自触发循环**：Agent 处理了自己发出的通知，又生成新通知，无限套娃。

所以 proactive 的核心工程问题不是"能不能自动做"，而是**"什么值得做、做到哪一步停"**。

## 做法：四层最小链路

**1. 触发层。** 三类来源：cron 定时扫描、webhook 事件（CI / 邮件 / PR）、文件与 inbox 变更监听。触发器全部用声明式配置，不写在 prompt 里，改阈值不用动提示词。

**2. 判断层。** 触发后先跑一次便宜模型的过滤判断，输入是结构化事件 + 固定评分规则，输出"推送 / 进日报 / 忽略"三档：

```yaml
trigger: ci_failed
on: webhook
judge:
  model: cheap
  rubric: |
    阻塞我当前分支 → 推送
    其他分支且可自动重试 → 重试后进日报
    无法判断 → 进日报
action_allow: [retry, read_logs]
action_deny: [send_message, deploy]
quiet_hours: "23:00-08:00"
```

**3. 行动层。** proactive 会话使用**单独的凭证和权限档位**：默认只读 + 少量白名单写操作（重试、打标签）。任何对外发送、部署类动作，一律留到有人确认。

**4. 汇报层。** 90% 的事件进每日 digest，一次推完；只有标记为"打断级"的才即时推送。每条 proactive 动作落日志：触发 ID、理由、token 消耗、最终动作。

## 踩坑点

- **自触发循环**：Agent 的 digest 又被 inbox 监听当成新事件抓回来。解法是给所有 Agent 产出的消息打来源标记，触发层直接丢弃。
- **非幂等重试**：webhook 重复投递导致重试跑了三次。给每个触发事件生成 dedup key，行动层先查再执行。
- **rubric 漂移**：随手改了判断规则里的措辞，推送量翻倍。rubric 要当代码对待，每次改动观察一周推送接受率。
- **成本**：把"持续盯着"改成"事件驱动才推理"，token 消耗降了一个数量级。

## 可复用建议

1. **先写标准，再写代码**：把"什么值得打断我"写成书面规则。规则说不清楚，说明还不该做 proactive。
2. **digest 是默认档**，即时推送是例外，不是反过来。
3. **proactive ≠ 自主**：单独权限档、单独凭证、单独日志，出问题能一键停整条链路。
4. **用"推送接受率"当北极星指标**（点开数 / 总推送数），低于一半就该收紧阈值。

## 总结

proactive 能力的价值不在于 Agent 有多主动，而在于它对"打扰成本"的建模。触发声明式、判断便宜化、行动白名单、汇报聚合——这四件事做到位，Agent 才能从"你问它答"升级为"它先想到，但你始终说了算"。先从一条最简单的 cron + digest 链路跑起来，比一次搭完全自动系统靠谱得多。
