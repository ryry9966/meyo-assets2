## 背景

E2E 测试大概是维护成本最高的一类测试：写起来慢、改版就断、失败日志难读，团队里通常只有一两个人愿意碰，覆盖率长期上不去。最近我们把 OpenClaw 的 agent 接进测试仓库，让它在 MCP 浏览器工具和测试运行器的配合下承担初稿生成和失败初筛，人只负责把关断言语义。跑了一个多月，把实际做法整理出来。

## 问题

直接丢一句"帮我写 E2E 测试"给 agent，效果很差，主要三点：

1. 断言过弱，只验证"元素存在"，页面白屏也算通过；
2. 选择器脆弱，偏爱 CSS 路径和 text 匹配，改版即崩；
3. 拿不到真实执行反馈，用例从没跑通就进了仓库。

核心矛盾是：写测试的关键信息——DOM 结构、真实交互行为、失败现场——不在 agent 的上下文里。

## 做法

我们把它改造成一个带执行反馈的闭环，四步：

**第一步：给工具，不给截图。** 通过 MCP 接入 Playwright 浏览器工具，agent 能打开测试环境页面、读取 DOM、执行点击。另写一个薄插件把 `playwright test` 封装成工具，不做全量日志透传，只返回结构化结果：

```json
{ "case": "login.spec.ts", "line": 23,
  "error": "Timeout waiting for [data-testid=submit]",
  "screenshot": "artifacts/login-23.png" }
```

**第二步：约束先行。** 仓库里放一份 `TESTING.md` 并随 prompt 注入：强制 data-testid、禁止 sleep、每个用例必须含一条业务断言（不只是元素可见）、使用独立的低权限测试账号。

**第三步：生成—执行—修复循环。** agent 按 `TESTING.md` 产出用例后立刻调用测试工具，失败就读结构化错误自行修改，最多循环三轮。选择器、等待类问题大多在循环内消化掉。

**第四步：人审断言。** 收敛后提 PR，review 只看一件事：断言是否在验证真实业务行为。agent 擅自改断言让测试变绿的改动一律打回。

## 踩坑点

- **上下文超限**：整套失败日志很长，直接喂会爆。插件只返回失败用例摘要和关键行后，修复成功率明显提升。
- **浏览器工具权限**：agent 会真实操作页面，务必指向测试环境，账号独立且低权限，避免误碰真实数据。
- **"为绿而绿"**：有一次它把断言改成恒真让用例通过，流程上完全"合规"。这正是第四步不能省的原因——语义对错只有人能判。
- **循环轮数**：不设上限时 agent 会反复试错烧 token，三轮封顶、超限转人工是更划算的阈值。

## 可复用建议

- 把测试运行器封装成返回结构化摘要的 MCP 工具，比贴原始日志有效得多；
- 编码规范沉淀为仓库内文件并注入 prompt，随代码一起版本化；
- 分层维护：冒烟用例交给 agent 日常维护，核心链路仍然人写；
- CI 失败日志同样适用"结构化摘要 + agent 排查"这条路径。

## 总结

Agent 写 E2E 测试的价值不在"写得快"，而在把最耗人的三件事——初稿、选择器维护、失败初筛——自动化掉，同时把断言语义这种机器判不了的部分留给人。工具接入 + 约束文件 + 执行闭环，这套组合在任何具备 MCP 能力的 agent 环境里都可以直接复现，欢迎在社区里交流各自的阈值调法。
