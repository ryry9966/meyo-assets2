## 背景

团队每天要发一份"昨日进展"日报，数据散在好几处：服务日志、agent 运行记录、任务队列的完成事件。以前的做法是人肉翻日志、复制粘贴、再写两句总结。时间成本高不说，还经常漏掉关键错误。

这篇帖子记录我们用 OpenClaw 搭的一条日报流水线：定时触发 → 日志清洗 → agent 结构化提取 → 校验 → 渲染推送。总共不到 200 行脚本加一个定时 agent 任务。

## 问题

把原始日志直接丢给 agent 总结，会遇到三个麻烦：

1. 日志非结构化，多行堆栈、编码混杂，token 浪费严重；
2. 输出格式不稳定，今天多一个字段明天少一个，下游没法消费；
3. 结论无法溯源——你不知道报告里那句"接口延迟升高"到底对应哪条日志。

所以核心原则是：**LLM 只做提取和归纳，不做解析和校验**。解析交给确定性脚本，格式交给 schema。

## 做法

**第一步：日志落盘与分区。** 各数据源统一写到 `logs/YYYY-MM-DD/` 目录，按天分区，原始文件只读不改。取数时用 `logs/$(date -d yesterday +%F)/`，日期显式传参。

**第二步：确定性预处理。** 一个 Python 脚本做三件事：按行首时间戳正则把多行堆栈折叠成单条记录、字段拍平、过滤噪音（healthcheck、DEBUG 之类），产出 JSONL，每条带 `source/level/ts/message` 和行号 ID。这一步之后体积通常缩到 10%~20%。

**第三步：agent 提取。** cron 触发 agent 任务，prompt 里明确三件事：输入是 JSONL；输出必须符合给定 JSON Schema（分类事件、异常汇总、待办建议三个数组）；引用事件必须携带行号 ID，禁止编造。temperature 设 0。

**第四步：schema 校验与降级。** 用 `jsonschema` 校验输出，失败就带上错误信息重试一次；再失败就降级为"异常计数 + 日志路径"的简版报告——宁可粗糙也不要编造。

**第五步：渲染与归档。** Markdown 模板填槽后推送到 IM webhook，同时把结构化结果存到 `reports/YYYY-MM-DD.json`，供后续 diff 和复盘。

## 踩坑点

- **堆栈没折叠**：agent 把一条堆栈当十条错误统计，次数虚高。折叠必须在预处理里做，别指望模型数对。
- **时区问题**：cron 00:05 跑，容器是 UTC，取到的"昨天"其实是前天。所有日期显式传参，prompt 里不出现"昨天"这种相对词。
- **任务重叠**：上游延迟导致单次处理超周期，cron 二次触发。加了个带过期时间的锁文件。
- **schema 漂移**：上游加了个字段，agent 自作主张塞进输出。校验器开 `additionalProperties: false` 拦住了。schema 就是契约，要收紧。
- **上下文超长**：高峰期日志翻倍直接爆窗口。改成 map-reduce：先按小时分片提取，再对分片结果二次归纳。

## 可复用建议

1. 解析、提取、渲染三段解耦，任何一段坏了可单独重跑；
2. 永远落一份结构化中间产物（JSON），Markdown 只是它的视图；
3. 每条结论带溯源 ID，可点回原始日志；
4. 幂等设计：同一天重跑是覆盖，不是追加；
5. 先跑简版（只有错误计数），流水线稳了再加归纳和建议。

## 总结

流水线上线三周，日报写作时间从每天 20 分钟降到 0，漏报率也明显下降。经验归结为一句话：把不确定的活儿交给 agent，把确定的活儿留给脚本，中间用 schema 卡住。模板和校验器已放进社区仓库，欢迎提 issue 讨论。
