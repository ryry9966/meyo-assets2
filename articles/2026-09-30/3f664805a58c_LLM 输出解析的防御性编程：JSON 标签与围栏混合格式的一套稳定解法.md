## 背景

在 OpenClaw 插件和 Agent 工具链里，让模型返回结构化数据是常见需求。我们通常在 prompt 里约定输出格式，比如包在 ```json 围栏里，或包在 `<json>` 标签里。但只要跑得够久、换过模型版本、或用户输入里塞了奇怪内容，输出格式就会漂移：有时是围栏，有时是标签，有时两者嵌套，有时前后还带一段解释文字。

解析器按理想格式写，线上迟早挂。这篇记录我们最终收敛的一套防御性解析做法。

## 问题：格式漂移的几种形态

实际踩到的输出变体：

1. ```json / ```json5 / 裸 ``` 围栏，甚至围栏缩进在 markdown 列表里
2. `<json>`、`<JSON>`、`<output>` 等标签，或标签里再套围栏
3. JSON 前后带解释文字，中文场景下还可能混入全角冒号、全角逗号当分隔符
4. JSON 字符串值里本身含 `{ }` 或反引号（比如返回代码片段）
5. max_tokens 截断导致的残缺 JSON

## 做法：分层提取 + 本地修复

核心思路是把解析拆成四层，逐层降级：

**第一层，直接 `json.loads` / `JSON.parse`。** 模型完全听话时的最快路径。

**第二层，围栏与标签剥离。** 用正则去掉 ```` ``` ```` 围栏和 `<tag>...</tag>`，注意围栏语言标注可有可无，标签名建议走白名单。

**第三层，括号配平扫描。这是关键。** 不要用 `\{.*\}` 这类贪婪正则，它会吞掉多个对象；非贪婪的又会截断嵌套结构。写一个几十行的状态机：逐字符扫描，维护"是否在字符串内、是否转义、深度计数"三个状态，深度归零即截取候选片段。它能稳定处理"字符串值里带花括号"的情况。

**第四层，容错修复。** 把候选片段交给 json_repair（Python）或 jsonrepair（Node）这类库，处理尾逗号、单引号、缺引号等常见病。全角标点替换放最后，且必须跳过字符串内部，否则会污染中文值。

失败时别只抛异常：把原始输出原文落日志，函数返回 `(parsed, confidence, raw)` 三元组，`raw` 留给人工排查。

## 踩坑点

- 正则提取是重灾区：贪婪匹配多吃、非贪婪截断、没处理字符串内的花括号，这三种错误我都写过。
- 全角标点"一刀切"替换，曾把值为「备注：加急」的字段也改了——值没坏但测试快照全变；更糟的是值里含引号时直接解析错乱。替换必须感知字符串边界。
- Python 的 `json.loads` 默认接受 `NaN`/`Infinity`，不是严格 JSON，下游走严格校验会炸，用 `parse_constant` 拦掉。
- 别迷信 `temperature=0`。模型升级一次，格式分布就悄悄变了，我们见过从"总是围栏"变成"总是裸 JSON"的案例。
- 解析失败后用"请只输出 JSON"重试，多一次往返还常常再失败。本地修复先行，重试留给结构性失败。

## 可复用建议

1. 把级联封装成 `extract_json(text)` 单一入口，全项目共用，禁止各处自己写正则。
2. 每次线上解析失败都是测试素材：脱敏后收进漂移样本库，跑进 CI。我们攒了三十多条真实坏样本，回归价值很高。
3. 有条件优先用 provider 原生的结构化输出 / tool call schema，这是第一道防线，标签只是兜底。
4. 把解析成功率当指标监控，突降通常意味着上游模型或 prompt 变了，比用户报障早得多。
5. prompt 改动与解析回归测试绑定：改 prompt 必须跑一遍样本库。

## 总结

把 LLM 输出当作不可信输入，是这类解析的全部出发点。约束解码优于宽松提取，宽松提取优于本地修复，修复失败要有日志兜底而不是盲重试。解析器是你系统契约的一部分，不该指望模型替你守住它。
