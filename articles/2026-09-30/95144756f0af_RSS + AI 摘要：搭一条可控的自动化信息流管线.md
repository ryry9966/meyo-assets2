## 背景

RSS 没死，只是被藏起来了。大量博客、GitHub Release、arXiv、论坛板块都有稳定 feed，RSSHub 之类的工具还能把没有 feed 的站点转出来。所以问题从来不是“没有信息源”，而是“读不过来”——我订阅了 60 多个源，每天新增条目 300~500 条，人工精读不现实。

## 问题

直接把每条 RSS 丢给 LLM 总结，会踩三个坑：

1. **成本失控**：逐条调用，token 和请求数爆炸；
2. **质量不稳**：feed 里常常只有 description，全文被截断，模型开始“脑补”；
3. **不可检索**：总结完就沉底了，想查“上周那篇讲 MCP auth 的文章”根本找不回来。

于是这条管线的目标很朴素：抓全 → 去重 → 过滤 → 分批摘要 → 汇总推送 → 原文可溯。

## 做法

技术栈很轻：Python + SQLite + 定时任务，摘要走 OpenClaw 的 Agent 能力（换成任意 API 也行）。

1. **抓取层**：cron 每 2 小时跑一次 `feedparser` 拉全部源，按 `(feed_id, link)` 建唯一索引，重复直接跳过。源列表放 YAML 配置，加源只改配置。
2. **正文补全**：description 过短的条目请求原文页面，用 readability 类库抽正文，超过 8k 字符截断并打上 `truncated` 标记。
3. **过滤层**：两层漏斗——正则黑名单（标题含“融资/招聘/广告”直接丢）+ 启发式打分（关键词命中、源权重）。实测能砍掉约 40% 的量。
4. **摘要层**：不逐条调用。把同源相邻条目拼成 batch（每批 3~5 条），要求模型输出 JSON：`{id, one_line, key_points[], tags[]}`。摘要里强制保留“信息不足”的兜底选项——宁可输出“原文要点不足”，不允许编。
5. **汇总层**：每天早上把 24h 内条目的 one_line 再做一次 map-reduce，生成按 tag 分组的日报，每条挂原文链接。
6. **消费层**：日报推到 IM webhook；同时把“查日报 / 按关键词检索历史条目”封装成 MCP tool。平时在 OpenClaw 里直接问 agent“昨天关于 X 的内容有哪些”，它调 tool 返回带链接的结果。

## 踩坑点

- **幻觉主要来自截断**：早期没做 `truncated` 标记，模型对被截断的全文硬总结，编造了不存在的结论。加上“截断就只总结可见部分”的约束后明显收敛。
- **去重要在入库时做，不要在摘要后做**：同一内容常被多个源转载且标题各异。现在入库前对正文取 simhash，相似度高的合并 entry。
- **时区坑**：有的 feed 的 pubDate 是 UTC，有的是本地时间。统一转 UTC 存储、展示层再转，否则日报会漏掉“今天早上”的条目。
- **批处理别贪大**：一批塞 10 条以上，key_points 会开始互相串，3~5 条是实测上限。
- **缓存摘要结果**：以正文 hash 为 key 存摘要，重跑管线不重复计费。

## 可复用建议

- **原始数据永远保留**（正文、时间、链接）。摘要是衍生物，随时可以换模型重跑；
- **抓取 / 摘要 / 推送拆成独立阶段**，各自幂等，坏了哪段补跑哪段；
- **让模型输出结构化 JSON 并校验**，不要让它写散文再拿正则解析；
- **把检索能力做成 MCP tool**，而不是又做一个 web 页面——在 agent 生态里，前者的复用性高得多。

## 总结

这套东西没有一步是新鲜的：RSS、去重、map-reduce 摘要都是老手艺。价值在于管线本身——每层可观测、可重跑、成本可控。上线一个月，我的阅读时间从“刷一小时”变成“读 5 分钟日报 + 按需追问”，漏掉重要文章的情况反而更少了。原因很简单：过滤规则是显式的，错了可以改，而不是交给算法黑盒。
