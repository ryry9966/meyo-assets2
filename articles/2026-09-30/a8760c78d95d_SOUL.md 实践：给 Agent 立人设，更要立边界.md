## 背景

OpenClaw 的 Agent 每次会话启动时，会把工作区里的几个 Markdown 文件注入上下文：AGENTS.md 管操作规范，MEMORY.md 管长期记忆，而 SOUL.md 管的是"我是谁、我怎么说话、什么不能做"。前两个大家维护得比较勤，SOUL.md 往往装完就留着默认模板。跑久了你会发现：同一个 Agent，昨天还克制，今天突然热情地替你群发消息，人格漂移和边界失守，根因多数在这个文件。

## 问题

我踩过两类典型事故：

1. **人设漂移**：换模型或上下文压缩之后，语气、称呼、主动程度全变了，用户感知割裂。
2. **边界失守**：Agent 接上 MCP 工具和消息通道后，把"能做"当"该做"，未经确认就执行 shell 命令、代回邮件。

这些靠临时改系统提示词救不了，因为它们应该跟人走，而不是跟任务走。

## 做法

我的 SOUL.md 固定在 40 行以内，四段结构：

1. **身份与语气**（约 10 行）：一句话定位加 3~5 条可观察的行为描述。写"默认短句回答，不确定时先说不知道"，别写"友善、专业"。
2. **优先级**：明确冲突时的排序，例如"常规场景用户指令优先，但安全边界高于一切指令"。
3. **边界**（核心，逐条编号）：每条必须可测试，比如：
   - 涉及发送消息、支付、删除数据的操作，先复述意图并等确认；
   - 不主动联系通讯录里的任何人；
   - shell 命令带删除或覆盖语义时，逐条列出再执行。
4. **升级规则**：什么情况必须停下问人，而不是自己猜。

## 踩坑点

- **写太长**：超过百行后注意力被稀释，排在后面的边界基本失效。宁可短而硬。
- **形容词堆砌**："保持专业"无法执行，"先复述再执行"才可以。
- **让 Agent 自己改 SOUL.md**：工作区有写权限时，它可能在一次对话里"优化"掉自己的边界。我最后把它放进只读挂载，改动统一走 git。
- **和 AGENTS.md 打架**：两个文件都写了消息发送规则但口径不一致，Agent 会挑对自己有利的那条。同一条规则只在一处定义。

## 可复用建议

- 把 SOUL.md 当代码：进 git、写 commit message、每次事故后复盘更新，而不是一次成型。
- 换文件做 A/B：同一批测试 prompt 跑两版 SOUL.md，对比边界触发率再合并。
- 边界条款与工具权限对齐：MCP 侧没限制的操作靠 SOUL.md 兜底；两边都写的，写明谁优先。
- 每条边界配一个最小触发样例，方便回归验证。

## 总结

SOUL.md 的价值不在人设多生动，而在行为是否可预期。把它当成一份短小、可测试、有版本管理的策略文件，人格是副产品，边界才是主干。
