## 背景

Agent 产出的内容基本都是 Markdown，但“生成完成”不等于“可以发布”。博客、掘金、知乎、公众号、GitHub README 对 Markdown 的支持差异很大——公众号甚至不直接认 Markdown，只接受带内联样式的 HTML。如果每次发布都手动改格式，自动化就失去了意义。这篇帖子分享一条比较稳妥的管线做法：以规范化 Markdown 作为唯一事实源，平台差异全部交给转换层。

## 问题：格式漂移

直接把 AI 输出扔进各平台编辑器，常见故障有：

- 公众号编辑器会剥掉 `class`，不认脚注和任务列表；
- 表格在窄屏端挤成一团，深层嵌套列表直接渲染错乱；
- 图片外链被防盗链拦截，或者 AI 干脆编造出不存在的图床地址；
- 代码块语言标签不统一（`ts` / `typescript` 混用），高亮时好时坏。

本质问题是：AI 输出的是“方言 Markdown"，各平台又是另一套方言，中间缺一层规范。

## 做法：五步管线

1. **规范化（normalize）**：用 remark/unified 把原始输出解析成 mdast，统一列表符号、标题层级（一级标题只允许出现在文首）、代码块语言映射和软换行策略。
2. **AST 级 lint**：基于 mdast 写规则检查——表格列数上限、按平台的语法禁用清单、链接可达性、图片 URL 白名单。不合规直接打回给 Agent 重写，而不是发布后人工救火。
3. **平台转换器**：每个目标平台一个转换器。公众号走 markdown-it 自定义 renderer 输出内联样式 HTML；掘金/博客基本直出，只做图片重传；知乎需要处理 HTML 白名单截断。
4. **图片落库**：所有远程图片在转换前抓取、压缩、传到自有对象存储，替换为稳定 URL。这一步独立做，不要混进渲染器。
5. **产物即工件**：发布结果落盘（HTML 快照 + 元数据），转换器改动可以用旧快照做 diff 回归测试。

如果整套跑在 Agent 里，就把“规范化 + lint + 转换 + 发布"封装成 MCP tool，Agent 只负责写内容，格式适配对它是透明的。

## 踩坑点

- **别用正则改 Markdown**。嵌套代码块、HTML 块内的 Markdown 语义都会骗过正则，务必走 AST。
- **AI 爱生成宽表格**。我们在 lint 里限制最多 4 列，超了就让 Agent 改写成列表，比渲染端兜底干净得多。
- **硬换行与软换行**。公众号对单个换行不敏感，需要在转换器里统一替换为段落或 `<br>`，否则段落全粘在一起。
- **脚注、任务列表、数学公式**是兼容性重灾区，默认在 lint 里禁掉，除非对应转换器明确支持。
- **不要手动转义 HTML**。转义交给渲染器，预处理里做一次会变成 `&amp;lt;` 这种二次转义事故。

## 可复用建议

- 规范化和 lint 规则抽成独立包，所有平台转换器共享；
- 每条 lint 规则配一个最小失败样例，当测试跑；
- 转换器保持纯函数：输入规范 Markdown，输出平台格式，不碰网络；图片重传等网络操作独立成前置步骤；
- 接入新平台时，先手工发三篇，找出实际被剥离的语法，再写转换器，不要凭文档想象。

## 总结

多平台发布的问题不在 Markdown 本身，而在于把“内容”和“表示”耦合在了一起。一条 AST 管线、一份平台差异清单、若干纯函数转换器，就足以让 Agent 生成的内容一次编写、多端一致。原则是先 lint 打回、后转换兜底，自动化管线才经得起长期运行。
