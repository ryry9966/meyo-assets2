## 背景

社区里用 OpenClaw 跑内容类工作流的不少：Agent 负责收集资料、写稿，最后产出一份 Markdown。但“写完”离“发布”还差一段——同一份 Markdown，公众号、知乎、掘金、静态博客的接受度完全不同。我们的做法是把格式适配抽成独立管线：Agent 只产出标准 Markdown，其余交给工具链。

## 问题

实际跑起来有四类典型麻烦：

1. **方言差异**：公众号编辑器基本只认内联样式的 HTML；知乎会剥离大部分标签和自定义 class；掘金支持 GFM 但对脚注、mermaid 不友好；静态博客最宽容。
2. **AI 输出不规范**：标题层级跳跃（H1 下直接 H3）、列表嵌套过深、混入裸 HTML 和 HTML 注释，脚注语法各家渲染不一。
3. **资产问题**：图片外链在微信端有防盗链，代码块高亮风格各平台不一致。
4. **搬运成本**：每发一个平台手动调一遍格式，工作流自动化的收益基本被吃掉。

## 做法

核心原则：**AST 优先，正则兜底；一份源文件，多个渲染目标。**

1. **规范化（normalize）**：用 unified/remark 系（`remark-parse` + `remark-gfm`）把 AI 输出解析成 mdast，跑一遍 fix：重排标题层级、清理裸 HTML、统一列表缩进和中英混排空格。产出“规范 Markdown”，作为唯一事实源。
2. **平台适配器（adapter）**：每个平台实现一个 `render(ast, platform)`。公众号走 mdast → 内联样式 HTML（样式表自维护，配合 `juice` 内联）；知乎输出受限 HTML，表格、代码块降级为截图或列表；掘金和博客直出 GFM。适配器只做转换，不做业务判断。
3. **资产处理**：图片统一先传图床，渲染时按平台重写 URL；代码块在管线内预生成高亮，不依赖目标平台的 highlighter。
4. **发布前校验**：检查标题层级连续、外链可达、图片存在，以及是否有未适配的节点类型（比如 mermaid 漏到了不支持的平台）。
5. **接进 Agent**：整条管线封成一个 CLI 或 MCP tool，Agent 只需调 `publish --platform wechat,zhihu`。

## 踩坑点

- 别用正则做 Markdown 转换。代码块里的 `#`、列表里嵌代码块，嵌套结构一定会翻车，AST 解析是唯一稳妥路径。
- 公众号会剥 `<style>` 标签和 class，样式必须内联到每个元素；本地渲染通过不算数，贴进编辑器预览一次才算数。
- AI 很爱写脚注和 mermaid，但知乎、公众号都不支持，要在管线里显式降级，而不是等渲染报错。
- 图片防盗链是隐性坑：本地预览正常，发布后裂图。发布前把所有图源换成目标平台可访问的 URL。
- 中英混排、标点全角半角，在 normalize 阶段统一处理，别指望各平台帮你排版。

## 可复用建议

- 用快照测试固化各平台输出：源文件不变而渲染结果变了就报错，升级依赖时特别有用。
- 适配器写成无状态纯函数，方便单测，也方便日后新增平台。
- front-matter 里带上平台元数据（摘要、封面、标签），Agent 一次产出全部发布所需信息。

## 总结

这条管线的关键不在某个具体库，而在“规范中间表示 + 平台适配器”的分层：Agent 对格式差异无感知，平台规则变化只改适配器。放在 OpenClaw 的插件体系里，它天然适合做成一个可复用的发布工具，欢迎在社区帖里交流各自的适配方案。
