## 背景

OpenClaw 跑久之后，主会话（main session）会积累大量历史：频道消息、工具调用结果、失败重试的痕迹。为了让重活不压垮主上下文，常见做法是用 `sessions_spawn` 拉起子 Agent——它有自己的上下文窗口和 transcript，跑完只把结论带回来。听起来简单，但“隔离”的边界比想象中模糊，我踩过不少坑，这里整理成一份可复用的实践。

## 问题

隔离没做好时，典型症状有四种：

- 子 Agent 的中间输出、报错、重试日志被写回主会话，上下文迅速膨胀，模型开始“失焦”；
- 子 Agent 直接读主会话 transcript 或共享同一份 memory，等于没隔离；
- 子 Agent 崩溃后主会话挂起，等一个永远不会来的结果；
- 孤儿 session 文件在 agents 目录下越积越多，磁盘和排查成本一起涨。

本质是两个问题：**transcript 隔离没闭环**，以及**返回值没有契约**。

## 做法

1. **划清主/子边界**：主会话只负责调度和对话；子 Agent 的任务描述里写清目标、约束、超时，不附带无关上下文。
2. **收紧返回契约**：要求子 Agent 返回固定结构的摘要（结论 + 关键数据 + 风险点）。OpenClaw 只把最终结果作为 tool result 注入主会话，中间过程留在子 session 的 transcript 里。
3. **文件系统单独划地盘**：子 Agent 的草稿写进独立 tmp 目录，任务结束即清理；禁止它写主工作区的 `MEMORY.md` / `AGENTS.md`，否则污染会“穿越”到未来所有会话。
4. **配超时与兜底**：spawn 时设超时，超时返回一句明确的失败说明，主会话据此决定重试还是降级。
5. **定期清孤儿**：检查 `~/.openclaw` 下的 sessions 目录。注意重置主会话（`/new`）不会顺带删除子 session 文件，需要脚本或手动清理。

## 踩坑点

- **最常见的破防**：为了让子 Agent“了解背景”，把主会话 transcript 路径发给它。隔离瞬间失效，而且污染是双向的。
- **返回值过大**：子 Agent 带回几万 token 的原始抓取内容，主会话照样爆。隔离的是过程，不是结果体积。
- **权限继承**：子 Agent 默认可能拿到与主 Agent 相同的工具集。写文件、发消息这类有副作用的工具，务必按需裁剪。
- **嵌套 spawn 不设上限**：一层套一层，出错时 transcript 散落在多个 session 里，几乎无法排查。
- **误以为重置主会话就干净了**：共享文件和 memory 里的污染依然存在。

## 可复用建议

- 把子 Agent 当**纯函数**：任务进、摘要出，副作用要么为零、要么显式声明。
- 给子 Agent 定一个固定 JSON 返回 schema，主会话解析失败即视为任务失败并重试。
- 子 session 的 transcript 留作审计日志，定期归档删除，不在主流程中引用。
- 工具权限最小化：只给完成该任务必需的工具。
- 在 `AGENTS.md` 里写明“子 Agent 禁写 memory”，让策略对模型本身可见。

## 总结

OpenClaw 的 session 隔离，核心是三层：**transcript 分文件、结果走单一返回通道、共享面（文件系统 / memory / 工具权限）显式收窄**。做到这三点，子 Agent 才是“用完即走”的工人，而不是往主会话里倒垃圾的邻居。隔离不是配置一次就完事——每次新增自动化流程时，建议把上面的清单过一遍。
