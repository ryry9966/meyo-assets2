## 背景

最近在用 OpenClaw 做批量任务时遇到瓶颈：一个“分析 20 个日志文件并各自生成摘要”的任务，单个 Agent 串行跑了近半小时，而且上下文塞满后质量明显下滑。这促使我把任务改造成 subagent 编排模式——主 Agent 负责拆分与汇总，子 Agent 并行处理具体工作。本文记录这套做法和踩过的坑。

## 问题

单 Agent 串行有三个典型痛点：

1. **慢**：子任务之间明明互不依赖，却在排队执行；
2. **上下文污染**：第 15 个文件的分析会被前 14 个的中间结果干扰，摘要开始互相“串味”；
3. **脆弱**：跑到第 18 个文件时一次工具调用失败，整个任务作废重来。

判断是否值得并行化的核心标准只有两条：**任务是否天然可拆，子任务之间是否低耦合**。满足这两点再动手，否则别碰。

## 做法

我采用的是经典的 fan-out / fan-in 结构：

**第一步：拆分。** 主 Agent 把总任务切成 N 个自包含的子任务。关键是“自包含”——每个子 Agent 拿到的 prompt 必须带上它需要的全部上下文（文件路径、输出格式、边界条件），绝不能假设它能“看到”主对话。

**第二步：定义输出契约。** 规定每个子 Agent 统一写入 `output/task-{id}.md`，开头是 JSON 元信息（状态、耗时、错误码），后面是正文。这一步决定了汇总阶段顺不顺利。

**第三步：并行派发。** 通过 subagent 机制同时拉起 N 个子 Agent，每个绑定独立输出路径。并发数先控制在 3–5，观察 token 消耗和速率限制后再加。

**第四步：汇总。** 主 Agent 不逐份阅读，而是先读所有 JSON 元信息做健康检查，失败的子任务单独重试，成功的批量交给一个轻量汇总步骤。

实际效果：同样的 20 个日志任务，从 28 分钟压到 7 分钟，单份摘要质量反而更稳——因为每个子 Agent 的上下文只装一个文件。

## 踩坑点

- **上下文不会自动继承。** 子 Agent 拿不到主对话历史。我第一次跑就漏传了“输出目录”这个前提，五个子 Agent 全写到了默认路径。后来把所有共享前提做成模板变量，派发前强制填充。
- **共享资源冲突。** 两个子 Agent 同时改同一个文件、同时操作同一个 git 分支，会互相覆盖。解法很朴素：一个子任务一个独立输出，合并动作只留给主 Agent。
- **部分失败是常态。** 并行意味着必然有失败，一定要设计“接受部分结果”的路径，不要一失败就全部重来。
- **过度并行。** 有依赖的任务（先调研再写码）强行并行，汇总阶段会冒出一堆互相矛盾的中间产物，返工成本比省下的时间还高。

## 可复用建议

1. 子 Agent 的 prompt 做成模板，可变部分参数化，编排代码就退化成纯配置；
2. 并行前确认操作幂等，重跑不产生副作用；
3. 输出一律结构化（固定路径 + 固定字段），汇总逻辑才能稳定；
4. 并发数从小到大试，2–3 个跑通再扩；
5. 每个子 Agent 设超时和一次重试，超时即标记失败降级，别拖住整体；
6. 主 Agent 里留一个“串行回退”开关，排查问题时切回串行更好定位。

## 总结

subagent 并行不是银弹，收益完全取决于任务结构：独立子任务多，收益接近线性；任务耦合重，并行只会放大混乱。工程重心其实不在“并行”本身，而在接缝处——上下文怎么传、资源怎么隔离、结果怎么合并。把这三件事模板化之后，这套编排就成了可反复复用的基础设施。
