## 背景

多数人对 Agent 的用法是"一问一答"：你发消息，它回复，然后双方都下线。但 OpenClaw 的 Agent 本质上是个常驻进程，Gateway 一直活着，完全有能力"自己找活干"。HEARTBEAT.md 就是这个能力的入口：Agent 按固定间隔（默认 30 分钟）被唤醒一次，读取工作区里的 HEARTBEAT.md，执行其中定义的任务。文件为空或不存在时，心跳直接跳过，不产生消耗。

## 问题

被动模式有几个真实的痛点：

- **跟进会断**。你让 Agent "盯着 CI，挂了告诉我"，它答完就忘，你还是得自己再问一遍。
- **值守成本高**。收尾类的事（看日志、查磁盘、对日历）每次都要人发起，常驻能力被浪费。
- **朴素实现会翻车**。如果每次心跳都无脑跑一堆检查，token 消耗加通知轰炸，会让人三天就关掉这个功能。

## 做法

1. **建文件**。在 Agent 工作区（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`，写成 checklist：

```markdown
# Heartbeat Tasks
- [ ] 检查 ~/logs/app.log 最后 50 行，出现 ERROR 才汇报
- [ ] `df -h /` 使用率超过 85% 才汇报
- [ ] 每天第一次心跳时汇总今日日历
```

2. **配间隔**。在 `openclaw.json` 的 heartbeat 配置里调整间隔，默认 30 分钟对多数场景够用，起步可以放宽到 60 分钟。

3. **约定输出**。没事发生时让 Agent 回 `HEARTBEAT_OK`，不会打扰你；有异常才转成主动消息。这是控制通知噪音的关键约定。

4. **接入工具**。心跳里可以正常调用 MCP 工具和脚本，比如用 GitHub MCP 查 CI 状态，用 filesystem 读日志。

## 踩坑点

- **任务写太模糊**。"看看有没有问题"这种描述，Agent 每次的行为都不可复现。每条任务必须带明确命令和阈值。
- **没做状态去重**。同一个 ERROR 不处理，它每 30 分钟报一次。任务里必须写"仅在状态变化时汇报"，或让它维护一个记录上次状态的小文件。
- **重活塞进心跳**。心跳占用的是 Agent 会话，长任务会阻塞对话。正确分层：cron/脚本负责干活并落结果文件，心跳只负责"读结果 + 判断 + 汇报"。
- **上下文污染**。心跳和你的对话共用会话，喋喋不休的心跳会挤占上下文。汇报要短，没事就一个 OK。
- **优先级靠位置**。文件是顺序读取的，重要任务放前面，别指望它自己理解优先级。

## 可复用建议

- 固定用"检查 → 阈值 → 仅变化时通知"的三段式模板写任务，几乎不会出错。
- 把 HEARTBEAT.md 和工作区一起纳入 git，心跳配置变成可版本化、可回滚的基础设施。
- 把心跳当"传感器"用，别当"执行器"用：探测交给它，动作交给脚本，Agent 只做判断和转述。
- 心跳任务可以调 MCP 工具，但保持每条任务在一两步内完成，复杂流程拆给外部脚本。
- 起步阶段宁可只写一两条任务，观察一周通知量和 token 消耗后再加。

## 总结

HEARTBEAT.md 的价值不在"能定时跑任务"——cron 几十年来都能做。它真正的意义是给常驻 Agent 一个低成本的主动性入口：文件即配置、空文件即静默、约定即降噪。把任务写得具体、把状态管理做进去、把重活分层出去，Agent 就能从问答工具变成真正在值班的助手。先跑通一两条检查任务，比一次性写十个更能活过第一周。
