## 背景

我们大部分 Agent 用法是拉式的：开会话、提问、拿到答案、关掉。但如果 OpenClaw 跑在一台 24 小时在线的家庭服务器或 VPS 上，你真正想要的是推式——它应该自己发现磁盘快满了、关注的仓库来了新 issue、某个截止日期快到了。心跳机制就是干这个的：Agent 每隔一段时间自动醒来一次，读取工作区里的 `HEARTBEAT.md`，按里面的条目判断要不要干活。

## 问题

传统的 cron + 脚本能定时执行，但逻辑写死，没有判断力；纯对话式 Agent 有判断力，却没有时间观念，你不开口它永远不动。`HEARTBEAT.md` 是两者之间的折中：一个人类可读、随手可改的 Markdown 文件，充当 Agent 的"常备指令"，由心跳循环周期性注入，由 Agent 自己判断哪些条目此刻该执行、哪些该保持沉默。

## 做法

1. 在工作区（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`；
2. 条目按"条件 + 动作 + 沉默条款"来写，例如：

```markdown
# HEARTBEAT.md

## 常驻检查
- 每次心跳检查磁盘占用，超过 85% 时提醒我
- 每天 08:00（本地时区）汇总新邮件，只列需要我回复的

## 条件触发
- repo owner/repo 出现新的 P0 issue 时通知我

## 沉默条款
- 以上均不满足时，回复 NO_REPLY，不要给我发任何消息
```

3. 在配置里调整心跳间隔（默认约 30 分钟），按条目密度取舍；
4. 重活用 `HEARTBEAT_BATCH` 交给子会话执行，主会话只负责调度和汇报，避免长时间占用上下文。

关键约定是 `NO_REPLY`：Agent 判断无事可做时返回它，这次心跳就不会给你发任何消息。沉默是默认态，触发才是例外。

## 踩坑点

- **文件越长，心跳越贵。** 每次唤醒都是一次完整的模型调用，条目还会稀释注意力。控制在 20 行以内，砍掉从未触发过的条目。
- **条件模糊等于纵容自由发挥。**"时不时看看群消息"这种写法，轻则产生噪音，重则做出你没授权的操作。条件必须能被工具输出验证。
- **忘写沉默条款，三天后你会把它静音。** 不写 `NO_REPLY`，Agent 每次心跳都会汇报"暂无异常"。
- **上下文膨胀。** 心跳持续往会话注入内容，长期跑的会话要定期重置，或直接用独立的心跳会话。
- **不稳定工具的死循环。** 依赖爬虫、外部 API 的条目容易失败重试，最好加一条"连续失败 3 次就报告并暂停该检查"。
- **时区。** 容器里默认 UTC，"每天 8 点"可能不是你以为的 8 点。
- **别在文件里放密钥。** `HEARTBEAT.md` 会被注入 prompt，当成公开文件来写。

## 可复用建议

- 把它当成一个**有判断力的 crontab**：格式固定为常驻检查 / 条件触发 / 沉默条款三段，越规整越不容易跑偏；
- 放进 git 管理，改条目走 commit，出了问题能回溯是哪次修改引入的；
- 定期人工 review 心跳日志，只保留真正触发过且输出有用的条目——这是修剪，不是加法；
- 心跳负责"什么时候看"，能力靠 MCP 工具和插件补齐"能不能做"，两层分开演进；
- 从 1~2 个条目起步，稳定跑一周再扩。

## 总结

`HEARTBEAT.md` 本身只有十来行 Markdown，但它改变的是 Agent 的工作模式：从被动应答的工具，变成带值守责任的服务。工程上的难点不在功能开启，而在克制——条目要少、条件要明确、沉默要成为默认。把它当作一份需要持续修剪的巡检清单，而不是愿望清单，它就能长期稳定地替你盯着那台机器。
