## 背景

OpenClaw 里 agent 的行为由三层决定：模型本身、系统提示词、workspace 下的一组 Markdown 文件。其中 `SOUL.md` 最容易被误解——很多人只把它当成"给 bot 起名 + 写句座右铭"的装饰。但跑一段时间你会发现，它是实打实的行为约束层：语气漂不漂、群聊里该不该说话、敏感操作怎么处理，都和这份文件的写法直接相关。

## 问题

不加约束的 agent 常见几种表现：

- **人格漂移**：今天高冷明天话痨，同一件事在不同会话里口径不一致；
- **边界失控**：群里每条都接话，或者反过来被点名也不回应；
- **越权执行**：把"帮我看下账单"理解成"帮我把欠费缴了"；
- **信息外泄**：把 workspace 里的私人笔记当上下文复述出去。

靠改代码里的 system prompt 治标不治本：改动要重新部署、没法 review、经验也没法积累。SOUL.md 的价值在于把人格和边界变成一份**可版本管理的文本资产**。

## 做法

在 workspace 根目录维护 SOUL.md，建议按五个区块组织：

1. **身份定位**：一两句话讲清"我是谁、为谁服务、基调是什么"；
2. **语气与称呼**：具体到"对陌生人的第一句怎么回""群里只回答被点名的问题"；
3. **能力边界**：明确能做/不做什么，例如"可以读取本地笔记，但不主动把任何文件发送到外部"；
4. **敏感操作规则**：支付、删除、外发类动作，必须先复述内容并向用户确认；
5. **拒绝与升级话术**：超出边界时是直接拒绝还是转人工。

两条写作纪律：

- **规则要可判定**。"保持专业"没有约束力；"代码问题必须附可运行示例，闲聊回复不超过三句"才可执行。
- **保持短**。30–60 行以内，超出的部分大概率被模型稀释。

把 SOUL.md 放进 git，改人格像改代码一样走 diff 和 commit。注意新规则对新会话生效，老会话不会自动继承，验证时记得开新会话。

## 踩坑点

- **形容词堆砌**：写满"聪明、友好、可靠"，模型只会输出平均值人格；
- **规则互相冲突**：既要求"有主见"又要求"顺着用户"，遇到冲突时行为不可预测，必须显式给优先级；
- **职责错位**：定时任务、工具用法别写进来——性格底线归 SOUL.md，工具经验归 TOOLS.md，多 agent 分工归 AGENTS.md；
- **只覆盖单聊**：群聊是重灾区，务必写清"何时沉默"；
- **一次写完就不管**：agent 出一次意外就补一条规则，不做这个闭环，文件很快失效。

## 可复用建议

- 建一份 10 条左右的固定测试问题集（含边界试探类），每次改完跑一遍，相当于**人格回归测试**；
- 每条规则旁注释来源，如"起因：xx 群聊抢话事件"，半年后你会感谢这行注释；
- 用"如果……就……"句式改写所有规则，可判定性会自然提升。

## 总结

SOUL.md 不是人设包装，而是给 agent 的一份行为契约。**写小、写准、进版本管理、出事就补**——做到这四条，agent 的表现会稳定得多。人格是长期资产，别用一次性 prompt 的方式对待它。
