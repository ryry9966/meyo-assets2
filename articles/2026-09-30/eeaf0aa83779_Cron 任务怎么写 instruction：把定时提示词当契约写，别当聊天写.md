## 背景

OpenClaw 的 cron 定时任务大概是社区里使用率最高的自动化能力之一：晨报、周报摘要、日程提醒、定时巡检。但翻看大家分享的配置，instruction 普遍写得很"聊天"——一句"每天早上帮我总结一下日程"就完事。这种写法在交互场景没问题，因为人在线，可以追问；放到 cron 里，问题就出来了。

## 问题出在哪

Cron 任务和对话有三个本质差异，instruction 必须围绕它们重新设计：

1. **无上下文**。定时任务运行在全新 session 里，agent 不知道你昨天聊过什么，甚至不知道"今天"指哪天——除非你明确给出时间锚点。
2. **无人值守**。跑错没人拦，数据失败没人补，输出漂移几天后你才注意到。
3. **一次成型**。没有追问机会，instruction 缺什么，agent 就靠猜什么。

## 我的做法：六段式契约

把 instruction 当接口契约写，固定六段结构：

```markdown
1. 时间锚点：以系统当前时间作为"今天"
2. 数据来源：调用哪个工具、查什么范围、什么参数
3. 处理规则：排序、去重、过滤、截断
4. 输出格式：结构、行数上限、语言
5. 失败降级：工具调用失败时标注"数据不可用"，禁止编造
6. 投递目标：发到哪个会话，无内容时怎么处理
```

以晨报为例的实际写法：

```markdown
以系统当前时间作为"今天"。
数据来源：调用 calendar 工具查询今天 08:00–22:00 的事件；
调用 mail 工具拉取最近 12 小时未读，仅保留标记为重要的。
处理：按时间排序、去重，每条压缩到一行。
输出：Markdown，分「今日日程」「待跟进」两节，总计不超过 15 行。
失败处理：任一工具调用失败，在对应小节写"数据不可用"，禁止推测或编造。
投递：结果发送到 <指定会话>；若无任何新内容，只发一句"今晨无新增"。
```

重点是第 5 段。没有它，模型在数据拿不到时大概率会"补全"一段看起来合理的内容——这是定时任务里最危险的失败模式，因为它不报错。

## 踩坑点

- **对话口吻**。"帮我看看……"隐含"有人会回答你"，agent 可能停下来等人确认，任务就静默挂了。
- **范围失控**。"总结所有未读消息"听起来合理，跑一周你就会删掉它。过滤条件必须写死。
- **忽略时区**。服务器若是 UTC，"早上 8 点"执行时的"今天"和你理解的不是同一天。先对齐 cron 调度与 instruction 里的时间口径。
- **重复投递**。任务重试可能导致同一结果发两遍。涉及发消息的任务，加一条"若已发送过则跳过"。
- **直接上调度**。新任务先手动触发跑通，看 3–5 次输出稳定后再开 schedule。

## 可复用建议

- 一个 cron 只做一件事，复杂流程拆成多个任务串联，别写"超级任务"。
- instruction 进 git，改一次提交一次，输出漂移时能回溯是哪次改动引入的。
- 每周翻一次 run 历史，按"哪段格式开始飘"定向修补，不要整段重写。
- 沉淀自己的六段模板，新任务复制改参数，五分钟上线。

## 总结

Cron 任务的 instruction 不是提示词，是契约：输入（时间锚点 + 数据来源）、输出（格式 + 投递）、异常（失败降级 + 幂等）都要写死。写得越像接口文档，任务越可预期；写得越像聊天，翻车越随机。
