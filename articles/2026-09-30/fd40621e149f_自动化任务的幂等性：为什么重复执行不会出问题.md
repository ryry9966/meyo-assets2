## 背景

OpenClaw 的典型用法之一是"挂机自动化"：定时跑一个 Agent 任务、用 webhook 触发 MCP 工具、让插件周期性同步数据。这些场景有个共同点——你无法保证任务只跑一次。调度器重试、网络超时后手动补跑、用户手滑再点一次，都是常态。

## 问题

非幂等的任务在重复执行时会放大副作用：

- 日报任务每次运行都 append 一份文件 → 目录里出现三份同一天的报告
- webhook 处理器收到上游重试 → 同一条消息被推送两次
- Agent 因超时重调"创建工单"的 MCP 工具 → 系统里出现重复工单

多数人第一次意识到问题，都是"任务显示成功，但数据翻倍"的时候。

## 做法

核心思路一句话：为每个任务定义**自然键**，让所有写操作变成 upsert。

1. **确定自然键。** 日报任务用日期，webhook 用消息 ID，同步任务用"源路径 + 内容 hash"。键必须来自业务事实，而不是运行时刻。
2. **生成物覆盖写，不追加。** 输出固定为 `daily-2024-06-01.md`，重跑就是覆盖。
3. **外部副作用带幂等键。** 调用不支持幂等的接口时，自己生成 `Idempotency-Key`（自然键的 hash），交给下游去重。
4. **状态落盘。** 用一个 JSON 或 SQLite 记录"这个键处理到哪一步"，中断后从断点续跑，而不是从头再来。
5. **原子写。** 先写临时文件再 rename，避免重跑时读到半成品状态。

插件里的常见模式：

```python
key = f"daily:{today}"            # 自然键
if state.get(key) == "done":
    return                        # 已完成，直接跳过
result = do_work()
write_tmp_then_rename(output(key), result)
state[key] = "done"
```

## 踩坑点

- **"先查再写"不是真幂等。** 两个实例并发跑，都查到"没做过"，然后都写。要么加文件锁或数据库唯一约束，要么直接接受 upsert 语义，让后写覆盖先写。
- **自然键里混入了时间戳或随机数。** `report-{now}.md` 每次都不一样，等于没做。另外注意时区：UTC 和本地时间的"今天"可能不是同一天。
- **重试发生在错误的层级。** Agent 外层重试一次，MCP 工具内部又重试一次，两层互不知情。幂等键要贯穿到底，工具识别到同键应直接返回上次结果。
- **状态文件损坏比没有状态更糟。** 半写的 JSON 会让任务永远卡在"进行中"。原子写之外，启动时还要校验并能回退。
- **幂等窗口有期限。** 状态记录保留 7 天没问题，但依赖消息 ID 永久去重的场景，要确认上游 ID 不会复用。

## 可复用建议

- 设计任何自动化任务前先回答："这个任务跑两遍，世界状态会变吗？"答案是会，就先补幂等设计，再上线。
- 把幂等键写进日志。排查"为什么执行了两次"时，可以按 key 串起两次执行的完整链路。
- MCP 工具尽量提供 upsert 语义（create_or_update），把幂等做进工具层，Agent 层就天然安全。
- 定期挑一个历史任务完整重跑一遍作为演练，能提前暴露隐藏的非幂等写路径。

## 总结

幂等性不是锦上添花，而是自动化的入场券。调度器重试、网络抖动、人的手滑都是常态，任务设计的起点应该是"重复执行是安全的"。记住三件事：**自然键、覆盖写、状态原子落盘**。做到这三点，你的 OpenClaw 定时任务才敢真的无人值守。
