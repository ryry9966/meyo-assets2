## 背景

E2E 测试大概是前端工程里"最该写但最没人爱写"的部分：用例模式重复、选择器脆弱、改一版 UI 全线飘红。AI 出现后，"让它帮我生成测试代码"是很多人的第一反应，但实际效果往往一般——生成的代码看着像回事，一跑就红。

在 OpenClaw 里折腾了一段时间后我发现，问题不在"AI 会不会写"，而在"AI 只写不跑"。这篇文章记录一套 agent + MCP 的协作流程，目标是让 agent 交付的测试是**跑绿过的**，而不是"看起来对"的。

## 直接生成的三个问题

1. **选择器幻觉**：模型默认编造 `data-testid="submit-btn"` 这类选择器，页面上根本不存在。
2. **断言太浅**：只断言"页面加载成功"，不验证业务状态（比如订单是否真的创建）。
3. **无法自证**：AI 不知道代码能不能跑通，交付即终点，验证成本全转嫁给人。

## 做法：从"生成"改成"探索 → 骨架 → 编码 → 闭环"

先给 agent 配三样工具：Playwright MCP（浏览器操作）、测试运行器（终端）、仓库读写。流程分四步：

**第一步，先探索再写码。** 让 agent 用浏览器工具打开目标页面，导出可访问性树 / DOM 结构，基于真实结构取选择器。强制用 `getByRole`、`getByLabel` 这类语义定位，禁止裸 CSS 路径。

**第二步，先骨架后实现。** agent 先输出用例步骤和断言点清单（自然语言），人确认业务语义没偏，再让它落成 Playwright 代码。这一步能拦掉大半"跑得通但测错了"的用例。

**第三步，闭环自跑。** agent 自己执行 `npx playwright test`，读失败输出，修选择器、改等待策略，然后重跑。设一个迭代上限（我设 5 轮），防止无限循环。

**第四步，人工复核断言。** agent 保证"能跑绿"，人保证"该测的测了"。

## 踩坑点

- **测试红了不一定是测试的错。** 最危险的情况是 agent 反复改断言把用例"迁就绿"——那可能暴露的是真 bug。我在提示词里写死：疑似产品缺陷时停下报告，禁止改断言让测试通过。
- **警惕硬等待。** AI 很爱写 `waitForTimeout(3000)`，环境一慢就 flaky。要约束它只用条件等待（`waitFor` / `expect` 轮询）。
- **测试数据不固定，agent 会到处打补丁。** 数据漂移导致用例偶挂时，它倾向到处加 sleep 和 try-catch。根因是数据，让它去建 fixture，而不是糊补丁。
- **上下文别塞满。** 每轮只回贴失败用例名 + 错误摘要，不要全量日志，否则几轮就爆上下文。

## 可复用建议

- 把"先快照、后骨架、跑绿才算完成"固化成一段 Skill / 系统提示词，一次调好反复用。
- 把测试运行器包成 MCP 工具，返回结构化失败摘要，比喂原始日志省一半 token。
- 给 agent 划边界：只读产品代码、只写测试文件，避免它顺手"修复"业务代码。
- 一个 PR 只覆盖一条业务路径，review 成本可控。
- 回归可以交给定时任务：夜间自动跑一遍，天亮看 agent 留下的失败归因。

## 总结

这套流程跑下来的体感是：AI 写 E2E 的真正价值不在"替你写代码"，而在把"写—跑—修"的循环从小时级压到分钟级。agent 承担机械闭环，人保留业务判断——测试该测什么、红线在哪，这两件事目前还是别外包。
