# OpenClaw 多模型路由实战：GPT 和本地模型的分工边界

## 背景

OpenClaw 这类常驻个人 Agent，和一次性脚本最大的区别是调用频率：消息监听、定时任务、MCP 工具编排，一天下来几百上千次模型调用很正常。全部走 GPT 这类云端模型，成本和延迟都会变成问题；全部换成本地小模型，复杂任务质量又明显掉档。多模型路由不是为了炫技，而是把“贵而强”和“便宜可控”放到各自合适的位置。

## 问题

我们最初的配置很粗暴：主 Agent 全量走 GPT，月底账单难看；后来一刀切到本地模型，工具调用成功率从 95%+ 掉到 70% 附近，MCP 工具参数填错、JSON 输出坏掉的情况明显变多。本质问题是：不同任务对模型能力的要求差异极大，但当时没有路由层，只有一个模型选择。

## 做法

1. **先做任务分级。** 把 Agent 内的调用分成三类：编排类（多步规划、复杂工具链、长上下文摘要）、高频类（分类、打标签、格式化、简单问答）、敏感类（涉及个人数据、聊天记录的任务）。
2. **声明多个 provider。** 在 OpenClaw 的模型配置里同时接入云端一家（GPT 系列）和本地一个（Ollama 跑 qwen 或 deepseek 蒸馏版）。
3. **按 Agent 粒度指定模型。** 主对话 Agent 用 GPT 兜底，负责规划和最终回复；后台的预处理、日志摘要、通知文案等子 Agent 全部指向本地模型。fallback 链在本地超时或报错时回落云端——注意这是可用性兜底，不是质量兜底。
4. **敏感任务写死规则。** 直接在路由规则里固定走本地，不做智能判断。隐私边界不该依赖一个分类器的输出。
5. **小评测集持续验证。** 每个任务类型准备 20 条左右固定用例，路由调整前后对比成功率、平均延迟、月成本三个数。

## 踩坑点

- **别让本地小模型做编排。** 7B 级模型的 function calling 稳定性远不如 GPT，多步工具链中间一步参数填错，后面全是垃圾。经验是：本地模型只做“叶子任务”，不做“调度任务”。
- **上下文窗口是隐形杀手。** 本地模型 context 短，长对话被截断时不报错，只会答非所问。路由规则里加一条长度预判，超阈值强制走云端。
- **fallback 会掩盖故障。** 本地挂了自动回落云端很好用，但也把问题埋住了。日志里必须显式记录每次实际使用的模型，否则排障时会误判。
- **量化版本差异大。** 同名模型的 Q4 量化在工具调用这类结构性输出上和 FP16 差距明显，别只跑几轮对话测试就上线。
- **embedding 别混用。** 检索侧一半索引是云端 embedding、一半是本地，召回质量会莫名下降，全链路统一一个 embedding 模型。

## 可复用建议

- 路由策略写成一页表：任务类型、使用模型、理由、回退方案。谁改配置都能看懂。
- 判断“能否下沉到本地”只看两条：输出是否对结构化要求低（自然语言即可）、失败代价是否可接受。两条都满足才迁。
- Prompt 写成模型无关的，不在系统提示里绑死某家的风格，切换成本会低很多。
- 模型版本 pin 死。云端模型静默更新也可能改变工具调用行为。

## 总结

多模型路由的核心不是省多少钱，而是给每次调用找到能力与成本的匹配点。OpenClaw 的 Agent 粒度配置足够支撑这套做法：云端模型守住编排和复杂推理的质量底线，本地模型吃掉高频、敏感、低风险的长尾任务。先分级、再路由、持续用小评测集验证，比一上来就上“智能路由”靠谱得多。
