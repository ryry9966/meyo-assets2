## 背景

用 OpenClaw 做日常自动化，最常见的瓶颈不是模型能力，而是主会话上下文。让它调研三个库的文档、审查十个模块、批量处理一批日志——串行跑下来，主上下文塞满中间产物，之后每轮对话都背着这些包袱，慢、贵、还容易"忘事"。

OpenClaw 提供了 subagent 机制（如 `sessions_spawn` 拉起子会话），但很多人要么没用，要么一开就翻车。这篇记录我们团队摸索出的一套稳妥用法。

## 问题

单 agent 串行执行有三个结构性问题：

1. **上下文污染**：中间结果全部堆在主会话，真正重要的结论被稀释；
2. **串行耗时**：互不依赖的任务排队执行，墙钟时间是各任务之和；
3. **角色混乱**：主 agent 既是调度者又是执行者，顾此失彼。

## 做法

**第一步：判断任务可否并行。** 三个标准——子任务之间没有共享写状态；输入可以独立获取；输出能被结构化汇总。读多写少的任务（调研、审查、批量分析）最适合，涉及写文件的任务要谨慎。

**第二步：拆分下发。** 每个子 agent 的 prompt 固定四要素：任务范围、可用工具白名单、约束（时间/长度）、输出格式。子 agent 看不到父会话，必要上下文必须显式写进去，一句"按我们之前讨论的来"等于没说。

**第三步：限定并行度。** 我们控制在 2~4 个。并行度再高，容易触发限流，也超出自己盯得住的范围。

**第四步：收敛汇总。** 要求子 agent 只返回结构化摘要——结论、依据、风险点三段式，原始细节留在子会话里。主 agent 拿到的是干净的结果，不是几千字流水账。

**第五步：失败处理。** 明确要求子 agent 汇报执行状态。单个子任务失败就单独重试，不要整体重跑。

## 踩坑点

- **上下文隔离**：子 agent 不知道父会话聊过什么，漏传背景是最常见的失败原因；
- **并行写同一文件必冲突**：写操作要么串行，要么按文件分区给不同子 agent；
- **不限输出格式**，子 agent 会用长文回报，主上下文再度被污染，等于白拆；
- **限流**：并行请求集中打出，错误信息常常比结果先到，做好退避重试；
- **成本是乘法**：每个子 agent 有独立上下文，token 消耗不是加法，拆之前先估算。

## 可复用建议

- 准备一个固定的子 agent prompt 模板：角色 / 范围 / 工具白名单 / 输出 schema，每次复用只改变量；
- 输出格式优先 JSON 或固定小节，方便主 agent 程序化汇总；
- 保留子会话日志，出问题时能回放定位，别让子 agent 黑盒运行；
- 主 agent 只做调度和裁决，忍住不要亲自下场干活；
- 收益最大化的场景：多源调研、批量代码审查、多文件独立重构。

## 总结

Subagent 不是银弹，本质是把"调度"和"执行"拆开。任务能切成互相独立的块时，并行收益非常明显；任务本身强耦合时，强行并行只会制造冲突和调试地狱。判断标准永远是：独立输入、独立执行、可汇总输出。满足这三条，再拆不迟。
