# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

Agent 接上 MCP 之后，事情起了变化：工具调用不再只是"生成一段文本"，而是真正产生副作用——写文件、调接口、发消息、改配置、花钱。框架侧（包括 OpenClaw 这类）默认往往给 agent 较大自由度，权限边界经常只靠 system prompt 里一句"请谨慎操作"。Demo 里够用，接到真实生产环境就不够了。

## 问题

实际跑起来，翻车通常是两个方向：

- **该问不问**：agent 自作主张删了数据表、给客户群发了消息、把预算花超了。
- **不该问老问**：每一步都要人点确认，人很快退化成"无脑批准机"，确认机制形同虚设——这比不确认更危险，因为它制造了"我们有权限控制"的假象。

所以核心问题不是"问还是不问"，而是缺一个**可执行的判定函数**。

## 做法一：先给动作分级

按两个轴划分：**可逆性** 和 **影响半径**。

| 级别 | 特征 | 策略 |
|---|---|---|
| T0 | 只读、本地、纯查询 | 自动执行，记日志 |
| T1 | 可逆写操作（沙箱内建文件、开分支、存草稿） | 自动执行，保留 diff |
| T2 | 对外生效或不可逆（发送、发布、删除、花钱、改生产配置） | 必须问人 |
| T3 | 高危凭据（支付密钥、root、批量删除） | 不给 agent，走人工通道 |

## 做法二：把边界落在工具层，不是提示词层

1. **工具注册时声明 capability 和 tier**，MCP server 或框架按 tier 决定路由：自动放行、记录、还是触发确认。
2. **T2 工具强制走 dry-run**：先输出"将做什么、改哪里、如何回滚"，人确认后才真正调用。
3. **确认卡片必须有信息量**：目标、diff、影响范围、回滚命令。拒绝"我可以继续吗？"这种问法——人类没法基于它做判断。
4. **授权带时效**："本会话内允许"，而不是永久放行。检测到异常（调用频次突增、参数越界）自动降级回逐次确认。

## 踩坑点

- **确认疲劳**：问得太碎，人开始盲批。合并批量操作为一次确认，低风险操作攒起来事后审计。
- **模糊提问**：不带上下文的确认等于让人掷硬币。
- **权限蠕变**：一次"就这次吧"的例外如果被写回配置，就成了永久规则。例外必须显式过期。
- **凭据泄漏**：env 里的 key 被读进上下文，agent "知道"了就能用。高危凭据放框架侧受控通道，不进模型上下文。
- **只测快乐路径**：演练时专门测"agent 拿到任务无关工具时会怎样"，观察它会不会越界，而不是只验证它能完成任务。

## 可复用建议

- 每个 skill 上线前，标注其全部工具的 tier；
- 对外生效的调用默认 deny，显式 allow；
- 确认请求缺 diff 或回滚方式，框架直接拒发；
- 所有授权带会话/时间范围；
- 审计日志不只记"批了什么"，还记"当时 agent 看到了什么"；
- 每月复核 allowlist，删掉没人用的授权。

## 总结

权限边界不是 prompt 工程的附属品，而是产品和工程决策。目标不是让 agent 问得更少或更多，而是让它**在对的时刻、带着足够的信息去问**。人的注意力是稀缺资源，应该只花在真正不可逆的那几个动作上。
