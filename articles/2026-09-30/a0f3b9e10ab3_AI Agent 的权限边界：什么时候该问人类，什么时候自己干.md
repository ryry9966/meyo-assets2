## 背景

给 OpenClaw 挂上几个 MCP server 之后，agent 的能力曲线会陡然上升：能读文件、跑 shell、调外部 API、发消息。能力上来之后，第一个撞上的往往不是能力问题，而是权限问题——它到底哪些事可以自己拍板，哪些必须停下来问人？

## 问题：两个极端都不可用

实践中常见两种失败模式：

- **过度请示**。每一步都弹确认，人很快变成点"允许"的机器。一周后所有人都形成了肌肉记忆式同意，审批沦为形式。
- **过度放权**。agent 悄悄执行了一条 `rm -rf`，或者把未确认的草稿直接发给了客户群。一次事故就足以摧毁整个自动化方案的信任。

核心矛盾在于：问得太多等于没问，问得太少等于裸奔。

## 做法：按"可逆性 × 影响半径"分级

不要用"看起来危不危险"做判断，用两个可量化的维度：**能不能撤销**、**波及范围是否超出工作区**。由此把所有工具调用分成三级：

| 级别 | 特征 | 例子 | 策略 |
|---|---|---|---|
| L0 | 只读 | 读文件、list、查询 API | 直接干，事后汇报 |
| L1 | 可逆写 | 工作区内建文件、本地 commit、跑测试 | 直接干，留日志 |
| L2 | 不可逆或出圈 | 删数据、push、发邮件/消息、计费 API、改密钥 | 必须人批 |

落地五步：

1. **盘点工具**：逐个给 MCP tool 标级，写进网关 / tool policy 配置，不靠模型临场判断。
2. **L2 走强制 gate**：确认逻辑在 harness / 网关层实现，模型只能发起请求，不能自己放行。
3. **带上下文地问**：审批界面展示将执行的具体命令、diff、目标地址，而不是一句"可以继续吗"。没有上下文的确认请求本身就是噪音。
4. **默认拒绝**：审批超时即取消。人不在，任务就停，绝不默认放行。
5. **全量留痕**：每次 gate 的请求内容、决定、审批人写日志，事后可审计。

## 踩坑点

- **把"读"当安全**。不少 GET 并非无副作用：触发 webhook、消耗计费额度、写审计记录。接入新工具时先验证，别凭方法名定性。
- **批量授权**。"本会话内都允许"对 L1 合理，对 L2 是灾难——删库只需要一次同意。
- **Prompt injection 穿透**。恶意内容可以诱导模型"觉得"这事不用问。这正是 gate 必须放在系统层的原因——模型自律不是边界，只是装饰。
- **跳过 dry-run**。让 L2 操作先输出执行计划再交人批，能拦掉大部分事故，成本几乎为零。

## 可复用建议

- 新工具默认按 L2 接入，观察一两周再降级；降级容易，回滚信任很难。
- 分级表作为团队共享配置维护，别让每个人自己发明标准。
- 每次事故后回看 gate 日志，只问一个问题：这个操作当初为什么没被拦住？

## 总结

权限边界本质上不是信任问题，而是接口设计问题。可逆且不出圈的事让 agent 自己干、留好日志；不可逆或影响出圈的事必须经人审批，且由系统层强制执行、带上下文提问、默认拒绝。做到这几点，自动化才敢真正放手。
