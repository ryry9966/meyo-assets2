## 背景

Agent 接上 MCP 和插件之后，能力边界从"生成文本"扩展到了"执行动作"：读写文件、调内部 API、发消息、部署服务。能力上得很快，但"哪些该自己做"这件事，多数项目并没有明确答案，往往靠系统提示词里一句"请谨慎操作"兜底。

## 问题

实际跑起来只有两种失败模式：

1. **事事都问**。每写一个文件都要确认，用户退化成人肉按钮，自动化的价值归零。
2. **自作主张**。在错误目录执行了删除、把测试配置推到生产、给整个通讯录发了邮件。这类事故的共同点不是模型笨，而是权限边界没有被定义过。

所以这可以收敛为一个工程问题：给每个工具调用一个明确的前置判断——**自动执行、询问后执行、直接拒绝**。

## 做法：按风险给工具分层

不要按工具类型分，按**出错后果**分。每个接入的 MCP 工具过一遍四个问题：可逆吗？影响范围多大？有成本吗（钱/数据/信任）？会碰到凭据或他人吗？

据此分四层：

- **L0** 只读、本地、沙箱内：直接自动执行，记日志。
- **L1** 可逆写操作（git 覆盖内的文件、可回滚的迁移脚本）：自动执行 + 变更留痕，保证能一键回退。
- **L2** 不可逆或有外部效应：发消息、删数据、花钱、动生产。Agent 必须先给出计划（做什么、为什么、影响面、回滚方式），人批准后才执行。这是"问人"的核心区。
- **L3** 凭据、权限配置、安全策略：默认硬拒绝，改动走人工流程，不进入 Agent 的可调用面。

落地顺序：盘点全部工具 → 逐个打层 → **在网关/插件层配置确认开关，而不是只写进系统提示词** → 给 L2 做统一的确认卡片（内容、理由、diff、回滚命令）→ 全量审计日志。

## 踩坑点

- **确认发生在执行之后**。常见于工具内部的重试逻辑：第一次调用失败自动重试，第二次就真发出去了。确认必须卡在真正产生副作用的调用之前。
- **确认卡片没有信息量**。只弹"是否继续"，三个月后用户就是无脑点确认。宁可要求 Agent 附上 diff 和回滚命令，也不给纯 yes/no。
- **权限只写在提示词里**。提示词约束会被长上下文稀释，也可能被注入绕过。要落在工具网关层：未打标的 L2 工具默认拒绝。
- **一次性授权被复用**。用户批准了"删这 10 个文件"，Agent 顺手把同批次的 200 个也删了。授权应绑定参数指纹，参数变了就重新问。
- **调试配置带上线**。演示时图省事全开，忘了改回来。权限配置建议进版本管理，变更走 review。

## 可复用建议

一个快速判断清单，拿去直接用：

- 能撤销吗？能→降一层，不能→升一层。
- 出错的最坏结果，你能当面解释清楚吗？不能→问人。
- 这个动作每天会发生 50 次吗？高频动作要往 L0/L1 压，否则确认疲劳会摧毁整个机制。
- 拿不准时，问人的成本永远低于回滚失败的成本。

另外，把"问人"设计成 Agent 的正常能力而不是失败：**提案式交互**（Agent 给方案、人批注）比打断式弹窗体验好得多，审批记录也天然成为项目文档。

## 总结

权限边界不是给模型上枷锁，而是把信任显式化：可逆且小范围的自己做并留痕；不可逆或有外部效应的先提案后执行；碰凭据的硬拒绝。规则放在工具层而不是提示词里，确认带上下文而不是裸 yes/no。做到这几点，Agent 才敢真正放手用。
