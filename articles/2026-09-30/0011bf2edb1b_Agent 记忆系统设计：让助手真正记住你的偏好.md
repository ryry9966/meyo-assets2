## 背景

在社区里做 Agent 的朋友大概都遇到过类似场景：你反复告诉助手"项目用 pnpm 不用 npm""commit message 用中文"，但换个会话它又忘了。根因很简单——LLM 本身无状态，模型上下文就是它全部的记忆。要让助手真正记住偏好，得在 Agent 框架层自己搭记忆系统。这里分享我们在基于 MCP 工具链的 Agent 上落地的一套最小可行方案。

## 问题

直接上手会撞到三个典型坑：

1. **全量堆砌**：把历史对话塞进一个 memory 文件随 system prompt 注入，几天后文件膨胀到几万 token，关键偏好被噪声淹没，注入成本也失控。
2. **只写不删**：偏好会变。用户三个月前喜欢 REST，现在全面转 GraphQL，旧记忆和新指令冲突，模型行为变得随机。
3. **检索不准**：纯向量检索对"项目名、版本号、构建工具名"这类精确匹配很弱，召回一堆语义相近但不相关的内容。

本质上，记忆是"写入策略 + 检索策略 + 生命周期管理"的工程问题，不是接一个向量库就完事。

## 做法

我们的方案分四步：

**1. 分层存储**
- 核心档案（profile）：稳定偏好，如技术栈、代码风格、时区，控制在几十条内，每次会话固定注入；
- 情景记忆（episodic）：按会话生成的摘要，带时间戳，按需检索；
- 工作记忆（scratch）：单任务内的临时状态，会话结束即清理。

**2. 明确写入触发。** 不要让模型每轮自由决定写不写，行为会不稳定。我们用两个触发点：一是显式修正——用户说"记住""以后都用 X"，立即写入；二是会话结束时跑一次抽取，从对话中提炼结构化条目。每条记忆是自包含的一句话，附类型、来源、置信度和时间戳，而不是原始聊天记录。

**3. 检索与注入预算。** 通过 MCP 暴露 `memory_search` / `memory_write` 两个工具。检索先走标签和关键词过滤，再用向量召回兜底，取并集重排。注入设硬预算：核心档案加检索结果合计不超过 800 token，超了按"最近使用时间 + 置信度"截断。

**4. 冲突与清理。** 同一主题的新记忆覆盖旧的，不追加；超过 90 天未被召回的条目移入归档区；每月跑一次合并去重。记忆文件本身用 git 管理，diff 可审。

## 踩坑点

- **记忆条目不写来源**：模型推断出的"用户偏好"会被二次强化，务必区分是用户显式声明还是模型推断，推断的置信度要打折。
- **去重缺失**：同一条"用 pnpm"被写了七遍，检索时全部召回，等于变相堆砌。写入前先按主题查重。
- **注入预算不设上限**：记忆越多越好是错觉，挤占任务上下文反而降质。
- **没有删除入口**：给用户一个"忘掉 X"指令，既是隐私需要，也是纠错手段。敏感信息坚持本地存储。

## 可复用建议

- 从一个 markdown 档案文件 + 会话摘要起步，先跑通写入—检索—清理闭环，再考虑向量库，不要一上来过度设计。
- 记忆条目写成"用户在 X 场景下偏好 Y"的独立断言，方便检索和冲突判断。
- 用命中率衡量效果：被召回的记忆是否真的影响了输出？定期人工抽查比盯 token 数有用。

## 总结

让 Agent 记住偏好，关键不在存储选型，而在三件事：写入有触发、注入有预算、记忆有生命周期。先把最朴素的档案文件做扎实，分层和向量检索是后续的自然演进。记忆系统做到最后，比拼的是克制——能不记的不记，该忘的及时忘。
