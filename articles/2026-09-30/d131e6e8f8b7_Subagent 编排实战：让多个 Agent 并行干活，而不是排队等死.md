## 背景

用单个 Agent 干长活的人大概都遇到过这种场景：「调研这 8 个 MCP server 分别提供哪些工具，整理成对比表」。主 Agent 一个个读仓库、调工具、贴日志，40 分钟过去，上下文塞满中间产物，最后写总结时已经开始"失忆"——前面的搜索结果早被挤出了注意力窗口。

这类任务的共同特征很明确：**子任务之间互相独立，且以"读"为主**。这正是 subagent 编排的用武之地。

## 问题

单 Agent 串行跑长任务，实际会撞上三堵墙：

1. **上下文污染**：搜索结果、文件全文、报错日志全堆在主对话里，真正重要的任务目标反而被稀释；
2. **串行瓶颈**：8 个独立调研排成一列纵队，总耗时等于全部之和；
3. **失败连锁**：链条中间一次工具调用抽风，后面全盘皆输，只能从头再来。

## 做法

我目前的编排流程分五步：

1. **拆任务**。先把需求摊开，圈出彼此独立的子任务，每个写清楚输入和期望输出。判断标准很朴素：这个子任务不看别的子任务的结果能不能干？能，就可以并行。
2. **写自包含的 brief**。subagent 看不到你和主 Agent 的对话历史，派发时必须给完整上下文：目标、范围、禁止事项、返回格式，一样不能省。
3. **并行派发，设并发上限**。同一批 fan-out 3~5 个，每个子任务设 token 和时间预算，防止个别 subagent 失控烧钱。
4. **要求结构化返回**。明确要求 subagent 只返回摘要或固定字段的 JSON，而不是原始抓取内容——这一步是主上下文不爆炸的关键。
5. **抽查验证**。subagent 说"done"不代表真做完了，关键结论至少抽查一两条来源。

## 踩坑点

- **brief 不自包含**：只派一句"帮我查一下 X"，subagent 只能瞎猜范围，返回一堆答非所问的东西；
- **让 subagent 回传原始内容**：主上下文照样被塞爆，等于白拆；
- **并行写同一批文件**：两个 subagent 同时改一个文件，后写的覆盖先写的。写操作要么串行，要么按文件分区、各管一段；
- **有隐藏依赖还强并行**：下游拿到的是上游"还没生成"的结果，失败得莫名其妙；
- **没有失败隔离**：一个 subagent 挂了就整批重跑。正确姿势是收集各路结果和报错，只重试失败的那几个。

## 可复用建议

- **一句话判断**：读多写少、互不依赖 → fan out；写共享状态、有先后依赖 → 串行或分区；
- **brief 模板固定四段**：目标 / 范围与边界 / 禁止事项 / 返回格式，照着填就不会漏；
- **并发从 3~5 起步**，别一上来开 20 个，先把限流和成本摸清楚；
- **留日志**：每个 subagent 的 brief 和返回值落盘，出问题时复盘全靠它；
- **三个常用模式**：调研类用 fan-out/fan-in；写代码用 builder + critic（一个干、一个审）；批量处理文件用 map-reduce 按列表切分。

## 总结

Subagent 编排的本质是**上下文隔离 + 并行执行**，不是魔法。它不会让单个 Agent 变聪明，但能让该并行的活并行跑，把主 Agent 的注意力留给真正需要判断的部分。编排水平的高低，几乎完全取决于拆任务的颗粒度和输出契约定得严不严。建议从小任务开始：下次遇到要读五个以上来源的活，先试一次 fan-out，体感会很直接。
