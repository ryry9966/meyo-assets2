## 背景

把模型搬到本地跑，动机通常有三个：数据不出门、没有按 token 计费的心理负担、给自动化流程提供一个不限速的 API。对写 Agent 和 MCP 工具链的人来说，本地模型还有个隐藏价值：系统提示词和调用频率可以随便折腾，不用心疼额度。我在一台 32GB 内存 + 12GB 显存台式机上折腾了两个月，把 7B 到 32B 的模型过了一遍，记录一下能稳定落进工作流的做法。

## 问题

网上教程大多停在"跑通 demo"：终端对话正常就收工。但接进 Agent 之后完全是另一回事：工具调用要模型稳定输出合法 JSON，长上下文不能静默丢内容，自动化场景还要考虑并发。这三点恰好是消费级硬件 + 量化模型最薄弱的地方。

## 做法

1. **先算显存账**。经验公式：模型权重 + KV cache ≈ 显存占用。Q4_K_M 量化的 7B 约 4.5GB，14B 约 9GB，32B 约 19GB。8GB 卡跑 14B Q4 勉强，上下文一拉长就爆。
2. **选型**。中文场景 Qwen 系列在 7B/14B/32B 三档都比较稳；显存不够可以试 MoE 结构的模型，激活参数少，部分层 offload 到 CPU 后速度尚可。
3. **起服务**。Ollama 上手最快，llama.cpp 的 llama-server 更可控（能调 GPU 层数、上下文大小）。两者都暴露 OpenAI 兼容接口，Agent 侧基本零改动。
4. **接 Agent/MCP**。把 base_url 指到本机端口即可。重点验证工具调用：准备 5-10 个真实任务（含多工具串联），跑 batch 统计 JSON 解析成功率。
5. **压测**。观察 tokens/s 和显存峰值，记录能承受的最大并发——消费级卡基本就是 1 到 2。

## 踩坑点

- **默认上下文太小**。Ollama 默认 num_ctx 只有 2048/4096，超长输入会被静默截断，RAG 场景里表现为"检索到了但答非所问"。务必显式设置。
- **KV cache 比想象中吃显存**。32B 模型开 32K 上下文可能再加 8-10GB，量化省下的空间全交给上下文了。
- **量化等级对工具调用的影响大于对聊天的影响**。Q4 以下聊天还行，函数调用开始出现字段缺失、参数幻觉。Agent 场景建议 Q5/Q6 起步，或者换小模型 + 更高精度。
- **并发能力弱**。两个 Agent 同时打过来会排队甚至 OOM。前面加个简单请求队列，比调参管用。
- **散热**。持续推理下笔记本和 Mac 都会降频，跑分成绩和长跑表现是两回事。

## 可复用建议

- 建自己的评测集：10 个带工具调用的真实任务，每次换模型/量化跑一遍，看成功率和耗时，比看榜单有用。
- 双模型策略：小模型（7B）做意图路由和格式化，大模型（14B/32B）做推理，延迟和显存都能压下来。
- 模型文件用版本化目录管理，配置里写死哈希，避免"上周还好好的"。
- 日志保留原始请求/响应，本地模型行为飘了能回溯。

## 总结

本地部署的门槛不在"跑起来"，而在"能进生产工作流"。把显存账算清、把上下文参数显式化、用自己的任务集验收工具调用，一台 12GB 显存的机器就能稳定托起日常 Agent 自动化。它替代不了云端旗舰模型，但在隐私敏感、高频调用、离线场景里，是一条值得认真维护的备用生产线。
