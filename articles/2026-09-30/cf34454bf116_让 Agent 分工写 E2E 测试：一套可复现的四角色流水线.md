## 背景

E2E 测试是那种"都知道该写，但永远排不上优先级"的活。原因很实际：一条稳定的端到端用例，要先摸清页面结构、选择器、异步行为，再处理测试数据和幂等性，单条成本高，页面一改就脆。

LLM 出现后，"让 AI 写测试"看起来很诱人，但试过的人大多撞过同一个坑：一次性把需求丢给模型，它会自信地写出根本不存在的选择器、形同虚设的断言，外加一堆 `waitForTimeout(3000)`。问题不在模型不会写测试，而在于它没有现场信息，也没有反馈回路。

最近我在 OpenClaw 里用多 Agent 协作试了这件事，核心思路是：不让一个 Agent 包办，拆成采集、编写、执行、审查四个角色，用 MCP 工具和落盘文件串起来。跑通两条核心路径后，把经验整理出来。

## 单 Agent 一次性生成为什么不行

- **选择器幻觉**：模型凭训练记忆猜 `.submit-btn`，真实 DOM 里可能是 `data-testid="submit"`。
- **测试通过 ≠ 测到了**：断言很弱，甚至走进 catch 分支也算绿。
- **没有修复闭环**：一次生成，失败后靠人肉读日志，AI 的优势归零。
- **上下文超载**：把整站代码塞进一个对话，很快失效。

## 做法：四角色协作流水线

**1. 采集 Agent（挂浏览器类 MCP）**
给它 Playwright MCP 之类的浏览器工具，让它像真人一样走一遍目标路径：打开页面、点击、填表。要求它把每一步的真实选择器、可见文案、关键请求、需要等待的信号，落盘成 `facts.md`。这一步是地基——后续代码只准引用这份文件里的选择器，不许自己编。

**2. 编写 Agent（无浏览器权限）**
输入是 `facts.md` 加仓库里的测试规范（目录结构、fixture、POM 约定）。限定框架和断言库，弱断言直接打回。它没有浏览器权限，想编选择器也编不了，只能老老实实引用事实清单。

**3. 执行 Agent（有跑测试权限）**
跑 `npx playwright test`，读失败输出并区分两类问题：代码 bug 回给编写 Agent 修；环境或数据问题记录下来，不硬修。设循环上限，比如 3 轮，超了就停下交给人。

**4. 审查 Agent**
只做减法：扫硬等待、被注释的断言、catch 里吞掉的失败、对执行顺序的依赖。产出一份简短意见，人最后只看这份意见和 diff。

角色之间全部通过文件传递，不依赖对话记忆——任何时刻中断都能接上，人也得以在任意节点插入检查。

## 踩坑点

- **最隐蔽的坑：执行 Agent 为了"变绿"改断言**。生成与验证必须分离，执行 Agent 没有改测试代码的权限，只能改实现代码或上报。
- **采集 Agent 走错路径**：登录态没准备好，采回来一堆登录页选择器。先备好 fixture 和种子数据，再放 Agent 进浏览器。
- **token 消耗超预期**：主要在执行循环。控制单轮注入量，只喂相关 spec 的失败日志。
- **动态内容**：时间戳、随机 ID、列表顺序，要求编写 Agent 用正则或排序后断言。这类规则直接写进它的系统提示词，比事后修快得多。

## 可复用建议

- 每个角色独立系统提示词加工具白名单，权限最小化。
- `facts.md` 是给人看的第一现场，保留人工审核环节。
- 从一条最核心的路径开始跑通全流程，不要一上来圈十个页面。
- 把打回标准（弱断言、硬等待、顺序依赖）固化成审查 Agent 的 checklist，沉淀进仓库。

## 总结

这套流程的价值不在于"AI 替你写测试"，而在于把 E2E 最贵的部分——摸清页面真实结构和修复回路——自动化了，同时用职责分离避免 Agent 自欺欺人。四个角色各配一份提示词加一组 MCP 工具，迁到别的仓库基本只是改约定。AI 写测试的上限，取决于你愿不愿意给它真实信息和失败反馈。
