## 背景

玩 Agent 和 MCP 久了，两个问题会越来越明显：一是云 API 账单随自动化任务频次线性上涨；二是定时任务经常要碰隐私数据——本地文件、聊天记录、内网信息，全扔给云端不放心。所以我的思路是：核心决策链路走云上强模型，高频、低难度、涉敏感数据的自动化任务下沉到本地模型。这篇记录我在一台 12GB 显存的家用机上把这条链路跑通的完整过程。

## 问题

家用硬件的现实约束有三个：显存有限、上下文吃紧、以及最容易被低估的一点——**Agent 场景对 tool calling 的要求远高于聊天**。模型在聊天窗口里对答如流，不代表它能稳定产出合法的工具调用 JSON。很多"8G 内存也能跑"的宣传，在多轮工具循环的真实负载下基本不成立。

## 做法

**1. 先算显存预算，再选模型。** 粗略公式：权重 ≈ 参数量 × 量化位宽 ÷ 8，另留 1.5–2GB 给 KV cache 和运行时开销。Q4 量化下 7B 约 4.5GB、14B 约 9GB。8GB 卡选 7–8B，12GB 可上 14B，24GB 以上再考虑 32B。

**2. 选运行时。** 图省事用 Ollama，自带 OpenAI 兼容端点；想细调采样和分层参数用 llama.cpp 的 `llama-server`；显存充裕且需要并发的再上 vLLM。家用场景前两者够了。

**3. 起服务并接入。** `ollama serve` 后端点是 `http://127.0.0.1:11434/v1`，把 Agent 框架的 provider 指过去即可：

```yaml
provider: openai-compatible
base_url: http://127.0.0.1:11434/v1
model: qwen2.5:14b-instruct-q4_K_M
```

**4. 先验证工具调用，再上真实任务。** 写一个只挂一两个 MCP 工具的测试 Agent，跑一条"读文件 → 摘要 → 写回"的链路，人工检查每次调用的参数是否完整、字段有没有编造。这一步不能跳。

**5. 用真实负载压测。** 把完整的系统提示和全部 MCP 工具 schema 灌进去，观察上下文占用和 tokens/s，而不是靠聊天窗口打分。

## 踩坑点

- **小模型工具调用不稳**：Q4 的 7B 经常漏参数、幻觉出不存在的字段。优先选官方明确支持 function calling 的 instruct 版本；仍不行就在系统提示里加严格的 JSON 输出约束，并精简工具描述。
- **上下文溢出**：十几个 MCP server 的 schema 轻松吃掉 5–8k token，8k 上下文直接爆。16k 起步，KV cache 用 q8_0 量化能省近半显存。
- **内存卸载是坑**：模型层溢出到 CPU 后，tokens/s 可能从 40 掉到 3，多轮 Agent 循环体验崩坏。宁可选小一号的模型，也别卸载。
- **并发排队**：默认单请求队列，Agent 里并行子任务会互相阻塞。Ollama 设 `OLLAMA_NUM_PARALLEL`，llama-server 用 `-np`。
- **版本漂移**：模型 tag 更新后行为可能变化，配置里 pin 具体量化版本号，别用 latest。

## 可复用建议

- 全链路统一走 OpenAI 兼容协议，云端和本地切换只改 base_url 和模型名。
- 留一份工具调用冒烟测试脚本，每次换模型或换量化先跑一遍，两分钟发现八成问题。
- 显存预算公式记牢，买卡和选模型前先算再动手。
- 把"多轮 + 带工具 + 长系统提示"的链路作为唯一验收标准。

## 总结

本地模型不是云端的替代品，而是给自动化流水线补一层可离线、可托管、成本固定的执行底座。把"选型 → 显存预算 → 兼容端点 → 工具调用验证 → 并发与上下文调优"这条路径走通一遍之后，后续换模型就只是改一行配置的事。跑不通的地方大多不在模型本身，而在接入和验证的姿势上——这也是最值得沉淀成团队资产的部分。
