## 背景

Agent 要干活，就得摸得到外部世界：读文件、查数据库、调内部 API、发消息。在 MCP 出现之前，这件事没有统一做法——每个 Agent 框架自定义一套工具格式，每个工具写一遍接入胶水代码。你做 5 个 Agent、接 10 个工具，理论上就是 50 份互不通用的胶水。

MCP（Model Context Protocol）就是冲着这个来的：把「模型应用 ↔ 外部能力」的接口标准化。它是开放协议，client-server 架构：Agent 宿主（host）内跑 client，能力提供方写成 MCP server，通过 JSON-RPC 通信，本地常用 stdio，远程走 streamable HTTP。一个 server 对外暴露三类东西：**tools**（可调用的动作）、**resources**(可读取的数据)、**prompts**（可复用的提示模板）。

一句话概括价值：接入成本从 **N×M 降到 N+M**。工具方只写一次 server，任何支持 MCP 的 Agent 都能用；这套流程与宿主无关——无论你跑在 OpenClaw 还是自建框架里，server 这一端完全复用。

## 问题

实践中真正卡人的不是"连不上"，而是：

1. 各家工具 schema 互不兼容，换个框架等于重写；
2. 工具越接越多，Agent 的工具列表和选择逻辑越来越乱；
3. 想把内部系统能力开放给 Agent，缺标准的安全边界和调试手段。

## 做法与步骤

以给本地 Agent 加"查内部工单"能力为例：

1. **盘点能力边界**。想清楚需要哪几个动作：`list_tickets`、`get_ticket`、`add_comment`。一个工具一个明确意图，粒度别太碎。
2. **用官方 SDK 写最小 server**。Python 用 FastMCP 几十行就能起来；选 transport（本地 stdio 最省事），为每个工具写清参数 schema 和 description。
3. **接入宿主**。在 Agent 框架配置里注册 server，重启后先验证工具发现（`tools/list`）返回的条目符合预期。
4. **用 MCP Inspector 调试**。先用 inspector 脱离 Agent 单独跑通 server，再回到 Agent 侧看表现，排查时能省一半时间。
5. **观察真实调用**。看模型怎么选工具、传什么参数，回头修 description——这是循环最多的环节。

## 踩坑点

- **description 是写给模型的 prompt，不是写给开发者的注释**。写"查询工单"，模型不知道何时该用；写清"当用户询问工单状态、提供工单号或关键词时使用"，调用准确率明显不同。
- **返回内容没截断**。一个工具吐几千行 JSON 直接吃满上下文。分页、限制字段、必要时只返回摘要。
- **工具重名**。Agent 预置工具和 MCP 工具撞名时行为不可预期，给 server 的工具加统一前缀。
- **把 server 当业务后端写**。塞满状态和业务逻辑后没法治理。server 保持薄，权限和审计留在你自己的服务里——MCP 解决连接标准化，不替你解决安全。
- **超时与阻塞**。长任务同步等结果，Agent 表现得像卡死。改成提交任务返回 ID，再用另一个工具查进度。

## 可复用建议

- 每个server 先只暴露 3–5 个工具，拿到真实调用数据再扩。
- 错误信息要"给模型看"而不只是"给人看"，可读的错误能让模型自我修正，减少无效重试。
- 所有 tool call 落日志：参数、返回摘要、耗时。排障时回放非常有用。
- server 尽量无状态，升级重启不牵连 Agent 会话。

## 总结

MCP 不是什么智能革命，它就是把一件重复且脏的工程活标准化了：Agent 与外部能力的连接。对个人 Agent 项目的直接收益是——新工具从"改框架代码"变成"起一个 server"。建议从最小 server 开始，把 description 质量和返回体积这两个细节做扎实，剩下的坑基本都能绕开。
