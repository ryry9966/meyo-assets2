## 背景

OpenClaw 的 `memory_recall` 是 agent 长期记忆的入口：把历史会话、决策记录、踩坑笔记切块入库，模型通过 MCP tool 按需检索几段塞回上下文。检索质量直接决定"助手到底记不记得你上周说过的话"。

我们的记忆库目前约 4000 条 chunk（每条 200–500 字），本地 SQLite 存储。最初用纯语义检索（本地嵌入模型 + sqlite-vec），跑了一段时间后发现一类高频失败，于是做了一轮对比实验，最终落地为混合检索。本文记录结论和踩坑。

## 问题：两类失败模式

**纯语义的失败**：查"上次那个 403 是怎么解决的"，命中的都是语义相近的"权限/鉴权"讨论，但真正那条记录的关键字是 `ERR_HTTP_403_FORBIDDEN`、`nginx deny`——嵌入后权重被稀释，排到 20 名开外。嵌入模型对错误码、函数名、配置键这类 token 基本不敏感。

**纯全文的失败**：查"我们讨论过部署到边缘节点那次"，记忆里写的是"CDN 回源改造"，没有字面重叠，BM25 直接空结果。中文同义改写场景，全文检索很脆。

结论前置：两类检索是互补关系，不是二选一。语义管"意思相近"，全文管"字面精确"；标识符和错误码场景，全文是刚需。

## 做法：双路检索 + RRF 融合

1. **存储层**：SQLite 单库两张表，`memory`（id / timestamp / session / text）+ FTS5 虚表。中文分词用 trigram tokenizer。
2. **向量层**：写入时用本地嵌入模型生成向量，存入 sqlite-vec，增量索引，不做启动全量重算。
3. **召回管线**：query 同时发两路——FTS5 MATCH 取 top-20，向量余弦取 top-20；用 RRF 融合：`score = Σ 1/(60 + rank)`，重排取 top-k。
4. **时间衰减**：score 乘按天数的指数衰减，解决"三个月前的旧闻压过昨天的关键决策"。
5. **预算控制**：注入上下文的 chunk 总量封顶（我们设 1200 token），宁缺毋滥。
6. **留痕**：每次 recall 记录 query 和最终命中，攒够 40 条就是一个可用的迷你评测集。

## 踩坑点

- FTS5 默认分词器对中文整句不切分，必须 trigram 或外挂 jieba，否则中文全文检索等于没有。
- 别过早调融合权重。RRF 零调参起步就够；我们先试了加权线性融合，效果不稳定又退了回来。
- 嵌入必须持久化。试过每次启动重算，4000 条要十几秒，改增量后写入即可用。
- 时间衰减系数别拍脑袋，按评测集扫三个值取最优；衰减太强会把陈年架构决策全部埋掉。
- 召回条数不是越多越好，top-8 之后模型开始被无关片段带偏。上下文预算比召回率更稀缺。

## 可复用建议

- 直接上混合检索；纯语义只在语料几乎全是自然语言叙述时才值得。
- 全文路径永远保留，它是标识符 / 错误码场景的唯一可靠兜底。
- 评测先行：哪怕只有 20 条"问题 → 期望命中的记忆 ID"，也比肉眼比参数可靠。
- 记忆条目要自包含：写入时带日期、会话、主题，单条检出来才有独立可读性。

## 总结

语义 vs 全文不是选型题，是分工题。我们的最终形态很朴素：SQLite + FTS5(trigram) + 本地嵌入 + RRF，没有引入任何重型向量数据库。上线后评测集 recall@5 从纯语义的 0.62 提到 0.83，主要收益来自标识符类 query。下一步计划把"哪些召回真的被模型引用了"的信号回流进评测集，让记忆系统自己长出评测能力。
