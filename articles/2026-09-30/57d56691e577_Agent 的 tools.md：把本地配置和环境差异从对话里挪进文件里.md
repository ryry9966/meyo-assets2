## 背景

跑 Agent 做自动化时，最容易被低估的不是模型能力，而是环境。每台机器的包管理器、路径、端口、Python 版本、代理设置都不一样：你的笔记本上用 uv，同事用 pip，CI 里什么都没有。Agent 默认靠“探索”认识环境——`which`、`ls`、试跑命令——慢、贵，而且容易猜错。

## 问题

环境知识目前散落在三个地方：聊天记录（换会话就没了）、README（写给人不写给 Agent）、口头约定（等于没有）。结果是同一个任务在 A 机器顺利跑完，到 B 机器 Agent 开始反复试错，甚至执行危险动作：往全局环境 pip install、覆盖配置文件、连错数据库。

我踩过最典型的一次：Agent 在新机器上找不到 uv，“贴心地”降级成全局 pip install，把一个干净的容器环境污染了。问题不在模型，在于它手里没有任何持久的环境事实可依据。

## 做法：把环境写成 tools.md

核心思路一句话：**约定优于探索**。在项目根目录放一个 tools.md，Agent 会话启动时先读它，把环境事实一次性装进上下文。

推荐三层结构：

1. **全局层**（如 `~/.openclaw/tools.md`）：个人机器通用事实——shell、默认编辑器、代理、常用路径。
2. **项目层**（仓库根目录，进 git）：包管理器、启动/测试命令、端口、目录约定。
3. **差异层**：按机器或角色分节（laptop / server / ci），只写不同的部分。

一个可抄的骨架：

```markdown
# tools.md
## 环境
- 包管理器：uv（禁止 pip install 到全局）
- Python：3.12，虚拟环境在 .venv/
- 启动：uv run python -m app
## 端口与依赖
- 开发端口 8787；Postgres 走本机 5432，连接串读 .env
## 禁区
- 不要动 deploy/ 和 *.prod.yaml
## 机器差异
### server-a
- GPU 可用；用 conda 而非 uv
```

三条写法原则：

- **写事实，不写散文。**“用 uv，禁用全局 pip”比“我们建议现代化工具链”有用得多。
- **敏感信息不落盘，只写指针。**“密钥读 .env / 密钥管理服务”，别把 token 写进文件再 commit。
- **发现不符就回写。**Agent 发现文件与现实冲突时，要求它提示你更新 tools.md，而不是把结论留在对话里。

## 踩坑点

- **写太长。**tools.md 常驻上下文，超过一两屏就是在稀释关键信息，细节外链出去。
- **写了不维护。**环境变了文件没变，Agent 会拿着过期事实更自信地做错事——过期文档比没有文档危险。
- **假设 Agent 会自动发现。**不同框架的加载约定不一样，先确认你的会话初始化逻辑真的读了它，别想当然。
- **差异写成 if-else 长句。**不如按机器分节直给，Agent 检索起来也准。
- **骨架用脚本生成可以，但必须人工过一遍再入库**，别把临时实验配置带进去。

## 可复用建议

- 固定四段：环境事实 / 常用命令 / 禁区 / 机器差异，团队里所有人写出来格式一致。
- 每次因为环境踩坑，把结论回写成一条。这是这个文件增值最快的方式。
- 进阶：写个二十行的校验脚本，比对 tools.md 声明与实际环境，塞进 CI 定期跑，防止漂移。
- 个人层和项目层分开管理：前者 gitignore，后者进仓库，权限边界清晰。

## 总结

tools.md 的本质，是把易失的对话上下文里的环境知识，挪进持久、可审查、可版本化的文件。成本是几十行 Markdown，收益是 Agent 在任何机器上都能少试错、少闯祸、可复现。对长期跑自动化工作流的人来说，这可能是投入产出比最高的一个文件。
