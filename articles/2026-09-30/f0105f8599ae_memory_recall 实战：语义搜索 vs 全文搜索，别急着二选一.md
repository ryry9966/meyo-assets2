## 背景

Agent 跑了几个月后，memory 目录里堆了上百个 markdown：MEMORY.md、按天的记录、项目备忘。这时 memory_recall 的质量直接决定“这个 agent 记不记得事”。检索路线无非两条：全文检索（BM25/FTS5）和语义检索（embedding 向量）。我两套都部署过，结论是：这不是选型题，而是先搞清楚你的查询长什么样。

## 问题

两类典型查询，各自会让其中一种检索挂掉：

- **名词型**：“那次 cron 为什么改成 15 分钟”。关键词、命令、配置名。语义检索会把命令 token 模糊掉，召回一堆“调度相关”的无关段落，反而不如精确匹配。
- **改写型**：“上次说的那个部署方案”。原文里可能压根没这几个字，写的是“staging 发布流程”。全文检索直接查空。

还有中文特有的坑：SQLite FTS5 默认的 unicode61 分词器会把一整句中文当成一个 token，中文查询命中率接近零。这个坑通常最先爆，且症状有迷惑性——你会以为是自己数据写得烂。

## 做法

1. **先分块**：不要整个文件一个向量。按 markdown 的 h2/h3 小节切，200–500 字一块，每块附带日期和来源路径，召回粒度才够细。
2. **全文路**：FTS5 + 中文分词（trigram 或外部分词后入库），专门负责命令、ID、专有名词。
3. **语义路**：中文场景选中文表现稳定的 embedding 模型；几百条规模用 sqlite-vec 本地存就够，不必上向量数据库。
4. **融合**：两路各取 top-5，用 RRF（reciprocal rank fusion）合并后直接拼给模型，别为了重排再引入一个模型。
5. **建回归集**：攒 20 条真实历史查询，一半名词型一半改写型。每次改索引或换模型后跑一遍，看 top-5 命中率，用数据说话。

## 踩坑点

- FTS5 中文分词不配，召回为零。先测这个，再谈别的优化。
- 换 embedding 模型 = 全量重建索引。向量记录里存好模型名和版本，否则新旧向量混着算余弦，结果悄悄变差，还很难排查。
- top-k 别贪多，10 块以上上下文反而稀释模型注意力，等于没检索。
- 语义检索对“最近”“上周”这类时间词不敏感，时间型查询要么按文件名日期前置过滤，要么单独走一层。

## 可复用建议

- 小规模（500 块以内）纯全文 + 好的分词可能就够了，先压测再决定要不要上向量。
- 写 memory 时就为检索负责：一条一个主题、带日期、带关键词。**写入质量对召回的影响大于检索算法。**
- 同样的规则适用于自建 MCP 记忆插件或接外部记忆库：分块策略和元数据设计，比向量库选型重要得多。
- 混合检索 + RRF 是当前性价比最高的默认解，OpenClaw 内置的 memory_search 本身就是两条腿方案，重点是把分词和分块配好。

## 总结

语义搜索赢在改写和跨词理解，全文搜索赢在名词和精确串，各管一类查询。实践中多数人的 memory_recall 效果差，原因不在选型，而在分块太粗和中文分词没配对。先把记忆内容写好、把回归集建起来，再谈换更贵的模型——顺序反了就是白花钱。
