## 背景

OpenClaw 的 agent 每次会话都像一次“新员工入职”：没有记忆，只能靠系统提示和当前对话理解你的工作空间。团队里靠口口相传的约定——目录怎么摆、命令怎么跑、哪些东西不能碰——对它来说默认全是空白。AGENTS.md 就是补这块空白的通用格式：一个放在工作空间根目录的 Markdown 文件，agent 开工前会先读它，相当于它的入职手册。

## 问题

没有这份手册时的典型症状：

- 每次都要在对话里重复“用 pnpm 别用 npm”、“`migrations/` 下别乱动”；
- 换个会话或换个模型，行为立刻漂移；
- 同事各自调教出的 agent 习惯不同，自动化跑出来的提交风格五花八门。

本质上，口头约定不是资产，会话一关就清零。

## 做法

从最小可用版本开始，五步：

1. 在工作空间根目录建 `AGENTS.md`，先写三段：项目一句话概览、目录结构要点、常用命令。
2. 命令必须带确切参数，用祈使句，不留发挥空间：

```bash
pnpm -r build        # 全量构建
pytest -x tests/     # 单测，首个失败即停
```

3. 再加两段：代码与提交约定、禁区。禁区用否定句写死，例如“不要修改 `migrations/`，不要直接 push 到 main”。
4. 有子项目就在子目录放一份 `AGENTS.md` 覆盖根规则，OpenClaw 就近优先。
5. 进 git、走 PR 评审。它是仓库契约的一部分，不是个人笔记。

验证方式很朴素：新开会话，丢三条典型任务过去，看它是否按文件里的约定执行。这相当于给手册做冒烟测试。

## 踩坑点

- **写太长。** 几百行的 AGENTS.md 等于没写，关键指令被稀释。控制在一到两屏。
- **写成散文。** “我们崇尚质量文化”这类句子没有任何可执行信息。
- **把密钥、token 写进去。** 它会进版本库，也会被读进 agent 上下文，双重泄露面。
- **只建一份、从不更新。** 约定变了文件没变，agent 会理直气壮地按旧规矩办事。
- **双轨维护。** 同时养着 AGENTS.md 和各家编辑器的 rules 文件，两边迟早漂移。OpenClaw 场景下收敛到 AGENTS.md 单一来源。

## 可复用建议

- 用固定骨架：概览 / 目录 / 命令 / 约定 / 禁区 / 已知坑。六个标题，缺什么补什么，不预先堆内容。
- 养成“打补丁”习惯：每次手动纠正 agent 后，顺手把这条纠正写回文件。同一件事需要纠正第二次，就是文档的失职。
- 禁区条目放文件末尾并加显眼标记，实测冷启动时遵循率最高。
- 每月按 onboarding 文档的标准 review 一次：一个完全不了解项目的人（或 agent），能否只靠它完成基础工作？

## 总结

AGENTS.md 的价值不在格式本身，而在于把易逝的口头约定沉淀成可评审、可继承的文件。写它时记住读者是 AI：短句、确切命令、明确禁区；维护它时记住读者是人：进了 git、走了评审，它才算得上工作空间真正的手册。成本半小时，回报是每次会话省下的重复沟通。
