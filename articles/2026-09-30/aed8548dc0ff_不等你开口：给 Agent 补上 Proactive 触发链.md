## 背景

目前大部分 agent 的使用模式还是"你问它答"：用户发起请求，模型执行并返回。但真正高价值的场景往往是你没想起来问的事——CI 挂了、监控指标快到阈值、某份共享文档被改了、等了很久的价格到了目标位。这类事件驱动的主动性，靠对话式交互天然覆盖不了。OpenClaw 的会话模型本质是被动应答，想做 proactive，触发链得自己搭。

## 问题

Proactive 的难点不是"能不能执行任务"，而是三个更工程化的问题：

1. **触发源从哪来**：agent 平时不运行，谁唤醒它？
2. **谁决定值不值得打断用户**：判断错了就是骚扰，用户一旦 mute，主动能力直接归零。
3. **权限怎么收**：没人盯着的任务会默默积累写权限，出事就是静默出事。

## 做法

我在自己的实例上拆成四层，跑下来比较稳：

**第一步，接事件源。** 最实用的三种：定时触发（cron，适合日报、巡检）；Webhook / MCP 工具回调（CI 结果、表单提交、第三方状态变化）；文件与状态 watcher（目录变更、数据库行变化）。

**第二步，加决策层。** 事件进来不直接执行，先跑一个轻量判断：输入是事件摘要 + 用户偏好 + 最近交互历史，输出三选一——`act`（立即执行并通知）、`batch`（攒进摘要，随下次日报发出）、`suppress`（丢弃并记日志）。这一步把"主动性"变成显式的分类问题，而不是模型的自由发挥。

**第三步，动作分层。** 只读操作默认放行；写操作走 allowlist，且 proactive 路径的写权限必须单独授予；push 类通知设静默时段。

**第四步，节流和审计。** dedup key + cooldown 在编排层硬编码，不依赖 prompt 自觉；每条主动行为记录 trigger、证据、动作、成本四个字段，总开关一键可关。

## 踩坑点

- **自激励循环**：agent 自己发出的消息被自己的 listener 再次捕获，循环调用。解法：所有 agent 产出的消息打来源标记，事件入口统一过滤。
- **提醒疲劳**：前两天用户觉得惊喜，第三天就 mute 了。阈值宁高勿低，拿不准就进 batch。
- **定时任务成本失控**：每 5 分钟跑一次判断，九成结论是"无事发生"，token 全烧在空转上。先便宜后贵：规则预筛（关键词、阈值），命中才进模型。
- **上下文过期**：早上排的任务晚上才执行，中间状态早变了。执行前必须重新拉取关键状态，不能信任调度时刻的快照。

## 可复用建议

1. 先跑两周"只读 + 摘要式"主动，验证信噪比后再逐步放开写操作。
2. 在系统 prompt 里写一部"主动宪法"：不确定就不说，宁可漏报，不可误报。
3. 节流、去重、静默时段全部放编排层，prompt 只负责判断，不负责纪律。
4. 每个主动行为都要能回答三个问题：为什么触发、依据是什么、怎么关掉。

## 总结

Proactive 不是把 prompt 写得更"聪明"，而是把触发、决策、节流、审计拆成独立的工程组件，让模型只做它擅长的那一段判断。主动性的上限由工程决定，不由模型决定——把控制权留在自己手里，agent 才敢放心地"先你一步"。
