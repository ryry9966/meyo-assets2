## 背景

在 OpenClaw 里，cron 任务的本质很朴素：到点把一段 instruction 喂给 agent，让它自己跑完、自己交付。听起来和平时聊天没区别，但有个关键差异——**无人值守**。你在场时，agent 可以反问"你指的是哪个仓库？"；凌晨三点触发的任务没人回答它。所以 cron instruction 的全部要领，基本围绕一件事：预判它会在哪里卡住，提前把答案写进 prompt。

## 常见翻车

我踩过也见过的高频翻车，大致四类：

1. **相对时间含糊**。"每天早上整理一下昨天的进展"——"昨天"按哪个时区算？agent 在服务器上感知的日期可能和你差一天。
2. **输出没有去向**。agent 干完活，结论停在会话里，你根本看不到。
3. **失败静默变编造**。数据源挂了，agent 不报错，靠模型脑补补全，连续一周产出看起来正常的假日报。这是最危险的一类。
4. **任务范围膨胀**。instruction 里不断"顺便也看看 XX"，堆到十几行后执行成功率明显下降。

## 做法：六段式骨架

后来我固定用一个六段式模板，基本覆盖所有定时任务：

```text
【任务】一句话说清做什么
【先做】执行第一步：确认当前日期 / 读取某文件 / 调用某工具
【数据】明确来源：用哪个 MCP 工具、哪个路径、哪个 server
【规则】范围、过滤条件、取舍标准
【输出】格式（几段/表格列）+ 去向（发到哪个渠道 / 写到哪个文件）
【异常】拿不到数据或失败时：明确报告原因，禁止编造
```

对比一个例子。坏写法：

> 每天早上八点汇总我的 GitHub 通知发给我。

好写法：

```text
【任务】生成每日开发摘要。
【先做】确认今天日期，读取 ~/notes/todo.md 的未完成项。
【数据】用 github MCP 工具拉过去 24 小时的 notifications，只看 repo A 和 repo B。
【规则】按 repo 分组，每条一句话；超过 10 条只留 mentioned 和 review requested。
【输出】三段以内，发到 Telegram，开头带日期。
【异常】拉取失败就发"数据源不可用 + 原因"，不要凭记忆补内容。
```

同样的意图，第二种写法把所有需要 agent "猜"的地方都钉死了。

## 踩坑点

- **时区**：cron 表达式和"今天"是两套时间。instruction 里让 agent 先显式确认日期，比事后排查省事得多。
- **频率**：每 5 分钟一次的重活，token 和消息噪声都遭不住。先问自己"这个间隔里产出真的会变吗"。
- **会话隔离**：别假设 cron 能记住你上次聊天说过什么，它是独立触发的，上下文要自带。
- **幂等**：写文件类任务加一句"覆盖而非追加"，避免重复执行堆出十份重复内容。

## 可复用建议

1. **上线前手动跑一遍**：把 instruction 直接丢给 agent 执行一次，人工触发是定时任务最便宜也最有效的测试。
2. **instruction 进 git**：和代码一样做 diff，改坏了能回滚，也能看清任务是怎么一步步膨胀的。
3. **一个任务一条 instruction**：想做第二件事就新建任务。合并指令是翻车重灾区。
4. **失败要"响"**：宁可收到一条"任务失败：原因 xxx"，也不要一条安静的成功假象。

## 总结

写 cron instruction 时把心态换一下：这不是在跟 agent 聊天，而是在给一个能力很强、但完全不了解背景的值班同事写交接单——什么时候做、拿什么数据、做成什么样、出了问题怎么报告。把这四件事写清楚，定时任务的成功率会有肉眼可见的提升。
