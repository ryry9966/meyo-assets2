## 背景

Agent 最大的能力来自 shell 和文件系统工具，最大的风险也在这里。让一个偶尔会幻觉的模型拿着能执行任意命令的入口去干活，相当于把 root 权限交给一个不太靠谱的实习生。OpenClaw 的设计前提很明确：模型输出本质上是不可信的。任何“我在 system prompt 里写清楚了不许删文件”的做法，只能降低概率，不能构成安全边界。

## 问题

常见的翻车路径是：agent 想清理构建产物，`rm -rf` 的目标在变量展开后变成空字符串，或者相对路径被解析到了工作区之外。事故往往不是模型“想删”，而是它对路径的理解和真实文件系统不一致。所以问题要拆成两层：怎么让它删不到边界之外，以及万一删了怎么恢复。

## 做法：五层防御，层层假设上一层会失效

以典型 OpenClaw 部署为例（具体配置项以你所用的版本文档为准）：

1. **进程与文件系统隔离**。Agent 的 shell 在容器或受限 jail 内运行，可写挂载点只有 workspace 一个目录，其余全部只读或不挂载。物理上不存在“删到工作区之外”的路径。
2. **最小权限用户**。沙箱内跑在非特权用户下，无 sudo，不挂载宿主的 docker socket，把容器逃逸的收益压到最低。
3. **工具门控**。删除、覆盖、改权限这类动作走独立的工具入口，进入前先做路径规范化（realpath 解析符号链接），再和允许列表比对。命中放行，不命中直接拒绝——不存在“问一下模型要不要”这个环节。
4. **MCP 作用域收窄**。每个 MCP server 按需挂目录，filesystem 类 server 的根固定在 workspace，而不是用户家目录。插件一多，这条比其他措施都更能减少误伤面。
5. **可恢复性**。workspace 初始化为 git 仓库，agent 每完成一个阶段自动提交；删除类操作优先移入回收目录而非直接 unlink。成本极低，但把单次事故从“不可逆”变成“一次 revert"。

验证方法很朴素：部署完故意让 agent 删 workspace 外的一个文件，观察它被拒绝的报错路径；再让它删 workspace 内的文件，确认走的是回收目录。

## 踩坑点

- 图省事把 `~` 整个挂进沙箱，agent 立刻能读到 SSH key 和各类 token。
- 路径校验只做字符串前缀判断，没做 realpath，agent 借符号链接一层就绕出去了。
- 为了跑 CI 挂了 docker socket，等于把宿主 root 送了出去。
- 用 prompt 约束替代机制约束。prompt 会漂移，挂载和权限不会。
- 沙箱内网络全通，agent 可能把 workspace 打包外发——删文件防住了，数据没防住。

## 可复用建议

- 每新增一个插件或 MCP，先问：它需要哪些路径和网络？按需给，缺省拒绝。
- 把“危险操作必须过门控”写进团队规范，而不是写在 system prompt 里。
- 定期做红队演练：明确指示 agent 去越界，看边界是否还成立。
- 沙箱日志落盘并定期回顾，拒绝记录的信息量往往比成功记录更大。

## 总结

“Agent 不会误删文件”不是模型的品行，而是沙箱模型的性质：不可信输出 + 物理边界 + 工具门控 + 可恢复。OpenClaw 把安全假设建立在“模型一定会犯错”上，工程上反而更省心。下次接入新工具时，先补边界，再放权限。
