## 背景

OpenClaw 的 Agent 默认带 shell 执行能力（exec 工具），跑自动化任务很好用，但也意味着一个误读路径或幻觉参数的模型，理论上可以敲出 `rm -rf`。OpenClaw 的设计假设很直接：**模型一定会犯错，所以边界不能靠 prompt 约束，要靠运行时隔离**。sandbox 就是这个假设的落地位置。

## 问题：`rm` 到底删的是谁的东西

启用 Docker sandbox 后，Agent 的所有命令都在容器内执行，容器根文件系统是镜像层，怎么删都不影响宿主机。真正的风险面只有一类：**bind mount 进容器的目录**——在那里删除是真实删除。所以"Agent 不会误删文件"的准确表述是：它只能删你明确挂载给它的东西，且越界操作默认要过审批。

## 做法：四层防线

1. **容器隔离**：exec/bash/cron 类工具默认落在 sandbox 容器，以非 root 用户运行；workspace 以 bind mount 进入容器，是唯一可写面。
2. **工具策略**：宿主机级 exec 设为 `ask`（逐次人工确认）或 `deny`，只有低风险任务交给 full。
3. **路径最小化**：只挂任务需要的子目录，参考用的上下文一律只读挂载。
4. **可恢复性**：workspace 纳入 git，Gateway 的 reset 只重建 workspace，不动挂载卷。

一份最小配置（字段名以当前版本文档为准，思路一致）：

```json
{
  "agents": {
    "defaults": {
      "sandbox": { "mode": "all", "workspaceAccess": "rw" },
      "tools": { "exec": { "host": "ask" } }
    }
  }
}
```

## 踩坑点

- 为了省事把 `$HOME` 或整个仓库根挂进容器——沙箱还在，但保护范围等于没有。**挂载即授权**。
- 挂载卷内的删除不可逆，git 管理 workspace 不是可选项，是必选项。
- 给容器挂 `docker.sock` 做 CI 类任务：等于把宿主机 root 交给 Agent，直接放弃这个方案。
- 审批白名单写得太宽（比如放行 `bash -c` 任意拼接），`ask` 形同虚设。
- 多 agent 共享 sandbox 时，一个 agent 的 `rm` 会影响另一个的工作区，敏感任务用 per-agent 隔离。

## 可复用建议

- 上线前做一次红队演练：明确要求 Agent"删除工作区外的一个文件"，观察它是被拦、报错还是绕路，把结果写进团队文档。边界要验证过才算存在。
- 只读上下文一律 `ro` 挂载，写权限按任务临时给、用完回收。
- 高危命令（`rm`、`chmod -R`、`curl | sh`）在策略层统一 deny，走人工通道，不要指望模型自觉。
- 按信任级别拆配置：不同风险的任务对应独立的 agent 定义 + sandbox scope，不要一份配置打天下。

## 总结

OpenClaw 防"误删"靠的不是模型的自觉，而是三个问题的答案：**命令发生在哪里**（容器内）、**能碰到哪些路径**（最小挂载）、**越界操作谁说了算**（审批链）。把这三点固化成默认配置，Agent 的 `rm` 就只能作用于你明确交出去的那一小块，误操作的代价从"灾难"降为"可恢复"。安全模型的价值不在拦截多么聪明，而在默认边界足够小。
