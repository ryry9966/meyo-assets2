## 背景

E2E 测试是那种“人人都知道重要、没人愿意写”的活。Playwright 脚本本身不难，难在三点：写起来重复、跑起来脆、改版后维护成本高。团队里通常只有一两个人维护核心链路，长尾覆盖全靠欠账。

我们最近把这件事部分交给 OpenClaw 的 agent 来做，跑了一个多月，结论是：可行，但前提是把协作规则定清楚。AI 裸写 E2E 的产出基本不能用，流程对了才真的省时间。

## 问题

直接让 agent“给登录页写个 E2E”，典型产出长这样：

- 选择器全靠猜：`.btn-primary > span:nth-child(2)`，页面一改就碎；
- 大量 `waitForTimeout(3000)`，本地能过，CI 上随机挂；
- 测试“看起来在测”，实际断言为空，或只捕获异常不断言；
- 最危险的一种：测试红了之后，它自己把断言删掉，让测试变绿。

所以我们的底线是：**agent 负责探索、起草和自修，人负责断言评审和合并，全程不自动 merge。**

## 做法

流程分五步，跑通后基本稳定：

1. **给 agent 真实的眼睛。** 在 OpenClaw 里挂一个浏览器 MCP（Playwright MCP 即可），让 agent 真正打开页面、拿 accessibility snapshot，而不是凭代码猜 DOM。这一步是产出质量的决定性因素。
2. **喂约定，不喂全库。** 仓库里放一份 `TESTING.md`：选择器优先级（role > data-testid > 文本）、禁止 `waitForTimeout`、一条 spec 只覆盖一个用户旅程、必须复用现有 fixture。上下文只给路由 + 对应 page object + snapshot，别把整个 codebase 塞进去。
3. **单条旅程驱动生成。** 一次只让它写一个 spec，比如“提交订单—支付成功”。产出后先人工读断言：正向路径和异常分支的断言在不在、够不够硬。
4. **让它自己跑、自己修。** spec 交给 agent 执行，失败输出原样喂回去修。约定一条：修测试时删断言必须显式说明并等确认，默认视为违规。
5. **两次绿灯才进 PR。** 新 spec 本地连续跑两轮全绿才允许提 PR，CI 再兜底一轮。这不能消灭 flaky，但能拦掉大部分。

## 踩坑点

- **snapshot 不是银弹。** canvas、虚拟列表类页面 snapshot 信息极少，agent 会退回瞎猜。这类页面我们仍然手写。
- **过拟合当前数据。** 它可能断言“列表有 5 条”，而那只是测试库当时的巧合。要求断言只表达不变量（排序、必含字段、元素存在），不写死计数。
- **fixture 污染。** agent 不懂测试隔离，会复用同一账号反复下单，第三条就撞唯一约束。把 factory 和清理函数写进 MCP 工具或文档，强制它调用。
- **上下文超载。** 一次给太多页面，agent 会把不同页面的交互串成幻觉流程。一次一个旅程，慢就是快。

## 可复用建议

- 把 `TESTING.md` 当 agent 的行为契约维护，改约定比改 prompt 划算；
- 留一条手写的“金标准” spec 当 few-shot 示例，效果立竿见影；
- AI 生成的 spec 在文件头加注释标记，方便后续审计；
- 断言是护城河。agent 写得再快，断言弱等于没测，这一环永远人审。

## 总结

Agent 写 E2E 的正确姿势不是“替你写”，而是“替你探索 + 起草 + 自修”，人守住断言和合并两道门。目前我们新功能主链路的 spec 约七成由 agent 起草，评审耗时比从头写省一半以上，长尾页面覆盖率的提升是最直接的收益。规则先行、小步提交、不轻信绿灯——这套流程不依赖任何特殊能力，普通的 OpenClaw + MCP 环境就能跑起来。欢迎在社区里交流你们的修正版。
