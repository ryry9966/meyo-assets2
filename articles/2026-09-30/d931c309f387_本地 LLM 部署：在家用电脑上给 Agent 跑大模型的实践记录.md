## 背景

玩 Agent 和 MCP 一段时间后，一个现实问题浮出来：工具调用循环频繁、上下文长，云端 API 的账单和隐私顾虑都在涨。于是我把一个 14B 模型搬到了自己 16GB 显存的台式机上，配合本地 Agent 跑了两周，把完整过程记录下来。

## 问题

本地跑模型和“能聊天”是两回事，Agent 场景的难点在于：

- 一次任务往往十几轮工具调用，每轮都带上系统提示 + 工具 schema + 历史结果，上下文轻松超过 8k；
- 小模型对 function calling 的格式遵循度不稳定，参数幻觉会直接让工具链崩掉；
- 家用显卡显存有限，模型大小、量化等级、上下文长度三者互相挤压。

## 做法

**1. 先算显存账，再选模型。** Q4_K_M 量化下，7B 约占 5–6GB，14B 约 9–10GB，32B 需要 24GB 显存或部分走 CPU。16GB 显存跑 14B + 8k 上下文是甜点位。

**2. 部署推理服务。** 用 Ollama 或 llama.cpp 的 server 模式，拉起 OpenAI 兼容端点（默认 11434 或 8080 端口）。选自带 function calling 模板的模型，Qwen 系列对中文和工具调用都比较稳。

**3. 接入 Agent。** 只改 base_url 指向本地端点，密钥随便填。建议把温度压到 0.1–0.2，工具调用稳定性明显更好。

**4. 调上下文。** 显式设置 num_ctx / context length 到 8k–16k。KV cache 可以粗估：层数 × 2 × KV 头数 × 头维度 × 上下文长度 × 2 字节（fp16）。开 flash attention 和 KV cache 量化能省不少显存。

**5. 验证工具链。** 写一个 20 条任务的评测脚本，统计工具调用成功率和参数错误率，本地、云端各跑一遍对比。

## 踩坑点

- **上下文默认值陷阱**：不少运行时默认 2048/4096，Agent 跑到一半工具输出被静默截断，模型开始“编”工具结果。这是最隐蔽的坑。
- **显存溢出到 CPU**：模型放不下时部分层 offload 到内存，吞吐从 40 tok/s 掉到 3 tok/s，一次任务要等几分钟。宁可换小一档的模型。
- **工具 schema 太复杂**：嵌套数组 + 枚举的参数，14B 以下模型经常填错。把工具参数做扁平化、加枚举校验、失败自动重试一次，成功率能拉回可用水平。
- **RAG 别用主模型做 embedding**：单独跑一个 bge-m3 之类的 embedding 服务，开销小、质量更好。

## 可复用建议

1. 推理服务和 Agent 进程分离部署，本地/云端切换只改一个环境变量，方便随时 A/B 对比；
2. 评测脚本常备，换模型只看两个数：工具调用成功率、每千 token 成本（电费也算进去）；
3. 本地模型适合做“草稿层”——路由、分类、摘要、简单工具调用；复杂推理留给云端大模型，混合路由是目前最务实的架构。

## 总结

家用电脑跑本地模型，做 Agent 开发和 MCP 联调完全够用。两周下来最大的收获是迭代速度：没有限流、没有账单焦虑，改完 prompt 秒级重跑。但生产级的复杂推理仍建议走云端。本地管高频轻任务，云端管重活，这条路在当前模型水平下是性价比最优解。
