## 背景

OpenClaw 的 cron 用起来门槛很低：一条 cron 表达式 + 一段 instruction，agent 到点执行。但实际跑一阵后，很多人的定时任务会开始飘——该发的日报没发、内容不对，或者 agent 自作主张干了一堆额外动作。问题通常不在 cron 本身，而在那段 instruction 的写法。

## 问题：cron 执行时和对话完全是两回事

对话里 agent 有上下文，你可以随时追问和纠正。cron 触发时，这三个条件都不成立：

1. **没有澄清机会**。instruction 含糊，agent 只能猜。
2. **上下文不可靠**。cron 会话可能是干净启动的，你在聊天里说的"以后日报都按那个格式"，它未必知道。
3. **没人盯着**。跑挂了、发重了、发错渠道了，都是事后才发现。

所以 cron instruction 的本质不是"提醒"，而是一份交给无人值守状态的 SOP。

## 做法：把 instruction 拆成五段

我现在固定用这个结构：

1. **目标**：一句话说清任务。"每天 09:00（Asia/Shanghai）生成昨日服务运行日报并推送。"
2. **数据来源**：写死工具和命令，比如"用 exec 运行 `bash ~/scripts/daily_report.sh`，以脚本输出为准"，别让 agent 自由发挥去找数据。
3. **输出结构**：给固定骨架（异常摘要 / 关键指标 / 待办），并限死长度："全文不超过 200 字"。
4. **投递渠道**：明确工具和目标，"通过 message 工具发送到 Telegram 的 xxx 会话"，避免它回复到当前会话或发错地方。
5. **失败处理**：定义取不到数据时的行为。"脚本失败则原样贴出错误输出并注明数据缺失，不要编造数值，重试不超过 1 次。"

我还会在结尾加一条禁止项：**"除上述动作外，不要执行任何其他操作。"** 这句话实测能挡住 agent 顺手清理日志、顺手回复旧消息之类的意外。

## 踩坑点

- **别用依赖历史的表述**。"和上次一样""按之前那个格式"——cron 会话里没有"上次"。
- **时区要写死**。cron 表达式按系统时区解析，instruction 里的时间语义再和 agent 确认一遍，两边对不上就会"早八变晚八"。
- **日期让它自己查**。在 instruction 里要求先运行 `date` 确认今天几号，别靠模型猜，长周期任务尤其容易在这里出错。
- **输出不限长**，日报会越写越长，token 和阅读成本一起涨。
- **失败语义不定义**，agent 可能自行"补偿"——比如拿昨天的数据当今天发，这比不发更糟。
- 心跳/重试机制和 cron 叠加时注意去重，否则同一条日报可能发两遍。

## 可复用建议

- 把每条 cron 的 instruction 当代码管理：单独存文件、进 git，改动走 commit，出问题能 diff 能回滚。
- 上 cron 前先手动触发一次，验证全链路：数据 → 生成 → 投递。
- 允许的话给关键任务加一条"干跑"指令版本，只生成不投递，用来安全验证改动。
- 每季度清理一次：cron 里最常见的就是"设了就忘"的任务，早就没人在看了。

## 总结

判断 cron instruction 写得好不好，标准很简单：把它交给一个完全不了解背景的同事，他能不能只靠这段话把事情做对。能，任务就稳；不能，迟早飘。本质上你写的不是一句 prompt，而是一份无人值守的交接文档——按交接文档的标准写，按代码的标准管，定时任务才能长期省心。
