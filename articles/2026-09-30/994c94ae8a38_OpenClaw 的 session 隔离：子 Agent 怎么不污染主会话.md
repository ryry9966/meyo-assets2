## 背景

用 OpenClaw 跑日常自动化久了，主会话（`agent:main`）会越长越胖。尤其是让主 Agent 委派子 Agent 去做批量抓取、代码巡检这类"过程很吵"的活，如果子 Agent 的工具调用轨迹和中间输出都回流主会话，上下文很快被撑爆，主 Agent 的注意力也会被无关的中间状态稀释。OpenClaw 的 session 机制在设计上是隔离的，但用不对照样会把污染带回来。

问题拆开看有三个：

1. **上下文污染**：子 Agent 的完整工具轨迹回流主会话，token 消耗和噪音双升；
2. **指令串扰**：子 Agent 的临时指令、系统提示片段混进主会话历史，影响后续行为；
3. **文件冲突**：多个子 Agent 并发写同一个 workspace，产生覆盖和脏数据。

## 做法

**1. 用 delegate/subagent 方式派活，而不是让主 Agent 在同一会话里"扮演角色"。** 子 Agent 会拿到独立的 session key，任务在单独的会话文件里执行，主会话只接收最终返回值。这是隔离的第一道墙。

**2. 把任务写成接口。** 子 Agent 默认看不到主会话历史，派活时必须显式带上：输入是什么、期望返回什么格式、超时多少。别指望它"知道"。

**3. 控制回流体积。** 让子 Agent 返回结构化摘要（结论 + 关键数据 + 产物路径），大块中间产物落盘成文件，主会话里只留路径。session 隔离不等于结果可以无限回灌，这是隔离的另一半。

**4. 裁剪子 Agent 的工具白名单。** 抓取任务就只给 fetch/read，不给 write/exec，降低爆炸半径。

**5. 验证隔离生效。** 跑完一个子任务后查看 sessions 列表：子会话应独立存在，主会话长度不应异常增长。这步花十秒，能省掉后面一小时排障。

## 踩坑点

- **嵌套派活没设深度上限**。子 Agent 又开子 Agent，会话文件暴涨，磁盘和调度都被拖垮。任务模板里固定写死最大嵌套层数。
- **以为子 Agent 会继承主会话记忆**。它不会。产出偏差大时，先检查是不是关键上下文没压进任务描述。
- **返回值没约定格式**。子 Agent 把整段日志丢回来，等于把污染换了个方向带回来。
- **并发写同一目录**。多个子 Agent 的产物互相覆盖，建议按会话或任务 ID 分目录。
- **排障只看主会话**。主会话里只有摘要，完整的工具轨迹在子会话文件里，不看它容易误判。

## 可复用建议

- 固化一个"子 Agent 返回模板"：结论一句话、数据表、产物路径列表，三类之外不收。
- 中间产物一律落盘、会话只传引用——这条原则不只适用于子 Agent 场景。
- 每类自动化任务固定工具白名单和超时，写进任务模板，减少每次手写的不一致。
- 定期清理调试期产生的一次性子会话，别让它们静默堆积。

## 总结

session 隔离不是配置一次就完事，它是一条团队约定：**过程留在子会话，结果以紧凑契约回流主会话**。把派活当接口设计、把大产物放文件、把工具权限收窄，OpenClaw 的主会话才能长期保持干净、可预测、可审计。
