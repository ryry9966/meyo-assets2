## 背景

OpenClaw 的主会话本质上是一条持续增长的长上下文。跑自动化任务（定时巡检、批量抓取、多轮工具调用）几天后，transcript 里堆满历史 tool output，模型注意力被稀释，表现为"变笨"、变慢、费用上涨。子 Agent（session 分叉）是官方给的解法，但不少人用了一段时间发现主会话照样被塞满——问题通常不在隔离机制本身，而在回传方式没约定好。

## 污染从哪来

子 Agent 的隔离是双向的：主会话上下文不进入子 Agent，这个方向一般没问题；容易漏的是反方向——子 Agent 的产物怎么回到主会话。常见污染路径有三条：

1. **原始工具输出直接回传**：子 Agent 跑了 40 次工具调用，把全部 stdout 塞回主会话，隔离形同虚设。
2. **共享写资源**：子 Agent 和主会话写同一个 memory 文件、同一工作目录、同一份 MCP 缓存，互相覆盖。
3. **隐式回传**：某些插件的 hook（如 `on_result`）默认把中间结果 append 到主 session，配置没关。

## 我的做法

以批量巡检任务为例，四步：

**第一步，spawn 时声明隔离参数。** 创建子 Agent 显式指定独立 session_id 和空 context，不开 `inherit_history`。文档里都写了，但默认模板里 inherit 往往是开的，图省事就会踩。

**第二步，约定返回 schema。** 子 Agent 结束时只返回结构化摘要，比如 `{status, key_findings, artifact_path}`，长度限制 200 字以内。原始输出一律落盘到独立工作目录，主会话只拿文件路径这个"指针"。

**第三步，收缩子 Agent 的工具面。** 只给任务必需的 tool allowlist；有状态的 MCP 服务（比如带会话的浏览器实例）给子 Agent 起独立实例，别共用。

**第四步，关掉隐式回传 hook。** 逐个检查所用插件的 hook 配置，把 `on_result` / `append_to_main` 之类的默认项关掉，只保留显式 return。

## 踩坑点

- **摘要写太长等于换一种污染**。见过子 Agent 返回 2000 字"总结"，比原始日志还难处理。schema 里加长度约束，超限直接截断。
- **并发子 Agent 写同一 memory 文件会互相覆盖**。要么每个子 Agent 独立目录，要么加文件锁。
- **shell 环境也是共享的**。子 Agent 改了工作目录、装了依赖，主会话后续任务可能被殃及。临时任务建议一次性容器或独立 venv。
- **隔离验证别靠感觉**。跑一次后 diff 主会话 transcript 的行数，正常涨幅应该只有那段结构化摘要。

## 可复用建议

- 主会话只留"结论 + 指针"，大产物全部落盘。
- 把返回 schema 写进子 Agent 的 system prompt 模板，固化成团队约定。
- 每周看一次主会话体积，超阈值就归档重建。隔离做得好，这应该是低频操作。

## 总结

Session 隔离不是开个开关就完事，核心是把"子 Agent 往主会话传什么"变成显式契约：结构化摘要 + 文件指针，其余一律隔离。做到这一点，主会话才能长期保持清爽。
