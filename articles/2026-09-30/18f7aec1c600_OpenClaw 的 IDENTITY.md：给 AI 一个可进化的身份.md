## 背景

OpenClaw 的 workspace 里有一组"元文件"：`AGENTS.md` 管做事方式，`SOUL.md` 管性格与价值观，而 `IDENTITY.md` 管"我是谁"。它通常只有几行——Name、Creature、Vibe、Emoji、Avatar。首次启动时 bootstrap 流程甚至会引导 agent 自己起草这份文件。

看起来像个装饰性配置，但它是每次会话都会被注入上下文的身份定义，也是跨渠道（IM、CLI、Web）保持一致人格的锚点。

## 问题

实际跑一段时间后，常见三类症状：

1. **人格漂移**：今天话痨明天冷淡，跨会话不一致；
2. **迭代黑盒**：想调整语气，改了文件却说不清是哪次改动起了作用；
3. **身份串味**：多个 agent 或多人共用环境时，工作区配置互相泄漏。

根因往往是把身份当成一次性文本，而不是有版本、有边界的工程产物。

## 做法：把 IDENTITY.md 当产品维护

1. **保持"身份卡"粒度。** 官方模板的字段就是边界：它回答"我是谁"，不回答"我该怎么做事"（归 `AGENTS.md`），也不回答"我信什么"（归 `SOUL.md`）。
2. **进 git，配 changelog。** workspace 本身就该是仓库。每次改 Vibe 描述，commit message 写清动机（如"回复太长，收敛为短句风格"），两周后回看能直接定位行为变化的源头。
3. **稳定层 + 实验层。** 上半部分是不变的身份事实；下半部分用注释标出"实验中"的特质，观察一两周再转正或删除。
4. **改完做回归。** 固定一组日常问法（打招呼、报错求助、被拒绝的请求），对比改前改后的回复倾向，不凭感觉调人格。
5. **多 agent 场景**用独立 workspace 加独立 remote，身份文件随工作区走，不共享。

## 踩坑点

- **把行为规则塞进身份文件**（如"回复必须简洁"），和 `AGENTS.md` 冲突后表现不稳定。身份是名词，行为是动词，分开写。
- **写成小作文。** 文件越长，每次注入的 token 越多，模型反而抓不住重点。十行以内是经验值。
- **Vibe 里写负面清单**（"不要傲慢"），容易反向触发；改成正向描述（"平实、克制"）效果好得多。
- **Avatar/Emoji 会被消息渠道实际使用。** 只改名不改头像，用户感知的人格就劈叉了。
- 字段名随版本可能有差异，改动前先对照自己 workspace 里的模板，别照抄网上的旧示例。

## 可复用建议

- 把 `IDENTITY.md` 当 API 对待：字段稳定、值可迭代、变更有记录。
- 每月 review 一次：过去一个月哪些回复让你不满意？是不是身份描述导致的？
- 团队共用 agent 时，身份变更走 PR review——人格也是需要 code review 的资产。

## 总结

`IDENTITY.md` 的价值不在它写了什么，而在它让"AI 是谁"变成一个可 diff、可回滚、可评审的文件。agent 自己起草初稿，人负责迭代和守边界——人格不需要复杂，但需要一致和可追溯，这恰好是工程师擅长的事。
