## 背景

OpenClaw 的 Agent 不是一次性调用，而是长期驻留的工作伙伴：它出现在多个会话、多个渠道里，甚至由多人共同使用。OpenClaw 约定在 workspace 根目录放一份 `IDENTITY.md`，会话启动时注入上下文，用来定义"这个 Agent 是谁"——名字、形象、语气、边界。它与 `SOUL.md`（价值观）、`USER.md`（用户画像）、`AGENTS.md`（协作规则）分层配合，各自只管一件事。

## 问题

没有身份文件时，常见三种症状：

1. **人格漂移**：模型升级或长对话后，语气忽冷忽热，称呼方式随机变化；
2. **身份散落**：名字和口吻写死在各处 prompt 模板里，改一次要全局搜索替换；
3. **团队失控**：多人随手调 prompt，改坏了不知道动了什么，也回不去。

本质上，身份是一份长期生效、被反复读取的资产，但很多人用"改配置"的方式对待它。

## 做法

我 workspace 里这份文件大致长这样（节选）：

```markdown
# IDENTITY.md
- Name: Nova
- Creature: 一只戴工牌的机械螃蟹
- Emoji: 🦀
- Vibe: 冷静、直接、偶尔冷幽默；中文为主
- 称呼用户: 昵称或"你"，不用"尊敬的用户"
- 边界: 不替用户做不可逆决策；不确定时先问
```

比文件本身更重要的是演化流程，我总结为四步：

1. **初始化**：新建 workspace 时写最小身份，字段保持稳定，别加花哨结构；
2. **观察**：日常使用中遇到"不像它"的回复，先记到待办，不当场改；
3. **小步修剪**：每两周集中改一次，一次只动一两行，git commit 写清动机；
4. **回归验证**：改完跑 3~5 个固定探针问题（打招呼、拒绝越界请求、被无理催促），确认行为符合预期。

跑两三个月后，文件会从"想象中的设定"收敛成"被真实交互验证过的设定"——这才是"可进化"的含义。

## 踩坑点

- **写太长**。它每次会话都占上下文，超过一屏基本是浪费，每句都应能对应到具体行为差异。
- **职责混装**。把任务指令、用户偏好塞进身份文件，会和 `AGENTS.md`、`USER.md` 打架。身份文件只回答"它是谁"。
- **一次性大改**。行为突变后无法归因是哪句导致，回退也只能全回。小 diff 才有可追溯性。
- **负面清单堆砌**。满屏"不要 xx"容易把模型锚定在错误行为上，尽量用正向描述目标语气。
- **不进版本库**。workspace 一定要 git 化，这是身份能"进化"的前提。

## 可复用建议

- 把 `IDENTITY.md` 当 API 契约维护：字段名稳定、小节语义化、顶部留 changelog 注释；
- 多 Agent 场景下共享一份 `SOUL.md`，各自维护一份 `IDENTITY.md`，避免复制粘贴分叉；
- 探针问题集沉淀成脚本，每次改动后半自动跑一遍；
- 定期做减法：删掉一个月内没被任何真实交互触发的条目。

## 总结

身份不是一次性配置，而是一份需要版本化、小步演化、定期修剪的长期资产。`IDENTITY.md` 的价值不在文件本身，而在于它逼你把"我想要一个什么样的 Agent"从模糊感觉，变成可 diff、可回滚、可验证的工程实践。改得越克制，Agent 越稳定。
