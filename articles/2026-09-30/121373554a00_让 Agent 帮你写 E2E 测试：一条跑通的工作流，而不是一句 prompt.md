## 背景

E2E 测试是典型的"高价值、高成本"工作：覆盖真实用户路径，但写起来冗长、选择器脆、改版就断。我们团队在 Agent 工作流里跑了近半年的"AI 辅助写 E2E"，从最初"一句话生成测试"的翻车，到现在形成一条稳定流程。这篇把做法和踩坑摊开讲。

## 问题：直接让 Agent 写，产出基本不能用

最直接的方案是把页面 URL 丢给 Agent，让它"生成 Playwright 测试"。三类问题反复出现：

1. **同义反复测试**：Agent 倾向断言"代码做了什么"而非"用户需要什么"——注册后断言 localStorage 里多了个字段，而不是断言跳转到工作台。
2. **选择器赌运气**：`nth-child(3)`、动态 class 一改版就挂。
3. **修复即退化**：测试挂了让 Agent 修，它走的最短路径是删断言、加 `waitForTimeout(5000)`。测试绿了，等于没测。

核心矛盾：Agent 没真正"用过"这个产品，它只是在猜。

## 做法：探索 → 评审 → 生成 → 回灌

**第一步，让 Agent 先当用户。** 通过 Playwright 类的 MCP 工具，让 Agent 真实操作页面：登录、下单、改配置，每步截图记录。这一步的产出不是代码，是一份"用户路径清单"。

**第二步，人评审路径，不评审代码。** 清单进 code review：删掉臆造的边角路径，补上它没发现的业务规则。10 分钟成本，决定了后面生成质量的上限。

**第三步，按路径逐条生成。** 每条路径一次生成，约束写进仓库的 AGENTS.md：选择器必须用 `data-testid`、禁止硬编码 sleep、单用例只测一条路径、断言基于用户可见结果。Agent 能读真实 DOM，选出的选择器往往比人拍的稳。

**第四步，失败回灌分诊。** CI 挂了把日志喂回 Agent，让它先分类：选择器漂移 / 环境 flaky / 真实 bug。前两类它自己提 PR，最后一类转人工。这一步省的时间最多。

## 踩坑点

- **一口气生成整套测试**，质量断崖式下降。按路径切片，单次控制在 2-3 个用例。
- **没有选择器约定就开工**。先花半天给核心页面补 `data-testid`，比后面改十轮测试便宜。
- **无差别授予"修测试"权限**。我们吃过亏：它把一个真实 bug 的断言改弱让测试变绿。现在凡涉及断言变更的 PR 必须人工过。
- **不监控 flaky 率**。加了 40 个 AI 测试后 flaky 飙到 15%，团队信任崩了，比没有测试更糟。

## 可复用建议

1. 测试约定沉淀成仓库内的 Agent 指令文件，全员共用一份，别每次对话里口述。
2. "用户路径清单"独立进版本管理，生成、重构、补测都以它为锚点。
3. 上线后盯两个数：人工维护测试的时长、套件 flaky 率。前者在降、后者没涨，这套流程才算成立。

## 总结

Agent 写 E2E 的价值不在"替你思考测试"，而在消灭样板劳动：起草用例、修选择器、分诊失败。测试设计权和断言语义必须留在人手里。把它当一个手快但需要盯着的初级工程师来用，流程就稳了。
