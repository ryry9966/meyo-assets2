## 背景

Agent 的价值不在"听懂需求"，而在"把事办成"。办成事就得碰外部服务：查库存、发工单、调内部接口。在 OpenClaw 里，标准路径是通过 MCP 或插件把 API 包成工具（tool），由模型决定何时调用、传什么参数。思路简单，但接第一个真实服务时你会发现，坑全在细节里。

## 问题：裸调 API 为什么总翻车

- 模型不按预期调工具：参数缺失、编造 ID、把该用 GET 的事塞给 POST；
- 网络层不可靠：超时、限流、偶发 5xx，直接卡死整个 agent loop；
- 安全边界模糊：key 混进 prompt 或日志；模型拼出的 URL 被直接请求（SSRF）；
- 错误不结构化：模型看到 `error: null` 只能瞎猜，然后反复重试同一个错。

## 做法：把 API 包成靠得住的工具

**1. 一个工具只做一件事，schema 收紧。** 模型靠读工具描述来决策，描述质量直接决定调用准确率。字段写清格式和示例，能用 enum 就用：

```json
{
  "name": "query_order",
  "parameters": {
    "order_id": {
      "type": "string",
      "pattern": "^ORD-\\d{8}$",
      "description": "订单号，形如 ORD-20240501，不能传用户昵称"
    }
  }
}
```

**2. 凭证走配置，不进上下文。** key 放环境变量或密钥服务，工具执行时注入；日志统一打码。

**3. 传输层独立加固。** 统一 HTTP client：超时 10 秒（写操作更短）、指数退避重试、只重试幂等请求、写操作带 idempotency key，再加个简单熔断。

**4. 错误也要"喂"回给模型。** 返回 `{code, message, hint}` 结构：429 就提示等待后重试，404 就提示确认 ID。永远别把原始堆栈直接扔给它。

## 踩坑记录

- 工具返回 200KB 原始 JSON，几轮对话后 context 爆了。改成只返回决策相关字段，列表类结果给摘要 + 单独的详情工具。
- 对非幂等的下单 POST 做了自动重试，结果创建了两条重复工单。重试策略和幂等必须在工具层保证，别指望模型"记得"。
- 工具描述写"查询用户信息"，模型把用户昵称当 userId 传了。描述里必须写清参数格式，最好带反例。
- base URL 做成可配置后忘了加域名白名单，有一次模型生成了内网地址。凡是来自模型输出、要发请求的 URL，都要过校验。

## 可复用建议

1. **分层**：transport（超时/重试/熔断）→ tool（schema/鉴权/裁剪）→ agent（决策），每层独立可测。工具先脱离 agent 跑单测，再挂进去联调。
2. **返回瘦身**：给模型的数据只保留决策需要的部分，长内容拆成"列表 + 详情"两个工具。
3. **上线前回归**：备一份刁钻用例清单——缺参数、错 ID、限流、超时、空结果，逐条过一遍。

## 总结

对接外部服务的本质，不是"让模型会调 API"，而是把不稳定的网络世界包成模型可信任、可理解的窄接口：schema 是契约，传输层是保险，结构化错误是反馈回路。这三层做扎实了，Agent 和 API 的握手才算真正完成。
