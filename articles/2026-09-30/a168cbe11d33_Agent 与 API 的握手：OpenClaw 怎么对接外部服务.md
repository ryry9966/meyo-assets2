## 背景

Agent 本身只会推理，真正"能干活"靠的是工具调用。OpenClaw 对接外部服务时，难点从来不是"能不能调通一次"，而是怎么让调用**稳定、可控、可排查**。这段时间接了几个内部服务（工单系统、向量检索、一个内部 HTTP API），把经验整理成这篇。

## 问题

实践中反复出现三类故障：

1. **认证混乱**：API key 被塞进 system prompt，随上下文到处泄漏；token 过期后 Agent 反复盲目重试。
2. **工具描述模糊**：Agent 不知道"什么时候该调、参数怎么填"，要么不调，要么编参数。
3. **无超时无重试策略**：一个慢接口拖死整轮对话，用户端表现为"Agent 卡住"。

## 做法

按下面的顺序做，基本能覆盖 90% 的场景：

**1. 选对接入方式。** 优先用 MCP server 封装外部服务——协议标准、工具可跨项目复用。只是一次性脚本场景，直接写自定义 tool 更快，别过度设计。

**2. 认真写工具 schema。** `name` 用动宾结构精确命名；`description` 写清"何时用、何时不用"；参数逐个标注类型、必填性和取值格式。schema 是 Agent 唯一的"说明书"，这里省的字以后都是坑。

**3. 认证收敛。** Key 走环境变量或 secret manager，在 MCP server / 插件层注入，绝不进对话上下文。token 刷新逻辑封装在服务端封装层里，对 Agent 透明。

**4. 超时、重试、错误结构化。** 每个工具设明确 timeout（建议 10–30s）；只有幂等接口才自动重试；失败时返回 Agent 能读懂的结构化错误（错误码 + 一句人话原因），让它自己决定下一步——换参数重试、降级还是直接告知用户。

**5. 留可观测性。** 每次调用记：工具名、参数摘要、耗时、返回状态。出问题时这是唯一的现场。

## 踩坑点

- **工具注册太多**，Agent 出现选择困难，调错工具的概率明显上升。按场景裁剪，一轮任务里可见的工具别超过十个。
- **大 JSON 直接塞回上下文**。一次向量检索返回 50 条完整文档，几轮就把窗口吃光。在工具层先裁剪字段、截断长度，只回 Agent 真正需要的。
- **忽略 rate limit**。批量任务里 Agent 调用频率远超人工，429 之后不做退避就是雪崩。
- **非幂等接口配了自动重试**，结果重复创建了两张工单。重试前先想清楚接口语义。

## 可复用建议

- 把认证注入、超时重试、日志这三件套抽成**内部 MCP server 模板**，新服务对接只填 schema 和 endpoint，半小时上线。
- 错误返回统一格式：`{ code, message, hint }`，`hint` 告诉 Agent 建议动作。
- 提供一个 `dry_run` 参数，先校验参数不真正执行，联调阶段能省大量回滚成本。

## 总结

对接外部服务的本质，是把人类的工程约定（认证、幂等、限流、观测）翻译成 Agent 能理解的接口契约。契约写得越清楚，Agent 的行为越可预期。先把 schema、超时、错误格式这三件事做扎实，再谈更复杂的编排。
