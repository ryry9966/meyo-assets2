## 背景

OpenClaw 的价值在于"能动手"：查工单、写文档、同步数据，最终都要落到对外部服务的真实调用上。MCP 与插件体系把这件事标准化了——Agent 不直接摸 HTTP，而是通过一组描述清晰的工具与外界握手。但工具接得越多，翻车的方式也越多样，值得把对接流程沉淀成一套约定。

## 问题

实际对接中反复出现三类故障：

1. **鉴权散落**：API key 一部分写在配置、一部分塞在环境变量，出处不清、轮换困难，甚至混进对话上下文。
2. **工具面太宽**：把整个 REST API 原样暴露成几十个工具，Agent 选错工具、传错参数的概率随数量上升。
3. **错误被吞**：上游返回 500，工具层 catch 后返回空结果，Agent 误以为操作成功，继续执行后续步骤。

## 做法

我们的团队约定是：**一个领域一个 MCP server，一个动作一个工具**。以对接一套工单系统为例：

1. **划边界**。列出真正需要的能力（查询、创建、评论），只封装这几个动作，不做通用透传接口。
2. **写清 schema**。每个工具的 description 用一句话说明"什么时候该用我"，参数带类型和枚举。描述质量直接决定 Agent 的工具选择准确率。
3. **收口鉴权**。凭据只从环境变量或密钥文件注入 MCP server 进程，工具参数与返回值里永远不出现 token。
4. **定义错误契约**。超时、限流、业务错误统一转成结构化返回：错误码 + 人可读信息 + 是否可重试，让 Agent 能据此决定重试还是上报。
5. **写操作加闸门**。创建/删除类工具支持 `dry_run` 参数，默认返回"将要执行什么"的预览；高危动作走审批通道。
6. **可观测**。每次工具调用记录服务名、耗时、状态码，密钥字段脱敏后再落日志。

## 踩坑点

- **返回值过大**。一次查询回传全量 JSON，直接把上下文撑爆。工具层做裁剪，只返回 Agent 真正需要的字段。
- **非幂等写遇上重试**。网络超时后 Agent 重试，工单被创建两次。写接口应强制携带幂等键（如内容哈希），由服务端去重。
- **长任务同步等待**。导出报表要跑两分钟，工具调用早已超时。应拆成"提交任务 + 轮询状态"两个工具，或改走回调。
- **description 太模糊**。"处理数据"这种描述会让 Agent 在多个工具间乱猜。描述里要写清对象、动作和典型场景。

## 可复用建议

- 新接一个服务时，先回答三个问题：读还是写？幂等吗？失败后 Agent 该做什么？答案基本决定了工具设计。
- 错误信息写给两个读者：Agent（结构化、可判断下一步）和人（可读、可排查）。
- 上线前用固定输入跑一遍回归：正常路径、超时、鉴权失败各一次，确认 Agent 行为符合预期，而不是只测"能不能调通"。

## 总结

对接外部服务，本质是给 Agent 建立一套"有礼貌的握手"协议：工具面收敛、鉴权收口、错误结构化、写操作可控。做到这四点，Agent 与 API 之间就不只是能调通，而是能长期稳定地协作。欢迎在社区里分享你们对接时踩过的坑。
