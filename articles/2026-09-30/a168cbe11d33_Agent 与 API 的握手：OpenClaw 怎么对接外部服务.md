## 背景

OpenClaw 的价值不在聊天，而在动手：查库、调内部接口、触发流水线、发通知。这些动作最终都落到同一件事上——调用外部服务的 API。OpenClaw 提供两条主路：接现成的 MCP server，或者自己写一个薄插件/脚本工具。最近对接了一个内部 HTTP 服务，把过程和反复踩的坑记录下来。

## 问题

上手时最常纠结的三件事：

1. 用 MCP server 还是直接写个脚本工具？
2. 工具 schema 怎么写，agent 才不会乱传参数？
3. 鉴权、超时、报错这些脏活放在哪一层？

## 做法与步骤

**1. 先选集成路径。** 服务已有标准 MCP 实现就直接接，零成本；内部一次性接口则写一个薄 HTTP 工具，不必为它单起一个 MCP 进程。我的判断标准：被多个 agent 共享、复用次数大于两次，走 MCP；否则薄插件够用。

**2. 把工具定义当提示词写。** LLM 是靠工具的 description 和参数说明决定怎么调的。参数名用领域语言（`user_id` 而不是 `id`），description 里写清单位、格式和副作用，例如“此操作会创建真实工单”。

**3. 鉴权放配置层。** token 走环境变量，配置文件只留引用；不同服务用不同凭据，方便单独轮换。

**4. 错误要“说人话”。** 返回给 agent 的错误别只抛堆栈，翻译成一句话加可行动建议：`rate_limited：请 30 秒后重试`。agent 拿到结构化错误才有能力自愈。

**5. 剪裁返回体。** 接口返回 200 个字段，agent 往往只需要 5 个。在适配层做字段筛选和摘要，省 token，也减少幻觉空间。

## 踩坑点

- **超时没设**：agent 会一直等，整个会话卡死。统一 10–30 秒超时并显式报错。
- **幂等性**：agent 重试一次 POST，结果创建了三张工单。写操作务必带幂等键，或在工具层去重。
- **把 200 当成功**：不少内部接口 HTTP 200 但 body 里业务码非零，适配层要把业务错误翻译出来。
- **日志泄密**：调试日志把 Authorization 头整个打出来了。日志脱敏应该进代码评审清单。

## 可复用建议

- 适配层保持“薄且笨”：不做业务决策，只做转换和校验。确定性越强，agent 表现越稳。
- 一个工具一个动作。宁可多定义两个工具，也不要做一个带 mode 参数的万能工具。
- 上线前先 dry-run：让 agent 输出“将要调用的参数”由人确认，观察一周再放开自动执行。
- 工具命名带版本（如 `query_order_v2`），改参数语义时别原地改，给自己留退路。

## 总结

对接外部服务的本质不是“打通 HTTP"，而是把一个不确定的网络世界，翻译成 agent 能理解的确定性接口。选对集成路径、把工具定义当提示词写、错误和幂等想在前面，这次握手才算握牢。后续打算再写一篇 MCP server 从零到上线的完整记录，欢迎在社区里交流各自的对接姿势。
