## 背景

Agent 本体只负责推理，真正干活的永远是它身后的工具。在 OpenClaw 的典型场景里，Agent 要查数据库、调内部服务、触发第三方 API，对接质量直接决定自动化任务的可靠性。MCP 生态起来之后，"接一个服务"有了更标准的路径，但标准协议不等于开箱即用——握手阶段的细节仍然要自己处理。

## 问题

实际对接中反复出现三类故障：

1. **Agent 不会用工具**：参数填错、该调不调、不该调乱调；
2. **调用结果不可控**：超时挂死、返回体巨大撑爆上下文、报错信息 LLM 读不懂；
3. **安全与稳定性缺位**：密钥写进配置文件、写操作无幂等、失败重试造成重复提交。

## 做法与步骤

**1. 选对接路径。** 简单的 HTTP 服务用轻量插件包一层即可；需要跨项目复用、或想接入现成生态的，写成 MCP server。原则是先跑通再标准化，不要一上来追求架构完美。

**2. 把工具 schema 当接口文档写。** 名称用动词短语（`query_order_status`，而不是 `api2`），描述里写清楚"什么时候该用、什么时候不该用、参数格式举例"。LLM 靠这段文字做决策，写得含糊它就只能靠猜。

**3. 做一层薄适配。** 不要把上游原始响应直接塞回上下文。适配层负责三件事：字段裁剪（只留 Agent 需要的）、错误翻译（把 500/401 变成一句 LLM 能理解且知道下一步怎么办的人话）、单位与时间格式归一。

**4. 补齐工程兜底。** 每个外呼设 timeout；读操作加指数退避重试；写操作带幂等键；密钥走环境变量注入，日志统一脱敏。

**5. 先用 mock 验一遍。** 本地起一个 mock 服务，模拟成功、超时、报错三种响应，把 Agent 的决策链路验通，再切真实上游。

## 踩坑点

- **工具描述写得太"全"反而害事**：一个工具塞十几个可选参数，Agent 选择困难。拆成小工具，每个只做一件事。
- **报错只透传状态码**：Agent 看到 `HTTP 500` 只会机械重试。错误信息要带"建议动作"，比如"参数 date 格式应为 YYYY-MM-DD"。
- **无脑重试写接口**：下单、发通知这类操作，重试就是事故。只有确认幂等的操作才允许自动重试。
- **返回体不裁剪**：一次列表查询返回几千条记录，上下文直接被吃光，后续推理质量骤降。默认分页 + 截断 + 摘要。
- **忽略工具的启用开关**：出问题时需要能一键停用单个工具，而不是重启整个 Agent。

## 可复用建议

- 建一个统一的工具适配模板：入参校验、timeout、重试、错误翻译、日志五件套固定下来，新工具照着填空。
- 工具调用日志记录 args、耗时、结果状态——排障时这是唯一可靠的证据链。
- 对上游做健康检查与降级：服务不可用时让 Agent 明确说"暂时不可用"，而不是拿着旧数据继续编。

## 总结

Agent 与 API 的握手本质上是一份契约：schema 是语言，适配层是翻译，错误处理是反馈通道。在 OpenClaw 侧把工具定义写清楚、把响应裁剪干净、把失败路径设计好，Agent 输出的稳定性会有肉眼可见的提升。对接没有黑魔法，全是工程活。
