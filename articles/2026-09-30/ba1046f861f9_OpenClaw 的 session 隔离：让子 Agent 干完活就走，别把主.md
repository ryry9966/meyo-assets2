## 背景

OpenClaw 的主会话是长期存活的：你跟助手聊天、它维持上下文、往 memory 里沉淀长期记忆，都在这一条线上。但实际用起来，大部分工作并不是"对话"，而是任务——定时抓数据、批量处理文件、调 MCP 工具做排查。这类工作如果在主会话里直接跑，工具输出、中间推理、报错重试会全部灌进上下文。

## 问题

污染的典型症状有三个：

- 主会话 compaction 明显提前，聊天时助手"忘事"越来越快；
- 子任务的报错日志混进对话历史，之后的回答风格被带偏；
- memory 文件被任务过程细节写脏，长期记忆里全是临时信息。

根本原因只有一个：任务上下文和对话上下文没有分家。

## 做法

1. **任务型工作一律 spawn 子 agent**。子 agent 拿到独立的 session 文件，和主会话物理隔离，跑完即弃。
2. **要求结构化回传**。spawn 指令里写明：最终只返回一段摘要加关键字段，不要把过程贴回来。主会话只接收这段摘要。
3. **细节按需拉取**。需要回看时用 sessions_history 查子 agent 的历史，而不是让子 agent 主动倾倒全部日志。
4. **权限收敛**。子 agent 的工具面按任务最小化配置，MCP server 和插件按需挂载；写 memory 的权限默认不给子 agent。
5. **定时任务走独立通道**。cron / webhook 触发的任务固定用独立 agent 和专属 session key，绝不复用主会话的 key。

## 踩坑点

- **"顺便在对话里跑一下"是最常见的破口**。一次图省事，几千 token 的工具输出进了主上下文，之后每一轮对话都在为它付利息。
- **子 agent 之间复用 session key 会串台**。A 任务的上下文出现在 B 任务里，排查时非常迷惑。key 按任务命名，用完即弃。
- **子 agent 直接写共享 memory**。过程性结论被沉淀成长期记忆。要么禁写，要么让它把"值得记的"作为结果字段返回，由主会话决定是否入库。
- **嵌套 spawn 层数太深**。失败时链路难查。控制在一到两层，更深的逻辑拆成顺序调用。
- **隔离不等于不管**。子 agent 的超时、重试、失败摘要，都要在 spawn 指令里事先约定，否则任务静默失败你都不知道。

## 可复用建议

- 一个好记的心智模型：**主会话是桌面，只放结论和当前工作；子 agent 是车间，脏活、日志、中间态全留在车间**。
- 把"独立 session + 最小权限 + 结构化回传"写成团队 spawn 模板，每次复用，不要临场发挥。
- 定期清理子 agent 的 session 文件——它们是日志，不是资产。
- 排查污染时，先看主会话最近一次 compaction 的时间点，往前找体积异常大的工具输出，通常一抓一个准。

## 总结

session 隔离不是什么高级特性，本质是纪律：任务进车间，结论回桌面。每次 spawn 前想清楚三件事——独立 session、最小权限、结构化回传——主会话就能长期保持干净，助手也不会越用越"失忆"。
