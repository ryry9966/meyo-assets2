## 背景

OpenClaw 默认配置通常是"一个模型打天下"：主 Agent、心跳任务、记忆整理全走同一个云端模型。跑了一段时间后有两件事很明显：一是账单里相当一部分消耗来自心跳摘要、会话总结这类**低难度、高频率**的调用；二是有些上下文（本地笔记、私人日志相关内容）我们并不希望发到云端。

## 问题

单模型策略的代价不只是"贵"：

- 云端强模型干杂活，成本和延迟都是浪费；
- 本地模型干重活（规划、代码修改、复杂工具编排），质量塌方，表现为工具调用混乱、答非所问；
- 全走云端时，隐私敏感内容被迫出机器。

所以真正要解决的是：**把任务分层，让不同层走不同模型。**

## 做法

我们采用静态分层路由，规则简单但够用。

**1. 按任务分级**

- 高风险（主 Agent 的规划、代码改动、最终回复、多工具编排）→ 云端强模型（GPT 系）
- 低风险（心跳摘要、记忆压缩、格式化、简单分类）→ 本地模型（Ollama 跑 Qwen/Llama 系）
- 涉及敏感本地文件的任务 → 优先本地，确需云端时人工确认

**2. 配置上落地**（示意，以你版本的实际 schema 为准）：

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4.1",
        "fallbacks": ["ollama/qwen2.5:14b"]
      }
    },
    "list": [
      { "id": "memory-worker", "model": { "primary": "ollama/qwen2.5:14b" } }
    ]
  }
}
```

把记忆/摘要拆成独立 agent 挂本地模型，主 Agent 保持 GPT。会话内还可以用 `/model` 临时切换，方便对比效果。

**3. 加一层 fallback**：云端偶发限流时落到本地，保证 Agent 不断线——但前提是可观测，见下面踩坑点。

## 踩坑点

- **本地模型上下文窗口**：OpenClaw 注入的系统提示 + 工具结果很长，8k 窗口的本地模型会截断到"失忆"。本地模型至少选 32k 上下文的。
- **function calling 兼容性**：不少本地模型的工具调用 JSON 不稳，症状是"工具没触发"。选官方明确支持 tool use 的模型。
- **fallback 静默降质**：出错落到本地后质量下降，用户只觉得 Agent 变笨了。日志里必须能看出每条回复用的是哪个模型；排障时用开关强制单模型，隔离变量。
- **心跳任务挂云端**：我们最初的心跳摘要没单独配模型，一个月白烧不少 token。所有高频定时任务都检查一遍走的哪条路由。
- **显存与冷启动**：Ollama 的 keep_alive 设太短会反复加载模型，设太长又和开发环境抢显存。给常驻 worker 单独配一个中等模型最省心。

## 可复用建议

- **二八原则起步**：约 20% 关键决策给云端，80% 杂活留本地，先跑两周看数据再调比例。
- **小评测集**：每类任务准备 10–20 条样例，改路由规则前后各跑一遍，避免"感觉上没变差"。
- **粗粒度优先**：路由维度先按 agent / 任务类型划分，不要一上来做按内容的动态路由——复杂度高、收益存疑。
- **成本按任务类型统计**：只看每日总量，没法证明优化有效。

## 总结

多模型路由不是炫技，而是在质量、成本、隐私之间做显式取舍。OpenClaw 的 per-agent 模型配置加上 fallback 链，已经足够搭出一套静态分层路由：强模型管决策，本地模型管体力活。先粗后细，先静态后动态，用数据决定下一步。
