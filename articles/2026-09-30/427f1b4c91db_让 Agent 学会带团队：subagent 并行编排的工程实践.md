单 agent 跑长任务时，常见三种症状：上下文被中间过程塞满、研究/编码/写作混在一起互相污染、所有步骤串行导致一件事等半小时。最近我们把几条自动化流程改成了 subagent 编排，核心思路一句话：**主 agent 只做拆解、分发、汇总，脏活交给并行的 subagent。**

## 问题

- 主 agent 上下文有限，让它在一次会话里"查资料 + 改代码 + 写报告"，任何一步的中间产物都会挤占后续步骤的注意力；
- 串行执行慢：三个互不依赖的调研任务排队跑，纯属浪费；
- 工具权限没有隔离：研究 agent 没必要拿到文件写入权限。

## 做法

**1. 定义分工明确的 agents。** 在 `openclaw.json` 里为每个 subagent 单独配 model、workspace 和允许的 MCP 工具。研究型用长上下文模型、只读工具；编码型接终端和文件系统，workspace 用独立目录。

**2. 主 agent 充当编排者。** 收到任务先拆成互不依赖的子任务，再通过 `sessions_spawn` 给对应 agent 各开一条会话，prompt 里写清楚：目标、边界、输出格式、禁止事项。spawn 是异步的，可以一次发出多个再统一收。

**3. 约定结果契约。** 要求每个 subagent 返回固定结构的 JSON（结论、关键依据、未解决问题、产物路径），而不是把整段过程日志丢回来。主 agent 只消费摘要，上下文压力骤降。

**4. 并发上限 + 超时。** 同时最多跑 3~4 个 subagent，每个设置轮数/token 上限，超时由主 agent 记录后决定重试或放弃。

## 踩坑点

1. **上下文不会自动共享。** subagent 看不到主 agent 的历史，spawn prompt 必须自包含。我们吃过亏：以为对方知道项目背景，结果它按默认假设写了一版全错的代码。
2. **并行写同一批文件必冲突。** 两个 agent 同时改一个仓库，后提交的会踩掉先提交的。要么分目录，要么用 git worktree 隔离，最后由主 agent 合并。
3. **subagent 也会跑飞。** 没有轮数上限的调研 agent 会无限打开新网页。上限要显式给，宁可让它带着"未完成"标记返回。
4. **僵尸会话。** 编排者中途被打断，spawn 出去的会话还在后台烧钱。定期检查活跃 subagent 列表并手动清理。

## 可复用建议

- spawn prompt 模板固定四要素：**目标 / 输入材料 / 输出 JSON schema / 禁止事项**。模板化之后分发质量稳定很多；
- 编排者保持"瘦"：不做具体工作，只拆解、分发、校验、汇总。一旦它开始自己动手，编排就退化回了单 agent；
- 判断能否并行只看一条：子任务之间是否有数据依赖。有依赖就串行，别为了并行而并行。

## 总结

subagent 编排带来的收益不是"更聪明"，而是更快的完成速度、更干净的上下文、以及权限与成本的隔离——本质上是把工程里的职责分离、接口契约、资源限额搬进了 agent 世界。建议先把一条重复流程拆成"编排者 + 2~3 个专职 subagent"跑起来，再逐步扩展，比一开始就搭多层编排靠谱得多。
