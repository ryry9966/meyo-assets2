## 背景

在 OpenClaw 的插件、Agent 工作流和 MCP 工具调用里，让模型输出 JSON 是最常见的需求：函数参数、结构化抽取、中间结果传递。但只要跑得够久就会发现，同一个 prompt 下的输出格式并不稳定：有时是裸 JSON，有时包了 ```json 围栏，有时外面套了 `<answer>` 标签，有时前后还各带一句"以下是解析结果："。Prompt 里的"只输出 JSON"能降低概率，但从来不是保证。

## 问题

大多数实现只有一层解析：`json.loads(response)`，或者一条写死的正则。格式一变就抛异常，整条流水线挂掉；更糟的情况是用宽松正则硬匹配，偶尔抽错块，错误悄悄往下游传，排查成本远高于重写解析层。解析层是 LLM 和确定性代码之间唯一的边界，值得按"不可信输入"来设防。

## 做法：分层解析流水线

核心思路：先走最便宜的路径，逐级加码，每层失败再进下一层，全程记录命中的路径。

```python
import json, re

FENCE = re.compile(r"```(?:json)?\s*(.*?)```", re.S)
TAG   = re.compile(r"<(?:json|answer|result)>(.*?)</(?:json|answer|result)>", re.S)

def extract_json(text: str):
    candidates = [text.strip()]
    candidates += [m.strip() for m in FENCE.findall(text)]
    candidates += [m.strip() for m in TAG.findall(text)]
    for raw in candidates:
        try:
            return json.loads(raw), "direct"
        except json.JSONDecodeError:
            pass
    # 兜底：括号配平扫描（需感知字符串内的引号转义）
    for i, c in enumerate(text):
        if c in "{[":
            block = _balanced_slice(text, i)
            if block:
                try:
                    return json.loads(block), "balanced-scan"
                except json.JSONDecodeError:
                    continue
    # 修复通道：去尾逗号、全角引号、True/False/None 归一化后重试
    try:
        return json.loads(_light_repair(text)), "repaired"
    except json.JSONDecodeError:
        raise ParseError("no valid json", preview=text[:200])
```

实际落地时建议再加两件事：

1. **schema 校验**。抽出来是一回事，结构对不对是另一回事。用 pydantic/jsonschema 验证，失败时把校验错误信息回喂给模型重试一次，命中率很高。
2. **原始输出落日志**。raw text、命中的解析路径、修复动作一起记录，事后能回放，也能沉淀测试样本。

## 踩坑点

- **贪婪正则**：`.*` 会把"思考段里的 JSON"和"答案里的 JSON"拼在一起。用非贪婪加锚定，或者干脆用配平扫描。
- **配平计数必须感知字符串**：`{"a": "包含 } 的文本"}` 这种，朴素计数会提前截断。
- **围栏嵌套**：模型在字符串值里写 ``` 会击穿基于 FENCE 的抽取，所以围栏抽取只能当一层，不能当唯一手段。
- **别盲信修复库**：截断的 JSON 被补全成 null 后结构合法、语义已错，必须过 schema 才算通过。
- **中文场景高发**：全角引号 “ ”、尾逗号、Markdown 列表混排，修复通道要覆盖这些。
- **环境漂移**：模型升级、温度调高、上下文变长都会改变输出习惯，老 prompt 换模型后务必回归一遍解析测试。

## 可复用建议

- 全项目只留一个 `extract_json` 入口，所有插件和工具复用，不要各写各的正则。
- 把线上真实失败样本沉淀成 fixture 做回归测试，这个语料库比任何理论推演都有价值。
- 解析失败抛带类型的异常，附上原文前 200 字符；不要吞掉，也不要让链条静默降级。
- prompt 模板和解析器当同一个版本管理，改任何一侧都要跑两侧的测试。

## 总结

LLM 的文本输出本质上是一份不可信的序列化结果。解析层的正确姿势不是"写一个更强的正则"，而是分层防御：直接解析 → 围栏/标签抽取 → 配平扫描 → 修复通道 → schema 校验 → 带错误反馈的重试。每一层都便宜、独立、可测试，合起来能吃掉绝大多数格式漂移。剩下的极少数失败，靠日志和 fixture 持续喂养这套流水线就够了。
