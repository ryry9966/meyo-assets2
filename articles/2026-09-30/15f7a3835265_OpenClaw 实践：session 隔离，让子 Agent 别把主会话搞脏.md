## 背景

用 OpenClaw 跑自动化时间长了，最常见的崩坏方式不是报错，而是**变慢、变贵、变笨**。主会话是长期上下文：它记着你的偏好、项目状态和历史决策。一旦把重活直接丢进主会话——批量读文件、跑长任务、调 MCP 工具拉回大段输出——上下文就会被中间产物填满。

## 问题

实际表现通常是三类：

1. **Token 消耗线性膨胀**：几轮子任务之后，每次请求都拖着一大堆早已无关的工具输出；
2. **中间结论“渗”进主会话**：子任务的临时状态被主 agent 记住，后续回答开始引用这些过期信息，方向被带偏；
3. **并发互相踩**：多个子任务同时写同一个工作目录，主会话还以为事情都做完了。

三件事根因相同：**子 Agent 和主会话共享同一个 session**。

## 做法

我们团队现在的固定套路是四步：

1. **派生时开独立 session**。派生（spawn）子 agent 时显式声明隔离 session，子 agent 从白纸开始，只带任务描述和最小必要上下文，不继承主会话的聊天历史。
2. **约定回传协议**。子 agent 结束时不回传原始过程，只回传三段式结构化摘要：**结论 / 变更清单 / 遗留风险**，并给条目和字数设上限。
3. **工作目录隔离**。子任务在独立子目录或独立 workspace 里干活，用完归档或即弃，避免并发写冲突。
4. **生命周期管理**。给子 agent 设超时和显式终止；长任务把状态落盘到文件，而不是靠会话记忆续命。

**验证方法**：派生后翻主会话记录，应该只能看到摘要；子任务的完整过程去 agents 目录下对应的独立 session 文件里找。找不到差异，说明隔离没生效。

## 踩坑点

- **隔离了 session 没隔离 workspace**：两个子 agent 并发写 `~/main-project`，会话是干净的，文件系统脏了，主会话拿到的“结果”互相覆盖。
- **回传摘要太“全”**：把子 agent 的最后一条完整回复原样塞回来，等于换了个方向污染主会话。摘要必须裁剪。
- **忘了回收**：隔离 session 文件也会累积，agents 目录下的历史 session 要定期清理，否则磁盘和排查成本都在涨。
- **最小上下文给太少**：子 agent 缺关键约定（代码风格、路径规范），产出对不齐，主会话还得返工。隔离不等于断联，“宪法级”约束要写进任务描述。

## 可复用建议

- 判断标准一句话：**这个子任务的中间过程，主会话以后还需要看吗？** 不需要 → 隔离。
- 回传只用三段式：结论 / 变更清单 / 风险，超限就砍。
- 子 agent 的工具权限按任务最小授予，不要默认继承主会话的全部 MCP 工具。
- 把会话卫生当例行运维：定期看 session 目录大小、清理孤儿任务、检查并发目录冲突。

## 总结

session 隔离的本质是**信息分层**：主会话保留“状态和决策”，子 agent 消化“过程和噪音”。OpenClaw 提供了隔离机制，但边界要自己画——回传什么、在哪干活、何时回收，这三条画清楚了，长跑的自动化才不会越跑越沉。
