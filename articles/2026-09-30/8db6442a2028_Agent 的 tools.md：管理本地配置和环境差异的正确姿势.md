# Agent 的 tools.md：管理本地配置和环境差异的正确姿势

## 背景

跑 Agent 做自动化的人迟早会撞上同一个问题：同一套指令，在公司笔记本上跑得好好的，搬到家里的服务器或 CI 容器里就开始报错。原因不在模型，而在环境——路径、包管理器、shell、工具版本、代理设置，每台机器都不一样。tools.md 就是为这个场景准备的约定：用一个 Markdown 文件把"这台机器上有什么、怎么调"显式写下来，Agent 启动时读取，而不是靠提示词硬编码，也不是每次会话现场教学。

## 问题

常见的三种失败姿势：

1. **写死在系统提示里。**"构建用 `~/scripts/build.sh`"，换台机器路径不存在，Agent 开始自由发挥。
2. **散落在对话里。**这次告诉它"这台机器用 apt"，下次新会话又忘了，知识不可积累。
3. **假设环境一致。**提示词里写 `brew install`，到 Linux 容器直接失败；容器里能跑的命令在 macOS 上又未必有。

本质是环境的隐性知识没有被结构化，Agent 只能猜。

## 做法：两层结构 + 一个探测脚本

推荐"全局 + 项目"两层结构：

- **机器级** `~/.agent/tools.md`：描述这台机器的通用环境——OS、包管理器、shell、代理、常用工具的真实路径和版本。
- **项目级** `<repo>/tools.md`：只写项目相关差异——构建命令、虚拟环境位置、前置条件。项目级覆盖全局级同名条目。

每个工具条目建议固定字段：命令、前置条件、版本、失败回退。例如：

```markdown
- node: ~/.nvm/versions/node/v20/bin/node
  前置: 新 shell 需先 source nvm
  回退: 版本不对时用 nvm use 20
```

基线不用手写。写一个二十行的 probe 脚本，探测 `which node`、`python3 --version`、`echo $SHELL` 这类信息生成草稿，再人工补充语义说明（"为什么用它""什么时候会失败"）。探测脚本可以进 dotfiles，语义部分自己维护。

**密钥永远不进 tools.md**。只写"token 从 `~/.config/xxx/env` 读取"，不写值本身。

## 踩坑点

1. **写成百科全书。**四五十个工具全列上去，Agent 的注意力被稀释，反而抓错重点。只写高频和易错的。
2. **只写不更新。**工具升级后文件过期，Agent 按旧路径调用必然失败。在装新工具的流程里加一步"顺手更新"，或让 probe 脚本定期校验漂移。
3. **和 MCP 重复。**MCP server 已暴露的能力，不要再写一份手工命令，两处描述漂移后 Agent 行为不可预测。
4. **描述太含糊。**"用我的脚本构建"——哪个脚本、什么参数、在哪个目录执行，全靠 Agent 猜。
5. **缺环境标注。**有平台差异的条目要写清"仅 macOS"或"容器内路径不同"。

## 可复用建议

- 固定四段模板：**环境概述 / 常用工具表 / 已知差异 / 禁止事项**。最后一段很实用，比如"不要用 sudo""不要全局 pip install"。
- 机器相关内容留在本地，公共部分可团队共享，共享前跑一遍脱敏检查。
- 把 probe 脚本挂到登录 shell 或 CI 里，tools.md 与真实环境漂移时能第一时间发现。

## 总结

tools.md 做的事，是把"每台机器不一样"这件烦人的事，变成一份版本化的、Agent 可读的显式声明。核心原则四条：**分层**（全局 + 项目）、**精简**（只写高频易错）、**可校验**（脚本探测 + 定期对账）、**不含密钥**。做到这四条，同一套 Agent 配置跨机器迁移的成本会明显下降，出问题时也多了一个能一眼定位的排查入口。
