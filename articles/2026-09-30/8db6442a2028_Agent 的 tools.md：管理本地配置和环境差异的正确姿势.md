## 背景

如果你和我一样，在不止一台机器上跑 Agent——一台 macOS 开发机、一台 Linux 服务器、再加几个容器化的测试环境——大概率遇到过这种场景：同一个任务，在这台机器上好好的，换台机器 Agent 就开始用错的包管理器、找不到对的 Python、或者往一个不存在的路径写文件。

系统提示词是全局的，但环境是本地的。tools.md 就是补这个缝隙的文件：Agent 启动时读取它，用来了解"这台机器"的实际情况。它不是配置中心的替代品，而是把环境事实从提示词里拆出来，按机器落地。

## 问题：三种常见的错误姿势

1. **环境信息硬编码进全局提示词**。换机器就要改提示词，改完忘记同步，Agent 带着过期认知继续干活。
2. **什么都不写，指望 Agent 自己探测**。探测费 token、费时间，而且不一定准——shell 别名、代理设置这类东西，Agent 探测不到。
3. **把 secrets 顺手写进 tools.md**。文件跟着 workspace 同步，密钥跟着走，迟早出事。

## 做法：分层 + 只写事实

我目前用两层结构：

- **全局层**：workspace 里的通用约定，所有机器共享。比如"回复用简体中文""不主动执行删除类命令""优先用 uv 而不是 pip"这类与机器无关的规则。
- **机器层**：每台机器一份本地覆盖文件，不入 git。只写事实，不写观点。

机器层我固定的骨架大概是这样：

```markdown
# 本机环境
- OS: Debian 12 (apt)
- Python: /usr/local/bin/python3.12 (系统级，勿动)
- 网络: 需走 http://127.0.0.1:7890 代理
- 禁区: ~/data 只读，不要写入
```

几条原则：

- 每条都是可执行的陈述，不写解释和背景故事。Agent 每轮都要读，篇幅就是 token。
- 路径写绝对路径。"用 python3"在不同机器上可能指向 3.8，也可能指向 3.12。
- 差异点优先写"禁区"，其次写"怎么做"。告诉 Agent 什么不能碰，比罗列所有该做的事更有性价比。
- secrets 一律不进 tools.md，走环境变量或密钥管理器，文件里只留一句指向。

## 踩坑点

- **全局层和机器层写矛盾指令**。Agent 不会帮你仲裁，表现通常是行为不稳定。约定机器层永远覆盖全局层，并定期全文搜一遍冲突项。
- **系统升级后文件过期**。我升级过一次 Python 主版本，忘了改 tools.md，Agent 按旧路径调了两天解释器。现在"改环境必须同步改 tools.md"已经进了部署 checklist。
- **写成散文**。早期我写过几百字的环境说明，实测 Agent 对长段落里关键约束的召回明显变差，改成一行列一项后稳定很多。

## 可复用建议

- 写一个 bootstrap 脚本生成机器层初始版本：探测 OS、包管理器、运行时版本，人工复核后落盘，避免手抄漏项。
- 机器层文件加进 `.gitignore` 和同步排除清单，这是防 secrets 泄漏的最后防线。
- 每月或每次大版本升级后花五分钟做一次环境审计：路径是否还准、禁区是否还成立。

## 总结

tools.md 的价值不在于"多一个配置文件"，而在于把环境差异从提示词和运气里剥离出来，变成一份机器可读、人工可审的事实清单。全局层管约定，机器层管事实，secrets 走密钥通道——分层清楚了，Agent 在哪台机器上表现都一致。
