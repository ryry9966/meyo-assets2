## 背景

OpenClaw 的 Agent 默认是被动模型：你发消息，它响应。但在值班类场景——盯 CI、看磁盘、定时汇总——被动意味着你成了人肉定时器。OpenClaw 内置了一个很小的机制：heartbeat。每隔一段时间（默认约 30 分钟，可在 `agents` 配置的 heartbeat 项调整，键名以所用版本文档为准），系统会"戳"一下 agent，并把工作区根目录的 `HEARTBEAT.md` 内容注入这次唤醒。agent 读一遍清单，要么执行需要做的事，要么回复 `HEARTBEAT_OK`——这条回复会被系统吞掉，不会推给你。

## 问题

`HEARTBEAT.md` 本身没有任何魔法，它就是一段 markdown。真正的问题在于怎么写：写成愿望清单，agent 每次心跳要么胡乱动作要么干脆沉默；写成长文档，每个 tick 白烧 token；写成 cron 表达式，模型根本不按 cron 语义执行。这个文件写得好不好，直接决定你拥有的是一个安静的值班员，还是一个每半小时骚扰你一次的机器人。

## 做法

第一步，在工作区根目录建 `HEARTBEAT.md`，每条按"条件 + 动作 + 沉默条款"写：

```markdown
# HEARTBEAT.md

## 每次心跳
- 检查 ~/logs/ci 最近新增的 FAIL：有则汇总最近一次失败原因与链接，无则 HEARTBEAT_OK。

## 工作日上午
- 本地时间 09:00 后且今日摘要未生成时，汇总昨天 git 提交，三行以内。

## 低频
- df -h / 使用率超过 85%，且最近 24h 未提醒过才输出；状态写入 .heartbeat-state.json。
```

第二步，按实际需求调整心跳间隔，夜间和低频任务拉长。

第三步，跑一周看日志：哪些条目真触发过、哪些每次空转、有没有重复提醒，按结果删减。

## 踩坑点

1. **文件每 tick 全量注入上下文**。20 行以内为宜，注释和背景说明都是纯成本。
2. **时间语义是"软"的**。模型按心跳时刻自行判断，粒度下限就是心跳间隔，"每小时第 7 分钟"这种写法没有意义。
3. **动作必须幂等**。磁盘超阈值这类条目，不做"已提醒过就跳过"的判断，就会每 30 分钟提醒一次。让 agent 把状态写进一个小 state 文件是最省事的解法。
4. **心跳触发的工具调用是真实执行的**。MCP/插件的写权限按最小化配置，别让心跳拿到能改关键配置的权限。
5. **`HEARTBEAT_OK` 是降噪阀**。每条都写清"什么情况下不做任何事"，否则它每次心跳都找话说。
6. **别把密钥、token 写进去**，它每次都会进模型上下文。

## 可复用建议

- 模板三要素：可测的判定条件、小而具体的动作、明确的沉默条款。
- 状态外置：需要跨心跳记忆的判断写文件，不依赖对话历史。
- 从 2~3 条起步，观察一周再扩。心跳清单和 cron 一样，蔓延起来就没人看了。
- 适合放的：失败重试提醒、日报汇总、磁盘/证书到期检查、定时抓取摘要。不适合放的：需要人拍板的长任务链。

## 总结

`HEARTBEAT.md` 把 agent 从问答机变成值班员，本质是一个成本很低、语义很软的调度原语。它可靠与否不取决于机制，而取决于你写清单的工程纪律：可测的条件、幂等的动作、明确的沉默。先让它少说话，再让它多做事。
