## 背景

给 agent 配记忆（memory_recall）时绕不开一个问题：召回用什么检索。我的场景是：agent 把用户偏好、项目约定、踩过的坑写成 memory 条目存进本地库，下次对话按需召回。条目几百条，单条几十到几百字，量级不大但召回质量直接决定 agent 像不像"记得你"。

## 问题

一开始只接了向量检索（embedding + 余弦相似度），用着用着发现两类失效：

- 问"上次 5173 端口冲突怎么解决的"，语义检索返回一堆讲端口概念的条目，偏偏漏掉那条记着具体命令的；
- 反过来，纯关键词也撑不住：查"之前怎么处理构建慢"，召回不了写着"编译耗时高"的条目。

一句话：语义检索泛化好但丢精确 token，全文检索保精确但不认同义改写。这不是选型口味问题，是两类查询天然存在。

## 做法

最后两条路都留，走混合召回：

1. **全文路**：SQLite FTS5，memory 写入时同步建索引，查询走 BM25；
2. **语义路**：中文小模型出向量，cosine 相似度，只取 top 20；
3. **融合**：RRF（倒数排名融合），k=60，直接合并两路排名，省掉分数归一化；
4. **兜底**：结果带时间戳和来源，召回后由 agent 自己筛，不靠阈值一刀切；
5. 攒了 30 条真实 query 的评测集，每次改动跑一遍看 top5 命中率，不拍脑袋调参。

## 踩坑点

- **FTS5 默认分词对中文基本无效**，整句会变成一个 token。要么上 trigram，要么写入前先用 jieba 切词再存，这一步漏了全文路等于白建。
- **中文 embedding 别随手用英文模型**。我换成中文专用小模型后，top5 命中率差了将近一倍。
- **chunk 别贪大**。早期按整段对话切，一条 800 字，向量被稀释，"具体命令"那段根本召回不到。改到 200–300 字按语义边界切才正常。
- **相似度阈值卡太死会"召回为空"**，agent 就开始装傻。宁可多给几条让它自己判断。
- **记忆会过期**。三个月前"用 npm"的条目会一直干扰召回，最后加了时间衰减加权才消停。

## 可复用建议

- 先上全文检索 + 时间加权，够用就别上向量——多一个组件多一个故障点；
- 存条目时保留命令、路径、错误码原文，别让总结环节改写掉，这是精确召回的命根子；
- 混合召回用 RRF 而不是加权分数，两路分数量纲不一致的坑直接绕开；
- 20–50 条真实 query 的评测集，比任何直觉调参都有效；
- 换 embedding 模型前先算全量重嵌入成本，本地小模型几千条几分钟的事，API 模型攒大库就肉疼了。

## 总结

语义和全文不是二选一，是分工：精确 token 靠全文，模糊意图靠语义，RRF 把两者缝起来，时间衰减处理过期记忆。现在的召回比单路稳定得多，代价是多维护一个 FTS 索引和一个向量文件。对个人 agent 的量级，这个复杂度完全值得。
