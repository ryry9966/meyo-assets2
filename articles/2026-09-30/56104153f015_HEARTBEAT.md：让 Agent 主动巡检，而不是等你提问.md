## 背景

大多数 Agent 的交互模型是问答式的：你提问，它执行，然后沉寂。但真正有价值的自动化往往是周期性的——盯服务健康、查 CI 状态、每天汇总一次日报。OpenClaw 提供了一个很轻的机制 `HEARTBEAT.md`：放在工作区（默认 `~/.openclaw/workspace/`）的一个 Markdown 文件，Agent 会按固定间隔（默认 30 分钟）读取它并执行里面的任务，全程不需要任何人在场。

## 问题

把「主动做事」交给 Agent 有两个天然风险：一是刷屏，每次心跳都给你发一条"没什么事"；二是烧 token，心跳本身就是一次模型调用。HEARTBEAT.md 的设计目标，就是在「主动性」和「安静」之间找到平衡。

## 做法

1. 在工作区根目录创建 `HEARTBEAT.md`，写入任务清单，例如：
   - 每 30 分钟检查一次服务健康接口，连续两次失败才报告；
   - 每天早上 9 点汇总昨日 git 提交，生成三行摘要。
2. 每个任务写明「安静退出条件」：无事发生时让 Agent 回复 `HEARTBEAT_OK`，系统会把它识别为静默信号，不会推给用户。
3. 按需调整节奏：`HEARTBEAT_INTERVAL_SECS` 控制心跳周期，`HEARTBEAT_ENABLED=0` 可整体关闭。
4. Agent 自己也能编辑这个文件。直接对它说"以后每天早上提醒我看构建状态"，它会自己把条目写进去——这是它和普通 cron 脚本最大的区别。

## 踩坑点

- **指令含糊必然刷屏。**"看看有什么值得报告的"是反模式，Agent 会觉得一切都值得报告。必须写清楚"什么情况下才发消息"。
- **任务要幂等。**心跳可能在上一轮没跑完时再次触发，重复检查、重复发消息都要能容忍。
- **消耗是真实的。**每 30 分钟一次调用，一个月就是上千次；清单越长 token 越多，只放真正需要巡检的事。
- **时区问题。**心跳 prompt 里带当前时间，但"早上 9 点"是否是你以为的 9 点，先验证一次再信任。
- **别留一次性任务。**做完记得删，或让 Agent 完成后自己移除该条目，否则它会永远巡检下去。

## 可复用建议

- 用「触发条件 + 动作 + 报告条件 + 静默条件」四段式写每个任务，可验证性远好于自然语言描述。
- 把心跳消息路由到一个专门的低优先级会话或频道，避免污染主对话。
- 先用较长间隔（比如 60 分钟）试运行一两天，观察消息量和 token 消耗，再收紧。
- 分工上，HEARTBEAT.md 适合周期巡检；事件驱动的即时任务仍交给 cron、webhook 加 MCP 工具，两者互补而不是替代。

## 总结

HEARTBEAT.md 的本质是把"值班表"交给了 Agent：文件即任务清单，心跳即巡检循环，静默 token 保证不打扰。写好它的关键不在功能本身，而在纪律——每个任务都要定义清楚"什么时候闭嘴"。做到这一点，Agent 才能真正从"等你提问的工具"变成"值得托付的值班员"。
