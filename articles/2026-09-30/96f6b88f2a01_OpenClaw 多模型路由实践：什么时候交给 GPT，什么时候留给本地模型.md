## 背景

OpenClaw 接模型的方式比较开放：云端 API 和本地推理服务（Ollama、vLLM 起的都行）可以同时挂在同一份配置里。但实际用下来，大多数人会走向两个极端——要么所有任务都打云端大模型，月底账单难看；要么为了省成本全切本地，agent 在复杂任务上频繁翻车。我们的自动化工作流跑了几个月，逐步收敛出一条清晰的路由策略，这里把判断标准和落地步骤整理出来。

## 问题

核心矛盾是：agent 的不同环节对模型能力的需求差别很大，但默认配置只有一个模型。规划、工具编排这类任务需要强推理和稳定的 function calling；而摘要、分类、格式清洗这类任务，本地 7B~14B 模型已经够用。用同一个模型服务所有环节，要么浪费，要么不可靠。

## 做法

1. **任务分型。** 先把手头工作流拆成四类：主循环规划与工具调用、长上下文阅读、批量轻量处理（摘要/打标/抽取）、敏感数据处理。
2. **双 provider 配置。** 云端模型承担第 1、2 类；本地模型（我们用 vLLM 起的 Qwen 系列）承担第 3、4 类。敏感数据强制本地，这条不参与路由判断，是硬规则。
3. **绑定而非猜测。** 路由按任务类型静态绑定，不要按关键词动态猜。关键词路由短期看着聪明，维护两周后就是灾难。
4. **降级链。** 云端模型超时或限流时落到本地，保证 agent 不中断；反过来不成立——本地失败直接报错并告警，不要静默升级到云端，避免敏感数据外泄。
5. **记账与抽查。** 每类任务记录 token 消耗和耗时，每周抽样对比本地与云端的输出质量，路由规则据此调整。

## 踩坑点

- **本地模型的 function calling 兼容性是最大的坑。** 同一套工具 schema，云端稳定通过，本地模型偶发参数格式错误。结论：主循环不要用本地模型，哪怕它宣称支持工具调用。
- **上下文长度。** 本地模型窗口小，长对话会被截断，agent 表现为“忘了前面的步骤”，非常难排查。交给本地模型的任务要主动控制输入长度。
- **本地推理慢会拖垮整条自动化链路**，注意给工具调用环节单独设超时。
- **降级链要防循环：** 云端失败落本地，本地重试又触发云端，来回震荡。降级只走一层，之后就是明确的失败。

## 可复用建议

- 先窄后宽：只把一类低风险、大批量的任务先切到本地，跑稳了再扩大范围。
- 用任务类型路由，不用关键词路由。
- 云端永远作为最终兜底，但敏感数据除外——那类任务的兜底是“失败并告警”，不是换模型。
- 路由日志留全，出问题时能回放当时每一步用的是哪个模型。

## 总结

多模型路由的价值不在“省了多少钱”，而在于让 agent 的每个环节都跑在能力匹配的模型上。静态绑定 + 一层降级 + 硬性隐私规则，这套组合简单、可维护，我们跑了三个月没再大改过。路由规则不需要聪明，需要的是稳定和可解释。
