## 背景

LLM 本身无状态。用 OpenClaw 做常驻开发助手半年，我的结论是：**"记住偏好"不是模型能力问题，是工程问题**。它最初每天重新问我构建工具、代码风格、部署习惯，直到我把记忆当成独立子系统来设计，体验才真正稳定下来。

## 问题：三种常见但失败的做法

1. **全塞进 system prompt**：上下文膨胀、成本上升，核心偏好被噪音稀释，注意力反而更差。
2. **历史全量向量化检索**："上周随口一提"和"长期偏好"被平等召回，噪声大。
3. **让模型"自己记住"**：没有持久化层，会话一断全丢，还容易幻觉出你没说过的偏好。

## 做法：三层存储 + 三条路径

**存储分层**（全部纯文本，放 workspace 里）：

- **核心档案**：一个不超过 500 token 的文件，只放稳定偏好——语言、代码风格、工具链、沟通语气。每轮加载，保证底线记忆。
- **项目记忆**：每个项目一个目录，记录约定、路径、部署方式，通过 memory_search 按需检索，不默认加载。
- **情景笔记**：每日会话摘要，由子 Agent 用廉价模型抽取"值得记的点"，写入带日期的 markdown，作为记忆的原材料。

**写入路径**分两条：显式（用户说"记住 xxx"，直接落盘）与隐式（会话结束后抽取）。每条记忆带 `scope / timestamp / source` 三个字段；冲突时新条目显式覆盖（supersede）旧条目并保留历史，不做静默合并。

**读取路径**做触发规则：核心档案默认加载；项目记忆只在命中项目关键词或用户显式询问时检索。不要每轮都跑一次搜索，延迟和噪声都不划算。

**更新路径**：每月跑一次 consolidation（cron 即可）——合并重复、删除过时、把高频出现的情景笔记晋升为正式偏好。

## 踩坑点

- **记忆无限膨胀**：三个月后检索质量明显下降。设条目上限 + 定期 GC，宁可删。
- **冲突未处理**："用 pnpm"和"换 npm 了"同时被召回，必须显式 supersede，不能靠模型临场判断。
- **隐式抽取幻觉**：模型会把推测写成事实。隐式记忆必须带原文引用，无引用条目在 consolidation 时降权。
- **跨项目污染**：A 项目的部署习惯混进 B 项目。scope 在写入时就定死，别指望检索阶段过滤。
- **写入不可见**：静默写入会摧毁信任。落盘时在会话里明示"已记录：xxx"，且文件允许用户直接手改——文件系统本身就是最好的管理界面。

## 可复用建议

- 先用 markdown + grep，条目过千之前别急着上向量库，结构化文件的可控性远高于黑盒索引。
- 始终加载的核心档案，500 token 是预算红线，超了就下沉到项目记忆。
- 写入要便宜且频繁，读取要挑剔且有触发条件。
- 把记忆当代码测：维护一组"它是否记得 X"的回归用例，换模型或改提示词后跑一遍。
- 这是数据工程问题：schema、生命周期、清理策略，比"更聪明的总结 prompt"重要得多。

## 总结

让 Agent 记住你，靠的不是更强的模型，而是克制的设计：分层存储、显式覆盖、按需读取、定期清理、全程透明。这套方案不依赖特定框架，OpenClaw 的 workspace + cron 就能跑通，迁移到别的 Agent 框架同样成立。建议从核心档案这一个文件开始，先跑起来，再逐步长出检索和 consolidation。
