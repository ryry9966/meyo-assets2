# 背景与问题

绝大多数 Agent 部署是纯被动模式：你不发消息，它永远沉默。日报、巡检、提醒这类"本该有人主动做"的事，最后还是靠人记得发起。cron + 脚本能定时执行，但缺乏判断力——脚本不知道"这条错误值不值得吵你"，于是要么静默漏报，要么凌晨三点给你发全套日志。

OpenClaw 的 heartbeat 机制就是为这个缝隙设计的：后台调度器按固定间隔（默认 30 分钟，可在配置中调整）唤醒一次 Agent，把工作区根目录下的 `HEARTBEAT.md` 内容作为输入交给它，由模型判断这轮该做什么、该不该打扰你。文件不存在或为空时直接跳过，不产生调用。换句话说，HEARTBEAT.md 是你给 Agent 的一份"值班须知"。

# 做法

1. **建文件**：在工作区根目录创建 `HEARTBEAT.md`，写一个短清单。每条任务按"检查什么 → 做什么 → 什么条件下才上报"三段式写，例如：
   - 检查 GitHub 通知，只有出现等待我 review 的 PR 才发消息；
   - 每天早上汇总系统日志中的新报错模式，无新增就保持安静；
   - 检查工作区磁盘占用，超过 80% 才提醒。
2. **调间隔**：在配置里设置心跳间隔和推送目标（发到哪个频道/会话），初期建议拉长间隔观察。
3. **写沉默条款**：明确加入"没有值得说的事就什么都不发"。这条比任何任务都重要，否则你会每半小时收到一句"暂无异常"。
4. **灰度上线**：先跑一个轻量任务几天，观察 token 消耗和打扰频率，再逐条增加。

# 踩坑点

- **每次心跳都是一次真实的模型调用**。文件越长，常驻成本越高。保持 3–5 条活跃任务，做完的立即删除。
- **"每 30 分钟汇报一次"是反模式**。心跳的价值在"发现异常才出声"，例行汇报应限定时间触发，而不是每轮都执行。
- **任务耗时不要超过心跳间隔**，否则会重叠堆积。心跳里只放分钟级任务，长任务交给脚本或独立会话。
- **MCP 工具凭证过期会导致静默失败**。在任务里要求 Agent：工具调用失败必须上报，不许默默跳过。
- **"每天早上"这类相对时间依赖时区配置**。配错了，"早安播报"会准时出现在半夜三点。

# 可复用的建议

把 HEARTBEAT.md 当成一份 SRE 值班手册来维护：每条 = 触发条件 + 动作 + 上报阈值，核心模式是"检查 → 判断 → 只浮出异常"。建议把文件纳入 git 管理，一来可审计你授予了哪些"主动性"，二来出问题能快速回滚。另外，心跳任务只有和 MCP 工具组合才有威力——没有工具的 Agent 心跳只能看，有工具的才能查、算、动手。写任务时多问一句：这条任务失败时，我怎么知道它失败了？

# 总结

HEARTBEAT.md 把 Agent 的交互模型从"你拉它答"变成"它带着判断力推"。工程上的全部难度在于：写出知道什么时候该闭嘴的任务。管好这个文件，它是个称职的值班员；管不好，它就是个每半小时打扰你一次的噪音源。
