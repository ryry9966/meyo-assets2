## 背景

日常开发里 Git 操作占比不小：写 commit message、切分支、合并后清理、推送前检查。这些动作高度模式化，正好适合交给 agent。OpenClaw 接上 MCP git 工具后，让助手读仓库状态、生成提交、管理分支是可行的。但直接放开权限会出事，这篇记录我们团队跑了一个多月的配置方案。

## 问题

没上自动化之前，几个痛点反复出现：

1. commit message 质量随机，回溯问题时找不到线索；
2. 分支命名混乱，`feature/`、`fix/`、个人缩写混用；
3. 合并完忘删本地分支，几周后一堆 stale branch；
4. 更危险的：agent 在错误状态下执行操作——没看清 diff 就 `add` 全部，或者把调试代码提交进去。

## 做法

**第一步：接 MCP git 服务，只挂最小工具集。** 初期只开 `status` / `diff` / `log` / `branch` 这类只读工具，跑一周确认 agent 判断准确后，再放开 `add` / `commit` / `branch -d`。

**第二步：约定写进 agent 可读的项目级文件。** 在仓库里放一份 skill/规范文档，agent 每次会话自动读取：commit message 用 Conventional Commits、中文正文、单次提交只做一件事；分支命名 `feature/日期-短描述`；push 前必须先 `pull --rebase`。

**第三步：护栏规则写死在系统提示里：**

- 任何写操作前必须先跑 `git status` 和 `git diff`，禁止凭对话记忆判断仓库状态；
- 禁止 `add -A`，逐文件 add，并在提交说明里写明改动理由；
- 禁止 force push，禁止操作主分支，push 前停下来等人工确认；
- 每次 git 操作追加记录到日志文件，方便事后审计。

**第四步：提交前检查接入流程。** agent 提交前自动跑 lint 和测试，失败就不提交，直接汇报原因。

## 踩坑点

- **最大的坑是 agent 凭上下文"想象"文件状态。** 有一次它把一个我早已 revert 的改动又提交回去，因为它引用的是对话早期看到的 diff。解法就是上面的强制规则：状态判断只认工具实时输出。
- **auto-commit 循环：** agent 修 bug 时把自己的中间态提交了七八次，历史很脏。后来规定 agent 自身的修改走独立 WIP 分支，任务完成由我人工确认后再合并。
- **大仓库 diff 撑爆上下文：** 让它先跑 `git diff --stat` 概览，再按文件挑重点看，不要全量喂。
- **MCP git server 的目录权限要严格限定**，不要让它能触达仓库之外的路径。

## 可复用建议

1. **权限渐进**：只读 → 本地写 → push，每阶段观察一周再放权；
2. **约定进文件而不是口头**：agent 每次会话都读，团队新人也能直接复用同一套规范；
3. **写操作保留人工确认点**：让 agent 产出"待执行命令列表"再执行，比直接执行稳得多；
4. **日志即审计**：所有 agent git 操作落盘，出问题能完整回放。

## 总结

AI 助手管 Git 的价值不在"打字快"，而在把团队规范固化成机器可执行的规则。权限收敛、状态实时校验、人工确认点——这三件事做扎实，自动化的收益才是正的。整套配置一个下午能搭完，建议从只读模式开始试，跑顺了再逐步放权。
