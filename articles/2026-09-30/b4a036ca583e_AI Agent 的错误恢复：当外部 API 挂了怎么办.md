## 背景

在 OpenClaw 里跑长任务 agent，外部依赖是常态：LLM 供应商、搜索工具、MCP server、内部业务接口。任务一长（几十分钟、跨多个工具调用），"某个 API 短暂不可用"几乎必然发生。单次请求挂了重试就行，但 agent 有状态——计划执行到一半、已经产生副作用、上下文里堆着报错——处理方式完全不同。

## 问题在哪

实践中最常见的三种失败模式：

1. **一挂全崩**：一个非核心工具超时，整个任务直接失败重来，前面所有步骤白跑。
2. **无限重试**：模型收到报错后决定"再试一次"，工具层没有预算控制，token 烧掉一圈最后还是失败。
3. **假装成功**：错误信息太长太乱地进了上下文，模型总结时直接脑补出结果，下游拿到脏数据。

这三类问题的根因相同：把错误处理交给了模型即兴发挥，而不是交给工程结构。

## 我的做法：拆成三层

### 工具层（adapter / MCP wrapper）

- **统一调用执行器**：超时、指数退避 + 随机抖动、最多 N 次。重试只针对瞬时错误（超时、429、5xx）；400/401/404 直接判死，不浪费预算。
- **幂等键**：所有有副作用的调用（写库、发消息、创建工单）强制携带 idempotency key，重试不会产生两份。
- **错误归一化**：不管下游返回什么格式，到 agent 这层统一是 `{code, retryable, message}` 的结构化对象。

### 任务层（agent 编排）

- **checkpoint**：每个工具调用成功后持久化状态，恢复时从最后一步续跑，不从头重开。
- **失败分级**：核心步骤失败 → 暂停并报告；可选步骤失败 → 跳过并标记降级。别让一个天气插件挂了导致整条流水线终止。
- **重试预算**：任务级总预算（次数 + 墙钟时间），超了就走 abort 路径。给模型一个明确的"放弃并汇报"出口，它才不会硬编一个结果。

### 提示词层

- 不要把原始 stack trace 塞进上下文。给模型的是一句压缩后的事实："步骤 3 的搜索工具超时，已重试 3 次，可跳过或稍后重试"，外加明确的选项。
- 生成最终报告时，强制要求引用每个步骤的实际返回状态，压制脑补。

## 踩坑记录

- 重试了非幂等的 POST，结果创建了两张一模一样的工单。教训：幂等键不是可选项。
- 退避没加抖动，API 一恢复，几十个并发任务同一瞬间打过去，又把它打挂了。
- 把 429 当成永久错误直接中止任务——429 的意思是"等等再来"，不是"没权限"。
- 断路器恢复阈值设得太敏感，半开状态反复抖动，反而放大了故障。
- 报错原文进了上下文后，模型开始对着错误信息"深度分析"并自己发明恢复方案，越搞越乱。

## 可复用的建议

1. 所有工具调用走同一个执行器，不要每个插件自己写 try/catch。
2. 定义清晰的任务状态机：`pending / running / retryable / degraded / failed / done`，可观测才有得排障。
3. 做故障演练：手动停掉某个 MCP server，看 agent 是崩、是绕、还是干净地报告。没演练过的恢复逻辑等于没写。
4. 监控重试率和降级率，它们是上游健康度的先行指标，比等用户报障早得多。

## 总结

Agent 的错误恢复不是提示词工程，是基础设施问题：错误要分类、重试要有预算、状态要可续跑、失败要能降级、放弃要有出口。模型只负责在这些护栏内做决策。护栏搭好了，API 挂掉就只是日志里的一行 warn，而不是半夜的告警电话。
