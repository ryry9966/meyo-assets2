## 背景

绝大多数 AI 助手的交互模型是"你问，它答"。真用起来会发现，最有价值的场景往往反过来：CI 红了它先说、日报到点自己来、巡检清单有异常它先看一眼。OpenClaw 的架构（gateway + agent + channel）天然适合做这件事，问题只是触发源怎么接、动作怎么收敛。

## 问题

把"被动应答"改成"主动出击"，工程上要解决三件事：

1. **触发从哪来**：定时、外部事件、还是自我巡检；
2. **判断谁来做**：是触发即通知，还是 agent 自己决定"值不值得打扰用户"；
3. **边界怎么控**：主动行为的权限、频率、成本，都比交互式的更难管。

## 做法

我按三层触发逐步落地，建议按同样顺序：

**第一层：定时任务（cron）**。最简单也最稳。在 gateway 侧注册 cron，到点由脚本组装结构化上下文（日期、待办文件、近期会话摘要），投递给 agent 会话产出日报。关键是触发与生成解耦——cron 只负责"叫醒"，prompt 由脚本拼装，可以单独迭代。

**第二层：事件钩子（webhook）**。把 CI 失败、监控告警这类外部事件经一个薄中转层转成 agent 消息。中转层做三件事：验签、去重（相同 fingerprint 5 分钟内只投一次）、限流（每小时最多 N 条进入 agent）。agent 收到后判断"直接转述"还是"先自查再汇报"。

**第三层：心跳巡检（heartbeat）**。低频定时（我设 6 小时一次）让 agent 读一份固定路径的巡检清单（markdown 文件，进 git 管理），逐项判断：无异常就静默结束，有异常才发消息。这一层的核心是**默认沉默**。

模型路由上做简单分级：触发先走便宜模型做 triage，输出"需行动 / 仅告知 / 可忽略"，只有前两类才升级到主模型执行。

## 踩坑点

- **自触发循环**：agent 主动发的消息如果进了某个也会触发它的通道，就自我循环。把触发源和对话通道分开，触发消息打专用标记，agent 侧直接跳过。
- **心跳成本失控**：清单写得太宽，agent 每次全量检查甚至调工具，一天几十次调用。后来收敛到 5 项以内，并在文件头部写明"无异常直接结束"。
- **时区**：cron 按 UTC 配的，日报半夜发。显式写时区，别依赖宿主机默认值。
- **通知疲劳**：第二层刚上线时告警全转发，用户三天后开始无视。加去重和"仅高危转发"规则后恢复有效。
- **幂等**：webhook 重试导致同一动作执行两次。主动动作落库带唯一 ID，执行前查重。

## 可复用建议

1. 先做日报再做实时事件，先验证"打扰是否值得"，再提频率；
2. 主动行为单独收紧权限，不要复用交互会话的完整能力；
3. 所有主动消息写进同一个日志通道，方便审计和复盘；
4. 设每日配额，超限静默降级为"只记录不发送"；
5. 巡检清单当代码维护，改动走 review。

## 总结

Proactive 的难点不在"触发"，而在收敛：触发分层、判断分级、行为受限、默认沉默。做到这四点，主动的助手才是省事的，而不是另一套需要看管的告警系统。上面的三层结构用 OpenClaw 现有的 gateway 能力加少量胶水脚本即可实现，建议从一份每日日报开始跑通再往上加。
