## 背景

OpenClaw 的记忆默认落在 `memory/` 目录的 markdown 文件里，`memory_recall` 负责在对话中把相关条目拉回上下文。默认检索方式偏全文/关键词路线，于是社区里反复出现同一个问题：要不要加 embeddings + 向量库，升级成语义搜索？

## 问题

两条路线各有盲区：

- **全文搜索**对“换了个说法”无能为力。记忆里写的是“客户偏好周一下午开会”，用户问“什么时候方便约会议”，关键词不重叠，直接漏检。
- **语义搜索**反过来，对精确 token 很差：错误码、文件路径、函数名这类内容在 embedding 空间里会被“模糊掉”，还容易召回语义相近但事实错误的记忆——而 agent 恰恰最容易信这种。

## 做法

我从真实会话整理了 30 条 recall 问题当评测集，标好期望命中的记忆条目，然后三步走：

1. **跑全文基线**：统计 hit@3，发现失败案例里约七成是同义改写，三成是关键词根本不在记忆里（后者是记忆质量问题，换搜索引擎救不了）。
2. **语义方案最小实现**：按记忆条目切 chunk（一条事实一个 chunk），选多语种中文友好的小模型做向量化，向量库用 sqlite-vec，写入路径上增量更新索引。
3. **混合融合**：两路各取 top5，用 RRF 融合排序；检测到精确 token（路径、错误码格式）时给全文链路额外加权。

结果：改写类问题 hit@3 从 54% 提到 86%，精确 token 类保持 100%，单次 recall 延迟增加约 120ms（本地推理），可接受。

## 踩坑点

- **chunk 切太碎会丢上下文**。“项目代号 X” 和 “X 已停用” 分开后，单独召回任何一条都会误导。按条目切、条目内写完整，比反复调 chunk 大小有用得多。
- **记忆是 agent 自己写的，边跑边改**。索引必须挂在写入路径上，靠定时全量重建会有一段“记忆失忆”窗口。
- **embedding 模型的语种要匹配**。中文语料配英文为主的模型，相似度明显偏松，换模型前先拿自己的语料试测。

## 可复用建议

- 记忆条目少于几百条时，别上向量库。全文检索 + 结构化条目已经够用，先省下运维成本。
- **先建评测集再改方案**。没有 hit@3 这类指标，一切优化都只是感觉。
- 混合优于单选：关键词管精确 token，向量管同义改写，RRF 是性价比最高的融合方式。
- 召回结果保留来源（文件 + 行号），agent 能引用，你排障也有抓手。

## 总结

这个问题没有标准答案，取决于你的查询分布：改写多就加语义，精确 token 多就靠全文，两者都有就混合。对我这种中等规模、中英混杂的个人实例，混合方案是明确的赢家——但这个结论是被 30 条测试集推出来的，不是被某篇博客推出来的。建议你也从建评测集开始。
