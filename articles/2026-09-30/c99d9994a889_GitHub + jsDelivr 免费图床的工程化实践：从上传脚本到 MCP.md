## 背景

写博客、开源插件 README、让 Agent 产出技术文档，图片放哪是个绕不开的小问题。对象存储要实名、按量计费；免费图床要么限速要么跑路。GitHub 仓库 + jsDelivr 是存在多年的组合，缺点明显但胜在零成本、链路透明。配合 OpenClaw 的自动化能力，值得把这套老方案重新整理成工程化用法。

## 问题

我的诉求只有三条：

1. 图片链接长期稳定，Markdown 里直接引用；
2. 上传能自动化——Agent 写文档时能自己完成「存图、拿链接、插入」这一步；
3. 不引入额外付费和运维。

## 做法

1. **建一个公共仓库**（如 `assets`），图片单独放，不和代码混。
2. **目录按 `blog/2025/06/` 组织**，文件名用 `日期-内容哈希前8位.webp`，保证不可变。
3. **引用走 jsDelivr 的 GitHub 源**：

   ```
   https://cdn.jsdelivr.net/gh/<user>/<repo>@v2025.06/blog/2025/06/a1b2c3d4.webp
   ```

   用 release tag 而不是分支名，缓存语义更干净。
4. **上传脚本约 30 行**：调 GitHub Contents API 提交文件 → 拼接 CDN 链接 → 返回 Markdown 片段。我把它包成一个 MCP tool，接口就一个：输入本地文件路径，输出可粘贴的 Markdown。Agent 写文档时直接调用，链路里不需要人工中转。
5. 若确实覆盖了同名文件，手动请求 `https://purge.jsdelivr.net/gh/...` 刷缓存——但更推荐根本不覆盖。

## 踩坑点

- **缓存不更新**：jsDelivr 对同一版本缓存很激进，同名覆盖后旧图可能存活一两天。结论：文件名永远不可变，改图就换新文件名。
- **单文件 20MB 上限**，仓库也别养太肥。上传前统一压成 WebP、限制最大边长、剥离 EXIF。
- **私有仓库不生效**，jsDelivr 只能拉 public 仓库。
- **匿名调 GitHub API 每小时只有 60 次**，脚本里记得带 token（5000 次/时）。
- **国内访问有波动**：可以换 `fastly.jsdelivr.net` / `gcore.jsdelivr.net` 测试，但要认清它不是 SLA 服务；正式站点建议留一条自建兜底线路。
- **合规边界**：jsDelivr 定位是开源项目分发，别拿来当视频床或大流量下载站。个人博客/文档的图片量级没问题。

## 可复用建议

- 仓库根维护一个 `manifest.json`（路径、哈希、时间、来源），排查和回收都方便；
- 本地保留原图，GitHub 仓库当分发层而非备份层；
- MCP tool 的返回值直接设计成可粘贴的 Markdown，Agent 链路里少一次格式转换；
- 上线前用 `curl -I` 确认 200 与缓存命中头，别等读者反馈才发现 404。

## 总结

这套方案的本质，是用 Git 提交的不可变性去换 CDN 的免费缓存。只要守住三条线——文件名不可变、上传前压缩、合规使用——它对个人文档和开源插件就是够用且可控的。剩下的接入成本，一个 MCP tool 就能吃掉：以后图的问题，交给 Agent 自己解决。
