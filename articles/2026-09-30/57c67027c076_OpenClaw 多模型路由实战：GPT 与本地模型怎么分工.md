## 背景

OpenClaw 在我们场景里是常驻网关：接了 Telegram 和几个 webhook，主 agent 每天处理大量杂活——消息摘要、定时提醒、MCP 工具编排。之前全走云端强模型，两个问题：月账单超预算，且部分数据（内部群消息）不方便出域。换成本地模型（Ollama 跑 Qwen 系列）又扛不住复杂的多步工具调用。于是做了分层路由。

## 问题

“能配多个模型”不等于“会路由”。真正要回答的是三件事：

1. 哪些任务必须强模型：规划、多工具链、长上下文推理；
2. 哪些任务本地够用：分类、摘要、格式转换、记忆抽取这类高频低难度的活；
3. 本地失败时怎么降级，而不是把超时请求原样砸回云端。

## 做法

先给任务分档：

- **A 档（云端强模型）**：主 agent 对话、多工具编排、写代码，质量优先；
- **B 档（本地 7B–14B）**：摘要、打标签、routine 回复、记忆压缩，频率高但容错也高；
- **C 档（规则/最小模型）**：路由判断本身，避免“用大模型选模型”的循环开销。

落地步骤：

1. 在 `models.providers` 注册本地 provider，OpenAI 兼容，`baseUrl` 指向 Ollama 的 `/v1`；
2. 主 agent 的 `model` 配云端，`models` 回退链里挂本地——本地做兜底而非首选；
3. 高频轻任务不进主对话：拆成子 agent，或在插件里直接调本地模型；
4. 加一层薄路由：先用本地小模型做任务分类，置信度低才升级到云端。

配置骨架大致是：

```json
{
  "agents": {
    "main": { "model": "openai/gpt-4.1", "models": ["ollama/qwen2.5:14b"] }
  },
  "models": {
    "providers": {
      "ollama": { "baseUrl": "http://127.0.0.1:11434/v1", "api": "openai-completions" }
    }
  }
}
```

字段名以你实际版本为准，思路一致即可。

## 踩坑点

- **本地 tool calling 不稳**：小模型会拼错参数、漏字段。对策是只给它一两个工具，别把整个 MCP 工具箱暴露给它；
- **上下文截断**：8k 的本地模型塞进 10k 的工具输出会静默截断，先摘要再进上下文；
- **fallback 雪崩**：本地一超时，请求全量涌向云端，账单反而更高，务必配并发和预算上限；
- **embedding 换型要慎重**：换了向量模型，旧记忆检索质量明显下降，要提前准备重建索引；
- **输出风格漂移**：子 agent 参数不同会产出不一致的格式，后面接一层 schema 校验。

## 可复用建议

- 先跑一两周全云端，拿到真实的 token 分布和任务分布，再定路由比例，别拍脑袋；
- 日志按任务类型打成本标签，路由规则跟着数据迭代；
- 每档留少量流量灰度到上一档，观察质量差异再决定扩大或收缩；
- 攒 20–50 条典型任务做评测集，换模型前后各跑一遍再切换。

## 总结

多模型路由的价值不在于省几个 token，而在于把强模型用在决策点上：云端负责推理和编排，本地负责吞吐和隐私。先测量、再分层、后降级，路由规则保持可解释、可回滚。渠道越多、agent 越多的场景，这套结构的收益越大。
