## 背景

做 Agent 自动化的人过去一年基本都撞过同一堵墙：模型能力不差，难的是让它稳定地"够到"外部世界。读本地文件、查数据库、发消息、操作浏览器——每接一个工具，都要为当时用的 Agent 框架单独写一套胶水代码，换个框架还得重写。

MCP（Model Context Protocol）就是冲着这个来的：2024 年底开源的开放协议，目标只有一个——把"模型应用 ↔ 外部工具/数据"这段接口标准化。现在主流客户端（OpenClaw、Claude Desktop、各类 IDE 插件）都已支持，社区里文件系统、Git、Postgres、浏览器控制等常用 server 基本齐了。

## 它到底解决什么问题

本质是 N×M 变 N+M 的老问题：N 个 Agent 应用要接 M 个工具，两两适配得写 N×M 个连接器。MCP 把它拆成两端各自实现协议：

- **Host/Client**：你的 Agent 应用（如 OpenClaw），负责发起连接、管理权限；
- **Server**：独立进程或远程服务，对外暴露三类能力——**Tools**（模型可调用的函数）、**Resources**（可读取的上下文/数据）、**Prompts**（可复用的提示模板）。

传输层两种：本地用 stdio（拉起子进程），远程用 Streamable HTTP（新规范已用它取代早期的 HTTP+SSE）。类比 USB-C：设备不管你是谁，插上、协商、用。

## 上手步骤（以本地 stdio 为例）

1. 确认客户端支持 MCP，找到 MCP 配置入口（通常是 JSON 配置）；
2. 配一个最简单的 server：

```json
{
  "mcpServers": {
    "fs": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/home/me/projects"]
    }
  }
}
```

3. 重载客户端，确认工具列表里出现了该 server 声明的工具；
4. 让模型执行一个只读操作（如列目录），观察调用参数是否正确；
5. 跑顺之后再加第二个 server，或用官方 SDK（TS/Python）写自己的。

## 踩坑点

- **stdout 是协议通道**。stdio 模式下 server 往 stdout 打任何调试日志都会破坏 JSON-RPC 会话，日志一律走 stderr。这是新手第一大坑。
- **环境问题**：command 用绝对路径或 uvx/npx 拉起，避免"我机器上能跑"；Windows 下注意解释器路径和引号转义。
- **工具描述决定调用质量**。模型选工具基本靠 name + description + JSON Schema，描述含糊就会乱调或拒调。把 description 当写给"只能看这一行字的实习生"的说明书。
- **工具太多反而变笨**。十几个 server 全开、几十个工具挤在上下文里，选择错误率明显上升，按任务开停。
- **权限别一步到位**。filesystem、数据库先只读，观察一段时间再放开写。工具返回的内容也是注入面，别因为"是我配的"就默认安全。

## 可复用建议

- 一个 server 只管一个领域，小而聚焦，别做万能瑞士军刀；
- 本地维护一份 mcp.json 片段库，换机器即插即用；
- 新 server 先用最小脚本单独跑通 list_tools 和一次调用，再挂进 Agent 循环，排查成本最低；
- 自研 server 优先暴露 Resources（只读），Tools 里带副作用的操作加显式确认参数。

## 总结

MCP 没有让你的模型更聪明，它做的是把接线工作标准化：接入成本从 N×M 降到 N+M，能力边界从代码挪进配置，且可审计。对 OpenClaw 用户来说，值得的投入顺序是：先吃透两三个高质量社区 server，再按需自研。协议本身不复杂，复杂的是你愿意给模型开多大的口子。
