## 背景

OpenClaw 的 agent 是长驻进程，天然适合"不用人盯着也能干活"。平台提供了两条定时路径：

- **cron**：标准 cron 表达式调度，到点执行一条预先写好的 prompt，可跑在隔离会话里，结果可投递到指定频道。
- **heartbeat**：周期性心跳。每到间隔，agent 在主会话里被唤醒一次，自己去读工作区的 `HEARTBEAT.md`，判断现在有没有值得做的事。

两者都能实现"定时"，但设计意图完全不同。我最初混着用，踩了不少坑，这里把选型思路整理出来。

## 问题：混用会出什么状况

典型错误有两类：

1. 把一堆"看一眼有没有事"的模糊检查拆成十几个 cron 任务——每 30 分钟查一次收件箱、每 20 分钟看看 CI……数量一多，prompt 重复、token 翻倍，改一处要动十处。
2. 反过来，用 heartbeat 做"每天 9 点发日报"这种确定性任务——它不保证准点，日报变成"9 点到 9 点半之间某刻"，还可能因为 agent 判断"今天没啥可报"而直接沉默。

核心矛盾：**确定性任务要准点和可审计，判断性任务要上下文和自主权**，两种机制各管一头。

## 做法

### 第一步：给任务定性

问一个问题：触发条件和产出能不能在写任务时就完全确定？

- 能（"每天 8:30 汇总 GitHub 通知发到群里"）→ cron。
- 不能，需要现场判断（"如果有人催我的 PR 就提醒我"）→ heartbeat。

### 第二步：确定性任务走 cron

```
openclaw cron add --name "morning-report" \
  --cron "30 8 * * 1-5" \
  --session isolated \
  --deliver channel:telegram \
  --prompt "汇总最近 24 小时仓库 issue 与 PR 动态，按优先级输出不超过 10 条"
```

（不同版本参数名略有差异，以 `openclaw cron add --help` 为准。）

要点：隔离会话里 agent 没有主会话记忆，prompt 必须自包含——要什么数据、输出什么格式、发给谁，一次写清。

### 第三步：判断性任务交给 heartbeat

把模糊诉求写成结构化清单放进 `HEARTBEAT.md`，一条一个条件，写清楚"什么情况才动作"：

```markdown
# Heartbeat 检查项
- CI 失败且涉及 main 分支 → 立即通知，附失败链接
- 收件箱有等待超过 4 小时的关键邮件 → 提醒
- 其他情况 → 不动作，保持安静
```

"不动作"这条很重要，见下文踩坑点。

### 第四步：混合模式

实际用下来最舒服的分工：heartbeat 当哨兵，低频巡逻、做判断；发现需要重活（抓数据、生成报告）时当场执行，或引导你登记成 cron 任务。哨兵便宜，重活走确定性调度。

## 踩坑点

1. **heartbeat 间隔贪小**。心跳在主会话里唤醒，每次带着完整上下文跑一遍，默认 30 分钟已不便宜。调到 5 分钟，token 消耗肉眼可见地上涨，而绝大多数 tick 什么都没发生。
2. **`HEARTBEAT.md` 写成散文**。第一版我写"帮我盯着工作相关的事"，结果 agent 每次都觉得有事做，隔一会儿冒一条消息。改成明确触发条件 +"其他情况不动作"后才安静下来。
3. **隔离会话丢上下文**。cron prompt 里引用"上次的讨论"，隔离会话里什么都没有。要么把上下文写进 prompt，要么改跑主会话（代价是污染主上下文）。
4. **cron 跑完没人知道**。没配投递渠道时任务静默执行，我一度以为没跑，排查半天才定位到。
5. **重复覆盖**。同一个"检查邮件"既在 heartbeat 清单里又建了 cron，两边同时触发时动作打架。一个意图只留一个入口。

## 可复用建议

- 一句话判断：**有明确时刻和明确产出 → cron；只有模糊条件、需要判断 → heartbeat。**
- cron prompt 按"输入—动作—输出—投递目标"四段写，当脚本注释对待。
- `HEARTBEAT.md` 当规则引擎写，不当愿望清单写，每条都要有"不动作"的兜底。
- 从默认 30 分钟心跳起步，观察一周真实触发率再调。
- 定期 `cron list` 清理僵尸任务，尤其是调试期留下的每分钟任务。

## 总结

cron 和 heartbeat 不是竞争关系，而是调度谱系的两端：cron 管"什么时候做"，heartbeat 管"要不要做"。把确定性交给表达式，把判断交给 agent，token 账单和打扰频率都会正常很多。先给任务定性、再选机制，永远比事后迁移便宜。
