## 背景

用 OpenClaw 做自动化一段时间后，最容易撞到的天花板是串行。以我的每日信息聚合任务为例：拉取十几个 RSS 源、逐个做摘要和打分、汇合成早报。单 agent 一条链路跑下来要十几分钟，中途任何一步超时，整个任务重来。后来我把中间那段"逐源处理"改成 subagent 并行，耗时降到原来的三分之一。这篇记录做法和踩过的坑。

## 问题

并行不是"多开几个就快了"，真正要解决的是三件事：

1. **任务能不能切**：子任务之间是否独立，有没有共享的可变资源；
2. **上下文怎么传**：主 agent 的长对话如果原样塞给每个子 agent，token 消耗会成倍增长；
3. **结果怎么收**：并行执行下失败是常态，汇总层必须能识别部分失败，而不是把空结果当成功。

## 做法

我的编排结构固定为"切分 → 并行执行 → 汇总"三段：

1. **切分**。主 agent 先产出任务清单，每个子任务包含：输入数据、期望输出格式（统一固定字段的 JSON，如 `status` / `summary` / `score`）、允许使用的工具范围。切分原则：子任务之间零写冲突，共享资源只读。
2. **执行**。并行度控制在 3～5。每个 subagent 的提示词只带三样东西：任务描述、输入数据、输出模板，不继承主 agent 的对话历史。
3. **汇总**。subagent 只返回结构化结果，不落盘、不发消息。主 agent 逐条检查 `status`，失败的进入重试队列（最多一次），最终由主 agent 统一写文件、发通知。

关键的一条：**写操作全部收口到主 agent**。子 agent 是"只读工人"，返回 diff 或结论，由主 agent 串行落盘。

## 踩坑点

- 两个 subagent 同时编辑同一个文件，后写的覆盖先写的。改成子 agent 只返回 diff 后解决。
- 子 agent 继承了主 agent 全部上下文，单轮 token 翻了五倍。改为显式传最小输入。
- 并行度开到 8 触发上游限流，批量失败。加并发上限和指数退避重试。
- 子 agent 失败后静默返回空字符串，汇总层当成正常结果。强制要求 `status` 字段，空结果视为失败。
- 子 agent 里再 spawn subagent，层级失控、日志没法看。硬性限制嵌套深度为 1。

## 可复用建议

- 把"切分-执行-汇总"固化成一个 skill/插件，提示词模板化，不要每次临时写。
- subagent 的输出契约（字段名、类型）提前定死，汇总层才有稳定性。
- 每个子任务的输入输出单独落一份日志，出问题按任务回放，而不是翻整段会话。
- 幂等优先：子任务重跑不应产生副作用，副作用只留给主 agent。

## 总结

subagent 并行不是免费午餐，收益完全取决于任务本身是否可切分、无冲突。我的经验是：编排逻辑越"笨"越稳定——主 agent 负责拆和收，子 agent 负责算，写操作收口，失败显式化。做到这四点，多数批处理类自动化任务都能安全提速。
