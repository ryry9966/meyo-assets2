## 背景

OpenClaw 的长期记忆落在 memory 目录里：每日增量笔记加上历史 md 文件，Agent 通过 memory_recall 把相关片段捞回上下文。检索实现通常两条路：基于 SQLite FTS5 的全文搜索（BM25 打分），以及本地 embedding 后的向量语义搜索。社区里经常争“哪个更好”，我用自己的记忆库对比了两周，结论先说：这不是二选一的问题。

## 问题

两类典型召回场景表现完全不同：

- **精确 token 类**：报错码、文件路径、命令行参数、服务名。比如“上次 502 那次部署的回滚命令是什么”。全文搜索基本秒中；小参数量的本地 embedding 模型对稀有 token 召回很差，经常被“语义相近但内容无关”的条目挤掉。
- **转述查询类**：记录时写的是“上线后网关报错”，提问时说的是“那次部署事故”。语义搜索能跨过措辞差异；BM25 因字面零重叠直接空手而归。

## 做法

1. 从自己的记忆库挑 20 个真实问题，一半精确 token 类、一半转述类，做成固定评测集（一列查询 + 期望命中的文件名）。
2. 分别只开全文、只开语义，取 top-5，人工标注命中与否，算 recall@5。
3. 开混合检索（两路结果用 RRF 融合），同样跑一遍。
4. 调融合权重，观察不同查询类型的得分变化。

我的数据（样本小，仅供参考）：精确类 BM25 recall@5 约 0.9，纯语义只有 0.4；转述类反过来，语义 0.8，BM25 约 0.3。混合后两类都稳定在 0.85 以上。

## 踩坑点

- **中文分词**：FTS5 默认 unicode61 对中文基本按单字切，BM25 权重会失真。要么换分词器插件，要么接受它在中文语料上的分数仅供参考。
- **换 embedding 模型必须重建向量索引**，新旧向量混在一个库里，余弦相似度算出来全是错的。这个坑我只踩过一次，代价是全量重索引。
- **记忆条目太少**（几十条以内）时上语义搜索收益有限，索引维护成本反而不划算。
- **时间敏感查询**：“上周那个问题”这类问法，两种检索都会召回内容相似但时间错位的条目，最后还是得靠文件名里的日期做过滤。

## 可复用建议

- 默认上混合检索，别纠结单选。BM25 兜精确 token，向量兜转述，RRF 默认参数就够用，不必先调权重。
- 写记忆时迁就检索：错误码、路径、命令原样保留，别改写成“漂亮”的总结句，这对两种检索都有利。
- 评测集固定下来，换模型、换分词器后重跑一遍，五分钟的事，能省掉大量玄学调参。
- 记忆量不到百条时，先用纯 FTS，别过度工程。

## 总结

语义搜索和全文搜索不是竞品，而是互补：一个解决“换个说法还能找到”，一个解决“这个词必须精确”。真正的工作量不在选型，而在把记忆条目写成可检索的样子，并保留一个随时能重跑的小评测集。
