## 背景

Agent 跑久了，记忆检索就是体验的分水岭。我们的 memory_recall 最初是一套很朴素的方案：记忆落 SQLite，用 FTS5 建全文索引，召回即查表。后来为了处理“换个说法问同一个问题”的场景，又叠了一路向量检索（sqlite-vec + bge-m3）。跑了几个月，两条路线的优缺点都踩得差不多了，本文记录对比结论和一个混合方案，供正在选型的同学参考。

## 问题

两个真实失败案例，分别对应两路的盲区：

- **全文搜索的坑**：用户问“上次那个数据库连接超时怎么解决的”，记忆里存的是“pg pool exhaustion，调大 max_connections”。词面完全不重叠，FTS5 召回 0 条。同义改写是关键词检索的天然死穴。
- **语义搜索的坑**：用户问“那个 502 报错”，向量检索排第一的是一段无关的部署笔记，因为整体语义“服务器、错误、排查”太像了；真正含 "502 Bad Gateway" 的条目排到第 8。精确标识符（错误码、ID、变量名）是嵌入检索的天然弱项。

结论很明显：单选任何一路，都会在另一半 query 上翻车。

## 做法

我们的记忆后端是自建的 MCP tool，recall 接口对上层透明，所以改造成本集中在工具内部：

1. **入库先结构化**：每条 memory 带 type（决策/故障/偏好/片段）、时间戳、项目 tag，为后续过滤留口子。
2. **双路索引并行写**：FTS5 换 jieba 分词处理中文；向量侧用 bge-m3，chunk 控制在 300 字左右。
3. **混合召回**：两路各取 top 10，用 RRF（倒数排名融合）合并，最终只取前 5。
4. **精确匹配加成**：query 中出现高区分度 token（错误码、ID）时，FTS 命中直接置顶。
5. **建评测集**：攒了 40 条真实查询，每次调参跑一遍 hit@5，人肉核对，不靠感觉。

效果：纯 FTS 的 hit@5 约 62%，纯向量约 71%，混合后到 86%，代价是单次 recall 多几十毫秒，完全可接受。

## 踩坑点

- FTS5 默认的 unicode61 分词器对中文基本不可用——整段汉字被当成一个 token，必须换 jieba 或 ICU tokenizer。
- **chunk 尺寸两头翻车**：切太大，一条记忆塞满细节，向量语义被稀释，什么查询都“有点像”；切太小，召回的碎片拼不出结论。
- **向量索引的数据腐化**：某条记忆更新后忘了重新 embedding，检索回来的永远是旧版本。写入和更新必须走同一条 pipeline。
- 召回条数别贪多。top 10 塞进上下文，噪音多于信息，agent 反而开始自由发挥。前 3~5 条的质量远比数量重要。
- 别跳过元数据过滤：先按项目/时间筛，再进检索，能消掉一大半误召回。

## 可复用建议

- **别一上来就上向量库**。先用 FTS 跑两周，把真实 miss 的 query 记下来：miss 多是“换了个说法问”，再补语义检索；是“关键词对不上数据”，先修分词和数据结构。
- 混合召回 + RRF 是工程上性价比最高的默认解，两路独立可测，单路挂了还能降级。
- **评测集比选型更重要**。没有几十条真实 query，你调的所有参数都是玄学。
- 给 memory 加 TTL 和去重——陈旧且互相矛盾的记忆，比没有记忆更危险。

## 总结

语义搜索解决“怎么说”，全文搜索解决“说什么”。memory_recall 是高频、延迟敏感的路径，混合方案在这里不是过度设计，是基本卫生。顺序建议：先量测、再混合、小步替换，每一步都有数据兜底。
