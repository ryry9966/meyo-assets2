## 背景

我们团队维护一个中等规模的前端项目，E2E 用 Playwright，两百多个用例。老三样问题：写用例慢、改版后选择器批量失效、覆盖缺口长期补不上。最近一个多月，我们把 OpenClaw 的 Agent 接进测试流程，让它承担"初稿生成 + 失败修复循环"这两段最耗人的工作，记录一下实际效果和教训。

## 问题

直接把需求描述丢给 Agent 让它生成测试，效果通常很差，主要是三类：

1. **假测试**：断言写的是"元素可见"而不是业务结果，跑通了但什么都没验证；
2. **脆选择器**：依赖自动生成的 class、nth-child，一次重构全挂；
3. **硬等待**：`waitForTimeout(3000)` 满天飞，本地过、CI 挂。

根源不是模型不会写测试，而是它缺上下文、缺反馈回路——不知道你们的用例规范，也看不到真实运行失败的信息。

## 做法

核心思路一句话：**给 Agent 窄工具，不给自由**。

**第一步，准备上下文。** 写一份 `TESTING.md`，包含定位器规范（统一 data-testid）、fixture 约定、Page Object 结构、禁止事项（禁硬等待、禁 mock 核心接口），作为系统提示注入。

**第二步，暴露窄 MCP 工具。** 通过 MCP server 只给三个：`get_accessibility_tree`（拿页面结构化快照，比截图和原始 DOM 干净得多）、`run_test`（跑指定 spec，返回截断后的失败输出）、`read_file`。工具越少，跑偏概率越低。

**第三步，受限迭代。** 流程：读需求 → 拿页面快照 → 生成 spec 草稿 → 运行 → 读失败输出 → 修复。迭代上限 3 轮，超过就停，标记"需人工介入"，避免无限烧 token。

**第四步，人工审查。** 只审三件事：断言是否验证业务结果、有没有硬等待、选择器是否符合规范。其余格式问题让它自己修。

## 踩坑点

- **失败输出不截断会炸上下文**。一次 Playwright 报错几千行，Agent 直接"失忆"。我们在 `run_test` 里只返回最后 N 行加错误摘要。
- **Agent 爱过度 mock**。它会顺手把报错的接口 mock 掉让测试变绿。务必在 TESTING.md 里明确禁止，审查时检查 mock 列表。
- **测试数据污染共享环境**。Agent 生成的 fixture 用固定名字，多次运行互相覆盖。要求所有数据带随机后缀，并写 teardown。
- **Accessibility tree 不是银弹**。动态弹窗、iframe 内的内容拿不全，这类场景人工补。

## 可复用建议

- 先固化测试规范文档，再接 Agent。没有规范，Agent 只会放大混乱。
- 用"断言强度"评估产出，而不是用例数量：抽查 10 个用例，看断言是否落在业务结果上。
- Agent 产出一律走 PR 流程，与人类提交同等对待，不设豁免。
- 只在新功能开发时启用初稿生成；存量用例重构收益低、风险高，先别动。

## 总结

一个多月下来，新功能 E2E 初稿的编写时间从人均 2-3 小时降到 30 分钟以内，但审查时间没有减少——也不应该减少。Agent 擅长样板代码和机械的"运行-修复"循环；断言语义、稳定性判断这些"测试是否真的有效"的问题，仍然属于人。把这条边界划清楚，这套协作才真正省时间。
