# 背景

用 OpenClaw 跑长任务的人大概都遇到过同一个体感：主会话越聊越"糊"。让它先调研再改代码，中间的工具调用记录——读文件、grep、报错堆栈——全部留在主会话上下文里，几轮之后模型开始忘记最初的约束，甚至把探索阶段的半成品结论当成事实继续推。

子 Agent 机制本质上就是为这个问题准备的：给一个独立的 context、限定工具集，跑完只回传结果。它的完整执行转录留在自己的 session 里，主会话只看到一份摘要。听起来简单，但用得好和用得差，效果差距很大。

# 问题：污染具体有三种形态

1. **上下文膨胀**：子任务里几十次文件读取挤占主会话窗口，有效信息被稀释。
2. **指令漂移**：探索过程中的临时结论、失败的尝试进入历史后，模型后续会不自觉地引用它们。
3. **状态误解**：主会话"看到"了子任务的操作过程，误以为这些是当前共识，而实际上文件系统和会话记忆已经分叉。

# 做法：把脏活隔离出去

**1. 明确边界。** 把"可独立验收"的工作下放给子 Agent，典型三类：只读调研（代码地图、依赖梳理）、批量机械修改（重命名、格式迁移）、独立验证（跑测试、复现 bug）。需要多轮澄清的交互式工作不要下放。

**2. 写自足的 brief。** 子 Agent 看不到主会话历史，启动 prompt 必须自己站得住。我们的四段式模板：

```
目标：...
范围：仅 src/acl/，禁止触碰测试文件
约束：不引入新依赖，遵循现有命名风格
交付：结论 + 改动文件清单 + 遗留风险，不超过 20 行
```

**3. 限定工具集。** 调研型子 Agent 只给读类工具，验证型只给跑测试和读日志。工具越少，跑偏概率越低。

**4. 约定回传格式。** 子 Agent 的完整转录留在它的 session 里，主会话只进那一页结构化摘要。这是隔离生效的关键一步。

**5. 用文件系统做事实源。** 子 Agent 的产出落在文件里（代码、diff、报告），主会话需要细节时自己去读文件，而不是依赖转述。

# 踩坑点

- **brief 不自足**：子 Agent 会按通用工程习惯干活，项目里的特殊约定（命名规范、禁止的依赖）必须显式写进 prompt，别指望它"应该知道"。
- **回传太长**：不约束返回格式的话，子 Agent 会把整个执行过程复述一遍，隔离等于白做。上限写进 brief 里。
- **并行写冲突**：多个子 Agent 同时改同一批文件，后写的覆盖先写的。要么按文件切分任务，要么改串行。
- **diff 之外无真相**：主会话对子任务的理解只有那份摘要，验收时用 git diff，不要凭印象。发现不对就丢弃重跑，成本只是一次子任务。
- **调试现场丢失**：子 Agent session 通常是一次性的，重要任务让它把中间产物写到固定目录，事后才有据可查。

# 可复用建议

- 把四段式 brief 模板放进项目仓库，团队统一复用，避免每个人手感不一。
- 沉淀一份"哪些任务走子 Agent"的团队约定：只读调研、批量修改、独立验证走下放，其余留在主会话。
- 主会话保持"指挥官"角色：读摘要、做决策、写关键代码；批量操作全部下放。

# 总结

session 隔离不是省 token 的小技巧，而是长会话保持可靠的前提。一句话概括：子 Agent 用独立上下文换执行空间，用结构化摘要换主会话的清晰度，用文件系统当唯一事实源。隔离做对了，主会话跑到几十轮，仍然记得住最初的目标。
