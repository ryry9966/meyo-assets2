## 背景

现在大多数 Agent 的交互模式仍是"你问一句、它答一句"。OpenClaw 这类常驻网关型 Agent 有个天然优势：它一直在线，接得上 cron、webhook、文件变更这些事件源，闲置时间其实是最大的未利用资源。我们最近把一个纯问答助手改造成了带主动能力的版本，诉求很朴素：早上自动出一份当日摘要，仓库和服务器有异常时先于用户发现。这篇记录做法和代价。

## 问题：主动 ≠ 多说话

Proactive 的难点不是"能不能主动"，而是"该不该主动"。三个具体矛盾：

1. 触发太密 → 烦人，用户直接关掉；
2. 触发太疏 → 形同虚设；
3. 主动执行写操作（发消息、改文件）→ 风险不可控。

## 做法

**1. 事件分层。** 触发源分两类：周期类（heartbeat，每 30 分钟一次轻量唤醒）和事件类（cron、webhook、文件 watcher、MCP 工具回调）。事件类直接进入评估，周期类先过一道便宜的门控。

**2. 决策门控，observe ≠ speak。** 心跳唤醒时不直接调主模型，先用规则 + 小模型判断"有没有值得说的事"：与上次快照做 diff、是否在冷却窗口内、是否在免打扰时段。没有就静默结束，主模型根本不启动。这一步把 token 成本降了一个数量级。

**3. 动作分级。** 主动产出分两档：只读报告（汇总、提醒、摘要）直接推送；写操作（给别人发消息、下单、删文件）只生成"建议卡片"，等用户一句确认。白名单可以慢慢扩大，但默认收紧。

## 踩坑点

- **心跳污染主会话。** 最初心跳结果直接写进主对话 session，几天后上下文全是噪音，回答质量肉眼可见地下降。解决：心跳用独立 session，主动消息只在触发时注入摘要。
- **没有去重，变成复读机。** 监控类触发尤其明显，同一个告警每 30 分钟推一次。加"已上报指纹 + 冷却时间"后世界清净了。
- **免打扰没做时区判断**，凌晨三点推日报。调度一律用用户本地时区，安静时段显式配置。
- **工具回调带敏感内容**，被直接推到群聊渠道。主动渠道要和交互渠道分开，敏感信息只走私聊或落文件。

## 可复用建议

- 从只读开始攒信任，写操作永远要确认，哪怕流程上烦一点。
- 给主动行为定预算：每日主动消息上限写进配置，超限静默聚合到下一次。
- 每次主动决策留日志（触发源、门控结论、是否推送），一周后回看日志调阈值，比拍脑袋靠谱。
- 触发器和门控做成插件或 MCP server 形式，调度核心保持"无知"，扩展时不改主逻辑。

## 总结

Proactive 不是让 Agent 话变多，而是让"说话"变成一次需要通过门控的决策。事件分层 + 便宜的门控 + 动作分级，这套结构我们已经在两个项目里复用，代码量不大，收益明显。建议先拿一个场景（每日摘要或单指标监控）跑通全链路，再谈扩展。
