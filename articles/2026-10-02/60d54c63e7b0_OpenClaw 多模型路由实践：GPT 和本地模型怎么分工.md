## 背景

我的 OpenClaw 跑了半年左右，挂着十几个 MCP 工具、三个常驻 agent，还有一批定时任务（日志摘要、RSS 过滤、代码评审草稿）。早期偷懒，所有请求都走同一个云端大模型，账单稳定，但两个问题越来越明显：一是大量“分类、摘要、格式化”类的低难度任务也在烧 token，成本大头其实是垃圾负载；二是部分内容（服务器日志、内部数据）我不想送出去，但又不得不送。

于是把本地模型（Ollama 跑 Qwen 系列）接进来做了混合路由。跑了一个多月，记录一下分工原则和踩过的坑。

## 问题：不是“谁更强”，而是“任务值多少钱”

混合路由容易走两个极端：全走云端（贵、隐私差），或全走本地（长上下文和多工具编排场景质量明显下滑）。核心判断标准我总结为**决策密度**——这个任务错了之后，修复成本有多高。

## 做法

**1. 按决策密度给任务分三档**

- 高：任务规划、代码生成、复杂工具编排（一次调用链里涉及 3 个以上 MCP 工具）→ 云端强模型
- 中：单工具调用、带格式的结构化输出、总结 → 本地中档模型
- 低：文本清洗、分类打标、简单改写 → 本地小模型，甚至直接规则兜底

**2. 在 OpenClaw 里配置多 provider + 升级链**

大致结构如下（字段名以你版本的实际 schema 为准）：

```yaml
models:
  planner: gpt-4.1        # 云端，负责规划和代码
  worker: qwen2.5:14b     # 本地，负责执行和摘要
routing:
  default: worker
  escalate:               # 满足条件就升级到 planner
    - tools_used >= 3
    - task_type in [code, plan]
  fallback_on_error: planner
```

**3. 用子 agent 拆分而不是全局切换**

比“整个会话换模型”更稳的做法是：主 agent 固定用云端模型做拆解和汇总，把可并行的叶子任务（逐条摘要、字段抽取）分发给本地 worker。上下文在主 agent 手里，本地模型只处理截断后的小片段，失败率低很多。

**4. 灰度和统计**

路由规则先在定时任务上跑两周，记录每类任务的 token 消耗、失败率、平均耗时，再决定是否推广到交互会话。

## 踩坑点

- **工具调用能力差异是最大的坑。** 本地模型在多工具场景下会漏参数、编造工具名，MCP 工具一多尤其明显。结论：凡是涉及工具编排的链路，不要降级，这笔钱省不得。
- **JSON 输出漂移。** 本地模型的 schema 遵循度不稳定，必须加校验和一次重试，否则下游解析静默坏掉。
- **上下文窗口不对齐。** 本地 32k、云端 128k+，长会话直接路由过去会截断到面目全非。路由判断里要加上“当前上下文长度”这个条件。
- **fallback 不要静默。** 本地失败自动升云端的逻辑要配告警，否则一次 Ollama 崩溃就变成账单刺客，你还不知道。
- **本地并发受显存限制。** 批量任务要排队，别按云端的 QPS 心智来设计并发。

## 可复用建议

1. 路由规则放配置里，别写死在代码里——模型迭代很快，规则要能跟着换。
2. 先测量再路由：没有分任务的 token/失败率数据，任何分工方案都是猜。
3. 隐私敏感内容（日志、客户数据）强制本地，不做智能判断，规则越简单越可靠。
4. 维护一个 30~50 条的固定评测集，每次调整路由后跑一遍回归。

## 总结

多模型路由的本质是成本工程：把云端模型的预算集中花在决策密度高的地方，其余交给本地。我现在的账单降了约六成，隐私数据彻底不出门，代价是多了一层需要维护的路由配置和校验逻辑。如果你的 OpenClaw 负载里低难度任务占比超过一半，这个改造值得做；如果大部分都是复杂编排，那老实用强模型反而是最省心的方案。
