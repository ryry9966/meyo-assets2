## 背景

用过一段时间 OpenClaw 之后会发现一个尴尬的现实：它的默认形态是"问答机"——你不发消息，它就静止。但真正有价值的场景往往不是问答，而是巡检：早上汇总一次 GitHub 通知、发现 inbox 里堆积的待办、某个文件被改了需要跟进。这些事不需要对话，需要的是"到点自己看一眼"。

OpenClaw 内置的心跳机制就是为此设计的：Agent 每隔一段时间被自动唤醒，读取 workspace 根目录下的 `HEARTBEAT.md`，判断有没有该做的事。有就执行并汇报，没有就按约定回 `NO_REPLY`——这条回复会被吞掉，用户端无感知。文件每次心跳都会重新读取，改完即时生效，不用重启。

## 问题

把主动性交给 Agent 之前，我踩过两类极端：

- **全靠 cron + 脚本**：定时任务能跑，但上下文不在 Agent 手里，脚本只负责"通知我"，判断和跟进还是落回人身上；
- **全塞给心跳**：把"帮我盯着仓库"这类模糊任务写进 HEARTBEAT.md，结果 Agent 每半小时纠结一次要不要汇报——要么刷屏，要么干脆不动。

## 做法

HEARTBEAT.md 的本质是一份"值班手册"。核心是每条任务写清三件事：触发条件、要做的动作、静默规则。

```markdown
# Heartbeat 任务清单

## 定时
- 工作日 09:00（Asia/Shanghai）：汇总我关注仓库过去 24h 的
  GitHub 通知，只展开需要我回复的 issue，其余一句话带过。

## 条件触发
- 当 inbox.md 存在未处理条目：分类、给出建议动作，
  处理完把条目移入"已完成"区块。

## 静默规则
- 没有到期任务时，回复 NO_REPLY，不输出任何内容。
```

配置上注意两点：

1. 心跳间隔默认 30 分钟，按任务时效调整——晨报类 60 分钟足够，实时监控不如交给 webhook；
2. 每次心跳都是一次模型调用，即使最后 `NO_REPLY` 也消耗 token。如果版本支持，给心跳单独配一个便宜的模型，成本能降一个量级。

## 踩坑点

- **任务写得模糊**。"帮我关注一下 XX"没有触发条件，Agent 只能靠猜。写清"什么情况、做什么、怎么汇报"。
- **没有完成态**。提醒类任务做完不删，第二天继续提醒。约定：完成就移走或打标记，心跳只看"待办区"。
- **时区没写明**。心跳跑在服务器上，"早上 8 点"可能不是你以为的 8 点，统一写 `Asia/Shanghai`。
- **污染主会话**。心跳与对话共用上下文，高频心跳会把历史撑大，还容易在你正聊着时插进一条汇报。间隔别低于 15 分钟，汇报控制篇幅。
- **把重活塞进心跳**。心跳适合"看一眼、判断一下"，批量处理应该让 Agent 写成脚本或任务文件按需执行。

## 可复用建议

- 三段式模板：`触发条件 / 动作 / 静默规则`，缺一不可；
- 分层原则：需要模型判断的进心跳，纯定时的走 cron，事件驱动的走 webhook——心跳只做最后 10% 的智能部分；
- 每周清理一次 HEARTBEAT.md，删掉已经不看的汇报项。任务清单和代码一样，会腐烂。

## 总结

HEARTBEAT.md 的价值不在于"自动化"，而在于把"什么时候想起来"这件事从人转移给 Agent。写好它的关键不是多写任务，而是少写、写准：每条都有明确的触发条件和静默出口。当心跳安静地跑着、只在真正有事时冒泡，Agent 才算从工具变成了同事。
