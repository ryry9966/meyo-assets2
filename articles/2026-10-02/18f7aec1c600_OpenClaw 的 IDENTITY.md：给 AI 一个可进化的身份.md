## 背景

OpenClaw 的 workspace 是 agent 的“家目录”，里面的 markdown 文件会在每次会话启动时被读进上下文。多数人第一个认真对待的是 AGENTS.md（行为规则）和 SOUL.md（性格底色），而 IDENTITY.md 往往保留着模板默认值——名字、emoji、avatar 都还是初始状态。结果就是：agent 有了脾气，却没有一个像样的“自我介绍”。

## 问题

在没有独立身份文件之前，常见的三种做法都有代价：

1. **硬编码在系统提示里**：改个名字要动代码、重新部署，变更没有历史；
2. **混进 SOUL.md 或 AGENTS.md**：身份和规则搅在一起，调语气时经常误伤指令；
3. **散落在各插件 prompt 里**：每个插件描述的 agent 形象略有出入，跨插件行为漂移。

本质问题是：模型每次会话都是无状态的，身份必须有一个每次都加载、且可以低成本迭代的单一事实来源。

## 做法

我们的实践是把 IDENTITY.md 当成“生产配置”来维护。

**第一步：扁平字段化。** 不写小作文，用短字段：

```markdown
# IDENTITY.md
- Name: Byte
- Creature: 一只工程师气质的狸猫
- Vibe: 直接、克制、偶尔冷幽默
- Emoji: 🦝
- Language: 中文为主，技术名词保留英文
```

**第二步：划清职责边界。** IDENTITY.md 只回答“我是谁”（静态）；SOUL.md 回答“我如何行事”（价值观与边界）；AGENTS.md 回答“我如何干活”；MEMORY.md 存易变状态。谁的内容谁带走，绝不交叉。

**第三步：进 git，走 PR。** workspace 本来就该在版本控制里。身份变更单独成 commit，涉及语气的调整走 review，出问题可回滚到任意版本。

**第四步：证据驱动迭代。** 发现语气不对时，不要整段重写，只加一行修正，然后观察一周。另备 3~5 条固定测试 prompt，每次改动后跑一遍对比输出。

## 踩坑点

- **身份写成背景小说。** 几百字的角色设定会让模型过度拟合人设、削弱指令遵从，控制在 15 行以内；
- **放易变内容。** “当前在做项目 X”属于 MEMORY.md。身份几个月才动一次，记忆天天在涨；
- **文件间互相矛盾。** 身份写“口语化”，AGENTS.md 又要求“正式报告格式”，模型会随机站队。改身份前先全文检索一遍冲突；
- **语言字段缺失。** 用英文写身份却期待中文输出，容易中英混排，显式写明语言策略；
- **改了不生效。** 长会话持有旧的工作区快照，改动要重启会话或等下次 heartbeat 才加载；
- **多实例共用一份。** 克隆 workspace 起多个实例时，一处修改全体生效，需要按实例做覆盖。

## 可复用建议

- **schema 保持极简**：字段化 + 短行，远比自由文本可控；
- **基座 + 增量**：团队维护一份 base 身份，各实例用 override 文件叠加差异，类似配置分层；
- **定期修剪**：每季度删一遍不再改变行为的行，身份文件“只减不增”是健康信号；
- **小步慢改**：身份进化和记忆积累相反——记忆要快，身份要慢，每次只动一处。

## 总结

IDENTITY.md 只有十几行，却是每次会话里唯一回答“我是谁”的文件。把它当代码管理：短、版本化、可回滚、改动有依据。身份不是一次性的角色扮演设定，而是一项长期演进、有人 review 的配置资产——这大概就是“可进化”在工程上的含义。
