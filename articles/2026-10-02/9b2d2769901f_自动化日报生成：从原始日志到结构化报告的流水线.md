## 背景

我们团队过去每天早上要人工翻一遍前一天的日志（服务日志、Agent 会话记录、CI 运行结果），再手写一份日报发到群里。动作重复、格式漂移，还经常漏掉关键告警。这篇帖记录我用 OpenClaw 搭的一条日报流水线：定时触发 → 日志聚合 → Agent 生成结构化报告 → 推送到频道。整体思路不复杂，但有几个坑值得提前说清。

## 问题

把"日报"直接丢给模型是不可行的：

1. 原始日志量大且噪声高，整段塞进上下文既贵，摘要还容易漂移；
2. 模型复述数字不可靠，告警次数、失败率这类硬指标错一个就失去信任；
3. 不固定结构时，每次产出的段落都不一样，没法归档对比。

所以核心矛盾是：**数据要准确，表达要自然**。这决定了流水线的分工。

## 做法

整条链路分四段，每段落盘中间产物，方便排查和回放：

**1. 采集（脚本，非模型）**。OpenClaw 定时任务每天 08:30 触发一条 shell 脚本，拉取"昨天 00:00–24:00"窗口内的日志，统一转成 JSONL。日期边界用本地时区显式锚定。

**2. 聚合（脚本，非模型）**。用一段几十行的 Python 做确定性统计：错误 Top-N、各服务请求量与失败率、Agent 任务成功/失败数、CI 失败明细，输出 `aggregated.json`。原则只有一条：**凡是能算出来的，绝不交给模型算**。

**3. 生成（Agent）**。把 `aggregated.json` 喂给 Agent，同时给一个严格的 JSON Schema（字段固定：服务状态、异常与告警、变更记录、风险与待办），要求只引用输入中的数字、不得编造。输出过 Schema 校验，失败重试一次，仍失败则降级为直接渲染聚合数据——保证日报永远发得出去。

**4. 投递与归档**。校验通过的 `report.json` 套进 Markdown 模板渲染，经频道插件推送到群，同时写入一个 git 仓库做长期归档，方便月末回看趋势。

## 踩坑点

- **时区边界**：定时任务跑在 UTC 容器里，第一天日报统计的其实是"前天 16:00 到昨天 16:00"。所有日期一律在脚本里用 `Asia/Shanghai` 显式换算。
- **数字幻觉**：最初让模型自由组织全文，失败率会被"四舍五入"得面目全非。改成模板注入数字、模型只写定性描述后，问题消失。
- **静默失败**：流水线挂了比没有日报更糟。加了心跳逻辑——任一阶段失败都向频道发一条简短告警，附失败阶段名。
- **敏感信息**：日志里偶有 token 和手机号，聚合脚本里加一层正则脱敏，再进模型。

## 可复用建议

- 聚合与叙述分离：确定性代码管数据，LLM 只管最后一公里的表达。
- 模板即契约：报告结构写成 Schema，产出才稳定、可归档、可对比。
- 中间产物落盘：`raw → aggregated.json → report.json → report.md`，任何一环出错都能单独重放。
- 先手动触发跑一周，确认数据可信后再挂定时，不要一上来就全自动化。

## 总结

日报本身不值钱，值钱的是"每天早上不需要人去翻日志"。这条流水线的关键不是某个精巧的 prompt，而是分工：把可计算的交给脚本，把可校验的交给 Schema，把只剩表达的部分交给 Agent。照这个骨架，周报、值班交接单都能低成本复用。
