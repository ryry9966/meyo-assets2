## 背景

跑了一段时间 OpenClaw 之后，手上的自动化任务越来越多：定时抓取、数据清洗、各类 agent 的日常执行。日志散落在不同插件的输出目录里，格式各异。每天早上人工翻一遍日志、汇总成日报，大概要花二十分钟，而且经常漏掉真正重要的异常。

于是把这件事做成了流水线：每天早上 9 点，自动收到一份结构化日报。本文记录做法和踩过的坑。

## 问题

核心矛盾有三个：

1. **格式不统一**。不同 agent、不同插件输出的日志结构完全不同，有的纯文本，有的 JSON，有的带多行堆栈。
2. **不能直接丢给 LLM 总结**。原始日志一天几万行，直接塞进上下文会超限；更糟的是让模型"统计"数字，它真的会编。
3. **报告格式漂移**。每次让模型自由发挥，日报样式都不一样，没法横向对比。

## 做法

流水线分五步，每步职责单一：

**1. 采集与归一化。** 写一个 normalize 阶段，把所有数据源统一转成 JSONL，字段固定为 `timestamp / source / level / event / duration`。解析失败的行不报错，丢弃并计数，计数本身也进日报。

**2. 时间窗切片。** 按自然日聚合，时区统一转成本地业务时区后再切，这一步后面细说坑。

**3. 指标先行。** 用代码算好所有硬数字：任务总数、成功率、平均耗时、Top 5 错误。原则是——**数字归代码，叙述归模型**。

**4. 分块摘要。** 超过阈值的日志按块喂给 LLM，prompt 里明确约束：只允许引用给定的数字和事件，不得补全推断。每块输出固定 schema 的 JSON，最后合并。

**5. 组装与投递。** 模板渲染成 Markdown，推送到 IM webhook；同时归档一份 JSON 原始版，方便事后复查和回填。

调度直接用定时任务触发，整条链路无人工介入。

## 踩坑点

- **时区**：服务器是 UTC，最初按 UTC 切日，结果"昨天"的边界和业务认知对不上，晚上 8 点后的任务全被算到第二天。统一转 +8 后再聚合，问题消失。
- **模型编数字**：早期让 LLM 直接从日志里"统计错误次数"，它给出了一个看起来很合理但完全错误的数。改成代码算数、模型只写解读后彻底解决。这是整条流水线最重要的一条原则。
- **重复投递**：调度重试导致同一份日报推了两次。加了幂等键（日期字符串），当天已生成则直接跳过。
- **日志噪音**：debug 级别日志把上下文撑爆，分块数量翻倍。入库前按 level 过滤，噪音降了一个数量级。
- **prompt 漂移**：改一次 prompt，日报风格就变一次。后来把 prompt 当代码版本管理，改动走提交记录。

## 可复用建议

- **schema 先行**：先定报告的 JSON schema，再反推 prompt 和渲染模板，格式稳定性问题基本消失。
- **中间结果落盘**：每个阶段的输出都缓存到磁盘，出问题时可以从任意阶段重放，排查成本极低。
- **留 dry-run 模式**：跑一遍全流程但不投递，调 prompt 和模板时非常省心。
- **失败也要报告**：流水线自身挂了，也要推送一条"日报生成失败"的通知，静默失败最危险。

## 总结

这套流水线上线后，每天早上的日报稳定产出，人工成本归零，而且因为指标是代码算的，数字完全可信。LLM 在这里的定位是"解读员"而不是"统计员"——把确定性的事交给代码，把需要语言能力的事交给模型，是这类自动化任务里最值得记住的分工方式。
