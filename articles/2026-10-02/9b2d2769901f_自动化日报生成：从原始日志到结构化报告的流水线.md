## 背景

我们团队跑着十来个服务和若干定时 Agent 任务，日志分散在容器、文件和各家监控面板里。过去每天的日报靠人工早上翻日志、拼数字、写两句结论，不仅耗半小时，还经常漏掉凌晨的异常。目标很朴素：每天早上 9 点，一条结构化日报自动出现在群里，人不碰原始日志。

## 问题

拆开看其实是三个问题：

1. **数据散**：日志格式不统一，同一个"错误"在不同服务里叫法不同；
2. **口径不统一**：人工统计时 P95 有时算全天、有时算工作时间，周同比经常对不上；
3. **总结不稳定**：直接让模型"读日志写总结"，数字幻觉频出，日报反而不如手写可信。

核心决策是：**把"算数"和"写话"彻底分开**。统计交给确定性脚本，模型只负责叙述。

## 做法

整条流水线分五步：

1. **日志归一化**：凌晨 cron 脚本拉取前一天日志，统一成固定 JSON schema（`ts / level / service / event / latency_ms / trace_id`），同时落盘一份 raw snapshot 留档。
2. **指标计算**：纯脚本统计 P95 延迟、错误率 TopN、关键事件计数，输出 `metrics.json`。这一步零模型参与，可以写单元测试。
3. **Agent 汇总**：OpenClaw 定时任务触发 agent，通过 MCP 工具读取 `metrics.json`（避免大文件塞上下文），prompt 里锁定输出 schema：结论 / 异常 / 待办 / 数据附录，并附上昨日报告作为 few-shot。
4. **校验与兜底**：用 JSON Schema 校验 agent 输出，字段缺失或数值与 `metrics.json` 对不上就重试一次；仍失败则降级为纯模板报告 + 触发告警。
5. **分发与留档**：推送到群 webhook，Markdown、metrics、prompt 版本号一起写进归档目录，事后任何一份数字都能回溯。

## 踩坑点

- **模型对不上数**：早期让模型直接读日志，错误计数天天飘。改成只喂聚合指标后才稳定——这是整条流水线最重要的一次重构。
- **时区**：日志是 UTC，人是 UTC+8，第一版日报统计的实际是"昨天的明天"。归一化阶段统一转本地时区。
- **输出解析失败**：prompt 里要求"先输出 JSON"，模型偶尔还是夹带解释文字。Schema 校验 + 一次重试解决了大半。
- **流水线自己也会挂**：有一次脚本静默失败，群里安静了一天才被发现。现在"日报未按时发出"本身就是一条独立告警。
- **Token 浪费**：日志全文塞给模型又贵又没用，采样 + 聚合指标足够。

## 可复用建议

- **固定 schema 是前提**：数据层稳定，叙述层才敢放手让模型写。
- **prompt 当代码管理**：版本号随报告归档，改了什么可 diff、可回滚。
- **留黄金样本做回归**：改 prompt 后跑一遍历史数据，人工对比新旧输出。
- **数字可溯源**：报告附录带上 metrics 文件路径，任何结论都能点回原始数据。

## 总结

这条流水线的价值不在模型多强，而在于把不确定的部分（自然语言叙述）压缩到最后一小步，把确定的部分（统计、校验、兜底、分发）全部工程化。Agent 只负责"把数字说成人话"，稳定性反而最高。下一步计划让周报、月报复用同一层 metrics，只换叙述模板。
