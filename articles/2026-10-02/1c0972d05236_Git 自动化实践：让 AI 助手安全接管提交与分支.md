## 背景

日常 git 操作里有一大块是纯机械劳动：写 commit message、给分支命名、清理已合并分支、提交前整理变更。把 OpenClaw 的 agent 接上终端工具（或一个 git MCP server）之后，很自然地会想把这些活儿交出去。但第一次让 agent 跑 `git add -A && git commit`，你就明白这事不能裸奔。

## 问题

直接给 agent 完整 shell 权限操作 git，常见的翻车方式有五种：

1. **提交脏东西**：`.env`、构建产物、调试代码被 `add -A` 一锅端进历史；
2. **擅自改历史**：agent 遇到冲突时自己 amend / rebase，某些提交悄悄消失；
3. **分支失控**：每个任务开新分支，不清理也不切回，两周后仓库里躺着一堆 `agent/task-7`；
4. **message 不可读**：乱加 emoji、编造署名，回溯时对不上号；
5. **危险命令混入**：`push --force`、`reset --hard`、`clean -fd` 夹在正常任务里执行。

根源不是 agent 笨，而是我们把「能执行 git」和「该执行哪些 git」混为一谈了。

## 做法

核心原则一句话：**收窄权限、白名单执行、hook 兜底、全程留痕**。

1. **不给裸 shell，给受控工具层。** 封装一组脚本或 MCP 工具，只暴露白名单子命令：`status` / `diff` / `log` / `branch` / `add` / `commit`。明确拒绝 `push --force`、`reset --hard`、`rebase`、`clean`、`checkout -- .`。
2. **add 带路径约束。** 提供 `agent_commit` 脚本，只接受显式路径，内部先跑 secret 扫描（gitleaks 之类）和大文件检查，不过关直接拒绝。agent 永远碰不到 `-A`。
3. **commit 走模板。** 约定 `type(scope): summary` 格式，prompt 里写死，禁止 emoji 和编造署名；要求提交前先输出一段 diff 摘要——这段摘要本身就是给你 review 用的。
4. **分支划隔离区。** agent 只允许在 `agent/` 前缀分支工作，主分支对其只读；任务结束自动删除已合并的 `agent/*`，超期未合并的列出来提醒人。
5. **提交前状态检查。** 校验当前分支、detached HEAD、未跟踪敏感文件，条件不满足就拒绝执行并汇报，而不是自作主张。
6. **审计日志。** 每次写操作记录时间、分支、命令、涉及文件，出问题能回放。

## 踩坑点

- **`git add -A` 是事故第一来源。** 哪怕 prompt 里禁了，长上下文中 agent 也会忘。唯一可靠的办法是工具层根本不提供这个能力，而不是靠叮嘱。
- **MCP git server 不等于沙箱。** 部分实现底层是拼 shell 命令，路径注入要自己测，上线前用恶意输入过一遍。
- **detached HEAD 陷阱。** agent checkout 到某个 commit 后继续提交，这些提交不在任何分支上，GC 后就没了。提交前必须校验分支状态。
- **hook 是最后防线，但可被绕过。** agent 会用 `--no-verify` 跳过 pre-commit，把它也加进禁用列表，hook 里再校验一次。
- **人机并发冲突。** 你本地 rebase 时 agent 也在推分支。简单做法：agent 的 git 任务串行化、进队列。

## 可复用建议

- 把白名单工具层做成团队共享资产：一份工具配置 + 一份 prompt 约定，别每人各写一套；
- 先上 dry-run：让 agent 输出「打算执行的操作清单」，人确认后真执行，稳定一两周再放开；
- 每周让 agent 出仓库健康报告：stale 分支、未合并变更、异常大文件——顺便检验它的权限边界；
- 审计日志进统一日志系统，和人的操作用不同 tag 区分。

## 总结

让 AI 管 git，目标不是全自动，而是把机械劳动交出去、把不可逆决策留下来。权限收窄、白名单执行、hook 兜底、操作留痕，这四件事做到位，agent 才算一个能放心共事的协作者。建议从「只允许提交到 `agent/` 分支」这个最小场景跑起，比一次铺开全自动靠谱得多。
