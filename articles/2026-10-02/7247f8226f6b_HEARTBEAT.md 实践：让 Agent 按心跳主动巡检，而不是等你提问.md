## 背景

大多数人用 Agent 还是"一问一答"：你想起来，才去问它。但很多事不需要你记着——每天扫一眼 GitHub 通知、盯服务器磁盘、检查某个接口是否还活着。OpenClaw 提供了一个很轻的机制：**HEARTBEAT.md**。Agent 按固定间隔"醒来"读这个文件，有活就干，没活就继续睡，文件为空或只有占位内容时不会打扰你。

## 问题

没有心跳的 agent 有两个典型痛点：

1. **人成了调度器**。所有周期性任务都靠你记得发起。
2. **cron + 脚本解决不了需要判断力的部分**。"这次变更值不值得通知我？""这个错误要不要吵你？"写不成死规则。

## 做法

**1. 建文件。** 工作区根目录放 `HEARTBEAT.md`（默认 `~/.openclaw/workspace/`），两三行就能跑：

```markdown
- 每天早上 8 点汇总 GitHub 通知，超过 10 条才发消息
- 检查 example.com 返回码，非 200 才通知
```

**2. 配间隔。** `openclaw.json` 的 heartbeat 配置可调间隔（默认约 30 分钟）。验证阶段先调成 2 分钟，确认行为符合预期再调回。

**3. 写"可判定"的指令。** 每行一个任务：动词开头 + 明确条件 + 明确通知策略。"关注一下服务器"是坏指令；"磁盘使用率超 85% 才发消息"是好指令。

**4. 加全局约定**（放文件开头）：

```markdown
- 只在结果有变化时才通知我，否则保持沉默
- 任务完成后，把这行从本文件删掉
```

**5. 让它自我维护。** Agent 本身能写文件：执行完自删、发现值得周期跟踪的事自加。跑一两周后，你会得到一份被真实使用过滤过的任务清单。

## 踩坑点

- **文件写长**。每次心跳都会把整个文件注入上下文，一天几十次，长文等于持续烧 token。原则：永远不超过一屏。
- **一次性任务不清理**。"明天提醒我交房租"不删掉就会天天触发。一次性的事走普通对话。
- **模糊指令导致消息轰炸**。没有通知门槛的任务，agent 倾向于"有产出就汇报"，很快你会把它静音。
- **把它当记忆用**。事实、偏好、项目背景进 memory；HEARTBEAT.md 只放"要做什么"。
- **夜间打扰**。定时任务没分时段，凌晨三点收推送。通知策略里写清楚允许的时段。
- **静默失败**。心跳中工具调用没权限、网络挂了，agent 可能什么都不说。约定"失败也要报，哪怕一句话"。

## 可复用建议

- 把 HEARTBEAT.md 理解成**带判断力的 crontab**：cron 管"什么时候跑"，它管"跑完值不值得吵你"。
- 三个通知等级够用：**沉默 / 变更才说 / 立即说**，每个任务标一个。
- 每周让 agent 自己汇总心跳执行记录，砍掉连续两周没触发过通知的任务——要么门槛太高，要么任务已死。
- 成本先算再调：单次心跳 token 消耗 × 一天次数。多数场景 30–60 分钟足够。
- 团队共用 agent 时，HEARTBEAT.md 进 git，改任务走 PR——"谁来吵你"这件事值得过审。

## 总结

HEARTBEAT.md 的价值不在"定时执行"——cron 早就做得到——而在于执行者是一个有上下文、有判断力的 agent：它知道这个变化上次是什么样，知道哪些事不值得叫你。文件要小、指令要可判定、通知要有门槛。做到这三点，agent 就从"你想起才问的工具"，变成"按自己的节拍巡检的同事"。
