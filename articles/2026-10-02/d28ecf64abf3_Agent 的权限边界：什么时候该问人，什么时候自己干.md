## 背景

OpenClaw 这类常驻 agent 的麻烦在于它不是"用完即走"的工具：它握着 shell、文件系统、消息通道、定时任务，还能挂一堆 MCP server 和插件。能力越多，一个问题越绕不过去——哪些动作它可以直接干，哪些必须停下来问人？

## 两个极端都试过

实践中常见两种失败模式。

一种是**事事都问**：删个临时文件要确认，读个目录要确认。最后你变成人肉回车键，agent 的自动化价值趋近于零，更糟的是人陷入审批疲劳，开始不假思索地点"允许"。

另一种是**什么都不问**：一次未经确认的 force push、一条发错群的消息、一张误删的表——只需要一次，你就再也不敢开权限，然后退回第一种模式。

所以真正的问题不是"问不问"，而是怎么分级。

## 做法：按可逆性 × 影响面分三档

我们把分级写进项目的权限配置，由工具层强制执行，而不是靠 system prompt 里的一段话——prompt 会被偶尔忽略，护栏不会。

- **第一档，自动执行**：只读操作，以及 workspace 内可逆的小范围写操作——读文件、查状态、写草稿、git commit 但不 push。这档不需要任何打断。
- **第二档，带护栏的自动执行**：有副作用但可逆、影响面可控——往白名单会话发消息、安装明确列出的依赖。护栏是两条：执行前落审计日志（工具、参数、理由），执行后发一条简短通知。出问题能回放、能回滚。
- **第三档，必须人工确认**：不可逆或对外可见的操作——删除、force push、对外发送、涉及钱的调用、白名单之外的系统变更。

三个关键细节：

1. **白名单拦参数，不只拦工具名。** 只看"允许 shell 工具"没用，`git status` 和 `rm -rf` 走的是同一个工具，参数级的前缀/正则约束才是底线。
2. **确认请求要"可回答"。** 别问"我可以执行 X 吗"，直接给 diff、影响范围和备选方案，让人做选择题而不是阅读理解。
3. **区分确认与通知。** 确认是"不回复就不执行"，通知是"干了，说一声"。混用会导致要么阻塞、要么形同虚设。

## 踩坑点

- **深夜确认轰炸**。无人响应的确认要么超时自动执行（危险），要么永久挂起（任务烂尾）。定时任务等无人值守场景，只允许第一、二档。
- **新接的 MCP server 默认全量授权**。每加一个工具都重新过一遍三档，别因为"来源可靠"就放行。
- **规则写在 prompt 里但工具层没有 enforcement**。模型偶尔会"创造性"地绕过措辞去达成目标，信任工具层，别信任话术。
- **事后通知写得太啰嗦**，人开始无视通知，第二档的护栏就悄悄退化了。

## 可复用建议

- 默认最小权限，白名单增长要慢；出一次事故，先收紧再排查。
- 把分级配置做成版本化文件，随仓库走，团队和多个 agent 实例共用同一套标准。
- 每周回放一次审计日志，重点看第二档里 agent 自作主张的部分——边界最容易被慢慢蚕食的就是那里。
- 给确认加预算：单个任务最多触发 N 次人工确认，超了就拆任务，或者整体升级给人接手。

## 总结

权限边界不是为了限制 agent，恰恰相反：有了清晰且被工具层强制的分级，你才敢放手让它做第一、二档的事。确定性来自配置和护栏，不来自更长的 prompt。先小后大，先可逆后不可逆，边界的松紧跟着信任的积累走，不要一步到位。
