## 背景

OpenClaw 的记忆体系很朴素：`memory/` 目录下一堆 markdown 笔记，加上一个 `memory_recall` 工具，助手按需召回相关片段注入上下文。争议在于 recall 底层怎么检索——默认走语义搜索（embedding + 向量相似度），也有人自己接了 SQLite FTS5 / BM25 的全文索引。社区两条路线各有拥趸，但拿数据说话的不多。

## 问题

我的场景：约 200 条记忆，涵盖项目决策、部署记录、个人偏好。实测中遇到两类典型翻车：

- **语义搜索翻车**：问“上周为什么把 cron 从每 5 分钟改成每小时”，召回一堆“定时任务最佳实践”，真正那条决策记录排第五。
- **全文搜索翻车**：问“数据库连接池那个报错怎么解决的”，但笔记里当时写的是 "pool exhausted"，查询词对不上，直接空手而归。

结论先行：单用哪个都有明显盲区。

## 做法

1. **建评测集**：从历史会话里挑 40 个真实问题，人工标注应命中的记忆条目，指标用 hit@3。
2. **跑三种配置**：纯语义、纯全文、混合（两路各取 top5，RRF 融合排序）。
3. **中文分词单独处理**：FTS5 默认的 unicode61 tokenizer 对中文基本是摆设，接 jieba 分词后重建索引才可用。
4. **向量化**：轻量中文 embedding 模型，768 维，200 条记忆一次跑完几秒钟。

结果（hit@3）：语义 72%，全文 65%，混合 88%。样本不大，但趋势稳定——混合明显占优，且两路翻车的题目几乎不重叠。

## 踩坑点

- **改了 memory 文件必须重建索引**。有次只改了标题，语义索引还是旧向量，新标题永远查不到。后来在保存钩子里挂了增量重建。
- **全文搜索对查询词极其敏感**。口语化提问和笔记术语对不上是常态，这恰是语义搜索的主场。
- **小语料上语义搜索会“过度自信”**：没相关内容也硬凑一条相似度 0.6 的。加阈值，低于 0.55 直接返回空，让助手老实承认没记住。
- **RRF 权重别拍脑袋**。一开始 1:1 融合，发现全文路噪音更多，调成语义：全文 = 2:1 才稳。

## 可复用建议

- 记忆 **少于 100 条**：先用全文 + jieba，别上向量——收益低，还要多维护一份 embedding 依赖。
- 记忆 **上千条或中英混排**：直接上混合检索，RRF 是性价比最高的方案。
- **评测集必须用真实提问**，别自己编查询——自己编的词天然贴近笔记用词，会严重高估全文搜索。
- 给 recall 结果加相似度/得分日志，跑一周再回头调参，比空想有用。

## 总结

这不是“哪个更好”的问题，而是“什么规模、什么查询习惯”的问题：语义搜索解决“说法不一致”，全文搜索解决“专有名词精确匹配”，而记忆检索两种需求同时存在。OpenClaw 的 recall 链路足够开放，两条路都能自己接。花半天建个 40 题的评测集，比看十篇对比文章都值。
