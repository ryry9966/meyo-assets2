## 背景

单 Agent 串行处理多任务的痛点很明显：当自动化流程里同时存在“查数据、读文档、分析日志”这类互不依赖的事，主 Agent 只能一步步来，一轮任务跑十几分钟；而且所有中间结果都堆在主 Agent 的上下文里，跑着跑着就开始遗忘前面的约束。Subagent（子代理）的思路是把任务拆给多个独立 Agent 实例并行执行，主 Agent 只负责拆分、派发和汇总。

## 问题

实际用下来主要卡在三点：一是什么任务能拆、怎么判断独立性；二是子 Agent 的输出格式五花八门，汇总时经常返工；三是并发一上去，API 限流、token 费用、写资源冲突全跟着来了。

## 做法

以我跑的一个周报流程为例：拉取三个数据源 → 各自生成摘要 → 合并成一篇报告。

1. **拆分判断**：列出所有子任务，标出各自的读写资源。只有“读不冲突、写不同目标”的才算可并行。三个数据源各写各的草稿文件，满足条件。
2. **定契约**：每个 subagent 固定一段 role 描述 + 输出 schema（必须返回 JSON，含 `source`、`summary`、`anomalies` 三个字段）。格式不对直接判失败重跑，不靠主 Agent 去猜。
3. **派发与隔离**：主 Agent 一次 spawn 三个 subagent，每个只挂它需要的 MCP 工具（数据源 A 的子 Agent 不给写入类工具），上下文只塞该子任务必需的背景，不带全局对话历史。
4. **并发控制**：从 2 起步，最终定在 3。再高就会撞 rate limit，单个子任务反而变慢。
5. **容错**：每个 subagent 设超时（5 分钟）和一次重试；失败时返回显式错误对象，主 Agent 汇总时生成“部分结果”，并在报告里标注缺失项，而不是整轮作废。
6. **汇总**：主 Agent 只做合并、去重、冲突标注，不再自己重新查询——否则等于白拆。

## 踩坑点

- **假独立**：两个子 Agent 都要改同一个配置文件，并行后互相覆盖。现在凡涉及写操作，一律退回串行或加文件锁。
- **隔离过头**：子 Agent 不知道全局约定（比如术语表），产出对不上。解决：把必要约定写进子任务的 prompt 模板，别指望“它应该知道”。
- **递归失控**：subagent 又去 spawn subagent。现在硬性限制嵌套深度为 1。
- **静默失败**：子 Agent 超时后返回空字符串，汇总阶段当成了“无异常”。之后所有 subagent 强制走结构化返回，错误也要带类型字段。
- **成本翻倍**：并行是把耗时换成了 token，三个并行不是快三倍，账单先快三倍。跑之前用日志估一下量级。

## 可复用建议

- 先串行跑通整个流程，确认每个子任务单独可用，再改并行。
- 每个 subagent 三件套缺一不可：一句话角色、一份输出 schema、一份工具白名单。
- 并发数、超时、重试全部做成配置项，不要写死在代码里。
- 每次运行记录耗时和 token 消耗，并行收益要用数据验证，而不是凭感觉。

## 总结

Subagent 编排的核心不是“多个 AI 很酷”，而是任务拆分、契约和隔离这三件朴素的事。并行只是拆分做对之后的自然收益；任务拆错了，并行只会更快地产生错误结果。先把串行流程打磨干净，再谈并行，是性价比最高的路径。
