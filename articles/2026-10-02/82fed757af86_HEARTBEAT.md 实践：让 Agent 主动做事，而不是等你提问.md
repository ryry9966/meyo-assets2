## 背景

OpenClaw 里的 Agent 默认是应答式的：你在聊天渠道发消息，它才被唤醒。但日常使用中，很多需求天生是主动的——早上推一份日程汇总、定时盯某个仓库的新 release、发现日志异常再通知你。为这类场景，OpenClaw 内置了一个很轻的机制：工作区里的 HEARTBEAT.md。

## 它解决的问题

原理一句话：网关按固定间隔（默认 30 分钟，可配）触发一次心跳回合，Agent 醒来后先读 HEARTBEAT.md，逐条判断有没有"现在该做的事"。有就执行；没有就回一个约定的 `HEARTBEAT_OK`，这条回复会被网关静默吞掉，不推进你的聊天窗口，也不产生噪音。相当于给 Agent 加了一个 markdown 版的 cron 触发器，但判断权在模型手里。

## 做法

1. 在 Agent 工作区（默认 `~/.openclaw/workspace/`）新建 HEARTBEAT.md，写清判定条件，而不是笼统目标：

```markdown
# 心跳清单
- 早上 8 点后第一次心跳：汇总今天日程和未读消息，发到 Telegram
- 检查 ~/logs/error.log 末尾 50 行，出现 FATAL 才通知我
- 每天最多一次：查看 openclaw 仓库是否有新 release
```

2. 在 openclaw.json 里调频率和通知渠道：

```json5
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "30m", "target": "telegram" }
    }
  }
}
```

3. 重启网关，在日志里确认 heartbeat 回合真的在跑，再逐步加条目。

## 踩坑点

- **Token 成本**：心跳空转也消耗一次模型调用。清单文件保持精简，低价值任务把间隔拉到 1 小时以上，比全局 10 分钟轮询划算得多。
- **重复执行**："检查服务器磁盘"这种没有完成态的条目，Agent 每个心跳都会做一遍。解法是引入状态：让它把上次结果和执行时间写进一个 scratch 状态文件，下个心跳先读状态再决定是否行动。
- **时间感不可靠**：让模型自己估"现在几点"容易出错。条件里写绝对阈值（"8 点后的第一次心跳"），并在状态里记录"今天是否已执行"。
- **重活别放心跳**：长脚本、批量抓取会把回合拖死。心跳里只做"判断 + 触发"，重活让它起后台任务或落地成脚本执行。
- **通知泄漏**：如果每次心跳都在聊天里冒一句"没有待办"，说明 `HEARTBEAT_OK` 没被静默处理，先查配置和版本。

## 可复用建议

- 清单条目 = 触发条件 + 动作 + 频次上限，三者缺一就容易抖动（反复触发或永远不触发）。
- 用一个小状态文件把"无状态清单"升级成"有状态巡检"，这是这套机制从玩具变工具的分水岭。
- 分层设频次：监控类 30 分钟、汇总类按天、信息源类 2 小时起，别用统一间隔硬套。

## 总结

HEARTBEAT.md 的价值不在"自动执行"本身，而在它把 Agent 从问答机变成了有自主节奏的进程。它刻意做得笨——只是定时读一个 markdown 清单——但配合状态文件和条件设计，足以覆盖个人助理里大部分主动场景。建议从一两条真正有价值的巡检写起，别把它堆成第二张待办清单。
