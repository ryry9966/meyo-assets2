# 背景

OpenClaw 里每个频道的对话默认跑在一个主 session 中：用户消息、模型回复、工具调用和工具输出，全部写进同一个上下文窗口。日常问答没问题，但一旦让主会话去干“重活”——比如翻 30 个文件找配置差异、读几百行日志定位报错——所有中间产物都会留在主会话历史里。

# 问题

这种污染有两个直接后果：

1. **上下文膨胀**。工具输出动辄几千 token，几轮重活之后主会话长度暴涨，响应变慢、成本上升，模型对早期对话的注意力也被稀释。
2. **干扰后续对话**。主会话残留大量无关的中间步骤，模型容易被旧的工具输出带偏，出现答非所问或重复执行已完成操作。

子 Agent 的 session 隔离就是为解决这个问题的。

# 做法

OpenClaw 提供 `sessions_spawn` 工具，可以在主会话里派生一个完全隔离的子 session：独立的会话文件、独立的上下文窗口、独立的工具调用历史。子 Agent 干完活，只有最终摘要回传给主会话。

实际操作四步：

1. **识别适合下放的任务**：读多写少、目标单一、一次性交付。典型如代码审计、日志排查、批量文件整理。
2. **写清楚任务描述**。子 Agent 看不到主会话历史，spawn 时必须把目标、范围、约束、期望的返回格式全部写进 task prompt。我常用四段式模板：目标 / 范围 / 交付物 / 禁止事项（不要写记忆、不要主动回复用户、不要动配置文件）。
3. **加 label 和超时**。`sessions_spawn` 支持 label 参数，养成 `audit-0607` 这类命名习惯，事后好清理；长任务设超时，避免子 Agent 卡死占资源。
4. **拿摘要、继续主线**。主会话只收到一段结构化摘要，历史干净，后续对话不受影响。

# 踩坑点

- **任务描述太模糊**。子 Agent 拿不到主会话上下文，“帮我看看刚才那个问题”只会得到泛泛而谈的结果。上下文必须显式传递。
- **文件系统和记忆是共享的**。session 隔离只隔离上下文，子 Agent 与主 Agent 共用同一个 workspace 和 MEMORY.md。不想让它写记忆，要么在 task prompt 里明说，要么收紧工具权限。
- **过度派生**。两行就能搞定的事也 spawn 子 Agent，等于额外付一次冷启动：新上下文要重新读文件，延迟和成本都上来了。
- **失败只回传错误**。子 Agent 中途失败，主会话拿到的可能是错误或空摘要。重活尽量拆成可幂等重试的小步，别指望一个超大子任务一次跑通。
- **session 文件会积累**。不带 label 的子会话事后很难辨认，定期用 `/status` 查看并清理。

# 可复用建议

- 判断标准：token 消耗大、单次交付、无需多轮交互的任务 → 子 Agent；需要来回追问的 → 留在主会话。
- 把 spawn 的 task prompt 模板固化下来（目标/范围/交付物/禁止事项），团队统一格式，摘要质量会稳定很多。
- 把子 Agent 的返回摘要当成接口契约，明确要求格式（如 JSON 列表），主会话才能可靠地继续处理。
- 工具权限按需收紧，尤其不希望子 Agent 触达消息发送类工具时。

# 总结

session 隔离的本质是“脏活隔离、摘要回传”：主会话只保留决策上下文，探索性的大量工具调用放进一次性子 session，用完即弃。配合明确的任务描述、label 命名和定期清理，这套模式能显著压住主会话的上下文膨胀，让长周期对话保持稳定。
