## 背景

跑 Agent 做本地自动化，最常见的翻车不是模型能力不行，而是它对"这台机器"一无所知：在 macOS 上执行 `apt-get`，往不存在的 venv 里装包，没配代理就卡在下载上。MCP 这类协议解决了"工具怎么调"，但"这台机器上哪些工具能用、路径在哪、有什么坑"往往还是散落在 system prompt 的只言片语里，换台机器就得重写。

OpenClaw 的工作区约定里本来就有 `TOOLS.md` 这个位置，用于给 Agent 记录工具笔记。但实践中单一文件很快会出问题：项目相关的配置要跟仓库走、能提交共享；机器相关的配置只能留在本机。混在一起，要么泄露，要么换台机器就失效。

## 做法：基线 + 本地 + 探针

**1. 基线层：项目仓库里的 `tools.md`（提交进 git）**

只写与项目相关、团队通用的事实：启动命令、端口约定、目录结构、脚本入口。写成陈述句，不写操作流程——流程是脚本和 skill 的事，这里只回答"是什么"。

**2. 本地层：`tools.local.md`（加入 .gitignore）**

只写机器相关的事实：操作系统与包管理器、Python/Node 版本、虚拟环境路径、GPU 是否可用、代理地址、Shell 类型。绝不写密钥，需要凭证的地方只写"从环境变量 XXX 读取"。

**3. 探针脚本生成本地层**

与其手写，不如探测后生成：

```bash
# probe.sh：探测结果写入 tools.local.md
{
  echo "os: $(uname -s)"
  echo "pkg: $(command -v brew >/dev/null && echo brew || echo apt)"
  echo "python: $(python3 --version 2>&1)"
  echo "venv: ${VIRTUAL_ENV:-none}"
} > tools.local.md
```

新机器跑一遍，几十秒拿到准确底稿，人工只补探测不到的坑，比如"这个代理只在内网生效"。

**4. 明确优先级**

给 Agent 的指令写清楚：先读基线 `tools.md`，再读 `tools.local.md`，冲突时以本地为准；本地没有的事实，运行时先探测再执行，不要凭训练记忆猜。

## 踩坑点

- **把密钥写进 tools.md**。最高频事故。文档会被读进上下文、进日志、被随手 commit，凭证只走环境变量或密钥管理器。
- **写成了操作手册**。一旦开始写"第一步……第二步……"，文档就会和实际脚本漂移。事实归 tools.md，步骤归脚本和 skill。
- **过期信息比缺失更危险**。系统升级、venv 挪了位置，文件没更新，Agent 会拿着旧地图走新路。给本地层加"最后验证日期"，探针脚本定期重跑。
- **和 MCP 配置重复定义**。工具列表以 MCP 配置为唯一来源，tools.md 只引用名字，不复述参数。
- **贪长**。每行都消耗上下文。我的经验是基线层控制在 60 行以内、本地层 30 行以内，写不下的内容说明该拆成独立文档按需加载。

## 可复用建议

- 把 `tools.md` 当代码评审：环境约定的变更走 PR，避免"某人本地改了没人知道"。
- Windows 机器单独注明路径分隔符和换行符差异，这类问题报错信息很隐晦。
- 文件里加一节"不确定项"：明确告诉 Agent 哪些事实需要运行时验证，比让它自信地猜要好。

## 总结

tools.md 不是又一份"给 AI 看的说明文档"，而是一套分层约定：基线层随仓库共享，本地层描述这台机器，探针脚本保证它不过期，优先级规则消除歧义。它把"环境差异"从 Agent 的猜测变成显式输入——换机器、换项目时，配置迁移就是复制一个文件、跑一次脚本的事。
