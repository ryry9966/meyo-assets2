## 背景

用 OpenClaw 做日常自动化一段时间后，主会话会碰到两个典型瓶颈：一是上下文被中间产物塞满——读文件、长输出、报错日志全混在一起，后面的问答质量肉眼可见地下降；二是任务只能串行，让主 agent 一边盯一个长任务一边回复你，体验很差。subagent 机制就是针对这两点：主 agent 把任务打包交给一个隔离的子会话去跑，结束后只把结果带回主上下文。

## 问题

拿我自己的场景举例：每周要做一次仓库巡检，包含扫描依赖更新、跑测试、整理 changelog 草稿三件事。它们彼此独立，但各自都耗时耗 token。以前主 agent 顺序执行，一轮十几分钟，期间主会话基本不可用；更要命的是中间输出撑爆上下文，巡检做完，agent 反而变"笨"了。

## 做法与步骤

1. **拆任务，先判断独立性。** 三个子任务互不依赖、不写同一批文件，适合并行。有先后依赖的（先跑测试、再写报告）不要硬拆成并行。
2. **写自包含的任务简报。** 子会话看不到主会话的上下文，spawn 时必须把目标、约束、输出格式一次说清。我的简报模板固定三行：做什么、不要碰什么、以什么格式返回。
3. **选运行模式。** 短任务（两分钟内）用前台等待，直接拿结果；长任务放后台，主会话继续干活，通过 session 状态轮询收结果。
4. **约定紧凑的返回格式。** 要求每个 subagent 只回结构化摘要：结论、关键数据、异常项，过程不带回。
5. **汇总与兜底。** 主 agent 收齐后合并成一份报告；超时或失败的子任务单独标记重跑，不阻塞整体流程。

## 踩坑点

- **误以为子会话共享上下文。** 最初我在简报里写"接着上面的分析继续"，子 agent 完全不知所措。简报必须自包含，这是最容易犯的错。
- **并行度失控。** 一口气开了 7 个子会话，撞上限流，账单也难看。现在稳定控制在 3 个以内。
- **共享资源冲突。** 两个子 agent 同时往同一个 git 工作区写文件，直接冲突。涉及写操作的任务要么串行，要么各给独立目录。
- **返回结果过长。** 子 agent 把整段日志贴回来，等于换了个地方污染主上下文。必须在简报里限定输出长度和格式。
- **嵌套 spawn。** 子 agent 又去开子 agent，排障时链路理不清。我的规则：只允许主会话派发，最多一层。

## 可复用建议

- 一个 subagent 只干一件窄任务，简报控制在几行内。
- 并行度从 2–4 起步，观察限流与成本后再加。
- 强制结构化、限长的返回格式——这是保护主上下文的关键手段。
- 长任务一律后台加轮询，别让主会话阻塞等待。
- 给子 agent 最小权限：只挂它需要的工具和 MCP，不要让它直接面对用户发消息。

## 总结

subagent 编排的本质，是把主 agent 从"干活的"升级为"派活的"。决定编排上限的是任务拆分质量和简报写作，机制本身反而简单。建议从一个真实的、可并行的重复流程入手，先跑两个并行子任务验证收益，再逐步扩大规模。并行不是目的——主会话保持干净、响应及时，才是。
