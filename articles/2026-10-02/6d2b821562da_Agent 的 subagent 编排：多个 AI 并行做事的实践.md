## 背景

单 agent 串行执行的瓶颈很明显：任务一多，上下文窗口被塞满，前后任务的中间产物互相污染，整批耗时就是所有子任务之和。在 OpenClaw 的日常场景里，这类需求其实很常见——同时给几个模块补测试、批量检查多个仓库的依赖状态、并行从几个 MCP 数据源拉数据做汇总。这些任务的共同点是：彼此独立、可拆分、单块工作量不大。这正好是 subagent 编排的主场。

## 问题

直接让一个 agent“同时干五件事”，会遇到三类麻烦：

1. 串行太慢，且一个任务卡住会阻塞整批；
2. 上下文混杂，agent 同时记住五件事时，产出质量和可调试性一起崩；
3. 并行写同一批文件直接冲突，产物也没法聚合——因为各 subagent 的“完成”标准根本不统一。

## 做法与步骤

**1. 先定任务契约，再谈并行。** 每个 subagent 的输入是一份结构化 spec：目标、允许调用的工具白名单（MCP 工具按需收窄）、输出 JSON schema。输出固定为 `status / artifacts / summary` 三个字段，主 agent 只认 schema，不认散文汇报。

**2. 上下文隔离。** subagent 不继承主对话历史，只拿最小必要信息。类比是“带着任务说明书进隔离房间干活”，不是开圆桌会议。隔离越干净，单任务质量和排障效率都越高。

**3. 控制并发。** 队列加信号量，同时最多 3~4 个。MCP 工具端通常有速率限制，并行度应取你的 API 配额能稳定支撑的水平，而不是能开多少开多少。

**4. 文件操作互斥。** 并行改代码时，给每个 subagent 分配独立目录或 worktree，最后由主 agent 统一合并。这是踩坑密度最高的一条。

**5. 超时、重试、以产物为准。** 每个 subagent 设硬超时，失败重试一次，再失败就标记 skipped。验收不看 subagent 自报的“已完成”，只看产物：文件确实改了、测试确实跑了、报告确实生成了。

**6. 禁止递归派生。** subagent 不允许再开 subagent，深度硬编码为 1，否则成本和调试难度指数级上升。

## 踩坑点

- subagent 声称完成但产物不存在：只信产物，不信汇报；
- 多个 subagent 同时装依赖、写锁文件：预先分配独立目录即可规避；
- 日志交错无法排障：每个 subagent 独立日志流，强制携带 task_id；
- token 成本翻倍：检索、摘要类子任务换便宜模型，主 agent 保持高质量；
- 工具权限没有按 subagent 收窄：并行环境下误操作会被放大，白名单必须逐任务下发。

## 可复用建议

把 subagent 定义沉淀成配置文件（角色、工具白名单、超时、并发组、输出 schema），按任务类型复用，而不是每次现写 prompt。粒度上有个经验法则：一个 subagent 一次只做一件事，且理想情况下 15 分钟内可以人工验收。最后，主 agent 的职责是拆解、调度和验收，不要自己下场干活——调度者一旦亲自写文件，整个编排就退化回串行了。

## 总结

subagent 编排本质是工程问题，不是提示词问题。契约、隔离、限流、以产物验收——四件事做扎实，多个 AI 并行干活才能真正省时间，而不是把混乱也一并并行放大。
