## 背景

大模型的会话是无状态的：窗口一关、session 一重置，助手就不认识你了。很多人第一反应是“上向量库”，但在实践中——尤其是在 OpenClaw 这种本地优先、以文件为工作区的 Agent 框架里——你会发现记忆系统的难点不在存储，而在**写入时机、检索信噪比和冲突处理**。这篇帖记录我给个人助手搭记忆层的过程，思路可以迁移到 MCP 工具或任意插件化 Agent。

## 三个真实问题

1. **状态易失**：上下文压缩、会话轮换后，口头约定过的偏好直接蒸发。
2. **全量写入不可行**：把所有对话都记下来等于没有记忆，检索时噪声会淹没信号。
3. **偏好会漂移**：三个月前“喜欢简洁回复”，现在要详细报告；append-only 的记忆库会留下自相矛盾的条目。

## 做法：四层结构 + 两个机制

**分层（核心设计）：**

- **L1 会话内存**：当前 context，随会话走，不持久化。
- **L2 核心偏好**：稳定、少量（我控制在 30 条以内），每次会话无条件注入。用结构化文件（如 YAML 或带 frontmatter 的 Markdown）而非自由文本，每条带 key、来源、更新时间。
- **L3 情节记忆**：按日期组织的笔记文件，记“某天做了什么、临时决定”，只在相关时通过 `memory_search` 之类的工具按需检索。
- **L4 程序性记忆**：能沉淀成技能/脚本/工作流的，直接自动化，不要靠“记住”。

**写入机制**：不依赖模型自觉。在任务收尾挂一个固定步骤（hook 或 prompt 约束）：先判断是否值得记；涉及长期偏好的，向用户确认后再落盘；同一主题用固定 key 做 upsert，不追加新条目。

**检索机制**：L2 常驻注入（控制在几百 token 内），L3 走语义检索 + 时间过滤。原则是宁缺毋滥——注入内容超过 context 的 5%，就该做裁剪。

## 踩坑点

- **记忆膨胀**：append-only 的记忆库三个月涨到几千行，检索命中率肉眼可见地下降。解法：偏好类条目强制 upsert，每月人工过一遍做合并与过期清理。
- **隐式推断错误**：模型会把一次性请求推断成永久偏好（“上次让我写短邮件”≠“永远写短邮件”）。写入前必须区分 explicit/implicit，后者只进 L3，不进 L2。
- **压缩截断**：会话压缩时把注入的记忆段落截掉了，助手“失忆”却无任何报错。检查压缩策略，把核心偏好放在不易被裁剪的位置。
- **敏感信息落盘**：密钥、住址被记进了明文文件。写入步骤里加一道脱敏规则，宁漏勿错。

## 可复用建议

- 偏好条目 schema 统一：`topic / content / source / confidence / updated_at`，为将来的合并和衰减留好字段。
- 建一个 10~20 条的“回忆测试集”，每次改动记忆策略后跑一遍，量化“到底记没记住”。
- 记忆文件纳入 git，变更有迹可循，也方便回滚。
- 先做文件式记忆，数据量真上来了再考虑向量库；别为十兆数据引入一整套基础设施。

## 总结

好的记忆系统 = 分层存储 + 可控写入 + 克制注入 + 定期维护。判断标准很简单：一周后，助手还会不会问出你已经回答过的问题。把记忆当产品做，而不是当功能堆。
