## 背景

OpenClaw 的 agent 日常跑在无状态的 LLM 会话上。每次新会话，模型对你的了解归零：技术栈、部署环境、代码风格、哪些目录不能碰——全得重新交代一遍。做过自动化流程的人都清楚，这种重复交代本身就是摩擦。MCP 出现之后，给 agent 外挂一个记忆库变得顺手，但"能存"和"记得对"之间差得很远。

## 问题

我见过三种典型失败：

1. **全塞 system prompt**。偏好攒到几十条后，注入内容比任务本身还长，成本上去了，注意力被稀释，模型反而开始忽略关键约束。
2. **聊天记录全量向量化**。检索回来一堆寒暄和过程性对话，真正的偏好被噪声淹没。
3. **只写不删**。三个月前用户说"要详细解释"，上周说"别啰嗦"，两条并存，命中哪条看运气。

根子在于：把记忆系统当成了"录音机"，而它应该是"有纪律的状态管理"。

## 做法

我目前的方案是分层结构 + 一条写入纪律：

**1. 分层。** 记忆分三类：稳定偏好（技术栈、风格约束）、半稳定事实（服务器地址、项目结构）、易变上下文（当前任务状态）。只有前两类进长期记忆库。

**2. 结构化存储。** 每条记忆是固定 schema 的记录：`{key, value, scope, confidence, source, updated_at}`。不存聊天原文，只存提炼后的结论——不存"用户说了一大段关于部署的话"，存 `deploy_target: homelab-k3s`。

**3. 写入走 MCP tool，不走事后抽取。** 暴露 `memory_save` / `memory_get` / `memory_forget` 三个 tool。写入触发条件收得很紧：用户显式说"记住"，或用户纠正了 agent 的行为（负反馈是最强信号，置信度直接拉满）。其余情况宁可不写。

**4. 读取分两档。** 会话启动时注入 confidence 最高、最近使用的前 N 条（我设 10 条）；其余按需通过 `memory_get` 检索。

**5. 更新即覆盖。** 同一 key 写入新值时，旧值标记 superseded，保留版本链但不再参与检索。低置信度写入先进 staging，避免一次性上下文污染长期记忆。

## 踩坑点

- **负反馈没用上**。"别这样"比"我喜欢那样"信号强得多，但最初版本只监听正面表达，导致同类错误反复出现。
- **scope 不分**。把单次任务的临时要求（"这次用 Python 写"）存成了全局偏好，第二次任务直接翻车。scope 字段是事后补的。
- **没有可观测性**。有段时间 agent 行为奇怪，查了半天才发现是某条过期偏好被命中。现在每次会话可以 dump 当前注入的记忆列表，问题一眼定位。
- **覆盖无痕**。早期直接覆盖旧值，没有时间戳和来源，出问题无法回溯。版本链不是为了炫技，是为了能回滚。

## 可复用建议

- 先做结构化 KV，再考虑向量检索。偏好类记忆天然是键值型的，一上来就上 RAG 属于过度设计。
- 写入门槛 > 检索技巧。垃圾进垃圾出，检索再花哨也救不回来。
- 每条记忆必须带 `source` 和 `updated_at`，这是调试的地基。
- 定期把 memory store 导出成文件人工过一遍，十几分钟，比任何自动清理都可靠。
- `memory_forget` 和 `memory_save` 同等重要，给用户一条明确的遗忘路径。

## 总结

让 agent"记住你"，核心不是让模型更聪明，而是把记忆当成一个需要治理的状态存储：分层、结构化、严进宽出、可回溯。OpenClaw + MCP 把 tool 的门槛降得很低，剩下的活儿其实是老派的工程设计——约束写入、控制注入、保留版本。这套东西没有任何黑魔法，但做过之后，agent 从"每次都要重新教"变成"偶尔纠正一下"，体感差距非常明显。
