# 背景

跑过生产级 Agent 流程的人都有体会：任务链越长，依赖的外部 API 越多——LLM 供应商、MCP 工具、第三方 SaaS、自建服务。任何一环抖动，整条链路就断。错误恢复不是锦上添花，而是 demo 和生产之间的分水岭。

## 问题：API 挂了之后，Agent 会发生什么

没有兜底设计时，通常是三种坏结局：

1. **无限重试**。LLM 收到报错后的第一反应是"再试一次"，没人拦它就能烧掉整个 token 预算。
2. **静默失败**。工具返回空结果或异常被吞掉，模型基于空数据一本正经地编造结论。
3. **级联崩溃**。一个非关键依赖（比如可选的摘要服务）挂掉，整条 pipeline 停摆。

根源在于：模型不会天然"放弃"或"换路"，除非你把恢复策略写成它可执行的规则。

## 做法：四道防线

**第一道：先分类，再重试。** 可重试的是 429、502/503/504、超时、网络抖动；不可重试的是 400、401、403、配额耗尽。服务端给了 `Retry-After` 就照办，别自作主张压短。

**第二道：指数退避 + 抖动，设硬上限。** 比如 1s/2s/4s，每次加 0–30% 随机抖动，最多 3 次。重试是给瞬时故障准备的，不是给"这服务已经死了"准备的。

**第三道：熔断与降级。** 同一依赖连续 N 次失败就短路，进入冷却期；期间走备用 provider、读缓存、或直接跳过可选步骤。设计流程时就要想清楚：哪些步骤是必须的，哪些挂了可以绕。

**第四道：把失败结构化地交回给模型。** 别返回裸报错字符串，返回类似：

```json
{"status":"failed","error_type":"rate_limit","retryable":true,"retry_budget_left":1,"hint":"30秒后重试或切换备用源"}
```

同时给模型明确的重试预算（"最多再试 2 次，然后汇报失败"），而不是一句"失败了就再试试"。

两个容易被忽略的工程细节：**幂等键**——重试写操作前想清楚会不会重复下单、重复发消息；**检查点**——长任务把状态落盘，恢复后续跑，而不是从头再来一遍。

## 踩坑点

- 对所有错误一把梭重试：401 重试一万次也不会好，只会浪费时间。
- 退避不加抖动：多个 Agent 实例同时重试，形成惊群，把刚缓过来的服务再次打挂。
- 让 LLM 自由发挥错误处理：这是最贵的 prompt 写法。
- 吞异常返回空字符串：模型会基于空数据继续编。
- 没设超时：一个挂起的 HTTP 请求就能阻塞整个事件循环，后面的任务全排队。

## 可复用建议

- 所有外部调用收敛到一个统一 client：重试、超时、日志在一处管理，别散落在各插件里。
- 错误分类表做成常量，业务代码里不写 magic number。
- 工具输出 schema 里天然包含 `failed` 状态——失败是合法结果，不是异常流。
- 关键流程入口加 preflight 健康检查，带病跑不如早失败。
- 每次重试带 trace ID 记录，事后能还原完整的故障时间线。

## 总结

错误恢复的本质不是"让 Agent 更聪明"，而是把工程纪律前置：分类决定能不能重试，限次决定重试多久，降级决定挂了怎么办，可观测决定事后能不能复盘。模型负责选路，代码负责兜底——这六个字大概就是这个主题的全部。
