## 背景

单 agent 串行干活有三个老问题：长任务把主会话堵死、中间过程把上下文塞满、一个环节慢全链路慢。subagent 的思路很直接：主 agent 只做拆解、派发、验收，具体执行交给多个拥有独立上下文的子代理，能并行的就并行。OpenClaw 里这套能力已经内置，但用得好和用得乱，差别很大。

## 问题

举个真实场景：给一个中型仓库补齐模块级文档，二十多个模块，逐个读代码、写摘要。单 agent 串行跑了一个多小时，而且读到后面早就忘了前面的整体结构，主上下文里全是代码碎片，后半部分产出质量明显下降。这就是典型的「该并行而不并行」。

## 做法

1. **一个子代理一件事**。每个子代理只负责一个模块，产出固定：一份 300 字以内的摘要 + 一个文档文件落盘。
2. **隔离上下文与权限**。只给子代理需要的工具（read / write / grep），限定工作目录，禁止再 spawn 子代理——深度硬限制为 1。
3. **控制并发度**。实测 3~4 是甜点区，更高并没有更快，瓶颈在模型侧限流和工具执行，不在编排层。
4. **规定返回格式**。只允许返回「完成/失败 + 文件路径 + 一句话要点」，禁止把全文贴回来。这是保护主 agent 上下文的关键一条。
5. **主 agent 聚合验收**。全部结束后统一过一遍产物，格式不对的挑出来单独重跑，而不是整批重来。

效果：同样的事并行后 15 分钟左右跑完，主会话上下文占用很小，中途还能继续交互。

## 踩坑点

- **任务描述不清，子代理自由发挥**。解法：派发指令里写死「输入是什么、产出是什么、写到哪、不要做什么」。
- **多个子代理写同一个文件，互相覆盖**。解法：一人一个目录，或文件名带模块前缀，最后由主 agent 合并。
- **子代理返回太长，聚合阶段主上下文爆炸**。解法：返回强制「摘要 + 路径」，细节让主 agent 按需去读文件。
- **递归 spawn 失控，成本翻倍**。解法：深度上限写死，子代理的工具清单里根本不给 spawn。
- **权限没收紧**。有个子代理顺手执行了清理命令，删掉了别的子代理的产物。之后默认所有子代理只读，写权限单独开。
- **并行不省钱**。token 总量比串行高 20%~50%，换来的是时间。值不值，看任务能否真正独立。

## 可复用建议

- 只把「可独立验收」的任务丢给子代理：边界清晰、有明确产物、失败可单独重试。
- 主 agent 当包工头，不当搬运工：拆解、派发、验收、重派，不碰执行细节。
- 返回值永远压缩，产物永远落盘。
- 先小规模验证（2 并发跑 2 个模块），确认产物质量再放量。
- 留好降级路径：并行失败退回串行，别让编排层成为单点。

## 总结

subagent 编排本质是一次工程约束练习：拆分粒度、上下文隔离、权限收紧、返回压缩，这四件事做对，多 agent 并行就是稳定的提速手段；做不对，它只是把串行的问题变成更难排查的并发问题。建议从一个真实的小任务起步，把这四条约束固化成自己的派发模板，再逐步放开规模。
