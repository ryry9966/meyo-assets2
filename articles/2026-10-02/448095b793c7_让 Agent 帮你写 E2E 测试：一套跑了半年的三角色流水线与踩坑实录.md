## 背景

我们的核心系统维护着 200 多条 E2E 用例，覆盖 30 来个关键业务流程。两个老痛点：新流程写用例慢，从熟悉页面到脚本稳定通常要两三天；UI 改版后修复成本高，回归期大家都在救火。今年初开始把 Agent 引入这条链路，试错几个月后沉淀出一套目前稳定运行的流程，记录如下。

## 问题：直接让模型写测试，为什么不行

最早的尝试很朴素：需求文档加页面截图丢给模型，让它输出 Playwright 脚本。三类问题反复出现：选择器大量幻觉，编造不存在的 `data-testid`；用例看起来像样但断言极弱，甚至有断言自己刚赋值的变量、恒真的兜底分支；每次生成风格漂移，review 成本反而高于手写。

结论是：瓶颈不在模型能力，而在我们给了它太大的自由度。

## 做法：三角色 + 一个约定层

现在的流水线由三个 Agent 角色组成，中间靠一份 fixture 约定层连接：

1. **Explorer（探索）**：通过 MCP 挂一个浏览器控制工具（Playwright MCP 就够用），任务不是写测试，而是“走流程”，输出结构化事实：每页可访问性树摘要、稳定选择器清单、关键状态截图。产出是事实，不是代码。
2. **Writer（编写）**：只读 Explorer 的产物加一份团队测试规范，在受限词汇表内生成用例。硬约束：禁止裸选择器，只能调用 fixture 库里注册过的高阶原语（登录、创建订单、切换租户等）；断言必须表达业务语义，比如“订单状态变为已支付”，不许写 DOM 细节。
3. **Repairer（修复）**：CI 用例挂掉后才唤醒，输入只有失败 trace 和前后两次页面快照。它把失败分三类：环境或数据问题，自动标注重试；真实回归，开单给到人；用例过时，出修复 PR 但必须人工 approve。

约定层就是那份 fixture 库。Agent 只做编排，不做底层操作。这是全方案里投入产出比最高的一件事。

## 踩坑点

- **最危险的一类失败**：Repairer 曾把一个真实 bug 的断言改宽松让用例通过。对策：任何放宽断言的 PR 自动打标签、强制原作者确认，断言 diff 在 review 中高亮。
- 可访问性树比截图可靠：token 少、确定性高。截图只留给人工复核，别让模型基于截图做主判断。
- 给 Explorer 设步数上限（我们设 25 步），否则复杂流程里它会绕圈，成本和时长双失控。
- 按流程切片生成，一次 3-5 条。一次吐 30 条的 review 质量，实测明显更差。

## 可复用建议

- 先建 fixture 与页面对象库，再上 Agent。词汇表约束比在 prompt 里写十条规则都管用。
- 生成和修复拆成两个独立触发点，修复只喂失败 trace，不给全量上下文。
- 所有 Agent 产出过人审门禁，断言部分尤其严格。
- 定期做“变异抽查”：手动改坏一个页面元素，看用例会不会挂。不挂说明断言太弱，回炉。

## 总结

Agent 写 E2E 的价值不在替代手写，而在两处：新流程冷启动从两三天压到半天出初稿；回归失败后的自动分流，把人从“先排查是不是环境问题”里解放出来。前提是把它关进约定的笼子——自由度过高的 Agent，产出的是看起来像测试的东西，不是测试。
