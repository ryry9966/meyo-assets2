# 背景

写自动化的人迟早会撞上一个事实：**你的任务一定会被执行两次。** Agent 调工具超时后重试、消息队列按 at-least-once 投递、cron 上一轮没跑完下一轮又触发、还有人工说"补跑一遍吧"。工程上 exactly-once 基本是幻觉，能依赖的只有 at-least-once。幂等性，就是把"重复投递"变成"无害重复"的那层设计。

# 问题

不幂等的任务在重试时的典型表现：

- Agent 工具调用超时（其实服务端已经成功），重试后建了两张一样的工单、发了两条通知；
- webhook 被重放，同一事件处理两次，数据重复入库；
- 补跑脚本把 append 型日志文件内容翻倍，或往数据库里整批插重复行。

问题不在"重试"本身，而在于重复执行改变了系统的最终状态。

# 做法

按副作用从弱到强逐层处理：

1. **先分类。** 纯读操作天然幂等，不用管。需要设计的是所有写操作和外部副作用。
2. **给任务一个幂等键。** 用业务上稳定的标识：客户端生成的 UUID、事件自带的 event_id、或自然键（日期+账号+动作）。不要用时间戳或自增序号——那等于没有键。
3. **写入用 upsert。** `INSERT ... ON CONFLICT DO UPDATE`、PUT 覆盖语义，数据库唯一索引兜底。重复执行落到同一行，天然收敛。
4. **状态变更加条件。** `UPDATE ... WHERE status = 'pending'`，配合状态机，第二次执行影响 0 行，无事发生。
5. **外部副作用先记账。** 发消息、调第三方这类退不回来的动作，先在本地落一条"待执行/已执行"记录（outbox 思路），执行成功再更新状态；重启或重试时先查账再动手。第三方若支持幂等键，直接透传。
6. **MCP / 插件工具层面**，把幂等键做成工具参数，并在工具描述里写明幂等语义，让 Agent 知道"重复调用是安全的"。

# 踩坑点

- **check-then-act 的竞态。** 应用层"先查有没有，没有再插"，在并发或双实例部署下必然穿帮。唯一约束才是最后防线，别只靠 if 判断。
- **超时 ≠ 失败。** 最容易出事故的假设。超时只说明"不知道结果"，所以每次可能已成功的调用都必须可以安全重发。
- **伪读操作。** "读取并标记已处理"、已读回执这类，看着是读，实际有副作用，不在幂等白名单里。
- **定时任务重叠。** 上一次没跑完下一次又起，用文件锁/分布式锁，或加"执行中"状态挡住。
- **外部 API 不支持幂等。** 只能靠本地记账加状态流转兜住，别指望对面替你兜底。

# 可复用建议

- 一句话判断标准：**这个操作连跑两遍，最终状态和跑一遍完全一样吗？** 答案是否，就补设计。
- 写脚本默认"可重跑"：要么开头做清理，要么全程 upsert，不依赖"只跑一次"的假设。
- 上线前做个土测试：同一任务手动连触发两次，核对结果是否一致。
- 幂等键格式、去重窗口这些约定写进工具描述和任务文档，别只存在某个人的脑子里。

# 总结

幂等性不是锦上添花的优化，而是自动化的入场券。重试、重放、补跑是常态，把每个写操作设计成"做两次和做一次结果一样"，你的 Agent、定时任务和插件才敢在没人盯着的深夜里安心跑。
