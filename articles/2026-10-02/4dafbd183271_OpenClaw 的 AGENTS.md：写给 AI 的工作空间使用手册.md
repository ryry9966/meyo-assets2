## 背景

OpenClaw 的工作空间里有一个容易被低估的文件：AGENTS.md。它的定位和 README 相反——README 写给人，AGENTS.md 写给 AI。Agent 在任务启动或进入某个目录时，会读取对应层级的 AGENTS.md，把其中的约定作为上下文注入会话。本质上是把"这个项目该怎么配合干活"的隐性知识，固化成一份 AI 每次都能看到的说明。

## 没有它时的问题

实践中最常见的三类浪费：

1. **重复交代**。每个新会话都要重新粘贴项目背景、测试命令、注意事项，prompt 又长又容易漏。
2. **自作主张**。项目用 pnpm，agent 用 npm 装依赖；`src/generated/` 下的生成代码被手改；同类任务两次执行的路径不一致。
3. **知识不沉淀**。上次排障得出的结论只留在聊天记录里，换个人、换台机器就丢了。

共同点是：约定存在于对话和人脑里，而不是工作空间里。

## 做法

1. 在仓库根目录建 `AGENTS.md`。Agent 按目录就近读取：在子目录执行任务时，子目录的 AGENTS.md 可以补充甚至覆盖根目录的规则。
2. 内容建议四块，宁少而准：
   - **项目概览**：一句话说清是什么、技术栈、入口在哪。
   - **构建与验证**：给可直接复制的完整命令，比如 `pnpm test --filter core`，不要写"运行测试"这种模糊描述。
   - **边界**：哪些目录不要动、哪些命令禁止执行、密钥如何处理。
   - **工具偏好**：优先走哪个 MCP 工具、浏览器操作的前置条件等。
3. 控制在一百行以内，条目化，命令一律放代码块。
4. 当活文档维护：agent 犯了错，就把纠正写成一条规则提交进去，随 PR 走版本控制，团队共享同一份。

## 踩坑点

- **写太长**。几十条规则互相稀释，关键约束反而被淹没。删到每条都不可再删为止。
- **命令过时**。重构后忘了更新，agent 反复失败。建议把"AGENTS.md 是否需要更新"列入 PR 检查项。
- **规则冲突**。根目录和子目录说法不一致时，实际生效的是哪条要自己验证，别猜。
- **写入敏感信息**。这份文件会进模型上下文，密钥、内网地址一律不要放。
- **当成强约束**。AGENTS.md 是强提示，不是沙箱。真正的硬限制要靠权限配置和工具白名单兜底。

## 可复用建议

- 团队维护一个模板，新项目复制后只改项目相关部分。
- 一条规则只说一件事，多用"必须/禁止"，少用"尽量"。
- 每次排障后自问：这个坑能不能变成一条规则？能就写进去。

## 总结

AGENTS.md 是典型的低成本高杠杆实践：半小时的投入，换来每个会话稳定一致的行为。它的价值不在初稿，而在持续修订——每一次"AI 做错然后被纠正"，都应该有机会变成文件里的一行字。写好这份给 AI 的手册，人就可以少当复读机。
