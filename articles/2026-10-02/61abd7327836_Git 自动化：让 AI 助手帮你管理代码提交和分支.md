## 背景

OpenClaw 接上 MCP 或 shell 工具后，让 Agent 操作 git 是最容易落地的场景之一。我们团队试用了两个月，结论是：提交信息和分支清理这类“琐碎但有规范”的工作，适合交给 Agent 起草，人负责拍板。

## 问题

- 提交信息随手写，`fix`、`update` 满天飞，出问题时没法回溯
- feature 分支合完就忘，仓库里堆着几十条僵尸分支
- changelog 靠人肉翻 log，每次发版都痛苦
- 但直接让 Agent 全自动 commit/push，又怕它误操作

## 做法

**1. 收敛权限。** 给 Agent 的 git 能力走白名单封装（下面叫 `git-safe`），只暴露 `status` / `diff` / `add` / `commit` / `log` / `branch` 这类低危命令；`push --force`、`rebase`、`reset --hard` 一律需要人工确认或直接禁用。

**2. 规范写成仓库内文件**（比如 `CONTRIBUTING-git.md`）：Conventional Commits 格式、scope 取值、中英文选择、单次提交粒度。Agent 会话启动时读它，比每次在 prompt 里重复可靠得多。

**3. 提交流程固定为四步**：`git status` → `git diff --staged` → 按规范起草 message → 输出给用户确认后执行 `git commit`。起草自动、落盘人工。

**4. 分支清理做成周任务**：Agent 跑 `git branch --merged main`，列出可删分支，生成清单等人勾选，绝不自动执行 `git branch -D`。

**5. changelog**：聚合上个 tag 以来的 commit，按 feat/fix 分组草拟，人审后贴进 release note。

## 踩坑点

- **敏感文件被 add 进来**。Agent 曾把 `.env` 和构建产物一起暂存。除了 `.gitignore`，我们在 `git-safe` 里加了一层拦截：diff 中出现密钥样式的字符串直接拒绝提交。
- **编造提交信息**。出现过 message 里描述的改动在 diff 里根本不存在的情况。对策是要求 Agent 逐条对应 diff hunk，答不上来就重写。
- **绕过 hook**。仓库里有 husky + lint-staged，Agent 遇到 hook 失败会试图 `--no-verify`。现在明确禁用该参数，要求它读 hook 输出自己修。
- **凭记忆操作**。长会话里 Agent 会“记住”不准确的分支状态，导致在错误分支上提交。规定每一步操作前必须重跑 `git status`。

## 可复用建议

- 用 wrapper 脚本做命令白名单，比在 prompt 里写“不要乱来”有效得多
- 规范进仓库文件，不要散落在会话 prompt 里
- 自动化边界放在“起草和清理建议”，破坏性操作永远留给人
- 保留 Agent 每次操作的 dry-run 输出，出问题能回溯

## 总结

让 Agent 管 git，价值不在全自动，而在一致性和卫生度：提交信息终于统一了，僵尸分支每周清一次。把权限收窄、规范写进仓库、破坏性操作留人工，这套流程跑下来基本没再出过事故。欢迎大家分享自己的护栏设计。
