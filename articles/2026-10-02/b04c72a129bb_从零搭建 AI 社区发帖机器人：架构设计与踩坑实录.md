# 背景

社区运营里有一类活儿很机械：整理每周精选、把仓库 release 和讨论区动态搬运成帖子。人工做两周就会想自动化。这篇记录我用 OpenClaw 搭一个发帖机器人的完整过程。目标从一开始就很明确：不是让 AI 自由发挥，而是让它在一个受限管道里稳定产出**可审核**的内容。

# 问题定义

动手前先把需求拆清楚，避免一上来就调模型：

- 定时从数据源（release、讨论区、往期热帖）取素材
- Agent 生成草稿，格式符合社区规范
- 发布前必须过 dry-run 或人工审核
- 失败可重试但不重复，全程可审计

真正的难点不是生成文本，而是**幂等、频控、审计**——这三件事模型帮不了你。

# 架构：三层拆分，Agent 保持"薄"

1. **调度层**：cron 触发 + 任务队列，负责"什么时候做"
2. **Agent 层**：OpenClaw agent + MCP 工具（`fetch_topics` / `draft_post` / `submit_for_review`），负责"做什么内容"
3. **执行层**：发帖插件，负责"能不能做"——校验、限速、幂等、审计日志

关键决策：Agent 只产出结构化草稿对象（标题、正文、标签、板块），不直接触碰发帖 API，所有副作用收口到执行层。MCP 工具的 schema 也要收紧，比如板块和标签用枚举，不给模型发挥空间：

```json
{
  "name": "submit_for_review",
  "input": {
    "category": { "enum": ["weekly", "release", "discussion"] },
    "tags": { "maxItems": 3 },
    "idempotency_key": "string"
  }
}
```

# 踩坑实录

**1. 幻觉板块。** 模型第一次运行就发明了不存在的"教程分享"板块。解决：枚举校验，非法值直接打回让 Agent 重试，而不是静默映射到默认板块——静默映射会让你永远不知道模型错在哪。

**2. 重试导致重复发帖。** 队列超时重试后，同一内容发了两遍。解决：幂等键由调度层在任务创建时生成，执行层按键去重。不要让 Agent 自己编 ID，它编的东西不可靠。

**3. 首跑即上线。** 最早没做 dry-run，测试环境连了生产 token，机器人直接把测试帖发了出去，删帖删到半夜。解决：执行层强制三级开关——`dry_run / 审核队列 / 直发`，默认 dry_run。

**4. 上下文膨胀。** 把最近 50 条帖子全塞进 prompt，token 成本翻倍且重点涣散。解决：改成检索式，工具只返回按相似度和时间筛过的 5 条摘要。

**5. 时区。** cron 按 UTC 跑，社区活动按北京时间排期，首帖早发了 8 小时。解决：调度层显式声明时区，任务携带计划时间字段，Agent 不参与任何时间计算。

# 可复用建议

- 能力放工具里，判断放 Agent 里，防护放执行层，三层职责不混
- 所有副作用工具必须幂等，幂等键由上层生成
- dry-run 是默认态，不是可选项
- 每次调用记录 tool call 的入参出参，出问题时这是唯一能还原现场的东西
- 先跑审核队列攒信任，再逐步放开发布权限；灰度永远比回滚便宜

# 总结

上线后机器人每周稳定产出周报类帖子，人工只做最后一步审核。复盘工作量：和模型相关的部分大概只占两成，剩下八成全在工程防护上。如果你也想做类似的事，建议从"只能 dry-run 的最小闭环"起步，先跑通审计日志，再谈自动化程度。欢迎在社区帖下交流你们的排障经验。
