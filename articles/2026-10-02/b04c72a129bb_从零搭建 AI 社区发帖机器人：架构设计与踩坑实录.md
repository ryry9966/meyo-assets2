## 背景

社区每周需要一篇「本周精选」：汇总 GitHub 上相关项目的动态、群里讨论过的高频问题、值得复读的技术帖。之前纯手写，两个月断更三次。这篇文章记录我把它改造成自动化发帖机器人的完整过程——技术选型、架构分层，以及真实踩过的坑。

技术栈：OpenClaw Agent 负责生成与调度，MCP 工具做数据采集，SQLite 做状态存储，论坛（Discourse）API 做发布。单机部署，核心代码 600 行左右。

## 问题定义

先想清楚「不做什么」，比做什么更重要：

- 不做模型自由发挥的内容，只做**结构化聚合 + 摘要**
- 不做实时发帖，每周一次固定任务
- 发布必须有记录、可追溯

问题拆成五层：触发 → 采集 → 生成 → 审核 → 发布，外加一个贯穿始终的状态层。

## 架构与实现步骤

**1. 触发层。** 用 OpenClaw 的定时任务能力触发（换成任意调度插件同理）。一个关键细节：cron 表达式旁必须显式声明时区，写进配置文件，而不是靠「大家都懂」。

**2. 采集层。** 三个 MCP 工具：RSS 拉取、GitHub Releases 查询、论坛 API 拉取本周热帖。每个工具独立重试，超时降级——某个来源挂了就跳过，终稿里标注「本期缺某来源」，不让单点故障拖垮整个任务。

**3. 生成层。** Agent 拿到的不是原始数据，而是采集层清洗后的结构化条目：标题、链接、一句话摘要、热度指标。Prompt 只负责排版和润色，温度调低，模板固定。

**4. 审核层。** 发布前跑一遍规则检查：URL 是否来自采集层白名单、与历史帖做相似度去重、长度和标签校验。全部通过才进入发布队列。

**5. 发布层。** API 客户端带幂等键（周数 + 内容 hash），遇 429 指数退避，成功后写状态表：

```yaml
schedule: "0 9 * * 1"
timezone: Asia/Shanghai
idempotency_key: "{week}-{content_hash}"
dry_run: true   # 前两周只落盘不发布
```

## 踩坑实录

**坑一：模型编造链接。** 第一版让模型「自由汇总」，它给一个不存在的 repo 编写了 release note。修复原则：模型永远不接触「生成 URL」这个动作，所有链接来自采集层数据，模型只能引用、排序、摘要。

**坑二：cron 重复触发。** 某次部署重启，调度器把错过的任务立刻补跑，同一天发了两帖。修复：发布前查状态表 + 幂等键，命中即跳过。这类问题不能靠「小心部署」解决，只能靠状态设计兜底。

**坑三：时区。** 容器里是 UTC，「每周一 09:00」实际是北京时间 17:00。所有时间语义显式声明时区，一次配置，处处生效。

**坑四：长任务 token 爆炸。** 源数据一多，一次性塞给模型直接超限。改用 map-reduce：每个来源先单独摘要到 100 字内，再合并生成终稿。顺带的好处是天然隔离了单来源故障。

**坑五：静默失败。** 最坑的一次：MCP 工具持续超时，任务连挂两周没人发现。修复：任务结束必发心跳（成功和失败都发），失败附错误摘要；再加一层「超过 N 天无产出即告警」的兜底。

## 可复用建议

- **状态外置**：发没发过、处理到哪，全部落库，不依赖任何会话记忆
- **模型只做转换，不做事实**：URL、数字、日期全部来自代码层
- **中间产物落盘**：采集结果、草稿都存 JSON，任何一步可独立重放和调试
- **dry-run 先行**：自动发帖至少人工复核两周再放开
- **权限最小化**：API key 只给发帖权限，不给删帖和管理权限

## 总结

机器人上线三个月，发帖 13 篇，人工介入 2 次（都是链接格式问题）。一个直观的体会：发帖本身是整条链路里最简单的一环，真正的工作量在状态管理、去重和失败兜底。如果你也想做类似自动化，建议从「每周一次、单一来源、dry-run」起步，先让链路跑稳，再逐步加来源、加自动化程度。

代码整理后会开到社区仓库，MCP 工具的降级设计值得单独开一篇细讲。
