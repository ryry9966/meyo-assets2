## 背景

LLM 本身无状态。OpenClaw 这类常驻 Agent 网关的价值恰恰在“长期相处”：装了几个插件、接了几组 MCP 工具之后，用户自然期待它记得“我用 Python”“部署走 docker compose”“报告别用 emoji”。但这些偏好每次会话结束就蒸发，体验立刻降级成一个冷启动的客服机器人。

## 问题：三种常见做法为什么不行

- **全塞 system prompt**：上下文膨胀，指令被稀释，成本随记忆条数线性涨。
- **每轮全文摘要**：细节丢失，越摘要越模糊，还会随时间“漂移”。
- **什么都进向量库**：召回噪声大，八竿子打不着的记忆也被检索出来干扰回答。

本质：记忆是数据工程问题，不是 prompt 技巧。

## 我现在的做法

1. **分层存储。** 偏好（结构化 KV：语言、工具链、语气）、事件（episodic，带时间戳）、流程（操作习惯）分开存，三者生命周期完全不同。
2. **抽取独立一跑。** 会话结束后用便宜模型跑专门的 extractor prompt，只写“30 天后仍然成立”的事实，输出强制走 schema 校验。用户显式说“记住 xx”则直写、高置信度。读写都收口成两个 MCP 工具（`memory.read` / `memory.write`），主 Agent 不直接碰库。
3. **先结构化，再谈向量。** 一张 SQLite 表就够：`key / value / confidence / updated_at / source / user_id`。偏好用 KV 精确匹配；只有事件类才建向量索引按需检索。
4. **注入小而准。** 每次会话拼一个 <1.5k token 的 memory block：高置信偏好优先，按 `updated_at` 排序。别把整库塞进去。
5. **冲突与遗忘。** 新旧冲突时不盲目 append——比对相似度，覆盖旧值并留版本号；长期未被召回的记忆自动降置信度；提供 `/memory list` 和 `/memory forget`，让用户能看、能删。

## 踩坑点

- **过度抽取**：把“今天下雨了”也存进来，两周后库就废了。抽取规则要苛刻。
- **覆盖错方向**：“用 vim”改成“用 VSCode”后，agent 偶尔还拿旧值。`updated_at` 必须参与排序，并允许用户一句话纠正。
- **跨用户串记忆**：namespace 一定挂在 `user_id` 上，不是 session，多渠道接入时尤其容易翻车。
- **记忆块过大**：超过 2k token 后指令遵循明显变差，看起来记了，实际等于没记。
- **回音室**：agent 记错一条还反复自我强化。所以“可查看、可清空”不是锦上添花，是刚需。

## 可复用建议

- 写路径比读路径重要，把一半精力花在抽取与校验上。
- 注入前做去重，相似度阈值 0.9 左右起步，再按实际误判调。
- 记忆必须人类可读、可编辑——JSON/YAML 落盘，别只存向量。
- 定期抽样回放历史对话，统计“该想起没想起”和“不该想起乱想起”两个指标，比看 demo 直观得多。

## 总结

好的记忆系统 = 结构化存储 + 克制的抽取 + 版本化更新 + 用户可控。先做出一张能跑的偏好表，再考虑向量索引和遗忘曲线。目标不是“什么都能记”，而是“记住的都对”。
