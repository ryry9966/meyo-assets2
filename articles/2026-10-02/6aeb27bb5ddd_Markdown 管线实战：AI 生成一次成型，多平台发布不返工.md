## 背景

用 Agent 生成内容已经很成熟，瓶颈反而落在“发出去”这一步。同一份 Markdown，公众号编辑器需要内联样式、知乎吃标准 GFM、GitHub 支持脚注，还有一些平台会直接吞掉 HTML。人肉复制粘贴调一次可以，放进自动化流程里，这一步会立刻碎掉。

我们的做法是：把格式适配做成一条独立的 Markdown 管线，在 OpenClaw 里封装成一个 MCP 工具（比如 `publish.markdown`），Agent 侧只传文件路径和目标平台列表，剩下的交给管线。

## 问题

- AI 输出的 Markdown 是“自由格式”：表格、脚注、嵌套列表、内联 HTML 混着来，平台渲染差异在自动化场景被无限放大。
- 图片外链被防盗链拦截，发布后变裂图；代码块的语言标记被剥掉；YAML frontmatter 原样发出去。
- 用正则做后处理，规则越堆越多，改一处崩三处。

## 做法

1. **锁定规范源。** Agent 产出一版 `canonical.md`，在生成端用 prompt 约束可用语法子集：禁用脚注、只用两级标题、图片必须是绝对地址。这是唯一事实源，语法子集越窄越好。
2. **AST 层转换，不碰字符串。** 用 unified/remark 读成 mdast，按目标平台写 transform 插件：`wechat-target` 把标题降级、把样式全部内联；`html-target` 给代码块包内联高亮。所有规则是纯函数，输入 mdast 输出 mdast，可单测。
3. **校验前置。** 每个平台配一个 lint 规则集，发布前检查“该平台不支持的节点”，直接报错而不是静默降级。
4. **图片中转独立成步。** 发布前统一做一次图床迁移（下载→上传目标可用图床→替换 URL），做成独立工具，必须原子完成。
5. **dry-run 快照。** 每次发布先渲染快照并 diff，快照文件进版本库，平台改版跑一遍回归就知道哪里崩了。

## 踩坑点

- **别用正则改 Markdown。** 嵌套代码块里的 ``` 会让你怀疑人生，AST 是底线。
- **别指望平台保留结构。** 公众号会把 h1 降级、丢 class，所有样式必须在转换端内联完成。
- **相对链接和多级列表缩进是重灾区。** 某些平台把 tab 和四空格渲染成不同层级，规范源里直接禁掉相对链接。
- **frontmatter 忘了剥**，正文开头多一块 `---`，看起来像事故现场。
- **抓图时机不一致**：先发文本后传图会出现占位失败，图床迁移必须前置。

## 可复用建议

- 规则集按“平台名 + 版本号”维护，平台改版 = 升版本 + 跑快照回归。
- 每个 adapter 签名一致：`transform(ast, options) -> ast`，新平台就是加一个文件。
- 快照测试别只比对 HTML，同时断言关键节点数量（图数、表数、代码块数），能抓住大多数静默丢失。
- 生成端约束永远比转换端兜底便宜，能靠 prompt 收窄的不要留给 adapter。

## 总结

多平台发布没有银弹，本质是“一个规范源 + N 个纯函数 adapter + 校验前置”。Agent 负责产出符合 schema 的 canonical 文档，管线负责可验证、可回归的转换。平台改版时，你改的是一个文件和一版快照，而不是整条流水线。
