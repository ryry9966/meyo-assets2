## 背景

用 OpenClaw 或任何常驻 Agent 的人都会遇到同一个尴尬：每次新会话，Agent 都是“失忆”的。你得重新解释自己用什么系统、哪个包管理器、喜欢什么回复风格。系统提示词能解决一部分，但它说的是“Agent 该怎么做事”，而“我是谁、我的环境长什么样”这类个人信息，更适合一个独立、可维护的文件——USER.md。

它和 AGENTS.md、SOUL.md 是同一套思路：把约定落在文件里，而不是散落在聊天记录和口头交代中。分工也很清晰——SOUL.md 定义助手人格，AGENTS.md 描述协作规范，USER.md 描述用户本人。

## 问题

没有 USER.md 时的典型症状：

- 每个会话开头都要自我介绍，或把偏好塞进全局 system prompt，改一次要动配置重启；
- 建议与你的环境不匹配：你用 pnpm 它给 npm，你主用 zsh 它默认 bash；
- 回复风格不稳定：有时啰嗦、有时滥用 emoji、有时铺垫半天不给结论；
- 红线靠“上次骂过它一次”维持，换个会话就忘。

## 做法

**1. 放对位置。** OpenClaw 会自动读取工作区下的 USER.md 并注入会话上下文，与其他记忆文件同级。如果你的框架没有这个约定，做法也简单：session 启动时读文件拼进 system prompt，或者用 MCP 把它暴露成 resource，任何客户端都能取。

**2. 只写事实，写短。** 30–60 行封顶，推荐分区：

```markdown
# USER
## 环境
- macOS 15 / zsh / VS Code
- 时区 Asia/Shanghai，回复用中文
## 技术栈
- Node + pnpm（不要给 npm/yarn 方案）
- Python 3.12 + uv
## 沟通风格
- 先结论后细节，不写寒暄
- 代码直接给可运行版本
## 边界
- 不主动 git push
- 改文件前先出 diff
- 涉及生产环境一律停下确认
## 当前重点（定期更新）
- xxx 项目，截止 7 月
```

**3. 建立维护机制。** 让 Agent 把“可能值得记住的事”先写进候选区或单独的 daily note，你每周确认后再合入正文。不要让它直接改 USER.md——这是防漂移的关键。每条信息带日期，方便清理过期内容。

## 踩坑点

- **写成小作文。** 上千字的自我描述会稀释上下文，Agent“知道”但抓不住重点。事实、偏好、红线各占一块即可。
- **放进敏感信息。** USER.md 会被读文件的子 Agent 和 MCP 工具看到，也可能被原样回显。密钥、地址、手机号一律放环境变量或密钥管理器。
- **信息过时。** 三个月前的项目描述会让 Agent 朝错误方向发力。过期内容果断删，不留“以防万一”。
- **与项目配置打架。** USER.md 说 pnpm，某个 repo 却明确要求 npm。优先级要写明：项目级配置 > 个人偏好。
- **职责混装。** 别把 commit 规范、代码风格塞进来，那属于 AGENTS.md。文件一混，维护成本立刻上升。

## 可复用建议

- 放进 dotfiles 仓库做版本管理（先脱敏），换机器零成本迁移；
- 身份复杂（主业 + 副业）的用户，用分区而不是拆成多个文件，加载逻辑保持简单；
- 团队场景每人一份 USER.md，多 Agent 协作时按人引用，比把所有人的偏好挤在一个 prompt 里干净得多；
- 每季度做一次减法：能删的删，剩下的才是 Agent 真正用得上的。

## 总结

USER.md 是典型的低成本、高杠杆做法：几十行事实，换来 Agent 不再反复跑偏、不用重复交代。它的价值不在“记住了什么”，而在把个人信息从聊天记录里收敛成一个可 review、可版本化、可审计的文件。花半小时写好它，Agent 才算真正认识你这个用户。
