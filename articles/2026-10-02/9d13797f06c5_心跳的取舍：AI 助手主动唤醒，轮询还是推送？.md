## 背景

Agent 要"主动"就绕不开唤醒机制：定时摘要、监控告警、收件箱巡检、到期提醒。在 OpenClaw 里最典型的就是 heartbeat——按固定间隔把 agent 拉起来一次，读一份 checklist（比如 `HEARTBEAT.md`），判断有没有活干。另一条路线是推送：webhook、消息队列、MCP 工具回调，事件到了直接触发。这两条路线怎么选，比想象中更工程化。

## 问题

**纯轮询的代价是空转。** 95% 的 tick 没有活干，但每次都烧一次模型调用，间隔压到 5 分钟就是成本灾难。

**纯推送的代价是基础设施。** 你得有公网可达的回调端点或常驻连接；NAT 环境、设备休眠、网络抖动都会让推送静默丢失。而且"扫一遍全量状态"这类需求（对账、巡检）天生不适合事件驱动。

## 做法

我们最终落地的是混合形态：**推送做主通道，心跳做兜底。**

1. **给触发源分类。** 时间驱动（每日摘要）→ 心跳；事件驱动（新邮件、CI 失败）→ 推送；阈值/巡检类（磁盘水位、未读汇总）→ 心跳 + 本地预检。
2. **把"什么都不做"做便宜。** 心跳先跑本地逻辑：比对 checklist 文件的 mtime、执行轻量条件判断，只有命中才唤醒模型。绝大多数 tick 应该终止在模型之前。
3. **推送侧做幂等和合并。** 事件带 dedup key，短窗口内同类事件合并成一条，断线重连后的 replay 靠时间戳去重。
4. **心跳加抖动和静默期。** 间隔 ±10% 抖动避免整点风暴，夜间降频或静默。
5. **留观测。** 每次 tick 记一行：触发时间、预检结果、是否唤醒模型。跑一周就能算出真实唤醒率。

## 踩坑点

- **心跳直接进模型是最贵的错误。** token 消耗和频率成正比，预检逻辑一定放在模型之前。
- **推送不会因为更先进就更可靠。** webhook 丢单是静默的，没有心跳兜底，你会在两周后发现提醒根本没发出去。
- **巡检类任务放推送会碎掉。** 100 个文件变更触发 100 个事件，不如心跳里一次批量扫完。
- **心跳任务和主对话抢队列。** 长任务要异步化，别让用户消息排队等心跳跑完。
- **时区。** cron 写死 UTC，用户会在 UTC+8 凌晨三点收到"早报"。

## 可复用建议

- 心跳间隔宁可粗（30 分钟起），实时性靠推送补，不要反过来。
- 每个 tick 都设计成幂等，重复执行无副作用。
- "静默丢失"是推送的默认属性，任何推送通道都要配一个低频对账心跳。
- 预检逻辑放插件或 MCP 工具里，而不是 system prompt 里，让模型只处理"确认有事"的情况。

## 总结

轮询和推送不是二选一，而是分层：**推送管延迟，心跳管可靠性。** 设计的核心不是选哪个，而是让"没事发生"的路径尽可能便宜、让"有事发生"的路径不丢不重。做到这两点，agent 的主动性才不会变成成本和噪音。
