## 背景

在 OpenClaw 这类 agent 框架里，助手不是常驻“思考”的进程，而是被唤醒才工作。唤醒来源基本就两种：定时心跳（轮询式，每隔 N 分钟醒来检查一次）和事件推送（外部发生什么，立刻把 agent 拉起来）。看起来推送更“先进”，但实际跑了几个月之后，我们的结论是：这不是二选一，而是分层。

## 问题

纯轮询有两个老毛病：间隔短，空闲时段也在烧 token 和配额，一次完整会话的心跳可能比白天真正干活还贵；间隔长，消息提醒、CI 失败这类时效敏感的事件全被拖到下个 tick。

纯推送也有硬伤：需要一个可达入口（公网 webhook 或常驻网关），每个事件源都要接入改造；agent 掉线或重启窗口期内事件直接丢失；而且它天然覆盖不了时间驱动任务——“每天早上八点发日报”这种事，推送帮不了你。

我们最初的心跳实现还犯了一个典型错误：每次 tick 都跑完整 agent 会话，带全量工具和长上下文去“看看有没有事”。一周账单出来才意识到，九成唤醒是无事空转。

## 做法

现在的结构分四步：

1. **先分类事件**。时间驱动（cron、定时提醒、记忆整理）走心跳；事件驱动（新消息、构建结果、状态变更）走推送。不要试图用一种机制糊所有场景。
2. **心跳保持便宜**。tick 只触发一段轻量检查 prompt：扫一眼待办队列和错过的 cron，有活才升级成完整会话。绝大多数 tick 在这一步就结束。
3. **推送进队列，不直连**。webhook 收到事件只做一件事：带 event ID 和 reason 写入 dispatch 队列，去重窗口内合并同类事件。agent 醒来从队列取活，掉线期间事件落盘，回来重放。
4. **节奏与退避**。心跳白天 15–30 分钟、夜间拉长到 1–2 小时，加随机抖动避免整点扎堆；唤醒失败按指数退避；每次唤醒记录 reason，月底做成本归因。

## 踩坑点

- **设备休眠**。本地部署时笔记本合盖，心跳整段消失，唤醒后要补跑错过的 cron——至少补最近一次，否则“早上八点的日报”永远不发。
- **自触发回路**。心跳让 agent 发了一条消息，这条消息又被当成事件推回来，无限循环。给自家输出加来源标记，来自 agent 自身的消息不再入队。
- **去重窗口一刀切**。CI 重试类事件 5 分钟窗口合适，消息类压 5 分钟就把真消息吞了。按事件类型分开配置。
- **心跳 prompt 悄悄变胖**。每次往检查 prompt 里塞一点上下文，三个月后它就是第二个完整会话。定期 review 这段 prompt 的 token 数。

## 可复用建议

- 从轮询起步跑通全流程，只对确认延迟敏感的事件加推送，不要一上来就全事件源接入。
- 轮询和推送收敛到同一个 dispatch 队列：它们只是不同的入队方式，下游逻辑只有一套。
- 心跳永远便宜，升级才贵。守住这条线，成本曲线就是平的。
- 唤醒 reason 日志从第一天就开始记，比事后补便宜十倍。

## 总结

Heartbeat 的本质是调度问题而非通信问题：轮询提供确定性的基础节拍，推送提供低延迟的捷径，两者在同一个队列汇合。先用最笨的方式把闭环跑通，再按事件时效性逐个引入推送。这套结构在我们场景里稳定跑了数月，改动成本也低，供参考。
