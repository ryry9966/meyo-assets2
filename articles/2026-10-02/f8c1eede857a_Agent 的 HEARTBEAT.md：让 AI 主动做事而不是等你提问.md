## 背景

大多数人用 Agent 的方式还是一问一答：打开对话、提需求、等结果。但只要你跑着一个常驻的 OpenClaw 网关，Agent 其实具备"自己醒来"的能力。`HEARTBEAT.md` 就是这套能力的入口：Agent 按固定间隔被唤醒，读取这个文件里的指令，决定这次醒来要做什么。

## 问题

纯被动 Agent 有两个天花板：一是监控类需求做不了——磁盘满了、日志报错了，你不问它就不说；二是提醒类需求做不了——"每天早上汇总未读消息"这种事，靠人记得去问就等于没做。写 cron 脚本能解决一部分，但脚本是死的，遇到"判断一下值不值得打扰我"这种模糊逻辑就无能为力。Heartbeat 的价值在于：**周期性触发 + 判断力**。

## 做法

1. 在 workspace 根目录（默认 `~/.openclaw/workspace/`）新建 `HEARTBEAT.md`，用自然语言写任务清单。
2. 在网关配置中设置心跳间隔（毫秒，默认 30 分钟），确认心跳已启用。
3. 重启网关，观察日志里是否出现周期唤醒记录。
4. 文件内容建议这样组织：

```markdown
# 心跳任务

## 巡检（每次醒来执行）
- 检查磁盘使用率，超过 85% 才汇报，否则沉默
- 检查服务日志新增 ERROR，仅汇报首次出现的

## 汇报规则
- 默认沉默，只在异常或变化时发消息
- 每天一次晨间汇总，其余时间不打扰
```

## 踩坑点

- **Token 消耗是真实的**。每次心跳都是一次完整的模型调用，哪怕无事可做。文件里塞几十条任务，账单会诚实反映。没需求时留空文件，Agent 只做最小健康检查。
- **噪音比漏报更毁体验**。写"汇报当前状态"，你会每 30 分钟收到一条废话。规则必须写清触发条件："仅在 X 时汇报"。
- **任务写太泛会漂移**。"帮我关注一下项目进展"每次执行的理解都不一样，几次后形同虚设。用可判定的条件句替代形容词。
- **别把它当任务队列**。心跳是轻量巡检，不是工作流引擎。高频或长耗时任务请走 cron + 消息触发。
- **权限边界要想清楚**。心跳期间 Agent 用的是你授予的全部权限，清理类、删除类操作务必写死安全条件，或干脆不放进心跳。

## 可复用建议

- 固定三段式结构：巡检项、事件规则、汇报规则。任务可增删，结构别动。
- **沉默是默认值**原则：所有任务默认不输出，命中明确条件才说话。这是心跳能否长期留存的生死线。
- 让 Agent 把巡检结果追加写入日志文件而不是直接发消息，你偶尔翻一眼即可，打搅感大幅下降。
- 每月清理一次：删掉不再执行的任务。心跳文件和收藏夹一样会腐烂。

## 总结

`HEARTBEAT.md` 本质上是一份写给未来自己的轮值手册：Agent 每次醒来读一遍，照着办。它不适合做重活，但非常适合做那些"重要但不紧急、又懒得每次开口"的事。核心技巧就一条：**把"什么时候说话"写得比"做什么事"更严格**。写好这个文件，Agent 才真正从应答机变成值班员。
