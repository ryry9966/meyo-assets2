## 背景

OpenClaw 的 cron 任务本质上很朴素：到点唤醒 agent，塞给它一段 instruction，然后放手。和对话场景最大的区别是冷启动——没有上下文、没有追问机会、没人坐在旁边。instruction 写成什么样，任务就跑成什么样。

## 问题

社区里多数 cron 问题，根因不在调度而在提示词。典型现象：

- 任务跑了，结果不知道去哪了；
- 输出格式每次漂移，时好时坏；
- "今天""最近"这类词导致时间错位，跨时区尤其明显；
- 没有内容的日子也准时发一条废话，打扰感很强；
- agent 重试后同一份报告发了两遍。

归纳起来，都是 instruction 没把契约写清楚。

## 做法

我的原则：把 cron instruction 当成给新同事的交接单，而不是一句话备注。一份能稳定跑的 instruction 至少包含五块：

1. **时间锚点**：第一步先取当前时间并确认时区，避免"今天"指错方向。
2. **目标与范围**：读什么、过滤什么、只处理哪个时间段，全部写死。
3. **数据来源**：MCP 工具名或工作区文件路径直接给全，不让 agent 猜。
4. **输出契约**：发到哪个会话、什么格式、没内容时怎么办（通常是记日志、不打扰）。
5. **失败策略**：报错时发一条带错误摘要的消息，重试上限写死，防止重复投递。

我实际在用的晨报模板：

```text
任务：每日晨报
1. 先执行 date 获取当前时间，按 Asia/Shanghai 确认今天日期。
2. 读取 ~/workspace/notes/inbox.md，只统计最近 24 小时新增条目。
3. 输出：
   - 有内容：按「新增 N 条 / 重点 / 风险」三段式，发到 #daily。
   - 无内容：只在工作区日志追加一行，不发消息。
4. 任一步骤报错：发一条含错误摘要的消息，最多重试 1 次。
```

上线流程也固定：先手动触发一次，验证输出落点和格式，确认无误再挂时间表。

## 踩坑点

- **相对时间**。"昨天"在 UTC+8 的凌晨和 UTC-5 的下午不是同一天，先取时间再做事。
- **输出没有落点**。agent 默默完成任务不发消息，等于没做；落点必须在 instruction 里显式指定。
- **格式漂移**。对话里你可以追问"再排个版"，cron 里没人接你的追问，输出结构必须给模板。
- **payload 塞满上下文**。长背景写进 cron 指令，改一次要重建任务；细节应该放工作区文档，instruction 里只引用路径。
- **幂等**。失败自动重试叠加网络抖动，很容易双发。重试上限和去重键（比如按日期命名输出）要提前想好。

## 可复用建议

- instruction 控制在半屏以内，细节进工作区文件；
- 每条任务必备五要素：时间锚点、范围、来源、输出契约、失败策略；
- 任何新 cron 先手动跑一次，再挂时间表；
- 输出加日期戳，既是去重键也是审计线索；
- 宁可"无内容不打扰"，也不要定时发废话——cron 的信任度是靠沉默攒出来的。

## 总结

cron 任务的 instruction 不是提示词技巧问题，而是接口设计问题：你在定义一个无人值守系统的输入契约。写完多问一句——"如果执行的人完全不了解背景，照这份单子能一次跑对吗？"答案是 否，就继续改。交接单写得越清楚，半夜被 agent 消息吵醒的次数就越少。
