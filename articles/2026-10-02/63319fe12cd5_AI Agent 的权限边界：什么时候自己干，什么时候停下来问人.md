## 背景

跑过一段时间的 Agent 都会遇到同一个问题：工具权限给多了怕出事，给少了 Agent 变成步步请示的实习生。OpenClaw 这类可接 MCP、可装插件的框架里，这个问题尤其现实——同一个 Agent 可能同时握着文件读写、HTTP 请求、shell 执行的能力，边界画在哪，直接决定它是一次提效工具还是一次事故源。

## 问题：两个方向的失败

权限边界的错误有两种，方向相反：

- **过度请示**：每一步都弹确认。人的注意力有限，第三天开始无脑点"允许"，确认框沦为仪式。这时请示机制形同虚设，比不请示更糟——它制造了"有人把关"的错觉。
- **过度放权**：Agent 自主执行了一条删库级命令，或给客户群发了措辞不当的消息。复盘会发现，问题不在模型"想不想"，而在工具层"让不让"。

## 做法：按三个维度给动作分级

不要按工具名分级，按动作属性分级。评估三个轴：**可逆性**（能否回滚）、**爆炸半径**（影响是本地还是外部）、**可验证性**（执行前能否低成本验证结果）。据此分四层：

- **L0 直接执行**：只读、本地、无副作用。读文件、搜索、列表，不打扰。
- **L1 执行后汇报**：可逆的写操作且结果可验证，如在 feature 分支提交、写本地草稿。先干，干完展示 diff。
- **L2 执行前确认**：难撤销或对外可见的动作，如合入 main、发邮件/消息、批量删除。确认内容必须带完整上下文：具体命令、改动 diff、接收方、回滚方法。
- **L3 永远确认 + 附加约束**：花钱、动生产、涉及凭证。除确认外，加硬阈值（单次金额上限、频率限制）和 dry-run 默认值。

关键工程点：**分级必须落在工具封装层，而不是系统提示词里**。提示词会被注入、会漂移；OpenClaw 的插件/MCP 接入层才是强制点——每个工具声明自己的等级，网关按等级决定放行、拦截或弹确认。L2/L3 工具尽量暴露 `dry_run` 参数，确认框里展示的就是 dry-run 的输出。

## 踩坑点

1. **确认疲劳**：请示率高于两三成，人就开始无脑批准。对策不是"加强提醒"，而是把更多动作降到 L1，靠测试和 diff 兜底。
2. **模糊确认**："我可以继续吗？"没有信息量。确认载荷应是"我将执行 `rm -rf ./build`，影响目录 X，回滚方式 Y"。
3. **复合工具藏雷**：一个叫"部署"的工具顺带清了数据库。封装保持单一职责，否则等级声明无意义。
4. **超时默认放行**：确认弹窗超时后自动执行，等于没有闸门。默认值应该是挂起并询问。
5. **没留审计日志**：哪些动作自动执行、哪些被人批准，事后查不到，分级策略就无法迭代。

## 可复用建议

- 先收紧后放宽：初期宁多问，攒一段"批准率接近 100%"的记录，再把模式稳定的动作逐条降到 L1，且可回退。
- 把等级声明做成插件/MCP 元数据，接入时自动校验；漏声明的默认按 L3 处理。
- 人的回复结构化：批准 / 拒绝 / 修改后批准，不收自由文本。
- 把"拒绝路径"也纳入测试：确认 Agent 被拒后会停，而不是换个说法重试绕过。

## 总结

权限边界不是一张固定清单，而是可逆性、爆炸半径、可验证性三者的函数。把闸门建在工具层而不是提示词里，把请示率压低、把确认信息密度提高——Agent 才能真正做到：该自己干的自己干，该问人的停下来问。
