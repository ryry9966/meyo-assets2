## 背景

做 Agent 和自动化时，把数据交给云端 API 并不总是合适的：家庭照片整理、内网文档问答、个人日程自动化，这些场景既在意隐私，也不想为高频调用付 token 费。过去一年，量化技术和推理运行时（Ollama、llama.cpp、vLLM）明显成熟，7B–32B 级别的模型在消费级硬件上已经从"能跑"变成"能干活"。这篇帖子记录我把本地模型接入 OpenClaw 工作流的完整过程。

## 问题

本地部署真正的难点不是下载模型，而是三件事：

1. **显存/内存预算**：模型尺寸、量化档位、上下文长度要一起算账；
2. **Agent 对模型的要求远高于聊天**：工具调用参数要合法、JSON 要稳定、长 system prompt 不能被截断；
3. **运行时默认配置坑多**，不调直接用，故障还往往是静默的。

## 做法

**第一步：算显存账。** 经验公式：Q4_K_M 量化权重约为参数量 × 0.6 GB（7B ≈ 4.5GB，14B ≈ 9GB，32B ≈ 20GB），再给 KV cache 留几个 GB（上下文越长吃得越多），最后留 20% 余量。粗略对应：8GB 显存跑 7B，16GB 跑 14B，24GB 跑 32B；Mac 统一内存 32GB 以上可以摸到 32B。

**第二步：选运行时。** 起步推荐 Ollama（自带 OpenAI 兼容端点）；N 卡且需要并发上 vLLM；要精细控制用 llama.cpp server。

**第三步：选模型。** 优先选原生训练过 tool calling 的系列（如 Qwen、Llama 3.x），纯聊天微调模型在 Agent 场景里基本不可用。

**第四步：改默认参数。** 最大的坑在这——Ollama 默认上下文很小（2048/4096，视版本而定），而 Agent 的 system prompt 加上 MCP 工具 schema 很容易超限，超限后是**静默截断**，模型表现为"忘了工具怎么用"。务必显式设置 `num_ctx`（或 `OLLAMA_CONTEXT_LENGTH`），建议 16k 起步。

**第五步：接入 OpenClaw。** 把模型提供方指向本地端点（如 `http://127.0.0.1:11434/v1`），先别上复杂任务：挑一个最简单的 MCP 工具（读文件、计算器都行），固定同一个任务跑 10 次，统计工具调用成功率。低于 8/10 就先换模型或降温度，别急着排查别的。

**第六步：建自己的基准。** 别信排行榜，用你真实的 Agent 循环测：工具调用成功率、JSON 合法率、单步耗时、循环能否正常终止。每次换模型或改配置前后各跑一遍。

## 踩坑点

- **上下文默认值太小** → 工具 schema 被截断，模型胡乱调用，这是最常见也最难察觉的问题；
- **量化档位过低**（Q2/Q3）→ JSON 输出频繁损坏、工具参数畸形，Agent 任务建议 Q4_K_M 起步，重工具场景上 Q5/Q6；
- **消费级显卡并发能力弱**：单请求没事，Agent 并行跑两三步就 OOM，要么排队要么砍上下文；
- **温度没调**：工具调用场景把 temperature 压到 0–0.2，稳定性提升非常明显；
- **别迷信参数量**：一个 14B 但 90% 正确调用工具的模型，好过一个 32B 但一半时候参数填错的模型。

## 可复用建议

- **分层路由**：本地模型承接高频简单步骤（摘要、分类、格式化），复杂规划交给云端；在 OpenClaw 里可以按子任务配不同模型，两者共存不冲突。
- **锁定模型版本**（digest），别让"latest"自动更新把跑得好好的 Agent 半路搞挂。
- **把失败的工具调用日志留下来**，它是区分"模型不行"还是"prompt 不行"最快的证据。

## 总结

家用电脑跑本地 LLM 已经是现实可行的方案，但请把它当一道工程预算题：显存要算、默认配置要改、评估要用自己的 Agent 循环而不是通用跑分。从 7B/14B 的 Q4 量化起步，先验证工具调用可靠性，再按真实需求向上加码——大部分自动化场景，14B 就够了。
