## 背景

每日日报本质上是个数据问题：你今天做了什么，答案都散落在 git 提交、终端历史、任务列表和 Agent 会话日志里。手写日报的痛点不在于"写"，而在于回忆和整理。我的做法是把这件事交给一条固定流水线：每晚定时收集当天数据，结构化后让模型做摘要，最后自动投递归档。

## 问题

直接把原始日志丢给 LLM 总结，有三个明显问题：

1. 日志又长又脏，token 消耗大，关键信息被噪音淹没；
2. 模型会"脑补"——日志里没有的工作项它也能编出来；
3. 输出格式不稳定，每天一个样，没法归档对比。

所以核心设计原则只有一句：**确定性的事交给脚本，模糊的事才交给模型。**

## 做法

流水线分四段，每段一个独立脚本，中间产物全部落盘。

**1. 采集。** 用 OpenClaw 的 cron 每天 21:30 触发。采集脚本只做确定性提取：git log 按作者和日期过滤、当日会话中被调用的工具与参数摘要、任务状态变更。统一输出 JSONL，每行带 `timestamp / source / action / summary` 字段。

**2. 归一化与压缩。** 去重（同一文件反复改动只留最后一条）、截断（超长条目砍掉）、脱敏（正则过滤 token、密钥、内网地址）。这步做完，数据量通常降到原始日志的 5% 以内，模型只看这些。

**3. 摘要。** Prompt 里带严格 schema：`done / in_progress / blocked / tomorrow` 四段，每条结论必须引用数据行 id，禁止出现引用之外的内容。用结构化输出而非自由文本，拿到结果先过 schema 校验，失败则携带错误信息重试一次。

**4. 渲染与投递。** 模板渲染成 Markdown，一份发群 webhook，一份按日期归档到仓库。LLM 阶段失败时走兜底：直接把归一化后的原始摘要发出去——宁可丑一点，不能断更。

## 踩坑点

- **时区**：cron 跑在 UTC，git log 的 `--since` 用本地日期查会差八小时。"昨天"的边界必须显式写成带时区的 ISO 时间。
- **重复运行**：cron 重试叠加手动补跑，容易出两份报告。加了简单的 lock 文件，策略是"当天已存在则覆盖"。
- **日志格式漂移**：升级后 session 日志结构变了，解析器静默产出空结果。现在每个采集器都有最小冒烟断言，产出为空即告警。
- **幻觉**：早期版本报告里多出一条根本没做的"修复部署脚本"。加引用校验才压住——每条结论必须能映射回具体数据行。

## 可复用建议

1. **分段解耦**：采集、归一化、摘要、投递各自独立，任何一段坏了都能单独重跑；中间产物落盘让调试成本极低。
2. **数据源配置化**：YAML 里声明"日报包含哪些来源、各自怎么取"，新增数据源不动主流程。
3. **先跑通一条再扩展**：第一版只有 git 一个来源，先把 schema、校验、兜底跑稳，再往上叠。
4. **给报告留证据链**：每条结论带引用 id，抽查时能秒级回溯，这也是对模型输出建立信任的基础。

## 总结

这条流水线跑了一个多月，日报从每天 15 分钟的手工活，变成早上瞥一眼的确认动作。经验浓缩成一句话：LLM 适合做"归并与措辞"，不适合做"提取与事实"。把事实层做扎实，剩下的交给模型，自动化才算真正站得住。
