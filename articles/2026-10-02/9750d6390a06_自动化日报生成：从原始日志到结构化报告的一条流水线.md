## 背景

我们小组每天下班前要交一份日报，数据散在 git 提交、CI 运行记录、服务日志和工单系统里。以前的做法是各人翻一遍、往群里贴一段，最后由值日同学拼成日报，全程 30–40 分钟，口径还经常不一致——有人贴 PR 链接，有人只写"继续开发中"。后来我们用 OpenClaw 的定时任务加几个 MCP 工具，搭了一条从原始日志到结构化报告的流水线，现在人工环节只剩最后审阅。

## 问题

直接"把日志丢给模型写日报"走不通，实际遇到三类问题：

1. 原始日志格式杂、噪声多，模型容易漏项，数字经常编错；
2. 日报需要固定结构（昨日完成 / 今日进行 / 风险 / 指标），自由生成不稳定；
3. 定时触发、失败重试、重复发送这些工程问题没人管。

## 做法

流水线分四层，每层独立可测：

1. **采集**：cron 触发 OpenClaw agent，通过三个 MCP 工具分别拉 git log、CI API、错误日志 tail，各自输出 JSON。
2. **归一化**：一个预处理脚本把三路数据映射到统一 schema：`source / event_type / timestamp / actor / summary / metrics`。时间统一转东八区，窗口取昨日 00:00–24:00，中间 JSON 落盘归档。
3. **摘要**：agent 只读归一化后的 JSON，按固定 schema 输出。事实字段（PR 数、失败任务列表、错误 Top3）直接抄自输入，只有"一句话总结"由模型生成，temperature 调低。
4. **渲染与分发**：JSON 套 Markdown 模板，推送到 IM 群机器人 webhook，同时按日期存进仓库，可 diff 可追溯。发送前跑一个规则校验器：必填字段齐全、关键数字与原始数据对得上；不通过就带着报错信息重试一次，再失败就降级为只发原始数据附件。

## 踩坑点

- **时区**：日志时间戳是 UTC，最初按本地日期切窗口，跨天任务要么漏要么重复。教训是先统一时区，再做日期切分。
- **别让模型算数**：第一版让模型直接从原始日志数 PR、汇总错误率，结果数字对不上。现在统计全部在脚本层完成，模型只负责组织语言。
- **结构化输出偶发漏字段**：靠 schema 校验 + 把校验错误回喂重试解决，不要赌概率。
- **幂等**：定时任务重叠触发会发两份日报，用"日期"做幂等键，发送前检查归档目录。
- **脱敏**：日志里常见 token 和内网 IP，归一化阶段用正则清洗，不要拖到生成之后。

## 可复用建议

- 先定 schema 再写 prompt，结构稳定比文笔重要；
- 采集 / 归一化 / 摘要 / 分发四层解耦，摘要层随时可换模型；
- 中间 JSON 一定归档，出问题可回放重跑，不用等第二天；
- 保留人工审阅：机器生成、人签名发出，前两周拿人工日报对照校准字段。

## 总结

这条流水线的核心不是"让 AI 写日报"，而是把数据链路工程化：结构在前、生成在后，事实由管道保证，模型只把话说顺。全部加起来约三个小脚本加十几行配置。建议从单一数据源（比如 git）跑通，再逐步扩展到 CI 和日志，别一上来铺满所有源。
