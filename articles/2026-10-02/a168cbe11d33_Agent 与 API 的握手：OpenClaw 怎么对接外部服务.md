# 背景

Agent 本身只是个“大脑”，真正干活靠的是手——也就是它能调用的工具和外部服务。OpenClaw 的使用场景决定了这个问题躲不开：用户在对话里说“帮我看下 CI 挂没挂”“把这条工单同步到看板”，背后全是 API 调用。

目前对接外部服务主要有三条路：现成的 MCP server、自己写的 skill/插件、以及兜底的脚本执行。三条路没有绝对优劣，只有场景匹配。

# 问题

实践中最常见的坑，都出在“接线”之前的假设上：

1. **把整个 REST API 平移成工具。** 40 个端点全暴露给模型，结果它经常选错工具、传错参数。
2. **错误信息对模型不友好。** 返回一大坨 HTML 错误页，模型要么反复重试，要么编造结果。
3. **鉴权散落在对话上下文里。** token 出现在上下文中，既不安全也浪费 token。

# 做法

我们的经验是按这个顺序走：

**第一步：盘点而不是开写。** 列出高频操作，标注只读/有副作用。只读且高频的先接，有副作用的放后面并加确认机制。

**第二步：选路径。** 社区已有 MCP server 的直接用配置接入，不重复造轮子。内部 HTTP API 建议写一个薄的 MCP server，把 REST 包装成 2–4 个语义明确的工具（比如 `search_tickets`、`create_ticket`），而不是逐端点映射。低频、一次性的需求用 skill 包脚本即可。

**第三步：为模型设计接口，而不是为人。** 工具描述里写清楚“什么时候用、什么时候不该用”，这一条能消掉大部分误调用。参数尽量扁平，枚举值直接写进 description。

**第四步：统一收口。** 鉴权、超时、重试、限流放在一个公共 client 层，工具层只写业务逻辑。所有工具调用记日志：参数摘要、耗时、状态码，方便回放排障。

# 踩坑点

- **工具数量超过 20 个后，选错率明显上升。** 解法是按场景拆 agent 或用子 agent，让每次会话只看到相关子集。
- **分页接口别直接暴露 `page` 参数**，模型会疯狂翻页。改成 `search` + 默认 limit，服务端聚合后一次返回。
- **幂等性要显式声明。** 哪些操作可重试、哪些不行，写进工具描述，否则模型重试一个非幂等的创建操作就是事故。
- **返回值控制在 2KB 以内**，超了就做摘要 + 提供二级 detail 工具。上下文被一条查询结果撑爆的教训很常见。
- **每个外部调用显式设 timeout。** 没设的话，模型干等 30 秒的典型表现是重复调用或者直接放弃。

# 可复用建议

- 先写“否决条件”再写功能描述：这个工具**不该**在什么情况下被调用。
- 错误返回统一包装成短 JSON，带一个 `hint` 字段告诉模型下一步怎么办（换参数、降级、上报人工）。
- 改 prompt 之前先跑固定用例集：准备几条真实对话回放，工具行为变更时做回归。
- 最小权限。一个只读看板的集成，不需要带写权限的 token。

# 总结

对接外部服务的核心不是“接得多”，而是“接得准”。少而语义清晰的工具、可行动的错误信息、收口在公共层的鉴权与重试，加上基本的观测日志——这四件事做完，agent 调 API 的可靠性会有质的提升。剩下的迭代交给真实使用中的日志，而不是凭空设计。
