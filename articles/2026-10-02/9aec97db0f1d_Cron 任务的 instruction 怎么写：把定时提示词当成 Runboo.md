## 背景

OpenClaw 的 cron 任务，本质是「定时把一段 instruction 喂给 agent」。很多人（包括我一开始）把这段 instruction 当聊天消息写：「帮我看看今天的邮件，整理一下发我。」手动在会话里这么说没问题，因为有上下文、有追问、有纠错。但 cron 触发时，agent 拿到的只有这一段话，没有会话历史。

我现在的验收标准就一条：**把这段 instruction 交给一个刚睡醒、很能干、但对项目一无所知的同事，他能不能一次做对？** 能，才是合格的 cron instruction；不能，就只是聊天记录。

## 问题：定时任务的三类典型翻车

1. **输出不可控**：没有格式约束，同一任务每天的产出结构都不一样，下游没法稳定消费。
2. **静默失败**：工具挂了、数据为空，agent 倾向于「脑补」一份看起来像样的结果。你三天后才发现日报一直是编的。
3. **时间边界模糊**：「今天」是哪个时区的今天？00:05 跑的任务，统计的是谁的一天？

## 做法：instruction 的最小四段结构

我固定用这个模板（可直接抄）：

```text
【任务】每天 08:30（Asia/Shanghai）执行的晨报汇总，无人触发，自包含。

【步骤】
1. 调用 mcp__mail__list_unread，只取触发时刻前 24 小时的未读邮件。
2. 调用 mcp__calendar__today，获取今日日程。
3. 任一步失败：跳过该部分，在输出末尾标注「数据源 X 不可用」，禁止编造数据。

【输出】
按此模板发到 #daily-report 频道，正文不超过 200 字：
- 邮件要点（≤5 条，一行一条）
- 今日日程（时间 + 事件名）
- 异常说明（无则写「无」）

【禁止】
- 不 @ 任何人，不回复消息
- 不调用步骤之外的任何工具
```

逐段说下理由：

- **任务头**：一句话说清这是什么、几点跑、给谁看。这是给 agent 做上下文重建，不能省。
- **步骤**：每步一个动词 + 一个工具。工具名写 MCP 的准确名称，别写「查一下邮件」这种自然语言——名称含糊 agent 就会猜，猜错就是幻觉。
- **失败兜底**：最重要、也最少人写的一段。明确「失败就标注，不要编」。
- **禁止项**：定时任务最容易失控的是副作用。发到哪、@ 谁、能不能调额外工具，全部写死。

## 踩坑点

- **先手跑，再固化**。指令先在会话里手动发一遍，确认工具可达、产出符合预期，再写进 cron。跳过这步等于没测就上线。
- **一个任务只做一件事**。晨报 + 周报拆成两个 cron，prompt 越长越顾此失彼。
- **输出契约化**。固定模板或 JSON，diff 友好、下游好解析，回归一眼能看出来。
- **把指令当代码管**。改 instruction 就记一笔 changelog，出问题时你能回答「上周五之前它长什么样」。
- **时间要写死窗口**。别依赖 agent 对「今天」的理解，统计区间用「触发时刻前 24 小时」这类锚点描述。

## 可复用建议

上线前过一遍自查清单：

1. 指令自包含吗？（不依赖会话历史）
2. 每个工具都有准确名称吗？
3. 有输出模板吗？
4. 失败有明确动作吗？
5. 时间有时区和统计窗口吗？
6. 幂等吗？任务重复触发一次会不会出双份数据？（写文件类任务用固定文件名覆盖，别用时间戳追加）

另外建议从**只读任务**起步（汇总、报告、提醒），稳定跑两周后再上**有副作用**的任务（发消息、改配置）。中间的信任，是靠上一阶段的稳定输出攒出来的，不是调出来的。

## 总结

Cron instruction 不是聊天消息，是一份交接文档：自包含、工具有名有姓、有输出契约、有失败兜底、有边界。写完用「新同事测试」验收一次，它能照着一次做对，这条定时任务才算上线。
