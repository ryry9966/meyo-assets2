## 背景

现在大多数 AI 助手还是纯被动式：用户发消息 → 模型响应 → 结束。但在 OpenClaw + MCP 的组合里，工具、数据源和定时能力都是现成的，缺的其实是一层"什么时候该主动"的决策逻辑。我们最近给内部助手加了一套 proactive 触发层，把"提醒 CI 挂了""发现日志里的异常模式""到点整理周报草稿"这类事情从用户发起改成了系统发起。跑了两周，记录一些工程结论。

## 问题

Proactive 最容易做砸的方式，就是拿一个 cron 直接怼 LLM：每 5 分钟跑一次全量推理，输出一段"建议"。结果通常是三选一：成本爆炸、通知疲劳，或者两条都占。真正的难点不是"能不能主动"，而是三个问题：

1. 什么事件值得触发？
2. 触发之后，值不值得打扰用户？
3. 打扰之后，动作边界在哪？

## 做法

我们把它拆成一个三层漏斗：

**第一层，事件接入。** 触发源收敛成统一事件格式：cron 定时、webhook、文件变更监听、MCP resource 轮询。每个触发器用 YAML 声明，强制带冷却时间（cooldown）和静默时段。

**第二层，评估。** 事件先进规则预筛（关键词、阈值、去重键），通过后才交给一个便宜的小模型判断"值不值得报"，输出三档：忽略 / 记录 / 推送。大模型只在第三档才被拉起来生成内容。

**第三层，动作分级。** 只读动作（查询、汇总）直接执行；可逆写操作执行后附上回滚入口；不可逆操作（对外发消息、删除、外部 API 调用）只生成草稿，等用户确认。每次主动决策落一条 evidence 日志：触发源、预筛结果、模型判断理由、最终动作。

## 踩坑点

- **去重没做好**：同一次 CI 失败连续提醒了 7 次，因为每次重试都会触发 webhook。后来加"状态键 + 冷却时间"，状态没变化就不重复推。
- **评估模型太积极**：prompt 里只写"判断是否重要"，它把所有事件都判成重要。改成强制输出"用户忽略这条的代价是什么"，重要性从"事件有多响"变成"错过有多亏"，误报率降了一大截。
- **静默时段没考虑时区**：凌晨三点推送测试环境告警。现在触发器配置里必须有显式 quiet hours。
- **没有 evidence 日志的那一周**，排查"它为什么自作主张"基本靠猜。

## 可复用建议

1. 把**打扰预算**当成显式配置：每天 proactive 推送上限，超了只记录不推送。
2. **主动 ≠ 自主**：动作分级矩阵（只读 / 可逆 / 不可逆）写死在系统层，不要交给模型现场决定。
3. **用户行为回写**：采纳、忽略、投诉三类反馈定期回扫，用来调阈值和 prompt。上线两周靠这个把推送量砍了 60%。
4. 上线顺序建议：先做整理类（汇总、草稿、备忘），再做告警类，最后才碰执行类。风险递增，信任也是递增的。

## 总结

Proactive 能力的核心不是让模型更聪明，而是让系统更守纪律：事件怎么进、判断怎么做、动作怎么分级，每一层都要有显式的工程约束。先控制打扰成本，再逐步放开动作边界——用户对"它主动做了事"的信任，是一点一点攒出来的。
