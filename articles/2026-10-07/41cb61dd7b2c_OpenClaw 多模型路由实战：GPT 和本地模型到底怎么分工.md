## 背景

OpenClaw 支持同时挂多个模型 provider，但社区里最常见的两种用法都是"一把梭"：要么所有任务全走 GPT，要么为了省钱全走本地模型。跑两周之后，前者账单难看、隐私数据出域，后者表现为 agent 频繁犯低级错误。这篇帖记录一下我在自己的 OpenClaw 实例上做模型路由的过程，思路可以直接搬。

## 问题

先说结论：**没有"哪个模型更好"，只有"哪类任务给哪个模型"**。我盘了一周的请求日志，任务大致分四类：

- 规划、多步 tool calling、复杂推理 → 对模型能力敏感
- 长上下文阅读、代码理解 → 对窗口大小敏感
- 批量摘要、格式化、简单分类 → 高频但简单
- 涉及私有数据的处理 → 隐私敏感

四类需求互相冲突，单一模型必然顾此失彼。

## 做法

1. **先分类，再路由。** 别急着改配置，先从日志里把任务类型统计出来。我的比例大约是 70% 的请求属于"轻任务"，但只消耗 20% 的价值。
2. **配置主备链。** 主模型设 GPT，fallback 指向本地模型（Ollama 起的即可），保证云端不可用时实例不瘫。
3. **按 agent 分模型。** 主 agent 用 GPT；专门跑批量摘要、日志清洗的子 agent 固定用本地模型。这是收益最大的一步，成本直接降了一半多。
4. **插件里做静态分发。** 在 hook 里按工具名/任务类型写显式映射，而不是搞"复杂度打分"的动态路由——后者误判一次，代价就是一轮失败的 tool call。
5. **加观测。** 每次请求记录：实际使用的模型、token 数、时延、tool call 成功率。没有这个，路由就是盲调。

## 踩坑点

- **本地模型的 function calling 是重灾区。** schema 稍复杂就漏参数、编字段名。凡是 tool-heavy 的任务，别路由给本地，省的钱不够返工。
- **上下文窗口不一致。** 长会话 fallback 到本地模型后被截断，表现为"agent 突然失忆"。会话类任务锁定主模型。
- **静默 fallback 会反向烧钱。** 本地模型失败重试三次再落回 GPT，时延和成本双输。fallback 必须打日志，失败率超阈值要告警。
- **输出格式不一致。** 本地模型 JSON 输出偶尔混入解释性文字，下游解析要容错，或者干脆只让它做不要求结构化输出的任务。

## 可复用建议

- 静态路由优先，动态路由后置。先跑通"按任务类型写死"，观察一个月再考虑优化。
- 建 20~30 条的小评测集，改任何路由规则前先跑一遍，防止"省了钱坏了活"。
- 隐私敏感的数据路径强制走本地，这条不参与任何 fallback。
- 把"哪些任务绝不能降级"写成清单放在配置注释里，比记忆可靠。

## 总结

多模型路由本质上是成本、质量、隐私三者之间的显式取舍，OpenClaw 把选择权交给了你，但不会替你做决定。先分类、静态分发、持续观测，三步走下来，我的月成本降了约 60%，核心任务质量没有可感知的下降。路由不是炫技，是把工程判断写进配置里。
