## 背景

跑 Agent 自动化一段时间后你会发现：代码 bug 好歹会报错，外部 API 的故障才是日常。MCP server 掉线、上游限流、token 过期、第三方服务半天不响应——这些不是异常路径，而是生产环境的常态。一个默认"工具调用永远成功"的 Agent，在长任务里迟早出事。

## 问题：两种典型失败

1. **可见的失败**：工具抛异常，流程中断。烦人但不致命。
2. **不可见的失败**：错误被工具层吞掉，或者错误信息太模糊，LLM 拿不到事实就开始"合理推测"。定时任务跑完，报告看起来完整，实际是编造的。这种静默错误比崩溃贵得多。

## 做法：三层恢复

**第一层：调用包装（transport 层）**

- 每次工具调用设超时，别让一个挂掉的 API 卡死整个循环
- 区分错误类型：429 / 5xx / 网络错误可重试；4xx 参数错误、401 鉴权失败重试无意义
- 重试用指数退避 + 随机抖动，上限 3 次左右

**第二层：把结构化错误还给模型**

不要抛异常让框架崩，而是返回约定格式的错误对象：

```json
{ "ok": false, "retryable": false,
  "hint": "上游限流，建议 60s 后重试或改用缓存数据" }
```

LLM 拿到这个才有判断依据：换工具、跳过、还是报告失败。`hint` 字段很关键，等于把你的运维经验写进错误里。

**第三层：Agent 级降级**

- 优先用上一步成功拿到的缓存/快照，并明确标注数据截止时间
- 没有替代数据时，让 Agent 输出明确的"该步骤失败"，而不是填一个像样的答案
- 长任务做 checkpoint，失败后从断点恢复，不重跑已成功的副作用步骤

## 踩坑点

- **重试非幂等操作**：POST 建工单重试三次，得到三个重复工单。带幂等键，或只对幂等操作开自动重试。
- **定时任务无限重试**：任务每 5 分钟跑一次，API 挂一整晚，日志和 token 费用一起爆炸。加熔断：连续 N 次失败后进入冷却，拉长间隔或跳过本轮。
- **把 4xx 当可重试**：参数错误重试一万次还是错。
- **错误上下文喂太长**：把整个堆栈塞给模型，注意力被污染。只给结构化摘要。

## 可复用建议

1. 给所有工具实现统一的错误契约（ok / retryable / hint），写进团队的 MCP 工具规范。
2. 每次工具失败打一条结构化日志：工具名、错误类型、耗时、重试次数。排障时这就是时间线。
3. 降级要有痕迹：输出里明确哪些数据来自缓存、哪一步被跳过，别让降级悄悄发生。
4. 上线前做故障演练：手动停掉某个 MCP server，看 Agent 是崩溃、编造还是正确降级。没演练过的恢复逻辑等于没有。

## 总结

错误恢复本质是系统工程，不是把"如果失败了请重试"写进 system prompt 就完事。真正有效的是：工具层诚实报告失败并给足上下文，编排层限制重试的爆炸半径，Agent 层只做有依据的降级决策。先让失败可见，再谈自愈。
