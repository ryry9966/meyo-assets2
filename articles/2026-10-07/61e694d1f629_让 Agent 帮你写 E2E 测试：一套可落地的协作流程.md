## 背景

E2E 测试是那种"人人都知道该写，但没人爱写"的活儿。覆盖率靠它兜底，但写一条用例要开浏览器、查选择器、等 CI、修 flaky，成本高得离谱。现在 Agent + MCP（比如 Playwright MCP、数据库 MCP）给这个问题提供了新解法：不是让 AI 凭空生成代码，而是让 Agent 真的去"用"你的系统，再把操作过程沉淀成测试。

## 问题

直接让模型"给这个页面写个 Playwright 测试"，产出通常不可用，原因主要有三个：

1. **模型没见过真实页面**，选择器全靠猜，写出来的 `page.click('#submit')` 一跑就挂；
2. **断言太弱**，生成的测试往往只验证"页面没报错"，跑通了但没兜住任何业务逻辑；
3. **API 幻觉**，混用不同版本的 Playwright/Jest API，本地根本跑不起来。

## 做法

我们在一个中后台项目里跑通了这样一条流水线：

**第一步：给 Agent 装上眼睛和手。** 挂上 Playwright MCP（浏览器操作）和仓库读写权限。关键点：Agent 必须能真实打开页面、截图、读 DOM，而不是靠你粘贴 HTML 片段。

**第二步：先探索，再写测试。** 提示词分两段：先让它走一遍目标流程（登录 → 建单 → 提交），记录每步的实际选择器和页面状态；确认路径走得通后，再要求它把这次探索翻译成测试代码。顺序很重要——先探索后写码，成功率比直接写码高很多。

**第三步：自闭环修复。** Agent 写完自己跑 `npx playwright test`，失败就把报错和截图带进上下文重写，上限 3 轮。3 轮还不过就停下来交给人，避免无限烧 token。

**第四步：人只审断言。** 选择器、等待、fixture 让 Agent 管，但每条断言（expect 什么值）必须人工过一遍，这是质量底线。

## 踩坑点

- **测试全绿但没测到东西**：Agent 特别擅长写"必过"的测试。对策是在项目里放一份测试规范文件（约定 `data-testid`、禁止 `waitForTimeout`、断言落到数据层面），作为上下文喂给 Agent。
- **选择器脆弱**：没有 `data-testid` 的老页面，改版就挂。先花半天补测试属性，比后面反复修用例划算。
- **认证卡点**：Agent 会卡死在验证码/滑块环节。这类流程用测试账号 + 环境变量注入 token 绕过，别指望 Agent 自己解。
- **上下文膨胀**：探索阶段的截图和 DOM 片段很大，多轮之后 token 爆炸。每轮只保留必要失败信息，探索记录落盘成文件按需读取。

## 可复用建议

1. 维护一份 `TESTING_GUIDE.md`（选择器规范、断言要求、禁止事项），每次塞进 Agent 上下文。这份文件的收益比任何提示词技巧都大。
2. 把"探索 → 生成 → 运行 → 修复"固化成脚本或自定义 MCP 工具，团队里谁都能一键复跑。
3. 把 Agent 当"初稿生产者"，测试的最终责任仍在人。新功能上线前跑一遍生成，review 成本远低于从零手写。

## 总结

Agent 写 E2E 测试的价值不在"全自动"，而在把写测试的边际成本压到 review 一条 diff 的水平。真实打开页面、先探索后生成、断言人工把关——这三件事做对了，产出基本可用。剩下的，交给时间收敛。
