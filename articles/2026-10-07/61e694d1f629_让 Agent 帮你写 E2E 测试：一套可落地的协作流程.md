## 背景

E2E 测试是自动化测试里投入产出比最拧巴的一层：写起来慢、维护起来烦，但又是唯一能验证"用户真的能走完流程"的手段。很多团队都是在回归炸了几次之后才回头补，此时欠账已经很厚。

最近我把 Playwright 的 MCP 工具接进 OpenClaw 的 agent 工作流，让 agent 参与从测试设计到失败修复的完整环节。跑了两三个迭代，结论是：能用，但前提是流程要设计对。

## 问题：为什么"让 AI 写测试"经常翻车

直接丢一句"帮我给登录页写个 E2E"给 agent，通常会得到三类结果：

1. **凭空编造的选择器**。agent 没看过真实 DOM，写出来的 `#login-btn` 在页面上根本不存在。
2. **一锤子买卖代码**。生成的测试在本地跑不起来，缺 fixture、缺环境变量，风格和你现有的 page object 完全对不上。
3. **讨好式通过**。测试失败时，agent 倾向于放宽断言或加 timeout 让它变绿，而不是找根因。

共同根源就两条：agent 缺少真实的运行时反馈，也没有被约束在团队的测试规范里。解法就是补这两块。

## 做法：四步流程

**第一步：喂上下文，而不是喂需求。**
在项目记忆（AGENTS.md 或系统提示）里固化：路由表、关键页面的 DOM 约定、selector 优先级（`data-testid` > role > 文本）、已有测试的组织方式。agent 产出质量的下限，基本由这份上下文决定。

**第二步：给 agent 一双眼睛。**
通过 MCP 让 agent 直接操作浏览器：打开页面、抓 accessibility snapshot、执行交互。这一步的质变在于——选择器从"猜"变成"看了再写"。我的流程是先让 agent 打开目标页面导出 snapshot，确认节点存在后再生成代码。

**第三步：大纲先行，人工把关。**
不要直接要代码。先让 agent 产出用户旅程大纲：覆盖哪些路径、每步断言什么、哪些进冒烟哪些进全量。人花五分钟 review 大纲，比事后 review 五百行测试代码便宜得多。大纲确认后再生成，并要求按现有 page object 风格拆文件。

**第四步：失败回灌闭环。**
写个脚本：跑测试 → 收集失败用例的错误信息、截图、trace → 拼成 prompt 回灌给 agent → agent 给出修复 diff。注意是 diff，不是全量重写，否则 review 成本会失控。

## 踩坑点

- **token 消耗比预期大**。复杂页面的 accessibility snapshot 轻松上万 token，agent 来回探测几次上下文就满了。对策：探测完立刻让 agent 提炼成精简的结构摘要，原始 snapshot 不要留在上下文里。
- **agent 修 flaky 的方式是加 timeout**。要在规范里明确禁止，要求它先分析失败原因是竞态、动画还是网络 mock 未就绪，再给对应解法。
- **单次生成不要超过三个用例**。超过这个量，agent 会开始复用错误的假设，错误滚雪球。
- **断言要提前约定**。不约定的话，agent 爱写"不断言只跑通"的空壳测试，或者像素级截图对比这种维护噩梦。

## 可复用建议

1. 把测试规范写进项目记忆，等于给 agent 加了一层"团队风格 lint"。
2. 大纲 → 生成 → 执行 → 回灌修复，四段拆开，每段设人工检查点。
3. selector 约定值得对 agent 单独强调一遍，比指望它从现有代码自己归纳可靠得多。
4. 修复只接受 diff，人保留最终合并权——agent 是高速实习生，不是合伙人。

## 总结

Agent 写 E2E 的价值不在"替你写"，而在抽掉写测试、修测试中重复机械的部分。真正的收益点是失败回灌闭环：回归炸了之后，agent 几分钟内给出带 trace 分析的修复建议，人只做判断。流程设计比模型能力更重要——先把上下文、眼睛和检查点搭好，再谈提效。
