## 背景

做 Agent 自动化绕不开一个基础问题：助手大部分时间在“睡觉”，它靠什么醒来？目前只有两条路：

- **轮询（heartbeat）**：Agent 按固定间隔自己醒来，检查信箱、任务队列或状态变化；
- **推送（push）**：外部事件（webhook、消息队列、MCP 工具回调）主动叫醒 Agent。

两者看似二选一，实际工程里几乎都需要混合。

## 问题

纯轮询的账很好算：延迟约等于间隔，token 成本约等于间隔的倒数。设 5 分钟一跳，平均感知延迟 2.5 分钟，一天 288 次心跳——其中 90% 以上可能是空转，但 token 和 API 配额照烧。

纯推送的坑在可靠性：需要常驻入口（webhook 服务、MQ consumer），断线、宕机、事件风暴都要自己兜底；更麻烦的是，协议层“没消息”和“消息丢了”不可区分，漏单是静默发生的。

## 做法：低频心跳兜底 + 推送加速

我们在 OpenClaw 插件里的分层方案：

1. **心跳作为兜底层**
   - 基础间隔 5–10 分钟起步，按时效性分档（立即 / 分钟级 / 小时级三个队列）；
   - 间隔加 ±20% 随机 jitter，避免多实例同步醒来；
   - 每次心跳先过规则闸门（有无未确认事件），无事件直接结束，不进 LLM。
2. **推送作为加速层**
   - 关键事件（用户消息、CI 失败、告警）走 webhook → 消息队列 → MCP 工具触发；
   - 推送体只携带事件引用（ID + 类型），Agent 醒来后回源拉详情，避免大 payload 和重放问题；
   - 消费侧按事件 ID 做幂等去重。
3. **对账机制**
   - 心跳除了查任务，还要核对“最近 N 分钟应收到 ACK 但未收到”的推送，缺失就补拉一次全量状态。这一步让心跳不再空转，而是承担兜底职责。

## 踩坑点

- 间隔照抄别人的：最初 1 分钟一跳，一晚烧掉当月 40% 的 token 配额，事后统计 95% 的心跳无事可做；
- 推送重试没做幂等键，MQ 重发导致同一任务被执行了三次；
- 容器休眠期间 webhook 静默丢失，系统表面正常、实际漏单，靠对账心跳才发现；
- 多实例心跳没加 jitter，同步醒来把数据库连接池打满；
- 安静时段（quiet hours）没做在心跳层，半夜被非紧急告警推送叫醒执行了任务。

## 可复用建议

- 能推则推，推不可靠则轮询兜底，两者是层次关系不是对立选项；
- 心跳先过规则闸门再进模型，把空转成本压到接近零；
- 所有推送消费写幂等键，按事件 ID 去重；
- 监控两个指标就够定位问题：**空转率**（无事件心跳占比）和**推送丢失率**（对账补拉次数）；
- 先量化时效性需求和 token 预算，再定间隔，顺序不要反。

## 总结

轮询是可靠性底座，推送是延迟优化。一个带对账能力的低频心跳，加上一条带幂等的推送通道，就能同时拿到可接受的延迟和成本。heartbeat 设计的本质不是选型，而是把“唤醒”拆成兜底、加速、对账三层，分别控制成本和正确性。
