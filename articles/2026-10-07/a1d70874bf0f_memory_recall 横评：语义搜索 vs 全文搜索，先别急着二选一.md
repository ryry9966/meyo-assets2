## 背景

OpenClaw 的 memory_recall 是 Agent 长期记忆的检索入口，底层默认走混合方案：SQLite FTS5 全文检索 + embedding 向量召回，再做分数融合。社区里常见两种极端声音：一种觉得向量搜索天然更"聪明"，另一种嫌 embedding 依赖外部 API、想整个关掉。我把两条路径单独拉出来，用自己的记忆库跑了一轮小样本对比，结论先放前面：**两者的失效区几乎不重叠，混合是默认正解**。

## 问题

- **纯语义搜索**：强在改述和跨语言，"上次部署出问题怎么处理的"能命中写着 deploy rollback 的记忆；弱在精确标识符——错误码、函数名、端口号会被 embedding 糊掉，top3 里经常全是"语义相邻"的错误条目。
- **纯全文搜索**：强在精确 token，零额外开销、不联网也能用；弱在同义改述，而且中文分词是老大难——FTS5 默认 tokenizer 不切中文词，整句进索引基本等于摆设。

## 做法

1. 从日常使用积累的记忆里取 40 条左右做库，攒了 16 条评测 query，覆盖四类：精确标识符、同义改述、中英跨语言、时间指代。
2. 分别跑纯 FTS、纯向量、混合三条路径，人工核对 top3 是否命中，统计 hit@3。
3. 配置走 `agents.defaults.memorySearch`，本地 embedding 起不来就 fallback 到 remote；FTS 侧确认 memory 目录已建索引。

| 查询类型 | 纯 FTS | 纯向量 | 混合 |
|---|---|---|---|
| 精确标识符（5 条） | 5/5 | 3/5 | 5/5 |
| 改述/跨语言（10 条） | 4/10 | 8/10 | 9/10 |
| 时间指代（1 条） | 0/1 | 0/1 | 0/1 |

样本很小，别当基准测试，只当方向参考。唯一没命中的时间指代，根因是那条记忆根本没写日期——检索救不了没写进去的东西。

## 踩坑

1. **先查库再怪算法。** 有两次"召回变差"，其实是同一条事实被写了三遍还互相矛盾，去重后指标直接涨。
2. 中文全文检索要换 trigram tokenizer，或入库前自己做分词，默认配置不可用。
3. 记忆要原子化：一个小节一件事，带上日期、精确标识符和关键英文名词。跨小节的长记忆切块后两头不讨好。
4. 换 embedding 模型等于全库重刷向量，相似度分布会变，评测集必须重跑。
5. 断网或没配 key 时 FTS 是唯一兜底，别把向量做成硬依赖。
6. 融合别上来就上 reranker，倒数排名融合（RRF）几行代码、零额外延迟，先够用再说。

## 可复用建议

- 默认保持混合检索，除非评测数据证明某一侧在拖后腿。
- 把记忆当成"写给检索器的数据"：日期 + 精确 token + 中英关键词，三样齐全。
- 评测集（10~20 条）放进配置仓库，任何检索相关变更后重跑一次，五分钟的事。
- recall 变差的排查顺序：库内容 → 切块方式 → 检索算法。倒过来做全是弯路。

## 总结

语义搜索和全文搜索不是二选一，而是互补：一个管"意思相近"，一个管"一字不差"。OpenClaw 默认混合正是这个原因。真正决定 recall 上限的，往往不是检索算法，而是你写记忆时的纪律。
