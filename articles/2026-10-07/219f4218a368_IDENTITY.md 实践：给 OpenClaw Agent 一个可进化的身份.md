## 背景

OpenClaw 的 agent 在每次会话启动时，会从 workspace 读取一组记忆文件来组装 system prompt，`IDENTITY.md` 是其中最"人格化"的一份：它定义 agent 叫什么、以什么姿态跟你说话。默认情况下这份文件几乎是空的，agent 就是个没有姓名的通用助手——能用，但没有连续性。

## 问题

实际用下来有三个痛点：

1. **行为漂移**。今天像个话痨客服，明天冷冰冰只回一句，跨会话没有任何稳定性。
2. **身份散落在各处**。名字写在一处、语气要求写在另一处的自定义 prompt 里，改一次要翻好几个文件。
3. **团队共享 agent 时互相覆盖**。每个人各自"调教"，谁也说不清当前人格是哪个版本。

## 做法

最小可用版本：在 workspace 根目录建 `IDENTITY.md`：

```markdown
- Name: 小钳
- Creature: 机械螃蟹，可靠、话少、直给
- Vibe: 像一个靠谱的后端同事，不寒暄，先给结论
- Emoji: 🦀
- Avatar: assets/crab.png
```

几点说明：

- **字段不用多**。五六个足够，每项一两行，宁可短而准，不要长而糊。
- **边界划清**：性格、称呼、表达风格放 `IDENTITY.md`；价值观、安全底线放 `SOUL.md`；用户个人信息放 `USER.md`。混着写迟早打架。
- **改完开新会话**（`/new` 或重启 gateway）才生效，当前会话的 system prompt 是启动时注入的。
- **用 git 管理**。身份变更和代码变更一样走提交，commit message 写清楚"为什么改"。

迭代节奏建议：改一处 → 开新会话 → 用固定的三五个问题测一下（比如让它处理一条 RAID 告警，看它是先问信息还是先给结论）→ 不符合预期就回退或再改。

## 踩坑点

- **写太长**。`IDENTITY.md` 全文进 system prompt，写成散文会稀释真正重要的指令。实测超过一屏后，风格指令反而开始失灵，一屏以内为佳。
- **形容词自相矛盾**。"简洁但温暖、严谨但活泼"这种组合，模型只能随机二选一，行为看起来像漂移，其实是提示词在打架。
- **让 agent 自己改身份且没有审计**。部分工作流里模型有 workspace 写权限，人格可能被悄悄改掉。建议身份文件由人工维护，或至少纳入 git diff review。
- **只改文件不换会话**，然后得出"不生效"的结论——这是最常见的误判。

## 可复用建议

- 把 `IDENTITY.md` 当"人格即配置"：小步提交、可回滚、有 review。
- 在 repo 里放一份固定的回归问题清单，每次改身份跑一遍。
- 多 agent 场景按 workspace 隔离，一个 workspace 一份身份，不要共用。
- 每月清理一次：删掉从未在行为中体现的描述。身份文件和代码一样会长赘肉。

## 总结

`IDENTITY.md` 的价值不在于"给 AI 起名字"的仪式感，而在于把人格从散落的 prompt 片段，收敛成一个可版本化、可 review、可回滚的文件。它很小，但它是 agent 长期行为一致性的锚点。建议从五行的最小版本开始，让 git 历史替你记录这个身份是怎么一步步长成现在这样的。
