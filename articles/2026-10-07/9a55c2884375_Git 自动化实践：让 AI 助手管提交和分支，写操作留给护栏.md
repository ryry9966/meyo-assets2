## 背景

日常开发里 Git 操作占了不小的重复劳动：写 commit message、切分支、清理合并后忘删的分支。这些事规则明确但琐碎，Agent + MCP 普及之后，很自然的想法是让 AI 助手接手。但 Git 里一半是只读操作（`status`/`diff`/`log`），一半是写操作（`commit`/`push`/`rebase`），后者出错的代价不小。这篇帖记录我在 OpenClaw 里搭的一套「AI 建议 + 脚本护栏」流程，重点是可安全复现。

## 问题

直接让 agent 跑 git，会遇到三个具体的坑：

1. **commit message 质量不稳**：模型不看完整 diff 时会编造改动，默认输出还偏「营销腔」；
2. **分支堆积**：已合并没删的、远程已 gone 的本地分支，靠人记不现实；
3. **权限失控**：agent 一次幻觉就可能在 main 上直接 commit，甚至 force push。

## 做法

思路一句话：**AI 只产出建议和清单，写操作一律过护栏。**

**第一步：收敛工具面。** 给 agent 只挂只读 Git 能力（MCP server 或 shell 白名单）：`status`、`diff`、`log`、`branch -vv`。push / rebase / reset 根本不出现在它的工具列表里。

**第二步：结构化生成 commit message。** 工作流模板固定三步：

- 先 `git diff --stat` 看规模，超过阈值就按文件拆分，避免 diff 塞爆上下文；
- 让模型输出 `type(scope): subject` 格式的 2~3 个候选，并要求每条引用 diff 中的具体改动作为依据，防幻觉；
- 人选一条，由本地脚本（不是 agent）执行 `git commit -F msgfile`。多行 message 用文件传递，绕开 shell 转义地狱。

**第三步：分支巡检定时任务。** 让 agent 每周跑 `git branch -vv` + `git branch --merged main`，产出三类清单：已合并可删 / 远程已失效 / 长期未动。我只 review 后用脚本批量删，删除动作不经过 agent。

**第四步：护栏钩子。** pre-commit 钩子里两条硬规则：当前在 main 则拒绝提交（除非显式环境变量放行）；message 不符合 Conventional Commits 正则则打回重写。push 一律 `--force-with-lease`，禁止裸 `-f`。

## 踩坑点

- **diff 超长**：一次大重构，模型只看到前 200 行，message 写得驴唇不对马嘴。改成先 `--stat` 再分块，效果立刻正常。
- **index.lock 冲突**：agent 重试时上一个 git 进程没退干净，撞锁报错。后来在包装脚本里加了进程互斥才稳。
- **「顺手」改写历史**：有次让它「整理一下提交」，它提议 interactive rebase 改最近 10 条。必须写进 prompt 明令禁止——历史改写永远人工。

## 可复用建议

1. **能力白名单优先于 prompt 约束**：删掉危险工具，比求它别用靠谱得多。
2. **沉淀成 skill / 模板**：把「生成 message」「分支巡检」封装成 OpenClaw 的可复用单元，团队不用每人调一遍 prompt。
3. **写操作留日志**：谁、何时、执行了什么，出问题能回溯。
4. **从小范围开始**：先只做 message 生成，跑稳两周再放分支清理，别一步到位。

## 总结

这套东西的本质不是「AI 替你 git」，而是把 Git 里规则明确的部分——描述、归类、巡检——交给模型，把不可逆操作留给人加钩子。跑了一个多月，commit message 规整了不少，本地堆积的 30 多个僵尸分支也清干净了。收益不算惊艳但很稳定，这正是自动化该有的样子。欢迎在评论区交流你们的护栏方案。
