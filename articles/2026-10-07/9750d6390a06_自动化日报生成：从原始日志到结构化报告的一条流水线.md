## 背景

我们团队每天要出一份运维日报：服务错误数、发布变更、告警处理进展。过去是人工打开四个面板抄数，每天固定 20-30 分钟，还经常漏项。上 Agent 之后第一反应是“让模型自己读日志写日报”。试了两周，结论是：不能直接这么做，但拆成流水线之后可以跑稳。这里给出我们最终落地的版本。

## 问题

把原始日志直接丢给 Agent，会撞上三个墙：

1. **量太大**。一天的 access log 加 error log 轻松几十万行，token 开销离谱，且远超上下文。
2. **数字不可信**。模型数数不准，让它统计 5xx 有多少条，两次运行结果能差出 10%。
3. **格式漂移**。模型自由发挥，今天一个版本明天一个版本，下游没法对比。

## 做法

核心原则一句话：**数字由代码算，模型只负责写“人话”**。

1. **采集层**：三个 source——应用日志（SSH+grep 或 HTTP 拉取）、git log（按时间窗过滤 merge/fix）、工单 API。每层只拉数据，不做判断。
2. **归一化**：所有 source 输出统一 JSON schema：`timestamp`（强制转北京时间）、`source`、`level`、`actor`、`event`、`raw_ref`。`raw_ref` 保留原始行号或链接，后面溯源用。
3. **本地聚合**：脚本做 count、去重、top-N 错误聚类。数据量从几十万行缩到几 KB，才进得动模型。
4. **Agent 层**：通过 MCP 工具把聚合后的 JSON 喂给模型，prompt 固定输出分段（概况/异常/变更/待办），温度 0.2，明确要求只基于给定数据写、没数据就写“无”。
5. **渲染与推送**：Jinja2 模板渲染 Markdown，所有数字字段由代码直接注入模板，不经过模型。推 IM webhook，同时落盘存档。

调度用 cron（Agent 定时任务也行），23:55 跑，跑完发一条心跳。心跳没来就是流水线挂了——**流水线自己也要被监控**。

## 踩坑点

- **时区**。日志是 UTC，报告按北京时间出，第一天就把早上 8 点的告警算进了昨天。归一化时在代码里强制转时区，别指望在 prompt 里写“注意时区”。
- **模型写数字**。哪怕给了数据，让模型复述总数也可能抄错。所有数字一律代码填模板，模型只写异常归因段落。
- **格式漂移靠 schema 兜底**。模型输出先过 JSON schema 校验，不过就 fallback 到纯模板版（只有数字没文案）。日报宁可不华丽，不能断。
- **静默失败**。有次工单 API 改了字段名，日报里“工单处理”整段消失但没人发现。加了两道保险：字段缺失即告警 + 每周人工抽查一次。

## 可复用建议

- **分层解耦**：采集、聚合、叙事、渲染各自独立。叙事层挂了，至少数字日报还在发。
- **一切带 raw_ref**：日报里的数字点开能跳到原始日志行，这是信任的基础，排查也快得多。
- **从一个 source 起步**：先只接应用日志，跑稳一周再加 git 和工单，别第一天上全家桶。
- **存档即数据集**：每天落盘的 JSON 攒两个月后，顺手就能出周报趋势，几乎零成本。

## 总结

日报自动化这件事，价值不在“让 AI 写作文”，而在把统计从人身上拿走。模型擅长把结构化的异常聚合成人能读的段落，不擅长的是数数和守时。让代码干代码擅长的事，Agent 只出现在它真正增值的那一层。这条流水线跑了两个月，日报没断过，人工时间归零，维护成本大约是每周十分钟看心跳加抽查。
