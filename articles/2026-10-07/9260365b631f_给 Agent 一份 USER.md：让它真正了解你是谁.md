## 背景

Agent 的会话是无状态的。每次新开会话，模型对"你是谁"的了解归零：时区、代码风格、常用工具链、能接受的风险边界，都得重讲一遍。系统提示词是开发者写的，面向所有用户；而"你这个用户"的信息，只能由你自己提供。

OpenClaw 的 workspace 机制给了我们一个很自然的位置——在工作区放一个 `USER.md`，会话启动时注入。成本几乎为零，但多数人要么没写，要么写成了一篇散文。

## 问题

不写 USER.md 的代价不是"体验差"，而是行为不可预期：

- 同一类任务，今天给 TypeScript 明天给 Python；
- 部署脚本默认 `sudo`，而你的机器上有更细的权限约定；
- 让它中文回复，它隔三差五切回英文；
- 你三月已经换了项目方向，七月它还在按旧认知给建议。

这些不是模型能力问题，是上下文缺失问题。而上下文，是你可以低成本自给的。

## 做法

核心心态：把它当作"给自己写的配置文件"，而不是自我介绍。骨架建议五段，一行一个事实：

```markdown
# USER.md
## 环境
- 时区 Asia/Shanghai；主力机 macOS，终端 zsh
## 技术偏好
- 后端 Go，前端尽量 Svelte；包管理 pnpm
## 沟通偏好
- 中文回复；先结论后展开；不确定就直说，别编
## 边界
- 不主动 git push --force；删数据前必须确认
## 当前上下文
- 在做 XX 项目，deadline 6 月底
```

三步落地：

1. 在 workspace 根目录建 `USER.md`，按骨架填 15 行以内；
2. 确认注入生效：在 AGENTS.md 里显式引用，或实际检查一次会话的 system prompt 是否包含其内容；
3. 进 git 管理，每月 diff 一次，重写"当前上下文"段落。

## 踩坑点

- **写成简历**。大段叙事模型提取困难，短句事实最有效。
- **信息过期**。换了时区没更新，Agent 会"自信地错"。宁可留空，不要留旧值。
- **塞敏感信息**。API key、手机号别放——这份文件会随每次请求发出去。
- **和项目级文件打架**。USER.md 写了 pnpm，某仓库实际用 npm 时应以项目配置为准。优先级自己定，并直接写进文件里。
- **太长**。超过一两百行，等于用自己的配置淹没任务上下文。

## 可复用建议

- 稳定信息放 USER.md，动态记忆放 Agent 的 memory 工具，别混用；
- 让 Agent 把"它推断出的关于你的事实"先追加到草稿区，你确认后再合并，避免它自作主张污染文件；
- 团队场景拆成 USER.md（个人）+ TEAM.md（共同约定），分别注入；
- 把它当 config 对待：改动走 git，review 有据可查。

## 总结

USER.md 的杠杆率极高：半小时写一份，换来的是每次会话省掉的开场白，以及明显更稳定的行为。它不会让模型变聪明，但能显著减少"聪明却用错方向"的时刻。先写起来，再迭代。
