## 背景

跑过一段时间 Agent 自动化的人都会遇到同一个困境：工具给多了怕出事，给少了 Agent 又基本废掉。在 OpenClaw 这类可挂 MCP、插件的框架里，一个 Agent 可能同时握着文件读写、shell、HTTP 请求、消息发送的权限。"敏感操作请先确认"如果只写在系统提示词里，长上下文跑几轮之后，模型一定会漂。

## 问题

判断标准模糊会导致两个极端：

- **全部要确认**：用户一天点几十次"允许"，最后变成无脑点击，确认机制名存实亡；
- **全部放行**：一条 rm、一条发到真实用户群的消息，就足够翻车。

本质上这不是提示词问题，是权限工程问题。

## 做法：按四个维度给工具分级

每次工具调用前，先看四个轴：

1. **可逆性**：能不能撤销？git 里能回滚的文件写入和删除生产表不是一个量级；
2. **影响面**：只碰 workspace，还是会出网、触达真实用户、动钱；
3. **失败代价**：搞错了要花多少时间/金钱/信任去补救；
4. **可审计性**：事后能否从日志完整还原发生了什么。

据此分四级：

- **T0 只读**（读文件、搜索、查询）：直接放行；
- **T1 可逆写**（workspace 内写文件、git 提交）：放行 + 全量日志；
- **T2 出沙箱但可沟通**（调外部 API、发消息草稿）：必须确认；
- **T3 不可逆/高危**（删数据、付款、改生产配置）：默认拒绝，需白名单显式授权。

关键一步：**分级判定放在工具调用层**（OpenClaw 的工具包装 / 网关），不放提示词里。模型可以说"我觉得这个操作很安全"，但网关不看它的意见。

确认交互也要做对：一次确认只对应一个动作，展示真实命令、diff、目标地址和回滚方式，而不是"Agent 想执行一个操作，是否允许？"

## 踩坑点

- **边界写在提示词里**：多轮之后必然漂移，必须工具层强制；
- **确认疲劳**：把 T2 攒成"执行以下 40 步？"——那不是确认，是甩锅；
- **工具名骗人**：名为 read 的工具可能有缓存写入副作用，分级要按真实副作用来；
- **批准被复用**：一次批准不能变成同类操作永久放行，批准要绑定具体参数；
- **插件继承权限**：子 Agent / 插件默认继承全套权限是常见事故源，按插件单独 scope。

## 可复用建议

- 新工具上线默认 T2，跑稳两周（有日志佐证）再考虑降级到 T1；
- 设一个"确认预算"：日均确认超过 20 次，说明分级错了，回去调；
- 每周翻一次审批日志：高频通过且零事故的操作降级，出过一次惊吓的升级；
- T2/T3 工具先接 dry-run，确保确认时看到的输出等于真实执行会做的事。

## 总结

问人的标准其实只有一条：**不可逆，或影响出了沙箱**。其余交给策略层自动放行并留痕。Agent 的自主性不是模型给的，是你的权限层设计出来的——提示词负责让 Agent 表现好，网关负责兜住它表现不好的时候。
