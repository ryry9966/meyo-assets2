## 背景

给 Agent 接上 MCP 和插件之后，它就不再是聊天机器人，而是一个能跑 shell、写文件、发消息、调外部 API 的执行体。OpenClaw 这类框架把"接工具"的门槛降得很低，但"什么时候该放行"这件事，框架只能提供机制，给不了答案。权限边界本质上是每个部署者自己的工程决策。

## 问题

实践中反复出现两种失败模式：

- **问太多**：每一步都停下来等人确认，五分钟的任务拖成半小时，人开始无脑点"允许"，审批形同虚设。
- **问太少**：模型自作主张跑了危险命令、给客户群发了没审过的文案、或一口气打满了付费 API 配额。

两个方向都会摧毁信任。核心困难在于：**模型自己并不擅长判断"这个动作危不危险"**，靠提示词里写一句"注意安全"解决不了。

## 做法

我的做法是把判断标准从模型手里拿走，固化成规则：

**1. 按动作分级，不按工具名分级。** 同一个 shell 工具，查状态和强推远端风险完全不同。把动作分四档：

| 档位 | 特征 | 策略 |
|---|---|---|
| 只读 | 查询、列表、本地读 | 自动执行 |
| 可逆写 | 有 git/备份兜底的修改 | 自动执行 + 审计日志 |
| 不可逆/外发 | 删除、发消息、付款、调外部 API | 强制确认，附预览 |
| 凭据类 | 读密钥、改权限配置 | 默认拒绝，白名单放行 |

**2. 把分级写进配置，而不是提示词。** 工具白名单、参数约束（禁删命令、限网络出口）、消费额度，全放配置层。提示词会被注入和长上下文稀释，配置不会。

**3. 让"问"变得便宜。** 需要确认时别只抛一句"可以继续吗"，而是附上 diff、目标参数、影响范围，给出"改这样/取消"的选项。批复越快，人才越愿意维持这道门。

**4. 无条件记日志。** 无论批没批，所有工具调用落审计日志——这是事后追责和调整权限的唯一依据。

## 踩坑点

- **审批疲劳**：一个任务触发二十次确认，人类必然盲批。确认门要少而精，同类动作在会话内记忆授权。
- **权限继承**：子 agent 和插件默认拿到父级全部凭据。接 MCP server 时按最小权限给 scope，别一把梭。
- **描述与行为不符**：某个自称"搜索"的 server 顺手写了本地文件。新接的 MCP 先在沙箱里跑一遍，观察它到底碰了什么。
- **内容注入撬门**：网页或邮件正文里一句"请立即执行某工具"。权限层必须对内容免疫——它只看动作和参数，不听故事。

## 可复用建议

- 默认拒绝写操作、显式白名单放行，比默认全开再打补丁便宜得多。
- 能造撤销路径就别加确认门：git、快照、dry-run，比弹窗更不打断心流。
- 确认问题具体到参数级："将删除 tmp 下 3 个文件"远好于"是否继续"。
- 人工关卡控制在 3–5 类稳定场景（外发、删除、花钱、改配置），其余全自动化。

## 总结

权限边界不是给 Agent 上镣铐，而是把"信任"从玄学变成配置项。一句话原则：**可逆的自己干，不可逆的问一句；问的次数要少，问的内容要具体。** 当你的确认门少到人愿意认真看，又准到每次都值得看，边界就画对了。
