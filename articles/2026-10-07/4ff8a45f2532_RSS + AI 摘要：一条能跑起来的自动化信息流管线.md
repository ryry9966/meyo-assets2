## 背景

订阅源越攒越多：技术博客、GitHub Release、行业 newsletter……RSS 是少数还保持开放的分发协议，但原始 feed 只解决"聚合"，不解决"读完"。我的目标很朴素：每天早上固定时间，Agent 自动抓取订阅源、逐条摘要、按重要度排序，最后推一条日报到聊天窗口，十分钟扫完当天信息。

## 管线设计

整条链路分五段，每段产物落盘，出问题能逐段定位：

1. **抓取**：订阅源用 OPML 管理，脚本定时拉 feed，原始条目存 JSON；
2. **正文提取**：多数 feed 只有 summary，用 readability 类工具回源抓全文；
3. **过滤去重**：URL 指纹去重 + 关键词黑名单，先砍掉大部分噪音；
4. **摘要**：Agent 批量调用模型，固定输出结构化字段（标题 / 一句话摘要 / 分类 / 重要度评分）；
5. **推送**：拼装成 Markdown 日报，经 OpenClaw 的 channel 推到聊天端。

调度用 OpenClaw 的定时任务跑一个 shell 入口，摘要环节走 Agent + MCP 工具调用，也可以封装成插件复用。

## 踩坑点

- **摘要空洞甚至幻觉**：只喂 summary 时模型基本在编。必须回源抓全文；抓不到就标记 skip，绝不让模型自由发挥。prompt 里显式写"仅基于给定正文输出，无信息则置空"。
- **token 成本失控**：正文截断（如前 3000 字）+ 去重先行 + 每日源数量设上限，三项做完成本基本可控。
- **输出格式不稳定**：别用正则硬解析。开 JSON mode，配 schema 校验，失败重试一次，再失败落错误日志而不是吞掉。
- **重复推送**：按条目 GUID/URL 做指纹，已推送集合落盘，重启后不重发。
- **反爬与限流**：自定义 UA、失败退避重试、记录每个源上次成功时间，长期 403 的源及时剔除。

## 可复用建议

- 中间产物全部落盘，纯文件就能 debug 整条管线，不要一上来就上数据库；
- prompt 当配置文件管理，模板与代码分离，改提示词不用发版；
- 先跑一周 dry-run（只抓取和评分、不推送），人工抽检信噪比，达标再开推送；
- 用重要度评分做闸门，低于阈值的只进归档不进日报，控制打扰感；
- 源清单保持 OPML 导入导出，随时可迁移，别被单一工具绑定。

## 总结

这套管线核心代码几百行，价值不在技术难度，而在把"信息获取"和"信息消费"解耦：RSS 保证开放可迁移，AI 负责压缩，Agent 负责调度与推送。后续打算加两件事：把播客转文字接入同一条管线，以及用自己的收藏/点击行为做反馈排序。先跑稳，再优化。
