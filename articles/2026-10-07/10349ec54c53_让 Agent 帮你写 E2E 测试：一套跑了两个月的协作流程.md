## 背景

E2E 测试的处境一直尴尬：大家都知道有价值，但写起来慢、维护起来烦。一条核心链路的用例手写往往要半天，UI 一改选择器全崩，团队最后通常只留几条冒烟用例，覆盖率长期停在"有但不敢信"的状态。

我们最近把 E2E 初稿工作交给 Agent（OpenClaw + 浏览器自动化 MCP + Playwright），跑了两个多月。结论是：可行，但前提是流程约束好。

## 问题

直接让 AI"给这个页面写个测试"，产出基本不能用，典型问题四个：

1. **选择器脆。** 模型倾向写 `div > span:nth-child(3)` 这类结构性选择器，UI 微调就挂。
2. **断言弱。** 生成的经常是"页面加载成功"这种恒真断言，看似通过，什么都没验证。
3. **幻觉 API。** 框架版本不匹配时，Agent 会若无其事地调用不存在的方法。
4. **用例重复。** 同一流程换五种姿势生成五遍，跑起来又慢又吵。

## 做法

流程分五步，核心思路：Agent 负责体力活，人负责判断"测什么、断什么"。

1. **先写测试约定文档。** 一份 markdown，写清：统一用 `data-testid`、禁止 `sleep` 固定等待、fixture 造数规范、命名规则。让 Agent 每次生成前先读它——这一步的收益比换模型大得多。
2. **让 Agent 先"逛"应用。** 通过浏览器 MCP 实际操作一遍目标流程，把真实 DOM 和交互路径带进上下文，而不是凭想象写。幻觉率显著下降。
3. **生成初稿，一流程一 PR。** 每次只生成一条流程的用例，diff 控制在可 review 的规模。
4. **人工只 review 断言。** 操作步骤（点哪、填什么）基本可以放过，重点看断言是否锁住业务结果——金额对不对、状态流转对不对，而不是按钮存在。
5. **失败回喂闭环。** 把运行器的真实产物（trace、截图路径、失败断言）喂回 Agent 让它修，而不是让它凭报错文本猜。

## 踩坑点

- **约定文档必须配 lint 强制。** 光写在文档里 Agent 偶尔会飘。我们加了一条 CI 规则：出现结构性选择器或 `sleep` 直接打回。
- **别让它一次生成全站用例。** 上下文越长质量越差，且一个坏 pattern 会被复制 N 遍。
- **MCP 工具返回要截断。** 整页 HTML 直接进上下文，token 爆炸且噪音大，只保留可交互元素摘要即可。
- **警惕"改断言迁就错误"。** Agent 修失败用例时，有概率把断言改成永远通过来"修复"测试，review 时盯紧 diff 里的断言变更。

## 可复用建议

- 约定文档 + lint + MCP 工具注入，这三件套是通用底座，不限于 E2E 场景。
- "生成"和"修复"当两个独立任务分开跑，上下文隔离，效果都更好。
- 断言的 ownership 永远在人手里，这是整套流程的底线。

## 总结

Agent 写 E2E，不是"AI 替你测"，而是"AI 消灭写用例的体力活"。约定先行、小步生成、真实报错回喂、断言人工把关——做到这四点，初稿成本大约降到原来的三分之一，后续维护成本则取决于你们的选择器纪律。建议从一条稳定的读路径（浏览类流程）开始试点，写路径（下单、支付）放后面。
