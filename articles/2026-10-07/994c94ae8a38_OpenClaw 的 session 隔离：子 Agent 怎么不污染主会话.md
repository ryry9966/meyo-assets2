## 背景

OpenClaw 里主会话是长期存在的：它绑着你的聊天渠道，历史、记忆、工具权限都在同一条线上。子 Agent 则是“临时工”——通过 `sessions_spawn` 之类的方式拉起来跑一个具体任务（并行抓取、批量处理、跑脚本），跑完就该退场。隔离机制的意义就在于：临时工的 process 留在临时工的 session 里，主会话只收结论。

## 问题

没有隔离（或隔离被绕过）时，典型的“污染"长这样：

- 子 Agent 的中间输出、工具调用全量进入主会话历史，上下文暴涨，很快触发压缩，真正重要的细节反而被压掉；
- 主会话的模型被几百行子任务日志带偏，一个简单回复决策变得犹豫；
- 多个子 Agent 交叉写入共享状态，谁覆盖谁全看运气；
- 成本失控：之后每一轮对话都背着子任务的尸体。

## 做法 / 步骤

1. **spawn 时只传任务，不传历史。** 给子 Agent 的 prompt 写清目标、输入路径、期望输出格式，不要把主会话原文整段粘进去。
2. **结果即摘要。** 子 Agent 的返回值应是它自己消化后的结论（几行到一段），主会话只注入这一条，过程留在子会话。
3. **共享状态走文件，不走会话。** 需要交接的数据让子 Agent 写到约定路径（如 `workspace/subagent/<task>.json`），主会话按需读文件，不靠聊天记录传递。
4. **每个子任务打 label、设超时。** 便于事后定位，也避免僵尸会话挂着占资源。
5. **调试看子会话本身。** 用 sessions 列表 / history 命令查看子 Agent 的独立记录，别在主会话里翻中间输出——那里本来就不该有。

一个可参考的任务描述形态（字段名以你锁定的版本为准）：

```text
task: 读取 workspace/data/urls.txt，逐条抓取标题，汇总写入 workspace/out/titles.json
label: fetch-titles-0301
timeout: 15m
```

## 踩坑点

- **变相污染**：spawn prompt 里贴了整段主会话。子会话确实隔离了，但污染通过 prompt 走了后门，效果等于没隔离。
- **记忆越权**：子 Agent 带记忆类工具权限时，顺手写了共享记忆文件，下次主会话"记住了"子任务的碎碎念。不想被记住就收窄它的工具范围。
- **并发写冲突**：多个子 Agent 写同一个输出文件。用任务名区分路径，或改成各写各的、由主会话合并。
- **版本差异**：不同版本 sessions 相关的命令与配置名略有出入，动手前先 `openclaw --help` 对一遍，别照抄旧帖。

## 可复用建议

把父子会话当成一份契约：**输入 = 任务描述，输出 = 最终结果，其余一切留在子会话内部。** 落到操作上：

- 任务描述自包含，不依赖“你刚才看到的内容"；
- 结果先自压缩再返回，大输出落文件、传路径；
- 交接走文件系统，不走会话历史；
- 每个子任务有 label 和超时，跑完清理；
- 跑批类工作单独定义一个轻量 agent 配置（更小的模型、收窄的工具集），与主会话配置解耦。

## 总结

session 隔离不是把子 Agent 藏起来，而是明确信息边界：主会话只关心“任务做完没有、结论是什么"，子 Agent 的过程细节属于它自己的 session 文件。守住这条边界，上下文长度、token 成本和模型的专注度都会稳定很多——这不是优化技巧，是跑长会话的基本功。
