## 背景

OpenClaw 的 cron 任务本质上是「定时触发的单轮 agent 调用」：到点后，系统把你写的 instruction 作为 prompt 发给 agent，跑完把结果投递到指定渠道。它没有聊天上下文，也没有人在旁边追问。大部分翻车的 cron 任务，问题不在调度本身，而在 instruction 写成了聊天消息。

## 问题

观察下来，常见失败模式有三类：

1. **依赖上下文**。写「把我上次说的那个仓库总结一下」——cron 是全新会话，agent 根本不知道「上次」是什么。
2. **时间指代模糊**。「今天」「昨天」靠 agent 猜时区，跨机器部署后行为不一致。
3. **输出失控**。没规定什么时候该说话、按什么格式说，结果每天准时收到一条「今天没有新内容」，或者长篇大论刷屏。

## 做法：把 instruction 当程序写

我的模板分六段，每段一两句：

```text
任务：<一句话说清目标>
数据源：<明确的文件路径 / 工具 / MCP server>
步骤：<3-5 步，顺序执行>
判定：<什么条件下发消息，什么条件下静默>
输出：<固定格式模板>
异常：<失败时记日志、静默、下轮重试>
```

举一个实际在跑的例子（仓库 issue 晨报）：

```text
任务：每日晨报，汇报仓库新增 issue。
数据源：gh CLI，仓库 my-org/my-repo；
       游标文件 ~/.openclaw/cron/issue-cursor.json。
步骤：1) 读游标，取上次处理的最新时间戳；
     2) 拉取 created 晚于该时间戳的 issue，上限 20 条；
     3) 只保留带 bug 或 enhancement 标签的。
判定：无新增 → 静默结束，只更新游标；有新增 → 发送。
输出：每条一行「#编号 标题（标签）」，最多 10 条，末尾注明总数。
异常：gh 报错 → 追加到 ~/logs/cron-errors.log，不发消息，下轮重试。
最后一步始终更新游标文件。
```

核心思路是三件事：**静默优先、显式状态、固定输出**。游标文件让任务天然幂等，判定段保证「没事不打扰」。

## 踩坑点

- **没跑过就上线**。先把 instruction 直接贴进会话手动跑一两次，再调成 5 分钟一次观察两轮，最后才设真实周期。
- **「自由发挥」式收尾**。不写输出格式，agent 每次的格式都不一样。模板里给死格式，效果立竿见影。
- **状态散落在对话里**。想让它「记住上次发过什么」，必须落盘到 workspace 文件，别指望会话记忆。
- **高频 + 重任务**。每 5 分钟全量扫一遍 RSS 源，一晚上烧掉的 token 够心疼。重任务降频，或改成增量游标。
- **异常路径不写**。不写失败怎么办，agent 就会即兴发挥——编数据、发道歉消息都有可能。失败就该记日志、静默、下轮重试。

## 可复用建议

1. instruction 本体保持精简，细节放 workspace 里的 spec 文件，instruction 只写「规则见 /path/spec.md」。
2. 每个任务配独立的游标/状态文件，路径写死在 instruction 里。
3. instruction 和代码一样做版本管理，改一次存一版，回滚有依据。
4. 默认静默，有事才说话——通知渠道的价值来自「响了就值得看」。

## 总结

Cron 的 instruction 不是聊天消息，是一份无人值守的作业说明。写完问自己三个问题：它知道去哪拿数据吗？它知道什么时候闭嘴吗？它失败的时候会干什么？三个问题都有明确答案，这个任务才配挂上定时器。
