## 背景

Agent 接上 MCP 和插件之后，能力从"聊天"变成了"动手"。在 OpenClaw 这类框架里，一个 agent 可能同时握着文件读写、shell、HTTP 请求、消息发送这些工具。权限边界的核心问题只有一个：**哪些动作可以直接执行，哪些必须停下来等人确认。**

这个问题靠 system prompt 里写一句"请谨慎操作"是解决不了的——它是工具层的系统设计问题。

## 问题：两个极端都不对

实践中常见两种失败模式：

- **什么都问**："要不要读取这个文件？"用户很快会变成无脑按 y，确认机制形同虚设；
- **什么都不问**：agent 自行执行删除、对外发送、付费调用，出事之后才回滚。

根因在于权限不是开关，而是一个连续谱。需要按动作本身的属性分级，而不是按"感觉危险与否"。

## 做法：可逆性 × 影响半径，四级放行

我们用两个维度给所有工具动作分类：**可逆性**（能不能撤销）和**影响半径**（只影响自己，还是影响别人）。

| 级别 | 特征 | 例子 | 策略 |
|---|---|---|---|
| Tier 0 | 只读 | 检索、读文件、沙箱计算 | 自动执行 |
| Tier 1 | 区内可逆写 | 新建文件、开分支、写草稿 | 自动执行 + 全量日志 |
| Tier 2 | 触达外部 | 调付费 API、改共享配置 | 必须确认 |
| Tier 3 | 不可逆/高影响 | 删除、发消息、部署生产、资金 | 永远问，不接受批量放行 |

落地四步：

1. **盘点工具**：把 agent 可用的全部工具（含每个 MCP server 提供的）列出来，逐个标注副作用类型；
2. **映射到策略**：在工具调用链上做 gating（tool policy / 网关层），不要写在 prompt 里——prompt 是建议，策略是强制；
3. **设计确认内容**：不能只给"是否继续 y/n"，必须带上完整动作预览：目标、参数、diff。确认的价值在上下文，不在按钮；
4. **日志 + 定期复盘**：所有放行可追溯，每周看一次记录，把高频确认且零事故的动作降级为自动。

## 踩坑点

- **确认疲劳比不确认更危险**。问得太频繁，用户会条件反射点同意，等于亲手拆掉了边界；
- **工具输出是攻击面**。agent 读了网页或文件之后，内容里可能藏着注入指令，诱导它去调写工具。只读操作也可能间接导致危险写操作，gating 必须在写工具侧，而不是在读工具侧放掉警惕；
- **白名单只膨胀不收缩**。不定期清理，半年后"临时放行"就变成了永久权限；
- **批量操作绕过逐项检查**。agent 把 100 条删除包装成一个循环，逐条确认就失去意义——批量动作整体升到 Tier 3；
- **不要默认 MCP 工具可信**。每接入一个新 server，就是引入一条新的信任边界，走默认 deny。

## 可复用建议

一句口诀：**读的自动，区内写留痕，出去的必问，删发钱永远问。**

再补三条：

- 新工具默认 deny，显式分级后再放开；
- 确认必须带预览，否则宁可不问（问了也是白问）；
- 所有自动放行都有日志，所有确认记录都可回溯。

## 总结

权限边界不是 prompt 技巧，而是工具层的系统设计。按"可逆性 × 影响半径"分级，把 gating 做在工具调用链上而不是模型提示词里，配合可审计的日志和定期升降级，agent 才敢放手干该干的事，人也只在真正关键的节点出现。

好的边界设计，目标从来不是"多问"，而是**问得少，但每一问都值得**。
