## 背景

用 Agent 做自动化一段时间后，能力会自然堆积：几个 MCP server、一堆自定义工具、若干写好的操作手册。OpenClaw 的 Skills 机制就是为这个阶段设计的——把"能力"从一次性塞进系统提示词，改成按需加载的模块。

## 问题：能力越多，上下文越脏

我们最初的做法很直接：所有工具说明、操作步骤全部写进 system prompt。结果是：

- 一次普通对话，光能力描述就占掉上万 token；
- 工具一多，模型选错工具的概率明显上升，两个功能相近的工具经常被混用；
- 改一个技能的说明，要把整份提示词重新校对一遍。

本质上这是把"能力管理"和"上下文管理"混在了一起。Skills 机制的核心就是把它们拆开：上下文里常驻的只是一份轻量索引，正文按需加载。

## 做法：三层渐进式加载

Skills 的加载分三层：

1. **元数据常驻**：每个技能只有 name + description 进入上下文，几十 token；
2. **正文按需**：模型判断命中某个技能后，才读取完整 SKILL.md；
3. **资源再按需**：技能里引用的脚本、数据文件，执行时才碰。

落地分三步。

**第一步，建目录。** 每个技能一个文件夹：

```
skills/
  log-triage/
    SKILL.md
    scripts/scan.py
```

**第二步，写 SKILL.md。** frontmatter 里的 description 是路由的唯一依据，务必写"何时触发"而不是"我有什么功能"：

```markdown
---
name: log-triage
description: 分析服务日志错误模式。当用户要求排查线上报错、
统计异常频率时使用。不适用于本地代码调试。
allowed-tools: read, bash
---
## 步骤
1. 先运行 scripts/scan.py 做频率统计
2. 对 top3 错误各给出一个归因假设
```

**第三步，验证路由。** 用三类查询做测试：应该命中的、不应该命中的、边界模糊的，逐个观察模型是否选对技能。

## 踩坑记录

- **description 写成功能清单。** "支持日志分析、支持格式转换"这种写法路由几乎必然失败。改成触发条件——"当用户粘贴大段日志并要求归因时使用"——命中率立刻上来。
- **技能之间触发范围重叠。** 我们有两个技能都能处理"数据清洗"，模型随机二选一。解法是在 description 里互相划清边界，明确写"不适用于 X"。
- **正文越写越长。** 有人把完整 SOP 都塞进 SKILL.md，一个技能两千行。正文建议控制在几百行内：确定性逻辑下沉到脚本，SKILL.md 只留指令。
- **忘了元数据本身也占上下文。** 五十个技能的 description 加起来不是小数目。建议季度性清理，删掉长期不触发的。

## 可复用建议

- 一个技能只做一件事，宁多勿大；
- description 套模板：做什么 + 何时用 + 何时不用；
- 可自动化的步骤写成脚本，SKILL.md 里只写"何时调用哪个脚本"；
- "索引 + 按需加载"这套思路同样适用于 MCP 工具收敛——工具列表太长时，先收敛再谈提示词优化，顺序别反。

## 总结

Skills 机制的本质是一次上下文经济学的取舍：用一点路由判断的开销，换取大头上下文的按需分配。它不神秘，关键就两件事——把 description 当作路由键认真写，把技能正文控制住不膨胀。做好这两点，能力堆到几十个也能保持清爽。
