## 背景

LLM 本身无状态，每次会话都从零开始。把聊天历史塞进上下文窗口只能算短期记忆，一旦换会话或超出窗口，助手就忘了你上周说过"邮件别用列表体"。对 OpenClaw 这类常驻 Agent 来说，用户的预期是"越用越懂我"，这意味着记忆必须是一个独立的、可持续维护的数据层，而不是上下文里堆出来的副产品。

## 问题：三种常见失败模式

1. **全量注入 system prompt**：偏好和聊天摘要一股脑塞进去，上下文膨胀、成本上升，无关记忆稀释关键指令，模型反而记不准。
2. **只做会话内记忆**：重启即失忆，跨项目、跨设备的偏好无法沉淀。
3. **对聊天记录做全文/向量检索**：召回大量过期信息，新旧偏好冲突时模型随机站队，用户体感"时对时错"。

根因是同一件事：记忆没有分类、没有生命周期、没有工具化。

## 做法：五步搭建

**1. 先分类，再存储。** 至少分四类：用户画像（稳定事实，如时区、语言）、偏好（风格习惯，如"回复要短"）、情节（做过什么事）、工作记忆（当前任务）。画像与偏好常驻注入，情节按需检索，工作记忆留在会话内即可。

**2. 存储选最简单的。** 起步用单个 Markdown 文件，OpenClaw 用户可以直接写一个小插件或 MCP 工具来读写，git 做版本控制。文件超过一两百行再考虑 SQLite 或向量库。可读可改的文件带来的可观测性，价值远超提前上向量检索。

**3. 写入分两条路。** 稳定事实走"提议—确认"：Agent 识别到"我以后都用 TypeScript"这类表述，生成一条记忆写入提案，用户确认才落盘。情节类走静默抽取，但必须带时间戳和来源会话 ID，方便去重与审计。

**4. 读取有预算。** 每条记忆带 `scope`（user / project / session）和 `updated_at`。会话启动时注入画像与偏好，设定 token 上限；情节类用检索补充，设相似度阈值并按时间衰减加权，宁缺毋滥。

**5. 更新靠覆盖，不靠追加。** 同一主题的新记忆替换旧条目，记录 supersede 关系；定期跑压缩合并，把"回复要短"的五个变体收敛成一条。

最后，把读写封装成 MCP 工具：`remember / recall / forget / list`。Agent 通过工具操作记忆，用户也能随时查看和手动编辑——记忆黑盒是信任杀手。

## 踩坑点

- **向量召回噪音**：embedding 会拉回八竿子打不着的旧对话。先加阈值和 rerank，不行就退回"画像常驻 + 关键词 + 时间衰减"，效果未必差。
- **新旧冲突**：只追加不覆盖，等于让模型掷硬币。supersede + 时间戳是底线。
- **记错东西**：Agent 会从歧义对话里抽出错误偏好（比如把同事的话当成你的），稳定事实必须走用户确认。
- **作用域泄漏**：项目记忆出现在私人会话里很尴尬。scope 必须在注入前由代码过滤，不要指望 prompt 提醒模型"别提"。
- **没有回归测试**：改一次写入逻辑，记忆质量会悄悄退化。攒一组"应记住 / 应召回 / 应遗忘"的用例，每次改动跑一遍。

## 可复用建议

- 记忆条目固定五个字段：`id`、`content`、`scope`、`source`、`updated_at`，克制比花哨重要。
- 所有读写打日志，排障时你会感谢自己。
- 第一版永远是"一个 Markdown 文件 + 常驻画像 + 确认式写入"，跑顺了再演进。
- 忘记和记住同样重要：提供 forget 工具，用户删得掉，才敢让它记。

## 总结

Agent 记忆本质是数据工程问题，不是模型问题。分类、生命周期、工具化、可观测性这四件事做扎实，比任何炫技的向量检索都更能让助手"真正记住你"。从最简单的方案起步，让用户看得见、改得了，记忆系统才立得住。
