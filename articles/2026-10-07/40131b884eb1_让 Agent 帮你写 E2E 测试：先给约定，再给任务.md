# 让 Agent 帮你写 E2E 测试：先给约定，再给任务

## 背景

E2E 测试大概是自动化里最不受待见的一层：写起来慢、跑起来抖、改版就红，多数团队的对策是尽量少写。Agent 工具链成熟之后，一个很自然的想法是：把页面丢给 agent，让它直接生成 Playwright 用例。我先后在两个项目里试过，结论是——**直接生成基本不可用，但调整协作方式后，agent 能承担 E2E 维护里七八成的机械劳动**。

## 问题

直接让 agent 生成测试，产出普遍有三个毛病：

- 只写 happy path，异常分支完全不管；
- 断言极弱，常常只检查"元素出现了"，功能实际坏了测试照样绿；
- 选择器来自当时渲染出的 DOM 快照，一次样式重构全线崩。

根因很简单：agent 只看到一份静态快照，它不知道应用怎么异步加载、哪些字段是业务结果、团队有什么工程约定。这不是模型能力问题，是你没给它干活所需的信息。

## 做法

我们现在的流程分四步，第三步最关键：

**1. 先给约定，再给任务。** 写一份简短的测试规范文档：强制 `data-testid` 选择器、统一用封装好的 wait 工具、禁止裸 sleep、断言必须落到业务结果（接口返回、订单号、落库状态）。这份文档每次会话放进上下文，用 MCP 的话也可以做成 resource 让 agent 按需读取。

**2. 让 agent 先"操作一遍"再写。** 别让它看截图猜行为。用 Playwright MCP 这类浏览器工具，让 agent 实际走完用户流，观察真实 DOM 结构和网络请求，再动手写。生成的用例质量立刻不一样。

**3. 自跑自修，形成闭环。** 把测试执行命令也交给 agent（一个脚本或 MCP 工具），失败的报错原样喂回去，让它迭代两三轮。agent 最有价值的不是一次生成，而是"跑挂了—看报错—修—再跑"这个循环，它做得比大多数人快。

**4. 人只审一件事：这个测试能不能挂。** 拿到产出后，故意把对应功能改坏一次，确认测试真的会红。断言语义必须人来把关，这步不能省。

## 踩坑点

- **一次生成二十条用例**：产出全是浅层重复。一次只给一个用户流，效果反而更好。
- **裸 sleep 假绿**：agent 很爱写 `waitForTimeout(3000)`。规范里明确禁掉，只允许调用统一的 wait 函数。
- **快照选择器**：agent 会顺手用运行时抓到的 class 写选择器。约定 `data-testid` 后，重构存活率高很多。
- **flaky 传染**：agent 不会犹豫，给什么环境就往里灌什么。维护一份已知 flaky 清单，写新用例前先让它读，别在抖动的环境里叠加新的不稳定。

## 可复用建议

- 那份测试规范文档是整个流程里复用价值最高的资产，比任何 prompt 模板都值钱，值得单独维护和版本化。
- 一定要让 agent 能自己执行测试。开环生成等于让实习生盲写，闭环才谈得上质量。
- 把"审断言"固化成 checklist：业务结果断言了吗？异常分支覆盖了吗？改坏功能它真的会红吗？

## 总结

Agent 在 E2E 测试里的正确分工很清楚：它负责机械部分——探索页面、写样板、修选择器、跑测试分诊失败；人负责语义部分——断言什么算对、哪些流值得测、稳定性边界在哪。流程一句话概括：**先探索、再生成、自跑自修、人审断言**。做不到闭环，agent 只是个打字快的生成器；做到了，它才是个能干活的搭档。
