## 背景

团队每天都要日报：值班要汇总服务状态，业务要跟踪关键指标，个人要回顾 agent 任务执行情况。这类事低价值但高频率，最适合交给自动化。我们的目标是：每天早上 8 点，一条结构化日报自动出现在群里，人只做审核，不做搬运。

## 问题

最初的做法很直接：写个 cron，把当天日志原样塞给 LLM，让它"总结成日报"。跑了一周就暴露三个问题：

1. **上下文爆掉**。原始日志一天几十万行，直接投喂不是截断就是费用失控。
2. **数字不可信**。LLM 算数不可靠，日报里的 QPS、错误率偶尔被"编"出来，而日报恰恰是大家最信任数字的地方。
3. **格式漂移**。同一个 prompt，今天输出表格明天输出散文，下游没法解析。

## 做法

核心思路一句话：**数据归脚本，叙述归模型**。模型只负责把算好的结构化数据写成通顺段落，不接触原始日志。

流水线分四步：

**Step 1：采集与归一化。** 定时任务把散落各处的原始日志（服务日志、agent 执行记录、MCP 工具调用流水）收敛到本地目录，统一转成 JSONL，带统一的 `timestamp / source / level / payload` 字段。纯脚本，不用模型。

**Step 2：脚本预聚合。** 一个不依赖 LLM 的聚合脚本产出中间产物：关键指标（QPS 均值/峰值、错误率、耗时分布）、异常事件列表（ERROR 及以上）、agent 任务成败统计。输出是固定 schema 的 JSON。

**Step 3：Agent 生成叙述。** 用 OpenClaw 的 agent 挂日报模板 prompt，输入就是 Step 2 的 JSON。模板里明确要求：数字只能引用输入字段，不得自行计算或推断；每节固定标题；末尾附"待人工确认"清单。

**Step 4：校验与推送。** 生成结果先过 schema 校验（字段齐不齐、数字类型对不对），再由插件推送到群。校验失败走重试，重试仍失败则推送降级版（只有原始 JSON 表格）——宁可不优雅，不能不开天窗。

## 踩坑点

- **时区**。cron 按 UTC 跑、日志按本地时间记录，导致第一版日报统计的是"昨天 16 点到今天 16 点"。归一化时强制统一为带时区的时间戳。
- **重复推送**。任务超时重试导致同一份日报发两次。给每次生成加按日期的幂等键，推送前查重。
- **幻觉数字**。即便 prompt 写了"不得计算"，模型偶尔还是会擅自求和。解法是把所有计算下沉到 Step 2，prompt 里只允许引用字段名。
- **模板改动无记录**。日报格式被随手改过几次，回溯对不上。把模板和 schema 放进版本库，改动走 PR。

## 可复用建议

1. 日报里出现数字，就别让模型算，一个都别让它算。
2. 中间产物用固定 schema 的 JSON，方便单独测试 Step 2，也方便换模型做对比。
3. 降级路径要提前设计：自动化任务的可靠性 = 正常路径 × 异常路径。
4. 先跑两周影子模式（生成但不推送），人工对照确认稳定后再上线。

## 总结

这套流水线没有用到什么高深的东西，本质是把"人肉看日志"拆成"脚本算数 + 模型说话"两段。Agent 和 MCP 解决的是连接与调度，而报告的可信度来自工程约束：schema、校验、幂等、降级。跑到现在，日报维护成本接近零，唯一需要人的地方，是每天扫一眼"待人工确认"清单——这恰好是我们想要的位置。
