## 背景

在 OpenClaw 的插件和自动化流程里，让 LLM 按约定格式输出是最常见的集成方式：插件发一段 prompt，要求模型返回 JSON，随后代码解析这份 JSON，再转给 MCP 工具或写入下游系统。

问题是，模型并不总是守约。同一个模型、同一个 prompt，输出可能是裸 JSON，可能是带 ```json 围栏的代码块，可能前后混着一句"以下是结果："，也可能混入注释和尾逗号这类宽松语法。格式漂移不是偶发 bug，而是常态，防御性解析值得单独对待。

## 问题

最朴素的做法是直接 `json.loads(response)`，它会以三种方式挂掉：

1. **围栏残留**：```json ... ``` 整段进来，loads 直接报错；
2. **混合标签**：JSON 前后夹着自然语言、小标题，甚至另一个 markdown 片段；
3. **宽松语法**：尾逗号、单引号、`//` 注释、全角引号，对话模型输出里出现率不低。

失败的表现也分两种：流程直接中断；或者更隐蔽——插件捕获异常后静默丢弃结果，你以为模型没产出，其实是解析层把它吞了。

## 做法

我们的解析层分四步，做成独立模块供所有插件复用：

**第一步：提取。** 正则优先匹配 ``` 围栏，语言标注可能是 json、jsonc、json5 甚至为空，不要写死匹配 `json`；没有围栏时，降级为取第一个 `{` 或 `[` 到最后一个 `}` 或 `]` 之间的片段。

**第二层：宽松解析。** 第一遍直接 `json.loads`；失败后做清洗——去尾逗号、全角引号换半角、剥离行注释——再试；仍失败，交给 `json_repair` 这类容错库兜底。

**第三步：校验。** 用 pydantic 或 JSON Schema 验证字段名和类型：缺字段给默认值，多余字段忽略，不允许校验层抛异常打穿流程。

**第四步：重试与留痕。** 校验失败时，把原始输出和报错信息拼进修复 prompt 让模型自纠，最多重试一到两次；无论成败，原始输出完整落日志。

## 踩坑点

- **单引号全局替换会炸内容。** 字符串值里本身含引号时，盲目 `replace("'", '"')` 会把合法 JSON 改坏。只在 loads 失败后处理，且优先用容错库。
- **贪婪截断不保险。** 如果 JSON 前的解释文字里也含大括号，"取首尾大括号"可能切错范围。围栏优先，截断只作降级路径。
- **prompt 约束不是保险。** "只输出 JSON"能降低漂移概率，但高温度或长上下文下依然会漂，prompt 和解析器必须双保险。
- **流式场景别急着解析。** 半截 JSON 必然解析失败，等流结束，或做增量括号配对。

## 可复用建议

- 解析器做成独立中间件，所有 agent 和插件走同一条链路，不要各自 `loads`；
- 优先用成熟的 `json_repair`，别把正则堆到无法维护；
- 提取、清洗、校验、重试职责分开，单测各覆盖一层；
- 收集解析失败的原始输出，定期复盘漂移模式，反过来收紧 prompt。

## 总结

LLM 输出的格式漂移无法根治，但可以驯服。核心思路八个字：**分层兜底，全程留痕**。不指望模型永远守约，而是保证它违约时，你的流程依然可控、可查、可自动修复。这层代码写一次，后面所有插件都省心。
