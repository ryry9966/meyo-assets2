# 背景

在 OpenClaw 里跑过一段时间 Cron 任务后，我的一个感受是：**定时任务的 instruction 和聊天 prompt 是两种东西**。聊天时有上下文兜底——用户在线、可以追问、错了能立刻纠正；而 Cron 是无人值守的，到点就把一段 instruction 喂给 agent 执行，跑完没人确认对不对。

很多第一版 Cron 任务都会踩同样的坑：明明只该发一条日报，群里连发三条；说“总结最近的提交”，agent 自己猜了个时间窗口；数据源挂了，任务每半小时往频道里刷一条报错。这些问题本质上都不是模型能力问题，而是 instruction 没写够。

# 问题：Cron 缺了三样东西

写聊天 prompt 可以省略的信息，Cron 任务必须自带：

- **没有会话上下文**——agent 不知道你是谁、之前聊过什么；
- **没有实时纠正**——跑偏了没人拉回来；
- **没有失败兜底的人**——出错后重试、静默、上报，全靠 instruction 里预先写好的规则。

所以判断一个 Cron instruction 合不合格，标准只有一个：**没人盯着，它能不能稳定跑对**。

# 做法：按六要素写，别按对话写

我的模板是六个要素，缺一个就大概率出事：

1. **目标**：一句话说清这个 job 干什么，一个 job 只干一件事；
2. **数据源**：读哪个路径、哪个接口，写绝对路径；
3. **时间窗口**：写“昨天 00:00–24:00”或“过去 24 小时”，禁止写“最近”“最近一些”；
4. **动作与边界**：聚合、过滤、上限（如“最多 10 条”）都写明，防止自由发挥；
5. **输出**：落到哪个文件、发到哪个通道、什么格式；
6. **异常处理**：源不可达怎么办、没数据怎么办。

一个实际的例子：

```
目标：每个工作日 09:00 生成昨日工作日报
数据源：读取 ~/notes/ 下昨天 00:00–24:00 新增的 md 文件
动作：按项目聚合要点，最多 10 条
输出：写入 ~/reports/2025-01-15.md（用实际日期）；
      仅当有内容时在 #daily 频道发一条文件链接
异常：目录不可读时重试一次，仍失败则追加一行到 ~/reports/run.log，
      不在频道发声
安静条件：没有新增文件则不输出、不通知
```

# 踩坑点

- **“帮我看看……”式开头**。聊天可以，Cron 不行——没有上下文，agent 不知道看什么、给谁看。第一句永远写目标。
- **不幂等**。按天聚合的任务手动重跑一次，就是两条重复推送。解法是用日期做 key：产物文件按日期命名，已存在则跳过。
- **状态不外置**。不要假设任务能记住上次跑到哪。上次处理的位置、已推送的 id，都写到文件或数据库里，instruction 只引用路径。
- **instruction 越改越长**。长背景、参考资料放到固定文件里，instruction 里只留路径，否则每次运行都在烧 token，改起来也乱。
- **没有运行日志**。出问题没法排查。让任务每次运行往一个 log 文件 append 一行，成本极低，收益极大。

# 可复用建议

- Cron instruction 纳入版本管理，改了什么、为什么改，有据可查；
- 新任务先设短周期（比如每 30 分钟跑一个无害动作），观察两三天行为稳定后再拉到正式周期；
- 多用“如果…则…否则…”的结构化句式，少用形容词。模糊措辞在聊天里会被上下文纠正，在 Cron 里会被直接执行。

# 总结

Cron 的 instruction 不是提示词，是一份**无人值守的小程序规格书**。六要素写全、安静默认、状态外置、幂等设计——做到这四点，我这边 Cron 任务的“惊吓”基本归零了。如果你也踩过别的坑，欢迎在评论区补充。
