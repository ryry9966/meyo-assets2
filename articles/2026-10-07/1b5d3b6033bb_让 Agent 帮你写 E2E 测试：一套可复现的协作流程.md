## 背景

E2E 测试是投入产出比最拧巴的一类：写起来慢、挂起来莫名、改版后维护成本高，团队里往往只有一两个人愿意写。过去半年我们在内部项目里尝试让 Agent 参与这件事，结论是：一句“帮我生成 E2E 测试”基本不可用，但把流程拆开、让 Agent 在每个环节做擅长的事，产出质量会明显上一个台阶。下面是我们跑通并沉淀的一套做法。

## 问题出在哪

- **选择器幻觉**：模型没见过你的页面，会编造 `data-testid` 和 class，生成一堆首跑就红的用例。
- **断言过弱**：AI 写“能通过”的测试比写“有价值”的容易得多，大量用例只检查元素存在。
- **上下文不够**：整站 DOM 塞进去又贵又丢细节。
- **缺乏维护视角**：AI 不知道哪些是核心路径、哪些是低频功能，均匀用力反而浪费。

## 我们的流程

核心思路：**让 Agent 有眼睛（真实浏览器）、有手脚（MCP 工具）、有约定（测试规范），人只卡大纲和断言两道关。**

1. **生成大纲**。让 Agent 读路由结构和核心业务代码，按用户关键路径输出测试大纲：前置状态、操作步骤、期望结果，只输出文字。人先审一遍，砍掉低价值路径。
2. **真实探路**。通过 Playwright MCP 之类的浏览器工具，让 Agent 逐条执行大纲：真实打开页面、点击、填表，记录每一步实际可用的选择器和页面快照。这一步把“猜 DOM”变成“读 DOM”。
3. **基于事实生成代码**。把探路记录连同大纲喂回去，生成 Playwright 测试代码。选择器来自真实运行，幻觉问题基本消失。
4. **失败自愈**。本地跑一遍，把报错和 trace 原样回喂给 Agent，让它自己修。限定两轮，修不好转人工。
5. **人工终审**。重点看断言：是否断在关键业务结果上（订单创建成功、状态流转），而不是停留在“元素出现了”。

## 踩过的坑

- **别一次生成全站用例**。一个页面、一条路径一次会话，质量稳定得多，上下文也干净。
- **规范要写进约定文件**（AGENTS.md 这类）：强制 `data-testid`、禁止 sleep、等待统一走 `expect` 的自动重试。Agent 会遵守，前提是你写清楚了。
- **警惕“永真”测试**：`try/catch` 包一圈、失败也放行——审断言时专门盯这个。
- **探路数据用完即弃**。页面改版后旧选择器记录就是毒药，让记录跟会话走，不留档。
- **时序问题人工兜底**。动画、懒加载导致的偶发挂，Agent 修起来容易用力过猛（到处加超时），这类直接人改。

## 可复用的建议

- 先固定选择器规范，再上 Agent，顺序不能反；
- 大纲 review 的 10 分钟比代码 review 的一小时值钱；
- 让 Agent 在“执行 → 报错 → 修复”的闭环里干活，比单向生成靠谱；
- MCP 浏览器工具是关键，没有“眼睛”的生成都是猜。

## 总结

这套流程跑下来，E2E 用例从 12 条涨到 60+，新增一条核心路径的测试从半天缩到 20 分钟左右。AI 没有取代测试设计——哪些路径值得测、断言断在哪，仍需要人来判断；它取代的是重复、机械、易错的环节。Agent 协作的关键从来不是“放手让它干”，而是把人的判断放在正确的卡点上。
