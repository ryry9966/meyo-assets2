## 背景

做 Agent 和自动化的人迟早会遇到这个问题：工作流一天跑几百次调用，云 API 账单越来越难看；或者任务涉及私有代码、内部日志，不方便往外送。这时候"本地跑一个模型当廉价执行器"就从玩具需求变成了工程需求。这篇笔记记录我在一台 32GB 内存 + 8GB 显存的机器上，把本地模型接入 OpenClaw 工作流的完整过程。

## 问题

本地部署的宣传和现实之间有三道沟：

1. **硬件门槛被低估**。跑得动和跑得好用是两回事，7B 模型谁都能跑，但让它稳定完成工具调用是另一回事。
2. **上下文配置容易被忽略**。很多推理框架默认 2K~4K 上下文，Agent 场景下长对话很快"失忆"。
3. **小模型的 function calling 不稳定**。榜单分高不代表你的 MCP 工具链它能用。

## 做法

**第一步：按内存选模型，而不是按榜单。**
8GB 显存选 7B/8B 的 Q4 量化；16GB 显存可以上 14B；想跑 32B 至少要 24GB 显存或大内存 + 接受慢速。我的经验是：优先选工具调用经过专门训练的模型系列（如 Qwen 系列的 instruct 版本），参数量可以妥协，工具调用能力不能。

**第二步：用 Ollama 或 llama.cpp 起服务。**
两者都暴露 OpenAI 兼容接口。llama.cpp 的 `llama-server` 更可控，适合精确调参；Ollama 更省心，适合快速验证。建议先 Ollama 跑通，再决定要不要迁到 llama.cpp。

**第三步：改掉默认参数，这三项最关键：**

```bash
ollama run qwen2.5:14b
# 或启动时显式指定
OLLAMA_CONTEXT_LENGTH=16384 ollama serve
```

- `num_ctx`：Agent 场景建议 16K 起步，注意 KV cache 会随上下文线性吃显存；
- `temperature`：涉及结构化输出（JSON 工具调用）的自动化任务，压到 0.2~0.4；
- GPU offload 层数：显存不够时框架会自动把部分层放 CPU，速度会断崖式下跌，宁可换小一号的模型全量进显存。

**第四步：接入 OpenClaw。**
把模型配置里的 `base_url` 指向 `http://localhost:11434/v1`，模型名填本地标签。如果你的 Agent 框架要求特定的工具调用格式，先跑一个最小用例：一个 MCP 工具、一条指令，确认模型能返回可解析的工具调用 JSON。

**第五步：用真实工作流做冒烟测试。**
不要只测"你好"这种对话，直接跑一条带 2~3 个 MCP 工具的完整链路，观察：调用是否触发、参数是否正确、失败后会不会重试死循环。

## 踩坑点

- **上下文忘改**：默认 2K 上下文，Agent 跑到第三轮就开始丢系统提示，表现是"突然忘了自己的任务"。这是最高频的坑。
- **工具调用格式漂移**：小模型偶尔输出带注释的 JSON 或多余字段，解析直接失败。缓解办法是 Agent 侧加一层宽容解析 + 一次重试。
- **显存假象**：模型权重加载进去了，但推理时 KV cache 一涨就 OOM。留 20% 余量。
- **并发为零**：本地单卡就是单队列，Agent 并行分支会排队。设计工作流时把本地模型当串行资源。

## 可复用建议

1. **混合路由比全本地更务实**：敏感任务和廉价重复任务走本地，复杂推理走云 API，在 Agent 的路由层按任务类型分流。
2. **用自己的工作流 benchmark**：准备 10 条真实任务的测试集，换模型时跑一遍对比成功率和耗时，比看榜单有用得多。
3. **固定版本 + 记录配置**：模型标签、量化版本、上下文参数写成配置文件进版本库，避免"上次能跑这次不行"。

## 总结

家用电脑跑大模型，2025 年已经不是能不能的问题，而是值不值的问题。结论是：作为 Agent 工作流里的"廉价执行器"和隐私兜底，本地模型已经完全可用；但要做对三件事——选对量化档位、改掉默认上下文、用真实工具链验证调用能力。先跑通一条最小链路，再逐步扩大它的职责范围，比一上来就追求"完全离线"靠谱得多。
