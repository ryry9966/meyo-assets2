## 背景

Agent 本身只会推理，真正干活靠的是外部能力。一个只会对话的 Agent 价值有限；接上工单系统、数据库、IM 通知之后，它才从"会说"变成"会做"。在 OpenClaw 生态里，对接外部服务主要有两条路：**MCP server**（标准协议，工具复用性好）和**原生插件/自定义 tool**（灵活，但 schema 要自己管）。这篇帖整理一次真实对接过程的做法和教训，供复用。

## 问题

对接时最常撞到四类问题：

1. **鉴权散落各处**：token 写死在配置里，泄露风险高，轮换还得改代码；
2. **工具描述含糊**：模型不知道何时该调、参数怎么填，要么不调要么乱调；
3. **网络不老实**：超时、限流、5xx 是常态，没有重试策略的对接上线第一天就会挂；
4. **返回值失控**：第三方接口一次回吐几十 KB 的 JSON，直接塞进上下文，几轮就把 token 吃光。

## 做法

我们的对接流程固定成五步：

**第一步：收敛工具面。** 不要把第三方 API 的每个 endpoint 都包成工具。先问一句"Agent 到底要完成什么任务"，通常 3–5 个高内聚的工具就够。比如对接工单系统，只需要"查单 / 建单 / 回复"三个，其余留给人工。

**第二步：写清楚的 schema 和描述。** 工具描述是写给模型看的文档。参数要说明格式（日期是 `YYYY-MM-DD` 还是时间戳）、必填项和典型示例。描述写得好，调试时间能省一半。

**第三步：鉴权集中在适配层。** token 走环境变量或密钥管理，插件只读引用；带过期时间的凭据在适配层统一刷新，工具函数里永远不碰原始密钥。

**第四步：统一错误与重试。** 在适配层包一层：超时设短（10 秒级）、指数退避重试、限流识别（429 读 Retry-After）。关键是把失败翻译成模型能理解的一句话返回，比如"服务暂不可用，已重试 3 次"，而不是把原始 stack trace 抛回去。

**第五步：裁剪返回值。** 工具层只返回任务需要的字段，大结果做摘要或分页。宁可多调一次，不要一次灌爆上下文。

## 踩坑点

- **写操作重试没带幂等键**：建单、下单类接口重试就是重复数据。写操作务必带 idempotency key，或在工具层先查再写；
- **长任务用同步调用**：导报表跑了 3 分钟，Agent 循环整个卡死。改成"提交任务 + 轮询状态"，工具秒回；
- **描述与实现不同步**：改了接口忘了改描述，模型按旧文档调用，报错极其迷惑。把描述当代码对待，进 review；
- **错误被吞掉**：适配层 catch 之后返回空结果，模型以为成功，继续往下走。失败必须显式告知。

## 可复用建议

- 工具粒度对齐**任务**，而不是对齐 API 文档；
- 鉴权、重试、裁剪三件事全放适配层，工具函数保持"薄"；
- 每个写操作工具都想清楚幂等方案；
- 上线前用固定的测试 prompt 跑一遍调用链，记录 token 消耗做基线；
- 日志同时记"模型想干什么"和"实际发生了什么"，排障时这两条对不上的地方就是 bug。

## 总结

对接外部服务本质上是一次协议设计：OpenClaw 这边是模型的推理习惯，那边是服务的工程约束，适配层就是翻译官。工具面收敛、描述清晰、失败可表达——这三点做到位，大部分问题在上线前就能消掉。剩下的，交给日志和监控。
