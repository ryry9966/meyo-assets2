## 背景

Agent 的价值不在于会聊天，而在于能动手。OpenClaw 里的 agent 要查库存、发工单、拉报表，最终都要落到「调外部 API」这一步。模型本身没有网络权限，真正干活的是你注册给它的工具层——MCP server、自定义插件或脚本。这一层设计得好不好，直接决定 agent 是可靠助手还是随机故障源。

## 常见问题

实践中反复出现三类翻车：

1. **鉴权混乱**：API key 硬编码在插件里，或被打进 system prompt，随日志和对话记录外泄。
2. **工具描述含糊**：模型猜参数，猜错就重试，重试还错，最后输出一坨看似合理的数据。
3. **没有防护**：无超时、无重试上限，一个挂起的下游服务能让整个会话卡死。

## 做法

按下面的顺序接一个外部服务，基本能一次跑通：

**1. 先盘 API，再写代码。** 确认鉴权方式（Header key / OAuth）、限流阈值、写接口是否幂等。这三件事记下来，后面每一步都依赖它。

**2. 选集成路径。** 标准化程度高、想复用给多个 agent 的服务，用 MCP server；只有内部一个 agent 用、且想精细控制错误处理的，写 OpenClaw 插件更省事。不要为了 MCP 而 MCP。

**3. 控制工具粒度。** 一个服务暴露 3~5 个粗粒度工具，好过 20 个细碎工具。描述里写清「什么时候该用我、参数单位是什么、哪些值不允许」，例如：status 只接受 open/closed，不要传数字。

**4. 鉴权走环境变量或密钥存储。** 插件启动时读取，绝不进 prompt、不进代码库、不进日志。

**5. 加防护栏。** 每次调用设 5~10 秒超时；网络错误指数退避重试，最多 3 次；写操作带幂等键；对可访问域名做白名单。

**6. 收敛返回值。** 下游返回 50KB 的 JSON 不要原样塞回上下文，先过滤、截断，只留模型做决策需要的字段。

## 踩坑点

- **重试了不该重试的请求**：POST 下单没有幂等键，超时后重试，用户收到两单。写操作要么幂等，要么只允许人工确认后重发。
- **工具太多**：注册 30 个工具后模型开始选错，把两个工具的参数混着传。合并工具，精简到一屏能看完。
- **错误信息直接透传**：把下游堆栈原文丢给模型，它会拿错误当数据处理。应返回结构化的 `{ok: false, reason: "..."}`，让模型能判断该重试还是该上报用户。
- **日志打印完整请求头**：Authorization header 进了日志系统，等于密钥泄露。日志层务必脱敏。

## 可复用建议

接新服务前过一遍这张清单：

- [ ] 鉴权方式、限流、幂等性已确认
- [ ] 工具描述包含使用时机 + 参数约束
- [ ] 超时、重试上限、退避策略已配置
- [ ] 密钥走环境变量，日志已脱敏
- [ ] 大响应已做裁剪
- [ ] 写操作有确认或幂等机制

另外，给每个外部调用打 trace ID。agent 说「我做过了」和你能在日志里查到，是两回事。

## 总结

对接外部服务本质是个工程问题，不是提示词问题。工具层做得干净——鉴权收敛、描述明确、防护齐全——模型的调用准确率会自然上来；反过来，靠在 system prompt 里反复叮嘱模型「小心点」，兜不住底层的故障。先把手上的工具层按清单过一遍，比急着接下一个服务更值。
