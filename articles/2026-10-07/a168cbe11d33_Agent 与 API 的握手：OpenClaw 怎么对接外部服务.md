## 背景

Agent 的实际能力上限，往往不是模型智商决定的，而是它能稳定调用哪些工具决定的。在 OpenClaw 里对接外部服务，常见有三条路径：让模型直接发 HTTP 请求、挂一个 MCP server、写原生插件。这篇帖子记录我给 OpenClaw 接几个第三方 API 时的选型逻辑和踩坑实录，给有同样需求的邻居省点时间。

## 问题

动手前先想清楚三个典型问题：

1. **模型会“以为自己会调 API"**——没有注册成工具的接口，它只能靠幻觉拼参数，看起来调了，实际什么都没发生；
2. **密钥放哪**——放错位置要么不安全，要么污染上下文；
3. **失败不可控**——接口超时或限流时，Agent 没有重试意识，一步失败，整条任务链报废。

## 做法

**1. 先选对接方式，别急着写代码**

- 只有一两个简单只读接口：注册成轻量 HTTP 工具，成本最低；
- 接口多、参数复杂、还想复用给其他 Agent：封装成 MCP server，一次封装处处可用；
- 需要常驻进程、监听事件、跑长任务：走插件机制，别硬塞给 MCP。

**2. 工具描述是写给模型看的文档**

description 里写清楚"什么时候该用、参数含义、返回什么"，参数必须带类型和约束。实测一个模糊的 description，会让模型在两个相似工具之间乱选，报错后又反复重试，白白烧 token。

**3. 鉴权与配置分离**

密钥走环境变量或配置层，不进系统提示词、不进对话上下文、不打进日志。工具内部读配置完成鉴权，模型只看到"调用成功/失败"，永远接触不到原始凭据。

**4. 防御性设计三件套：超时、重试、裁剪**

- 每个工具调用设明确超时，超时返回结构化错误，而不是干等着；
- 网络类错误做 2~3 次指数退避重试：5xx 和超时才重试，4xx 直接报错；
- 返回体做字段裁剪和分页，别让一个大 JSON 把上下文撑爆。

**5. 先只读，再放开写**

任何对接先跑只读版本冒烟：让 Agent 查一次真实数据，对着工具调用日志核对参数对不对，确认无误后再放开写操作。写操作务必加人工确认环节。

## 踩坑点

- **相似工具必选错**：两个功能相近的工具，模型经常选错。解法不是加更多说明，而是合并成一个带 mode 参数的工具；
- **MCP 进程静默挂掉**：stdio 传输下 server 崩了要能被拉起，否则整场会话工具全失效，外在表现是模型"突然变笨"；
- **时间是重灾区**：接口要 UTC、模型给本地时间，提前在工具描述里锁死格式和时区；
- **错误信息要可行动**：别只回一个 `error`，要回模型能读懂、能指导下一步动作的结构化信息。

## 可复用建议

- 工具宁少而准：一个 Agent 挂 30 个工具的调用准确率，远低于 8 个；
- 保留调用日志（时间、参数摘要、耗时、结果码），排查时能回放；
- 把鉴权、超时、重试做成统一的工具基类或模板，新接口只填业务逻辑；
- 接口变更时优先改 description 和参数 schema，尽量不动调用代码。

## 总结

Agent 与 API 的握手，本质是把 HTTP 接口翻译成"模型能正确使用的工具语言"。工程重心就三件事：**描述写准、凭据隔离、失败可控**。把这三件做扎实，OpenClaw 对接外部服务就从碰运气，变成可复制的标准动作。欢迎在社区帖里补充你们遇到的其他坑。
