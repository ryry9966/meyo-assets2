## 背景

Agent 脱离外部服务时，只是个会聊天的盒子。真正让它有生产力的，是"能动手"：查库存、建工单、触发内部系统。在 OpenClaw 的体系里，对接路径主要有三条：MCP server、原生 HTTP 工具、社区插件。这篇帖记录我最近给一个内部系统做对接的完整过程，重点是那些文档里不会写的部分。

## 问题

对接时卡人的从来不是"能不能调通"，而是三件事：

- **认证不统一**：有的服务用 Bearer token，有的要 HMAC 签名，还有的得先换临时 ticket，有效期还短；
- **返回体不可控**：一个接口吐回 20KB 的 JSON，模型真正需要的只有三个字段；
- **模型选错工具或传错参数**：根源多半不在模型，而在工具描述和 schema 写得糊。

## 做法

我分四步走，每步验证通过才进下一步：

1. **手动跑通目标 API**。用 curl 把认证、限流、分页行为摸清。别指望 agent 帮你探索 API，那是浪费 token。
2. **写一层薄封装**。每个工具只做一件事，输入输出用严格 schema 约束。比如"创建工单"只收 `title`、`priority`、`body`，多余参数直接拒。
3. **裁剪响应**。封装层把原始 JSON 压成最小结构，分页只回首页加 total，避免上下文被撑爆。
4. **挂进 OpenClaw 跑真实任务**，盯调用日志：模型是否在正确场景选中该工具、参数有没有幻觉。发现描述不清晰就改 description，通常比改系统提示词管用。

## 踩坑点

- description 写成 API 文档腔，模型反而不敢调。用"任务语言"写清楚**什么时候该用、什么时候不该用**，效果立竿见影。
- 没设超时和重试上限，一次网络抖动让 agent 卡死整轮会话。超时 10 秒、重试 2 次加指数退避，是我现在的默认值。
- secret 泄进了工具报错信息，跟着进了对话历史。封装层必须做脱敏，这步不能省。
- 限流没处理，批量任务跑一半全 429。退避逻辑要下沉到封装层统一做，别指望模型自己会"等一下"。

## 可复用建议

- 认证、重试、脱敏、响应裁剪全部下沉到封装层，工具函数本身保持"傻瓜化"。
- 一类操作一个工具，别做万能接口。模型面对 `do_something(action, params)` 这类结构时，参数错误率明显上升。
- 工具描述按模型视角写，不按后端视角写。
- 日志落盘并带请求 ID，出问题时能回放完整链路，排查效率差一个量级。

## 总结

Agent 对接外部服务，九成工程量在封装层和描述层，一成才在"调通 API"。把脏活累活挡在模型看不见的地方，这次握手才算握稳。有类似实践欢迎在评论区交流。
