## 背景

RSS 没死，只是退到了工具层。它的问题从来不是"过时"，而是订阅源一多，未读列表比天气还让人焦虑。过去我们靠规则过滤，现在多了一个选项：让 LLM 当第一读者。这篇记录我用 OpenClaw 定时任务加一套拉取脚本搭的摘要管线，目标是每天早上收到一份不超过 20 条的摘要，其余沉到归档里。

## 问题

- 订阅源 60+，每天新增条目 300~500，人工筛选成本太高
- 全文逐条丢给 LLM 总结，token 成本和延迟都不划算
- 摘要容易写成"正确但无用"的废话，比如"这篇文章讨论了 XX"

## 做法

管线分四层，各自独立：

1. **拉取层**：feedparser 定时拉 RSS，按 GUID + 链接去重，写入本地 SQLite。只存标题、链接、summary 和首段截断的正文，不存全文——控制成本的第一步。不想写脚本的话，拉取层也可以换成现成的 RSS 类 MCP 工具，接口一致即可。
2. **粗筛层**：规则先行。关键词黑名单（"招聘""活动回顾"之类）直接打标跳过，能砍掉约 30% 的量。
3. **摘要层**：不逐条调用，把粗筛后的 20~30 条打包成一次请求，要求输出结构化结果：每条一行标题 + 一句话摘要 + 相关度评分（1~5）。用便宜的小模型跑。
4. **交付层**：按评分排序，4 分以上进当日摘要，渲染成 Markdown 推送到频道；其余写归档文件，周末人工抽查，顺便校准评分。

调度用 OpenClaw 定时任务触发，各层通过 SQLite 解耦，任何一层挂了重跑即可，不会重复推送。

## 踩坑点

- 只拿 RSS 的 summary 字段总结，很多源只给标题或截断文本，模型会脑补。对策：正文过短的条目标记"仅标题参考"，不生成摘要。
- 打包摘要的 prompt 必须明确"只依据给定文本"，否则偶尔会出现条目里没有的结论。上线前用一批旧条目做过对照检查。
- 相关度评分前期很不稳定，同一篇在不同批次里 3 分和 5 分摇摆。把评分标准和几个锚点示例写进 prompt 后才收敛。
- 有个源的 pubDate 全是当前时间，去重全靠 GUID。遇到奇葩源别信时间戳。
- 一次性推太长的摘要在移动端没人看，控制条数比控制字数更有效。

## 可复用建议

- **先规则后模型**：能用关键词、来源权重解决的别上 LLM，省钱也稳定。
- **结构化输出 + 本地落库**：中间产物可回放、可审计，prompt 调坏了也不丢数据。
- **评分标准要迭代**：每月抽样核对评分与实际价值的偏差，管线是养出来的，不是搭完就完。
- **从小源池起步**：先跑两周再加源，否则调 prompt 时噪音太大。

## 总结

整套管线不到 200 行代码，每天成本几毛钱，换来的是把信息筛选从半小时压到五分钟。它不会替你读文章，但能把"该看哪几篇"这个决策做得很便宜。RSS 在这里的角色是稳定、可控、可归档的输入源——这恰恰是算法推荐流给不了的。
