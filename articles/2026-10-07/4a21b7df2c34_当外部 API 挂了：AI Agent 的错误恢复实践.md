## 背景

Agent 落地到生产环境后，外部依赖远比想象中脆弱：LLM 供应商限流、MCP server 超时、第三方 SaaS 偶发 5xx、API key 过期。开发时一次成功跑通的链路，放到自动化场景里每天执行几百次，任何一环都可能出问题。错误恢复不是可选项，而是 Agent 工程的必答题。

## 问题：三种典型的错误姿势

1. **一失败就整体终止**：任务跑到一半断掉，前面的工作全部作废。
2. **盲目重试**：没有退避、没有上限，遇到 429 还在猛打请求，把限流变成封禁，甚至制造重试风暴。
3. **错误被吞掉**：HTTP 状态码 200，但错误信息藏在响应体里，Agent 以为成功了，拿着空数据继续往下走，产出完全错误的结果。

## 做法：把恢复拆成四层

**第一层：错误分类。** 在统一的客户端封装里，把错误分成可重试（429、5xx、超时）和不可重试（400、401、403、参数错误）。不可重试的错误直接上抛，不要浪费重试次数。

**第二层：受控重试。** 指数退避加抖动（jitter），初始 1 秒，上限 5 次；优先读取响应里的 Retry-After。重试上限不是性能参数，是止损参数。

**第三层：熔断与降级。** 连续失败 N 次后熔断，冷却期内不再请求，切换到备选方案：备用供应商、缓存结果，或把任务入队等恢复后补偿执行。Agent 层面可以给模型一个结构化的错误对象（是否可重试、建议动作），允许它换工具绕路，但必须设硬预算——时间、token、重试次数的上限放在代码层，防止模型陷入无限循环烧钱。

**第四层：断点续跑。** 每完成一个工具调用就持久化一次状态。恢复时不重跑整个任务，只从断点继续。这一层要求写操作幂等：用幂等键或"先查再写"，避免重试导致重复下单、重复发通知。

## 踩坑点

- **非幂等操作裸重试**：支付、发消息这类调用，重试前必须确认副作用是否已发生。
- **超时配置错位**：客户端超时比服务端处理时间还短，或者 MCP server 默认超时把长任务静默杀掉，日志里只看到连接断开。
- **200 不等于成功**：务必校验响应体和业务码，很多错误藏在正常状态码下面。
- **把重试决策全交给模型**：LLM 对"再试一次"有天然的执念，约束必须代码化，不能靠 prompt 自觉。
- **重启即重来**：没有 checkpoint，一次崩溃等于全部工作量清零。

## 可复用建议

1. 所有外部调用收敛到一个统一的弹性客户端层，重试、超时、日志只写一处。
2. 每个任务带 trace ID，熔断触发时主动告警，而不是等用户反馈。
3. 用故障注入做测试：mock 出 429 和 500 验证恢复路径，别只测 happy path。
4. 降级链路提前设计好：主服务 → 备用 → 入队 → 人工介入，而不是临场发挥。

## 总结

外部 API 挂掉是常态而不是异常。Agent 的可靠性不取决于成功率多高，而取决于失败后能不能被控地重试、优雅地降级、完整地续跑。把这四层做进基础设施里，Agent 才敢放到无人值守的场景去跑。
