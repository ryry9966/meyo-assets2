## 背景

E2E 测试一直是工程团队最想自动化、又最不想维护的部分：用例多、选择器易碎、环境抖动频繁，写的人嫌烦，改的人头疼。最近我们在几个内部项目里尝试了一套流程：让 Agent 挂上浏览器操作工具（Playwright MCP 一类的能力），亲自"打开页面—探索—写用例—跑测试—读失败报告—修复"，把人从样板代码里解放出来，只负责业务断言的把关。

## 问题：一次性生成基本不可用

直接把需求文档丢给模型说"帮我写 E2E"，通常得到三种结果：

- **选择器靠猜**：`div:nth-child(3) > button` 这类东西，跑一次挂一次；
- **断言过弱**：只验证"元素可见"，测不出任何业务逻辑；
- **数量失控**：一口气生成几十个用例，CI 直接红成一片。

根源在于模型没有真实页面上下文，只是按"测试大概长什么样"在补全。所以关键不是提示词写得多精致，而是让 Agent 先动手，再动笔。

## 做法：四步闭环

**1. 给 Agent 挂浏览器工具。** 让它能 navigate、点击、填表、截图。先以"探索者"身份走一遍关键路径，顺手记录每一步的实际 DOM 结构和接口行为。

**2. 用项目规则约束输出。** 在仓库规则文件里写死约定：

```text
- 框架固定：Playwright + TypeScript
- 选择器优先级：data-testid > role，禁止长链 CSS 层级
- 禁止硬编码 sleep，统一依赖 expect(...).toBeVisible() 自动等待
- 每轮最多新增 3~5 个用例，本地跑绿后才允许提交
```

**3. 让 Agent 自己跑、自己修。** 失败时把 trace 和报错喂回去，由它判断是选择器问题、等待问题还是真实 bug。这个循环一般两三轮收敛。

**4. 人只审断言。** 业务是否被正确验证、异常分支是否覆盖，仍然人来拍板。Agent 提 PR，走正常 code review 合入。

## 踩坑点

- **Agent 悄悄改业务代码让测试变绿。** 必须做权限隔离：测试目录可写，业务代码只读。
- **探索产物丢失。** 每轮探索的页面结构、截图要落盘存档，否则换个会话就从零开始。
- **弱断言堆积。** 我们加了一条人工检查线：每个用例至少一个"业务结果级"断言（订单状态、返回值、落库数据），只查可见性的直接打回。
- **环境抖动被掩盖。** Agent 倾向用重试掩盖 flaky，重试次数写死为 1，flaky 必须修根因。
- **单会话上下文不够。** 大系统按模块拆任务，一次只啃一个子域。

## 可复用建议

- 把测试规范沉淀为仓库里的规则文件，Agent 的输出质量取决于约束是否具体；
- 按"关键路径优先"排任务：登录、下单、支付这类主干流程收益最大；
- 失败报告（trace、截图、网络日志）是 Agent 最有效的输入，比自然语言描述好用得多；
- 把 Agent 产出当草稿而非成品，合并门槛与人工测试保持一致。

## 总结

这套流程跑下来，用例编写成本明显下降（内部体感在一半以上），Review 负担没有明显增加。核心经验一句话：不要让 Agent"写测试"，而是让它"操作真实系统，并把观察固化成测试"，人负责定义什么算对。具体工具会换，这个分工逻辑是可迁移的。
