## 背景

作为 OpenClaw 用户，我的大部分自动化流程原本都挂在云端 API 上。三个痛点促使我把一部分负载搬回本地：一是定时任务和数据整理要接触个人隐私数据，全走云端不太放心；二是 7×24 常驻 Agent，API 账单按月涨；三是断网时整条自动化链路直接瘫痪。结论先行：本地模型不需要“更强”，只需要“够用、常在、便宜”。

## 问题

动手前先想清楚三个问题：

1. 我这张卡到底能塞下多大的模型？
2. 量化到什么程度，质量还够 Agent 用？
3. 小模型能不能稳定完成工具调用？

第三个问题最容易被低估，后面细说。

## 做法

**1. 算显存预算。** 粗略公式：`参数量 × 每参数字节数 + KV cache`。Q4_K_M 量化约每参数 4.5~5 字节，14B 模型权重约 9GB，再留 2~4GB 给上下文，一张 12GB 卡刚好。想跑 32B，请直接按 24GB 卡规划。

**2. 选运行时。** 家用场景 Ollama 上手最快；llama.cpp 更可控，可精细调 KV cache 量化；vLLM 并发好但吃显存。我先跑通 Ollama，需要细调再下沉。

**3. 选模型。** 优先挑官方声明支持 tool calling 的 instruct 模型；中文场景 Qwen 系列性价比不错。从 7B/14B 起步，别一上来就追 32B。

**4. 接入 OpenClaw。** Ollama 自带 OpenAI 兼容接口，在 OpenClaw 的模型配置里加一个 provider 指到 `http://localhost:11434`，先跑最小 Agent 循环（单轮对话 + 一个工具），通了再逐个挂 MCP 工具。这一步的关键是先验证工具调用，再谈别的。

**5. 建回归集。** 从自己真实的自动化任务里抽 20 条典型输入存成文件，每次换模型、换量化版本都跑一遍对比。这比任何公开榜单都贴近你的真实体验。

## 踩坑点

- **小模型工具调用不稳。** 7B 模型两步以上的工具链就会丢参数、编造不存在的工具名，甚至输出非法 JSON。工具调用质量是选型的第一门槛，不是推理能力。
- **上下文长度吃显存。** KV cache 随 context 线性增长，8k 拉到 32k 可能直接 OOM。Agent 加 MCP 工具的系统提示词本来就长，务必实测，别按纸面参数推算。
- **并发排队。** Agent 会并行发请求，单卡推理排队后看起来像“卡死”，实际是在等。降低并发或加队列超时。
- **量化别太狠。** Q4_K_M 是甜点；Q2 以下工具调用基本残废，省下的显存不值得。
- **采样参数。** Agent 任务温度给低（0.1~0.3），高温度会放大 JSON 格式错误率。

## 可复用建议

1. **做路由而不是二选一**：简单任务（摘要、分类、格式化）走本地，复杂推理回落云端，OpenClaw 侧按任务配不同模型即可。
2. **模型配置进版本库**：模型 tag、量化版本、context 长度、采样参数全部记录，回滚和复现有据可查。
3. **显存留 15% 余量**给 KV cache 和系统，跑满必炸。
4. **一切以自己的回归集为准**，别信“跑分换算”。

## 总结

本地 LLM 不会替代云端模型做难题，但在自动化、隐私敏感、离线这三类场景里已经完全可用。真正的工程量不在“把它跑起来”，而在“让它稳定地待在 Agent 循环里”：显存预算、工具调用验证、回归评测——这三件事做扎实，家用电脑就能长期当一个可靠的推理节点。
