## 背景

RSS 解决的是“聚”的问题，没解决“读”的问题。订阅源一多，一天几百条进来，人肉扫标题不现实。LLM 摘要听起来是解药，但直接“把 feed 扔给模型”很快会撞上三个问题：正文截断、重复推送、token 成本失控。这篇记录我在 OpenClaw 里跑了几个月的一条管线，重点聊模型之外的部分——那才是决定它能不能活下去的东西。

## 问题拆解

一条可长期运行的管线，先满足三个硬条件：

- **幂等**：同一篇文章只处理一次，管线重跑不重复推送
- **便宜**：抓取、过滤阶段几乎零成本，只有进入摘要环节的条目才花 token
- **可诊断**：每次跑完知道抓了多少、滤了多少、发了多少

## 做法：五个环节

1. **源管理**。源列表放一个 YAML 配置，每项带 tag（daily / weekly）决定推送节奏。原生 RSS 直接用，不提供的走 RSSHub 补。
2. **定时抓取**。用 OpenClaw 的 cron 任务触发一个 skill，只解析 XML 拿 title / link / guid，这一步不碰正文。也可以把抓取封装成 MCP tool，让 agent 在会话里按需调用，两套入口共享同一份去重状态。
3. **去重**。本地 SQLite 存已处理条目的 hash。主键用“link 去掉 UTM 参数后的规范化结果”，title hash 做兜底——有些源的 guid 根本不稳定。
4. **摘要**。去重后的条目分批（10–20 条/批）交给模型，结构化输出。超过 2000 字符截断。两阶段设计：先用便宜模型做 worth_click 初筛，标记为高价值的才用主力模型细摘。
5. **推送**。digest 按 tag 聚合成一条消息，走 OpenClaw 已接入的通道发出，同时落一份 Markdown 归档。

实际在用的摘要 prompt 骨架：

```
你是信息流编辑。对以下条目各输出：
- summary: 一句话中文摘要，只基于给定内容，禁止推测
- worth_click: true/false，是否值得点开原文
内容不足以判断时，summary 输出 "信息不足"
```

## 踩坑点

- **feed 里只有前 200 字**。很多源不给全文，摘了等于摘了个开头。要么接全文抽取（jina reader / trafilatura），要么对这类源只做 worth_click 筛选、不做摘要。
- **guid 靠不住**。同一篇文章换个 tracking 参数就是“新条目”，规范化 link 能消掉大部分。
- **并发不控制会撞限流**。批间加 sleep，遇到 429 退避重试，宁慢勿崩。
- **模型编造**。“只基于给定内容”这句必须显式写进 prompt。我试过省掉，摘要里出现了原文没有的结论。
- **cron 时区**。OpenClaw 容器默认 UTC，第一周 digest 全部偏移 8 小时才发。容器时区要显式设置，别信默认值。

## 可复用建议

- 两阶段设计（便宜过滤 → 贵摘要）是最划算的一处优化，token 开销降了约一个量级。
- 状态持久化别省，SQLite 足够，别放内存。
- 给每个源记连续失败次数，连续挂 N 次推一条告警给自己。源悄悄 404 一个月是常态，“静默失效”比报错更伤。
- 源列表和 prompt 都进版本管理，改了什么、为什么改，回头能查。

## 总结

这条管线里，模型调用大概只占 20% 的代码量，剩下 80% 是去重、状态、重试、时区这类无聊工程。但决定它能否长期跑下去的，恰恰是那 80%。先让管线无聊但可靠，再考虑换更好的模型——顺序别反。
