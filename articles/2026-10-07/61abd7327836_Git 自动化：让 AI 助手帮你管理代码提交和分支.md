## 背景

日常开发里，Git 操作占了不少碎片时间：写 commit message、切分支、给分支命名、清理合并完的旧分支。这些事不难，但重复。最近几个月我把其中一部分交给 OpenClaw 通过 MCP 的 Git 工具来做，整体思路一句话：**AI 读 diff 起草，人确认，钩子兜底**。

## 问题

之前的真实痛点有三个：

1. commit message 质量不稳定，赶时间就是 `fix` 和 `wip`，两周后自己都看不懂；
2. 分支命名随缘，`test2`、`final-fix-ok` 这类名字在远端越积越多；
3. 每次让 AI 改代码，还得手动描述"我改了什么"，信息重复。

## 做法

核心分三层：工具层、约定层、流程层。

**1. 工具层：接入 Git MCP**

给 Agent 挂上 Git 工具集（官方 mcp-server-git 或自写脚本都行），只暴露：

- 读：`status`、`diff`、`log`、`branch -a`
- 写：`add`、`commit`、`checkout -b`、`branch -d`
- 明确不暴露：`push --force`、`reset --hard`、`rebase -i`、`clean -fd`

**2. 约定层：把规范写成文件**

在仓库里放一份约定文件（我们放在 AGENTS.md），写清楚：

- Commit 格式：Conventional Commits，scope 怎么选；
- 分支命名：`feat/`、`fix/`、`chore/` + 小写短横线；
- 禁止入库清单：`.env*`、`*.pem`、构建产物。

Agent 每次操作前读这份文件，不用在对话里反复交代。

**3. 流程层：固定工作流**

```
status + diff --stat  →  确认改动范围
生成 message 草稿      →  人过目确认
add + commit          →  husky 钩子做最后校验
任务结束               →  列出已合并分支，问一次再删
```

关键是"草稿—确认"这步不能省。Agent 起草的 message 偶尔抓不准真实意图（比如三处改动其实是同一个修复），人扫一眼十秒钟，值得。

## 踩坑点

- **`.env` 差点入库**：Agent 对"该提交什么"的判断不可靠，光靠约定文件不够。后来加了 pre-commit 钩子做敏感文件黑名单——这层必须机器来守，不能靠 prompt。
- **大 diff 概括失真**：一次改 40+ 文件时，起草的 message 会把不相关的改动揉在一起。现在先让它跑 `diff --stat` 分块看，或者干脆拆成多次提交。
- **交互式命令卡死**：`rebase -i` 在 Agent 的非交互 shell 里直接挂起。要么禁用，要么用 `GIT_SEQUENCE_EDITOR` 指向脚本的方案替代。
- **幻觉提交信息**：偶尔出现 message 描述了 diff 里根本不存在的改动。在流程里固定加一句"message 每一句必须能对应 diff 里的实际改动"，能压下去大半。

## 可复用建议

1. **权限分三档**：读随意、写需确认、破坏性命令不开放。这条比任何 prompt 技巧都重要。
2. **约定进仓库不进对话**：团队所有人（和所有人的 Agent）共享同一份规范，新人 Agent 开箱即用。
3. **先跑一周 dry-run**：Agent 只起草不执行，你手动贴进去，观察 message 质量达标后再放开写权限。
4. **留日志**：所有 Agent 的 Git 操作记下来，出问题能回溯。

## 总结

这套东西没有黑科技，本质是"AI 起草、人审核、钩子兜底"的分工。每天省下的时间大概十几分钟，不算多，但 commit 历史变干净了，回看代码不用再猜"这个 fix 到底修了啥"。Git 自动化的价值不在快，而在于让历史记录这项被动欠的债，变成顺手还清的日常。
