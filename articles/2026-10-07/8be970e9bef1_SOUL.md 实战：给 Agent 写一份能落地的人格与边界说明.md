## 背景

OpenClaw 的工作区里，`SOUL.md` 是少数每次会话都会被完整注入系统提示的文件之一。和 `AGENTS.md`（操作规程）、`MEMORY.md`（长期记忆）分工不同，它决定 agent「是谁、怎么说话、什么不做」。很多人的顺序是：装插件、接 MCP、跑自动化，`SOUL.md` 还是默认那几行——结果同一个助手在不同会话里判若两人。

## 问题

没有显式人格定义时，行为由模型默认风格决定：过度迎合、回答冗长、该确认的不确认。更麻烦的是边界。OpenClaw 这类能执行 shell、发消息、调外部 API 的 agent，一旦没写清「哪些动作必须先问」，它会在一次顺利的自动化之后顺手做掉下一个相似动作——而那个动作可能花了钱、发了不该发的消息。事后翻日志追责，不如一开始把边界写成文本。

## 做法

我的 `SOUL.md` 保持在一屏以内，四段结构：

1. **身份**：两三句话，它服务谁、总体定位（例如「工程搭档，不是客服」）。
2. **语气**：写可观测的行为，不写形容词。「回复先结论后细节，默认不超过三段」比「简洁友好」可执行得多。
3. **边界**：写成可判定规则。涉及花钱、对外发送、删除文件、改生产配置 → 必须列出将执行的命令并等确认。格式用「触发条件 + 动作」，模型执行最稳定。
4. **绝不做**：少量绝对化禁令，比如不替我承诺 deadline、不看完整 diff 不 push。

改完不靠感觉验收。我留了七八条固定提问（正常任务、模糊指令、诱导越界的请求），每次改完重跑一遍对比输出，相当于人格层面的回归测试。

## 踩坑点

- **写太长**。早期版本三千多字，实际生效的只有开头结尾。它和 `AGENTS.md`、`MEMORY.md` 挤在同一个注入窗口里，越长越稀释。
- **任务流程混进来**。有段时间把部署步骤也写进去，它变成第二份操作手册，和 `AGENTS.md` 打架。后来原则定死：SOUL.md 只管「是谁和什么不做」，怎么做进 AGENTS.md。
- **边界太死**。最初所有写操作都要确认，一周后我开始无脑点批准，边界形同虚设。收窄到「不可逆」和「外部副作用」两类，确认才有意义。
- **没有版本管理**。工作区放 git，`SOUL.md` 每次修改单独 commit，出问题能 diff 出「哪次改动让行为变了」。

## 可复用建议

- 从 20 行起步，宁短而可执行，不长而全面。
- 每条规则用「当 X 发生时，做 Y」自查，写不出来的就是没想清楚。
- 踩过的坑回写成规则，`SOUL.md` 应该是单调递增的纪律清单，不是一次性设计产物。
- 人格和记忆分离：风格进 `SOUL.md`，事实进 `MEMORY.md`，别让 agent 把「我的偏好」记成「我的身份」。

## 总结

`SOUL.md` 的价值不在让 agent「更有性格」，而在把行为从模型默认值变成工程可控的配置。写法上没有玄学：短、具体、可判定，配合版本管理和固定用例回归，人格就是可以 review、可以回滚的代码。
