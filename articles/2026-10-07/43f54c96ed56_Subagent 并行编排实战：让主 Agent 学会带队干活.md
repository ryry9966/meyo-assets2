## 背景

单个 Agent 的主循环适合线性任务：读代码、改文件、跑测试。但当任务变成批量化——给 20 个模块各补一遍单测、把 30 篇文档做摘要、对 5 个仓库做安全扫描——串行的问题就暴露了：慢，而且所有中间输出都堆在主会话上下文里，跑一半主 Agent 就开始"失忆"。

subagent 编排的思路很朴素：主 Agent 只负责拆解、派发、验收，具体执行交给多个并行的子会话，每个子会话有独立上下文和独立工具权限。OpenClaw 里可以通过会话派生类工具（或自己封装一层 MCP 工具）拉起子会话，天然适合这种模式。

## 先说为什么需要编排

- **上下文污染**：主会话每跑完一个子任务，中间输出几千 token，十来个任务后已经看不到全局。
- **串行太慢**：批任务之间往往相互独立，串行纯属浪费。
- **风险隔离**：子任务跑在受限环境（比如只给只读工具），失败也不污染主流程。

## 做法：以"批量补测试"为例

**步骤 1：拆任务。** 主 Agent 列出模块清单写入 plan 文件。关键是判定独立性——模块间没有文件修改冲突才允许并行。

**步骤 2：定契约。** 每个 subagent 的派发 prompt 固定成模板：

- 目标：只负责 `modules/foo.py`
- 工作区：独立 git worktree 或独立目录
- 输出：测试写入 `tests/test_foo.py`，状态写入 `results/foo.json`（成功/失败/原因）
- 汇报：只回一句 "done/fail + 结果文件路径"，禁止把代码全文贴回来

**步骤 3：控制并发。** 别一口气 spawn 20 个。配额、速率限制、本机负载都会爆炸。经验值是并发 3~5，用简单队列循环派发，跑完一个补一个。

**步骤 4：聚合验收。** 主 Agent 只读 `results/` 目录做汇总，对失败项决定重试或亲自接手。全程主会话上下文增长基本恒定。

## 踩坑点

1. **共享状态冲突**：两个 subagent 同时改同一文件，或同时连同一个有状态 MCP server，结果互相覆盖。有状态的 MCP 连接要么每个 agent 独立实例，要么改成只读加外部执行。
2. **结果回流失控**：subagent 若把完整输出直接 return 给主 Agent，上下文污染原样复现。必须强制"文件落地 + 摘要汇报"。
3. **失败被吞**：子会话超时崩溃后，主 Agent 不核对状态文件就会误判成功。验收步骤必须逐项检查。
4. **成本线性上涨**：并行 5 个 agent 就是 5 倍 token 消耗。放量前先用 1~2 个任务试跑，确认模板没问题再上量。
5. **幂等性**：subagent 中途挂掉重试时要能安全重复执行，比如先清空输出文件再写。

## 可复用建议

- 派发 prompt 模板化，放进插件或脚本里复用，别每次手写。
- 一切交接走文件，不走上下文。`results/` 目录就是你和 subagent 之间的 API。
- 并发上限写进配置，默认保守（3），稳定后再调。
- 每个 subagent 留独立会话日志，排障时可以回放完整轨迹。
- 最小权限：只给完成任务必需的工具，能只读就只读。

## 总结

subagent 编排的本质不是"更快"，而是**隔离与契约**：上下文隔离让主 Agent 保持清醒，文件契约让并行结果可验收。先把任务拆干净、把契约定死，再谈并发数。做对这两件事，20 个模块的批量任务可以从半天压到二十分钟，而且主会话结束时你还看得懂发生了什么。
