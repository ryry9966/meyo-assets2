## 背景

社区每周要固定产出几篇技术周报和资料汇总帖，人工做了一段时间后问题很明显：耗时、容易忘、格式不统一。于是我基于 OpenClaw 搭了一个发帖机器人，目标是：**定时抓取信源 → Agent 生成草稿 → 人工确认 → 定时发布**。本文记录整体设计和实际踩过的坑。

## 问题拆解

这个需求看似只是“自动发帖”，拆开后是四件事：

1. **信源获取**：从 RSS、仓库 release 等渠道拉取结构化内容；
2. **内容生成**：Agent 按模板生成草稿，而不是自由发挥；
3. **质量闸门**：发布前必须有人工确认环节；
4. **发布可靠性**：不重发、不漏发、失败可追踪。

## 架构与做法

整体分三层：

- **调度层**：cron 触发任务，每个任务带唯一 task_id；
- **Agent 层**：OpenClaw Agent 负责编排，只做决策，不直接执行副作用；
- **工具层**：全部通过 MCP 工具暴露，职责单一：

| 工具 | 职责 |
| --- | --- |
| fetch_sources | 抓取并裁剪信源，返回结构化片段 |
| save_draft | 草稿落库（SQLite），返回 draft_id |
| approve | 人工确认，状态流转 draft → approved |
| publish | 发布已确认草稿，携带幂等键 |

状态机是单向的：`draft → approved → published`，任何回退都需显式操作。所有状态落库，不依赖对话上下文——Agent 重启后照样能接上。

## 踩坑实录

**1. cron 重叠触发导致重复发帖。** 上线第二天就复现：上一轮任务没跑完，下一轮 cron 又启动了。解决办法是任务级锁 + 状态机校验，非 `approved` 状态一律拒绝发布。

**2. MCP 工具返回内容过大。** 最初把整个 RSS 页面原样塞给模型，上下文直接爆炸，摘要质量反而下降。改成在工具端先做裁剪：只保留标题、摘要、链接，单次返回固定条数。经验是——**返回给模型的内容要“少而结构化”，而不是“多而原始”**。

**3. 超时重试造成同一篇发两次。** publish 调用超时后 Agent 自动重试，服务端没有去重，同一篇帖子发了两遍。修复：publish 强制携带幂等键（draft_id + 内容指纹），服务端遇到重复键直接返回上次结果。所有有副作用的工具都应如此。

**4. Prompt 越写越长，输出反而漂移。** 为了控制风格往系统提示里堆规则，结果格式时好时坏。最后回退为固定模板 + 少量示例 + 输出长度硬限制，稳定性明显提升。模板管结构，示例管语气，比堆形容词管用。

**5. 时区问题。** cron 服务器是 UTC，社区受众按北京时间活跃，发布时间整体偏移 8 小时。调度层统一显式声明时区，别信默认值。

## 可复用建议

- 工具粒度宁小勿大，一个工具只做一件事，方便定位问题；
- 一切外部副作用必须带幂等键；
- 状态落库，不依赖上下文记忆；
- 上线前用灰度账号空跑一周，重点观察重复与失败路径；
- 记录每次工具调用的入参出参，排障时这是唯一真相。

## 总结

发帖机器人的难点不在“生成”，而在编排与可靠性：状态机、幂等、闸门缺一不可。Agent 负责聪明，工具层负责可靠，两者边界清晰，系统才敢无人值守地跑。欢迎在评论区交流你们在 MCP 工具设计和自动化任务上的踩坑经验。
