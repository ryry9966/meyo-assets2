## 背景

OpenClaw-CN 社区日常消息量不小，精华整理、周报发布这类活儿重复且费时。我用 OpenClaw + MCP 搭了一个发帖机器人，跑了一个多月：定时抓取社区动态，生成摘要草稿，人工确认后自动发布。这篇帖子记录架构取舍和踩过的坑，供想折腾类似东西的朋友参考。

## 问题定义

动手前定了三条硬性要求：

1. **内容可溯源**：摘要里的每个链接必须真实存在，不允许模型“凭记忆”写
2. **不重复**：同一话题不连发，相似内容能去重
3. **可控**：直发前必须过人工审核，出问题随时能停

## 架构设计

整体分四层：

- **触发层**：cron 定时触发 + webhook（出现高热度新帖时可手动触发）
- **Agent 层**：OpenClaw agent，system prompt 只定义角色和输出格式，不承担业务规则
- **工具层**：MCP server 封装三个工具——`fetch_posts`（抓取）、`save_draft`（写草稿库）、`publish`（唯一发帖入口）
- **存储层**：SQLite 存草稿、已发帖的 content hash、发帖时间

关键决策是**把业务规则全部下沉到工具层**。冷却时间、去重、频率上限都写在 `publish` 里，prompt 只负责引导内容质量。实践证明，prompt 里写“请勿频繁发帖”这类约束，在多轮对话后必然失效；代码里的 `if` 不会。

## 执行流程

```
fetch_posts → filter → save_draft → 人工审核 → publish
```

抓取近 24h 帖子，agent 筛出 5–8 条生成摘要草稿入库，人工在后台确认后，`publish` 校验去重和冷却时间再发布。

## 踩坑实录

**坑 1：模型编造链接。** 早期让 agent 自己补全 URL，结果出现了站点下根本不存在的路径。修复：prompt 明确要求引用必须逐字来自工具返回值，`publish` 前再校验一次 URL 可达性。

**坑 2：重试导致重复发帖。** publish 超时后 agent 自动重试，同一条内容发了两遍。修复：publish 做成幂等——发帖前查 content hash，命中直接返回“已发布”。至少做到先写库再发帖，而不是反过来。

**坑 3：cron 并发。** 定时任务偶尔重叠，两个 agent 实例同时跑。修复：发布环节加数据库锁，触发层保证单实例运行。

**坑 4：上下文膨胀。** 一次性塞几百条帖子进去，摘要质量明显下降。修复：抓取层先用规则粗筛（关键词 + 时间窗），agent 只精筛 20 条以内的输入。

**坑 5：裸奔直发。** 头三天让机器人直发，措辞生硬被社区吐槽。改成草稿审核模式跑两周，把高频措辞问题沉淀进 style prompt，质量才稳定下来。

## 可复用建议

- **写入口唯一化**：发帖只走一个工具，所有约束都拦在这里
- **先只读，后写入；先草稿，后直发**
- **prompt 管内容，代码管行为**，别指望模型守纪律
- 外部输入全部落库留痕，出问题能回放定位
- 假设每次调用都可能超时重试，一切按幂等设计

## 总结

这类机器人的难点不在“让 agent 会干活”，而在“让它只在边界内干活”。工具层承担了 80% 的工程约束，agent 层专注内容生成，人只出现在最后一环。一个多月下来，周报制作时间从 2 小时降到 15 分钟，没翻过车——因为翻车路径基本都被提前堵死了。
