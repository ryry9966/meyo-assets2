## 背景

我们平时用 Agent 的方式基本是"人肉触发"：想起来才去问一句。但很多事并不需要人想——邮箱有没有待处理邮件、磁盘还剩多少、某个监控页是否正常。OpenClaw 的 Agent 内置了心跳机制：每隔一段时间自动醒来，读取工作区根目录的 `HEARTBEAT.md`，按里面的指令决定要不要做事。没有这个文件，心跳直接跳过，零成本。也就是说，"主动性"是现成的，只是大多数人从来没写过这个文件。

## 问题

实际用下来有两种典型失败模式：

1. 文件里堆满模糊指令，比如"帮我盯着所有服务"。每轮心跳都触发一次推理，token 持续消耗，产出却多是"一切正常"之类的废话。
2. 反过来，任务没有"保持沉默"的条件，Agent 每轮都汇报一次，三天后你就把通知渠道静音了。

本质问题是：心跳不是定时任务框架，而是"值班巡检"机制。任务写得像不像巡检单，直接决定这套机制是省心还是烦人。

## 做法

在工作区根目录建 `HEARTBEAT.md`，每个任务按固定三段写：

```markdown
## 收件箱巡检
- 触发：有未读的重要邮件
- 动作：摘要后转发到我的 IM
- 沉默：没有重要邮件时不发任何消息

## 磁盘水位
- 触发：根分区使用率 > 85%
- 动作：清理包管理器缓存并通知我
- 沉默：低于阈值时保持安静
```

几个配套配置值得调：

- 心跳间隔默认 30 分钟，低频任务可以在文件里写明"每小时才检查一次"，或直接调整间隔。
- 给心跳单独指定更便宜的模型。巡检大多是判断题，不需要旗舰模型。
- 没事可做时让 Agent 回复 `HEARTBEAT_OK`，这条消息会被静默吞掉，不会打扰你。
- 某个 Agent 不需要主动性，直接在配置里关掉它的心跳即可。

## 踩坑点

- **文件越长，成本越高**：`HEARTBEAT.md` 的内容每轮心跳都会进入上下文。保持在一页以内，塞不下的任务说明该拆去 cron 或脚本。
- **巡检 ≠ 定时任务**："每天 9 点整发日报"这种精确触发，用 cron 推消息给 Agent；心跳适合"看看状态有没有异常"这类模糊巡检。两者混用是新手最常见的架构错误。
- **弱模型会误判**：为省钱用太小的模型，出现过把测试环境告警当成生产事故转发的情况。心跳模型至少要能稳定执行"判断 + 沉默"这套指令。
- **没有审计就没法调优**：让 Agent 把每次心跳的决定追加到一个日志文件，一周后回看，哪些任务在空转一目了然。

## 可复用建议

- 任务模板固定为"触发 / 动作 / 沉默"三行，沉默规则必须显式写。
- 新起一个 `HEARTBEAT.md` 时最多放 2-3 个任务，跑一周再往上加。
- 每周清理一次：日志里连续一周没有实际动作的任务，删掉。
- 分工想清楚再写：心跳负责状态巡检，cron 负责定点动作，脚本负责重活。

## 总结

HEARTBEAT.md 的价值不在"让 AI 更智能"，而在把你脑子里那部分定期检查项外包出去。它是值班表，不是许愿池：触发条件明确、沉默规则显式、文件保持精简，这套机制就能长期安静地跑着，只在你真正需要时出声。写第一份 HEARTBEAT.md 花 20 分钟，省下的是之后每天几十次的"我去看看"。
