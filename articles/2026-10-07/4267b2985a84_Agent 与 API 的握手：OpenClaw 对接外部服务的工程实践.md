## 背景

大模型本身只会生成文本，Agent 的真正价值在于"能动手"——查数据库、提工单、触发构建。在 OpenClaw 里，这条链路的核心是工具调用：模型决定"调什么、传什么参数"，OpenClaw 负责把请求真正发到外部服务，再把结果喂回上下文。听起来只是一个 HTTP 调用，但实际对接时，握手失败的场景远比成功多。

## 问题

社区里常见的三种接法，各有各的坑：

1. 直接在 prompt 里写 URL，指望模型"自己会调"——不可控，也不安全；
2. 把几十个 REST 接口一股脑注册成 tool——模型选不准、参数乱填；
3. 每对接一个服务就手写一遍胶水代码——不可复用，维护成本线性增长。

更隐蔽的问题在工程层面：鉴权怎么管、超时怎么设、失败要不要重试、返回结果太长怎么办。这些不解决，Demo 能跑，生产必翻车。

## 做法

以"让 Agent 查询内部工单系统"为例，标准流程四步：

1. **协议选型**：能力只给当前项目用，OpenClaw 内置 tool 定义足够；多个 Agent / 多个项目都要用，优先封装成 MCP server，一次实现、处处挂载。
2. **收窄接口**：不要把 `/api/tickets` 的全部能力透出去。定义成 `query_tickets(status, owner, limit)` 这种单一意图的工具，参数尽量用枚举而非自由字符串，模型填对的概率会高很多。
3. **鉴权与配置分离**：token 走环境变量或 secret 配置，绝不写进 tool 描述，也不打进日志。
4. **错误处理**：客户端超时设 10–30 秒；查询类幂等操作可做 2 次指数退避重试；下单、发消息这类非幂等操作必须带客户端生成的 request id，让服务端去重。

## 踩坑点

- **tool 描述是写给模型看的，不是写给人的**。"查询工单"不如"按状态和负责人查询工单列表，status 可选 open/closed/all，默认 open"。
- **工具越多，选择越乱**。超过 15 个 tool 后误选率明显上升，按场景拆分挂载比全量注册好。
- **大返回值撑爆上下文**。一个返回 500 条记录的接口，先在封装层做分页或字段裁剪，再交给模型。
- **重试撞上非幂等**。某次对接消息推送服务，网络超时后盲目重试，用户收到三条相同通知。request id 是底线。
- **错误信息要"可推理"**。返回 `{"error": "rate_limited", "retry_after": 30}` 远好过一个 HTML 错误页，模型能据此决定等待还是放弃。

## 可复用建议

- 把 tool schema 当作"给模型的 API 文档"来写：参数含义、默认值、边界条件都写清楚。
- 每次工具调用记录 trace id、入参摘要、耗时和状态码——排障时这就是唯一的证据链。
- 封装层只做三件事：参数校验、响应裁剪、错误归一化，让模型看到的永远是干净的结构化数据。
- 新服务上线前先 dry run：固定输入跑十次，确认模型稳定用对参数再放开。

## 总结

Agent 与 API 的握手，本质是把"工程师熟悉的接口契约"翻译成"模型能理解并稳定使用的工具描述"。MCP 还是内置 tool 只是载体，真正决定可靠性的是接口收窄、鉴权分离、幂等设计和结构化错误这四个工程细节。先把封装层做扎实，再谈自动化编排，路径会顺很多。
