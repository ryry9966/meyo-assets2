## 背景

最近在用 OpenClaw 做自动化时遇到一类典型任务：一次性审查十几个 PR 的 diff、批量跑日志分析、给一批文档打标签。单 Agent 串行做，问题是显而易见的——主对话的上下文越滚越大，跑到第五个任务时模型已经开始"忘了"前面的约定，而且总耗时就是所有子任务的简单相加。

Subagent 编排是这类场景的自然解法：主 Agent 负责拆任务和汇总，每个子 Agent 拿到独立的上下文和工具白名单，并行执行，只回传结构化结果。

## 问题

真正动手时发现核心难点不在"能不能并行"，而在三件事：

1. **上下文隔离的代价**：子 Agent 看不到主对话，如果 prompt 里不带足背景，它要么重复劳动，要么做出错误假设。
2. **写冲突**：多个子 Agent 同时改同一个文件、往同一个分支提交，结果就是互相覆盖。
3. **结果不可汇总**：子 Agent 各说各话，主 Agent 拿到一堆自由文本，拼不出结论。

## 做法

我的编排结构最终收敛成这样：

1. **先跑单 Agent 版本**。用串行方式把任务完整走一遍，确认拆分边界合理——哪些子任务真正独立、哪些其实有隐藏依赖。这一步不能省，否则并行化只是在放大错误。
2. **定义子 Agent 的三要素**：目标（一句话）、边界（能碰哪些 MCP 工具、禁止写哪些资源）、输出 schema（强制 JSON，字段固定）。
3. **并发限流**。同时最多跑 3 个子 Agent。经验上看，超过 3 个后 API 限流和结果汇总的复杂度都会陡增，收益反而下降。
4. **读写分离**。子 Agent 只做"读 + 生成"（分析、打分、摘要），所有写操作（改文件、提交、发通知）收敛到主 Agent，由它按顺序落地。这一条解决了绝大部分冲突。
5. **失败策略前置**。每个子 Agent 设超时（比如 120 秒）和重试上限（1 次），失败的结果带错误标记回传，主 Agent 决定是重派还是降级为人工。

按这个结构跑批量日志分析，10 个子任务原本串行约 18 分钟，限流 3 并发后压到 7 分钟左右，主对话的 token 消耗也降了一个量级——因为子 Agent 的中间过程不会污染主上下文。

## 踩坑点

- **递归 spawn 必须禁掉**。子 Agent 再去开子 Agent，很快失控。我把深度硬编码为 1。
- **schema 不校验等于没有 schema**。早期有子 Agent 在 JSON 里多包了一层 markdown 代码块，主 Agent 解析直接挂。后来在解析侧做了宽松剥离，才稳定下来。
- **并行 = 成本倍增**。3 个并发就是 3 份上下文费用，跑之前先估一下，别等账单教育你。
- **日志要按子 Agent 分文件存**。全混在一个 session 里，排障时根本分不清哪句话是谁说的。

## 可复用建议

- 把子 Agent 的 prompt 做成模板：`目标 / 背景 / 工具白名单 / 输出 schema / 禁止事项` 五段式，新任务只改参数。
- 写操作永远收敛到一处，哪怕牺牲一点并行度。
- 判断一个任务适不适合 subagent 编排，就看三点：可拆分、读多写少、子任务彼此独立。三条不占全，不如老实串行。

## 总结

Subagent 编排的价值不在于"并行"本身，而在于**上下文隔离 + 结构化约束**带来的稳定性。把拆分边界、输出 schema、写操作收敛这三件事做扎实，多 Agent 并行才是一个可靠的工程手段，而不是炫技。
