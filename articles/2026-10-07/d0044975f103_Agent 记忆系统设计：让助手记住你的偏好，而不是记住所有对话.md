## 背景

大模型本身无状态，每次会话都是白纸。Context window 再大，也装不下你半年积累下来的使用习惯。对于跑在 OpenClaw 里的常驻 Agent 来说，记忆系统不是锦上添花，而是它从"工具"变成"助手"的分界线。

## 问题

常见三种失败模式：

1. **什么都不记**——每次都要重复交代项目路径、代码风格、部署偏好；
2. **全都记**——把对话原样塞进记忆文件，检索时噪音淹没信号，Agent 反而被过时信息带偏；
3. **记了不用**——记忆躺在文件里，Agent 从不主动读，或者每次全量注入撑爆 prompt。

核心矛盾：记忆的价值在"准"，不在"多"。

## 做法

**第一步：明确记什么。** 按来源分两类：显式偏好（用户明说"记住我喜欢 pnpm"、"别用 emoji"）和隐式偏好（用户反复纠正的行为）。一次性指令（"这次先别跑测试"）绝不进长期记忆——这是最常见的错误。

**第二步：分层存储。** 我用三层结构：

- 会话内：不落盘，靠 context；
- 工作记忆：当前任务的临时状态，任务结束即清理；
- 长期记忆：结构化 JSON，每条含 `content`、`source`（explicit/implicit）、`confidence`、`created_at`、`last_hit`。

**第三步：克制写入。** 显式指令直接写；隐式行为需重复出现 ≥2 次才写。写入前做查重与冲突检测：语义冲突时不覆盖，而是标记 `superseded_by`，保留历史链。

**第四步：按需读取。** 会话启动只注入 top-K 高置信度偏好（控制在几百 token），其余通过 MCP 暴露 `memory_search` 工具按需查询。条目少于 50 条时，平铺文件 + 关键词过滤完全够用，先别上向量库。

## 踩坑点

1. **Agent 会编造记忆。** 必须要求它引用记忆 ID 或原文，否则它会把"我以为你说过"当成记忆输出。
2. **记忆是攻击面。** 能被工具写入的记忆等于不可信输入，注入一条恶意偏好比普通 prompt injection 危害更持久。写入来源必须留痕。
3. **临时偏好污染。** "这周用 A 方案"没有 TTL，一个月后还在生效。隐式偏好要加时间衰减。
4. **检索精度假象。** 条目一多，向量检索 top-5 里一半不相关。先做结构化字段过滤，再考虑 embedding。

## 可复用建议

- 先用最土的方案跑通：一个 JSON 文件 + `memory_write` / `memory_search` / `memory_review` 三个 MCP 工具，运行两周再优化；
- 让用户可见可删：定期输出记忆摘要供确认，删错条目比补写容易；
- 记录 `last_hit` 和 `hit_count`，长期未命中的条目先进回收站，不硬删；
- 偏好和事实分开存：技术栈选型是事实，回复风格是偏好，混存会让检索很乱。

## 总结

记忆系统的核心不是存得多，而是**写得克制、读得精准、错得可回滚**。先用文件加三个工具把闭环跑起来，等积累了真实的检索失败案例，再决定要不要引入向量库。让 Agent 记住你的前提，是你能随时看到并纠正它记住了什么。
