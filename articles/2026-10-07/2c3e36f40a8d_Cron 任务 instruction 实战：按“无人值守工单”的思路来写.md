# 背景

OpenClaw 的 cron 功能，本质上是定时唤醒一次 agent，把一段 instruction 喂给它。很多人把这段 instruction 当成普通聊天消息来写——“每天早上帮我看下邮件”——上线后就会发现任务要么空转，要么产出了没人看。过去半年我跑了十几个定时任务（日报汇总、仓库巡检、关键词监控），把经验整理成这篇。

# 问题：无人值守是前提差异

对话式 prompt 和 cron instruction 的根本区别在于：**没有人在场**。

- 你不在，agent 反问“你想看哪几个仓库？”就没人回答，这一轮直接浪费。
- 会话上下文不存在，“按我们上次说的”等于什么都没说。
- 产出没有落点，跑完了也没人知道它跑过。

所以核心原则只有一句：**把 instruction 当作给一个只收到这一条消息的实习生写的工单**。

# 做法：五段式模板

我的 instruction 现在基本固定为五段：

1. **任务目标**：一句话，动词开头。例如“汇总过去 24 小时内……”
2. **数据来源与范围**：写死路径、频道、过滤条件。不要用“今天的”“最近的”这类相对词，用“过去 24 小时”“截至本次运行时刻”。
3. **输出位置**：明确送达哪个频道/会话，或写到哪个文件路径。没有落点的任务等于白跑。
4. **输出格式**：给下游机器消费的，规定固定结构；给人看的，限制长度，比如“不超过 12 行”。
5. **异常处理**：拿不到数据怎么办、重复运行怎么办。显式写“不要推测内容”。

一个实际例子：

```text
任务：汇总过去 24 小时内 #ops 频道出现过的报错关键词。
来源：只读 #ops，范围为上次运行之后的新消息。
输出：发到 #daily-report，格式为"关键词 — 次数 — 代表性一条"，总长不超过 12 行。
异常：频道不可达或无新消息时，输出"本次无新增"，不要推测内容。
```

另外注意：调度时间信息不要写进 instruction，交给 cron 表达式。instruction 里再写一遍“每天九点”，迟早和表达式打架。

# 踩坑点

- **对话式口吻**：写“帮我看下……”，agent 会反问或等待确认。改成直接陈述式指令。
- **时区**：cron 按网关所在时区执行，“每天早上”跨了时区边界就是另一个故事。部署前确认时区，instruction 里用相对窗口而不是“今天”。
- **幂等缺失**：没写去重条件，agent 每轮全量处理，日报重复推送。加一句“只处理上次运行之后新增的条目”。
- **异常变静默**：agent 拿不到数据时，自己“编了个合理的总结”。必须在 instruction 里显式允许它报失败。
- **instruction 越写越长**：高频任务里塞几百字背景说明，token 成本翻倍。背景知识放到 workspace 的文件里，instruction 只给路径。

# 可复用建议

- 上线前手动触发跑 3–5 次，完整看一遍会话输出，确认没问题再挂 schedule。
- 一个 cron 只做一件事。想做“日报 + 巡检”，拆成两个任务，互不拖累。
- instruction 放文件里用 git 管，改 prompt 也该有版本记录。
- 输出保持固定格式，以后要接下游自动化时，agent 侧一行不用改。

# 总结

Cron instruction 的写法不是提示词技巧问题，而是工单写法问题：目标、来源、范围、落点、异常，五要素齐全，任务才可能在没人盯着的时候跑对。先把“没有人在场”当成默认前提，大部分坑就自动避掉了。
