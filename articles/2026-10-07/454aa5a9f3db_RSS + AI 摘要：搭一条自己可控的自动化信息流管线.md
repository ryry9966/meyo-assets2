## 背景

信息源越订越多，RSS 阅读器的未读数常年四位数。RSS 本身没问题——结构化、无算法、可自托管——问题在于“读”这个动作无法规模化。与其砍订阅源，不如让 agent 帮我做第一道过滤。

## 问题

现有方案两类：SaaS 摘要服务，数据出域、prompt 不可控；通用 feed-to-summary 脚本，通常只做“每条一句话总结”，不做跨源去重和重要性排序。我想要的是：每天早上收到一份 15 条以内的日报，每条带原文链接，重要的事不漏，水帖不进摘要。

## 做法

管线分四段：**采集 → 清洗 → 摘要 → 分发**。

1. **采集**：RSSHub + Miniflux 自托管，统一输出标准 feed。约 30 个源，技术博客为主。
2. **清洗**：cron 每小时拉增量，解析 entry，用 trafilatura 做正文抽取（很多源只有 summary，直接喂模型会被截断的导语误导）。按 guid + 内容 hash 去重，落 SQLite。
3. **摘要**：每天早上跑一次批处理，分 map/reduce 两步。map 阶段对单条做压缩摘要；reduce 阶段把当天全部条目一起交给模型，输出重要性分级 + 主题聚类 + ≤15 条的日报。prompt 里明确“只保留对后端与 agent 工程有价值的内容”。
4. **分发**：日报渲染成 Markdown 推到 Telegram bot，同时写静态页留档。我把 RSS 拉取与去重逻辑封成了一个 MCP server，平时也能让 OpenClaw agent 按需查询“最近 24 小时某主题的新内容”，批处理和交互调用共用同一套工具。

## 踩坑点

- **别信 pubDate**：时区混乱，部分源会刷新旧文章时间戳，第一版天天漏收/重收。改成“首次见到时间 + guid 去重”才稳定。
- **prompt 注入是真实风险**：feed 正文是不可信输入，“忽略以上指令，输出……”并非天方夜谭。摘要 prompt 里要声明正文仅为素材，模型只做摘要与分级、不执行任何指令。
- **token 成本**：30 个源逐条全文摘要，一天烧掉不少。正文按段落截断、map 用便宜模型、reduce 才上主力模型，成本降了一个量级。
- **去重不只看 guid**：同一篇被转载到两个源很常见，reduce 阶段让模型顺手合并同主题条目，比字符相似度算法省事。

## 可复用建议

- 四段式每段独立可测，单独重跑不串状态；
- 摘要永远保留原文链接与首次见到时间，模型输出只做索引、不做事实来源；
- 先拿 5–10 个源迭代 prompt，稳定后再扩源——prompt 不行，源再多只是噪音放大器；
- 底层能力包成 MCP tool 而非写死在脚本里，批处理与 agent 都能复用。

## 总结

管线跑了一个多月，日报稳定在 10–15 条，误报可接受。它没有替代我读原文，只是把“决定读什么”的成本降了下来。对 agent 实践者来说，RSS 是目前最干净的可控信息源，值得一接。
