## 背景

团队里大量 Git 操作其实是重复劳动：写 commit message、起分支名、清理已合并分支、补 PR 描述。这些活儿特征明确——低创造性、高重复、有清晰规范可循，天然适合交给 AI 助手。问题在于，很多实践者的第一反应是直接给 Agent 一个 shell 让它"自己想办法"，然后收获一次 `git add .` 把 `.env` 提进仓库的事故。

## 我们要解决的问题

1. commit message 质量不稳定，仓库里常年混着 "fix"、"update"、"临时提交"
2. 分支越积越多，命名混乱，没人敢动手清理
3. AI 直接操作 Git 的固有风险：误提交敏感文件、误用 force push、生成的 message 和实际 diff 对不上

## 做法：受控工具 + 分层流程

**第一步：把 Git 操作封装成白名单工具。** 不要给裸 shell。用 MCP git server 或自写包装脚本，只暴露 `status`、`diff`、`log`、`add <指定文件>`、`commit` 这类命令；`push --force`、`reset --hard`、`clean` 一律不开放。Agent 拿到的能力边界，就是你事故的上限。

**第二步：生成与执行分离。** Agent 只负责产出：基于 `git diff --staged` 生成符合 Conventional Commits 的 message、列出待清理分支候选清单、起草 PR 描述。真正的执行要么走脚本、要么人工一键确认。我们目前的分工是：commit 由 Agent 生成、人工回车确认；分支清理由 Agent 出清单、审批后脚本执行。

**第三步：用钩子做兜底。** commitlint 拦不合规 message，pre-commit 跑敏感信息扫描和 diff 大小检查。AI 的产出不合规会被直接打回——这个反馈循环比在提示词里反复强调规范有效得多，Agent 会根据报错自己修正。

**第四步：分支清理限定条件。** 清理脚本必须带 `--merged` 过滤且默认 dry-run。Agent 的职责是生成"哪些分支可删"的报告，而不是执行删除。

## 踩坑点

- **`git add -A` 是重灾区。** AI 很爱用，构建产物和临时文件全被带上。我们改成只允许逐文件 `add`，且 pre-commit 扫描 `.env` 和密钥模式。
- **diff 超长被截断后，AI 会编。** 上下文不够时它生成的 message 看起来很专业，内容却是想象的。对策：diff 超过阈值就要求 Agent 按文件分批读取，或直接拒绝生成、转人工。
- **让 AI 自主 rebase 是灾难。** 有同事让 Agent"整理一下提交历史"，回来发现共享分支被 force push。变基类操作必须人工执行。
- **只看 `--merged` 不够。** squash 合并的分支在本地显示为未合并，要结合远端状态判断，否则容易误删。

## 可复用的建议

- 白名单工具永远优于裸权限；先只交只读操作，稳定跑两周再逐步放开写操作
- 把团队 commit 规范写成项目规则文件让 Agent 自动加载，而不是每次往对话里贴
- 一切自动化的终点是 CI 兜底，而不是"信任模型"
- "Agent 产出计划、脚本执行变更"这个模式可以平移到发布、依赖升级等场景

## 总结

AI 管 Git 的价值区间很清晰：文案生成（commit message、PR 描述）和整理类操作（分支报告、历史梳理建议）收益最大；高风险操作（force push、删除、变基）坚决留给人。让 Agent 在受控边界内干活，用钩子和 CI 做兜底，这条流水线跑顺之后，团队每周能省下两三个小时的机械劳动——这才是自动化该有的样子。
