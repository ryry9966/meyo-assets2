## 背景

给 Agent 接上 shell、文件读写、MCP 工具之后，第一个真实的问题不是它能不能干活，而是干活之前要不要问你。问多了，人变成盖章机器——弹窗看都不看就点确认；问少了，一次误删、一条发错群的消息、一次 force push，就够你修一下午。权限边界不是安全摆设，是效率问题：目标是让人的注意力只花在真正不可逆的决策上。

## 问题：两种失败模式

**过问**：每一步都确认。两周后你会形成"秒批"的肌肉记忆，确认环节形同虚设，Agent 的速度被人的响应速度拖死。

**过放**：提示词里写一句"危险操作需谨慎"。模型对"危险"的理解和你不一致——它觉得顺手改配置不算什么，你觉得那是事故。

## 做法：四档分级

用两个维度判断：**可逆性**（能不能撤销）和**影响范围**（只碰本地，还是出了机器、出了组织）。

- **T0 自动执行**：只读、可逆、局部。读文件、搜索、跑测试、查 git 状态。不确认，但进审计日志。
- **T1 自动执行 + 留痕**：本地写操作。新建分支、写草稿、小规模本地重构。做完记录在案，可回滚。
- **T2 会话内确认一次**：装依赖、改配置、批量文件操作（批量要设上限，比如单次不超过 20 个文件）。本次会话放行，下个会话重新问。
- **T3 每次必问**：删除、推远端、对外发消息、花钱、动生产。判据就一条——不可逆，或者影响出了你的机器。

落地三个关键点：

1. **边界写在工具层，不写在提示词层。** 提示词规则会被长上下文稀释，也可能被 Agent 读到的外部内容（网页、issue 评论）间接注入绕过。MCP 工具的 allowlist 和确认钩子才是硬边界，提示词只做软引导。
2. **问的时候要带上下文。** 不是"我可以执行吗"，而是：完整命令或 diff + 为什么 + 拒绝的后果。人三秒能判断才叫确认，否则只会催生盲批。
3. **T0/T1 全量记日志。** 每周翻一次，把高频自动操作和误操作拿出来调档。边界是校准出来的，不是设计一次就完。

## 踩坑点

- 用"危险""谨慎"这类模糊词写规则。直接列白名单/黑名单，把 T3 动作清单写死。
- "永远允许"给了一整类工具。批准范围要收窄到具体操作模式，而不是整个工具。
- 批量操作只确认一次。一个决定点乘 50 倍爆炸半径，等于没审，必须设硬上限。
- 新工具默认全放。新接入的 MCP 工具先挂 T2 观察一段时间，再降档。
- 用放权解决确认疲劳。疲劳的根因是问得不好（没上下文、太频繁），该改问法，不该拆边界。

## 可复用建议

一句话判据：**可逆且只碰本地 → 自动干；不可逆、出机器、花钱 → 必须问。** 中间地带先按 T2 处理，观察两周再调。降低询问频率的正道是把上下文喂足（diff、原因、影响），而不是把权限放大。

## 总结

权限边界的目标不是零打扰，也不是零风险，而是把人的注意力当稀缺资源来分配：确定性高的操作让 Agent 全速跑，不可逆和对外的影响留给人。边界落在工具层、询问带上下文、档位靠日志校准——做到这三条，Agent 才能既快又可控。
