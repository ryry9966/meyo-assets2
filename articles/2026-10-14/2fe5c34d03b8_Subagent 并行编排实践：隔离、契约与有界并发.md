## 背景

用 OpenClaw 做日常自动化，主 agent 的典型工作模式是一条串行循环：收消息 → 调工具 → 出结果。任务少的时候没问题，但一旦碰到批量场景——比如在十个仓库里核对 release note、给一组日志文件分类打标、同时起草几份不同风格的文档——两个短板就暴露了：慢，而且中间结果全堆在主上下文里，几轮下来上下文被灌满，后面几步的推理质量肉眼可见地下滑。

## 问题

具体拆开是三件事：

1. 串行耗时随任务数线性增长，一个慢任务阻塞整批；
2. 子任务的原始输出（长日志、大段网页内容）污染主上下文，主 agent 反而变笨；
3. 没有失败隔离，第 7 个任务挂了会拖住后面 3 个。

共性很明显：这些子任务本来相互独立，却被塞进了同一条串行管线。subagent 编排就是把它们拆出来并行跑。

## 做法

我的流程可以概括成四步：拆任务、定契约、控并发、再汇总。

**第一步，拆任务。** 先判断子任务是否真正独立：输入不互相依赖、输出不互相引用、不争抢同一个写资源。任务写成一份清单（JSON 数组），每项带唯一 task id。

**第二步，定契约。** 每个子 agent 的 prompt 固定四段：一句话目标、输入位置、输出格式、禁止事项。关键约束是——子 agent 把完整产物写进自己的 workspace 目录，只回传一个 JSON：

```json
{ "task_id": "t03", "status": "ok",
  "artifacts": ["out/t03/report.md"],
  "summary": "3 行以内的结论" }
```

主 agent 只读 summary，需要细节时再按路径打开文件。

**第三步，控并发。** 扇出宽度从 3 起步，观察上游模型的 rate limit 再调；每个子 agent 用独立 session 和独立目录（确实要改同一仓库就用 git worktree），并设单任务超时。

**第四步，再汇总。** 主 agent 收齐 summary 后统一处理；失败任务收集起来，第二轮串行重试一次，仍失败就报告，不死磕。

## 踩坑点

- **子 agent 回传全文。** 最初没限制返回长度，四个子 agent 跑完主上下文直接爆掉。强制"落盘 + 摘要"后解决。
- **写资源竞争。** 两个子 agent 同时往同一个分支提交，互相覆盖。要么目录隔离，要么加文件锁。
- **MCP 工具瓶颈。** 部分 MCP server 是单实例，并发调用会排队甚至 429。这类调用单独降并发，配退避重试。
- **任务描述太模糊。** 子 agent 拿到"整理一下这个仓库"就会自由发挥。一句话目标加明确禁止清单（"不要改代码，只产出报告"）能有效收敛。
- **没有超时。** 一次卡死的子 agent 让整批等了二十分钟。现在每个任务必设超时，超时即标记失败。
- **缺日志。** 编排出问题最难的是定位哪个子任务。task id、起止时间、token 消耗都要落日志。

## 可复用建议

- 把"清单 → 分发 → 回收 → 汇总"沉淀成固定的 skill 或插件模板，子 agent 的 prompt 放独立目录做版本管理；
- 返回契约全项目统一，主 agent 的汇总逻辑不必为每个场景重写；
- 任务设计成幂等的，重跑不出副作用；
- 三步以内、彼此依赖的任务别硬编排，串行反而省心。

## 总结

subagent 编排的本质不是"多个 AI 显得很强"，而是三件朴素的事：隔离（独立 session/workspace）、契约（落盘 + 结构化摘要）、有界并发（限宽 + 超时）。它是工具不是目标——任务少、依赖深的时候，一条老实的串行循环仍然是更好的选择。
