## 背景

Agent 类系统的可靠性，往往不取决于模型本身，而取决于它调用的那些外部工具。一个自动化流程里，LLM 推理可能只占几秒，大部分时间花在搜索、CRM、消息推送、支付这些第三方 API 上。传统后端挂一个依赖，通常是报 5xx 等恢复；Agent 不一样——它拿到失败结果后会继续推理：重试、换思路、甚至自己编个结果把流程走完。错误恢复没设计好，小故障会被放大成静默的数据污染。

## 问题：三种典型的失败放大

1. **重试风暴**：429/503 触发无限重试，token 和配额被打穿。
2. **幻觉兜底**：原始报错直接进上下文，模型"理解"之后开始编造数据补全流程。
3. **副作用重复**：写操作超时后重试，订单、消息发两遍——你以为失败了，服务端其实成功了。

## 做法

**Step 1：错误分类。** 把异常分成可重试（429、502、503、超时）与不可重试（400、401、404）。判断依据是：同样的请求再发一次，结果会不会不同。

**Step 2：有界重试 + 退避。** 最多 3 次，指数退避加随机抖动（如 1s / 2s / 4s ±20%）。关键是"有界"——上限到了就把状态交给上层，而不是在循环里耗着。

**Step 3：熔断。** 同一工具连续失败 N 次（如 5 次），标记为不可用并进入冷却期（如 60s），期间调用直接短路返回。避免 Agent 每轮都去撞一个已经挂掉的服务。

**Step 4：结构化降级。** 不要把堆栈喂给模型，给它受控的状态：

```json
{ "status": "unavailable", "tool": "crm_search", "retry_after_s": 60 }
```

明确告诉它：工具暂时不可用，可以等待、跳过或换方案。模型的可选项是有限的，而不是自由发挥。

**Step 5：写操作幂等。** 所有产生副作用的调用带幂等键，超时后先查询确认再决定是否重发。这一步能解决绝大多数重复副作用问题。

**Step 6：断点续跑。** 任务状态落盘，恢复时从最后成功的步骤继续，而不是从头再来。

## 踩坑点

- **把 timeout 当失败**：请求可能已在服务端执行成功。写操作必须先查询确认。
- **熔断太敏感**：一次失败就断路会误伤偶发抖动，用滑动窗口统计失败率更稳。
- **退避没有抖动**：多个 Agent 实例同步重试，恢复中的服务被二次打挂。
- **降级数据不标注**：fallback 的缓存数据如果不标来源和时效，会污染下游决策，事后很难排查。
- **重试逻辑散落在各插件里**：改一处漏三处，行为不一致。

## 可复用建议

- 所有工具调用收口到**统一的 executor**：分类、重试、熔断、结构化错误输出都在这一层做，插件只写业务逻辑。
- 给每个工具定义**错误契约**，作为插件接口的一部分，和参数 schema 一起维护。
- **可观测性**：每次重试、每次熔断打开都留日志；熔断打开建议直接告警，那是依赖出问题的明确信号。
- 开发环境做**故障注入**：手动让某工具返回 503，观察 Agent 行为是否在预期内。

## 总结

外部 API 挂掉不可怕，可怕的是 Agent 在没有约束的情况下自行处理失败。核心就三层：有界的重试、明确的熔断、结构化的降级——把"怎么办"的选项收窄并显式化，让模型在受控空间里决策。这套东西不性感，但决定了自动化流程能不能在生产环境活过第一周。
