## 背景

让单个 Agent 干长链条的活，问题很明显：串行慢，中间产物把上下文越撑越大，跑到一半就开始“失忆”。典型场景：批量审查 20 个 PR、对 15 个服务做日志巡检、给一批文档抽结构化信息。这类任务天然可拆分，适合并行。

OpenClaw 的 subagent 派生机制给了个顺手的出路：主 Agent 保留调度权，把可拆分的子任务派给多个子 Agent，各自独立上下文，干完只交摘要回来。

## 问题

直接上并行，通常撞上三件事：

1. 子任务串行等结果，总耗时等于全部子任务之和；
2. 子任务的完整输出塞回主上下文，等于没拆；
3. 一个子任务失败或挂死，整批卡住。

所以编排要解决的不是“能不能并行”，而是：边界怎么切、结果怎么收、失败怎么办。

## 做法

以批量文档抽取为例，我的流程分五步：

**1. 切分任务。** 按资源粒度切，一份文档一个子任务，输入互不重叠、输出互不影响。这是后面一切的前提。

**2. 定契约。** 每个子 Agent 用固定系统提示词 + 白名单工具（比如只读文件 + 一个指定的 MCP 工具），返回格式锁死：

```json
{"task_id": "doc_007", "status": "ok | failed",
 "summary": "一行内结论", "output_path": "/runs/batch3/doc_007.json"}
```

**3. 控并发。** 信号量限 3~5 个同时跑。不是越多越好，后面讲。

**4. 只收摘要。** 子 Agent 的完整输出先落盘，主上下文只进 `summary` 和路径，需要细节时按路径再取。

**5. 失败兜底。** 每个子任务显式设超时（如 120s），失败重试一次，仍失败就标 skipped，主 Agent 汇总时带上失败清单。允许部分成功，比整批重跑务实。

## 踩坑点

- **并发拉满。** 第一版我开了 10 并发，触发 API 限流后进入重试风暴，总耗时反而比 5 并发更长。并发数要按限流配额反推。
- **共享工作目录。** 两个子 Agent 同时写同一份中间文件，互相覆盖。改成每个子任务一个独立编号目录后消失。
- **全量回传。** 有次偷懒让子 Agent 直接返回完整抽取结果，20 份文档下来主上下文直接爆了。明细必须落盘，主上下文只收摘要。
- **无超时。** 一个子 Agent 卡在循环工具调用上，整批白等半小时。超时必须显式设。
- **不留痕。** 每个子 Agent 的 prompt、输出、耗时都写进运行目录，否则排查时两眼一抹黑。

## 可复用建议

- 子任务独立工作目录，路径随 task_id 生成；
- 结构化返回 + 明细落盘，主上下文只收摘要；
- 并发 = min(子任务数, 限流允许值)，从 3 起步逐步调；
- 子任务设计成幂等，重跑不产生副作用；
- 用 MCP 做权限隔离，按子任务挂最小工具集，防止子 Agent 越界；
- 先用 2~3 个子 Agent 灰度验证契约，跑稳再放量。

## 总结

Subagent 编排的价值不在“多个 AI 一起跑”，而在边界设计和结果聚合：任务切得干净，上下文才不污染；回收做得克制，主 Agent 才有余力做汇总。先把小规模并行的契约跑稳，再谈规模，这条路径比一步到位靠谱得多。欢迎在评论区交流你们的切分粒度和并发经验。
