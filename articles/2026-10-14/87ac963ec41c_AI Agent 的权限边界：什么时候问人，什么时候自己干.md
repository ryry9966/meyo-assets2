# 背景

Agent 接上 shell、文件系统、MCP 和一堆插件之后，问题就从"它能不能做到"变成了"它该不该自己做"。权限边界没设计好，会掉进两个坑：要么事事请示，人沦为盖章机器；要么大胆自主，一条 `rm -rf` 或一次误发的消息让你连夜回滚。

# 问题：两个失败方向

- **过度请示**：确认弹窗太频繁，人会不读内容直接点"同意"，这道闸等于没装，甚至更危险——它制造了虚假的安全感。
- **过度放权**：只读操作和破坏性操作被同等对待，agent 在长任务里自主执行了不可逆动作，事后你连它在哪一步做的都得翻日志找。

两个坑的根源相同：把"要不要问人"当成对模型的信任问题，而它其实是个工程问题。

# 做法：三步划边界

1. **按"可逆性 × 影响范围"分类**。只读、可撤销、影响限于本机 → 自动执行；可撤销但对外可见（提交到共享仓库）→ 自动执行 + 事后通知；不可逆或对外触达（发消息、发布、支付、删数据）→ 必须问人。
2. **分层设闸：allow / ask / deny**。工具层和参数层都要覆盖。比如 allow `git status`、`git diff`，ask `git push`、`npm publish`，deny `rm -rf` 和一切外发请求。参数层很关键：允许写 `./src`，不等于允许写任意路径。
3. **让确认"值得看"**。别问"我可以继续吗"，要展示具体内容：diff、完整命令、目标地址、预期副作用。人看一眼就能判断，这才是有效的确认。高频场景用会话级预授权："本次任务内你可以在 `./src` 下自由写入，其他先问我。"

# 踩坑点

- **绕闸**：封了 shell 写文件，agent 换个 MCP 工具照样写。等价能力必须一并封，否则清单形同虚设。
- **只读 ≠ 无害**：读了 `.env`，凭证进入上下文，随后可能被外发。敏感读取也要设闸或做输出过滤。
- **预授权泄漏**：上个任务批准的权限延续到下个任务。预授权必须绑定会话和任务范围，到点失效。
- **子 agent 继承**：派生的子任务若不显式收窄权限，主 agent 的边界会被悄悄突破。

# 可复用建议

- **默认策略**：对内只读默认允许，对外不可逆默认询问，破坏性默认拒绝。宁可先紧后松。
- **权限当代码管**：清单进版本库，改动走 review，谁在什么时候放宽了权限，一目了然。
- **每周过一遍自主执行日志**：反复被批准的模式下沉到 allow 清单，缓解确认疲劳；从没被批准的考虑收紧。
- **写一份"自治契约"**：这个 agent 能独自做什么、必须问什么，贴在系统提示词旁边，人和 agent 对齐同一份预期。

# 总结

权限边界的本质不是"信不信模型"，而是错误的代价是否对称：可逆且便宜的错误，放手让它自己干并记日志；不可逆或代价高的动作，把人放进回路，并让每次确认都具体、可判断。闸门的目标是让人保持有效，而不只是人在场。
