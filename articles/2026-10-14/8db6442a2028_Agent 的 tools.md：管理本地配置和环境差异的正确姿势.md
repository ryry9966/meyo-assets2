## 背景

跑 OpenClaw / MCP 这类 agent 框架时，系统提示词和插件描述都是"通用版"的，但真正决定执行成败的往往是你这台机器的具体状态：Python 在 pyenv 里还是系统里、代理端口是多少、备份脚本放在哪。OpenClaw 的做法是在工作区放一个 `tools.md`，每次会话随工作区文件一起注入上下文，相当于给 agent 一份"本机说明书"。这份文件写得好不好，直接决定 agent 是上手就能干活，还是每个任务先猜半天。

## 问题

常见的失控方式有三种：

1. **配置散落**：本机信息分布在 shell rc、README、口头经验里，agent 全靠试探，同样的问题每次会话重猜一遍。
2. **多机漂移**：笔记本、服务器、容器里工具版本和路径不同，一份经验到处套用，报错全靠现场排查。
3. **越写越危险**：图省事把 API key、内网地址直接写进提示词类文件，随上下文进日志、进缓存，事后很难清理。

## 做法

按四步把 `tools.md` 建起来：

**1. 建基线模板，进版本库**

```markdown
# tools.md
## 环境基线
- OS / Shell / 语言版本及管理器（pyenv、nvm）
## 路径与脚本
- 项目根、自定义脚本的绝对路径和用途
## 行为约定
- git push 前必须确认；不主动执行 rm -rf
## 已知坑
- 代理走 127.0.0.1:7890，curl 需显式带 -x
```

模板命名为 `tools.md.example` 提交进 git，真实文件加进 `.gitignore`。

**2. 机器差异单独覆盖**

单文件内分"通用 / 本机"两节，或按机器放 `tools.linux.md` 一类的差异文件。原则：git 里只有模板和通用约定，具体值留在本机。

**3. 只写模型猜不到的内容**

控制在 50–80 行。已装工具、版本、路径、网络约束、危险操作红线，这些才有信息增量；"请友好回复"之类的通用规则交给系统提示词，别在这里重复。

**4. 脚本生成草稿 + 定期对账**

写个十几行的 shell 脚本拼 `uname`、`which`、`--version` 的输出生成初稿，再人工修剪。之后定期让 agent 自己读 `tools.md`，逐条核对命令是否存在，过期条目直接删。

## 踩坑点

- **密钥写进正文**：只写"密钥在环境变量 `XXX_TOKEN`"，绝不写值本身。
- **文件膨胀**：超过百行后上下文预算被吃掉，核心指令反而被稀释——删比加更重要。
- **过期文档比没有更糟**：agent 倾向于相信文档而不是现实，文档写着 Python 3.10 实际是 3.12 时，它会按错的走。改环境必须同步改文档。
- **职责重叠**：`tools.md` 只写环境事实，不写任务流程和人格设定，那些归 AGENTS.md / 系统提示词管。
- **多机 symlink 同步**：一份文件多处软链，改一台坏三台。用模板 + 差异文件。

## 可复用建议

- 把它当 runbook 维护：唯一的修改触发条件是"环境变了"。
- 新机器冷启动流程固定为：拉模板 → 跑生成脚本 → 修剪，十分钟可用。
- 重要会话开头让 agent 复述一遍关键环境信息，确认文件真的被加载了。

## 总结

`tools.md` 的本质，是把"我的机器长什么样"从隐式经验变成显式、可版本化、可审计的上下文。写模型猜不到的，控制体积，密钥不落盘，定期对账——做到这四条，agent 在任何一台新机器上都能少猜九成。
