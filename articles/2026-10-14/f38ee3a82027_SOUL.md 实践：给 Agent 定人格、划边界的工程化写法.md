## 背景

OpenClaw 的工作区里有几个约定俗成的 markdown 文件：`AGENTS.md` 管任务规则，`USER.md` 管用户画像，`SOUL.md` 管"这个 Agent 是谁"。SOUL.md 每轮会话都会被注入 system prompt，相当于 Agent 的长期契约。它不是玄学，就是一段会反复生效的自然语言配置，写得准，行为稳；写得虚，行为飘。

## 问题

我不写 SOUL.md 时踩到的三个实际问题：

1. **人格漂移**：换模型、升级版本后，语气和决策风格明显变化，昨天还简洁克制，今天开始满屏客套。
2. **边界靠自觉**：Agent 在授权场景里"举一反三"，比如允许它查日历后，它顺手替我回复了一条消息。能力给了，刹车没给。
3. **调优无从下手**：行为不对时只能对着聊天记录猜是哪句 prompt 出的问题，改一处全身抖。

## 做法

我现在的 SOUL.md 骨架，六段，控制在 40 行以内：

```markdown
# 身份
你是我的技术助理。定位：处理开发与运维琐事，不是聊天伙伴。

# 语气
- 简体中文，先结论后细节，默认不超过 200 字
- 不确定就说不确定，禁止编造路径和命令

# 边界（硬性）
- 未经我确认，不发送任何对外消息（消息/邮件/评论）
- 不读取 ~/.ssh、.env、钱包类目录
- 删除、付费、对外操作，先列计划等我点头

# 失败时的默认行为
- 工具连续失败 2 次就停下汇报，不自行换路子硬试

# 关系
- 我的话也可能情绪化，按事实处理，不顺着情绪走
```

三条要点：

1. **写行为，不写形容词**。"友好专业"没有信息量，"先结论后细节、不超过 200 字"才是可执行的。LLM 对具体指令的遵循度远高于抽象人格描述。
2. **正面示例一段顶十条**。在文件末尾贴一个"理想回复示例"，few-shot 的稳定性比我预想的好。
3. **边界必须可验证**。"别乱来"没用；"未经确认不发消息"能在出事后明确定位是哪条约束失效了。

## 踩坑点

- **写太长**。第一版我写了 150 行，重点被稀释，模型开始选择性失忆；砍到 40 行后遵循度反而上升。SOUL.md 每轮都进上下文，越长越贵也越糊。
- **和 AGENTS.md 抢活**。把任务流程塞进 SOUL.md，两边冲突时行为随机。人格归 SOUL.md，流程归 AGENTS.md。
- **绝对化边界导致过度拒绝**。"永远不要发消息"导致我确认后它也不发。改成条件式："仅在我回复'确认'后发送"。
- **改完不留档**。用 git 管理 workspace，每次改动单独提交并写明原因，出问题能 diff 出"哪次改动引入的行为"。
- **跨模型假设**。同一句"克制一点"，不同模型解读差异很大。换模型后用一组固定测试问题回归一遍，再决定要不要改措辞。

## 可复用建议

- **人格与权限做双保险**：SOUL.md 写"不做"，工具层/权限配置保证"做不了"。纯靠 prompt 的边界只是君子协定。
- **一次只改一处**，改完跑固定测试集（我留了 8 个典型问题），避免"改 A 坏 B"。
- **敏感信息别进 SOUL.md**。它是每轮都会发送的上下文，不是保险箱。

## 总结

SOUL.md 不是给 AI"注入灵魂"的仪式，而是一份需要版本化、可回归验证的长期 prompt 契约。我的经验浓缩成三句：人格写行为不写形容词，边界写条件不写禁令，改一处测一轮。它决定不了 Agent 的上限，但能兜住下限。
