# 背景

OpenClaw 的 cron 任务，本质是"定时触发的独立会话"：到点后系统把 instruction 注入一个全新 session，agent 跑完把结果送到指定渠道。它不是"接着昨天聊天继续"的那种对话——没有历史、没有上下文，也没人在场回答反问。

很多人把 cron instruction 当聊天消息写，比如"早上八点看看新闻总结给我"。这种写法在即时对话里勉强能用，放进 cron 就会暴露各种问题。

# 问题

实际踩过的坑大致三类：

1. **信息不自足**。agent 不知道今天几号、你在哪个时区、总结完发到哪。"给我发消息"在 cron 里是无效指令——没人能回答它的追问。
2. **失败不可见**。数据源挂了、搜索结果为空，agent 沉默。你分不清"任务没跑"和"跑了但没事发生"。
3. **指令过载**。三四个不相关任务塞进一条 instruction，或贴一大段静态资料，跑起来范围失控，输出又臭又长。

# 做法

把每条 cron instruction 当成一份"独立任务简报"来写，五个要素：

- **时间锚点**：写明"以系统当前时间为准，时区 Asia/Shanghai"（若平台支持时间占位符则用占位符）。日期相关的任务必须带时区。
- **任务与边界**：动词明确，"查 X、筛 Y"，再补一句"只做这些，不要展开其他动作"。
- **输出规格**：条数上限、格式（要点/一句话）、发送渠道在 job 配置里指定，instruction 里再写清收件人和格式，双保险。
- **失败分支**：明确写"如果结果为空或执行失败，回复'今日无更新'，不要猜测、不要编造"。这一条让沉默变成信号。
- **保持短小**：两三百字以内。长篇静态内容放 workspace 文档，instruction 只写"参考 xxx.md"，让 agent 现场读。

一个可复用的骨架：

> 以当前系统时间（Asia/Shanghai）为准。任务：……。步骤：1) …… 2) ……。输出：不超过 5 条要点，发送到 \<channel\>。若数据为空或出错，回复"今日无更新"。

配套两条工程习惯：

- **一个 job 一个目的**。日报、提醒、监控分开建，各自调频率，互不干扰。
- **先跑一次再上线**。新建任务先设一个几分钟后的触发时间，发到测试渠道，确认格式和送达没问题，再改成正式周期。

# 踩坑点

- **时区**。服务器多为 UTC，写 `0 8 * * *` 实际是北京时间 16 点。cron 表达式的时区和 instruction 里的时区要一起核对。
- **密钥进 instruction**。别把 token、密码写进定时提示词，放环境变量或受控文件。
- **有副作用的任务没护栏**。"帮我把这条发出去"如果周期配错就会重复执行，加一句"今天已发过则跳过"。
- **假设工具可用**。任务要联网搜索，但对应 session 没开对应技能，agent 只会硬编。上线前确认该 job 用到的工具已启用。

# 可复用建议

- job 命名带语义：`daily-news-digest`、`weekly-review-reminder`，配一份简单登记文档（名称/周期/instruction 摘要），每季度回顾一次。
- instruction 改动像改代码：改了什么、为什么改，记一笔，效果退化时能回滚。
- 长期上下文（你的偏好、固定栏目）写进 workspace 文档，别在每条 instruction 里复制一遍。

# 总结

Cron instruction 不是聊天消息，是一段无人值守时也要能独立执行的"小程序"。**自足、显式输出、显式失败分支、够短**——守住这四条，定时任务会从"碰运气"变成"可预期"。
