## 背景

做 Agent 的同学大多遇到过同一个问题：工具越接越多，系统提示词越来越胖。接上十几个 MCP server 之后，光工具描述就能吃掉几千 token，模型在几十个候选工具里挑花了眼——选错率上升、首 token 延迟变长、账单变厚。

OpenClaw 的 Skills 机制就是冲着这个问题来的：把"能力"从**常驻**改成**按需**。核心思路是渐进式披露（progressive disclosure）——上下文里只保留一张轻量技能索引，真正干活时才把技能正文加载进来。

## 问题：全量加载的三个代价

- **上下文浪费**：工具描述每轮对话都在场，用不用都烧 token；
- **选择噪声**：候选越多，模型选错工具的概率越高；
- **维护困难**：能力散落在各种配置里，改一处动全身。

## 做法：三段式结构

一个 Skill 就是一个目录，通常包含三样东西：

1. **元数据（manifest）**：名字 + 一句话描述 + 触发条件，这部分常驻索引；
2. **正文（SKILL.md）**：详细步骤、参数约定、注意事项，按需读取；
3. **资源**：脚本、模板、参考文档，正文里引用，用到再取。

一个最小可用的 manifest 大概长这样：

```yaml
name: file-batch-rename
description: 当用户需要按规则批量重命名或整理文件时使用
trigger: 批量重命名 / rename / 整理文件
entry: SKILL.md
```

落地步骤：

1. 盘点现有 MCP 工具，按场景分组，把"低频但重要"的能力抽成 Skill；
2. 写 manifest，描述用"什么时候用我"的句式，别写成功能说明书；
3. 正文控制在 200 行以内，超了就拆成子技能；
4. 准备 10～20 条测试对话，验证触发命中率再上线；
5. 上线后记录每次触发日志，一周后回看命中率并修剪。

## 踩坑点

- **描述太泛**：写"帮你处理文件"等于没写，什么都匹配。要写成"当用户要求批量重命名或按规则整理文件时使用"；
- **索引膨胀**：技能列表本身也会变胖。索引控制在 30 个以内，超了就合并或做二级索引；
- **中英触发不一致**：用户混用中英文时，manifest 里最好把两种语言的高频场景都覆盖；
- **技能套技能没有出口**：Skill A 引用 B，B 又引用 A，务必设加载深度上限；
- **副作用不设门槛**：删数据、发消息这类操作，确认逻辑必须写进正文，不要指望模型自觉。

## 可复用建议

- 一个技能只做一件事，宁可多建几个小的；
- 描述是写给模型看的，站在"模型如何做决定"的角度措辞；
- 把触发日志做成周报，命中率长期低于 50% 的技能要么改描述要么下线；
- 技能包按目录组织，团队共享时带版本号，避免"我这能跑"式扯皮。

## 总结

Skills 机制的本质是给能力建索引：**索引常驻、正文按需、资源再懒加载**。它不提升模型本身的能力，但改变了上下文的组织方式——让有限的窗口装"目录"，而不是装"全书"。对已经接了一堆 MCP 工具的团队来说，这是成本最低的一次重构。
