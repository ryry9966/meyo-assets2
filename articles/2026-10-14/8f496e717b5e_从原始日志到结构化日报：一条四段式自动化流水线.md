## 背景

日报是典型的高频低价值劳动：数据其实全在日志里——git 提交、CI 结果、告警记录、agent 执行历史，但没人愿意每天花二十分钟从里面捞事实。我们的做法是把它做成流水线：定时触发、无人值守、产出直接推送到 IM 群。

## 问题

最直觉的方案是把原始日志整包丢给模型"帮我总结一下"。试过就会踩三个坑：一是上下文装不下，日志稍多就被截断；二是幻觉，模型会补全日志里不存在的"修复了某问题"；三是格式漂移，今天五个小节明天三个，没法归档比对。

根因在于：日志是给机器读的，不是给模型读的。找事实的活应该交给确定性代码，模型只做最后一公里的表达。

## 做法

流水线拆成四段，每段独立可跑、独立排障：

1. **采集**。用 OpenClaw 的 cron 任务（或系统 crontab）在每天固定时间触发，按源拉取过去 24 小时数据：git log、CI 状态、告警、agent 会话记录。一个源一个脚本，统一输出 JSON。
2. **清洗聚合**。纯代码，不过模型。去重、归类、计数，正则脱敏 token、密钥、内网 IP，中间结果落盘。
3. **结构化组装**。把中间产物映射到固定 schema，例如：

```json
{
  "date": "2025-06-12",
  "commits": { "total": 23, "highlights": ["..."] },
  "incidents": ["..."],
  "agent_runs": { "total": 41, "failed": 3 },
  "todos": ["..."]
}
```

schema 就是合同，字段和类型一旦定下就不轻易改。

4. **生成投递**。这一步才让 LLM 上场：输入只有结构化 JSON 和固定输出模板，按"概览 / 关键变更 / 异常与处理 / 待办"四节成文。产物存档一份，再走 webhook 推送。

## 踩坑点

- **时区**：日志时间戳是 UTC，日报按本地时间切窗，第一天就出现跨天错位。切窗逻辑单独封装，只在一处做转换。
- **日志轮转**：凌晨跑批时前一天尾部日志已被 rotate。改为延长保留期，采集脚本启动时校验窗口完整性，缺失即告警。
- **幂等**：手动重跑导致日报发两遍。以日期为幂等键，投递前查重。
- **格式漂移**：模型偶尔往输出里塞自造字段。产物先过 schema 校验，失败重试一次，再失败降级为原始摘要并告警。
- **脱敏时机**：脱敏必须发生在数据进入模型之前，不能指望模型自己"注意"。

## 可复用建议

- 先定 schema 再写 prompt，顺序反了会一直返工。
- 每阶段落盘中间产物，出问题时能区分是采集漏了还是生成跑偏。
- 采集脚本保持平台无关：先 shell/Python 跑通，再逐步封装成 MCP tool 或 skill，复用到周报、复盘等流程。
- 日报质量抖动时，先怀疑数据源，再怀疑 prompt。

## 总结

这条流水线的核心价值不是省下二十分钟，而是把事实采集与语言表达解耦：确定性代码负责数据，模型只负责措辞。结构固定之后，日报从"每天重新创作"变成"每天填充模板"，可靠性才立得住。后续把同一套 schema 复用到周报和事故复盘，边际成本很低。
