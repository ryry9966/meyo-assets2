## 背景

OpenClaw 的 agent 不是无状态的 API 调用，而是长期跑在你机器上的常驻助手：有 workspace、有记忆文件、会挂 MCP 工具、会在多个会话里代表你发言。SOUL.md 就是 workspace 里定义“这个 agent 是谁”的文件，每轮对话都会注入 system 上下文。它决定的不只是语气，还有行为边界和取舍优先级。

## 问题

SOUL.md 缺失或写得很敷衍时，常见症状：

- **语气漂移**：模型升级或长对话后，同一个 agent 忽然变得啰嗦、过度热情，或者反过来过度冷淡；
- **越界执行**：随口一句“看看这个 repo”，它直接 push 了分支；
- **记忆污染人格**：MEMORY.md 里积累的碎片逐渐覆盖你最初的设定；
- **多会话不一致**：在群里是一个人，私聊是另一个人。

这些都是“人格没有落盘”的表现——全靠模型默认值和临场发挥。

## 做法

我的 SOUL.md 控制在 40 行左右，分四段：

1. **身份**：一句话说清它是谁、代表谁说话。例如“你是我的工程助手，对外发言代表我个人风格，偏克制、直接”。
2. **语气与风格**：给 2-3 条可执行的描述，如“默认短回复；不确定就说不确定；不用感叹号轰炸”。
3. **原则**：写原则而不是规则清单。模型擅长泛化，“宁可少做，不可做错”一条，比二十条禁令有效。
4. **边界**：具体、可判定。比如：删除文件、对外发消息、付款类操作必须先确认；不主动给第三方发消息；不把 A 会话的内容带进 B 会话。

配套分工要清楚：SOUL.md 管“是谁”，AGENTS.md 管“怎么干活”（构建、测试、提交规范），USER.md 管你的个人事实。三者别混写。

维护方式：agent 表现不符合预期时，不要在对话里骂它，把结论写回 SOUL.md，用 git 管理，行为回归都能 diff 出原因。

## 踩坑点

- **写太长**。SOUL.md 每轮都吃 token，过长的规则列表还会让模型忽略中间段落。50 行以内是我验证过的上限。
- **形容词堆砌**。“聪明、友好、专业”没有约束力，写具体场景才有用。
- **文件间互相矛盾**。SOUL.md 说“先确认再动手”，AGENTS.md 里的自动化流程却要求直接执行，模型会随机选一边。改一处要全局检查。
- **边界收太死**。全是“不要”，agent 会畏手畏脚，什么都来问你，反而不可用。每条边界要配升级路径：“不确定时，问一句再动手”。
- **当成一次性配置**。换模型、升版本后行为会变。留一组固定测试 prompt，每次改完跑一遍再上线。

## 可复用建议

- 段落骨架直接抄：身份 → 语气 → 原则 → 边界 → 不确定时的升级方式，五段够用；
- 边界只写“可判定”的：能明确回答“刚才那次操作越界了吗”的规则才值得进文件；
- SOUL.md 进 git，和 workspace 其他文件一起版本化；
- 定期抽查 MEMORY.md，删掉与 SOUL.md 冲突的记忆条目，防人格被记忆带偏。

## 总结

SOUL.md 本质是在身份层做 prompt 工程，成本极低（几十行文本），收益是长期行为一致性。它不会让 agent 更聪明，但能防止它在你不在场的时候变成另一个人。第一版十分钟就能写完，之后靠日常摩擦持续修订——这比任何一次性的精细调教都划算。
