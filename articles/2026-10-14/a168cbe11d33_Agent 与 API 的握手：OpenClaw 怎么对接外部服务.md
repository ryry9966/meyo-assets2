## 背景

OpenClaw 的价值不在聊天本身，而在于它能替你动手：查单、发通知、跑脚本、调内部系统。要让 Agent 真正"动手"，绕不开和外部 API 打交道。这篇帖整理几个在社区里跑了一段时间的对接实践，说清楚选型、配置和踩坑，尽量少谈理念。

## 问题：三条路怎么选

对接外部服务，常见三种路径：

1. **MCP Server**：把第三方 API 包一层，暴露成标准工具，Agent 自主决定何时调用；
2. **插件/Skill**：封装成固定动作，路径可控，适合审批、发布这类出错代价高的操作；
3. **Cron/Webhook 自动化**：不走对话，定时或事件触发直接调 API，Agent 只负责生成参数。

选型原则很简单：需要模型自主组合的走 MCP；流程固定、高风险的走插件；与对话无关的走自动化。别为了"显得智能"把所有东西都暴露成工具——工具越多，误调用概率越高。

## 做法

以对接一个内部工单 API 为例：

1. **先写薄封装**。不让 Agent 直接面对原始 REST 接口，用 MCP 收敛成两三个语义明确的工具，如 `create_ticket`、`list_tickets`；
2. **工具描述写死、写细**。描述是给模型看的说明书，含糊的描述是误调用最大来源；
3. **凭证走环境变量**，权限最小化：查询与写入工具分开，写入加确认开关；
4. **联调期开 dry-run**：先让 Agent 输出它准备调用的工具和参数，人工核对再放行；
5. **接日志**：每次工具调用记录参数、耗时、返回码，出问题靠这个回溯。

示意配置（节选）：

```yaml
mcp:
  servers:
    tickets:
      command: ./mcp-tickets
      env:
        TICKETS_API_KEY: ${TICKETS_API_KEY}
      tools:
        - create_ticket   # 写操作，需确认
        - list_tickets    # 读操作
      timeout: 15s
      dry_run: true       # 联调期开启
```

## 踩坑点

- **超时卡死对话**：外部 API 慢会阻塞整轮推理。给每个工具设硬超时，长任务改异步加轮询；
- **重试副作用**：网络抖动自动重试，结果创建了三张一样的工单。非幂等接口务必带幂等键；
- **密钥进上下文**：有人把 key 写进工具描述"方便测试"，直接进了对话日志。密钥只放环境变量，这是红线；
- **限流**：Agent 连续多轮工具调用很容易触发 429，客户端侧加个令牌桶，比等服务端惩罚划算；
- **错误信息太"底层"**：把 `ECONNRESET` 原样抛给模型，它只会重试。翻译成人话——"5 秒超时，建议缩小查询范围"——模型才有机会自我修正。

## 可复用建议

- 一律自建薄封装层，第三方 API 变更时只改一处；
- 单个 Agent 的工具数量控制在个位数，宁少勿多；
- 写操作默认确认，读操作放宽；
- dry-run 和日志先跑顺，再逐步放开权限，不要反过来。

## 总结

Agent 对接外部服务，工程上没有魔法：薄封装、显式描述、最小权限、可观测。OpenClaw 给了 MCP 和插件两套抓手，选哪套取决于你信不信任模型自己做决定。先把失败路径设计好，成功路径自然就稳了。有更复杂的网关或鉴权方案，欢迎在评论区交流。
