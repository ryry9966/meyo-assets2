## 背景

`memory_recall` 是 Agent 长期记忆的入口：会话里遇到“上次怎么配的”“那个报错最后怎么解决的”这类问题时，Agent 调用它把历史记忆片段捞回上下文。我的实例默认走语义检索（向量相似度），跑了三个月后发现它在两类查询上持续翻车：**精确关键词**（报错码、配置项名、驼峰 ID）和**中文短查询**。于是停下来做了一次系统对比，把过程和结论记录在此。

## 问题

两条路线的短板都很典型：

- **语义检索**：擅长“意思相近但用词不同”的改写，但对代码、版本号、报错串这类高熵 token 很弱——embedding 把它们打散后，召回结果经常“语义对，但不相关”。
- **全文搜索**（BM25 / SQLite FTS5）：精确命中强，但中文不分词基本不可用，且对同义改写零容忍——搜“模型”找不到写着"LLM"的条目。

## 做法

1. **建评估集**：从真实会话里挑 40 条查询，每条标注应命中的记忆条目 ID，存成 YAML，写个脚本算 recall@5。这一步最重要。
2. **测语义路线**：换过三个 embedding 模型，发现语料只有 800 条左右时模型间差距不大；chunk 从 512 降到 256（按段落切）反而提升明显。
3. **测全文路线**：FTS5 默认 tokenizer 对中文是灾难（整段成一个 token），挂上 jieba 分词后 recall@5 从 0.2 提到 0.6。
4. **上混合**：双路各召回 top-10，RRF 融合取 top-5；查询含报错码/驼峰命名时给全文路加权，纯自然语言问句时给语义路加权。
5. **元数据过滤**：每条记忆带时间戳、来源、标签，先过滤再排序，收益比换模型还大。

## 踩坑点

- **刚写的记忆搜不到**：索引是批量重建的，改成写入后同步更新索引才正常。
- **小语料别急着上向量库**：记忆少于几百条时，全文往往就够了，语义检索反而“过度泛化”。
- **top-k 失控**：直接注入 10 条会撑爆上下文预算、稀释重点，最终限定 top-5 并做长度截断。
- **时效性**：半年前的旧方案排在昨晚刚改的新配置前面，加了指数时间衰减权重才修好。

## 可复用建议

- 先建 20 条查询的回归评估，再谈任何改动——没有数字的调优都是玄学。
- 记忆写入时带上结构化元数据，检索质量的上限往往在数据侧，不在模型侧。
- 混合召回 + RRF 是默认起点；实现上两路可共用一个 SQLite，不必引入独立向量库。
- 查询路由不用做重：一个正则判断“是否包含代码样 token”就够用。

## 总结

结论不意外，但没有捷径：语义和全文各解决一半问题。混合方案在我的评估集上把 recall@5 从单路最好的 0.68 提到 0.85。真正花时间的不是检索算法，而是分词、元数据、评估集这些“不性感”的工程细节。推荐的落地顺序：小语料先全文 → 建评估集 → 语义补盲区 → 混合融合 → 元数据过滤兜底。
