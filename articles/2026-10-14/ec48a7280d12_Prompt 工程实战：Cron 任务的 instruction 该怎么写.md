## 背景

OpenClaw 的 cron 任务，本质上是「定时把一段 instruction 喂给 agent」。不少人的做法是把交互聊天里调好的 prompt 直接搬过去，结果跑出来的东西要么没发到该发的地方，要么内容对不上，甚至编数据。我目前维护十几个定时任务（早报、监控摘要、周报草稿），踩过不少坑，把可复用的写法整理一下。

## 问题：cron 里的 agent 和你聊天的 agent 不一样

写 cron instruction 前，先认清三个约束：

1. **没有历史上下文**。每次触发基本是一次独立会话，「按我们之前说的」「上次那个」全部失效。
2. **不能追问**。凌晨触发时没人回答澄清问题，指令含糊它就只能猜。
3. **结果没人盯着**。产出落在 cron 自己的会话里，你不主动看就等于没跑。

所以 cron instruction 的定位不是聊天 prompt，而是一份**给无人值守执行者的任务书**。

## 做法：五段式模板

我现在的 cron instruction 都按这个骨架写：

```text
【背景】本条消息由定时任务触发，没有历史对话，缺信息时按默认规则处理，不要提问。
【任务】一句话说清要做什么。
【输入】数据来源：文件路径 / RSS / 关键词列表，越具体越好。
【输出】发到哪里（哪个会话/频道）、什么格式、多长、什么语言。
【异常】某一步失败时怎么办：如实标注失败，禁止编造内容。
```

以早报任务为例，关键句长这样：

> 读取 `~/notes/watchlist.md` 中的关键词；抓取配置里的三个 RSS 源，筛 24 小时内命中的条目；按来源分组发到 Telegram「日报」会话，每条一句话摘要加原文链接，全文不超过 300 字；任一源抓取失败，在对应分组标注「来源暂不可用」，不要补条目。

另外两步不能省：

- **让 agent 自己确认日期**：instruction 里写明「先用时间工具取当前日期（Asia/Shanghai）」，别依赖「今天」这种词，时区和触发时间经常对不上。
- **上线前手动触发**：同一份 instruction 先在交互会话里跑两三次，确认输出没问题再挂 cron；上线第一周回头翻它产出的会话记录，做微调。

## 踩坑点

- **对话式引用**：「就像我们昨天讨论的」——cron 没有昨天，相关背景要直接写全。
- **没写输出去向**：结果躺在 cron 会话里没人看，输出位置必须显式指定。
- **没写失败路径**：源挂了，agent 会「贴心地」编几条凑数。失败处理必须是一等公民。
- **一条 cron 塞多个任务**：改一个需求整条 instruction 重测，老老实实拆开。
- **配置写死在 instruction 里**：关键词、源列表这类易变内容放文件里，instruction 只引用路径，改配置不用动 cron。

## 可复用建议

1. 写完自检一遍：换成另一个人，在没有任何上下文的情况下，能不能仅凭这段文字照着执行？
2. 约束输出长度时，给「不超过 300 字」比给「简洁一点」有效得多。
3. 流程和配置分离：instruction 只管流程，易变内容全部外置成文件。
4. 像看监控一样定期回看 cron 产出，instruction 是要迭代的，不是一次写完的。

## 总结

Cron instruction 写得好不好，判据只有一个：**一个没有上下文、不能追问、无人监督的执行者，能不能仅凭这段文字把事做对**。把它当交接文档写，而不是当聊天消息发。模板就五段——背景、任务、输入、输出、异常，够用了。
