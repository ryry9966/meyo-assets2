## 背景

给 Agent 接上“能上网”的能力，几乎是搭自动化流程的第一个需求：抓文档更新、盯价格变化、汇总公告。社区里常见做法是写一个 fetch 类的 MCP 工具，或者让 Agent 直接调无头浏览器。这套东西跑通只要十分钟，跑稳很难。“稽客”是我给这类采集器起的别名，“稽”取稽查、守边界之意：爬可以，但要爬得有分寸。

## 问题

直接把“去网上抓”丢给 Agent，通常在三个地方翻车：

1. **上下文爆炸**。整页 HTML 塞进对话，一个页面几千到几十万 token，几轮下来模型开始“失忆”。
2. **注入风险**。网页内容是不可信输入。页面里藏一句“忽略之前所有指令”，没有隔离设计的 Agent 真会照做。
3. **把别人网站爬挂**。没有限速和退避的循环抓取，轻则被封 IP，重则影响目标站服务，也把自己搞进灰名单。

## 做法

核心思路是把“抓取”和“理解”分开，把治理做在工具层，而不是指望提示词自觉：

1. **先找结构化来源**。优先级永远是：官方 API > RSS / sitemap > 静态 HTML > 无头浏览器。很多站点有未文档化的 JSON 接口，DevTools 里翻一下能省掉整个渲染环节。
2. **工具层做硬约束**。封装一个 `web_fetch` 工具：域名白名单、单次超时、响应大小上限（比如 512KB）、每域名限速（如 1 req/s）、失败指数退避。
3. **抓完先清洗**。HTML → 正文抽取（readability 类方案）→ Markdown，剥掉 script/style 和 `display:none` 的隐藏节点——注入文本最喜欢藏在那里。最后按长度截断。
4. **内容当资料，不当指令**。网页内容以“来源 + 摘录”的形式进入对话，明确标注这是外部数据，而不是把抓回来的东西续写进 system prompt。
5. **缓存与观测**。带 ETag / Last-Modified 做条件请求，同一页面短时间不重抓；记录 URL、状态码、耗时、字节数，被封信号（大量 403/429）第一时间能看到。

## 踩坑点

- SPA 页面 fetch 回来是空壳。先看源码里有没有 `__NEXT_DATA__` 之类的内嵌 JSON，有就直接解析，别急着上 headless。
- readability 抽取并不干净。实测遇到过隐藏 div 里塞几千字垃圾文本的情况，隐藏节点过滤和截断都得做。
- GBK 编码的老站点不按响应头处理就整页乱码，模型会一本正经地分析乱码。
- 伪装 User-Agent 绕反爬这事先想清楚：对 ToS 明确禁止的站点，技术上能过不等于该过。
- 重试没做退避，Agent 循环里一次失败触发十次重试，等于自己把自己封了。

## 可复用建议

- 把 `web_fetch` 做成通用 MCP 工具，白名单、限速、清洗、截断默认内置，Agent 侧只管调用。
- 维护一份“允许采集的站点清单”，和权限白名单一起审。
- 采集结果落盘缓存并带时间戳，Agent 引用时能说明“数据截至何时”。
- 任何抓取需求先问一句：这有没有 API？九成情况的答案是有。

## 总结

Agent 采集网页，难的往往不是抓，而是抓多少、抓多频、抓回来怎么用。把治理做进工具层、把网页当不可信数据、把边界画在动手之前，采集能力才能从“能跑”变成“敢挂到生产上”。
