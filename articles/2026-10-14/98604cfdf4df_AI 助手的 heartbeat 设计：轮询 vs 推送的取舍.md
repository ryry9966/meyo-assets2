## 背景

OpenClaw 的 agent 是常驻运行的，除了被动响应消息，还需要「主动醒来」的能力：定时巡检、汇总日报、检查文件变更。官方的 heartbeat 就是为此设计的——agent 按固定间隔被唤醒一次，无事则返回 `HEARTBEAT_OK`，有事则执行并（可选）向你汇报。这本质上是一套轮询（polling）模型。

## 问题

轮询天然有两个矛盾：间隔太短，token 烧得快，还可能频繁打扰；间隔太长，事件发生后最多要等一个完整周期才有反应。而推送（push / webhook）延迟低、按需触发，但要求你有可达的入口、稳定的连接和幂等的处理逻辑。很多自动化翻车，不是选错了模型，而是没想清楚哪些事适合轮询、哪些事必须推送。

## 做法：轮询兜底 + 推送加速

我的方案是混合模型，分四步：

1. **分类事件**。agent 需要感知的事分三类：用户主动发起（消息、指令）、时间驱动（日报、巡检）、外部事件驱动（CI 失败、监控告警、邮件到达）。
2. **用户发起的走推送通道**，不需要 heartbeat 参与——消息平台本身就是事件推送，agent 被动响应即可。
3. **时间驱动和低优先级的外部事件走 heartbeat**：把 heartbeat prompt 写成「检查待办清单文件，无事返回 `HEARTBEAT_OK`，有事按优先级处理」，间隔从默认 30 分钟起步。
4. **高时效事件（如构建失败）单独走 webhook 或 cron 触发**，直接调起 agent 执行，不指望下一次 heartbeat 恰好撞上。

## 踩坑点

- **heartbeat 空转烧 token**：早期没写短路逻辑，每次唤醒都让模型「找点事做」，一天多烧不少 token。prompt 里必须明确：无事可做时只回复 `HEARTBEAT_OK`。
- **heartbeat 变成消息轰炸**：让它「有事就汇报」，结果每个小变化都发进聊天。改成只有超过阈值或需要决策的事才推送，其余写进状态文件等日报汇总。
- **轮询与推送重复触发**：webhook 刚处理完，下一次 heartbeat 又读到同一个状态文件，动作执行两遍。解法是所有任务写成幂等，处理前先检查状态标记。
- **并发写状态**：heartbeat 和用户消息同时触发的两个会话改同一个文件，出现脏写。给共享状态加简单文件锁，或约定各会话只写自己的目录。

## 可复用建议

- 间隔从保守值（30 分钟）开始，观察一周真实触发率再调。
- heartbeat 输出协议要极简：`HEARTBEAT_OK` 或「动作 + 原因」，方便日志分析和成本归因。
- 状态和任务放进 agent 可读的清单文件，让轮询变成「读清单」而不是「凭记忆找事」。
- 幂等优先于精确：轮询模型下重复触发是常态，不是异常。

## 总结

轮询换来的是简单和鲁棒：无需公网入口、断线自愈、实现成本近零，对个人 agent 场景通常划算。推送的价值在低延迟和高时效事件，但要把幂等和重试做扎实。OpenClaw 的 heartbeat 提供了轮询的骨架，把推送留给消息通道和定时任务——二者分工而不是二选一，是我实践下来最省心的形态。
