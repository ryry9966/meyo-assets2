## 背景

OpenClaw 的 agent 默认是"常驻"的：除了被动响应消息，还有一套 heartbeat 机制，按固定间隔把 agent 唤醒一次，让它主动检查有没有该做的事——读一遍 HEARTBEAT.md 里的清单、扫一眼邮件摘要、跑个定时汇总。单 agent 单渠道时这没什么可设计的，但接入渠道一多、任务一杂，"每次唤醒由什么触发"就会变成一个正经的架构问题。

## 问题

本质是两种唤醒模型的取舍：

- **轮询（polling）**：agent 定时醒来，主动看一遍状态。实现零成本、行为可预期；代价是没料也要付 token，且事件到响应平均要等半个周期。
- **推送（push）**：外部事件发生时（webhook、消息渠道、队列）主动敲 agent。延迟低、空闲零成本；但端点暴露、丢事件、重复投递、顺序问题都得自己扛。

难的不是二选一，而是你的事件根本不止一类。

## 做法

我们目前的方案是按延迟容忍度分流：

1. **给事件分类**。用户私聊、报警类：秒到分钟级，走推送（消息渠道本来就是推的，报警接 webhook）；RSS/邮件摘要、日报类：分钟到小时级可容忍，走轮询或 cron。
2. **轮询侧瘦身**。heartbeat 间隔别拍脑袋，先算账：日 token 消耗 ≈ 唤醒次数 × 单次唤醒 token。检查清单放在 HEARTBEAT.md 这类静态文件里让模型按需读，而不是全量塞进 prompt；并约定"无事则极简回复"，避免每次唤醒都触发长输出。
3. **推送侧做幂等**。webhook 至少一次投递是常态，事件带 id + 时间戳，agent 侧按 id 去重；处理进度用 cursor（比如最后处理到的邮件 id）落盘，重连后从 cursor 续跑，不靠会话记忆。
4. **兜底对账**。推送链路再可靠也留一条低频轮询当保险：比如 30 分钟一次空转检查，发现 cursor 落后就补拉。两条链路写同一个状态文件，结果天然合并。
5. **记录唤醒原因**。每次唤醒打一条日志：poll / push / cron，附 token 消耗。跑一周你自然知道哪条链路在烧钱。

## 踩坑点

- **心跳撞车**：cron 和 heartbeat 同时命中一个任务，用户收到两条重复播报。解法是任务层加"进行中/已完成"标记，唤醒后先看标记再动手。
- **深夜骚扰**：heartbeat 默认不分时段。务必设 active hours，非活跃时段只累积不打扰，到点合并成一条摘要。
- **本地部署暴露 webhook**：家庭 NAT 环境要么内网穿透，要么退回本地轮询队列，别为了推送硬开公网端点。
- **忙时唤醒**：上个任务没跑完 heartbeat 又来了。要么跳过等下个周期，要么入队，千万别并发两个会话互抢工具。
- **空转成本被低估**：30 分钟一次的心跳，单次带上完整系统提示词，一个月下来是真金白银。先测量，再调频率。

## 可复用建议

- 经验法则：延迟要求 < 几秒 → 推送；> 5–10 分钟 → 轮询；中间地带 → cron（本质是定时推送）。
- 别把单一机制信到死：推送为主必留低频轮询兜底；轮询事件升级为推送时，幂等要重做一遍。
- 把唤醒原因当一等公民记录，成本优化从日志开始，不从猜测开始。

## 总结

heartbeat 设计没有标准答案，只有事件分级：轮询买简单，推送买延迟。我们的默认配置是"低频轮询兜底 + 推送处理敏感事件 + cursor 去重 + active hours 静音"。建议先跑纯轮询拿到基线数据，再逐类事件迁到推送——每迁一类，token 账单和响应延迟都会立刻给你反馈。
