## 背景

在 OpenClaw 自动化实践中，一个任务被执行多次是常态而非例外：LLM 的工具调用可能因网络超时被框架重发，定时调度器可能在上轮任务超时后叠加触发，用户会手动点重跑，MCP 调用也可能在会话恢复时被重放。所以「逻辑写对了」并不够，还必须保证「多跑两遍也不会坏」——这就是幂等性。

## 问题

多数副作用操作天然不幂等：`send_message` 多发一条消息，`create_ticket` 多建一张工单，计数器加两次就翻倍。更麻烦的是，重试发生在多层——HTTP 层、工作流引擎、人工操作——任何一层都可能让一次逻辑任务物理执行 2~3 次。重复通知只是表象，更隐蔽的危害是状态被重复写入推偏，后续所有任务都在错误的状态上做决策。

## 做法

1. **先给操作分类**。只读查询天然幂等；「设置为目标值」类写入（upsert / ensure）天然幂等；真正危险的只有「追加 / 递增」类。尽量把操作往前两类靠，把「创建一条记录」改写成「确保存在自然键为 X 的记录」。
2. **建幂等键**。从业务语义派生稳定 key，如 `hash(trigger_id + 任务类型 + 目标对象)`，写入 SQLite/KV，执行前先查。key 必须跨重试保持一致，这是全部前提。
3. **意图日志 + 状态机**。执行前先落「即将执行」的意图，执行后写 done。中断重启后靠台账对账：有意图没 done，先查外部真实结果，而不是盲目重跑。
4. **key 全链路透传**。Agent 层生成的 key 通过参数传给 MCP 工具；工具层若自造 key，上层重试就完全防不住。

## 踩坑点

- **随机 UUID 当 key**：每次重试生成新 UUID，key 形同虚设。必须由业务语义派生。
- **check-then-set 竞态**：两个并发实例都先查「不存在」再插入，双双通过。用 SETNX 或数据库唯一约束这类原子操作，别在应用层「先查后插」。
- **TTL 太短**：key 过期后重试才来。TTL 要覆盖最大重试窗口，宁长勿短。
- **只防了正常路径**：副作用已发生但 done 没写入，重跑照样重复。意图日志必须先落，对账必须能查外部真实状态。

## 可复用建议

- 团队规范定一条：没有幂等键的递增类操作不允许上线。
- 工具设计优先 ensure 语义，让 Agent 先做一次廉价读，再决定写。
- 所有副作用尝试用 append-only 方式留痕，排查重复问题时全靠它。
- CI 里加一条测试：同一任务连跑两遍，断言无重复副作用。

## 总结

在 Agent 系统里，重复执行不是意外，而是日常。幂等性不是某个库的功能，而是一种设计契约：每个 MCP 工具都应当按「会被执行两次」来设计。代价是一个 key 加一份台账，收益是任何任务都可以放心重跑——重跑从赌博变成常规操作。
