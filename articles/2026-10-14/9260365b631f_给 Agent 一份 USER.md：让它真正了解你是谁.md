## 背景

重度使用 Agent 的人大多遇到过同一个场景：新开会话，第一件事是重新自我介绍。“我用 pnpm”“时区是 UTC+8”“回答直接给结论”。这些信息每次都要重复，根源在于 Agent 每个会话都是近乎白纸地启动——它知道怎么干活，但不知道你是谁。

OpenClaw 的 workspace 里有两个容易混淆的文件：AGENTS.md 描述“这个项目怎么干活”，USER.md 描述“我是什么样的人、在什么环境里干活”。前者是项目说明书，后者是你的用户画像。把 USER.md 用好，改动很小，收益贯穿所有会话。

## 问题

没有 USER.md 时，典型症状有三个：

1. 每次会话开头都要粘贴一遍偏好，忘一次就返工一次；
2. 方案的默认值总不对——推荐 npm 而你全团队用 pnpm，生成 UTC 时间而你固定在 UTC+8；
3. 风格不稳定：有时啰嗦有时精简，输出格式每次都变。

本质是“关于你的稳定事实”没有沉淀成一个启动时必读的持久层。

## 做法

USER.md 放在 workspace 根目录，OpenClaw 每次会话会自动加载。我的结构：

```markdown
# USER

## 身份与环境
- 后端开发，主力 Go / Python
- macOS + Docker，时区 UTC+8

## 工程偏好
- 前端 pnpm，Python 用 uv
- 改动必须带测试
- 提交信息遵循 Conventional Commits

## 沟通风格
- 先结论后解释，先代码后说明
- 不确定的事明说，不要编造
- 中文交流，代码注释用英文

## 红线
- 不要自动执行 git push
```

维护节奏：初始版本手写一次，之后每月回顾。也可以让 Agent 参与修订——月底跑一句“读 USER.md，对照近期我纠正过你的地方，提出修改建议”，人工确认后合并。

## 踩坑点

- **写太长**。我第一版 200 多行，每次会话白烧 token，关键条目反而被稀释。控制在 100 行内，只放高频且稳定的事实。
- **放敏感信息**。API key、内网地址、真实客户名不要进来——它会进入每一次对话上下文。USER.md 里只写“密钥走 .env，禁止硬编码”。
- **和 AGENTS.md 抢地盘**。“这个项目用 React”归 AGENTS.md，“我讨厌 class 组件”才归 USER.md。边界混乱会让两个文件互相矛盾，Agent 行为随机。
- **写愿望不写事实**。“请输出高质量代码”没有信息量。只收可执行、可验证的具体约定。
- **过期不清理**。换栈、换团队后旧条目还在。文件头加一行“最后更新日期”，强迫自己定期过目。
- **和 memory 混用**。USER.md 管稳定画像，memory 管滚动日志，“今天做了什么”不要写进 USER.md。

## 可复用建议

- workspace 放进私有 git 仓库，每次修订有 diff 可查，回滚方便；
- 分类固定为环境、技术栈、偏好、红线，新增条目先问“半年后还成立吗”；
- 红线放最前面，权重最高的约定值得最优先注入；
- 多项目场景可拆分：全局画像进 USER.md，项目级约定进各项目的 AGENTS.md。

## 总结

USER.md 本质上是把“每次口头重复的自己”变成“一份版本化的配置”。它不神奇，工程上只是把隐性上下文显性化、持久化。半小时写第一版，每月十分钟维护，换来的是每个新会话默认就在你的上下文里干活。对重度使用 Agent 的人来说，这是性价比最高的一类基础建设。
