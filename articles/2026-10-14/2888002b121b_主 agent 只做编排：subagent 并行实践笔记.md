## 背景

单 agent 串行干活有两个瓶颈：慢，以及上下文污染。比如让主 agent 同时调研三个库的用法、扫五个目录、读十几篇文档，大量中间内容会堆进它自己的上下文，最后既慢又容易"忘事"。subagent 的价值就在这里：把独立子任务派给多个子代理，各自持有独立上下文，主 agent 只收结果。在 OpenClaw 里，主 agent 可以通过工具调用派生独立的 subagent 会话，配合 MCP 工具和插件，这套模式是能落地的。

## 最初的问题

我一开始把"并行"理解成"同时发 N 个差不多的 prompt"，结果：子代理互相覆盖文件、返回内容长短不一没法聚合、token 消耗直接翻倍。根因是任务没拆干净，输入输出没有契约。

## 做法

以一次"给项目补齐 API 文档"为例：

1. **拆任务，先分读写**。只读型任务（扫代码、查文档、比对版本）才并行；凡是写文件的，拆成互不重叠的分片，或者干脆串行。
2. **给子代理定契约**。每个子代理的 prompt 固定三段：任务范围（只处理哪个模块）、工具白名单、返回格式。返回一律要求"结论摘要 + 关键文件路径 + 未解决问题"，限 300 字以内。
3. **主 agent 只做编排和聚合**。spawn 之后不掺和具体执行，收齐结果后自己汇总、去重、决定下一步。
4. **控制并发和失败**。并发压到 3~5，超时 5 分钟，失败重试一次，再失败降级为串行。
5. **限制深度**。禁止子代理再 spawn 子代理，编排层级最多一层，避免递归失控。

跑下来，原本约 40 分钟的串行扫描压缩到 12 分钟左右，主 agent 的上下文占用也明显下降。

## 踩坑点

- **子代理返回太长**：早期让它返回全文，聚合时把主上下文撑爆。改成"摘要+路径"后解决。
- **并发写同一文件**：两个子代理同时改一个 config，后写的覆盖先写的。写操作必须串行或按文件分片。
- **上下文传少了**：子代理不知道"不要动哪些东西"，产出跑偏。现在每个 prompt 里显式写负向约束。
- **工具权限没收紧**：子代理继承了全部 MCP 工具，一次误操作清了临时目录。之后按任务最小化分配工具集。
- **成本误判**：并行不是免费的，token 消耗近似 N 倍，低价值任务不值得并行。

## 可复用建议

- 把编排 prompt 沉淀成模板：任务描述、边界、返回格式、负向约束四段固定，只替换变量。
- 并发池和重试逻辑放到插件层实现，别让主 agent 用自然语言"记住"这些规则。
- 聚合单独做：去重、冲突检测、生成最终摘要，最好封装成一个独立的 MCP 工具或脚本，而不是靠模型即兴发挥。
- 每次跑完记录任务数、耗时、token 花费、失败率，攒几轮数据再决定哪些任务值得并行。

## 总结

subagent 编排的本质不是"多开几个 AI"，而是上下文隔离、任务分解、结果聚合这三件事。收益来自把只读、可拆分的脏活外包出去，让主 agent 保持在低上下文、高决策的状态。建议先拿两个子代理把契约和聚合跑通，再逐步放大并发，比一步到位靠谱得多。
