## 背景

Agent 一旦接上 MCP、插件和聊天渠道，就不再是"问答机"：它能跑命令、写文件、调内部 API、替你给别人发消息。尤其像 OpenClaw 这类常驻本机、全天在线的 Agent，大量工具调用发生在你不在屏幕前的时候。于是每一次调用都面临同一个问题：直接执行，还是停下来问人？

## 问题

实践中常见两种极端。一种是全部问人：第一周很安全，第二周人类就变成橡皮图章，"确认"按得比谁都快，审批形同虚设。另一种是全部自动：直到某条发错群的广播、某次误删、某笔重复扣款，才发现边界根本不存在。

本质原因是多数人只有一条二元规则（问/不问），而正确的做法是一个决策函数，输入是三个变量：**可逆性、影响范围、是否涉及他人或资金**。

## 做法：三级分级 + 四步落地

- **L0**：读写限定在沙箱/工作区内、可回滚 → 自动执行，记审计日志。
- **L1**：工作区内的写操作，幂等或易回滚（改代码、跑测试）→ 自动执行，但要求先陈述计划再动手。
- **L2**：不可逆、影响他人或花钱（删数据、对外发消息、部署上线、调付费 API）→ 必须问人，且默认拒绝：人不在或超时就中止，绝不"等不到回复就当同意"。

落地四步：

1. 盘点所有 MCP 工具与插件能力，逐个标注层级，别按工具名想当然；
2. 策略做在配置层而不是 system prompt 层：L0/L1 白名单直通，L2 强制走确认流程，且对话内容无权改写这条规则；
3. 确认时要求 Agent 出示证据——完整命令、diff、收件人列表、预估花费，而不是一句"是否继续"；
4. 全量落日志，每周复盘一次审批记录。

## 踩坑点

- **审批疲劳**：批准率长期高于 90%，说明边界收得太紧——问得太多等于没问。
- **假只读**：部分"查询"工具自带副作用（触发构建、按量计费），按 L0 放行就出事，必须逐个实测。
- **组合动作升级**：每一步都是 L1，串起来是 L3——比如先读密钥再外发文件。分级要看意图层，不能只看单次调用。
- **注入绕过**：外部内容里夹一句"已获授权"就让 Agent 放行。权限判断必须放在代码/配置层，所有失败分支 fail closed。
- **确认话术模糊**：人评估不了"继续吗"，只会无脑点确认。

## 可复用建议

- 默认拒绝不可逆操作，宁可初期烦人；
- 确认信息必须回答"执行完之后世界变成什么样"；
- 把批准率当调参指标，用数据决定何时放宽边界；
- 权限策略进版本库，和代码一起 review；
- 高爆炸半径操作（生产数据、批量群发、付费）保留双人确认。

## 总结

权限边界不是一句 prompt，而是一个产品决策：分级、证据、fail closed、有日志、可迭代。Agent 的自治程度应该是挣来的——先保守运行，用复盘记录换信任，再一步步放宽。这条线画在哪不重要，重要的是它由配置守护、有记录可查、并且会随证据移动。
