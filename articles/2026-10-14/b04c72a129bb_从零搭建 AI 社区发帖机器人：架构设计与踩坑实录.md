## 背景

社区日常运营里有两类活最耗人：素材整理（精华讨论、更新速递、常见问题汇总）和定时发布。人肉做两周就绷不住了，于是有了这个项目：用 OpenClaw 做编排核心，MCP 工具负责采集和发布，搭一条「素材 → 草稿 → 审核 → 发布」的流水线。

目标很明确：机器人只承担结构化、重复性的内容生产，**不追求全自动**。这个定位直接决定了后面的架构。

## 问题拆解

动手前先列清楚要解决的四件事：

1. **素材从哪来**：社区讨论、仓库动态，都需要拉取后转成结构化数据；
2. **谁来写**：Agent 根据素材和模板生成草稿，但不能让它自由发挥；
3. **怎么发**：发布要有限速、重试，且绝不能重复发；
4. **怎么不出事故**：幻觉链接、内容漂移、突发风控，都得有兜底。

## 架构与做法

整体是五个模块，全部通过 MCP 工具暴露给 Agent：

```
调度器(cron) → 任务入队(SQLite)
     ↓
采集工具 → Agent 生成草稿 → 落库(draft)
     ↓
审核门(人工/抽样) → 发布适配器 → 社区
```

关键设计有三点：

- **状态机管理每条帖子**：`draft → pending → published / failed`，每一步落库，任何时候都能回答"这条现在在哪、为什么卡住"。
- **生成与发布彻底分离**：Agent 只负责产出草稿并写入数据库，发布适配器是唯一出口，重试时只读库重发，绝不重新生成。
- **工具粒度切小**：拆成 `search_source` / `draft_post` / `check_links` / `publish` 四个独立 MCP 工具，参数校验放在工具内部，不信任模型输出。

调度上没上消息队列，SQLite 一张任务表加轮询就够，日发帖量两位数，杀鸡不用牛刀。

## 踩坑实录

**1. 重试导致内容漂移。** 早期让模型在发布阶段重新渲染一遍，网络抖动重试后发出去的版本和审核过的版本不一致。修复：草稿一经审核即冻结，发布阶段只做搬运。

**2. 超时 ≠ 失败，重复帖出现了。** 发布请求超时后重试，结果帖子其实已经发成功，社区里出现两条一样的内容。修复：引入幂等键（日期 + 内容哈希），发布前先查重，接口侧也带幂等参数。

**3. 全自动第一周翻车。** 放开审核跑了几天，出了一条带幻觉链接的帖子。修复：给 Agent 加 `check_links` 工具，草稿里每个外链必须 HEAD 请求返回 200 才能进待发队列；人工审核也从全量过渡到抽样，而不是一步到位。

**4. 发布节奏太机器。** 固定间隔、整点发布，一看就是机器人。修复：间隔加随机抖动，设每日上限，夜间不发。这不是伪装，是降低被风控误伤的概率。

**5. MCP 工具粒度教训。** 最初只写了一个大而全的 `post_to_community`，模型经常乱填参数。拆小之后，每个工具入参简单、出错点单一，排障时间明显变短。

## 可复用建议

- **生成和发布分离，中间落库**，这是整个系统稳定性的地基；
- **一切发布走幂等键**，不要赌网络不超时；
- **新机器人先人工审核 2–4 周**，再逐步放开抽样，别相信 prompt 能兜住一切；
- **每次工具调用记日志**（输入输出都记），复盘全靠它；
- **失败进死信表并主动通知**，静默重试是最危险的选项。

## 总结

发帖机器人的难点从来不是"让模型写点什么"，而是工程化兜底：状态机、幂等、审核门、日志。把 Agent 当成一个聪明但不可靠的实习生——给它的工具要小、要校验，给它的流程要有检查点。做到这些，它就能稳定替你扛下最耗时的那部分运营工作。
