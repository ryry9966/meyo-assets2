## 背景

社区日常运营里有一类重复劳动：把仓库更新、精华帖、外部资讯整理成固定格式的帖子发出去。量大、规律、价值密度低，很适合交给自动化。我基于 OpenClaw 搭了一个发帖机器人，跑了两个多月，累计发帖 140+，中途出过几次事故。这里把架构决策和踩坑记录下来，供有类似需求的同学参考。

## 目标与约束

- 内容源：GitHub release、社区 RSS、精华帖榜单，每天汇总一条日报
- 每条帖子必须过人审（至少冷启动阶段）
- 失败可重试，但绝不能重复发帖
- 不想写大而全的服务，尽量复用 agent + MCP 工具

## 架构：五层，生成与发布彻底分离

1. **调度层**：cron 触发，唯一入口，只负责"到点了，跑一次"，不带业务逻辑。
2. **采集层**：三个 MCP tool —— `fetch_rss`、`fetch_releases`、`fetch_hot_posts`，只做抓取和清洗，返回结构化 JSON。
3. **生成层**：agent 拿到 JSON 后按模板产出草稿，prompt 中写死"不得添加源数据之外的事实"。
4. **审核层**：草稿写入 SQLite，状态 `pending`，人工 approve 后进入发布队列。
5. **发布层**：独立的 publisher 插件，扫队列、调社区 API、回写状态。

关键决策是**生成和发布彻底切开**：agent 只产出草稿，永远不直接碰发帖 API。这是后面没出大事故的主要原因。

## 实施步骤

1. 先写三个 MCP tool，用 mock 数据调通 schema
2. 跑通"采集 → 生成 → 落库"，不接发布，先看一周草稿质量
3. 加 SQLite 状态表：`id、content_hash、status、created_at、posted_url`
4. 接发布 API，`content_hash` 加唯一索引做幂等
5. 加失败告警（webhook 通知）

## 踩坑实录

**坑 1：agent 编造条目。** 第一周草稿里出现一条源数据中不存在的"更新"，是模型自己补的。解法：prompt 要求逐条引用来源 URL，并在生成层之后加校验脚本——草稿中每个条目 URL 必须能在采集层原始 JSON 里找到，否则打回。

**坑 2：重复发帖。** 一次 cron 重叠执行（上一轮没跑完下一轮又触发），同一篇日报发了两遍。解法：发布前先 `INSERT` 一条 `posting` 状态记录，靠唯一索引抢锁，抢不到就跳过；cron 侧再加 flock。

**坑 3：时区。** 服务器是 UTC，我按本地时间理解的"每天早上"实际是下午，日报变成下午发。小事，但第一周很迷惑。

**坑 4：RSS 源结构变化。** 某个源把 `title` 改成了 `headline`，机器人连续三天发空条目且**没有报错**——抓取"成功"了，只是字段是 undefined。教训：tool 层必须对关键字段做断言，缺字段就显式失败。宁可失败，不要静默产出空内容。

**坑 5：模板漂移。** 模板改了三四次后，新旧草稿格式不一致，审核时难以对比。后来把模板版本号写进库，问题才收敛。

## 可复用建议

- agent 只生成，不发布；发布走独立、无智能的确定性代码
- 幂等靠数据库约束，不靠"程序记得发过了"
- 任何 LLM 产出，都要有一条不经过模型的校验路径
- 工具层宁可抛错，不要返回"看起来正常"的空数据
- 先 dry-run 一周再接真实发布，成本极低，收益极大

## 总结

这个项目代码量不大，真正的难点全在边界上：怎么防止模型多说、怎么防止系统重发、怎么让失败可见。把"生成"和"执行"切开，把智能限定在中间一层，其余都用最笨但最可靠的方式做。这套结构后来复用到周报和公告场景，基本只改 prompt 和模板就能跑。
