## 背景

OpenClaw 这类长期运行的 Agent，和普通聊天机器人最大的区别是生命周期：它跨天、跨渠道地为你服务，而 LLM 本身无状态，每次会话都是白纸。如果你发现自己每天都要重复“提交信息用中文”“别用这个端口”，说明记忆层没做好。OpenClaw 的 workspace 里其实已经有记忆底座（MEMORY.md、每日笔记、会话压缩、memory_search），但“有地方记”和“记得对、找得到”是两回事。

## 问题

自己搭记忆系统，最常见的失败不是“记不住”，而是：

1. **什么都记**，检索时噪音淹没信号，context 被无用记忆污染；
2. **只靠向量召回**，换个说法就搜不到；
3. **没有来源和时间**，三个月前的过时偏好还在影响输出；
4. **重复堆积**，同一条偏好被记了十几个变体，没人清理。

## 做法：三层分离 + 严格的写入路径

我把记忆拆成三层，目前跑得比较稳：

**1. 静态偏好层（手维护）**：硬性偏好、工具链、代码风格，固定放在一个 profile 文件里，每次会话开始直接注入。预算控制在 1k token 内，只放“几乎每次都用得上”的内容。这层不走检索，确定性最高。

**2. 情景层（自动写，按需读）**：每日笔记、会话压缩时顺手抽取的摘要。不进 system prompt，只通过 memory_search 按需召回。

**3. 检索层**：向量 + 关键词混合召回，叠加时间衰减权重。纯向量检索对“上周定的流程”这类带时间语义的查询很不可靠，关键词和日期过滤是必要兜底。

写入路径单独设计，用一个自定义 MCP 工具 `write_memory` 落盘，条目带 schema：

```yaml
type: preference | fact | oneoff
content: string
source: session_id
confidence: 0..1
created_at: ts
ttl: days | null
supersedes: id | null
```

关键规则：明确指令（“以后都……”）直接写；模型自行判断的内容先入低置信暂存区，复现几次再升级；一次性任务只进情景层；写入前先查重合并，冲突时新条目标记 supersedes，旧条目降权但不删，方便回滚。

## 踩坑点

- **让模型自己决定什么重要**：不加约束时它什么都想记，第一天就写了 40 条。改成“明确指令直接写、其余进暂存区”才稳定。
- **只做向量检索**：问“我上个月定的部署方式”召回不到，补了关键词索引和按日期过滤后才正常。
- **没有 TTL 和冲突处理**：换掉的包管理器、废弃的端口，旧记忆还会冒出来干扰。
- **敏感信息明文落盘**：API key、住址别进记忆文件，写入工具里加一层正则拦截。

## 可复用建议

- 条目必须带 `source` + 时间，清理时才知道“谁说的、多可信”。
- 静态层用“小而准”换“大而全”，超预算就说明该合并了。
- 攒一个 10~20 条的召回测试集（过去真实问过的问题），每次调检索参数跑一遍，别凭感觉。
- 每周跑一次 cron 任务做合并、降权和过期清理，别指望记忆自动收敛。

## 总结

记忆系统的本质不是“存得多”，而是**写入时严格、召回时克制**。三层分离解决“记什么”，带 schema 的写入工具解决“怎么记”，混合检索加衰减解决“怎么找”。OpenClaw 的 workspace 文件方案已经把底座铺好了，剩下的工程量主要在写入规则和定期维护上，这部分没有捷径，但做一次能吃很久。
