## 背景

用 OpenClaw 做自动化一段时间后，能力扩展基本走两条路：要么往系统提示词里堆说明文档，要么把所有工具都挂成 MCP server。前者上下文成本高——不管今天用不用，几百行说明常驻 token；后者工具列表膨胀，模型在几十个 tool 描述里挑花眼，还经常误调用。Skills 机制给了一个折中方案：把能力写成独立的技能文件夹，平时只暴露一行 name + description，触发时才加载正文。本质上是**渐进式披露**。

## 问题

具体到日常使用，痛点有三个：

- 一份 300 行的说明常驻 system prompt，多几个能力就几千 token 白烧；
- 全量挂载的 MCP 工具描述互相干扰，该用 A 工具时调了 B；
- 团队沉淀的 SOP（发布步骤、排障流程）只能靠人肉贴给模型，下次会话又丢了。

## Skills 的三级加载

理解加载时机是用好它的前提：

1. **元数据级**：启动时只有 name/description 进上下文，每个技能几十 token；
2. **正文级**：模型判断任务匹配时，才读取完整 SKILL.md；
3. **资源级**：SKILL.md 里引用的脚本、模板，按需执行或读取。

## 做法

1. **建目录**：`~/.openclaw/skills/deploy-check/`，内放 `SKILL.md`。
2. **写 frontmatter**：name 和 description。description 是唯一的"路由器"，要写"何时用"，不要写"这是什么"。反例：`部署相关知识`；正例：`当用户要求发布、回滚或检查线上服务状态时使用，包含发布前检查清单与回滚步骤`。
3. **正文控制在 200–500 行**：写判断性内容——步骤、边界条件、失败时怎么办，不要写模型本来就会的废话。
4. **确定性操作写成脚本**：放在同目录，SKILL.md 里明确写"执行 `scripts/check.sh`，不要手动逐步操作"。模型直接跑脚本，省 token 也稳定。
5. **重开会话验证**：用贴近真实使用的触发语问一句，确认技能被加载；再问一个不相关的问题，确认没被误触发。

## 踩坑点

- **description 写太泛**：要么永不触发，要么次次触发。它是唯一常驻的路由信息，值得反复打磨。
- **数量失控**：几十个技能的元数据本身就是上下文负担，定期删并。
- **同名技能重复**：全局目录和个人目录放了重名技能，加载顺序不确定，行为诡异。
- **把 Skills 当 MCP 用**：技能是"指令 + 脚本"，不是常驻连接。查数据库、调外部 API 这类实时工具仍走 MCP，技能只负责教模型怎么用好这些工具。
- **带副作用的脚本不加防护**：模型可能在不该跑的环境执行。脚本里自己加 dry-run 和环境检查，别指望模型自觉。

## 可复用建议

- **沉淀节奏**：同一件事手工教模型两次，就写成技能。这是最低成本的 SOP 固化。
- **一个技能只做一类事**：超过 500 行就拆，路由粒度太粗会误触发。
- **脚本管确定性，正文管判断**：不要在正文里复述脚本能干的事。
- **技能目录进 git**：团队共享同一套 SOP，评审和回滚都有据可查。

## 总结

Skills 的价值不在于"更多能力"，而在于"更便宜的按需能力"。元数据常驻、正文触发、资源按需的三级结构，把上下文预算花在刀刃上。在我们的实践中，它更适合定位成**团队 SOP 的执行载体**：人会排障、会发布的经验，写成技能后，助手第一次就能照着做对——这才是个体经验到系统能力的实际转化路径。
