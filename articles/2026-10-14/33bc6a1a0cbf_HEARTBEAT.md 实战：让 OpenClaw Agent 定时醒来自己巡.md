## 背景

大多数 Agent 的交互模型是"你问它答"：你不发消息，它就安静待着。但如果你跑的是 OpenClaw 这种常驻本地的个人助手，它完全可以定时醒来自己干活。HEARTBEAT.md 就是干这个的——workspace 根目录下的一个普通 Markdown 文件，Agent 每隔一段时间（默认 30 分钟，由 `HEARTBEAT_INTERVAL_SECS` 控制）被唤醒一次，读一遍文件，判断有没有该做的事。没有事做就回 `HEARTBEAT_OK`，静默通过，几乎不产生打扰。

## 问题

实践中两种典型翻车：

1. **心跳开着，文件是空的**：每次唤醒纯烧 token，什么都没干。
2. **把它当需求文档写**：塞了十几条模糊任务（"关心一下项目进展"），Agent 频繁汇报鸡毛蒜皮，通知轰炸，体验比不开心跳还差。

核心矛盾是：心跳给了 Agent 主动性，但主动性多吵人，完全取决于你把文件写成什么样。

## 做法

**Step 1**：配置里确认心跳开启，间隔先设长一点（如 1800 秒）观察行为，别一上来就调短。

**Step 2**：每条任务按"三段式"写清楚：

- **条件**：什么情况才算"该做"，必须带阈值或时间范围
- **动作**：具体、可一步执行的操作
- **静默规则**：不满足条件时回 `HEARTBEAT_OK`，保持安静

**Step 3**：参考写法：

```markdown
# HEARTBEAT

## 收件箱巡检
- 条件: GitHub 通知出现 review requested 或 CI 失败
- 动作: 摘要失败的 job 名和链接发我
- 静默: 全绿或仅红点通知 → HEARTBEAT_OK

## 磁盘空间
- 条件: 根分区剩余 < 15%
- 动作: 列出 /var/log 下最大的 3 个目录，不要自己删
- 静默: ≥15% → HEARTBEAT_OK
```

**Step 4**：手动触发一次心跳验证行为，再观察一两个周期，确认静默规则真的生效。

## 踩坑点

- **任务模糊 = 通知噪音**。每个任务必须可判定、有阈值，"帮我盯着点"这类写法直接毙掉。
- **心跳默认跑在主会话里**，和日常对话共享上下文。文件要保持轻量，别当备忘录堆东西，否则既污染上下文又拉高每次唤醒的成本。
- **精确时间的任务用 cron 更合适**（比如每天 9 点发日报）。心跳是"周期巡检"，不是"定时闹钟"，别混用。
- **多 Agent 场景**注意用分段/定向心跳，不然 A 的任务 B 也跟着执行一遍。
- **改完文件必须实测**。Agent 对条目的理解和你的预期不一定一致，尤其是"静默"边界。

## 可复用建议

- 模板固定为"条件 / 动作 / 静默"三行结构，新任务只按格式追加，不破坏现有条目。
- 静默规则里明确"有副作用的操作（删文件、给第三方发消息）先汇报、等确认，不要自作主张"。
- 每月清理一次：连续一个月没触发过的任务直接删，心跳文件不是仓库。
- token 敏感就把间隔拉长。心跳的价值在"该响的时候响"，不在高频空转。

## 总结

HEARTBEAT.md 的本质，是把 Agent 从"被动应答"升级为"周期性自主巡检"。但它不是一个智能开关，而是你和 Agent 之间的一份契约文件：写得多具体，它就多省心；写得多含糊，它就多吵人。建议从一两条带阈值、带静默规则的任务起步，跑稳了再逐步加，让主动性建立在可验证的规则上，而不是靠模型自由发挥。
