## 背景

跑自动化任务久了都会撞到同一个瓶颈：让一个 Agent 从调研、写代码、跑测试到整理报告一条龙做完，前期还行，越到后面越容易"失焦"——上下文被中间产物塞满，模型开始遗忘最初目标，甚至拿着过期信息继续改文件。

OpenClaw 这类框架本身支持在主会话里派生 subagent（通过 agent 工具或自定义 MCP 工具触发独立会话），所以问题从来不是"能不能并行"，而是**怎么拆、怎么收**。

## 问题

具体到我们最近的一个场景：批量给十几个仓库做依赖升级 + 跑回归测试 + 汇总报告。单 Agent 串行做，一轮要四十多分钟；更糟的是做到第五六个仓库时上下文已经很长，开始出现重复改同一个文件、漏跑测试这类低级错误。提速是次要的，**质量随上下文膨胀而劣化**才是主要矛盾。

## 做法

1. **主 Agent 只做编排**：拆任务、发任务、收结果、做最终决策，不亲自碰具体文件。
2. **按"独立工作区"切粒度**：一个 subagent 负责一个仓库，各自有独立会话和上下文，互不污染。
3. **派发时给完整任务简报**：仓库路径、分支、验收标准（测试通过、构建成功）、输出格式。记住 subagent 看不到你的聊天历史，要把它当成第一天入职的同事来交代。
4. **并发控制在 2–4 个**：收到的结果要求结构化摘要（结论 / 改动点 / 风险三段式），主 Agent 汇总后再决定是否需要人工介入。
5. **失败不自动重试**：先把失败原因收回来，由主 Agent 判断是环境问题还是任务描述问题，再决定重发还是升级处理。

## 踩坑点

- **最大的坑：subagent 返回结果太啰嗦。** 几个并行任务一收，主会话上下文瞬间被撑爆，编排者自己先失焦了。一定要在简报里写死"返回不超过 N 字的摘要"。
- **并行写同一个文件必然冲突。** 我们规定每个任务只写自己目录下的文件，共享产物（比如汇总表）只由主 Agent 写。
- **subagent 是"零起步"上下文。** 简报里少写一句"测试命令是 `pnpm test`"，它就会自己猜，猜错的代价是整轮重来。
- **并发太高撞 API 限流**，重试风暴比慢更糟。
- **别把强依赖任务硬拆并行。** B 需要 A 的产出时，串行反而省 token 也省心。

## 可复用建议

- 先把任务写成"给新同事的交接文档"，再判断哪些能并行——写不清楚简报的任务，通常也不适合拆出去。
- subagent 的核心价值是**上下文隔离**，不只是提速。需要干净上下文的子任务（代码评审、日志分析），即使串行也值得拆出去。
- 结果回传永远用结构化摘要，原始过程留在 subagent 自己的会话里，需要时再捞。
- 给每个 subagent 明确的完成标准，并约定"不确定就报失败"——宁可慢一轮，不要静默的错误结果。

## 总结

subagent 编排的本质不是"多开几个 AI"，而是**上下文管理**：主 Agent 保持轻量做决策，子任务在隔离环境里各自干完、摘要回传。拆得对，四十分钟的活能压到十分钟出头；拆得不对，token 翻倍，还多出一堆需要人工收拾的现场。

建议从两条约束起步：**每个 subagent 一个独立目录 + 结构化摘要回传**。跑顺了再加并发，别一上来就追求"十个 AI 齐飞"。
