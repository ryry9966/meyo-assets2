# OpenClaw 的 sandbox 安全模型：为什么 Agent 不会误删文件

## 背景

给 Agent 接上 shell 和文件工具之后，"它能干多少活"和"它能闯多少祸"是同一件事。自动化任务经常无人值守运行，MCP 插件又各自声明文件读写能力，一旦模型输出非预期命令——比如一个错误的 glob、一次工作目录漂移——损失就是实打实的。OpenClaw 在设计上不指望模型"自觉"，而是把安全做在运行时层。

## 问题

"误删"不是假设，而是几类高频真实场景：

1. **路径混淆**：Agent 在错误的 cwd 下执行 `rm -rf ./build`，删掉了不该删的目录；
2. **通配符失控**：`rm *.log` 在 shell 层展开后范围远超预期；
3. **提示词注入**：读进来的网页或文档内容诱导模型执行破坏性命令；
4. **软链逃逸**：workspace 里的符号链接指向 `~/.ssh` 或 `/etc`，删链接变成删目标。

仅靠 system prompt 写"请不要删除文件"是零约束力的，模型迟早会违反。防线必须落在工具和系统层。

## 做法：四层递进的 sandbox 模型

OpenClaw 的思路是分层兜底，每一层独立成立：

**第一层：workspace 边界。** Agent 默认被限制在一个 workspace 根目录内，边界外的路径在工具层直接不可见、不可写。所有路径先做 `realpath` 解析再校验，符号链接展开后越界的同样拒绝。

**第二层：破坏性命令拦截。** 对 `rm`、`rmdir`、`find -delete`、`dd` 等高危动词做策略匹配，命中后不是报错了事，而是**改写语义**——把删除重定向到 trash 目录：

```
deny:    rm -rf /  等绝对高危模式
transform: rm <path>  →  mv <path> ~/.trash/<timestamp>/
confirm: workspace 外的写入 → 转人工确认
```

关键点：匹配前必须解析成绝对路径并模拟 shell 展开，否则 `rm *` 这种字面上不含 `rm -rf` 的命令会漏网。

**第三层：OS 级强制。** Agent 进程跑在独立低权限用户下，用 Landlock / bubblewrap / 容器做挂载约束：敏感目录只读挂载或干脆不挂载，网络出口按需白名单。这一层不信任上面任何一层。

**第四层：可回滚 + 审计。** 批量写操作前自动快照（git init 或目录快照），每次写路径进审计日志。出问题能回放，出事故能定位。

四层的关系是"或"而非"与"：任何一层单独失效，其他层仍能阻止真实删除。

## 踩坑点

- **确认机制别让模型自答**：如果"确认"由模型自己输出 yes 完成，等于没确认。确认必须落到人工或确定性策略上。
- **trash 跨文件系统会失败**：`mv` 跨挂载点会退化为复制+删除，大目录可能静默失败，需要 fallback 到 copy-then-verify。
- **拦得太狠用户就会关沙箱**：allowlist 过严导致任务跑不通，用户一键禁用保护，反而更危险。按项目粒度调策略，别一刀切。
- **插件是旁路**：MCP 工具如果自带原生文件句柄，就绕过了命令拦截层。每个插件的 scope 要在宿主侧强制收窄，而不是信任插件声明。
- **cwd 漂移**：`cd` 之后相对路径全变，路径校验必须每次基于解析后的绝对路径重新做，不能缓存。

## 可复用建议

- 默认拒绝高危动词，删除一律先进 trash，保留期后再真删；
- 所有路径校验基于 realpath，workspace 边界在工具层和 OS 层各做一次；
- 批量操作前自动快照，写操作全量审计；
- 用对抗性 prompt 主动测试自己的沙箱，而不是等线上事故；
- 插件 scope 最小化，宿主侧强制执行。

## 总结

Agent 不误删文件，靠的不是模型聪明，而是系统让破坏性操作**要么不可能、要么可逆、要么需确认**。把安全放在 prompt 里是祈祷，放在运行时里才是工程。这套分层模型不依赖任何特定模型的能力上限，换模型、换版本，防线不变。
