## 背景

在 OpenClaw 里写插件、MCP 工具或定时自动化任务时，让 LLM 返回结构化 JSON 是最常见的模式。提示词里通常会写一句“请把结果放在 ```json 代码块中”。Demo 阶段一切正常，但任务一上量就会发现问题：同一个模型、同一份提示词，返回的"JSON"格式并不稳定。

## 问题

实测常见变体至少有：裸 JSON（无围栏）、```json / ```JSON / 无语言标注的 ```、结果前后带解说文字、JSON 字符串字段里嵌套代码块（含反引号）、全角引号混入、尾逗号、注释，以及 max_tokens 截断导致的残缺 JSON。很多人的第一版解析长这样：

```python
data = json.loads(resp.split("```json")[1].split("```")[0])
```

演示能跑，生产必挂。挂一次不只是这条消息失败——在自动化链路里，它会中断后续流程；更糟的情况是异常被 `except` 吞掉后返回空值，静默污染下游数据。

## 做法

我的思路是“分层提取 + 受控修复 + 校验 + 有界重试”，收口在一个统一解析函数里：

1. **分层提取**：优先正则匹配 ```json…```（大小写不敏感），失败则匹配 `<json>…</json>` 类标签，再失败退化到裸 JSON 检测——找第一个 `{` 或 `[`，用括号配对扫描定位闭合。每层命中即返回。
2. **字符串感知扫描**：括号配对时跳过引号内内容（处理 `\"` 转义），否则字段值里的花括号会算错层级。
3. **受控修复**：只做低风险操作——去尾逗号、全角引号转半角、去 `//` 注释；截断的 JSON 可尝试“逐步截断 + 补全闭合”或 json-repair 类库，但必须给结果打上 `truncated` 标记。
4. **Schema 校验**：解析成功不等于结果正确，用 pydantic / jsonschema 校验字段与类型，不通过按失败处理。
5. **有界重试**：失败时把原始输出和具体报错一起回传给模型，最多重试 2 次；仍失败则走兜底分支（默认值/跳过/告警），并完整落盘原始输出。

## 踩坑点

- `split("```json")` 对 ```JSON 和无语言标注的围栏直接失效；
- 贪婪正则 ```` ```(.*)``` ```` 遇到字段内嵌套反引号会抓多，应非贪婪并对齐最后一个围栏；
- 单引号转双引号的“修复”很危险，内容含撇号就会改坏数据，宁可不修；
- 括号计数不处理字符串转义，是最常见的隐蔽 bug；
- 截断修复可能“成功”但静默丢数据，列表类结果尤其要警惕；
- 温度调 0 不能保证格式稳定，别赌。

## 可复用建议

- 全项目只用一个解析入口，别每个脚本各写一份；
- 真实失败样本存成 fixture 加回归测试，解析器会越养越稳；
- 有 JSON mode / tool call / 结构化输出参数时优先用，标签解析只做兜底；
- 提示词里给一个标准输出示例，few-shot 锚定格式比“请严格输出 JSON”有效得多；
- 解析函数返回 `(ok, data, raw, error)` 四元组，让上游决定降级策略，别在解析层偷偷吞错。

## 总结

对 LLM 输出做解析，本质是在和“偶尔不守约的接口”打交道。防御性解析 = 分层提取兜住格式漂移、字符串感知扫描避免低级错误、schema 校验守住语义、有界重试留出恢复空间、原始日志保证可回溯。这套东西不复杂，但值得在第一个插件上线前就做好。
