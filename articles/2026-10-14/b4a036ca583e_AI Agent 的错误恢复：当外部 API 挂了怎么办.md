## 背景

Agent 跑久了你会发现，真正让人头疼的往往不是模型能力，而是它依赖的外部 API：LLM 供应商限流、搜索工具超时、内部 MCP server 重启。一次自动化任务里任何一个工具调用失败，轻则任务卡死，重则 Agent 在报错信息上"自由发挥"，给你编一个看起来合理的答案。

## 问题

实际出故障时，常见的几种死法：

1. **没设超时**，HTTP 请求无限挂起，任务队列被堵死；
2. **盲目重试**，对 4xx 也照样重试，既烧配额又掩盖配置错误；对 429 不加退避，把限流变成封禁；
3. **部分失败**，五步流程走到第三步挂了，从头重跑会导致重复扣款、重复发消息；
4. **模型即兴发挥**，把原始报错丢给 LLM，它可能把失败包装成"成功"。

## 做法

我们的思路是把错误处理收敛成一个统一的封装层，所有 MCP 工具调用都过这一层：

1. **错误分类**：只分四类——`TRANSIENT`（超时、5xx）、`RATE_LIMITED`（429）、`PERMANENT`（4xx、鉴权失败）、`DEGRADED`（断路器已打开）。重试只对前两类生效。
2. **退避重试**：指数退避加随机抖动，比如 1s/2s/4s ± 30%，最多 3 次，并设总时间预算。
3. **全链路超时**：HTTP 客户端、工具封装、任务级 deadline 三层都要设，取最小者生效。
4. **断路器**：连续失败 N 次后标记该工具不可用，冷却期内直接走降级路径，不再打爆对方。
5. **降级与告知**：关键工具预定义降级策略——切备用供应商、读缓存、或明确告诉模型"该工具不可用，跳过此步并向用户说明"。错误用结构化格式（错误码 + 一句话描述）注入上下文，不要丢堆栈。
6. **幂等与断点**：多步自动化在每步之间持久化状态，失败后从断点恢复；非幂等操作（支付、发消息）带幂等键，重试才安全。

## 踩坑点

- 重试非幂等操作，结果重复下单——我们交过最贵的学费；
- 退避不加抖动，几十个 Agent 实例同步重试，形成重试风暴；
- 400 也重试，三次之后还是 400，配额烧完了，真正的问题（参数拼错）反被日志淹没；
- 原始报错直接塞给模型，它回复"已成功处理"，实际啥也没干。要在 prompt 里约定失败协议，比如"工具返回 UNAVAILABLE 时必须输出 needs_attention，禁止推测结果"；
- 各层超时互相矛盾：任务级 10s、HTTP 层 30s，任务超时永远轮不到生效。

## 可复用建议

- 写一个通用工具包装器，统一超时 / 重试 / 断路器 / 结构化错误，新接入的 MCP 工具零成本获得这套能力；
- 处理任何错误前先回答三个问题：要不要重试？要不要降级？要告诉模型什么？
- 用故障注入做测试：CI 里放一个永远 500 的 mock 工具，观察 Agent 行为是否符合预期，这比线上救火便宜得多。

## 总结

错误恢复的目标不是消灭故障，而是让故障模式可预期、有边界：瞬时的重试，永久的快败，打不通的降级，搞不定的就明说。最危险的不是 API 挂掉，而是模型替你假装它没挂。
