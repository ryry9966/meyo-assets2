## 背景

OpenClaw 的主会话是按通道/联系人维度长期存在的：你日常对话、下指令，所有工具调用、命令输出、中间推理都会追加进同一个上下文。上下文是有限资源，塞得越多，模型对早期指令的遵从越差，token 开销也越高。

而长任务——批量整理文件、跑数据脚本、定时抓取，天然产生大量过程输出。这些输出如果全落在主会话里，出问题只是时间问题。

## 问题

我们实际遇到过的三种污染：

1. **过程噪音**：一个批量重命名任务，几十条命令输出直接刷进主会话，之后几天的对话质量明显下降。
2. **跨话题串扰**：昨晚调试脚本的上下文残留，让今天闲聊式提问的回答风格奇怪，甚至错误关联旧任务。
3. **并发覆盖**：两个定时任务同时往主会话写，结果交错，事后没法从 transcript 还原哪个任务说了什么。

## 做法

核心原则一句话：**过程留在子会话，结论回主会话**。

1. **用 spawn 子会话跑任务**。主会话下发任务描述后通过 `sessions_spawn` 起独立子 agent，子会话有自己的上下文，几十轮工具调用不会碰主会话。
2. **定义返回契约**。任务描述里写死：只返回结构化摘要——结论、关键数字、产物路径，不回传原始日志。主会话最终只多一两行记录。
3. **工作目录隔离**。给子任务单独目录（如 `tasks/<日期>-<任务名>/`），并在 AGENTS.md 里明确子 agent 不得改动 workspace 下的 SOUL.md、AGENTS.md，防止任务顺手"优化"了主 agent 的行为。
4. **工具收敛**。子 agent 只挂必需工具，尤其不给消息发送类工具，避免它绕过主会话直接给你发消息，出现两个声音。有条件再把命令执行放进 sandbox。
5. **生命周期管理**。设超时；结束后按需清理或归档 session，transcript 保留最近 N 个用于排障。

## 踩坑点

- **返回值也是污染源**。只隔离"过程"不够，子 agent 返回五千字原文，主会话照样被撑爆。返回契约必须写进任务描述，主会话拿到后也别"顺手全文转发"。
- **目录没隔离**。子任务把 workspace 下的配置当普通文件改了，主会话行为突变，排查半天才发现。子任务目录一定要显式指定。
- **session key 命名随意**。并发任务用了同一个 key，日志互相覆盖。用「日期+任务名+随机后缀」的规范，事后审计 transcript 才有迹可循。
- **清理过度**。为省磁盘把 transcript 全删了，出问题无法复现。保留滑动窗口即可。

## 可复用建议

- 固化任务描述模板：目标、输入、输出契约、目录、超时，五段式，每次 spawn 直接填。
- 在 AGENTS.md 写一条全局规则：预计超过 N 轮或大输出量的任务，必须 spawn 子会话执行。
- 每周看一眼 sessions 目录，确认没有失控的常驻子会话。

## 总结

session 隔离不是什么高级特性，本质是约束信息流向：子会话承担过程，主会话只接收结论。把返回契约、目录隔离、工具收敛这三件事做成默认习惯，主会话就能长期保持"干净"，长会话质量衰减的问题基本压得下去。
