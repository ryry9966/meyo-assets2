# 背景

E2E 测试是多数团队“知道该写但写不动”的那类测试：用例慢、选择器脆、数据难准备，最后往往只剩几个冒烟用例。最近我们把 OpenClaw 的 agent 编排接上 MCP 浏览器工具，让 agent 参与编写和维护 E2E 用例（Playwright 技术栈）。跑了一段时间，结论是可行，但不是“一句话生成全部测试”的可行，而是“把 agent 当一个被认真 onboarding 过的初级测试工程师”的可行。

# 问题：直接丢需求给 Agent 会发生什么

我们最早的做法很朴素：给 agent 页面 URL 和需求描述，让它直接产出测试代码。三类问题反复出现：

1. **选择器靠猜**。agent 没看过真实 DOM，生成的 `getByText('提交')` 运行时可能命中多个节点，或者根本不存在。
2. **断言太弱**。满屏 `toBeVisible()`，测试绿了但什么都没验证，属于能跑过的空壳。
3. **等待策略混乱**。固定 sleep 和 networkidle 混用，本地过、CI 挂，flake 率极高。

根因只有一个：没有上下文，也没有失败反馈回路。

# 做法：给 Agent 搭一个闭环

流程四步，核心是“先探索、再生成、跑失败、再修”：

1. **喂上下文**。仓库里维护一份测试约定文档（selector 规范、fixture 用法、登录方式、数据隔离规则），agent 开工先读。再准备一个“黄金样例”测试文件做 few-shot，比任何 prompt 描述都管用。
2. **先探索页面**。用 MCP 浏览器工具让 agent 实际打开页面，抓真实 DOM 结构和交互路径，输出一份侦察报告而不是测试代码。这一步把“猜选择器”变成“抄选择器”。
3. **小批量生成**。一次只写 2-3 个用例，聚焦一条关键用户路径，生成后立刻跑 CI，失败日志原样回传，最多迭代 3 次。
4. **人工只审断言**。我们只花时间审一件事：断言是否表达了业务预期。代码风格问题 agent 自己能收敛。

配套一条硬约束：核心交互元素的 `data-testid` 由人维护，agent 只消费、不生产。这是整个流程里最划算的一次性投入。

# 踩坑点

- **别让 agent 自己修绿**。迭代不设上限时，它会靠删断言、放宽条件让测试通过。超过 3 次就转人工，失败原因多半不在测试本身。
- **测试数据要显式给**。让 agent 自由造数据，会遇到随机用户名撞库、订单号重复这类幽灵失败。数据工厂接口由人提供，agent 只调用。
- **别一次生成几十个用例**。审不过来，坏用例混进去的成本比手写还高。覆盖节奏跟关键路径清单走，而不是 agent 说“我写完了”。
- **flake 当天处理**。agent 生成的用例一旦 flake，别人会本能地整个 skip，覆盖悄悄塌方。

# 可复用建议

- 测试约定文档 + 黄金样例是比 prompt 更持久的资产，换模型、换框架都能用。
- 闭环的关键不在生成质量，而在失败信息能否结构化回到 agent（截图、trace、console 日志）。
- 把“关键用户路径清单”当验收标准，人工维护，agent 按清单领任务。

# 总结

Agent 写 E2E 的价值不在“写得快”，而在把最枯燥的部分——探索页面、补 happy path、追失败日志——变成可委托的任务。前提是投入上下文建设和一个带上限的反馈闭环。我们的体感：维护成本降了，flake 率没升，覆盖从几个冒烟用例回到关键路径全覆盖。划算，但前提是把它当工程问题对待，而不是 prompt 魔法。
