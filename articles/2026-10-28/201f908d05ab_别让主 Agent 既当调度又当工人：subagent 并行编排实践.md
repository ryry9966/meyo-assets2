## 背景

单 agent 干活的瓶颈很直观：上下文有限、全程串行、所有中间产物堆在同一个会话里。我们最近做一个批量任务——给二十多个模块统一升级依赖并跑回归——单 agent 跑一轮要四十多分钟，中途检索内容一多就开始"忘事"，改着改着把前面确认过的约束丢掉。

这类任务的共性是：子任务输入独立、无共享可变状态、结果可以结构化合并。这正是 subagent 并行编排的适用场景。

## 核心问题

把编排和执行混在主 agent 里，有三个代价：

1. **上下文污染**：子任务的日志、中间文件、报错全进同一个上下文，很快撑爆；
2. **串行瓶颈**：任务间明明无依赖，却排队执行；
3. **故障耦合**：一个子任务失败，重试时往往把整个流程重跑。

## 做法

**第一步：判定可并行性。** 三条硬标准：输入互不依赖、不写同一份可变状态（同一仓库/同一配置文件不行）、结果能用统一 schema 描述。不满足就别硬拆，串行更稳。

**第二步：编排者与执行者分离。** 主 agent 只做拆分、分发、汇总，不亲自干活。编排 prompt 里明确三件事：子任务切分维度、每个子任务的工具白名单、统一的返回格式。

**第三步：隔离执行环境。** 涉及代码改动的子任务，各自用独立 git worktree 或独立目录；工具按子任务最小化授予，只读型任务不给写权限。

**第四步：控制并发与重试。** 并发上限从 3 开始验证；子任务设计成幂等的，失败单独重试，绝不整体重跑。

**第五步：结构化汇总。** 每个 subagent 只返回 JSON 摘要：状态、改动路径、关键结论、异常码。主 agent 先做机器校验（路径存在性、状态合法性），再做交叉判断。

一个最小编排结构：

```text
主 agent（编排者）
 ├─ 拆分：按模块切成 N 个独立子任务
 ├─ 分发：输入 + 工具白名单 + 返回 schema
 ├─ 并行执行：subagent 1..N（独立上下文 / 独立目录）
 └─ 汇总：收集 JSON → 校验 → 输出报告
```

改造后同样的批量升级任务，8 并发不到 7 分钟跑完，主 agent 上下文占用只有原来的一小部分。

## 踩坑点

- **子 agent 改同一个仓库**：早期没做 worktree 隔离，两个子任务同时改 package 文件，互相覆盖。凡是写操作，先隔离再并行。
- **返回原始日志**：有子任务把整份构建日志塞进返回值，主 agent 上下文瞬间膨胀，后续判断质量明显下降。返回值必须是摘要，日志落盘给路径即可。
- **没有并发上限**：一次性发出十几个 subagent，触发外部服务限流，重试风暴把成本翻倍。限流和退避要写进编排逻辑，不能指望子任务自觉。
- **子任务不幂等**：重试导致重复提交了两次 PR。副作用类操作加去重键，或改成"子任务只产出 diff，提交动作由主 agent 收口"。
- **排查困难**：并行之后出了问题难定位。每个 subagent 的输入、返回、耗时单独落一份 trace，这是事后能复盘的前提。

## 可复用建议

1. 先定义统一的子任务 schema（输入、工具白名单、返回格式），再写编排逻辑，顺序别反。
2. 从 2–3 个并行度开始验证整条链路，跑通再放大。
3. 汇总前先做机器可校验的检查，把主 agent 的判断力留给真正需要判断的部分。
4. 把"拆分标准 + 返回 schema"沉淀成编排模板，同类任务直接复用。

## 总结

subagent 编排的价值不在"多开几个 agent"，而在三件事：任务边界切得干净、上下文彼此隔离、结果有统一契约。做到这三点，并行才是加速；做不到，并行只是把混乱放大了数倍。建议从一个真实的批量任务入手，小并发跑通全链路，再逐步扩大规模。
