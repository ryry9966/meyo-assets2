## 背景

我们团队每天要出一份服务运行日报：请求量、错误 Top N、关键告警、重点变化摘要。以前靠人工登录几台机器 grep + 手动粘贴，一次 20–40 分钟，还经常漏项。日志源分散在 nginx access log、应用日志和一个错误上报服务里，格式各不相同。这篇帖子记录我用 OpenClaw 搭的“原始日志 → 结构化日报”流水线，思路可以平移到任何类似场景。

## 问题

最初偷懒的方案是把日志直接丢给 Agent 总结，结果暴露两个致命问题：

1. 一天的 access log 轻松上百万行，远超上下文，只能截断，结论基本靠猜；
2. 模型复述数字时会错、会编，而日报里最不能错的就是数字。

结论很清楚：**数字必须由确定性代码算，LLM 只负责把算好的结果“说成人话”。**

## 做法

整条流水线分四步，前三步确定性，第四步才让 Agent 介入：

**1. 收集层（确定性）**：一个脚本按固定时间窗（昨天 00:00–24:00，UTC+8）拉取三个日志源，用 jq 归一化成统一 JSON Lines，落盘为当天中间产物 `logs-YYYYMMDD.jsonl`。

**2. 聚合层（确定性）**：从中间产物算出请求总量、分状态码计数、错误 Top 10、P95/P99 耗时、环比变化，输出一个几百字节到几 KB 的统计 JSON 块。

**3. 叙述层（Agent）**：OpenClaw Agent 拿到统计 JSON + 仓库里版本化的提示词模板，输出日报的解读部分：异常点定位、可能原因、建议关注项。提示词里硬性约束：只允许引用输入 JSON 中出现过的数字，禁止外推。

**4. 分发层（确定性）**：渲染 Markdown 写入内部 wiki 固定目录，webhook 推到 IM 群。整条流水线由 cron 触发，Agent 通过 MCP 工具调用收集与分发脚本。

## 踩坑点

- **时区与时间窗**：机器是 UTC，按本地时间切“昨天”，导致早高峰数据进了前一天。修复：收集脚本显式写死 UTC+8 窗口。
- **静默失败**：日志源偶尔拉取失败，会生成“几乎为空”的日报，看起来像系统很安稳。修复：每层产物做最小 schema 校验，失败走独立告警，不发空报告。
- **输出格式漂移**：Agent 偶尔自作主张改标题层级、加 emoji，下游渲染错位。修复：分发层做一次结构断言，不合格自动重试一次。
- **字段变更**：上游升级把 `status` 改成 `status_code`，聚合层悄悄算出全零。修复：对全零结果做可疑性检查，直接报错。

## 可复用建议

1. **先聚合后生成**：任何“日志→报告”任务，先把数据压到 KB 级再喂 Agent，成本、稳定性、准确性三赢。
2. **中间产物落盘**：每步输出存文件，出问题可单步重跑，方便回溯。
3. **模板进仓库**：提示词跟代码走 review，改措辞和改逻辑一样提 PR。
4. **数字只来自代码**：Agent 输出里任何统计数字，必须能对回输入 JSON。
5. **从单源起步**：先只接一个日志源跑稳两周再扩，不要一上来全量接入。

## 总结

流水线上线约两个月，日报人工耗时从每天 30 分钟降到零，累计人工干预 3 次（均为上游字段变更）。核心经验一句话：**别让 LLM 碰原始日志，也别让它算数**。把它放在流水线中段做归纳和叙述，数据正确性交给确定性代码兜底。脚本骨架和模板结构整理后会发到社区仓库，欢迎踩坑交流。
