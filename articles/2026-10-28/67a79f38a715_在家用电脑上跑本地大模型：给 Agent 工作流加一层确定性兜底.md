## 背景

社区里不少人的 Agent + MCP 自动化链路已经跑起来了，但模型那一端基本都挂在云端 API 上。时间长了有三个现实问题：token 费用随任务频次线性上涨；自动化任务 7×24 打 API，限流和超时让流程变得脆弱；部分涉及本地文件和私人数据的工具调用，数据出境让人不放心。把其中一部分负载挪到本地，是很多工程党的自然下一步。

我自己的场景：一个每天定时跑的信息汇总 Agent，挂了几个 MCP 工具（文件检索、剪贴板、HTTP 抓取）。这类任务不需要顶级推理能力，本地 7B~14B 量化模型足够，还能无脑重试。

## 问题

本地部署的门槛不在"能不能跑起来"，而在三件事：

1. 硬件预算和模型规格的匹配——显存/内存的账要自己算；
2. Agent 场景对模型的要求和聊天场景完全不同：结构化输出、工具调用、超长 system prompt，这些恰恰是小模型的短板；
3. 运行时默认配置是为聊天设计的，直接拿来跑 Agent 会踩很多隐性坑。

## 做法

**第一步，盘点硬件。** 核心公式：显存占用 ≈ 模型体积 × 1.1 + KV cache。KV cache 与上下文长度成正比，Agent 的 system prompt 加工具定义轻松吃掉 8K~16K token，这部分经常被漏算。16G 显存跑 14B Q4 比较从容；8G 显存建议 7B Q4 起步；纯 CPU/内存也能跑，Mac 统一内存是另一条路。

**第二步，选运行时。** Ollama 上手最快，llama.cpp 可控性最强，显存富裕可以上 vLLM。关键是它们都暴露 OpenAI 兼容接口——接 OpenClaw 或任何 Agent 框架时，接入层代码一行不用改。

**第三步，选模型和量化。** Q4_K_M 是性价比拐点，再往下压（Q2/Q3）省的显存远不抵工具调用可靠性的损失。优先选官方声明支持 function calling 的模型，在 Agent 场景这是硬指标，不是加分项。

**第四步，改配置再接入。** Ollama 默认上下文只有 2K/4K，必须在启动参数或 Modelfile 里显式调大，否则 Agent 长提示词会被静默截断——这是我踩过最隐蔽的坑。然后把 base_url 指向本地端口，工具调用配合 JSON schema 约束。

**第五步，用真实任务压测。** 别拿"你好"测延迟。直接用你 Agent 的真实 prompt + 工具定义跑 20 个样本，统计工具调用成功率和首 token 延迟，这组数字才代表真实体验。

## 踩坑点

- **上下文截断是静默的**：不报错，只是 Agent 表现变蠢。很多人以为模型不行，其实是配置问题；
- **低量化毁工具调用**：聊天看起来还行，function call 的 JSON 经常缺字段、格式漂移；
- **显存溢出到内存后速度断崖式下跌**，有时比纯 CPU 推理还慢。宁可降一档模型规格，也别让系统 swap；
- **采样参数**：Agent 场景建议低温（0~0.3），结构化输出务必配合 JSON mode 或 grammar 约束，别靠 prompt 祈祷。

## 可复用建议

- 建一个 20 条真实任务的本地评测集，每次换模型、换量化跑一遍，比看排行榜有用得多；
- 接入层统一走 OpenAI 兼容协议，运行时可随时切换（本地 ↔ 云端），Agent 代码零改动；
- 做一层简单路由：简单任务（分类、摘要、改写）走本地，复杂推理走云端，综合成本能降一个量级；
- 把显存预算和上下文配置写成注释留在配置文件里，三个月后的自己会感谢现在的自己。

## 总结

本地 LLM 的价值不是"替代云端"，而是让 Agent 链路中高频、低难度、隐私敏感的那部分调用拥有确定性兜底。先算显存账，再选对量化档位，最后用真实任务验证工具调用可靠性——这三步做完，家用电脑上的大模型就不再是玩具，而是你自动化基础设施里可依赖的一环。
