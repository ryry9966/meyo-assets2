## 背景

OpenClaw-CN 社区的日常运营里有不少重复劳动：每周整理精华帖、给新帖做分类归档、把常见问题的答案沉淀成 FAQ 回复。手动做一遍大约要两小时，还容易漏帖。这些工作信息源封闭、规则清晰，很适合交给跑在 OpenClaw 上的 agent。这篇帖子记录我把它跑起来的完整过程：架构怎么定、工具怎么接，以及上线第一周踩过的坑。

## 动手前先划红线

事后看，最重要的决定是动手前明确的三条边界：

1. 机器人只做两类事：每周精华汇总帖草稿、新帖 FAQ 回复建议。
2. 默认人审：所有写操作先生成草稿，推送给我确认后才提交。
3. 机器人无状态：已处理帖子 ID、去重哈希、任务游标全部落 SQLite，agent 每次运行只读入必要上下文。

## 架构与实现

整体四层：

- **调度层**：cron 触发 OpenClaw 定时任务，每周一上午（显式指定 UTC+8）拉取过去 7 天新帖。
- **工具层**：自写一个极小的 MCP server，只暴露三个工具：`list_new_posts(since)`、`create_draft(topic_ids)`、`submit_post(draft_id, approve_token)`。社区 API 的鉴权、限流、重试全部封在这层，agent 不直接碰 HTTP。
- **Agent 层**：系统提示词约束输出为 JSON，引用内容必须带原帖 ID，禁止编造链接。
- **审批层**：草稿生成后推送 IM 并附带一次性 token，我确认后 `submit_post` 才真正调发帖接口。

代码量很小：MCP server 约 200 行 Python，提示词 60 行，调度配置 10 行。真正花时间的都在细节里。

## 踩坑实录

**坑 1：第一版直接给了发帖权限。** 测试时 agent 把汇总帖发进了“闲聊”版块，还因重试逻辑连发两条。教训：写操作必须拆成 draft + submit 两段，submit 需要显式 approve_token，一次一换。

**坑 2：API 的 CSRF token 会过期。** 起初把 token 缓存在进程变量里，跑两天后批量 401。改成请求前校验、失效自动刷新，再加指数退避重试，才稳定。

**坑 3：模型会“补全”不存在的链接。** 汇总帖里出现过两个格式完全正确、ID 却是编造的帖子 URL。解法：工具只返回帖子 ID，提示词强制引用只用 ID，提交前校验层逐条查库，ID 不存在直接拦截并触发重新生成。

**坑 4：时区。** cron 按 UTC 跑，第一版汇总帖凌晨两点就发出去了。所有时间落库统一转 UTC+8，调度配置里显式写时区，不再依赖默认值。

**坑 5：上下文膨胀。** 第一周新帖 180+ 条，全量塞给 agent 后响应慢、摘要质量下降。改成两段式：脚本先按版块和互动量粗筛出 30 条，agent 再精选 10 条写摘要，质量反而更好，token 开销降到原来三分之一。

## 可复用的建议

- 写操作一律“草稿 + 显式批准”，不要相信第一版提示词的自觉性。
- MCP 工具面尽量小，3~5 个足够；鉴权、限流、重试藏在工具实现里，不进上下文。
- 状态放外部存储，agent 保持无状态，方便重放和排查。
- 每次运行写一条结构化日志（输入摘要、工具调用、产出 ID），出问题能复盘。
- 上线前用只读模式空跑一周，观察草稿质量，再逐步放开审批。

## 总结

机器人上线三周，稳定产出每周汇总，FAQ 回复建议采纳率约七成。最大的收获不是省下的时间，而是“审批层 + 幂等提交”这套模式——它让 agent 接管写操作变得可控、可回滚。下一步打算把版块分类规则做成可配置文件，让社区成员也能贡献分类样例，逐步把人从粗筛环节里解放出来。
