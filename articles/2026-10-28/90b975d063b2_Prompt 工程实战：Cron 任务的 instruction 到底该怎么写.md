## 背景

OpenClaw 的 cron 任务本质上是「调度时间 + 一条 instruction」：到点后 agent 拿着这条指令独自跑完，把结果投递到指定会话或落盘。它和交互式聊天最大的区别是——没有人在线。你没法追问、纠偏、临时补充上下文。所以 cron instruction 的质量，基本决定了这个任务的可靠度上限。

我维护着十来个定时任务：早报摘要、issue 巡检、价格监控、周报草稿。踩过一轮坑后，把写法收敛成了固定结构。

## 问题

新手最常犯的错，是把 cron instruction 写成聊天话术，比如「每天早上帮我看看 XX 有什么新闻」。对话里这样没问题，因为有追问机会；放进 cron 就会暴露三类问题：

- **上下文缺失**：到点跑的是新会话，它不知道"XX"指哪些来源、要什么颗粒度；
- **输出失控**：没定格式和长度，推到手机上就是一屏小作文；
- **失败无定义**：MCP 工具超时、接口限流、当天没数据，指令里没写怎么办，agent 只能自由发挥或静默失败。

## 做法

我现在每条 cron instruction 都按六段写，可以直接当模板：

1. **一句话目标**：任务为什么存在，给 agent 一个自行取舍的标准；
2. **输入来源**：写明调用哪个工具/MCP、查哪些源，不要只写“查一下”；
3. **执行步骤**：编号列出，尽量确定性：收集 → 过滤 → 排序 → 生成；
4. **输出模板**：固定字段 + 字数上限，摘要类我一般限 200 字、列表不超 5 条；
5. **时间与送达**：时区口径写死（如“以系统时间，UTC+8"），空结果和失败要不要推送，都定下来；
6. **边界禁止**：不调用哪些工具、不执行写操作、不访问清单以外的站点。

一个可以直接抄的最小骨架：

> 任务：每日早报。调用〈工具名〉获取〈来源列表〉过去 24h 的更新，以系统时间 UTC+8 为口径。
> 步骤：1 收集；2 过滤只保留与 X 相关；3 按重要度排序；4 按模板输出。
> 输出：3 条以内，每条不超过 40 字，末尾附数据时间戳；无符合条目时发送「今日无更新」。
> 禁止：访问来源之外的地址；执行任何写操作。

## 踩坑点

- **"今天/早上”是隐患**：任务 07:00 触发，服务器时区不同就是另一个"今天"，时间口径必须显式；
- **依赖会话记忆**：聊天里说过“只关注 A"，cron 的隔离会话未必知道，关键上下文要复制进指令；
- **一个任务塞五件事**：任何一步失败整条报废，拆成多个 cron 各管各的；
- **没做幂等**：修完 bug 补跑一次就推两份重复，输出要么覆盖同一文件，要么带日期去重；
- **空结果策略没定**：监控任务“没消息”到底是没数据还是没跑成？写清楚。

## 可复用建议

- 把 instruction 当「给实习生的工单」写：自包含、可验证、附一条验收样例，写完想象陌生人拿它能否一次做对；
- 上线前手动触发两三次，再用短周期（如每 30 分钟）观察 3~5 个周期，再切正式频率；
- instruction 入 git，每次调整记一笔，方便回溯"输出从哪天开始变的"；
- 区分两类任务：值得打扰你的走推送，只需留档的写文件，别全涌进聊天窗口。

## 总结

cron instruction 不是一句话，而是一份用自然语言写的小型任务规格书：目标、来源、输出、失败预案都要落到纸面。写的时候多花十分钟，能省掉之后每天翻聊天记录找“它到底干了什么”的时间。定时任务的可靠性从来不在调度表达式里，而在那条 instruction 里。
