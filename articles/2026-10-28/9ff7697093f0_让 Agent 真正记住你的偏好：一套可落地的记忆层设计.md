## 背景

做 Agent 的人大概都遇到过：上周明明告诉助手“项目用 pnpm，别用 npm”，这周它又开始 `npm install`。原因很朴素——LLM 本身无状态，会话结束记忆就没了；靠上下文窗口硬扛，既贵又不稳定。这篇文章记录我在 OpenClaw 插件里给助手加记忆层的一版实践，思路可以搬到任何支持 MCP 工具的 Agent 框架。

## 问题

三种常见做法都不太行：

1. **全量塞 system prompt**：token 成本线性涨，无关记忆还会稀释指令注意力；
2. **对聊天记录做 RAG**：召回粒度太碎，“用户偏好 Python”这种事实被淹没在寒暄里；
3. **指望模型“自己记着”**：不存在的，跨会话就是丢。

真正需要的是一个独立记忆层：有提取、有去重、有失效机制。

## 做法

我的结构分四步：

1. **记忆分型**。三类分开存：用户偏好（稳定，如技术栈、表达习惯）、项目上下文（半稳定，如路径、团队约定）、会话草稿（临时，会话结束即弃）。只有前两类持久化。
2. **结构化提取**。会话结束后跑一遍提取 pass，让模型只输出显式陈述的偏好/事实，固定 JSON：`{key, value, scope, confidence}`。不是每个字都要记，置信度低直接丢。
3. **去重与冲突处理**。以 `(scope, key)` 为主键，新值先查旧值：相同则更新 `updated_at` 和 `hit_count`；冲突则不覆盖，标记 `conflict` 交用户裁决，保留版本链。
4. **注入与衰减**。会话启动时按 `recency × hit_count` 排序取 top-N（我硬限 300 token 内）注入 system prompt 的一段小区域；30 天未命中进冷区，90 天未命中归档。

落地形态：用 MCP server 暴露 `memory.write / memory.search / memory.list` 三个工具，Agent 自己决定读写时机。存储起步一个 SQLite 就够，不必上向量库——key-value 加模糊匹配覆盖了九成场景。

## 踩坑

- **提取太激进**：早期把整个会话喂给提取器，记忆库很快变成噪音堆，注入后反而干扰执行。收窄到“只记显式偏好陈述”后才稳定。
- **过期记忆比没记忆更糟**：用户换了构建工具，旧记忆让助手反复坚持旧方案。衰减和冲突标记是必须的，不能只增不改。
- **注入挤占指令**：记忆块超过约 500 token 后，助手开始“忆大于令”，把过时偏好当命令执行。要硬限长度、按权重截断。
- **隐私泄漏**：记忆里出现过 API key 和内网地址。scope 要区分 personal / project / sensitive，sensitive 级别只存本地、不参与任何同步。

## 可复用建议

- 先做 KV + 显式提取，别一上来就上向量库和知识图谱；
- 记忆必须可见可编辑，给用户 `list / delete` 入口——信任问题比技术问题大；
- 写一组回归用例：“告知偏好 X 后隔会话是否遵守”，每次改动跑一遍；
- 所有写入带 `source` 和 `updated_at`，排障时能还原“它为什么这么想”。

## 总结

Agent 记忆不是玄学，本质上是一个带衰减的 ETL：提取 → 去重/冲突 → 注入 → 衰减。每一步都做简单、可观测，比一个聪明但黑盒的“记忆大脑”可靠得多。当前版本跑了一个月，偏好遵从率改善明显，但冲突裁决仍太依赖人工——下一步打算让助手在检测到冲突时主动向用户确认，而不是沉默地选边。
