## 背景

Agent 能做的事越来越多：跑 exec、读写文件、挂 MCP 工具、装各种插件，定时任务还能在你睡觉时自己跑。真正的问题早就不是"它能不能做到"，而是"这件事该不该不问我就做"。边界设计不好只有两种结局：全放开，一次事故毁掉所有信任；全都确认，人变成点确认的橡皮图章，Agent 退化成一个昂贵的自动补全。

## 问题

大多数人的配置是二值的：某个工具要么允许、要么禁用。但风险不是由工具决定的，是由操作决定的。同一个 HTTP 工具，读配置和删生产数据是两回事；同一个 exec，跑测试和 curl 外部接口也是两回事。按工具粒度管权限，粒度太粗。

## 做法

我们的做法是给"操作"而不是"工具"分级。每次操作前过四个问题：

1. **可逆吗？** 能以同等成本回滚的（分支上的 commit、工作区内的编辑）风险低；删数据、花钱、对外发布的不可逆操作风险高。
2. **影响面多大？** 只碰自己的沙箱工作区，还是会触达外部——给别人发消息、动生产环境、产生费用。
3. **结果可自验吗？** 跑完能通过读状态确认成功的（文件在不在、服务起没起来），可以放；需要人判断"这样对不对"的，收紧。
4. **频率高吗？** 高频低危走自动化，低频高危走确认。

映射成三档：

- **T0 自动执行**：只读、沙箱内写入、dry-run。不确认，直接跑，记日志。
- **T1 执行后汇报**：可逆的写操作，限定在工作区/分支内，做完附 diff 汇报。
- **T2 必须确认**：外部副作用（对外发消息）、破坏性操作、不可逆操作、超出预设路径或预算的任何东西。确认消息必须带完整计划和回滚方式，超时默认拒绝。

落地到 OpenClaw 这类网关：用 MCP 的 server 分组把工具拆成只读集和写集，按会话发 allowlist；把高危工具包一层"提案工具"——Agent 调用时只返回执行计划而不真执行，人确认后才放行；exec 的审批级别和路径白名单单独配；定时任务（cron/heartbeat）一律降级为 T0+T1，产物进草稿或队列，等你醒了再发。

## 踩坑点

- **确认疲劳**：问得太多，人就会闭眼点确认，这比不问更危险。确认频率超过每天几条，就该回头收紧 T1 范围。
- **确认信息没营养**："要执行删除，确认吗？"是无效确认。必须要求 Agent 给出精确命令、影响范围、回滚命令，三缺一就打回。
- **exec 绕过门禁**：你把 HTTP 工具设成需确认，Agent 用 exec 里一句 curl 就绕过去了。边界必须覆盖 shell，而不是只管具名工具。
- **定时任务权限放大**：凌晨三点没人看确认。无人值守的任务只给只读和草稿权。
- **权限漂移**：每次图省事就往白名单加一条，半年后边界形同虚设。定期 review 审计日志，删掉没人动的白名单。

## 可复用建议

- 默认只读，写权限按需申请，别反过来。
- 对外说话、花钱、发布，这三类永远 T2，没有例外。
- 每次确认必须携带三件套：干什么、影响什么、怎么回滚。
- 无人值守 = 降级权限，写成硬规则。
- 审计日志比权限配置更重要——边界设错了，至少要能事后看见。

## 总结

权限边界不是一段 system prompt 能解决的，它是工程问题：把分级写进工具层和网关配置，让 Agent 想越权也没有路径。从严格起步，根据审计日志逐步放宽——信任是攒出来的，不是配置出来的。
