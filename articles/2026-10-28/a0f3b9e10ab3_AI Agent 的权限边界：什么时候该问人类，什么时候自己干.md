## 背景

跑过一段时间 Agent 自动化的人都会遇到同一个问题：工具给多了不敢放手，给少了它寸步难行。OpenClaw 这类框架把 shell、文件系统、MCP 工具、插件全部接进同一个上下文，能力上限很高，但权限边界没有默认答案——你得自己定义，而且要用工程手段定义，不能靠感觉。

## 问题：两种失败模式

- **全都要问**：agent 每写一个文件、每跑一条命令都停下来等人确认。人很快进入无脑点允许的状态，确认环节形同虚设，整个流程退化成慢速半自动。
- **全都不问**：agent 在一次调试中顺手删了构建目录，或者把测试通知发进了真实用户群。出事那一刻你才发现，某些工具从来就不该被静默调用。

两种模式的根因相同：没有按操作本身的性质分级，而是把所有工具当成一个整体在管。

## 做法：按可逆性 × 影响范围分级

我用两个维度给工具打标：**出错了能不能撤销**（可逆性），**错了影响多大**（影响范围）。大致分四档：

1. **L0 自动放行**：只读、纯本地。读文件、搜索、git status、跑本地测试。这类操作问人纯属浪费双方时间。
2. **L1 自动但留痕**：工作区内的写操作，且走 git 可回滚。改代码、建分支、commit。前提是仓库干净、有版本控制兜底。
3. **L2 首次确认、按模式放行**：装依赖、改配置这类低危但可累积的操作。第一次确认时明确授权范围（如"本次会话内允许 npm install"），而不是无限授权。
4. **L3 必问**：不可逆、出网、花钱、动别人的数据。发消息、部署、删数据、改 DNS、调付费 API，没有讨论空间。

落地步骤：

1. 盘点工具清单，逐个按矩阵打标。MCP 工具看服务端声明（readOnlyHint、destructiveHint 这类注解），没声明的默认按 L3 处理。
2. 在网关/插件层做工具级白名单和确认门，不要只写进 system prompt——提示词会被长上下文稀释，工具层拦截才是硬约束。
3. 给 shell 和部署类工具加 dry-run：先输出将要执行的命令和 diff，确认后再真跑。
4. 所有"问了/没问/谁批的"写审计日志，这是后续调阈值的唯一依据。
5. 每周复盘一次：打断次数、误放行次数、误打断次数，按数据调整分级。

## 踩坑点

- **确认疲劳**：一天弹 30 次确认，人必然开始盲批。我的经验是给单任务确认次数设上限，超过就 checkpoint 汇总一次问完。
- **问题没有上下文**："可以继续吗？"是无效确认。有效的问题必须包含：执行什么命令/改哪些文件、目标环境、怎么回滚。
- **隐性副作用**：有些标着只读的 MCP 工具会写外部缓存或触发 webhook。新工具接入时先在沙箱里跑一遍再定级。
- **超时语义没定义**：agent 问了人，人没回，然后呢？必须默认拒绝并挂起，而不是超时后自作主张继续。
- **代码执行是提权通道**：agent 能写文件又能执行代码，就等于绕过了工具白名单。沙箱和路径限制要一起上。

## 可复用建议

- 一句话原则：**可逆且局部 → 自动；不可逆或出网 → 问人**。
- 先严后松：从全 L3 起步，用审计数据逐步放开；反向操作（先松后紧）通常先出事故。
- 把分级结果写成随仓库维护的工具分级表，团队共用，别散落在个人配置里。
- 确认请求本身做成结构化的：what / where / diff / rollback 四要素齐了才允许弹给用户。

## 总结

权限边界不是"信不信任模型"的态度问题，而是可逆性、影响范围、上下文充分度三个变量的工程问题。分级放行、带上下文的确认、审计日志、定期调参——这套组合跑下来，agent 该快的地方快、该停的地方停，人才真正敢把自动化挂上去。
