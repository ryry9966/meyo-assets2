## 背景

OpenClaw 的 cron 任务本质上是"无人值守的 agent 会话"：到点触发，agent 拿着一段 instruction 独立跑完，再把结果发到指定渠道。和聊天场景最大的区别是——运行时没有任何人在线补充上下文，instruction 写成什么样，任务就执行成什么样。

## 问题

很多人把 cron instruction 写成聊天口吻，比如"每天早上帮我看一下 GitHub 通知，有重要的就提醒我"。交互场景这样说没问题，用户在线可以追问；放进 cron 就会翻车：

- "重要的"没有标准，agent 要么全量转发，要么随机漏报；
- 失败没人知道，你以为摘要发了，其实工具调用报错后它安静结束；
- "今天/昨天"这类相对时间在时区不一致时直接跑偏；
- 输出格式漂移，第三周的日报和第一周长得完全不一样。

## 做法

我的习惯是把 cron instruction 当成一份"夜班交接说明"来写，固定五段结构：

1. **任务一句话定义**：这个任务是什么、多久跑一次、给谁看。保证三个月后你回头看还能秒懂。
2. **上下文与资源**：工作目录、状态文件路径、可用的 MCP 工具、时区。明确写出"以 Asia/Shanghai 为准，取过去 24 小时"，别依赖默认。
3. **执行步骤**：按顺序列清楚，分支写判断规则，例如"某数据源为空则跳过并在结果中注明，不要臆测内容"。
4. **输出契约**：发到哪个渠道、格式模板、长度上限。日报类任务我直接给固定模板，字段宁可留空也不许自由发挥。
5. **失败与边界**：工具报错时向指定频道发一条失败通知；写明禁止事项（不调用付费接口、不做计划外写入）和单次运行预算。

写完后手动触发跑两三遍，确认输出符合契约，再启用定时。

## 踩坑点

- **依赖对话记忆**：cron 会话不一定带上次的聊天上下文。跨运行状态（如"上次处理到哪"）要落盘成文件，让任务自己读写。
- **硬约束埋中间**：长 instruction 里模型最容易忽略中部内容。输出格式、禁止事项放开头或结尾，必要时重复一次。
- **静默失败**：不写失败路径，agent 遇错可能自己"合理编造"一份结果。失败动作必须显式。
- **不考虑幂等**：任务重跑会不会重复推送？加个简单的时间戳/ID 去重，能省掉很多半夜撤回消息的尴尬。
- **一次写太复杂**：先跑通最小闭环再逐步加步骤。instruction 和代码一样需要迭代，不是一次写完的。

## 可复用建议

- instruction 存成文件进版本管理，改坏了能 diff、能回滚；
- 每次运行结果追加写日志，排障时按时间对账；
- 留一个 dry-run 开关，改动后先试跑再上线；
- 每月 review 一次输出质量——instruction 也会"腐化"，环境变了约束会失效。

## 总结

Cron instruction 不是一句聊天消息，而是一份微型任务规格书：目标、上下文、步骤、输出、兜底，五样齐了，无人值守才可靠。不必追求完美，但每一条写清楚的约束，都是凌晨三点少收一条废消息的保险。
