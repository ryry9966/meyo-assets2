36kr 最近把 Agent 竞争的下半场概括成一句话：**上下文正在成为新的价值衡量基线**。翻译成工程师语言就是——模型能力趋同之后，决定一个 Agent 好不好用的，不再是“底层模型有多聪明”，而是“每一次调用时，模型的工作记忆里到底装了什么”。这看起来像个技术细节，实际上正在改写 Agent 产品的技术路线、成本结构和护城河。这篇文章把这条判断拆开，讲清楚它从哪来、为什么成立、以及怎么用。

## 一、从“卷模型”到“卷上下文”：竞争逻辑已经切换

- 2023 年到 2024 年上半年，AI 竞争的主轴是模型能力：刷 benchmark、拼 reasoning、比窗口参数，那时模型之间的差距肉眼可见。
- 2025 年之后，头部模型在主流任务上高度趋同。对绝大多数商业场景，换一个同档模型带来的提升，往往小于把检索、记忆、工具返回结果整理好所带来的提升。
- 行业里反复出现一类现象：同一个模型，客服 Agent 只是把策略从“整段资料塞进上下文”改成“按意图分片检索”，问题解决率就能差出两位数百分点。

一句话总结：**模型是发动机，上下文是整车的供油、导航与路况系统**。发动机差距缩小后，胜负手自然移向后者。

## 二、上下文到底是什么：给 Agent 的工作记忆做解剖

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-28/0b19ca2f17f7e11b.png)

技术上，上下文（context）指模型单次推理时能“看到”的全部信息，由五部分构成：

1. **System prompt**：角色设定、行为规则、工具说明书；
2. **工具 schema 与调用结果**：Agent 执行动作后拿回的返回值；
3. **对话历史**：多轮交互的完整记录；
4. **RAG 检索片段**：从知识库里按需捞出的相关文档；
5. **长期记忆**：用户偏好、历史任务结论等跨会话信息。

窗口演进很快：GPT-3 时代只有 2K/4K token，如今 128K 是主流，Claude 到 200K，Gemini 标到 1M 级别。但要区分一件事：**窗口大小只是内存容量，不等于内存里装的东西是对的**。容量再大，装错内容，推理照样跑偏。

## 三、长窗口 ≠ 好上下文：两个绕不开的物理约束

- **Lost in the middle**：Stanford 2023 年的实测研究发现，模型对上下文开头和结尾的信息利用率高，中间部分显著衰减——把关键事实埋在 50 页材料正中间，模型大概率“看了但没看进去”。
- **Context rot**：Agent 执行轨迹越长，早期指令在后续推理中被稀释得越厉害，表现为中途“忘了目标”、重复劳动。做长任务的团队对此都有体感。
- **成本曲线**：token 计费随上下文长度线性上涨；attention 的理论计算量是平方级（各种工程优化只是压低常数）；KV cache 对显存的占用同样随长度增长。

所以“全都塞进去”是最贵的下策。**长窗口是给检索和压缩兜底的，不是给懒人兜底的。**

## 四、上下文工程：一门正在成体系的新手艺

2025 年，Karpathy 把 context engineering 这个说法带火：它比 prompt engineering 大一个量级——后者研究“怎么问”，前者研究“每次调用前，给模型喂什么”。目前的主流手段：

- **RAG 按需检索**：不预载全部资料，按当前步骤动态取用；
- **Compaction（压缩摘要）**：旧对话滚动摘要，只保留结论和关键状态；
- **结构化外部记忆**：用文件系统、数据库当第二大脑，上下文里只放索引和指针；
- **子 Agent 隔离**：把大任务拆给子上下文并行处理，只回传结论，避免主上下文被过程噪音灌爆；
- **Prompt caching**：稳定前缀缓存复用，成本与延迟同时下降。

这些手段单看都不新鲜；组合成管线、并且能被量化评估，才是真正的门槛。

## 五、上下文即资产：商业价值的计量方式在变

- Web2 时代的护城河是数据，Agent 时代的护城河正在变成**可复用的上下文资产**：用户在产品里积累的任务历史、偏好、领域知识库，构成实打实的切换成本。
- 计量指标随之迁移：以前看 DAU/MAU，现在看 context hit rate（检索命中率）、每任务有效 token 数、每美元完成的任务数。“上下文成为价值衡量基线”的实质，就是这组指标正在取代传统增长指标，成为评估 Agent 产品的新参照。
- 协议层也在配合：MCP（Model Context Protocol）这类标准把“接入外部上下文”规范化。接入门槛降低之后，竞争焦点进一步转向“谁沉淀得更深”。

打个比方：搜索引擎索引的是全网网页，Agent 平台索引的是每个用户的“工作现场”——后者的密度和粘性都高一个量级。

## 六、三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-28/62e0822bc26f81f3.png)

1. **做 Agent 产品的人**：先建上下文管线和评估体系（命中率、压缩后信息保持率、长任务漂移率），再谈换模型。模型随时可替换，上下文系统才是持续迭代的资产。
2. **用 Agent 的人**：重要信息沉淀成结构化文档和知识库，别指望对话记忆永远在线。喂给 Agent 的材料质量决定输出上限——garbage in, garbage out，在上下文时代只会更成立。
3. **反共识提醒**：上下文的价值在信息密度，不在总量。只宣传“超长窗口”而忽视检索与压缩，相当于把内存当硬盘卖——容量数字好看，实际可用带宽一塌糊涂。

下半场的竞争，比的不再是谁的模型更能背书，而是谁能在每一次调用里，把**对的信息、在对的时刻、以对的密度**，装进模型的工作记忆。
