## 背景

现在的 Agent 大多是被动式的：用户发消息，模型响应，会话结束。但真实使用中，很多高价值场景是反过来的——日志里连续出现三次相同报错、日历上躺着一封没回的会议邀约、监控指标悄悄越过阈值。这些信号早就存在，只是助手没有"眼睛"。OpenClaw 加上 MCP 之后，接事件源的成本已经很低，proactive 能力从一个噱头变成了可以工程化落地的东西。

## 问题

我们最初的直觉是"多接几个触发器，让模型自己判断要不要行动"。跑了两周就撞墙：

- 助手在频道里看到自己的输出，又当成新事件处理，触发循环；
- 一次上游变更产生 20 多条事件，模型全跑一遍，当天 token 费用翻了四倍；
- proactive 消息泛滥，用户第三天就开始忽略，和垃圾通知没有区别。

结论很明确：proactive 的难点不在模型，而在触发器前面的过滤，和行动后面的授权。

## 做法

我们把系统拆成三层，LLM 放在最后一环：

1. **感知层**。统一的 Event Gateway 收集 cron、webhook、文件监听、消息监听四类事件源，做去重、合并和节流。同类事件在 5 分钟窗口内只保留一条，附上发生次数。
2. **决策层**。先用确定性规则粗筛：阈值判断、关键词匹配、静默时段检查。只有规则放行的事件才唤醒 Agent。这一步干掉了约 90% 的调用，是成本可控的关键。
3. **行动层**。按风险分级授权：低风险（生成摘要、起草草稿）直接执行；中风险（发消息、改配置）走"提议—确认"，助手把草案和理由推给用户，一键批准；高风险（删除、付款）永远不自动执行。

## 踩坑点

- **自触发循环**：Agent 的一条 proactive 消息本身又进了消息监听。解法是在 Gateway 按 actor ID 过滤自己的输出，并给每条事件加溯源标记。
- **状态过期**：事件到达时环境已经变了，Agent 拿着旧快照行动。我们在触发时强制重新拉取关键状态，而不是复用事件携带的数据。
- **权限蔓延**：为了让 Agent"更主动"，很容易不断给它加工具。后来我们固定了一条纪律：proactive 模式下可用工具列表比交互模式更短，每次变更都要过审。
- **时机不对**：凌晨推送技术摘要没人看。加上用户活跃时段和免打扰窗口后，接受率明显回升。

## 可复用建议

- 先跑两周"只提议不执行"模式，记录每条 proactive 行为的接受/忽略，接受率稳定在 90% 以上的动作类别才解锁自动执行。
- 给每个用户每天设 proactive 配额，按类别分桶，防止噪声失控。
- 每次触发都落一条结构化日志，带 reason 字段。事后调阈值全靠这份数据，凭感觉调一定会翻车。
- 触发规则用声明式配置而不是写死在代码里，出问题时可以单独回滚。

## 总结

Proactive 不是让模型更聪明，而是让系统学会"什么时候值得打扰用户"。感知层管信号质量，决策层管成本，行动层管信任。OpenClaw + MCP 解决的是接口问题，剩下的过滤、分级授权和反馈闭环，都是普通的工程活——但恰恰是这些，决定了用户觉得助手是"贴心"还是"烦人"。
