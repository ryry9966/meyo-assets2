## 背景

E2E 测试是工程里“人人知道重要、没人爱写”的部分：写起来慢、选择器脆弱、维护成本随页面迭代线性上涨。最近我们把 OpenClaw 的 Agent 接进测试流程，让它承担“探索页面 → 生成用例 → 修复失败”这三段最耗人的工作，跑了两个迭代，分享一套实测可行的协作方式。

## 问题：直接让 AI 写测试，为什么不行

最初我们试过最朴素的方案——把需求文档丢给模型，让它输出 Playwright 脚本。三类问题反复出现：

1. **选择器靠猜**。模型没见过真实 DOM，写出的 `button.submit-btn` 十有八九不存在。
2. **断言形同虚设**。用例“看起来在测”，实际只校验了元素存在，页面白屏也能绿。
3. **无视项目约定**。已有的 page object、fixture、登录 helper 全被绕开，一个测试文件自带一套登录逻辑，跑三次挂两次。

结论：Agent 缺的不是生成能力，是**上下文和反馈闭环**。

## 做法：五步协作流程

**第一步：喂真实上下文。** 通过 MCP 的浏览器工具让 Agent 实际打开目标页面，导出精简后的 DOM 骨架（去文案，保留标签、class、data-testid），再配一份关键操作的录制轨迹（HAR 或 trace）。上下文到位后，选择器从“猜”变成“引用”。

**第二步：先出用例清单，不出代码。** 让 Agent 基于上下文输出用户旅程清单：覆盖哪些路径、每条路径的断言点在哪。人工评审通过后，才进入代码生成。这一步成本极低，但能拦掉大量“测了个寂寞”的用例。

**第三步：在约定内生成代码。** 仓库放一份 `TESTING.md`：必须复用 `authFixture`、禁止裸 `waitForTimeout`、断言统一走 `expectPageReady()`。Agent 的 system prompt 强制引用这份文件，生成物只允许新增 `e2e/specs/` 下的文件，不许碰公共代码。

**第四步：跑 CI，失败回灌。** 用例进 CI 后，失败时把错误截图、trace 片段、报错堆栈拼成一条修复任务发回 Agent，只允许它改自己生成的那个文件；两轮修不好就打回人工。

**第五步：人工 gate。** Agent 的 PR 一律打 `agent:test` 标签，review 重点看断言质量而不是代码风格——风格它比人稳定，断言它比人会糊弄。

## 踩坑点

- **别让 Agent 自定等待策略**。它默认生成 `waitForTimeout(3000)` 这类定时炸弹，必须在约定里禁掉，统一改 `expect(...).toBeVisible()`。
- **别给完整 DOM**。几万 token 换不来等价信息量，精简骨架 + data-testid 清单足够，还省钱。
- **警惕“永远绿”**。某次生成的用例全绿，review 才发现它把 try/catch 包住了所有断言。约定里补了一条：禁止捕获断言异常。
- **失败回灌必须限定作用域**。不限的话它会顺手“优化”别人写的测试，diff 立刻不可审。
- **mock 要克制**。Agent 很爱用 `route` 拦接口，拦多了 E2E 就退化成集成测试。约定只允许拦截支付、三方登录这类不稳定依赖。

## 可复用建议

1. 三个文件是这套流程的地基：`TESTING.md`（约定）、`selectors.md`（核心页面选择器字典）、失败回灌的任务模板。换任何 Agent 框架都通用。
2. 把“用例清单评审”固定成流程节点，比事后逐行 review 代码省一半时间。
3. MCP 工具白名单只开浏览器读取类工具和运行测试的命令，不开对公共目录的写权限，把误伤面压到最小。

## 总结

Agent 写 E2E 测试的价值不在“全自动”，而在把最机械的三段工作——摸页面、写骨架、修 flaky——从人手里接走。能跑通的前提是工程约束先行：上下文喂足、作用域锁死、断言人工审。Agent 出活，人出判断，这套分工目前在我们仓库稳定运转，欢迎直接抄。
