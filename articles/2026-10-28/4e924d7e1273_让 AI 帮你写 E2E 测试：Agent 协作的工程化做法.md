## 背景

E2E 测试是团队里最容易被拖后腿的部分：写起来慢、维护成本高、一改版就红一片。很多项目最后只剩几条冒烟用例，核心链路全靠手工回归。

我们最近几个月把 E2E 编写交给 OpenClaw Agent 协作完成，结论是：Agent 确实能把单条用例的编写时间从半小时压到几分钟，但前提是别把它当"一键生成器"，而是当结对作者。

## 问题

直接把需求扔给 Agent，通常得到三类垃圾：

1. **选择器脆弱**：`text=提交订单` 这类定位一改文案就挂；
2. **断言空洞**：只断言"页面没报错"，测试永远绿，等于没测；
3. **环境幻觉**：编造不存在的 API 和登录方式，本地能跑纯属巧合。

根因是上下文不足——Agent 不了解你的路由、鉴权、测试基建和团队约定。

## 做法

我们的流程分四步：

1. **准备测试上下文包。** 在仓库放一份 AGENTS.md，写清楚：框架版本、登录方式（storageState 复用）、Page Object 目录结构、命名规范、禁止事项（不许新增依赖、不许用 sleep 硬等）。这份文档是整个流程里投入产出比最高的一件事。

2. **挂浏览器 MCP。** 给 Agent 接入 Playwright MCP 之类的浏览器工具，让它真实打开应用去探索：先走一遍目标链路，把关键节点的真实 DOM 结构抓下来，再基于真实选择器写用例，而不是凭空猜。

3. **小批量生成，一次一条链路。** 比如"登录 → 创建项目 → 邀请成员"，生成后立刻本地跑。挂了就把报错、截图、trace 回喂给 Agent 修，两三轮内基本收敛。

4. **人工只审断言。** 选择器和操作步骤交给 Agent，但每个用例的断言必须人过一遍：断的是业务结果（订单状态、DB 落库、接口返回）还是仅仅是 UI 现象？断言承载业务语义，这块不能外包。

## 踩坑点

- 不要让 Agent 自由发挥选择器优先级，在约定里明确：优先 `data-testid`，其次 role，文本定位只做兜底；
- 警惕"永远绿"的测试。我们统计过早期生成用例，约三成断言是 `toBeVisible` 级别的废话，这类直接打回；
- Agent 默认用硬编码 sleep 和超长 timeout 糊弄 flaky，在约定文档里写死网络等待的推荐写法；
- CI 的并发和超时约束 Agent 不知道，生成后要人工调并行粒度，否则 runner 直接 OOM；
- 新增依赖必须人工审批，我们见过它为一个断言引入整个 lodash。

## 可复用建议

- 把"测试上下文包"做成独立文档并纳入 code review，Agent 的产出质量基本取决于它；
- 一次只生成一条链路，批量生成只会得到批量返工；
- 建立 flaky 隔离区：连续两次失败的用例自动摘出主流程，回喂 Agent 修复，别让整个 CI 长期飘红；
- 用例质量和覆盖率报表一起看，防止"覆盖率上去了，质量下去了"。

## 总结

Agent 写 E2E 的价值不在"写得快"，而在把最机械的部分——探页面、写操作步骤、跑通——自动化，让人把精力留给断言设计和链路取舍。目前我们新链路的 E2E 约七成代码由 Agent 产出，人工主要做约定维护和断言评审。它不是替代测试工程师，是把测试工程师从体力活里捞出来。
