## 背景

团队每天要发一份服务日报：昨天有多少报错、哪些接口变慢了、有没有部署变更。之前靠人翻日志手写，格式不统一、漏项频繁，遇上值班交接更是断档。本文记录我用 OpenClaw 搭的一条日报流水线。思路不复杂，但几个坑值得提前说清楚。

## 问题

把需求拆开看，日报其实是三件事：

1. 从分散的日志源里取出"昨天"的数据；
2. 把海量噪声压成少量关键指标；
3. 用人话写出来，按时发到群里。

难点在第 2、3 步的边界：让 Agent 直接读原始日志，上下文很快爆掉，而且它自己"数"出来的数字不可信；全靠脚本模板，又写不出"错误数比昨天翻三倍"这类判断。所以核心原则是：**脚本负责算数，模型负责叙述**。

## 做法

整条流水线分四段，每段一个脚本，中间用固定的 JSON schema 衔接：

**1. 采集**：Python 脚本按天拉取各服务日志（轮转目录 + Loki 查询），统一成 JSONL：`{ts, service, level, event, extra}`。时间统一存 UTC，展示时再转本地时区。

**2. 预聚合**：纯脚本，不经过模型。输出固定结构的汇总：各服务的 error 数、Top-N 异常事件、p95 耗时、部署记录。结果通常只有几 KB，这就是后面喂给模型的全部内容。

**3. 叙述生成**：在 OpenClaw 里配置一个 agent，通过 MCP 工具读取第 2 步的汇总 JSON。prompt 中写死输出 schema（结论、异常、趋势、待跟进四段），并附前一天的报告做 few-shot 锚定格式。模型拿到的全是算好的数字，只做对比、归因和措辞。

**4. 投递**：系统 cron 每天早上触发，跑完整流程后把 Markdown 结果经 webhook 推到群聊。LLM 调用失败时降级为纯模板报告——数字永远在，只是少了"人话"总结。

## 踩坑点

- **别让模型算数**。早期我把原始日志直接丢给 agent，token 开销大，且它统计的错误次数和 grep 结果对不上。改成先聚合再喂，数字 100% 可复现。
- **日期边界**。日志按 UTC 存、报告按本地时区出，第一天就出现"日报少两小时数据"。解法是固定 cutoff 时间，并在报告头部写明统计区间。
- **输出漂移**。跑几天后模型开始自作主张改段落顺序。把输出 schema 写进 prompt，每次都给一份范例，格式稳定性明显提升。
- **静默失败**。cron 挂了没人知道，连续两天没出报才发现。加了心跳：任务完成才发报告，超时未发则单独告警。
- **重跑幂等**。手动补跑一次导致群里出现两条日报。所有产物按日期命名并覆盖写，投递前先检查当天是否已发。

## 可复用建议

- 把"确定性计算"和"文本生成"拆成两段，中间用 schema 隔开，任何一段都可单独替换、单独测试。
- prompt 当代码管理：进 git、改动走 review、留变更记录。
- 永远准备一条不依赖 LLM 的降级路径。自动化任务的底线是"按时产出"，而不是"产出得漂亮"。
- 中间产物落盘（按日期存 JSON），排查时能逐步回放定位问题，不必重跑全流程。

## 总结

流水线上线一个多月，日报没断过，团队从"写日报"变成了"看日报"。经验归结为一句话：自动化报告的价值不在于模型多聪明，而在于每个环节都可预测、可重放、可降级。脚本和 prompt 模板结构都很通用，大家可以直接改造，欢迎在社区贴出自己的变体和改进。
