# 背景

OpenClaw 的 agent workspace 里，`SOUL.md` 决定 agent "是谁"，`AGENTS.md` 决定"怎么干活"，`USER.md` 存用户侧事实。`SOUL.md` 会在会话启动时注入 system prompt。很多人装完就跑，这份文件保留着默认的几行，结果就是：agent 在 Telegram 里话痨、在 cron 任务里自作主张、跨会话语气漂移。

# 问题

实际会踩到三类坑：

1. **语气不一致**。同一个 agent，今天冷静简洁，明天热情过度，长会话压缩后人格还会漂。
2. **边界缺失**。没有明确"不做什么"，agent 会主动发消息、在群里抢答、执行昂贵工具调用。
3. **人格和操作规则混写**。把"收到报错先重试三次"塞进 SOUL.md，模型把它当个性而非流程，执行不稳定。

# 做法

一份能用的 SOUL.md 大概长这样（精简骨架）：

```markdown
# 身份
你是 XX，一个低调、工程化的助手。默认中文，技术词保留英文。

# 语气
简洁直接，先给结论再给细节。不用感叹号，不写客套开场白。

# 边界
- 不主动发起对话，除非 cron 任务明确要求汇报。
- 付款、删除数据、对外发送类操作，必须当前会话明确确认后才执行。
- 不确定就说不确定，禁止编造工具输出。

# 兜底
超出能力范围的问题，直接说明，并给出替代路径。
```

落地步骤建议：

1. 先用默认 SOUL.md 跑一周，记录让你不适的回复——这些就是待写入的边界。
2. 按"身份 / 语气 / 边界 / 兜底"四段写，控制在 1KB 左右。它每个会话都要注入，长文烧 token 还稀释重点。
3. workspace 本身是 git 仓库，每次改动单独提交，出问题可回滚。
4. 改完 `/new` 开新会话验证：先问一个身份探针问题，再故意诱导它越界，看红线是否生效。
5. 多渠道部署时，至少在两个渠道各测一轮，确认语气一致。

# 踩坑点

- **写成小作文**：超过两三千字，人格反而更不稳定，重点被稀释。
- **动态事实硬编码**：项目名、联系人这类常变内容放 `USER.md` / `MEMORY.md`，SOUL.md 只留稳定特质。
- **要求模型"永远不拒绝"**：人设写得再强势，也压不过模型本身的对齐行为，这类条目等于没写。
- **忘了生效时机**：SOUL.md 在会话启动时读取，改完不重开会话，测到的是旧配置。
- **过度拟人**："你深爱用户"这类强情感设定容易诱发讨好式回答，牺牲事实准确性。

# 可复用建议

- **边界写成可测语句**："不主动发消息"远比"要有分寸"可验证。
- **人格迭代当代码管理**：一条边界一个 commit，附上触发该边界的坏例子，方便复盘。
- **多 agent 场景抽公共底座**：工作助手和家庭助手各一份 SOUL.md，共享边界段落，差异化只留身份和语气。

# 总结

SOUL.md 的价值不在于让 agent 更"像人"，而在于把人格从玄学变成可 review、可回滚的配置文件。保持简短、职责分离、像测代码一样测边界，你的 agent 才能长期稳定地"是同一个人"。
