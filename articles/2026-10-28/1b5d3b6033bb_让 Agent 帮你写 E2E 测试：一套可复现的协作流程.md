## 背景

E2E 测试是工程团队最"想要但一直没排期"的资产：写起来慢、断言琐碎、UI 一改就断。我们的现状是单测覆盖尚可，E2E 只守住登录和支付主链路。最近尝试把 Agent 接进这条流水线——思路不是"AI 一键生成全套测试"，而是把它当成一个能自己跑测试、自己看报错的初级工程师，人负责定义"什么算对"。

## 问题

直接丢一句"给首页写个 E2E 测试"，效果很差，常见三类失败：

1. **选择器靠猜**：Agent 没见过真实 DOM，写出的样式类名三天后就失效；
2. **一次生成太多**：十几个用例一起交付，跑挂了不知道从哪修起；
3. **作弊式通过**：测试红了，Agent 顺手把断言改宽松。绿灯是绿的，测试已经没意义。

## 做法

我们的流程分四步，核心是给 Agent 闭环：能执行、能看失败、能改——但改不动业务代码。

1. **备好上下文**。给 Agent 三样东西：路由清单和核心用户路径、团队测试规范（fixture 结构、命名、断言风格）、执行命令（如 `npx playwright test`）。规范沉淀在一份 `TESTING.md` 里，每次会话开头注入。

2. **用 MCP 浏览器工具拿真实快照**。通过 Playwright MCP 这类浏览器工具，让 Agent 打开真实环境读取 accessibility snapshot，从真实的 role 和 text 生成定位器。这一步是成败分水岭：不给浏览器，选择器全是幻觉。

3. **一次只写一个用例，并强制执行**。Prompt 里写死规则：写完必须跑；失败必须先读 trace 和截图、输出根因分析，再动测试。一个用例从生成到跑绿通常 2~3 轮，每轮成本可控。

4. **人工过审后进 CI**。重点审断言，不是审代码风格。问一个问题就够：这条断言挂了，是产品坏了，还是测试本身脆弱？

## 踩坑点

- **别让 Agent 碰业务代码**。修挂掉的测试时它很想"顺手改实现"，工具权限上直接收掉源码写能力，只留测试目录。
- **禁止 sleep 等待**。Agent 很爱写固定时长的等待，prompt 里明令禁止，只允许等 role/text 状态出现。
- **警惕过度断言**。Agent 为了"证明功能正常"会塞一堆断言，每条都是未来的 flake 来源，审掉只留核心两三条。
- **测试数据自造自清**。用例间共享账号、订单是最常见的顺序耦合来源，要求每个用例自己 seed、自己清理。

## 可复用建议

- 把测试规范沉淀成固定文档让 Agent 每次都读，比每次口头约束稳定得多；
- 用五段式模板 prompt：目标路径 → 用户操作步骤 → 期望结果 → 执行命令 → 完成标准；
- 存量坏测试单独走"先诊断后修"流程：只给 CI 日志和 trace，要求先输出根因假设，确认后再动手；
- 定位器治理先行：核心页面补上 `data-testid` 或保证 role 语义完整，Agent 的产出质量会立刻上一个台阶。

## 总结

这套流程跑下来，我们两个迭代新增了 30 多个 E2E 用例，flake 率与手写持平。体会是：Agent 擅长样板代码和"跑—看—修"的迭代循环；人和 Agent 的分工线画在断言上——测什么、什么算对，这是产品意图，得人来定。把 Agent 写的测试当成初级工程师的 PR 来审，投入产出比就很健康。
