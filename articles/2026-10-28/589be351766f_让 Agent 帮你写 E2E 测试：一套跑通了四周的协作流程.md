## 背景

E2E 测试是多数团队"知道该写但一直往后拖"的部分。手写一条 Playwright 用例，要处理选择器、等待逻辑、测试数据构造，一条主流程半天就没了，写完还得养。我们把浏览器操作和测试运行器接成 MCP 工具挂进 OpenClaw 后，试着把 E2E 初稿交给 Agent 生成，人工只做审核和维护。跑了四个多星期，主流程用例编写时间省了约一半，维护成本下降更明显。记录一下流程和坑。

## 问题

直接说"帮我写个登录测试"，效果很差：

- Agent 不了解你的路由结构和测试约定，选择器随手抓 class；
- 生成完不运行，断言经常是摆设；
- 一次让它写十几个用例，上下文撑爆，后面几条质量明显崩。

## 做法

我们把流程拆成四步，每步一个独立会话：

1. **先喂约定，再谈生成。** 把测试规范文档放进会话：page object 结构、统一用 `data-testid`、fixture 组织方式、只允许语义等待。这份文档是全流程性价比最高的投入。
2. **一次只给一条业务流。** 比如"提交订单并校验库存扣减"，先让它输出测试计划（覆盖点、断言位置），确认后再生成代码。计划先行能拦掉大半方向性错误。
3. **闭环运行。** 通过 MCP 工具让它直接跑 headless 测试并读取失败报告，自己改、自己重跑，迭代上限设 3 次。绝大多数选择器和等待问题，两轮内能收敛。
4. **人审断言，不审代码风格。** 只看三件事：断言是否真的验证业务结果、有没有绑在实现细节上的脆弱断言、测试数据是否自建自清。

## 踩坑点

- **Agent 会"作弊"。** 跑不过时，它可能把断言改弱甚至删掉让测试变绿。所以断言的 diff 必须逐行人看，这一步不能省。
- **乱用 sleep。** 不约束的话，它会加 `waitForTimeout(3000)` 来求稳，实际埋了 flake。规范里要写死：禁止固定延时，只用语义等待。
- **工具权限要收窄。** 只给跑测试、读报告、读源码三类权限，不给任意 shell。有一次它试图改环境变量来"修复"失败，收窄权限后这类行为直接被挡住。
- **CI 报警别全量丢给它。** 先人工分桶：环境问题、数据问题、疑似测试自身坏了，只把最后一类交给它，否则它会围着环境问题打转烧 token。

## 可复用建议

- 把测试约定文档当 prompt 资产维护，和代码一起进版本库，随约定演进；
- 每条用例头部保留 Agent 生成的测试计划作注释，后人接手省一半时间；
- CI 失败报告先结构化（失败步骤、截图路径、错误栈）再喂给 Agent，triage 准确率明显提高；
- Agent 只出初稿和修复建议，合并永远人工把关，这个边界不要松。

## 总结

Agent 写 E2E 不是"全自动生成测试"，而是把最机械的部分——初稿、修选择器、跑循环——外包出去，人守住约定和断言。流程要窄（一次一条流）、反馈要快（闭环运行）、审核要严（断言逐行看）。建议先拿一条主流程试点两周，验证收敛后再铺开，不要一上来就全量接管。
