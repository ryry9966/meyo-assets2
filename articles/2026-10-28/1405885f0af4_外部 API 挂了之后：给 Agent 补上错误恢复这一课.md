## 背景

Agent 的能力上限，基本等于它能调用的工具上限。OpenClaw 里的 tool 调用、MCP server、各种插件，底层大多是 HTTP API。写 demo 时一切正常，但任务一长、并发一高，现实就来了：超时、429、502、证书过期、上游限流、返回半截数据。对长期运行的 agent 来说，**错误不是异常路径，是日常路径**。

## 问题

常见的三种坏做法：

1. **裸调用**：一次失败整个任务中断，前面烧掉的 token 和时间全部作废；
2. **无差别重试**：不管什么错误都硬重试，把对方打得更死，自己账单翻倍；
3. **吞错**：工具报错后返回空结果，模型拿到假象，开始一本正经地编——这是最隐蔽、危害最大的一种。

## 做法

按这个顺序搭一层恢复逻辑：

**1. 先给错误分类。** 只对"值得重试"的错误重试：超时、429、5xx 属于暂时性故障；4xx（除 429）是参数或权限问题，重试一百次结果一样。分类是后面一切的前提。

**2. 指数退避 + 抖动。** 比如 1s / 2s / 4s，每次叠加随机抖动，避免所有请求同一时刻撞回去。设 3~5 次上限，超过就放弃，转入下一步。

**3. 熔断。** 连续 N 次失败后短路一段时间，期间不再发真实请求，直接走降级路径。别让 agent 对着一具尸体做心肺复苏。

**4. 降级与兜底。** 备用 provider、本地缓存、或者干脆明确告诉用户"该能力暂不可用"。诚实的降级好过虚假的成功。

**5. 把错误如实、结构化地返回给模型。** 给它错误码 + 人类可读的原因 + 建议动作，让 agent 自己决定换路、问用户还是放弃。这是恢复链路里最关键的一环：模型看到真实错误，才能做出合理的下一步规划。

**6. 写操作必须幂等。** 所有创建/更新类调用带幂等键，重试才不会重复下单、重复发消息。

**7. 长任务做 checkpoint。** 状态持久化到磁盘，恢复时从断点续跑，而不是从头再烧一遍 token。

## 踩坑点

- 对非幂等接口盲目重试，重复写入比失败更难收拾；
- HTTP 200 但 body 里是错误信息——只看状态码会把失败当成功；
- timeout 设太短，把慢但健康的 API 误判为挂了；整体 deadline 要逐层向下传递，别只约束单次请求；
- 熔断阈值太敏感，服务在"抖动恢复"和"被熔断"之间反复横跳；
- 把原始堆栈直接喂给模型，它可能顺着错误信息编出一套似是而非的解释。

## 可复用建议

- 在插件层**统一封装一个 resilient invoke**：分类、退避、熔断、日志全部收在这一层，每个工具只写业务逻辑。散落在各工具里的 try-catch 迟早烂掉；
- 错误返回统一 schema，模型侧的处理逻辑只需写一次；
- 日志带 request id，故障后能重放现场；
- 定期做故障演练：手动把某个依赖关掉，观察 agent 是优雅降级还是当场去世。没演练过的恢复逻辑约等于没有。

## 总结

错误恢复不是什么炫技模块，而是一套朴素的工程纪律：**分类、退避、熔断、降级、幂等、留痕**。Agent 跑得稳不稳，大部分时候不取决于模型多聪明，而取决于工具层多扎实。下次写插件时，把这层先补上——它平时看不见，出事时救全场。
