## 背景

团队每天需要一份日报：昨天跑了多少任务、哪些失败、有哪些异常趋势。这件事不难，难在天天手动做——登几个面板、翻日志、拼格式，十几分钟就没了，漏项和口径不一致更是常态。

## 问题

日志散落在应用日志、Agent 运行记录和调度表三个地方。第一反应是把原始日志直接丢给模型总结，实际会撞上三堵墙：

1. 量大，超出上下文，成本也高；
2. 噪声多，重复告警会污染摘要；
3. 输出格式飘，今天一个"问题汇总"，明天写成散文。

所以核心思路定为一句话：**确定性代码做确定的事，模型只做最后一步归纳。**

## 做法

流水线四步，由一个定时任务驱动（cron 或 Agent 的定时能力均可）：

**1. 归一化抽取（脚本）**
脚本拉取三个来源昨天的记录，统一成同一份 JSON Lines：`{时间, 来源, 类型, 状态, 关键字段}`。只做字段映射和过滤，不做判断。

**2. 聚合去重（脚本）**
按 `类型+关键字段` 分组，计数、取首末时间、合并重复告警，产出中间聚合文件。它是后续所有步骤的唯一输入。

**3. 模型摘要（模型，只此一步）**
聚合结果（通常几百行内）连同一份固定 JSON schema 喂给模型，要求输出 `{总览, 异常清单, 趋势备注}`；异常清单每项必须带聚合文件里的行号引用，方便回查。格式用结构化输出/函数调用约束，不靠 prompt 恳求。

**4. 渲染与投递（模板）**
拿模型输出的 JSON 填进固定 Markdown 模板，写文件、推送链接到群频道。"趋势备注"为空则整节隐藏。

## 踩坑点

- **别让模型看原始日志。** 早期图省事直接喂日志，同一告警被模型当成三件事写。去重必须前置在代码层。
- **时区。** 日志时间戳是 UTC，"昨天"要按本地时区切，否则早上 8 点跑的日报会缺昨天最后几小时的记录。
- **幂等。** 重跑会生成两份报告。改用日期作报告 ID，重跑直接覆盖。
- **格式约束靠 schema 不靠提示词。** 只在 prompt 里写"请输出 JSON"的失败率明显高于结构化输出接口。
- **流水线自身要可观测。** 加了最朴素的一道保险：生成失败就发告警到同一频道，避免"日报悄悄断了三天没人发现"。

## 可复用建议

- 中间聚合文件落盘保留 7 天：模型摘要出问题时可人工复核口径，也便于回放调试。
- schema 和模板放同一目录，调口径只动这两个文件，抽取脚本不用碰。
- 这个骨架——定时触发 + 确定性预处理 + 受约束的单次模型调用——换成周报、告警摘要、发布回顾都能直接套。

## 总结

整条流水线没有用复杂技术，价值在边界划得清楚：代码负责抽取、去重、格式，模型只把几百行聚合数据压缩成一页人能读的报告，输出被 schema 锁死。上线后日报从每天十几分钟的手工活变成零操作，口径也比人肉拼接稳定得多。如果你也在用 Agent 做类似的事，建议从"先把数据结构化到模型只需摘要"这一步做起，后面的可靠性问题会少一大半。
