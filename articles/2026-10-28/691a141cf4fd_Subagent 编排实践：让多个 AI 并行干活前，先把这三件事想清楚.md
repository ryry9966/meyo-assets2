## 背景

单 agent 串行执行有个很实际的天花板：任务一多，上下文越滚越长，速度越来越慢，一个环节出错还会把整个会话拖进泥潭。最近在做一次仓库级代码体检（同时扫依赖版本、跑测试、审文档一致性）时，我把主任务拆给多个 subagent 并行跑，收益和坑都碰到一些，记录如下。

## 问题

- 串行长任务动辄几十分钟，等待时间不可接受；
- 所有中间输出堆在同一个上下文里，主 agent 很快"失焦"；
- 探索类任务（只读）和写操作混在一个会话里，风险无法隔离。

## 做法

1. **拆分先于并行**。只有满足"输入明确、输出可结构化、互不争抢资源"的子任务才值得拆。写操作按目录/文件划分所有权，一个文件只归一个子 agent。
2. **主 agent 只做 planner 和 aggregator**。先让主 agent 产出任务清单：每个子任务一段独立 prompt，写明目标、允许操作的目录、工具白名单、输出格式（强制 JSON 或固定段落结构）。
3. **子 agent 用独立会话**，各自从干净的上下文开始。探索/审计类只给只读工具；写类子 agent 限定工作区。并发控制在 2~4，实测再往上收益递减，还容易触发限流。
4. **汇总时只收摘要**。要求子 agent 返回结论 + 关键证据（文件路径、行号、命令退出码），不回传原始日志。主 agent 拿到几份短报告后，再决定是否追加修复任务。

## 踩坑点

- **隐藏依赖**：本以为"装依赖"和"跑测试"相互独立，结果测试 agent 在依赖装完前就启动，整批失败。有依赖就老老实实让那一层串行，或者让 planner 显式标注前置关系。
- **并发写冲突**：两个子 agent 各自改了同一个配置文件，后写的覆盖先写的。结论：所有权边界要划在文件级，不留"共享可写区"。
- **结果污染主上下文**：最初让子 agent 原样回传输出，两轮就把主会话撑爆。改成强制结构化摘要后，主上下文的增长才基本可控。
- **子 agent 失控**：某个探索任务陷入循环重试。后来给每个子 agent 加了最大轮数和超时，失败就返回失败原因，由主 agent 决定重试还是放弃。
- **限流与资源**：4 个并发加主 agent 自身，正好卡在 API 限流边缘，加了简单的排队间隔才稳定下来。

## 可复用建议

- 把子任务 prompt 做成模板：**目标 / 边界 / 工具白名单 / 输出 schema** 四段固定，换任务只换内容。
- 先 dry-run：只让 planner 输出拆分方案，人工确认后再并行执行，能拦住大部分隐藏依赖问题。
- 每个子 agent 独立留痕（会话日志分开存），排障时按子任务回放，比翻一个大日志快得多。
- 一个粗糙但好用的判断标准：**如果子任务的输出会改变另一个子任务的输入，就不并行。**

## 总结

Subagent 并行不是把任务随手撒出去，而是"先拆清楚、再限权限、只收摘要"。收益主要来自延迟下降和上下文隔离，风险集中在写冲突、隐藏依赖和结果污染三处。把拆分标准、prompt 模板和留痕机制固化下来，这套编排就可以稳定复用了。欢迎在社区帖子里贴你们的拆分模板，一起迭代。
