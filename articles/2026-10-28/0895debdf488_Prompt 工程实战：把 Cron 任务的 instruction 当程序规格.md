## 背景

OpenClaw 的 cron 任务，本质上是**无人值守的 prompt**：到点之后，agent 拿着你写的 instruction 独立执行，再把结果推到指定渠道。它和交互式对话最大的区别是——现场没有你。不能追问、不能澄清，跑错了也没人当场纠正，而且每次执行都是全新会话，不携带任何上下文。

## 问题

大多数人的第一版 cron instruction 是按聊天消息写的，比如"早上八点帮我看下今天的日程，简单总结一下"。这类写法有三个典型故障模式：

- **语义模糊**："简单总结"是多简单？发给谁、发到哪？agent 只能猜。
- **边界缺失**：没说能不能发消息、能不能改文件，agent 可能在任务里自作主张执行写操作。
- **无失败路径**：数据拿不到时，agent 倾向于硬编一段"看起来合理"的输出。

凌晨三点的定时任务没有任何兜底，错误输出会准时、安静地出现在你的群里。

## 做法

把 instruction 当成一份小型程序规格来写，固定五个要素：

1. **目标**：一句话说清交付物。"输出今日日程摘要，不超过 10 行。"
2. **输入**：写死数据来源和范围。用哪个日历、取哪个时间段、读哪个路径，不要让 agent "自己找"。
3. **输出契约**：格式、长度上限、发到哪个渠道、要不要 @。
4. **边界**：明确"只读"。不加这句，agent 可能顺手回复邮件或修改事件。
5. **异常处理**：写明"某项数据取不到时，只输出一行原因，不要推测补全"。

一个可直接套用的例子：

> "每天 08:30（Asia/Shanghai）读取主日历，汇总今天 00:00–24:00 的日程；输出为带时间的列表，不超过 10 行，发到 #daily；仅读取，不发送任何消息、不修改任何事件；若日历不可访问，只回复一行原因。"

任务若依赖 MCP 工具或插件，把工具名和调用范围也写死，避免 agent 自行挑替代品。上线前先手动触发一次验证，观察前几天输出，再放任它跑。

## 踩坑点

- **相对时间表述**："最近三条""一小时内的消息"在定时场景容易踩时区和切分点，尽量用绝对锚点并写明时区。
- **一个任务塞多件事**：抓取失败会拖垮整个交付，按交付物拆分。
- **不限输出长度**：晨报会随数据量膨胀成刷屏长文，最后被你自己屏蔽。
- **让 cron 代发消息**：写操作留给交互会话，定时任务默认只读，这是最稳的护栏。
- **instruction 散落各处**：cron 里的 prompt 也是资产，纳入版本管理，改一次提交一次。

## 可复用建议

- **模板化**：目标 / 输入 / 输出契约 / 边界 / 异常处理，五段式直接套。
- **先干跑**：新任务先在交互会话里粘贴 instruction，确认数据源和工具可用，再挂上 cron。
- **失败要出声**：宁可收到一句"没取到数据"，也不要收到一段编造的摘要。
- **定期清理**：每季度过一遍任务列表，删掉没人看的推送。

## 总结

Cron 任务的 instruction 不是聊天消息，而是一份无人值守时也能被正确执行的小规格。写清交付物、输入、输出、边界和失败路径，再把 prompt 当代码维护，定时自动化才能长期稳定地省心。
