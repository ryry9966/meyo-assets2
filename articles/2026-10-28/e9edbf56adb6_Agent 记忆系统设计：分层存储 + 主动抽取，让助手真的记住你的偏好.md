# 背景

OpenClaw 这类常驻 Agent 的核心卖点之一是"越用越懂你"，但很多部署的真实状态是：每次会话冷启动，偏好靠用户反复口述，聊天记录在文件里堆着，Agent 却读不回来。我们给自用实例加了一套记忆层，跑了一个多月，这篇把设计和踩过的坑整理出来。

# 问题

第一版直觉做法是把会话日志存下来，检索时塞回上下文。跑一周就暴露三个问题：

1. **日志 ≠ 记忆**。一次会话几万 token，真正持久的偏好可能就两三句，原样回灌，噪声远大于信号。
2. **检索精度差**。"我用 pnpm 不用 npm"这类精确事实，靠向量相似度经常召回一堆无关闲聊。
3. **没有更新机制**。两周前说"回复简短点"，后来改成"详细点"，旧记忆还在，模型行为来回横跳。

# 做法

核心思路：**把记忆当数据库设计，而不是当日志堆积**。分三层：

**L1 核心画像**：几百 token 的 JSON，固定注入 system prompt。只放高频高价值条目——时区、语言偏好、技术栈、回复风格。手写 + 命令维护，不走自动抽取。

**L2 偏好库**：SQLite 表，结构大致是 `{id, type, content, confidence, created_at, updated_at, hits}`。每条偏好有唯一键，冲突时按 updated_at 覆盖，保留版本历史供回滚。

**L3 情景档案**：会话结束后的批量归档，FTS5 关键词 + 向量双路检索，只在相关时按 top-k 注入。

**写入路径**：不要在对话中实时抽取——临时的、情绪化的表达容易被固化。会话结束或满 20 轮后跑一个独立抽取 pass，让模型输出结构化 patch（新增/更新/删除），带置信度，低于阈值直接丢弃。

**读取路径**：L1 每次必注入；L2 按 type 分组，只注入与当前任务相关的类别；L3 混合检索，分数不够硬阈值宁可不给。

**治理**：提供 `memory review / delete / export` 命令。永远假设抽取会出错，人工兜底是功能不是妥协。

# 踩坑点

- **记忆越多越聪明是错觉**。L1 超过 800 token 后，指令遵循和检索命中都开始下降，预算要当硬约束。
- **纯向量检索对精确事实不友好**。时区、路径、包管理器这类必须走精确匹配或 L2 结构化存储。
- **抽取时机不对会污染记忆**。实测边聊边写，把一次性的调试环境配置也固化成了长期偏好。
- **多实例命名空间**。工作和个人助手的记忆混在一个库里，检索互相干扰，按 namespace 隔离后才正常。
- **隐私**：记忆文件明文落盘，含真实偏好和工作上下文，同步到云端前先想清楚。

# 可复用建议

1. 先做 L1：手写 JSON + review 命令，一天工作量，解决 80% 的"记不住"。
2. 每条记忆带 `hits` 字段，定期淘汰长期未命中的冷记忆。
3. 抽取 pass 单独跑、结构化输出、人工可否决——别让主对话模型顺手写记忆。
4. 记忆更新做成可 diff 的事务，出问题能回滚。

# 总结

记忆系统的难点不在存储和检索，而在**写什么、什么时候写、怎么更新**。分层的意义是把少量确定性的内容（L1/L2）和大量不确定的内容（L3）分开对待。先让小而准的记忆稳定生效，再考虑规模化的语义检索，顺序反了会一直在调噪声。
