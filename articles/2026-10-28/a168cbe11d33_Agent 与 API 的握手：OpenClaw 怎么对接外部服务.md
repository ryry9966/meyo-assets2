## 背景

OpenClaw 这类本地 Agent 的价值不在"会聊天"，而在"能动手"。聊天模型只能产出文字，真正的自动化是让 Agent 去调 GitHub API 建工单、查监控接口、写数据库、触发 CI。对外部服务的对接质量，直接决定了 Agent 是玩具还是工具。

## 问题

对接外部服务时，失败基本落在三类：

1. **认证失败**：key 放错位置、过期、权限范围不够；
2. **语义错位**：工具描述写得太含糊，模型猜错参数，一发出去就是错误请求；
3. **失控调用**：没有超时、没给写操作设闸，Agent 跑起来就不可控。

根源通常是同一个误区：把"能调通 API"当成对接的全部。但模型调用 API 和人调用 API 不一样——它靠工具的 name、description 和参数 schema 做决策，描述不清晰它就瞎猜。

## 做法

我的流程是四步：

**第一步：先人肉调通。** 用 curl 把目标 API 走一遍，确认鉴权方式（Header key / Bearer / OAuth）、必要参数、返回结构。这步别省，很多"Agent 调不通"最后发现是 API 本身就要求特定 header。

**第二步：拆成小工具，别造大工具。** OpenClaw 的 skill / MCP 工具粒度越细，模型用得越准。与其写一个 `manage_project` 万能工具带十几个参数，不如拆成 `list_tasks`、`create_task`、`close_task` 三个，每个的 description 用一句话说清楚"干什么、什么时候该用我"。

**第三步：密钥走环境变量。** key 一律放 `.env` 或系统环境变量，配置里只写引用。别把 token 硬编码进 skill 文件再提交到仓库——这类泄漏事后很难清理。

**第四步：给返回值瘦身。** 很多接口返回几 MB 的 JSON，直接喂给模型会撑爆上下文、稀释注意力。在工具层先过滤字段、截断列表，只返回模型需要的部分，比如"只要 id 和 title"。

## 踩坑点

- **超时必须设。** 不设超时的 HTTP 调用会让 Agent 卡死一整轮，上层还以为它在"思考"。
- **写操作要二次确认。** 发消息、建资源、删东西这类副作用操作，默认让 Agent 先复述将执行的动作，或提供 dry-run 参数，跑顺了再放开。
- **description 别堆关键词。** 模型选工具主要看描述，写得像 SEO 它反而选错。
- **分页和限流。** 列表接口记得传分页并限制条数；有限流的 API 在工具层加退避重试，别让模型自己重试——它会无限循环。
- **日志落盘。** 每次工具调用记下入参、出参摘要、耗时，出问题时这是唯一证据。

## 可复用建议

整理成一句口诀：**人肉先通、小粒度拆分、密钥进环境、返回做瘦身、写操作设闸、超时和日志兜底。** 新接一个服务，照着过一遍，基本不会翻车。

## 总结

对接外部服务本质是个"接口设计"问题，不是"集成"问题。OpenClaw 里的每个工具都是模型的一个动词，动词越精确，Agent 行为越可靠。把工具当成给模型用的公共 API 来设计——描述清楚、粒度小、失败有反馈——握手就稳了。
