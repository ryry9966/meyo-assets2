## 背景

Agent 的价值不在对话本身，而在它能不能"动手"。OpenClaw 本质是编排层，真正的行动力来自外部服务：日历、数据库、CI、内部系统。MCP 让工具接入有了统一协议，但"接得上"和"接得稳"之间隔着不少工程细节。这篇帖记录我们团队对接几个外部 API 时的做法，偏实操，欢迎对照自己的场景取用。

## 问题

对接时最常见的四类翻车：

1. **凭证混乱**：key 直接写进配置文件跟着仓库走，或者所有服务共用一个高权限 token。
2. **工具描述含糊**：Agent 只能靠 description 猜参数，猜错就空转。
3. **没有超时与错误约定**：上游一挂整轮会话卡死；或者重试无退避，直接打出 429。
4. **返回值失控**：把上游原始 JSON 原样塞回上下文，几轮对话就把窗口吃满。

## 做法

我们的流程分五步：

**第一步，选对接方式。** 优先级：现成 MCP server > 自定义 skill 包一层 HTTP > 插件级封装。有官方 MCP 的服务直接用；只有 REST API 的，在 skill 里写薄封装；需要维护状态、高频调用的，才考虑做成插件。

**第二步，管好凭证。** key 放环境变量，配置文件里只留引用。对接内部系统用独立服务账号，scope 给到最小——先只读，跑稳了再申请写权限。

**第三步，把工具描述当接口文档写。** 每个参数注明类型、单位、取值范围、默认值。日期参数要写清格式和时区，枚举值全部列出。Agent 不会读你的源码，description 就是它的全部依据。

**第四步，约定超时、重试和错误格式。** 所有调用强制 timeout；只有幂等接口才自动重试，并加指数退避；返回统一为 `{ok, data, error, retryable}` 结构，让 Agent 拿到失败后能自己决策：换参数重试、跳过还是上报。

**第五步，先只读冒烟，再放开写入。** 新服务上线先跑一批只读场景，观察调用日志——参数对不对、裁剪后返回多大、失败率多少——再逐步解锁写操作。

## 踩坑点

- **上下文被返回值撑爆**：上游返回几十个字段，Agent 只需要三个。在封装层做字段裁剪，必要时暴露 `fields` 参数。
- **OAuth refresh token 过期**：本地跑得好好的，几天后突然 401。refresh 逻辑要放进封装层并落盘，不要指望 Agent 处理认证流程。
- **自然语言直接拼 URL**：Agent 生成的 query 没编码，特殊字符直接打挂请求。参数必须在封装层统一 encode 和校验。
- **工具堆太多**：一个 skill 挂十几个工具，Agent 的选择准确率明显下降。按场景拆分，当前会话只暴露需要的。
- **429 之后连环重试**：没有退避的重试，等于攻击自己的配额。

## 可复用建议

- 一个外部服务一个封装，接口尽量窄，别把上游 SDK 原样暴露给 Agent。
- 错误结构全项目统一，`retryable` 这个字段值回票价。
- 每次调用记日志：时间、参数摘要、耗时、状态。排查"Agent 为什么没调对"时，日志比猜靠谱得多。
- 封装写完先自己 curl 一遍确认行为，再交给 Agent——别把调试成本转嫁给模型。

## 总结

对接外部服务的核心不是"调通"，而是把认证、超时、错误、日志这四件事在封装层解决掉，让 Agent 面对的是一个干净、诚实、可预期的工具面。从单一只读服务开始，跑稳一个再接下一个，比一口气挂十个不稳定的工具划算得多。你们对接时踩过什么坑，评论区见。
