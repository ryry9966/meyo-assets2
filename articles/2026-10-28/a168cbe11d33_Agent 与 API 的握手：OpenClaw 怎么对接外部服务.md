## 背景

Agent 的价值上限，基本取决于它能调用什么。OpenClaw 本体更像一个调度器，真正干活的是工具：查工单、发消息、读数据库，背后都是一次对外部服务的调用。社区里常见两类玩法：直接接现成的 MCP server，或者自己写 skill 包一层 API。这篇把两条路的实践合并聊一下，重点放在「从 Demo 到能用」这段路。

## 问题

对接外部服务，演示很顺，落地很难。常见断点有这么几个：

- **鉴权**：key 放哪、怎么轮换、会不会被写进上下文和日志；
- **契约**：模型给出的参数和服务端要求的 schema 对不上；
- **稳定性**：超时、限流、重试导致重复操作；
- **返回值**：接口动辄返回几 MB 的 JSON，直接塞给模型就是灾难。

## 做法

**第一步，选接入路径。** 优先级建议：现成 MCP server > 自建薄 MCP wrapper > 在 skill 里直接发 HTTP。能复用就别造轮子，但生产环境我更倾向自建 wrapper——可观测、可控、出问题好定位。

**第二步，控制工具粒度。** 不要给 agent 一个「万能 HTTP 请求」工具，它大概率用错。按业务意图拆：`create_ticket`、`query_order`，一个工具干一件事。工具描述本质上是写给模型看的 API 文档，参数语义、单位、边界条件都要写清。

**第三步，鉴权收口。** key 走环境变量或 secret 管理，绝不进 prompt、不进日志。OAuth 场景单独处理 token 刷新，这件事不要指望模型记得。

**第四步，加防御层。** 统一超时（我的习惯是 10s 硬超时）、指数退避重试，且只对幂等接口重试。写操作加请求 ID 去重，避免 agent 一次重试把同一条消息发三遍。

**第五步，裁剪返回值。** 在 wrapper 里做字段筛选、分页截断。出错时返回一句「人话」给模型，比如「日期格式应为 YYYY-MM-DD」，比一坨 500 堆栈有用得多——错误信息要能引导 agent 自我修正。

## 踩坑点

- 工具描述含糊是参数幻觉的头号原因，可选参数一定显式标注；
- 没做响应裁剪，一次全量查询把上下文撑爆，后面全乱；
- 重试没考虑幂等，我在真实场景里见过重复下单；
- token 过期后 agent 反复重试，雪崩式刷接口，记得加熔断；
- 日志里打了完整请求体，key 泄到日志平台，复盘时一身冷汗。

## 可复用建议

1. 所有外部服务过一层薄适配，第三方 SDK 不直接暴露给 agent；
2. 每个工具单独灰度，出问题能一键下线；
3. 建一份「工具契约表」：参数、超时、幂等性、限流阈值，写代码前先填表；
4. 把调用日志当产品数据看：参数错误率高的工具，先改描述再改代码。

## 总结

对接外部服务没有魔法：选对路径、写清契约、管好密钥、兜住失败、裁剪输出。这五件事做扎实之后，模型反而是最不用担心的部分。建议从最小的一个工具跑通全链路，再谈编排和多工具协作。
