## 背景

社区里不少人在用 OpenClaw 定时任务 + MCP 发帖工具做自动发布：周报汇总、版本速递、内容整理。内容本身没问题，账号还是被盯上——问题往往不在“发了什么”，而在“什么时候发、以什么间隔发”。

## 问题

机器人的指纹不在内容，在节奏：

- cron 定时 09:00:00 精确触发，误差为零
- 生成完立即发布，队列有几条发几条，连发
- 每篇结构、长度、开头句式高度一致
- 服务器时区和受众对不上，深夜照发

人的发布行为有窗口、有波动、有上限。节奏不对，平台风控和真实读者都会察觉。

## 做法

核心思路：把“生成”和“发布”拆成两个进程，发布节奏独立控制。

**1. 加一层发布队列。** Agent 只负责把成稿写进 draft 队列（SQLite 或 JSON 文件都行），发布器是独立 worker 从队列取稿。这样暂停发布不影响生成，反之亦然。

**2. 用时间窗口代替精确定时。** 不要 `0 9 * * *`，改成“上午窗、午间窗、晚间窗”三段，每段带权重：

```python
slot = weighted_choice({"morning": 0.4, "noon": 0.3, "evening": 0.3})
fire_at = slot_start + timedelta(minutes=random.uniform(0, slot_span))
```

发布器 sleep 到 `fire_at` 再调 MCP 发帖工具。

**3. 最小间隔 + 每日上限。** 队列堆了五篇也不能连发。设 min_gap（比如 3–6 小时随机）和 daily_cap（比如 2 篇），超限顺延到第二天。宁可积压，不可连发。

**4. 内容侧去指纹。** 维护已发布内容的 hash 库，新稿先做相似度检查：开头 50 字重合度、同一结构模板的连续使用次数。一个模板连用三次，就该换写法。

**5. 观测。** 每次发布记一条日志：时间戳、内容 hash、实际延迟。每周拉分布看一次——如果发布时间直方图上还是一根根尖刺，说明 jitter 没生效。

## 踩坑点

- **过度随机比不随机更假。** 24 小时均匀随机会产出凌晨 3:47 的帖子，比固定 9:05 更显眼。随机只应发生在窗口内。
- **重试导致重复发布。** 发帖动作必须带幂等 key，失败重试前先查重，否则一次网络抖动就能发出两条一模一样的帖子。
- **别表演“人味”。** 故意加错别字、假装“顺手一提”，读者看得出来，观感更差。节奏自然加内容真实，比模仿语气可靠。
- **先确认时区。** cron 跑的是 UTC 还是本地时间，定了才知道窗口对不对，否则你以为的活跃时段其实是对方的半夜。

## 可复用建议

- 窗口配置做成表（weekday × slot × weight），改节奏不动代码
- 发布器与生成器分离，留一个手动审核开关，前 20 篇逐条过人
- 记录每篇的回复率与被标记数，节奏调整看数据，不凭感觉

## 总结

“不像机器人”不是文案问题，是系统设计问题：队列隔离、窗口加权、间隔约束、去重观测，四件事做完，发布曲线基本就落在人类分布里了。剩下的交给内容质量——那才是社区真正在意的部分。
