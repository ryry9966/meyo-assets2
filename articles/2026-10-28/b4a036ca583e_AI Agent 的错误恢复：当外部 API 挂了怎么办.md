## 背景

Agent 化的自动化任务跑得越久，依赖的外部服务就越多：搜索、数据库、行情、通知，以及各种 MCP server / 插件封装的第三方 API。对长任务来说，失败不是意外而是常态：限流、超时、5xx、凭证过期、工具进程崩掉。一次 API 抖动的最坏结局不是任务失败，而是模型编了个结果继续往下跑。

## 问题：三种典型失败姿势

- **死循环重试**：模型看到报错就原样再调一次，429 越打越多，最后账号被限。
- **幻觉兜底**：工具返回失败，模型“合理脑补”一个结果填进流程，下游全错，还很难被发现。
- **一刀切中断**：任何异常都终止任务，恢复时从头重放，前面烧掉的 token 和时间全部作废。

根因多半是同一个：把恢复策略写进了 prompt，而不是代码。

## 做法：四层防线

**第一层，错误分类。** 在工具封装层把错误分成可重试（超时、429、500/502/503）和不可重试（400、401、404、参数非法）。分类决定行为，别让模型猜。

**第二层，有界重试。** 指数退避加抖动，例如 1s/2s/4s、最多 3 次；重试在工具层同步完成，最终失败时返回结构化错误，而不是抛异常炸掉整个 loop。

**第三层，降级与熔断。** 连续 N 次失败就熔断该工具、快速失败；有备用 provider 就切换，有缓存就返回缓存并显式标注“非实时”，都没有就明确告知“该能力暂不可用”。

**第四层，断点与幂等。** 长任务按步骤 checkpoint，状态落盘，恢复时从断点续跑；所有写操作带幂等键（如 request ID），保证重试不会重复下单、重复发消息。

给模型的错误契约大致长这样：

```json
{
  "ok": false,
  "error_type": "rate_limited",
  "retryable": false,
  "recovered": false,
  "hint": "搜索暂不可用，可基于已有上下文继续，或询问用户"
}
```

模型拿到的是干净的“结果或结构化失败”。执行（重试、退避、切换）留给代码，决策（跳过、换路、问用户）留给模型。

## 踩坑点

- **让 LLM 自己重试**：烧 token、行为不确定，还容易幻觉出“重试成功了”。
- **重试非幂等操作**：POST 下单、发通知这类没有幂等键的重试，等于亲手制造重复数据。
- **退避过长阻塞主循环**：backoff 拉到 30 秒，整个 agent 卡死，不如直接熔断。
- **静默降级**：偷偷拿昨天的缓存顶上又不标注，用户以为拿到的是实时数据——信任损失比一次报错重得多。
- **把所有错误当可重试**：401 重试一万次也不会好，只会被封号。

## 可复用建议

- **统一错误契约**：所有 MCP 工具 / 插件返回同构的 `{ok, error_type, retryable, recovered, hint}`，agent 侧处理逻辑只写一次。
- **配置外置**：max_retries、退避基数、timeout、熔断阈值进配置文件，不同工具给不同档位。
- **记错误账本**：错误类型、工具名、时间戳落盘，定期看分布——限流多就去申请配额，超时多就去查网络。
- **启动探活**：agent 启动时对 MCP server 做健康检查，别等任务跑到一半才发现进程早死了。

## 总结

错误恢复是模型下面的一层工程，不是 prompt 里一句“失败了请重试”。原则一句话：确定性问题用确定性代码解决——分类、重试、熔断、幂等、断点；只有“接下来怎么办”这种依赖上下文的判断，才交给模型。外部 API 会挂，这不是你的 bug；挂了之后 agent 的行为，才是你的设计。
