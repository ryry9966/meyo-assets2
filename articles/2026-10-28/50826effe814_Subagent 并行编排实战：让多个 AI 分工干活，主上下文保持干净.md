## 背景

单 Agent 干久了会遇到两个老问题：一是任务之间明明没有依赖，却只能排队串行等；二是所有中间过程——探索日志、原始抓取内容、报错堆栈——全堆在主会话上下文里，跑几轮之后上下文被塞满，模型后半程开始"失忆"，输出质量肉眼可见地下降。

OpenClaw 的 subagent 机制给了第三条路：主 Agent 只做拆解和汇总，把具体执行交给若干拥有独立上下文的 subagent，彼此并行、互不污染。

## 问题

我当时的实际场景：批量整理一批本地文档 + 抓取若干网页 + 生成汇总报告。串行跑一次要 20 多分钟，而且抓取的原始内容把主会话撑得很臃肿，后半段报告明显不如前半段靠谱。

## 做法

我的编排结构大致三层：

1. **主 Agent 只做调度**：负责拆任务、下发、收结果、写最终报告，不直接碰执行工具。
2. **subagent 各自独立上下文**：每类任务一个 subagent（文档整理、网页抓取、格式校验），通过 MCP 挂各自需要的工具，工具范围收窄到最小集。
3. **结果落盘再汇总**：subagent 把产出写进约定好的文件（如 `results/xxx.md`），只给主 Agent 返回一段简短的结构化摘要。主 Agent 读文件，而不是读聊天记录。

并行策略很简单：无依赖的任务同时发；报告生成必须等前两类结果落盘后再启动。这就是最基本的 DAG 思路，不需要复杂框架，在任务描述里写清楚依赖即可。

## 踩坑点

- **两个 subagent 改同一个文件**：文档整理和格式校验最初都有写权限，出现过互相覆盖。后来固定"谁产出谁写入，其他人只读"。
- **subagent 摘要太长**：一开始让它"汇报工作"，返回几千字，主 Agent 上下文照样爆炸。改成强制 JSON 摘要 + 文件路径引用后才解决。
- **并发把配额打满**：5 个 subagent 同时抓网页，触发上游限流。加了并发上限（2–3）和重试退避。
- **任务描述不自包含**：subagent 看不到主会话历史，描述里必须把目标、约束、输出格式写全，不能写"按刚才说的做"。
- **成本翻倍**：并行等于并行烧 token。小任务不值得拆，我现在的门槛是预估超过 3 分钟或涉及大量原始素材的任务才拆。

## 可复用建议

- 给 subagent 定一个"任务契约"模板：目标 / 边界 / 可用工具 / 输出格式 / 完成标志，五个字段缺一不可。
- subagent 数量控制在 3–5 个以内，多了调度本身就成为负担。
- 用文件系统当协作媒介，不要靠上下文传递大块内容。
- 每个 subagent 保留独立运行日志，出问题能单独回放，不用重跑全流程。
- 失败要有兜底：超时降级为串行，或标记该分支失败后继续汇总，别让一个分支卡死整条流水线。

## 总结

subagent 编排的核心收益不是"快"，而是**隔离**：上下文隔离让主 Agent 保持清醒，职责隔离让每个执行者的工具面最小化，再加上无依赖任务并行，整条流程从 20 分钟压到 6 分钟左右。但它不是银弹——任务边界不清晰时，强行并行只会放大混乱。建议从"一个会阻塞主会话的长任务"开始试，先把任务契约和结果落盘这两个习惯跑通，再逐步扩展到更复杂的编排。
