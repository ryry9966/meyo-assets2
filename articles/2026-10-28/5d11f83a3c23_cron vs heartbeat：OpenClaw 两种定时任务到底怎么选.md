## 背景

用 OpenClaw 做个人自动化跑了一段时间后，所有"让 agent 自己干活"的需求基本都会落到两个机制上：**cron** 和 **heartbeat**。两者都能让 agent 周期性运转，但设计意图完全不同。我最初把 heartbeat 当"更聪明的 cron"用，结果 token 烧了不少，任务时机还不准；后来又把一堆状态检查塞进 cron，条件写死，需求稍微变一下就得改表达式。这篇把选型思路和踩过的坑整理一下。

## 两者的本质区别

- **cron：时间触发，payload 固定。** 几点几分执行、执行什么提示词，创建时就确定了。适合"我知道什么时候该做什么"——每天 9 点拉日报、整点数据同步、定时提醒。
- **heartbeat：周期唤醒 + agent 自主判断。** 每隔一段时间给 agent 一个唤醒提示，它结合当前上下文决定要不要行动，没事就静默。适合"我不确定什么时候有事，但有事你得知道"——有新邮件才通知、盯一个任务的变化。

一句话判断标准：**触发条件是时间，还是状态？** 时间就用 cron，状态就让 heartbeat 判断。

## 落地步骤

1. 列出所有自动化需求，分成两类：固定时刻类和状态驱动类。
2. 固定时刻类走 cron：通过 CLI 或直接在对话里让 agent 创建，写清 cron 表达式和 payload，指定投递渠道和会话。建议用独立会话，别污染主会话的上下文。
3. 状态驱动类走 heartbeat：先把间隔调大（比如 60 分钟），然后在 agent 的常驻指令里写明三件事——每次醒来检查哪几项、什么情况才算"值得打扰用户"、没事时明确返回 HEARTBEAT_OK 静默。
4. 跑一周后看日志，统计 heartbeat 的空转率（醒了多少次、真干活几次），再决定要不要收紧间隔。

## 踩坑点

- **heartbeat 默认间隔偏激进**。挂上几个 MCP 工具后，每次唤醒都可能触发真实工具调用，账单涨得比预期快。先调大间隔，看清消耗再收紧。
- **cron 时区跟网关宿主机走**。容器里默认 UTC 很常见，日报整体偏移 8 小时基本都是这个原因，先确认时区再写表达式。
- **没给 heartbeat 留静默出口**。agent 会动不动回一句"暂时没什么事"，渠道里全是噪音。必须在指令里明确"没事就别说话"。
- **长任务别挂在 heartbeat 里**。执行太久会堵住下一次唤醒；cron 也要注意上一次没跑完、下一次又触发的重叠问题。
- **半状态需求别硬凑 cron 表达式**。"每天看一眼再决定做不做"这类需求，拆成 cron 触发 + agent 内部判断，比把复杂条件编码进表达式稳得多。

## 可复用建议

- cron 管"何时"，heartbeat 管"是否值得"，各干各的，不要互相客串。
- heartbeat 指令越短越具体越好：枚举检查项和打扰阈值，比写一大段模糊描述有效得多。
- 两条链路都留日志，定期复盘空转和漏报，这是调间隔的唯一依据。
- 心跳间隔宁大勿小：宁可慢半拍，不要为省几分钟持续烧 token。

## 总结

cron 和 heartbeat 不是替代关系，而是分工关系。定时确定的事交给 cron 拿确定性，依赖上下文判断的事交给 heartbeat 拿灵活性。选型的核心就一个问题：这件事的触发条件，你现在是知道的，还是只有 agent 看了才知道？想清楚这一句，大部分定时任务都能放对地方。
