## 背景

OpenClaw 的 Agent 每次会话启动都会加载 workspace 里的一组 Markdown 文件。AGENTS.md 管"怎么干活"，TOOLS.md 管"工具怎么用"，USER.md 记"用户是谁"，而 SOUL.md 负责"我是谁、我怎么说话、我什么不做"。它本质上是人格层加边界层，不是任务清单。

实际用下来，SOUL.md 恰恰是最容易被写坏的文件：有人留空，有人写成小作文，还有人把操作规范、定时任务说明全塞进去。

## 问题

三种典型故障：

1. **人格缺失**：换模型、升版本后语气风格漂移，团队里多个实例表现不一致。
2. **人格过重**：角色扮演渗出到正常任务，出现"作为某角色我不能做这个"，该执行的反而不执行。
3. **边界缺失**：Agent 过度顺从，模糊指令也直接动手——改配置、发消息、删文件，事后才发现越权。

## 做法

**第一步：建文件**。在 `~/.openclaw/workspace/SOUL.md` 创建，控制在 30–60 行。

**第二步：结构化书写**，推荐骨架：

```markdown
# SOUL.md
## 我是谁
一句话身份定位，不超过两行。
## 语气
- 平铺直叙，不堆 emoji
- 不确定时直说，并给出依据
## 边界
- 删除类操作先确认再执行
- 涉及付款、群发消息：先复述意图
- 拒绝时说明原因，并给一个替代方案
```

**第三步：边界写成可验证的行为**。"当 X 发生时，我做 Y"。不要只写"要诚实""要谨慎"这类形容词，没法测试。

**第四步：和 AGENTS.md 分工**。SOUL 管"是什么人"，AGENTS 管"怎么干活"，同一件事只在一个文件里出现。

**第五步：回归验证**。新开会话或重启 gateway，准备 5 个边界用例：诱导越权、要求过度承诺、模糊危险指令、人设冲突提问、正常但无聊的任务。观察是否按预期确认、降级或拒绝。

**第六步：进 git**。workspace 用 git 管理，行为异常先看 diff——很多"突然变了"都是最近一次改动引入的。

## 踩坑点

- **全是否定句**。"不要 XX"堆十几条，遵循率很差。改成正向行为描述："删除前必须复述目标文件并等待确认"。
- **两个文件写重复条目**。SOUL 和 AGENTS 各有一条相似规则，措辞略有差异，Agent 表现就会随机化。改之前 grep 一遍。
- **人设强度失衡**。"永远不能拒绝用户"和"永远委婉"都会破坏边界，写中性、具体的行为。
- **改完不生效**。旧会话已加载旧文件，先 `/new` 或重启再测，不然会误判改动无效。
- **和 USER.md 冲突**。用户资料更新了，SOUL 里的假设没跟着改，行为就会自相矛盾。SOUL 只放稳定项。

## 可复用建议

- 骨架比例：身份 1 段 + 语气 3 条 + 边界 5 条 + 拒绝话术 1 段，超过 100 行就该拆。
- 每条边界配一个测试用例，攒成回归集，改 SOUL 必跑。
- SOUL.md 追求稳定，几个月不动是常态；高频变化的内容放 USER.md 和 AGENTS.md。
- 每季度 review 一次，删掉从未被触发过的条目。

## 总结

SOUL.md 的价值不在文采，而在**稳定、可测、可回滚**。把它当成 Agent 的小型宪法来维护：条目少、措辞具体、每条都能验证。人格让 Agent 好相处，边界让它可被信任——后者才是自动化场景里真正值钱的部分。
