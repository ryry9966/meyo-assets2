## 背景

大多数 AI 助手的交互模型是"你问我答"：你不发消息，它就是死的。但真正省时间的场景往往是那些你没意识到要办的事——每天早上汇总昨天的 CI 失败、磁盘快满时提醒、监控关键词出现后自动归档进笔记。这些事的共同点是：触发条件明确、动作可枚举，但人不想记。

## 问题

把"被动应答"改成"主动出手"，工程上会撞到三件事：

1. **何时触发**：轮询太贵，事件源又散；
2. **要不要出手**：判断错一次就是骚扰，用户把通知一关，比不做还糟；
3. **出手边界**：主动动作里有 mutating 的（给第三方发消息、改配置），失控成本高。

## 做法：一条最小可用的触发链

分四层，每层尽量薄。

**1. 触发源收敛。** 两种就够：cron / heartbeat 定时唤醒 + webhook / 文件事件。OpenClaw 的 heartbeat 自带固定周期唤醒，周期设 15–30 分钟起步，别信"每分钟查一次"的直觉。事件源通过插件 hook 或 webhook 进来，统一投递到同一个收件箱队列。

**2. 分诊层。** 每次唤醒不直接干活，先喂一份"状态快照 + 待处理触发"给模型，要求输出结构化决策：

```json
{ "decision": "ACT | QUEUE | DROP", "action": "...", "reason": "...", "event_id": "..." }
```

ACT 立即执行，QUEUE 攒进 digest，DROP 丢弃。这一步用小模型就够，省钱且延迟低。

**3. 执行与边界。** 维护一张动作白名单：只读动作（查询、汇总、写自己的笔记）直接执行；mutating 动作一律降级为"提议"，等你回一个字确认。宁可多问一次，不要猜。

**4. 观测。** 每次主动决策落一条日志：触发源、快照摘要、决策理由、执行结果。没有这层，出了"它半夜给我老板发了消息"这种事故，你连复现都做不到。

## 踩坑点

- **通知疲劳**：上线第一周 heartbeat 设了 5 分钟，第三天被自己 mute 了。改成 digest 后——低紧急度攒到整点合并推送——打扰量降了一个数量级。
- **决策抖动**：模型对 urgency 判断不稳定，同一件事这轮 ACT 下轮 DROP。解法是判据写死成显式规则（阈值、关键词），模型只分类、不定级。
- **重复执行**：webhook 重试 + 无幂等键 = 同一条消息发三遍。给每个触发源加 event id，执行前查重。
- **时区**：cron 用 UTC 写的，digest 在用户本地早上六点炸响。所有时间统一存 UTC，展示层转本地，别在触发层耍聪明。
- **上下文腐化**：快照喂太多历史，模型会脑补没发生的事。快照只放最近一次状态 + 当前触发，别贪。

## 可复用建议

- **先跑 observe-only 一到两周**：只记录"如果允许我会做什么"，人工审完再放执行权，能提前暴露九成误判。
- **reason 字段必填**：schema 约束下的理由会倒逼模型（和你）想清楚为什么出手。
- **触发源做成声明式配置**：新场景加一段配置就能上线，改行为不动代码。
- **给主动性设预算**：单日主动触达上限（比如 5 条），超了只进 digest。上限本身就是最好的产品约束。

## 总结

Proactive 不是让 agent 更聪明，而是把"何时触发、是否出手、能做什么"从模型直觉变成工程约束。触发源收敛、决策结构化、动作分级、全程留痕——四件事做到位，"不等你开口"才不会变成"不由分说"。从 observe-only 起步，逐步放权，让日志说话。
