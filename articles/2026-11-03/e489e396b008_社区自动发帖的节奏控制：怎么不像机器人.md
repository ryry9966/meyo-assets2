## 背景

我们在 OpenClaw-CN 的几个频道跑着一套自动化：周报摘要、新插件通告、issue 跟进提醒。链路很简单——agent 定时拉数据，通过自建的 MCP posting tool 写入频道。跑了两周，有群友直接说：“这机器人整点发帖，比闹钟还准。”功能都对，但节奏不对，自动发帖很容易变成社区噪音。

## 问题

回看日志，典型症状有三个：

1. **整点触发**：cron 设在 0 点和 9 点，分秒不差；
2. **连发**：一次跑批生成 4 条内容，30 秒一条全吐出去；
3. **复读机**：所有帖子同一个开头模板，群里一眼认出。

三者叠加，哪怕内容有价值，观感上就是垃圾推送；突发高频在平台侧也容易触发频控。

## 做法

我们把“节奏”收进 posting tool 的职责，而不是让每个 agent 任务自己管。核心五步：

1. **收口到队列**。所有发帖请求先进持久化队列，由单一 scheduler 消费，谁都不许直连发帖接口——这是后面一切的前提。
2. **令牌桶 + 配额**。每频道一个令牌桶：约 90–150 分钟回填一个令牌，桶容量 2，日配额 5 条；超了就拒绝并在日志标 `rate_limited`。
3. **活动窗口 + 抖动**。只在本地时间 9:00–22:30 发；间隔不是均匀随机，而是“基准间隔 × lognormal 抖动”，多数贴近基准、少数拖得很长。凌晨绝不发——机器不困，读的人困。
4. **去重与变体**。对最近 N 条历史做相似度粗筛（标题向量即可）；备 3–4 套开头模板，随机补一句上下文相关的导语。
5. **反馈降速**。每条帖记录回复/表情数，连续几条零互动就把该频道配额减半，并挂一条待人工审核的标记。

## 踩坑点

- **抖动别用均匀分布**：间隔在 min~max 间均匀跳，统计上依旧机械，lognormal 明显更自然。
- **重试引发连发**：scheduler 重启后，我们曾把积压的 6 条一口气补发。修法是恢复时按令牌桶重新排队，而不是补发。
- **时区**：服务器 UTC、社区 UTC+8，“早上 9 点发”实际是下午 5 点。活动窗口必须显式配置时区。
- **配额状态放内存**：重启即清零，限流形同虚设。令牌桶状态要落盘或进 Redis。
- **别假装是人**：我们试过模拟“正在输入”的延迟，被群友一句话戳穿，反而更尴尬。大方声明是自动化账号，把礼貌做在节奏和内容质量上，比伪装有效得多。

## 可复用建议

- 限流做进 MCP tool 层：agent 只管“发什么”，“何时发、发多少”由 tool 统一裁决；窗口、配额、抖动系数全部走配置文件，按频道给不同 profile。
- 发帖请求带幂等键，重试不产生重复帖。
- 留一个 kill switch：一条命令清空队列、暂停所有频道，出事故时救命。
- 每周人工 review 一次“计划 vs 实发”日志，按社区反馈微调参数。

## 总结

自动发帖不像机器人，关键不在伪装，而在克制：收口、限速、看场合、听反馈。节奏控制的本质是承认——一条帖子是打扰还是价值，由读的人投票，系统要做的就是把投票结果接回调度里。
