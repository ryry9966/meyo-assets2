## 背景

OpenClaw 的 cron 能力用起来很顺手：一段 crontab 表达式加一句 instruction，agent 就能每天定点干活。但实际跑下来，大多数"跑得不对"的定时任务，问题不在调度，而在 instruction 本身——大家习惯用写聊天提示词的方式去写它。

## 问题：定时任务和对话是两回事

对话里模型有完整上下文，写岔了你还能追问。Cron 任务是无人值守执行，且通常在新起的上下文里跑：

- 没有会话记忆，"像上次那样"是无效信息；
- 没有追问机会，模糊指令只能被模型自由发挥；
- 失败是静默的，你不看日志就不知道它今天压根没干活。

判断标准因此很简单：**一个不了解你任何背景的执行者，拿到这段 instruction 能不能一次跑对。**写 cron instruction 本质是在写交接单。

## 做法：六个必填项

先看一个常见的坏例子：

> 每天早上汇总一下我的 GitHub 通知发给我。

这句跑起来通常是三种结局：输出一大篇没人看、把无关通知全算进去、或者失败后什么都不发。改写后：

> 每天 08:05（Asia/Shanghai）。用 GitHub MCP 工具读取过去 24 小时的通知，只保留 mention 和 review request。结果为空则回复"今日无待处理"；有结果则按「仓库 / 标题 / 链接」逐条列出，最多 10 条，发到 Telegram 主会话。任一步工具调用失败，发一条含错误摘要的消息，禁止静默。

对比可以提炼出六个必填项：

1. **时间与时区**：调度器时区和你的体感时区可能不一致，写死。
2. **数据来源写死工具名**：不要写"查一下 GitHub"，要写清用哪个工具、哪个仓库、什么范围。
3. **筛选规则与阈值**：什么算"值得报告"，用可判定的条件，不用形容词。
4. **空结果行为**：数据为空时回一句"无事"还是保持静默，二选一写明。
5. **失败必须显式上报**：这是最重要的一条，明确禁止模型吞掉错误。
6. **输出渠道、格式、上限**：发到哪、什么结构、最多几条。上限同时是在控制 token 成本。

## 踩坑点

- **依赖对话记忆**："按我们上周讨论的口径"——cron 执行时拿不到，全靠模型脑补。
- **相对时间没定义**："最近的通知"是 1 小时还是 24 小时？统计窗口写成绝对区间。
- **任务重叠**：长任务没设超时，下一轮触发时上一轮没跑完，结果重复发送。
- **高频任务塞重逻辑**：每 5 分钟跑一次全量分析，不如拆成"定时采集 + 每日汇总"两级。
- **上线前不试跑**：先手动触发一次，看日志确认工具调用链和输出通道都通，再挂 cron。

## 可复用模板

把每条 cron instruction 按这个骨架过一遍：

> 【触发】时间 + 时区 ｜【输入】工具名 + 数据范围 ｜【规则】筛选条件与阈值 ｜【空态】空结果怎么办 ｜【异常】失败如何上报 ｜【输出】渠道 + 格式 + 条数上限 ｜【幂等】如何避免重复发送

新任务照着填空，老任务拿它做 review，十秒钟就能看出缺哪一项。

## 总结

Cron instruction 不是提示词，是交接单。写的时候少想"怎么让模型理解我"，多想"值班的人缺什么信息才会出错"。把上下文、边界、异常、出口全部显式化，定时任务才能从"偶尔能用"变成"敢长期挂着"。
