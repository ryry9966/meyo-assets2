## 背景

做 Agent 开发的人有个共同痛点：调试循环烧钱。一个 agent loop 反复调用，一轮回归测试下来几万 token 就没了；另外自动化任务经常要碰本地文件、日志、聊天记录，走云 API 始终有隐私顾虑。本地部署解决的就是这两个问题：**零边际成本的试错，以及数据不出门**。这也是我把本地模型接进 OpenClaw 工作流的原始动机。

## 先校准预期

本地模型不是云端模型的平替。8B~14B 的量化模型在总结、改写、简单工具调用上够用，但复杂多步推理和长上下文任务差距明显。我的定位一直是：**本地跑草稿和隐私任务，云端做重活**。带着这个预期，落地会顺利很多。

## 做法与步骤

**第一步：盘硬件。** 有 NVIDIA 显卡的按显存选：8GB 跑 7~8B Q4，12GB 跑 14B Q4，24GB 跑 32B Q4。Mac 按统一内存的 60%~70% 估算可用量。纯 CPU 能跑但慢，只建议做轻量任务。

**第二步：选推理引擎。** Ollama 起步最省事，一条命令拉模型即起服务，自带 OpenAI 兼容端点。需要精细控制（KV cache 量化、flash attention、自定义模板）再上 llama.cpp 或 LM Studio。对 Agent 用户来说，端点兼容性比极限性能重要，先用 Ollama 跑通再说。

**第三步：选模型和量化。** GGUF 的 Q4_K_M 是速度/质量甜点，不必迷信 Q8。优先选对 function calling 友好的模型：Qwen3 系列、Llama 3.1+ 在工具调用上表现稳定，中文场景 Qwen 是首选。

**第四步：接进 Agent 框架。** Ollama 默认监听 11434 端口，OpenAI 兼容路径是 `/v1`。在 OpenClaw（或任何支持自定义 base_url 的框架）里把 provider 指到 `http://localhost:11434/v1` 即可。**先别急着接 MCP**——手动发一个带 tools 的请求，确认模型能稳定吐出合法的工具调用 JSON。这一步不过关，后面全是白搭。

## 踩坑点

1. **上下文是隐形杀手**：KV cache 随上下文线性增长，8B Q4 标称 5GB，上下文拉到 32K 能再多吃好几个 G。而 Agent 恰恰是长上下文重灾区。
2. **keep_alive 陷阱**：模型默认闲置一段时间后卸载，自动化任务触发时冷启动要等几十秒。常驻任务记得设置保活，但要接受显存被长期占住。
3. **工具调用解析差异**：不同引擎对 tool call 的解析实现有出入，偶发"模型明明调对了，框架却解析失败"。升级引擎版本往往能解决。
4. **吞吐量**：agent 一轮循环生成成百上千 token，10 tok/s 的机器跑复杂 agent 是煎熬，流畅体验至少 30 tok/s 起步。
5. **别忘了 embedding**：RAG 或记忆检索场景需要单独跑一个 embedding 模型，显存要一起算进去。

## 可复用建议

- **分层路由**：简单任务和隐私任务走本地，复杂任务回落云端，按质量和成本做 fallback；
- **换量化档位前，先跑一套固定的评测 prompt 集**（必须包含工具调用 case），别凭感觉切换；
- 把"模型 + 量化 + 引擎版本"写进配置注释，出问题能快速回滚。

## 总结

本地部署的价值不只是省 API 钱，而是把试错成本降到零——你可以放心改 prompt、改工具描述、跑回归，不用心疼账单。一台普通电脑加 8~14B 量化模型，就能承载大部分日常 Agent 实验。顺序很重要：先验证工具调用，再接 MCP 和自动化，最后才谈性能调优。
