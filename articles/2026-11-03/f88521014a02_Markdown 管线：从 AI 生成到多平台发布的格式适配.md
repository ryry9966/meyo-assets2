## 背景

用 OpenClaw / Agent 做内容生产的同学大概都有类似流程：让模型产出 Markdown 初稿，人工修订，然后贴到公众号、知乎、掘金或者自己的博客。写的次数多了会发现，真正耗时的不是写作，而是“适配”——同一个文件，发到不同平台要手动改好几轮。

我们的做法是把这一步做成管线：规范化的源文件 + 一组针对平台的 AST 转换 + 发布前的自动校验。这篇帖记录一下结构和踩过的坑。

## 问题

各平台对 Markdown 的支持差异比想象中大：

- 公众号不支持外部 CSS，代码高亮需要内联样式；外部图床的图片会被拦截（403）
- 知乎会剥掉大部分 HTML class，脚注语法不渲染
- 多数平台不支持 Mermaid，需要预渲染成图片
- 表格、任务列表、`[^1]` 脚注这些 GFM 扩展，覆盖程度参差

如果每次都手工改，适配成本等于线性乘以平台数。管线要解决的核心问题是：**源文件唯一，产物多份，转换过程可测试**。

## 做法

**1. 源文件规范化（生成期 lint）**

在 AI 生成后就做 lint，而不是发布前。用一条简单规则清单卡住常见问题：

- 只允许一个 `#` 一级标题
- 代码块必须带语言标记
- 图片走相对路径 + 本地清单，禁止裸外链
- frontmatter 固定字段：`title`、`platforms`、`tags`

这一步可以包成 MCP 工具或脚本，挂在 Agent 的收尾动作里：模型写完自动跑，不合格就打回重写。

**2. AST 层转换，不做字符串替换**

用 remark / mdast（unified 生态）写转换器，每个平台一个 adapter：

- 公众号 adapter：高亮转内联 style、脚注降级为上标引用、图片 URL 重写为平台图床地址
- 通用 adapter：Mermaid 块预渲染为 SVG 并替换节点
- 转换器全部是纯函数，输入 AST 输出 AST，方便单测和快照对比

**3. 图片中转与清单**

发布前统一把图片上传到目标平台或固定图床，生成 `image-manifest.json` 记录「本地路径 → 各平台 URL」。URL 用内容哈希命名，重复发布不浪费配额，也利于缓存命中。

**4. 发布前冒烟校验**

对渲染产物做三件事：链接可达性检查、图片状态码检查、与上次发布的快照做 diff。最后一步成本极低但经常救命——能提前发现“整段被平台吃掉”这类事故。

**5. 发布编排**

一个 CLI 入口：`publish --target wechat|zhihu|juejin --file xxx.md`，内部串起 lint → transform → upload → verify。接入 OpenClaw 就是给 Agent 加一个工具调用，人工只保留最后一步确认。

## 踩坑点

- **正则字符串替换是坑的根源**：早期用正则处理脚注和代码块，遇到嵌套结构必挂，换 AST 后稳定
- **全角/半角标点混用**：模型输出里智能引号不一致，部分平台排版会拉开间距，lint 里统一收敛
- **嵌套列表超过两层**在公众号编辑器里会被压平，adapter 里主动降级为加粗段落
- **HTML 注释当草稿批注**：某些平台会原样渲染出来，统一在转换阶段删除
- **数学公式**：`$$` 和 `\(` 两种写法在不同渲染器表现不同，源文件强制只允许一种

## 可复用建议

- adapter 配置化：平台差异写成声明式规则表（“脚注→上标”“表格→HTML"），新平台接入只加配置
- 转换器保持纯函数 + 快照测试，改样式不引入回归
- 图片清单和发布记录持久化，保证幂等重发
- lint 尽量前置到生成阶段，越早发现问题返工越少

## 总结

多平台发布的痛点不在 Markdown 本身，而在“表示层”的碎片化。把规范校验前置、用 AST 做确定性转换、用清单管理副作用，就能把适配成本从每次手工劳动变成一次性工程投入。整套思路不绑定具体工具，用 pandoc + 自定义 filter 也能实现，关键是把“转换”当作代码来写、来测试。欢迎在评论区交流你们平台的 adapter 规则表。
