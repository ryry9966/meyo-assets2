## 背景：自动化任务一定会被重复执行

接入 OpenClaw 之后，很多日常事务交给了定时任务和 Agent：定时汇总通知、同步数据、webhook 触发推送。跑久了会发现一个规律：**任何自动化任务，最终都会被执行不止一次**。

原因很朴素：网络超时后的客户端重试；定时器重叠（上一轮没跑完，下一轮已触发）；排障时的手动 re-run；Agent 判断"上一步可能失败了"，自行再调一次工具。重试不是 bug，而是分布式系统的正常行为。真正的问题是：任务本身扛不扛得住重复。

## 问题：非幂等操作的翻车现场

幂等的定义：同一操作执行一次和执行 N 次，最终状态一致。常见的非幂等写法：

- `append` 追加写文件/数据库：跑三次就有三份重复数据；
- "发一条通知"：重试后群里出现两条相同消息；
- `create` 类工具：每次调用都新建一个对象；
- "同步新增数据"：新增判定依赖上次运行时间，窗口一重叠就重复或丢数据。

这类问题单次测试永远测不出来，只在重试发生时暴露——而重试往往发生在你最忙的时候。

## 做法：把重复执行变成无害操作

**1. 先分类。** 把任务里每个外部动作分成天然幂等（覆盖写、upsert、`mkdir -p`、按固定文件名写入）和非幂等（append、create、send），后者是改造对象。

**2. 用稳定的幂等键。** 给每个逻辑任务生成跨重试不变的 key，比如 `hash(任务名 + 触发日期 + 输入摘要)`。注意：不能用 `now()` 这类每次都变的值做 key，否则重试时 key 变了，去重就失效。执行前先查 key，存在即跳过。

**3. 把"创建"改成"确保存在"。** `create_user` 改成 `upsert_user`；报告用固定文件名覆盖，而不是 `report_20240501_1430.txt` 这种时间戳文件名——除非目的就是归档。

**4. 状态检查交给存储层。** 应用层"先查再插"有竞态：两次并发执行可能同时通过检查。正确做法是给存储加唯一约束，靠 `on conflict do nothing` 兜底，冲突即视为已执行。

**5. 记录执行台账。** 一张极简表就够：`idempotency_key, status, finished_at`。它既是去重依据，也是排障时回答"这个任务到底跑没跑过"的唯一可信来源。

**6. 删除类任务把"不存在"当成功**，返回正常结束而不是报错，否则重试会无限失败。

## 踩坑点

- **key 里掺了易变量**：秒级时间戳、随机 ID 放进 key，重试即失效。key 的输入只能包含任务逻辑定义相关的内容。
- **台账没有 TTL**：去重记录永久保留，表无限膨胀，周期性的合法重跑也会被误杀。过期时间设为任务周期的 3 倍左右。
- **"只读"工具其实有副作用**：写日志、发埋点、消耗配额。Agent 循环里重复调用读操作，成本照样翻倍。
- **部分失败**：写了一半的文件、发出但未确认的消息。恢复逻辑要设计成"检测并补完"，而不是"从头重做"——重做本身会制造新的重复。

## 可复用建议

- 定一条默认规则：凡是定时触发或 webhook 触发的任务，**必须假设它会被连续执行两次**，评审时按这个标准过一遍。
- 写 MCP 工具/插件时，优先暴露 `ensure_*` / `upsert_*` 语义，而不是裸的 `create_*`。
- 上线前做简单验证：测试环境连续跑两遍，diff 前后状态（文件数、行数、消息数），一致才算通过。
- Agent 的工作流提示里加一条硬约束："执行写操作前，先确认目标是否已存在。"

## 总结

幂等性不是什么高级架构概念，它只是承认了一个事实：重试一定会发生。与其指望"这次不会重复"，不如让每一次重复执行都变成无害的空转。先用幂等键挡住 create/send 类操作，再把剩余写操作改造成覆盖语义，最后用一张台账表兜底——三步下来，自动化任务就从"碰运气"变成了"可依赖"。
