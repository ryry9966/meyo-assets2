## 背景

在 OpenClaw 这类 agent/自动化体系里，任务被重复执行几乎是常态而非异常：webhook 重试、消息队列的 at-least-once 语义、网络超时后 agent 自行重试、MCP 工具调用失败后的 fallback，或者用户手动"再跑一次"。问题从来不是"会不会重复"，而是你的自动化设计能不能扛住重复。

## 问题

读操作天然幂等，危险的是写操作。几个典型翻车场景：

- 报警事件触发 agent 建工单，事件重投后建了三张重复工单；
- 定时任务把"同步数据"写成了"追加数据"，重跑一次数据量翻倍；
- agent 调外部 API 发通知，超时后重试，用户收到两条一模一样的消息。

根本原因是：很多自动化把写操作设计成**"执行一个动作"**（increment / insert / send），而不是**"收敛到一个状态"**（set / upsert / ensure）。前者执行两次就产生两份副作用，后者执行多少次结果都一样。幂等性的全部工作，就是把前者改造成后者。

## 做法

**1. 给每个业务操作定一个幂等键。**
"来源事件 ID + 操作类型 + 目标资源"是常见组合；定时任务可以用"任务名 + 周期"（如 `sync_20240601`）。键的粒度要对应**一次业务意图**，而不是一次执行。

**2. 先落状态，再执行。**
执行外部写之前，先把幂等键写入本地存储（SQLite 一张表就够），状态从 pending 到 done。检查逻辑：键不存在 → 写入 pending 并执行；已 done → 直接跳过；还是 pending → 视为并发或残留，先对账再动。

**3. 能"置状态"就不"追加"。**
upsert 代替 insert，"确保存在"代替"创建"，全量同步代替增量追加。协议层面 PUT 语义天然幂等，优先选这类接口。

**4. 不可避免的非幂等调用（如 POST 建资源）做补偿。**
API 支持幂等键头就用上；不支持就"查后建"——先确认目标是否已存在再创建，并把远端资源 ID 记回状态表，方便对账。

**5. 对账兜底。**
进程完全可能死在"已执行、未标 done"之间，所以重试路径上永远先看远端实际状态，再决定是重放还是直接标记完成。

## 踩坑点

- **幂等键里带时间戳**：每次重试生成新键，等于没做。
- **检查与写入不原子**：两个并发请求同时通过"不存在"检查，双双执行。用唯一约束 + 事务，或 Redis SETNX。
- **去重记录清理太狠**：键只留几小时，隔天重放照样重复。
- **拿 LLM 输出做键或做比对**：agent 每次生成的文本都不同，比对必然失败。键要锚定在触发事件上，不锚定在生成物上。
- **相同键、不同载荷的重试**：明确策略——拒绝，还是沿用第一次的载荷。别静默覆盖。

## 可复用建议

- 在插件/MCP server 层做一个统一的"幂等执行器"，收口所有外部写调用：键生成、状态表、执行、标记放一处，别让每个 workflow 自己造轮子。
- 状态表保持最小字段：`key`、`status`、`result_ref`、`created_at`，够用且好排查。
- CI 里加一条"跑两遍"用例：同一输入连续执行两次，断言副作用只发生一次。
- 设计新 workflow 时先问一句：**这个操作执行两次会发生什么？** 答不上来，就还没设计完。

## 总结

幂等不是一个需要安装的库，而是三个决定：定键、落状态、向目标状态收敛。agent 系统里失败与重试无法根除，把幂等做进默认路径，成本是一次表设计加一层包装；不做，代价迟早以重复工单、重复消息和脏数据的形式还回来。
