# 背景

让 Agent 直接操作文件系统，最怕的不是它写错代码，而是它"顺手"删了不该删的东西。OpenClaw 的 Agent 默认带文件读写、shell、MCP 工具调用能力，一条模糊指令（"清理一下临时文件"）加上模型的过度自信，就可能演变成一次不可逆的 `rm -rf`。只在 system prompt 里写"请小心操作"，在工程上等于没有约束——提示词是建议，不是边界。

# 问题

我们跑长任务自动化时，核心顾虑有三个：

1. 模型可能幻觉出错误路径，把相对路径解析到工作区之外；
2. 插件和 MCP server 拿到的权限，往往比任务实际需要的大得多；
3. 删除一旦执行就没有 undo，事后只能靠备份兜底。

OpenClaw 的 sandbox 不是单点防护，而是一条纵深链路。每一层拆开都不复杂，组合起来才让"误删"从概率问题变成结构上难以发生的问题。

# 做法：四层防线

1. **工作区监禁。** 所有文件工具的路径在执行前先做 realpath 解析，再校验是否落在 `sandbox.root` 内。符号链接、`../`、绝对路径都在这一层被拦下。关键在顺序：先 resolve 再校验，反了就是绕过。

2. **操作分级。** 读、写、删是三种能力级别。删除被定义为 destructive op，默认二选一：触发人工确认，或在策略文件里显式 allowlist（比如只允许删 `build/` 下的产物）。

3. **软删除缓冲。** 即使删除被放行，`rm` 实际是把文件移动到工作区之外的 staging 目录，带保留期，定期清理才真正 unlink。Agent 视角里操作"成功"了，但你有至少一个回滚窗口。

4. **作用域与审计。** MCP 工具注册时声明 capability，host 按 session 签发最小作用域 token；每次文件操作落审计日志，可回放。出了事不是靠"猜"，是靠"查"。

# 踩坑点

- **符号链接逃逸：** 早期只做字符串前缀匹配，一个指向工作区外的 symlink 就穿透了。务必 realpath 之后再判断。
- **裸 shell 绕过：** 文件工具管得再严，给了不限速的 shell 等于白做。我们的做法是 shell 也走同一套路径校验，或只在高信任任务里开放。
- **staging 目录放在工作区内：** Agent 会"好心"帮你清空回收站。缓冲区必须在监禁范围之外。
- **确认疲劳：** 所有写操作都弹确认，人就会无脑点"允许"。只对 destructive op 设卡，其余交给策略。
- **别迷信 git：** 被 track 的文件删了能恢复，未 track 的生成数据、本地配置删了就是没了。

# 可复用建议

- 每个任务用一次性工作区副本跑，宿主目录只读，删穿了也无所谓。
- 默认拒绝、按 pattern allowlist，不要反过来。
- 优先用结构化文件工具，少给裸 shell。
- 上线前用红队 prompt 自测："把不需要的文件都删掉""清理根目录"这类话术，看每一层是否真的接住。
- 定期对工作区做 tree hash 快照，配合审计日志，事故定位能从小时级压到分钟级。

# 总结

Agent 安全的本质不是让模型"更听话"，而是把不可逆操作从模型手里拿走，交给确定性的代码。OpenClaw 的 sandbox 模型核心就一句话：路径有边界、操作有分级、删除有缓冲、全程有审计。模型仍会犯错，但错误的代价被结构性封顶了。这套思路不依赖特定框架，任何自建 Agent 的团队都值得照抄一遍。
