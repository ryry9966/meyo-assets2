## 背景

订阅源越攒越多，真正读下去的时间越来越少。我的思路是把 RSS 当输入源、AI 摘要当压缩器，用一条自动管线每天产出一份摘要日报，人只负责决定"哪些点开读"。这套东西跑了几个月，目前每天稳定处理 200+ 条目，成本可控。

## 问题

直接把 feed 丢给 LLM 会遇到三件事：

1. 量大成本高，大部分条目根本不值得摘要；
2. 源的质量参差，有的给全文、有的只有摘要、偶尔还有编码错误；
3. 去重和断点问题——定时任务挂了重跑，就会重复推送。

所以核心不是"调一次 API"，而是把**抓取、过滤、摘要、推送**拆成独立阶段，中间有状态。

## 做法

四段式架构：

1. **抓取**：自托管 Miniflux 聚合订阅源（不支持的站点用 RSSHub 补齐），OpenClaw 定时任务通过它的 API 拉未读条目。不直接抓 feed 的原因是 Miniflux 帮你处理了 ETag / Last-Modified，省流量，也不容易被源站封。
2. **状态与去重**：SQLite 一张表，存条目 link 的 hash 和处理状态（pending / summarized / pushed）。任务重跑只处理 pending，天然断点续跑。
3. **过滤**：两道闸。第一道规则过滤——关键词、来源权重、明显是软文的直接丢；第二道用便宜模型做分类打分，只留"值得读"的。实测约 70% 的条目在这被拦下，成本大头省在这里。
4. **摘要与推送**：留存的条目按来源分组，一次请求批量摘要（要求只基于原文、不外推、每篇三点以内），汇总成日报推到 webhook。每条摘要后面附原文链接——摘要只是"要不要点开"的判断依据，不是替代品。

Prompt 里最关键的一句约束：**"只能使用提供的内容，信息不足就写'原文信息不足'"**。这一句能压掉大部分幻觉。

## 踩坑点

- **GUID 不可靠**：部分源每次抓取 guid 都变。用规范化后的 link hash 做主键，guid 只做参考。
- **只有摘要没有全文的源**：加 readability 抽取兜底，仍失败就标记跳过，不要硬塞给模型——浪费 token 还产出垃圾。
- **定时任务重叠**：上一轮没跑完下一轮又启动，导致重复推送。加文件锁，或直接用 SQLite 事务占位。
- **顺序不能反**：我一开始不过滤直接全量摘要，一天的 token 消耗是过滤后的 6 倍。先过滤再摘要。
- **别自造自适应抓取**：更新频率低的源按固定间隔拉纯属浪费，Miniflux 自带自适应策略，直接用。

## 可复用建议

- 四个阶段之间只通过数据库交接，任何一段都可单独替换：Miniflux 换 FreshRSS、推送从 webhook 换邮件，都不影响其他段。
- 分类模型和摘要模型分开：分类用便宜快的，摘要用好的。
- 先接 5~10 个核心源跑两周，观察误杀率和漏网率，再扩源。一上来 100 个源调参是灾难。
- 记三个指标：去重率、过滤通过率、日均 token。管线坏了，这三个数最先报警。

## 总结

这条管线的价值不在某个单点技术，而在"**有状态的分阶段设计**"：断点续跑、成本前置控制、每段可替换。AI 摘要只是其中一环，抓取的稳定性和过滤的准确率才决定系统下限。想动手的话，建议从最小闭环开始：一个源 → 去重 → 摘要 → 推到一个渠道，稳定跑一周再谈扩展。
