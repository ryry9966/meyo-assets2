## 背景

过去一年，项目级上下文的实践已经很成熟：AGENTS.md、CLAUDE.md、各类 MCP 资源，解决的都是"这个项目是什么、怎么构建、有什么约束"。但跨项目的"你是谁"始终没有安放处——换个会话，你就得重新交代一遍：我用 pnpm 不用 npm，回复用中文，别自动 push。

OpenClaw 的 workspace 机制天然适合放这类文件。既然有给项目写的 PROJECT.md，就该有一份给用户自己写的 USER.md。

## 问题

没有用户级上下文时，三个痛点反复出现：

1. **重复输入**：个人偏好在每个会话里口述一遍，成本高且容易漏。
2. **行为漂移**：同一个 Agent，今天简洁明天啰嗦，风格不可复现。
3. **错误默认值**：Agent 按通用假设行事——npm、英文回复、长篇解释——每次都要手动纠正。

这三件事本质是同一类问题：把本该静态化的上下文，放在了会话内的临时输入里。

## 做法

**第一步：建文件。** 在固定路径放一份 `USER.md`（建议 workspace 根目录），控制在 60 行以内，分四块：

```markdown
# 环境
- macOS + zsh，Node 用 fnm 管理
- 主力语言：TypeScript / Python

# 偏好
- 包管理器一律 pnpm，不要 npm/yarn
- 回复默认中文；代码示例带最小上下文，不超过 20 行
- 先给结论，再给推理过程

# 边界
- 不要自动 git push，不要动 .env
- 不确定我的意图时先问，不要猜

# 当前焦点
- xx 项目：在做导出插件（截至 2025-06）
```

**第二步：接入。** 最简单的方式是会话启动时把文件内容注入 system prompt；也可以封装成 MCP resource，让 Agent 按需读取，省 token。

**第三步：冷启动。** 让 Agent 帮你写初稿：提示它"面试我 10 个问题，然后生成 USER.md"。比自己从空白页开始快得多，而且问题本身会帮你暴露没意识到的偏好。

**第四步：版本化。** 进 git。偏好变更走 diff，你能清楚看到 Agent 的"人设"是怎么演化的。

## 踩坑点

- **写太长**。几百行的 USER.md 每次请求都在烧 token，关键指令还会被稀释。60 行是经验上限，超了就删。
- **信息过期**。三个月前的"当前焦点"会实打实误导 Agent 的建议方向。设个两周一次的 review。
- **写形容词不写行为**。"喜欢简洁的代码"没有操作性，"函数默认不超过 30 行"才能被执行。
- **放敏感信息**。这个文件会进每一次模型请求，API key、内网域名、客户名一律不要出现。
- **层级冲突**。项目配置说用 yarn、USER.md 说 pnpm，Agent 会随机选一个。定死优先级：项目级覆盖用户级。

## 可复用建议

- 在文件里留一个 `# Corrections` 区：每次你纠正 Agent，让它自己把修正追加进去，周度 review 后合并进正文。这是让 USER.md 持续贴近真实你的最低成本方式。
- 事实（环境、工具链）和偏好（风格、边界）分开写块，过期时好裁剪。
- 加一条自检指令："如果你的操作与 USER.md 冲突，先指出来再继续。"能拦截大部分静默违背。

## 总结

USER.md 的本质，是把"调教 Agent"从会话内的口头输入，变成一份版本化的静态资产。实现成本几乎为零——一个 markdown 文件加一行注入逻辑——换来的是所有会话的行为一致性。

建议这周就用 20 行写个最小版本跑起来，别追求一步到位。两周后 review 一次，你会很清楚该往里加什么、该删什么。
