## 背景

Agent 接上 MCP 和插件之后，能做的事从"聊天"变成了"动手"：读文件、调 API、写库、发消息。但很多团队对"哪些动作 Agent 可以直接干、哪些必须停下来问人"并没有清晰答案，往往靠 system prompt 里一句"注意安全"应付，出了事故才发现不够。

## 问题

两种典型翻车：

1. **问太多**。每个动作都要确认，人变成盖章机，自动化价值归零。更糟的是人会迅速疲劳，开始无脑点"同意"，确认机制形同虚设。
2. **干太多**。一条歧义指令下，Agent 把测试环境的清理脚本跑在了生产上，或者给全部客户群发了措辞错误的邮件。一次事故足以让团队直接关掉所有写权限。

本质问题是：**权限边界没有被显式建模**，散落在 prompt 语气和人的临场直觉里。

## 做法

用两个维度给动作分类：**可逆性**（能不能撤销）和**影响半径**（搞砸了波及多大）。

- 可逆 + 影响小 → 自动执行
- 不可逆 + 影响小 → 自动执行 + 告警
- 可逆 + 影响大 → 自动执行 + 留痕
- 不可逆 + 影响大 → 必须问人

落到工程上是四步：

1. **策略下沉到工具层**。在 MCP 网关或插件注册处给每个 tool 标注 `risk` 和 `reversible`，高风险动作强制走确认门，不依赖模型自觉。Prompt 会漂移，网关不会。
2. **不可逆动作必须有 dry-run**。发邮件、删数据、部署，先让 Agent 产出完整 payload 给人看 diff。人批准的应该是"这份内容"，而不是一句"继续吗"。
3. **给"问"这个动作定格式**。提问必须带上：做什么、为什么、diff/预览、回滚方案、超时后的安全侧默认行为。缺上下文的提问，等于把调查工作甩回给人。
4. **即使放行也设预算**。低风险动作按次数和时间窗限流，防止"每一步都合理、连起来是灾难"的循环调用。

## 踩坑点

- **确认疲劳是头号杀手**。实测一天弹出二十多次确认后，人的通过率接近 100% 且不再读内容。宁可收紧策略减少提问次数，也不要稀释每次提问的含金量。
- **可逆性会被链式动作破坏**。"关 PR 可逆"没问题，但若 CI 在 merge 后自动部署，"merge PR"就不可逆了。评估要看整条链，不看单步。
- **审计缺失比事故更糟**。谁批准的、何时、批准的是哪个版本，都要落日志。事后查"这封邮件谁让发的"却无记录，排查成本远超事故本身。
- **分清"需要人判断"和"需要人背锅"**。有些确认只是责任转移，对结果没有增益，这种应该砍掉。

## 可复用建议

- **从严起步，凭数据放松**：初期把灰区动作也设为"问"，同时记录"如果放行会怎样"。每周复盘日志，把连续安全的行为类别晋升为自动执行。边界是长出来的，不是一次画完的。
- **提问是稀缺资源**：每个确认点都应该值得人花 30 秒认真读。
- 策略代码化（网关配置），别写成 prompt 里的散文。

## 总结

权限边界不是"信任或不信任"的开关，而是可逆性 × 影响半径 × 上下文置信度的函数。可逆且影响小的交给 Agent 并留好日志；不可逆或影响大的强制过人，且让每一次"问"都带着 diff 和回滚方案。目标不是让 Agent 更胆小，而是让人的每一次介入都有价值。
