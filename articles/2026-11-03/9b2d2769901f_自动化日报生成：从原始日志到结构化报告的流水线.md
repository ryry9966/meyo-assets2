## 背景

团队里的“日报”通常是最容易被敷衍的环节：手写容易漏项，口径每个人不一样，忙起来干脆不写。而原始数据其实都在——git 提交、服务日志、任务流转、agent 自己的执行记录——缺的只是一条把它们串起来的流水线。OpenClaw 有定时触发、agent 编排、MCP 工具和插件推送，正好够拼一套“零手工日报”。

## 问题

最初的做法是让 agent 每天定时“读今天的日志，写一份日报”，跑了一周就暴露出四个问题：

1. **日志塞不进上下文**。一天几千行原始日志，截断后关键信息正好被切掉。
2. **数字会编**。模型把“约 200 条”写成“213 条”，看起来精确，其实是自己算的。
3. **格式漂移**。今天五个字段，明天变成四个，下游没法稳定消费。
4. **静默失败**。任务挂了日报也没人发现，三天后才被问“昨天的日报呢”。

## 做法

核心原则一句话：**确定性的活交给脚本，只有归类和措辞交给模型**。流水线分五步：

1. **采集**：定时任务触发，脚本拉取各来源日志（git、服务日志、任务系统），落到本地中间文件，不在 prompt 里现场拉。
2. **预处理**：脚本做去重、过滤 debug 级别、按模块聚合计数，输出固定 schema 的 JSON，并控制体积——每模块最多保留 20 条明细，其余只留计数。
3. **汇总**：agent 读中间文件生成摘要。prompt 里明确三条：只用给定数据；数字一律引用、不做心算；缺数据输出 unknown，禁止脑补。
4. **渲染**：模板引擎把结构化数据套进 Markdown 模板，模型只负责“一句话小结”这类措辞字段。
5. **推送与校验**：插件推送到群里；随后一个轻量脚本校验必填字段、抽查数字与中间文件是否一致，不一致就重跑或告警。

## 踩坑点

- **时间边界**。“一天”按 UTC 还是本地时区切，直接决定昨晚 23 点到今早之间的条目归哪天。统一在采集层打带时区的时间戳。
- **别让模型算数**。计数、百分比、环比全部由脚本算好放进中间文件，模型只做引用。
- **缺失策略没写清楚，模型就一定脑补**。unknown 必须是显式允许的输出。
- **定时重叠**。某次执行卡住超过间隔，下一轮又启动。加锁文件，或启动前检查上次运行状态。
- **失败不可见**。现在规定：失败也要推送一条错误摘要；另设独立检查，“连续 N 天没收到日报”就告警。
- **模板和 prompt 漂移**。改了模板忘了改 prompt，字段对不上。两者放同一目录一起版本化。

## 可复用建议

- LLM 的输入永远是脚本产出的小而干净的结构化文件，不要让它直接面对原始日志。
- 输出强制走固定 schema，渲染交给代码，模型不碰排版。
- 流水线本身也要可观测：记录每次运行的耗时、输入条数、校验结果。
- 上线前先跑一周“影子模式”：日报只发给自己核对，稳定后再推群。

## 总结

日报自动化省的不只是每天十分钟，而是把口径不一、漏项、延迟这些隐性成本固化成一条可校验的流水线。设计上只有一条主线：**让脚本管事实，让模型管表达，让校验兜底**。照这个思路拆，其他周期性汇报（周报、巡检报告）也基本是同一条流水线换个数据源。
