## 背景

过去半年我把 OpenClaw 接了一堆 MCP 工具：文件读写、Git、数据库查询、消息推送，还有几个内部系统的插件。Agent 能干的事越多，一个问题就越绕不过去：哪些动作它可以直接执行，哪些必须停下来问人？

## 问题

实践里两种失败模式都很常见：

- **什么都要问。** 每一步都弹确认，人很快疲劳，开始无脑点“允许”，审批形同虚设。
- **什么都不问。** 某次 Agent 判断“清理临时分支”合理，直接删了没人认领的远端分支——技术上没错，业务上炸了。

所以边界不是“多问”或“少问”的问题，而是要有一套可执行的判断标准，并且落在代码里，不是写在 system prompt 里靠模型自觉。

## 做法：四个维度 + 四层分级

判断一个动作该不该自动执行，我归纳成四个维度：

1. **可逆性**：能不能撤销？读操作天然可逆；发消息、写数据库要看有没有回滚手段。
2. **影响范围**：只影响本次会话，还是会波及其他用户、生产环境？
3. **成本**：执行错了，代价是重跑一次，还是数据丢失、资金损失？
4. **确定性**：输入到输出是否稳定？调一次天气 API 和“总结这批需求”是两回事。

据此分四层：

- **L0 直接执行**：只读查询、本地计算、dry-run。
- **L0.5 执行但留痕**：写日志文件、往测试环境发消息——自动执行，全部记入审计日志。
- **L1 汇总后确认**：低风险写操作攒一批，先给 diff/预览，人批一次，批量执行。
- **L2 逐笔确认 + 二次校验**：删数据、动生产、花钱的操作，单条确认，且确认信息必须带完整参数，不能只给一句“确认执行？”。

落地方式：在 MCP 工具层外面套一个 policy 层，每个工具声明自己的级别和所需审批，Agent 只能拿到“允许调用”的工具视图。审批走异步回调、带超时——超时默认拒绝，不是默认放行。

## 踩坑点

- **审批疲劳**：确认弹得太频繁，人就成了 yes machine。解法是把 L1 做成批量预览，把确认次数压下来。
- **问得太晚**：Agent 已经执行了前半段副作用才来问。要求“需审批的工具在调用前阻塞”，而不是事后补救。
- **权限写进 prompt**：改策略要发版，模型还会在长上下文里“忘记”。策略必须在网关/代码层强制。
- **超时语义没定义**：人会离开电脑。挂起的 Agent 要明确走“拒绝 + 说明原因 + 降级路径”，不能傻等。
- **没有审计日志**：出了事无法复盘“当时谁批的、批的时候看到了什么”。

## 可复用建议

- 写操作默认拒绝、白名单放行，不要反过来。
- 确认界面给 diff 和参数全文，让人**基于信息决策**，不是基于信任决策。
- 高危操作强制先跑 dry-run，把结果贴进确认信息。
- 策略配置进版本库，权限变更走 review。
- 每月回看一次审计日志：哪些 L2 从没出过事，考虑降级；哪些 L0 出过事，升级。

## 总结

权限边界本质上是在买保险：问人是为了兜底不可逆的错误，但每次询问都有人力成本。判断标准（可逆、范围、成本、确定性）+ 分层执行 + 代码层强制 + 审计回看，这套组合比“相信模型”或“全程人肉”都便宜。宁可第一版偏保守，跑出数据再放宽——先放飞再收权，成本高得多。
