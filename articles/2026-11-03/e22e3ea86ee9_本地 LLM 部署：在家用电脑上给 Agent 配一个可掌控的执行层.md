## 背景

过去一年，我把一部分 Agent 日常负载（文档整理、日志摘要、MCP 工具链里的低风险环节）从云端 API 逐步挪到了自己的台式机上。动机很朴素：数据不出门、成本固定、断网也能跑。结论先放在前面：可行，但必须按“跑 Agent”而不是“跑聊天”的思路来规划。

## 问题

本地模型与云端的差距，主要不在智商，而在工程约束：

- 显存预算直接决定模型上限，家用机没有弹性扩容；
- Agent 循环依赖工具调用和稳定的 JSON 输出，量化太狠的模型会在这里先崩；
- 长上下文的 KV cache 会吃掉你预估之外的显存，多轮对话越跑越慢。

## 做法

**1. 盘点硬件。** Q4 量化下的经验值：7B 约需 6GB 显存，14B 约 10GB，32B 约 20GB 起步。MoE 结构（如 30B-A3B 这类激活参数小的）对显存友好，16GB 显存 + 32GB 内存就能跑到可用的速度。显存不够时优先看内存带宽，别硬上大模型。

**2. 选运行时。** 图省事用 Ollama，要细粒度控制用 llama.cpp，Linux + N 卡且追求吞吐再考虑 vLLM。家用场景下，Ollama 的 OpenAI 兼容端点（`/v1`）足够对接绝大多数 Agent 框架。

**3. 选模型。** 中文能力 + 工具调用是硬指标，Qwen 系列在这个尺寸段比较稳。下载前先确认该模型明确支持 tool use，不要事后靠 prompt 硬凑。

**4. 接入 Agent。** 把 base_url 指向本地端点，关键是显式设置上下文长度和并发参数，然后先跑通一个最简的 MCP 工具调用闭环，再谈其他。

**5. 压测。** 用自己的 Agent 记录 tokens/s 和工具调用成功率，跑 20 个真实轮次，比看任何榜单都可靠。

## 踩坑点

- **上下文截断**：Ollama 的 `num_ctx` 默认值很小，Agent 多轮之后系统提示被悄悄裁掉，表现为“模型突然忘了工具”。第一件事就是把它设到 8k–16k，同时确认 KV cache 装得下。
- **量化档位**：Q4 是底线。Q3 以下经常输出畸形 JSON，工具解析直接失败。宁可换小一号的模型，也别用更狠的量化。
- **并发抢占**：本地跑 Agent 时，浏览器、IDE 的后台请求会抢显存；`OLLAMA_NUM_PARALLEL` 调大后显存近似翻倍，家用机建议保持 1–2。
- **聊天模板**：部分模型的 chat template 对工具调用支持不全，模型会把工具参数写进正文。换官方带 tool 支持的版本，别自己手改模板。

## 可复用建议

- **路由模式**：本地小模型做粗活（分类、摘要、格式校验），难任务仍走云端。这比“全本地”务实得多，成本与质量的平衡点也更容易守住。
- **精简工具描述**：本地模型上下文窗口小，每个 MCP 工具的 schema 都是实打实的 prompt 开销，能砍则砍。
- **固定模型版本**：记录模型 hash，否则一次 pull 更新就可能悄悄改变 Agent 行为，事后排查极其痛苦。

## 总结

本地部署的意义不是替代云端，而是给 Agent 架构增加一层可自主掌控、可离线运行的执行能力。建议的路径是：用现有硬件先跑通工具调用闭环，验证真实负载下的成功率，再逐步升级模型和显存。先闭环，再加码。
