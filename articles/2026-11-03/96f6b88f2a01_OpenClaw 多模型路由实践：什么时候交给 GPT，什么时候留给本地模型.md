## 背景

OpenClaw 的 agent 流程里，几乎每一步都在消耗 token：理解任务、拆解规划、调用 MCP 工具、整理结果。我们早期图省事全程走云端大模型，结果一天几十万 token 的自动化流水线，账单和敏感日志出域的风险两头受压。后来又试过全切本地，agent 的工具调用成功率立刻掉下来。结论很直接：路由不是二选一，而是按任务分层。

## 问题

观察下来主要有两类失败：

1. 本地小模型（7B 级）做 MCP 工具调用时，参数 JSON 拼错、函数名幻觉，插件直接报错；
2. 云端模型处理含客户数据的日志时，数据已经出了内网，合规上过不去。

同时还有成本问题：摘要、格式化、简单抽取这类活，用强模型纯属浪费。

## 做法

我们收敛成一个三层模型梯队，路由规则集中在 OpenClaw 的模型配置层，不散落在各插件 prompt 里：

```yaml
routing:
  rules:
    - match: contains_sensitive_data   # 硬规则，强制本地
      model: local/qwen-14b
    - match: needs_tool_call_or_plan   # 规划与复杂工具调用
      model: cloud/gpt-4.1
    - default:
      model: local/qwen-7b             # 摘要/抽取/格式化
  fallback:
    local_failure: cloud/gpt-4.1-mini
```

落地步骤：

1. **先跑基线**：准备 20~50 条代表性任务，分别用云端和本地跑一遍，统计 tool-call 成功率、格式合规率、耗时、单条成本，拿数据定分层线；
2. **粗粒度路由**：只做三层，敏感数据→本地、需要规划/工具调用→云端、其余→本地默认档；
3. **加校验和降级**：本地模型输出先过 schema 校验，失败自动重试一次，再失败降级到云端并记录日志；
4. **每周看一次降级率**：降级率持续偏高说明分层线画错了，调整而不是加规则。

## 踩坑点

- **tool call 兼容性**：本地模型爱输出单引号 JSON 或自创函数名，必须做 schema 校验，别指望 prompt 约束能兜住；
- **上下文窗口差异**：云端 128k，本地可能只有 8k~32k，路由到本地前先裁剪，保留 system、最近轮次和工具结果摘要，否则丢指令很隐蔽；
- **参数漂移**：temperature、top_p 在不同 provider 间要保持一致，否则同一路由策略表现忽好忽坏，排查半天发现是参数没对齐；
- **首 token 快 ≠ 总耗时短**：本地模型出字快但整体可能更慢，交互式任务和批处理要分开评估，别用同一个体感下结论；
- **别把路由做细**：按关键词分到五六种模型，维护成本很快超过收益，三层够了。

## 可复用建议

- 三层梯队 + 一条降级链路，是性价比最高的起步方案，先跑起来再优化；
- 敏感数据路由做成硬规则，而不是写进提示词求模型自觉；
- 每次更换本地模型版本，重跑同一套评测集，防止回归；
- 把每次路由决策和降级事件落日志，一周后的数据比任何直觉都可靠。

## 总结

多模型路由的本质，是承认模型能力不均匀：云端买准确率和长上下文，本地买隐私、成本和数据不出域。把决策点收敛到 OpenClaw 的统一路由层，用评测数据而不是感觉来调分层线，自动化流水线才能同时稳得住质量和账单。这套三层方案在我们环境里跑了一个多月，tool-call 成功率回到云端单模型的水平，token 成本降了约六成，供参考。
