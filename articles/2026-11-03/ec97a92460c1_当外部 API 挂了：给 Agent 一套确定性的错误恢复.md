## 背景

Agent 的能力边界，基本等于它调得动的工具边界。OpenClaw 插件、MCP server、各类 HTTP API——外部依赖越多，故障面越大。本地代码挂了能立刻修，第三方 API 挂了只能等。生产环境里 agent 的多数"抽风"其实不是模型问题，而是某次工具调用失败后，整个执行流失去了秩序。

## 问题：Agent 不会"体面地失败"

裸跑的 agent loop 遇到工具报错，常见三种结局：

1. 原始堆栈直接喂回模型，模型开始道歉、猜测，最后编一个看似合理的结果；
2. 无限重试，token 和配额一起烧光；
3. 静默返回空数据，下游照常执行，产出一份"看起来完整、实际全错"的报告。

这三种都比直接失败更糟——错误被藏起来了。

## 做法：把临场发挥变成确定性策略

**1. 统一 adapter。** 所有工具出口收敛到一层：强制超时（如 10s）、统一错误分类，只分三类——可重试（超时、429、502/503）、不可重试（401/404、参数错）、语义错误（HTTP 200 但 body 里 `success=false`，不少 API 就这么干，别漏）。

**2. 有界重试 + 退避。** 可重试错误最多 3 次，指数退避加抖动（1s/2s/4s ± random）。jitter 是为了避免多个会话同时被限流、又同时恢复，形成同步重试风暴。

**3. 熔断。** 同一工具在滑动窗口内连续失败 5 次，标记为 unhealthy，冷却 60s 内直接走降级路径，不再发请求。这保护的不只是那个 API，还有你的 token 预算。

**4. 显式降级。** 每个工具预先声明策略，四选一：返回带时间戳的缓存并标注"可能过期"；切换备用源；跳过该步骤并在最终回复中明说；交还用户决策。

**5. 结构化上报。** 失败也 return 约定好的结构，例如 `{"status":"tool_error","error_class":"rate_limit","retryable":false}`。模型看得见失败，但选择被策略收窄，不会自由发挥。

## 踩坑点

- **非幂等操作别自动重试。** 下单、支付类 POST 重试可能重复扣款，要么服务端支持幂等键，要么重试次数设 0，失败即交还用户。
- **200 不等于成功。** 只看 HTTP 状态码的 wrapper，会在语义错误面前全部漏判。
- **降级数据不标注新鲜度。** 用户拿两小时前的天气缓存当实时数据，比"查询失败"伤害更大。
- **熔断恢复太急。** 冷却一结束就放全量流量，对方没恢复又被打回熔断。建议半开：先放一两个探测请求。
- **混淆"工具失败"和"任务失败"。** 一次搜索挂了不代表整个任务失败，让 agent 分清这两者，行为会稳很多。

## 可复用建议

- 错误分类、重试、熔断做成公共库，所有插件复用，别各写一套；
- 用故障注入做测试：mock 出 429、500、慢响应，验证降级路径真的会被走到——很多降级逻辑上线后从没执行过；
- 日志记下 tool 名、错误类、重试次数、是否降级，排查时这就是你的时间线；
- 错误类别保持少而稳，3~5 个足够，类别越多模型越容易选错。

## 总结

外部 API 一定会挂，区别只是频率和时长。好的 agent 系统不是假设依赖永远可用，而是把"挂了之后发生什么"写成确定性代码：分类、重试、熔断、显式降级、结构化上报。模型负责决策，韧性交给工程。当第三方 API 凌晨超时，你的 agent 平静地回复"数据源暂不可用，已用缓存替代"——那一刻你会感谢下午写的那五十行 wrapper。
