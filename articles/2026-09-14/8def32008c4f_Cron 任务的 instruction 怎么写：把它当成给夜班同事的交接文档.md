## 背景

OpenClaw 里 cron 是最低调也最容易写砸的功能。它看起来只是"定时发一条消息给 agent"，很多人顺手把聊天时的 prompt 粘进去，结果发现：要么每天输出东拼西凑，要么静默失败，要么同一份摘要投递了两遍。

根因在于：cron 的 payload 是一条**无会话上下文、无人在环**的消息。你在聊天里能靠追问纠正的事，在 cron 里都没有第二次机会。

## 三个核心差异

写聊天 prompt 和写 cron instruction 的本质区别有三个：

1. **无上下文**：cron 触发时 agent 通常在一个干净的会话里，"继续昨天的""按上次的格式"这类指代全部失效。
2. **无确认**：跑完直接投递，没有你中途说"不对，重来"。输出契约必须在 instruction 里一次定死。
3. **无值守**：失败不吵你。数据拿不到、工具报错、格式漂移，都会静默发生。

所以我的结论是：**把 cron instruction 当成交接文档写，而不是当开场白写。**

## 做法：一个可复用的骨架

我目前稳定跑着十几个定时任务，instruction 基本收敛到这个结构：

```text
【任务】每天 09:00 汇总仓库昨日动态
【时间】执行时间为 {now}；统计区间 = 前一个自然日（本地时区）
【输入】只读取 ~/notes/daily/ 下对应日期的文件，不要浏览其他目录
【输出】投递到 #daily 频道，格式固定：
  1. 变更摘要（≤5 条）
  2. 风险点（≤2 条）
  3. 无内容的小节直接省略
【异常】找不到数据或工具失败时，只发一行"今日无更新"，不要推测、不要编造
【边界】全程只读，不执行写入/删除/外发操作
```

逐条说下为什么这么写：

- **显式注入时间**。别指望模型知道今天是几号。凡是带"今天/昨天/本周"的任务，时区和统计区间都要写清楚，宁可啰嗦。
- **锁输入源**。限定目录和文件名模式，防止 agent 自由发挥去别处找数据。
- **输出即契约**。下游要么是人看的频道，要么是被脚本解析的消息，格式必须可预测，条数上限也是契约的一部分。
- **失败分支显式定义**。明确"失败时发什么"，否则模型可能编一份看起来像真的摘要。
- **最小权限**。定时任务不需要写能力就不给，这是底线。

## 踩坑点

- **时区**：服务器多半是 UTC，cron 表达式写 `0 9 * * *` 实际是北京时间 17 点。调度时间要和 instruction 里的"自然日"对齐到同一时区。
- **重跑与幂等**：调试时手动触发的运行和定时触发撞车，会出现重复投递。任务设计上让重复执行无害——相同输入产出相同摘要，投递前判断当天是否已发。
- **频率迷信**：别用 cron 解决轮询问题。15 分钟跑一次"看看有没有新东西"，大部分时间在烧 token，事件驱动场景应该交给 webhook。
- **指令漂移**：instruction 改了三版之后，没人记得线上跑的是哪一版。cron 配置进 git，改 instruction 走 commit，和改代码一个待遇。

## 可复用建议

- 写新任务前先回答四个问题：谁触发、输入在哪、输出去哪、失败什么样。答不全就先别上线。
- 上线前手动触发两三次，并故意断掉数据源，验证失败分支真的生效。
- 每个 cron 只做一件事。想"顺便再汇总一下 XX"的时候，新建一个任务。
- 每月扫一遍任务列表，删掉没人看的投递。定时任务最大的成本不是 token，是没人阅读还在跑。

## 总结

Cron 的 instruction 不是 prompt 技巧问题，是任务契约问题。把无上下文、无确认、无值守这三个约束当成设计前提，用交接文档的标准去写——时间自足、输入收敛、输出固定、失败显式、权限最小——定时任务就能从"玄学抽卡"变成可信的基础设施。
