## 背景

Agent 的能力边界，基本等于它调得动的外部 API：搜索、数据库、MCP 工具、第三方模型服务……任何一个抖动，整条自动化链路就可能停摆。传统后端容错谈了很多年，但 Agent 场景多了个新变量：**失败信号会进入模型上下文，被 LLM 消化后再输出**。错误处理写得烂，Agent 不但不恢复，还会放大混乱。

## 问题：Agent 的挂法不太一样

实际跑 OpenClaw / MCP 工作流时，API 故障常演变成三种事故：

1. **无限重试**：插件层没设上限，429 或超时后死循环，一晚烧光配额。
2. **幻觉兜底**：工具返回报错文本，模型不承认失败，自己编一份“合理”结果交差，用户毫无察觉。
3. **上下文污染**：几 KB 的堆栈原样塞进对话，后续推理质量明显下降。

核心矛盾在于：重试策略本该由代码决定，很多实现却交给模型自由发挥——要么秒放弃，要么死磕到底。

## 做法：四层防线

**第一层：先分类，再重试。** 429/503/超时/网络错误可重试；401/400/404 重试无意义。非幂等写操作（下单、发消息）必须带幂等键，否则会重复发送、重复扣款。

**第二层：有界退避重试。** 指数退避加随机抖动，上限 3 次左右，尊重 `Retry-After` 头。所有外部调用强制设连接 + 读取双超时，不允许无限等待。

**第三层：熔断。** 连续失败超过阈值就打开熔断器，冷却期内快速失败——Agent 拿到的是毫秒级“服务不可用”，而不是挂着 30 秒超时。冷却结束进半开状态探测恢复。

**第四层：结构化降级。** 给模型的工具错误要结构化：错误码、是否可重试、建议动作，而不是原始堆栈。同时准备降级路径：备用数据源、带时间戳的缓存旧值，或者直接说“该数据源暂时不可用”。最后这条最重要——永远给 Agent 留一条诚实认输的路。

## 踩坑点

- **退避不加抖动**：多个 Agent 实例同时恢复，打出同步洪峰，把刚喘过气的 API 再打挂。
- **报错混进缓存**：缓存层没区分成功与失败响应，故障期间存下的 502 被反复回放。
- **降级数据不标新鲜度**：用户拿到三小时前的缓存，却以为是实时数据。
- **熔断阈值太敏感**：一两次抖动就跳闸，反复开关（flapping），比不熔断还吵。
- **在 prompt 里写“失败就重试 N 次”**：模型对次数和时机的执行不可靠，确定性逻辑请留在代码里。

## 可复用建议

- 外部调用收敛到统一的弹性封装层，超时、重试、熔断、结构化错误集中管理。
- 定一个工具错误标准 schema：`{ok, error_code, retryable, hint}`，MCP 工具和插件全部对齐。
- 写操作一律带幂等键；读操作允许返回“最后成功值 + 时间戳”。
- 监控至少覆盖工具调用错误率、P99 延迟、熔断器开合事件——错误率突变往往比用户投诉早半小时。
- prompt 只声明意图与底线（如“工具失败时如实告知用户，禁止编造”），策略交给代码。

## 总结

Agent 的错误恢复不是 prompt 工程，是系统设计。重试、熔断、降级这些老朋友在 Agent 场景不仅没过时，反而更关键——因为模型会把糟糕的失败处理放大成更糟糕的输出。把确定性逻辑放回代码，把结构化信号交给模型，并永远保留“如实说我办不到”这条路。这比任何花哨的自动恢复都可靠。
