## 背景

单 agent 跑复杂任务一段时间后，基本都会撞上同样的天花板：主上下文被工具输出塞满，后面每一步的决策质量都在下降；任务之间明明没有依赖，却只能排队串行执行。OpenClaw 的 agent 支持派生 subagent，这给了编排的空间——但“能派生”和“编排得好”之间差了不少工程细节。这篇记录我们实际跑并行 subagent 的做法。

## 问题

拆开看是三个具体问题：

1. **上下文污染**：子任务的大量中间输出（网页抓取结果、长日志、代码搜索命中）直接灌进主对话，真正重要的结论反而被稀释。
2. **串行等待**：比如“调研三个竞品的定价 + 整理本地数据 + 生成报告骨架”，前两个互不依赖，串行跑就是纯浪费时间。
3. **职责不清**：一个 agent 同时负责拆解、执行、汇总，system prompt 越补越长，改一处动全身。

## 做法

我们的编排结构比较朴素，四步：

1. **切分任务，先看依赖再看并行**。信息收集类任务（抓数据、查文档、扫描代码）通常彼此独立，适合 fan-out；分析和汇总类依赖上游产出，保持串行。
2. **定义产出契约**。每个 subagent 必须返回固定结构：结论、关键数据、失败原因（显式字段，不允许静默成功）。原始产物不进对话，落盘到 workspace 文件，摘要里只带文件引用。
3. **受控并发**。并发上限设 3–5，每个 subagent 带超时和一次重试，超限任务排队，而不是无脑全量并行。
4. **主 agent 只做汇总**。读各 subagent 的摘要和文件引用，校验失败字段，做最后的合并与决策。主上下文保持“瘦”。

## 踩坑点

- **并发写冲突**：两个 subagent 同时改同一个文件，后写的覆盖先写的。切分时按资源边界走，写操作收敛回主 agent，或者加文件锁。
- **过度隔离**：subagent 缺关键背景，产出方向跑偏。派发时显式传入必要前提（路径、约束、格式要求），别指望它自己猜。
- **静默失败**：subagent 报错后编了个“看起来合理”的答案。产出契约里的 failure 字段是必须校验的，不是摆设。
- **成本翻倍**：并行是乘法，token 消耗直接 ×N。限制 subagent 的工具集和最大轮数，砍掉不必要的 MCP 工具暴露。
- **聚合丢信息**：只看摘要会漏细节，关键原始数据务必先落盘再汇总。

## 可复用建议

- 按**数据边界**切 subagent，而不是按工具切——同一数据源的操作放在一起，天然避免写冲突。
- 把 subagent 当**无状态工人**用：派发信息完整、产出结构化、任务幂等可重试。
- 先串行跑通，再并行化。串行能跑对，并行出问题时才好定位是编排的锅还是任务本身的锅。
- 给每个 subagent 打 trace 标识，日志能串起来排查，否则出了问题只能靠猜。

## 总结

并行买的是延迟，付的是协调复杂度。subagent 编排的核心不是“开得多”，而是产出契约、并发上限、主 agent 保持精简这三件事。先让串行正确，再让并行可控，编排才真正稳定。
