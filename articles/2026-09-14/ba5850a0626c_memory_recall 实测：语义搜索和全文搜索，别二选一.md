## 背景

给 OpenClaw 上的 agent 挂了长期记忆之后，`memory_recall` 基本决定了它"像不像记得你"。常见的两条实现路线：把记忆切片向量化后做**语义搜索**，或者走传统**全文检索**（BM25 / SQLite FTS5）。我们在一个日常助理 agent 上把两条路并行跑了两周，结论先放前面：各有明确的失败场景，生产上建议混合，别站队。

## 问题：两种方案各输在一个真实场景上

- **语义搜索输的场景**：问"上次 ECONNRESET 那个报错最后怎么处理的"，向量检索返回一堆"网络不稳定、超时重试"的泛化笔记，偏偏漏掉了含这个 token 的那条。embedding 会把精确的标识符、错误码、数字"抹平"，这在工程记忆里是致命的。
- **全文搜索输的场景**：问"上次聊的部署老卡住的破事"，关键词和原文（"流水线阻塞"）一个都对不上，BM25 直接空手而归。用户回忆往事时几乎不会用原文措辞。

## 做法

1. **统一切片入库**：300–500 token 一片，附带时间戳、来源、tags 元数据。
2. **双路索引**：SQLite FTS5 做 BM25，sqlite-vec 做向量，同一条记忆两份索引，写入时同步更新。
3. **双路召回 + RRF 融合**：`memory_recall` 同时跑两路，各取 top-5，用倒数排名融合（RRF）合并后取 top-8。
4. **轻量路由加权**：查询里出现引号、大驼峰、错误码样式字符串时，给 BM25 侧加权。
5. **每周抽查**：从 recall 日志里抽 20 条人工看命中率，记进表格。

## 踩坑点

- **FTS5 默认分词器不切中文**，整段当一个大 token，中文全文检索形同虚设。必须换 trigram/ngram 或外挂分词，这是我们踩得最狠的一个坑。
- **中英混排的 embedding 选型要单独测**：不少通用模型对"中文描述 + 英文报错码"这种混合文本召回很差，选型时专门构造了一组错误码查询来测。
- **纯相似度有时间偏见**：一年前措辞相似的旧笔记会排到前面，加了时间衰减项才稳定下来。
- **RRF 别用 1:1 起步**：关键词噪声多的语料里，先压低 BM25 权重，观察日志再逐步放开。

## 可复用建议

- 混合检索当默认方案，纯向量只当 baseline 对照，不直接上生产。
- recall 结果把**分数和来源**一并返回给 agent，出现坏召回时能快速定位是哪一路的锅。
- 固定一个 30~50 条的"query → 期望命中的记忆 id"回归集，改索引参数、换 embedding 模型就在 CI 里跑一遍，比吵理论有用得多。

## 总结

语义搜索解决"换个说法也能找到"，全文搜索解决"精确 token 必须找到"——agent 的记忆召回两种查询都会遇到。双路索引 + RRF 融合 + 元数据过滤，用很小的工程代价覆盖了绝大多数场景。真正的关键不是选哪条路线，而是先建一个能跑的回归集，让命中率数据替你做决定。
