# 背景

OpenClaw 的 agent 默认走一个主模型，但接上 MCP 工具和插件之后，工作流里的任务其实差别很大：有的需要长上下文推理和多轮工具编排，有的只是把 JSON 归一化。全走云端 API，账单和数据隐私都难受；全换本地模型，复杂任务的成功率肉眼可见地往下掉。多模型路由要解决的就是一个问题：哪个活交给哪个模型。

# 问题

以我们一个典型的自动化工作流为例，任务构成大致是：入口消息解析、工具编排规划、网页/文档摘要、结果格式化输出。实测数据：

- 全部用云端主力模型时，单任务成本里 60% 以上花在摘要、格式化这类"低难度、高频率"环节；
- 全部换成 Qwen2.5-14B（Ollama）后，摘要环节没有问题，但多步工具编排的失败率从约 3% 涨到 20% 以上，主要挂在参数幻觉和长上下文截断上。

结论很直接：两端都不对，需要按任务路由。

# 做法

**1. 任务分级。** 按两个维度打标：失败代价（能否重试、是否写外部状态）和难度（输入长度、是否多轮工具调用）。得到一张简单路由表：

- 规划/编排、跨多个 MCP 工具的任务 → 云端主力模型
- 摘要、分类、实体抽取、格式转换 → 本地模型
- Embedding → 固定用一个模型，不参与路由

**2. 配置主备链。** OpenClaw 的模型配置支持 primary + fallbacks，路由不是二选一，而是"本地优先、云端兜底"（或反过来），可以按 agent 粒度覆盖（字段名以你本地版本为准）：

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "ollama/qwen2.5:14b",
        "fallbacks": ["openai/gpt-4o"]
      }
    }
  }
}
```

编排类 agent 单独覆盖配置，primary 直接指向云端。

**3. 显式路由旁路任务。** 摘要这类旁路环节不走主对话模型，而是在 skill/插件调用里直接指定模型参数。好处有两个：主 agent 的上下文不被旁路任务污染，旁路成本也单独可控。

最后上监控：记录每次调用的 model、耗时、token 数、是否触发 fallback。跑一周后按数据回头调路由表，比拍脑袋准得多。

# 踩坑点

- **上下文截断**：本地模型窗口普遍 8k–32k，长文档塞进去直接截断，工具调用 JSON 缺字段。路由条件里必须包含输入长度，不只是任务类型。
- **function calling 参差**：同一模型不同量化版本表现差异很大，14B 的 q4 量化参数幻觉明显多于 q8。选模型别只看名字，要看量化。
- **fallback 是静默的**：本地挂了自动切云端，质量回升了，但没人知道本地坏了。一定要给 fallback 事件加告警。
- **本地并发排队**：Ollama 默认串行，agent 并行跑三个子任务时会排队，表现为"莫名变慢"。`num_parallel` 需要显式调。
- **别混池**：embedding 模型和对话模型不要放进同一个路由池，调用协议和评测口径完全不同。

# 可复用建议

- 路由表用配置文件管理，不写死在代码里，方便灰度和回滚。
- 新模型上线先只接旁路任务，攒两周数据再考虑进关键路径。
- 关键路径永远保留云端兜底——本地只做降本，不做替代，除非你的场景能接受失败重试。
- 成本口径统一成"每千次工作流"，而不是"每 token"，不同路由策略才有可比性。

# 总结

多模型路由的目标不是"全部本地化"，而是把不同失败代价的任务分给不同成本档的模型。OpenClaw 的 primary/fallback 机制加上一张任务分级路由表，一个下午就能搭起来；真正的工作量在监控和持续迭代。先跑数据，再调策略，别信任何"一个模型打天下"的方案。
