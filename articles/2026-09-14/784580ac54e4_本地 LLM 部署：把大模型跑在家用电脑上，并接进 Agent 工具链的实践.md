## 背景

做 Agent / MCP 自动化的同学大多遇到过这样的场景：工具链里要过一遍用户隐私数据（聊天记录、本地文件、浏览器历史），全走云端 API 心里不踏实；或者批量跑任务，token 费用肉眼可见地涨。本地部署的价值就在这里——数据不出门、没有按量计费、断网也能跑。但本地模型和云端旗舰的能力差距，在多步 agent 任务里会被放大，这正好是本文要处理的核心矛盾。

## 问题

把本地模型直接接到 MCP / 插件链路上，常见几个坑：

1. **工具调用支持参差不齐**：不是所有开源模型都能稳定输出合法的 function call 格式；
2. **默认上下文窗口太小**：工具描述 + 多轮对话一上来就截断；
3. **显存预算和量化等级的取舍**：选错一步，速度或质量崩掉一边。

## 做法

**第一步：盘点硬件。** 显存决定上限，经验值：7B 模型 Q4 量化约占 5–6GB 显存，14B 约 9–10GB，32B 需要 20GB+，不够就会 offload 到内存，速度掉一个数量级。

**第二步：选运行时。** Ollama 上手最快，llama.cpp 灵活可控，显存充裕且要并发选 vLLM。OpenClaw 这类 agent 框架只要一个 OpenAI 兼容端点，以上三家都提供，把 `base_url` 指过去即可。

**第三步：选模型。** 优先选官方明确支持 tool use 且中文能力好的 instruct 版本（Qwen 系列是稳妥起点）；量化从 Q4_K_M 起步，别低于 Q4。

**第四步：调参数。** Ollama 默认 `num_ctx=2048`，agent 场景务必手动开到 8k–16k（显存允许就更大）。Embedding 模型单独跑，它很小，CPU 都够，别和主模型共用一套选型逻辑。

## 踩坑点

- **"模型忘了系统提示"**：九成是 `num_ctx` 没改，长工具描述把上下文吃穿了；
- **7B 级模型跑多步任务经常格式错乱、幻觉参数**，Q4 量化会加剧，工具调用场景建议至少 14B；
- **速度突然变慢**：先查日志确认是否发生了内存 offload，再怪模型；
- **并发请求排队**：本地单卡基本串行，agent 并行调工具时把超时调大。

## 可复用建议

1. **混合路由最务实**：隐私敏感和批量任务走本地，复杂推理走云端，写一层简单 router 按 task 类型分发，别硬扛；
2. **用自己的真实 agent 任务做评测**：通用榜单分数高不代表能稳定吐出合法的 tool call JSON；
3. **固化一键启动脚本**：模型拉取、`num_ctx`、端点配置写成 compose 或 shell 脚本，换机器五分钟复现。

## 总结

本地 LLM 不是云端的替代品，而是 agent 工具箱里的一档选择。门槛已经降到一张 16GB 显存的消费级显卡，真正的工作量在于接进 MCP / 插件链路后把它调稳。推荐的路径是：先用小模型打通全链路，再逐步加大模型规模和上下文窗口——这是试错成本最低的走法。欢迎在社区里贴出你的硬件配置和实测 token 速度，攒一份真实的机型对照表。
