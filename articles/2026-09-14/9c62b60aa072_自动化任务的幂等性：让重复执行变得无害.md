## 背景

在 OpenClaw 这类 agent 环境里，"只执行一次"是幻觉。定时任务可能和上一轮运行重叠；webhook 会被上游重发；agent 调用工具失败后自动重试；你自己调试时也会手动再跑一遍。执行次数不可控，是自动化的常态而非异常。

幂等性解决的就是这件事：**同一个任务执行一次和执行多次，最终效果一致。**

## 问题出在哪

把操作分成两类就清楚了：

- **天然幂等**：把状态设为某个值、按 key upsert、覆盖写。重复执行只是浪费点算力。
- **天然不幂等**：追加一条消息、计数加一、创建一张工单、调用发送类 API。重复执行就是事故。

大部分自动化事故，是第二类被当成了第一类处理。典型场景：skill 里"给群发一条日报"，网络超时后框架重试，群里出现两条日报。

## 做法

1. **给任务定一个幂等键**。用业务语义构造，不要用随机数：比如 `日报-2024-06-01`。同一个逻辑任务，无论被谁、被重试多少次触发，键相同。
2. **执行前查键，执行后写键**。用可靠存储（SQLite、Redis、带锁的 JSON 文件）记录"这个键已做过"，存在就跳过。
3. **写路径改成"按 key 写"**。能 upsert 就不 insert，能 set 就不 append，数据库层面用唯一约束兜底。
4. **外部 API 优先用它自带的幂等机制**。不少 API 支持幂等键参数或请求头，直接透传，把去重责任交给服务端。
5. **用状态机替代直接执行**。任务状态走 `pending → running → done`，重试时先看状态：`done` 跳过；`running` 且超时才重新捡起。

## 踩坑点

- **先查后写有竞态**。两个并发实例同时查到"没做过"，然后都执行。去重判断必须原子：`SETNX`、捕获唯一索引冲突，而不是"查一下再写"。
- **随机幂等键是最常见的 bug**。把生成 UUID 的代码写进了重试循环，每次重试都是新键，去重完全失效。键必须在重试之间保持稳定。
- **副作用成功、记录失败**。消息发出去了，写键那一步挂了，重试照样重复。无法和副作用放同一个事务时，至少先写 `running` 再执行，缩小窗口并配对账逻辑。
- **别依赖 agent 输出做去重**。LLM 每次措辞不同，靠内容相似度判断"是不是同一个任务"很不可靠。去重要锚定结构化 ID（任务 ID、事件 ID、日期），在触发时显式传入。
- **cron 重叠**。长任务赶上下一轮调度。跑之前检查上一轮状态，或加文件锁/分布式锁。

## 可复用建议

- 把"幂等键是什么、存在哪"写进每个 skill/插件的说明，当成接口契约的一部分。
- 在插件框架层做统一的去重包装器：接 key、自动查、自动记、带 TTL，业务代码不必各写一遍。
- 日志里永远带幂等键，排查"为什么执行了两次"时这是唯一线索。
- 按"至少一次投递 + 消费端去重"设计，不要追求"恰好一次"——后者在分布式环境里基本是错觉。

## 总结

幂等性不是阻止重试，而是让重试变得无害。在 agent 自动化里，调度器、webhook、人工触发、模型自主重试都可能让同一逻辑跑多次，重复执行是常态。给每个有副作用的任务一个稳定的幂等键，用原子方式查和写，剩下的交给状态机。做到这些，你的自动化才敢真正放手，让它半夜自己跑。
