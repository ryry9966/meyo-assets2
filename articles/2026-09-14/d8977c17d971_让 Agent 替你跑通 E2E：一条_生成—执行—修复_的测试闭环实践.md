## 背景

E2E 测试大概是前端工程里最"该做但总被推迟"的事：写起来慢、选择器脆、环境一抖就红。最近我们把几个新模块的 E2E 交给 OpenClaw 的 Agent 起草，配合浏览器类 MCP 工具（如 Playwright MCP），跑出了一条"探索页面 → 生成用例 → 实际执行 → 修复重跑"的闭环。本文记录做法和踩过的坑。

## 问题

- 手写 E2E 成本高：一条"登录 → 创建订单 → 取消"的流程就是两三百行代码。
- LLM 裸生成测试的通病：只覆盖 happy path；选择器靠猜，写完没人跑过；断言形同虚设，比如只判断元素存在。
- 核心差距在于：Agent 如果不能**自己运行并读到失败输出**，它写的测试就只是一段文本。

## 做法

1. **固定技术栈与约定**：项目统一 Playwright，把规范写进 skill / 系统提示——优先 `data-testid`、禁止裸 sleep、每个用例独立造数、结束必须清理。
2. **给 Agent 浏览器能力**：接入浏览器自动化 MCP，让它真实打开页面把业务流操作一遍，顺手记录关键交互的选择器，而不是凭空想象 DOM。
3. **限定产出范围**：一次会话只写一条业务流，输出符合仓库目录结构的 spec 文件，别贪多。
4. **闭环执行**：让 Agent 自己跑 `npx playwright test`，把失败 stack trace 贴回上下文，自行修选择器和等待逻辑；最多迭代三轮，仍失败就停下来向人汇报。
5. **人工 review**：重点看断言强度、测试数据是否污染环境、有没有伪等待。

## 踩坑点

- **选择器**：第一版几乎必用 `nth-child` 和超长层级 CSS，重跑必挂。强制 testid 优先后明显好转；老页面没有 testid 的，先补注再让 Agent 动手。
- **等待**：Agent 很爱写 `waitForTimeout(2000)`，短期绿、长期抖。统一改成 `expect(locator).toBeVisible()` 这类自动等待断言。
- **测试数据**：并行跑时多个用例撞同一个手机号，失败原因极难查。要求每个用例用带随机后缀的账号，并在 `afterAll` 里清理。
- **上下文成本**：整页 DOM 直接贴给 Agent 又烧 token 又全是噪音。改为让它通过 MCP 按需查询元素。
- **过度自信**：Agent 会宣称"测试已通过"但实际没跑。我们要求它贴出执行的命令和原始输出摘要——跑没跑，一眼可见。

## 可复用建议

- 把测试规范沉淀成 OpenClaw 的 skill 或提示词片段，而不是每次会话手打一遍。
- **闭环比生成重要**：能自己执行、自己读报错、自己修的 Agent 才真的省时间；只生成不执行的用例，大概率要人重写。
- 一次一条流，小步提交，生成的 spec 走正常 PR review，和人写的代码一视同仁。
- 提前备好种子数据脚本和测试账号，能省一半来回对话。

## 总结

Agent 写 E2E 的价值不在"零人工"，而在把最机械的部分——探索页面、起骨架、修选择器——自动化掉，让人聚焦在断言设计和业务正确性上。我们的体感：一条中等复杂度的业务流，从半天缩到一小时左右。前提是约定清晰、闭环执行、人审不省。工具是 Agent，流程仍然是工程。
