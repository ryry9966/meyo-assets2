# 本地 LLM 部署：把 Agent 的底座搬回家用电脑

## 背景

做 Agent / MCP 自动化时，很多请求天然涉及本地文件、聊天记录、内网数据，走云端 API 总有点别扭；高频调用的费用也是实打实的。本地部署的目标不是追平顶级云端模型的推理能力，而是把**能跑的那部分工作**留在本地：隐私敏感的任务、简单的工具编排、批处理和离线场景。

## 问题

动手前要先回答三个现实问题：

1. 我这块显卡/这台 Mac，能跑多大的模型？
2. 量化等级怎么选，损失多少？
3. 小模型的 function calling 质量，能不能撑起一个 Agent 循环？

第三点最容易被低估——模型能对话和能稳定调工具，是两回事。

## 做法

**1. 选运行时。** Ollama 上手最快，llama.cpp 的 `llama-server` 更可控，两者都提供 OpenAI 兼容端点；LM Studio 适合纯 GUI 用户。Agent 场景建议前两者。

**2. 按硬件做预算（Q4_K_M 量化，大致值）：**

- 7B/8B：约 5–6GB 显存，绝大多数独显可跑
- 14B：约 10GB
- 32B：约 20GB
- 显存不够看 MoE，如 Qwen3-30B-A3B，激活参数少，GPU+内存混合推理可用；macOS 统一内存机型可以适当放宽

**3. 量化默认 Q4_K_M**，有余量再上 Q6。别迷信 Q8，收益边际很小。

**4. 显式调大上下文窗口。** 这是最高频的坑：Ollama 老版本默认 `num_ctx=2048`，MCP 的工具 schema 一挂上去直接溢出，表现是模型"看不见"列表后面的工具。llama.cpp 用 `-c` 参数。上下文拉到 32k 后，KV cache 的显存占用可能超过权重本身，可以开量化 KV cache 缓解。

**5. 接入 Agent 框架。** `base_url` 指向 `http://localhost:11434/v1`，模型名填 pull 下来的名字。先用一个两轮工具调用脚本验证闭环，再接完整 Agent。

**6. llama.cpp 记得加 `--jinja`**，否则带工具的 chat template 渲染不对，工具调用会静默失败。

## 踩坑点

- **工具调用幻觉**：8B 级模型在参数复杂时容易编造字段。对策：schema 里写清 `enum` 和 `required`，单个小模型会话只挂必要的 MCP server，别把十几个工具全塞进去。
- **别用跑分选型**：拿你自己的 10–20 个真实任务做评测集，跑一遍对比，比看榜单可靠得多。
- **采样参数**：temperature 按模型卡片建议来，别照搬云端习惯。
- **macOS 与 CUDA 行为有差异**：批处理吞吐、上下文上限的表现不完全一致，脚本里别写死假设。

## 可复用建议

- **混合路由**：隐私任务和简单任务走本地，难题走云端，一个 if 判断就能省不少钱。
- **本地当草稿模型**：先本地粗跑，失败再升级到云端，成本和隐私兼顾。
- **部署脚本化**：`ollama pull` + 一个 systemd/launchd 服务 + 健康检查 `curl`，写成一个 20 行的初始化脚本，换机半小时恢复。
- **记录吞吐基线**：tokens/s 什么时候跌了，往往是显存溢出或后台进程抢资源。

## 总结

本地部署的价值不在"替代云端"，而在给 Agent 体系加一层**可控、便宜、离线可用**的底座。从 Qwen3-8B Q4 + Ollama 起步，一个晚上能跑通；之后用真实任务当尺子，按需升级模型、按需混合路由。先把闭环跑起来，再谈优化。
