## 背景

OpenClaw 的 cron 任务本质上是一条"到点自动执行的指令"：你写好 instruction，调度器在指定时间把它交给 agent，agent 在一个全新的会话里执行。这和聊天场景有本质区别——聊天时模型有上下文、有人随时纠正；而 cron 任务是无人值守的冷启动。

社区里经常看到类似反馈："任务跑是跑了，但结果要么驴唇不对马嘴，要么天天在编数据。"多数情况下问题不在模型，而在 instruction 的写法。

## 核心问题

cron instruction 常见三类故障：

1. **依赖不存在的上下文**。写了"继续上面的分析""还是老规矩"，但 cron 会话里没有"上面"，也没有"老规矩"。
2. **时间语义模糊**。"汇总昨天的 issues"——是自然日？执行时刻往前 24 小时？时区按谁的算？
3. **没有输出和兜底约定**。结果发到哪、发多长、数据拿不到时怎么办，全没写，模型只能自由发挥。

## 做法：五段式骨架

我把 cron instruction 固定成五段，每次只填参数、不改结构：

1. **目标**：一句话说清做什么，不带背景故事。
2. **输入**：明确用什么工具 / MCP / 文件，路径或参数写到可直接执行的程度。
3. **步骤**：编号列出动作，别写成描述性段落。
4. **输出**：格式模板 + 去向（哪个频道、哪个文件），并限制长度。
5. **兜底**：明确"获取失败时输出失败原因，禁止编造"。

举个实际例子（每日仓库汇总）：

```text
任务：汇总 openclaw 仓库过去 24 小时新增的 open issues。
步骤：
1. 调用 github 工具，筛选 created_at >= <执行时刻-24h> 的 issues
2. 按标签分组，每条输出编号、标题、链接
3. 总输出不超过 20 行 Markdown
输出：发送到 #dev-daily 频道。
兜底：API 失败或结果为空时，只发一行"获取失败：<原因>"，不要推测条目。
```

最后那句兜底不是废话——没有它，模型面对空结果很容易"贴心地"补几条像样的假数据。

## 踩坑点

- **语气写成对话**。"好的，我来帮你……"这类开头毫无意义，instruction 是规格说明，不是聊天。
- **相对时间不锚定**。"最近""今天"一律换成明确边界，时区在 instruction 里写死。
- **不限输出长度**。高频任务 + 无限输出 = 消息渠道被刷屏，最后被你自己静音。
- **没有幂等设计**。调度重试会重复执行，输出侧要做去重，或允许覆盖旧结果。
- **把知识塞进 prompt**。资料应放文件、让 agent 去读，instruction 只写"读哪、怎么处理"。

## 可复用建议

- **先手动验证**：挂 cron 之前，在对话里手动执行同一份 instruction，确认它能独立跑通。
- **低频起步**：先每天一次，观察一周稳定后再加密频率。
- **重要结果落盘**：写文件或数据库，消息里只发摘要，方便回溯。
- **当代码管理**：instruction 也要有版本意识，改了什么、为什么改，留个记录。

## 总结

写 cron instruction 时，把执行者当成一个能力很强但完全失忆的同事：目标、输入、步骤、输出、兜底，缺一样它就会用自己的想象补上。五段式不复杂，但足以把"到点乱跑"变成"到点交付"。
