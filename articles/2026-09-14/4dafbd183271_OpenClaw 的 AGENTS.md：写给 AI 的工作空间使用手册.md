# OpenClaw 的 AGENTS.md：写给 AI 的工作空间使用手册

## 背景

OpenClaw 的 Agent 每次会话启动时几乎是一张白纸：它能读文件、跑命令、调用 MCP 工具和插件，但不天然了解你的工作空间，目录为什么这样组织、哪些命令是标准流程、哪些文件绝对不能碰。AGENTS.md 就是解决这个问题的约定：放在工作空间根目录的一个 Markdown 文件，Agent 进入工作空间时会自动读取，作为长期上下文。可以把它理解为"写给 AI 的 README"。

## 问题

没有 AGENTS.md 的团队通常会积累三类成本：

1. **重复纠错**。上周刚纠正过"不要直接改生产配置"，新会话又原样犯一遍。
2. **约定失传**。构建用 pnpm、测试前要先起本地依赖、某些目录是生成物不许手改，这些散落在聊天记录里，换个会话就丢。
3. **边界模糊**。Agent 自由度过大，跑了一条本不该跑的命令，事后排查成本很高。

共同根源是：工作空间的使用规则只存在于人的脑子里，Agent 无从得知。

## 做法

我们的 AGENTS.md 控制在 80 行以内，固定六个区块：

- **项目概览**：三行以内说清这个工作空间是干什么的。
- **目录地图**：只列 Agent 容易误入的关键目录，标注"生成物勿改""只读"等属性。
- **约定**：包管理器、命名风格、提交信息格式等可被执行验证的规则。
- **工具使用**：MCP 工具和插件的选用规则，例如"查数据库走数据库 MCP，不要用 shell 拼 SQL"。
- **安全边界**：明确禁止操作——不读 .env、不删缓存目录、部署只走指定脚本。
- **求助规则**：什么情况下停下来问人，而不是自行猜测。

写法上有两条原则。第一，规则要具体到可执行："用 pnpm 不是 npm"有效，"写出优雅的代码"无效。第二，负向指令要配替代路径："不要直接 curl 线上接口，先用 scripts/debug-proxy.sh"。

维护节奏上把它当代码：进版本库、走 PR 评审。Agent 每犯一次新错误，评估是否值得加一条规则；每季度清理一次过时条目。

## 踩坑点

- **写太长**。超过两百行后，中间内容的遵从率明显下降。上下文是稀缺资源，规则越多，单条权重越低。
- **与工具链配置重复**。lint、tsconfig 已有的约束不要再抄一遍，两处漂移后 Agent 不知道听谁的。
- **写入敏感信息**。AGENTS.md 会进入每次会话的提示词，可能随日志外泄。密钥、内网地址一律不写。
- **只说"不要做什么"**。没有替代方案的禁令，Agent 换个姿势还会踩同一个坑。

## 可复用建议

- 从六区块模板起步，宁可留空，不要凑字数。
- 加一个"错误记录"小节，只保留近三个月仍在生效的条目。
- 改动后做回归验证：开一个干净会话，丢一个典型任务进去，观察行为是否符合预期。
- 子目录如有特殊约定，放局部 AGENTS.md，保持分层覆盖。

## 总结

AGENTS.md 的本质，是把团队的工作空间知识"配置化"：投入很小，收益随会话次数复利增长。判断它是否健康只有一个标准，新开的 Agent 会话，能否不问人就把日常任务做对。把它当代码维护，它会持续还债；当文档供着，它很快就会腐烂。
