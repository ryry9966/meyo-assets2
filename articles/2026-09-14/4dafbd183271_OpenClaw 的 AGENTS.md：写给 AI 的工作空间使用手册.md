## 背景

AGENTS.md 是近一年在 Agent 生态里逐渐沉淀下来的事实约定：在工作区根目录放一个纯 Markdown 文件，Agent 启动时自动读取，作为对当前工作区的长期记忆。可以把它理解为 README.md 的兄弟文件——README 写给人看，AGENTS.md 写给 AI 看。在 OpenClaw 这类以工作区为核心的 Agent 环境里，它是成本最低、见效最快的上下文注入手段，不需要写插件，不需要改配置，一个文件就够。

## 问题

没有 AGENTS.md 时，每个会话都在重复解释同样的事：构建和测试用什么命令、目录怎么组织、哪些文件不能动、哪些操作要先确认。结果就是同一个坑反复踩——Agent 用错包管理器、改了生成文件、绕过测试直接提交。更麻烦的是，团队里每个人调教出的行为不一致，换个会话就失效。

## 做法

1. **根目录建 AGENTS.md，控制在 100 行以内**。这是给 AI 的操作手册，不是文档库。
2. **按固定骨架写**，参考最小模板：

```markdown
# 项目概述
一句话说明 + 技术栈

# 常用命令
- 构建：pnpm build
- 测试：pnpm test（提交前必须通过，不可跳过）

# 约定
- 组件放 src/components，命名 PascalCase
- 提交信息遵循 Conventional Commits

# 禁区
- 不要修改 src/api/schema.generated.ts
- 删除文件前先列出清单等待确认

# 本地工具备注
- 文件检索优先走 mcp:fs 的 search，不要全目录读取
```

3. **子目录可再放 AGENTS.md** 处理局部规则，如 `docs/` 下的特殊写作规范。
4. **当代码管理**：进版本库、走 PR 评审，和 `.eslintrc` 同等地位。
5. **迭代维护**：Agent 每犯一次错，就把对应约束补成一行规则，让文件随项目演化。

## 踩坑点

- **写太长**。上下文预算有限，300 行的说明书等于没有说明书。指令是稀缺资源，一行能说清的不要用一段。
- **指令模糊**。“写高质量代码”是废话；“提交前必须跑 `pnpm test`，不允许 `--skip`”才是规则。写具体动作，不写态度。
- **和 lint 配置打架**。风格规则已经在 `.editorconfig`、eslint 里了，AGENTS.md 引用即可，复制一份会变成两处维护、互相矛盾。
- **写入敏感信息**。文件内容会进入模型上下文，密钥、内网地址、客户数据一律不要放。
- **内容过期**。规则与现实冲突时，Agent 会困惑，甚至两边都不遵守。改了构建方式，记得同步改文件，否则它比没有规则更糟。

## 可复用建议

- **冷启动测试**：规则写完后开一个全新会话，观察它是否按手册行动，而不是靠你上个会话的残留记忆。
- **给 MCP 工具补本地约定**：工具描述通常只说明通用用法，项目内的约定——比如资源路径前缀、哪个工具对应哪类任务——写在 AGENTS.md 里最合适。
- **把纠错变成积累**：每次手工纠正 Agent 之后，问自己“这条能不能写成一行规则”。坚持一个月，你会得到一份比多数 wiki 都准确的 AI 使用手册。
- **团队共享**：AGENTS.md 进仓库后，新人（和新的 Agent）开箱即得同一套行为基线，这比口口相传的“调教心得”可靠得多。

## 总结

AGENTS.md 的本质，是把口头的、一次性的“调教”沉淀为可版本化、可评审、可复用的工程资产。它不智能、不花哨，但把 Agent 的行为从碰运气变成可预期。花 20 分钟写第一版，之后每次踩坑补一行——这是当前性价比最高的 Agent 工程化实践，没有之一。
