## 背景

社区里不少人的工作流已经变成：让 Agent 写文档或帖子 → 人工微调 → 手动贴到 GitHub、公众号、知乎、掘金。前两步自动化程度不错，最后一步仍然靠复制粘贴加逐个修格式。当发布平台超过三个，这一步就成了整条链路里最不稳定、最费时的环节。

## 问题

Markdown 看似通用，实际上是方言集合。GFM 的表格、脚注、任务列表在公众号编辑器全部失效；知乎对内联 HTML 几乎零容忍；掘金的代码块高亮规则又和 GitHub 不一致。Agent 默认输出的是“标准姿势”的 Markdown，目标平台一多，人工适配成本线性增长，而且每次发布都在重复踩同样的坑。

## 做法

核心思路是**单一规范源 + 平台蒸馏器**，拆成四层：

```text
Agent 产出 → ① 规范层 → ② Lint 层 → ③ 蒸馏层 → ④ 校验层 → 各平台
```

1. **规范层**：约束 Agent 只输出一个严格子集——禁内联 HTML、图片一律用占位 token（`{{IMG:xxx}}`）、不用脚注、表格保持简单。这一步在 system prompt 或生成模板里做，成本最低。
2. **Lint 层**：用 remark 加自定义规则做静态检查，扫描相对路径、裸 HTML、超长代码行、平台黑名单语法。CI 或 Agent 工具调用里跑，不通过就打回重写，而不是下游硬修。
3. **蒸馏层**：每个目标平台一个纯函数。公众号走 HTML 转 inline-style（rehype + juice 的思路）；知乎走 CommonMark 降级；GitHub 基本直出，只做图片地址重写。
4. **校验层**：对蒸馏结果做确定性断言——图片可访问、代码块闭合、无 front matter 泄漏。

这套东西可以包装成一个 MCP tool（比如 `publish.render(target=wechat)`），Agent 只管产出规范稿，渲染交给管线。

## 踩坑点

- **图片是最大的坑**。相对路径发布即失效，蒸馏层强制走“上传图床 → 替换 URL”，失败要 fail loudly，不能留死链。
- 公众号编辑器会吞样式，只能靠 inline style 硬扛，别指望 class。
- 嵌套列表缩进在不同渲染器下解析不一致，规范层直接限制嵌套不超过两层，比下游修补靠谱。
- 校验别做成宽松警告——警告没人看。Lint 层报错打回，蒸馏层报错阻断发布。
- 校验别用 LLM 判断“看起来对不对”，用 URL 数量、代码块数量这类确定性断言。

## 可复用建议

- **约束前置永远比后置修补便宜**。给 Agent 的输出约束清单和平台能力矩阵放在同一个文件里维护。
- 蒸馏函数保持幂等：同一份规范稿跑两次结果必须一致，方便重试和缓存。
- 新增平台只加蒸馏器，不动规范层。规范层稳定后即冻结——改规范等于改契约，要走评审。

## 总结

多平台发布的复杂度不在“转换”本身，而在方言差异的管理。把 Markdown 收敛成一个严格子集，把平台差异隔离在蒸馏层，发布就从手工活变成可测试的工程问题。我们的实践里，规范层大概一页纸的约束，换掉了每次发布半小时的人工适配，这笔账是划算的。
