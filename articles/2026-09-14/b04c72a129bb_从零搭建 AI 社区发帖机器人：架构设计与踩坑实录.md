## 背景

OpenClaw-CN 社区每天有大量高质量的实践讨论，但运营侧有个现实问题：固定栏目（每周精选、新帖速递、活动提醒）靠人肉维护，漏发、迟发是常态。于是我用 OpenClaw + MCP 工具链搭了一个发帖机器人，稳定跑了一个多月。这篇帖子把架构和踩过的坑摊开讲，给有类似需求的同学参考。

## 核心问题

发帖机器人看似简单，真正的难点有三个：

1. **内容质量不可控**：LLM 直接生成的帖子容易模板化，一眼假；
2. **发布行为不可逆**：触发限流或社区规则红线，账号风险很高；
3. **长期运行稳定性**：cron、API、上游内容源任何一环抖动，都会导致断更或重复发帖。

## 架构与实现

整体采用「采集 → 生成 → 审查 → 发布 → 反馈」五段式流水线，各阶段解耦：

**1. 采集层**：通过 MCP 插件拉取社区 RSS 和精华帖列表，落 SQLite，记录 content hash 用于去重。

**2. 生成层**：OpenClaw agent 定时唤醒，读取候选素材，按栏目 prompt 模板生成草稿。关键设计：**agent 只产草稿，不直接发帖**。

**3. 审查层**：草稿进入待发队列，过两道检查——规则校验（敏感词、链接白名单、长度）+ 人工抽检（每天看一次队列，10 分钟以内）。

**4. 发布层**：独立 worker 通过 MCP 工具调用社区发帖接口，带重试和速率限制（令牌桶，默认 1 次 / 5 分钟）。

**5. 反馈层**：发布后 24h 回读互动数据写入统计表，作为下一轮选题输入。

## 踩坑实录

**坑 1：LLM 编造链接**。早期让 agent 直接引用帖子 URL，结果生成过不存在的链接。解法：链接只从采集层的结构化数据注入，prompt 里明确“禁止构造 URL"。

**坑 2：重复发帖**。一次 worker 重试风暴导致同一内容发了三遍，根因是重试没有幂等键。解法：以 content hash + 栏目 ID 做幂等键，发布前先查表。

**坑 3：cron 时区问题**。容器默认 UTC，定时帖晚了 8 小时。解法：显式声明 TZ，发布层再加时间窗口断言——不在预期时段直接拒绝执行。

**坑 4：模板化文风**。跑两周后被社区朋友吐槽“机器味”。解法：栏目 prompt 注入近期优秀人工帖做 few-shot，要求 agent 输出前自查口吻；人工抽检不过关的直接打回。

**坑 5：上下文膨胀**。反馈层数据全量塞给 agent，token 成本翻了几倍。解法：统计表先做聚合摘要，agent 只读摘要。

## 可复用建议

- **草稿与发布分离**是底线，agent 永远不要握有直接发布权限；
- 所有外部动作必须带**幂等键 + 速率限制**；
- 定时任务显式声明时区，发布动作做时间窗口校验；
- 内容源、prompt 模板、发布配置**全部配置化**，换社区只改配置；
- 留好数据回路，互动数据是唯一能客观评估机器人的指标。

## 总结

这个项目技术上没有黑魔法，价值在于把「LLM 能写」和「敢让它发」之间的鸿沟用工程手段填平：隔离权限、幂等、限流、人工抽检，缺一不可。上线一个多月，固定栏目零断更，人工介入时间从每天 40 分钟降到 10 分钟以内。如果你也在用 OpenClaw 做自动化，建议从最小闭环（单栏目 + 人工发布确认）起步，跑稳后再逐步放开自动化程度。
