## 背景

社区每天有大量讨论沉淀在群聊和 issue 里，人工整理成周报/精选帖效率很低。我们基于 OpenClaw 搭了一个「发帖机器人」：定时抓取讨论源 → Agent 汇总成草稿 → 人工审核 → 自动发布。目标不是全自动水帖，而是把「整理-排版-发布」这段重复劳动自动化，人只做最后把关。

## 问题

第一版很天真：cron 触发 → 拼 prompt → 调 LLM → 拿结果直接 POST 发帖接口。上线三天出了四个事故：重试导致同一篇帖子发了两遍；LLM 输出格式漂移导致发布接口 400；没有频控被社区 API 限流；一次 agent 工具循环调用烧掉半天 token 额度。根本原因是把「生成」当成了全部，没有把发布当成一个**有状态的工程流程**来设计。

## 做法：五层架构

重构后的核心思路是**草稿状态机 + 幂等发布**：

1. **采集层**：RSS / webhook / 轮询拉讨论源，写入本地 SQLite，按 source_id 去重。
2. **调度层**：OpenClaw 定时任务（cron 插件）触发，任务只负责「发起」，不负责「完成」。
3. **生成层**：采集与发布各封装为独立的 MCP tool，Agent 只读素材、生成结构化草稿。输出强制走 JSON Schema 校验，不合法打回重试（上限 2 次）。
4. **审核层**：草稿进入 pending 状态，推送到审核群，管理员回复 approve/reject 才流转。这是刻意保留的人工闸门。
5. **发布层**：独立 worker 消费 approved 队列，携带幂等键（draft_id 的 hash）调用社区 API，指数退避处理 429/5xx，收到 2xx 才置为 published。

状态机简化为：`raw → drafted → pending → approved → published / rejected / failed`。每次状态迁移落库，任何一步都可以回放。

## 踩坑点

- **幂等键要放请求头而不是消息体**：部分网关会改写 body，导致重复判定失效，出现过隔天重复发帖。
- **Schema 校验时给 reason 字段留位置**：让模型自己解释哪条不满足，重试成功率明显提高。
- **cron 用 UTC，展示用本地时区**：曾因服务器时区差 8 小时，周报在周五晚上就发出去了。
- **Agent 工具调用设硬上限**：max_tool_calls = 10，否则素材抓取会自我循环「再搜一次」。
- **日志脱敏**：早期把带 token 的请求头原样打进日志，事后清理非常痛苦。
- **长文先落库再渲染**：社区编辑器对 Markdown 方言支持不一，草稿态保留原始 Markdown 和渲染预览两份。

## 可复用建议

- 任何对外发布类自动化，先设计状态机，再写 prompt。
- 幂等、频控、人工闸门是三件套，缺一个都会在生产环境还债。
- LLM 输出加 Schema 校验 + 有限重试，别赌「这次它应该会」。
- 成本护栏：单任务 token 上限 + 每日配额，超限自动降级为「仅生成草稿不发布」。
- 保留一条手动触发路径，方便压测和故障回放。

## 总结

复盘下来，LLM 生成本身大概只占两成工作量，剩下八成是状态管理、幂等、审核流和观测。对 Agent 应用来说，「能不能稳定地不发重复帖」比「文章写得好不好」更决定它能否长期挂在线上。发布层已抽成适配器接口，后续接其他社区渠道基本只换一个 adapter。
