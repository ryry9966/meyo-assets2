## 背景

我们社区运营侧长期有个痛点：每周要稳定产出 3-5 篇技术帖（周报、教程、问题合集），人写慢，断更快。我的目标从来不是"全自动水帖"，而是让 Agent 负责选题、起草、排版，人负责最后一道审核，再由机器发出去。本文记录这条流水线的架构设计和一个多星期踩坑的过程。技术栈：OpenClaw 网关 + MCP 工具 + 一个自建的论坛发帖插件。

## 问题拆解

直接"让大模型调发帖接口"会撞上两类失败：

1. **内容失败**：生成质量不稳，偶发编造数据、引用不存在的帖子，直接发出去就是事故；
2. **工程失败**：定时任务重复触发、重试导致重复发帖、接口参数幻觉、错误被静默吞掉。

所以架构必须先回答三个问题：谁来定时？谁来写？谁来把关？

## 架构与步骤

整体分四层：

- **触发层**：cron 定时拉起 OpenClaw agent session（注意容器时区，默认 UTC 坑过我一次）。
- **生产层**：agent 通过 MCP 工具拉取素材（社区 issues、本周热帖、关键词检索），生成草稿写入本地 drafts 目录，每篇带唯一 `draft_id`。
- **审核层**：草稿链接推送到我的 IM 频道，我回复"通过 / 改第 X 段 / 毙掉"。审核通过前，发帖工具对 agent 不可见——发布工具只在审批阶段挂载。
- **发布层**：自写 MCP 插件封装论坛 API，入参只有 `title / body / draft_id`，schema 收得很死，模型没有发挥空间。

流程见 img1：cron → agent 起草 → 人工审核 → MCP 插件发帖 → 回执与日志归档。

## 踩坑点

1. **重试导致重复发帖**。网络超时后 agent 重试，同一内容发了两遍。解决：发布接口以 `draft_id` 做幂等键，服务端已存在则直接返回旧帖链接。
2. **模型幻觉接口参数**。早期让 agent 直接 fetch 论坛 REST API，它自己"猜"了一个 endpoint 和字段名，404 之后还试图"修复"。解决：对外请求全部收口到 MCP 工具，schema 用 enum + 必填字段，让它无从发挥。
3. **上下文被历史灌爆**。起初让 agent 读整周全部帖子做选题，token 爆、速度慢，质量反而下降。改成工具端先过滤和摘要，只回传 top 10 标题加摘要。
4. **定时任务静默失败**。cron 触发失败无人知晓，断更三天才发现。现在每次任务无论成败都回执到 IM，失败附带错误摘要。
5. **审核被口头指令绕过**。某次我说了句"这批都发了吧"，agent 直接批量挂载发布工具。后来把"挂载发布工具"本身也做成需要确认的动作，审核通道才真正可靠。

## 可复用建议

- **先草稿、后发布**：发布权限与生成权限分离，是这类机器人最重要的安全边界；
- **幂等键必须做**：任何写操作工具都应接受一个外部 ID；
- **工具 schema 越窄越好**：不是给模型更多自由，而是更少的出错空间；
- **定时任务必须有回执**：静默失败等于没有监控；
- **留审计日志**：`draft_id`、审核人、发布时间，出问题能回放。

## 总结

上线两周产出 9 篇帖子，毙掉 4 篇草稿——被毙掉的那部分，恰恰说明审核层在干活。整体判断：发帖本身不难，难的是把"生成"和"发布"之间那道人为闸门做扎实。Agent 适合当高产出的初稿作者，不适合当最终发布者；这个定位想清楚，架构自然就顺了。代码整理后打算抽成插件模板，感兴趣的同学关注后续帖。
