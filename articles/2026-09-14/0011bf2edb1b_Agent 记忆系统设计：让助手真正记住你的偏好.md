## 背景

LLM 本身无状态。每轮对话结束，模型对"你是谁、你怎么写代码、你偏好什么工具"一无所知。对做 OpenClaw Agent、MCP 插件的人来说，记忆系统是把一个"能用"的助手变成"顺手"的助手的关键一环。但多数实现停留在两个极端：要么把聊天记录全塞进上下文，要么干脆不做。

## 问题

两个极端都会失败：

- **全量塞上下文**：token 成本线性上涨，关键偏好被噪声淹没，能不能命中全靠运气。
- **不做记忆**：用户每次都要重复"我用 TypeScript""commit message 别加 emoji"。

核心矛盾是：记忆要足够多才能个性化，又要足够少才能被模型真正"看到"。这是工程问题，不是提示词问题。

## 做法

我们在一个 MCP 记忆插件里落地了一套方案，分五步：

1. **分层**。记忆拆三层：会话内工作记忆（原始上下文）、情景记忆（做过什么、踩过什么错）、偏好记忆（长期有效的用户画像）。只有第三层跨会话注入。
2. **结构化抽取**。在 `on_message_end` 钩子跑一次轻量抽取，条目 schema 固定：`key / value / scope(global|project) / confidence / source / updated_at`。自由文本式的记忆没法检索，也没法去重。
3. **本地存储**。SQLite 单文件起步就够，别急着上向量库。偏好类条目大多靠 key 精确匹配 + tag 过滤就能命中。
4. **受限注入**。`on_session_start` 时按相关性取 top-k，硬性预算 500 token 以内。宁可少注入，让模型主动调 `memory_read` 补查。
5. **更新与冲突**。新条目 confidence 高于旧条目才覆盖，覆盖时保留版本历史；高影响偏好（比如部署习惯）不自动写，先向用户确认。

关键取舍：把 `memory_read` / `memory_write` 做成 MCP tools，而不是纯背景注入，让 Agent 自己决定"要不要查、要不要记"，抽取只在对话结束后兜底。

## 踩坑点

- **什么都记等于什么都不记**。早期我们记下大量"用户今天提到 X"，噪声让命中率跌到不足三成。后来加置信度阈值，只有明确表态（"以后都……""默认用……"）才入偏好库。
- **偏好会过期**。用户半年前不用 Docker 了，旧记忆还在就会被错误执行。给条目加 `updated_at`，超时降权；被用户纠正一次直接标记 stale。
- **推断 ≠ 表态**。单次说"这次用 pnpm"不代表永远用。inferred 类条目的 confidence 上限要压低。
- **隐私**。记忆文件里曾出现 API key 片段，之后被原样注入别的会话。写入前必须过 PII 过滤，密钥类内容直接拒写。
- **scope 混用**。全局偏好和项目偏好混在一个命名空间，检索时互相污染。scope 必须在 schema 里强制区分。

## 可复用建议

- 先定 schema 再写代码，结构化是检索、去重、冲突处理的前提。
- 显式优于推断：重要偏好让用户确认，宁可多问一次。
- 记忆文件保持人类可读可编辑，出问题时用户能直接改。
- 每次写入记录 source（哪轮对话产生），排查"它为什么这么认为"靠这个。
- 评估只盯两个指标：偏好命中率、用户纠正次数。纠正次数上涨说明记忆在腐化。

## 总结

记忆系统不是"模型能不能记住"的能力问题，而是一套**写入—存储—检索—失效**的工程流程。结构化、少而准、可审计，做到这三点，助手就能在一次次会话间慢慢变得懂你——而且每一步你都能解释它为什么这么做。
