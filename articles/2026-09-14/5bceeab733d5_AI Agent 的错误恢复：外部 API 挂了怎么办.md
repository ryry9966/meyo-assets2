## 背景

Agent 的能力边界，基本等于它调得动的工具边界。OpenClaw 场景里，一个 Agent 背后往往挂着若干 MCP server、HTTP 插件和第三方 API：搜索、天气、内部网关、模型服务。这些外部依赖的可用性从来不是 100%——429 限流、5xx、超时、DNS 抖动、配额用尽，都是日常。

多数人只设计了"成功路径"。API 正常时一切优雅，一旦挂了，Agent 的行为往往比 API 本身更糟。

## 问题：失败不会静默，只会变形

外部 API 挂掉后，常见三种失控形态：

1. **模型硬编**：工具返回错误字符串，模型把它当普通数据，干脆自己编一个"合理"答案——用户拿到的是幻觉。
2. **重试风暴**：Agent 循环重试同一调用，token 烧了一轮又一轮，用户端只看到转圈。
3. **整条流水线卡死**：某个非关键工具失败导致任务中断，实际上完全可以降级继续。

根因是同一个：我们把错误处理交给了 LLM 的临场发挥，而它恰恰不擅长这个。

## 做法：把错误当成一种契约来设计

**第一步：错误分类。** 分清可重试与不可重试：超时、429、502/503/504 属于前者；401/403、参数错误属于后者。分类逻辑写在工具封装层，不要指望模型判断。

**第二步：指数退避 + 抖动。** 重试设上限（建议 2~3 次），间隔指数增长并加随机抖动，且只在工具封装内部做：

```python
@retry(
    retry=retry_if_exception(is_retryable),
    stop=stop_after_attempt(3),
    wait=wait_exponential_jitter(initial=1, max=8),
)
def call_tool(...): ...
```

**第三步：总预算 + 熔断。** 单次调用设超时，整个任务设 deadline。同一工具连续失败 N 次就熔断，一段时间内直接走降级路径，不再真正发请求。

**第四步：降级路径提前写好。** 按成本从低到高三层兜底：备用数据源 → 缓存的上次有效值（必须带时间戳）→ 明确告诉用户"该服务暂不可用"。关键是最后一层：诚实的失败回复，远好过一个像模像样的幻觉。

**第五步：失败结构化写回上下文。** 返回给模型的错误对象要区分"服务不可用"和"服务返回空结果"，并在系统提示里明确要求：工具不可用时不得推测答案，只能报告降级。

## 踩坑点

- **双层重试**：插件封装里 retry，编排层又 retry，3×3 = 9 次请求，放大故障。
- **无抖动的定时重试**：多个会话同时到期恢复，下游刚缓过来又被打挂。
- **空结果语义不明**：返回 `[]` 是"没数据"还是"调用失败"？不区分清楚，降级逻辑全靠猜。
- **重试太诚实**：LLM API 的重试同样计费，无上限重试等于烧钱；同步重试还让用户等待时间不可控。
- **兜底数据不标注**：把昨天的缓存当天新鲜数据返回，比不返回更危险。

## 可复用建议

- 所有外部调用走统一客户端封装：超时、重试、熔断、日志集中在一层，配置驱动，每个工具可有独立策略。
- 准备固定的"降级回复"模板，熔断触发时直接注入结果。
- 关键数据源维护 last-known-good 快照：值 + 时间戳，降级时一并返回给模型。
- 熔断打开时打告警，别等用户来报障。

## 总结

外部 API 挂掉是常态，不是异常。Agent 的可靠性 = 工具层的确定性处理（分类、退避、熔断）+ 上下文层的诚实表达（结构化错误、禁止推测）。把这两件事做扎实，Agent 才算能在真实世界里跑长活。
