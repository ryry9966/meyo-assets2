## 背景

OpenClaw 是常驻本机的 agent，能跑 shell、读写文件、挂 MCP 工具和插件。新用户的第一个问题几乎都是同一个：让模型直接碰我的文件系统，它"手滑"删了东西怎么办？

这个担心合理，但方向不对。OpenClaw 的安全模型从设计上就不假设模型可靠——提示词约束、模型自身对齐都不作为主要防线，真正的防线是进程边界和文件系统边界。

## 问题：误删从哪来

实际场景里，误删风险来自三个地方：

1. 模型幻觉出错误路径，`rm` 打偏；
2. 提示词歧义，用户说"清理一下"，agent 理解成另一个范围；
3. 第三方插件/MCP 工具行为不可预期，在 agent 的权限下做了越界操作。

如果 shell 命令直接以宿主机用户身份执行，这三层任何一层出错都是事故。所以正确的问题不是"怎么让模型别删错"，而是"让删错这件事物理上够不到宿主机"。

## 做法：四层机制

**1. 进程边界。** sandbox 模式下，shell 和文件工具跑在独立容器里。容器内没有宿主机的目录结构，只有显式挂载的 workspace，agent 看到的"根文件系统"是容器自己的。

**2. 路径收敛。** 写/删操作默认只对 workspace 生效。workspace 之外的路径对模型来说只是字符串，工具层直接拒绝，不存在"agent 答应了就能执行"的空间。

**3. 高危命令闸门。** shell 工具可配置审批，`rm`、`sudo` 这类命中规则的命令会暂停等人确认：

```json
{
  "sandbox": { "mode": "all" },
  "tools": { "shell": { "approval": "ask" } }
}
```

**4. 快照兜底。** workspace 级快照在危险操作前留存，哪怕真删错了也能回滚。

验证方法很简单：在宿主机放一个 canary 文件，进 agent 让它删这个路径。预期行为是：容器内提示"找不到该文件"、审批流程被触发、宿主机文件完好。三条都过，边界才算生效。

## 踩坑点

- **把整个 home 目录挂进 sandbox**：边界等于没有，容器只是换个地方删你的文件。
- **privileged 运行或挂载 Docker socket**：等于给逃逸开路，sandbox 语义直接失效。
- **嫌审批烦改成全放行**：闸门形同虚设，模型不稳定时段最危险。
- **软链穿边界**：把宿主目录 symlink 进 workspace，写删会顺着链出去，挂载前先检查。
- **多用户共享同一 workspace**：gateway 场景下的越权源头，应一人一个 workspace 或做目录隔离。

## 可复用建议

- workspace 用独立目录，只挂业务必需的子目录；
- 常驻实例一律 sandbox + shell 审批开启；
- 快照定期化，恢复流程先演练一次再谈安全感；
- 新装插件先在一次性容器里试跑，观察它实际碰了哪些路径；
- canary 文件做成升级后的固定回归项，每次版本更新重测一遍。

## 总结

OpenClaw 防误删的逻辑不是"让模型变靠谱"，而是让删除操作的可达范围被物理约束在 workspace 内、高危动作有人工闸门、兜底有快照。模型可以犯糊涂，边界不会。把安全建立在边界上而不是自觉上，是这套设计最值得借鉴的一点。
