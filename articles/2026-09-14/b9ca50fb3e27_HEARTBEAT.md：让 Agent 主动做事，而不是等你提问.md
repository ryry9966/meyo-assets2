## 背景

绝大多数时候，我们的 Agent 是个"等活儿"的员工：你不发消息，它就闲置。OpenClaw 的 heartbeat 机制提供了另一种模式——Agent 按固定间隔自己醒来，读一遍工作区里的 `HEARTBEAT.md`，判断有没有该做的事：有就执行并汇报，没有就保持沉默。主动性从代码搬进了一份 Markdown 文件。

## 问题：被动应答的三个盲区

1. **时效性任务没人触发**：监控、摘要类任务依赖你记得去问。
2. **cron 太硬**：写死时间的定时任务，表达不了"仅满足条件时才值得打扰我"。
3. **逻辑散落**：想在路上收到主动汇报，但任务分散在各种脚本里，改一次成本很高。

HEARTBEAT.md 的定位：把"什么时候主动做事"写成 Agent 能读懂的自然语言清单，调度交给心跳循环，条件判断交给模型。

## 做法

1. **确认心跳开启**。默认约每 30 分钟触发一次（间隔可配置），每次心跳 Agent 读取工作区根目录的 HEARTBEAT.md。
2. **用 checklist 写任务**，每条 = 触发条件 + 动作 + 汇报格式：

```markdown
# HEARTBEAT.md

- 每天 8 点后第一次心跳：汇总我关注仓库过去 24h 的 release，超过 3 条只列标题。
- 磁盘使用率 > 85%：发告警，附 df -h 摘要；否则什么都不说。
- 每周五下午：整理本周未完成 TODO。
```

3. **利用沉默约定**：明确写"无事可报就不输出"，空响应不会被转发到你的聊天渠道。
4. **精确时间交给 cron**：心跳是"轮询 + 判断"，不是精确调度。准点任务用 cron，HEARTBEAT.md 只放条件触发型任务。
5. **跑 2–3 天看日志**，按误报率迭代措辞。

## 踩坑点

- **成本被低估**：每次心跳都是一次真实的模型调用，30 分钟间隔 = 每天 48 次，哪怕大部分返回"没事"。任务少就把间隔拉到 1–2 小时。
- **模糊任务产生幻觉动作**："帮我看看有没有重要的事"会让 Agent 自由发挥。条件、动作、边界都要写死。
- **上下文污染**：心跳跑在主会话里，长清单加高频执行会挤占对话上下文，清单务必精简，重任务拆到独立脚本。
- **时区漂移**：写"早上 8 点"前先确认 Agent 拿到的系统时区。
- **外部 API 限流**：让 Agent 半小时拉一次平台数据很容易撞 rate limit，条件里加节流说明。
- **清单腐烂**：失效任务不删，Agent 会持续空转。定期 review，没跑过的条目直接删。

## 可复用建议

把 HEARTBEAT.md 当成"值班手册"而不是任务队列，条目按三类组织：

- **阈值告警类**：仅在超阈值时输出（磁盘、错误日志、余额）。
- **定期摘要类**：每天/每周一次 digest，并写明输出长度上限。
- **状态观察类**：只在指定窗口期生效，用"从 X 到 Y"限定范围。

每条都写清"无事发生时的行为"（默认沉默），这是控制打扰度的关键。

## 总结

HEARTBEAT.md 的价值不在调度本身，而在把主动性变成了可编辑的配置：不用重启、不用写脚本，改一个 Markdown 文件即可生效。配合 cron 处理精确时间、配合沉默约定控制噪音，Agent 就能从"你问它答"变成一个真正在线的值守角色。建议小步起步：先放一条阈值告警任务，跑稳了再加摘要类任务。
