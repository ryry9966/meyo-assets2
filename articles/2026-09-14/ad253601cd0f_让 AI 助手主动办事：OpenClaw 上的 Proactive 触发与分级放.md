## 背景

现在大多数 AI 助手还是被动应答：你问一句，它答一句。但 OpenClaw 这类带常驻进程、MCP 工具和插件体系的 agent 框架，其实已经具备主动出击的全部素材——定时任务、webhook、文件监听、MCP 调用的返回结果，都是现成的事件源。缺的不是能力，而是一套把"事件"变成"值得打扰用户的事"的工程管线。

## 问题

最直接的做法是把事件一股脑灌给模型，让它自由发挥。我们试过，会遇到三个典型故障：

1. **噪音爆炸**：CI 每次跑完都汇报，第三天用户开始全局静音，连真正重要的提醒一起埋掉。
2. **越权动作**：模型为了"省事"自动 commit、自动发消息，一次翻车就永久透支信任。
3. **不可观测**：不知道它为什么主动说话，阈值没法调，问题没法复盘。

## 做法

我们在 OpenClaw 上把 proactive 拆成了四层：

1. **事件归一**：cron、webhook、插件回调统一进一个事件通道，每条带幂等键。webhook 重试不会重复触发，这是管线层保证的，不指望模型自己判断。
2. **显著性过滤**：先用便宜规则（关键词、来源权重、去重窗口）砍掉约 80%，剩下的边界样本才交给小模型打分，过阈值才算 proactive 候选。规则在前、模型在后，成本和稳定性都可控。
3. **三分类决策**：候选项进入一个系统提示收得很窄的 agent run，只允许输出三种结果之一：`ignore` / `report` / `propose`。`propose` 生成的是"草案卡"——PR 描述写好、邮件起草、命令预填，但不执行。
4. **分级放行**：只读动作直接做；写操作和外部动作走白名单或一键确认；夜间低优先级候选聚合成日报，不打断。

## 踩坑点

- **阈值一开始设太低**。通知疲劳比没有通知更糟，用户会连重要提醒一起忽略。我们的经验是宁可漏报：上线前两周 ignore 率超过 40% 就收紧。
- **让 LLM 独扛过滤既贵又抖**。同一个 webhook 两次触发，模型可能给出不同决策，幂等和去重必须做在代码层。
- **执行时要复核前置条件**。早上八点基于昨晚数据起草的报告，凌晨可能已有变更。proactive 动作落地前，用最新状态再查一遍。
- **成本失控**。每个事件都起一次完整 agent run 很烧钱，先把规则层做厚，让模型只处理真正模糊的样本。

## 可复用建议

- 从一个**高价值、低风险**的场景起步：CI 失败归因、每日站会摘要、收件箱分诊草稿，都是好起点。
- 把"**提议而非执行**"作为默认姿态；被用户确认过的动作可以进白名单，逐步自动化。
- 盯三个指标：**触发数、采纳率、忽略率**。每周拿忽略样本回看阈值和规则。
- 静默时段、白名单、阈值等配置写成**版本化的 YAML**，别散落在对话记录里，改动要能 diff、能回滚。

## 总结

Proactive 不是模型能力问题，而是信号过滤 + 动作放行 + 反馈回路的工程问题。OpenClaw 生态里事件源和 MCP 工具都是现成的，真正要设计的是"什么值得打扰、打扰到什么程度"。把决策收敛到三分类、把执行收敛到分级放行，主动助手才能长期留在用户的信任预算内——不等你开口，但也不越界半步。
