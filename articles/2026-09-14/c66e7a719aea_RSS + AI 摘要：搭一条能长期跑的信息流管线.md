## 背景

我的信息源长期堆在 RSS 阅读器里：80 多个 feed，每天未读四五百条，真正值得点开的不到 5%。人工筛不动，算法推荐又会把视野越收越窄。RSS 提供的是稳定、结构化、完全可自治的数据源，配合本地 Agent 做摘要压缩，是一条能自己掌控的路线——这也是我最近一个月在 OpenClaw 上反复迭代的自动化项目。

## 问题

把 "RSS → LLM" 跑通很容易，跑"稳"很难。实际会撞上四类问题：feed 结构千奇百怪；摘要质量平庸（满屏"本文讨论了…"式废话）；同一新闻被十几个源转发造成重复；以及长期运行后没人管的 token 成本和故障恢复。

## 做法：四段式管线

**1. 采集层。** 用 MCP RSS 插件或独立脚本拉取 feed，入库前取 guid + 正文哈希作为唯一键，状态存 SQLite。feed 里只有 summary 的，用 readability 类工具抓原文，截断到前 2000 字。

**2. 去重层。** 两层判断：guid/URL 精确去重，标题 SimHash 近似去重（阈值 0.85 起步再调）。转发类内容只保留最早来源。

**3. 摘要层。** 按源分组批量送模型，prompt 里硬性要求"不超过 3 条要点 + 一句为什么值得读"，并附该源的历史摘要作风格锚点。输出写入 state 时带 source / model / prompt 版本号，方便回溯。

**4. 分发层。** cron 定时（我设每天 08:30 / 20:30）触发 Agent 汇总当日条目，生成 Markdown 日报推到 webhook。失败时降级为"只发标题列表"——管线断一截也得有产出。

## 踩坑点

- **feed 半残是常态**：相对链接、编码错误、CDN 限流都要兜底。解析失败重试 3 次后标记死源，每周跑一次源健康检查。
- **别把全文直接塞给模型**：成本翻倍，摘要反而发散。截断 + 分组批处理能把单日成本压到原来的 1/5。
- **摘要废话九成出在 prompt**：不强制"为什么值得读"，模型就输出安全但无用的概括。
- **cron 和 Agent 任务要加锁**：任务跑得慢时下个周期叠加执行，会出现重复日报。
- **摘要缓存按 "URL + prompt 版本" 做键**：改 prompt 后旧缓存自动失效，避免调试时重复烧 token。

## 可复用建议

1. **三层解耦、各自幂等**：任何一层可以单独重跑而不污染状态。
2. **状态全部落 SQLite**：一个文件可备份可迁移，别依赖内存或第三方云状态。
3. **prompt 当配置管理**：进 git，版本号写进产出的元数据。
4. **先小后大**：先接 5 个高质量源跑两周，确认摘要可用再扩量。信息管线的价值在漏斗质量，不在源数量。

## 总结

这套管线跑了一个多月，日均处理约 300 条，压缩成 20 条左右的摘要，每日阅读时间从 40 分钟降到 10 分钟以内。工程上没有任何黑科技，价值全在把去重、降级、成本控制这些枯燥细节做扎实。RSS 不会死，缺的只是替你做第一道筛选的可靠自动化。欢迎在社区里交换 feed 清单和 prompt 模板。
