# 背景

OpenClaw 的 Agent 是常驻运行的，用户不说话时它也在"活着"。Heartbeat 就是让它周期性自我唤醒一次：跑一个轻量提示词，检查待办、监控项、时间点，判断有没有值得主动汇报的事。另一个思路是推送：webhook、文件变更、cron 一次性任务、MCP 通知，直接把事件投进会话队列——事件驱动，无事件不醒来。

两种机制我都在用，但很晚才想清楚它们的边界在哪。

# 问题

纯轮询的代价很直白：绝大多数唤醒是无事发生的，token 照烧；间隔拉太长又会漏掉时效性事件。

纯推送的问题更隐蔽：所有"该注意的事"都得有人给它接一个事件源。时间是事件吗？内部状态漂移是吗？"用户三天没用某服务了"这类判断没有天然的生产者。而且推送链路一断，你就全盲——系统失去了兜底感知能力。

我的结论：这不是二选一，是分工问题。

# 做法

1. **给触发源分类**。时间型（每天九点汇报）、模糊状态型（"最近活动异常"）归 heartbeat；精确事件型（CI 失败、新邮件）归推送。
2. **Heartbeat 保持笨而便宜**。固定小 system prompt，限制可用工具，间隔 30 分钟起步，夜间静默。关键是在提示词里写明"沉默是合法输出"——没事就输出 NO_REPLY，禁止硬找话说。
3. **推送侧做幂等与合并**。同一事件源短时间内多次触发，先进队列去重，合并成一个会话回合再交给模型。
4. **记录每次唤醒的 wake reason 和是否产生有效输出**，统计"有效唤醒比"。

# 踩坑点

- heartbeat 提示词没写"允许沉默"，模型为了证明这次唤醒有价值，开始编造"发现"来汇报。加了明确的静默契约后才停。
- 监控的服务抖动（flapping），推送没去重，一分钟灌了十几条消息。后来加了 5 分钟合并窗口。
- 心跳回合持续污染主会话上下文，历史迅速膨胀。把 heartbeat 挪到独立轻量 session，只在有产出时才写回主会话。
- cron 定时任务和 heartbeat 撞车，同一件事说了两遍。给推送事件加 idempotency key 解决。

# 可复用建议

- 默认架构：**低频 heartbeat 做兜底感知，推送做精确触发**。heartbeat 15–60 分钟，连续空闲可指数退避拉长。
- 心跳输出定死契约：静默 / 简短状态 / 需要用户决策，三选一，不许自由发挥。
- 盯"有效唤醒比"这个指标，长期低于 5–10% 就该拉长间隔，或直接砍掉心跳。
- 所有推送 handler 默认做幂等，不要相信上游不重发。

# 总结

轮询买到的是简单和状态感知，推送买到的是即时和省 token。真实系统里两者都要：heartbeat 当安全网，推送当手术刀。但 heartbeat 必须便宜、必须允许沉默——一个总想说话的心跳，比没有心跳更糟。
