## 背景

在 OpenClaw 插件和 MCP 工具链里，让模型输出结构化 JSON 是家常便饭。提示词里写“只输出 JSON，不要解释”，实际拿到的却五花八门：有时带代码围栏，有时裹在 `<result>` 标签里，有时两者套在一起，前后还附赠一段说明文字。解析这类混合格式，是自动化流水线里最常见的不稳定点。

## 问题

常见写法是直接 `json.loads(response)`，失败后再用正则去围栏。实际会踩到：

- 单一正则只能覆盖一种格式，标签和围栏混用时必然失效；
- 围栏提取时误用贪婪匹配，会把多个代码块的内容缝在一起；
- 模型有时在 JSON 字符串值里再嵌一层围栏，朴素的花括号计数会被打断；
- 解析“成功”不代表数据合法，缺字段、类型错、NaN 都会漏到下游。

## 做法

思路是**分层剥壳 + 候选评分**，而不是一把正则走天下：

1. **标签剥离**：按已知标签（`<result>`、`<json>` 等）提取内层内容，取最后一个闭合标签段，避免误命中提示词里的示例。
2. **围栏提取**：逐行扫描代码围栏的开合状态，记录每个代码块区间，保留围栏内原文。
3. **候选扫描**：对剩余文本做字符串感知的花括号配平扫描，找出所有 JSON 候选片段。
4. **评分择优**：逐个尝试解析，按 schema 命中度打分——必需字段齐全、类型正确得分高；平手时取最后一个（模型倾向把正式答案放在最后）。
5. **修复兜底**：对接近合法的候选做轻量修复（尾逗号、全角引号、裸换行转义），修完重新解析。
6. **终检**：pydantic / jsonschema 校验通过才放行；失败则带着具体校验错误重试一次，让模型自己改。

核心十几行示意：

```python
def extract_json(text: str, required: set[str]):
    cands = scan_balanced(strip_fences(peel_tags(text)))
    parsed = []
    for c in cands:
        try:
            obj = json.loads(repair(c))
            parsed.append((schema_score(obj, required), obj))
        except json.JSONDecodeError:
            continue
    return max(parsed, key=lambda x: x[0])[1] if parsed else None
```

## 踩坑点

- 匹配围栏的正则用非贪婪没问题，但想“取最长 JSON”时误用贪婪匹配，会把两个代码块缝成一个假 JSON。
- 花括号计数必须感知字符串：JSON 值里的花括号和转义引号都会干扰裸计数。
- `json.loads` 默认放行 `NaN` / `Infinity`，这不是严格 JSON，用 `parse_constant` 拦掉。
- 修复逻辑越写越多时，往往说明提示词本身有问题——修复率是提示词质量的信号，要监控而不是硬扛。
- 模型升级后输出分布会变，历史坏样本是最好的回归测试集。

## 可复用建议

- 把这条管线封装成工具函数，OpenClaw 插件和 MCP 工具调用共用一份，别各写各的。
- 日志里同时存**原始输出、提取结果、校验错误**三元组，出问题能完整回放。
- “解析成功”只是及格线，schema 校验才是硬门槛。
- 重试时把校验错误原文塞回提示词，比笼统地说“格式错了”成功率高得多。
- 提示词侧同步配合：要求模型用固定标签包裹输出，正反例各给一个，能显著降低混合格式概率。

## 总结

LLM 输出解析没有一劳永逸的正则。务实的做法是假设任何格式都可能出现：标签剥壳、围栏剥离、候选扫描、评分择优、轻量修复、schema 终检，层层设防。再把原始输出全部落日志，用坏样本养回归测试。防御性解析的本质不是让模型不出错，而是让出错时系统依然可观测、可恢复。
