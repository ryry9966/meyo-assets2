## 背景

OpenClaw 的 agent 主循环默认只绑一个模型。我们的实例最早全走 GPT-4 级云模型，跑两周后 token 账单很难看——事后统计，其中约七成请求只是消息摘要、定时任务汇报这类轻活。换成全本地（Qwen / Llama 系）之后账单归零，但工具调用成功率明显下滑，agent 退化成一个会说话的定时任务。于是我们把多模型路由当成正经工程问题来处理。

## 问题

路由的本质是在**成本、质量、延迟、隐私**四个维度之间做分配。难点不是“能不能路由”，而是两件事：按什么维度路由，以及路由错了怎么发现。

## 做法

**1. 先给任务分桶。** 按我们的实践拆四类：

- 规划与工具编排（多步 tool call、改配置、写代码）：留给强云模型；
- 高频低风险（消息摘要、分类打标、例行回复）：本地 7B~14B 足够；
- 隐私敏感（私聊内容、家庭自动化数据）：默认本地，确需上云先脱敏；
- 向量化与 rerank：本地 embedding，且长期固定一个模型。

**2. 配置路由。** 主 agent 保持强模型不动；在 skill/插件层面做模型覆写；再加一个前置分类步——用本地小模型先判复杂度打标，再决定分发目标。规则宁可粗，先跑通再细化。

**3. 兜底与观测。** 本地优先的任务在低置信或 JSON 解析失败时升级到云端；云端被限流时降级到本地，但给输出打质量标记。所有路由决策落日志，记录 tokens、首 token 延迟、失败率。

## 踩坑点

- **本地模型 function calling 不稳**：参数幻觉、JSON 断裂是常态。对策是给本地路由只开白名单工具，schema 尽量扁平。
- **上下文静默截断**：长会话塞给 8K 窗口的本地模型，agent 会“失忆”且无报错。路由层必须做长度预检。
- **质量回退难察觉**：摘要口径慢慢漂移，没人投诉但确实变差。维护 20~50 条真实 golden case，改路由前后各跑一遍。
- **fallback 循环**：本地失败→上云→限流→又回本地，重试叠加是延迟与成本的双杀，要设硬上限。
- **embedding 混用**：路由改动顺带换了 embedding 模型，向量库检索质量悄悄崩掉，换模型必须重建索引。

## 可复用建议

1. 按任务类型路由，不按感觉路由；先做 80/20：planner 上云，其余本地。
2. 隐私规则写成硬约束而不是可选项，碰私有渠道的数据默认不出机器。
3. 每条路由单独看指标，每周复盘一次，别等账单来了才动手。
4. 一次会话中途别频繁切模型——system prompt 和工具定义要保持一致，否则行为漂移比“慢”更难排查。

## 总结

多模型路由不是一次性配置，而是拿数据持续调整的过程：先粗分桶、再上分类器、最后靠日志和评测集收敛。我们目前云模型调用量降了约七成，工具链任务质量没有可感知的下降。这个平衡点建议你用自己的 golden case 去找，而不是照抄别人的比例。
