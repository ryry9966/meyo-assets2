## 背景

绝大多数 Agent 的使用模式是"拉"式的：你提问，它回答，会话结束就归档。但真把它当长期助手用，你会发现很多需求是周期性的——盯一下服务状态、看看某个仓库有没有新 release、到点汇总待办。OpenClaw 内置了心跳机制（heartbeat）：Agent 每隔一段默认 30 分钟被唤醒一次，如果工作区里有 `HEARTBEAT.md`，就读取并按清单干活；没有这个文件，心跳只做轻量 ACK，几乎不产生开销。

## 问题

没有 HEARTBEAT.md 之前，这些周期性需求要么散落在聊天记录里（你每天手动重复一遍），要么被迫写成独立 cron 脚本，脱离了 Agent 的上下文和工具链。"我希望它持续关心什么"这件事，一直缺少一个沉淀的地方。

## 做法

1. 确认配置里 heartbeat 已启用，`intervalMs` 按需调整，日常巡检 30 分钟足够。
2. 在工作区根目录建 `HEARTBEAT.md`，用清单格式写任务，每条必须包含两件事：检查什么、什么条件下才说话。
3. 观察两三个心跳周期，看日志确认执行路径，然后删掉产生噪音的任务。

示例：

```markdown
# 常驻巡检
- [ ] 检查 https://example.com/health，仅当非 200 时通知我
- [ ] 查看 ~/repos/api 的 git 状态，仅当有未提交改动超过 3 天时提醒
- [ ] 周五 18 点后：汇总本周未完成待办发到 Telegram
```

核心心得：**静默条件比动作更重要**。不写"仅当……"，它每次心跳都会汇报一遍，第二天你就会关掉通知。

## 踩坑点

- **Token 成本**：心跳是真实调用模型的。文件控制在 30 行以内，间隔别低于 30 分钟；心跳轮次可以指定更便宜的模型。
- **任务写得太模糊**："关注一下项目动态"这种写法，Agent 只能靠猜，结果不稳定。要写成可验证的事实判断。
- **和 cron 的边界**：精确到时刻的调度（每天 9:00 整）走 cron 触发；heartbeat 适合"周期巡检、条件触发"，两者别混用。
- **凭证缺失**：任务里调 MCP 工具，前提是凭证已配置。心跳失败往往只在日志里有痕迹，出问题先翻日志再怀疑任务本身。

## 可复用建议

- 每条任务固定四段式：目标 / 检查方式 / 通知条件 / 静默条件。
- 通知分三级：必须通知、仅记录、完全静默，写任务时明确到级。
- 像 review crontab 一样，每月过一遍 HEARTBEAT.md，删掉失效任务。
- 某个任务逻辑变复杂后，把它沉淀成脚本或 skill，HEARTBEAT.md 只留一行索引，别让它长成代码文件。

## 总结

HEARTBEAT.md 的本质，是把"你希望 Agent 持续关心什么"从聊天记录里沉淀成一个可版本管理、可 review 的文件。它的价值不在自动化本身，而在逼你把意图写清楚。建议从一条任务、一个明确的条件开始，跑一周再决定加第二条。
