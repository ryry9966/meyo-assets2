## 背景

用 Agent 干活久了，都会遇到同一个尴尬：每次新会话开场，都得重新自我介绍一遍。「我用 pnpm 不用 npm」「提交信息不要加 emoji」「我偏好的目录结构是这样」——这些话说过不下二十次，但 Agent 每次都像第一次见你。

项目侧的问题早就有了成熟方案：CLAUDE.md / AGENTS.md 这类工作区记忆文件，让 Agent 进入项目就自动带上项目上下文。但**用户侧**一直缺一个对应的载体——项目上下文是关于代码的，而你的技术栈、编码习惯、沟通偏好，是跟着人走的，不该散落在每个项目的配置里。

USER.md 就是补这块的：一个放在用户级工作区的纯文本档案，每次会话自动注入上下文。

## 问题

没有 USER.md 时的典型症状：

1. **重复解释成本高**。个人偏好靠对话零散传达，换个会话就丢。
2. **行为不一致**。同一个偏好，A 会话记住了，B 会话没记住，Agent 表现飘忽。
3. **团队没法沉淀**。个人约定只存在聊天记录里，无法版本化管理。

## 做法

核心步骤很简单：

**第一步：建文件。** 在用户级工作区根目录（如 `~/.openclaw/workspace/USER.md`）新建文件，Agent 启动时会随工作区上下文一起加载。

**第二步：写内容。** 建议用结构化短条目，控制在 100 行以内：

```markdown
# USER

## 技术栈
- 主语言：TypeScript / Python
- 包管理：pnpm（禁止 npm install）

## 代码风格
- 提交信息用祈使句，不加 emoji
- 优先给出现有代码的最小改动方案

## 沟通偏好
- 先给结论，再给推理
- 不确定时直接问我，不要猜
```

**第三步：验证加载。** 新开会话直接问「你知道我的包管理偏好是什么」，确认注入生效，别想当然。

**第四步：持续维护。** 每次纠正 Agent 之后，顺手让它「把这条更新进 USER.md」，档案会越用越准。

## 踩坑点

- **写太长**。超过两三百行后，关键偏好会被稀释，Agent 的注意力不是无限的。宁短勿全。
- **放敏感信息**。API key、真实姓名、公司内部域名不要写进去。这个文件很容易被复制、截图、进版本库，默认它将来会泄露。
- **和项目文件打架**。USER.md 是用户级默认值，项目里的 CLAUDE.md / AGENTS.md 应该覆盖它。设计分层时明确优先级：项目 > 用户 > Agent 默认。
- **信息过期**。技术栈会换，偏好会变。给文件顶部加个更新日期，每月扫一遍，删掉失效条目。
- **假设一定加载**。不同 Agent 框架对工作区文件的处理不一致，换工具后务必实测一次注入行为。

## 可复用建议

- 把 USER.md 放进 dotfiles 仓库做版本管理，多台机器同步一份。
- 分层维护：一份精简的「核心档案」（30 行内）+ 可选的扩展档案，按需加载。
- 用 MCP 的 memory 类工具做补充而非替代：USER.md 管「我是谁」这类稳定事实，memory 管会话中的动态状态，两者职责不要混。
- 团队内可以沉淀一份「USER.md 模板」，新人入职改几个字段就能用。

## 总结

USER.md 解决的不是什么高深问题，而是一个朴素工程问题：**把重复传达的上下文固化成文件**。它成本低（一个 Markdown 文件）、可版本化、可跨项目复用。花半小时写好第一版，之后每次和 Agent 的对话都省掉开场白——这笔投入在任何严肃的 Agent 工作流里都值得。
