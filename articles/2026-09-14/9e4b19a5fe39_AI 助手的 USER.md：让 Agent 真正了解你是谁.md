## 背景

玩 Agent 的人都遇到过同一个尴尬：每次开新会话，都要重新介绍一遍自己。“我是后端，主力 Go，服务跑在自托管 k8s 上，别给我生成 Python 脚本……”说一次两次还好，天天说就是纯浪费 token。

项目侧我们有 `CLAUDE.md` / `AGENTS.md` 这类约定文件，告诉 Agent 这个仓库怎么构建、怎么测试。但“用户是谁”这件事，一直散落在会话记忆和临时口头交代里。USER.md 就是把这部分上下文固化下来的做法——一个放在工作区里的 Markdown 文件，Agent 每次启动时读取，作为“我服务的是谁”的基准事实。

## 问题

没有 USER.md 时，典型症状有三个：

1. **输出风格漂移**。今天给你带解释的长答案，明天只甩一行命令，因为 Agent 每轮都在重新猜你的偏好。
2. **重复交代环境约束**。时区、默认语言、禁用的工具链，说漏一次就翻车一次。
3. **多 Agent 场景上下文割裂**。主 Agent 知道的事，子 Agent 和 MCP 工具一无所知，行为不一致。

## 做法

最小可行版本，五步：

1. 在工作区根目录（或 Agent 配置目录）建 `USER.md`，用 git 管理。
2. 分区写，控制在 50 行以内，推荐结构：

```markdown
# User Profile
## 身份与技术栈
后端开发，主力 Go，少量 TS；自托管，不用云厂商托管服务。
## 环境约束
时区 UTC+8；系统 Debian；Python 仅限数据处理脚本。
## 沟通偏好
先给结论再给推理；代码注释用中文；不确定时直接问，别猜。
## 边界
不要主动升级依赖大版本；不生成需要 sudo 的命令。
```

3. 挂载方式按框架选：OpenClaw 里可作为始终加载的上下文文件注册进 Agent 配置；走 MCP 的话做成一个只读 resource，子 Agent 按需拉取，解决割裂问题。
4. 在系统提示里加一条引用规则，例如：“回答前先对齐 USER.md 中的环境与偏好；与其冲突时，以用户当次输入为准。"
5. 提交 git。之后每次偏好变化就改文件、提 commit，变更历史就是你的偏好演进史。

## 踩坑点

- **写太长**。超过几百行就成了第二个系统提示，token 成本上去，关键信息反而被稀释。原则：只写“会影响 Agent 决策的事实”，不写简历。
- **混入敏感信息**。真实姓名、手机号、内网域名、密钥统统不要。USER.md 会被每次会话读取，等于常驻上下文，是泄露面最大的文件。
- **把行为指令写进去**。“回复要幽默”这类风格指令放这里容易和项目级指令打架。USER.md 只承载事实与约束，行为规则留在系统提示。
- **忘声明优先级**。当 USER.md 和当次指令冲突时，Agent 可能坚持“档案里的你”，跟你犟。引用规则里务必写明：当次输入 > USER.md。
- **信息过期**。换机器、换技术栈后忘更新，Agent 会拿旧事实纠正你。配合 git，至少每月 review 一次。

## 可复用建议

- **分层**：全局 USER.md 放通用事实（时区、语言、沟通偏好），项目目录再放一份 overlay 补充项目相关上下文，加载时后者覆盖前者。
- **写成可验证的陈述**：与其写“熟悉容器”，不如写“容器运行时为 containerd，日常用 nerdctl"。可验证的事实才能被 Agent 用来做纠错。
- **统一 schema**：小团队约定相同段落结构，任何人接手同事的 Agent 环境都能快速读懂这份档案。

## 总结

USER.md 不是什么新协议，只是把你反复口述的自我介绍，变成一份受版本管理的声明式文件。它解决的问题很朴素：让 Agent 的个性化从“每轮猜”变成“读一次”。工程量半小时，收益是所有会话、所有 Agent 共享同一份对你的理解。建议从今天的最小版本开始写，跑两周再修剪——文件会替你记住你是谁，而且比会话记忆可靠得多。
