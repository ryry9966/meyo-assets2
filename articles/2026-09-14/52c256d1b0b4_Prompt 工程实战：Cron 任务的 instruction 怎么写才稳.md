## 背景

在 OpenClaw 里，cron 任务的 instruction 本质是一段"定时注入给 agent 的完整 prompt"。它和日常会话不同：定时触发时通常是一个干净的独立上下文，agent 不记得你昨天聊到哪。所以 instruction 的质量，几乎直接决定任务的质量——它是无人值守场景下唯一的"交接文档"。

## 问题：三类典型翻车

1. **写成备忘录**："每天早上整理一下新闻发给我"。"整理一下"没有边界，agent 每次发挥都不一样。
2. **依赖不存在的上下文**：instruction 里写"继续昨天的分析"，但 cron 是独立会话，agent 根本不知道"昨天"指什么。
3. **没有失败路径**：数据源挂了，agent 不报错，而是"善意地"编一份早报。无人值守场景下，这是最危险的一种。

## 做法：五段式 instruction 骨架

我把 cron instruction 固定成五段，实测能覆盖大部分定时任务：

1. **角色与目标**（1–2 句）：这是干什么的，产出给谁看。
2. **数据来源与工具**：明确用哪个工具 / MCP / 文件路径取数，禁止凭记忆作答。
3. **执行步骤**：3–5 步，每步一个动作。
4. **输出契约**：发到哪个 channel、什么格式、长度上限、是否带链接。
5. **失败路径**：明确"取不到数据时只发失败说明，不要编造内容"。

以一个"每日仓库动态摘要"为例：

```text
你是我的仓库值班助手。任务：汇总主仓过去 24 小时的 commit 与 issue 动态。
1. 用 github 工具查询最近的 commits 和新增 issue；
2. 按"代码变更 / 社区讨论"两类归纳，每类不超过 3 条；
3. 输出到 #daily 频道，总长不超过 200 字，附 issue/PR 链接；
4. 工具调用失败或返回为空时，只发送"今日数据获取失败：<原因>"，禁止编造任何条目。
```

注意细节：时间窗口写死（"过去 24 小时"而非"昨天"）、输出上限写死、失败行为用禁止性指令表达。

## 踩坑点

- **别把调度逻辑写进 instruction**。"每天 9 点执行"这类话留给 cron 表达式，写进 prompt 只会稀释指令。
- **确认时区**。cron 按哪个时区跑先查一次，"早上 8 点"差 8 小时是高频事故。
- **输出目的地不写，默认进主会话**。日积月累刷屏；要么显式指定 channel，要么让任务静默写文件。
- **上线前用"立即运行"手动验证 3–5 次**，翻会话日志看实际执行过程，比上线后靠猜强。
- **instruction 改版留版本号**。文件头加一行注释记录改动日期和内容，出问题能回滚。

## 可复用建议

- 把每条 instruction 当成交接文档，写给一个完全不知道背景的新同事：他拿到就能独立完成，才算合格。
- 一个任务只做一件事。"早报 + 周报"拆成两个任务、两份 prompt，不要复用。
- 单条 instruction 控制在 15 行以内；超过 30 行说明该拆任务，或者该把逻辑下沉到脚本 / 插件里，让 prompt 只做调度壳。
- 定期回看任务的实际输出。instruction 的退化是渐进的，每周扫一眼能提前发现漂移。

## 总结

cron instruction 的核心不是"写得更详细"，而是写出三个契约：**数据从哪来、产出长什么样、失败了怎么办**。定时任务是无人值守的，你不在场时的每一次发挥，都来自你当初写下的那十几行字。花十分钟把骨架套上，比事后排查十次幻觉便宜得多。
