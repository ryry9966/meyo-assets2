## 背景

团队日常有三类信息散落在不同地方：服务的访问日志、Agent 的任务执行记录、CI 与告警通知。日报的意义不在"汇报"本身，而在于第二天早上五分钟内判断"昨天有没有异常、今天要处理什么"。之前这事靠人肉：grep 日志、截图、拼群消息，每天固定消耗 20-30 分钟，且每个人摘的重点都不一样。

## 问题

把这件事交给 Agent 之前，先明确三个难点：

1. 原始日志是半结构化的，行格式不统一，直接喂给模型既浪费 token 又容易漏；
2. 模型擅长归纳，不擅长精确统计——让 LLM 数错误次数，几乎必然数错；
3. 流水线一旦静默失败，第二天才发现"今天的日报呢"，比人肉还糟。

所以设计原则是：**规则做抽取，模型做归纳，调度做兜底**。

## 做法

流水线分四步，跑在一台内网机器上，由 cron 触发 OpenClaw 的定时任务：

**1. 归一化。** 各数据源先用脚本清洗成统一的中间格式（JSON Lines），每条只保留 `ts / source / level / event / meta` 五个字段。纯规则，不经过模型：

```json
{"ts":"2025-06-12T10:23:41+08:00","source":"gateway","level":"warn","event":"upstream_timeout","meta":{"upstream":"search-api","cost_ms":3200}}
```

**2. 规则聚合。** 脚本做计数、分桶、TopN：错误按类型聚合计数，耗时取 P95，Agent 任务按成功/失败分桶，产出一份结构化摘要 JSON。这一步的输出是"事实"，不允许模型改写。

**3. 模型归纳。** 把摘要 JSON 加上前一天的报告样例交给 Agent，生成三段式正文：异常事项（带数字引用）、趋势变化、今日待办。Prompt 里明确要求只能引用输入 JSON 中出现的数字，禁止推断。输出后用脚本校验正文中的数字能否在摘要里找到，不过就重试一次。

**4. 分发与兜底。** 报告通过 MCP 工具推送到群机器人，同时落一份 Markdown 进仓库留档。每一步写执行状态，任何一步失败，兜底脚本就发一条"日报生成失败：xxx"的裸消息——宁可收到失败通知，也不要静默缺报。

## 踩坑点

- **时区**：日志里混着 UTC 和 +08:00，第一版跑出来的"昨日"跨了两个自然日。归一化阶段统一转带时区的 ISO 格式，聚合按本地日切。
- **让模型算数**：早期把原始日志直接丢给模型，错误计数每次都不一样。改成脚本统计后立刻稳定。
- **Schema 漂移**：上游服务新增了事件类型，聚合脚本不报错但数字悄悄变了。现在 `event` 作开放枚举，未知类别单独成列，日报出现"未知事件 N 条"就触发人工检查。
- **重试不幂等**：推送失败后重试，群里出现两条日报。给每次运行生成 `run_id`，推送前查重。

## 可复用建议

1. 中间格式先定 schema 再写转换，schema 是整条流水线的契约；
2. 任何进入 LLM 的数据都应是已聚合的结构化摘要，而不是原始日志；
3. 给流水线加 dry-run 模式，改 prompt 或规则时先离线跑，diff 新旧报告；
4. 失败通知比成功通知更重要。

## 总结

流水线上线后，日报从每天 25 分钟人工降到 0，且数字口径统一。核心经验一句话：把模型放在它擅长的位置（归纳、措辞），把它不擅长的（统计、计数、计时）全部留给规则代码。下一步计划把告警处理回执也接进来，让日报反向标注"哪些告警已被处理"，形成闭环。
