## 背景

跑 OpenClaw 一段时间后，agent 每天会产生大量过程数据：会话日志、工具调用记录、cron 任务输出、git 提交。这些信息散落在不同文件里，靠人每天翻日志写日报，既费时又容易漏掉关键异常。这篇文章记录我们把它做成一条自动化流水线的过程，思路可以直接复用到周报、值班摘要等场景。

## 问题

最初的做法很直觉：定时让 agent「读一下今天的日志，写个总结」。跑了一周就暴露出几个问题：

- **上下文超限**：一天的工具调用日志轻松几十万 token，直接塞给模型放不下；
- **输出不稳定**：同样的日志，今天五段明天三段，格式全看模型心情；
- **噪声淹没信号**：心跳、重试类日志和真正的异常混在一起，模型经常把无关紧要的 retry 当成重点；
- **静默失败**：某天任务没跑成没人发现，日报直接断档。

结论很明确：让模型端到端处理原始日志，是在用它最不擅长的部分。

## 做法

我们把管道拆成四段，确定性工作全部交给代码，模型只负责最后一层的归纳和措辞：

1. **定时采集**：cron 触发脚本，按日期窗口收集各数据源，先做规则过滤——按 event_type 白名单保留有效事件，去重、截断超长字段。输出统一 JSONL，每条包含时间戳、来源、事件类型和一句话摘要。
2. **结构化摘要**：把清洗后的 digest 交给 agent，prompt 固定不变，要求严格输出 JSON，schema 大致是：今日完成事项（带来源引用）、异常与告警、关键指标、待跟进。
3. **校验与渲染**：代码层做 schema 校验，不合格就带着报错重试一次；通过后套固定的 Markdown 模板渲染成日报。
4. **分发与留档**：推送到 IM webhook，digest 和最终日报按日期归档。

整条管道跑下来，单日 token 成本比直塞日志的方案降了一个数量级。

## 踩坑点

- **时区错位**：日志源是 UTC，报告却按本地时区的「昨天」切分，第一版每天凌晨的数据都算错天。采集阶段统一转换时区再落盘。
- **格式漂移**：只在 prompt 里写「输出 JSON」不够，模型偶尔会加解释性前后缀。校验失败后把报错原样喂回去重试，基本能收敛。
- **心跳缺失**：管道挂掉时「没有日报」不会触发任何告警。加了一个独立的心跳检查：每天固定时间没收到产出文件就报警到群里。
- **agent 直接写文件不可控**：早期让 agent 自己落盘，路径和文件名经常出错。改成模型只返回结构，I/O 全部由脚本负责。

## 可复用建议

1. **规则优先，模型兜底**：能用 grep / jq 做的过滤，不要浪费 token。
2. **报告即数据**：中间产物 digest 单独归档，换 prompt 后可以离线重跑、对比效果，不用等第二天。
3. **prompt 和模板进版本管理**：日报风格突变时，能定位到是哪次改动引起的。
4. **人工修正是免费标注**：记录谁改了日报的哪一段，反哺过滤规则，管道会越跑越准。

## 总结

这条管道的本质是分工：代码处理确定性（采集、过滤、格式、I/O），模型处理不确定性（归纳、措辞、优先级判断）。落地之后，日报从每天二十分钟的人工活变成零成本的定时产物，而且比手写更少遗漏。如果你也在用 agent 处理日常事务，建议从「先规约日志、再交给模型」这个顺序开始，不要反过来。
