## 背景

我们团队有个惯例：每天下班前发一份工作日报，内容是当天处理的关键事件、异常告警、部署变更和遗留问题。坚持三个月后，成本问题暴露了——每人每天花 15-30 分钟翻日志、拼格式，而且口径不统一，重要告警时常漏写。

于是我把这件事交给 Agent 来做，搭了一条「原始日志 → 结构化日报」的流水线。跑了两个多月，分享一下实现思路和踩过的坑。

## 问题拆解

日报本质上是一个 ETL + 摘要任务：

- **数据分散**：系统日志、Git 提交、告警记录、任务看板各在一处；
- **噪声大**：一天几十万行日志，有价值的可能不到 1%；
- **需要判断力**：哪些值得写进正文，哪些折叠成附录，规则很难穷举。

## 做法四步，每步独立可测

1. **采集**：用定时任务（cron 触发的 skill）每天固定时间拉取过去 24 小时的数据源。关键设计：原始数据原样落到本地 staging 目录，不做任何清洗，保证可回放。
2. **结构化提取**：这一步不用 LLM。用规则和正则按 schema 归类——时间戳、级别、来源、事件类型；Git 提交按 repo 分组，告警按严重度分级。产出一个中间 JSON。
3. **摘要与判断**：把中间 JSON 喂给 Agent，按固定模板生成草稿：重点事件（最多 5 条）、异常告警、变更记录、待办。Prompt 里明确约束：所有数字必须来自输入数据，禁止推断。
4. **投递**：草稿先发到 review 频道，人工确认后才推正式渠道。头两周全量人工审，稳定后只在告警类内容上保留人工闸门。

## 踩坑点

- **Token 爆炸**：直接把原始日志扔给 LLM 会瞬间超限。解决：提取层先聚合（相同错误按次数合并），进入摘要层的数据控制在几千 token 内。
- **时区边界**：流水线跑在 UTC 容器里，「昨天」的边界算错过一次，导致日报重复和漏事件。现在统一用带时区的区间查询，并在中间 JSON 里显式记录查询窗口。
- **幻觉数字**：早期版本 LLM 会顺手把告警次数四舍五入。加上「数字必须可溯源到输入字段」的约束后基本解决，抽查也对得上。
- **静默失败**：定时任务挂了没人知道。给流水线本身加了心跳——指定时间没收到完成通知就单独告警。

## 可复用建议

- **Schema 先行**：先定义日报的字段结构，再倒推每层处理逻辑，比「先喂日志再说」稳定得多；
- **原始数据不可变**：staging 只追加不修改，出问题永远能重跑；
- **分层解耦**：规则能做的别用 LLM，LLM 只做判断和措辞；
- **保留人工闸门**：前期让草稿过人，既是质量兜底，也是校准 prompt 的素材来源。

## 总结

这条流水线的价值不只是省了写日报的时间，更在于**口径统一和可追溯**——每条日报内容都能回溯到原始日志。全部实现大概两百行配置加一个 skill 脚本，没有引入新依赖。如果你的团队还在手动拼日报，建议从最小版本开始：先只接告警和 Git 两个数据源，跑通再扩。
