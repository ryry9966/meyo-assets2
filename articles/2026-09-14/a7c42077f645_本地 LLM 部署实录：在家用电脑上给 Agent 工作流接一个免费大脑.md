# 背景

做 Agent 自动化一段时间后，多数人会碰到两个现实问题：一是任务里常带隐私数据（本地文件、聊天记录、内部文档），全走云端 API 不放心；二是高频调用下 API 账单肉眼可见地涨。本地跑一个开源模型，是值得认真评估的选项。这篇帖子记录我在一台 32GB 内存、RTX 3060 12GB 的台式机上部署本地 LLM，并接入 OpenClaw 工作流的全过程。

# 问题

本地部署不是“下载个模型就能用”，实际要解决三件事：

1. 显存有限，模型参数量、量化等级、上下文长度三者要相互妥协；
2. 模型必须暴露 OpenAI 兼容接口，才能被 Agent 框架和 MCP 客户端直接调用；
3. 小参数模型在工具调用上明显弱于云端模型，工作流稳定性需要验证。

# 做法

**第一步：评估硬件。** 显存决定上限。经验值：7B 模型 Q4 量化约需 5–6GB 显存（含上下文），14B 需要 10–12GB，再往上基本要 24GB 卡或多卡。我的 12GB 卡实际可用区间是 7B–14B。

**第二步：选推理引擎。** 优先 Ollama 或 llama.cpp：一键拉模型、自带 OpenAI 兼容端点（默认 `http://localhost:11434/v1`）。追求吞吐再考虑 vLLM，但配置成本高；LM Studio 适合快速试模型。

**第三步：选模型和量化。** Q4_K_M 是性价比基准线。做 Agent 工具调用，优先选官方支持 function calling 的 instruct 版本（如 Qwen 系列），不要用社区随机微调版。

**第四步：接入 OpenClaw。** 配置里把 base URL 指向本地端点，模型名填 Ollama 里的 tag 即可。MCP server 本身不感知模型在哪，链路天然兼容。

**第五步：跑真实工作流验证。** 别只看聊天效果，直接跑你的自动化任务：让模型读文件、调工具、输出结构化 JSON，连续跑 20 次统计成功率。

# 踩坑点

- **上下文长度是显存杀手。** 8K 上下文能跑的模型，拉到 32K 可能直接 OOM，KV cache 占用随上下文线性增长。建议从 8K 起步，按需加。
- **量化太狠会毁掉工具调用。** Q4 以下经常输出残缺 JSON 或幻觉出不存在的工具参数。宁可换小一档的模型，也不要用 Q2/Q3 量化。
- **温度和重复惩罚要调。** Agent 场景建议 temperature 0.1–0.3，默认的 0.8 会让结构化输出抖动。
- **GPU 层数别拉满。** 部分层放 CPU 有时反而比显存换页快，用 `num_gpu` 参数做 A/B 测试。
- **RAG 场景记得 embedding 模型也要本地化**，否则隐私数据还是会发到外部 API。

# 可复用建议

1. 写一个固定的冒烟测试脚本（10 个工具调用 case），换任何模型先跑一遍再上线；
2. 本地小模型处理路由、分类、格式化等简单任务，复杂推理仍走云端，混合路由是当前性价比最高的架构；
3. 模型文件统一目录存放，用 GGUF 命名规范管理版本，避免“上次用的哪个文件”的尴尬。

# 总结

本地 LLM 已经到了“能干活”的程度，但它的定位是高频、低复杂度、隐私敏感的任务节点，不是云端模型的完全替代。12GB 显存跑 7B–14B 模型接入 OpenClaw 工作流，一次配置约一个晚上，之后每天几百次调用零成本。建议先拿一个不重要的子任务试点，用成功率数据说话，再决定推广范围。
