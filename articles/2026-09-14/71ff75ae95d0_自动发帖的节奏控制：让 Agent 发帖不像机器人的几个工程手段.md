## 背景

OpenClaw 这类 Agent 框架接上 MCP 工具后，“定时往社区发帖”十分钟就能跑起来：一个 cron 触发、一个发帖插件、循环即可。但跑起来后，问题往往不是能不能发，而是发出来的东西一眼就是机器发的：整点准时报到、每帖长度接近、开头句式雷同、凌晨三点照发不误。轻则被成员屏蔽，重则被版主当 spam 清理。

## 问题拆解

“像机器人”通常不是单一信号，而是几个维度叠加：

1. **时间分布过于规整**：固定间隔、固定整点，间隔方差接近零；
2. **内容同构**：模板复用率高，长度和段落结构稳定得可疑；
3. **只发不互动**：纯广播，行为序列里没有对话；
4. **节奏与环境脱节**：服务器按 UTC 跑，发帖却出现在目标社区的深夜。

## 做法

我们的方案是一个独立的发布调度层：Agent 只负责产出内容，节奏全部在这层控制。

**1. 抖动调度，但别用均匀随机。** 均匀分布的随机间隔本身也是可识别特征。更接近真实习惯的做法：先定义活跃时间窗（按社区本地时间，比如 9:00–23:00），窗口内用对数正态分布采样间隔，工作时段密、午休和晚间稀。

**2. 时区对齐。** 调度一律用社区所在时区计算，服务器内部存 UTC，只在调度边界转换。这条最便宜也最容易漏。

**3. 多样性做在结构层，不做措辞层。** 让模型每句换一种说法，往往产出更差，混乱的句式反而更假。我们的做法：主题队列轮转、强制长度分布（短帖/中等/长文按比例混排）、开头方式维护一个手写模式池。

**4. 相似度闸门。** 发布前对近期帖子做 shingle 重叠检测，超阈值就打回重写或丢弃，顺带防自我重复。

**5. 补发上限。** Worker 宕机恢复后一口气清空积压队列是典型的机器特征。规则：每次唤醒最多补发 1–2 条，其余标记过期丢弃。

**6. 发读比。** 约束发布与互动的比例，比如每发 3 帖前先有若干次回复或引用行为。纯广播账号在谁眼里都可疑。

## 踩坑点

- **均匀随机不等于自然**。第一版用 `random.uniform`，间隔直方图一画，平顶分布，还是假。
- **重试导致重复帖**。发帖 API 超时但实际成功，重试即双发。用幂等键（内容哈希 + 目标板块）在服务端去重。
- **限流恢复不当**。429 指数退避后要重算当天配额，否则会挤占后续窗口形成小峰值。
- **多样性调过头**。为了不像机器把每帖写成随机长度，短帖质量崩了，反而引来更多质疑。

## 可复用建议

- 节奏参数收敛到一个配置文件：活跃窗口、分布类型、日配额、补发上限，不要散在代码里。
- 必须有 dry-run 模式：调度层完整跑一遍，只写日志不发帖，上线前先看一周的模拟发布时间表顺不顺眼。
- 落一张发布流水表（计划时间、实际时间、内容哈希、相似度得分），排查异常全靠它。
- 冷启动阶段保留人工审核：前 20–30 帖走审批队列，参数调稳后再放全自动。

## 总结

节奏控制的本质不是伪装，而是把发布行为约束到与目标社区真实人类活动同分布；分布对齐了，检测者手里的统计特征自然失效。工程优先级建议：时区对齐 > 补发上限 > 相似度闸门 > 非均匀抖动 > 发读比。前两条几乎零成本，任何自动发帖系统都建议先做这两条，再谈别的。
