## 背景

Agent 的核心能力是“调用工具”。模型再强，不能查库、不能触发 CI、不能调三方服务，就只是个会聊天的文本生成器。OpenClaw 的定位，是让 Agent 通过统一的工具协议（MCP / 插件 / HTTP tool）和外部世界握手。这件事听起来只是“包一层 API”，实际工程里坑不少——模型这边讲的是 JSON Schema，服务那边讲的是各自的认证、分页和限流规则，中间的翻译层才是真正决定 Agent 上限的地方。

## 问题

实际对接时常见三类麻烦：

1. **认证**：token 放哪、怎么刷新、怎么保证不进日志；
2. **协议差异**：REST、GraphQL、Webhook 各一套，分页和错误码五花八门；
3. **Agent 侧可用性**：工具描述写得含糊，模型就乱传参数；工具一多，选择就开始出错。

## 做法

**Step 1：盘点服务清单。** 先列出 Agent 真正需要的能力（读数据、写数据、触发动作），而不是把服务的全部接口都包一遍。宁可少而准，不要多而杂。

**Step 2：选对接路径。** 已有 MCP server 的直接接，按场景选 transport——本机进程走 stdio，远程服务走 streamable HTTP。没有现成 MCP 的，写一个薄封装，只暴露最核心的 3~5 个操作。一次性需求直接用 HTTP 请求工具加内联说明，别过度设计。

**Step 3：认真定义工具 schema。** 参数名尽量沿用服务的原始字段名；description 里写清楚“什么时候该用这个工具、什么时候不该用”。这部分对模型行为的影响比代码本身更大。

**Step 4：认证走环境变量或 secrets 管理**，封装层只读配置；token 过期逻辑放在封装层自动处理，不要指望模型自己重试登录。

**Step 5：错误返回要结构化**——状态码加一段可读原因，让 Agent 能判断该重试、换路还是放弃。网络类错误统一加指数退避。

**Step 6：每次调用留痕**：工具名、参数摘要、耗时、结果状态。排查问题时这四项比任何猜测都管用。

## 踩坑点

- 工具描述太空泛，模型在几个相似工具之间反复选错；
- 忽略分页，Agent 拿到第一页就下结论，结果错了一半；
- 没做限流保护，批量任务把对方 API 打挂，key 被封；
- 长耗时任务同步阻塞 Agent 循环，正确姿势是“提交任务 + 轮询/回调”；
- 写操作没有 dry-run，一次误调用删了生产数据；
- secrets 打进了调试日志，事后才发现。

## 可复用建议

- 一个工具只做一件事，参数控制在 5~6 个以内；
- 封装层保持薄，业务编排逻辑留在 Agent 的提示和流程里；
- 所有写操作默认提供 dry-run 参数；
- 能用 MCP 就用 MCP，社区轮子通常比自己造的可靠；
- 上线前用一组固定输入做回归测试，schema 一变立刻能发现。

## 总结

对接外部服务本质上是两件事：把服务能力翻译成模型能理解的语言（schema + 描述），把工程问题（认证、限流、错误、审计）拦在封装层。工具层的质量决定了 Agent 的行为下限——这部分值得慢工出细活，而不是跑通第一次调用就收工。
