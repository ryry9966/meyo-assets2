## 背景

Agent 真正产生价值，往往不在对话本身，而在能不能"动手"：查工单、发消息、调内部系统。在 OpenClaw 里，这一层由工具/MCP 接入承担——agent 决定调用什么，工具层负责和外部 API 打交道。这个"握手"做得好不好，直接决定 agent 是可用的自动化组件，还是一个只会道歉的聊天框。

## 常见问题

实际对接中反复出现三类问题：

1. 模型选错工具或传错参数——根源通常不是模型，而是 tool schema 写得含糊；
2. 错误处理缺失——API 返回 401/429 后，agent 要么卡死要么无限重试；
3. 安全边界模糊——密钥出现在日志或上下文里。

## 做法

以接一个内部工单 API 为例，我们的流程大致是：

1. **先盘服务，再谈接入。** 列出要暴露的能力（查工单、建工单、改状态），区分只读和写操作。只读先上，写的后上。
2. **选接入形态。** 标准场景用 MCP server 包一层；简单场景直接写 OpenClaw 插件。判断标准：是否需要多客户端复用、是否需要独立进程隔离。
3. **认证收口。** 密钥从环境变量或凭据存储注入，不进 system prompt，也不进工具返回值；token 过期在适配层静默刷新。
4. **schema 写给模型看，不是写给开发者看。** 参数描述具体到格式（时间戳是 ISO8601 还是 epoch），取值有限就上 enum，别指望模型猜。
5. **错误转译。** 把 HTTP 错误压成一句模型可读的话，比如"rate limited, retry after 30s"，而不是把整个 HTML 错误页抛进上下文。
6. **观测跟上。** 每次工具调用记录：工具名、参数摘要、耗时、状态码。出问题时，这是唯一的线索来源。

## 踩坑点

- **返回体太大。** 一个 list 接口返回几百条记录，直接塞爆上下文。我们在适配层做默认分页加字段裁剪，agent 需要更多再翻页。
- **非幂等写操作被重试。** 网络超时后自动重试，结果建了两张一样的工单。写操作要么带幂等键，要么不自动重试、把决定权交回 agent。
- **工具命名冲突。** 两个 MCP server 都有 `search` 工具，模型随机挑一个。统一按 `服务_动作` 命名（如 `tickets_search`）后才消停。
- **401 触发重试风暴。** 凭据失效时模型反复重试同一调用。适配层对 401 直接返回终结性错误，附一句"需要人工更新凭据"。

## 可复用建议

- 每个外部服务一个薄适配层，业务逻辑不写在工具实现里；
- 写操作统一加确认门或 dry-run 参数；
- 错误返回定死契约：一句人话加结构化 code，方便 agent 判断该重试还是该放弃；
- tool description 里写清"什么时候不该用我"，往往比写清"怎么用"更能减少误调用。

## 总结

对接外部服务本质上是个接口设计问题，只是调用方从代码变成了模型。schema 写清楚、错误说人话、密钥管严、写操作设防——这四件事做到位，OpenClaw agent 的握手就算握稳了。剩下的迭代，交给日志和真实使用反馈。
