## 背景

社区里越来越多人在跑带 MCP、插件和自动化的 Agent。常见的工作方式是：Agent 挂着内部工具和文档，出问题时把日志、trace、截图贴到社区求助，或者把调好的 workflow 分享出来。这个动作本身没问题，但它是一个**信息出口**——而大多数人只防"入口"（prompt 注入），很少管出口。

## 问题

实际见过几类泄漏：

1. 贴 debug 日志求助，日志里带着发给模型的完整 context：内部系统 prompt、内部服务域名、工具参数里的真实数据。
2. 分享 workflow 配置，里面留着内部项目代号、目录结构和没删干净的 token。
3. 演示用 Agent 挂着生产凭证和全量 MCP，对话中把内部 SOP 原文吐出来。
4. Agent 自动回复社区帖子的场景下没有出口审查，模型把记忆里的内部信息组织进了回复。

这些不是模型"变笨"，而是我们没给它划红线。

## 做法

我们的流程分四步：

1. **分级**。写一页纸明确"可以公开"（通用架构、踩坑模式、脱敏流程图）和"不可公开"（prompt 原文、内部端点、真实数据、项目代号）。这一页纸比任何工具都管用。
2. **隔离**。建一个"演示 profile"：独立 workspace、独立 MCP 实例、只挂演示必需的插件、只读权限、不接生产凭证。社区演示和生产用两套环境。
3. **裁剪**。分享日志前跑清洗脚本：正则匹配内部域名、token 格式、邮箱、IP，替换为占位符；截图前检查终端可见区域。MCP 的 debug 日志默认带全量 tool arguments，这点尤其要记得。
4. **出口审查**。如果 Agent 会自动发内容到社区，发送前加一道关卡：人工过一遍，或规则过滤（禁词表 + 内部域名黑名单）。

## 踩坑点

- **打码不彻底**：遮了 token 却留下内部域名，一条就够反推出内网结构。
- **"改了名字"但留了路径**：项目代号换了，目录结构和函数名组合起来仍可识别。
- **上下文恢复**：演示时 Agent 恢复旧会话记忆，把之前调试的内部信息带进新对话。演示 profile 要禁用跨会话记忆。
- **以为本地跑就安全**：本地确实不外发，但分享 trace/replay 文件时，里面是全量 context。
- **规则过滤的假安全感**：禁词表挡不住改写过的表述，自动化审查只能兜底，不能当唯一防线。

## 可复用建议

- 建一个 `demo-profile`：最小插件、只读、无生产凭证、无记忆，一次配好长期用。
- 清洗脚本放进分享前的固定流程，别依赖记忆和自觉。
- 那页"能说什么"的一页纸，新人入职就发。
- 每月 review 一次 Agent 挂载的工具清单，权限只减不增。

## 总结

Agent 安全常被理解为"防注入"，但出口和入口同样重要。社区分享有价值，值得继续做——前提是把流程工程化：分级、隔离、裁剪、审查。四步都不重，做完之后你贴出来的内容，才真正只包含你想让人看到的部分。
