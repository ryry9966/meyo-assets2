## 背景

Agent 接上 MCP 之后，能力从"生成文本"变成了"执行动作"：写文件、调内部 API、发消息、动数据库。问题也随之从"它能不能做到"变成"它该不该不打招呼就做"。

我们在内部跑了几个月自动化 agent 之后的一个直观感受：权限边界设计得好不好，直接决定了你是在"用 agent"，还是在"给 agent 擦屁股"。

## 问题

实践中很容易滑向两个极端：

- **什么都问**：每次写文件、每次查库都要人点确认。人很快疲劳，开始无脑点"允许"，审批形同虚设——这比不审批更危险。
- **什么都不问**：agent 某天把测试环境的清理脚本跑到了生产上，或者给客户列表群发了一版没校验的文案。

所以真正要回答的是：有没有一个可操作的判断标准，而不是靠拍脑袋逐个配置。

## 做法：按四个维度分级

我们对每个工具调用问四个问题：

1. **可逆吗？** 改错了能不能一条命令回滚？
2. **影响范围多大？** 只碰一个资源还是批量？内部还是对外？
3. **幂等吗？** 重跑一次会不会造成二次伤害？
4. **有真实成本吗？** 花钱、发消息给别人、占额度？

据此分成四档：

- **L0 自动执行**：只读、沙箱内、dry-run。配置读取、日志检索、代码检索。
- **L1 自动执行 + 审计日志**：可逆的写操作。写草稿文件、改 staging、往 feature 分支提交（不碰 main）。
- **L2 一次确认、批量放行**：agent 先列出完整计划（改哪些文件、执行哪些 SQL），人看一眼 diff，确认后整批执行。适合"改 20 个文件里的同一处配置"这类重复劳动。
- **L3 必须逐次确认**：对外副作用。发邮件/消息、生产部署、支付、删除、任何不可逆操作。

落地上的几个具体手段：

- MCP 工具按读写拆分 server：只读的默认全开，写工具默认 deny。
- 危险工具强制带 `dry_run` 参数，agent 第一轮只能拿到"将会做什么"的结果。
- 审批界面展示 diff 和参数，不做裸的"是否继续"。
- 即使是已批准的操作，也设预算上限和频率上限。

## 踩坑点

- **确认疲劳**：L3 划得太宽，人一天点几十次"允许"，最后开始秒点。宁可收窄 L3，把"确认后放行一批"放进 L2。
- **打包夹带**：agent 把一个危险操作混在长长的无害列表里，人看累了就整批通过。审批粒度必须能单独看到每一个副作用。
- **无效确认**："是否继续？"这种问法人根本没法判断。必须展示"将执行 X，影响 Y，回滚方式 Z"。
- **重试放大**：网络超时后 agent 自动重试，非幂等操作被执行三次。写工具要么本身幂等，要么外面包一层带去重的执行器。
- **间接注入**：工具返回内容里被塞进指令，把一个原本 L0 的流程"带"到了写操作。工具输出要当成不可信输入处理，写操作前重新校验意图。

## 可复用建议

- 给每个 agent 写一页权限策略文档，像 review 代码一样 review 它，出事故后回溯修订。
- **默认拒绝是底线**：新接入的 MCP 工具先按 L3 处理，观察一段时间再降级。
- 降级要有数据支撑：某类操作连续 N 次零人工修正，才考虑从 L2 降到 L1。
- 审计日志记录每次工具调用的完整参数和结果——没有日志的权限体系等于没有权限体系。
- 定期做"越界演练"：故意丢给 agent 一个边界模糊的任务，看它会不会越权。

## 总结

权限边界不是一次性的配置，而是一个随信任积累动态调整的策略：默认收紧、凭证据降级、出事故回滚。判断标准可以很朴素——可逆、小范围、幂等、低成本就放手让它干；反之就必须有人的签名。Agent 的自主性是"挣"来的，不是配置文件里写出来的。

欢迎在评论区聊聊你们社区的分级实践，尤其是 L2 和 L3 的边界怎么划的。
