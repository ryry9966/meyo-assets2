## 背景

OpenClaw 这类常驻 Agent，"醒来干活"的方式只有两种：一种是 **heartbeat**——固定间隔自我唤醒，读一遍任务清单，有事处理，没事保持安静；另一种是**推送**——外部事件通过 webhook / MCP notification 直接触发 Agent。不少新用户默认只开 heartbeat，也有人在别人建议下"全上 webhook"。两种极端都有代价，值得把取舍讲清楚。

## 问题

取舍的核心是三个变量：**延迟要求、空闲成本、可靠性兜底**。

- **轮询**：延迟上限等于间隔；空闲时也在烧 token；不依赖入站连通性，内网 / NAT 环境友好；天然兜底——这轮漏掉的事件，下一轮能补上。
- **推送**：延迟低，空闲零成本；但要求事件源能主动调到你，网关需要暴露并做好鉴权；而且推送是**有损的**——Agent 重启、网络抖动、事件源在推送前挂掉，事件就没了，且你不知道丢了。

## 做法

1. **先盘点事件源，按延迟分类。** 秒级到分钟级必须响应的（CI 失败告警、监控阈值）走推送；周期性任务（定时汇总、巡检收件箱）走 heartbeat 或 cron。cron 管"定点"，heartbeat 管"机动巡检"，别混用。
2. **heartbeat 从默认间隔（如 30 分钟）起步**，先跑一周，记录唤醒次数和 token 消耗，再决定是否调密。不要一上来就改 5 分钟。
3. **心跳内容做成清单文件**（类似 HEARTBEAT.md），只写检查项和动作约定，模型每次醒来读它。清单是配置不是代码，改动成本要低。
4. **紧急事件接 webhook 插件**，事件体里带幂等 ID，Agent 侧维护已处理集合做去重。
5. **混合架构**：推送是快路径，heartbeat 拉长到 60 分钟做兜底 sweep，负责捡漏 + 活性自证。
6. **加锁**：上一轮没跑完时跳过本轮 tick，避免 run 堆叠。

## 踩坑点

1. **心跳噪音**：模型醒来没事做，却回一句"今天没什么事"，消息面板全是垃圾。解法：约定静默协议——无事时输出空响应或特定标记，不落用户消息。
2. **token 成本误判**：30 分钟间隔一天 48 次唤醒，每次都带完整 system prompt。有人调到 5 分钟，日成本直接涨一个数量级。先测量，再调参。
3. **webhook 裸奔**：公网 URL 不加校验，等于任何人都能指挥你的 Agent。至少上 shared secret + HMAC 签名，附带时间戳防重放。
4. **纯推送丢事件**：Agent 重启窗口内的 webhook 静默丢失，事后无感知。任何推送链路都必须回答"漏了怎么办"——答案通常就是 heartbeat。
5. **重叠执行**：长任务跨过 tick 间隔，两个 run 并发写同一状态文件。加互斥锁或 skip-if-running 判断。

## 可复用建议

- 一句口诀：**延迟要求决定要不要推送，可靠性要求决定要不要轮询，成本决定间隔**。
- 推送配 sweep 兜底；高频轮询项反过来评估能否事件化。
- heartbeat 的 system prompt 保持最小化，清单文件即配置。
- active hours（工作时间内才心跳）是性价比最高的省钱手段。
- 记录每次唤醒原因（tick / webhook / cron），一周后你就有了调优依据，而不是靠感觉。

## 总结

轮询和推送不是二选一。工程上更常见的答案是混合：**推送负责低延迟，heartbeat 负责兜底和活性自证**。先量化自己的延迟需求和成本约束，再选路径配比——这比照搬任何模板都可靠。
