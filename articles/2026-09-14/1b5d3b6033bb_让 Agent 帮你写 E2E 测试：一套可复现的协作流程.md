## 背景

E2E 测试一直是“人人都知道重要、没人愿意写”的活。Playwright 上手不难，难的是梳理用户路径、维护 selector、保证断言语义正确。Agent + MCP 的组合给了这件事一个新的解法：agent 可以直接操作浏览器、读源码、跑命令，E2E 里最耗体力的部分可以被明显压缩。

过去两个月，我把这套流程在两个内部项目上跑通了，覆盖登录、下单、后台配置等约 30 条关键路径。下面是做法和一些真实的坑。

## 问题拆解

手写 E2E 的成本主要在三处：

1. **路径梳理**：哪些流程值得测、断言什么，需要人脑过一遍；
2. **编写与调试**：selector、等待、测试数据准备，机械且耗时；
3. **失败修复**：UI 一改，测试批量挂掉，排查靠人肉看截图。

其中 2 和 3 是 agent 最擅长的，1 仍然需要人主导。

## 做法

**第一步：给足上下文。** 把 testid 命名规范、测试目录结构、鉴权方式、seed 数据脚本写进仓库的 agent 规则文件（如 `AGENTS.md`）。同时提供一个“黄金样例”测试文件——agent 模仿已有代码风格的能力，远强于凭空发明。

**第二步：让 agent 先走一遍流程。** 通过 Playwright MCP 让 agent 实际打开 dev server，按用户路径点击操作，边走边记录关键节点。这一步很关键：agent 拿到的是真实 DOM，而不是它想象中的 DOM。

**第三步：小步生成。** 一个 flow 生成一个 spec 文件，约束条件写死：只用 `getByTestId`、禁止裸 `sleep`、等待必须基于元素状态。生成后立刻跑一遍，失败信息直接喂回去修。

**第四步：人审断言。** 这是唯一不能省的人工环节。重点看断言是否表达了业务语义（金额、状态、条数），而不是“元素存在”这种恒真断言。

**第五步：固化修复闭环。** CI 失败时把 trace 文件路径回传给 agent，让它判断是产品 bug 还是测试过期。跑顺之后，把整个流程封装成团队共用的 prompt 模板或 skill。

## 踩坑点

- **幻觉 selector**：agent 会自信地写出页面上根本不存在的 testid。必须强制它先用浏览器工具确认真实 DOM，再动手写。
- **恒真断言**：AI 很乐意写“页面加载成功”式的测试，全部绿色但什么都没验证。审断言比审代码重要。
- **一次生成太多**：让它一口气写 20 个用例，后半段质量明显崩坏。一个 flow 一个 flow 来，总时长反而更短。
- **隐式等待泛滥**：不加约束的话，`waitForTimeout(3000)` 会到处出现，flaky 率飙升。规则文件里必须显式禁止。
- **忽视现有基建**：agent 默认从零写登录逻辑，和项目里的 fixture 体系冲突。黄金样例能解决大半问题。

## 可复用建议

- 规范进规则文件，不要靠对话里反复叮嘱；
- 浏览器 MCP + 本地 seed 脚本是这套流程的基座，优先把这两个打通；
- 失败时回传 trace 而不是截图，信息密度高一个量级；
- agent 负责 0 到 0.6，人负责断言语义和边界用例，这个分工目前最稳。

## 总结

Agent 写 E2E 不是“全自动测试”，而是把编写、调试、修复这三段最耗时的循环压缩掉。效果好坏几乎完全取决于你喂给它的上下文质量——规范、样例、真实 DOM 访问，缺一样它就开始编。建议从一条最关键的用户路径开始跑通全流程，再逐步扩展覆盖面。
