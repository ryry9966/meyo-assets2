## 背景

OpenClaw 里有两个能力看起来重叠，实际执行模型完全不同：

- **cron**：调度器驱动。用 cron 表达式定义时间点，到点唤醒 agent 执行一段预置 prompt，跑在**隔离会话**里，跑完可以把结果投递到指定 channel。
- **heartbeat**：agent 周期性自醒。每个心跳周期 agent 读一遍工作区的 `HEARTBEAT.md`，有内容就处理，没内容就回 `NO_REPLY` 继续睡。它跑在**主会话**里，带着完整上下文。

两者都能“定时干活”，但选错了会带来消息重复、上下文污染和 token 账单翻倍。

## 问题

实践里最常见的三个纠结：

1. “每天早八推日报”用哪个？
2. “盯一个长任务，状态变了叫我”用哪个？
3. 两个混用之后，为什么行为变得不可预测？

## 选型判断

核心标准就两条：**要不要上下文**，以及**时间要不要准**。

| 维度 | cron | heartbeat |
|---|---|---|
| 触发方式 | 调度器到点唤醒 | agent 自醒读 HEARTBEAT.md |
| 会话 | 隔离会话 | 主会话，带历史 |
| 时间精度 | 精确 | 近似间隔 |
| 状态依赖 | 无状态，prompt 自包含 | 可依赖对话与工作区文件 |
| 成本模型 | 按任务次数 | 按间隔持续消耗 |

**cron 适合**：日报/周报、定时备份、定时拉数据——时间点明确、不依赖聊天历史、结果可投递。

**heartbeat 适合**：inbox 巡检、盯进行中的任务、等外部回调——“要不要打扰用户”这个判断本身依赖之前的对话。

## 踩坑点

1. **heartbeat 间隔设太短**。每次唤醒都是一次模型调用，10 秒一次一个月的 token 很可观。从 300 秒起步，看日志再调。
2. **把 HEARTBEAT.md 当 TODO 队列**。文件塞满积压后，agent 每次心跳都在还债。这个文件只放“当前周期需要检查的事”，做完就删，控制在几行以内。
3. **cron 里引用主会话上下文**。cron 是隔离会话，“我们刚才说的那个东西”会失败。需要的上下文要么写进任务 prompt，要么让任务先去读工作区文件。
4. **心跳和主对话抢会话**。用户正在聊天时心跳触发，会出现排队或穿插回复。高频检查改用 cron 更稳。
5. **cron 静默失败**。任务报错不一定有通知。排查“为什么没发消息”之前，先看调度日志里最近几次的执行状态。

## 可复用建议

- 一句话选型：**时间驱动用 cron，状态驱动用 heartbeat**。
- 长任务监控的推荐组合：用脚本或 cron 轮询外部状态，变化时写入工作区文件；heartbeat 只负责“看到文件变了就报告”。把轮询从模型调用降级为本地检查，token 成本几乎归零。
- 每个 cron 任务显式写明投递目标和失败行为，别依赖默认值。
- 心跳间隔按“能容忍的延迟”倒推，而不是越小越好。

## 总结

cron 和 heartbeat 不是替代关系：cron 是精确、隔离、无状态的定时器，heartbeat 是带上下文的低频自检循环。大多数定时需求 cron 就够，heartbeat 留给真正需要连续状态判断的场景。先用 cron 起步，发现缺上下文再迁到 heartbeat——这个方向的迁移成本比反方向低得多。
