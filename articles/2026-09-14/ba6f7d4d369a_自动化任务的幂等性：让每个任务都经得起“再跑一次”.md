## 背景

在 OpenClaw 的日常使用里，“同一个任务被执行两次以上”几乎是常态：定时器触发重叠、Agent 因为工具调用超时自动重试、MCP 客户端断线重连后重发请求、调度器对失败任务做补偿重跑。自动化系统的默认语义是“至少执行一次”（at-least-once），而不是“恰好一次”。

幂等性（Idempotency）就是让这件事变得无害的设计原则：**同一操作执行一次和执行 N 次，系统的最终状态一致**。

## 问题

举一个真实场景：一个定时把 issue 汇总发到群里的任务。某天它执行完“发送”动作、还没来得及写入“已完成”标记时进程被杀。调度器判定失败后补跑——群里出现了两条一模一样的汇总。

类似的还有：重跑脚本导致库存加两次、webhook 重投造成记录重复创建、清理任务先删后建留下空窗。这些事故的共同点是：任务把“做了什么”当作结果，而不是把“世界处于什么状态”当作结果。

## 做法

我的原则很简单：**任何自动化任务，都必须经得起“再跑一次”**。落地分四步：

1. **盘点副作用**。列出任务里所有写操作：发消息、写库、调外部 API。只读部分不用管。
2. **选定幂等键**。用一个业务上稳定的标识做去重依据，比如 `task_id + 日期窗口`，而不是随机 ID 或当前时间戳。
3. **把“增量动作”改写成“状态设定”**。数据库写入用 upsert 或带唯一约束的 `INSERT ... ON CONFLICT DO NOTHING`；文件同步改成“根据源重建目标状态”而不是追加式修改；发通知前先查“这个 key 是否已发送”。
4. **原子地记账**。执行记录和动作尽量放同一事务里；做不到时，接受可能重复调用，靠幂等键在外部去重，而不是追求“恰好一次”——那在分布式环境里是幻觉。

在 MCP / 插件层面可以更进一步：给所有工具的 schema 统一加一个可选的 `idempotency_key` 参数，由调用方（Agent 或调度器）在重试时复用同一个 key，服务端据此去重。这是把幂等性从“每个脚本自己操心”升级成“平台约定”的做法。

## 踩坑点

- **先查后写的竞态**：两个并发实例都查到“未执行”，然后都执行。要靠唯一约束兜底，不能靠业务查询。
- **用时间戳当幂等键**：每次重试生成新 key，去重完全失效。key 必须来自业务语义（如“3 月 5 日的日报”），不来自执行时刻。
- **外部 API 不受你控制**：发消息、支付的第三方接口可能本身不幂等，重试策略要保守，或在调用前落库标记、调用后确认。
- **标记写早了**：先写“已完成”再干活，中途失败就永远不会重跑。宁可 at-least-once + 幂等，也不要丢任务。
- **去重表无限增长**：加过期清理，或按时间窗口分区。

## 可复用建议

- 新任务上线前做个简单测试：**连跑三次，断言最终状态和跑一次完全一致**。这个测试比任何代码评审都更容易暴露幂等漏洞。
- 优先用声明式思路写自动化：“确保某状态成立”比“执行某动作”天然更幂等。
- 幂等键的生成规则写进团队约定，避免每个脚本各造一套。

## 总结

自动化系统里，重复执行不是异常，而是设计前提。幂等性不是什么高级技巧，而是一条很便宜的风险底线：一个唯一约束、一个稳定的业务 key，就能把“至少一次”的执行模型变成无害的。与其追求精确控制执行次数，不如让每一次执行都变得可重复。
