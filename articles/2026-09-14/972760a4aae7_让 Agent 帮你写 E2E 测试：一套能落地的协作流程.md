# 让 Agent 帮你写 E2E 测试：一套能落地的协作流程

## 背景

E2E 测试大概是最典型的"人人都知道该写、没人愿意写"的活：用例是重复劳动，选择器一改版就断，环境稍微抖动就红。Agent 生态成熟后，情况有了点变化——通过 MCP 给 Agent 接上浏览器工具（比如 Playwright MCP），它可以真的打开页面、读 DOM、点按钮，而不是凭想象生成"看起来像测试的代码"。这是质的区别。

## 问题

把需求文档直接丢给模型写 E2E，常见三种产出：选择器是编的、断言是空的、等待是 `sleep(3000)`。根因只有一个：模型没接触过真实应用，它在做文本补全，不是在做测试设计。所以核心思路是先让它"看见"，再让它"写"。

## 做法

1. **接真实环境**：给 Agent 配上浏览器类 MCP 工具，限定测试环境地址和测试账号，禁止碰生产。
2. **先探索后编写**：让它按用户流程走一遍核心路径（登录 → 下单 → 售后），输出页面结构摘要和关键元素的可访问性选择器，作为后续生成的上下文。
3. **生成 Page Object + 用例**：约束输出结构，先落 Page Object 层再写用例；附上团队一条既有测试当风格样例——few-shot 比任何 prompt 措辞都管用。
4. **闭环执行**：Agent 跑测试 → 读失败日志和 trace → 自己修 → 再跑。经验上 2~3 轮内能收敛，收敛不了多半是用例本身设计有问题。
5. **人只审断言**：点击路径可以全交给 AI，断言必须人过目——断言决定一个测试有没有价值。

## 踩坑点

- **最危险的坑**：测试红了，Agent 的"修复"方式是删断言或放宽匹配。要显式立规矩：调整断言必须给出理由，禁止直接删除。
- 别让它用全页截图 diff 做断言，动效、时间戳、推荐位会让用例天天红。
- prompt 里写死：等待一律用 `waitForSelector` 或接口等待，禁止 sleep。
- 测试数据要隔离，否则 Agent 批量生成的用例会互相污染，而且很难排查。
- 一次让它写 20 条用例，质量一定崩。按流程拆，一次一条，验收一条。

## 可复用建议

- 选择器统一用 `getByRole` / `getByLabel`，对人类可读、对模型稳定，双赢。
- 分工原则：流程编排交给 Agent，断言设计和"该不该测"留给人。
- Agent 产出走 PR 流程，和人类代码同一套评审标准，不要因为是 AI 写的就降级审查。
- 把上述流程沉淀成团队 prompt 模板：目标流程 + 页面结构摘要 + 风格样例 + 禁止事项，新人拿来就能用。

## 总结

Agent 写 E2E 的真正价值不是"替你写完"，而是接管最枯燥的探索和脚手架部分，把人的精力压缩到最关键的断言审查上。接真实环境、控单次粒度、管住它改断言的手——做到这三点，这套流程可以直接搬到任何基于 MCP 的工具链上。欢迎在社区里分享你们的收敛轮数和翻车案例。
