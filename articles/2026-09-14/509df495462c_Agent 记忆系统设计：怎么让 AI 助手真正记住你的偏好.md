## 背景

大模型本身无状态，Agent 一旦脱离当前会话，上下文就清零。我们接好了 MCP、装了一堆工具，agent 能干活了，但每个新会话开头都得重新交代一遍：包管理器用 pnpm、代码注释写中文、部署先过 staging。工具解决了"能做"，记忆解决的是"知道该怎么做"。这篇记录一下我在 OpenClaw 里搭偏好记忆的实践。

## 问题拆解

失败的实现大多有个共同点：把记忆当成"聊天记录存档"，只管存，不管取和管。真正要回答的是三个问题：

- **记什么**：显式偏好（"别用 var"）和隐式模式（连续三次拒绝某类方案）要分开对待
- **何时写**：不能每轮都写，噪音会淹没有效记忆
- **何时读**：读多了挤占上下文预算，读少了等于没记

## 做法

我按三层组织：

1. **会话内记忆**：上下文窗口天然提供，不用做
2. **偏好档案**：结构化 JSON，小而稳定，每次装配 prompt 时全文注入，硬性控制在 500 token 内
3. **情景记忆**：向量库存任务片段和决策原因，按当前任务语义检索 top-3

**写路径**：每 N 轮或会话结束触发一次抽取，抽取 prompt 强制输出原子事实，每条带原文引用、时间戳、置信度。新事实与已有条目做去重和冲突合并——同主题冲突时新覆盖旧，旧条目降权保留而非删除（偏好会变，但历史有审计价值）。

**读路径**：偏好档案走固定注入通道，确定性最强；情景记忆走检索。同时用 MCP 暴露 `memory_write` / `memory_search` 两个工具，让 agent 在任务执行中主动查证，比纯系统注入灵活。

## 踩坑点

- **过度抽取**：寒暄也进库，两周后档案全是垃圾。加置信度阈值，低于阈值不写；抽取类别用白名单圈死
- **无来源记忆**：模型会脑补你没说过的偏好。强制带原文引用，没引用的抽取结果直接丢弃
- **检索污染**：纯向量相似度会召回字面相近但语义无关的条目。先用结构化字段（类别、项目）过滤，再走向量
- **上下文膨胀**：全量注入很快撑爆 prompt。给记忆区设硬预算，超了按"置信度 × 时间衰减"排序截断
- **多用户隔离**：memory key 忘带 user_id，单人测试没事，上线就串数据。这是最容易漏的一个

## 可复用建议

- 先做结构化档案，别急着上向量库。80% 的偏好场景，一个几百行的 JSON 就够
- 一条记忆只记一件事，原子化，方便合并与审计
- 写入三原则：低置信度不写、冲突必合并、无来源不落库
- 每周跑一次 consolidation 任务，合并重复、淘汰长期未命中的降权条目
- 所有读写打日志。记忆系统不可解释 = 不可调试

## 总结

记忆不是个开关，而是一条带生命周期的数据管道：抽取 → 校验 → 合并 → 注入 → 衰减。建议从最小可用开始——一个 JSON 档案、一个抽取任务、一条注入通道，跑两周统计误记率和命中率，再决定要不要引入向量检索。先让它"记得准"，再追求"记得多"。
