## 背景

大模型本身是无状态的。每次新会话你都得重新交代一遍：代码用 TypeScript、部署在自家 homelab、commit message 别加 emoji。上下文窗口看起来很大，但它是“工作内存”，不是“硬盘”——会话结束即清零。OpenClaw 这类常驻 Agent 的价值恰恰在于跨会话连续性，所以记忆系统是绕不开的一环。

## 问题：三种常见的错误做法

1. **全塞进 system prompt**。偏好积累到几百条后 prompt 膨胀，注意力被稀释，模型反而开始忽略关键指令。
2. **只写不改**。三个月前记的“用 Docker”，在你换成 Podman 之后还在和新指令打架。
3. **全量自动记录**。每轮对话都存，检索时噪声淹没信号，等于没有记忆。

核心矛盾在于：记忆的**写入、读取、更新**是三个独立的工程问题，“存起来”解决不了任何一个。

## 做法：三层记忆 + 明确的读写路径

**第一层：用户画像。** 稳定的结构化偏好——语言、时区、代码风格、常用工具。用 KV/JSON 存储，每轮固定注入，控制在几百 token 内。这层命中率接近 100%，值得常驻。

**第二层：情景记忆。** 项目决策、排障结论、临时约定。带时间戳，按语义检索、按需注入，并设硬预算（建议不超过上下文的 10%）。

**第三层：知识库。** 文档、笔记走 RAG，和记忆分开，不要混在一起检索。

写路径分两种：

- **显式**：用户说“记住 XX”，直接写入，置信度最高。
- **隐式**：用便宜的小模型从对话中抽取候选，设阈值——同一信号出现 2~3 次才入库。一次性吐槽不该变成永久偏好。

每条记忆至少带这些字段：`{content, type, confidence, source, created_at, last_used, superseded_by}`。更新用 upsert 而非追加：新偏好覆盖旧的，旧条目标记 superseded，保留一段时间便于回溯。

存储别过度设计：SQLite 加向量列（如 sqlite-vec），或者干脆一个手工可编辑的 Markdown 文件，足够撑过前几个月。

## 踩坑点

- **嵌入检索对中文短句不友好。**“不要用分号”这类偏好句向量区分度很低，建议混合检索（关键词 + 向量），画像层直接用 tag 匹配更稳。
- **隐式抽取误判。** 见过 Agent 把随口一句抱怨记成“讨厌 PostgreSQL”。置信度阈值之外，给未确认记忆设 TTL，到期未复现就清理。
- **记忆不可见。** 用户看不到也删不掉 Agent 记了什么，信任会崩。提供 `memory list / memory remove` 这类命令，透明是底线。
- **并发写冲突。** 多设备同时跑 Agent 时，固定单写者，或按时间戳 last-write-wins。
- **不度量检索命中。** 写了却从不被检索的记忆是死重。定期做一次 GC：低置信度 + 长期未命中的条目直接清掉。

## 可复用建议

1. 先手写一版画像文件跑两周，观察哪些偏好真的反复出现，再上自动抽取。
2. 记忆注入给上下文设硬预算，超限按 recency + frequency 裁剪。
3. 给每次注入记录日志，统计命中率——这是判断记忆系统有没有用的唯一客观指标。
4. 画像层优先结构化字段，不用自由文本。

## 总结

让 Agent 记住你，本质是设计一条完整的数据生命周期：什么值得写、写进哪层、什么时候读、怎么被覆盖。模型能力决定上限，这套工程流程才决定下限。从一个小 Markdown 文件开始，保持透明、可度量、可清理，比一上来就上向量数据库有用得多。
