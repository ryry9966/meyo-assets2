## 背景

OpenClaw 里 `memory_recall` 是 agent 长期记忆的入口。底层通常是「markdown 记忆文件 + 本地索引」：全文索引（FTS）负责字面命中，向量索引负责语义命中。很多装完就一直用默认配置，直到某天发现助手“记性不好”，才开始怀疑检索这一层。

## 问题

两个典型的翻车场景：

1. 问“上次线上 500 报错是怎么解决的”，但记忆里写的是“GET /api/v2/orders 返回 E1412 的处理记录”。查询词和原文零字面重叠，全文检索直接空手而归。
2. 问“v2.3.1 那个改动的上下文”，语义检索返回一堆“版本管理相关”的泛泛段落，真正含 `v2.3.1` 的那条没进 top3。

结论很清楚：两种检索各有**系统性盲区**，不是谁全面碾压谁。

## 做法

我们做了一次小规模对比：

1. **建评测集**：从最近两周真实会话里挑 25 个“希望助手能想起来”的问题，分三类——精确标识符类（错误码、版本号）、同义改写类、混合类。
2. **分别跑两种检索**：先用全文模式过一遍记 hit@3，再配置 embedding provider 切到语义模式重跑。
3. **对比结果**：标识符类全文几乎全胜；改写类语义明显更好；混合类看命中的词是否恰好落在分词边界上，波动很大。
4. **落地**：切回混合检索，把全文权重调高（约 0.6 / 0.4）。更保守的做法是全文命中为空时才降级到语义，召回路径上行为更可预测。

## 踩坑点

- **中文分词**：FTS 默认 tokenizer 对中文基本按连续字符串切，query 稍长召回就是零。换 trigram 或外挂分词后效果立刻不同，这一步收益最大。
- **embedding 选型**：本地小模型的中文向量质量参差，别只看榜单分；另外向量维度一旦变更，整库必须重建。
- **索引不同步**：直接改了记忆文件但没触发 reindex，检索结果永远是旧的。改完务必重建索引，排查“明明写了却想不起来”时先查这个。
- **延迟**：远程 embedding API 首次建库很慢，离线跑批完成，不要在 recall 路径上现算向量。

## 可复用建议

- **评测集是资产**：每次改检索配置跑一遍，五分钟，防退化。没有它，所有调参都是玄学。
- **留 miss 日志**：recall 为空或答错时把 query 记下来，攒两周就知道该优化哪一头。
- **写入时兼顾检索**：记忆条目开头带上标识符和别名，一行同时喂饱两种检索。
- **别迷信语义**：错误码、版本号、路径名这类 query，keyword 是地基，语义只是补充。

## 总结

语义搜索解决“说法不一样”，全文搜索解决“字面必须对上”，而 memory_recall 的真实 query 里两种都有。工程答案并不新鲜：**混合检索 + 一套小型评测集 + 持续看 miss 日志**。先量化，再调参，比争论“哪个更好”有用得多。
