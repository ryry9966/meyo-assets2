## 背景

在 OpenClaw 里跑内容类 Agent，最常见的产出物就是 Markdown。模型生成很方便，但"生成完"和"发得出去"之间差着一整条管线：公众号只吃带内联样式的 HTML，知乎对代码块和扩展语法支持有限，静态站点要干净的 md，RSS 期望绝对图片链接。同一段 md 直接粘出去，十次有八次跑版。

## 问题

本质是**单一格式对多目标方言的适配问题**，而且差异不在渲染层，在内容模型层：

- 语法子集不同：脚注、任务列表、数学公式各有各的支持度；
- 样式载体不同：公众号会剥掉语义标签，只认 inline style；
- 资源引用不同：外链图片要么被防盗链拦掉，要么被平台转存压缩；
- Agent 产出本身不稳定：列表嵌套层级随机、中英文标点混用、代码块语言标签缺失。

## 做法

把管线拆成五段，每段可独立测试：

1. **生成约束**。在 prompt 或工具 schema 里直接限制 LLM 只用受支持的语法子集：不写脚注、不内嵌 HTML、图片只输出占位节点。生成端松一点，后面全要还债。
2. **归一化**。用 unified/remark 把 md 解析成 mdast，做一遍 lint + 清洗：列表统一缩进、标点规范化、空段落合并。此后所有下游只面对同一个标准 AST，不再碰原始字符串。
3. **目标转换**。每个平台写一个 AST → 目标格式的纯函数 transformer。公众号那路是 mdast → HTML + 内联样式映射表；知乎那路是 mdast → 受限 md；静态站直接透传源文件。transformer 不读全局状态，单测很好写。
4. **资源处理**。图片在发布前统一走图床中转，把临时 URL 换成稳定外链，并在 AST 层替换节点。平台二次压缩不可控，但至少初始链接是可用的。
5. **校验与发布**。渲染后跑一遍 lint：内联样式是否齐全、代码块语言标签是否保留、图片是否全部可达，通过后再交给发布工具（MCP tool 或 CLI）。

我目前的形态是一个 MCP tool：入参是源 md 和目标平台列表，出参是各平台就绪的产物。Agent 只负责写内容，格式适配完全收敛在管线里。

## 踩坑点

- 公众号编辑器会剥 class，所有样式必须内联；`<section>` 嵌套在粘贴时可能丢失，自动化前先验证通道（API 或富文本剪贴板）。
- 防盗链：部分图床链接在后台预览时直接挂，加一道自检（HEAD 请求 + referer 模拟）能省很多排障时间。
- 别相信 LLM 的代码块语言标注，缺失时按内容启发式补。
- 全角/半角标点在不同平台的搜索与排版表现不一致，归一化阶段统一掉。
- 宽表格在移动端必炸，给一个"转图片"或"转列表"的降级路径。

## 可复用建议

- 源文件永远是干净的 Markdown，任何一步都别往源里塞平台私货；
- 样式映射、语法降级规则单独成配置文件，改平台样式不动代码；
- 每个平台留一份 golden sample，CI 里做快照测试，平台改版时 diff 一眼可见；
- 先手工发两三篇摸清平台边界，再写自动化，别上来就全托管。

## 总结

多平台发布看起来是排版问题，实际是内容模型问题。把 Markdown 当成 AST 中间表示，生成端约束语法子集，转换端做成纯函数，资源端提前中转，校验端兜底——Agent 的产出才能稳定落进每个平台的坑位。这条管线真正的价值不在"自动发"，而在平台改版时，你只需要改一处。
