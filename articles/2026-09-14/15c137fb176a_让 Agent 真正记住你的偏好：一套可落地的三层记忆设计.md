## 背景

用过 Agent 的人大概都有类似体验：上周明明说过"回复用中文、代码示例用 TypeScript"，今天开个新会话，它又全部忘光。对 OpenClaw 这类常驻型个人 Agent 来说，会话之间断档是常态，记忆系统不是锦上添花，而是核心组件。

## 问题

常见的三种错误做法：

1. **全量塞 system prompt**：把历史摘要全部注入，token 成本线性上涨，关键指令反而被噪音稀释；
2. **只靠会话历史**：跨会话、跨客户端直接归零；
3. **无结构存储**：把记忆当日志堆，检索时召回一堆无关内容。

本质问题：记忆是"数据库 + 检索 + 产品决策"的混合问题，不是 prompt 技巧能绕过去的。

## 我的做法：三层记忆 + 受控读写

**分层存储**

- **L1 用户画像**：结构化 KV，如 `language: zh-CN`、`code_style: typescript`，每轮固定注入，总量控制在 200 token 以内；
- **L2 长期事实**：带时间戳的摘要条目（项目背景、常用工具路径），按需检索，不全量注入；
- **L3 会话摘要**：超长会话压缩旧轮次，只留结论。

**写入侧**：通过 MCP 暴露 `memory_write` / `memory_search` 两个工具。写入前先过一道判断——这条信息是"持久偏好"还是"一次性上下文"？只有前者入库，且必须带 `confidence` 和 `source` 字段。

**检索侧**：每轮用户输入先做相关性检索，top-k（建议 k≤3）注入上下文。命中即更新 `last_hit`，长期未命中的条目进衰减队列。

**冲突处理**：新偏好覆盖旧偏好，但保留旧版本和变更时间，方便回溯"它为什么这么理解我"。

## 踩坑点

1. **写入过激**：用户说"这次用 Python 写"，被存成"用户偏好 Python"。后来在写入判断里显式要求区分时间范围词，一次性限定词不入库；
2. **只写不清**：三个月后画像里还留着早已弃用的工具链。`last_hit` 超过 30 天的条目自动降权或归档；
3. **隐私裸奔**：早期 API key、家庭地址曾被原文写入。现在写入前跑一遍敏感信息过滤，命中即拒绝并提示用户；
4. **检索过度**：top-k 给到 10 时，模型反而开始忽略 system prompt 里的硬约束。经验是少即是多；
5. **用户不可见**：早期用户无法查看和删除自己的记忆，信任成本极高。一个 `memory_list` 工具加管理命令是刚需，不是可选。

## 可复用建议

- 记忆条目统一 schema：`{id, type, content, confidence, source, created_at, last_hit}`，别用自由文本糊；
- 写入宁缺毋滥，召回宁少勿多；
- 显式指令（"记住…"）直写高置信度；隐式观察到的行为低置信度入库，观察多次再升级；
- 准备一个固定的评测问题集，每次调整检索策略后跑一遍命中率，凭数据调参，不凭感觉。

## 总结

记忆系统的难点不在"存"，而在**什么该存、什么时候取、什么时候忘**。把它当成一个带淘汰策略的小型数据库来设计，再用 MCP 工具化暴露读写能力，Agent 才能稳定地表现出"它记得我"——而不是每次都靠运气。
