## 背景

OpenClaw 的 Agent 本质上是无状态的：每次会话都是一张白纸，它对"你是谁"的全部认知，来自工作区里被注入上下文的那几份 Markdown。`AGENTS.md` 管行为规范，`MEMORY.md` 管会话沉淀，而 `USER.md` 是留给用户自己写的档案——默认几乎是空的。多数人要么不用它，要么把所有东西一股脑塞进去，结果 Agent 始终用通用口吻回答问题。

## 问题

Agent 不认识你，代价是具体的：不知道时区，定时任务排错时段；不知道技术栈，每次都输出保姆级废话；不知道红线，该确认的事直接执行；不知道项目背景，每个会话都要重新解释一遍。重复自我介绍的摩擦成本积累下来，很多人干脆放弃个性化，退回到"每次手打上下文"的原始状态。

## 做法

**1. 固定结构，写事实不写规则。** 我现在用的是四段式：环境与时区、技术栈与偏好、红线、更新记录。示例：

```markdown
# USER.md
<!-- last reviewed: 2025-06-30 -->
## 环境与时区
- 常驻 UTC+8，工作日 10:00–19:00 在线，深夜禁止任何对外发送
- 主力机 macOS，服务器 Ubuntu 22.04，shell 一律 zsh

## 技术栈与偏好
- 后端 Python/FastAPI；前端话题只要结论，不要教程
- 提交信息遵循 Conventional Commits

## 红线
- never 直接 push 到 main；never 未经确认联系任何人
- 删数据、对外发布，必须先复述计划等我确认

## 更新记录
- 2025-06-30: 换组，删除旧项目条目
```

**2. 控制篇幅。** 全文压在 1–2 KB 以内。每次会话都要付注入成本，长文档还会稀释关键条目——红线埋在三千字自传里等于没有。

**3. 和其他文件划清边界。** 关于"我"的稳定事实进 USER.md，Agent 该怎么做进 AGENTS.md，单次会话的结论进 MEMORY.md。混装的结果是指令冲突，行为不可预测。

**4. 定更新协议。** Agent 可以提议追加，但必须带日期、经我确认；每周用一次例行任务让它列出疑似过期的条目，人工过一遍。

**5. 用 git 管工作区。** 改动可 diff、可回滚，谁改的、为什么改，一目了然。

## 踩坑点

- **放任 Agent 自写。** 未经确认的"事实"会变成持久真相——它猜错一次时区，所有定时任务跟着错。
- **敏感信息裸奔。** 工作区可能被各类工具读取和同步，密钥、住址、家人信息不要明文写，要引用不写值。
- **没有日期标记。** 半年前的档案就是噪音源，角色和项目变了不删，Agent 会拿着旧地图导航。
- **重度格式化。** 嵌套表格、多级列表在注入时容易丢结构，纯标题加短句列表最稳。

## 可复用建议

把 USER.md 当成"给新同事的 onboarding 文档"来写，而不是自传：一屏读完、事实一句话一条、红线用 must/never 明示、头部挂 last reviewed 日期。易变的内容宁可不写，交给 MEMORY.md；每季度修剪一次。坚持一个月后的体感是：最有价值的往往不是偏好清单，而是红线段——它是唯一每次都切实改变 Agent 行为的部分。

## 总结

USER.md 是整套记忆机制里成本最低、见效最快的一层：一个文件、几分钟维护，换来 Agent 从"通用客服"变成"知道分寸的同事"。它不解决记忆问题，只解决认知问题——但认知对了，记忆才有意义。
