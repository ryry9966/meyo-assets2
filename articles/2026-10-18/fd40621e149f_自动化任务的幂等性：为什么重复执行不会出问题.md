## 背景

跑 OpenClaw 的人迟早会遇到这个场景：给 agent 配了个定时任务，每天早上汇总信息推到群里。某天网络抖了一下，调度器判定超时自动重试——群里出现了两条一模一样的汇总。

这不是 bug，重试机制在正常工作。真正的问题是：你的任务不支持被重复执行。自动化系统里重试是常态而不是异常——网关会重试，MCP 客户端会重试，agent 在某步失败后重新规划，也会把之前的工具调用再发一遍。幂等性就是让重复执行不出问题的关键：同一个任务执行一次和执行 N 次，最终状态一致。

## 问题：哪些操作天生不幂等

先把常见操作分两类：

- **天然幂等**：覆盖写文件、"把状态置为 X"、按固定路径 upsert、删除已存在的东西。执行多次无所谓。
- **天然不幂等**：追加写、发消息、创建工单、计数器自增，一切 insert 语义的操作。

大部分翻车出在第二类。框架层只负责重试，副作用是你代码里的事，默认没人帮你兜底。

## 做法：三步加上幂等保护

**第一步，盘点副作用。** 列出工作流里所有改变外部状态的步骤：发了什么消息、写了哪张表、调了哪些 API。能改成覆盖语义的先改——"同步数据"用全量 upsert 替代增量 insert，很多问题在这一步就消失了。

**第二步，给剩余操作加幂等键。** 幂等键是逻辑任务的确定性标识，形如 `任务名 + 时间窗口 + 目标对象`，例如 `daily_digest:2024-06-01`。执行副作用前先查这个键是否处理过，处理过就跳过。单机场景一张 SQLite 表足够：

```sql
CREATE TABLE idempotency (
  key TEXT PRIMARY KEY,
  status TEXT,
  created_at INTEGER
);
```

**第三步，先落库再执行。** 别"成功后再记录"——执行和记录之间崩掉，重启后照样重复。正确顺序：插入幂等键（pending）→ 执行副作用 → 更新为 done。重启后扫一遍 pending，就知道哪些事没做完。主键唯一约束还能挡并发：两次重试同时插入同一个键，只有一个成功。

## 踩坑点

- **随机 UUID 当幂等键。** 每次重试生成新 UUID，等于没去重。键必须确定性：同样的逻辑任务算出同样的键。
- **check-then-act 竞态。** 先查再插在并发下会双双通过检查，要靠唯一约束或原子操作兜底，别只靠 if 判断。
- **幂等记录只放内存。** 进程一重启全丢，白做。至少落文件或 SQLite。
- **键的作用域不对。** 太窄去重不掉；太宽会误杀——每日汇总的键忘了带日期、或没对齐时区，就会出现漏发或只发一次。
- **超时后的未知状态。** 发送超时，你不知道对面收没收到。能查目标状态的先查（部分 API 支持按幂等键反查）；不能查就接受 at-least-once，让下游去重。
- **记录无限增长。** 幂等表要定期清理，但清理窗口必须大于最大重试间隔，否则长重试会穿透。

## 可复用建议

- 优先把任务设计成"声明期望状态"而非"执行动作"，前者天然幂等，这是收益最大的一条。
- 单机和插件脚本里，那张三字段的幂等表能覆盖 80% 的场景，直接复制。
- 把幂等性测试加进清单：同一任务连跑两遍，断言第二遍之后外部状态无变化。
- 调第三方 API 前先查文档有没有官方幂等键支持（消息、支付类 API 常见），有就用官方的，别自己造。

## 总结

可靠自动化 = 会重试 + 幂等。重试把偶尔的失败救回来，幂等保证救的过程不制造新问题。写任何自动化任务时，默认假设它会被执行两次——这个习惯能省掉之后大部分凌晨排障。
