## 背景

在 OpenClaw 的日常使用里，"同一个任务被执行不止一次"是常态而非异常：

- 定时任务在重启后重放错过的时间窗口；
- webhook / 消息通道因超时而重试投递；
- agent 在多轮规划中重复调用同一个 MCP 工具；
- 插件对同一条消息的事件回调被触发两次。

分布式投递的默认语义是"至少一次"，编排层很难保证严格的"恰好一次"。所以真正的问题不是"如何只跑一次"，而是"跑两次也没关系"——这就是幂等性。

## 问题

不幂等的任务，故障模式很典型：重复创建工单、重复发通知、文件被追加两次、配额被扣两次。更麻烦的是排查——日志里两次调用长得一模一样，你分不清是重试还是新请求。

Agent 场景还多一层：LLM 输出本身不确定，同一输入两次执行可能生成不同计划。指望"模型每次做出相同决策"来保证一致性不现实，幂等必须落到工具层和数据层。

## 做法

1. **给写操作设计稳定的幂等键**。键必须能从任务输入推导，而不是现场随机生成。比如日报任务用 `digest-{日期}-{用户ID}`，而不是 `uuid()`——后者每次重试都变，形同虚设。定时任务用逻辑时间窗口（如 `cron-20250601T0900`）做键，而不是 `now()`。

2. **用存储约束兜底**。幂等键落库加唯一索引，写入用 upsert 或条件插入。并发重放时第二个请求会被数据库拒绝，不依赖应用层"先查再写"的竞态窗口。

3. **状态机 + 副作用放最后**。任务先写 `pending` 记录，副作用（发消息、调外部 API）成功后再标 `done`；执行副作用前先查状态，已 `done` 直接跳过。崩溃在中间也不要紧，重放会从 pending 恢复。

4. **工具设计成声明式**。与其让模型调用"追加一条记录"，不如提供"确保目标状态"式的工具（set / upsert 语义），内部做 diff，无变化就返回 no-op。把幂等做进接口契约，而不是祈祷提示词让模型表现一致。

5. **验证很简单**：同一任务连续跑两遍，断言第二次副作用为零。写进测试，改动后回归。

## 踩坑点

- **幂等键里混入时间戳或随机数**，重试时键变化，去重完全失效。这是最常见的翻车点。
- **粒度错了**：键太粗，合法的第二次执行被吞掉（同一天两条不同提醒被合并）；键太细，等于没去重。先写清楚"什么算同一次任务"。
- **副作用发生在标记之前且不可重放**：状态是 done 但消息没发出去。外部 API 优先选支持幂等键的接口，不支持的就自己记调用流水，重放前核对。
- **去重表无限膨胀**：给幂等记录加 TTL，保留略长于最大重试窗口即可。
- **只靠编排层检查**：加了"执行前判断"但没加唯一约束，并发下照样穿透。存储层约束才是最后防线。

## 可复用建议

- 设计任何自动化任务时，默认假设它会被执行两次。
- 写操作三件套：稳定幂等键 + 唯一约束 + 状态标记。
- 自己写 MCP 工具时，参数里预留幂等键字段，并在文档写明语义。
- 工具返回值里带上"本次是执行还是跳过"，方便上层和日志区分重试与新请求。

## 总结

幂等不是锦上添花，而是自动化能长期跑下去的前提。重试、重放、并发在 agent 系统里不可避免，与其在编排层小心翼翼追求"恰好一次"，不如让每一次执行都收敛到同一个结果。把幂等做进数据模型和工具接口，任务重复跑十次，结果也和跑一次一样。
