## 背景

在 OpenClaw 这类 agent 系统里，"同一段逻辑被跑两次"不是异常，而是常态：

- 调度器超时后重发任务；
- webhook 是至少一次（at-least-once）投递，失败就重推；
- agent 规划失败后自我纠正，重新调用同一个工具；
- 手动重跑和定时任务叠加在一起。

也就是说，自动化任务的真实执行模型不是"恰好一次"，而是"至少一次"。幂等性的作用，就是把"至少一次"收敛成"效果上恰好一次"：同一个任务重复执行，最终状态不变，副作用不叠加。

## 问题

非幂等的典型翻车现场：

- 创建类接口用 POST，重试后插了两条一样的工单；
- 通知插件没做去重，用户收到三条相同消息；
- 脚本重复追加日志、重复解压，目录越跑越脏；
- agent 每轮重规划都重写一遍配置，把人工改过的字段冲掉。

共同点：副作用是**增量式**的（append / create / send），执行次数直接反映在最终状态里。

## 做法

可落地的三层做法：

**1. 先分类，再动手。** 只读操作天然幂等，不用管；"设置到某个绝对状态"的写操作（upsert、按 id 删除、整文件覆盖写）也是安全的；只有增量式操作需要专门处理。这类操作通常占比不高，别过度设计。

**2. 给任务定义幂等键。** 键必须来自业务语义，而不是执行环境，比如 `hash(源数据ID + 业务日期 + 动作名)`。同一任务无论重试多少次，键不变；换一条数据或换一天，键才变。把键随任务一路透传到最底层的工具/MCP 调用。

**3. 执行前查重，执行后记账。** 用 SQLite/Redis 存 `键 → 状态`：查键，已成功就跳过；否则先落盘写入"执行中"标记，再执行副作用，成功后更新状态。崩溃恢复时，"执行中"的记录配合超时策略决定重做还是跳过——这步不能省，否则崩溃窗口里的那次执行会丢。

底层再兜一层：数据库用唯一约束 + ON CONFLICT；发消息优先用平台的去重字段/client token；写文件用临时文件 + 原子 rename。

## 踩坑点

- **键里掺了时间戳或随机数。** 每次重试生成新键，去重形同虚设，这是最常见的错误。
- **键的作用域不对。** 只用数据 ID，跨天的重复任务会被误杀；只用动作名，不同数据互相干扰。必须覆盖"哪条数据 + 哪个时间窗口 + 哪个动作"。
- **check-then-act 竞态。** 两个并发实例同时查到"不存在"，然后都执行。唯一约束或分布式锁至少要有一个，光靠查询判断不够。
- **重试时 payload 变了。** 键相同但内容不同，要提前定策略：拒绝还是版本化键，含糊处理最危险。
- **TTL 太短。** 键记录 5 分钟过期，对方平台 30 分钟后才重推，照样重复。
- **想当然认为 API 幂等。** 很多创建类接口不是，先查文档有没有 idempotency key 支持，没有就在自己这层挡住。

## 可复用建议

- 在工具/MCP 层统一幂等键规范，插件自动继承，别让每个脚本自己发明一套；
- 优先写"描述目标状态"的任务，而不是"执行一串动作"的任务，状态收敛天然幂等；
- CI 里加一条断言：同一任务连跑两遍，副作用计数不变；
- 心智模型反过来记：重试是默认行为，去重才是需要显式写的代码。

## 总结

幂等性不是运行时打的补丁，而是任务定义阶段就该确定的属性。在 agent 反复规划、调度不断重试的环境里，"每次执行都可能发生两次"应作为默认假设。把键定对、把账记好、把唯一约束加上，重复执行就从风险变成了普通的重试路径。
