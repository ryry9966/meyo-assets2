## 背景

信息源越来越散，但 RSS 依然是最可控的订阅协议——没有推荐算法，没有交互干扰。我的订阅列表常年维持在 40+ 个源，靠人工精读不现实。这篇记录我用 OpenClaw 搭的一条「抓取 → 过滤 → 摘要 → 分发」管线，稳定跑了一个多月，现在每天早上收到一份几分钟就能扫完的日报。

## 问题

- 多数博客的 RSS 只给摘要或首段，信息密度不够；
- 全文直接喂给模型，token 成本和噪声都高；
- 同一条新闻被多个源重复报道，日报里全是重复项；
- 纯 LLM 生成的日报容易编造细节，且无法追溯原文。

## 做法

**1. 订阅源治理。** 先用 OPML 导出并分类（技术博客 / 论文 / 项目动态），每类一个 feed 组，低价值源每周裁剪。抓取层我用自建的 FreshRSS 做标准化，MCP 侧写了个很薄的 RSS tool，OpenClaw agent 按组调用。

**2. 增量抓取与去重。** 条目入库（SQLite）前做三道判重：GUID、link 归一化、标题相似度阈值。跨源重复的合并为一条，保留全部原文链接。

**3. 两级过滤。** 第一级不走 LLM：关键词 + 源权重打分，先砍掉约 70% 条目；第二级才把剩余条目（经 readability 抽取后的正文）交给 agent 批量摘要。Prompt 里强制三条约束：只允许使用给定文本、每条摘要必须附原文链接、不确定就标注「未确认」。

**4. 分发。** 日报输出为 Markdown，一个 webhook 推到 IM，同时落盘到笔记仓库，方便回溯某天结论的依据。

## 踩坑点

- **全文抽取别省。** 很多 feed 正文混着导航和脚本，直接进模型既浪费又干扰摘要，先过一遍正文抽取。
- **编码和日期是大坑。** 部分源的 date 字段格式不规范，排序会乱，入库时统一 UTC，兜底用「抓取时间」。
- **cron 任务会重叠。** 抓取耗时超过调度间隔时任务堆积，加了 lock 文件才稳。
- **摘要漂移。** Prompt 改动后质量波动明显。我把原始条目全部留在库里，改 prompt 后可以离线重放对比，而不是只凭当天的感觉下判断。

## 可复用建议

- 管线三段（抓取 / 摘要 / 分发）进程解耦，任何一段失败可单独重跑；
- 原始条目永远比摘要值钱，先落库再处理；
- 成本控制优先做规则过滤，LLM 只处理打过分的条目；
- 从 10–20 个源起步，跑稳一周再扩，不要一上来 200 个源。

## 总结

这套管线的核心不是「AI 替你读新闻」，而是把信息流的控制权拿回来：源可裁剪、质量可回放、成本可估算。OpenClaw 在这里承担调度和摘要两段，抓取与去重都是普通工程手段。跑通之后，每天的输入从「刷几十个 tab」变成「扫一份带链接的日报」，值得为它花一个周末。
