# 背景

在 OpenClaw 里，cron 是最常用的自动化入口：每天定时汇总日志、巡检服务、生成简报。很多人把 cron 的 instruction 当成一句普通聊天指令来写——“每天早上帮我看下日志”。交互场景这样写没问题，因为你在场，agent 可以追问。但 cron 触发时没有人在场，这一句话就是任务的全部上下文。

# 问题

cron 任务和交互对话有三个本质区别：

1. **冷启动**：没有前文，agent 不知道自己为什么被调用，也不知道“上次”发生了什么。
2. **无人值守**：想追问没人回答，想确认没人确认，只能自行发挥。
3. **可能重复**：调度会重试、会延迟，甚至和上一次执行重叠。

对应到实际故障，就是重复告警、静默失败、时间区间算错、任务越跑越偏。

# 做法：按六段结构写

我现在的模板分六段，按顺序填：

1. **自报家门**：开头写明“这是一次定时触发任务，计划每天 08:00 触发”，并让 agent 先取当前时间再计算统计区间，避免“今天”这种模糊表述。
2. **输入来源**：要读哪些文件、调哪些 MCP 工具，路径写全、范围写死。不写“参考之前的结论”。
3. **动作边界**：明确做什么，也要写不做什么。巡检类任务我会加“只读，不修改任何文件”。
4. **输出契约**：结果写到哪、异常发到哪，正常简报和异常告警分别长什么样。
5. **幂等规则**：写清如何判断“这事已经做过”，比如当日标记文件存在则跳过。
6. **失败出口**：工具失败重试几次；最终失败必须留痕，而不是什么都不剩。

一个简化的每日日志简报示例：

```text
[定时任务] 计划每天 08:00 触发。
1. 先获取当前日期，统计过去 24h 内 /logs/app/ 下的 ERROR 日志。
2. 只读，不修改任何文件。
3. 正常：写入 /reports/daily-YYYY-MM-DD.md，含错误总数、TOP3 报错、环比。
4. 异常：ERROR 超 100 或日志缺失时，额外发一条告警。
5. 幂等：当日报告文件已存在则直接结束，不重写。
6. 工具失败：重试 2 次，仍失败则写 /reports/failed.log 后结束。
```

# 踩坑点

- **对话语气**：写成“帮我看看……”agent 容易停下来等人或自由发挥。cron 里要用祈使句加编号步骤。
- **依赖会话记忆**：调试时口头交代的约定，冷启动时大概率不在上下文里。约定要么写进 instruction，要么落成固定文件并指名读取。
- **时间假设**：“检查今天的日志”在时区差异或调度延迟下会算错区间，务必让 agent 先取时间。
- **输出没人消费**：有任务跑了两周才发现结果一直写进没人订阅的会话，上线前先确认输出真的能被看到。
- **一任务多职责**：一个 instruction 塞五件事，排查起来非常痛苦。一个 cron 只做一件事，要组合就编排多个任务。

# 可复用建议

- 新任务上线前几天保持详细输出，每步结果落日志文件，稳定后再精简。
- instruction 顶部加一行版本注释，改版先 diff，并手动触发一次验证，别直接上线。
- 结果优先落文件再发消息：文件是事实来源，消息只是通知。

# 总结

cron 的 instruction 本质是在给一个没有上下文、无人值守、可能重复执行的执行者写操作手册。自包含、幂等、输出有契约、失败有出口——这四点做到，定时任务才算从“碰运气”变成“可运维”。
