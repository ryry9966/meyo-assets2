## 背景

Agent 本体只负责推理和决策，真正"落地"的动作几乎都发生在外部调用上：查数据、发消息、触发任务。OpenClaw 的思路是把 LLM 的规划能力和工具执行解耦，工具面支持直接注册 HTTP 工具，也支持通过 MCP 接入标准化服务。这篇文章记录我们把十几个外部服务接进 OpenClaw 的过程，重点不是"怎么调通"，而是"怎么调稳"。

## 问题

最初的做法很朴素：把 API 文档摘要塞进系统提示词，让模型自己拼请求。跑 demo 没问题，进了生产就接连翻车：

- 模型会编造不存在的参数值；
- 上游偶发 5xx，agent 拿到原始报错后开始自由发挥，输出不可控；
- 一个写接口被重试了三次，产生了三笔重复工单；
- 调试日志里直接打出了完整的 Authorization 头。

根因都一样：我们让模型直接面对了原始 API，而"握手"里属于工程的部分——鉴权、重试、校验、降级——没有一层兜底。

## 做法

我们的经验是分四步，每一步都在压缩模型自由发挥的空间。

**1. 收敛工具粒度。** 不要把一个服务的 30 个端点全注册成工具。按 agent 实际任务拆，通常 3~5 个足够。粒度越细，schema 越含糊，选错率越高。

**2. 写严格的工具 schema。** 参数用枚举而不是自由字符串，必填项标清楚，description 写"什么情况下用这个工具"，而不只是"这个工具是什么"。模型选工具基本靠 description，这部分值得花时间打磨。

**3. 中间加一层薄适配器。** 不让模型发出的请求直达上游，而是在 OpenClaw 的工具实现里统一处理：超时 10 秒封顶；只对幂等的 GET 做重试；返回体先裁剪再回给模型，比如只取列表前 20 条加一个 total。错误也翻译成结构化的 `{code, message, hint}`，而不是把整段堆栈丢回去。

**4. 用 MCP 管理有状态的服务。** 对需要维护连接、有会话概念的服务（数据库、消息队列），走 MCP server 接入，把状态留在 server 侧，工具本身保持无状态。这样 OpenClaw 重启或上下文重置，连接不跟着断。

## 踩坑点

- **写接口必须显式声明非幂等。** 我们在工具 description 里写明"调用会创建真实资源"，并在适配器对所有 POST 加请求去重键，模型层面的重试直接被网关拦掉。
- **返回体膨胀是最常见的隐性炸点。** 一个看似无害的查询接口返回几千条记录，几轮对话就把上下文吃满。裁剪规则写在适配器里，别指望模型自己省着用。
- **密钥只走环境变量。** 工具实现里读环境变量，日志统一脱敏。见过把 key 写进工具配置再随仓库提交的，这个坑不值得踩第二次。
- **上游 schema 变更要有人兜底。** 给关键服务加一个每日探活任务，用固定参数打一遍，返回结构变了就告警，通常比用户报障早半天。

## 可复用建议

收敛成三条原则：**模型只做选择，工程负责执行；错误必须结构化回传；一切出网请求有超时、有日志、有上限。** 满足这三条的对接，基本都能平稳跑过第一周。

## 总结

对接外部服务不难，难的是把"模型的自由度"和"系统的确定性"划清边界。OpenClaw 提供了工具注册和 MCP 两条接入路径，但真正决定稳定性的是你在中间那层适配器里写了多少约束。握手是双向的：API 提供能力，你提供护栏。
