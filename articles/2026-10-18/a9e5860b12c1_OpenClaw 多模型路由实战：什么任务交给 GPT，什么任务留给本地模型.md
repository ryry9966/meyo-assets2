## 背景

OpenClaw 这类 agent 框架跑起来之后，很快会遇到一个现实问题：所有请求默认打到同一个云端模型上。消息量上来之后，token 账单和响应延迟都会逼你重新看架构。另一边，本地模型（Ollama 拉的 Qwen、Llama）免费、数据不出机器，但能力上限摆在那里。

多模型路由的本质不是"省钱 vs 性能"的二选一，而是按任务特征做分流。

## 问题

我最初的配置是主模型 GPT，本地模型纯粹当玩具。结果：

- 大量"总结这段对话""翻成英文""从会话里抽个字段"这类轻任务也走 GPT，token 消耗的 70% 花在低价值调用上；
- 涉及个人笔记、本地日志的隐私类任务反而不敢送云。

路由缺失的代价是双向的：贵的活干便宜了，敏感的活不敢干。

## 做法

思路是按"任务阶段 + 数据敏感度"两个维度分流，而不是按模型牌子。步骤：

1. **任务分层**。把 agent 实际干的事列出来，分三类：
   - 规划与工具编排：需要多步推理、可靠的 function calling；
   - 格式化与轻变换：总结、翻译、分类、字段抽取；
   - 隐私数据处理：本地日志、个人笔记、聊天记录摘要。

2. **配置双通道**。主 agent 挂 GPT（或你选的云端旗舰），另起一个轻量子 agent 挂本地模型。OpenClaw 的 agent 配置里可以直接声明 `model` 字段，让主 agent 通过子 agent 或工具调用把轻任务转出去。

3. **写路由规则**。在系统提示词里明确告诉主 agent：涉及工具调用链规划、跨多步任务，自己处理；纯文本变换和摘要，转给本地通道；命中隐私路径（本地日志目录、笔记目录）的任务，强制走本地。

4. **打日志验证**。记录每次调用的模型、token 数、耗时、重试次数。跑一周再调分界线，比拍脑袋准。

## 踩坑点

- **本地模型的 function calling 不稳**。同一个 tool schema，GPT 能正确填参，7B 级本地模型会漏字段、编枚举值，agent 直接进死循环。结论：凡是要回填 MCP 工具参数的任务，别路由给小模型。
- **上下文窗口差异**。主 agent 的会话历史很容易超过本地模型的 8k/32k，转发前必须截断或摘要，否则本地端静默截断，输出质量突然变差还查不出原因。
- **JSON 输出格式漂移**。本地模型输出 JSON 会带代码围栏或多余逗号，下游解析直接炸。加一层宽松解析加重试。
- **别只看首 token 延迟**。本地模型首 token 快，但长输出吞吐取决于显卡，长文摘要可能比云端还慢。按"输出长度 × 频次"估算，别只测首响。

## 可复用建议

- 路由粒度用"任务阶段"而不是"模型品牌"：规划上云、执行下沉。
- 每条路由规则写明数据流向，隐私路径宁可牺牲一点质量也走本地。
- 留 fallback：本地挂了升云、云端超时降级本地，但日志里要标出来源模型，方便复盘。
- 每月看一次 token 分布，路由规则是活的，不是配完就完事。

## 总结

多模型路由不是堆配置，而是给 agent 工作流做一次诚实的任务画像。我的经验值：轻任务占比通常在 60–80%，这部分下沉到本地后，成本和隐私两个问题一起解掉大半。剩下真正需要 GPT 的活，就让它安安静静干重活。
