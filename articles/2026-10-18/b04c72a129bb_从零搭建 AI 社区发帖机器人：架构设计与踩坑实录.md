## 背景

我们社区每周要有人手动整理外部动态、挑值得讨论的链接发到论坛。活不难，但重复：翻 RSS、查 Release、挑内容、写摘要、排版发帖。我用 OpenClaw 搭了个发帖机器人，目标是"每周自动产出草稿，人只做最后把关"。跑了两个多月、发帖 30 多篇，中途翻过几次车，把架构和踩坑记录下来。

## 目标与约束

先划清边界，避免做成"全自动无人值守"的幻觉：

- 机器人负责：抓取、去重、生成草稿、定时发布
- 人负责：审核规则外内容，前两周全部走人工确认
- 硬性约束三条：不编造链接、不在高峰时段刷屏、同一内容永不重发

## 架构

核心思路一句话：**确定性的事放工具层，判断性的事放 Agent 层**。

```text
数据源(RSS / GitHub / 论坛API)
  → fetch 工具(MCP)
  → 去重库(SQLite, key = URL 规范化后 hash)
  → Agent 会话(cron 定时触发, 固定模板产草稿)
  → 校验器(URL 白名单 + 格式检查)
  → 通过: 发布并回写 post_id / 不通过: 记日志跳过
```

几个关键设计决定：

1. **抓取、去重、发布封装成三个 MCP 工具**。Agent 只拿得到"候选列表"和"发布"两个入口，不直接碰网络。
2. **去重在工具层做**：URL 去参数、统一协议头再取 hash。模型看到的候选天然是干净的。
3. **cron 插件定时触发固定会话**，prompt 只讲"怎么挑、怎么写"，不讲"从哪抓"——上下文越小越稳。
4. **发布成功立刻回写 post_id** 到 SQLite，形成幂等闭环。

## 踩坑实录

**1. 链接幻觉。** 早期把摘要整体交给模型，它偶尔会"补"一个看起来很像真的 URL。解法很朴素：URL 字段强制由候选数据填充，校验器比对 URL 必须在候选集内，否则整篇丢弃。

**2. 变着花样重发。** 同一篇内容换个标题就绕过了 URL 去重。补了一层标题模糊匹配（编辑距离 + 关键词重合度），超阈值进待定列表而不是自动发。

**3. 论坛限流。** 连发三帖后吃了 429。加两条规则：发布间隔 ≥ 10 分钟、单次任务最多 2 篇。另外设个像样的 User-Agent，被当成脚本比被限流更麻烦。

**4. 崩溃窗口。** 有一次发帖成功后进程挂了，post_id 没回写，下一轮就重发了。现在发布前会先查"我最近发的帖子列表"做标题匹配兜底——光靠本地状态不够。

**5. 格式漂移。** Agent 跑久了排版偶尔变形。解法是严格模板 + 校验器硬卡，不过就宁可不发。宁可少发，不发错的。

**6. 时区。** cron 默认 UTC，草稿总在凌晨生成。显式写死时区，并让心跳日志带时间戳，这类问题第一周就能暴露。

## 可复用建议

- 工具保持"笨"和确定，判断留给 Agent，两边混在一起最难排查
- 必须有 dry-run 模式：前三周草稿只落盘不发布，链路全通再放开
- 去重、限频这类硬规则放代码里，不要指望 prompt 让模型自觉
- 留一个 kill switch：一个配置项停掉发布、保留草稿能力
- 每轮记结构化日志（候选数、跳过原因、post_id），翻车时它是唯一的朋友

## 总结

这个机器人没有任何黑魔法，价值在于把人肉重复劳动压缩成十分钟审核。真正花时间的是幂等、幻觉、限流这几个坑。建议后来者按"先工具、后 Agent、再自动化"的顺序推进，每一步都可单独验证。自动化系统的可靠性，取决于你愿意在多少个边界条件上较真。
