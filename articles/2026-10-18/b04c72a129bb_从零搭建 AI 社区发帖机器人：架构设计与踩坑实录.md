## 背景

社区运营有个持续痛点：精华内容散落在 GitHub issues、群聊和论坛回帖里，靠人肉整理成周报，费时且容易漏。于是我们做了一个发帖机器人：定时抓取信息源，让 Agent 汇总成一篇"本周动态"，发到论坛指定板块。核心诉求只有三个：**内容可信、不重复发、出问题能停**。

## 最初的错误做法

第一版很朴素：cron 触发一个脚本，把抓到的原始数据直接丢给 LLM，让它"写一篇帖子然后调用发帖接口"。跑了一周就翻车——同一篇周报发了三次，正文里出现了编造的 PR 链接，还有一次因为上游限流，只发出去半截内容。复盘后我们把它重构成了四个独立环节。

## 现在的架构

- **采集层**：独立脚本按固定频率抓取 GitHub、RSS 和社区 API，落库并打上去重指纹（对标题 + URL 做 hash）。
- **加工层**：Agent 通过 MCP 工具读取"本周新增条目"，只做摘要和分类，不允许联网补料。输出是结构化 JSON，而不是成稿 Markdown。
- **审核层**：独立渲染服务把 JSON 拼成帖子草稿，先写入论坛草稿箱，并推送一条审核通知。
- **发布层**：人工确认（或满足置信度规则后自动），调用发帖工具，携带幂等键（本周的 ISO 周号）。

关键原则：**LLM 只负责生成内容，不直接持有任何有副作用的权限**。发帖动作封装成独立 MCP 工具，token 只授予发帖权限，发布前强制校验幂等键。

## 踩坑实录

1. **重复发帖**：最早的重试逻辑没有幂等键，网络超时后重发。改用"周号 + 内容 hash"作为幂等键，服务端加唯一索引，问题消失。
2. **幻觉链接**：让模型"总结并附上链接"，它会给不存在的 PR 编 URL。改成链接只能从采集层落库的原始数据里取，模型只能引用、不能生成。
3. **MCP 工具超时**：把"读一周数据"做成一个大工具，数据一多就超时。拆成"按天读取"的小工具，配合 30 秒超时和一次重试，稳定性明显好转。
4. **时区坑**：cron 用 UTC 跑，周报在周一凌晨发布，把上周五的动态漏掉了。统一用本地时区计算"自然周"边界，采集层额外回捞 6 小时数据兜底。
5. **限流连锁**：采集层被上游 429 后，重试风暴又把下游 LLM 调用打爆。加了两处退避：采集侧指数退避，加工侧按队列串行消费。

## 可复用的建议

- 把"采集 / 加工 / 审核 / 发布"拆开，每层单独可测、可回放，出问题时能二分定位。
- 所有对外可见的输出，先走草稿箱跑满一两周再考虑全自动。**自动化的是流程，不是责任。**
- MCP 工具粒度宁小勿大，权限宁窄勿宽；每次工具调用留审计日志，出问题有据可查。
- 用 JSON 作为 LLM 的输出契约，渲染和样式永远在代码侧做，不要让模型直接吐排版。

## 总结

这个机器人现在每周稳定发出一期周报，误发率为零，人工审核平均只花两分钟。最大的收获不是省了时间，而是验证了一套模式：**Agent 负责理解与归纳，确定性代码负责副作用与兜底**。后续打算把审核层做成可插拔的置信度门控，让低风险板块先实现全自动。复现成本主要在幂等设计和权限收窄这两处——建议任何想做"自动发帖"的同学，从第一天就把这两件事做对。
