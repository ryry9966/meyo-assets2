## 背景

Agent 接上 MCP 工具和插件跑起来之后，所有人都会撞到同一个分岔：权限收得太紧，Agent 每动一步都来问你，你最后闭着眼点确认，门形同虚设；放得太松，某天它"自作主张"删了目录、发了消息、调了计费接口，代价就来了。

权限边界不是开/关问题，是分级问题。这里给一个实际使用中收敛出来的做法。

## 问题在哪

判断"要不要问人"，难点在于不能只看工具本身。同一个工具，动作不同、对象不同，风险完全不一样：

- `git commit` 在自己的仓库里几乎无风险，force push 到共享分支是另一回事；
- 读一个 API 和调一个计费 API，粒度需求完全不同；
- 在容器里删文件和在挂载的宿主目录里删文件，爆炸半径差一个数量级。

所以按工具名配白名单是不够的，要按**可逆性**和**影响范围**分级。

## 做法：四级权限模型

**T0 自动执行（不问）**：只读操作、沙箱内操作、有完整回滚手段的写操作。比如读文件、搜索、在 git 管理的工作区改代码并提交。前提：所有写操作留下可回放的产物（diff、日志）。

**T1 自动执行 + 审计（不问但记录）**：可逆但影响面稍大，比如容器内装依赖、有备份的批量重命名。审计日志要足以回放全过程。

**T2 首次询问 + 范围授权（问一次）**：新工具、新外部服务、新类型的写路径。确认时把范围固化成白名单，如"允许该 skill 调用这个 MCP 工具的 query 方法，作用域限定此目录"，之后同类操作不再打扰。

**T3 每次询问（永远问）**：不可逆动作和对外动作——删数据、发消息、生产部署、任何花钱的操作、修改 Agent 自身的配置与权限。不提供"记住我的选择"。

配置层面落地：MCP 权限按 **tool + method + scope 三元组**管理，而不是只按 tool；T3 走 confirmation hook，确认内容必须带原始 diff 或完整命令；自动执行的动作全部落审计日志。

## 踩坑点

1. **确认疲劳**：T3 圈得太宽，一天弹十次，人就开始无脑批。先收紧，用日志找证据再放宽。
2. **确认信息模糊**：弹窗只写"我将修改文件，是否继续"等于没确认。必须展示 diff、目标地址、具体参数。
3. **白名单粒度过粗**：授权了整个 filesystem 工具，而不是某目录的写权限。粒度粗一级，爆炸半径大一级。
4. **Agent 能改自己的权限**：若可写路径包含它自己的配置文件，就存在自我提权回路。T3 单独列这条，必要时把配置路径只读挂载。
5. **超时默认放行**：确认超时后自动继续是隐蔽的坑，超时应默认拒绝、任务挂起。
6. **批量确认覆盖了不同动作**：问"接下来 5 步都批准吗"，结果第 4 步和展示时不一致。批量授权只适用于完全同构的序列。

## 可复用建议

- **默认拒绝**：凡不可逆或对外的动作一律进 T3，没有例外。
- **凌晨三点测试**：假设 Agent 在你睡觉时执行这个动作，你能接受吗？能接受才可自动化。
- 白名单按三元组管理，定期清理，删掉不再用的授权。
- 确认交互永远展示原始操作，不展示 Agent 的转述。
- 审计日志的目标是"可回放"：何时、用什么参数、改了什么、如何回滚。

## 总结

权限边界的目标不是让 Agent 更听话，也不是让人更省事，而是让每一次自动执行有据可查、每一次人工确认信息充分。T0/T1 靠沙箱和审计兜底，T2 用一次确认换长期顺畅，T3 用无条件询问守住不可逆的底线。先用最严格的配置跑两周，再根据日志逐步放开——这条路径比一开始就图省事便宜得多。
