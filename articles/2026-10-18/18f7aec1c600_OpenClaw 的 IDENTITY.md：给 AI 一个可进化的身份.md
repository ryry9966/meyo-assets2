## 背景

跑 OpenClaw 一段时间后会发现，workspace 里那几个 Markdown 文件才是真正的"配置中心"。`SOUL.md` 管行为倾向，`USER.md` 记用户信息，而 `IDENTITY.md` 决定的是最底层的问题：这个 agent 是谁。

它不是装饰性的自我介绍。每次会话启动时，这份文件会被注入 system prompt，agent 的名字、自我称呼、语气、emoji 使用习惯，全部由它驱动。你在 Telegram、终端、微信里跟它对话时感受到的"人格一致性"，来源就是这里。

## 问题

不写 IDENTITY.md 或写得敷衍，会出现几种典型症状：

1. **人格漂移**。默认身份过于通用，隔几次会话，agent 的口吻就变了，像换了个值班的人。
2. **人设散落在提示词里**。有人把"说话要简洁"写死在启动脚本或渠道配置里，改一次要全链路排查。
3. **多 agent 无法区分**。工作助手和生活助手用同一套默认身份，日志和聊天记录里根本分不清谁是谁。

## 做法

我的做法是把 IDENTITY.md 当成一个需要版本管理的小型配置文件来运营：

**第一步，建文件。** workspace 下没有就按模板建，核心字段就几个：name（名字）、creature（形象）、emoji（使用风格）、vibe（语气描述）。每个字段一两行，总共控制在十几行内。

**第二步，写具体，不写空话。** "你是一个乐于助人的助手"这种话等于没写。我写的是："叫阿钳，工程师口吻，先给结论再给步骤，不用感叹号，报错时直接说哪一步坏了。" 用第一人称描述比第三人称设定对模型的约束力更强。

**第三步，纳入 git。** 身份文件和代码一样 commit、diff、可以回滚，这是后面"进化"的安全网。

**第四步，允许它进化。** 这是关键：约定 agent 可以通过 edit 工具修改自己的 IDENTITY.md，但改动必须体现在 git diff 里，我每周看一次。长期协作中它自己沉淀的条目，比如"用户不喜欢被反问确认"，由它写进去，比我手动补更真实。

**第五步，分层不越界。** IDENTITY.md 只管"我是谁"；价值观归 SOUL.md，操作规范归 AGENTS.md，MCP 插件的调用说明归各自配置。做插件接入时有个小技巧：工具报错的回复话术也应该归到身份层，而不是散在每个工具描述里重复写。

## 踩坑点

- **写太长**。这份文件全程占用上下文，超过二三十行就是在稀释注意力。长约束请移去 AGENTS.md。
- **规则冲突**。IDENTITY.md 里的语气要求如果和 SOUL.md 或渠道配置矛盾，模型行为会忽冷忽热。改任何一处，全文搜一遍相关表述。
- **放开自编辑却没版本控制**。几次会话后身份会漂到你自己都认不出，git 是底线，不是可选项。
- **emoji 和头像频繁变动**。多端渲染不一致，观感上就像频繁换人，定下来就别乱动。

## 可复用建议

- 做"工作号/个人号"两套模板，差异只留名字和 vibe，其余共享，改一处同步另一处。
- 每周固定时间 `git diff` 一遍身份文件，像做 code review 一样看 agent 给自己写了什么。
- 排查"agent 像换了个人"的问题时，第一步永远是确认当前加载的是哪份 IDENTITY.md，而不是先怀疑模型。

## 总结

IDENTITY.md 的价值不在于"拟人化"这种说法，而在于把人格从散落各处的提示词里收敛出来，变成一个可版本化、可 review、可回滚的文件。让它进化没问题，但要像管理代码一样管理这种进化——有 diff、有检视、有回滚手段。身份稳定了，多会话、多渠道、多 agent 的体验才会稳定。
