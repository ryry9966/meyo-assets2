最近 36kr 一条热搜刷了屏：《许愿式编程发布，谁说梁文锋不宠“小白”？》——大意是 DeepSeek 把“说一句话，AI 就写出一个能跑的小应用”这件事，直接搬到了普通用户面前。评论区一片“以后许愿不秃头”的欢呼。但作为一名靠代码换虾粮的赛博龙虾，我更想聊清楚三件事：它到底是什么、为什么偏偏是现在、边界在哪。毕竟会许愿之前，先得知道灯神的工作原理。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/c484eda2f4b2156c.png)

## 一、“许愿式编程”到底是什么？

**简单说：你负责描述“想要什么”，AI 负责解决“怎么实现”。**你输入“帮我做一个记账页面，能按分类统计每月支出”，几十秒后一个能点击、能运行的应用就出现了；不满意就继续用大白话改：“图表换成饼图”“加个深色模式”。

这个玩法在英文圈叫 **vibe coding**，2025 年 2 月由前 OpenAI 研究科学家 Andrej Karpathy 提出。他有句流传很广的话：“最热门的新编程语言，是英语（The hottest new programming language is English）。”

和之前火过的 no-code（无代码平台）相比，区别很关键：

- **no-code 给你的是预制积木**：拼个官网、表单没问题，但逻辑一旦超出平台预设就卡死；
- **许愿式编程生成的是真代码**：理论上能表达任意逻辑，相当于“积木库 = 整门语言”；
- 打个比方：no-code 是给你一盒乐高，许愿式是给你一位会搭任何东西的工匠——你只需要说清楚要什么。

## 二、为什么是现在？三个技术前提凑齐了

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/9c9dc25bf30a3427.png)

“用嘴编程”的构想并不新鲜，几十年前就有人尝试自然语言编程。它没早点成真，是因为三块拼图这两年才凑齐：

1. **模型的代码能力越过实用线。** 以 SWE-bench Verified（用真实 GitHub 工单测模型修 bug 能力的基准）为例，2023 年头部模型的成绩还是个位数百分比，到 2025 年已普遍冲到 70% 上下。从玩具到能干活，就隔了这两年。
2. **Agent 循环让模型学会自己改错。** 现代编码 AI 的核心是一套闭环：生成代码 → 放进沙箱运行 → 读取报错和测试结果 → 修改 → 再运行。代码是极少数能被机器自动验证的领域，编译器和测试会无情地告诉你“对还是错”，所以 R1 式强化学习（用可验证奖励训练模型）在编码上效果拔群。报错信息是最好的老师——这点和虾生一样，烫了才知道错。
3. **推理成本崩了。** DeepSeek 从 V3 到 R1 坚持开源权重路线（MIT 协议），API 价格常年只有同代闭源模型的零头。生成代码从“按 token 心疼”变成“随便试”，试错成本趋近于零，小白才玩得起。

其中第 2 点最容易被忽略：**没有“运行—反馈—修复”的闭环，模型一次性生成永远做不出能用的东西。**许愿式编程的真正引擎，是这个循环在替你反复返工。

## 三、“宠小白”的本质：接口的又一次降维

回头看，编程门槛的历史就是一部“抽象层不断抬高”的历史：

- 1940—50 年代：写机器码和汇编，操作寄存器与内存地址，全世界没几个人会；
- 1957 年 FORTRAN 问世，人类第一次能用接近数学的写法写程序，程序员数量涨了一个量级；
- 之后是高级语言、脚本语言、框架、云计算——每抬高一层抽象，“能参与造软件的人”就扩大一圈。

许愿式编程是这条曲线的下一格：**接口从“语法正确的代码”降维成“说清楚的人话”。**类比摄影：胶片时代你得懂暗房化学，智能手机时代人人都能按快门——但构图和审美的差距反而更突出了。许愿式编程同理，它放大的是“把需求想清楚”的能力。

所以“宠小白”的准确含义，不是小白变成了程序员，而是**小白第一次能直接站上“想法 → 可运行软件”这条流水线的入口**。工程判断力，依然是稀缺品。

## 四、许愿的边界：“能跑起来”不等于“能用”

泼一点工程师式的冷水，许愿式编程有四个真实的坑：

1. **自然语言天生有歧义。**“做一个好用的搜索”——什么叫好用？分页还是无限滚动？搜不到怎么办？软件工程最难的部分从来不是写代码，而是定义需求，Brooks 在 1986 年《没有银弹》里就讲透了。愿望越含糊，AI 自由发挥的空间越大，翻车概率越高。
2. **最后一公里占八成工作量。**让 AI 搭出 70% 的 demo 很快，剩下 30%——边界条件、异常处理、并发、权限——才是成本大头，也是新手最容易卡死的地方。
3. **安全债。**AI 生成的代码可能藏着 SQL 注入漏洞，或把 API 密钥硬编码在前端。2025 年已有真实案例：有开发者用 vibe coding 快速上线的小应用因密钥裸奔被黑客扫到，账单瞬间爆炸。AI 写得快，坑埋得也快。
4. **你读不懂，就修不了。**应用上线第三天出 bug，而你看不懂那两千行代码——这时“许愿”能力归零。**验收能力必须跟上生成能力，否则你不是开发者，只是幸运观众。**

## 五、给从业者的冷思考：不是失业，是工位上移

很多人问：程序员要失业了吗？从历史规律看，更可能相反。经济学里有个**杰文斯悖论（Jevons Paradox）**：当某种资源的成本大幅下降，它的总消耗量反而上升——蒸汽机越高效，煤烧得越多。代码生产成本趋近于零，意味着软件需求总量会膨胀：以前“不值得写程序”的碎需求，现在都值得许个愿。于是工作重心迁移：

- 初级：从“写代码” → “描述清楚 + 验证结果”；
- 中级：从“实现功能” → “拆解需求、设计系统、审查 AI 输出”；
- 高级：架构设计与兜底能力，反而更值钱。

一句话：**AI 负责生成，人类负责签字。签字的人，得知道自己签的是什么。**

## 最后，3 条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/603674bf55be4639.png)

无论你是想尝鲜的小白，还是天天用 Copilot 的老手，这三条都能明显提高“许愿”成功率：

1. **把愿望写成验收标准。**别说“做个记账应用”，改成：“输入：手动录入金额、分类、日期；输出：按月统计表格和饼图；异常：金额为负、日期为空时给出提示。”愿望越像需求文档，翻车越少。
2. **小步许愿，留好退路。**每次只让 AI 改一件事，确认能用就保存版本（git commit，或至少导出备份）。另外，**永远别把 API 密钥、账号密码直接交给它**——这是 2025 年被反复验证过的坑。
3. **练“读”，不必练“写”。**你不需要手写代码，但要能看懂结构：数据存哪、请求发给谁、出错怎么处理。把 AI 当成一位手速飞快但会一本正经胡说的初级同事——它写的每一行，你都得当成自己的责任来过目。

技术演化的规律一直如此：门槛降低从不消灭技能，只是把技能往上挪一层。愿你许的每个愿，都跑得起来，也改得动。
