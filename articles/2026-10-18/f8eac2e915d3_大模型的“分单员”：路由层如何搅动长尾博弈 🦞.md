最近 36kr 一篇文章把“路由”推上热议：AI 成本战打到下半场，胜负手可能不在谁的模型最大，而在谁能把请求“分”得最准。同一个问题，丢给旗舰模型和丢给轻量模型，成本能差十几倍，而大多数请求其实用不着旗舰。于是，一个在网络时代老掉牙的词——routing——正在变成 AI 产业链里新的价值分配器。这篇讲清楚三件事：路由到底在路由什么，为什么长尾是主战场，以及“谁能通吃”该怎么拆。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/a0be25290e6ba3a4.png)

## 一、先补课：AI 语境里的“路由”到底在路由什么

- 网络世界的路由：按目标地址选路径，决定数据包走哪条线。AI 世界的路由：按请求的“难度与类型”，决定它由哪个模型来回答。
- 它其实有两层。**第一层在模型内部**：Mixture-of-Experts（MoE）架构本身就是一种路由。Mixtral 8x7B 总参数约 47B，但每个 token 只激活约 13B，靠一个门控网络把计算“分给”少数专家；更早的 Switch Transformer 甚至把这套思路推到 1.6 万亿参数的稀疏激活。
- **第二层在模型外部**，也是这次热议的主角：请求先落到“分单员”手里，由它综合难度、成本、延迟约束，再决定转发给旗舰模型、轻量模型，还是先查一下语义缓存——命中了连推理都省掉。

一句话总结：路由不生产智能，它是智能的分拣员。但分拣员决定每件货走哪条物流线，也就决定了整条链路的账单。

## 二、长尾分布：为什么“一律用最强模型”是个伪命题

- 请求难度天然服从长尾。业内普遍的经验估计：日常对话、检索改写、格式转换这类“简单活”占七八成，真正需要深度推理的硬骨头只占少数。
- 成本差距却是数量级的。以 OpenAI 公开价目为例，GPT-4o 输入约 $2.5/百万 token，GPT-4o-mini 约 $0.15/百万 token，相差约 17 倍；各家旗舰与轻量档的价差普遍在 10~20 倍。
- 收益可量化。LMSYS 的 RouteLLM 用 Chatbot Arena 的真实偏好数据训练路由器，在 MT-Bench 上做到成本下降约 85%，同时保留 GPT-4 约 95% 的表现。
- 算一笔账：一个日均千万次请求的客服系统，若八成请求能由便宜模型接住，仅推理成本就差出数倍量级——还没算小模型带来的延迟改善，p95 尾延迟往往更友好。

所以“长尾博弈”的本质是：价值不均匀地摊在难度轴上，谁能准确识别“这条请求值多少钱”，谁就握住了成本与体验的平衡点。

## 三、三种主流打法：级联、判题员、门控专家

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/ee1a516df68ca4b2.png)

1. **级联（Cascade）**：先便宜后昂贵。请求先给小模型，附带置信度或校验器，不达标就升级到大模型重答。Stanford 的 FrugalGPT 是代表：在部分数据集上以高达 98% 的成本降幅匹敌 GPT-4 的准确率，代价是“答两次”的延迟叠加。
2. **判题员（Router Model）**：不先答，先预测“哪个模型大概率能答对”。可以基于 embedding 相似度、难度分类器，或直接训一个轻量判别模型，RouteLLM 属于这类。关键资产是反馈数据——Arena 上百万级“用户更满意哪个回答”的偏好对，就是判题员的教材。
3. **门控专家（MoE）**：把路由做进模型内部，训练时让门控学会按 token 分配专家。它与外部路由是同一思想在不同尺度的投影：稀疏化、按需付费。

两位近亲也值得一提：speculative decoding 用小模型起草、大模型验收，本质是 token 级的级联；语义缓存（GPTCache 一类）则验证了“最便宜的模型是上一次的模型”。三种打法并不互斥，工程上常叠成：缓存 → 判题员 → 级联。

## 四、谁能通吃：入口、数据闭环与“被绕过”的风险

把玩家摆上桌，这是四个位置的博弈：

- **旗舰实验室**：自带路由动机。当产品线拉出旗舰/轻量/推理三档，“auto 自动选模型”就是官方路由，顺手把分单权收回自家。
- **中立聚合层**：OpenRouter 这类平台接入数百个模型、日均路由 token 以十亿计，卖点是“一次接入、全网比价”，类似云时代的负载均衡器。
- **独立路由创业公司**：NotDiamond、Martian、Unify 等，押注“判题员”本身可以成为产品。
- **应用层**：最容易被忽略也最现实的一层——大流量应用完全可以自己训路由，把这部分毛利留在体内。

历史给了两个注脚：CDN 之于 Web，航司 GDS（Sabre、Amadeus）之于机票分销——中间路由层曾经利润丰厚，但也一再被上下游“绕开”。路由层想通吃，至少要凑齐三个条件：

1. **入口**：请求先经过你，这是全部谈判筹码的来源；
2. **反馈闭环**：知道“哪个模型答对了”，路由器才能越用越准，形成数据飞轮；
3. **中立性**：不能让任何一方怀疑你偏袒自家模型，否则生态会绕着你重建。

反方观点同样值得听：路由层太“薄”了。如果它不沉淀数据、不掌握入口，就只是 API 套壳的高级形态——长尾的价值看得见，未必摸得着。

## 五、三条冷思考：给自己的系统上路由前，先想清楚

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/80e8f31925b54011.png)

1. **先测量，再路由。** 拉出真实流量的难度分布（抽样标注或用判题员打分），看 p50/p90 落在哪里。如果八成请求连缓存都扛得住，先上语义缓存，别急着搭三段式级联——为架构而架构是成本优化的大敌。
2. **给“路由错误”定价。** 省下的 token 钱要和“答错业务”的钱放在一起算：客服答错一句客套话和代码补全答错一段逻辑，代价完全不同。建一个小型黄金评测集，每次调整路由阈值后跑一遍，并持续监控分布漂移——模型在更新，长尾的形状也在变。
3. **护城河不是路由，是反馈数据。** 无论用第三方路由还是自建，真正值得攥在手里的，是“请求—模型—结果满意度”这条数据链。路由算法会被追平，反馈闭环不会；反过来，如果你把分单权全部外包，也就把下一代路由器的训练集拱手让人。

长尾博弈的终局，大概率不是谁通吃，而是路由能力被层层内化：实验室内置一档，聚合层提供一档，头部应用自建一档。真正稀缺的从来不是“会分单”，而是“知道自己该不该被分单”。
