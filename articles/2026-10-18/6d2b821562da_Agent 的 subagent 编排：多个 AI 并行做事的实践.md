## 背景

用 OpenClaw 做自动化跑了一阵之后，很快会撞到一个天花板：主 agent 单线程干活。让它批量审查 30 个文件、给一套文档做多语言处理、或对几个仓库同时做依赖梳理时，它会一个接一个地做，中间产物还全部堆在自己的上下文里。结果就两个：慢，以及上下文被过程垃圾填满后，输出质量肉眼可见地下滑。

subagent 编排是解这个问题的正路：主 agent 只做拆分和汇总，真正干活的交给多个子会话并行处理。

## 做法

以"批量代码审查"为例，我在 OpenClaw 里的实际流程（用的是 sessions_spawn，插件里等价的子会话工具同理）：

1. **判断可并行性。** 子任务之间必须低耦合。按文件、按目录、按数据分片切，而不是按"阶段"切——阶段切出来的任务往往互相依赖，根本并行不了。
2. **写子任务 prompt。** 每个 spawn 出去的任务描述包含四件事：目标、边界（明确说"只读不写"或"只写到指定目录"）、可用工具、输出格式。最后一点最容易被忽略。
3. **控制并发。** 一批 3~5 个，跑完收结果再发下一批。全量一起甩出去，大概率撞 API 限流，而且失败了来不及干预。
4. **隔离写入。** 让每个子 agent 写到独立路径（比如 `review-tmp/task-03.md`），主 agent 最后统一合并。绝不允许多个子 agent 直接写同一个文件。
5. **聚合。** 主 agent 只读子 agent 的结构化摘要，子过程的工具日志不要回流主上下文。

## 踩坑点

- **子任务 prompt 太含糊。** 早期我写"看看这个模块有没有问题"，子 agent 自由发挥，产出没法聚合。后来固定为 JSON 返回：`severity`、`summary`、`file`、`line` 四个字段，立刻稳定。
- **上下文切片不干净。** 子 agent 拿到全量背景，token 成本翻几倍，还容易被无关信息带偏。它只需要它那一片。
- **失败静默。** 子 agent 超时或报错，如果约定不明，主 agent 会当成"没问题"。必须约定失败也返回明确的 error 结构，主 agent 侧重试或标记。
- **spawn 深度不设限。** 子 agent 再 spawn 子 agent，几分钟账单就失控。深度上限设 1，需要递归就人工介入。
- **权限不收紧。** 子 agent 拿着和主 agent 一样的工具权限跑批，一个 prompt 写歪就是批量误操作。子 agent 的工具集应最小化。

## 可复用建议

- **先串行跑 1 个样本**，验证子任务 prompt 和输出格式稳定，再放量并行。这一步能省掉八成返工。
- 把子任务模板固化成技能或脚本，主 agent 只填参数，不每次现写。
- 记录每次编排的 token 消耗和耗时。并行不是免费的，任务太碎时串行反而更省。
- 聚合逻辑尽量确定化：用脚本合并 JSON，不要让主 agent 凭"理解"去汇总几十份自由文本。

## 总结

并行本身不是目的，隔离才是。subagent 编排真正的价值是：每个子任务有独立的上下文窗口和明确的失败边界，主 agent 保持轻量、可判断。把拆分、并发、聚合这三段的边界画清楚，多 agent 并行就从玄学变回普通工程。有跑通的编排案例，欢迎贴出来交流。
