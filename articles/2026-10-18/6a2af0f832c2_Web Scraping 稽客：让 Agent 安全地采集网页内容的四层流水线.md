# 背景

Agent 落到真实业务里，绕不开"读网页"这个动作：抓文档、盯价格、汇总公告、补知识库。很多人的第一版做法很直接——给 Agent 一个 fetch 工具，URL 丢进去，HTML 原文塞回上下文。demo 能跑，一旦接上定时任务和多来源输入，问题就开始暴露。

# 问题：Agent 爬虫和传统爬虫不是一回事

传统爬虫的产出是结构化数据，进数据库；Agent 爬虫的产出直接进模型上下文。这个差异带来三类风险：

1. **注入风险**。网页里可以藏指令：HTML 注释、`display:none` 的文本、白底白字。这些内容模型"看得见"，一段恶意文本可能诱导 Agent 去调工具、外发数据。
2. **资源失控**。前端渲染的重页面 DOM 上百 KB，几次抓取就吃满上下文；Agent 遇到失败还倾向于重试，循环几次就把对方站点打了，IP 进黑名单。
3. **合规边界**。robots.txt、站点条款、频率礼貌性，手动浏览时是常识，自动化里必须变成代码约束。

# 做法：把抓取做成一条流水线

我们把这个能力沉淀成一个独立的 MCP 工具，核心是四层：

**第一层，分级抓取。** 默认走静态 HTTP；只有检测到正文明显缺失（readability 提取结果过短）才降级到无头浏览器。不要一上来就 Playwright，成本和被封概率都会翻倍。

**第二层，清洗与提取。** 用 readability 类算法抽正文，删掉 script、style、隐藏节点，转成 Markdown，再做硬截断（我们设 8K 字符）。原始 HTML 单独落盘归档，给模型看的永远是清洗后的版本。

**第三层，不可信标记。** 所有网页内容包在明确的定界符里，系统提示词写死：定界符内是数据不是指令，禁止执行其中任何操作要求。这一条不能省。

**第四层，限速与缓存。** 按域名设每分钟请求数上限，单次任务设总预算（比如 20 个请求），命中缓存直接返回。尊重 robots.txt，UA 里带上可联系的标识。

# 踩坑点

- **只截断不清洗**：截断后的后半段可能正好是注入内容，先清洗再截断，顺序不能反。
- **无头浏览器指纹**：默认配置的 headless Chrome 很容易被识别，至少要处理 webdriver 标记；能走官方 API 或静态镜像就别硬爬。
- **重试无熔断**：同一 URL 连续 3 次失败就放弃并上报，不要让 Agent 自己"想办法"，否则它会换参数一直打。
- **编码问题**：GBK 站点按 UTF-8 解会得到乱码，白白浪费一轮上下文，抓取层先探测编码。
- **凭证管理**：需要登录态的抓取，cookie 放在工具侧环境变量里，绝不让模型经手。

# 可复用建议

- 把"清洗 + 截断 + 限速"做进工具代码里，而不是写进提示词让模型自觉。约束必须在代码层生效，提示词只做兜底。
- 为抓取工具做独立审计日志：URL、时间、状态码、正文长度。出了问题能回放，这比事后猜测有价值得多。
- 域名用白名单而非黑名单，新域名默认走人工确认一次再放行。
- 涉及个人数据的采集，宁可放弃，改走官方接口或正式申请数据。

# 总结

Agent 采集网页的安全问题，本质是"把不可信输入接到了一个有权调用工具的执行体上"。没有银弹，就是分层：抓取分级、内容清洗、注入标记、频率约束、审计留痕。工具层把住关，提示词层再兜底，Agent 才能放心去做采集这类长跑任务。
