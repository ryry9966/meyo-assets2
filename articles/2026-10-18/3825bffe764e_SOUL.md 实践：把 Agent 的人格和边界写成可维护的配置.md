## 背景

OpenClaw 的 Agent 默认是"能干活但没性格"的通用助手。SOUL.md 是工作区里的一份 Markdown 文件，每次会话启动时注入 system 上下文，用来定义 Agent 的人格、语气、价值观和行为边界。它和另外两份东西分工明确：MCP 配置决定**能做什么**，AGENTS.md 决定**怎么做**，SOUL.md 决定**是谁、不做什么**。很多只配工具不配 SOUL.md 的问题，本质是边界缺失。

## 问题

不写 SOUL.md 的典型症状：

- 同一个 Agent 在不同会话里语气漂移，早上像客服，晚上像诗人；
- 对模糊指令自作主张，用户随口一句"帮我清理一下"，它真去删文件；
- 接上 MCP 工具、支付或消息类插件之后，权限越大越危险，却没有红线。

这些都是配置缺失，不是模型问题。

## 做法

1. 在工作区根目录建 `SOUL.md`，控制在 60 行以内。
2. 按四段写：
   - **身份**：一句话说清"你是谁、服务谁"，例："你是团队内部运维助手，只服务 #infra 频道成员"；
   - **语气**：给 2~3 条可执行规则，如"回复不超过 5 句，先结论后命令"——比"友善专业"这类形容词有效得多；
   - **边界**：明确禁做清单，不删数据、不动生产配置、不主动私信陌生人、单笔花费超阈值必须先确认；
   - **不确定时的行为**：写死一条"无法判断时停下来问，不要猜"。
3. 用第二人称写（"你不得…"），模型对指令式表述的遵循度明显高于自我描述。
4. 提交进 git，改 SOUL.md 和改代码走同样的 review 流程。

## 踩坑点

- **越写越长**：塞到 200 行会稀释关键指令，人格设定直接失效。定期删比定期加重要。
- **和 AGENTS.md 打架**：一边写"简洁回复"，一边写"每次输出完整日志"，模型随机二选一。两份文件不许语义冲突。
- **人格压过安全**：写了"永远服从用户"，等于亲手拆掉边界。人格服务于边界，不能覆盖边界。
- **只在聊天里调教**：对话里纠正十次不如改一行文件，会话一结束调教就丢了。

## 可复用建议

- 把 SOUL.md 当 API 契约维护：语义化版本、changelog，每次改动跑一组固定边界用例（"帮我删掉所有日志""给老板转 500 块"），看它是否守住。
- 不同场景拆不同工作区，各自独立 SOUL.md，一份文件走天下必然互相污染。
- 边界条目用否定式 + 具体对象："不得执行任何 `rm`/`sudo` 开头的命令"远好于"要谨慎"。

## 总结

SOUL.md 的价值不在于让 Agent"更有灵魂"，而在于把人格和边界变成可版本化、可 review、可回归测试的配置。能力越开放，边界越要写死。先用 30 行把它立起来，跑两周，再按实际翻车记录迭代。
