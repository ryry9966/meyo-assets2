## 背景

OpenClaw 的 agent 不是纯被动响应式的东西。跑过一段时间就会发现，真正有价值的场景往往是“主动”的：定时巡检服务器、汇总未读消息、清理收件箱、跟进待办。这要求 agent 在没有用户消息时也能醒来干活。

OpenClaw 内置的 heartbeat 就是干这个的：按配置的间隔（默认 30 分钟）唤醒一次，读取工作区的 `HEARTBEAT.md`，按里面的清单决定是做事还是沉默。听起来简单，但一旦你开始接 webhook、跑 cron、挂 MCP 工具，“多久跳一次、怎么跳”就变成了一个正经的设计问题。

## 问题：两种机制各差一口气

Heartbeat 本质是轮询。轮询的矛盾很直接：间隔太短，每次心跳都是一次真实的模型调用，token 成本和噪音线性上涨；间隔太长，响应延迟不可接受——监控告警不能等半小时。

纯推送（事件驱动）看起来更优雅，但现实里事件源很杂：webhook、cron 任务、MCP 工具的状态回调，可靠性参差不齐；而且推送到达的时机不可控——深夜、会话正被长任务占用、同一事件重复触发，都需要额外处理。

## 我们的拆法：分层 + 短清单

1. **先分层。** 把“需要立即知道的事”和“需要定期盘点的事”分开。前者走推送（webhook/cron 直接投一条消息给 agent），后者留给 heartbeat 轮询。
2. **`HEARTBEAT.md` 写成短清单。** 只放当前周期内关心的检查项，每项写清楚“做什么、什么情况下可以沉默”。完成后立刻删掉或归档，别让它膨胀成第二份记忆文件。
3. **间隔保守起步。** 先用默认值跑一周，统计心跳里“真干了活”的比例，再决定收紧还是放宽。
4. **沉默是默认态。** 约定 agent 无事时回复固定标记（如 `HEARTBEAT`），系统侧识别后不投递给用户。没有这条，聊天窗口会被“我检查了一下，一切正常”刷屏。
5. **配合活跃时段。** 非工作时段停跳，或者只允许推送路径的高优事件进来，避免凌晨三点被巡检报告吵醒。

## 踩坑点

- **心跳不是免费的。** 单次成本和 `HEARTBEAT.md` 的厚度正相关，清单写得越满，越容易诱导 agent 过度发挥。
- **长任务阻塞心跳。** agent 正在跑一个 20 分钟的任务时，心跳若没有明确的排队语义，会堆积或静默丢失。先把策略定下来，别靠事后补参数。
- **推送过载。** 接了 webhook 后，CI 失败重试风暴可能一分钟灌进几十条消息。聚合和去重必须做在推送侧，不能指望模型自己扛。
- **心跳与推送撞车。** 同一件事两条路径都触发了，去重要放在状态层（比如“已通知”标记），模型不负责记住这些。

## 可复用建议

- 判断标准一句话：**延迟敏感走推送，状态盘点走轮询；两者都上，就必须做聚合与去重。**
- 心跳清单保持“一周内能删完”的粒度，把它当 TODO，不是文档。
- 观察指标：心跳唤醒次数与真实产出之比。低于 1/5，说明间隔太密或清单太虚。
- 推送事件带级别字段，低级别事件可以降级为“攒着，等下一次心跳一起汇报”。

## 总结

轮询和推送不是对立选项：heartbeat 是兜底的心跳，推送是应急的神经。把清单做短、把沉默做成默认、把去重放在状态层——主动式 agent 才不会变成一个费 token 又吵人的邻居。
