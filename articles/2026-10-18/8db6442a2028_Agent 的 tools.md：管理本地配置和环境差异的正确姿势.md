## 背景

Agent 没有跨会话记忆。它对“这台机器长什么样”的全部认知，都来自你每次喂给它的上下文。于是同一个问题反复出现：开发机上跑得好好的任务，换到家里的服务器、容器或 CI 就开始卡壳——路径不对、包管理器不同、Python 版本差一个大版本。很多时候不是 Agent 能力不够，而是它对环境的假设全靠猜。

## 问题

多数人的做法是把环境信息直接塞进系统提示或任务描述，代价很直接：

- 提示词越写越长，大量 token 花在重复描述同一台机器上；
- 多项目、多 agent 各写一份，改一处漏三处；
- 环境变了没人同步，Agent 按过期信息执行，轻则报错，重则自作主张装依赖；
- 偶尔有人顺手把 API key 也写进去，直接送进模型上下文。

根因只有一个：**环境事实缺少单一事实来源**。另外要说明，如果你已经在用 MCP 这类工具协议，tools.md 依然有价值——协议解决“工具怎么调”，tools.md 解决“这台机器上有什么、约定是什么”，两者互补。

## 做法：把环境写成一个 tools.md

核心动作很轻：在项目根目录放一个 `tools.md`，约定 Agent 每次会话先读它。

```markdown
# tools.md

## 环境
- OS: Ubuntu 22.04，shell 为 bash
- Python 3.11（pyenv，项目用 .venv）
- 包管理：uv（不要用 pip install --user）

## 工具路径
- ffmpeg: /usr/local/bin/ffmpeg
- node: ~/.nvm/versions/node/v20/bin/node

## 项目约定
- 测试：pnpm test（不要带 --watch）
- 日志：./logs/ 按日期分文件

## 限制
- 容器内无 sudo，不能 apt install
- 出网走代理 http://127.0.0.1:7890
```

内容原则：只写“几乎每次会话都可能用到”的事实，用短句和列表，字段顺序固定，方便 Agent 快速定位。

**第二步，分层。** 机器级事实（shell、全局工具、代理）放全局层的 tools.md；项目级约定放项目内。冲突时项目层优先，并显式写明覆盖关系，不要留给我 Agent 自行仲裁。

**第三步，让 Agent 参与维护。** 加一条约定：执行中发现工具缺失、路径不对、版本不符，先更新 tools.md 再继续，而不是只在对话里口头修正。这样环境修正会沉淀下来，而不是随会话消失。

**第四步，处理版本控制。** tools.md 入库（不含任何密钥），机器私有差异拆到 `tools.local.md` 并加入 gitignore，加载时合并。

## 踩坑点

1. **密钥入档。** tools.md 是给 LLM 读的，写进去等于直接进上下文。密钥只走环境变量。
2. **写成人读的 README。** 长段落对 Agent 检索不友好，短列表反而更准。
3. **过期信息比没有信息更糟。** 关键条目可加“最近验证”标记，或写个小脚本探测路径与版本后自动刷新。
4. **双向漂移。** Agent 改了文件但没提交，其他人拉到的就是旧世界。把“改动后必须过一遍 git diff”写进约定。
5. **越写越长。** 超过几百行就该拆：高频事实留在 tools.md，一次性排障记录移去别的文档。

## 可复用建议

- 起步模板就用四段：环境、工具路径、项目约定、限制，每段一屏以内。
- 把“换机器、升版本、加工具后十分钟内更新”当成纪律，而不是待办事项。
- 在 CI 里加一步校验：tools.md 里声明的命令和路径是否真实存在，防止文档静默腐烂。
- 团队场景下把 tools.md 当代码 review——它本质是 prompt 的一部分，改它就是改 Agent 的行为。

## 总结

tools.md 的价值不在文件本身，而在于把环境事实从提示词工程里拆出来，变成可版本化、可审计、可分层的东西。Agent 需要的不是更强的记忆，而是一份诚实、新鲜、结构化的环境清单。建议从当前项目写第一版开始，四十行就够，跑一周再修剪。
