## 背景

Agent 的价值在“能动手”。OpenClaw 里模型本体只负责推理，真正查工单、拉指标、传文件这些动作，都来自外部服务对接。社区目前两条主流路径：把现有 REST API 包一层 MCP server，或者写插件把工具直接注册进 runtime。这篇帖记录我最近接了三个内部服务（工单系统、指标查询、对象存储）之后的做法，偏工程细节，不聊概念。

## 问题

对接做糙了，问题通常不在“调不通”，而在“调不稳”：

- 模型选错工具或传错参数，重试两三轮才对；
- 一次大 JSON 返回把上下文窗口撑爆，后面几轮对话质量骤降；
- 密钥进了日志甚至 conversation 历史；
- 第三方限流触发 429，agent 循环里没退避，配额几分钟烧光。

## 做法

1. **先选接入形态**。标准 API、想跨 client 复用，包 MCP wrapper；鉴权复杂（签名、密钥轮换），放到插件层做，agent 只拿最终结果。
2. **schema 是写给模型看的**。参数描述要写清格式和约束：“日期，格式 YYYY-MM-DD，不允许未来时间”远比 `date: 查询日期` 有效。枚举值全部列出，必填可选分明。
3. **鉴权隔离**。密钥只放环境变量或 secret 存储，工具进程内读取；日志统一脱敏 Authorization 头。
4. **超时与幂等重试**。统一 10s 超时；GET 可重试并做指数退避；写操作必须带幂等键，否则默认不自动重试。
5. **响应裁剪**。在工具层过滤字段、限制行数、强制分页，返回给模型的只留决策需要的部分。
6. **错误语义化**。把 4xx 转成模型能自纠的结构化信息，例如 `{"error":"invalid_param","field":"start_date","hint":"需为 YYYY-MM-DD"}`，实测下一轮大多能自己修正。

## 踩坑点

- 工具描述里塞整段 API 文档：token 翻倍，模型反而更难选。描述压到几行内，细节放参数级描述里。
- 下单类 POST 接了自动重试，产生过一笔重复工单。此后所有写操作默认关闭重试，靠幂等键兜底。
- 流式接口包成同步工具，30s 必超时。拆成“提交任务拿 ID”和“轮询状态”两个工具才稳定。
- 工具数超过 15 个后，模型选择准确率肉眼可见地下降。按场景拆 session 或做工具分组，别指望一个 agent 全都要。

## 可复用建议

- 沉淀一个统一的 wrapper 模板：超时、退避、日志脱敏、错误归一化四件事只写一次，新服务只填 handler。
- 一个服务只暴露 2~4 个高内聚工具，别把 REST 全量映射成工具列表。
- 准备 10 条左右固定测试问题（覆盖空结果、错参数、限流场景），每次改 schema 后跑一遍回归。
- 工具 schema 变更走版本号，线上 agent 不吃静默升级。

## 总结

Agent 与 API 的握手，本质是三份契约：schema 决定模型怎么调工具，鉴权与超时决定工具怎么调服务，错误语义决定模型能不能自我修正。把这三份契约写扎实，比多堆几个工具、或者换更强的模型，对稳定性的贡献都大。你们在对接里踩过什么坑，欢迎跟帖交流。
