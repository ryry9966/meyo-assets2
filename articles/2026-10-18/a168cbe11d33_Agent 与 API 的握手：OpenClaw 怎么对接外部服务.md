## 背景

OpenClaw 这类 Agent 的核心循环是「理解意图 → 调工具 → 汇总结果」，但它本身不连任何业务系统。真正让它能查数据、发消息、操作外部服务的，是外面那一圈对接层：skill、MCP server，或者一段被它调起的脚本。对接层做得好不好，直接决定 Agent 是「能用的助手」还是「只会道歉的聊天框」。这篇记录一下我对接外部 API 的通用路径。

## 问题

把一个外部服务接进 OpenClaw，听起来就是发个 HTTP 请求，实际会撞上四类问题：

1. **鉴权**：key 放哪、怎么轮换、会不会被写进对话记录；
2. **契约模糊**：工具描述含糊，Agent 就会自己编参数；
3. **返回失控**：接口甩回 50KB 的 JSON，直接撑爆上下文；
4. **副作用**：Agent 对「发送」「下单」这类非幂等操作的理解，和你的预期不一定一致。

## 做法

我的路径是三步，顺序别反：

**第一步，先手动跑通。** 用 curl 或十行脚本把 API 调通，确认鉴权方式（Header / Query / OAuth）、分页和错误码。这一步不碰 Agent，纯 CLI 排错成本最低。

**第二步，封装成窄接口。** 不要把整个 API 面暴露给 Agent，一个动作一个命令：

```bash
openclaw-ext create-issue --repo foo/bar --title "..." --body "..."
```

脚本内部做三件事：从环境变量读 key、校验参数、把返回裁剪成二十行以内的摘要（关键 ID + 状态 + 报错原文）。记住：输出是给模型看的，人话和错误码都得有。

**第三步，写成 skill 或挂成 MCP。** skill 适合单个 Agent 的私有流程，MCP 适合多个 Agent 复用的通用能力。无论哪种，工具描述就是合同：每个参数写清类型、示例、什么情况**不该**调用。描述上多花十分钟，线上少一半幻觉。

## 踩坑点

- **key 进了 git**：用环境变量或本地未跟踪的 env 文件，提交前 `git status` 多看一眼；
- **重试撞上非幂等**：发消息失败自动重试，结果发了两条。写操作要么先查后写，要么带客户端去重 ID；
- **MCP server 起不来**：多半是 stdio 模式下环境变量没传进去，或子进程往 stdout 多打了一行日志污染了协议流，调试期把 stdout 和 stderr 分干净；
- **返回里带大段 base64 或长文本**：在封装层截断，别指望模型自己省 token；
- **描述里写「参数随便传」**：默认值写死、可选项标清，模糊描述是幻觉的温床。

## 可复用建议

- 一个外部服务一个 skill / MCP，最小权限，别做万能网关；
- 错误信息按「给模型看」的标准写：说明原因，给出下一步动作；
- 所有调用落本地日志文件——出问题时，Agent 的自述远不如日志可信；
- 外部接口会漂移，封装层留个版本号字段，schema 变了就在这一层挡住，别让 Agent 直面变化。

## 总结

Agent 与外部服务的握手，本质是工程问题而不是提示词问题：先把 API 手动跑通，再封一层窄接口做鉴权和裁剪，最后用严格的工具描述把行为边界交给 Agent。对接层稳了，OpenClaw 才谈得上可靠。
