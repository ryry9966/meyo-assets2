## 背景

Agent 跑起来之后，模型开销很快就上来了。我们团队的工作流是：planner 拆解任务、executor 调 MCP 工具、最后汇总写报告。这套流程如果全部走 GPT，单次成本不高，但一天几百次调用下来，账单和限流都会成为问题；反过来全走本地模型，复杂规划环节的失败率又明显上去。OpenClaw 支持在配置里同时挂多个模型并按规则路由，这篇帖记录我们划这条分工线的过程。

## 问题

路由策略最难的不是"配多个模型"，而是决定谁接什么活。我们最初的坑是只按成本路由——把所有"看起来简单"的任务都丢给本地 14B 模型，结果 tool call 解析失败率从 2% 涨到 17%，重试吃掉的 token 比省下的还多。也有团队反过来全走云端，碰到客户数据不能出内网的场景直接卡死。所以路由要同时权衡三个维度：**能力要求、数据敏感性、成本与延迟**。

## 做法

**1. 按角色分层，不按任务逐条判断。** 我们最终收敛成四类：

- planner / 多步推理与决策 → GPT
- 结构化抽取、分类、格式转换 → 本地模型
- 长上下文摘要 → 本地模型（注意窗口）
- 涉及私有数据的环节 → 强制本地，且该 agent 显式禁用外发类工具

**2. 用配置表达规则，别写死在 prompt 里：**

```yaml
# 字段名以你手上的 OpenClaw 版本为准，示意结构
router:
  rules:
    - match: { agent: planner }
      model: gpt-4o
    - match: { agent: extractor }
      model: ollama/qwen2.5:14b
  fallback:
    from: ollama/qwen2.5:14b
    to: gpt-4o
    on: [parse_error, timeout]
```

**3. 给本地输出加校验。** JSON schema 校验 + 连续两次解析失败自动升级到云端，升级事件记日志——这份日志后来成了调路由规则的主要依据。

**4. 切流量前跑回归。** 30~50 条覆盖成功和失败路径的任务集，对比成功率、平均 token、P95 延迟，再决定放量。

## 踩坑点

- **本地模型的 tool call 兼容性是最大的坑**：JSON 里多注释、参数名漂移、该给数组时给了字符串。涉及三参数以上 MCP 工具调用的环节，我们后来全留给云端。
- **量化版本差异比想象大**：14B Q4 做 classifier 都会偶发翻车，评测别拿 FP16 的结果替代。
- **上下文窗口没算进去**：本地 32k 窗口跑到一半溢出，fallback 上云时还要重发全量上下文，成本反升。
- **隐私判断要早做**：模型在本地跑了，但 trace、记忆库同步走的还是云，等于白忙。
- **采样参数按模型分别配**：直接沿用 GPT 的 temperature，本地模型输出风格会明显漂移。

## 可复用建议

- 路由的最小单位是 agent 角色，不是单条任务；先粗后细。
- 升级信号用客观指标（解析失败、超时），不要用模型自评。
- 每周看一次 per-route 的成本/延迟报表，再决定收紧或放宽规则。
- 敏感路径单独建一个 agent，绑定本地模型并显式禁网，别指望规则匹配兜底。

## 总结

多模型路由本质是能力、隐私、成本的三方权衡。我们的经验是：从"按角色粗分"起步，用校验和日志把失败变成可观测信号，跑一两周再精细化。一开始就堆细粒度规则的，最后基本都收敛回三四条。
