## 背景

单 agent 串行干活的天花板很明显：上下文有限、速度慢，一个长任务跑完，早期信息早被压缩得面目全非。OpenClaw 的 subagent 机制给了另一条路：主 agent 通过 agents 工具派生多个子 agent，每个子 agent 有独立会话和上下文（可以单独配模型），主 agent 只负责拆任务和收结果。

最近我把「每周整理几十个文档/频道并生成摘要」的流程从串行 40 多分钟压到 10 分钟以内，记录一下做法和踩过的坑。

## 问题

原流程是单 agent 循环处理：逐个读、逐个总结、最后汇总。三个问题：串行慢，几十个任务排队；上下文越滚越大，后半程的总结质量明显下降；中途一次失败就得从头再来。

这类子任务彼此独立、无共享写目标，是典型的可并行场景。

## 做法

分三步：

**1. 拆任务。** 原则：一个子 agent 对应一个独立输入、一个独立输出。每个源文档一个子任务，prompt 里写死：只读指定路径，只写自己名下的结果文件（如 `results/task-07.md`），不动别的。

**2. 并发 spawn。** 主 agent 把任务列表展开循环派发，prompt 模板自包含：任务目标、输入输出路径、固定输出格式（要点/风险/建议三节），以及一句关键约束——「不要向用户提问，拿不准就标记 SKIPPED」。并发数控制在 4。

**3. 文件即接口。** 子 agent 不把长文本直接回传，结果落盘；主 agent 只读各结果文件的「要点区」做二次汇总。这样主 agent 自己的上下文始终很轻。

## 踩坑点

- **写冲突**：最初两个子 agent 都往同一个 `summary.md` 追加，互相覆盖。改成各自独立输出文件后才稳定。
- **上下文不继承**：子 agent 看不到主会话历史，背景、术语、格式约定必须全部写进 prompt，不能指望「它应该知道」。
- **MCP/工具连接开销**：每个子 agent 会各自拉起工具连接，并发开到 8 时明显变慢且触发限流，砍回 3-4 恢复正常。
- **僵尸子 agent**：有个子 agent 卡在重试循环，主 agent 一直干等。后来统一加超时：超时即终止并标记该任务，下一轮补跑。
- **成本**：并行等于 token 消耗放大。大批量前先用 3 个任务试水，估出单任务成本再放量。

## 可复用建议

1. 并发从 3-5 起步，验证稳定后再往上提；
2. 任务模板化：system prompt 固定，变量只有输入/输出路径；
3. 区分读写角色：收集类子 agent 只读输入、只写自己的文件，不给全局写权限；
4. 结果先收敛再回传：子 agent 输出短摘要加文件引用，别把全文塞回主会话；
5. 幂等设计：任务可重跑、可跳过，单个失败不阻塞整体。

## 总结

subagent 编排的本质不是「更多的 AI」，而是工程上的任务隔离：输入隔离、输出隔离、上下文隔离。把主 agent 当调度器，子 agent 当无状态 worker，文件当接口，大部分批量场景都能套用这套模式。

它不解决任务间强依赖的问题——那种场景，老老实实串行或分阶段跑更靠谱。
