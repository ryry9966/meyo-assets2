# AI 助手的 heartbeat 设计：轮询打底，推送加速

## 背景

在 OpenClaw 这类常驻 agent 网关里，heartbeat 是让助手"自己醒来干活"的机制：定时摘要、收件箱巡检、保持会话活性。默认实现是轮询——按固定间隔唤醒，读工作区的 HEARTBEAT.md 清单，有事处理，没事沉默。但当你要接 webhook、监控告警这类事件源时，就会遇到那个经典问题：轮询还是推送？

## 两种方式的本质差异

**轮询**：agent 定时醒来检查状态。
- 优点：实现简单，不需要公网入口，故障域小，行为可预测。
- 缺点：延迟下限等于间隔；且在 AI 助手场景，空转并不免费——每次 tick 若直接拼 prompt 调模型，就是纯烧 token。

**推送**：外部事件主动触发（webhook、消息队列）。
- 优点：精确、低延迟、无空转。
- 缺点：要暴露入口并做鉴权，要处理重试、去重、事件风暴，链路长，故障点多。

## 实际做法

1. **先列清单**。心跳到底要干什么？定时日报、巡检、事件响应，用途不同，机制不同。
2. **轮询打底**。interval 从 30 分钟起步，配 activeHours（如 08:00–22:00），夜里不醒；心跳走独立 session 或固定 target，避免污染用户对话上下文。
3. **加便宜的预检层**。tick 到来时先跑本地脚本判断"有没有值得唤醒模型的事"（新消息数、文件变更、清单是否为空），没有就结束本次心跳。这是省 token 的关键，OpenClaw 的 HEARTBEAT.md 沉默机制本质上就是它。
4. **高价值事件上推送**。延迟敏感的源（告警、Git push）加 webhook，HMAC 签名校验，事件先落队列再进 agent。
5. **合并窗口 + 幂等**。消费侧设 30–60 秒合并窗口，同一去重键只唤醒一次，心跳 prompt 里注明本次合并了几条事件。
6. **记账**。每次唤醒记录 reason（tick / event / catch-up）、是否触发模型调用、token 消耗，每周看一次空唤醒率。

## 踩坑点

- 心跳与用户会话共用上下文：助手会"记得"一堆系统噪声，回复质量明显下降，务必隔离。
- 间隔太密（分钟级）：限流 + 费用翻倍；太疏：提醒类任务失准。
- webhook 重试没做幂等：同一条告警触发三条重复回复。
- 设备休眠错过心跳：恢复后补跑要节流，否则一口气补十几次。
- cron 按 UTC 写死：activeHours 全部错位，改完时区记得实测验证。

## 可复用建议

- 把 interval 当预算参数管，而不是功能开关随手调。
- 默认"轮询 + 便宜预检"，只有延迟要求明确时才引入推送。
- 唤醒原因做成一等日志，成本问题基本都能从这里定位。
- 一切推送入口都假设会被重放，幂等键先行。

## 总结

轮询和推送不是二选一：轮询做底盘，推送做加速器，预检层和合并窗口负责控成本。心跳设计的核心问题从来不是"多久醒一次"，而是"这次醒来的理由，值不值得一次模型调用"。
