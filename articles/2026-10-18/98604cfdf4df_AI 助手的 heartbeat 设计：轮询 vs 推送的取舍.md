## 背景

OpenClaw 的 agent 天然是"被动"的：没人发消息，它就不动。heartbeat 是给 agent 装上脉搏的机制——每隔固定时间（默认 30 分钟，可配）醒来跑一次轻量检查，看有没有值得主动汇报的事。用久了你会发现，heartbeat 本质是轮询（polling）；而当你接了 MCP 工具、外部 webhook 和自动化插件后，另一个选项就出现了：让事件主动推（push）给 agent。两条路怎么分，是我最近踩得最多的一个设计题。

## 问题

轮询的问题很直接：间隔短了烧 token，每次心跳都是一次带上下文的模型调用；间隔长了不实时；大部分心跳是空转，检查一圈什么都没有。

推送的问题更隐蔽：agent 通常在网关后面，外部系统要先打通一条可信入口；没有鉴权的 webhook 等于把"向 agent 注入指令"的权限开放出去，是实打实的安全洞；推送失败是静默的，队列堆积你未必知道；事件一多，agent 被碎片化消息打断，反而失去 heartbeat 的节奏感。

## 我的做法：分类，然后混合

不要在轮询和推送里二选一，按事件属性分流：

1. **先给事件定性。** 凡是"分钟级必须到达、用户会关心"的（CI 挂了、关键邮件、服务器告警），走推送；"晚几分钟无所谓、可以攒着批量看"的（RSS 摘要、磁盘巡检、明日日程），留在 heartbeat 轮询里。
2. **把 heartbeat 做成廉价脉搏。** heartbeat 文件只放一张简短清单，明确要求：无事可报就保持沉默，有事才说话。间隔从默认值出发，观察一两周 token 消耗再调，别一上来就 5 分钟。
3. **推送走中转层。** 外部系统不直连 agent，而是打到一个小的 relay（一段脚本即可）做三件事：校验来源、合并去抖（debounce）、按统一的结构化格式投递给网关。agent 收到的永远是"一种消息"，处理逻辑最收敛。
4. **用状态文件去重。** 不管哪条路径进来的事件，agent 在本地维护一个小 state（事件 key + 时间戳），同一件事 heartbeat 和 push 都触到时，只报一次。

## 踩坑点

- **heartbeat prompt 太重**：早期我把巡检逻辑全塞进心跳，一次吃掉大量 token。后来把重活挪给 cron 定时任务，心跳只做"要不要说话"的判断。
- **webhook 裸奔**：第一版 relay 没加鉴权，测试时才发现任何人都能 POST。至少要 token 校验加来源白名单。
- **推送丢消息**：agent 离线或网关重启时，push 直接蒸发。relay 侧加本地队列和简单重试，比事后排查"为什么没通知我"便宜得多。
- **通知疲劳**：心跳如果每次都汇报，用户很快会无视 agent 的消息。"沉默是默认态"要写死在心跳提示里。
- **双路径重复报警**：同一次 CI 失败，push 报了一遍，15 分钟后 heartbeat 又报一遍。去重 state 是后来补的，建议一开始就有。

## 可复用建议

- 决策规则一句话：看延迟要求和事件量。秒/分钟级且用户必看 → push；分钟到小时级、可批量 → poll；两者都不满足的，先不做。
- 把 heartbeat 当"心跳"，把 push 当"神经信号"：心跳证明 agent 活着、顺便巡检；神经信号负责即时反射。职责别混。
- 所有进入 agent 的事件统一成一种结构化格式，轮询和推送只是两条入口，处理逻辑收敛到一处。

## 总结

heartbeat 的价值不是"定时干活"，而是给 agent 一个低成本的自主节律；推送的价值是及时性，代价是入口安全和可靠性工程。我的结论是混合架构：轮询保底、推送加速、relay 收口。先把事件按延迟和重要性分好类，再决定走哪条路——多数纠结，其实是分类没做。
