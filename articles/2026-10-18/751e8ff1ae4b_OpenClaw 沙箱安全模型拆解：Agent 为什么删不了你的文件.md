## 背景

给 Agent 接上 shell 工具之后，社区里被问得最多的问题之一就是：让模型自己执行命令，它会不会哪天“抽风”把目录删了？这不是杞人忧天——LLM 在路径解析、通配符展开、多轮任务上下文串台时，确实可能做出破坏性操作。

OpenClaw 的思路不是“相信模型”，而是从环境层面限制破坏半径：**即使模型想删，也够不着**。

## 问题：误删的真实路径

误删通常不是模型“有恶意”，而是三类情况：

1. **路径解析错**：相对路径、通配符展开超出预期范围；
2. **上下文串台**：上一轮任务的目标路径被带进下一轮执行；
3. **插件越权**：某个 MCP 工具自带文件写权限，绕过了 shell 侧的约束。

所以防线必须是系统性的。单靠在 system prompt 里写“请不要删除文件”，工程上不可靠。

## 做法：四层沙箱模型

**第一层：执行隔离。** 默认在 Docker 沙箱内执行 shell 命令。容器里看到的“整个系统”，其实只是镜像层加 workspace 挂载。`rm -rf /` 删掉的是容器层，宿主机毫发无损。

**第二层：文件系统收窄。** 只把需要的 workspace 目录挂进容器，其余路径根本不存在于 Agent 的视野里。能删的前提是“看得见”，看不见就删不了。

**第三层：工具分级与确认门。** 读、写、执行权限分离；高危命令模式（`rm -rf`、`mkfs`、`dd`、递归 chmod 之类）可配置为黑名单或强制人工确认。推荐策略是：沙箱内自动放行、宿主机操作必确认——这样确认弹窗才是“值得看”的信号，而不是噪音。

**第四层：快照兜底。** 危险任务执行前对 workspace 打快照，出问题可回滚。这是最后一道保险。

配置思路示意（字段名以你使用的版本为准）：

```yaml
sandbox:
  mode: docker
  workspace: ./workspace   # 只挂这一个目录
  docker:
    network: none          # 按需再放开
```

## 踩坑点

- **图省事关掉沙箱直跑宿主机**：最常见的翻车原因。慢几秒总比重装系统强。
- **把 `~` 整个 bind 进容器**：等于把家门钥匙交给 Agent，隔离形同虚设。
- **容器内挂载 docker.sock**：基本等于沙箱逃逸，别这么干。
- **MCP/插件有自己的文件访问**：exec 沙箱管不住它们，工具权限需要单独收窄。
- **workspace 里的软链接指向外部**：可能成为逃逸通道，保持 workspace 干净。
- **确认弹窗疲劳**：什么都点“同意”，确认门就白设了。把确认留给真正的高危操作。

## 可复用建议

- **默认拒绝**：最小挂载，能只读就只读。
- **环境分离**：实验任务用独立的 scratch workspace，生产目录对 Agent 设为只读。
- **混沌演练**：定期在测试环境让 Agent 执行 `rm -rf /`，验证沙箱兜底真实生效，而不是假设它生效。
- **审计回看**：检查 session 日志，确认命令实际执行的位置和你以为的一致。
- **升级重测**：版本升级后重跑一遍沙箱验证，别假设默认行为不变。

## 总结

Agent 不误删文件，靠的不是模型自觉，而是分层防御：执行隔离挡住宿主机、路径收窄挡住无关目录、工具分级挡住高危命令、快照兜住残余风险。四层各管一段，缺一层风险就漏一层。

对使用者的要求其实只有一句话：**别为了方便，亲手把沙箱拆了。**
