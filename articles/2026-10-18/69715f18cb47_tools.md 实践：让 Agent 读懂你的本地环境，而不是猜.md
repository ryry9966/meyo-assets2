## 背景

跑 OpenClaw 或任何带工具调用的 Agent，最省事的假设是"环境是统一的"。实际上不是：家里台式机是 Linux，笔记本是 macOS，公司机器上 Python 在 conda 里，MCP server 有的用 npx 起有的用 uvx 起，Docker socket 挂载路径也各不相同。这些差异散落在系统提示词、零散配置和口口相传里，Agent 每次会话都要重新试探。

tools.md 是一个很朴素的解法：在项目根目录放一份纯 Markdown，声明式地告诉 Agent——这台机器上有什么工具、怎么调用、有什么坑。它不是协议，不需要新依赖，本质上是给 Agent 的环境 README。

## 问题

没有 tools.md 时常见三类麻烦：

1. **重复试探**。Agent 每次都重新探测环境：跑 `which`、试路径、猜包管理器，浪费 token 也浪费时间，还可能猜错。
2. **幻觉工具**。提示词里写了"可以调 XX 脚本"，但那台机器上根本没有，Agent 会反复重试直到失败。
3. **配置漂移**。两台机器、两个项目各写各的，路径硬编码，换台机器就崩，排查半天发现只是环境差异。

## 做法

我的做法分三层：

**第一层：仓库级 tools.md（提交 git）。** 写团队通用事实：脚本清单、MCP server 列表、启动命令、目录约定。控制在 60 行以内，多用表格。

**第二层：tools.local.md（进 gitignore）。** 放本机差异：绝对路径、端口、conda 环境名。只写变量名和语义，敏感值走 `.env`。

**第三层：显式注入。** 在 agent 启动配置或 workspace 指令里写明"会话开始先读这两份文件再决定调用方式"，别指望 Agent 会主动翻目录。

骨架示例：

```markdown
# Tools
## shell
- 默认 bash；macOS 为 zsh，注意 glob 差异
## python
- 一律通过 uv 运行，不要直接调 python3
## mcp
- filesystem: 已挂载项目根目录，禁止写 ../
- browser: 无头模式加 --headless
## 禁区
- 不动 /etc 下任何配置
- 数据库只读，写操作需人工确认
```

## 踩坑点

- **把密钥写进 tools.md**。文件会被完整读进上下文，还可能被同步、被贴进日志。密钥永远只放 `.env`，文档里写变量名。
- **写成散文**。长文档会稀释 Agent 的注意力，关键约束反而被忽略。用表格和短句，一行一条。
- **和 MCP manifest 重复**。工具能力边界 manifest 已经声明了，tools.md 只补充它说不清的东西：本地路径、启动方式、平台差异、禁区。
- **忘了更新**。加了新脚本没写进去，Agent 调用三次失败后才被人肉提醒。把"改工具就改 tools.md"挂进 code review 清单。

## 可复用建议

- 每条工具记录四要素：调用命令、前置条件、平台差异、失败时的替代方案。
- 给每段内容标注验证日期，超过三个月没碰的条目优先怀疑过期。
- 换新机器时别手写：让 Agent 对着旧 tools.md 逐条跑探测命令生成初稿，你只做审校——这本身就是最好的验收测试。
- 定期反问 Agent："你现在有哪些工具？X 怎么跑？"答不上来或答错，就是文档该改的信号。

## 总结

tools.md 的价值不在文件本身，而在于把环境知识从隐性口述变成显式、可版本管理、可审计的资产。它解决的不是能力问题，是一致性问题——Agent 不需要更聪明，只需要每次都拿到同样准确的事实。先从 30 行写起，跑两周，被坑一次加一条，收敛速度比你预想的快。
