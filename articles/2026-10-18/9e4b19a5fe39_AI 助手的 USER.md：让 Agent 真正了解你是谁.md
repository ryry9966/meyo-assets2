## 背景

用 Agent 做日常开发，最明显的摩擦不是模型不够聪明，而是它每次醒来都不认识你。上下文一清空，你的技术栈、时区、命名习惯、正在推进的项目全部归零。于是每轮对话都要自我介绍一遍，或者忍受它给出的"通用正确但与你无关"的答案。

OpenClaw 的 workspace 机制给了这个问题一个很工程化的解法：`USER.md`。和定义行为边界的 `AGENTS.md`、定义人格的 `SOUL.md` 不同，USER.md 只做一件事——用一份静态文件持久化"你是谁"。

## 问题

没有 USER.md 时的典型症状：

- 每次都要重复说明技术栈和偏好；
- Agent 给的代码示例风格随机，有时还是你早已不用的框架；
- 它不知道你的作息窗口和日程语境；
- `MEMORY.md` 记的是事件流水，缺一份稳定的"底座事实"。

记忆文件回答"发生过什么"，USER.md 回答"我一直是谁"。两者混用，事实和流水会互相污染。

## 做法

在 workspace 根目录建 USER.md，控制在 150 行以内，建议分五段：

```markdown
# User Profile

## Basics
- 时区、语言、作息窗口
- 角色定位（例：后端为主，偶尔写前端）

## Tech Stack
- 主力语言 / 框架 / 部署环境
- 明确列出"不要用"的东西

## Preferences
- 代码风格、注释密度
- 沟通偏好：先结论后细节 / 直接给 diff

## Current Projects
- 正在推进的 2-3 个项目，各一句话上下文

## Boundaries
- 不主动做的事（例：不自动 commit、不改 .env）
```

配套两个习惯：

1. **手动初始化，增量维护**。第一次自己写；之后让 Agent 用自定义命令（比如 `/profile update`）把你口头说的偏好追加进去，人负责 review diff。
2. **进版本控制**。放进 git，改坏了能回滚，跨机器同步也顺手。

## 踩坑点

- **写太长**。超过几百行后关键偏好会被稀释，模型注意力不平均。宁可删旧条目，也别只堆新条目。
- **放敏感信息**。手机号、密钥、内网地址不要写——这个文件可能随截图或同步泄露。
- **和 AGENTS.md 打架**。AGENTS.md 管行为，USER.md 管事实。两处都写"回复要简短"这类指令，后面改一处忘一处。
- **只写不删**。项目结了、栈换了，旧条目还留着，Agent 会基于过期事实给过时建议。每月固定 review 一次。

## 可复用建议

- 把 USER.md 当**配置文件**看：有 schema、有 review 流程、有生命周期，而不是日记。
- 团队场景拆两层：个人偏好放 USER.md，团队约定放项目里的 AGENTS.md。
- 验证注入链路是否生效：新开会话直接问"我的部署环境是什么"，答案来自文件而不是猜测，说明链路是通的。

## 总结

USER.md 本质上是一份人工审核过的、低频变更的用户上下文配置。它不解决记忆问题，但让每次记忆重建都有稳定锚点。花半小时写好它，比每天多聊十轮更能提升 Agent 的"懂你程度"——个性化不是玄学，是上下文工程。
