## 背景

E2E 测试的投入产出一直不好看：写一条用例要熟悉路由、页面状态和选择器，维护成本更高。我们团队的现状很典型——单测覆盖尚可，E2E 只有几条冒烟，出了问题靠人肉回归。Agent 兴起后，"让 AI 写测试"听起来顺理成章，但实际落地发现：直接丢一个 URL 给模型让它生成 spec，产出基本不可用——选择器靠猜、框架 API 靠编、断言永远是"元素可见"这种废话。真正能用的方案，是把测试编写拆成多个 Agent 角色的协作流程。

## 问题：单 Agent 直接生成为什么不行

- **没有运行时上下文**：模型看不到真实 DOM，只能凭训练语料猜 selector；
- **写完不跑**：生成不等于可用，未执行的测试比没有测试更糟，是假安全感；
- **写与修混在同一上下文**：一边生成一边补丁，越改越乱，最后没人分得清哪句是"事实"。

## 做法：三个角色 + MCP 工具

我们的流水线基于 Playwright + 浏览器类 MCP 工具 + 仓库内 Agent 脚手架：

1. **探索 Agent**：通过浏览器 MCP 真实打开页面，沿关键用户路径记录 DOM 结构、可交互元素、接口返回。产出不是代码，是一份"路径笔记"。
2. **编写 Agent**：拿到路径笔记 + 仓库测试规范（page object 目录、fixture 约定、强制 `data-testid`），生成 spec 草稿。系统提示里明确禁止 `waitForTimeout` 和文本选择器。
3. **验证 Agent**：在隔离环境跑 spec，失败时把报错、截图、trace 回喂给编写侧，但**只允许修 2 轮**，修不过就标记"待人工"，绝不硬凑绿灯。

人的位置在 PR 环节：Agent 产出走 PR，人只审 selector 和断言语义；CI 上无头运行并配重试策略。

## 踩坑点

- **编造 API**：模型会 import 不存在的 fixture，或用错 Playwright 版本语法。把本地依赖的类型摘要塞进上下文，能压掉大部分。
- **假断言**：Agent 倾向写"跑得过"的断言。我们要求每条用例至少一个业务语义断言（列表条数、订单状态字段），验证 Agent 会做这道检查。
- **测试数据**：账号和种子数据管理不清，Agent 就会在用例里 hardcode。统一走 seed 脚本 + 独立租户环境。
- **修循环失控**：不设轮次上限，验证 Agent 会反复改 selector 直到超时，token 烧得快还不出活。
- **MCP 浏览器会话**：登录态必须隔离，否则并行任务互相踢 session，表现为"时好时坏"的假 flaky。

## 可复用建议

- 把测试规范写成一份 Markdown 常量，所有 Agent 共享，改规范只改一处；
- 用例粒度对齐用户路径而非单个页面，模型在"路径级"任务上明显更稳；
- Agent 输出一律当草稿，selector 人工审查不可省略；
- 先让 Agent 补齐高频回归路径，别一上来追求覆盖率数字。

## 总结

Agent 写 E2E 的价值不在"全自动生成"，而在把探索、编写、验证拆开，各自带工具、带约束、带上限，人守住断言语义这一关。这条流水线我们跑了一个多月，新增回归用例的成本降到约原来的三分之一，误报率没有上升。它不性感，但能落地。
