## 背景

在 OpenClaw 这类 agent 环境里，"任务只跑一次"是一种假设，不是事实。cron 触发器可能在网关重启后补跑；MCP 工具调用超时后，agent 换个措辞再调一次；webhook 上游有自己的重试策略；你自己也会手动 re-run。**重试是常态，不是异常。**所以幂等性不是加分项，是自动化任务的底线设计。

## 问题

一个典型场景：每天定时把日报汇总发到群里。某天网关重启，cron 补跑，群里出现两条一模一样的日报。再比如插件里的"追加一行日志""创建一个工单""计数器 +1"，重复执行都会产生脏数据。

根因通常有两类：

- **触发层重复**：同一定时任务被触发两次；
- **执行层重复**：结果没送达（超时），但副作用已经发生，上层选择重试。

关键认知：网络和 agent 循环决定了调用语义是 **at-least-once**。你要做的不是消灭重试，而是让重复执行无害。

## 做法

1. **给任务定一个稳定的幂等键**。从业务含义推导，而不是每次随机生成：`2025-06-01:daily-digest:group-a`。随机 UUID 每次都不同，等于没做。
2. **先记账，再执行**。执行前在本地状态库（SQLite 或 JSON 都够用）写入一条记录，状态 `pending`；执行完标记 `done`；重试时看到已有记录就跳过或续跑。
3. **优先"确保态"而非"动作"语义**。把"给用户加 admin 角色"改写成"确保用户角色是 admin"；把"追加写文件"改成"用完整目标内容重写文件"。这类操作天然幂等，不需要额外状态。
4. **下游能挡就下游挡**。数据库用 upsert 不用 insert；调用外部 API 时携带去重键；消息接收方按 message id 去重。本地账本是第一道防线，下游约束是最后一道。

核心逻辑很短：

```text
function runTask(key, task):
  if ledger.get(key) == done: return lastResult
  ledger.set(key, pending)
  result = task.execute()
  ledger.set(key, done, result)
  return result
```

## 踩坑点

- **"先查后做"不是原子的**。两个并行执行都查到"没做过"，然后都做了。要么加锁，要么用 set-if-absent 抢占记录，谁先写入谁执行。
- **标记时机要清楚**：先标 `done` 再执行副作用，崩溃时丢任务；先执行再标 `done`，中间崩溃会重跑一次。所以下游去重必须保留，本地账本只是把重复概率压到极低。
- **幂等键里的时间统一用 UTC**，否则跨机器或夏令时会算出两个不同的"今天"。
- **老记录要清理**，清理窗口必须大于最大重试间隔，否则要么状态库膨胀，要么误判重复。
- **在工具描述里写清幂等语义**。LLM 遇到超时会自行决定重试，如果 MCP 工具的 description 写明"重复调用安全且返回相同结果"，agent 的行为会稳定得多。

## 可复用建议

- 把 `withIdempotency(key, fn)` 做成插件公共工具，所有写操作默认走它。
- 每个工具标注幂等属性：idempotent / not idempotent，以及重复调用的后果。
- 上线前**故意跑两遍**：同一任务连续触发两次，检查副作用只有一份。这是最便宜的测试，也是最真实的。
- 读操作天然幂等，别过度设计；把精力花在写操作和外部副作用上。

## 总结

Agent 自动化的默认语义是"至少执行一次"，幂等性是把 at-least-once 变成 effectively-once 的手段。核心就三件事：**稳定的幂等键、先记账后执行、ensure 语义优先**，然后用"故意跑两遍"来验证。做到这些，重试就从事故源变成了安全网。
