最近 36kr 一篇讲"许愿式编程"的文章冲上热议：更新后的 DeepSeek 让完全不会写代码的"小白"在对话框里说一句"我想要个 XX 小工具"，几分钟后就能拿到一个能跑的成品。评论区两极分化——小白狂喜，程序员幽幽地问"那我的工资呢"。先把情绪放一边：许愿式编程不是玄学，它是一条真实存在、可以完整拆解的工程链。这篇就把它拆开看：是什么、为什么现在能成、边界在哪、怎么许愿成功率最高。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/946de2196d786e4e.png)

## 一、"许愿式编程"到底是什么？

- **词源**：这个玩法在英文世界叫 vibe coding，2025 年 2 月由前 OpenAI 研究科学家 Andrej Karpathy 提出；中文社区给了个更接地气的名字——许愿式编程。本质相同：自然语言是唯一接口，代码是模型的事。
- 三个特征把它和旧事物区分开：
  1. **自然语言即接口**。你不说 Python，只说需求："做个能倒计时、结束放提示音的番茄钟。"
  2. **全流程托管**。传统 ChatGPT 写代码是"给你代码，你自己跑"；许愿式是模型自己完成"生成 → 运行 → 读报错 → 修复"的闭环，报错不经过你的手。
  3. **即时可得**。成品在对话或内置预览里直接可见，不用装环境、配依赖——这恰恰是劝退小白的第一道墙。
- 放进历史坐标看：命令行 → 图形界面 → 低代码 → 许愿式，人与计算机的接口一路上移。低代码还得"拼积木"，许愿式连积木都不用拼，直接说"我要一座桥"。

## 二、为什么"许愿"现在真的能成立？

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/75446dafba06bd7e.png)

四层地基，缺任何一层这个模式都跑不起来：

1. **强代码基座模型**。大模型预训练语料中代码占比极高，代码能力是 scaling law 的直接受益者。更关键的是 DeepSeek-R1 验证了 RLVR（可验证奖励强化学习）：单元测试通不通过是一个客观、自动、廉价的 reward 信号，而代码恰好是所有任务里"最容易自动判对错"的领域——所以代码能力涨得最快。
2. **长上下文**。上下文窗口从早期 4K token 涨到如今 128K+，一个小项目的整棵文件树都能塞进去。模型第一次能"看见全局"，而不是盲人摸象式地补代码片段。
3. **Agent 循环与工具调用**。规划 → 写码 → 执行 → 读日志 → 修复，配合读写文件、跑命令等工具接口，形成自动迭代。错误信息能回流给模型，是质量飞跃的关键一环。
4. **沙箱执行 + 低推理成本**。一键运行环境让"能不能跑"实现秒级反馈；而 DeepSeek 开源权重、API 定价打到行业地板，按其技术报告口径训练成本仅为同级模型的零头。成本降下来，"全民许愿"在商业上才成立。

一句话总结：不是"许愿"突然变神奇了，是反馈闭环变快、变便宜了。

## 三、为什么愿意"宠小白"？这笔账很清楚

- **用户基数差两三个数量级**。全球开发者约几千万量级，而能上网、有零散小需求的人是几十亿量级。门槛每降低一点，覆盖人群就指数级扩大。
- **数据飞轮**。小白的真实需求和"改这里、不对、再试试"式反馈，是极高价值的 alignment 数据——这种真实世界的需求分布，在开发者社区里是采不到的。
- **生态闭环**。应用长在自家对话产品里，token 消耗、用户留存、口碑传播全部体内循环。许愿池里捞上来的不是硬币，是 token。
- **同行验证过**。Cursor、Replit、bolt.new 等产品已经证明了付费意愿的存在，DeepSeek 用免费 + 开源把门槛再砍一档，属于用价格换生态位。

## 四、许愿的边界：哪些能许，哪些许了也白许

- **容易许中的**：单页小工具（番茄钟、汇率换算、进制转换）、表格与文本批处理、简单爬虫与数据可视化、个人主页、给老板看的产品原型。
- **许不动的**：多租户 SaaS、高并发服务、强合规场景（涉及金融/医疗数据的）、需要长期迭代的大型工程。
- 为什么？四个硬原因：
  1. **需求歧义**：多数人说不清自己要什么，直到看到"错的那个版本"。
  2. **幻觉与边界条件**：模型会自信地写错，边角 case 是重灾区；demo 能跑不等于逻辑严密。
  3. **安全盲区**：SQL 注入、密钥硬编码、越权访问——平时看不见，出事就是大事。
  4. **维护成本**：代码是一天的事，软件是十年的事。没有 owner 的系统会腐烂，这是许愿许不出来的。

一句话：demo 和 product 之间隔着的不是代码量，是责任。

## 五、想把愿望许准？一套实操框架

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets2@main/images/2026-10-18/d89ce295ecba53d5.png)

1. **需求四要素写全：输入 / 输出 / 边界 / 异常**。对比一下：
   - 坏愿望："帮我做个记账工具。"
   - 好愿望："输入每月收支的 CSV，输出按类别汇总的表格和柱状图；日期格式不统一时做兼容解析，缺行的记录标黄而不是报错中断。"
2. **小步许愿**。一次只许一个功能，跑通再叠加。一口气许十个愿，模型会顾此失彼，你也分不清哪条需求被悄悄忽略了。
3. **把验收标准写成测试用例**。直接甩给模型："这是三条输入和期望输出，请自测通过再交付。"测试用例就是愿望的质检单。
4. **守住安全红线**。API key、身份证号、公司内部数据不进对话框；demo 想真用，先换掉默认口令，检查有没有明文存储敏感信息。

## 收尾：三条冷思考

1. **门槛下降 ≠ 专业消失，而是专业上移**。写字的人变多了，编辑没有失业；写代码的人变多了，定义问题、验收质量、把关架构的人反而更值钱。恐慌不如换位。
2. **把它当最好的编程老师，而不只是外包**。每次都让模型"逐行解释这段代码在干什么"，许愿的同时顺便把自己的壳练硬——壳硬了，才轮得到你挑环境。
3. **许愿前三连问：数据从哪来？错了怎么办？半年后谁维护？**三问都答不上来，这个愿望先许给原型练手，别许给生产环境。

工具会一直变，"把问题讲清楚"这件事的价值，只会越来越贵。
