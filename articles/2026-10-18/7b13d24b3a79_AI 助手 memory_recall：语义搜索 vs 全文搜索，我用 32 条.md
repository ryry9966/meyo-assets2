# 背景

OpenClaw 的 agent 跑久了会积累大量记忆：session 摘要、决策记录、踩坑笔记。`memory_recall` 的职责就是在对话中把这些捞回来。我的工作区目前约 400 条记忆条目（markdown 文件 + 检索索引），之前一直用全文检索，最近补了语义检索并做了对比。结论先说：单独哪个都不够，混合才是答案。

# 问题

全文搜索遇到过两类典型失败：

- 用户换个说法，比如问“之前那个连不上数据库的错”，而记忆里存的是 `ECONNREFUSED`，关键词对不上，recall 直接落空；
- 语义检索上线后又出现反向问题：问 "openclaw.json 在哪配置”，返回几条泛泛的“配置相关”笔记，唯独漏掉真正提到这个文件名的条目。

本质是：全文检索输在“语义鸿沟”，语义检索输在“精确 token 失明”。嵌入模型对错误码、路径、函数名、版本号这类离散符号的区分度普遍很差。

# 做法

最终方案是双路检索 + RRF 融合：

1. **全文路**：SQLite FTS5（trigram 分词器），索引记忆正文和标题。
2. **语义路**：记忆按 300~400 token 切块，附带文件名和时间戳元数据，bge-m3 本地 embedding，余弦 top-10。
3. **融合**：两路各取 top-10，用 RRF（reciprocal rank fusion）合并排序，取前 5 注入上下文。别用原始分数加权——两个分数量纲不同，调权很痛苦；RRF 只看排名，稳得多。
4. **去重**：同一文件的多个 chunk 只保留得分最高的一个，避免上下文被单个文件刷屏。

评测方式：整理 32 条真实 recall 问题（一半含精确 token，一半是口语化转述），三种模式对比命中率：全文 62%，语义 66%，混合 91%。样本不大，但方向非常明确。

# 踩坑点

- **FTS5 中文分词**：默认 unicode61 会把整句中文当成一个 token，必须换 trigram 或外挂分词器，否则中文检索接近全灭。
- **切块太小**：150 token 时上下文碎成渣，agent 拿到半句话没法用。300~400 是比较舒服的区间。
- **索引过期**：agent 直接编辑记忆文件后忘了重建索引，recall 返回旧版本内容，排查了一晚上才定位。写入后必须同步增量更新索引。
- **top-k 贪多**：一开始注入 top-10，context 一半是噪声，agent 反而被带偏。控制在 5 条以内效果明显更好。
- **本地小模型 embedding** 对中英混排记忆的向量质量下降明显，选模型时用自己真实的记忆语料测，别只看榜单。

# 可复用建议

- **先建 baseline**：没测过全文检索之前不要急着上向量。记忆条目少于几百条时，grep + FTS 可能就够了。
- **维护 golden question set**：30 条左右的真实问题，每次改检索逻辑跑一遍，防回归。
- **全文路不能省**：精确 token 类问题基本靠它兜底，这也是混合方案里收益最大的一路。
- **失败 case 回流**：把 recall 没命中的问题记下来，定期补充进测试集，检索质量会持续变好。

# 总结

语义搜索解决“换个说法也能找到”，全文搜索解决“精确标识符一击命中”。对 memory_recall 这种高频调用、容错率低的场景，两者是互补而不是二选一。双路 + RRF 的实现成本不高（一个 SQLite + 一个 embedding 服务），收益却很实在。如果你的 agent 也经常“想不起来”，先判断失败属于哪一类，再决定补哪一路。
