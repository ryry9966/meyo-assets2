## 背景

用 OpenClaw 跑自动化任务久了，你会发现一个规律：每个新会话里的 agent 都像一个刚入职的实习生——能力不差，但对你的项目一无所知。用 `pnpm` 还是 `npm`？测试怎么跑？哪些目录不能碰？这些你得在 prompt 里反复说，换个会话又说一遍。README 是写给人的，agent 需要一份自己的手册。

AGENTS.md 就是这个约定：一个放在工作区根目录的 Markdown 文件，OpenClaw 的 agent 在会话初始化时会自动读取它，作为理解这个工作区的默认上下文。它不是新概念，本质上是把"口头交代"固化成文件。

## 问题

没有 AGENTS.md 时，常见的三类麻烦：

1. **重复解释**：项目约定全靠每次会话手工输入，成本高且容易漏；
2. **行为漂移**：不同会话用不同包管理器、不同代码风格，产出的补丁风格不一致；
3. **危险操作**：agent 自作主张执行清理命令、force push、改动不该动的配置文件。

## 做法

1. **位置**：根目录放一份全局 AGENTS.md；子项目目录可以再放一份，规则冲突时以就近那份为准。
2. **内容骨架**，建议固定五段：
   - 项目概览：一句话说清是什么、技术栈是什么；
   - 常用命令：构建、测试、lint 的准确命令，能复制执行；
   - 代码约定：命名、目录结构、错误处理风格；
   - 边界红线：哪些目录只读、哪些操作必须先确认、禁止哪些命令；
   - 已知坑：环境特例，比如"必须用 WSL 跑脚本"。
3. **长度**：控制在 100 行以内，一屏读完。
4. **迭代**：agent 犯一次错，就把对应规则补进去一次。

## 踩坑点

- **写成小作文**：超过几百行，中间的内容基本会被忽略。规则要短、可执行，别写背景故事。
- **与 README 或其他指令文件冲突**：agent 面对矛盾规则会随机选边。要么合并，要么显式声明谁优先。
- **空话规则**："写出高质量代码"等于没写。换成"函数不超过 50 行，报错统一走 `AppError`"这种可判定的表述。
- **内容过期**：构建命令改了、手册没改，比没有手册更糟。把它当代码管理，进 code review。
- **塞入秘密**：key、内网地址不要写，它会随上下文进入每一个会话。

## 可复用建议

- 建一个团队模板仓库，五段结构固定，新项目复制即用；
- 加一节"错误日志"，记录 agent 踩过的坑，这份文件会越用越准；
- 验证方法：新会话里让 agent 复述工作区规则，答不上来说明文件太长或太模糊；
- 和 MCP 工具配合：像"提交前必须跑测试"这类流程约束，写成工具调用的强制前置步骤，比纯文字约定可靠得多。

## 总结

AGENTS.md 不会让 agent 变聪明，但能让它少犯重复的错。它的本质是把团队里那些"老人才知道"的隐性约定，变成一份随仓库分发的工程资产。写法上记住三个词：短、具体、随错误迭代。今天就可以从根目录那份十行的文件开始。
