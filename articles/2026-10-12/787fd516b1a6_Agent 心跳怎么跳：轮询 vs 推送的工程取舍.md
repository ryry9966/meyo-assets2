## 背景

OpenClaw 的 agent 是常驻进程，默认靠 heartbeat 周期性唤醒：每隔一段时间（`heartbeat.every`，默认 30 分钟）读一次 HEARTBEAT.md，判断有没有值得做的事。很多人装完的第一反应是调快——"能不能 1 分钟一跳？"也有人反着来，想把所有触发改成 webhook 推送，彻底告别轮询。两条路都有人踩坑，这里把取舍讲清楚。

## 问题

轮询和推送本质是在三种成本之间做交换：

- **时延成本**：轮询的响应上限就是间隔本身，30 分钟的心跳意味着平均 15 分钟的感知延迟；
- **Token 成本**：每次心跳都是一次真实的模型调用（哪怕只做检查），间隔越短烧得越快；
- **工程成本**：推送需要可达的入口、鉴权、重试，还要处理 agent 正忙时的排队与并发。

## 做法

我们的实践是分三层：

1. **任务分类**：列出 agent 要响应的所有事件，按"能容忍多久延迟"分组——监控告警、主人消息是秒级；日报汇总、仓库巡检是小时级。
2. **秒级需求走推送**：用 webhook 插件或 MCP 工具把外部事件直接注入 agent 的消息通道，事件到达即触发，不走心跳。
3. **其余走轮询兜底**：`heartbeat.every` 保持 30m 默认值，HEARTBEAT.md 里只放三五条轻量检查项（有没有未读摘要、有没有到期任务），让每次心跳保持"便宜"。

## 踩坑点

- **心跳检查写太重**：把巡检逻辑全塞进 HEARTBEAT.md，结果每次唤醒都跑一轮完整 agent loop，一天下来 token 账单翻了几倍。心跳里只做判断，重活让心跳去触发独立的 cron 或子任务；版本支持的话，给心跳单独配一个更便宜的小模型。
- **推送没有幂等**：webhook 重试导致同一事件触发两次执行。给事件加去重键，agent 侧先查再执行。
- **只信推送**：网关重启、网络抖动期间事件会丢。推送通道之外保留一个较稀的轮询对账（比如每小时一次），当"死人开关"。
- **多 agent 同频心跳**：几个实例都在整点醒来，挤在一起打 API。给间隔加随机抖动。

## 可复用建议

- 默认配置：30m 心跳 + 极简 HEARTBEAT.md，先跑一周看日志再调参，不要拍脑袋定间隔。
- 判断标准：延迟容忍小于心跳间隔的一半，才值得为它单独建推送通道，否则别增加这条链路的维护成本。
- 监控两个数：心跳唤醒次数、每次心跳的 token 消耗。任何一个持续上涨，通常说明检查项悄悄变重了。

## 总结

轮询买的是简单和可靠，推送买的是时延。绝大多数场景下，正确答案是"稀疏轮询做底座、关键事件走推送"，而不是二选一。心跳的价值不在于跳得多快，而在于每一次跳都便宜、可预期、出了问题能从日志里看出来。
