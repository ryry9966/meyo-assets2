## 背景

过去半年，我把一部分自动化工作流从云端 API 迁到了本地模型。动机很实际：一是隐私，家庭笔记、日志、截图这类数据不想出网；二是成本，Agent 循环里高频小请求，账单攒起来并不少；三是本地推理没有网络抖动，单次请求延迟反而更稳定。

## 问题

本地模型跑聊天和跑 Agent 是两回事。聊天只看“答得好不好”，Agent 还额外要求：稳定的工具调用（function calling）、足够长的上下文（MCP server 返回的内容很吃 token）、可靠的结构化输出。而家用硬件——单卡 8~24GB 显存，或者干脆纯 CPU——把可选范围压得很窄。所以真正要解决的问题是：在给定硬件下，选什么模型、什么推理框架、什么量化档位，才能让 Agent 循环稳定跑起来。

## 做法

1. **先盘硬件，再定模型档位。** 8~12GB 显存从 7B~8B 的 Q4_K_M 起步；16~24GB 可以碰 14B~32B；纯 CPU 跑 7B~14B，预期 5~15 tok/s，只适合低频任务。
2. **选推理框架。** 求快用 Ollama，要细粒度控制用 llama.cpp，Linux + 好卡 + 高并发用 vLLM。三者都提供 OpenAI 兼容接口，Agent 侧切换成本很低。
3. **模型必须原生支持工具调用**，这是硬性筛选项。同尺寸下工具调用格式的遵守程度差异很大，别只看聊天评测榜。
4. **接入 Agent 框架。** base_url 指向 localhost，显式设置上下文窗口，temperature 压到 0.2 以下再测工具调用。
5. **用真实 MCP 工具验收。** 不要用 demo 函数。我拿文件读写加一个 HTTP 抓取的 MCP server 跑 20 轮真实任务，统计工具调用成功率和死循环次数。

## 踩坑点

- **上下文窗口默认值是大坑。** 不少运行时默认只有 4K，Agent 的 system prompt + 工具描述 + MCP 返回内容轻松超限，而且表现是“悄悄截断”而非报错。务必显式配置。
- **KV cache 比权重更吃显存。** 8B 模型权重约 5GB，但 32K 上下文的 KV cache 能再吃掉好几 GB。估算余量要按“权重 + 峰值上下文”算。
- **量化对聊天影响小，对工具调用影响大。** Q4 以下，先跑一遍工具调用回归再上线。
- **小模型失败时会死循环重试。** 给 Agent 循环加硬性重试上限和失败退出路径，否则一个坏工具调用能挂住整个流程。
- **流式输出 + JSON 解析在小模型上容易碎**，关键链路用 JSON schema 约束输出。

## 可复用建议

- **建“模型档案”**：模型名、量化档位、上下文长度、框架、实测 tok/s、工具调用成功率，像管理依赖一样 pin 住版本。
- **写一个十分钟基准脚本**：固定一组带工具调用的任务，换模型、换量化只看两个数——吞吐和成功率。
- **混合路由**：本地模型处理高频简单任务（分类、格式转换、摘要），困难推理走云端，别硬扛。

## 总结

家用硬件跑本地模型，如今是真正可用的，但定位是“窄而稳”的自动化执行层，不是全能助手。把工具调用成功率当第一指标来测，把上下文窗口当显式配置来管，剩下的就只是普通工程活了。
