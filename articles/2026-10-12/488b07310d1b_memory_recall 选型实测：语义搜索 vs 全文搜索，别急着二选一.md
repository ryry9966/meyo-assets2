## 背景

OpenClaw 的 agent 跑久了会积累大量 memory 条目：用户偏好、项目约定、踩过的坑、MCP 工具的调用备注。`memory_recall` 是这些内容写入上下文前的最后一道检索，它的质量直接决定 agent 是"记性好"还是"似懂非懂"。

社区里常见的两条路线：语义搜索（embedding + 向量索引）和全文搜索（SQLite FTS5 / BM25）。争论不少，实测数据不多。我拿自己 4000+ 条 memory 做了一轮对照，结论先放在这里：两条路都不是银弹，混合方案 + 一个小评测集才是正解。

## 问题

语义搜索的强项是同义改写。memory 里存着"用户忌辛辣"，查询"他不吃辣的"照样命中。但它会在精确标识符上翻车：文件名、错误码、版本号、API 路径，embedding 很容易把两个名字相近的包混为一谈。

全文搜索正好相反：精确 token 一击即中，但换个说法就抓瞎——查"授权失败"，找不到存成"401 报错处理"的条目。

单选哪条路，都有明显盲区。

## 做法

我的环境：memory 全部存 SQLite，单条 200 字以内；向量索引用 sqlite-vec，模型是本地跑的 bge-small-zh；全文索引用 FTS5，中文走 trigram。

1. **先建评测集。** 从历史会话里人工挑 50 对「查询 → 应命中的 memory」。这是整个工作的核心资产，比选哪个模型重要得多。
2. **分别跑两种检索，统计 recall@5。** 实测：语义 0.72，全文 0.61，两路合并后 0.86——增益主要来自彼此补盲区。
3. **合并用 RRF（倒数排名融合）**：两路各取 top 10，按 `1/(60+rank)` 加权求和重排，20 行代码的事。
4. **重排前先做元数据过滤**：按 tag、时间窗砍掉明显不相关的，两路检索都受益。

## 踩坑点

- **FTS5 默认的 unicode61 分词器对中文基本不可用**，会把整句当成一个 token。要么切 trigram，要么写入前用 jieba 预分词，别指望默认配置。
- **短文本 embedding 噪声大。** 单条 memory 只有十几个字时，向量质量明显下降。写入前把 tag 和上下文拼进 embedding 输入，能缓解不少。
- **语义检索的 top1 陷阱：** 分数最高但讲的是另一个实体的"相似条目"。加一层关键词校验——查询里的硬 token 必须出现在结果中——能过滤掉大半误召回。
- **别忘了时间衰减。** 三个月前的旧约定不该和昨天写的同权，`score *= decay(age)` 一行的事，不加会持续污染上下文。
- **评测集要持续喂。** 每次人工纠正一次召回，就把这对样本记下来，评测集会自己长大。

## 可复用建议

- 条目在几千条以内时，别上独立向量库。SQLite + FTS5 + sqlite-vec 一个文件搞定，运维成本为零，对个人 agent 完全够用。
- **先上全文搜索打底**，等评测集里改写类查询开始掉分，再补语义这条路。反过来做，大概率在为还没出现的问题付复杂度。
- k 取 5~8 比较稳。往上下文里塞太多召回，噪声的代价往往比漏召回更高。
- 一切调参用 recall@k 说话，别凭感觉换模型、换分词器。

## 总结

语义搜索解决"换个说法还能找到"，全文搜索解决"精确 token 必须命中"——memory_recall 两个都需要，RRF 是性价比最高的合流点。但顺序很重要：先把评测集搭起来，再谈方案选型。没有度量，一切搜索优化都是玄学。
