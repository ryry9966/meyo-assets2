## 背景：Agent 的默认姿态是"被动的"

多数人用 OpenClaw 的方式是聊天驱动：你问一句，它动一下。但一个常驻 agent 理论上应该有"值班"能力——定时看一眼该看的东西，有异常再开口。OpenClaw 提供了这个入口：心跳机制。每次心跳触发，agent 执行一个完整 turn，读工作区根目录的 `HEARTBEAT.md`，按其中指令决定是否行动；无事可做就回复 `HEARTBEAT_OK`，不打扰你，本轮结束。

## 问题：为什么你的心跳要么沉默要么轰炸

两种最常见的失败：

1. 文件不存在或为空，心跳直接静默跳过——你以为配了定时任务，其实什么都没发生。
2. 指令写得太泛（"帮我看看有什么新东西"），agent 为了显得有用每次都汇报，消息轰炸外加烧 token。

本质原因：把心跳当 cron 用，但它实际是"每轮都过一遍模型判断的巡检"。写法决定它是助手还是噪音源。

## 做法：五步写对 HEARTBEAT.md

**1. 确认路径与间隔。** 多 agent 时各工作区一份，全局配置大致长这样：

```jsonc
{
  "agents": {
    "defaults": {
      "heartbeat": {
        "every": "45m",
        "activeHours": { "start": "08:00", "end": "23:00" }
      }
    }
  }
}
```

**2. 每条指令写成"条件 → 动作 → 汇报门槛"：**

```markdown
# 无事请回 HEARTBEAT_OK，不要发消息

- ~/tasks/inbox.md 存在超 24h 未处理条目：
  汇总成不超过 3 行发我，处理后移入 done 区。
- ~/projects/api 远端有新 commit：超过 10 个才提醒，附区间。
- 每天第一次心跳查磁盘占用，>85% 才报。
- 报过警的事项写入 .heartbeat-state.json，未恢复不重复报。
```

**3. 显式写沉默规则。** 开头一句"无事不要发消息"比任何调参都管用。

**4. 状态落盘去重。** 报警状态写入独立文件，避免同一问题每 45 分钟喊一遍。

**5. 小步试跑。** 间隔临时调到 2 分钟，观察两轮日志确认行为，再调回。健康的标志是大多数心跳走 `HEARTBEAT_OK` 短路。

## 踩坑点

- **心跳是完整 agent turn，不是免费定时器。** 默认 30 分钟一次，一天约 48 次调用。条目控制在 5–8 条，必要时换便宜模型跑心跳。
- **心跳跑在主会话里**，上下文会累积。高频心跳加长清单会推高上下文成本，注意降频或拆 agent。
- **别放重活。** 全量扫描、慢爬虫会拖垮 turn 甚至超时；重计算交给 cron 或按需调 MCP 工具。
- **小心自指指令。** "把结果追加回 HEARTBEAT.md"这类写法会让文件膨胀、行为失控，状态一律写到别的文件。
- **权限边界**：心跳期间工具照常可用，涉及系统命令的条目先确认沙箱与权限。

## 可复用建议

- 把 HEARTBEAT.md 当"值班巡检表"，不当调度器：真正的定时任务用 cron，产出丢给 agent 消费。
- 三个稳定模板：**异常巡检**（异常才报）、**每日摘要**（每天第一次心跳汇总）、**状态机**（报警前先查状态文件）。
- 用 git 管这个文件，每次行为变更都有 diff 可回溯。
- 心跳 turn 里可以正常调 MCP 工具，适合轻量监控聚合（拉指标、查队列深度），前提是单轮能完成。

## 总结

HEARTBEAT.md 的价值不在"自动化"三个字，而在于它逼你把"什么值得打扰我"写成明确规则。写得好，agent 从问答工具变成真正的值守角色；写得差，它就是每半小时响一次的噪音发生器。建议从一两条高价值巡检起步，跑一周再扩。
