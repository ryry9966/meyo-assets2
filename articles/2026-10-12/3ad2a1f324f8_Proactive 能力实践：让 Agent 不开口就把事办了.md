## 背景

大多数 Agent 的用法还停留在“被动响应”：人发指令，模型执行。这个模式的天花板很明显——你能想到的它才做，你想不到的它不做。而 OpenClaw 的架构天然留了一个口子：除了被动收消息，还可以通过定时器、webhook、MCP 事件通知让 Agent 自主唤醒。这篇记录我把自己的 Agent 从“有问必答”改造成“每天自动处理三件事”的过程，重点不是炫技，而是怎么让 proactive 不变成骚扰。

## 问题：Proactive 很容易变成垃圾信息推送

第一版我直接把几个 Cron 任务和 CI webhook 绑到模型上：触发就跑，跑完就推。坚持不到一周：

- 早间简报没有信息量，因为醒来时数据还没更新，模型只能拿套话凑字数；
- CI webhook 一晚上触发 20 多次，通知列表直接刷屏；
- 最危险的一次，它“主动”帮我重排了工作目录里的文件，全程没有确认。

结论：proactive 的瓶颈不在模型聪明不聪明，而在触发源、判断标准和执行边界这三件事是否可控。

## 做法：三层结构，每层都可以短路

**触发层**。统一三类入口：定时（Cron）、事件（webhook / MCP 通知）、状态（轮询阈值）。关键是每个触发都带 payload，标注“它为什么醒来”，后面所有判断都基于这个 payload。

**判断层**。触发不直接进主模型。先用规则挡掉明显无意义的（空数据、重复事件、无变化），再用便宜的小模型评估“这次值不值得打扰用户”，通过后才注入主模型上下文。仅这一层，我的 token 消耗降了七成。

**执行层**。动作分三级：静默记录（只写日志）、轻量通知（一句话推送，附触发原因）、写操作（必须先给出方案等人确认，或限定在白名单内）。核心约束是：任何主动推送必须带“为什么是现在”这一句，用户才有依据判断这个触发该留该删。

## 踩坑点

1. **定时漂移**：Cron 只保证按时醒，不保证醒来有事干。解法是在 payload 里加“无变化则跳过”标记，配合判断层直接短路。
2. **事件风暴**：同一来源 5 分钟内的多次事件先合并（debounce），不要逐条喂给模型。
3. **上下文污染**：主动会话要和主对话隔离。凌晨三点的巡检任务如果直接写进主会话，第二天你的对话窗口就是满的。
4. **过度自信**：写权限不要一上来就给。先让它静默记录两周，人工复盘主动行为日志，确认命中率之后再逐级放开。

## 可复用建议

- 触发要“便宜”：规则层过滤得越狠，模型层就越省，成本和噪音一起降；
- Proactive 是信任的函数：静默记录 → 通知 → 写操作，按这个顺序逐步放权，不要跳级；
- 每周复盘一次主动行为日志，命中率低于阈值的触发器直接删掉，宁可少不要滥；
- 事件接入优先走 MCP 的通知机制，而不是自己手写 webhook 胶水代码，少维护一层，也方便复用别人写好的 server。

## 总结

Proactive 能力的本质不是“让模型自作主张”，而是三个工程边界：触发源可控、判断标准显式、执行分级清晰。正确的路径是先让它安静地把小事做对，积累足够的反馈样本，再逐步交出更大的权限。判断标准也很朴素——当它连续几次在你开口之前把事办对、且没有一次办错时，这个能力才算真正成立。
