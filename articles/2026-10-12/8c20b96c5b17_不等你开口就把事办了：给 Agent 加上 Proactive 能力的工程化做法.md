## 背景

多数 AI 助手默认是个被动应答器：你问一句，它答一句。真正的价值拐点在 proactive——不等你开口，它已经在监控、判断、动手。OpenClaw 这类框架其实已经把基础设施给齐了：heartbeat 周期唤醒、cron 定时、webhook 事件接入、MCP/插件提供执行工具。剩下的不是玄学，是工程问题：什么该触发，什么时候该闭嘴。

## 问题

把被动 Agent 改成主动的，最容易死在三件事上：

1. **噪音**。每 30 分钟唤醒一次，汇报"一切正常"，三天后你就把它静音了。
2. **误动作**。Agent 自作主张发消息、删文件，错一次，信任就没了。
3. **成本失控**。高频心跳加上膨胀的上下文，token 账单比被动模式高一个量级。

## 做法

我目前在用的分层结构，四步：

**第一步：盘点事件源。** 三类——定时类（cron、heartbeat）、事件类（webhook、文件变更、消息频道）、状态类（磁盘、队列长度、日历）。检测层用确定性脚本，不要让 LLM 盯 metrics。

**第二步：把"要不要打扰用户"做成显式决策。** 心跳唤醒时给 Agent 一份精简 checklist（放 HEARTBEAT.md 或独立 prompt 文件），让它对每个信号输出三选一：忽略 / 进摘要 / 立即告警。选择忽略的只写日志，不出声。

**第三步：分级输出。** 立即告警走即时通道；摘要类攒到固定时刻（比如每晚九点）合并成一条；所有主动动作落一份审计日志，事后可查。

**第四步：执行带闸门。** MCP 工具按风险分级：只读工具随便调；可逆操作（打草稿、建文件）直接做；不可逆操作（发送、支付、删除）必须生成待确认项，等你点头。Agent 可以"准备好"，但不该"替你按下去"。

## 踩坑点

- **去重缺失**。同一个告警每小时报一次，是因为 Agent 没有状态。给它一个小的 state 文件记录"上次已报告的事件 ID"，触发前先比对。
- **心跳 prompt 膨胀**。checklist 塞到 40 条之后，误判率和成本一起涨。控制在 10 条以内，低频任务挪去 cron，别全挂在心跳上。
- **让 LLM 做检测**。让模型看 CPU 曲线判断异常，又贵又抖。检测交给阈值脚本，LLM 只负责"这堆日志说明了什么"。
- **时区与调度**。cron 跑在 UTC，摘要在你午休时到。所有定时统一到本地时区，并在配置里显式声明。
- **没有关闭开关**。每个 proactive 任务必须支持一句"这个别再提醒我了"，否则用户会用静音整个会话来投票。

## 可复用建议

- 一句话原则：**检测用确定性代码，判断用 LLM，执行用工具，兜底靠人。**
- 先做摘要，再做告警，最后才考虑自动执行。信任是逐级给的。
- 把 proactive 任务当代码管理：checklist、阈值、告警路由全进版本库，改行为等于改配置，可回滚。
- 每条主动消息附带一句"为什么找你"。可解释性，决定你忍不忍得了它。

## 总结

Proactive 不是给 system prompt 加一句"请你主动一点"，而是调度、事件源、工具、决策层四件事的组合。工程上真正难的不是让它开口，而是让它在该沉默的时候沉默——安静地记日志，该说话时才说话。从一条每晚的摘要开始，比从全自动代理开始，靠谱得多。
