## 背景

做自动化流水线时有个常见模式：主 agent 一条主线干到底——读文档、查 MCP、写代码、跑测试，全部塞进同一个上下文。任务一复杂，上下文迅速膨胀，工具调用变慢，中途一个环节出错还会污染后面所有判断。

## 问题

我们有个典型场景：给一批第三方 API 写对接适配。单 agent 串行做，一轮下来 20 多分钟，而且读到第 4、5 个接口时，前面的细节已经开始“遗忘”，产出质量肉眼可见地下滑。核心矛盾有两个：

1. 上下文是稀缺资源，探索过程和最终产出不该混在一条线程里；
2. 各接口之间相互独立，串行纯粹是浪费。

## 做法

我们的编排原则很简单：**主 agent 只做拆解和验收，subagent 只做执行。**

1. **拆任务**：主 agent 把目标切成若干可独立交付的子任务，每个子任务写清输入（文档路径）、产出（一个适配文件 + 结构化总结）、完成标准。
2. **定义 subagent**：每个 subagent 配独立 system prompt 和受限的工具白名单（只开文件读写和对应的 MCP 查询工具），明确禁止它做拆解之外的决策。
3. **并行调度**：并发数控制在 3 左右，而不是能开多少开多少。每个 subagent 带超时和重试上限。
4. **结构化回传**：subagent 返回固定 schema 的 JSON（状态、产出路径、遗留问题），主 agent 只读摘要，不去翻原始过程。
5. **验收兜底**：收齐结果后统一跑一次校验（lint + 单测），不过关的子任务单独重派，不重跑全局。

效果：同批任务从 20+ 分钟压到 7 分钟左右，主上下文长度基本持平——过程性探索都发生在 subagent 自己的上下文里。

## 踩坑点

- **上下文不会自动共享**。Subagent 看不到主 agent 的对话历史，brief 里少写一句，它就按自己理解来。我们的办法是把 brief 当正式接口文档写。
- **并发写同一文件必炸**。两个 subagent 同时改配置文件，后写的覆盖先写的。要么按文件划分任务，要么加锁。
- **“我做完了”不可信**。Subagent 会理直气壮地报告成功，必须有独立校验兜底，最好基于产出物（文件、测试结果）而非它的自述。
- **限流和超时要提前设**。并行后工具调用速率翻倍，MCP 侧限流一来就是批量失败。并发从 2 起步逐步加，比一步到位稳。
- **回传内容要克制**。让 subagent 把全过程贴回来，等于把上下文膨胀问题原样搬回主 agent。

## 可复用建议

- 一个 subagent 只交付一件事，交付物越具体越好编排；
- 工具权限按需最小化，既降风险也减少它乱探索；
- 把 brief 和回传 schema 模板化存起来，新任务只换参数；
- 先串行跑通单个 subagent，再开并行，别一上来就调并发。

## 总结

Subagent 编排的价值不在“多个 AI 一起跑”这个噱头，而在两件事：上下文隔离带来的稳定性，独立任务并行带来的速度。前提是拆解粒度合理、brief 写清楚、验收独立于执行。这三件事做扎实了，编排本身就是水到渠成的工程问题。
