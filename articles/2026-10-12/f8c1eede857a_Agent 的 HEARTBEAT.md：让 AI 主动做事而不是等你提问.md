# 背景

OpenClaw 的 agent 默认是被动模式：你发消息，它干活。但很多事不需要你发起——备份跑没跑、仓库夜里有没有新 issue、明早汇总一下动态。OpenClaw 内置了心跳机制：gateway 按固定间隔唤醒 agent，agent 读取工作区里的 `HEARTBEAT.md`，按内容决定"干活还是闭嘴"。这份文件就是 agent 的主动任务清单。

# 问题

多数人装完后这个文件是空的，心跳每次跑一圈发现无事可做，返回 `HEARTBEAT_OK` 后被 gateway 丢弃，功能等于白开。另一类人往里写了任务，但写得像聊天："帮我看看服务器"——结果 agent 每半小时汇报一次"服务器看起来正常"，一晚上刷你几十条消息。核心问题不是机制不行，而是这份文件要按**值班手册**来写，不是按对话来写。

# 做法

**1. 找到文件**：默认工作区（一般是 `~/.openclaw/workspace/`）下的 `HEARTBEAT.md`；多 agent 场景改对应 agent 的工作区。

**2. 按"条件触发"写任务**，而不是"每次都做"：

```markdown
# 心跳任务

规则：只在有值得汇报的结果时说话；无异常直接回复 HEARTBEAT_OK。

- 首次跨入每天 8 点后的心跳：汇总仓库夜间新增 issue/PR，发到 #daily
- 读取 /srv/backup/LAST_RUN 时间戳，超过 26 小时未更新则发告警
- 同一异常不重复报告，除非状态变化
```

**3. 配置间隔**（字段名以你当前版本文档为准）：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "30m" }
    }
  }
}
```

**4. 验证**：重启 gateway 后把间隔临时调短（如 2 分钟）跑半天，看日志确认每次心跳的输入输出和误报率，再调回正常值。

关键机制：心跳轮次里如果 agent 只回了 `HEARTBEAT_OK`，这条回复会被丢弃、不会推给你；只有它真正调用消息工具（发频道/私聊）你才会收到。所以"沉默规则"必须写进文件，靠模型自觉不如靠制度。

# 踩坑点

- **模糊指令 = 定时刷屏**。"看看有没有问题"没有判定标准，agent 会倾向汇报点什么。每条任务必须写清"什么条件才算事"。
- **间隔太短烧 token**。每次心跳都是一次完整 session turn，工具越多、上下文越大，30 分钟起步，任务少可放宽到 1–2 小时。
- **机器休眠心跳停摆**。gateway 跑在合盖笔记本上，夜里就没有心跳。监控类任务放常开机器或 VPS。
- **"记住上次状态"不可靠**。靠模型记忆去重，重启后可能重复告警。让心跳把状态落盘（文件/JSON）或走 MCP 工具存外部，每次先读再判断。
- **心跳不是 cron**。整点执行的任务（每天 9:00 准时发日报）用定时任务更准；heartbeat 适合"周期巡检、有情况再说"。
- **任务列表会腐化**。每条任务每次心跳都要读一遍，成本线性涨，季度性任务做完记得删。

# 可复用建议

- **模板四段式**：目标 → 判定条件 → 动作（发到哪）→ 静默规则。
- **一条原则**：默认沉默，异常说话。宁可漏报一次再补，也不要周期性废话磨掉你的注意力。
- **状态外置**：上次检查结果写入文件，心跳先读状态再决策，去重和阈值都放在状态里。
- **轻判断、重执行**：HEARTBEAT.md 里只写判断逻辑，重活让 agent 调脚本或 MCP 工具完成。
- **上线节奏**：短间隔观察几天日志 → 确认误报率 → 再进常态运行。

# 总结

HEARTBEAT.md 本质是把"你什么时候想被通知"写成一份机器可执行的值班手册。写得越像 SRE 的告警规则（条件明确、默认静默、状态可查），agent 就越像可靠的值班员；写得越像聊天，它就越像每小时来问"有事吗"的实习生。花半小时把这份文件当生产配置维护，是 OpenClaw 自动化里性价比最高的一步。
