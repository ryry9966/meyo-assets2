## 背景

LLM 本身无状态。在 OpenClaw 这类长期运行的 Agent 场景里，这个问题会被放大：你今天说“commit message 用中文”，明天说“文档里别用 emoji”，后天又说“这个项目统一用 pnpm”——每开一个新会话，助手全部忘光，你得再说一遍。

常见的第一反应是把偏好写进系统提示词。偏好少时没问题，但三个月后 system prompt 里堆了 40 条“注意事项”，模型开始互相矛盾，token 成本也上去了。记忆系统要解决的是：把“用户偏好”从手动搬运，变成一条有生命周期的数据管线。

## 问题：三种常见失败模式

1. **全塞 system prompt**：上下文膨胀，指令稀释，旧偏好永不失效。
2. **全量历史检索**：召回一堆闲聊噪声，真正有用的偏好被淹没。
3. **只写不改**：记忆只增不更新，“用 npm”和“改用 pnpm”并存，模型随机听一条。

根因是多数实现只有“存”和“取”，没有**合并、衰减和分级**。

## 做法：三层记忆 + 五步生命周期

方案分三层：

- **静态画像层**：核心偏好（语言、代码风格、常用工具链），常驻 system prompt，控制在 800 token 以内；
- **情景记忆层**：会话结束后由 LLM 提取摘要，带时间戳和标签入库；
- **检索层**：向量 + 关键词混合检索，按需注入，不常驻。

生命周期五步：**提取 → 存储 → 合并 → 注入 → 衰减**。

存储用统一 schema，先别过度设计：

```json
{
  "id": "toolchain_017",
  "content": "包管理器统一用 pnpm",
  "category": "toolchain",
  "scope": "global",
  "confidence": 0.9,
  "hit_count": 12,
  "updated_at": "2025-06-01"
}
```

两条关键规则：

- **合并**：新旧记忆冲突时走 latest-wins，旧条目带版本号归档，不硬删；
- **注入**：按“相似度 × recency × hit_count”加权，每次最多取 5 条并设 token 上限，防止吃穿上下文。

另外，把记忆做成一组 MCP 工具（`memory_write` / `memory_search` / `memory_forget`）暴露给 Agent 显式调用，而不是纯后台 RAG——调用链路可见，出问题能查日志。

## 踩坑点

1. **提取太激进**。早期连“用户今天问了天气”都存，一周后库里全是垃圾。后来加判定：只存“会影响未来行为”的信息。
2. **矛盾不合并**。模型同时引用新旧偏好，行为抖动。至少要做 latest-wins。
3. **敏感信息入库**。用户贴 API key 求助，被当成“环境信息”记住。入库前加正则 + LLM 双重过滤，命中直接拒存。
4. **只靠向量**。项目名、路径这类专有名词召回不稳，关键词兜底必须有。
5. **静默写入**。上线初期让用户逐条确认新记忆，提取准确率稳了再放开自动化。

## 可复用建议

- **schema 先行**：先定字段再写代码，后面换存储实现不动 schema；
- **个人规模别上向量库**：几百条记忆，一个 JSONL 文件 + 内存检索完全够，先把管线跑通；
- **读写全留日志**：每次注入了哪些记忆、为什么命中，可回溯才可调优；
- **用命中率评估**：注入的记忆被模型实际引用的比例低于 30%，说明提取或检索该返工了。

## 总结

记忆系统不是一个功能，而是一条管线：提取、存储、合并、注入、衰减，缺一环都会退化成“看起来记住了”。我的建议是先做最土的版本——文件存储 + 显式工具调用 + 人工确认，跑通后再逐步加向量检索和自动合并。原则只有一条：宁可少记，不可记错。
