## 背景

单 agent 干活的瓶颈往往不是智力，而是上下文和串行。让它"把这 20 个模块的 API 用法梳理一遍"，它会一路读文件、记笔记、试错，等全部做完，主会话里塞满了中间过程，既贵又难继续追问；同时这一切是串行的，快不起来。

subagent 编排就是针对这个问题的：主 agent 只负责拆任务、派任务、收结果；每个子 agent 拥有独立上下文，干完把结论交回来。OpenClaw 里可以用内置的子会话派生（spawn）能力，也可以通过 MCP / 插件自己拼一套，思路是通用的。

## 问题

拆开看就三个痛点：

1. **上下文污染**：探索过程（读文件、检索、试错）全堆在主会话，真正有用的结论只占一小部分；
2. **串行慢**：互不依赖的任务排队执行，总时长是累加的；
3. **职责不清**：一个 agent 同时干几件事，工具调用互相干扰，出错难定位。

## 做法

我们目前跑得比较稳的流程是五步：

1. **画依赖，判并行**。先列出任务，标注谁依赖谁的输出。有依赖的串行或合并，无依赖的才进并行池。这步偷懒，后面全是返工。
2. **写任务卡**。派发每个子 agent 时带上：目标、输入（文件路径/检索范围）、边界（不许做什么）、工具白名单（只给需要的 MCP 和插件）、返回格式、超时时间。任务卡越明确，子 agent 跑偏概率越低。
3. **隔离执行**。每个子 agent 独立会话，工具集收敛。只读调研任务绝不给写权限。
4. **产物落盘**。约定子 agent 把详细结果写成独立文件（如 `reports/auth-module.md`），上下文里只回传：结论摘要 + 产物路径 + 状态（成功/失败/部分完成）。
5. **汇总与兜底**。主 agent 读取各份产物做合并；某个子 agent 失败时明确记录缺口，由主 agent 补做或标注跳过，绝不静默吞掉。

一个实际例子：做代码迁移评估时，派 3 个子 agent 分别扫描认证、支付、定时任务三个模块的旧 API 调用点，各自产出报告文件，主 agent 汇总成迁移清单。原来串行跑约 20 分钟且主会话爆掉，并行后 7 分钟收工，主会话只多了三段摘要。

## 踩坑点

- **伪并行**：看着独立，实际 B 需要 A 的结论，并行后 B 只能瞎猜再返工。依赖图先行。
- **共享写冲突**：多个子 agent 同时改同一文件，后写覆盖先写。约定各写各的文件，合并动作只留给主 agent。
- **回流过厚**：子 agent 把整个探索过程贴回来，主上下文照样爆炸。返回格式里强制"只给结论和路径"。
- **并发失控**：一口气 spawn 十个，token 消耗和接口限速一起爆。经验值是 3-5 个一批，分批跑。
- **权限过宽**：图省事给子 agent 全量工具，出问题难排查。白名单按任务最小化。
- **静默失败**：子 agent 挂了但返回空结果，主 agent 照常汇总，产出看起来完整实则缺块。状态字段是必须的。

## 可复用建议

- 把任务卡做成模板（目标/输入/边界/白名单/返回格式/超时），沉淀成插件或脚本，不要每次手写 prompt；
- 产物落盘优先于上下文回流，token 消耗立降一个量级；
- 子 agent 设计成幂等可重跑，失败重试才没有心理负担；
- 新场景先用 2 个子 agent 小规模验证，跑通再扩并发；
- 定期回看子 agent 的产物质量，检查拆分粒度——拆太细，调度开销会吃掉并行收益。

## 总结

subagent 编排的核心不是"多开几个 AI"，而是三件事：**上下文隔离、任务并行、结构化汇总**。先把任务拆干净、把权限收窄、把产物落盘，并行才有收益；否则只是把一个混乱的会话变成五个。从两个子 agent 开始跑通一轮再扩，是最省事的路径。
