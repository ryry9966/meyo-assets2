## 背景

跑过自动化 Agent 的人大概率都遇到过：任务执行到第 3 步，搜索 API 开始 429；或者深夜批量抓取，上游 503 一片。Agent 自身逻辑没毛病，坏在外部依赖上。而多数框架的默认行为是抛异常、任务终止，或者更糟——模型看到空结果，自己编一个答案交差。

## 问题拆解

外部 API 故障不是一种故障，是四种：

1. **瞬时故障**：429、503、超时，重试大概率能过；
2. **持续故障**：配额耗尽、服务下线，重试只是烧钱；
3. **参数性失败**：400、鉴权过期，重试无意义，得修调用方；
4. **部分成功**：批量任务挂一半，状态不一致。

对这四类用同一套策略（无脑重试），是 Agent 自动化最常见的翻车原因。

## 我的做法

给所有工具调用套一层统一执行器，四个动作：

**一、错误分类。** 在执行器里把 HTTP 状态码和异常归一化成结构化错误，比如 `{type: "rate_limit", retryable: true, hint: "429, wait 30s"}`。关键是把它作为工具结果返回给模型，而不是抛异常。模型拿到结构化 hint 能自己决定降级或换路，拿到原始堆栈只会胡乱重试。

**二、有界重试。** 只对 retryable 的错误重试，指数退避加抖动，上限 3 次。写操作必须带幂等键，否则重试可能重复建单、重复发消息。

**三、熔断。** 同一工具连续失败 N 次（比如 5 次），标记为不健康，冷却 5 分钟内直接走降级路径，不再发真实请求。熔断状态放 Redis 这类共享存储，多实例部署才不会各熔各的。

**四、降级要有出口。** 优先级依次是：备用 API → 带时间戳的缓存数据（明确告知可能过期）→ 持久化任务状态、中断等待恢复后续跑。最不该选的是"返回空结果让模型自由发挥"。

## 踩坑点

- **超时要小于任务预算。** 单次 30s 超时 × 重试 3 次 = 90s，如果整个任务 SLA 是 60s，重试设计再好也没用。先算总预算再分配。
- **别重试非幂等操作。** 吃过亏：重试导致同一份报表发了三遍。
- **别把失败藏起来。** 见过 Agent 在工具连续失败后"成功"完成任务——是它编的。工具结果里必须显式区分"查询成功但为空"和"查询失败"。
- **熔断粒度。** 按「工具 + endpoint」熔断，不要按整个 Provider，否则一个接口抖动会连累其他健康接口。

## 可复用建议

- 所有插件 / MCP 工具接入统一错误 schema，团队内约定 `retryable` 字段语义；
- 每次重试记一条带 request id 的日志，事后复盘才不抓瞎；
- 在 Agent 的系统提示里写清降级决策规则，别指望它临场发明；
- 长任务每步落盘状态，恢复时从断点续跑，而不是从头再来。

## 总结

错误恢复的目标不是消灭失败，而是让失败**可见、有界、可续**。四个原则：分类再重试、写操作必幂等、熔断要有共享状态、降级永远优于编造。做到这几点，外部 API 挂掉时，你的 Agent 才是"降级运行"，而不是"一本正经地胡说"。
