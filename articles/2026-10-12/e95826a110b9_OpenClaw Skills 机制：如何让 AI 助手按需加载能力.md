## 背景

OpenClaw 的能力扩展主要有两条路：MCP 工具和 Skills。MCP 解决“接得上”的问题——把外部系统暴露成可调用的工具；Skills 解决“用得对”的问题——把某一类任务的操作知识（步骤、参数约定、失败兜底）写成结构化文档，挂进 agent 的能力索引。

Skills 的核心设计是**渐进式加载**：session 启动时，agent 只读入每个 skill 的 `name` 和 `description` 两行元数据；当任务描述命中某个 skill 时，才把完整正文及引用的脚本、资源文件载入上下文。装 50 个 skill，常驻开销也只是 50 段简介。

## 问题

不按需加载的后果，做 agent 的都见过：所有工具说明、操作手册全塞进 system prompt，上下文一开跑就占掉大半；无关指令互相干扰，模型在 20 个能力里挑错那个；改一处配置要动整段 prompt，无法单独维护。本质上这是检索问题——能力应该在对的时机进入上下文，而不是一直在。

## 做法

以给助手加一个“清理服务器日志”的 skill 为例：

1. **建目录**：在 `~/.openclaw/skills/log-cleanup/` 下建 `SKILL.md`（跟项目走的能力可放 workspace 级 skills 目录）。
2. **写 frontmatter**：name 用小写短横线；description 是触发路由的唯一依据，要像写检索词一样写——覆盖“做什么、什么时候用、输入是什么”，例如：“清理远程服务器日志文件，当用户要求释放磁盘空间、删除或归档旧日志时使用”。
3. **写正文**：操作步骤、参数示例、失败兜底（找不到路径怎么办、删除前是否需确认）。控制在几十行内，让模型读到的是一页说明书，不是一本书。
4. **能脚本化的别让模型背**：清理逻辑写成 `scripts/cleanup.sh`，正文只教 agent 何时以什么参数调用。脚本执行是确定性的，模型复述不是。
5. **验证**：重载 session 后直接提一个匹配任务，观察是否触发；也可在会话里问“你现在有哪些能力”，确认元数据已挂载。

## 踩坑点

- **description 太泛或太短**。“处理文件”这种描述既难触发也易误触发。描述里写清动词、对象、场景。
- **正文过长**。SKILL.md 写到几百行，等于把 prompt 膨胀换了个位置。主文档留主干，细节拆到引用文件里按需再读。
- **触发歧义**。两个 skill 的 description 高度重叠时，路由会摇摆。一个 skill 只管一件事，重叠部分合并或明确划界。
- **脚本路径假设错误**。agent 的工作目录不一定是 skill 目录，脚本里的相对路径容易翻车，用绝对路径或在正文中写明调用方式。
- **改了不生效**。SKILL.md 是启动时索引的，改完记得重载，别在旧 session 里排查半天。

## 可复用建议

- description 模板：`<动作> + <对象> + <触发场景> + <边界>`，照着填，命中率明显提高。
- 一个 skill 一件事；描述里出现“以及”“同时”就该拆。
- 需要 API key、依赖环境的，环境装在宿主机，skill 只写使用说明——它是说明书，不是安装包。
- 团队共用的 skill 放 workspace 跟项目走，个人习惯类的放用户级目录。
- 定期翻 session 日志：哪些 skill 从没触发过、哪些被误触发，description 是需要迭代的，不是写完就完。

## 总结

Skills 机制的价值不在“能装多少插件”，而在把能力的索引与正文分离，让上下文始终只装当前任务需要的东西。写好一段 description 的投入产出比，远高于堆一个大而全的 SKILL.md。建议从一两个高频任务开始试，先跑通触发链路，再逐步沉淀成自己的能力库。
