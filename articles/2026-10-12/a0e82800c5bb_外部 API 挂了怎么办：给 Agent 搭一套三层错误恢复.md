## 背景

跑过一段时间 OpenClaw 的人都会有体感：Agent 流程里最不稳定的就是外部依赖。MCP server 连的第三方 API、插件里调的搜索/天气/行情接口、自动化脚本依赖的 webhook——它们不会提前打招呼就 5xx、限流、超时。普通应用挂了顶多报个错，Agent 的麻烦在于失败会进入推理循环：模型看到报错后可能瞎编一个答案、疯狂重试，或者干脆卡死整个会话。

## 问题

实际跑下来，故障通常表现为四种：

1. 工具返回错误后，模型“脑补”结果继续往下走（最危险，用户完全无感知）；
2. 模型自己反复重试同一个坏接口，把限流打得更死，token 也烧得飞快；
3. 工具调用没有超时，一个挂起的请求阻塞整个 agent loop；
4. 接口返回 200 但数据是降级/过期的，静默污染下游。

根因只有一个：错误处理交在了模型手里，而模型天然倾向“把事情办成”。

## 做法：把恢复逻辑做成三层

**第一层：工具层包装（必做）。** 每个调外部 API 的工具统一走一个 wrapper：

- 硬超时：连接 5s、总时长 15s，绝不依赖库的默认值；
- 错误分类：429、5xx、超时算可重试；400/401/403/404 直接失败，重试只会浪费配额；
- 重试：指数退避 + 抖动，最多 2 次，且绝不在工具层和提示词里同时重试。

**第二层：熔断。** 同一上游连续失败 3 次就打开熔断器，冷却 60 秒内直接 fail fast。给模型的是一个立刻返回的结构化错误，而不是让它对着挂起的连接干等。OpenClaw 这类常驻进程适合把熔断状态做成插件内单例，重启才清零。

**第三层：降级。** 熔断期间别让 skill 直接死掉：

- 只读接口：返回本地缓存的 last-good 值，并附上数据时间戳；
- 有备胎的：切备用 provider；
- 都没有：返回 `{ok:false, retryable:true, reason:"upstream_down"}`，让 Agent 明确告诉用户“这个能力暂时不可用”。

关键点：给模型的错误必须是结构化的。自然语言报错会诱发模型去“解读”它，结构化字段才能让它走对分支。

另外两个容易被忽略的点：写操作要带幂等键——超时不等于失败，盲目重试 POST 会造成重复下单、重复发消息；每个 skill 调用设一个总墙钟预算，超了就终止，不要无限等。

## 踩坑点

- **双重重试**：wrapper 里重试 3 次，提示词又让模型“失败了再试试”，最坏变成 3×N 次。重试策略只放一层，建议放工具层。
- **无差别重试**：401 重试一百次也不会好，只会烧 token 和触发风控。
- **降级不带时间戳**：模型拿着三小时前的缓存当实时数据讲，比直接报错更糟。
- **报错写成大段自然语言**：模型会把它当上下文继续推理，而不是当失败信号。
- **熔断只存在单进程内存里**：网关多实例部署时各实例各自为政，等于没熔断。

## 可复用建议

- 把统一错误包络 `{ok, error_code, retryable, hint, data_ts}` 做成公共库，所有插件复用；
- 只读 API 加一层带 TTL 的本地缓存，既抗抖动又省配额；
- 上线前故意把某个工具指向一个死地址跑完整流程，确认 Agent 会如实报告而不是编造；
- 日志里把 `retry` / `breaker_open` / `fallback` 三类事件单独打标，出问题时五分钟内能定位。

## 总结

外部 API 一定会挂，问题不是“会不会”，而是“挂的时候 Agent 表现得像不像个靠谱系统”。核心原则：恢复逻辑下沉到工具层，用熔断止血、用降级保可用、用结构化错误让模型走对分支、用诚实的失败报告保住信任。这套东西一个下午就能搭完，但每次故障都能帮你省掉几小时的排查。
