## 背景

跑多 Agent 流水线时，最贵的资源不是 token 单价，而是主会话的上下文。OpenClaw 里通过 MCP 工具或插件拉起子 Agent 很方便，但方便的另一面是：如果不做 session 隔离，子 Agent 的每一次工具调用、每一份读进来的文件、每一段报错堆栈，默认都会混进主会话历史。

## 问题

我们最早没做隔离，主会话几千条消息里八成是子 Agent 的中间过程。症状很典型：

- 上下文涨得快，成本和延迟一起涨；
- 主 Agent 开始“记得”无关细节，回答被带偏；
- 子 Agent 改了共享工作目录里的文件，主流程接着用，状态对不上；
- 排查时分不清哪条记录是谁写的。

本质上，session 既是执行边界也是记忆边界，边界不清，污染只是时间问题。

## 做法

我们的约定就三句话：子 Agent 独立 session、输入给摘要、输出交摘要。

1. **独立 session 派发**。拉起子 Agent 时分配全新 session id，主会话历史一个字不带。子 Agent 工作目录指向任务级 scratch 目录（如 `work/<task-id>/`），读写都在里面完成。
2. **定义输入契约**。只传任务描述 + 最小必要上下文：目标、涉及路径、约束、超时。不要图省事把主会话最后 N 条贴过去。
3. **定义输出契约**。子 Agent 只回传结构化摘要：结论、产物路径、阻塞项。原始日志落盘到 scratch 目录，主会话里只留路径引用，需要审计再翻。
4. **收敛工具面**。子 Agent 只挂必需的工具，禁止再派生子 Agent（或递归深度限 1），避免隔离层被套娃击穿。

这样主会话留下的痕迹，只有一条“派发了什么、拿回了什么”。

## 踩坑点

- **上下文给太少**：子 Agent 按猜测干活，方向错了还得重派。最小上下文是迭代出来的，建议把契约写成模板慢慢补。
- **共享目录冲突**：两个子 Agent 同时改一个文件，谁后写谁赢。任务级 scratch 目录是底线。
- **session id 复用**：有一次图省事复用旧 id，子 Agent 一启动就继承了半屏陈旧历史，排查半天。隔离的前提是 id 干净。
- **异步返回时机**：主流程不阻塞继续跑，等结果回来时前置假设已经变了。要么同步等，要么拿到结果后显式校验状态。
- **静默失败**：子 Agent 挂了却回了个空的“成功”，主流程拿着空摘要继续走。输出契约里必须有明确的失败状态位。

## 可复用建议

- 把 session 当记忆边界：默认隔离，共享必须显式声明。
- 摘要进、摘要出（summary in, summary out），中间过程一律落盘。
- 给主会话留“上下文预算”，派发和回收各占一小段就够。
- 契约模板化：输入模板、输出模板、目录约定，三件套齐了再开并行。

## 总结

session 隔离不是什么高级特性，就是工程纪律：执行可以并行，记忆必须有界。子 Agent 干完活，交回一份干净的摘要，主会话保持短而准——这件事做对之后，多 Agent 流水线的可调试性会好一个量级。我们踩过的坑基本都是“图省事”换来的，值得。
