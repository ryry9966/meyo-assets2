## 背景

OpenClaw 是模型无关的 agent 网关：`models.json` 里可以同时挂云端和本地 provider，主模型之外还能配 fallback 链，甚至按 agent 粒度钉死模型。能力都在，缺的往往不是配置，而是策略。我观察到两种极端都很常见：全走云端，月账单里最贵的其实是摘要、分类这类"轻任务"；全走本地，多步工具调用一多，成功率掉得难看。

## 问题：一刀切的三个代价

1. **成本错配**：token 花在了不需要旗舰模型的地方
2. **质量塌方**：长上下文 + 多工具 + 本地小模型，基本等于给 agent 埋雷
3. **隐私默认出网**：笔记、聊天记录、内部文档不该无差别地发出去

## 做法：按任务画像分流

**第一步，任务分三类：**

- 高频轻任务（摘要、格式化、路由判断）→ 本地小模型
- 中等任务（日常问答、单文件小改动）→ 本地优先，失败再升级
- 低频重任务（多步 tool use、规划、长会话）→ 云端旗舰

**第二步，两层配置。** 全局层：云端为主模型，本地做可用性兜底；agent 层：给跑流水线的 agent 直接指定本地模型。示意如下（provider 按实际情况改）：

```json
{
  "agents": {
    "defaults": { "model": "openai/gpt-...", "fallbacks": ["ollama/qwen3:14b"] },
    "summarizer": { "model": "ollama/qwen3:14b" }
  }
}
```

**第三步，观测再收敛。** 给关键 agent 记三个数：用了哪个模型、token 消耗、重试次数。跑一两周，用数据划边界，而不是拍脑袋。

## 踩坑点

- **本地模型的 function calling 格式漂移**：工具一多就崩。我的规则是本地只接"零工具或单一工具"的任务
- **上下文窗口**：本地 8k~32k 塞不下长会话，先截断或摘要再喂
- **fallback 顺序别想当然**：把本地模型放在质量敏感任务的后备位，等于给失败加一道确认
- **VRAM 争抢**：本地推理和 IDE 补全、浏览器抢显存，OOM 的表现是"莫名超时"，先查显存再查网络
- **重试风暴**：本地挂了切云、云也慢，重试必须有指数退避和次数上限

## 可复用建议

路由前问三个问题：**要出网吗？要强工具调用吗？延迟敏感吗？** 三个都不满足才考虑本地。另外准备一组"能力探针"——固定的小任务集（一次 tool call、一次 JSON 输出、一次长摘要），换模型或升级版本后跑一遍，别等线上才发现回归。最后建一张模型预算表，按任务类别估 token 量，月度对账。

## 总结

多模型路由不是省钱小技巧，而是把任务难度和模型能力对齐的工程手段。OpenClaw 把选择权交给了你，边界要靠分类、配置和数据一点点磨出来。如果不知道从哪开始，先落地"摘要走本地、规划走云端"这一条，比一次改完所有配置靠谱得多。
