## 背景

OpenClaw 的优势之一是模型可插拔：同一个 Agent 网关后面，既可以接 GPT 这类云端 API，也可以通过 Ollama / LM Studio 挂本地模型。但常见用法是两个极端——要么全走云端（账单难看、隐私悬空），要么全走本地（复杂任务质量崩、Agent 循环卡死）。多模型路由要回答的不是"哪个模型更强"，而是"哪类任务交给哪类模型"。

## 问题

我自己的场景：一个 7×24 跑着的心跳和定时任务（消息分类、笔记整理、定时摘要），加上日常交互式的规划、写代码、多步工具编排。前者量大但简单，后者量小但难。全走 GPT 时，每月 token 开销里八成花在"分类、格式化"这种小活上；全走本地 7B 模型时，多步工具调用经常解析失败。

## 做法

按三个维度给任务分层：**复杂度、频率、敏感度**。

1. **云端 GPT 负责**：交互式规划、代码生成、多步 Agent 编排、长上下文任务。
2. **本地模型负责**：高频低难度自动化（定时摘要、消息分类、字段抽取），以及涉及私人笔记、密钥相关内容的任务。
3. **配置路由**：默认模型设为本地，交互会话和复杂 Agent 单独覆写为 GPT；再配一条 fallback 链，云端不可用时降级到本地，保证心跳任务不中断。
4. **加日志**：一个简单 hook 记录每次调用的模型、耗时、token 数、是否成功。路由策略是调出来的，不是设计出来的。

## 踩坑点

- **本地模型的工具调用是重灾区**。聊天质量看着不错，一到 function call 就吐畸形 JSON，Agent 表现为"卡住不动"。切换前先用你真实的 MCP 工具集单独压测 tool calling，别只看对话评测。
- **上下文长度差异**。本地模型往往 8k–32k，长会话静默截断后行为诡异。路由规则除了任务类型，还要加上下文长度判断。
- **fallback 会反向烧钱**。本地失败自动升到 GPT 很方便，但一旦本地配置坏了，可能一整夜的高频任务全走云端。给 fallback 触发加告警或每日预算上限。
- **别让隐私数据被 fallback 送出去**。敏感任务要禁用向上 fallback，宁可失败后在本地重试。

## 可复用建议

- 维护一张三层任务表，直接落进配置，新任务先归层再上线。
- 每层留 5–10 条冒烟用例，模型升级后跑一遍再切流量。
- 经验法则：批量自动化走"本地优先、失败升级"，交互式规划走"云端优先"。端到端延迟要实测——弱 GPU 上的本地模型，可能比 API 还慢。

## 总结

多模型路由的核心是把"任务画像"对上"模型画像"：频率看成本，复杂度看能力，敏感度看去向。从两三条粗规则起步，靠日志持续迭代，比一开始就设计精巧的分级策略更有效。
