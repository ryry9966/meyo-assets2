## 背景

信息源越订越多，真正读进去的越来越少。RSS 没死，它只是缺一层"压缩"。这篇帖子记录我给自己搭的一条自动化管线：RSS 拉取 → AI 摘要 → 每日日报，全程跑在自托管环境上，由 OpenClaw 的定时任务触发，每天早上推一份摘要到 IM。跑了一个多月，值得把经验沉淀下来。

## 问题

三个痛点：

1. 订阅 60+ 个源，每天原始条目几百条，人工筛不动；
2. 大量条目是同一事件的重复报道或低信噪比内容，逐条打开成本太高；
3. 现成 SaaS 工具要么闭源、要么摘要质量不可控，数据还要过第三方。

目标先定死：**AI 只做导读，不做替代**——压缩信息、保留原文链接，最终判断权留给人。

## 做法

架构分四层，每层独立可替换：

1. **拉取层**：自托管 Miniflux 管订阅，靠 ETag / If-Modified-Since 做增量拉取，30 分钟一轮，不打扰源站。
2. **过滤层**：规则粗筛——关键词黑名单、标题去重、只保留 24h 内条目，先把几百条压到 30~50 条。
3. **摘要层**：粗筛后的条目分批进 LLM，结构化输出：一句话结论、3 个关键点、值得深读的理由、1-5 分评分。prompt 里明确"只允许基于原文，不确定就写不确定"。
4. **分发层**：摘要 + 原文链接拼成 Markdown 日报，OpenClaw agent 定时任务每天 8 点推到 Telegram；评分 ≥4 的条目单独实时推送。

整套东西就是一个脚本加一个 skill，跑完发心跳，安静即异常。

## 踩坑点

- **摘要幻觉**：早期 LLM 会"补全"原文没有的细节。解法是要求每条关键点都能对应原文，抽查时按链接回溯验证。
- **RSS 正文残缺**：很多源 feed 里只有 summary，直接摘要等于摘要简介。加一步 readability 全文抓取；抓不到就降级为"标题级摘要"，不硬编。
- **去重不彻底**：同一事件十家媒体各发一遍，标题去重抓不住。改成标题 + 首段 embedding 聚类后才压干净。
- **成本失控**：最初全量进 LLM，日 token 消耗比预期高一个量级。改成"规则粗筛 → embedding 粗排 → LLM 精排"三级漏斗后降了约 80%。
- **过度平滑**：所有摘要看起来同等重要。加评分字段并按评分排序日报后，问题基本消失。

## 可复用建议

1. **分级订阅**：核心源全文摘要，边缘源只出标题 + 一句话，别一视同仁。
2. **结构化输出**：摘要 prompt 固定 JSON schema，下游拼装才稳定。
3. **日报聚合优于实时推送**：实时只留给高评分条目，否则管线本身会变成新的噪音源。
4. **每周人工审一次被过滤的条目**：防止过滤器悄悄吃掉重要内容。
5. **全链路留痕**：feed 原文、LLM 输入输出都落盘，方便回放和调 prompt。

## 总结

这条管线跑了一个多月，日均信息处理从"刷不完"变成"10 分钟读完日报"。核心经验就两条：**过滤做在摘要之前，AI 做导读不做替代**。它不会让你"知道得更多"，但能用更少的注意力覆盖同样的信息面——这已经是很大的改进。管线本身就是几个脚本加一个定时任务，欢迎按自己的源结构改。
