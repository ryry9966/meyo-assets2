## 背景

写自动化任务时，我们默认它"跑一次就完事"。但在 OpenClaw 这类 Agent 环境里，任务被触发两次是常态而不是异常：webhook 超时后上游重发、定时任务与上一次还没结束的执行重叠、Agent 遇到不确定结果自行重试，或者有人手动点了两下"重新运行"。

幂等性（idempotency）就是让同一个任务执行多次，最终状态和执行一次完全一致。它不是锦上添花，而是你敢开重试、敢开调度的前提。

## 问题：不出事只是运气好

几个典型的非幂等写法：

- 收到事件就往群里发一条消息——重试后发两条；
- 定时脚本每次追加写库——重叠执行产生重复行；
- Agent 调 MCP 工具"创建一条记录"——超时后不知道成没成功，重试就重复创建。

共同点：副作用是"累加式"的，执行次数会改变最终状态。

## 做法：四个层次，由内到外

**1. 优先用目标态语义。** 把"创建 X"改成"确保 X 存在"：先查再写，或按唯一键 upsert。凡是"把世界调整到某个状态"的操作，天然可重放。

**2. 从触发源派生幂等键。** 键必须来自事件本身，而不是执行过程：优先级是上游事件 ID > 内容哈希 > 任务名 + 时间窗。把它传给支持幂等头的下游 API，或自己记录。

**3. 维护一张去重台账。** 最简实现是一张表加唯一约束：

```sql
CREATE TABLE processed_events (
  event_key  TEXT PRIMARY KEY,
  status     TEXT DEFAULT 'done',
  created_at TEXT DEFAULT (datetime('now'))
);
```

执行前 INSERT，冲突就跳过；INSERT 成功才执行副作用。

**4. 原子地"认领"。** 并发场景下"先查再做"有竞态：两个实例都查到"没做过"。用数据库唯一约束、Redis SETNX 或文件锁，让"认领"本身成为原子操作，谁抢到谁执行。

## 踩坑点

- **用 UUID 或时间戳当幂等键。** 每次重试都生成新键，等于没做。键必须能从"同一次触发"稳定推导出来。
- **时间窗粒度选错。** "任务名 + 日期"适合日级任务；一天要跑多次的任务会被误杀。先想清楚"什么算重复"。
- **台账和副作用之间崩掉。** 记了 done 但动作没执行（或反过来）。用 pending → 执行 → done 的状态机，恢复时以真实下游状态为准，不轻信本地记录。
- **外部 API 不支持幂等头。** 那就必须把去重挡在调用之前，别指望对方兜底。
- **补偿逻辑忘了幂等。** 清理、回滚同样可能跑两次。"删到不存在"是安全的，"每次删一条"不安全。

## 可复用建议

- 把"任何任务都会在最糟糕的时刻至少跑两遍"当成默认设计假设。
- 读操作随便重试；写操作先问一句：这个调用跑两遍会怎样？
- 显式验证：把同一任务连跑两次，断言状态不变、无重复产物。写成固定集成测试，比口头约定可靠。
- 在项目里沉淀一个统一的去重中间件（比如给 MCP 工具外层包一层），比每个脚本各写一套更不容易出错。

## 总结

幂等性解决的不是性能问题，而是信任问题：只有重复执行无害，你才敢放开重试、并发和调度，自动化才敢真正交给机器。下次写任务时，先花五分钟回答"它跑两遍会发生什么"——这五分钟，通常比后面排重、清脏数据省下的不止一个晚上。
