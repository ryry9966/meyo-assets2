## 背景

团队每天的日报，多数时候是"打开五个面板，复制粘贴，再凭记忆补两句"。信息散落在服务器日志、git 提交、CI 记录和群聊里，人肉汇总既耗时又容易漏。OpenClaw 本身具备定时任务、agent 调用和消息通道推送能力，很适合把这件事做成一条固定流水线：数据进、报告出，人只做最后确认。

## 问题

直接让 agent"看日志写日报"，实际会踩三个坑：

1. 原始日志又长又脏，token 开销大，关键信息被淹没；
2. 模型自由发挥，每天报告结构不一样，没法横向对比和归档检索；
3. 任务静默失败，连续几天没收到日报才发现，事后追溯困难。

## 做法

把流水线拆成三层，各层独立可测：

**收集层（纯脚本，不经模型）。** 用 20 行左右的脚本把多源日志归一化成 JSONL：`{ts, source, level, msg}`。这一步做规则过滤：丢弃 DEBUG、合并重复条目、按关键词保留 error/warn/deploys。实测这一步能把进入模型的数据量压掉 90% 以上。

**加工层（OpenClaw 定时任务 + agent）。** cron 在每天 18:30 触发，agent 读取当天的 JSONL，按固定 schema 输出：

```json
{
  "date": "2025-06-12",
  "summary": "一句话总结",
  "highlights": ["关键变更，最多 5 条"],
  "risks": ["未处理告警"],
  "metrics": { "commits": 14, "errors": 2 }
}
```

prompt 里明确要求只输出 JSON、字段不得增删；解析失败就带着报错信息自动重试一次。

**输出层。** JSON 渲染成 markdown 模板，经通道插件推送到群，同时按日期落盘归档，方便回溯和对比。

## 踩坑点

- **时区**：cron 跟服务器时区走，日志却是 UTC，"今天"的边界会错。统一在收集层转成同一时区并打标。
- **敏感信息**：日志里偶有 token、内网地址。脱敏必须放在进模型之前，不要指望模型帮你保密。
- **重复推送**：手动重跑任务导致同一份日报发两遍。给每次运行生成 run_id，推送前查重。
- **幻觉**：模型会把日志里没有的事"总结"出来。保留原始输入快照供抽查；risks 字段强制要求标注来源行号。
- **静默失败**：加心跳——任务完成后写一条状态记录，另一个低频任务检查"今天有没有心跳"，没有就告警到群。

## 可复用建议

- 三层解耦是核心：收集层不依赖模型，加工层不关心来源，输出层可换通道。换数据源或换推送渠道都只动一层。
- schema 单独存成文件，prompt 引用它，别把格式要求散落在字符串里。
- 先只接一个数据源跑一周，确认格式稳定、抽查无幻觉，再逐个接入 git、CI 等来源。
- 成本上，先过滤再进模型，比"全量塞给模型让它挑重点"更便宜也更稳定。

## 总结

日报的价值不在"生成"这个动作，而在稳定、格式一致、可追溯。LLM 在这条流水线里只做两件事：压缩信息、归纳要点；结构化和可靠性全部交给普通代码。想清楚这个边界，流水线跑起来之后基本不用管，偶尔调整一下过滤规则就够了。
