# 心跳的设计取舍：轮询还是推送

## 背景

OpenClaw 的 heartbeat 本质上是一个定时轮询：agent 每隔 N 分钟被唤醒一次，跑一遍轻量检查，有事就说话，没事就沉默。不少新用户的第一反应是"这不够实时"，想直接改成 webhook 推送。我们团队两种模式都跑过一段时间，这里记录一下实际的取舍过程。

## 问题

轮询和推送的差别不在"能不能做到"，而在三个工程指标上：

- **时效性**：轮询的延迟上限就是 interval；推送理论上秒级到达
- **成本**：轮询无论有没有事都要消耗一次模型调用；推送只在事件发生时花钱
- **可靠性**：轮询是 agent 主动拉，通道故障表现为"整体变慢"；推送依赖外部通道可达，webhook 丢了往往是静默失败

## 做法

我们的最终形态是混合架构：**推送管触发，心跳管兜底**。

1. 保留默认 heartbeat（30 分钟档），把它当"对账"用：检查推送是否漏了、任务是否卡住，日报类内容集中在这里产出。
2. 高时效事件单独走推送：邮件、日历、Git 仓库变更这类事件，通过 Cron 任务或插件 webhook 直接触发对应 agent 会话，不等服务下一次心跳。MCP 工具侧产生的状态变化也走这条路。
3. 心跳 prompt 写明"只在有事时回复"，无事保持静默，避免每半小时一条"一切正常"。
4. 配置 active hours，夜间心跳降频或关闭，只保留推送白名单。

## 踩坑点

- **interval 调到分钟级后 token 消耗约是原来的 30 倍**，而其中 95% 的唤醒什么都没发生。高频轮询只在"轮询结果本身要驱动自动化"时才值得。
- **推送通道是单点**：一次 webhook 配置错误，我们三天没收到任何提醒，直到某次心跳对账才发现。这就是不能全删轮询的原因。
- **推送和心跳并发处理同一事件会重复执行动作**。我们的解法是给每个事件带去重键，agent 执行前先查状态。
- **心跳记录会持续撑大会话上下文**，跑一周后响应明显变慢。定期开新会话、心跳记录单独存放，比反复调 prompt 更有效。

## 可复用建议

- 事件驱动优先、轮询兜底，两者都按幂等设计——幂等比精细的去重逻辑更重要
- 心跳间隔按"能接受的最大延迟"倒推，不要按"想要多实时"正推
- 任何静默失败的通道都要配一个周期性对账机制，心跳天然适合干这个
- 心跳 prompt 越短越稳，把它当成 cron 的执行说明，而不是聊天

## 总结

轮询换推送不是升级，而是用"延迟"换来了"通道可靠性"这个新问题。OpenClaw 的 heartbeat 看起来朴素，但它给系统提供了一个不依赖任何外部服务的基线节拍。我们的经验是：**推送负责快，心跳负责稳**——删掉任何一个，另一个都会在几周内出问题。
