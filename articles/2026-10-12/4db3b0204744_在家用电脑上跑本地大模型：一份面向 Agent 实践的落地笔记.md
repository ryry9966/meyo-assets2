## 背景

做 Agent / MCP 自动化时，很多任务要碰私有数据：本地文件、聊天记录、截图、日志。全走云端 API，隐私和成本都是长期负担。本地模型的价值不在于"媲美旗舰"，而在于：成本固定、可离线、数据不出门。对 OpenClaw 用户来说，比较现实的定位是**分层架构**——日常自动化（格式化、摘要、规则判断）交给本地小模型，复杂规划再兜底到云端。

## 问题

家用硬件的现实约束很直接：没有 A100，只有 8–24GB 显存的消费级卡，或者纯 CPU。核心问题就三个：跑多大的模型？量化到什么程度？量化之后工具调用（function calling）还稳不稳？

## 做法

1. **摸清硬件上限**。显存 ≈ 模型权重 + KV cache（随上下文长度线性增长）。参考值：7B Q4 约 4–5GB，14B Q4 约 9GB，32B Q4 约 20GB，别忘了给 KV cache 留余量。
2. **选运行时**。Ollama 上手最快；llama.cpp / LM Studio 可调参数更细；显存充足且需要并发就上 vLLM。三者都提供 OpenAI 兼容接口，接入成本差不多。
3. **选模型**。优先官方支持 function calling 的 instruct 版本。Agent 场景宁可选小一号但工具调用稳定的，不要大一号但量化很狠的。
4. **接入 Agent**。base_url 指到本地端口，温度压到 0–0.3，先跑一个最小 MCP 工具调用冒烟测试，再挂完整插件链。
5. **做分层路由**。在 agent 框架里配置模型路由，或自己写个轻量判断层：简单任务走本地，复杂任务走云端。

## 踩坑点

- **KV cache 比想象中吃显存**。长上下文能把 8GB 卡直接打爆，务必限制 context 长度或开启 KV cache 量化。
- **量化对工具调用的影响远大于对话**。Q4 以下容易出现 JSON 参数畸形、漏字段。从 Q4_K_M 起步；工具调用频繁失败时，先升量化再排查 prompt。
- **首次加载慢不是推理慢**。模型冷加载动辄几十秒，自动化脚本里设置 keep_alive 让模型常驻，否则定时任务体验很差。
- **纯 CPU 别抱幻想**。CPU 跑 14B 以上基本无法支撑交互式 agent，CPU 路径留给批量离线任务。
- **流式输出兼容性**。个别运行时的 stream 格式与 OpenAI 有细微差异，接 agent 框架前先用 curl 裸测一遍，能省掉很多玄学排查。

## 可复用建议

- **用真实任务做 benchmark，别只看榜单**。对 agent 来说，`tokens/s` 和工具调用成功率这两个指标就够了，MMLU 高两分没有意义。
- **维护一组冒烟用例**：3–5 个包含工具调用的典型任务，每次换模型或量化等级后跑一遍，几分钟就能判断"能不能用"。
- **模型名参数化**。配置文件里把模型 ID 做成变量，本地/云端一键切换，方便 A/B 对比和故障回退。

## 总结

本地 LLM 在家用硬件上已经完全可用，但要摆正定位：它是隐私友好、成本固定的"日常自动化工人"，不是全能旗舰。目前性价比最高的组合是——小模型 + 稳定工具调用 + 分层路由。先跑通最小链路，再逐步加上下文和插件，别一上来就追求本地全托管。

以上数据基于我本机（RTX 4060 Ti 16GB + 32GB 内存）的实测，欢迎在评论区交流不同硬件下的配置参数。
