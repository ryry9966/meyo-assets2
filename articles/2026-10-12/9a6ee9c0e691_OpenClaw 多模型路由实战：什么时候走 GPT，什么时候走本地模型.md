## 背景

OpenClaw 的 agent 跑起来之后，token 消耗很快：一个带工具调用的任务来回十几轮，一天下来云端账单不小。同时我们不少场景涉及内部文档和客户数据，走云端始终有合规顾虑。本地模型（Ollama / vLLM 起的 7B–14B）免费、数据不出机器，但能力上限摆在那里。多模型路由要解决的不是“哪个模型更好”，而是“什么任务配什么模型”。

## 问题

两种极端我们都试过：全走 GPT，账单和隐私审查都难受；全走本地，agent 在工具调用环节频繁产出不合法的 JSON，循环重试直接卡死。更深的痛点是：路由决策散落在各个 workflow 里，谁也说不清某个任务为什么用了这个模型，出了问题没法归因。

## 做法

1. **任务分级**。A 类是多步工具调用、长上下文推理，必须云端强模型；B 类是格式化、字段抽取、摘要改写，本地模型足够；C 类是路由判定本身，用规则 + 小分类模型，成本几乎为零。
2. **声明模型组**。在 OpenClaw 的 model profile 里定义 cloud 和 local 两组，路由规则按“任务类型 × 上下文长度”两个维度走：上下文超过本地窗口的直接路由云端，不做无谓尝试。
3. **单向降级链**。本地失败（schema 校验不过、超时）重试一次后升级云端；云端限流或超预算则降级本地，并在输出上打“需复核”标记。降级只允许单向，防止 A→B→A 的重试风暴。
4. **留痕**。每次路由写一条日志，带 `route_reason` 字段（规则命中、fallback 升级、预算触发等）。没有这份日志，后面所有调优都是拍脑袋。

## 踩坑点

- **本地模型 function calling 不稳**：JSON 结构时对时错。schema 校验 + 最多重试一次就升级，不要在本地死磕。
- **静默截断**：本地模型 8k 窗口，超长上下文被悄悄截断，agent 表现为“忘事”。排查先看 token 数，再怀疑提示词。
- **embedding 混用**：本地 embed + 云端 chat 没问题，但检索库一旦换 embed 提供商，必须全量重建索引，否则召回悄悄劣化。
- **GPU 冷启动**：模型加载后首个请求 20 秒以上，用定时 warmup 或常驻进程解决。

## 可复用建议

- 按“任务类型 × 上下文长度 × 敏感级别”三维路由，别只用关键词匹配。
- 本地模型上线前跑 50 条 golden set，工具调用通过率低于 95% 不进生产路由。
- 云端白名单制：涉及客户数据的任务默认本地，用云端需要显式开启。
- `route_reason` 日志攒两周再优化，用数据说话。

## 总结

多模型路由的价值不在省了多少钱，而在让每个任务的模型选择变得可解释、可回溯。从规则路由起步，先有分级和日志，等数据攒够了，再考虑学习型 router。工程上，简单规则 + 严格留痕，比一个黑盒智能路由可靠得多。
