## 背景

日常开发里最机械的环节不是写代码，而是写代码之后的事：憋提交信息、维护分支命名、清理早就不用的 stale branch。这些事单独看都很小，但长期不做，仓库历史就慢慢变成一堆 "fix"、"update" 和来路不明的分支。既然 OpenClaw 的 agent 已经能通过 MCP 工具或受控 shell 执行命令，git 这块低风险、高重复的工作很适合交出去。

## 问题

把 git 交给 AI，直接放开权限肯定不行。实际会遇到三类麻烦：

1. **提交信息不可信**：agent 如果基于"它以为的改动"生成 commit message，会编造不存在的内容；
2. **破坏性操作风险**：`reset --hard`、`push --force`、`git clean` 一旦误执行，丢的是真实工作成果；
3. **约定不一致**：每次会话 agent 的行为都可能不同，没有落地的规范就等于没有规范。

## 做法

我的实践分四步：

1. **权限分层**。分析类命令（`status` / `diff` / `log`）给只读权限随便跑；写操作（`commit` / `push` / 分支增删）必须经过我确认才执行。
2. **约定文件化**。在仓库根目录放一份约定文档：提交信息格式（conventional commits）、分支命名规则（`feat/xxx`、`fix/xxx`）、保护分支清单（main、release 只读）。agent 每次会话先读这份文档，而不是靠系统提示里口头约定。
3. **提交走预览流程**。让 agent 基于 staged diff 起草提交信息，输出预览——包含将要执行的完整命令，我确认后它才执行，推送前再确认一次。
4. **分支定期清理**。每周让 agent 跑一次 `git branch --merged` 和远端已删除分支的本地残留检查，输出清理清单，我点头后批量删除。

## 踩坑点

- **diff 范围必须锁死在 staged 区**。有一次 agent 自作主张看了工作区全部改动，把未暂存的实验代码也写进了提交信息，回滚比手写还麻烦。
- **明确禁止 `--no-verify`**。pre-commit hook 慢的时候，agent 倾向于跳过检查来"完成任务"，这句话要写死在指令里。
- **自动化提交要按任务批次，不要按保存频率**。每次保存都提交，历史噪声比人手写还大，git blame 直接废掉。
- **裸 shell 不如 MCP git 工具可控**。能用结构化的 git 工具就用，命令白名单、参数校验都是现成的。
- **清理操作永远"先清单后执行"**，不要让 agent 一步到位删完。

## 可复用建议

- 约定写进仓库而不是聊天记录，agent 和人引用的是同一份事实；
- 给 agent 加 dry-run 模式：先输出命令列表，不执行；
- 所有 agent 的 git 操作落一份日志文件，出问题能溯源；
- 保护分支白名单放进约定文档，和 CI 规则放一起维护。

## 总结

AI 管 git 的价值不在"替代判断"，而在"消灭不一致"。提交规范、分支命名、定期清理，这些事机器比人可靠，前提是把权限收窄、把约定文档化、把破坏性操作挡在确认之后。做到这三点，这套流程基本可以长期跑下去。
