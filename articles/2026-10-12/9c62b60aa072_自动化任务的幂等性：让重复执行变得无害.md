## 背景

在 OpenClaw 这类自动化场景里，任务很少只跑一次：cron 在服务重启后补跑、webhook 上游重投递、agent 失败后整轮重试、用户没看到动静再手动触发一遍。重试不是异常路径，而是常态。幂等性解决的就是这个问题：同一任务执行一次和执行 N 次，系统最终状态必须一致。做到这一点，重复执行就从隐患变成了无害机制。

## 问题

几个典型翻车现场：

- 定时日报任务给群发消息，进程重启后 cron 补跑，群里出现两条日报；
- webhook 驱动的 agent 遇到上游重发同一事件，重复创建了 issue；
- 长任务跑到一半超时，重新执行后，前半段已完成的副作用又来一遍。

先分清操作性质：追加写、发消息、自增计数、调用有副作用的外部 API，是**非幂等**的；覆盖写、删除已存在资源、带唯一约束的 upsert，是天然幂等的。设计第一步，是找出任务里属于前者的环节。

## 做法

1. **先定幂等键。** 键必须来自业务语义，而不是运行时随机量：

```python
idem_key = f"digest:{repo}:{utc_date}"   # 而非 f"run:{uuid4()}"
```

定时任务用「日期 + 数据源 + 动作」，webhook 用上游事件 ID。

2. **执行前原子占位。** SQLite 唯一索引、Redis `SETNX`、文件 `O_EXCL` 都行，抢不到键就直接退出或返回缓存结果。必须是原子操作，不能"先查一下再跑"。

3. **写操作尽量 upsert。** 日报写固定文件名覆盖，同步数据用 merge 而非 append。

4. **外部副作用加去重。** 发消息、建工单前按幂等键查执行记录，存在即跳过；对方 API 支持幂等令牌就直接传。自己写 MCP 工具时，给有副作用的 tool 显式留一个幂等键参数。

5. **长任务按步骤落 checkpoint。** 每步独立的键和状态记录，失败从断点续跑，而不是从头重来。

容易忽视的一点：幂等键要在代码里算，不要让模型生成——LLM 每次输出的"任务标识"很可能不一样，等于没有去重。

## 踩坑点

- **用时间戳或随机 UUID 当键**：重试天然被当成新任务，去重形同虚设；
- **check-then-act 竞态**：两个进程同时查到"没跑过"然后都执行，必须原子占位；
- **去重窗口太短**：人可能隔几小时才手动重触发，TTL 早已过期，执行记录建议永久保留；
- **半完成任务**：第 1 步成功、第 2 步失败，重跑会重复第 1 步的副作用；
- **时区歧义**：键里的"日期"固定用哪个时区要写死，跨午夜的任务容易跑两次。

## 可复用建议

- 默认假设：**任何自动化迟早会跑第二次**，设计时就按这个来；
- 触发和意图分离：cron/webhook 只是触发信号，幂等键才是任务的身份；
- 保底方案是一张流水表 `(key, status, result, updated_at)`，成本极低，还能顺带回答"这个任务到底跑没跑过"；
- 验收方式简单粗暴：staging 环境连跑两次，diff 最终状态，有差异就是没做干净。

## 总结

幂等不是给失败准备的补丁，而是自动化的默认属性。OpenClaw 场景里 agent 的不确定性已经够多了，任务层再把重复执行变成隐患，出了问题几乎无法排查。先定键、原子占位、覆盖写、留流水——四件事做完，重试就不再是事故，而是系统正常运转的一部分。
