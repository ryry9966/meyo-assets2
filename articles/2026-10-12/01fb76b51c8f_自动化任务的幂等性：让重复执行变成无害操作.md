## 背景

跑 OpenClaw 自动化一段时间后你会发现一个事实：任务很少“只执行一次”。cron 在机器重启后可能补跑；webhook 会按对方的重试策略重复投递；agent 调工具超时后，经常自己决定再调一次；更别提你手痒手动触发的那个“再跑一遍”。

“一次触发等于一次执行”这个假设，在自动化场景里基本不成立。

## 问题

于是问题变成：同一个任务跑两遍，会发生什么？

如果答案是“晨报发了两条”“同一批笔记被同步了两次，生成一堆重复文件”“自动建 issue 的插件建出两个一模一样的 issue”，那这些任务就是非幂等的。幂等的定义很朴素：**同一操作执行一次和执行多次，系统的最终状态一致。**

注意，目标不是消灭重试——你消灭不了——而是让重试变得无害。

## 做法

1. **先分类操作。** 天然幂等的：固定路径覆盖写文件、把状态更新为某个值、删除类操作。天然非幂等的：追加（append）、创建（create）、发消息。改造重点全在后者。
2. **给每个“逻辑任务”定一个稳定的幂等键。** 由代码确定性生成，例如 `daily-report:2024-06-01:group-a`，粒度对应“一次逻辑执行”。键不要让模型即兴生成——LLM 两次输出的键不一样，去重就形同虚设。
3. **建一个去重账本。** SQLite 一张表或一个 JSON 文件都行：执行前先向账本 INSERT 幂等键（建唯一索引），插入成功才执行，冲突直接跳过；执行确认成功后，再把状态落为 done。
4. **对外部系统先查后写。** 创建前先查目标系统“是否已存在”，同时用约定兜底：issue 标题带日期、文件名含日期，让重复创建在物理上撞车。
5. **第三方 API 带 Idempotency-Key。** 支持就一定带上；不支持就在本地账本里挡一层。
6. **让重试安全。** 中间状态记“进行中 + 租约时间”，租约过期后允许下一轮接管，而不是一崩就永久卡死。

## 踩坑点

- **先查后做的竞态。** 两次并发都查到“不存在”，然后都去创建。要靠账本先插入占位或数据库唯一约束这种原子操作，而不是纯 check-then-act。
- **幂等键粒度错了。** 键太粗，“每天一次”变成“永远一次”，合法的下一轮被吞掉；键里混入时间戳或随机数，则永远去不了重。
- **先记账后执行，执行崩了。** 账上留着“已完成”，任务从此再也不跑。状态只能在实际成功后落为成功。
- **日期边界。** 键里的日期在任务跨午夜运行到一半时变了，前后两半落在不同的键上。

## 可复用建议

- 写任何 cron / webhook 任务前先回答一句：**这个任务现在连跑两遍会发生什么？** 答不上来就别上线。
- 能覆盖就别追加，能对账就别创建。
- 把去重账本做成插件里的通用工具函数，所有定时任务共用一份，别每个脚本自己造。
- 上线前手动连跑两遍，当冒烟测试。

## 总结

幂等性不是什么高级技巧，而是自动化的准入门槛。超时、补跑、人工重复触发，都会给你制造“第二次执行”。把每次执行的副作用设计成可重放的，你的 OpenClaw 定时任务和 agent 自动化才敢真的放着不管。判断标准也很简单：重复执行的结果和执行一次完全一样，才算及格。
