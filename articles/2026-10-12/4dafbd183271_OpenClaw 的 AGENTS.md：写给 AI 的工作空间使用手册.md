# OpenClaw 的 AGENTS.md：写给 AI 的工作空间使用手册

## 背景

OpenClaw 的会话机制决定了：每次新对话，模型都是一张白纸。它不知道你的目录结构，不知道测试该用 pnpm 还是 npm，更不知道 `legacy/` 目录动不得。过去这些上下文靠两条路补：在聊天框里反复粘贴，或者写进全局系统提示。前者低效且每会话丢失，后者粒度太粗，无法表达项目级差异。

AGENTS.md 是更轻的答案：在工作空间根目录放一个 Markdown 文件，OpenClaw 在会话启动时自动读取并注入上下文。本质上是给 AI 写的「工作空间使用手册」——和 README 面向人类是同一个逻辑，只是读者换了。

## 问题

没有手册的实践，通常撞上三类麻烦：

1. **指令重复输入**。团队成员各存各的粘贴模板，新会话从零开始。
2. **行为漂移**。构建命令用错、生成文件散落在根目录、动不动跑全量测试耗掉几分钟。
3. **MCP 工具装了但不会被恰当使用**。工具接入后，Agent 不知道在本工作空间哪些场景该优先用哪个，要么自作主张，要么反复来问。

根因相同：关键约束只存在于人的脑子里和聊天记录里。

## 做法

一份实用的 AGENTS.md，骨架就五段：

- **结构概述**：目录用途几句话讲清，尤其是「禁碰区」（`generated/`、`vendor/`、迁移脚本）。
- **命令约定**：构建/测试/lint 的首选命令，长任务的预期耗时与超时默认值。
- **风格约束**：语言版本、格式化工具、提交信息规范。
- **工具规则**：哪类任务优先用哪个 MCP 工具。例如「文件检索优先走本地索引，失败再联网」「任何写库操作先询问」。
- **边界**：不读 `.env`、不无确认执行破坏性命令、不改 CI 配置。

写法上坚持两个原则：**分层**与**克制**。全局约束放根目录；某个子模块的特殊规则（比如某插件有独立构建方式）放它自己的 AGENTS.md，OpenClaw 会按工作目录逐级读取。全文控制在一屏以内——它是约束清单，不是文档堆砌，多一段废话，重要规则的权重就被稀释一分。

然后把它当代码维护：进版本库、改动走 PR review。顺便建立团队共识：**同一个问题被纠正两次，就必须写进 AGENTS.md**。

## 踩坑点

- **写太长**。超出一屏后关键规则沉底，Agent 表现得像读过百页手册但不知道哪页重要。
- **混入流水账**。「上周试过 X 方案不行」这类历史应该进文档，手册里只留当前有效的规则。
- **内容过期**。命令改了手册没更新，Agent 会忠实地执行错误命令——过期规则比没有规则更糟。
- **与插件配置冲突**。AGENTS.md 和权限白名单、MCP 工具描述打架时，Agent 行为不可预测；改任何一边前先通读另一边。
- **把它当安全边界**。它是引导，不是隔离。真正要拦的东西（破坏性操作、敏感文件）必须靠权限配置硬性兜底，手册只是第一层说明。

## 可复用建议

1. 新工作空间初始化时带上模板，哪怕只有五段骨架，也强于空白。
2. 每月花十分钟审一次：删过期条目、合并重复项。
3. MCP 工具的 description 与手册互相呼应：工具描述说「能做什么」，手册说「什么时候该用它」。
4. 规则说不清的地方放示例，一个正确路径比三段描述管用。

## 总结

AGENTS.md 的价值不在技术多深，而在于把原本散落在脑子和聊天记录里的约定，沉淀成可版本化、可 review、可被每个新会话自动遵守的文件。成本极低：一个 Markdown，几十分钟。回报是 Agent 行为的显著收敛。写短、写准、保持更新，就够了。
