## 背景

单 agent 干复杂任务迟早会撞上两个瓶颈：一是上下文，工具返回的原始数据很快把对话撑爆，agent 开始忘事、重复读文件；二是串行，所有步骤排队执行，耗时随任务规模线性增长。

subagent 模式的思路很简单：主 agent 只做拆解、派发和汇总；子 agent 各自开独立上下文，带着明确的任务说明和受限的工具集去干活，干完只回传压缩后的结果。在 OpenClaw 里，可以给不同 agent 配置各自的 workspace 和工具白名单，主 agent 通过任务分发机制把子任务派出去，MCP 工具按需挂给对应子 agent，主 agent 不必全量持有。

## 我遇到的问题

一个具体场景：给中型代码仓库做迁移前调研，外加通过 MCP 收集几个外部依赖的版本信息。主 agent 一路串行读文件、调搜索，两轮下来上下文塞满，后面开始漏模块、反复读同一段代码，一次任务跑得很久，结果还不完整。

## 做法

1. **划清可并行的边界。** 只把“读多写少、相互独立、结果可验证”的任务派出去。检索、调研、批量格式检查适合并行；写文件、改配置默认串行。
2. **给每个子 agent 写清契约。** 目标一句话、必要上下文（不要指望它继承父对话）、允许的工具白名单、输出格式（限定长度或 JSON 字段）、停止条件。
3. **控制并发。** 同时 3 个左右起步，跑顺了再加大，别一上来就开满。
4. **收口要窄。** 主 agent 只接收结构化摘要，原始日志落盘到工作区文件，需要时按路径回读，上下文预算留给决策。
5. **失败要有出口。** 每个子任务设超时；失败的重派一次，仍失败就降级为串行或标记人工介入，别让主 agent 干等。

## 踩坑点

- **子 agent 回传太啰嗦**，反而把主上下文撑爆。输出契约里必须限长，只许给结论加证据路径。
- **两个子 agent 同时改同一个文件**，后写覆盖先写。写操作收敛回主 agent，或坚持单写者原则。
- **子 agent 缺上下文开始脑补。** 父 agent 觉得显然的信息，子 agent 一无所知，任务说明里把路径、约束、验收标准写全。
- **并发不是越多越好。** 任务小到几步能完成时，编排开销超过收益，先串行测出基线再决定。
- **权限没收紧。** 子 agent 顺手做了不该做的事，最小权限是底线，不是可选项。

## 可复用建议

- 子 agent 提示词做成模板：目标 / 上下文 / 工具白名单 / 输出格式 / 停止条件，五段式，每次只改目标段。
- 结果统一 JSON：`status`、`findings`、`artifacts`、`issues` 四个字段，主 agent 的汇总逻辑不用每次重写。
- 全量日志写工作区文件，主 agent 只看摘要，这条原则贯穿始终。
- 记录每次的并行度、耗时和 token 消耗，拿数据决定是否继续并行，别凭感觉。

## 总结

subagent 编排解决的是上下文和串行两个瓶颈，但它把复杂度从“执行”转移到了“契约设计”。任务边界划得清、输出契约写得严，并行就是提效；划不清，并行只是把混乱加速。建议从只读调研类任务开始试点，跑通收口和失败处理，再碰写操作。
