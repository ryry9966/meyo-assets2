## 背景

跑自动化的人迟早会碰上这几件事：Agent 超时后重试了同一个工具调用；定时任务和手动触发撞车；消息队列把同一条事件投递了两次；流水线在第三步挂掉，重跑时前两步又被执行了一遍。这些场景的共同点是：代码没改，但结果坏了——工单建了两张，通知发了两遍，数据库里多出一堆重复行。

## 问题

根因是操作不幂等。幂等的定义很朴素：同一操作执行一次和执行 N 次，系统的最终状态一致。GET、PUT 覆盖写、DELETE 天然幂等；而"新建一条记录""发送一条通知""追加一段配置"这类增量式操作，重复执行就会累积副作用。

自动化系统几乎保证不了"只执行一次"——网络抖动、进程崩溃、人工重跑都会带来至少一次（at-least-once）的重复。可靠性工程里的基本共识是：与其追求 exactly-once 执行，不如让每次操作幂等，两者叠加的效果等价于 exactly-once。

## 做法

在 OpenClaw / MCP 的工具链里落地，我按三步走：

1. **给工具分类。** 把每个 MCP 工具标注为"天然幂等"或"有副作用"。凡是写操作、外发操作（发消息、建工单、调第三方 API）都归入后者。
2. **引入幂等键。** 对有副作用的工具，调用前生成一个 key，并在本地维护去重表：key、状态、返回结果。重复调用先查表——已成功就直接返回上次结果，不再真正执行。关键是 key 要从"意图"派生而不是"尝试次数"派生：用任务 ID + 步骤名 + 入参哈希生成确定性 key，重试多少次 key 都相同。
3. **让存储层兜底。** 去重表和实际执行之间存在竞态，所以数据库层面加唯一约束（unique index / `INSERT ... ON CONFLICT DO NOTHING`），把"重复插入"变成"被数据库拒绝"，不依赖应用层判断。

对于外部副作用（邮件、webhook），把去重放在发送边界：记录已发送的消息 ID，发送前查重。

## 踩坑点

- **每次重试生成新的随机 UUID 当 key。** 去重完全失效，key 必须在多次尝试间保持稳定。
- **先查后写的竞态。** 两个并发任务同时查到"不存在"，然后各自插入。应用层判断挡不住并发，唯一约束才行。
- **把失败结果也缓存进 key。** 重试会一直拿到失败的旧结果。只缓存成功结果，失败允许重试。
- **key 粒度不对。** 太粗会误杀合法的不同操作，太细又漏掉真正的重复。建议：操作类型 + 目标对象 + 关键参数哈希。
- **去重记录 TTL 太短。** 补偿重试往往几分钟后才来，TTL 要覆盖最大重试窗口。

## 可复用建议

- 工具设计尽量声明式：接受目标状态做覆盖写（upsert），而不是增量操作。
- 去重表做成通用组件：key / status / result / created_at 四列，所有任务复用。
- CI 里加一条断言：同一任务连跑两遍，第二遍应是 no-op（无新增副作用）。
- 在工具文档里明确标注"可安全重试"与否，Agent 的重试策略据此决定。

## 总结

自动化的可靠性不来自"保证只跑一次"——那做不到——而来自"跑多次也无害"。把幂等当作工具设计的一等公民：确定性幂等键 + 存储层唯一约束 + 发送边界去重，三道防线叠上去之后，重试、撞车、重跑就从事故变成了日志里普通的一条记录。
