# RSS + AI 摘要：搭一条自己可控的信息流管线

## 背景

RSS 没死，它反而是目前噪音最低、可控性最强的信息源。但订阅源一多，未读列表就成了压力源。我的目标是：机器先读，人只读摘要，整条管线跑在自己的 OpenClaw 实例上，不依赖任何第三方聚合服务。

## 问题

直接把 RSS 条目扔给 LLM 会遇到三个坑：

1. 相当一部分源只给摘要不给全文；
2. 条目高度重复，同一件事五家源同时在写；
3. 不加控制的话，token 成本和推送噪音都会失控。

## 做法

**1. 采集层**：cron 定时跑 `rss-parser` 拉源，存 SQLite，主键用 GUID + 内容 hash。只处理新条目，保证幂等。

**2. 清洗层**：对只有 summary 的源做全文抓取（readability 抽正文），失败则降级用 feed 自带摘要。然后两级去重：先 URL/hash 精确去重，再对标题做相似度聚类，跨源重复只保留最早一条，标注"另有 N 条同题"。

**3. 摘要层**：这是唯一交给 Agent 的环节。通过 MCP 工具把清洗后的条目按批（每批 ≤ 10 条）喂给 OpenClaw agent，要求输出固定 JSON schema：`title`、`one_liner`、`key_points`（≤3 条）、`tags`、`score`（0–10，按我的兴趣画像打分）。代码侧校验 schema，不合法重试一次，再失败标记人工处理。

**4. 推送层**：score 高于阈值的即时推送，其余攒到晚上九点合成一份日报，日报导语也由 agent 生成。通道随意，我用 webhook 到 IM。

## 踩坑点

- **全文抓取失败率高**：约两成站点有反爬或需要 JS 渲染。别硬刚，降级用原始摘要，命中率足够。
- **长列表摘要会静默丢条目**：一次喂 50 条，LLM 会悄悄吞掉几条。分批 + schema 校验 + 条数断言（输出条数 == 输入条数）缺一不可。
- **打分漂移**：同一篇文章隔天分差能到 3 分。把兴趣画像从一句"我对 X 感兴趣"改成明确的关键词 + 权重后，稳定多了。
- **重跑灾难**：cron 重叠触发过一次，日报推了两遍。所有状态落库，推送前检查"当天日报是否已发"，别把状态放内存。

## 可复用建议

- **分层解耦**：抓取、清洗、摘要、推送各自独立、各自幂等，中间状态落库。Agent 只做摘要，确定性逻辑全用代码，不要什么都塞进 prompt。
- **把 LLM 当不可靠函数对待**：schema 约束 + 校验 + 重试 + 降级，四件套。
- **成本靠缓存和分级**：内容 hash 没变就不重新摘要；初筛用小模型，日报导语才用大模型。实测月成本是个位数人民币的量级。
- **留反馈回路**：记录你实际点开的条目，每周回看 score 分布，手动调画像。这个回路比反复调 prompt 有用。

## 总结

这条管线没用到任何新奇技术，价值在于把"读"这个动作从人挪到机器，且每层的失败模式都有兜底。RSS 提供稳定输入，代码提供可靠性，LLM 提供压缩能力，三者各干各的。建议从 5–10 个源起步，跑稳了再加量。
