# 背景

OpenClaw 的 `memory_recall` 是 agent 回忆长期记忆的入口：会话中模型调用它去检索 memory 目录里的历史笔记、结论、配置片段，检索质量直接决定助手"记不记得住事"。可选路径主要是两条：语义搜索（embedding 向量相似度）和全文搜索（FTS/BM25 关键词匹配）。社区里常争论哪个更好，我用自己的 memory 库（约 400 条笔记，中文为主）做了一轮实测。

# 问题

两种检索的失效模式完全不同：

- **全文搜索**：查询词和记忆里的字面必须对得上。问"那次部署失败的根因"，如果笔记里写的是"上线回滚"，就搜不到。
- **语义搜索**：擅长同义改写，但对精确标识符很不可靠——错误码、配置键名、命令、IP，向量化后常被泛化掉，反而召回一堆"语义相近但没用"的段落。

所以真正的问题不是"哪个好"，而是各自的失败场景怎么分布。

# 做法

1. 构造一个 30 条查询的评测集，三类各 10 条：精确匹配类（错误码、键名）、同义改写类、时间相关类，每条人工标注应命中的笔记。
2. 分别跑三种模式：纯全文、纯语义、混合（OpenClaw 的 hybrid 默认用 RRF 融合两路排名）。
3. 统计 recall@5。

结果：改写类语义明显占优（8/10 vs 3/10）；精确类全文几乎全中（9/10 vs 5/10）；混合两类都稳定在 8–9/10。结论清晰——混合不是和稀泥，是补位。

配置上值得改的三处：

- **保持 hybrid 开启，融合用 RRF**。别把两路原始分数相加，量纲不同，加权很容易被某一路淹没。
- **全文侧中文分词**：默认 tokenizer 对中文基本按整句切，换成 trigram（ngram）后精确召回提升明显；上 jieba 更好，但多一个运行时依赖，按需取舍。
- **语义侧换 embedding 模型**：小模型对技术术语泛化严重，换一个中文效果更好的模型，收益比调参数大得多。

# 踩坑点

- **分数融合**：最初自己加权求和，语义分数普遍偏高，全文形同虚设；换成 RRF（按排名倒数融合）才恢复正常。
- **分块太大**：按整篇日记切，召回回来的段落一半不相关还占上下文 token；按标题/日期切小块明显更准。
- **记忆过期**：召回常带回半年前的旧结论且排名靠前。给索引加时间元数据、对近期记录加权，或在 memory 文件里显式写"此条已作废，见 xxx"，比检索端补救有效。
- **索引重建**：换 embedding 模型必须全量重建向量索引。忘掉这步，会出现新旧向量混在同一空间的诡异召回结果。

# 可复用建议

- 默认 hybrid + RRF：全文当保底，语义当增强，不要二选一。
- 把那 30 条评测查询放进仓库，改配置、换模型后跑一遍，两分钟的事，避免凭感觉调参。
- 中文场景下，trigram 是全文检索性价比最高的起点。
- 让 agent 定期整理记忆、给过期条目打标记，比在检索端打补丁更治本。
- 排查召回问题时，先看原始命中文本再谈调参——很多"检索不准"其实是记忆本身写得不清楚。

# 总结

语义和全文不是竞争关系，而是失效模式互补的两条腿。实测中混合模式在三类查询上都接近单路最优，代价只是一次融合和索引维护。对 OpenClaw 用户来说，比"选哪个"更重要的一件事：留一份自己的评测集，让每次调整都有数字支撑。
