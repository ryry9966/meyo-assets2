## 背景

Agent 接上 MCP 之后，动作从"生成文本"变成了"产生副作用"：改文件、调接口、发消息、跑命令。这时问题不再是模型能力强不强，而是策略层缺位——大多数出事的场景，不是模型做错了什么，而是没人定义过"什么允许它做"。

## 问题：两个方向的失败

权限边界的失败只有两种形态：

- **问太多**：每步都确认，人很快进入橡皮图章模式，弹窗等于没有弹窗；
- **放太开**：Agent 在凌晨自主跑了一条不可逆的清理命令，你第二天才从日志里看见。

两者根源相同：没有把动作按风险分档，而是用一个全局开关（确认一切 / 允许一切）偷懒。

## 做法：四个步骤

**1. 给每个工具打标。** 按 MCP tool annotations 的思路分类：只读、可逆写、不可逆写、外部副作用。注意 `readOnlyHint`、`destructiveHint` 这类只是声明，不完全信任 server，自己在配置里维护一份更可靠。

**2. 分四档策略：**

| 档位 | 范围 | 动作 |
|---|---|---|
| L0 | 只读、查询、dry-run | 自动执行 |
| L1 | 可逆写（先备份的配置修改、建 PR 不 merge） | 自动执行 + 全量留痕 |
| L2 | 不可逆 / 外发（发消息、删数据、部署、花钱） | 必须确认 |
| L3 | 明确 deny list | 直接拒绝 |

**3. 策略放代码，不放 system prompt。** 在 OpenClaw 这类有工具调用链路的框架里，加一层 hook 或网关做检查。模型可以建议，放行与否由确定性逻辑决定。靠模型自我评估"这个操作危不危险"，等于没有边界。

**4. 配额与歧义做调节阀。** 同类 L1 操作超过每日配额自动升 L2；输入有歧义（多个候选目标、参数对不上）时降级到确认，而不是让模型猜。

## 踩坑点

1. **确认疲劳是最大的坑。** 弹窗同意率长期接近 100%，说明边界划错了——把真正低风险的操作降档，让弹窗重新"值得看"。
2. **拒绝打包确认。** "我要做 A、B、C，可以吗"会把危险项藏进无害项。要求逐项列出，附将要执行的原始命令或 diff。
3. **理论可逆 ≠ 实际可逆。** 发出去的消息撤回了，对方也已经看过。外发类一律按不可逆处理。
4. **只读 ≠ 无害。** 读本身没问题，但读到的内容被组装进外发消息时，就成了泄露通道。规则要落在"外发"这个动作上，永远 L2。
5. **确认卡片必须可答。** 展示将要执行的原文，而不是 Agent 的转述——人没法为一句概括负责。

## 可复用建议

- 从最严配置起步，用日志数据逐步放宽；反过来做会付出真实代价。
- 每条自动放行都记录：工具、参数、命中的规则，定期抽查。
- 给 L1 设每日配额，配额是比"信任"便宜得多的安全机制。
- 策略变更走 review，和代码变更同等对待。

## 总结

"什么时候问人"不是玄学，是三个问题：**这个动作可逆吗？影响面多大？出错后的挽回成本比问一次高多少？** 用这三问给工具分档，把档位写进配置而不是提示词，再靠日志持续校准——Agent 的自主性就有了工程意义上的边界。
