## 背景

让 Agent 拿到 shell 和文件工具之后，它会不会一时"抽风"执行 `rm -rf` 把目录删掉？这是我们群里被问得最多的问题。担心是合理的：LLM 会幻觉出错误路径、误解指令、在长上下文里丢失边界。在 prompt 里写一句"请小心操作"解决不了问题——安全不能建立在概率上。

## 问题

OpenClaw 的设计前提很直接：**假设模型迟早会发出一次破坏性操作，系统的任务是让这次操作打不出去，而不是指望它不发生。** 只靠 prompt 约束、事后审计或人工盯屏，分别会在幻觉、止损和响应频率上漏掉。

## 做法：四层防御

**1. Workspace 根目录绑定。** 会话启动时绑定一个 workspace root，所有文件工具在执行前先做 realpath 解析，解析后逃出 root 的路径（包括 `../` 和符号链接）在工具层直接拒绝。模型收到的是明确报错，可以自行纠错重试，而不是静默失败。

**2. 进程级隔离。** Shell 工具不是裸 exec，而是放进容器/命名空间里跑：workspace 目录读写挂载，其余文件系统只读或干脆不可见，临时目录用 tmpfs，容器内以非 root 用户运行并裁剪 capabilities。模型就算拼出 `/etc/...` 这种绝对路径，进程视图里也没有写权限。

**3. 危险命令闸门。** Shell 工具前有一层模式匹配：`rm -rf`、`dd`、`mkfs`、管道进 `sh` 等模式命中后默认拒绝，或升级为人工确认；删除操作默认 move 进回收站目录并保留宽限期，而非直接 unlink。

**4. 快照与审计。** 批量写/删之前自动对 workspace 做一次 git commit，所有工具调用连同完整参数写入审计日志，可 diff、可回滚。

## 最小配置步骤

声明 workspace root → 开启 sandbox 模式 → 配置 deny 列表与人工确认阈值 → 开启快照 → 做一次验收测试：放一个金丝雀文件，故意诱导 Agent 执行越界删除，确认三层拦截都生效、快照和日志都落盘。

## 踩坑点

- **符号链接与 TOCTOU**：先 resolve 再判断仍不够，检查与执行之间路径可能被替换。OpenClaw 用 openat + nofollow 语义打开文件，自己写 MCP 文件插件时最容易漏这条。
- **只沙箱文件工具、不沙箱 shell**：模型用 `echo x > /etc/hosts` 就能绕过文件工具的路径检查。边界要落在进程上，不是落在工具 API 上。
- **容器内跑 root**：只读挂载形同虚设，务必用非 root 用户并裁剪能力。
- **快照时机错误**：删了一半才快照等于没快照，必须发生在第一批写操作之前。
- **确认状态被复用**：人工批准过一次 rm，不代表同类命令全部放行，确认必须绑定到具体命令和具体路径。

## 可复用建议

默认拒绝、白名单放行，不要反过来；不可逆操作一律人工确认或走可回滚路径；把"模型会犯错"当作设计常量，安全机制必须在模型之外生效；上线前用对抗性 prompt 做一轮红队测试并留档拦截日志；写自定义插件时不要自己重写路径校验，统一走框架提供的守卫函数。

## 总结

OpenClaw 敢让 Agent 动文件系统，不是因为模型更聪明，而是最坏情况被锁在一个可恢复的范围里：路径出不了 workspace，进程出不了容器，删除进得了回收站，操作留得下审计。**安全是系统属性，不是 prompt 属性。** 建议大家按上面的最小配置跑一遍验收测试，欢迎回帖贴出你的拦截日志。
