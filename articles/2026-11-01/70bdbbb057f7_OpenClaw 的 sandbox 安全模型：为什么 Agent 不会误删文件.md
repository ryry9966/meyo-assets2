## 背景

Agent 拿到 shell 和文件读写工具之后，大家最关心的问题往往不是"它能干什么"，而是"它会不会哪天把我的目录删了"。OpenClaw 在这件事上的思路很直接：不指望模型永远不犯错，而是默认它一定会犯错，然后用 sandbox 把错误的爆炸半径锁死在工作区内。

## 问题：误删不是概率问题，是架构问题

单纯靠提示词约束行为，工程上是站不住的：

- **输出非确定**：同一条指令在不同上下文里可能生成不同的命令，"清理一下临时文件"可能被展开成很宽的 glob；
- **路径歧义**：相对路径、`~` 展开、软链接，都可能导致"以为在工作区里操作，实际落在外面"；
- **提示注入**：MCP 工具返回的内容、网页摘要里可能藏着诱导执行危险命令的文本；
- **人的锅**：把工作区挂载成整个 home、或者图省事直接放行 exec，等于裸奔。

所以 OpenClaw 的安全模型不依赖"模型听话"，而是靠运行时边界。

## 做法：四层防线

1. **工作区根目录校验**。文件类工具（read/write/edit）默认以 workspace 为根，路径先规范化、软链接先 resolve，再做前缀校验，越界直接拒绝，而不是事后补救。
2. **容器化 exec**。开启 sandbox 后，shell 命令跑在容器里：默认只挂载工作区目录、非 root 用户执行、网络可关。就算容器里真执行了 `rm -rf`，能伤到的也只有挂进去的那一个目录。
3. **工具策略**。按 agent 配置工具白名单，高危操作可以要求人工确认或直接禁用，能力本身就该按需授予。
4. **审计与可回滚**。命令和文件写入有日志；建议工作区本身就是 git 仓库，任何误操作都能 revert。

配置思路（示意，键名以所用版本文档为准）：

```text
sandbox.enabled = true
sandbox.backend = docker
sandbox.mounts  = [workspace]     # 只挂工作区
sandbox.network = off             # 需要装依赖时临时开
tools.policy.exec = confirm       # 高危动作加确认门槛
```

## 踩坑点

- **挂载范围贪大**：把整个 home 挂进容器是最常见的翻车点，sandbox 直接形同虚设；
- **Docker socket 挂载**：容器里能碰 docker.sock 约等于宿主机 root，绝对不要为方便放进去；
- **软链接逃逸**：工作区里提前放了指向外部的软链接，不同版本对 resolve 后路径的判定可能有差异，升级后建议回归测试；
- **文件属主错乱**：容器内非 root 写出的文件在宿主机上属主可能是映射 UID，删不掉改不了，注意 user 映射；
- **图省事关 sandbox**：注入风险是按概率累积的，快是快一点，出一次就够本了；
- **平台差异**：非 Linux 后端在权限映射、路径大小写上行为不同，验收别只在一台机器上做。

## 可复用建议

1. **验证而非相信**：接入新 agent 时，故意让它"删除工作区外的一个文件"，确认被拒。这条应该进接入 checklist；
2. **git init 是最便宜的保险**：所有 agent 工作区默认初始化仓库；
3. **最小挂载原则**：需要什么挂什么，宁可后面再加；
4. **高危工具默认禁用**：exec 可用时也要评估是否真需要网络；
5. **日志落到固定位置**：出事后能回放，比任何事后分析都值钱。

## 总结

OpenClaw 对"误删文件"的态度很工程化：模型不可信是前提，sandbox 提供的是确定性边界——路径校验挡住越界写，容器挡住越界命令，工具策略挡住不该有的能力，git 和审计日志负责兜底恢复。安全从来不是提示词里写一句"请小心"，而是让错误发生时，根本够不到重要的东西。
