## 背景

OpenClaw 的 agent 并不是每次都从零开始。它在 workspace（默认 `~/.openclaw/workspace`）里维护一组常驻文件，其中 `AGENTS.md` 会在每次会话被注入上下文——相当于新人入职第一天拿到的那本《工作手册》。如果说 README.md 是写给人看的，那 AGENTS.md 就是写给 AI 看的。

这个约定也不只属于 OpenClaw：越来越多的 agent 工具会读取仓库里的 AGENTS.md，子目录的可以覆盖根目录的。对经常让 agent 混合操作 workspace 和外部仓库的人来说，这一点很实用。

## 没有它会怎样

踩过这些坑的人应该很熟悉：

- 每次都重复交代：脚本入口在哪、用什么包管理器、commit message 什么格式；
- agent 行为漂移：今天生成的代码一个风格，明天又变了；
- 多 agent、多工具协作时各说各话，没有统一的“房间公约”；
- 明明说过“不要动那个目录”，三天后它又动了。

根源在于：这些约定只存在于聊天历史里，而聊天历史是易失的、会被截断的。

## 怎么写：三条原则加一个流程

**原则一：写操作约定，不写需求。** “不要动那个目录”是临时要求；“所有脚本入口在 scripts/，测试用 `pnpm test` 跑”才是操作约定。手册解决“怎么做”，不解决“做什么”。

**原则二：命令优先于描述。** 与其写“请格式化代码”，不如直接写明具体命令。agent 执行明确命令的可靠性，远高于理解模糊意图。

**原则三：短。** 建议控制在 60–100 行内。上下文是稀缺资源，规则越多，单条权重越低。

落地流程：

1. 先建最小版本：项目结构、常用命令、一两条安全红线；
2. agent 犯了可预防的错，别只在群里抱怨，沉淀成一条规则；
3. 发现规则过时或互相冲突，当场删改，保持手册与现实同步；
4. 放进版本控制，改动可回溯。

分层放：个人习惯和全局偏好放 workspace 根目录，项目特有的放项目子目录——越靠近代码越具体。

## 踩坑点

- **写成大杂烩**：把任务清单、临时笔记全塞进去。任务归 TODO，手册只放稳定约定；
- **敏感信息入库**：API key、内网地址直接写进手册。手册会被读取、可能被上传，密钥一律走环境变量；
- **规则互相打架**：一份说用 pnpm、一份说用 npm，agent 只能靠猜。发现冲突先合并再谈其他；
- **写完就忘**：约定随代码演进，建议每两周通读一遍，过期即删。

## 可复用建议

给个骨架，可以直接抄：

- 项目结构与入口（3–5 行）
- 常用命令：构建 / 测试 / 部署
- 代码风格与提交规范
- 安全红线：哪些目录只读、哪些操作必须先确认
- 输出偏好：报告格式、语言习惯

再配一个土办法：另建一个“候补区”文件，平时想到规则先丢进去，每周 review 一次，确认稳定再移入 AGENTS.md，避免手册被冲动式规则污染。

## 总结

AGENTS.md 的价值不在于“多配置了一个文件”，而在于把你和 agent 之间的协作，从“每次口头约定”升级为“持久化的工程契约”。它是 workspace 里性价比最高的一份文档：写一次，每次会话生效。规则少而准，永远比多而全有用。
