# 背景

OpenClaw 的 agent 会话本质上是无状态的：每次启动，它对工作空间的认知清零，一切信息都来自上下文。人类协作者靠 README、口头约定和 review 习惯对齐，而 agent 需要一个固定、机器可读的入口。AGENTS.md 承担的就是这个角色，放在工作空间根目录，agent 进入时会自动读取，相当于你给 AI 交接时递过去的那份“上岗手册”。

# 问题

没有这份手册时，症状很固定：每次会话都要重复交代构建命令；agent 在 npm 项目里顺手装了 pnpm；提交信息风格随机；中间产物散落在仓库根目录；调用某个 MCP 工具前漏了前置步骤，报错后才回溯。常见对策是把说明贴进 system prompt 或会话开头，但这样 token 开销大、版本不统一，换个会话就失效。

# 做法

1. **先写最短可用版。** 根目录建 AGENTS.md，包含四块：项目结构一段话、构建/测试/部署的完整命令、硬性风格约束、“不要做”清单。别追求完备，先能跑。
2. **分层放置。** 全局约定放根目录，局部规范放子目录，例如 `plugins/` 下写插件目录结构和命名规则，agent 就近读取、逐层合并。
3. **用祈使句和短条目。** 命令给可直接复制执行的完整形式，并注明预期工作目录；规则一条说一件事，避免散文式描述。
4. **写清与自动化的边界。** 哪些定时任务允许 agent 触发、调用 MCP 工具的前置条件、生成文件允许落在哪些目录——这些是自动化场景里最容易出事故的地方。
5. **像代码一样维护。** 提交进仓库、走 review，构建流程变更时同步更新。

# 踩坑点

- **写太长。** 几千字的手册很快失修，agent 上下文也吃紧。主文件控制在一两屏，细节下沉到子目录。
- **和 README 混同。** AGENTS.md 是操作指令不是项目介绍，“本项目采用微服务架构”这类话对 agent 没有行动价值。
- **只有正面规则。** 负面清单往往更有效：禁止改 lockfile、禁止跳过 lint 提交、禁止执行删除类命令。
- **命令省略了执行目录。** agent 在错误路径下跑测试，得出的结论全是错的。
- **手册里出现密钥或内网地址**，随仓库一起泄露。

# 可复用建议

- 固定一个骨架：项目地图 / 常用命令 / 风格约束 / 禁止事项 / 已知坑。
- 判断标准很简单：同一件事向 agent 口头解释超过两次，就该写进 AGENTS.md。
- 每次排障后把根因回写成一条约束，形成“事故 → 规则”的闭环，手册会越来越贴合实际。
- 改动手册后用一个固定任务（让 agent 完成一次典型的小改动）验证行为是否符合预期，而不是凭感觉判断“变好了”。

# 总结

AGENTS.md 不是又一份文档，而是工作空间与 agent 之间的接口契约。它的维护成本远低于在每个会话里重复解释的成本，且随项目一起演进。从最短版本开始，让它在踩坑中长出来，是投入产出比最高的做法。
