## 背景

跑 Agent 做自动化的人大多遇到过这类场景：同一套 skill / MCP 配置，笔记本上正常，换到 Linux 服务器后 Agent 找不到工具；同事的提示词拷过来，路径、包管理器全对不上。Agent 默认只能看到你给它的上下文，它并不知道你机器上 `ffmpeg` 装在哪、用的是 `brew` 还是 `apt`、MCP 服务起在哪个端口。

我的做法是把这份"环境事实"固化成一个 `tools.md`，让 Agent 开工前先读它。本质上是给 Agent 一份环境契约，而不是靠它猜。

## 问题

不做这件事，通常有三种代价：

1. **幻觉式调用**：Agent 假设 `python` 存在，实际只有 `python3`；假设配置在 `~/.config`，实际在 `~/Library`。
2. **差异散落在对话里**：每次换机器都要重新解释一遍，或者把个人路径写进团队共享的 prompt，互相污染。
3. **上下文膨胀**：有人把工具手册全文塞进系统提示词，token 花了一堆，Agent 还抓不住重点。

## 做法

分两层管理：

- **全局层**：`~/.openclaw/tools.md`，记录本机通用事实——OS、shell、包管理器、常用 CLI 绝对路径、已运行的 MCP server 及端口。
- **项目层**：仓库根目录 `tools.md`，记录该项目特有的工具、启动命令、版本约束、外部服务依赖。

结构建议控制在 60–100 行，核心四段：

1. **环境概览**：OS / shell / 关键版本号，一张表格搞定。
2. **工具清单**：名称、调用方式、路径、备注。写"可直接执行的调用"，不写散文。
3. **差异段**：明确列出"本机可能不同的项"，如路径前缀、端口、代理设置。
4. **常见报错**：三五个高频问题及一句话解法。

两个配套原则：

- **差离值本地化**。项目层只写占位符和默认值，每个人的真实路径写进 gitignore 掉的 `tools.local.md`。Agent 按 项目 → 本地 的顺序读取，本地覆盖项目。
- **密钥永不落盘到 md**。只写"密钥在 .env 的 `FOO_KEY`"，不写值。

再加一个十行的 `doctor.sh`，逐项检查工具是否存在、版本是否匹配，Agent 开工前跑一次，把结果当作事实来源，比让它自己 `which` 一圈省事。

## 踩坑点

- 把 A 机器的绝对路径提交进共享文件，B 机器拉下来直接失效。绝对路径只进 `tools.local.md`。
- 文件越写越长，Agent 反而开始忽略后段内容。超过 100 行就该砍，手册归 `docs/`。
- 工具迁移后忘了更新，Agent 按旧信息调用，报错还执着重试。把 `tools.md` 的改动纳入 PR review。
- Windows 与 Unix 的路径分隔符、shell 语法差异，写清楚，而不是指望 Agent 自适应。
- 全局层和项目层对同一工具给出冲突描述。定好优先级，并在文件头写明覆盖规则。

## 可复用建议

- 把 `tools.md` 当代码对待：有模板、有 review、有变更记录。
- 仓库里放 `tools.example.md`，新人克隆后复制改名，十分钟完成环境对齐。
- 表格优先于段落，Agent 对结构化信息的命中率明显高于叙述。
- 定期让 Agent 自检：读 `tools.md`，跑 doctor，输出差异报告，人只处理报告。

## 总结

`tools.md` 解决的不是技术难题，而是把"Agent 到底运行在什么环境"从隐式对话变成显式契约。分层、精简、密钥外置、可校验——四条守住，环境差异就从反复踩坑，变成换台机器也能十分钟跑通的日常。
