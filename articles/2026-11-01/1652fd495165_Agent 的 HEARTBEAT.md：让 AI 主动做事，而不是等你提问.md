## 背景：一问一答不是 Agent 的全部

目前大部分 Agent 的工作模式仍是"你问它答"：不发消息，它就永远安静。但有一类任务，用户不想发起、却希望被惦记——昨天的日报生成了没有、仓库里是不是堆了三天的未推送提交、磁盘快满了没有。这类事 cron 也能做，但 cron 只会执行固定命令，做不了"失败才通知""异常先收集上下文再判断"这类带条件的逻辑。

OpenClaw 的 heartbeat 机制就是为这个准备的：Agent 每隔一段时间被自动唤醒一次，读取工作区里的 `HEARTBEAT.md`。文件为空就静默跳过；文件里有清单，就按清单主动执行，该调工具调工具，该跑脚本跑脚本。本质上，它是把 Agent 的"主动权"收编进一份你手动维护、可版本管理的 Markdown 文件里。

## 做法：从小起步，四步

**1. 建文件，只写一两条低风险任务。** 放在 workspace 根目录，就是普通 Markdown 清单：

```markdown
# Heartbeat checklist

- 检查 ~/reports 是否缺昨天的日报，缺了就补跑生成脚本，结果写日志
- git 仓库存在超过 3 天未推送的本地提交时，在会话里提醒我
- 禁止：主动给任何联系人发消息、修改任何文件
```

**2. 拉长间隔。** 默认心跳比较频繁（约半小时一轮），先用长间隔（60–120 分钟）观察 token 消耗和输出质量，别一上来就高频。

**3. 设预算。** 给心跳回复设置 token 上限（如 `HEARTBEAT_TOKEN_BUDGET`），防止某次任务膨胀成一篇长文。也可以让心跳走便宜模型，主对话保留强模型。

**4. 每周迭代。** 删掉两周内没产生过价值的条目，把新踩到的需求写进去。它是活文档，不是一次性配置。

## 踩坑点

- **清单写太模糊。**"帮我看看有什么新鲜事"这类条目，每次心跳都会产生随机输出，纯烧 token。每条都要写成可判定的条件。
- **低估成本。**心跳开销 = 次数 × 每次完整上下文，一个月下来不小。间隔、预算、精简 workspace 是三个杠杆；文件为空虽会静默跳过，但唤醒本身仍有开销。
- **主动外发是高危动作。**绝对不要写"觉得有用的信息就发给我"，模型对"有用"的判断和你不一样，很快会变成噪音制造机。输出一律先落文件，通知只在满足严格条件时触发。
- **别替代 cron。**备份、清理这类确定性任务仍交给系统定时器，heartbeat 只放需要"判断"的事，两者混用会把简单问题的排查复杂化。
- **先验证再信任。**跑头两周，每次心跳后核对它实际做了什么，和清单逐条对照。

## 可复用建议

每条任务用"**条件 → 动作 → 输出去向**"三段式来写，缺一段就补齐再上线。显式写禁止事项，负向约束往往比正向指令更稳定。心跳执行记录单独落盘，事后能审计"它到底干了什么"——这对长期使用建立信任很关键。

## 总结

HEARTBEAT.md 的价值不在技术复杂度，而在于它把 Agent 的主动性从模型的自由发挥，变成一份人工可审、可回滚的配置。起步阶段越克制越好：清单短、间隔长、输出静默，跑稳两周再逐步加任务。主动做事的 Agent 好用，但可控才是前提。
