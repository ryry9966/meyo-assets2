## 背景

Agent 接上 MCP 和一批插件之后，能力上限很快不是瓶颈，问题变成了：它到底能不能自己动手。在 OpenClaw 这类框架里，一个会话可能同时拥有读文件、执行命令、调 MCP 工具、对外发消息的权限。能力越大，"每次都问"和"从来不问"两种极端就越不可接受。

## 问题

实践中反复见到两类失败：

- **全程请示**：agent 每读一个文件都弹确认，人被训练成"无脑回车"，审批机制名存实亡。
- **全程放权**：agent 自作主张删了目录、往群里发了未核实的消息，或者把一个失败的高危操作默默重试了三次。

核心矛盾是：安全和效率没法靠人肉实时平衡，得靠一套显式的分级规则。

## 做法：按风险分四级

判断只看三件事：**能不能回滚、影响面有多大、人能不能在 30 秒内判断对错**。

| 级别 | 典型操作 | 策略 |
|---|---|---|
| L0 只读 | 搜索、读文件、查状态 | 自动执行，记审计日志 |
| L1 可逆写 | 建分支、写临时文件、出草稿 | 自动执行，保留回滚路径 |
| L2 外部可见 | push、发消息、调付费 API | 必须确认，审批带上下文 |
| L3 不可逆高危 | 删数据、动生产、支付 | 默认拒绝，双人确认 |

落地三步：

1. **工具层收口**。MCP server 和插件不要整体放行，按工具名做 allowlist；exec 类工具限制工作目录和命令前缀，能进沙箱就进沙箱。
2. **会话层声明**。把分级规则写进 agent 的系统提示或配置，明确"L2 以上必须停下询问"，而不是指望模型自觉。
3. **动作时判定**。权限检查发生在每次工具调用前，不是任务开始时发一张通行证。

## 踩坑点

- **询问疲劳**。什么都问等于什么都不问。宁可把 L0/L1 划宽一点让 agent 顺畅干活，也别让审批框淹没真正需要人的那几次。
- **风险升级不触发重审**。任务开头是安全的，中间步骤把风险抬高了。典型场景：先只读分析，然后顺手"清理"了文件。所以权限必须在动作发生时判定，而不是任务开始时。
- **审批请求缺上下文**。只弹一句"是否执行 xx 脚本"，人没法判断，只能瞎点。审批应附带 diff、影响面说明和回滚命令，让人 10 秒内做得了决定。
- **dry-run 掩盖副作用**。预演通过不代表实跑安全，尤其涉及外部状态的操作。
- **工具权限被继承**。新挂一个 MCP server，里面所有工具默认可用，等于变相提权。新工具上线应先进沙箱或默认 deny。

## 可复用建议

- 默认 deny，用 allowlist 放行，宁紧勿松；
- 每个写操作都定义回滚命令，没有回滚路径的写操作自动升到 L3；
- 高危操作加冷却期或二次输入确认，防"手滑批准"；
- 全量审计日志：谁、何时、批准或执行了什么，事后能复盘；
- 分级规则进配置、进 code review，和功能代码同等对待。

## 总结

权限边界不是"信不信任模型"的态度问题，是工程问题。分级标准够客观（可逆性、影响面、可判断性），规则写进配置而不是写在心里，审批带足上下文，日志全量留存。做到这四点，agent 该自己干的时候不会烦你，该问的时候你也敢放心点确认。
