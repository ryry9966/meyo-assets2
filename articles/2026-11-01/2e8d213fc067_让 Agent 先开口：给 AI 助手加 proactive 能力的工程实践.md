## 背景

目前多数 Agent 交互是拉式的：你发消息，它回话。这种"问答机"模式在自动化场景里明显不够用——CI 挂了、日历冲突、依赖仓库发了新版本，这些事你希望它主动告诉你，而不是你挨个去查。

在 OpenClaw 这类框架里做 proactive，本质上是给 Agent 加一套"触发—感知—门控"的外围系统。模型只负责最后的判断和表达，触发和节流全是工程活。

## 问题：主动不等于多说话

最常见的错误实现是：挂一个每分钟跑的 cron，把完整系统提示词和全部记忆塞进去跑一轮，结果原样推到聊天通道。跑几天你会遇到三件事：通知噪音大到被静音、token 账单难看、偶尔因为监听器抓到了自己的消息而进入循环。

proactive 的难点不在"让它动起来"，而在"让它知道什么时候闭嘴"。

## 做法：触发、门控、动作三层

以我落地的场景为例：监控几个仓库的 CI 状态和 issue 动向，异常时推送，平时攒成每日摘要。

**1. 触发层。** cron 心跳（15 分钟一次）负责轮询类信号，webhook 负责事件类信号。触发层只做采集，产出结构化信号（来源、时间、内容、去重键），不带任何对话上下文。

**2. 门控层。** 这是全系统代码量最大、也最值钱的部分，按顺序过五道筛子：

- 去重：以 `repo + event_type + 对象 ID` 做键，加 TTL 缓存，拦住 webhook 重复投递；
- 自触发过滤：Agent 自身产生的消息打来源标记，监听器直接丢弃；
- 静默时段：本地时区 22:00–8:00 只进缓存不推送；
- 配额：每类信号每日推送上限，超出降级进 digest；
- 重要度：规则先行（失败→高分，普通评论→低分），规则判不了的才调一次小模型打分，避免每条信号都烧 token。

**3. 动作层。** 高分信号立即推送；中分进当日 digest 定时合并；写类动作（重启任务、提 issue）默认带确认，无人值守时直接拒绝并记录。每次触发落一行日志：信号、判定结果、原因。

## 踩坑点

- **自触发循环**：Agent 推到群里的消息又被自己的 webhook 监听器抓回来，几分钟刷屏。来源标记必须从第一天就有，事后补很痛苦。
- **去重键太粗**：一开始用 `repo + event_type` 做键，同一个 issue 的两条不同评论被吞掉一条。键要细到对象实例。
- **噪音疲劳**：上线第一周推了 40 多条，我开始无脑划掉。阈值宁可从紧起步，靠日志回放慢慢放松。
- **时区**：服务器是 UTC，静默时段不换算，摘要会在凌晨四点准时到达。
- **权限外溢**：proactive 任务无人值守，却默认继承了交互会话的全部工具权限。高危工具要么收窄，要么强制确认。

## 可复用建议

1. 从一个低风险、高价值的只读场景起步（摘要、监控、提醒），跑稳两周再扩。
2. proactive 做成独立 skill，触发器、阈值、静默时段全部外置配置，别写死在主循环里。
3. 门控判定必须可解释、可回放，否则你永远在盲调阈值。
4. 默认动作是 suppress 而不是 push——拿不准就不打扰，攒进 digest。

## 总结

proactive 的工程量大头在门控层，模型反而不是重点。评价一套实现好不好，只看一个指标：用户主动屏蔽它的速度。目标不是让 Agent 更能说，而是让它在正确的时间、用更少的条数，说真正值得说的话。
