## 背景

Agent 产出内容只是完成了一半。同一篇 Markdown 要进公众号、掘金、知乎和静态博客，各平台渲染器差异极大，手工适配是最消磨人的环节。我们把这一段做成了确定性管线：AI 只负责产出一份"规范 Markdown"，格式适配全部交给代码。

## 问题

实际踩到的坑集中在几类：

- 公众号会静默剥离外链图片和绝大多数 HTML，代码块原生无高亮；
- 任务列表、脚注在部分平台直接降级为普通文本，单换行被合并成一段；
- AI 输出不稳定：代码 fence 时而 `ts` 时而 `typescript`，偶尔夹带 front matter 或多余的 `<br>`；
- 逐平台写正则补丁，两周后没人敢动。

结论：需要一个中间表示，而不是 N 份手改稿。

## 做法

管线分四层，核心是"单一事实源 + 平台适配器"：

1. **生成层**：system prompt 约束模型只输出受限 GFM——不用内联 HTML、不用脚注、图片只写占位符；
2. **规范层**：用 remark 解析为 mdast 做 lint/fix，统一 fence 语言名、压缩空行、剥掉 front matter、校验标题层级；
3. **适配层**：每个平台一个纯函数 `(ast) => payload`。公众号适配器把代码块转成内联样式的 `pre`，图片走"下载→重传→替换 URL"；博客适配器负责注入 front matter；
4. **发布层**：产物直调平台 API 或落盘，保留 dry-run 先出预览。

骨架很短：

```js
const ast = fix(parse(raw));
const payload = toWechat(ast); // 纯函数，可单测
```

## 踩坑点

- 别用正则改 Markdown。代码块里的假语法、嵌套列表缩进，正则必炸，一律走 AST；
- 转换必须幂等：同一输入跑两遍结果一致，否则重试机制会放大污染；
- 图片是最隐蔽的：公众号对外链图静默替换成裂图，不报任何错，重传后必须校验返回 URL 可访问；
- 代码块里的 `<` 会被部分平台当标签吞掉，序列化阶段显式转义；
- 千万别让 AI 直接产出目标平台格式——格式和内容耦合后，管线无法回归测试。

## 可复用建议

- 维护一份覆盖你全部实际语法的"特性烟测文档"，每次改适配器跑一遍 diff；
- 适配器保持纯函数、无副作用，单测成本极低；
- 记录每次转换的 AST diff 日志，线上出问题可回放；
- 在 OpenClaw 里把发布封装成一个 skill / MCP 工具，入参只留平台名和源文件路径，管线细节对 Agent 不可见，防止模型自作主张改格式。

## 总结

这条管线的价值不在某个炫技转换，而在于把格式适配从"每次发布的认知负担"变成"一次性的工程投入"。AI 管内容，AST 管结构，适配器管平台，各管一段。最直观的变化：多平台发一篇内容，从半小时的修修补补变成一条命令。
