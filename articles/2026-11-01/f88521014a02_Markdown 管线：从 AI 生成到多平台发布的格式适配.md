## 背景

用 Agent 批量产出技术内容后，最大的摩擦不在生成，而在发布。同一篇 Markdown 要进公众号、知乎、静态博客、Notion，各平台渲染规则差异很大。人工复制粘贴调格式，每次十分钟起步，量一大就不可持续。我们把它做成了管线，核心思路只有一句：**AI 只产出一份受约束的 Markdown，平台差异全部交给下游转换层**。

## 问题

直接让模型"生成能发布的格式"不可靠，踩过的坑：

1. 模型会在 Markdown 里混入 HTML 标签和内联样式，各平台清洗策略不同，结果不可控；
2. 表格在公众号编辑器里经常崩，合并单元格直接丢列；
3. 代码块高亮依赖内联 CSS，粘贴时会被剥掉一部分；
4. 相对路径图片出站就挂，各平台外链防盗链策略还不一样；
5. 脚注、目录、任务列表等扩展语法，支持参差不齐。

## 做法

管线分四层，全部脚本化，适合挂到 OpenClaw 的 MCP 工具链上：

1. **生成层**：定义一份"可发布 Markdown 子集"规范——只允许 h2-h4、段落、列表、围栏代码块、引用、普通表格、图片。prompt 约束 + 生成后校验，双保险。
2. **校验层**：markdownlint 加自定义规则做 lint，例如禁止内联 HTML、图片必须走占位符。这一层是生成侧和转换侧的契约，违反就打回重生成，不要靠人读。
3. **转换层**：基于 remark/unified 的 AST 做转换，每个平台一个适配插件。公众号走自定义 renderer 输出内联样式 HTML；博客直接用原 AST 渲染；知乎走精简子集。AST 级操作比正则可靠一个量级。
4. **资产层**：发布前把图片统一传到自己的 OSS，生成绝对 URL 再分发，绕开相对路径和防盗链问题。

## 踩坑点

- 公众号 API 写入会被更激进地清洗，实测走剪贴板富文本粘贴存活率更高，自动化时优先考虑 headless 浏览器方案；
- 中文语境下 `_` 和 `*` 容易误触发强调，校验层加一条规则：正文中出现的下划线一律转义；
- 各平台对空行的解释不同，转换层先统一做软换行归一化，再进各适配器；
- 每次改渲染规则，用固定样例集跑渲染快照 diff，否则改动很容易悄悄弄坏某个平台。

## 可复用建议

- 把"可发布子集"当独立文档维护，它就是生成侧和发布侧之间的接口契约；
- 新平台只写适配插件，不动上游；上游规则变更只改 lint；
- 样例集 + 渲染快照是最便宜的回归测试；
- Agent 只做编排（调 lint、调转换、上报失败），格式判断逻辑收敛在脚本里，不要散落在 prompt 里。

## 总结

多平台发布的本质，是把格式适配从"人的经验"变成"可测试的代码"。约束生成、AST 转换、资产收口三层做完，一篇稿子从生成到五端发布可以压缩到分钟级，且失败可定位。管线的价值不在省下的几分钟，而在于发布质量不再依赖手气。
