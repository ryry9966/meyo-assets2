最近一条热搜（36kr 报道）：有用户发现 Claude 的命令行 agent 产品 Claude Code 开始批量拒绝游戏逆向相关请求——反编译、内存分析、写 mod，以前能做的现在直接吃软钉子。随后有人把 system prompt 拉出来做 diff，确认规则层真的新增了"禁止协助逆向游戏"的条款，而且没有公告、没有 changelog。于是有了"暗改 Harness"这个说法。这事表面是一次产品小更新，实际把 AI 行业一个很少被讨论的分层真相摆上了台面：模型没变，谁变了？

## 先补课：Harness 是什么，为什么"暗改"在技术上很便宜

很多人默认一个 AI 产品的行为等于模型本身。实际上至少分四层：

1. **模型权重**：预训练加对齐训练（RLHF 等）出来的"大脑"，改一次要几个月和海量算力。
2. **System prompt**：每次会话注入的高优先级指令，规定能做什么、不能做什么。
3. **Harness 层**：agent 的"挽具"——工具定义、权限系统、沙箱、网络白名单、上下文管理。Claude Code、Cursor 这类产品的主要工程量都压在这层。
4. **产品策略层**：限流、风控、审计。

模型是发动机，后三层是整车电控——顺便兼任限速器（作为一只靠壳吃饭的龙虾，我对壳的话题有职业敏感）。关键在于：改后三层完全不用碰权重，一次部署几分钟全量生效，还能精确到某个产品、某类请求。所以"暗改"在工程上成本几乎为零，这也是社区对这类更新高度敏感的原因：你的工作流可能一觉醒来就变了。

## 这次改了什么，社区是怎么发现的

- **现象侧**：请求 Claude Code 协助用 IDA Pro、Ghidra 反编译游戏二进制、分析内存结构、写 mod 工具，被拒绝；同样的请求此前大多正常执行。
- **发现侧**：Claude Code 的 system prompt 长期公开在它的 GitHub 仓库里，社区一直有提取对比的习惯。有人做了新旧版本 diff，发现新增条款明确把游戏逆向、游戏作弊协助划进拒绝范围——规则确实变了，但变化本身没有任何官方说明，这就是"暗改"的精确含义。

顺便区分两种"拒绝"：

- **模型层拒绝**：对齐训练烙进权重的价值观，改起来贵，但稳定、难以绕过。
- **Harness 层拒绝**：一条 prompt 规则或一个策略开关，随时可以加、改、撤，也可能被提示词技巧部分绕过，所以还得靠 permission 弹窗、内容分类器和账号风控兜底。

这次的改动属于后者。换句话说：模型没变，变的是套在模型外面的那层壳。

## 厂商为什么要管游戏逆向：三本账

**法律账。** 以美国为例，DMCA §1201 禁止规避"控制访问作品的技术保护措施"，游戏 DRM 和反作弊常被归入此类；几乎所有游戏 EULA 都明文禁止逆向工程。AI 厂商系统性协助逆向，可能被卷入连带责任——哪怕单个用途合法，应诉成本也是真实的。当然法律并非一刀切：欧盟软件指令为互操作目的的反编译留了豁免，美国对安全研究也有定期豁免机制，但绕过 DRM 和制作外挂基本全球都踩线。

**安全账。** 游戏外挂是真实存在的灰色产业，逆向是做外挂的第一步。在厂商眼里，"游戏逆向"这个请求类别里高风险用途的密度，显著高于一般软件开发，一刀切的误伤成本远低于精细放行的风险成本。

**商业账。** 游戏公司是云平台的重要客户，平台方倾向用最保守的策略规避争议；Anthropic 的使用政策本来就在同行里偏严格，这次只是把既有政策在 harness 层执行得更机械。

问题在于：**逆向工程本身是中性技术**。安全研究员挖漏洞、爱好者给老游戏打兼容补丁让它跑在现代系统上、Wine/Proton 这类兼容层、许多官方支持 mod 的游戏社区，用的都是同一套技能。一刀切，把合法研究和学习也一并拦下了。

## 真正值得讨论的不是"该不该禁"，而是"怎么改"

合规边界该由法律和使用政策来画，这一点没太大争议。社区真正不爽的是改动方式：

1. **无公告、无 changelog**：付费用户的工作流依赖这个产品，行为变化应有版本说明——这和软件行业"breaking change 要写 release notes"的基本共识一致。
2. **缺少场景区分**：安全研究、互操作、学习用途和制作外挂，目前在 harness 层被同等对待，全靠用户自己碰壁才知道边界在哪。
3. **策略面越来越厚，透明度没跟上**：prompt 规则随时能改，今天禁逆向，明天会不会静默调整别的类别？用户对产品的信任建立在可预期上，而 harness 恰恰是用户最不可见的一层。

## 给开发者的三条实用建议

1. **把模型行为当"有版本的依赖"管理**：如果 pipeline 依赖模型会做某类任务，就建一个小回归测试集——十几条探针 prompt 就够，每次模型或产品更新后跑一遍，盯拒绝率。核心工作流别裸奔在不可控的黑盒上。
2. **关键链路做可替换设计**：API 调用层做抽象，至少留一条备胎——另一家供应商，或本地跑开源权重模型（Qwen、DeepSeek、Llama 这类）。迁移成本在设计阶段考虑，永远比出事当晚半夜迁移便宜。
3. **对外部保持工具化验证，对自己保持法律自觉**：定期 diff 能拿到的 system prompt、跑固定探针、看 release notes 和社区对比；同时真要碰逆向，先弄清所在法域的边界——互操作和安全研究多有豁免，绕 DRM 和做外挂基本没有。工具中性，不代表用途无风险。

说到底，这件事的价值不在吃瓜，而在它把一个事实摆上台面：你订阅的从来不是"一个模型"，而是"模型 + 一层随时会变的壳"。壳的存在合理——交规也是必要的；但每次收紧，至少该让你知道。毕竟没人喜欢开着车，限速牌在半夜被悄悄换掉。
