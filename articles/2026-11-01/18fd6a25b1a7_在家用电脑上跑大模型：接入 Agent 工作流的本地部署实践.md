## 背景

跑了一年 OpenClaw 的自动化流程后，我有个直接感受：Agent 的日常开销大头不在"想"，而在"等"——等 API 返回、等额度、等账单。家里那台 4070 主机大部分时间在吃灰，于是花了两个周末把本地模型接进 Agent 工作流。这篇记录能跑通的最小路径和踩过的坑。

## 问题

本地模型跑 Agent 和跑聊天是两回事，差距集中在三点：

1. **工具调用**：很多小模型宣称支持 function calling，但在多轮工具循环里频繁产出不合法 JSON；
2. **上下文**：Agent 的系统提示词加工具定义动辄几千 token，运行时默认上下文窗口偏小且会静默截断，表现为"模型突然忘了自己是谁"；
3. **显存**：量化模型本体 + KV cache 要一起算，上下文开大后显存翻倍很常见。

## 做法

1. **盘点硬件**。经验值：8GB 显存跑 7~8B 的 Q4 量化；16GB 上 14B；24GB 可试 32B。Mac 统一内存另算，但要给系统留余量。
2. **选运行时**。图省事用 Ollama，要控制并发和上下文用 llama.cpp 的 llama-server，两者都提供 OpenAI 兼容接口——这是后面一切的前提。
3. **选模型**。中文 + 工具调用场景优先 Qwen 系列，Q4_K_M 是质量与体积的平衡点；别用小众微调权重做 Agent 主力，翻车概率高。
4. **接入 OpenClaw**。把本地运行时当成一个 OpenAI 兼容的自定义 provider，baseUrl 指向本机，再挂给主 Agent 或某个子 Agent：

```json
{
  "models": {
    "providers": {
      "local-ollama": {
        "baseUrl": "http://127.0.0.1:11434/v1",
        "apiKey": "ollama",
        "api": "openai-completions"
      }
    }
  }
}
```

（字段名以你版本的配置文档为准，思路不变。）

5. **验证**。写一个 20 行的冒烟脚本：强制触发一次工具调用 → 校验返回 JSON 是否合法 → 连跑三轮。如果你的工具层走的是 MCP server，本地模型对工具 schema 的遵循度就是第一道门槛，这个脚本比任何跑分都接近真实体验。

## 踩坑点

- 上下文窗口必须显式设置（如 Ollama 的 `num_ctx`），默认值很小；调大后记得重算显存；
- 量化低于 Q4 后，工具调用失败率的恶化比"智力下降"来得更早，优先保 Q4；
- 长会话 token 会滚雪球，配合会话压缩或定期重置，否则显存和延迟双双崩掉；
- 别拿单轮聊天测性能，要拿真实 Agent 循环测——单次工具调用的往返延迟才是体感；
- macOS 上长任务注意热节流，内存占用别顶满。

## 可复用建议

- 所有模型统一走 OpenAI 兼容接口，换模型只改配置、不动代码；
- 做模型分层：高频低难度子任务交给本地小模型，难推理回落云端大模型，成本和可用性都划算；
- 冒烟脚本纳入"换模型必跑"清单；
- 记录每轮 token 用量和单次工具调用延迟，这两个数字足以判断要不要升级硬件。

## 总结

家用电脑跑本地模型，如今已足够承担 Agent 工作流里的常规任务，但还独挑不了大梁。可行路线是：**兼容接口 + 显式上下文 + 工具调用冒烟测试**，先从 7~8B 当子 Agent 开始，跑稳了再扩大。数据不出门、边际成本为零，对长期挂机的自动化场景来说，这两点的价值比跑分数字实在得多。
