## 背景

Agent 用久了都会遇到同一个问题：能力越堆越多。MCP 工具、常用脚本、领域 prompt 片段……早期做法是全部塞进系统提示词。十几个工具时还行，到了三四十个，问题就出来了：每轮对话都背着全套描述，token 开销固定上涨，模型在相似工具之间选错的概率也明显变高。

OpenClaw 的 Skills 机制本质是对此的工程化解法：把能力从“常驻上下文”改成“按需加载”，思路类似操作系统的按页加载——平时只留索引，用到才读正文。

## 问题：上下文是稀缺资源

具体拆开是三个问题：

1. **成本**：工具描述、使用说明全部常驻，每轮对话都在为用不到的能力付费。
2. **注意力稀释**：上下文越长，模型对单条指令的遵循度越差，工具误选率上升。
3. **维护**：一个大 prompt 文件改一行要整体 review，改坏了难回滚。

Skills 的解法是分级加载：第一级只有 name + description（常驻，几十 token）；第二级是 SKILL.md 正文（命中时才加载）；第三级是正文引用的脚本、模板（真正执行时才读）。

## 做法

以给助手加一个“日志检索”能力为例。

第一步，建目录和清单文件：

```
skills/
  log-search/
    SKILL.md
    scripts/parse_log.py
```

第二步，写 SKILL.md，重点是 frontmatter：

```markdown
---
name: log-search
description: 当用户要求查询、过滤或统计服务日志时使用。
  覆盖 Nginx 访问日志和应用错误日志，
  不适用于数据库慢查询分析。
---

## 步骤
1. 确认日志路径与时间范围
2. 先读 scripts/parse_log.py 头部注释，再按说明调用
3. 输出按错误码分组统计
```

第三步，验证触发。用三类 prompt 测试：明确命中（“统计昨晚的 500 错误”）、边缘情况（“昨天服务是不是挂过”）、明确不命中（“分析慢 SQL”）。观察 description 是否把请求路由到预期位置。

## 踩坑点

- **description 写成“是什么”而不是“什么时候用”**。写“这是一个日志工具”基本不会触发；写清触发条件和排除项，命中率才稳定。
- **能力边界重叠**。两个 skill 都声称处理“日志”，模型只能猜。要么合并，要么在 description 里显式划界（如上例排除慢查询）。
- **正文当垃圾桶**。所有细节都塞进 SKILL.md，等于变相恢复常驻加载——命中一次就全量进上下文。长细节放引用文件。
- **假设模型会“主动”读文件**。正文要写指令式步骤（“先读 xxx 再执行”），含糊的“参见相关脚本”经常被跳过。
- **只加不减**。Skill 数量会自然膨胀，建议每月看一次触发日志，把长期不命中或常误触发的下掉、合并。

## 可复用建议

- 一个 skill 只做一件事。判定标准：description 能否一两句写清，且不出现“和/或”。
- 把 description 当路由规则写：触发条件 + 适用范围 + 排除项，三段式最稳。
- 正文控制在百行以内，超过就拆引用文件。
- 有副作用的 skill（执行脚本、改文件），在正文里写明幂等性约束和回滚方式。

## 总结

Skills 机制的价值不在“多了一种插件格式”，而在于把能力管理的粒度从“整套系统提示词”细化到“可独立路由的单元”。对长期运行的 Agent 来说，这直接决定上下文成本曲线和工具选择的稳定性。建议先拆两三个最占上下文的能力做验证，比一次性重构现实得多。
