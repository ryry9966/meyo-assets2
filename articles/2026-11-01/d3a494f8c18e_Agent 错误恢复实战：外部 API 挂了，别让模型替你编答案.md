## 背景

跑过自动化流程的人都有体感：Agent 链路里最不稳定的往往不是模型，而是它调用的外部 API——MCP 工具、第三方接口、自建服务。传统服务挂了会老老实实报错返回，Agent 的问题是它"太聪明"：模型拿到一段报错 HTML 或超时堆栈，很可能顺手编一个看起来合理的答案继续往下跑。所以在 Agent 场景里，错误恢复不只是工程问题，还是提示词与编排的问题。

## 三类典型故障

- **瞬时故障**：限流 429、网关 502、偶发超时，占绝大多数，重试就能解决；
- **持续故障**：依赖服务宕机或接口改版，重试只会烧配额和时间；
- **语义故障**：接口返回 200 但 body 里是错误码，或返回结构和预期不符。

更麻烦的是 Agent 循环会放大问题：一次失败可能触发模型自发重试十几轮，token 烧完，任务还没恢复。

## 做法：分层处理

原则是把恢复逻辑做在工具适配层和编排层，模型只负责决策，不负责机械重试。

**1. 统一错误契约。** 所有外部调用过一层适配器，把原始响应归一化成 `{code, retryable, message}`。超时、5xx、429 标记为可重试；参数错误、鉴权失败标记为不可重试。给模型的 message 写成人话，比如"工具暂不可用，预计 60 秒后恢复"，而不是丢堆栈。

**2. 受限重试。** 指数退避加抖动，最多 3 次，仅在 retryable 时触发；429 优先读 Retry-After。非幂等操作（下单、发消息）必须带幂等键，否则宁可把错误抛给上层。

**3. 熔断与降级。** 同一工具连续失败 N 次就熔断，冷却期内直接向模型返回"不可用"，让它改道：切换备用工具、使用带时间戳标记的缓存数据、跳过可选步骤，或升级给人工。哪些步骤是非必经路径，要提前在任务定义里标出来。

**4. 断点续跑。** 任务状态持久化，恢复时从最后成功的工具调用继续，而不是从头再算一遍。

## 踩坑点

- **把原始报错直接塞给模型**：它会把 HTML 错误页当数据处理，输出一本正经的幻觉。
- **只在 prompt 里写"失败请重试"**：模型没有可靠的计数概念，重试上限必须在代码里卡死。
- **重试非幂等接口**：导致重复扣款、重复发消息，这类事故最难回滚。
- **把 200 但 body 异常当成功**：对工具返回做 schema 校验，别信状态码。
- **熔断后对模型完全隐藏故障**：模型不知道工具挂了就不会调整计划；要给它干净的状态，而不是堆栈细节。
- **多会话共享配额**：单会话限流没问题，全局配额被打爆，需要全局限速器。

## 可复用建议

- 每个工具一张配置卡：timeout、max_retries、退避基数、熔断阈值、降级策略，集中管理，别散落在各处 prompt 里。
- 在 CI 里做故障注入：mock 一个必超时的接口，验证整条链路的降级行为，比线上救火便宜得多。
- 不可逆动作（支付、删除、对外发送）一律走人工确认，自动恢复不能替你做决定。
- 日志按工具调用粒度记结构化事件，事后能回放完整的恢复过程。

## 总结

API 挂了不可怕，可怕的是 Agent 在故障里安静地跑偏。恢复能力的核心是分层：适配层管重试与熔断，编排层管降级与续跑，模型层只拿干净的错误状态做决策。把这套做扎实，Agent 才配得上"自动化"三个字。
