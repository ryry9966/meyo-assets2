## 背景

Agent 跑久了，记忆库成了最值钱的资产：历史决策、踩过的坑、用户偏好、项目约定。我在 OpenClaw 里给助手挂了一个 `memory_recall` 工具，底层是 SQLite 存的记忆条目。用下来发现，召回质量直接决定助手"记不记得住事"——库再大，召不回等于没存。

## 问题：两条路都有坑

最初直接上语义检索：条目过 embedding 存 sqlite-vec，查询时算余弦相似度。表现：

- 模糊描述、口语化提问召回不错；
- 但专有名词、配置项名、命令行片段经常搜不到，或者排在前面的都是"语义相近但答非所问"的条目。

换成 SQLite FTS5 全文检索（BM25）：

- 关键词命中极准，代码片段、参数名、报错信息一搜一个准；
- 但换个说法就抓瞎："部署脚本挂了"搜不到写着"CI 流水线失败处理"的条目。

单选哪个都有明显短板，这才认真做混合召回。

## 做法

1. **统一存储结构**：每条记忆含原文、摘要、标签、时间戳、来源 session。原文进 FTS5 虚表，摘要和原文的 embedding 进向量表。
2. **两路并行召回**：查询同时走 FTS5（top 8）和向量检索（top 8）。
3. **RRF 融合**：倒数排名融合，不用对齐两路相似度分数的量纲，实现二十来行。
4. **元数据过滤前置**：时间范围、标签先过滤再召回，避免"三年前的旧配置"靠相似度挤进前排。
5. **温和的时间加权**：融合分数乘一个轻量衰减，别设狠了。
6. **建评测集**：从真实对话里挑 30 条查询，标注期望命中的记忆 ID，每次改动跑一遍命中率。

效果：纯语义命中 21 条，纯全文命中 24 条，混合 RRF 命中 27 条，代价是几十行代码。

## 踩坑点

- **FTS5 默认 tokenizer 不切中文**：整段中文会成为一个 token，等于搜不了。要么换支持中文分词的 tokenizer，要么入库前先分好词再写入。
- **embedding 模型挑内容类型**：记忆里有大量代码片段时，注意模型是否训过代码，否则代码条目的向量质量很差。
- **top-k 别贪大**：召回 20 条塞进 context，噪声比信息多，回答质量反而下降。8~12 条加好的排序，比 30 条强。
- **时间衰减别过猛**：系数设狠了，半年前的关键决策永远召不回，助手开始"失忆式瞎编"。
- **记忆要有失效概念**：召回一条过期配置，模型照着答，比不召回更糟。更新记忆时写新条目并标记旧条目过期，过滤时排除。

## 可复用建议

- 混合召回（FTS + 向量 + RRF）是默认起点，纯语义并不是"更高级"的选择。
- 先有评测集再调参，凭感觉调权重是玄学。
- 元数据过滤的价值常被低估：时间、标签、来源比相似度分数更能挡住垃圾召回。
- `memory_recall` 的入参设计成"关键词 + 时间范围 + 标签"的组合，让模型自己拼条件，比单一 query 参数灵活得多。

## 总结

语义搜索解决"换个说法也找得到"，全文搜索解决"关键词必须命中"，两者覆盖的失败模式几乎不重叠。对个人 agent 来说，SQLite FTS5 + 向量扩展 + RRF 是成本最低、可解释性最好的组合，一个下午能落地。别急着上重型 reranker，先把评测集建起来——数据会告诉你下一步该优化什么。
