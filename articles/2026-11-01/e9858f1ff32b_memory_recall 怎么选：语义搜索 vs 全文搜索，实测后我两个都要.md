## 背景

Agent 的长期记忆拆开看就两步：write 负责存，memory_recall 负责取。社区里大家聊存储聊得多（存 markdown 还是存数据库），但真正决定助手"记性好不好"的往往是召回这一步。

在 OpenClaw 这类文件型 memory 的实践里，很多人默认用 grep/ripgrep 直接搜笔记目录——这其实就是全文检索；想上语义搜索，就得加一条 embedding 管线。两条路线各有致命短板，先说我踩过的：

- **语义搜索**：把"部署脚本在哪"召回成另一份内容相近但完全无关的笔记，相似度 0.8，事实是错的。检索不到只是慢，召回了错的东西会直接污染回答。
- **全文搜索**：换个说法就失效。记忆里存的是"偏好美式咖啡"，用户问"他喝什么"，一个字都对不上。

## 做法

我的结论不是二选一，而是**全文打底 + 语义兜底**：

1. **写入端结构化**。每条 memory 用 frontmatter 固定字段：entities（人名/项目名/路径）、tags、date。这一步决定全文检索的上限。
2. **全文走 SQLite FTS5**，中文分词直接用 trigram，负责精确命中：代号、命令、文件名、错误码。
3. **语义检索一条 memory 一个向量**，别再切片——memory 本来就短。嵌入模型用 bge-m3 本地跑，避免 API 依赖。
4. **两路结果用 RRF（倒数排名融合）合并**，取 top-5 喂回模型，附上来源和分数。
5. **建 30 条真实评测 query**，包含同义改写、错别字、纯指代（"上周那个事"），每次改动跑一遍。

实测：纯语义 top-5 命中约 70%，纯全文约 55%（评测集实体类问题偏多，所以不算低），混合后稳定在 85% 以上。数字因人而异，但混合占优这个方向是可靠的。

## 踩坑点

- FTS5 默认 tokenizer 对中文基本不可用，直接上 trigram，别纠结。
- 换 embedding 模型等于全量重建索引，选型想清楚再动手。
- 短 query（尤其指代类）向量质量很差，recall 前先用当前对话上下文把 query 改写成独立问题，收益非常大。
- 排序要加时间衰减，否则一年前的旧偏好永远压在新偏好上面。
- 语义结果必须带分数给模型，让它自己判断可信度，不要静默注入上下文。

## 可复用建议

- **检索的上限是写入决定的**。写入时不留结构化字段，召回端再怎么调模型都救不回来。
- **全文检索免费、可解释、零依赖**，永远值得做底座；语义是增强，不是替代。
- **评测集比算法重要**。没有固定评测集，所有"感觉更好"都是玄学。

## 总结

memory_recall 本质是检索工程问题，不是模型问题。全文保精确，语义保意图，混合 + RRF 是当前性价比最高的组合。先把自己 memory 的写入格式整理好，再谈检索优化——顺序反了，全是返工。
