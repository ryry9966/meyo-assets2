## 背景

OpenClaw 的 cron 任务，本质是定时把一条 instruction 塞给 agent，让它在没有你陪跑的情况下自己跑完。它和交互式对话最大的区别是：**没有上下文**。你昨天聊过什么、你"默认它知道"什么，它在触发那一刻统统不知道。instruction 就是它醒来时看到的全部世界。

## 问题

我最早写的 cron instruction 大概是：「每天早上看看 GitHub 通知和日历，有重要的就提醒我」。跑了三天就废了：两天发了废话，一天该报的没报，还有一天它自己"总结"出一份根本不存在的会议纪要。复盘下来，问题不在调度，在 prompt 写法。

## 做法

后来我把 instruction 当成"给夜班值班同事的交接单"来写，固定六个块：

1. **目标**：一句话说清这次运行要判断什么，而不是"看看""关注一下"。
2. **输入来源**：明确用哪个工具取什么数据。写"用 GitHub 工具拉取 unread notifications"，而不是"看看通知"。
3. **判断标准**：什么算"重要"。给可执行规则，比如"提到我或 CI 失败算重要；bot 的 weekly digest 不算"。
4. **输出动作**：往哪个通道发、什么格式、发几条。以及最关键的一条——**无事可报时保持沉默**。
5. **失败分支**：取不到数据、工具报错时怎么办。我的写法是"跳过本次，在日志里记一行原因"，绝不允许编数据补位。
6. **边界**：限定最多几步、允许动哪些工具，防止它为了"看日历"顺手去翻文件系统。

## 踩坑点

- **假设有对话上下文**。cron 里的"接着上次说的"是空中楼阁，它跑在一个干净的会话里。
- **沉默规则缺失**。agent 默认倾向于"汇报点什么"，通知疲劳就是这么来的。
- **没写失败分支**。agent 宁愿编一份像样的结果，也不愿交白卷，这是最危险的一类错误。
- **时区**。"每天 9 点"是哪个时区的 9 点，第一次上线前务必确认。
- **instruction 长期打补丁**。每次出问题就加一句"不要 XX"，三个月后变成一锅粥。出问题时重写，比追加有效。

## 可复用建议

- 把每条 cron instruction 存进 git，改动像改代码一样提交，任务跑挂了能 diff 回溯。
- 新任务先手动触发（或用极短间隔）跑几次，确认行为符合预期再上正式排程。
- instruction 结尾固定加一句自检："如果以上任一步无法完成，报告原因并结束，不要推测数据。"
- 输出统一落盘一份，方便事后审计 agent 当时到底看到了什么、为什么做出那个判断。

## 总结

Cron 任务的 instruction 不是"提示词"，而是一份无人值守的作业说明书。检验标准很简单：**一个没参与过你们对话的人，照着这份单子，能不能做出和你预期一致的判断**。能做到，这份 instruction 就算合格了；做不到，再精准的 cron 表达式也救不回来。
