## 背景

Agent 的本体是模型，模型只会生成文本，真正“动手”靠工具调用。在 OpenClaw 里对接外部服务通常有三条路：直接挂现成的 MCP server、用插件机制封装私有 API、或者写一层薄的 HTTP 工具适配器。最近把内部工单系统接进了 Agent，把流程和踩过的坑整理如下。

## 问题

裸接 API 看着简单，实际会撞上四类事：

1. **鉴权**：密钥放哪，怎么不进上下文和日志；
2. **Schema**：参数描述含糊，模型就乱填；
3. **容错**：超时、重试、限流，非幂等接口重试会造重复数据；
4. **上下文**：接口返回大 JSON 直接塞给模型，token 爆掉还干扰判断。

## 做法

1. **选接入方式。** 目标服务已有 MCP server 就直接挂载；没有就写适配器，把 REST 调用拆成粒度合适的 tool。原则是“一个 tool 干一件事”，`create_ticket` 和 `query_ticket` 分开，别做一个万能 action 让模型传 JSON 字符串。
2. **认真写 schema 和 description。** name 用动词+名词，description 写清何时该用、何时不该用、参数的枚举、格式和单位。这不是文档，是提示词的一部分，直接决定调用质量。
3. **鉴权收敛到适配层。** 密钥从环境变量读，在适配器里注入 header；返回结果剥掉凭据字段；日志落盘前脱敏。
4. **容错设计。** 统一超时（10s 量级）、指数退避重试，且只对幂等操作重试；写操作带幂等键。错误不要抛异常了事，而是返回结构化对象（错误码 + 一句原因 + 建议动作），模型才能自己决定重试、改参数还是问用户。
5. **先 mock 后联调。** 本地起假服务先验证 tool 定义和错误路径，再切真实环境；调用全量记 trace，方便回放。

## 踩坑点

- description 只写“调用工单接口”，模型把查询当创建用；补上典型场景说明后明显好转。
- 列表接口默认返回 200 条，两轮对话就吃满上下文；改成默认 10 条 + `has_more` 标记，让模型按需翻页。
- 网络抖动触发重试，重复建了三张单；写操作统一加幂等键后解决。
- 上游悄悄改了字段名，Agent 开始传空值；适配层加 schema 校验，失败就报错而不是透传。
- 错误信息里带内部 URL 和 token 片段，被模型原样念给用户；适配层加了错误白名单。

## 可复用建议

- **薄适配层**：API 语义不泄漏进 Agent，统一在适配器翻译。
- **schema 优先**：先定 tool 契约再写实现，description 当提示词写。
- **结构化错误**：错误码 + 原因 + 建议，模型才能自愈。
- **上下文预算**：任何返回设上限，分页优于全量。
- **幂等与限流**：写操作带幂等键，读操作尊重 429。
- **密钥不过模型**：凭据只存在于适配层。

## 总结

对接外部服务的目标不是“能调通”，而是给模型一个边界清晰、错误可读、成本可控的接口面。鉴权、容错、schema 这些工程活儿做扎实，Agent 的稳定性才会从看运气变成可预期。欢迎在评论里交流你们对接第三方服务时的容错策略。
