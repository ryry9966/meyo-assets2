## 背景

Agent 本身只会“想”，不会“做”。OpenClaw 里的 agent 要查工单、发通知、读内部系统，最终都落在一件事上：调外部 HTTP API。MCP 把工具调用协议标准化了，但协议只解决“怎么握手”，不解决“握完手怎么才能不出事”。这篇记录一下我们内部对接的常见模式和踩过的坑。

## 问题

实际对接中最常见三类故障：

1. **模型用不好工具**：参数多、描述含糊，agent 乱传参，或者干脆绕过工具自己编答案；
2. **链路不稳**：上游限流、超时、5xx 一来，agent 陷入死循环重试，或把原始报错直接吐给用户；
3. **边界不清**：密钥混进日志和会话历史，写操作没有闸门，一个误调用就造成线上事故。

## 做法

以“让 agent 查询内部工单系统”为例，推荐的接入步骤：

1. **选好接入层**。长期服务建议把外部 API 包成一个薄 MCP server，工具接口就是 agent 能看到的全部世界。临时验证可以先用 HTTP 插件，但别让它活过一周。
2. **工具定义要窄**。一个工具只做一件事；参数尽量枚举化、格式写死（比如日期固定 `YYYY-MM-DD`）；描述写“什么时候该用我、什么时候不该”，而不是复述 API 文档。
3. **收窄返回**。API 回 200 行 JSON，agent 拿到的应该只有它需要的几个字段。裁剪和摘要放在工具层，别让原始响应撑爆上下文。
4. **错误要翻译**。429、超时、5xx 在工具层拦截，返回结构化结果如“限流，建议 30 秒后重试”。重试与退避逻辑也放工具层，不要指望模型自己会节制。
5. **密钥走环境变量**。API key 只进进程环境，不进 prompt、不进会话历史、不进日志。
6. **读写分离**。查询类工具默认放行，写操作（建单、发消息）单独挂权限开关，先在灰度环境验证再放开。

## 踩坑点

- **描述写成文档复读机**，模型反而不知道何时调用。描述的核心是触发条件和边界，不是参数罗列。
- **POST 被 agent 重试导致重复建单**。写接口要么带幂等键，要么在工具层按请求指纹去重。
- **原始 JSON 塞满上下文**，agent 开始幻觉字段名——这是排查难度最高的一类问题，因为表现像模型 bug，实际是数据 bug。
- **一个 agent 挂十几个工具**，选择准确率肉眼可见地下降。按场景拆 profile，哪个场景加载哪组工具。

## 可复用建议

- 把“对接外部服务”固化成模板：**薄 MCP server + 环境变量密钥 + 裁剪返回 + 结构化错误**。新服务接入通常只改一个文件。
- 每个工具配一个最小调用用例，升级模型或改 system prompt 后回归一遍——工具行为对 prompt 的敏感度远超预期。
- 上线后保留工具调用链日志：入参、耗时、返回码三个字段，足够定位九成问题。

## 总结

Agent 对接外部服务，本质不是“接 API”，而是给模型造一个足够窄、足够稳、可观察的工具世界。MCP 解决了握手，剩下的全是工程活：窄接口、翻译错误、守住密钥与写权限。把这套模板沉淀进团队，OpenClaw 里每接一个新服务的边际成本就会趋近于零。
