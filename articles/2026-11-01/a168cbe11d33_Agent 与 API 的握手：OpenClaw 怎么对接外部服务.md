## 背景

早期用 OpenClaw，Agent 大部分时间在"说"：总结、翻译、写文案。但社区里的问题越来越多变成"做"：查库存、发工单、同步日历。让 Agent 真正对接外部服务，是它从聊天玩具变成自动化工具的分水岭。

MCP 的出现让这件事有了标准形状——工具声明、参数 schema、调用协议都规范化了。但标准归标准，真正接一个生产 API 时，坑都藏在标准没写的部分。

## 问题：直接把 API 塞给 Agent 会怎样

最省事的做法是写一个通用 HTTP 工具，让模型自己拼 URL 和参数。我们的经验是：demo 能跑，生产必挂。典型故障模式：

- 模型幻觉出不存在的路径或参数，请求打到错误接口
- 响应体太大，直接把上下文撑爆
- 限流 429 没有退避，连环重试雪上加霜
- 非幂等接口重试导致重复下单、重复建单
- 密钥写死在配置里，跟着日志一起被打印出去

这些问题的共同点：不是模型能力问题，是工程边界没画好。

## 做法：五步握手

**1. 用插件层封 API，别让模型裸拼请求。** 把每个外部服务封装成 OpenClaw 插件或 MCP server，工具粒度按"业务动作"切，比如 `create_ticket` 而不是 `http_post`。模型只负责选工具、填参数，URL、鉴权、重试都收在插件代码里。

**2. 参数用 JSON Schema 严格约束。** 必填项、枚举值、格式都在 schema 里声明，OpenClaw 调用前会校验。schema 写得越死，幻觉空间越小。

**3. 输出先裁剪再回传。** API 返回 200 条记录，不要原样塞给模型。插件层做分页和字段过滤，只回传决策需要的部分，必要时先做一层摘要。

**4. 密钥走环境变量或专用凭证存储。** 插件读取凭据，不进 prompt、不进日志、不进上下文。轮换密钥只改环境配置，不动 Agent 逻辑。

**5. 失败要可预期。** 统一超时（我们一般 10s）、指数退避重试（最多 3 次）、非幂等请求强制带幂等键。错误回传给模型时用结构化短描述，让 Agent 能判断"重试、放弃还是问用户"。

## 踩坑点

- **schema 太宽松**：参数全写成 string，模型填什么都"合法"，出错查不到原因。宁可 schema 写严，调用失败也比写脏数据强。
- **忽略分页语义**：只取第一页当全量结果，数据对不上还以为是模型错了。
- **重试没带幂等键**：支付类接口超时重试，订单重复创建，事后对账才发现。
- **日志带敏感头**：Authorization 头整段打进调试日志等于密钥裸奔，日志必须先脱敏。
- **没有健康检查**：外部服务挂了，Agent 陷入重试循环烧 token。插件层先探活，失败快速短路。

## 可复用建议

- 沉淀一个内部"API 接入模板"：schema 校验、超时、重试、脱敏日志、mock 开关都是现成的，新服务只填业务逻辑，接入时间从一天缩到半小时。
- 先用 mock 模式跑通 Agent 编排，再切真实 API，联调成本大幅下降。
- 给每个工具记指标：成功率、P95 耗时、重试次数。Agent 行为异常时，先看工具指标，再看对话记录。

## 总结

Agent 对接外部服务的本质，是把"模型的不确定性"关进"工程的确定性"里：模型负责理解和决策，插件负责鉴权、校验、重试和裁剪。OpenClaw + MCP 已经把协议层铺好了，剩下的活是老老实实的接口工程——schema 严一点，输出窄一点，失败路径想全一点。握手握不握得稳，看的不是模型多聪明，而是边界定义得多清楚。
