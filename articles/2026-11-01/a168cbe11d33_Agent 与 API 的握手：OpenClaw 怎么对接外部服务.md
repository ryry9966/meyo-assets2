# Agent 与 API 的握手：OpenClaw 怎么对接外部服务

## 背景

OpenClaw 本身不生产能力，它的价值在于把模型推理和真实世界的接口连起来。无论是查快递、开工单，还是调内部系统的一条查询接口，Agent 真正“干活”的那一步，永远是调一个外部服务。这一步稳不稳，直接决定自动化流程能不能放它过夜跑。

## 问题

很多对接是这样失败的：把 API 文档整段塞进 prompt，让模型自己拼 URL、拼鉴权。结果可以预见——密钥进了上下文、参数偶尔幻觉、超时没有兜底、一次自动重试把订单创建了三遍。本质是把“协议层”和“决策层”混在了一起：模型擅长决定“调哪个工具、传什么参数”，但不擅长也不应该负责“怎么可靠地调”。

## 做法

我们的做法是给每个外部服务包一层薄适配，优先走 MCP：

1. **圈范围**。先接只读接口（查询、列表），写操作放第二阶段，且必须支持 dry-run。
2. **写薄封装**。用 MCP server 或插件把 REST 包成工具：一个工具只做一件事，入参用严格 JSON Schema，出参做字段裁剪，只返回模型需要的部分。
3. **管好鉴权**。API key 走环境变量或密钥文件，由适配层读取，永不进入对话上下文和日志。
4. **兜住错误**。适配层内做超时、限流退避和错误码翻译，把 503 翻译成模型能理解的“服务暂不可用，建议稍后重试”，而不是抛一堆堆栈。
5. **写操作加幂等键**。客户端生成 idempotency key，重试不产生重复副作用。
6. **先灰度**。新工具先只对自己可见，观察一周调用日志再放开。

## 踩坑点

- **工具描述写得太泛**。像 `query_data` 这种名字会让模型滥用。描述里写清适用场景和反面例子，调用准确率高很多。
- **返回体太大**。一次 20KB 的 JSON 会挤爆上下文、稀释注意力。裁剪、分页、摘要都必须在适配层做完。
- **重试无幂等**。POST 类接口没加幂等键就自动重试，是最容易出事故的地方。
- **超时不分层**。连接超时、读超时、模型侧超时要分开设，否则 Agent 会在一个坏接口上干等到底。
- **密钥图省事写进配置仓库**。私有仓库也不建议，统一走环境变量，配合定期轮换。

## 可复用建议

- 适配层保持"薄"：鉴权、重试、裁剪三件事之外，不要往里塞业务逻辑。
- 每个工具配一条最小可复现的 curl 用例，回归时直接跑。
- 日志记工具名、参数摘要、耗时、状态码，不落原文密钥。
- 工具数量克制：相关接口合并成一个带枚举参数的工具，往往比十个相似工具更好用。
- 假设上游一定会挂：关键写操作保留一个人工确认位。

## 总结

Agent 对接外部服务的正确姿势，不是让模型更像工程师，而是工程师先把工程活儿干完：鉴权、重试、幂等、裁剪都沉淀在适配层，模型只负责决策。OpenClaw 的 MCP / 插件机制正好提供了这条边界。边界画清楚了，“握手”才握得稳。
