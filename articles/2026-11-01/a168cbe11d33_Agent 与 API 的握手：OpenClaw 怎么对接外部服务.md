## 背景

Agent 的价值最终落在“能不能干活”上，而干活大概率意味着调外部服务：查工单、发通知、拉数据、写记录。OpenClaw 本身是执行器，真正的能力边界在它握到的工具上。社区里常见的两条路：给模型直接挂 HTTP 调用工具，或者走 MCP 把外部服务标准化地接进来。两种我们都试过，这篇聊聊实际对接中比较稳的路径。

## 问题

直接对接会遇到三件事：

1. 模型不知道接口长什么样，参数全靠猜，猜错就重来一轮；
2. 鉴权、限流、超时这些工程问题没人兜底，一次失败把整轮任务带崩；
3. 返回体动辄几十 KB，塞进上下文又贵又乱，模型还得自己捞关键字段。

## 做法

我们的思路是“薄封装 + 结构化返回”，四步：

**第一步：用 MCP server 包一层。** 不把原始 API 裸露给 Agent，而是写一个薄薄的 MCP server，每个 tool 对应一个业务动作，比如 `query_order`、`create_ticket`。JSON Schema 里把参数类型、必填项、示例写清楚——description 是写给模型看的接口文档，含糊一个词，调用就歪一次。

**第二步：鉴权收敛到 server 侧。** API key 走环境变量注入，Agent 侧只见 tool 不见凭证；token 过期刷新也在这层做，不要让模型去处理 401。

**第三步：裁剪返回体。** 外部接口返回 50 个字段，Agent 通常只需要 5 个。在 server 里做字段映射和截断；分页数据只回第一页加总数，让模型自己决定要不要翻页。

**第四步：把错误写成“给模型看的提示”。** 返回 `{"error": "date format should be YYYY-MM-DD, got 2024/01/01"}`，模型下一轮就能自我修正；返回一个裸的 500，它只会原地重试。

## 踩坑点

- **非幂等操作被重试。** 网络超时后模型很可能重发请求，下单、发消息这类动作要在 server 侧加幂等键，或在 tool 描述里明确标注“此操作不可重试”。
- **工具挂太多。** 一次挂 40 个 tool，模型的选择准确率明显下降。按场景拆 profile，单次会话只挂相关的十来个。
- **写操作没有 dry-run。** 建议每个写类 tool 配一个 preview 参数，默认只回显将要执行的动作，确认后再真执行。
- **日志泄密。** 把请求体原样打进日志，凭证就跟着落盘了。脱敏必须在 server 里做，别指望事后清理。

## 可复用建议

- description 写三样就够：干什么、参数含义、什么时候**不该**调用。最后一样最常被漏。
- 所有 tool 返回统一外层结构（`ok / data / error`），Agent 的分支判断会稳定很多。
- 接新服务先写一个只读 tool 跑通全链路，验证鉴权和返回裁剪，再逐步放开写权限。

## 总结

对接外部服务不是“调通了”就完事。握手的关键在三层约定：Schema 是给模型看的文档，MCP server 是工程护栏，裁剪过的返回体是省下来的上下文成本。把这三层做扎实，Agent 才能从“演示能跑”走到“敢让它值班”。欢迎在社区帖子里贴出你们的 tool 描述写法，一起对齐最佳实践。
