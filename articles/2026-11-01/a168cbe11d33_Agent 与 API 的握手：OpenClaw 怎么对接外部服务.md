## 背景

Agent 的价值在于能"动手"。一个只会聊天的模型意义有限，OpenClaw 这类 agent 框架的核心能力，是把 LLM 的决策接到真实世界的 API 上：查工单、发消息、写数据库、触发构建。但"接得上"和"接得稳"是两回事。这篇帖子记录我们把几个内外部服务接进 OpenClaw 的过程，重点放在 MCP 与 HTTP tool 两条路线的选择，以及落地时的细节。

## 问题

实际对接时，坑基本不在"能不能调通"，而在这些地方：

- 工具描述写得像人看的文档，模型却读不懂什么时候该用、参数怎么填；
- API 返回原始大 JSON，直接灌进上下文，几次调用就撑爆窗口；
- 错误处理缺失，agent 拿到一句 `Error` 后盲目重试或直接放弃；
- 密钥管理混乱，调试日志里能看到明文 key；
- 写操作没有幂等和确认机制，agent 一重试就重复下单。

## 做法

**1. 先选路线。** 目标服务已有现成 MCP server，直接接，省掉重复封装；没有的话再评估工作量：简单 REST 接口用一个薄 HTTP tool 封装即可；鉴权复杂、需要会话状态的（比如 OAuth token 刷新），建议写成独立 MCP server，把 token 生命周期收在里面，agent 不感知。

**2. 定工具契约。** 每个工具固定四要素：做什么（一句面向模型的话，不是面向人的文档）、参数 schema（带类型和必填标记）、返回结构（只挑 agent 需要的字段）、错误语义。原则是一个工具一个动作，别把 50 个 endpoint 平铺给模型挑。

**3. 统一错误信封。** 所有工具返回统一结构：`{ok, error_code, message, retryable, hint}`。`retryable` 告诉 agent 能不能重试，`hint` 用一句话说明"下次该怎么传参"。这一条对我们调用成功率的提升最明显。

**4. 收口鉴权与超时。** 密钥只放在配置或环境变量里，在工具实现层注入请求头，绝不出现在 prompt 和参数里；每个调用强制 timeout（我们设 10s）；网络类错误指数退避重试 2 次；POST 类操作带幂等键。

**5. 用脚本验证，不靠手感。** 准备一组 fixture 用例：正常调用、参数缺失、服务端 500、触发限流，跑 agent 看它是否选对工具、传对参数、对错误做出合理反应。每次改工具描述都重跑一遍，防止"顺手改一句话"引发行为回退。

## 踩坑点

- **描述里的模糊措辞是隐形杀手。** "查询相关数据"这种描述会让模型乱猜；改成"按邮箱查客户工单列表，返回最近 20 条"后，误调率明显下降。
- **返回体要裁剪。** 大 JSON 先在工具层做字段筛选和截断，别指望模型自己忽略无关字段。
- **分页别指望 agent。** 要么在工具内聚合完再返回，要么在描述里明确写"最多返回 X 条，如何取更多"。
- **危险操作加确认。** 删除、支付类工具在 OpenClaw 里配置 human-in-the-loop，接入成本很低，省下的后悔药很贵。

## 可复用建议

- 维护一份团队级"工具契约模板"，四要素写死，新人照填；
- 本地起一个 mock server 做离线评测，把工具选择回归塞进 CI；
- 工具调用日志带 request id，排查"agent 到底干了什么"时不抓瞎；
- 工具数量超过 15 个左右就该做分组或路由，别考验模型的选择能力。

## 总结

对接外部服务的本质，是把一次 API 调用翻译成一份模型能稳定执行的契约。选 MCP 还是 HTTP tool 是次要的，工具描述、错误信封、鉴权收口、幂等与确认这四件事，才决定 agent 靠不靠谱。先把这些做扎实，再谈更花哨的编排。
