## 背景

社区每周要发一期「MCP 生态动态」：抓几个仓库的 release，整理成 Markdown，手动发帖。重复六周之后，我把它自动化了——一个跑在家用服务器上的 OpenClaw Agent，定时取数、总结、发帖。本文记录架构取舍和踩过的坑。

## 问题定义

先收敛需求，避免做成自动灌水机：

- 数据源固定：YAML 配置的仓库列表 + RSS
- 频率固定：每周一上午一期
- 有草稿模式：前四周内容先进待审队列，人工确认才发
- 幂等：任何环节崩溃重启，不能重复发帖
- 可观测：失败必须告警，不能静默失败

## 架构

五个模块 + SQLite 做状态存储，单进程，没上消息队列——规模不需要。

`scheduler (cron) → fetcher → summarizer (Agent) → publisher → state`

三个关键决策：

1. **状态机而非流水线**。每期内容有 `fetched → summarized → pending_review → published` 四态，每步都是「读状态、做事、写状态」，崩溃后从断点恢复。
2. **内容哈希做幂等键**。发布前用正文哈希查库，已存在则跳过。
3. **LLM 只做改写，不做检索**。原始 release notes 由 fetcher 抓好、结构化成 JSON 再喂给模型，prompt 明确要求只允许使用输入中的信息，禁止补充版本号、日期和功能描述。

## 步骤

1. 用 MCP 插件封装 GitHub Releases 抓取，输出统一 schema 的 JSON
2. Agent 以结构化输出（JSON Schema 校验）生成草稿，校验失败重试三次，仍失败降级为「原文链接列表」
3. 草稿写入 SQLite，状态 `pending_review`，同时推一张卡片到我的 IM
4. 人工确认后，到点调用社区发帖 API，指数退避 + 随机抖动
5. 成功后记录 post_id；失败进重试队列，超 5 次告警

## 踩坑实录

**坑 1：模型编造版本号。** 第一版让 Agent 自己调工具查 release，它会在抓取失败时「合理脑补」一个 v1.2.3。改成 fetcher 强制先抓、抓不到就显式标注「本周无更新」才解决。教训：别让模型同时负责取数和写作。

**坑 2：重复发帖。** 一次发布成功后进程被 OOM kill，状态没写库，下一轮又发了一遍。修复：先写带时间戳的 `publishing` 中间态，重启时发现该状态超 10 分钟，就主动调社区 API 查重。先查重再发布，是通用原则。

**坑 3：社区风控。** 连续两周固定时间发帖后，账号被限流一次。之后加了 ±15 分钟随机延迟，并补了社区对机器人的申报：帖子首行现在有明确的 bot 标识和人工负责人。自动化不等于匿名。

**坑 4：Markdown 方言。** 表格竖线、四空格缩进代码块在社区渲染器里都会翻车。最后限制 LLM 只能输出段落、列表、一级代码围栏三种元素，渲染问题归零。

**坑 5：cron 时区。** 服务器是 UTC，「每周一 09:00」实际在北京时间 17 点发。低级，但真实。

## 可复用建议

- 取数与生成分离，模型输入必须是结构化原始数据
- 一切发布类操作：先查重、写中间态、指数退避
- 草稿模式不是可选项，新 bot 至少人工审核运行一个月
- prompt 和数据源配置进 Git，变更可回溯
- 加心跳监控：任务没跑比跑失败更危险

## 总结

整套东西约 600 行 Python 加一个 MCP 插件，没引入重型组件。最大的收获不是省下的时间，而是把「自动发帖」当成一个有状态服务来设计之后，它才开始真正可信。现阶段我仍保留人工确认环节——在社区场景里，信任的建立速度远慢于它的崩塌速度。
