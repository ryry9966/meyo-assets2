## 背景

我维护一个两百人左右的技术社区，每周要整理 GitHub issue 精选和群内高赞讨论，发一篇「本周精选」。人工做一次约 2~3 小时，还容易漏。于是用 OpenClaw 搭了一个发帖机器人，稳定跑了一个多月，这里记录架构取舍和踩过的坑。

## 目标与硬约束

- 输入：GitHub 仓库动态、RSS、群聊摘录
- 输出：定时发布到社区固定板块
- 硬约束：发布前必须有人工审核；不允许重复发帖；失败可追溯

## 架构与步骤

整体是一条五段流水线，核心是 OpenClaw Agent，通过 MCP 接入各层工具：

1. **触发层**：cron 定时触发（每周一 09:00），保留手动触发入口。
2. **采集层**：两个 MCP tool，分别拉取 GitHub 动态和 RSS，原始数据带时间戳落盘为 JSON。
3. **草稿层**：Agent 读取落盘数据生成草稿。Prompt 明确「只允许引用采集数据中出现的链接与数字，缺失就写『本周无』」。
4. **审核层**：草稿写入 `drafts/` 目录并推送通知，人工用 `approve <id>` 放行，未审核草稿 48 小时后自动作废。
5. **发布层**：独立发帖 tool，带幂等键（内容 hash），发布结果写日志。

关键决策是**采集、生成、发布三层完全分离**，任何一层都可以独立重跑。

## 踩坑实录

**1. 重复发帖。** 第一版把状态放内存里，进程重启后记不清发没发过，同一天发了两篇。解法：状态外置到文件，发布前用「内容 hash + 目标日期」做幂等键查重。

**2. 模型编造链接。** 有次草稿里出现了采集数据中不存在的 issue 链接。解法：生成后增加校验步骤，提取草稿中所有 URL，逐一比对采集数据的 URL 集合，不一致直接打回重写——不要靠 prompt 祈祷。

**3. 时区问题。** cron 按 UTC 跑，帖子在凌晨发出。显式声明时区，并在日志里打印每次实际触发时间。

**4. 审核被绕过。** 早期发布 tool 挂在同一个 Agent 下，Agent 偶尔会「自作主张」直接调用。解法：发布 tool 要求显式的 approval token，该 token 只能由人工审核命令产生，Agent 自己无法生成。

**5. 上下文超限。** 群聊摘录一多，原始数据直接塞爆窗口。解法：采集层先做粗筛和分块摘要，草稿层只拿摘要加元数据。

## 可复用建议

- 任何会对外发声的自动化，必须有独立于 Agent 意图之外的人工闸门
- 状态务必外置，「幂等键 + 查重」是底线
- 对 LLM 输出做结构性校验（URL、数字、日期），而不是只依赖 prompt
- 先做 dry-run 模式：全链路跑通但最后一步只写日志不发布，观察一周再放开
- 失败时宁可跳过本期，也不要降级发出低质内容

## 总结

这个机器人本身技术含量不高，价值主要在流程设计：分层解耦、幂等发布、人工闸门、输出可校验。跑通后每周维护成本降到 10 分钟以内。下一步计划把审核命令也接进 MCP，实现移动端放行。如果你社区也有类似的重复性内容工作，建议从「采集—草稿—审核」这条最小链路做起，先别急着全自动。
