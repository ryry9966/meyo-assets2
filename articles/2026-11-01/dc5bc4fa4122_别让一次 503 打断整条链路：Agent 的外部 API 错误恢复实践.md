## 背景

Agent 跑起来之后，最不稳定的往往不是模型，而是它依赖的外部 API。一个典型的自动化任务要串起 LLM 推理、搜索、数据库写入、webhook 通知——任何一环抖一下，整条链路就断。MCP 工具和插件挂得越多，暴露面越大。

本地调试一切正常，上线后每天总有几次 429、超时、503。问题不是“会不会挂”，而是挂了之后 Agent 的行为是否可控。

## 问题

直接把错误抛给模型，有两类典型翻车：

1. **重试失控**。模型看到报错倾向于“再试一次”，没有退避、没有上限。遇到限流就是重试风暴，配额烧光，甚至触发封禁。
2. **幻觉式降级**。错误信息混进上下文后，有的模型会编一个“看起来合理”的结果继续走——搜索 API 挂了，它假装搜到了东西。这比直接失败更危险。

还有重复副作用：写操作失败重试，但没有幂等保护，结果消息发两遍、订单下两单。

## 做法

原则只有一条：**确定性的恢复逻辑放在代码/工具层，模型只拿干净的信号做判断。**

1. **统一调用 wrapper**：所有外部请求走同一封装。超时必设（连接和读取都设），指数退避重试（2s→4s→8s，加随机抖动），上限 3 次；遇到 429 优先读 `Retry-After` 响应头。
2. **区分可重试与不可重试**：429、5xx、网络超时可重试；400、401、403、404 重试没有意义，直接走失败路径。大量时间浪费在对 401 无脑重试上。
3. **设整体 deadline**：单次调用成功不等于任务能完成。给每个任务一个总时间预算，超时就落盘、暂停、转人工，不无限续命。
4. **工具层返回结构化错误**：MCP 工具别抛裸异常，返回类似：

```json
{ "ok": false, "retryable": false, "error_code": "AUTH_FAILED" }
```

模型拿到 `retryable: false`，就知道该放弃或降级，而不是瞎试。

5. **准备降级路径**：主搜索挂了切备用源；备用也挂，把任务标记 `pending` 写入队列，恢复后从断点续跑。关键写操作带 idempotency key，重试天然安全。
6. **上下文卫生**：不要把完整堆栈塞给模型，压缩成一行结构化错误。上下文里错误信息越多，幻觉式降级概率越高。

## 踩坑点

- **没有全局并发闸门**：多个 Agent 实例各自重试，叠加仍是风暴。限流要在服务层统一做，不是每个 Agent 自己数数。
- **只退避不熔断**：服务已经挂了，还在按节奏打。连续失败 N 次应熔断一段时间，直接走降级。
- **降级路径没演练过**：fallback 写了但从没触发，真出事时备用 key 过期、配额为零。建议定期手动断掉主路径做故障演练。
- **恢复后从零重跑**：长任务没 checkpoint，第 8 步挂了，恢复后从头来，前面的写操作全部重复。

## 可复用建议

- retry / backoff / timeout / 熔断做成团队统一的 client 封装，一处修改，所有 Agent 生效。
- 每次失败和重试都打日志（错误码、耗时、第几次），观测一周，你会发现 80% 的失败集中在一两个 API 上。
- 在系统提示里明确写一句：“工具返回 retryable=false 时不要重试，汇报并停止。” 一句话能省掉很多事故。

## 总结

外部 API 挂是常态，Agent 的可靠性不取决于“不失败”，而取决于失败后的行为是否可预期。核心三件事：**分类错误、有节制地重试、永远备好降级路径**。确定性逻辑交给代码，给模型一个干净的结构化信号——这条线划清楚了，Agent 才敢放到生产上跑。
