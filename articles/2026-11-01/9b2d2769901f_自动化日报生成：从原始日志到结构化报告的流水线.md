## 背景

我们团队有十来个常驻服务，此前日报基本靠人肉：登录机器翻日志、记错误数和部署情况、拼 Markdown 发群里。每天固定消耗 20–30 分钟，不同人值班时格式和颗粒度还不一致。后来用 OpenClaw 的定时任务加 MCP 工具把整条链路自动化了，本文记录流水线设计与踩坑，供有类似需求的伙伴参考。

## 问题

最初的想法很朴素：脚本抓日志，直接丢给 Agent 总结。跑了一周暴露三个问题：

1. **原始日志量太大**：每天约 40 万行，远超模型上下文，截断或漏报，关键事故经常被淹没。
2. **输出格式不稳定**：今天表格明天散文，下游没法稳定解析。
3. **不敢信**：没有校验环节，模型偶尔会“编”出一条看起来合理的部署记录。

结论：LLM 只适合做生成环节，上游要有确定性的预处理，下游要有确定性的校验。

## 做法：五段式流水线

1. **采集**：定时任务每小时增量拉取各服务日志，统一转成 JSONL，字段带明确的时区标记。解决“分散、格式不一”。
2. **预处理**：纯规则脚本，不经模型——按错误码聚合计数、算 P95 延迟、抽取部署与告警事件、脱敏 IP 和用户名，产出几百行以内的统计摘要。这是整条流水线最值得花时间的一段。
3. **生成**：Agent 的输入只有统计摘要 + 前一日日报，按预定义 JSON Schema 输出结构化日报；对可疑点，通过 MCP 工具按需回查原始日志片段，而不是预加载全部日志。
4. **校验**：独立脚本做 Schema 校验 + 硬性检查（错误量超阈值必须出现在日报、当天有部署则记录不得为空）。失败带着错误信息重试一次，再失败就降级——只发规则统计。
5. **分发**：渲染 Markdown 推送 IM 群，JSON 原件按日期归档备查。

## 踩坑点

- **别让模型碰原始日志**：哪怕 1/10 的量也容易超限，注意力还会被噪音稀释。规则聚合先行，模型只看摘要。
- **格式靠 Schema，不靠 Prompt 求告**：在 prompt 里写“请务必输出 JSON”，远不如 Schema 校验加重试可靠。
- **关键事件要有兜底**：漏报比多报严重，硬性检查项不要依赖模型的“自觉”。
- **时区问题悄无声息**：日志源与统计窗口时区不一致，日报会安静地漏掉半夜的错误。采集端统一打 UTC 标记，展示层再转本地。
- **脱敏放预处理，别指望生成端**：敏感信息一旦进入模型上下文，就收不回来了。

## 可复用建议

- 聚合规则、报告模板、校验清单三者做成独立配置，互不耦合，接新服务只改配置。
- 保留各层中间产物（原始日志、统计摘要、结构化 JSON），排查“日报为什么这么写”时可全链路回放。
- 先接一个服务跑稳两周再横向复制，不要一步到位接全部服务。
- 生成层设计成可替换：统计摘要足够好，换模型甚至不上模型，日报都能出。

## 总结

流水线上线后，人工介入只剩“看一眼再转发”，多数日子连这一步都省了。回顾下来，真正保证质量的是规则预处理和独立校验，模型只是把数据变成可读叙述的一环。做日报自动化的朋友，建议把精力优先投在管道两端，而不是中间最显眼的生成环节。
