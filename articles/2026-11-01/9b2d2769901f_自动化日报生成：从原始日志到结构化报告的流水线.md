## 背景

我们团队每天要发一封日报：昨天跑了哪些任务、哪些失败、核心指标变化如何。数据源散在 cron 输出、CI 记录、服务日志和几个 Agent 的运行痕迹里。此前靠人肉汇总，每天 30–40 分钟，还经常漏掉非工作时间的异常。

## 问题

拆开看是三个痛点：

1. **格式不统一**：各来源日志结构各异，没有可比性；
2. **噪音大**：重复告警和调试输出淹没真正需要关注的错误；
3. **结构漂移**：人写的日报每天侧重不同，无法做纵向趋势对比。

## 做法

核心思路一句话：**把模型放在摘要层，而不是采集层**。流水线分四段：

1. **采集**：OpenClaw 定时任务在 23:50 触发，脚本拉取各来源日志落盘到本地目录。
2. **归一化**：确定性脚本把日志压成统一 JSON：`{source, timestamp, level, event, metrics}`。同类错误只保留计数加首尾样本，超长字段截断。
3. **摘要**：写了一个轻量 MCP server，只暴露 `fetch_digest` 和 `send_report` 两个工具，Agent 负责读摘要、按模板产出严格 JSON（带 schema 校验），失败自动重试一次，仍失败就降级为原始摘要加人工标记。
4. **渲染投递**：校验通过后渲染成固定 Markdown 模板，webhook 推群，同时落盘归档一份。

## 踩坑点

- **别让模型直接读原始日志**。第一版偷懒把日志整段塞进去，token 爆了，关键错误还被漏掉。归一化和压缩是前提，不是优化项。
- **时区问题**。日志是 UTC，日报按本地日期切窗口，上线首晚统计全是空的——窗口差了一天。采集脚本里统一转本地时区。
- **流水线自己也会挂**。最隐蔽的坑是日报任务静默失败：没收到日报比收到错的日报更糟。加了心跳检查，超过 00:10 未投递就单独告警。
- **模板要冻结**。输出 schema 频繁改动会让历史日报失去可比性。v1 定稿后只加字段、不删字段、不改含义。

## 可复用建议

1. **中间格式先行**：先定 JSON schema，再写采集脚本，最后才接模型，顺序不能反。
2. **职责切干净**：模型只做摘要和归因，数据搬运全部交给确定性脚本。
3. **归档中间产物**：归一化 JSON 保留 30 天，后续做周报、月报可以直接再聚合，不用重跑采集。
4. **支持 dry-run**：改模板先在本地看渲染结果，再切到线上投递。
5. **MCP 工具设计得足够"笨"**：一个只读摘要，一个只发报告。Agent 的编排逻辑越薄，系统越稳。

## 总结

流水线上线后，日报耗时从 30 分钟降到接近零，结构统一之后终于能做周级别的趋势对比。回头看，自动化日报的价值不在"让 AI 写字"，而在先把数据变成可比的结构——模型只负责最后一公里的归纳。这套四段式结构（采集 → 归一化 → 摘要 → 投递）不依赖特定工具栈，换成你们现有的调度和推送渠道同样成立。
