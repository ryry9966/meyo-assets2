## 背景

我们团队每天要发一份日报，内容覆盖服务异常、发布变更、关键指标和待办事项。过去靠人工翻日志、翻 git 记录、翻群消息，每天花 20-30 分钟，还经常漏项。最近我用 OpenClaw 搭了一条流水线，把这件事压到每天早上自动完成，人工只做最后确认。本文记录做法和踩坑。

## 问题

直接让 Agent"读日志写日报"有三个明显问题：

1. 原始日志量大且噪，仅网关日志一天就几十万行，直接喂给模型既贵又容易截断；
2. 模型擅长组织语言，不擅长算数，让它自己统计错误率，数字经常对不上；
3. 流水线本身也会挂，挂了没人知道，比没有日报更糟。

所以核心思路是：**数字让脚本算，叙事让模型写，投递前再让脚本校验。**

## 做法

整体分四层：

**1. 采集层（定时任务 + 脚本）**
用 OpenClaw 的定时任务每天 06:30 触发一个脚本，拉取三类数据源：git log（昨日 commit）、CI 结果、错误日志 topN。统一输出为 JSON Lines，每行带 `source / timestamp / payload`。

**2. 预聚合层**
脚本先算好结构化指标：错误率、P95 延迟、变更条数、失败任务列表，输出一份"摘要包"（通常 2-3KB）。模型只看摘要包，不看原始日志。

**3. Agent 层**
OpenClaw Agent 收到摘要包后，按固定 JSON schema 产出报告字段：`incident / change / metric / risk / todo`。prompt 里明确两条约束：所有数字必须原样引用摘要包，不得自行计算；不确定的字段填 `unknown` 而不是编造。需要细节时通过 MCP 工具回查原始日志，查完再写。

**4. 渲染与投递层**
脚本把 schema 渲染成 Markdown 模板，做两项校验：报告中出现的所有数字必须能在摘要包里找到；必填字段不得为空。通过后推送群 webhook，并归档到 git 仓库留档。校验失败则降级发送"原始摘要 + 失败原因"，保证每天有产出。

## 踩坑点

- **时区混乱**：日志里 UTC 和本地时间混着，第一版日报总"少昨天最后两小时"。统一在采集层转成带时区的 ISO 8601 才解决。
- **模型改数字**：即使 prompt 明令禁止，模型偶尔还是会"顺手四舍五入"。加数字校验后这类问题被拦在投递前。
- **重试导致重复推送**：webhook 超时触发重试，群里收到三份日报。给每次运行生成 `run_id`，投递前查重。
- **流水线静默失败**：脚本挂掉时群反而安静。补了一条心跳消息，连续两个周期没收到即告警。

## 可复用建议

1. 阶段之间用固定 JSON schema 做契约，换模型或改 prompt 不影响上下游；
2. 先接一个数据源跑通闭环，再横向加源，不要一上来铺四个；
3. 每次运行的输入摘要包和输出报告都归档，出问题能回放定位；
4. prompt 模板进 git 做版本管理，改模板和改代码一样走 review。

## 总结

这条流水线上线一个月，日报从"每天人工 20 分钟"变成"自动生成 + 人工 1 分钟确认"。关键不在模型多强，而在于把算数、校验、投递这些确定性环节交还给脚本，模型只做它擅长的归纳与表达。Agent 自动化项目的可靠性，往往取决于你愿意把多少逻辑从 prompt 里挪出去。
