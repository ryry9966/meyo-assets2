## 背景

团队每天要发一封日报，内容包括：昨日代码提交、CI 失败情况、线上错误 Top 项、工单进展。过去靠人工在几个系统之间来回切换，复制粘贴再改写，费时且容易漏。这篇记录我们用 OpenClaw 搭的自动化日报流水线，思路可以迁移到任何「原始数据 → 结构化报告」的场景。

## 问题

三个核心痛点：

1. **数据源分散**：git、CI、错误日志、工单系统各在一处，格式各异；
2. **直接把原始日志丢给 Agent 总结效果很差**：上下文超限、数字编造、重复内容；
3. **静默失败**：定时任务挂了没人知道，日报看起来正常，内容其实是旧的。

## 做法

流水线分四步，Agent 只参与中间两步：

### 1. 采集（纯脚本，无 LLM）
cron 每天 7:00 触发脚本，拉取 git log（昨日时间窗）、CI 结果 API、错误日志、工单状态变更。关键在**脚本侧先聚合**：错误日志按指纹（去掉变量后的 message）分组计数，只把聚合计数结果交给模型，不喂原始行。

### 2. 结构化（LLM）
把聚合后的 JSON 喂给 Agent，要求输出固定 schema 的 JSON：每个条目必须带 `source` 和 `count` 字段；prompt 中明确「某字段数据为空就写'无'，不要推测」。

### 3. 渲染（模板）
用 Jinja2 模板把 JSON 渲染成 Markdown 日报。样式调整只改模板，不碰流水线。

### 4. 校验 + 分发
发送前做一次**机械校验**：日报中的数字与采集 JSON 逐一比对，不一致就重试或降级发送纯统计版，最后推到 IM webhook。

## 踩坑点

- **时区**：第一版用 UTC 计算昨日窗口，漏掉了晚 8 点后的提交。改为显式用本地时区生成时间窗，并在脚本里打印起止时间便于核对。
- **解释性幻觉**：即使给了结构化数据，模型偶尔会给计数「合理化」，编造错误原因。加了一条硬规则：解释性文字只能来自输入 JSON 的 `note` 字段，否则整句删除。
- **幂等**：手动重跑导致发了两封日报。加了当日锁文件，同一天第二次运行只覆盖草稿、不发送。
- **上下文膨胀**：某天 CI 大量重试，聚合 JSON 超长。给采集层加了每类条数上限，超限合并为「其他 N 条」。

## 可复用建议

1. **采集与摘要严格分离**，LLM 只看聚合摘要，永远不接触原始日志——这一条解决了八成的幻觉和成本问题；
2. **固定中间 schema**，采集输出和摘要输出都是带版本号的 JSON，任何一步都可单独测试、回放；
3. **保留降级路径**，LLM 步骤失败时发一封纯数字版日报，比不发强；
4. **staleness 自检**，日报末尾由脚本附上「数据窗口：X 至 Y」，收件人一眼能看出数据是否新鲜；
5. 校验交给确定性代码做，不要让模型自己检查自己。

## 总结

这套流水线跑了一个多月，日报从每天 20 分钟人工降到 0，数字准确率反而比人工复制粘贴更高（因为有机械校验兜底）。核心经验一句话：**让 Agent 做它擅长的语言组织，把数据准确性交给确定性代码**。整条流水线没有任何一步依赖模型的「聪明」，这正是它稳定的原因。
