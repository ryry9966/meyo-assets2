## 背景

跑过一段时间 Agent 自动化的人都有体会：任务链里真正容易出事的不是模型，而是外部依赖。LLM API 限流、MCP 工具背后的第三方服务 502、搜索接口超时、Webhook 对端失联——任何一环抖动，整条流程就可能中断。

Agent 场景比传统后端更麻烦的地方在于：**出错之后的决策权在模型手里**。错误信息处理得不好，轻则模型反复重试浪费 token，重则它编造一个"看起来成功"的结果继续往下跑，等我们发现时脏数据已经写进去了。

## 问题：三类典型故障

实践中最常撞上的是这三类：

1. **瞬时故障**：429 限流、502/503、网络抖动。占日常故障的大多数，重试通常能解决。
2. **持续性故障**：上游宕机、密钥失效、配额用尽。重试无意义，需要降级或切换。
3. **半成功状态**：请求超时，但服务端实际已执行。对写操作（发消息、建工单、下单）最危险，盲目重试等于重复执行。

## 做法：四层恢复策略

**第一层：错误分类。** 在工具/MCP 封装层把错误归一化成结构化结果，至少区分 `retryable` / `fatal` / `unknown`，附上状态码和一句话原因。不要把裸异常堆栈直接丢给模型。

**第二层：带退避的重试。** 指数退避加随机抖动，重试 2~3 次，并用**总时间预算**（比如 30 秒）兜底，而不是只看次数。429 场景优先读响应头里的 `Retry-After`。

**第三层：降级与兜底。** 关键工具准备 Plan B：备用 API、缓存的历史结果、或"跳过该步骤并明确标记"。核心是让 Agent 知道自己在降级模式运行，而不是假装一切正常。

**第四层：断点续跑。** 长任务每步落盘（状态、已完成步骤、中间产物），失败后从断点恢复，而不是从头再来。

## 踩坑点

- **重试风暴**：任务链里多个节点同时对同一个挂掉的 API 重试，会把限流变成雪崩。重试逻辑放在封装层统一管，别让模型自己决定"再试一次"。
- **写操作没有幂等键**：超时后重试导致重复发消息。所有对外写操作必须带幂等键，靠服务端去重。
- **错误信息不结构化**：模型收到一段报错文本就开始脑补，把失败当成部分成功。错误要短、可判定。
- **无限重试**：没有时间预算的重试循环会烧光 token 还卡死整个任务队列。
- **降级不告知**：静默用缓存数据完成任务，下游拿到过期数据毫不知情。降级结果要显式标注。

## 可复用建议

- 所有工具调用统一走一个带超时、重试、熔断的 wrapper，错误输出固定 schema。
- 对外写操作一律幂等键 + 本地记录"已提交"状态，重试前先查。
- 加熔断器：连续 N 次失败直接短路走降级，冷却期后再探测恢复。
- 系统提示里写明："工具返回失败时，禁止编造结果，必须如实上报并等待决策。"这句话实测能挡掉大部分幻觉式"成功"。
- 关键任务每步存 checkpoint，恢复成本远小于重跑。

## 总结

外部 API 挂掉不是异常，是常态。Agent 的健壮性不取决于模型多聪明，而取决于错误被呈现得多清晰、恢复机制被设计得多机械可靠。把重试、降级、幂等、断点这些"无聊"的工程活做扎实，自动化流程才经得起生产环境的折腾。欢迎在评论区交流你们的降级方案。
