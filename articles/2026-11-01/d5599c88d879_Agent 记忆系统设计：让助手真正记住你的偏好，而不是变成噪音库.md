## 背景

LLM 本身是无状态的，上下文窗口再大，也只是"本次会话内的临时记忆"。做 Agent 和自动化时，用户最常提的诉求往往不是"更聪明"，而是"别让我每次重新交代一遍"。MCP 让挂一个记忆工具变得很容易，但大多数实现跑两周就退化成噪音库——记了一堆没用的，真正要用的反而想不起来。

## 问题

三种常见做法都会失败：

- **全量塞进 system prompt**：token 成本线性上涨，大量无关记忆还会稀释模型注意力；
- **对历史会话做 RAG**：召回的是原始对话碎片，噪声大，质量完全依赖 embedding；
- **会话结束让模型写总结**：有损压缩，多轮迭代后信息漂移，越总结越离谱。

核心矛盾不在存储，而在三个没设计好的策略：写什么、怎么读、何时过期。

## 做法

按下面的分层和策略起步，够用很久：

**1. 记忆分三类。** 偏好（结构化、低频变：语言、代码风格、时区、常用工作流）、事件（项目背景、进行中的任务）、会话内工作记忆（不落盘）。只有前两类进存储。

**2. 写入从严。** 只记两类内容：显式声明（"以后统一用 pnpm"）和重复出现的模式（同一倾向出现 ≥2 次才写入）。记忆工具内部加一道 write gate，先做相关性分类，琐碎内容直接丢弃。

**3. 存储从简。** 别一上来就上向量库。一个 SQLite 或 JSON 文件，命名空间按用户/项目隔离，每条记忆至少六个字段：`content`、`type`、`source`（explicit/implicit）、`confidence`、`created_at`、`last_used_at`。这几个字段是后面所有策略的原材料。

**4. 读取从俭。** 稳定偏好固定注入 system prompt，总量卡在 300–500 token；事件记忆按需检索，查询相关才召回。落地方式最省事的是做成一个独立的 MCP server，对外收敛到三个工具：`remember` / `recall` / `forget`，外加一个 `list` 供用户审计。

**5. 更新与遗忘。** 新旧记忆冲突时做 supersede（覆盖而非追加）；implicit 记忆带 TTL，比如 30 天未被使用自动降权；低置信度记忆在使用前先向用户确认。

## 踩坑记录

- **记忆污染**：没有写入门槛，Agent 连"用户今天问了天气"都存，一周后召回全是垃圾；
- **只追加不覆盖**：用户从 pip 迁到 uv，旧偏好还在，Agent 每次都给过时建议。冲突检测必须做在写入端；
- **注入过量**：偏好塞到 2000 token 后，模型行为反而变保守，开始复读记忆。上限要卡死；
- **偏好过期但用户没说**：靠 TTL 加定期确认兜底，让 Agent 在合适时机问一句"还按之前的习惯来吗"；
- **隐私**：记忆库是最敏感的数据。本地优先、明文可导出、一条命令可清空，别默认上云；
- **无法回归**：记忆让行为不确定。留一组固定的回放用例，每次改记忆策略跑一遍对比输出。

## 可复用建议

1. 从"结构化 profile + 自由笔记"起步，向量检索是后置优化，不是起点；
2. 每条记忆必带时间戳和来源，缺了这两项，过期和冲突策略都无从谈起；
3. 宁可少记，不要错记——错误记忆比没有记忆伤害更大；
4. 让用户能看到、能编辑每条记忆，透明度比聪明更重要；
5. schema 第一天就版本化，后期迁移会感谢你。

## 总结

记忆系统的难点不在模型，在工程：写入门槛、读取配额、过期机制，缺一个就会劣化成噪音库。先用最朴素的存储跑通"写-读-更新-遗忘"的闭环，再根据真实使用数据决定要不要引入更复杂的检索。让助手记住你之前，先管好它的记性。
