## 背景

OpenClaw 的 Cron 任务让 agent 可以在无人值守时按计划干活：晨报、监控告警、RSS 摘要、定期巡检。但社区里大量"定时任务不好用"的案例，根因往往不在调度配置，而在 instruction 本身——很多人用写聊天 prompt 的方式去写定时任务，agent 醒来时其实是一脸茫然的。

## 问题：Cron instruction 和普通对话 prompt 是两回事

三个本质区别：

1. **无上下文**。每次触发都是全新会话，上一轮聊过什么、昨天报告写了什么，agent 拿不到——除非你在指令里显式让它读文件。
2. **无澄清机会**。没人在旁边回答追问，指令必须一次写清，含糊的地方它会自己脑补。
3. **结果直接进通知渠道**。写糊了的代价不是"回答一般"，而是每天推送 800 字废话，或者同一条告警连报三天，直到你把这个任务关掉。

## 做法：一份稳定的 instruction 长这样

1. **自包含上下文**：开头交代"你是谁、这次触发干什么"。时间别写"今天早上"，写成"以系统当前时间为准的过去 24 小时"。
2. **工具与数据来源**：明确用哪个 MCP/插件取数，主路径失败降级到什么。写"自己想办法"在无人值守场景下等于失控。
3. **跳过条件（最重要）**：显式写出"什么情况下不发消息"。没有跳过条件，agent 会为了"完成工作"硬凑产出。
4. **固定输出模板**：限条数、限字段、限长度。输出越结构化，越适合进推送渠道，也方便后续脚本归档。
5. **状态与去重**：让任务把"上次已处理的 ID / 水位"写进固定文件，本次先读再比对。Cron 本身不提供记忆，记忆要自己搭。
6. **失败降级与预算**：写明失败几次后发送失败摘要并结束，同时给工具调用次数设上限，防止单次任务烧掉大量 token。

可以直接套用的骨架：

```text
你正在执行定时任务 [任务名]，以系统当前时间为准。

目标：检查 <数据源>，筛选 <时间窗口> 内满足 <条件> 的条目。
工具：优先用 <A>；失败时改用 <B>；均失败走失败路径。
跳过条件：若无符合条目，直接结束本次任务，不发送任何消息。
去重：读取 <路径>/last_state.json，跳过已出现的 ID，结束后更新该文件。
输出：最多 5 条，每条含 [标题/链接/一句话摘要]，总长不超过 300 字。
失败路径：连续失败 2 次后，发送一条失败说明并结束。
预算：工具调用不超过 10 次。
```

## 踩坑点

- 用对话语气写指令（"帮我看看最近有什么好玩的"），agent 会自由发挥，产出不可控。
- 相对时间歧义："昨天"指自然日还是过去 24 小时？跨时区更乱，一律用相对当前时间的时间窗口。
- 漏写跳过条件 → 每天固定收到一条"今天没有值得汇报的内容"，一周后你会直接屏蔽这个任务。
- 把去重寄托在"agent 应该记得发过"上——它不记得。
- 高频任务（如每 5 分钟）配长 instruction，token 成本和噪声同步上涨，先想清楚频率是否必要。

## 可复用建议

- 新任务先手动触发跑 2~3 次 dry run，观察真实输出，再上调度。
- 写完自检一遍：没人盯着时，指令里的每一步是否有唯一解？每多一句模糊表述，就多一个未来的排障点。
- 所有 cron 输出落一份日志文件，出问题时比翻聊天记录快得多。

## 总结

Cron instruction 的本质是一份无人值守的岗位说明书：目标、工具、跳过条件、输出格式、失败路径，缺一不可。写的时候别把 agent 当成"记得住事"的老同事，把它当成每天入职一次、手里只有一页说明书的实习生——任务就稳了。
