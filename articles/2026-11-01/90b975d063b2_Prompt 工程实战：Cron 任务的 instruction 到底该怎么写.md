## 背景

OpenClaw 的 cron 本质上是：到点唤醒 agent，在一个独立会话里执行一条 instruction，产出投递到指定 channel。很多朋友把这条 instruction 当成平时聊天里的一句话来写——"帮我总结一下今天的邮件"——结果要么跑题，要么编数据，要么输出长得没法看。

核心原因一句话：**cron 触发时没有对话上下文**。日常聊天里 agent 能靠历史消息补全你的意图，而 cron 任务是一次性、无状态的，这条 instruction 就是它拥有的全部信息。所以它不是"消息"，而是一份独立的工单。

## 问题

我第一批 cron 任务几乎踩全了典型失败：

- 输出漫无目的："总结"没有来源、没有格式、没有长度约束；
- 数据源挂了，agent 用训练记忆"善意补全"，产出看起来像真的；
- 时间语义错位："今天"按 UTC 算，凌晨跑的日报少了一整天数据；
- 消息投到错误的会话，或超长被 IM 截断。

## 做法：五段式模板

现在每条 cron instruction 我都按五段写，稳定性明显提升：

1. **目标**：一句话说清产出什么。"每晚 22:30 生成仓库今日动态摘要"。
2. **数据来源**：写死工具和路径，用哪个 API、读哪个文件，杜绝"你自己找"。
3. **步骤**：3~5 步有序清单，agent 会更稳定地按流程执行。
4. **输出格式**：结构 + 长度上限。"Markdown 列表，最多 5 条，全文不超过 200 字"，比"简洁一点"有效得多。
5. **异常处理**：显式写兜底。"数据源请求失败时，只回复'数据获取失败：<原因>'，禁止用旧数据或推测填充"。

另外把时间语义写死：时区、"今天"的起止边界都放进 instruction，不依赖 agent 猜。

## 踩坑点

- **相对时间歧义**：跨零点任务里"昨天/今天"最容易翻车，永远显式给时区和边界。
- **默认有上下文**："继续上次的""还是那个仓库"在 cron 里无解，每次都要写全。
- **静默编造**：最危险的失败模式，因为产出"看起来是对的"。禁止编造必须作为默认条款。
- **输出超长**：Telegram / 飞书都有消息长度限制，上限要写进 instruction。
- **任务堆积**：长任务配短间隔，上一轮没跑完下一轮又触发。要么拉长间隔，要么在 instruction 里加"若上一轮未完成则跳过"的约束。

## 可复用建议

- **建模板库**：日报、监控、提醒这类任务，各沉淀一条验证过的模板，改参数复用，不要每次重写。
- **先手动跑再挂 cron**：把 instruction 直接发给 agent 验证输出，符合预期后再定时。
- **回看投递记录**：跑一周后复盘实际消息，用真实失败案例反哺 instruction，这是迭代最快的路径。
- **兜底条款默认带**："失败要报告，禁止编造"写进每一条任务。

## 总结

写 cron instruction，本质上是在给一个没有记忆但执行力很强的实习生下一次性工单：目标、来源、步骤、格式、兜底，缺一不可。经验之谈：异常路径写清楚了，正常路径往往也就顺了。
