## 背景

用 OpenClaw 跑自动化时，主会话既是聊天入口，也是编排层。任务简单时所有工具调用都在主循环里跑，没什么问题。一旦任务变复杂——批量抓网页、读大文件、跑长流程——把活儿拆给子 agent（`sessions_spawn`）之后，新问题出现了：**子 agent 跑完，主会话反而被搞脏了**。

## 问题的具体表现

1. 子 agent 的长工具输出以"结果"形式整段塞回主会话，很快触发 compaction，早前的上下文被压掉，主会话开始"失忆"。
2. 子 agent 和主会话共享同一个 workspace，写文件互相覆盖，主流程读到了中间态。
3. 一次性子会话没清理，sessions 目录只增不减，重启后还占着。
4. 排障时分不清哪条记录属于哪个 session，日志对不上。

## 做法

核心思路一句话：**主会话只做编排和验收，子 agent 只带回摘要，不带回过程。**

第一步，spawn 时显式声明隔离面，别依赖默认值：

```jsonc
{
  "task": "抓取并总结这 20 个页面的变更点",
  "session": "isolated",      // 新会话，不继承主会话历史
  "workspace": "./runs/2024-06-scrape", // 独立工作目录
  "duration": "oneshot"       // 跑完即收
}
```

第二步，给子 agent 一个**契约式返回**：大产物写文件，最终返回只包含三段——结论、产物路径、风险与未决项，并对返回长度给硬约束（比如 200 字以内）。

第三步，验证隔离确实生效：用 `sessions_list`（或 `/status`）确认子会话独立存在；跑完后检查主会话 transcript 的增量，应该只有那条摘要，没有过程记录。

第四步，收尾。one-shot 会话自动结束；确实需要常驻的子会话，设个定期清理。

## 踩坑点

- **spawn 时带上了主会话历史**，等于没隔离。子 agent 会把主会话上下文重新展开一遍，污染来得更快。确认是"新会话 + 只注入任务描述"。
- **摘要不够"小"**。500 字的摘要 × 10 个子任务，照样爆上下文。返回预算要当作参数来管。
- **上下文隔离 ≠ 文件系统隔离**，反过来也一样。两个是独立的开关，都要显式设置，别以为开了沙箱上下文就干净了。
- **工具集漂移**：子 agent 没带上线主会话在用的某个 MCP server，任务跑到一半失败，失败详情又整段写回主会话。spawn 前核对子会话实际加载的工具。
- sessions 目录没有自清理机制，膨胀是静默发生的，等你发现时已经几个 GB。

## 可复用建议

- 把 spawn 配置沉淀成模板片段，隔离参数写死在模板里，团队成员复制即用，不靠口头约定。
- 子 agent 的 prompt 开头固定一句："你运行在独立会话中，主会话看不到你的执行过程，只有最终返回会被带回。"实测能显著减少子 agent 往返回里塞过程的倾向。
- 给 session 和任务定命名规范（日期 + 任务类型 + 序号），排障时日志能对上。
- 把"审计 sessions 目录大小"加进日常维护，和清理临时文件同等对待。

## 总结

OpenClaw 的 session 隔离不是一个开关，而是三层的事：**上下文层**（新会话、不继承历史）、**文件系统层**（独立 workspace 或沙箱）、**生命周期层**（one-shot 或显式回收）。默认值不等于安全，全部显式声明，再用契约式返回管住"带回来的东西"，主会话才能长期保持干净、稳定跑长任务。这套做法同样适用于任何有编排关系的多 agent 场景。
