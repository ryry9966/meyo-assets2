## 背景

团队日常沟通里，日报是高频但低价值的劳动：每天从 git、CI、issue 系统、agent 会话日志里翻数据，拼成一段话发到群里。这件事适合交给自动化——难点不在于"生成一段话"，而在于把散落的原始日志变成模型可以可靠消费的结构化输入。本文记录我们用 OpenClaw + MCP 搭的一条日报流水线，稳定运行约两个月后，人工介入基本归零。

## 问题

直接让 agent "读一下今天的日志，写个日报"，会遇到三个硬问题：

1. 原始日志量大且噪，上下文塞不下；塞下了也容易被无关信息带偏；
2. 模型擅长叙述、不擅长计数，让它自己统计 commit 数、失败率，数字经常错；
3. 输出格式不稳定，下游（群机器人、邮件）没法消费。

## 做法

核心思路：把流水线拆成**采集—聚合—叙述—分发**四段，LLM 只做第三段。

**第一步，采集。** 用三个 MCP tool 分别拉数据源：git log（按时间窗）、CI 运行记录、agent 会话摘要。每个 tool 只做一件事，返回原始 JSON。

**第二步，聚合。** 这一步纯脚本，不经过模型：按仓库聚合 commit、按状态归类 CI 失败、抽取高频变更关键词。输出一份固定的中间 JSON schema，例如 `{ commits, ci_failures, highlights }`。这份 schema 就是整条流水线的契约。

**第三步，叙述。** agent 只拿聚合后的 JSON 和一段固定 prompt，任务被约束为"把结构化数据转写成人话"，并被明确禁止编造 schema 之外的事实。输出用 JSON Schema 校验，失败自动重试一次；仍失败则降级为纯数据模板，不经过模型。

**第四步，分发。** cron 触发 OpenClaw 任务，产物同时推群和归档到对象存储。失败时单独发一条告警，和日报本身分开。

## 踩坑点

- **让模型自己数数必翻车。** 有一次日报里 commit 数凭空多了 40%，原因是把原始 git log 直接丢给了模型。改为脚本预聚合后未再复现。
- **时区。** cron 跑在 UTC，日志按本地时间过滤，第一周日报内容整体错位一天。所有时间窗在采集层统一转 UTC，只在渲染层转本地。
- **重试导致重复推送。** 任务超时重跑会再发一份日报，下游群被刷屏。加了幂等键（日期 + 版本号），同键不重发。
- **schema 漂移。** 上游 CI 系统升级后字段改名，聚合脚本静默产出空数组，日报连续三天"无异常"。教训：聚合结果为空时应当告警而不是照常生成——"太干净"本身就是异常信号。

## 可复用建议

- 数据和叙述分离，LLM 永远不接触原始日志，只消费聚合结果；
- 中间 JSON schema 进版本库当接口维护，改动走 review；
- prompt 与代码同仓库管理，改措辞和改逻辑一样要有 diff 记录；
- 保留一条绕过模型的降级路径，模型故障时日报不能断；
- 上线先跑 dry-run，产物只写文件不发群，人工比对一周再放开。

## 总结

这条流水线的价值不在"省了写日报的十分钟"，而在于把日报从主观叙述变成了可验证的数据产物：数字可追溯、格式可校验、故障可降级。LLM 在其中只承担它真正擅长的转写工作，其余交给确定性脚本。经验上，任何"从一堆原始数据到一段固定格式输出"的场景，都可以套用这个四段式结构。
