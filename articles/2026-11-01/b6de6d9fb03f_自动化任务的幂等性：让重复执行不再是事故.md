## 背景

跑 OpenClaw 自动化一段时间后，你会遇到一类很典型的现象：同一个任务明明只配置了一次，结果却执行了两次。常见来源有三个：

- **重试**：agent 调用 MCP 工具超时，框架或模型层发起重试，但上一次其实已经成功；
- **重复触发**：webhook 对方没在超时窗口内收到 200，按约定重推；
- **重叠执行**：cron 周期比任务耗时短，上一轮没跑完，下一轮又启动了。

这些都不是 bug，是分布式环境的常态。所以真正的问题是：**你的任务被重复执行时，结果是否依然正确**。这就是幂等性——同一操作执行一次和执行多次，对外效果相同。

## 问题：哪些操作天然不幂等

| 操作 | 重复执行的后果 |
|---|---|
| 向群里发一条通知 | 用户收到两条重复消息 |
| INSERT 一条记录 | 数据库出现重复行 |
| 向文件追加一行 | 内容翻倍 |
| 调用创建类 API | 生成两个订单/工单 |

而覆盖写文件、设置状态值、按 key 的 upsert，天然幂等，重复跑没有副作用。写任务前先做这个分类，大部分工作量就省了。

## 做法：三个层次

**1. 幂等键 + 状态记录（最常用）**

给每次“业务上只该发生一次的执行”一个**确定性**的键，比如 `digest-20250607`（任务名+日期，而不是随机 UUID）。执行前查状态存储（SQLite 一张表、Redis、甚至一个 JSON 文件都行）：

```text
key = "digest-" + today
if state.exists(key): return "already done"
do_work()
state.mark_done(key)
```

键里要带业务语义：按“当天”去重的日报任务，补跑昨天和今天的应该互不冲突。

**2. 写操作本身幂等化**

能 upsert 就不要 insert；能覆盖写就不要追加写；写文件用“临时文件 + 原子 rename"。外部 API 如果支持幂等键（不少创建类 API 都有），重试时带上同一个 key，服务端会返回同一个结果。

**3. 工具层兜底**

给 agent 用的 MCP 工具要记住：超时不等于失败，可能已经成功。创建类工具内部应支持调用方传入 token，或者自己按业务键去重，不要指望上层永远不重试。

## 踩坑点

- **幂等键用随机 UUID**：每次重试都是新键，等于没做。键必须由业务输入决定。
- **状态只存内存**：进程一重启，去重记录就丢了。
- **check-then-act 竞态**：“先查有没有，没有就执行”两步之间可能插入另一个实例。用唯一约束、原子 SETNX 兜底，前置检查只是优化。
- **过度去重**：把合法的第二次执行也吞了。比如“每天一次的清理”，手动补跑被判为重复。去重粒度要跟业务走，别只看任务名。
- **cron 重叠**：幂等解决“结果正确”，不解决“资源浪费”。长任务加锁或用 flock，让重叠轮次直接跳过。

## 可复用建议

1. 每个自动化任务写一行注释说明幂等策略：“按 日期 去重，状态存 SQLite"，排障时省半小时。
2. 把“幂等键 + 状态检查 + 标记完成”封装成一个 run-once helper，所有定时任务复用，别每个脚本各写一套。
3. 日志里始终打印幂等键，出现重复执行时能一眼对上是哪一次。
4. 上线前做个廉价演练：连触发两次、断网重试一次、重启进程再跑一次，看结果是否一致。

## 总结

幂等不是出事之后再补的补丁，而是写自动化任务时默认要回答的问题：**这个操作跑两次会怎样？** 大部分场景，一个确定性幂等键加一个落盘的状态记录就能解决；剩下的交给 upsert、原子写和工具层兜底。当重复执行从“事故”变成“无所谓”，你的自动化才真正敢交给 cron 和 agent 去跑。
