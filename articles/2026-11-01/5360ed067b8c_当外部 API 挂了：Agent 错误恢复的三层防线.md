# 背景

Agent 链路越长，外部依赖越多。一次典型的 OpenClaw 任务里，可能同时调用搜索、数据库、第三方业务 API 和若干 MCP 工具。任何一环抖动——限流、超时、5xx——都会把错误抛进 Agent 的上下文。处理不好，轻则任务中断，重则模型在报错信息旁边"脑补"一份结果继续往下跑，这是比失败更糟的结局。

# 问题

实践中最常见的三类故障模式：

1. **不分类地重试**。401、404 和 503、timeout 在 Agent 眼里都是"工具报错了"，无差别重试只会烧 quota；对 429 硬重试还会加重对端压力，形成重试风暴。
2. **失败后编造结果**。原始错误字符串被塞进上下文，模型倾向于给出"看起来合理"的补偿性回答，用户拿到的是假数据。
3. **一个挂全停**。链路上某个非关键 API 挂掉，整个 pipeline 跟着失败，缺少降级路径。

# 做法

核心是三层：调用层、Agent 层、策略层。

**第一层：统一的调用封装**。所有外呼走同一个 client，内置三件事：

- 连接/读取双超时（如 connect 3s、read 15s），杜绝单点挂死整个循环；
- 错误分类：可重试（timeout、429、5xx）与不可重试（4xx、协议错误）；
- 指数退避 + 随机抖动，上限 3 次，尊重 `Retry-After` 头。

```python
for attempt in range(3):
    try:
        return call_api(...)
    except RetryableError:
        sleep(min(base * 2**attempt, cap) + random())
raise ToolError(kind="transient", hint="上游暂不可用，请告知用户")
```

**第二层：给模型结构化错误**。不要把原始堆栈丢给 LLM。返回 `{status, data, hint}` 三元组，并在工具描述里明确约束："临时故障时告知用户稍后重试，禁止编造数据。" 这一句 prompt 约束比任何重试逻辑都便宜。

**第三层：熔断与降级**。同一端点连续失败 N 次后熔断，冷却窗口内直接快速失败，期间用半开探测恢复。降级路径按业务定：备用 provider、过期缓存（显式标注"数据来自缓存"）、或跳过该步骤继续主流程。

# 踩坑点

- **非幂等操作裸重试**。对支付类 POST 重试会重复扣款，必须带幂等键，或只对查询类操作开自动重试。
- **退避无抖动**。定时任务批量触发时，无 jitter 的退避会让所有实例同一时刻重试，把刚缓过来的服务再次打挂。
- **熔断粒度全局化**。一个坏端点把所有工具都熔断，应按 endpoint 隔离。
- **混淆故障层级**。MCP server 进程崩了和上游 API 挂了是两回事：前者重启进程，后者才走重试/降级，混在一起排查会很痛苦。
- **重试次数设太大**。3 次以内通常够了；重试是给瞬时抖动准备的，不是给持续性故障续命。

# 可复用建议

- 把重试、超时、熔断收敛到一个封装里，参数集中可调，别在每个工具里各写一套；
- 故障演练常态化：开发环境注入 429、超时、畸形响应，验证 Agent 的降级行为是否符合预期；
- 每次失败落日志并携带 request id，保留样本用于回放测试；
- 对用户可见的降级要显式声明，"此数据来自 10 分钟前的缓存"远好于静默换数据。

# 总结

错误恢复不是兜底代码，而是 Agent 接口设计的一部分。目标从来不是"永不失败"，而是让失败以 Agent 和用户都能正确行动的方式呈现：分类清楚、重试克制、降级诚实。做到这三点，外部 API 挂掉就只是一条告警，而不是一次事故。
