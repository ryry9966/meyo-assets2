## 背景

社区里不少人在用 OpenClaw Agent + MCP 工具做自动发帖：日报摘要、版本通告、聚合回帖。起步通常是一条 cron 定时任务，跑两周就会暴露问题：内容没硬伤，但账号的行为曲线一眼就是机器——整点发布、格式雷同、只发不读。轻则被折叠限流，重则被管理员当营销号处理。

## 问题：三种“一眼假”

1. **时间假**：cron 每 2 小时整触发，时间戳精确到秒。
2. **文本假**：同一模板、同一句式、同一结尾，连字数都稳定。
3. **行为假**：账号只有 publish 动作，没有浏览、引用、回复，交互图谱是孤立的。

节奏控制解决的就是这三件事，都是工程问题，不是玄学。

## 做法

### 1. 调度层：加权抖动 + 活跃窗口

别用均匀随机，均匀分布依然规整。建议“基准间隔 × 随机因子”，且因子向短间隔偏斜（如 `rand()**2`），偶尔留出长空窗——人类发帖本来就是簇状的。再把发布压进社区时区的活跃窗口，我的配置长这样：

```yaml
cadence:
  window: "09:00-23:00"   # 社区时区
  base_interval_min: 90
  jitter: weighted        # 短间隔为主，偶发长间隔
  daily_cap: 5            # 含回复
```

### 2. 内容层：结构可变，内核稳定

- 模板拆成开头 / 正文 / 收尾三段，各备 3–5 个变体随机组合；
- 采样温度提到 1.0 上下，few-shot 里放几条真人帖子做锚；
- 砍掉一切固定物：签名、固定 hashtag、固定 emoji、固定字数；
- 长度主动分层：有的日子只发两句话的短讯。

### 3. 行为层：读 > 评 > 发

发布前先有 fetch 动作，并按比例约束：每发 1 帖，至少 3 次抓取、1 条针对性回复（引用具体内容，不写“说得好”）。孤立的发布动作是最容易被识别的特征。

### 4. 监控层：账本 + 熔断

每条发布写进 SQLite/JSONL：时间、频道、长度、24h 互动数。互动中位数持续下滑或出现折叠/举报，自动降频到一半；连续两天异常就暂停，转人工处理。

## 踩坑点

- **服务器时区是 UTC**：不处理时区，帖子全落在北京时间凌晨，比整点更假。
- **过度随机**：为了“自然”让帖子落到凌晨两点，反而更可疑。窗口约束的优先级高于抖动。
- **重试风暴**：发布 API 返回 429 后立刻重试，直接触发封禁。用指数退避加抖动，重试上限 2 次。
- **温度调太高**：内容开始跑题。1.0 附近加严格结构约束，比单纯降温更稳。

## 可复用建议

- 调度、生成、发布三个模块分离，各自独立限速，别写在一个循环里；
- 发布账本是底线，所有节奏判断都从账本回看，不靠感觉；
- 新账号前 20 条全部人工过审，之后保持 10% 抽检；
- 节奏全部配置化，不同平台不同窗口，不要硬编码。

## 总结

节奏控制的本质不是伪装，而是把发布频率压到社区可承受的范围、把“广播”变成“参与”。自检标准只有一条：这条帖子如果由你手动发出，你自己会不会觉得打扰？会，就说明节奏还没调对。
