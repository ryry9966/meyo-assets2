## 背景

写 OpenClaw 插件或 Skill 时，凡是让模型"返回 JSON"的场景——工具路由、参数抽取、批处理流水线的中间格式——都会撞上同一个现实：**你要求的格式，和模型实际给的格式，从来不是同一个东西。**

提示词里明明写了"只输出 JSON"，实际拿到的可能是：

- ` ```json ` 围栏包裹的（多数情况）
- 裸 JSON，前面还挂着一句"好的，以下是结果："
- 三个代码块，前两个是它推理时自带的示例
- 全角标点、中文引号、尾逗号
- 流式场景下截断的半截对象

## 问题

裸 `json.loads()` 在真实流量下的失败率远比 demo 里高。而在 Agent 链路里，解析失败不只是报个错：Skill 中断、MCP 工具拿到空参数、自动化任务静默跳过。更常见的翻车姿势是上线时只用一条正则提取代码块，跑几天后死在各种边缘 case 上。

防御性解析的目标不是"让模型听话"，而是**承认输出不可控，用分层降级把成功率抬上去**。

## 做法：五层解析链

把解析收敛成单一入口函数，按成本从低到高逐层尝试：

```python
import json, re

FENCE_RE = re.compile(r"```(?:json)?\s*(.*?)```", re.DOTALL)

def parse_llm_json(raw: str):
    s = raw.strip().lstrip("\ufeff")
    # L1: 直接解析
    try:
        return json.loads(s)
    except Exception:
        pass
    # L2: 代码围栏，优先取最后一个（模型常先给示例后给答案）
    for block in reversed(FENCE_RE.findall(s)):
        try:
            return json.loads(block.strip())
        except Exception:
            continue
    # L3: 无围栏，从首个 { 或 [ 做括号配平
    for i, ch in enumerate(s):
        if ch in "{[":
            frag = _balanced(s, i)
            if frag:
                try:
                    return json.loads(_repair(frag))
                except Exception:
                    continue
    raise ValueError(f"unparseable: {raw[:200]}")
```

```python
def _balanced(s, start):
    """括号配平，带字符串/转义状态机"""
    pair = {"{": "}", "[": "]"}
    depth, in_str, esc = 0, False, False
    for j in range(start, len(s)):
        c = s[j]
        if in_str:
            if esc: esc = False
            elif c == "\\": esc = True
            elif c == '"': in_str = False
        else:
            if c == '"': in_str = True
            elif c == s[start]: depth += 1
            elif c == pair[s[start]]:
                depth -= 1
                if depth == 0: return s[start:j + 1]

def _repair(s):
    """克制修复：全角标点归一 + 尾逗号"""
    s = (s.replace("\u201c", '"').replace("\u201d", '"')
          .replace("\uff0c", ",").replace("\uff1a", ":"))
    return re.sub(r",\s*([}\]])", r"\1", s)
```

四个实现要点：

1. **围栏块优先取最后一个。** 模型经常在推理过程中先写示例代码块，最终答案在最后，这比"取第一个"靠谱得多。
2. **括号配平必须带字符串状态机。** 简单的 `count('{')` 会被字符串内容里的花括号打崩。
3. **修复要克制。** 只做标点归一和尾逗号清理；解析成功不等于结束，外层必须再过 schema 校验，防止坏数据被"修"成合法但语义错误的样子。
4. **失败必须落日志。** 把 raw 原文截断后记下来，这是后续改提示词最有价值的语料。

## 踩坑点

- 非贪婪匹配 `(.*?)` 会拿到推理中的示例块而不是答案；
- `json.loads` 默认放行 `NaN`/`Infinity`（非标准 JSON），下游序列化时才炸，需要时用 `parse_constant` 拦截；
- 模型偶尔输出连续多个 JSON 对象或 NDJSON，用 `JSONDecoder.raw_decode` 循环取；
- 重试时要把具体解析错误回喂给模型，否则同样的提示词只会得到同样的脏输出；
- 高温度是格式漂移的主要来源，任务型调用把 temperature 压下来，比任何解析技巧都有效。

## 可复用建议

- **单一入口**：全项目只允许通过 `parse_llm_json` 拿数据，禁止散落的裸 `loads`；
- **源头约束优先**：模型侧支持 structured output / JSON mode 就优先用，解析链只是兜底；
- **攒回归集**：把日志里的失败样本整理成单测语料，每次改提示词或解析逻辑都跑一遍；
- **成功标准是 schema 通过**：`loads` 不抛异常不算解析成功。

## 总结

LLM 输出解析本质上是在和一个概率性接口做集成。分层降级、克制修复、校验兜底、日志反哺——这套组合不到百行代码，但能把插件和自动化链路的解析失败率压掉一个量级。别在提示词里跟格式死磕，把力气花在防御上。
