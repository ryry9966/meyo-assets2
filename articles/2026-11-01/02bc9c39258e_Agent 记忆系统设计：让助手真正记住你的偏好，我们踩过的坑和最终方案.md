## 背景

大模型本身是无状态的，对话一结束，上下文就没了。我们在社区里写 OpenClaw 插件和 MCP 工具时，最常被问到的问题之一就是：怎么让助手记住"我喜欢简洁回复""这个项目用 pnpm 不用 npm"这类偏好，而不是每次都重新交代一遍。

我们花了几周重构自己的记忆模块，把踩过的坑和最终方案整理出来，供参考。

## 问题：三种失败模式

最初的做法很朴素：一个 memory.md，agent 判断"值得记"就往里追加。跑了一个月暴露三个问题：

1. **记了不该记的**。一次性事实（"这周在出差"）和持久偏好（"回复用中文"）混在一起，检索时互相干扰。
2. **只增不改**。偏好变了（换包管理器），旧记忆还在，模型经常被两条矛盾条目搞晕。
3. **检索噪音**。文件滚到几千行后，全量注入 token 成本失控，截断后又恰好截掉关键条目。

## 做法：分层 + 三条通路

现在的结构分三层：

- **L1 会话草稿**：当轮上下文内的临时记录，会话结束即丢弃；
- **L2 偏好档案**：几十条以内的高置信偏好，每次会话开始固定注入，控制在 300 token 内；
- **L3 事件日志**：SQLite + FTS5 存全量记忆，按需检索。

三条通路各自独立：

**写入**：通过 MCP 暴露 `memory_write` 工具，强制带字段：`type`（preference / fact / event）、`scope`（global / project:path）、`confidence`、`supersedes`。用廉价模型在会话结束时批量提取候选记忆，持久偏好需用户确认后才进 L2。

**读取**：会话开始注入 L2；对话中遇到相关问题时用嵌入检索 L3，按 `相似度 × 0.6 + 置信度 × 0.25 + 时间衰减 × 0.15` 打分。命中必须带 memory id，方便用户说"第 3 条不对"。

**更新**：不物理删除，新条目通过 `supersedes` 指向旧条目并标记废弃。冲突规则很简单：scope 更具体的赢，同 scope 则新的赢。每周跑一次合并任务，收拢语义重复的条目。

## 踩坑点

- **嵌入模型对中文不友好**。换成中文优化过的嵌入模型后召回明显变好，之前中文 query 检英文记忆基本靠运气。
- **scope 不设就会跨项目污染**。"用 pnpm"是项目级偏好，不是全局的，这条我们吃过亏。
- **全量注入是慢性毒药**。L2 一开始放得宽，两个月涨到 2000 token，压回 300 后体感没变差。
- **"忘掉这条"必须能用**。记忆可编辑比记忆准确更重要，用户有掌控感才敢让它记。
- **敏感信息默认不写**。密钥、住址这类走白名单拦截，本地存储优先。

## 可复用建议

- 别一上来就上向量库。单文件 + grep 能撑到两百条以上，先跑通写入和更新通路。
- 每条记忆必须有 type、scope、confidence、supersedes 四个字段，缺哪个后面都要补课。
- 写入从严、读取从宽：值得持久化的偏好，宁可多问一句确认。
- 留一套固定验收用例（"它还记得我用 pnpm 吗"），每次改动跑一遍。记忆回归比想象中容易坏。

## 总结

记忆系统的难点不在存储，在治理：什么该记、记到哪层、怎么作废。我们的经验是把写入做得克制、更新做得显式、读取做得可溯源。先从单文件加字段约束起步，等检索真正成为瓶颈再引入向量方案——多数个人助手场景，走不到那一步。
