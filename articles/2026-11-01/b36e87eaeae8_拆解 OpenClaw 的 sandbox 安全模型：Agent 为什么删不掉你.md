## 背景

OpenClaw 的 Agent 默认拿到 shell 和文件读写工具，能自己跑构建、改配置、清理目录。能力越强，"手滑"的代价越高：一条拼错的 `rm -rf`，或一次对"清理一下构建产物"的理解偏差，足以让工作区报废。所以在 OpenClaw 里，sandbox 不是锦上添花，而是敢把任务交给 Agent 自动跑的前提。

## 问题：误删是怎么发生的

复盘实际案例，误删几乎不来自"Agent 变坏了"，而是三类工程失误：

1. **路径解析错位**：模型把相对路径拼错，或把 `~` 当字面量处理，操作落到意料之外的目录；
2. **通配符扩大伤害面**：`rm build/*` 经 shell 展开后范围失控；
3. **间接执行**：Agent 自己写了个清理脚本再运行它，危险命令藏在脚本里，只盯对话流根本拦不住。

只靠 prompt 约束（"请小心删除"）等于没有防线，必须做成结构化的沙箱模型。

## 做法：四层防御

**第一层：文件系统 jail。** Agent 的所有文件工具以 workspace 为虚拟根，进程跑在容器/namespace 里，宿主机目录默认不可见。需要外部数据用只读 bind mount 挂进来；可写区域只有 workspace 和一块 tmpfs，会话结束即丢弃。

**第二层：工具层路径校验。** MCP 文件工具执行前先对路径做 `realpath` 解析，再校验前缀是否仍在 workspace 内。这一步专治符号链接：即使 workspace 里有个指向 `~/Documents` 的软链，解析后越界照样拒绝。

**第三层：策略与确认。** 删除类操作（命中 denylist 的 `rm -rf`、`git clean`、递归覆盖等）不直接执行，而是进确认队列等人工放行；低风险操作走 allowlist 静默通过。注意 denylist 只是兜底，不是唯一防线。

**第四层：自动快照。** 任何批量写入前，框架强制在 workspace 里打一个 git checkpoint。即使前三层全失守，`git reset --hard` 一分钟恢复。这一层是敢放手自动化的心理基础。

## 踩坑点

- **只做字符串前缀校验必被软链绕过**，务必 realpath 之后判断；
- **denylist 匹配的是命令原文**，通配符在 shell 展开后实际参数已变形，别指望它精确拦截；
- **挂载 docker.sock 等于放弃隔离**：容器内能操控宿主 Docker，jail 形同虚设；
- **不要随手提权**：Agent 在沙箱里找不到依赖时会"申请权限"，正确做法是把它需要的路径显式只读挂进去，而不是拆掉边界；
- **平台差异**：不同宿主的沙箱机制成熟度差别很大，跨平台团队直接统一容器化最省心。

## 可复用建议

1. 默认最小权限，按任务临时授予、会话结束回收；
2. 快照由框架强制触发，不要指望 Agent"记得备份"；
3. 审计日志（谁、何时、动了什么、被谁批准）单独落盘且只读；
4. 上线前做一次红队自测：让 Agent 故意 `rm -rf /`、建软链越界、写脚本间接删除，逐层验证真的拦得住。

## 总结

OpenClaw 的答案是分层防御：jail 圈定物理边界，工具层校验路径合法性，策略层把高危操作交还给人，快照层保证任何错误可逆。单看每一层都有绕过方式，但叠加之后攻击成本高到不现实。所谓"Agent 不会误删文件"，真相不是模型变可靠了，而是整个系统从一开始就假设它会犯错。
