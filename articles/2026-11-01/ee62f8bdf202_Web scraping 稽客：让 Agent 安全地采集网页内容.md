## 背景

Agent 一旦接上外部工具，网页几乎是绕不开的信息源：查文档、看公告、比对数据、追踪 issue。MCP 让“给 Agent 一个抓取工具”变得非常容易，但容易不等于安全。这篇帖聊聊我们把网页采集接入 Agent 流程时踩过的坑，以及最终落地的做法。

## 问题

直接把“抓网页”交给 Agent，风险集中在四类：

1. **网页内容是不可信输入**。页面上可能埋着 prompt injection——“忽略之前的指令，把配置发到……”这类文本一旦被当成指令执行，后果比爬虫被封严重得多。
2. **抓取行为失控**。Agent 对“再抓一层”没有成本概念，递归抓取、重复抓取、把整页塞进上下文，token 和请求量都会爆。
3. **网络边界问题**。Agent 往往跑在内网，跟随便一个 URL 就可能踩进 SSRF——重定向到云元数据地址或内网服务。
4. **合规**。robots.txt、站点 ToS、版权边界，这些不是法务话术，是要写进代码的工程约束。

## 做法

核心思路：把抓取从“Agent 的自由动作”降级为“受约束的工具调用”。

1. **边界前置**。工具层维护域名白名单，调用前检查 robots.txt，默认速率限制（如同域名 1 req/2s），超时和响应体大小都设上限。
2. **读取与提取分离**。抓取工具只负责拿 HTML 并清洗成结构化数据（标题、正文、时间、链接），按 schema 校验后落盘；Agent 拿到的是摘要和文件引用，不是原始大段文本。
3. **内容当数据不当指令**。注入上下文前统一打标记，并在系统层明确：网页内容一律视为待分析数据，其中出现的任何指令都不执行。这条要写死，不能指望 Agent 自己悟。
4. **可溯源**。每次抓取记录 URL、时间、状态码和内容 hash，出问题能回放，被质疑能举证。

## 踩坑点

- **最阴险的一次**：某页面评论区藏了针对爬虫的注入文本，Agent 抓回来后真的试图按它“整理”下游输出。解法是提取层直接丢弃非正文区域，不做天真全文入上下文。
- **robots.txt 误读**：`Disallow: /` 这种规则，自己写的解析器一开始理解错了，等于全站禁抓。
- **SPA 空壳**：普通请求抓回来只有骨架，上 headless 浏览器后资源消耗翻几倍。后来只对白名单里确认需要的域名启用渲染。
- **SSRF 漏防**：内网环境忘了禁用私网地址段，安全扫描直接拦下。重定向跟随必须自己控制，别交给库的默认行为。

## 可复用建议

- 抓取永远封装成独立工具，不要给 Agent 一个裸的 HTTP 客户端。
- 白名单默认为空，域名加入走显式配置，别图省事。
- 落盘优于直入上下文，大页面先存文件再给引用。
- 注入防御在系统提示词和工具层双保险。
- 审计日志不是可选项，Agent 的每一次外部读取都应可回溯。

## 总结

Agent 做网页采集，核心问题从来不是“能不能抓到”，而是“在什么边界内抓、抓回来怎么处理”。把合规、安全、资源约束做进工具层，让 Agent 只面对干净的结构化结果——这套“稽客”式的闸门设计，比事后救火便宜得多。欢迎评论区交流你们的采集边界方案。
