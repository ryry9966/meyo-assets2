## 背景

用 OpenClaw 跑长任务后有个明显变化：agent 会连续改几十个文件。如果每一步都等我手动 commit，任务节奏就断了；如果放任它裸跑 `git` 命令，又出过几次吓人的操作。折腾两个月后，现在 agent 的提交和分支管理基本不用我管。核心思路一句话：**能力放给 agent，边界写进脚本**。

## 问题

直接让 agent 操作 git，踩过的坑大致四类：

1. 提交信息瞎编：agent 描述的是“它以为改了什么”，和实际 diff 对不上；
2. 危险操作：`push --force`、直接在 main 上 commit、`reset --hard` 丢工作区；
3. 误提交 `.env`、构建产物；
4. 多个会话同时操作同一个仓库，互相踩。

## 做法

**第一步：约定提交规范。** 在 agent 常驻指令里写死：遵循 Conventional Commits；commit 前必须先读 `git diff`；信息只写“为什么改”，不写“改了哪些文件”。措辞要用“必须/禁止”，泛泛的“建议规范”agent 不会稳定遵守。

**第二步：用包装脚本收权。** agent 不直接调 git，而是调一个 `safe_git.sh`，内部维护 deny list：拦截 `push --force`、`push main`、`commit -n`、`add -A`（要求显式路径），每次调用追加到日志文件便于回溯。这是整套方案里收益最大的一步。

**第三步：分支生命周期模板化。** 每个任务开始时，agent 按 `agent/<任务slug>` 建分支，阶段性 checkpoint 用 `feat:`/`chore:` 前缀提交，任务结束开 PR，合并后由它清理本地分支。命名统一后，`git branch --list 'agent/*'` 一条命令就能盘点所有 agent 产物。

**第四步：校验交给 hook，不交给自觉。** pre-commit 挂 lint + 密钥扫描，违规直接拒绝，agent 收到报错会自己修正。不要指望提示词解决所有问题，hook 是兜底。

## 踩坑点

- **commit 信息幻觉**：即便要求先读 diff，偶尔仍会夸大。加一条硬规则：信息里的每个名词必须能在 diff 中找到，不符就重写。
- **改写已推送历史**：agent 很喜欢 `commit --amend`，分支一旦已推送，amend 就是制造冲突。deny list 对已推送分支禁用 `amend`/`rebase`。
- **并发冲突**：两个会话同时切分支会互相干扰。改用 `git worktree`，每任务一个独立工作目录，冲突归零。
- **提交粒度失控**：要么一次塞几十个文件，要么一行一个 commit。给个锚点：一个逻辑变更一个 commit，diff 超 300 行必须拆。

## 可复用建议

- 把 `safe_git.sh` + 指令模板打包成 skill，按仓库传参（deny list 可覆盖），新仓库接入一分钟搞定；
- 高风险操作（删分支、push）保留人工确认；提供 dry-run 模式，让 agent 先输出“打算执行的命令”再执行；
- deny list 宁可一开始太严，跑顺了再放开；反过来补漏会很痛。

## 总结

Agent 管 Git 的价值不在省几条命令，而在于让长任务有了清晰的存档点和可回滚路径。关键是把所有“不要做什么”固化成脚本和 hook，而不是写进提示词祈祷它听话。护栏是代码，自动化才敢真开。
