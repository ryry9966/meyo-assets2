## 背景

OpenClaw 的 agent 跑久了，memory 里会积累大量条目：部署记录、会议结论、用户偏好、踩坑笔记。`memory_recall` 是 agent 主动查记忆的工具，它的检索质量直接决定 agent 是"记得住事"还是"一本正经地编"。

我的场景是一个长期运行的个人助理 agent，memory 目录约三百条 Markdown 笔记。最初用全文搜索，后来换成 embedding 语义检索，结果两边都有翻车现场，这篇把实测结论整理出来。

## 问题

两个引擎各自暴露了典型盲区：

- **全文搜索翻车**：用户问"上次部署踩的那个坑"，原文写的是"v2.3.1 发布回滚记录"，字面零重叠，检索不到。
- **语义搜索翻车**：用户问"v2.3.1 的回滚命令是什么"，返回一堆"语义上差不多"的部署笔记，唯一包含精确版本号的最相关条目反而排到后面。

结论先行：这不是二选一的问题，而是**分工问题**。

## 做法与步骤

1. **先建评测集**：从真实对话日志里捞 20~30 条查询，标注每条的期望命中条目。不要拍脑袋造查询，造出来的分布和真实使用差很远。
2. **两路并行**：全文搜索用 SQLite FTS5（中文必须换分词器，后面细说），语义检索用本地向量库 + 中文 embedding 模型（bge 系列即可，不必上 API）。
3. **量化对比**：跑 recall@5，人工核对命中率。我的数据大致是：含版本号/报错码/路径的查询，关键词路 recall 高出语义路约 30%；意译类、口语化查询则反过来。
4. **上混合检索**：两路各取 top-k，用 RRF（倒数排名融合）合并分数，含精确标识符的查询给关键词路额外加权。伪代码十行以内，不值得引入重依赖。

## 踩坑点

- **FTS5 默认分词器对中文基本无效**：整句会被当成一个 token，"看起来能用"实际召回极差。必须换 jieba 分词或 tokenizer 插件，这是全文搜索方案最大的隐形坑。
- **embedding 模型换版本后向量不兼容**，全库需重建。memory 的写入脚本要从一开始就记录模型名和版本，否则升级那天会很痛苦。
- **短查询语义漂移**：两三个词的查询，向量检索容易飘到"感觉像"的条目上。
- **两个引擎都默认"越像越好"**，但"上周说的偏好"应该比"半年前的"权重高。加一个简单的 recency 衰减因子，收益明显。
- **召回失败很难被察觉**：agent 拿不到记忆时会自己编一个。务必在 recall 结果为空时让它明确说"没找到"，并把空结果写日志。

## 可复用建议

- 先有评测集再选引擎，20 条真实查询胜过任何直觉和 benchmark。
- 默认上混合检索，纯语义或纯关键词都有明确盲区。
- **memory 条目本身的写法比检索参数更重要**：一条一事、带日期、带标签，检索调优的边际收益远不如把记忆写干净。
- 粗略分工：精确标识符（版本号、路径、ID、报错码）信关键词；意译、口语、模糊描述信语义。
- 定期回看 recall 空结果日志，那里就是你 memory 该补的洞。

## 总结

语义搜索解决"换个说法还能找到"，全文搜索解决"逐字精确命中"。混合检索 + 时间衰减 + 空结果透明化，才是 `memory_recall` 的稳妥形态。别迷信向量库，也别低估关键词——工程上没有万能检索，只有分工明确的检索。
