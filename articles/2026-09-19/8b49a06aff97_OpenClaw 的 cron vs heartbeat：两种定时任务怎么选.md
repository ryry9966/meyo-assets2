## 背景

OpenClaw 的 agent 有两种“到点干活”的机制：cron job 和 heartbeat。两者都能定时，于是很多人第一反应是“随便用一个”。结果常见三类症状：token 账单莫名偏高、整点任务不准时、agent 每半小时发一条“一切正常”。这篇帖把机制差异、选型判据和踩过的坑整理一下。

## 先分清机制

**cron**：你定义一个 cron 表达式（支持显式时区），到点后 gateway 把一个固定 prompt 投递到指定会话，结果可回投到某个渠道。触发是确定性的——几点几分、执行什么，都是你写死的。

**heartbeat**：agent 按固定间隔（默认 30 分钟）自唤醒一次，读取工作区的 HEARTBEAT.md，自行判断“有没有事要做”。没事就回约定信号保持安静，有事才动手。

一句话总结：cron 是“到点执行你写好的指令”，heartbeat 是“定时自查你留的巡检清单”。

## 选型判据

| 需求 | 选哪个 |
|---|---|
| 每天 08:30 发日报 | cron |
| 收件箱 / 日历巡检 | heartbeat |
| 精确到分钟的动作 | cron |
| 价格低于阈值才提醒（低频） | heartbeat |
| 同类监控但高频（分钟级） | cron 跑脚本判断，别用 LLM |
| 顺手做的日常维护 | heartbeat |

核心两条：

1. **时间本身是不是需求？** 是 → cron。
2. **是不是“多数时候没事”？** 是 → heartbeat；如果每次醒来都有活干，或频率很高 → cron。

## 实操要点

**cron 侧：**
1. 定义任务时写全四件事：表达式、时区、会话目标（isolated 隔离会话还是 main 主会话）、结果投递渠道。
2. 输出长、噪音大的任务用 isolated 会话，避免污染主会话上下文。
3. 一次性任务用一次性调度，跑完自动禁用，别留尸体。

**heartbeat 侧：**
1. HEARTBEAT.md 保持短，写成检查项，每项一句“什么情况才算有事”。
2. 明确写上“没事就回约定信号、不发消息”，否则它会礼貌地每半小时汇报一次。
3. 重活留给 cron 或手动触发，心跳只做判断和轻量动作。

## 踩坑点

1. **时区**：cron 默认按 gateway 主机时区算，容器里往往是 UTC，“早八”变“下午四点”。显式写时区，别赌。
2. **心跳间隔调太密**：每次唤醒都是一次 LLM 调用，5 分钟一醒，月底账单会教育你。
3. **HEARTBEAT.md 越写越长**：每次心跳都要全量读取并推理，清单越长单次成本越高，定期删过时项。
4. **心跳跑在主会话**：会读也会写主会话历史。敏感或重任务放 cron 的 isolated 会话。
5. **设备休眠 / 网关没起**：两种机制都会漏跑。对“必须不漏”的任务，外面套一层系统级监控兜底。
6. **用 cron 硬编码条件逻辑**：在 prompt 里写“每天检查 XX，有变化再说”，条件分支你永远写不全，agent 会自由发挥。这类“条件触发”本质是 heartbeat 的活。

## 可复用建议

- 心智模型：**cron 管日程表，heartbeat 管巡检表**。
- 新任务先问三问：几点做？做什么？没事怎么办？答案是“固定时间 / 固定动作 / 无所谓”→ cron；答案是“不定时 / 看状态 / 通常没事”→ heartbeat。
- 两者可组合：heartbeat 只负责发现异常并在主会话留一条提醒，重处理交给 cron 或人工确认后触发。
- 上线后跑一周，看三个指标：触发次数、token 消耗、打扰次数，再回头调间隔和清单。

## 总结

不要把 heartbeat 当免费 cron 用，也不要用 cron 表达式硬编码状态判断。时间驱动选 cron，状态驱动选 heartbeat；精确、高频、成本敏感 → cron；低频、条件式、允许安静 → heartbeat。配好后看日志调参，比一开始就追求“完美配置”务实得多。
