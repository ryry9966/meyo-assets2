## 背景

最近接了一个多仓库文档迁移的活：四十多个模块的 README 要统一重写成新格式，还要逐个检查失效链接。一开始用单个 Agent 串行跑，到第八个模块时上下文已经塞满，前面读过的规范它开始"记混"，输出质量明显下滑；而且整体预计要跑六七个小时，中途一次 API 超时就得从头再来。

于是把任务改造成 subagent 编排：主 Agent 只负责拆任务和收结果，具体干活交给一批并行的子 Agent。跑通之后把经验整理出来，供大家参考。

## 单 Agent 的三个瓶颈

1. **上下文污染**：所有中间产物堆在同一个上下文里，任务越多，主 Agent 越"健忘"。
2. **串行慢**：子任务之间明明没有依赖，却只能排队。
3. **失败成本高**：长任务没有检查点，一步出错全部重来。

## 做法：四步编排

**第一步：拆任务，划边界。** 让主 Agent 先输出任务清单，每个子任务必须满足：输入是显式传入的文件列表，输出是固定结构的 JSON，且不与其他子任务写同一个文件。独立性是并行的前提，这步不能省。

**第二步：定义子 Agent。** 每个子 Agent 一个独立上下文、精简的工具集、一段短 prompt。比如文档迁移里，子 Agent 只拿到本模块的源文件路径、格式规范、输出 schema，不需要知道全局任务长什么样。

**第三步：受控并行。** 并发不是越大越好。用信号量把并发压在 3~4，既避开 API 限流，也控制成本。伪代码大致是：

```text
tasks   = planner.decompose(goal)
results = pool.map(worker.run, tasks, concurrency=4)
final   = planner.merge(results)
```

**第四步：结构化汇总。** 子 Agent 输出强制过 schema 校验，不合规重试一次，两次不过降级为串行人工处理。主 Agent 拿到的永远是干净的结构化结果，而不是一大段自由文本。

## 踩坑点

- **假独立**：两个子 Agent 各自要更新同一个索引文件，并行跑直接互相覆盖。后来把"写索引"拆成汇总阶段的串行任务才解决。共享写操作必须剥离出来。
- **输出跑偏**：早期没做 schema 校验，有子 Agent 返回带解释的长文，主 Agent 解析失败。校验加重试是刚需。
- **静默失败**：某个子 Agent 超时返回空结果，主 Agent 误以为"该模块无需修改"。后来给每个子任务加了显式 status 字段（done / failed / skipped），failed 必须带原因。
- **过度编排**：有一次只有三个小任务，拆分加汇总的开销比直接干完还大，token 还多花一倍。任务少于三四个、或子任务强依赖时，别硬上并行。

## 可复用建议

1. 先串行验证拆分逻辑，再开并行。拆错了，并行只是把错误放大 N 倍。
2. 子 Agent 遵循"窄输入、窄输出"：只给完成任务所需的最小上下文，只要求结构化输出。
3. 并发数、超时、重试次数全部做成配置，别写死。
4. 每个子 Agent 的输入输出落盘留日志，排查问题时这是唯一救命的东西。
5. 成本预估先行：并行不减少 token 消耗，只缩短时间，先算账再开跑。

## 总结

Subagent 编排的核心不是"Agent 越多越强"，而是**边界划分**：任务边界清晰、写操作不冲突、输出格式可校验，并行才有意义。改造后同样规模的迁移从六七小时压到一个半小时左右，中途失败只需重跑单个子任务。如果你的场景里有一批彼此独立、重复劳动的子任务，这套模式值得试一次；反之，一个足够好的单 Agent 往往就是最优解。
