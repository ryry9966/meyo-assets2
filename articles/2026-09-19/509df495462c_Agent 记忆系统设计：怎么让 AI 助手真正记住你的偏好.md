## 背景

LLM 本身无状态。每次会话结束，上下文清零，用户偏好——代码风格、回复详略、常用工具链、项目约定——全部丢失，用户只能反复交代。对 OpenClaw 这类常驻本地 Agent 来说这个问题更刺眼：它理应"越用越懂你"，但默认什么都不记。

## 问题：存下来 ≠ 记得住

三种常见天真做法都会失败：

1. **全塞进 system prompt**：上下文膨胀，成本线性涨，旧偏好和新指令互相打架。
2. **会话结束后做摘要**：有损压缩，细节漂移，摘要本身越滚越长。
3. **只上向量库**：语义相似 ≠ 当前任务相关，检索回来经常是噪音。

真正的核心矛盾是三件事：**写什么**（捕获策略）、**读什么**（注入策略）、**怎么失效**（生命周期）。这是个工程问题，不是模型问题。

## 做法：分层记忆 + 独立读写通道

我目前跑的方案分三层：

- **核心档案（profile）**：结构化 key-value，如语言偏好、时区、代码风格。控制在 300 token 内，每次会话无条件注入。
- **情景笔记（episodic）**：会话结束时由模型抽取候选记忆，人工确认后写入，带时间戳和来源。
- **长尾知识（semantic）**：向量库，只在相关性高的任务里按 top-k 检索，设硬性 token 预算（≤500）。

写入侧封装成一组 MCP 工具：`memory_write` / `memory_search` / `memory_list` / `memory_delete`，Agent 按需调用，宿主无关。每条记忆固定五个字段：**内容、来源、时间戳、置信度、作用域**（用户级/项目级）。

冲突处理用"新覆盖旧 + 保留历史版本"，不要简单 append。用户说"改用 Go 了"，旧记录应标记过期而不是删除。

## 踩坑点

1. **过度捕获**。模型倾向于连寒暄都存，一周后检索全是垃圾。给抽取步骤设高门槛：只存可复用、会影响未来行为的偏好。
2. **记忆是注入通道**。存进去的内容会被读回上下文，用户粘贴的文档里可能夹带指令。读回时用引用块包裹并标注来源，别让它和系统指令平权。
3. **旧记忆绑架新任务**。Agent 会过度信任"他喜欢简洁回复"，但用户这次要详细报告。提供会话级覆盖规则：**明确指令 > 检索记忆**。
4. **没有遗忘机制**。只进不出的记忆库半年后基本不可用，至少要有 TTL 或置信度衰减。
5. **对用户不可见**。看不到 Agent 记了什么，就不会有人信任它。`memory_list` 加一键删除，既是功能也是底线。

## 可复用建议

- 别一上来就上向量库。一个结构化 profile 文件 + 一个笔记文件，能解决 70% 的问题。
- 注入预算是硬约束：核心档案 + 检索结果合计不超过 800 token。
- 验证用回放法：同一批任务，开/关记忆各跑一遍对比差异，避免"感觉变好了"。
- 字段设计第一天就定好（含作用域和来源），后补迁移非常痛苦。

## 总结

让 Agent 记住偏好，难点不在存储，而在**写入门槛、读取预算、失效策略**这三件工程事。先做小而硬的结构化档案，确认瓶颈后再加语义检索，并且始终让用户能看到、能删掉被记住的一切。记忆系统做对了，Agent 才算从"工具"变成"搭档"。
