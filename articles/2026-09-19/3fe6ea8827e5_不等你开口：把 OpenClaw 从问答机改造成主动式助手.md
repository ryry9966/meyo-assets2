## 背景

大多数人对 AI 助手的使用还停留在"拉"模式：我提问，它回答，会话结束就归零。但真正耗时间的场景往往是"事情发生了，而你不知道"——CI 凌晨挂了、PR 闲置三天没人看、磁盘快满了、某封邮件等你拍板。这类事的特点是：等你想起来去问的时候，最佳处理时机已经过了。

OpenClaw 这类常驻型 agent 框架的价值恰恰在这里：它跑在你自己的机器上，24 小时在线，有工具、有记忆、有投递通道（Telegram/WhatsApp 等），天然适合从"问答机"升级成"主动式助手"。所谓 proactive，拆开看就是三件事：**可靠的触发器、靠谱的判断策略、有边界的执行**。

## 问题

真正动手做之后会发现，难点不是"怎么让它动起来"，而是三个更具体的工程问题：

1. 触发源怎么组织？定时任务、事件回调、周期巡检，三套机制各自为政很快失控。
2. 判断谁来做？传统方案是 cron + webhook 直接推 IM，但它没有判断力——不能汇总、不能分轻重、更不能顺手做后续动作。
3. 无人监督时，权限边界画在哪？

## 做法

我落地的是一个分层结构：

**第一层：心跳巡检（heartbeat）。** OpenClaw 支持agent 周期性自我唤醒（默认约 30 分钟，间隔和活跃时段可调，参数名以所用版本文档为准）。在 workspace 的 `HEARTBEAT.md` 里写巡检清单，每次唤醒 agent 读清单、通过按需挂载的 MCP 工具（GitHub、文件系统等）检查状态，然后决定：汇报，还是静默。关键设计是"无事不扰"——没有值得说的事就直接结束，不给用户发消息。

**第二层：定时任务（cron job）。** 日报、周报、固定时间段的批量检查交给 cron。要点是给每个任务隔离 session、写清输出格式和投递目标，让"定时产出"和"日常对话"互不污染。

**第三层：事件触发。** 对时效性高的事件（CI 失败、重要邮件到达），用轻量脚本接 webhook，把事件写入约定的队列文件，由心跳或独立短任务消费。不要每个事件源单独拉一条链路。

**判断策略：把分级规则写进清单文件，当成代码维护。** 例如：主分支 CI 挂了 → 立即通知；PR 收到 review 意见 → 记入晚间日报；磁盘使用率 > 85% → 立即通知；其余 → 只写日志。

另外，主动能力不等于只发通知。更好的形态是"通知 + 预处理"：报告 CI 挂了的同时附上失败日志摘要和初步归因；发现邮件待回复时先起草好回稿，等你一句话确认。

## 踩坑点

1. **心跳成本被低估。** 每次唤醒都是一次带完整工具定义的 LLM 调用。把间隔调到 5 分钟之前，先算清日调用量；挂载的工具按需最小化，工具定义本身就是上下文开销。
2. **"过度热情"问题。** agent 倾向于每次唤醒都汇报点什么来证明自己在工作，结果变成狼来了。必须在清单里显式写明"无事则静默"，并利用框架的静默机制。
3. **自我触发循环。** 主动消息 → 你回复 → 又生成新任务 → 再发消息。把主动行为放在隔离 session，并限制单次主动行为的后续动作数量。
4. **状态不持久导致重复报告。** 心跳唤醒默认无状态，agent 不记得上次查到哪。把游标（上次检查的 commit、已处理的 alert id）写进文件，作为下次唤醒的输入。
5. **写操作没有闸门。** 凌晨自动给你同事发消息、顺手创建 issue，这类事出一次就够记一辈子。所有对外或破坏性写操作，要么白名单，要么走"先草稿、后确认"。

## 可复用建议

- 先跑两周"观察模式"：所有判断只写日志、不投递，统计误报率后再放开通知。
- 触发器、判断规则、状态游标全部进 git，像改代码一样提 PR 维护它们。
- 每个巡检项写清停止条件和输出格式，避免开放式指令。
- 心跳上下文尽量精简，不要把全部长期记忆塞进去。

## 总结

proactive 的本质不是"换一个更聪明的模型"，而是一个工程问题：可靠的触发器保证不漏事，分级策略保证不吵人，权限边界保证不出事。把这三件事当代码管起来，"不等你开口就把事办了"才是一种可持续的常态，而不是演示视频里的一次性魔术。
